# SWE.2 ECU Software Architecture

## 1. Overview
This document baselines the SWE.2 ECU Software Architecture. It outlines the software components, interfaces, static and dynamic behavior, scheduling/concurrency models, and failure behavior. It allocates software requirements (SWE.1) to these components and verifies completeness.

## 2. Software Architecture Components
The ECU software is partitioned into the following high-level components:
* **SW-CORE (Core Operating System & Schedulers):** Manages task scheduling, memory protection (MPU), and inter-process communication (IPC).
* **SW-DRV (Hardware Abstraction & Drivers):** Encapsulates the microcontroller peripherals (ADC, PWM, CAN, LIN, Ethernet) and provides hardware-agnostic interfaces.
* **SW-NET (Network & Gateway Services):** Handles diagnostic routing, CAN-FD/Ethernet switching, SecOC (Secure Onboard Communication), and UDS protocol.
* **SW-APP (Application Layer):** Contains the control algorithms, ML inference integration, and application-specific diagnostic monitors.
* **SW-SAFE (Safety & Diagnostics):** Implements ASIL B/D safety mechanisms, watchdog management, and the Diagnostic Event Manager (DEM).

## 3. Interfaces & Static/Dynamic Behavior
* **Internal Interfaces:** Standardized IPC channels for SW-APP to communicate with SW-NET. Strict client-server model implemented via RTE (Runtime Environment) abstraction.
* **External Interfaces:** Sensor data ingested via SW-DRV, forwarded to SW-APP. Actuator commands generated by SW-APP are validated by SW-SAFE before transmission via SW-DRV.
* **Scheduling/Concurrency:** Priority-based preemptive scheduling. SW-SAFE runs at highest priority (1ms task), SW-APP runs at 10ms and 50ms intervals. Resource contention is avoided via lock-free buffers.
* **Hardware Constraints:** Flash memory limited to 4MB, RAM to 1MB. CPU load max target is 75% at peak operations.

## 4. Failure Behavior & Variants
* **Failure Modes:** In case of ML-Detect timeout, SW-APP falls back to rule-based fallback control. SW-SAFE triggers a safe state (limp-home mode) if SW-CORE detects a timing violation (deadline miss).
* **Variants:** HW-ECU-RevA and HW-ECU-RevB are supported via calibration parameter selection at startup (no separate binaries).

## 5. Requirement Allocation & Traceability
All applicable SWE.1 requirements (REQ-SWE1-01 to REQ-SWE1-140) have been allocated to the architectural components.
* **Completeness:** 100% of SWE.1 requirements are mapped.
* **Consistency:** Bidirectional traceability is retained in the `SWE2-ARCH-TRACE-20260912` matrix.
* **Evaluation:** Alternatives evaluated included a symmetric multi-processing (SMP) approach, but asymmetric multi-processing (AMP) was chosen for stricter safety separation.

## 6. Approvals and Baseline
This architecture is baselined and approved for SWE.3 Detailed Design and SWE.4/SWE.5 verification planning.
