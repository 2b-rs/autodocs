   semantics, which C12 reserves for re-review — flagged deliberately rather than
   buried.

   existing leader-profile size assertion (`< 13000`). The block was compressed to
   fit rather than the budget raised, since raising an existing guard to admit new
   text is a weakening. The wording is consequently terse; if the Architect wants
   the fuller phrasing, the budget question must be decided deliberately.

## C-1 (`F-C12-01`) — merged reads now state provenance. FIXED.

The finding was correct and the defect was mine. Reads from a linked worktree returned
the committed baseline and branch-local entries as one unlabelled body of text.

`read_memory_text` now renders a merged read as two labelled sections:

    ### shared baseline (committed and integrated)
    ### branch-local (on this worktree's branch only; NOT yet shared -- do not
        treat as established practice)

Provenance comes from the shared checkout's `HEAD` via `committed_baseline_lines()`.
**Failure direction is deliberate:** if that resolution fails for any reason the shared
set is empty, so every entry degrades to *branch-local*. The label can under-claim that
something is shared; it cannot over-claim it. Reading from the shared checkout is
unchanged and stays unlabelled.

**Red-first evidence.** `MergedReadProvenanceTest` run against the delivered candidate's
`memory_store.py`, blob re-verified as `5864b4c89caac28e78ab1782f9e27eb61222b6c2`:
**FAILED (failures=2)** — the merged read returned
`shared practice` and `uncommitted branch note` with no section markers at all. The same
cases pass on the corrected candidate.

Adjacent cases: baseline-only read (labelled shared, no branch-local section emitted);
mixed read (both sections, shared before branch-local, each entry asserted **absent from
the other section**, not merely present in its own); shared-checkout read (unlabelled,
unchanged path).

## C-2 (`F-C12-02`) — root canary. DISCHARGED BY CONSTRUCTION, and named.

**A dedicated "root canary" fixture is unnecessary here, because the shared/primary
checkout is rejected by enumeration before any mutation can occur.**
`resolve_write_workspace()` raises `MemoryRoutingError` when the resolved worktree top
level equals the common root, and that check runs before any lock directory, parent
directory, temporary file, or memory file is created. A canary observing "the root did
not change" would be observing a path the resolver never reaches.

The enumerated rejections proving this are
`MemoryWorkspaceRoutingTest.test_shared_primary_checkout_rejects` and
`test_symlink_resolving_to_root_rejects` — the latter covering the case where the root is
reached under a different spelling.

**Zero-mutation canaries that do exist, named as requested:**

1. `MemoryWorkspaceRoutingTest.assert_rejected_without_mutation()` — used by all twelve
   negative cases. Captures a sha256 digest map of *every* memory file in the fixture
   before the rejected call and asserts equality after, plus absence of `logs/` and of the
   lock directory. This is a canary over the whole fixture, not only the root.
2. `GeneratedProfileMemoryRoutingTests.test_rendering_touches_no_live_profile_root` —

the start of the contract and at delivery, but not between — the wrong cadence for a timed
