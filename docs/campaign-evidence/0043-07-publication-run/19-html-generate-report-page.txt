### A false positive this session produced and is reporting rather than burying

An initial version of this check walked the whole tree and compared the mtime of
**all 4499 HTML pages** against `run_finished_at`. It reported 4072 pages as
"older than the run". **That result is wrong, and the check was wrong, not the
tree.**

Two reasons, both confirmed against the ledger entry:

1. Generation is deliberately incremental. The run reports
   `changed_targets: 0` and `unchanged_skipped: 305`: a page whose rendered
   content did not change is intentionally not rewritten, so its mtime stays
   old. Filesystem mtime is therefore not a validity signal for an unchanged
   page -- treating it as one would mark every idempotent build stale.
2. The check compared pages the cohort never claimed to build. This run's
   `html_generate` stage covers `de` and `en`; the flagged files were
   overwhelmingly `ru/`, `es/`, `fr/` and similar, produced by earlier runs and
   outside this cohort entirely.

The invariant that actually matters -- and the one the acceptance criterion
names -- is about the **published report page** being no older than the run it
reports, which is what the table above measures, and which `_src/validate.py`
enforces mechanically as firing condition (a) `stale-build-report`. That
authoritative check, not this ad hoc mtime walk, is the binding one: it compares
the page model's binding fields against the newest ledger entry rather than
guessing from timestamps. It fired correctly in stage 17 and is re-run in
stage 20.

Recorded because a discarded measurement that looked alarming is exactly the
kind of thing a reviewer should be told about by the author rather than
rediscover.
