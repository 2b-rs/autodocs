## 1. Overview & Architecture

Feature `0033` establishes a secure, deterministic, privacy-preserving, and standards-compliant review-request intake, queueing, and triage pipeline for public AUTOSAR and S-Core documentation. This dossier consolidates operator and user guidance, triage/moderation procedures, privacy/security limitations, compatibility/migration instructions, support/rollback steps, and formal release notes.

## 2. User & Operator Guidance

### 2.1 Browser Intake Modes
1. **Interactive In-Browser Dialog (`review_request.js`):**
   - Available on every eligible record/component page across all multilingual documentation trees (`en`, `de`, `fr`, `ja`, `zh`).
   - Triggered via the **Flag for review** button (`[data-review-request-open]`).
   - **Form Fields:**
     - `Category` (required): `factual-accuracy`, `outdated-source`, `missing-context`, `ai-hallucination-suspected`, or `other`.
     - `Rationale` (required): Descriptive text detailing the reason for review (minimum 2 characters, maximum 4000 characters).
     - `Evidence Section` (optional):
       - `Supporting Link`: Valid `http://` or `https://` URL (strictly disallowing `javascript:` and `data:` schemes).
       - `Quote or Note`: Free-text excerpt or specification errata citation.
   - **Review Request Confirmation Step:**
     - Clicking *Review request* validates all fields and constructs an immutable package object conforming to `review-request-package@v1` with client version `1.0.0` and an RFC 9562 compliant `UUIDv7`.
     - Displays all pinned record metadata (canonical ID, version, content hash, status, deep source URL), actor claim, category, rationale, and request ID.
     - The exact same package object and IDs are preserved and reused across Export, Submission, and retries.

2. **Submission & Export Channels:**
   - **Direct GitHub Submission (`[data-submit]`):** Sends the confirmed package payload as a structured GitHub issue using an authenticated personal access token (`ara-review-github-token-v1`).
   - **JSON Export (`[data-export]`):** Downloads a standalone `.json` file (`review-request-<timestamp>.json`) containing the exact confirmed package. To prevent unauthenticated assertion of verified authority, `actor_claim.identity_kind` is safely downgraded to `self_declared` while retaining the submitter's handle.
   - **Local Package Staging (`[data-save-local]`):** Adds the request to the browser's persistent review collection in `localStorage` (`STORE = "ara-review-package-v1"`).
   - **Editing (`[data-edit]`):** Returns the user to the input form, resetting the confirmed package so that subsequent confirmation mints a fresh validated package.

3. **No-JavaScript Intake Fallback:**
   - When JavaScript is disabled or unavailable, pages render accessible static links with pre-filled target parameters linking to public GitHub issue templates or mail intake protocols, ensuring 100% intake accessibility.

## 3. Local Storage Staging & Multi-Tab Behavior

### 3.1 Local Storage Collection (`ara-review-package-v1`)
- Review requests staged locally reside in `localStorage.getItem("ara-review-package-v1")`.
- **Discriminator:** Staged items carry an explicit discriminator:
  - Review requests: `item_kind: "review-request"`, tagged with `status: "local-only"`.
  - Curator decisions: `outcome: "accept" | "reject"`.
- **Drawer Rendering (`review.js`):**
  - Displays a distinct *Review Request* chip alongside curator decision items.
  - Subtitle explicitly marks items as `(local-only)`.
  - Item removal (`[data-remove]`) or clear-all (`[data-clear]`) removes the items cleanly.
- **Multi-Tab & Quota Constraints:**
  - `localStorage` updates emit standard `storage` events; browser drawer components re-render on active tab focus.
  - Payloads are bounded (max 50 items or 5 MB storage ceiling). Exceeding quota prompts the user to export or clear staged items.
  - **Delayed-Submit Staleness:** Local packages retain their creation timestamp and baseline content hash. If submitted long after creation against an updated record version, the server-side intake verifies baseline freshness and routes stale items to historical review.

## 4. Identity & Trust Levels

Feature `0033` strictly distinguishes four identity tiers:
1. **GitHub-Authenticated (`github_authenticated`):** Verified OAuth / fine-grained Personal Access Token against the GitHub API. Carries high trust.
2. **Self-Declared (`self_declared`):** User-supplied name/handle stored locally in `localStorage` (`ara-review-identity`). Exported JSON files always use this level.
3. **Anonymous / Reader (`anonymous-reader`):** Fallback identity when no handle is provided.
4. **Governed Automation / Pipeline (`pipeline_automation`):** Internal system actors and test harnesses.

**Token & Credential Safety:**
- Auth tokens are never serialized into exported JSON files, queue files, public URLs, or client-rendered HTML scripts.
- Tokens reside strictly in client `localStorage` under key `ara-review-github-token-v1` and are cleared on disconnect.

## 5. Triage, Moderation & Abuse Handling

### 5.1 Intake Validation & Triage Pipeline
- **Gate 1 — Strict Schema Conformance (`review_request_package.py`):**
  - Requires `schema: "review-request-package@v1"`, semver string `client_schema_version: "1.0.0"`, valid `UUIDv7`, non-empty canonical ID, valid category, and non-empty rationale.
- **Gate 2 — Target Resolution & Freshness:**
  - Verifies `target_canonical_id` against the authoritative record database.
  - Detects stale content hashes and marks items for re-curation if the record has been updated since request creation.
- **Gate 3 — Duplicate & Rate Controls (`curation_flags.py` / `review_flags.py`):**
  - Replays of identical `request_id` or same record + rationale return cached receipts.
  - Rate limiting throttles submissions exceeding threshold per IP/token.
  - Malformed or suspicious inputs are routed to a restricted quarantine queue (`_src/queue/quarantine/`) with audit logs.

### 5.2 Curator & Moderator Responsibilities
- **Moderators:** Inspect quarantined items, discard spam/abuse, and verify sender authenticity.
- **Curators:** Review valid requests in `_src/queue/active/`, inspect cited errata evidence, and record immutable `accept` or `reject` decisions.
- **Terminal Outcomes:**
  - **`accepted`:** Promotes request to candidate database modification and static regeneration.
  - **`rejected`:** Permanently closes the request without modifying factual database records or published pages.

## 6. Privacy & Data Protection (GDPR & GitHub Limitations)

1. **Data Minimization:**
   - Only requested feedback, optional evidence references, and declared handles are stored.
   - PII scrubbing filters email addresses and bearer tokens from rationale and logs.
2. **Retention Policy (`0033-07.03`):**
   - Active queue items: Retained until decision (target <= 30 days).
   - Accepted/Rejected decision records: Retained in append-only audit log for 365 days.
   - Quarantined abuse records: Retained for 90 days for forensic audit, then purged.
3. **Public GitHub Transparency Disclosure:**
   - Submitters are explicitly warned that submitting issues directly to public GitHub repositories makes the rationale and issue title public and subject to GitHub's third-party retention and terms.

## 7. Compatibility, Migration & Rollback

### 7.1 Migration from Feature 0021 / 0036
- Legacy review flags (`kind: "review_flag"`, legacy UUIDv4) are automatically migrated to `review-request-package@v1` with `legacy_migrated: true` tag upon ingestion.
- Unparseable historical records are safely placed in quarantine without halting pipeline generation.

### 7.2 Rollback & Incident Recovery Steps
1. **Disable Browser Ingestion:** Set `<meta name="review-request-enabled" content="false">` in site configuration.
2. **Revert Candidate Changes:** Execute `git revert <commit-sha>` on the affected branch.
3. **Regenerate Public Site:** Run `python3 _src/generate.py && python3 _src/validate.py`.
4. **Queue Recovery:** Active queue files are backed up in `_src/queue/.backup/` prior to any batch migration.
