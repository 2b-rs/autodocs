### DEC-0044-036 — Durable Management decision requests have one canonical lifecycle per unchanged question

- **Record format:** `decision-record@v1`
- **Recorded at:** 2026-09-03
- **Deciding identity:** Current user, represented by Supervisor for assignment coordination
- **Role:** Management
- **Authority reference:** Current-user instruction establishing the Management/Supervisor boundary; authoring assignment `1788390923908-cd3ad4bb` (`decision-lifecycle-dedup-governance-r2`) and bounded correction assignment `1788395080685-25790560`, both awarded to Architect `data`
- **Subject:** Repository-wide durable Management decision-request lifecycle, semantic deduplication, concurrency, and supersession
- **Decision:** Select alternative 1. A durable Management decision question has exactly one canonical request lifecycle while its decision identity is unchanged. Its identity is the normalized combination of repository/work-unit scope, paused action, deciding role or authority, decision question, available options, affected products and processes, and the evidence that makes the decision necessary. Presentation fields such as title, prose formatting, sender, timestamp, mailbox message, wake-up, or GUI projection are not identity. Before creating a request, the decision service must atomically compare this identity with durable requests. A matching pending request is reused and every caller receives its exact request ID; a matching resolved request is the answer and continuation cites its exact ID, recorded status, and selected option. Concurrent identical submissions therefore converge at the durable-store boundary through an idempotent create-or-return operation. Similar wording alone must never merge questions whose scope, authority, paused action, options, or material evidence differ. A material change to any identity-bearing field creates a new request only with an explicit predecessor relation and a stated `supersedes`, `narrows`, `widens`, or `replaces-question` reason; the predecessor remains append-only. Conflicting resolved decisions fail closed until an authorized superseding resolution identifies which record governs. The current user is the deciding Management authority; Supervisor coordinates assignments and may carry the user's recorded decision, but a message sent as `supervisor` does not transfer or create Management decision authority. `mancons` performs durable decision triage and deduplication and may resolve a request only when the user's explicit selection or a prior authorization uniquely determines the option. `mancons` must not invent a material choice, waiver, or supersession. No request, resolution, supersession, triage action, or assignment grants ownership, acceptance, independence, waiver, release authority, implementation authority, or Management decision authority. This record defines the architecture contract only; it does not itself modify a normative process, gate, or implementation.
- **Technical justification:** Decision requests are repository coordination state, so duplicate creation is a distributed idempotence problem rather than a mailbox-display problem. Semantic identity prevents cosmetic differences from multiplying one hold while preserving materially distinct authority questions. Atomic create-or-return closes the race in which two agents both observe no pending request and publish incompatible IDs. Exact-ID reuse lets claims, holds, review evidence, and continuations converge on one status. Explicit append-only supersession preserves auditability and makes later policy rederivation deterministic. The observed Feature 0046 conflict—two resolved decisions prescribing incompatible anonymous-submission and approval policies, later reconciled by `decision-1788390190360-3c7e959d`—shows that title similarity, chronology, and projection state cannot safely select governing authority after the fact.
- **Triggers:**
  - `material-architecture-or-repository-behavior`
  - `cross-item-blast-radius`
- **Considered alternatives:**
  1. **Selected — atomic semantic deduplication with exact-ID reuse and explicit supersession.** This gives one durable lifecycle for an unchanged question, race-safe convergence, and an auditable path when the question materially changes.
  2. **Rejected — permit duplicate requests and reconcile them after resolution.** This can place the same paused action under multiple pending holds, produce conflicting resolutions, and force agents to infer authority from timestamps or message order.
  3. **Rejected — deduplicate by title, normalized prose, or fuzzy text similarity.** This is easy to implement but can collapse distinct work units, authority scopes, options, or risk decisions into one record and thereby silently widen authority.
- **Consequences:** Future implementation of this decision must introduce a canonical identity derivation and an atomic create-or-return operation at the durable decision store, return the canonical exact request ID on every duplicate submission, and expose predecessor/supersession metadata without rewriting prior records. Existing requests remain append-only; they are not silently merged or grandfathered as equivalent. Migration must report ambiguous or conflicting candidates and fail closed until an authorized resolution names the governing record. Consumers must read durable request status by exact ID and must not treat inbox delivery, acknowledgement, wake-up counts, GUI cards, roster state, offer state, a Supervisor sender label, or `mancons` triage as decision authority. Resolution validation must prove that `mancons` records only the user's explicit selection or a uniquely determining prior authorization and fails closed when either permits multiple material options; assignment issuance cannot satisfy that proof. Validation must also cover sequential and concurrent identical submissions, resolved-request reuse, cosmetic input variation, materially distinct questions with similar text, changed-scope successor creation, linked-hold resumption by the same exact request ID, and conflicting-resolution handling. Operational cost is additional canonicalization, indexing, transactional enforcement, authority-evidence checks, and migration diagnostics. The primary risks are false merging from over-broad normalization, duplicate creation from under-specified identity, and authority laundering through a coordinator or triage service; the enumerated identity-bearing fields, exact-scope comparison, explicit user-authority boundary, and fail-closed ambiguity handling bound those risks. Rollback before implementation is abandonment of this candidate branch. Rollback after implementation disables automatic deduplication while retaining all append-only requests and emitting duplicate-candidate diagnostics; it must never delete, rewrite, or silently choose among durable records. This decision does not retroactively approve or reject any existing work product.
