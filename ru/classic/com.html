Системная архитектура и роль кластера модулей

Службы Communication Services располагаются между RTE и зависящими от шины модулями интерфейсов и транспортных протоколов. Кластер состоит из тракта данных (Com, PduR) и тракта управления (ComM). Для COM модуль PDU Router является единственным нижним уровнем (RS COM с. 12).

  • Com предоставляет для RTE API сигналов, например Com_SendSignal [SWS_Com_00197] и Com_ReceiveSignal [SWS_Com_00198]. Он отображает сигналы на I-PDU.
  • PduR передает I-PDU без изменений и согласованно в целевые модули [SWS_PduR_00160]. Путь маршрутизации однозначно определяется ID источника и целевыми ID [SWS_PduR_00161]. Вниз по стеку PduR обслуживает интерфейсы и транспортные протоколы [SWS_PduR_00424]. Вверх по стеку он обслуживает Com и пользователей TP, таких как DCM (SWS PduR с. 24).
  • ComM берет на себя управление ресурсами для своих пользователей. Пользователями являются Runnable, SW-C, BswM или DCM (SWS ComM с. 30). ComM управляет режимами из ComM_ModeType [SWS_ComM_00672]. Эти режимы он реализует через <BusSm>_RequestComMode в соответствующем Bus State Manager [SWS_ComM_00958], [SWS_ComM_00962].

Общесистемное управление на уровне ECU берет на себя BswM. Он может запускать и останавливать группы I-PDU в Com ([SWS_Com_91001], [SWS_Com_91002]). Кроме того, он переключает группы трактов маршрутизации PduR ([SWS_PduR_00615], [SWS_PduR_00617], SWS BswM с. 166).

Контекстная диаграмма: Com и PduR образуют тракт данных, ComM управляет Bus State Manager и Nm, BswM переключает группы в Com и PduR. Источники: [SWS_PduR_00424], [SWS_Com_00669], [SWS_ComM_00958], [SWS_ComM_00164], [SWS_ComM_00275], [SWS_ComM_00873]

Взаимодействие и пути взаимодействия

Отправка. Com передает I-PDU с помощью PduR_ComTransmit [SWS_Com_00669]. PduR преобразует ID для целевого модуля [SWS_PduR_00766] и вызывает <Lo>_Transmit для каждой цели [SWS_PduR_00625].

  • При передаче Singlecast PduR транслирует возвращаемое значение [SWS_PduR_00626].
  • При передаче Multicast одной успешной цели достаточно для E_OK [SWS_PduR_00218].
  • PDU верхнего уровня PduR не буферизует [SWS_PduR_00629].
  • Подтверждение поступает в Com в виде Com_TxConfirmation [SWS_PduR_00627]. При Multicast это происходит только после последнего подтверждения [SWS_PduR_00589].

Trigger Transmit. Некоторые интерфейсы запрашивают данные только в момент отправки. В этом случае PduR перенаправляет запрос в Com_TriggerTransmit [SWS_PduR_00430] и возвращает его возвращаемое значение [SWS_PduR_00661]. Com возвращает E_NOT_OK в двух случаях: если I-PDU остановлен [SWS_Com_00884] или если буфер слишком мал [SWS_Com_00869]. Процесс показан на SWS PduR с. 106.

Диаграмма последовательности: передача I-PDU через FrIf выполняется в два этапа: сначала запрос на передачу, затем получение данных через Trigger Transmit. Источники: [SWS_Com_00197], [SWS_PduR_00430], [SWS_Com_00884], [SWS_PduR_00627], SWS PduR с. 106

Прием и шлюз. Вызов PduR_<Lo>RxIndication [SWS_PduR_00362] приводит к Com_RxIndication [SWS_PduR_00621] для каждой цели. Маршрутизацию 1:n на верхние уровни [SWS_PduR_00164] можно комбинировать со шлюзами между интерфейсами [SWS_PduR_00436]. Примером является маршрутизация CAN→CAN с одновременным локальным приемом (SWS PduR с. 114). Большие I-PDU используют тракт TP с Com_StartOfReception, Com_CopyRxData и Com_TpRxIndication ([SWS_Com_00691], [SWS_Com_00692], [SWS_Com_00650]). PduR перенаправляет туда callback-функции TP ([SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429]).

Группы сигналов. Для обеспечения атомарности RTE сначала обновляет все групповые сигналы. Затем она инициирует Com_SendSignalGroup ([SWS_Com_00200], SWS RTE с. 329). Напротив, COM Based Transformer обменивается группой как массивом байтов ([SWS_Com_00851], [SWS_Com_00854]). Расположение и длина этого массива определены в [SWS_Com_00844] и [SWS_Com_00845].

Тракт управления. Пользователь запрашивает связь с помощью ComM_RequestComMode [SWS_ComM_00110]. В качестве альтернативы DCM сообщает об активной диагностике [SWS_ComM_00873]. Затем ComM запрашивает режим у Bus State Manager и согласовывает действия с Nm в зависимости от варианта NM (SWS ComM с. 167). При Partial Networking ComM записывает биты PNC через Com_SendSignal ([SWS_ComM_00164], [SWS_ComM_00959]). BswM может переключать группы трактов маршрутизации в зависимости от состояния PNC. Этот источник относится к релизу R21-11 и носит информационный характер (ModeManagementGuide с. 50).

Диаграмма последовательности: запрос на связь через ожидание CommunicationAllowed приводит к запросу к шине и к NM. Источники: [SWS_ComM_00110], [SWS_ComM_00871], [SWS_ComM_00390], [SWS_ComM_00675], SWS ComM с. 167

Синхронизация, реентерабельность и контексты задач

Com выполняет циклическую обработку в трех главных функциях: Com_MainFunctionRx, Com_MainFunctionTx и Com_MainFunctionRouteSignals. Каждая из них является реентерабельной для различных экземпляров, но не для одного и того же экземпляра ([SWS_Com_00398], [SWS_Com_00399], [SWS_Com_00400]). Периоды их вызова описаны в ECU-экстракте как временные базисы (Interoperability с. 98). Если сконфигурирована ComPreparationNotification, MainFunctionTx вызывает ее перед обработкой I-PDU [SWS_Com_00886]. RTE предоставляет ее для каждого экземпляра (SWS RTE с. 832).

ComM выполняет обработку для каждого канала в ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429]. ComM_RequestComMode реентерабельна [SWS_ComM_00110], и соответствующий Runnable может вызываться параллельно (SWS ComM с. 107). Callback-функции NM работают асинхронно [SWS_ComM_00390]. ComM_Nm_PrepareBusSleepMode реентерабельна, но не для одного и того же канала NM [SWS_ComM_00391].

В тракте данных повсеместно действует одно и то же правило: реентерабельно для различных PduId, не реентерабельно для одного и того же PduId. Это относится к Com_RxIndication [SWS_Com_00123], Com_TxConfirmation [SWS_Com_00124], PduR_<Lo>RxIndication [SWS_PduR_00362] и PduR_<Lo>TxConfirmation [SWS_PduR_00365]. Интерпретация: интегратор, по-видимому, должен предотвращать одновременное поступление сообщений об одном и том же PDU из контекста прерывания и задачи, например с помощью эксклюзивных областей. Контекст вызова в источниках не определен.

При наличии нескольких разделов для ComM действуют три правила:

  • ComM должен разрешать вызовы из сторонних разделов, например через сателлит [SWS_ComM_01019].
  • ComM вызывает API <Bus>SM только в разделе соответствующего Bus State Manager [SWS_ComM_01020].
  • ComM использует API сигналов Com только в разделе соответствующего сигнала [SWS_ComM_01021].

Жизненные циклы и режимы работы

PduR имеет ровно один конечный автомат [SWS_PduR_00644] с состояниями PDUR_UNINIT и PDUR_ONLINE ([SWS_PduR_00324], [SWS_PduR_00742]). После включения питания он не инициализирован [SWS_PduR_00325]. PduR_Init [SWS_PduR_00334] приводит к трем последствиям:

  • переход в PDUR_ONLINE [SWS_PduR_00326],
  • освобождение всех буферов [SWS_PduR_00645],
  • установка значений по умолчанию [SWS_PduR_00308].

Маршрутизация выполняется только в состоянии PDUR_ONLINE ([SWS_PduR_00328], [SWS_PduR_00330]). Группы трактов маршрутизации запускаются в соответствии с конфигурацией [SWS_PduR_00709]. Таблицы маршрутизации Post-Build разрешается заменять только в неинициализированном состоянии [SWS_PduR_00296]. Активную конфигурацию возвращает PduR_GetConfigurationId [SWS_PduR_00280].

Com инициализируется с помощью Com_Init [SWS_Com_00432]. При этом он самостоятельно запускает I-PDU без группы [SWS_Com_00840]. Все остальные I-PDU активны, как только выполняется одна из их групп [SWS_Com_00771]. Остановка отменяет ожидающие запросы на передачу [SWS_Com_00777], а последующие подтверждения игнорируются [SWS_Com_00800]. Com_DeInit завершает межконтроллерную связь (Inter-ECU) [SWS_Com_00130]. Интерпретация: запуск групп I-PDU после перехода в Full Communication, вероятно, чаще всего берет на себя правило BswM. В источниках упоминаются только доступные для этого действия (SWS BswM с. 93).

Для ComM_Init [SWS_ComM_00146] модулю ComM требуется уже инициализированный NvM. Только так он может загрузить статус блокировки, счетчики блокировок и данные PNC (SWS ComM с. 97, SWS ComM с. 144). ComM_DeInit [SWS_ComM_00147] допустим только в том случае, если все каналы находятся в состоянии No Communication. При этом ComM сохраняет энергонезависимые параметры (SWS ComM с. 114). Статус инициализации возвращает ComM_GetStatus [SWS_ComM_00242] в виде значения типа [SWS_ComM_00668].

Для каждого канала ComM_StateType различает пять состояний и подсостояний [SWS_ComM_00674]:

  • Запрос пользователя приводит к переходу в COMM_NO_COM_REQUEST_PENDING. Там канал ожидает CommunicationAllowed ([SWS_ComM_00871], SWS ComM с. 69, с. 63).
  • Пассивные каналы переходят в COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915]. То же самое относится к каналам SLAVE_ACTIVE без запроса [SWS_ComM_01017].
  • Если Nm сообщает Prepare Bus-Sleep, следует COMM_SILENT_COMMUNICATION [SWS_ComM_00826]. В этом состоянии выполняется только прием (SWS ComM с. 71).
  • Сообщения о пробуждении от EcuM, относящиеся к каналу или PNC ([SWS_ComM_00275], [SWS_ComM_91001], [SWS_ComM_01014]), приводят по этому тракту к Nm_PassiveStartup (SWS ComM с. 75).

Диаграмма состояний: конечный автомат состояний каналов ComM с трактами запросов, пробуждения (Wake-up) и завершения работы (Shutdown). Источники: [SWS_ComM_00674], [SWS_ComM_00915], [SWS_ComM_00826], [SWS_ComM_01018], [SWS_ComM_00392], SWS ComM с. 63

Partial Networking дополняет систему конечными автоматами PNC. Их исходным состоянием является COMM_PNC_NO_COMMUNICATION ([SWS_ComM_00964], SWS ComM с. 37). Динамическое сопоставление PNC с каналами в R20-11 все еще помечено как DRAFT ([SWS_ComM_91013], [SWS_ComM_01026]). В более поздних релизах сигнатура ComM_GetPncToChannelMapping переведена на битовые векторы (SWS ComM с. 122). Для R20-11 действует требование.

Обработка ошибок, трассировка DET и деградация

Com сообщает об ошибках разработки через Det_ReportError с ModuleId 50 [SWS_Com_00442]:

  • COM_E_PARAM [SWS_Com_00803]
  • COM_E_UNINIT [SWS_Com_00804]
  • COM_E_PARAM_POINTER [SWS_Com_00805]
  • COM_E_INIT_FAILED [SWS_Com_00837]

Если запрос на передачу большого I-PDU пропускается, Com сообщает об ошибке времени выполнения COM_E_SKIPPED_TRANSMISSION ([SWS_Com_00863], [SWS_Com_00864]).

Функциональная деградация Com осуществляется через контроль дедлайнов:

  • При отсутствии своевременного подтверждения передачи Com вызывает уведомления о таймауте [SWS_Com_00304]. Подтверждение останавливает таймеры [SWS_Com_00880].
  • При приеме действие SUBSTITUTE заменяет значения замещающими значениями ([SWS_Com_00875], [SWS_Com_00876]).
  • Неудачный прием TP обрабатывается как инвалидация [SWS_Com_00838].
  • Сигналы без установленного бита обновления отбрасываются [SWS_Com_00802].
  • Контроль приема можно включать и выключать по группам ([SWS_Com_91003], [SWS_Com_91004]).

PduR распознает, среди прочего, ошибки PDUR_E_UNINIT, PDUR_E_PDU_ID_INVALID и PDUR_E_ROUTING_PATH_GROUP_ID_INVALID ([SWS_PduR_00100], [SWS_PduR_00119], [SWS_PduR_00221], [SWS_PduR_00648]). Неудавшийся вызов <DstLo>_Transmit он не повторяет [SWS_PduR_00256]. В случае переполнения FIFO он очищается, и сообщается PDUR_E_PDU_INSTANCES_LOST ([SWS_PduR_00255], [SWS_PduR_00670]). Если в шлюзе TP выходит из строя одна из целей, остальные продолжают работу [SWS_PduR_00803]. Только если дают сбой все цели, прием прерывается [SWS_PduR_00804]. При отключенных трактах маршрутизации API немедленно возвращают E_NOT_OK ([SWS_PduR_00717], SWS PduR с. 69).

ComM сообщает, среди прочего, об COMM_E_UNINIT и COMM_E_PARAM_POINTER [SWS_ComM_00234]. Без инициализации он блокирует нормальную работу [SWS_ComM_00612]. Для целенаправленной деградации служит блокировка режимов:

  • Один канал или весь ECU можно ограничить режимом No Communication ([SWS_ComM_00163], [SWS_ComM_00124]).
  • Процессы пробуждения можно подавлять [SWS_ComM_00156].
  • Статус содержится в битовом поле [SWS_ComM_00669] и сохраняется при перезагрузке ECU (SWS ComM с. 84).
  • Отклоненные запросы возвращают COMM_E_MODE_LIMITATION [SWS_ComM_00110] и подсчитываются [SWS_ComM_00224].
  • Опционально ComM затем принудительно инициирует сброс через BswM [SWS_ComM_00355].

Проанализированный материал не содержит событий DEM для данного кластера. Обработка ошибок опирается на сообщения DET и описанную выше функциональную деградацию ([SWS_PduR_00100], [SWS_ComM_00234]).

Сгенерированное ИИ руководство по кластеру на основе связанных разделов спецификации. Нормативными для R20-11 являются исключительно требования. Утверждения, обозначенные как «интерпретация» или «вероятно», не подкреплены источниками. Фрагменты документации из других релизов служат только для пояснения.
