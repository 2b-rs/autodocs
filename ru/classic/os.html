Системная архитектура и роль кластера «Operating System»

Кластер включает в себя только модуль Os. Он расширяет OSEK OS, например программными счетчиками в качестве действия аларма и автоматически запускаемыми абсолютными алармами SWS OS с. 38. Кроме того, он объединяет задачи, ISR, алармы, ScheduleTables, счетчики и хуки в OS-Applications. Они являются либо trusted, либо non-trusted SWS OS с. 61. Сконфигурированное или выполняющееся в данный момент OS-Application возвращают GetApplicationID [SWS_Os_00016] и GetCurrentApplicationID [SWS_Os_00797]. Оба пространства идентификаторов пронумерованы без пропусков начиная с нуля, так же как и идентификаторы Core [SWS_Os_00826] [SWS_Os_00825].

В архитектуре BSW OS является поставщиком служб с фиксированными правами доступа. Таблица общей спецификации BSW определяет, какие группы модулей могут использовать те или иные OS-сервисы: RTE/BSW-Scheduler, BswM, CDD, EcuM, MCAL, StbM и остальная часть BSW SWS BSWGeneral с. 48. CDD, например, должен использовать только GetCounterValue и GetElapsedValue CDD-Guideline с. 21. Inter-OS-Application Communicator (IOC) является частью OS. Он дополняет внутреннюю связь RTE и связь на основе COM в качестве третьего типа коммуникации SWS OS с. 119. В R20-11 раздельная генерация кода IOC и OS предусмотрена как DRAFT [SWS_Os_00831].

Контекстная диаграмма: OS является основой выполнения, защиты и коммуникации для EcuM, StbM, RTE, BswM и CDD. Источники: SWS BSWGeneral с. 48, SWS EcuM с. 82, SWS StbM с. 220, ALEH с. 76

Взаимодействие и пути взаимодействия

Синхронизация времени со StbM: обзор безопасности для R20-11 относит SyncScheduleTable, StartScheduleTableSynchron, GetScheduleTableStatus и SetScheduleTableAsync к связи между синхронизированной базой времени и OS-счетчиком FSM-Übersicht с. 66. Последовательность такова: в StbM_MainFunction StbM сначала запрашивает GetScheduleTableStatus [SWS_Os_00227]. Только в состояниях WAITING, RUNNING или RUNNING_AND_SYNCHRONOUS он затем передает значение синхронизации через SyncScheduleTable [SWS_Os_00199] SWS StbM с. 220. Интерпретация: эта последовательность взята из более поздних релизов и, по-видимому, применима по смыслу и к R20-11. По значению синхронизации OS определяет дрейф между временем таблицы и счетчиком синхронизации SWS OS с. 52.

Диаграмма последовательности: StbM синхронизирует явно синхронизированную ScheduleTable только в подходящем состоянии. Источники: SWS StbM с. 220, [SWS_Os_00199], [SWS_Os_00227]

IOC между разделами и Core: для семантики «data» (LastIsBest) OS создает IocWrite/IocRead [SWS_Os_91003] [SWS_Os_91005], для семантики «event» (Queue) IocSend/IocReceive [SWS_Os_00718] [SWS_Os_00738]. При LastIsBest RTE копирует свой буфер во внутренний буфер IOC, из которого читает получатель SWS OS с. 190. Если Queue заполнена, отправитель сообщает IOC_E_LIMIT, а получатель при следующем чтении получает IOC_E_LOST_DATA SWS OS с. 218. Опционально IOC при каждом приеме вызывает <ReceiverPullCB> на принимающем Core [SWS_Os_00757].

Вызовы через границы разделов: с помощью CallTrustedFunction [SWS_Os_00097] вызывающая сторона переходит в контекст защиты предоставляющего OS-Application. Для этого заглушка упаковывает аргументы в структуру. OS проверяет полномочия и в случае отказа возвращает E_OS_SERVICEID SWS OS с. 185. В качестве асинхронных альтернатив BSW-Distribution-Guide называет ActivateTask или SetEvent для задачи целевого раздела BSW-Distribution-Guide с. 66. Для вызовов между Core существуют ActivateTaskAsyn и SetEventAsyn [SWS_Os_91022] [SWS_Os_91023].

Синхронизация, реентерабельность и контексты выполнения

Большинство OS-сервисов являются синхронными и реентерабельными. Некоторые исключения важны для интеграции:

СервисРеентерабельность / типОбоснование

ControlIdleнереентерабельно[SWS_Os_00769]
IocSend_<IocId>асинхронный; генерируется для каждого отправителя, нереентерабельный для одного и того же отправителя[SWS_Os_00718]

Spinlocks: для взаимного исключения между Core OS предоставляет спинлоки. GetSpinlock [SWS_Os_00686] активно ожидает, не снимая вызывающую сторону с планирования. В Extended Status он возвращает E_OS_INTERFERENCE_DEADLOCK или E_OS_NESTING_DEADLOCK SWS OS с. 199. TryToGetSpinlock [SWS_Os_00703] вместо этого немедленно возвращает управление. Перед завершением задачи и перед WaitEvent все спинлоки должны быть освобождены с помощью ReleaseSpinlock [SWS_Os_00695]. От взаимного влияния на одном и том же Core помогает заключение в SuspendAllInterrupts, которое OS через OsSpinlockLockMethod также может взять на себя SWS OS с. 101. Спинлоки можно вызывать на уровне задач и ISR категории 2. Из ISR категории 1 поведение не определено SWS OS с. 115.

Категории ISR и правила контекста: контекст OS доступен только в ISR категории 2. Вне ISR категории 2 GetISRID INVALID_ISR возвращает [SWS_Os_00511] SWS OS с. 171. Из ISR категории 1 результат GetCurrentApplicationID не определен SWS OS с. 162. API источников прерываний существуют только для источников категории 2 [SWS_Os_00808]; вложенные вызовы возвращают E_OS_NOFUNC [SWS_Os_00809]. Согласно [SWS_Os_00811], EnableInterruptSource дополнительно сбрасывает флаг ожидания. Однако определение API [SWS_Os_91020] содержит для этого параметр ClearPending. Интерпретация: сброс, вероятно, привязан к ClearPending == TRUE. Синхронный вызов ActivateTask через границы Core возвращается только после активации или обнаружения ошибки на целевом Core SWS OS с. 103.

Жизненные циклы и режимы работы

Запуск: в Master-Core-StartPreOS EcuM сначала в цикле запускает все сконфигурированные Core с помощью StartCore. Затем он вызывает StartOS(ECUM_DEFAULT_APP_MODE) SWS EcuM с. 82. После StartOS вызов StartCore больше не допускается [SWS_Os_00676]. GetCoreID [SWS_Os_00674], напротив, разрешено вызывать еще до StartOS SWS OS с. 111. После StartOS и перед StartupHooks OS переводит все OS-Applications в состояние APPLICATION_ACCESSIBLE SWS OS с. 62. Затем выполняются StartupHook_<App> [SWS_Os_00539]. Если IOC сконфигурирован, StartOS в режиме по умолчанию инициализирует его структуры данных через IocInit (DRAFT) [SWS_Os_00830] [SWS_Os_91026].

ScheduleTables: OS запускает ScheduleTable абсолютно [SWS_Os_00358] или относительно текущего значения счетчика [SWS_Os_00347]. StopScheduleTable [SWS_Os_00006] останавливает ее. Последующий перезапуск снова начинается с начала таблицы SWS OS с. 46. NextScheduleTable [SWS_Os_00191] связывает две таблицы в цепочку. При синхронном запуске [SWS_Os_00201] таблица ожидает первого значения синхронизации, при необходимости — неограниченно долго SWS OS с. 49. SetScheduleTableAsync [SWS_Os_00422] завершает синхронизацию, но Expiry Points продолжают обрабатываться SWS OS с. 188. Пять состояний определяет [SWS_Os_00784].

Диаграмма состояний: жизненный цикл явно синхронизированной ScheduleTable. Источники: [SWS_Os_00784], SWS OS с. 49, SWS OS с. 188

OS-Applications: нормативными для R20-11 являются три состояния [SWS_Os_00773]. Более поздние релизы содержат для этого типа только два значения SWS OS с. 161.

  • APPLICATION_ACCESSIBLE: начальное состояние, объекты OS-Application доступны извне SWS OS с. 62.
  • APPLICATION_RESTARTING: действует до тех пор, пока само OS-Application не вызовет AllowAccess [SWS_Os_00501].
  • APPLICATION_TERMINATED: окончательно завершено; состояние можно запросить через GetApplicationState [SWS_Os_00499].

Idle и Shutdown: ControlIdle выбирает для каждого Core действие Idle, например, для мер по энергосбережению [SWS_Os_00769]. По умолчанию используется IDLE_NO_HALT [SWS_Os_00793]. Синхронизированный Shutdown запускает ShutdownAllCores [SWS_Os_00713]. Этот вызов не возвращает управление и игнорируется из non-trusted кода SWS OS с. 204. EcuM выполняет его в Master-Core-OffPreOS после BswM_Deinit и SchM_Deinit SWS EcuM с. 91. Затем на каждом Core выполняются зависящие от приложения Shutdown-хуки, после чего следуют барьер синхронизации и глобальный ShutdownHook SWS OS с. 88 SWS OS с. 189 [SWS_Os_00541].

Обработка ошибок, нарушения защиты и деградация

Сообщение об ошибках через возвращаемые значения и хуки: OS сообщает об ошибках через возвращаемые значения StatusType, многие из них — только в Extended Status. Специфичные для AUTOSAR коды ошибок определены в [SWS_Os_91025]. Указатели, которые равны NULL_PTR, OS отклоняет в Extended Mode с E_OS_ILLEGAL_ADDRESS SWS OS с. 38. Обнаруженные ошибки передаются в ErrorHook или ErrorHook_<App> [SWS_Os_00540], например, в API источников прерываний [SWS_Os_00810]. Особым случаем является IncrementCounter: если действие аларма завершается сбоем, OS вызывает Error-хуки, однако сама служба возвращает E_OK SWS OS с. 190. В случае ActivateTaskAsyn сообщения об ошибках теряются, если вызывающий объект больше не существует SWS OS с. 203. Подключение OS к DET в имеющихся материалах не подтверждено.

Защита доступа: Если сконфигурированные права доступа к OS-объекту отсутствуют, служба возвращает E_OS_ACCESS SWS OS с. 73. Для предварительной проверки предусмотрены CheckObjectAccess [SWS_Os_00256], CheckObjectOwnership [SWS_Os_00017] и проверки памяти [SWS_Os_00512] [SWS_Os_00513]. Их результат оценивают макросы OSMEMORY_IS_* SWS OS с. 160. Несконфигурированный индекс Trusted-Function вызывает ErrorHook с E_OS_SERVICEID SWS OS с. 85. Доступ на запись можно ограничить даже для доверенных OS-Applications [SWS_Os_00795].

Эскалация через ProtectionHook: При тяжелых нарушениях защиты OS вызывает ProtectionHook [SWS_Os_00538]. Его ProtectionReturnType [SWS_Os_00787] определяет реакцию: завершить задачу или ISR, завершить OS-Application (с перезапуском или без) либо остановить систему SWS OS с. 187.

Диаграмма последовательности: пути эскалации после нарушения защиты, управляемые возвращаемым значением ProtectionHook. Источники: SWS OS с. 187, [SWS_Os_00538], [SWS_Os_00787], ALEH с. 69

Завершение и перезапуск: OS-Application также может быть целенаправленно завершена с помощью TerminateApplication [SWS_Os_00258]. Затем OS завершает ее задачи и ISR, блокирует ее прерывания и останавливает ее алармы и ScheduleTables SWS OS с. 62. В R20-11 RestartType с RESTART/NO_RESTART управляет перезапуском [SWS_Os_00788]. Более поздние релизы используют вместо этого OS_OSAPPLICATION_RESTART и игнорируют параметр SWS OS с. 194. Для внешне инициированного перезапуска руководство предусматривает следующие шаги: уведомить RTE, сохранить решение для OSRestartTask, вызвать TerminateApplication(<partition>, RESTART) и передать сообщение в DEM ALEH с. 75. OSRestartTask инициирует очистку с помощью CallTrustedFunction напрямую или через BswM. После этого AllowAccess снова освобождает OS-Application ALEH с. 76 [SWS_Os_00501].

Сгенерированное ИИ руководство по кластеру на основе выдержек из спецификаций, содержащихся в полезной нагрузке. Нормативными являются требования R20-11; в случае расхождений действует оригинальная спецификация.

Операционная система AUTOSAR представляет собой статически настроенную вытесняющую операционную систему, работающую в режиме реального времени, в соответствии с OSEK/VDX с задачами, событиями, сигналами тревоги, таблицами расписаний и защитой памяти.
