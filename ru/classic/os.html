Обеспечивает детерминированное планирование реального времени, защиту памяти, многоядерную синхронизацию и локализацию ошибок.

Модульный кластер Operating System обеспечивает детерминированное планирование реального времени для задач и ISR, а также защиту памяти и изоляцию ошибок в секционированных OS-Applications [SWS_Os_00445]. Он поддерживает многоядерные системы благодаря межъядерным спинлокам, асинхронной активации задач и Inter-OS-Application Communicator (IOC) [SWS_Os_00686], [SWS_Os_00824]. При возникновении нарушений защиты OS через конфигурируемые хуки позволяет целенаправленно завершать или контролируемо перезапускать отдельные разделы во время выполнения ApplicationLevelErrorHandling с. 53.

Модульный кластер «Operating System» в AUTOSAR Classic предоставляет фундаментальную инфраструктуру выполнения и защиты для программных компонентов и модулей базового программного обеспечения. Операционная система инкапсулирует такие ресурсы, как задачи, ISR, сигналы тревоги и счетчики, в OS-Applications [SWS_Os_00445], разделяя при этом доверенные (trusted) и недоверенные разделы [SWS_Os_00446] для обеспечения строгой локализации ошибок на основе защиты памяти MPU SafetyConceptStatusReport с. 49. В многоядерных системах OS управляет логическими ядрами с помощью стандартизированных ID ядер [SWS_Os_00790] и предоставляет Inter-OS-Application Communicator (IOC) для обмена данными и событиями между ядрами и разделами [SWS_Os_00824].

Контекстная диаграмма: встраивание кластера OS в архитектуру базового программного обеспечения AUTOSAR и интерфейсы к EcuM, StbM, RTE и аппаратному обеспечению. Источники: [SWS_Os_00445], [SWS_Os_00790], SWS_BSWGeneral с. 48.

Наряду с событийно-управляемым планированием задач OS обеспечивает управление выполнением по времени с помощью Schedule Tables [SWS_Os_00783]. Они могут синхронизироваться с глобальными базисами времени автомобиля через Synchronized Time-Base Manager (StbM) с помощью SyncScheduleTable [SWS_Os_00199], SWS_SynchronizedTimeBaseManager с. 220. Для синхронизации между ядрами модуль предлагает низкоуровневые спинлоки со встроенным обнаружением взаимных блокировок [SWS_Os_00686], в то время как межъядерные активации задач могут выполняться асинхронно с помощью ActivateTaskAsyn [SWS_Os_91022].

В случае сбоя (например, при превышении пределов памяти) OS активирует ProtectionHook [SWS_Os_00538]. С помощью его возвращаемого значения сбойная OS-Application может быть изолирована и контролируемо завершена либо заново инициализирована через выделенную задачу перезапуска без сброса всей системы [SWS_Os_00787], ApplicationLevelErrorHandling с. 53.

Диаграмма состояний: жизненный цикл и состояния секционирования AUTOSAR OS-Application в случае сбоя. Источники: [SWS_Os_00773], [SWS_Os_00258], ApplicationLevelErrorHandling с. 53.

1. Системная архитектура и роль модульного кластера

Модульный кластер «Operating System» образует в многоуровневой модели AUTOSAR фундаментальную основу System Services для выполнения и координации всех программных компонентов реального времени и модулей Basic Software. Базовый модуль [SWS_Os_00445] инкапсулирует задачи (Tasks), процедуры обработки прерываний (ISRs), алармы (Alarms), счетчики (Counters) и таблицы расписания (Schedule Tables) в конфигурируемых единицах выполнения, так называемых OS-Applications. При этом операционная система строго различает доверенные (trusted) и недоверенные (non-trusted) OS-Applications [SWS_Os_00446], чтобы обеспечить функциональную безопасность и защиту памяти в соответствии с требуемыми классами масштабируемости SafetyConceptStatusReport с. 49.

В многоядерных архитектурах OS управляет логическими ядрами, на которые ссылаются через уникальные идентификаторы типа CoreIdType [SWS_Os_00790]. Идентификаторы ядер отсчитываются от нуля и расположены последовательно [SWS_Os_00825], при этом константа OS_CORE_ID_MASTER обозначает мастер-ядро SWS_OS с. 111. Через встроенный Inter-OS-Application Communicator (IOC) операционная система предоставляет механизмы для безопасной передачи данных между разделами и ядрами [SWS_Os_00824]. За счет стандартизации интерфейсов согласно OSEK OS и их AUTOSAR-специфичных расширений OS гарантирует детерминированное поведение в реальном времени для вышестоящих модулей, таких как ECU State Manager (EcuM), Synchronized Time-Base Manager (StbM), а также среда выполнения RTE SWS_BSWGeneral с. 48.

Контекстная диаграмма: встраивание кластера OS в архитектуру базового программного обеспечения AUTOSAR и интерфейсы к EcuM, StbM, RTE и аппаратному обеспечению. Источники: [SWS_Os_00445], [SWS_Os_00790], SWS_BSWGeneral с. 48.

2. Взаимодействие и пути интеракции между модулями

Взаимодействие между объектами OS и уровнями архитектуры AUTOSAR осуществляется по четко разграниченным путям управления и данных. Для межраздельного обмена данными IOC генерирует типизированные коммуникационные функции с семантикой без очередей («data», IocWrite / IocRead) или с очередями («event», IocSend / IocReceive) [SWS_Os_00718], [SWS_Os_00738]. При групповых передачах используются службы IocSendGroup и IocReceiveGroup соответственно [SWS_Os_00728], [SWS_Os_00746]. Если внутренний буфер приемника переполняется, IOC сигнализирует об этом отправителю со статусом IOC_E_LIMIT и фиксирует IOC_E_LOST_DATA для последующих операций чтения SWS_OS с. 225.

Если недоверенная OS-Application должна получить доступ к привилегированным службам доверенного раздела, контролируемое переключение контекста выполняется через системную службу CallTrustedFunction [SWS_Os_00097]. При этом параметры передаются через структуру указателей типа TrustedFunctionParameterRefType [SWS_Os_00776]. Операционная система временно переключает полномочия MPU на полномочия целевого приложения SWS_OS с. 172. Функция GetCurrentApplicationID во время этого выполнения возвращает идентификатор вызванной Trusted Application, тогда как GetApplicationID возвращает исходное вызывающее приложение [SWS_Os_00797].

Для временного согласования с внешними базисами времени модуль StbM синхронизирует явно сконфигурированные Schedule Tables через интерфейсы OS. Сначала StbM циклически опрашивает состояние синхронизации через GetScheduleTableStatus [SWS_Os_00227], а затем передает текущее значение синхронизации в OS с помощью SyncScheduleTable [SWS_Os_00199]. После этого операционная система вычисляет отклонение от точек истечения (Expiry Points) и ступенчато корректирует времена задержки, пока таблица не начнет выполняться синхронно с глобальным базисом времени SWS_OS с. 57, SWS_SynchronizedTimeBaseManager с. 220.

Диаграмма последовательности: явная синхронизация OS-Schedule-Table менеджером Synchronized Time-Base Manager (StbM). Источники: [SWS_Os_00199], [SWS_Os_00227], SWS_SynchronizedTimeBaseManager с. 220.

3. Синхронизация, реентерабельность и контексты задач

Модель времени выполнения четко различает уровень задач, уровни прерываний категории 1 (Cat 1 ISR) и категории 2 (Cat 2 ISR), а также хук-процедуры. В то время как Cat 1 ISR выполняются без накладных расходов операционной системы и не могут вызывать службы OS, Cat 2 ISR полностью управляются OS [SWS_Os_00782]. Активный идентификатор ISR можно определить с помощью GetISRID; при вызове вне Cat 2 ISR служба возвращает INVALID_ISR [SWS_Os_00511]. Отдельными источниками прерываний можно целенаправленно управлять на уровне контроллера прерываний через EnableInterruptSource, DisableInterruptSource и ClearPendingInterrupt [SWS_Os_91020], [SWS_Os_91019], [SWS_Os_91021].

Для синхронизации критических секций между границами процессорных ядер OS предоставляет спинлоки [SWS_Os_00791]. Спинлок захватывается синхронно с блокировкой с помощью GetSpinlock [SWS_Os_00686] или опрашивается без блокировки через TryToGetSpinlock [SWS_Os_00703]. Освобождение выполняется через ReleaseSpinlock [SWS_Os_00695]. Чтобы исключить взаимоблокировки (deadlocks), OS в расширенном статусе выполняет проверку на ошибки вложенности и перекрытия (E_OS_INTERFERENCE_DEADLOCK, E_OS_NESTING_DEADLOCK) SWS_OS с. 199.

Для межъядерных активаций задач и установки событий OS предоставляет асинхронные варианты API: ActivateTaskAsyn и SetEventAsyn немедленно возвращают управление вызывающей стороне, не дожидаясь выполнения на целевом ядре [SWS_Os_91022], [SWS_Os_91023]. Возможные ошибки при этом не возвращаются вызывающей стороне, а протоколируются через сконфигурированные Error-Hooks [SWS_Os_00816], SWS_OS с. 203.

4. Типичные жизненные циклы и режимы работы

Запуск системы в решающей степени координируется ECU State Manager (EcuM). На мастер-ядре EcuM перед запуском операционной системы запускает подчиненные ядра через службу OS StartCore [SWS_Os_00676], SWS_ECUStateManager с. 82. Затем каждое запущенное ядро автономно вызывает StartOS. После вызова StartOS операционная система переводит все сконфигурированные OS-Applications в состояние APPLICATION_ACCESSIBLE, прежде чем будут выполнены Startup-Hooks SWS_OS с. 62. Количество успешно запущенных ядер можно запросить во время выполнения с помощью GetNumberOfActivatedCores SWS_OS с. 196.

Schedule Tables подчиняются четко определенному конечному автомату состояний. Их можно запустить абсолютно через StartScheduleTableAbs [SWS_Os_00358], относительно через StartScheduleTableRel [SWS_Os_00347] или синхронно через StartScheduleTableSynchron [SWS_Os_00201]. Таблицы можно объединять в цепочки (NextScheduleTable, состояние SCHEDULETABLE_NEXT) [SWS_Os_00191] или с помощью StopScheduleTable немедленно переводить в состояние покоя SCHEDULETABLE_STOPPED [SWS_Os_00006]. Текущую явную синхронизацию можно прервать с помощью SetScheduleTableAsync, при этом обработка Expiry Points продолжается [SWS_Os_00422].

Для режимов энергосбережения при простое OS предлагает интерфейс ControlIdle, с помощью которого EcuM может конфигурировать состояние покоя отдельных ядер [SWS_Os_00769]. При завершении работы EcuM координирует деинициализацию всех уровней и в завершение вызывает ShutdownAllCores или ShutdownOS для контролируемой остановки всей системы SWS_ECUStateManager с. 90.

5. Обработка ошибок, трассировка DET и деградация

Нарушения защиты (такие как превышение границ памяти или нарушения таймингов) приводят к активации глобального ProtectionHook [SWS_Os_00538]. На основе ошибки хук принимает решение о стратегии восстановления (recovery) через возвращаемое значение типа ProtectionReturnType [SWS_Os_00787]: завершение вызвавшей сущности (PRO_TERMINATETASKISR), полное завершение затронутого раздела (PRO_TERMINATEAPPL), инициация контролируемого перезапуска раздела (PRO_TERMINATEAPPL_RESTART) или завершение работы блока управления (PRO_SHUTDOWN) ApplicationLevelErrorHandling с. 60.

Если OS-Application завершается или перезапускается, OS переводит ее из состояния APPLICATION_ACCESSIBLE в APPLICATION_RESTARTING или APPLICATION_TERMINATED [SWS_Os_00773]. Все активные задачи, ISR, алармы и Schedule Tables раздела немедленно останавливаются, а все прерывания отключаются [SWS_Os_00447]. В состоянии APPLICATION_RESTARTING монопольно выполняется OsRestartTask для выполнения очистки перед тем, как нормальный режим работы будет снова разрешен ApplicationLevelErrorHandling с. 53, ApplicationLevelErrorHandling с. 76.

Диаграмма состояний: жизненный цикл и состояния секционирования AUTOSAR OS-Application в случае сбоя. Источники: [SWS_Os_00773], [SWS_Os_00258], ApplicationLevelErrorHandling с. 53.

Для превентивного предотвращения ошибок операционная система предлагает функции проверки защиты памяти, такие как CheckTaskMemoryAccess и CheckISRMemoryAccess [SWS_Os_00512], [SWS_Os_00513], а также проверки прав доступа через CheckObjectAccess и CheckObjectOwnership [SWS_Os_00256], [SWS_Os_00017]. С помощью этих стандартизированных проверок можно гарантировать, что недоверенные компоненты не совершат несанкционированный доступ на запись или выполнение в памяти SWS_OS с. 73.

Контекст данного руководства: составлено на основе спецификаций AUTOSAR Classic для релиза R20-11. Все интерфейсы и переходы состояний строго подтверждены указанными требованиями SWS.

Операционная система AUTOSAR представляет собой статически настроенную вытесняющую операционную систему, работающую в режиме реального времени, в соответствии с OSEK/VDX с задачами, событиями, сигналами тревоги, таблицами расписаний и защитой памяти.
