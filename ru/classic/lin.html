Lin_ConfigType тип

Это тип внешней структуры данных, содержащей общие данные инициализации для драйвера LIN и настроек SFR, влияющих на каналы LIN. Указатель на такую ​​структуру предоставляется процедуре инициализации драйвера LIN для настройки драйвера, LIN аппаратного блока и LIN аппаратных каналов.

Lin_FrameCsModelType тип

Этот тип используется для указания модели контрольной суммы, которая будет использоваться для кадра LIN.

Lin_FrameDlType тип

Этот тип используется для указания количества SDU байтов данных для копирования.

Lin_FramePidType тип

Представляет все действительные защищенные идентификаторы, используемые функцией Lin_ Send Frame().

Lin_FrameResponseType тип

Этот тип используется для указания, требуется ли процессору кадров передавать ответную часть кадра LIN.

Lin_PduType тип

Этот тип используется для предоставления PID, модели контрольной суммы, длины данных и указателя SDU от интерфейса LIN к драйверу LIN.

Lin_SlaveErrorType тип

Этот тип представляет типы ошибок ведомого устройства, которые обнаруживаются во время приема заголовка и передачи/приема ответа.

Lin_StatusType тип

LIN состояния операций для LIN канала или кадра, возвращаемые службой API Lin_ Get Status().

Системная архитектура и роль кластера модулей

Кластер формирует стек связи LIN платформы Classic Platform от аппаратного обеспечения до управления режимами. Четыре модуля распределяют задачи следующим образом:

  • Lin — это драйвер MCAL. Он инкапсулирует контроллер LIN или UART и вычисляет классическую или расширенную контрольную сумму [SWS_Lin_00019]. Кадры он принимает в виде Lin_PduType с PID, моделью контрольной суммы, типом ответа, длиной и указателем на SDU [SWS_Lin_00232].
  • LinTrcv управляет внешним трансивером через режимы LINTRCV_TRCV_MODE_NORMAL, …_STANDBY и …_SLEEP [SWS_LinTrcv_00168] и проверяет события пробуждения [SWS_LinTrcv_00012].
  • LinIf — это аппаратная абстракция. Модуль управляет таблицами расписания и состояниями каналов, а также содержит транспортный протокол LinTp [SWS_LinIf_00350].
  • LinSM реализует запросы режимов от ComM [SWS_LinSM_00126] и сообщает состояние и расписание модулю BswM [SWS_LinSM_00229].

Роль узла определяет с помощью конфигурации, какие функции предоставляет модуль:

  • Только в мастере присутствуют Lin_SendFrame, Lin_GoToSleep и Lin_GetStatus [SWS_Lin_00287] [SWS_Lin_00288] [SWS_Lin_00289], а также LinSM_ScheduleRequest [SWS_LinSM_00241].
  • Только в слейве присутствуют функции обратного вызова драйвера из LinIf [SWS_LinIf_00863] [SWS_LinIf_00866] и LinSM_GotoSleepIndication [SWS_LinSM_00243].
  • Для слейвов LinIf также управляет NAD и PID согласно модели узла стандарта ISO 17987-3 [SWS_LinIf_00767] [SWS_LinIf_00778] LinIf-SWS с. 59.

Контекстная диаграмма: модули кластера располагаются между ComM/BswM/PduR и аппаратным обеспечением, события пробуждения дополнительно проходят через EcuM. Источники: [SWS_LinSM_00126] [SWS_LinIf_00360] [SWS_LinIf_00544] [SWS_Lin_00234] [SWS_LinIf_00378]

Взаимодействие и пути взаимодействия

Тракт мастера. LinIf обрабатывает таблицу расписания в LinIf_MainFunction_<LinIfChannel.ShortName> [SWS_LinIf_00384]. Слот передачи выполняется следующим образом:

  1. LinIf получает данные через <User_TriggerTransmit> [SWS_LinIf_00528] и передает их с помощью Lin_SendFrame [SWS_Lin_00191].
  2. Если верхний уровень возвращает E_NOT_OK, кадр не отправляется [SWS_LinIf_00706].
  3. Не ранее чем по истечении максимальной длины кадра LinIf запрашивает статус с помощью Lin_GetStatus [SWS_Lin_00168] LinIf-SWS с. 35.
  4. При LIN_TX_ERROR или LIN_TX_BUSY следует <User_TxConfirmation> с E_NOT_OK [SWS_LinIf_00728].

Если верхним уровнем является PduR, <User_TriggerTransmit> фиксирован PduR_LinIfTriggerTransmit [SWS_LinIf_00722]. LinIf_Transmit резервирует только спорадические (мастер) или управляемые событиями (слейв) кадры [SWS_LinIf_00201] LinIf-SWS с. 79. При NULL_SCHEDULE он отклоняет запрос [SWS_LinIf_00719].

Тракт слейва. Процесс инициируется заголовком мастера:

  1. Драйвер сообщает о каждом заголовке через LinIf_HeaderIndication с PID и указателем на свой буфер [SWS_Lin_00280] [SWS_LinIf_91004].
  2. LinIf оценивает PID:
    • В случае кадра на передачу <User_TriggerTransmit> записывает данные непосредственно в буфер драйвера [SWS_LinIf_00738], а LinIf устанавливает Drc = LIN_FRAMERESPONSE_TX [SWS_LinIf_00739].
    • Кадры на прием получают LIN_FRAMERESPONSE_RX [SWS_LinIf_00733].
    • Нерелевантные кадры получают LIN_FRAMERESPONSE_IGNORE [SWS_LinIf_00748].
  3. Lin анализирует Drc, Cs и Dl [SWS_Lin_00282] [SWS_Lin_00283] [SWS_Lin_00286].
  4. Каждый релевантный ответ Lin завершает перед следующим заголовком с помощью Rx-Indication, Tx-Confirmation или Error-Indication [SWS_Lin_00285].
  5. LinIf передает результат дальше в <User_RxIndication> или <User_TxConfirmation> [SWS_LinIf_00734] [SWS_LinIf_00741].

Более новые релизы заменяют эти коллауты трактом LSduR (статус DRAFT) LinIf-SWS с. 43. Для R20-11 действуют интерфейсы <User_…>.

Диаграмма последовательности: слейв отправляет свой ответ только после индикации заголовка, заполнения буфера верхним уровнем и разрешения через Drc. Источники: [SWS_Lin_00280] [SWS_LinIf_00738] [SWS_LinIf_00739] [SWS_Lin_00283] [SWS_LinIf_00742] LinIf-SWS с. 121

Транспортный протокол и смена расписания. LinTp_Transmit подготавливает TP-сообщение [SWS_LinIf_00351]. В мастере LinTp запрашивает смену расписания через BswM_LinTp_RequestMode с помощью LinTp_Mode [SWS_LinIf_00360] [SWS_LinIf_00629]. Затем цепочка выполняется следующим образом LinIf-SWS с. 132:

  1. BswM вызывает LinSM_ScheduleRequest [SWS_LinSM_00113].
  2. LinSM вызывает LinIf_ScheduleRequest [SWS_LinIf_00202].
  3. LinIf подтверждает операцию через <User>_ScheduleRequestConfirmation модулю LinSM_ScheduleRequestConfirmation [SWS_LinIf_00520] [SWS_LinSM_00129].

Имена параметров этих API были переименованы в R22-11 Release Overview с. 50. В R20-11 они еще называются Schedule/schedule.

Синхронизация, реентерабельность и контексты задач

Циклическая обработка. Для каждого канала существует LinIf_MainFunction_<LinIfChannel.ShortName>. Другие API LinIf, такие как LinIf_GotoSleep, LinIf_Transmit, LinIf_ScheduleRequest и LinIf_Wakeup, могут прерывать ее. Поэтому совместно используемые области необходимо защищать LinIf-SWS с. 119. LinSM_MainFunction ведет таймеры тайм-аута [SWS_LinSM_00156].

Прямые вызовы. Переходы в спящий режим намеренно не ожидают следующего вызова MainFunction. Таким образом, они выполняются в контексте вызывающей стороны:

  • LinSM вызывает LinIf_GotoSleep немедленно [SWS_LinSM_00036] [SWS_LinSM_00231].
  • LinIf вызывает Lin_GoToSleepInternal немедленно [SWS_LinIf_00757].

Функции обратного вызова слейва. Функции обратного вызова реентерабельны для различных каналов, но не для одного и того же [SWS_LinIf_91005] [SWS_LinIf_91006] [SWS_LinIf_91007]. На схеме LinIf_HeaderIndication следует непосредственно за аппаратным прерыванием LinIf-SWS с. 121. Интерпретация: таким образом, функции обратного вызова, вероятно, в большинстве случаев выполняются в контексте ISR. Поэтому <User_TriggerTransmit> должна оставаться короткой. Сам драйвер выполняет отправку и прием без блокировки Lin-SWS с. 28.

Реентерабельность в R20-11. R20-11 объявляет Lin_GoToSleep, Lin_Wakeup и Lin_GetStatus как «Non Reentrant» [SWS_Lin_00166] [SWS_Lin_00169] [SWS_Lin_00168]. Более новые документы допускают реентерабельность для различных каналов Lin-SWS с. 43. Для R20-11 нормативной является более строгая редакция.

Аналогичное различие существует и для трансивера: LinIf_SetTrcvMode реентерабельна [SWS_LinIf_00544], а вызываемая LinTrcv_SetOpMode — нет [SWS_LinTrcv_00002]. Интерпретация: параллельные вызовы должны быть сериализованы на уровне интеграции.

Multicore. Канал и канал трансивера должны принадлежать к одному и тому же разделу ECUC [SWS_Lin_CONSTR_00279] [SWS_LinTrcv_00177].

Жизненные циклы и режимы работы

Инициализация. Руководство по управлению режимами выполняет инициализацию в следующем порядке: Lin_Init, LinIf_Init, LinSM_Init, LinTp_Init [SWS_Lin_00006] [SWS_LinIf_00198] [SWS_LinSM_00155] ModeManagementGuide с. 54. Положение LinTrcv_Init [SWS_LinTrcv_00001] из первоисточника не ясно. При этом модули устанавливают следующие начальные состояния:

  • LinIf_Init устанавливает в мастере NULL_SCHEDULE [SWS_LinIf_00197] LinIf-SWS с. 90.
  • LinTp_Init устанавливает каждый канал в LINTP_CHANNEL_IDLE [SWS_LinIf_00710].
  • LinSM запускается в LINSM_NO_COM без уведомления ComM или BswM LinSM-SWS с. 23.

Диаграмма состояний: коммуникационные режимы LinSM и состояния каналов LIN драйвера; LIN_CH_SLEEP_PENDING существует только в мастере. Источники: [SWS_LinSM_00220] [SWS_LinSM_00301] LinSM-SWS с. 24 Lin-SWS с. 23 Lin-SWS с. 37

Режим Sleep в мастере. Если ComM запрашивает COMM_NO_COMMUNICATION, LinSM вызывает LinIf_GotoSleep [SWS_LinSM_10208]. Затем LinIf отправляет команду Go-to-sleep с помощью Lin_GoToSleep. При этом канал даже в случае ошибки переходит в LIN_CH_SLEEP_PENDING Lin-SWS с. 43. Подтверждение поступает в LinSM как LinSM_GotoSleepConfirmation [SWS_LinSM_00135].

Диаграмма последовательности: запрос на переход в спящий режим принимается синхронно, однако команда отправляется только в следующей MainFunction модуля LinIf и подтверждается асинхронно. Источники: [SWS_LinSM_00036] [SWS_LinSM_00135] [SWS_LinIf_00521] LinSM-SWS с. 47 LinIf-SWS с. 93

Режим Sleep в слейве. Переход инициируют два события: MRF с NAD 0 [SWS_LinIf_00750] или тайм-аут простоя шины [SWS_LinIf_00755]. LinIf сообщает об обоих событиях через LinSM_GotoSleepIndication [SWS_LinIf_00756] [SWS_LinSM_91000]. Дальнейший ход выполнения LinIf-SWS с. 55:

  1. LinSM вызывает LinIf_GotoSleep.
  2. LinIf переводит драйвер в спящий режим через Lin_GoToSleepInternal и подтверждает это с помощью TRUE [SWS_LinIf_00759].
  3. Если ComM ранее запросил COMM_NO_COMMUNICATION [SWS_LinSM_00230], то ComM получает ComM_BusSM_BusSleepMode [SWS_LinSM_00233].
  4. В противном случае LinSM перезапускает процесс пробуждения [SWS_LinSM_00234].

Опционально трансивер переключается параллельно через LinIf_SetTrcvMode(LINTRCV_TRCV_MODE_SLEEP) [SWS_LinSM_00138] LinIf-SWS с. 137.

Процесс пробуждения со стороны ComM. При COMM_FULL_COMMUNICATION LinSM запускает таймер подтверждения и напрямую вызывает LinIf_Wakeup LinSM-SWS с. 27 LinSM-SWS с. 27. Работающий таймер Silence-after-Wakeup задерживает этот вызов [SWS_LinSM_00237]. LinIf принимает решение на основе флага пробуждения:

  • Если флаг не установлен, LinIf вызывает Lin_Wakeup с импульсом пробуждения [SWS_LinIf_00205] LinIf-SWS с. 89.
  • Если флаг установлен, то Lin_WakeupInternal без импульса, вероятно, достаточно [SWS_Lin_00262].

Слейв подтверждает пробуждение только при первом принятом заголовке [SWS_LinIf_00761].

Внешние события пробуждения. EcuM вызывает LinIf_CheckWakeup. В зависимости от источника LinIf выполняет ветвление на Lin_CheckWakeup или LinTrcv_CheckWakeup [SWS_LinIf_00378] [SWS_Lin_00160]. Об обнаруженном событии драйверы сообщают в EcuM и через LinIf_WakeupConfirmation в LinIf [SWS_LinIf_00715] [SWS_LinTrcv_91002] Lin-SWS с. 42. Уведомление о пробуждении от трансивера контролируется LinIf_SetTrcvWakeupMode [SWS_LinIf_00550] [SWS_LinTrcv_00169].

Обработка ошибок, трассировка DET и деградация

Ошибки разработки (DET). Все модули проверяют параметры и состояние инициализации через DET:

  • LinIf: [SWS_LinIf_00376] [SWS_LinIf_00849]
  • Lin, в том числе LIN_E_STATE_TRANSITION [SWS_Lin_00258] [SWS_Lin_00260]
  • LinSM: [SWS_LinSM_00053] [SWS_LinSM_00240]
  • LinTrcv: [SWS_LinTrcv_00005] LinTrcv-SWS с. 26

Ошибки времени выполнения. Lin обязательно требует Dem_SetEventStatus [SWS_Lin_00234]. Аппаратные тайм-ауты драйвер сообщает как LIN_E_TIMEOUT [SWS_Lin_00290]. В слейве Lin возвращает ошибки как Lin_SlaveErrorType [SWS_Lin_91140] [SWS_Lin_00277]. LinIf в таком случае расценивает ответ как потерянный и сообщает о LINIF_E_RESPONSE, за исключением LIN_ERR_HEADER [SWS_LinIf_00735] [SWS_LinIf_00729]. LinSM сообщает о непоступивших функциях обратного вызова как LINSM_E_CONFIRMATION_TIMEOUT [SWS_LinSM_00224].

Деградация. Несколько механизмов поддерживают упорядоченную работу после возникновения ошибок:

  • Сигнал response_error: ошибки ответа устанавливают сигнал через Com_SendSignal [SWS_LinIf_00744] [SWS_LinIf_00764]. После успешной отправки он сбрасывается [SWS_LinIf_00747] LinIf-SWS с. 58.
  • Согласованность LinSM: при E_NOT_OK LinSM повторно устанавливает прежнее состояние, чтобы ComM и BswM получили индикацию [SWS_LinSM_00177].
  • Прерывания LinTp: при тайм-ауте N_As или N_Cr LinTp прерывает операцию и сообщает E_NOT_OK модулю PduR [SWS_LinIf_00801] [SWS_LinIf_00806].
  • Нехватка буфера: при отсутствии буфера приема LinTp приостанавливает заголовки SRF [SWS_LinIf_00679]. В качестве альтернативы он прерывает процесс и возвращается к расписанию приложения [SWS_LinIf_00792] [SWS_LinIf_00879].
  • Node Configuration: ожидающий ответ LinIf отбрасывает при наступлении тайм-аута N_As [SWS_LinIf_00786].

Сгенерированное ИИ руководство по кластеру для R20-11 на основе предоставленных выдержек из спецификаций. Нормативными являются исключительно связанные элементы спецификации. Утверждения, обозначенные как интерпретация, не подкреплены требованиями.
