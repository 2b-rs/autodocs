Lin_ConfigType тип

Это тип внешней структуры данных, содержащей общие данные инициализации для драйвера LIN и настроек SFR, влияющих на каналы LIN. Указатель на такую ​​структуру предоставляется процедуре инициализации драйвера LIN для настройки драйвера, LIN аппаратного блока и LIN аппаратных каналов.

Lin_FrameCsModelType тип

Этот тип используется для указания модели контрольной суммы, которая будет использоваться для кадра LIN.

Lin_FrameDlType тип

Этот тип используется для указания количества SDU байтов данных для копирования.

Lin_FramePidType тип

Представляет все действительные защищенные идентификаторы, используемые функцией Lin_ Send Frame().

Lin_FrameResponseType тип

Этот тип используется для указания, требуется ли процессору кадров передавать ответную часть кадра LIN.

Lin_PduType тип

Этот тип используется для предоставления PID, модели контрольной суммы, длины данных и указателя SDU от интерфейса LIN к драйверу LIN.

Lin_SlaveErrorType тип

Этот тип представляет типы ошибок ведомого устройства, которые обнаруживаются во время приема заголовка и передачи/приема ответа.

Lin_StatusType тип

LIN состояния операций для LIN канала или кадра, возвращаемые службой API Lin_ Get Status().

Обеспечивает экономически эффективное объединение датчиков и исполнительных механизмов в сеть через Local Interconnect Network в автомобиле.

Кластер модулей LIN Communication реализует стандартизированное подключение подсистем шины LIN через модули LinSM, LinIf, LinTrcv и Lin (SWS COMManager с. 19). Он управляет передачей кадров на основе расписания у master-узлов, а также реактивной обработкой заголовков и пересылкой данных у slave-узлов ([SWS_LinIf_91004], [SWS_Lin_00168]). Одновременно кластер координирует упорядоченный переход между режимом полной коммуникации и спящим режимом, а также автономную обработку ошибок через сигнал response_error ([SWS_LinIf_00763]).

Кластер модулей LIN Communication предоставляет полную реализацию протокола LIN для AUTOSAR и включает в себя менеджер состояний LinSM, интерфейс LinIf (включая транспортный протокол LinTp), драйвер трансивера LinTrcv и драйвер MCAL Lin (SWS COMManager с. 19). Он подключает подсети, датчики и исполнительные механизмы к коммуникационной матрице AUTOSAR и строго разделяет master-узлы с автономным выполнением расписания и чисто реактивно отвечающие slave-узлы ([SWS_LinIf_00197], [SWS_Lin_00272]).

Архитектурная диаграмма: послойная архитектура и взаимосвязи интерфейсов кластера LIN между службами связи, уровнем абстракции и MCAL. Источники: SWS COMManager с. 19, AUTOSAR SWS LINInterface с. 133.

Передача данных на master-ECU осуществляется путем периодического управления драйвером через Lin_SendFrame с последующим опросом статуса через Lin_GetStatus ([SWS_Lin_00168]). На slave-узле, напротив, распознавание заголовка в драйвере приводит к синхронному callback-вызову LinIf_HeaderIndication ([SWS_LinIf_91004]). Интерфейс принимает решение о приеме, ответе или игнорировании на основе PID и подтверждает завершение через LinIf_RxIndication или LinIf_TxConfirmation ([SWS_LinIf_91005], [SWS_LinIf_91006]). Диагностические сообщения обрабатываются встроенным LinTp путем автоматического переключения таблицы расписания ([SWS_LinIf_00641]).

В рабочем цикле LinSM координирует переходы между состояниями LINSM_NO_COM и LINSM_FULL_COM ([SWS_LinSM_00026], [SWS_LinSM_00032]). Пробуждение осуществляется импульсом на шине через Lin_Wakeup ([SWS_Lin_00169]). Переход в спящий режим происходит у master-узла путем активной отправки sleep-кадра, а у slave-узла — после приема команды перехода в сон или при неактивности шины (Bus-Idle) через LinIf_GotoSleep, Lin_GoToSleepInternal и управление переводом трансивера в спящий режим ([SWS_LinSM_00231], [SWS_LinIf_00757]).

Диаграмма последовательности: взаимодействие модулей BSW при переходе slave-узла LIN в спящее состояние после сигнала Bus-Sleep. Источники: [SWS_LinSM_91000], [SWS_LinSM_00231], [SWS_LinIf_00757], AUTOSAR SWS LINStateManager с. 48.

Ошибки коммуникации фиксируются на slave-узлах через LinIf_LinErrorIndication и автономно передаются ведущему узлу в сигнале response_error ([SWS_LinIf_91007], [SWS_LinIf_00763]). Межканальные области синхронизации и строгое разделение между циклическими задачами (LinIf_MainFunction) и ISR драйвера обеспечивают стабильность системы ([SWS_LinIf_00384]).

Системная архитектура & роль кластера модулей

Модульный кластер LIN Communication предоставляет в стеке Basic Software AUTOSAR Classic стандартизированную связь через Local Interconnect Network (LIN) согласно ISO 17987. Он функционирует преимущественно как экономичная подсистемная шина для подключения датчиков и актуаторов в автомобильной сети (AUTOSAR FO Features с. 58). Кластер охватывает несколько уровней архитектуры AUTOSAR: LIN State Manager (LinSM) работает на уровне Communication Services, LIN Interface (LinIf), включая встроенный транспортный протокол (LinTp), формирует Communication Abstraction, LIN Transceiver Driver (LinTrcv) входит в состав ECU Abstraction, а LIN Driver (Lin) располагается как низкоуровневый модуль в Microcontroller Abstraction Layer (MCAL) (SWS COMManager с. 19).

С точки зрения архитектуры кластер строго разграничивает ведущие (Master) и ведомые (Slave) узлы. LIN-Master автономно управляет шинным трафиком с помощью таблиц расписания и генерирует все заголовки (Header), тогда как LIN-Slave сугубо реактивно отвечают на принятые заголовки или анализируют сигналы ([SWS_LinIf_00197], [SWS_Lin_00272]). Для задач диагностики и транспортировки согласно ISO 14229 модуль LIN Interface инкапсулирует функциональность TP, которая обрабатывает сегментированные диагностические сообщения (Master Request Frame MRF и Slave Response Frame SRF) через PduR и DCM ([SWS_LinIf_00351], [SWS_LinIf_00629]). Внешне кластер активно взаимодействует с Communication Manager (ComM), Basic Software Mode Manager (BswM), PDU Router (PduR) и ECU State Manager (EcuM) (SWS COMManager с. 19).

Архитектурная диаграмма: послойная архитектура и взаимосвязи интерфейсов кластера LIN между службами связи, уровнем абстракции и MCAL. Источники: SWS COMManager с. 19, AUTOSAR SWS LINInterface с. 133.

Взаимодействие и пути взаимодействия между модулями

Пути взаимодействия в кластере принципиально различаются в зависимости от роли узла. В LIN-Master модуль LIN Interface через свою периодическую задачу инициирует обработку активной таблицы расписания. Для наступивших кадров передачи LinIf запрашивает полезные данные с помощью механизмов Trigger-Transmit верхнего уровня и передает структуру Lin_PduType в LIN-драйвер через Lin_SendFrame ([SWS_Lin_00232], SWS LINInterface с. 37). Драйвер передает заголовок и данные в неблокирующем режиме ([SWS_Lin_00027]). По истечении максимального времени передачи кадра LinIf определяет результат передачи через Lin_GetStatus ([SWS_Lin_00168], SWS LINInterface с. 35). В слотах приема LinIf считывает данные, помещенные драйвером в буфер, и перенаправляет их на верхние уровни ([SWS_Lin_00233]).

На узле LIN-Slave тракт данных выполняется по событиям: если MCAL-драйвер Lin распознает на аппаратном уровне валидный заголовок с полями Break, Synch и PID, он синхронно вызывает функцию обратного вызова LinIf_HeaderIndication ([SWS_Lin_00280], [SWS_LinIf_91004]). Интерфейс проверяет защищенный идентификатор (PID) по внутренней таблице PID ([SWS_LinIf_00816], [SWS_LinIf_00823]). Если кадр предназначен для отправки, LinIf запрашивает полезные данные, настраивает тип ответа на LIN_FRAMERESPONSE_TX и предоставляет данные драйверу в буфере ([SWS_Lin_00230]). Если кадр сконфигурирован на прием, драйвер после полного приема байтов сообщает об успехе через LinIf_RxIndication ([SWS_LinIf_91005]), после чего LinIf передает данные в PDU Router. Подтверждения отправленных ответов ведомого узла (Slave Response) поступают через LinIf_TxConfirmation ([SWS_LinIf_91006]).

Кроме того, через LIN Interface прозрачно инкапсулируется управление трансивером: запросы режима, такие как LinIf_SetTrcvMode, интерфейс синхронно передает в LinTrcv_SetOpMode ([SWS_LinIf_00544], [SWS_LinTrcv_00002]). При транзакциях транспортного протокола LinTp управляет через BswM_LinTp_RequestMode целенаправленным переключением таблицы расписания ведущего узла между прикладным режимом (LINTP_APPLICATIVE_SCHEDULE), диагностическим запросом (LINTP_DIAG_REQUEST) и диагностическим ответом (LINTP_DIAG_RESPONSE) ([SWS_LinIf_00641], [SWS_LinIf_00642], [SWS_LinIf_00643]).

Диаграмма последовательности: динамический поток управления и данных при индикации заголовка, триггеринге передачи и квитировании приема на узле LIN-Slave. Источники: [SWS_Lin_00280], [SWS_LinIf_91004], [SWS_LinIf_91005], AUTOSAR SWS LINInterface с. 133.

Синхронизация, реентерабельность и контексты задач

Выполнение задач внутри модульного кластера разделено между контекстами циклических задач и низкоуровневыми уровнями прерываний. Ядром циклического управления выполнением в LIN Interface является диспетчеризуемая функция LinIf_MainFunction_<LinIfChannel.ShortName>, которая в обязательном порядке инстанциируется отдельно для каждого сконфигурированного LIN-канала ([SWS_LinIf_00384], [SWS_LinIf_00725]). Она берет на себя переключение слотов расписания, опрос состояния драйвера и обработку таймаутов транспортного протокола ([SWS_LinIf_00800], SWS LINInterface с. 119). Параллельно с этим LinSM_MainFunction управляет таймерами обратного отсчета и подтверждения для асинхронных запросов каналов и пробуждения ([SWS_LinSM_00162], [SWS_LinSM_00159]).

В отличие от уровня задач, подпрограммы MCAL-модуля драйвера Lin при наличии контроллера с управлением по прерываниям или интерфейса UART выполняются в контексте прерывания (ISR) (AUTOSAR CP SWS LINDriver с. 53). Функции обратного вызова LinIf_HeaderIndication, LinIf_RxIndication и LinIf_TxConfirmation синхронно инициируются непосредственно из этого контекста ISR ([SWS_Lin_00280], [SWS_LinIf_91005], [SWS_LinIf_91006]). Это требует строгой защиты критических секций (Exclusive Areas) в LIN Interface: управляющие вызовы, такие как LinIf_Transmit, LinIf_GotoSleep, LinIf_ScheduleRequest или LinIf_Wakeup, могут изменять внутренние структуры каналов только с защитой от параллельного доступа из LinIf_MainFunction или обратных вызовов ISR (SWS LINInterface с. 119).

С точки зрения реентерабельности функции API модулей LinIf и LinSM преимущественно разработаны как реентерабельные для разных каналов или сетей, но нереентерабельные для одного и того же канала ([SWS_LinSM_00126], [SWS_LinIf_00201], [SWS_LinIf_00204]). Аналогично ведут себя службы драйвера в Lin (например, Lin_Wakeup, Lin_GoToSleepInternal), которые должны строго синхронизироваться для каждого физического канала ([SWS_Lin_00167], [SWS_Lin_00169]). В случае простого оборудования UART без многобайтового FIFO LIN-драйвер временно буферизует байты программно ([SWS_Lin_00026]), что, по всей видимости (Interpretation:), при высокой нагрузке на шину приводит к увеличению числа прерываний CPU на ведомых узлах. Типичные жизненные циклы и режимы работы

При запуске системы BswM инициализирует модули BSW в заданной последовательности: сначала инициализируются базовые драйверы Lin_Init и LinTrcv_Init, затем LinIf_Init, LinTp_Init и, наконец, LinSM_Init (ModemanagementGuide с. 54). LinIf_Init по умолчанию устанавливает расписание всех каналов Master в NULL_SCHEDULE ([SWS_LinIf_00233]) и загружает на ведомых узлах предварительно сконфигурированные таблицы NAD и PID ([SWS_LinIf_00767], [SWS_LinIf_00768]). LinSM запускается в состоянии LINSM_NO_COM, не отправляя при инициализации обратных вызовов в ComM или BswM ([SWS_LinSM_00026], [SWS_LinSM_00166]).

Если ComM запрашивает разрешение связи через LinSM_RequestComMode(COMM_FULL_COMMUNICATION), LinSM напрямую инициирует LinIf_Wakeup и запускает таймер контроля ([SWS_LinSM_00047], [SWS_LinSM_00100]). LinIf передает через Lin_Wakeup физический импульс пробуждения в шину ([SWS_LinIf_00205], [SWS_Lin_00043]). Если LinIf сообщает об успешном процессе пробуждения через LinSM_WakeupConfirmation(success=TRUE), состояние переходит в LINSM_FULL_COM ([SWS_LinSM_00049], [SWS_LinSM_00132]). Об этом сигнализируется в ComM через ComM_BusSM_ModeIndication и в BswM через BswM_LinSM_CurrentState ([SWS_LinSM_00033], [SWS_LinSM_00192]). На ведомых узлах шина считается успешно пробужденной только тогда, когда ведущий узел отправляет первый LIN-заголовок и он принимается ([SWS_LinIf_00761], SWS LINStateManager с. 28).

Переход в спящий режим (Go-to-Sleep) имеет принципиальные различия: на ведущем узле запрос COMM_NO_COMMUNICATION приводит к вызову LinIf_GotoSleep ([SWS_LinSM_00036], [SWS_LinSM_10208]). LinIf дает указание драйверу через Lin_GoToSleep отправить стандартизированный кадр Go-to-Sleep в шину ([SWS_Lin_00166], [SWS_Lin_00089]). На ведомом узле, напротив, интерфейс принимает команду Go-to-Sleep или фиксирует таймаут простоя шины (Bus-Idle-Timeout) и информирует LinSM через LinSM_GotoSleepIndication ([SWS_LinSM_91000]). Затем LinSM синхронно вызывает LinIf_GotoSleep ([SWS_LinSM_00231]). Интерфейс локально переключает драйвер через Lin_GoToSleepInternal в состояние LIN_CH_SLEEP ([SWS_LinIf_00757], [SWS_Lin_00095]) и переводит трансивер через LinIf_SetTrcvMode(LINTRCV_TRCV_MODE_SLEEP) в спящее состояние ([SWS_LinIf_00544], AUTOSAR CP SWS LINInterface с. 137). После подтверждения LinSM_GotoSleepConfirmation модуль LinSM окончательно переходит в LINSM_NO_COM ([SWS_LinSM_00046], [SWS_LinSM_00233]).

Диаграмма последовательности: взаимодействие модулей BSW при переходе slave-узла LIN в спящее состояние после сигнала Bus-Sleep. Источники: [SWS_LinSM_91000], [SWS_LinSM_00231], [SWS_LinIf_00757], AUTOSAR SWS LINStateManager с. 48.

Обработка ошибок, трассировка DET и деградация

Кластер имеет многоуровневую концепцию обнаружения ошибок и диагностики. Ошибки разработки фиксируются через Default Error Tracer (Det): о недопустимых параметрах канала или сети сообщают LIN_E_INVALID_CHANNEL ([SWS_Lin_00259]), LINIF_E_NONEXISTENT_CHANNEL ([SWS_LinIf_00539]) или LINSM_E_NONEXISTENT_NETWORK ([SWS_LinSM_00127]). Вызовы неинициализированных модулей влекут за собой LIN_E_UNINIT, LINIF_E_UNINIT или LINSM_E_UNINIT ([SWS_Lin_00258], [SWS_LinSM_00128]). Ошибки трансивера, такие как недопустимые номера сетей, передаются модулем LINTRCV_E_INVALID_LIN_NETWORK в DET ([SWS_LinTrcv_00145]).

Сбои связи, возникающие в процессе работы, классифицируются как ошибки времени выполнения: интерфейс определяет LINIF_E_RESPONSE при ошибочных кадрах, а также LINIF_E_NC_NO_RESPONSE при отсутствии ответов на запросы Node-Configuration ([SWS_LinIf_00729]). О физических ошибках шины и протокола (ошибки кадрирования, ошибки контрольной суммы, ошибки побитового мониторинга) MCAL-драйвер на ведомом узле сообщает через LinIf_LinErrorIndication со статусом Lin_SlaveErrorType ([SWS_LinIf_91007], [SWS_Lin_91140]). На ведущих узлах Lin_GetStatus возвращает подробные коды ошибок, такие как LIN_TX_HEADER_ERROR, LIN_TX_ERROR или LIN_RX_ERROR, в интерфейс ([SWS_Lin_00168], [SWS_Lin_00233]).

Центральным механизмом обработки ошибок для LIN-Slave является стандартизированный сигнал response_error. LIN Interface управляет этим 1-битным сигналом автономно: при возникновении ошибки передачи LinIf устанавливает бит, который передается ведущему узлу в следующем безусловном кадре передачи ([SWS_LinIf_00763], SWS LINInterface с. 58). После успешной передачи кадра LinIf автоматически сбрасывает флаг ([SWS_LinIf_00747]). В диагностическом канале LinTp контролирует строгие временные окна протокола: при отсутствии N-PDU таймеры $N_{As}$ и $N_{Cr}$ штатно прерывают транзакцию и сообщают об E_NOT_OK в PDU Router ([SWS_LinIf_00799], [SWS_LinIf_00804], [SWS_LinIf_00806]). Если в PDU Router не хватает емкости буфера, интерфейс прерывает прием и переключает таблицу расписания ведущего узла обратно в прикладной режим ([SWS_LinIf_00676], [SWS_LinIf_00792]).
