Can_ConfigType тип

Это тип внешней структуры данных, содержащей общие данные инициализации для драйвера CAN и настроек SFR, влияющих на все контроллеры. Кроме того, он содержит указатели на структуры конфигурации контроллера. Содержимое структуры данных инициализации CAN зависит от аппаратного обеспечения.

Can_ControllerStateType тип

Состояния, которые используются несколькими функциями режима контроллера.

Can_ErrorStateType тип

Состояния ошибок контроллера CAN.

Can_ErrorType тип

Перечисление представляет собой расширенный набор CAN типов ошибок, о которых может сообщать типичный CAN HW. Это означает, что не все CAN HW смогут поддерживать полный набор.

Can_HwHandleType тип

Представляет дескрипторы аппаратного объекта аппаратного блока CAN. Для аппаратных устройств CAN с более чем 255 объектами HW используется расширенный диапазон.

Can_HwType тип

Этот тип определяет структуру данных, которая четко предоставляет дескриптор аппаратного объекта, включая соответствующий контроллер CAN и, следовательно, Can Drv, а также конкретный идентификатор Can.

Can_IdType тип

Представляет идентификатор L — PDU. Два старших бита определяют тип кадра: 00 CAN сообщение со стандартом CAN ID 01 CAN FD кадр со стандартом CAN ID 10 CAN сообщение с расширенным CAN ID 11 CAN FD кадром с расширенным CAN ID

Can_PduType тип

Этот тип объединяет Pdu Id (sw Pdu Handle), Sdu length (длина), Sdu Data (sdu) и Can Id (id) для любых CAN L - SDU.

Системная архитектура и роль кластера модулей

Кластер «CAN Communication» охватывает стек CAN платформы Classic Platform от аппаратного обеспечения контроллера до транспортного уровня.

  • Can (CAN Driver): инкапсулирует аппаратное обеспечение контроллера. Он записывает L-PDU с помощью Can_Write в аппаратные объекты [SWS_Can_00233]. При этом передается структура Can_PduType, состоящая из swPduHandle, длины, данных и CAN-ID [SWS_Can_00415].
  • CanIf (CAN Interface): абстрагирует несколько экземпляров драйвера через собственные ControllerId и TransceiverId [SWS_CANIF_00653] [SWS_CANIF_00655].

Верхние уровни не обращаются ни к приемным буферам драйвера, ни к буферам передачи CanIf CanIf с. 48. Сам CanIf обращается к аппаратным буферам исключительно через сервисы драйвера [SWS_CANIF_00023].

CAN Transceiver Driver (CanTrcv) управляет внешними микросхемами трансиверов. Для каждого типа оборудования существует ровно один экземпляр драйвера для всех однотипных трансиверов [SWS_CanTrcv_00016]. Его обобщенная модель состояний отделяет ComM и EcuM от специфичных для микросхем состояний CanTrcv с. 19.

CAN Transport Layer (CanTp) следует стандарту ISO 15765-2, если SWS не исключает обратное [SWS_CanTp_00033]. Он сегментирует и выполняет сборку N-SDU и управляет несколькими соединениями одновременно [SWS_CanTp_00096], например запросом UDS и OBD параллельно CanTp с. 41.

Вверх CanIf связывается через функции обратного вызова (Callbacks), адресат которых определяется конфигурацией CanIf с. 133. Типичными адресатами являются:

  • PduR_CanIfRxIndication [SWS_CANIF_00442]
  • CanTp_RxIndication [SWS_CANIF_00448]
  • CanSM_ControllerBusOff [SWS_CANIF_00559]
  • EcuM_ValidateWakeupEvent [SWS_CANIF_00563]

Контекстная диаграмма: CanIf выполняет центральную роль посредника между Can или CanTrcv и пользователями PduR, CanTp, CanSM и EcuM. Источники: [SWS_CANIF_00318] [SWS_CANIF_00415] [SWS_CANIF_00358] [SWS_CANIF_00711] [SWS_CANIF_00448] CanIf с. 133

Взаимодействие и пути взаимодействия

Путь передачи: CanIf_Transmit [SWS_CANIF_00005] вызывает Can_Write с HTH, принадлежащим к TxPduId [SWS_CANIF_00318]. Если драйвер возвращает E_OK, CanIf также возвращает E_OK [SWS_CANIF_00162].

Если аппаратный объект не свободен, Can_Write сообщает CAN_BUSY [SWS_Can_00039]. При активированной буферизации CanIf помещает L-PDU в CanIfTxBuffer [SWS_CANIF_00381] CanIf с. 138.

При каждом подтверждении передачи выполняется следующая цепочка действий:

  1. CanIf проверяет буферы освободившегося аппаратного объекта [SWS_CANIF_00386].
  2. Он отправляет ожидающий L-PDU с наивысшим приоритетом согласно [SWS_CANIF_00668] [SWS_CANIF_00070].
  3. При E_OK он удаляет его из буфера еще до того, как вернется подтверждение [SWS_CANIF_00183].
  4. Затем CanIf уведомляет пользователя через <User_TxConfirmation> [SWS_CANIF_00383]. Для PduR это PduR_CanIfTxConfirmation [SWS_CANIF_00439].

На схемах более новых релизов здесь указывается LSduR_CanIfTxConfirmation CanIf с. 157. Для R20-11 действует наименование PduR.

Диаграмма последовательности: при CAN_BUSY CanIf буферизует L-PDU и отправляет его при следующем подтверждении передачи в порядке приоритета. Источники: CanIf с. 138 CanIf с. 157 [SWS_CANIF_00381] [SWS_CANIF_00668] [SWS_CANIF_00183]

Путь приема: драйвер сообщает о каждом принятом L-PDU через CanIf_RxIndication [SWS_CANIF_00006]. CanIf обрабатывает его в следующем порядке CanIf с. 73:

  1. программная фильтрация, если она сконфигурирована [SWS_CANIF_00389]
  2. проверка длины данных [SWS_CANIF_00390]
  3. определение целевого уровня [SWS_CANIF_00056] и вызов его сервиса приема [SWS_CANIF_00135]

Опционально CanIf дополнительно сохраняет L-SDU для CanIf_ReadRxPduData [SWS_CANIF_00198] [SWS_CANIF_00199].

Транспортный путь, передача: CanTp_Transmit [SWS_CanTp_00212] работает асинхронно [SWS_CanTp_00176]. Если N-SDU не помещается в N-PDU, CanTp запускает многокадровую передачу [SWS_CanTp_00232]. Полезные данные он запрашивает для каждого сегмента с помощью PduR_CanTpCopyTxData [SWS_CanTp_00086], так как не копирует их внутренне [SWS_CanTp_00298].

Транспортный путь, прием: о SF или FF CanTp сообщает с помощью PduR_CanTpStartOfReception [SWS_CanTp_00079]. Управление потоком ориентируется на буфер, о котором там сообщается [SWS_CanTp_00080] [SWS_CanTp_00082].

В R20-11 CanIf вызывает CanTp_TxConfirmation [SWS_CANIF_00550]. В более новом месте документа вместо этого называется LSduR CanTp с. 64.

Диаграмма последовательности: при сегментированном приеме CanTp управляет передатчиком с помощью Flow Control в зависимости от буфера PduR. Источники: CanTp с. 37 [SWS_CanTp_00079] [SWS_CanTp_00222] [SWS_CanTp_00223] [SWS_CanTp_00084]

Управление трансивером: CanIf перенаправляет сервисы трансивера напрямую:

  • CanIf_SetTrcvMode вызывает CanTrcv_SetOpMode [SWS_CANIF_00358].
  • CanIf_GetTrcvWakeupReason вызывает CanTrcv_GetBusWuReason [SWS_CANIF_00368].
  • CanIf_SetTrcvWakeupMode вызывает CanTrcv_SetWakeupMode [SWS_CANIF_00372].

После завершения смены режима CanTrcv сообщает CanIf_TrcvModeIndication [SWS_CanTrcv_00158]. CanIf передает это дальше в CanSM_TransceiverModeIndication [SWS_CANIF_00712].

Синхронизация, реентерабельность и контексты задач

Can работает по прерываниям или в режиме опроса (Polling). Для опроса существуют циклические функции:

  • Can_MainFunction_Write для подтверждений передачи [SWS_Can_00225]
  • Can_MainFunction_Read для приема [SWS_Can_00226]
  • Can_MainFunction_BusOff [SWS_Can_00227] и Can_MainFunction_Wakeup [SWS_Can_00228]
  • Can_MainFunction_Mode для смены состояний контроллера [SWS_Can_00368]

Поэтому функции обратного вызова CanIf выполняются в зависимости от конфигурации в контексте прерывания или в контексте задачи CanIf с. 155 CanIf с. 156. CanIf_CheckWakeup также может вызываться в обоих контекстах CanIf с. 101.

CanIf защищает вытесняющие обращения к общим ресурсам друг от друга [SWS_CANIF_00064]. Это особенно относится к:

  • буферам передачи [SWS_CANIF_00033]
  • CAN-ID при CanIf_SetDynamicTxId, который может прерываться CanIf_Transmit [SWS_CANIF_00673]

Реэнтрантность определена для каждого сервиса: CanIf_RxIndication является реэнтрантным [SWS_CANIF_00006], CanIf_SetPduMode — нет [SWS_CANIF_00008]. Для коротких критических секций Can предоставляет Can_DisableControllerInterrupts [SWS_Can_00231] и Can_EnableControllerInterrupts [SWS_Can_00232]. Многократная блокировка требует стольких же разблокировок Can с. 61.

В CanTp уровень прерываний и уровень задач разделены:

  • CanTp_RxIndication и CanTp_TxConfirmation должны допускать вызов в контексте прерывания [SWS_CanTp_00235] [SWS_CanTp_00236].
  • Контроль тайм-аутов (N_As, N_Bs, N_Cs, N_Ar, N_Br, N_Cr, STmin) выполняет CanTp_MainFunction [SWS_CanTp_00164]. Ее период конфигурируется [SWS_CanTp_00300].
  • Каждый канал соединения имеет собственные буферы, таймеры и собственный конечный автомат [SWS_CanTp_00122].

CanTrcv циклически проверяет с помощью CanTrcv_MainFunction все шины в режимах STANDBY и SLEEP на наличие событий пробуждения [SWS_CanTrcv_00112].

Жизненные циклы и режимы работы

Инициализация: EcuM инициализирует CanIf, а также драйвер и драйвер трансивера раздельно. После этого контроллеры остаются в состоянии STOPPED CanIf с. 40. Can_Init [SWS_Can_00223] и CanTrcv_Init [SWS_CanTrcv_00001], вероятно, выполняются до CanIf_Init [SWS_CANIF_00001] (интерпретация). Документально подтверждено только то, что используемые CanTrcv драйверы должны быть готовы заранее [SWS_CanTrcv_00099].

После инициализации действуют следующие состояния:

  • CanIf переключает все каналы в CANIF_OFFLINE [SWS_CANIF_00864].
  • CanTrcv_Init переводит каждый трансивер в зависимости от конфигурации в состояние SLEEP или STANDBY [SWS_CanTrcv_00148].
  • CanTp переходит после CanTp_Init из CANTP_OFF в CANTP_ON [SWS_CanTp_00170] и выполняет сегментацию только там [SWS_CanTp_00238].

Режимы контроллера: режимы (Can_ControllerStateType [SWS_Can_91013]) запрашивает CanSM через CanIf_SetControllerMode [SWS_CANIF_00003]. CanIf после этого вызывает Can_SetControllerMode [SWS_CANIF_00308]. Переход выполняется асинхронно и сообщается через CanIf_ControllerModeIndication [SWS_CANIF_00699] модулю CanSM [SWS_CANIF_00711] CanIf с. 152.

Режимы PDU: выше находится режим канала CanIf_PduModeType [SWS_CANIF_00137]. Его можно изменить только в состоянии STARTED [SWS_CANIF_00874]. Если контроллер переходит в STOPPED, действует следующее:

  • CanIf очищает соответствующие буферы передачи [SWS_CANIF_00485].
  • Для незавершенных передач формируется отрицательное подтверждение [SWS_CANIF_00739].
  • Канал переводится в режим оффлайн [SWS_CANIF_00866].

Sleep: CAN_CS_SLEEP переводит канал в CANIF_OFFLINE [SWS_CANIF_00865]. При частичном сетевом взаимодействии (Partial Networking) CanIf дополнительно активирует PnTxFilter [SWS_CANIF_00749]. Он пропускает только сконфигурированные PN-PDU [SWS_CANIF_00750] и деактивируется с первым подтверждением передачи [SWS_CANIF_00751]. Перед переходом в режим пониженного энергопотребления CanSM сбрасывает флаг WUF, чтобы не потерять кадр пробуждения [SWS_CanTrcv_00194] CanTrcv с. 57.

Wakeup: CanIf_CheckWakeup опрашивает драйвер или трансивер [SWS_CANIF_00395]. Он возвращает E_OK, как только какой-либо источник отвечает положительно [SWS_CANIF_00720]. Валидация выполняется через CanIf_CheckValidation [SWS_CANIF_00178] и <User_ValidateWakeupEvent> [SWS_CANIF_00179].

Shutdown: CanTp_Shutdown закрывает все соединения и переводит CanTp в CANTP_OFF [SWS_CanTp_00202]. Верхние уровни при этом не уведомляются [SWS_CanTp_00200]. Для деинициализации существуют Can_DeInit [SWS_Can_91002], CanIf_DeInit [SWS_CANIF_91002] и CanTrcv_DeInit [SWS_CanTrcv_91001]. Условие: ни один контроллер больше не находится в состоянии STARTED, и нет незавершенных передач Can с. 59 CanIf с. 81. После этого трансивер возвращается в NOT_ACTIVE [SWS_CanTrcv_91003].

Диаграмма состояний: CanTrcv_Init ведет из NOT_ACTIVE в SLEEP или STANDBY; CanTrcv_SetOpMode переключает между активными режимами, CanTrcv_DeInit возвращает в NOT_ACTIVE. Интерпретация: прямой переход SLEEP→NORMAL следует легенде схемы (1a–1c). На схеме используется CANIF_TRCV_MODE_*; здесь приведены обозначения R20-11. Источники: CanTrcv с. 19 [SWS_CanTrcv_00148] [SWS_CanTrcv_00102] [SWS_CanTrcv_00120] [SWS_CanTrcv_00121] [SWS_CanTrcv_91003]

Обработка ошибок, трассировка DET и деградация

Ошибки разработки: все модули сообщают о них в DET. Коды ошибок сведены в таблицы для каждого модуля: Can [SWS_Can_91019], CanIf [SWS_CANIF_91006], CanTp [SWS_CanTp_00293], CanTrcv [SWS_CanTrcv_00050]. Типичными являются проверки на недопустимые идентификаторы и указатели, например в CanIf_SetControllerMode [SWS_CANIF_00311] или CanIf_RxIndication [SWS_CANIF_00416]. До инициализации сервисы CanIf отклоняют нормальную работу с кодом E_NOT_OK [SWS_CANIF_00661]; CanTp сообщает в этом случае CANTP_E_UNINIT [SWS_CanTp_00031].

Ошибки времени выполнения отправляются в Det_ReportRuntimeError [SWS_CANIF_91007] [SWS_CanTrcv_91006]. Примеры:

  • неуспешная проверка длины [SWS_CANIF_00168]
  • передача по оффлайн-каналу [SWS_CANIF_00382]
  • отсутствие связи с трансивером [SWS_CanTrcv_00114]

Производственные ошибки поступают в DEM. CanTrcv_MainFunctionDiagnostics сообщает о CANTRCV_E_BUS_ERROR при установленном флаге BUSERR как FAILED. При сброшенном флаге она соответственно сообщает о событии обратно [SWS_CanTrcv_00206] [SWS_CanTrcv_00227]. Функция существует только при CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. CanIf сообщает о производственных ошибках только при возникновении вызвавшего их события [SWS_CANIF_00223].

Security Events: связанные с безопасностью ошибки шины CanIf передает в IdsM [SWS_CANIF_00913]. Источниками являются CanIf_ErrorNotification [SWS_CANIF_00915] [SWS_CANIF_00916] и события Bus-Off [SWS_CANIF_00918].

Bus-Off и перезапуск: Can сообщает о Bus-Off через CanIf_ControllerBusOff [SWS_CANIF_00218]. CanIf после этого переводит канал в оффлайн [SWS_CANIF_00866] и информирует CanSM [SWS_CANIF_00724] CanIf с. 154. Перезапуск запускает CanSM с CanIf_SetControllerMode в STARTED CanIf с. 160. С помощью CanIf_GetTxConfirmationState он проверяет, поступали ли подтверждения передачи с момента запуска [SWS_CANIF_00734] [SWS_CANIF_00740].

Состояние ошибки и счетчики ошибок доступны через отдельные сервисы:

  • CanIf_GetControllerErrorState [SWS_CANIF_91001] с Can_ErrorStateType [SWS_Can_91003]
  • API счетчиков [SWS_CANIF_91003] [SWS_CANIF_91004]

Деградация в CanTp: CanTp прерывает сбойные сессии по отдельности:

  • При тайм-ауте (N_As, N_Bs, N_Cr) он завершает затронутую сессию и сообщает E_NOT_OK модулю PduR [SWS_CanTp_00310] [SWS_CanTp_00316] [SWS_CanTp_00313].
  • После WFTmax кадров FC(WAIT) он прерывает прием [SWS_CanTp_00223].
  • Если CanIf_Transmit возвращает отказ, он завершает текущее соединение [SWS_CanTp_00342] [SWS_CanTp_00343].

Другие каналы при этом остаются незатронутыми, поскольку каждый канал обладает собственными ресурсами [SWS_CanTp_00122].

Модули в кластере

CAN Driver (Can)

Драйвер CAN обеспечивает аппаратно-зависимый доступ к внутренним и внешним контроллерам CAN (CAN 2.0B, CAN FD, CAN XL).

BSW ID 80 27 API (19 функций, 8 типов) #include "Can.h"

CAN Interface (CanIf)

CanIf абстрагирует аппаратные детали CAN и обеспечивает единый доступ к нескольким контроллерам и приемопередатчикам CAN для модулей более высокого уровня (PduR, CanTp, CanNm, CanSM).

BSW ID 60 50 API (47 функций, 3 типа) #include "CanIf.h"

CAN Transceiver Driver (CanTrcv)

Управляет состояниями физических приемопередатчиков шины и обнаружением пробуждения на линиях CAN.

BSW ID 70 23 API (17 функций, 6 типов) #include "CanTrcv.h"

CAN Transport Layer (CanTp)

Обеспечивает сегментацию и повторную сборку CAN сообщений размером до 4095 байт (ISO 15765-2).

BSW ID 35 12 API (11 функций, 1 тип) #include "CanTp.h"
