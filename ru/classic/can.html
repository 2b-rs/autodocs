Can_ConfigType тип

Это тип внешней структуры данных, содержащей общие данные инициализации для драйвера CAN и настроек SFR, влияющих на все контроллеры. Кроме того, он содержит указатели на структуры конфигурации контроллера. Содержимое структуры данных инициализации CAN зависит от аппаратного обеспечения.

Can_ControllerStateType тип

Состояния, которые используются несколькими функциями режима контроллера.

Can_ErrorStateType тип

Состояния ошибок контроллера CAN.

Can_ErrorType тип

Перечисление представляет собой расширенный набор CAN типов ошибок, о которых может сообщать типичный CAN HW. Это означает, что не все CAN HW смогут поддерживать полный набор.

Can_HwHandleType тип

Представляет дескрипторы аппаратного объекта аппаратного блока CAN. Для аппаратных устройств CAN с более чем 255 объектами HW используется расширенный диапазон.

Can_HwType тип

Этот тип определяет структуру данных, которая четко предоставляет дескриптор аппаратного объекта, включая соответствующий контроллер CAN и, следовательно, Can Drv, а также конкретный идентификатор Can.

Can_IdType тип

Представляет идентификатор L — PDU. Два старших бита определяют тип кадра: 00 CAN сообщение со стандартом CAN ID 01 CAN FD кадр со стандартом CAN ID 10 CAN сообщение с расширенным CAN ID 11 CAN FD кадром с расширенным CAN ID

Can_PduType тип

Этот тип объединяет Pdu Id (sw Pdu Handle), Sdu length (длина), Sdu Data (sdu) и Can Id (id) для любых CAN L - SDU.

Предоставляет аппаратные драйверы, абстракцию интерфейсов, сегментацию и управление трансивером для CAN.

Кластер объединяет драйвер CAN, CAN Interface, транспортный протокол согласно ISO 15765-2 и драйвер трансивера в нижнюю часть коммуникационного стека CAN. Верхние уровни отправляют данные через CanIf_Transmit(). CanIf отображает L-PDU на аппаратные объекты, буферизует их при занятом оборудовании и распределяет сообщения о приеме и подтверждении [SWS_CANIF_00005]. CanTp сегментирует большие сообщения и пошагово забирает данные через PduR [SWS_CanTp_00086]. Отправка выполняется только тогда, когда контроллер находится в состоянии CAN_CS_STARTED и PDU-канал готов к отправке; режимами управляет CanSM через CanIf.

Кластер формирует нижнюю часть коммуникационного стека CAN. Can управляет контроллерами и почтовыми ящиками (Mailboxes), CanIf абстрагирует драйверы, контроллеры и трансиверы, CanTp выполняет сегментацию согласно ISO 15765-2, а CanTrcv управляет режимами работы трансивера. CanIf обращается к аппаратным буферам только через сервисы драйвера [SWS_CANIF_00023]. Для верхних уровней он предоставляет единые диапазоны для ControllerId и TransceiverId [SWS_CANIF_00653] [SWS_CANIF_00655].

Контекстная диаграмма: CanIf выступает посредником между PduR, CanTp, CanSM и EcuM с одной стороны и драйверами Can и CanTrcv — с другой. Источники: [SWS_CANIF_00005] [SWS_CANIF_00006] [SWS_CANIF_00358]

При отправке CanIf_Transmit() вызывает Can_Write() с соответствующим HTH [SWS_CANIF_00318]. Если драйвер возвращает CAN_BUSY, CanIf буферизует L-PDU [SWS_CANIF_00381]. Во время подтверждения отправки он отправляет следующую буферизованную запись с наивысшим приоритетом [SWS_CANIF_00668]. Принятые L-PDU проходят в CanIf программную фильтрацию и проверку длины данных перед тем, как CanIf перенаправит их в CanTp или PduR [SWS_CANIF_00389] [SWS_CANIF_00390]. CanTp сам не буферизует полезные данные, а забирает их через PduR_CanTpCopyTxData() или передает через PduR_CanTpCopyRxData() [SWS_CanTp_00086] [SWS_CanTp_00269].

Диаграмма последовательности: прямая отправка или буферизация при CAN_BUSY с последующей досылкой из буфера в CanIf_TxConfirmation. Источники: [SWS_CANIF_00381] [SWS_CANIF_00183]

Can работает по прерываниям или по опросу через свои MainFunctions [SWS_Can_00225] [SWS_Can_00226]. CanTp_RxIndication() должна допускать вызов в контексте прерывания [SWS_CanTp_00235], в то время как CanTp_MainFunction() контролирует таймауты протокола [SWS_CanTp_00164]. CanIf защищает общие буферы от вытесняющего доступа [SWS_CANIF_00064].

После инициализации все каналы CanIf находятся в состоянии CANIF_OFFLINE [SWS_CANIF_00864]. CanSM переключает контроллеры через CanIf_SetControllerMode() [SWS_CANIF_00308]. Состояние SLEEP принудительно устанавливает CANIF_OFFLINE, STOPPED или BusOff принудительно устанавливают CANIF_TX_OFFLINE [SWS_CANIF_00865] [SWS_CANIF_00866]. О BusOff модуль CanIf сообщает в CanSM [SWS_CANIF_00724]. Ошибки направляются в DET; CanTrcv дополнительно сообщает CANTRCV_E_BUS_ERROR в DEM [SWS_CanTrcv_00206]. CanTp прерывает сессии при таймаутах с отрицательным подтверждением [SWS_CanTp_00310].

Системная архитектура и роль кластера

Кластер «CAN Communication» формирует нижнюю часть коммуникационного стека AUTOSAR для CAN. Он простирается от близкого к аппаратному обеспечению драйвера CAN до транспортного протокола, поверх которого работают PduR и DCM. Ядром является CAN Interface, который отвязывает верхние уровни от деталей драйвера и оборудования. Он обращается к аппаратно-специфичным коммуникационным буферам исключительно через сервисы драйвера [SWS_CANIF_00023]. Контроллеры и трансиверы нескольких экземпляров драйвера он абстрагирует через собственные диапазоны для ControllerId и TransceiverId [SWS_CANIF_00653] [SWS_CANIF_00655].

Взаимодействие и пути взаимодействия

Отправка: верхний уровень вызывает CanIf_Transmit() [SWS_CANIF_00005]. CanIf определяет HTH для TxPduId и вызывает Can_Write() со структурой Can_PduType [SWS_CANIF_00318] [SWS_Can_00415]. Если Can_Write() возвращает E_OK, то и CanIf_Transmit() возвращает E_OK [SWS_CANIF_00162]. Если свободного объекта отправки нет, драйвер сообщает CAN_BUSY [SWS_Can_00039]. При включенной буферизации отправки CanIf затем помещает L-PDU в CanIfTxBuffer [SWS_CANIF_00381] [SWS_CANIF_00063] CanIf с. 138.

Подтверждение отправки: после успешной передачи Can вызывает CanIf_TxConfirmation() [SWS_CANIF_00007]. Для этого драйвер запоминает swPduHandle из Can_Write() Can с. 40. При этом CanIf проверяет, есть ли буферизованные записи для освободившегося HTH. Запись с наивысшим приоритетом согласно ISO 11898-1 он отправляет следом и немедленно удаляет ее из буфера [SWS_CANIF_00386] [SWS_CANIF_00070] [SWS_CANIF_00668] [SWS_CANIF_00183]. Затем верхний уровень получает <User_TxConfirmation>(E_OK) [SWS_CANIF_00383].

Диаграмма последовательности: запрос на отправку с прямой передачей или буферизацией при CAN_BUSY и досылкой из буфера во время подтверждения отправки. Источники: [SWS_CANIF_00318] [SWS_CANIF_00381] [SWS_CANIF_00668] [SWS_CANIF_00183] CanIf с. 157

Прием: Can сообщает о принятом L-PDU через CanIf_RxIndication() [SWS_CANIF_00006]. Для BasicCAN-HRH модуль CanIf сначала выполняет программную фильтрацию, а затем проверку длины данных [SWS_CANIF_00389] [SWS_CANIF_00390] [SWS_CANIF_00663]. После этого он передает индикацию сконфигурированному получателю [SWS_CANIF_00415] [SWS_CANIF_00056], например в CanTp_RxIndication [SWS_CANIF_00448] или в PduR_CanIfRxIndication [SWS_CANIF_00442].

Транспортный протокол: CanTp_Transmit() [SWS_CanTp_00212] запускает сегментированную передачу, если данные не помещаются в один N-PDU [SWS_CanTp_00232]. CanTp сам не буферизует полезные данные, а забирает их для каждого SF, FF и CF через PduR_CanTpCopyTxData() [SWS_CanTp_00086] [SWS_CanTp_00298]. Кадры он передает через CanIf_Transmit() [SWS_CanTp_00216]. При приеме SF или FF модуль CanTp запрашивает доступный буфер с помощью PduR_CanTpStartOfReception() [SWS_CanTp_00079] [SWS_CanTp_00080]. Каждый CF он копирует с помощью PduR_CanTpCopyRxData() [SWS_CanTp_00269]. Если буфера для следующего блока недостаточно, CanTp отправляет Flow Control WAIT [SWS_CanTp_00082] [SWS_CanTp_00325] CanTp с. 37.

Трансивер: CanIf_SetTrcvMode() передает запросы режима в CanTrcv_SetOpMode() [SWS_CANIF_00358]. После переключения CanTrcv вызывает CanIf_TrcvModeIndication() [SWS_CanTrcv_00158], и CanIf пересылает уведомление в CanSM [SWS_CANIF_00712]. Точно так же CanIf_GetTrcvWakeupReason() и CanIf_SetTrcvWakeupMode() делегируют вызовы в CanTrcv [SWS_CANIF_00368] [SWS_CANIF_00372].

Синхронизация, реентерабельность и контексты задач

CanIf_Transmit() является реентерабельным для различных PduId, но не для одного и того же PduId [SWS_CANIF_00005]. CanIf должен защищать доступ к общим ресурсам от взаимного вытеснения [SWS_CANIF_00064]. В частности, это касается буферов отправки [SWS_CANIF_00033], CanId динамических L-PDU во время CanIf_SetDynamicTxId() [SWS_CANIF_00673] и буфера приема во время CanIf_ReadRxPduData() [SWS_CANIF_00199].

Can поддерживает работу по прерываниям и по опросу. В зависимости от конфигурации MainFunctions опрашивают подтверждения отправки, прием, BusOff, Wakeup и режим контроллера [SWS_Can_00225] [SWS_Can_00226] [SWS_Can_00227] [SWS_Can_00228] [SWS_Can_00368] CanIf с. 152. Поэтому функции обратного вызова (Callbacks), такие как CanIf_ControllerBusOff(), выполняются либо на уровне прерываний, либо на уровне задач CanIf с. 119. Can_DisableControllerInterrupts() и Can_EnableControllerInterrupts() действуют по принципу вложенности: каждая блокировка требует отдельного снятия [SWS_Can_00231] [SWS_Can_00232] Can с. 61.

CanTp_RxIndication() и CanTp_TxConfirmation() должны допускать вызов в контексте прерывания [SWS_CanTp_00235] [SWS_CanTp_00236]. CanTp_MainFunction() циклически обслуживает таймеры N_As, N_Bs, N_Cs, N_Ar, N_Br, N_Cr и STmin [SWS_CanTp_00213] [SWS_CanTp_00164]. Их такт определяется параметром CanTpMainFunctionPeriod [SWS_CanTp_00300]. Интерпретация: этот период, предположительно, определяет достижимое разрешение таймаутов. Каждое соединение использует собственные буферы, таймеры и собственный автомат состояний [SWS_CanTp_00122] CanTp с. 42. CanTrcv_MainFunction() циклически проверяет шины в состояниях STANDBY и SLEEP на наличие событий пробуждения [SWS_CanTrcv_00013] [SWS_CanTrcv_00112].

Жизненные циклы и режимы работы

EcuM инициализирует CanIf с помощью CanIf_Init(), а драйверы Can и CanTrcv — отдельно каждый CanIf с. 40 [SWS_Can_00223] [SWS_CanTrcv_00001]. CanTrcv_Init() переводит каждый трансивер в зависимости от конфигурации в SLEEP или STANDBY [SWS_CanTrcv_00148]. Драйверы, используемые модулем CanTrcv, должны быть предварительно готовы [SWS_CanTrcv_00099]. После инициализации CanIf ожидает, что контроллеры находятся в состоянии STOPPED, и переключает все каналы в CANIF_OFFLINE [SWS_CANIF_00864]. Вызовы сервисов до инициализации CanIf отклоняет [SWS_CANIF_00661]. Интерпретация: поэтому Can и CanTrcv, вероятно, должны инициализироваться до CanIf. CanTp переходит с помощью CanTp_Init() из CANTP_OFF в CANTP_ON [SWS_CanTp_00027] [SWS_CanTp_00170]. Сегментация выполняется только в состоянии CANTP_ON [SWS_CanTp_00238] CanTp с. 27.

Переключением режимов управляет CanSM: CanIf_SetControllerMode() вызывает Can_SetControllerMode() [SWS_CANIF_00003] [SWS_CANIF_00308]. О завершении Can сообщает асинхронно через CanIf_ControllerModeIndication(), и CanIf пересылает это в CanSM [SWS_CANIF_00699] [SWS_CANIF_00711]. Состояниями контроллера являются UNINIT, STOPPED, STARTED и SLEEP [SWS_Can_91013] Can с. 38. Выше них располагаются режимы PDU-каналов CanIf [SWS_CANIF_00137]. CanIf_SetPduMode() принимается только в состоянии CAN_CS_STARTED [SWS_CANIF_00874]. SLEEP принудительно переводит в CANIF_OFFLINE; STOPPED или BusOff принудительно переводят в CANIF_TX_OFFLINE [SWS_CANIF_00865] [SWS_CANIF_00866].

Диаграмма состояний: режимы PDU-каналов CanIf определяются через CanIf_SetPduMode и переключением режима контроллера. Источники: [SWS_CANIF_00137] [SWS_CANIF_00864] [SWS_CANIF_00865] [SWS_CANIF_00866] [SWS_CANIF_00874] CanIf с. 61

Для пробуждения CanIf_CheckWakeup() опрашивает драйверы через Can_CheckWakeup() или CanTrcv_CheckWakeup() [SWS_CANIF_00395] [SWS_Can_00360] [SWS_CanTrcv_00143]. CanIf_CheckValidation() сообщает о событии пробуждения в <User_ValidateWakeupEvent> только в том случае, если с момента пробуждения был сохранен корректный прием [SWS_CANIF_00178] [SWS_CANIF_00179] [SWS_CANIF_00286] CanIf с. 102. При частичной работе в сети (Partial Networking) PnTxFilter после CAN_CS_SLEEP блокирует все отправки, кроме PN-Filter-PDU. Только подтверждение отправки или прием снимает блокировку [SWS_CANIF_00749] [SWS_CANIF_00750] [SWS_CANIF_00751] [SWS_CANIF_00896]. Перед переходом в режим энергосбережения CanSM сбрасывает флаг WUF через CanIf_ClearTrcvWufFlag(), чтобы не было потеряно пробуждение по кадру [SWS_CANIF_00766] [SWS_CanTrcv_00194] [SWS_CanTrcv_00195] CanTrcv с. 57. Работа модулей завершается с помощью Can_DeInit(), CanIf_DeInit() и CanTrcv_DeInit() [SWS_Can_91002] [SWS_CANIF_91002] [SWS_CanTrcv_91001].

Обработка ошибок, трассировка DET и деградация

Все модули кластера сообщают об ошибках разработки в DET. CanIf делает это, например, при недействительном TxPduId или нулевом указателе [SWS_CANIF_00319] [SWS_CANIF_00320]. При этом CanTp дополнительно возвращает E_NOT_OK [SWS_CanTp_00294]; Can и CanTrcv используют собственные коды ошибок [SWS_Can_91019] [SWS_CanTrcv_00050]. Ошибки времени выполнения касаются, среди прочего, отклоненной длины данных [SWS_CANIF_00168], попыток отправки по каналам в режиме CANIF_OFFLINE [SWS_CANIF_00382], потерянных входящих сообщений [SWS_Can_91020] и отсутствия связи с трансивером [SWS_CanTrcv_00113].

Из рассмотренных свидетельств только CanTrcv указывает запись DEM: CanTrcv_MainFunctionDiagnostics() устанавливает CANTRCV_E_BUS_ERROR в FAILED или PASSED в зависимости от флага BUSERR [SWS_CanTrcv_00218] [SWS_CanTrcv_00206] [SWS_CanTrcv_00227] CanTrcv с. 48.

О BusOff модуль Can сообщает через CanIf_ControllerBusOff() [SWS_CANIF_00218]. После этого CanIf переводит канал в режим CANIF_TX_OFFLINE и информирует CanSM [SWS_CANIF_00866] [SWS_CANIF_00724] CanIf с. 147. При переходе в состояние CAN_CS_STOPPED модуль CanIf очищает буферы отправки и подтверждает незавершенные отправки отрицательно [SWS_CANIF_00485] [SWS_CANIF_00739]. Для восстановления (Recovery) CanSM с помощью CanIf_GetTxConfirmationState() может запросить, поступало ли подтверждение отправки с момента последнего запуска контроллера [SWS_CANIF_00734] [SWS_CANIF_00740] CanIf с. 103. Состояние ошибки и счетчики ошибок можно запросить через CanIf [SWS_CANIF_91001] [SWS_Can_91003] [SWS_CANIF_91003]. Если активирована передача отчетов о событиях безопасности (Security Event Reporting), CanIf сообщает об ошибках шины, а также о событиях Error-Passive и BusOff в IdsM [SWS_CANIF_00913] [SWS_CANIF_00915] [SWS_CANIF_00917] [SWS_CANIF_00918].

Диаграмма последовательности: сообщение BusOff передается от контроллера через Can и CanIf в CanSM; CanIf при этом блокирует путь отправки и сбрасывает буферы отправки. Источники: [SWS_CANIF_00218] [SWS_CANIF_00724] [SWS_CANIF_00866] [SWS_CANIF_00918] [SWS_CANIF_00734] CanIf с. 147

CanTp прерывает сессии при таймаутах и уведомляет верхний уровень отрицательно, например при N_As, N_Bs или N_Cr [SWS_CanTp_00310] [SWS_CanTp_00316] [SWS_CanTp_00313]. Так же CanTp поступает после WFTmax последовательных FC(WAIT) [SWS_CanTp_00223] или при FC с Overflow [SWS_CanTp_00309]. В качестве режима деградации CanIf в режиме CANIF_TX_OFFLINE_ACTIVE подтверждает отправки перед верхними уровнями без фактической отправки в шину [SWS_CANIF_00072].

Сформированное ИИ руководство на основе спецификаций AUTOSAR для модулей Can, CanIf, CanTp и CanTrcv (Classic Platform R20-11). Нормативными являются исключительно требования, на которые даны ссылки; утверждения, обозначенные как интерпретация, источниками не подтверждены.

Модули в кластере

CAN Driver (Can)

Драйвер CAN обеспечивает аппаратно-зависимый доступ к внутренним и внешним контроллерам CAN (CAN 2.0B, CAN FD, CAN XL).

BSW ID 80 27 API (19 функций, 8 типов) #include "Can.h"

CAN Interface (CanIf)

CanIf абстрагирует аппаратные детали CAN и обеспечивает единый доступ к нескольким контроллерам и приемопередатчикам CAN для модулей более высокого уровня (PduR, CanTp, CanNm, CanSM).

BSW ID 60 50 API (47 функций, 3 типа) #include "CanIf.h"

CAN Transceiver Driver (CanTrcv)

Управляет состояниями физических приемопередатчиков шины и обнаружением пробуждения на линиях CAN.

BSW ID 70 23 API (17 функций, 6 типов) #include "CanTrcv.h"

CAN Transport Layer (CanTp)

Обеспечивает сегментацию и повторную сборку CAN сообщений размером до 4095 байт (ISO 15765-2).

BSW ID 35 12 API (11 функций, 1 тип) #include "CanTp.h"
