EcuM_CheckRamHash функция

Эта выноска предназначена для проверки целостности RAM. Цель этого теста — убедиться, что после длительного периода SLEEP содержимое RAM остается согласованным. Проверка не обязательно должна быть исчерпывающей, поскольку во время пробуждения она потребует довольно много времени на обработку. Хорошо спроектированная проверка выполнится быстро и с достаточной вероятностью обнаружит RAM дефекты целостности. Эта спецификация не делает никаких предположений об алгоритме, выбранном для конкретного ECU. Области RAM, которые будут проверяться, должны выбираться тщательно. Это зависит от самого алгоритма проверки и структуры задачи. Содержимое стека задачи, выполняющей проверку RAM, например. скорее всего, это невозможно проверить. Рекомендуется выполнять генерацию хеша и проверку в одной и той же задаче, и чтобы эта задача не была вытесняемой и чтобы между генерацией хэша и проверкой хэша было лишь мало активности. Сама проверка RAM предоставляется разработчиком системы. В случае применения многоядерности и наличия Satellite-Ecu M(s): этот API будет вызываться только Master-EcuM.

uint8 EcuM_CheckRamHash (void);

Этот вызов вызывается EcuM для проверки источника пробуждения. Если обнаружено действительное пробуждение, об этом должно быть сообщено на EcuM через EcuM_ValidateWakeupEvent().

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup функция

Этот вызов вызывается EcuM для опроса источника пробуждения. Он также должен быть вызван ISR источника пробуждения для настройки PLL и проверки других источников пробуждения, которые могут быть подключены к тому же прерыванию.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);
EcuM_ClearWakeupEvent функция

Очищает события пробуждения.

void EcuM_ClearWakeupEvent (EcuM_WakeupSourceType sources);
EcuM_DeterminePbConfiguration функция

Эта выноска должна оценивать некоторые условия, например контакт порта или значение NVRAM, чтобы определить, какая конфигурация после сборки будет использоваться в оставшейся части процесса запуска. Он должен загрузить эти данные конфигурации в область памяти, доступную всем модулям BSW, и вернуть указатель на конфигурацию после сборки EcuM в качестве основы для всех конфигураций после сборки модуля BSW.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources функция

Модуль менеджера ECU вызывает EcuM_DisableWakeupSources для установки источника(ов) пробуждения, определенного в битовом поле WakeupSource, чтобы они не могли разбудить ECU.

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources функция

Модуль менеджера ECU вызывает EcuM_EnableWakeupSource, чтобы позволить разработчику системы уведомить источники пробуждения, определенные в битовом поле WakeupSource, о том, что SLEEP будет введено, и соответствующим образом настроить их источник.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup функция

Этот API вызывается любым модулем SW, источник пробуждения которого проверяется асинхронно (например, асинхронный драйвер Can Trcv), а проверка пробуждения возвращает отрицательный результат (пробуждение по этому источнику отсутствует). API отменяет CheckWakeupTimer для WakeupSource. Если соответствующее CheckWakeupTimer отменено, проверка этого источника пробуждения завершается.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);

Системная архитектура и роль кластера модулей

Кластер «System Services» включает в себя модули, обеспечивающие запуск, режимы работы, Sleep/Shutdown и контроль выполнения программы блока управления Classic Platform. При этом ECU State Manager является системной службой, которая устанавливает конечное состояние аппаратного обеспечения после завершения работы OS (SWS EcuM с. 82, [SWS_EcuM_04020]). Четыре модуля выполняют четко разграниченные роли:

  • BswM арбитрирует входящие индикации режимов ([SWS_BswM_00035]). Правила логически связывают ModeRequestPorts и запускают списки действий True или False (Mode Management Guide с. 32). Действия выполняются исключительно в контексте списка действий ([SWS_BswM_00147]).
  • EcuM инициализирует BSW, запускает и останавливает OS, а также управляет состояниями источников пробуждения ([SWS_EcuM_02811], [SWS_EcuM_04091]). Собственного конечного автомата он не имеет. Смену состояний он принимает от BswM (SWS EcuM с. 99, [SWS_EcuM_04116]).
  • WdgM контролирует Supervised Entities с помощью контрольных точек ([SWS_WdgM_00263]) и формирует на их основе Global Supervision Status ([SWS_WdgM_00360]). Режимы сторожевого таймера он устанавливает через WdgIf_SetMode ([SWS_WdgM_00186]).
  • Wdg управляет внутренними или внешними аппаратными средствами сторожевого таймера ([SWS_Wdg_00161], [SWS_Wdg_00076]). Он обслуживает аппаратное обеспечение до тех пор, пока условие триггера остаётся действительным ([SWS_Wdg_00144]).

Контекстная диаграмма: контекстная диаграмма показывает BswM как модуль, принимающий решения о режимах, EcuM как исполнитель последовательностей жизненного цикла и цепочку контроля WdgM → WdgIf → Wdg → Hardware. Источники: SWS EcuM с. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Взаимодействие и пути взаимодействия

EcuM ↔ BswM (ECU Mode Handling): этот путь активен, если сконфигурирован EcuMModeHandling ([SWS_EcuM_04115]). Компоненты SW-C запрашивают и снова освобождают RUN и POST_RUN через EcuM_RequestRUN и EcuM_RequestPOST_RUN соответственно ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). О результате арбитража EcuM сообщает через BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). Затем BswM устанавливает состояние с помощью EcuM_SetState ([SWS_EcuM_04122]). Как только RTE подтверждает переключение, EcuM сообщает состояние обратно через BswM_EcuM_CurrentState ([SWS_EcuM_04143], [SWS_BswM_91003]).

Путь пробуждения: драйверы сообщают о пробуждениях через EcuM_SetWakeupEvent, который помечает событие как ожидающее ([SWS_EcuM_01117]). Если требуется валидация, EcuM запускает протокол валидации ([SWS_EcuM_02975]). Валидацию выполняет ровно один модуль BSW (SWS EcuM с. 69). Вызов им EcuM_ValidateWakeupEvent уведомляет BswM и ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). О каждой смене состояния источника пробуждения сообщается в BswM как о запросе режима ([SWS_EcuM_04003]).

Диаграмма состояний: диаграмма состояний показывает жизненные циклы источника пробуждения (NONE, PENDING, VALIDATED, EXPIRED) и сообщение в BswM при входе в каждое состояние. Источники: [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM с. 64

WdgM → Wdg: Wdg_SetTriggerCondition принимает таймаут в миллисекундах и внутренне преобразует его с учётом текущего режима в значение счётчика ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). Подпрограмма обслуживания драйвера ведёт себя следующим образом:

  • Если счётчик больше нуля, она декрементирует его и триггерит аппаратное обеспечение ([SWS_Wdg_00134]).
  • При нуле триггеринг прекращается, сторожевой таймер истекает ([SWS_Wdg_00135]).

Интерпретация: WdgIf, вероятно, передаёт режим и условие триггера в соответствующий адресуемый экземпляр Wdg. Несколько экземпляров имеют уникальные имена ([SWS_Wdg_00172]).

EcuM → WdgM (Reset): WdgM_PerformReset является обязательной целью сброса ([SWS_EcuM_04005], [SWS_EcuM_04044]). Она устанавливает условие триггера всех драйверов в 0, и аппаратные сторожевые таймеры вследствие этого вызывают сброс ([SWS_WdgM_00264], SWS WdgM с. 82). В качестве причины выключения доступно ECUM_CAUSE_WDGM ([SWS_EcuM_04045]).

Синхронизация, реентерабельность и контексты задач

BswM_MainFunction: она оценивает все правила, использующие запрос с BSWM_DEFERRED ([SWS_BswM_00075]). Таймеры BswM всегда обрабатываются с отсрочкой ([SWS_BswM_00220]). Напротив, запросы с «immediate» оцениваются немедленно (Mode Management Guide с. 32).

EcuM_MainFunction: она выполняется во всех экземплярах EcuM ([SWS_EcuM_04011]). Она отслеживает таймауты валидации ([SWS_EcuM_04082]) и валидирует кандидатов на пробуждение после WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction: она запускает контроль при первом вызове после WdgM_Init ([SWS_WdgM_00406]) и затем в каждом периоде рассчитывает Global Supervision Status (SWS WdgM с. 34).

Контекст прерывания: Службы пробуждения доступны для вызова из контекста прерывания, контекста OS и контекста без OS ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). Однако они специфицированы как «Non-Reentrant, Non-Interruptible» ([SWS_EcuM_02826], [SWS_EcuM_02828]). Исключением является EcuM_ValidateWakeupEvent: оно реентерабельно и доступно для вызова из контекста прерывания и контекста задачи ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Реентерабельность WdgM и Wdg:

  • WdgM_SetMode, WdgM_DeInit и Wdg_SetTriggerCondition не являются реентерабельными ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • Во время текущей смены режима WdgM_GetMode все еще возвращает старый режим ([SWS_WdgM_00168], SWS WdgM с. 77).
  • Wdg блокирует прерывания для согласованности данных только через предусмотренные механизмы BSW ([SWS_Wdg_00040]).

Multicore: на каждом Core выполняется собственный экземпляр EcuM. Главный EcuM запускает остальные Core (SWS EcuM с. 71). Из этого следуют такие обязанности:

  • Каждый экземпляр обрабатывает события пробуждения своего собственного Core ([SWS_EcuM_04012]).
  • Все локальные для Core BswM инициализируются ([SWS_EcuM_04014]).
  • Для каждого Core резервируется ресурс RES_AUTOSAR_ECUM ([SWS_EcuM_03010]).
  • C-API доступны в каждом разделе, в котором выполняется EcuM ([SWS_EcuM_04095]).

BswM условно реентерабелен для многораздельных систем ([SWS_BswM_00002]).

Жизненные циклы и режимы работы

Запуск (StartPreOS): EcuM_Init выполняет последовательность StartPreOS ([SWS_EcuM_02684]). Она включает в себя:

  • блоки инициализации 0 и 1 в сконфигурированном порядке ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • выбор конфигурации Post-Build ([SWS_EcuM_02906]),
  • проверку согласованности всех конфигураций Post-Build перед первой инициализацией BSW ([SWS_EcuM_02796]).

Согласно описанию структуры, Wdg_Init относится к функциям инициализации, используемым EcuM (SWS EcuM с. 34). Wdg_Init устанавливает режим по умолчанию и таймаут ([SWS_Wdg_00001]).

Запуск (StartPostOS): EcuM_StartupTwo выполняется в задаче, запущенной с помощью StartOS ([SWS_EcuM_02806]). Она запускает SchM и инициализирует BswM ([SWS_EcuM_02932]). BswM_Init требует наличия только инициализированных OS и SchM (SWS BswM с. 69). Дополнительные драйверы BswM может инициализировать на фазе UP, например через EcuM_AL_DriverInitBswM_<x> (SWS EcuM с. 46, [SWS_EcuM_04114]).

Диаграмма последовательности: диаграмма последовательности показывает порядок выполнения StartPreOS и StartPostOS на мастер-Core. Источники: [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM с. 82, SWS EcuM с. 42

Sleep: перед EcuM_GoDownHaltPoll BswM, как правило, должен выбрать цель SLEEP (SWS EcuM с. 54, [SWS_EcuM_91002]). Ход процесса:

  1. GoSleep активирует источники пробуждения; при этом OS остается активной ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. Затем, в зависимости от режима Sleep, следует Halt с RAM-хэшем ([SWS_EcuM_02863]) или Poll ([SWS_EcuM_02962]). Ни одно пробуждение не должно быть потеряно ([SWS_EcuM_02188]).
  3. Пробуждение переводит в последовательность WakeupRestart с повторной инициализацией драйверов ([SWS_EcuM_02963], [SWS_EcuM_02923]).

В R20-11 коллаут опроса называется EcuM_CheckWakeup ([SWS_EcuM_02929]). Только начиная с R21-11 он называется EcuM_CheckWakeupHook (SWS EcuM с. 145).

Сторожевой таймер в режиме Sleep: перед переходом в Sleep WdgM_DeInit переключается в режим Sleep с приемлемыми условиями триггера и останавливает мониторинг (SWS WdgM с. 59, [SWS_WdgM_00407]). Однако описание структуры EcuM называет только WdgM_PerformReset в качестве зависимости WdgM. Поэтому вызов WdgM_DeInit, предположительно, осуществляется через действие BswM или интеграционный код.

Диаграмма последовательности: диаграмма последовательности показывает фазу SLEEP с Halt: GoSleep, RAM-хэш, Wakeup и WakeupRestart. Источники: SWS EcuM с. 54, SWS EcuM с. 55, SWS EcuM с. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown: ход процесса:

  1. OffPreOS выполняет деинициализацию BswM и SchM (SWS EcuM с. 90). После этого BswM больше не обрабатывает режимы ([SWS_BswM_00120]).
  2. В качестве последнего действия EcuM вызывает ShutdownOS ([SWS_EcuM_02952]). Хук завершения работы вызывает EcuM_Shutdown ([SWS_EcuM_02953]).
  3. В завершение следуют EcuM_AL_Reset или EcuM_AL_SwitchOff ([SWS_EcuM_04074], [SWS_EcuM_04075]).

Источники пробуждения должны быть очищены перед Dem_Shutdown и NvM_WriteAll через пользовательские коллауты BswM (SWS EcuM с. 124, [SWS_BswM_00054]). Пробуждение во время завершения работы приводит к перезапуску после его окончания ([SWS_EcuM_02756]). Wdg не имеет собственного интерфейса деинициализации ([SWS_Wdg_00031]).

Обработка ошибок, трассировка DET и деградация

Ошибки разработки (DET):

  • BswM игнорирует индикации до инициализации и сообщает о BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). О неудачных действиях он сообщает как об ошибке времени выполнения BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • EcuM сообщает о дублирующихся запросах RUN и неподходящих освобождениях ([SWS_EcuM_03024], [SWS_EcuM_03023]), а также о неизвестных источниках пробуждения ([SWS_EcuM_02867]).
  • WdgM и Wdg определяют собственные коды ошибок ([SWS_WdgM_00004], [SWS_Wdg_00010]). О неудачном выполнении WdgIf_SetMode WdgM сообщает как о WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Неустранимые ошибки: EcuM перенаправляет их в EcuM_ErrorHook ([SWS_EcuM_04033]). Примерами являются несогласованные конфигурационные данные или неудачная проверка RAM ([SWS_EcuM_91003]). Ошибки, возвращаемые функциями инициализации во время инициализации, EcuM игнорирует ([SWS_EcuM_02980]).

Деградация мониторинга: глобальный статус запускается как WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Смена режима разрешена только в состояниях OK и FAILED ([SWS_WdgM_00145]). Отключение сторожевого таймера может быть запрещено конфигурацией ([SWS_WdgM_00031]). Эскалация происходит следующим образом:

  1. В состоянии EXPIRED реакция на ошибку откладывается на настраиваемое допустимое отклонение (SWS WdgM с. 34).
  2. В состоянии STOPPED WdgM сообщает о WDGM_E_SUPERVISION, после чего следует сброс сторожевого таймера ([SWS_WdgM_00375]).
  3. Неудачная смена режима также приводит к переходу в STOPPED (SWS WdgM с. 57).

Диагностика после сброса: SEID, истекший первым, сохраняется в дважды инвертированном виде в неинициализированной RAM. Он доступен для чтения еще до WdgM_Init ([SWS_WdgM_00348], [SWS_WdgM_00349]). О смене статуса WdgM сообщает через Mode-порты ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset еще существует в R20-11 ([SWS_BswM_00157]), но становится устаревшим начиная с R21-11 (SWS BswM с. 2).

Ошибки драйвера и последняя защита: Wdg сообщает о производственных ошибках WDG_E_MODE_FAILED и WDG_E_DISABLE_REJECTED в DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). Если EcuM_AL_SwitchOff зависает в дедлоке, аппаратный сторожевой таймер сбрасывает блок управления (SWS EcuM с. 141).

BSW ID 42 35 API (32 функции, 3 типа) #include "BswM.h"

Watchdog Manager (WdgM)

Осуществляет текущий контроль, контроль сроков и логический мониторинг хода программы.

BSW ID 13 19 API (11 функций, 8 типов) #include "WdgM.h"

Watchdog Driver (Wdg)

Обслуживание аппаратного сторожевого таймера и настройка режима.

BSW ID 102 5 API (4 функции, 1 тип) #include "Wdg.h"
