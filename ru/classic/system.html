EcuM_CheckRamHash функция

Эта выноска предназначена для проверки целостности RAM. Цель этого теста — убедиться, что после длительного периода SLEEP содержимое RAM остается согласованным. Проверка не обязательно должна быть исчерпывающей, поскольку во время пробуждения она потребует довольно много времени на обработку. Хорошо спроектированная проверка выполнится быстро и с достаточной вероятностью обнаружит RAM дефекты целостности. Эта спецификация не делает никаких предположений об алгоритме, выбранном для конкретного ECU. Области RAM, которые будут проверяться, должны выбираться тщательно. Это зависит от самого алгоритма проверки и структуры задачи. Содержимое стека задачи, выполняющей проверку RAM, например. скорее всего, это невозможно проверить. Рекомендуется выполнять генерацию хеша и проверку в одной и той же задаче, и чтобы эта задача не была вытесняемой и чтобы между генерацией хэша и проверкой хэша было лишь мало активности. Сама проверка RAM предоставляется разработчиком системы. В случае применения многоядерности и наличия Satellite-Ecu M(s): этот API будет вызываться только Master-EcuM.

uint8 EcuM_CheckRamHash (void);

Этот вызов вызывается EcuM для опроса источника пробуждения. Он также должен быть вызван ISR источника пробуждения для настройки PLL и проверки других источников пробуждения, которые могут быть подключены к тому же прерыванию.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);
EcuM_ClearWakeupEvent функция

EcuM_DeterminePbConfiguration функция

Эта выноска должна оценивать некоторые условия, например контакт порта или значение NVRAM, чтобы определить, какая конфигурация после сборки будет использоваться в оставшейся части процесса запуска. Он должен загрузить эти данные конфигурации в область памяти, доступную всем модулям BSW, и вернуть указатель на конфигурацию после сборки EcuM в качестве основы для всех конфигураций после сборки модуля BSW.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources функция

Модуль менеджера ECU вызывает EcuM_DisableWakeupSources для установки источника(ов) пробуждения, определенного в битовом поле WakeupSource, чтобы они не могли разбудить ECU.

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources функция

Модуль менеджера ECU вызывает EcuM_EnableWakeupSource, чтобы позволить разработчику системы уведомить источники пробуждения, определенные в битовом поле WakeupSource, о том, что SLEEP будет введено, и соответствующим образом настроить их источник.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup функция

Этот API вызывается любым модулем SW, источник пробуждения которого проверяется асинхронно (например, асинхронный драйвер Can Trcv), а проверка пробуждения возвращает отрицательный результат (пробуждение по этому источнику отсутствует). API отменяет CheckWakeupTimer для WakeupSource. Если соответствующее CheckWakeupTimer отменено, проверка этого источника пробуждения завершается.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook функция

1. Системная архитектура и роль модульного кластера

Кластер модулей System Services образует функциональную основу AUTOSAR Classic Platform. Он включает в себя BSW Mode Manager (BswM), ECU State Manager (EcuM), Watchdog Manager (WdgM), а также низкоуровневый Watchdog Driver (Wdg) SWS_ECUStateManager с. 35. Совместно эти модули управляют целостным жизненным циклом ECU, координируют низкоуровневые и прикладные режимы работы, а также обеспечивают временной и логический контроль выполнения программ для соблюдения функциональной безопасности SafetyConceptStatusReport с. 15.

В многоуровневой архитектуре AUTOSAR BswM, EcuM и WdgM располагаются на уровне System Services над уровнями абстракции и драйверов, в то время как Watchdog Driver (Wdg) в составе Microcontroller Abstraction Layer (MCAL) обслуживает аппаратные регистры сторожевого таймера [SWS_Wdg_00106]. При этом EcuM в гибком варианте реализации (EcuM Flex) выступает в роли связующего звена с аппаратным обеспечением для ранних последовательностей начальной загрузки и поздних последовательностей отключения до и после запуска операционной системы соответственно. Он больше не имеет собственного сложного конечного автомата для режимов приложения, а делегирует арбитраж режимов модулю BswM SWS_ECUStateManager с. 103. Внешние диагностические стандарты, такие как UDS (ISO 14229), и протоколы сетевого управления связываются непосредственно с вычислением правил модуля BswM через определенные интерфейсы BSW (такие как сервис 0x28 CommunicationControl через Dcm) [SWS_BswM_00048].

Контекстная диаграмма: архитектура и взаимодействие System Services с BSW, RTE и аппаратным обеспечением. Источники: SWS_ECUStateManager с. 34, AUTOSAR_EXP_ModeManagementGuide с. 61.

2. Взаимодействие и пути интеракции между модулями

Взаимодействие внутри кластера характеризуется четко разграниченными связями управления и оповещения. В рамках ECU Mode Handling модуль EcuM принимает запросы на такие состояния, как RUN или POST_RUN, от программных компонентов (SW-C) и передает агрегированный результат арбитража через [SWS_BswM_91004] модулю BswM ModeManagementGuide с. 34. Поскольку EcuM не принимает собственного решения о переходе, BswM вычисляет сконфигурированные логические правила и синхронно предписывает целевое состояние через EcuM_SetState модулю [SWS_EcuM_04116]. Затем EcuM транслирует это состояние через RTE в приложение и подтверждает текущий статус выполнения модулю BswM через BswM_EcuM_CurrentState [SWS_BswM_91003].

Параллельный путь взаимодействия соединяет BswM, WdgM и Wdg. Программные компоненты и модули BSW сообщают о достижении определенных контрольных точек модулю WdgM, который определяет на их основе локальный и глобальный статус мониторинга SWS_WatchdogManager с. 51. Изменения состояния локального мониторинга WdgM предоставляет через выделенные порты режимов [SWS_WdgM_00148]. В зависимости от вышестоящего состояния системы BswM переключает режим работы Watchdog Manager через WdgM_SetMode [SWS_WdgM_00154]. После этого WdgM настраивает Watchdog Driver (Wdg) через Watchdog Interface (WdgIf) и управляет аппаратным триггированием через Wdg_SetTriggerCondition [SWS_Wdg_00155].

Диаграмма последовательности: путь взаимодействия при обработке режимов ECU между SW-C, EcuM, BswM и RTE. Источники: SWS_ECUStateManager с. 103, ModeManagementGuide с. 34.

3. Синхронизация, реентерабельность и контексты задач

Выполнение System Services детерминированно распределяется по периодическим уровням задач, асинхронным функциям обратного вызова и контекстам прерываний. Периодическую основную нагрузку управления режимами несет BswM_MainFunction, которая вызывается в контексте задачи OS планировщиком BSW Scheduler (SchM) и обрабатывает все правила, требующие отложенного вычисления [SWS_BswM_00053]. При возникновении событий с немедленным вычислением правил они обрабатываются непосредственно синхронно в контексте вызывающей индикации BSW или API SW-C ModemanagementGuide с. 31.

В многоядерных системах стандартизация требует строгого распределения ресурсов. BswM_Init спроектирован условно реентерабельным, чтобы обеспечить возможность раздельного инстанцирования для каждого раздела или ядра процессора [SWS_BswM_00002]. Во время фаз сна и удержания EcuM резервирует собственные ресурсы OS ядра (RES_AUTOSAR_ECUM_<core#>), чтобы гарантировать синхронизацию между ведущими и ведомыми ядрами (Master и Slave) [SWS_EcuM_03010]. Инициализация драйверов через EcuM_AL_DriverInitZero и EcuM_AL_DriverInitOne вызывается отдельно на каждом ядре и инициализирует исключительно локальные для ядра модули MCAL [SWS_EcuM_04145]. Очистка событий пробуждения через EcuM_ClearWakeupEvent явно является непрерываемой и может выполняться как из контекста задач, так и из контекстов прерываний [SWS_EcuM_02807].

4. Типичные жизненные циклы и режимы работы

Жизненный цикл электронного блока управления нормативно подразделяется на фазы STARTUP, UP, SHUTDOWN и SLEEP [SWS_EcuM_91005]. Фаза STARTUP начинается до запуска операционной системы в последовательности StartPreOS с вызова EcuM_Init, анализа причины сброса и загрузки конфигурации Post-Build через EcuM_DeterminePbConfiguration AUTOSAR_SWS_ECUStateManager с. 38. После передачи управления операционной системе через StartOS модуль EcuM в StartPostOS инициализирует SchM, а также BswM [SWS_EcuM_02934]. Затем BswM берет управление на себя и запускает оставшиеся модули BSW, а также приложение.

В процессе штатной работы (фаза UP) EcuM и BswM управляют режимами RUN и POST_RUN, а также опциональной службой Alarm Clock SWS_ECUStateManager с. 75. При переходе в состояние сна (SLEEP) кластер структурно различает HALT (останавливает CPU) и POLL (пониженная тактовая частота CPU) SWS_ECUStateManager с. 54. Предварительно вызов WdgM_DeInit деинициализирует Watchdog Manager и корректирует тайм-ауты триггеров, чтобы предотвратить нежелательные сбросы во время завершения работы [SWS_WdgM_00261]. В последовательности опроса EcuM блокируется в цикле проверки с периодическими вызовами EcuM_SleepActivity и EcuM_CheckWakeupHook до тех пор, пока не будет обнаружено событие пробуждения [SWS_EcuM_03020].

Обнаруженные события пробуждения проходят строгое управление состояниями от ECUM_WKSTATUS_NONE через PENDING до VALIDATED или EXPIRED [SWS_EcuM_04091]. О каждом изменении статуса EcuM синхронно сигнализирует модулю BswM с помощью BswM_EcuM_CurrentWakeup [SWS_BswM_00131]. Валидация пробуждения защищает от переходных помех на шине и отслеживает временное окно с помощью конфигурируемых таймеров валидации [SWS_EcuM_04004]. Если жизненный цикл завершается в фазе SHUTDOWN, OffPreOS деактивирует BswM и SchM перед тем, как OffPostOS сбросит ECU или отключит питание через интеграционные коллауты, такие как EcuM_AL_Reset или EcuM_AL_SwitchOff AUTOSAR_SWS_ECUStateManager с. 49.

Диаграмма состояний: конечный автомат источников пробуждения модуля EcuM с уведомлением BswM. Источники: AUTOSAR_SWS_ECUStateManager с. 60, [SWS_EcuM_04091].

5. Обработка ошибок, трассировка DET и деградация

Для обнаружения ошибок времени выполнения и конфигурации кластер интегрирует стандартизированные механизмы оповещения в Default Error Tracer (Det). Если сущность пытается через EcuM_ReleasePOST_RUN выполнить деактивацию без предварительного запроса, EcuM сообщает об ошибке разработки ECUM_E_MISMATCHED_RUN_RELEASE в Det [SWS_EcuM_03026]. Множественные запросы одного и того же пользователя фиксируются с помощью ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03025]. Точно так же WdgM отслеживает вызовы API в неинициализированном состоянии и сообщает WDGM_E_UNINIT, если службы вызываются до завершения инициализации [SWS_WdgM_00288].

Контроль безопасности опирается на трехступенчатый функциональный контроль модуля WdgM (Alive Supervision, Deadline Supervision и логический контроль потока управления) SafetyConceptStatusReport с. 47. Если ошибка мониторинга приводит к нарушению допусков погрешностей, глобальный статус мониторинга переходит из WDGM_GLOBAL_STATUS_OK через FAILED в WDGM_GLOBAL_STATUS_EXPIRED и, наконец, в STOPPED [SWS_WdgM_00387]. В этом состоянии WdgM устанавливает условие триггера для всех драйверов сторожевого таймера в 0, в результате чего аппаратный сторожевой таймер незамедлительно сбрасывает микроконтроллер [SWS_WdgM_00232]. Для контролируемых аварийных сбросов WdgM предоставляет сервис WdgM_PerformReset, который останавливает непрерывный повторный триггинг и форсирует аппаратный сброс [SWS_WdgM_00264]. Для защиты после длительных фаз сна EcuM также проверяет целостность энергозависимой памяти с помощью EcuM_CheckRamHash, чтобы перехватить некорректные перезапуски при повреждении RAM [SWS_EcuM_02921].
