Роль: единый доступ NvM к Fee и Ea

Memory Abstraction Interface (MemIf) является верхним уровнем Memory Hardware Abstraction. Он скрывает от верхних уровней то, сколько модулей Fee и Ea расположено под ним, и предоставляет им виртуальную сегментацию в едином линейном адресном пространстве (SWS MemIf с. 7). Согласно SRS, MemIf заменяет прежние интерфейсные уровни драйверов для EEPROM и Flash. Менеджер NVRAM может обращаться через него к нескольким модулям абстракции без необходимости внесения изменений при замене драйвера памяти или микросхемы памяти (SRS MemHwAb с. 5).

MemIf не имеет собственного поведения при работе с памятью. Его API отображается на API нижележащих модулей абстракции. В отношении функционального поведения спецификация ссылается на эти модули или на драйверы памяти (SWS MemIf с. 17). Соответственно, каждое определение службы описывает лишь вызов одноименной функции выбранного модуля, например в MemIf_Read [SWS_MemIf_00039] и MemIf_Write [SWS_MemIf_00040]. Требуемые функции Ea перечислены как Required Interfaces [SWS_MemIf_00047].

Диаграммы более поздних релизов показывают под Fee или Ea дополнительно MemAcc и Mem. Вызов MemIf_Write → Fee_Write остается там неизменным (SWS Fee с. 48). Следующая диаграмма показывает интеграцию с напрямую подключенными драйверами, как представлено в последовательности Ea_Write (SWS Ea с. 41).

Контекстная диаграмма: MemIf распределяет задания NvM на Fee или Ea; драйверы и обратная связь по заданиям для NvM находятся вне MemIf. Источники: SWS MemIf с. 7, SWS Fls с. 58, SWS Ea с. 41, [SWS_MemIf_00048]

Выбор устройства через DeviceIndex: макрос или таблица диспетчеризации

Параметр DeviceIndex выбирает модуль абстракции и тем самым устройство памяти. Если сконфигурирован только один модуль абстракции, параметр игнорируется. В этом случае MemIf должен быть реализован как набор макросов, которые напрямую отображаются на API модуля, например #define MemIf_Write(DeviceIndex, BlockNumber, DataPtr) Fee_Write(BlockNumber, DataPtr) (SWS MemIf с. 17, по состоянию на R24-11). SRS указывает на то же самое: если библиотека производителя заменяет все модули Fee и Ea, MemIf состоит только из макросов (SRS MemHwAb с. 5).

Если сконфигурировано несколько модулей, MemIf должен отображать вызовы на соответствующий модуль с использованием эффективных механизмов. Спецификация называет для этого таблицы указателей на функции. Интерпретация обрезанного там примечания: DeviceIndex, вероятно, служит индексом для этих таблиц (SWS MemIf с. 17).

Для типа параметра существует различие между релизами. В R20-11 DeviceIndex имеет тип uint8 ([SWS_MemIf_00039], [SWS_MemIf_00041]). Фрагменты документов из R23-11 и последующих показывают uint16 (SWS MemIf с. 18). Для R20-11 действует uint8.

Диаграмма деятельности: конфигурация определяет, попадает ли вызов в Fee/Ea напрямую через макрос или после проверки через DeviceIndex. Источники: SWS MemIf с. 17, [SWS_MemIf_00006], [SWS_MemIf_00039]

«Синхронно» относится только к принятию задания. Сама работа выполняется асинхронно в циклических функциях Main нижележащих модулей. В последовательности Ea_Write это происходит в цикле по Eep_MainFunction в задаче BSW (SWS Ea с. 41). Последовательность Fee_Write согласно спецификации применима и к остальным асинхронным службам (SWS Fee с. 48). Возвращаемое значение MemIf_Write является возвращаемым значением вызванной функции модуля [SWS_MemIf_00040].

О завершении задания NvM узнает одним из двух способов:

  • Модуль абстракции вызывает NvM_JobEndNotification напрямую; MemIf в этом не участвует (SWS Fee с. 48).
  • NvM опрашивает MemIf_GetJobResult в режиме опроса [SWS_MemIf_00043].

Сам API MemIf не содержит функции обратного вызова [SWS_MemIf_00038].

Диаграмма последовательности: MemIf_Write возвращает управление сразу после перенаправления; выполнение и сообщение о результате происходят асинхронно. Источники: SWS Ea с. 41, SWS Fee с. 48, [SWS_MemIf_00040], [SWS_MemIf_00043]

Статус устройства, результат задания и рабочий режим

MemIf_GetStatus [SWS_MemIf_00042] возвращает значение MemIf_StatusType [SWS_MemIf_00064]. Возможными значениями являются MEMIF_UNINIT, MEMIF_IDLE, MEMIF_BUSY и MEMIF_BUSY_INTERNAL. При MEMIF_BUSY_INTERNAL модуль абстракции занят внутренним управлением; драйвер под ним при этом может быть занят или свободен. Fee сообщает это значение, например, во время реорганизации флеш-памяти (SWS Fee с. 30). Те же типы используют и драйверы, например Fls_GetStatus (SWS Fls с. 35). Таким образом, типы из MemIf.h образуют общий словарь стека памяти.

Диаграмма состояний: изменение состояния модуля абстракции, как его транслирует MemIf_GetStatus. Источники: [SWS_MemIf_00064], SWS Fee с. 30

MemIf_GetJobResult возвращает MemIf_JobResultType [SWS_MemIf_00065]. Обзор значений:

  • MEMIF_JOB_OK и MEMIF_JOB_FAILED: задание завершено успешно или неуспешно соответственно.
  • MEMIF_JOB_PENDING: задание еще не завершено.
  • MEMIF_JOB_CANCELED: задание отменено.
  • MEMIF_BLOCK_INCONSISTENT: блок несогласован или не найден.
  • MEMIF_BLOCK_INVALID: блок помечен как недействительный.

Запросить можно только результат последнего принятого задания (SWS Fee с. 31). В драйвере флеш-памяти все типы заданий разделяют один результат, который при каждом новом задании перезаписывается на MEMIF_JOB_PENDING (SWS Fls с. 36).

Диаграмма состояний: жизненный цикл результата задания от принятия до конечного значения. Источники: [SWS_MemIf_00065], SWS Fls с. 36, SWS Fee с. 31

MemIf_SetMode — единственная служба заданий, не имеющая DeviceIndex. Он вызывает функции SetMode всех нижележащих модулей [SWS_MemIf_00038]. Параметр MemIf_ModeType принимает MEMIF_MODE_SLOW и MEMIF_MODE_FAST [SWS_MemIf_00066]. Драйверы интерпретируют это как обычный доступ по SPI или SPI-burst (SWS Eep с. 34). Eep_SetMode не разрешается вызывать во время выполняющейся операции. Fls_SetMode отклоняет смену режима в состоянии «busy» (SWS Fls с. 42). Интерпретация: поэтому вызов MemIf_SetMode, вероятно, целесообразен только тогда, когда ни одно устройство не обрабатывает задание.

Отмена выполняющихся заданий

MemIf_Cancel не возвращает значения и передает отмену выбранному модулю [SWS_MemIf_00041]. Fee_Cancel и Ea_Cancel сами выполняются синхронно, но являются асинхронными по отношению к аппаратному обеспечению (SWS Fee с. 45, SWS Ea с. 44). В тракте Flash отмена передается далее в Fls_Cancel. Обратная связь об ошибке возвращается через Fee_JobErrorNotification и NvM_JobErrorNotification обратно в NvM (SWS Fls с. 58). После этого результат задания сообщает MEMIF_JOB_CANCELED, что Fee классифицирует как «неудачно» (SWS Fee с. 31).

Для планирования действует граничное условие: Fls_Cancel не разрешается вызывать во время выполняющейся Fls_MainFunction. Это можно обеспечить двумя способами (SWS Fls с. 58):

  • Функции заданий NvM и драйвера выполняются последовательно в одной и той же задаче.
  • Задача функции Main является непрерываемой.

Диаграмма последовательности: отмена выполняется синхронно вниз; сообщение об ошибке передается в NvM в обход MemIf. Источники: SWS Fls с. 58, [SWS_MemIf_00041], SWS Fee с. 31

Интеграция: заголовки, зависимости и отображение памяти

Структура файлов выглядит следующим образом (SWS MemIf с. 10):

  • MemIf.h подключает заголовки модулей абстракции (Fee.h, Ea.h), MemIf_Cfg.h (с MemIf_Types.h) и Std_Types.h.
  • MemIf.c подключает MemIf_MemMap.h и опционально Det.h.

Std_ReturnType и Std_VersionInfoType импортируются из Std_Types.h [SWS_MemIf_00037]. Det_ReportError является опциональным интерфейсом [SWS_MemIf_00048].

Контекстная диаграмма: отношения включения MemIf с конфигурацией, стандартными типами, Fee/Ea и DET. Источники: SWS MemIf с. 10, [SWS_MemIf_00047]

Что касается отображения памяти, руководство по распределению приводит MemIf наряду с FLS и FEE в качестве примера для «Type I». Чтобы ограничить область действия одним ядром, можно использовать SwAddrMethod с локальной областью действия (EXP BSWDistribution с. 31). Спецификация MemoryMapping показывает MemIf как часть кластера ICC2 MEM. В нем MemIf_SetMode является BswCalledEntity, а модуль имеет префикс секции MEMIF (SWS MemMap с. 53).

Поведение при ошибке

MemIf определяет две ошибки разработки [SWS_MemIf_00006]:

  • MEMIF_E_PARAM_DEVICE (0x01): неверный индекс устройства.
  • MEMIF_E_PARAM_POINTER (0x02): указатель NULL в качестве аргумента.

Предположительно, ошибка указателя относится к параметрам DataBufferPtr и VersionInfoPtr. Сообщение передается через Det_ReportError [SWS_MemIf_00048]. При активном обнаружении ошибок и обнаруженной ошибке действует следующее:

  • Read, Write, InvalidateBlock и EraseImmediateBlock возвращают E_NOT_OK ([SWS_MemIf_00044], [SWS_MemIf_00046]).
  • MemIf_GetJobResult возвращает MEMIF_JOB_FAILED (SWS MemIf с. 21).

Специфические коды ошибок разработки API не возвращает (SWS MemIf с. 12).

Ошибки времени выполнения из Fee или Ea модуль MemIf сам не обрабатывает; предусмотренная реакция — «N/A». Только в режиме опроса NvM узнает об ошибке через MemIf_GetJobResult с результатом MEMIF_JOB_FAILED (ErrorDescription с. 58, ErrorDescription с. 60, соответственно R20-11). Неинициализированный Fee можно распознать по запросу его состояния (ErrorDescription с. 53).

Восстановление берет на себя NvM. Если затронут процесс записи, он увеличивает счетчик повторов и прерывает операцию после превышения предела. Об ошибке он сообщает в DEM; через NvM_GetErrorStatus затем можно запросить NVM_REQ_NOT_OK (EXP ErrorDescription с. 45, EXP ErrorDescription с. 58, по состоянию на R25-11). MEMIF_BLOCK_INCONSISTENT и MEMIF_BLOCK_INVALID, напротив, описывают состояние содержимого блока и передаются без изменений [SWS_MemIf_00065].

Диаграмма деятельности: в зависимости от конфигурации стека ошибка времени выполнения поступает в NvM путем опроса через MemIf или через обратный вызов; реакция возлагается на NvM. Источники: ErrorDescription с. 58, EXP ErrorDescription с. 45, [SWS_MemIf_00043]

Использование

Синхронная функция MemIf_Read ([SWS_MemIf_00039]) вызывает функцию Read нижележащего модуля абстракции памяти, выбранного через параметр DeviceIndex. Функция имеет идентификатор службы (Service ID) 0x02 и объявлена через заголовочный файл MemIf.h.

Передаваемые параметры согласно [SWS_MemIf_00039] включают:

  • DeviceIndex (входной, uint8): выбирает базовый модуль абстракции памяти.
  • BlockNumber (входной, uint16): указывает номер блока.
  • BlockOffset (входной, uint16): определяет смещение внутри блока.
  • DataBufferPtr (выходной, uint8*): указатель на буфер данных для результата чтения.
  • Length (входной, uint16): определяет длину считываемых данных.

Обработка ошибок и возвращаемые значения

В качестве типа возвращаемого значения функция Std_ReturnType возвращает ([SWS_MemIf_00039]):

  • если обнаружение ошибок разработки (Development Error Detection) для Memory Abstraction Interface активировано и обнаружена ошибка разработки согласно [SWS_MemIf_00022], функция возвращает E_NOT_OK.
  • В противном случае она возвращает значение, возвращаемое вызванной функцией нижележащего модуля.

Параллелизм и ограничения

Спецификация определяет MemIf_Read как нереентрабельную (Non Reentrant), а также синхронную (Synchronous) ([SWS_MemIf_00039]). Интерпретация: в связи с отсутствием реентрабельности одновременный вызов из прерывающих контекстов или параллельных задач, вероятно, недопустим и требует координации вызовов на стороне вызывающего компонента.

Использование MemIf_JobResultType

Перечислимый тип MemIf_JobResultType ([SWS_MemIf_00065]) предоставляется через заголовочный файл MemIf.h и обозначает результат последнего выполненного задания (Job) в модуле MemIf.

Тип включает следующие значения статуса:

  • MEMIF_JOB_OK: задание успешно завершено.
  • MEMIF_JOB_FAILED: задание завершено неуспешно.
  • MEMIF_JOB_PENDING: задание ещё не завершено и находится в обработке.
  • MEMIF_JOB_CANCELED: задание было отменено.
  • MEMIF_BLOCK_INCONSISTENT: запрошенный блок противоречив (может содержать повреждённые данные) или не был найден.
  • MEMIF_BLOCK_INVALID: запрошенный блок помечен как недействительный; запрошенная операция не может быть выполнена.

Значения перечисления различают общий статус выполнения и причины ошибок, относящиеся к блоку. В то время как MEMIF_JOB_FAILED сигнализирует об общем сбое, MEMIF_BLOCK_INCONSISTENT и MEMIF_BLOCK_INVALID позволяют целенаправленно реагировать на ошибки нарушения целостности или валидности затронутого блока.

Интерпретация: наличие MEMIF_JOB_PENDING указывает на асинхронную обработку заданий; вышележащие модули, вероятно, используют это возвращаемое значение для синхронизации статуса или для опроса момента завершения.

<h4>Роль: единый доступ NvM к Fee и Ea</h4>
<p>Memory Abstraction Interface (MemIf) является верхним уровнем Memory Hardware Abstraction. Он скрывает от верхних уровней то, сколько модулей Fee и Ea расположено под ним, и предоставляет им виртуальную сегментацию в едином линейном адресном пространстве (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYABSTRACTIONINTERFACE.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYABSTRACTIONINTERFACE">SWS MemIf с. 7</a>). Согласно SRS, MemIf заменяет прежние интерфейсные уровни драйверов для EEPROM и Flash. Менеджер NVRAM может обращаться через него к нескольким модулям абстракции без необходимости внесения изменений при замене драйвера памяти или микросхемы памяти (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER">SRS MemHwAb с. 5</a>).</p>
<p>MemIf не имеет собственного поведения при работе с памятью. Его API отображается на API нижележащих модулей абстракции. В отношении функционального поведения спецификация ссылается на эти модули или на драйверы памяти (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf с. 17</a>). Соответственно, каждое определение службы описывает лишь вызов одноименной функции выбранного модуля, например в <code>MemIf_Read</code> <a class="spec-record-ref" data-req="SWS_MemIf_00039" href="../../spec/record.html?id=SWS_MemIf_00039">[SWS_MemIf_00039]</a> и <code>MemIf_Write</code> <a class="spec-record-ref" data-req="SWS_MemIf_00040" href="../../spec/record.html?id=SWS_MemIf_00040">[SWS_MemIf_00040]</a>. Требуемые функции Ea перечислены как Required Interfaces <a class="spec-record-ref" data-req="SWS_MemIf_00047" href="../../spec/record.html?id=SWS_MemIf_00047">[SWS_MemIf_00047]</a>.</p>
<p>Диаграммы более поздних релизов показывают под Fee или Ea дополнительно MemAcc и Mem. Вызов <code>MemIf_Write</code> → <code>Fee_Write</code> остается там неизменным (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write">SWS Fee с. 48</a>). <h4>Выбор устройства через DeviceIndex: макрос или таблица диспетчеризации</h4>
<p>Параметр <code>DeviceIndex</code> выбирает модуль абстракции и тем самым устройство памяти. Если сконфигурирован только один модуль абстракции, параметр игнорируется. В этом случае MemIf должен быть реализован как набор макросов, которые напрямую отображаются на API модуля, например <code>#define MemIf_Write(DeviceIndex, BlockNumber, DataPtr) Fee_Write(BlockNumber, DataPtr)</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf с. 17</a>, по состоянию на R24-11). SRS указывает на то же самое: если библиотека производителя заменяет все модули Fee и Ea, MemIf состоит только из макросов (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER">SRS MemHwAb с. 5</a>).</p>
<p>Если сконфигурировано несколько модулей, MemIf должен отображать вызовы на соответствующий модуль с использованием эффективных механизмов. Спецификация называет для этого таблицы указателей на функции. Интерпретация обрезанного там примечания: <code>DeviceIndex</code>, вероятно, служит индексом для этих таблиц (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf с. 17</a>).</p>
<p>Для типа параметра существует различие между релизами. В R20-11 <code>DeviceIndex</code> имеет тип <code>uint8</code> (<a class="spec-record-ref" data-req="SWS_MemIf_00039" href="../../spec/record.html?id=SWS_MemIf_00039">[SWS_MemIf_00039]</a>, <a class="spec-record-ref" data-req="SWS_MemIf_00041" href="../../spec/record.html?id=SWS_MemIf_00041">[SWS_MemIf_00041]</a>). Фрагменты документов из R23-11 и последующих показывают <code>uint16</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read">SWS MemIf с. 18</a>). Для R20-11 действует <code>uint8</code>.</p>

<h4>Статус устройства, результат задания и рабочий режим</h4>
<p><code>MemIf_GetStatus</code> <a class="spec-record-ref" data-req="SWS_MemIf_00042" href="../../spec/record.html?id=SWS_MemIf_00042">[SWS_MemIf_00042]</a> возвращает значение <code>MemIf_StatusType</code> <a class="spec-record-ref" data-req="SWS_MemIf_00064" href="../../spec/record.html?id=SWS_MemIf_00064">[SWS_MemIf_00064]</a>. При <code>MEMIF_BUSY_INTERNAL</code> модуль абстракции занят внутренним управлением; драйвер под ним при этом может быть занят или свободен. Fee сообщает это значение, например, во время реорганизации флеш-памяти (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus">SWS Fee с. 30</a>). Драйверы интерпретируют это как обычный доступ по SPI или SPI-burst (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_2_Eep_SetMode.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_2_Eep_SetMode">SWS Eep с. 34</a>). Eep_SetMode не разрешается вызывать во время выполняющейся операции. Fls_SetMode отклоняет смену режима в состоянии «busy» (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_9_Fls_SetMode.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_9_Fls_SetMode">SWS Fls с. 42</a>). Интерпретация: поэтому вызов <code>MemIf_SetMode</code>, вероятно, целесообразен только тогда, когда ни одно устройство не обрабатывает задание.</p>

<h4>Отмена выполняющихся заданий</h4>
<p><code>MemIf_Cancel</code> не возвращает значения и передает отмену выбранному модулю <a class="spec-record-ref" data-req="SWS_MemIf_00041" href="../../spec/record.html?id=SWS_MemIf_00041">[SWS_MemIf_00041]</a>. Fee_Cancel и Ea_Cancel сами выполняются синхронно, но являются асинхронными по отношению к аппаратному обеспечению (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel">SWS Fee с. 45</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_3_Ea_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_3_Ea_Cancel">SWS Ea с. 44</a>). В тракте Flash отмена передается далее в <code>Fls_Cancel</code>. Обратная связь об ошибке возвращается через <code>Fee_JobErrorNotification</code> и <code>NvM_JobErrorNotification</code> обратно в NvM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job">SWS Fls с. 58</a>). После этого результат задания сообщает <code>MEMIF_JOB_CANCELED</code>, что Fee классифицирует как «неудачно» (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult">SWS Fee с. 31</a>).</p>
<p>Для планирования действует граничное условие: <code>Fls_Cancel</code> не разрешается вызывать во время выполняющейся <code>Fls_MainFunction</code>. Это можно обеспечить двумя способами (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job">SWS Fls с. 58</a>):</p>
<ul>
<li>Функции заданий NvM и драйвера выполняются последовательно в одной и той же задаче.</li>
<li>Задача функции Main является непрерываемой.</li>
</ul>

<h4>Поведение при ошибке</h4>
<p>MemIf определяет две ошибки разработки <a class="spec-record-ref" data-req="SWS_MemIf_00006" href="../../spec/record.html?id=SWS_MemIf_00006">[SWS_MemIf_00006]</a>:</p>
<ul>
<li><code>MEMIF_E_PARAM_DEVICE</code> (0x01): неверный индекс устройства.</li>
<li><code>MEMIF_E_PARAM_POINTER</code> (0x02): указатель NULL в качестве аргумента.</li>
</ul>
<p>Предположительно, ошибка указателя относится к параметрам <code>DataBufferPtr</code> и <code>VersionInfoPtr</code>. Сообщение передается через <code>Det_ReportError</code> <a class="spec-record-ref" data-req="SWS_MemIf_00048" href="../../spec/record.html?id=SWS_MemIf_00048">[SWS_MemIf_00048]</a>. При активном обнаружении ошибок и обнаруженной ошибке действует следующее:</p>
<ul>
<li>Read, Write, InvalidateBlock и EraseImmediateBlock возвращают <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_MemIf_00044" href="../../spec/record.html?id=SWS_MemIf_00044">[SWS_MemIf_00044]</a>, <a class="spec-record-ref" data-req="SWS_MemIf_00046" href="../../spec/record.html?id=SWS_MemIf_00046">[SWS_MemIf_00046]</a>).</li>
<li><code>MemIf_GetJobResult</code> возвращает <code>MEMIF_JOB_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_5_MemIf_GetJobResult.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_5_MemIf_GetJobResult">SWS MemIf с. 21</a>).</li>
</ul>
<p>Специфические коды ошибок разработки API не возвращает (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_Requirements_Tracing.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_Requirements_Tracing">SWS MemIf с. 12</a>).</p>
<p>Ошибки времени выполнения из Fee или Ea модуль MemIf сам не обрабатывает; предусмотренная реакция — «N/A». Только в режиме опроса NvM узнает об ошибке через <code>MemIf_GetJobResult</code> с результатом <code>MEMIF_JOB_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_1_2_2_Memory_Abstraction_Interface.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_1_2_2_Memory_Abstraction_Interface">ErrorDescription с. 58</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_2_2_2_Memory_Abstraction_Interface.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_2_2_2_Memory_Abstraction_Interface">ErrorDescription с. 60</a>, соответственно R20-11). Неинициализированный Fee можно распознать по запросу его состояния (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation">ErrorDescription с. 53</a>).</p>
<p>Восстановление берет на себя NvM. Если затронут процесс записи, он увеличивает счетчик повторов и прерывает операцию после превышения предела. Об ошибке он сообщает в DEM; через <code>NvM_GetErrorStatus</code> затем можно запросить <code>NVM_REQ_NOT_OK</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_2_2_2_5_NVRAM_Manager.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_2_2_2_5_NVRAM_Manager">EXP ErrorDescription с. 45</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_2_7_2_5_NVRAM_Manager.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_2_7_2_5_NVRAM_Manager">EXP ErrorDescription с. 58</a>, по состоянию на R25-11). <code>MEMIF_BLOCK_INCONSISTENT</code> и <code>MEMIF_BLOCK_INVALID</code>, напротив, описывают состояние содержимого блока и передаются без изменений <a class="spec-record-ref" data-req="SWS_MemIf_00065" href="../../spec/record.html?id=SWS_MemIf_00065">[SWS_MemIf_00065]</a>.</p>
