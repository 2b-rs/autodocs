Управляет пробуждением, запуском и отключением коммуникации по шине для каждого FlexRay-кластера по поручению ComM и BswM.

FlexRay State Manager запускает для каждого FlexRay-кластера конечный автомат, который преобразует коммуникационные требования ComM в пробуждение, запуск и отключение через FlexRay Interface. FrSM_RequestComMode только сохраняет требование; его обработка происходит лишь в циклической главной функции кластера [SWS_FrSM_00020]. О достигнутых режимах FrSM сообщает в ComM и BswM. BswM может завершить работу в режиме Key-Slot-Only или переключить все кластеры в режим приёма. В качестве FullCom рассматриваются только FRSM_ONLINE и FRSM_LOW_NUMBER_OF_COLDSTARTERS (SWS FrSM с. 38).

FlexRay State Manager преобразует коммуникационные требования ComM для каждого FlexRay-кластера в вызовы к FlexRay Interface. В ответ он сообщает о режиме шины через ComM_BusSM_ModeIndication и о своём детальном состоянии через BswM_FrSM_CurrentState [SWS_FrSM_00096]. Опционально он использует DEM, DET и FrNm, а также другие службы FrIf [SWS_FrSM_00097]. FrSm_Init переводит автоматы всех кластеров в FRSM_READY (SWS FrSM с. 35).

Контекстная диаграмма: ComM и BswM управляют, SchM задаёт такты, FrIf выполняет; ошибки направляются в DEM, DET, FrNm и опционально в CDD. Источники: [SWS_FrSM_00096], [SWS_FrSM_00097]

FrSM_RequestComMode лишь сохраняет запрос. Только главная функция кластера обрабатывает его (SWS FrSM с. 36, [SWS_FrSM_00118]). При запросе FullCom условие WUReason определяет, отправляет ли FrSM шаблоны пробуждения самостоятельно, пересылает ли одностороннее пробуждение на второй канал или запускается напрямую. При запуске он вызывает FrIf_StartCommunication, а для ECU с холодным стартом — дополнительно FrIf_AllowColdstart. При POC normal active он переходит в FRSM_ONLINE (SWS FrSM с. 20, SWS FrSM с. 52). Если NoCom запрашивается из состояния FullCom, FrSM останавливает коммуникацию уже при вызове. После t_TrcvStdbyDelay он переводит трансиверы в режим ожидания (standby) и возвращается в FRSM_READY [SWS_FrSM_00209].

Диаграмма состояний: восемь основных состояний для каждого кластера и параллельный пассивный режим ECU. Переходы в FRSM_ONLINE_PASSIVE и FRSM_LOW_NUMBER_OF_COLDSTARTERS интерпретированы. Источники: SWS FrSM с. 18, SWS FrSM с. 27

Для ComM статус FullCom действует только в FRSM_ONLINE и FRSM_LOW_NUMBER_OF_COLDSTARTERS (SWS FrSM с. 38). В распоряжении BswM находятся два специальных режима работы. FrSm_AllSlots завершает работу в режиме Key-Slot-Only [SWS_FrSM_00172]. FrSm_SetEcuPassive переключает все кластеры в режим только приёма [SWS_FrSM_00174]. FrSM_BswM_StateType сообщает об обоих измерениях в комбинации [SWS_FrSM_00199]. В R20-11 некоторые функции ещё называются FrSm_…, а идентификаторы сервисов (Service IDs) отличаются от более поздних релизов [SWS_FrSM_00020].

В случае сбоя FrSM сообщает об ошибках разработки, таких как FRSM_E_UNINIT или FRSM_E_INV_HANDLE [SWS_FrSM_91001]. Если синхронизация не удаётся, он вызывает FrNm_StartupError. О потере синхронизации он опционально сообщает через <Cdd>_SyncLossErrorIndication [SWS_FrSM_00190].

Роль: менеджер состояния шины между ComM, BswM и FlexRay Interface

FlexRay State Manager (FrSM) преобразует коммуникационные требования ComM для каждого FlexRay-кластера в управляющие вызовы к FlexRay Interface. ComM запрашивает через FrSM_RequestComMode ComM_ModeType для NetworkHandleType [SWS_FrSM_00020]. О достигнутом режиме шины FrSM сообщает обратно через ComM_BusSM_ModeIndication, а о своём детальном состоянии — в BswM BswM_FrSM_CurrentState [SWS_FrSM_00096]. Он никогда не управляет контроллерами и трансиверами напрямую. Для этого он использует функции FrIf, сгруппированные в спецификации в такие функциональные элементы, как FE_START (FrIf_StartCommunication) или FE_HALT (FrIf_HaltCommunication) (SWS FrSM с. 22).

Кроме того, FrSM использует опциональные службы: Dem_SetEventStatus, Det_ReportError, FrIf_AllSlots, FrIf_GetNumOfStartupFrames, FrIf_GetWakeupRxStatus, FrIf_SetWakeupChannel и FrNm_StartupError [SWS_FrSM_00097]. Свои типы он импортирует, среди прочего, из ComM, ComStack_Types, DEM, Fr и FrIf [SWS_FrSM_00095]. BswM также активно управляет FrSM. Например, для сценариев диагностики он может перевести его в пассивный режим через FrSm_SetEcuPassive() (EXP ModeMgmt с. 36).

Контекстная диаграмма: FrSM находится между запрашивающими сторонами ComM/BswM, генератором тактов SchM и исполняющим FrIf, а также сообщает об ошибках в DEM, DET, FrNm и опциональный CDD. Источники: [SWS_FrSM_00096], [SWS_FrSM_00097], [SWS_FrSM_00118], [SWS_FrSM_00190]

Конечный автомат для каждого кластера и параллельный пассивный режим ECU

Для каждого кластера FrSM поддерживает собственный автомат с восемью состояниями: FRSM_READY, FRSM_WAKEUP, FRSM_STARTUP, FRSM_HALT_REQ, FRSM_ONLINE, FRSM_ONLINE_PASSIVE, FRSM_KEYSLOT_ONLY и FRSM_LOW_NUMBER_OF_COLDSTARTERS. Каждое состояние сопоставлено с POC-состоянием контроллера:

  • FRSM_ONLINE соответствует POC:normal active с полной коммуникацией.
  • FRSM_ONLINE_PASSIVE соответствует POC:normal passive. Из-за ошибок синхронизации часов данные там не передаются и не принимаются.
  • В FRSM_KEYSLOT_ONLY разрешается выполнять передачу только в слотах Key-Slot.

Это сопоставление описывает SWS FrSM с. 18. Переходы определены таблично, и FrSM выполняет их действия в установленном там порядке (SWS FrSM с. 24).

Параллельно с этим существуют состояния FRSM_ECU_ACTIVE и FRSM_ECU_PASSIVE (SWS FrSM с. 18). FrSm_SetEcuPassive переключает все кластеры ECU совместно в режим только приема или обратно [SWS_FrSM_00174]. Если при этом кластер не находится в FRSM_READY, FrSM выполняет для него FE_TRCV_NORMAL (SWS FrSM с. 40). FrSM_BswM_StateType отображает оба измерения: для каждого основного состояния существует значение с суффиксом _ECU_PASSIVE, от FRSM_BSWM_READY (0x00) до FRSM_LOW_NUMBER_OF_COLDSTARTERS_ECU_PASSIVE (0x0F) [SWS_FrSM_00199]. Эти два понятия пассивного состояния не следует путать. ONLINE_PASSIVE является следствием нарушения синхронизации, ECU_PASSIVE же — намеренным режимом приема.

Во внешнем представлении значение имеет только режим, возвращаемый FrSM_GetCurrentComMode. COMM_FULL_COMMUNICATION действует исключительно в FRSM_ONLINE и FRSM_LOW_NUMBER_OF_COLDSTARTERS, во всех остальных состояниях действует COMM_NO_COMMUNICATION (SWS FrSM с. 38, [SWS_FrSM_00024]). SilentCom на FlexRay не поддерживается (SWS FrSM с. 18).

Диаграмма состояний: основной автомат на каждый кластер с путями пробуждение → запуск → онлайн, а также останов → готовность, наряду с пассивным режимом ECU, общим для всех кластеров. Интерпретация: переходы к FRSM_ONLINE_PASSIVE и FRSM_LOW_NUMBER_OF_COLDSTARTERS выведены из таблицы состояний и условий. Источники: SWS FrSM с. 27, SWS FrSM с. 18, SWS FrSM с. 20, [SWS_FrSM_00209]

От FrSm_Init до полной коммуникации: пробуждение и запуск

FrSm_Init является синхронной и нереэнтрантной. Функция получает указатель на FrSM_ConfigType, зависящую от реализации конфигурацию post-build ([SWS_FrSM_00013], [SWS_FrSM_00198]). Она переводит все автоматы кластеров в FRSM_READY (переход T00) и сохраняет адрес конфигурации. Если активно FrSMDevErrorDetect, она дополнительно фиксирует успешную инициализацию (SWS FrSM с. 35).

FrSM_RequestComMode работает асинхронно. Функция сохраняет запрошенный режим как reqComMode. Он обрабатывается только при следующем выполнении FrSM_MainFunction_<FrSMCluster.ShortName> в автомате соответствующего кластера (SWS FrSM с. 36). Для каждого кластера предусмотрена одна основная функция, предоставляемая через SchM_FrSm.h [SWS_FrSM_00118]. Период ее вызова, предположительно, определяется параметром FrSMMainFunctionCycleTime (SWS FrSM с. 62).

При запросе FullCom в FRSM_READY FrSM вычисляет условие WUReason. Если установлен FrSMCheckWakeupReason, он опрашивает каждый трансивер через FrIf_GetTransceiverWUReason. Результатом является NO_WU_BY_BUS, PARTIAL_WU_BY_BUS или ALL_WU_BY_BUS; без проверки принимается NO_WU_BY_BUS (SWS FrSM с. 20). Если ECU был разбужен шиной, он запускается без собственного пробуждения (SWS FrSM с. 52). Если в двухканальном узле пробуждение поступило только по одному каналу, FE_SET_WU_CHANNEL_FORWARD пересылает его на другой канал (SWS FrSM с. 22, SWS FrSM с. 56).

Диаграмма деятельности: из WUReason определяется, выполняет ли FrSM пробуждение самостоятельно, пересылает ли пробуждение или запускается напрямую. Интерпретация: ветвь для ECU без функции пробуждения выведена из FrSMIsWakeupEcu. Источники: SWS FrSM с. 20, SWS FrSM с. 22, SWS FrSM с. 54

В FRSM_WAKEUP FrSM передает шаблоны пробуждения через FE_WAKEUP, то есть FrIf_SendWUP на каждый контроллер. Он повторяет это до тех пор, пока не будет достигнут FrSMNumWakeupPatterns или не будет обнаружен трафик на шине (busTrafficDetected). Если контроллер переходит в HALT из-за ошибки, передача прерывается (SWS FrSM с. 27).

Диаграмма деятельности: повторная передача шаблонов пробуждения с вычислением vPOC!WakeupStatus и прерыванием при HALT контроллера. Источники: SWS FrSM с. 27, SWS FrSM с. 18

Запуск начинается с FrIf_StartCommunication. FrIf_AllowColdstart вызывается модулем FrSM только при FrSMIsColdstartEcu (SWS FrSM с. 22). Затем он сообщает FRSM_STARTUP в BswM. Как только статус POC становится normal active, следуют FrIf_SetState(FRIF_GOTO_ONLINE), сообщение FRSM_ONLINE и индикация режима в ComM (SWS FrSM с. 50, SWS FrSM с. 52).

Диаграмма последовательности: одноканальное пробуждение и запуск до FRSM_ONLINE, распределенные по нескольким вызовам основной функции. Интерпретация: порядок внутри вызовов реконструирован по иллюстрациям спецификации и упрощен. Источники: SWS FrSM с. 50, SWS FrSM с. 52, [SWS_FrSM_00118]

Режим Key-Slot-Only, деблокирование всех слотов и малое число узлов холодного старта

Если контроллер сконфигурирован с pKeySlotOnlyEnabled, запуск сначала завершается в FRSM_KEYSLOT_ONLY. Это состояние соответствует POC:normal active с vPOCSlotMode ≠ AllSlots (SWS FrSM с. 18, SWS FrSM с. 55). Выход из него осуществляется через FrSm_AllSlots [SWS_FrSM_00172]. Функция вызывает FrIf_AllSlots для каждого контроллера кластера и возвращает E_OK только в том случае, если все вызовы вернули E_OK. Ее можно отключить на этапе прекомпиляции с помощью FrSMAllSlotsSupport (SWS FrSM с. 41). Согласно иллюстрации в спецификации, BswM разрешает полную работу. Только после этого FrSM сообщает FRSM_ONLINE и FullCom в ComM (SWS FrSM с. 57).

Диаграмма последовательности: двухэтапный запуск: сначала только key-слоты, затем деблокирование всех слотов через FrSm_AllSlots. На иллюстрации спецификации сообщение для BswM обозначено как FRSM_ONLINE_KEYSLOT_ONLY, здесь же приведено значение R20-11 FRSM_BSWM_KEYSLOT_ONLY. Источники: SWS FrSM с. 57, SWS FrSM с. 55, [SWS_FrSM_00172], [SWS_FrSM_00199]

FRSM_LOW_NUMBER_OF_COLDSTARTERS означает полную коммуникацию, при которой кластер синхронизирован только через sync-фреймы (SWS FrSM с. 18). Условие lowNumberOfColdstarters выполняется, если FrIf_GetNumOfStartupFrames() сообщает о меньшем количестве startup-фреймов, чем задано опциональным параметром FrSMMinNumberOfColdstarter (SWS FrSM с. 20).

Возврат к NoCom и таймеры кластера

NoCom может быть запрошен, пока автомат находится в FRSM_ONLINE, FRSM_KEYSLOT_ONLY, FRSM_LOW_NUMBER_OF_COLDSTARTERS или FRSM_ONLINE_PASSIVE. В этом случае переход обрабатывается уже FrSM_RequestComMode, не дожидаясь основной функции (SWS FrSM с. 36). Сюда относятся FrIf_SetState(FRIF_GOTO_OFFLINE), FrIf_HaltCommunication и сообщение HALT_REQ в BswM. В последующих циклах вызова FrSM сообщает NoCom в ComM, заново инициализирует контроллеры, переводит трансиверы в STANDBY и сообщает READY (SWS FrSM с. 58).

Диаграмма последовательности: от FullCom к NoCom. Останов происходит синхронно в вызове запроса, повторная инициализация и переход в режим standby следуют со сдвигом по времени в основной функции. Интерпретация: последовательность реконструирована по иллюстрации в спецификации. Источники: SWS FrSM с. 58, SWS FrSM с. 36, [SWS_FrSM_00209]

Для каждого кластера FrSM работает с несколькими таймерами (SWS FrSM с. 21):

  • t1 задерживает FrIf_AllowColdstart. При FrSMDurationT1 = 0 вызов следует непосредственно за FrIf_StartCommunication.
  • t2 определяет, через какое время запуск повторяется.
  • t3 контролирует переход к FullCom.
  • t4 обеспечивает сброс бита блокировки холодного старта двухканальным узлом.
  • t_TrcvStdbyDelay задерживает повторную инициализацию и переход в standby. Если FrSMTrcvStdbyDelay не сконфигурирован или равен 0, автомат немедленно переходит из FRSM_HALT_REQ в FRSM_READY [SWS_FrSM_00209].

Конфигурация для каждого FrSMCluster и состояние интерфейсов R20-11

Контейнер FrSMCluster (1..*) описывает кластер, который на одном ECU может охватывать несколько контроллеров. Он содержит:

  • таймеры с FrSMDurationT1 по FrSMDurationT4,
  • роли FrSMIsColdstartEcu и FrSMIsWakeupEcu,
  • FrSMNumWakeupPatterns и FrSMStartupRepetitions,
  • ссылки FrSMComMNetworkHandleRef и FrSMFrIfClusterRef.

Это содержимое описывает SWS FrSM с. 62. В общем виде также конфигурируются FrSMVersionInfoApi для FrSM_GetVersionInfo и FrSMSyncLossErrorIndicationName (SystemTemplate с. 1528, [SWS_FrSM_00029]).

Многие детали взяты из более поздних релизов. Для R20-11 действуют требования, и в некоторых пунктах они отличаются:

  • Функции называются FrSm_Init, FrSm_AllSlots и FrSm_SetEcuPassive и доступны через FrSm.h.
  • FrSM_RequestComMode имеет Service-ID 0x02 и является реэнтрантной для различных кластеров. В более поздних источниках указаны 0x40 и другие имена параметров.
  • FrSM_GetCurrentComMode в R20-11 имеет Service-ID 0x03.

Ссылки: [SWS_FrSM_00013], [SWS_FrSM_00020], [SWS_FrSM_00024], SWS FrSM с. 36.

Поведение при ошибке

Для ошибок разработки определены следующие коды [SWS_FrSM_91001]:

  • FRSM_E_PARAM_POINTER: недействительный указатель. Сервис немедленно выполняет возврат.
  • FRSM_E_INV_HANDLE: недействительный сетевой дескриптор.
  • FRSM_E_UNINIT: модуль не инициализирован.
  • FRSM_E_INV_MODE: недействительный режим коммуникации.
  • FRSM_INIT_FAILED: сбой инициализации.

Некоторые случаи регламентированы явно. FrSm_AllSlots сообщает при недействительном дескрипторе FRSM_E_INV_HANDLE и возвращает E_NOT_OK (SWS FrSM с. 41). FrSm_SetEcuPassive сообщает об ошибке разработки до инициализации (SWS FrSM с. 40). FrSM_GetCurrentComMode возвращает в R20-11 без предварительной инициализации E_NOT_OK [SWS_FrSM_00024].

На уровне шины FrSM реагирует следующим образом:

  • При ошибках синхронизации часов кластер переходит в FRSM_ONLINE_PASSIVE (SWS FrSM с. 18).
  • Если синхронизация не удается, FrSM вызывает FrNm_StartupError [SWS_FrSM_00097].
  • Запуск повторяется после t2 (SWS FrSM с. 21). FrSMStartupRepetitions, предположительно, ограничивает число повторений.

FrSM сообщает статус запуска как DEM-событие FRSM_E_CLUSTER_STARTUP, в случае успеха — с PASSED (SWS FrSM с. 52). Идентификаторы событий находятся в FrSMClusterDemEventParameterRefs (SWS FrSM с. 62). Опционально <Cdd>_SyncLossErrorIndication информирует с помощью true о потере синхронизации. С помощью false функция указывает на то, что синхронизация восстановлена или запрос FullCom был отозван [SWS_FrSM_00190]. Если имя функции не сконфигурировано, это сообщение не отправляется (SystemTemplate с. 1528).

Использование и семантика

Функция FrSM_RequestComMode вызывается модулем Communication Manager (ComM) для запуска или останова коммуникации в определенном кластере FlexRay [SWS_FrSM_00020]. Интерфейс объявлен через заголовочный файл FrSm.h и имеет Service-ID 0x02 [SWS_FrSM_00020]. Поскольку сервис специфицирован как асинхронный, функция лишь подтверждает прием запроса на переключение, в то время как фактический переход состояния выполняется отложенно [SWS_FrSM_00020].

Параметры и возвращаемые значения

Функция ожидает два входных параметра для управления коммуникационным режимом [SWS_FrSM_00020]:

  • NetworkHandle (тип NetworkHandleType): определяет кластер FlexRay, для которого запрашивается коммуникационный режим [SWS_FrSM_00020].
  • ComM_Mode (тип ComM_ModeType): содержит желаемый модулем ComM режим коммуникации для указанной сети [SWS_FrSM_00020].

Возвращаемое значение типа Std_ReturnType показывает результат проверки запроса [SWS_FrSM_00020]:

  • E_OK: запрос на смену режима был успешно принят [SWS_FrSM_00020].
  • E_NOT_OK: запрос был отклонен и не принят [SWS_FrSM_00020].

Параллелизм и ограничения

Согласно спецификации, FrSM_RequestComMode реализована как реентерабельная для различных кластеров FlexRay [SWS_FrSM_00020]. Для одного и того же кластера FlexRay вызов, предположительно, не является реентерабельным, в связи с чем следует избегать конкурирующих вызовов для одного и того же экземпляра. Специфические коды ошибок, такие как сообщения DET или DEM, в полезной нагрузке не определены [SWS_FrSM_00020].

Это указание по использованию было автоматически сгенерировано на основе спецификации AUTOSAR Classic R20-11.

Служба FrSm_AllSlots.

Асинхронная сервисная функция FrSm_AllSlots предоставляется через заголовочный файл FrSm.h и служит для выхода из так называемого «Key Slot Only Mode» для указанного кластера FlexRay [SWS_FrSM_00172].

Вызов и параметры: для идентификации коммуникационной сети параметру NetworkHandle передается соответствующий кластер FlexRay, для которого должен быть запрошен режим переключения [SWS_FrSM_00172]. Других входных параметров нет [SWS_FrSM_00172].

Возвращаемое значение и семантика: вызов возвращает E_OK, если запрос на переключение был успешно принят, или E_NOT_OK, если запрос был отклонен [SWS_FrSM_00172]. Поскольку это асинхронная операция, E_OK подтверждает лишь прием поручения; фактический переход в режим полной работы всех слотов, вероятно, вступит в силу с задержкой по времени в контексте State Manager.

Параллелизм и ограничения: функция является реентерабельной для различных кластеров FlexRay [SWS_FrSM_00172]. Для одинаковых кластеров она спроектирована как нереентерабельная, поэтому вызывающие стороны должны синхронизировать параллельные запросы к одному и тому же кластеру. Специфические коды ошибок для DET или DEM в описании функции не упоминаются.

Взаимодействие и диапазон значений

Значения этого типа используются во взаимодействии с интерфейсом BswM_FrSM_CurrentState для передачи текущего состояния работы и связи в модуль BswM [SWS_FrSM_00199]. Диапазон значений включает в себя следующие значения перечисления:

  • FRSM_BSWM_WAKEUP (0x04) и FRSM_BSWM_WAKEUP_ECU_PASSIVE (0x05)
  • FRSM_BSWM_HALT_REQ (0x06) и FRSM_BSWM_HALT_REQ_ECU_PASSIVE (0x07)
  • FRSM_BSWM_KEYSLOT_ONLY (0x08) и FRSM_BSWM_KEYSLOT_ONLY_ECU_PASSIVE (0x09)
  • FRSM_BSWM_ONLINE (0x0A) и FRSM_BSWM_ONLINE_ECU_PASSIVE (0x0B)
  • FRSM_BSWM_ONLINE_PASSIVE (0x0C) и FRSM_BSWM_ONLINE_PASSIVE_ECU_PASSIVE (0x0D)

Это, предположительно, служит для того, чтобы сообщать в BswM состояние связи кластера FlexRay в сочетании с пассивным режимом электронного блока управления (ECU), чтобы тот мог координировать соответствующие смены режимов.
