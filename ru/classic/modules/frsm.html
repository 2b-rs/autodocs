Роль FrSM: преобразователь режимов между ComM, BswM и FlexRay Interface

FlexRay State Manager (FrSM) представляет собой диспетчер состояний шины для FlexRay. Для каждого кластера FlexRay он принимает режим связи через FrSM_RequestComMode ([SWS_FrSM_00020]). Этот режим он преобразует в управляющие последовательности для коммуникационных контроллеров и трансиверов, инициируя для этого функции FlexRay Interface (FrIf_*, [SWS_FrSM_00096]). Диаграмма конечного автомата описывает это назначение как трансляцию COMM_NO_COMMUNICATION и COMM_FULL_COMMUNICATION в низкоуровневые процессы (SWS FrSM Fig. 7.1 с. 24).

FrSM передает обратную связь в двух направлениях. О достигнутом режиме шины он сообщает модулю ComM с помощью ComM_BusSM_ModeIndication, а о своем внутреннем состоянии — модулю BswM с помощью BswM_FrSM_CurrentState ([SWS_FrSM_00096]). Значение, передаваемое в BswM, имеет тип FrSM_BswM_StateType ([SWS_FrSM_00199]). В то же время BswM выступает в роли инициатора: он может перевести FrSM в пассивное состояние, например, для сценариев диагностики с помощью FrSm_SetEcuPassive() (EXP ModeMgmt с. 36). В режиме Key-Slot-Only он разрешает полнофункциональную работу (SWS FrSM Fig. 9.10 с. 55).

EcuM инициализирует модуль с помощью FrSm_Init, передавая указатель на post-build-структуру FrSM_ConfigType ([SWS_FrSM_00013], [SWS_FrSM_00198]). На Figure 9.1 EcuM, FrIf и FrSM показаны как участники этой фазы (SWS FrSM Fig. 9.1 с. 46). Затем планировщик BSW вызывает для каждого кластера собственную FrSM_MainFunction_<FrSMCluster.ShortName> (Service-ID 0x80, предоставляемую через SchM_FrSm.h, [SWS_FrSM_00118]). Опционально FrSM подключает DEM, DET, FrNm_StartupError и другие сервисы FrIf ([SWS_FrSM_00097]). Кроме того, предусмотрен конфигурируемый обратный вызов CDD при потере синхронизации ([SWS_FrSM_00190]).

Контекстная диаграмма: FrSM принимает запросы от EcuM, SchM, ComM и BswM, управляет аппаратным обеспечением исключительно через FrIf и отправляет уведомления в ComM, BswM, DEM, DET, FrNm, а также в опциональный CDD. Источники: [SWS_FrSM_00096], [SWS_FrSM_00097], [SWS_FrSM_00118], [SWS_FrSM_00190], SWS FrSM Fig. 9.1 с. 46, EXP ModeMgmt с. 36

Две параллельные области: состояния контроллеров для каждого кластера и пассивный режим ECU

Конечный автомат состоит из двух параллельных областей (SWS FrSM с. 18, SWS FrSM Fig. 7.1 с. 24):

  • Область [CcCtrl] включает восемь состояний для каждого кластера.
  • Область [TrcvCtrl] управляет режимом приема через FRSM_ECU_ACTIVE и FRSM_ECU_PASSIVE.

В таблице 7.1 каждому состоянию кластера сопоставляется состояние POC контроллера FlexRay (SWS FrSM с. 18):

Состояние FrSMСостояние POCЗначение
FRSM_READYreadyСостояние покоя после инициализации
FRSM_WAKEUPwake-upFrSM выполняет Wakeup
FRSM_STARTUPstart-upFrSM выполняет Startup
FRSM_HALT_REQnormal active/passiveFrSM завершает работу
FRSM_ONLINEnormal activeполнофункциональная связь
FRSM_ONLINE_PASSIVEnormal passiveнет передачи данных из-за ошибок синхронизации часов
FRSM_KEYSLOT_ONLYnormal active, режим слотов ≠ AllSlotsпередача только в Key-слотах
FRSM_LOW_NUMBER_OF_COLDSTARTERSnormal activeполнофункциональная связь, синхронизация только по Sync-кадрам

Состояния FRSM_ONLINE, FRSM_KEYSLOT_ONLY, FRSM_LOW_NUMBER_OF_COLDSTARTERS и FRSM_ONLINE_PASSIVE образуют группу FullCom (SWS FrSM с. 36). Переход происходит, когда в исходном состоянии выполняется его условие и наступает событие. Соответствующие действия FrSM выполняет в порядке, указанном в таблице переходов (SWS FrSM с. 24). Переменные, такие как reqComMode или wakeupCounter, являются лишь вспомогательными средствами, делающими спецификацию более читаемой (SWS FrSM с. 18).

FrSm_SetEcuPassive переключает область [TrcvCtrl] для всех кластеров одновременно ([SWS_FrSM_00174]). С TRUE она переходит в FRSM_ECU_PASSIVE, а с FALSE — в FRSM_ECU_ACTIVE. Если при этом кластер не находится в FRSM_READY, то есть его трансиверы не находятся в режиме Standby, то для этого кластера выполняется FE_TRCV_NORMAL (SWS FrSM с. 40).

Диаграмма состояний: область [CcCtrl] переводит каждый кластер из FRSM_READY через Wakeup и Startup в FullCom и обратно через FRSM_HALT_REQ. Область [TrcvCtrl] независимо от этого переключает пассивный режим. Переходы внутри FullCom определяются таблицей переходов; здесь они не показаны. Источники: SWS FrSM с. 27, SWS FrSM с. 35, [SWS_FrSM_00174], [SWS_FrSM_00209]

От запроса FullCom к работе в режиме онлайн: Startup и Wakeup

FrSM_RequestComMode работает асинхронно ([SWS_FrSM_00020]). Функция сохраняет желаемый режим как reqComMode; он обрабатывается при следующем запуске функции MainFunction соответствующего кластера (SWS FrSM с. 36). Для R20-11 согласно [SWS_FrSM_00020] действует следующее:

  • параметры NetworkHandle и ComM_Mode,
  • Service-ID 0x02,
  • реентерабельна для различных кластеров.

Напротив, фрагмент документации из более поздних релизов указывает Service-ID 0x40 и параметры network/mode. Для R20-11 действует требование (SWS FrSM с. 36).

Без отправки шаблона пробуждения кластер переходит из FRSM_READY непосредственно в Startup (SWS FrSM с. 52, SWS FrSM Fig. 9.3 с. 48):

  1. Трансиверы переводятся в FRTRCV_TRCVMODE_NORMAL.
  2. Контроллеры запускаются с помощью FrIf_StartCommunication.
  3. Для Coldstart-ECU (FrSMIsColdstartEcu) FrIf_AllowColdstart разрешает холодный пуск.

Таймер t1 задерживает это разрешение на FrSMDurationT1. При значении 0 оно следует непосредственно за FrIf_StartCommunication (SWS FrSM с. 21).

После этого функция MainFunction циклически опрашивает FrIf_GetPOCStatus (SWS FrSM Fig. 9.5 с. 50, [SWS_FrSM_00096]). Если она возвращает FR_POCSTATE_NORMAL_ACTIVE, то:

  • FrSM сообщает о событии DEM FRSM_E_CLUSTER_STARTUP со статусом PASSED,
  • он переводит FrIf в режим онлайн с помощью FRIF_GOTO_ONLINE,
  • он информирует BswM и ComM.

Диаграмма последовательности: запрос сохраняется и преобразуется функцией MainFunction в действия по запуску (Startup). Переход в режим онлайн происходит только тогда, когда статус POC сообщает normal active. Вместо подписей к рисунку используются значения FrSM_BswM_StateType из R20-11. Источники: SWS FrSM Fig. 9.3 с. 48, SWS FrSM с. 52, SWS FrSM Fig. 9.7 с. 52, [SWS_FrSM_00020], [SWS_FrSM_00199]

Если ECU должен сначала разбудить кластер, он проходит через FRSM_WAKEUP ([SWS_FrSM_00097]). С помощью FrIf_SetWakeupChannel он выбирает канал пробуждения, при этом FR_CHANNEL_AB использовать запрещено. Затем с помощью FrIf_SendWUP он отправляет шаблон пробуждения. Двухканальный ECU, разбуженный от шины на канале A, целенаправленно пересылает сигнал пробуждения на канал B (SWS FrSM с. 56, SWS FrSM Fig. 9.8 с. 53).

Количество повторений шаблона определяется параметром FrSMNumWakeupPatterns (SWS FrSM с. 27). Повторение прекращается, как только обнаруживается трафик на шине. Если из-за ошибки контроллер переходит в HALT, отправка прерывается. Этот фрагмент документации взят из R23-11/R24-11; полезная нагрузка не содержит отдельного требования R20-11 на этот счет.

Активити-диаграмма: отправка шаблона пробуждения повторяется под управлением счетчика. Она завершается при обнаружении трафика на шине, достижении заданного числа повторений или при переходе контроллера в HALT из-за ошибки. Источники: SWS FrSM с. 27, SWS FrSM с. 18

Запуск в режиме Key-Slot-Only и работа в режиме приема по запросу BswM

Если на контроллере установлен pKeySlotOnlyEnabled, узел после запуска (Startup) сначала осуществляет передачу только в Key-слотах (SWS FrSM Fig. 9.10 с. 55, [SWS_FrSM_00199]). При этом кластер находится в FRSM_KEYSLOT_ONLY, о чем FrSM сообщает модулю BswM как FRSM_BSWM_KEYSLOT_ONLY. Согласно Figure 9.10, затем BswM разрешает полнофункциональную работу с помощью FrSm_AllSlots ([SWS_FrSM_00172]). Для этой асинхронной функции действует следующее (SWS FrSM с. 41):

  • Она вызывает FrIf_AllSlots для каждого контроллера кластера.
  • Она возвращает E_OK только в том случае, если все эти вызовы возвращают E_OK.
  • Ее можно отключить во время компиляции с помощью FrSMAllSlotsSupport.

Если после этого статус POC сообщает FR_SLOTMODE_ALL, кластер переходит в FRSM_ONLINE (SWS FrSM с. 57).

Диаграмма последовательности: только вызов FrSm_AllSlots из BswM переводит работу из режима Key-слотов в полнофункциональный режим. FrSM сообщает об этом переходе, как только статус POC показывает режим слотов ALL. На Figure 9.10 состояние BswM обозначено как FRSM_ONLINE_KEYSLOT_ONLY, тогда как тип из R20-11 определяет его как FRSM_BSWM_KEYSLOT_ONLY. Источники: [SWS_FrSM_00172], [SWS_FrSM_00199], SWS FrSM с. 57, SWS FrSM Fig. 9.10 с. 55

FrSm_SetEcuPassive синхронна и нереентерабельна; единичный вызов воздействует на все кластеры FlexRay в ECU ([SWS_FrSM_00174]). Тип FrSM_BswM_StateType для каждого значения состояния содержит вариант с суффиксом _ECU_PASSIVE, например FRSM_BSWM_ONLINE_ECU_PASSIVE (0x0B) ([SWS_FrSM_00199]). Интерпретация: FrSM, вероятно, передает модулю BswM состояние [CcCtrl] и статус пассивности [TrcvCtrl] в одном значении, что позволяет правилам BswM оценивать их совместно (SWS FrSM с. 35).

Возврат в NoCom и запрос текущего режима связи

Если запрос NoCom поступает в то время, когда кластер находится в состоянии FullCom, FrSM_RequestComMode, согласно более поздней версии спецификации, обрабатывает переход непосредственно в теле вызова (SWS FrSM с. 36). На Figure 9.11 для этого показан двухэтапный процесс (SWS FrSM с. 58, SWS FrSM Fig. 9.11 с. 56):

  1. В самом вызове: FrIf_SetState с FRIF_GOTO_OFFLINE, FrIf_HaltCommunication, отправка сообщения HALT_REQ в BswM и COMM_NO_COMMUNICATION в ComM.
  2. В последующих запусках MainFunction: повторная инициализация контроллера с помощью FrIf_ControllerInit, перевод трансиверов в режим STANDBY, отправка сообщения READY.

Если FrSMTrcvStdbyDelay не сконфигурирован или установлен в 0, таймер t_TrcvStdbyDelay не запускается; переход из FRSM_HALT_REQ в FRSM_READY в таком случае происходит немедленно ([SWS_FrSM_00209]). При скоординированном завершении работы нескольких шин FrSM выступает участником Nm-координации (SWS Nm Fig. 9.1 с. 83).

Диаграмма последовательности: запрос NoCom останавливает связь и немедленно сообщает о NoCom. Повторная инициализация контроллера и перевод трансиверов в режим ожидания (Standby) происходят циклически, при необходимости после t_TrcvStdbyDelay. Источники: SWS FrSM с. 58, SWS FrSM Fig. 9.11 с. 56, [SWS_FrSM_00209], [SWS_FrSM_00096]

В R20-11 FrSM_GetCurrentComMode является синхронной, имеет Service-ID 0x03 и реентерабельна для различных кластеров ([SWS_FrSM_00024]). Функция записывает текущий режим по переданному адресу. Она возвращает COMM_FULL_COMMUNICATION только в FRSM_ONLINE и FRSM_LOW_NUMBER_OF_COLDSTARTERS, а во всех остальных состояниях — COMM_NO_COMMUNICATION (SWS FrSM с. 38). Это также относится к FRSM_KEYSLOT_ONLY и FRSM_ONLINE_PASSIVE, хотя оба они принадлежат к группе FullCom. SilentCom на FlexRay не поддерживается (SWS FrSM с. 18).

Конфигурация для каждого кластера FlexRay: роли, таймеры и переключатели

Каждый кластер описывается контейнером FrSMCluster (кратность 1..*), который может содержать несколько контроллеров на один ECU (SWS FrSM с. 62). Он содержит, среди прочего:

  • ссылки FrSMComMNetworkHandleRef и FrSMFrIfClusterRef,
  • роли FrSMIsColdstartEcu и FrSMIsWakeupEcu,
  • параметры повторения FrSMStartupRepetitions, FrSMStartupRepetitionsWithWakeup и FrSMNumWakeupPatterns,
  • время цикла FrSMMainFunctionCycleTime.

Описание контейнера взято из R23-11 и более поздних версий. Из требований R20-11 подтвержден FrSMTrcvStdbyDelay ([SWS_FrSM_00209]). Таймерами для каждого кластера являются (SWS FrSM с. 21):

  • t1 (FrSMDurationT1): задерживает вызов FrIf_AllowColdstart.
  • t2 (FrSMDurationT2): интервал, по истечении которого повторяется Startup.
  • t3 (FrSMDurationT3): контролирует переход в FullCom.
  • t4: гарантирует, что двухканальный узел снимет блокировку Coldstart-Inhibit и станет Leading Coldstarter.
  • t_TrcvStdbyDelay: задерживает повторную инициализацию контроллера и перевод трансиверов в режим Standby ([SWS_FrSM_00209]).

На уровне модуля действуют следующие переключатели:

  • FrSMDevErrorDetect активирует обнаружение ошибок разработки (SWS FrSM с. 35).
  • FRSM_VERSION_INFO_API включает или выключает API Version-Info во время компиляции ([SWS_FrSM_00029]); в System Template этот параметр называется FrSMVersionInfoApi.
  • FrSMSyncLossErrorIndicationName задает имя обратного вызова CDD; если параметр отсутствует, индикация не выполняется (SystemTemplate с. 1528, [SWS_FrSM_00190]).

Импортированные типы, включая ComM_ModeType, NetworkHandleType и типы из Fr_GeneralTypes.h, перечислены в [SWS_FrSM_00095].

Поведение при ошибке

Об ошибках разработки FrSM сообщает через Det_ReportError ([SWS_FrSM_00097]) с кодами из [SWS_FrSM_91001]:

  • FRSM_E_PARAM_POINTER (0x01): служба возвращает управление без выполнения каких-либо действий.
  • FRSM_E_INV_HANDLE (0x02): недействительный дескриптор сети.
  • FRSM_E_UNINIT (0x03): модуль не инициализирован.
  • FRSM_E_INV_MODE (0x04): запрошен недопустимый режим связи.
  • FRSM_INIT_FAILED (0x05): сбой инициализации.

Чтобы другие функции могли проверять инициализацию, FrSm_Init при активном обнаружении ошибок запоминает успешное прохождение инициализации (SWS FrSM с. 35). В R20-11 FrSM_GetCurrentComMode отклоняет запросы до инициализации с кодом E_NOT_OK ([SWS_FrSM_00024]). Передача недопустимого NetworkHandle в FrSm_AllSlots приводит к FRSM_E_INV_HANDLE и E_NOT_OK (SWS FrSM с. 41). Запрос SilentCom, вероятно, подпадает под FRSM_E_INV_MODE, поскольку этот режим на FlexRay не поддерживается (SWS FrSM с. 18).

Если запуск завершается сбоем, срабатывают таймеры: t2 повторяет Startup, а t3 контролирует достижение FullCom (SWS FrSM с. 21). Если кластер не удается синхронизировать, FrSM вызывает FrNm_StartupError ([SWS_FrSM_00097]). О запуске кластера он сообщает как о DEM-событии FRSM_E_CLUSTER_STARTUP (SWS FrSM Fig. 9.7 с. 52). Соответствующие события указываются по ссылке в контейнере FrSMClusterDemEventParameterRefs (SWS FrSM с. 62).

В процессе работы автомат состояний различает два случая сбоя (SWS FrSM с. 18):

  • Ошибки синхронизации часов приводят к переходу в FRSM_ONLINE_PASSIVE; данные не передаются.
  • При недостаточном количестве узлов «холодного» пуска (coldstarter) действует FRSM_LOW_NUMBER_OF_COLDSTARTERS: синхронизация выполняется только по Sync-фреймам, коммуникация сохраняется в полном объеме.

Если ECU теряет синхронизацию, вызывается <Cdd>_SyncLossErrorIndication с true ([SWS_FrSM_00190]). С false вызов следует, как только ECU снова сможет синхронизироваться или запрос FullCom будет снят. На этапе Wakeup вызванный ошибкой переход контроллера в состояние HALT прерывает передачу паттерна (SWS FrSM с. 27).

Использование и контекст вызова

Функция FrSM_RequestComMode ([SWS_FrSM_00020]) служит Communication Manager (ComM) для запуска или останова связи в определенном кластере FlexRay (Startup или Shutdown). Она предоставляется через заголовочный файл FrSm.h и имеет Service-ID 0x02.

Выполнение функции осуществляется асинхронно. Она принимает следующие параметры:

  • NetworkHandle (входной параметр): идентифицирует конкретный кластер FlexRay, для которого запрашивается режим связи.
  • ComM_Mode (входной параметр): передает запрашиваемый режим связи.

Возвращаемые значения и обработка ошибок

Функция возвращает значение статуса типа Std_ReturnType:

  • E_OK: запрос режима был принят (Request accepted). Поскольку вызов выполняется асинхронно, это возвращаемое значение подтверждает принятие задачи FlexRay State Manager.
  • E_NOT_OK: запрос режима был отклонен (Request not accepted).

Параллелизм

Касательно параллелизма [SWS_FrSM_00020] указывает, что FrSM_RequestComMode ревentrantна для различных кластеров FlexRay (Reentrant for different Flex Ray clusters).

Это указание по использованию было сгенерировано автоматически на основе спецификации AUTOSAR Classic Release R20-11.

Функция объявляется с сигнатурой Std_ReturnType FrSm_AllSlots (NetworkHandleType NetworkHandle) и обрабатывает следующие входные и выходные параметры [SWS_FrSM_00172]:

  • Входные параметры: NetworkHandle (тип: NetworkHandleType). Этот параметр идентифицирует соответствующий кластер FlexRay, для которого запрашивается режим связи [SWS_FrSM_00172].
  • Входные/выходные параметры: отсутствуют (None) [SWS_FrSM_00172].
  • Выходные параметры: отсутствуют (None) [SWS_FrSM_00172].

Вызов обладает асинхронной семантикой (Asynchronous) и возвращает значение типа Std_ReturnType [SWS_FrSM_00172]:

  • E_OK: запрос был принят (Request accepted) [SWS_FrSM_00172].
  • E_NOT_OK: запрос не был принят (Request not accepted) [SWS_FrSM_00172].

Тип перечисления FrSM_BswM_StateType определяет состояния FlexRay State Manager (FrSM), которые передаются в Basic Software Mode Manager (BswM), и объявлен через заголовочный файл FrSm.h [SWS_FrSM_00199].

Использование и взаимодействие

Этот тип служит основой данных для передачи статуса в BswM с помощью интерфейса BswM_FrSM_CurrentState [SWS_FrSM_00199]. На основе переданных состояний BswM оценивает смену режимов и координирующие действия коммуникации всего транспортного средства.

Диапазон значений

Согласно [SWS_FrSM_00199] диапазон значений включает следующие состояния от 0x00 до 0x0F:

  • FRSM_BSWM_READY (0x00) и FRSM_BSWM_READY_ECU_PASSIVE (0x01)
  • FRSM_BSWM_STARTUP (0x02) и FRSM_BSWM_STARTUP_ECU_PASSIVE (0x03)
  • FRSM_BSWM_WAKEUP (0x04) и FRSM_BSWM_WAKEUP_ECU_PASSIVE (0x05)
  • FRSM_BSWM_HALT_REQ (0x06) и FRSM_BSWM_HALT_REQ_ECU_PASSIVE (0x07)
  • FRSM_BSWM_KEYSLOT_ONLY (0x08) и FRSM_BSWM_KEYSLOT_ONLY_ECU_PASSIVE (0x09)
  • FRSM_BSWM_ONLINE (0x0A) и FRSM_BSWM_ONLINE_ECU_PASSIVE (0x0B)
  • FRSM_BSWM_ONLINE_PASSIVE (0x0C) и FRSM_BSWM_ONLINE_PASSIVE_ECU_PASSIVE (0x0D)
  • FRSM_LOW_NUMBER_OF_COLDSTARTERS (0x0E) и FRSM_LOW_NUMBER_OF_COLDSTARTERS_ECU_PASSIVE (0x0F)

Интерпретация: парное предоставление регулярных состояний и вариантов с суффиксом _ECU_PASSIVE, вероятно, сигнализирует о том, находится ли электронный блок управления в пассивном режиме во время соответствующего статуса связи.
