Роль Platform_Types.h: общая база типов базового программного обеспечения Classic

Модуль «platform» состоит из заголовочного файла Platform_Types.h. Через него доступны все стандартизированные базовые типы и символы платформы, например uint8 [SWS_Platform_00013], boolean [SWS_Platform_00026] и CPU_TYPE [SWS_Platform_00064]. Модуль не содержит функций. Он определяет, какие диапазоны значений, разрядность в битах и кодировки код на определенной платформе может принимать как исходные условия. Причиной этого является требование, чтобы все модули базового программного обеспечения использовали только типы данных AUTOSAR. Нативные типы C, такие как char, int или long, запрещены, поскольку их размер, знак и точность зависят от платформы (RS_BSWGeneral с. 65).

Модули обычно не подключают эти типы напрямую. В примере из спецификации требований Eep.h включает файл Std_Types.h, а тот автоматически подключает Platform_Types.h (RS_BSWGeneral с. 65). Такие библиотеки, как Bfx, явно возводят свои сокращения u8, u16, s32 и boolean к типам платформы (SWS_BFXLibrary с. 8). Сам файл изменять запрещено: любое расширение аннулирует соответствие AUTOSAR [SWS_Platform_00002].

Контекстная диаграмма: Platform_Types.h является общей базой типов. Модули BSW получают к ней доступ через Std_Types.h; библиотеки, интерфейсы служб и шаблоны моделей обращаются к ней напрямую. Источники: RS_BSWGeneral с. 65, SWS_BFXLibrary с. 8, StandardizationTemplate с. 77, [SWS_Platform_00002]

Целочисленные типы: точная ширина или оптимизированный под платформу минимальный диапазон

Стандартные целочисленные типы имеют фиксированную разрядность и диапазоны значений. uint8, uint16, uint32 и uint64 являются беззнаковыми с разрядностью 8, 16, 32 и 64 бита ([SWS_Platform_00013], [SWS_Platform_00014], [SWS_Platform_00015], [SWS_Platform_00066]). С sint8 по sint64 — это их знаковые аналоги ([SWS_Platform_00016], [SWS_Platform_00017], [SWS_Platform_00018], [SWS_Platform_00067]). Их диапазоны, например -128..+127 для sint8, обусловлены тем, что AUTOSAR поддерживает для компилятора и целевой системы только арифметику в дополнительном коде [SWS_Platform_00061].

Оптимизированные типы, напротив, гарантируют только минимальный диапазон. uint8_least, uint16_least и uint32_least имеют как минимум 8, 16 и 32 бита соответственно и являются производными от uint ([SWS_Platform_00020], [SWS_Platform_00021], [SWS_Platform_00022]). С sint8_least по sint32_least — знаковые варианты, производные от sint ([SWS_Platform_00023], [SWS_Platform_00024], [SWS_Platform_00025]). В спецификации упоминаются два типичных сценария применения: счетчики циклов максимум со 124 итерациями и аргументы switch с 17 состояниями. В обоих случаях следует выбирать uint8_least (SWS_PlatformTypes с. 17).

В полезной нагрузке находятся такие объявления, как typedef unsigned int uint8_least; или typedef unsigned long uint32;. Интерпретация: это отображения для конкретного компилятора. Нормативной является только требуемая разрядность или минимальная разрядность ([SWS_Platform_00015], [SWS_Platform_00020]).

Типы с плавающей точкой и указательные типы для значений и буферов данных

Для значений с плавающей точкой действуют форматы согласно IEEE 754-2008:

  • float32 соответствует формату binary32, диапазон ±3.4028235e+38 [SWS_Platform_00041].
  • float64 соответствует формату binary64, диапазон ±1.7976931348623157e+308 [SWS_Platform_00042].

Для буферов данных без фиксированного типа существуют два указательных типа с заданным направлением:

  • VoidPtr (void*) предназначен для буферов, возвращающих данные вызывающей стороне [SWS_Platform_91001] (SWS_PlatformTypes с. 27).
  • ConstVoidPtr (const void*) предназначен для буферов, передаваемых вызываемой стороне [SWS_Platform_91002] (SWS_PlatformTypes с. 28).

Диаграмма деятельности: выбор подходящего платформенного типа — от boolean через указатели на буфер и типы с плавающей точкой до оптимизированных или строго определенных по ширине целых чисел. Источники: [SWS_Platform_00026], [SWS_Platform_91001], [SWS_Platform_91002], [SWS_Platform_00041], [SWS_Platform_00042], SWS_PlatformTypes с. 17

boolean, TRUE и FALSE: представление и допустимые выражения

В R20-11 boolean реализуется как беззнаковый целочисленный тип с наименьшей битовой длиной, которую платформа поддерживает нативно, чаще всего 8 бит [SWS_Platform_00027]. Зафиксированное объявление имеет вид typedef unsigned char boolean; [SWS_Platform_00026].

Отличие в более поздних релизах: редакция для R24-11/R25-11 требует тип C99 _Bool и больше не определяет размер объекта (SWS_PlatformTypes с. 18). Для R20-11 действует вышеуказанное требование.

Кроме того, boolean должен отображаться на тип, на который могут указывать указатели. Поэтому эффективные битовые типы некоторого аппаратного обеспечения исключены [SWS_Platform_00060]. Это необходимое условие для таких интерфейсов, как CanNm_CheckRemoteSleepIndication, возвращающих результат через boolean* (SWS_CANNetworkManagement с. 68).

TRUE (1) и FALSE (0) определяются только в том случае, если они еще не существуют (#ifndef TRUE) [SWS_Platform_00056]. Их разрешается использовать только вместе с boolean [SWS_Platform_00055]. Для работы с переменными типа boolean действуют следующие правила [SWS_Platform_00034]:

  • Присваивания разрешены только с TRUE, FALSE, операциями сравнения или логическими выражениями (&&, ||, !).
  • Арифметические и побитовые операторы, такие как +, ++, <<, ~ или &, запрещены.
  • Операции сравнения ограничены == TRUE, == FALSE, != TRUE, != FALSE, if (var) и if (!var) (SWS_PlatformTypes с. 18).

Диаграмма деятельности: проверка допустимости присваивания или сравнения с переменной типа boolean. Источники: [SWS_Platform_00034], [SWS_Platform_00055], SWS_PlatformTypes с. 18

Символы платформы CPU_TYPE, CPU_BIT_ORDER и CPU_BYTE_ORDER

Platform_Types.h указывает для каждой платформы три свойства CPU, каждое в виде #define:

  • Разрядность регистров через CPU_TYPE [SWS_Platform_00044]. Допустимы CPU_TYPE_8, CPU_TYPE_16, CPU_TYPE_32 и CPU_TYPE_64 ([SWS_Platform_00045], [SWS_Platform_00064]).
  • Порядок битов на уровне регистров через CPU_BIT_ORDER ([SWS_Platform_00043], [SWS_Platform_00038]).
  • Порядок байтов в памяти через CPU_BYTE_ORDER ([SWS_Platform_00046], [SWS_Platform_00039]).

Соответствие порядку байтов и битов однозначно. Порядок битов big-endian дает MSB_FIRST, порядок битов little-endian дает LSB_FIRST ([SWS_Platform_00048], [SWS_Platform_00049]). Порядок байтов big-endian дает HIGH_BYTE_FIRST, порядок байтов little-endian дает LOW_BYTE_FIRST ([SWS_Platform_00050], [SWS_Platform_00051]).

Спецификация предостерегает от смешивания нумерации битов и их значимости. В архитектурах Motorola с порядком битов big-endian Bit0 обозначает старший значащий бит, во всех остальных — младший. В аккумуляторе же MSB всегда находится крайним слева (SWS_PlatformTypes с. 15).

Диаграмма деятельности: последовательность определения трех символов платформы для целевой платформы без расширения файла. Источники: [SWS_Platform_00045], [SWS_Platform_00048], [SWS_Platform_00049], [SWS_Platform_00050], [SWS_Platform_00051], [SWS_Platform_00002]

Что касается порядка байтов, спецификация демонстрирует 16-битное значение. Его старший байт называется Byte1, а младший — Byte0. При HIGH_BYTE_FIRST Byte1 находится по адресу n, а Byte0 — по адресу n+1, при LOW_BYTE_FIRST — наоборот (SWS_PlatformTypes с. 16). Это обозначение не является однозначным и может отличаться в документации производителей (SWS_PlatformTypes с. 16). На практике порядок байтов важен там, где данные преобразуются между представлением на шине и представлением процессора. Например, AUTOSAR COM должен поддерживать преобразование порядка байтов для типов от uint16 до float64 (подтверждение из R25-11: RS_COM с. 14).

Диаграмма деятельности: размещение значения uint16 в памяти в зависимости от CPU_BYTE_ORDER по мотивам Figure 7.2/7.3 спецификации. Источники: SWS_PlatformTypes с. 16, [SWS_Platform_00039]

Платформенные типы в сервисных интерфейсах и моделях

Другие спецификации строят свои сигнатуры на основе этих типов. Два примера из R24-11/R25-11 демонстрируют правило направления для указателей на буфер ([SWS_Platform_91001], [SWS_Platform_91002]):

  • Key Manager передает в KeyM_ServiceCertificateByCertId данные запроса как ConstVoidPtr с длиной типа uint32. Результаты он принимает через буфер VoidPtr, доступный размер которого указывает ResponseDataLength (INOUT) (SWS_KeyManager с. 111).
  • Операция CSM RandomSeed передает seed как ConstVoidPtr (SWS_CryptoServiceManager с. 124).

Диаграмма последовательности: вызывающая сторона предоставляет данные запроса только для чтения через ConstVoidPtr и получает данные обратно через буфер VoidPtr. Возвращаемое значение сообщает, принял ли сервис запрос. Источники: SWS_KeyManager с. 111, SWS_KeyManager с. 97, [SWS_Platform_91001], [SWS_Platform_91002]

В модели эти типы также прочно закреплены. Из шаблона Blueprint /AUTOSAR/Platform/ImplementationDatatypes_Blueprint/uint8 выводится элемент /AUTOSAR_Platform/ImplementationDatatypes/uint8. Благодаря этому поставщики программного обеспечения находят его по предсказуемому пути (StandardizationTemplate с. 77). Record Layouts ссылаются на базовые типы, такие как /AUTOSAR/Platform/BaseTypes_Blueprint/sint16 (GeneralBlueprintsSupplement с. 47). Библиотеки, такие как Crc, используют uint8, uint32 и boolean непосредственно в своих API (SWS_CRCLibrary с. 41).

Поведение при ошибке

Platform_Types.h предоставляет только типы и символы, доступные через этот файл ([SWS_Platform_00013], [SWS_Platform_00038]). Поэтому поведение при ошибках во время выполнения с возвращаемыми значениями или сообщениями об ошибках, вероятно, отсутствует. Вместо этого ошибки возникают при интеграции и использовании:

  • Расширенный или дополненный файл: любое расширение аннулирует соответствие AUTOSAR [SWS_Platform_00002].
  • Повторные определения: если компилятор уже предоставляет эти символы, повторных определений следует избегать с помощью условной проверки ([SWS_Platform_00054], [SWS_Platform_00056]).
  • Неверные символы платформы: CPU_BYTE_ORDER или CPU_BIT_ORDER, не соответствующие аппаратному обеспечению, нарушают требования с [SWS_Platform_00048] по [SWS_Platform_00051]. Интерпретация: код, выполняющий ветвление по этим символам, в таком случае некорректно собирал бы многобайтовые значения (см. SWS_PlatformTypes с. 16).
  • Битовый тип для boolean: без возможности адресации указателем параметры нельзя передавать через указатели [SWS_Platform_00060].
  • Недопустимые выражения, такие как var++ или var = a & b, нарушают [SWS_Platform_00034].
  • Представления отрицательных чисел, отличные от дополнительного кода, AUTOSAR не поддерживает [SWS_Platform_00061].

Platform Types (Platform_Types)

Фундаментальные типы данных, специфичные для конкретной платформы (целые, логические значения, числа с плавающей запятой), сопоставленные с CPU архитектурными примитивами.

  • typedef sint8_least This optimized AUTOSAR type shall be at least 8 bit signed.

  • typedef ConstVoidPtr This standard AUTOSAR type shall be a void pointer to const.
  • CPU_TYPE This symbol shall be defined as #define having one of the values CPU_TYPE_8, CPU_TYPE_16, CPU_TYPE_32 or CPU_TYPE_64 according...
  • CPU_BIT_ORDER This symbol shall be defined as #define having one of the values MSB_FIRST or LSB_FIRST according to the platform.
  • CPU_BYTE_ORDER This symbol shall be defined as #define having one of the values HIGH_BYTE_FIRST or LOW_ BYTE_FIRST according to the platform.
