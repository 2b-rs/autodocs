Роль ComM между пользователями, Bus State Manager и жизненным циклом

Communication Manager (ComM) принимает потребность в коммуникации от своих пользователей и преобразует её в режимы коммуникации физических каналов. Пользователями могут быть раннейблы, SW-C, BswM или DCM (SWS ComM с. 30). На нижнем уровне ComM обращается исключительно к Bus State Manager. Режимы он запрашивает с помощью <BusSm>_RequestComMode() [SWS_ComM_00958] и опрашивает их с помощью <BusSm>_GetCurrentComMode() [SWS_ComM_00963]. Префикс (CanSM, LinSM, FrSM, EthSM) определяется из ComMBusType [SWS_ComM_00962]. Сообщённый режим шины ComM получает через ComM_BusSM_ModeIndication и передаёт его пользователям через RTE и BswM [SWS_ComM_00675].

Другими партнерами являются:

  • Nm, через колбэки ComM_Nm_*,
  • EcuM, который сообщает о пробуждениях,
  • NvM, для постоянных данных,
  • BswM, с BswM_ComM_CurrentPNCMode и BswM_ComM_InitiateReset [SWS_ComM_00829].

Контекстная диаграмма: ComM выступает посредником между пользователями (RTE, DCM, BswM) с одной стороны и Nm, а также Bus State Manager с другой стороны. NvM, Com и SchM являются поставщиками сервисов. Источники: SWS ComM (Abb.) с. 17, [SWS_ComM_00829], [SWS_ComM_00871].

Инициализация: ComM_Init принимает структуру post-build ComM_ConfigType и заново инициализирует внутренние конечные автоматы [SWS_ComM_00146] [SWS_ComM_00162]. При этом ComM считывает энергонезависимые параметры из NVRAM. Если это не удаётся, он использует значения по умолчанию (SWS ComM с. 97).

Состояние и работа: ComM_GetStatus возвращает COMM_UNINIT или COMM_INIT [SWS_ComM_00242] [SWS_ComM_00668]. Во время работы для каждого канала функционирует собственный ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429].

Партиционирование: вызовы из сторонних разделов должны обеспечиваться через сателлит [SWS_ComM_01019]. API Bus State Manager вызываются ComM только в их разделе [SWS_ComM_01020].

Деинициализация: ComM_DeInit [SWS_ComM_00147] действует только тогда, когда все каналы находятся в COMM_NO_COMMUNICATION. При этом ComM сохраняет NV-параметры (SWS ComM с. 114).

Конечный автомат канала: No, Silent и Full Communication

ComM_ModeType поддерживает четыре значения [SWS_ComM_00672]:

  • COMM_NO_COMMUNICATION,
  • COMM_SILENT_COMMUNICATION,
  • COMM_FULL_COMMUNICATION,
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST, только внутри.

Пользователям разрешено запрашивать только No и Full. Silent служит исключительно для синхронизации с NM (SWS ComM с. 30, [SWS_ComM_00110]). Для каждого канала выполняется собственный конечный автомат (SWS ComM с. 65). ComM_StateType кодирует основные состояния и подсостояния [SWS_ComM_00674].

Переход в Full Communication:

  • Запрос без активного ограничения или активная диагностика приводит к COMM_NO_COM_REQUEST_PENDING (SWS ComM с. 69).
  • Дальнейший переход в Full происходит только тогда, когда ComM_CommunicationAllowed освобождает канал [SWS_ComM_00871]. Если запрос снимается раньше, канал возвращается в исходное состояние (SWS ComM с. 63).

Завершение работы в зависимости от варианта ComMNmVariant:

  • PASSIVE и SLAVE_PASSIVE безусловно переходят в COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915].
  • SLAVE_ACTIVE переходит туда, как только запросы пользователей перестают поступать [SWS_ComM_01017].
  • ComM_Nm_PrepareBusSleepMode при FULL или PASSIVE приводит к Silent [SWS_ComM_00826]. Там передача отключена, приём остаётся активным (SWS ComM с. 71).
  • Slave-каналы завершают коммуникацию через ComM_BusSM_BusSleepMode [SWS_ComM_01018] [SWS_ComM_91000].
  • Каналы LIGHT выходят из Full по истечении ComMNmLightTimeout (SWS ComM с. 78).

Диаграмма состояний: основные состояния и подсостояния канала ComM с событиями-триггерами для каждого варианта NM. Источники: SWS ComM (Abb.) с. 46, SWS ComM (Abb.) с. 41, [SWS_ComM_00826], [SWS_ComM_00915], [SWS_ComM_01017], [SWS_ComM_01018].

Запрос коммуникации со стороны пользователей и диагностики

Пользователи и сопоставление: пользователь идентифицируется через ComM_UserHandleType. Допустимыми являются значения 0..254; 255 обозначает COMM_NOT_USED_USER_ID [SWS_ComM_00670]. Пользователи статически сопоставлены с каналами [SWS_ComM_00995] или PNC [SWS_ComM_00912]. Одновременное сопоставление с PNC и с его каналом недопустимо [SWS_ComM_00996].

Порты к RTE:

  • UR_{user_name} предоставляет интерфейс ComM_UserRequest [SWS_ComM_01011] [SWS_ComM_01000].
  • UM_{user_name} предоставляет интерфейс переключения режимов ComM_CurrentMode [SWS_ComM_01010] [SWS_ComM_01001]. Группа режимов ComMMode запускается в COMM_NO_COMMUNICATION [SWS_ComM_01012].

Диаграмма кооперации: порты, через которые пользовательские SW-C, менеджеры режимов и инструменты для сопоставления PNC взаимодействуют с ComM. Источники: SWS ComM (Abb.) с. 81, [SWS_ComM_01006], [SWS_ComM_01007], [SWS_ComM_01008], [SWS_ComM_01009], [SWS_ComM_91107].

Запрос и освобождение: запрос поступает либо через ComM_RequestComMode [SWS_ComM_00110], либо через ComM_DCM_ActiveDiagnostic [SWS_ComM_00873]. Диагностика снова освобождает канал с помощью ComM_DCM_InactiveDiagnostic [SWS_ComM_00874]. Во время активной диагностики ограничение временно не действует (SWS ComM с. 69).

Диаграмма последовательности: активный запуск от No к Full Communication на примере CAN в зависимости от варианта NM. Источники: SWS ComM с. 167, SWS ComM (Abb.) с. 107, SWS ComM с. 75.

Опрос:

  • ComM_GetRequestedComMode возвращает энергозависимо сохранённый в ComM запрос пользователя [SWS_ComM_00079] (SWS ComM с. 118).
  • ComM_GetCurrentComMode опрашивает Bus State Manager [SWS_ComM_00083].
  • ComM_GetMaxComMode учитывает активные ограничения [SWS_ComM_00085].
  • При наличии нескольких каналов на одного пользователя обе функции возвращают наименьший режим (SWS ComM с. 119, SWS ComM с. 117).
  • Опционально порт CR_{channel_name} указывает пользователей, которые в данный момент удерживают канал в Full [SWS_ComM_00904] [SWS_ComM_00906] [SWS_ComM_01005].

Пробуждение, сетевое управление и штатное отключение

Пассивный запуск: он начинается с ComM_EcuM_WakeUpIndication [SWS_ComM_00275] или ComM_EcuM_PNCWakeUpIndication [SWS_ComM_91001]. При пробуждении PNC объём зависит от ComMSynchronousWakeUp:

  • При FALSE только связанные каналы переходят в COMM_NO_COM_REQUEST_PENDING [SWS_ComM_01014].
  • При TRUE переходят все каналы [SWS_ComM_01015].

В состоянии Network Requested ComM затем запрашивает Nm_PassiveStartup. Для управляемых каналов это происходит на управляющем канале [SWS_ComM_01016]. То же самое относится к ситуации после ComM_Nm_RestartIndication [SWS_ComM_00792] (SWS ComM с. 75).

Диаграмма последовательности: реакция на пробуждение или перезапуск NM вплоть до Full Communication. Источники: SWS ComM (Abb.) с. 104, [SWS_ComM_00383], [SWS_ComM_01016], [SWS_ComM_00915].

Отключение: оно начинается, когда последний пользователь освобождает Full или срабатывает ComM_LimitChannelToNoComMode (SWS ComM с. 166). Порядок действий:

  1. В состоянии Ready Sleep ComM вызывает Nm_NetworkRelease при FULL (SWS ComM с. 78).
  2. NM сообщает о ComM_Nm_PrepareBusSleepMode [SWS_ComM_00391]; канал переходит в Silent.
  3. NM сообщает о ComM_Nm_BusSleepMode [SWS_ComM_00392]; канал переходит в No Communication.

ComM_Nm_NetworkMode, наоборот, указывает на вход в Network Mode [SWS_ComM_00390].

Диаграмма последовательности: освобождение или принудительное ограничение через Ready Sleep и Silent вплоть до Bus-Sleep, опционально со сбросом ECU. Источники: SWS ComM (Abb.) с. 106, SWS CanNm с. 87, SWS CanSM с. 29, [SWS_ComM_00826], [SWS_ComM_00355].

Кластеры Partial Network и динамическое сопоставление PNC (Draft)

Базовый принцип: PNC пробуждают логические группы ECU вместо целых шин (SWS ComM с. 31). Для каждого PNC существует собственный конечный автомат; действия PNC выполняются до действий канала (SWS ComM с. 35). Режимы описывает ComM_PncModeType [SWS_ComM_00673].

Сопоставление с каналами:

  • PNC сопоставляются с каналами через ComMChannelPerPnc [SWS_ComM_00913].
  • Битовая позиция PNC вычисляется согласно [SWS_ComM_00825].
  • Для хостов с Ethernet-коммутатором действует конфигурационное ограничение [SWS_ComM_CONSTR_00001].

Особенность R20-11: обмен статусом всё ещё происходит через Com-сигналы (Com_SendSignal, колбэк EIRA/ERA ComM_COMCbk_<sn>) [SWS_ComM_00164] [SWS_ComM_00959] [SWS_ComM_00819]. Только R21-11 заменяет его специализированными API (SWS ComM с. 2).

Диаграмма состояний: конечный автомат PNC с локальным запросом, шлюзовым ERA и триггерами пробуждения. Источники: SWS ComM с. 37, SWS ComM с. 34, SWS ComM с. 43, [SWS_ComM_00964], [SWS_ComM_00165], [SWS_ComM_01053].

Динамическое сопоставление PNC с каналами: эта функция является новой в R20-11 и помечена как Draft (SWS ComM с. 2).

  • Фаза обучения: ComM_PnLearningRequest запускает её [SWS_ComM_91019] [SWS_ComM_01026]. Шлюзы пересылают запросы на обучение [SWS_ComM_01028]. ComM_Nm_RepeatMessageLeftIndication завершает фазу [SWS_ComM_01029].
  • Во время фазы обучения ComM переносит принятые биты ERA в сопоставление [SWS_ComM_01031] и отправляет собственное членство [SWS_ComM_01032] [SWS_ComM_01033].
  • API управления: ComM_GetPncToChannelMapping, ComM_UpdatePncToChannelMapping, ComM_ResetPncToChannelMapping и ComM_UpdatePncMembership [SWS_ComM_91013] [SWS_ComM_91015] [SWS_ComM_91017] [SWS_ComM_91021].

Различия между релизами:

  • В R20-11 ComM_GetPncToChannelMapping имеет параметры boolean* MappingTable и PncCnt. Более поздние релизы используют uint8-битовый вектор с PNCBitVectorLength (SWS ComM с. 122); определяющим здесь является [SWS_ComM_91013].
  • Требования R20-11 в отличие от этого говорят о ComM_GetPncMappingTable [SWS_ComM_01034].
  • ComM_Nm_ForwardSynchronizedPncShutdown в R20-11 имеет только параметр Channel [SWS_ComM_91003]. Позже добавляется битовый вектор PNC (SWS ComM с. 137).

Диаграмма последовательности: фаза обучения PNC от запуска через обновление сопоставления до выхода из Repeat Message. Источники: SWS ComM с. 56, SystemTemplate (Abb.) с. 329, [SWS_ComM_01026], [SWS_ComM_01029], [SWS_ComM_01031], [SWS_ComM_01035].

Ограничение коммуникации и сохраняемый статус ингибирования

Статус ингибирования: представляет собой битовое поле [SWS_ComM_00669]:

  • Бит 0: ингибирование пробуждения,
  • Бит 1: Limit to No Com.

ComMEcuGroupClassification действует как маска, определяющая, какие ингибирования вообще разрешено выполнять. Она устанавливается через ComM_SetECUGroupClassification [SWS_ComM_00552] (SWS ComM с. 73). Статус сохраняется в энергонезависимой памяти и восстанавливается при запуске (SWS ComM с. 84).

Управляющие API:

  • ComM_LimitChannelToNoComMode [SWS_ComM_00163],
  • ComM_LimitECUToNoComMode [SWS_ComM_00124],
  • ComM_PreventWakeUp [SWS_ComM_00156],
  • ComM_GetInhibitionStatus для считывания [SWS_ComM_00619].

SW-C менеджера режимов обращаются к этим функциям через интерфейсы ComM_ChannelLimitation, ComM_ChannelWakeup и ComM_ECUModeLimitation [SWS_ComM_00743] [SWS_ComM_00742] [SWS_ComM_00741] (SWS ComM (Abb.) с. 68).

Действие ограничения:

  • Активно запрошенный канал переходит в Ready Sleep, несмотря на существующие запросы пользователей. Канал, поддерживаемый в активном состоянии пассивно, остаётся незатронутым (SWS ComM с. 88).
  • Запросы во время действия ограничения отклоняются. После его отмены пользователи должны запросить заново (SWS ComM с. 91).
  • Если установлен ComMResetAfterForcingNoComm, ComM инициирует сброс ECU через BswM [SWS_ComM_00355].
  • Отклонённые запросы Full подсчитываются счётчиком запретов. ComM_ReadInhibitCounter считывает его, ComM_ResetInhibitCounter сбрасывает его [SWS_ComM_00224] [SWS_ComM_00108]. Обе функции доступны только при ComMModeLimitationEnabled и сконфигурированном блоке NvM (SWS ComM с. 130).

Диаграмма деятельности: путь принятия решений при активации «Limit to No Com» вплоть до опционального сброса. Источники: SWS ComM с. 88, SWS ComM с. 84, [SWS_ComM_00163], [SWS_ComM_00110], [SWS_ComM_00355].

Поведение при ошибке

Неинициализированный модуль: без инициализации все API, кроме ComM_Init, ComM_GetVersionInfo и ComM_GetStatus, не выполняют стандартных операций и возвращают E_NOT_OK [SWS_ComM_00612].

Ошибки разработки: ошибками разработки являются COMM_E_UNINIT, COMM_E_WRONG_PARAMETERS, COMM_E_PARAM_POINTER и COMM_E_INIT_FAILED [SWS_ComM_00234].

Специфические возвращаемые значения лежат в диапазоне [SWS_ComM_91027]:

Bus-Off: CanSM сообщает о COMM_SILENT_COMMUNICATION через ComM_BusSM_ModeIndication (EXP ErrorDescription с. 19). ComM передаёт этот режим пользователям [SWS_ComM_00675].

Деинициализация: ComM_DeInit не может сообщить об ошибке. Поэтому вызывающая сторона должна предварительно убедиться, что все каналы находятся в No Communication (SWS ComM с. 114).
