Роль SecOC: защита I-PDU наряду с маршрутизатором PDU

SecOC (Secure Onboard Communication) защищает I-PDU от манипуляций и повторного воспроизведения. При отправке SecOC добавляет к Authentic I-PDU аутентификационную информацию, состоящую из при необходимости усеченного Freshness Value и аутентификатора. В результате получается Secured I-PDU. При приеме эта информация проверяется перед тем, как Authentic I-PDU будет передана дальше ([SWS_SecOC_00040], SWS SecOC Рис. 7.2 с. 30). Аутентификатор вычисляется путем конкатенации трех частей: Data Identifier (SecOCDataId), защищенная часть Authentic I-PDU и полный Freshness Value (SWS SecOC с. 29).

В архитектуре SecOC располагается рядом с PduR. Верхние уровни, такие как Com, отправляют данные через PduR_<Up>Transmit. Затем PduR вызывает SecOC_[If|Tp]Transmit, и SecOC снова передает Secured I-PDU через PduR интерфейсу шины или транспортному протоколу (SWS SecOC с. 40, SWS SecOC Рис. 1.1 с. 10). MetaData из Authentic PDU отображаются без изменений в Secured PDU, и наоборот верно то же самое ([SWS_SecOC_00212]). Никакой другой модуль не должен зависеть от SecOC, чтобы систему можно было собрать и без SecOC (SWS SecOC с. 39).

SecOC взаимодействует с несколькими другими модулями:

  • Криптографию предоставляет CSM, в том числе через Csm_MacGenerate и Csm_MacVerify ([SWS_SecOC_00138]). Для асинхронных заданий CSM модуль SecOC предоставляет специфичные для производителя функции обратного вызова (SWS SecOC с. 78).
  • Freshness Values поступают от Freshness Manager. В случае SecOCQueryFreshnessValue = RTE он подключается через порт FreshnessManagement ([SWS_SecOC_91001]), а в случае CFUNC — через функции C ([SWS_SecOC_00231], [SWS_SecOC_00247]).
  • Об ошибках SecOC сообщает в DET ([SWS_SecOC_00101]).
  • Security Events передаются в IdsM ([SWS_SecOC_00273]).

Контекстная диаграмма: SecOC встраивается через PduR между верхними и нижними коммуникационными модулями и получает криптографию от CSM, а свежесть — от Freshness Manager. Источники: SWS SecOC Рис. 1.1 с. 10, [SWS_SecOC_00138], [SWS_SecOC_91001], [SWS_SecOC_00142], [SWS_SecOC_00273]

Состояние модуля и циклические Main Functions

SecOC поддерживает два состояния: SECOC_UNINIT и SECOC_INIT ([SWS_SecOC_00162]):

  • Успешная инициализация с помощью SecOC_Init переводит модуль в SECOC_INIT ([SWS_SecOC_00106]).
  • SecOC_DeInit останавливает защищенную связь, отбрасывает все буферизованные I-PDU и переводит модуль в неинициализированное состояние ([SWS_SecOC_00161]). При этом также очищаются внутренние глобальные переменные (SWS SecOC с. 65).
  • Для вызовов API без инициализации предусмотрена ошибка SECOC_E_UNINIT, а для неудачной инициализации — SECOC_E_INIT_FAILED ([SWS_SecOC_00101]).
  • Если модуль не инициализирован, SecOC_MainFunctionTx немедленно возвращает управление (SWS SecOC с. 84).

Фактическая криптографическая обработка выполняется не в контексте вызова функций отправки или приема, а циклически. Для каждого сконфигурированного экземпляра SecOCMainFunctionTx или SecOCMainFunctionRx имеется собственная SecOC_MainFunctionTx_<shortName> или SecOC_MainFunctionRx_<shortName> ([SWS_SecOC_00176], [SWS_SecOC_00171]). Соответствующий период настраивается с помощью SecOCMainFunctionPeriodTx или SecOCMainFunctionPeriodRx (SWS SecOC с. 130, SWS SecOC с. 129). Tx-PDU обрабатывается в той Main Function, на которую указывает ссылка SecOCTxPduMainFunctionRef ([SWS_SecOC_00276]).

Диаграмма состояний: обработка происходит только в SECOC_INIT; SecOC_DeInit сбрасывает все буферы. Источники: [SWS_SecOC_00162], [SWS_SecOC_00106], [SWS_SecOC_00161], [SWS_SecOC_00101], SWS SecOC с. 84

Тракт передачи: от Authentic I-PDU к Secured I-PDU

Процесс отправки начинается с SecOC_IfTransmit или SecOC_TpTransmit ([SWS_SecOC_00112], [SWS_SecOC_91008]). SecOC копирует полную Authentic I-PDU в собственную память до того, как начнется передача Secured I-PDU ([SWS_SecOC_00252]). После этого вызов возвращает управление.

При следующем вызове SecOC_MainFunctionTx все новые Authentic I-PDU проходят аутентификацию. Каждая готовая Secured I-PDU немедленно отправляется через PduR (SWS SecOC с. 84). Формирование включает шесть шагов: от подготовки Secured I-PDU до увеличения Freshness Counter и отправки (SWS SecOC с. 33).

В режиме CFUNC значение Freshness Value возвращает одна из двух функций в зависимости от SecOCProvideTxTruncatedFreshnessValue:

  • SecOC_GetTxFreshnessTruncData, которая дополнительно предоставляет усеченное значение ([SWS_SecOC_00230], [SWS_SecOC_91003]), или
  • SecOC_GetTxFreshness ([SWS_SecOC_00231], [SWS_SecOC_91004]).

О том, что отправка Secured I-PDU была инициирована, SecOC сообщает модулю Freshness Manager через SecOC_SPduTxConfirmation или FreshnessManagement_SPduTxConfirmation ([SWS_SecOC_00232], [SWS_SecOC_00233]).

После отправки SecOC берет на себя роль верхнего модуля по отношению к нижнему уровню (SWS SecOC с. 40):

  • Getriggerte Übertragung (например, FrIf): нижний уровень запрашивает данные с помощью SecOC_TriggerTransmit ([SWS_SecOC_00127]). Для этого требуется предварительный вызов SecOC_IfTransmit; режим работы AlwaysTransmit использовать нельзя (SWS SecOC с. 44).
  • Transportprotokolle: данные запрашиваются с помощью SecOC_CopyTxData ([SWS_SecOC_00129]).
  • Подтверждение: результат из SecOC_[If|Tp]TxConfirmation SecOC передает наверх через PduR_SecOC[If|Tp]TxConfirmation ([SWS_SecOC_00063]).

Если настроен SecOCPduType = SECOC_TPPDU, то SecOC_TpTransmit запускает процесс отправки. Затем SecOC фрагментами забирает Authentic I-PDU у верхнего уровня через PduR_SecOCTpCopyTxData ([SWS_SecOC_00253], [SWS_SecOC_00254], SWS SecOC Рис. 9.4 с. 109).

Диаграмма последовательности: вызов отправки выполняет только буферизацию; обработка свежести, MAC и отправка происходят развязано в SecOC_MainFunctionTx. Расположение SecOC_SPduTxConfirmation после успешного вызова отправки является интерпретацией. Источники: SWS SecOC Рис. 9.1 с. 96, [SWS_SecOC_00252], [SWS_SecOC_00231], [SWS_SecOC_00232], [SWS_SecOC_00063]

Тракт приема: буферизация, верификация, передача

При приеме для SecOC всегда действует один и тот же порядок: сначала принять полную Secured I-PDU в собственную память, затем верифицировать ее в следующем SecOC_MainFunctionRx (SWS SecOC с. 50). Authentic I-PDU копируется только тогда, когда Secured I-PDU получена полностью ([SWS_SecOC_00255]).

  • Bus-Interfaces: о приеме сообщается через SecOC_RxIndication ([SWS_SecOC_00124]).
  • Transportprotokolle: прием происходит через SecOC_StartOfReception, SecOC_CopyRxData и SecOC_TpRxIndication ([SWS_SecOC_00130], [SWS_SecOC_00128], [SWS_SecOC_00125]). При SECOC_TPPDU SecOC передает начало приема на верхний уровень через PduR_SecOCTpStartOfReception (SWS SecOC с. 54).

Верификация выполняется в шесть фиксированных шагов ([SWS_SecOC_00040]):

  1. Разделить Authentic I-PDU, Freshness Value и Authenticator.
  2. Получить Freshness Value от Freshness Manager.
  3. Сформировать данные для аутентификации.
  4. Проверить Authenticator.
  5. Подтвердить результат DEM Freshness Manager.
  6. Передать Authentic I-PDU на верхний уровень.

Какая функция возвращает Freshness Value, зависит от SecOCUseAuthDataFreshness:

  • При FALSE модуль SecOC вызывает SecOC_GetRxFreshness ([SWS_SecOC_00247], [SWS_SecOC_91007]).
  • При TRUE модуль SecOC вызывает SecOC_GetRxFreshnessAuthData, передавая при этом фрагмент Authentic I-PDU ([SWS_SecOC_00246], [SWS_SecOC_91006]).
  • В режиме RTE те же правила действуют для операций FreshnessManagement ([SWS_SecOC_00244], [SWS_SecOC_00245]).

Если проверка прошла успешно, результатом является SECOC_VERIFICATIONSUCCESS ([SWS_SecOC_00242]), и Authentic I-PDU передается на верхний уровень (PRS SecOC с. 18).

Для шлюзов SecOC поддерживает тракты с повторной аутентификацией, то есть верификацию на шине-источнике и повторную аутентификацию для целевой шины. «Gatewaying-on-the-fly» при этом не поддерживается (SWS SecOC с. 57, SWS SecOC Рис. 9.9 с. 102).

Диаграмма последовательности: индикация выполняет только буферизацию. Верификация, подтверждение модулю Freshness Manager и передача далее выполняются в SecOC_MainFunctionRx в порядке, определенном в SWS_SecOC_00040. Источники: SWS SecOC Рис. 9.5 с. 100, [SWS_SecOC_00040], [SWS_SecOC_00247], [SWS_SecOC_00243]

Диаграмма последовательности: при приеме TP модуль Secured I-PDU полностью буферизуется по сегментам и только после этого верифицируется. Источники: SWS SecOC Рис. 9.6 с. 101, [SWS_SecOC_00130], [SWS_SecOC_00128], [SWS_SecOC_00125], [SWS_SecOC_00255], [SWS_SecOC_00040]

Интерфейсы приложений: статус верификации, Override, Default-Pattern

Verifikationsstatus. Результат каждой верификации объединяет SecOC_VerificationStatusType: Freshness Value ID и результат типа SecOC_VerificationResultType ([SWS_SecOC_00160], [SWS_SecOC_00149]). Куда передается статус, определяет Propagation Mode:

  • При BOTH или FAILURE_ONLY он передается приложению через VerificationStatusIndication, а при NONE уведомление не отправляется ([SWS_SecOC_00271], [SWS_SecOC_91016]).
  • При SecOCPropagateOnlyFinalVerificationStatus = TRUE сообщается только конечный статус, в противном случае — также каждая неудачная промежуточная попытка ([SWS_SecOC_00272]).
  • Freshness Manager получает результат через SecOC_VerificationStatusCallout, например, для синхронизации счетчиков ([SWS_SecOC_00119], [SWS_SecOC_00243]).
  • SecOC_VerifyStatus информирует приложение о результате проверки ([SWS_SecOC_91014]).

Override. С помощью SecOC_VerifyStatusOverride приложение может принудительно задать поведение для Freshness Value ID или Data ID ([SWS_SecOC_00122], [SWS_SecOC_00142]). Значения SecOC_OverrideStatusType для R20-11 ([SWS_SecOC_00991]):

  • SECOC_OVERRIDE_DROP_UNTIL_NOTICE и SECOC_OVERRIDE_DROP_UNTIL_LIMIT: проверка CSM не выполняется, I-PDU отбрасывается, результатом является SECOC_NO_VERIFICATION.
  • SECOC_OVERRIDE_PASS_UNTIL_NOTICE: проверка выполняется, однако I-PDU передается дальше независимо от результата.
  • SECOC_OVERRIDE_CANCEL: завершает активный Override.

В фрагменте документа из R23-11 дополнительно упоминаются SECOC_OVERRIDE_SKIP_UNTIL_LIMIT и SECOC_OVERRIDE_PASS_UNTIL_LIMIT (SWS SecOC с. 102). Текст требования R20-11 в полезной нагрузке в этом месте сокращен.

Default-Pattern. SecOC_SendDefaultAuthenticationInformation включает или выключает для каждого Freshness Value ID отправку с использованием SecOCDefaultAuthenticationInformationPattern ([SWS_SecOC_91013]). Этот интерфейс существует только в том случае, если данный шаблон сконфигурирован ([SWS_SecOC_00002], [SWS_SecOC_91020]).

Конфигурация, структура PDU и раздельные Cryptographic I-PDU

Konfigurationscontainer. Каждая защищаемая PDU передачи настраивается в SecOCTxPduProcessing, а каждая проверяемая PDU приема — в SecOCRxPduProcessing. К ним относятся Data ID, Freshness Value ID, длины и счетчики попыток (SWS SecOC с. 155, SWS SecOC с. 140).

PDU-Aufbau. Secured I-PDU состоит из опционального заголовка, Authentic I-PDU, опционального Freshness Value и Authenticator. Freshness Value и Authenticator могут передаваться в усеченном виде (SWS SecOC Рис. 5 с. 29). Неиспользуемые области SecOC заполняет SecOCTxPduUnusedAreasDefault ([SWS_SecOC_00269]). Какой объем данных приемник выделяет в качестве Authentic I-PDU, зависит от заголовка и типа длины:

  • Без заголовка и со статической длиной применяется сконфигурированная длина глобальной PDU ([SWS_SecOC_00257]).
  • Без заголовка и с динамической длиной применяется длина, о которой сообщает нижний уровень ([SWS_SecOC_00258]).
  • При наличии заголовка применяется длина из заголовка ([SWS_SecOC_00259]).

Getrennte Cryptographic I-PDU. При использовании SecOCTxSecuredPduCollection Secured I-PDU отправляется в виде двух сообщений: как Authentic I-PDU и как отдельная Cryptographic I-PDU ([SWS_SecOC_00201], TPS SystemTemplate Рис. 6.18 с. 244). Для этого действуют следующие правила:

  • Оба сообщения отправляются в одном и том же цикле Main Function ([SWS_SecOC_00202]).
  • Message Linker, представляющий собой повторяемый в Cryptographic I-PDU фрагмент Authentic I-PDU, связывает оба сообщения ([SWS_SecOC_00209], [SWS_SecOC_00210]).
  • Приемник выполняет верификацию только тогда, когда получены оба сообщения с подходящим Linker ([SWS_SecOC_00203], [SWS_SecOC_00211]).
  • В случае успеха SecOC очищает оба буфера. В случае неудачи оба сообщения остаются буферизованными, и проверка повторяется при поступлении новых данных ([SWS_SecOC_00207], [SWS_SecOC_00208]).
  • Верхний уровень получает E_OK только в том случае, если оба подтверждения отправки имели значение E_OK ([SWS_SecOC_00270]).
  • При стратегии переполнения QUEUE использование Rx-Collection недопустимо ([SWS_SecOC_CONSTR_00265]).

Поведение при ошибке

Sendeseite.

  • Если CSM сообщает об устранимой ошибке (например, E_BUSY), SecOC не отправляет Secured I-PDU. Authentic I-PDU сохраняется и проходит повторную аутентификацию в следующей Main Function ([SWS_SecOC_00151]).
  • Если достигнуто SecOCAuthenticationBuildAttempts, SecOC сообщает SECOC_E_CRYPTO_FAILURE в DET ([SWS_SecOC_00155]).
  • При достижении лимита, при E_NOT_OK запроса свежести или при неустранимой ошибке CSM модуль SecOC отправляет данные с шаблоном по умолчанию (Default-Pattern), если он активирован ([SWS_SecOC_00229]).
  • Если шаблон не сконфигурирован, SecOC удаляет Authentic I-PDU и прерывает запрос на отправку (SWS SecOC с. 124). Сконфигурированный, но не активированный шаблон, вероятно, обрабатывается аналогично, поскольку остальная часть [SWS_SecOC_00229] в полезной нагрузке обрезана.

Прерывание и ошибки при передаче данных.

  • Если верхний уровень выполняет отмену через SecOC_IfCancelTransmit или SecOC_TpCancelTransmit ([SWS_SecOC_00113], [SWS_SecOC_91009]), SecOC немедленно информирует нижний уровень, останавливает все связанные действия и освобождает буферы (SWS SecOC с. 48).
  • Если нижний уровень сообщает об ошибке отправки, SecOC обрабатывает ее лишь тем, что не отправляет подтверждение верхнему уровню (там же).
  • Если PduR_SecOCTpCopyTxData возвращает BUFREQ_E_BUSY, SecOC повторяет вызов в следующей Main Function. При BUFREQ_E_NOT_OK SecOC немедленно прекращает выполнение с E_NOT_OK ([SWS_SecOC_00260], [SWS_SecOC_00266]).
  • Для приема то же самое действует при PduR_SecOCTpCopyRxData ([SWS_SecOC_00267]).

Empfangsseite. SecOC ведет по два счетчика для каждой Secured I-PDU, которые при начальной обработке установлены в 0 ([SWS_SecOC_00234], [SWS_SecOC_00235]):

  • Счётчик сборки: увеличивается при E_BUSY запроса свежести и при устранимых ошибках CSM ([SWS_SecOC_00236], [SWS_SecOC_00237]). Ниже SecOCAuthenticationBuildAttempts повтор выполняется в следующей Rx-Main-Function ([SWS_SecOC_00238]). При достижении предела SecOC отбрасывает PDU с SECOC_AUTHENTICATIONBUILDFAILURE ([SWS_SecOC_00240]).
  • Счётчик верификации: увеличивается при подлинной ошибке проверки, при этом счётчик сборки сбрасывается ([SWS_SecOC_00239]). При достижении предела SecOCAuthenticationVerifyAttempts или при E_NOT_OK/KEY_FAILURE SecOC отбрасывает PDU с SECOC_VERIFICATIONFAILURE ([SWS_SecOC_00241]).

Если запрос свежести возвращает E_NOT_OK, PDU отбрасывается с SECOC_FRESHNESSFAILURE ([SWS_SecOC_00256]). [SWS_SecOC_00248], напротив, описывает тот же случай как подсчитываемый сбой верификации с сообщением DET SECOC_E_FRESHNESS_FAILURE ([SWS_SecOC_00114]). Интерпретация: оба требования действуют для R20-11. Как именно они разграничиваются между собой, спецификация оставляет открытым; проекту интеграции следует прояснить это с поставщиком.

Override может отменить отбрасывание ([SWS_SecOC_00240]). Если PDU со статической длиной оказывается слишком короткой, SecOC молча отбрасывает её ([SWS_SecOC_00268]). R20-11 связывает это с параметром EcuC DynamicLength; в фрагменте документации R23-11 вместо этого используется SecOCDynamicRuntimeLengthHandling (SWS SecOC с. 52).

События безопасности. О неудачных проверках MAC и отсутствующих значениях Freshness Values модуль SecOC сообщает как о SECOC_SEV_MAC_VERIFICATION_FAILED или SECOC_SEV_FRESHNESS_NOT_AVAILABLE соответственно в IdsM ([SWS_SecOC_00274], [SWS_SecOC_00275]).

Диаграмма деятельности: устранимые ошибки учитываются в SecOCAuthenticationBuildAttempts, а подлинные ошибки проверки — в SecOCAuthenticationVerifyAttempts; каждое прерывание получает собственный результат. Источники: SWS SecOC Рис. 7.5 с. 42, SWS SecOC Рис. 9.10 с. 103, [SWS_SecOC_00236]–[SWS_SecOC_00242], [SWS_SecOC_00256]

Диаграмма деятельности: на стороне передачи исчерпание лимита повторных попыток приводит либо к отправке с шаблоном по умолчанию (Default-Pattern), либо к прерыванию. Ветвь «сконфигурировано, но не активировано», предположительно, относится к прерыванию. Источники: [SWS_SecOC_00151], [SWS_SecOC_00155], [SWS_SecOC_00229], [SWS_SecOC_91013], SWS SecOC с. 124

Константы перечисления отражают возможные результаты и причины ошибок процесса верификации:

  • SECOC_VERIFICATIONSUCCESS (0x00): криптографическая верификация I-PDU прошла успешно.
  • SECOC_VERIFICATIONFAILURE (0x01): верификация в целом завершилась неудачно.

Использование SecOC_OverrideStatusType

Перечислимый тип SecOC_OverrideStatusType определяет согласно [SWS_SecOC_00991] различные рабочие режимы для переопределения статуса верификации в модуле SecOC. Тип предоставляется через заголовочный файл Rte_SecOC_Type.h и управляет поведением при обработке и пересылке I-PDU на вышележащий уровень.

Значения перечисления разделяются по своей семантике и длительности действия (до отмены или до достижения счетчика Number Of Messages To Override):

  • Сброс (Drop): при SECOC_OVERRIDE_DROP_UNTIL_NOTICE (0x00) и SECOC_OVERRIDE_DROP_UNTIL_LIMIT (0x01) верификация аутентификатора не выполняется (нет вызова CSM). Затрагиваемая I-PDU отбрасывается, а результат верификации устанавливается в SECOC_NO_VERIFICATION.
  • Отмена: с помощью SECOC_OVERRIDE_CANCEL (0x02) отменяется активное переопределение статуса верификации.
  • Проверка и пересылка (Pass): при SECOC_OVERRIDE_PASS_UNTIL_NOTICE (0x40), а также SECOC_OVERRIDE_PASS_UNTIL_LIMIT (0x42) выполняется проверка, и I-PDU передается на верхний уровень независимо от исхода. В случае ошибки результат устанавливается в SECOC_VERIFICATIONFAILURE_OVERWRITTEN.
  • Пропуск и пересылка (Skip): при SECOC_OVERRIDE_SKIP_UNTIL_LIMIT (0x41) и SECOC_OVERRIDE_SKIP_UNTIL_NOTICE (0x43) верификация опускается, I-PDU пересылается, и результатом является SECOC_NO_VERIFICATION. Если сконфигурирован сбор PDU (SecOCRxSecuredPduCollection), SecOC обрабатывает SecOCRxAuthenticPdu напрямую, не дожидаясь SecOCRxCryptographicPdu.

Примечание: это указание по использованию основано на положениях спецификации [SWS_SecOC_00991] в AUTOSAR Release R20-11.

This function performs the processing of the Sec OC module's authentication and verification processing for the Rx path. Hereby is the short name of the Sec OCMain Function Rx configuration container in the ECU configuration.
