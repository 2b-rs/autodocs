Роль BswM: арбитр режимов базового программного обеспечения

В электронном блоке управления запросы режимов сходятся в BSW Mode Manager (BswM), и он преобразует их в действия. Он выполняет арбитраж на основе входящих индикаций режимов [SWS_BswM_00035]. При этом спецификация различает два типа входных данных (SWS BswM с. 26):

  • Запросы режимов обычно поступают от прикладных SW-C, а иногда и от BSW-модулей, таких как DCM.
  • Индикации режимов всегда поступают от BSW-модулей, например, от шинно-ориентированных State Manager или EcuM.

В компонентной модели BswM является сервисным компонентом, обслуживающим только Mode Requests собственного электронного блока управления (SWS BswM с. 48).

BswM оказывает воздействие через действия. В принципе он может вызывать любую функцию AUTOSAR-BSW (SWS BswM с. 92). В качестве опциональных интерфейсов спецификация называет, среди прочего, Com_IpduGroupStart, Com_IpduGroupStop и Com_EnableReceptionDM [SWS_BswM_00008]. Кроме того, BswM может выполнять пользовательские callout [SWS_BswM_00270]. Их параметры определяются во время конфигурации в контейнере BswMUserCallout [SWS_BswM_00054]. Обязательных интерфейсов к другим модулям BswM не имеет [SWS_BswM_00007].

Контекстная диаграмма: API оповещения BSW-модулей и порты SW-C сходятся в BswM; на основе правил он воздействует через действия на Com, PduR, EthIf, EcuM, J1939Rm и callout. Источники: SWS BswM с. 87, [SWS_BswM_00008], [SWS_BswM_00201], [SWS_BswM_00202], Guide Modemanagement с. 45, Guide Modemanagement с. 61

Входы: индикации, запросы и события

Для BSW-модулей BswM предоставляет C-API для каждого источника. Внутри он отображает каждый вызов на Mode Request Port (Guide Modemanagement с. 18). Для этого таблица сопоставления связывает каждый параметр API с конфигурационной ссылкой (SWS BswM с. 87). Пример: BswM_CanSM_CurrentState сопоставляется с источником BswMCanSMIndication через пару Network / BswMCanSMChannelRef [SWS_BswM_00049]. Этот источник создается один раз для каждого CAN-канала (Guide Modemanagement с. 24).

API оповещения по происхождению:

  • Bus State Manager: CanSM, LinSM, FrSM и EthSM сообщают о своем состоянии ([SWS_BswM_00049], [SWS_BswM_00052], [SWS_BswM_00051], [SWS_BswM_00050]). LinSM также сообщает об активной таблице расписания [SWS_BswM_00058], а LinTp запрашивает режим LIN-TP [SWS_BswM_00156].
  • ComM: сообщает о режимах каналов [SWS_BswM_00047] и режимах PNC [SWS_BswM_00148] и сигнализирует через BswM_ComM_InitiateReset о Shutdown [SWS_BswM_00217].
  • Управление сетью: Nm и J1939Nm сообщают об изменении состояния ([SWS_BswM_91002], [SWS_BswM_00194]). Nm дополнительно сигнализирует о CarWakeUp [SWS_BswM_00235].
  • Память и диагностика: сообщения поступают от NvM ([SWS_BswM_00104], [SWS_BswM_00152]), DCM ([SWS_BswM_00048], [SWS_BswM_00158]) и J1939Dcm [SWS_BswM_00165].
  • Service Discovery: сообщает через три функции обратного вызова ([SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]).
  • EthIf и WdgM: EthIf сообщает о состояниях линков групп портов коммутатора [SWS_BswM_91001]. WdgM запрашивает сброс раздела [SWS_BswM_00157].

Если BSW-модуль не имеет собственного интерфейса запросов, он использует общий вызов BswM_RequestMode с типами BswM_UserType и BswM_ModeType ([SWS_BswM_00046], [SWS_BswM_00216], [SWS_BswM_00214]). SW-C обращаются к BswM через три типа портов:

  • modeRequestPort: Required Port для запросов режимов [SWS_BswM_00201].
  • modeNotificationPort: Required Port, через который BswM получает отслеживаемые изменения режимов [SWS_BswM_00200].
  • modeSwitchPort: Provided Port, через который BswM сам переключает режимы [SWS_BswM_00202].

События, такие как BswM_ComM_InitiateReset, конфигурируются как BswMEventRequestPort (SWS BswM с. 102). Арбитраж учитывает как возникновение события, так и его сброс (SWS BswM с. 26).

Связь с релизом R20-11: согласно истории изменений (SWS BswM с. 2), R20-11 принес следующие изменения:

  • Повторное внедрение BswM_EcuM_CurrentState [SWS_BswM_91003] и BswM_EcuM_RequestedState [SWS_BswM_91004].
  • Поддержка групп портов коммутатора Ethernet.
  • Новое действие BswMEthIfStartAllPorts [SWS_BswM_00286].
  • Отказ от Pretended Networking.

Два последующих изменения пока не затрагивают R20-11: BswM_WdgM_RequestPartitionReset [SWS_BswM_00157] был помечен как устаревший только в R21-11, а SoAd-Mode-Request был добавлен только в R21-11 (SWS BswM с. 2).

Правила, списки действий и момент вычисления

Поведение BswM настраивается с помощью правил и списков действий (Guide Modemanagement с. 32):

  • Правило представляет собой логическое выражение над текущими значениями Mode Request Ports.
  • В зависимости от результата BswM выполняет список действий True или False.
  • Список действий содержит атомарные действия, вложенные списки действий или ссылки на другие правила.

Действия разрешено вызывать только в контексте списка действий [SWS_BswM_00147].

Когда вычисляется правило, определяет параметр BswMRequestProcessing для каждого порта:

  • IMMEDIATE: все правила, ссылающиеся на данный порт, вычисляются немедленно (Guide Modemanagement с. 32). Для запросов от SW-C RTE должна запускать Runnable арбитража через DataReceiveEvent (SWS BswM с. 48).
  • BSWM_DEFERRED: правила вычисляются в BswM_MainFunction [SWS_BswM_00053] [SWS_BswM_00075].

Для таймеров действуют особые правила. BswMTimer независимо от своей конфигурации всегда обрабатывается как DEFERRED и проходит арбитраж в Main Function [SWS_BswM_00220]. В версии R23-11 управлять им можно только через действие BswMTimerControl, а его разрешение кратно времени цикла Main Function (SWS BswM с. 37).

Начальные значения влияют на то, какие правила вообще подвергаются арбитражу. При отсутствии начального значения (BswMModeInitValue) условие режима считается неопределенным до первого обновления. Правила с неопределенными условиями не арбитрируются (SWS BswM с. 30). Это уточнение взято из версии R23-11. Предположительно, по смыслу оно применимо уже к R20-11; однако соответствующее требование R20-11 здесь отсутствует.

Диаграмма деятельности: сообщение проверяется, сохраняется и, в зависимости от типа обработки, вычисляется немедленно или в Main Function; после этого следует список действий True или False. Источники: [SWS_BswM_00080], [SWS_BswM_00095], [SWS_BswM_00075], [SWS_BswM_00147], [SWS_BswM_00238], Guide Modemanagement с. 32, SWS BswM с. 30

Жизненный цикл и запуск под управлением EcuM

BswM_Init [SWS_BswM_00002] инициализирует все глобальные переменные модуля. После этого BswM может выполнять арбитраж запросов режимов. До вызова должны быть инициализированы только OS и SchM (SWS BswM с. 69). Переданный указатель указывает на post-build данные в BswM_ConfigType [SWS_BswM_00213]. BswM_Init является «Conditionally Reentrant», так как BswM может быть инстанциирован в нескольких разделах (SWS BswM с. 69). Поэтому EcuM вызывает BswM_Init в цикле для каждого экземпляра BswM ядра (SWS EcuM с. 83).

В последовательности StartPostOS EcuM сначала запускает планировщик BSW. Затем он инициализирует BswM и после этого завершает инициализацию SchM (SWS EcuM с. 42). С этого момента BswM управляет дальнейшим запуском: он обеспечивает выполнение подпрограмм инициализации остальных BSW-модулей и запуск RTE (Guide Modemanagement с. 36). В примере руководства это происходит следующим образом:

  1. Правило DEFERRED запускает NvM_ReadAll.
  2. NvM сообщает о завершении через BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. Затем последующее правило запускает RTE (NV-Daten-Leitfaden с. 20).

Диаграмма последовательности: EcuM инициализирует BswM в StartPostOS; затем правила BswM продвигают запуск через NvM_ReadAll и Rte_Start. Источники: SWS EcuM с. 42, Guide Modemanagement с. 36, NV-Daten-Leitfaden с. 20, [SWS_BswM_00002]

При завершении работы EcuM в последовательности OffPreOS вызывает BswM_Deinit [SWS_BswM_00119] для каждого экземпляра BswM ядра (SWS EcuM с. 90). После этого BswM больше не обрабатывает режимы, даже если продолжают поступать запросы или вызывается Main Function [SWS_BswM_00120]. Если раздел BswM перезапускается, RestartTask сообщает об этом через BswM_BswMPartitionRestarted [SWS_BswM_00193].

Диаграмма состояний: BswM выполняет арбитраж только между BswM_Init и BswM_Deinit; до и после этого обработка режимов не выполняется. Источники: [SWS_BswM_00002], [SWS_BswM_00119], [SWS_BswM_00120], [SWS_BswM_00076], [SWS_BswM_00078], SWS BswM с. 69

Взаимодействие с EcuM, источниками пробуждения и группами портов Ethernet

При ECU Mode Handling EcuM не имеет собственного конечного автомата (SWS EcuM с. 99). Он выполняет арбитраж запросов RUN и POST_RUN от SW-C и сообщает результат через BswM_EcuM_RequestedState [SWS_BswM_91004], поскольку только BswM принимает решение о переходах. Этот процесс представляет собой цикл:

  1. BswM устанавливает состояние с помощью EcuM_SetState.
  2. EcuM передает режим в RTE (SWS EcuM с. 99).
  3. После подтверждения от RTE EcuM сообщает о новом состоянии в BswM через BswM_EcuM_CurrentState [SWS_BswM_91003] (Guide Modemanagement с. 34).

С такой структурой можно продолжать использовать и унаследованные SW-C, написанные для EcuM с фиксированным конечным автоматом (Guide Modemanagement с. 61).

Диаграмма последовательности: EcuM сообщает результат RUN Request Protocol, BswM принимает решение и устанавливает состояние, и только после подтверждения от RTE следует BswM_EcuM_CurrentState. Источники: SWS EcuM с. 99, Guide Modemanagement с. 34, Guide Modemanagement с. 61, [SWS_BswM_91003], [SWS_BswM_91004]

Источники пробуждения проходят в EcuM через состояния NONE, PENDING, VALIDATED и EXPIRED. О каждом переходе в одно из этих состояний EcuM сообщает через BswM_EcuM_CurrentWakeup [SWS_BswM_00131] (SWS EcuM с. 64). В BswM этому соответствует источник BswMEcuMWakeupSource с начальным значением ECUM_WKSTATUS_NONE, создаваемый однократно для каждого источника пробуждения (Guide Modemanagement с. 29).

Диаграмма состояний: каждое изменение состояния источника пробуждения поступает в BswM как индикация режима. Источники: SWS EcuM с. 60, SWS EcuM с. 63, SWS EcuM с. 64, [SWS_BswM_00131]

Группы портов коммутатора Ethernet появились в R20-11. ComM сообщает о режиме PNC через BswM_ComM_CurrentPNCMode [SWS_BswM_00148]. BswM знает соответствие между PNC и группой портов и вызывает EthIf_SwitchPortGroupRequestMode с ETH_MODE_ACTIVE или ETH_MODE_DOWN (Guide Modemanagement с. 49). В обратном направлении EthIf через BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001] сообщает накопленное состояние линка тех групп портов, которые не сопоставлены ни с одним EthIfController (SWS EthIf с. 29). С помощью действия BswMEthIfStartAllPorts BswM запускает все порты через EthIf_StartAllPorts [SWS_BswM_00286].

Диаграмма последовательности: режим PNC управляет группой портов, а накопленное состояние линка возвращается в BswM. Источники: Guide Modemanagement с. 49, SWS EthIf с. 92, SWS EthIf с. 29, [SWS_BswM_00148], [SWS_BswM_91001]

Конфигурация и привязка к экземплярам Request Ports

Инструмент конфигурирования отображает параметры API на ссылаемые контейнеры ECUC (Guide Modemanagement с. 32). Два примера:

  • BswMDcmComModeRequest связывает через BswMDcmComMChannelRef аргумент Network функции BswM_Dcm_CommunicationMode_CurrentState с каналом ComM [SWS_BswM_00048].
  • В BswM_J1939DcmBroadcastStatus BswM вычисляет бит в позиции ссылаемой ComMChannelId (SWS BswM с. 70). Отобразить можно только первые 16 каналов [SWS_BswM_00165].

В J1939 BswM переключает в зависимости от состояния J1939Nm [SWS_BswM_00194] три вещи: группы COM-I-PDU, группы путей маршрутизации PduR и обработку запросов J1939Rm (Guide Modemanagement с. 45).

О типах данных и вспомогательных интерфейсах:

  • BswM_ModeType и BswM_UserType являются производными от uint16 ([SWS_BswM_00214], [SWS_BswM_00216]).
  • Импортированные типы соседних модулей приведены в едином списке [SWS_BswM_00001].
  • BswM_GetVersionInfo возвращает информацию о версии [SWS_BswM_00003].
  • Функция Main Function доступна через SchM_BswM.h [SWS_BswM_00053].

Поведение при ошибке

Если BswMDevErrorDetect активен, API оповещения проверяют две вещи:

  • Инициализация: если BswM не инициализирован, оповещение игнорируется и в DET отправляется BSWM_E_UNINIT. Примерами являются CanSM [SWS_BswM_00080], EthSM [SWS_BswM_00081], расписание LinSM [SWS_BswM_00086], PNC [SWS_BswM_00149] и задания NvM [SWS_BswM_00153].
  • Диапазон значений: значения вне допустимого диапазона также отбрасываются и передаются с BSWM_E_REQ_MODE_OUT_OF_RANGE, например в [SWS_BswM_00095], [SWS_BswM_00150], [SWS_BswM_00133] и [SWS_BswM_00154].

Функция Main Function ведет себя иначе: если она вызывается до инициализации, она немедленно возвращает управление и не сообщает об ошибке [SWS_BswM_00076].

К кодам ошибок разработки относятся, среди прочего, BSWM_E_UNINIT (0x01), BSWM_E_NULL_POINTER, BSWM_E_REQ_USER_OUT_OF_RANGE, BSWM_E_REQ_MODE_OUT_OF_RANGE и BSWM_E_PARAM_CONFIG [SWS_BswM_00230]. Если действие возвращает E_NOT_OK, BswM сообщает об ошибке времени выполнения BSWM_E_ACTION_FAILED. Ее значение находится в диапазоне от 0x80 до 0xFF и конфигурируется в BswMReportFailRuntimeErrorId [SWS_BswM_00238].

Системные ошибки поступают в BswM как обычные индикации режима. При Bus-Off CanSM отправляет сообщения в следующем порядке (SWS CanSM с. 70):

  1. CANSM_BSWM_BUS_OFF в BswM,
  2. COMM_SILENT_COMMUNICATION в ComM,
  3. событие PRE_FAILED в DEM.

Если восстановление прошло успешно, следует CANSM_BSWM_FULL_COMMUNICATION (SWS CanSM с. 65). Реакция системы на это определяется исключительно правилами через BswMCanSMIndication [SWS_BswM_00049]. Другими путями обработки ошибок являются сброс раздела, запрошенный WdgM [SWS_BswM_00157], и оповещение о перезапуске раздела [SWS_BswM_00193].

Диаграмма последовательности: при Bus-Off CanSM информирует BswM раньше ComM и DEM; после восстановления CanSM снова сообщает о полной коммуникации. Источники: SWS CanSM с. 70, SWS CanSM с. 65, Fehlerbeschreibung с. 19, [SWS_BswM_00049]

BSW Mode Manager (BswM)

Арбитражирует запросы режима и выполняет списки действий для управления переходами состояний системы.

Возможности — Обзор

  • void BswM_BswMPartitionRestarted (void); Function called by Restart Task if the partition containing the Bsw M has been restarted.
  • void BswM_CanSM_CurrentState (NetworkHandleType Network, Can SM_Bsw MCurrentStateType Current State); Function called by Can SM to indicate its current state.
  • void BswM_ComM_CurrentMode (NetworkHandleType Network, ComM_ModeType RequestedMode); Function called by Com M to indicate the current communication mode of a Com M channel.
  • void BswM_ComM_CurrentPNCMode (PNCHandleType PNC, ComM_PncModeType Current PncMode); Function is called by Com M to indicate the current mode of the PNC.
  • void BswM_ComM_InitiateReset (void); Function is called by Com M to signal a shutdown.
  • void BswM_Dcm_ApplicationUpdated (void); This function is called by the DCM in order to report an updated application.

Программные сущности, взаимодействующие с BswM в качестве вызывающей стороны или пользователя режимов, передают значения этого типа в интерфейсы модуля, чтобы обозначить источник запроса режима. Объявление BswM_UserType предоставляется через заголовочный файл BswM.h.

Обработка ошибок и параллелизм

Спецификация в [SWS_BswM_00216] не определяет для BswM_UserType собственных кодов ошибок, сообщений DET или DEM, а также специфических требований к реентерабельности или синхронизации. Поскольку речь идет о простом определении типа, условия относительно контекста вызова и параллелизма применяются к соответствующим функциям BswM, принимающим этот тип в качестве параметра. В системе конкретные числовые значения, вероятно, являются сконфигурированными ID пользователей (интерпретация: сопоставление сконфигурированных идентификаторов).
