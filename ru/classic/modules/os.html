Роль Classic-OS и его соседи в стеке BSW

Модуль os — это ядро реального времени Classic Platform. Он управляет Counter, Schedule Tables, OS-Applications, ядрами и спинлоками и предоставляет свои сервисы через Os.h, например StopScheduleTable [SWS_Os_00006] или GetSpinlock [SWS_Os_00686]. Таймеры, которые OS использует напрямую и которые не управляются драйвером GPT, оно инициализирует и конфигурирует самостоятельно (SWS OS с. 39). IOC также является частью операционной системы. Она образует третий вид коммуникации наряду с внутри-RTE коммуникацией и коммуникацией между ECU (SWS OS с. 119).

Другие модули BSW могут использовать OS только с ограничениями. Общая спецификация BSW определяет в таблице, какие группы модулей могут вызывать какие сервисы OS: RTE/BSW-Scheduler, BswM, EcuM, MCAL, StbM и остальные модули (SWS BSW General с. 48).

  • EcuM запускает ядра с помощью StartCore [SWS_Os_00676] и останавливает их с помощью ShutdownAllCores [SWS_Os_00713] (SWS EcuM с. 82).
  • StbM использует сервисы синхронизации для Schedule Tables (SWS StbM с. 152).
  • Complex Drivers должны ограничиваться GetCounterValue и GetElapsedValue (CDD-Leitfaden с. 21).

Контекстная диаграмма: EcuM, StbM, RTE, Complex Drivers и OS-Applications используют OS каждый через свою собственную, четко разграниченную группу сервисов. Источники: SWS BSW General с. 48, SWS EcuM с. 82, SWS StbM с. 152, SWS OS с. 122, [SWS_Os_00097]

Counter и Schedule Tables: от тика до Expiry Point

Для Counter существует три сервиса:

  • GetCounterValue [SWS_Os_00383] возвращает текущий тик Counter.
  • GetElapsedValue [SWS_Os_00392] возвращает разность относительно ранее прочитанного значения. Аппаратные таймеры при этом корректируются так, чтобы наименьшее значение было равно нулю, а последующие чтения возрастали вплоть до переполнения (SWS OS с. 39).
  • IncrementCounter [SWS_Os_00399] инкрементирует только программные Counter. Для аппаратных Counter он возвращает E_OS_ID. Если инициированное при этом действие аларма завершается сбоем, он вызывает Error-Hooks, но сам возвращает E_OK (SWS OS с. 190).

Если сконфигурирован OsSecondsPerTick, OS дополнительно предоставляет сервисный интерфейс OsService_{Counter}. Он работает со значениями типа TimeInMicrosecondsType [SWS_Os_00560] [SWS_Os_00794].

За запуск и останов Schedule Table отвечает приложение (SWS OS с. 46). Существует два варианта запуска:

  • StartScheduleTableAbs [SWS_Os_00358] обрабатывает Initial Expiry Point, как только Counter достигает значения Start + InitialOffset.
  • StartScheduleTableRel [SWS_Os_00347] выполняет относительный расчет: Now + Offset + InitialOffset. В статусе EXTENDED он отклоняет смещение, равное 0 или превышающее OsCounterMaxAllowedValue − InitialOffset, возвращая E_OS_VALUE. Для неявно синхронизированных таблиц он возвращает E_OS_ID (SWS OS с. 179).

Оба варианта возвращают E_OS_STATE, если таблица уже запущена [SWS_Os_00358].

Другие сервисы управления:

  • StopScheduleTable [SWS_Os_00006] немедленно прерывает обработку. Последующий перезапуск снова начинается с начала таблицы (SWS OS с. 46).
  • NextScheduleTable [SWS_Os_00191] переключается на следующую таблицу после завершения текущей таблицы. До этого момента следующая таблица сообщает SCHEDULETABLE_NEXT. Если целевую таблицу приводит в действие другой Counter, сервис возвращает E_OS_ID (SWS OS с. 184).
  • GetScheduleTableStatus [SWS_Os_00227] возвращает состояние как ScheduleTableStatusType [SWS_Os_00784] через ссылку [SWS_Os_00785] (SWS OS с. 189).

Диаграмма состояний: жизненный цикл Schedule Table со всеми пятью значениями ScheduleTableStatusType, включая состояния для явной синхронизации. Источники: SWS OS с. 43, SWS OS с. 49, [SWS_Os_00784]

Явная синхронизация с глобальной базой времени

Существует два типа синхронизации:

  • Неявная: счетчик синхронизации управляет таблицей напрямую. Встречаются только состояния STOPPED, NEXT и RUNNING_AND_SYNCHRONOUS (SWS OS с. 48).
  • Явная (OsScheduleTblSyncStrategy = EXPLICIT): таблицу приводит в действие другой OS-Counter. StartScheduleTableSynchron [SWS_Os_00201] запускает ее только тогда, когда доступно значение синхронизации. Initial Expiry Point следует затем через (Duration − Value) + InitialOffset тиков приводящего Counter (SWS OS с. 49). Таблицы без стратегии EXPLICIT сервис отклоняет со значением E_OS_ID (SWS OS с. 185).

SyncScheduleTable [SWS_Os_00199] передает текущее значение счетчика синхронизации. Поскольку длительность таблицы соответствует модулю этого счетчика, OS может определить дрейф (SWS OS с. 52). Коррекция выполняется в настраиваемых Expiry Points, в пределах сконфигурированных границ для укорачивания и удлинения (SWS OS с. 57).

SetScheduletableAsync [SWS_Os_00422] завершает синхронизацию, в то время как Expiry Points продолжают обрабатываться. В более поздних релизах этот сервис пишется как SetScheduleTableAsync (SWS OS с. 188).

Типичным пользователем является StbM. В своей Main Function он запрашивает статус таблицы. SyncScheduleTable он вызывает только при состояниях WAITING, RUNNING или RUNNING_AND_SYNCHRONOUS (SWS StbM с. 220). Документы по безопасности соотносят эти сервисы с требованием безопасности «Синхронизация с глобальным временем» (Safety Concept Status Report с. 49, Functional Safety Measures с. 66).

Диаграмма последовательности: StbM синхронизирует Schedule Table циклически и только тогда, когда это позволяет ее статус. Источники: SWS StbM с. 220, [SWS_Os_00227], [SWS_Os_00199]

OS-Applications: назначение, права доступа и Trusted Functions

OS-Application объединяет Trusted Functions, Tasks, ISR, алармы, Schedule Tables, Counter и хуки в конфигурируемую сущность. Она бывает либо trusted, либо non-trusted (SWS OS с. 61). Для идентификации существует два сервиса:

  • GetApplicationID [SWS_Os_00016] возвращает сконфигурированную OS-Application вызывающего объекта.
  • GetCurrentApplicationID [SWS_Os_00797] возвращает OS-Application, в которой вызывающий объект выполняется в данный момент. За пределами CallTrustedFunction оба значения совпадают. При вызове из ISR категории 1 значение не определено [SWS_Os_00798]. Если ни одна OS-Application не выполняется, оно равно INVALID_OSAPPLICATION [SWS_Os_00799].

Идентификаторы типа ApplicationType [SWS_Os_00772] начинаются с нуля и не имеют пропусков [SWS_Os_00826].

CheckObjectOwnership [SWS_Os_00017] определяет, какой OS-Application принадлежит объект. CheckObjectAccess [SWS_Os_00256] проверяет, разрешено ли OS-Application использовать ID задачи (Task), ресурса (Resource), Counter, аларма или Schedule Table. При недействительных аргументах он возвращает NO_ACCESS (SWS OS с. 177). Если вызывающий объект передает системному сервису ID объекта без сконфигурированного права доступа, сервис завершается с E_OS_ACCESS. Сами сервисы проверки исключены из этого правила (SWS OS с. 73).

Права доступа к памяти запрашивают CheckTaskMemoryAccess [SWS_Os_00513] и CheckISRMemoryAccess [SWS_Os_00512]. Право считается действительным только тогда, когда оно существует для всей запрошенной области (SWS OS с. 174). Результат типа AccessType [SWS_Os_00777] вычисляется с помощью таких макросов, как OSMEMORY_IS_WRITEABLE (SWS OS с. 160). Даже trusted OS-Applications могут работать с ограничением на запись [SWS_Os_00795].

CallTrustedFunction [SWS_Os_00097] вызывает функцию, адресуемую через TrustedFunctionIndexType [SWS_Os_00775]. Функция выполняется с настройками защиты предоставляющей OS-Application. Аргументы передаются в виде структуры через TrustedFunctionParameterRefType [SWS_Os_00776] (SWS OS с. 172). Если индекс не сконфигурирован, OS вызывает ErrorHook с E_OS_SERVICEID (SWS OS с. 85). В R20-11 сервис является синхронным или асинхронным в зависимости от того, как ведет себя вызываемая функция [SWS_Os_00097]. BSW Distribution Guide использует его для маршрутизации вызовов между BSW-модулями в различных разделах (BSW Distribution Guide с. 66).

Диаграмма последовательности: вызов Trusted Function проходит через заглушку и проверку OS вплоть до выполнения в предоставляющей OS-Application. Источники: SWS OS с. 185, SWS OS с. 396, [SWS_Os_00097]

Доступ к периферии и источники прерываний под действием Service Protection

Для доступа к адресам периферии существует три семейства сервисов. Все они адресуют область типа AreaIdType [SWS_Os_91000]:

  • ReadPeripheral8/16/32 [SWS_Os_91013] [SWS_Os_91015] [SWS_Os_91014]
  • WritePeripheral8/16/32 [SWS_Os_91010] [SWS_Os_91012] [SWS_Os_91011]
  • ModifyPeripheral8/16/32 [SWS_Os_91016] [SWS_Os_91018] [SWS_Os_91017]. Сервисы Modify вычисляют *Address = ((*Address & Clearmask) | Setmask) (SWS OS с. 175).

В статусе EXTENDED эти сервисы сообщают E_OS_ID, E_OS_VALUE (адрес вне области) или E_OS_CALLEVEL. E_OS_ACCESS возвращается, если вызывающая Task или ISR не имеет доступа (SWS OS с. 195).

Для каждой ISR категории 2 OS предоставляет три сервиса [SWS_Os_00808]: DisableInterruptSource [SWS_Os_91019], EnableInterruptSource [SWS_Os_91020] и ClearPendingInterrupt [SWS_Os_91021]. При этом действуют следующие правила:

  • Тот, кто повторно блокирует уже заблокированный источник или повторно разрешает уже разрешенный, в статусе EXTENDED получает E_OS_NOFUNC [SWS_Os_00809].
  • Обнаруженные ошибки возвращаются и передаются в ErrorHook [SWS_Os_00810].
  • ClearPendingInterrupt сбрасывает только флаг Pending в контроллере прерываний [SWS_Os_00813] [SWS_Os_00814].
  • Если OS-Application вызывает сервисы для ISR, которая ей не принадлежит, она получает E_OS_ACCESS (SWS OS с. 177).

Внимание, противоречие: [SWS_Os_00811] требует при разблокировке сбрасывать флаг Pending. Определение API [SWS_Os_91020] делает именно это выбираемым через параметр ClearPending.

Многоядерный режим: запуск ядер, спинлоки, IOC и координированное отключение

StartCore [SWS_Os_00676] запускает дополнительное ядро под управлением AUTOSAR OS. После StartOS вызовы возвращают E_OS_ACCESS. На каждом запущенном таким образом ядре затем должен быть вызван StartOS (SWS OS с. 166). Эти детальные правила взяты из более поздних версий спецификации. Интерпретация: вероятно, они применимы и к R20-11, поскольку определения R20-11 называют те же возвращаемые значения [SWS_Os_00676].

Другие сервисы ядер:

  • StartNonAutosarCore [SWS_Os_00682] запускает ядра вне AUTOSAR OS.
  • GetCoreID [SWS_Os_00674] возвращает логический ID типа CoreIdType [SWS_Os_00790]. Диапазон значений начинается с нуля и не имеет пропусков [SWS_Os_00825].
  • GetNumberOfActivatedCores [SWS_Os_00672] в R20-11 подсчитывает ядра, активированные через StartCore. Более поздние релизы говорят вместо этого о ядрах, на которых выполняется AUTOSAR OS (SWS OS с. 196).

Спинлоки защищают общие данные через границы ядер:

  • GetSpinlock [SWS_Os_00686] выполняет активное ожидание без вытеснения вызывающего объекта (SWS OS с. 199).
  • TryToGetSpinlock [SWS_Os_00703] немедленно возвращается, если Task на другом ядре удерживает блокировку, и сообщает результат через TryToGetSpinlockType [SWS_Os_00792] (SWS OS с. 203).
  • ReleaseSpinlock [SWS_Os_00695] освобождает блокировку.
  • Значение 0 для SpinlockIdType обозначает INVALID_SPINLOCK [SWS_Os_00791].

В статусе EXTENDED OS распознает два вида взаимной блокировки: вытеснение на том же ядре (E_OS_INTERFERENCE_DEADLOCK) и некорректную вложенность (E_OS_NESTING_DEADLOCK). Через OsSpinlockLockMethod OS может автоматически защитить блокировку от вытеснения (SWS OS с. 101).

ActivateTask через границы ядер ведет себя синхронно. Асинхронные варианты ActivateTaskAsyn [SWS_Os_91022] [SWS_Os_00816] и SetEventAsyn [SWS_Os_91023] [SWS_Os_00817] сообщают об ошибках только через глобальный ErrorHook (SWS OS с. 103). Они доступны только в системах с OS-Applications [SWS_Os_00818] [SWS_Os_00819].

IOC передает данные с помощью сгенерированных функций (SWS OS с. 218):

  • IocWrite [SWS_Os_91003] и IocRead [SWS_Os_91005] для небуферизованной семантики «data».
  • IocSend [SWS_Os_00718] и IocReceive [SWS_Os_00738] для буферизованной семантики «event».
  • Групповые варианты [SWS_Os_00728] [SWS_Os_91004] [SWS_Os_00746] [SWS_Os_91006], IocEmptyQueue [SWS_Os_00754] и опциональный callback получателя [SWS_Os_00757].

В статусе DRAFT версия R20-11 также содержит IocInit [SWS_Os_91026] [SWS_Os_00835], который вызывает StartOS в режиме по умолчанию [SWS_Os_00830]. Также в статусе DRAFT находятся раздельные режимы генератора для кода OS и IOC [SWS_Os_00831] [SWS_Os_00833] [SWS_Os_00834].

ControlIdle [SWS_Os_00769] определяет для каждого ядра, что происходит во время простоя. По умолчанию используется IDLE_NO_HALT [SWS_Os_00793]. Недопустимые указания ядра или режима возвращают E_OS_ID [SWS_Os_00771], допустимые — E_OK [SWS_Os_00770].

ShutdownAllCores синхронно завершает работу OS на всех ядрах и никогда не возвращает управление. Вызовы из non-trusted кода игнорируются (SWS OS с. 204). Сначала выполняются специфичные для приложений Shutdown-Hooks [SWS_Os_00541], а после синхронизации всех ядер — глобальный ShutdownHook (SWS OS с. 98).

Диаграмма последовательности: EcuM запускает все ядра перед StartOS; ShutdownAllCores распределяет завершение работы по остальным ядрам и синхронизирует их перед ShutdownHook. Источники: SWS EcuM с. 82, SWS EcuM с. 91, SWS OS с. 98, [SWS_Os_00713].

Поведение при ошибке

Многие проверки выполняются только в состоянии EXTENDED, например E_OS_ID при недействительных идентификаторах (SWS OS с. 182). В этом режиме OS также проверяет аргументы-указатели на NULL_PTR и затем возвращает E_OS_ILLEGAL_ADDRESS (SWS OS с. 38). Специфичные для OS коды ошибок, такие как E_OS_PROTECTION_MEMORY, E_OS_STACKFAULT или E_OS_CORE, определены в [SWS_Os_91025]. Если задача или ISR категории 2 вызывает ошибку, вызывается ErrorHook ее OS-Application, ErrorHook_<App> [SWS_Os_00540].

Тяжелые ошибки, такие как нарушения памяти или времени выполнения, вызывают ProtectionHook [SWS_Os_00538]. Его возвращаемое значение типа ProtectionReturnType [SWS_Os_00787] определяет реакцию. Затем OS завершает задачу или ISR, завершает OS-Application (с перезапуском или без него) либо выключает систему (SWS OS с. 187).

Диаграмма деятельности: возвращаемое значение ProtectionHook определяет реакцию OS на нарушение защиты. Источники: SWS OS с. 187, EXP ALEH с. 69, [SWS_Os_00787]

Когда OS завершает OS-Application, она прекращает выполнение ее выполняющихся, готовых и ожидающих задач и ISR. Кроме того, она блокирует ее прерывания и останавливает ее алармы и Schedule Tables (SWS OS с. 62).

TerminateApplication [SWS_Os_00258] завершает собственное OS-Application. Чужое OS-Application разрешено завершать только доверенному (trusted) вызывающему компоненту. Опция RestartType [SWS_Os_00788] в R20-11 принимает значения RESTART и NO_RESTART. Более поздние релизы содержат только OS_OSAPPLICATION_RESTART и игнорируют этот параметр (SWS OS с. 158, SWS OS с. 194).

Состояние OS-Application согласно ApplicationStateType [SWS_Os_00773] возвращает GetApplicationState [SWS_Os_00499]. Из APPLICATION_RESTARTING оно возвращается с помощью AllowAccess [SWS_Os_00501] в APPLICATION_ACCESSIBLE.

Перезапуск описан в руководстве по обработке ошибок на уровне приложений. OS активирует OSRestartTask. Он инициирует операции очистки в других разделах с помощью CallTrustedFunction (EXP ALEH с. 69, EXP ALEH с. 76).

В асинхронных службах ошибки не доходят до вызывающего компонента. Если вызывающий компонент уже завершен, вызовы Error-Hook также отменяются (SWS OS с. 203).

Диаграмма состояний: жизненный цикл OS-Application в R20-11 с фазой перезапуска и возвратом через AllowAccess. Источники: SWS OS с. 59, EXP ALEH с. 53, SWS OS с. 62, [SWS_Os_00773], [SWS_Os_00501]

Использование

С помощью системной службы CallTrustedFunction ([SWS_Os_00097]) приложение OS-Application — независимо от того, сконфигурировано ли оно как доверенное (trusted) или недоверенное (non-trusted) — может вызывать определённую Trusted Function. Объявление предоставляется через заголовочный файл Os.h.

Службе передаются два входных параметра:

  • FunctionIndex (тип TrustedFunctionIndexType): обозначает индекс вызываемой Trusted Function ([SWS_Os_00097]).
  • FunctionParams (тип TrustedFunctionParameterRefType): указатель на параметры функции. Если параметры не требуются, должен передаваться указатель NULL ([SWS_Os_00097]).

Синхронное или асинхронное поведение CallTrustedFunction напрямую зависит от вызываемой функции: если вызываемая Trusted Function синхронна, вызов службы также ведёт себя синхронно. Кроме того, вызов может инициировать перепланирование (rescheduling) в операционной системе ([SWS_Os_00097]).

Обработка ошибок

Служба возвращает значение статуса типа StatusType ([SWS_Os_00097]):

  • E_OK: вызов выполнен без ошибок.
  • E_OS_SERVICEID: для указанного FunctionIndex функция не определена.

Параллелизм и ограничения

Функция специфицирована как реentrantная ([SWS_Os_00097]). Идентификатор службы (Service-ID) данной службы: 0x02.

Это указание по использованию сгенерировано автоматически на основе спецификации AUTOSAR.
