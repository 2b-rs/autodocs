Роль Crypto Driver в криптографическом стеке

Crypto Driver располагается на уровне Microcontroller Abstraction Layer под Crypto Interface (CryIf) и Crypto Service Manager (CSM). Он предоставляет универсальный интерфейс для синхронных и асинхронных криптографических примитивов и выполняет хранение, конфигурирование и управление ключами. ЭБУ интегрирует ровно один CSM и один CryIf. Однако CryIf может обращаться к нескольким Crypto Driver SWS_CryptoDriver с. 15. Спецификация объединяет предоставляемые возможности в две службы: криптографические службы и управление ключами SWS_CryptoDriver с. 24.

Центральной единицей исполнения является Crypto Driver Object. Оно представляет собой независимый криптографический модуль, например аппаратный ускоритель AES в составе HSM или программную реализацию для RSA. Каждое Crypto Driver Object является конечной точкой криптографического канала SWS_CryptoDriver с. 15. Объект всегда обрабатывает только одно задание. Драйвер с n объектами может обрабатывать параллельно n заданий, при этом задания в очереди не считаются находящимися «в обработке» (фрагмент документа версии R25-11) SWS_CryptoDriver с. 23. Поэтому Crypto_ProcessJob и Crypto_CancelJob адресуют объект через objectId [SWS_Crypto_91003] [SWS_Crypto_00122].

Контекстная диаграмма: Crypto Driver обслуживает CryIf через Crypto Driver Objects и использует NvM, DET и SchM в качестве соседних модулей. Источники: SWS_CryptoDriver с. 15, AUTOSAR_CP_SWS_CryptoServiceManager с. 28, [SWS_Crypto_91017], [SWS_Crypto_91012]

Запуск, создание экземпляров и разделение на разделы

Crypto_Init является синхронной и нереентерабельной и инициализирует драйвер [SWS_Crypto_91000]. При этом параметр configPtr всегда должен быть нулевым указателем [SWS_Crypto_00215]. Интерпретация: конфигурация, таким образом, не выбирается во время выполнения, а, вероятно, статически привязана в драйвере. С этим согласуется то, что содержимое Crypto_ConfigType зависит от реализации [SWS_Crypto_91016]. При запуске драйвер считывает сохраненные значения ключей SWS_CryptoDriver с. 35. Если значение не удается загрузить, он переводит соответствующий ключ в состояние недействительного [SWS_Crypto_00198]. При обнаружении нулевого указателя Crypto_GetVersionInfo сообщает CRYPTO_E_PARAM_POINTER в DET [SWS_Crypto_91001] SWS_CryptoDriver с. 56.

Если в одном ЭБУ присутствует несколько экземпляров драйвера, имена файлов, имена API и опубликованные параметры должны различаться по схеме Crypto_<vi>_<ai> SWS_CryptoDriver с. 23. Этот префикс имеют и функции обратного вызова NvM, например Crypto_<vi>_<ai>_NvBlock_Init_<NvBlock> [SWS_Crypto_91023]. Если драйверу для внутренних нужд требуются случайные числа, например для Crypto_KeyExchangeCalcPubVal, для этого необходимо сконфигурировать Crypto Driver Object 0 [SWS_Crypto_00224]. Объекты без собственного стандартного генератора случайных чисел получают свои случайные числа от объекта 0 [SWS_Crypto_00225]. При этом они вызывают только генераторы собственного драйвера [SWS_Crypto_00226].

При разделении на разделы драйвер работает в каждом разделе как независимый экземпляр. Вызов API влияет только на тот раздел, в котором он выполняется [SWS_Crypto_CONSTR_00001]. Разделы Crypto Driver Object должны являться подмножеством разделов драйвера [SWS_Crypto_CONSTR_00002]. Объект для HSM должен назначаться не более чем одному разделу [SWS_Crypto_CONSTR_00003]. Руководство BSW-Distribution-Guide обосновывает такое разделение распределением нагрузки по криптографическим экземплярам BSWDistributionGuide с. 59.

Обработка заданий через Crypto_ProcessJob

Все криптографические службы выполняются через реентерабельную функцию Crypto_ProcessJob(objectId, job). Выполняется ли задание синхронно или асинхронно, зависит от его конфигурации [SWS_Crypto_91003]. Эта информация содержится в Crypto_JobType SWS_CryptoDriver с. 26. Типы заданий драйвер импортирует из Crypto_GeneralTypes.h модуля CSM [SWS_Crypto_00042].

В асинхронном случае интерфейсная функция передает примитиву только необходимую информацию. Вычисление может инициировать функция Main Function. По завершении драйвер уведомляет CryIf через CRYIF_CallbackNotification и передает задание и результат SWS_CryptoDriver с. 27. Crypto_MainFunction вызывается циклически, если настроена асинхронная обработка и существуют очереди заданий [SWS_Crypto_91012].

Диаграмма последовательности: асинхронное задание немедленно возвращает управление, вычисляется в функции Main Function и завершается через функцию обратного вызова. Передача от CryIf к CSM помечена как интерпретация. Источники: [SWS_Crypto_91003], [SWS_Crypto_91012], SWS_CryptoDriver с. 27

Задание содержит поле флагов с режимами работы START, UPDATE и FINISH. Флаги можно комбинировать, и тогда они всегда выполняются в этом порядке. START прерывает все предыдущие запросы того же задания SWS_CryptoDriver с. 25. Вызов Single-Call соответствует комбинации START|UPDATE|FINISH SWS_CryptoInterface с. 22. Для заданий управления ключами спецификация рекомендует CRYPTO_OPERATIONMODE_SINGLECALL SWS_CryptoDriver с. 66.

Диаграмма деятельности: флаги START, UPDATE и FINISH обрабатываются в фиксированном порядке. Источники: SWS_CryptoDriver с. 25, SWS_CryptoInterface с. 22

Если установлен флаг job->jobRedirectionInfoRef и активен соответствующий бит конфигурации, драйвер использует элементы ключа вместо буферов в качестве входных или выходных данных [SWS_Crypto_00203] [SWS_Crypto_00204]. Для этого действуют минимальные права: например, входному элементу требуется CRYPTO_RA_INTERNAL_COPY «или ниже» [SWS_Crypto_00221]. На стороне CSM этому соответствует контейнер конфигурации CsmInOutRedirections AUTOSAR_CP_SWS_CryptoServiceManager с. 167.

Ключи, элементы ключей и права доступа

Ключ состоит из одного или нескольких элементов ключа. Примерами являются ключевой материал, вектор инициализации или состояние seed. Каждый элемент содержит права на чтение и запись в виде значений перечисления, числовые значения которых образуют иерархию SWS_CryptoDriver с. 28. При прямом доступе на чтение и запись эти права должны соблюдаться [SWS_Crypto_00219]. Интерпретация: требования выполнять «эту операцию» только при CRYPTO_RA_ALLOWED/CRYPTO_RA_ENCRYPTED [SWS_Crypto_00222] или CRYPTO_WA_ALLOWED/CRYPTO_WA_ENCRYPTED [SWS_Crypto_00223], вероятно, относятся к Crypto_KeyElementGet [SWS_Crypto_91006] и Crypto_KeyElementSet [SWS_Crypto_91004]. Задания же используют назначенные им элементы без проверки прав. Исключением является Redirection [SWS_Crypto_00221].

Crypto_KeyElementIdsGet перечисляет существующие идентификаторы элементов ключа. При вызове keyElementIdsLengthPtr содержит размер буфера, а по завершении — фактическое количество [SWS_Crypto_00160] SWS_CryptoDriver с. 78. Для копирования предусмотрены две функции:

  • Crypto_KeyCopy копирует ключ со всеми элементами в пределах одного и того же драйвера [SWS_Crypto_00155].
  • Crypto_KeyElementCopy копирует отдельный элемент [SWS_Crypto_00148].

Исходный элемент должен иметь как минимум те же права, что и целевой. Исходному ключу требуется как минимум CRYPTO_RA_INTERNAL_COPY [SWS_Crypto_00220]. Если элементы отображаются непосредственно на флеш-память, синхронный вызов может длиться значительно дольше SWS_CryptoDriver с. 77.

Crypto_KeyElementCopyPartial копирует фрагмент со смещением источника и назначения [SWS_Crypto_91015]. Функция возвращает CRYPTO_E_KEY_SIZE_MISMATCH, если исходный элемент короче суммы смещения и длины [SWS_Crypto_00207] или если максимального буфера назначения недостаточно [SWS_Crypto_00208]. В противном случае она копирует [SWS_Crypto_00209] и при необходимости корректирует длину назначения [SWS_Crypto_00210] [SWS_Crypto_00211].

Диаграмма деятельности: проверки длины и корректировка длины при частичном копировании. Обе проверки размера приводят к одному и тому же возвращаемому значению, поэтому их порядок не имеет значения. Источники: [SWS_Crypto_00207], [SWS_Crypto_00208], [SWS_Crypto_00209], [SWS_Crypto_00210], [SWS_Crypto_00211]

Для генерации и деривации ключевого материала предусмотрены следующие функции:

  • Crypto_KeyGenerate генерирует новый ключевой материал [SWS_Crypto_91007].
  • Crypto_KeyDerive выполняет деривацию ключа в targetCryptoKeyId [SWS_Crypto_91008].
  • Crypto_RandomSeed передает seed [SWS_Crypto_91013].
  • Crypto_KeyExchangeCalcPubVal вычисляет собственное открытое значение для обмена ключами [SWS_Crypto_91009].
  • Crypto_KeyExchangeCalcSecret сохраняет общий секрет как элемент того же ключа [SWS_Crypto_91010] SWS_CryptoDriver с. 84.

Состояние ключа и персистентность в NvM

Каждый ключ является либо действительным, либо недействительным:

  • Crypto_KeySetValid устанавливает его как действительный [SWS_Crypto_91014].
  • Crypto_KeySetInvalid устанавливает его как недействительный [SWS_Crypto_91020].
  • Crypto_KeyGetStatus возвращает текущее состояние [SWS_Crypto_91019].

Функции для запроса и аннулирования состояния ключа, согласно истории изменений, были добавлены в R20-11 SWS_CryptoDriver с. 2. Если ключ недействителен, такие службы, как Crypto_KeyGenerate или Crypto_KeyExchangeCalcSecret, возвращают значение CRYPTO_E_KEY_NOT_VALID SWS_CryptoDriver с. 80 SWS_CryptoDriver с. 84.

Диаграмма состояний: переходы между действительным и недействительным состояниями, а также аннулирование при запуске. Начальное состояние после успешной загрузки не определено в документации и поэтому не отображено. Источники: [SWS_Crypto_91014], [SWS_Crypto_91020], [SWS_Crypto_91019], [SWS_Crypto_00198]

Обработка элементов ключа в NvM также появилась в R20-11 SWS_CryptoDriver с. 2. Ключ ссылается не более чем на один блок NvM, а его KeyType охватывает один или несколько KeyElements AUTOSAR_SWS_CryptoDriver с. 32. Драйвер записывает элементы при валидации и считывает их при инициализации SWS_CryptoDriver с. 35. Версия R25-11 уточняет, что сохранение инициирует только KEYSETVALID, но не Crypto_KeyElementSet. Таким образом, драйвер может совместно проверять взаимозависимые элементы и сохранять их за одну операцию записи SWS_CryptoDriver с. 37.

Для обмена данными с NvM драйвер предоставляет четыре функции обратного вызова:

  • Init инициализирует блок [SWS_Crypto_91023].
  • ReadFrom копирует данные из зеркала NvM во внутренний буфер [SWS_Crypto_91024].
  • WriteTo заполняет зеркало непосредственно перед записью [SWS_Crypto_91025].
  • Callback сообщает о завершении асинхронного запроса отдельного блока [SWS_Crypto_91026].

В качестве опции драйвер использует NvM_SetRamBlockStatus и NvM_WriteBlock [SWS_Crypto_91017].

Диаграмма последовательности: персистентность ключей при запуске и при валидации. Какая функция NvM инициирует операцию записи, помечено как интерпретация. Источники: [SWS_Crypto_91024], [SWS_Crypto_91025], [SWS_Crypto_91026], [SWS_Crypto_91017], SWS_CryptoDriver с. 37

Отмена выполняемых заданий

Crypto_CancelJob(objectId, job) является синхронной и реентерабельной, однако не для одного и того же Crypto Driver Object [SWS_Crypto_00122]. Возвращаемое значение зависит от состояния обработки:

  • Если драйвер в данный момент не обрабатывает задание, он возвращает E_OK без дальнейшей обработки [SWS_Crypto_00214].
  • Если он может отменить выполняемое задание, он удаляет его и возвращает E_OK [SWS_Crypto_00122].
  • Если он не может отменить его, например из-за аппаратных ограничений, он возвращает CRYPTO_E_JOB_CANCELED [SWS_Crypto_00183].

«В обработке» здесь означает, что объект активно занят заданием. Задание, для которого остается выполнить только FINISH, не считается находящимся в обработке SWS_CryptoDriver с. 25. На CRYPTO_E_JOB_CANCELED CSM реагирует отменой на следующем подходящем шаге и сообщает об этом через отрицательный Closing-Callback SWS_CryptoServiceManager с. 80.

Диаграмма деятельности: три возможных результата запроса на отмену. Источники: [SWS_Crypto_00122], [SWS_Crypto_00183], [SWS_Crypto_00214], SWS_CryptoServiceManager с. 80

Поведение при ошибке

Если обнаружение ошибок разработки активно, драйвер сообщает следующие коды в DET: CRYPTO_E_UNINIT (0x00), CRYPTO_E_INIT_FAILED (0x01), CRYPTO_E_PARAM_POINTER (0x02), CRYPTO_E_PARAM_HANDLE (0x04), CRYPTO_E_PARAM_VALUE (0x05), а также код для слишком малых буферов [SWS_Crypto_00040]. Через API эти коды не возвращаются SWS_CryptoDriver с. 15. Примером служит Crypto_KeySetValid: без инициализации функция сообщает CRYPTO_E_UNINIT и возвращает E_NOT_OK [SWS_Crypto_00196]. При недопустимом значении cryptoKeyId она сообщает CRYPTO_E_PARAM_HANDLE [SWS_Crypto_00197]. Тот же шаблон применяется, например, для Crypto_KeyElementCopyPartial [SWS_Crypto_00205] и для targetCryptoKeyId при Crypto_KeyDerive [SWS_Crypto_00180].

Перед каждым заданием драйвер проверяет job->cryptoKeyId и при необходимости targetCryptoKeyId [SWS_Crypto_00217]. При CRYPTO_KEYDERIVE целевая область всегда должна находиться в допустимом диапазоне [SWS_Crypto_00202]. Если буфер слишком мал, драйвер не выполняет операцию. При активном DET он сообщает CRYPTO_E_SMALL_BUFFER, без DET возвращает E_NOT_OK [SWS_Crypto_00195]. Для CRYPTO_HASH и CRYPTO_MACGENERATE вместо этого выдается результат, усеченный до старших битов [SWS_Crypto_00065]. В более новом месте документа дополнительно упоминается CRYPTO_RANDOMGENERATE. Это не подтверждается имеющимися здесь требованиями R20-11 SWS_CryptoDriver с. 49.

Результаты времени выполнения драйвер сообщает через возвращаемые значения, такие как CRYPTO_E_BUSY, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE и CRYPTO_E_KEY_NOT_VALID [SWS_Crypto_91018]. При исчерпании энтропии служба генерации случайных чисел возвращает CRYPTO_E_ENTROPY_EXHAUSTED. Crypto_ProcessJob затем дополнительно сообщает об ошибке времени выполнения CRYPTO_E_RE_ENTROPY_EXHAUSTED [SWS_Crypto_00141]. Для ошибок NvM предусмотрен CRYPTO_E_RE_NVM_ACCESS_FAILED [SWS_Crypto_00194]. Однако поврежденные блоки NvM должно обрабатывать приложение SWS_CryptoDriver с. 35.

Диаграмма деятельности: типичная цепочка проверок вызова драйвера от проверок DET до выполнения. Порядок проверок является интерпретацией. Источники: [SWS_Crypto_00196], [SWS_Crypto_00197], [SWS_Crypto_00217], [SWS_Crypto_00195], [SWS_Crypto_00065], [SWS_Crypto_91018]

Crypto Driver (Crypto)

Драйвер низкого уровня, выполняющий криптографические примитивы в аппаратных модулях безопасности (HSM) или программных библиотеках.

Crypto_KeyCopy функция

Копирует ключ со всеми его элементами в другой ключ в том же криптодрайвере. Примечание. Если фактический ключевой элемент напрямую сопоставлен с флэш-памятью, при вызове этой функции может возникнуть большая задержка (синхронная операция).

Std_ReturnType Crypto_KeyCopy (uint32 crypto KeyId, uint32 target Crypto KeyId);
Crypto_KeyDerive функция

Получает новый ключ, используя ключевые элементы в данном ключе, идентифицируемые идентификатором криптографического ключа. Данный ключ содержит ключевые элементы для пароля, соль. Производный ключ хранится в элементе key с идентификатором 1 ключа, идентифицируемого целевым идентификатором ключа Crypto. Количество итераций задается в ключевом элементе CRYPTO_KE_KEYDERIVATION_ITERATIONS.

Std_ReturnType Crypto_KeyDerive (uint32 crypto KeyId, uint32 target Crypto KeyId);

Вычисляет общедоступное значение для обмена ключами и сохраняет открытый ключ в ячейке памяти, указанной указателем общедоступного значения.

Std_ReturnType Crypto_KeyExchangeCalcPubVal (uint32 crypto KeyId, uint8* public ValuePtr, uint32* public Value LengthPtr);

Вычисляет общий секретный ключ для обмена ключами с использованием ключевого материала ключа, идентифицируемого идентификатором криптографического ключа и открытым ключом партнера. Общий секретный ключ хранится как ключевой элемент в том же ключе.
