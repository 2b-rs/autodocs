Роль: точка сбора между источниками логов и PDU Router

Модуль Dlt принимает сообщения логирования и трассировки от программных компонентов и модулей BSW и передает их в виде сообщений Dlt внешнему клиенту. Основными интерфейсами для этого являются Dlt_SendLogMessage и Dlt_SendTraceMessage [SWS_Dlt_00241] [SWS_Dlt_00243]. В начале тракта данных находится SW-C или модуль BSW, в конце — PDU Router SWS Dlt с. 26. Отправка осуществляется исключительно через PduR_DltTransmit [SWS_Dlt_00762]. Формат сообщений, команды и протокол взаимодействия с инструментом определяет спецификация протокола Log and Trace SWS Dlt с. 9.

SW-C обращаются к модулю через два порта RTE:

  • SwcMessageService_{SW-C} для регистрации и отправки [SWS_Dlt_91001],
  • ControlService_{SW-C} для управления настройками логирования [SWS_Dlt_00499].

В обратном направлении Dlt уведомляет SW-C через SessionControlCallback_{SW-C} [SWS_Dlt_00779] и вызывает инъекции через InjectCallback_{SW-C} [SWS_Dlt_00778]. Дополнительными источниками являются DET через Dlt_DetForwardErrorTrace [SWS_Dlt_00430] и RTE через сгенерированные хуки VFB-Trace [SWS_Dlt_00027]. Из нижележащих модулей Dlt использует Det_ReportError, а также службы Gpt, NvM и StbM [SWS_Dlt_00763].

Контекстная диаграмма: SW-C, RTE, DET и EcuM вызывают Dlt; Dlt использует NvM, источники времени и PduR. Источники: [SWS_Dlt_91001] [SWS_Dlt_00779] [SWS_Dlt_00027] [SWS_Dlt_00430] [SWS_Dlt_00763] [SWS_Dlt_00762]

Запуск: буферизация до Dlt_Init, конфигурация из NvM, задержка запуска

Dlt_Init является синхронной и нереентерабельной. Поскольку Dlt использует NVRAM Manager, инициализация должна происходить на очень позднем этапе запуска и только после NvM [SWS_Dlt_00239]. Согласно диаграмме последовательности, EcuM вызывает эту функцию SWS Dlt с. 159. Источники могут выполнять логирование еще до инициализации. Поэтому Dlt должен иметь возможность буферизовать данные из Dlt_SendLogMessage и Dlt_SendTraceMessage также до Dlt_Init [SWS_Dlt_00003].

Если DltGeneralNvRAMSupport равно TRUE, действует следующее:

  • Dlt_Init считывает персистентно сохраненные значения с помощью NvM_ReadBlock [SWS_Dlt_00453].
  • Dlt проверяет валидность блоков [SWS_Dlt_00449].
  • Сохраненная конфигурация используется в качестве начального значения [SWS_Dlt_00350].

Если поддержка NvRAM отключена, действует статическая конфигурация SWS Dlt с. 26. Промежуточно буферизованные данные обрабатываются в обычном порядке только после того, как модуль инициализирован и истек опциональный DltGeneralStartUpDelayTimer [SWS_Dlt_00005].

Диаграмма последовательности: данные, буферизованные до Dlt_Init, обрабатываются только после инициализации и истечения задержки запуска. Источники: [SWS_Dlt_00003] [SWS_Dlt_00453] [SWS_Dlt_00005] SWS Dlt с. 90

Сессии, Application-/Context-ID и регистрация контекста

Каждый источник сообщений идентифицируется через Dlt_SessionIDType (uint32) [SWS_Dlt_00225]:

  • Для SW-C это Port Defined Argument Value [SWS_Dlt_00022]. Значения начинаются с 0x1000 [SWS_Dlt_00023].
  • Модули BSW используют свой Modul-ID [SWS_Dlt_00023].
  • Каждый порт, подключенный к Dlt, получает уникальный SessionId, диапазон значений является непрерывным [SWS_Dlt_00332].

SW-C с множественным инстанцированием и SW-C с несколькими портами к Dlt имеют соответственно несколько сессий EXP LSA с. 159. По содержанию сообщение сопоставляется через ApplicationId и ContextId. Оба имеют размер четыре байта, 0x00000000 является подстановочным значением (wildcard) [SWS_Dlt_00226] [SWS_Dlt_00227].

С помощью Dlt_RegisterContext источник регистрирует кортеж из ApplicationId и ContextId вместе с описаниями [SWS_Dlt_00245]. Dlt запоминает, через какой порт был зарегистрирован кортеж [SWS_Dlt_00021], и ведет для каждого кортежа уровень логирования и статус трассировки SWS Dlt с. 20. Если программный модуль останавливается, он вызывает Dlt_UnregisterContext [SWS_Dlt_00769]. Затем Dlt удаляет этот кортеж и больше не уведомляет его об изменениях. Если DltGeneralRegisterContextNotification активен, Dlt дополнительно сообщает о дерегистрации через Dlt_GetLogInfo со статусом 5 SWS Dlt с. 21.

Диаграмма состояний: жизненный цикл кортежа ApplicationId/ContextId с возвращаемыми значениями API регистрации. Источники: [SWS_Dlt_00245] [SWS_Dlt_00769] SWS Dlt с. 49 SWS Dlt с. 50

От вызова отправки до PDU: фильтры, LogChannels и развязанная отправка

API отправки являются синхронными и реентерабельными [SWS_Dlt_00241] [SWS_Dlt_00243]. Помимо полезных данных они получают информационную структуру:

  • Dlt_MessageLogInfoType с argCount, logLevel, options, contextId и appId [SWS_Dlt_00236],
  • Dlt_MessageTraceInfoType, которая вместо уровня логирования содержит тип трассировки [SWS_Dlt_00237].

Еще в контексте вызывающей стороны сообщение последовательно проходит метку времени, фильтр уровня логирования/статуса трассировки, выбор канала, проверку длины, порог канала и буферизацию SWS Dlt с. 23 SWS Dlt с. 92.

Для выбора канала Dlt собирает в следующем порядке SWS Dlt с. 32:

  1. все LogChannels с точно совпадающим кортежем,
  2. все LogChannels с подходящим ApplicationId и ContextId-шаблоном,
  3. Default-LogChannel, если список после этого все еще пуст.

Назначения можно изменять во время выполнения с помощью Dlt_SetLogChannelAssignment [SWS_Dlt_00751]. В R20-11 Dlt_AssignmentOperation кодирует DLT_ASSIGN_ADD как 0x01, а DLT_ASSIGN_REMOVE — как 0x02 [SWS_Dlt_00730]. Более поздние версии присваивают DLT_ASSIGN_REMOVE вместо этого значение 0x00 SWS Dlt с. 87. Сообщение отбрасывается с DLT_E_MSG_TOO_LARGE только в том случае, если оно слишком длинное для всех назначенных каналов SWS Dlt с. 31.

Диаграмма деятельности: шаги обработки в контексте вызывающей стороны и места, в которых сообщение отбрасывается. Источники: SWS Dlt с. 23 SWS Dlt с. 32 SWS Dlt с. 31 SWS Dlt с. 32

Собственно отправка отделена от вызова API и происходит в контексте Dlt_TxFunction [SWS_Dlt_91005]. Развязка сокращает время блокировки вызывающих сторон и делает возможными формирование трафика и повторные попытки отправки. Заголовок собирается перед PduR_DltTransmit, и каждая попытка отправки увеличивает счетчик передач сообщения SWS Dlt с. 35. Метку времени Dlt запрашивает только при DltHeaderUseTimestamp = TRUE, а именно через Gpt_GetTimeElapsed [SWS_Dlt_00654] или StbM_GetCurrentTime [SWS_Dlt_00655].

Сообщение удаляется из буфера канала при наступлении одного из следующих случаев SWS Dlt с. 38:

  • PduR_DltTransmit возвращает E_NOT_OK.
  • Поступает положительное Dlt_TxConfirmation [SWS_Dlt_00273].
  • После отрицательного подтверждения превышено сконфигурированное число повторов.

Для каналов на базе TP этот процесс, вероятно, дополняют Dlt_CopyTxData [SWS_Dlt_00516] и Dlt_TpTxConfirmation [SWS_Dlt_00756]. Dlt_TriggerTransmit [SWS_Dlt_00754], по всей видимости, обслуживает PDU с триггерным управлением.

Диаграмма последовательности: прием сообщения в контексте вызывающей стороны, затем циклическая развязанная отправка с повторением. Источники: SWS Dlt с. 92 SWS Dlt с. 35 SWS Dlt с. 38 [SWS_Dlt_00273]

Типы сообщений, поля заголовка и фиксированные источники (DET, DEM, VFB-Trace)

Dlt_MessageType различает сообщения логирования, трассировки приложений, сетевой трассировки и управления [SWS_Dlt_00224]. В расширенном заголовке Dlt устанавливает поле MSTP в 0x0 для Dlt_SendLogMessage и в 0x1 для Dlt_SendTraceMessage. Поле MTIN определяется из переданной информационной структуры SWS Dlt с. 35, то есть из одного из этих типов PRS LT с. 24:

  • Dlt_MessageLogLevelType [SWS_Dlt_00230],
  • Dlt_MessageTraceType [SWS_Dlt_00231],
  • Dlt_MessageNetworkTraceInfoType при сетевой трассировке [SWS_Dlt_00233].

Бит 0 поля Dlt_MessageOptionsType указывает на подробный режим (Verbose) [SWS_Dlt_00229]. В режиме Non-Verbose 4-байтовый Message ID несет статическое значение сообщения [SWS_Dlt_00228]. Полезная нагрузка содержит тогда только Message ID и нестатические данные PRS LT с. 23.

Для ошибок DET модуль Dlt в R20-11 предоставляет Dlt_DetForwardErrorTrace [SWS_Dlt_00432]. Эти сообщения содержат ApplicationId «DET» и ContextId «STD» [SWS_Dlt_00376]. В R25-11 эта функция была удалена SWS Dlt с. 1. События DEM используют «DEM»/«STD0» и Message ID 0x00000001 [SWS_Dlt_00377]. Идентификаторы сообщений с 0x00000001 по 0x00000003 зарезервированы для DEM, DET и сообщений трассировки [SWS_Dlt_00031].

Для VFB-Trace модуль Dlt предоставляет функцию-хук для каждого сконфигурированного события RTE. Ее прототип берется из BswModuleEntry RTE [SWS_Dlt_00027] [SWS_Dlt_00335]. Порядок действий в каждом хуке:

  1. Хук проверяет статус трассировки своего ContextId [SWS_Dlt_00281].
  2. Он вызывает внутренний эквивалент Dlt_SendTraceMessage [SWS_Dlt_00285], причем в режиме Non-Verbose [SWS_Dlt_00277].
  3. Полезная нагрузка содержит все аргументы хука [SWS_Dlt_00278].

Каждый хук имеет собственный ContextId [SWS_Dlt_00279]. Устанавливаются DLT_TYPE_APP_TRACE и DLT_TRACE_VFB [SWS_Dlt_00484], при этом ApplicationId имеет значение «VFBT» SWS Dlt с. 23.

Диаграмма последовательности: хук VFB-Trace выполняет отправку только в том случае, если статус трассировки его ContextId активен. Источники: [SWS_Dlt_00281] [SWS_Dlt_00285] [SWS_Dlt_00277] [SWS_Dlt_00484] SWS Dlt с. 23

Поведение при ошибке

API отправки сообщают о проблемах через свои возвращаемые значения [SWS_Dlt_00495] [SWS_Dlt_00241]:

  • DLT_E_UNKNOWN_SESSION_ID: сессия неизвестна.
  • DLT_E_MSG_TOO_LARGE: сообщение слишком длинное для всех назначенных каналов.
  • DLT_E_NO_BUFFER: недостаточно места в буфере.

Если буфер полон, сообщение отбрасывается, устанавливается флаг переполнения для буфера канала и в зависимости от конфигурации отправляется управляющее сообщение «BufferOverflowNotification» SWS Dlt с. 32 SWS Dlt с. 95. Помимо Dlt_GetLogInfo, это единственная команда, которую Dlt отправляет самостоятельно SWS Dlt с. 44. На ошибки при регистрации Dlt отвечает с DLT_E_CONTEXT_ALREADY_REG или DLT_E_CONTEXT_NOT_YET_REG [SWS_Dlt_00495].

R20-11 определяет следующие коды ошибок:

  • Ошибки разработки: DLT_E_PARAM, DLT_E_PARAM_POINTER, DLT_E_INIT_FAILED, DLT_E_REGISTRATION [SWS_Dlt_00727].
  • Ошибки времени выполнения: DLT_E_SKIPPED_TRANSMISSION, DLT_E_DEPRECATED_PARAMETER, DLT_E_MULTIPLE_REQUESTS [SWS_Dlt_00728].

Команды управления для неизвестного кортежа получают ответ DLT_E_ERROR SWS Dlt с. 39. Служба Control также поддерживает DLT_E_NOT_SUPPORTED [SWS_Dlt_00772]. Если источник времени не возвращает значение, временная метка устанавливается в 0x00000000 SWS Dlt с. 30. Неудачные передачи повторяются до сконфигурированного максимального числа раз SWS Dlt с. 38.

Diagnostic Log and Trace (DLT)

Модуль DLT собирает сообщения журнала и точки трассировки и форматирует их в стандартизированные кадры DLT для внешних инструментов.

Возможности — Обзор

  • void Dlt_Init (const Dlt_ConfigType* config); Dlt is using the NVRam Manager and is to be initialized very late in the ECU startup phase.
  • void Dlt_GetVersionInfo (Std_VersionInfoType* versioninfo); Returns the version information of this module.
  • Std_ReturnType Dlt_SendTraceMessage (Dlt_SessionIDType sessionId, const Dlt_MessageTraceInfoType* traceInfo, const uint8* trace Data, uint16 trace Data Length); The service represents the interface to be used by basic software modules or by software components to trace parameters.
  • Std_ReturnType Dlt_SendLogMessage (Dlt_SessionIDType sessionId, const Dlt_MessageLogInfoType* logInfo, const uint8* log Data, uint16 log Data Length); The service represents the interface to be used by basic software modules or by software component to send Log Messages.
  • Std_ReturnType Dlt_UnregisterContext (Dlt_SessionIDType sessionId, Dlt_ApplicationIDType appId, Dlt_ContextIDType contextId); The service has to be called when a software module is going to be stopped.
  • void Dlt_DetForwardErrorTrace (uint16 moduleId, uint8 instanceId, uint8 apiId, uint8 errorId); Service to fo rward error reports from Det to Dlt.
  • Std_ReturnType Dlt_SetLogLevel (Dlt_ApplicationIDType appId, Dlt_ContextIDType contextId, Dlt_MessageLogLevelType new Log Level); This service is used to change the Log Level for the given tuple of Application ID/ Context ID.
  • Std_ReturnType Dlt_SetTraceStatus (Dlt_ApplicationIDType appId, Dlt_ContextIDType contextId, boolean new Trace Status); The service Dlt_ Set Trace Status sets the trace status for a specific tuple of Application ID and Context ID.
  • Std_ReturnType Dlt_GetLogInfo (uint8 options, Dlt_ApplicationIDType appId, Dlt_ContextIDType contextId, uint8* status, Dlt_LogInfoType* logInfo); Called to request information about registered Application Ids, their Context Ids and the corresponding log level.
