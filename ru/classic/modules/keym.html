Роль KeyM между мастером ключей, приложениями и CSM

Key Manager (KeyM) состоит из двух субмодулей. Субмодуль Crypto-Key инициализирует, обновляет и обслуживает криптографический ключевой материал электронного блока управления, например ключи для Secured I-PDU. Эти ключи предоставляет мастер ключей, который может находиться в автомобиле или в бэкенде. Связь с ним обычно осуществляется через диагностические команды (SWS KeyM с. 24). Субмодуль сертификатов хранит состояние PKI-сертификатов и предоставляет их содержимое ([SWS_KeyM_00066], [SWS_KeyM_00083]). KeyM сам не сохраняет ключевой материал. Он передает его через обязательные интерфейсы Csm_KeyElementSet, Csm_KeyElementGet и Csm_KeySetValid в ключи CSM ([SWS_KeyM_00076]). Другими используемыми интерфейсами являются Csm_KeyDerive, Csm_SignatureVerify, Det_ReportError и IdsM_SetSecurityEvent ([SWS_KeyM_00078]).

Прикладные SWC обращаются через порты RTE. Для каждого сертификата имеется порт KeyMCertificate_{KeyMCertificate}, для каждого элемента сертификата — порт KeyMCertificateElement_…, а также порты KeyMCryptoKey и KeyMCryptoKeyNotification ([SWS_KeyM_00160], [SWS_KeyM_00162], [SWS_KeyM_00163], [SWS_KeyM_00164]). Модули BSW также используют KeyM:

  • Реализация TLS в TcpIp получает сертификаты с помощью KeyM_GetCertificate (SWS TcpIp с. 134).
  • DCM считывает белые списки с помощью KeyM_CertElementGetFirst/KeyM_CertElementGetNext (SWS DCM с. 162).
  • Результаты верификации DCM получает через сконфигурированный в качестве callback Dcm_KeyMAsyncCertificateVerifyFinished (SWS DCM с. 245).

Контекстная диаграмма: KeyM выступает посредником между приложениями или DCM/TcpIp и CSM, StbM, NvM, IdsM и DET; Key-Handler являются конфигурируемыми расширениями. Источники: [SWS_KeyM_00076], [SWS_KeyM_00078], [SWS_KeyM_00160], SWS KeyM (Рис. 9.4) с. 119, SWS TcpIp с. 134

Цепочка сертификатов и ее конфигурация

Сертификаты описываются в конфигурации через контейнеры KeyMCertificate. Во время выполнения адресация к ним осуществляется через дескрипторы KeyM_CertificateIdType и KeyM_CertElementIdType, оба типа uint16 ([SWS_KeyM_00301], [SWS_KeyM_00300]). Каждый контейнер содержит три ссылки:

  • на вышестоящий сертификат; при этом корневой сертификат ссылается на самого себя,
  • на задание CSM для проверки подписи,
  • на ключ CSM для открытого ключа сертификата.

Эту структуру показывает SWS KeyM (Рис. 7.3) с. 22. Если все шаги проверки безошибочны, KeyM устанавливает открытый ключ в ключ CSM, на который ссылается KeyMCertCsmSignatureVerifyKeyRef, и проверяет его с помощью Csm_KeySetValid ([SWS_KeyM_00170]).

Данные сертификата передаются как KeyM_CertDataType. Структура состоит из certDataLength и указателя certData на буфер вызывающей стороны ([SWS_KeyM_00041]). Размеры типов данных RTE определяются конфигурацией: KeyMKeyCertNameMaxLength для имен и KeyMCertificateElementMaxLength для буферов элементов ([SWS_KeyM_91000], [SWS_KeyM_91004]).

Контекстная диаграмма: трехзвенная цепочка Root – Intermediate – Working Certificate со ссылками на одно задание CSM и один ключ CSM для каждого; Root ссылается на себя. Источники: SWS KeyM (Рис. 7.3) с. 22, [SWS_KeyM_00170]

Статус сертификата: от установки до действительности

Каждый сертификат имеет статус типа KeyM_CertificateStatusType, который возвращает KeyM_CertGetStatus ([SWS_KeyM_91003], [SWS_KeyM_00066]). Жизненный цикл согласно SWS KeyM (Рис. 7.4) с. 24:

  • После KeyM_Init сертификат находится в состоянии KEYM_CERTIFICATE_NOT_AVAILABLE.
  • KeyM_SetCertificate с длиной > 0, KeyM_ServiceCertificate или загрузка при запуске приводят к переходному состоянию KEYM_CERTIFICATE_NOT_PARSED.
  • После успешного синтаксического анализа следует KEYM_CERTIFICATE_PARSED_NOT_VALIDATED.
  • KeyM_SetCertificate с длиной 0 сбрасывает сертификат и статус.

KEYM_CERTIFICATE_VALID сертификат достигает только после полной, безошибочной верификации ([SWS_KeyM_00170]). Если проверка завершается неудачно, остается специфический статус ошибки, например KEYM_E_CERTIFICATE_VALIDITY_PERIOD_FAIL, KEYM_E_CERTIFICATE_SIGNATURE_FAIL или KEYM_E_CERTIFICATE_INVALID_CHAIN_OF_TRUST ([SWS_KeyM_91003]).

Диаграмма состояний: сертификат проходит «недоступен → не разобран → разобран → действителен»; ошибки синтаксического анализа и верификации ведут к собственным статусам ошибок. Интерпретация: сопоставление статусов ошибок верификации и путь сброса из всех состояний являются производными. Источники: SWS KeyM (Рис. 7.4) с. 24, SWS KeyM (Рис. 7.4) с. 33, [SWS_KeyM_91003]

KeyM_SetCertificate сохраняет предоставленный сертификат лишь временно в сконфигурированном классе памяти, обычно в RAM. Для постоянного хранения, например корневого сертификата, предназначена KeyM_ServiceCertificate ([SWS_KeyM_00057], SWS KeyM с. 31). Для асинхронной верификации существует три варианта:

  • KeyM_VerifyCertificates проверяет ровно одну пару из нижнего и верхнего сертификатов ([SWS_KeyM_00059]).
  • KeyM_VerifyCertificate определяет цепочку для установленного сертификата самостоятельно из сохраненных сертификатов ([SWS_KeyM_00060]).
  • KeyM_VerifyCertificateChain проверяет переданную вызывающей стороной цепочку, отсортированную в порядке PKI ([SWS_KeyM_00061]).

Если вызов возвращает E_OK, сконфигурированная KeyMCertificateVerifyCallbackNotificationFunc позже сообщает результат как KeyM_CertificateStatusType ([SWS_KeyM_00153], [SWS_KeyM_00073]).

Диаграмма последовательности: рабочий сертификат устанавливается, проходит синтаксический анализ, асинхронно верифицируется; затем открытый ключ устанавливается и валидируется в CSM, результат сообщается через callback. Источники: SWS KeyM (Рис. 9.4) с. 119, [SWS_KeyM_00060], [SWS_KeyM_00170], [SWS_KeyM_00153]

Сервисы сертификатов и доступ к элементам сертификатов

Если установлены KeyMServiceCertificateFunctionEnabled и KeyMCertificateManagerEnabled, субмодуль сертификатов предоставляет KeyM_ServiceCertificate. Через него мастер ключей вводит или обновляет постоянно сохраненные сертификаты ([SWS_KeyM_00021], [SWS_KeyM_00056]). Операция выбирается через KeyM_ServiceCertificateType ([SWS_KeyM_00039]):

  • запросить CSR или вернуть подписанный CSR,
  • установить или обновить корневой или промежуточный сертификат,
  • предоставить список отзыва,
  • специфичные для производителя расширения в зарезервированной области 0x80–0x9F.

Операция выполняется асинхронно и завершается с KeyM_ServiceCertificateCallbackNotification ([SWS_KeyM_00149], [SWS_KeyM_00152]). Опционально можно подключить Key-Handler KeyM_KH_ServiceCertificate ([SWS_KeyM_00072]).

Отличия от более поздних релизов: они дополняют KeyM_ServiceCertificateByCertId и сокращают callback до CertId и Result (SWS KeyM с. 92). Для R20-11 действует сигнатура с ResultDataLength и ResultDataPtr ([SWS_KeyM_00147]). Попытки установки и обновления для корневых и промежуточных сертификатов стандартизированы как Security Events от KEYM_SEV_INST_ROOT_CERT_OP до KEYM_SEV_UPD_INTERMEDIATE_CERT_OP ([SWS_KeyM_00172]).

Диаграмма последовательности: корневой или промежуточный сертификат вносится через KeyM_ServiceCertificate, разбирается, проверяется по времени и в зависимости от конфигурации сохраняется в NvM или CSM; о завершении сообщает сервисный callback. Источники: SWS KeyM (Рис. 9.5) с. 120, [SWS_KeyM_00056], [SWS_KeyM_00149], [SWS_KeyM_00147]

Содержимое распарсенных сертификатов KeyM_CertElementGet считывает по сконфигурированному Objekt-ID ([SWS_KeyM_00063], [SWS_KeyM_00127]). Элементы с множественными значениями можно обойти двумя способами:

  • с помощью KeyM_CertElementGetFirst/KeyM_CertElementGetNext и удерживаемого вызывающей стороной KeyM_CertElementIteratorType, которое должно оставаться неизменным до завершения ([SWS_KeyM_00064], [SWS_KeyM_00065], [SWS_KeyM_00042]),
  • по индексам с помощью KeyM_CertificateElementGetCount и KeyM_CertificateElementGetByIndex ([SWS_KeyM_91015], [SWS_KeyM_91014]).

Итерация допустима только для элементов с KeyMCertificateElementHasIteration = TRUE ([SWS_KeyM_00148]).

Обновление ключей в виде сессии Start–Prepare–Update–Finalize

Субмодуль Crypto-Key может эксплуатироваться в сессионном режиме. KeyM_Start открывает сессию, KeyM_Finalize закрывает ее; между ними принимаются такие операции, как KeyM_Prepare и KeyM_Update ([SWS_KeyM_00050], [SWS_KeyM_00053], SWS KeyM с. 25). KeyM_StartType отличает производственный режим OEM с повышенными правами от режима мастерской ([SWS_KeyM_00038]).

Если активирован Key-Handler, KeyM_Start передает параметры в KeyM_KH_Start и принимает его возвращаемое значение. Так можно реализовать, например, специфичные для производителя проверки подписи ([SWS_KeyM_00067], SWS KeyM с. 25). Соответственно KeyM_Prepare и KeyM_Finalize делегируют полномочия KeyM_KH_Prepare и KeyM_KH_Finalize ([SWS_KeyM_00068], [SWS_KeyM_00070]). О завершении финализации сообщает KeyM_CryptoKeyFinalizeCallbackNotification, если установлено KeyMCryptoKeyStartFinalizeFunctionEnabled ([SWS_KeyM_00080], [SWS_KeyM_00079]).

Диаграмма последовательности: сессия ключей открывается с KeyM_Start, подготавливается с KeyM_Prepare, асинхронно обновляется с KeyM_Update и закрывается с KeyM_Finalize; Key-Handler подключаются в зависимости от конфигурации. Источники: [SWS_KeyM_00050], [SWS_KeyM_00067], [SWS_KeyM_00068], [SWS_KeyM_00077], [SWS_KeyM_00080], SWS KeyM (Рис. 9.2) с. 117

KeyM_Update работает асинхронно ([SWS_KeyM_00052]). Целевой ключ KeyM находит одним из двух путей:

  • по имени в KeyMCryptoKeyName ([SWS_KeyM_00091]),
  • без действительного имени — по битам 121..124 данных запроса, интерпретируемых как SHE-M1M2M3, сопоставленным с KeyMCryptoKeyCryptoProps ([SWS_KeyM_00154]).

Без совпадения и без Key-Handler вызов завершается с KEYM_E_PARAMETER_MISMATCH ([SWS_KeyM_00155]). С Key-Handler обновление протекает следующим образом:

  1. KeyM вызывает KeyM_KH_Update с найденным ключом или 0xFFFFFFFFul ([SWS_KeyM_00092]) и предоставляет при этом внутренний буфер ([SWS_KeyM_00097]).
  2. Если обработчик сообщает KEYM_KH_UPDATE_KEY_UPDATE_REPEAT с данными, KeyM сохраняет или выводит ключ в CSM и вызывает обработчик снова ([SWS_KeyM_00096], [SWS_KeyM_00055]).
  3. Если обработчик сообщает KEYM_KH_UPDATE_FINISH, KeyM копирует результат в буфер вызывающей стороны и вызывает KeyM_CryptoKeyUpdateCallbackNotification ([SWS_KeyM_00093]).

До этого callback вызывающей стороне не разрешается изменять буфер результатов ([SWS_KeyM_00156]).

Диаграмма деятельности: KeyM_Update определяет целевой ключ по имени или данным SHE и обрабатывает его напрямую либо в цикле Key-Handler до KEYM_KH_UPDATE_FINISH. Источники: [SWS_KeyM_00091], [SWS_KeyM_00092], [SWS_KeyM_00093], [SWS_KeyM_00096], [SWS_KeyM_00154], [SWS_KeyM_00155]

KeyM_Verify проверяет ключи в зависимости от конфигурации синхронно. При KeyMCryptoKeyVerifyAsyncMode = TRUE проверка выполняется асинхронно, и результат поступает через KeyM_CryptoKeyVerifyCallbackNotification ([SWS_KeyM_00054], [SWS_KeyM_00151], [SWS_KeyM_00081]).

Работа модуля: инициализация, синхронизация и правила вызова

KeyM_Init инициализирует модуль ([SWS_KeyM_00043]). Указатель на конфигурацию всегда должен быть NULL_PTR ([SWS_KeyM_00158]), хотя в описании параметров упоминается набор конфигурации post-build. Интерпретация: следовательно, в R20-11 конфигурация фактически не должна передаваться через этот указатель. KeyM_Deinit переводит модуль в неинициализированное состояние ([SWS_KeyM_00047]). Версия начиная с R23-11 дополнительно требует при этом активного удаления ключевого материала в RAM (SWS KeyM с. 49).

KeyM_MainFunction вызывается периодически с сконфигурированным интервалом ([SWS_KeyM_00074]). KeyM_MainBackgroundFunction работает во время простоя вытесняющей операционной системы и подходит для ресурсоемких синхронных функций, таких как KeyM_KH_Update ([SWS_KeyM_00075]). Предположительно, эти функции продвигают выполнение асинхронных сервисов: об их принятии API сообщают с помощью E_OK, об их завершении — callback ([SWS_KeyM_00060], [SWS_KeyM_00052]). Сервисы в целом не являются реентерабельными; функции итератора реентерабельны только для каждого отдельного итератора ([SWS_KeyM_00057], [SWS_KeyM_00064]). Имена callback конфигурируются и подключаются через KeyM_Externals.h ([SWS_KeyM_00073], SWS KeyM с. 91).

Поведение при ошибке

При активном обнаружении ошибок разработки KeyM при каждом вызове проверяет ([SWS_KeyM_00144], [SWS_KeyM_00145], [SWS_KeyM_00146], [SWS_KeyM_00036]):

  • инициализацию (KEYM_E_UNINIT),
  • размеры буферов (KEYM_E_SMALL_BUFFER),
  • непредвиденные указатели NULL (KEYM_E_PARAM_POINTER).

Если ссылочный сертификат имеет класс памяти KEYM_STORAGE_IN_CSM или KEYM_STORAGE_IN_NVM, спецификация требует KEYM_E_CONFIG_FAILURE, без режима разработки — E_NOT_OK ([SWS_KeyM_00166]).

Синхронные возвращаемые значения используют специфичные для KeyM значения ([SWS_KeyM_00040]):

  • KEYM_E_BUSY: другие задания еще выполняются,
  • KEYM_E_PENDING: задание принято, обработка асинхронная,
  • KEYM_E_KEY_CERT_SIZE_MISMATCH, KEYM_E_PARAMETER_MISMATCH и KEYM_E_KEY_CERT_INVALID.

Функции сертификатов добавляют другие коды. KEYM_E_KEY_CERT_EMPTY означает пустые слоты, KEYM_E_KEY_CERT_READ_FAIL — отказ в доступе, а KEYM_E_CERT_INVALID_CHAIN_OF_TRUST — недействительный вышестоящий сертификат ([SWS_KeyM_00058], [SWS_KeyM_00060], SWS KeyM с. 66). Неитерируемые элементы возвращают KEYM_E_CERT_INVALID ([SWS_KeyM_00148]). KeyM_CertElementGet при неудаче устанавливает выходную длину в ноль ([SWS_KeyM_00063], SWS KeyM с. 71).

Асинхронные ошибки приходят в callback. KeyM_ResultType различает, среди прочего, KEYM_RT_NOT_OK, KEYM_RT_KEY_CERT_INVALID, KEYM_RT_KEY_CERT_WRITE_FAIL, KEYM_RT_KEY_CERT_UPDATE_FAIL и KEYM_RT_CERT_INVALID_CHAIN_OF_TRUST ([SWS_KeyM_91008]). Проверки сертификатов возвращают подробный статус из KeyM_CertificateStatusType ([SWS_KeyM_00073], [SWS_KeyM_91003]).

Неудачная проверка цепочки дополнительно является Security Event KEYM_SEV_CERT_VERIF_FAILED (ID 5) ([SWS_KeyM_00172]). В IdsM о нем сообщается только при KeyMEnableSecurityEventReporting = TRUE. Более поздние релизы называют это событие SEV_CERT_CHAIN_VERIFICATION_FAILED (SWS KeyM с. 38); для R20-11 действует имя из [SWS_KeyM_00172].

Key Manager (KeyM)

Управляет жизненным циклом, хранением и распространением криптографических ключей и сертификатов.

Возможности — Обзор

  • void KeyM_Init (const KeyM_ConfigType* ConfigPtr); This function initializes the key management module.
  • void KeyM_Deinit (void); This function resets the key management module to the uninitialized state.
  • void KeyM_GetVersionInfo (Std_VersionInfoType* VersionInfo); Provides the version information of this module.
  • Std_ReturnType KeyM_Start (KeyM_StartType StartType, const uint8* Request Data, uint16 Request Data Length, uint8* Response Data, uint16* Response Data Length); This function is optional and only used if the configuration item Key MCrypto Key Start Finalize Function Enabled is set to true.
  • Std_ReturnType KeyM_Prepare (const uint8* Request Data, uint16 Request Data Length, uint8* Response Data, uint16* Response Data Length); This function is used to prepare a key update operation.

Эта функция предоставляет общее количество элементов данных, доступных для указанного элемента сертификата. Обычно доступен только один элемент данных. Но в некоторых случаях одному элементу сертификата может быть присвоено несколько элементов данных подряд. Эта функция извлекает общее количество элементов. Затем к отдельным элементам данных можно получить доступ с помощью Key M_ Certificate Element Get By Index().
