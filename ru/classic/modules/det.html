Роль Default Error Tracer и границы его системы

Default Error Tracer (DET) централизованно принимает сообщения об ошибках в Classic-стеке. Он предоставляет три сервиса отправки сообщений. Det_ReportError служит для ошибок разработки [SWS_Det_00009], Det_ReportRuntimeError — для ошибок времени выполнения [SWS_Det_01001]. Для транзиентных ошибок в R20-11 еще предусмотрен Det_ReportTransientFault [SWS_Det_01003]. К ним добавляются сервисы управления Det_Init, Det_Start und Det_GetVersionInfo [SWS_Det_00008] [SWS_Det_00010] [SWS_Det_00011]. Все сервисы доступны через Det.h.

DET сам по себе не анализирует сообщения по существу. Он распределяет их по сконфигурированным Error Hooks и Callouts (SWS DET с. 16). Согласно описанию ошибок, действующему для R20-11, через код интегратора он таким образом взаимодействует с DEM и RTE (ErrorDescription с. 10). Кроме того, предусмотрена опциональная пересылка в Dlt через Dlt_DetForwardErrorTrace [SWS_Det_00211].

Контекстная диаграмма: DET находится между отправляющими сообщения модулями и кодом интегратора. Путь к DEM и Dlt открывают только конфигурация и Callouts. Источники: SWS DET Abb. Interfaces с. 28, ErrorDescription с. 10, [SWS_Det_00211]

Запуск: Det_Init и Det_Start в процедуре запуска EcuM

EcuM содержит Det_Init и Det_ReportError среди своих опциональных интерфейсов (SWS EcuM с. 142). Det_Init имеет Service-ID 0x00, является синхронным и нереэнтрантным. Параметр ConfigPtr указывает на выбранный набор конфигурации [SWS_Det_00008]. Его тип Det_ConfigType имеет специфичную для реализации структуру [SWS_Det_00210]. Det_Start (0x02) запускает трассировщик и также является синхронным и нереэнтрантным [SWS_Det_00010].

Согласно схеме инициализации, EcuM сначала вызывает Det_Init, а затем Det_Start (SWS DET Abb. Initialisierung с. 32). Какие сервисы уже действуют между этими двумя вызовами, источники не определяют. Этот вопрос остается здесь открытым. Det_GetVersionInfo (0x03) является реэнтрантным и записывает информацию о версии по переданному указателю [SWS_Det_00011].

Диаграмма последовательности: EcuM инициализирует DET с набором конфигурации и затем запускает его. Только после этого следуют сообщения во время работы. Источники: SWS DET Abb. Initialisierung с. 32, [SWS_Det_00008], [SWS_Det_00010]

Три пути отправки сообщений с общей схемой нумерации

Все три сервиса сообщений имеют одинаковые параметры: ModuleId (uint16), InstanceId, ApiId и ErrorId или FaultId (каждый uint8) [SWS_Det_00009] [SWS_Det_01001] [SWS_Det_01003].

  • ModuleId берется из списка модулей базового программного обеспечения. BSW использует только диапазон 0..255.
  • InstanceId отсчитывается с 0. Модуль, имеющий только один экземпляр, передает 0.
  • ApiId и ErrorId определяет SWS сообщающего модуля (EXP LSA с. 157).

Какой именно сервис применяется, зависит от типа ошибки:

  • Об ошибках разработки модуль BSW сообщает через Det_ReportError со своим идентификатором модуля. Это действует только в том случае, если сконфигурировано обнаружение ошибок разработки (SWS BSWGeneral с. 57). Типичным для этого является запрос вида #if (SPI_DEV_ERROR_DETECT == ON) (EXP LSA с. 113). Примером служит недопустимый параметр в CanIf (SWS CanIf с. 101).
  • Ошибки времени выполнения, такие как ADC_E_BUSY, обрабатываются через Det_ReportRuntimeError (SWS Adc с. 95).
  • Переходные ошибки обрабатываются через сервис Transient-Fault (SWS BSWGeneral с. 53).

В своем описании модуля модуль заявляет эту потребность как ErrorTracerNeeds. Каждый из трех сервисов является там опциональной ролью (TPS BSWMDT с. 266).

Примечание к релизу: Det_ReportTransientFault в R20-11 является нормативным [SWS_Det_01003]. В более поздних версиях этот сервис указан как устаревший (SWS DET с. 24). В R24-11 переходные ошибки были удалены полностью (SWS DET с. 1).

Диаграмма деятельности: тип ошибки определяет сервис сообщений, список вызываемых хуков или callout-функций и последствия для сообщающего модуля. Источники: SWS BSWGeneral с. 57, [SWS_Det_00501], [SWS_Det_00009]

Распределение по хукам ошибок и callout-функциям

Каждый вызов Det_ReportError вызывает все функции, сконфигурированные в DetErrorHook [SWS_Det_00501]. Хуки получают те же параметры, что и исходный вызов (SWS DET с. 16). Интерфейс хука <User_Error_Hooks> имеет Service-ID 0x10, а также является синхронным и реентерабельным [SWS_Det_00181]. Он всегда возвращает E_OK (SWS DET с. 25).

Диаграмма последовательности: Det_ReportError последовательно вызывает все сконфигурированные хуки, опционально также Dlt. В R20-11 сервис не возвращает управление сообщающему модулю. Источники: SWS DET Abb. ReportError с. 36, [SWS_Det_00501], [SWS_Det_00009], SWS Dlt с. 25

Для Det_ReportRuntimeError действует тот же принцип со списком DetReportRuntimeErrorCallout [SWS_Det_00501]. Callout <DetReportRuntimeErrorCallout> имеет Service-ID 0x11 [SWS_Det_00184]. DET возвращает сообщающему модулю E_OK (SWS DET Abb. Runtime mit Hook с. 35). Если callout-функции не сконфигурированы, он сразу отвечает E_OK (SWS DET Abb. Runtime ohne Hook с. 35).

Диаграмма последовательности: при ошибках времени выполнения E_OK является возвращаемым значением как со сконфигурированными callout-функциями, так и без них. Источники: SWS DET Abb. Runtime mit Hook с. 35, SWS DET Abb. Runtime ohne Hook с. 35, [SWS_Det_00184]

Переходные ошибки DET распределяет по списку DetReportTransientFaultCallout [SWS_Det_00501]. Callout имеет Service-ID 0x12 [SWS_Det_00187]. В отличие от ошибок времени выполнения, здесь DET передает возвращаемое значение callout-функции сообщающему модулю. Без callout-функций он возвращает E_OK (SWS DET Abb. Transient mit Hook с. 36, SWS DET Abb. Transient ohne Hook с. 36). Более поздняя версия определяет для нескольких callout-функций логическое «ИЛИ» возвращаемых значений (SWS DET с. 24). Предположительно, это правило действует уже в R20-11.

Диаграмма последовательности: при переходных ошибках результат callout-функций определяет значение, возвращаемое сообщающему модулю. Источники: SWS DET Abb. Transient mit Hook с. 36, SWS DET Abb. Transient ohne Hook с. 36, [SWS_Det_00187]

Подключение SW-C через сервисный порт DETService

SW-C обращаются к DET через RTE. Для каждого сконфигурированного экземпляра модуля DET предоставляет порт Det_{Name} с интерфейсом DETService [SWS_Det_00205]. Операции ReportError и ReportRuntimeError вызывают C-API с идентификатором модуля этого порта [SWS_Det_00202]. Необходимые типы uint8 и uint16 являются типами данных AUTOSAR [SWS_Det_00200].

ModuleId и InstanceId передает не сама SW-C. RTE дополняет их как «port defined argument values» [SWS_Det_00203] [SWS_Det_00204]. Их определение тем самым относится к конфигурации RTE [SWS_Det_00206]. ApiId и ErrorId не стандартизированы для SW-C и находятся в диапазоне 0x00..0xFF [SWS_Det_00203].

Диаграмма кооперации: каждый экземпляр SW-C имеет собственный порт DET. При этом RTE дополняет идентификаторы. Источники: SWS DET Abb. Service-Ports с. 33, [SWS_Det_00205], [SWS_Det_00206]

Конфигурация списков хуков и сигнатур callout-функций

Уведомление конфигурируется в контейнере DetNotification (0..1). Он содержит списки DetErrorHook и DetReportRuntimeErrorCallout (каждый 0..*). В имеющейся более поздней версии они имеют класс конфигурации Pre-compile (SWS DET с. 37). R20-11 дополнительно содержит список DetReportTransientFaultCallout [SWS_Det_00501]. Хук должен иметь тот же тип, что и Det_ReportError, то есть Std_ReturnType (*f)(uint16, uint8, uint8, uint8).

В общем случае callout-функции имеют ту же сигнатуру, что и соответствующая функция. Несколько callout-функций для одного и того же сервиса имеют одинаковый ID (SWS DET с. 25). Описание ошибок в R20-11 ограничивает то, что разрешено делать таким обработчикам: сохранять событие, вызывать DEM или выполнять короткие целесообразные действия (ErrorDescription с. 10). Все три callout-интерфейса специфицированы как reentrant [SWS_Det_00181] [SWS_Det_00184] [SWS_Det_00187].

Поведение при ошибке

В R20-11 для Det_ReportError в графе Sync/Async указано «Not Applicable: The function never returns» [SWS_Det_00009]. Таким образом, ошибки разработки обрабатываются как утверждения (assertions). После хуков нормальный поток управления не продолжается, например из-за бесконечного цикла или останова. Если сконфигурирован только один хук, он может взять на себя обработку исключения (RS BSWGeneral с. 33).

Диаграмма последовательности действий отличается от этого: она показывает стрелку возврата и называет такое поведение зависимым от реализации (SWS DET Abb. ReportError с. 36). Лишь в R21-11 поведение вызова было уточнено (SWS DET с. 1). Для R20-11 определяющим является требование.

При ошибках времени выполнения сообщающий модуль продолжает работу, поскольку Det_ReportRuntimeError всегда возвращает E_OK [SWS_Det_01001] (SWS DET с. 23). При переходных ошибках сообщающий модуль получает результат callout-функций в качестве возвращаемого значения [SWS_Det_01003] (SWS DET Abb. Transient mit Hook с. 36).

Сам DET имеет только одну собственную ошибку разработки: DET_E_PARAM_POINTER (0x01). Она возникает, если Det_GetVersionInfo вызывается с нулевым указателем [SWS_Det_00301]. Об этой ошибке DET сообщает всем функциям, сконфигурированным в callout-функциях. Ошибки времени выполнения и производственные ошибки к DET неприменимы (SWS DET с. 18).

Дальнейшие подробные доказательства

  • [SWS_Det_00009]: сервис сообщений об ошибках разработки. В R20-11 он не возвращает управление.
  • [SWS_Det_01001] и [SWS_Det_00184]: ошибки времени выполнения и соответствующий callout с фиксированным возвращаемым значением E_OK.
  • [SWS_Det_01003] и [SWS_Det_00187]: переходные ошибки, существовавшие только до R24-11. Правило возврата для более поздней версии приведено в SWS DET с. 24.
  • [SWS_Det_00501] и [SWS_Det_00181]: правило распределения и сигнатура хука. Правила для сигнатур приведены в SWS DET с. 25.
  • [SWS_Det_00008], [SWS_Det_00010] и [SWS_Det_00210]: инициализация, запуск и тип конфигурации.
  • С [SWS_Det_00202] по [SWS_Det_00206]: сервисный порт DETService для SW-C.
  • [SWS_Det_00301]: единственная собственная ошибка DET.
  • [SWS_Det_00211] с SWS Dlt с. 25: пересылка в Dlt.
  • SWS DET с. 37: конфигурационный контейнер DetNotification.

Сгенерированное ИИ руководство по модулю на основе фрагментов спецификации в полезной нагрузке. Нормативными для R20-11 являются связанные требования. Утверждения, помеченные как интерпретация, обоснованы в исходном тексте.

Функция Det_ReportError служит центральным сервисом модуля Default Error Tracer (DET) для сообщения об ошибках разработки ([SWS_Det_00009]). Интерфейс доступен через заголовочный файл Det.h.

Использование и параметры

Вызов выполняется модулями BSW при обнаружении ошибки разработки с передачей точного контекста ошибки ([SWS_Det_00009]):

  • ModuleId: идентификатор модуля вызывающего программного модуля.
  • InstanceId: индексный ID экземпляра модуля (начиная с 0; модули только с одним экземпляром передают 0).
  • ApiId: идентификатор сервиса API, в котором возникла ошибка.
  • ErrorId: идентификатор конкретной ошибки разработки согласно спецификации вызывающего модуля.

Формально функция имеет тип возвращаемого значения Std_ReturnType, однако не возвращает никакого значения, а использует этот тип исключительно для совместимости с сервисами и хуками ([SWS_Det_00009]). Классификация по синхронной или асинхронной семантике неприменима, поскольку Det_ReportError согласно спецификации никогда не возвращает управление вызывающей стороне ([SWS_Det_00009]).

Параллелизм и последовательность выполнения

Функция специфицирована как реентерабельная ([SWS_Det_00009]). При вызове Det_ReportError DET выполняет все функции обратного вызова, сконфигурированные в параметре DetErrorHook ([SWS_Det_00501]).

Взаимодействие

Другие модули BSW сообщают об ошибках параметров напрямую этому сервису. Так, например, CAN-интерфейс при недопустимом параметре TransceiverId в CanIf_SetTrcvMode() или CanIf_SetTrcvWakeupMode() сообщает код ошибки CANIF_E_PARAM_TRCV ([SWS_CANIF_00538], CAN Interface §8.3 «CanIf_SetTrcvMode»; [SWS_CANIF_00535], CAN Interface §8.3 «CanIf_SetTrcvWakeupMode»). При недопустимом параметре режима CanIf_SetTrcvWakeupMode() аналогично сообщает CANIF_E_PARAM_TRCVWAKEUPMODE в Det_ReportError ([SWS_CANIF_00536], CAN Interface §8.3 «CanIf_SetTrcvWakeupMode»).

Это указание по использованию основано на спецификациях версии AUTOSAR R20-11.

Использование и сигнатура

Синхронный сервис Det_ReportRuntimeError ([SWS_Det_01001]) служит для сообщения об ошибках времени выполнения в Default Error Tracer (DET) и доступен через заголовочный файл Det.h. Функция имеет следующие параметры:

  • ModuleId: идентификатор модуля вызывающего модуля.
  • InstanceId: индексный ID экземпляра модуля (для модулей с одним экземпляром — 0).
  • ApiId: идентификатор сервиса API, в котором была обнаружена ошибка.
  • ErrorId: специфический идентификатор обнаруженной ошибки времени выполнения (определен в спецификации вызывающего модуля).

Возвращаемое значение всегда E_OK ([SWS_Det_01001]).

Параллелизм и поведение

Интерфейс определен как реентерабельный ([SWS_Det_01001]). При вызове Det_ReportRuntimeError вызываются все функции обратного вызова, сконфигурированные в DetReportRuntimeErrorCallout ([SWS_Det_00503]).

Взаимодействие и контекст ошибки

Вызывающие модули используют сервис для сообщения о специфических состояниях ошибок во время выполнения. Так, например, модуль CanIf при запросе передачи по каналу в режиме CANIF_OFFLINE сообщает код ошибки CANIF_E_STOPPED в Det_ReportRuntimeError ([SWS_CANIF_00382], AUTOSAR_SWS_CANInterface с. 40 §7.10 «Transmit data flow»). Другим сценарием применения является превышение глобальной длины PDU при отключенном усечении в CanIf_Transmit(), что вызывает сообщение об ошибке времени выполнения CANIF_E_TXPDU_LENGTH_EXCEEDED ([SWS_CANIF_00900], AUTOSAR_SWS_CANInterface с. 81 §8.3.7 «CanIf_ReadRxPduData»).

Это указание по использованию основано на спецификации AUTOSAR Classic Release R20-11.

Использование и семантика

Функция Det_ReportTransientFault согласно [SWS_Det_01003] служит для сообщения о транзиентных сбоях в Default Error Tracer. Сервис выполняется синхронно и специфицирован как реентерабельный. Объявление предоставляется через Det.h.

Передаваемые параметры включают:

Взаимодействие и поведение callout

При вызове Det_ReportTransientFault согласно [SWS_Det_00502] вызываются все callback-функции, сконфигурированные в DetReportTransientFaultCallout.

Для возвращаемого значения типа Std_ReturnType согласно [SWS_Det_01003] действует следующая семантика:

  • Если ни один callout не сконфигурирован, происходит немедленный возврат с E_OK.
  • Если callout присутствует, возвращается возвращаемое значение этого сконфигурированного callout.
  • Если настроено несколько callout, возвращается результат логической операции ИЛИ (сумма) всех возвращаемых значений callout. Поскольку определено E_OK = 0, сервис возвращает E_OK только тогда, когда без исключения все вызванные callout сообщают E_OK.
