Роль и границы системы: от события датчика к квалифицированному Security Event

Intrusion Detection System Manager (IdsM) — это модуль BSW платформы Classic Platform, который принимает бортовые события безопасности (SEv) через стандартизированный интерфейс. Он фильтрует их по настраиваемым правилам в квалифицированные события (QSEv), после чего сохраняет или отправляет их SWS IdsM с. 7. В качестве датчиков выступают модули BSW, проприетарные CDD и SW-C. Приемниками являются IDS Reporter (IdsR), доступный через PduR, а также DEM/Sem для локального сохранения SWS IdsM с. 16 [SWS_IdsM_01202] [SWS_IdsM_01601].

Является ли система действительно скомпрометированной, IdsM явно не оценивает. Он не знает значения контекстных данных; обнаружение и реагирование находятся за пределами модуля, например в SOC [SWS_IdsM_CONSTR_00001]. Спецификация также допускает, что события SEv могут отбрасываться в зависимости от частоты сообщений или нагрузки на систему SWS IdsM с. 11.

Другие соседние модули и их задачи:

  • DET: ошибки разработки
  • DCM: диагностический доступ к Reporting Mode
  • NvM: сохранение Reporting Mode в энергонезависимой памяти
  • BswM: поставщик Block State
  • StbM или SW-C: источник меток времени
  • CSM: цифровые подписи
  • BSW Scheduler: циклический вызов

Источники: SWS IdsM с. 13. То, какие файлы заголовков подключаются, зависит от соответствующих конфигурационных переключателей, например Det.h при IdsMDevErrorDetect и PduR.h при IdsMSinkIdsR [SWS_IdsM_00101] [SWS_IdsM_00105].

Контекстная диаграмма: IdsM располагается между датчиками (BSW/CDD напрямую, SW-C через RTE) и приемниками IdsR (через PduR) или DEM/Sem. Управляющими и вспомогательными модулями являются BswM, DCM, NvM, StbM, CSM и DET. Источники: SWS IdsM с. 20, SWS IdsM с. 13, [SWS_IdsM_91027], [SWS_IdsM_91028].

Жизненный цикл: инициализация и циклическая обработка

IdsM_Init инициализирует все внутренние переменные и переводит модуль в состояние «инициализирован» [SWS_IdsM_00202] [SWS_IdsM_91001]. Повторный вызов в инициализированном состоянии не выполняет повторную инициализацию. При активном IdsMDevErrorDetect он вместо этого сообщает IDSM_E_ALREADY_INITIALIZED [SWS_IdsM_00204]. В неинициализированном состоянии любой API, кроме IdsM_Init и IdsM_GetVersionInfo, приводит к ошибке DET [SWS_IdsM_00203].

Основная работа выполняется асинхронно. IdsM_MainFunction вызывается периодически и обрабатывает события, которые были поставлены в очередь во время вызовов API [SWS_IdsM_91000] SWS IdsM с. 19. Период IdsMMainFunctionPeriod одновременно служит временной базой для всех интервальных фильтров. Их интервалы должны быть кратны этому периоду и начинаются с первого вызова MainFunction [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01064] [SWS_IdsM_01065].

Диаграмма состояний: только IdsM_Init делает модуль пригодным для использования. Ошибочные вызовы в обоих состояниях передаются в DET без изменения состояния. Источники: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], [SWS_IdsM_91000].

Передача сообщений о Security Events: идентификация, варианты API и буферизация

Каждый экземпляр SEv описывается четырьмя параметрами: IdsMExternalEventId, IdsMSensorInstanceId, внутренне вычисленным IdsMInternalEventId и именем события [SWS_IdsM_00600] [SWS_IdsM_00601]. Для использования действуют следующие правила (SWS IdsM с. 21):

  • Датчики используют исключительно символическую константу контейнера IdsMEvent, но ни в коем случае не внутреннее числовое значение [SWS_IdsM_00602] [SWS_IdsM_00607].
  • Внешний ID 0xFFFF недействителен [SWS_IdsM_00604].
  • Если существует только один экземпляр модуля, экземпляр датчика по умолчанию равен 0 [SWS_IdsM_00608].

Для отправки сообщений предусмотрено шесть синхронных нереэнтрантных сервисов. Они различаются передаваемыми дополнительными данными. Варианты со счетчиком и временной меткой предназначены для интеллектуальных датчиков (SW-C или CDD), которые определяют эти значения самостоятельно SWS IdsM с. 19. Если имеется только временная метка без собственного счетчика, передается count = 1 [SWS_IdsM_00405].

Контекстные данные передаются как указатель на массив байтов и могут иметь длину до 1500 байт [SWS_IdsM_00501] [SWS_IdsM_00502]. Для датчиков SW-C действуют два дополнительных параметра SWS IdsM с. 37:

  • IdsMEventMaxContextDataSize ограничивает объем контекстных данных [SWS_IdsM_01300].
  • IdsMAdditionalParameterOption (None, Count, CountTimestamp) определяет, какие параметры предоставляет интерфейс сервисного порта [SWS_IdsM_01301] [SWS_IdsM_01303].

При приеме IdsM сохраняет SEv в буфере событий (Event Buffer) [SWS_IdsM_00702]. Контекстные данные помещаются в буфер контекстных данных (Context Data Buffer) такого же или ближайшего большего размера, который связывается с буфером событий [SWS_IdsM_00705] [SWS_IdsM_00706]. Без контекстных данных буфер контекста не выделяется [SWS_IdsM_00709]. Количество и размеры буферов настраиваются [SWS_IdsM_00701] [SWS_IdsM_00704]. Для количества буферов событий спецификация рекомендует: число экземпляров фильтров агрегации плюс верхний предел параллельно обрабатываемых событий SWS IdsM с. 22.

Диаграмма последовательности: отправка сообщения в контексте датчика только буферизует SEv. Установка временной метки, фильтрация и квалификация выполняются только при циклическом вызове IdsM_MainFunction (вариант со StbM в качестве источника времени). Источники: SWS IdsM с. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01104].

Диаграмма деятельности: отсутствие буфера событий вызывает внутреннее SEv. Отсутствие буфера контекстных данных приводит к тому, что событие обрабатывается далее без контекстных данных. Источники: SWS IdsM с. 27, [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708].

Квалификация: Reporting Mode и цепочка фильтров

Каждое SEv имеет обязательный фильтр режима отчетности (Reporting Mode). Он не является частью цепочки фильтров, а привязан непосредственно к событию; его значение по умолчанию берется из IdsMReportingModeFilter [SWS_IdsM_01010] [SWS_IdsM_01011] [SWS_IdsM_01012]. Значения IdsM_Filters_ReportingModeType означают [SWS_IdsM_91013] SWS IdsM с. 91:

  • IDSM_REPORTING_MODE_OFF: событие отбрасывается.
  • IDSM_REPORTING_MODE_BRIEF / IDSM_REPORTING_MODE_DETAILED: отправка сообщения соответственно без или с контекстными данными.
  • …_BYPASSING_FILTERS: отправка сообщения в обход цепочки фильтров.

Только после Reporting Mode оценивается цепочка фильтров, назначенная данному SEv [SWS_IdsM_01001] [SWS_IdsM_01002]. Активированные фильтры выполняются в фиксированном порядке: Block State, Forward Every Nth, Event Aggregation, Event Threshold [SWS_IdsM_01004]. Если фильтр отбрасывает SEv, дальнейшая обработка прекращается [SWS_IdsM_01005] SWS IdsM с. 25. Цепочка фильтров должна содержать как минимум один фильтр [SWS_IdsM_CONSTR_00002]. Отдельные фильтры функционируют следующим образом:

  • Block State: BswM сообщает текущее состояние через IdsM_BswM_StateChanged. Если это состояние относится к числу указанных по ссылке IdsMBlockState, SEv отбрасывается [SWS_IdsM_01022] [SWS_IdsM_01023] SWS IdsM с. 28.
  • Forward Every Nth: первое и затем каждое n-е SEv пересылаются без изменений [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  • Aggregation: события SEv удерживаются в течение IdsMEventAggregationTimeInterval. В конце интервала дальше передается одно SEv с суммой всех счетчиков; контекстные данные и временная метка берутся по выбору из первого или последнего SEv [SWS_IdsM_01043] [SWS_IdsM_01046] [SWS_IdsM_01047] [SWS_IdsM_01048] [SWS_IdsM_01049] SWS IdsM с. 40.
  • Threshold: пока сумма счетчиков в интервале остается ниже IdsMEventThresholdNumber, события отбрасываются; при достижении порогового значения они пересылаются дальше. По окончании интервала счетчик сбрасывается [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063] SWS IdsM с. 41.

Диаграмма деятельности: сначала Reporting Mode принимает решение об отбрасывании, обходе или фильтрации. Затем SEv проходит активированные фильтры в фиксированном порядке, пока не будет отброшено или не станет QSEv. Источники: SWS IdsM с. 35, SWS IdsM с. 24, [SWS_IdsM_01004], [SWS_IdsM_01005], [SWS_IdsM_91013].

Обогащение и пересылка квалифицированных событий

События QSEv независимо от приемника имеют фиксированную структуру в соответствии с протоколом IDS [SWS_IdsM_01200]. Какие приемники используются, определяет конфигурация для каждого IdsMEvent [SWS_IdsM_01201] SWS IdsM с. 35. При IdsMSinkIdsR событие QSEv отправляется через PduR_IdsMTransmit как IDS Message [SWS_IdsM_01203] [SWS_IdsM_01498]. Перед отправкой в IdsR действуют ограничения на уровне экземпляра: ограничение частоты (Rate Limiting) ограничивает количество QSEv за интервал, ограничение трафика (Traffic Limiting) — количество байтов за интервал [SWS_IdsM_01070] [SWS_IdsM_01081] [SWS_IdsM_01091] SWS IdsM с. 32.

Способ передачи зависит от размера SWS IdsM с. 38:

  • Если сообщение IDS вместе с подписью помещается в Bus-PDU, используется IF-PDU [SWS_IdsM_01400]; подтверждение поступает через IdsM_TxConfirmation [SWS_IdsM_01500].
  • В противном случае используются TP-PDU [SWS_IdsM_01401]. PduR забирает данные по сегментам через IdsM_CopyTxData [SWS_IdsM_01501] и подтверждает через IdsM_TpTxConfirmation [SWS_IdsM_01502].
  • До подтверждения IdsM не вызывает PduR_IdsMTransmit повторно [SWS_IdsM_01499].

Диаграмма последовательности: после применения ограничений QSEv передается в зависимости от размера в виде IF- или TP-PDU. Следующая передача может начаться только после подтверждения. Источники: [SWS_IdsM_01070], [SWS_IdsM_01400], [SWS_IdsM_01401], [SWS_IdsM_01499], [SWS_IdsM_01501], [SWS_IdsM_01502].

Опционально IdsM подписывает каждое QSEv. Это активируется глобально с помощью задания CSM, на которое ссылается IdsMCsmJobReference. Подпись формируется через Csm_SignatureGenerate; при асинхронных заданиях CSM сообщает результат через IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01208] SWS IdsM с. 36. Приемник DEM/Sem в R20-11 помечен как DRAFT; он сохраняет сообщение IDS целиком [SWS_IdsM_01600] [SWS_IdsM_01602].

Временные метки включаются глобально через IdsMTimestampOption [SWS_IdsM_01100] [SWS_IdsM_01103] SWS IdsM с. 33. Действуют следующие правила SWS IdsM с. 34:

  • Если датчик не предоставляет временную метку, IdsM запрашивает ее сам: при «AUTOSAR» через StbM_GetCurrentTime, при «Custom» — через интерфейс IdsM_CustomTimestamp от SW-C [SWS_IdsM_01104] [SWS_IdsM_01107] [SWS_IdsM_01109] [SWS_IdsM_01111].
  • Временные метки, переданные датчиком, имеют приоритет и усекаются до 62 младших битов [SWS_IdsM_01108] [SWS_IdsM_01110].
  • При «None» даже переданные временные метки игнорируются [SWS_IdsM_01106].

Открытый вопрос спецификации: [SWS_IdsM_01112] требует, чтобы бит опции временной метки был равен 0, если API временных меток используются без параметра временной метки. Как это соотносится с [SWS_IdsM_01101], текст оставляет без ответа.

Диаграмма деятельности: источник временной метки определяется из IdsMTimestampOption и переданного параметра. Источники: SWS IdsM с. 87, [SWS_IdsM_01104], [SWS_IdsM_01106], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110].

Reporting Mode во время выполнения: диагностика и сохраняемость в NvM

Если активен IdsMDiagnosticSupport, Reporting Mode можно считывать и изменять через DCM [SWS_IdsM_01800] [SWS_IdsM_01900] [SWS_IdsM_02000] SWS IdsM с. 40:

  • Чтение происходит в два этапа: IdsM_Dcm_GetReportingMode_Start запускает процедуру, IdsM_Dcm_GetReportingMode_RequestResults возвращает результат через указатель [SWS_IdsM_02001] [SWS_IdsM_02002].
  • Изменение выполняется через IdsM_Dcm_SetReportingMode_Start. Недействительный режим или недействительный Event-ID приводят к E_NOT_OK с DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01901] [SWS_IdsM_01902] [SWS_IdsM_01903].

После успешного изменения IdsM инициирует NvM_WriteBlock [SWS_IdsM_01701]. Если сохранение завершается ошибкой, он возвращает режим к предыдущему значению и отвечает DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905]. При запуске он считывает сохраненный режим. Для этого блок NvM должен содержаться в NvM_ReadAll; при отсутствии значений в NvM действует конфигурация [SWS_IdsM_01703] [SWS_IdsM_01704] [SWS_IdsM_01705] SWS IdsM с. 39.

Диаграмма последовательности: чтение выполняется в два этапа через Start и RequestResults. При изменении сначала выполняется проверка, затем сохранение, а в случае ошибки — откат. Источники: [SWS_IdsM_02001], [SWS_IdsM_02002], [SWS_IdsM_01902], [SWS_IdsM_01903], [SWS_IdsM_01701], [SWS_IdsM_01904], [SWS_IdsM_01905].

Поведение при ошибке

При активном IdsMDevErrorDetect модуль IdsM сообщает об ошибках разработки в DET. Кодами ошибок являются IDSM_E_PARAM_INVALID (0x0A), IDSM_E_PARAM_POINTER (0x0B), IDSM_E_PARAM_LENGTH (0x0C), IDSM_E_UNINIT (0x0D) и IDSM_E_ALREADY_INITIALIZED (0x0E) [SWS_IdsM_02003]. Внимание: [SWS_IdsM_00203] указывает для вызовов в неинициализированном состоянии IDSM_E_PARAM_UNINIT. Этот код отсутствует в таблице ошибок; вместо него там указан IDSM_E_UNINIT. Проверки параметров в деталях:

  • Неизвестный securityEventId в API отправки сообщений, а также count = 0 в вариантах со счетчиком приводят к IDSM_E_PARAM_INVALID [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106] SWS IdsM с. 42.
  • contextDataSize, превышающий наибольший IdsMContextDataBufferSize, приводит к IDSM_E_PARAM_LENGTH [SWS_IdsM_02107] [SWS_IdsM_02108] [SWS_IdsM_02109] SWS IdsM с. 43.
  • Недопустимый NULL_PTR приводит к IDSM_E_PARAM_POINTER SWS IdsM с. 42.

Об узких местах во время выполнения IdsM сообщает через собственные внутренние SEv, если они сконфигурированы. Они имеют собственные буферы и не фильтруются фильтрами уровня экземпляра [SWS_IdsM_91015] [SWS_IdsM_00802] [SWS_IdsM_00803] SWS IdsM с. 24. Существует три внутренних SEv:

  • нет доступного Event Buffer [SWS_IdsM_00703]
  • нет доступного Context Data Buffer; в этом случае SEv обрабатывается дальше без контекстных данных [SWS_IdsM_00707] [SWS_IdsM_00708]
  • превышено ограничение трафика [SWS_IdsM_01094]

Если при диагностическом изменении сохранение завершается сбоем, применяется описанный выше откат [SWS_IdsM_01905].

IdsM_CopyTxData функция

Эта функция вызывается для получения передаваемых данных сегмента I-PDU (N-PDU). Каждый вызов этой функции предоставляет следующую часть данных I-PDU, если только retry->TpDataState не равен TP_ DATARETRY. В этом случае функция перезапускается для копирования данных, начиная со смещения от текущей позиции, указанной retry->TxTpDataCnt. Размер оставшихся данных записывается в позицию, указанную в AvailableDataPtr.

BufReq_ReturnType IdsM_CopyTxData (PduIdType id, const PduInfoType* info, const RetryInfoType* retry, PduLengthType* availableDataPtr);
