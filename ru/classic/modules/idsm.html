Собирает события безопасности от сенсоров, фильтрует их и перенаправляет квалифицированные события в приемники.

IdsM собирает Security Events, о которых сообщают модули BSW, CDD и SW-C, буферизует их и обрабатывает асинхронно в IdsM_MainFunction [SWS_IdsM_00702]. Reporting Mode и цепочка фильтров из фильтров состояния блокировки (Block State), прореживания (Sampling), агрегации и пороговых значений преобразуют их в квалифицированные события [SWS_IdsM_01004]. Они передаются через PduR в IdsR или сохраняются в DEM/Sem. Метка времени, подпись и диагностический доступ опциональны. Значение контекстных данных IdsM не оценивает; реагирование на атаки находится за пределами модуля.

IdsM принимает Security Events (SEv) от сенсоров безопасности, то есть от BSW-модулей, CDD и SW-C. С помощью цепочки фильтров он преобразует их в Qualified Security Events (QSEv) [SWS_IdsM_00902]. Модуль отправляет QSEv через PduR в IdsR, сохраняет их в DEM/Sem или и то, и другое [SWS_IdsM_01202] [SWS_IdsM_01600]. Значение контекстных данных он не оценивает. Реагирование на атаки находится за пределами модуля, например в SOC [SWS_IdsM_CONSTR_00001].

Контекстная диаграмма: IdsM соединяет сообщающие сенсоры с приемниками PduR/IdsR и DEM/Sem. BswM, StbM, CSM, DCM и NvM подключены опционально. Источники: SWS IdsM с. 20, [SWS_IdsM_91023].

Сенсоры сообщают через IdsM_SetSecurityEvent или один из пяти вариантов с контекстными данными (до 1500 байт), счетчиком и меткой времени [SWS_IdsM_00300] [SWS_IdsM_00404] [SWS_IdsM_00501]. При этом они всегда используют символическое имя IdsMEvent [SWS_IdsM_00607]. Служба отправки сообщений лишь буферизует SEv. Сама обработка выполняется асинхронно в IdsM_MainFunction [SWS_IdsM_00702]. Если свободный Event Buffer отсутствует, IdsM инициирует внутренний SEv, если таковой сконфигурирован [SWS_IdsM_00703].

Квалификация начинается с Reporting Mode. Возможные значения: OFF, BRIEF, DETAILED и варианты, обходящие фильтры [SWS_IdsM_01002] [SWS_IdsM_91013]. Затем активные фильтры выполняются в фиксированном порядке: Block State, Forward Every n-th, Aggregation, Threshold [SWS_IdsM_01004]. Если какой-либо фильтр отбрасывает SEv, обработка завершается [SWS_IdsM_01005]. Перед отправкой в IdsR дополнительно действуют ограничения частоты и трафика [SWS_IdsM_01070]. Они, по-видимому, распространяются и на режимы обхода (интерпретация).

Диаграмма деятельности: сначала Reporting Mode, затем цепочка фильтров, в конце — ограничения экземпляра перед IdsR. Источники: SWS IdsM с. 35, [SWS_IdsM_01004], [SWS_IdsM_01070]

Опционально можно подключить дополнительные функции [SWS_IdsM_01100] [SWS_IdsM_01204] [SWS_IdsM_01901] [SWS_IdsM_01702]:

  • Метка времени из StbM или из приложения
  • Подпись через CSM
  • Чтение и изменение Reporting Mode через DCM, с сохранением в NvM и откатом при ошибках

Об ошибках разработки IdsM сообщает в DET только при активном IdsMDevErrorDetect [SWS_IdsM_02003]. Приемник DEM/Sem в R20-11 имеет статус DRAFT [SWS_IdsM_01601].

Роль: от зарегистрированного события безопасности к квалифицированному событию

Intrusion Detection System Manager (IdsM) собирает Security Events (SEv). Их распознают и передают сенсоры безопасности, то есть BSW-модули, Complex Device Drivers или SW-C SWS IdsM с. 10. IdsM проверяет каждое SEv по конфигурируемой последовательности фильтров — цепочке фильтров. Если SEv проходит эту проверку, оно становится Qualified Security Event (QSEv) [SWS_IdsM_00902]. Дальнейшей обработке подлежат только QSEv. Они передаются через PduR в IdsR на другом блоке управления, сохраняются в DEM/Sem или и то, и другое [SWS_IdsM_01202] [SWS_IdsM_01600] SWS IdsM с. 35.

Граница системы очерчена узко. IdsM не знает значения контекстных данных и поэтому не решает самостоятельно, скомпрометирована ли система. Распознавание и реагирование находятся за пределами модуля, например в SOC [SWS_IdsM_CONSTR_00001]. Обязательные интерфейсы к другим модулям отсутствуют [SWS_IdsM_91023]. Каждое сопряжение подключается через конфигурацию. Это подтверждается условными включениями заголовочных файлов:

  • Det.h при IdsMDevErrorDetect
  • Dem.h при IdsMSinkDem
  • Dcm.h при IdsMDiagnosticSupport
  • NvM.h при IdsMNvmBlockDescriptor
  • PduR.h при IdsMSinkIdsR

Подтверждения для данных включений: с [SWS_IdsM_00101] по [SWS_IdsM_00105].

Контекстная диаграмма: IdsM находится между сообщающими сенсорами и приемниками PduR/IdsR, а также DEM/Sem. BswM, StbM, CSM, DCM и NvM предоставляют рабочее состояние, время, подпись и диагностический доступ. Источники: SWS IdsM с. 20, SWS IdsM с. 14, [SWS_IdsM_01022], [SWS_IdsM_01104], [SWS_IdsM_01206], [SWS_IdsM_01701]

Запуск, идентификация событий и интерфейсы отправки сообщений

IdsM_Init инициализирует все внутренние переменные и переводит модуль в состояние «инициализирован» [SWS_IdsM_00202] [SWS_IdsM_91001]. Только IdsM_Init и IdsM_GetVersionInfo разрешено вызывать до этого момента времени SWS IdsM с. 21. Повторный вызов IdsM_Init не инициализирует модуль во второй раз [SWS_IdsM_00204].

Диаграмма состояний: модуль имеет два состояния. Ошибочные вызовы в обоих состояниях сообщают об ошибке в DET только при активном обнаружении ошибок разработки. Источники: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], SWS IdsM с. 21

Каждое SEv идентифицируется тремя идентификаторами и именем события [SWS_IdsM_00600]:

  • IdsMExternalEventId глобально уникален и берется из Security Extract. Значение 0xFFFF недопустимо [SWS_IdsM_00603] [SWS_IdsM_00604].
  • IdsMSensorInstanceId по умолчанию равен 0, если существует только один экземпляр модуля [SWS_IdsM_00608].
  • IdsMInternalEventId модуль IdsM вычисляет внутренне [SWS_IdsM_00601].

Сенсоры сообщают исключительно через символическое имя контейнера IdsMEvent. Им не разрешается полагаться на внутреннее значение [SWS_IdsM_00602] [SWS_IdsM_00607]. Для отправки сообщений доступно шесть служб:

Какой интерфейс применяется, зависит от IdsMAdditionalParameterOption (None, Count, CountTimestamp) [SWS_IdsM_91027] [SWS_IdsM_91028] [SWS_IdsM_01301] [SWS_IdsM_01303]. В R20-11 эти службы являются нормативными. Более поздние релизы обозначают их как OBSOLETE SWS IdsM с. 67.

Буферизация и асинхронная обработка в IdsM_MainFunction

Службы отправки сообщений не обрабатывают SEv немедленно. IdsM сначала помещает его в Event Buffer. Фильтрация и пересылка осуществляются позже и асинхронно в циклически вызываемой IdsM_MainFunction [SWS_IdsM_00702] [SWS_IdsM_00901] [SWS_IdsM_91000]. Число Event Buffers (IdsMNumberOfEventBuffers) конфигурируемо [SWS_IdsM_00701]. В качестве ориентира спецификация рекомендует количество экземпляров фильтра агрегации плюс верхний предел параллельно обрабатываемых событий SWS IdsM с. 24.

Диаграмма последовательности: сообщение возвращает управление сразу после буферизации. Метка времени, фильтрация и пересылка выполняются только в IdsM_MainFunction. Источники: SWS IdsM с. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01107]

Контекстные данные располагаются в собственных Context Data Buffers с конфигурируемым размером до 1500 байт [SWS_IdsM_00704] SWS IdsM с. 122. IdsM выбирает буфер такого же или следующего большего размера и связывает его с Event Buffer [SWS_IdsM_00705] [SWS_IdsM_00706]. SEv без контекстных данных не занимает такой буфер [SWS_IdsM_00709]. Для собственных внутренних SEv модуля IdsM предусмотрены отдельные раздельные буферы [SWS_IdsM_00802].

Диаграмма деятельности: так распределяются буферы при поступлении SEv. Если контекстный буфер отсутствует, SEv обрабатывается без контекстных данных. Если отсутствует Event Buffer, обработка SEv невозможна. Источники: [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708], [SWS_IdsM_91015], SWS IdsM с. 27.

Квалификация: Reporting Mode, цепочка фильтров и границы экземпляра

Сначала IdsM анализирует Reporting Mode. Каждое SEv имеет ровно один фильтр Reporting Mode. Этот фильтр обязателен, привязан непосредственно к SEv и не относится к цепочке фильтров [SWS_IdsM_01010] [SWS_IdsM_01011]. Начальное значение берется из IdsMReportingModeFilter [SWS_IdsM_01012]. Цепочка фильтров следует только после этого [SWS_IdsM_01002]. IdsM_Filters_ReportingModeType поддерживает следующие режимы [SWS_IdsM_91013]:

  • IDSM_REPORTING_MODE_OFF: событие не передается.
  • IDSM_REPORTING_MODE_BRIEF: сообщение без контекстных данных.
  • IDSM_REPORTING_MODE_DETAILED: сообщение с контекстными данными.
  • Оба варианта …_BYPASSING_FILTERS: сообщение как BRIEF или DETAILED, но без фильтрации.

Цепочка фильтров сопоставлена с SEv [SWS_IdsM_01001] [SWS_IdsM_00903]. Каждому IdsMFilterChain требуется как минимум один фильтр [SWS_IdsM_CONSTR_00002]. Активные фильтры выполняются в фиксированном порядке [SWS_IdsM_01004]. Если фильтр отбрасывает SEv, анализ немедленно прекращается. В противном случае SEv переходит к следующему фильтру [SWS_IdsM_00904] [SWS_IdsM_00905] [SWS_IdsM_01005]. Четыре фильтра в этом порядке:

  1. Block State: BswM сообщает о текущем состоянии через IdsM_BswM_StateChanged в виде битовой маски типа IdsM_Filters_BlockStateType. Если это состояние указано по ссылке в IdsMBlockState, фильтр отбрасывает SEv [SWS_IdsM_01022] [SWS_IdsM_01023] [SWS_IdsM_91017]. Фильтр может ссылаться максимум на 16 состояний SWS IdsM с. 85.
  2. Forward Every n-th: первое SEv пропускается, затем каждое n-е согласно IdsMNthParameter. Данные при этом остаются неизменными [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  3. Event Aggregation: во время интервала фильтр ничего не передает далее. В конце интервала формируется одно-единственное SEv с суммирующим счетчиком [SWS_IdsM_01043] [SWS_IdsM_01046]. Контекстные данные и метка времени берутся из первого или последнего SEv интервала в зависимости от IdsMContextDataSourceSelector [SWS_IdsM_01047] [SWS_IdsM_01049]. Пример приведен в SWS IdsM с. 40.
  4. Event Threshold: фильтр отбрасывает SEv до тех пор, пока сумма счетчика в текущем интервале остается ниже IdsMEventThresholdNumber. По истечении интервала сумма сбрасывается [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063]. Пример приведен в SWS IdsM с. 41.

Все интервалы кратны IdsMMainFunctionPeriod. Интервал агрегации и пороговый интервал отсчитываются от первого вызова Main Function [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01065].

Перед отправкой в IdsR действуют два ограничения для всего экземпляра IdsM [SWS_IdsM_01070]:

  • Ограничение частоты разрешает не более IdsMRateLimitationMaximumEvents QSEv за интервал [SWS_IdsM_01081].
  • Ограничение трафика разрешает не более IdsMTrafficLimitationMaximumBytes байт за интервал [SWS_IdsM_01091] [SWS_IdsM_01093].

Внутренние SEv модуля IdsM не проходят эти фильтры экземпляра. Однако специфичные для события фильтры у них могут быть [SWS_IdsM_00803] [SWS_IdsM_00804]. Интерпретация: режимы обхода обходят только цепочку фильтров. Ограничения частоты и трафика, по-видимому, распространяются и на них, поскольку [SWS_IdsM_01070] требует соблюдения этих ограничений перед любой передачей в IdsR.

Диаграмма деятельности: сначала Reporting Mode, затем фильтры в фиксированном порядке, в конце — ограничения экземпляра перед IdsR. Несконфигурированные фильтры опускаются. Источники: SWS IdsM с. 35, [SWS_IdsM_01002], [SWS_IdsM_01004], [SWS_IdsM_01070], [SWS_IdsM_91013]

Метка времени, IDS-сообщение и приемники

Метка времени опциональна и управляется глобально через IdsMTimestampOption [SWS_IdsM_01100]:

  • None: функция отключена. Переданные метки времени игнорируются [SWS_IdsM_01103] [SWS_IdsM_01106].
  • AUTOSAR: источником является StbM_GetCurrentTime [SWS_IdsM_01104] [SWS_IdsM_01107].
  • Custom: IdsM запрашивает приложение через интерфейс IdsM_CustomTimestamp (операция Get) на порту CustomTimestamp [SWS_IdsM_01109] [SWS_IdsM_01111].

Если сенсор сам передает метку времени, она имеет приоритет [SWS_IdsM_01108]. IdsM усекает ее до 62 младших битов [SWS_IdsM_01110]. Согласно диаграммам выполнения, IdsM определяет метку времени в Main Function для всех буферизованных событий SWS IdsM с. 87.

Диаграмма деятельности: как выбирается источник метки времени в зависимости от IdsMTimestampOption. Источники: [SWS_IdsM_01106], [SWS_IdsM_01107], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110], SWS IdsM с. 86

QSEv имеет одинаковую структуру независимо от того, в какой приемник оно направляется [SWS_IdsM_01200]. IDS-сообщение состоит из Event Frame и, опционально, Timestamp, Context Data и Signature PRS IDS с. 11. Какие приемники использует событие, определяется конфигурацией IdsMEvent [SWS_IdsM_01201].

Подпись опциональна. Она активируется глобально, как только сконфигурирован IdsMCsmJobReference. Она инициируется через Csm_SignatureGenerate. Для синхронных задач подпись готова немедленно, для асинхронных результат сообщает IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01207] [SWS_IdsM_01208].

Для приемника IdsR модуль IdsM передает данные через PduR_IdsMTransmit [SWS_IdsM_01498]. Если сообщение помещается в шинную PDU, используется IF-PDU, в противном случае — TP-PDU [SWS_IdsM_01400] [SWS_IdsM_01401]. Новое задание на передачу выдается только после подтверждения предыдущего [SWS_IdsM_01499]. Приемник DEM/Sem сохраняет полное IDS-сообщение. В R20-11 он имеет статус DRAFT [SWS_IdsM_01601] [SWS_IdsM_01602].

Диаграмма последовательности: сначала опциональная подпись через CSM, затем передача в виде IF- или сегментированной TP-PDU с подтверждением. Источники: [SWS_IdsM_01207], [SWS_IdsM_01208], [SWS_IdsM_01500], [SWS_IdsM_01501], [SWS_IdsM_01502], SWS IdsM с. 49

Диагностическая реконфигурация и персистентность Reporting Mode

Диагностический доступ опционален и активируется через IdsMDiagnosticSupport [SWS_IdsM_01800].

  • Изменение: DCM вызывает IdsM_Dcm_SetReportingMode_Start с новым значением [SWS_IdsM_01901] [SWS_IdsM_91008]. Если режим или ID события недопустимы, IdsM отвечает с E_NOT_OK и DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01902] [SWS_IdsM_01903].
  • Чтение: DCM сначала вызывает IdsM_Dcm_GetReportingMode_Start, а затем с помощью IdsM_Dcm_GetReportingMode_RequestResults забирает результат [SWS_IdsM_02001] [SWS_IdsM_02002].

После успешного изменения IdsM инициирует NvM_WriteBlock [SWS_IdsM_01701]. Если сохранение завершается сбоем, он восстанавливает предыдущее значение и сообщает DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905].

При запуске IdsM использует сохраненные значения. Если они отсутствуют, действует конфигурация [SWS_IdsM_01703] [SWS_IdsM_01704]. Блок NvM должен содержаться в NvM_ReadAll и называется IdsM_NvMRamBlockData или IdsM_NvMRomBlockData [SWS_IdsM_01705] [SWS_IdsM_01706] [SWS_IdsM_01707]. Поведение при ошибке

Ошибки разработки IdsM сообщает в DET только при активном IdsMDevErrorDetect. Коды ошибок приведены в [SWS_IdsM_02003]:

  • IDSM_E_PARAM_INVALID: все шесть сервисов передачи сообщений сообщают об этой ошибке при неизвестном Event-ID. Варианты со счетчиком дополнительно сообщают о ней при count = 0 [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106].

О нехватке ресурсов IdsM сообщает как о собственных внутренних SEv, если они сконфигурированы [SWS_IdsM_91015]:

  • нет свободного Event Buffer (ID 46) [SWS_IdsM_00703]
  • нет подходящего Context Data Buffer (ID 47). В этом случае SEv обрабатывается без контекстных данных [SWS_IdsM_00707] [SWS_IdsM_00708]
  • превышено ограничение трафика (ID 48) [SWS_IdsM_01094]

Отклонение SEv фильтром является штатным поведением, а не ошибкой [SWS_IdsM_00904]. Ошибка отправки возвращается в виде E_NOT_OK в подтверждении [SWS_IdsM_91009]. Правило повтора с IdsMTransmissionRetryDelay появляется только в R25-11 SWS IdsM с. 51.

Тип данных IdsM_Filters_ReportingModeType основан на базовом типе uint8 и предоставляется через заголовочный файл IdsM_Types.h для программных компонентов [SWS_IdsM_91013]. Он описывает стандартизированные режимы отчетности, применяемые в фильтре режимов отчетности в Intrusion Detection System Manager (IdsM) для целевой обработки и пересылки событий безопасности [SWS_IdsM_91013].

С помощью определенных значений перечисления точно контролируется, сообщается ли событие и какой уровень детализации при этом используется [SWS_IdsM_91013]:

  • IDSM_REPORTING_MODE_OFF (0x00): событие подавляется и не передается вышестоящим инстанциям [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_BRIEF (0x01): событие передается без дополнительных контекстных данных в компактной форме [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_DETAILED (0x02): событие передается подробно с включением всех релевантных контекстных данных [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_BRIEF_BYPASSING_FILTERS (0x03): событие обходит последующие ступени фильтрации и передается нефильтрованным без контекстных данных [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_DETAILED_BYPASSING_FILTERS (0x04): событие обходит последующие ступени фильтрации и передается нефильтрованным, включая все контекстные данные [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_INVALID (0xFF): обозначает недействительный режим отчета в пределах диапазона значений [SWS_IdsM_91013].

Таким образом, эти значения сочетают в себе два функциональных измерения управления: степень детализации через контекстные данные и целенаправленный обход регулярных механизмов фильтрации путем байпасирования (bypassing) [SWS_IdsM_91013]. Это позволяет IdsM дифференцированно обрабатывать инциденты безопасности в зависимости от критичности и конфигурации фильтров [SWS_IdsM_91013].
