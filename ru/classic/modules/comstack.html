Роль ComStack_Types: общий словарь типов коммуникационного стека

Модуль «comstack» не является исполняемым компонентом. Через ComStack_Types.h он предоставляет типы данных, с помощью которых модули коммуникационного стека Classic описывают PDU, буферы и каналы. Все девять типов данного релиза, согласно спецификации, являются «Available via ComStack_Types.h», от PduInfoType до NetworkHandleType ([SWS_COMTYPE_00011], [SWS_COMTYPE_00038]). PduLengthType должен использоваться во всем AUTOSAR-Com-стеке электронного блока управления, за исключением драйверов шины ([SWS_COMTYPE_00008], SWS ComStackTypes с. 16). Тем самым очерчена граница системы: выше драйверов шины интерфейсы, маршрутизаторы, транспортные протоколы и верхние уровни используют одни и те же типы. RTE также импортирует для колбэков Large-Data среди прочего BufReq_ReturnType, PduIdType, PduInfoType, PduLengthType и RetryInfoType из ComStack_Types.h (SWS RTE с. 833).

Относительно источников: цитируемые фрагменты документов взяты преимущественно из релизов с R23-11 по R25-11. Только диаграмма Retry спецификации J1939Tp подтверждена и для R20-11. Нормативными для R20-11 являются требования. Отклонения указаны в тексте, например, в отношении PNCHandleType ([SWS_COMTYPE_00036], SWS ComStackTypes с. 17).

Контекстная диаграмма: ComStack_Types.h обеспечивает общими типами все модули стека выше драйверов шины; границы диапазонов формируются на основе конфигурации EcuC. Источники: [SWS_COMTYPE_00005], [SWS_COMTYPE_00008], [SWS_COMTYPE_00038], TPS EcuC с. 205, SWS RTE с. 833

Идентификация PDU: PduIdType и локальные для модуля Handle-ID

PduIdType в R20-11 может варьироваться как uint16 или uint8. Размер определяется наибольшим количеством PDU, которое использует отдельный программный модуль. Генератор формирует границу диапазона на основе конфигурации EcuC в ComStack_Cfg.h ([SWS_COMTYPE_00005]). В EcuC этому соответствует параметр PduIdTypeEnum со значениями UINT8 и UINT16. Если хотя бы один модуль управляет более чем 256 PDU, требуется uint16 (ECUConfiguration с. 153).

Значение PduIdType не является общесистемным ключом. Это дескриптор внутри каждого вызываемого модуля: каждый BSW-модуль с PDU-API ведет собственный список PDU-ID в качестве таблицы поиска (SWS PduR с. 33). Маршрутизатор PDU идентифицирует путь маршрутизации по исходному ID и целевым ID. Он преобразует ID в тракте передачи и в тракте подтверждения, передавая значение PduInfoType без изменений (SWS PduR с. 33). Чтобы смежные модули ссылались на одну и ту же PDU, EcuC определяет межмодульную EcucPduCollection с глобальными Pdu-объектами (TPS EcuC с. 190).

Диаграмма последовательности: PduR преобразует значения PduIdType для каждого целевого модуля, передает PduInfoType без изменений и перенаправляет подтверждение с преобразованным обратно ID в Com. Источники: SWS PduR с. 33, SWS PduR с. 33, [SWS_COMTYPE_00005]

Содержимое PDU: PduInfoType, PduLengthType и метаданные

PduInfoType объединяет базовую информацию о PDU любого типа. SduDataPtr указывает на полезные данные, MetaDataPtr — на метаданные, а SduLength задает длину в байтах ([SWS_COMTYPE_00011], SWS ComStackTypes с. 17). Длина имеет тип PduLengthType. Он генерируется как uint8, uint16 или uint32 в зависимости от максимальной длины PDU в электронном блоке управления. Без сегментации разрядность определяется размером фрейма шины, для FlexRay — максимум 255 байт и, следовательно, uint8. При наличии сегментации разрядность определяется максимальной длиной сегментированной N-PDU ([SWS_COMTYPE_00008], SWS ComStackTypes с. 16).

Метаданными являются, например, CAN-ID, Socket-ID или диагностические адреса. Они состоят из статически сконфигурированной для каждой PDU последовательности элементов. Элементы размером более 8 бит представлены в порядке байтов платформы ([SWS_COMTYPE_00011]). Порядок и позиция элементов определяются конфигурацией EcuC глобальной PDU. Сортировка по длине делает выравнивание избыточным (SWS BSWGeneral с. 67). Пример применения: для группы сокетных соединений SoAd передает данные только по тому соединению, которое указывает PduInfoType.MetaDataPtr (SWS SoAd с. 30).

Для времени жизни указателей действует эксплуатационное правило: при индикации приема переданный указатель данных действителен только до возврата из функции индикации (SWS CanNm с. 73). Длина 0 имеет несколько специальных значений. Вызов CopyRxData с SduLength 0 опрашивает свободный буфер приема верхнего уровня; SduDataPtr в этом случае может быть NULL_PTR (SWS DoIP с. 77). При передаче SduLength 0 обозначает I-PDU неизвестной длины. PduR передает эту длину всем целевым TP-модулям (SWS PduR с. 43).

Согласование буфера при приеме TP: BufReq_ReturnType

BufReq_ReturnType хранит результат запроса буфера. Значения жестко заданы: BUFREQ_OK (0), BUFREQ_E_NOT_OK (1), BUFREQ_E_BUSY (2) и BUFREQ_E_OVFL (3). В случае BUFREQ_E_BUSY запрашивающая сторона должна повторять запрос в течение определенного времени ([SWS_COMTYPE_00012], SWS ComStackTypes с. 19).

Прием TP выполняется в три шага:

  1. Транспортный протокол сообщает с помощью PduR_<User:LoTp>StartOfReception общую длину TpSduLength и данные первого фрейма. Через bufferSizePtr он получает обратно доступный размер буфера и вычисляет на его основе размер блока.
  2. Он передает сегменты дальше с помощью CopyRxData.
  3. Он завершает прием с помощью RxIndication (SWS PduR с. 92).

BUFREQ_OK означает здесь «соединение принято», даже если в качестве размера буфера сообщается 0 (SWS PduR с. 92). FlexRay-AR-TP сам не содержит буферов сообщений. Он обменивается данными с верхним уровнем по частям (SWS FrArTp с. 50).

Диаграмма последовательности: прием TP начинается с StartOfReception, доставляет данные через CopyRxData и завершается RxIndication; если запуск одиночного фрейма отклонен, RxIndication не следует. Источники: SWS FrArTp с. 50, SWS FrArTp с. 50, SWS PduR с. 92, [SWS_COMTYPE_00012]

Передача с повтором: RetryInfoType и TpDataStateType

При пофрагментной передаче транспортный протокол передает с CopyTxData структуру RetryInfoType. Она состоит из TpDataState и TxTpDataCnt; последний представляет собой смещение повторно передаваемых байтов ([SWS_COMTYPE_00037], SWS ComStackTypes с. 20). Эти три состояния означают следующее ([SWS_COMTYPE_00027], SWS ComStackTypes с. 19):

  • TP_DATACONF: все ранее скопированные данные подтверждены и могут быть удалены из TP-буфера.
  • TP_DATARETRY: уже скопированные данные необходимо предоставить повторно, начиная со смещения TxTpDataCnt.
  • TP_CONFPENDING: ранее скопированные данные должны быть сохранены.

Диаграмма Retry спецификации SAE-J1939-TP иллюстрирует это взаимодействие. Для каждого блока первый пакет запрашивается с TP_DATACONF, последующие — с TP_CONFPENDING. Если теряется TP.DT, TP возвращается к первому пакету блока. Затем он выполняет повторный запрос с TP_DATARETRY; при этом TxTpDataCnt является смещением относительно начала блока (SWS J1939Tp с. 55). FrArTp также устанавливает TP_CONFPENDING при несегментированной передаче с активированным Retry (SWS FrArTp с. 50).

Диаграмма последовательности: для каждого блока TpDataState управляет тем, подтверждаются ли данные, удерживаются или копируются повторно с начала блока. Источники: SWS J1939Tp с. 55, [SWS_COMTYPE_00027], [SWS_COMTYPE_00037]

Как верхний уровень реагирует на это состояние, демонстрирует прямой TP-шлюз PduR для одиночных фреймов. При TP_DATACONF, TP_CONFPENDING или отсутствии указателя RetryInfoType он копирует SduLength байт. При TP_DATARETRY он предварительно возвращает позицию назад на TxTpDataCnt байт (SWS PduR с. 57). Не каждый верхний уровень обрабатывает информацию о повторе: в колбэках LdCom параметр retry, согласно спецификации, не обрабатывается модулем LdCom и его верхним уровнем (SWS LdCom с. 34). Начиная с AUTOSAR 4.3.1, параметр в PduR_<User:LoTp>CopyTxData является указателем на const RetryInfoType (SWS PduR с. 3).

Диаграмма деятельности: PduR на основе TpDataState решает, копировать ли данные напрямую, вернуть позицию назад или отклонить запрос. Источники: SWS PduR с. 57, [SWS_COMTYPE_00027], [SWS_COMTYPE_00012]

Каналы, подсети и изменяемые параметры TP

NetworkHandleType хранит идентификатор коммуникационного канала. Он представляет собой отсчитываемый от нуля uint8 с диапазоном значений 0..255 ([SWS_COMTYPE_00038], SWS ComStackTypes с. 20). В случае Mirror_GetNetworkId он обозначает ComM-канал, в случае CanSM_TxTimeoutException — соответствующую сеть CAN (SWS Mirror с. 78, SWS CanSM с. 87). Колбэки управления сетью, такие как Nm_RemoteSleepIndication, также идентифицируют NM-канал с помощью этого типа (SWS Nm с. 89).

PNCHandleType хранит идентификатор кластера частичной сети. В R20-11 он является производным от uint8 ([SWS_COMTYPE_00036]). Представленный же фрагмент документа из R23-11 указывает в качестве базового типа uint16 (SWS ComStackTypes с. 17). Для R20-11 действует версия требований uint8.

TPParameterType указывает параметр, который должен изменяться во время выполнения. Допустимыми значениями являются TP_STMIN (Separation Time), TP_BS (Block Size) и TP_BC (управление полосой пропускания транспортного протокола FlexRay) ([SWS_COMTYPE_00031], SWS ComStackTypes с. 18). Модули ограничивают использование. J1939Tp_ChangeParameter принимает только TP_BS со значениями до 255 (SWS J1939Tp с. 42). FrArTp отклоняет изменения во время текущего приема со статусом E_NOT_OK (SWS FrArTp с. 49).

Поведение при ошибке

Сами типы не обладают поведением при ошибках. Однако они передают результаты, на основании которых реагируют модули ([SWS_COMTYPE_00012]). При несегментированной передаче FrArTp действует следующее:

  • Если PduR_FrArTpCopyTxData возвращает BUFREQ_E_BUSY, TP повторяет вызов до истечения FrArTpTimeCs.
  • При BUFREQ_E_NOT_OK или по истечении времени он прерывает операцию и вызывает PduR_FrArTpTxConfirmation с E_NOT_OK.
  • Если PduR_FrArTpStartOfReception возвращает для одиночного фрейма BUFREQ_E_NOT_OK или BUFREQ_E_OVFL, прием немедленно завершается без PduR_FrArTpRxIndication (SWS FrArTp с. 50).

Диаграмма деятельности: BUFREQ_E_BUSY приводит к повторным попыткам до наступления таймаута; BUFREQ_E_NOT_OK и BUFREQ_E_OVFL приводят к прерыванию. Источники: SWS FrArTp с. 50, SWS FrArTp с. 44, [SWS_COMTYPE_00012]

В прямом TP-шлюзе для TP_DATARETRY действуют два правила. Если PduR не может вернуть позицию назад, он отвечает BUFREQ_E_NOT_OK и оставляет позицию и данные без изменений. Если после возврата позиции назад данные отсутствуют, он отвечает BUFREQ_E_BUSY (SWS PduR с. 57). В шлюзе On-the-fly PduR не поддерживает повторную передачу уже отправленных данных (SWS PduR с. 58). При Multicast-TP-маршрутизации он в ответ на TP_DATARETRY, согласно фрагменту документа, возвращает E_NOT_OK (SWS PduR с. 41).

Кроме того, PduR не предпринимает собственных мер по обработке ошибок. Она передает ошибки из возвращаемых значений вышестоящему модулю-источнику, который отвечает за их обработку (SWS PduR с. 46, SWS PduR с. 49).

Communication Stack Types (ComStack_Types)

Стандартизированные типы, идентификаторы PDU, длины и типы запросов к буферу (PduIdType, PduLengthType, PduInfoType, BufReq_ReturnType), используемые на всех уровнях связи.

Типы — Обзор

  • typedef PduIdType This type is used within the entire AUTOSAR Com Stack except for bus drivers.
  • typedef PduLengthType This type shall be used within the entire AUTOSAR Com Stack of an ECU except for bus drivers.
  • struct PduInfoType Variables of this type shall be used to store the basic information about a PDU of any type, namely a pointer variable...
  • typedef PNCHandleType Used to store the identifier of a partial network cluster.
  • enum TPParameterType Specify the parameter to which the value has to be changed (BS or STmin).
  • enum BufReq_ReturnType Variables of this type shall be used to store the result of a buffer request.
  • enum TpDataStateType Variables of this type shall be used to store the state of TP buffer.
  • struct RetryInfoType Variables of this type shall be used to store the information about Tp buffer handling.
  • typedef NetworkHandleType Variables of the type Network Handle Type shall be used to store the identifier of a communication channel.

typedef uint16 PduLengthType;
PNCHandleType тип

Используется для хранения идентификатора частичного сетевого кластера.

typedef uint8 PNCHandleType;
RetryInfoType тип

Переменные этого типа должны использоваться для хранения информации об обработке буфера Tp.

typedef struct { TpDataStateType TpDataState; PduLengthType TxTpDataCnt; } RetryInfoType;
TpDataStateType тип

Переменные этого типа должны использоваться для хранения состояния буфера TP.

typedef enum { TP_DATACONF, TP_DATARETRY, TP_CONFPENDING } TpDataStateType;
TPParameterType тип

Укажите параметр, значение которого необходимо изменить (BS или STmin).

typedef enum { TP_STMIN, TP_BS, TP_BC } TPParameterType;
