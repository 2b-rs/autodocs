Системная архитектура и роль кластера модулей

Кластер включает в себя единственный модуль — Runtime Environment (Rte). Она реализует на каждом блоке управления пути связи, которые определяет конфигурация ECU. При этом она также реализует семантику коммуникационных атрибутов из описаний компонентов [SWS_Rte_02200] [SWS_Rte_02201]. RTE конфигурируется и генерируется индивидуально для каждого ECU [SWS_Rte_05000] [SWS_Rte_01316]. Генератор создает C-код, который должен соответствовать MISRA C [SWS_Rte_01167] [SWS_Rte_01168]. Расположение RTE между прикладным и базовым программным обеспечением показывает схема архитектуры ECU (SWS RTE с. 113).

Вниз по стеку RTE использует исключительно стандартизированные сервисы AUTOSAR, в том числе OS, COM, LdCom и Transformer [SWS_Rte_02250]. В состав генерируемого кода входит также Basic Software Scheduler (SchM). Он обслуживает диспетчеризацию, режимы, триггеры и Exclusive Areas BSW-модулей. Методология предусматривает для этого отдельный шаг генерации, который создает только код планировщика (TR Methodology с. 463).

Генератор описывает созданную RTE саму как BSW-модуль. Сюда относятся BswModuleDescription, BswInternalBehavior и BswImplementation [SWS_Rte_05165] [SWS_Rte_05166] [SWS_Rte_05167]. API жизненного цикла Rte и SchM представлены в нем как BswModuleEntry [SWS_Rte_05177]. Основными интерфейсными файлами являются:

  • Rte.h [SWS_Rte_01157] и заголовочный файл жизненного цикла Rte_Main.h [SWS_Rte_01158],
  • Rte_Type.h с объявлениями типов [SWS_Rte_01161],
  • Application Header Rte_[Byps_]<name>.h для каждого типа компонентов [SWS_Rte_01003],
  • Rte_Cbk.h с прототипами функций обратного вызова [SWS_Rte_03796].

Контекстная диаграмма: RTE является посредником между SW-Cs и BSW-сервисами OS, IOC, COM, LdCom, NvM (через NvBlockSwComponentType) и BndM. BSW-Scheduler относится к тому же сгенерированному коду. Источники: [SWS_Rte_02250], [SWS_Rte_03001], [SWS_Rte_01377], [SWS_Rte_03884], SWS RTE с. 259, SWS OS с. 128

Взаимодействие и пути взаимодействия

SW-C состоит из нескольких RunnableEntitys. RTE запускает их в соответствии со связанными RTEEvents [SWS_Rte_02202] [SWS_Rte_02203] (SWS RTE с. 119).

Для взаимодействия отправитель-получатель (Sender-Receiver) действует следующее:

  • Puffer: буферизация выполняется на стороне получателя [SWS_Rte_02515].
    • «data» (без очереди) следует принципу last-is-best: новое значение перезаписывает старое [SWS_Rte_02516] [SWS_Rte_02520].
    • «events» попадают в очередь FIFO [SWS_Rte_02521] [SWS_Rte_02522]. При переполнении буфера новое событие отбрасывается и устанавливается флаг ошибки [SWS_Rte_02523]. Приложение видит это как RTE_E_LOST_DATA [SWS_Rte_02571].
  • Zugriffsarten:
    • При неявном чтении RTE перед запуском Runnable предоставляет копию, которая остается неизменной во время выполнения [SWS_Rte_06000] [SWS_Rte_06001] [SWS_Rte_06004].
    • Явно сущности Runnable обращаются через Rte_Read, Rte_Receive и Rte_Send [SWS_Rte_01091] [SWS_Rte_01092] [SWS_Rte_01072].
    • Неявно сущности Runnable выполняют запись через Rte_IWrite [SWS_Rte_03744].

Связь Inter-ECU через COM:

  • Составные данные RTE передает атомарно через группы сигналов [SWS_Rte_04527] [SWS_Rte_03008] (SWS RTE с. 326).
  • COM сообщает о событиях через Callbacks, такие как Rte_COMCbk_<sn> [SWS_Rte_03530] [SWS_Rte_03001]. Эти Callbacks активируют Runnables или пробуждают Runnables категории 2 в точках ожидания [SWS_Rte_03531] [SWS_Rte_03532].
  • Фильтры значений при связи Inter-ECU выполняются в COM, а intra-ECU — в RTE [SWS_Rte_05500].
  • Отличие релизов: в R20-11 [SWS_Rte_04505] требует ComHandleId. Более новый фрагмент документации вместо этого упоминает Com Symbolic Name (SWS RTE с. 324).

Большие массивы байтов через LdCom:

  • Большие массивы байтов RTE в R20-11 передает и принимает через LdCom и LdCom_Transmit [SWS_Rte_01376] [SWS_Rte_01377] [SWS_Rte_01378].
  • При передаче по TP RTE блокирует буфер сигналов до подтверждения [SWS_Rte_01379] [SWS_Rte_01380] (SWS RTE с. 350).
  • Отличие релизов: фрагмент для R25-11 вместо этого описывает «Large Data Path in COM» с Com_Transmit (SWS RTE с. 343). Для R20-11 применяется LdCom.

Client-Server-Kommunikation:

  • Клиенты вызывают службы через Rte_Call синхронно или асинхронно [SWS_Rte_01102] [SWS_Rte_01293] [SWS_Rte_01294]. Асинхронные результаты они получают с помощью Rte_Result [SWS_Rte_01111].
  • Если вызов не является прямым вызовом функции, RTE буферизует Requests на стороне сервера в очереди FIFO, а ответы — на стороне клиента с длиной очереди 1 [SWS_Rte_02527] [SWS_Rte_02528]. Через очередь Request она сериализует доступ к серверу [SWS_Rte_02530].
  • RTE отслеживает Timeouts независимо от режима приема [SWS_Rte_03763] (SWS RTE с. 358).

Другие пути:

  • Запросы к NvM от SW-C сущности Runnable из NvBlockSwComponentType перенаправляют в NvM (SWS RTE с. 259). Возвращаемые значения API NvM регулируются [SWS_Rte_04535].
  • Bulk-NvData RTE считывает через BndM [SWS_Rte_03883] [SWS_Rte_03884].
  • Между ядрами Rte_Call выполняет запись в IOC и активирует задачу сервера на целевом ядре (SWS OS с. 128). В IOC-Callbacks RTE не выполняет ExecutableEntities и предотвращает одновременный доступ к одному и тому же IOC-API [SWS_Rte_02736] [SWS_Rte_02737].

Синхронизация, реентерабельность и контексты задач

Контексты выполнения:

  • Runnables выполняются в контексте OS-Task или ISR2 (SWS RTE с. 119). Внутри Task RTE соблюдает сконфигурированный порядок выполнения [SWS_Rte_02207].
  • Прерывания категории 1 не должны достигать RTE. Соответствующие конфигурации генератор отклоняет [SWS_Rte_03594] (SWS RTE с. 182).
  • ISR2 может активировать ExecutableEntities через внешние триггеры [SWS_Rte_04564]. Runnables компонентов SW-Cs RTE, напротив, не позволяет выполнять в контексте прерывания [SWS_Rte_03600].
  • Callbacks RTE не должны блокировать [SWS_Rte_01165].
  • Вызывается ли после Runnable Schedule, определяют от [SWS_Rte_05113] до [SWS_Rte_05115].

Согласованность данных: RTE гарантирует согласованность для связи через AUTOSAR-Interfaces [SWS_Rte_03514] и для InterRunnableVariables [SWS_Rte_03516].

  • Для неявных InterRunnableVariables она предотвращает одновременный доступ. Для явных — блокирует конкурирующий доступ [SWS_Rte_03517] [SWS_Rte_03519] (SWS RTE с. 207).
  • Вход в Exclusive Areas и выход из них осуществляются с помощью Rte_Enter и Rte_Exit [SWS_Rte_03515] [SWS_Rte_01120] [SWS_Rte_01123]. Различные области разрешается вкладывать друг в друга [SWS_Rte_01122].
  • Механизм защиты выбирается с помощью RteExclusiveAreaImplMechanism: ALL_INTERRUPT_BLOCKING [SWS_Rte_03504], OS_INTERRUPT_BLOCKING [SWS_Rte_05164], OS_RESOURCE [SWS_Rte_03595] или NONE [SWS_Rte_03999].
  • Если сущности Runnable вызывают блокирующий API внутри Exclusive Area, он возвращает RTE_E_IN_EXCLUSIVE_AREA [SWS_Rte_02739].

Reentranz:

  • Один и тот же экземпляр Runnable разрешается активировать параллельно только в том случае, если установлен canBeInvokedConcurrently [SWS_Rte_03523] [SWS_Rte_05083].
  • Множественные экземпляры RTE поддерживает только через Code-Sharing [SWS_Rte_03015] [SWS_Rte_02002]. Экземпляр идентифицируется с помощью Instance Handle, который Entry Point получает в качестве первого параметра [SWS_Rte_01016] [SWS_Rte_02015].
  • Поскольку экземпляры планируются независимо, точки входа должны быть реентерабельными (SWS RTE с. 804).

Mehrkern- und Partitionssysteme: здесь [SWS_Rte_02711] ограничивает глобальные переменные в Rte.c. Кроме того, [SWS_Rte_02712] требует отдельных файлов Rte_Partition_<PartitionName>.

Жизненные циклы и режимы работы

Запуск BSW-Scheduler:

  • До его инициализации доступны только SchM_Enter и SchM_Exit (SWS RTE с. 400).
  • SchM_Start генерируется всегда, возвращает управление за конечное время и должен вызываться до BswM_Init() [SWS_Rte_04546] [SWS_Rte_04547] [SWS_Rte_04548] (SWS RTE с. 927).
  • SchM_StartTiming запускает периодические события и требует предварительного выполнения SchM_Init [SWS_Rte_04549] [SWS_Rte_04550] [SWS_Rte_04551].
  • Все три вызова выполняются ровно один раз для каждого ядра с помощью EcuM (SWS RTE с. 928).

Запуск RTE:

  • EcuM вызывает Rte_Start в конце Startup-Phase II, когда OS доступна и все BSW-модули инициализированы [SWS_Rte_02569] [SWS_Rte_02585] (SWS RTE с. 460).
  • В случае сбоя выделения ресурсов Rte_Start возвращает RTE_E_LIMIT, в противном случае — RTE_E_OK [SWS_Rte_01261] [SWS_Rte_01262] (SWS RTE с. 806).
  • Начальные значения защищают получателей от неинициализированных данных [SWS_Rte_06009] [SWS_Rte_06010] [SWS_Rte_02517].

Завершение работы и перезапуск раздела:

  • Rte_Stop следует в начале Shutdown-Phase I [SWS_Rte_02570] [SWS_Rte_02584]. Если ресурс не удается освободить, функция сообщает RTE_E_LIMIT [SWS_Rte_01260].
  • После этого RTE больше не активирует Runnables на этом ядре [SWS_Rte_02538].
  • До полной инициализации и после остановки RTE игнорирует входящие запросы Client-Server, а также данные Sender-Receiver [SWS_Rte_02535] [SWS_Rte_02536] (SWS RTE с. 461). BSW-Scheduler ведет себя аналогично [SWS_Rte_04552].
  • При перезапуске раздела RTE восстанавливает исходную среду [SWS_Rte_02735].

Диаграмма последовательности: запуск и Shutdown для BSW-Scheduler и RTE для каждого ядра под управлением EcuM. Интерпретация: порядок SchM_Init и SchM_Start явно не подтвержден. Источники: [SWS_Rte_04546], [SWS_Rte_04549], [SWS_Rte_02569], [SWS_Rte_02570], [SWS_Rte_02538], SWS RTE с. 400, SWS RTE с. 460

Modusverwaltung:

  • RTE ведет активный режим каждого Mode Machine Instance [SWS_Rte_02546] и при инициализации инициирует переход в начальные режимы [SWS_Rte_02544] (SWS RTE с. 433).
  • Mode Manager запрашивает переключение через Rte_Switch [SWS_Rte_02631]. Уведомления помещаются в очередь FIFO для каждого экземпляра [SWS_Rte_02718] [SWS_Rte_02719].
  • При переполнении очереди новое уведомление отбрасывается [SWS_Rte_02720]. Между разделами RTE затем сообщает RTE_E_LIMIT [SWS_Rte_02675]. Только после завершения переключения она удаляет уведомление из очереди [SWS_Rte_02721].
  • Сам переход [SWS_Rte_02665] разделяет на десять шагов (EXP ModeManagementGuide с. 15):
    1. Активировать Mode Disablings [SWS_Rte_02661].
    2. Выполнить сущности On-exit [SWS_Rte_02562].
    3. Выполнить сущности On-transition [SWS_Rte_02707] [SWS_Rte_02708].
    4. Выполнить сущности On-entry [SWS_Rte_02564].
    5. Переключить Mode Disablings [SWS_Rte_02563].
    6. Вызвать срабатывание ModeSwitchedAckEvent [SWS_Rte_02587].
  • Выполняемые сущности Runnable не прерываются при смене режима [SWS_Rte_02504]. Даже переключение в тот же самый режим выполняется полностью [SWS_Rte_02669].
  • Подтверждение Mode Manager запрашивает через Rte_SwitchAck [SWS_Rte_02725].
  • Режимы могут также активировать OS-Schedule-Tables [SWS_Rte_05146].

Диаграмма деятельности: запрос на смену режима ставится в очередь или отбрасывается при переполнении очереди. Затем он проходит упорядоченные шаги перехода вплоть до подтверждения. Источники: [SWS_Rte_02665], [SWS_Rte_02718], [SWS_Rte_02720], [SWS_Rte_02721], [SWS_Rte_02587], EXP ModeManagementGuide с. 15

Обработка ошибок, трассировка и деградация

Состояния ошибок SW-C получает исключительно как возвращаемое значение RTE-API типа Std_ReturnType [SWS_Rte_01034] (SWS RTE с. 579). Спецификация различает три класса ошибок:

  • Immediate Infrastructure Errors перезаписывают ошибки приложения [SWS_Rte_02593].
  • Overlayed Errors используют отдельный бит и могут комбинироваться с другими ошибками [SWS_Rte_01318] (SWS RTE с. 686).
  • Ошибки приложения занимают младшие 6 бит [SWS_Rte_02573].

Degradation:

  • Для несоединенных портов RTE определяет фиксированное поведение [SWS_Rte_01329] [SWS_Rte_01330]. Rte_Call затем сообщает RTE_E_UNCONNECTED [SWS_Rte_01334].
  • Отправители инвалидируют данные через Rte_Invalidate [SWS_Rte_01206], что активируется через handleInvalid [SWS_Rte_05024]. Intra-ECU RTE реализует инвалидацию самостоятельно [SWS_Rte_05025]:
    • При keep она обрабатывает прием как ошибку [SWS_Rte_05030].
    • При replace она заменяет недействительное значение на initValue [SWS_Rte_05049].
  • Недействительные значения приводят к RTE_E_INVALID [SWS_Rte_02626]. При активной проверке диапазона значения вне диапазона приводят к RTE_E_OUT_OF_RANGE [SWS_Rte_03845] [SWS_Rte_03846] [SWS_Rte_01371] (SWS RTE с. 420).
  • Контроль устаревания данных выполняется согласно aliveTimeout. Значение 0 отключает его [SWS_Rte_03759] [SWS_Rte_02710]. При неявном доступе Rte_IStatus возвращает статус [SWS_Rte_02600].

Диаграмма последовательности: прием Inter-ECU от COM-Callback через активацию Runnable до возвращаемого статуса Rte_Read. Интерпретация: момент времени, в который RTE считывает группу сигналов из COM, не подтвержден документально. Источники: [SWS_Rte_03004], [SWS_Rte_03531], [SWS_Rte_01135], [SWS_Rte_01091], [SWS_Rte_02626], [SWS_Rte_01371], SWS RTE с. 326

Защита памяти: В системах с защитой памяти RTE проверяет указатели из ненадежных (untrusted) разделов перед их дальнейшей передачей [SWS_Rte_02752] [SWS_Rte_02753]. О нарушениях она сообщает как RTE_E_SEG_FAULT [SWS_Rte_02754] (SWS RTE с. 378).

Konfigurationsfehler: многие ошибки генератор перехватывает уже во время генерации и отклоняет конфигурацию, например [SWS_Rte_02009] и [SWS_Rte_05083]. Строгость проверки управляется параметром strictConfigurationCheck [SWS_Rte_05148] [SWS_Rte_05149].

Трассировка: Полезная нагрузка не содержит требований DET или DEM к RTE. Наблюдаемость вместо этого обеспечивает VFB-Tracing, которую можно отключить или активировать для сконфигурированных событий [SWS_Rte_01327] [SWS_Rte_01328]. Она служит для отладки SW-Cs, а не самой RTE (SWS RTE с. 836). Примерами Hooks являются API-Start-Hooks [SWS_Rte_01238] и Task_Dispatch [SWS_Rte_01244]. Они объявляются в заголовке Rte_Hook[_<client>].h [SWS_Rte_01250].

Поддержка измерений и калибровки

RTE выделяет память для параметров калибровки [SWS_Rte_03961] (SWS RTE с. 241). Из методов эмуляции с программной поддержкой (SW) одновременно активен только один [SWS_Rte_03909] [SWS_Rte_03943]:

  • Single Pointered: справочная таблица в RAM [SWS_Rte_03913].
  • Double Pointered: справочная таблица в ROM или Flash [SWS_Rte_03914].
  • InitRam: копия параметров в RAM из ROM/Flash [SWS_Rte_03915].

Поддержка измерений может быть отключена отдельно от этого [SWS_Rte_03903]. Выбранный метод и информацию о символах генератор документирует в McSupportData и McSwEmulationMethodSupport [SWS_Rte_05118] [SWS_Rte_05137] (SWS RTE с. 258).

Сгенерированное ИИ руководство на основе предоставленных требований и фрагментов документации. Фрагменты документации из других релизов использовались только в той мере, в какой они не противоречат R20-11; различия указаны. Пожалуйста, проверяйте нормативные детали в спецификации.

Runtime Environment (RTE) реализует виртуальную функциональную шину (VFB) на конкретном ECU и обеспечивает все связи между и внутри ECU между программными компонентами (SW-C) и базовым программным обеспечением.
