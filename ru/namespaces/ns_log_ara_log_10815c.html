Позволяет создавать контексты журналирования, форматированные потоки сообщений и отслеживать состояние клиентов.

Пространство имен ara::log предоставляет адаптивные службы протоколирования, управляя контекстными логгерами и типизированно выводя потоки сообщений в приемники, такие как бэкенд DLT или консоль [SWS_LOG_00021]. Приложения получают логгеры через фабричные функции, подготавливают форматированные полезные данные с помощью оберток аргументов и потокобезопасно передают данные в сообщения журнала. Важным граничным условием является то, что владение всеми экземплярами логгеров остается за фреймворком, тогда как регистрация обработчика статуса соединения явно не является потокобезопасной [SWS_LOG_00205].

Контекст

Пространство имен ara::log предоставляет центральную инфраструктуру протоколирования для адаптивных приложений. Его основная ответственность включает управление контекстами протоколирования через класс Logger, структурированное создание сообщений журнала через LogStream, а также типизированную передачу форматированных полезных данных через Argument и Format. Фреймворк выступает связующим звеном между вызовами протоколирования со стороны приложения и целевыми приемниками: в качестве первичного приемника служит бэкенд DLT (Diagnostic Log and Trace), статус подключения которого представляется через перечисление ClientState [SWS_LOG_00098]. Если модель недоступна, в качестве приемника по умолчанию выступает консоль [SWS_LOG_00021]. Изменения состояния внешних партнеров по коммуникации можно отслеживать с помощью функций обратного вызова типа ConnectionStateHandler [SWS_LOG_00265].

Контекстная диаграмма: партнеры по взаимодействию фреймворка протоколирования между приложением, консолью, бэкендом DLT и внешним клиентом. Источники: [SWS_LOG_00021], [SWS_LOG_00098], [SWS_LOG_00205].

Жизненный цикл

Экземпляры Logger конструируются не непосредственно приложением, а создаются фабричными функциями CreateLogger и регистрируются во фреймворке протоколирования [SWS_LOG_00021], [SWS_LOG_00263]. Отношения владения определены однозначно: владение полностью остается за фреймворком протоколирования («Ownership stays within the Logging framework»), который выдает вызывающей стороне ссылки (Logger&) [SWS_LOG_00021]. В качестве альтернативы создание может выполняться на основе модели с помощью ara::core::InstanceSpecifier [SWS_LOG_00256]. Интерпретация: поскольку фреймворк сохраняет владение, время жизни зарегистрированных логгеров, вероятно, привязано к вышестоящему процессу.

С точки зрения параллелизма создание логгеров через CreateLogger специфицировано как потокобезопасное [SWS_LOG_00021]. Напротив, регистрация обработчиков состояния соединения через RegisterConnectionStateHandler явно не потокобезопасна («not thread-safe») [SWS_LOG_00205]; поэтому она, как правило, должна выполняться на этапе инициализации до запуска параллельных активностей. Кроме того, в каждый момент времени может быть активен только один обработчик; повторная регистрация немедленно заменяет предыдущие обратные вызовы [SWS_LOG_00205]. Жизненный цикл соединения внешних партнеров по коммуникации проходит этапы kUnknown (бэкенд DLT еще не активен), kNotConnected и kConnected [SWS_LOG_00098].

Путь использования

Обычный порядок действий включает настройку мониторинга, получение логгера и форматированный вывод сообщений:

  • Регистрация обратного вызова соединения с помощью RegisterConnectionStateHandler [SWS_LOG_00205].
  • Получение ссылки на Logger через CreateLogger с указанием идентификатора контекста (Context ID), описания и, опционально, уровня важности по умолчанию из LogLevel (например, kWarn или kInfo) [SWS_LOG_00018], [SWS_LOG_00021].
  • Создание структурированных аргументов с помощью Arg с добавлением идентификатора, единицы измерения и указаний по форматированию [SWS_LOG_00201]. Для этого предусмотрены вспомогательные функции, такие как Dflt [SWS_LOG_00208], целочисленные форматы, такие как Dec [SWS_LOG_00211], Hex [SWS_LOG_00209], Bin [SWS_LOG_00215] и Oct [SWS_LOG_00213], а также форматы с плавающей точкой, такие как DecFloat [SWS_LOG_00217], EngFloat [SWS_LOG_00219], HexFloat [SWS_LOG_00221] или AutoFloat [SWS_LOG_00223], инкапсулирующие спецификаторы из Fmt [SWS_LOG_00206].
  • Передача полезных данных в LogStream через перегруженные операторы operator<<, в том числе для LogLevel [SWS_LOG_00063], ara::core::ErrorCode [SWS_LOG_00124], std::chrono::duration [SWS_LOG_00125], ara::core::InstanceSpecifier [SWS_LOG_00126] и указателей const void* [SWS_LOG_00127].

Диаграмма последовательности: типичная последовательность взаимодействия при инициализации, создании логгеров и выводе форматированных данных через LogStream. Источники: [SWS_LOG_00021], [SWS_LOG_00063], [SWS_LOG_00124], [SWS_LOG_00201], [SWS_LOG_00205].

Сценарии ошибок

Функции пространства имен в основном объявлены с noexcept и предоставляют гарантии отсутствия исключений (No-Throw), однако подчиняются строгим предусловиям и правилам обработки нарушений:

  • Нарушения манифеста: при модельном создании логгера через CreateLogger(const ara::core::InstanceSpecifier&) могут возникать специфические нарушения времени выполнения: InstanceSpecifierMappingIntegrityViolation (спецификатор не удается разрешить в модели или он не указывает на PortPrototype), PortInterfaceMappingViolation (тип сопоставления не соответствует ожидаемому PortInterface), ProcessMappingViolation (подходящий процесс не найден), а также InstanceSpecifierAlreadyInUseViolation (спецификатор уже используется в процессе) [SWS_LOG_00256].
  • Недопустимая типизация аргументов: вызов Arg синтаксически некорректен («ill-formed»), если тип T не является ни арифметическим типом, ни bool, и не может быть преобразован ни в ara::core::StringView, ни в ara::core::Span<const ara::core::Byte>. Аналогично, передача текста единицы измерения, отличного от nullptr, unit для строк, байтовых диапазонов (byte spans) или логических типов приводит к ошибке [SWS_LOG_00201].
  • Отображение ошибок: при выводе экземпляра core::ErrorCode на консоль код ошибки форматируется платформозависимым образом, при этом должны содержаться имя домена (ErrorCode::Domain().Name()) и целочисленный номер ошибки [SWS_LOG_00124].

Перечисление ara::log::ClientState отражает текущее состояние подключения внешнего клиента к бэкенду DLT [SWS_LOG_00098]. Оно базируется на типе данных std::int8_t и подключается через заголовочный файл #include "ara/log/common.h" или заголовочный файл предварительного объявления #include "ara/log/log_fwd.h" [SWS_LOG_00098].

Состояния и семантика

Перечисление определяет три дискретных состояния подключения [SWS_LOG_00098]:

  • kUnknown (-1): бэкенд DLT еще не готов к работе; фактическое состояние подключения на данный момент не может быть определено [SWS_LOG_00098].
  • kNotConnected: внешний клиент не обнаружен [SWS_LOG_00098].
  • kConnected: удаленный клиент успешно подключен [SWS_LOG_00098].

Взаимодействие и параллелизм

Перечисление служит в первую очередь параметром передачи для функции обратного вызова ConnectionStateHandler (определенной как std::function<void(ClientState)>), которая регистрируется через ara::log::RegisterConnectionStateHandler [SWS_LOG_00265]. Этот обработчик объявлен как потокобезопасный [SWS_LOG_00265]. Интерпретация: зарегистрированные обработчики, вероятно, вызываются асинхронно, как только бэкенд DLT обнаруживает смену состояния внешнего клиента.
