Контекст

Пространство имен <SI-Namespace>::proxy::methods предоставляет в модуле com платформы AUTOSAR Adaptive Platform клиентские интерфейсные представители для вызовов методов. В сервис-ориентированной архитектуре AUTOSAR Adaptive коммуникационные связи определяются через сервисные интерфейсы (ServiceInterface). Если такой интерфейс содержит операции типа ClientServerOperation, генератор интерфейсов создает для каждой из этих операций специализированный класс метода в пространстве имен прокси.

При этом архитектура принципиально различает две разновидности методов, управляемые атрибутом метамодели fireAndForget:

  • Класс <Method>: этот класс генерируется для каждой ClientServerOperation, для которой сконфигурировано ClientServerOperation.fireAndForget == FALSE. Он представляет синхронные или асинхронные вызовы «запрос-ответ», при которых клиент ожидает ответ или результат от сервера.
  • Класс <FnFMethod>: этот класс создается для операций, для которых действует ClientServerOperation.fireAndForget == TRUE. Он реализует чистый односторонний шаблон обмена сообщениями (fire-and-forget), при котором вызов отправляется без передачи клиенту какого-либо подтверждения или возвращаемого значения со стороны сервера.

В рамках общей иерархии <SI-Namespace>::proxy эти классы инкапсулируют сериализацию входных параметров, передачу в нижележащую коммуникационную инфраструктуру, а для регулярных методов — также прием данных ответа.

Жизненный цикл

Время жизни классов в пространстве имен <SI-Namespace>::proxy::methods тесно связано с вышестоящим экземпляром прокси соответствующего сервисного интерфейса. Интерпретация: экземпляры <Method> и <FnFMethod>, вероятно, инстанцируются как члены сгенерированного класса сервис-прокси и поэтому полностью разделяют его жизненный цикл.

При инстанцировании сервис-прокси (после успешного обнаружения сервиса и привязки к конкретному экземпляру сервиса) встроенные объекты методов инициализируются. При этом они получают контекст доступа к нижележащему коммуникационному биндингу. Пока сервис-прокси остается валидным, экземпляры методов доступны клиентскому приложению. При уничтожении сервис-прокси связанные объекты методов также прекращают существование. Выполняемые асинхронные вызовы или еще ожидающие ответы должны быть обработаны или инвалидированы до или во время вызова деструктора прокси.

С точки зрения параллелизма вызовы методов спроектированы таким образом, что несколько потоков прикладного программного обеспечения могут вызывать один и тот же прокси-метод, если реализация промежуточного слоя обеспечивает потокобезопасность отправки. Поскольку объекты методов обычно не сохраняют состояние контекста вызова между последовательными вызовами, они по существу действуют как интерфейсы функций без сохранения состояния для передачи сообщений.

Путь использования

Типичный процесс использования классов из <SI-Namespace>::proxy::methods делится на следующие фазы:

  1. Предоставление прокси: клиентское приложение находит требуемый экземпляр сервиса с помощью механизма обнаружения сервисов модуля com и инстанцирует типизированный прокси.
  2. Доступ к методу: приложение обращается к конкретному члену-методу прокси. Интерпретация: вызов объекта метода, вероятно, обычно выполняется через перегруженный оператор вызова функции (operator()) соответствующего объекта.
  3. Выполнение регулярных методов (<Method>): при выполнении регулярной операции приложение передает объявленные входные параметры. Объект метода перенаправляет запрос через промежуточный слой на сервер и возвращает вызывающему приложению объект, инкапсулирующий асинхронный результат. Затем приложение может синхронно блокироваться до получения результата или зарегистрировать асинхронное уведомление.
  4. Выполнение методов Fire-and-Forget (<FnFMethod>): при выполнении односторонней операции приложение также передает входные параметры объекту метода. Тот инициирует передачу и немедленно возвращает управление приложению без предоставления объекта возврата или состояния для результата.

Сценарии ошибок

При вызове классов из <SI-Namespace>::proxy::methods необходимо учитывать различные уровни ошибок, различающиеся в зависимости от семантики вызова:

  • Ошибки коммуникации и привязки: предварительным условием для любого вызова метода является работоспособный транспортный канал к экземпляру сервиса. При обрыве сетевого соединения или недоступности экземпляра сервиса вызовы завершаются с ошибкой. Для регулярных классов <Method> соответствующая ошибка передается через объект результата.
  • Ошибки приложения: если сервер не может успешно обработать регулярную <Method>, клиенту возвращается ошибка приложения, определенная в сервисном интерфейсе.
  • Поведение при ошибках для Fire-and-Forget: интерпретация: для <FnFMethod> ошибки обработки на стороне сервера, вероятно, не возвращаются вызывающей стороне, так как fire-and-forget семантически не предусматривает ответного сообщения. Для приложения это означает, что исключения или ошибки вычислений на стороне сервера остаются незамеченными, если для этой цели не используется отдельный обратный канал (например, событие). Напротив, локальные ошибки при приеме параметров или при отправке могут сигнализироваться непосредственно в вызывающем контексте.
