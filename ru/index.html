Adaptive Platform в одном предложении

AUTOSAR Adaptive Platform — это сервисно-ориентированная среда выполнения для производительных автомобильных компьютеров: Adaptive Applications выполняются как самостоятельные процессы POSIX, динамически запускаются и контролируются, а также обмениваются данными через сервисы, определённые контрактами, вместо статически соединённых сигналов (EXP PlatformDesign §3.3 «Adaptive Platform – Characteristics», §8.2 «Service Oriented Communication»).

ARA — программный интерфейс по этой ссылке

Все документированные здесь пространства имён ara::* вместе образуют интерфейс ARA (AUTOSAR Runtime for Adaptive Applications). Каждый Functional Cluster платформы экспортирует свой C++ API в отдельном Namespace — от базовых типов в ara::core через сервисную коммуникацию в ara::com до платформенных сервисов, таких как ara::exec, ara::per или ara::crypto (EXP PlatformDesign §4.1 «Logical view», EXP SWArchitecture §9.1 «Building Block View – Overview»).

Functional Cluster Adaptive Platform и типичные взаимодействия адаптивного приложения (узел кликабельный). Источники: EXP PlatformDesign §4.1, EXP SWArchitecture §9.1. Частичная интерпретация: выбор и маркировка взаимодействий суммируют главы упомянутых источников.

Общие концепции

  • Машина и усилитель; Кластер программного обеспечения: A Machine — это (возможно, виртуализированная) среда выполнения; Программное обеспечение упаковывается в виде устанавливаемого Software Cluster и обновляется через ara::ucm (EXP SWArchitecture §13.4 «Software Cluster», §13.5 «Machine»).
  • Функциональные группы и состояния: Процессы назначаются функциональным группам; ara::sm инструктирует управление выполнением запускать/останавливать процессы через состояния группы функций (EXP SWArchitecture §13.2 «Function Group», EXP PlatformDesign гл. 7 «State Management»).
  • Manifests: Execution, Service-Instance и Machine-Manifest декларативно настраивают развертывание, поведение запуска и привязку службы (EXP PlatformDesign §4.4 «Manifest», EXP SWArchitecture §13.6 «Manifest»).
  • Обработка ошибок без исключений: на всей платформе ошибки возвращаются как ara::core::Result/ErrorCode (EXP PlatformDesign §18.1 «Error Handling», EXP SWArchitecture §13.12 «Error Handling»).
  • Безопасность & Безопасность как сечение: E2E защита, Health Monitoring (ara::phm), стек, удостоверение & управление доступом, обнаружение вторжений (ara::idsm) и брандмауэр (ara::fw) защищают платформу и связь (EXP PlatformDesign гл. 17 «Safety», EXP SWArchitecture §13.13 «Trusted Platform»).

Перекрёстные связи между модулями

Скруглённые рамки = модули; узлы = подобласти модуля (Namespaces или функциональные группы). Стрелка A → B: точки API подобласти A (сигнатуры, поля, параметры) ссылаются на типы подобласти B — это определено из связанных деклараций данной справки; толщина линии соответствует числу точек ссылок (точное число отображается как tooltip на стрелке). Подпись ребра = вид взаимодействия с целью: возвращаемые значения, асинхронные результаты, обработка ошибок, типы данных, адресация экземпляров, вспомогательные функции; «использует» обозначает прочие ссылки на типы. Светло-серые стрелки: моделирование сервиса через ara::com. Все узлы связаны со страницами соответствующих Namespace/классов.

Видимость API для приложений

Не каждый элемент спецификации, описанный здесь, является частью общедоступного API ARA: документы SWS указывают в своей главе 5 («Зависимости от других функциональных кластеров», таблица 5.1 в каждом случае), какие интерфейсы предоставляются исключительно другим функциональным кластерам. Эта ссылка делает это последовательно видимым в цвете фона соответствующего модуля, пространства имен и имени класса - на странице каждого элемента (заголовок страницы и метка справа в строке навигации), во всех ссылках на элемент на страницах более высокого уровня и на связанных узлах диаграмм. По умолчанию фон очень бледный, чтобы обеспечить хорошую читаемость, и становится немного более насыщенным при наведении курсора мыши:

  • APPLICATION Blue: может использоваться непосредственно адаптивными приложениями, например B. ara::core, ara::com, ara::log, ara::per, ara::crypto, ara::diag, ara::rds, ara::shwa (запускается как библиотека в процессе приложения, SWS SHWA гл. 1), ara::tsync (активное и пассивное время) базовое использование, SWS TSync §2.2) и ara::idsm (приложения в качестве датчиков безопасности, SWS IdsM §7.2). ara::exec::ExecutionClient также принадлежит сюда, но может сообщать только о своем собственном состоянии процесса [SWS_EM_01401].
  • PRIVILEGED Red: только для выделенных приложений, авторизованных через IAM или сопоставление манифеста; авторизованный пользователь указан в скобках в строке навигации. Примеры: PackageManagement-Service из ara::ucm («UCM Client» = например, OTA клиент или диагностическое приложение, SWS UCM §7.1), StateMachine-Services из ara::sm для SM-Control-Application [SWS_SM_00600], Suspend-to-RAM-API ara::sm::s2r (только IAM-аутентифицированные спутники с SuspendToRamSatelliteMapping, [SWS_SM_00715]) а также ara::fw (изменение состояния только с помощью AdaptiveFirewallToPortPrototypeMapping, [AP_SWS_Fw_40013]).
  • INTERNAL Темно-серый: чисто внутренние интерфейсы кластера, конечно, не для приложений; Использование Functional Cluster находится в скобках в строке навигации. Примеры: ara::exec::StateClient включая FunctionGroup/FunctionGroupState (только для State Management, SWS EM Tab. 5.1), весь модуль ara::nm (Service-Interface удален для приложений, переполнение сетевых запросов State Management, SWS NM §4.1 и Tab. 5.1), ara::phm::RecoveryAction (SWS PHM Tab. 5.1), а также все apext::* интерфейсы нормативных приложений «Platform Extension Interfaces» (интеграция платформы с базовым программным обеспечением: Watchdog, Power, UDS транспорт, менеджер значений актуальности, трассировка/ARTI).

Страницы-агрегаты (Module, Namespaces) со смешанным содержимым получают ключевое слово большинства Sub-Elements и перечисляют исключения в скобках, например APPLICATION (Except INTERNAL StateClient, …). Цветовую схему можно изменить централизованно в блоке видимости style.css: значения цветов через --vis-app-rgb (синий), --vis-priv-rgb (красный) и --vis-internal-rgb (тёмно-серый), бледность фонов через --vis-bg-alpha (стандарт) и --vis-bg-alpha-hover (Mouseover).

Интерпретация: Цветовая классификация представляет собой классификацию ИИ на основе таблиц 5.1, главы об использовании (глава 7) и приложений соответствующего SWS; сами стандарты не предусматривают такой поэлементной классификации. Сопутствующие типы (домены ошибок, исключения, дескрипторы) сопоставлены с видимостью их основного интерфейса.

Интерпретация: Группировка модулей в этом обзоре (базовый, среда выполнения, связь, хранилище, безопасность, диагностика) соответствует структуре строительных блоков архитектурной документации и не является нормативной классификацией стандартов.
