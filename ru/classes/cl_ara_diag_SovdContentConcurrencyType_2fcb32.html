Контекст

Структура ara::diag::SovdContentConcurrencyType является элементом спецификации модуля diag в составе AUTOSAR Adaptive Platform ([SWS_DM_02182]). Она служит для определения поведения параллелизма (Concurrency Type) для портов, связанных с SOVD Content (Service-Oriented Vehicle Diagnostics) (AUTOSAR_AP_SWS_Diagnostics §8.8.3 «Struct: SovdContentConcurrencyType»). Через SOVD в современных автомобильных системах обеспечивается стандартизированный сервис-ориентированный доступ к диагностическим данным и диагностическим функциям. Поскольку доступ к диагностическому содержимому может осуществляться как для чтения, так и для записи, эта структура представляет собой формальное соглашение об интерфейсе относительно того, какие формы параллельных вызовов допустимы.

В общей системе взаимодействуют три основных компонента: Diagnostic Management (DM) как центральный диагностический экземпляр, прикладной SOVD Content Port, а также предоставляющее адаптивное приложение (Adaptive Application). Diagnostic Management (DM) выступает в роли вызывающей стороны, направляя диагностические запросы на чтение и запись в порт ([SWS_DM_02185]). При этом структура SovdContentConcurrencyType действует как дескриптор конфигурации порта и в обязательном порядке сообщает DM, разрешено ли выполнять операции параллельно или они должны быть сериализованы диагностической системой.

Контекстная диаграмма: взаимодействие между Diagnostic Management (DM), SOVD Content Port и Adaptive Application при управлении поведением параллелизма. Источники: [SWS_DM_02182], [SWS_DM_02185], AUTOSAR_AP_SWS_Diagnostics §8.8.3 «Struct: SovdContentConcurrencyType».

Жизненный цикл

Будучи базовой структурой данных C++ (struct), ara::diag::SovdContentConcurrencyType не имеет активной логики управления и внутреннего конечного автомата (AUTOSAR_AP_SWS_Diagnostics §8.8.3 «Struct: SovdContentConcurrencyType»). Объявление предоставляется через заголовочный файл #include "ara/diag/concurrency.h" ([SWS_DM_02183]). Создание, присваивание и уничтожение следуют стандартным правилам языка C++ для простых типов значений; динамические ресурсы операционной системы или области памяти кучи монопольно не управляются.

Структура определяет три открытые переменные-члена типа ConcurrencyType, которые управляют поведением дифференцированно в зависимости от типа доступа:

  • read: определяет тип параллелизма для операций чтения ([SWS_DM_02183], AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.1 «read»). Переменная по умолчанию предварительно инициализирована значением ConcurrencyType::kNotConcurrent.
  • write: определяет тип параллелизма для операций записи ([SWS_DM_02184], AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.3 «write»). Значение по умолчанию также равно ConcurrencyType::kNotConcurrent.
  • readWrite: определяет допустимость одновременных вызовов методов чтения и записи ([SWS_DM_02185], AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.2 «readWrite»). Здесь в качестве значения по умолчанию также предварительно задано ConcurrencyType::kNotConcurrent.

Срок службы экземпляра тесно связан с жизненным циклом связанного порта. Как правило, экземпляр, вероятно, создается на стеке или как член класса порта на этапе инициализации приложения, конфигурируется и передается в диагностическую систему. Благодаря предварительной инициализации всех трех переменных значением ConcurrencyType::kNotConcurrent сразу после создания экземпляра действует принцип превентивной защиты: без явного переконфигурирования система защищает приложение от параллельного выполнения. Переходы состояний в смысле внутреннего конечного автомата отсутствуют; возможные модификации касаются исключительно назначения параметров перед вводом в эксплуатацию.

Путь использования

Стандартный сценарий использования ara::diag::SovdContentConcurrencyType подразделяется на определение, параметризацию и последующий анализ со стороны среды выполнения диагностики:

  1. Подключение интерфейса: приложение включает заголовочный файл ara/diag/concurrency.h, благодаря чему становятся доступны определения типов SovdContentConcurrencyType и ConcurrencyType ([SWS_DM_02183]).
  2. Создание экземпляра: при создании диагностического порта, связанного с SOVD, объявляется экземпляр структуры. Изначально переменные read, write и readWrite имеют состояние kNotConcurrent ([SWS_DM_02183], [SWS_DM_02184], [SWS_DM_02185]).
  3. Настройка параллелизма: если логика приложения рассчитана на многократные параллельные вызовы, переменные-члены корректируются. Например, если порт может обрабатывать несколько запросов на чтение одновременно, read устанавливается в ConcurrencyType::kConcurrent. Если приложение способно одновременно обрабатывать операции чтения и записи без несогласованности данных, readWrite устанавливается в ConcurrencyType::kConcurrent ([SWS_DM_02185]); при этом само приложение, по-видимому, отвечает за потокобезопасность задействованных структур данных.
  4. Предоставление для Diagnostic Management: сконфигурированная структура связывается с SOVD Content Port, благодаря чему демон Diagnostic Management (DM) получает сведения о требованиях к семантике выполнения.
  5. Вызовы во время выполнения со стороны DM: при входящих диагностических запросах DM учитывает конфигурацию: если readWrite установлено в kConcurrent, DM разрешено вызывать API чтения и записи параллельно ([SWS_DM_02185]). Если же настройка установлена в kNotConcurrent, DM, по-видимому, выполняет сериализацию вызовов во избежание конфликтов на стороне приложения.

Настоящее руководство было автоматически сгенерировано на основе спецификации AUTOSAR Adaptive Platform R25-11 (модуль diag).

<p class="diagram-note">Контекстная диаграмма: взаимодействие между Diagnostic Management (DM), SOVD Content Port и Adaptive Application при управлении поведением параллелизма. Источники: <a class="spec-record-ref" data-req="SWS_DM_02182" href="../spec/record.html?id=SWS_DM_02182">[SWS_DM_02182]</a>, <a class="spec-record-ref" data-req="SWS_DM_02185" href="../spec/record.html?id=SWS_DM_02185">[SWS_DM_02185]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=351">AUTOSAR_AP_SWS_Diagnostics §8.8.3 «Struct: SovdContentConcurrencyType»</a>.</p>

<h4>Жизненный цикл</h4>
<p>Будучи базовой структурой данных C++ (<code>struct</code>), <code>ara::diag::SovdContentConcurrencyType</code> не имеет активной логики управления и внутреннего конечного автомата (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=351">AUTOSAR_AP_SWS_Diagnostics §8.8.3 «Struct: SovdContentConcurrencyType»</a>). Объявление предоставляется через заголовочный файл <code>#include "ara/diag/concurrency.h"</code> (<a class="spec-record-ref" data-req="SWS_DM_02183" href="../spec/record.html?id=SWS_DM_02183">[SWS_DM_02183]</a>). Создание, присваивание и уничтожение следуют стандартным правилам языка C++ для простых типов значений; динамические ресурсы операционной системы или области памяти кучи монопольно не управляются.</p>
<p>Структура определяет три открытые переменные-члена типа <code>ConcurrencyType</code>, которые управляют поведением дифференцированно в зависимости от типа доступа:</p>
<ul>
<li><code>read</code>: определяет тип параллелизма для операций чтения (<a class="spec-record-ref" data-req="SWS_DM_02183" href="../spec/record.html?id=SWS_DM_02183">[SWS_DM_02183]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=351">AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.1 «read»</a>). Переменная по умолчанию предварительно инициализирована значением <code>ConcurrencyType::kNotConcurrent</code>.</li>
<li><code>write</code>: определяет тип параллелизма для операций записи (<a class="spec-record-ref" data-req="SWS_DM_02184" href="../spec/record.html?id=SWS_DM_02184">[SWS_DM_02184]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=352">AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.3 «write»</a>). Значение по умолчанию также равно <code>ConcurrencyType::kNotConcurrent</code>.</li>
<li><code>readWrite</code>: определяет допустимость одновременных вызовов методов чтения и записи (<a class="spec-record-ref" data-req="SWS_DM_02185" href="../spec/record.html?id=SWS_DM_02185">[SWS_DM_02185]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=352">AUTOSAR_AP_SWS_Diagnostics §8.8.3.1.2 «readWrite»</a>). Здесь в качестве значения по умолчанию также предварительно задано <code>ConcurrencyType::kNotConcurrent</code>.</li>
</ul>
<p>Срок службы экземпляра тесно связан с жизненным циклом связанного порта. Как правило, экземпляр, вероятно, создается на стеке или как член класса порта на этапе инициализации приложения, конфигурируется и передается в диагностическую систему. Благодаря предварительной инициализации всех трех переменных значением <code>ConcurrencyType::kNotConcurrent</code> сразу после создания экземпляра действует принцип превентивной защиты: без явного переконфигурирования система защищает приложение от параллельного выполнения. Переходы состояний в смысле внутреннего конечного автомата отсутствуют; возможные модификации касаются исключительно назначения параметров перед вводом в эксплуатацию.</p>

<h4>Путь использования</h4>
<p>Стандартный сценарий использования <code>ara::diag::SovdContentConcurrencyType</code> подразделяется на определение, параметризацию и последующий анализ со стороны среды выполнения диагностики:</p>
<ol>
<li><strong>Подключение интерфейса:</strong> приложение включает заголовочный файл <code>ara/diag/concurrency.h</code>, благодаря чему становятся доступны определения типов <code>SovdContentConcurrencyType</code> и <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_02183" href="../spec/record.html?id=SWS_DM_02183">[SWS_DM_02183]</a>).</li>
<li><strong>Создание экземпляра:</strong> при создании диагностического порта, связанного с SOVD, объявляется экземпляр структуры. Изначально переменные <code>read</code>, <code>write</code> и <code>readWrite</code> имеют состояние <code>kNotConcurrent</code> (<a class="spec-record-ref" data-req="SWS_DM_02183" href="../spec/record.html?id=SWS_DM_02183">[SWS_DM_02183]</a>, <a class="spec-record-ref" data-req="SWS_DM_02184" href="../spec/record.html?id=SWS_DM_02184">[SWS_DM_02184]</a>, <a class="spec-record-ref" data-req="SWS_DM_02185" href="../spec/record.html?id=SWS_DM_02185">[SWS_DM_02185]</a>).</li>
<li><strong>Настройка параллелизма:</strong> если логика приложения рассчитана на многократные параллельные вызовы, переменные-члены корректируются. Например, если порт может обрабатывать несколько запросов на чтение одновременно, <code>read</code> устанавливается в <code>ConcurrencyType::kConcurrent</code>. Если приложение способно одновременно обрабатывать операции чтения и записи без несогласованности данных, <code>readWrite</code> устанавливается в <code>ConcurrencyType::kConcurrent</code> (<a class="spec-record-ref" data-req="SWS_DM_02185" href="../spec/record.html?id=SWS_DM_02185">[SWS_DM_02185]</a>); при этом само приложение, по-видимому, отвечает за потокобезопасность задействованных структур данных.</li>
<li><strong>Предоставление для Diagnostic Management:</strong> сконфигурированная структура связывается с SOVD Content Port, благодаря чему демон Diagnostic Management (DM) получает сведения о требованиях к семантике выполнения.</li>
<li><strong>Вызовы во время выполнения со стороны DM:</strong> при входящих диагностических запросах DM учитывает конфигурацию: если <code>readWrite</code> установлено в <code>kConcurrent</code>, DM разрешено вызывать API чтения и записи параллельно (<a class="spec-record-ref" data-req="SWS_DM_02185" href="../spec/record.html?id=SWS_DM_02185">[SWS_DM_02185]</a>). Если же настройка установлена в <code>kNotConcurrent</code>, DM, по-видимому, выполняет сериализацию вызовов во избежание конфликтов на стороне приложения.</li>
</ol>
