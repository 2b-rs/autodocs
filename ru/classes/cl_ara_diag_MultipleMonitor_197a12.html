Контекст

Класс ara::diag::MultipleMonitor служит для реализации операций монитора через сгруппированные интерфейсы монитора ([SWS_DM_01695]). Он выступает в качестве центрального посредника между прикладной диагностической и функциональной логикой и диагностической системой (Diagnostic Management, DM). В то время как простой монитор отображает только один тракт контроля ошибок, MultipleMonitor обеспечивает управление и передачу отчетов о состоянии нескольких мониторов через общий порт интерфейса ([SWS_DM_01695], [SWS_DM_01698]).

Привязка к модели AUTOSAR осуществляется через экземпляр порта (PortPrototype) типа DiagnosticMultipleMonitorInterface ([SWS_DM_01695]). Через этот порт экземпляр мониторинга регистрируется и перенаправляет команды, а также обратную связь, такую как управление устранением дребезга и статус квалификации, в DM или принимает запросы от диагностической системы ([SWS_DM_01698], [SWS_DM_01699]).

Жизненный цикл

Экземпляр MultipleMonitor обладает строгой объектной идентичностью и привязан к жестко определенному контексту выполнения. Конструктор требует ara::core::InstanceSpecifier, который адресует соответствующий порт в модели системы ([SWS_DM_01695]). Во избежание побочных эффектов и множественных привязок как конструктор копирования, так и конструктор перемещения (Move) и соответствующие операторы присваивания явно удалены ([SWS_DM_02065], [SWS_DM_02066], [SWS_DM_02063], [SWS_DM_02064]). Тем самым передача экземпляра между областями видимости исключена.

После инстанцирования объект находится в состоянии инициализации: каждый управляемый в нем монитор перед своим первым использованием должен быть сконфигурирован ровно один раз через одну из перегрузок ConfigureMonitor ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). Как только мониторы инициализированы, вызов Offer() активирует пересылку запросов со стороны Diagnostic Management ([SWS_DM_01699]). Пересылка может быть снова приостановлена с помощью StopOffer() ([SWS_DM_01700]). Что касается потокобезопасности, конструирование является потокобезопасным ([SWS_DM_01695]), в то время как методы конфигурации и предоставления (ConfigureMonitor, Offer, StopOffer) не являются потокобезопасными ([SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700]). Отправка отчетов через ReportMonitorAction защищена в зависимости от модели параллелизма, определенной на этапе проектирования или в конструкторе ([SWS_DM_01698]).

Диаграмма состояний: состояния жизненного цикла экземпляра MultipleMonitor от создания через конфигурацию и предоставление до остановки. Источники: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700].

Путь использования

Стандартный порядок использования MultipleMonitor делится на фазы создания, конфигурации отдельных мониторов, предоставления и текущей отправки отчетов о событиях:

  1. Создание: приложение инстанцирует MultipleMonitor с указанием InstanceSpecifier ([SWS_DM_01695]).
  2. Конфигурация монитора: для каждого контролируемого события или каждого monitorHandle определяется подходящая стратегия устранения дребезга. Для этого в AUTOSAR предусмотрены четыре специализированные перегрузки ConfigureMonitor:
    • Внутреннее для монитора устранение дребезга с регистрацией функции обратного вызова для определения Fault Detection Counter (FDC) ([SWS_DM_01696]).
    • Устранение дребезга по времени с передачей параметров типа TimeBased ([SWS_DM_01697]).
    • Устранение дребезга по счетчику с помощью параметров типа CounterBased ([SWS_DM_01702]).
    • Работа без устранения дребезга, при которой регистрируется только опциональный InitMonitorNotifier ([SWS_DM_01973]).
    Каждая перегрузка для каждого дескриптора монитора должна вызываться ровно один раз ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]).
  3. Предоставление сервиса: вызовом Offer() интерфейс переводится в активное состояние, благодаря чему демон Diagnostic Management может доставлять запросы этому обработчику ([SWS_DM_01699]).
  4. Сообщение о состоянии: во время работы логика приложения передает результаты проверки, команды управления устранением дребезга или команды предварительного сохранения через ReportMonitorAction(monitorHandle, action) ([SWS_DM_01698]).
  5. Деактивация: перед завершением работы или при временной деактивации пересылки диагностики вызывается StopOffer() ([SWS_DM_01700]).

Диаграмма последовательности: типичный порядок вызовов для конфигурации, предоставления и сообщения о состоянии нескольких диагностических мониторов. Источники: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01698], [SWS_DM_01699], [SWS_DM_01700].

Сценарии ошибок

Ошибочные ситуации в MultipleMonitor сигнализируются частью через стандартизированные нарушения платформы (Violations), частью через ara::core::Result со специфическими кодами ошибок:

  • Нарушения модели и процесса при конструировании: если сопоставление InstanceSpecifier завершается сбоем, возникают документированные нарушения времени выполнения ([SWS_DM_01695]):
    • InstanceSpecifierMappingIntegrityViolation: идентификатор не может быть разрешен в модели Executable или не ссылается на PortPrototype.
    • PortInterfaceMappingViolation: порт, на который указывает ссылка, не типизирован с помощью DiagnosticMultipleMonitorInterface.
    • ProcessMappingViolation: для смоделированного процесса во время выполнения отсутствует подходящий контекст процесса.
    • InstanceSpecifierAlreadyInUseViolation: идентификатор в работающем процессе уже занят другим экземпляром.
  • Ошибки конфигурации: вызов ConfigureMonitor в случае ошибки возвращает DiagErrc::kInvalidArgument ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). Это происходит, например, если переданы недопустимые параметры или противоречивые состояния устранения дребезга (например, kPreFailed при внутреннем устранении дребезга).
  • Ошибки предоставления: если Offer() вызывается, когда сервис уже предлагается, операция завершается сбоем с кодом ошибки DiagOfferErrc::kAlreadyOffered ([SWS_DM_01699]).
  • Недопустимые дескрипторы мониторов при отправке отчетов: если в ReportMonitorAction передается несконфигурированный или некорректный monitorHandle, вызов не прерывается, а согласно спецификации молчаливо игнорируется ([SWS_DM_01698]).

Данное руководство по классу основано на требованиях AUTOSAR Adaptive Platform для модуля Diag (Release R25-11).
