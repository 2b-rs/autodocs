Объединяет результаты диагностических тестов нескольких мониторов и управляет ими через общий адаптивный интерфейс порта.

Класс ara::diag::MultipleMonitor объединяет операции мониторинга нескольких диагностических мониторов через общий интерфейс порта в системе AUTOSAR [SWS_DM_01695]. Перед отправкой результатов тестов каждый монитор должен быть сконфигурирован индивидуально, а общий сервис должен быть активирован для Diagnostic Management через Offer [SWS_DM_01696]. Поскольку операции копирования и перемещения полностью запрещены, каждый экземпляр жестко привязан к контексту своего создания. Некорректные дескрипторы мониторов во время штатной работы отказоустойчиво игнорируются при отправке сообщений о статусе.

Контекст

Класс ara::diag::MultipleMonitor служит для реализации операций мониторов через интерфейсы для нескольких мониторов (Multiple Monitor Interfaces) в рамках AUTOSAR Adaptive Platform [SWS_DM_01695]. В отличие от интерфейсов для одиночных мониторов, MultipleMonitor объединяет мониторинг ошибок и отправку отчетов о статусе нескольких диагностических мониторов через общий PortPrototype, который в модели должен быть типизирован через DiagnosticMultipleMonitorInterface [SWS_DM_01695].

При этом вся система задействует трех ключевых партнеров по взаимодействию:

  • Прикладное программное обеспечение: инстанцирует класс, конфигурирует отдельные мониторы и циклически либо по событиям передает результаты тестов, а также указания по устранению дребезга [SWS_DM_01695], [SWS_DM_01698].
  • MultipleMonitor: управляет конфигурациями мониторов, принимает отчеты о действиях и обеспечивает передачу данных в Diagnostic Management [SWS_DM_01696], [SWS_DM_01699].
  • Diagnostic Management (DM): обрабатывает информацию о статусе соответствующих путей мониторинга ошибок и после активации сервиса перенаправляет входящие сообщения запросов в обработчик мониторов [SWS_DM_01698], [SWS_DM_01699], [SWS_DM_01700].

Контекстная диаграмма: интеграция MultipleMonitor между прикладным программным обеспечением и Diagnostic Management. Источники: [SWS_DM_01695], [SWS_DM_01698], [SWS_DM_01699].

Жизненный цикл

Инстанцирование MultipleMonitor выполняется синхронно путем передачи ara::core::InstanceSpecifier, который устанавливает привязку к порту [SWS_DM_01695]. С точки зрения владения класс спроектирован как строго привязанный к месту ресурс: конструктор копирования [SWS_DM_02065], конструктор перемещения [SWS_DM_02066] и все операторы присваивания [SWS_DM_02063], [SWS_DM_02064] явно удалены (delete). Таким образом, экземпляр не может быть ни скопирован, ни перемещен.

Что касается состояния сервиса, после создания экземпляр изначально неактивен. Вызовом Offer() активируется перенаправление диагностических запросов со стороны DM [SWS_DM_01699]. С помощью StopOffer() это перенаправление можно целенаправленно снова заблокировать, например перед завершением работы или при реконфигурации [SWS_DM_01700].

Требования к параллелизму дифференцированы: конструктор объявлен как потокобезопасный [SWS_DM_01695]. Напротив, конфигурация монитора через ConfigureMonitor, а также механизмы управления сервисом Offer и StopOffer специфицированы как непотокобезопасные и требуют внешней координации вызовов [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700]. Потокобезопасность ReportMonitorAction является условной (conditional): она определяется через ConcurrencyType, заложенный в контексте конструирования [SWS_DM_01698]. Интерпретация: поскольку конструктор C++ принимает исключительно InstanceSpecifier, этот ConcurrencyType, вероятно, настраивается через манифест, заданный в модели. Вопрос Q-33b384f8537e387b (открытый)

Путь использования

Типичное использование MultipleMonitor следует фиксированной последовательности фаз:

  1. Создание: создание объекта с спроектированным InstanceSpecifier [SWS_DM_01695].
  2. Конфигурация: каждый назначенный монитор перед использованием должен быть сконфигурирован ровно один раз через перегрузку ConfigureMonitor [SWS_DM_01696]. При этом на выбор доступны четыре вида устранения дребезга:
    • без устранения дребезга с регистрацией InitMonitorNotifier [SWS_DM_01973],
    • устранение дребезга по времени со значениями по умолчанию TimeBased [SWS_DM_01697],
    • устранение дребезга по счетчику со значениями по умолчанию CounterBased [SWS_DM_01702] или
    • внутреннее для монитора устранение дребезга с передачей указателя на функцию для опроса текущего счетчика обнаружения неисправностей (FDC) [SWS_DM_01696].
  3. Активация: вызов Offer(), чтобы позволить Diagnostic Management пересылать запросы [SWS_DM_01699].
  4. Работа: непрерывная отправка результатов монитора или команд управления в DM через ReportMonitorAction с передачей соответствующего monitorHandle и action [SWS_DM_01698].
  5. Завершение: вызов StopOffer() для отключения пересылки сообщений запросов [SWS_DM_01700].

Диаграмма последовательности: фазы жизненного цикла и цикла использования MultipleMonitor. Источники: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01698], [SWS_DM_01700].

Сценарии ошибок

Спецификация определяет для MultipleMonitor четкое поведение при ошибках и исключениях:

  • Нарушения интеграции и моделирования (Violations):\nПри инстанцировании фреймворк проверяет согласованность модели [SWS_DM_01695]:
    • InstanceSpecifierMappingIntegrityViolation: идентификатор не указывает на PortPrototype или не может быть разрешен в модели.
    • PortInterfaceMappingViolation: порт не типизирован DiagnosticMultipleMonitorInterface.
    • ProcessMappingViolation: для исполняемого процесса отсутствует подходящий смоделированный процесс.
    • InstanceSpecifierAlreadyInUseViolation: идентификатор уже используется другим экземпляром в том же процессе.
  • Ошибки конфигурации:\nВсе перегрузки ConfigureMonitor возвращают ara::core::Result<void>. При некорректных параметрах, таких как недопустимые значения устранения дребезга или семантика отката (например, kPreFailed при внутреннем устранении дребезга), возвращается ошибка DiagErrc::kInvalidArgument [SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973].
  • Ошибка активации службы:\nЕсли Offer() вызывается, когда служба уже активно предлагается, вызов завершается с кодом ошибки DiagOfferErrc::kAlreadyOffered [SWS_DM_01699].
  • Отказоустойчивость при сообщениях о действиях:\nМетод ReportMonitorAction не возвращает код ошибки (тип возвращаемого значения void). Если он вызывается с недопустимым или неизвестным monitorHandle, вызов в соответствии со спецификацией автоматически игнорируется [SWS_DM_01698].

Данное руководство основано на спецификации AUTOSAR Adaptive Platform R25-11 и подготовлено в автоматическом режиме.

Использование

Метод ara::diag::MultipleMonitor::ConfigureMonitor инициализирует диагностический монитор для внутримониторного устранения дребезга [SWS_DM_01696]. Через параметр monitorHandle адресуется настраиваемый монитор, в то время как с помощью initMonitor регистрируется callback-функция уведомления для реинициализаций, а с помощью getFaultDetectionCounter — функция для опроса текущего значения счетчика сбоев (FDC) [SWS_DM_01696]. Выполнение происходит синхронно и возвращает ara::core::Result<void> AUTOSAR_AP_SWS_Diagnostics §8.44.2.1.3.4 «ConfigureMonitor».

Обработка ошибок и параллелизм

В случае ошибки возвращается ошибочный результат DiagErrc::kInvalidArgument [SWS_DM_01696]. Предположительно, это происходит в частности тогда, когда передаются недопустимые указатели на функции или присутствуют несовместимые состояния при внутреннем устранении дребезга (интерпретация). Вопрос Q-3de0f2b0cc427ef3 (открытый) Операция специфицирована как noexcept, а также как исключениебезопасная (exception safe), однако прямо обозначена как непотокобезопасная (not thread-safe) [SWS_DM_01696]. Поэтому вызовы на одном и том же экземпляре монитора должны синхронизироваться со стороны приложения.

Порядок и взаимодействие

Каждая перегрузка ConfigureMonitor может вызываться для монитора строго один раз; монитор готов к работе только после этого шага инициализации [SWS_DM_01696]. При внутримониторном устранении дребезга приложение диагностического монитора обрабатывает логику устранения дребезга самостоятельно и передает в Diagnostic Management только окончательные результаты AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.5.3 «Monitor-internal debouncing». Для других механизмов устранения дребезга предусмотрены альтернативные перегрузки для мониторинга на основе времени [SWS_DM_01697], на основе счетчика [SWS_DM_01702] или без устранения дребезга [SWS_DM_01973].

Это указание по использованию создано автоматически на основе спецификации.

      Использование
      

      Синхронная функция-член ara::diag::MultipleMonitor::ConfigureMonitor из заголовочного файла ara/diag/multiple_monitor.h конфигурирует диагностический монитор с устранением дребезга на основе времени ([SWS_DM_01697], SWS Diagnostics §8.44.2.1.3.2 «ConfigureMonitor(MonitorHandleType, InitMonitorNotifier, TimeBased)»). При вызове передаются дескриптор monitorHandle для идентификации монитора, callback-функция initMonitor типа InitMonitorNotifier, а также параметры устранения дребезга defaultValues типа TimeBased ([SWS_DM_01697]). В качестве возвращаемого значения служит ara::core::Result<void>, а сигнатура функции объявлена как noexcept ([SWS_DM_01697]).
      


      Условия вызова и параллелизм
      

      Монитор может использоваться только после завершения этого шага инициализации ([SWS_DM_01697]). Каждый перегруженный вариант ConfigureMonitor может быть вызван для одного экземпляра монитора строго один раз ([SWS_DM_01697]). Интерфейс хотя и является исключениебезопасным (exception safe), но не потокобезопасен (not thread-safe), поэтому параллельные вызовы на одном и том же экземпляре должны синхронизироваться со стороны пользователя ([SWS_DM_01697]).
      


      Обработка ошибок
      

      Если конфигурация завершается неудачно, вызов возвращает объект ошибки внутри ara::core::Result, в частности код ошибки DiagErrc::kInvalidArgument ([SWS_DM_01697]).
      


      Взаимодействие

                                    •
