Контекст

Класс ara::diag::ServiceValidation представляет собой функциональный элемент интерфейса для валидации входящих диагностических запросов в модуле AUTOSAR Adaptive diag с учётом специфики производителя и поставщика [SWS_DM_00772]. В зависимости от моделирования атрибута DiagnosticServiceValidationMapping.category валидация с помощью метода Validate выполняется либо как проверка производителя, либо как проверка поставщика в рамках очерёдности кодов отрицательного ответа (NRC) согласно главе 8.7 стандарта ISO 14229-1 [SWS_DM_00772].

Во взаимодействии в основном участвуют три стороны:

  • Адаптивное приложение: реализует конкретную логику валидации путём специализации виртуальных методов Validate [SWS_DM_00774] и Confirmation [SWS_DM_00775].
  • Diagnostic Management (DM): принимает запросы UDS, перенаправляет их после успешной активации с помощью Offer для предварительной проверки в экземпляр [SWS_DM_00776] и сообщает об окончательном завершении через Confirmation [SWS_DM_00775].
  • Диагностический тестер: инициирует диагностические сообщения, необработанные данные и метаинформация которых являются предметом проверки [SWS_DM_00774].

Жизненный цикл

Инстанцирование ServiceValidation осуществляется явно путём передачи ara::core::InstanceSpecifier, который должен указывать на смоделированный PortPrototype объекта DiagnosticServiceValidationInterface [SWS_DM_00772]. Конструктор специфицирован как потокобезопасный [SWS_DM_00772]. Экземпляр ServiceValidation нельзя ни копировать, ни перемещать: конструктор копирования [SWS_DM_01689], оператор присваивания [SWS_DM_01687], конструктор перемещения [SWS_DM_01690] и оператор присваивания перемещением [SWS_DM_01688] явно удалены (= delete).

После конструирования экземпляр находится в состоянии Не предлагается. Вызовом Offer() разблокируется перенаправление входящих запросов со стороны Diagnostic Management [SWS_DM_00776]. Если обработку требуется приостановить или завершить, вызов StopOffer() блокирует пересылку дальнейших диагностических сообщений [SWS_DM_00777]. Активацию можно возобновить повторным вызовом Offer(). Окончательное уничтожение выполняется через виртуальный деструктор ~ServiceValidation() [SWS_DM_00773].

С точки зрения параллелизма методы Offer, StopOffer, Validate, Confirmation, а также деструктор классифицированы как непотокобезопасные [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Вызовы этих операций при конкурентном доступе должны синхронизироваться приложением.

Диаграмма состояний: жизненный цикл и переходы между состояниями экземпляра ServiceValidation. Источники: [SWS_DM_00772], [SWS_DM_00773], [SWS_DM_00776], [SWS_DM_00777].

Путь использования

Типовой порядок действий по защите диагностических служб подразделяется на следующие шаги:

  1. Инстанцирование: приложение создаёт экземпляр с привязкой к смоделированному порту [SWS_DM_00772].
  2. Активация: вызов Offer(). Diagnostic Management получает команду перенаправлять входящие диагностические сообщения в этот экземпляр [SWS_DM_00776].
  3. Валидация: при каждом входящем диагностическом запросе DM вызывает метод Validate [SWS_DM_00774]. Передаются данные запроса (включая идентификатор службы) в виде ara::core::Span<const std::uint8_t>, а также контекст через MetaInfo. Данные запроса остаются действительными до тех пор, пока не будет выполнено соответствующее Promise или пока обработка не будет отменена через CancellationHandler [SWS_DM_00774].
  4. Асинхронный результат: метод возвращает ara::core::Future<void> [SWS_DM_00774]. При успешной валидации Future разрешается без ошибок. Если запрос недопустим, Future завершается с соответствующим кодом отрицательного ответа (NRC) из DiagUdsNrcErrc согласно ISO 14229-1 [SWS_DM_00774].
  5. Подтверждение завершения: как только обработка диагностического запроса полностью завершена, DM вызывает Confirmation для передачи общего результата (status) и metaInfo [SWS_DM_00775].
  6. Отмена регистрации: перед завершением работы приложение вызывает StopOffer() [SWS_DM_00777]. Интерпретация: после вызова StopOffer() выполняющиеся запросы на валидацию, чьё Future ещё не было выполнено, вероятно, либо отбрасываются, либо прерываются со стороны DM.

Диаграмма последовательности: последовательность взаимодействия между приложением, обработчиком ServiceValidation и Diagnostic Management (DM). Источники: [SWS_DM_00774], [SWS_DM_00775], [SWS_DM_00776], [SWS_DM_00777].

Сценарии ошибок

Ошибочные ситуации могут возникать на различных этапах и сигнализируются с помощью специализированных механизмов:

  • Нарушения при конструировании и моделировании: в случае сбоя связывания InstanceSpecifier фреймворк сообщает об определённых Violations [SWS_DM_00772]:
    • InstanceSpecifierMappingIntegrityViolation: Идентификатор не удается разрешить или он не указывает на PortPrototype.
    • PortInterfaceMappingViolation: PortPrototype не типизирован с помощью DiagnosticServiceValidationInterface.
    • ProcessMappingViolation: для ссылки не существует подходящего смоделированного процесса для текущего процесса времени выполнения.
    • InstanceSpecifierAlreadyInUseViolation: InstanceSpecifier уже используется другим экземпляром в работающем процессе.
  • Ошибочная активация: если Offer() вызывается в момент, когда служба уже предлагается, вызов завершается с ошибкой и возвращает код ошибки DiagOfferErrc::kAlreadyOffered с семантикой отката в возвращаемом значении ara::core::Result<void> [SWS_DM_00776].
  • Ошибка валидации: если проверка обнаруживает нарушенное условие (например, недостаточные предварительные условия или требования безопасности), ошибка передаётся через DiagUdsNrcErrc в ara::core::Future<void> [SWS_DM_00774]. Поскольку Validate объявлен как noexcept, генерация исключений C++ запрещена.
  • Безопасность исключений: все методы класса специфицированы как безопасные с точки зрения исключений (exception safe) и аннотированы noexcept [SWS_DM_00772] [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Состояния ошибок без исключения отображаются через типы возвращаемых значений и сообщения платформы.

Настоящее руководство по классу основано на требованиях спецификации AUTOSAR Adaptive Platform R25-11.
