Контекст

Класс ara::diag::DataTransferReadByPullHandler служит для стандартизированной обработки передачи данных для чтения, инициируемой такими диагностическими запросами, как RequestReadFile или RequestReadDirectory AUTOSAR_AP_SWS_Diagnostics §8.10.2 «Class: DataTransferReadByPullHandler», [SWS_DM_01506]. Он выступает в качестве интерфейса между диагностическим фреймворком AraDiag и фактической реализацией приложения.

Концепция передачи основана на механизме pull: AraDiag последовательно запрашивает фрагменты данных из реализации приложения, чтобы затем передать их UDS-клиенту (диагностическому тестеру) [SWS_DM_01513]. При этом класс инкапсулирует специфичное для приложения предоставление содержимого файлов или каталогов в контексте служб передачи UDS.

Контекстная диаграмма: интеграция обработчика между UDS-клиентом, фреймворком AraDiag и приложением. Источники: [SWS_DM_01506], AUTOSAR_AP_SWS_Diagnostics §8.10.2 «Class: DataTransferReadByPullHandler»

Жизненный цикл

Для экземпляров DataTransferReadByPullHandler действуют строгие правила создания, владения и уничтожения:

  • Создание: конструктор по умолчанию объявлен как protected и noexcept=default [SWS_DM_01507]. Интерпретация: поскольку класс содержит чисто виртуальные интерфейсные методы, а конструктор по умолчанию защищен, прикладному программному обеспечению, вероятно, следует реализовать и инстанцировать собственный производный класс обработчика.
  • Запрет копирования: как конструктор копирования [SWS_DM_01509], так и оператор присваивания копированием [SWS_DM_01512] явно удалены (=delete). Обработчик предназначен ровно для одного сеанса передачи файла (single file transfer session) и не подлежит копированию AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.2 «Constructors».
  • Перемещение: конструктор перемещения [SWS_DM_01508] и присваивание перемещением [SWS_DM_01511] определены как noexcept=default AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1 «Special Member Functions», что обеспечивает поддержку передачи владения.
  • Условие уничтожения: деструктор является виртуальным и специфицирован как noexcept=default [SWS_DM_01510]. Ключевым инвариантом является то, что экземпляр ни в коем случае не должен уничтожаться до того, как был вызван ExitRead() [SWS_DM_01510], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1.2 «Destructor».
  • Параллелизм: виртуальные интерфейсные методы Read() и ExitRead() классифицированы как непотокобезопасные (not thread-safe) [SWS_DM_01513], [SWS_DM_01514].

Путь использования

Типичная последовательность вызовов при передаче данных для чтения на основе pull включает две основные фазы:

  1. Цикл чтения pull: во время текущей передачи AraDiag повторно вызывает метод Read() обработчика [SWS_DM_01513]. При этом AraDiag передает представление памяти response_data (типа ara::core::Span<const ara::core::Byte>) на предварительно выделенный буфер, а также meta_info и cancellation_handler. Реализация приложения формирует содержимое следующего блока данных и копирует его в буфер в пределах максимального размера диапазона (span) [SWS_DM_01513].
  2. Возврат фрагмента: Read() возвращает ara::core::Future<std::uint32_t>. Future выполняется с количеством байтов, фактически записанных в буфер [SWS_DM_01513]. AraDiag встраивает эти полезные данные в положительный ответ UDS непосредственно после blockSequenceCounter в виде transferResponseParameterRecord [SWS_DM_01513], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 «Read».
  3. Завершение сеанса: как только все данные переданы или передачу необходимо завершить, AraDiag вызывает ExitRead() [SWS_DM_01514]. Передаются причина завершения (exit_type типа DataTransferExitType), специфичные для автопроизводителя параметры (transfer_request_parameter_record), а также метаданные и обработчик отмены [SWS_DM_01514].
  4. Конец транзакции: приложение подтверждает завершение сеанса через ara::core::Future<ara::core::Vector<ara::core::Byte>>. В случае положительного подтверждения содержащиеся в векторе данные помещаются после идентификатора службы (SID) в качестве transferResponseParameterRecord в положительный ответ UDS [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 «ExitRead». Экземпляр обработчика разрешается уничтожать только после этого вызова [SWS_DM_01510].

Диаграмма последовательности: последовательность вызовов при итеративном чтении pull и последующем ExitRead. Источники: [SWS_DM_01513], [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 «ExitRead», AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 «Read»

Сценарии ошибок

Спецификация определяет четкие требования для состояний ошибок и исключительных ситуаций:

  • Коды ошибок UDS (NRC): если при считывании блока данных или при завершении передачи возникает ошибка, соответствующее future не выполняется в штатном режиме. Вместо этого future должно быть завершено в состоянии ошибки с подходящим кодом отрицательного ответа (NRC) из DiagUdsNrcErrc согласно ISO 14229-1 [SWS_DM_01513], [SWS_DM_01514]. На его основе AraDiag формирует сообщение с отрицательным ответом UDS.
  • Обработка отмены: параметры cancellation_handler позволяют приложению активно проверять с помощью cancellation_handler.IsCanceled(), был ли отменен диагностический диалог [SWS_DM_01513], [SWS_DM_01514]. В качестве альтернативы с помощью cancellation_handler.SetNotifier() можно зарегистрировать функцию обратного вызова, которая вызывается фреймворком при отмене диалога [SWS_DM_01513], [SWS_DM_01514].
  • Срок действия буферов: переданный AraDiag буфер response_data в Read(), а также transfer_request_parameter_record в ExitRead() имеют ограниченное время жизни. Они действительны только до тех пор, пока не будет выполнено соответствующее promise или пока обработка не будет отменена через cancellation_handler [SWS_DM_01513], [SWS_DM_01514].
  • Преждевременное уничтожение: уничтожение экземпляра DataTransferReadByPullHandler до выполнения ExitRead() представляет собой нарушение условий контракта API [SWS_DM_01510].

Настоящее руководство основано на спецификации AUTOSAR Adaptive Platform R25-11 (модуль diag) и создано автоматически.
