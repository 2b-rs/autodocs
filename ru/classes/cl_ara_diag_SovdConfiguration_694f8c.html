Контекст

Класс ara::diag::SovdConfiguration представляет собой обобщенный интерфейс для SOVD-конфигураций (Service-Oriented Vehicle Diagnostics) на AUTOSAR Adaptive Platform ([SWS_DM_01860], AUTOSAR_AP_SWS_Diagnostics §8.54.1 «Class: SovdConfiguration»). Как только в системе смоделирована хотя бы одна SOVD-конфигурация, экземпляр Diagnostic Server предоставляет стандартизированный SOVD-метод для перечисления всех предоставленных конфигураций ([SWS_DM_01429], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2 «SOVD API – Configuration»).

Для явно смоделированных SOVD-конфигураций производный экземпляр ara::diag::SovdConfiguration действует как обработчик приложения. Diagnostic Server (DM) выступает в качестве посредника: входящие внешние запросы по SOVD-методам Read Configuration и Write Configuration принимаются сервером Diagnostic Server и перенаправляются приложению через методы интерфейса RequestGetConfiguration ([SWS_DM_01787]) и RequestPutConfiguration ([SWS_DM_01788]) соответственно.

Контекстная диаграмма: встраивание ara::diag::SovdConfiguration между внешним SOVD-клиентом и Diagnostic Server. Источники: [SWS_DM_01787], [SWS_DM_01788], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 «Configuration – Explicit Configurations»

Жизненный цикл

Классы приложения наследуют от ara::diag::SovdConfiguration и инстанцируют объект через конструктор, который требует ara::core::InstanceSpecifier, а также ConcurrencyType ([SWS_DM_01864]). InstanceSpecifier связывает объект со смоделированным прототипом порта.

С точки зрения отношений владения класс спроектирован как единственный экземпляр: как конструктор копирования ([SWS_DM_01866]), так и оператор присваивания с копированием ([SWS_DM_01868]) удалены (delete). Операции перемещения (конструктор перемещения и оператор присваивания с перемещением) объявлены как protected и noexcept ([SWS_DM_01867], [SWS_DM_01869]).

После инстанцирования объект сначала находится в неактивном состоянии. Только вызов Offer() дает возможность демону Diagnostic Management пересылать запросы для этого обработчика ([SWS_DM_01872]). Если сервис больше не должен быть доступен, пересылка деактивируется через StopOffer() ([SWS_DM_01930]). Для уничтожения объекта служит виртуальный деструктор ~SovdConfiguration() ([SWS_DM_01865]). Интерпретация: в штатном сценарии завершения работы перед уничтожением объекта, вероятно, должен вызываться StopOffer(), чтобы исключить асинхронный доступ во время выполнения деструктора.

Что касается параллелизма, конструктор является потокобезопасным ([SWS_DM_01864]), тогда как Offer() ([SWS_DM_01872]), StopOffer() ([SWS_DM_01930]) и деструктор ([SWS_DM_01865]) не потокобезопасны. Потокобезопасность методов обработчика RequestGetConfiguration ([SWS_DM_01870]) и RequestPutConfiguration ([SWS_DM_01871]) является условной: она зависит от того, был ли при конструировании передан ConcurrencyType::kConcurrent или ConcurrencyType::kNotConcurrent.

Путь использования

Типичный сценарий использования для обработки запросов SOVD-конфигурации включает следующие этапы:

  1. Инициализация: приложение инстанцирует производный класс с подходящим InstanceSpecifier и требуемым режимом параллелизма ([SWS_DM_01864]).
  2. Предоставление сервиса: вызовом Offer() активируется пересылка запросов ([SWS_DM_01872]).
  3. Обработка запроса (чтение): если SOVD-запрос на чтение поступает на Diagnostic Server ([SWS_DM_01787]), он вызывает RequestGetConfiguration ([SWS_DM_01870]). Приложение обрабатывает переданные configurationId, а также MetaInfo, отслеживает CancellationHandler и возвращает ara::core::Future с std::tuple из DataTransferReadSession и SovdConfigurationMetaInfo.
  4. Обработка запроса (запись): при запросе на запись ([SWS_DM_01788]) сервер вызывает RequestPutConfiguration ([SWS_DM_01871]), после чего приложение предоставляет Future с DataTransferWriteSession и метаинформацией.
  5. Завершение сервиса: перед завершением работы компонента приложение деактивирует прием дальнейших запросов через StopOffer() ([SWS_DM_01930]).

Диаграмма последовательности: предоставление сервиса и асинхронная обработка SOVD-запроса на чтение. Источники: [SWS_DM_01787], [SWS_DM_01870], [SWS_DM_01872], [SWS_DM_01930]

Сценарии ошибок

Ошибочные ситуации могут возникать на различных этапах взаимодействия:

  • Нарушения конструирования: при вызове конструктора ([SWS_DM_01864]) могут возникать ошибки моделирования и сопоставления:
    • InstanceSpecifierMappingIntegrityViolation: идентификатор не может быть разрешен в контексте исполняемого файла или не указывает на PortPrototype.
    • PortInterfaceMappingViolation: PortPrototype не типизирован с помощью DiagnosticSovdConfigurationInterface.
    • ProcessMappingViolation: отсутствует сопоставление с подходящим смоделированным процессом.
    • InstanceSpecifierAlreadyInUseViolation: InstanceSpecifier уже используется внутри процесса.
  • Ошибки при предоставлении (Offer): Offer() возвращает ara::core::Result<void> ([SWS_DM_01872]). Возможные коды ошибок:
    • DiagOfferErrc::kConfigurationMismatch: конфигурация мониторинга не совпадает с DEXT (семантика отката).
    • DiagOfferErrc::kAlreadyOffered: сервис уже предлагался ранее (семантика отката).
  • Ошибки при обработке конфигурации: если чтение или запись экземпляра конфигурации завершается сбоем, реализация через Future, возвращенный RequestGetConfiguration ([SWS_DM_01870]) или RequestPutConfiguration ([SWS_DM_01871]), передает стандартизированный код ошибки SOVD согласно ISO 17978-3 / ASAM SOVD 1.1. Кроме того, CancellationHandler сигнализирует, если текущая беседа была прервана.

Настоящее руководство основано на спецификации AUTOSAR Adaptive R25-11 (модуль diag) и описывает интеграцию, а также правила жизненного цикла класса ara::diag::SovdConfiguration.
