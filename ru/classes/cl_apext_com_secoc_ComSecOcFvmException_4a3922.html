Контекст

Класс apext::com::secoc::ComSecOcFvmException определяет специализированный тип исключения для защищенной бортовой коммуникации (SecOC) в рамках AUTOSAR Adaptive Platform [SWS_CM_12512]. Его основная ответственность заключается в сигнализации об ошибочных ситуациях, инициируемых Freshness Value Manager (FVM) в процессе работы AUTOSAR_AP_SWS_CommunicationManagement §C.2.4 «Class: ComSecOcFvmException». SecOC гарантирует подлинность и актуальность передаваемых сообщений для защиты от атак повторного воспроизведения, при этом FVM отвечает за предоставление, обновление и проверку значений свежести.

Архитектурно класс расположен в пространстве имен apext::com::secoc и открыто наследует базовый класс ara::core::Exception. Благодаря этой иерархии наследования класс исключений полностью интегрируется в базовую модель обработки ошибок Adaptive Platform. В то время как большая часть модуля Communication Management передает ошибочные результаты операций преимущественно через типы возвращаемых значений на основе значений, такие как ara::core::Result, ComSecOcFvmException предоставляет стандартизированный канал для оповещения вызывающих экземпляров об особых состояниях ошибок управления значениями свежести через механизм исключений C++.

Жизненный цикл

Жизненный цикл экземпляра ComSecOcFvmException начинается при обнаружении ошибки внутри Freshness Value Manager. Создание выполняется контролируемо через единственный открытый конструктор класса, который должен быть явно вызван с экземпляром ara::core::ErrorCode [SWS_CM_12513]. Сигнатура explicit ComSecOcFvmException(ara::core::ErrorCode errorCode) noexcept; исключает нежелательные неявные преобразования типов и гарантирует благодаря спецификации как noexcept и безопасности относительно исключений (exception safe), что во время конструирования самого объекта исключения не могут возникнуть другие ошибки AUTOSAR_AP_SWS_CommunicationManagement §C.2.4.1.1.1 «ComSecOcFvmException».

Что касается отношений владения, исключение инстанциируется и немедленно передается среде выполнения C++ с помощью throw. Во время раскрутки стека объект исключения подчиняется управлению жизненным циклом среды выполнения, пока не будет связан в подходящем блоке catch. После прохождения обработчика исключения объект автоматически уничтожается при выходе из области видимости. Поскольку класс по существу инкапсулирует переданный код ошибки и не управляет эксклюзивными динамическими системными ресурсами, копирование является эффективным, а уничтожение не имеет побочных эффектов. В конкурентных средах каждый объект исключения действует локально для потока, поэтому механизмы синхронизации между потоками не требуются.

Путь использования

Типичный сценарий использования включает инстанцирование в случае ошибки со стороны Freshness Value Manager, перенаправление через механизм исключений, а также перехват и анализ в вызывающем контексте приложения. Чтобы иметь возможность использовать интерфейс, необходимо подключить заголовочный файл apext/com/secoc/fvm_error_domain.h [SWS_CM_12513].

Обычный процесс сценария обработки ошибок делится на следующие фазы:

  1. Обнаружение ошибки: SecOC Freshness Value Manager определяет нештатное условие во время управления значениями свежести, например, сбой синхронизации или недопустимое состояние.
  2. Генерация кода ошибки: FVM идентифицирует причину ошибки и генерирует соответствующий ara::core::ErrorCode. Интерпретация: поскольку объявление класса подключается через заголовок apext/com/secoc/fvm_error_domain.h, переданные коды ошибок, вероятно, поступают преимущественно из Error Domain, специфичного для FVM.
  3. Конструирование исключения: через конструктор ComSecOcFvmException безопасно относительно исключений создается объект исключения с передачей кода ошибки [SWS_CM_12513].
  4. Возбуждение исключения: экземпляр возбуждается с помощью throw, в результате чего нормальный поток управления прерывается и инициируется раскрутка стека.
  5. Перехват и обработка: вызывающая сторона перехватывает исключение. Интерпретация: перехват исключения на практике, вероятно, происходит по ссылке на apext::com::secoc::ComSecOcFvmException или полиморфно на базовый класс ara::core::Exception. Затем считывается встроенный ara::core::ErrorCode для принятия последующих мер.

Диаграмма последовательности: типичный процесс обработки исключения при ошибке в Freshness Value Manager. Источники: [SWS_CM_12512], [SWS_CM_12513], AUTOSAR_AP_SWS_CommunicationManagement §C.2.4.1.1.1 «ComSecOcFvmException».

Сценарии ошибок

Являясь носителем информации об ошибках, ComSecOcFvmException сам по себе не предоставляет подверженных ошибкам операций, а отражает результат сценариев ошибок внутри FVM. Существенным предварительным условием для создания является передача действительного ara::core::ErrorCode в конструктор [SWS_CM_12513]. Гарантия noexcept конструктора обеспечивает то, что сама передача ошибки никогда не завершится сбоем.

На уровне системной архитектуры следует обратить внимание на следующие критические ситуации:

  • Необработанные исключения: если выброшенное ComSecOcFvmException не перехвачено в стеке вызовов подходящим блоком catch, это приводит к вызову std::terminate и, следовательно, к аварийному завершению процесса. Вызывающие стороны функционала FVM должны предусмотреть соответствующие блоки.
  • Потеря контекста ошибки: если исключение обрабатывается только как общее исключение C++ без опроса содержащегося ara::core::ErrorCode, детальная причина ошибки теряется для целей диагностики и логирования.
  • Недопустимое состояние ошибки: корректность анализа ошибок зависит от того, чтобы переданный ErrorCode точно отражал возникшее состояние ошибки в Freshness Value Manager.
