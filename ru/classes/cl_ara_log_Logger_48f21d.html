класс ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Инкапсулирует контекст логирования для потокобезопасной регистрации форматированных или моделированных сообщений журнала.

Класс ara::log::Logger представляет контекст для регистрации сообщений журнала внутри процесса приложения через временные потоки или моделированные форматы сообщений [SWS_LOG_00064]. Поскольку конструктор по умолчанию удален, создание и управление жизненным циклом полностью осуществляются фреймворком логирования [SWS_LOG_00259]. Перед ресурсоемкой подготовкой данных сообщения можно запросить текущий активный уровень логирования. Все интерфейсы класса специфицированы как потокобезопасные и допускают вызов из нескольких потоков без необходимости синхронизации.

Контекст

Класс ara::log::Logger представляет контекст логгера внутри процесса приложения или области процесса в модуле log. Такой контекст инкапсулирует конкретный ID контекста, соответствующее описание, а также стандартный уровень логирования. Разработчики приложений взаимодействуют с экземплярами логгера для передачи сообщений журнала во фреймворк логирования либо через объекты потоков, такие как LogStream [SWS_LOG_00064], либо в виде структурированных моделированных сообщений [SWS_LOG_00204]. Экземпляры выступают посредниками между внутренними потоками приложения и бэкендом логирования.

Контекстная диаграмма: интеграция логгера между приложением, фреймворком логирования и LogStream. Источники: [SWS_LOG_00064], [SWS_LOG_00259].

Жизненный цикл

Управление экземплярами подчиняется строгому владению со стороны фреймворка логирования. Чтобы обеспечить автоматическую регистрацию в бэкенде логирования при создании и дерегистрацию при завершении работы процесса приложения, конструктор по умолчанию удален [SWS_LOG_00259]. Приложения не должны и не могут напрямую инстанцировать объекты Logger, а вместо этого обязаны использовать функции создания ara::log::CreateLogger. Уничтожение и освобождение осуществляются через деструктор [SWS_LOG_00260], управляемый фреймворком логирования, благодаря чему пользователям не нужно заботиться о времени жизни.

С точки зрения конкурентности все методы доступа специфицированы как потокобезопасные (thread-safe), среди прочего [SWS_LOG_00070], [SWS_LOG_00255] и [SWS_LOG_00260]. Благодаря этому несколько параллельных потоков могут одновременно использовать один и тот же контекст логгера без необходимости в дополнительных механизмах синхронизации на стороне приложения.

Путь использования

Типичное использование логгера охватывает проверку текущей конфигурации, адаптацию пороговых значений и отправку сообщений:

  • Проверка полномочий вывода: перед трудоемкой подготовкой данных протоколирования с помощью IsEnabled можно запросить, выдается ли активно требуемый уровень логирования [SWS_LOG_00070].
  • Конфигурация: минимальное пороговое значение формирования сообщений экземпляра логгера можно переконфигурировать во время выполнения с помощью SetThreshold [SWS_LOG_00255].
  • Потоковое логирование: через специфические методы для отдельных уровней важности — LogFatal [SWS_LOG_00064], LogError [SWS_LOG_00065], LogWarn [SWS_LOG_00066], LogInfo [SWS_LOG_00067], LogDebug [SWS_LOG_00068] или LogVerbose [SWS_LOG_00069] — а также через динамический WithLevel [SWS_LOG_00131] создается объект LogStream. Он принимает данные через оператор <<. Обычно время жизни потокового объекта заканчивается с точкой с запятой инструкции [SWS_LOG_00064].
  • Смоделированные сообщения: в качестве альтернативы типизированные и смоделированные сообщения могут передаваться напрямую с помощью Log [SWS_LOG_00204] или с указанием атрибутов с помощью LogWith [SWS_LOG_00133].

Диаграмма последовательности: типичная последовательность при проверке пороговых значений и потоковом протоколировании. Источники: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064].

Сценарии ошибок

Интерфейсы класса в значительной степени специфицированы как noexcept и безопасные к исключениям (exception safe), что минимизирует непредвиденные прерывания во время выполнения [SWS_LOG_00070], [SWS_LOG_00255]. Тем не менее существуют формальные условия ошибок и граничные случаи:

  • Некорректные параметры модели: если Log вызывается с аргументами, не соответствующими спецификации смоделированного сообщения, программа на C++ построена некорректно (ill-formed) и дает сбой во время компиляции [SWS_LOG_00204].
  • Отсутствующие свойства атрибутов: если кортеж для LogWith содержит типы, не удовлетворяющие требуемым критериям атрибутов, функция не участвует в разрешении перегрузки [SWS_LOG_00133]. Исключение, по всей видимости, осуществляется через SFINAE или концепты.
  • Безопасность к исключениям при разрушении: деструктор ~Logger объявлен как not exception safe [SWS_LOG_00260]. По всей видимости, это связано с тем, что при отмене регистрации в бэкенде логирования могут возникать ошибки, которые нельзя распространять через исключения.

Данное руководство основано исключительно на спецификации AUTOSAR для модуля log в Adaptive Release R25-11.
