класс ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Контекст

Класс ara::log::Logger представляет контекст логирования внутри процесса приложения или области процессов AUTOSAR Adaptive. Такой контекст инкапсулирует ключевые свойства для протоколирования: ID контекста, соответствующее описание ID контекста, а также настраиваемый стандартный уровень логирования (Default Log Level). С помощью этих контекстов вывод журнала внутри системы дифференцируется и управляется.

В архитектуре системы ara::log::Logger выступает в качестве посредника между тремя участниками:

  • Процесс приложения (Application Process): использует экземпляры ara::log::Logger для отправки сообщений, динамического опроса или корректировки порогов фильтрации.
  • Фреймворк журналирования: сохраняет строгое владение («strong ownership») всеми экземплярами логгера, управляет их созданием с помощью фабричных функций, таких как ara::log::CreateLogger, и берет на себя внутреннее обслуживание (housekeeping).
  • Бэкенд журналирования: принимает непосредственно данные журнала; контексты логгера автоматически регистрируются в бэкенде во время фазы инициализации и отменяют регистрацию во время штатного завершения процесса.

Контекстная диаграмма: встраивание класса Logger во взаимодействии с приложением, фреймворком журналирования и бэкендом. Источники: [SWS_LOG_00259]

Жизненный цикл

Управление экземплярами ara::log::Logger строго контролируется фреймворком для обеспечения непрерывной синхронизации с бэкендом журналирования:

  • Создание и отношения владения: Конструктор по умолчанию явно удален (Logger() = delete, [SWS_LOG_00259]). Прямое инстанцирование приложением запрещено. Создание осуществляется контролируемым образом через такие функции, как ara::log::CreateLogger. Владение остается за фреймворком журналирования.
  • Регистрация и очистка: Контекст логгера при своем создании автоматически регистрируется в бэкенде журналирования. При завершении процесса отмена регистрации происходит автоматически, что освобождает разработчиков приложений от ручного управления жизненным циклом.
  • Уничтожение: Деструктор ~Logger() специфицирован ([SWS_LOG_00260]). Он объявлен потокобезопасным, однако указан как небезопасный относительно исключений («not exception safe») ([SWS_LOG_00260]).
  • Параллелизм: Все методы для журналирования и запроса пороговых значений специфицированы как потокобезопасные ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). Несколько потоков могут параллельно использовать один и тот же экземпляр логгера.

Путь использования

Типичный процесс отправки сообщений журнала делится на следующие фазы:

  1. Проверка или настройка порога фильтрации: Приложение может задать порог фильтрации экземпляра во время выполнения через SetThreshold(threshold) ([SWS_LOG_00255]). Перед ресурсоемкой подготовкой данных журнала с помощью IsEnabled(logLevel) можно запросить, соответствует ли требуемый уровень журналирования настроенному порогу отчетности ([SWS_LOG_00070]). Если проверка возвращает false, подготовку можно пропустить.
  2. Инициация потокового журналирования: Для текстового журналирования класс предоставляет специфические методы для каждого уровня серьезности:
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • WithLevel(logLevel) ([SWS_LOG_00131]) для программного определения срочности.
    Каждый из этих методов возвращает объект LogStream, принимающий аргументы через оператор потока << ([SWS_LOG_00064]).
  3. Время жизни потока и вывод: В стандартном случае время жизни объекта LogStream ограничено одной инструкцией и заканчивается точкой с запятой после последнего аргумента ([SWS_LOG_00064]). При необходимости поток можно присвоить переменной, чтобы продлить его время жизни на несколько инструкций ([SWS_LOG_00064]).
  4. Вывод смоделированных сообщений: В качестве альтернативы потоковой передаче предварительно смоделированные сообщения могут быть выведены через Log(id, args...) ([SWS_LOG_00204]). Если необходимо передать дополнительные атрибуты, вызов выполняется через LogWith(attrs, msgId, params...) с кортежем атрибутов ([SWS_LOG_00133]).

Диаграмма последовательности: последовательность вызовов операции отфильтрованного потокового журналирования. Источники: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064]

Сценарии ошибок

Обработка ошибок в ara::log::Logger основана преимущественно на статической проверке типов во время компиляции и строгой безопасности исключений:

  • Несоответствующие аргументы для смоделированных сообщений: Если шаблонная функция Log(id, args...) вызывается с параметрами, которые не соответствуют в точности определению смоделированного сообщения, программа сформирована некорректно («ill-formed») ([SWS_LOG_00204]). Это приводит к ошибке во время компиляции.
  • Недопустимые атрибуты в LogWith: В LogWith(attrs, msgId, params...) функция исключается из разрешения перегрузки с помощью SFINAE, если элемент кортежа атрибутов не представляет собой допустимый атрибут ([SWS_LOG_00133]).
  • Гарантии безопасности исключений: Все функции журналирования и опроса (включая IsEnabled, SetThreshold, все методы Log*, WithLevel, Log и LogWith) специфицированы как безопасные относительно исключений («exception safe») и объявлены с noexcept ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). Исключением является деструктор ~Logger(), который указан как небезопасный относительно исключений («not exception safe») ([SWS_LOG_00260]). Интерпретация: по всей видимости, это означает, что при внутренних ошибках очистки или освобождения в рамках обслуживания бэкенда ошибочные состояния перехватываются не полностью, поэтому отмена регистрации должна происходить во время штатного завершения процесса.

Настоящее руководство было сгенерировано системой ИИ на основе спецификации AUTOSAR для R25-11.
