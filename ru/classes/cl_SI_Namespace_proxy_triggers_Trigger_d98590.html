Оформляет подписку на сервисные триггеры без данных и подсчитывает поступающие импульсы срабатывания для клиентского приложения.

Класс <SI-Namespace>::proxy::triggers::<Trigger> позволяет клиентским приложениям подписываться на триггерные импульсы без данных через Communication Management [SWS_CM_00723]. После регистрации обратного вызова через SetReceiveHandler() приложение считывает вновь поступившие импульсы с помощью GetNewTriggers() [SWS_CM_00226], [SWS_CM_00250]. Безопасность относительно исключений стандартно гарантируется за исключением UnsetReceiveHandler() [SWS_CM_11614].

Контекст

Сгенерированный прокси-класс <SI-Namespace>::proxy::triggers::<Trigger> представляет на стороне клиента ровно один триггерный элемент, смоделированный в сервисном интерфейсе в роли trigger AUTOSAR_AP_SWS_CommunicationManagement §8 «Service proxy Trigger class». В отличие от потоков данных на основе событий, триггер передает чистые импульсы срабатывания без полезных данных. Класс служит связующим звеном между использующим клиентским приложением, Communication Management (ara::com) и системой мониторинга E2E. Его основная задача заключается в управлении подпиской на входящие триггеры, регистрации обратных вызовов уведомлений о поступлении импульсов или изменениях статуса, а также в предоставлении количества поступивших срабатываний через счетчик [SWS_CM_00226], [SWS_CM_00250].

Жизненный цикл

Время жизни экземпляра <SI-Namespace>::proxy::triggers::<Trigger> привязано к времени жизни вышестоящего сервисного прокси-объекта, в котором он существует как член класса. С точки зрения состояний подписка на триггер проходит несколько фаз, которые отображаются через ara::com::SubscriptionState и могут быть запрошены через GetSubscriptionState() [SWS_CM_01105]:

  • Не подписано: исходное состояние до вызова Subscribe() или после успешного выполнения Unsubscribe() [SWS_CM_00723], [SWS_CM_00810].
  • Подписка ожидает подтверждения (kSubscriptionPending): промежуточное состояние после инициирования Subscribe() во время подтверждения подписки [SWS_CM_00723].
  • Подписано (kSubscribed): подписка активна; поступающие импульсы триггера инкрементируют внутренний счетчик и приводят к уведомлению зарегистрированного обработчика [SWS_CM_00226], [SWS_CM_00250].

Повторный вызов Subscribe() в состояниях kSubscribed или kSubscriptionPending не имеет эффекта и завершается без каких-либо действий [SWS_CM_00723]. Аналогично ведет себя Unsubscribe(), если подписка на триггер на момент вызова отсутствует [SWS_CM_00810]. Для наблюдения за переходами между состояниями приложение может задать соответствующий обратный вызов с помощью SetSubscriptionStateChangeHandler() [SWS_CM_01107] или разрегистрировать его через UnsetSubscriptionStateChangeHandler() [SWS_CM_01108].

Диаграмма состояний: жизненный цикл подписки на триггер с переходами через Subscribe и Unsubscribe. Источники: [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_01105].

Путь использования

Типичный сценарий использования для обработки триггерных сигналов, управляемой событиями, включает настройку обратных вызовов, активацию подписки и опрос счетчика:

  1. Регистрация обработчиков: приложение опционально задает обработчик состояния через SetSubscriptionStateChangeHandler() [SWS_CM_01107], а также в обязательном порядке обработчик приема через SetReceiveHandler() [SWS_CM_00250]. Для конкурентных архитектур доступны перегрузки с выделенным ExecutorT, определяющие контекст выполнения для асинхронных вычислений [SWS_CM_00352], [SWS_CM_01106].
  2. Запрос подписки: подписка на триггер запускается с помощью Subscribe() [SWS_CM_00723].
  3. Прием сигнала и опрос счетчика: как только поступает импульс триггера, Communication Management вызывает TriggerReceiveHandler без параметров [SWS_CM_00250]. Внутри этого обработчика приложение вызывает GetNewTriggers() для обновления счетчика триггера и считывания количества поступивших с момента последнего вызова импульсов [SWS_CM_00226]. При этом значение 0 сигнализирует об отсутствии новых импульсов.
  4. Завершение: для корректного освобождения ресурсов приложение вызывает Unsubscribe() [SWS_CM_00810] и удаляет установленные обработчики через UnsetReceiveHandler() [SWS_CM_11614], а также UnsetSubscriptionStateChangeHandler() [SWS_CM_01108].

Диаграмма последовательности: типичный процесс обработки триггеров от регистрации и подписки через прием сигналов до отмены регистрации. Источники: [SWS_CM_00226], [SWS_CM_00250], [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_11614].

Сценарии ошибок

Спецификация определяет конкретные условия нарушений (Violations) и гарантии безопасности исключений для методов интерфейса:

  • InvalidHandlerViolation: возникает, если в SetReceiveHandler() [SWS_CM_00250], [SWS_CM_00352], SetSubscriptionStateChangeHandler() [SWS_CM_01106], [SWS_CM_01107] или SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107] передается недопустимый или нулевой вызываемый объект (callable).
  • InsufficientPermissionsViolation: инициируется при Subscribe(), если контроль доступа (Grant Enforcement) отклоняет полномочия на подписку на триггер [SWS_CM_00723].
  • Ошибки транспорта в механизме E2E-защиты: сбойные состояния передачи сообщаются через обработчик, зарегистрированный с помощью SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107], регистрацию которого можно отменить через UnsetTransportFaultConditionHandler() [SWS_CM_00108].
  • Безопасность исключений: практически все операции объявлены как noexcept и являются безопасными к исключениям (exception safe) [SWS_CM_00226], [SWS_CM_00723]. Исключение составляет UnsetReceiveHandler(), который согласно спецификации явно классифицирован как небезопасный к исключениям (not exception safe) [SWS_CM_11614]; вероятно, данный вызов при ошибках может распространять исключения или требует отдельной обработки ошибок в клиентском приложении.

Данное руководство основано исключительно на спецификации AUTOSAR Adaptive R25-11 для модуля Communication Management.

          Использование
          

          Функция SetReceiveHandler вызывается в области видимости класса триггера прокси сервиса (<SI-Namespace>::proxy::triggers::<Trigger>) и подключается через заголовочный файл <SiNamespaceDerivedDirectoryPath>/<SiShortname>_proxy.h [SWS_CM_00250]. Триггеры наряду с событиями, методами и полями образуют один из четырех механизмов коммуникации в ara::com EXP_ARAComAPI §4.2 «Means of Communication».
          

          Параметр handler типа ara::com::TriggerReceiveHandler принимает вызываемый объект, который вызывается Communication Management при поступлении триггера. Сам обработчик не имеет параметров; для запроса текущего значения счетчика триггеров внутри функции обратного вызова должен вызываться метод GetNewTriggers конкретного класса триггера [SWS_CM_00250].
          

          Обработка ошибок и безопасность исключений
          

          Регистрация не возвращает значения (void) и определена как noexcept, а также exception safe [SWS_CM_00250]. Нарушение соглашения о вызовах в форме InvalidHandlerViolation возникает, если переданный вызываемый объект не существует или равен null [SWS_CM_00250].
          

          Взаимодействие и варианты
          

          Для сценариев, в которых обработчик триггера должен выполняться в определенном контексте выполнения, существует шаблонная перегрузка с ExecutorT [SWS_CM_00352]. Сопоставимые методы регистрации для обратных вызовов доступны на уровне прокси также для событий ([SWS_CM_00181], [SWS_CM_11356]) и полей ([SWS_CM_11605], [SWS_CM_11611]) EXP_ARAComAPI §5.3.1 «Proxy Class API’s».
          

          

          Это указание по использованию было сгенерировано ИИ на основе спецификации AUTOSAR.
