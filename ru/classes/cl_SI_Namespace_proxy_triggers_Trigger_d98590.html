Контекст

Сгенерированный класс <SI-Namespace>::proxy::triggers::<Trigger> представляет клиентский интерфейс для элемента Trigger, определенного в ServiceInterface в роли trigger AUTOSAR AP SWS CommunicationManagement с. 39. В отличие от механизмов на основе событий (Events), передающих сериализованные полезные данные, триггер служит исключительно для уведомления о наступлении события без передачи данных приложения. В число партнеров по взаимодействию входят прокси-приложение (клиент), промежуточное программное обеспечение Communication Management (ara::com) для передачи сигналов, а также опциональные контексты выполнения (ExecutorT) для развязки асинхронных задач [SWS_CM_00352], [SWS_CM_01106]. Кроме того, существует интерфейс для сквозной защиты (E2E) с целью приема транспортных ошибок [SWS_CM_00106].

Жизненный цикл

Экземпляр триггера, предположительно, жестко привязан как объект-член к сроку жизни вышестоящего сервисного прокси и создается, а также освобождается вместе с ним. Класс объявлен как final. Функциональный жизненный цикл в значительной степени определяется состоянием подписки (ara::com::SubscriptionState) [SWS_CM_01105]:

  • Не подписан: исходное состояние экземпляра. Вызов Unsubscribe() в этом состоянии не дает никакого эффекта и немедленно возвращает управление [SWS_CM_00810].
  • Подписка запрошена: при вызове Subscribe() [SWS_CM_00723] инициируется подписка в Communication Management. Состояние переходит в kSubscriptionPending или непосредственно в kSubscribed. Если при вызове Subscribe() триггер уже находится в kSubscribed или kSubscriptionPending, метод возвращает управление без выполнения каких-либо действий [SWS_CM_00723].
  • Подписано (kSubscribed): триггерные сигналы поставщика сервиса активно принимаются. Текущее состояние можно синхронно запросить с помощью GetSubscriptionState() [SWS_CM_01105]. За изменениями состояния можно асинхронно следить через зарегистрированный обработчик [SWS_CM_01107].
  • Отмена подписки: вызов Unsubscribe() [SWS_CM_00810] прекращает доставку и возвращает триггер в состояние без подписки.

Диаграмма состояний: переходы состояний подписки на триггер. Источники: [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_01105]

Путь использования

Типичная последовательность вызовов для использования прокси-триггера подразделяется на конфигурацию, подписку, обработку сигналов и очистку:

  1. Регистрация обработчиков: при необходимости приложение предварительно регистрирует функции обратного вызова для уведомлений. С помощью SetReceiveHandler() задается функция без параметров, которая вызывается Communication Management при поступлении триггера [SWS_CM_00250]. Для выполнения в выделенном контексте потока предусмотрена шаблонная перегрузка с ExecutorT [SWS_CM_00352]. Смену статуса подписки можно отслеживать с помощью SetSubscriptionStateChangeHandler() [SWS_CM_01107], [SWS_CM_01106], тогда как о транспортных ошибках сообщается через SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107].
  2. Активация подписки: приложение вызывает Subscribe() [SWS_CM_00723], чтобы запустить сигнализацию.
  3. Получение сигнала и обновление счетчика: при поступлении триггера Communication Management вызывает TriggerReceiveHandler [SWS_CM_00250]. Приложение вызывает GetNewTriggers() [SWS_CM_00226] внутри обработчика или циклически. Этот метод считывает количество триггеров, поступивших с момента предыдущего вызова, и обновляет счетчик. Возвращаемое значение 0 указывает на то, что с тех пор новый триггер не принимался [SWS_CM_00226].
  4. Завершение подписки и отмена регистрации: для прекращения приема приложение вызывает Unsubscribe() [SWS_CM_00810]. Заданные обработчики можно сбросить с помощью UnsetReceiveHandler() [SWS_CM_11614], UnsetSubscriptionStateChangeHandler() [SWS_CM_01108] и UnsetTransportFaultConditionHandler() [SWS_CM_00108].

Диаграмма последовательности: процесс регистрации обработчиков, оформления подписки, приема триггера и опроса счетчика. Источники: [SWS_CM_00226], [SWS_CM_00250], [SWS_CM_00723], [SWS_CM_00810]

Сценарии ошибок

Методы класса триггера преимущественно объявлены с noexcept и обозначены как безопасные к исключениям [SWS_CM_00226], [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_01105]. Определены следующие ошибочные ситуации и нарушения (Violations):

  • Недопустимый колбэк (InvalidHandlerViolation): если в SetReceiveHandler() [SWS_CM_00250], [SWS_CM_00352], SetSubscriptionStateChangeHandler() [SWS_CM_01107], [SWS_CM_01106] или SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107] передается несуществующий или пустой вызываемый объект (null-обработчик), система сообщает о InvalidHandlerViolation.
  • Недостаточные права доступа (InsufficientPermissionsViolation): если Grant Enforcement отклоняет право доступа к элементу триггера, вызов Subscribe() отклоняется с InsufficientPermissionsViolation [SWS_CM_00723].
  • Безопасность к исключениям при удалении обработчика приема: в отличие от методов UnsetSubscriptionStateChangeHandler() [SWS_CM_01108] и UnsetTransportFaultConditionHandler() [SWS_CM_00108], метод UnsetReceiveHandler() специфицирован как not exception safe [SWS_CM_11614].
  • Транспортные ошибки на сетевом уровне: ошибки сквозной передачи асинхронно передаются через обработчик, заданный с помощью SetTransportFaultConditionHandler() [SWS_CM_00106].

Данное руководство основано на спецификациях AUTOSAR для Adaptive Platform выпуска R25-11 и обобщает принципы функционирования прокси-триггеров.
