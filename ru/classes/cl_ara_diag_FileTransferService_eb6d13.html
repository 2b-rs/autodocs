Контекст

Интерфейсный класс ara::diag::FileTransferService ([SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §8.18 «Header: ara/diag/file_transfer.h») предоставляет в AUTOSAR Adaptive функциональную абстракцию для файловой передачи диагностических данных. Он служит для реализации службы UDS 0x38 (RequestFileTransfer) и обеспечивает стандартизированный обмен файлами и информацией о каталогах через границы процессов (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»).

В процессах передачи файлов участвуют три основных компонента:

  • Диагностический клиент: инициирует файловые операции через стандартизированные вызовы служб UDS (RequestFileTransfer 0x38, TransferData 0x36, а также RequestTransferExit 0x37).
  • Diagnostic Management (Diagnostic Server Instance): принимает диагностические сообщения клиента, выполняет обработку протокола и перенаправляет запросы зарегистрированному экземпляру службы (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Realization of modeOfOperation»).
  • Adaptive Application: реализует прикладные callback-методы ara::diag::FileTransferService, создает сеансы данных и осуществляет доступ к локальной файловой системе.

Архитектура поддерживает различные стратегии обмена данными (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»):

  • Simple: копирует данные между Adaptive Application и Diagnostic Management; подходит для небольших размеров файлов.
  • Zero Copy: исключает копирование в памяти между приложением и Diagnostic Management для эффективного использования ресурсов при больших объемах данных.
  • OS File System Handle: передача нативных файловых дескрипторов операционной системы для прямой передачи без затрат на копирование в диагностическом стеке.

Контекстная диаграмма: партнеры по взаимодействию и распределение ролей при файловой передаче диагностических данных. Источники: [SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer».

Жизненный цикл

Класс ara::diag::FileTransferService выступает в качестве базового класса для специализированных диагностических обработчиков приложения. При инстанцировании конструктор ожидает ara::core::InstanceSpecifier, указывающий на смоделированный PortPrototype типа DiagnosticRequestFileTransferInterface, а также определение параллелизма через ConcurrencyType ([SWS_DM_01325]).

Отношения экземпляров и владения строго регламентированы:

  • Защита от копирования: класс представляет собой уникальный экземпляр; конструктор копирования ([SWS_DM_01327]) и оператор присваивания с копированием ([SWS_DM_01329]) удалены (delete).
  • Перемещаемость: конструктор перемещения ([SWS_DM_01328]) и оператор присваивания с перемещением ([SWS_DM_01330]) определены в области видимости protected.
  • Уничтожение: виртуальный деструктор ~FileTransferService() ([SWS_DM_01326]) обеспечивает корректную очистку производных классов.

Функциональный жизненный цикл активно управляется приложением:

  1. Предоставлен: после создания Diagnostic Management еще не перенаправляет запросы к экземпляру.
  2. Активен (предлагается): вызовом Offer() Diagnostic Management авторизуется для передачи запросов обработчику службы ([SWS_DM_01336]).
  3. Деактивирован: вызов StopOffer() отзывает разрешение и блокирует дальнейшую пересылку новых запросов ([SWS_DM_01337]).

В отношении потокобезопасности AUTOSAR проводит различие: функции обратного вызова интерфейса согласуют свое поведение параллелизма с переданным в конструктор ConcurrencyType (kConcurrent или kNotConcurrent) ([SWS_DM_01325]). Административные методы, такие как Offer(), StopOffer(), а также деструктор, напротив, специфицированы как непотокобезопасные ([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

Диаграмма состояний: фазы жизненного цикла экземпляра FileTransferService. Источники: [SWS_DM_01325], [SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337].

Путь использования

Интерфейс охватывает все режимы работы, определенные в службе UDS 0x38, с помощью выделенных чисто виртуальных методов:

  • RequestReadFile: вызывается при modeOfOperation ReadFile (0x04) ([SWS_DM_01314], [SWS_DM_01331]).
  • RequestWriteFile: вызывается при modeOfOperation ReplaceFile (0x03) с WriteFileMode::kReplace ([SWS_DM_01313], [SWS_DM_01324], [SWS_DM_01333]), а также для kAdd.
  • RequestResumeWriteFile: вызывается при modeOfOperation ResumeFile (0x06) ([SWS_DM_01316], [SWS_DM_01334]).
  • RequestReadDirectory: вызывается при modeOfOperation ReadDir (0x05) ([SWS_DM_01315], [SWS_DM_01332]).
  • DeleteFile: выполняет полное удаление файла при modeOfOperation DeleteFile ([SWS_DM_01335]).

Типичный сценарий использования для чтения файла (ReadFile) состоит из следующих шагов:

  1. Предоставление: Приложение создает экземпляр своего производного сервисного класса и активирует интерфейс с помощью Offer() ([SWS_DM_01336]).
  2. Начальный запрос на передачу: Диагностический клиент отправляет UDS-команду 0x38 (ReadFile). Diagnostic Server перенаправляет вызов через RequestReadFile(fileName, dataFormatIdentifier, metaInfo, cancellationHandler) в приложение ([SWS_DM_01314], [SWS_DM_01331]).
  3. Установление сессии: Приложение проверяет запрос и асинхронно возвращает ara::core::Future, содержащий кортеж из инициализированной DataTransferReadSession и размеров файлов (FileSizes) ([SWS_DM_01331]). Diagnostic Management отвечает на UDS-запрос положительно.
  4. Передача блоков: Для каждого последующего запроса TransferData (0x36) клиента Diagnostic Server вызывает методы чтения зарегистрированных в сессии обработчиков ([SWS_DM_01317]).
  5. Завершение передачи: После полной передачи клиент отправляет RequestTransferExit (0x37). В ответ Diagnostic Server вызывает метод Exit сессии ([SWS_DM_01318]) и завершает операцию.

Диаграмма последовательности: процесс чтения файла в соответствии с UDS-службами 0x38, 0x36 и 0x37. Источники: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331], [SWS_DM_01336].

Сценарии ошибок

Условия ошибок перехватываются и регистрируются на различных уровнях системы:

  • Ошибки конструирования и моделирования: Если конфигурация не соответствует модели системы, создание экземпляра завершается сбоем ([SWS_DM_01325]):
    • InstanceSpecifierMappingIntegrityViolation: Идентификатор не удается разрешить или он не указывает на PortPrototype.
    • PortInterfaceMappingViolation: Порту DEM, типизированному DiagnosticRequestFileTransferInterface, не хватает DiagnosticServiceGenericMapping.
    • ProcessMappingViolation: Для смоделированного процесса не существует подходящего процесса времени выполнения.
    • InstanceSpecifierAlreadyInUseViolation: InstanceSpecifier уже используется внутри процесса.
  • Многократное предоставление: Повторный вызов Offer() для уже активного экземпляра возвращает ошибку с DiagOfferErrc::kAlreadyOffered ([SWS_DM_01336]).
  • Диагностические отрицательные ответы (NRC): Если файловые операции в виртуальных методах не могут быть успешно выполнены, приложение сигнализирует об этом через возвращаемый ara::core::Future с UDS Negative Response Code (NRC) из диапазона ошибок DiagUdsNrcErrc согласно ISO 14229-1 ([SWS_DM_01331], [SWS_DM_01332], [SWS_DM_01333], [SWS_DM_01334], [SWS_DM_01335]).
  • Отмена операции: С помощью параметра CancellationHandler приложение может во время асинхронных файловых операций непрерывно проверять статус отмены с помощью cancellationHandler.IsCanceled() или зарегистрировать уведомление через cancellationHandler.SetNotifier(), чтобы незамедлительно освободить ресурсы при преждевременном прерывании сессии ([SWS_DM_01331], [SWS_DM_01335]).

Это руководство по классам основано на спецификации AUTOSAR Adaptive Platform Release R25-11.
