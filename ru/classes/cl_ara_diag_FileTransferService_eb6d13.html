Позволяет адаптивным приложениям предоставлять операции с файлами и директориями для диагностических служб UDS.

Сервисный интерфейс служит для подключения прикладной передачи файлов к Diagnostic Management для службы UDS RequestFileTransfer ([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»). После создания экземпляра приложение активирует перенаправление входящих файловых запросов с помощью Offer() и асинхронно обрабатывает файловые операции, такие как чтение, запись или удаление, через специализированные методы-обработчики ([SWS_DM_01336]). При операциях чтения и записи сервис предоставляет объекты сессий, через которые осуществляется фактическая передача данных. Экземпляры класса не могут копироваться и требуют жёсткой привязки через спецификатор экземпляра.

Контекст

Класс ara::diag::FileTransferService определяет диагностический интерфейс для реализации службы UDS RequestFileTransfer (0x38) в AUTOSAR Adaptive Platform ([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»). Он функционирует как Service-Interface между Diagnostic Management (DM или Diagnostic Server) и конкретным диагностическим приложением для гибкой обработки чтения, записи, возобновления и удаления файлов или директорий через границы процессов (SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»).

В сценарии передачи файлов обычно участвуют три стороны: внешний UDS-клиент (диагностический тестер), Diagnostic Server в качестве посредника, а также адаптивное приложение, наследующее от FileTransferService. При входящих диагностических запросах Diagnostic Server делегирует запрос реализованным виртуальным методам сервиса ([SWS_DM_01313], [SWS_DM_01314]). Для последующих передач данных (UDS 0x36 TransferData) и завершения (UDS 0x37 RequestTransferExit) Diagnostic Management обращается напрямую к классам обработчиков, предоставляемым через объекты сессий (DataTransferReadSession или DataTransferWriteSession) ([SWS_DM_01317], [SWS_DM_01318]).

Контекстная диаграмма: взаимодействие между UDS-клиентом, Diagnostic Management, реализацией сервиса и сессиями передачи. Источники: [SWS_DM_01317], [SWS_DM_01318], SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer».

Жизненный цикл

Экземпляр FileTransferService создаётся с указанием смоделированного ara::core::InstanceSpecifier, а также модели параллелизма ConcurrencyType ([SWS_DM_01325]). Через ConcurrencyType определяется, должны ли методы обратного вызова класса быть реализованы потокобезопасно (kConcurrent) или непотокобезопасно (kNotConcurrent) ([SWS_DM_01325], [SWS_DM_01331]). Будучи защищённой единичной функцией, класс не может копироваться ([SWS_DM_01327], [SWS_DM_01329]), однако поддерживает семантику перемещения ([SWS_DM_01328], [SWS_DM_01330]).

После инстанцирования сервис должен быть явно активирован через метод Offer(), чтобы Diagnostic Management перенаправлял входящие запросы ([SWS_DM_01336]). С помощью StopOffer() перенаправление можно в любой момент отключить снова ([SWS_DM_01337]). Интерпретация: вероятно, требуется вызывать StopOffer() перед уничтожением объекта виртуальным деструктором ~FileTransferService() ([SWS_DM_01326]), чтобы избежать потерянных обращений к обратным вызовам со стороны Diagnostic Management. Ни Offer(), StopOffer(), ни деструктор не являются потокобезопасными ([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

Диаграмма состояний: переходы состояний экземпляра FileTransferService между инстанцированием, предоставлением и завершением. Источники: [SWS_DM_01325], [SWS_DM_01336], [SWS_DM_01337], [SWS_DM_01326].

Путь использования

Типичный процесс файловой операции подразделяется на конфигурацию, инициацию операции и последующую блочную передачу. Сначала при UDS-запросе 0x38 с режимом ReadFile (0x04) Diagnostic Management перенаправляет вызов в RequestReadFile ([SWS_DM_01314], [SWS_DM_01331]). Приложение обрабатывает имя файла, а также форматные и метаданные и асинхронно через ara::core::Future возвращает кортеж из DataTransferReadSession и размеров файла (FileSizes) ([SWS_DM_01331]). Интерпретация: какая стратегия передачи (такая как копирование, zero-copy или дескриптор файловой системы) будет использована, приложение определяет, предположительно, при создании экземпляра соответствующего класса сессии (SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer», [SWS_DM_01317]).

После положительного подтверждения клиент запрашивает блоки данных через TransferData (0x36). В ответ на это Diagnostic Server напрямую вызывает метод Read зарегистрированного обработчика DataTransferReadSession ([SWS_DM_01317]). Как только все блоки переданы, клиент завершает транзакцию с помощью RequestTransferExit (0x37), после чего Diagnostic Server вызывает метод Exit обработчика ([SWS_DM_01318]). Аналогичные шаблоны действуют для записи через RequestWriteFile ([SWS_DM_01313], [SWS_DM_01333]) с режимом WriteFileMode ([SWS_DM_01324]), возобновления через RequestResumeWriteFile ([SWS_DM_01316], [SWS_DM_01334]), чтения директории через RequestReadDirectory ([SWS_DM_01315], [SWS_DM_01332]) или прямого удаления через DeleteFile ([SWS_DM_01335]).

Диаграмма последовательности: процесс операции чтения через UDS 0x38, 0x36 и 0x37. Источники: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331].

Сценарии ошибок

Ошибки могут возникать в нескольких фазах:

  • Нарушения при конструировании: в случае сбоя разрешения или сопоставления InstanceSpecifier возникают ошибки моделирования, такие как InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation или InstanceSpecifierAlreadyInUseViolation ([SWS_DM_01325]).
  • Ошибки активации: повторный вызов Offer() при уже активном сервисе возвращает ошибку DiagOfferErrc::kAlreadyOffered ([SWS_DM_01336]).
  • Диагностические коды ошибок (NRC): если операция не может быть успешно выполнена, методы обратного вызова в ara::core::Future возвращают подходящий отрицательный код ответа UDS (NRC согласно ISO 14229-1) через DiagUdsNrcErrc ([SWS_DM_01331], [SWS_DM_01333], [SWS_DM_01335]).
  • Обработка прерывания: через переданный объект CancellationHandler приложение может с помощью IsCanceled проверить, был ли прерван диалог, или через SetNotifier зарегистрировать функцию уведомления для асинхронных прерываний ([SWS_DM_01331], [SWS_DM_01335]).

Настоящее руководство основано исключительно на спецификации AUTOSAR R25-11 и создано автоматически.

Метод DeleteFile класса ara::diag::FileTransferService (SWS Diagnostics §8.18.1.2.3.1 «DeleteFile», заголовочный файл #include "ara/diag/file_transfer.h") обрабатывает полное удаление файла в рамках UDS-службы RequestFileTransfer (0x38) с режимом DeleteFile [SWS_DM_01335]. UDS-служба предоставляется на стороне сервера согласно ISO 14229-1 [SWS_DM_01310] SWS Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer».

При вызове передаются три параметра [SWS_DM_01335]:

  • fileName (ara::core::String): указание пути и имя целевого файла (интерпретация: несмотря на редакционное указание «file to read» в тексте спецификации, речь идет об удаляемом файле).
  • metaInfo (MetaInfo const &): метаинформация текущего диагностического запроса.
  • cancellationHandler (CancellationHandler): позволяет проверять статус прерывания через cancellationHandler.IsCanceled(), а также регистрировать функцию уведомления через cancellationHandler.SetNotifier() в случае прерывания текущей беседы.

В качестве асинхронного результата функция возвращает ara::core::Future<void> [SWS_DM_01335]. Успешное завершение сигнализирует клиенту диагностики о положительном поведении ответа. В случае ошибки необходимо предоставить соответствующий UDS-NRC согласно ISO 14229-1 через DiagUdsNrcErrc в Future [SWS_DM_01335].

Функция специфицирована как noexcept и считается исключеннобезопасной («exception safe») [SWS_DM_01335]. Требование к потокобезопасности является условным и управляется через переданный конструктору ConcurrencyType [SWS_DM_01335].
