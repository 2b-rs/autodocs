Служит для валидации пути сертификатов X.509 и цепочек сертификатов на основе сконфигурированных якорей доверия.

Класс ara::crypto::x509::CertificateValidationCtx служит для валидации сертификатов X.509 и полных цепочек сертификатов в соответствии с RFC 5280 ([SWS_CRYPT_50122]). Перед выполнением приложение конфигурирует контекст путем добавления якорей доверия, опциональных промежуточных сертификатов, моментов времени проверки, а также параметров проверки и при необходимости подключает ответы OCSP для проверки отзыва ([SWS_CRYPT_50117]). Если ответы OCSP регистрируются, параметры валидации должны обязательно определять соответствующее поведение OCSP во избежание ошибок несовместимости при проверке пути. Все методы интерфейса являются безопасными относительно исключений и рассчитаны на конкурентный доступ.

Контекст

Класс ara::crypto::x509::CertificateValidationCtx определяет стандартизированный интерфейс для валидации сертификатов X.509 и цепочек сертификатов в соответствии с RFC 5280 ([SWS_CRYPT_50122], [SWS_CRYPT_50123]). В общей системе AUTOSAR Adaptive Platform он берет на себя задачу подтверждения отношений доверия, верификации путей сертификатов и определения статуса криптографических сертификатов перед их использованием в отношениях безопасности.

В качестве центрального партнера по взаимодействию выступает вызывающее приложение, которое снабжает контекст якорями доверия ([SWS_CRYPT_50117]), недоверенными промежуточными сертификатами ([SWS_CRYPT_50118]), а также информацией об отзыве в виде ответов OCSP ([SWS_CRYPT_50124]). Результат валидации предоставляется как CertificateValidationResult ([SWS_CRYPT_50122]).

Контекстная диаграмма: интеграция CertificateValidationCtx между приложением, входными сертификатами, проверками отзыва и объектом результата. Источники: [SWS_CRYPT_50117], [SWS_CRYPT_50122], [SWS_CRYPT_50124].

Жизненный цикл

Экземпляры интерфейса управляются через псевдоним типа Sptr ([SWS_CRYPT_50116]) как std::shared_ptr<CertificateValidationCtx>, что обеспечивает разделяемое владение и гибкое управление временем жизни со стороны использующих программных компонентов. Поскольку речь идет о чисто виртуальном интерфейсном классе, открытый конструктор отсутствует; создание конкретного экземпляра контекста, по всей видимости, осуществляется через соответствующие функции создания провайдерной реализации криптографического стека.

В отношении конкурентности все виртуальные функции-члены специфицированы как потокобезопасные (thread-safe) ([SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50122]). Кроме того, все методы гарантируют безопасность исключений (exception safe) и объявлены с noexcept ([SWS_CRYPT_50117], [SWS_CRYPT_50122]). С точки зрения состояния контекст ведет себя как конфигурируемый аккумулятор: он принимает параметры проверки, сертификаты и ответы о статусе и сохраняет их для шагов валидации.

Путь использования

Типичное использование контекста валидации подразделяется на структурированную последовательность шагов конфигурации и последующее выполнение валидации:

  1. Сохранение якорей доверия: с помощью AddTrustedCertificate ([SWS_CRYPT_50117]) добавляются один или несколько доверенных сертификатов в качестве исходных точек для валидации пути. Дополнительные недоверенные промежуточные сертификаты могут быть предоставлены через AddUntrustedCertificate ([SWS_CRYPT_50118]).
  2. Конфигурация правил валидации и опорного времени: через SetValidationOptions ([SWS_CRYPT_50120]) передается битовая маска для управления поведением при проверке. С помощью SetCurrentTime ([SWS_CRYPT_50121]) может быть задан явный момент времени для проверок действительности; если этот вызов опущен, контекст автоматически использует системное время ([SWS_CRYPT_50121]). Если требуется исключить из проверки определенные неподдерживаемые критические расширения, их OID можно зарегистрировать через IgnoreCriticalExtension ([SWS_CRYPT_50119]). Это не имеет эффекта, если установлена опция kIgnoreUnknownCriticalExtensions ([SWS_CRYPT_50119]).
  3. Дополнение информации об отзыве: через AddOcspResponse ([SWS_CRYPT_50124]) можно добавить один или несколько ответов OCSP. При этом издатель ответа OCSP должен быть либо предварительно сохранен в контексте в качестве сертификата, либо обладать атрибутом Extended Key Usage id-kp-OCSPSigning того же CA, либо передаваться через опциональный параметр trustedOcspIssuerCertificate ([SWS_CRYPT_50124]).
  4. Выполнение валидации: для проверки целевого сертификата служит ValidateCertificate ([SWS_CRYPT_50122]). В качестве альтернативы ValidateCertificateChain ([SWS_CRYPT_50123]) выполняет валидацию упорядоченной цепочки сертификатов, начиная с конечного сертификата в позиции 0. При этом сертификаты, зарегистрированные ранее через AddUntrustedCertificate, игнорируются, и исключительно переданная цепочка проверяется на соответствие доверенным сертификатам ([SWS_CRYPT_50123]).

Диаграмма последовательности: типичный порядок вызовов для конфигурации и валидации сертификатов. Источники: [SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50122], [SWS_CRYPT_50124].

Сценарии ошибок

Обработка ошибок осуществляется согласованно через ara::core::Result без исключений C++:

  • Недопустимые параметры конфигурации: если SetValidationOptions вызывается с недопустимой битовой маской, вызов завершается сбоем и возвращает код ошибки ara::crypto::CryptoErrc::kInvalidArgument с семантикой отката ([SWS_CRYPT_50120]).
  • Противоречивая конфигурация OCSP: если хотя бы один ответ OCSP был сохранен через AddOcspResponse без указания поведения для OCSP в CertificateValidationOptions, как ValidateCertificate ([SWS_CRYPT_50122]), так и ValidateCertificateChain ([SWS_CRYPT_50123]) возвращают ошибку ara::crypto::CryptoErrc::kIncompatibleArguments с семантикой отката.
  • Неудачная валидация OCSP: если подпись или происхождение ответа OCSP в AddOcspResponse ([SWS_CRYPT_50124]) не могут быть проверены на соответствие определенным критериям, функция возвращает соответствующий код состояния CertificateValidationStatus или ошибку, специфичную для реализации, вместо kValid.
  • Ошибки, специфичные для реализации: при внутренних неполадках криптографической библиотеки такие методы, как AddTrustedCertificate ([SWS_CRYPT_50117]) или IgnoreCriticalExtension ([SWS_CRYPT_50119]), могут сообщать специфичные для реализации коды ошибок в объекте результата.

Настоящее руководство основано на требованиях спецификации AUTOSAR Adaptive Platform R25-11.

Использование

Метод AddOcspResponse класса ara::crypto::x509::CertificateValidationCtx валидирует переданный ответ OCSP (ocspResponse) и при его действительности добавляет его к набору ранее сохранённых ответов OCSP в контексте валидации [SWS_CRYPT_50124]. К контексту может быть добавлено несколько ответов [SWS_CRYPT_50124]. Через опциональный параметр trustedOcspIssuerCertificate может быть передан конкретный сертификат, считающийся доверенным при проверке ответа OCSP; если этот параметр опущен, валидация использует сертификаты, ранее сконфигурированные с помощью AddTrustedCertificate [SWS_CRYPT_50124].

Синхронный вызов возвращает ara::core::Result<CertificateValidationStatus>, которое при успешном принятии содержит статус kValid или в противном случае отражает результат валидации OCSP либо ошибку [SWS_CRYPT_50124].

Обработка ошибок

Спецификация не определяет стандартизированных кодов ошибок для этого вызова [SWS_CRYPT_50124]. В случае сбоя операции либо в результате передаётся соответствующий статус валидации, либо через объект Result сигнализируется специфичная для реализации ошибка [SWS_CRYPT_50124].

Параллелизм и ограничения

Операция специфицирована как thread-safe и exception-safe [SWS_CRYPT_50124]. Для успешной валидации ответа OCSP должно выполняться одно из следующих условий [SWS_CRYPT_50124]:

  • Издатель был ранее сохранён в контексте как доверенный или несанкционированный сертификат [SWS_CRYPT_50124].
  • Подпись исходит от сертификата с установленным расширением id-kp-OCSPSigning того же центра сертификации (CA) [SWS_CRYPT_50124].
  • Подпись исходит от доверенного CA, переданного напрямую через trustedOcspIssuerCertificate [SWS_CRYPT_50124].

Взаимодействие

Зарегистрированные ответы OCSP учитываются в последующих проверках валидации, таких как выполняемые [SWS_CRYPT_50122] (ValidateCertificate) и [SWS_CRYPT_50123] (ValidateCertificateChain). Интерпретация: по всей видимости, ответы OCSP должны добавляться до запуска валидации пути, чтобы можно было учесть статус отзыва сертификатов.

                              virtual ara::core::Result< CertificateValidationResult::Sptrc > ValidateCertificateChain (const ara::core::Span< Certificate::Sptrc > certificateChain) noexcept=0;
                              

                              Performs certificate path validation according to RFC 5280 and according to the previous configuration of the context. The function ignores any certificates added to the context via Add UntrustedCertificate. Instead, the function validates the provided chain against any trusted certificate that has been set using the function AddTrustedCertificate.

                              Использование и параметры

Функция игнорирует сертификаты, ранее зарегистрированные через AddUntrustedCertificate, и валидирует переданную цепочку исключительно относительно якорей доверия, сохраненных с помощью AddTrustedCertificate [SWS_CRYPT_50123].
