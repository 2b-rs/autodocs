Служит интерфейсом для выполнения обновлений программного обеспечения по протоколу ASAM SOVD в диагностическом сервере AUTOSAR.

Класс предоставляет интерфейс со стороны приложения для выполнения стандартизированных обновлений программного обеспечения по протоколу SOVD в соответствии с ASAM SOVD [SWS_DM_01796]. После инстанцирования приложение активирует пересылку диагностических запросов специфическим обработчикам обновления через метод Offer() [SWS_DM_01924]. Через асинхронные методы пакеты регистрируются, подготавливаются, устанавливаются автоматически или вручную, а также снова удаляются. Все процессы, связанные с передачей данных и жизненным циклом, обрабатываются при этом неблокирующим образом через future-объекты.

Контекст

Класс ara::diag::SovdSwUpdate определяет интерфейс для реализации стандартизированных обновлений программного обеспечения в соответствии с ASAM SOVD в AUTOSAR Adaptive Platform [SWS_DM_01874]. Поскольку сама бизнес-логика обновлений программного обеспечения находится не в функциональном кластере Diagnostic Management (DM), выполнение остается за соответствующим приложением, тогда как ara::diag::SovdSwUpdate концентрируется на стандартизированной обработке базового протокола SOVD AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept». Для загрузки файлов обновлений при этом используются стратегии передачи, специфицированные для службы UDS 0x38 (RequestFileTransfer) AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept», [SWS_DM_01923].

В процессах участвуют три основных компонента: внешний клиент SOVD, экземпляр Diagnostic Server (DM) для управления протоколами и маршрутизацией, а также зависящая от приложения реализация обработчика ara::diag::SovdSwUpdate [SWS_DM_01796], [SWS_DM_01924].

Контекстная диаграмма: взаимодействие между клиентом SOVD, Diagnostic Server (DM) и ara::diag::SovdSwUpdate. Источники: [SWS_DM_01796], [SWS_DM_01924], AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept».

Жизненный цикл

Создание экземпляра ara::diag::SovdSwUpdate выполняется через конструктор с указанием ara::core::InstanceSpecifier, ссылающегося на прототип порта смоделированного DiagnosticSovdUpdateInterface, а также режима параллелизма (ConcurrencyType: kConcurrent или kNotConcurrent) [SWS_DM_01910]. Конструктор специфицирован как потокобезопасный и исключениебезопасный [SWS_DM_01910]. Будучи представителем уникального экземпляра интерфейса, конструктор копирования и оператор присваивания копированием удалены (=delete) и защищены [SWS_DM_01912], [SWS_DM_01914]. Конструирование перемещением и присваивание перемещением доступны в защищенном режиме, однако не являются потокобезопасными [SWS_DM_01913], [SWS_DM_01915].

Уничтожение объекта выполняется через виртуальный деструктор ~SovdSwUpdate(), который считается непотокобезопасным [SWS_DM_01911]. Должны ли виртуальные методы обратного вызова класса выполняться параллельно, напрямую зависит от переданного конструктору ConcurrencyType [SWS_DM_01910], [SWS_DM_01916].

Путь использования

Интерпретация: поскольку предоставляемые методы интерфейса объявлены чисто виртуальными (=0), производный прикладной класс, по всей видимости, должен реализовывать их для выполнения фактического обновления, в то время как базовый класс регулирует подключение к платформе.

Стандартный процесс делится на следующие фазы:

  • Предоставление: после создания объекта приложение вызывает Offer(), чтобы позволить Diagnostic Management перенаправлять входящие сообщения SOVD этому экземпляру [SWS_DM_01924].
  • Запрос сведений и регистрация: через GetAllUpdates() можно запросить существующие пакеты обновления [SWS_DM_01797], [SWS_DM_01916]. Если требуется передать новый пакет, Diagnostic Server запрашивает регистрацию через RequestUpdatePackageRegistration(), которая асинхронно предоставляет сессию записи (DataTransferWriteSession) вместе с идентификатором пакета обновления [SWS_DM_01923]. Подробности и статус определяются через GetUpdatePackageDetails() и GetUpdatePackageStatus() [SWS_DM_01802], [SWS_DM_01917], [SWS_DM_01921].
  • Установка или удаление: установка может запускаться либо автоматически с помощью PutUpdatePackageAutomated() [SWS_DM_01799], [SWS_DM_01918], либо выполняться в два этапа через PrepareUpdatePackage() [SWS_DM_01800], [SWS_DM_01919] с последующим ExecuteUpdatePackage() [SWS_DM_01801], [SWS_DM_01920]. Пакеты, которые больше не требуются, удаляются через DeleteUpdatePackage() [SWS_DM_01922].
  • Завершение: перед завершением работы приложение деактивирует пересылку сообщений вызовом StopOffer() [SWS_DM_01925].

Диаграмма последовательности: типовой процесс регистрации и установки пакета через SOVD. Источники: [SWS_DM_01799], [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923], [SWS_DM_01924]

Сценарии ошибок

При предложении служб через Offer() могут возникать специфические ошибки в типе возвращаемого значения ara::core::Result<void>: DiagOfferErrc::kAlreadyOffered, если экземпляр уже предложен, а также DiagOfferErrc::kConfigurationMismatch, если конфигурация не совпадает с диагностическим экстрактом (DEXT) [SWS_DM_01924].

Если конструктор вызывается с некорректным состоянием модели, сообщается об архитектурных нарушениях, включая InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation или InstanceSpecifierAlreadyInUseViolation [SWS_DM_01910].

Все функциональные операции обновления возвращают ara::core::Future, который в случае ошибки передает коды ошибок в соответствии с ASAM SOVD 1.1 или ISO 17978-3 [SWS_DM_01917], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923]. Кроме того, все асинхронные методы принимают CancellationHandler, через который сигнализируется о преждевременном прерывании текущего диагностического соединения [SWS_DM_01916], [SWS_DM_01919], [SWS_DM_01923].

Чисто виртуальная функция DeleteUpdatePackage класса ara::diag::SovdSwUpdate вызывается согласно [SWS_DM_01803] экземпляром Diagnostic Server, когда требуется выполнить SOVD-метод «Delete Update Package from an SOVD Server» ([SWS_DM_01922]). Она инициирует удаление пакета обновления на стороне сервера.

Вызов выполняется асинхронно и возвращает ara::core::Future<void>, которое указывает на успешное завершение или предоставляет объект ошибки [SWS_DM_01922]. Сигнатура требует следующих входных параметров:

  • updatePackageId: обозначает как ara::core::String уникальный ID удаляемого пакета обновления.
  • metaInfo: передает в виде MetaInfo const& дополнительную контекстную информацию запроса.
  • cancellationHandler: передает объект типа CancellationHandler, информирующий о том, был ли прерван текущий диалог.

Если во время обработки возникает ошибка, Future заполняется соответствующей ошибкой SOVD. Спецификация предписывает для этого использование подходящих кодов ошибок из ASAM SOVD 1.1 или ISO 17978-3 [SWS_DM_01922].

Что касается конкурентности, метод определен как условно потокобезопасный: должна ли реализация выполняться потокобезопасной (thread-safe) или непотокобезопасной (non-thread-safe), определяется через ConcurrencyType, переданный в конструктор [SWS_DM_01922]. Кроме того, функция объявлена как noexcept и безопасная относительно исключений, вследствие чего исключения не должны выходить за ее пределы.

      Использование
      
  
      Чисто виртуальный метод ExecuteUpdatePackage интерфейса ara::diag::SovdSwUpdate служит для выполнения SOVD-метода «Execute Installation of an Update» [SWS_DM_01920]. Объявление находится в заголовочном файле ara/diag/sovd_sw_update.h AUTOSAR_AP_SWS_Diagnostics §8.58.2.1.3.2 «ExecuteUpdatePackage». В качестве входных параметров передаются идентификатор пакета обновления (updatePackageId) и данные запроса (metaInfo) [SWS_DM_01920]. Кроме того, объект cancellationHandler информирует о том, если текущий диалог был прерван [SWS_DM_01920]. Вызов выполняется асинхронно и возвращает ara::core::Future<void>, которое предоставляет положительный результат или сообщает об ошибке SOVD [SWS_DM_01920].
      
  
  
      Обработка ошибок
      
  
      Интерфейс специфицирован как noexcept и безопасный относительно исключений («exception safe») [SWS_DM_01920]. Ошибки во время выполнения, следовательно, не должны генерироваться через C++-исключения, а должны возвращаться асинхронно через ara::core::Future с применимыми кодами ошибок из ASAM SOVD 1.1 или ISO 17978-3 [SWS_DM_01920].
      
  
  
      Параллелизм и граничные условия
      
  
      В отношении потокобезопасности существует условное требование («conditional»): должна ли функция реализовываться потокобезопасной или непотокобезопасной, определяется через параметр ConcurrencyType, переданный конструктору [SWS_DM_01920]. Реализация, вероятно, должна анализировать cancellationHandler, чтобы штатно завершить установку пакета при прерывании диалога [SWS_DM_01920].
