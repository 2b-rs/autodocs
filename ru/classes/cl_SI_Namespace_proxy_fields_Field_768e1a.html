Позволяет клиентским приложениям асинхронно опрашивать, изменять и отслеживать по подписке поле сервиса.

Класс служит клиентским интерфейсом для доступа к полю, определённому в ServiceInterface, и объединяет функции геттера, сеттера, а также уведомлений. Через [SWS_CM_00112] и [SWS_CM_00113] значения можно асинхронно запрашивать и изменять, если соответствующие операции смоделированы. Для обновлений поля используется механизм кэширования на основе подписки, который буферизует уведомления и пересылает их через обработчики обратного вызова. Существенным граничным условием является соблюдение минимальных интервалов отправки, а также отсутствие семантики отката при операциях записи.

Контекст

В управлении связью AUTOSAR Adaptive Platform (ara::com) класс <SI-Namespace>::proxy::fields::<Field> представляет отдельное смоделированное в сервисном интерфейсе поле (Field) на стороне клиента или прокси. Класс объединяет доступ к значениям атрибута и совмещает три функциональные роли: опрос текущего значения (геттер), изменение значения (сеттер), а также приём асинхронных изменений значения (нотификатор) (AUTOSAR_AP_EXP_ARAComAPI с. 10). Он функционирует как интерфейс между клиентским приложением и базовым уровнем связи (Network Binding).

Какие операции доступны на экземпляре, определяет дефиниция сервисного интерфейса: метод Get() генерируется только в том случае, если сконфигурирован Field.hasGetter == TRUE [SWS_CM_00112]. Метод Set() доступен исключительно в том случае, если выполняется Field.hasSetter == TRUE [SWS_CM_00113]. Конкретный тип данных поля при этом типобезопасно отображается через предоставляемый псевдоним типа FieldType [SWS_CM_11403].

Жизненный цикл

Объекты полей инстанцируются как члены вышестоящего прокси-класса. Поэтому время их жизни, вероятно, напрямую связано с жизненным циклом соответствующего экземпляра прокси. Для основанного на событиях механизма нотификатора экземпляр проходит чётко регламентированный жизненный цикл подписки:

  • Не подписан: изначально поле находится в состоянии kNotSubscribed.
  • Подписка запрошена: синхронным вызовом Subscribe(maxSampleCount) [SWS_CM_11601] настраивается буфер и запускается регистрация. Нотификатор переходит в kSubscriptionPending или после подтверждения уровнем связи — в kSubscribed, причём этот переход состояния, предположительно, осуществляется асинхронно.
  • Подписка завершена: с помощью Unsubscribe() [SWS_CM_11602] поток уведомлений останавливается, и состояние возвращается к kNotSubscribed.

Текущее состояние можно в любое время синхронно запросить с помощью GetSubscriptionState() [SWS_CM_11604]. Чтобы отслеживать изменения состояния асинхронно, с помощью SetSubscriptionStateChangeHandler() можно зарегистрировать обратный вызов [SWS_CM_11607], опционально с выделенным контекстом выполнения [SWS_CM_11608]. Перед уничтожением экземпляра или при деактивации зарегистрированные обратные вызовы следует явно удалить через UnsetReceiveHandler() [SWS_CM_11606], UnsetSubscriptionStateChangeHandler() [SWS_CM_11609], а также UnsetTransportFaultConditionHandler() [SWS_CM_00126].

Диаграмма состояний: жизненный цикл подписки нотификатора через ara::com::SubscriptionState. Источники: [SWS_CM_11601], [SWS_CM_11602], [SWS_CM_11604].

Путь использования

Типичный сценарий использования включает регистрацию уведомлений, прием новых данных, а также точечный доступ на чтение и запись:

  1. Настройка подписки: приложение вызывает Subscribe() с желаемой ёмкостью кэша [SWS_CM_11601] и регистрирует с помощью SetReceiveHandler() функцию обратного вызова уведомлений без параметров [SWS_CM_11605]. Для архитектур с параллелизмом выполнение может быть делегировано через исполнитель (executor) [SWS_CM_11611]. Кроме того, для событий нотификатора можно зарегистрировать обработчик транспортных ошибок [SWS_CM_00109], [SWS_CM_00110].
  2. Обработка сэмплов: как только управление связью принимает новые данные поля, оно запускает обработчик приёма. Обработчик определяет доступные места в буфере через GetFreeSampleCount() [SWS_CM_11603] и обрабатывает новые значения через GetNewSamples() [SWS_CM_11610]. Состояние E2E полученных уведомлений можно проверить с помощью GetE2EStateMachineStateNotifier() [SWS_CM_11612].
  3. Явное чтение: получение текущего значения осуществляется асинхронно через Get() [SWS_CM_00112] и возвращает ara::core::Future<FieldType> [SWS_CM_11403]. После завершения статус проверки E2E можно верифицировать с помощью GetE2EStateMachineStateGetter() [SWS_CM_00145].
  4. Явная запись: модификация значения осуществляется через Set(value) [SWS_CM_00113]. Возвращённый ara::core::Future<FieldType> предоставляет результат операции Set, статус E2E которого можно считать через GetE2EStateMachineStateSetter() [SWS_CM_00146].

Диаграмма последовательности: типичный ход взаимодействия с уведомлениями, а также операций Get и Set. Источники: [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601], [SWS_CM_11605], [SWS_CM_11610].

Сценарии ошибок

При использовании методов поля могут возникать различные состояния ошибок:

  • Сбой связи: если сетевая передача при Get() или Set() терпит неудачу, в объекте Future передаётся ошибка ComErrc::kCommunicationFailure [SWS_CM_00112], [SWS_CM_00113]. Для Get() действует семантика отката; для Set() применяется no_rollback_semantics, так что при тайм-ауте на сервере может возникнуть неопределённое состояние [SWS_CM_00113].
  • Нарушение интервала отправки: если запросы отправляются чаще, чем сконфигурировано в deployment, это приводит к ComErrc::kMinimumSendIntervalViolationError [SWS_CM_00112], [SWS_CM_00113].
  • Границы буфера: если память при Subscribe() не может быть выделена, метод возвращает ComErrc::kMaxSampleCountNotRealizable [SWS_CM_11601]. Если при GetNewSamples() запрашивается слишком много сэмплов, вызов завершается сбоем с ComErrc::kMaxSamplesExceeded [SWS_CM_11610].
  • Нарушения доступа и обработчиков: отсутствие прав на выполнение приводит к InsufficientPermissionsViolation при Get(), Set() или Subscribe() [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601]. Передача пустых или недопустимых вызываемых объектов (Callable) в функции регистрации обработчиков вызывает InvalidHandlerViolation [SWS_CM_11605], [SWS_CM_11607], [SWS_CM_00109].
  • Идемпотентность: повторный вызов Subscribe() с идентичным значением буфера в состояниях kSubscribed или kSubscriptionPending не имеет эффекта [SWS_CM_11601]; точно так же Unsubscribe() возвращается без эффекта при отсутствии активной подписки [SWS_CM_11602].

Использование

Метод Get служит в области видимости прокси <SI-Namespace>::proxy::fields::<Field> для асинхронного запроса текущего значения поля ([SWS_CM_00112]; см. также AUTOSAR_AP_EXP_ARAComAPI §6 «FieldGet»). Функция предоставляется через заголовочный файл прокси <SiNamespaceDerivedDirectoryPath>/<SiShortname>_proxy.h и существует только тогда, когда для поля смоделирован Field.hasGetter == TRUE ([SWS_CM_00112]). Она не принимает параметров и возвращает ara::core::Future<FieldType>, который после успешной передачи содержит текущее значение ([SWS_CM_00112]).

Обработка ошибок и граничные условия

Интерфейс определен как noexcept и безопасный к исключениям ([SWS_CM_00112]). В случае сбоя операции возвращаемый ara::core::Future содержит код ошибки с семантикой отката ([SWS_CM_00112]):

  • ComErrc::kCommunicationFailure: сетевой биндинг сообщает об устранимой ошибке связи или о сбое защищенной связи ([SWS_CM_00112]).
  • ComErrc::kMinimumSendIntervalViolationError: запрос на отправку поступил быстрее, чем позволяет сконфигурированный для элемента минимальный интервал отправки (minimumSendInterval) ([SWS_CM_00112]).
  • InsufficientPermissionsViolation: выполнение отклонено механизмом контроля полномочий (Grant Enforcement) ([SWS_CM_00112]).

Ошибки приложения (Application Errors) для геттера отсутствуют ([SWS_CM_00113]).

Взаимодействие

На стороне скелетона обработка запроса геттера требует наличия обратного вызова, регистрируемого через RegisterGetHandler ([SWS_CM_00114]). Каждый вызов Get() выполняет сквозную проверку (E2E); полученный статус состояния можно синхронно запросить на стороне прокси через GetE2EStateMachineStateGetter ([SWS_CM_00145]).
