Позволяет поставщикам услуг отправлять события со стороны сервера подписанным приложениям.

Класс <SI-Namespace>::skeleton::events::<Event> служит поставщикам услуг на AUTOSAR Adaptive Platform для публикации данных событий подписанным приложениям. События могут отправляться либо на основе копирования, либо эффективно без копирования через буферы, предварительно выделенные с помощью Allocate() ([SWS_CM_90438]). Вызов отправки через Send() строго требует, чтобы соответствующий экземпляр сервиса был предварительно успешно предложен и чтобы соблюдался сконфигурированный минимальный интервал отправки ([SWS_CM_00162]).

Контекст

Класс <SI-Namespace>::skeleton::events::<Event> представляет собой серверный интерфейс для публикации событий сервиса в рамках AUTOSAR Adaptive Platform. Он позволяет сервисному приложению (скелетону) асинхронно передавать обновленные данные событий типа SampleType ([SWS_CM_11400]) всем подписанным клиентским приложениям ([SWS_CM_00162]). При этом скелетон напрямую взаимодействует с коммуникационным уровнем (Communication Management), который берет на себя обнаружение экземпляров сервисов и физическое распределение данных событий. Помимо отправки данных, экземпляр Event отслеживает текущее состояние подписки и сообщает об изменениях круга подписчиков поставщику услуг ([SWS_CM_12008], [SWS_CM_12011]).

Контекстная диаграмма: взаимодействие класса Event с поставщиком услуг, Communication Management и подписчиками. Источники: [SWS_CM_00162], [SWS_CM_90437], [SWS_CM_12011]

Жизненный цикл

Инстанциирование класса Event происходит совместно с вышестоящим экземпляром сервиса скелетона. Предположительно, время жизни экземпляра Event жестко связано со временем жизни скелетона, так что объект события становится пригодным для использования только после конструирования сервиса и прекращает свое существование с его уничтожением. Перед активной передачей данных сервис должен быть предложен, так как попытки передачи до предложения сервиса завершаются сбоем ([SWS_CM_00162]).

Во время фазы эксплуатации экземпляр отражает состояние соединений с подписчиками. С помощью GetSubscriptionState() можно запросить текущее состояние ([SWS_CM_12011]). Для асинхронной реакции на изменения состояния приложение регистрирует соответствующий обратный вызов с помощью SetSubscriptionStateChangeHandler() ([SWS_CM_12008]), опционально привязанный к определенному контексту выполнения через объект Executor ([SWS_CM_12009]). При завершении или перенастройке сервиса этот обработчик можно снова дерегистрировать с помощью UnsetSubscriptionStateChangeHandler() ([SWS_CM_12010]). Все методы запроса состояния и методы обработчиков объявлены как noexcept и гарантируют безопасность исключений ([SWS_CM_12008], [SWS_CM_12011]).

Путь использования

Для публикации данных событий сервисному приложению доступны два принципиальных режима передачи: передача на основе копирования и метод Zero-Copy через управляемую память (EXP ara::com API с. 10).

При обычном пути использования поставщик услуг сначала при необходимости регистрирует обратный вызов для изменений подписки ([SWS_CM_12008]). Как только подписчики появляются, приложение либо создает локальные данные и передает их по значению в Send() ([SWS_CM_00162]), при этом Communication Management создает копию данных и пересылает ее всем подписчикам (EXP ara::com API с. 10).

В качестве альтернативы, во избежание затрат на копирование, приложение запрашивает буфер памяти в виде ara::com::SampleAllocateePtr<SampleType> напрямую у коммуникационного уровня через Allocate() ([SWS_CM_90438], EXP ara::com API с. 10). После заполнения буфера он передается через специализированную перегрузку Send() ([SWS_CM_90437]). Интерпретация: предполагается, что при отправке право владения памятью полностью переходит к Communication Management, поскольку приложению явно запрещен любой дальнейший доступ к данным после вызова ([SWS_CM_90437]).

Диаграмма последовательности: типичный процесс передачи событий, включая регистрацию обработчика и выделение памяти. Источники: [SWS_CM_12008], [SWS_CM_90438], [SWS_CM_90437], [SWS_CM_00162]

Сценарии ошибок

Вызовы Send() возвращают ara::core::Result<void>, который в случае ошибки содержит соответствующий код ошибки типа ara::com::ComErrc ([SWS_CM_00162], [SWS_CM_90437]). К определенным случаям ошибок относятся:

  • ComErrc::kServiceNotOffered: сервис еще не был предоставлен через OfferService() перед попыткой отправки ([SWS_CM_00162], [SWS_CM_90437]).
  • ComErrc::kMinimumSendIntervalViolationError: нарушен сконфигурированный для события минимальный интервал отправки (minimumSendInterval), так как вызовы отправки выполнялись слишком часто подряд ([SWS_CM_00162], [SWS_CM_90437]).

Кроме того, при выделении памяти и конфигурации обработчиков необходимо соблюдать предварительные условия:

  • Allocate() не является безопасным по отношению к исключениям (not exception safe) и приводит к SampleAllocationViolation при недостаточных ресурсах памяти или к AllocateUsageViolation при недопустимом использовании пользовательских аллокаторов ([SWS_CM_90438]).
  • SetSubscriptionStateChangeHandler() требует допустимого, вызываемого функционального объекта; если передан нулевой или несуществующий обработчик, это приводит к InvalidHandlerViolation ([SWS_CM_12008], [SWS_CM_12009]).

Настоящее руководство основано на спецификации AUTOSAR Adaptive Platform R25-11.

ara::com::SampleAllocateePtr< SampleType > Allocate ();

Allocating data for event transfer when Communication Management is responsible for the data.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: fc3608719061 Provenance

Метод Allocate вызывается на уровне скелетона для события ([SWS_CM_90438]; AUTOSAR_AP_EXP_ARAComAPI §5.4.1 «Skeleton Class API’s») с целью выделения памяти для передачи данных события, если Communication Management (ara::com) отвечает за управление данными ([SWS_CM_90438]). Он возвращает экземпляр типа ara::com::SampleAllocateePtr<SampleType> ([SWS_CM_90438]). Этот тип указателя концептуально ведет себя как std::unique_ptr<T>, так что в любой момент времени только одна сторона является владельцем указателя (ARAComAPI §6 «Event Allocate/Send sample Binding implementer hint»).

В отношении обработки ошибок и безопасности исключений Allocate специфицирован как not exception safe ([SWS_CM_90438]). Спецификация определяет два возможных нарушения (Violations):

  • SampleAllocationViolation: недостаточно ресурсов памяти для выделения данных ([SWS_CM_90438]).
  • AllocateUsageViolation: выделение памяти недопустимо выполнено через пользовательский аллокатор ([SWS_CM_90438]).

Концепция Allocate направлена прежде всего на поддержку механизмов zero-copy, в частности при IPC-транспорте на основе разделяемой памяти (shared memory), при этом предполагается строгая синхронизация между читателями и писателями (ARAComAPI §6 «Event Allocate/Send sample Binding implementer hint»). Разработчики реализации должны учитывать, что требования к сериализации могут свести на нет zero-copy, если типы данных в развертывании не настроены как бинарно совместимые или если логика обнаружения исключает это (ARAComAPI §6 «Event Allocate/Send sample Binding implementer hint»).

Во взаимодействии с отправкой событий полученный через Allocate указатель памяти передается в Send(ara::com::SampleAllocateePtr<SampleType> data) ([SWS_CM_90437]). После вызова Send сервисное приложение больше не должно обращаться к данным, как только Communication Management отправляет данные всем подписанным приложениям ([SWS_CM_90437]).

Функция [SWS_CM_00162] служит на стороне поставщика сервиса внутри <SI-Namespace>::skeleton::events::<Event> для отправки данных событий всем подписанным приложениям. При этом варианте ответственность за выделение памяти под данные полностью остается за использующим приложением. Через параметр data передается объект данных, после чего реализация биндинга создает внутреннюю копию во время вызова (ARAComAPI, Figure 6.17 «BrakeEvent Class»). После возврата из синхронного вызова метода приложение может сразу же модифицировать или освобождать исходную область памяти.

          

          
Метод объявлен с noexcept и специфицирован как безопасный относительно исключений. Он возвращает ara::core::Result<void>, который в случае успеха содержит void, а в случае ошибки сообщает коды ошибок из [SWS_CM_10432] ([SWS_CM_00162]):

          

            

          • ComErrc::kServiceNotOffered: возникает, если экземпляр сервиса еще не был предоставлен через OfferService().
            • 

          • ComErrc::kMinimumSendIntervalViolationError: возникает, если запрос на отправку был сделан быстрее сконфигурированного минимального интервала отправки (ServiceInterfaceDeploymentElement.minimumSendInterval).
            • 

          

          
В отличие от zero-copy-альтернативы [SWS_CM_90437], которая требует полученных через Allocate() указателей типа ara::com::SampleAllocateePtr, данный вызов не требует привязки памяти к фреймворку. Такое же поведение передачи и те же условия ошибок действуют согласно [SWS_CM_00119] и для метода обновления Update полей.

                •

              По сравнению с сигнатурой [SWS_CM_00162], при которой передаются данные под управлением приложения и копируются Communication Management, данный вариант нацелен на zero-copy-коммуникацию через разделяемую память (ARAComAPI §6.18 «Event Allocate/Send sample»).
