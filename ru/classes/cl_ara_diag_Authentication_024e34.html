Контекст

Класс ara::diag::Authentication предоставляет интерфейс для адаптивных приложений, позволяя им обрабатывать аутентификацию службы UDS (служба UDS 0x29 Authentication) в качестве обработчика службы AUTOSAR_AP_SWS_Diagnostics §4.1 «Limitations of sub-functions». Приложение реализует чисто виртуальные методы этого класса для выполнения входящих криптографических проверок, в то время как Diagnostic Manager (DM) управляет перенаправлением диагностических запросов [SWS_DM_01130].

Взаимодействие включает в себя три основные стороны: внешний диагностический тестер, Diagnostic Manager в качестве посредника для сообщений UDS, а также адаптивное приложение, которое через конкретный подкласс ara::diag::Authentication берет на себя фактическую проверку сертификатов и владения [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].

Контекстная диаграмма: интеграция ara::diag::Authentication между диагностическим тестером, Diagnostic Manager и приложением. Источники: [SWS_DM_01130], [SWS_DM_01126], AUTOSAR_AP_SWS_Diagnostics §4.1

Жизненный цикл

Создание экземпляра выполняется явно путем указания ara::core::InstanceSpecifier и ConcurrencyType [SWS_DM_01124]. InstanceSpecifier ссылается на смоделированный PortPrototype для DiagnosticAuthenticationInterface. С помощью параметра concurrencyType приложение определяет, обрабатываются ли вызовы потокобезопасно (kConcurrent) или непотокобезопасно (kNotConcurrent) [SWS_DM_01124]. Экземпляры ara::diag::Authentication строго привязаны к своей идентичности: конструкторы копирования и перемещения, а также операторы присваивания удалены (=delete) [SWS_DM_01609], [SWS_DM_01610], [SWS_DM_01607], [SWS_DM_01608].

После создания обработчик сначала находится в пассивном состоянии. Только вызов Offer() авторизует Diagnostic Manager для перенаправления входящих диагностических запросов экземпляру [SWS_DM_01130]. Метод StopOffer() снова отключает это перенаправление [SWS_DM_01131]. При уничтожении экземпляра через виртуальный деструктор ~Authentication() его жизненный цикл завершается; этот деструктор специфицирован как not thread-safe [SWS_DM_01125].

Путь использования

Типичный процесс диагностической аутентификации следует фиксированной последовательности: подготовка, проверка сертификата и подтверждение владения:

  1. Предоставление: Приложение создает экземпляр своего производного класса Authentication и сообщает о готовности к приему в Diagnostic Manager через Offer() [SWS_DM_01124], [SWS_DM_01130].
  2. Верификация сертификата: При поступлении запроса на аутентификацию Diagnostic Manager в зависимости от конфигурации диагностики вызывает либо VerifyCertificateUnidirectional() [SWS_DM_01126], либо VerifyCertificateBidirectional() [SWS_DM_01127]. Приложение проверяет переданный сертификат клиента и челлендж тестера. В качестве ответа оно асинхронно через ara::core::Future возвращает сгенерированный серверный челлендж, а также Ephemeral Public Key (при двунаправленной аутентификации дополнительно сертификат сервера и собственное подтверждение владения) [SWS_DM_01126], [SWS_DM_01127].
  3. Подтверждение владения (Proof of Ownership): На следующем шаге DM вызывает метод VerifyOwnership() [SWS_DM_01128]. Приложение проверяет переданное тестером подтверждение владения (clientPOWN) с использованием открытого ключа из ранее полученного сертификата и сгенерированного серверного челленджа. В случае успеха оно возвращает информацию о сессионном ключе в Future [SWS_DM_01128].
  4. Отмена регистрации: Перед завершением работы приложение отзывает предложение с помощью StopOffer() [SWS_DM_01131].

Функции обратного вызова могут вызываться реентрабельно при запросах от различных клиентов [SWS_DM_01126], [SWS_DM_01127]. С помощью переданного CancellationHandler приложение может проверить, была ли отменена обработка, или зарегистрировать обработчик уведомлений об отмене [SWS_DM_01126], [SWS_DM_01128].

Диаграмма последовательности: типичный процесс аутентификации через Diagnostic Manager. Источники: [SWS_DM_01130], [SWS_DM_01126], [SWS_DM_01128], [SWS_DM_01131]

Сценарии ошибок

При использовании ara::diag::Authentication необходимо учитывать следующие условия ошибок и предварительные проверки:

  • Ошибки конструирования (Violations): Если сопоставление InstanceSpecifier завершается неудачно (например, InstanceSpecifierMappingIntegrityViolation или PortInterfaceMappingViolation), процесс настроен некорректно (ProcessMappingViolation) или повторно указывается уже используемый идентификатор (InstanceSpecifierAlreadyInUseViolation), платформа сообщает о соответствующем нарушении [SWS_DM_01124].
  • Повторное предоставление: Если Offer() вызывается, когда служба уже предоставляется, метод возвращает ошибку с кодом ошибки DiagOfferErrc::kAlreadyOffered [SWS_DM_01130].
  • Ошибки верификации и протокола: Если проверка сертификата или верификация подтверждения владения завершается сбоем (например, недействительная подпись или истекший срок действия сертификата), приложение возвращает в Future соответствующий Negative Response Code (NRC) стандарта ISO-14229-1 с использованием DiagUdsNrcErrc [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].
  • Преждевременное прерывание: Если диагностический сеанс связи прерывается со стороны тестера или DM, cancellationHandler.IsCanceled() сообщает значение TRUE; приложению следует прервать криптографические операции, чтобы освободить вычислительные ресурсы [SWS_DM_01126].

Это руководство основано на требованиях спецификации AUTOSAR Adaptive R25-11.
