Контекст

Класс ara::diag::DoIPGroupIdentification в модуле диагностики AUTOSAR Adaptive предоставляет интерфейс для запроса текущего статуса групповой идентификации (GID-статуса) для протокола DoIP ([SWS_DM_00724]). Прикладные диагностические компоненты наследуются от этого базового класса и реализуют чисто виртуальный метод запроса GetGidStatus() ([SWS_DM_00724]).

В качестве связующего элемента данный класс взаимодействует с тремя ключевыми участниками системы:

  • Adaptive Application: реализует конкретный обработчик, создаёт экземпляр и управляет его доступностью ([SWS_DM_00722], [SWS_DM_00725]).
  • Diagnostic Management (DM): выполняет функции центрального диспетчера на платформе и перенаправляет входящие сообщения DoIP зарегистрированному обработчику ([SWS_DM_00725], [SWS_DM_00726]).
  • Стек протокола DoIP: требует актуального GID-состояния для идентификации узлов автомобиля и сетевых групп в рамках внешнего взаимодействия с транспортным средством ([SWS_DM_00724]).

Контекстная диаграмма: участники взаимодействия интерфейса DoIPGroupIdentification. Источники: [SWS_DM_00722], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726].

Жизненный цикл

Инстанцирование выполняется через конструктор DoIPGroupIdentification с указанием смоделированного ara::core::InstanceSpecifier и ConcurrencyType ([SWS_DM_00722]). Класс представляет собой стационарный отдельный экземпляр для назначенного порта. Операции копирования и перемещения явно удалены (AUTOSAR_AP_SWS_Diagnostics, с. 71): недоступны ни конструктор копирования ([SWS_DM_01641]), ни конструктор перемещения ([SWS_DM_01642]), ни оператор присваивания с копированием ([SWS_DM_01639]), ни оператор присваивания с перемещением ([SWS_DM_01640]).

С точки зрения работы экземпляр проходит чётко определённые фазы:

  1. Инициализирован: после конструирования объект существует, однако ещё не зарегистрирован в DM в качестве активного получателя.
  2. Предложен (Offered): путём вызова Offer() Diagnostic Management авторизуется для перенаправления запросов обработчику ([SWS_DM_00725]).
  3. Остановлен: вызов StopOffer() отзывает у DM полномочия на перенаправление и возвращает экземпляр в неактивное состояние ([SWS_DM_00726]).

Деструктор является виртуальным и определён как noexcept ([SWS_DM_00723]). Интерпретация: перед уничтожением объекта приложению, вероятно, потребуется вызвать StopOffer(), чтобы гарантировать, что DM больше не будет перенаправлять входящие запросы ликвидируемому обработчику.

Что касается параллелизма, конструктор является потокобезопасным ([SWS_DM_00722]). Для чисто виртуального метода GetGidStatus() требуемая потокобезопасность зависит от параметра concurrencyType ([SWS_DM_00722], [SWS_DM_00724]): при kConcurrent подкласс должен быть реализован как потокобезопасный, при kNotConcurrent этого не требуется. Административные методы Offer() ([SWS_DM_00725]) и StopOffer() ([SWS_DM_00726]), а также деструктор ([SWS_DM_00723]) не являются потокобезопасными и требуют синхронизированных вызовов.

Путь использования

Предоставление и выполнение групповой идентификации DoIP следует фиксированной последовательности вызовов:

  1. Создание подкласса: приложение определяет производный класс и переопределяет метод GetGidStatus() ([SWS_DM_00724]).
  2. Инстанцирование: создаётся производный объект; при этом передаётся InstanceSpecifier соответствующего PortPrototype и определяется модель параллелизма ([SWS_DM_00722]).
  3. Предложение службы (Offer): приложение активирует перенаправление вызовом Offer() ([SWS_DM_00725]). DM переводит перенаправление в активный режим.
  4. Запрос статуса: при поступлении входящих сообщений DoIP DM вызывает метод GetGidStatus() обработчика ([SWS_DM_00724]). Приложение возвращает результат асинхронно через ara::core::Future<GidStatus> ([SWS_DM_00724]). Интерпретация: асинхронный интерфейс через Future, вероятно, был выбран для того, чтобы компенсировать возможные задержки при считывании аппаратных или низкоуровневых данных групповой идентификации без блокировки потока DM.
  5. Завершение (StopOffer): перед деинициализацией приложение вызывает StopOffer() ([SWS_DM_00726]), в результате чего перенаправление деактивируется. После этого объект может быть уничтожен ([SWS_DM_00723]).

Диаграмма последовательности: типичный процесс от регистрации через асинхронный опрос статуса до отмены регистрации. Источники: [SWS_DM_00722], [SWS_DM_00723], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726].

Сценарии ошибок

Условия ошибок главным образом сосредоточены вокруг нарушений конфигурации при инстанцировании и недопустимых переходов состояний во время выполнения:

  • Нарушения модели и портов (конструктор) ([SWS_DM_00722]):
    • InstanceSpecifierMappingIntegrityViolation: InstanceSpecifier не удается разрешить в контексте выполнения или он не указывает на PortPrototype.
    • PortInterfaceMappingViolation: Порт, на который ссылается сопоставление DiagnosticDoIpGroupIdentificationPortMapping, не типизирован через DiagnosticDoIPGroupIdentificationInterface.
    • ProcessMappingViolation: Для смоделированной InstanceRef во время выполнения отсутствует подходящий процесс.
    • InstanceSpecifierAlreadyInUseViolation: Указанный InstanceSpecifier внутри текущего процесса уже занят существующим экземпляром.
  • Ошибки времени выполнения при Offer ([SWS_DM_00725]): Если Offer() вызывается, когда сервис уже предлагается, вызов завершается сбоем и возвращает в ara::core::Result код ошибки DiagOfferErrc::kAlreadyOffered с семантикой отката.
  • Безошибочные методы: Для GetGidStatus() не специфицированы стандартизированные коды ошибок ([SWS_DM_00724]). StopOffer() имеет тип возвращаемого значения void и не определяет состояний ошибок ([SWS_DM_00726]).
  • Безопасность исключений: Все методы класса объявлены с noexcept и специфицированы как безопасные к исключениям (exception safe) ([SWS_DM_00722], [SWS_DM_00723], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726], AUTOSAR_AP_SWS_Diagnostics, с. 73).

Данное руководство основано на спецификации AUTOSAR Adaptive Platform R25-11 (модуль diag) и обобщает архитектуру, жизненный цикл, а также поведение при ошибках.
