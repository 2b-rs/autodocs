Служит клиентским приложениям в качестве типизированного заместителя для поиска сервисов и взаимодействия с экземпляром сервиса.

Класс <SI>Proxy служит клиентским приложениям типизированным представителем Service Interface для передачи вызовов методов, событий и полей [SWS_CM_99447]. После успешного поиска сервиса экземпляр предпочтительно создается с помощью безысключительного фабричного метода Create() [SWS_CM_10438]. Класс обладает семантикой перемещения (Move-Only) и требует полного освобождения всех удерживаемых выборок данных (samples) перед его уничтожением во избежание нарушений предусловий [SWS_CM_99444].

Контекст

Сгенерированный класс <SI>Proxy выступает в коммуникационной архитектуре AUTOSAR Adaptive Platform в качестве типизированной конечной точки клиента для определенного Service Interface. Он инкапсулирует взаимодействие клиентского приложения с удаленным или локальным экземпляром этого сервиса. В число партнеров по взаимодействию входят использующий программный компонент, сам экземпляр прокси, а также лежащее в основе управление связью (ara::com), контролирующее сетевое связывание и передачу сообщений. Через выделенные элементы данных events::<Event> [SWS_CM_99445], fields::<Field> [SWS_CM_99446] и methods::<Method> [SWS_CM_99447] прокси предоставляет прямой доступ к событиям, полям и методам интерфейса сервиса.

Контекстная диаграмма: интеграция прокси Service Interface между клиентским приложением и управлением связью. Источники: [SWS_CM_99445], [SWS_CM_99446], [SWS_CM_99447].

Жизненный цикл

Создание экземпляра прокси предполагает предварительно успешно выполненный поиск сервиса, возвращающий валидный экземпляр дескриптора (HandleType). Предпочтительное создание осуществляется безысключительно через статический фабричный метод Create() в соответствии с идиомой именованного конструктора [SWS_CM_10438], который возвращает ara::core::Result с прокси или кодом ошибки. В качестве альтернативы существует явный конструктор <SI>Proxy(handle), специфицированный как небезопасный относительно исключений и способный в случае ошибки выбросить ara::com::ComException [SWS_CM_00131]. Дескриптор, использованный для инициализации, можно запросить в любой момент через GetHandle() [SWS_CM_10383].

С точки зрения отношений владения прокси обладает семантикой исключительно перемещения (Move-Only): конструктор копирования [SWS_CM_00136] и оператор присваивания с копированием [SWS_CM_11551] явно удалены. Передача экземпляра допускается исключительно через конструктор перемещения [SWS_CM_00137] или безысключительный оператор присваивания с перемещением [SWS_CM_11552]. В течение времени жизни статус доступности сервиса можно активно опрашивать с помощью GetServiceState() [SWS_CM_01073]. В качестве альтернативы SetServiceStateChangeHandler() позволяет зарегистрировать функцию обратного вызова при изменениях статуса [SWS_CM_01074], которая по выбору может быть привязана к пользовательскому контексту через ExecutorT [SWS_CM_01076]. Регистрацию обработчика можно отменить через UnsetServiceStateChangeHandler() [SWS_CM_01075].

Уничтожение выполняется через деструктор ~<SI>Proxy() [SWS_CM_99444]. Он объявлен как небезопасный относительно исключений и требует в качестве обязательного предусловия, чтобы перед уничтожением клиент больше не удерживал открытых выборок данных (data samples), во избежание нарушений [SWS_CM_99444].

Путь использования

Типичный сценарий использования делится на четыре фазы:

  1. Поиск сервиса: клиент ищет экземпляры сервиса либо синхронно через FindService() с InstanceIdentifier [SWS_CM_00122] или модельным InstanceSpecifier [SWS_CM_00622] EXP ARAComAPI §2 «Service Interface Proxy», либо асинхронно через StartFindService() [SWS_CM_00123] [SWS_CM_00623]. Для асинхронного поиска дополнительно может передаваться ExecutorT [SWS_CM_11352] [SWS_CM_11365] EXP ARAComAPI §2 «Service Interface Proxy». Асинхронный поиск после обнаружения желаемого экземпляра должен быть остановлен через StopFindService() [SWS_CM_00125] EXP ARAComAPI §2 «Service Interface Proxy».
  2. Инстанцирование: из определенного ServiceHandleContainer выбирается дескриптор и передается в Create() для создания экземпляра прокси [SWS_CM_10438]. Интерпретация: фабричный метод Create(), вероятно, является основным путем инстанцирования по сравнению с выбрасывающим исключения конструктором.
  3. Взаимодействие: приложение взаимодействует с сервисом посредством вызовов методов (methods::<Method>) [SWS_CM_99447], мониторинга событий (events::<Event>) [SWS_CM_99445] или доступа к полям (fields::<Field>) [SWS_CM_99446].
  4. Очистка: после завершения взаимодействия экземпляр прокси уничтожается, при этом должно быть гарантировано, что не осталось недействительных ссылок на выборки данных [SWS_CM_99444].

Диаграмма последовательности: типичный процесс поиска сервиса, инстанцирования прокси и взаимодействия через методы. Источники: [SWS_CM_00122], [SWS_CM_10438], [SWS_CM_99447], [SWS_CM_99444].

Сценарии ошибок

Ошибки возвращаются преимущественно через тип ошибки ara::com::ComErrc в ara::core::Result:

  • ComErrc::kServiceNotAvailable: возникает при Create(), если ранее предложенный сервис больше недоступен [SWS_CM_10438]. При прямом вызове конструктора это приводит вместо этого к ara::com::ComException [SWS_CM_00131].
  • ComErrc::kCommunicationFailure: возвращается методами FindService() [SWS_CM_00122] [SWS_CM_00622], StartFindService() [SWS_CM_00123] [SWS_CM_00623], Create() [SWS_CM_10438] и GetServiceState() [SWS_CM_01073], если сетевое связывание обнаруживает устранимую ошибку связи или ошибку защищенной коммуникации.

Дополнительно специфицированы следующие нарушения (Violations):

  • ErroneousServiceHandleViolation: дескриптор, переданный в Create() или конструктор, недействителен или поврежден [SWS_CM_10438] [SWS_CM_00131].
  • InsufficientPermissionsViolation: отказ в доступе при поиске сервиса или инстанцировании из-за механизма контроля полномочий (Grant Enforcement) [SWS_CM_00122] [SWS_CM_10438].
  • InvalidHandlerViolation: передача недействительного или пустого обратного вызова в StartFindService() [SWS_CM_00123] или SetServiceStateChangeHandler() [SWS_CM_01074].
  • InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, InstanceSpecifierAlreadyInUseViolation: возникают при модельных вызовах поиска, если сопоставление InstanceSpecifier ошибочно или уже используется [SWS_CM_00622] [SWS_CM_00623].
  • DanglingSamplesViolation: уничтожение прокси при еще существующих ссылках на выборки данных [SWS_CM_99444].

Использование и семантика

Статический фабричный метод Create служит согласно [SWS_CM_10438] для создания экземпляра прокси (<SI>Proxy) без генерации исключений в соответствии с идиомой именованного конструктора. В качестве параметра handle он требует предварительно определенный дескриптор сервиса согласно [SWS_CM_00131]. Вызов выполняется синхронно и объявлен как noexcept. Результат возвращается в ara::core::Result, который в случае успеха содержит готовый к работе экземпляр прокси.

Обработка ошибок

Если во время инстанцирования возникает ошибка, Create через ara::core::Result возвращает код ошибки типа ara::com::ComErrc [SWS_CM_10438]:

  • ComErrc::kServiceNotAvailable: сервис больше не доступен после предварительного предложения через OfferService().
  • ComErrc::kCommunicationFailure: сетевая привязка сообщает об устранимой ошибке коммуникации или сбое защищенного соединения.

Обе ошибки обладают семантикой отката (rollback) [SWS_CM_10438]. При структурных ошибках или ошибках, связанных с безопасностью, действуют специфицированные нарушения (violations): если переданный дескриптор равен null или поврежден, имеет место ErroneousServiceHandleViolation. Если у вызывающего процесса в рамках grant enforcement отсутствуют необходимые полномочия для экземпляра, запрос отклоняется и обрабатывается как InsufficientPermissionsViolation (SWS CommunicationManagement §8 «Security», [SWS_CM_10438]).

Параллелизм и граничные условия

Интерпретация: поскольку Create работает синхронно и связывает коммуникационные ресурсы, вызов для различных дескрипторов, вероятно, является реентерабельным, однако из-за возможной сетевой инициализации его не следует выполнять в критичных по времени циклах жесткого реального времени.
