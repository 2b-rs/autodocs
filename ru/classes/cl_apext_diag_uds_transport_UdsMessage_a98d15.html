класс apext::diag::uds_transport::UdsMessage

[SWS_DM_00291] Upstream: RS_Diag_04147

class UdsMessage {...};

class represents an UDS message exchanged between DM generic core (UdsTransport ProtocolMgr) and a specific implementation of UdsTransportProtocolHandler on diagnostic request reception path or diagnostic response transmission path. UdsMessage provides the storage for UDS requests/responses.

Instances of UdsMessage (with optimized resource allocation) are only created by DM generic core, the UdsTransportProtocolHandler can read/write on it.

Служит носителем данных и информации для UDS-сообщений при обмене данными в менеджере диагностики Adaptive.

Класс apext::diag::uds_transport::UdsMessage представляет собой стандартизированный объект хранения и передачи диагностических сообщений, которыми обмениваются типовое ядро диагностики и транспортные обработчики. Экземпляры создаются исключительно типовым ядром с оптимизированным выделением памяти и предоставляются через UdsMessagePtr [SWS_DM_09012]. В тракте приема обработчик заполняет предоставленный буфер данных, начиная с идентификатора сервиса, и пересылает сообщение после добавления метаданных канала при их наличии [SWS_DM_00388]. Если ядро не может обработать сообщение из-за текущей нагрузки, в выделении отказывается и возвращается нулевой указатель [SWS_DM_00386].

Контекст

Класс apext::diag::uds_transport::UdsMessage представляет собой центральный объект данных и хранения для UDS-сообщений, которыми обмениваются типовое ядро Diagnostic Management (DM Generic Core или UdsTransportProtocolMgr) и конкретная реализация UdsTransportProtocolHandler. Он служит инкапсуляцией и хранилищем (Storage) для входящих UDS-запросов и исходящих UDS-ответов.

Помимо полезных данных UdsMessage передает параметры адресации диагностической коммуникации: адрес источника Address [SWS_DM_00293] через GetSa() [SWS_DM_00297], целевой адрес через GetTa() [SWS_DM_00298], а также тип адреса TargetAddressType (физический с kPhysical или функциональный с kFunctional) [SWS_DM_00296] через GetTaType() [SWS_DM_00299]. Кроме того, через AddMetaInfo() могут быть добавлены специфичные для канала метаданные, такие как параметры соединения для DoIP [SWS_DM_00294], [SWS_DM_00302].

Контекстная диаграмма: взаимодействие между ядром DM, транспортным обработчиком и UdsMessage. Источники: [SWS_DM_09012], [SWS_DM_00385], [SWS_DM_00345]

Жизненный цикл

Экземпляры UdsMessage создаются с оптимизированным выделением ресурсов исключительно типовым ядром Diagnostic Management. Чтобы исключить неконтролируемое инстанцирование протокольными обработчиками, конструктор по умолчанию объявлен защищенным (protected) [SWS_DM_09012]. Обработчики получают доступ к объектам сообщений исключительно через указатели владения типа apext::diag::uds_transport::UdsMessagePtr [SWS_DM_00303] или для доступа только на чтение через apext::diag::uds_transport::UdsMessageConstPtr [SWS_DM_00304], AUTOSAR_AP_SWS_Diagnostics с. 98.

Уничтожение объекта выполняется через виртуальный деструктор ~UdsMessage() [SWS_DM_09010]. Что касается параллелизма, методы запроса информации об адресации (GetSa, GetTa, GetTaType) являются реентерабельными (reentrant) и безопасными относительно исключений (noexcept) [SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299]. Доступ к буферу данных через GetPayload(), а также добавление метаданных через AddMetaInfo(), напротив, классифицируются как потоконебезопасные, поскольку реализация в рамках этих вызовов может выполнять выделение буферов и ресурсов [SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302].

Путь использования

В штатном процессе тракта приема UdsTransportProtocolHandler анонсирует входящий UDS-запрос через UdsTransportProtocolMgr::IndicateMessage() в DM [SWS_DM_00385]. Если DM готов к приему, он подтверждает это статусом kIndicationOk и передает UdsMessagePtr с минимальным размером в один байт и запрошенной DM емкостью буфера [SWS_DM_00385].

Затем протокольный обработчик вызывает неконстантный метод GetPayload(), чтобы получить доступную для записи ссылку на базовую область памяти (uds_transport::ByteSpan&) [SWS_DM_00301]. Он заполняет этот буфер, начиная с идентификатора сервиса (SID), вплоть до максимальной емкости объекта UdsMessage или полной длины сообщения [SWS_DM_00388]. После опционального добавления специфичных для канала метаданных через AddMetaInfo() [SWS_DM_00302] обработчик пересылает заполненный объект через UdsTransportProtocolMgr::HandleMessage() в ядро диагностики [SWS_DM_00345]. (Интерпретация: в тракте передачи диагностических ответов предоставление UdsMessage, по всей видимости, выполняется типовым ядром аналогичным образом.)

Диаграмма последовательности: последовательность взаимодействия при приеме UDS-сообщения. Источники: [SWS_DM_00385], [SWS_DM_00386], [SWS_DM_00388], [SWS_DM_00301], [SWS_DM_00302], [SWS_DM_00345]

Сценарии ошибок

Если DM не может обработать сообщение, анонсированное через IndicateMessage(), поскольку он занят активной обработкой сервиса той же сессии Tester-Present, он возвращает статус kIndicationOccupied и UdsMessagePtr, равный nullptr [SWS_DM_00386]. В этом случае UdsMessage не предоставляется и прием прерывается. Неизвестный целевой адрес также приводит к результату kIndicationUnknownTargetAddress с нулевым указателем в качестве ссылки на сообщение AUTOSAR_AP_SWS_Diagnostics с. 100.

При заполнении буфера протокольный обработчик должен учитывать заданную емкость буфера: входящие запросы, превышающие предоставленную емкость UdsMessage, ограничиваются полным размером буфера [SWS_DM_00388]. Кроме того, одновременный незащищенный доступ к GetPayload() или AddMetaInfo() из нескольких потоков приводит к неопределенному поведению, поскольку эти интерфейсы явно специфицированы как потоконебезопасные (unsafe) [SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302].

Данное руководство по классу составлено на основе спецификации AUTOSAR R25-11 для Adaptive Platform.

virtual void AddMetaInfo (MetaInfoMap metaInfo) noexcept;

add new metaInfo to this message.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: f214c6d35475 Provenance

Виртуальная функция-член AddMetaInfo класса apext::diag::uds_transport::UdsMessage служит для назначения новых метаданных диагностическому сообщению [SWS_DM_00302]. Как правило, она вызывается плагином транспортного протокола для добавления каналоспецифичной дополнительной информации — например, предварительно определенных ключей метаданных для DoIP — к соответствующему диагностическому запросу AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».

Для использования интерфейса действуют следующие рамочные условия [SWS_DM_00302]:

  • Контекст вызова и заголовочный файл: объявление предоставляется через заголовочный файл apext/diag/uds_transport/uds_message.h и выполняется непосредственно на экземплярах UdsMessage AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».
  • Входные параметры: входной параметр metaInfo типа MetaInfoMap передает добавляемую метаинформацию запроса [SWS_DM_00302].
  • Возвращаемое значение: синхронная функция не возвращает значения (void) [SWS_DM_00302].
  • Обработка ошибок: операция снабжена спецификатором noexcept и специфицирована как бессбойная (exception safe); специфические коды ошибок отсутствуют [SWS_DM_00302].

В отношении параллелизма метод объявлен как непотокобезопасный (thread safety: unsafe) [SWS_DM_00302]. Интерпретация: следовательно, вызывающие стороны, вероятно, несут ответственность за защиту от параллельного доступа к одному и тому же экземпляру UdsMessage с помощью внешних механизмов, поскольку спецификация не предусматривает внутренней синхронизации AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».
