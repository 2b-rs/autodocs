класс apext::diag::uds_transport::UdsMessage

[SWS_DM_00291] Upstream: RS_Diag_04147

class UdsMessage {...};

class represents an UDS message exchanged between DM generic core (UdsTransport ProtocolMgr) and a specific implementation of UdsTransportProtocolHandler on diagnostic request reception path or diagnostic response transmission path. UdsMessage provides the storage for UDS requests/responses.

Instances of UdsMessage (with optimized resource allocation) are only created by DM generic core, the UdsTransportProtocolHandler can read/write on it.

Контекст

Класс apext::diag::uds_transport::UdsMessage инкапсулирует UDS-сообщение (Request или Response) и выступает в качестве центрального хранилища диагностических данных, которыми обмениваются типовое ядро Diagnostic Management (UdsTransportProtocolMgr) и конкретная реализация транспортного протокола (UdsTransportProtocolHandler). Экземпляр предоставляет базовый буфер сообщений как на тракте приема диагностических запросов (RX), так и на тракте передачи диагностических ответов (TX).

Помимо чисто полезных данных, UdsMessage управляет метаданными и адресной информацией. Через GetSa() запрашивается адрес источника ([SWS_DM_00297]), а через GetTa() — целевой адрес ([SWS_DM_00298]) типа Address ([SWS_DM_00293]). Тип целевого адреса определяется с помощью GetTaType() ([SWS_DM_00299]), при этом перечисление TargetAddressType различает физическую (kPhysical) и функциональную (kFunctional) адресацию ([SWS_DM_00296]). Кроме того, специфичная для канала дополнительная информация (например, предварительно определенные метаданные для плагинов DoIP) может быть прикреплена к сообщению через метод AddMetaInfo() в виде MetaInfoMap ([SWS_DM_00302], [SWS_DM_00294]).

Контекстная диаграмма: взаимодействие ядра DM, обработчика транспортного протокола и UdsMessage. Источники: [SWS_DM_00385], [SWS_DM_09012].

Жизненный цикл

Экземпляры UdsMessage создаются исключительно типовым ядром Diagnostic Management в условиях оптимизированного выделения ресурсов. Конструктор по умолчанию UdsMessage() объявлен защищенным (protected) ([SWS_DM_09012]), чтобы явно запретить обработчикам транспортных протоколов самостоятельно создавать экземпляры.

Отношения владения и передача объектов UdsMessage регулируются с помощью интеллектуальных указателей. Для этого платформа определяет псевдонимы типов UdsMessagePtr для доступа на запись ([SWS_DM_00303]) и UdsMessageConstPtr для константного доступа на чтение ([SWS_DM_00304]). При приеме сообщения ядро DM передает владение экземпляром обработчику через UdsMessagePtr ([SWS_DM_00385]). После завершения заполнения сообщение снова передается ядру DM для обработки ([SWS_DM_00345]). Освобождение и уничтожение происходят детерминированно через виртуальный деструктор по умолчанию ~UdsMessage() ([SWS_DM_09010]).

С точки зрения параллелизма методы запроса адреса (GetSa(), GetTa(), GetTaType()) специфицированы как реентерабельные ([SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299]). Напротив, методы для доступа к полезным данным и метаданным (GetPayload() и AddMetaInfo()) не являются потокобезопасными (unsafe) ([SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302]), поскольку реализациям разрешено выполнять выделение буферов и ресурсов при вызовах GetPayload().

Путь использования

Типичная последовательность действий на тракте приема диагностики (RX) подразделяется на следующие шаги:

  1. Оповещение: UdsTransportProtocolHandler принимает UDS-запрос из сети и сигнализирует о его поступлении вызовом UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00385]).
  2. Инстанцирование и предоставление буфера: Если DM может обработать запрос, IndicateMessage() возвращает std::pair ([SWS_DM_00309]) со статусом kIndicationOk и UdsMessagePtr, который владеет созданным UdsMessage. Выделенный буфер имеет минимальный размер в один байт ([SWS_DM_00385]).
  3. Заполнение полезных данных: Обработчик вызывает неконстантную перегрузку GetPayload() ([SWS_DM_00301]) и получает ссылку на uds_transport::ByteSpan&. Обработчик заполняет объект UdsMessage принятыми данными UDS, начиная с идентификатора службы (SID), либо до полной емкости сообщения, либо до полной длины принятого UDS-запроса ([SWS_DM_00388]).
  4. Добавление метаданных: При необходимости обработчик добавляет каналоспецифичные метаданные через AddMetaInfo() ([SWS_DM_00302]).
  5. Пересылка в ядро DM: Как только полезные данные полностью записаны в UdsMessage, обработчик передает сообщение через UdsTransportProtocolMgr::HandleMessage() в универсальное ядро DM для дальнейшей диагностической обработки ([SWS_DM_00345]).
  6. Доступ для чтения в ядре DM: Диагностическое ядро считывает данные сообщения (A_Data согласно ISO) только для чтения через константную перегрузку GetPayload() const ([SWS_DM_00300]).

Интерпретация: на пути диагностического ответа (TX) универсальное ядро DM, вероятно, аналогичным образом самостоятельно заполняет объект UdsMessage данными ответа и передает его UdsTransportProtocolHandler для передачи.

Диаграмма последовательности: процесс приема сообщений и заполнения буфера на пути приема. Источники: [SWS_DM_00301], [SWS_DM_00302], [SWS_DM_00345], [SWS_DM_00385], [SWS_DM_00388].

Сценарии ошибок

При взаимодействии и выделении буфера могут возникать следующие ошибочные ситуации:

  • DM занят (Busy): Если DM уже занят активной обработкой службы того же диалога, IndicateMessage() возвращает статус kIndicationOccupied и нулевой указатель для UdsMessagePtr ([SWS_DM_00386]). В этом случае UdsMessage не предоставляется. Исключением являются функциональные запросы TesterPresent с установленным suppressPosRspMsgIndicationBit (полезная нагрузка 0x3E 0x80), которые валидны в любой момент времени и могут обрабатываться ([SWS_DM_00386], [SWS_DM_00126]).
  • Неизвестный адрес назначения: Если адрес назначения сообщения не может быть разрешен, DM сигнализирует об этом с помощью результата kIndicationUnknownTargetAddress и устанавливает UdsMessagePtr в nullptr (AUTOSAR_AP_SWS_Diagnostics с. 100). Выделение объекта сообщения не выполняется.
  • Ограничение буфера: Емкость переданного объекта UdsMessage ограничена выделением памяти, заданным DM. Обработчик может выполнять запись в буфер не более чем до предела его емкости ([SWS_DM_00388]).

<h4>Контекст</h4>
<p>Класс <code>apext::diag::uds_transport::UdsMessage</code> инкапсулирует UDS-сообщение (Request или Response) и выступает в качестве центрального хранилища диагностических данных, которыми обмениваются типовое ядро Diagnostic Management (<code>UdsTransportProtocolMgr</code>) и конкретная реализация транспортного протокола (<code>UdsTransportProtocolHandler</code>). Экземпляр предоставляет базовый буфер сообщений как на тракте приема диагностических запросов (RX), так и на тракте передачи диагностических ответов (TX).</p>
<p>Помимо чисто полезных данных, <code>UdsMessage</code> управляет метаданными и адресной информацией. Через <code>GetSa()</code> запрашивается адрес источника (<a class="spec-record-ref" data-req="SWS_DM_00297" href="../spec/record.html?id=SWS_DM_00297">[SWS_DM_00297]</a>), а через <code>GetTa()</code> — целевой адрес (<a class="spec-record-ref" data-req="SWS_DM_00298" href="../spec/record.html?id=SWS_DM_00298">[SWS_DM_00298]</a>) типа <code>Address</code> (<a class="spec-record-ref" data-req="SWS_DM_00293" href="../spec/record.html?id=SWS_DM_00293">[SWS_DM_00293]</a>). Тип целевого адреса определяется с помощью <code>GetTaType()</code> (<a class="spec-record-ref" data-req="SWS_DM_00299" href="../spec/record.html?id=SWS_DM_00299">[SWS_DM_00299]</a>), при этом перечисление <code>TargetAddressType</code> различает физическую (<code>kPhysical</code>) и функциональную (<code>kFunctional</code>) адресацию (<a class="spec-record-ref" data-req="SWS_DM_00296" href="../spec/record.html?id=SWS_DM_00296">[SWS_DM_00296]</a>). Кроме того, специфичная для канала дополнительная информация (например, предварительно определенные метаданные для плагинов DoIP) может быть прикреплена к сообщению через метод <code>AddMetaInfo()</code> в виде <code>MetaInfoMap</code> (<a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>, <a class="spec-record-ref" data-req="SWS_DM_00294" href="../spec/record.html?id=SWS_DM_00294">[SWS_DM_00294]</a>).</p>

<h4>Жизненный цикл</h4>
<p>Экземпляры <code>UdsMessage</code> создаются исключительно типовым ядром Diagnostic Management в условиях оптимизированного выделения ресурсов. Конструктор по умолчанию <code>UdsMessage()</code> объявлен защищенным (<code>protected</code>) (<a class="spec-record-ref" data-req="SWS_DM_09012" href="../spec/record.html?id=SWS_DM_09012">[SWS_DM_09012]</a>), чтобы явно запретить обработчикам транспортных протоколов самостоятельно создавать экземпляры.</p>
<p>Отношения владения и передача объектов <code>UdsMessage</code> регулируются с помощью интеллектуальных указателей. Для этого платформа определяет псевдонимы типов <code>UdsMessagePtr</code> для доступа на запись (<a class="spec-record-ref" data-req="SWS_DM_00303" href="../spec/record.html?id=SWS_DM_00303">[SWS_DM_00303]</a>) и <code>UdsMessageConstPtr</code> для константного доступа на чтение (<a class="spec-record-ref" data-req="SWS_DM_00304" href="../spec/record.html?id=SWS_DM_00304">[SWS_DM_00304]</a>). При приеме сообщения ядро DM передает владение экземпляром обработчику через <code>UdsMessagePtr</code> (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>). После завершения заполнения сообщение снова передается ядру DM для обработки (<a class="spec-record-ref" data-req="SWS_DM_00345" href="../spec/record.html?id=SWS_DM_00345">[SWS_DM_00345]</a>). Освобождение и уничтожение происходят детерминированно через виртуальный деструктор по умолчанию <code>~UdsMessage()</code> (<a class="spec-record-ref" data-req="SWS_DM_09010" href="../spec/record.html?id=SWS_DM_09010">[SWS_DM_09010]</a>).</p>
<p>С точки зрения параллелизма методы запроса адреса (<code>GetSa()</code>, <code>GetTa()</code>, <code>GetTaType()</code>) специфицированы как реентерабельные (<a class="spec-record-ref" data-req="SWS_DM_00297" href="../spec/record.html?id=SWS_DM_00297">[SWS_DM_00297]</a>, <a class="spec-record-ref" data-req="SWS_DM_00298" href="../spec/record.html?id=SWS_DM_00298">[SWS_DM_00298]</a>, <a class="spec-record-ref" data-req="SWS_DM_00299" href="../spec/record.html?id=SWS_DM_00299">[SWS_DM_00299]</a>). Напротив, методы для доступа к полезным данным и метаданным (<code>GetPayload()</code> и <code>AddMetaInfo()</code>) не являются потокобезопасными (unsafe) (<a class="spec-record-ref" data-req="SWS_DM_00300" href="../spec/record.html?id=SWS_DM_00300">[SWS_DM_00300]</a>, <a class="spec-record-ref" data-req="SWS_DM_00301" href="../spec/record.html?id=SWS_DM_00301">[SWS_DM_00301]</a>, <a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>), поскольку реализациям разрешено выполнять выделение буферов и ресурсов при вызовах <code>GetPayload()</code>.</p>

<h4>Путь использования</h4>
<p>Типичная последовательность действий на тракте приема диагностики (RX) подразделяется на следующие шаги:</p>
<ol>
<li><strong>Оповещение:</strong> <code>UdsTransportProtocolHandler</code> принимает UDS-запрос из сети и сигнализирует о его поступлении вызовом <code>UdsTransportProtocolMgr::IndicateMessage()</code> (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>).</li>
<li><strong>Инстанцирование и предоставление буфера:</strong> Если DM может обработать запрос, <code>IndicateMessage()</code> возвращает <code>std::pair</code> (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>) со статусом <code>kIndicationOk</code> и <code>UdsMessagePtr</code>, который владеет созданным <code>UdsMessage</code>. Выделенный буфер имеет минимальный размер в один байт (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>).</li>
<li><strong>Заполнение полезных данных:</strong> Обработчик вызывает неконстантную перегрузку <code>GetPayload()</code> (<a class="spec-record-ref" data-req="SWS_DM_00301" href="../spec/record.html?id=SWS_DM_00301">[SWS_DM_00301]</a>) и получает ссылку на <code>uds_transport::ByteSpan&amp;</code>. Обработчик заполняет объект <code>UdsMessage</code> принятыми данными UDS, начиная с идентификатора службы (SID), либо до полной емкости сообщения, либо до полной длины принятого UDS-запроса (<a class="spec-record-ref" data-req="SWS_DM_00388" href="../spec/record.html?id=SWS_DM_00388">[SWS_DM_00388]</a>).</li>
<li><strong>Добавление метаданных:</strong> При необходимости обработчик добавляет каналоспецифичные метаданные через <code>AddMetaInfo()</code> (<a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>).</li>
<li><strong>Пересылка в ядро DM:</strong> Как только полезные данные полностью записаны в <code>UdsMessage</code>, обработчик передает сообщение через <code>UdsTransportProtocolMgr::HandleMessage()</code> в универсальное ядро DM для дальнейшей диагностической обработки (<a class="spec-record-ref" data-req="SWS_DM_00345" href="../spec/record.html?id=SWS_DM_00345">[SWS_DM_00345]</a>).</li>
<li><strong>Доступ для чтения в ядре DM:</strong> Диагностическое ядро считывает данные сообщения (A_Data согласно ISO) только для чтения через константную перегрузку <code>GetPayload() const</code> (<a class="spec-record-ref" data-req="SWS_DM_00300" href="../spec/record.html?id=SWS_DM_00300">[SWS_DM_00300]</a>).</li>
</ol>
<p>Интерпретация: на пути диагностического ответа (TX) универсальное ядро DM, вероятно, аналогичным образом самостоятельно заполняет объект <code>UdsMessage</code> данными ответа и передает его <code>UdsTransportProtocolHandler</code> для передачи.</p>

<h4>Сценарии ошибок</h4>
<p>При взаимодействии и выделении буфера могут возникать следующие ошибочные ситуации:</p>
<ul>
<li><strong>DM занят (Busy):</strong> Если DM уже занят активной обработкой службы того же диалога, <code>IndicateMessage()</code> возвращает статус <code>kIndicationOccupied</code> и нулевой указатель для <code>UdsMessagePtr</code> (<a class="spec-record-ref" data-req="SWS_DM_00386" href="../spec/record.html?id=SWS_DM_00386">[SWS_DM_00386]</a>). В этом случае <code>UdsMessage</code> не предоставляется. Исключением являются функциональные запросы <code>TesterPresent</code> с установленным <code>suppressPosRspMsgIndicationBit</code> (полезная нагрузка <code>0x3E 0x80</code>), которые валидны в любой момент времени и могут обрабатываться (<a class="spec-record-ref" data-req="SWS_DM_00386" href="../spec/record.html?id=SWS_DM_00386">[SWS_DM_00386]</a>, <a class="spec-record-ref" data-req="SWS_DM_00126" href="../spec/record.html?id=SWS_DM_00126">[SWS_DM_00126]</a>).</li>
<li><strong>Неизвестный адрес назначения:</strong> Если адрес назначения сообщения не может быть разрешен, DM сигнализирует об этом с помощью результата <code>kIndicationUnknownTargetAddress</code> и устанавливает <code>UdsMessagePtr</code> в <code>nullptr</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=100">AUTOSAR_AP_SWS_Diagnostics с. 100</a>). Выделение объекта сообщения не выполняется.</li>
<li><strong>Ограничение буфера:</strong> Емкость переданного объекта <code>UdsMessage</code> ограничена выделением памяти, заданным DM. Обработчик может выполнять запись в буфер не более чем до предела его емкости (<a class="spec-record-ref" data-req="SWS_DM_00388" href="../spec/record.html?id=SWS_DM_00388">[SWS_DM_00388]</a>).</li>
</ul>
