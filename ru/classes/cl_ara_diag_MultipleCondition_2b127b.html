Контекст

Класс ara::diag::MultipleCondition ([SWS_DM_01730]) предоставляет в модуле diag платформы AUTOSAR Adaptive Platform объединенный интерфейс для управления несколькими диагностическими условиями (Diagnostic Conditions). В то время как отдельные условия обычно отображаются через класс ara::diag::Condition, ara::diag::MultipleCondition обеспечивает управление и опрос нескольких условий через общий интерфейс порта (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»).

Функционально оба интерфейса обладают одинаковой семантикой и предлагают однотипные операции (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»). Существенное отличие заключается в том, что в ara::diag::MultipleCondition каждая операция принимает дополнительный идентификатор типа ConditionHandleType ([SWS_DM_01728], [SWS_DM_01729]).

К основным участникам взаимодействия класса относятся:

  • Adaptive Application: создает экземпляр класса и управляет состояниями назначенных условий с помощью SetCondition либо считывает их через GetCondition ([SWS_DM_01728], [SWS_DM_01729]).
  • Diagnostic Management (DM): выступает в качестве подсистемы платформы, обрабатывает изменения состояний и предоставляет информацию об условиях для диагностических процедур ([SWS_DM_01728]).
  • Моделирование манифеста: каждое определенное в системе DiagnosticCondition требует сопоставления через DiagnosticMultipleConditionPortMapping, чтобы задать возможность использования интерфейса множественных условий для этого условия (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»). Назначенный PortPrototype при этом обязательно должен быть типизирован с помощью DiagnosticMultipleConditionInterface ([SWS_DM_01727]).

Контекстная диаграмма: встраивание ara::diag::MultipleCondition и взаимодействие с приложением, моделированием и Diagnostic Management. Источники: [SWS_DM_01727], [SWS_DM_01730], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»

Жизненный цикл

Создание экземпляра выполняется через явный конструктор MultipleCondition(const ara::core::InstanceSpecifier &specifier) ([SWS_DM_01727]). При инстанцировании объект привязывается к PortPrototype, на который ссылается InstanceSpecifier. Конструктор специфицирован как безопасный относительно исключений (exception safe) и потокобезопасный (thread-safe) ([SWS_DM_01727]).

С точки зрения отношений владения и перемещаемости класс строго привязан к месту своего создания:

  • Конструктор копирования удален: MultipleCondition(MultipleCondition &) = delete ([SWS_DM_02072]).
  • Оператор присваивания копированием удален: operator=(MultipleCondition &) = delete ([SWS_DM_02073]).
  • Конструктор перемещения удален: MultipleCondition(MultipleCondition &&) noexcept = delete ([SWS_DM_02071]).
  • Оператор перемещающего присваивания удален: operator=(MultipleCondition &&) = delete ([SWS_DM_02074]).

Таким образом, экземпляры ara::diag::MultipleCondition не могут быть ни скопированы, ни перемещены (pinned object). На протяжении всего срока использования они должны оставаться по фиксированному адресу памяти.

Уничтожение выполняется через деструктор ~MultipleCondition() noexcept ([SWS_DM_01737]). Он является безопасным относительно исключений, однако явно объявлен как not thread-safe ([SWS_DM_01737]). Поэтому вызывающее приложение должно гарантировать, что во время процесса уничтожения параллельный доступ к объекту не происходит.

Для потокобезопасности выполняемых операций (GetCondition и SetCondition) действует условная синхронизация (conditional thread-safety): должны ли методы быть реализованы как потокобезопасные или непотокобезопасные, определяется с помощью ConcurrencyType ([SWS_DM_01728], [SWS_DM_01729]). Интерпретация: поскольку конструктор C++ в [SWS_DM_01727] не содержит аргумента ConcurrencyType, данное свойство в архитектуре ПО, вероятно, настраивается через модель портов и оценивается через InstanceSpecifier.

Путь использования

Типичный процесс использования ara::diag::MultipleCondition подразделяется на этапы инстанцирования, идентификации отдельного условия, а также выполнения операций записи и чтения:

  1. Инстанцирование и привязка к порту: приложение создает экземпляр MultipleCondition с указанием соответствующего InstanceSpecifier ([SWS_DM_01727]).
  2. Адресация условий через дескрипторы: отдельные условия адресуются через числовые значения типа ConditionHandleType ([SWS_DM_01735]). Если в модели не задан DiagnosticMultipleConditionPortMapping.overrideId, Diagnostic Manager присваивает дескрипторы в алфавитном порядке короткого имени DiagnosticCondition, начиная с 0x010000 (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»).
  3. Установка состояния (SetCondition): приложение синхронно обновляет статус условия через SetCondition(conditionHandle, condition) ([SWS_DM_01729]). Вызов возвращает ara::core::Result<void>, который информирует об успехе или неудаче.
  4. Запрос состояния (GetCondition): для считывания текущего статуса приложение вызывает GetCondition(conditionHandle) ([SWS_DM_01728]). Вызов возвращает ara::core::Future<ConditionType>. Затем приложение может асинхронно разрешить и обработать результат.

Диаграмма последовательности: типичный порядок вызовов для управления условиями и их опроса с помощью ara::diag::MultipleCondition. Источники: [SWS_DM_01727], [SWS_DM_01728], [SWS_DM_01729], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»

Сценарии ошибок

Случаи ошибок при работе с ara::diag::MultipleCondition делятся на нарушения конфигурации и моделирования во время инстанцирования, а также ошибки времени выполнения при вызовах методов:

  • Ошибки инициализации (Violations) ([SWS_DM_01727]):
    • InstanceSpecifierMappingIntegrityViolation: InstanceSpecifier не может быть разрешен в контексте модели Executable или указывает на элемент модели, который не является PortPrototype.
    • PortInterfaceMappingViolation: указанный по ссылке PortPrototype не типизирован с соблюдением соответствия типов через DiagnosticMultipleConditionInterface.
    • ProcessMappingViolation: подходящая InstanceRef существует в модели, однако отсутствует подходящий смоделированный процесс для текущего процесса времени выполнения.
    • InstanceSpecifierAlreadyInUseViolation: конструктор был вызван с InstanceSpecifier, который в рамках текущего процесса уже занят другим экземпляром.
  • Ошибки времени выполнения при SetCondition ([SWS_DM_01729]):
    • DiagErrc::kInvalidArgument: сигнализирует о недопустимых аргументах (семантика отката, например при kPreFailed с внутренним устранением дребезга).
  • Ошибки времени выполнения при GetCondition ([SWS_DM_01728]):
    • DiagErrc::kInvalidArgument: указанное conditionHandle недействительно (семантика отката).
    • DiagErrc::kServiceNotAvailable: вызов не может быть выполнен, поскольку базовая функциональность Diagnostic Management в настоящее время недоступна (семантика отката).

Данное руководство по классу основано на спецификации AUTOSAR Adaptive Platform R25-11 (модуль diag) и обобщает требования к ara::diag::MultipleCondition.

<h4>Контекст</h4>
<p>Класс <code>ara::diag::MultipleCondition</code> (<a class="spec-record-ref" data-req="SWS_DM_01730" href="../spec/record.html?id=SWS_DM_01730">[SWS_DM_01730]</a>) предоставляет в модуле <em>diag</em> платформы AUTOSAR Adaptive Platform объединенный интерфейс для управления несколькими диагностическими условиями (Diagnostic Conditions). В то время как отдельные условия обычно отображаются через класс <code>ara::diag::Condition</code>, <code>ara::diag::MultipleCondition</code> обеспечивает управление и опрос нескольких условий через общий интерфейс порта (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>).</p>
<p>Функционально оба интерфейса обладают одинаковой семантикой и предлагают однотипные операции (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>). Существенное отличие заключается в том, что в <code>ara::diag::MultipleCondition</code> каждая операция принимает дополнительный идентификатор типа <code>ConditionHandleType</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>).</p>
<p>К основным участникам взаимодействия класса относятся:</p>
<ul>
<li><strong>Adaptive Application</strong>: создает экземпляр класса и управляет состояниями назначенных условий с помощью <code>SetCondition</code> либо считывает их через <code>GetCondition</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>).</li>
<li><strong>Diagnostic Management (DM)</strong>: выступает в качестве подсистемы платформы, обрабатывает изменения состояний и предоставляет информацию об условиях для диагностических процедур (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>).</li>
<li><strong>Моделирование манифеста</strong>: каждое определенное в системе <code>DiagnosticCondition</code> требует сопоставления через <code>DiagnosticMultipleConditionPortMapping</code>, чтобы задать возможность использования интерфейса множественных условий для этого условия (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>). Назначенный <code>PortPrototype</code> при этом обязательно должен быть типизирован с помощью <code>DiagnosticMultipleConditionInterface</code> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</li>
</ul>

<h4>Жизненный цикл</h4>
<p>Создание экземпляра выполняется через явный конструктор <code>MultipleCondition(const ara::core::InstanceSpecifier &amp;specifier)</code> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>). При инстанцировании объект привязывается к <code>PortPrototype</code>, на который ссылается <code>InstanceSpecifier</code>. Конструктор специфицирован как безопасный относительно исключений (<em>exception safe</em>) и потокобезопасный (<em>thread-safe</em>) (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</p>
<p>С точки зрения отношений владения и перемещаемости класс строго привязан к месту своего создания:</p>
<ul>
<li>Конструктор копирования удален: <code>MultipleCondition(MultipleCondition &amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02072" href="../spec/record.html?id=SWS_DM_02072">[SWS_DM_02072]</a>).</li>
<li>Оператор присваивания копированием удален: <code>operator=(MultipleCondition &amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02073" href="../spec/record.html?id=SWS_DM_02073">[SWS_DM_02073]</a>).</li>
<li>Конструктор перемещения удален: <code>MultipleCondition(MultipleCondition &amp;&amp;) noexcept = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02071" href="../spec/record.html?id=SWS_DM_02071">[SWS_DM_02071]</a>).</li>
<li>Оператор перемещающего присваивания удален: <code>operator=(MultipleCondition &amp;&amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02074" href="../spec/record.html?id=SWS_DM_02074">[SWS_DM_02074]</a>).</li>
</ul>
<p>Таким образом, экземпляры <code>ara::diag::MultipleCondition</code> не могут быть ни скопированы, ни перемещены (<em>pinned object</em>). На протяжении всего срока использования они должны оставаться по фиксированному адресу памяти.</p>
<p>Уничтожение выполняется через деструктор <code>~MultipleCondition() noexcept</code> (<a class="spec-record-ref" data-req="SWS_DM_01737" href="../spec/record.html?id=SWS_DM_01737">[SWS_DM_01737]</a>). Он является безопасным относительно исключений, однако явно объявлен как <em>not thread-safe</em> (<a class="spec-record-ref" data-req="SWS_DM_01737" href="../spec/record.html?id=SWS_DM_01737">[SWS_DM_01737]</a>). Поэтому вызывающее приложение должно гарантировать, что во время процесса уничтожения параллельный доступ к объекту не происходит.</p>
<p>Для потокобезопасности выполняемых операций (<code>GetCondition</code> и <code>SetCondition</code>) действует условная синхронизация (<em>conditional thread-safety</em>): должны ли методы быть реализованы как потокобезопасные или непотокобезопасные, определяется с помощью <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>). Интерпретация: поскольку конструктор C++ в <a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a> не содержит аргумента <code>ConcurrencyType</code>, данное свойство в архитектуре ПО, вероятно, настраивается через модель портов и оценивается через <code>InstanceSpecifier</code>.</p>

<h4>Путь использования</h4>
<p>Типичный процесс использования <code>ara::diag::MultipleCondition</code> подразделяется на этапы инстанцирования, идентификации отдельного условия, а также выполнения операций записи и чтения:</p>
<ol>
<li><strong>Инстанцирование и привязка к порту</strong>: приложение создает экземпляр <code>MultipleCondition</code> с указанием соответствующего <code>InstanceSpecifier</code> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</li>
<li><strong>Адресация условий через дескрипторы</strong>: отдельные условия адресуются через числовые значения типа <code>ConditionHandleType</code> (<a class="spec-record-ref" data-req="SWS_DM_01735" href="../spec/record.html?id=SWS_DM_01735">[SWS_DM_01735]</a>). Если в модели не задан <code>DiagnosticMultipleConditionPortMapping.overrideId</code>, Diagnostic Manager присваивает дескрипторы в алфавитном порядке короткого имени <code>DiagnosticCondition</code>, начиная с <code>0x010000</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>).</li>
<li><strong>Установка состояния (SetCondition)</strong>: приложение синхронно обновляет статус условия через <code>SetCondition(conditionHandle, condition)</code> (<a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>). Вызов возвращает <code>ara::core::Result&lt;void&gt;</code>, который информирует об успехе или неудаче.</li>
<li><strong>Запрос состояния (GetCondition)</strong>: для считывания текущего статуса приложение вызывает <code>GetCondition(conditionHandle)</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>). Вызов возвращает <code>ara::core::Future&lt;ConditionType&gt;</code>. Затем приложение может асинхронно разрешить и обработать результат.</li>
</ol>

<h4>Сценарии ошибок</h4>
<p>Случаи ошибок при работе с <code>ara::diag::MultipleCondition</code> делятся на нарушения конфигурации и моделирования во время инстанцирования, а также ошибки времени выполнения при вызовах методов:</p>
<ul>
<li><strong>Ошибки инициализации (Violations)</strong> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>):
<ul>
<li><code>InstanceSpecifierMappingIntegrityViolation</code>: <code>InstanceSpecifier</code> не может быть разрешен в контексте модели Executable или указывает на элемент модели, который не является <code>PortPrototype</code>.</li>
<li><code>PortInterfaceMappingViolation</code>: указанный по ссылке <code>PortPrototype</code> не типизирован с соблюдением соответствия типов через <code>DiagnosticMultipleConditionInterface</code>.</li>
<li><code>ProcessMappingViolation</code>: подходящая <code>InstanceRef</code> существует в модели, однако отсутствует подходящий смоделированный процесс для текущего процесса времени выполнения.</li>
<li><code>InstanceSpecifierAlreadyInUseViolation</code>: конструктор был вызван с <code>InstanceSpecifier</code>, который в рамках текущего процесса уже занят другим экземпляром.</li>
</ul>
</li>
<li><strong>Ошибки времени выполнения при SetCondition</strong> (<a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>):
<ul>
<li><code>DiagErrc::kInvalidArgument</code>: сигнализирует о недопустимых аргументах (семантика отката, например при <code>kPreFailed</code> с внутренним устранением дребезга).</li>
</ul>
</li>
<li><strong>Ошибки времени выполнения при GetCondition</strong> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>):
<ul>
<li><code>DiagErrc::kInvalidArgument</code>: указанное <code>conditionHandle</code> недействительно (семантика отката).</li>
<li><code>DiagErrc::kServiceNotAvailable</code>: вызов не может быть выполнен, поскольку базовая функциональность Diagnostic Management в настоящее время недоступна (семантика отката).</li>
</ul>
</li>
</ul>
