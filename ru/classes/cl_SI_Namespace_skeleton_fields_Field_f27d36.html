Позволяет скелетону сервиса (service skeleton) предоставлять, обновлять и типизированно обрабатывать запросы к полям.

Класс <SI-Namespace>::skeleton::fields::<Field> предоставляет на стороне сервера поле ServiceInterface и объединяет функции геттера, сеттера и уведомления для предоставляемого сервиса. Приложение-провайдер регистрирует асинхронные обработчики ([SWS_CM_00114], [SWS_CM_00116]) для входящих обращений на чтение и запись и активно рассылает изменения значений подписанным клиентам через метод Update ([SWS_CM_00119]). При этом передаваемые обработчики обязательно должны быть валидными, тогда как вызовы отправки должны соблюдать сконфигурированное минимальное время отправки, чтобы избежать таких ошибок, как kMinimumSendIntervalViolationError.

Контекст

Шаблонный класс <SI-Namespace>::skeleton::fields::<Field> инкапсулирует серверное представление смоделированного в ServiceInterface поля в рамках Adaptive Communication Management. Для каждого поля, определенного в интерфейсе сервиса, промежуточное ПО генерирует соответствующий экземпляр класса в пространстве имен skeleton::fields с использованием пути к заголовку #include "<SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h". Поле сочетает в себе функциональные особенности передачи данных и вызовов методов, опционально располагая геттером, сеттером и функцией уведомления. Соответствующий тип данных значения поля предоставляется через псевдоним типа FieldType ([SWS_CM_11402]). К центральным участникам взаимодействия относятся предоставляющее приложение-провайдер, экземпляр поля скелетона в качестве посредника, подписанные потребители сервиса (прокси), а также опциональные контексты выполнения в форме исполнителя (executor) ([SWS_CM_11360], [SWS_CM_11362]).

Контекстная диаграмма: участники взаимодействия класса скелетона Field при запросах и уведомлениях. Источники: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360].

Жизненный цикл

Время жизни экземпляра поля тесно связано с вышестоящим экземпляром скелетона сервиса. Интерпретация: экземпляр Field, вероятно, инстанцируется как объект-член соответствующего класса скелетона и полностью разделяет его жизненный цикл. Доступность отдельных методов интерфейса напрямую зависит от определения в проекте программного обеспечения: метод RegisterGetHandler существует только в том случае, если поле было сконфигурировано с Field.hasGetter == TRUE ([SWS_CM_00114]), тогда как RegisterSetHandler требует наличия сеттера через Field.hasSetter == TRUE ([SWS_CM_00116]). Для защиты коммуникации от сквозных транспортных ошибок приложение может зарегистрировать специальный обработчик через SetTransportFaultConditionHandler ([SWS_CM_00096]) и при необходимости удалить его с помощью UnsetTransportFaultConditionHandler ([SWS_CM_00098]). С точки зрения параллелизма перегрузки с параметром шаблона ExecutorT (такие как ara::core::Executor) предоставляют возможность перенести выполнение функций обратного вызова в определенный асинхронный контекст выполнения ([SWS_CM_11360], [SWS_CM_11362], [SWS_CM_00097], AUTOSAR_AP_EXP_ARAComAPI с. 11).

Путь использования

Штатный рабочий процесс подразделяется на конфигурацию функций обратного вызова, обработку запросов, а также активную отправку обновлений данных:

Интерпретация: регистрацию обработчиков целесообразно выполнять до предоставления сервиса, чтобы иметь возможность бесперебойно обслуживать входящие запросы. При наличии геттера приложение привязывает функцию обратного вызова через RegisterGetHandler, которая возвращает ara::core::Future<FieldType> ([SWS_CM_00114]). Для модифицирующих обращений оно регистрирует через RegisterSetHandler обработчик, который принимает новое значение, обрабатывает его и также асинхронно предоставляет результирующее состояние через future ([SWS_CM_00116]). Если поставщик сервиса хочет самостоятельно обновить значение поля, он вызывает метод Update с новым значением ([SWS_CM_00119], AUTOSAR_AP_EXP_ARAComAPI с. 11). В результате внутреннее состояние поля устанавливается заново. Если поле было смоделировано с функцией уведомления (Field.hasNotifier == TRUE), Update инициирует немедленную передачу измененного значения данных всем зарегистрированным подписчикам ([SWS_CM_00119], [SWS_CM_00120], [SWS_CM_00162]).

Диаграмма последовательности: типичный процесс регистрации обработчика, обработки запроса и обновления данных. Источники: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119].

Сценарии ошибок

Условия ошибок проявляются либо как нарушения контрактов программирования при регистрации, либо как ошибки передачи во время выполнения. Все методы регистрации обработчиков — RegisterGetHandler, RegisterSetHandler и SetTransportFaultConditionHandler — специфицированы как noexcept и обладают гарантией безопасности исключений exception safe ([SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00096]). В качестве предварительного условия требуется, чтобы переданный вызываемый объект (callable) существовал и не был равен null; несоблюдение этого требования приводит к возбуждению InvalidHandlerViolation ([SWS_CM_00114], [SWS_CM_11360], [SWS_CM_00116], [SWS_CM_11362], [SWS_CM_00096], [SWS_CM_00097]).

При активном обновлении через Update обратная связь об ошибках осуществляется через возвращаемый тип ara::core::Result<void> ([SWS_CM_00119]). При возникновении ошибки объект Result возвращает код ошибки из ara::com::ComErrc. В частности, отправка через более короткие интервалы, чем определено атрибутом развертывания ServiceInterfaceDeploymentElement.minimumSendInterval, приводит к возврату ошибки ComErrc::kMinimumSendIntervalViolationError ([SWS_CM_00119]).

Данное руководство основано на спецификации AUTOSAR Adaptive Platform Release R25-11 и было создано автоматически.

Использование

Метод RegisterGetHandler вызывается на стороне сервера для объекта поля скелетона ([SWS_CM_00114]). Он существует в сгенерированном коде исключительно в том случае, если в описании интерфейса для соответствующего поля был сконфигурирован геттер (Field.hasGetter == TRUE) (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Передаётся обратный вызов handler типа std::function<ara::core::Future<FieldType>()>, который вызывается реализацией связывания при входящем запросе Get() от прокси.

Регистрация такого обработчика полностью опциональна (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Обычно сервисной реализации не требуется обработчик геттера, так как Communication Management кэширует значение, заданное последним через Update(), и самостоятельно отвечает на запросы прокси. Обработчик имеет смысл прежде всего тогда, когда вычисление значения поля требует много времени или вычислительных ресурсов и поэтому должно производиться асинхронно через паттерн Promise/Future только при фактической необходимости.

Обработка ошибок и граничные условия

Функция не имеет возвращаемого значения, объявлена как noexcept и является исключение-безопасной (exception safe) ([SWS_CM_00114]). Если переданный вызываемый объект не существует или равен null, возникает ошибка InvalidHandlerViolation ([SWS_CM_00114]).

Взаимодействие

В отличие от RegisterSetHandler, вызов которого обязателен при наличии сеттера (EXP ARAComAPI §5.4.8.2 «Registering Setters»), RegisterGetHandler остаётся сугубо опциональным. Если обработчик должен обрабатываться асинхронно в определённом контексте выполнения, дополнительно доступна перегруженная шаблонная функция с ExecutorT ([SWS_CM_11360]).

      Использование
      

      Метод RegisterGetHandler в пространстве имён <SI-Namespace>::skeleton::fields::<Field> регистрирует обратный вызов на стороне приложения (handler), который вызывается коммуникационной привязкой при входящем вызове Get() от прокси ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). В отличие от базовой перегрузки без параметров [SWS_CM_00114], метод принимает контекст выполнения executor типа ExecutorT, в котором выполнение обратного вызова происходит асинхронно ([SWS_CM_11360]). В качестве исполнителя может использоваться стандартизированный ara::core::Executor или определяемый пользователем тип с таким же интерфейсом ([SWS_CM_11360]).
      

      Зарегистрированный обработчик возвращает ara::core::Future<FieldType>, благодаря чему вычисление значения поля отвязывается через паттерн Promise/Future ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). Регистрация является полностью опциональной: если обработчик не зарегистрирован, Communication Management автономно отвечает на запросы последним значением, установленным через Update() (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Обработчик-геттер в первую очередь подходит для вычисления ресурсоёмких или требующих много времени значений полей по требованию (EXP ARAComAPI §5.4.8.1 «Registering Getters»).
      

      Ограничения и обработка ошибок
      

      Метод присутствует в скелетоне исключительно в том случае, если в IDL для поля был сконфигурирован геттер (Field.hasGetter == TRUE, [SWS_CM_00114], EXP ARAComAPI §5.4.8.1 «Registering Getters»). RegisterGetHandler объявлен как noexcept; однако если передаётся недопустимый или пустой вызываемый объект (Callable), возникает InvalidHandlerViolation ([SWS_CM_11360]). Интерпретация: переданный исполнитель (Executor), по всей видимости, должен оставаться действительным на протяжении всего времени использования обработчика, поскольку входящие запросы направляются асинхронно в его контекст.
