Позволяет клиентским приложениям подписываться на сервисные события и принимать типизированные новые выборки данных.

Интерфейсный класс <SI-Namespace>::proxy::events::<Event> позволяет клиентским приложениям в AUTOSAR Adaptive Platform принимать сервисные события на стороне потребителя через модуль com. Типичная последовательность включает запрос подписки через Subscribe [SWS_CM_00141], реактивное оповещение через зарегистрированные обработчики, а также синхронную выборку данных с помощью GetNewSamples [SWS_CM_00701]. При этом нельзя одновременно удерживать больше указателей на выборки, чем было зарезервировано при подписке, а перед отменой подписки через Unsubscribe все ссылки должны быть освобождены.

Контекст

C++-класс <SI-Namespace>::proxy::events::<Event> представляет собой интерфейс на стороне потребителя для сервисного события в модуле com платформы AUTOSAR Adaptive Platform (релиз R25-11). В рамках сервисно-ориентированного шаблона связи этот сгенерированный класс выступает в качестве локального представителя события, предоставляемого скелетоном сервера. Клиентские приложения используют экземпляры этого класса для подписки на данные событий, приема входящих выборок (samples) из коммуникационной сети и управления их жизненным циклом на стороне потребителя AUTOSAR_AP_EXP_ARAComAPI с. 10.

Основными партнерами по взаимодействию для данного класса являются:

  • Приложение (Subscriber): Инициирует регистрацию подписки на событие через Subscribe [SWS_CM_00141], сохраняет процедуры обратного вызова для приема данных и изменения состояния, а также запрашивает новые выборки через GetNewSamples [SWS_CM_00701].
  • Communication Management: Координирует передачу данных событий через нижележащее промежуточное ПО (middleware), управляет состоянием сети и выполняет зарегистрированные обработчики оповещений при поступлении новых событий или изменении состояния [SWS_CM_00181], [SWS_CM_00333].
  • Контекст выполнения (Executor): При использовании перегруженных методов регистрации асинхронные обработчики выполняются внутри явно переданного контекста ExecutorT [SWS_CM_11354], [SWS_CM_11356], [SWS_CM_00100].

Контекстная диаграмма: отношения взаимодействия между приложением, прокси-событием и Communication Management. Источники: [SWS_CM_00141], [SWS_CM_00181], AUTOSAR_AP_EXP_ARAComAPI с. 10

Жизненный цикл

Инстанцирование и уничтожение <SI-Namespace>::proxy::events::<Event> в качестве члена вышестоящего прокси-класса, по всей вероятности, жестко привязаны к сроку службы сервисного прокси. После создания событие изначально находится в неподписанном состоянии. Текущий статус подписки можно в любое время запросить через GetSubscriptionState, которая возвращает состояние как ara::com::SubscriptionState [SWS_CM_00316].

Переход в активное состояние подписки инициируется через Subscribe, при этом максимальное количество одновременно доступных слотов кэша задается через maxSampleCount [SWS_CM_00141]. Если в момент вызова событие уже находится в состояниях kSubscribed или kSubscriptionPending и переданное значение совпадает с текущим, вызов не производит действия [SWS_CM_00141]. Об изменениях состояния подписки Communication Management сообщает через обработчик, который регистрируется с помощью SetSubscriptionStateChangeHandler [SWS_CM_00333] или с контекстом выполнения через SetSubscriptionStateChangeHandler [SWS_CM_11354]. Эту регистрацию можно отменить через UnsetSubscriptionStateChangeHandler [SWS_CM_00334] AUTOSAR_AP_EXP_ARAComAPI с. 10.

Кроме того, класс управляет состоянием сквозной защиты (E2E). Через GetE2EStateMachineState определяется состояние ara::com::e2e::SMState конечного автомата E2E, зафиксированное при последнем внутреннем вызове E2E_Check() во время GetNewSamples() [SWS_CM_11554]. Некорректные условия передачи могут отслеживаться обработчиками, которые устанавливаются через SetTransportFaultConditionHandler [SWS_CM_00099] или [SWS_CM_00100] и удаляются через UnsetTransportFaultConditionHandler [SWS_CM_00105].

Прекращение подписки выполняется через Unsubscribe [SWS_CM_00151] AUTOSAR_AP_EXP_ARAComAPI с. 10. Если событие в этот момент не подписано, метод возвращает управление без выполнения каких-либо действий [SWS_CM_00151]. Все функции-члены объявлены как noexcept и обеспечивают полную безопасность относительно исключений.

Путь использования

Типичный процесс использования прокси-события подразделяется на следующие последовательные фазы:

  1. Инициация подписки: Приложение вызывает Subscribe(maxSampleCount) [SWS_CM_00141], чтобы зарезервировать размер буфера для входящих выборок.
  2. Настройка оповещения: Через SetReceiveHandler [SWS_CM_00181] (или с контекстом выполнения через [SWS_CM_11356]) регистрируется обратный вызов без параметров, вызываемый Communication Management при поступлении новых событий.
  3. Выборка и обработка данных: В функции обратного вызова приложение вызывает GetNewSamples [SWS_CM_00701]. Переданный вызываемый объект (callable) f с сигнатурой void(ara::com::SamplePtr<SampleType const>) последовательно обрабатывает каждую выборку. При этом SampleType соответствует специализированному типу полезных данных события [SWS_CM_11401]. Возвращаемое значение предоставляет в виде ara::core::Result<std::size_t> точное количество выборок, переданных в f [SWS_CM_00701].
  4. Мониторинг кэша: С помощью GetFreeSampleCount [SWS_CM_00705] приложение может проверить количество неиспользуемых мест в локальном кэше, чтобы заблаговременно обнаружить дефицит буфера.
  5. Разыменование и отмена регистрации: После завершения обработки данных триггер приема отключается с помощью UnsetReceiveHandler [SWS_CM_00183], а подписка завершается через Unsubscribe [SWS_CM_00151].

Диаграмма последовательности: типичная последовательность оформления подписки, оповещения, обработки выборок и отмены подписки. Источники: [SWS_CM_00141], [SWS_CM_00181], [SWS_CM_00701], [SWS_CM_00151]

Сценарии ошибок

При использовании класса могут возникать специфические коды ошибок и нарушения времени выполнения, требующие защитных проверок:

  • Ошибка конфигурации при повторной подписке: Если Subscribe вызывается, когда событие уже подписано, и новое maxSampleCount отличается от текущего значения, вызов завершается с кодом ошибки ComErrc::kMaxSampleCountNotRealizable [SWS_CM_00141]. При отсутствии полномочий система отклоняет выполнение с InsufficientPermissionsViolation [SWS_CM_00141].
  • Превышение границ буфера: Если приложение удерживает больше экземпляров ara::com::SamplePtr, чем было гарантировано в предыдущем вызове Subscribe, GetNewSamples возвращает код ошибки ComErrc::kMaxSamplesExceeded; в этом случае выборки данных могли быть отброшены [SWS_CM_00701].
  • Передача недопустимого обработчика: Если в SetReceiveHandler, SetSubscriptionStateChangeHandler или SetTransportFaultConditionHandler передается недопустимый или пустой (null) вызываемый объект, генерируется InvalidHandlerViolation ([SWS_CM_00181], [SWS_CM_11356], [SWS_CM_00333], [SWS_CM_11354], [SWS_CM_00099], [SWS_CM_00100]).
  • Оставшиеся выборки при отмене подписки: Если перед вызовом Unsubscribe не были освобождены все удерживаемые ara::com::SamplePtr, это приводит к DanglingSamplesViolation [SWS_CM_00151].

Данное руководство было сгенерировано ИИ на основе спецификации AUTOSAR R25-11.
