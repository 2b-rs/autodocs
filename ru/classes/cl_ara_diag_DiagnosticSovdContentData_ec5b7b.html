Контекст

Структура ara::diag::DiagnosticSovdContentData является частью AUTOSAR Adaptive Platform в модуле diag и предоставляется через заголовочный файл ara/diag/diagnostic_sovd_content_data.h ([SWS_DM_02385], AUTOSAR_AP_SWS_Diagnostics §8.59.1 «Struct: DiagnosticSovdContentData»). Она служит стандартизированным контейнером передачи данных для содержимого протокола ASAM Service-Oriented Vehicle Diagnostics (SOVD) в рамках Diagnostic Management (DM).

С функциональной точки зрения структура данных инкапсулирует коллекцию элементов содержимого SOVD через открытый член elements типа ara::core::Vector<DiagnosticSovdContentElementData> ([SWS_DM_02386], AUTOSAR_AP_SWS_Diagnostics §8.59.1.1.1 «elements»). Эта структура используется на интерфейсе между тремя главными участниками: внешним SOVD-клиентом, внутриавтомобильным демоном Diagnostic Management (DM), а также конкретными поставщиками диагностических сервисов приложения Adaptive (например, экземплярами ara::diag::GenericDiagnosticSovdOperation или SovdOperationExecution) ([SWS_DM_02174], [SWS_DM_02180], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»).

Контекстная диаграмма: интеграция DiagnosticSovdContentData в обмен данными между внешним SOVD-клиентом, Diagnostic Management и логикой приложения. Источники: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02385].

Жизненный цикл

Являясь чистой структурой данных (struct), ara::diag::DiagnosticSovdContentData подчиняется обычной семантике значений C++ ([SWS_DM_02385]). Она не имеет собственного менеджера жизненного цикла или хранилища состояния, а создается и передается по мере необходимости.

Как правило, экземпляр создается исполняющим диагностическим приложением по завершении операции SOVD или при предоставлении данных для запроса на чтение (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»). Приложение заполняет вектор elements соответствующими записями DiagnosticSovdContentElementData ([SWS_DM_02386]). Затем структура передается в DM в качестве возвращаемого значения или внутри контейнеров ответов (например, возвращаемых значений StartSynchronousExecution или GetStatusResponse.Parameters) ([SWS_DM_02176], [SWS_DM_02181]).

Diagnostic Management принимает владение или считывает содержащиеся значения для заполнения атрибута parameters исходящего тела SOVD-ответа в соответствии с ASAM SOVD ([SWS_DM_02176], [SWS_DM_02181]). После завершения сериализации или генерации ответа экземпляр уничтожается согласно стандартным правилам области видимости C++. Поскольку речь идет о структуре данных, внутренняя синхронизация потоков отсутствует; доступ через границы потоков требует семантики перемещения (move-семантики) или внешней координации со стороны вызывающего кода.

Путь использования

Основной сценарий использования ara::diag::DiagnosticSovdContentData заключается в выполнении операций SOVD и передаче отчетов об их статусе, а также в выделенных запросах на чтение SOVD:

  1. Получение запроса: внешний клиент отправляет метод SOVD «Start Execution of an Operation» на Diagnostic Server ([SWS_DM_01396], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»).
  2. Вызов операции приложения: после успешной валидации Diagnostic Management перенаправляет вызов через ara::diag::GenericDiagnosticSovdOperation::StartExecution в приложение ([SWS_DM_02174]).
  3. Заполнение структуры данных: логика приложения обрабатывает операцию и генерирует результат в виде экземпляра DiagnosticSovdContentData, чей вектор elements принимает выходные данные ([SWS_DM_02386]).
  4. Подготовка ответа компонентом DM: DM принимает результат, извлекает из него значения для атрибута SOVD parameters и отправляет клиенту соответствующее спецификации тело ответа SOVD ([SWS_DM_02176]).

Аналогично структура используется при запросах статуса («Read the Status of an operation»): при успешном вызове SovdOperationExecution::GetStatus значения для parameters в теле ответа выводятся из DiagnosticSovdContentData, предоставленной в GetStatusResponse.Parameters ([SWS_DM_02180], [SWS_DM_02181], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operation Read the Status of an operation»). Кроме того, структура возвращается в качестве результата асинхронных интерфейсов, таких как Read(...), через ara::core::Future<DiagnosticSovdContentData> (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»).

Диаграмма последовательности: взаимодействие при синхронном выполнении операции SOVD и возврате параметров через DiagnosticSovdContentData. Источники: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176] [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02386].

Сценарии ошибок

При использовании и передаче ara::diag::DiagnosticSovdContentData имеют значение несколько предварительных условий и режимов сбоев:

  • Сбой проверки безопасности: как при запуске операции ([SWS_DM_02174]), так и при запросе статуса операции ([SWS_DM_02180]) обязательным предварительным условием является успешная проверка proximity_challenge. В случае сбоя этой проверки операция отклоняется; функции приложения не вызываются, а предоставление или анализ DiagnosticSovdContentData не происходят.
  • Сбой запроса статуса: если SovdOperationExecution::GetStatus не может быть успешно выполнен, формирование стандартного тела ответа SOVD отменяется, а извлечение parameters из DiagnosticSovdContentData не производится ([SWS_DM_02181]).
  • Асинхронная отмена при операциях чтения: если DiagnosticSovdContentData запрашивается в рамках Read(...), система передает ara::diag::CancellationHandler (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»). Если он запрашивает отмену, создание и заполнение DiagnosticSovdContentData может или должно быть завершено досрочно.

Настоящее руководство основано на спецификации AUTOSAR Adaptive R25-11. Все нормативные требования взяты из модуля diag.
