Служит абстрактным базовым классом для плагинов транспорта UDS, предназначенных для передачи и пересылки диагностических сообщений.

Абстрактный класс служит плагинам транспорта UDS базовым интерфейсом для стандартизированного подключения к адаптивному управлению диагностикой (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»). Производная реализация пересылает принятые диагностические сообщения менеджеру протокола и передает сгенерированные ответные сообщения диагностическому тестеру по сетевым каналам. Жизненный цикл подчиняется строгой последовательности из создания, отдельной инициализации, асинхронного запуска и упорядоченной остановки ([SWS_DM_00329]). После инстанцирования эксплуатационные вызовы методов не являются потокобезопасными (not thread-safe) и требуют скоординированного управления со стороны ядра диагностики.

Контекст

Класс apext::diag::uds_transport::UdsTransportProtocolHandler представляет собой абстрактный базовый класс в модуле diag AUTOSAR Adaptive Platform. Он определяет стандартизированный интерфейс, через который проприетарные или специфичные для протокола плагины транспорта UDS подключаются к адаптивному управлению диагностикой (DM) (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00315]). Каждый конкретный транспортный протокол — например, для диагностики по автомобильным сетевым средам — реализует этот интерфейс в виде производного подкласса. DM, вероятно, монопольно владеет соответствующим экземпляром обработчика и управляет им на протяжении всего его эксплуатационного жизненного цикла. Взаимодействие между ядром диагностики и плагином осуществляется через ссылку transportprotocolManager типа UdsTransportProtocolMgr&, которая передается в конструкторе и сохраняется в защищенном виде ([SWS_DM_09015], [SWS_DM_09025]). Каждый обработчик идентифицируется числовым UdsTransportProtocolHandlerID, который можно запросить через GetHandlerID() ([SWS_DM_00325]).

Жизненный цикл

Жизненный цикл обработчика транспортного протокола UDS строго последовательно управляется со стороны DM ([SWS_DM_00329]). После инстанцирования через конструктор UdsTransportProtocolHandler ([SWS_DM_09015]) метод Initialize() отделяет фактическую инициализацию протокола от создания объекта ([SWS_DM_00319]). За исключением опционального запроса через GetPeriodicHandler(), DM не имеет права вызывать методы обработчика до успешного возврата из InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). После успешной инициализации вызов Start() переводит обработчик в активное состояние обработки ([SWS_DM_00322]). Чтобы минимизировать время запуска, Start() спроектирован как асинхронная операция; DM, вероятно, внутренне координирует параллельный запуск нескольких обработчиков. Если DM при завершении работы переходит в состояние ApplicationState.kTerminating, он дает обработчику указание на завершение через Stop() ([SWS_DM_00323], [SWS_DM_00333]). DM ожидает завершения, которое обработчик подтверждает вызовом UdsTransportProtocolMgr::HandlerStopped() ([SWS_DM_00340]). После возврата из Stop() плагину запрещен любой вызов методов менеджера, кроме HandlerStopped() ([SWS_DM_01741]). Освобождение ресурсов в конечном итоге происходит через виртуальный деструктор ([SWS_DM_09016]). В то время как конструктор потокобезопасен, методы рабочего интерфейса объявлены как непотокобезопасные.

Диаграмма состояний: фазы жизненного цикла и переходы между состояниями обработчика транспорта UDS. Источники: [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00329], [SWS_DM_01745], [SWS_DM_01746]

Путь использования

В штатном режиме диагностики обработчик обрабатывает входящие сообщения и передает ответы. Как только на сетевом интерфейсе присутствуют как минимум адрес источника, адрес назначения, тип адресации (физический или функциональный), общая длина сообщения, а для многобайтовых полезных данных — первые два байта (payloadInfo), реализация сообщает о запросе менеджеру через UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00342], AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer»). Каждый запрос привязан к уникальному каналу (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»). Для ответа DM передает диагностический ответ тому же обработчику и каналу с помощью Transmit(message, channelId) ([SWS_DM_00327], [SWS_DM_00348]). После физической передачи обработчик возвращает переданный объект сообщения менеджеру через UdsTransportProtocolMgr::TransmitConfirmation() ([SWS_DM_00327], [SWS_DM_00351]). Специализированный сценарий использования касается перезагрузок блока управления (ECU) (служба UDS 0x11) с положительным ответом после перезапуска: здесь DM перед перезагрузкой запрашивает через NotifyReestablishment(channelId) энергонезависимое сохранение информации о соединении обработчиком; после перезапуска и повторного Start() обработчик сообщает о восстановлении того же канала через ChannelReestablished() ([SWS_DM_00326], [SWS_DM_01744]).

Диаграмма последовательности: последовательность индикации UDS-сообщения и передачи ответа. Источники: [SWS_DM_00327], [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00351]

Сценарии ошибок

Если инициализация транспортного уровня завершается сбоем и Initialize() возвращает статус InitializationResult::kInitializeFailed, DM немедленно прерывает процесс запуска этого протокола и больше не вызывает никаких методов на данном экземпляре ([SWS_DM_01745], [SWS_DM_09017]). Если периодические передачи не поддерживаются транспортным протоколом, вызов GetPeriodicHandler() возвращает ara::core::Result с кодом ошибки kConfigurationMismatch ([SWS_DM_01068]). Если запрошенное восстановление канала для сброса ECU не может быть гарантировано, NotifyReestablishment() завершается сбоем и сигнализирует об этом возвращаемым значением false ([SWS_DM_00326]). Наконец, если операция отправки диагностического ответа на сетевом уровне завершается неудачно, обработчик должен уведомить об этом менеджера при подтверждении, установив аргумент result в TransmitConfirmation() в значение kTransmitFailed ([SWS_DM_00351]).

Настоящее руководство было автоматически сгенерировано на основе спецификации AUTOSAR R25-11.

NotifyReestablishment функция

Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().

          Чисто виртуальный метод Initialize служит для явной инициализации экземпляра apext::diag::uds_transport::UdsTransportProtocolHandler и формально отделяет этот процесс от конструирования объекта [SWS_DM_00319]. Он вызывается модулем Diagnostic Manager (DM) синхронно и без параметров, не генерирует исключений (noexcept) и возвращает InitializationResult [SWS_DM_00319] [SWS_DM_09017].
          

          Жизненный цикл и параллелизм
          

          Вызов встроен в управление жизненным циклом транспортного уровня UDS AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer». DM должен управлять фазами в строгом порядке: конструирование, вызов Initialize, запуск через Start и завершение через Stop [SWS_DM_00329]. Метод специфицирован как непотокобезопасный (not thread-safe) [SWS_DM_00319]; поэтому DM, вероятно, выполняет его в рамках синхронной фазы инициализации без параллельных обращений.
          

          Обработка ошибок и взаимодействие
          

          Метод сигнализирует о результате через перечислитель InitializationResult::kInitializeOk или InitializationResult::kInitializeFailed [SWS_DM_09017]. Дальнейшее поведение DM напрямую зависит от возвращаемого значения:
          

            

          • В случае успешного возврата со значением kInitializeOk DM разрешено вызывать последующие методы обработчика; до получения этого успешного возвращаемого значения, за исключением GetPeriodicHandler, никакой другой вызов метода не допускается [SWS_DM_01746].
            • 

          • Если обработчик возвращает kInitializeFailed, DM полностью прерывает процесс инициализации этого транспортного протокола и больше не вызывает никаких методов у затронутого экземпляра [SWS_DM_01745].

              функция NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
