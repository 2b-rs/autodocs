Контекст

Класс apext::diag::uds_transport::UdsTransportProtocolHandler является абстрактным базовым классом для специфических и проприетарных плагинов транспортного протокола UDS в Diagnostic Management (DM) платформы AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00315]). Он изолирует универсальное ядро диагностики от особенностей конкретных сетей передачи и транспортных уровней, таких как DoIP или протоколы на базе CAN.

Обработчик транспорта взаимодействует главным образом с тремя участниками:

  • Diagnostic Management Core: DM управляет всем жизненным циклом обработчика и через ссылку на менеджер apext::diag::uds_transport::UdsTransportProtocolMgr предоставляет сопряженную сторону для индикаций состояния и данных ([SWS_DM_09015], [SWS_DM_09025]).
  • Сетевой уровень и клиент диагностики: плагин осуществляет физический или логический обмен данными с внешним по отношению к автомобилю или встроенным диагностическим тестером ([SWS_DM_00326], [SWS_DM_00351]).
  • Периодический обработчик (опционально): если соответствующий транспортный протокол поддерживает периодические передачи, обработчик через GetPeriodicHandler() предоставляет ссылку на UdsTransportProtocolPeriodicHandler ([SWS_DM_01068]).

Жизненный цикл

Жизненный цикл реализации транспортного протокола строго управляется со стороны DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer», [SWS_DM_00329]). Создание выполняется через конструктор UdsTransportProtocolHandler(handlerId, transportProtocolMgr), в котором DM присваивает обработчику уникальный идентификатор типа UdsTransportProtocolHandlerID, а также ссылку на соответствующий UdsTransportProtocolMgr ([SWS_DM_09015], [SWS_DM_09025]). Назначенный ID можно запросить в любое время через GetHandlerID() ([SWS_DM_00325]). Конструктор заявлен как потокобезопасный ([SWS_DM_09015]).

Чтобы отделить ресурсоемкую инициализацию протокола от конструктора, DM затем вызывает Initialize() ([SWS_DM_00319], [SWS_DM_00329]). За исключением GetPeriodicHandler(), DM не должен вызывать никаких других методов обработчика до успешного возврата из InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). После успешной инициализации DM запускает протокол через Start() ([SWS_DM_00322]). Поскольку Start() выполняется асинхронно, DM может запускать несколько обработчиков параллельно, чтобы минимизировать время выхода на рабочий режим ([SWS_DM_00322]).

Когда приложение DM переходит в состояние ApplicationState.kTerminating, оно вызывает Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). DM ожидает, пока обработчик подтвердит остановку через UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). После возврата из Stop() плагин обработчика не должен вызывать никаких других методов менеджера — за единственным исключением подтверждения HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). Последующее уничтожение выполняется через виртуальный деструктор ([SWS_DM_09016]).

Диаграмма состояний: фазы жизненного цикла и условия переходов обработчика транспортного протокола UDS. Источники: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Путь использования

В процессе работы обработчик выполняет двунаправленный обмен сообщениями UDS:

  1. Прием сообщений (индикация): как только по каналу поступает новое сообщение UDS и становятся известны адрес источника, адрес назначения, тип адресации (физическая или функциональная), общая длина сообщения, а также первые байты полезных данных (при сообщениях размером более одного байта — не менее двух байтов), плагин вызывает UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 «Indication of UDS message reception», [SWS_DM_00342], [SWS_DM_00330]). При этом обработчик передает идентификатор канала в параметре globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»).
  2. Отправка сообщений (передача): DM отправляет соответствующий диагностический ответ UDS обратно через тот же обработчик и тот же канал (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer», [SWS_DM_00348]). Для этого он вызывает Transmit(message, channelId) ([SWS_DM_00327]). Сообщение передается обработчику как UdsMessageConstPtr наподобие std::unique_ptr.
  3. Квитирование отправки: как только сообщение отправлено по сети (или возникла ошибка), обработчик должен вернуть владение message в DM через UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). При этом результат передается как kTransmitOk или kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Еще одним специфическим сценарием использования является восстановление каналов после сброса блока управления (служба UDS 0x11 с положительным ответом после сброса): при этом перед перезапуском DM вызывает NotifyReestablishment(channelId) ([SWS_DM_00326]). Плагин сохраняет параметры соединения (например, IP-адреса и порты) в энергонезависимой памяти. После повторного запуска через Start() плагин распознает повторное подключение того же клиента диагностики и уведомляет DM через UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Диаграмма последовательности: прием сообщений UDS, передача ответа и последующее квитирование. Источники: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Сценарии ошибок

Интерфейс обрабатывает различные исключительные и ошибочные ситуации:

  • Неудачная инициализация: если Initialize() возвращает значение InitializationResult::kInitializeFailed ([SWS_DM_09017]), DM полностью прерывает процесс запуска этого транспортного протокола и больше не вызывает никаких методов для этого экземпляра ([SWS_DM_01745]).
  • Неподдерживаемые периодические передачи: если конкретный протокол не поддерживает периодические передачи, вызов GetPeriodicHandler() возвращает ara::core::Result с кодом ошибки kConfigurationMismatch ([SWS_DM_01068]).
  • Отказ в восстановлении канала: если плагин не может выполнить постоянное резервирование канала (например, из-за отсутствия энергонезависимой памяти или нестабильного сопоставления), NotifyReestablishment(channelId) возвращает значение false ([SWS_DM_00326]).
  • Ошибка передачи в сети: если сетевой уровень не смог отправить сообщение, запрошенное через Transmit(), обработчик должен передать результат kTransmitFailed в TransmitConfirmation ([SWS_DM_00351]). Невозврат буфера приводит к утечкам ресурсов в DM.
  • Нарушение последовательности после остановки: если плагин после возврата из Stop() вызывает в UdsTransportProtocolMgr любой метод, кроме HandlerStopped(), это является нарушением последовательности протокола ([SWS_DM_00323], [SWS_DM_01741]).

Настоящее руководство по классу основано на спецификации AUTOSAR Adaptive R25-11.

              функция NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
