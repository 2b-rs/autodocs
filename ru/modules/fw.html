Firewall как Functional Cluster: роль и границы системы

Functional Cluster Firewall (пространство имен ara::fw) предоставляет приложениям ровно один прикладной программный интерфейс. Это класс ara::fw::FirewallStateSwitchInterface с методом SwitchFirewallState [AP_SWS_Fw_82008]. Согласно описанию архитектуры, данный кластер основан на демоне. Он реализует интерфейс FirewallStateSwitchInterface со стереотипом «aapAPI,aapPortInterface», а Adaptive Application использует его через отношение «use» EXP SWArchitecture с. 126. Диаграмма прецедентов содержит два варианта использования. «Switch Firewall State» инициируется со стороны Adaptive Application. В «Report Security Event» участвует Intrusion Detection System Manager. В качестве еще одного актора выступает Operating System EXP SWArchitecture с. 197.

Архитектурный эскиз SWS четко разделяет зоны ответственности:

  • Machine Manifest предоставляет конфигурацию Firewall с ее правилами фильтрации.
  • FC Firewall конфигурирует с его помощью Firewall Engine.
  • OEM-приложение задает состояние Firewall.
  • События безопасности (Security Events, SEvs) передаются в IdsM SWS Firewall с. 16.

Такое же разделение показывает проект платформы EXP PlatformDesign с. 97. Таким образом, фактическая инспекция пакетов находится за пределами API. Сценарий смены состояния относит применение правил к Operating System и помечает его как «aapInformative» EXP SWArchitecture с. 232.

Контекстная диаграмма: FC Firewall выступает посредником между конфигурацией манифеста, задающим состояние приложением, исполняющим механизмом (Engine) или операционной системой и IdsM. Источники: SWS Firewall с. 16, EXP SWArchitecture с. 126, EXP SWArchitecture с. 232

Фильтрация по состоянию: состояния Firewall и правила фильтрации

Основой концепции является фильтрация по состоянию. Специфичные для OEM состояния Firewall отражают ситуации, в которых ожидается различный сетевой трафик, например движение, парковка или сеанс диагностики. Правила фильтрации сопоставляются с состоянием. Для инспекции и фильтрации Firewall использует только правила текущего активного состояния. Текущее состояние устанавливается приложением через API FC Firewall EXP PlatformDesign с. 92. В C++ это метод SwitchFirewallState(EnumT firewallState) [AP_SWS_Fw_82008].

Сами правила являются содержимым манифеста. Диаграмма требований Foundation показывает цепочки фильтрации на нескольких уровнях:

  • Ethernet с MAC-адресами и EtherType,
  • IPv4,
  • TCP с распознаванием состояния по флагам или ICMP,
  • SOME/IP с Service-ID, Method-ID и Client-ID RS Firewall с. 12.

На транспортном уровне манифест моделирует FirewallRule с атрибутами bucketSize и refillAmount. К этому добавляется TransportLayerRule с диапазонами портов и checksumVerification, которая специализируется в правила UDP и TCP TPS Manifest с. 687.

Если пакет не соответствует ни одному из определенных правил, применяется Default Action. Версия SWS R23-11 дополнительно описывает, как для заблокированного таким образом пакета определяется уровень протокола, на котором возник Mismatch. Определяющим является правило с наибольшим количеством последовательных совпадений, начиная с самого нижнего сетевого уровня. На первом несоответствующем уровне генерируется специфичное для данного уровня SEv SWS Firewall с. 31. Этот фрагмент взят из R23-11 и в полезной нагрузке не покрывается требованием R25-11. Поэтому его следует рассматривать как пояснение, а не как нормативное требование.

Диаграмма деятельности: проверяются только правила активного состояния Firewall. При отсутствии совпадения применяется Default Action, и заблокированный пакет приводит к возникновению специфичного для уровня SEv (представление согласно R23-11). Источники: EXP PlatformDesign с. 92, SWS Firewall с. 31

От InstanceSpecifier к смене состояния

Сначала приложение создает экземпляр FirewallStateSwitchInterface. Для этого служит явный конструктор, ожидающий ara::core::InstanceSpecifier. Он является noexcept и специфицирован как потокобезопасный (thread-safe) [AP_SWS_Fw_82002]. Интерпретация: InstanceSpecifier, вероятно, обозначает RPortPrototype приложения, типизированный в манифесте через FirewallStateSwitchInterface. Диаграмма манифеста устанавливает именно это отношение портов, но не называет сам спецификатор TPS Manifest с. 677.

Смену состояния инициирует SwitchFirewallState(EnumT firewallState). Метод является noexcept и возвращает ara::core::Future<void> [AP_SWS_Fw_82008]. Сценарий «Switch Firewall State» демонстрирует эту последовательность в три шага:

  1. Adaptive Application вызывает SwitchFirewallState() в FC Firewall.
  2. FC Firewall в цикле вызывает для каждого FirewallRule applyRule() в Operating System.
  3. После этого ответ возвращается приложению EXP SWArchitecture с. 232.

Представление того же сценария в R22-11 показывает аналогичную последовательность действий EXP SWArchitecture с. 158. Поскольку applyRule() помечен как «aapInformative», цикл описывает лишь общий принцип. Обязательный интерфейс операционной системы он не определяет EXP SWArchitecture с. 232.

Диаграмма последовательности: приложение конструирует экземпляр интерфейса и запрашивает смену состояния. FC Firewall применяет каждое правило, и результат возвращается в виде ara::core::Future<void>. Источники: [AP_SWS_Fw_82002], [AP_SWS_Fw_82008], EXP SWArchitecture с. 232

Сгенерированные типы состояний и привязка к манифесту

Допустимые состояния Firewall не образуют фиксированного типа платформы. Для каждого смоделированного интерфейса в пространстве имен ara::fw::states генерируется собственный enum class {<fwssi-sn>} : std::uint32_t. Он подключается через ara/fw/states/{<fwssi-sn>}.h, а список перечислителей берется из модели [AP_SWS_Fw_81001]. Для каждого смоделированного состояния Firewall создается перечислитель вида {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002]. Интерпретация: тип параметра EnumT из SwitchFirewallState, вероятно, представляет собой этот сгенерированный тип состояния, поскольку [AP_SWS_Fw_81001] явно определяет его как тип состояния для FirewallStateSwitchInterface [AP_SWS_Fw_82008].

В метамодели FirewallStateSwitchInterface представляет собой PortInterface. Он агрегирует через роль firewallStateMachine (0..*) элементы типа ModeDeclarationGroupPrototype TPS Manifest с. 263. Предположительно, режимы этой группы предоставляют перечислители из [AP_SWS_Fw_81002]. Однако источники явно не описывают это отображение.

На уровне машины AdaptiveFirewallModuleInstantiation собирает специфичные для машины настройки Firewall (TPS_MANI_03296, статус DRAFT). Метакласс AdaptiveFirewallToPortPrototypeMapping связывает это инстанцирование через ссылку firewall (0..1) с RPortPrototype приложения TPS Manifest с. 677. В примечании к этому метаклассу при этом говорится о «FirewallModeSwitchInterface». Диаграмма и API, напротив, последовательно используют FirewallStateSwitchInterface TPS Manifest с. 677.

Диаграмма кооперации: диаграмма показывает цепочку от инстанцирования Firewall через сопоставление и порт приложения до сгенерированного типа состояния. Ребра к InstanceSpecifier и к сгенерированному enum являются интерпретациями. Источники: TPS Manifest с. 263, TPS Manifest с. 677, [AP_SWS_Fw_81001], [AP_SWS_Fw_82002]

Жизненный цикл и параллелизм экземпляра интерфейса

Экземпляр FirewallStateSwitchInterface не является копируемым. Конструктор копирования и оператор присваивания с копированием удалены [AP_SWS_Fw_82004] [AP_SWS_Fw_82005]. Перемещение, напротив, разрешено, так как конструктор перемещения и оператор присваивания с перемещением — noexcept [AP_SWS_Fw_82006] [AP_SWS_Fw_82007]. Таким образом, экземпляр можно передать другому владельцу, но нельзя дублировать.

Потокобезопасность определена для каждой операции. В следующей таблице обобщены данные от [AP_SWS_Fw_82002] до [AP_SWS_Fw_82008]:

ОперацияТребованиеПотокобезопасность
Конструктор из InstanceSpecifier[AP_SWS_Fw_82002]thread-safe
Деструктор[AP_SWS_Fw_82003]not thread-safe
Конструктор перемещения[AP_SWS_Fw_82006]not thread-safe
Оператор присваивания с перемещением[AP_SWS_Fw_82007]not thread-safe
SwitchFirewallState[AP_SWS_Fw_82008]нет данных в полезной нагрузке

Уничтожение и перемещение должны быть защищены извне от одновременного использования одного и того же экземпляра [AP_SWS_Fw_82003] [AP_SWS_Fw_82006]. Для SwitchFirewallState полезная нагрузка не содержит сведений о потокобезопасности [AP_SWS_Fw_82008]. Поэтому не следует предполагать возможность параллельных вызовов для одного и того же экземпляра без уточнения у поставщика платформы.

Диаграмма состояний: диаграмма показывает жизненный цикл экземпляра интерфейса от конструирования через смену состояния и перемещение до уничтожения. Копирование не предусмотрено. Источники: [AP_SWS_Fw_82002], [AP_SWS_Fw_82003], [AP_SWS_Fw_82004], [AP_SWS_Fw_82006], [AP_SWS_Fw_82007]

Security Events для Intrusion Detection System Manager

Помимо переключения состояний, Firewall поддерживает Intrusion Detection System. Для заблокированных сообщений специфицирован набор событий безопасности (Security Events), которые передаются в IdsM. IdsM берет на себя их квалификацию и дальнейшую обработку. Он передает их в SOC или сохраняет персистентно в блоке управления EXP PlatformDesign с. 92. Сценарий «Report Security Event» связывает Operating System, FC Firewall и IdsM через взаимодействия packetBlocked(), handlePacketBlocked(), raiseSecurityEvent() и ReportEvent(). Некоторые их части помечены как «aapInformative» EXP SWArchitecture с. 232.

Для пакетов, блокируемых Default Action, в SWS для R23-11 указаны специфичные для уровней события SWS Firewall с. 31:

  • SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH для Ethernet,
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

Эти имена событий не покрываются требованиями R25-11 в полезной нагрузке. Их действительность для R25-11 необходимо сверить с актуальной SWS SWS Firewall с. 31.

Диаграмма последовательности: заблокированный пакет преобразуется FC Firewall в Security Event и передается в IdsM. Порядок отдельных шагов интерпретирован на основе подписей к рисункам. Источники: EXP SWArchitecture с. 232, EXP PlatformDesign с. 92

Поведение при ошибке

Для SwitchFirewallState специфицированы две ошибки: FwErrc::kServiceNotAvailable и FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]. Их значения определяет перечисление FwErrc, а именно kServiceNotAvailable=1 и kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]. Метод является noexcept и возвращает ara::core::Future<void>. Поэтому вызывающая сторона оценивает эти ошибки через Future, а не через исключение из вызова [AP_SWS_Fw_82008].

Обе ошибки относятся к FwErrorDomain. Домен предоставляет следующие компоненты:

  • GetFwErrorDomain() возвращает ссылку на объект домена; функция является constexpr и thread-safe [AP_SWS_Fw_83002].
  • MakeErrorCode создает ara::core::ErrorCode из FwErrc и дополнительных данных [AP_SWS_Fw_83003].
  • Name() и Message() возвращают имя домена и текст сообщения для кода; обе функции являются thread-safe [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • Псевдонимы Errc и Exception указывают на FwErrc и FwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

Конструктор по умолчанию домена удален, хотя его описание гласит «Constructs a new FwErrorDomain object» [AP_SWS_Fw_83009]. Поэтому доступ к домену осуществляется через GetFwErrorDomain().

Для передачи ошибки в виде исключения используется ThrowAsException. Функция создает и генерирует FwException. Она является noexcept(false) и классифицирована как «not exception safe» [AP_SWS_Fw_83012]. Само исключение создается через явный thread-safe конструктор FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005].

На уровне пакетов ошибочным случаем является блокировка пакета. Пакеты без подходящего правила подпадают под Default Action, а заблокированные сообщения передаются в IdsM как Security Events EXP PlatformDesign с. 92. Интерфейс в [AP_SWS_Fw_82008] не предусматривает обратного канала к приложению для таких событий. Их обработка возлагается на IdsM.

Диаграмма деятельности: диаграмма показывает обработку результата Future из SwitchFirewallState, сопоставление обоих значений FwErrc и опциональную повторную генерацию в виде FwException. Источники: [AP_SWS_Fw_82008], [AP_SWS_Fw_83001], [AP_SWS_Fw_83002], [AP_SWS_Fw_83012]
