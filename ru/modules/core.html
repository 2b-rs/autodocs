Классификация & назначение

Модуль ara::core является базовой базовой библиотекой адаптивной платформы AUTOSAR и определен в официальной спецификации AUTOSAR_AP_SWS_Core.pdf (R25-11). Он предоставляет безошибочный тип возврата ara::core::Result, а также базовый класс домена ошибок ara::core::ErrorDomain, который определяет контекст для набора ошибочных условий; Подклассы ErrorDomain являются корнем всех данных об ошибках [SWS_CORE_10303]. Обработка ошибок в Адаптивной платформе обычно осуществляется без исключений C++ через ara::core::ErrorCode и ara::core::Result в соответствии с концепцией «ValueOrError» (EXP InterfacesGuidelines). Пространство имен ara и все базовые пространства имен также зарезервированы AUTOSAR; Если адаптивное приложение добавляет туда свои собственные объявления, поведение не определено (EXP InterfacesGuidelines). Таким образом, ara::core формирует общую основу для инициализации, обработки ошибок и правил параллелизма для всех функциональных кластеров AP.

Ключевые объекты и типичное использование

ara::core::Result<T, E> содержит либо значение, либо ошибку; тип ошибки должен быть ErrorCode, иначе возникает ошибка компиляции [SWS_CORE_00701], со специализациями для ссылочных типов [SWS_CORE_00901] и значений void [SWS_CORE_00801]. Result создаётся через статические фабричные функции FromValue [SWS_CORE_00733] либо FromError [SWS_CORE_00736]. Bind применяет Callable к содержащемуся значению и возвращает новый Result; если экземпляр не содержит значения, исходная ошибка переносится без изменений [SWS_CORE_00768]. Resolve возвращает значение или в случае ошибки вызывает совместимый Callable [SWS_CORE_00767], тогда как ErrorOr [SWS_CORE_00764][SWS_CORE_00763] предоставляет простые резервные значения. Экземпляры ErrorDomain равны тогда и только тогда, когда совпадают их уникальные 64-битные идентификаторы; доступ обычно осуществляется через не-членные accessor, такие как GetFutureErrorDomain [SWS_CORE_10401].

Создание, жизненный цикл & Ownership

Жизненный цикл всей ARA централизованно управляется двумя свободными функциями ara::core::Initialize и ara::core::Deinitialize. Initialize запускает ARA-Framework; это может включать инициализацию внутренних структур данных и системных ресурсов, а также запуск фоновых потоков [SWS_CORE_15003]. Если Initialize использует внедрение аргументов командной строки, соответствующие аргументы должны быть прозрачно удалены, чтобы не влиять на разбор аргументов приложения [SWS_CORE_15006]. Успешный вызов переводит Framework в состояние, в котором все сконфигурированные компоненты могут немедленно обслуживать вызовы API [SWS_CORE_90026]; повторный вызов без предшествующего Deinitialize возвращает kAlreadyInitialized, не нарушая работу текущего экземпляра [SWS_CORE_90029]. Напротив, Deinitialize запускает завершение работы Framework, включая остановку запущенных фоновых потоков и освобождение динамической памяти и прочих системных ресурсов [SWS_CORE_15004]; если Framework не был успешно инициализирован или уже деинициализирован, каждый вызов возвращает kNotInitialized [SWS_CORE_90030].

Лишь небольшое, явно названное подмножество ara::core — среди прочих. ErrorCode, StringView, Result (без ValueOrThrow), ErrorDomain (без ThrowAsException), Initialize, Abort, SetAbortHandler и AddAbortHandler - можно использовать независимо от Initialize/Deinitialize можно использовать [SWS_CORE_15002]. Поведение всех других функций ARA до Initialize определяется реализацией [SWS_CORE_15005], а вызов после Deinitialize за пределами этого подмножества также имеет поведение, определяемое реализацией, поскольку соответствующая проверка во время выполнения намеренно не требовалась по соображениям производительности [SWS_CORE_90022]. Guidelines for using Adaptive Platform interfaces резюмирует это как обязательный контракт запуска/выключения: Initialize должен вызываться в точке входа, Deinitialize - только после того, как все ресурсы ARA будут освобождены в других потоках; оба доставляют Result<void>, который необходимо проверить, и ошибка не может быть исправлена, поэтому приложение должно завершиться с EXIT_FAILURE (EXP InterfacesGuidelines). Кроме того, AUTOSAR AP RS General запрещает функции инициализации, специфичные для кластера: если кластер функций требует явной инициализации или деинициализации, он должен использовать исключительно ara::core::Initialize/ara::core::Deinitialize.

Обработка ошибок, параллелизм и ограничения

Спецификация точно определяет Thread Safety: нестатическая функция-член AUTOSAR API является thread-safe, если её допускается одновременно вызывать на одном объекте из нескольких Threads без синхронизации вызывающим кодом; деструкторы и операторы присваивания обычно не thread-safe [SWS_CORE_13200]. Если не thread-safe функцию-член всё же конкурентно вызывают на одном объекте, поведение не определено — даже если другая участвующая функция thread-safe [SWS_CORE_13203]; напротив, конкурентный вызов на различных экземплярах без синхронизации допустим [SWS_CORE_13205]. Callbacks или чисто виртуальные функции, специфицированные как non-thread-safe, реализация ARA вызывает исключительно последовательно, например ara::tsync::SynchronizedTimeBaseNotifier, тогда как, например, ara::phm::RecoveryAction::RecoveryHandler является thread-safe [SWS_CORE_13214]. Использование произвольных ARA API в Signal Handler приводит к неопределённому поведению, если не указано иное [SWS_CORE_13210] (EXP InterfacesGuidelines: Async-Signal-Safety). Кроме того, AUTOSAR AP RS General требует, чтобы каждая функция API указывала свой уровень Thread Safety как «thread-safe», «not thread-safe» или «conditional», а контракт Thread Safety действует двусторонне: если API специфицирован как thread-safe, то и реализация, предоставляемая Vendor или пользователем, например Callbacks или чисто виртуальные Skeleton-функции, должна соблюдать это обещание (EXP InterfacesGuidelines).

Для неисправимых ошибок ara::core отличает Violation от обычной обработки ошибок: Violation является следствием нарушения предусловий или постусловий Framework и неустранимо, подобно неуспешной Assertion [SWS_CORE_00021]. При стандартизированном Violation процесс аварийно завершается через ara::core::Abort; Debug-сообщение согласно определению DLT выводится в stderr и должно записываться в Log-Sinks с Context ID распознавшего Functional Cluster [SWS_CORE_00090]. Пока выполняется вызов Abort, дальнейшие вызовы блокируют вызывающие Threads [SWS_CORE_12407]; установленные Abort-Handler вызываются в обратном порядке установки, а без Handler вызывается std::abort() [SWS_CORE_12404]. Это разделение между устранимыми посредством Result/ErrorCode ошибками и неустранимыми Violations [SWS_CORE_00021] поддерживается AUTOSAR AP RS General как общий принцип для всех Functional Cluster AP.

Интеграция & конфигурация

Каждый Functional Cluster ARA использует стандартизированные настройки журнала и трассировки из ara::core, в частности идентификатор контекста и диапазон идентификаторов сообщений [SWS_CORE_00055], при регистрации через ara::log. С этой целью спецификация, среди прочего, определяет стандартизированные идентификаторы контекста журнала для каждого Functional Cluster. #COM для com, #COR для ядра, #CRY для шифрования, #DIA для диагностики, #EXE для exec, #LOG для журнала и #PER для per [SWS_CORE_90024]. На уровне требований AUTOSAR AP RS General добавляется, что интерфейсы ARA должны использовать типы ara::core вместо стандартных типов C++ при условии, что ara::core предоставляет эквивалентный тип. Поскольку пространство имен ara полностью зарезервировано для AUTOSAR, все типы данных Functional Cluster также доступны через файл заголовка пересылки <fc>_fwd.h (EXP InterfacesGuidelines).
