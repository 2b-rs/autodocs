Роль ara::core как общей основы всех Functional Clusters

Functional Cluster Core решает две задачи. Он определяет базовые требования, действующие для всех Functional Clusters в Adaptive Platform. Кроме того, он предоставляет функциональность для всего фреймворка, прежде всего общие типы данных, которые несколько Functional Clusters используют в своих публичных интерфейсах (SWS Core с. 8). Сам Core зависит только от спецификации интерфейса операционной системы, то есть по сути от стандартной библиотеки C++ (SWS Core с. 10). Все символы находятся в пространстве имен ara::core и являются общедоступными, если не указано иное (SWS Core с. 47).

Сквозные правила действуют также для реализации других кластеров:

  • Директивы include следуют шаблону #include "ara/fc/header.h".
  • Публичным заголовочным файлам требуются include guards, по возможности уникальные в масштабах всей системы (SWS Core с. 23).
  • Символы с префиксом ARA зарезервированы для AUTOSAR.
  • Спецификаторы объявления разрешается дополнять только inline и friend (SWS Core с. 24).

В качестве нативных интерфейсов описание архитектуры называет две группы: Initialize()/Deinitialize(), а также Abort()/SetAbortHandler() (EXP SWArchitecture с. 60, [SWS_CORE_00051]).

Контекстная диаграмма: Core является базовым уровнем между приложениями, другими Functional Clusters и стандартной библиотекой C++. Прерывание через std::abort распознается Execution Management как Abnormal Termination. Источники: SWS Core с. 8, SWS Core с. 10, SWS Core с. 187, SWS Core с. 39, EXP SWArchitecture с. 60

Запуск и завершение среды выполнения ARA

ara::core::Initialize представляет собой (предварительную) инициализацию фреймворка ARA. До этого любое взаимодействие с ARA недопустимо. Исключением являются типы, которые должны быть пригодны для использования независимо от инициализации:

  • ErrorCode и StringView,
  • Result, но без ValueOrThrow ([SWS_CORE_00766]),
  • ErrorDomain с его подклассами, но без ThrowAsException ([SWS_CORE_00154]) (SWS Core с. 182).

Это исключение обосновывается тем, что именно эти типы требуются для самой инициализации (SWS Core с. 46). Initialize может настраивать структуры данных и системные ресурсы, а также запускать фоновые потоки (SWS Core с. 45). При необходимости она инициализирует и другие Functional Clusters (SWS Core с. 187).

ara::core::Deinitialize выполняет штатное завершение работы фреймворка. Сюда входят завершение фоновых потоков и освобождение памяти и других системных ресурсов. Если при этом параллельно продолжают выполняться вызовы ARA, поведение не определено (SWS Core с. 45). Перед вызовом использование интерфейсов ARA должно быть завершено. Рекомендуется размещать вызов после статической инициализации и перед уничтожением статических данных (SWS Core с. 182).

Диаграмма состояний: среда выполнения ARA переключается через Initialize и Deinitialize между тремя фазами. Вне инициализированной фазы доступен только фиксированный набор типов. Источники: SWS Core с. 182, SWS Core с. 182, SWS Core с. 45

Классы ошибок и значения ошибок: ErrorCode, ErrorDomain, Result

Core различает три вида неудачных операций (SWS Core с. 25):

  • Error означает, что функция API, предполагаемая безошибочной, не может выполнить свое назначение. Error является устранимой ошибкой.
  • Violation соответствует непройденному утверждению и является неустранимой.
  • Corruption возникает из-за повреждения системных ресурсов и также является неустранимой.

Для каждого вида определена обработка (SWS Core с. 27):

  • Errors возвращаются в виде Result или Future.
  • Violations завершают операцию либо через исключение, не производное от ara::core::Exception, либо через ara::core::Abort ([SWS_CORE_00052]). Неудачное выделение памяти по умолчанию также считается Violation.
  • Corruptions приводят к аварийному завершению процесса.

Диаграмма деятельности: тип обнаруженного условия определяет, возвращается ли значение ошибки либо завершается операция или процесс. Источники: SWS Core с. 25, SWS Core с. 27, [SWS_CORE_00052]

ErrorCode содержит три компонента: значение ошибки, ссылку на домен ошибок и необязательные дополнительные данные от поставщика. Их можно получить через Value() ([SWS_CORE_00514]) и SupportData() ([SWS_CORE_00516]). При сравнении ([SWS_CORE_00571]) учитываются только значение и домен, а дополнительные данные игнорируются. Как правило, ErrorCode создается через перенаправляющую форму Result::FromError ([SWS_CORE_00736]) (SWS Core с. 28).

Result следует концепции ValueOrError: он содержит либо значение, либо ошибку. По умолчанию ErrorType является ErrorCode (SWS Core с. 30). Типичные способы доступа:

  • HasValue() ([SWS_CORE_00751]),
  • Value() ([SWS_CORE_00755]),
  • Error() ([SWS_CORE_00757]),
  • ValueOrThrow() ([SWS_CORE_00766]). Эта функция связывает подход без использования исключений с исключениями C++. Их базовый тип ara::core::Exception ([SWS_CORE_00611]) возвращает ErrorCode через Error() ([SWS_CORE_00613]).

Специализация Result<void, E> не содержит operator-> и Bind (SWS Core с. 70, [SWS_CORE_00851]).

Асинхронные результаты с использованием Future и Promise

Future и Promise тесно связаны с std::future и std::promise. Оба разделяют общее состояние. Отличия обусловлены только интеграцией с Result (SWS Core с. 89). В частности, существует два различия:

  • SetError ([SWS_CORE_00353]) заменяет set_exception.
  • GetResult() ([SWS_CORE_00336]) возвращает Result и никогда не генерирует исключений.

Разделение обязанностей очевидно: Result служит для синхронных вызовов, Future — для асинхронных вызовов с потокобезопасным последующим получением данных (SWS Core с. 31).

Последовательность действий на стороне поставщика:

  1. Поставщик создает Promise ([SWS_CORE_00341]).
  2. С помощью get_future() ([SWS_CORE_00344]) он получает соответствующий Future и возвращает его.
  3. Позже он выполняет Promise с помощью set_value ([SWS_CORE_00345], [SWS_CORE_00346]), SetError или SetResult ([SWS_CORE_00355]).

В ara::com привязка вызывает set_value или SetError. В результате этого блокирующие вызовы get(), wait(), wait_for() и wait_until() возвращают управление (SWS CM с. 106). Наглядный пример демонстрирует выполнение в рабочем потоке после того, как Future уже был возвращен (EXP ARAComAPI с. 59).

Диаграмма последовательности: поставщик немедленно возвращает Future и позже асинхронно устанавливает общее состояние со значением или ошибкой. Источники: [SWS_CORE_00341], [SWS_CORE_00344], [SWS_CORE_00345], [SWS_CORE_00353], [SWS_CORE_00326], SWS CM с. 106, EXP ARAComAPI с. 59

Потребитель имеет несколько шаблонов доступа:

  • get() ([SWS_CORE_00326]) и wait() ([SWS_CORE_00328]) блокируют выполнение.
  • wait_for() ([SWS_CORE_00329]) и wait_until() ([SWS_CORE_00330]) возвращают FutureStatus ([SWS_CORE_00361]). Это позволяет отличить полученный результат от таймаута (ARAComAPI (Рис. 6.15) с. 1).
  • then() ([SWS_CORE_00331]) регистрирует продолжение, опционально с Executor ([SWS_CORE_00337]).
  • is_ready() ([SWS_CORE_00332]) не блокирует выполнение и подходит для приложений реального времени, работающих по принципу опроса (EXP ARAComAPI с. 58).

Futures не поддерживают копирование ([SWS_CORE_00334]). Ненужный результат отбрасывается путем перезаписи Future объектом Future, сконструированным по умолчанию ([SWS_CORE_00322]) (EXP ARAComAPI с. 59). Дополнительно предусмотрен Executor. Согласно сигнатуре, execute возвращает Future результата вызова ([SWS_CORE_00024]), тогда как oneway_execute ничего не возвращает ([SWS_CORE_00025]).

Диаграмма деятельности: потребитель выбирает между блокирующим получением, ожиданием с ограничением по времени, продолжением и неблокирующим опросом. Источники: [SWS_CORE_00326], [SWS_CORE_00329], [SWS_CORE_00331], [SWS_CORE_00332], [SWS_CORE_00336], EXP ARAComAPI с. 58

Типы данных, контейнеры и ресурсы памяти

Core переопределяет типы, которые практически эквивалентны типам, уже существующим в стандарте C++. Причина: поведение выделения памяти для типов std:: часто непригодно для автомобильной отрасли. Функции, которые по стандарту C++ генерируют исключения, вместо этого вызывают у этих типов Violation (SWS Core с. 41). В частности:

  • Vector ведет себя как std::vector, только аллокатор по умолчанию зависит от реализации (SWS Core с. 129, [SWS_CORE_01390]).
  • Map ведет себя аналогично std::map (SWS Core с. 130, [SWS_CORE_01496]).
  • String определен как BasicString<> с фиксированным символьным типом char (SWS Core с. 133, [SWS_CORE_03001]) и неявно преобразуется в StringView ([SWS_CORE_03301]).

Спецификация сама признает, что поведение аллокации Map, Vector и String описано только как зависящее от реализации (SWS Core с. 10).

Другие типы заимствованы из более новых стандартов C++ (SWS Core с. 43):

  • Optional отображает опциональные элементы записей. Наличие значения проверяется с помощью operator bool или has_value() ([SWS_CORE_01129], SWS Core с. 131, ARAComAPI (Рис. 6.3) с. 1).
  • StringView представляет собой представление символов только для чтения (SWS Core с. 132, [SWS_CORE_02112]).
  • Span является представлением непрерывной последовательности внешних объектов (SWS Core с. 137, [SWS_CORE_01901]). Возможность использования as_bytes без проблем с алиасингом зависит от реализации (SWS Core с. 155, [SWS_CORE_01980]).
  • Byte не является целочисленным типом и не допускает неявных преобразований (SWS Core с. 44).
  • Для Array вызов get<I> с I >= N приводит к ошибке компиляции (SWS Core с. 127, [SWS_CORE_01282]).

Различия между релизами: выдержки из R21-11 в двух пунктах не соответствуют требованиям R25-11; определяющими являются требования.

  • Согласно R21-11, Array::at отсутствует (SWS Core с. 41). В R25-11, напротив, введен at() как noexcept ([SWS_CORE_01273]).
  • Согласно R21-11, Optional не имеет функций-членов value (SWS Core с. 131). В R25-11 они специфицированы ([SWS_CORE_01130]).

Для управления памятью предусмотрены полиморфные ресурсы памяти. Базовый класс MemoryResource открыто предоставляет allocate/deallocate/is_equal и закрытые хуки do_*. Ниже находятся MonotonicBufferResource, а также синхронизированные и несинхронизированные пуловые ресурсы (EXP SWArchitecture с. 61). Пуловые ресурсы конструируются с помощью PoolOptions и вышестоящего ресурса ([SWS_CORE_00030], [SWS_CORE_00067]). Они предоставляют release() ([SWS_CORE_00037]) и upstream_resource() ([SWS_CORE_00038]) и не поддерживают копирование ([SWS_CORE_00034], [SWS_CORE_00046]).

Собственные домены ошибок и привязка к экземпляру через InstanceSpecifier

Программный модуль с самостоятельной логикой должен определять собственные домены ошибок. Домен ошибок состоит из пяти частей, которые все находятся в пространстве имен модуля (SWS Core с. 32):

  • перечисления ошибок,
  • базового класса исключений,
  • подкласса ErrorDomain,
  • глобальной функции доступа,
  • перегрузки MakeErrorCode.

Для этих частей действуют строгие правила:

  • Перечисление называется <SN>Errc, не содержит значений успеха и оставляет 0 незанятым (SWS Core с. 33).
  • Подкласс представляет собой final и имеет псевдонимы Errc и Exception (SWS Core с. 34).
  • Функция доступа Get<SN>ErrorDomain является constexpr и возвращает синглтон (SWS Core с. 35).
  • Домены должны быть литеральными типами (SWS Core с. 30).

Идентичность домена основана на уникальном 64-битном ID ([SWS_CORE_00121], [SWS_CORE_00151], [SWS_CORE_00137]). Диапазон значений разделен (SWS Core с. 37):

  • Бит 63 = 1 и бит 62 = 0: домены AUTOSAR,
  • старшие 32 бита = 0xc000'0000: домены производителей,
  • бит 63 = 0: пользовательские домены.

FutureErrorDomain имеет ID 0x8000'0000'0000'0013 ([SWS_CORE_00480]). Все остальные ошибки Core относятся к CoreErrorDomain (SWS Core с. 84).

InstanceSpecifier устанавливает связь с экземпляром модели. Он идентифицирует экземпляры прототипов портов в метамодели AUTOSAR с помощью списка имен, разделенных «/», от Executable до PortPrototype. Синтаксически некорректные пути отклоняются. Для конструирования существует два способа: не генерирующий исключений фабричный метод Create или конструктор, который может генерировать исключение при недопустимом вводе (SWS Core с. 40).

Поведение при ошибке

ara::core::Abort ([SWS_CORE_00052]) немедленно и аварийно завершает процесс, без раскрутки стека и без вызова деструкторов статических объектов (SWS Core с. 38). Функция обладает следующими свойствами:

  • Она никогда не возвращает управление.
  • Она записывает переданный текст как сообщение журнала в стандартный поток ошибок.
  • Одновременные дополнительные вызовы блокируют вызывающие потоки.

Этот вызов считается Explicit Operation Abortion (SWS Core с. 8).

С помощью SetAbortHandler ([SWS_CORE_00051]) можно установить AbortHandler ([SWS_CORE_00050]). Его тип выводится из прототипа, который не реализован ([SWS_CORE_00053], SWS Core с. 183). Обработчик, завершающий процесс, должен использовать для этого std::abort, чтобы Execution Management распознал Abnormal Termination. Если обработчик возвращает управление или ни один обработчик не установлен, Abort сам вызывает std::abort() (SWS Core с. 39). В R25-11 дополнительно вводится AddAbortHandler ([SWS_CORE_00054]). Его семантика не описана подробно в полезной нагрузке и поэтому здесь не рассматривается.

Диаграмма деятельности: Abort всегда завершается остановкой процесса, либо обработчиком, либо посредством std::abort. Интерпретация: сообщение журнала выводится до вызова обработчика. Источники: SWS Core с. 38, SWS Core с. 39, [SWS_CORE_00051], [SWS_CORE_00052]

На асинхронной стороне уничтоженный Promise ([SWS_CORE_00349]) приводит к завершенному Future. Он содержит ErrorCode из FutureErrorDomain со значением FutureErrc::kBrokenPromise ([SWS_CORE_00400]). Это происходит, например, при уничтожении ServiceProxy (SWS CM с. 290). Ошибки же связи ara::com сообщает через SetError с ошибками из ComErrorDomain (SWS CM с. 300).

Диаграмма последовательности: уничтожение прокси уничтожает Promise и завершает ожидающий Future со значением kBrokenPromise. Источники: SWS CM с. 290, [SWS_CORE_00349], [SWS_CORE_00400], [SWS_CORE_00336]

Определены еще два случая ошибок:

  • Если Message() вызывается с кодом ошибки из чужого домена, это является Violation ([SWS_CORE_00153], SWS Core с. 51).
  • Ошибка из Deinitialize — единственный гарантированно доступный способ информирования, например, когда ara::log уже деинициализирован. Она считается неустранимой (SWS Core с. 45).
