Роль State Management и разграничение с Execution Management

State Management определяет оперативное состояние платформы. Execution Management выполняет переходы между состояниями (SWS EM с. 51). На основе специфичных для приложения входных данных State Management определяет целевой набор активных Function Group States. Их переключение он запрашивает у Execution Management через API StateClient (EXP SWArch с. 50; SWS SM с. 40). Подход StateMachine является опциональным. Он переносит специфичный для проекта арбитраж в SMControlApplication, который запрашивает только сконфигурированные переходы (SWS SM с. 28; SWS SM с. 42).

State Management предоставляет следующие сервисы ara::com:

  • UpdateRequest для Update and Configuration Management ([SWS_SM_91102]).
  • StateMachineService и UpdateAllowedService для SMControlApplication ([SWS_SM_91107], [SWS_SM_91108]).
  • StateMachineNotification::CurrentState для любых Adaptive Applications ([SWS_SM_91109]).

Для Suspend-to-RAM добавляются S2RHub и S2RSatellite, для операционной системы — расширение платформы PowerStateInterface (EXP SWArch с. 51; SWS SM с. 163). State Management, в свою очередь, требуются интерфейсы Execution Management, Platform Health Management и Network Management (SWS SM с. 17; EXP SWArch с. 77).

Контекстная диаграмма: State Management находится между управляющими приложениями, кластерами платформы и операционной системой. Источники: SWS SM с. 16, EXP SWArch с. 51, EXP SWArch с. 52, [SWS_SM_71001]

От запуска машины к Controller-StateMachine

Операционная система запускает Execution Management в качестве первого процесса. Execution Management активирует Machine Function Group State Startup, и State Management должен являться частью этого состояния (EXP SWArch с. 216). Результат этого самостоятельно инициированного перехода возвращает GetInitialMachineStateTransitionResult. После этого ответственность за смену состояний возлагается на State Management (SWS EM с. 48; SWS EM с. 56). Если Startup так и не будет достигнут, State Management может прервать переход с помощью SetState. Начальным результатом тогда будет kOperationCanceled (SWS EM с. 57).

В подходе StateMachine сначала запускается StateMachine типа Controller. Она управляет MachineFG и запускает Agents (SWS SM с. 46). Если сессия обновления активна, контроллер переходит в состояние ContinueUpdate вместо начального состояния (SWS SM с. 91). После успешного вызова «StartStateMachine» предлагаются StateMachineService и StateMachineNotification. Контроллер не ждет завершения начального ActionList (SWS SM с. 45; SWS SM с. 59).

Диаграмма последовательности: Execution Management передает управление после Startup, контроллер запускает Agents. Источники: SWS SM с. 93, SWS EM с. 56, SWS SM с. 45

Остановка переводит Agent-StateMachine через ее состояние «Off», после чего она больше не существует. Уже работающий Agent при «StartStateMachine» с параметром переходит в переданное состояние (SWS SM с. 63; SWS SM с. 60).

Диаграмма состояний: жизненный цикл Agent-StateMachine от запуска до прекращения ее сервисов. Источники: SWS SM с. 10, SWS SM с. 62, SWS SM с. 63

Смена состояния: RequestTransition и ActionLists

RequestTransition оценивает переданное значение в TransitionRequestTable относительно текущего состояния ([SWS_SM_91107]; SWS SM с. 50). Вызов возвращает ошибку в следующих случаях:

  • kInvalidValue: значение не сконфигурировано.
  • kTransitionNotAllowed: значение не сконфигурировано для текущего состояния.
  • kRecoveryTransitionOngoing: выполняется устранение ошибки.
  • kUpdateInProgress: StateMachine помечена как «ImpactedByUpdate».

Источники: SWS SM с. 49; SWS SM с. 83. Если запрос принимается, ожидающие запросы получают kOperationCanceled. Выполняющийся ActionList останавливается, и ActionList целевого состояния запускается немедленно (SWS SM с. 50).

ActionListItems запускаются в сконфигурированном порядке и выполняются параллельно, пока не встретится SYNC. В конце каждого ActionList действует неявный SYNC (SWS SM с. 55). Существуют элементы для Function Group States, Sleep, SetNetworkHandle, Start/Stop StateMachine и Suspend-to-RAM (SWS SM с. 54). Sleep не блокирует входящие триггеры (SWS SM с. 64). Ошибки при обработке приводят к kTransitionFailed (SWS SM с. 51). Во время перехода CurrentState имеет значение «InTransition» ([SWS_SM_91109]). Переходы NetworkHandle в FullCom или NoCom также вызывают табличные переходы (SWS SM с. 52).

Диаграмма деятельности: проверки и результаты вызова RequestTransition; порядок проверок является интерпретацией. Источники: [SWS_SM_91107], SWS SM с. 49, SWS SM с. 50, SWS SM с. 83

Сессии обновления с Update and Configuration Management

Сессия начинается с RequestUpdateSession. State Management может отклонить ее, если машина не подлежит обновлению. Вторую параллельную сессию он отклоняет с kNotAllowedMultipleUpdateSessions ([SWS_SM_91102]; SWS SM с. 30). Разрешено ли обновление, решает SMControlApplication через поле UpdateAllowed. На каждую машину приходится максимум один порт UpdateRequest, и только процесс контроллера инстанцирует его ([SWS_SM_91108]; SWS SM с. 79).

PrepareUpdate, VerifyUpdate и PrepareRollback получают список затронутых Function Groups. Каждая StateMachine, управляющая одной из них, помечается как «ImpactedByUpdate». Если затронут Agent, контроллер также помечается ([SWS_SM_91103], [SWS_SM_91104], [SWS_SM_91105]; SWS SM с. 82). Вне активной сессии эти методы и StopUpdateSession возвращают kOperationRejected (SWS SM с. 31). Затронутые Agents обрабатываются по-разному в зависимости от метода:

  • При PrepareUpdate и PrepareRollback они останавливаются.
  • При VerifyUpdate они переводятся в состояние VerifyUpdate.

Источники: SWS SM с. 84; SWS SM с. 85; SWS SM с. 89. StopUpdateSession переводит контроллер в AfterUpdate и снова освобождает RequestTransition ([SWS_SM_91101]; SWS SM с. 95).

Диаграмма последовательности: процесс сессии обновления с точки зрения контроллера. Источники: SWS SM с. 81, SWS SM с. 84, SWS SM с. 89, [SWS_SM_91102]

ResetMachine является Fire&Forget. За прогрессом Update and Configuration Management следит через ResetMachineNotifier, поскольку машина и UCM после перезапуска должны синхронизироваться заново ([SWS_SM_91100], [SWS_SM_91106]; SWS SM с. 33).

Диаграмма состояний: значения поля ResetMachineNotifier без неспецифицированных промежуточных значений. Источники: SWS SM с. 33, SWS SM с. 90, SWS SM с. 93, SWS SM с. 95

Suspend-to-RAM через S2R Hub, сателлиты и PowerStateInterface

Приложения обрабатываются по-разному в зависимости от suspendToRamAwareness (SWS SM с. 109):

  • При suspendToRamNotSupported они завершаются путем смены Function Group.
  • При suspendToRamAware они уведомляются как S2R Satellite.

Сателлит создается через Create или конструктор с InstanceSpecifier и регистрируется с помощью Offer ([SWS_SM_81014], [SWS_SM_81003], [SWS_SM_81012]). StopOffer отменяет его регистрацию, блокирует до завершения выполняющихся колбэков и должен вызываться перед уничтожением ([SWS_SM_81013]; SWS SM с. 38). Колбэки EnterSuspendMode и LeaveSuspendMode чисто виртуальные и возвращают ara::core::Future<void> ([SWS_SM_81010], [SWS_SM_81011]).

RequestToEnterSuspendMode и RequestToLeaveSuspendMode вызывают все активно зарегистрированные, IAM-аутентифицированные сателлиты. Они возвращают управление, как только все ответили, отменили регистрацию или истек таймаут (по умолчанию 1000) ([SWS_SM_81110], [SWS_SM_81111]; SWS SM с. 36). Затем EnterSuspendToRamOs инициирует перевод операционной системы в состояние Suspend. Интерпретация: предположительно, это происходит через PowerStateInterface::SetPowerState с kPmSuspendToRam ([SWS_SM_81112], [SWS_SM_71001], [SWS_SM_71002]).

О пробуждении операционная система сообщает через WakeUpHandler, зарегистрированный с RegisterWakeUpHandler. Затем контроллер автономно переходит в LeaveSuspend, чей ActionList должен содержать LeaveSuspendToRam ([SWS_SM_71003], [SWS_SM_71004]; SWS SM с. 103). В подходе StateMachine контроллер использует Hub внутренне. В этом случае приложениям запрещено использовать S2RHub (SWS SM с. 96). Все API S2R имеют статус DRAFT.

Диаграмма последовательности: вход в Suspend-to-RAM и возврат после пробуждения; шаг с операционной системой является интерпретацией. Источники: SWS SM с. 36, SWS SM с. 37, SWS SM с. 98, [SWS_SM_81112]

Правила конфигурации и зоны ответственности

В каждом состоянии MachineFG, кроме Off, должен выполняться процесс с аффинитетом STATE_MANAGEMENT. Иначе машина, например, зависнет в Startup (SWS SM с. 146). Для Function Groups и NmNetworkHandles действуют правила однозначности:

  • На каждую Function Group и каждый NmNetworkHandle ссылается ровно одна StateMachine.
  • Все ActionLists одной StateMachine содержат одно и то же множество Function Groups и NmNetworkHandles.

Источники: SWS SM с. 48; SWS SM с. 66; SWS SM с. 57; SWS SM с. 58. Только контроллер использует Start/StopStateMachine. Agents управляют только Function Groups из того же множества claimedFunctionGroups и требуют состояния «Off» (SWS SM с. 58; SWS SM с. 47; SWS SM с. 48). Длительность ActionList ограничивает maxActionListDuration. Если значение отсутствует, действует глобальное значение экземпляра модуля (SWS SM с. 68).

Поведение при ошибке

Если Platform Health Management или Execution Management сообщает об ошибке и StateMachine не помечена как «ImpactedByUpdate», она устанавливает флаг Recovery. Она вычисляет ErrorRecoveryTable и немедленно переходит в целевое состояние. Обязательная запись ANY перехватывает несконфигурированные ErrorCodes (SWS SM с. 69; SWS SM с. 70). StateMachines, затронутые обновлением, игнорируют такие запросы и только протоколируют их (SWS SM с. 82). Новая ошибка во время текущего Recovery считается «nested recovery». Все соответствующие вызовы RecoveryHandler() получают в этом случае тот же результат (SWS SM с. 29). Флаг сбрасывается только после успешной обработки Recovery-ActionList (SWS SM с. 72).

Другие источники ошибок формируют собственные ErrorCodes:

  • Ошибки SetState kNoCommunication, kInvalidTransition и kInvalidMetaModelIdentifier отображаются на functionGroupTransitionRequestFailedError.
  • Таймауты ActionList, запуск и остановка Agent, а также LeaveSuspendToRam имеют собственные ErrorCodes со значением по умолчанию 1.

Источники: SWS SM с. 73; SWS SM с. 74; SWS SM с. 76. kIntegrityOrAuthenticityCheckFailed повторяется при каждой последующей попытке, устранение находится за пределами State Management (SWS SM с. 40). Если State Management не отвечает вовремя на RecoveryHandler(), Platform Health Management вызывает FireWatchdogReaction(). Ошибки контроля исполнения (Supervision) в самом State Management приводят к перезапуску машины (EXP SWArch с. 234; EXP SWArch с. 235).

На уровне API State Management сообщает об ошибках через SmErrorDomain с именем «Sm» и значениями SmErrc, такими как kOfferFailed или kCommunicationFailed ([SWS_SM_81240], [SWS_SM_81248]). MakeErrorCode и GetSmDomain создают коды ([SWS_SM_81244], [SWS_SM_81251]). SmException передает их, если включены исключения C++ ([SWS_SM_81243], [SWS_SM_81250]). Hub объединяет ответы сателлитов в kAtLeastOneRejected, kAtLeastOneHadIssuesToLeave, kCommunicationTimeout или kCommunicationFailed (SWS SM с. 37).

Диаграмма последовательности: обработка ошибок через ErrorRecoveryTable и откат к реакции Watchdog. Источники: EXP SWArch с. 220, EXP SWArch с. 220, SWS SM с. 69, SWS SM с. 82
