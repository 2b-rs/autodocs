Роль: сетевые запросы между State Management и шиной

Адаптивное Network Management (NM) координирует переключение нижележащих физических и частичных сетей между нормальным режимом работы и режимом Bus-Sleep. Оно должно работать независимо от используемого стека связи SWS NM с. 5. С технической точки зрения оно основано на PRS NetworkManagementProtocol. Для отправки и приёма NM-сообщений оно использует стек связи SWS NM с. 9. Согласно ограничениям, в настоящее время поддерживается только UdpNM SWS NM с. 8.

Сверху граница системы строго очерчена. Приложения не обращаются к NM напрямую. Они запрашивают функции у State Management, а State Management в зависимости от конфигурации запрашивает или освобождает логические сети SWS NM с. 14 SWS NM с. 29. Единственным интерфейсом является класс ara::nm::NetworkHandle в заголовке ara/nm/network_handle.h [SWS_ANM_01000]. Он явно предназначен только для State Management EXP SWArch с. 77. Соответственно, State Management указывает его в числе своих требуемых интерфейсов EXP SWArch с. 56. Оба кластера основаны на демонах: State Management использует интерфейс, а NM реализует его SWS NM с. 13.

Более старые фрагменты SWS (главы 8/9) противоречат этому. Там утверждается, что NM не содержит API и предоставляет всё через сервисы SWS NM с. 26. Однако нормативным для R25-11 является C++-класс NetworkHandle с его методами [SWS_ANM_01000] [SWS_ANM_01009]. Обзор Platform Design описывает этот переход от интерфейса ara::com к прямым вызовам методов EXP PlatformDesign с. 60.

Контекстная диаграмма: приложения взаимодействуют с NM только косвенно через State Management, которое управляет NM через NetworkHandle. NM обменивается NM-сообщениями через стек связи. Источники: SWS NM с. 13, SWS NM с. 14, SWS NM с. 9, [SWS_ANM_01000]

От логической сети к каналу: дескрипторы, Partial Networks и экземпляры NM

Логическая сеть отображается ровно на одну частичную или физическую сеть. Частичная же сеть может быть сопоставлена нескольким физическим сетям. Каждый порт, предоставляемый NM, управляет ровно одной логической сетью, и порты связываются с логическими сетями через манифест. При использовании Partial Networking необходимо дополнительно сконфигурировать сопоставление частичных сетей с физическими. Без Partial Networking порт отображается непосредственно на физические сети SWS NM с. 14.

Обзор SWS демонстрирует многоуровневую структуру. Экземпляры Network-Handle воздействуют на конечные автоматы Partial Network. Они управляют канальными экземплярами NM, каждый из которых имеет свой автомат состояний сети (Network State Machine), работающий, в свою очередь, на сетях SWS NM с. 18 EXP PlatformDesign с. 60. Конечный автомат Partial Network зависит от реализации. Однако его поведение должно соответствовать требованиям к Partial Networking из PRS SWS NM с. 24.

Диаграмма взаимодействия: дескрипторы воздействуют на канальные экземпляры NM через конечные автоматы Partial Network. При этом одна частичная сеть (PN2) может затрагивать две сети. Источники: SWS NM с. 18, SWS NM с. 14, SWS NM с. 15

Работа с ara::nm::NetworkHandle: запрос, опрос, уведомление

Дескриптор создаётся из InstanceSpecifier прототипа порта типа NetworkManagementPortInterface. Конструктор является noexcept и потокобезопасным [SWS_ANM_01001]. Копирование невозможно [SWS_ANM_01005] [SWS_ANM_01006], перемещение возможно [SWS_ANM_01003] [SWS_ANM_01004]. Деструктор не является потокобезопасным [SWS_ANM_01002].

NetworkStateType поддерживает только kNoCom и kFullCom. kFullCom действует, когда все назначенные сети находятся в FULL_COM, в противном случае действует kNoCom [SWS_ANM_01358]. Дескриптор разделяет два представления:

  • Запрошенное состояние: SetNetworkRequestedState запрашивает или освобождает PNC, VLAN или физическую сеть [SWS_ANM_01009]. GetNetworkRequestedState считывает это состояние [SWS_ANM_01008].
  • Фактическое состояние: GetNetworkState считывает текущее состояние сети [SWS_ANM_01007].

Интерпретация: фактическое состояние kFullCom, вероятно, соответствует Network Mode назначенных каналов. Ведь Network Mode означает, что сеть запрошена или активна SWS NM с. 15.

Для обоих представлений предусмотрено по одному нотификатору типа NetworkStateChangeNotifier. Он представляет собой std::function, который получает новый NetworkStateType [SWS_ANM_01020]. RegisterNetworkStateChangeNotifier и RegisterNetworkRequestedStateChangeNotifier принимают не более одного нотификатора каждый [SWS_ANM_01010] [SWS_ANM_01012]. Согласно таблице интерфейсов, каждая последующая регистрация перезаписывает существующую EXP SWArch с. 77. Варианты с ExecutorT выполняют нотификатор в переданном контексте выполнения [SWS_ANM_01014] [SWS_ANM_01015]. Отмена регистрации выполняется с помощью UnregisterNetworkStateChangeNotifier или UnregisterNetworkRequestedStateChangeNotifier [SWS_ANM_01011] [SWS_ANM_01013].

Что касается потокобезопасности: потокобезопасными являются только оба геттера [SWS_ANM_01007] [SWS_ANM_01008]. SetNetworkRequestedState, а также все функции регистрации и отмены регистрации таковыми не являются [SWS_ANM_01009] [SWS_ANM_01010] [SWS_ANM_01013]. Поэтому вызывающая сторона должна самостоятельно сериализовать эти вызовы для каждого дескриптора.

Диаграмма последовательности: создается дескриптор, регистрируются нотификаторы, запрашивается сеть, выполняется асинхронное уведомление и, наконец, сеть снова освобождается. Источники: [SWS_ANM_01001], [SWS_ANM_01009], [SWS_ANM_01015], [SWS_ANM_01007], SWS NM с. 13, SWS NM с. 18

Поведение канала: децентрализованный алгоритм NM и режимы работы

Алгоритм работает децентрализованно и прямо. Каждый узел принимает решение исключительно на основе принятых и отправленных пакетов NM. Периодические пакеты NM, рассылаемые по многоадресной передаче всем узлам, поддерживают кластер в активном состоянии. Узел, готовый перейти в спящий режим, больше не передает данные. Однако он откладывает переход в спящий режим до тех пор, пока поступают пакеты от других узлов SWS NM с. 13. Каждый узел может интегрироваться в уже работающий кластер SWS NM с. 11.

Для каждого физического канала NM реализует режимы Network Mode, Prepare Bus-Sleep Mode и Bus-Sleep Mode. Для приложений эти режимы не видны SWS NM с. 15. Network Mode подразделяется на Repeat Message, Normal Operation и Ready Sleep SWS NM с. 16. Подробный порядок работы:

  • При входе в Network Mode выполняется переход в Repeat Message и запускается таймер таймаута NM со значением NmTimeoutTime. Каждый успешно принятый или отправленный пакет NM перезапускает таймер SWS NM с. 17.
  • Если сеть освобождается в Normal Operation, NM переходит в Ready Sleep, и передача останавливается. Принятый бит Repeat Message Request Bit приводит к возврату в Repeat Message SWS NM с. 18.
  • Prepare Bus-Sleep длится NmWaitBusSleepTime и завершается переходом в Bus-Sleep. Если до этого поступает пакет NM, NM немедленно возвращается в Network Mode SWS NM с. 19.

При передаче первый пакет после входа в Repeat Message задерживается на NmMsgCycleOffset. Затем NM передает циклически с NmMsgCycleTime SWS NM с. 22. Биты Repeat Message Request Bit, Active Wakeup Bit и NM Coordinator Sleep Ready Bit в отправляемых сообщениях всегда равны 0 SWS NM с. 20. Не поддерживаются обнаружение узлов, роль мастер-координатора, координированное отключение через CBV, а также Passive Mode SWS NM с. 8.

Диаграмма состояний: режимы работы экземпляра NM для каждого канала с подсостояниями Network Mode и управляемыми по времени переходами в спящий режим. Источники: SWS NM с. 15, SWS NM с. 16, SWS NM с. 17, SWS NM с. 18, SWS NM с. 19

Partial Networking: оценка приема и агрегированное состояние запроса

NmPnEnabled включает или выключает оценку информации PN при приеме. Правила при включенном Partial Networking SWS NM с. 24:

  • Если бит PNI равен 1, NM вызывает нотификатор NetworkHandle, как только принятый BitVector изменяет состояние запроса релевантной PN или канала.
  • Если бит PNI равен 0, NM тем не менее обрабатывает полезные данные.
  • Геттер возвращает агрегированное состояние запроса PN и не отражает последнюю принятую информацию. Предположительно, под этим подразумевается GetNetworkRequestedState [SWS_ANM_01008].
  • NmPnResetTime должно быть больше, чем NmMsgCycleTime.

Каждый бит области PN-Info соответствует частичной сети. Опционально NM отфильтровывает сообщения, не содержащие установленного в 1 бита сконфигурированного для блока управления PNC SWS NM с. 25. В том же месте упоминаются методы RequestNetwork/ReleaseNetwork приложения Adaptive Application. В R25-11 их место занимает SetNetworkRequestedState, вызываемый компонентом State Management [SWS_ANM_01009].

При изменении принятых полезных данных NM вызывает уведомление SWS NM с. 23. Полезные данные и PNI не перекрываются SWS NM с. 21. Доступ приложений к полезным данным больше не предусмотрен. Остается открытым вопрос, должен ли он в будущем осуществляться через State Management SWS NM с. 8.

Диаграмма деятельности: цепочка решений при приеме сообщения NM с Partial Networking, от переключателя NmPnEnabled до уведомления. Источники: SWS NM с. 24, SWS NM с. 25, SWS NM с. 23

Привязка к экземпляру и конфигурация в манифесте

В метамодели манифеста NmInstantiation содержит элементы NmNetworkHandle TPS Manifest с. 621. NetworkHandlePortMapping связывает прототип порта в Process с NmNetworkHandle TPS Manifest с. 620. Порт типизирован с помощью NetworkManagementPortInterface, специализации PortInterface TPS Manifest с. 263. Через этот порт конструктор получает свой InstanceSpecifier [SWS_ANM_01001].

С State Management модуль NM связан в трех местах:

  • NmHandleToFunctionGroupStateMapping через mappingDirection отображает состояния дескриптора на Function-Group-States TPS Manifest с. 624.
  • SmInteractsWithNmMapping связывает StateManagementNmActionItem (nmStateRequest) с дескриптором TPS Manifest с. 874.
  • NmInteractsWithSmMapping соединяет дескриптор с StateManagementStateRequest TPS Manifest с. 875.

Диаграммы SWS State Management показывают два дополнительных правила. Один дескриптор может влиять на несколько автоматов состояний SWS SM с. 53. На установку дескриптора автоматами состояний, напротив, действует ограничение SWS SM с. 66.

Поведение при ошибке

Ошибки передаются как ara::core::Result. Они относятся к домену NmErrorDomain [SWS_ANM_01101], который возвращает GetNmDomain [SWS_ANM_01109]. NmErrc определяет kServiceNotAvailable = 1 и kInvalidHandler = 2 [SWS_ANM_01111]. Ошибки распределяются следующим образом:

  • Геттеры и сеттеры сообщают kServiceNotAvailable [SWS_ANM_01007] [SWS_ANM_01008] [SWS_ANM_01009].
  • Функции регистрации сообщают kInvalidHandler [SWS_ANM_01010] [SWS_ANM_01012] [SWS_ANM_01014] [SWS_ANM_01015].
  • Функции отмены регистрации имеют тип void noexcept и не содержат пути обработки ошибок [SWS_ANM_01011] [SWS_ANM_01013].

Если геттер возвращает ошибку, Result не содержит NetworkStateType [SWS_ANM_01007]. Поэтому такую ошибку не следует интерпретировать как kNoCom. Интерпретация: kServiceNotAvailable, вероятно, указывает на то, что работающий на основе демона кластер NM SWS NM с. 13 в данный момент недоступен.

Для использования исключений с помощью MakeErrorCode создается ErrorCode [SWS_ANM_01110]. ThrowAsException генерирует из этого NmException [SWS_ANM_01108] [SWS_ANM_01100] [SWS_ANM_01102]. Имя домена и текст сообщения возвращают Name и Message [SWS_ANM_01106] [SWS_ANM_01107].

На уровне протокола NM спроектирован как отказоустойчивый. Если в Prepare Bus-Sleep он все еще принимает пакет NM, он возвращается в Network Mode для максимально быстрого восстановления связи SWS NM с. 19. Если пакеты больше не поступают вовсе, таймер переводит все узлы в спящий режим SWS NM с. 13.

Диаграмма деятельности: порядок обработки вызывающей стороной результатов функций NetworkHandle вплоть до исключения. Источники: [SWS_ANM_01111], [SWS_ANM_01109], [SWS_ANM_01108], [SWS_ANM_01009], [SWS_ANM_01010], [SWS_ANM_01013]
