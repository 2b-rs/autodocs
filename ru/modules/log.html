Роль ara::log и интеграция в платформу

Functional Cluster Log and Trace предоставляет для Adaptive Applications и служб платформы интерфейсы, с помощью которых они передают информацию журнала на коммуникационную шину, в консоль, в файловую систему или в ARTI-Trace. Для каждого уровня важности существует собственный метод (SWS LogAndTrace с. 8). В центре находится класс ara::log::Logger. Он представляет контекст логгера внутри Application process (SWS LogAndTrace с. 68). Отдельные сообщения формируются как ara::log::LogStream (SWS LogAndTrace с. 57). API спроектирован независимо от нижележащего Logging back-end (SWS LogAndTrace с. 11).

Интерфейс Logger используется в масштабах всей платформы. Execution Management, Diagnostic Management, Persistency, Network Management и другие кластеры указывают его как требуемый интерфейс (SWS LogAndTrace с. 13, EXP SWArchitecture с. 58). Log and Trace сам использует синхронизацию времени для определения временных меток (SWS LogAndTrace с. 14). Данные трассировки от компонентов, не относящихся к AUTOSAR, таких как события ядра, поступают в кластер через адаптер OS/ara::log (SWS LogAndTrace с. 8, SWS LogAndTrace с. 38).

Контекстная диаграмма: приложения и кластеры платформы используют Logger; Log and Trace получает временные метки от Time Synchronization и обслуживает консоль, файл, сеть и ARTI. Источники: SWS LogAndTrace с. 13, SWS OperatingSystemInterface с. 21, SWS LogAndTrace с. 14

От инициализации до зарегистрированного контекста логгера

Перед каждым использованием любого API ara::log фреймворк логирования должен быть инициализирован через ara::core::Initialize(), иначе поведение не определено. Будет ли инициализировано логирование, определяет параметр манифеста Executable.loggingBehavior (SWS LogAndTrace с. 17). Кроме того, фреймворк должен быть инициализирован, если Executable имеет PortPrototype типа LogAndTraceInterface (SWS LogAndTrace с. 22).

Затем приложение регистрирует один или несколько контекстов. CreateLogger существует в трех вариантах:

  • с ID контекста, описанием и уровнем логирования по умолчанию [SWS_LOG_00021],
  • без уровня логирования [SWS_LOG_00263],
  • с ara::core::InstanceSpecifier; здесь логгер определяется из манифеста [SWS_LOG_00256].

Для строковых вариантов действует следующее: без модели стандартным приемником является консоль [SWS_LOG_00021]. В варианте с InstanceSpecifier параметры CtxID, AppID, ECU ID и Session ID берутся из модели, и устанавливаются соединения с приемниками (SWS LogAndTrace с. 29).

Контекст при создании автоматически регистрируется в бэкенде логирования и отменяет регистрацию при завершении процесса. Поэтому приложения не должны конструировать Logger самостоятельно (SWS LogAndTrace с. 68); конструктор по умолчанию удален [SWS_LOG_00259]. CreateLogger возвращает ссылку на экземпляр, принадлежащий фреймворку (SWS LogAndTrace с. 22). При вызове Log and Trace также сообщает, используется ли локальная или глобально синхронизированная база времени (SWS LogAndTrace с. 36). При ara::core::Deinitialize() фреймворк передает все остающиеся в буфере сообщения в приемники (SWS LogAndTrace с. 18).

Диаграмма последовательности: инициализация, регистрация контекста через CreateLogger и вывод оставшихся буферов при Deinitialize. Источники: [SWS_LOG_00021], SWS LogAndTrace с. 17, SWS LogAndTrace с. 18, SWS LogAndTrace с. 36

Построение немоделированных сообщений с помощью LogStream

Немоделированные сообщения в протоколе DLT называются «verbose». Они создаются по шаблону строителя (SWS LogAndTrace с. 24, SWS LogAndTrace с. 23). Каждый метод входа возвращает объект LogStream, который принимает аргументы через operator<< (SWS LogAndTrace с. 25). LogLevel представляет собой enum на основе std::uint8_t, содержащий среди прочего kFatal (0x01), kError (0x02) и kWarn (0x03) [SWS_LOG_00018].

Операторы вставки существуют для арифметических типов, bool, строк и нескольких типов ara::core [SWS_LOG_00040] [SWS_LOG_00062] [SWS_LOG_00124] [SWS_LOG_00128]. Для char перегрузка намеренно отсутствует; отдельный символ можно логировать как ara::core::StringView (SWS LogAndTrace с. 24). Пользовательские типы поддерживаются с помощью дополнительных перегрузок operator<< (SWS LogAndTrace с. 57). Кроме того, к сообщению можно прикрепить:

  • теги [SWS_LOG_00132]; они отображаются в том порядке, в котором были добавлены (SWS LogAndTrace с. 26),
  • место в исходном коде [SWS_LOG_00129],
  • уровень конфиденциальности [SWS_LOG_00258].

Сообщение отправляется деструктором при выходе из области видимости [SWS_LOG_00262] или явно через Flush. Flush передает текущий буфер дальше и начинает новый поток сообщений [SWS_LOG_00039]. Это необходимо, только если тот же объект продолжает использоваться в области видимости (SWS LogAndTrace с. 59). LogStream нельзя копировать [SWS_LOG_00174]; конструктор перемещения служит только для возврата из фабричных функций [SWS_LOG_00176]. Операторы вставки не являются потокобезопасными [SWS_LOG_00040], в отличие от методов логгера [SWS_LOG_00064]. Поэтому в многопоточных приложениях не следует хранить глобальные объекты LogStream (SWS LogAndTrace с. 26).

Диаграмма последовательности: сообщение Verbose создается через точку входа, заполняется и передается фреймворку через Flush или деструктор. Источники: [SWS_LOG_00067], [SWS_LOG_00039], [SWS_LOG_00262], SWS LogAndTrace с. 57

Диаграмма состояний: жизненный цикл объекта LogStream от создания до передачи; Flush возвращает в состояние заполнения. Источники: [SWS_LOG_00039], [SWS_LOG_00262], SWS LogAndTrace с. 23

Моделированные сообщения, TraceSwitch и ARTI

Моделированные сообщения в протоколе DLT называются «non-verbose». Их статические части находятся в модели ARXML, благодаря чему по сети передается меньше данных (SWS LogAndTrace с. 23). Они отправляются одним вызовом Logger::Log [SWS_LOG_00204]. Если уровень не достигает порогового значения, вызов после передачи параметров обходится всего в одну проверку if (PlatformDesign с. 74). С помощью LogWith можно дополнить такие атрибуты, как Location или Tag [SWS_LOG_00133] (SWS LogAndTrace с. 34).

Типы и переменные constexpr для сообщений создаются генератором ara::log Modeled Message Generator из LogAndTraceMessageCollectionSet и DltLogSink (SWS LogAndTrace с. 29). Для каждого Collection-Set создается файл messages.h в пространстве имен, сформированном из SymbolProps (SWS LogAndTrace с. 31). Этот файл должен быть явно подключен (SWS LogAndTrace с. 34).

Контекстная диаграмма: сгенерированные из модели заголовки (сообщения, TraceSwitch, специализации TraceArti) и их использование приложением. Источники: SWS LogAndTrace с. 31, SWS LogAndTrace с. 39, SWS LogAndTrace с. 42

Для трассировки TraceSwitch перенаправляет моделированные сообщения в зависимости от Executable.traceSwitchConfiguration: логгеру, в ara::log::ext::TraceArti, обоим или никому. Решение принимается во время компиляции (SWS LogAndTrace с. 39, SWS LogAndTrace с. 40). Статически можно дополнительно подключить ARTI: если DltLogChannel.logTraceLogMode установлено в kArti, Logger::Log вызывает функцию TraceArti, причем до форматирования и фильтрации (SWS LogAndTrace с. 42).

TraceArti не является интерфейсом приложения; только фреймворк вызывает его внутри [SWS_LOG_20000] (SWS LogAndTrace с. 90). В отношении заголовочного файла источники расходятся: в документе указан ara/log/trace_arti.h (SWS LogAndTrace с. 39), тогда как в требовании для R25-11 — apext/log/trace_arti.h. Определяющим является требование [SWS_LOG_20000].

Диаграмма деятельности: маршрутизация вызова Log через TraceSwitch (время компиляции), а также через приемник ARTI и фильтр (время выполнения). Источники: SWS LogAndTrace с. 42, SWS LogAndTrace с. 39, [SWS_LOG_00204]

Аргументы, указания по форматированию и их представление в приемниках

Arg упаковывает значение вместе с необязательным именем, необязательной единицей измерения и указанием по форматированию [SWS_LOG_00201]. В консоли значение и атрибуты отображаются как единый аргумент [SWS_LOG_00203]. Указания по форматированию предоставляют вспомогательные функции, такие как Dflt, Hex, Bin, DecFloat или AutoFloatMax [SWS_LOG_00208] [SWS_LOG_00209] [SWS_LOG_00215] [SWS_LOG_00217] [SWS_LOG_00224]. Они устанавливают поля fmt и precision структуры Format [SWS_LOG_00225] [SWS_LOG_00226]. Учитывать ли эти указания, приложение для просмотра решает самостоятельно (SWS LogAndTrace с. 27).

Для консоли действует следующее (SWS LogAndTrace с. 43, SWS LogAndTrace с. 44):

  • Имя и единица измерения добавляются через двоеточие, например speed:42.1:km/h.
  • bool отображается как 0 или 1.
  • Необработанные данные отображаются в виде шестнадцатеричных октетов, разделенных апострофами.
  • Длительности отображаются в виде целого числа с единицей SI, например 42ns.

В привязке DLT уровни логирования отображаются 1:1 (SWS LogAndTrace с. 44). bool становится BOOL, строки — STRG с UTF-8, диапазоны байтов — RAWD (SWS LogAndTrace с. 45).

Конфигурация манифеста и связь с экземпляром

Машинозависимые настройки собирает LogAndTraceInstantiation. Каждый процесс передает через Execution Manifest параметры Application ID, описание, уровень логирования по умолчанию, режим логирования и при необходимости путь к файлу (SWS LogAndTrace с. 18). Application ID берется из DltApplication.applicationId. За ее уникальность в пределах ECU отвечает интегратор (SWS LogAndTrace с. 19). Context ID, напротив, не моделируется; разработчик назначает ее уникальной в пределах процесса (SWS LogAndTrace с. 21).

Режим логирования соответствует category элемента DltLogSink (SWS LogAndTrace с. 20):

  • DLT_LOGSINK_FILE выбирает вывод в файл (SWS LogAndTrace с. 44). Ее path предназначен только для разработки и интеграции, но не для серийного производства (SWS LogAndTrace с. 21).
  • DLT_LOGSINK_NETWORK или DLT_LOGSINK_DLT выбирают привязку DLT (SWS LogAndTrace с. 44).

Выход Ethernet настраивается PlatformModuleEthernetEndpointConfiguration, на которую указывает DltLogSink (SWS LogAndTrace с. 21). Во время развертывания DltLogSinkToPortPrototypeMapping отображает PortPrototype в контексте Process на DltLogSink (SWS LogAndTrace с. 28). Если указана ссылка на timeBaseResource, каждое сообщение DLT содержит метку времени (SWS LogAndTrace с. 36).

Во время выполнения SetThreshold устанавливает пороговое значение логгера [SWS_LOG_00255]. IsEnabled перед ресурсоемкой подготовкой данных проверяет, активен ли уровень [SWS_LOG_00070]. Интерпретация: IsEnabled, вероятно, отражает значение, установленное через SetThreshold. RegisterConnectionStateHandler регистрирует обратный вызов для изменений состояния соединения; активен только последний зарегистрированный обратный вызов [SWS_LOG_00205] [SWS_LOG_00265].

Контекстная диаграмма: цепочка модели от Executable через порт и сопоставление до приемника, инстанцирования и ECU. Источники: SWS LogAndTrace с. 28, SWS LogAndTrace с. 21, SWS LogAndTrace с. 36

Поведение при ошибке

Принцип: ошибки во фреймворке логирования или в системе не должны нарушать работу приложения. Затронутые вызовы незаметно отбрасываются; поэтому интерфейсы не предусматривают ни возвращаемых значений, ни исключений (SWS LogAndTrace с. 22). Соответственно, функции noexcept [SWS_LOG_00064]. При высокой одновременной нагрузке Log and Trace выполняет внутреннюю буферизацию во избежание потери данных (SWS LogAndTrace с. 37). Отдельные случаи ошибок:

  • Отсутствие инициализации: поведение не определено (SWS LogAndTrace с. 17).
  • Логгер без привязки к модели: вызов Log для такого логгера игнорируется (SWS LogAndTrace с. 29).
  • Сообщение без аргументов: оно отбрасывается (SWS LogAndTrace с. 23).
  • Неразрешимый InstanceSpecifier: если его невозможно разрешить в модели Executable или он указывает на элемент, отличный от PortPrototype, возникает InstanceSpecifierMappingIntegrityViolation [SWS_LOG_00256].
  • Ill-formed во время компиляции: неподходящие аргументы для Log [SWS_LOG_00204], непригодные типы для Arg [SWS_LOG_00201] или тип для WithPrivacy, который не является ни целочисленным, ни enum [SWS_LOG_00258], делают программу некорректной (ill-formed).
  • Состояние соединения: ClientState::kUnknown сообщает о еще не работающем бэкенде DLT, kNotConnected — об отсутствии удаленного клиента [SWS_LOG_00098]. Интерпретация: приложения, по-видимому, могут отложить обширный вывод диагностических данных до kConnected.
  • ~Logger: деструктор помечен как небезопасный относительно исключений [SWS_LOG_00260].
