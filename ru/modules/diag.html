Роль диагностического модуля

ara::diag — это интерфейс приложений Diagnostic Manager (DM): приложения предоставляют диагностические функции, в то время как DM координирует трафик UDS и SOVD, состояние разговора и обработку событий/DTC. Экземпляр Diagnostic Server создается со своими собственными ресурсами для каждого DiagnosticContributionSet; однако несколько экземпляров совместно используют транспортный уровень UDS [SWS_DM_00420]. Это означает, что API не является произвольным клиентом UDS, а страницей обратного вызова и состояния привязанного к конфигурации Diagnostic Server.

Путь запроса и ограничения сервера

Диспетчер транспорта назначает запросы UDS с физическим адресом именно серверу с совпадающим диагностическим адресом, тогда как функциональные запросы сопоставляются всем соответствующим экземплярам сервера [SWS_DM_00390] [SWS_DM_00391]. DoIP — возможный транспортный контекст; спецификация требует DoIP поддержки SWS Diagnostics §7.1.2 «DoIP» в соответствии с ISO 13400-2 при соответствующей настройке. Обработка UDS затем запускается как диагностический диалог и, в зависимости от службы, вызывает специализированные или общие ara::diag интерфейсы.

Transport Manager и Diagnostic Server сопоставляют сообщения UDS по адресу; специфичная для приложения обработка происходит в контексте Server. Источники: SWS Diagnostics §7.1.3 «Dispatching of UDS Requests», SWS Diagnostics §7.3.1 «Interaction between DM and applications».

Разговор, доступ и обслуживание услуг

Conversation представляет диалог времени выполнения клиента, идентифицируемого по исходному адресу и глобальному каналу с Diagnostic Server [SWS_DM_00421]. Там видны сессия, уровень безопасности и активность. Класс SecurityAccess предоставляет обратные вызовы начального значения/ключа для UDS 0x27; GenericUDSService — это точка расширения для настроенных пользовательских служб диагностики.

Последовательность иллюстрирует определённое спецификацией сопоставление UDS 0x27 с GetSeed и CompareKey. Источники: SWS Diagnostics §7.3.2.8.9 «SecurityAccess», [SWS_DM_00764], [SWS_DM_00765].

Путь хранения событий и ошибок

Для мониторинга ошибок приложение сообщает о квалифицированных действиях монитора через Monitor. Condition и OperationCycle обеспечивают условия окружающей среды и цикла соответственно. DTCInformation предоставляет SWS Diagnostics §7.3.4 «Diagnostic Event Management» результирующий статус DTC, информацию о сохранении и очистке.

Связь обработки Event: Conditions управляют оценкой Monitor; действия Monitor и Operation-Cycles влияют на состояния Event и DTC. Источники: SWS Diagnostics §7.3.4.1.2 «Monitors», SWS Diagnostics §7.3.4.3 «Operation Cycles Management», SWS Diagnostics §7.3.4.4 «Event memory». Частичная интерпретация: представление объединяет несколько определённых спецификацией обязанностей в совместное взаимодействие объектов.

Поведение при ошибке

Специфичный для приложения UDS-сервис сообщает о предметно отрицательной обработке сервиса через канал ошибок своего Future с помощью ErrorCode из DiagUdsNrcErrorDomain либо DiagUdsNrcErrc. Diagnostic Server выводит из этого однобайтный NRC и отправляет отрицательный UDS-ответ; для GenericUDSService::HandleMessage явно предусмотрен применимый NRC. Возвращаемые значения, принимаемые DM, находятся в диапазоне от 0x01 до 0xFE. SWS Diagnostics §7.3.2.6.1 «NRCs created by application» [SWS_DM_02059] [SWS_DM_02060] [SWS_DM_00618]

Если обработка занимает больше времени, чем позволяет таймер P2/P2* текущего сеанса, диагностический сервер генерирует отрицательный ответ 0x78 (kRequestCorrectlyReceivedResponsePending). Он может повторять этот отзыв до конца своей службы; Однако если их количество достигает настроенного предела maxNumberOfRequestCorrectlyReceivedResponsePending, он должен прервать внутреннюю или внешнюю обработку и отправить 0x10 (kGeneralReject). SWS Diagnostics §7.3.2.6 «UDS response handling» [SWS_DM_00368] [SWS_DM_00369] [SWS_DM_00526]

Diagnostic Server преобразует ошибку NRC приложения в отрицательный ответ UDS и самостоятельно управляет границами Response-Pending. Источники: SWS Diagnostics §7.3.2.6 «UDS response handling», SWS Diagnostics §7.3.2.6.1 «NRCs created by application», [SWS_DM_00368], [SWS_DM_00369], [SWS_DM_02060].

В случае ошибок локального API DiagErrorDomain привязан к DiagErrc через его псевдоним Errc. К ним относятся, помимо прочего, kConfigurationMismatch, kReportIgnored, kInvalidArgument, kNotOffered, kBusy, kFailed, kMemoryError и kServiceNotAvailable. Спецификация отделяет путь предложения от этого: второй вызов Offer() возвращает DiagOfferErrc::kAlreadyOffered. [SWS_DM_00514] [SWS_DM_00518] [SWS_DM_00619]

В пути событий Monitor::Offer() возвращает ту же ошибку предложения; ReportMonitorAction(), однако, не имеет возвращаемого значения. MonitorAction, который не поддерживается для настроенного типа устранения дребезга, указывается как UnexpectedMonitorActionHandlingViolation. Если интерфейс ara::diag, необходимый для обработки услуги, не предлагается или больше не предлагается, DM отвечает тестеру 0x94 (kResourceTemporarilyNotAvailable). [SWS_DM_01088] [SWS_DM_00543] [SWS_DM_01257]

На границе транспорта UDS реализация транспорта через UdsTransportProtocolMgr::TransmitConfirmation подтверждает окончательный результат сети: при непередаваемом ответе UDS результатом является kTransmitFailed, в противном случае — kTransmitOk. Тем самым ошибка передачи отделяется от отрицательного ответа UDS. SWS Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer» [SWS_DM_00350] [SWS_DM_00351] [SWS_DM_00312]
