class ara::log::LogStream

[SWS_LOG_00173] Upstream: RS_LT_00003, RS_LT_00046

class LogStream final {...};

Represents a Log message, allowing stream operators to be used for appending data. Note: Normally Application processes would not use this class directly. Instead one of the log methods provided in the main Logging API shall be used. Those methods automatically setup a temporary object of this class with the given log severity level. The only reason to use this class directly is, if the user wants to hold a ara::log::LogStream object longer than the default one-statement scope. This is useful in order to create log messages that are distributed over multiple code lines. See the ara::log::LogStream::Flush method for further information. Once this temporary object gets out of scope, its destructor takes care that the message buffer is ready to be processed by the Logging framework. Besides the existing supported operator<< overloads for ara::log::LogStream it can be easily extended for other derived types by providing a stream operator that makes use of already supported types.

Example: struct MyCustomType { int8_t foo; ara::core::String bar; };

LogStream& operator<<(LogStream& out, const MyCustomType& value) { return (out << value.foo << value.bar); }

// Producing the output "42 the answer is." Logger& ctx0 = CreateLogger("CTX0", "Context Description CTX0"); ctx0.LogDebug () << MyCustomType{42, " the answer is."};

Puffert Protokolldaten über Stream-Operatoren und übergibt formatierte Nachrichten an das Logging-Framework.

Die Klasse ara::log::LogStream repräsentiert eine formatierbare Protokollnachricht, deren interner Puffer über Stream-Operatoren schrittweise mit Daten und Metadaten befüllt wird. Instanzen werden typischerweise temporär über Logging-Methoden bezogen und leiten den erfassten Inhalt beim Verlassen des Gültigkeitsbereichs über den Destruktor automatisch an das Logging-Framework weiter [SWS_LOG_00262]. Für mehrzeilige oder wiederverwendete Nachrichten kann die Weiterleitung explizit über Flush() ausgelöst werden [SWS_LOG_00039]. Als zentrale Randbedingung ist die Klasse nicht threadsicher und unterbindet Kopiervorgänge vollständig.

Kontext

Die Klasse ara::log::LogStream repräsentiert eine formatierbare Protokollnachricht im adaptiven Logging-Subsystem. Sie stellt eine nachrichtenbasierte Pufferschnittstelle bereit, die über überladene Stream-Operatoren das schrittweise Anhängen heterogener Nutzdaten an einen internen Puffer ermöglicht.

Im regulären Anwendungsfall interagieren Anwendungsprozesse nicht direkt über eine explizite Instanziierung mit LogStream. Stattdessen stellt die Haupt-Logging-API (beispielsweise über Logging-Methoden wie LogDebug()) temporäre Instanzen dieser Klasse bereit, die bereits mit dem geforderten Severity-Level initialisiert sind. Der einzige vorgesehene Grund für das Halten eines LogStream-Objekts über den standardmäßigen Ein-Anweisungs-Gültigkeitsbereich (One-Statement-Scope) hinaus besteht darin, Protokollnachrichten über mehrere Codezeilen hinweg zusammenzusetzen. Sobald das Objekt seinen Gültigkeitsbereich verlässt oder explizit geleert wird, wird der Pufferinhalt an das Logging-Framework zur weiteren Verarbeitung übergeben.

Lebenszyklus

Die Erzeugung von LogStream-Instanzen erfolgt primär als temporäres Objekt über Factory-Methoden der Haupt-Logging-API. Zur effizienten Bereitstellung deklariert die Klasse einen Move-Konstruktor als noexcept [SWS_LOG_00176]. Dieser Move-Konstruktor wird typischerweise lediglich deklariert und nicht definiert, was C++14-konformen Compilern erlaubt, Return Value Optimization (RVO) bei der Rückgabe aus Factory-Funktionen zu nutzen [SWS_LOG_00176]. Eine Duplizierung oder Verschiebezuweisung von Instanzen ist strikt ausgeschlossen: Der Kopierkonstruktor [SWS_LOG_00174], der Kopierzuweisungsoperator [SWS_LOG_00175] und der Move-Zuweisungsoperator [SWS_LOG_00177] sind gelöscht (=delete).

Das Lebensende wird durch den Destruktor ~LogStream() verwaltet [SWS_LOG_00262]. Verlässt das Objekt seinen Gültigkeitsbereich (beispielsweise am Ende eines Funktionsblocks oder einer Anweisung), sorgt der Destruktor intern dafür, dass der Pufferinhalt zur Verarbeitung an das Logging-Framework weitergeleitet wird [SWS_LOG_00039], [SWS_LOG_00262].

Wird eine LogStream-Instanz im selben Gültigkeitsbereich für mehrere aufeinanderfolgende Nachrichten wiederverwendet, muss die Elementfunktion Flush() aufgerufen werden [SWS_LOG_00039]. Wichtig ist hierbei, dass Flush() den Puffer nicht leert, sondern die aktuellen Daten an das Logging-Framework sendet und unmittelbar einen neuen Nachrichtenstrom initiiert [SWS_LOG_00039].

Bezüglich der Nebenläufigkeit sind sämtliche Elementfunktionen als nicht threadsicher spezifiziert ([SWS_LOG_00039], [SWS_LOG_00040], [SWS_LOG_00129]). Ein LogStream-Exemplar darf daher nicht ohne externe Synchronisation von mehreren Threads parallel verwendet werden.

Nutzungspfad

Ein typischer Protokollierungsablauf umfasst die folgenden Phasen:

  1. Stream-Bereitstellung: Der Anwendungsprozess ruft eine Logging-Methode auf, welche eine temporäre LogStream-Instanz erzeugt und via RVO zurückgibt [SWS_LOG_00176].
  2. Metadaten-Anreicherung: Vor oder während der Dateneingabe können optionale Attribute über Methodenchaining angefügt werden, darunter Quellcode-Orte via WithLocation(file, line) [SWS_LOG_00129], Tags via WithTag(tag) [SWS_LOG_00132] oder Vertraulichkeitsstufen via WithPrivacy(value) [SWS_LOG_00258]. Jede dieser Methoden gibt eine Referenz auf *this zurück.
  3. Datenbefüllung: Über überladene Operatoren operator<< werden Nutzdaten in den internen Puffer geschrieben. Die Schnittstelle unterstützt Standardtypen wie boolesche Werte [SWS_LOG_00040], Ganzzahlen verschiedener Breiten [SWS_LOG_00041], [SWS_LOG_00044], Gleitkommazahlen [SWS_LOG_00049], Zeichenketten und String-Ansichten [SWS_LOG_00051], [SWS_LOG_00062], Byte-Sequenzen über core::Span<const core::Byte> [SWS_LOG_00128] sowie strukturierte Argumente über Argument<T> [SWS_LOG_00203]. Zudem kann der Operator für benutzerdefinierte Typen erweitert werden.
  4. Übergabe an das Framework: Beim Verlassen des Gültigkeitsbereichs leitet der Destruktor die Nachricht weiter [SWS_LOG_00262]. Soll die Instanz für weitere Nachrichten bestehen bleiben, wird Flush() explizit aufgerufen [SWS_LOG_00039].

Fehlerszenarien

Die Klasse folgt einem strikten No-Exception-Design. Sämtliche Elementfunktionen, einschließlich der Stream-Operatoren ([SWS_LOG_00040] bis [SWS_LOG_00051], [SWS_LOG_00062], [SWS_LOG_00128], [SWS_LOG_00203]), WithLocation() [SWS_LOG_00129], WithTag() [SWS_LOG_00132], WithPrivacy() [SWS_LOG_00258], Flush() [SWS_LOG_00039] und des Destruktors [SWS_LOG_00262], sind als noexcept deklariert und ausnahmesicher („exception safe“).

Fehlerbedingungen und Verwendungsrisiken beschränken sich auf die folgenden Szenarien:

  • Typfehler bei WithPrivacy: Das Template WithPrivacy<T> verlangt zwingend, dass T ein ganzzahliger Typ oder ein Aufzählungstyp ist. Wird die Funktion mit einem abweichenden Typ instanziiert, ist das Programm fehlerhaft (ill-formed) und führt zu einem Übersetzungsfehler [SWS_LOG_00258]. Zudem werden nur die niederwertigsten 8 Bit des übergebenen Werts genutzt, höherwertige Bits werden ignoriert [SWS_LOG_00258].
  • Fehlende Thread-Sicherheit: Da LogStream als nicht threadsicher definiert ist ([SWS_LOG_00039], [SWS_LOG_00040]), führen konkurrierende Lese- oder Schreiboperationen auf derselben Instanz ohne externe Synchronisation vermutlich zu Dateninkonsistenzen oder Pufferbeschädigungen (Interpretation). Question Q-30a5037999c96fa2 (open)
  • Pufferübernahme bei Flush: Da Flush() den Puffer nicht physisch leert, sondern lediglich den aktuellen Inhalt an das Logging-Framework übergibt [SWS_LOG_00039], muss bei Wiederverwendung bedacht werden, dass semantisch eine neue Nachricht begonnen wird.
