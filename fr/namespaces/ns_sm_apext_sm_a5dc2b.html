Contexte

Le namespace apext::sm définit des interfaces d'extension spécifiques à la plateforme (Platform Extension Interfaces) pour le Functional Cluster State Management au sein de l'AUTOSAR Adaptive Platform (AUTOSAR_AP_SWS_StateManagement Anhang C « Platform Extension Interfaces »). Conformément à la spécification, les Platform Extension Interfaces sont destinées à être fournies ou utilisées par l'OEM ou l'intégrateur système afin d'étendre de manière ciblée les fonctionnalités de la plateforme (AUTOSAR_AP_SWS_StateManagement Anhang C « Platform Extension Interfaces »). Au cœur de apext::sm se trouve la coordination des états d'énergie du système avec le système d'exploitation sous-jacent (Operating System, OS). À cette fin, la classe PowerStateInterface sert d'intermédiaire entre la gestion des états à l'échelle de la plateforme et les commandes d'énergie spécifiques au système d'exploitation.

Trois composants participent principalement à cette coordination : l'OEM ou intégrateur de plateforme, qui implémente ou intègre les interfaces d'extension, le système d'exploitation (tel qu'un noyau Linux avec ses modes d'énergie natifs) ainsi que le Functional Cluster State Management avec sa machine d'états centrale Controller (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »). En plus de l'alignement des états d'énergie, l'interface permet également la transmission directe de signaux de réveil proches du matériel à State Management via l'alias de fonction WakeUpHandler ([SWS_SM_71004]).

Cycle de vie

L'intégration des extensions de plateforme s'effectue via le fichier d'en-tête apext/sm/power_state_interface.h ainsi que le fichier d'en-tête de redirection apext/sm/sm_fwd.h ([SWS_SM_71002], [SWS_SM_71004]). L'instanciation et la durée de vie de l'implémentation de PowerStateInterface relèvent des services de base de la plateforme ; la classe devrait être instanciée par l'OEM ou l'intégrateur durant la phase d'initialisation du système afin d'être disponible avant la transition vers des états d'économie d'énergie.

Pour la représentation des états d'énergie du noyau, le namespace définit l'énumération PowerState avec le type de base std::uint32_t ([SWS_SM_71002]). Les valeurs de l'énumération reflètent les états d'énergie Linux standardisés du point de vue du noyau :

  • kPmSuspendToIdle (valeur 1, dérivée de PM_SUSPEND_TO_IDLE),
  • kPmSuspendToRam (valeur 2, dérivée de PM_SUSPEND_TO_RAM),
  • kPmHibernation (valeur 3, dérivée de PM_HIBERNATION),
  • kPmOff (valeur 4, dérivée de PM_OFF) ([SWS_SM_71002]).

Concernant la concurrence, il est explicitement spécifié pour la fonction de rappel WakeUpHandler (using WakeUpHandler = std::function<void(void)>;) qu'elle n'est pas thread-safe (not thread-safe) ([SWS_SM_71004]). Les appelants issus de l'environnement du système d'exploitation doivent synchroniser l'appel en conséquence.

Parcours d'utilisation

Un cas d'utilisation central de apext::sm est le réveil autonome de la machine depuis un état de veille tel que Suspend-to-RAM (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »). Alors que les applications de contrôle (SMControlApplication) demandent normalement les transitions de manière explicite, State Management peut également réagir de façon autonome à des événements externes (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »).

Le déroulement s'effectue selon les étapes suivantes :

  1. Le système se trouve dans un mode d'économie d'énergie correspondant à un état tel que kPmSuspendToRam ([SWS_SM_71002]).
  2. Un événement matériel ou système externe réveille le système d'exploitation.
  3. Le système d'exploitation signale l'événement, s'il est implémenté, à State Management via l'interface apext::sm::WakeUpHandler (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »).
  4. State Management déclenche alors une séquence de réveil autonome et fait passer la machine d'états Controller dans l'état de réveil défini LeaveSuspend (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state », [SWS_SM_CONSTR_00036]).
  5. Dans cet état, l'entrée configurée LeaveSuspendToRam au sein de ActionList est exécutée ([SWS_SM_CONSTR_00037]), rétablissant ainsi le fonctionnement normal du système sans intervention d'une application de contrôle externe (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »).

Scénarios d'erreur

Lors de l'utilisation et du raccordement des interfaces, des conditions spécifiques de modélisation et d'exécution doivent être respectées :

  • État de réveil manquant dans le manifeste : Pour la StateMachine de type Controller, un état nommé LeaveSuspend doit obligatoirement être configuré à l'issue de la création du manifeste ([SWS_SM_CONSTR_00036]). Si cet état est manquant, State Management ne peut pas exécuter le réveil autonome.
  • Action manquante dans LeaveSuspend : L'état LeaveSuspend doit obligatoirement contenir l'élément LeaveSuspendToRam dans son ActionList ([SWS_SM_CONSTR_00037]). Une configuration incomplète empêche la reprise du fonctionnement conformément aux spécifications.
  • Problèmes de concurrence au niveau de WakeUpHandler : Comme le type WakeUpHandler est normativement spécifié comme non thread-safe ([SWS_SM_71004]), des signalisations simultanées et non coordonnées provenant de plusieurs threads du système d'exploitation ou de pilotes conduisent vraisemblablement à des situations de compétition. Le code intégrateur appelant doit sécuriser l'appel.
  • Interface non implémentée : Le WakeUpHandler est déclaré comme une interface d'intégration optionnelle (« if implemented ») (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 « Autonomous wake-up from suspend state »). Si aucune implémentation n'est fournie par l'OEM, les signaux du système d'exploitation ne peuvent pas être traités de manière autonome.
