Contexte

Dans le module AUTOSAR Adaptive core (Release R25-11), le namespace namespace std occupe une position architecturale particulière. Alors que les types de données et interfaces spécifiques à la plateforme sont déclarés dans le namespace ara::core, l'extension de std fait office de couche d'intégration conforme aux normes dans le système de types et de templates de la bibliothèque standard C++. Selon les exigences de la norme de langage ISO C++, l'extension du namespace standard est exclusivement permise pour les spécialisations explicites de templates de types définis par l'utilisateur.

Les spécialisations contenues dans le module core couvrent deux périmètres d'interface essentiels de la bibliothèque standard C++ :

  • Infrastructure de hachage : spécialisations du template de fonction std::hash pour les classes centrales d'AUTOSAR. En font partie les types de base élémentaires ara::core::Monostate, ara::core::String et ara::core::StringView ainsi que les conteneurs et wrappers génériques ara::core::Optional<T>, ara::core::Variant<...> et ara::core::Vector<T, Allocator>. Ces spécialisations servent vraisemblablement à rendre des types de données issus de ara::core directement utilisables comme clés dans des conteneurs associatifs non ordonnés standard tels que std::unordered_map ou std::unordered_set, sans implémentation manuelle de foncteurs dédiés.
  • Protocole de tuple : spécialisations des templates std::tuple_size et std::tuple_element pour le type de conteneur séquentiel ara::core::Array<T, N>. Ces spécialisations devraient principalement permettre la décomposition structurelle de tableaux via l'interface standardisée de tuple, soutenant ainsi des mécanismes du langage comme les liaisons structurées (structured bindings).

Ces spécialisations permettent de garantir que les types de vocabulaire de l'Adaptive Platform fonctionnent de manière fluide avec les algorithmes standard et les infrastructures STL, sans imposer de ruptures d'interface.

Parcours d'utilisation

Les spécialisations au sein de namespace std ne sont généralement pas utilisées dans les programmes applicatifs via des appels de méthode impératifs directs. Au lieu de cela, elles agissent comme des points de personnalisation déclaratifs (customization points) résolus automatiquement dans le cadre du code générique et des instanciations de templates. Un flux d'utilisation typique comprend l'interaction de plusieurs composants :

  1. Instanciation de classes de base AUTOSAR : une application ou un composant système instancie des structures de données concrètes, par exemple un ara::core::Array<T, N>, un type de chaîne de caractères ara::core::String ou un conteneur d'état générique ara::core::Optional<T>.
  2. Transmission à des conteneurs génériques de la bibliothèque standard : les types sont déclarés en tant que types de clés dans des conteneurs standard. Lors de la définition d'une table de hachage, le conteneur standard fait implicitement appel à la spécialisation std::hash<ara::core::String> ou std::hash<ara::core::Optional<T>>.
  3. Évaluation de la fonction de hachage : au moment de l'exécution, l'opérateur d'appel de fonction operator() de la spécialisation std::hash respective est exécuté. Celui-ci calcule à partir de l'état de l'objet transmis une valeur de hachage de type std::size_t. Pour les types composites tels que ara::core::Vector<T, Allocator> ou ara::core::Variant<...>, le calcul s'effectue en prenant en compte les éléments contenus ou le type actif.
  4. Métaprogrammation et déconstruction : lors de l'utilisation de ara::core::Array<T, N>, le compilateur interroge le nombre fixe d'éléments du tableau via std::tuple_size<ara::core::Array<T, N>>::value. En parallèle, le type d'élément exact à la position I est déterminé au moment de la compilation via std::tuple_element<I, ara::core::Array<T, N>>::type, ce qui autorise une décomposition sûre au niveau des types.

Scénarios d'erreur

Comme la fonctionnalité du namespace repose sur des spécialisations de templates, les scénarios d'erreur et de cas limites se manifestent principalement au moment de la compilation ainsi que lors d'états d'exécution spécifiques :

  • Absence de capacité de hachage des types de données internes : pour des spécialisations paramétriques telles que std::hash<ara::core::Optional<T>> ou std::hash<ara::core::Vector<T, Allocator>>, le calcul présuppose vraisemblablement qu'une spécialisation valide de std::hash existe également pour le type de données contenu T. Si celle-ci fait défaut pour un type défini par l'utilisateur, la compilation s'interrompt avec une erreur d'instanciation.
  • Dépassement de plage pour l'index de tuple : si la spécialisation std::tuple_element<I, ara::core::Array<T, N>> est instanciée avec un index I >= N, le processus de compilation échoue. Conformément à la sémantique standard des tableaux, aucun alias de type n'est défini pour les index en dehors des limites du tableau.
  • Distribution uniforme et collisions de hachage : comme pour toutes les spécialisations de std::hash, l'interface garantit uniquement la cohérence (des objets identiques fournissent des hachages identiques), mais pas l'absence de collision ni la sécurité cryptographique. Les applications ne doivent donc pas utiliser les valeurs de hachage pour des contrôles d'identité critiques pour la sécurité ou comme clés persistantes d'un démarrage de programme à l'autre.
  • Comportement en cas d'états vides : pour des types à occupation optionnelle ou variable tels que ara::core::Optional<T> ou ara::core::Variant<...>, le calcul de hachage doit être bien défini même pour des états vides. La spécialisation pour ara::core::Monostate fournit une valeur de hachage constante qui fait office d'état de base bien défini et empêche tout comportement indéfini.
