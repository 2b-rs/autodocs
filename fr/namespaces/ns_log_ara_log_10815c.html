Permet la création de contextes de journalisation, de flux de messages formatés et la surveillance de l’état du client.

L’espace de noms ara::log fournit des services de journalisation adaptatifs en gérant des enregistreurs de contexte et en émettant des flux de messages typés vers des puits tels que le dorsal DLT ou la console [SWS_LOG_00021]. Les applications obtiennent des enregistreurs via des fonctions de fabrique, préparent des données utiles formatées via des wrappers d’arguments et injectent les données de manière thread-safe dans les messages de journalisation. Contrainte essentielle : la propriété de toutes les instances d’enregistreur reste au framework, tandis que l’enregistrement du gestionnaire d’état de connexion est explicitement non thread-safe [SWS_LOG_00205].

Contexte

L’espace de noms ara::log fournit l’infrastructure centrale de journalisation pour les applications adaptatives. Ses responsabilités principales englobent la gestion des contextes de journalisation via la classe Logger, la génération structurée de messages de journalisation via LogStream ainsi que la transmission typée de données utiles formatées via Argument et Format. Le framework sert de lien entre les appels de journalisation côté application et les puits cibles : le dorsal DLT (Diagnostic Log and Trace) sert de puits principal, son état de connectivité étant représenté par l’énumération ClientState [SWS_LOG_00098]. Si aucun modèle n’est disponible, la console fait office de puits par défaut [SWS_LOG_00021]. Les changements d’état des correspondants externes peuvent être surveillés via des fonctions de rappel du type ConnectionStateHandler [SWS_LOG_00265].

Diagramme de contexte : partenaires d’interaction du framework de journalisation entre l’application, la console, le dorsal DLT et le client externe. Sources : [SWS_LOG_00021], [SWS_LOG_00098], [SWS_LOG_00205].

Cycle de vie

Les instances de Logger ne sont pas construites directement par l’application, mais instanciées par les fonctions de fabrique CreateLogger et enregistrées dans le framework de journalisation [SWS_LOG_00021], [SWS_LOG_00263]. Les relations de propriété sont clairement définies : la propriété reste intégralement au sein du framework de journalisation (« Ownership stays within the Logging framework »), qui renvoie des références (Logger&) à l’appelant [SWS_LOG_00021]. Alternativement, la création peut s’effectuer de manière basée sur un modèle à l’aide d’un ara::core::InstanceSpecifier [SWS_LOG_00256]. Interprétation : puisque le framework conserve la propriété, la durée de vie des enregistreurs enregistrés devrait être liée au processus parent.

En ce qui concerne la concurrence, la création d’enregistreurs via CreateLogger est spécifiée comme étant thread-safe [SWS_LOG_00021]. En revanche, l’enregistrement des gestionnaires d’état de connexion via RegisterConnectionStateHandler est explicitement non thread-safe (« not thread-safe ») [SWS_LOG_00205] ; il doit donc généralement avoir lieu durant la phase d’initialisation avant le démarrage d’activités concurrentes. De plus, un seul gestionnaire peut être actif à la fois ; un nouvel enregistrement remplace immédiatement les rappels précédents [SWS_LOG_00205]. Le cycle de vie de connexion des correspondants externes passe par les étapes kUnknown (dorsal DLT pas encore actif), kNotConnected et kConnected [SWS_LOG_00098].

Parcours d'utilisation

Le déroulement régulier comprend la configuration de la surveillance, l’obtention de l’enregistreur et l’émission de messages formatés :

  • Enregistrement du rappel de connexion au moyen de RegisterConnectionStateHandler [SWS_LOG_00205].
  • Obtention de la référence à Logger via CreateLogger en spécifiant un identifiant de contexte, une description et éventuellement un niveau de gravité par défaut issu de LogLevel (par ex. kWarn ou kInfo) [SWS_LOG_00018], [SWS_LOG_00021].
  • Création d’arguments structurés au moyen de Arg avec adjonction d’un identifiant, d’une unité et d’indications de formatage [SWS_LOG_00201]. Des fonctions d’aide telles que Dflt [SWS_LOG_00208], des formats d’entiers tels que Dec [SWS_LOG_00211], Hex [SWS_LOG_00209], Bin [SWS_LOG_00215] et Oct [SWS_LOG_00213] ainsi que des formats à virgule flottante tels que DecFloat [SWS_LOG_00217], EngFloat [SWS_LOG_00219], HexFloat [SWS_LOG_00221] ou AutoFloat [SWS_LOG_00223] encapsulant les spécificateurs de Fmt sont disponibles à cet effet [SWS_LOG_00206].
  • Transmission de données utiles dans le LogStream via des opérateurs surchargés operator<<, notamment pour LogLevel [SWS_LOG_00063], ara::core::ErrorCode [SWS_LOG_00124], std::chrono::duration [SWS_LOG_00125], ara::core::InstanceSpecifier [SWS_LOG_00126] et des pointeurs const void* [SWS_LOG_00127].

Diagramme de séquence : séquence d’interaction typique lors de l’initialisation, de la création d’enregistreurs et de l’émission de données formatées via LogStream. Sources : [SWS_LOG_00021], [SWS_LOG_00063], [SWS_LOG_00124], [SWS_LOG_00201], [SWS_LOG_00205].

Scénarios d'erreur

Les fonctions de l’espace de noms sont pour la plupart déclarées avec noexcept et offrent des garanties d’absence d’exception, mais sont soumises à des préconditions et à des règles de violation strictes :

  • Violations de manifeste : lors de la création basée sur un modèle d’un enregistreur via CreateLogger(const ara::core::InstanceSpecifier&), des violations d’exécution spécifiques peuvent être déclenchées : InstanceSpecifierMappingIntegrityViolation (le spécificateur ne peut pas être résolu dans le modèle ou ne fait pas référence à un PortPrototype), PortInterfaceMappingViolation (le type de mappage ne correspond pas au PortInterface attendu), ProcessMappingViolation (aucun processus correspondant trouvé) ainsi que InstanceSpecifierAlreadyInUseViolation (le spécificateur est déjà utilisé dans le processus) [SWS_LOG_00256].
  • Typage d’argument non valide : l’appel de Arg est syntaxiquement incorrect (« ill-formed ») si le type T n’est ni un type arithmétique ni bool et ne peut être converti ni en ara::core::StringView ni en ara::core::Span<const ara::core::Byte>. De même, la transmission d’un texte d’unité différent de nullptr unit pour des chaînes de caractères, des plages d’octets (spans) ou des types booléens entraîne une erreur [SWS_LOG_00201].
  • Représentation des erreurs : lors de l’émission d’une instance de core::ErrorCode sur la console, le code d’erreur est formaté de manière spécifique à l’implémentation, le nom de domaine (ErrorCode::Domain().Name()) et le numéro d’erreur intégral devant être inclus [SWS_LOG_00124].

Ce guide est basé sur la spécification du module log dans la version R25-11 de l’Adaptive Platform.

L'énumération ara::log::ClientState représente l'état de connexion actuel d'un client externe au backend DLT [SWS_LOG_00098]. Elle repose sur le type de données std::int8_t et est intégrée via le fichier d'en-tête #include "ara/log/common.h" ou l'en-tête de transmission #include "ara/log/log_fwd.h" [SWS_LOG_00098].

États et sémantique

L'énumération définit trois états de connexion discrets [SWS_LOG_00098] :

  • kUnknown (-1) : le backend DLT n'est pas encore opérationnel ; l'état de connexion effectif ne peut pas être déterminé à ce moment [SWS_LOG_00098].
  • kNotConnected : aucun client externe n'a été détecté [SWS_LOG_00098].
  • kConnected : un client distant est connecté avec succès [SWS_LOG_00098].

Interaction et concurrence

L'énumération sert principalement de paramètre de transmission pour le rappel de fonction ConnectionStateHandler (défini comme std::function<void(ClientState)>), qui est enregistré via ara::log::RegisterConnectionStateHandler [SWS_LOG_00265]. Ce gestionnaire est déclaré comme thread-safe [SWS_LOG_00265]. Interprétation : les gestionnaires enregistrés devraient être appelés de manière asynchrone dès que le backend DLT détecte des changements d'état du client externe.
