Contexte

L'espace de noms ara::rds fournit, au sein d'AUTOSAR Adaptive Platform (release R25-11), des interfaces fonctionnelles et des structures de données pour le streaming de flux de données brutes (Raw Data Streams). La tâche principale du module consiste à transférer et à traiter efficacement sur des connexions réseau tant des flux de données binaires génériques que des datagrammes de flux typés et spécialisés. L'espace de noms s'articule en deux domaines fonctionnels essentiels : le transfert générique client-serveur de flux binaires et le transfert standardisé selon la norme IEEE 1722.

Pour la communication générique, l'espace de noms définit les points de terminaison centraux RawDataStreamServer et RawDataStreamClient. Alors que le serveur est responsable de l'acceptation des connexions réseau entrantes ainsi que de la lecture ou de l'écriture des flux de données, le client agit en tant que contrepartie active pour l'établissement de la connexion puis l'accès en lecture et en écriture. Le résultat d'une opération de lecture est encapsulé dans la classe d'assistance ReadDataResult.

Pour les flux de données multimédias ou temporels critiques, ara::rds met à disposition des composants dédiés au protocole IEEE 1722. Le rôle de l'émission de données est ici assuré par IEEE1722RawDataStreamProducer, tandis que la réception et le filtrage sont effectués par IEEE1722RawDataStreamConsumer. Les datagrammes transmis sont représentés par une série de classes structurées, parmi lesquelles la représentation de base IEEE1722Datagram, des structures d'en-tête communes telles que IEEE1722DatagramAVTPDUCommonHeaderFields et IEEE1722DatagramAVTPDUCommonStreamHeaderFields ainsi que des dérivations spécifiques au format telles que IEEE1722DatagramAAF, IEEE1722DatagramRVF, IEEE1722DatagramCRF, IEEE1722DatagramTSCF, IEEE1722DatagramNTSCF et IEEE1722Datagram61883_IIDC.

Diagramme de contexte : interaction des points de terminaison de communication et des processeurs de flux dans l'espace de noms ara::rds. Sources : aucun enregistrement SWS direct n'est disponible dans la charge utile.

Parcours d'utilisation

Un chemin d'utilisation typique dans l'espace de noms ara::rds diffère selon qu'une connexion de flux point à point générique ou un streaming typé selon l'IEEE 1722 est implémenté. Lors d'un transfert générique, l'application serveur initialise d'abord une instance de RawDataStreamServer et attend les demandes de connexion entrantes. Parallèlement, l'application cliente crée un RawDataStreamClient qui établit une connexion réseau avec le serveur.

Une fois la connexion établie avec succès, l'échange bidirectionnel de données binaires a lieu. Interprétation : la transmission des données binaires sur la connexion réseau devrait reposer sur des protocoles de transport tels que TCP ou UDP, l'échange de données s'effectuant soit par blocs, soit par mise en mémoire tampon. Les opérations de lecture sur les points de terminaison fournissent comme valeur de retour une instance de ReadDataResult, qui met à disposition les données utiles lues ainsi que des informations d'état sur l'opération de lecture. Une fois le transfert de données achevé, les flux et les connexions sont fermés de manière ordonnée par les parties impliquées.

Dans le cas d'application du streaming IEEE 1722, une application émettrice crée le IEEE1722RawDataStreamProducer. Celui-ci est alimenté par des datagrammes structurés dont les en-têtes sont paramétrés via IEEE1722DatagramAVTPDUCommonHeaderFields ou IEEE1722DatagramAVTPDUCommonStreamHeaderFields. Interprétation : les classes de datagrammes spécifiques telles que IEEE1722DatagramAAF (audio) ou IEEE1722DatagramRVF (vidéo) devraient encapsuler des charges utiles AVTP standardisées afin de permettre un streaming audio et vidéo déterministe dans le réseau de bord du véhicule. Du côté récepteur, le IEEE1722RawDataStreamConsumer s'abonne aux flux de données typés et transmet les datagrammes reçus à l'application de traitement.

Scénarios d'erreur

Les situations d'erreur survenant pendant l'initialisation, l'établissement de la connexion ou le transfert de données en cours sont signalées dans l'espace de noms ara::rds par le biais du modèle d'erreur uniforme d'AUTOSAR Adaptive Platform. Celui-ci repose sur l'architecture de domaines ara::core::ErrorDomain et les codes d'erreur de type ara::core::ErrorCode.

L'énumération RdsErrc [SWS_RDS_12367], qui est définie comme enum class RdsErrc : ara::core::ErrorDomain::CodeType et répertorie les états d'erreur spécifiques au module de Raw Data Stream, en constitue un élément central. Les déclarations se trouvent dans le fichier d'en-tête #include "ara/rds/rds_error_domain.h".

Pour associer les codes d'erreur au domaine d'erreur RDS, l'en-tête fournit la fonction GetRdsErrorDomain [SWS_RDS_11298], qui renvoie une référence vers l'objet de domaine global RdsErrorDomain. Afin de générer un code d'erreur complet à partir d'une valeur d'énumération et de données supplémentaires optionnelles, on utilise la fonction MakeErrorCode [SWS_RDS_11299], qui est déclarée comme constexpr ara::core::ErrorCode MakeErrorCode(RdsErrc code, ara::core::ErrorDomain::SupportDataType data) noexcept.

Les scénarios d'erreur typiques comprennent les échecs d'établissement de connexion, les interruptions de connexion pendant le flux de données, les débordements de tampon ou les erreurs de format lors de l'analyse syntaxique d'en-têtes IEEE 1722. Lorsque de tels états se produisent, les méthodes concernées renvoient généralement un ara::core::ErrorCode correspondant. Si des exceptions sont utilisées du côté appelant ou si des erreurs doivent être transférées dans un contexte d'exception, la classe RdsException représente le type d'exception associé pour l'espace de noms.

Ce guide est basé sur la spécification d'AUTOSAR Adaptive Platform release R25-11. Toutes les indications s'appuient sur les définitions et entrées SWS contenues dans la charge utile de la spécification.
