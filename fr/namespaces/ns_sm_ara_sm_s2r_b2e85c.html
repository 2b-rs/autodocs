Contexte

L’espace de noms ara::sm::s2r fournit des interfaces et des mécanismes pour la fonctionnalité Suspend-to-RAM (S2R) au sein du module State Management (SM) (AUTOSAR_AP_SWS_StateManagement §7.5 « Interaction with Suspend-to-RAM Functionality »). L’objectif du fonctionnement Suspend-to-RAM est l’optimisation significative des temps de démarrage et d’arrêt, en plaçant la Machine dans un état qui permet un redémarrage rapide au lieu d’effectuer un shutdown complet suivi d’un démarrage à froid (AUTOSAR_AP_SWS_StateManagement §7.5 « Interaction with Suspend-to-RAM Functionality »).

Le rôle central dans l’espace de noms est assuré par la classe S2RHub (AUTOSAR_AP_SWS_StateManagement §7.5.1 « S2R Hub »). Le hub coordonne la communication avec des instances réparties de S2RSatellite. Les applications dont les unités exécutables sont configurées comme suspendToRamAware intègrent une telle instance de satellite afin d’être notifiées des cycles de suspension et de reprise à venir (AUTOSAR_AP_SWS_StateManagement §7.5 « Interaction with Suspend-to-RAM Functionality », [SWS_SM_00710]). Les processus qui sont déclarés comme suspendToRamNotSupported doivent déjà être arrêtés par des procédures de State Management (p. ex. arrêt des groupes de fonctions concernés) avant la transition du système d’exploitation vers l’état de suspension (AUTOSAR_AP_SWS_StateManagement §7.5 « Interaction with Suspend-to-RAM Functionality »).

Pour le contrôle du S2RHub, il existe deux approches mutuellement exclusives ([SWS_SM_00684]) :

  • Approche StateMachine : le Controller intègre la fonctionnalité S2RHub de manière interne via des objets ActionListItem associés. Dans ce mode de fonctionnement, l’accès à l’API C++ du hub est interdit aux applications de contrôle externes afin d’éviter les conditions de concurrence et les incohérences d’état (AUTOSAR_AP_SWS_StateManagement §7.7 « StateMachine approach », [SWS_SM_00684]).
  • API C++ directe : une application de contrôle externe (telle que SMControlApplication) utilise directement les méthodes de classe du S2RHub (AUTOSAR_AP_SWS_StateManagement §7.5.1 « S2R Hub »).

Diagramme de contexte : interaction entre la commande, S2RHub, S2RSatellite et les applications adaptatives. Sources : AUTOSAR_AP_SWS_StateManagement §7.5.1 « S2R Hub », [SWS_SM_00710].

Cycle de vie

La création et la libération d’instances dans l’espace de noms ara::sm::s2r sont strictement liées à des vérifications d’autorisations (Identity and Access Management, IAM) et à des affectations configurées :

  • Instanciation du hub : dans l’approche StateMachine, State Management crée une instance de S2RHub dès qu’un ActionListItem des types EnterSuspendToRam, EnterSuspendToRamOS ou LeaveSuspendToRam se termine ([SWS_SM_00690]). Pendant l’exécution du constructeur ara::sm::s2r::S2RHub::S2RHub, il est vérifié si le contexte de processus correspond à l’affectation dans SuspendToRamHubMapping.process ([SWS_SM_00706]). Seuls les processus autorisés via SuspendToRamHubMapping sont autorisés à déclencher des opérations de suspension au moyen d’une instance de hub identifiée par SuspendToRamModuleInstantiation ([SWS_SM_00714]).
  • Création du satellite : une instance de satellite est instanciée via la méthode factory ara::sm::s2r::S2RSatellite::Create ([SWS_SM_00716]).
  • Phase d’enregistrement : après sa création, le satellite s’enregistre auprès du hub au moyen de ara::sm::s2r::S2RSatellite::Offer ([SWS_SM_00710]). Le hub valide le contexte de processus par rapport à la configuration dans SuspendToRamSatelliteMapping.process et rejette les tentatives d’enregistrement non autorisées ([SWS_SM_00715]). Dès l’enregistrement réussi, le satellite est considéré comme activement enregistré ([SWS_SM_00710]).
  • Désenregistrement : l’enregistrement actif prend fin dès que le satellite appelle ara::sm::s2r::S2RSatellite::StopOffer ([SWS_SM_00710], [SWS_SM_00713]).

Parcours d'utilisation

Le flux d’utilisation typique comprend la préparation de l’état de repos, le passage en mode de suspension ainsi que le réveil coordonné après la réactivation de la Machine :

  1. Mise à disposition : chaque application compatible S2R initialise son S2RSatellite et signale qu’elle est prête à recevoir au hub via Offer() ([SWS_SM_00710]).
  2. Demande de suspension : pour initier l’état de repos, ara::sm::s2r::S2RHub::RequestToEnterSuspendMode est appelé ([SWS_SM_00701]). Dans l’approche StateMachine, cela s’effectue via le ActionListItem EnterSuspendToRam en utilisant maxActionItemDuration comme paramètre de timeout ([SWS_SM_00689]).
  3. Notification des satellites : le hub adresse tous les satellites activement enregistrés et déclenche leur callback ara::sm::s2r::S2RSatellite::EnterSuspendMode ([SWS_SM_00701], [SWS_SM_00711]). RequestToEnterSuspendMode bloque jusqu’à ce que tous les satellites adressés aient réagi, se soient désenregistrés ou qu’un timeout de communication survienne ([SWS_SM_00702]).
  4. Suspension du système d’exploitation : si tous les satellites sont préparés, la commande de suspension proprement dite du système d’exploitation peut être déclenchée via EnterSuspendToRamOs ([SWS_SM_00692]).
  5. Demande de réveil : après le réveil, la commande appelle ara::sm::s2r::S2RHub::RequestToLeaveSuspendMode ([SWS_SM_00703]). Dans l’approche StateMachine, cela s’effectue par le ActionListItem LeaveSuspendToRam ([SWS_SM_00691]). Conformément à la contrainte [SWS_SM_CONSTR_00035], LeaveSuspendToRam ne doit être attribué qu’exclusivement à des états chargés de quitter le mode de suspension, et non aux états de repos eux-mêmes.
  6. Réactivation des satellites : le hub appelle ara::sm::s2r::S2RSatellite::LeaveSuspendMode sur les satellites enregistrés ([SWS_SM_00703], [SWS_SM_00711]). L’appel retourne dès que tous les satellites ont répondu, ont été désenregistrés ou que le timeout est écoulé ([SWS_SM_00707]).
  7. Désinscription : si un processus ou un satellite est terminé, le désenregistrement auprès du hub s’effectue via StopOffer() ([SWS_SM_00710], [SWS_SM_00713]).

Diagramme de séquence : séquence d’appels depuis l’enregistrement jusqu’au désenregistrement en passant par Suspend et Resume. Sources : [SWS_SM_00701], [SWS_SM_00702], [SWS_SM_00703], [SWS_SM_00707], [SWS_SM_00710], [SWS_SM_00711], [SWS_SM_00713].

Scénarios d'erreur

Dans l’interaction entre le hub et les satellites, les conditions d’erreur et préconditions suivantes sont spécifiées :

  • Violation de l’IAM lors de la création du hub : si le contexte de processus de l’appelant de S2RHub::S2RHub ne correspond pas à la configuration SuspendToRamHubMapping.process, la violation InsufficientPermissionsViolation est signalée et l’événement de sécurité SEV_ACCESS_CONTROL_SM_IAM_ACCESS_DENIED est déclenché ([SWS_SM_00706]).
  • Authentification manquante sur le satellite : si le commutateur IAM « Force IAM switch » est activé, S2RSatellite::Create renvoie le code d’erreur kAuthenticationRequired ([SWS_SM_00716]).
  • Rejet de satellites non autorisés : si le contexte de processus du satellite ne concorde pas avec SuspendToRamSatelliteMapping.process, le hub rejette l’enregistrement ([SWS_SM_00715]).
  • Timeout de communication : si un satellite adressé ne répond pas pendant RequestToLeaveSuspendMode dans l’intervalle de temps spécifié par timeout, le hub renvoie le code d’erreur kCommunicationTimeout ([SWS_SM_00707]).
  • Refus par les satellites : Si au moins une instance satellite répond négativement avec kRejected lors de la sortie de l'état de repos, le hub fournit kAtLeastOneHadIssuesToLeave comme résultat global ([SWS_SM_00707]). Un résultat global positif n'est obtenu que si tous les satellites confirment positivement ou se désenregistrent régulièrement via StopOffer ([SWS_SM_00707]).
  • Restrictions de configuration et d'utilisation : L'attribution de LeaveSuspendToRam à des états Suspend de la StateMachine est interdite ([SWS_SM_CONSTR_00035]). De même, l'accès simultané à l'API C++ de S2RHub lorsque l'approche StateMachine est active est prohibé ([SWS_SM_00684]).

Ce guide est basé sur la spécification AUTOSAR Adaptive R25-11. Toutes les indications s'appuient sur les exigences SWS et les passages de documents référencés.

<p>Le flux d’utilisation typique comprend la préparation de l’état de repos, le passage en mode de suspension ainsi que le réveil coordonné après la réactivation de la Machine :</p>
<ol>
<li><strong>Mise à disposition :</strong> chaque application compatible S2R initialise son <code>S2RSatellite</code> et signale qu’elle est prête à recevoir au hub via <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_SM_00710" href="../spec/record.html?id=SWS_SM_00710">[SWS_SM_00710]</a>).</li>
<li><strong>Demande de suspension :</strong> pour initier l’état de repos, <code>ara::sm::s2r::S2RHub::RequestToEnterSuspendMode</code> est appelé (<a class="spec-record-ref" data-req="SWS_SM_00701" href="../spec/record.html?id=SWS_SM_00701">[SWS_SM_00701]</a>). Dans l’approche StateMachine, cela s’effectue via le <code>ActionListItem</code> <code>EnterSuspendToRam</code> en utilisant <code>maxActionItemDuration</code> comme paramètre de timeout (<a class="spec-record-ref" data-req="SWS_SM_00689" href="../spec/record.html?id=SWS_SM_00689">[SWS_SM_00689]</a>).</li>
<li><strong>Notification des satellites :</strong> le hub adresse tous les satellites activement enregistrés et déclenche leur callback <code>ara::sm::s2r::S2RSatellite::EnterSuspendMode</code> (<a class="spec-record-ref" data-req="SWS_SM_00701" href="../spec/record.html?id=SWS_SM_00701">[SWS_SM_00701]</a>, <a class="spec-record-ref" data-req="SWS_SM_00711" href="../spec/record.html?id=SWS_SM_00711">[SWS_SM_00711]</a>). <code>RequestToEnterSuspendMode</code> bloque jusqu’à ce que tous les satellites adressés aient réagi, se soient désenregistrés ou qu’un timeout de communication survienne (<a class="spec-record-ref" data-req="SWS_SM_00702" href="../spec/record.html?id=SWS_SM_00702">[SWS_SM_00702]</a>).</li>
<li><strong>Suspension du système d’exploitation :</strong> si tous les satellites sont préparés, la commande de suspension proprement dite du système d’exploitation peut être déclenchée via <code>EnterSuspendToRamOs</code> (<a class="spec-record-ref" data-req="SWS_SM_00692" href="../spec/record.html?id=SWS_SM_00692">[SWS_SM_00692]</a>).</li>
<li><strong>Demande de réveil :</strong> après le réveil, la commande appelle <code>ara::sm::s2r::S2RHub::RequestToLeaveSuspendMode</code> (<a class="spec-record-ref" data-req="SWS_SM_00703" href="../spec/record.html?id=SWS_SM_00703">[SWS_SM_00703]</a>). Dans l’approche StateMachine, cela s’effectue par le <code>ActionListItem</code> <code>LeaveSuspendToRam</code> (<a class="spec-record-ref" data-req="SWS_SM_00691" href="../spec/record.html?id=SWS_SM_00691">[SWS_SM_00691]</a>). Conformément à la contrainte <a class="spec-record-ref" data-req="SWS_SM_CONSTR_00035" href="../spec/record.html?id=SWS_SM_CONSTR_00035">[SWS_SM_CONSTR_00035]</a>, <code>LeaveSuspendToRam</code> ne doit être attribué qu’exclusivement à des états chargés de quitter le mode de suspension, et non aux états de repos eux-mêmes.</li>
<li><strong>Réactivation des satellites :</strong> le hub appelle <code>ara::sm::s2r::S2RSatellite::LeaveSuspendMode</code> sur les satellites enregistrés (<a class="spec-record-ref" data-req="SWS_SM_00703" href="../spec/record.html?id=SWS_SM_00703">[SWS_SM_00703]</a>, <a class="spec-record-ref" data-req="SWS_SM_00711" href="../spec/record.html?id=SWS_SM_00711">[SWS_SM_00711]</a>). L’appel retourne dès que tous les satellites ont répondu, ont été désenregistrés ou que le timeout est écoulé (<a class="spec-record-ref" data-req="SWS_SM_00707" href="../spec/record.html?id=SWS_SM_00707">[SWS_SM_00707]</a>).</li>
<li><strong>Désinscription :</strong> si un processus ou un satellite est terminé, le désenregistrement auprès du hub s’effectue via <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_SM_00710" href="../spec/record.html?id=SWS_SM_00710">[SWS_SM_00710]</a>, <a class="spec-record-ref" data-req="SWS_SM_00713" href="../spec/record.html?id=SWS_SM_00713">[SWS_SM_00713]</a>).</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Dans l’interaction entre le hub et les satellites, les conditions d’erreur et préconditions suivantes sont spécifiées :</p>
<ul>
<li><strong>Violation de l’IAM lors de la création du hub :</strong> si le contexte de processus de l’appelant de <code>S2RHub::S2RHub</code> ne correspond pas à la configuration <code>SuspendToRamHubMapping.process</code>, la violation <code>InsufficientPermissionsViolation</code> est signalée et l’événement de sécurité <code>SEV_ACCESS_CONTROL_SM_IAM_ACCESS_DENIED</code> est déclenché (<a class="spec-record-ref" data-req="SWS_SM_00706" href="../spec/record.html?id=SWS_SM_00706">[SWS_SM_00706]</a>).</li>
<li><strong>Authentification manquante sur le satellite :</strong> si le commutateur IAM « Force IAM switch » est activé, <code>S2RSatellite::Create</code> renvoie le code d’erreur <code>kAuthenticationRequired</code> (<a class="spec-record-ref" data-req="SWS_SM_00716" href="../spec/record.html?id=SWS_SM_00716">[SWS_SM_00716]</a>).</li>
<li><strong>Rejet de satellites non autorisés :</strong> si le contexte de processus du satellite ne concorde pas avec <code>SuspendToRamSatelliteMapping.process</code>, le hub rejette l’enregistrement (<a class="spec-record-ref" data-req="SWS_SM_00715" href="../spec/record.html?id=SWS_SM_00715">[SWS_SM_00715]</a>).</li>
<li><strong>Timeout de communication :</strong> si un satellite adressé ne répond pas pendant <code>RequestToLeaveSuspendMode</code> dans l’intervalle de temps spécifié par <code>timeout</code>, le hub renvoie le code d’erreur <code>kCommunicationTimeout</code> (<a class="spec-record-ref" data-req="SWS_SM_00707" href="../spec/record.html?id=SWS_SM_00707">[SWS_SM_00707]</a>).</li>
<li><strong>Refus par les satellites :</strong> Si au moins une instance satellite répond négativement avec <code>kRejected</code> lors de la sortie de l'état de repos, le hub fournit <code>kAtLeastOneHadIssuesToLeave</code> comme résultat global (<a class="spec-record-ref" data-req="SWS_SM_00707" href="../spec/record.html?id=SWS_SM_00707">[SWS_SM_00707]</a>). Un résultat global positif n'est obtenu que si tous les satellites confirment positivement ou se désenregistrent régulièrement via <code>StopOffer</code> (<a class="spec-record-ref" data-req="SWS_SM_00707" href="../spec/record.html?id=SWS_SM_00707">[SWS_SM_00707]</a>).</li>
<li><strong>Restrictions de configuration et d'utilisation :</strong> L'attribution de <code>LeaveSuspendToRam</code> à des états Suspend de la StateMachine est interdite (<a class="spec-record-ref" data-req="SWS_SM_CONSTR_00035" href="../spec/record.html?id=SWS_SM_CONSTR_00035">[SWS_SM_CONSTR_00035]</a>). De même, l'accès simultané à l'API C++ de <code>S2RHub</code> lorsque l'approche StateMachine est active est prohibé (<a class="spec-record-ref" data-req="SWS_SM_00684" href="../spec/record.html?id=SWS_SM_00684">[SWS_SM_00684]</a>).</li>
</ul>
<p class="ai-note">Ce guide est basé sur la spécification AUTOSAR Adaptive R25-11. Toutes les indications s'appuient sur les exigences SWS et les passages de documents référencés.</p>
