Contexte

L'espace de noms apext::tsync fournit des extensions de plateforme (Platform Extensions) du module AUTOSAR Adaptive tsync pour le Freshness Value Management (FVM). Dans les architectures de calculateurs automobiles réparties, le Freshness Value Management protège les messages de synchronisation temporels critiques ainsi que ceux pertinents pour la sécurité contre les attaques par rejeu et par retardement, en générant, gérant et vérifiant des valeurs de fraîcheur dynamiques.

La tâche principale de l'espace de noms réside dans la fourniture de l'interface centrale FVM pour le module ara::tsync ainsi que des structures de données associées. Les valeurs de fraîcheur sont ainsi encapsulées par la classe conteneur FVContainer, qui accueille aussi bien la longueur en bits de la valeur que les données utiles proprement dites sous la forme d'un vecteur. Pour un traitement standardisé des erreurs, l'espace de noms définit un domaine d'erreur autonome TsyncFvmErrorDomain avec son énumérateur d'erreur associé TsyncFvmErrc [SWS_TS_14202], la fonction fabrique d'erreur MakeErrorCode [SWS_TS_14213] ainsi que la classe d'exception TsyncFvmException.

Diagramme de contexte : interaction entre ara::tsync, l'interface FVM, le FVContainer et le domaine d'erreur. Sources : [SWS_TS_14202], [SWS_TS_14212], [SWS_TS_14213].

Cycle de vie

Les composants de l'espace de noms apext::tsync sont soumis à des conditions de cycle de vie et de concurrence clairement délimitées :

  • Domaine d'erreur : la classe TsyncFvmErrorDomain fait office de domaine d'erreur global à l'échelle du processus. La fonction GetTsyncFvmErrorDomain() permet d'obtenir à tout moment une référence vers l'objet d'instance global. La fonction est spécifiée comme constexpr, thread-safe et sûre vis-à-vis des exceptions [SWS_TS_14212], ce qui fait que le domaine d'erreur reste disponible pendant toute la durée d'exécution de l'application.
  • Instance de gestionnaire : une phase d'initialisation est prévue pour le Freshness Value Manager. Interprétation : l'initialisation du Freshness Value Manager devrait constituer une phase de démarrage distincte dont l'échec empêche durablement l'utilisation du gestionnaire. Cela est étayé par le code d'erreur TsyncFvmErrc::kFVInitializeFailed, qui est explicitement défini comme une erreur irrémédiable (« Unrecoverable Error »), à la suite de laquelle le FVM ne peut plus être utilisé [SWS_TS_14202].
  • Conteneur de données : les instances de FVContainer possèdent un cycle de vie propre à l'appel. Elles sont créées pour accueillir des valeurs de fraîcheur, transmises pendant la vérification ou la création du message et peuvent être à nouveau détruites une fois l'opération terminée.

Parcours d'utilisation

Un chemin d'utilisation typique pour la sécurisation des messages de synchronisation se décompose selon les étapes d'interaction suivantes :

  1. Demande : Interprétation : l'interface FVM devrait être appelée par des composants au sein de ara::tsync pour la demande et la vérification de valeurs de fraîcheur. Le module temporel de niveau supérieur intègre l'interface FVM afin de fournir des valeurs de fraîcheur pour les messages sortants ou entrants.
  2. Transmission des données : en cas de détermination réussie, le Freshness Value Manager renseigne une instance de FVContainer avec la longueur en bits et le vecteur d'octets de la valeur de fraîcheur, puis la transmet à la synchronisation temporelle appelante.
  3. Signalement d'erreur : si aucune valeur valide n'est disponible à l'exécution, le sous-système génère via MakeErrorCode [SWS_TS_14213] un code d'erreur standardisé de type ara::core::ErrorCode en utilisant TsyncFvmErrc::kFVNotAvailable [SWS_TS_14202].
  4. Évaluation de l'erreur : l'appelant évalue le résultat. Interprétation : les appelants devraient pouvoir effectuer une nouvelle tentative de lecture en cas de kFVNotAvailable, car il s'agit d'un état d'erreur récupérable.

Scénarios d'erreur

Le traitement des erreurs dans apext::tsync suit le modèle standard d'AUTOSAR Adaptive via ara::core::ErrorCode :

  • TsyncFvmErrc::kFVNotAvailable (valeur 1) : caractérise une erreur récupérable (« Recoverable Error »). Cet état signale que la valeur de fraîcheur requise est temporairement indisponible [SWS_TS_14202]. La logique appelante peut traiter cette situation en répétant la récupération à un moment ultérieur.
  • TsyncFvmErrc::kFVInitializeFailed (valeur 2) : caractérise une erreur irrémédiable (« Unrecoverable Error »). Ce code indique que l'initialisation du Freshness Value Manager a échoué et que le module n'est pas opérationnel [SWS_TS_14202].

La construction de codes d'erreur s'effectue via MakeErrorCode(TsyncFvmErrc, ara::core::ErrorDomain::SupportDataType) [SWS_TS_14213], qui intègre des données de diagnostic propres au constructeur et dont l'exécution est garantie thread-safe ainsi que sûre vis-à-vis des exceptions. Pour les chemins logiciels fonctionnant avec des exceptions C++, la classe d'exception dérivée TsyncFvmException est disponible.

<h4>Cycle de vie</h4>
<p>Les composants de l'espace de noms <code>apext::tsync</code> sont soumis à des conditions de cycle de vie et de concurrence clairement délimitées :</p>
<ul>
<li><strong>Domaine d'erreur :</strong> la classe <code>TsyncFvmErrorDomain</code> fait office de domaine d'erreur global à l'échelle du processus. La fonction <code>GetTsyncFvmErrorDomain()</code> permet d'obtenir à tout moment une référence vers l'objet d'instance global. La fonction est spécifiée comme <code>constexpr</code>, thread-safe et sûre vis-à-vis des exceptions <a class="spec-record-ref" data-req="SWS_TS_14212" href="../spec/record.html?id=SWS_TS_14212">[SWS_TS_14212]</a>, ce qui fait que le domaine d'erreur reste disponible pendant toute la durée d'exécution de l'application.</li>
<li><strong>Instance de gestionnaire :</strong> une phase d'initialisation est prévue pour le Freshness Value Manager. Interprétation : l'initialisation du Freshness Value Manager devrait constituer une phase de démarrage distincte dont l'échec empêche durablement l'utilisation du gestionnaire. Cela est étayé par le code d'erreur <code>TsyncFvmErrc::kFVInitializeFailed</code>, qui est explicitement défini comme une erreur irrémédiable (« Unrecoverable Error »), à la suite de laquelle le FVM ne peut plus être utilisé <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>.</li>
<li><strong>Conteneur de données :</strong> les instances de <code>FVContainer</code> possèdent un cycle de vie propre à l'appel. Elles sont créées pour accueillir des valeurs de fraîcheur, transmises pendant la vérification ou la création du message et peuvent être à nouveau détruites une fois l'opération terminée.</li>
</ul>

<h4>Parcours d'utilisation</h4>
<p>Un chemin d'utilisation typique pour la sécurisation des messages de synchronisation se décompose selon les étapes d'interaction suivantes :</p>
<ol>
<li><strong>Demande :</strong> Interprétation : l'interface <code>FVM</code> devrait être appelée par des composants au sein de <code>ara::tsync</code> pour la demande et la vérification de valeurs de fraîcheur. Le module temporel de niveau supérieur intègre l'interface <code>FVM</code> afin de fournir des valeurs de fraîcheur pour les messages sortants ou entrants.</li>
<li><strong>Transmission des données :</strong> en cas de détermination réussie, le Freshness Value Manager renseigne une instance de <code>FVContainer</code> avec la longueur en bits et le vecteur d'octets de la valeur de fraîcheur, puis la transmet à la synchronisation temporelle appelante.</li>
<li><strong>Signalement d'erreur :</strong> si aucune valeur valide n'est disponible à l'exécution, le sous-système génère via <code>MakeErrorCode</code> <a class="spec-record-ref" data-req="SWS_TS_14213" href="../spec/record.html?id=SWS_TS_14213">[SWS_TS_14213]</a> un code d'erreur standardisé de type <code>ara::core::ErrorCode</code> en utilisant <code>TsyncFvmErrc::kFVNotAvailable</code> <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>.</li>
<li><strong>Évaluation de l'erreur :</strong> l'appelant évalue le résultat. Interprétation : les appelants devraient pouvoir effectuer une nouvelle tentative de lecture en cas de <code>kFVNotAvailable</code>, car il s'agit d'un état d'erreur récupérable.</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Le traitement des erreurs dans <code>apext::tsync</code> suit le modèle standard d'AUTOSAR Adaptive via <code>ara::core::ErrorCode</code> :</p>
<ul>
<li><strong><code>TsyncFvmErrc::kFVNotAvailable</code> (valeur 1) :</strong> caractérise une erreur récupérable (« Recoverable Error »). Cet état signale que la valeur de fraîcheur requise est temporairement indisponible <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>. La logique appelante peut traiter cette situation en répétant la récupération à un moment ultérieur.</li>
<li><strong><code>TsyncFvmErrc::kFVInitializeFailed</code> (valeur 2) :</strong> caractérise une erreur irrémédiable (« Unrecoverable Error »). Ce code indique que l'initialisation du Freshness Value Manager a échoué et que le module n'est pas opérationnel <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>.</li>
</ul>
<p>La construction de codes d'erreur s'effectue via <code>MakeErrorCode(TsyncFvmErrc, ara::core::ErrorDomain::SupportDataType)</code> <a class="spec-record-ref" data-req="SWS_TS_14213" href="../spec/record.html?id=SWS_TS_14213">[SWS_TS_14213]</a>, qui intègre des données de diagnostic propres au constructeur et dont l'exécution est garantie thread-safe ainsi que sûre vis-à-vis des exceptions. Pour les chemins logiciels fonctionnant avec des exceptions C++, la classe d'exception dérivée <code>TsyncFvmException</code> est disponible.</p>
