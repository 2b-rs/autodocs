Processus de publication

Cette page décrit le flux complet du pipeline de la référence API AUTOSAR Adaptive Platform : depuis les principaux enregistrements de spécifications, en passant par la traduction et les diagrammes, jusqu'à la sortie, la validation, le reporting et la traçabilité HTML. Il s’adresse aussi bien aux conservateurs, aux mainteneurs qu’aux agents d’IA. Les instructions d'agent opérationnel (comme AGENTS.md) sont elles-mêmes maintenues en tant qu'artefacts de pipeline autonomes avec leur propre cycle de vie de conservation et de révision et sont référencées ici.

1. Aperçu

Le pipeline suit un modèle déterministe en couches : Base de données de spécifications → Curation et révision → i18n Segmentation → Traduction de diagramme → HTML Génération → Validation → Rapports et traçabilité. Chaque publication est créée de manière reproductible à partir des sources définies sous _src/.

2. Source de vérité et catégories d'artefacts

La structure de classement fait une distinction stricte entre les sources faisant autorité, les artefacts de pipeline gérés et les produits de build éphémères :

  • Source de vérité (pertinente) : _src/spec/records/**/*.json (enregistrements de spécifications) ainsi que des catalogues tels que _src/spec/namespaces.json et _src/spec/projects.json. Toutes les modifications de contenu doivent être effectuées ici.
  • Artefacts de pipeline (versionnés/conservés) : modèles de pages sous _src/sources/pages/, files d'attente de révision et de curation, registres i18n (_src/i18n/), sources de diagrammes (.dot, .seq.json) et instructions d'agent (par exemple AGENTS.md).
  • Artéfacts de build générés (jetables) : L'intégralité de l'arborescence HTML (index.html, classes/, namespaces/, modules/, services/) et toutes les arborescences de langues localisées (en/, es/, pt/, fr/, ru/, ar/, hi/, ko/, zh/, nl/).
  • Produits de travail et de cache : PDF cache (_src/spec/pdf-cache/), output/, et archives d'exécution et de journaux à output/run-archive/.

3.1 Processus d'examen et de rétroaction

La plateforme propose deux voies d'interaction distinctes et clairement définies pour l'assurance qualité et les corrections :

Journal des décisions du conservateur (review.js)

Pour que les conservateurs et évaluateurs autorisés approuvent (accept) ou rejettent (reject) les candidats à l'extraction peu clairs directement sur le panneau des exigences.

Processus : les décisions sont collectées localement dans le package dans le navigateur, puis soumises sous la forme d'un problème structuré GitHub. Après l'ingestion, la décision est appliquée directement à l'ensemble de données.

Processus de demande d'indicateur pour révision (review_request.js)

Pour que tous les visiteurs du site Web signalent les écarts, les sources obsolètes ou le contexte manquant dans les ensembles de données publiés.

Flux : une requête crée une tâche de file d'attente immuable. Les agents IA analysent l'indice et préparent une suggestion ; La décision finale appartient toujours aux conservateurs humains.

Stockage, identité et protection des données

Les deux processus s'exécutent de manière efficace sur les données et sont isolés dans le navigateur (localStorage) :

  • ara-review-package-v1 : Cache pour les partages du panneau Curator collectés.
  • ara-review-github-token-v1 : jeton GitHub facultatif pour les soumissions authentifiées (réutilisé entre les deux dialogues).
  • ara-review-identity : nom auto-sélectionné pour les soumissions non authentifiées.
  • Pas de cookies, pas de suivi et pas de stockage côté serveur des données incomplètes du formulaire.

4. Multilinguisme (i18n) : Extraction, Traduction et Fusion

L'internationalisation s'effectue via un pipeline déterministe JSONL :

  1. Extraction : python3 _src/i18n_extract.py extrait tous les segments de texte nouveaux et modifiés des sources canoniques allemandes et leur attribue des identifiants stables.
  2. Traduction : Traduction des segments dans les 10 langues cibles (en, es, pt, fr, ru, ar, hi, ko, zh, nl). Les fragments de code, les identifiants et les jetons d'espace réservé restent protégés et inchangés.
  3. Fusionner : _src/i18n_translate.py merge fusionne les segments traduits avec l'inventaire source et signale les traductions manquantes ou incomplètes.

Les segments qui ne sont pas traduits reviennent automatiquement à la version allemande originale dans l'arborescence des langues générée.

5. Traduction de diagramme

Les graphiques sont générés à partir des sources .dot et .seq.json. Les étiquettes qu'elles contiennent sont extraites comme du texte normal, traduites et insérées dans les diagrammes générés d'une manière spécifique à la langue lors de la construction. Cela signifie que tous les diagrammes sont disponibles de manière cohérente dans les 10 langues.

6. Génération HTML

Le générateur _src/generate.py transforme les modèles de page (_src/sources/pages/*.json) et les enregistrements de spécifications en pages HTML statiques. Une arborescence HTML complète et autonome est générée pour chaque langue. L'appel s'effectue via :

python3 _src/generate.py --lang=all

7. Validation et contrôle qualité

Avant la publication, _src/validate.py vérifie la cohérence du résultat global :

  • Vérification de tous les liens et ancres internes et externes.
  • Recherchez les pages orphelines ou les références manquantes.
  • Vérification des appartenances aux espaces de noms et de la cohérence des signatures.
  • Contrôle de l'exhaustivité de i18n et détection des mélanges de langues involontaires.

Un code de sortie autre que 0 bloque l'étape de release et force la correction des sources sous-jacentes.

9. Gestion des erreurs et directives

Les écarts, erreurs de validation ou lacunes de traduction ne peuvent jamais être corrigés directement dans le HTML généré. Les corrections de bogues sont toujours effectuées au niveau de la source faisant autorité (_src/spec/ ou _src/sources/pages/), suivies d'une reconstruction et d'une validation complètes. Les refus dans les lots de traduction doivent être vérifiés et soumis à nouveau par l’équipe de curation.
