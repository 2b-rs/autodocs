Architecture système et rôle du cluster de modules

Les Communication Services se situent entre la RTE et les modules de protocoles de transport et d'interface spécifiques aux bus. Le cluster se compose d'un chemin de données (Com, PduR) et d'un chemin de commande (ComM). Pour COM, le PDU Router constitue l'unique couche inférieure (RS COM p. 12).

  • Com fournit l'API de signaux à la RTE, par ex. Com_SendSignal [SWS_Com_00197] et Com_ReceiveSignal [SWS_Com_00198]. Il mappe les signaux sur des I-PDU.
  • PduR transfère les I-PDU de manière inchangée et cohérente vers les modules cibles [SWS_PduR_00160]. Un chemin de routage est défini de manière univoque par l'ID source et les ID cibles [SWS_PduR_00161]. Vers le bas, le PduR dessert les interfaces et les protocoles de transport [SWS_PduR_00424]. Vers le haut, il dessert Com et les utilisateurs de TP tels que DCM (SWS PduR p. 24).
  • ComM assure la gestion des ressources pour ses utilisateurs. Les utilisateurs sont des Runnables, des SW-C, BswM ou DCM (SWS ComM p. 30). ComM gère les modes issus de ComM_ModeType [SWS_ComM_00672]. Il applique les modes via <BusSm>_RequestComMode auprès du Bus State Manager compétent [SWS_ComM_00958], [SWS_ComM_00962].

Le BswM assure le contrôle à l'échelle de l'ECU. Il peut démarrer et arrêter des groupes d'I-PDU dans Com ([SWS_Com_91001], [SWS_Com_91002]). En outre, il commute des groupes de chemins de routage du PduR ([SWS_PduR_00615], [SWS_PduR_00617], SWS BswM p. 166).

Diagramme de contexte : Com et PduR forment le chemin de données, ComM pilote les Bus State Managers et Nm, BswM commute des groupes dans Com et PduR. Sources : [SWS_PduR_00424], [SWS_Com_00669], [SWS_ComM_00958], [SWS_ComM_00164], [SWS_ComM_00275], [SWS_ComM_00873]

Interaction et chemins d'interaction

Émission. Com transmet une I-PDU avec PduR_ComTransmit [SWS_Com_00669]. Le PduR convertit l'ID vers le module cible [SWS_PduR_00766] et appelle <Lo>_Transmit pour chaque cible [SWS_PduR_00625].

  • En cas de singlecast, le PduR transmet la valeur de retour [SWS_PduR_00626].
  • En cas de multicast, une seule cible réussie suffit pour E_OK [SWS_PduR_00218].
  • Le PduR ne met pas en mémoire tampon les PDU d'une Upper Layer [SWS_PduR_00629].
  • La confirmation parvient à Com sous forme de Com_TxConfirmation [SWS_PduR_00627]. En cas de multicast, cela n'a lieu qu'après la dernière confirmation [SWS_PduR_00589].

Trigger Transmit. Certaines interfaces ne récupèrent les données qu'au moment de l'émission. Le PduR relaie alors la demande à Com_TriggerTransmit [SWS_PduR_00430] et renvoie sa valeur de retour [SWS_PduR_00661]. Com renvoie E_NOT_OK dans deux cas : lorsque l'I-PDU est arrêtée [SWS_Com_00884] ou lorsque le tampon est trop petit [SWS_Com_00869]. SWS PduR p. 106 montre le déroulement.

Diagramme de séquence : l'émission d'une I-PDU via FrIf se fait en deux étapes, d'abord l'ordre d'émission, puis la récupération des données par Trigger Transmit. Sources : [SWS_Com_00197], [SWS_PduR_00430], [SWS_Com_00884], [SWS_PduR_00627], SWS PduR p. 106

Réception et passerelle. Un appel de PduR_<Lo>RxIndication [SWS_PduR_00362] conduit pour chaque cible à Com_RxIndication [SWS_PduR_00621]. Le routage 1:n vers les Upper Layers [SWS_PduR_00164] peut être combiné avec des passerelles entre interfaces [SWS_PduR_00436]. Un exemple est le routage CAN→CAN avec réception locale simultanée (SWS PduR p. 114). Les I-PDU de grande taille utilisent le chemin TP avec Com_StartOfReception, Com_CopyRxData et Com_TpRxIndication ([SWS_Com_00691], [SWS_Com_00692], [SWS_Com_00650]). Le PduR relaie les callbacks TP vers celui-ci ([SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429]).

Groupes de signaux. Afin d'assurer l'atomicité, la RTE met d'abord à jour tous les signaux de groupe. Ensuite, elle déclenche Com_SendSignalGroup ([SWS_Com_00200], SWS RTE p. 329). En revanche, le COM Based Transformer échange le groupe sous la forme d'un tableau d'octets ([SWS_Com_00851], [SWS_Com_00854]). L'emplacement et la longueur de ce tableau sont définis dans [SWS_Com_00844] et [SWS_Com_00845].

Chemin de commande. Un utilisateur demande de la communication avec ComM_RequestComMode [SWS_ComM_00110]. Alternativement, DCM signale un diagnostic actif [SWS_ComM_00873]. ComM demande alors le mode auprès du Bus State Manager et se coordonne avec Nm selon la variante de NM (SWS ComM p. 167). En cas de Partial Networking, ComM écrit les bits PNC via Com_SendSignal ([SWS_ComM_00164], [SWS_ComM_00959]). Le BswM peut commuter des groupes de chemins de routage en fonction de l'état PNC. Cette source provient de la version R21-11 et est informative (ModeManagementGuide p. 50).

Diagramme de séquence : une demande de communication mène, en passant par l'attente de CommunicationAllowed, à la demande de bus et de NM. Sources : [SWS_ComM_00110], [SWS_ComM_00871], [SWS_ComM_00390], [SWS_ComM_00675], SWS ComM p. 167

Synchronisation, réentrance et contextes de tâches

Com effectue un traitement cyclique dans trois fonctions principales : Com_MainFunctionRx, Com_MainFunctionTx et Com_MainFunctionRouteSignals. Chacune est réentrante pour différentes instances, mais pas pour la même instance ([SWS_Com_00398], [SWS_Com_00399], [SWS_Com_00400]). L'extrait ECU décrit leurs périodes d'appel sous forme de bases de temps (Interoperability p. 98). Si une ComPreparationNotification est configurée, la MainFunctionTx l'appelle avant le traitement de l'I-PDU [SWS_Com_00886]. La RTE la met à disposition par instance (SWS RTE p. 832).

ComM traite par canal dans ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429]. ComM_RequestComMode est réentrant [SWS_ComM_00110], et le Runnable associé peut être appelé de manière concurrente (SWS ComM p. 107). Les callbacks de NM fonctionnent de manière asynchrone [SWS_ComM_00390]. ComM_Nm_PrepareBusSleepMode est réentrant, mais pas pour le même canal NM [SWS_ComM_00391].

Dans le chemin de données, la même règle s'applique partout : réentrant pour différentes PduId, non réentrant pour la même PduId. Cela concerne Com_RxIndication [SWS_Com_00123], Com_TxConfirmation [SWS_Com_00124], PduR_<Lo>RxIndication [SWS_PduR_00362] et PduR_<Lo>TxConfirmation [SWS_PduR_00365]. Interprétation : l'intégrateur devrait donc devoir empêcher que la même PDU ne soit signalée simultanément depuis le contexte d'interruption et le contexte de tâche, par exemple au moyen de zones exclusives. Les sources ne définissent pas le contexte d'appel.

En cas de partitions multiples, trois règles s'appliquent à ComM :

  • ComM doit autoriser les appels provenant de partitions tierces, par exemple via un satellite [SWS_ComM_01019].
  • ComM n'appelle les API <Bus>SM que dans la partition du Bus State Manager respectif [SWS_ComM_01020].
  • ComM n'utilise les API de signaux de Com que dans la partition du signal respectif [SWS_ComM_01021].

Cycles de vie et modes de fonctionnement

PduR possède exactement une machine à états [SWS_PduR_00644] avec les états PDUR_UNINIT et PDUR_ONLINE ([SWS_PduR_00324], [SWS_PduR_00742]). Après la mise sous tension, il est non initialisé [SWS_PduR_00325]. PduR_Init [SWS_PduR_00334] produit trois effets :

  • passage à PDUR_ONLINE [SWS_PduR_00326],
  • libération de tous les tampons [SWS_PduR_00645],
  • affectation des valeurs par défaut [SWS_PduR_00308].

Le routage n'a lieu que dans l'état PDUR_ONLINE ([SWS_PduR_00328], [SWS_PduR_00330]). Les groupes de chemins de routage démarrent conformément à la configuration [SWS_PduR_00709]. Les tables de routage post-build ne doivent être remplacées qu'à l'état non initialisé [SWS_PduR_00296]. La configuration active est fournie par PduR_GetConfigurationId [SWS_PduR_00280].

Com est initialisé avec Com_Init [SWS_Com_00432]. Il démarre lui-même les I-PDU sans groupe [SWS_Com_00840]. Toutes les autres I-PDU sont actives dès que l'un de leurs groupes est en cours d'exécution [SWS_Com_00771]. Un arrêt annule les demandes d'émission en attente [SWS_Com_00777], et les confirmations ultérieures sont ignorées [SWS_Com_00800]. Com_DeInit met fin à la communication inter-ECU [SWS_Com_00130]. Interprétation : Le démarrage des groupes d'I-PDU après Full Communication devrait être généralement pris en charge par une règle BswM. Les sources ne mentionnent que les actions disponibles à cet effet (SWS BswM p. 93).

ComM a besoin pour ComM_Init [SWS_ComM_00146] d'un NvM déjà initialisé. C'est le seul moyen pour lui de charger le statut d'inhibition, les compteurs d'inhibition et les données PNC (SWS ComM p. 97, SWS ComM p. 144). ComM_DeInit [SWS_ComM_00147] n'est autorisé que lorsque tous les canaux sont en No Communication. Ce faisant, ComM sauvegarde les paramètres non volatils (SWS ComM p. 114). L'état d'initialisation est fourni par ComM_GetStatus [SWS_ComM_00242] sous la forme d'une valeur de type [SWS_ComM_00668].

Par canal, ComM_StateType distingue cinq états et sous-états [SWS_ComM_00674] :

  • Une requête utilisateur mène à COMM_NO_COM_REQUEST_PENDING. Le canal y attend CommunicationAllowed ([SWS_ComM_00871], SWS ComM p. 69, p. 63).
  • Les canaux passifs passent à COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915]. Il en va de même pour les canaux SLAVE_ACTIVE sans requête [SWS_ComM_01017].
  • Si Nm signale Prepare Bus-Sleep, COMM_SILENT_COMMUNICATION [SWS_ComM_00826] s'ensuit. Dans cet état, seule la réception a encore lieu (SWS ComM p. 71).
  • Les notifications de réveil d'EcuM, liées à un canal ou à un PNC ([SWS_ComM_00275], [SWS_ComM_91001], [SWS_ComM_01014]), mènent via ce chemin à Nm_PassiveStartup (SWS ComM p. 75).

Le Partial Networking complète des machines d'états PNC. Leur état initial est COMM_PNC_NO_COMMUNICATION ([SWS_ComM_00964], SWS ComM p. 37). L'affectation dynamique PNC-canal est encore marquée comme DRAFT dans R20-11 ([SWS_ComM_91013], [SWS_ComM_01026]). Gestion des erreurs, traçage DET et dégradation

Com signale les erreurs de développement via Det_ReportError avec ModuleId 50 [SWS_Com_00442] :

  • COM_E_PARAM [SWS_Com_00803]
  • COM_E_UNINIT [SWS_Com_00804]
  • COM_E_PARAM_POINTER [SWS_Com_00805]
  • COM_E_INIT_FAILED [SWS_Com_00837]

Si une demande d'émission d'une grande I-PDU est ignorée, Com signale l'erreur d'exécution COM_E_SKIPPED_TRANSMISSION ([SWS_Com_00863], [SWS_Com_00864]).

Sur le plan fonctionnel, Com se dégrade via la surveillance d'échéance :

  • En l'absence de confirmation d'émission en temps voulu, Com appelle les notifications d'expiration [SWS_Com_00304]. Une confirmation arrête les timers [SWS_Com_00880].
  • À la réception, l'action SUBSTITUTE remplace les valeurs par des valeurs de substitution ([SWS_Com_00875], [SWS_Com_00876]).
  • Une réception TP ayant échoué est traitée comme une invalidation [SWS_Com_00838].
  • Les signaux dont le bit de mise à jour n'est pas défini sont rejetés [SWS_Com_00802].
  • La surveillance de réception peut être activée et désactivée par groupe ([SWS_Com_91003], [SWS_Com_91004]).

PduR connaît entre autres les erreurs PDUR_E_UNINIT, PDUR_E_PDU_ID_INVALID et PDUR_E_ROUTING_PATH_GROUP_ID_INVALID ([SWS_PduR_00100], [SWS_PduR_00119], [SWS_PduR_00221], [SWS_PduR_00648]). Il ne répète pas un <DstLo>_Transmit ayant échoué [SWS_PduR_00256]. Si une FIFO déborde, elle est vidée et PDUR_E_PDU_INSTANCES_LOST est signalé ([SWS_PduR_00255], [SWS_PduR_00670]). Si une destination tombe en panne dans la passerelle TP, les autres continuent [SWS_PduR_00803]. La réception n'est interrompue que si toutes les destinations échouent [SWS_PduR_00804]. Lorsque les chemins de routage sont désactivés, les API retournent immédiatement avec E_NOT_OK ([SWS_PduR_00717], SWS PduR p. 69).

ComM signale entre autres COMM_E_UNINIT et COMM_E_PARAM_POINTER [SWS_ComM_00234]. Sans initialisation, il refuse le fonctionnement normal [SWS_ComM_00612]. L'inhibition de mode sert à une dégradation ciblée :

  • Un canal ou l'ensemble de l'ECU peut être limité à No Communication ([SWS_ComM_00163], [SWS_ComM_00124]).
  • Les processus de réveil peuvent être supprimés [SWS_ComM_00156].
  • L'état se trouve dans un champ de bits [SWS_ComM_00669] et est conservé après un reset de l'ECU (SWS ComM p. 84).
  • Les requêtes rejetées renvoient COMM_E_MODE_LIMITATION [SWS_ComM_00110] et sont comptabilisées [SWS_ComM_00224].
  • En option, ComM force ensuite un reset via BswM [SWS_ComM_00355].

Le matériel analysé ne mentionne aucun événement DEM pour ce cluster. Le traitement des erreurs s'appuie sur les notifications DET et la dégradation fonctionnelle décrite ci-dessus ([SWS_PduR_00100], [SWS_ComM_00234]).
