EcuM_CheckRamHash fonction

Ce callout est intended à fournir un RAM intégrité test. le goal de ce test est à garantir que après un long SLEEP durée, RAM contenus est encore cohérent. le vérifier ne avoir besoin à être exhaustive depuis ce would consume quite quelque traitement temps pendant wakeups. A bien designed vérifier va execute quickly et detect RAM intégrité defects avec un suffisant probability. ce specification ne make tout hypothèse à propos du algorithme choisi pour un particular ECU. le areas de RAM qui sera vérifié ont à être choisi carefully. il dépend sur le vérifier algorithme itself et le tâche structure. pile contenus du tâche exécutant le RAM vérifier e.g. très likely ne peut pas être vérifié. il est good practice à ont le hash generation et checking dans le même tâche et que ce tâche n'est pas preemptible et que là est seulement little activity entre hash generation et hash vérifier. le RAM vérifier itself est fourni par le système designer. en cas de applied multi core et existence de Satellite-Ecu M(s): Cette API sera appelé par le maître-EcuM seulement.

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation fonction

Ce callout est appelée par le EcuM à valider un réveil source. si un valide réveil a été detected, il doit être signalé à EcuM via EcuM_ValidateWakeupEvent().

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup fonction

Ce callout est appelée par le EcuM à poll un réveil source. il doit également être appelé par le ISR d'un réveil source à définir haut le PLL et vérifier autre réveil sources que peut être connecté au même interruption.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);
EcuM_ClearWakeupEvent fonction

EcuM_DeterminePbConfiguration fonction

Ce callout devrait evaluate quelque condition, like port broche ou NVRAM valeur, à determine qui post-build configuration doit être utilisé dans le remainder du démarrage processus. il doit charger ce données de configuration dans un piece de mémoire que est accessible par tous BSW modules et doit renvoyer un pointeur vers le EcuM post-build configuration comme un base pour tous BSW module post-build configrations.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources fonction

le ECU gestionnaire module appels EcuM_DisableWakeupSources à définir le réveil source(s) défini dans le wakeupSource champ de bits de sorte que they ne sont pas able à wake le ECU haut.

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources fonction

le ECU gestionnaire module appels EcuM_EnableWakeupSource à permettre le système designer à notifier réveil sources défini dans le wakeupSource champ de bits que SLEEP sera entered et à adjust leur source en conséquence.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup fonction

Cette API est appelée par tout SW module whose réveil source est vérifié asynchronously (e.g. asynchrone Can Trcv pilote) et le vérifier du réveil renvoie un négatif résultat (aucun réveil par ce source). le API annule le CheckWakeupTimer pour le WakeupSource. si le correponding CheckWakeupTimer est annulé le vérifier de ce réveil source est terminé.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook fonction

le ECU State Manager va appel l'erreur hook si l'erreur codes "ECUM_E_RAM_CHECK_ FAILED" ou "ECUM_E_CONFIGURATION_DATA_INCONSISTENT" occur. dans ce situation il n'est pas possible à continuer traitement et le ECU doit être arrêté. le integrator peut choose le modality how le ECU est arrêté, i.e. réinitialisé, halt, restart, safe état etc.

void EcuM_ErrorHook (uint16 reason);

1. Architecture système & rôle du cluster de modules

Le cluster de modules System Services constitue l’épine dorsale fonctionnelle de l’AUTOSAR Classic Platform. Il comprend le BSW Mode Manager (BswM), l’ECU State Manager (EcuM), le Watchdog Manager (WdgM) ainsi que le pilote matériel Watchdog Driver (Wdg) SWS_ECUStateManager p. 35. Ensemble, ces modules pilotent le cycle de vie global du calculateur, coordonnent les modes de fonctionnement bas niveau et applicatifs, et assurent la surveillance temporelle et logique de l’exécution du programme afin de garantir la sécurité fonctionnelle SafetyConceptStatusReport p. 15.

Dans l’architecture en couches AUTOSAR, BswM, EcuM et WdgM sont situés dans la couche des System Services au-dessus des couches d’abstraction et de pilotes, tandis que le Watchdog Driver (Wdg), en tant que partie intégrante de la Microcontroller Abstraction Layer (MCAL), dessert les registres matériels du timer watchdog [SWS_Wdg_00106]. L’EcuM fait office, dans sa variante flexible (EcuM Flex), de liaison avec le matériel pour les séquences de démarrage précoce et d’arrêt tardif, respectivement avant et après le lancement du système d’exploitation. Il ne possède plus sa propre machine à états complexe pour les modes d’application, mais délègue l’arbitrage de mode au BswM SWS_ECUStateManager p. 103. Les standards de diagnostic externes tels qu’UDS (ISO 14229) et les protocoles de gestion de réseau s’interfacent directement, via des interfaces BSW définies (comme le service 0x28 CommunicationControl via Dcm), dans l’évaluation des règles du BswM [SWS_BswM_00048].

2. Interaction & voies d'interaction entre les modules

L’interaction au sein du cluster se caractérise par des relations de contrôle et de notification clairement délimitées. Dans le cadre de l’ECU Mode Handling, le EcuM reçoit des requêtes pour des états tels que RUN ou POST_RUN de la part de composants logiciels (SW-Cs) et transmet le résultat d’arbitrage agrégé au BswM via [SWS_BswM_91004] ModeManagementGuide p. 34. Étant donné que le EcuM ne prend pas de décision de transition propre, le BswM évalue les règles logiques configurées et assigne l’état cible de manière synchrone au [SWS_EcuM_04116] via EcuM_SetState. Le EcuM répercute ensuite cet état vers l’application via la RTE et confirme l’état d’exécution actuel au BswM via BswM_EcuM_CurrentState [SWS_BswM_91003].

Un chemin d’interaction parallèle relie BswM, WdgM et Wdg. Les composants logiciels et les modules BSW signalent l’atteinte de checkpoints définis au WdgM, qui en déduit le statut de surveillance local et global SWS_WatchdogManager p. 51. Le WdgM met à disposition les changements d’état de la surveillance locale par l’intermédiaire de ports de mode fournis [SWS_WdgM_00148]. En fonction de l’état système de niveau supérieur, le BswM commute le mode de fonctionnement du Watchdog Manager via WdgM_SetMode [SWS_WdgM_00154]. Le WdgM configure alors le Watchdog Driver (Wdg) via la Watchdog Interface (WdgIf) et commande le déclenchement matériel via Wdg_SetTriggerCondition [SWS_Wdg_00155].

3. Synchronisation, réentrance et contextes de tâche

L’exécution des System Services est répartie de manière déterministe entre des niveaux de tâches périodiques, des rappels asynchrones et des contextes d’interruption. La charge principale périodique de la gestion des modes est portée par BswM_MainFunction, qui est appelée dans le contexte d’une tâche OS par le BSW Scheduler (SchM) et traite toutes les règles devant être évaluées de manière différée [SWS_BswM_00053]. Si des événements nécessitant une évaluation immédiate des règles surviennent, ils sont traités directement de façon synchrone dans le contexte de l’indication BSW appelante ou de l’API de SW-C ModemanagementGuide p. 31.

Dans les systèmes multicœurs, la normalisation exige une allocation stricte des ressources. BswM_Init est conçu pour être réentrant sous condition, afin de permettre des instanciations séparées par partition ou cœur de processeur [SWS_BswM_00002]. Durant les phases de sommeil et de maintien, le EcuM réserve des ressources OS propres au cœur (RES_AUTOSAR_ECUM_<core#>) afin de sécuriser la synchronisation entre cœurs maîtres et esclaves [SWS_EcuM_03010]. L’initialisation des pilotes via EcuM_AL_DriverInitZero et EcuM_AL_DriverInitOne est appelée séparément sur chaque cœur et initialise exclusivement les modules MCAL locaux au cœur [SWS_EcuM_04145]. L’effacement des événements de réveil via EcuM_ClearWakeupEvent est explicitement non interruptible et peut être exécuté aussi bien depuis des contextes de tâche que d’interruption [SWS_EcuM_02807].

4. Cycles de vie et modes de fonctionnement typiques

Le cycle de vie d’un calculateur est normativement structuré en phases STARTUP, UP, SHUTDOWN et SLEEP [SWS_EcuM_91005]. La phase STARTUP débute avant le lancement du système d’exploitation dans la séquence StartPreOS avec l’appel de EcuM_Init, l’évaluation de la cause du reset et le chargement de la configuration post-build via EcuM_DeterminePbConfiguration AUTOSAR_SWS_ECUStateManager p. 38. Après le transfert du contrôle au système d’exploitation via StartOS, le EcuM initialise le SchM ainsi que le BswM dans StartPostOS [SWS_EcuM_02934]. Ensuite, le BswM prend les commandes et démarre les modules BSW restants ainsi que l’application.

En cours de fonctionnement (phase UP), EcuM et BswM gèrent les modes RUN et POST_RUN ainsi que le service optionnel Alarm Clock SWS_ECUStateManager p. 75. Lors d’un passage à l’état de sommeil (SLEEP), le cluster distingue structurellement HALT (arrête la CPU) et POLL (fréquence d’horloge CPU réduite) SWS_ECUStateManager p. 54. En amont, l’appel WdgM_DeInit désinitialise le Watchdog Manager et adapte les délais d’expiration de déclenchement afin d’éviter des resets indésirables pendant la phase d’arrêt [SWS_WdgM_00261]. Dans la séquence d’interrogation (poll), le EcuM bloque dans une boucle de vérification avec des appels périodiques de EcuM_SleepActivity et EcuM_CheckWakeupHook, jusqu’à ce qu’un événement de réveil soit détecté [SWS_EcuM_03020].

Les événements de réveil détectés traversent une gestion d’états stricte allant de ECUM_WKSTATUS_NONE à VALIDATED ou EXPIRED en passant par PENDING [SWS_EcuM_04091]. Le EcuM signale chaque changement d’état de façon synchrone au BswM au moyen de BswM_EcuM_CurrentWakeup [SWS_BswM_00131]. La validation du réveil protège contre les perturbations transitoires du bus et surveille la fenêtre temporelle au moyen de timers de validation configurables [SWS_EcuM_04004]. Si le cycle de vie se termine par un SHUTDOWN, OffPreOS désactive le BswM et SchM, avant que OffPostOS ne réinitialise le calculateur ou ne le mette hors tension via des callouts d’intégration tels que EcuM_AL_Reset ou EcuM_AL_SwitchOff AUTOSAR_SWS_ECUStateManager p. 49.

5. Gestion des erreurs, traçage DET et dégradation

Pour détecter les erreurs d’exécution et de configuration, le cluster intègre des mécanismes standardisés de notification vers le Default Error Tracer (Det). Si une entité tente d’émettre une libération via EcuM_ReleasePOST_RUN sans requête préalable, le EcuM signale l’erreur de développement ECUM_E_MISMATCHED_RUN_RELEASE au Det [SWS_EcuM_03026]. Les requêtes multiples émanant du même utilisateur sont enregistrées avec ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03025]. De même, le WdgM surveille les appels d’API à l’état non initialisé et signale WDGM_E_UNINIT si des services sont appelés avant l’achèvement de l’initialisation [SWS_WdgM_00288].

La surveillance de la sécurité repose sur le contrôle fonctionnel à trois niveaux du WdgM (Alive Supervision, Deadline Supervision et contrôle logique du flux d’exécution) SafetyConceptStatusReport p. 47. Si une anomalie de surveillance entraîne la violation des tolérances aux pannes, le statut global de surveillance passe de WDGM_GLOBAL_STATUS_OK à WDGM_GLOBAL_STATUS_EXPIRED via FAILED, puis finalement à STOPPED [SWS_WdgM_00387]. Dans cet état, le WdgM remet à 0 la condition de déclenchement pour tous les pilotes de watchdog, ce qui amène le watchdog matériel à réinitialiser immédiatement le microcontrôleur [SWS_WdgM_00232]. Pour les resets d’urgence contrôlés, le WdgM fournit le service WdgM_PerformReset, qui arrête le réarmement continu et force le reset matériel [SWS_WdgM_00264]. En guise de sécurisation après des phases prolongées de sommeil, le EcuM vérifie en outre la cohérence de la mémoire volatile au moyen de EcuM_CheckRamHash afin d’intercepter les redémarrages défaillants en cas de corruption de la RAM [SWS_EcuM_02921].
