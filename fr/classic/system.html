EcuM_CheckRamHash fonction

Ce callout est intended à fournir un RAM intégrité test. le goal de ce test est à garantir que après un long SLEEP durée, RAM contenus est encore cohérent. le vérifier ne avoir besoin à être exhaustive depuis ce would consume quite quelque traitement temps pendant wakeups. A bien designed vérifier va execute quickly et detect RAM intégrité defects avec un suffisant probability. ce specification ne make tout hypothèse à propos du algorithme choisi pour un particular ECU. le areas de RAM qui sera vérifié ont à être choisi carefully. il dépend sur le vérifier algorithme itself et le tâche structure. pile contenus du tâche exécutant le RAM vérifier e.g. très likely ne peut pas être vérifié. il est good practice à ont le hash generation et checking dans le même tâche et que ce tâche n'est pas preemptible et que là est seulement little activity entre hash generation et hash vérifier. le RAM vérifier itself est fourni par le système designer. en cas de applied multi core et existence de Satellite-Ecu M(s): Cette API sera appelé par le maître-EcuM seulement.

uint8 EcuM_CheckRamHash (void);

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);

Architecture système et rôle du cluster de modules

Le cluster « System Services » comprend les modules qui prennent en charge le démarrage, les modes de fonctionnement, Sleep/Shutdown et la surveillance du déroulement de programme d'un calculateur Classic Platform. L'ECU State Manager est ici le service système qui établit l'état matériel final après l'arrêt de l'OS (SWS EcuM p. 82, [SWS_EcuM_04020]). Les quatre modules ont des rôles clairement distincts :

  • BswM arbitre les indications de mode entrantes ([SWS_BswM_00035]). Des règles associent logiquement les ModeRequestPorts et déclenchent des listes d'actions True ou False (Mode Management Guide p. 32). Les actions s'exécutent exclusivement dans le contexte d'une liste d'actions ([SWS_BswM_00147]).
  • EcuM initialise la BSW, démarre et arrête l'OS et gère les états des sources de réveil ([SWS_EcuM_02811], [SWS_EcuM_04091]). Il ne possède pas de machine à états propre. Il reprend les changements d'état du BswM (SWS EcuM p. 99, [SWS_EcuM_04116]).
  • WdgM surveille les Supervised Entities via des Checkpoints ([SWS_WdgM_00263]) et en déduit un Global Supervision Status ([SWS_WdgM_00360]). Il définit les modes de watchdog via WdgIf_SetMode ([SWS_WdgM_00186]).
  • Wdg pilote le matériel de watchdog interne ou externe ([SWS_Wdg_00161], [SWS_Wdg_00076]). Il dessert le matériel tant que la condition de déclenchement est valide ([SWS_Wdg_00144]).

Diagramme de contexte : le diagramme de contexte montre le BswM comme décideur des modes, l'EcuM comme exécutant des séquences de cycle de vie et la chaîne de surveillance WdgM → WdgIf → Wdg → matériel. Sources : SWS EcuM p. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Interaction et chemins d'interaction

EcuM ↔ BswM (ECU Mode Handling) : ce chemin est actif lorsque EcuMModeHandling est configuré ([SWS_EcuM_04115]). Les SW-C demandent RUN et POST_RUN via EcuM_RequestRUN ou EcuM_RequestPOST_RUN et les libèrent ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). L'EcuM signale le résultat de l'arbitrage via BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). Le BswM définit ensuite l'état via EcuM_SetState ([SWS_EcuM_04122]). Dès que la RTE a confirmé le changement, l'EcuM signale l'état en retour via BswM_EcuM_CurrentState ([SWS_EcuM_04143], [SWS_BswM_91003]).

Chemin de réveil : les pilotes signalent les réveils via EcuM_SetWakeupEvent, qui marque l'événement comme pending ([SWS_EcuM_01117]). Si une validation est requise, l'EcuM démarre le protocole de validation ([SWS_EcuM_02975]). La validation est prise en charge par exactement un module BSW (SWS EcuM p. 69). Son appel de EcuM_ValidateWakeupEvent notifie le BswM et le ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). Chaque changement d'état d'une source de réveil est signalé au BswM sous la forme d'une requête de mode ([SWS_EcuM_04003]).

Diagramme d'états : le diagramme d'états montre les cycles de vie d'une source de réveil (NONE, PENDING, VALIDATED, EXPIRED) et le message du BswM lors de l'entrée dans chaque état. Sources : [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM p. 64

WdgM → Wdg : Wdg_SetTriggerCondition reçoit un délai d'attente en millisecondes et le convertit en interne en une valeur de compteur en tenant compte du mode actuel ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). La routine de maintenance du pilote se comporte comme suit :

  • Si le compteur est supérieur à zéro, elle le décrémente et déclenche le matériel ([SWS_Wdg_00134]).
  • À zéro, elle ne déclenche plus, et le watchdog expire ([SWS_Wdg_00135]).

Interprétation : WdgIf devrait transmettre le mode et la condition de déclenchement à l'instance Wdg adressée correspondante. Plusieurs instances portent des noms uniques ([SWS_Wdg_00172]).

EcuM → WdgM (Reset) : WdgM_PerformReset est une cible de reset obligatoire ([SWS_EcuM_04005], [SWS_EcuM_04044]). Elle définit la condition de déclenchement de tous les pilotes sur 0, ce qui amène les watchdogs matériels à déclencher un reset ([SWS_WdgM_00264], SWS WdgM p. 82). ECUM_CAUSE_WDGM est disponible en tant que cause d'arrêt ([SWS_EcuM_04045]).

Synchronisation, réentrance et contextes de tâches

BswM_MainFunction : elle évalue toutes les règles qui utilisent une requête avec BSWM_DEFERRED ([SWS_BswM_00075]). Les temporisateurs du BswM sont toujours traités en différé ([SWS_BswM_00220]). Les requêtes avec « immediate » sont en revanche évaluées immédiatement (Mode Management Guide p. 32).

EcuM_MainFunction : elle s'exécute dans toutes les instances d'EcuM ([SWS_EcuM_04011]). Elle surveille les délais de validation ([SWS_EcuM_04082]) et valide les candidats au réveil après le WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction : elle démarre la surveillance lors du premier appel après WdgM_Init ([SWS_WdgM_00406]) et calcule ensuite le Global Supervision Status à chaque période (SWS WdgM p. 34).

Contexte d'interruption : les services de réveil peuvent être appelés depuis un contexte d'interruption, d'OS et sans OS ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). Ils sont toutefois spécifiés comme « Non-Reentrant, Non-Interruptible » ([SWS_EcuM_02826], [SWS_EcuM_02828]). EcuM_ValidateWakeupEvent constitue une exception : elle est réentrante et peut être appelée depuis un contexte d'interruption et de tâche ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Réentrance de WdgM et Wdg :

  • WdgM_SetMode, WdgM_DeInit et Wdg_SetTriggerCondition ne sont pas réentrants ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • WdgM_GetMode fournit encore l'ancien mode pendant un changement de mode en cours ([SWS_WdgM_00168], SWS WdgM p. 77).
  • Wdg ne verrouille les interruptions pour la cohérence des données que par les mécanismes BSW prévus ([SWS_Wdg_00040]).

Multicore : une instance propre d'EcuM s'exécute sur chaque Core. L'EcuM maître démarre les autres Cores (SWS EcuM p. 71). Il en découle les obligations suivantes :

  • Chaque instance traite les réveils de son propre Core ([SWS_EcuM_04012]).
  • Tous les BswM locaux au core sont initialisés ([SWS_EcuM_04014]).
  • Une ressource RES_AUTOSAR_ECUM est réservée par Core ([SWS_EcuM_03010]).
  • Les API C sont disponibles dans chaque partition où un EcuM s'exécute ([SWS_EcuM_04095]).

Le BswM est conditionnellement réentrant pour les systèmes multi-partitions ([SWS_BswM_00002]).

Cycles de vie et modes de fonctionnement

Démarrage (StartPreOS) : EcuM_Init exécute la séquence StartPreOS ([SWS_EcuM_02684]). Elle comprend :

  • les blocs d'initialisation 0 et 1 dans l'ordre configuré ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • la sélection de la configuration post-build ([SWS_EcuM_02906]),
  • le contrôle de cohérence de toutes les configurations post-build avant la première initialisation de la BSW ([SWS_EcuM_02796]).

Selon la description structurelle, Wdg_Init fait partie des fonctions d'initialisation utilisées par l'EcuM (SWS EcuM p. 34). Wdg_Init définit le mode par défaut et le délai d'attente ([SWS_Wdg_00001]).

Démarrage (StartPostOS) : EcuM_StartupTwo s'exécute dans une tâche démarrée par StartOS ([SWS_EcuM_02806]). Il démarre le SchM et initialise le BswM ([SWS_EcuM_02932]). BswM_Init ne requiert qu'un OS et un SchM initialisés (SWS BswM p. 69). Le BswM peut initialiser d'autres pilotes lors de la phase UP, par exemple via EcuM_AL_DriverInitBswM_<x> (SWS EcuM p. 46, [SWS_EcuM_04114]).

Diagramme de séquence : le diagramme de séquence montre l'ordre de StartPreOS et de StartPostOS sur le Core maître. Sources : [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM p. 82, SWS EcuM p. 42

Sleep : avant EcuM_GoDownHaltPoll, le BswM doit typiquement avoir sélectionné une cible SLEEP (SWS EcuM p. 54, [SWS_EcuM_91002]). Le déroulement :

  1. GoSleep active les sources de réveil ; l'OS reste alors actif ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. Selon le mode Sleep, Halt avec hachage de la RAM ([SWS_EcuM_02863]) ou Poll ([SWS_EcuM_02962]) suit ensuite. Aucun réveil ne doit être perdu pendant ce processus ([SWS_EcuM_02188]).
  3. Un réveil mène à la séquence WakeupRestart avec réinitialisation des pilotes ([SWS_EcuM_02963], [SWS_EcuM_02923]).

Dans R20-11, le callout de Poll s'appelle EcuM_CheckWakeup ([SWS_EcuM_02929]). Ce n'est qu'à partir de R21-11 qu'il s'appelle EcuM_CheckWakeupHook (SWS EcuM p. 145).

Watchdog en Sleep : avant le Sleep, WdgM_DeInit bascule vers un mode de veille avec des conditions de déclenchement compatibles et arrête la surveillance (SWS WdgM p. 59, [SWS_WdgM_00407]). La description structurelle de l'EcuM ne mentionne toutefois que WdgM_PerformReset comme dépendance WdgM. L'appel de WdgM_DeInit s'effectue donc vraisemblablement via une action du BswM ou du code d'intégration.

Diagramme de séquence : le diagramme de séquence montre la phase SLEEP avec Halt : GoSleep, hachage de la RAM, Wakeup et WakeupRestart. Sources : SWS EcuM p. 54, SWS EcuM p. 55, SWS EcuM p. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown : le déroulement :

  1. OffPreOS désinitialise le BswM et le SchM (SWS EcuM p. 90). Ensuite, le BswM ne traite plus aucun mode ([SWS_BswM_00120]).
  2. En tant que dernière activité, l'EcuM appelle ShutdownOS ([SWS_EcuM_02952]). Le hook de shutdown appelle EcuM_Shutdown ([SWS_EcuM_02953]).
  3. Pour finir, EcuM_AL_Reset ou EcuM_AL_SwitchOff suivent ([SWS_EcuM_04074], [SWS_EcuM_04075]).

Les sources de réveil doivent être effacées avant Dem_Shutdown et NvM_WriteAll via des callouts utilisateur du BswM (SWS EcuM p. 124, [SWS_BswM_00054]). Un réveil pendant l'arrêt entraîne un redémarrage après son achèvement ([SWS_EcuM_02756]). Wdg ne possède pas d'interface propre de désinitialisation ([SWS_Wdg_00031]).

Gestion des erreurs, traçage DET et dégradation

Erreurs de développement (DET) :

  • Le BswM ignore les indications avant l'initialisation et signale BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). Il signale les actions en échec en tant qu'erreur d'exécution BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • L'EcuM signale les demandes RUN en double et les libérations inappropriées ([SWS_EcuM_03024], [SWS_EcuM_03023]) ainsi que les sources de réveil inconnues ([SWS_EcuM_02867]).
  • WdgM et Wdg définissent leurs propres codes d'erreur ([SWS_WdgM_00004], [SWS_Wdg_00010]). WdgM signale un échec de WdgIf_SetMode sous la forme WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Erreurs irrécupérables : EcuM les transmet à EcuM_ErrorHook ([SWS_EcuM_04033]). Des exemples sont des données de configuration incohérentes ou un échec du test de RAM ([SWS_EcuM_91003]). EcuM ignore les erreurs retournées pendant l'initialisation des fonctions Init ([SWS_EcuM_02980]).

Dégradation de la surveillance : l'état global démarre en tant que WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Les changements de mode ne sont autorisés que dans les états OK et FAILED ([SWS_WdgM_00145]). La désactivation du watchdog peut être interdite par configuration ([SWS_WdgM_00031]). L'escalade se déroule comme suit :

  1. Dans l'état EXPIRED, la réaction d'erreur est différée d'une tolérance configurable (SWS WdgM p. 34).
  2. Dans l'état STOPPED, WdgM signale WDGM_E_SUPERVISION, et un reset de watchdog s'ensuit ([SWS_WdgM_00375]).
  3. Un changement de mode en échec mène également à STOPPED (SWS WdgM p. 57).

Diagnostic après le reset : le SEID ayant expiré en premier est stocké sous forme doublement inversée dans une RAM non initialisée. Il est lisible dès avant WdgM_Init ([SWS_WdgM_00348], [SWS_WdgM_00349]). WdgM signale les changements d'état via des Mode-Ports ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset existe encore dans R20-11 ([SWS_BswM_00157]), mais devient obsolète à partir de R21-11 (SWS BswM p. 2).

Erreurs de pilote et ultime protection : Wdg signale les erreurs de production WDG_E_MODE_FAILED et WDG_E_DISABLE_REJECTED au DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). Si EcuM_AL_SwitchOff est bloqué dans un interblocage, le watchdog matériel réinitialise le calculateur (SWS EcuM p. 141).
