Architecture système et rôle du cluster de modules

Le cluster comprend un seul module, la Runtime Environment (Rte). Elle met en œuvre sur chaque calculateur les chemins de communication définis par la configuration de l'ECU. Ce faisant, elle réalise également la sémantique des attributs de communication issus des descriptions de composants [SWS_Rte_02200] [SWS_Rte_02201]. La RTE est configurée et générée individuellement pour chaque calculateur [SWS_Rte_05000] [SWS_Rte_01316]. Le générateur produit du code C qui doit être conforme à MISRA C [SWS_Rte_01167] [SWS_Rte_01168]. La position de la RTE entre le logiciel d'application et le Basic Software est présentée sur le schéma d'architecture de l'ECU (SWS RTE p. 113).

Vers le bas, la RTE utilise exclusivement des services AUTOSAR standardisés, parmi lesquels OS, COM, LdCom et Transformer [SWS_Rte_02250]. Le code généré comprend en outre le Basic Software Scheduler (SchM). Il gère l'ordonnancement, les modes, les déclencheurs et les Exclusive Areas des modules BSW. La méthodologie prévoit pour cela une étape de génération propre, qui ne produit que le code du scheduler (TR Methodology p. 463).

Le générateur décrit la RTE générée elle-même comme un module BSW. En font partie BswModuleDescription, BswInternalBehavior et BswImplementation [SWS_Rte_05165] [SWS_Rte_05166] [SWS_Rte_05167]. Les API de cycle de vie de Rte et de SchM y apparaissent sous la forme BswModuleEntry [SWS_Rte_05177]. Les fichiers d'interface centraux sont :

  • Rte.h [SWS_Rte_01157] et l'en-tête de cycle de vie Rte_Main.h [SWS_Rte_01158],
  • Rte_Type.h avec les déclarations de types [SWS_Rte_01161],
  • l'Application Header Rte_[Byps_]<name>.h pour chaque type de composant [SWS_Rte_01003],
  • Rte_Cbk.h avec les prototypes de callback [SWS_Rte_03796].

Diagramme de contexte : la RTE assure l'intermédiation entre les SW-C et les services BSW OS, IOC, COM, LdCom, NvM (via NvBlockSwComponentType) et BndM. Le BSW-Scheduler fait partie du même code généré. Sources : [SWS_Rte_02250], [SWS_Rte_03001], [SWS_Rte_01377], [SWS_Rte_03884], SWS RTE p. 259, SWS OS p. 128

Interaction et chemins d'interaction

Une SW-C se compose de plusieurs RunnableEntitys. La RTE les démarre conformément aux RTEEvents associés [SWS_Rte_02202] [SWS_Rte_02203] (SWS RTE p. 119).

Pour la communication Sender-Receiver :

  • Tampon : la mise en mémoire tampon s'effectue du côté récepteur [SWS_Rte_02515].
    • « data » (non queued) suit la règle last-is-best : une nouvelle valeur écrase l'ancienne [SWS_Rte_02516] [SWS_Rte_02520].
    • Les « events » arrivent dans une file d'attente FIFO [SWS_Rte_02521] [SWS_Rte_02522]. Lorsque le tampon est plein, le nouvel événement est rejeté et un indicateur d'erreur est positionné [SWS_Rte_02523]. L'application le voit sous la forme RTE_E_LOST_DATA [SWS_Rte_02571].
  • Modes d'accès :
    • Lors de la lecture implicite, la RTE met à disposition avant le démarrage du runnable une copie qui reste inchangée pendant l'exécution [SWS_Rte_06000] [SWS_Rte_06001] [SWS_Rte_06004].
    • De manière explicite, les runnables accèdent via Rte_Read, Rte_Receive et Rte_Send [SWS_Rte_01091] [SWS_Rte_01092] [SWS_Rte_01072].
    • De manière implicite, les runnables écrivent via Rte_IWrite [SWS_Rte_03744].

Communication inter-ECU via COM :

  • La RTE transmet les données composites de manière atomique via des groupes de signaux [SWS_Rte_04527] [SWS_Rte_03008] (SWS RTE p. 326).
  • COM signale les événements via des callbacks tels que Rte_COMCbk_<sn> [SWS_Rte_03530] [SWS_Rte_03001]. Ces callbacks activent des runnables ou réveillent des runnables de catégorie 2 aux points d'attente [SWS_Rte_03531] [SWS_Rte_03532].
  • Les filtres de valeur s'exécutent dans COM pour la communication inter-ECU, et dans la RTE pour la communication intra-ECU [SWS_Rte_05500].
  • Différence de version : dans R20-11, [SWS_Rte_04505] exige le ComHandleId. Le passage documentaire plus récent parle à la place du Com Symbolic Name (SWS RTE p. 324).

Grands tableaux d'octets via LdCom :

  • Dans R20-11, la RTE envoie et reçoit de grands tableaux d'octets via LdCom et LdCom_Transmit [SWS_Rte_01376] [SWS_Rte_01377] [SWS_Rte_01378].
  • En cas de transmission TP, la RTE verrouille le tampon de signal jusqu'à la confirmation [SWS_Rte_01379] [SWS_Rte_01380] (SWS RTE p. 350).
  • Différence de version : le passage de R25-11 décrit à la place « Large Data Path in COM » avec Com_Transmit (SWS RTE p. 343). Pour R20-11, LdCom s'applique.

Communication client-serveur :

  • Les clients effectuent des appels synchrones ou asynchrones via Rte_Call [SWS_Rte_01102] [SWS_Rte_01293] [SWS_Rte_01294]. Ils récupèrent les résultats asynchrones avec Rte_Result [SWS_Rte_01111].
  • Si l'appel n'est pas un appel de fonction direct, la RTE met en mémoire tampon les requêtes côté serveur dans une file d'attente FIFO et les réponses côté client avec une longueur de file de 1 [SWS_Rte_02527] [SWS_Rte_02528]. Elle sérialise l'accès au serveur via la file d'attente des requêtes [SWS_Rte_02530].
  • La RTE surveille les dépassements de délai indépendamment du mode de réception [SWS_Rte_03763] (SWS RTE p. 358).

Autres chemins :

  • Les demandes NvM des SW-C sont transmises par les runnables du NvBlockSwComponentType au NvM (SWS RTE p. 259). Les valeurs de retour des API NvM sont régies par [SWS_Rte_04535].
  • La RTE lit les Bulk-NvData via le BndM [SWS_Rte_03883] [SWS_Rte_03884].
  • Entre les cœurs, Rte_Call écrit dans l'IOC et active la Server-Task sur le cœur cible (SWS OS p. 128). Dans les IOC-Callbacks, la RTE n'exécute pas d'ExecutableEntities, et elle empêche les accès simultanés à la même IOC-API [SWS_Rte_02736] [SWS_Rte_02737].

Synchronisation, réentrance et contextes de tâches

Contextes d'exécution :

  • Les runnables s'exécutent dans le contexte d'une tâche d'OS ou d'une ISR2 (SWS RTE p. 119). Au sein d'une tâche, la RTE respecte l'ordre d'exécution configuré [SWS_Rte_02207].
  • Les interruptions de catégorie 1 ne doivent pas atteindre la RTE. Le générateur rejette les configurations correspondantes [SWS_Rte_03594] (SWS RTE p. 182).
  • Une ISR2 peut activer des ExecutableEntities via des déclencheurs externes [SWS_Rte_04564]. En revanche, la RTE ne laisse pas s'exécuter les runnables des SW-C dans un contexte d'interruption [SWS_Rte_03600].
  • Les callbacks de la RTE ne doivent pas être bloquants [SWS_Rte_01165].
  • Le fait que Schedule soit appelé après un runnable est régi par [SWS_Rte_05113] à [SWS_Rte_05115].

Cohérence des données : la RTE garantit la cohérence pour la communication via les interfaces AUTOSAR [SWS_Rte_03514] et pour les InterRunnableVariables [SWS_Rte_03516].

  • Pour les InterRunnableVariables implicites, elle évite les accès simultanés. Pour les explicites, elle bloque les accès concurrents [SWS_Rte_03517] [SWS_Rte_03519] (SWS RTE p. 207).
  • L'entrée et la sortie des Exclusive Areas s'effectuent avec Rte_Enter et Rte_Exit [SWS_Rte_03515] [SWS_Rte_01120] [SWS_Rte_01123]. Différentes zones peuvent être imbriquées [SWS_Rte_01122].
  • RteExclusiveAreaImplMechanism sélectionne le mécanisme de protection : ALL_INTERRUPT_BLOCKING [SWS_Rte_03504], OS_INTERRUPT_BLOCKING [SWS_Rte_05164], OS_RESOURCE [SWS_Rte_03595] ou NONE [SWS_Rte_03999].
  • Si des runnables appellent une API bloquante au sein d'une Exclusive Area, celle-ci renvoie RTE_E_IN_EXCLUSIVE_AREA [SWS_Rte_02739].

Réentrance :

  • La même instance de runnable ne peut être activée de manière concurrente que si canBeInvokedConcurrently est défini [SWS_Rte_03523] [SWS_Rte_05083].
  • La RTE ne prend en charge les instances multiples que par le biais du partage de code [SWS_Rte_03015] [SWS_Rte_02002]. L'instance est identifiée par l'Instance Handle que l'Entry Point reçoit comme premier paramètre [SWS_Rte_01016] [SWS_Rte_02015].
  • Comme les instances sont ordonnancées de manière indépendante, les Entry Points doivent être réentrants (SWS RTE p. 804).

Systèmes multicœurs et à partitions : ici, [SWS_Rte_02711] restreint les variables globales dans Rte.c. De plus, [SWS_Rte_02712] exige des fichiers propres Rte_Partition_<PartitionName>.

Cycles de vie et modes de fonctionnement

Démarrage du BSW-Scheduler :

  • Avant son initialisation, seuls SchM_Enter et SchM_Exit sont disponibles (SWS RTE p. 400).
  • SchM_Start est toujours généré, retourne dans un temps fini et doit être appelé avant BswM_Init() [SWS_Rte_04546] [SWS_Rte_04547] [SWS_Rte_04548] (SWS RTE p. 927).
  • SchM_StartTiming démarre les événements périodiques et nécessite un appel préalable à SchM_Init [SWS_Rte_04549] [SWS_Rte_04550] [SWS_Rte_04551].
  • Les trois appels sont effectués exactement une fois par cœur par l'EcuM (SWS RTE p. 928).

Démarrage de la RTE :

  • L'EcuM appelle Rte_Start à la fin de la Startup Phase II, lorsque l'OS est disponible et que tous les modules BSW sont initialisés [SWS_Rte_02569] [SWS_Rte_02585] (SWS RTE p. 460).
  • En cas d'échec d'une allocation de ressources, Rte_Start renvoie RTE_E_LIMIT, sinon RTE_E_OK [SWS_Rte_01261] [SWS_Rte_01262] (SWS RTE p. 806).
  • Des valeurs initiales protègent les récepteurs contre les données non initialisées [SWS_Rte_06009] [SWS_Rte_06010] [SWS_Rte_02517].

Shutdown et redémarrage de partition :

  • Rte_Stop a lieu au début de la Shutdown Phase I [SWS_Rte_02570] [SWS_Rte_02584]. Si une ressource ne peut pas être libérée, la fonction signale RTE_E_LIMIT [SWS_Rte_01260].
  • Après cela, la RTE n'active plus aucun runnable sur ce cœur [SWS_Rte_02538].
  • Avant l'initialisation complète et après l'arrêt, la RTE ignore les requêtes client-serveur entrantes ainsi que les données Sender-Receiver [SWS_Rte_02535] [SWS_Rte_02536] (SWS RTE p. 461). Le BSW-Scheduler se comporte de manière analogue [SWS_Rte_04552].
  • Lors d'un redémarrage de partition, la RTE rétablit un environnement initial [SWS_Rte_02735].

Sources : [SWS_Rte_04546], [SWS_Rte_04549], [SWS_Rte_02569], [SWS_Rte_02570], [SWS_Rte_02538], SWS RTE p. 400, SWS RTE p. 460

Gestion des modes :

  • La RTE gère le mode actif de chaque Mode Machine Instance [SWS_Rte_02546] et initie lors de l'initialisation la transition vers les modes initiaux [SWS_Rte_02544] (SWS RTE p. 433).
  • Un Mode Manager demande des changements via Rte_Switch [SWS_Rte_02631]. Les notifications arrivent dans une file d'attente FIFO par instance [SWS_Rte_02718] [SWS_Rte_02719].
  • Lorsque la file d'attente est pleine, la nouvelle notification est rejetée [SWS_Rte_02720]. Entre partitions, la RTE signale alors RTE_E_LIMIT [SWS_Rte_02675]. Ce n'est qu'après l'achèvement du changement qu'elle retire la notification de la file d'attente [SWS_Rte_02721].
  • [SWS_Rte_02665] divise la transition elle-même en dix étapes (EXP ModeManagementGuide p. 15) :
    1. Activer les Mode Disablings [SWS_Rte_02661].
    2. Exécuter les entités on-exit [SWS_Rte_02562].
    3. Exécuter les entités on-transition [SWS_Rte_02707] [SWS_Rte_02708].
    4. Exécuter les entités on-entry [SWS_Rte_02564].
    5. Basculer les Mode Disablings [SWS_Rte_02563].
    6. Déclencher les ModeSwitchedAckEvents [SWS_Rte_02587].
  • Les runnables en cours d'exécution ne sont pas interrompus lors d'un changement de mode [SWS_Rte_02504]. Même un changement vers le même mode est intégralement exécuté [SWS_Rte_02669].
  • Le Mode Manager interroge la confirmation via Rte_SwitchAck [SWS_Rte_02725].
  • Les modes peuvent en outre activer des Schedule Tables de l'OS [SWS_Rte_05146].

Diagramme d'activité : une demande de changement de mode est mise en file d'attente ou rejetée si la file est pleine. Elle parcourt ensuite les étapes de transition ordonnées jusqu'à la confirmation. Sources : [SWS_Rte_02665], [SWS_Rte_02718], [SWS_Rte_02720], [SWS_Rte_02721], [SWS_Rte_02587], EXP ModeManagementGuide p. 15

Traitement des erreurs, traçage et dégradation

La SW-C ne reçoit les états d'erreur qu'en tant que valeur de retour de l'API RTE de type Std_ReturnType [SWS_Rte_01034] (SWS RTE p. 579). La spécification distingue trois classes d'erreurs :

  • Les Immediate Infrastructure Errors écrasent les erreurs d'application [SWS_Rte_02593].
  • Les Overlayed Errors utilisent un bit propre et peuvent être combinées avec d'autres erreurs [SWS_Rte_01318] (SWS RTE p. 686).
  • Les erreurs d'application occupent les 6 bits de poids faible [SWS_Rte_02573].

Dégradation :

  • Pour les ports non connectés, la RTE définit un comportement fixe [SWS_Rte_01329] [SWS_Rte_01330]. Rte_Call signale alors RTE_E_UNCONNECTED [SWS_Rte_01334].
  • Les émetteurs invalident les données par Rte_Invalidate [SWS_Rte_01206], activé via handleInvalid [SWS_Rte_05024]. En intra-ECU, la RTE met elle-même en œuvre l'invalidation [SWS_Rte_05025] :
    • Avec keep, elle traite la réception comme une erreur [SWS_Rte_05030].
    • Avec replace, elle remplace la valeur invalide par le initValue [SWS_Rte_05049].
  • Les valeurs invalides conduisent à RTE_E_INVALID [SWS_Rte_02626]. Lorsque la vérification de plage (range check) est active, les valeurs hors plage mènent à RTE_E_OUT_OF_RANGE [SWS_Rte_03845] [SWS_Rte_03846] [SWS_Rte_01371] (SWS RTE p. 420).
  • La surveillance des données obsolètes suit aliveTimeout. La valeur 0 la désactive [SWS_Rte_03759] [SWS_Rte_02710]. En cas d'accès implicite, Rte_IStatus fournit le statut [SWS_Rte_02600].

Sources : [SWS_Rte_03004], [SWS_Rte_03531], [SWS_Rte_01135], [SWS_Rte_01091], [SWS_Rte_02626], [SWS_Rte_01371], SWS RTE p. 326

Protection de la mémoire : dans les systèmes à mémoire protégée, la RTE vérifie les pointeurs provenant de partitions non approuvées (untrusted) avant de les transmettre [SWS_Rte_02752] [SWS_Rte_02753]. Elle signale les violations sous la forme RTE_E_SEG_FAULT [SWS_Rte_02754] (SWS RTE p. 378).

Erreurs de configuration : le générateur intercepte de nombreuses erreurs dès le moment de la génération et rejette la configuration, par exemple [SWS_Rte_02009] et [SWS_Rte_05083]. Le niveau de rigueur de sa vérification est contrôlé par strictConfigurationCheck [SWS_Rte_05148] [SWS_Rte_05149].

Traçage : la charge utile ne contient aucune exigence DET ou DEM de la RTE. L'observabilité est offerte à la place par le traçage VFB, qui peut être désactivé ou activé pour des événements configurés [SWS_Rte_01327] [SWS_Rte_01328]. Il sert au débogage des SW-C, et non de la RTE elle-même (SWS RTE p. 836). Les hooks de début d'API [SWS_Rte_01238] et Task_Dispatch [SWS_Rte_01244] sont des exemples de hooks. Ils sont déclarés dans l'en-tête Rte_Hook[_<client>].h [SWS_Rte_01250].

Prise en charge de la mesure et de la calibration

La RTE alloue la mémoire pour les paramètres de calibration [SWS_Rte_03961] (SWS RTE p. 241). Parmi les méthodes d'émulation avec support SW, une seule est active à la fois [SWS_Rte_03909] [SWS_Rte_03943] :

  • Single Pointered : table de référence en RAM [SWS_Rte_03913].
  • Double Pointered : table de référence en ROM ou Flash [SWS_Rte_03914].
  • InitRam : copie en RAM des paramètres issus de la ROM/Flash [SWS_Rte_03915].

La prise en charge de la mesure peut être désactivée séparément [SWS_Rte_03903]. Le générateur documente la méthode choisie et les informations de symboles dans McSupportData et McSwEmulationMethodSupport [SWS_Rte_05118] [SWS_Rte_05137] (SWS RTE p. 258).
