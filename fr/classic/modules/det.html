Rôle du Default Error Tracer et sa limite système

Le Default Error Tracer (DET) reçoit les signalements d'erreurs de manière centralisée dans la pile Classic. Il propose trois services de notification. Det_ReportError sert pour les erreurs de développement [SWS_Det_00009], Det_ReportRuntimeError pour les erreurs d'exécution [SWS_Det_01001]. Pour les erreurs transitoires, la R20-11 propose encore Det_ReportTransientFault [SWS_Det_01003]. À cela s'ajoutent les services d'administration Det_Init, Det_Start et Det_GetVersionInfo [SWS_Det_00008] [SWS_Det_00010] [SWS_Det_00011]. Tous les services sont disponibles via Det.h.

Le DET n'évalue pas lui-même fonctionnellement les notifications. Il les distribue aux Error Hooks et Callouts configurés (SWS DET p. 16). Selon la description d'erreur valable pour la R20-11, il atteint ainsi le DEM et la RTE via du code spécifique à l'intégrateur (ErrorDescription p. 10). De plus, une transmission optionnelle vers le Dlt via Dlt_DetForwardErrorTrace est prévue [SWS_Det_00211].

Diagramme de contexte : le DET se situe entre les modules émetteurs et le code intégrateur. Seuls la configuration et les callouts ouvrent la voie vers le DEM et le Dlt. Sources : SWS DET Abb. Interfaces p. 28, ErrorDescription p. 10, [SWS_Det_00211]

Démarrage : Det_Init et Det_Start dans la séquence de démarrage de l'EcuM

L'EcuM répertorie Det_Init et Det_ReportError parmi ses interfaces optionnelles (SWS EcuM p. 142). Det_Init possède la Service-ID 0x00 et est synchrone et non réentrant. Le paramètre ConfigPtr pointe vers le jeu de configuration sélectionné [SWS_Det_00008]. Le type de ce dernier, Det_ConfigType, présente une structure spécifique à l'implémentation [SWS_Det_00210]. Det_Start (0x02) démarre le traceur et est également synchrone et non réentrant [SWS_Det_00010].

D'après le schéma d'initialisation, l'EcuM appelle d'abord Det_Init, puis Det_Start (SWS DET Abb. Initialisierung p. 32). Les sources ne précisent pas quels services sont déjà effectifs entre les deux appels. Ce point reste ouvert ici. Det_GetVersionInfo (0x03) est réentrant et écrit les informations de version dans le pointeur transmis [SWS_Det_00011].

Diagramme de séquence : l'EcuM initialise le DET avec un jeu de configuration, puis le démarre. Ce n'est qu'ensuite que suivent les notifications en fonctionnement. Sources : SWS DET Abb. Initialisierung p. 32, [SWS_Det_00008], [SWS_Det_00010]

Trois voies de signalement avec un schéma de numérotation commun

Les trois services de notification ont les mêmes paramètres : ModuleId (uint16), InstanceId, ApiId et ErrorId ou FaultId (chacun uint8) [SWS_Det_00009] [SWS_Det_01001] [SWS_Det_01003].

  • Le ModuleId provient de la liste des modules du logiciel de base. La BSW n'utilise que la plage 0..255.
  • Le InstanceId compte à partir de 0. Un module ne comportant qu'une seule instance transmet 0.
  • ApiId et ErrorId sont définis par la SWS du module notificateur (EXP LSA p. 157).

Le service applicable dépend du type d'erreur :

  • Un module BSW signale les erreurs de développement via Det_ReportError avec son identifiant de module. Cela ne s'applique que si la détection des erreurs de développement est configurée (SWS BSWGeneral p. 57). Une requête telle que #if (SPI_DEV_ERROR_DETECT == ON) (EXP LSA p. 113) est typique à cet effet. Un exemple est un paramètre non valide dans la CanIf (SWS CanIf p. 101).
  • Les erreurs d'exécution telles que ADC_E_BUSY passent par Det_ReportRuntimeError (SWS Adc p. 95).
  • Les erreurs transitoires passent par le service de fautes transitoires (SWS BSWGeneral p. 53).

Dans sa description de module, un module déclare ce besoin sous la forme de ErrorTracerNeeds. Chacun des trois services y constitue un rôle optionnel (TPS BSWMDT p. 266).

Note sur la version : Det_ReportTransientFault est normatif dans R20-11 [SWS_Det_01003]. Les versions ultérieures mentionnent le service comme obsolète (SWS DET p. 24). Avec R24-11, les erreurs transitoires ont été totalement supprimées (SWS DET p. 1).

Diagramme d'activité : le type d'erreur détermine le service de notification, la liste des hooks ou callouts appelés ainsi que la conséquence pour l'émetteur. Sources : SWS BSWGeneral p. 57, [SWS_Det_00501], [SWS_Det_00009]

Distribution aux Error Hooks et Callouts

Chaque appel de Det_ReportError appelle toutes les fonctions configurées dans DetErrorHook [SWS_Det_00501]. Les hooks reçoivent les mêmes paramètres que l'appel initial (SWS DET p. 16). L'interface de hook <User_Error_Hooks> a la Service-ID 0x10 et est synchrone et réentrante [SWS_Det_00181]. Elle renvoie toujours E_OK (SWS DET p. 25).

Diagramme de séquence : Det_ReportError appelle successivement tous les hooks configurés, et optionnellement le Dlt. Dans R20-11, le service ne retourne pas à l'émetteur. Sources : SWS DET Abb. ReportError p. 36, [SWS_Det_00501], [SWS_Det_00009], SWS Dlt p. 25

Pour Det_ReportRuntimeError, le même principe s'applique avec la liste DetReportRuntimeErrorCallout [SWS_Det_00501]. Le callout <DetReportRuntimeErrorCallout> a la Service-ID 0x11 [SWS_Det_00184]. Le DET renvoie E_OK au notificateur (SWS DET Abb. Runtime mit Hook p. 35). Si aucun callout n'est configuré, il répond immédiatement avec E_OK (SWS DET Abb. Runtime ohne Hook p. 35).

Diagramme de séquence : en cas d'erreurs d'exécution, E_OK est la valeur de retour, avec ou sans callouts configurés. Sources : SWS DET Abb. Runtime mit Hook p. 35, SWS DET Abb. Runtime ohne Hook p. 35, [SWS_Det_00184]

Le DET distribue les erreurs transitoires à la liste DetReportTransientFaultCallout [SWS_Det_00501]. Le callout a la Service-ID 0x12 [SWS_Det_00187]. Contrairement aux erreurs d'exécution, le DET transmet ici la valeur de retour du callout au notificateur. Sans callout, il fournit E_OK (SWS DET Abb. Transient mit Hook p. 36, SWS DET Abb. Transient ohne Hook p. 36). La version ultérieure définit pour plusieurs callouts le OU logique des valeurs de retour (SWS DET p. 24). Cette règle s'applique probablement déjà dans R20-11.

Diagramme de séquence : en cas d'erreurs transitoires, le résultat des callouts détermine la valeur retournée à l'émetteur. Sources : SWS DET Abb. Transient mit Hook p. 36, SWS DET Abb. Transient ohne Hook p. 36, [SWS_Det_00187]

Raccordement des SW-C via le port de service DETService

Les SW-C accèdent au DET via la RTE. Pour chaque instance de module configurée, le DET met à disposition un port Det_{Name} avec l'interface DETService [SWS_Det_00205]. Les opérations ReportError et ReportRuntimeError appellent l'API C avec l'identifiant de module du port [SWS_Det_00202]. Les types requis uint8 et uint16 sont des types de données AUTOSAR [SWS_Det_00200].

ModuleId et InstanceId ne sont pas transmis par la SW-C elle-même. La RTE les complète en tant que « port defined argument values » [SWS_Det_00203] [SWS_Det_00204]. Leur définition relève donc de la configuration de la RTE [SWS_Det_00206]. ApiId et ErrorId ne sont pas standardisés pour les SW-C et se situent dans la plage 0x00..0xFF [SWS_Det_00203].

Diagramme de collaboration : chaque instance de SW-C possède son propre port DET. La RTE complète alors les identifiants. Sources : SWS DET Abb. Service-Ports p. 33, [SWS_Det_00205], [SWS_Det_00206]

Configuration des listes de hooks et des signatures de callouts

La notification est configurée dans le conteneur DetNotification (0..1). Il contient les listes DetErrorHook et DetReportRuntimeErrorCallout (chacune 0..*). Dans la version ultérieure présente, elles ont la classe de configuration Pre-compile (SWS DET p. 37). R20-11 contient en plus la liste DetReportTransientFaultCallout [SWS_Det_00501]. Un hook doit avoir le même type que Det_ReportError, c'est-à-dire Std_ReturnType (*f)(uint16, uint8, uint8, uint8).

En général, les callouts ont la même signature que la fonction associée. Plusieurs callouts pour le même service portent la même ID (SWS DET p. 25). La description d'erreur de R20-11 limite ce que ces handlers sont autorisés à faire : enregistrer l'événement, appeler le DEM ou exécuter des actions courtes et appropriées (ErrorDescription p. 10). Les trois interfaces de callout sont spécifiées comme réentrantes [SWS_Det_00181] [SWS_Det_00184] [SWS_Det_00187].

Comportement en cas d'erreur

Dans R20-11, la mention pour Det_ReportError sous Sync/Async est « Not Applicable: The function never returns » [SWS_Det_00009]. Les erreurs de développement sont donc traitées comme des assertions. Après les hooks, le flux de contrôle normal ne se poursuit pas, par exemple en raison d'une boucle infinie ou d'un arrêt. Si un seul hook est configuré, celui-ci peut prendre en charge le traitement des exceptions (RS BSWGeneral p. 33).

Le schéma de déroulement s'en écarte : il montre une flèche de retour et qualifie le comportement de dépendant de l'implémentation (SWS DET Abb. ReportError p. 36). Ce n'est qu'avec R21-11 que le comportement d'appel a été clarifié (SWS DET p. 1). Pour R20-11, l'exigence fait foi.

En cas d'erreurs d'exécution, l'émetteur continue son exécution car Det_ReportRuntimeError renvoie toujours E_OK [SWS_Det_01001] (SWS DET p. 23). En cas d'erreurs transitoires, l'émetteur reçoit le résultat des callouts comme valeur de retour [SWS_Det_01003] (SWS DET Abb. Transient mit Hook p. 36).

Le DET lui-même ne connaît qu'une seule erreur de développement propre : DET_E_PARAM_POINTER (0x01). Elle survient lorsque Det_GetVersionInfo est appelé avec un pointeur nul [SWS_Det_00301]. Le DET signale cette erreur à toutes les fonctions configurées dans les callouts. Les erreurs d'exécution et de production ne sont pas applicables au DET (SWS DET p. 18).

La fonction Det_ReportError sert de service central du Default Error Tracer (DET) pour le signalement d'erreurs de développement ([SWS_Det_00009]). L'interface est disponible via le fichier d'en-tête Det.h.

Utilisation et paramètres

L'appel est effectué par des modules BSW lors de la détection d'une erreur de développement en transmettant le contexte exact de l'erreur ([SWS_Det_00009]) :

  • ModuleId : Identifiant de module du module logiciel appelant.
  • InstanceId : ID d'instance du module basée sur un index (commençant à 0 ; les modules ne comportant qu'une seule instance transmettent 0).
  • ApiId : Identifiant du service API dans lequel l'erreur est survenue.
  • ErrorId : Identifiant de l'erreur de développement spécifique conformément à la spécification du module appelant.

Formellement, la fonction possède le type de retour Std_ReturnType, mais ne renvoie aucune valeur et ne possède ce type qu'à des fins de compatibilité avec les services et hooks ([SWS_Det_00009]). Une classification en sémantique synchrone ou asynchrone n'est pas applicable, étant donné que Det_ReportError ne retourne jamais vers l'appelant selon la spécification ([SWS_Det_00009]).

Concurrence et déroulement

La fonction est spécifiée comme réentrante ([SWS_Det_00009]). Lors d'un appel de Det_ReportError, le DET exécute toutes les fonctions de callback ayant été configurées dans le paramètre DetErrorHook ([SWS_Det_00501]).

Interaction

D'autres modules BSW signalent directement les erreurs de paramètres à ce service. Ainsi, l'interface CAN signale par exemple le code d'erreur CANIF_E_PARAM_TRCV en cas de paramètre TransceiverId non valide dans CanIf_SetTrcvMode() ou CanIf_SetTrcvWakeupMode() ([SWS_CANIF_00538], CAN Interface §8.3 « CanIf_SetTrcvMode » ; [SWS_CANIF_00535], CAN Interface §8.3 « CanIf_SetTrcvWakeupMode »). En présence d'un paramètre de mode non autorisé, CanIf_SetTrcvWakeupMode() signale de manière correspondante CANIF_E_PARAM_TRCVWAKEUPMODE à Det_ReportError ([SWS_CANIF_00536], CAN Interface §8.3 « CanIf_SetTrcvWakeupMode »).

Cette note d'utilisation est basée sur les spécifications de la version R20-11 d'AUTOSAR.

Utilisation et signature

Le service synchrone Det_ReportRuntimeError ([SWS_Det_01001]) sert au signalement d'erreurs d'exécution au Default Error Tracer (DET) et est disponible via l'en-tête Det.h. La fonction possède les paramètres suivants :

  • ModuleId : Identifiant de module du module appelant.
  • InstanceId : ID d'instance du module basée sur un index (pour les modules à instance unique, 0).
  • ApiId : Identifiant du service API dans lequel l'erreur a été détectée.
  • ErrorId : Identifiant spécifique de l'erreur d'exécution détectée (défini dans la spécification du module appelant).

La valeur de retour est toujours E_OK ([SWS_Det_01001]).

Concurrence et comportement

L'interface est définie comme réentrante ([SWS_Det_01001]). Lors de l'appel de Det_ReportRuntimeError, toutes les fonctions de callback configurées dans DetReportRuntimeErrorCallout sont appelées ([SWS_Det_00503]).

Interaction et contexte d'erreur

Les modules appelants utilisent le service pour signaler des états d'erreur spécifiques pendant l'exécution. Ainsi, le module CanIf signale par exemple le code d'erreur CANIF_E_STOPPED à Det_ReportRuntimeError lors d'une demande d'émission sur un canal en mode CANIF_OFFLINE ([SWS_CANIF_00382], AUTOSAR_SWS_CANInterface p. 40 §7.10 « Transmit data flow »). Un autre cas d'utilisation est le dépassement de la longueur globale de PDU lorsque la troncature est désactivée dans CanIf_Transmit(), ce qui déclenche le signalement de l'erreur d'exécution CANIF_E_TXPDU_LENGTH_EXCEEDED ([SWS_CANIF_00900], AUTOSAR_SWS_CANInterface p. 81 §8.3.7 « CanIf_ReadRxPduData »).

Cette note d'utilisation est basée sur la spécification AUTOSAR Classic Release R20-11.

Utilisation et sémantique

La fonction Det_ReportTransientFault sert, selon [SWS_Det_01003], à signaler des fautes transitoires au Default Error Tracer. Le service est exécuté de manière synchrone et est spécifié comme réentrant. La déclaration est fournie via Det.h.

Les paramètres transmis comprennent :

  • ModuleId : identifiant de module du module logiciel appelant.
  • InstanceId : ID d'instance du module basé sur un index (commençant à 0 ; les modules à instance unique transmettent toujours 0).
  • ApiId : identificateur du service d'API dans lequel la faute transitoire s'est produite.
  • FaultId : identificateur de chaque faute transitoire détectée.

Interaction et comportement du callout

Lors de l'appel de Det_ReportTransientFault, toutes les fonctions de rappel configurées sous DetReportTransientFaultCallout sont appelées conformément à [SWS_Det_00502].

Pour la valeur de retour de type Std_ReturnType, la sémantique suivante s'applique selon [SWS_Det_01003] :

  • Si aucun callout n'est configuré, un retour immédiat a lieu avec E_OK.
  • Si un callout est présent, la valeur de retour de ce callout configuré est renvoyée.
  • Si plusieurs callouts sont configurés, le OU logique (somme) de toutes les valeurs de retour des callouts est renvoyé. E_OK = 0 étant défini, le service ne renvoie E_OK que si, sans exception, tous les callouts appelés signalent E_OK.

Concurrence et restrictions

En raison de la réentrance spécifiée ([SWS_Det_01003]), l'interface peut être appelée de manière concurrente par plusieurs instances de module ou tâches, à condition que les callouts configurés prennent en charge ce comportement.

Cette note d'utilisation est basée exclusivement sur le contenu de spécification d'AUTOSAR Classic R20-11.

Utilisation

La fonction de callback <User_Error_Hooks> selon [SWS_Det_00181] sert d'interface de hook spécifique à l'utilisateur pour la notification d'erreurs de développement survenues dans le Default Error Tracer (DET). Elle possède le Service-ID 0x10 et est fournie via le fichier d'en-tête Det_Externals.h.

L'appel a lieu de manière synchrone au moment du signalement de l'erreur. L'interface accepte les paramètres suivants :

  • ModuleId (uint16) : Identifiant de module du module logiciel émetteur.
  • InstanceId (uint8) : ID d'instance du module basée sur un index (commençant à 0 ; pour les modules à instance unique, il convient de transmettre 0).
  • ApiId (uint8) : Identifiant du service API dans lequel l'erreur a été détectée (conformément à la spécification du module source).
  • ErrorId (uint8) : Identifiant de l'erreur de développement détectée (conformément à la spécification du module source).

Valeur de retour et traitement des erreurs

La fonction renvoie toujours E_OK comme valeur de retour de type Std_ReturnType [SWS_Det_00181]. Aucun état d'erreur propre ni aucune valeur de retour divergente ne sont pris en charge ; un acheminement interne vers le Diagnostic Event Manager (DEM) ou des journaux d'erreurs distincts n'est pas prévu à cette interface selon la spécification.

Concurrence et restrictions

Conformément à [SWS_Det_00181], la fonction est définie comme réentrante. Le traitement s'effectuant de manière synchrone, l'implémentation du hook spécifique à l'utilisateur devrait être conçue comme non bloquante afin de ne pas retarder indûment le temps d'exécution du composant appelant.

Utilisation et contexte d'appel

La fonction callout <Det Report Runtime Error Callout> est déclarée via l'en-tête Det_Externals.h [SWS_Det_00184]. L'appel s'effectue de manière synchrone et est spécifié comme réentrant [SWS_Det_00184]. Comme valeur de retour, la fonction renvoie toujours E_OK de type Std_ReturnType, car cela est prescrit pour les services [SWS_Det_00184].

L'interface possède l'ID de service 0x11 et attend quatre paramètres d'entrée [SWS_Det_00184] :

  • ModuleId : identifiant (Module ID) du module logiciel émetteur [SWS_Det_00184].
  • InstanceId : ID d'instance du module basé sur un index commençant à 0. Si le module ne possède qu'une seule instance, la valeur 0 doit être transmise pour celle-ci [SWS_Det_00184].
  • ApiId : identificateur de la fonction d'API dans laquelle l'erreur d'exécution a été constatée, défini dans la spécification de l'appelant respectif [SWS_Det_00184].
  • ErrorId : identifiant de l'erreur d'exécution signalée conformément à la spécification du module appelant [SWS_Det_00184].

Gestion des erreurs et concurrence
