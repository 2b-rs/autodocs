Reçoit de manière centralisée les messages d'erreur du logiciel de base et des SW-C et les transmet aux hooks d'intégrateur.

Le Default Error Tracer reçoit de manière centralisée les messages d'erreur des modules BSW et des SW-C. Il existe pour cela Det_ReportError pour les erreurs de développement, Det_ReportRuntimeError pour les erreurs d'exécution et Det_ReportTransientFault pour les erreurs transitoires, chacune avec un identifiant de module, d'instance, d'API et d'erreur. Le DET transmet chaque message à tous les hooks ou callouts configurés de l'intégrateur [SWS_Det_00501]. Le fonctionnement est démarré par Det_Init et Det_Start depuis l'EcuM. La contrainte la plus importante : dans R20-11, Det_ReportError ne retourne pas à l'appelant, mais arrête le flux de contrôle du programme à la manière d'une assertion [SWS_Det_00009].

Le Default Error Tracer est le point de collecte central des messages d'erreur provenant du logiciel de base et des composants logiciels. Il propose trois services de notification de structure identique avec les paramètres ModuleId, InstanceId, ApiId et ErrorId ou FaultId : Det_ReportError pour les erreurs de développement, Det_ReportRuntimeError pour les erreurs d'exécution et Det_ReportTransientFault pour les erreurs transitoires ([SWS_Det_00009], [SWS_Det_01001], [SWS_Det_01003]). L'EcuM met en service le DET avec Det_Init, puis Det_Start ([SWS_Det_00008], SWS DET Fig. 1 p. 34).

Diagramme de contexte : Le DET reçoit des messages des modules BSW et des SW-C et les transmet à des hooks d'intégrateur et, optionnellement, à Dlt. Sources : SWS DET Fig. 2 p. 28, [SWS_Det_00202]

Le DET n'évalue pas lui-même les messages. Chaque service de notification appelle tous les hooks ou callouts configurés pour lui (DetErrorHook, DetReportRuntimeErrorCallout, DetReportTransientFaultCallout), et ce avec les mêmes paramètres que le message [SWS_Det_00501]. C'est via ce code d'intégrateur que le DET atteint également le DEM ou la mémoire des défauts. Les callouts doivent se limiter à des actions courtes et appropriées ErrorDescription p. 10.

Les SW-C émettent des notifications via l'interface client-serveur DETService. La RTE ajoute ModuleId et InstanceId sous forme de « port defined argument values » issues de la configuration du DET, et la SW-C reçoit toujours E_OK en retour ([SWS_Det_00203], [SWS_Det_00204]).

Pour les cas d'erreur, la manière dont les trois services retournent est déterminante. Det_ReportError ne retourne pas dans R20-11 : après les hooks, le flux de contrôle est arrêté, à l'instar d'une assertion ([SWS_Det_00009], RS BSWGeneral p. 33). En revanche, les messages d'exécution retournent avec E_OK. Les messages transitoires transmettent la valeur du callout, ou E_OK en l'absence de callout SWS DET Fig. 6 p. 36. Les erreurs transitoires sont supprimées à partir de R24-11, et les appels Dlt à partir de R25-11 SWS DET p. 1.

Diagramme de séquence : En cas d'erreur de développement, le DET appelle tous les hooks configurés et s'arrête ensuite sans retourner à l'émetteur. Sources : SWS DET Fig. 9.2 p. 34, [SWS_Det_00009]

Rôle du Default Error Tracer à la frontière du système

Le Default Error Tracer (DET) est le point de collecte central auquel les modules du logiciel de base et les composants logiciels signalent les erreurs détectées. Dans R20-11, il propose à cet effet trois services de notification de structure identique : Det_ReportError pour les erreurs de développement [SWS_Det_00009], Det_ReportRuntimeError pour les erreurs d'exécution [SWS_Det_01001] et Det_ReportTransientFault pour les erreurs transitoires [SWS_Det_01003]. S'y ajoutent les services de gestion Det_Init, Det_Start et Det_GetVersionInfo ([SWS_Det_00008], [SWS_Det_00010], [SWS_Det_00011]). Le DET n'évalue pas lui-même le contenu des messages. Il notifie les hooks d'erreur configurés à chaque message reçu SWS DET p. 16.

Vers l'extérieur, le DET est connecté de manière étroite. Comme seule interface attendue, la spécification mentionne la transmission optionnelle à Dlt via Dlt_DetForwardErrorTrace issu de Dlt_Det.h ([SWS_Det_00211], SWS DET Fig. 2 p. 28). Le DET n'atteint DEM et la RTE que par le biais de code spécifique à l'intégrateur au sein des callouts ErrorDescription p. 10.

Diagramme de contexte : Le DET reçoit des messages des modules BSW et, via la RTE, des SW-C. Il est démarré par l'EcuM et ne transmet les messages qu'au code d'intégrateur configuré et, optionnellement, à Dlt. Sources : SWS DET Fig. 2 p. 28, [SWS_Det_00202], [SWS_Det_00211], ErrorDescription p. 10

Démarrage : Initialisation et démarrage par l'EcuM

L'ECU State Manager initialise le DET avec Det_Init (service ID 0x00). Ce faisant, il transmet un pointeur vers le jeu de configuration sélectionné de type Det_ConfigType, dont le contenu est spécifique à l'implémentation ([SWS_Det_00008], [SWS_Det_00210]). Ensuite, Det_Start (service ID 0x02) démarre le traceur [SWS_Det_00010]. Les deux services sont synchrones et non réentrants. Le schéma R20-11 montre les deux appels successifs issus de l'EcuM SWS DET Fig. 1 p. 34. L'EcuM répertorie Det_Init et Det_ReportError de manière correspondante comme interfaces optionnelles SWS EcuM p. 142.

La spécification ne justifie pas pourquoi l'initialisation et le démarrage sont séparés. Interprétation : cette division en deux étapes devrait permettre d'initialiser le DET très tôt lors du démarrage et de n'autoriser le fonctionnement régulier que lors d'une étape ultérieure [SWS_Det_00010].

Diagramme de séquence : L'EcuM appelle d'abord de manière synchrone Det_Init avec le pointeur de configuration, puis Det_Start. Sources : SWS DET Fig. 1 p. 34, [SWS_Det_00008], [SWS_Det_00010]

Trois voies de notification et leurs identifiants

Les trois services de notification partagent la même structure de paramètres :

  • ModuleId (uint16) ;
  • InstanceId (uint8), la valeur 0 pour les modules à instance unique ;
  • ApiId (uint8) ;
  • ErrorId ou FaultId (uint8).

Les identifiants d'API et d'erreur sont définis à chaque fois par la SWS du module émetteur ([SWS_Det_00009], [SWS_Det_01001], [SWS_Det_01003]). L'ID de module est issu de la liste des modules du logiciel de base. Le logiciel de base n'en utilise que la plage 0..255 EXP LSA p. 157.

Le choix de la bonne voie découle de la classification des erreurs. Les préconditions fondamentales violées sont des erreurs de développement et sont traitées comme une assertion ; des exemples sont des erreurs logicielles, une intégration défectueuse ou une configuration non valide. Les autres erreurs sont des erreurs d'exécution ou de production EXP LSA p. 154. Si la détection des erreurs de développement est configurée, les modules BSW signalent les erreurs de développement avec leur ID de module attribué via Det_ReportError SWS BSWGeneral p. 57. Un commutateur de préprocesseur tel que SPI_DEV_ERROR_DETECT active ou masque l'appel EXP LSA p. 113.

Diagramme d'activité : Si une précondition fondamentale est violée, une erreur de développement est signalée via Det_ReportError. Sinon, la pertinence diagnostique fait la distinction entre erreur de production et erreur d'exécution (Det_ReportRuntimeError). Sources : EXP LSA p. 154, [SWS_Det_00009], [SWS_Det_01001].

Les erreurs d'exécution sont par exemple signalées par le pilote ADC avec ADC_E_BUSY ou par Dds en cas de messages rejetés, à chaque fois via Det_ReportRuntimeError (SWS Adc p. 95, SWS Dds p. 53). Un module BSW décrit son besoin à l'aide du type de ServiceNeeds ErrorTracerNeeds. Ce dernier connaît les rôles Det_ReportError, Det_ReportRuntimeError et Det_ReportTransientFault TPS BSWMDT p. 266.

Hooks et callouts comme passerelle vers le code d'intégrateur

Chaque appel de Det_ReportError invoque toutes les fonctions configurées dans DetErrorHook. De même, Det_ReportRuntimeError et Det_ReportTransientFault appellent tous les callouts issus respectivement de DetReportRuntimeErrorCallout et DetReportTransientFaultCallout [SWS_Det_00501]. Les hooks et les callouts possèdent la signature du service déclencheur et reçoivent les mêmes paramètres ([SWS_Det_00181], [SWS_Det_00184], [SWS_Det_00187], SWS DET p. 16). L'interface de hook <User_Error_Hooks> possède le service ID 0x10. Elle est synchrone et réentrante et renvoie toujours E_OK SWS DET p. 25.

Ce que font les callouts relève de la décision de l'intégrateur. En cas d'erreurs d'exécution et transitoires, ils doivent se limiter à un petit nombre d'actions : enregistrer l'événement, appeler le DEM ou exécuter une autre action brève et appropriée ErrorDescription p. 10. Après un appel de Det_ReportRuntimeError, le DET retourne toujours avec E_OK, que des callouts soient configurés ou non (SWS DET Fig. 4 p. 35, SWS DET Fig. 5 p. 35).

Diagramme de séquence : Det_ReportRuntimeError appelle tous les callouts configurés et retourne dans tous les cas avec E_OK vers l'émetteur du signalement. Sources : SWS DET Fig. 4 p. 35, SWS DET Fig. 5 p. 35, [SWS_Det_00501]

Pour Det_ReportTransientFault, en revanche, le DET transmet la valeur de retour du callout à l'émetteur du signalement. Sans callout, il fournit E_OK (SWS DET Fig. 6 p. 36, SWS DET Fig. 7 p. 36). En présence de plusieurs callouts, une version ultérieure décrit une combinaison logique OU des valeurs de retour : E_OK n'est retourné que si tous les callouts fournissent E_OK. Cette règle devrait vraisemblablement déjà s'appliquer à R20-11 SWS DET p. 24.

Diagramme de séquence : Det_ReportTransientFault transmet les valeurs de retour des callouts à l'émetteur du signalement ; sans callout, il retourne E_OK. La combinaison OU en cas de callouts multiples est signalée comme une hypothèse. Sources : SWS DET Fig. 6 p. 36, SWS DET Fig. 7 p. 36, SWS DET p. 24

Raccordement de composants logiciels via des ports de service

Les SW-C accèdent au DET via l'interface client-serveur DETService. Ses opérations appellent Det_ReportError ou le signalement d'exécution avec l'ID de module du port [SWS_Det_00202]. ModuleId et InstanceId ne sont pas transmis par la SW-C elle-même. La RTE les complète sous forme de « port defined argument values », dont les valeurs proviennent de DetModuleId et DetInstanceId de la configuration du DET ([SWS_Det_00204], [SWS_Det_00205], [SWS_Det_00206]). Pour les SW-C, ApiId et ErrorId ne sont pas standardisés et peuvent être attribués librement dans la plage 0x00..0xFF. La valeur de retour est toujours E_OK [SWS_Det_00203]. L'interface de port utilise les types de données AUTOSAR uint8 et uint16 [SWS_Det_00200].

Diagramme de séquence : la SW-C ne transmet que ApiId et ErrorId. La RTE complète ModuleId et InstanceId à partir de la configuration, le retour est E_OK. Sources : [SWS_Det_00202], [SWS_Det_00203], [SWS_Det_00204], SWS DET Fig. 3 p. 33

Configuration des notifications

Les fonctions de notification se trouvent dans le conteneur optionnel DetNotification (multiplicité 0..1). Il contient les listes DetErrorHook et DetReportRuntimeErrorCallout (chacune 0..*). DetErrorHook est configuré au moment de la précompilation et requiert le type de fonction Std_ReturnType (*f)(uint16, uint8, uint8, uint8) SWS DET p. 37. Dans R20-11 s'y ajoute DetReportTransientFaultCallout [SWS_Det_00501]. Le schéma de paramètres montre en outre le conteneur obligatoire DetGeneral avec DetVersionInfoApi et DetForwardToDlt SWS DET (alt) Fig. 6 p. 43. À partir de DetConfigSet/DetModule et DetModuleInstance, la configuration forme les ports Det_{Name} ainsi que l'identifiant de module et d'instance [SWS_Det_00205].

Comportement en cas d'erreur

Les erreurs de développement sont traitées comme des assertions. Après l'appel des hooks configurés, le flux de contrôle normal ne se poursuit pas et le DET interrompt l'exécution, par exemple par une boucle infinie ou une instruction d'arrêt RS BSWGeneral p. 33. L'entrée relative à Det_ReportError dans R20-11 sous Sync/Async y correspond : « Not Applicable: The function never returns » [SWS_Det_00009]. Les schémas montrent ce HALT avec et sans hook configuré (SWS DET Fig. 9.2 p. 34, SWS DET Fig. 9.3 p. 35).

Diagramme de séquence : un module BSW détecte une erreur de développement et appelle Det_ReportError. Le DET appelle tous les hooks configurés, puis s'arrête sans retourner vers l'émetteur du signalement. Sources : SWS DET Fig. 9.2 p. 34, SWS DET Fig. 9.3 p. 35, [SWS_Det_00009], [SWS_Det_00501]

Certains schémas divergent à ce sujet. Un diagramme de séquence indique que le comportement synchrone ou asynchrone dépend de l'implémentation et représente un retour vers l'appelant SWS DET Fig. 5 p. 36. Le schéma Dio montre également un retour après Det_ReportError SWS Dio Fig. 5 p. 41. La référence normative pour R20-11 est [SWS_Det_00009]. Une clarification de l'indication Sync/Async n'a suivi qu'avec R21-11 SWS DET p. 1.

Les erreurs d'exécution et transitoires n'interrompent pas le flux d'exécution du programme : le DET retourne vers l'émetteur du signalement avec une valeur de retour ([SWS_Det_01001], [SWS_Det_01003]). Le DET lui-même ne connaît qu'une seule erreur de développement qui lui est propre. DET_E_PARAM_POINTER (0x01) survient lorsque Det_GetVersionInfo est appelé avec un pointeur nul [SWS_Det_00301]. Une version ultérieure stipule que cette erreur est signalée à tous les callouts configurés. C'est vraisemblablement aussi ainsi que cela doit être compris pour R20-11 SWS DET p. 18.

Preuves détaillées supplémentaires

  • [SWS_Det_00009] : signature de Det_ReportError, Service-ID 0x01, ne retourne pas.
  • [SWS_Det_01001], [SWS_Det_01003] : signalements d'exécution et transitoires avec les Service-ID 0x04 et 0x05.
  • [SWS_Det_00501] : obligation d'appeler tous les hooks et callouts configurés.
  • [SWS_Det_00181], [SWS_Det_00184], [SWS_Det_00187] : signatures des hooks et callouts avec les Service-ID 0x10, 0x11 et 0x12.
  • [SWS_Det_00202] à [SWS_Det_00206] : modèle de port de service pour les SW-C.
  • [SWS_Det_00008], [SWS_Det_00010], [SWS_Det_00210] : démarrage et type de configuration.
  • [SWS_Det_00211], [SWS_Det_00301] : transmission Dlt et erreur de développement propre.

Des versions ultérieures modifient le périmètre fonctionnel. Une version issue de R23-11/R24-11 marque Det_ReportTransientFault comme OBSOLETE SWS DET p. 24. Selon l'historique des modifications, les erreurs transitoires sont supprimées avec R24-11 et les appels Dlt avec R25-11 SWS DET p. 1. Dans R20-11, les deux fonctions font encore partie de la spécification ([SWS_Det_01003], [SWS_Det_00211]).

La fonction synchrone Det_Init sert de service central pour l'initialisation du Default Error Tracer ([SWS_Det_00008]). Elle est fournie via le fichier d'en-tête Det.h et possède la signature void Det_Init (const Det_ConfigType* ConfigPtr). Via le paramètre d'entrée formel ConfigPtr, la fonction reçoit un pointeur vers l'ensemble de données de configuration sélectionné du module. Aucune valeur de retour n'est prévue pour ce service ([SWS_Det_00008]).

En ce qui concerne le comportement à l'exécution, Det_Init est obligatoirement spécifié comme non réentrant (Non Reentrant) ([SWS_Det_00008]). Pour cette raison, la fonction ne doit en aucun cas être appelée en parallèle ou de manière interruptive depuis différents contextes d'exécution pendant le fonctionnement. Le module devrait vraisemblablement être appelé de manière centralisée pendant la phase d'initialisation du logiciel de base, avant même que d'autres modules ou composants BSW ne transmettent des erreurs au DET (interprétation).

La fonction est définie avec l'ID de service 0x00 ([SWS_Det_00008]). Des codes d'erreur propres, des mécanismes spécifiques de gestion des erreurs ou des messages d'erreur distincts via DET ou DEM ne sont pas indiqués pour cet appel d'initialisation dans le présent extrait de spécification.

Dans le cadre du traçage des exigences, l'interface satisfait aux exigences générales d'AUTOSAR relatives aux conventions uniformes de nommage des API selon [SRS_BSW_00310] (SWS DefaultErrorTracer §6 « Requirements Tracing »).

fonction Det_ReportError [SWS_Det_00009] 📄 PDF

Std_ReturnType Det_ReportError (uint16 ModuleId, uint8 InstanceId, uint8 ApiId, uint8 ErrorId);

service pour signaler développement erreurs.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 52a5f1bc3a91 Provenance

La fonction Det_ReportError sert, dans les modules BSW d’AUTOSAR Classic, à signaler les erreurs de développement lorsque la détection d’erreurs est active ([SWS_BSW_00045], [SWS_Det_00009]). L’interface est déclarée réentrante ([SWS_Det_00009]). Le comportement d’exécution ne retourne pas à l’appelant (« never returns ») ; le type de retour Std_ReturnType n’existe que pour la compatibilité avec des services et des hooks ([SWS_Det_00009]).

Les paramètres transmis identifient de manière univoque le contexte de l’erreur ([SWS_Det_00009]) :

  • ModuleId (uint16) : identifiant de module AUTOSAR du module notifiant ; le logiciel de base utilise la plage de 0 à 255 (EXP_LayeredSoftwareArchitecture §3 « Default Error Tracer »).
  • InstanceId (uint8) : instance de module à partir de 0 ; pour les instances uniques, 0 est transmis ([SWS_Det_00009]).
  • ApiId (uint8) : identifiant du service d’API détectant l’erreur ([SWS_Det_00009]).
  • ErrorId (uint8) : identifiant d’erreur spécifique du module BSW ([SWS_BSW_00045], [SWS_Det_00009]).

Les erreurs de développement représentent des violations fondamentales de préconditions dues à des erreurs logicielles, des erreurs de configuration ou des problèmes d’intégration (EXP_LayeredSoftwareArchitecture §3 « Error Classification », [SRS_BSW_00337] libellé pas encore importé), comme par exemple l’appel d’un module non initialisé ([SWS_BSW_00243]) ou des paramètres invalides ([SWS_CANIF_00538]). Elles sont gérées comme des assertions : après l’appel de tous les callbacks configurés dans DetErrorHook ([SWS_Det_00501]), le flux de contrôle normal ne doit pas se poursuivre ; le DET interrompt l’exécution, par exemple au moyen d’une boucle infinie, d’une instruction d’arrêt ou d’une réinitialisation ([SRS_BSW_00337] libellé pas encore importé, EXP_LayeredSoftwareArchitecture §3 « Error Classification »).

Cette note d’utilisation a été générée par une IA sur la base de la spécification AUTOSAR R20-11.

fonction Det_Start [SWS_Det_00010] 📄 PDF

void Det_Start (void);

service à démarrer le Default Error Tracer.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: c7a7762c6c8d Provenance Questions ouvertes (1)

La fonction d’API synchrone Det_Start sert à démarrer le Default Error Tracer (DET) ([SWS_Det_00010]). Ce service est déclaré dans le fichier d’en-tête Det.h sous le Service-ID 0x02 (SWS_DefaultErrorTracer §8.1.3.3 « Det_Start »). Conformément à la syntaxe void Det_Start(void), la fonction ne prend aucun paramètre d’entrée ni de sortie et ne fournit aucune valeur de retour à l’appelant ([SWS_Det_00010]).

Pour l’intégration et l’exécution, des conditions spécifiques s’appliquent :

  • Réentrance et concurrence : la fonction est définie comme non réentrante (Non Reentrant) ([SWS_Det_00010]). Les appels parallèles depuis plusieurs tâches ou contextes d’interruption sont interdits.
  • Contexte d’appel : interprétation : l’appel devrait typiquement avoir lieu de manière centralisée pendant le démarrage du système après l’initialisation de base, afin d’activer le suivi des erreurs dans le calculateur.
  • Traitement des erreurs : l’interface ne signale aucun état d’erreur en retour ; dans l’extrait de spécification, aucun code d’erreur ni événement DET ou DEM n’est défini pour cet appel ([SWS_Det_00010]).

Dans l’ensemble du système, Det_Start respecte la convention de nommage standardisée pour le logiciel de base AUTOSAR selon [SRS_BSW_00310] libellé pas encore importé (SWS_DefaultErrorTracer §6 « Requirements Tracing »).

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: a935ac5290c8 Provenance

La fonction [SWS_Det_01001] sert de service BSW central dans Det.h pour la réception des erreurs d'exécution (Runtime Errors). Elle fonctionne de manière synchrone et est conçue pour être réentrante [SWS_Det_01001].

Utilisation et paramètres

Les modules BSW appelants transmettent quatre paramètres obligatoires à [SWS_Det_01001] lors de la notification d'erreur :

  • ModuleId : identifiant de module du module BSW qui signale l'erreur.
  • InstanceId : numéro d'instance basé sur un index (pour les modules ne comportant qu'une seule instance, la valeur 0).
  • ApiId : identifiant de la fonction d'API dans laquelle l'erreur s'est produite.
  • ErrorId : identifiant spécifique au module de l'erreur d'exécution détectée.

Le service renvoie toujours la valeur de retour E_OK au module appelant [SWS_Det_01001].

Interaction et gestion des erreurs
