Rôle de Platform_Types.h : base de types commune du logiciel de base Classic

Le module « platform » est constitué du fichier d'en-tête Platform_Types.h. Il rend disponibles tous les types de base standardisés et les symboles de plateforme, tels que uint8 [SWS_Platform_00013], boolean [SWS_Platform_00026] et CPU_TYPE [SWS_Platform_00064]. Le module ne contient aucune fonction. Il définit les plages de valeurs, largeurs de bits et codages que le code peut présupposer sur une plateforme. La raison en est l'exigence selon laquelle tous les modules du logiciel de base doivent utiliser uniquement des types de données AUTOSAR. Les types C natifs tels que char, int ou long sont interdits, car leur taille, leur signe et leur précision dépendent de la plateforme (RS_BSWGeneral p. 65).

La plupart du temps, les modules n'incluent pas directement les types. Dans l'exemple de la spécification des exigences, Eep.h inclut le fichier Std_Types.h, et celui-ci inclut automatiquement Platform_Types.h (RS_BSWGeneral p. 65). Les bibliothèques telles que Bfx rattachent expressément leurs abréviations u8, u16, s32 et boolean aux types de plateforme (SWS_BFXLibrary p. 8). Le fichier lui-même ne doit pas être modifié : toute extension annule la conformité AUTOSAR [SWS_Platform_00002].

Diagramme de contexte : Platform_Types.h constitue la base de types commune. Les modules BSW y accèdent via Std_Types.h, tandis que les bibliothèques, les interfaces de service et les blueprints de modèles s'y réfèrent directement. Sources : RS_BSWGeneral p. 65, SWS_BFXLibrary p. 8, StandardizationTemplate p. 77, [SWS_Platform_00002]

Types entiers : largeur exacte ou plage minimale optimisée pour la plateforme

Les types entiers standard ont des largeurs de bits et des plages de valeurs fixes. uint8, uint16, uint32 et uint64 sont non signés avec 8, 16, 32 et 64 bits ([SWS_Platform_00013], [SWS_Platform_00014], [SWS_Platform_00015], [SWS_Platform_00066]). sint8 à sint64 sont les équivalents signés ([SWS_Platform_00016], [SWS_Platform_00017], [SWS_Platform_00018], [SWS_Platform_00067]). Leurs plages, par exemple -128..+127 pour sint8, découlent du fait qu'AUTOSAR ne prend en charge que l'arithmétique en complément à deux pour le compilateur et le système cible [SWS_Platform_00061].

Les types optimisés ne garantissent en revanche qu'une plage minimale. uint8_least, uint16_least et uint32_least ont au moins 8, 16 ou 32 bits et sont dérivés de uint ([SWS_Platform_00020], [SWS_Platform_00021], [SWS_Platform_00022]). sint8_least à sint32_least sont les variantes signées et sont dérivées de sint ([SWS_Platform_00023], [SWS_Platform_00024], [SWS_Platform_00025]). La spécification mentionne deux cas d'utilisation typiques : les compteurs de boucle avec au maximum 124 itérations et les arguments switch avec 17 états. Dans les deux cas, il convient de choisir uint8_least (SWS_PlatformTypes p. 17).

Dans le payload figurent des déclarations telles que typedef unsigned int uint8_least; ou typedef unsigned long uint32;. Interprétation : ce sont des mappages pour un compilateur donné. Seule la largeur ou la largeur minimale requise est normative ([SWS_Platform_00015], [SWS_Platform_00020]).

Types à virgule flottante et pointeurs pour les valeurs et les tampons de données

Pour les valeurs à virgule flottante, les formats selon l'IEEE 754-2008 s'appliquent :

  • float32 suit le format binary32, plage ±3.4028235e+38 [SWS_Platform_00041].
  • float64 suit le format binary64, plage ±1.7976931348623157e+308 [SWS_Platform_00042].

Pour les tampons de données sans type fixe, il existe deux types pointeurs avec une direction définie :

  • VoidPtr (void*) est destiné aux tampons qui renvoient des données à l'appelant [SWS_Platform_91001] (SWS_PlatformTypes p. 27).
  • ConstVoidPtr (const void*) est destiné aux tampons qui sont transmis à l'appelé [SWS_Platform_91002] (SWS_PlatformTypes p. 28).

Diagramme d'activité : sélection du type de plateforme approprié, de boolean aux entiers optimisés ou de largeur exacte, en passant par les pointeurs de tampon et la virgule flottante. Sources : [SWS_Platform_00026], [SWS_Platform_91001], [SWS_Platform_91002], [SWS_Platform_00041], [SWS_Platform_00042], SWS_PlatformTypes p. 17

boolean, TRUE et FALSE : représentation et expressions autorisées

Dans R20-11, boolean est implémenté sous forme de type entier non signé, avec la longueur en bits la plus courte prise en charge nativement par la plateforme, généralement 8 bits [SWS_Platform_00027]. La déclaration enregistrée est typedef unsigned char boolean; [SWS_Platform_00026].

Divergence dans les versions ultérieures : la version pour R24-11/R25-11 exige le type C99 _Bool et ne définit plus la taille de l'objet (SWS_PlatformTypes p. 18). Pour R20-11, l'exigence ci-dessus s'applique.

De plus, boolean doit être mappé sur un type vers lequel des pointeurs peuvent pointer. Les types de bits efficaces de certains matériels sont donc exclus [SWS_Platform_00060]. C'est une condition préalable pour des interfaces telles que CanNm_CheckRemoteSleepIndication, qui renvoient un résultat via boolean* (SWS_CANNetworkManagement p. 68).

TRUE (1) et FALSE (0) ne sont définis que s'ils n'existent pas encore (#ifndef TRUE) [SWS_Platform_00056]. Ils ne doivent être utilisés qu'avec boolean [SWS_Platform_00055]. Les règles suivantes s'appliquent à l'utilisation des variables boolean [SWS_Platform_00034] :

  • Les affectations ne sont autorisées qu'avec TRUE, FALSE, des comparaisons ou des expressions logiques (&&, ||, !).
  • Les opérateurs arithmétiques et au niveau du bit tels que +, ++, <<, ~ ou & sont interdits.
  • Les comparaisons sont limitées à == TRUE, == FALSE, != TRUE, != FALSE, if (var) et if (!var) (SWS_PlatformTypes p. 18).

Diagramme d'activité : vérification de la validité d'une affectation ou d'une comparaison avec une variable boolean. Sources : [SWS_Platform_00034], [SWS_Platform_00055], SWS_PlatformTypes p. 18

Symboles de plateforme CPU_TYPE, CPU_BIT_ORDER et CPU_BYTE_ORDER

Platform_Types.h indique pour chaque plateforme trois propriétés du CPU, chacune sous la forme #define :

  • La largeur des registres via CPU_TYPE [SWS_Platform_00044]. Sont autorisés CPU_TYPE_8, CPU_TYPE_16, CPU_TYPE_32 et CPU_TYPE_64 ([SWS_Platform_00045], [SWS_Platform_00064]).
  • L'ordre des bits au niveau des registres via CPU_BIT_ORDER ([SWS_Platform_00043], [SWS_Platform_00038]).
  • L'ordre des octets en mémoire via CPU_BYTE_ORDER ([SWS_Platform_00046], [SWS_Platform_00039]).

La correspondance avec l'endianness est univoque. L'ordre des bits big-endian donne MSB_FIRST, l'ordre des bits little-endian donne LSB_FIRST ([SWS_Platform_00048], [SWS_Platform_00049]). L'ordre des octets big-endian donne HIGH_BYTE_FIRST, l'ordre des octets little-endian donne LOW_BYTE_FIRST ([SWS_Platform_00050], [SWS_Platform_00051]).

La spécification met en garde contre la confusion entre la numérotation des bits et leur poids. Sur les architectures Motorola avec un ordre des bits big-endian, Bit0 désigne le bit de poids fort, et sur toutes les autres, le bit de poids faible. Dans l'accumulateur, le MSB se trouve en revanche toujours tout à gauche (SWS_PlatformTypes p. 15).

Diagramme d'activité : procédure définissant les trois symboles de plateforme pour une plateforme cible sans étendre le fichier. Sources : [SWS_Platform_00045], [SWS_Platform_00048], [SWS_Platform_00049], [SWS_Platform_00050], [SWS_Platform_00051], [SWS_Platform_00002]

Concernant l'ordre des octets, la spécification montre une valeur de 16 bits. Son octet de poids fort s'appelle Byte1 et son octet de poids faible Byte0. Avec HIGH_BYTE_FIRST, Byte1 se trouve à l'adresse n et Byte0 à n+1 ; avec LOW_BYTE_FIRST, c'est l'inverse (SWS_PlatformTypes p. 16). Cette dénomination n'est pas univoque et peut différer dans les documentations des fabricants (SWS_PlatformTypes p. 16). En pratique, l'ordre des octets est important là où les données sont converties entre la représentation sur le bus et celle du processeur. AUTOSAR COM doit par exemple prendre en charge la conversion d'endianness pour uint16 à float64 (référence issue de R25-11 : RS_COM p. 14).

Diagramme d'activité : implantation en mémoire d'une valeur uint16 selon CPU_BYTE_ORDER, inspirée de Figure 7.2/7.3 de la spécification. Sources : SWS_PlatformTypes p. 16, [SWS_Platform_00039]

Types de plateforme dans les interfaces de service et les modèles

D'autres spécifications construisent leurs signatures sur ces types. Deux exemples issus de R24-11/R25-11 montrent la règle de direction des pointeurs de tampon ([SWS_Platform_91001], [SWS_Platform_91002]) :

  • Le Key Manager transmet dans KeyM_ServiceCertificateByCertId les données de requête sous forme de ConstVoidPtr avec une longueur de type uint32. Il reçoit les résultats via un tampon VoidPtr dont la taille disponible est indiquée par ResponseDataLength (INOUT) (SWS_KeyManager p. 111).
  • L'opération CSM RandomSeed transmet le seed sous forme de ConstVoidPtr (SWS_CryptoServiceManager p. 124).

Diagramme de séquence : l'appelant fournit des données de requête en lecture seule via ConstVoidPtr et reçoit des données en retour via un tampon VoidPtr. La valeur de retour indique si le service a accepté la commande. Sources : SWS_KeyManager p. 111, SWS_KeyManager p. 97, [SWS_Platform_91001], [SWS_Platform_91002]

Les types sont également solidement ancrés dans le modèle. L'élément /AUTOSAR_Platform/ImplementationDatatypes/uint8 est dérivé du blueprint /AUTOSAR/Platform/ImplementationDatatypes_Blueprint/uint8. Les fournisseurs de logiciels le trouvent ainsi via un chemin prévisible (StandardizationTemplate p. 77). Les Record Layouts font référence à des types de base tels que /AUTOSAR/Platform/BaseTypes_Blueprint/sint16 (GeneralBlueprintsSupplement p. 47). Des bibliothèques telles que Crc utilisent directement uint8, uint32 et boolean dans leurs API (SWS_CRCLibrary p. 41).

Comportement en cas d'erreur

Platform_Types.h ne fournit que des types et symboles disponibles via ce fichier ([SWS_Platform_00013], [SWS_Platform_00038]). Il ne devrait donc pas y avoir de comportement d'erreur à l'exécution avec des valeurs de retour ou des messages d'erreur. Les erreurs surviennent plutôt lors de l'intégration et de l'utilisation :

  • Fichier étendu ou complété : toute extension annule la conformité AUTOSAR [SWS_Platform_00002].
  • Définitions doubles : si le compilateur fournit déjà les symboles, les redéfinitions doivent être évitées par une vérification conditionnelle ([SWS_Platform_00054], [SWS_Platform_00056]).
  • Symboles de plateforme incorrects : un CPU_BYTE_ORDER ou un CPU_BIT_ORDER qui ne correspond pas au matériel enfreint [SWS_Platform_00048] à [SWS_Platform_00051]. Interprétation : le code effectuant un branchement sur ces symboles assemblerait alors de manière incorrecte les valeurs multi-octets (cf. SWS_PlatformTypes p. 16).
  • Type de bit pour boolean : sans capacité de pointage, aucun paramètre ne peut être transmis via un pointeur [SWS_Platform_00060].
  • Les expressions non autorisées telles que var++ ou var = a & b enfreignent [SWS_Platform_00034].
  • AUTOSAR ne prend en charge aucune représentation des nombres négatifs autre que le complément à deux [SWS_Platform_00061].
