Mappe les blocs de mémoire logique sur des adresses EEPROM et traite de manière asynchrone les tâches de lecture et d'écriture.

L'EEPROM Abstraction mappe les blocs logiques du NvM sur les adresses d'une EEPROM et utilise en R20-11 le pilote Eep. Les tâches de lecture, d'écriture, d'invalidation et d'effacement sont acceptées de manière synchrone et exécutées de façon asynchrone dans la Main Function appelée cycliquement ([SWS_Ea_00096]). Le module signale l'achèvement ou l'échec par callback au NvM ou via le résultat de tâche. Une écriture concerne toujours l'ensemble du bloc. Seul R20-11 contient encore Ea_SetMode et un Ea_Cancel synchrone ([SWS_Ea_00088]).

L'EEPROM Abstraction (Ea) mappe les blocs logiques sur les adresses EEPROM. Elle se situe entre MemIf et le pilote EEPROM Eep ; le numéro de bloc désigne également l'adresse de début du bloc ([SWS_Ea_00087]). Vers le bas, Ea utilise dans R20-11 les services Eep de lecture, d'écriture, d'effacement, d'annulation et de changement de mode ([SWS_Ea_00097]). Ce n'est qu'à partir de R21-11 que MemAcc remplace le pilote Eep et que Ea_SetMode est supprimé (SWS EA p. 1).

Diagramme de contexte : Ea entre NvM/MemIf et Eep, initialisé par EcuM et cadencé par le BSW Scheduler. Sources : [SWS_Ea_00084], [SWS_Ea_00096], [SWS_Ea_00097]

Après Ea_Init avec un pointeur vers le jeu de configuration ([SWS_Ea_00084]), Ea_GetStatus signale l'un des états MEMIF_IDLE, MEMIF_BUSY ou MEMIF_BUSY_INTERNAL ([SWS_Ea_00089]). Ce dernier représente une gestion interne telle qu'un ramasse-miettes (SWS EA p. 28).

La lecture, l'écriture, l'invalidation et l'effacement immédiat sont asynchrones. E_OK confirme uniquement que la tâche a été acceptée. L'exécution a lieu dans la Ea_MainFunction appelée cycliquement ([SWS_Ea_00086], [SWS_Ea_00096]). La lecture est possible avec un décalage et une longueur quelconques. L'écriture concerne toujours l'ensemble du bloc avec un décalage nul (SWS EA p. 25). Le fait que la tâche d'écriture démarre également dans la Main Function relève de l'interprétation.

Diagramme de séquence : acceptation synchrone, exécution asynchrone via Eep et retour par callback au NvM. Sources : SWS Eep p. 50, [SWS_Ea_00094], [SWS_Ea_00099]

Ea_Cancel est synchrone dans R20-11 ([SWS_Ea_00088]). Le module signale les erreurs via les codes EA_E_UNINIT à EA_E_INVALID_CANCEL ([SWS_Ea_91001], [SWS_Ea_91002]). Selon la configuration, les erreurs matérielles parviennent au NvM par l'une des deux voies :

  • par l'interrogation du résultat de la tâche MEMIF_JOB_FAILED,
  • par le callback NvM_JobErrorNotification.

La restauration est prise en charge dans chaque cas par le NvM (ErrorDescription p. 48).

Rôle dans la pile mémoire : du bloc logique à l'adresse EEPROM

L'EEPROM Abstraction (Ea) se situe dans la pile mémoire entre le Memory Abstraction Interface (MemIf) et le pilote EEPROM (Eep). Vers le haut, elle propose des services orientés bloc. Le numéro de bloc désigne un bloc logique et en même temps son adresse de début dans l'EEPROM ([SWS_Ea_00086], [SWS_Ea_00087]). MemIf transmet les tâches de lecture et d'écriture au module d'abstraction sélectionné par le paramètre DeviceIndex et transmet sa valeur de retour (SWS MemIf p. 18, SWS MemIf p. 19).

Vers le bas, Ea utilise dans R20-11 les services du pilote EEPROM : Eep_Read, Eep_Write, Eep_Erase, Eep_Cancel, Eep_GetStatus, Eep_GetJobResult et Eep_SetMode. À cela s'ajoute Det_ReportRuntimeError ([SWS_Ea_00097]). Det_ReportError est une interface optionnelle ([SWS_Ea_00098]). Les types importés Eep_AddressType, Eep_LengthType, MemIf_StatusType, MemIf_JobResultType et MemIf_ModeType reflètent cette intégration ([SWS_Ea_00083]).

Concernant la classification des versions : selon l'historique des modifications, Ea_SetMode disparaît à partir de R21-11. De plus, Ea_Cancel devient asynchrone, l'alignement des tampons est ajouté et MemAcc remplace Eep comme couche inférieure (SWS EA p. 1). Pour R20-11, Eep constitue donc encore la couche inférieure et Ea_SetMode un service. Les règles relatives à l'alignement des tampons (SWS EA p. 19) ne s'appliquent pas à R20-11.

Diagramme de contexte : Ea assure l'intermédiaire entre NvM/MemIf en haut et le pilote Eep en bas. EcuM initialise le module, le BSW Scheduler l'active cycliquement et DET réceptionne les signalements d'erreurs. Sources : [SWS_Ea_00084], [SWS_Ea_00096], [SWS_Ea_00097], [SWS_Ea_00098], [SWS_Ea_00099], [SWS_Ea_00100], SWS EA p. 34

Démarrage et états du module

Ea_Init initialise le module de manière synchrone et n'est pas réentrant. ConfigPtr pointe vers le jeu de configuration sélectionné ([SWS_Ea_00084]). Ea_ConfigType est une structure comportant des éléments spécifiques à l'implémentation ([SWS_Ea_00190]). D'après le diagramme de séquence de la spécification, l'ECU State Manager appelle Ea_Init lors du démarrage (SWS EA p. 47). Comme il ne s'agit que d'un appel unique, il apparaît dans le diagramme d'états ci-dessous sous la forme d'une transition.

Ea_GetStatus fournit l'état de fonctionnement de manière synchrone sous forme de MemIf_StatusType ([SWS_Ea_00089]) :

  • MEMIF_UNINIT : avant l'initialisation.
  • MEMIF_IDLE : aucune tâche ni gestion interne n'est en cours.
  • MEMIF_BUSY : un ordre de la couche supérieure est en cours de traitement.
  • MEMIF_BUSY_INTERNAL : une opération de gestion interne est en cours, telle qu'une réorganisation de la mémoire EEPROM (ramasse-miettes). Le pilote peut également être temporairement occupé à cette occasion.

Les états sont décrits dans SWS EA p. 28. Le module accepte une tâche d'écriture aussi bien dans l'état MEMIF_IDLE que dans l'état MEMIF_BUSY_INTERNAL (SWS EA p. 25).

Diagramme d'états : cycle de vie de l'état du module de MEMIF_UNINIT via MEMIF_IDLE vers MEMIF_BUSY ou MEMIF_BUSY_INTERNAL. Une tâche d'écriture est acceptée depuis la gestion interne. Sources : [SWS_Ea_00084], [SWS_Ea_00089], SWS EA p. 28, SWS EA p. 25, SWS EA p. 27

Accepter des tâches et les exécuter dans Ea_MainFunction

Ea_Read, Ea_Write, Ea_InvalidateBlock et Ea_EraseImmediateBlock sont asynchrones. E_OK signifie seulement que le module a accepté la tâche. E_NOT_OK signifie qu'il l'a rejetée ([SWS_Ea_00086], [SWS_Ea_00087], [SWS_Ea_00091], [SWS_Ea_00093]). Jusqu'à l'obtention du résultat, Ea_GetJobResult signale la valeur MEMIF_JOB_PENDING ([SWS_Ea_00090]).

Le travail effectif est réalisé par Ea_MainFunction, accessible via SchM_Ea.h ([SWS_Ea_00096]). Le Basic Software Scheduler appelle directement la fonction. Elle ne prend aucun paramètre, ne renvoie aucune valeur et n'est pas réentrante (SWS EA p. 36).

Diagramme d'activité : vérifications lors de l'acceptation d'une tâche et leurs codes d'erreur. L'ordre des vérifications est une supposition. Sources : [SWS_Ea_91001], [SWS_Ea_91002], [SWS_Ea_00089], [SWS_Ea_00090], SWS EA p. 25

Ea_Read calcule l'adresse de lecture à partir du numéro de bloc et de l'offset. L'offset et la longueur peuvent prendre n'importe quelle valeur de leur plage de types, de sorte qu'un nombre arbitraire d'octets peut être lu à partir de n'importe quelle position dans le bloc. L'opération de lecture s'exécute expressément de manière asynchrone dans la Main Function (SWS EA p. 24).

Ea_Write calcule l'adresse d'écriture à partir du numéro de bloc avec un offset fixe de zéro. La fonction définit la longueur sur la longueur configurée pour le bloc (SWS EA p. 25). Une écriture concerne donc toujours le bloc entier ([SWS_Ea_00087]). Le schéma relatif à la demande d'écriture montre le cheminement ultérieur via Eep_Write, la Eep_MainFunction cyclique, Ea_JobEndNotification et NvM_JobEndNotification (SWS Eep p. 50).

Interprétation : pour la lecture, le démarrage de la tâche de pilote dans Ea_MainFunction est expressément requis. Pour l'écriture, il devrait en être de même, car Ea_MainFunction traite les demandes requises ([SWS_Ea_00096]). Dans le cas d'une bibliothèque spécifique à un constructeur, les diagrammes de séquence ne sont contraignants que pour la relation avec les modules appelants, et non pour les appels adressés au pilote (SWS EA p. 45).

Diagramme de séquence : une demande d'écriture est acceptée de manière synchrone, exécutée de manière asynchrone via le pilote et signalée au NvM par un callback. Sources : SWS Eep p. 50, SWS MemIf p. 19, [SWS_Ea_00087], [SWS_Ea_00094], [SWS_Ea_00099]

Gestion des blocs : mappage d'adresses, cohérence et invalidation

La fig. 7.1 compare la mémoire virtuelle et la mémoire physique. Le numéro de bloc (16 bits) et l'offset (16 bits) forment une adresse virtuelle, de sorte qu'un bloc peut couvrir jusqu'à 64 KiB. Physiquement, les blocs sont alignés sur la taille de page virtuelle configurée EA_VIRTUAL_PAGE_SIZE ; l'espace virtuel non utilisé n'occupe pas de mémoire (SWS EA p. 23).

Ea gère pour chaque bloc sa propre information de cohérence. Au démarrage d'une opération d'écriture, le bloc est considéré comme incohérent, puis de nouveau comme cohérent après un achèvement réussi. Ea doit pouvoir distinguer un bloc incohérent d'un bloc intentionnellement invalidé (SWS EA p. 19, version R24-11). Pour l'appelant, les deux cas deviennent visibles via les résultats de job MEMIF_BLOCK_INCONSISTENT et MEMIF_BLOCK_INVALID ([SWS_Ea_00090]).

Ea_InvalidateBlock invalide le bloc BlockNumber ([SWS_Ea_00091]). Selon l'implémentation, cela s'effectue via la fonction d'effacement du pilote ou via une information de gestion interne qui doit alors être stockée de manière non volatile (SWS EA p. 31).

Ea_EraseImmediateBlock efface un bloc ([SWS_Ea_00093]). La fonction est destinée aux services de diagnostic ou aux services système comparables qui effacent au préalable la zone pour les données immédiates. Elle calcule l'adresse avec un offset de zéro. Elle garantit qu'Ea peut écrire des données immédiates (SWS EA p. 34).

Mode de fonctionnement, annulation et notifications

Dans R20-11, Ea_SetMode commute le mode du pilote EEPROM avec le paramètre Mode de type MemIf_ModeType. Le service est asynchrone et non réentrant ([SWS_Ea_00085]). La signature abrégée sans paramètre dans les éléments d'API en diffère ; la description du service fait foi. Les schémas présentent la chaîne NvM → MemIf_SetMode → Ea_SetMode → Eep_SetMode (SWS EA p. 42). À partir de R21-11, ce service disparaît (SWS EA p. 1).

Diagramme de séquence : un changement de mode est transmis depuis le NvM via MemIf et Ea jusqu'au pilote (uniquement jusqu'à R20-11). Sources : [SWS_Ea_00085], SWS EA p. 52, SWS EA p. 42

Ea_Cancel annule la demande asynchrone en cours et est synchrone dans R20-11 ([SWS_Ea_00088]). Le passage ultérieur du document décrit le service comme asynchrone ; pour R20-11, c'est l'exigence qui fait foi. Sur le fond, selon ce passage : à l'état MEMIF_BUSY, Ea appelle la fonction d'annulation du pilote et réinitialise ses variables internes. Le résultat du job est alors MEMIF_JOB_CANCELED (SWS EA p. 27). MemIf transmet l'annulation (SWS MemIf p. 20). Une annulation sans demande en attente produit EA_E_INVALID_CANCEL ([SWS_Ea_91002]).

Diagramme de séquence : Ea_Cancel se ramifie, selon l'état du module, en annulation auprès du pilote, message d'erreur ou retour sans modification. Sources : [SWS_Ea_00088], [SWS_Ea_91002], [SWS_Ea_00097], SWS EA p. 27, SWS MemIf p. 20

La couche inférieure signale le succès ou l'échec d'une tâche asynchrone via Ea_JobEndNotification ou Ea_JobErrorNotification ([SWS_Ea_00094], [SWS_Ea_00095]). Ea signale ensuite au NvM NvM_JobEndNotification ou NvM_JobErrorNotification depuis NvM_MemIf.h ([SWS_Ea_00099], [SWS_Ea_00100]). MemIf ne fournit lui-même aucun callback (SWS MemIf p. 24).

Les callbacks peuvent s'exécuter au niveau interruption. Leur temps d'exécution doit donc rester court, et la conception du système doit y adapter la configuration (SWS EA p. 35). Ea_GetVersionInfo est le seul service réentrant ([SWS_Ea_00092]).

Comportement en cas d'erreur

Les codes d'erreur figurent dans deux tableaux.

  • Premier tableau ([SWS_Ea_91001]) : EA_E_UNINIT (0x01), EA_E_INVALID_BLOCK_NO (0x02), EA_E_INVALID_BLOCK_OFS (0x03), EA_E_PARAM_POINTER (0x04) et EA_E_INVALID_BLOCK_LEN (0x05).
  • Second tableau ([SWS_Ea_91002]) : EA_E_BUSY (0x06) et EA_E_INVALID_CANCEL (0x08).

EA_E_INIT_FAILED a été supprimé avec R20-11 (SWS EA p. 1). Interprétation : le premier tableau devrait recenser les erreurs de développement via le Det_ReportError optionnel, le second les erreurs d'exécution via Det_ReportRuntimeError ([SWS_Ea_00097], [SWS_Ea_00098]).

Lorsque la détection des erreurs de développement est active, à l'état non initialisé : Ea_GetJobResult signale EA_E_UNINIT et renvoie MEMIF_JOB_FAILED (SWS EA p. 30). Ea_Cancel signale EA_E_UNINIT et retourne sans modifier les variables internes (SWS EA p. 27). Ea_GetVersionInfo signale EA_E_PARAM_POINTER en cas de pointeur NULL (SWS EA p. 32). Ea_InvalidateBlock et Ea_EraseImmediateBlock ne renvoient E_NOT_OK que lorsque DET est actif ([SWS_Ea_00091], [SWS_Ea_00093]).

Le pilote EEPROM détecte les erreurs matérielles. La réaction d'Ea dépend de l'implémentation. Selon la configuration, le signalement s'effectue par l'une des deux voies : par une interrogation avec le résultat de job MEMIF_JOB_FAILED ou par le callback NvM_JobErrorNotification. La restauration est prise en charge par le NvM (ErrorDescription p. 48, [SWS_Ea_00095], [SWS_Ea_00100]). Pour la voie par interrogation, la description des erreurs mentionne Eep_GetJobResult. Le fait qu'Ea interroge cette fonction dans sa Main Function est vraisemblablement sous-entendu ainsi, mais n'est pas expressément stipulé.

Le résultat du job distingue finement les types d'erreur ([SWS_Ea_00090]) :

  • MEMIF_JOB_CANCELED : annulation, considéré comme ayant échoué.
  • MEMIF_JOB_FAILED : la tâche a échoué.
  • MEMIF_BLOCK_INCONSISTENT : le bloc peut contenir des données corrompues.
  • MEMIF_BLOCK_INVALID : le bloc a été invalidé, l'opération n'est pas exécutable.

Diagramme de séquence : selon la configuration, une erreur de pilote parvient au NvM par callback ou par interrogation du résultat de job. Sources : ErrorDescription p. 48, [SWS_Ea_00095], [SWS_Ea_00100], [SWS_Ea_00090], [SWS_Ea_00097]

La fonction Ea_Init sert à l'initialisation du module EEPROM Abstraction ([SWS_Ea_00084]). Elle est mise à disposition via le fichier d'en-tête Ea.h et place le module dans l'état opérationnel ([SWS_Ea_00084]).

  • Paramètres : le paramètre d'entrée est ConfigPtr (type const Ea_ConfigType*), qui pointe vers le jeu de données de configuration sélectionné. Il n'existe ni paramètres d'entrée/sortie ni paramètres de sortie.
  • Valeur de retour : la fonction ne renvoie aucune valeur de retour (void).

Concernant le contexte d'appel, la présente entrée ne contient aucune prescription explicite ; l'initialisation devrait typiquement être effectuée de manière centralisée lors de la phase de démarrage du calculateur, avant l'exécution d'autres fonctions du module. Aucun code d'erreur spécifique, aucune réaction en cas d'erreur ni aucun message vers DET et DEM ne sont mentionnés dans [SWS_Ea_00084].

Utilisation et sémantique

La fonction Ea_SetMode sert à commuter le mode de fonctionnement du pilote EEPROM sous-jacent ([SWS_Ea_00085]). Elle accepte comme paramètre d'entrée le mode souhaité Mode de type MemIf_ModeType ([SWS_Ea_00085]). L'exécution s'effectue de manière asynchrone (Asynchronous), de sorte que la commutation effective du pilote continue d'être traitée en arrière-plan après l'appel ([SWS_Ea_00085]).

Concurrence et restrictions

  • Réentrance : la fonction est spécifiée comme non réentrante (Non Reentrant) ([SWS_Ea_00085]). Les appels parallèles depuis des tâches ou des contextes différents doivent être évités du côté appelant.
  • Contexte d'appel et paramètres : aucun paramètre d'entrée/sortie ou de sortie pure ne doit être transmis ; seul le paramètre d'entrée Mode est prévu ([SWS_Ea_00085]).

fonction Ea_Read [SWS_Ea_00086] 📄 PDF

Std_ReturnType Ea_Read (uint16 Block Number, uint16 Block Offset, uint8* DataBufferPtr, uint16 Length);

lit longueur octets de bloc Blocknumber à décalage bloc décalage dans le tampon données tampon Ptr.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 43bc307f1243 Provenance

Utilisation et sémantique

La fonction Ea_Read sert à lire des données utiles à partir d'un bloc EEPROM logique spécifié via l'en-tête Ea.h [SWS_Ea_00086]. Le paramètre Block Number permet d'adresser le bloc logique, ce qui détermine également son adresse de départ dans l'EEPROM [SWS_Ea_00086]. Le paramètre Block Offset définit le décalage de lecture relatif au sein du bloc, tandis que Length définit le nombre d'octets à lire [SWS_Ea_00086]. Les données de destination sont écrites dans le tampon référencé par Data Buffer Ptr [SWS_Ea_00086].

L'appel se comporte de manière asynchrone (Asynchronous) : la valeur de retour E_OK signale exclusivement que le module Ea a accepté la demande d'ordre, tandis que E_NOT_OK indique un rejet de l'ordre [SWS_Ea_00086]. Interprétation : le transfert de données s'effectuant de manière asynchrone en arrière-plan, le tampon référencé devrait devoir être mis à disposition inchangé et valide jusqu'à l'exécution complète de l'ordre.

Concurrence et restrictions

L'interface est spécifiée comme non réentrante (Non Reentrant) [SWS_Ea_00086]. Les appels parallèles issus de différents contextes d'exécution ne sont par conséquent pas autorisés et doivent être synchronisés du côté appelant.
