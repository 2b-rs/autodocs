Rôle du BswM : arbitre pour les modes du logiciel de base

Dans le calculateur, les souhaits de mode convergent vers le BSW Mode Manager (BswM), qui les traduit en actions. Il arbitre sur la base des indications de mode entrantes [SWS_BswM_00035]. La spécification distingue ici deux types d'entrées (SWS BswM p. 26) :

  • Les requêtes de mode proviennent principalement de SW-C d'application, occasionnellement aussi de modules BSW tels que le DCM.
  • Les indications de mode proviennent systématiquement de modules BSW, tels que les State Managers spécifiques au bus ou l'EcuM.

Dans le modèle de composants, le BswM est un composant de service qui ne dessert que les Mode Requests de son propre calculateur (SWS BswM p. 48).

Le BswM agit par l'intermédiaire d'actions. Il peut en principe appeler n'importe quelle fonction de la BSW AUTOSAR (SWS BswM p. 92). Comme interfaces optionnelles, la spécification mentionne notamment Com_IpduGroupStart, Com_IpduGroupStop et Com_EnableReceptionDM [SWS_BswM_00008]. De plus, le BswM peut exécuter des callouts utilisateur [SWS_BswM_00270]. Leurs paramètres sont définis au moment de la configuration dans le conteneur BswMUserCallout [SWS_BswM_00054]. Le BswM n'a pas d'interfaces obligatoires vers d'autres modules [SWS_BswM_00007].

Diagramme de contexte : les API de notification des modules BSW et les ports de SW-C convergent vers le BswM ; à partir de règles, il agit via des actions sur Com, PduR, EthIf, EcuM, J1939Rm et les callouts. Sources : SWS BswM p. 87, [SWS_BswM_00008], [SWS_BswM_00201], [SWS_BswM_00202], Guide Modemanagement p. 45, Guide Modemanagement p. 61

Entrées : indications, requêtes et événements

Pour les modules BSW, le BswM propose une API C par source. En interne, il mappe chaque appel sur un Mode Request Port (Guide Modemanagement p. 18). La table d'affectation associe pour cela chaque paramètre d'API à une référence de configuration (SWS BswM p. 87). Par exemple : BswM_CanSM_CurrentState est affecté à la source BswMCanSMIndication via la paire Network / BswMCanSMChannelRef [SWS_BswM_00049]. Cette source est créée une fois par canal CAN (Guide Modemanagement p. 24).

Les API de notification selon leur provenance :

  • Bus State Manager : CanSM, LinSM, FrSM et EthSM signalent leur état ([SWS_BswM_00049], [SWS_BswM_00052], [SWS_BswM_00051], [SWS_BswM_00050]). LinSM signale en outre la table d'ordonnancement active [SWS_BswM_00058], et LinTp demande un mode LIN-TP [SWS_BswM_00156].
  • ComM : signale les modes de canal [SWS_BswM_00047] et les modes PNC [SWS_BswM_00148], et signale un arrêt via BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Gestion de réseau : Nm et J1939Nm signalent les changements d'état ([SWS_BswM_91002], [SWS_BswM_00194]). Nm indique en outre un CarWakeUp [SWS_BswM_00235].
  • Mémoire et diagnostic : les notifications proviennent de NvM ([SWS_BswM_00104], [SWS_BswM_00152]), DCM ([SWS_BswM_00048], [SWS_BswM_00158]) et J1939Dcm [SWS_BswM_00165].
  • Service Discovery : signale via trois callbacks ([SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]).
  • EthIf et WdgM : EthIf signale les états de liaison de groupes de ports de commutateur [SWS_BswM_91001]. WdgM demande une réinitialisation de partition [SWS_BswM_00157].

Si un module BSW ne dispose pas de sa propre interface de requête, il utilise l'appel générique BswM_RequestMode avec les types BswM_UserType et BswM_ModeType ([SWS_BswM_00046], [SWS_BswM_00216], [SWS_BswM_00214]). Les SW-C atteignent le BswM via trois types de ports :

  • modeRequestPort : Required Port pour les requêtes de mode [SWS_BswM_00201].
  • modeNotificationPort : Required Port par lequel le BswM reçoit les changements de mode observés [SWS_BswM_00200].
  • modeSwitchPort : Provided Port par lequel le BswM commute lui-même des modes [SWS_BswM_00202].

Les événements tels que BswM_ComM_InitiateReset sont configurés comme BswMEventRequestPort (SWS BswM p. 102). L'arbitrage prend en compte aussi bien la survenue d'un événement que son effacement (SWS BswM p. 26).

Référence à la release R20-11 : selon l'historique des modifications (SWS BswM p. 2), R20-11 a apporté les modifications suivantes :

  • Réintroduction de BswM_EcuM_CurrentState [SWS_BswM_91003] et BswM_EcuM_RequestedState [SWS_BswM_91004].
  • Prise en charge des groupes de ports de commutateur Ethernet.
  • Nouvelle action BswMEthIfStartAllPorts [SWS_BswM_00286].
  • Suppression du Pretended Networking.

Deux modifications ultérieures ne concernent pas encore R20-11 : BswM_WdgM_RequestPartitionReset [SWS_BswM_00157] n'a été marqué comme obsolète qu'avec R21-11, et la requête de mode SoAd n'a été ajoutée qu'avec R21-11 (SWS BswM p. 2).

Règles, listes d'actions et moment de l'évaluation

Le comportement du BswM est configuré par le biais de règles et de listes d'actions (Guide Modemanagement p. 32) :

  • Une règle est une expression logique portant sur les valeurs actuelles des Mode Request Ports.
  • Selon le résultat, le BswM exécute la liste d'actions True ou la liste d'actions False.
  • Une liste d'actions contient des actions atomiques, des listes d'actions imbriquées ou des références à d'autres règles.

Les actions ne peuvent être appelées que dans le contexte d'une liste d'actions [SWS_BswM_00147].

Le moment où une règle est évaluée est déterminé pour chaque port par le paramètre BswMRequestProcessing :

  • IMMEDIATE : toutes les règles référençant le port sont évaluées immédiatement (Guide Modemanagement p. 32). Pour les requêtes de SW-C, la RTE doit pour cela déclencher un runnable d'arbitrage via un DataReceiveEvent (SWS BswM p. 48).
  • BSWM_DEFERRED : les règles sont évaluées dans BswM_MainFunction [SWS_BswM_00053] [SWS_BswM_00075].

Des règles particulières s'appliquent aux temporisateurs. Un BswMTimer est toujours traité comme DEFERRED, indépendamment de sa configuration, et arbitré dans la Main Function [SWS_BswM_00220]. Dans la version R23-11, il ne peut être contrôlé que via l'action BswMTimerControl, et sa résolution est un multiple du temps de cycle de la Main Function (SWS BswM p. 37).

Les valeurs initiales influent sur les règles qui sont arbitrées. En l'absence de valeur initiale (BswMModeInitValue), une condition de mode est considérée comme indéfinie jusqu'à la première mise à jour. Les règles comportant des conditions indéfinies ne sont pas arbitrées (SWS BswM p. 30). Cette précision provient de la version R23-11. Vraisemblablement, elle s'applique déjà par analogie à R20-11 ; une exigence R20-11 correspondante n'est toutefois pas disponible ici.

Diagramme d'activité : une notification est vérifiée, enregistrée et évaluée immédiatement ou dans la Main Function selon le mode de traitement ; puis suit la liste d'actions True ou False. Sources : [SWS_BswM_00080], [SWS_BswM_00095], [SWS_BswM_00075], [SWS_BswM_00147], [SWS_BswM_00238], Guide Modemanagement p. 32, SWS BswM p. 30

Cycle de vie et démarrage sous le contrôle de l'EcuM

BswM_Init [SWS_BswM_00002] initialise toutes les variables globales au module. Ensuite, le BswM peut arbitrer les souhaits de mode. Avant l'appel, seuls l'OS et le SchM doivent être initialisés (SWS BswM p. 69). Le pointeur transmis référence les données post-build dans BswM_ConfigType [SWS_BswM_00213]. BswM_Init est « Conditionally Reentrant » car le BswM peut être instancié dans plusieurs partitions (SWS BswM p. 69). C'est pourquoi l'EcuM appelle BswM_Init dans une boucle pour chaque instance du BswM d'un cœur (SWS EcuM p. 83).

Dans la séquence StartPostOS, l'EcuM démarre d'abord le planificateur BSW. Il initialise ensuite le BswM et termine après cela l'initialisation du SchM (SWS EcuM p. 42). À partir de ce point, le BswM pilote la suite du démarrage : il veille à ce que les routines d'initialisation des autres modules BSW s'exécutent et à ce que la RTE soit démarrée (Guide Modemanagement p. 36). Dans l'exemple du guide, le déroulement est le suivant :

  1. Une règle DEFERRED déclenche NvM_ReadAll.
  2. Le NvM signale l'achèvement via BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. Une règle consécutive démarre ensuite la RTE (NV-Daten-Leitfaden p. 20).

Diagramme de séquence : l'EcuM initialise le BswM dans StartPostOS ; ensuite, les règles du BswM font progresser le démarrage via NvM_ReadAll et Rte_Start. Sources : SWS EcuM p. 42, Guide Modemanagement p. 36, NV-Daten-Leitfaden p. 20, [SWS_BswM_00002]

Lors de l'arrêt, l'EcuM appelle BswM_Deinit [SWS_BswM_00119] dans la séquence OffPreOS pour chaque instance du BswM du cœur (SWS EcuM p. 90). Après cela, le BswM ne traite plus aucun mode, même si d'autres requêtes continuent d'arriver ou si la Main Function est appelée [SWS_BswM_00120]. Si la partition du BswM est redémarrée, la RestartTask le signale via BswM_BswMPartitionRestarted [SWS_BswM_00193].

Diagramme d'états : le BswM n'arbitre qu'entre BswM_Init et BswM_Deinit ; avant et après, aucun traitement de mode n'a lieu. Sources : [SWS_BswM_00002], [SWS_BswM_00119], [SWS_BswM_00120], [SWS_BswM_00076], [SWS_BswM_00078], SWS BswM p. 69

Interaction avec l'EcuM, les sources de réveil et les groupes de ports Ethernet

Dans le cadre de l'ECU Mode Handling, l'EcuM ne possède pas de machine d'états propre (SWS EcuM p. 99). Il arbitre les requêtes RUN et POST_RUN des SW-C et signale le résultat via BswM_EcuM_RequestedState [SWS_BswM_91004], car seul le BswM décide des transitions. Le déroulement forme une boucle :

  1. Le BswM définit l'état avec EcuM_SetState.
  2. L'EcuM transmet le mode à la RTE (SWS EcuM p. 99).
  3. Après le retour de la RTE, l'EcuM signale le nouvel état au BswM via BswM_EcuM_CurrentState [SWS_BswM_91003] (Guide Modemanagement p. 34).

Cette structure permet également de continuer à utiliser des Legacy-SW-C qui ont été écrits pour l'EcuM avec une machine d'états fixe (Guide Modemanagement p. 61).

Diagramme de séquence : l'EcuM signale le résultat du RUN Request Protocol, le BswM décide et applique l'état, et ce n'est qu'après le retour de la RTE que suit BswM_EcuM_CurrentState. Sources : SWS EcuM p. 99, Guide Modemanagement p. 34, Guide Modemanagement p. 61, [SWS_BswM_91003], [SWS_BswM_91004]

Dans l'EcuM, les sources de réveil traversent les états NONE, PENDING, VALIDATED et EXPIRED. L'EcuM signale chaque entrée dans l'un de ces états via BswM_EcuM_CurrentWakeup [SWS_BswM_00131] (SWS EcuM p. 64). Dans le BswM, y correspond la source BswMEcuMWakeupSource avec la valeur initiale ECUM_WKSTATUS_NONE, qui est créée une fois pour chaque source de réveil (Guide Modemanagement p. 29).

Diagramme d'états : chaque transition d'état d'une source de réveil parvient au BswM sous forme d'indication de mode. Sources : SWS EcuM p. 60, SWS EcuM p. 63, SWS EcuM p. 64, [SWS_BswM_00131]

Les groupes de ports de commutateur Ethernet sont nouveaux dans R20-11. ComM signale le mode PNC via BswM_ComM_CurrentPNCMode [SWS_BswM_00148]. Le BswM connaît l'affectation du PNC au groupe de ports et appelle EthIf_SwitchPortGroupRequestMode avec ETH_MODE_ACTIVE ou ETH_MODE_DOWN (Guide Modemanagement p. 49). Dans le sens inverse, EthIf signale via BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001] l'état de liaison accumulé des groupes de ports qui ne sont associés à aucun EthIfController (SWS EthIf p. 29). Avec l'action BswMEthIfStartAllPorts, le BswM démarre tous les ports via EthIf_StartAllPorts [SWS_BswM_00286].

Diagramme de séquence : le mode PNC commande le groupe de ports, et l'état de liaison accumulé retourne vers le BswM. Sources : Guide Modemanagement p. 49, SWS EthIf p. 92, SWS EthIf p. 29, [SWS_BswM_00148], [SWS_BswM_91001]

Configuration et référence d'instance des Request Ports

L'outil de configuration mappe les paramètres d'API sur les conteneurs ECUC référencés (Guide Modemanagement p. 32). Deux exemples :

  • BswMDcmComModeRequest relie via BswMDcmComMChannelRef l'argument Network de BswM_Dcm_CommunicationMode_CurrentState à un canal ComM [SWS_BswM_00048].
  • Pour BswM_J1939DcmBroadcastStatus, le BswM évalue le bit à la position de la ComMChannelId référencée (SWS BswM p. 70). Seuls les 16 premiers canaux [SWS_BswM_00165] peuvent être mappés.

Pour J1939, en fonction de l'état J1939Nm [SWS_BswM_00194], le BswM commute trois éléments : les groupes d'I-PDU COM, les groupes de chemins de routage PduR et le traitement des requêtes J1939Rm (Guide Modemanagement p. 45).

Concernant les types de données et les interfaces auxiliaires :

  • BswM_ModeType et BswM_UserType dérivent de uint16 ([SWS_BswM_00214], [SWS_BswM_00216]).
  • Les types importés des modules voisins sont répertoriés de manière regroupée [SWS_BswM_00001].
  • BswM_GetVersionInfo fournit les informations de version [SWS_BswM_00003].
  • La Main Function est disponible via SchM_BswM.h [SWS_BswM_00053].

Comportement en cas d'erreur

Si BswMDevErrorDetect est actif, les API de signalement vérifient deux choses :

  • Initialisation : si le BswM n'est pas initialisé, la notification est ignorée et BSWM_E_UNINIT est signalé au DET. CanSM [SWS_BswM_00080], EthSM [SWS_BswM_00081], la table LinSM [SWS_BswM_00086], PNC [SWS_BswM_00149] et les jobs NvM [SWS_BswM_00153] en sont des exemples.
  • Plage de valeurs : les valeurs en dehors de la plage autorisée sont également rejetées et signalées avec BSWM_E_REQ_MODE_OUT_OF_RANGE, par exemple dans [SWS_BswM_00095], [SWS_BswM_00150], [SWS_BswM_00133] et [SWS_BswM_00154].

La Main Function se comporte différemment : si elle est appelée avant l'initialisation, elle retourne immédiatement et ne signale aucune erreur [SWS_BswM_00076].

Parmi les codes d'erreur de développement figurent entre autres BSWM_E_UNINIT (0x01), BSWM_E_NULL_POINTER, BSWM_E_REQ_USER_OUT_OF_RANGE, BSWM_E_REQ_MODE_OUT_OF_RANGE et BSWM_E_PARAM_CONFIG [SWS_BswM_00230]. Si une action renvoie E_NOT_OK, le BswM signale l'erreur d'exécution BSWM_E_ACTION_FAILED. Sa valeur est comprise entre 0x80 et 0xFF et est configurée dans BswMReportFailRuntimeErrorId [SWS_BswM_00238].

Les erreurs système parviennent au BswM sous forme d'indications de mode ordinaires. Lors d'un Bus-Off, CanSM signale dans cet ordre (SWS CanSM p. 70) :

  1. CANSM_BSWM_BUS_OFF au BswM,
  2. COMM_SILENT_COMMUNICATION à ComM,
  3. un événement PRE_FAILED au DEM.

Si la reprise réussit, CANSM_BSWM_FULL_COMMUNICATION suit (SWS CanSM p. 65). La manière dont le système y réagit relève uniquement des règles via BswMCanSMIndication [SWS_BswM_00049]. D'autres voies d'erreur sont la réinitialisation de partition demandée par le WdgM [SWS_BswM_00157] et la notification d'un redémarrage de partition [SWS_BswM_00193].

Diagramme de séquence : en cas de Bus-Off, CanSM informe le BswM avant ComM et DEM ; après la reprise, CanSM signale à nouveau une communication complète. Sources : SWS CanSM p. 70, SWS CanSM p. 65, Fehlerbeschreibung p. 19, [SWS_BswM_00049]
