Arbitre les demandes et indications de mode par le biais de règles et déclenche à partir de là des actions dans le logiciel de base.

Le BSW Mode Manager reçoit des indications de mode provenant de modules BSW et des demandes de mode provenant de SW-C. Il les arbitre au moyen de règles configurées, dont le résultat déclenche des listes d'actions True ou False [SWS_BswM_00035]. Conformément à BswM_Init, il pilote ainsi la suite de l'initialisation du logiciel de base, l'ECU Mode Handling avec l'EcuM et l'activation de la communication, par exemple pour des groupes d'I-PDU ou des groupes de ports Ethernet. BswM_MainFunction évalue périodiquement les règles dotées d'entrées BSWM_DEFERRED, toutes les autres immédiatement [SWS_BswM_00075]. Si DET est actif, les demandes non valides ou arrivant avant l'initialisation sont ignorées et signalées.

Le BSW Mode Manager (BswM) est l'instance centrale d'arbitrage du logiciel de base. Il reçoit des indications de mode de modules BSW tels qu'EcuM, ComM, les Bus State Managers, NvM, DCM ou Sd, ainsi que des demandes de mode de SW-C. Sur cette base, il détermine la marche à suivre par le biais de règles configurées [SWS_BswM_00035], SWS BswM p. 26. Les entrées arrivent sous forme d'API C, de ports de SW-C ou d'événements. Chaque API C est associée à un port de requête concret via des paramètres de référence SWS BswM p. 87.

Diagramme de contexte : de nombreux émetteurs alimentent le BswM ; il agit par des actions sur Com, EthIf, EcuM, la RTE et des callouts. Sources : [SWS_BswM_00035], [SWS_BswM_00008], Mode-Mgmt-Guide p. 18

Une règle est une expression logique portant sur les valeurs actuelles des ports. Selon le résultat, elle exécute la liste d'actions True ou la liste d'actions False. Les listes d'actions contiennent des actions, des listes imbriquées ou d'autres règles Mode-Mgmt-Guide p. 32. Avec BSWM_IMMEDIATE, une règle est évaluée immédiatement. Avec BSWM_DEFERRED, cela a lieu dans BswM_MainFunction [SWS_BswM_00075]. Les règles dont les conditions sont encore indéfinies ne sont pas arbitrées SWS BswM p. 30.

Diagramme d'activité : une requête est vérifiée, enregistrée et, selon son type de traitement, évaluée immédiatement ou périodiquement au regard des règles. Sources : [SWS_BswM_00075], SWS BswM p. 30

L'EcuM appelle BswM_Init [SWS_BswM_00002] dans la séquence StartPostOS SWS EcuM p. 42. Ensuite, le BswM pilote par des règles la suite de l'initialisation jusqu'au démarrage de la RTE, dans l'exemple avec NvM_ReadAll et BswM_NvM_CurrentJobMode [SWS_BswM_00152], Mode-Mgmt-Guide p. 36. Lors de l'ECU Mode Handling, le BswM décide seul des transitions de l'EcuM SWS EcuM p. 99. Depuis R20-11, il commute en outre des groupes de ports Ethernet d'après les états de PNC Mode-Mgmt-Guide p. 49. Après BswM_Deinit, plus aucun traitement de mode n'a lieu [SWS_BswM_00120].

Lorsque DET est actif, les API d'entrée ignorent les appels antérieurs à l'initialisation et signalent BSWM_E_UNINIT [SWS_BswM_00080]. Elles traitent de la même façon les valeurs hors de la plage admissible et signalent BSWM_E_REQ_MODE_OUT_OF_RANGE [SWS_BswM_00095]. Si une action échoue, le BswM signale l'erreur d'exécution configurable BSWM_E_ACTION_FAILED [SWS_BswM_00238].

Rôle du BswM : arbitrage central des modes du logiciel de base

Le BSW Mode Manager (BswM) reçoit des demandes de mode et des indications de mode. À partir de là, il arbitre par le biais de règles configurées quelles actions doivent être exécutées [SWS_BswM_00035], SWS BswM p. 26. Les demandes de mode proviennent généralement de SW-C d'application, mais peuvent aussi émaner de modules BSW tels que le DCM. Les indications de mode sont toujours fournies par d'autres modules BSW, tels que les State Managers propres aux bus et l'EcuM. Le BswM traite ces deux types de façon identique et les regroupe sous le terme de « mode arbitration request » SWS BswM p. 26.

Le BswM est modélisé comme un composant de service qui dessert les Mode Requests locaux au calculateur (ECU) SWS BswM p. 48. Il n'a aucune interface obligatoire vers d'autres modules [SWS_BswM_00007]. Ses actions appellent des fonctions d'autres modules BSW. Pour cela, la spécification mentionne une liste d'interfaces optionnelles, telles que Com_IpduGroupStart, Com_IpduGroupStop ou le pilotage de la surveillance de réception de groupes d'I-PDU [SWS_BswM_00008], SWS BswM p. 93. La frontière du système est ainsi nettement tracée : les modules émetteurs se contentent de rapporter leur état. La réaction à cet état est uniquement définie par la logique configurée dans le BswM Mode-Mgmt-Guide p. 32.

Sources : [SWS_BswM_00035], [SWS_BswM_00008], [SWS_BswM_00202], [SWS_BswM_00270], Mode-Mgmt-Guide p. 18, SWS EcuM p. 99

Entrées : indications de mode via API C, ports et événements

Le conteneur BswMModeRequestSource définit la manière dont une entrée parvient au module. Il existe trois types Mode-Mgmt-Guide p. 18 :

  • une API C qu'un module BSW appelle directement et que le BswM traduit en interne en un Mode Request,
  • un RPort avec SenderReceiverInterface (BswMSwcModeRequest),
  • un RPort avec ModeSwitchInterface (BswMSwcModeNotification).

Pour les types de ports, le BswM génère des ports selon des modèles de nommage fixes [SWS_BswM_00201], [SWS_BswM_00200]. Dans R20-11, les API C peuvent être regroupées selon leur provenance :

  • État du calculateur (ECU) et réveil : BswM_EcuM_CurrentState [SWS_BswM_91003], BswM_EcuM_RequestedState [SWS_BswM_91004], BswM_EcuM_CurrentWakeup [SWS_BswM_00131].
  • Communication : BswM_ComM_CurrentMode [SWS_BswM_00047], BswM_ComM_CurrentPNCMode [SWS_BswM_00148], BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Bus State Managers et LinTp : CanSM [SWS_BswM_00049], EthSM [SWS_BswM_00050], FrSM [SWS_BswM_00051], LinSM [SWS_BswM_00052] avec indication de table de planification (Schedule) [SWS_BswM_00058] ainsi que BswM_LinTp_RequestMode [SWS_BswM_00156].
  • Gestion de réseau et Ethernet : BswM_Nm_StateChangeNotification [SWS_BswM_91002], BswM_Nm_CarWakeUpIndication [SWS_BswM_00235], BswM_J1939Nm_StateChangeNotification [SWS_BswM_00194], BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001].
  • Diagnostic : BswM_Dcm_CommunicationMode_CurrentState [SWS_BswM_00048], BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], BswM_J1939DcmBroadcastStatus [SWS_BswM_00165].
  • Mémoire : BswM_NvM_CurrentBlockMode [SWS_BswM_00104], BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  • Service Discovery : BswM_Sd_* [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210].
  • Partitions : BswM_WdgM_RequestPartitionReset [SWS_BswM_00157], BswM_BswMPartitionRestarted [SWS_BswM_00193].
  • Générique : BswM_RequestMode [SWS_BswM_00046] n'est prévu que pour les modules BSW sans interface propre. Il opère avec BswM_UserType [SWS_BswM_00216] et BswM_ModeType [SWS_BswM_00214], tous deux dérivés de uint16.

Chaque API est associée à exactement un type de port de requête. Les paramètres tels que Network sont associés à un port concret par le biais de paramètres de référence tels que BswMCanSMChannelRef ou BswMComMChannelRef SWS BswM p. 87. C'est pourquoi, par exemple, un BswMCanSMIndication est créé par canal CAN Mode-Mgmt-Guide p. 24. Toutes les API de notification sont synchrones. À l'exception de BswM_ComM_InitiateReset, qui n'est pas réentrante, elles sont réentrantes [SWS_BswM_00217], [SWS_BswM_00049].

Outre les ports de requête de mode dotés d'un état, il existe des ports de requête d'événements. Par leur intermédiaire, les modules BSW transmettent des événements, par exemple via BswM_ComM_InitiateReset() SWS BswM p. 102. Le BswM arbitre aussi bien sur ces événements que sur leur réinitialisation SWS BswM p. 26. D'après l'historique des modifications, R20-11 a introduit les nouveautés suivantes SWS BswM p. 2 :

  • réintroduction de BswM_EcuM_CurrentState et BswM_EcuM_RequestedState,
  • nouvelle notification BswMNmStateChangeNotification,
  • prise en charge de la commutation des groupes de ports Ethernet.

BswM_WdgM_RequestPartitionReset ne devient obsolète que dans R21-11 SWS BswM p. 2.

Règles et listes d'actions : de l'entrée à l'action

Le comportement du BswM est configuré au moyen de règles et de listes d'actions. Une règle est une expression logique portant sur les valeurs actuelles des ports de requête de mode. Selon le résultat, son évaluation exécute la liste d'actions True ou la liste d'actions False Mode-Mgmt-Guide p. 32. Une liste d'actions peut contenir SWS BswM p. 31 :

  • des actions atomiques,
  • des listes d'actions imbriquées,
  • des références à des règles, qui sont alors évaluées dans le contexte de cette liste.

Les actions ne doivent être appelées que dans le contexte d'une liste d'actions [SWS_BswM_00147]. Un schéma de la spécification illustre un exemple de règle. Elle associe via AND une condition de mode (MyModeRequestPort égal à MODE_A) au port d'événement ComMInitiateReset SWS BswM p. 25.

Le moment où une règle est évaluée est déterminé par BswMRequestProcessing pour chaque port :

  • BSWM_IMMEDIATE : toute règle qui référence le port est immédiatement traitée Mode-Mgmt-Guide p. 32. Pour les ports de SW-C, le BswM enregistre à cette fin un Runnable que la RTE lance lors de la réception des données SWS BswM p. 48.
  • BSWM_DEFERRED : le BswM lit la valeur de manière cyclique. BswM_MainFunction [SWS_BswM_00053] évalue toutes les règles qui utilisent au moins une entrée de ce type [SWS_BswM_00075].

Diagramme d'activité : une requête entrante est vérifiée, enregistrée et, selon son type de traitement, évaluée immédiatement ou dans la MainFunction au regard des règles ; les règles aux conditions indéfinies ne sont pas prises en compte. Sources : [SWS_BswM_00075], [SWS_BswM_00080], [SWS_BswM_00095], SWS BswM p. 30, Mode-Mgmt-Guide p. 32

Via BswMModeInitValue, un port reçoit une valeur initiale lors de l'initialisation. Si elle fait défaut, la condition est considérée comme indéfinie jusqu'à la première actualisation. Les règles dont les conditions sont indéfinies ne sont pas arbitrées SWS BswM p. 30. Les exemples du guide définissent par conséquent des valeurs initiales, comme CANSM_BSWM_NO_COMMUNICATION pour les indications CanSM Mode-Mgmt-Guide p. 24.

Pour gérer les temporisations, le BswM met à disposition des timers. Un BswMTimer constitue une source interne de requête de mode (Mode Request Source) et ne se pilote que par l'intermédiaire de l'action BswMTimerControl ; il n'existe aucune interface externe SWS BswM p. 37. Son déroulement SWS BswM p. 37 :

  • Lors de l'initialisation, tous les timers sont arrêtés.
  • BSWM_TIMER_START charge le timer avec BswMTimerValue et définit BSWM_TIMER_STARTED.
  • À chaque exécution de BswM_MainFunction, la valeur est décrémentée de son temps de cycle.

Indépendamment de leur configuration, les timers sont toujours traités en mode DEFERRED [SWS_BswM_00220]. La valeur BSWM_TIMER_EXPIRED devrait marquer le compte à rebours écoulé. Il s'agit d'une interprétation, car la section est abrégée dans le payload SWS BswM p. 37.

Diagramme d'états : cycle de vie d'un BswMTimer de STOPPED à EXPIRED en passant par STARTED, piloté exclusivement par des actions et la MainFunction. Sources : [SWS_BswM_00220], SWS BswM p. 37

Outre les fonctions issues de la liste d'interfaces optionnelles [SWS_BswM_00008], il existe des actions spécifiques. Ainsi, BswMEthIfStartAllPorts appelle EthIf_StartAllPorts lors de son exécution [SWS_BswM_00286]. Des fonctions librement définies sont configurées en tant que BswMUserCallout. Le nom et les paramètres sont alors fixés au moment de la configuration de l'ECU [SWS_BswM_00054], [SWS_BswM_00270].

Démarrage, chaînes d'initialisation et arrêt

BswM_Init [SWS_BswM_00002] reçoit un pointeur vers la configuration post-build BswM_ConfigType [SWS_BswM_00213]. La fonction initialise toutes les variables globales. Ensuite, le BswM est prêt à arbitrer les requêtes. Seuls l'OS et le SchM sont requis au préalable SWS BswM p. 69. L'EcuM appelle BswM_Init dans la séquence StartPostOS après SchM_Start() ; suivent ensuite SchM_Init et SchM_StartTiming SWS EcuM p. 42. Sur les systèmes multicœurs, l'appel s'effectue dans une boucle sur chaque instance de BswM du cœur SWS EcuM p. 81. Pour de telles instances multiples dans plusieurs partitions ou cœurs, BswM_Init est réentrante sous condition SWS BswM p. 69.

Diagramme de séquence : déroulement de StartPostOS avec initialisation de chaque instance de BswM entre SchM_Start et SchM_Init ; ensuite, la MainFunction s'exécute de manière cyclique. Sources : [SWS_BswM_00002], SWS EcuM p. 42, SWS EcuM p. 78, SWS BswM p. 37

À partir de là, le BswM prend en charge le contrôle d'exécution. Il veille à ce que les routines d'initialisation restantes du logiciel de base soient appelées et que la RTE soit démarrée Mode-Mgmt-Guide p. 36. Les modules qu'il doit initialiser sont décrits par le conteneur EcuM EcuMDriverInitListBswM SWS EcuM p. 224. Dans l'exemple du guide, l'initialisation se déroule ainsi Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20 :

  1. Une règle DEFERRED initialise les pilotes NVRAM et déclenche NvM_ReadAll.
  2. Le NvM signale la fin de la tâche via BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. Cette notification déclenche le reste de l'initialisation et la transition vers ECU_RUN.

Le guide présente encore un paramètre uint8 pour cette API ServiceId Mode-Mgmt-Guide p. 26. La signature avec NvM_MultiBlockRequestType [SWS_BswM_00152] fait toutefois autorité pour R20-11.

Diagramme de séquence : deuxième phase d'initialisation pilotée par règles avec NvM_ReadAll, notification en retour du NvM et démarrage consécutif de la RTE. Sources : [SWS_BswM_00152], [SWS_BswM_00075], Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20

Lors de l'arrêt, selon le guide NV, le BswM est chargé d'écrire les blocs modifiés, dans l'exemple au moyen de NvM_WriteAll NV-Data-Guide p. 41. Le NvM lui signale également l'interruption d'un WriteAll via l'indication du mode de tâche SWS NvM p. 155. Dans la séquence OffPreOS, l'EcuM désinitialise le BswM en tant que première étape SWS EcuM p. 50. Après BswM_Deinit [SWS_BswM_00119], aucun traitement de mode n'a plus lieu, même si des requêtes arrivent ou si la MainFunction est appelée [SWS_BswM_00120].

Interaction avec l'EcuM : ECU Mode Handling et sources de réveil

Lors de l'ECU Mode Handling, l'EcuM arbitre les requêtes RUN et POST_RUN des SW-Cs. Il ne possède pas de machine d'états propre ; seul le BswM décide du moment où une transition a lieu SWS EcuM p. 99. Le déroulement Mode-Mgmt-Guide p. 34 :

  1. L'EcuM signale le résultat du RUN Request Protocol via BswM_EcuM_RequestedState [SWS_BswM_91004].
  2. Le BswM définit l'état au moyen de EcuM_SetState.
  3. L'EcuM signale le mode correspondant à la RTE.
  4. Après le retour d'information de la RTE, l'EcuM appelle BswM_EcuM_CurrentState [SWS_BswM_91003].

Les états sont ECUM_STATE_STARTUP, ECUM_STATE_APP_RUN, ECUM_STATE_APP_POST_RUN, ECUM_STATE_SHUTDOWN et ECUM_STATE_SLEEP Mode-Mgmt-Guide p. 34. Ce couplage permet de réutiliser des SW-Cs conçus pour l'EcuM doté d'une machine d'états fixe. Un SW-C de compatibilité n'est pas nécessaire pour cela Mode-Mgmt-Guide p. 61.

Diagramme de séquence : l'EcuM arbitre les requêtes RUN, le BswM décide de la transition, la RTE est informée et la confirmation revient sous forme de CurrentState vers le BswM. Sources : [SWS_BswM_91004], [SWS_BswM_91003], SWS EcuM p. 99, Mode-Mgmt-Guide p. 34, Mode-Mgmt-Guide p. 61

L'EcuM signale les changements d'état des sources de réveil via BswM_EcuM_CurrentWakeup [SWS_BswM_00131]. Dans l'automate d'états des sources de réveil, chacun des états NONE, PENDING, VALIDATED et EXPIRED appelle cette API lors de son entrée SWS EcuM p. 60. En détail :

  • Si l'EcuM valide un événement, il signale VALIDATED SWS EcuM p. 134.
  • Si la validation échoue jusqu'au timeout, il signale EXPIRED SWS EcuM p. 63.
  • Dans la séquence GoSleep, il réinitialise les sources avec ECUM_WKSTATUS_NONE SWS EcuM p. 54.
  • Dans la séquence Poll, il signale PENDING ou VALIDATED selon le besoin de validation SWS EcuM p. 57.

Un BswMEcuMWakeupSource est créé pour chaque source de réveil Mode-Mgmt-Guide p. 29.

Diagramme d'états : états d'une source de réveil dans l'EcuM ; chaque entrée génère une notification vers le BswM. Sources : [SWS_BswM_00131], SWS EcuM p. 60, SWS EcuM p. 57, SWS EcuM p. 63

Contrôle de la communication : bus, réseaux partiels, diagnostic et services

Un cas d'application typique est l'activation de groupes d'I-PDU. Dans le guide, une règle sur une indication du CanSM active les groupes d'I-PDU d'un canal CAN Mode-Mgmt-Guide p. 32. Le CanSM signale pour cela les états CANSM_BSWM_NO_COMMUNICATION, CANSM_BSWM_SILENT_COMMUNICATION, CANSM_BSWM_FULL_COMMUNICATION et CANSM_BSWM_BUS_OFF [SWS_BswM_00049], Mode-Mgmt-Guide p. 22. Il signale l'état FULL_COMMUNICATION par exemple lors de l'effet E_TX_ON SWS CanSM p. 65.

Pour les réseaux partiels, ComM signale chaque changement d'état d'un PNC via BswM_ComM_CurrentPNCMode [SWS_BswM_00148], SWS ComM p. 35. Le BswM commute ainsi des groupes de ports de switch Ethernet Mode-Mgmt-Guide p. 49 :

  • Il connaît l'affectation du PNC à EthIfSwitchPortGroup.
  • Il appelle EthIf_SwitchPortGroupRequestMode avec ETH_MODE_ACTIVE ou ETH_MODE_DOWN.
  • EthIf renvoie l'état de liaison résultant du groupe via BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001], SWS EthIf p. 92.

Diagramme de séquence : la requête et la libération de PNC commutent un groupe de ports Ethernet via des règles du BswM ; EthIf signale l'état de liaison déterminé en retour au BswM. Sources : [SWS_BswM_00148], [SWS_BswM_91001], Mode-Mgmt-Guide p. 49, SWS EthIf p. 92

Le diagnostic envoie également des notifications au BswM :

  • Service UDS 0x28 (CommunicationControl) : le DCM appelle BswM_Dcm_CommunicationMode_CurrentState pour chaque réseau concerné [SWS_BswM_00048], SWS DCM p. 147. Le comportement est configuré via BswMDcmComModeRequest ; son BswMDcmComMChannelRef correspond à l'argument Network SWS BswM p. 64.
  • Saut vers le bootloader : si l'application a été mise à jour à cette occasion, le DCM signale BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], SWS DCM p. 231.
  • J1939 : BswM_J1939DcmBroadcastStatus transmet un masque de bits par ComMChannelId, qui ne couvre que les 16 premiers canaux [SWS_BswM_00165], SWS BswM p. 70. Selon les états de J1939Nm, le BswM commute des groupes d'I-PDU Com, des groupes de chemins de routage PduR et le traitement des requêtes du J1939Rm Mode-Mgmt-Guide p. 45.

Le Service Discovery signale les états des Client Services, Consumed Eventgroups et Event Handlers [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]. Pour le Sd, ces appels sont des interfaces optionnelles SWS Sd p. 122.

Comportement en cas d'erreur

Si BswMDevErrorDetect est actif, les API d'entrée vérifient d'abord si le BswM est initialisé. Dans le cas contraire, elles ignorent la requête et signalent BSWM_E_UNINIT au DET, par exemple [SWS_BswM_00080], [SWS_BswM_00081], [SWS_BswM_00149], [SWS_BswM_00112], [SWS_BswM_00086], [SWS_BswM_00132]. De plus, elles vérifient si les valeurs transmises se situent dans la plage autorisée. En cas de violation, la requête est également ignorée et BSWM_E_REQ_MODE_OUT_OF_RANGE est signalé, par exemple [SWS_BswM_00095], [SWS_BswM_00097], [SWS_BswM_00150], [SWS_BswM_00113], [SWS_BswM_00110], [SWS_BswM_00154]. Si BswM_MainFunction est appelée avant l'initialisation, elle retourne immédiatement sans signaler d'erreur [SWS_BswM_00076].

Les codes d'erreur de développement du BswM selon [SWS_BswM_00230] :

ErreurCodeValeur
Appel avant l'initialisationBSWM_E_UNINIT0x01
Pointeur nul transmisBSWM_E_NULL_POINTER0x02
Paramètre non valide (non spécifique)BSWM_E_PARAM_INVALID0x03
Utilisateur demandeur hors plageBSWM_E_REQ_USER_OUT_OF_RANGE0x04

Si une action renvoie E_NOT_OK, le BswM signale l'erreur d'exécution BSWM_E_ACTION_FAILED. La valeur se situe entre 0x80 et 0xFF et est configurée dans BswMReportFailRuntimeErrorId [SWS_BswM_00238]. Le BswM rejette les configurations qui contiennent à la fois BswMBswModeInitValue et BswMCompuScaleModeValue pour un BswMModeInitValue SWS BswM p. 30. Le code BSWM_E_REQ_USER_OUT_OF_RANGE devrait servir à la vérification de requesting_user dans BswM_RequestMode. Il s'agit d'une interprétation, car le passage correspondant est tronqué dans le payload [SWS_BswM_00230], SWS BswM p. 86.
