Rôle de la RTE entre les composants logiciels et le Basic Software

La RTE est une couche d'exécution configurée et générée individuellement pour chaque instance d'ECU [SWS_Rte_05000] [SWS_Rte_01316]. Elle met en œuvre les chemins de communication décrits dans la configuration de l'ECU et réalise la sémantique des attributs de communication des composants logiciels [SWS_Rte_02200] [SWS_Rte_02201]. Sa position entre le logiciel d'application et le Basic Software est illustrée par le schéma d'architecture (SWS_RTE p. 113). Pour sa réalisation, la RTE n'utilise que des services de base définis, parmi lesquels AUTOSAR OS, COM et Efficient COM for Large Data [SWS_Rte_02250]. Le module comprend également le Basic Software Scheduler (SchM), qui planifie l'exécution des modules BSW (SWS_RTE p. 459).

Diagramme de contexte : la RTE sert d'intermédiaire entre les SW-C, les modules BSW, l'OS, COM/LdCom et le NvM. L'EcuM pilote son cycle de vie. Sources : [SWS_Rte_02250] [SWS_Rte_03530] [SWS_Rte_89015] SWS_RTE p. 259 SWS_RTE p. 928

La RTE est générée en C. Son code doit respecter la norme MISRA-C, et tous les symboles visibles de l'extérieur portent le préfixe Rte_ [SWS_Rte_01167] [SWS_Rte_01168] [SWS_Rte_01171]. Pour chaque type de composant, un Application Header File Rte_[Byps_]<name>.h est créé, ne contenant que les informations pertinentes pour ce composant. Les API de cycle de vie sont déclarées dans Rte_Main.h, les types dans Rte_Type.h [SWS_Rte_01000] [SWS_Rte_01003] [SWS_Rte_01004] [SWS_Rte_01158] [SWS_Rte_01161].

Cycle de vie : démarrage et arrêt de la RTE et du BSW-Scheduler

Tant que le BSW-Scheduler n'est pas initialisé, seuls SchM_Enter et SchM_Exit sont disponibles. L'EcuM appelle SchM_Init avant que le premier module BSW ne doive être planifié. SchM_Init reçoit un pointeur de configuration [SWS_Rte_08060], retourne en un temps fini [SWS_Rte_07273] et initialise les mode machine instances associées, y compris les on-entry-ExecutableEntitys des modes initiaux [SWS_Rte_02544]. Avec SchM_Init débute l'activation via BswBackgroundEvents, avec SchM_StartTiming l'activation via BswTimingEvents (SWS_RTE p. 459).

La même chose s'applique à SchM_Start et SchM_StartTiming : les deux API sont toujours générées et doivent retourner en un temps fini [SWS_Rte_04546] [SWS_Rte_04547] [SWS_Rte_04548] [SWS_Rte_04549] [SWS_Rte_04550] [SWS_Rte_04551]. Les références documentaires des versions ultérieures ajoutent trois règles (SWS_RTE p. 927, SWS_RTE p. 928) :

  • SchM_Start est appelée avant BswM_Init.
  • SchM_Init est appelée avant SchM_StartTiming.
  • L'EcuM appelle chacune des trois fonctions exactement une fois par cœur, et ce seulement après que les modules requis tels que l'OS ont été initialisés.

Rte_Start suit à la fin de la phase de démarrage II. À ce moment-là, l'OS et tous les modules BSW sont prêts (SWS_RTE p. 460). L'API est toujours générée et doit retourner en un temps fini [SWS_Rte_01309] [SWS_Rte_02569] [SWS_Rte_02585]. Rte_Start initialise les machines de mode de la RTE et met à zéro les compteurs de séquence des liaisons client-serveur entre ECU [SWS_Rte_02544] [SWS_Rte_02655]. Rte_Start ne démarre les runnables déclenchés par des TimingEvents ou des BackgroundEvents que s'il n'y a pas de Rte_StartTiming (SWS_RTE p. 460). Interprétation : si Rte_StartTiming est présent, cette activation ne devrait débuter qu'avec l'appel de Rte_StartTiming [SWS_Rte_06753].

Lors de l'arrêt, l'EcuM appelle Rte_Stop au début de la phase d'arrêt I, tant que l'OS est encore disponible [SWS_Rte_02570] [SWS_Rte_01310] [SWS_Rte_02584] (SWS_RTE p. 461). À partir de cet appel, la RTE n'active plus aucun runnable sur le cœur concerné. Elle n'interrompt toutefois pas les runnables déjà en cours d'exécution [SWS_Rte_02538]. Vient ensuite SchM_Deinit, qui est soumis à deux conditions : il ne doit être appelé qu'après la fin de Rte_Stop, et ce avant que l'OS ne soit arrêté. SchM_Deinit libère les ressources de la partie ordonnanceur et retourne en un temps fini [SWS_Rte_07277] (SWS_RTE p. 951). D'après les références documentaires à partir de R23-11, SchM_Deinit appelle également à cette occasion Rte_Rips_SchM_Deinit de tous les plug-ins concernés [SWS_Rte_89019] (SWS_RTE p. 1028).

Exécution des runnables et multi-instanciation

Un composant logiciel se compose de plusieurs RunnableEntitys. Celles-ci s'exécutent dans des tâches d'OS ou des ISR2 et sont déclenchées par des RTEEvents [SWS_Rte_02202] [SWS_Rte_02203] (SWS_RTE p. 119). Au sein d'une tâche, l'ordre d'exécution configuré s'applique. Le générateur génère lui-même les corps des tâches [SWS_Rte_02207] [SWS_Rte_06200] [SWS_Rte_06201]. Une seule et même instance de runnable peut être activée par plusieurs RTEEvents, y compris par des événements de types différents [SWS_Rte_03520] [SWS_Rte_03524].

Les règles suivantes s'appliquent au contexte d'interruption :

  • En principe, la RTE empêche les runnables de composants de s'exécuter dans le contexte d'interruption [SWS_Rte_03600].
  • Les interruptions de catégorie 1 ne doivent pas atteindre la RTE [SWS_Rte_03594].
  • Si un événement est mappé sur une ISR2, l'activation y est expressément prévue [SWS_Rte_04564] (SWS_RTE p. 182).

La RTE prend en charge plusieurs instances d'un type de composant exclusivement par le biais de code partagé, et non par duplication de code [SWS_Rte_02002] [SWS_Rte_03015] (SWS_RTE p. 126). Chaque instance est identifiable de manière unique via un handle d'instance. Le point d'entrée d'un runnable reçoit ce handle comme premier paramètre [SWS_Rte_02015] [SWS_Rte_01012] [SWS_Rte_01016]. Les instances étant planifiées indépendamment les unes des autres, les points d'entrée devraient être réentrants (SWS_RTE p. 804). La même instance de runnable ne peut être activée simultanément plusieurs fois que si canBeInvokedConcurrently est défini sur TRUE [SWS_Rte_03523] [SWS_Rte_05083] (SWS_RTE p. 208).

Communication Sender-Receiver et client-serveur avec leurs tampons

Pour la communication Sender-Receiver, la RTE prend en charge les accès explicites et implicites [SWS_Rte_06011]. Lors de la lecture implicite, la RTE lit les données avant le démarrage du runnable et les fournit sous forme de copie. Cette copie reste inchangée pendant toute l'exécution [SWS_Rte_06000] [SWS_Rte_06001] [SWS_Rte_06004] (SWS_RTE p. 286). La mise en tampon a lieu du côté récepteur [SWS_Rte_02515], de manière différente selon la sémantique :

  • Avec la sémantique de données, la RTE conserve un unique ensemble de données. Chaque nouvelle valeur écrase la précédente ; jusqu'à la première réception, la valeur initiale s'applique [SWS_Rte_02516] [SWS_Rte_02518] [SWS_Rte_02520] [SWS_Rte_06010].
  • Avec la sémantique d'événements (queued), la RTE stocke les événements dans une file d'attente FIFO [SWS_Rte_02521] [SWS_Rte_02522]. Sa longueur résulte de RteQueuedReceiverQueueLength ou, à défaut, de queueLength (SWS_RTE p. 320).

Diagramme d'activité : un événement est ajouté ou rejeté si la file d'attente est pleine. Le prochain accès explicite en lecture signale la perte et réinitialise l'indicateur d'erreur. Sources : [SWS_Rte_02522] [SWS_Rte_02523] [SWS_Rte_02524] [SWS_Rte_02525] [SWS_Rte_02572]

Entre les ECU, la RTE transmet les signaux via COM. Elle traite les données composites de manière atomique sous forme de groupe de signaux [SWS_Rte_04527] (SWS_RTE p. 326). Via les callbacks COM, COM peut activer des runnables [SWS_Rte_03530] [SWS_Rte_03531]. Dans R20-11, la RTE transmet et reçoit les grands tableaux d'octets via LdCom [SWS_Rte_01376] [SWS_Rte_01377] (SWS_RTE p. 350). La référence documentaire issue de R25-11 décrit à la place « Large Data Path in COM » pour cela (SWS_RTE p. 343). Pour R20-11, l'exigence fait foi.

La RTE génère les appels client-serveur selon le point d'appel du serveur sous la forme d'un Rte_Call synchrone ou asynchrone [SWS_Rte_01102] [SWS_Rte_01293] [SWS_Rte_01294]. Les paramètres d'une opération sont traités de manière atomique [SWS_Rte_04518]. Si l'appel n'est pas réalisé sous la forme d'un appel direct ou d'une Trusted Function, la RTE met en mémoire tampon à deux endroits [SWS_Rte_02527] [SWS_Rte_02528] (SWS_RTE p. 358) :

  • les requêtes côté serveur dans une file d'attente FIFO,
  • les réponses côté client dans une file d'attente de longueur 1.

La RTE surveille le délai d'expiration indépendamment du mode de réception. La valeur 0 désactive la surveillance [SWS_Rte_03763] [SWS_Rte_03767] (SWS_RTE p. 355).

Le client récupère le résultat avec Rte_Result, qui fournit RTE_E_TIMEOUT en cas de dépassement de délai. Machines de mode et déroulement d'une transition de mode

Pour les ModeDeclarationGroupPrototypes de chaque gestionnaire de mode, la RTE gère les modes actifs dans des mode machine instances [SWS_Rte_02546]. Les changements de mode sont notifiés de manière asynchrone via des ModeSwitchInterfaces sous forme de communication 1:n. La notification n'indique que le mode suivant [SWS_Rte_02508] [SWS_Rte_02566] [SWS_Rte_02567]. La RTE ne prend pas en charge plusieurs émetteurs pour la même machine de mode [SWS_Rte_02670]. Chaque machine de mode possède une file d'attente FIFO pour les notifications de changement. Si elle est pleine, la RTE rejette les nouvelles notifications. Une notification reste dans la file d'attente jusqu'à ce que le changement soit terminé [SWS_Rte_02718] [SWS_Rte_02719] [SWS_Rte_02720] [SWS_Rte_02721] (SWS_RTE p. 322).

Une transition se déroule en dix étapes [SWS_Rte_02665] :

  1. Les Mode Disablings sont activés [SWS_Rte_02661].
  2. La RTE exécute les on-exit-ExecutableEntitys [SWS_Rte_02562].
  3. Elle exécute les on-transition-ExecutableEntitys et attend leur fin [SWS_Rte_02707] [SWS_Rte_02708].
  4. Elle exécute les on-entry-ExecutableEntitys [SWS_Rte_02564].
  5. Elle lève les désactivations précédentes [SWS_Rte_02563].
  6. Enfin, elle déclenche les ModeSwitchedAckEvents [SWS_Rte_02587].

Les étapes 1 à 9 peuvent s'exécuter en parallèle sur chaque cœur. L'étape 10 ne suit que lorsque les autres étapes sont terminées pour l'ensemble de la machine de mode (ModemanagementGuide p. 15). Même si le nouveau mode est identique à l'ancien, la transition est exécutée [SWS_Rte_02669]. Le générateur rejette les configurations avec des runnables de catégorie 2 sur des événements de mode [SWS_Rte_02500] [SWS_Rte_02662] (SWS_RTE p. 426).

Diagramme d'activité : les dix étapes d'une transition de mode. Les étapes 1 à 9 s'exécutent par cœur, l'étape 10 seulement après achèvement sur tous les cœurs. Sources : [SWS_Rte_02665] [SWS_Rte_02708] [SWS_Rte_02721] ModemanagementGuide p. 15

Un gestionnaire de mode peut faire confirmer l'achèvement d'un changement via Rte_SwitchAck. L'API fournit RTE_E_TRANSMIT_ACK dès que le changement est terminé, et RTE_E_TIMEOUT lorsque le délai a été dépassé [SWS_Rte_02725] [SWS_Rte_02729] [SWS_Rte_02728] (SWS_RTE p. 716). Selon le mode actif, la RTE peut activer des OS-Schedule-Tables [SWS_Rte_05146]. Les types Rte_Rips_SwitchNotificationStatusType et Rte_DsmqStatusType décrivent le statut lors de l'enfilement et du défilement des notifications de changement [SWS_Rte_91113] [SWS_Rte_91102]. Les références documentaires correspondantes sont toutefois issues de R24-11 et R25-11 (SWS_RTE p. 980, SWS_RTE p. 982).

Génération, liaison des variantes ainsi que mesure et calibration

Dans la méthodologie, la RTE est créée dans l'activité « Generate BSW and RTE ». Les entrées sont l'ECU Extract et les ECU Configuration Values (Methodology p. 103). Le générateur lie la variabilité avec les moments de liaison SystemDesignTime et CodeGenerationTime dès la phase Contract et la phase Generation. Il rejette les entrées sans variante clairement sélectionnée [SWS_Rte_06501] [SWS_Rte_06502] [SWS_Rte_06507] [SWS_Rte_06509] (SWS_RTE p. 467). Il met en œuvre la variabilité PreCompileTime dans le code généré. Il refuse la variabilité LinkTime pertinente pour la RTE [SWS_Rte_06510] [SWS_Rte_06511]. Le commutateur strictConfigurationCheck régit si le générateur a le droit de compléter lui-même les parties de configuration manquantes [SWS_Rte_05148] [SWS_Rte_05150]. Il décrit lui-même la RTE générée comme module BSW. En font partie BswModuleDescription, BswInternalBehavior, BswImplementation ainsi que des BswModuleEntrys pour les API de cycle de vie [SWS_Rte_05165] [SWS_Rte_05166] [SWS_Rte_05167] [SWS_Rte_05177] (SWS_RTE p. 101).

La RTE alloue elle-même la mémoire pour les paramètres de calibration [SWS_Rte_03961]. Pour l'émulation de données avec support logiciel, les variantes single pointered, double pointered et initRam sont proposées. Exactement une d'entre elles est active par build RTE [SWS_Rte_03943] [SWS_Rte_03909] [SWS_Rte_03913] [SWS_Rte_03914] [SWS_Rte_03915]. L'émulation peut également être désactivée pour l'ensemble du code RTE [SWS_Rte_03942] (SWS_RTE p. 232). Le support de calibration peut être défini comme actif ou non par type de composant [SWS_Rte_05145]. Pour les outils de mesure et de calibration, le générateur crée McSupportData. Un élément McSwEmulationMethodSupport-Element y documente la méthode sélectionnée [SWS_Rte_05118] [SWS_Rte_05137] [SWS_Rte_05138] (SWS_RTE p. 258). Ces données sont intégrées dans la génération A2L (Methodology p. 414).

Comportement en cas d'erreur

Un composant ne reçoit les informations d'erreur et de statut qu'en tant que valeur de retour de l'API de la RTE [SWS_Rte_01034] (SWS_RTE p. 579). Les types d'erreurs ont des priorités différentes :

  • Les Immediate Infrastructure Errors ont la priorité sur les erreurs d'application [SWS_Rte_02593].
  • Les Overlayed Errors sont signalées via un bit dédié et peuvent être combinées avec n'importe quel autre code [SWS_Rte_01318] (SWS_RTE p. 584).

Cycle de vie. Si Rte_Start ne peut pas créer une ressource requise, il fournit RTE_E_LIMIT, sinon RTE_E_OK [SWS_Rte_01261] [SWS_Rte_01262] (SWS_RTE p. 806). Avant l'initialisation complète et après l'arrêt, la RTE ignore les requêtes client-serveur entrantes ainsi que les données Sender-Receiver [SWS_Rte_02535] [SWS_Rte_02536]. Le BSW-Scheduler se comporte de manière correspondante [SWS_Rte_04552]. Un appel ainsi ignoré fournit RTE_E_TIMEOUT [SWS_Rte_04553] [SWS_Rte_04554].

Communication.

  • La RTE traite les ports non connectés de manière contrôlée ; Rte_Call fournit alors RTE_E_UNCONNECTED [SWS_Rte_01329] [SWS_Rte_01334].
  • Si la vérification de plage est active et qu'une valeur reçue est hors limites, l'API fournit RTE_E_OUT_OF_RANGE [SWS_Rte_03845] [SWS_Rte_03846] [SWS_Rte_01371] (SWS_RTE p. 420).
  • Si un composant au sein de l'ECU reçoit une valeur invalidée, le comportement dépend de handleInvalid. Avec keep, la réception est traitée comme une erreur. Avec replace, la RTE remplace la valeur par la valeur initiale [SWS_Rte_05030] [SWS_Rte_05049] (SWS_RTE p. 317).
  • Si un composant d'une partition non approuvée (untrusted) transmet des pointeurs, la RTE vérifie la propriété de la mémoire. En cas de violation, elle signale RTE_E_SEG_FAULT [SWS_Rte_02752] [SWS_Rte_02753] [SWS_Rte_02754].

Configuration. Le générateur rejette les configurations erronées dès le départ, par exemple des longueurs de file d'attente ≤ 0 ou des délais d'attente contradictoires [SWS_Rte_02526] [SWS_Rte_02723] [SWS_Rte_03764].

Utilisation

La fonction Rte_Start ([SWS_Rte_02569]), qui est toujours générée ([SWS_Rte_01309]), alloue et initialise les ressources système et de communication utilisées par la RTE ([SWS_Rte_03015]). Elle ne possède aucun paramètre de transmission, renvoie un Std_ReturnType et doit se terminer dans un temps d'exécution fini sans boucle infinie ([SWS_Rte_02585]).

Contexte d'appel et concurrence

Rte_Start ne doit être appelée sur chaque Core qu'exactement une fois par le EcuStateManager depuis un contexte d'OS de confiance, après que tous les modules de logiciel de base requis pour la RTE ont été initialisés ([SWS_Rte_CONSTR_09035]). L'appel s'effectue indépendamment sur chaque Core ([SWS_Rte_07615]) et couvre les activités de démarrage spécifiques aux partitions pour toutes les partitions affectées à ce Core ([SWS_Rte_07616]).

Ordre d'initialisation et interaction

Dans le cadre de Rte_Start, une séquence de démarrage coordonnée est exécutée :

  • Les variables allouées pour les ramBlocks sont initialisées en fonction de la RteInitializationStrategy configurée ([SWS_Rte_07632]).
  • Après l'initialisation des variables, mais avant l'exécution de Runnable Entities, la RTE appelle les fonctions d'initialisation Rte_Rips_Rte_Start de tous les RTE Implementation Plug-Ins impliqués ([SWS_Rte_80052]).
  • Les Runnables déclenchées par InitEvent sont activées une seule fois ([SWS_Rte_06761]), et la transition vers les modes initiaux est engagée ([SWS_Rte_06766]).
  • S'il n'existe pas de Rte_StartTiming séparé, Rte_Start démarre en outre l'activation des Runnables qui sont contrôlées par des TimingEvents ([SWS_Rte_07575]) ou des BackgroundEvents ([SWS_Rte_07178]).

Certaines fonctions telles que Rte_SetMirror peuvent être explicitement appelées dès avant Rte_Start ([SWS_Rte_07319]).

Gestion des erreurs

Si Rte_Start est appelée avant SchM_Init, le planificateur du logiciel de base ou la RTE signale l'erreur RTE_E_UNINIT (0x07) ([SWS_Rte_07683]) lorsque RteDevErrorDetectUninit est activé. De même, l'appel non autorisé d'API RTE surveillées avant Rte_Start entraîne le signalement de RTE_E_UNINIT ([SWS_Rte_07682]).

Utilisation et sémantique

La fonction Rte_Stop ([SWS_Rte_02570]) sert à la finalisation de la RTE sur le Core appelant et libère toutes les ressources système et de communication occupées par la RTE sur ce Core ([SWS_Rte_01262]). L'interface est toujours fournie ([SWS_Rte_01310]), ne possède pas de paramètres, renvoie Std_ReturnType et se termine en un temps d'exécution fini ([SWS_Rte_02584]).

Conditions d'ordonnancement et concurrence

  • Après l'appel de Rte_Stop sur un Core, la RTE ne doit plus activer, démarrer ou libérer de RunnableEntitys sur ce Core ([SWS_Rte_02538]).
  • Rte_Stop doit être appelée par le EcuStateManager avant l'arrêt des modules de logiciel de base requis par la RTE ([SWS_Rte_CONSTR_09038]).
  • L'API SchM_Deinit ne doit être appelée qu'après la fin complète de Rte_Stop ([SWS_Rte_CONSTR_09056]).
  • La fonction Rte_GetMirror reste appelable même après l'arrêt de la RTE par Rte_Stop et s'appuie sur un système d'exploitation en cours d'exécution ([SWS_Rte_07350]).

Interaction et gestion des erreurs

  • Au sein de Rte_Stop, la RTE appelle les fonctions d'arrêt Rte_Rips_Rte_Stop de tous les RTE Implementation Plug-Ins impliqués ([SWS_Rte_80053]), lesquelles doivent obligatoirement être fournies aux côtés d'autres API de cycle de vie ([SWS_Rte_70047]).

  • Dans le contexte de la spécification, le statut d'erreur RTE_E_LIMIT est en outre mentionné lorsqu'une limite interne a été dépassée ou que l'allocation d'une ressource requise a échoué ([SWS_Rte_01262]).

La fonction Rte_Rips_SchM_Deinit réinitialise les parties d'un RTE Implementation Plug-In (RIPS) qui sont pertinentes pour les opérations du Basic Software Scheduler (SchM) ([SWS_Rte_89019]). L'interface est déclarée via le fichier d'en-tête Rte_Rips_<PlugIn>.h et possède l'ID de service 0xF3.

Concurrence et restrictions

La fonction est spécifiée comme non réentrante (Non Reentrant) ([SWS_Rte_89019]). Un appel parallèle ou concurrent pour la même instance de plug-in est donc inadmissible.

Rte_Rips_SchM_Deinit est fermement intégré dans le cycle de vie de la RTE et de ses plug-ins :

  • Chaque RTE Implementation Plug-In doit obligatoirement fournir les fonctions standardisées de cycle de vie Rte_Rips_SchM_Init, Rte_Rips_Rte_Start, Rte_Rips_Rte_Stop et Rte_Rips_SchM_Deinit ([SWS_Rte_70047]).

Utilisation

Le type Rte_DsmqStatusType ([SWS_Rte_91102]) est dérivé de uint8 et représente l'état d'opérations sur une file d'attente de modes partagée distribuée (Distributed Shared Mode Queue, DSMQ). Conformément à [SWS_Rte_80085], le type est défini dans l'en-tête Rte_Type.h avec ses littéraux associés.

La plage de valeurs comprend cinq états définis ([SWS_Rte_91102]) :

  • RTE_DSMQ_ENQUEUED_FIRST (0x01) : la notification de changement de mode a été enfilée dans une DSMQ auparavant vide.
  • RTE_DSMQ_ENQUEUED_NOT_FIRST (0x02) : la notification a été enfilée dans une DSMQ non vide.
  • RTE_DSMQ_ENQUEUE_FAILED (0x03) : l'enfilage dans une DSMQ non vide a échoué.
  • RTE_DSMQ_DEQUEUED_LAST (0x04) : la dernière notification de changement de mode a été défilée de la DSMQ.
  • RTE_DSMQ_DEQUEUED_NOT_LAST (0x05) : une notification de changement de mode a été défilée de la DSMQ, d'autres notifications restant dans la file d'attente.

Gestion des erreurs

Si l'enfilage d'une notification de changement de mode dans une DSMQ non vide échoue, cela est indiqué par la valeur d'état RTE_DSMQ_ENQUEUE_FAILED (0x03) ([SWS_Rte_91102]). Aucun message DET ou DEM spécifique n'est défini pour ce type de données.

Interaction et concurrence

Les valeurs de ce type sont transmises comme paramètre d'entrée dsmqstatus à des interfaces du RTE Implementation Plug-In (RIPS) :

  • Rte_Rips_<PlugIn>_DsmqSwitch_<BswSwcI>_<MMI> ([SWS_Rte_91103]) notifie le plug-in de manière synchrone de l'enfilage dans une DSMQ.
  • Rte_Rips_<PlugIn>_DsmqTransitionEnd_<BswSwcI>_<MMI> ([SWS_Rte_91106]) signale au plug-in de manière synchrone la fin d'une transition de mode spécifique dans un OsTask de transition DSMQ.

Les deux services RIPS appelants sont spécifiés comme synchrones et réentrants ([SWS_Rte_91103], [SWS_Rte_91106]).
