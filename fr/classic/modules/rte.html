Relie les composants logiciels entre eux ainsi qu’au logiciel de base et coordonne leur exécution.

Le Runtime Environment (RTE) relie les composants logiciels AUTOSAR entre eux ainsi qu’aux modules du logiciel de base et régule, via le Basic Software Scheduler (SchM), l’ordonnancement déterministe sur la Classic Platform (SWS_RTE p. 100). Le cycle de vie est coordonné via des interfaces standardisées, depuis SchM_Init et Rte_Start jusqu’à Rte_Stop et SchM_Deinit [SWS_Rte_08060], [SWS_Rte_03015]. En plus des modèles émetteur-récepteur et client-serveur, des mécanismes de pointeurs logiciels pour les paramètres de calibration ainsi que des contrôles de protection mémoire aux frontières de partitions assurent un fonctionnement temps réel robuste [SWS_Rte_03914], [SWS_Rte_02752].

Le Runtime Environment (RTE) découple les composants logiciels AUTOSAR du matériel du calculateur et coordonne, conjointement avec le Basic Software Scheduler (SchM), l’exécution de tous les flux applicatifs et du logiciel de base (SWS_RTE p. 100). Le démarrage contrôlé s’effectue par étapes via l’EcuStateManager : SchM_Init initialise d’abord les structures du planificateur, suivi de SchM_Start avant l’appel de BswM_Init, puis de SchM_StartTiming pour autoriser les événements BSW périodiques [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548]. Les SW-C applicatifs sont ensuite démarrés via Rte_Start et arrêtés lors de la phase d’arrêt par Rte_Stop avant la désinitialisation via SchM_Deinit [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551].

Diagramme de séquence : coordination temporelle du démarrage et de l’arrêt entre EcuM, SchM et RTE. Sources : [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

La communication couvre les modèles émetteur-récepteur et client-serveur, aussi bien intra- qu’inter-ECU (SWS_RTE p. 286). Les éléments de données non mis en mémoire tampon garantissent des valeurs initiales cohérentes via initValue, tandis que les événements mis en mémoire tampon sont traités via des files d’attente FIFO [SWS_Rte_06009], [SWS_Rte_02521]. Dans les interactions client-serveur, des descripteurs de transaction à deux éléments associent les requêtes asynchrones aux réponses correspondantes [SWS_Rte_02649]. Les changements de mode via Rte_Switch exécutent une séquence déterministe en dix étapes, où les Distributed Shared Mode Queues garantissent l’ordre de traitement strict de plusieurs machines de modes [SWS_Rte_02631], [SWS_Rte_02665], [SWS_Rte_91102].

Diagramme de contexte : structures d’adressage et d’indirection des méthodes de calibration Single Pointered et Double Pointered. Sources : [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

Pour la calibration en ligne, le RTE génère des structures de pointeurs selon le principe Single Pointered ou Double Pointered, ce qui permet de modifier des groupes de paramètres en RAM sans émulation matérielle [SWS_Rte_03913], [SWS_Rte_03914]. Les dépassements de plage erronés ou les délais d’attente dépassés sont signalés au composant appelant via Std_ReturnType, tandis que des vérifications de protection mémoire aux frontières de partitions empêchent les manipulations non autorisées [SWS_Rte_01034], [SWS_Rte_03845], [SWS_Rte_02752].

Rôle et limites système du RTE dans la Classic Platform

Le Runtime Environment (RTE) constitue l’épine dorsale fonctionnelle de l’architecture AUTOSAR Classic en découplant complètement les composants logiciels (SW-C) du matériel informatique sous-jacent ainsi que des modules du Basic Software (BSW) proches du matériel (SWS_RTE p. 100). Le générateur RTE produit pour chaque calculateur une interface sur mesure qui résout toutes les relations de communication – aussi bien localement sur un microcontrôleur (intra-ECU) qu’à l’échelle du réseau via des bus de communication (inter-ECU) – par des appels d’API uniformes tels que Rte_Read, Rte_Write ou Rte_Call [SWS_Rte_01091], [SWS_Rte_01102]. Grâce à la mise à disposition d’un élément BswModuleDescription généré ainsi que des descriptions BswInternalBehavior associées, le RTE s’intègre en tant que partie intégrante dans le schéma de configuration et de paquetage d’AUTOSAR [SWS_Rte_05165], [SWS_Rte_05166].

Les instanciations multiples d’un même composant logiciel ne sont résolues par le RTE que par des Runnable Entities réentrantes avec partage de code ; la duplication de code n’est expressément pas prise en charge [SWS_Rte_03015], [SWS_Rte_02002]. Pour chaque instance, un identifiant d’instance unique est transmis dans le code C ou adressé via la Component Data Structure (CDS), ce qui garantit des exécutions d’instances parallèles dans des contextes de tâches partagés sans corruption mutuelle des données (SWS_RTE p. 126, SWS_RTE p. 804). En complément des SW-C applicatifs, le RTE prend en charge l’ordonnancement cyclique et la gestion des modes de tous les modules BSW via le Basic Software Scheduler (SchM) [SWS_Rte_08060], [SWS_Rte_07273].

Cycle de vie et coordination du démarrage de SchM et du RTE

Le démarrage du système requiert un ordre strictement défini entre le planificateur BSW (SchM) et le RTE orienté application (SWS_RTE p. 459). Avant l’initialisation du SchM, seules les fonctions de verrouillage SchM_Enter et SchM_Exit sont disponibles pour des raisons de sûreté système. L’EcuStateManager appelle d’abord la fonction SchM_Init, ce qui initialise les structures de données internes et les machines de modes, et démarre les BswSchedulableEntities associées à des Background-Events [SWS_Rte_08060], [SWS_Rte_07584]. SchM_Start doit être appelée avant même l’appel de BswM_Init [SWS_Rte_07273], [SWS_Rte_04548]. L’activation des traitements BSW périodiques (BswTimingEvents) est ensuite validée via SchM_StartTiming [SWS_Rte_04548], [SWS_Rte_04551], [SWS_Rte_07574].

Diagramme de séquence : coordination temporelle du démarrage et de l’arrêt entre EcuM, SchM et RTE. Sources : [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

Ce n’est que lorsque les services de base nécessaires sont opérationnels que l’EcuStateManager active l’exécution des SW-C applicatifs avec Rte_Start et déclenche les transitions de mode pour les Runnables On-Entry non groupées [SWS_Rte_03015], [SWS_Rte_06766]. En cas d’échec de l’allocation des ressources lors de Rte_Start, la fonction renvoie le code d’erreur RTE_E_LIMIT [SWS_Rte_01262]. Lors de l’arrêt du calculateur, Rte_Stop termine d’abord l’exécution applicative et ignore à partir de cet instant les requêtes et données entrantes [SWS_Rte_02538], [SWS_Rte_02535], [SWS_Rte_02536]. Ce n’est qu’après l’arrêt complet de Rte_Stop que SchM_Deinit peut être appelée, libérant toutes les ressources système du planificateur et déclenchant les nettoyages spécifiques aux plug-ins via Rte_Rips_SchM_Deinit [SWS_Rte_04551], [SWS_Rte_07277], [SWS_Rte_89019].

Modèles de communication : émetteur-récepteur et client-serveur

Dans le paradigme émetteur-récepteur, le RTE fait une distinction fondamentale entre la sémantique de données et la sémantique d’événements (SWS_RTE p. 286). Avec la sémantique de données (swImplPolicy != queued), seule la dernière valeur écrite est conservée dans le tampon et consommée de manière explicite au moyen de Rte_Read ou de manière implicite via Rte_IRead [SWS_Rte_01091], [SWS_Rte_06000]. En cas de lecture implicite, le RTE garantit une copie cohérente de la valeur des données sur l’ensemble de la durée d’exécution de la Runnable Entity [SWS_Rte_06001]. Avant la première réception, le RTE fournit la valeur initValue configurée, de sorte qu’aucun état mémoire non initialisé ne soit traité [SWS_Rte_06009], [SWS_Rte_06010].

Diagramme de séquence : communication émetteur-récepteur inter-ECU pour signaux non mis en mémoire tampon avec sécurisation par valeur initiale. Sources : [SWS_Rte_01091], [SWS_Rte_06009], [SWS_Rte_01289], AUTOSAR_SWS_RTE p. 148.

En revanche, la sémantique d’événements (swImplPolicy = queued) traite des séquences de données sans perte via des structures de tampons FIFO, qui sont remplies au moyen de Rte_Send et décrémentées par Rte_Receive [SWS_Rte_01072], [SWS_Rte_01092], [SWS_Rte_02521]. Si la limite de tampon définie via RteQueuedReceiverQueueLength est atteinte, le RTE rejette les nouvelles données entrantes et active un indicateur d’erreur correspondant [SWS_Rte_08940], [SWS_Rte_02523]. Pour les gros volumes de données, le RTE utilise des voies de transport spécialisées telles que LdCom ou Large-Data-COM avec verrouillage du tampon de signal [SWS_Rte_01376], [SWS_Rte_01379].

La communication client-serveur prend en charge les appels synchrones (Rte_Call) ainsi que les interactions asynchrones avec interrogation séparée du résultat via Rte_Result [SWS_Rte_01102], [SWS_Rte_01111]. Côté serveur, le RTE met les requêtes entrantes en mémoire tampon dans une file d’attente FIFO, à condition qu’aucun appel direct ne soit configuré, tandis que la réponse est temporairement stockée côté client dans un tampon de longueur 1 [SWS_Rte_02527], [SWS_Rte_02528]. Lors d’appels inter-partitions ou inter-calculateurs, un Transaction Handle bipartite, composé d’un identifiant client et d’un compteur de séquence, assure l’association exacte des paquets de réponse à la requête initiale [SWS_Rte_02649], [SWS_Rte_08711].

Gestion des modes, transitions d’états et Distributed Shared Mode Queues

La gestion des modes permet une commutation coordonnée des états de fonctionnement via des machines de modes dédiées (ModeMachineInstances), qui sont pilotées via Rte_Switch [SWS_Rte_02631]. Chaque transition d’état suit une séquence déterministe de dix étapes individuelles, comprenant notamment l’activation de verrous de mode, l’attente contrôlée de la fin des Runnables concernées ainsi que l’exécution séquentielle des entités OnExit, OnTransition et OnEntry [SWS_Rte_02665]. Ce n’est qu’après l’achèvement complet de toutes les phases que l’événement d’acquittement ModeSwitchedAckEvent est déclenché, dont l’état peut être interrogé via Rte_SwitchAck [SWS_Rte_02679], [SWS_Rte_02725], [SWS_Rte_02758].

Diagramme d’activité : déroulement déterministe en dix étapes d’une transition de mode au sein d’une ModeMachineInstance. Sources : [SWS_Rte_02665], [SWS_Rte_02679], EXP_ModeManagementGuide p. 16.

Afin d’imposer un ordre strict des changements de mode lorsque plusieurs machines de modes sont présentes – par exemple entre l’état d’allumage et l’état du moteur –, le RTE fournit des Distributed Shared Mode Queues (DSMQ) (SWS_RTE p. 442). L’état des opérations d’enfilement et de défilement dans de telles files d’attente est signalé via le type Rte_DsmqStatusType [SWS_Rte_91102]. Pour les transitions de clusters logiciels, Rte_Rips_SwitchNotificationStatusType représente les états d’enfilement et de défilement correspondants [SWS_Rte_91113]. Interprétation : pour le planificateur BSW, la configuration de points de synchronisation avant Rte_Start devrait être privilégiée afin d’établir des états système déterministes avant l’autorisation des tâches cycliques [SWS_Rte_06767]. Calibration, émulation de données et topologie mémoire

Les paramètres de calibration sont localisés de manière centralisée en mémoire par le RTE, car seul le générateur RTE connaît l’occupation globale de tous les composants et partitions sur le calculateur [SWS_Rte_03961]. Afin de permettre des calibrations en ligne sans matériel d’émulation spécialisé, le RTE prend en charge des méthodes d’émulation logicielle telles que la Single Pointered Method et la Double Pointered Method (SWS_RTE p. 236, SWS_RTE p. 237). Dans la Single Pointered Method, il existe en RAM une table de pointeurs (<RteParameterRefTab>) composée d’entrées void* qui pointent vers ParameterElementGroups [SWS_Rte_03913], [SWS_Rte_03947].

Diagramme de contexte : structures d’adressage et d’indirection des méthodes de calibration Single Pointered et Double Pointered. Sources : [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

La Double Pointered Method utilise quant à elle une indirection à deux niveaux : une table de référence stockée en ROM/Flash pointe vers des groupes de paramètres, tandis qu’un pointeur de base modifiable (Base reference) en RAM pointe initialement vers cette table Flash et peut être redirigé vers une copie modifiée en RAM lors d’une calibration [SWS_Rte_03914]. Les ParameterDataPrototypes sont ici séparés en groupes distincts en fonction de leur swAddrMethod [SWS_Rte_03908]. Le générateur RTE exporte l’ensemble des informations de structure et de pointeurs dans le conteneur McSupportData via McSwEmulationMethodSupport, afin de donner aux outils de calibration (tels qu’INCA ou CANape) un accès précis à l’adressage A2L [SWS_Rte_05118], [SWS_Rte_05137], [SWS_Rte_05138]. Interprétation : pour les calculateurs de sécurité hautement intégrés, la Double Pointered Method devrait être préférée, car la table de pointeurs elle-même reste principalement dans la Flash protégée et n’occupe des tampons RAM que lors d’une calibration active. Partitionnement, protection mémoire et communication inter-OS-Application

Dans les architectures multicœurs et à protection mémoire, la RTE interconnecte les composants logiciels par-delà les frontières de partitions (OS-Applications) au moyen de l'Inter-OS-Application Communication (IOC) (SWS_RTE p. 372). La RTE remplace ici les tampons de signaux internes par des tampons IOC proches du matériel et des fonctions de protection générées. Pour l'accès aux sections exclusives (ExclusiveAreas), l'intégrateur sélectionne des paramètres de configuration propres au mécanisme (RteExclusiveAreaImplMechanism), allant du verrouillage d'interruptions jusqu'aux spinlocks OS pour les accès inter-cœurs (SWS_RTE p. 203).

Lorsqu'une partition non testée ou non sécurisée (Non-Trusted) transmet des paramètres de type pointeur à une partition BSW ou SWC de confiance, la RTE effectue obligatoirement des contrôles d'adresse et de plage de mémoire [SWS_Rte_02752], [SWS_Rte_02753]. Le pointeur n'est relayé que si l'intégralité de l'objet mémoire référencé appartient à la partition appelante, ce qui empêche efficacement les violations de zone de protection et l'écrasement non autorisé d'espaces mémoire tiers (SWS_RTE p. 378).

Comportement en cas d'erreur

Le traitement des erreurs de la RTE sépare strictement les erreurs d'infrastructure des erreurs applicatives (SWS_RTE p. 579). Tous les états d'erreur sont immédiatement signalés à l'appelant via le type de retour Std_ReturnType [SWS_Rte_01034]. Parmi les erreurs directes d'infrastructure figurent notamment RTE_E_TIMEOUT (129), RTE_E_LIMIT (130), RTE_E_NO_DATA (131), RTE_E_UNCONNECTED (134), RTE_E_IN_EXCLUSIVE_AREA (135) ainsi que RTE_E_SEG_FAULT (136) (SWS_RTE p. 586).

Diagramme de séquence : détection et propagation d'erreurs de plage de valeurs via Rte_Read. Sources : [SWS_Rte_01091], [SWS_Rte_01371], [SWS_Rte_03845], AUTOSAR_CP_SWS_RTE p. 409.

Lorsque la validation des données est activée (DataSemantics range check), la RTE vérifie les valeurs de signaux entrantes par rapport à des plages de valeurs définies [SWS_Rte_01371]. Si une valeur reçue est hors limites, l'API de lecture RTE_E_OUT_OF_RANGE retourne [SWS_Rte_03845], [SWS_Rte_03846]. Pour les signaux dotés d'une Invalidation-Policy, en présence de replace, la RTE remplace la valeur par la initValue ou, en présence de keep, conserve la valeur précédente et lève un événement d'erreur [SWS_Rte_05030], [SWS_Rte_05049]. En cas de surveillance de timeout via aliveTimeout, la RTE enregistre l'absence via Rte_COMCbkRxTOut et propage RTE_E_TIMEOUT aux SW-C en attente [SWS_Rte_08061], [SWS_Rte_03763].

Preuves détaillées supplémentaires

La conception technique exacte de la RTE et du scheduler s'appuie sur les exigences clés suivantes du payload :

  • Cycle de vie et intégration SchM : [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_04551] et [SWS_Rte_03015] normalisent le démarrage et l'arrêt au niveau du cœur (SWS_RTE p. 459).
  • Génération d'interfaces et de fonctions : [SWS_Rte_01091] (Rte_Read), [SWS_Rte_01072] (Rte_Send), [SWS_Rte_01102] (Rte_Call) et [SWS_Rte_01111] (Rte_Result) régissent les signatures et les sémantiques d'appel (SWS_RTE p. 720, SWS_RTE p. 731).
  • Gestion des modes et DSMQ : [SWS_Rte_02665] définit les 10 niveaux de transition ; [SWS_Rte_91102] et [SWS_Rte_91113] consignent l'état de la file d'attente (EXP_ModeManagementGuide p. 16, SWS_RTE p. 982).
  • Méthodes de calibration : [SWS_Rte_03913] et [SWS_Rte_03914] spécifient les structures de tables Single et Double Pointered (SWS_RTE p. 236, SWS_RTE p. 237).
  • Signalement des erreurs : [SWS_Rte_01034], [SWS_Rte_01262] ainsi que [SWS_Rte_03845] garantissent des codes d'erreur cohérents via Std_ReturnType (SWS_RTE p. 586).

La fonction Rte_Start alloue et initialise les ressources système et de communication utilisées par la RTE [SWS_Rte_03015]. L'API est toujours générée [SWS_Rte_01309], possède la signature Std_ReturnType Rte_Start (void) [SWS_Rte_02569] et doit impérativement retourner dans un temps d'exécution fini, sans boucle infinie [SWS_Rte_02585].

La fonction ne doit être appelée sur chaque Core qu'exactement une fois par le EcuStateManager depuis un contexte OS de confiance, après que tous les modules de Basic Software requis par la RTE ont été initialisés [SWS_Rte_CONSTR_09035]. L'appel est exécuté indépendamment sur chaque Core [SWS_Rte_07615] et effectue les activités de démarrage spécifiques aux partitions pour toutes les partitions assignées à ce Core [SWS_Rte_07616].

Au cours de son déroulement, la RTE initialise les variables allouées pour les blocs de RAM en fonction de la stratégie configurée [SWS_Rte_07632]. Après l'initialisation des variables, mais avant l'exécution des Runnables, la RTE appelle les fonctions d'initialisation Rte_Rips_Rte_Start de tous les RTE Implementation Plug-Ins impliqués [SWS_Rte_80052]. Ensuite, la RTE active en une seule fois tous les Runnables déclenchés par InitEvent [SWS_Rte_06761] et amorce la transition vers les modes initiaux [SWS_Rte_06766]. Si l'API Rte_StartTiming n'existe pas, Rte_Start démarre en outre l'activation des Runnables déclenchés par TimingEvent [SWS_Rte_07575] ou BackgroundEvent [SWS_Rte_07178].

Pour la gestion des erreurs, lorsque RteDevErrorDetectUninit est activé, la RTE ou le SchM signale l'erreur RTE_E_UNINIT (0x07) si Rte_Start est appelé avant SchM_Init [SWS_Rte_07683]. Avant l'exécution de Rte_Start, les API d'exécution de la RTE ne doivent pas être appelées, sous peine de provoquer également RTE_E_UNINIT [SWS_Rte_07682] ; Rte_SetMirror peut en revanche déjà être appelé avant Rte_Start [SWS_Rte_07319].

La fonction Rte_Stop ([SWS_Rte_02570]) est générée dans chaque configuration ([SWS_Rte_01310]) et sert à finaliser la RTE sur le Core exécutant ([SWS_Rte_01262]). À cette occasion, l'ensemble des ressources système et de communication allouées par la RTE sur ce Core sont libérées ([SWS_Rte_01262]). L'appel synchrone retourne avec certitude dans un temps d'exécution fini ([SWS_Rte_02584]).

Dans le système global, Rte_Stop doit être appelé par le EcuStateManager avant que les modules de Basic Software requis par la RTE ne soient arrêtés ([SWS_Rte_CONSTR_09038]).
