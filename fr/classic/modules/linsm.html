Rôle du LinSM entre ComM, BswM et LinIf

Le LIN State Manager (LinSM) est le gestionnaire d’état de bus pour LIN. Le ComM demande les capacités de communication souhaitées par ses utilisateurs auprès des gestionnaires d’état de bus SWS ComM p. 19. Pour LIN, cela s’effectue via LinSM_RequestComMode [SWS_LinSM_00126]. Le LinSM convertit ces demandes pour chaque réseau LIN en appels vers la LIN Interface. Il renvoie le résultat via les interfaces obligatoires ComM_BusSM_ModeIndication, ComM_BusSM_BusSleepMode, BswM_LinSM_CurrentState et BswM_LinSM_CurrentSchedule. Il contrôle le bus, entre autres, via LinIf_GotoSleep et LinIf_ScheduleRequest [SWS_LinSM_00229]. De manière optionnelle, il utilise Det_ReportError et LinIf_SetTrcvMode [SWS_LinSM_00138].

La frontière du système est étroitement délimitée. Le LinSM ne gère que les réseaux ; le pilote LIN qui dessert un réseau est encapsulé par le LinIf SWS LinSM p. 28. Un réveil par le cluster n’est pas traité par le LinSM, mais par l’EcuM. Cela conduit le ComM à demander le réseau, de sorte que le LinSM ne voit que COMM_FULL_COMMUNICATION dans les deux cas SWS LinSM p. 27. Le module importe les types ComM_ModeType, NetworkHandleType et LinIf_SchHandleType [SWS_LinSM_00219].

Modèle d’états par réseau LIN

Au démarrage, LINSM_UNINIT est actif, avant même qu'une API ne soit appelée SWS LinSM p. 22. LinSM_Init initialise le module avec un pointeur vers LinSM_ConfigType [SWS_LinSM_00155] [SWS_LinSM_00221]. Ensuite, LINSM_NO_COM s'applique pour chaque réseau. LinSM_Init ne signale cette première transition ni au ComM ni au BswM, car le ComM n'est alors potentiellement pas encore initialisé SWS LinSM p. 23. Dans LINSM_NO_COM, le bus reste silencieux.

LINSM_FULL_COM est le seul état dans lequel la communication sur le bus LIN est autorisée. Chaque réseau l'atteint indépendamment des autres. Lors de l'entrée, le ComM reçoit COMM_FULL_COMMUNICATION et le BswM LINSM_FULL_COM SWS LinSM p. 23. Le sous-état LINSM_RUN_COMMUNICATION devient actif [SWS_LinSM_00301]. Le LinSM notifie le BswM via LinSM_ModeType avec les valeurs LINSM_FULL_COM (0x01) et LINSM_NO_COM (0x02) [SWS_LinSM_00220] SWS BswM p. 72.

Le second sous-état LINSM_GOTO_SLEEP couvre le temps d'attente de la confirmation de sleep. Si LinSM_GotoSleepConfirmation survient dans ce sous-état, le LinSM passe à LINSM_NO_COM indépendamment du paramètre success ; dans tous les autres états, le callback est ignoré SWS LinSM p. 24. LINSM_GOTO_SLEEP est probablement activé dès que LinIf_GotoSleep retourne avec E_OK ; la source s'interrompt à cet endroit. Un schéma plus ancien nomme l'état d'exécution LINSM_RUN_SCHEDULE SWS LinSM Fig. 5 p. 22. Le nom issu de [SWS_LinSM_00301] fait foi.

Diagramme d'états : l'état du module englobe une machine d'états propre pour chaque réseau LIN avec NO_COM et FULL_COM ; le passage en veille s'effectue via LINSM_GOTO_SLEEP (condition d'entrée à titre d'interprétation). Sources : [SWS_LinSM_00301], SWS LinSM p. 24, SWS LinSM Fig. 7.1 p. 20, SWS LinSM Fig. 7.2 p. 21

Réveil : de la demande du ComM à LINSM_FULL_COM

LinSM_RequestComMode fonctionne de manière asynchrone. Le changement de mode n'est pas immédiat, et le LinSM notifie l'appelant après achèvement [SWS_LinSM_00126]. En cas de COMM_FULL_COMMUNICATION, le LinSM appelle LinIf_Wakeup directement, c'est-à-dire sans attendre la Main Function suivante, et réinitialise le compteur de répétitions SWS LinSM p. 27. Auparavant, il démarre pour le réseau un temporisateur de confirmation avec LinSMConfirmationTimeout SWS LinSM p. 27.

Le LinIf signale l'envoi du signal de réveil via LinSM_WakeupConfirmation [SWS_LinSM_00132]. Lorsque success = TRUE, le réseau passe à LINSM_FULL_COM. Sinon, le LinSM rétablit l'état précédent afin que le ComM et le BswM reçoivent tout de même une notification de mode SWS LinSM p. 27. Si LinSMTransceiverPassiveMode est configuré, le LinSM active le transceiver via LinIf_SetTrcvMode lors de l'entrée dans LINSM_FULL_COM SWS LinSM p. 23.

Un temporisateur de silence après réveil avec LinSMSilenceAfterWakeupTimeout évite les tentatives de réveil trop rapprochées [SWS_LinSM_00235]. Si le ComM demande COMM_FULL_COMMUNICATION alors que ce temporisateur est en cours d'exécution, le LinSM retarde LinIf_Wakeup jusqu'à son expiration [SWS_LinSM_00237]. Si la communication complète est toujours demandée après l'expiration, le LinSM redémarre le processus de réveil [SWS_LinSM_00236].

Un esclave ne confirme le réveil que lorsqu'il reçoit le premier en-tête LIN du maître SWS LinIf p. 52. Si le maître ne commence pas l'ordonnancement, la confirmation ne parvient pas. Le temporisateur dans le LinSM expire alors afin qu'il n'attende pas indéfiniment SWS LinSM p. 27.

Diagramme de séquence : réveil interne avec LinIf_Wakeup direct, surveillance par temporisateur et notification de mode dans les deux cas de résultat. Sources : [SWS_LinSM_00126], [SWS_LinSM_00132], SWS LinSM p. 27, SWS LinSM Fig. 8 p. 42

Mise en veille : le maître émet, l'esclave réagit

Master: si le ComM demande COMM_NO_COMMUNICATION dans LINSM_FULL_COM, le LinSM appelle LinIf_GotoSleep pour envoyer la commande Goto-Sleep [SWS_LinSM_10208]. L'appel s'effectue directement, c'est-à-dire sans attendre la Main Function suivante [SWS_LinSM_00036]. Dans tous les autres cas, il n'a pas lieu [SWS_LinSM_10209]. Si LinIf_GotoSleep renvoie E_NOT_OK, LinSM_RequestComMode retourne également E_NOT_OK. En même temps, le LinSM rétablit l'état antérieur afin d'informer le ComM et le BswM [SWS_LinSM_00177].

Le LinIf signale via LinSM_GotoSleepConfirmation si la commande a été envoyée [SWS_LinSM_00135]. La notification de l'entrée dans LINSM_NO_COM au BswM et au ComM a lieu dans tous les cas, même après un problème SWS LinSM p. 24.

Diagramme de séquence : Goto-Sleep sur le maître avec branchement selon la valeur de retour de LinIf_GotoSleep. Sources : [SWS_LinSM_00036], [SWS_LinSM_00177], [SWS_LinSM_00135], SWS LinSM Fig. 6 p. 47

Slave: si le ComM demande COMM_NO_COMMUNICATION dans LINSM_FULL_COM, le LinSM enregistre uniquement la requête et retourne E_OK [SWS_LinSM_00230]. L'impulsion provient du bus. Le LinIf appelle LinSM_GotoSleepIndication lorsqu'une commande Goto-Sleep est reçue ou qu'un timeout de bus inactif survient [SWS_LinSM_91000]. Le LinSM appelle alors directement LinIf_GotoSleep dans LINSM_FULL_COM [SWS_LinSM_00231].

Si LinIf_GotoSleep retourne E_OK et que COMM_NO_COMMUNICATION a été demandé, le LinSM signale l'événement bus-sleep au ComM via ComM_BusSM_BusSleepMode [SWS_LinSM_00233]. Des versions ultérieures formulent cette obligation sans la condition E_OK SWS LinSM p. 26 ; l'exigence s'applique pour R20-11. En revanche, si la communication complète est demandée, le LinSM redémarre le processus de réveil après la séquence Goto-Sleep [SWS_LinSM_00234].

Diagramme de séquence : sur l'esclave, le bus déclenche la mise en veille ; la demande du ComM décide entre la notification de bus-sleep et un nouveau réveil. Sources : [SWS_LinSM_00230], [SWS_LinSM_00231], [SWS_LinSM_00233], [SWS_LinSM_00234], SWS LinSM Fig. 7 p. 48

Diagramme d'activité : logique de décision de LinSM_RequestComMode selon le mode demandé, l'état et le type de nœud. Sources : [SWS_LinSM_10208], [SWS_LinSM_10209], [SWS_LinSM_00177], [SWS_LinSM_00230], [SWS_LinSM_00237], SWS LinSM p. 36

Commutation de tables d'ordonnancement (maître LIN uniquement)

LinSM_ScheduleRequest et LinSM_ScheduleRequestConfirmation n'existent que si au moins un canal est configuré en tant que maître [SWS_LinSM_00241] [SWS_LinSM_00242]. Avec LinSM_ScheduleRequest, la couche supérieure demande de manière asynchrone une autre table d'ordonnancement [SWS_LinSM_00113]. Le LinSM transmet immédiatement la demande à LinIf_ScheduleRequest et retourne sa valeur de retour SWS LinSM p. 26. L'appelant typique est le BswM, qui utilise le LinSMScheduleIndex symbolique SWS LinSM p. 52. Le flux du protocole de transport LIN (LinTp) passe également de cette manière par le BswM vers des tables de diagnostic SWS LinIf p. 142.

Après LinSM_ScheduleRequestConfirmation [SWS_LinSM_00129], le LinSM signale la table active via BswM_LinSM_CurrentSchedule SWS BswM p. 80, pour autant que son temporisateur n'ait pas encore expiré. Pour les autres cas, les règles suivantes s'appliquent SWS LinSM p. 26 :

  • Si le temporisateur a expiré, le LinSM signale la table inchangée.
  • En cas de E_NOT_OK de LinIf_ScheduleRequest, il signale l'ancienne table lors de la Main Function suivante.
  • Il signale également les changements non demandés, comme la NULL-Schedule lors de la mise en veille.

Dans R20-11, le paramètre s'appelle schedule [SWS_LinSM_00113]. R22-11 a renommé les arguments Release Overview p. 50, des versions ultérieures le nomment ScheduleTableIdx SWS LinSM p. 34.

Configuration : type de nœud, base de temps et initialisation

LinSMNodeType détermine le périmètre de l'API. Les fonctions maître sont présentes dès qu'un canal est maître ; LinSM_GotoSleepIndication est présent dès qu'un canal est esclave [SWS_LinSM_00241] [SWS_LinSM_00243]. Des configurations mixtes sont ainsi possibles. Les paramètres post-build se trouvent dans la structure spécifique à l'implémentation LinSM_ConfigType [SWS_LinSM_00221].

LinSM_MainFunction cadence périodiquement les temporisateurs des timeouts de demande [SWS_LinSM_00156]. Chaque réseau possède son propre temporisateur de confirmation. LinSMConfirmationTimeout doit être égal à 0 ou à un multiple entier de la période de la Main Function SWS LinSM p. 27.

Le conteneur LinSMSchedule (0..*, maître uniquement) fait référence à des tables LinIf ; LinSMScheduleIndex doit correspondre à la valeur LinIf SWS LinSM p. 52. Un exemple dans le guide de gestion des modes montre une règle BswM appelant LinSM_Init après LinIf_Init Modemanagement-Leitfaden p. 54 [SWS_LinSM_00155].

Comportement en cas d'erreur

Avec LinSMDevErrorDetect, le LinSM signale les erreurs de développement au DET. Les codes sont LINSM_E_UNINIT, LINSM_E_NONEXISTENT_NETWORK, LINSM_E_PARAMETER, LINSM_E_PARAM_POINTER et LINSM_E_INIT_FAILED [SWS_LinSM_00053]. Les callbacks tels que LinSM_GotoSleepIndication signalent un réseau invalide ou l'état UNINIT [SWS_LinSM_00239] [SWS_LinSM_00240]. En cas de telles erreurs, les services retournent en outre E_NOT_OK SWS LinSM p. 36. Des pointeurs invalides transmis à LinSM_GetCurrentComMode et LinSM_GetVersionInfo entraînent LINSM_E_PARAM_POINTER SWS LinSM p. 35 SWS LinSM p. 34.

En l'absence de callback du LinIf, l'erreur d'exécution LINSM_E_CONFIRMATION_TIMEOUT s'applique [SWS_LinSM_00224]. Interprétation : elle est probablement signalée via Det_ReportRuntimeError. Cette interface n'est toutefois définie comme obligatoire que dans une version ultérieure SWS LinSM p. 41.

Sur le plan fonctionnel, le LinSM maintient la cohérence des gestionnaires de mode, même en cas d'erreur :

  • Un réveil ayant échoué conduit à une nouvelle notification de l'ancien état SWS LinSM p. 27.
  • Une confirmation de sleep infructueuse conduit tout de même à LINSM_NO_COM SWS LinSM p. 24.
  • Un LinIf_GotoSleep rejeté génère E_NOT_OK et une notification d'état [SWS_LinSM_00177].
  • Un changement de table rejeté entraîne la notification de l'ancienne table SWS LinSM p. 26.

Utilisation et sémantique

La fonction LinSM_ScheduleRequest ([SWS_LinSM_00113]) permet à une couche supérieure de demander le changement d'une table d'ordonnancement (schedule table) sur un réseau LIN. Le service est mis à disposition via l'en-tête LinSM.h, fonctionne de manière asynchrone et est spécifié comme réentrant.

Paramètres d'entrée :

  • network (NetworkHandleType) : Identification du canal LIN.
  • schedule (LinIf_SchHandleType) : Pointeur ou descripteur (handle) vers la nouvelle table d'ordonnancement à demander.

Valeurs de retour et comportement en cas d'erreur

La fonction renvoie un état de type Std_ReturnType ([SWS_LinSM_00113]) :

  • E_OK : La demande pour la table d'ordonnancement a été acceptée avec succès.
  • E_NOT_OK : La demande n'a pas pu être exécutée (par exemple si le module n'est pas initialisé).

Dépendances de configuration et interaction

La disponibilité de LinSM_ScheduleRequest est liée à la configuration du rôle du module : conformément à [SWS_LinSM_00241], la fonction n'est disponible que si le module LinSM est configuré en tant que maître LIN sur au moins un canal via le paramètre de configuration LinSMNodeType. Dans une configuration exclusivement esclave LIN, la fonction n'est pas disponible.

De manière analogue, la fonction de confirmation associée LinSM_ScheduleRequestConfirmation requiert également qu'au moins un canal soit exploité en tant que maître LIN ([SWS_LinSM_00242]).

La fonction LinSM_RequestComMode ([SWS_LinSM_00126]) sert à demander un mode de communication pour un canal LIN. L'appel se comporte de manière asynchrone : le changement de mode n'est pas effectué immédiatement, mais le LinSM avertit l'appelant dès que la transition d'état est terminée. Sont transmis comme paramètres d'entrée network pour l'identification du canal LIN ainsi que mode pour le mode de communication demandé.

En ce qui concerne la concurrence, l'interface est spécifiée comme réentrante ([SWS_LinSM_00126]). En guise de valeur de retour, la fonction fournit E_OK lorsque la demande a été acceptée avec succès. Si l'exécution de la demande n'est pas possible – par exemple si le module n'est pas initialisé –, E_NOT_OK est retourné ([SWS_LinSM_00126]).

Lors de l'interaction avec d'autres modules, le comportement d'erreur suivant est régi : si un appel de LinIf_GotoSleep fournit la valeur de retour E_NOT_OK, LinSM_RequestComMode doit également répondre par E_NOT_OK ([SWS_LinSM_00177]). Si le module LinSM renvoie la valeur E_NOT_OK lors de LinSM_RequestComMode, le même état doit être conservé ou défini, de sorte que ComM_BusSM_ModeIndication et BswM_LinSM_CurrentState soient appelés ([SWS_LinSM_00177]).

La fonction de rappel (callback) LinSM_ScheduleRequestConfirmation ([SWS_LinSM_00129]) sert de retour d'information au module LinSM dès qu'une nouvelle table d'ordonnancement précédemment demandée a effectivement été activée. Elle est appelée par l'interface LIN (LinIf).

Utilisation et paramètres

L'appel a lieu de manière synchrone et ne fournit pas de valeur de retour (void). La fonction est déclarée via l'en-tête LinSM.h et possède l'ID de service 0x20 conformément à [SWS_LinSM_00129]. Elle accepte deux paramètres d'entrée :

  • network (NetworkHandleType) : Identification du canal LIN concerné.
  • schedule (LinIf_SchHandleType) : Pointeur ou descripteur (handle) vers la table d'ordonnancement désormais active.

Concurrence et restrictions

Selon la spécification, la fonction est classifiée comme réentrante ([SWS_LinSM_00129]), ce qui permet de traiter des confirmations simultanées pour différents canaux.

Interaction

La fonction fait office d'interface dans l'interaction entre LinIf et LinSM : après qu'un changement de table d'ordonnancement a été initié, LinIf informe le LinSM via cette routine de rappel de la prise d'effet de la commutation ([SWS_LinSM_00129]).

Utilisation et contexte d'appel

La fonction de rappel LinSM_GotoSleepIndication ([SWS_LinSM_91000]) du module LinSM possède l'ID de service 0x03 et est déclarée via le fichier d'en-tête LinSM.h. Elle est appelée par l'interface LIN (LinIf) dès que la commande de passage en veille (« go to sleep command ») a été enregistrée sur le réseau ou qu'un délai d'inactivité du bus (« bus idle timeout ») est survenu ([SWS_LinSM_91000]).
