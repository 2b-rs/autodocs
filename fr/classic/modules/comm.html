Rôle du ComM entre les utilisateurs, les Bus State Managers et le cycle de vie

Le Communication Manager (ComM) prend en charge les besoins de communication de ses utilisateurs et les convertit en modes de communication des canaux physiques. Les utilisateurs peuvent être des Runnables, des SW-C, le BswM ou le DCM (SWS ComM p. 30). Vers le bas, le ComM s'adresse exclusivement aux Bus State Managers. Il demande les modes avec <BusSm>_RequestComMode() [SWS_ComM_00958] et les interroge avec <BusSm>_GetCurrentComMode() [SWS_ComM_00963]. Le préfixe (CanSM, LinSM, FrSM, EthSM) découle de ComMBusType [SWS_ComM_00962]. Le ComM reçoit le mode de bus notifié via ComM_BusSM_ModeIndication et le transmet aux utilisateurs via la RTE et le BswM [SWS_ComM_00675].

Les autres partenaires sont :

  • Nm, via les rappels ComM_Nm_*,
  • EcuM, qui signale les réveils,
  • NvM, pour les données persistantes,
  • BswM, avec BswM_ComM_CurrentPNCMode et BswM_ComM_InitiateReset [SWS_ComM_00829].

Diagramme de contexte : le ComM fait l'intermédiaire entre les utilisateurs (RTE, DCM, BswM) d'une part, et le Nm ainsi que les Bus State Managers d'autre part. Le NvM, le Com et le SchM sont des fournisseurs de services. Sources : SWS ComM (Abb.) p. 17, [SWS_ComM_00829], [SWS_ComM_00871].

Initialisation : ComM_Init reprend la structure post-build ComM_ConfigType et réinitialise les machines d'état internes [SWS_ComM_00146] [SWS_ComM_00162]. Ce faisant, le ComM lit les paramètres non volatils depuis la NVRAM. En cas d'échec, il utilise les valeurs par défaut (SWS ComM p. 97).

État et fonctionnement : ComM_GetStatus fournit COMM_UNINIT ou COMM_INIT [SWS_ComM_00242] [SWS_ComM_00668]. En fonctionnement, une ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429] propre s'exécute pour chaque canal.

Partitionnement : les appels provenant de partitions tierces doivent être rendus possibles par le biais d'un satellite [SWS_ComM_01019]. Le ComM n'appelle les API des Bus State Managers que dans leur partition [SWS_ComM_01020].

Désinitialisation : ComM_DeInit [SWS_ComM_00147] ne prend effet que si tous les canaux sont dans COMM_NO_COMMUNICATION. Ce faisant, le ComM sauvegarde les paramètres NV (SWS ComM p. 114).

Machine d'état de canal : No, Silent et Full Communication

ComM_ModeType prend quatre valeurs [SWS_ComM_00672] :

  • COMM_NO_COMMUNICATION,
  • COMM_SILENT_COMMUNICATION,
  • COMM_FULL_COMMUNICATION,
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST, uniquement en interne.

Les utilisateurs ne sont autorisés à demander que No et Full. Silent sert uniquement à la synchronisation avec le NM (SWS ComM p. 30, [SWS_ComM_00110]). Une machine d'état distincte s'exécute pour chaque canal (SWS ComM p. 65). ComM_StateType encode les états principaux et les sous-états [SWS_ComM_00674].

Chemin vers Full Communication :

  • Une demande sans limitation active ou un diagnostic actif mène à COMM_NO_COM_REQUEST_PENDING (SWS ComM p. 69).
  • La transition vers Full n'a lieu que lorsque ComM_CommunicationAllowed libère le canal [SWS_ComM_00871]. Si la demande disparaît auparavant, le canal retourne à l'état initial (SWS ComM p. 63).

Désactivation selon la variante de ComMNmVariant :

  • PASSIVE et SLAVE_PASSIVE passent inconditionnellement à COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915].
  • SLAVE_ACTIVE y passe dès qu'il n'existe plus aucune demande d'utilisateur [SWS_ComM_01017].
  • ComM_Nm_PrepareBusSleepMode mène à Silent lors de FULL ou PASSIVE [SWS_ComM_00826]. L'émission y est désactivée, la réception reste active (SWS ComM p. 71).
  • Les canaux esclaves mettent fin à la communication via ComM_BusSM_BusSleepMode [SWS_ComM_01018] [SWS_ComM_91000].
  • Les canaux LIGHT quittent Full après l'expiration de ComMNmLightTimeout (SWS ComM p. 78).

Demande de communication par les utilisateurs et le diagnostic

Utilisateurs et affectation : un utilisateur est identifié via ComM_UserHandleType. Les valeurs 0..254 sont valides ; 255 correspond à COMM_NOT_USED_USER_ID [SWS_ComM_00670]. Les utilisateurs sont affectés statiquement à des canaux [SWS_ComM_00995] ou à des PNC [SWS_ComM_00912]. Une affectation simultanée à un PNC et à son canal est interdite [SWS_ComM_00996].

Ports vers la RTE :

  • UR_{user_name} propose l'interface ComM_UserRequest [SWS_ComM_01011] [SWS_ComM_01000].
  • UM_{user_name} propose l'interface de changement de mode ComM_CurrentMode [SWS_ComM_01010] [SWS_ComM_01001]. Le groupe de modes ComMMode démarre dans COMM_NO_COMMUNICATION [SWS_ComM_01012].

Diagramme de collaboration : ports par lesquels les SW-C utilisateurs, les Mode Managers et les outils de mappage PNC interagissent avec le ComM. Sources : SWS ComM (Abb.) p. 81, [SWS_ComM_01006], [SWS_ComM_01007], [SWS_ComM_01008], [SWS_ComM_01009], [SWS_ComM_91107].

Demande et libération : une demande arrive soit par ComM_RequestComMode [SWS_ComM_00110], soit par ComM_DCM_ActiveDiagnostic [SWS_ComM_00873]. Le diagnostic libère de nouveau le canal avec ComM_DCM_InactiveDiagnostic [SWS_ComM_00874]. Pendant un diagnostic actif, une limitation est temporairement inopérante (SWS ComM p. 69).

Diagramme de séquence : démarrage actif de No vers Full Communication sur l'exemple de CAN, selon la variante NM. Sources : SWS ComM p. 167, SWS ComM (Abb.) p. 107, SWS ComM p. 75.

Interrogations :

  • ComM_GetRequestedComMode fournit le souhait de l'utilisateur enregistré de manière volatile dans le ComM [SWS_ComM_00079] (SWS ComM p. 118).
  • ComM_GetCurrentComMode interroge les Bus State Managers [SWS_ComM_00083].
  • ComM_GetMaxComMode prend en compte les limitations actives [SWS_ComM_00085].
  • En présence de plusieurs canaux par utilisateur, les deux fonctions fournissent chacune le mode le plus bas (SWS ComM p. 119, SWS ComM p. 117).
  • En option, le port CR_{channel_name} indique les utilisateurs qui maintiennent actuellement un canal sur Full [SWS_ComM_00904] [SWS_ComM_00906] [SWS_ComM_01005].

Réveil, gestion de réseau et arrêt ordonné

Démarrage passif : il débute par ComM_EcuM_WakeUpIndication [SWS_ComM_00275] ou ComM_EcuM_PNCWakeUpIndication [SWS_ComM_91001]. Lors d'un réveil de PNC, l'étendue dépend de ComMSynchronousWakeUp :

  • Avec FALSE, seuls les canaux référencés passent à COMM_NO_COM_REQUEST_PENDING [SWS_ComM_01014].
  • Avec TRUE, tous les canaux basculent [SWS_ComM_01015].

À l'état Network Requested, le ComM demande ensuite Nm_PassiveStartup. Pour les canaux gérés, cela s'effectue sur le canal gestionnaire [SWS_ComM_01016]. Il en va de même après ComM_Nm_RestartIndication [SWS_ComM_00792] (SWS ComM p. 75).

Diagramme de séquence : réaction à un réveil ou à un redémarrage NM jusqu'à Full Communication. Sources : SWS ComM (Abb.) p. 104, [SWS_ComM_00383], [SWS_ComM_01016], [SWS_ComM_00915].

Arrêt : il commence lorsque le dernier utilisateur libère Full ou que ComM_LimitChannelToNoComMode prend effet (SWS ComM p. 166). Le déroulement :

  1. Dans Ready Sleep, le ComM appelle Nm_NetworkRelease lors de FULL (SWS ComM p. 78).
  2. Le NM signale ComM_Nm_PrepareBusSleepMode [SWS_ComM_00391] ; le canal passe à Silent.
  3. Le NM signale ComM_Nm_BusSleepMode [SWS_ComM_00392] ; le canal passe à No Communication.

ComM_Nm_NetworkMode signale inversement l'entrée dans le Network Mode [SWS_ComM_00390].

Diagramme de séquence : libération ou limitation forcée via Ready Sleep et Silent jusqu'à Bus-Sleep, avec réinitialisation de l'ECU en option. Sources : SWS ComM (Abb.) p. 106, SWS CanNm p. 87, SWS CanSM p. 29, [SWS_ComM_00826], [SWS_ComM_00355].

Partial Network Cluster et mappage dynamique de PNC (Draft)

Principe de base : les PNC réveillent des groupes logiques d'ECU au lieu de bus entiers (SWS ComM p. 31). Une machine d'état propre existe pour chaque PNC ; les actions de PNC s'exécutent avant les actions de canal (SWS ComM p. 35). ComM_PncModeType décrit les modes [SWS_ComM_00673].

Affectation aux canaux :

  • Les PNC sont mappés sur les canaux via ComMChannelPerPnc [SWS_ComM_00913].
  • La position binaire d'un PNC est calculée selon [SWS_ComM_00825].
  • Pour les hôtes équipés d'un commutateur Ethernet, une restriction de configuration s'applique [SWS_ComM_CONSTR_00001].

Particularité de R20-11 : l'échange d'état s'effectue encore via des signaux Com (Com_SendSignal, rappel EIRA/ERA ComM_COMCbk_<sn>) [SWS_ComM_00164] [SWS_ComM_00959] [SWS_ComM_00819]. Ce n'est que R21-11 qui le remplace par des API dédiées (SWS ComM p. 2).

Diagramme d'état : machine d'état de PNC avec demande locale, ERA de passerelle et déclencheurs de réveil. Sources : SWS ComM p. 37, SWS ComM p. 34, SWS ComM p. 43, [SWS_ComM_00964], [SWS_ComM_00165], [SWS_ComM_01053].

Mappage dynamique PNC-vers-canal : cette fonctionnalité est nouvelle dans R20-11 et signalée comme Draft (SWS ComM p. 2).

  • Phase d'apprentissage : ComM_PnLearningRequest la démarre [SWS_ComM_91019] [SWS_ComM_01026]. Les passerelles retransmettent les demandes d'apprentissage [SWS_ComM_01028]. ComM_Nm_RepeatMessageLeftIndication termine la phase [SWS_ComM_01029].
  • Pendant la phase d'apprentissage, le ComM intègre les bits ERA reçus dans le mappage [SWS_ComM_01031] et transmet sa propre appartenance [SWS_ComM_01032] [SWS_ComM_01033].
  • API d'administration : ComM_GetPncToChannelMapping, ComM_UpdatePncToChannelMapping, ComM_ResetPncToChannelMapping et ComM_UpdatePncMembership [SWS_ComM_91013] [SWS_ComM_91015] [SWS_ComM_91017] [SWS_ComM_91021].

Différences entre versions :

  • Dans R20-11, ComM_GetPncToChannelMapping comporte les paramètres boolean* MappingTable et PncCnt. Les versions ultérieures utilisent un vecteur de bits uint8 avec PNCBitVectorLength (SWS ComM p. 122) ; [SWS_ComM_91013] fait foi ici.
  • Les exigences R20-11 mentionnent en divergence ComM_GetPncMappingTable [SWS_ComM_01034].
  • Dans R20-11, ComM_Nm_ForwardSynchronizedPncShutdown ne comporte que le paramètre Channel [SWS_ComM_91003]. Un vecteur de bits PNC s'y ajoute ultérieurement (SWS ComM p. 137).

Diagramme de séquence : phase d'apprentissage PNC, du démarrage à la sortie de Repeat Message en passant par la mise à jour du mappage. Sources : SWS ComM p. 56, SystemTemplate (Abb.) p. 329, [SWS_ComM_01026], [SWS_ComM_01029], [SWS_ComM_01031], [SWS_ComM_01035].

Restriction de communication et état d'inhibition persistant

État d'inhibition : il s'agit d'un champ de bits [SWS_ComM_00669] :

  • Bit 0 : inhibition de réveil,
  • Bit 1 : Limit to No Com.

ComMEcuGroupClassification agit comme un masque définissant quelles inhibitions sont autorisées à être exécutées. Il est configuré via ComM_SetECUGroupClassification [SWS_ComM_00552] (SWS ComM p. 73). L'état est stocké de manière non volatile et restauré au démarrage (SWS ComM p. 84).

API de commande :

  • ComM_LimitChannelToNoComMode [SWS_ComM_00163],
  • ComM_LimitECUToNoComMode [SWS_ComM_00124],
  • ComM_PreventWakeUp [SWS_ComM_00156],
  • ComM_GetInhibitionStatus pour la lecture [SWS_ComM_00619].

Les SW-C Mode Manager accèdent à ces fonctions via les interfaces ComM_ChannelLimitation, ComM_ChannelWakeup et ComM_ECUModeLimitation [SWS_ComM_00743] [SWS_ComM_00742] [SWS_ComM_00741] (SWS ComM (Abb.) p. 68).

Effet de la limitation :

  • Un canal activement demandé passe à Ready Sleep malgré des demandes d'utilisateurs existantes. Un canal maintenu réveillé passivement reste inchangé (SWS ComM p. 88).
  • Les demandes formulées pendant la limitation sont rejetées. Après sa levée, les utilisateurs doivent émettre une nouvelle demande (SWS ComM p. 91).
  • Si ComMResetAfterForcingNoComm est défini, le ComM déclenche une réinitialisation de l'ECU via le BswM [SWS_ComM_00355].
  • Un compteur d'inhibition comptabilise les demandes Full rejetées. ComM_ReadInhibitCounter le lit, ComM_ResetInhibitCounter le remet à zéro [SWS_ComM_00224] [SWS_ComM_00108]. Les deux n'existent qu'avec ComMModeLimitationEnabled et un bloc NvM configuré (SWS ComM p. 130).

Diagramme d'activité : chemin de décision lors de l'activation de « Limit to No Com » jusqu'à la réinitialisation optionnelle. Sources : SWS ComM p. 88, SWS ComM p. 84, [SWS_ComM_00163], [SWS_ComM_00110], [SWS_ComM_00355].

Comportement en cas d'erreur

Module non initialisé : sans initialisation, toutes les API hormis ComM_Init, ComM_GetVersionInfo et ComM_GetStatus n'exécutent aucune opération normale et renvoient E_NOT_OK [SWS_ComM_00612].

Erreurs de développement : les erreurs de développement sont COMM_E_UNINIT, COMM_E_WRONG_PARAMETERS, COMM_E_PARAM_POINTER et COMM_E_INIT_FAILED [SWS_ComM_00234].

Erreur de lecture NVRAM : si la lecture échoue, le ComM utilise les valeurs par défaut (SWS ComM p. 97). L'erreur d'exécution COMM_E_READ_NV_FAILED provient d'une version ultérieure et n'est pas normative pour R20-11 (SWS ComM p. 96).

Bus-Off : le CanSM signale COMM_SILENT_COMMUNICATION via ComM_BusSM_ModeIndication (EXP ErrorDescription p. 19). Le ComM transmet ce mode aux utilisateurs [SWS_ComM_00675].

Désinitialisation : ComM_DeInit ne peut signaler aucune erreur. L'appelant doit donc s'assurer au préalable que tous les canaux sont dans No Communication (SWS ComM p. 114).
