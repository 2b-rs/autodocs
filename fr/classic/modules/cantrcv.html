Commande les émetteurs-récepteurs CAN externes : modes de fonctionnement, détection de réveil et réveil sélectif via des trames de réveil.

CanTrcv commande des émetteurs-récepteurs CAN externes et les mappe sur un modèle de mode générique comprenant NORMAL, STANDBY et SLEEP. CanIf demande les changements de mode de manière asynchrone ; le pilote signale en retour les modes atteints via une indication [SWS_CanTrcv_00158]. De plus, il détecte les réveils, les signale à EcuM et prend en charge le réveil sélectif via des trames de réveil en présence d'un matériel approprié. Contrainte principale : SLEEP n'est accessible que depuis STANDBY [SWS_CanTrcv_00104], et aucun réveil ne doit être perdu pendant la désactivation des notifications.

Le CAN Transceiver Driver (CanTrcv) encapsule les émetteurs-récepteurs CAN externes derrière un modèle de mode générique. Ainsi, ComM et EcuM restent découplés du matériel concret (SWS CanTrcv p. 19). Il existe une instance de pilote pour chaque type de matériel d'émetteur-récepteur [SWS_CanTrcv_00016]. Le pilote est sollicité via CanIf et pilote le matériel via Dio et Spi, qui doivent être initialisés avant CanTrcv_Init [SWS_CanTrcv_00099]. Après l'initialisation, chaque émetteur-récepteur se trouve, selon la configuration de chaque canal, en STANDBY ou SLEEP [SWS_CanTrcv_00148]. CanTrcv_DeInit mène à NOT_ACTIVE [SWS_CanTrcv_91003].

CanTrcv_SetOpMode commute entre NORMAL, STANDBY et SLEEP [SWS_CanTrcv_00102]. SLEEP n'est autorisé que depuis STANDBY [SWS_CanTrcv_00104]. Un passage vers le mode actuel n'est pas une erreur [SWS_CanTrcv_00161]. La fonction opère de manière asynchrone : dès que le mode cible est atteint, CanTrcv le signale via CanIf_TrcvModeIndication [SWS_CanTrcv_00158].

Diagramme d'états : Init mène à STANDBY ou SLEEP, SLEEP n'est accessible que via STANDBY, DeInit mène à NOT_ACTIVE. Sources : SWS CanTrcv p. 19, [SWS_CanTrcv_00148]

CanIf vérifie les réveils via CanTrcv_CheckWakeup. Cette fonction signale les réveils détectés au moyen de EcuM_SetWakeupEvent [SWS_CanTrcv_00146]. CanTrcv_MainFunction scrute les bus en STANDBY et SLEEP [SWS_CanTrcv_00112]. CanTrcv_SetWakeupMode peut désactiver la notification, l'activer ou effacer les réveils mémorisés. Aucun réveil ne doit être perdu lors de cette opération [SWS_CanTrcv_00095].

Les émetteurs-récepteurs compatibles PN (CanTrcvHwPnSupport) réveillent en outre via des trames de réveil configurées [SWS_CanTrcv_00175]. Lors de l'arrêt, CanSM efface d'abord le drapeau WUF puis bascule vers STANDBY [SWS_CanTrcv_00194]. Ensuite, CanSM fait vérifier le drapeau de réveil de manière asynchrone [SWS_CanTrcv_00224].

En cas d'erreur :

  • Lorsque la DET est activée, les erreurs de développement sont signalées ; lorsque la DET est désactivée, les API renvoient E_NOT_OK [SWS_CanTrcv_00050].
  • Le pilote signale une communication matérielle perturbée en tant qu'erreur d'exécution CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006].
  • CanTrcv_MainFunctionDiagnostics signale les erreurs de bus en tant que CANTRCV_E_BUS_ERROR au DEM [SWS_CanTrcv_00206].

Diagramme de séquence : lors de l'arrêt PN, le drapeau WUF est effacé, l'émetteur-récepteur est commuté vers STANDBY et le drapeau de réveil est vérifié de manière asynchrone. Sources : SWS CanTrcv p. 55, [SWS_CanTrcv_00194]

Rôle : pilote pour émetteurs-récepteurs CAN externes sous CanIf

Le CAN Transceiver Driver (CanTrcv) pilote des composants d'émetteurs-récepteurs CAN externes. Il mappe leurs états matériels sur un modèle générique de modes de fonctionnement. Ce modèle vise à couvrir de manière homogène de nombreux émetteurs-récepteurs disponibles. D'après la spécification, il accepte pour cela de comporter un ou deux états en trop pour un composant donné, mais découple ainsi ComM et EcuM du matériel (SWS CanTrcv p. 19). Le matériel d'émetteur-récepteur doit pour cela offrir une interface pouvant être mappée sur ce modèle [SWS_CanTrcv_00098].

Vers le haut, CanIf est le partenaire direct :

  • CanIf_SetTrcvMode appelle CanTrcv_SetOpMode (SWS CanIf p. 95).
  • CanIf_GetTrcvMode appelle CanTrcv_GetOpMode (SWS CanIf p. 97).
  • CanIf_GetTrcvWakeupReason appelle CanTrcv_GetBusWuReason (SWS CanIf p. 98).

Les retours passent par CanIf_TrcvModeIndication, qui fait partie des interfaces obligatoires [SWS_CanTrcv_00085]. D'autres callbacks CanIf sont répertoriés pour les indications PN [SWS_CanTrcv_00086]. Vers le bas, CanTrcv utilise Dio et Spi pour le pilotage matériel ainsi que des types Icu, DEM et EcuM, comme le montre la liste des imports [SWS_CanTrcv_00084]. Le pilote réalise les temps d'attente lors des transitions d'état avec Tm_BusyWait1us16bit [SWS_CanTrcv_00230]. Le planificateur BSW appelle CanTrcv_MainFunction et CanTrcv_MainFunctionDiagnostics (SWS CanTrcv p. 47).

Diagramme de contexte : CanTrcv est exploité par CanIf, EcuM et le planificateur, et accède au matériel via Dio, Spi et Icu. Il signale les erreurs à DET et DEM. Sources : [SWS_CanTrcv_00084], [SWS_CanTrcv_00085], [SWS_CanTrcv_00146], SWS EcuM p. 35

Initialisation, cycle de vie et désinitialisation

Avant l'appel de CanTrcv_Init [SWS_CanTrcv_00001], l'environnement doit avoir initialisé tous les pilotes utilisés, en particulier Spi et Dio [SWS_CanTrcv_00099]. La référence documentaire ajoute deux contraintes temporelles : l'initialisation doit intervenir rapidement après la mise sous tension, et les services sous-jacents doivent être courts et synchrones (SWS CanTrcv p. 26).

CanTrcv_Init initialise tous les émetteurs-récepteurs connectés conformément à leurs séquences d'initialisation et à la configuration issue de ConfigPtr [SWS_CanTrcv_00180]. Le contenu de CanTrcv_ConfigType est spécifique au matériel [SWS_CanTrcv_00209]. Ensuite, chaque émetteur-récepteur se trouve en CANTRCV_TRCVMODE_SLEEP ou CANTRCV_TRCVMODE_STANDBY ; cela est configurable par émetteur-récepteur [SWS_CanTrcv_00148].

L'initialisation vérifie en même temps la présence de réveils :

  • Si le matériel le permet, CanTrcv_Init vérifie si une activité de l'émetteur-récepteur a déclenché le réveil. Elle signale le résultat au moyen de EcuM_SetWakeupEvent avec la source issue de CanTrcvWakeupSourceRef [SWS_CanTrcv_00167].
  • Pour les émetteurs-récepteurs compatibles PN, la séquence de configuration est en outre réexécutée si le drapeau POR ou SYSERR est positionné. Dans le cas contraire, la configuration stockée dans l'émetteur-récepteur reste valide [SWS_CanTrcv_00182].
  • Un drapeau POR positionné est par ailleurs signalé comme réveil via CanTrcvPorWakeupSourceRef [SWS_CanTrcv_00183].

La notification POR est adaptée aux émetteurs-récepteurs dotés d'une alimentation intégrée. Chez ces derniers, un réveil passif ressemble pour l'ECU à une réinitialisation à la mise sous tension (SWS EcuM p. 70).

Diagramme d'activité : l'initialisation vérifie l'accessibilité matérielle, traite POR/SYSERR, signale les réveils à EcuM et se termine pour chaque canal en STANDBY ou SLEEP. L'ordre des vérifications est une interprétation. Sources : [SWS_CanTrcv_00180], [SWS_CanTrcv_00182], [SWS_CanTrcv_00183], [SWS_CanTrcv_00167], [SWS_CanTrcv_00148]

CanTrcv_DeInit [SWS_CanTrcv_91001] place le matériel d'émetteur-récepteur dans l'état NOT_ACTIVE [SWS_CanTrcv_91003]. Dans cet état, il peut être configuré avec une nouvelle séquence de configuration (SWS CanTrcv p. 49). L'état initial attendu est CANTRCV_TRCVMODE_NORMAL ; sinon, la vérification des erreurs de développement signale CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005].

Modes de fonctionnement NORMAL, STANDBY et SLEEP

CanTrcv_TrcvModeType définit les trois modes [SWS_CanTrcv_00163]. CanTrcv_SetOpMode [SWS_CanTrcv_00002] commute l'état interne de l'émetteur-récepteur adressé sur l'un de ces modes [SWS_CanTrcv_00102]. Pour les transitions, les règles suivantes s'appliquent :

  • Depuis NORMAL, l'utilisateur ne demande que STANDBY ou NORMAL [SWS_CanTrcv_00103].
  • Depuis STANDBY, il ne demande que SLEEP ou STANDBY [SWS_CanTrcv_00104].
  • D'après le schéma, NORMAL est accessible depuis l'ensemble des trois modes (SWS CanTrcv p. 19).
  • Un passage vers le mode actuel est autorisé et ne constitue pas une erreur [SWS_CanTrcv_00161].
  • Si le matériel ne prend pas en charge le mode demandé, la fonction renvoie E_NOT_OK [SWS_CanTrcv_00105].

Diagramme d'états : après Init, l'émetteur-récepteur se trouve en STANDBY ou SLEEP. SLEEP n'est accessible que via STANDBY, NORMAL depuis tous les modes. DeInit mène à NOT_ACTIVE. Sources : SWS CanTrcv p. 19, [SWS_CanTrcv_00148], [SWS_CanTrcv_00103], [SWS_CanTrcv_00104], [SWS_CanTrcv_91003]

CanTrcv_SetOpMode opère de manière asynchrone : E_OK signifie seulement que la demande a été acceptée (SWS CanTrcv p. 33). Ce n'est qu'une fois le mode cible atteint que CanTrcv appelle CanIf_TrcvModeIndication avec le TransceiverId abstrait de CanIf [SWS_CanTrcv_00158]. CanSM ignore une telle notification pour SLEEP, car SLEEP n'est demandé que par le code d'intégration (SWS CanSM p. 94).

Sur le matériel compatible PN, CanTrcv_SetOpMode vérifie en plus les drapeaux POR et SYSERR [SWS_CanTrcv_00186]. Après un POR, il réinitialise l'émetteur-récepteur [SWS_CanTrcv_00187]. CanTrcv_GetOpMode [SWS_CanTrcv_00005] renvoie de manière synchrone l'état actuel [SWS_CanTrcv_00106].

Diagramme de séquence : un changement de mode est accepté de manière synchrone et confirmé plus tard par une indication via CanIf à CanSM. Sources : SWS CanTrcv p. 52, [SWS_CanTrcv_00158], [SWS_CanTrcv_00186]

Réveil : détection, cause et commande des notifications

Un réveil est détecté par interruption ou par scrutation (SWS EcuM p. 179). CanIf interroge pour cela la fonction CanTrcv_CheckWakeup [SWS_CanTrcv_00143] via CanIf_CheckWakeup (SWS CanIf p. 56). Si le matériel le permet, cette fonction valide un réveil par une activité de l'émetteur-récepteur et le signale au moyen de EcuM_SetWakeupEvent [SWS_CanTrcv_00146].

CanTrcv_MainFunction [SWS_CanTrcv_00013] scrute tous les bus en STANDBY et SLEEP à la recherche de réveils et positionne un drapeau de réveil [SWS_CanTrcv_00112]. Elle est vraisemblablement pertinente avant tout dans le cas d'une configuration par scrutation ; le schéma de configuration prévoit à cet effet la valeur CanTrcvWakeUpByPolling (ECUC-Parameter p. 185).

CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] renvoie la cause de réveil détectée par l'émetteur-récepteur [SWS_CanTrcv_00107]. Les valeurs possibles sont par exemple CANTRCV_WU_BY_BUS, CANTRCV_WU_INTERNALLY ou CANTRCV_WU_RESET [SWS_CanTrcv_00165]. La précision avec laquelle les causes peuvent être distinguées dépend fortement du matériel (SWS CanTrcv p. 35).

Pour les interruptions de réveil, le pilote utilise des canaux ICU. Il n'appelle Icu_EnableNotification et Icu_DisableNotification que si CanTrcvIcuChannelRef est configuré [SWS_CanTrcv_00171]. Lors du passage à STANDBY, il active les canaux [SWS_CanTrcv_00172]. La référence documentaire issue de R24-11 mentionne en outre la désactivation lors du passage à NORMAL (SWS CanTrcv p. 23).

Diagramme de séquence : un réveil est vérifié auprès de l'émetteur-récepteur par interruption ou scrutation via CanIf, signalé à EcuM et interrogé ultérieurement quant à sa cause. Sources : SWS EcuM p. 179, SWS EcuM p. 138, SWS EcuM p. 140, [SWS_CanTrcv_00146], [SWS_CanTrcv_00112]

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] commande la notification de réveil via CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164] :

  • CANTRCV_WUMODE_DISABLE : les réveils ne sont pas signalés, mais sont enregistrés en interne [SWS_CanTrcv_00093].
  • CANTRCV_WUMODE_ENABLE : un réveil enregistré est signalé comme « present » [SWS_CanTrcv_00111].
  • CANTRCV_WUMODE_CLEAR : un réveil enregistré est effacé [SWS_CanTrcv_00094].

Aucun réveil ne doit être perdu pendant la phase de désactivation [SWS_CanTrcv_00095]. L'effacement sert à rejeter les réveils mémorisés lorsque la notification est désactivée, sous le contrôle de la couche supérieure [SWS_CanTrcv_00150]. CanIf transmet la demande à CanTrcv via CanIf_SetTrcvWakeupMode (SWS CanIf p. 100).

Réveil sélectif (Partial Networking)

Avec le Partial Networking, les nœuds restent en mode basse consommation jusqu'à ce que des trames de réveil prédéfinies (WUF) les réveillent. Les émetteurs-récepteurs compatibles PN ne réagissent donc pas seulement au motif de réveil (WUP), mais aussi à ces trames (SWS CanTrcv p. 27). CanTrcvHwPnSupport indique si le matériel en est capable [SWS_CanTrcv_00174]. C'est uniquement lorsque ce paramètre est TRUE qu'existent le conteneur CanTrcvPartialNetwork et cinq API : CanTrcv_GetTrcvSystemData, CanTrcv_ClearTrcvWufFlag, CanTrcv_ReadTrcvTimeoutFlag, CanTrcv_ClearTrcvTimeoutFlag et CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00175].

CanTrcvPnFrameCanId, CanTrcvPnFrameCanIdMask et CanTrcvPnFrameDataMask définissent les trames auxquelles l'émetteur-récepteur réagit [SWS_CanTrcv_00177]. CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] active la fonction de réveil PN avec PN_ENABLED [SWS_CanTrcv_00221] et la désactive avec PN_DISABLED [SWS_CanTrcv_00222].

Le déroulement de l'arrêt est central :

  1. CanSM efface le drapeau WUF via CanTrcv_ClearTrcvWufFlag afin qu'aucun réveil par trame ne soit perdu lors de l'entrée en mode basse consommation. Ensuite, l'émetteur-récepteur passe en STANDBY [SWS_CanTrcv_00194].
  2. CanTrcv confirme l'effacement par CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195].
  3. Enfin, CanSM demande la vérification asynchrone CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223]. CanTrcv signale le résultat au moyen de CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224].

Pour le raccordement SPI, la spécification décrit une variante asynchrone (SWS CanTrcv p. 55) et une variante synchrone (SWS CanTrcv p. 57).

Diagramme de séquence : lors de l'arrêt PN, le drapeau WUF est effacé, l'émetteur-récepteur est commuté vers STANDBY et le drapeau de réveil est vérifié de manière asynchrone après la mise en veille du contrôleur. Sources : SWS CanTrcv p. 55, SWS CanTrcv p. 56, SWS CanSM p. 36, [SWS_CanTrcv_00194], [SWS_CanTrcv_00224]

Pour le diagnostic, CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] lit la configuration et l'état de l'émetteur-récepteur en tant que uint32 [SWS_CanTrcv_00189]. Les drapeaux de timeout et de silence sont lus ou effacés via CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215], CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216] et CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217]. CanTrcv_TrcvFlagStateType indique leur état [SWS_CanTrcv_00211].

Configuration et référence d'instance

Il existe pour chaque type de matériel d'émetteur-récepteur une instance de pilote qui dessert tous les composants de ce type [SWS_CanTrcv_00016]. Le schéma CanIf montre le cas de contrôleurs identiques dotés de types d'émetteurs-récepteurs différents, ce qui nécessite alors deux pilotes d'émetteur-récepteur (SWS CanIf p. 34). Un conteneur CanTrcvChannel (multiplicité 1..*) décrit chaque canal. Il contient entre autres CanTrcvHwPnSupport, CanTrcvInitState, CanTrcvWakeupByBusUsed ainsi que les références de source de réveil (SWS CanTrcv p. 70).

Une différence entre les sources concerne l'état après Init. Le schéma de configuration mentionne CanTrcvOpModeNormal comme valeur par défaut de CanTrcvInitState (ECUC-Parameter p. 187). La référence normative pour R20-11 est toutefois [SWS_CanTrcv_00148], qui ne prévoit après Init que SLEEP ou STANDBY. Le pilote doit rejeter les configurations présentant des assignations de partition non prises en charge [SWS_CanTrcv_00231].

Comportement en cas d'erreur

Les erreurs de développement issues de [SWS_CanTrcv_00050] suivent un modèle uniforme. Lorsque la DET est activée, les API signalent :

  • CANTRCV_E_UNINIT en cas d'appel avant Init, par exemple [SWS_CanTrcv_00122] et [SWS_CanTrcv_00124] ;
  • CANTRCV_E_INVALID_TRANSCEIVER en cas d'ID non valide, par exemple [SWS_CanTrcv_00123] et [SWS_CanTrcv_00129] ;
  • CANTRCV_E_PARAM_POINTER en cas de pointeurs NULL, par exemple [SWS_CanTrcv_00132] et [SWS_CanTrcv_00133] ;
  • CANTRCV_E_TRCV_NOT_NORMAL ou CANTRCV_E_TRCV_NOT_STANDBY en cas de transitions non autorisées [SWS_CanTrcv_00120] [SWS_CanTrcv_00121] ;
  • Erreur de paramètre en cas de mode non valide [SWS_CanTrcv_00087] ou de mode de réveil non valide [SWS_CanTrcv_00089].

Si la DET est désactivée, les API renvoient E_NOT_OK dans ces cas.

Si la communication avec le transceiver est perturbée, le pilote signale l'erreur d'exécution CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006] via Det_ReportRuntimeError [SWS_CanTrcv_00085]. Cela s'applique par exemple dans Init [SWS_CanTrcv_00113], SetOpMode [SWS_CanTrcv_00114], GetOpMode [SWS_CanTrcv_00115], SetWakeupMode [SWS_CanTrcv_00117], GetTrcvSystemData [SWS_CanTrcv_00190] et ClearTrcvWufFlag [SWS_CanTrcv_00196]. CanTrcv_GetBusWuReason constitue une exception : dans ce cas, selon [SWS_CanTrcv_00116], elle retourne E_OK. Init signale un débit binaire non pris en charge sous la forme CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168].

Diagramme d'activité : les appels d'API traversent des contrôles d'erreurs de développement, puis l'accès matériel avec traitement des erreurs d'exécution. L'ordre de contrôle est une interprétation. Sources : [SWS_CanTrcv_00050], [SWS_CanTrcv_00122], [SWS_CanTrcv_00123], [SWS_CanTrcv_00132], [SWS_CanTrcv_00114], [SWS_CanTrcv_00116]

Les erreurs de bus sont traitées comme des erreurs de production. La condition préalable est que le matériel puisse distinguer les erreurs de bus d'autres erreurs [SWS_CanTrcv_00178] et que CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. Ensuite, CanTrcv_MainFunctionDiagnostics [SWS_CanTrcv_00218] lit cycliquement le drapeau BUSERR. Elle signale CANTRCV_E_BUS_ERROR en tant que DEM_EVENT_STATUS_FAILED [SWS_CanTrcv_00206] ou DEM_EVENT_STATUS_PASSED [SWS_CanTrcv_00227] à DEM [SWS_CanTrcv_00228] [SWS_CanTrcv_00229]. L'événement DEM est référencé via CanTrcvDemEventParameterRefs (SWS CanTrcv p. 78).
