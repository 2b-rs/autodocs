Rôle du pilote entre CanIf et le matériel transceiver

Le pilote de transceiver CAN encapsule le composant physique de commande de bus d'un canal CAN. Il commute les modes de fonctionnement du composant, détecte les événements de réveil et lit les données d'état et de diagnostic. Son modèle d'état générique vise à couvrir le plus grand nombre possible de transceivers disponibles et à découpler ComM ainsi qu'EcuM du matériel concret (SWS CanTrcv p. 19). Pour cela, le matériel doit fournir une interface pouvant être mise en correspondance avec ce modèle [SWS_CanTrcv_00098]. Dans le schéma fonctionnel de la pile CAN, le chemin de commande vers le transceiver est séparé du chemin de données passant par le contrôleur CAN et le pilote CAN (SWS CanTrcv p. 9).

Le partenaire vers le haut est CanIf. CanIf_SetTrcvMode appelle CanTrcv_SetOpMode (SWS CanIf p. 95), CanIf_GetTrcvMode appelle CanTrcv_GetOpMode (SWS CanIf p. 97), et CanIf_SetTrcvWakeupMode appelle CanTrcv_SetWakeupMode (SWS CanIf p. 92). Les retours sont transmis à CanIf via des callbacks. Pour cela, CanTrcv requiert obligatoirement CanIf_TrcvModeIndication et Det_ReportRuntimeError [SWS_CanTrcv_00085]. CanIf_CheckTrcvWakeFlagIndication et CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00086] sont entre autres optionnels. Vers le bas, le pilote commande le matériel via Dio et Spi (SWS CanTrcv p. 26). Il importe des types depuis DEM, Dio, EcuM, Icu et Spi [SWS_CanTrcv_00084].

Diagramme de contexte : CanTrcv est sollicité par CanIf, commande le matériel via Dio/Spi et notifie CanIf, EcuM, DEM et DET. Sources : [SWS_CanTrcv_00085], [SWS_CanTrcv_00084], SWS CanTrcv p. 52.

Cycle de vie : de NOT_ACTIVE à CanTrcv_DeInit en passant par CanTrcv_Init

Avant que CanTrcv_Init [SWS_CanTrcv_00001] ne soit appelé, l'environnement doit avoir initialisé tous les pilotes BSW utilisés par le pilote [SWS_CanTrcv_00099]. La spécification justifie cela par des exigences temporelles, telles que la lecture précoce du matériel après la mise sous tension (SWS CanTrcv p. 26). Init initialise tous les transceivers connectés à l'aide de leurs séquences d'initialisation et de la configuration issue de ConfigPtr [SWS_CanTrcv_00180]. Cette configuration a le type CanTrcv_ConfigType [SWS_CanTrcv_00209]. Selon la configuration, Init place chaque transceiver dans CANTRCV_TRCVMODE_SLEEP ou CANTRCV_TRCVMODE_STANDBY [SWS_CanTrcv_00148]. Si Init détecte un réveil dû à l'activité du transceiver, il le signale à EcuM_SetWakeupEvent [SWS_CanTrcv_00167] avec la source issue de CanTrcvWakeupSourceRef.

Différence entre les sources : le diagramme de configuration du conteneur CanTrcvChannel indique également CANTRCV_OP_MODE_NORMAL pour CanTrcvInitState, et ce comme valeur par défaut (SWS CanTrcv p. 54). [SWS_CanTrcv_00148], qui ne mentionne que SLEEP ou STANDBY comme état cible, reste déterminant pour R20-11.

CanTrcv_DeInit [SWS_CanTrcv_91001] fait passer le matériel à l'état NOT_ACTIVE [SWS_CanTrcv_91003]. Dans cet état, il peut être reconfiguré à l'aide d'une nouvelle séquence de configuration (SWS CanTrcv p. 49). Si la détection d'erreurs de développement est active et que le transceiver ne se trouve pas dans CANTRCV_TRCVMODE_NORMAL, DeInit signale CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005]. DeInit est donc attendu depuis NORMAL.

Diagramme d'état : selon la configuration, Init mène de NOT_ACTIVE vers SLEEP ou STANDBY. L'abaissement s'effectue par étapes (NORMAL → STANDBY → SLEEP), NORMAL est accessible depuis chaque mode, DeInit ramène vers NOT_ACTIVE. Sources : [SWS_CanTrcv_00148], [SWS_CanTrcv_00103], [SWS_CanTrcv_00104], [SWS_CanTrcv_91003], SWS CanTrcv p. 19

Commuter les modes de fonctionnement NORMAL, STANDBY et SLEEP

CanTrcv_SetOpMode [SWS_CanTrcv_00002] fonctionne de manière asynchrone. E_OK signifie seulement que la demande a été acceptée (SWS CanTrcv p. 33). Le pilote commute l'état interne sur NORMAL, STANDBY ou SLEEP [SWS_CanTrcv_00102]. Une fois le mode atteint, il appelle CanIf_TrcvModeIndication avec le CanIf-TransceiverId abstrait [SWS_CanTrcv_00158]. Il réalise les temps d'attente lors des changements d'état avec Tm_BusyWait1us16bit [SWS_CanTrcv_00230].

Les règles suivantes s'appliquent à l'ordre des modes :

  • Depuis NORMAL, l'utilisateur ne peut demander que STANDBY ou NORMAL [SWS_CanTrcv_00103].
  • Depuis STANDBY, il ne peut demander que SLEEP ou STANDBY [SWS_CanTrcv_00104].
  • Selon la légende du diagramme d'état, NORMAL peut être demandé depuis les trois modes (SWS CanTrcv p. 19).
  • Une demande du mode actuel est autorisée et ne constitue pas une erreur [SWS_CanTrcv_00161].
  • Si le matériel ne prend pas en charge le mode demandé, l'appel renvoie E_NOT_OK [SWS_CanTrcv_00105].

CanIf ne vérifie pas lui-même cet ordre (SWS CanIf p. 88). Selon la spécification CanSM, seul le code d'intégration demande SLEEP, pas CanSM (SWS CanSM p. 94). CanTrcv_GetOpMode [SWS_CanTrcv_00005] fournit l'état actuel de manière synchrone dans OpMode [SWS_CanTrcv_00106], typé comme CanTrcv_TrcvModeType [SWS_CanTrcv_00163].

Diagramme de séquence : le changement de mode est accepté de manière synchrone et confirmé de manière asynchrone par indication. Sources : [SWS_CanTrcv_00002], [SWS_CanTrcv_00158], [SWS_CanTrcv_00230], SWS CanTrcv p. 56

Détecter, mettre en mémoire tampon et signaler les événements de réveil

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] contrôle si les événements de réveil sont relayés. Le paramètre a le type CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164] :

  • CANTRCV_WUMODE_ENABLE signale un événement enregistré comme « present » [SWS_CanTrcv_00111].
  • CANTRCV_WUMODE_DISABLE bloque le signalement. Le transceiver et le pilote continuent de détecter et d'enregistrer les événements en interne [SWS_CanTrcv_00093].
  • CANTRCV_WUMODE_CLEAR supprime les événements enregistrés [SWS_CanTrcv_00094]. Ce mode est conçu pour la phase de signalement bloqué [SWS_CanTrcv_00150].

Pendant le blocage, aucun événement ne doit être perdu [SWS_CanTrcv_00095].

Diagramme d'activité : SetWakeupMode bifurque vers ENABLE, DISABLE et CLEAR après la vérification des paramètres. Sources : [SWS_CanTrcv_00111], [SWS_CanTrcv_00093], [SWS_CanTrcv_00094], [SWS_CanTrcv_00117], SWS CanTrcv p. 37

Les réveils sont détectés de deux manières :

  • CanTrcv_MainFunction [SWS_CanTrcv_00013] échantillonne cycliquement tous les bus en STANDBY et SLEEP et positionne un drapeau d'événement de réveil [SWS_CanTrcv_00112].
  • CanIf appelle CanTrcv_CheckWakeup [SWS_CanTrcv_00143] lors d'une interruption de réveil. Dans la mesure où le matériel le prend en charge, la fonction vérifie si le transceiver en était la cause et le signale avec CanTrcvWakeupSourceRef à EcuM_SetWakeupEvent [SWS_CanTrcv_00146].

Le point d'entrée de la deuxième voie est constitué par CanIf_CheckWakeup, que le code d'intégration appelle dans le cadre de EcuM_CheckWakeup (SWS CanIf p. 56, SWS EcuM p. 163). Interprétation : l'échantillonnage cyclique devrait compléter la voie pilotée par interruption pour les cas où aucune interruption de réveil n'est disponible.

Si CanTrcvIcuChannelRef est configuré, CanTrcv commute la notification de réveil via Icu_EnableNotification et Icu_DisableNotification [SWS_CanTrcv_00171]. Lors de la transition vers STANDBY, il active les canaux ICU [SWS_CanTrcv_00172]. Une version ultérieure les désactive en outre lors de la transition vers NORMAL (SWS CanTrcv p. 22).

CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] [SWS_CanTrcv_00107] fournit la cause d'un réveil, par exemple CANTRCV_WU_BY_BUS, CANTRCV_WU_INTERNALLY, CANTRCV_WU_RESET ou CANTRCV_WU_NOT_SUPPORTED [SWS_CanTrcv_00165]. La précision avec laquelle les causes peuvent être distinguées dépend fortement du matériel (SWS CanTrcv p. 35).

Diagramme de séquence : une interruption matérielle mène, via EcuM, le code d'intégration et CanIf, à CanTrcv_CheckWakeup et, le cas échéant, à EcuM_SetWakeupEvent. Sources : [SWS_CanTrcv_00143], [SWS_CanTrcv_00146], SWS EcuM p. 176, SWS EcuM p. 163

Réveil sélectif (Partial Networking) et drapeaux du transceiver

Les transceivers avec réveil sélectif ne se réveillent pas seulement sur le Wake-up Pattern, mais également sur des Wake-up Frames, en abrégé WUF (SWS CanTrcv p. 27). CanTrcvHwPnSupport indique si le matériel en est capable [SWS_CanTrcv_00174]. Le conteneur CanTrcvPartialNetwork ainsi que les API de drapeaux et de données système n'existent que si ce paramètre est défini [SWS_CanTrcv_00175]. CanTrcvPnFrameCanId, CanTrcvPnFrameCanIdMask et CanTrcvPnFrameDataMask définissent quelle trame de réveil est acceptée [SWS_CanTrcv_00177]. CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] active ou désactive la fonction PN avec PN_ENABLED ou PN_DISABLED [SWS_CanTrcv_00210] [SWS_CanTrcv_00221] [SWS_CanTrcv_00222].

Lors de l'arrêt, CanSM utilise CanTrcv_ClearTrcvWufFlag [SWS_CanTrcv_00214] afin qu'aucun réveil par trame ne soit perdu lors du passage dans un mode basse consommation. Ensuite, le transceiver doit passer à STANDBY [SWS_CanTrcv_00194]. CanTrcv signale que le drapeau est effacé via CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195]. L'appel asynchrone CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223] confirme sa vérification via CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224]. CanSM répète la demande d'effacement du WUF à l'état S_PN_CLEAR_WUF (SWS CanSM p. 37).

D'autres fonctions sont disponibles pour le diagnostic et la surveillance PN :

  • CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215], CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216] et CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217] utilisent CanTrcv_TrcvFlagStateType [SWS_CanTrcv_00211].
  • CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] fournit la configuration et l'état bruts sous forme de uint32 [SWS_CanTrcv_00189].

Les drapeaux POR et SYSERR sont vérifiés à deux endroits :

  • Sur le matériel compatible PN, CanTrcv_SetOpMode vérifie les deux drapeaux [SWS_CanTrcv_00186]. Si POR est défini, la séquence de configuration est à nouveau exécutée [SWS_CanTrcv_00187].
  • Lors de l'initialisation, la fonction de réveil sélectif est reconfigurée dès que POR ou SYSERR est défini [SWS_CanTrcv_00182].

Un POR défini est en outre signalé via EcuM_SetWakeupEvent avec la source issue de CanTrcvPorWakeupSourceRef [SWS_CanTrcv_00183].

Diagramme de séquence : lors de l'arrêt PN, l'effacement du WUF, STANDBY et la vérification du drapeau de réveil se succèdent, chacun avec une confirmation par indication. Sources : [SWS_CanTrcv_00194], [SWS_CanTrcv_00195], [SWS_CanTrcv_00224], SWS CanTrcv p. 57, SWS CanTrcv p. 53

Configuration par canal de transceiver et instanciation

Pour chaque type de matériel de transceiver, un calculateur possède une instance de pilote. Celle-ci dessert tous les composants de ce type [SWS_CanTrcv_00016], adressés via le paramètre uint8 Transceiver. Chaque canal est décrit dans un conteneur CanTrcvChannel (multiplicité 1..*). Il contient entre autres CanTrcvChannelId, CanTrcvInitState, CanTrcvWakeupByBusUsed, CanTrcvHwPnSupport, CanTrcvIcuChannelRef ainsi que les références aux sources de réveil pour Wakeup, POR et SYSERR (SWS CanTrcv p. 67). L'accès matériel est configuré via des références à des canaux Dio ou des séquences Spi (SWS CanTrcv p. 78).

Le pilote doit rejeter les affectations de partition qu'une implémentation ne prend pas en charge [SWS_CanTrcv_00231]. Si le matériel peut distinguer les erreurs de bus d'autres erreurs matérielles, cela est indiqué par CanTrcvBusErrFlag [SWS_CanTrcv_00178]. Les informations de version sont fournies par CanTrcv_GetVersionInfo [SWS_CanTrcv_00008].

Comportement en cas d'erreur

Les erreurs sont classifiées selon le schéma BSW général (SWS CanTrcv p. 23). Sont notamment définies comme erreurs de développement CANTRCV_E_INVALID_TRANSCEIVER (1), CANTRCV_E_PARAM_POINTER (2), CANTRCV_E_UNINIT (11), CANTRCV_E_TRCV_NOT_STANDBY (21), CANTRCV_E_TRCV_NOT_NORMAL (22) et CANTRCV_E_PARAM_TRCV_WAKEUP_MODE (23) [SWS_CanTrcv_00050]. Tous les contrôles suivent le même modèle : si la DET est active, l'erreur est signalée ; si la DET est désactivée, la fonction renvoie E_NOT_OK. Des exemples en sont [SWS_CanTrcv_00122], [SWS_CanTrcv_00123] et [SWS_CanTrcv_00132]. S'appliquent en particulier à CanTrcv_SetOpMode :

  • Un OpMode non valide entraîne CANTRCV_E_PARAM_TRCV_OPMODE [SWS_CanTrcv_00087].
  • Des séquences de modes non autorisées entraînent CANTRCV_E_TRCV_NOT_NORMAL ou CANTRCV_E_TRCV_NOT_STANDBY [SWS_CanTrcv_00120] [SWS_CanTrcv_00121].

Pour CanTrcv_Init, un débit en bauds non pris en charge signale CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168].

Diagramme d'activité : le diagramme montre les chemins de contrôle et d'erreur de CanTrcv_SetOpMode jusqu'à l'acceptation de la demande. L'ordre des contrôles n'est pas défini dans les sources et n'est organisé ici que par souci de clarté. Sources : [SWS_CanTrcv_00122], [SWS_CanTrcv_00123], [SWS_CanTrcv_00087], [SWS_CanTrcv_00120], [SWS_CanTrcv_00121], [SWS_CanTrcv_00105], [SWS_CanTrcv_00186], [SWS_CanTrcv_00114]

Si la communication avec le transceiver est absente ou défaillante, le pilote signale l'erreur d'exécution CANTRCV_E_NO_TRCV_CONTROL (26) [SWS_CanTrcv_91006]. Cela s'applique à Init [SWS_CanTrcv_00113], SetOpMode [SWS_CanTrcv_00114], GetOpMode [SWS_CanTrcv_00115], SetWakeupMode [SWS_CanTrcv_00117], GetTrcvSystemData [SWS_CanTrcv_00190] et ClearTrcvWufFlag [SWS_CanTrcv_00196]. Ces fonctions renvoient alors E_NOT_OK. En revanche, CanTrcv_GetBusWuReason renvoie dans ce cas E_OK [SWS_CanTrcv_00116]. Interprétation : la valeur de retour n'indique donc probablement aucune cause valide ici. En cas d'erreur, le type prévoit la valeur CANTRCV_WU_ERROR [SWS_CanTrcv_00165].

CANTRCV_E_BUS_ERROR est défini comme Extended Production Error [SWS_CanTrcv_00228]. Il est détecté lorsque le drapeau BUSERR est positionné et que la fonction est configurée et prise en charge par le matériel [SWS_CanTrcv_00229]. La fonction cyclique CanTrcv_MainFunctionDiagnostics [SWS_CanTrcv_00218] n'existe que pour CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. Elle signale via Dem_SetEventStatus FAILED [SWS_CanTrcv_00206] ou PASSED [SWS_CanTrcv_00227]. L'événement associé est référencé via CanTrcvDemEventParameterRefs (SWS CanTrcv p. 78).

Diagramme d'activité : selon l'état du drapeau BUSERR, la fonction de diagnostic signale FAILED ou PASSED à DEM. Sources : [SWS_CanTrcv_00205], [SWS_CanTrcv_00206], [SWS_CanTrcv_00227], SWS CanTrcv p. 48

Utilisation

La fonction CanTrcv_SetOpMode définit l’état interne du transceiver spécifié sur le mode de fonctionnement OpMode ([SWS_CanTrcv_00002], [SWS_CanTrcv_00102]). Les modes cibles possibles sont CANTRCV_TRCVMODE_NORMAL, CANTRCV_TRCVMODE_STANDBY et CANTRCV_TRCVMODE_SLEEP ([SWS_CanTrcv_00102]). L’appel se comporte de manière asynchrone ([SWS_CanTrcv_00002]). Comme valeur de retour, E_OK signale que la demande de changement de mode a été acceptée, tandis que E_NOT_OK est renvoyé si la demande a été rejetée, qu’un paramètre n’est pas valide ou que le mode demandé n’est pas pris en charge côté matériel ([SWS_CanTrcv_00002], [SWS_CanTrcv_00105]).

Transitions d’état et restrictions

Pour le passage entre les modes de fonctionnement, les règles de transition suivantes s’appliquent :

  • Si le transceiver se trouve dans le mode CANTRCV_TRCVMODE_NORMAL, l’appelant ne peut demander que CANTRCV_TRCVMODE_STANDBY ou CANTRCV_TRCVMODE_NORMAL ([SWS_CanTrcv_00103]).
  • Si le transceiver se trouve dans le mode CANTRCV_TRCVMODE_STANDBY, l’appelant ne peut demander que CANTRCV_TRCVMODE_SLEEP ou CANTRCV_TRCVMODE_STANDBY ([SWS_CanTrcv_00104]).

La fonction est réentrante pour des transceivers différents ([SWS_CanTrcv_00002]). Si le Selective Wakeup est pris en charge par le matériel, CanTrcv_SetOpMode vérifie les drapeaux POR et SYSERR de l’état du transceiver ([SWS_CanTrcv_00186]).

Gestion des erreurs

Si la détection de développement (DET) est active, CanTrcv_SetOpMode signale les erreurs de développement correspondantes (dans le cas contraire, E_NOT_OK est renvoyé) :

  • CANTRCV_E_UNINIT : appel avant l’initialisation du module CanTrcv ([SWS_CanTrcv_00122]).
  • CANTRCV_E_INVALID_TRANSCEIVER : appel avec un numéro de transceiver non valide ([SWS_CanTrcv_00123]).
  • CANTRCV_E_PARAM_TRCV_OPMODE : valeur de paramètre non valide pour OpMode ([SWS_CanTrcv_00087]).
