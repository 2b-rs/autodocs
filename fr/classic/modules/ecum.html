Commande le démarrage, l'arrêt, les phases de veille et les sources de réveil du calculateur en interaction avec le BswM.

L'ECU State Manager contrôle le cycle de vie d'un calculateur Classic. Il initialise le logiciel de base jusqu'au démarrage de l'OS, conduit l'ECU vers les cibles d'arrêt SLEEP, RESET ou OFF et gère les sources de réveil ainsi que leur validation [SWS_EcuM_04136]. L'Integration Code prend en charge les étapes proches du matériel via des callouts. L'EcuM arbitre les demandes RUN et POST_RUN des utilisateurs, mais le BswM décide des transitions d'état et les notifie en retour par EcuM_SetState [SWS_EcuM_04116]. La contrainte la plus importante est qu'aucun événement de réveil ne doit être perdu durant la phase SLEEP.

L'ECU State Manager (EcuM) est responsable dans la Classic Platform du démarrage, de l'arrêt et des phases de veille du calculateur. EcuM_Init exécute la séquence StartPreOS avec les blocs d'initialisation 0 et 1. Ce faisant, l'EcuM sélectionne et vérifie la configuration post-build, puis appelle finalement StartOS. Ensuite, EcuM_StartupTwo démarre le SchM et le BswM [SWS_EcuM_02684] [SWS_EcuM_02906] [SWS_EcuM_02932]. L'Integration Code fournit les étapes proches du matériel sous forme de callouts, par exemple EcuM_AL_DriverInitZero [SWS_EcuM_02905].

Diagramme d'états : l'ECU traverse STARTUP, UP, SHUTDOWN et SLEEP. Depuis SLEEP, elle retourne vers UP via WakeupRestart. Sources : RS ModeManagement p. 15, [SWS_EcuM_91005], [SWS_EcuM_02963]

L'EcuM ne décide pas lui-même des transitions d'état. Il collecte les demandes RUN et POST_RUN des utilisateurs configurés et transmet le résultat au BswM. Il prend en charge les changements d'état de ce dernier via EcuM_SetState et les relaie à la RTE [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04116] SWS EcuM p. 103. EcuM_SelectShutdownTarget mémorise la cible SLEEP, RESET ou OFF uniquement pour plus tard [SWS_EcuM_02585]. Lors de l'arrêt, OffPreOS désinitialise le BswM et le SchM, vérifie les événements de réveil et termine l'OS. Le hook de shutdown appelle ensuite EcuM_Shutdown, qui se termine par EcuM_AL_Reset ou EcuM_AL_SwitchOff [SWS_EcuM_03021] [SWS_EcuM_04074] [SWS_EcuM_04075].

La phase SLEEP débute par EcuM_GoDownHaltPoll. En premier lieu, GoSleep active les sources de réveil du mode veille. Ensuite suit soit Halt avec vérification du hash de la RAM, soit Poll avec une boucle sur EcuM_SleepActivity et EcuM_CheckWakeup. L'étape finale est constituée par WakeupRestart avec EcuM_AL_DriverRestart [SWS_EcuM_91002] [SWS_EcuM_02389] [SWS_EcuM_02863] [SWS_EcuM_03020] [SWS_EcuM_02963]. Durant cette phase, aucun événement de réveil ne doit être perdu [SWS_EcuM_02188].

Les sources de réveil sont des bits individuels dans EcuM_WakeupSourceType et possèdent chacune l'un des états NONE, PENDING, VALIDATED ou EXPIRED [SWS_EcuM_04040] [SWS_EcuM_04091]. Les pilotes signalent les événements avec EcuM_SetWakeupEvent. Si une validation est configurée, l'EcuM démarre un timeout. Seul un EcuM_ValidateWakeupEvent avant son expiration mène à VALIDATED ; en cas de référence de canal configurée, ComM est alors également informé. Dans le cas contraire, la source devient EXPIRED [SWS_EcuM_02709] [SWS_EcuM_02645] [SWS_EcuM_04082].

Diagramme d'activité : un événement de réveil est validé immédiatement ou reste PENDING jusqu'à ce qu'une confirmation arrive ou que le timeout expire. Sources : SWS EcuM p. 63, [SWS_EcuM_02566], [SWS_EcuM_04082]

En cas d'erreur, l'EcuM appelle le callout EcuM_ErrorHook si la configuration est incohérente ou si la vérification de la RAM échoue [SWS_EcuM_04033] [SWS_EcuM_91003]. Il signale à DET les erreurs de développement telles que les demandes multiples ou les sources de réveil inconnues [SWS_EcuM_03024] [SWS_EcuM_02867].

Rôle et frontière système de l'ECU State Manager

L'ECU State Manager (EcuM) définit dans la Classic Platform le cadre du cycle de vie du calculateur. Il initialise le logiciel de base jusqu'au démarrage du système d'exploitation. Ensuite, il conduit l'ECU de manière contrôlée vers l'une des cibles d'arrêt SLEEP, RESET ou OFF [SWS_EcuM_04136]. EcuM_StateType définit ses états : STARTUP, RUN, POST_RUN, SHUTDOWN et SLEEP [SWS_EcuM_91005]. Il les signale aux SW-C via le Mode-Declaration-Group EcuM_Mode, dont le mode initial est STARTUP [SWS_EcuM_04107] [SWS_EcuM_04132].

Diagramme d'états : l'ECU traverse STARTUP, UP, SHUTDOWN et SLEEP. Depuis SLEEP, elle retourne vers UP via WakeupRestart ; après un reset matériel ou un cycle d'alimentation, elle redémarre dans STARTUP. Sources : RS ModeManagement p. 15, [SWS_EcuM_91005], [SWS_EcuM_02963], [SWS_EcuM_04001]

L'EcuM ne décide pas lui-même des transitions d'état. Il ne possède pas de machine d'états propre, arbitre seulement les demandes et délègue les transitions au BSW Mode Manager (BswM) SWS EcuM p. 103. Il externalise les étapes proches du matériel et spécifiques au projet dans des callouts de l'Integration Code, disponibles via EcuM_Externals.h. EcuM_AL_DriverInitZero et EcuM_AL_SwitchOff en sont des exemples [SWS_EcuM_02905] [SWS_EcuM_02920]. Les interfaces des modules voisins sont répertoriées dans les tables des fonctions importées, telles que BswM_EcuM_CurrentWakeup, Can_Init et Det_ReportError [SWS_EcuM_02858] [SWS_EcuM_02859].

Diagramme de contexte : l'EcuM se situe entre les SW-C, le BswM, l'Integration Code, l'OS, les pilotes MCAL et ComM. Le BswM décide des transitions, l'Integration Code exécute les étapes matérielles. Sources : SWS EcuM p. 34, [SWS_EcuM_02858], [SWS_EcuM_04135]

Démarrage : StartPreOS, StartPostOS et données de configuration

Avant EcuM_Init, l'EcuM ne suppose qu'une initialisation minimale du MCU : une pile est configurée et les variables C sont initialisées SWS EcuM p. 39. EcuM_Init exécute la séquence StartPreOS et ne retourne pas car elle appelle StartOS [SWS_EcuM_02811] [SWS_EcuM_02684]. Tous les modules nécessaires au démarrage de l'OS sont alors initialisés [SWS_EcuM_02603].

Init Block 0 (EcuM_AL_DriverInitZero) prépare le chargement des données post-build. Il ne doit par conséquent utiliser que des modules configurés au moment de la précompilation ou de l'édition de liens [SWS_EcuM_02905]. Ensuite, EcuM_DeterminePbConfiguration fournit un pointeur vers EcuM_ConfigType. Cette structure référence les configurations de tous les autres modules BSW [SWS_EcuM_02906] [SWS_EcuM_02801]. Elle contient un identifiant de variante et un hash. L'EcuM vérifie le hash par rapport à ECUM_CONFIGCONSISTENCY_HASH, et ce pour tous les modules configurables en post-build, avant que le premier d'entre eux ne soit initialisé [SWS_EcuM_02794] [SWS_EcuM_02798] [SWS_EcuM_02796].

Init Block 1 (EcuM_AL_DriverInitOne) initialise les pilotes après un reset de mise sous tension (Power-on-Reset), parmi lesquels le MCU [SWS_EcuM_02907] SWS EcuM p. 146. L'ordre au sein des deux blocs est défini par EcuMDriverInitListZero et EcuMDriverInitListOne. Chaque fonction d'initialisation reçoit ses paramètres à partir du conteneur EcuMModuleService associé [SWS_EcuM_02559] [SWS_EcuM_02730]. L'EcuM convertit la cause de reset du pilote Mcu en une source de réveil et la mémorise. Si la cause ne peut pas être déterminée, il applique ECUM_WKSOURCE_RESET [SWS_EcuM_02623] [SWS_EcuM_02601]. Si EcuMResetLoopDetection est activé, l'EcuM appelle le callout EcuM_LoopDetection à chaque démarrage [SWS_EcuM_04137].

Diagramme de séquence : EcuM_Init traverse Init Block 0, la sélection et la vérification de la configuration, Init Block 1 et l'évaluation du reset jusqu'à StartOS. Ensuite, EcuM_StartupTwo démarre le SchM et le BswM. Sources : SWS EcuM p. 38, SWS EcuM p. 78, [SWS_EcuM_02684], [SWS_EcuM_02932]

Après le démarrage de l'OS, une tâche démarrée directement à la suite de StartOS appelle EcuM_StartupTwo [SWS_EcuM_02806]. Cette fonction exécute StartPostOS : elle initialise et démarre le SchM et appelle BswM_Init [SWS_EcuM_02932] SWS EcuM p. 42. Le BswM prend en charge les initialisations supplémentaires via les fonctions générées EcuM_AL_DriverInitBswM_<x> [SWS_EcuM_04114].

Sur les calculateurs multicœurs, une instance d'EcuM s'exécute par cœur, et l'EcuM maître démarre les autres cœurs. Init Block 0 et 1 s'exécutent sur chaque cœur, mais n'y initialisent que ses modules MCAL. Le SchM, l'OS et tous les BswM locaux au cœur sont démarrés sur chaque cœur [SWS_EcuM_04145] [SWS_EcuM_04093] [SWS_EcuM_04014] SWS EcuM p. 71.

RUN et POST_RUN : demandes des utilisateurs et arbitrage avec le BswM

Si EcuMModeHandling est actif, les utilisateurs peuvent demander et relâcher RUN et POST_RUN [SWS_EcuM_04115] [SWS_EcuM_04130]. EcuM_RequestRUN, EcuM_ReleaseRUN, EcuM_RequestPOST_RUN et EcuM_ReleasePOST_RUN servent à cet effet. Tous les quatre attendent un identifiant d'utilisateur configuré de type EcuM_UserType [SWS_EcuM_04124] [SWS_EcuM_04127] [SWS_EcuM_04128] [SWS_EcuM_04129]. L'EcuM trace les demandes par utilisateur, et un utilisateur ne peut pas les imbriquer. Il gère les demandes RUN et POST_RUN dans des variables distinctes [SWS_EcuM_04126] [SWS_EcuM_04125] SWS EcuM p. 116. Les SW-C accèdent à ces services via le port StateRequest_{UserName} [SWS_EcuM_04135].

L'EcuM signale la première demande RUN ou POST_RUN au BswM avec BswM_EcuM_RequestedState(ECUM_STATE_APP_RUN, ECUM_RUNSTATUS_REQUESTED). Il signale la dernière libération de RUN ou de POST_RUN avec l'état respectif et ECUM_RUNSTATUS_RELEASED [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04119]. Le BswM évalue ses règles et définit le nouvel état avec EcuM_SetState. L'EcuM indique ensuite à la RTE le mode approprié et signale BswM_EcuM_CurrentState [SWS_EcuM_04122] [SWS_EcuM_04116] [SWS_EcuM_04143] après le retour de celle-ci. Le guide de gestion des modes présente les règles BswM appropriées, par exemple le passage à POST_RUN dès que RUN est libéré Mode-Management-Guide p. 34.

Diagramme de séquence : l'EcuM arbitre les demandes des utilisateurs et communique le résultat au BswM. Le BswM renvoie l'état via EcuM_SetState, et l'EcuM le transmet à la RTE. Sources : [SWS_EcuM_04144], [SWS_EcuM_04117], [SWS_EcuM_04116], [SWS_EcuM_04143]

Cibles d'arrêt et arrêt via OffPreOS et OffPostOS

EcuM_SelectShutdownTarget enregistre la cible et le mode uniquement pour la phase ultérieure de SHUTDOWN ou de SLEEP et ne déclenche rien par lui-même [SWS_EcuM_02822] [SWS_EcuM_00624] [SWS_EcuM_02585]. Avec la cible SLEEP, le paramètre de mode sélectionne un mode de veille configuré, et avec la cible RESET, un mode de réinitialisation. Pour OFF, il est ignoré [SWS_EcuM_02979] [SWS_EcuM_02185]. Les modes de réinitialisation comprennent au moins Mcu_PerformReset, WdgM_PerformReset et la commutation d'une broche d'E/S [SWS_EcuM_04005] [SWS_EcuM_04044]. La cause d'un arrêt est consignée avec EcuM_SelectShutdownCause [SWS_EcuM_04007] [SWS_EcuM_04050]. EcuM_GetLastShutdownTarget fournit la cible à partir de laquelle le dernier réveil ou démarrage a eu lieu. Cette valeur reste inchangée jusqu'au prochain arrêt [SWS_EcuM_02156].

La phase de SHUTDOWN se termine soit par OFF, soit par RESET [SWS_EcuM_03022]. Le moment où la cible est définie est généralement déterminé par le BswM SWS EcuM p. 66. Dans OffPreOS, le BswM et le SchM sont désinitialisés et les événements de réveil sont vérifiés. Si des événements sont en attente, RESET est défini comme cible. La dernière action est ShutdownOS [SWS_EcuM_03021] [SWS_EcuM_02952] SWS EcuM p. 49.

Ensuite, le hook de shutdown appelle EcuM_Shutdown, qui ne retourne pas. Après EcuM_OnGoOffTwo, il s'ensuit EcuM_AL_Reset pour la cible RESET et EcuM_AL_SwitchOff [SWS_EcuM_02953] [SWS_EcuM_02917] [SWS_EcuM_04074] [SWS_EcuM_04075] pour la cible OFF. Interprétation : même avec RESET et OFF, le BswM devrait déclencher la phase via EcuM_GoDownHaltPoll, car la description de son retour fait la distinction selon la cible d'arrêt [SWS_EcuM_91002].

Diagramme de séquence : OffPreOS désinitialise le BswM et le SchM, vérifie les événements de réveil et met fin à l'OS. OffPostOS bifurque ensuite vers la réinitialisation ou l'arrêt selon la cible de shutdown. Sources : SWS EcuM p. 49, SWS EcuM p. 49, [SWS_EcuM_02953], [SWS_EcuM_91002]

Phase SLEEP : GoSleep, Halt ou Poll et WakeupRestart

Si SLEEP est sélectionné comme cible, EcuM_GoDownHaltPoll initie la phase SLEEP. L'appelant doit avoir préalablement défini la cible appropriée [SWS_EcuM_91002] SWS EcuM p. 54. Dans GoSleep, l'EcuM active via EcuM_EnableWakeupSources toutes les sources de réveil issues de EcuMWakeupSourceMask du mode de veille cible. Sur les ECU multicœurs, il alloue en plus la ressource spécifique au cœur RES_AUTOSAR_ECUM. Contrairement à l'arrêt, l'OS reste actif [SWS_EcuM_02389] [SWS_EcuM_03010] [SWS_EcuM_02951]. Aucun événement de réveil ne doit être perdu. Si l'un d'eux s'est déjà produit pendant GoSleep, Halt et Poll sont ignorés [SWS_EcuM_02188].

Les modes de veille qui arrêtent le microcontrôleur exécutent la séquence Halt. Avant cela, l'EcuM appelle EcuM_GenerateRamHash, puis EcuM_CheckRamHash [SWS_EcuM_02960] [SWS_EcuM_02863]. En revanche, les modes de veille à fréquence d'horloge réduite utilisent la séquence Poll. Celle-ci appelle EcuM_SleepActivity et EcuM_CheckWakeup dans une boucle bloquante jusqu'à ce qu'un événement soit signalé comme pending ou validé [SWS_EcuM_02962] [SWS_EcuM_03020]. Dans R20-11, EcuM_CheckWakeup est encore un callout. Ce n'est qu'à partir de R21-11 que ce callout s'appelle EcuM_CheckWakeupHook [SWS_EcuM_02929] SWS EcuM p. 145.

Un événement de réveil mène à la séquence WakeupRestart [SWS_EcuM_02963] SWS EcuM p. 56 :

  1. Le MCU revient en mode normal.
  2. EcuM_DisableWakeupSources désactive les sources de réveil actuellement en attente ; toutes les autres restent armées [SWS_EcuM_02922].
  3. EcuM_AL_DriverRestart réinitialise les pilotes concernés [SWS_EcuM_02923].
  4. L'ordonnanceur est de nouveau libéré.

En revanche, si une réinitialisation matérielle ou un cycle d'alimentation survient pendant la veille, l'ECU redémarre dans STARTUP [SWS_EcuM_04001].

Diagramme de séquence : GoSleep prépare les sources de réveil, Halt ou Poll mettent en œuvre la veille, et WakeupRestart ramène à l'état UP. Sources : SWS EcuM p. 52, SWS EcuM p. 85, SWS EcuM p. 87, SWS EcuM p. 58

En option, l'EcuM gère une horloge qui compte les secondes depuis le raccordement de la batterie [SWS_EcuM_04069]. Chaque utilisateur peut définir au maximum une alarme de réveil. L'alarme maître correspond toujours à l'alarme utilisateur la plus précoce [SWS_EcuM_04070] [SWS_EcuM_04072]. EcuM_SetAbsWakeupAlarm rejette une date ultérieure avec ECUM_E_EARLIER_ACTIVE et une date déjà écoulée avec ECUM_E_PAST [SWS_EcuM_04059] [SWS_EcuM_04060]. En quittant SLEEP, l'EcuM annule toutes les alarmes [SWS_EcuM_04009].

Sources de réveil : états, validation et interrogation

L'EcuM gère jusqu'à 32 sources de réveil sous forme de masque de bits de type EcuM_WakeupSourceType. Cinq bits sont prédéfinis, parmi lesquels ECUM_WKSOURCE_POWER et ECUM_WKSOURCE_RESET. D'autres sources reçoivent via EcuMWakeupSourceId les bits 5 à 31 [SWS_EcuM_04040] [SWS_EcuM_02165] [SWS_EcuM_02166] SWS EcuM p. 63. Chaque source se trouve dans l'un des états NONE, PENDING, VALIDATED ou EXPIRED [SWS_EcuM_04091] [SWS_EcuM_04041]. L'EcuM signale chaque changement d'état au BswM sous la forme d'une demande de mode [SWS_EcuM_04003].

Diagramme d'états : une source de réveil passe de NONE à VALIDATED ou EXPIRED en passant par PENDING. Chaque transition d'état est signalée au BswM, et EcuM_ClearWakeupEvent réinitialise la source à NONE. Sources : SWS EcuM p. 60, [SWS_EcuM_04091], [SWS_EcuM_02683]

Un pilote signale un événement détecté exactement une fois avec EcuM_SetWakeupEvent SWS EcuM p. 71. La fonction peut également être appelée depuis un contexte d'interruption ou un contexte sans OS. Elle applique un OU logique aux bits transmis dans la variable Pending. Elle ignore les sources qui n'appartiennent pas au mode de veille sélectionné [SWS_EcuM_02826] [SWS_EcuM_02171] [SWS_EcuM_01117] [SWS_EcuM_04138].

Si l'événement doit être validé, l'EcuM démarre un délai d'attente spécifique à la source conformément à EcuMValidationTimeout. Si la même source est signalée à nouveau, le délai d'attente ne redémarre pas [SWS_EcuM_02975] [SWS_EcuM_02565] [SWS_EcuM_02709] [SWS_EcuM_02712]. Si aucune validation n'est configurée pour une source, EcuM_SetWakeupEvent a simultanément le même effet que EcuM_ValidateWakeupEvent. Les cinq sources prédéfinies ne sont jamais validées [SWS_EcuM_02566] [SWS_EcuM_02625].

La validation proprement dite s'exécute dans EcuM_MainFunction, qui appelle pour cela le callout EcuM_CheckValidation [SWS_EcuM_02539] [SWS_EcuM_02925] SWS EcuM p. 64. EcuM_ValidateWakeupEvent produit les effets suivants [SWS_EcuM_02710] [SWS_EcuM_04078] [SWS_EcuM_04079] [SWS_EcuM_02645] [SWS_EcuM_04140] :

  • Elle arrête le délai d'attente et positionne les bits dans la variable Validated.
  • Elle signale ECUM_WKSTATUS_VALIDATED au BswM.
  • Si un canal ou un PNC est configuré, elle appelle ComM_EcuM_WakeUpIndication ou ComM_EcuM_PNCWakeUpIndication.

Si le délai d'attente expire, la fonction principale active le bit Expired et signale ECUM_WKSTATUS_EXPIRED [SWS_EcuM_04081] [SWS_EcuM_04082]. À l'état RUN, la validation n'a d'effet que pour les canaux de communication [SWS_EcuM_02790] [SWS_EcuM_02791].

Diagramme d'activité : pour les sources ne nécessitant pas de validation, un événement est immédiatement validé. Pour les autres, il reste PENDING jusqu'à ce que EcuM_ValidateWakeupEvent survienne ou que le délai d'attente expire et que la source devienne EXPIRED. Sources : SWS EcuM p. 63, SWS EcuM p. 78, [SWS_EcuM_02566], [SWS_EcuM_04082]

EcuM_GetPendingWakeupEvents, EcuM_GetValidatedWakeupEvents et EcuM_GetExpiredWakeupEvents interrogent l'état actuel. EcuM_ClearWakeupEvent efface les bits transmis de l'ensemble des trois variables [SWS_EcuM_01156] [SWS_EcuM_02533] [SWS_EcuM_04076] [SWS_EcuM_02683].

Certaines sources de réveil disposent d'une alimentation électrique intégrée, de sorte que leur réveil agit comme un power-on-reset. Pour celles-ci, EcuM_StartCheckWakeup démarre un CheckWakeupTimer, qui empêche un arrêt prématuré. EcuM_SetWakeupEvent ou EcuM_EndCheckWakeup arrête à nouveau le temporisateur [SWS_EcuM_04096] [SWS_EcuM_04098] [SWS_EcuM_02927] SWS EcuM p. 70.

Comportement en cas d'erreur

L'EcuM signale les erreurs non récupérables via le callout EcuM_ErrorHook avec le code d'erreur associé [SWS_EcuM_04033] [SWS_EcuM_02904]. Dans R20-11, il existe deux codes pour cela [SWS_EcuM_91003] [SWS_EcuM_02987] :

  • ECUM_E_CONFIGURATION_DATA_INCONSISTENT en cas de données post-build incohérentes.
  • ECUM_E_RAM_CHECK_FAILED lorsque le test de RAM échoue après le réveil.

Si un appel à l'OS échoue, l'EcuM conserve l'état demandé et appelle également l'ErrorHook [SWS_EcuM_04139]. Une version ultérieure de la spécification introduit pour la première fois un code propre ECUM_E_OS_CALL_FAILED et l'indication que le hook ne retourne pas SWS EcuM p. 102. L'EcuM ignore les erreurs survenues pendant l'initialisation, par exemple les valeurs de retour des fonctions Init [SWS_EcuM_02980].

Lorsque la détection des erreurs de développement est activée, toutes les fonctions vérifient leurs paramètres et leurs conditions d'exécution. Pour cela, ECUM_E_UNINIT, ECUM_E_SERVICE_DISABLED, ECUM_E_PARAM_POINTER et ECUM_E_INVALID_PAR sont disponibles [SWS_EcuM_03009]. L'EcuM signale d'autres cas au DET :

  • Demandes multiples d'un même utilisateur sous la forme ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03024] [SWS_EcuM_03025].
  • Libérations sans demande correspondante sous la forme ECUM_E_MISMATCHED_RUN_RELEASE [SWS_EcuM_03023] [SWS_EcuM_03026].
  • Sources de réveil inconnues sous la forme ECUM_E_UNKNOWN_WAKEUP_SOURCE ; la variable interne reste alors inchangée [SWS_EcuM_02867] [SWS_EcuM_02868].
  • États non valides fournis à EcuM_SetState sous la forme ECUM_E_STATE_PAR_OUT_OF_RANGE [SWS_EcuM_04123].

Ce callout est intended à fournir un RAM intégrité test. le goal de ce test est à garantir que après un long SLEEP durée, RAM contenus est encore cohérent. le vérifier ne avoir besoin à être exhaustive depuis ce would consume quite quelque traitement temps pendant wakeups. A bien designed vérifier va execute quickly et detect RAM intégrité defects avec un suffisant probability. ce specification ne make tout hypothèse à propos du algorithme choisi pour un particular ECU. le areas de RAM qui sera vérifié ont à être choisi carefully. il dépend sur le vérifier algorithme itself et le tâche structure. pile contenus du tâche exécutant le RAM vérifier e.g. très likely ne peut pas être vérifié. il est good practice à ont le hash generation et checking dans le même tâche et que ce tâche n'est pas preemptible et que là est seulement little activity entre hash generation et hash vérifier. le RAM vérifier itself est fourni par le système designer. en cas de applied multi core et existence de Satellite-Ecu M(s): Cette API sera appelé par le maître-EcuM seulement.

uint8 EcuM_CheckRamHash (void);
