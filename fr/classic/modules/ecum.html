Rolle und Verwendungszweck des ECU State Managers (EcuM)

Der ECU State Manager (EcuM) verwaltet den globalen Lebenszyklus eines AUTOSAR-Steuergeräts. Er steuert den Bootvorgang, koordiniert Wakeup-Quellen, initialisiert Basistreiber vor und nach dem Start des Betriebssystems und begleitet das geordnete Herunterfahren (Shutdown) oder Versetzen in energiesparende Schlafzustände (Sleep) [SWS_EcuM_02813]. In modernen Architekturen (EcuM Fixed / Flexible) arbeitet er eng mit dem BSW Mode Manager (BswM) zusammen [SWS_EcuM_02811].

Phasen des Steuergeräte-Lebenszyklus

Der Lebenszyklus unterteilt sich in klar definierte Abschnitte:

  1. STARTUP I (Pre-OS): Nach Reset führt EcuM_Init hardwarenahe Treiber-Inits durch (Mcu, Port, Dio, Watchdog) und ruft StartOS auf [SWS_EcuM_02813].
  2. STARTUP II (Post-OS): Im ersten OS-Task übernimmt EcuM_StartupTwo die Initialisierung von BSW-Diensten (Dem, NvM, ComM, BswM) [SWS_EcuM_02815].
  3. UP / RUN: Das Steuergerät befindet sich im Normalbetrieb. Module fordern über EcuM_RequestRUN den Erhalt des aktiven Betriebs an [SWS_EcuM_02817].
  4. SHUTDOWN & SLEEP: Sobald alle RUN-Anforderungen entfallen, koordiniert der EcuM die Deinitialisierung und das Abschalten über EcuM_GoDown bzw. ShutdownOS [SWS_EcuM_02820].

Zustandsablauf: Gestaffelte Initialisierung über EcuM_Init und EcuM_StartupTwo bis zur RUN-Phase und geordnetem Shutdown.

Wakeup-Validierung und Reset-Gründe

Der EcuM erfasst Wakeup-Events (CAN-Traffic, Klemmenwechsel, Timer) und startet eine konfigurierbare Validierungsphase. Unplausible Wakeup-Signale werden gefiltert, bevor das Steuergerät vollständig hochgefahren wird [SWS_EcuM_02812].

ECU State Manager (EcuM)

Controls ECU lifecycle states: Startup, Run, PostRun, Sleep, and Shutdown.

fonction EcuM_CheckRamHash [SWS_EcuM_02921] 📄 PDF

uint8 EcuM_CheckRamHash (void);

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

EcuM_WakeupSourceType defines a bitfield with 5 pre-defined positions (see Range). The bitfield provides one bit for each wakeup source. In WAKEUP, all bits cleared indicates that no wakeup source is known. In STARTUP, all bits cleared indicates that no reason for restart or reset is known.
