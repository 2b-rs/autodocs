Rôle et frontière du système : de l'événement de capteur au Security Event qualifié

L'Intrusion Detection System Manager (IdsM) est le module BSW de la Classic Platform qui reçoit les événements de sécurité embarqués (SEv) via une interface standardisée. Il les filtre selon des règles configurables pour obtenir des événements qualifiés (QSEv), puis les enregistre ou les envoie SWS IdsM p. 7. Les modules BSW, les CDD propriétaires et les SW-C font office de capteurs. Les puits sont l'IDS Reporter (IdsR), joint via le PduR, ainsi que DEM/Sem pour le stockage local SWS IdsM p. 16 [SWS_IdsM_01202] [SWS_IdsM_01601].

L'IdsM n'évalue expressément pas si un système est effectivement compromis. Il ne connaît pas la signification des données de contexte ; la détection et la réaction se situent hors du module, par exemple au sein d'un SOC [SWS_IdsM_CONSTR_00001]. La spécification accepte en outre que des SEv soient rejetés selon la fréquence de signalement ou la charge du système SWS IdsM p. 11.

Autres modules voisins et leurs tâches :

  • DET : erreurs de développement
  • DCM : accès de diagnostic au Reporting Mode
  • NvM : persistance du Reporting Mode
  • BswM : fournisseur du Block State
  • StbM ou une SW-C : source d'horodatage
  • CSM : signatures
  • BSW Scheduler : appel cyclique

Justificatifs : SWS IdsM p. 13. L'inclusion des en-têtes dépend des commutateurs de configuration correspondants, par ex. Det.h lors de IdsMDevErrorDetect et PduR.h lors de IdsMSinkIdsR [SWS_IdsM_00101] [SWS_IdsM_00105].

Diagramme de contexte : l'IdsM se situe entre les capteurs (BSW/CDD directement, SW-C via la RTE) et les puits IdsR (via PduR) ou DEM/Sem. Les modules de commande et de support sont BswM, DCM, NvM, StbM, CSM et DET. Sources : SWS IdsM p. 20, SWS IdsM p. 13, [SWS_IdsM_91027], [SWS_IdsM_91028].

Cycle de vie : initialisation et traitement cyclique

IdsM_Init initialise toutes les variables internes et place le module dans l'état « initialisé » [SWS_IdsM_00202] [SWS_IdsM_91001]. Un nouvel appel dans l'état initialisé ne réinitialise pas le module. Si IdsMDevErrorDetect est actif, il signale à la place IDSM_E_ALREADY_INITIALIZED [SWS_IdsM_00204]. Dans l'état non initialisé, chaque API, à l'exception de IdsM_Init et IdsM_GetVersionInfo, entraîne une erreur DET [SWS_IdsM_00203].

Le travail effectif s'exécute de manière asynchrone. IdsM_MainFunction est appelée périodiquement et traite les événements mis en file d'attente lors des appels d'API [SWS_IdsM_91000] SWS IdsM p. 19. La période IdsMMainFunctionPeriod constitue également la base temporelle de tous les filtres d'intervalle. Leurs intervalles doivent être des multiples de cette période et débutent avec le premier appel de la MainFunction [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01064] [SWS_IdsM_01065].

Diagramme d'états : seul IdsM_Init rend le module utilisable. Les appels erronés dans les deux états sont signalés au DET sans modifier l'état. Sources : [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], [SWS_IdsM_91000].

Signalement des Security Events : identité, variantes d'API et mise en mémoire tampon

Chaque instance de SEv est décrite par quatre éléments : IdsMExternalEventId, IdsMSensorInstanceId, un IdsMInternalEventId calculé en interne et le nom de l'événement [SWS_IdsM_00600] [SWS_IdsM_00601]. Pour l'utilisation, les règles suivantes s'appliquent (SWS IdsM p. 21) :

  • Les capteurs utilisent exclusivement la constante symbolique du conteneur IdsMEvent, jamais la valeur numérique interne [SWS_IdsM_00602] [SWS_IdsM_00607].
  • L'ID externe 0xFFFF n'est pas valide [SWS_IdsM_00604].
  • S'il n'existe qu'une seule instance de module, l'instance de capteur est définie par défaut sur 0 [SWS_IdsM_00608].

Pour le signalement, six services synchrones non réentrants sont mis à disposition. Ils se distinguent par les données supplémentaires fournies. Les variantes avec compteur et horodatage s'adressent aux Smart Sensors (SW-C ou CDD) qui déterminent eux-mêmes ces valeurs SWS IdsM p. 19. Si seul un horodatage est présent sans compteur propre, count = 1 est transmis [SWS_IdsM_00405].

Qualification : Reporting Mode et chaîne de filtrage

Chaque SEv dispose d'un filtre obligatoire de Reporting Mode. Il ne fait pas partie de la chaîne de filtrage, mais est directement rattaché à l'événement ; sa valeur par défaut provient de IdsMReportingModeFilter [SWS_IdsM_01010] [SWS_IdsM_01011] [SWS_IdsM_01012]. Les valeurs de IdsM_Filters_ReportingModeType signifient [SWS_IdsM_91013] SWS IdsM p. 91 :

  • IDSM_REPORTING_MODE_OFF : l'événement est rejeté.
  • IDSM_REPORTING_MODE_BRIEF / IDSM_REPORTING_MODE_DETAILED : signalement respectivement sans ou avec données de contexte.
  • …_BYPASSING_FILTERS : signalement en contournant la chaîne de filtrage.

Ce n'est qu'après le Reporting Mode que la chaîne de filtrage associée au SEv est évaluée [SWS_IdsM_01001] [SWS_IdsM_01002]. Les filtres activés s'exécutent selon un ordre fixe : Block State, Forward Every Nth, Event Aggregation, Event Threshold [SWS_IdsM_01004]. Si un filtre rejette le SEv, toute évaluation ultérieure est omise [SWS_IdsM_01005] SWS IdsM p. 25. Une chaîne de filtrage requiert au moins un filtre [SWS_IdsM_CONSTR_00002]. Les différents filtres fonctionnent ainsi :

  • Block State: Le BswM signale l'état actuel via IdsM_BswM_StateChanged. Si cet état appartient aux IdsMBlockState référencés, le SEv est rejeté [SWS_IdsM_01022] [SWS_IdsM_01023] SWS IdsM p. 28.
  • Forward Every Nth: Le premier puis chaque n-ième SEv sont transmis sans modification [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  • Aggregation: Les SEv sont retenus pendant IdsMEventAggregationTimeInterval. À la fin de l'intervalle, un SEv comportant la somme de tous les compteurs est transmis ; les données de contexte et l'horodatage proviennent au choix du premier ou du dernier SEv [SWS_IdsM_01043] [SWS_IdsM_01046] [SWS_IdsM_01047] [SWS_IdsM_01048] [SWS_IdsM_01049] SWS IdsM p. 40.
  • Threshold: Tant que la somme des compteurs dans l'intervalle est inférieure à IdsMEventThresholdNumber, l'événement est rejeté ; dès que la valeur de seuil est atteinte, il est transmis. À la fin de l'intervalle, le compteur est réinitialisé [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063] SWS IdsM p. 41.

Diagramme d'activité : le Reporting Mode décide d'abord du rejet, du contournement ou du filtrage. Le SEv traverse ensuite les filtres activés dans un ordre fixe jusqu'à ce qu'il soit rejeté ou devienne un QSEv. Sources : SWS IdsM p. 35, SWS IdsM p. 24, [SWS_IdsM_01004], [SWS_IdsM_01005], [SWS_IdsM_91013].

Enrichissement et transmission des événements qualifiés

Indépendamment du puits, les QSEv ont une structure fixe conforme au protocole IDS [SWS_IdsM_01200]. La configuration définit pour chaque IdsMEvent les puits utilisés [SWS_IdsM_01201] SWS IdsM p. 35. Avec IdsMSinkIdsR, le QSEv est envoyé via PduR_IdsMTransmit en tant qu'IDS Message [SWS_IdsM_01203] [SWS_IdsM_01498]. Avant l'envoi à l'IdsR, des limitations à l'échelle de l'instance s'appliquent : la limitation de débit restreint le nombre de QSEv par intervalle, la limitation de trafic restreint les octets par intervalle [SWS_IdsM_01070] [SWS_IdsM_01081] [SWS_IdsM_01091] SWS IdsM p. 32.

Le chemin de transmission dépend de la taille SWS IdsM p. 38 :

  • Si l'IDS Message avec sa signature tient dans une PDU de bus, une IF-PDU est utilisée [SWS_IdsM_01400] ; la confirmation provient de IdsM_TxConfirmation [SWS_IdsM_01500].
  • Dans le cas contraire, des TP-PDU sont utilisées [SWS_IdsM_01401]. Le PduR récupère les données par segments via IdsM_CopyTxData [SWS_IdsM_01501] et confirme via IdsM_TpTxConfirmation [SWS_IdsM_01502].
  • Avant la confirmation, l'IdsM n'appelle pas PduR_IdsMTransmit une nouvelle fois [SWS_IdsM_01499].

Diagramme de séquence : après la limitation, un QSEv est transmis sous forme d'IF-PDU ou de TP-PDU selon sa taille. La transmission suivante ne peut débuter qu'après la confirmation. Sources : [SWS_IdsM_01070], [SWS_IdsM_01400], [SWS_IdsM_01401], [SWS_IdsM_01499], [SWS_IdsM_01501], [SWS_IdsM_01502].

L'IdsM signe facultativement chaque QSEv. Cela est activé globalement par un job CSM référencé via IdsMCsmJobReference. La signature est générée via Csm_SignatureGenerate ; pour les jobs asynchrones, le CSM signale le résultat via IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01208] SWS IdsM p. 36. Le puits DEM/Sem est identifié comme DRAFT dans R20-11 ; il enregistre l'IDS Message complet [SWS_IdsM_01600] [SWS_IdsM_01602].

Les horodatages sont activés globalement via IdsMTimestampOption [SWS_IdsM_01100] [SWS_IdsM_01103] SWS IdsM p. 33. Les règles suivantes s'appliquent SWS IdsM p. 34 :

  • Si le capteur ne fournit pas d'horodatage, l'IdsM le récupère lui-même : pour « AUTOSAR » via StbM_GetCurrentTime, pour « Custom » via l'interface IdsM_CustomTimestamp auprès d'une SW-C [SWS_IdsM_01104] [SWS_IdsM_01107] [SWS_IdsM_01109] [SWS_IdsM_01111].
  • Les horodatages signalés par le capteur ont la priorité et sont tronqués aux 62 bits de poids faible [SWS_IdsM_01108] [SWS_IdsM_01110].
  • Pour « None », même les horodatages transmis sont ignorés [SWS_IdsM_01106].

Un point en suspens dans la spécification : [SWS_IdsM_01112] exige que le bit d'option d'horodatage soit à 0 lorsque les API d'horodatage sont utilisées sans paramètre d'horodatage. Le texte laisse en suspens la façon dont cela s'articule par rapport à [SWS_IdsM_01101].

Diagramme d'activité : la source d'horodatage est déterminée à partir de IdsMTimestampOption et du paramètre signalé. Sources : SWS IdsM p. 87, [SWS_IdsM_01104], [SWS_IdsM_01106], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110].

Reporting Mode à l'exécution : diagnostic et persistance NvM

Si IdsMDiagnosticSupport est actif, le Reporting Mode peut être lu et modifié via le DCM [SWS_IdsM_01800] [SWS_IdsM_01900] [SWS_IdsM_02000] SWS IdsM p. 40 :

  • La lecture se fait en deux étapes : IdsM_Dcm_GetReportingMode_Start initie la routine, IdsM_Dcm_GetReportingMode_RequestResults fournit le résultat via un pointeur [SWS_IdsM_02001] [SWS_IdsM_02002].
  • La modification s'effectue via IdsM_Dcm_SetReportingMode_Start. Un mode non valide ou un ID d'événement non valide entraîne E_NOT_OK avec DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01901] [SWS_IdsM_01902] [SWS_IdsM_01903].

Après une modification réussie, l'IdsM déclenche NvM_WriteBlock [SWS_IdsM_01701]. Si la persistance échoue, il rétablit le mode à la valeur précédente et répond avec DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905]. Au démarrage, il lit le mode persisté. Le bloc NvM doit être inclus dans NvM_ReadAll à cet effet ; si des valeurs NvM manquent, la configuration s'applique [SWS_IdsM_01703] [SWS_IdsM_01704] [SWS_IdsM_01705] SWS IdsM p. 39.

Diagramme de séquence : la lecture s'effectue en deux étapes via Start et RequestResults. Lors de la modification, une vérification a d'abord lieu, puis la persistance et, en cas d'erreur, une rétrogradation. Sources : [SWS_IdsM_02001], [SWS_IdsM_02002], [SWS_IdsM_01902], [SWS_IdsM_01903], [SWS_IdsM_01701], [SWS_IdsM_01904], [SWS_IdsM_01905].

Comportement en cas d'erreur

Lorsque IdsMDevErrorDetect est actif, l'IdsM signale les erreurs de développement au DET. Les codes d'erreur sont IDSM_E_PARAM_INVALID (0x0A), IDSM_E_PARAM_POINTER (0x0B), IDSM_E_PARAM_LENGTH (0x0C), IDSM_E_UNINIT (0x0D) et IDSM_E_ALREADY_INITIALIZED (0x0E) [SWS_IdsM_02003]. Attention : [SWS_IdsM_00203] mentionne IDSM_E_PARAM_UNINIT pour les appels à l'état non initialisé. Le tableau des erreurs ne contient pas ce code ; il indique IDSM_E_UNINIT à la place. Les contrôles de paramètres en détail :

  • Un securityEventId inconnu lors des API de signalement ainsi que count = 0 dans les variantes avec compteur produisent IDSM_E_PARAM_INVALID [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106] SWS IdsM p. 42.
  • Un contextDataSize supérieur au plus grand IdsMContextDataBufferSize produit IDSM_E_PARAM_LENGTH [SWS_IdsM_02107] [SWS_IdsM_02108] [SWS_IdsM_02109] SWS IdsM p. 43.
  • Un NULL_PTR non autorisé produit IDSM_E_PARAM_POINTER SWS IdsM p. 42.

L'IdsM signale les goulots d'étranglement à l'exécution via ses propres SEv internes, pour autant que ceux-ci soient configurés. Ils disposent de leurs propres mémoires tampons et ne sont pas filtrés par les filtres à l'échelle de l'instance [SWS_IdsM_91015] [SWS_IdsM_00802] [SWS_IdsM_00803] SWS IdsM p. 24. Il existe trois SEv internes :

  • aucun Event Buffer disponible [SWS_IdsM_00703]
  • aucun Context Data Buffer disponible ; le SEv est alors traité sans données de contexte [SWS_IdsM_00707] [SWS_IdsM_00708]
  • limitation de trafic dépassée [SWS_IdsM_01094]

Si la persistance échoue lors d'une modification de diagnostic, le rollback décrit ci-dessus intervient [SWS_IdsM_01905].

Le type IdsM_Filters_ReportingModeType ([SWS_IdsM_91013]) définit les modes de rapport utilisés par le filtre de mode de rapport (reporting mode filter) du module IdsM. Le type de base est dérivé de uint8 et est mis à disposition via l'en-tête IdsM_Types.h.

Plage de valeurs et sémantique

Le type définit la manière dont, ou si, un événement de sécurité (Security-Event) détecté est relayé :

  • IDSM_REPORTING_MODE_OFF (0x00) : l'événement n'est pas signalé.
  • IDSM_REPORTING_MODE_BRIEF (0x01) : l'événement est signalé sous forme compacte sans données de contexte.
  • IDSM_REPORTING_MODE_DETAILED (0x02) : l'événement est signalé de manière détaillée, données de contexte incluses.
  • IDSM_REPORTING_MODE_BRIEF_BYPASSING_FILTERS (0x03) : l'événement est signalé sans filtrage, sans données de contexte, en contournant les filtres.
  • IDSM_REPORTING_MODE_DETAILED_BYPASSING_FILTERS (0x04) : l'événement est signalé sans filtrage avec ses données de contexte, en contournant les filtres.
  • IDSM_REPORTING_MODE_INVALID (0xFF) : caractérise un mode de rapport invalide.

Utilisation et restrictions

En tant qu'énumération ou type de configuration, IdsM_Filters_ReportingModeType pilote la logique de filtrage et de transmission des événements de sécurité au sein de la chaîne de filtrage de l'IdsM.
