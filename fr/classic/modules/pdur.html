Rôle dans la pile de communication : intermédiaire neutre pour les I-PDU

Le PDU Router (PduR) relie les utilisateurs indépendants du bus tels que Com ou Dcm aux interfaces de communication (CanIf, FrIf, LinIf) et aux protocoles de transport (CanTp, FrTp). Il transfère une I-PDU de manière inchangée et cohérente de la source aux destinations [SWS_PduR_00160]. Ce faisant, il effectue le routage exclusivement le long de chemins de routage configurés [SWS_PduR_00162]. Un chemin est déterminé de manière univoque par deux indications : l'ID d'I-PDU source de la configuration de PduR et les ID d'I-PDU de destination des modules appelés [SWS_PduR_00161]. Le PduR convertit ces ID dans le chemin d'émission tout comme dans le chemin de confirmation et d'indication [SWS_PduR_00766], SWS PduR p. 33.

Du point de vue du calculateur, il existe trois classes d'opérations. Premièrement la réception vers des modules locaux, deuxièmement l'émission depuis des modules locaux et troisièmement la passerelle entre des modules d'interface ou TP. La réception et la passerelle peuvent être combinées SWS PduR p. 29. Les modules voisins sont décrits de manière générique via les espaces réservés <Up>, <Lo> und <LoTp> SWS PduR p. 96. Des Complex Drivers peuvent également être connectés ; leur apiServicePrefix remplace alors les espaces réservés [SWS_PduR_00504]. Chaque module voisin reçoit son propre fichier d'en-tête, tel que PduR_CanIf.h [SWS_PduR_00216].

Diagramme de contexte : Le PduR se situe entre les utilisateurs supérieurs, les modules d'interface et de TP et est commandé par BswM via des groupes de chemins de routage. Sources : [SWS_PduR_00424], [SWS_PduR_00504], SWS PduR p. 96, SWS BswM p. 166

Les modules voisins ne peuvent s'appeler directement que sous deux conditions : PduRZeroCostOperation est défini, et tous les chemins de routage sont Pre-Compile [SWS_PduR_00287]. Le PduR devient alors une simple couche de macros SWS PduR p. 65. Si ne serait-ce qu'un seul chemin n'est pas Pre-Compile, le générateur doit signaler une erreur [SWS_PduR_00619]. Indépendamment de cela, le générateur doit éliminer par optimisation les fonctionnalités non utilisées, comme le TP, la passerelle ou la gestion de FIFO [SWS_PduR_00764].

Cycle de vie et état de configuration : de PDUR_UNINIT à PDUR_ONLINE

Il existe exactement une machine d'états [SWS_PduR_00644]. Elle connaît les états PDUR_UNINIT et PDUR_ONLINE de PduR_StateType [SWS_PduR_00324], [SWS_PduR_00742]. Après la mise sous tension, le PduR est dans PDUR_UNINIT [SWS_PduR_00325]. Seul un PduR_Init réussi le fait passer à PDUR_ONLINE [SWS_PduR_00326], [SWS_PduR_00334]. Le routage n'a lieu que dans PDUR_ONLINE [SWS_PduR_00328], pas du tout dans PDUR_UNINIT [SWS_PduR_00330]. Un schéma plus ancien montre en plus un état PDUR_REDUCED SWS PduR p. 30. Pour R20-11, le modèle à deux états selon [SWS_PduR_00324] s'applique toutefois.

Diagramme d'états : Seul PduR_Init mène de PDUR_UNINIT au mode de routage ; un nouvel appel Init constitue une erreur. Sources : [SWS_PduR_00324], [SWS_PduR_00100], [SWS_PduR_00296], SWS PduR p. 53

PduR_Init reçoit un pointeur sur PduR_PBConfigType [SWS_PduR_00743]. Cette structure est spécifique à l'implémentation et se trouve dans PduR_PBcfg.c [SWS_PduR_00241]. Lors de l'initialisation, le PduR effectue trois choses :

  • Il libère tous les tampons [SWS_PduR_00645].
  • Il initialise les tampons d'émission avec les valeurs par défaut configurées [SWS_PduR_00308].
  • Il active les groupes de chemins de routage conformément à la configuration initiale [SWS_PduR_00709], c'est-à-dire selon PduRIsEnabledAtInit SWS PduR p. 131.

Dans la variante post-build, les tables de routage sont interchangeables [SWS_PduR_00295], toutefois uniquement à l'état non initialisé [SWS_PduR_00296]. PduR_GetConfigurationId fournit l'PduRConfigurationId unique de la configuration active [SWS_PduR_00341], [SWS_PduR_00280], [SWS_PduR_00281]. Son type est PduR_PBConfigIdType sur la base de uint16 [SWS_PduR_00771]. PduR_GetVersionInfo [SWS_PduR_00338] n'est disponible que si PduRVersionInfoApi est défini System Template p. 656.

Émission et réception locales via des interfaces de communication

Si un module supérieur appelle PduR_<User:Up>Transmit [SWS_PduR_00406], le PduR appelle <Lo>_Transmit pour chaque interface de destination [SWS_PduR_00625]. Il ne met alors pas l'I-PDU en tampon [SWS_PduR_00629] et ne vérifie pas non plus sa longueur [SWS_PduR_00745]. En cas de singlecast, il transmet la valeur de retour [SWS_PduR_00432]. En cas de multicast, une seule destination réussie suffit pour E_OK [SWS_PduR_00218]. La confirmation au module supérieur ne suit alors qu'après la dernière confirmation d'interface [SWS_PduR_00589]. En singlecast, le PduR transmet PduR_<User:Lo>TxConfirmation [SWS_PduR_00365] ainsi que le résultat à <Up>_TxConfirmation [SWS_PduR_00627].

Sur les bus déclenchés sur base de temps, l'interface récupère elle-même les données, et ce via PduR_<User:Lo>TriggerTransmit [SWS_PduR_00369]. Le PduR relaie cette requête à <Up>_TriggerTransmit [SWS_PduR_00430] et renvoie sa valeur de retour [SWS_PduR_00661]. L'interface signale les I-PDU reçues avec PduR_<User:Lo>RxIndication [SWS_PduR_00362]. Le PduR appelle ensuite <Up>_RxIndication pour chaque module cible [SWS_PduR_00621], [SWS_PduR_00164], également sans vérification de longueur [SWS_PduR_00744].

Diagramme de séquence : L'émission via FrIf se décompose en trois phases temporellement distinctes : requête, récupération des données par TriggerTransmit et confirmation. Sources : [SWS_PduR_00430], [SWS_PduR_00627], SWS PduR p. 106

Chemins de protocole de transport pour les I-PDU segmentées

Sur les chemins TP, le PduR fonctionne avec un handshake de copie qui permet des I-PDU plus grandes qu'une trame Layered Architecture p. 97. La réception se déroule en trois étapes :

  1. Le PduR transmet PduR_<User:LoTp>StartOfReception [SWS_PduR_00507] à <Up>_StartOfReception [SWS_PduR_00549] et renvoie sa valeur de retour [SWS_PduR_00623].
  2. Viennent ensuite les appels de CopyRxData pour les différents segments [SWS_PduR_00512], [SWS_PduR_00428].
  3. L'indication de réception [SWS_PduR_00375], [SWS_PduR_00429] conclut le processus.

Un appel de copie avec SduLength = 0 interroge uniquement le tampon disponible ou les données disponibles [SWS_PduR_00740].

Diagramme de séquence : Lors de la réception TP, le PduR demande un tampon au module supérieur pour chaque segment et renvoie ses réponses de manière inchangée. Sources : [SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429], SWS PduR p. 75

Lors de l'émission, le PduR appelle <LoTp>_Transmit pour chaque TP de destination [SWS_PduR_00634]. Les modules TP récupèrent ensuite les données avec PduR_<User:LoTp>CopyTxData [SWS_PduR_00518]. Le PduR transmet ces appels à <Up>_CopyTxData [SWS_PduR_00299], [SWS_PduR_00676]. En cas de multicast, il copie d'abord pour chaque position avec TP_CONFPENDING ; pour toutes les autres destinations, il copie les mêmes données avec TP_DATARETRY [SWS_PduR_00631], [SWS_PduR_00632]. En cas de singlecast, <Up>_TpTxConfirmation suit directement [SWS_PduR_00301]. En cas de multicast, elle ne suit qu'après la dernière confirmation, et ce avec E_OK si au moins une destination a réussi [SWS_PduR_00765], [SWS_PduR_00381]. Les destinations d'une requête d'émission sont soit uniquement des interfaces, soit uniquement des modules TP, jamais un mélange [SWS_PduR_00633].

Diagramme de séquence : Lors du multicast TP, le PduR récupère plusieurs fois les mêmes données auprès du module supérieur et combine les confirmations en une seule. Sources : [SWS_PduR_00631], [SWS_PduR_00632], [SWS_PduR_00765], SWS PduR p. 86

Fonctionnement en passerelle entre réseaux : mise en tampon, FIFO et On-the-fly

Entre interfaces, le PduR prend en charge le gatewaying 1:n [SWS_PduR_00436]. Il transmet immédiatement les I-PDU et ne génère pas de cycles d'émission propres [SWS_PduR_00437]. Une I-PDU n'est routée qu'entre interfaces ou qu'entre modules TP, jamais de manière mixte [SWS_PduR_00638]. Le fait que le PduR mette en tampon dépend de la mise à disposition des données de la destination :

  • Avec PDUR_DIRECT, l'interface de destination copie déjà les données dans l'appel Transmit [SWS_PduR_00303].
  • Avec PDUR_TRIGGERTRANSMIT, le PduR met l'I-PDU en tampon jusqu'à l'appel TriggerTransmit [SWS_PduR_00306].

Sans mise en tampon, le PduR transmet la plus petite des deux longueurs, longueur de réception ou longueur de destination [SWS_PduR_00783]. Avec mise en tampon, il copie au maximum PduRPduMaxLength [SWS_PduR_00746].

Une FIFO peut être configurée pour chaque I-PDU de destination [SWS_PduR_00307]. À partir de PduRQueueDepth > 1, le tampon se comporte comme une FIFO [SWS_PduR_00785], et les nouvelles I-PDU sont ajoutées à la fin [SWS_PduR_00787]. En cas de mise à disposition directe, la règle suivante s'applique : si la FIFO est vide et qu'aucune confirmation n'est en attente, le PduR émet immédiatement [SWS_PduR_00665]. Sinon, il met l'I-PDU en file d'attente [SWS_PduR_00793] et l'émet après la prochaine confirmation [SWS_PduR_00667]. En cas de Trigger-Transmit, le PduR copie l'entrée la plus ancienne et la supprime ; s'il reste ensuite du contenu, il appelle de nouveau <DstLo>_Transmit [SWS_PduR_00666]. Si la FIFO est vide, la récupération renvoie E_NOT_OK [SWS_PduR_00662].

Diagramme d'activité : Dans une passerelle d'interface, la mise à disposition des données et l'état de la FIFO déterminent si le PduR émet immédiatement, met en file d'attente ou attend TriggerTransmit. Sources : [SWS_PduR_00665], [SWS_PduR_00786], [SWS_PduR_00255], SWS PduR p. 112

Les passerelles TP fonctionnent dans l'un de deux modes :

  • Direct : Le PduR n'appelle <DstLoTp>_Transmit qu'après une indication de réception réussie [SWS_PduR_00551].
  • On-the-fly : La retransmission commence dès que PduRTpThreshold est atteint [SWS_PduR_00317]. Ce mode n'est autorisé qu'avec exactement un module TP de destination [SWS_PduR_00708], SWS PduR p. 58.

Si TpSduLength tient dans le tampon dédié, le PduR utilise celui-ci ; sinon, il récupère dynamiquement un tampon depuis PduRTxBuffer [SWS_PduR_00797], [SWS_PduR_00798]. Il transmet les MetaData à la destination [SWS_PduR_00794]. Si un récepteur local est en outre configuré, le PduR démarre après une réception réussie une session de réception propre auprès de ce module [SWS_PduR_00789].

Diagramme de séquence : Dans la passerelle On-the-fly, la réception sur CAN1 et l'émission sur CAN2 se chevauchent dès que le seuil est atteint. Sources : [SWS_PduR_00317], [SWS_PduR_00708], [SWS_PduR_00518], SWS PduR p. 100

Commuter des groupes de chemins de routage au moment de l'exécution

Les conteneurs PduRRoutingPathGroup regroupent les chemins d'un réseau ou d'un type de PDU SWS PduR p. 131. Ils sont adressés via PduR_RoutingPathGroupIdType, un uint16 [SWS_PduR_00654]. Ils sont commutés avec PduR_EnableRouting et PduR_DisableRouting [SWS_PduR_00615], [SWS_PduR_00617]. Le paramètre initialize détermine si les tampons individuels sont réinitialisés à la valeur par défaut ou conservés [SWS_PduR_00617]. L'activation a un effet immédiat [SWS_PduR_00715]. Si une API utilise l'ID d'I-PDU d'un chemin désactivé, le PduR renvoie E_NOT_OK sans autre action, dans la mesure où le type de retour le permet [SWS_PduR_00717]. Cela s'applique expressément aussi aux fonctions d'annulation [SWS_PduR_00710], [SWS_PduR_00726].

L'appelant typique est BswM via l'action BswMPduRouterControl SWS BswM p. 166. Le guide de gestion de mode mentionne deux cas d'application : les I-PDU sans groupe d'I-PDU Com, par exemple via LdCom, et la commutation en fonction de l'état PNC que ComM signale à BswM Mode-Management-Guide p. 50. Des versions ultérieures précisent la façon dont les chemins avec plusieurs groupes sont réévalués SWS PduR p. 69. Ces règles ne font pas partie des exigences R20-11 présentées ici.

Diagramme de séquence : BswM désactive un groupe de chemins de routage ; les appels d'émission sur les chemins concernés échouent jusqu'à ce que le groupe soit réactivé. Sources : [SWS_PduR_00617], [SWS_PduR_00717], [SWS_PduR_00715], Mode-Management-Guide p. 50

Comportement en cas d'erreur

Si PduRDevErrorDetect est actif, le PduR signale les erreurs de développement au DET [SWS_PduR_00100], SWS PduR p. 72 :

  • PDUR_E_INIT_FAILED en cas de pointeur de configuration non valide [SWS_PduR_00100].
  • PDUR_E_UNINIT en cas d'appels avant l'initialisation, à l'exception de PduR_Init et PduR_GetVersionInfo [SWS_PduR_00119], et pour PduR_Init en dehors de PDUR_UNINIT [SWS_PduR_00100].
  • PDUR_E_PDU_ID_INVALID en cas d'ID de PDU non valide [SWS_PduR_00221].
  • PDUR_E_PARAM_POINTER en cas de pointeurs nuls [SWS_PduR_00100].
  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID en cas d'ID de groupe inconnu [SWS_PduR_00648], [SWS_PduR_00649]. La fonction de commutation elle-même retourne dans ce cas sans effet [SWS_PduR_00647], [SWS_PduR_00716].

Le PduR ne signale pas d'erreurs de production SWS PduR p. 60.

Si des instances d'I-PDU sont perdues, le PduR signale l'erreur d'exécution PDUR_E_PDU_INSTANCES_LOST. Cette erreur a été introduite avec AUTOSAR 4.3.1 SWS PduR p. 3 ; elle est signalée via Det_ReportRuntimeError [SWS_PduR_91001]. Deux situations la déclenchent :

  • La FIFO est pleine : le PduR la vide et traite la nouvelle I-PDU comme si la FIFO était vide [SWS_PduR_00255], [SWS_PduR_00669], [SWS_PduR_00670].
  • <DstLo>_Transmit renvoie E_NOT_OK : le PduR rejette l'instance et transmet la suivante [SWS_PduR_00788], [SWS_PduR_00807].

Interprétation : La désactivation d'un groupe devrait être considérée comme un « arrêt » au sens de [SWS_PduR_00663] ; les FIFO associées seraient alors également vidées.

Le PduR ne répète pas les émissions de passerelle ayant échoué [SWS_PduR_00256]. Lors d'émissions locales avec une seule destination, le module supérieur reçoit la valeur de retour de la destination [SWS_PduR_00626], [SWS_PduR_00700]. En présence de plusieurs destinations, [SWS_PduR_00701] exige que toutes les destinations renvoient E_OK ; cela concerne probablement le chemin d'émission TP, alors qu'un seul succès suffit pour le multicast d'interface selon [SWS_PduR_00218].

Pour la réception TP et les passerelles TP, ce qui suit s'applique :

  • Le PduR ne fait que relayer localement les indications de réception TP erronées [SWS_PduR_00207] ; dans la passerelle, elles mettent fin au traitement [SWS_PduR_00689].
  • Si une passerelle On-the-fly ne peut pas mémoriser les données, le PduR renvoie BUFREQ_E_NOT_OK [SWS_PduR_00687]. Si un tampon manque totalement, il renvoie BUFREQ_E_OVFL [SWS_PduR_00799].
  • Si une destination tombe en panne, les autres continuent [SWS_PduR_00803], [SWS_PduR_00806]. Ce n'est que lorsque toutes les destinations TP échouent que le PduR met fin au côté réception [SWS_PduR_00804].
  • En cas d'erreur, le PduR interrompt les récepteurs TP locaux dans la passerelle ou les indique avec E_NOT_OK [SWS_PduR_00790], [SWS_PduR_00791], [SWS_PduR_00792].

Utilisation

La fonction synchrone PduR_EnableRouting sert à activer un groupe de chemins de routage ([SWS_PduR_00615]). Le groupe de chemins de routage respectif, préalablement défini dans la configuration du routeur de PDU ([SWS_PduR_00615]), est adressé via le paramètre d’entrée id de type PduR_RoutingPathGroupIdType. Le service ne renvoie aucune valeur de retour (void) et est déclaré avec le service ID 0xf3 via le fichier d’en-tête PduR.h ([SWS_PduR_00615]).

Gestion des erreurs

Concernant les états d’erreur possibles, les codes d’erreur suivants sont spécifiés pour PduR_EnableRouting ([SWS_PduR_00100]) :

  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (0x08) : est constaté lorsqu’une table de routage ou un ID de groupe de chemins de routage non valide est transmis(e) à la fonction ([SWS_PduR_00100]).
  • PDUR_E_UNINIT (0x01) : survient lorsque ce service API est appelé avant l’initialisation réussie du module du routeur de PDU ([SWS_PduR_00100]).

Concurrence et restrictions

La fonction est spécifiée comme réentrante ([SWS_PduR_00615]).

Utilisation

La fonction synchrone PduR_DisableRouting ([SWS_PduR_00617]) sert à désactiver un groupe de chemins de routage (Routing Path Group) dans le routeur de PDU. Elle ne possède aucune valeur de retour (void) et est mise à disposition via l’en-tête PduR.h.

Lors de l’appel, la fonction attend deux paramètres d’entrée :

  • id : identifie le groupe de chemins de routage à désactiver, tel qu’il est défini dans la configuration du routeur de PDU.
  • initialize : commande le traitement des tampons uniques (Single Buffers). Lors de la transmission de true, ces tampons sont initialisés à leur valeur par défaut ; avec false, le contenu actuel du tampon est conservé.

Concurrence et restrictions

Selon [SWS_PduR_00617], la fonction est spécifiée comme réentrante. Pour un appel valide, le module PduR doit avoir été préalablement initialisé.

Traitement des erreurs et interaction

Concernant le traitement des erreurs, il existe des liens directs avec [SWS_PduR_00100] :

  • Si la fonction est appelée sans que le module ne soit initialisé, cela concerne l’erreur PDUR_E_UNINIT (valeur d’erreur 0x01).
  • Si une table de routage ou un ID de groupe non valide est transmis(e) à PduR_DisableRouting, le code d’erreur PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (valeur d’erreur 0x08) est prévu.

Le type énuméré PduR_StateType décrit les états du PDU Router ([SWS_PduR_00742]). Il est disponible via l'en-tête PduR.h et définit le cycle de vie fondamental du module.

Conformément à [SWS_PduR_00324], le module PDU Router se compose d'exactement deux états, qui sont représentés par les valeurs du type :

  • PDUR_UNINIT : le PDU Router n'est pas initialisé ([SWS_PduR_00742], [SWS_PduR_00324]).
  • PDUR_ONLINE : le PDU Router a été initialisé avec succès ([SWS_PduR_00742], [SWS_PduR_00324]).

Dans l'interaction, ce type sert de base d'état pour le PDU Router, le passage à PDUR_ONLINE indiquant l'achèvement réussi de l'initialisation du module, tandis que PDUR_UNINIT représente l'état avant ou après la sortie du fonctionnement opérationnel.
