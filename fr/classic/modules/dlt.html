Rôle : point de collecte entre les sources de log et le PDU Router

Le module Dlt reçoit les messages de log et de trace provenant des composants logiciels et des modules BSW, puis les transmet sous forme de messages Dlt à un client externe. Les interfaces centrales pour cela sont Dlt_SendLogMessage et Dlt_SendTraceMessage [SWS_Dlt_00241] [SWS_Dlt_00243]. Au début du chemin de données se trouve une SW-C ou un module BSW, et à la fin le PDU Router SWS Dlt p. 26. L'envoi s'effectue exclusivement via PduR_DltTransmit [SWS_Dlt_00762]. La spécification du protocole Log-and-Trace définit le format des messages, les commandes et le protocole vers l'outil SWS Dlt p. 9.

Les SW-C accèdent au module via deux ports RTE :

  • SwcMessageService_{SW-C} pour l'enregistrement et l'envoi [SWS_Dlt_91001],
  • ControlService_{SW-C} pour contrôler les paramètres de log [SWS_Dlt_00499].

Dans le sens inverse, Dlt notifie la SW-C via SessionControlCallback_{SW-C} [SWS_Dlt_00779] et appelle des injections via InjectCallback_{SW-C} [SWS_Dlt_00778]. D'autres sources sont le DET via Dlt_DetForwardErrorTrace [SWS_Dlt_00430] et la RTE via des hooks de trace VFB générés [SWS_Dlt_00027]. Parmi les modules sous-jacents, Dlt utilise Det_ReportError ainsi que des services de Gpt, NvM et StbM [SWS_Dlt_00763].

Démarrage : mise en mémoire tampon avant Dlt_Init, configuration issue de NvM, délai de démarrage

Dlt_Init est synchrone et non réentrante. Étant donné que Dlt utilise le NVRAM Manager, l'initialisation doit avoir lieu très tard dans la phase de démarrage et seulement après le NvM [SWS_Dlt_00239]. Selon le diagramme de séquence, l'EcuM appelle la fonction SWS Dlt p. 159. Les sources peuvent déjà journaliser avant l'initialisation. Dlt doit donc également pouvoir mettre en mémoire tampon les données issues de Dlt_SendLogMessage et Dlt_SendTraceMessage avant Dlt_Init [SWS_Dlt_00003].

Si DltGeneralNvRAMSupport est TRUE, ce qui suit s'applique :

  • Dlt_Init lit les valeurs stockées de manière persistante avec NvM_ReadBlock [SWS_Dlt_00453].
  • Dlt vérifie la validité des blocs [SWS_Dlt_00449].
  • La configuration enregistrée sert de valeur initiale [SWS_Dlt_00350].

Si le support NvRAM est désactivé, la configuration statique s'applique SWS Dlt p. 26. Les données mises en mémoire tampon intermédiaire ne sont traitées normalement que lorsque le module est initialisé et que le DltGeneralStartUpDelayTimer optionnel a expiré [SWS_Dlt_00005].

Sessions, Application-/Context-ID et enregistrement de contexte

Chaque source de message est identifiée par un Dlt_SessionIDType (uint32) [SWS_Dlt_00225] :

  • Pour les SW-C, il s'agit d'une Port Defined Argument Value [SWS_Dlt_00022]. Les valeurs commencent à 0x1000 [SWS_Dlt_00023].
  • Les modules BSW utilisent leur ID de module [SWS_Dlt_00023].
  • Chaque port raccordé à Dlt reçoit une SessionId unique, la plage de valeurs est contiguë [SWS_Dlt_00332].

Les SW-C instanciées plusieurs fois et les SW-C disposant de plusieurs ports vers Dlt ont ainsi plusieurs sessions EXP LSA p. 159. Sur le plan du contenu, un message est associé via ApplicationId et ContextId. Tous deux ont une taille de quatre octets, 0x00000000 étant la valeur générique [SWS_Dlt_00226] [SWS_Dlt_00227].

Avec Dlt_RegisterContext, une source déclare un tuple composé d'ApplicationId et de ContextId avec leurs descriptions [SWS_Dlt_00245]. Dlt mémorise par quel port le tuple a été enregistré [SWS_Dlt_00021], et gère pour chaque tuple un niveau de log et un état de trace SWS Dlt p. 20. Si un module logiciel est arrêté, il appelle Dlt_UnregisterContext [SWS_Dlt_00769]. Dlt supprime alors le tuple et ne le notifie plus des modifications. Si DltGeneralRegisterContextNotification est actif, Dlt signale en outre le désenregistrement par Dlt_GetLogInfo avec le statut 5 SWS Dlt p. 21.

De l'appel d'envoi à la PDU : filtres, LogChannels et transmission découplée

Les API d'envoi sont synchrones et réentrantes [SWS_Dlt_00241] [SWS_Dlt_00243]. En plus des données utiles, elles reçoivent une structure d'informations :

  • Dlt_MessageLogInfoType avec argCount, logLevel, options, contextId et appId [SWS_Dlt_00236],
  • Dlt_MessageTraceInfoType, qui contient un type de trace au lieu du niveau de log [SWS_Dlt_00237].

Toujours dans le contexte de l'appelant, le message passe successivement par l'horodatage, le filtre de niveau de log/d'état de trace, la sélection de canal, la vérification de longueur, le seuil de canal et la mise en mémoire tampon SWS Dlt p. 23 SWS Dlt p. 92.

Pour la sélection du canal, Dlt collecte dans cet ordre SWS Dlt p. 32 :

  1. tous les LogChannels avec un tuple correspondant exactement,
  2. tous les LogChannels avec une ApplicationId correspondante et une ContextId générique,
  3. le LogChannel par défaut si la liste est encore vide après cela.

Les associations peuvent être modifiées à l'exécution avec Dlt_SetLogChannelAssignment [SWS_Dlt_00751]. Dlt_AssignmentOperation code en R20-11 DLT_ASSIGN_ADD sous la valeur 0x01 et DLT_ASSIGN_REMOVE sous la valeur 0x02 [SWS_Dlt_00730]. Des versions ultérieures attribuent en revanche la valeur 0x00 à DLT_ASSIGN_REMOVE SWS Dlt p. 87. Un message n'est rejeté avec DLT_E_MSG_TOO_LARGE que s'il est trop long pour tous les canaux assignés SWS Dlt p. 31.

Diagramme d'activité : étapes de traitement dans le contexte de l'appelant et emplacements où un message est rejeté. Sources : SWS Dlt p. 23 SWS Dlt p. 32 SWS Dlt p. 31 SWS Dlt p. 32

L'envoi proprement dit est découplé de l'appel d'API et s'effectue dans le contexte de Dlt_TxFunction [SWS_Dlt_91005]. Ce découplage maintient un temps de blocage court pour les appelants et permet le traffic shaping ainsi que les réémissions. L'en-tête est assemblé avant PduR_DltTransmit, et chaque tentative d'envoi incrémente un compteur d'envoi du message SWS Dlt p. 35. Dlt ne récupère un horodatage que si DltHeaderUseTimestamp = TRUE, et ce via Gpt_GetTimeElapsed [SWS_Dlt_00654] ou StbM_GetCurrentTime [SWS_Dlt_00655].

Un message est retiré du tampon de canal lorsque l'un des cas suivants se produit SWS Dlt p. 38 :

  • PduR_DltTransmit renvoie E_NOT_OK.
  • Une Dlt_TxConfirmation positive arrive [SWS_Dlt_00273].
  • Après une confirmation négative, le nombre de répétitions configuré est dépassé.

Pour les canaux basés sur TP, Dlt_CopyTxData [SWS_Dlt_00516] et Dlt_TpTxConfirmation [SWS_Dlt_00756] devraient compléter ce déroulement. Dlt_TriggerTransmit [SWS_Dlt_00754] dessert vraisemblablement des PDU pilotées par trigger.

Types de messages, champs d'en-tête et sources fixes (DET, DEM, trace VFB)

Dlt_MessageType distingue les messages de log, de trace applicative, de trace réseau et de contrôle [SWS_Dlt_00224]. Dans l'Extended Header, Dlt définit le champ MSTP sur 0x0 pour Dlt_SendLogMessage et sur 0x1 pour Dlt_SendTraceMessage. Le champ MTIN découle de la structure d'informations transmise SWS Dlt p. 35, c'est-à-dire de l'un de ces types PRS LT p. 24 :

  • Dlt_MessageLogLevelType [SWS_Dlt_00230],
  • Dlt_MessageTraceType [SWS_Dlt_00231],
  • Dlt_MessageNetworkTraceInfoType en cas de trace réseau [SWS_Dlt_00233].

Le bit 0 de Dlt_MessageOptionsType indique le mode Verbose [SWS_Dlt_00229]. En mode Non-Verbose, un Message ID de 4 octets porte la signification statique du message [SWS_Dlt_00228]. Le payload ne contient alors que le Message ID et les données non statiques PRS LT p. 23.

Pour les erreurs DET, Dlt fournit Dlt_DetForwardErrorTrace en R20-11 [SWS_Dlt_00432]. Ces messages portent l'ApplicationId « DET » et la ContextId « STD » [SWS_Dlt_00376]. Cette fonction a été supprimée avec R25-11 SWS Dlt p. 1. Les événements DEM utilisent « DEM »/« STD0 » et le Message ID 0x00000001 [SWS_Dlt_00377]. Les Message ID 0x00000001 à 0x00000003 sont réservés aux messages DEM, DET et de trace [SWS_Dlt_00031].

Pour la trace VFB, Dlt met à disposition une fonction de hook pour chaque événement RTE configuré. Son prototype provient du BswModuleEntry de la RTE [SWS_Dlt_00027] [SWS_Dlt_00335]. Déroulement au sein de chaque hook :

  1. Le hook vérifie l'état de trace de sa ContextId [SWS_Dlt_00281].
  2. Il appelle un équivalent interne de Dlt_SendTraceMessage [SWS_Dlt_00285], et ce en mode Non-Verbose [SWS_Dlt_00277].
  3. Le payload contient tous les arguments du hook [SWS_Dlt_00278].

Chaque hook possède sa propre ContextId [SWS_Dlt_00279]. DLT_TYPE_APP_TRACE et DLT_TRACE_VFB sont définis [SWS_Dlt_00484], l'ApplicationId est « VFBT » SWS Dlt p. 23.

Diagramme de séquence : un hook de trace VFB n'émet que si l'état de trace de sa ContextId est actif. Sources : [SWS_Dlt_00281] [SWS_Dlt_00285] [SWS_Dlt_00277] [SWS_Dlt_00484] SWS Dlt p. 23

Dlt reçoit les messages de contrôle via les entrées DltRxPdu configurées SWS Dlt p. 128. Il existe deux voies pour cela :

  • Dlt_RxIndication [SWS_Dlt_00272],
  • les callbacks TP Dlt_StartOfReception [SWS_Dlt_91006], Dlt_CopyRxData [SWS_Dlt_91008] et Dlt_TpRxIndication [SWS_Dlt_91007].

Comportement en cas d'erreur

Les API d'envoi signalent les problèmes via leurs valeurs de retour [SWS_Dlt_00495] [SWS_Dlt_00241] :

  • DLT_E_UNKNOWN_SESSION_ID : la session est inconnue.
  • DLT_E_MSG_TOO_LARGE : le message est trop long pour tous les canaux assignés.
  • DLT_E_NO_BUFFER : l'espace de mémoire tampon est insuffisant.

Si le tampon est plein, le message est rejeté, un drapeau d'overflow est positionné pour le tampon de canal et, selon la configuration, le message de contrôle « BufferOverflowNotification » est envoyé SWS Dlt p. 32 SWS Dlt p. 95. En plus de Dlt_GetLogInfo, il s'agit de la seule commande que Dlt envoie de sa propre initiative SWS Dlt p. 44. Dlt répond aux erreurs lors de l'enregistrement par DLT_E_CONTEXT_ALREADY_REG ou DLT_E_CONTEXT_NOT_YET_REG [SWS_Dlt_00495].

R20-11 définit les codes d'erreur suivants :

  • Erreurs de développement : DLT_E_PARAM, DLT_E_PARAM_POINTER, DLT_E_INIT_FAILED, DLT_E_REGISTRATION [SWS_Dlt_00727].
  • Erreurs d'exécution : DLT_E_SKIPPED_TRANSMISSION, DLT_E_DEPRECATED_PARAMETER, DLT_E_MULTIPLE_REQUESTS [SWS_Dlt_00728].

Les commandes de contrôle pour un uplet inconnu reçoivent pour réponse DLT_E_ERROR SWS Dlt p. 39. Le service de contrôle connaît en outre DLT_E_NOT_SUPPORTED [SWS_Dlt_00772]. Si la source temporelle ne fournit aucune valeur, l'horodatage est défini à 0x00000000 SWS Dlt p. 30. Les transmissions ayant échoué sont réessayées jusqu'au nombre maximal configuré SWS Dlt p. 38.

La fonction synchrone et réentrante Dlt_SendTraceMessage ([SWS_Dlt_00243]) sert aux modules de logiciel de base (BSW) ainsi qu'aux composants logiciels (SW-C) pour la transmission de paramètres de trace. Elle est disponible via le fichier d'en-tête Dlt.h.

Paramètres et transmission

  • sessionId : identifiant de module (ID de module au sein de la BSW ou valeur d'argument définie par le port au sein d'un SW-C).
  • traceInfo : pointeur vers une structure (Dlt_MessageTraceInfoType) contenant les informations requises pour le filtrage des messages.
  • traceData : pointeur vers le tampon contenant les paramètres à tracer, qui constituent la charge utile du message de trace.
  • traceDataLength : longueur du tampon de données transmis en octets.
