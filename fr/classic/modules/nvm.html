Gère les blocs de données non volatiles et les synchronise de manière asynchrone entre la RAM et la mémoire NV.

Le NVRAM Manager (NvM) est le seul point d'accès à la mémoire non volatile. Il copie implicitement les blocs NVRAM entre la RAM et la mémoire NV [SWS_NvM_00038]. Au démarrage, NvM_ReadAll déclenché par le BswM remplit les blocs RAM ; lors de l'arrêt, NvM_WriteAll sauvegarde les blocs modifiés. Les requêtes individuelles telles que NvM_WriteBlock sont mises en file d'attente de manière asynchrone, traitées par ordre de priorité et acquittées par statut ou rappel [SWS_NvM_00185]. Le NvM intercepte les erreurs de lecture via des répétitions, des copies redondantes et des données par défaut ; les utilisateurs doivent néanmoins vérifier eux-mêmes l'état des blocs.

Le NVRAM Manager (NvM) constitue le seul point d'accès à la mémoire non volatile [SWS_NvM_00384]. Il copie implicitement les blocs entre la NVRAM et la RAM ; l'application travaille directement avec les données en RAM [SWS_NvM_00038]. Vers le bas, il utilise la Memory Abstraction Interface avec la Fee ou l'Ea [SWS_NvM_00051]. Il signale les états au BswM, et les erreurs au DEM et au DET [SWS_NvM_00745] [SWS_NvM_00592].

Diagramme de contexte : intégration du NvM entre les utilisateurs, le BswM, MemIf/Fee/Ea ainsi que le DEM et le DET. Sources : [SWS_NvM_00384] [SWS_NvM_00465] [SWS_NvM_00746]

Chaque bloc NVRAM se compose d'un bloc NV, d'un bloc RAM et d'un Administrative Block, complétés en option par un bloc ROM contenant des données par défaut [SWS_NvM_00138]. Il existe les types Native, Redundant et Dataset ; ils diffèrent par le nombre de blocs NV et ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559]. Le NvM synchronise le bloc RAM implicitement de façon directe ou explicitement via un miroir RAM avec des rappels [SWS_NvM_00511].

Le cycle de vie se déroule en trois étapes :

  • Le BswM appelle NvM_Init de manière exclusive [SWS_NvM_00693].
  • NvM_ReadAll vérifie d'abord l'ID de configuration, puis remplit les blocs RAM [SWS_NvM_00073] [SWS_NvM_00718].
  • Lors de l'arrêt, NvM_WriteAll sauvegarde les blocs modifiés [SWS_NvM_00092]. NvM_CancelWriteAll effectue une interruption non destructive [SWS_NvM_00238].

Les requêtes individuelles telles que NvM_WriteBlock sont mises en file d'attente et passent ensuite à NVM_REQ_PENDING [SWS_NvM_00185]. En option, le NvM utilise une file d'attente propre pour les requêtes immédiates [SWS_NvM_00378]. Le résultat est fourni par NvM_GetErrorStatus ou par un rappel configuré [SWS_NvM_00015] [SWS_NvM_00740].

Diagramme de séquence : une requête d'écriture asynchrone est mise en file d'attente, traitée dans NvM_MainFunction et acquittée par rappel, notification au BswM et interrogation de statut. Sources : [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00891], SWS NvM p. 160

Le NvM intercepte les erreurs de lecture selon trois niveaux :

  • les répétitions de lecture configurées [SWS_NvM_00526],
  • la seconde copie des blocs redondants [SWS_NvM_00199],
  • les données par défaut avec le résultat NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202].

Interprétation : l'ordre des niveaux devrait suivre l'énumération figurant dans l'Error Description. Le NvM répète les erreurs d'écriture jusqu'à NVM_MAX_NUM_OF_WRITE_RETRIES et signale ensuite NVM_E_REQ_FAILED au DEM [SWS_NvM_00684]. Les utilisateurs vérifient eux-mêmes le statut de leurs blocs [SWS_NvM_00694].

Rôle dans la pile de mémoire : unique point d'accès à la mémoire non volatile

Le NVRAM Manager (NvM) centralise l'accès aux données non volatiles. L'environnement s'adresse à la mémoire non volatile exclusivement via le NvM, qui met à disposition pour cela une interface de rappel [SWS_NvM_00384]. L'accès est implicite : le NvM copie les blocs entre la NVRAM et la RAM partagée. L'application travaille directement avec les données en RAM, en respectant les règles de synchronisation [SWS_NvM_00038] [SWS_NvM_00692]. Un bloc est sélectionné via son ID de bloc configuré [SWS_NvM_00069] [SWS_NvM_00471]. Pour cela, les couches supérieures intègrent uniquement NvM.h [SWS_NvM_00691]. Le schéma relatif à la mise à jour implicite illustre la répartition du travail : d'autres parties du logiciel de base déclenchent la sauvegarde et la restauration de tous les blocs en fonction de l'état de l'ECU. La SW-C accède uniquement au contenu de ses blocs RAM (SWS NvM p. 121).

Vers le bas, le NvM fonctionne avec la Memory Abstraction Interface. Conjointement avec la Fee ou l'Ea, elle met à disposition un espace d'adressage linéaire virtuel de 32 bits [SWS_NvM_00051] [SWS_NvM_00465]. Le NvM calcule les sommes de contrôle via le module Crc [SWS_NvM_00466]. Il apprend la fin d'une tâche de couche inférieure par deux moyens :

  • par interrogation périodique (polling) via MemIf_GetJobResult,
  • lorsque le polling est désactivé, via NvM_JobEndNotification et NvM_JobErrorNotification [SWS_NvM_00440] [SWS_NvM_00441] (Error Description p. 43).

Les erreurs de production sont transmises au DEM [SWS_NvM_00592], les erreurs de développement au DET [SWS_NvM_00614]. Le NvM signale les états des requêtes au BswM [SWS_NvM_00745] [SWS_NvM_00746].

Structure d'un bloc NVRAM et les trois types de gestion

Un bloc NVRAM se compose des éléments obligatoires bloc NV, bloc RAM et Administrative Block. Un bloc ROM contenant des données par défaut est optionnel [SWS_NvM_00138] [SWS_NvM_00139] [SWS_NvM_00020]. La composition est définie au moment de la configuration par le descripteur de bloc [SWS_NvM_00140]. Les différents composants :

  • Le bloc NV contient les données utiles ainsi que, de manière optionnelle, le CRC et l'en-tête [SWS_NvM_00125] (SWS NvM p. 39).
  • Le bloc RAM peut être situé dans la RAM globale sans restriction d'adresse [SWS_NvM_00088].
  • L'Administrative Block est invisible pour l'application. Il conserve l'index de jeu de données, les attributs et le champ d'erreur/statut [SWS_NvM_00134] [SWS_NvM_00135] [SWS_NvM_00136].

Le NvM prend en charge les types NVM_BLOCK_NATIVE, NVM_BLOCK_REDUNDANT et NVM_BLOCK_DATASET [SWS_NvM_00137]. Ils se distinguent par le nombre de blocs NV et ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559] (SWS NvM p. 10). Pour les blocs de type Dataset :

  • NvM_SetDataIndex sélectionne l'élément. Les index à partir de NvMNvBlockNum adressent les blocs ROM [SWS_NvM_00014] [SWS_NvM_00445] (NV Data Handling p. 10).
  • L'index n'est pas enregistré de manière persistante ; NvM_Init le réinitialise à zéro [SWS_NvM_00160] [SWS_NvM_00192].
  • La SW-C est responsable de la définition correcte [SWS_NvM_00695].

Cycle de vie : NvM_Init, NvM_ReadAll et NvM_WriteAll

Le BswM appelle NvM_Init de manière exclusive [SWS_NvM_00693]. NvM_Init réinitialise les files d'attente et les machines à états et signale en interne « INIT DONE » [SWS_NvM_00399]. Il n'initialise ni les blocs RAM ni les modules sous-jacents [SWS_NvM_00091] [SWS_NvM_00193]. Le pointeur de configuration est toujours NULL_PTR [SWS_NvM_00881]. Ce n'est qu'après cela que NvM_MainFunction traite les requêtes [SWS_NvM_00257].

NvM_ReadAll remplit ensuite les blocs RAM [SWS_NvM_00718]. L'appel ne fait que notifier la requête. Le traitement est différé jusqu'à ce que les requêtes de blocs individuels soient achevées [SWS_NvM_00243]. La tâche s'exécute ensuite en trois étapes :

  1. D'abord, elle compare l'ID de configuration enregistré avec celui compilé [SWS_NvM_00073]. En cas de divergence, le comportement dépend de NvMDynamicConfiguration : avec NvMDynamicConfiguration == FALSE, la divergence est ignorée [SWS_NvM_00248]. Sinon, les blocs non résistants aux modifications reçoivent des données par défaut [SWS_NvM_00249] [SWS_NvM_00674] (NV Data Handling p. 15).
  2. Ensuite, elle effectue une itération sur les blocs utilisateur à l'exception des ID de bloc 0 et 1 [SWS_NvM_00244]. Ce faisant, elle ne traite que les blocs avec un bloc RAM permanent ou une synchronisation explicite [SWS_NvM_00118].
  3. Pour finir, elle positionne le résultat global sur NVM_REQ_OK ou NVM_REQ_NOT_OK [SWS_NvM_00895] [SWS_NvM_00301].

Dans l'exemple de gestion des modes, la règle du BswM NvMReadAllFinished ne démarre le reste de l'initialisation qu'après l'achèvement de NvM_ReadAll (Mode Management Guide p. 31).

Diagramme de séquence : démarrage asynchrone avec NvM_Init, NvM_ReadAll et retour de l'état multibloc au BswM. Sources : [SWS_NvM_00693] [SWS_NvM_00243] [SWS_NvM_00073] [SWS_NvM_00888] [SWS_NvM_00889], NV Data Handling p. 20

Lors de l'arrêt, le BswM appelle NvM_WriteAll [SWS_NvM_00092]. La tâche se comporte comme suit :

  • Elle écrit les blocs RAM permanents ou récupère les données synchronisées de manière explicite via NvM_WriteRamBlockToNvm [SWS_NvM_00252].
  • Elle vérifie préalablement l'état « valid/modified » [SWS_NvM_00682].
  • Elle ignore les blocs protégés et verrouillés sans émettre de message d'erreur [SWS_NvM_00434] [SWS_NvM_00750].
  • Les autres requêtes ne l'interrompent pas [SWS_NvM_00567].

Les utilisateurs marquent les blocs modifiés avec NvM_SetRamBlockStatus(…, TRUE), pour autant que l'API soit activée [SWS_NvM_00406] [SWS_NvM_00408]. Pour les blocs à Dirty Flag, la RTE prend en charge cet appel (NV Data Handling p. 41).

NvM_CancelWriteAll est réservé au BswM [SWS_NvM_00703] et reste sans effet si NvM_WriteAll n'est pas en cours d'exécution [SWS_NvM_00233]. Le bloc en cours est conclu de façon non destructive [SWS_NvM_00238]. Les blocs restants et le résultat multibloc reçoivent NVM_REQ_CANCELED [SWS_NvM_00236] [SWS_NvM_00237] (SWS NvM p. 161).

Deux autres requêtes multiblocs complètent le cycle de vie :

  • NvM_ValidateAll positionne les blocs avec validation automatique à « VALID / CHANGED » [SWS_NvM_00856].
  • NvM_FirstInitAll écrit des données par défaut dans les blocs ou les invalide si aucune donnée n'est présente [SWS_NvM_00913] [SWS_NvM_00919].

Une longueur de file d'attente de un s'applique à toutes les requêtes multiblocs [SWS_NvM_00380].

Diagramme de séquence : arrêt avec NvM_WriteAll et interruption optionnelle par NvM_CancelWriteAll. Sources : [SWS_NvM_00092] [SWS_NvM_00682] [SWS_NvM_00238] [SWS_NvM_00237] [SWS_NvM_00889], Mode Management Guide p. 37

Requêtes individuelles : files d'attente, priorités et retours d'information

Les requêtes de bloc individuel telles que NvM_ReadBlock, NvM_WriteBlock ou NvM_RestoreBlockDefaults sont asynchrones. La fonction prend en charge les paramètres, met la requête en file d'attente et retourne [SWS_NvM_00195] [SWS_NvM_00208] [SWS_NvM_00224]. Ensuite, le résultat de bloc est positionné sur NVM_REQ_PENDING [SWS_NvM_00185]. En cas de dépassement de la file d'attente, la fonction retourne E_NOT_OK [SWS_NvM_00184]. Un bloc n'est mis en file d'attente que s'il n'est pas déjà en attente ou en cours de traitement [SWS_NvM_00385].

D'autres services agissent de manière synchrone dans le contexte de l'appelant, par exemple NvM_SetDataIndex [SWS_NvM_00448] et NvM_GetErrorStatus (SWS NvM p. 158). NvM_CancelJobs retire les requêtes en attente d'un bloc ; une tâche en cours d'exécution est toutefois poursuivie [SWS_NvM_00536] [SWS_NvM_00537].

Le traitement s'effectue de manière sérialisée selon la priorité [SWS_NvM_00162]. Si NvMJobPrioritization est actif, le NvM utilise deux files d'attente, dont une pour les requêtes d'écriture immédiates (données de crash) [SWS_NvM_00564] [SWS_NvM_00378]. Une telle requête NvM_WriteBlock interrompt de manière destructive une tâche en attente [SWS_NvM_00300]. NvM_MainFunction redémarre ensuite la tâche interrompue [SWS_NvM_00258]. Sans priorisation, le NvM opère dans l'ordre d'arrivée, sans tâches immédiates [SWS_NvM_00379]. Les requêtes qui parviennent pendant une requête multibloc sont mises en file d'attente et exécutées ensuite [SWS_NvM_00568] [SWS_NvM_00569].

Chaque requête asynchrone consigne son résultat dans le champ d'erreur/statut [SWS_NvM_00175]. NvM_GetErrorStatus lit ce champ [SWS_NvM_00015]. En outre, il existe deux voies de notification optionnelles :

  • Si un rappel est configuré, NvM_MainFunction appelle NvM_SingleBlockCallbackFunction [SWS_NvM_00740] [SWS_NvM_00347]. Sans rappel, il n'y a pas de notification asynchrone [SWS_NvM_00742] (SWS NvM p. 160).
  • Avec NvMBswMBlockStatusInformation, le NvM signale l'acceptation et le résultat au BswM [SWS_NvM_00890] [SWS_NvM_00891] (SWS NvM p. 162).

Diagramme de séquence : requête d'écriture asynchrone avec notifications de statut au BswM, rappel et interrogation de statut. Sources : [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00740] [SWS_NvM_00890] [SWS_NvM_00891], SWS NvM p. 160

Synchronisation du bloc RAM et état du bloc

Le NvM connaît deux modes pour synchroniser les données avec le bloc RAM de l'application. Lors de la synchronisation implicite, il travaille directement sur ce bloc RAM. L'application met le bloc à disposition et n'y accède plus jusqu'à la fin de la requête [SWS_NvM_00698] [SWS_NvM_00699]. Si elle transmet NULL_PTR, le NvM utilise le bloc RAM permanent [SWS_NvM_00898] [SWS_NvM_00900]. Un bloc temporaire par pointeur reste néanmoins possible [SWS_NvM_00278]. Les services PRAM opèrent toujours sur le bloc RAM permanent [SWS_NvM_00765] [SWS_NvM_00794]. Dans le scénario RTE, ce bloc est une Per-Instance-Memory (NV Data Handling p. 32).

En cas de synchronisation explicite (NvMBlockUseSyncMechanism), l'échange passe par un miroir RAM interne [SWS_NvM_00511]. Il n'en existe exactement qu'un seul, dimensionné d'après le plus grand bloc concerné [SWS_NvM_00513]. Le NvM appelle NvMWriteRamBlockToNvCallback ou NvMReadRamBlockFromNvCallback [SWS_NvM_00515] [SWS_NvM_00516]. Si un rappel retourne E_NOT_OK, il répète l'appel au cycle suivant, jusqu'à NvMRepeatMirrorOperations fois [SWS_NvM_00579] [SWS_NvM_00840]. Jusqu'au rappel, l'application est encore autorisée à modifier le bloc RAM [SWS_NvM_00705]. Un bloc utilise soit la synchronisation explicite, soit un bloc RAM permanent, mais pas les deux [SWS_NvM_00904]. Le mécanisme permet des blocs partagés via un NvBlockSwComponentType (NV Data Handling p. 12).

Diagramme de séquence : requête d'écriture avec synchronisation explicite via le miroir RAM, y compris la répétition en cas de E_NOT_OK. Sources : [SWS_NvM_00515] [SWS_NvM_00705] [SWS_NvM_00579] [SWS_NvM_00840], NV Data Handling p. 27

Pour les blocs RAM permanents ou le miroir, le NvM gère un état « valid »/« invalid » [SWS_NvM_00128] [SWS_NvM_00132]. Les transitions en détail :

  • NvM_ReadBlock invalide le bloc RAM permanent dès la mise en file d'attente [SWS_NvM_00198].
  • Après une lecture réussie, il est « valid/unchanged » [SWS_NvM_00200].
  • Après le chargement de données par défaut, il est « valid/changed » [SWS_NvM_00366].
  • NvM_SetRamBlockStatus(…, TRUE) le marque comme modifié et déclenche un recalcul du CRC en arrière-plan [SWS_NvM_00406] [SWS_NvM_00121].
  • Après une écriture réussie, il est considéré comme « valid/unmodified » [SWS_NvM_00472].

Configuration, mécanismes de protection et rattachement aux partitions

Pour les ressources limitées, il existe trois classes de configuration d'API [SWS_NvM_00149]. La classe 1 ne prend pas en charge les blocs de type Dataset [SWS_NvM_00365]. Les tables de descripteurs sont générées [SWS_NvM_00143]. Les utilisateurs déclarent le besoin en mémoire au moment de la configuration [SWS_NvM_00030]. Les modules BSW le font via NvBlockNeeds (BSWMD Template p. 241). L'intégrateur ECU en déduit la configuration du NvM (Methodology p. 444).

Plusieurs mécanismes de protection sont disponibles pour les différents blocs :

  • Un champ d'attributs gère la protection en écriture [SWS_NvM_00054] ; NvMBlockWriteProt l'active par défaut [SWS_NvM_00326].
  • Les blocs avec NvMWriteBlockOnce ne sont écrits qu'une seule fois [SWS_NvM_00397]. Le NvM rejette les requêtes d'écriture avant la première lecture [SWS_NvM_00952].
  • Pour les blocs verrouillés (NvM_SetBlockLockStatus), NvM_WriteBlock fournit E_NOT_OK [SWS_NvM_00749]. Ni NvM_SetRamBlockStatus ni NvM_SetBlockProtection ne modifient le verrouillage [SWS_NvM_00754].
  • Sont en outre optionnels un en-tête Static-Block-ID [SWS_NvM_00522], une comparaison CRC pour éviter les écritures inutiles [SWS_NvM_00849] et le chiffrement via le CSM [SWS_NvM_00976].

En cas de partitionnement, le NvM appelle les interfaces dans le contexte de la partition respectivement attribuée. Les fonctions générales s'exécutent dans la partition maître [SWS_NvM_00969]. Seul le maître propose NvM_ReadAll et NvM_WriteAll [SWS_NvM_00970] [SWS_NvM_00971] [SWS_NvM_CONSTR00974]. Les SW-C accèdent au NvM via des ports liés aux blocs :

  • PS_{Block} (Service) [SWS_NvM_00847]
  • PAdmin_{Block} (Administration) [SWS_NvM_00843]
  • PM_{Block} (Miroir) [SWS_NvM_00844]
  • PNJF_{Block} (Notification de fin de tâche) [SWS_NvM_00846]

Comportement en cas d'erreur

Lors de la lecture, le NvM évalue les messages de la MemIf de différentes manières :

  • Il signale une divergence de CRC comme NVM_E_INTEGRITY_FAILED [SWS_NvM_00203].
  • Il signale MEMIF_JOB_FAILED comme NVM_E_REQ_FAILED [SWS_NvM_00654].
  • MEMIF_BLOCK_INVALID n'entraîne que NVM_REQ_NV_INVALIDATED, sans notification au DEM [SWS_NvM_00341] [SWS_NvM_00652].

Ensuite, plusieurs étapes de restauration interviennent :

  1. En cas d'erreurs de CRC, des répétitions de lecture configurées s'ensuivent [SWS_NvM_00526].
  2. Pour les blocs redondants, le NvM lit la seconde copie et tente de restaurer la redondance [SWS_NvM_00199] [SWS_NvM_00531]. En cas d'échec, il signale NVM_E_LOSS_OF_REDUNDANCY [SWS_NvM_00546].
  3. Enfin, le NvM charge des données par défaut avec le résultat NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202]. Le contenu NV reste alors inchangé [SWS_NvM_00172].

En l'absence de données par défaut, le bloc RAM reste invalide [SWS_NvM_00658] [SWS_NvM_00204]. Interprétation : l'ordre des niveaux devrait suivre l'énumération figurant dans l'Error Description (Error Description p. 62). Cette source s'écarte des exigences sur deux points. Elle mentionne NVM_REQ_RESTORED_FROM_ROM au lieu de NVM_REQ_RESTORED_DEFAULTS. De plus, elle résume l'échec définitif globalement par NVM_E_REQ_FAILED. Les exigences mentionnées ci-dessus font autorité.

Lors de l'écriture, le NvM compte les retours négatifs jusqu'à NVM_MAX_NUM_OF_WRITE_RETRIES [SWS_NvM_00213] [SWS_NvM_00216]. Si la limite est dépassée, il positionne NVM_REQ_NOT_OK et signale NVM_E_REQ_FAILED [SWS_NvM_00683] [SWS_NvM_00684] (Error Description p. 43). Deux autres cas d'erreur :

  • Si la vérification d'écriture échoue, le NvM signale NVM_E_VERIFY_FAILED et répète l'écriture [SWS_NvM_00528] [SWS_NvM_00529].
  • Un bloc redondant est considéré comme écrit dès qu'une copie a réussi [SWS_NvM_00284].
