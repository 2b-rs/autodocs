Rôle du NvM dans la pile de mémoire

Le NVRAM Manager (NvM) est le service central pour les données non volatiles de la Classic Platform. Il offre exclusivement un accès implicite : il copie des blocs entre la mémoire NV et la RAM, et l'application travaille avec les données en RAM [SWS_NvM_00038] [SWS_NvM_00692]. L'environnement ne doit accéder à la mémoire non volatile que par l'intermédiaire du NvM [SWS_NvM_00384]. Vers le bas, le NvM s'appuie sur le Memory Abstraction Interface (MemIf). Conjointement avec Flash EEPROM Emulation (Fee) ou EEPROM Abstraction (Ea), il met à disposition un espace d'adressage virtuel linéaire de 32 bits [SWS_NvM_00051]. Les couches supérieures n'intègrent que NvM.h [SWS_NvM_00691].

Selon la configuration, le NvM reçoit les résultats de la couche inférieure de deux manières. Soit Fee/Ea appellent les callbacks NvM_JobEndNotification et NvM_JobErrorNotification, soit le NvM interroge le statut du job en mode polling [SWS_NvM_00438] [SWS_NvM_00440] [SWS_NvM_00346]. Ces deux voies de détection sont également décrites par ErrorDescription p. 43. Autres modules voisins :

  • Les erreurs de production vont au DEM [SWS_NvM_00592].
  • Les erreurs de développement vont au DET [SWS_NvM_00614].
  • Les CRC sont calculés par le module Crc [SWS_NvM_00466].
  • Le NvM informe le BswM des états multiblocs et monoblocs [SWS_NvM_00745] [SWS_NvM_00746].
  • De manière optionnelle, le NvM chiffre des blocs via le CSM [SWS_NvM_00976].

Diagramme de contexte : le NvM assure l'intermédiation entre les utilisateurs et le BswM d'une part et MemIf/Fee/Ea d'autre part ; DEM, DET, Crc et CSM sont des services auxiliaires. Sources : [SWS_NvM_00051], [SWS_NvM_00438], [SWS_NvM_00745], [SWS_NvM_00976], EXP_NVDataHandling p. 8

Blocs NVRAM : structure et types de gestion

Chaque bloc NVRAM se compose de trois éléments obligatoires : bloc NV, bloc RAM et bloc administratif. Un bloc ROM est optionnel [SWS_NvM_00138] [SWS_NvM_00139]. La composition est définie au moment de la configuration par le descripteur de bloc [SWS_NvM_00140]. Les composants en détail :

  • Le bloc NV contient des données utiles ainsi que, de manière optionnelle, un CRC et un en-tête [SWS_NvM_00125].
  • Le bloc ROM fournit des données par défaut pour les blocs NV vides ou corrompus [SWS_NvM_00020].
  • Le bloc administratif réside en RAM et est invisible pour l'application. Il conserve l'index de dataset, les attributs et les informations d'erreur et d'état [SWS_NvM_00134] [SWS_NvM_00135].

Voir à ce sujet le schéma AUTOSAR_SWS_NVRAMManager p. 10.

Un bloc est adressé par son ID de bloc [SWS_NvM_00069]. NvM_BlockIdType est un uint16 ; les bits de sélection de dataset réduisent sa plage de valeurs [SWS_NvM_00471]. Deux ID sont réservés : 0 pour le résultat multibloc et 1 pour l'ID de configuration [SWS_NvM_00244].

Pour les blocs DATASET, NvM_SetDataIndex sélectionne l'élément. Les index à partir de NvMNvBlockNum renvoient à des blocs ROM [SWS_NvM_00014] [SWS_NvM_00445]. L'index n'est pas enregistré de manière persistante, et NvM_Init le réinitialise à zéro. L'utilisateur est responsable de la sélection correcte [SWS_NvM_00160] [SWS_NvM_00192] [SWS_NvM_00695] (NVDataHandling p. 10).

Démarrage : NvM_Init et NvM_ReadAll

NvM_Init est exclusivement appelée par le BswM [SWS_NvM_00693]. Le pointeur de configuration est toujours NULL_PTR [SWS_NvM_00881]. La fonction réinitialise les variables internes et signale « INIT DONE » ; ce n'est qu'ensuite que le NvM traite les demandes [SWS_NvM_00399] [SWS_NvM_00257]. Pour des raisons de temps, elle n'initialise ni les blocs NVRAM ni d'autres modules et ne modifie aucun bloc RAM permanent [SWS_NvM_00091] [SWS_NvM_00193] [SWS_NvM_00400].

Les données sont ensuite chargées par la demande multibloc NvM_ReadAll [SWS_NvM_00158]. L'appel ne fait que signaler la demande et retourne immédiatement [SWS_NvM_00243]. Il n'est disponible que dans le maître NvM [SWS_NvM_00970]. Le job se déroule selon les étapes suivantes :

  1. Il compare d'abord l'ID de configuration enregistrée avec celle compilée [SWS_NvM_00073] [SWS_NvM_00246].
  2. Si NvMDynamicConfiguration est FALSE, il ignore une divergence [SWS_NvM_00248]. Dans le cas contraire, la préparation étendue au runtime suit [SWS_NvM_00249] (NVDataHandling p. 15).
  3. Il itère ensuite sur les blocs utilisateur [SWS_NvM_00244]. Il ne traite que les blocs dotés d'un bloc RAM permanent ou d'une synchronisation explicite [SWS_NvM_00118].

Si un CRC RAM configuré est correct, le contenu de la RAM est considéré comme valide [SWS_NvM_00364]. Pour chaque bloc, le callback monobloc peut être appelé [SWS_NvM_00281]. Le résultat global est NVM_REQ_OK, ou NVM_REQ_NOT_OK dès qu'un bloc échoue [SWS_NvM_00895] [SWS_NvM_00301].

Le NvM signale l'acceptation et l'achèvement de la demande au BswM [SWS_NvM_00888] [SWS_NvM_00889]. Le BswM poursuit ensuite le démarrage, par exemple avec Rte_Start() (NVDataHandling p. 20 ; ModeManagementGuide p. 38).

Sources : [SWS_NvM_00091], [SWS_NvM_00243], [SWS_NvM_00516], [SWS_NvM_00889], NVDataHandling p. 20, AUTOSAR_SWS_NVRAMManager p. 163

Demandes monoblocs : file d'attente, priorité et retour d'information

Les services monoblocs comme NvM_ReadBlock ou NvM_WriteBlock fonctionnent de manière asynchrone. Ils prennent en charge les paramètres, mettent la demande en file d'attente et retournent [SWS_NvM_00195] [SWS_NvM_00208] [SWS_NvM_00766]. Après une mise en file d'attente réussie, le résultat est positionné sur NVM_REQ_PENDING [SWS_NvM_00185]. En cas de débordement de la file d'attente, l'appel renvoie E_NOT_OK [SWS_NvM_00184]. Un bloc n'est mis en file d'attente que s'il n'est pas déjà en attente ou en cours de traitement [SWS_NvM_00385].

Le travail proprement dit s'effectue dans NvM_MainFunction [SWS_NvM_00256]. Le NvM y extrait la demande de priorité la plus élevée et traite les demandes les unes après les autres [SWS_NvM_00155]. Les règles suivantes s'appliquent à l'ordre :

  • Avec NvMJobPrioritization, le NvM utilise deux files d'attente ; l'une d'elles est destinée aux demandes d'écriture immédiates (données de crash) [SWS_NvM_00564] [SWS_NvM_00378].
  • Les demandes immédiates interrompent de manière destructive les jobs en cours ; ceux-ci sont ensuite redémarrés [SWS_NvM_00182] [SWS_NvM_00300] [SWS_NvM_00258].
  • Sans priorisation, l'ordre d'arrivée s'applique [SWS_NvM_00379].
  • NvM_WriteAll n'est pas interrompu. Les demandes de lecture et d'écriture qui arrivent pendant une demande multibloc sont mises en file d'attente et exécutées ensuite [SWS_NvM_00567] [SWS_NvM_00568] [SWS_NvM_00569].

Le tampon RAM utilisé dépend du pointeur transmis. Avec NULL_PTR, le NvM utilise le bloc RAM permanent ou la synchronisation explicite [SWS_NvM_00898] [SWS_NvM_00899] [SWS_NvM_00900] [SWS_NvM_00901]. Une autre adresse sert de bloc RAM temporaire, même si un bloc permanent est configuré [SWS_NvM_00278] [SWS_NvM_00280]. Il existe des services PRAM dédiés pour les blocs RAM permanents [SWS_NvM_00764] [SWS_NvM_00793] (NVDataHandling p. 32).

Le résultat figure dans le champ d'erreur/d'état du bloc administratif [SWS_NvM_00175] et peut être interrogé via NvM_GetErrorStatus [SWS_NvM_00451]. Si un callback monobloc est configuré, chaque demande se termine par son appel depuis NvM_MainFunction [SWS_NvM_00740] [SWS_NvM_00347] [SWS_NvM_00467]. De plus, le BswM peut être informé bloc par bloc [SWS_NvM_00890] [SWS_NvM_00891]. NvM_CancelJobs supprime les demandes en attente d'un bloc ; un job déjà en cours d'exécution est poursuivi [SWS_NvM_00536] [SWS_NvM_00537].

Diagramme de séquence : l'appel retourne immédiatement ; le traitement et le retour d'information par callback ou interrogation de statut suivent lors d'appels ultérieurs à NvM_MainFunction. Sources : [SWS_NvM_00185], [SWS_NvM_00184], [SWS_NvM_00346], [SWS_NvM_00347], [SWS_NvM_00451], NVDataHandling p. 43

État du bloc RAM et synchronisation avec l'application

Le NvM gère pour le bloc RAM permanent ou le miroir un état « valide » ou « invalide » [SWS_NvM_00132] [SWS_NvM_00128]. Il distingue en outre les blocs valides selon qu'ils sont modifiés ou inchangés [SWS_NvM_00682] [SWS_NvM_00472]. Les transitions en détail :

  • Les demandes de lecture et de restauration invalident le bloc lors de la mise en file d'attente ou au démarrage du job [SWS_NvM_00198] [SWS_NvM_00227].
  • Une lecture réussie donne « valide/inchangé » [SWS_NvM_00200].
  • Les valeurs par défaut chargées donnent « valide/modifié » [SWS_NvM_00366] [SWS_NvM_00228]. Sans valeurs par défaut, le bloc reste invalide [SWS_NvM_00658].
  • NvM_SetRamBlockStatus avec TRUE et NvM_ValidateAll marquent le bloc comme modifié [SWS_NvM_00406] [SWS_NvM_00856] (EXP_NVDataHandling p. 18).
  • Après une écriture réussie, le bloc est considéré comme inchangé [SWS_NvM_00472].

Diagramme d'état : les demandes de lecture et de restauration rendent le bloc RAM temporairement invalide ; seule une opération d'écriture ramène « modifié » à « inchangé ». L'état initial est une interprétation. Sources : [SWS_NvM_00198], [SWS_NvM_00200], [SWS_NvM_00366], [SWS_NvM_00406], [SWS_NvM_00472], [SWS_NvM_00658]

En cas de synchronisation implicite, le NvM et l'application accèdent au même bloc RAM. Après une demande de lecture ou d'écriture, l'application ne doit donc le réutiliser qu'après le retour d'information [SWS_NvM_00698] [SWS_NvM_00699] (EXP_NVDataHandling p. 27). Si plusieurs applications partagent un bloc, elles sont elles-mêmes responsables de sa cohérence [SWS_NvM_00697].

Alternativement, NvMBlockUseSyncMechanism configure une synchronisation explicite [SWS_NvM_00511]. Le NvM crée alors exactement un miroir RAM et l'utilise comme tampon [SWS_NvM_00513] [SWS_NvM_00514]. Entre l'application et le miroir, les callbacks NvMWriteRamBlockToNvCallback et NvMReadRamBlockFromNvCallback copient les données [SWS_NvM_00515] [SWS_NvM_00516]. Leurs signatures sont NvM_WriteRamBlockToNvm et NvM_ReadRamBlockFromNvm [SWS_NvM_00539] [SWS_NvM_00540]. Pour ce cas d'usage, ce sont des entrées obligatoires (BSWModuleDescriptionTemplate p. 242).

Jusqu'au callback, l'application peut continuer à modifier son bloc [SWS_NvM_00705] (NVDataHandling p. 26). Si un callback signale E_NOT_OK, le NvM l'appelle à nouveau lors du cycle suivant de NvM_MainFunction, au maximum NvMRepeatMirrorOperations fois [SWS_NvM_00840] [SWS_NvM_00579]. Un bloc avec synchronisation explicite ne doit pas avoir de bloc RAM permanent [SWS_NvM_00904]. Avec une NvBlockSwComponent, la RTE implémente ces callbacks (NVDataHandling p. 34).

Diagramme de séquence : en cas de synchronisation explicite, le NvM ne prend en charge les données que dans le callback de miroir, c'est-à-dire de manière différée par rapport à la demande ; un callback ayant échoué est répété. Sources : [SWS_NvM_00515], [SWS_NvM_00579], [SWS_NvM_00705], [SWS_NvM_00840], [SWS_NvM_00901], EXP_NVDataHandling p. 13

Arrêt, mécanismes de protection et configuration

L'arrêt est déclenché par le BswM avec NvM_WriteAll [SWS_NvM_00092]. L'appel retourne immédiatement et n'est disponible que dans le maître NvM [SWS_NvM_00254] [SWS_NvM_00971]. Le job écrit les blocs RAM permanents ou appelle le callback de miroir [SWS_NvM_00018] [SWS_NvM_00252]. Auparavant, il vérifie l'état « valide/modifié » [SWS_NvM_00682]. Il ignore les blocs protégés en écriture et verrouillés sans message d'erreur [SWS_NvM_00434] [SWS_NvM_00750].

Pour que seuls les blocs modifiés soient écrits, l'utilisateur signale les modifications via NvM_SetRamBlockStatus, pour autant que cette API soit configurée [SWS_NvM_00408] [SWS_NvM_00453]. Avec storeAtShutdown, la RTE s'en charge (NVDataHandling p. 41). NvM_CancelWriteAll est réservé au BswM [SWS_NvM_00703]. Le bloc en cours de traitement est achevé de manière cohérente ; les autres blocs reçoivent NVM_REQ_CANCELED [SWS_NvM_00238] [SWS_NvM_00236] [SWS_NvM_00237] (ModeManagementGuide p. 37).

Diagramme de séquence : les modifications signalées au runtime ne sont écrites que lors de NvM_WriteAll ; le BswM peut annuler et attend la notification du résultat. Sources : [SWS_NvM_00092], [SWS_NvM_00238], [SWS_NvM_00682], [SWS_NvM_00889], NVDataHandling p. 41

Aperçu d'autres mécanismes de protection et de configuration :

  • Protection en écriture : la protection en écriture est un attribut de bloc. Avec NvMBlockWriteProt, elle est active par défaut, et l'environnement peut la lever avec NvM_SetBlockProtection [SWS_NvM_00054] [SWS_NvM_00326] [SWS_NvM_00578].
  • Écriture unique : les blocs avec NvMWriteBlockOnce ne sont écrits qu'une seule fois. Leur protection ne peut pas être levée, et les demandes d'écriture avant la première lecture sont rejetées [SWS_NvM_00397] [SWS_NvM_00398] [SWS_NvM_00952].
  • Verrouillage : le verrouillage via NvM_SetBlockLockStatus ne peut pas être modifié par d'autres services [SWS_NvM_00548] [SWS_NvM_00754].
  • Intégrité : un Static Block ID dans l'en-tête est déposé lors de l'écriture et vérifié lors de la lecture [SWS_NvM_00522] [SWS_NvM_00523] [SWS_NvM_00524]. Une comparaison CRC permet d'éviter l'écriture de données inchangées [SWS_NvM_00849] [SWS_NvM_00850].
  • Étendue : il existe trois classes de configuration d'API ; la classe 1 ne prend pas en charge DATASET [SWS_NvM_00149] [SWS_NvM_00365].
  • Initialisation initiale : NvM_FirstInitAll écrit des valeurs par défaut ou invalide des blocs, en ignorant alors la protection en écriture [SWS_NvM_91001] [SWS_NvM_00913] [SWS_NvM_00919] [SWS_NvM_00931].

Comportement en cas d'erreur

Erreurs de développement. Lorsque la détection d'erreurs est activée, le NvM signale notamment au DET :

  • NVM_E_UNINIT [SWS_NvM_00614]
  • NVM_E_PARAM_BLOCK_ID [SWS_NvM_00618]
  • NVM_E_PARAM_ADDRESS [SWS_NvM_00616]
  • NVM_E_BLOCK_PENDING [SWS_NvM_00615]
  • NVM_E_BLOCK_LOCKED [SWS_NvM_00748]
  • NVM_E_WRITE_PROTECTED [SWS_NvM_00962]

Pour une file d'attente pleine, NVM_E_QUEUE_FULL est en outre défini [SWS_NvM_00947].

Erreurs de lecture. Le NvM gère lui-même la restauration (ErrorDescription p. 62). Il procède pour cela étape par étape :

  1. En cas d'erreurs de CRC ou de Static Block ID, il relit le cas échéant [SWS_NvM_00526] [SWS_NvM_00582].
  2. Pour les blocs REDUNDANT, il lit le deuxième bloc NV [SWS_NvM_00199]. Si un exemplaire est valide, le résultat est NVM_REQ_OK, sans notification au DEM [SWS_NvM_00279] [SWS_NvM_00655]. Le NvM tente ensuite de rétablir la redondance ; en cas d'échec, il signale NVM_E_LOSS_OF_REDUNDANCY [SWS_NvM_00531] [SWS_NvM_00546].
  3. Dans le cas contraire, il charge les valeurs par défaut (NVM_REQ_RESTORED_DEFAULTS), sans modifier le bloc NV [SWS_NvM_00202] [SWS_NvM_00172].
  4. S'il n'y a pas de valeurs par défaut, le bloc RAM reste invalide [SWS_NvM_00658]. Le résultat dépend alors du type d'erreur :
    • Erreur CRC : NVM_REQ_INTEGRITY_FAILED et message DEM NVM_E_INTEGRITY_FAILED [SWS_NvM_00204] [SWS_NvM_00203]
    • Erreur de job : NVM_REQ_NOT_OK et message DEM NVM_E_REQ_FAILED [SWS_NvM_00359] [SWS_NvM_00654]

Un bloc invalidé donne NVM_REQ_NV_INVALIDATED sans entrée DEM [SWS_NvM_00341] [SWS_NvM_00652].

L'ErrorDescription mentionne de manière divergente les valeurs de résultat NVM_REQ_REDUNDANCY_FAILED et NVM_REQ_RESTORED_FROM_ROM (ErrorDescription p. 62). Les exigences [SWS_NvM_00279] [SWS_NvM_00202] font toutefois foi pour R20-11.

Diagramme d'activité : la restauration en lecture passe par Read-Retry, copie redondante et données par défaut ; ce n'est qu'ensuite qu'une erreur est positionnée et signalée au DEM. Sources : [SWS_NvM_00526], [SWS_NvM_00199], [SWS_NvM_00279], [SWS_NvM_00202], [SWS_NvM_00204], [SWS_NvM_00359], [SWS_NvM_00341], AUTOSAR_EXP_ErrorDescription p. 76

Erreurs d'écriture. Quel que soit le type de gestion, le NvM répète les opérations d'écriture ayant échoué, au maximum NVM_MAX_NUM_OF_WRITE_RETRIES fois [SWS_NvM_00168] [SWS_NvM_00213] [SWS_NvM_00216]. Il positionne ensuite NVM_REQ_NOT_OK et signale NVM_E_REQ_FAILED [SWS_NvM_00683] [SWS_NvM_00684] (ErrorDescription p. 43). Si la vérification d'écriture échoue, il signale NVM_E_VERIFY_FAILED et répète l'écriture [SWS_NvM_00528] [SWS_NvM_00529]. Pour les blocs REDUNDANT, un exemplaire écrit avec succès suffit pour NVM_REQ_OK [SWS_NvM_00284]. Vérifier les données erronées et fournir des données valides avant la prochaine écriture incombe à l'application [SWS_NvM_00694] [SWS_NvM_00696].

fournit synchrone et asynchrone bloc-based données management pour non-volatile storage (EEPROM, Flash).

Utilisation et sémantique

La fonction NvM_WriteRamBlockToNvm est une routine de callback spécifique au bloc ([SWS_NvM_00539]) appelée par le module NvM pour permettre à l'application de copier des données depuis le bloc RAM permanent vers le miroir RAM interne (Mirror) du NvM. La déclaration est fournie via NvM_Externals.h. La fonction est exécutée de manière synchrone et est définie comme non réentrante (Non Reentrant) ([SWS_NvM_00539]).

Via le paramètre de sortie NvMBuffer, le module NvM transmet l'adresse de destination du tampon dans lequel l'application doit déposer les données à écrire ([SWS_NvM_00539]).

Valeurs de retour

Le type Std_ReturnType sert de retour d'état ([SWS_NvM_00539]) :

  • E_OK : la routine de callback a été traitée avec succès ([SWS_NvM_00539]).
  • Toute autre valeur de retour : le traitement de la routine de callback a échoué ([SWS_NvM_00539]).

Interaction et contexte d'appel

NvM_WriteRamBlockToNvm sert de callback pour la synchronisation explicite et est utilisé dans les contextes suivants :

  • Arrêt du système : lors de l'arrêt, le job de NvM_WriteAll appelle le callback NvM_WriteRamBlockToNvm pour la synchronisation ([SWS_NvM_00018]). Cela s'effectue pour les blocs dont le paramètre de configuration NvMSelectBlockForWriteAll est défini sur true ([SWS_NvM_00252]).
  • Opérations de bloc : en cas de synchronisation explicite, les fonctions NvM_WriteBlock ([SWS_NvM_00303]) et NvM_WritePRAMBlock ([SWS_NvM_00803]) présupposent la validité du miroir RAM dans le NvM. Si le bloc RAM permanent référencé devait encore être invalide, il est automatiquement validé après l'exécution du callback NvM_WriteRamBlockToNvm.

La fonction NvM_ReadRamBlockFromNvm est une routine de callback spécifique au bloc ([SWS_NvM_00540]) appelée par le gestionnaire NVRAM pour que l'application copie les données depuis le tampon miroir interne du module NvM vers le bloc RAM. Elle est mise à disposition via l'en-tête NvM_Externals.h.

Utilisation et sémantique

  • Synchronicité et réentrance : l'appel est exécuté de manière synchrone et est spécifié comme non réentrant (Non Reentrant) ([SWS_NvM_00540]).
  • Paramètres d'entrée : via le paramètre d'entrée NvMBuffer (type const void*), la routine reçoit l'adresse du tampon à partir duquel les données peuvent être lues ([SWS_NvM_00540]). Il n'y a pas de paramètres d'entrée/sortie ou de sortie pure.
  • Valeur de retour : la fonction de callback renvoie l'état sous forme de Std_ReturnType : E_OK signale un traitement réussi ; toute valeur de retour différente signale un traitement échoué ([SWS_NvM_00540]).

Interaction et gestion des erreurs

La routine sert de callback de synchronisation explicite. Dans le cadre du service multi-blocs NvM_ReadAll, le NvM traite des blocs RAM permanents ou appelle NvM_ReadRamBlockFromNvm pour des blocs configurés en conséquence (notamment lorsque NvmSelectBlockForReadall == TRUE est configuré) ([SWS_NvM_00118], [SWS_NvM_00356]).

Si l'opération de copie échoue au sein de la routine applicative, la fonction doit renvoyer une valeur d'erreur (différente de E_OK) ([SWS_NvM_00540]). Aucun message d'erreur DET ou DEM spécifique n'est défini dans les données de spécification pour ce callback.

Il est fourni via le fichier d'en-tête Rte_NvM_Type.h ([SWS_NvM_00470]). En interaction avec des blocs redondants (type NVM_BLOCK_REDUNDANT), la fonction NvM_InvalidateNvBlock ne définit le résultat de la requête NvM_RequestResultType à NVM_REQ_OK que lorsque les deux blocs NV ont été invalidés ([SWS_NvM_00274]).

Utilisation

Le type NvM_InitBlockRequestType est défini conformément à [SWS_NvM_91123] comme uint8 et disponible via le fichier d'en-tête Rte_NvM_Type.h. Il identifie la nature de l'opération effectuée sur un bloc lorsqu'elle est signalée via une fonction de rappel correspondante.

La plage de valeurs comprend quatre constantes spécifiées :

  • NVM_INIT_READ_BLOCK (0x00) : l'opération NvM_ReadBlock ou NvM_ReadPRAMBlock a été demandée pour le bloc.
  • NVM_INIT_RESTORE_BLOCK_DEFAULTS (0x01) : la restauration de données par défaut via NvM_RestoreBlockDefaults ou NvM_RestorePRAMBlockDefaults a été demandée pour le bloc.
  • NVM_INIT_READ_ALL_BLOCK (0x02) : le bloc est traité dans le cadre de l'opération collective NvM_ReadAll.
  • NVM_INIT_FIRST_INIT_ALL (0x03) : le bloc est traité dans le cadre de NvM_FirstInitAll.

Interaction et intégration

L'évaluation du paramètre de type NvM_InitBlockRequestType permet à l'utilisateur, dans le callback, de déterminer de manière différenciée si un bloc individuel est lu ou restauré de façon ciblée, ou si le traitement a lieu au sein d'une séquence système globale (phase de démarrage via ReadAll ou initialisation initiale via FirstInitAll). La fonction de rappel devrait typiquement servir à la fourniture ou à l'initialisation de données de bloc lors de demandes de lecture ou de restauration. Dans l'implémentation, il est recommandé d'effectuer un branchement sur toutes les valeurs d'énumération définies afin de réagir en fonction des exigences.
