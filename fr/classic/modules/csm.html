Le CSM en tant que couche de services entre les utilisateurs et les pilotes cryptographiques

Le Crypto Service Manager met à disposition des applications et des modules BSW des services cryptographiques via une API uniforme. Ceux-ci comprennent le hachage, le MAC, le chiffrement et le déchiffrement, l'AEAD, les signatures, les nombres aléatoires et la gestion des clés, par exemple via Csm_Hash [SWS_Csm_00980], Csm_MacGenerate [SWS_Csm_00982], Csm_AEADEncrypt [SWS_Csm_01023] ou Csm_SignatureVerify [SWS_Csm_00996]. Le CSM n'effectue pas de calculs lui-même. Il transmet les requêtes via la Crypto Interface (CryIf) à des Crypto Driver Objects, qui peuvent être matériels (par ex. HSM) ou logiciels. Le chemin allant d'une file d'attente du CSM à un Crypto Driver Object via la CryIf est appelé canal (SWS CSM p. 29). Les fonctions CryIf requises sont listées dans [SWS_Csm_91100]. Det_ReportError est une interface optionnelle [SWS_Csm_91101].

Les composants logiciels y accèdent via des ports de service RTE, que le chapitre « Service Interfaces » définit formellement (SWS CSM p. 85). Les modules BSW utilisent directement l'API C. Deux exemples :

  • Le DCM vérifie le Proof-of-Ownership avec Csm_SignatureVerify en mode CRYPTO_OPERATIONMODE_SINGLECALL (SWS DCM p. 152).
  • L'IdsM reçoit le résultat des jobs asynchrones de signature via un callback configuré dans le CSM (SWS IdsM p. 77).

Jobs, files d'attente et canaux : comment un appel de service est transmis

Un job est une instance d'une primitive cryptographique configurée [SWS_Csm_00941]. Pour chaque job, une seule instance est traitée à un instant donné. Différents jobs peuvent s'exécuter en parallèle (SWS CSM p. 21). À l'exécution, la structure Crypto_JobType porte le job. Elle contient jobId, jobState, la structure d'entrée/sortie jobPrimitiveInputOutput, les informations de la primitive et les identifiants de clé [SWS_Csm_01013], [SWS_Csm_01009], [SWS_Csm_01012] (SWS CSM p. 20).

Les jobs peuvent être mis en file d'attente dans des CsmQueues configurées [SWS_Csm_00940]. Les files d'attente trient selon la priorité du job [SWS_Csm_00944]. Chaque file d'attente est associée à exactement un canal, sa taille étant configurable (SWS CSM p. 29). La spécification régit expressément deux cas (SWS CSM p. 21) :

  • Si le job est déjà ACTIVE, l'appel de service appelle directement CryIf_ProcessJob et transmet sa valeur de retour.
  • Si un job doit être mis en file d'attente et que la file d'attente est pleine, il est rejeté avec CRYPTO_E_BUSY.

Pour les jobs synchrones, la spécification recommande une taille de file d'attente de 0. Toutefois, les jobs synchrones et asynchrones peuvent utiliser le même canal. Dans le cas d'un job actif, le CSM suppose que l'appelant souhaite continuer, par exemple avec « update ». La vérification de plausibilité incombe alors au pilote (SWS CSM p. 29).

Traitement synchrone et asynchrone au rythme de Csm_MainFunction

La configuration du job détermine si un service de données fonctionne de manière synchrone ou asynchrone. C'est par exemple ainsi que cela est décrit pour Csm_Hash et Csm_Encrypt [SWS_Csm_00980], [SWS_Csm_00984]. Le choix est codé dans Crypto_ProcessingType [SWS_Csm_01049].

Si une interface asynchrone est configurée, Csm_MainFunction est appelée cycliquement. Elle vérifie les files d'attente et transmet les jobs à la CryIf [SWS_Csm_00479] (SWS CSM p. 21). Pour le multi-cœur, les règles suivantes s'appliquent :

  • Il existe une Csm_MainFunction_<shortName> pour chaque instance configurée de CsmMainFunction [SWS_Csm_00479].
  • Csm_Init peut être fourni par partition [SWS_Csm_00646].
  • Les files d'attente sont traitées dans la MainFunction référencée via CsmQueueMainFunctionRef (SWS CSM p. 36).

Le résultat est renvoyé par le biais d'une chaîne de rappels. La CryIf signale l'achèvement avec Csm_CallbackNotification(job, result) [SWS_Csm_00970]. Si le bit FINISH est défini, le CSM appelle le callback configuré [SWS_Csm_01044]. Sa signature est <Csm_ApplicationCallbackNotification>(jobId, result), son nom est configurable [SWS_Csm_00971]. Les SW-C reçoivent la notification via le port CallbackNotification_{Job} [SWS_Csm_00934], [SWS_Csm_00928]. Les longueurs et les résultats de vérification reviennent de manière asynchrone via Csm_LengthPtr et Csm_VerifyResultPtr [SWS_Csm_91045], [SWS_Csm_91046].

Streaming, Single Call et cycle de vie d'un job

Le paramètre mode est un champ de drapeaux composé de « START », « UPDATE » et « FINISH ». Les drapeaux peuvent être combinés de sorte qu'un appel exécute plusieurs opérations [SWS_Csm_01039]. Crypto_OperationModeType définit les valeurs suivantes [SWS_Csm_01029] :

  • CRYPTO_OPERATIONMODE_START : réinitialise le job.
  • …_UPDATE : calcule des résultats intermédiaires.
  • …_STREAMSTART : Start et Update en un seul appel.
  • …_FINISH : finalise le calcul.

Grâce à FINISH, l'application peut terminer un calcul [SWS_Csm_01046]. START et FINISH sans UPDATE mènent à E_NOT_OK [SWS_Csm_01045]. Le streaming est adapté aux très grands volumes de données, car UPDATE peut être appelé aussi souvent que nécessaire. L'approche Single Call permet d'économiser des coûts d'appel pour les petites données (EXP Crypto Services p. 12).

Le job connaît deux états [SWS_Csm_01028] :

  • CRYPTO_JOBSTATE_IDLE s'applique après Csm_Init et après l'achèvement de FINISH.
  • CRYPTO_JOBSTATE_ACTIVE s'applique après START ou UPDATE.

Les transitions d'état proprement dites sont exécutées par le Crypto Driver (SWS CSM p. 22).

Un contexte de travail en cours peut être sauvegardé avec Csm_SaveContextJob et restauré avec Csm_RestoreContextJob [SWS_Csm_91063], [SWS_Csm_91064]. Les éléments de clé ne font pas partie du contexte. Dans deux cas, l'appel retourne immédiatement avec E_NOT_OK : lorsque le job est IDLE ou lorsqu'il est en cours de traitement par le pilote (SWS CSM p. 35).

Clés : éléments, validité, génération et échange

Une clé est constituée d'un ou plusieurs éléments de clé [SWS_Csm_00954]. Leurs identifiants sont fixés, par exemple CRYPTO_KE_MAC_KEY (1), CRYPTO_KE_CIPHER_IV (5) et CRYPTO_KE_KEYGENERATE_SEED (16) [SWS_Csm_01022]. Les services de clés ne proposent que la fonction Csm_<Service>() [SWS_Csm_00950]. Les fonctions suivantes fonctionnent de manière synchrone :

  • Csm_KeyElementSet [SWS_Csm_00957]
  • Csm_KeyElementGet [SWS_Csm_00959]
  • Csm_KeyCopy [SWS_Csm_01034]
  • Csm_KeyElementCopy [SWS_Csm_00969]
  • Csm_KeyElementCopyPartial [SWS_Csm_91025]

Des versions ultérieures de la documentation exigent en outre : après une fonction de gestion des clés, le CSM ne traite aucun nouveau job de la file d'attente jusqu'à la prochaine MainFunction (SWS CSM p. 60, R24-11/R25-11). Pour R20-11, la charge utile ne contient aucune exigence à ce sujet.

L'état de la clé est CRYPTO_KEYSTATUS_INVALID ou CRYPTO_KEYSTATUS_VALID [SWS_Csm_91102]. Il est contrôlé à l'aide de ces fonctions :

  • Csm_KeySetValid [SWS_Csm_00958]
  • Csm_KeySetInvalid [SWS_Csm_91075]
  • Csm_KeyGetStatus [SWS_Csm_91047], qui appelle CryIf_KeyGetStatus (SWS CSM p. 63)

Les variantes basées sur les jobs Csm_JobKeySetValid et Csm_JobKeySetInvalid s'exécutent de manière synchrone ou asynchrone selon la configuration du job. Dans R20-11, elles acceptent jobId et keyId [SWS_Csm_91027], [SWS_Csm_91002]. Le passage documentaire ultérieur n'affiche plus que jobId (SWS CSM p. 76). La signature de R20-11 fait foi.

Csm_KeyGenerate génère du matériel de clé [SWS_Csm_00955]. Le résultat aboutit dans CRYPTO_KE_KEYGENERATE_KEY, l'algorithme provient de CRYPTO_KE_KEYGENERATE_ALGORITHM. L'entropie de la graine détermine la qualité de la clé (SWS CSM p. 67). La manière dont les générateurs de nombres aléatoires sont initialisés avec une graine est spécifique au projet. Cela doit cependant avoir lieu avant la première requête (SWS CSM p. 59). Csm_RandomSeed appelle CryIf_RandomSeed [SWS_Csm_01051], [SWS_Csm_01052]. Csm_KeyDerive appelle CryIf_KeyDerive [SWS_Csm_00956], [SWS_Csm_01018].

Pour l'échange de clés Diffie-Hellman, y compris sur courbes elliptiques, il existe deux étapes. Csm_KeyExchangeCalcPubVal calcule sa propre valeur publique. Csm_KeyExchangeCalcSecret calcule le secret partagé à partir de la valeur publique du partenaire [SWS_Csm_00966], [SWS_Csm_00967]. Toutes deux existent également sous forme de variantes de jobs [SWS_Csm_91031], [SWS_Csm_91032]. Les éléments CRYPTO_KE_KEYEXCHANGE_BASE, …_PRIVKEY et …_OWNPUBKEY contiennent le matériel de clé (SWS CSM p. 70).

Formes d'interfaces, types de données et configuration

En plus des fonctions C dans Csm.h, la RTE génère des ports liés aux jobs :

  • CsmJob_{Job} pour une utilisation synchrone avec CRYPTO_USE_PORT, fixé à CRYPTO_OPERATIONMODE_SINGLECALL [SWS_Csm_91023].
  • La variante asynchrone avec CRYPTO_USE_PORT_OPTIMIZED [SWS_Csm_91062].
  • Ports de clé CsmKey_{Key} [SWS_Csm_01042], [SWS_Csm_01905].
  • Ports de contexte [SWS_Csm_91105], [SWS_Csm_91106].

Pour chaque service, il existe une interface synchrone telle que CsmHash_{PrimitiveCfg} et une asynchrone telle que CsmHash [SWS_Csm_00946], [SWS_Csm_91051]. Les types de mémoire tampon sont des tableaux de uint8 issus de Rte_Csm_Type.h. Leur taille résulte de longueurs maximales configurées, par exemple pour Csm_HashDataType_{Crypto}, Csm_HashResultType_{Crypto} et Csm_MacGenerateDataType_{Crypto} [SWS_Csm_01920], [SWS_Csm_00912], [SWS_Csm_00935].

Le contenu de Csm_ConfigType est spécifique à l'implémentation [SWS_Csm_01085]. Le configPtr de Csm_Init doit être un pointeur nul (SWS CSM p. 48). Les principaux contenus de configuration :

  • Un CsmJob porte CsmJobId, CsmJobPriority, CsmJobPrimitiveRef et CsmJobInterfaceUsePort (SWS CSM p. 166).
  • Les primitives sont réalisées sous forme de structures Crypto_PrimitiveInfoType constantes (SWS CSM p. 23) [SWS_Csm_01011].
  • Un CsmKey référence une clé CryIf via CsmKeyRef (SWS CSM p. 161).
  • Une CsmQueue met en mémoire tampon les jobs lorsque le matériel est occupé et détermine le canal (SWS CSM p. 164).

Grâce à Crypto_JobRedirectionInfoType, les entrées et sorties peuvent être redirigées vers des éléments de clé [SWS_Csm_91026], [SWS_Csm_91024].

Comportement en cas d'erreur

Les services signalent leur résultat sous la forme Std_ReturnType ou Crypto_ResultType. En plus de E_OK et E_NOT_OK, il existe des codes spécifiques tels que CRYPTO_E_BUSY, CRYPTO_E_ENTROPY_EXHAUSTED et CRYPTO_E_KEY_NOT_VALID [SWS_Csm_91044], [SWS_Csm_91043]. Pour les services de vérification, E_OK signifie uniquement que la requête a réussi. Le verdict proprement dit figure dans verifyPtr sous forme de CRYPTO_E_VER_OK ou CRYPTO_E_VER_NOT_OK [SWS_Csm_01050], [SWS_Csm_01024].

Si la détection des erreurs de développement est active, le CSM signale les erreurs suivantes au DET [SWS_Csm_91004] :

  • CSM_E_PARAM_POINTER
  • CSM_E_PARAM_HANDLE
  • CSM_E_UNINIT
  • CSM_E_INIT_FAILED, en cas d'échec de l'initialisation (SWS CSM p. 48)
  • CSM_E_PROCESSING_MODE

Un débordement de file d'attente constitue l'erreur d'exécution CSM_E_QUEUE_FULL [SWS_Csm_01089].

Si Csm_KeyElementSet échoue, l'état de l'élément est inconnu. L'application peut le vérifier avec Csm_KeyGetStatus (SWS CSM p. 62) [SWS_Csm_00957]. La dérivation et la copie peuvent échouer avec CRYPTO_E_KEY_READ_FAIL, …_WRITE_FAIL, …_SIZE_MISMATCH ou CRYPTO_E_KEY_EMPTY [SWS_Csm_00956], [SWS_Csm_00969].

Csm_CancelJob annule les jobs asynchrones ou en streaming [SWS_Csm_00968]. Les valeurs de retour signifient :

  • E_OK : le job est retiré.
  • CRYPTO_E_JOB_CANCELED : l'annulation n'a lieu qu'à la prochaine étape appropriée et est signalée via un callback d'achèvement négatif.

Le passage documentaire ultérieur précise : pour les jobs synchrones, Csm_CancelJob signale CSM_E_PROCESSING_MODE. Le CSM retire le job de la file d'attente ou appelle CryIf_CancelJob (SWS CSM p. 80).
