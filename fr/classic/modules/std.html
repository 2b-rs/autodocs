Std_Types.h comme base de types commune pour BSW, RTE et application

Le module std ne propose aucune fonction. Il fournit exclusivement des types et des symboles qui sont tous disponibles via Std_Types.h. En font partie le type de retour Std_ReturnType [SWS_Std_00005], la structure de version Std_VersionInfoType [SWS_Std_00015] et le type de pointeur de fonction Std_ExtractProtocolHeaderFieldsType [SWS_Std_91003]. La frontière du système fixe l'exigence BSW imposée à l'en-tête des types standard : tous les types et constantes standard d'AUTOSAR doivent figurer dans Std_Types.h. Cet en-tête inclut Platform_Types.h et Compiler.h. Il définit Std_ReturnType, E_OK/E_NOT_OK ainsi que STD_ON, STD_OFF, STD_HIGH, STD_LOW, STD_ACTIVE et STD_IDLE SRS BSWGeneral p. 62.

Tout module utilisant des types d'entiers AUTOSAR ou le type de retour standard inclut Std_Types.h. L'objectif est un accès homogène à l'échelle de la plateforme aux types standard SRS BSWGeneral p. 62. La RTE et les modules BSW partagent expressément le même type de retour [SWS_Std_00005]. Le planificateur BSW le renvoie également lors de SchM_Call au-delà des limites de partition BSWDistributionGuide p. 13. Pour les Complex Device Drivers, les en-têtes de configuration avec leurs commutateurs STD_ON/STD_OFF reposent également sur Std_Types.h CDD-Guideline p. 14.

Diagramme de contexte : Std_Types.h s'appuie sur Platform_Types.h et Compiler.h et est utilisé par les modules BSW, les en-têtes de configuration, la RTE et les transformeurs. Sources : SRS BSWGeneral p. 62, CDD-Guideline p. 14, [SWS_Std_00005], [SWS_Std_91003]

Std_ReturnType : Plage de valeurs, disposition des bits et extensions spécifiques aux modules

Std_ReturnType est défini comme typedef uint8 Std_ReturnType;. E_OK (0) et E_NOT_OK (1) sont préaffectés. La plage 0x02–0x3F est disponible pour les erreurs spécifiques à l'utilisateur [SWS_Std_00005]. En temps normal, seuls E_OK et E_NOT_OK doivent être utilisés. Si ces valeurs ne suffisent pas, un module peut définir d'autres valeurs dans les six bits de poids faible et les nomme avec son préfixe de module. Les bits 7 et 8 sont réservés et sont définis par la spécification de la RTE [SWS_Std_00011].

La RTE justifie le type de base uint8 par des questions de compatibilité. Un enum pourrait avoir une taille différente selon les RTE de différents fabricants. C'est pourquoi les valeurs d'erreur sont déclarées par #define. Les bits réservés hébergent notamment l'erreur recouvrable RTE_E_LOST_DATA (64) et les erreurs d'infrastructure immédiates à partir de 128, par exemple RTE_E_COM_STOPPED SWS RTE p. 586. Ce tableau est issu de R23-11. Pour R20-11, la réservation des bits est elle-même définie de manière normative par [SWS_Std_00011].

Dans le modèle UML du BSW, une extension spécifique à un module est modélisée sous la forme d'une classe <Ma>_ReturnType avec le stéréotype «extra_literals». Ses valeurs portent le préfixe du module et se situent dans la plage 0x02–0x3f. Selon le même guide, Std_ReturnType est en outre le seul type de retour autorisé pour les opérations dans les interfaces de service client/serveur BSWUMLModelModelingGuide p. 28. Des exemples en sont Csm_ReturnType avec CSM_E_BUSY = 2 TR BSWUMLModelModelingGuide p. 29 et l'extension CAN_BUSY = 0x02 du pilote CAN pour Can_Write() SWS CANDriver p. 54.

Diagramme d'activité : Une valeur Std_ReturnType peut être classée en trois zones : bits réservés à la RTE, valeurs standard E_OK/E_NOT_OK et plage spécifique au module 0x02–0x3F. Sources : [SWS_Std_00005], [SWS_Std_00011], SWS StandardTypes p. 15, SWS RTE p. 586

Diagramme de collaboration : Les extensions de module telles que Csm_ReturnType ou CAN_BUSY occupent la plage 0x02–0x3F, la RTE occupant les bits supérieurs réservés. Sources : TR BSWUMLModelModelingGuide p. 29, SWS CANDriver p. 54, [SWS_Std_00011]

Interrogation de la version via Std_VersionInfoType

Std_VersionInfoType est une structure comportant les champs vendorID et moduleID (chacun de type uint16) ainsi que sw_major_version, sw_minor_version et sw_patch_version (chacun de type uint8). Elle sert à interroger la version d'un module BSW via <Module name>_GetVersionInfo() [SWS_Std_00015]. La règle de nommage associée désigne GetVersionInfo comme nom de service. void Eep_21_LDExt_GetVersionInfo(Std_VersionInfoType *versioninfo) SRS BSWGeneral p. 60 sert d'exemple.

La fonction s'exécute de manière synchrone et est réentrante. Elle comporte exactement un paramètre de type Std_VersionInfoType, importé depuis Std_Types.h. Sa présence est configurée pour chaque module au moment de la précompilation via <Ma>VersionInfoApi. Les informations publiées du module sont fournies : Vendor Id, Module Id et le numéro de version spécifique au constructeur SWS BSWGeneral p. 76. Interprétation : Les champs devraient correspondre aux paramètres VendorId, ModuleId et SwMajorVersion/SwMinorVersion/SwPatchVersion de CommonPublishedInformation ECU ConfigurationParameters p. 14. Si la détection des erreurs de développement est active, les modules vérifient le pointeur. En présence de NULL, ils signalent par exemple CAN_E_PARAM_POINTER SWS CANDriver p. 57 ou ADC_E_PARAM_POINTER SWS ADCDriver p. 80.

Diagramme de séquence : L'interrogation de la version est un appel synchrone avec vérification facultative du pointeur, au cours duquel le module remplit la structure. Sources : [SWS_Std_00015], SWS BSWGeneral p. 76, SWS CANDriver p. 57, SWS NVRAMManager p. 158

Types de transformeurs : Erreurs, classes et codes forward dans l'état R20-11

Dans R20-11, Std_TransformerError est une structure composée de errorCode (type uint8) et de transformerClass (type Std_TransformerClass) [SWS_Std_00021]. Bien que la vue d'ensemble de l'API indique typedef uint8 comme signature, la définition de structure de l'exigence fait foi. Les versions ultérieures typent errorCode en tant que Std_TransformerErrorCode. La signification des valeurs s'y applique à chaque fois à la chaîne de transformeurs concrète SWS StandardTypes p. 16. Std_TransformerClass dérive de uint8 et admet les valeurs suivantes : STD_TRANSFORMER_UNSPECIFIED (0x00), STD_TRANSFORMER_SERIALIZER (0x01), STD_TRANSFORMER_SAFETY (0x02), STD_TRANSFORMER_SECURITY (0x03) et STD_TRANSFORMER_CUSTOM (0xFF) [SWS_Std_00024].

Les deux types suivants possèdent le statut Draft dans R20-11. Std_TransformerForward est une structure composée de errorCode (type Std_TransformerForwardCode) et de transformerClass [SWS_Std_00027]. Std_TransformerForwardCode prend les valeurs E_OK (0x00), E_SAFETY_INVALID_REP (0x01), E_SAFETY_INVALID_SEQ (0x02) et E_SAFETY_INVALID_CRC (0x03) [SWS_Std_00029]. [SWS_Std_00027] a été supprimé avec R22-11 SWS StandardTypes p. 1. Les versions ultérieures utilisent également les littéraux STD_E_FORWARDCODE_*, dont les descriptions ne peuvent pas être mises en correspondance exacte avec les noms de R20-11 SWS StandardTypes p. 17. Pour R20-11, les noms de l'exigence s'appliquent. Interprétation : Les codes devraient servir à réinjecter de manière ciblée les erreurs de sécurité détectées lors de la retransmission. C'est également ce qu'indiquent les fonctions E2E-Forward qui reconstruisent sur les données de sortie les erreurs détectées SWS E2ELibrary p. 107.

Dans la spécification de la RTE des versions ultérieures, Rte_Send peut comporter un paramètre d'entrée facultatif forwardedCode et un paramètre de sortie facultatif Std_TransformerError transformerError SWS RTE p. 704. Rte_Call comporte également un transformerError facultatif en sortie SWS RTE p. 731. Pour Rte_Trigger, ce paramètre n'est généré que si une PortAPIOption avec errorHandling = transformerErrorHandling référence le port SWS RTE p. 774.

Diagramme de séquence : Une erreur de la chaîne de transformeurs parvient à l'appelant de deux manières : sous la forme d'un Std_TransformerError avec classe et comme valeur de retour pour les erreurs de communication. Sources : [SWS_Std_00021], [SWS_Std_00024], SWS RTE p. 731, SwCluster-Guideline p. 245, SWS RTE p. 586

Type de message, résultat de message et extraction d'en-tête dans les chaînes de transformeurs C/S

Std_MessageTypeType dérive de uint8. Il distingue STD_MESSAGETYPE_REQUEST (0x00) et STD_MESSAGETYPE_RESPONSE (0x01), la plage 0x02–0x3F est réservée pour de futurs types [SWS_Std_91001]. Le type code les types de messages dans AUTOSAR, actuellement limités aux requêtes et réponses dans la communication C/S [SWS_Std_00017]. La vue d'ensemble de l'API nomme le type de manière abrégée Std_MessageType, mais le nom Std_MessageTypeType fait foi. Std_MessageResultType distingue STD_MESSAGERESULT_OK (0x00) et STD_MESSAGERESULT_ERROR (0x01), 0x02–0x3F sont réservés [SWS_Std_91002] [SWS_Std_00019]. Pour les deux types, des releases ultérieures annoncent d'éventuels littéraux supplémentaires SWS StandardTypes p. 18 SWS StandardTypes p. 19.

Std_ExtractProtocolHeaderFieldsType est un pointeur de fonction avec les paramètres const uint8* buffer, uint32 bufferLength ainsi que les sorties messageType et messageResult. La fonction cible renvoie Std_ReturnType et est synchrone et réentrante [SWS_Std_91003]. Son objet se limite actuellement à REQUEST/RESPONSE et OK/ERROR SWS StandardTypes p. 20. Dans <Mip>_Inv_<transformerId>, l'argument optionnel extractProtocolHeaderFields pointe vers la fonction d'extraction d'un transformer précédent de la chaîne. L'argument n'existe que si le XfrmImplementationMapping possède une XfrmTransformerClassExtractProtocolHeaderFields TransformerGeneral p. 40. Une implémentation appropriée est SomeIpXf_ExtractProtocolHeaderFields SWS SOMEIPTransformer p. 61. Interprétation : le transformer E2E appelle probablement cette fonction pour les profils PXXm via le pointeur et transmet messageType/messageResult à l'E2E-Library SWS E2ETransformer p. 54.

Comportement en cas d'erreur

Pour std, seules des définitions de types et de symboles sont disponibles, à commencer par [SWS_Std_00005]. Le comportement en cas d'erreur résulte donc de la manière dont les modules utilisateurs emploient ces valeurs :

  • Erreur générique : E_NOT_OK indique l'échec d'une requête. Can_GetControllerErrorState signale par exemple CAN_E_UNINIT en cas d'initialisation manquante et renvoie E_NOT_OK SWS CANDriver p. 64.
  • Valeurs d'erreur spécifiques : des valeurs supplémentaires ne sont autorisées qu'avec un préfixe de module et uniquement dans les six bits de poids faible. Les bits 7 et 8 restent réservés à la RTE [SWS_Std_00011].
  • En-tête erroné : SomeIpXf_ExtractProtocolHeaderFields renvoie E_NOT_OK si la version du protocole est incorrecte ou si bufferLength est inférieur à un en-tête SOME/IP minimal SWS SOMEIPTransformer p. 61. Le transformer E2E bifurque alors vers la branche FALSE SWS E2ETransformer p. 38.
  • Erreur de transformer : transformerError contient l'erreur de la chaîne de transformers, tandis que la valeur de retour indique des erreurs de communication SwCluster-Guideline p. 245. La table des erreurs de la RTE répertorie RTE_E_HARD_TRANSFORMER_ERROR (138) et RTE_E_SOFT_TRANSFORMER_ERROR (140) SWS RTE p. 586.
  • Callbacks : les callbacks qui sont des services AUTOSAR renvoient Std_ReturnType. L'appelant peut supposer E_OK, bien que des erreurs puissent néanmoins se produire dans des systèmes partitionnés SWS BSWGeneral p. 69.
  • Compatibilité des types : les API de service BSW appelées via la RTE doivent renvoyer Std_ReturnType. Un autre type ou void entraîne une incompatibilité RS BSWGeneral p. 63. De plus, les valeurs de retour doivent correspondre des deux côtés ModelConstraints p. 197.
  • Conflit de nom avec OSEK : E_OK est protégé par STATUSTYPEDEFINED afin d'éviter qu'il ne soit défini deux fois [SWS_Std_00006] SRS BSWGeneral p. 62.

Utilisation

Le type Std_ReturnType est défini comme typedef uint8 Std_ReturnType; et est fourni via le fichier d'en-tête Std_Types.h ([SWS_Std_00005]). Il sert de type de retour d'API standardisé, utilisé conjointement par la RTE et les modules BSW ([SWS_Std_00005]).

Gestion des erreurs et plage de valeurs

Si les valeurs standards E_OK et E_NOT_OK ne suffisent pas, la plage de valeurs allant de 0x02 à 0x3F est disponible pour les erreurs spécifiques à l'utilisateur ([SWS_Std_00005]) :

  • Des valeurs d'erreur spécifiques à l'utilisateur peuvent être définies en utilisant les 6 bits de poids faible (least significant bits) ([SWS_Std_00011]).
  • Pour le nommage des valeurs définies par l'utilisateur, l'utilisation du préfixe respectif du module est obligatoire ([SWS_Std_00011]).

Interaction et disposition des bits (Bit-Layout)

La disposition de Std_ReturnType correspond aux stipulations de la spécification RTE ([SWS_Std_00011]). Les bits 7 et 8 sont ici réservés et sont définis par la spécification RTE ([SWS_Std_00011]).

Le type Std_MessageType est utilisé conformément à [SWS_Std_91001] pour coder différents types de messages. Il est disponible via l'en-tête Std_Types.h et repose sur le type de base uint8.

Selon [SWS_Std_91001], le codage est actuellement limité à la distinction entre requêtes et réponses dans la communication client/serveur (C/S Communication). Le type définit les valeurs suivantes :

Utilisation et plage de valeurs

Le type de données Std_MessageResultType ([SWS_Std_91002]) est un type standard élémentaire du module Std dans AUTOSAR Classic version R20-11. Il est fourni via le fichier d'en-tête Std_Types.h et repose sur la définition typedef uint8 Std_MessageResultType;. Son rôle est le codage uniforme de différents types de résultats pour les messages de réponse.

Conformément à [SWS_Std_00019] ainsi qu'à [SWS_Std_91002], ce codage est actuellement limité à la distinction entre messages de réponse réussis et erronés. La plage de valeurs spécifiée comprend les définitions suivantes :

  • STD_MESSAGERESULT_OK (valeur 0x00) : signale le résultat réussi d'un message de réponse ([SWS_Std_91002]).
  • STD_MESSAGERESULT_ERROR (valeur 0x01) : signale le résultat erroné d'un message de réponse ([SWS_Std_91002]).
  • Plage de valeurs de 0x02 à 0x3F : cette plage est réservée pour les futurs résultats de messages ([SWS_Std_91002]).

Interaction et gestion des erreurs
