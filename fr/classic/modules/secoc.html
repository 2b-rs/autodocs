Rôle de SecOC : sécurisation des I-PDU aux côtés du PDU-Router

SecOC (Secure Onboard Communication) protège les I-PDU contre la manipulation et le rejeu. À l'émission, SecOC adjoint à une Authentic I-PDU des informations d'authentification, composées d'une Freshness Value le cas échéant tronquée et d'un Authenticator. Cela donne naissance à une Secured I-PDU. À la réception, ces informations sont vérifiées avant que l'Authentic I-PDU ne soit transmise ([SWS_SecOC_00040], SWS SecOC Fig. 7.2 p. 30). L'Authenticator est calculé à partir de la concaténation de trois parties : Data Identifier (SecOCDataId), partie sécurisée de l'Authentic I-PDU et Freshness Value complète (SWS SecOC p. 29).

Dans l'architecture, SecOC se situe aux côtés du PduR. Les couches supérieures telles que Com émettent via PduR_<Up>Transmit. Le PduR appelle ensuite SecOC_[If|Tp]Transmit, et SecOC transmet de nouveau la Secured I-PDU via le PduR à une interface de bus ou à un protocole de transport (SWS SecOC p. 40, SWS SecOC Fig. 1.1 p. 10). Les MetaData d'une Authentic PDU apparaissent inchangées dans la Secured PDU, et inversement ([SWS_SecOC_00212]). Aucun autre module ne doit dépendre de SecOC afin qu'un système puisse également être construit sans SecOC (SWS SecOC p. 39).

SecOC collabore avec plusieurs autres modules :

  • La cryptographie est fournie par le CSM, entre autres via Csm_MacGenerate et Csm_MacVerify ([SWS_SecOC_00138]). Pour les jobs CSM asynchrones, SecOC fournit des callbacks spécifiques au constructeur (SWS SecOC p. 78).
  • Les Freshness Values proviennent d'un Freshness Manager. Avec SecOCQueryFreshnessValue = RTE, il est raccordé via le port FreshnessManagement ([SWS_SecOC_91001]), avec CFUNC via des fonctions C ([SWS_SecOC_00231], [SWS_SecOC_00247]).
  • SecOC signale les erreurs à la DET ([SWS_SecOC_00101]).
  • Les Security Events sont transmis à l'IdsM ([SWS_SecOC_00273]).

État du module et Main Functions cycliques

SecOC connaît deux états, SECOC_UNINIT et SECOC_INIT ([SWS_SecOC_00162]) :

  • Une initialisation réussie avec SecOC_Init conduit à SECOC_INIT ([SWS_SecOC_00106]).
  • SecOC_DeInit arrête la communication sécurisée, élimine toutes les I-PDU mises en mémoire tampon et place le module dans l'état non initialisé ([SWS_SecOC_00161]). Les variables globales internes sont également effacées à cette occasion (SWS SecOC p. 65).
  • Pour les appels d'API sans initialisation, l'erreur SECOC_E_UNINIT est prévue, et pour une initialisation ayant échoué, SECOC_E_INIT_FAILED ([SWS_SecOC_00101]).
  • Si le module n'est pas initialisé, SecOC_MainFunctionTx retourne immédiatement (SWS SecOC p. 84).

Le traitement cryptographique proprement dit ne s'exécute pas dans le contexte d'appel des fonctions d'émission ou de réception, mais de manière cyclique. Pour chaque instance configurée de SecOCMainFunctionTx ou SecOCMainFunctionRx, il existe une SecOC_MainFunctionTx_<shortName> ou SecOC_MainFunctionRx_<shortName> propre ([SWS_SecOC_00176], [SWS_SecOC_00171]). La période respective est configurée via SecOCMainFunctionPeriodTx ou SecOCMainFunctionPeriodRx (SWS SecOC p. 130, SWS SecOC p. 129). Une Tx-PDU est traitée dans la Main Function qui est référencée via SecOCTxPduMainFunctionRef ([SWS_SecOC_00276]).

Voie d'émission : de l'Authentic I-PDU à la Secured I-PDU

Une opération d'émission commence par SecOC_IfTransmit ou SecOC_TpTransmit ([SWS_SecOC_00112], [SWS_SecOC_91008]). SecOC copie l'Authentic I-PDU complète dans sa propre mémoire avant que la transmission de la Secured I-PDU ne commence ([SWS_SecOC_00252]). L'appel retourne ensuite.

Lors du prochain appel de SecOC_MainFunctionTx, toutes les nouvelles Authentic I-PDU sont authentifiées. Chaque Secured I-PDU finalisée est immédiatement émise via le PduR (SWS SecOC p. 84). La génération comprend six étapes, de la préparation de la Secured I-PDU jusqu'à l'incrémentation du Freshness Counter et à l'envoi (SWS SecOC p. 33).

Dans le mode CFUNC, la Freshness Value est fournie par l'une des deux fonctions, en fonction de SecOCProvideTxTruncatedFreshnessValue :

  • SecOC_GetTxFreshnessTruncData, qui fournit en plus la valeur tronquée ([SWS_SecOC_00230], [SWS_SecOC_91003]), ou
  • SecOC_GetTxFreshness ([SWS_SecOC_00231], [SWS_SecOC_91004]).

SecOC signale au Freshness Manager que l'envoi d'une Secured I-PDU a été initié via SecOC_SPduTxConfirmation ou FreshnessManagement_SPduTxConfirmation ([SWS_SecOC_00232], [SWS_SecOC_00233]).

Après l'envoi, SecOC assume vis-à-vis de la couche inférieure le rôle d'un module supérieur (SWS SecOC p. 40) :

  • Transmission déclenchée (par ex. FrIf) : la couche inférieure récupère les données avec SecOC_TriggerTransmit ([SWS_SecOC_00127]). Cela suppose un appel préalable de SecOC_IfTransmit ; le mode de fonctionnement AlwaysTransmit ne doit pas être utilisé (SWS SecOC p. 44).
  • Protocoles de transport : les données sont récupérées avec SecOC_CopyTxData ([SWS_SecOC_00129]).
  • Confirmation : SecOC transmet vers le haut le résultat de SecOC_[If|Tp]TxConfirmation via PduR_SecOC[If|Tp]TxConfirmation ([SWS_SecOC_00063]).

Si SecOCPduType = SECOC_TPPDU est configuré, SecOC_TpTransmit déclenche l'opération d'émission. SecOC récupère alors l'Authentic I-PDU par segments auprès de la couche supérieure via PduR_SecOCTpCopyTxData ([SWS_SecOC_00253], [SWS_SecOC_00254], SWS SecOC Fig. 9.4 p. 109).

Voie de réception : mettre en mémoire tampon, vérifier, transmettre

En réception, SecOC applique toujours le même ordre : prendre d'abord l'intégralité de la Secured I-PDU dans sa propre mémoire, puis la vérifier dans le prochain SecOC_MainFunctionRx (SWS SecOC p. 50). L'Authentic I-PDU n'est copiée que lorsque la Secured I-PDU est entièrement disponible ([SWS_SecOC_00255]).

  • Interfaces de bus : la réception est signalée via SecOC_RxIndication ([SWS_SecOC_00124]).
  • Protocoles de transport : la réception s'effectue via SecOC_StartOfReception, SecOC_CopyRxData et SecOC_TpRxIndication ([SWS_SecOC_00130], [SWS_SecOC_00128], [SWS_SecOC_00125]). Pour SECOC_TPPDU, SecOC transmet le début de réception à la couche supérieure via PduR_SecOCTpStartOfReception (SWS SecOC p. 54).

La vérification suit six étapes fixes ([SWS_SecOC_00040]) :

  1. Décomposer l'Authentic I-PDU, la Freshness Value et l'Authenticator.
  2. Obtenir la Freshness Value auprès du Freshness Manager.
  3. Former les données à authentifier.
  4. Vérifier l'Authenticator.
  5. Confirmer le résultat au DEM Freshness Manager.
  6. Transmettre l'Authentic I-PDU à la couche supérieure.

La fonction qui fournit la Freshness Value dépend de SecOCUseAuthDataFreshness :

  • Pour FALSE, SecOC appelle SecOC_GetRxFreshness ([SWS_SecOC_00247], [SWS_SecOC_91007]).
  • Pour TRUE, SecOC appelle SecOC_GetRxFreshnessAuthData et transmet à cette occasion un extrait de l'Authentic I-PDU ([SWS_SecOC_00246], [SWS_SecOC_91006]).
  • En mode RTE, les mêmes règles s'appliquent aux opérations de FreshnessManagement ([SWS_SecOC_00244], [SWS_SecOC_00245]).

Si la vérification réussit, le résultat est SECOC_VERIFICATIONSUCCESS ([SWS_SecOC_00242]) et l'Authentic I-PDU est transmise à la couche supérieure (PRS SecOC p. 18).

Pour les passerelles, SecOC prend en charge les voies de réauthentification, c'est-à-dire la vérification sur le bus source et une nouvelle authentification pour le bus cible. Le « gatewaying-on-the-fly » n'est pas pris en charge dans ce cadre (SWS SecOC p. 57, SWS SecOC Fig. 9.9 p. 102).

Interfaces d'application : statut de vérification, Override, Default-Pattern

Statut de vérification. SecOC_VerificationStatusType récapitule le résultat de chaque vérification : le Freshness Value ID et un résultat de type SecOC_VerificationResultType ([SWS_SecOC_00160], [SWS_SecOC_00149]). Le Propagation Mode régit l'entité à laquelle le statut est signalé :

  • Avec BOTH ou FAILURE_ONLY, il est transmis à l'application via VerificationStatusIndication, tandis qu'avec NONE, la notification n'a pas lieu ([SWS_SecOC_00271], [SWS_SecOC_91016]).
  • Avec SecOCPropagateOnlyFinalVerificationStatus = TRUE, seul le statut final est signalé, sinon chaque tentative intermédiaire ayant échoué l'est également ([SWS_SecOC_00272]).
  • Le Freshness Manager reçoit le résultat via SecOC_VerificationStatusCallout, par exemple pour synchroniser des compteurs ([SWS_SecOC_00119], [SWS_SecOC_00243]).
  • SecOC_VerifyStatus informe l'application du résultat de vérification ([SWS_SecOC_91014]).

Override. Avec SecOC_VerifyStatusOverride, l'application peut forcer le comportement pour un Freshness Value ID ou Data ID ([SWS_SecOC_00122], [SWS_SecOC_00142]). Les valeurs R20-11 de SecOC_OverrideStatusType ([SWS_SecOC_00991]) sont :

  • SECOC_OVERRIDE_DROP_UNTIL_NOTICE et SECOC_OVERRIDE_DROP_UNTIL_LIMIT : aucune vérification CSM, l'I-PDU est rejetée, le résultat est SECOC_NO_VERIFICATION.
  • SECOC_OVERRIDE_PASS_UNTIL_NOTICE : la vérification a lieu, mais l'I-PDU est transmise quel que soit le résultat.
  • SECOC_OVERRIDE_CANCEL : met fin à un Override actif.

Le passage du document de la R23-11 mentionne en plus SECOC_OVERRIDE_SKIP_UNTIL_LIMIT et SECOC_OVERRIDE_PASS_UNTIL_LIMIT (SWS SecOC p. 102). Le texte de l'exigence de la R20-11 est tronqué à cet endroit dans le payload.

Default-Pattern. SecOC_SendDefaultAuthenticationInformation active ou désactive l'émission avec SecOCDefaultAuthenticationInformationPattern pour chaque Freshness Value ID ([SWS_SecOC_91013]). L'interface n'existe que si ce pattern est configuré ([SWS_SecOC_00002], [SWS_SecOC_91020]).

Configuration, structure des PDU et Cryptographic I-PDU séparées

Conteneurs de configuration. Chaque PDU d'émission à sécuriser est configurée dans SecOCTxPduProcessing, et chaque PDU de réception à vérifier dans SecOCRxPduProcessing. En font respectivement partie le Data ID, le Freshness Value ID, les longueurs et les compteurs de tentatives (SWS SecOC p. 155, SWS SecOC p. 140).

Structure de PDU. Une Secured I-PDU se compose d'un en-tête optionnel, de l'Authentic I-PDU, d'une Freshness Value optionnelle et de l'Authenticator. La Freshness Value et l'Authenticator peuvent être transmis sous forme tronquée (SWS SecOC Fig. 5 p. 29). SecOC remplit les zones non utilisées avec SecOCTxPduUnusedAreasDefault ([SWS_SecOC_00269]). La portion que le récepteur extrait en tant qu'Authentic I-PDU dépend de l'en-tête et du type de longueur :

  • Sans en-tête et avec une longueur statique, la longueur configurée de la PDU globale s'applique ([SWS_SecOC_00257]).
  • Sans en-tête et avec une longueur dynamique, la longueur que la couche inférieure signale s'applique ([SWS_SecOC_00258]).
  • Avec en-tête, la longueur provenant de l'en-tête s'applique ([SWS_SecOC_00259]).

Cryptographic I-PDU séparée. Avec SecOCTxSecuredPduCollection, une Secured I-PDU est émise sous la forme de deux messages : comme Authentic I-PDU et comme Cryptographic I-PDU séparée ([SWS_SecOC_00201], TPS SystemTemplate Fig. 6.18 p. 244). Les règles suivantes s'appliquent à cet effet :

  • Les deux messages sont émis dans le même cycle de Main Function ([SWS_SecOC_00202]).
  • Un Message Linker, c'est-à-dire un extrait de l'Authentic I-PDU répété dans la Cryptographic I-PDU, lie les deux messages ([SWS_SecOC_00209], [SWS_SecOC_00210]).
  • Le récepteur ne procède à la vérification que lorsque les deux messages sont disponibles avec un Linker correspondant ([SWS_SecOC_00203], [SWS_SecOC_00211]).
  • En cas de succès, SecOC vide les deux tampons. En cas d'échec, les deux restent mis en mémoire tampon et la vérification est répétée lors de l'arrivée de nouvelles données ([SWS_SecOC_00207], [SWS_SecOC_00208]).
  • La couche supérieure ne reçoit E_OK que si les deux confirmations d'émission étaient E_OK ([SWS_SecOC_00270]).
  • Avec la stratégie de dépassement QUEUE, aucune Rx-Collection n'est autorisée ([SWS_SecOC_CONSTR_00265]).

Comportement en cas d'erreur

Côté émission.

  • Si le CSM signale une erreur récupérable (par ex. E_BUSY), SecOC n'émet aucune Secured I-PDU. L'Authentic I-PDU est conservée et est de nouveau authentifiée dans la prochaine Main Function ([SWS_SecOC_00151]).
  • Si SecOCAuthenticationBuildAttempts est atteint, SecOC signale SECOC_E_CRYPTO_FAILURE à la DET ([SWS_SecOC_00155]).
  • Lorsque la limite est atteinte, en cas de E_NOT_OK de la requête de fraîcheur ou en cas d'erreur CSM non récupérable, SecOC émet avec le Default-Pattern si celui-ci est activé ([SWS_SecOC_00229]).
  • Si le pattern n'est pas configuré, SecOC supprime l'Authentic I-PDU et interrompt la demande d'émission (SWS SecOC p. 124). Un pattern configuré mais non activé devrait être traité de la même manière, car le reste de [SWS_SecOC_00229] est tronqué dans le payload.

Interruption et erreurs lors du transfert de données.

  • Si la couche supérieure interrompt via SecOC_IfCancelTransmit ou SecOC_TpCancelTransmit ([SWS_SecOC_00113], [SWS_SecOC_91009]), SecOC informe immédiatement la couche inférieure, arrête toutes les actions associées et libère les tampons (SWS SecOC p. 48).
  • Si la couche inférieure signale une erreur d'émission, SecOC ne la traite qu'en omettant la confirmation à la couche supérieure (ibid.).
  • Si PduR_SecOCTpCopyTxData renvoie BUFREQ_E_BUSY, SecOC réitère l'appel dans la prochaine Main Function. En cas de BUFREQ_E_NOT_OK, SecOC interrompt immédiatement avec E_NOT_OK ([SWS_SecOC_00260], [SWS_SecOC_00266]).
  • Pour la réception, la même règle s'applique en cas de PduR_SecOCTpCopyRxData ([SWS_SecOC_00267]).

Côté réception. SecOC gère deux compteurs par Secured I-PDU, qui sont initialisés à 0 lors du premier traitement ([SWS_SecOC_00234], [SWS_SecOC_00235]) :

  • Compteur de build : s'incrémente en cas de E_BUSY de la requête de fraîcheur et lors d'erreurs CSM récupérables ([SWS_SecOC_00236], [SWS_SecOC_00237]). En dessous de SecOCAuthenticationBuildAttempts, une nouvelle tentative est effectuée dans la prochaine Rx-Main-Function ([SWS_SecOC_00238]). À la limite, SecOC rejette la PDU avec SECOC_AUTHENTICATIONBUILDFAILURE ([SWS_SecOC_00240]).
  • Compteur de vérification : s'incrémente lors d'un véritable échec de vérification, et le compteur de build est alors réinitialisé ([SWS_SecOC_00239]). À la limite SecOCAuthenticationVerifyAttempts ou en cas de E_NOT_OK/KEY_FAILURE, SecOC rejette la PDU avec SECOC_VERIFICATIONFAILURE ([SWS_SecOC_00241]).

Si la requête de fraîcheur renvoie E_NOT_OK, la PDU est rejetée avec SECOC_FRESHNESSFAILURE ([SWS_SecOC_00256]). En revanche, [SWS_SecOC_00248] décrit le même cas comme un échec de vérification comptabilisé avec notification DET SECOC_E_FRESHNESS_FAILURE ([SWS_SecOC_00114]). Interprétation : les deux exigences s'appliquent à R20-11. La spécification ne précise pas comment elles se délimitent mutuellement ; le projet d'intégration devrait clarifier ce point avec le fournisseur.

Un override peut outrepasser le rejet ([SWS_SecOC_00240]). Si une PDU de longueur statique s'avère trop courte, SecOC la rejette silencieusement ([SWS_SecOC_00268]). R20-11 lie cela au paramètre EcuC DynamicLength ; le passage documentaire de R23-11 utilise à la place SecOCDynamicRuntimeLengthHandling (SWS SecOC p. 52).

Security Events. SecOC signale les échecs de vérification MAC et les Freshness Values manquantes sous forme de SECOC_SEV_MAC_VERIFICATION_FAILED ou SECOC_SEV_FRESHNESS_NOT_AVAILABLE respectivement à l'IdsM ([SWS_SecOC_00274], [SWS_SecOC_00275]).

Utilisation de SecOC_OverrideStatusType

Le type d'énumération SecOC_OverrideStatusType définit, conformément à [SWS_SecOC_00991], les différents modes de fonctionnement pour la dérogation (override) de l'état de vérification dans le module SecOC. Le type est fourni via le fichier d'en-tête Rte_SecOC_Type.h et commande le comportement lors du traitement et de la transmission d'I-PDU à la couche supérieure.

Les valeurs d'énumération se subdivisent selon leur sémantique et leur durée de validité (jusqu'à révocation ou jusqu'à ce qu'un compteur Number Of Messages To Override soit atteint) :

  • Rejeter (Drop) : avec SECOC_OVERRIDE_DROP_UNTIL_NOTICE (0x00) et SECOC_OVERRIDE_DROP_UNTIL_LIMIT (0x01), aucune vérification d'authentificateur n'est effectuée (aucun appel CSM). L'I-PDU concernée est rejetée et le résultat de vérification est défini à SECOC_NO_VERIFICATION.
  • Interrompre : une dérogation active de l'état de vérification est interrompue via SECOC_OVERRIDE_CANCEL (0x02).
  • Vérifier et transmettre (Pass) : avec SECOC_OVERRIDE_PASS_UNTIL_NOTICE (0x40) ainsi que SECOC_OVERRIDE_PASS_UNTIL_LIMIT (0x42), la vérification a lieu et l'I-PDU est transmise à la couche supérieure, quelle que soit l'issue. En cas d'erreur, le résultat est défini à SECOC_VERIFICATIONFAILURE_OVERWRITTEN.
  • Ignorer et transmettre (Skip) : avec SECOC_OVERRIDE_SKIP_UNTIL_LIMIT (0x41) et SECOC_OVERRIDE_SKIP_UNTIL_NOTICE (0x43), la vérification n'a pas lieu, l'I-PDU est transmise et le résultat est SECOC_NO_VERIFICATION. Si une collection de PDU (SecOCRxSecuredPduCollection) est configurée, SecOC traite directement le SecOCRxAuthenticPdu sans attendre le SecOCRxCryptographicPdu.

Remarque : cette note d'utilisation est basée sur les stipulations de la spécification [SWS_SecOC_00991] dans la version AUTOSAR R20-11.
