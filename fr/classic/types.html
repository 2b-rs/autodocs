1. Architecture système et rôle du cluster de modules

Le cluster « General & Standard Types » constitue le fondement des types de la Classic Platform. Il ne fournit aucun service d'exécution. Il spécifie des types de données, des symboles et un type de pointeur de fonction sur lesquels reposent conjointement les modules BSW, la RTE et les transformeurs. Std_ReturnType est expressément « partagé entre la RTE et les modules BSW » [SWS_Std_00005]. Selon les exigences générales du BSW, Std_Types.h inclut les en-têtes Platform_Types.h et Compiler.h. Tout module utilisant des types entiers AUTOSAR ou le type de retour standard inclut Std_Types.h (SRS BSWGeneral p. 62).

  • platform (Platform_Types.h) définit la base dépendante de la plateforme :
    • Des types entiers de largeur fixe de uint8 à sint64 [SWS_Platform_00013] [SWS_Platform_00067], uniquement en complément à deux [SWS_Platform_00061].
    • Des types *_least optimisés, par exemple pour les compteurs de boucle [SWS_Platform_00020] (SWS PlatformTypes p. 17).
    • float32/float64 selon l'IEEE 754-2008 [SWS_Platform_00041].
    • boolean [SWS_Platform_00026].
    • Les symboles CPU_TYPE, CPU_BIT_ORDER et CPU_BYTE_ORDER [SWS_Platform_00064] [SWS_Platform_00038] [SWS_Platform_00039].
    • VoidPtr/ConstVoidPtr pour les tampons [SWS_Platform_91001] [SWS_Platform_91002].
    • Les extensions de ce fichier sont interdites [SWS_Platform_00002].
  • std (Std_Types.h) définit :
    • Std_ReturnType avec E_OK/E_NOT_OK [SWS_Std_00006].
    • Les symboles de commutation STD_ON/OFF, STD_HIGH/LOW et STD_ACTIVE/IDLE [SWS_Std_00010] [SWS_Std_00007] [SWS_Std_00013].
    • Std_VersionInfoType [SWS_Std_00015].
    • Les types de transformeur Std_TransformerError, Std_TransformerClass, Std_MessageTypeType et Std_MessageResultType [SWS_Std_00021] [SWS_Std_00024] [SWS_Std_91001] [SWS_Std_91002].
  • comstack (ComStack_Types.h) définit les types de communication :
    • PduIdType et PduLengthType [SWS_COMTYPE_00005] [SWS_COMTYPE_00008].
    • PduInfoType [SWS_COMTYPE_00011].
    • BufReq_ReturnType [SWS_COMTYPE_00012].
    • Les types TP TpDataStateType, RetryInfoType et TPParameterType [SWS_COMTYPE_00027] [SWS_COMTYPE_00037] [SWS_COMTYPE_00031].
    • Les descripteurs de canal et de réseau NetworkHandleType et PNCHandleType [SWS_COMTYPE_00038] [SWS_COMTYPE_00036].

Des références à des normes externes existent via l'ISO 17356-3 (OSEK) et l'IEEE 754-2008. En raison de l'ISO 17356-3, E_OK doit être défini sous la protection de STATUSTYPEDEFINED [SWS_Std_00006]. L'IEEE 754-2008 s'applique aux types à virgule flottante [SWS_Platform_00042].

Diagramme de contexte : les trois en-têtes de types constituent une base de dépendance pour les modules BSW, les modules de communication et la RTE. Sources : SRS BSWGeneral p. 62, SWS ADC p. 13, SWS WdgIf p. 11, [SWS_COMTYPE_00038], [SWS_Std_00005]

2. Interaction et chemins d'interaction

Les modules se superposent par couches. Les types ComStack sont dérivés des types de plateforme : NetworkHandleType est un uint8 dans la plage 0..255 et identifie un canal de communication [SWS_COMTYPE_00038]. La largeur de PduIdType est générée dans ComStack_Cfg.h sous la forme uint8 ou uint16 en fonction de la configuration EcuC [SWS_COMTYPE_00005] (ECUConfiguration p. 153).

Un chemin discret mais important relie PduInfoType à la définition de la plateforme. Les éléments de métadonnées de plus de 8 bits sont ordonnés selon l'ordre des octets de la plateforme [SWS_COMTYPE_00011]. Cet ordre est défini par CPU_BYTE_ORDER : HIGH_BYTE_FIRST pour Big Endian, LOW_BYTE_FIRST pour Little Endian [SWS_Platform_00050] [SWS_Platform_00051]. Dans la disposition Big Endian, l'octet de poids fort se trouve à l'adresse n (SWS PlatformTypes p. 16).

L'ordre des bits dans les registres est un sujet à part entière. En Big Endian, CPU_BIT_ORDER est défini sur MSB_FIRST [SWS_Platform_00048]. La spécification met en garde contre la confusion entre la dénomination des bits et leur poids (SWS PlatformTypes p. 15).

Les types de pointeurs régissent le sens des tampons. ConstVoidPtr désigne les tampons transmis à l'appelé. VoidPtr désigne les tampons contenant des données qui retournent à l'appelant [SWS_Platform_91001] [SWS_Platform_91002]. L'interface de service KeyM avec RequestData et ResponseData en constitue un exemple (SWS KeyM p. 111).

Le chemin le plus complexe concerne la chaîne de transformeurs. Std_ExtractProtocolHeaderFieldsType est un pointeur de fonction qui fournit, à partir d'un en-tête de protocole, les valeurs canoniques Std_MessageTypeType (Request/Response) et Std_MessageResultType (OK/ERROR) [SWS_Std_91003] [SWS_Std_00017] [SWS_Std_00019]. Les transformeurs inverses reçoivent facultativement ce pointeur en argument (ASWS TransformerGeneral p. 40). La bibliothèque E2E traite les valeurs extraites, par ex. dans E2E_P04mSinkCheck (SWS E2ELibrary p. 109). Ces passages de documents proviennent de versions ultérieures. Pour R20-11, seule la définition de type elle-même est normative.

Diagramme de séquence : un transformeur E2E côté serveur évalue via le pointeur de fonction les champs d'en-tête d'un transformeur SOME/IP situé en amont et les transmet à la vérification E2E. Interprétation : l'association d'un transformeur SOME/IP avec le profil E2E 4m constitue un exemple de chaîne. Sources : [SWS_Std_91003], SWS E2ETransformer p. 54, SWS SomeIpXf p. 61, SWS E2ELibrary p. 109

3. Synchronisation, réentrance et contextes de tâche

Les modules de types ne possèdent pas de MainFunctions propres ni de zones exclusives. Le seul élément comportemental dans le payload est le type de pointeur de fonction, et il est spécifié comme synchrone et réentrant [SWS_Std_91003]. Quiconque fournit une fonction pour ce pointeur doit donc respecter ces propriétés. SomeIpXf_ExtractProtocolHeaderFields est ainsi synchrone et réentrant (SWS SomeIpXf p. 61).

Les types de descripteurs servent de critère de distinction de réentrance dans les API utilisateur :

  • Les services de mise en miroir de bus sont « réentrants pour différents réseaux », c'est-à-dire différentes valeurs de NetworkHandleType [SWS_COMTYPE_00038] (SWS BusMirroring p. 77).
  • CanIf_TriggerTransmit est réentrant pour différentes valeurs de PduIdType [SWS_COMTYPE_00005] (SWS CanIf p. 107).
  • Std_ReturnType est également renvoyé par des fonctions qui s'exécutent au niveau interruption ou tâche, comme CanIf_CheckWakeup (SWS CanIf p. 101).

Les fonctions Get-Version-Information reposant sur Std_VersionInfoType doivent être synchrones et réentrantes [SWS_Std_00015] (SWS BSWGeneral p. 76).

4. Cycles de vie et modes de fonctionnement

La majeure partie du cluster intervient au moment de la compilation et de la configuration :

  • CPU_TYPE décrit la largeur de registre de la plateforme [SWS_Platform_00044] [SWS_Platform_00045].
  • STD_ON/STD_OFF activent ou désactivent des API par préprocesseur, par ex. <Ma>VersionInfoApi [SWS_Std_00010] (SWS BSWGeneral p. 76).
  • TRUE/FALSE sont protégés contre les prédéfinitions du compilateur à l'aide de #ifndef [SWS_Platform_00056] [SWS_Platform_00054].

À l'exécution, les types décrivent des états logiques. STD_ACTIVE/STD_IDLE désignent des états logiques [SWS_Std_00013]. STD_HIGH/STD_LOW désignent des niveaux physiques [SWS_Std_00007].

L'état du tampon TP constitue un véritable cycle de vie. RetryInfoType combine TpDataStateType avec l'offset TxTpDataCnt [SWS_COMTYPE_00037] :

  • TP_DATACONF confirme les données copiées jusqu'ici.
  • TP_DATARETRY demande une nouvelle copie à partir de l'offset spécifié [SWS_COMTYPE_00027].

Le schéma de J1939Tp mentionne en outre TP_CONFPENDING, qui n'est pas contenu dans l'extrait abrégé de l'exigence (SWS J1939Tp p. 55).

Diagramme de séquence : RetryInfoType commande la répétition d'un bloc de données après la perte de TP.DT. Sources : SWS J1939Tp p. 55, [SWS_COMTYPE_00027], [SWS_COMTYPE_00037]

5. Gestion des erreurs, traçage DET et dégradation

Std_ReturnType est le canal d'erreur central. Il est normalement utilisé avec E_OK ou E_NOT_OK. Les valeurs spécifiques au module se situent dans les 6 bits inférieurs (0x02–0x3F) et portent le préfixe du module. Les deux bits supérieurs sont réservés à la RTE [SWS_Std_00011] [SWS_Std_00005] (SWS StandardTypes p. 15). Exemples :

  • La RTE utilise les bits réservés pour les erreurs d'infrastructure à partir de 128 et pour les erreurs superposées avec la valeur 64 (SWS RTE p. 586).
  • Le pilote CAN ajoute CAN_BUSY = 0x02 (SWS CAN p. 54).
  • Dans le modèle UML, de telles extensions sont modélisées sous forme de <Ma>_ReturnType avec le stéréotype « extra_literals » (BSW UML Modeling Guide p. 28).

Pour les services BSW que l'application appelle via la RTE, la RTE attend toujours Std_ReturnType (RS BSWGeneral p. 63).

Les requêtes de tampon utilisent leur propre type BufReq_ReturnType. Avec BUFREQ_E_BUSY, la répétition incombe au demandeur, tandis que BUFREQ_E_OVFL signale une longueur impossible à satisfaire [SWS_COMTYPE_00012]. Conjointement avec TP_DATARETRY, il en découle la stratégie de dégradation de la pile de communication : répéter plutôt qu'interrompre.

La RTE signale les erreurs de transformeur via Std_TransformerError. Le type contient un code d'erreur et une Std_TransformerClass (Serializer, Safety, Security, Custom) [SWS_Std_00021] [SWS_Std_00024]. Il apparaît par exemple comme paramètre OUT facultatif de Rte_Call (SWS RTE p. 731).

Par rapport aux passages de documents plus récents, il existe des différences de version. Dans ces cas, c'est R20-11 qui s'applique :

  • errorCode est un uint8 dans R20-11 [SWS_Std_00021]. Les versions ultérieures utilisent Std_TransformerErrorCode (SWS StandardTypes p. 16).
  • Le type préliminaire Std_TransformerForwardCode connaît dans R20-11 les valeurs E_SAFETY_INVALID_REP/SEQ/CRC [SWS_Std_00029]. Les versions plus récentes les renomment en STD_E_FORWARDCODE_* (SWS StandardTypes p. 17).
  • boolean est dans R20-11 l'entier non signé le plus court nativement pris en charge [SWS_Platform_00027], et non pas le C99-_Bool comme plus tard (SWS PlatformTypes p. 18).
  • PNCHandleType est un uint8 dans R20-11 [SWS_COMTYPE_00036], plus tard un uint16 (SWS ComStackTypes p. 17).

Le traçage DET concerne le cluster indirectement. Les API utilisateur avec Std_VersionInfoType* vérifient si le pointeur est NULL et signalent par ex. CAN_E_PARAM_POINTER [SWS_Std_00015] (SWS CAN p. 57). Pour boolean, les affectations arithmétiques sont interdites et le type doit pouvoir être utilisé comme pointeur [SWS_Platform_00034] [SWS_Platform_00060].
