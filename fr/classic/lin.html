Architecture système et rôle du cluster de modules

Le cluster constitue la pile de communication LIN de la Classic Platform, du matériel jusqu'à la gestion des modes. Les quatre modules se répartissent les tâches comme suit :

  • Lin est le pilote MCAL. Il encapsule le contrôleur LIN ou l'UART et calcule la somme de contrôle classique ou améliorée [SWS_Lin_00019]. Il prend en charge les trames en tant que Lin_PduType avec PID, modèle de somme de contrôle, type de réponse, longueur et pointeur de SDU [SWS_Lin_00232].
  • LinTrcv commande le transceiver externe via les modes LINTRCV_TRCV_MODE_NORMAL, …_STANDBY et …_SLEEP [SWS_LinTrcv_00168] et vérifie les événements de réveil [SWS_LinTrcv_00012].
  • LinIf est l'abstraction matérielle. Il gère les tables d'ordonnancement et les états de canal, et contient le protocole de transport LinTp [SWS_LinIf_00350].
  • LinSM applique les demandes de mode du ComM [SWS_LinSM_00126] et signale l'état et l'ordonnancement au BswM [SWS_LinSM_00229].

Le rôle du nœud détermine par configuration les fonctions qu'un module fournit :

  • Ce n'est que dans le maître qu'existent Lin_SendFrame, Lin_GoToSleep et Lin_GetStatus [SWS_Lin_00287] [SWS_Lin_00288] [SWS_Lin_00289] ainsi que LinSM_ScheduleRequest [SWS_LinSM_00241].
  • Ce n'est que dans l'esclave qu'existent les callbacks de pilote du LinIf [SWS_LinIf_00863] [SWS_LinIf_00866] et LinSM_GotoSleepIndication [SWS_LinSM_00243].
  • Pour les esclaves, LinIf gère en outre le NAD et les PID selon le modèle de nœud de l'ISO 17987-3 [SWS_LinIf_00767] [SWS_LinIf_00778] LinIf-SWS p. 59.

Interaction et chemins d'interaction

Chemin maître. LinIf exécute la table d'ordonnancement dans LinIf_MainFunction_<LinIfChannel.ShortName> [SWS_LinIf_00384]. Un créneau d'émission se déroule comme suit :

  1. LinIf récupère les données via <User_TriggerTransmit> [SWS_LinIf_00528] et les transmet avec Lin_SendFrame [SWS_Lin_00191].
  2. Si la couche supérieure renvoie E_NOT_OK, la trame n'est pas émise [SWS_LinIf_00706].
  3. Au plus tôt après la longueur de trame maximale, LinIf interroge le statut avec Lin_GetStatus [SWS_Lin_00168] LinIf-SWS p. 35.
  4. En cas de LIN_TX_ERROR ou LIN_TX_BUSY, <User_TxConfirmation> suit avec E_NOT_OK [SWS_LinIf_00728].

Si la couche supérieure est le PduR, <User_TriggerTransmit> est fixe PduR_LinIfTriggerTransmit [SWS_LinIf_00722]. LinIf_Transmit ne mémorise que les trames sporadiques (maître) ou événementielles (esclave) [SWS_LinIf_00201] LinIf-SWS p. 79. Sous NULL_SCHEDULE, il la rejette [SWS_LinIf_00719].

Chemin esclave. Le déroulement est déclenché par l'en-tête du maître :

  1. Le pilote signale chaque en-tête via LinIf_HeaderIndication avec le PID et un pointeur vers son tampon [SWS_Lin_00280] [SWS_LinIf_91004].
  2. LinIf évalue le PID :
    • Pour une trame d'émission, <User_TriggerTransmit> écrit directement dans le tampon du pilote [SWS_LinIf_00738], et LinIf positionne Drc = LIN_FRAMERESPONSE_TX [SWS_LinIf_00739].
    • Les trames de réception reçoivent LIN_FRAMERESPONSE_RX [SWS_LinIf_00733].
    • Les trames sans pertinence reçoivent LIN_FRAMERESPONSE_IGNORE [SWS_LinIf_00748].
  3. Lin évalue Drc, Cs et Dl [SWS_Lin_00282] [SWS_Lin_00283] [SWS_Lin_00286].
  4. Lin conclut chaque réponse pertinente avant l'en-tête suivant par une Rx-Indication, une Tx-Confirmation ou une Error-Indication [SWS_Lin_00285].
  5. LinIf transmet le résultat à <User_RxIndication> ou <User_TxConfirmation> [SWS_LinIf_00734] [SWS_LinIf_00741].

Des versions plus récentes remplacent ces callouts par la voie LSduR (statut DRAFT) LinIf-SWS p. 43. Pour R20-11, ce sont les interfaces <User_…> qui s'appliquent.

Synchronisation, réentrance et contextes de tâches

Traitement cyclique. Il existe une LinIf_MainFunction_<LinIfChannel.ShortName> par canal. D'autres API LinIf telles que LinIf_GotoSleep, LinIf_Transmit, LinIf_ScheduleRequest et LinIf_Wakeup peuvent l'interrompre. Les zones partagées doivent donc être protégées LinIf-SWS p. 119. LinSM_MainFunction gère les temporisateurs d'expiration [SWS_LinSM_00156].

Appels directs. Les transitions vers le sommeil n'attendent délibérément pas la MainFunction suivante. Elles s'exécutent ainsi dans le contexte de l'appelant :

  • LinSM appelle immédiatement LinIf_GotoSleep [SWS_LinSM_00036] [SWS_LinSM_00231].
  • LinIf appelle immédiatement Lin_GoToSleepInternal [SWS_LinIf_00757].

Callbacks d'esclave. Les callbacks sont réentrants pour différents canaux, mais pas pour le même [SWS_LinIf_91005] [SWS_LinIf_91006] [SWS_LinIf_91007]. Sur le schéma, LinIf_HeaderIndication suit directement l'interruption matérielle LinIf-SWS p. 121. Interprétation : Les callbacks devraient ainsi s'exécuter la plupart du temps dans le contexte d'une ISR. <User_TriggerTransmit> devrait donc rester courte. Le pilote lui-même émet et reçoit de manière non bloquante Lin-SWS p. 28.

Réentrance dans R20-11. R20-11 déclare Lin_GoToSleep, Lin_Wakeup und Lin_GetStatus comme « Non Reentrant » [SWS_Lin_00166] [SWS_Lin_00169] [SWS_Lin_00168]. Des documents plus récents autorisent la réentrance pour différents canaux Lin-SWS p. 43. La version la plus stricte est normative pour R20-11.

Un écart similaire existe pour le transceiver : LinIf_SetTrcvMode est réentrant [SWS_LinIf_00544], mais le LinTrcv_SetOpMode appelé ne l'est pas [SWS_LinTrcv_00002]. Interprétation : L'intégration devrait sérialiser les appels concurrents.

Multicœur. Le canal et le canal de transceiver doivent appartenir à la même partition ECUC [SWS_Lin_CONSTR_00279] [SWS_LinTrcv_00177].

Gestion des erreurs, traçage DET et dégradation

Erreurs de développement (DET). Tous les modules vérifient les paramètres et l'état d'initialisation auprès du DET :

  • LinIf : [SWS_LinIf_00376] [SWS_LinIf_00849]
  • Lin, notamment LIN_E_STATE_TRANSITION [SWS_Lin_00258] [SWS_Lin_00260]
  • LinSM : [SWS_LinSM_00053] [SWS_LinSM_00240]
  • LinTrcv : [SWS_LinTrcv_00005] LinTrcv-SWS p. 26

Erreurs d'exécution. Lin requiert impérativement Dem_SetEventStatus [SWS_Lin_00234]. Le pilote signale les dépassements de délai matériels sous la forme LIN_E_TIMEOUT [SWS_Lin_00290]. Dans l'esclave, Lin renvoie les erreurs en tant que Lin_SlaveErrorType [SWS_Lin_91140] [SWS_Lin_00277]. LinIf considère alors la réponse comme perdue et signale LINIF_E_RESPONSE, sauf pour LIN_ERR_HEADER [SWS_LinIf_00735] [SWS_LinIf_00729]. LinSM signale l'absence de callbacks sous la forme LINSM_E_CONFIRMATION_TIMEOUT [SWS_LinSM_00224].

Dégradation. Plusieurs mécanismes maintiennent le fonctionnement de manière ordonnée après des erreurs :

  • Signal response_error : Les erreurs de réponse positionnent le signal via Com_SendSignal [SWS_LinIf_00744] [SWS_LinIf_00764]. Il est réinitialisé après une émission réussie [SWS_LinIf_00747] LinIf-SWS p. 58.
  • Cohérence de LinSM : Lors de E_NOT_OK, LinSM applique à nouveau l'état antérieur afin que ComM et BswM reçoivent une indication [SWS_LinSM_00177].
  • Interruptions de LinTp : En cas de dépassement de délai N_As ou N_Cr, LinTp s'interrompt et signale E_NOT_OK au PduR [SWS_LinIf_00801] [SWS_LinIf_00806].
  • Pénurie de tampons : En l'absence de tampon de réception, LinTp suspend les en-têtes SRF [SWS_LinIf_00679]. À défaut, il retourne avec abandon à l'ordonnancement applicatif [SWS_LinIf_00792] [SWS_LinIf_00879].
  • Node Configuration : LinIf rejette une réponse en attente lors du dépassement de délai N_As [SWS_LinIf_00786].
