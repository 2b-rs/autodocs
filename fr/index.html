L'Adaptive Platform en une phrase

L’AUTOSAR Adaptive Platform est un environnement d'exécution orienté services pour les ordinateurs de véhicules puissants : les applications adaptatives s'exécutent en tant que processus POSIX indépendants, sont démarrées et surveillées de manière dynamique et communiquent via des services définis contractuellement au lieu de signaux câblés statiquement (EXP PlatformDesign §3.3 « Adaptive Platform – Characteristics », §8.2 « Service Oriented Communication »).

ARA — l’interface de programmation de cette référence

Tous les espaces de noms ara::* documentés ici forment ensemble l'interface ARA (AUTOSAR Runtime for Adaptive Applications). Chaque Functional Cluster de la plateforme exporte son API C++ dans son propre espace de noms — depuis les types de base en ara::core jusqu'à la communication de service en ara::com jusqu'aux services de plateforme tels que ara::exec, ara::per ou ara::crypto (EXP PlatformDesign §4.1 « Logical view », EXP SWArchitecture §9.1 « Building Block View – Overview »).

Concepts généraux

  • Machine & Software Cluster : Un Machine est l'environnement d'exécution (éventuellement virtualisé) ; Le logiciel est fourni sous forme de Software Cluster installable et mis à jour via ara::ucm (EXP SWArchitecture §13.4 « Software Cluster », §13.5 « Machine »).
  • Groupes de fonctions et états : les processus sont affectés à des groupes de fonctions ; ara::sm demande au Execution Management de démarrer/arrêter les processus (EXP SWArchitecture §13.2 « Function Group », EXP PlatformDesign chap. 7 « State Management ») via les états du groupe de fonctions.
  • Manifests : les Execution, Service Instance et Machine Manifests configurent déclarativement le Deployment, le comportement de démarrage et la liaison de service (EXP PlatformDesign §4.4 « Manifest », EXP SWArchitecture §13.6 « Manifest »).
  • Gestion des erreurs sans exceptions : À l'échelle de la plateforme, les erreurs sont renvoyées sous la forme de ara::core::Result/ErrorCode (EXP PlatformDesign §18.1 « Error Handling », EXP SWArchitecture §13.12 « Error Handling »).
  • Safety & Security transverses : la protection E2E, le Health Monitoring (ara::phm), la pile cryptographique, l’Identity & Access Management, l’Intrusion Detection (ara::idsm) et le pare-feu (ara::fw) sécurisent la plateforme et la communication (EXP PlatformDesign chap. 17 « Safety », EXP SWArchitecture §13.13 « Trusted Platform »).

Interconnexions entre les modules

Cadres arrondis = modules ; nœuds = sous-domaines d’un module (namespaces ou groupes fonctionnels). Flèche A → B : les emplacements d’API du sous-domaine A (signatures, champs, paramètres) référencent des types du sous-domaine B — déterminé à partir des déclarations liées de cette référence ; l’épaisseur du trait correspond au nombre d’emplacements de référence (nombre exact dans l’infobulle de la flèche). Étiquette d’arête = type d’interaction avec la cible : valeurs de retour, résultats asynchrones, gestion des erreurs, types de données, adressage d’instances, fonctions utilitaires ; « utilise » désigne les autres références de types. Flèches gris clair : modélisation de service via ara::com. Tous les nœuds sont liés aux pages de namespace/classe correspondantes.

API visibilité pour les applications

Tous les éléments de spécification documentés ici ne font pas partie de l'API ARA publique : les documents SWS indiquent dans leur chapitre 5 (« Dépendances vers d'autres Functional Clusters », tableau 5.1 dans chaque cas) quelles interfaces sont exclusivement fournies aux autres Functional Clustern. Cette référence rend cela visible de manière cohérente dans la couleur d'arrière-plan du module, de l'espace de noms et du nom de classe respectifs - sur la page de chaque élément (en-tête de page et étiquette à droite dans la ligne de navigation), dans toutes les références à l'élément dans les pages de niveau supérieur et sur les nœuds liés des diagrammes. Par défaut, les fonds sont très pâles pour assurer une bonne lisibilité et deviennent un peu plus intenses au survol de la souris :

  • APPLICATION Bleu : Peut être utilisé directement par les applications adaptatives – par ex. Par ex. ara::core, ara::com, ara::log, ara::per, ara::crypto, ara::diag, ara::rds, ara::shwa (s'exécute comme une bibliothèque dans le processus d'application, SWS SHWA chap. 1), ara::tsync (utilisation de la base de temps active et passive, SWS TSync §2.2) et ara::idsm (applications comme capteurs de sécurité, SWS IdsM §7.2). ara::exec::ExecutionClient appartient également ici, mais ne peut signaler que son propre état de processus [SWS_EM_01401].
  • PRIVILEGED Rot :  uniquement pour les applications dédiées autorisées via IAM ou le mappage de manifeste ; l'utilisateur autorisé est entre parenthèses dans la ligne de navigation. Exemples : le PackageManagement-Service de ara::ucm (« UCM Client » = par exemple client OTA ou application de diagnostic, SWS UCM §7.1), le StateMachine-Services de ara::sm pour une application de contrôle SM [SWS_SM_00600], l'API Suspend-to-RAM ara::sm::s2r (uniquement les satellites authentifiés IAM avec SuspendToRamSatelliteMapping, [SWS_SM_00715]) et ara::fw (changement d'état uniquement avec AdaptiveFirewallToPortPrototypeMapping, [AP_SWS_Fw_40013]).
  • INTERNAL Gris foncé : interfaces purement internes au cluster, assurément non destinées aux applications ; le Functional Cluster utilisateur figure entre parenthèses dans la barre de navigation. Exemples : ara::exec::StateClient avec FunctionGroup/FunctionGroupState (uniquement pour State Management, SWS EM Tab. 5.1), l’ensemble du module ara::nm (interface de service pour applications supprimée, les demandes réseau passent par State Management, SWS NM §4.1 et Tab. 5.1), ara::phm::RecoveryAction (SWS PHM Tab. 5.1) ainsi que toutes les interfaces apext::* des annexes normatives « Platform Extension Interfaces » (intégration de plateforme vers le logiciel de base : watchdog, alimentation, transport UDS, Freshness Value Manager, Trace/ARTI).
