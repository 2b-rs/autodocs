Log and Trace comme couche de routage

ara::log transfère les messages des applications et des Functional Clusters vers les récepteurs configurés. L'application et le contexte sont séparés via des identifiants ; le seuil filtre les niveaux de gravité avant qu'un backend ne serve la console, le fichier ou le réseau. Comportement en cas d'erreur

Les erreurs dans le framework de journalisation ou dans le système sous-jacent ne devraient pas affecter le processus de candidature : les interfaces en question n'ont ni de valeurs de retour ni ne lèvent d'exceptions ; Les appels sont ignorés silencieusement en cas d'une telle erreur. SWS Log and Trace §7.1.6 « Initialization of the Logging framework » [SWS_LOG_00002]

Avant chaque utilisation de ara::log, ara::core::Initialize() est requis. Si le framework ne peut pas traiter les messages, par exemple parce que la communication du démon n'est pas encore établie ou que l'initialisation n'est pas encore terminée, ils sont stockés dans une file d'attente délimitée par logSink.queueSize. Si cette taille est dépassée, les entrées les plus anciennes doivent être supprimées ; la même règle s'applique après un crash de démon. SWS Log and Trace §7.8.1 « Startup » [SWS_LOG_00001] SWS Log and Trace §7.8.3 « Daemon crash »

Le diagramme d’activité présente le traitement de Queue spécifié lorsque Logging n’est pas disponible et lors de l’arrêt. Sources : SWS Log and Trace §7.8.1 « Startup » [SWS_LOG_00001] SWS Log and Trace §7.8.2 « Shutdown » [SWS_LOG_00123].

Après ara::core::Deinitialize(), l'application n'a plus besoin d'utiliser l'API de journalisation et ne peut plus enregistrer de messages. À ce stade, l’infrastructure doit transmettre tous les messages encore dans la file d’attente aux récepteurs de journaux configurés. SWS Log and Trace §7.8.2 « Shutdown » [SWS_LOG_00123]
