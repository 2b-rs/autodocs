Rôle de Safe Hardware Acceleration et frontière avec le processus d'application

Safe Hardware Acceleration (SHWA, namespace ara::shwa) rend l'accélération matérielle standardisée et portable exploitable pour des calculs sûrs et efficaces SWS SHWA p. 4. Selon la vue d'ensemble fonctionnelle, SHWA fournit des API pour les Adaptive Applications et d'autres Functional Clusters. Le cluster couvre trois tâches :

  • exécuter des traitements intensifs en calcul en parallèle sur l'accélérateur matériel (HWA),
  • détecter et corriger les erreurs des tâches qui s'y exécutent,
  • surveiller les états de fonctionnement des accélérateurs SWS SHWA p. 7.

Les exigences du cluster doivent prendre en compte les exigences de sécurité AUTOSAR SWS SHWA p. 5.

La vue d'ensemble de l'architecture attribue SHWA à la catégorie Safety. Contrairement à Platform Health Management, SHWA n'y est pas caractérisé comme daemon-based EXP SW-Architektur p. 127. Les interfaces sont des interfaces C++ natives qu'une Adaptive Application utilise directement EXP SW-Architektur p. 132. D'autres Functional Clusters peuvent également utiliser SHWA sans l'intervention d'une Adaptive Application. Leur partie bibliothèque utilise à cette fin ses propres informations de déploiement, leurs démons étant modélisés comme des Adaptive Applications SWS SHWA p. 23.

Côté matériel, Device distingue le type d'unité de calcul via IsCpu, IsGpu et IsAccelerator [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00311] [AP_SWS_SHWA_00312]. L'énumération Target désigne deux emplacements d'exécution : kDevice pour le dispositif ou l'accélérateur et kHostTask pour la Host-CPU [AP_SWS_SHWA_00102].

Diagramme de contexte : les Adaptive Applications et d'autres Functional Clusters utilisent SHWA comme interface native ; SHWA raccorde le CPU, le GPU et les accélérateurs. Sources : SWS SHWA p. 23, EXP SW-Architektur p. 127, [AP_SWS_SHWA_00310]

Quatre domaines d'interfaces d'ara::shwa

Le schéma de la spécification divise l'API en quatre domaines : gestion des données, exécution des tâches, gestion et surveillance des périphériques ainsi que traitement des erreurs SWS SHWA p. 17. La description de l'API présente les trois premiers domaines comme des couches EXP SHWA-API p. 15.

  • Gestion des données : Range et Id décrivent des tailles et des indices de une à trois dimensions [AP_SWS_SHWA_01009] [AP_SWS_SHWA_00709]. À cela s'ajoutent Buffer [AP_SWS_SHWA_00209], Accessor [AP_SWS_SHWA_00007] et PropertyList [AP_SWS_SHWA_00802].
  • Exécution des tâches : Queue [AP_SWS_SHWA_00908], TaskHandler [AP_SWS_SHWA_01202] et Event [AP_SWS_SHWA_00602].
  • Gestion et surveillance des périphériques : Platform [AP_SWS_SHWA_01107] et Device [AP_SWS_SHWA_00308]. S'y ajoute DeviceSelector avec GpuSelector, CpuSelector et AcceleratorSelector [AP_SWS_SHWA_00403] [AP_SWS_SHWA_00407] [AP_SWS_SHWA_00410] [AP_SWS_SHWA_00413] ainsi que DeviceMonitor [AP_SWS_SHWA_01407].
  • Traitement des erreurs : ErrorHandler [AP_SWS_SHWA_00507], ShwaErrorCode [AP_SWS_SHWA_01301], ShwaErrorDomain [AP_SWS_SHWA_01307] et ShwaException [AP_SWS_SHWA_01303].

Une application peut combiner plusieurs Queues, Devices et Buffers. Il en va de même pour les autres Functional Clusters SWS SHWA p. 22. Le schéma correspondant montre deux groupes indépendants. Chaque groupe se compose d'une Queue avec plusieurs tâches, de Buffers et d'un Device SWS SHWA p. 23.

Diagramme de collaboration : voici comment les classes centrales sont articulées entre les domaines : la Queue est liée à un Device, Submit fournit un Event et l'Accessor accède à un Buffer. Sources : SWS SHWA p. 17, [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01407]

Du périphérique à la Queue : sélection et configuration

Un Device peut être déterminé de trois manières :

  1. Énumération : Platform::GetPlatforms fournit les plateformes disponibles, GetDevices leurs Devices [AP_SWS_SHWA_01107] [AP_SWS_SHWA_01108].
  2. Sans argument : Device::Create() [AP_SWS_SHWA_00308].
  3. Via un sélecteur : Device::Create(deviceSelector) [AP_SWS_SHWA_00309].

Un DeviceSelector évalue un Device avec operator() et fournit pour cela un Result<int>. SelectDevice renvoie le Device sélectionné [AP_SWS_SHWA_00404] [AP_SWS_SHWA_00403]. GetInfo<InfoType> lit des informations supplémentaires sur le périphérique à partir de [AP_SWS_SHWA_00313].

La Queue est créée soit directement à partir d'un sélecteur, soit à partir d'un Device concret. Dans les deux variantes, un ErrorHandler est un paramètre obligatoire, une PropertyList est optionnelle [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00909]. GetDevice renvoie le Device lié. IsInOrder indique si les tâches de la Queue sont exécutées dans l'ordre [AP_SWS_SHWA_00910] [AP_SWS_SHWA_00911] EXP SW-Architektur p. 133.

Diagramme d'activité : trois voies mènent au Device, deux fabriques à la Queue ; chaque résultat est vérifié sous forme de Result. Sources : [AP_SWS_SHWA_01107], [AP_SWS_SHWA_00308], [AP_SWS_SHWA_00309], [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]

Fournir des données et soumettre des tâches

Range décrit des tailles de une à trois dimensions [AP_SWS_SHWA_01007] [AP_SWS_SHWA_01009]. Buffer::Create existe en plusieurs variantes [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00210] [AP_SWS_SHWA_00212] [AP_SWS_SHWA_00211] [AP_SWS_SHWA_00213] [AP_SWS_SHWA_00214] :

  • uniquement avec Range,
  • avec Range et allocateur supplémentaire,
  • uniquement avec allocateur,
  • avec des données hôte modifiables ou constantes.

Un Accessor accède à un Buffer. Il est créé sans ou avec TaskHandler [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00008]. Il propose operator[] avec Id ou un index linéaire [AP_SWS_SHWA_00009] [AP_SWS_SHWA_00010]. Il propose en outre Set et Get avec retour de Result [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012]. L'accès dépend du AccessMode avec les valeurs kRead, kWrite et kReadWrite. Pour kRead, ReferenceT est une référence constante [AP_SWS_SHWA_00101] [AP_SWS_SHWA_00014].

Queue::Submit(cfg, ErrorHandler&&) soumet une tâche et renvoie un Event [AP_SWS_SHWA_00912]. Le TaskHandler propose deux modes d'exécution : SingleTask pour une tâche unique et ParallelFor(bufferSize, cfg) pour une exécution à parallélisme de données [AP_SWS_SHWA_01203] [AP_SWS_SHWA_01204]. Le diagramme de cas d'utilisation mentionne comme scénarios d'utilisation « Single Instructions on Multiple Data » et « Multiple Instructions on Multiple Data » EXP SW-Architektur p. 203.

Interprétation : cfg devrait être une configuration appelable. Elle reçoit vraisemblablement le TaskHandler, y crée des Accessors et appelle SingleTask ou ParallelFor. C'est ce qu'indique la fabrique d'Accessors avec paramètre TaskHandler [AP_SWS_SHWA_00008].

Diagramme de séquence : les données sont fournies, une tâche à parallélisme de données est soumise et son achèvement est attendu. L'appel de cfg est marqué comme une interprétation. Sources : [AP_SWS_SHWA_01007], [AP_SWS_SHWA_00211], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01204], [AP_SWS_SHWA_00604]

Synchronisation via des Events et fonctions d'attente de la Queue

Chaque Submit renvoie un Event [AP_SWS_SHWA_00912]. Au niveau Event, il existe trois fonctions d'attente [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00605] [AP_SWS_SHWA_00606] :

  • Event::Wait() attend l'achèvement des tâches associées.
  • La variante statique avec liste d'événements attend plusieurs Events.
  • WaitFor(ms) limite l'attente dans le temps.

GetWaitList renvoie une liste d'Events [AP_SWS_SHWA_00603]. Au niveau de la Queue, Wait() attend de manière bloquante toutes les tâches en file d'attente, WaitFor(ms) fait de même avec une limite de temps [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] EXP SW-Architektur p. 133.

Les exigences indiquent la sécurité des threads pour chaque fonction individuellement :

  • Sécurisé vis-à-vis des threads : Queue::Create, Accessor::Create, Range::Create ainsi que Accessor::Set et Get [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00007] [AP_SWS_SHWA_01007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012].
  • Non sécurisé vis-à-vis des threads : Queue::Submit, Queue::Wait, Event::Wait, Device::Create et Accessor::operator[] [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00308] [AP_SWS_SHWA_00009].
  • Différences au sein d'une classe : Buffer::Create est sécurisé vis-à-vis des threads, la variante uniquement avec allocateur ne l'est en revanche pas [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00212].

Une deuxième variante de Submit accepte une secondaryQueue à la place de l'ErrorHandler [AP_SWS_SHWA_00913]. Interprétation : cette Queue devrait servir de Queue de secours si l'exécution sur la Queue primaire échoue. La variante remonte à la même exigence amont que le ErrorHandler [AP_SWS_SHWA_00507].

Diagramme de séquence : deux Queues fonctionnent indépendamment ; l'application se synchronise via des listes d'Events ou les fonctions d'attente de la Queue. Sources : [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00605], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917], SWS SHWA p. 22

Propriété des objets, propriétés et état du périphérique

Trois règles de conception s'appliquent à toutes les classes EXP SHWA-API p. 15 :

  • Les constructeurs sont privés ; les objets sont créés via des méthodes Create() nommées.
  • Les classes qui possèdent des données fournissent std::unique_ptr.
  • La plupart des retours sont encapsulés dans ara::core::Result.

Une version R23-11 de la description mentionnait encore ara::com::SamplePtr EXP Safe-API HWA p. 15 à cet endroit. Pour R25-11, les exigences font foi, et celles-ci définissent std::unique_ptr [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00908].

Pour la surveillance, un DeviceMonitor est créé à partir d'un Device ou d'un sélecteur [AP_SWS_SHWA_01407] [AP_SWS_SHWA_01408]. Status() fournit un DeviceStatus avec l'une de ces valeurs [AP_SWS_SHWA_01409] [AP_SWS_SHWA_00103] :

  • kReady : prêt pour l'exécution des tâches,
  • kNotAccesible : inaccessible,
  • kFailure : état d'erreur,
  • kUnknown : état indéterminable.

Les présentes sources ne précisent pas si cet état est transmis à d'autres Functional Clusters.

Comportement en cas d'erreur

SHWA signale les erreurs via ara::core::Result avec des codes issus de ShwaErrorCode. En font partie kRuntime, kTaskExecutionFailure, kMemoryNotAllocated, kIntegrityCorrupted (intégrité d'une mémoire tampon impossible à rétablir), kResourceBusy et kInvalidAccessMode [AP_SWS_SHWA_01301]. Certaines fonctions mentionnent d'autres codes : kAccessorFailure, kInvalidIndex, kFeatureNotSupported et kEventInvalidOperation [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00313] [AP_SWS_SHWA_00603].

Le domaine ShwaErrorDomain fournit Name, Message et ThrowAsException. GetShwaDomain et MakeErrorCode associent les codes au domaine. ShwaException transporte un code sous forme d'exception [AP_SWS_SHWA_01308] [AP_SWS_SHWA_01309] [AP_SWS_SHWA_01310] [AP_SWS_SHWA_01311] [AP_SWS_SHWA_01312] [AP_SWS_SHWA_01303].

Les erreurs lors de l'exécution et de l'attente ont des conséquences particulièrement lourdes. Si Submit, Queue::Wait, Queue::WaitFor ou Event::Wait signalent le code kRuntime, les données de la tâche ayant échoué doivent être considérées comme modifiées involontairement. Pour Event::Wait, cela s'applique également à kTaskExecutionFailure [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] [AP_SWS_SHWA_00604]. Les indications d'erreur de Submit portent le marquage no_rollback_semantics [AP_SWS_SHWA_00912].

Les interrogations de périphériques et Accessor::Get signalent entre autres des ressources occupées avec kResourceBusy [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00012]. Une allocation ayant échoué est signalée par Buffer::Create avec kMemoryNotAllocated [AP_SWS_SHWA_00212].

Un ErrorHandler encapsule une fonction std::function<void(ara::core::ErrorCode)> [AP_SWS_SHWA_00507]. HandleError(ShwaErrorCode) exécute le traitement et n'est pas thread-safe [AP_SWS_SHWA_00508]. Chaque file d'attente reçoit un ErrorHandler lors de sa création [AP_SWS_SHWA_00908]. Interprétation : l'implémentation devrait signaler via HandleError les erreurs des tâches soumises qui ne sont pas directement disponibles en tant que valeur de retour de Submit ; qui appelle HandleError n'est pas défini par les sources. Au niveau de l'appareil, DeviceStatus::kFailure indique un état d'erreur [AP_SWS_SHWA_00103].

Diagramme d'activité : un Result est évalué et les codes d'erreur SHWA sont classés, y compris les conséquences pour les données en cas d'erreurs de tâche. Sources : [AP_SWS_SHWA_01301], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00604], [AP_SWS_SHWA_01310], [AP_SWS_SHWA_00508]

ara::shwa

AcceleratorSelector classe

AcceleratorSelector manages accelerator selection for operations on HWA if available.

Accessor classe

Accessor manages read and write access to allocated memory by Buffer. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

Buffer classe

Buffer manages memory allocation for operations on the host or/and HWA. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

CpuSelector classe

CpuSelector manages CPU selection for operations on HWA if available Allows to get a device from any supported backends for which the device type is CPU.

Device classe

Device class represents HWA device. Provides access to the device but not controlling it. Designed as copyable since not owning resources.

DeviceMonitor classe

DeviceMonitor API class. Designed as copyable since not owning resources.

DeviceSelector classe

Class allowing to choose the most appropriate device of the available ones. This is a callable object taking a device reference and returning an integer rank. One of the device with the highest non-negative value is selected.

ErrorHandler classe

ErrorHandler manages asynchronous error handling for operations on HWA.

Event classe

Event class helps to manage task execution synchronization between HWA and Host application. Can be created only inside of the Queue otherwise it’s meaningless.

GpuSelector classe

GpuSelector manages GPU selection for operations on HWA if available Select a device from any supported backends for which the device type is GPU.

Id classe

Id API class. Designed as copyable since not owning resources.

Platform classe

Platform class is responsible for extracting different HWA platforms available for current application and listing Devices bind to each platform. Designed as copyable since not owning resources.

PropertyList classe

Property List class is designed to enable vendor specific SHWA functionality extension and adjustment. Properties are not standardized and can be defined by Vendor. Class using Property list is obliged to have HasProperty() and GetProperty() methods defined.

Queue classe

Queue API provides the functionality for parallel processing on selected Device. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ ptr, which may be moved. ≙ std::unique_

Range classe

Defines size of Buffer for one, two or three dimensions. Designed as copyable since not owning resources.

ShwaErrorDomain classe

Defines the error domain for Safe Hardware Acceleration.

ShwaException classe

Exception type could be thrown by application or other FC using Safe Hardware Acceleration. Safe Hardware Acceleration API is exception free and can only return an ErrorCode, but user code can transform this error to exception and throw if it’s alligned with system error handling architecture.

TaskHandler classe

Handles tasks execution on the selected Device Can be created only inside of the Queue otherwise it’s meaningless.
