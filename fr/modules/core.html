Classement et objectif

Le module ara::core est la bibliothèque de base de base d'AUTOSAR Adaptive Platform et est défini dans la spécification officielle AUTOSAR_AP_SWS_Core.pdf (R25-11). Il fournit le type de retour sans erreur ara::core::Result ainsi que la classe de base du domaine d'erreur ara::core::ErrorDomain, qui définit le contexte pour un ensemble de conditions d'erreur ; Les sous-classes ErrorDomain sont la racine de toutes les données d'erreur [SWS_CORE_10303]. La gestion des erreurs dans Adaptive Platform s'effectue généralement sans exceptions C++ via ara::core::ErrorCode et ara::core::Result selon le concept « ValueOrError » (EXP InterfacesGuidelines). L'espace de noms ara et tous les espaces de noms sous-jacents sont également réservés par AUTOSAR ; Si une application adaptative y ajoute ses propres déclarations, le comportement n'est pas défini (EXP InterfacesGuidelines). ara::core constitue ainsi la base commune pour les règles d'initialisation, de gestion des erreurs et de concurrence pour tous les clusters de fonctions AP.

Objets clés et utilisation typique

ara::core::Result<T, E> contient soit une valeur, soit une erreur ; le type d'erreur doit être ErrorCode, faute de quoi une erreur de compilation survient [SWS_CORE_00701], avec des spécialisations pour les types référence [SWS_CORE_00901] et pour les valeurs void [SWS_CORE_00801]. Un Result est créé au moyen des fonctions de fabrique statiques FromValue [SWS_CORE_00733] ou FromError [SWS_CORE_00736]. Bind applique un Callable à une valeur contenue et renvoie un nouveau Result ; si l'instance ne contient aucune valeur, l'erreur d'origine est reprise sans modification [SWS_CORE_00768]. Resolve renvoie la valeur ou appelle un Callable compatible en cas d'erreur [SWS_CORE_00767], tandis que ErrorOr [SWS_CORE_00764][SWS_CORE_00763] fournit des valeurs de repli simples. Les instances ErrorDomain sont égales si et seulement si leurs identifiants uniques de 64 bits coïncident ; l'accès s'effectue généralement via des accesseurs non membres comme GetFutureErrorDomain [SWS_CORE_10401].

Pour les conteneurs et le traitement de texte, le module fournit des implémentations compatibles PMR de la bibliothèque standard C++ : ara::core::Vector [SWS_CORE_01301], ara::core::Map [SWS_CORE_01400], ara::core::StringView [SWS_CORE_02001], ara::core::BasicString [SWS_CORE_03000] et ara::core::Span [SWS_CORE_01900]. Pour les références de modèle au niveau application, la classe final ara::core::InstanceSpecifier existe dans ara/core/instance_specifier.h et encapsule un chemin AUTOSAR-shortName [SWS_CORE_08001].

Génération, cycle de vie et propriété

Le cycle de vie de l'ensemble d'ARA est contrôlé de manière centralisée par les deux fonctions libres ara::core::Initialize et ara::core::Deinitialize. Initialize démarre le framework ARA ; cela peut inclure l'initialisation de structures de données internes et de ressources système, ainsi que le démarrage de threads d'arrière-plan [SWS_CORE_15003]. Si Initialize utilise l'injection d'arguments de ligne de commande, les arguments concernés doivent être retirés de manière transparente afin de ne pas affecter l'analyse des arguments de l'application [SWS_CORE_15006]. Un appel réussi place le framework dans un état où tous les composants configurés peuvent immédiatement traiter des appels d'API [SWS_CORE_90026] ; un second appel sans Deinitialize préalable renvoie kAlreadyInitialized sans perturber l'instance en cours [SWS_CORE_90029]. Inversement, Deinitialize lance l'arrêt du framework, y compris la terminaison des threads d'arrière-plan démarrés ainsi que la libération de la mémoire dynamique et d'autres ressources système [SWS_CORE_15004] ; si le framework n'est pas initialisé avec succès ou est déjà désinitialisé, chaque appel renvoie kNotInitialized [SWS_CORE_90030].

Seul un petit sous-ensemble explicitement désigné de ara::core – notamment ErrorCode, StringView, Result (sans ValueOrThrow), ErrorDomain (sans ThrowAsException), Initialize, Abort, SetAbortHandler et AddAbortHandler – peut être utilisé indépendamment de Initialize/Deinitialize [SWS_CORE_15002]. Le comportement de toutes les autres fonctions ARA avant Initialize est défini par l'implémentation [SWS_CORE_15005] ; de même, un appel après Deinitialize en dehors de ce sous-ensemble a un comportement défini par l'implémentation, car un contrôle d'exécution correspondant n'est délibérément pas exigé pour des raisons de performance [SWS_CORE_90022]. Les Guidelines for using Adaptive Platform interfaces résument cela comme contrat Startup/Shutdown obligatoire : Initialize doit être appelé au point d'entrée, Deinitialize seulement après que toutes les ressources ARA, y compris celles d'autres threads, ont été libérées ; les deux renvoient Result<void>, qui doit être contrôlé, et une erreur n'est pas récupérable, de sorte que l'application doit se terminer avec EXIT_FAILURE (EXP InterfacesGuidelines). En complément, AUTOSAR AP RS General interdit les fonctions d'initialisation propres aux clusters : si un Functional Cluster nécessite une initialisation ou désinitialisation explicite, il doit utiliser exclusivement ara::core::Initialize/ara::core::Deinitialize.

Gestion des erreurs, concurrence et restrictions

La spécification définit précisément la sécurité des threads : une fonction membre AUTOSAR-API non statique est thread-safe si elle peut être appelée simultanément sur le même objet depuis plusieurs threads sans synchronisation par l’appelant ; les destructeurs et les opérateurs d’affectation ne sont généralement pas thread-safe [SWS_CORE_13200]. Si une fonction membre non thread-safe est appelée simultanément sur le même objet, le comportement est indéfini — même si l’autre fonction impliquée est thread-safe [SWS_CORE_13203] ; les appels concurrents sur des instances différentes sont toutefois permis sans synchronisation [SWS_CORE_13205]. L’implémentation ARA appelle uniquement de façon séquentielle les rappels ou fonctions virtuelles pures spécifiés comme non thread-safe, par exemple ara::tsync::SynchronizedTimeBaseNotifier, tandis que ara::phm::RecoveryAction::RecoveryHandler thread-safe équivaut à [SWS_CORE_13214]. L’utilisation d’ARA-APIs dans un gestionnaire de signaux entraîne un comportement indéfini, sauf indication contraire [SWS_CORE_13210] (EXP InterfacesGuidelines : sécurité des signaux asynchrones). De plus, AUTOSAR AP RS General exige que chaque fonction API indique son niveau de sécurité des threads comme « thread-safe », « not thread-safe » ou « conditional » et que ce contrat s’applique dans les deux sens : si une API thread-safe est spécifiée, l’implémentation fournie par le fournisseur ou l’utilisateur, notamment les rappels ou les fonctions virtuelles pures Skeleton, doit également respecter cette promesse (EXP InterfacesGuidelines).

Pour les erreurs non récupérables, ara::core distingue la Violation du traitement d’erreur régulier : une Violation résulte de préconditions ou postconditions du framework enfreintes et n’est pas récupérable, à l’instar d’une Assertion échouée [SWS_CORE_00021]. En cas de Violation normalisée, le processus s’arrête anormalement via ara::core::Abort ; un message de débogage conforme à la définition DLT est émis sur stderr et doit être écrit dans les log sinks avec la Context ID du Functional Cluster qui l’a détectée [SWS_CORE_00090]. Pendant l’exécution d’un appel à Abort, les autres appels bloquent les threads appelants [SWS_CORE_12407] ; les Abort Handlers installés sont alors appelés dans l’ordre inverse de leur installation, et, sans handler, std::abort() est appelé [SWS_CORE_12404]. Cette séparation entre les erreurs récupérables via Result/ErrorCode et les Violations non récupérables [SWS_CORE_00021] est soutenue par AUTOSAR AP RS General comme principe général pour tous les Functional Clusters de l’AP.

Intégration & configuration

Chaque Functional Cluster ARA utilise, lors de la journalisation via ara::log, les paramètres Log-and-Trace standardisés de ara::core, notamment la Context ID et la plage de Message ID [SWS_CORE_00055]. À cette fin, la spécification définit des ID de contexte de journalisation normalisés pour chaque Functional Cluster, notamment #COM pour com, #COR pour core, #CRY pour crypto, #DIA pour diag, #EXE pour exec, #LOG pour log et #PER pour per [SWS_CORE_90024]. Au niveau des exigences, AUTOSAR AP RS General ajoute que les interfaces ARA doivent utiliser des types ara::core au lieu des types standard C++, à condition que ara::core fournisse un type équivalent. Étant donné que l’espace de noms ara est entièrement réservé à AUTOSAR, tous les types de données d’un Functional Cluster sont également disponibles via un fichier d’en-tête de transfert <fc>_fwd.h (EXP InterfacesGuidelines).
