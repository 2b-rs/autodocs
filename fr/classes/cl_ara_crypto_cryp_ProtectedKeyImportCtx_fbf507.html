Sert à dépaqueter et importer de manière sécurisée des clés et des données cryptographiques protégées au sein d'une application.

L'interface permet le dépaquetage et l'importation sécurisés de données et de clés cryptographiques protégées à l'aide d'une clé de transport configurée [SWS_CRYPT_50205]. Le matériel de clé dépaqueté peut soit être écrit directement dans un emplacement de clé persistant, soit être chargé en mémoire sous forme typée en tant qu'objet de clé [SWS_CRYPT_50207]. Toutes les méthodes fonctionnent de manière thread-safe et suivent une sémantique d'erreur stricte avec annulation (rollback), tandis que Reset garantit l'effacement sans résidu des tampons internes [SWS_CRYPT_50212].

Contexte

L'interface ara::crypto::cryp::ProtectedKeyImportCtx fournit un contexte cryptographique permettant d'importer et de dépaqueter de manière sécurisée des structures de données protégées, telles que du matériel de clé secret, dans le système. Le contexte agit comme intermédiaire entre une application demandeuse, un mécanisme de protection basé sur une clé de transport et les structures cibles de la cryptographie AUTOSAR. Les paquets de données sérialisés entrants sont authentifiés, déchiffrés et analysés par le contexte [SWS_CRYPT_50207]. Comme sources pour la clé de transport requise, on utilise soit des objets de clé symétrique autonomes [SWS_CRYPT_50205], soit des emplacements de clé d'un magasin de clés [SWS_CRYPT_50206]. En tant que puits, les objets de clé dépaquetés peuvent être directement transmis à l'application appelante ou être immédiatement sérialisés dans un emplacement de clé accessible en écriture [SWS_CRYPT_50207].

Cycle de vie

Pour un accès partagé, le contexte est généralement géré via le type de pointeur intelligent fourni Sptr [SWS_CRYPT_50085] ; les instances devraient alors être fournies par un composant pilote crypto compétent. Avant le traitement effectif, le contexte se trouve dans un état initial non configuré dans lequel aucune clé de transport n'est encore assignée. L'assignation d'une clé de transport s'effectue via la méthode SetKey, ce qui fait passer le contexte à l'état opérationnel [SWS_CRYPT_50205] [SWS_CRYPT_50206].

Après l'exécution réussie de l'opération Import, le contexte conserve les données dépaquetées et les métadonnées dans des tampons internes, de sorte que le type d'objet puisse être identifié et que les objets de clé puissent être lus [SWS_CRYPT_50207] [SWS_CRYPT_50208]. La méthode Reset permet de rétablir le contexte dans son état initial : tous les tampons internes contenant des données précédemment importées sont entièrement purgés et la clé de transport enregistrée est supprimée [SWS_CRYPT_50212]. Toutes les méthodes d'interface sont spécifiées comme étant sûres vis-à-vis des exceptions et thread-safe, ce qui permet de maîtriser les accès concurrents provenant de plusieurs contextes d'exécution [SWS_CRYPT_50207].

Diagramme d'états : phases de vie du contexte, de la configuration à la purge en passant par l'importation. Sources : [SWS_CRYPT_50205], [SWS_CRYPT_50206], [SWS_CRYPT_50207], [SWS_CRYPT_50212]

Parcours d'utilisation

Le déroulement régulier commence par la configuration de la clé de transport. Pour cela, l'application appelle SetKey soit avec un SymmetricKey::Sptr [SWS_CRYPT_50205], soit avec un KeySlot::Sptr [SWS_CRYPT_50206]. À l'étape suivante, la méthode Import est exécutée, à laquelle le paquet de données sérialisé est transmis sous forme de ReadOnlyMemRegion [SWS_CRYPT_50207]. Si la clé doit être stockée de façon persistante, il est possible de transmettre directement en option un WriteableKeySlot::Sptr dans lequel le matériel dépaqueté est écrit [SWS_CRYPT_50207].

Si aucun slot cible n'a été spécifié ou si la clé doit être utilisée de manière volatile, l'application détermine la catégorie du dernier objet importé via GetCryptoObjectType [SWS_CRYPT_50208]. En fonction de ce type, l'application appelle la méthode de récupération appropriée : GetPrivateKey pour les clés privées [SWS_CRYPT_50209], GetPublicKey pour les clés publiques [SWS_CRYPT_50211] ou GetSymmetricKey pour le matériel de clé symétrique [SWS_CRYPT_50210]. Si le protocole d'importation utilisé requiert un retour à l'expéditeur – comme par exemple avec les blocs de contrôle M4 et M5 d'une séquence SHE-LoadKey –, celui-ci peut être écrit dans un tampon fourni via GetResponse [SWS_CRYPT_41020]. Après l'achèvement de la séquence de traitement, un appel à Reset replace le contexte dans son état initial [SWS_CRYPT_50212].

Diagramme de séquence : séquence d'appels typique lors de l'importation et de la lecture de matériel de clé. Sources : [SWS_CRYPT_50205], [SWS_CRYPT_50207], [SWS_CRYPT_50208], [SWS_CRYPT_50210], [SWS_CRYPT_50212]

Scénarios d'erreur

Si une erreur survient pendant un appel de méthode, une sémantique stricte de rollback s'applique, préservant l'état antérieur à l'appel. Lors de la configuration via SetKey, l'appel échoue avec CryptoErrc::kUsageViolation si l'indicateur d'utilisation de la clé ne contient pas l'autorisation kAllowKeyUnwrapping [SWS_CRYPT_50205] [SWS_CRYPT_50206]. Si l'objet clé ou le slot référencé n'est fondamentalement pas utilisable comme clé de transport, CryptoErrc::kIncompatibleObject est signalé [SWS_CRYPT_50205] [SWS_CRYPT_50206].

Lors de l'appel de Import, des écarts de taille des données d'entrée entraînent CryptoErrc::kInvalidInputSize et des violations de format entraînent CryptoErrc::kInvalidArgument [SWS_CRYPT_50207]. Si le contrôle d'intégrité ou d'authenticité de la couche de protection échoue (par exemple en raison d'un message authentication code non valide ou d'une signature erronée), l'appel renvoie CryptoErrc::kAuthTagNotValid [SWS_CRYPT_50207]. Si le composant cryptographique est temporairement occupé, cela est signalé via CryptoErrc::kBusyResource [SWS_CRYPT_50207].

La condition préalable à la lecture de clés importées est l'exécution réussie de Import ; sinon, GetPrivateKey, GetPublicKey et GetSymmetricKey répondent par CryptoErrc::kProcessingNotFinished [SWS_CRYPT_50209] [SWS_CRYPT_50210] [SWS_CRYPT_50211]. Si le type de clé demandé ne correspond pas à l'objet effectivement déballé ou si aucun objet n'a encore été importé, les méthodes de récupération l'acquittent avec CryptoErrc::kNoSuchValue [SWS_CRYPT_50208] [SWS_CRYPT_50209] [SWS_CRYPT_50210] [SWS_CRYPT_50211]. Si le tampon de sortie n'offre pas une capacité suffisante lors de GetResponse, cela se traduit par CryptoErrc::kInsufficientCapacity [SWS_CRYPT_41020]. Si l'implémentation concrète ne prend pas en charge une sous-fonction (par exemple certains types de clés ou la réinitialisation), CryptoErrc::kUnsupported est renvoyé de manière uniforme [SWS_CRYPT_50205] [SWS_CRYPT_50208] [SWS_CRYPT_50212].

          La méthode GetPublicKey de la classe ara::crypto::cryp::ProtectedKeyImportCtx sert à récupérer de manière synchrone un pointeur vers une clé publique préalablement importée et déballée ([SWS_CRYPT_50211]). La fonction n'accepte aucun paramètre de transmission et renvoie le résultat avec sécurité de typage sous forme de ara::core::Result<PublicKey::Sptr> ([SWS_CRYPT_50211]).
          

          Avant l'appel, une opération d'importation doit s'être achevée avec succès ; sinon, l'appel échoue et renvoie le code d'erreur ara::crypto::CryptoErrc::kProcessingNotFinished ([SWS_CRYPT_50211]). Si le dernier objet cryptographique importé n'était pas une clé publique, cela se traduit par l'erreur ara::crypto::CryptoErrc::kNoSuchValue ([SWS_CRYPT_50211]). Si le contexte d'importation concret ne prend pas du tout en charge l'introduction de clés publiques, ara::crypto::CryptoErrc::kUnsupported est signalé ([SWS_CRYPT_50211]). Pour toutes les erreurs spécifiées, l'interface garantit une sémantique de rollback ([SWS_CRYPT_50211]).
          

          En matière de concurrence et de sécurité vis-à-vis des erreurs, la méthode est spécifiée comme thread-safe ainsi qu'exception-safe et ne lève aucune exception C++ (noexcept) ([SWS_CRYPT_50211]).
          

          Sur le plan fonctionnel, ce mécanisme d'importation se distingue d'autres interfaces : alors qu'un objet protégé est déballé ici, la fonction de même nom sur ara::crypto::cryp::PrivateKey ([SWS_CRYPT_22511]) fournit la clé publique d'une clé privée existante, laquelle a par exemple été générée auparavant au moyen de GeneratePrivateKey ([SWS_CRYPT_20722]).

                      fonction Import [SWS_CRYPT_50207] Upstream: RS_CRYPTO_02105
                      

                      virtual ara::core::Result< void > Import (ReadOnlyMemRegion serialized, ara::core::Optional< WriteableKeySlot::Sptr > keySlot) noexcept=0;
                      

                      The interface shall unwrap the protected data provided, parse the content, and make the parsed content (key-material and meta-data) available for retrieval by the application. If optionally a Key Slot is specified, the unwrapped key material shall be directly serialized into the KeySlot.

                      Utilisation
                      

                      La méthode synchrone Import de la classe ara::crypto::cryp::ProtectedKeyImportCtx déballe les données de clé protégées de la zone de mémoire serialized ([SWS_CRYPT_50207]). Elle analyse le contenu des données et met à disposition le matériel de clé extrait ainsi que les métadonnées pour la récupération ultérieure. Si un WriteableKeySlot est optionnellement transmis, le matériel de clé est directement sérialisé dans ce slot ([SWS_CRYPT_50207]). Interprétation : si aucun keySlot n'est transmis, le matériel de clé ne subsiste vraisemblablement que dans l'état du contexte d'importation.
                      


                      Gestion des erreurs
                      

                      La fonction renvoie un ara::core::Result<void>. Si l'opération échoue, une sémantique de rollback s'applique pour tous les codes d'erreur ([SWS_CRYPT_50207]) :
                      

                        

                      • ara::crypto::CryptoErrc::kInvalidInputSize : la taille d'entrée de serialized est inattendue ([SWS_CRYPT_50207]).
                        • 

                      • ara::crypto::CryptoErrc::kInvalidArgument : les données sérialisées ne correspondent pas au format attendu ([SWS_CRYPT_50207]).
                        • 

                      • ara::crypto::CryptoErrc::kAuthTagNotValid : la vérification d'authentification (MAC ou signature) échoue ([SWS_CRYPT_50207]).
                        • 

                      • ara::crypto::CryptoErrc::kBusyResource : l'opération ne peut pas être exécutée temporairement ([SWS_CRYPT_50207]).
                        • 

                      


                      Concurrence et interaction
                      

                      La méthode est sûre du point de vue des threads et sûre face aux exceptions (noexcept) ([SWS_CRYPT_50207]). Après un appel réussi, l'objet de clé déballé peut être récupéré depuis le contexte via GetPrivateKey ([SWS_CRYPT_50209]), GetSymmetricKey ([SWS_CRYPT_50210]) ou GetPublicKey ([SWS_CRYPT_50211]). Si le protocole sous-jacent exige un retour à l'expéditeur, GetResponse ([SWS_CRYPT_41020]) fournit la réponse du fournisseur cryptographique. Pour les formats de clés non protégés, les méthodes ImportPublicKey ([SWS_CRYPT_20732]), ImportSymmetricKey ([SWS_CRYPT_50014]) et ImportPrivateKey ([SWS_CRYPT_50132]) de la classe de fabrique CryptoProvider servent d'alternative.
