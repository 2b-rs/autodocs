Contexte

La classe ara::crypto::cryp::ProtectedKeyImportCtx définit une interface spécialisée pour le chargement et le décompactage sécurisés de clés cryptographiques et des métadonnées associées ([SWS_CRYPT_50207]). Elle intervient lorsque le matériel de clé doit être transmis à l'environnement d'application sous une forme protégée, chiffrée ou authentifiée (par exemple sous la forme d'un Wrapped Key Token) et y être mis à disposition.

En interaction avec d'autres composants, le contexte agit comme une interface entre l'application de traitement, les structures sources et de transport cryptographiques ainsi que les objets de clé qui en résultent :

  • Clé de transport : pour le déchiffrement et l'authentification des données, le contexte nécessite une Transport-Key. Celle-ci est soit directement transmise sous la forme d'un objet de clé symétrique ara::crypto::cryp::SymmetricKey ([SWS_CRYPT_50205]), soit référencée via un ara::crypto::keys::KeySlot ([SWS_CRYPT_50206]).
  • Données d'entrée : les données de clé sérialisées et protégées sont mises à disposition du contexte via une zone mémoire en lecture seule (ReadOnlyMemRegion) ([SWS_CRYPT_50207]).
  • Mémoire cible ou clés volatiles : après un import réussi, le matériel de clé extrait peut être soit directement déposé dans un emplacement persistant d'écriture de clé (WriteableKeySlot) ([SWS_CRYPT_50207]), soit obtenu via des méthodes d'interrogation typées en tant que smart pointer volatile vers des clés privées ([SWS_CRYPT_50209]), des clés symétriques ([SWS_CRYPT_50210]) ou des clés publiques ([SWS_CRYPT_50211]).
  • Réponses de protocole : si le scénario d'import sous-jacent prend en charge un protocole d'authentification ou d'acquittement (par exemple les retours M4 et M5 d'une transaction SHE-LoadKey), le contexte renvoie ces données de réponse à l'application ([SWS_CRYPT_41020]).

Cycle de vie

Les instances de ProtectedKeyImportCtx sont gérées en tant que pointeurs partagés via l'alias typé Sptr, qui est défini comme std::shared_ptr<ProtectedKeyImportCtx> ([SWS_CRYPT_50085]). Interprétation : l'instanciation effective devrait se faire via une méthode fabrique correspondante du CryptoProvider, puisqu'il s'agit d'une interface abstraite.

En fonctionnement opérationnel, le contexte traverse plusieurs états discrets :

  1. État initial : après la création ou après un nettoyage explicite, il n'existe aucune Key-Import-Key configurée et les tampons de données internes sont vides ([SWS_CRYPT_50212]).
  2. Configuré : en liant une clé de transport (Transport-Key) via SetKey() ([SWS_CRYPT_50205], [SWS_CRYPT_50206]), le contexte est prêt à traiter des paquets de données protégés.
  3. Données disponibles : après l'exécution réussie de Import() ([SWS_CRYPT_50207]), le contexte conserve les objets de clé analysés ainsi que les éventuels messages de réponse générés. Les méthodes d'accès (getters) peuvent être appelées depuis cet état.
  4. Réinitialisation : un appel de Reset() ([SWS_CRYPT_50212]) supprime la Transport-Key configurée, efface toutes les données mises en mémoire tampon des tampons internes et fait revenir le contexte à l'état initial.

En matière de concurrence, toutes les méthodes d'interface du contexte sont spécifiées comme étant sûres face aux exceptions (exception safe) et sûres pour les threads (thread-safe) ([SWS_CRYPT_50205], [SWS_CRYPT_50207], [SWS_CRYPT_50208], [SWS_CRYPT_50212]).

Diagramme d'états : phases et transitions d'état d'une instance de ProtectedKeyImportCtx. Sources : [SWS_CRYPT_50205], [SWS_CRYPT_50206], [SWS_CRYPT_50207], [SWS_CRYPT_50212].

Parcours d'utilisation

Un déroulement typique pour réaliser un import de clé protégé se divise selon les étapes suivantes :

  1. Configurer la clé de transport : l'application configure le contexte en appelant SetKey() avec un objet de clé symétrique ([SWS_CRYPT_50205]) ou un emplacement de clé ([SWS_CRYPT_50206]). La clé fournie doit disposer de l'autorisation d'utilisation correspondante.
  2. Exécuter l'import : la méthode Import() est appelée avec le tampon de données des données sérialisées ([SWS_CRYPT_50207]). Si un WriteableKeySlot est en outre indiqué, le contexte sérialise directement le matériel de clé décompacté dans cet emplacement.
  3. Identifier le type d'objet : Au moyen de GetCryptoObjectType(), il est possible de déterminer quel type d'objet cryptographique a été déballé ([SWS_CRYPT_50208]).
  4. Récupérer la clé et la réponse de protocole : Selon le type d'objet, l'application demande la clé via GetSymmetricKey() ([SWS_CRYPT_50210]), GetPrivateKey() ([SWS_CRYPT_50209]) ou GetPublicKey() ([SWS_CRYPT_50211]). Si le protocole d'importation prévoit un message de confirmation, celui-ci est transféré via GetResponse() dans un tampon mis à disposition ([SWS_CRYPT_41020]).
  5. Finalisation et nettoyage des tampons : Après une extraction réussie, Reset() est appelé afin de garantir que les données résiduelles sensibles soient supprimées des tampons internes et que le contexte soit réinitialisé proprement ([SWS_CRYPT_50212]).

Diagramme de séquence : ordre des appels lors de l'importation de clés protégées et de la lecture du résultat. Sources : [SWS_CRYPT_50205], [SWS_CRYPT_50207], [SWS_CRYPT_50208], [SWS_CRYPT_50210], [SWS_CRYPT_41020], [SWS_CRYPT_50212].

Scénarios d'erreur

Toutes les opérations retournent un ara::core::Result et utilisent en cas d'erreur une sémantique de rollback définie qui préserve l'état antérieur à l'appel :

  • Erreurs lors de la configuration des clés :
    • CryptoErrc::kUsageViolation : survient lorsque les indicateurs d'utilisation de la clé de transport ne contiennent pas le bit kAllowKeyUnwrapping ([SWS_CRYPT_50205], [SWS_CRYPT_50206]).
    • CryptoErrc::kIncompatibleObject : l'objet transmis ou la clé contenue dans le KeySlot ne peut pas être utilisé comme clé de transport ([SWS_CRYPT_50205], [SWS_CRYPT_50206]).
    • CryptoErrc::kUnsupported : l'implémentation du contexte prend exclusivement en charge l'autre variante respective de SetKey() (par ex. uniquement KeySlot au lieu d'un objet clé) ([SWS_CRYPT_50205], [SWS_CRYPT_50206]).
  • Erreurs pendant l'importation :
    • CryptoErrc::kInvalidInputSize : la zone mémoire transmise serialized a une taille inattendue et ne peut pas être déballée ([SWS_CRYPT_50207]).
    • CryptoErrc::kInvalidArgument : le format de données de serialized ne correspond pas au format d'importation requis ([SWS_CRYPT_50207]).
    • CryptoErrc::kAuthTagNotValid : l'élément d'authentification (signature ou MAC) est invalide, l'intégrité des données n'a pas pu être confirmée ([SWS_CRYPT_50207]).
    • CryptoErrc::kBusyResource : l'opération ne peut temporairement pas être exécutée, car des ressources internes sont occupées ([SWS_CRYPT_50207]).
  • Erreurs lors de l'interrogation du résultat :
    • CryptoErrc::kProcessingNotFinished : un appel de GetPrivateKey(), GetPublicKey() ou GetSymmetricKey() échoue si aucun appel réussi de Import() n'a eu lieu auparavant ([SWS_CRYPT_50209], [SWS_CRYPT_50210], [SWS_CRYPT_50211]).
    • CryptoErrc::kNoSuchValue : est retourné si aucun objet n'a été importé jusqu'à présent ou si le dernier objet importé ne correspond pas au type de clé interrogé ([SWS_CRYPT_50208], [SWS_CRYPT_50209], [SWS_CRYPT_50210], [SWS_CRYPT_50211]).
    • CryptoErrc::kInsufficientCapacity : le tampon de sortie transmis pour GetResponse() ne suffit pas à contenir la réponse de protocole ([SWS_CRYPT_41020]).
    • CryptoErrc::kUnsupported : signale que le contexte ne prend pas en charge une fonction spécifique – comme la détermination du type d'objet ([SWS_CRYPT_50208]), la génération de réponses ([SWS_CRYPT_41020]) ou la réinitialisation de l'état ([SWS_CRYPT_50212]).
