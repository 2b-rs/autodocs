Contexte

La classe ara::diag::MultipleCondition ([SWS_DM_01730]) fournit dans le module diag de l'AUTOSAR Adaptive Platform une interface regroupée pour la gestion de plusieurs conditions de diagnostic (Diagnostic Conditions). Alors que les conditions individuelles sont généralement représentées par la classe ara::diag::Condition, ara::diag::MultipleCondition permet de commander et d'interroger plusieurs conditions via une interface de port commune (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »).

D'un point de vue fonctionnel, les deux interfaces possèdent la même sémantique et proposent des opérations similaires (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »). La différence essentielle réside dans le fait que pour ara::diag::MultipleCondition, chaque opération prend en charge un identifiant supplémentaire de type ConditionHandleType ([SWS_DM_01728], [SWS_DM_01729]).

Les principaux partenaires d'interaction de la classe comprennent :

  • Adaptive Application : instancie la classe et commande les états des conditions associées au moyen de SetCondition ou les lit via GetCondition ([SWS_DM_01728], [SWS_DM_01729]).
  • Diagnostic Management (DM) : agit en tant que sous-système de plateforme, traite les changements d'état et met à disposition les informations sur les conditions pour les déroulements de diagnostic ([SWS_DM_01728]).
  • Modélisation du manifeste : chaque DiagnosticCondition définie dans le système requiert un mappage via un DiagnosticMultipleConditionPortMapping pour définir que l'interface à conditions multiples peut être utilisée pour cette condition (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »). Le PortPrototype associé doit obligatoirement être typé par un DiagnosticMultipleConditionInterface ([SWS_DM_01727]).

Diagramme de contexte : intégration d'ara::diag::MultipleCondition et interaction avec l'application, la modélisation et le Diagnostic Management. Sources : [SWS_DM_01727], [SWS_DM_01730], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »

Cycle de vie

La création d'une instance s'effectue via le constructeur explicite MultipleCondition(const ara::core::InstanceSpecifier &specifier) ([SWS_DM_01727]). Lors de l'instanciation, l'objet est lié au PortPrototype référencé par le InstanceSpecifier. Le constructeur est spécifié comme étant à l'épreuve des exceptions (exception safe) et sécurisé vis-à-vis des threads (thread-safe) ([SWS_DM_01727]).

En ce qui concerne la propriété et la transférabilité, la classe est strictement liée à son lieu de création :

  • Le constructeur de copie est supprimé : MultipleCondition(MultipleCondition &) = delete ([SWS_DM_02072]).
  • L'opérateur d'assignation par copie est supprimé : operator=(MultipleCondition &) = delete ([SWS_DM_02073]).
  • Le constructeur de déplacement est supprimé : MultipleCondition(MultipleCondition &&) noexcept = delete ([SWS_DM_02071]).
  • L'opérateur d'assignation par déplacement est supprimé : operator=(MultipleCondition &&) = delete ([SWS_DM_02074]).

Les instances de ara::diag::MultipleCondition ne peuvent donc être ni copiées ni déplacées (pinned object). Elles doivent rester à une adresse mémoire fixe pendant toute leur durée d'utilisation.

La destruction s'effectue via le destructeur ~MultipleCondition() noexcept ([SWS_DM_01737]). Celui-ci est à l'épreuve des exceptions, mais explicitement déclaré comme not thread-safe ([SWS_DM_01737]). L'application appelante doit donc s'assurer qu'aucun accès concurrent à l'objet n'a lieu pendant le processus de destruction.

Pour la sécurité des threads des opérations en cours (GetCondition et SetCondition), une synchronisation conditionnelle (conditional thread-safety) s'applique : le fait que les méthodes doivent être implémentées de manière thread-safe ou non thread-safe est déterminé par le ConcurrencyType ([SWS_DM_01728], [SWS_DM_01729]). Interprétation : étant donné que le constructeur C++ dans [SWS_DM_01727] ne comporte aucun argument ConcurrencyType, cette propriété devrait être configurée dans la conception logicielle via le modèle de port et évaluée via le InstanceSpecifier.

Parcours d'utilisation

Le flux typique d'utilisation de ara::diag::MultipleCondition se divise en plusieurs phases : instanciation, identification de la condition individuelle et exécution des opérations d'écriture et de lecture :

  1. Instanciation et liaison de port : l'application instancie MultipleCondition en spécifiant l'InstanceSpecifier approprié ([SWS_DM_01727]).
  2. Adressage des conditions via des descripteurs : les conditions individuelles sont adressées via des valeurs numériques de type ConditionHandleType ([SWS_DM_01735]). Si aucun DiagnosticMultipleConditionPortMapping.overrideId n'est défini dans le modèle, le Diagnostic Manager attribue des descripteurs par ordre alphabétique du nom court de DiagnosticCondition, en commençant par 0x010000 (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »).
  3. Définition de l'état (SetCondition) : l'application met à jour l'état d'une condition de manière synchrone via SetCondition(conditionHandle, condition) ([SWS_DM_01729]). L'appel renvoie un ara::core::Result<void> qui informe de la réussite ou de l'échec.
  4. Interrogation de l'état (GetCondition) : pour lire l'état actuel, l'application appelle GetCondition(conditionHandle) ([SWS_DM_01728]). L'appel renvoie un ara::core::Future<ConditionType>. L'application peut ensuite résoudre et évaluer le résultat de manière asynchrone.

Diagramme de séquence : ordre d'appel typique pour la gestion et l'interrogation de conditions au moyen de ara::diag::MultipleCondition. Sources : [SWS_DM_01727], [SWS_DM_01728], [SWS_DM_01729], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] « MultipleCondition ConditionHandleType Generation »

Scénarios d'erreur

Les cas d'erreur lors du travail avec ara::diag::MultipleCondition se divisent en violations de configuration et de modélisation pendant l'instanciation ainsi qu'en erreurs d'exécution lors d'appels de méthodes :

  • Erreurs d'initialisation (Violations) ([SWS_DM_01727]) :
    • InstanceSpecifierMappingIntegrityViolation : le InstanceSpecifier ne peut pas être résolu dans le contexte de modèle de l'Executable ou fait référence à un élément de modèle qui n'est pas un PortPrototype.
    • PortInterfaceMappingViolation : le PortPrototype référencé n'est pas typé de manière conforme au type par un DiagnosticMultipleConditionInterface.
    • ProcessMappingViolation : une InstanceRef correspondante existe dans le modèle, mais il n'existe aucun processus modélisé correspondant pour le processus d'exécution actuel.
    • InstanceSpecifierAlreadyInUseViolation : le constructeur a été appelé avec un InstanceSpecifier qui est déjà occupé par une autre instance au sein du processus actuel.
  • Erreurs d'exécution lors de SetCondition ([SWS_DM_01729]) :
    • DiagErrc::kInvalidArgument : signale des arguments non valides (sémantique de rollback, par ex. pour kPreFailed avec debouncing interne).
  • Erreurs d'exécution lors de GetCondition ([SWS_DM_01728]) :
    • DiagErrc::kInvalidArgument : le conditionHandle spécifié est non valide (sémantique de rollback).
    • DiagErrc::kServiceNotAvailable : l'appel ne peut pas être exécuté car une fonctionnalité essentielle de Diagnostic Management n'est actuellement pas disponible (sémantique de rollback).

Ce guide de classe est basé sur la spécification AUTOSAR Adaptive Platform R25-11 (module diag) et résume les exigences relatives à ara::diag::MultipleCondition.
