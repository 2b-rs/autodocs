Sert à la mise à disposition et au traitement côté application de ressources de configuration SOVD explicitement modélisées.

L'interface ara::diag::SovdConfiguration sert de gestionnaire générique pour les configurations SOVD explicitement modélisées, auquel le Diagnostic Server transmet les accès entrants en lecture et en écriture [SWS_DM_01860], [SWS_DM_01787]. Après l'instanciation basée sur les ports, l'application active la réception des messages via Offer et l'arrête au besoin avec StopOffer [SWS_DM_01872], [SWS_DM_01930]. La mise à disposition des données s'effectue de manière asynchrone via des sessions de lecture ou d'écriture, les erreurs fonctionnelles étant signalées selon l'ISO 17978-3 ou l'ASAM SOVD 1.1 [SWS_DM_01870].

Contexte

L'interface ara::diag::SovdConfiguration définit l'interface générique pour les gestionnaires de configuration SOVD explicitement modélisés au sein de l'architecture de diagnostic Adaptive AUTOSAR [SWS_DM_01860]. Dès lors qu'au moins une configuration SOVD est configurée dans le système, l'instance du Diagnostic Server du Diagnostic Management (DM) met à disposition vers l'extérieur la méthode standardisée SOVD Retrieve List of All Configurations Provided by the Entity conformément à ASAM SOVD [SWS_DM_01429]. Le Diagnostic Server transmet les accès entrants en lecture et en écriture sur une telle configuration explicite à l'implémentation concrète de ara::diag::SovdConfiguration : lors de l'appel de la méthode SOVD Read Configuration, le Diagnostic Server appelle la méthode RequestGetConfiguration [SWS_DM_01787], tandis que lors de l'appel de Write Configuration, la méthode RequestPutConfiguration est exécutée [SWS_DM_01788].

Diagramme de contexte : intégration d'ara::diag::SovdConfiguration entre le client SOVD externe, le Diagnostic Server (DM) et le gestionnaire spécifique à l'application. Sources : [SWS_DM_01429], [SWS_DM_01787], [SWS_DM_01788], [SWS_DM_01860].

Cycle de vie

L'instanciation de ara::diag::SovdConfiguration s'effectue côté application par la transmission d'un ara::core::InstanceSpecifier ainsi que l'indication d'un ConcurrencyType (kConcurrent ou kNotConcurrent) [SWS_DM_01864]. Le InstanceSpecifier référence un prototype de port d'un DiagnosticSovdConfigurationInterface dans le contexte du processus [SWS_DM_01864]. La classe ne doit pas être copiée (le constructeur de copie et l'opérateur d'assignation par copie sont déclarés comme delete) [SWS_DM_01866], [SWS_DM_01868], mais prend en charge les opérations de déplacement protégées [SWS_DM_01867], [SWS_DM_01869]. Pour recevoir des requêtes du Diagnostic Server, l'application doit appeler explicitement Offer [SWS_DM_01872]. Avec l'appel de StopOffer, la transmission des requêtes est à nouveau désactivée [SWS_DM_01930]. Lors de la destruction de l'instance via le destructeur virtuel [SWS_DM_01865], l'objet est libéré ; la libération suppose que le gestionnaire a été préalablement désenregistré de manière appropriée.

Diagramme d'états : phases du cycle de vie d'une instance SovdConfiguration, de l'initialisation à StopOffer en passant par l'état Offer. Sources : [SWS_DM_01864], [SWS_DM_01872], [SWS_DM_01930], [SWS_DM_01865].

Parcours d'utilisation

Un chemin d'utilisation typique commence, après la construction de la classe de gestionnaire dérivée, par l'enregistrement auprès du Diagnostic Management au moyen de Offer() [SWS_DM_01872]. Dès qu'un client externe adresse une requête de configuration SOVD à l'entité, le Diagnostic Server la transmet : lors d'une requête de lecture, RequestGetConfiguration est appelée, la configurationId, la metaInfo et un CancellationHandler étant transmis [SWS_DM_01870]. La méthode renvoie un ara::core::Future qui fournit de manière asynchrone un tuple composé d'une DataTransferReadSession et de SovdConfigurationMetaInfo [SWS_DM_01870]. De manière analogue, le serveur transmet les requêtes d'écriture via RequestPutConfiguration, qui fournit un future avec une DataTransferWriteSession et SovdConfigurationMetaInfo [SWS_DM_01871]. Avant l'arrêt du gestionnaire, l'application appelle StopOffer() afin de ne plus accepter de nouvelles requêtes [SWS_DM_01930].

Diagramme de séquence : séquence d'interaction typique lors de l'initialisation, du traitement d'une requête Read-Configuration et du désenregistrement subséquent. Sources : [SWS_DM_01872], [SWS_DM_01787], [SWS_DM_01870], [SWS_DM_01930].

Scénarios d'erreur

Dès l'instanciation dans le constructeur, des violations de modèle et de mappage peuvent survenir si le InstanceSpecifier ne peut pas être résolu dans le modèle (InstanceSpecifierMappingIntegrityViolation), si le prototype de port référencé n'est pas typé par un DiagnosticSovdConfigurationInterface (PortInterfaceMappingViolation), si aucun processus correspondant n'existe (ProcessMappingViolation) ou si l'identifiant est déjà occupé dans le processus actuel (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01864]. Lors de l'appel de Offer(), la méthode renvoie un ara::core::Result<void> qui signale en cas d'erreur DiagOfferErrc::kConfigurationMismatch si la configuration ne correspond pas au modèle DEXT, ou DiagOfferErrc::kAlreadyOffered si le service est déjà proposé [SWS_DM_01872]. Dans les méthodes asynchrones du gestionnaire RequestGetConfiguration et RequestPutConfiguration, l'application signale les états d'erreur via le ara::core::Future en utilisant des codes d'erreur SOVD standardisés selon l'ISO 17978-3 ou l'ASAM SOVD 1.1 [SWS_DM_01870], [SWS_DM_01871]. De plus, le CancellationHandler signale si une communication en cours a été interrompue [SWS_DM_01870], [SWS_DM_01871].

Ce guide repose exclusivement sur les spécifications de l'AUTOSAR Adaptive Platform Release R25-11.

fonction Offer [SWS_DM_01872] Upstream: RS_Diag_04261

ara::core::Result< void > Offer () noexcept;

This Offer will enable the DM to forward request messages to this handler.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: dd8ff181c42d Provenance

Utilisation

La méthode Offer de la classe ara::diag::SovdConfiguration sert à activer le transfert des requêtes de diagnostic par le Diagnostic Management (DM) vers le gestionnaire configuré [SWS_DM_01872]. L’appel s’effectue de manière synchrone, ne prend aucun paramètre et renvoie le résultat via ara::core::Result<void> [SWS_DM_01872]. Tant qu’un gestionnaire n’a pas été mis à disposition via Offer, le DM ne transfère aucune requête entrante, ce qui correspond au schéma fondamental de mise à disposition des interfaces de diagnostic (cf. [SWS_DM_01525], [SWS_DM_00809]).

Gestion des erreurs

En cas d’erreur, un ara::core::Result avec un code d’erreur de l’énumération DiagOfferErrc est renvoyé, avec application d’une sémantique de rollback [SWS_DM_01872] :

  • DiagOfferErrc::kAlreadyOffered : signalé lorsque le service a déjà été proposé précédemment [SWS_DM_01872].
  • DiagOfferErrc::kConfigurationMismatch : survient lorsque la configuration ne correspond pas aux données de description DEXT [SWS_DM_01872].

Concurrence et restrictions

L’opération est déclarée comme noexcept et sans émission d’exception (exception safe), mais elle est spécifiée comme non sécurisée pour les threads (not thread-safe) [SWS_DM_01872]. Les appels simultanés de la même instance depuis plusieurs threads doivent être évités par l’application appelante. Un nouvel appel après une mise à disposition déjà effectuée devrait probablement être acquitté par une erreur, sans changement d’état.

      Utilisation
      

      La méthode virtuelle pure RequestGetConfiguration de la classe ara::diag::SovdConfiguration est appelée par la Diagnostic Server Instance lorsque la méthode SOVD « Read Configuration » est exécutée pour une configuration SOVD explicitement modélisée ([SWS_DM_01787], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 « Configuration – Explicit Configurations »). Sont passés comme paramètres l'ID de configuration de l'instance à lire (configurationId), les métadonnées de la requête (metaInfo) ainsi qu'un cancellationHandler qui informe d'une éventuelle interruption de la conversation en cours ([SWS_DM_01870]).
      

      La fonction fonctionne de manière asynchrone et renvoie un ara::core::Future qui met à disposition un tuple constitué d'une session de lecture de fichiers (DataTransferReadSession) et de métadonnées de configuration associées (SovdConfigurationMetaInfo) ([SWS_DM_01870]). L'interface est déclarée comme noexcept et spécifiée comme sûre face aux exceptions ([SWS_DM_01870]).
      

      Gestion des erreurs et concurrence
      

      Si une erreur survient lors du traitement, aucune erreur C++ n'est levée, mais un code d'erreur SOVD pertinent selon ISO 17978-3 ou ASAM SOVD 1.1 est renvoyé via le Future ([SWS_DM_01870]).
      

      En ce qui concerne la sécurité vis-à-vis des threads, la spécification « conditional » s'applique : le fait que l'implémentation concrète de la fonction doive être conçue pour être thread-safe ou non thread-safe est décidé par le ConcurrencyType transmis au constructeur ([SWS_DM_01870]).

          La méthode d'API ara::diag::SovdConfiguration::RequestPutConfiguration est appelée par le Diagnostic Server lorsque la méthode « Write Configuration » doit être exécutée via l'interface SOVD pour une configuration explicitement modélisée [SWS_DM_01788], [SWS_DM_01871].
          

          Appel et paramètres
          

          La déclaration se trouve dans l’en-tête ara/diag/sovd_configuration.h. L’appel transmet les paramètres d’entrée suivants [SWS_DM_01871] :
          

            

          • configurationId : ID de l’instance de configuration à écrire sous forme de ara::core::String.
            • 

          • metaInfo : métadonnées relatives à la requête entrante (MetaInfo const &).
            • 

          • cancellationHandler : surveille l’opération en cours et signale si la communication a été interrompue.
            • 

          

          La méthode possède une sémantique asynchrone et renvoie un ara::core::Future qui, en cas de succès, met à disposition un tuple constitué d’une session d’écriture (DataTransferWriteSession) ainsi que des métadonnées associées (SovdConfigurationMetaInfo) [SWS_DM_01871].
          

          Gestion des erreurs et concurrence
          

          En cas d’erreur, le Future est résolu avec un code d’erreur SOVD approprié selon ISO 17978-3 ou ASAM SOVD 1.1 [SWS_DM_01871]. La fonction est déclarée comme noexcept et sans émission d’exception (exception safe). La sécurité des threads est conditionnelle (conditional) : le fait que l’implémentation concrète doive ou non être conçue de manière thread-safe est déterminé par le ConcurrencyType spécifié dans le constructeur [SWS_DM_01871].
          

          Interaction
          

          La fonction constitue le pendant en écriture de RequestGetConfiguration, qui est utilisée pour la méthode SOVD « Read Configuration » [SWS_DM_01787] (AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 « Configuration – Explicit Configurations »).
