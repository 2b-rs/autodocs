Sert d'interface pour le traitement des mises à jour logicielles via le protocole ASAM SOVD dans le serveur de diagnostic AUTOSAR.

La classe fournit l'interface côté application pour le traitement des mises à jour logicielles standardisées via le protocole SOVD selon ASAM SOVD [SWS_DM_01796]. Après l'instanciation, l'application active la transmission des requêtes de diagnostic aux gestionnaires de mise à jour spécifiques via la méthode Offer() [SWS_DM_01924]. Des paquets sont enregistrés, préparés, installés de manière automatisée ou manuelle, et supprimés via des méthodes asynchrones. L'ensemble des opérations relatives au transfert de données et au cycle de vie sont alors traitées de manière non bloquante par le biais de futures.

Contexte

La classe ara::diag::SovdSwUpdate définit l'interface de mise en œuvre des mises à jour logicielles standardisées conformément à ASAM SOVD au sein de l'AUTOSAR Adaptive Platform [SWS_DM_01874]. Étant donné que la logique métier proprement dite des actualisations logicielles ne se situe pas dans le cluster fonctionnel Diagnostic Management (DM), son exécution incombe à l'application respective, tandis que ara::diag::SovdSwUpdate se concentre sur le traitement conforme aux normes du protocole SOVD sous-jacent AUTOSAR_AP_SWS_Diagnostics §7.4 « SOVD Software Update API - concept ». Pour le téléversement de fichiers de mise à jour, des stratégies de transfert telles que spécifiées pour le service UDS 0x38 (RequestFileTransfer) sont employées ici AUTOSAR_AP_SWS_Diagnostics §7.4 « SOVD Software Update API - concept », [SWS_DM_01923].

Trois composants principaux participent aux séquences d’opérations : le client SOVD externe, l’instance du serveur de diagnostic (DM) pour la gestion des protocoles et du routage, ainsi que l’implémentation de gestionnaire spécifique à l’application de ara::diag::SovdSwUpdate [SWS_DM_01796], [SWS_DM_01924].

Diagramme de contexte : interaction entre le client SOVD, le serveur de diagnostic (DM) et ara::diag::SovdSwUpdate. Sources : [SWS_DM_01796], [SWS_DM_01924], AUTOSAR_AP_SWS_Diagnostics §7.4 « SOVD Software Update API - concept »

Cycle de vie

L’instanciation de ara::diag::SovdSwUpdate s’effectue via le constructeur en spécifiant un ara::core::InstanceSpecifier pointant vers un prototype de port d’un DiagnosticSovdUpdateInterface modélisé, ainsi qu’un mode de concurrence (ConcurrencyType : kConcurrent ou kNotConcurrent) [SWS_DM_01910]. Le constructeur est spécifié comme étant thread-safe et sûr vis-à-vis des exceptions [SWS_DM_01910]. Représentant une instance d’interface unique, le constructeur de copie et l’opérateur d’assignation par copie sont supprimés (=delete) et protégés [SWS_DM_01912], [SWS_DM_01914]. La construction par déplacement et l’assignation par déplacement sont disponibles avec une visibilité protégée, mais ne sont pas thread-safe [SWS_DM_01913], [SWS_DM_01915].

La destruction de l’objet est prise en charge via le destructeur virtuel ~SovdSwUpdate(), qui est considéré comme non thread-safe [SWS_DM_01911]. Le fait que les méthodes virtuelles de rappel de la classe doivent être exécutées de manière concurrente dépend directement du ConcurrencyType transmis au constructeur [SWS_DM_01910], [SWS_DM_01916].

Parcours d'utilisation

Interprétation : comme les méthodes d’interface fournies sont déclarées purement virtuelles (=0), une classe d’application dérivée devrait les implémenter pour exécuter la mise à jour proprement dite, tandis que la classe de base gère le raccordement à la plateforme.

Le déroulement régulier se divise en plusieurs phases :

  • Mise à disposition : après la création de l’objet, l’application appelle Offer() afin de permettre à Diagnostic Management de relayer les messages SOVD entrants vers cette instance [SWS_DM_01924].
  • Information et enregistrement : les paquets de mise à jour existants peuvent être interrogés via GetAllUpdates() [SWS_DM_01797], [SWS_DM_01916]. Si un nouveau paquet doit être transféré, le serveur de diagnostic demande un enregistrement via RequestUpdatePackageRegistration(), qui fournit de manière asynchrone une session d’écriture (DataTransferWriteSession) ainsi qu’un identifiant de paquet de mise à jour [SWS_DM_01923]. Les détails et l’état sont obtenus via GetUpdatePackageDetails() et GetUpdatePackageStatus() [SWS_DM_01802], [SWS_DM_01917], [SWS_DM_01921].
  • Installation ou suppression : l’installation peut soit être déclenchée de manière automatisée au moyen de PutUpdatePackageAutomated() [SWS_DM_01799], [SWS_DM_01918], soit s’effectuer en deux étapes via PrepareUpdatePackage() [SWS_DM_01800], [SWS_DM_01919] suivi de ExecuteUpdatePackage() [SWS_DM_01801], [SWS_DM_01920]. Les paquets devenus inutiles sont supprimés via DeleteUpdatePackage() [SWS_DM_01922].
  • Arrêt : avant l’arrêt, l’application désactive le relais des messages en appelant StopOffer() [SWS_DM_01925].

Diagramme de séquence : déroulement typique de l’enregistrement et de l’installation d’un paquet via SOVD. Sources : [SWS_DM_01799], [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923], [SWS_DM_01924]

Scénarios d'erreur

Lors de la proposition des services via Offer(), des erreurs spécifiques peuvent survenir dans le type de retour ara::core::Result<void> : DiagOfferErrc::kAlreadyOffered si l’instance est déjà proposée, ainsi que DiagOfferErrc::kConfigurationMismatch si la configuration ne correspond pas à l’extrait de diagnostic (DEXT) [SWS_DM_01924].

Si le constructeur est appelé avec un état de modèle erroné, des violations d’architecture sont signalées, notamment InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation ou InstanceSpecifierAlreadyInUseViolation [SWS_DM_01910].

Toutes les opérations fonctionnelles de mise à jour renvoient un ara::core::Future qui, en cas d’erreur, achemine des codes d’erreur conformes à ASAM SOVD 1.1 ou ISO 17978-3 [SWS_DM_01917], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923]. De plus, toutes les méthodes asynchrones reçoivent un CancellationHandler par lequel est signalée une interruption prématurée de la connexion de diagnostic en cours [SWS_DM_01916], [SWS_DM_01919], [SWS_DM_01923].

      L’interface est spécifiée comme noexcept et sans émission d’exception (« exception safe ») [SWS_DM_01920].
