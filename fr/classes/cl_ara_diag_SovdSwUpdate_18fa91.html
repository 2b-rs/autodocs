Contexte

La classe ara::diag::SovdSwUpdate constitue l'interface pour le traitement des mises à jour logicielles via le protocole Service-Oriented Vehicle Diagnostics (SOVD) conformément à ASAM SOVD et ISO 17978-3 ([SWS_DM_01874], [SWS_DM_01796]). Au sein de l'AUTOSAR Adaptive Platform, il existe une séparation fonctionnelle claire des tâches : la logique métier proprement dite pour l'exécution et la gestion des mises à jour logicielles reste dans l'application adaptative, tandis que le cluster fonctionnel Diagnostics (Diagnostic Server Instance ou Diagnostic Management) prend en charge la gestion du protocole SOVD sous-jacent (AUTOSAR_AP_SWS_Diagnostics §7.3 « Figure 7.4: SOVD Software Update API »).

En tant que classe de base abstraite, SovdSwUpdate définit les interfaces de rappel qui doivent être implémentées par le logiciel applicatif. Les requêtes entrantes de clients SOVD externes sont analysées par la Diagnostic Server Instance et déléguées à l'application via les méthodes correspondantes de SovdSwUpdate (AUTOSAR_AP_SWS_Diagnostics §7.3 « SOVD Software Update API »).

Diagramme de contexte : Partenaires d'interaction et répartition des rôles lors de la mise à jour logicielle SOVD. Sources : [SWS_DM_01796], [SWS_DM_01874], AUTOSAR_AP_SWS_Diagnostics §7.3 « Figure 7.4: SOVD Software Update API »

Cycle de vie

La création d'une instance spécifique à l'application s'effectue via le constructeur paramétré en spécifiant un identifiant d'instance (ara::core::InstanceSpecifier) et le modèle de concurrence souhaité (ConcurrencyType) ([SWS_DM_01910]). Le InstanceSpecifier référence ici un PortPrototype déclaré dans le manifeste logiciel, qui doit être typé selon un DiagnosticSovdUpdateInterface ([SWS_DM_01910]). Le concurrencyType détermine si les méthodes de rappel de l'instance doivent être appelées de manière thread-safe (kConcurrent) ou de manière séquentielle, respectivement non thread-safe (kNotConcurrent), en cas de requêtes simultanées ([SWS_DM_01910]).

Les instances de SovdSwUpdate sont liées de manière univoque à un port de service. Le constructeur de copie ainsi que l'opérateur d'affectation sont donc explicitement supprimés (=delete) ([SWS_DM_01912], [SWS_DM_01914]). Les opérations de déplacement sont définies comme protégées (protected) ([SWS_DM_01913], [SWS_DM_01915]).

Après une initialisation réussie, l'application doit activer explicitement le service au moyen de Offer() ([SWS_DM_01924]). Seul cet appel amène le Diagnostic Manager (DM) à transférer les requêtes SOVD entrantes vers les méthodes de gestionnaire enregistrées. Avant de détruire l'objet gestionnaire, le service doit être désenregistré via StopOffer() afin d'empêcher tout transfert ultérieur de requêtes ([SWS_DM_01925]). La destruction est achevée par le destructeur virtuel ~SovdSwUpdate() ([SWS_DM_01911]).

Parcours d'utilisation

Le déroulement opérationnel typique comprend plusieurs phases successives d'une mise à jour logicielle :

  1. Offre de service : L'application instancie sa classe dérivée de SovdSwUpdate et appelle Offer() ([SWS_DM_01924]).
  2. Enregistrement et transfert du paquet : Le Diagnostic Server transmet les requêtes d'enregistrement entrantes d'un client SOVD à RequestUpdatePackageRegistration() ([SWS_DM_01923]). La méthode renvoie un ara::core::Future avec un tuple composé d'une session d'écriture (DataTransferWriteSession) et d'un identifiant de paquet unique (updatePackageId) ([SWS_DM_01923]). Interprétation : Le transfert de données effectif de la charge utile de mise à jour devrait être traité via cette session d'écriture mise à disposition (AUTOSAR_AP_SWS_Diagnostics §7.3 « Figure 7.4: SOVD Software Update API »).
  3. Préparation du paquet : Pour préparer l'installation, le Diagnostic Server appelle PrepareUpdatePackage() ([SWS_DM_01800], [SWS_DM_01919]). À titre d'alternative, une installation automatisée peut être initiée via PutUpdatePackageAutomated() ([SWS_DM_01799], [SWS_DM_01918]).
  4. Exécution du paquet : L'installation du paquet de mise à jour préparé est initiée par l'appel de ExecuteUpdatePackage() ([SWS_DM_01801], [SWS_DM_01920]).
  5. Interrogation d'état et inspection : Pendant ou après l'opération, des informations détaillées et l'état peuvent être interrogés via GetUpdatePackageStatus() ([SWS_DM_01802], [SWS_DM_01921]), GetUpdatePackageDetails() ([SWS_DM_01917]) ou la liste globale via GetAllUpdates() ([SWS_DM_01797], [SWS_DM_01916]). Les paquets qui ne sont plus nécessaires sont supprimés via DeleteUpdatePackage() ([SWS_DM_01922]).

Diagramme de séquence : Modèle d'interaction pour l'enregistrement, l'installation et l'interrogation d'état d'un paquet de mise à jour. Sources : [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01802], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01923], [SWS_DM_01924]

Scénarios d'erreur

Les conditions d'erreur se divisent en erreurs de configuration et de modélisation, en erreurs d'état de service ainsi qu'en erreurs d'exécution spécifiques au protocole :

  • Erreurs de modèle et d'instanciation : Si la résolution du InstanceSpecifier échoue ou si celui-ci fait référence à un élément inapproprié, des violations à l'exécution (Violations) spécifiques sont signalées : InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation ainsi que InstanceSpecifierAlreadyInUseViolation si l'identifiant est déjà utilisé au sein du processus ([SWS_DM_01910]).
  • Erreurs d'offre : L'appel de Offer() renvoie un ara::core::Result<void>. En cas d'erreur, celui-ci contient DiagOfferErrc::kAlreadyOffered si le service est déjà offert, ou DiagOfferErrc::kConfigurationMismatch si la configuration ne correspond pas à l'extrait de diagnostic (DEXT) ([SWS_DM_01924]).
  • Erreurs d'exécution et de protocole : Les méthodes de rappel asynchrones renvoient des résultats sous forme de ara::core::Future. En cas d'erreur, un code d'erreur applicable selon ASAM SOVD 1.1 ou ISO 17978-3 doit être consigné dans le Future ([SWS_DM_01917], [SWS_DM_01918], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01922], [SWS_DM_01923]).
  • Gestion des annulations : Un CancellationHandler est transmis à toutes les méthodes asynchrones. L'application est responsable de son interrogation afin de terminer proprement une conversation client prématurément interrompue ([SWS_DM_01919], [SWS_DM_01920]).

Ce guide est basé sur la spécification AUTOSAR Adaptive Platform Release R25-11.
