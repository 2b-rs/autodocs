classe ara::log::LogStream

[SWS_LOG_00173] Upstream: RS_LT_00003, RS_LT_00046

class LogStream final {...};

Represents a Log message, allowing stream operators to be used for appending data. Note: Normally Application processes would not use this class directly. Instead one of the log methods provided in the main Logging API shall be used. Those methods automatically setup a temporary object of this class with the given log severity level. The only reason to use this class directly is, if the user wants to hold a ara::log::LogStream object longer than the default one-statement scope. This is useful in order to create log messages that are distributed over multiple code lines. See the ara::log::LogStream::Flush method for further information. Once this temporary object gets out of scope, its destructor takes care that the message buffer is ready to be processed by the Logging framework. Besides the existing supported operator<< overloads for ara::log::LogStream it can be easily extended for other derived types by providing a stream operator that makes use of already supported types.

Example: struct MyCustomType { int8_t foo; ara::core::String bar; };

LogStream& operator<<(LogStream& out, const MyCustomType& value) { return (out << value.foo << value.bar); }

// Producing the output "42 the answer is." Logger& ctx0 = CreateLogger("CTX0", "Context Description CTX0"); ctx0.LogDebug () << MyCustomType{42, " the answer is."};

Kontext und Rolle

Die Klasse ara::log::LogStream repräsentiert eine formatierte Logging-Nachricht innerhalb der AUTOSAR Adaptive Platform und stellt Stream-Operatoren zur Assemblierung von Lognachrichten bereit. In der Regel interagieren Anwendungsprozesse nicht direkt über Konstruktoren mit dieser Klasse. Stattdessen stellen die primären Schnittstellen der Logging-API (beispielsweise ein Logger-Kontext) spezifische Logging-Methoden bereit, die temporäre Instanzen von ara::log::LogStream mit dem passenden Schweregrad (Severity Level) konfigurieren und zurückgeben.

Die Interaktion erfolgt typischerweise zwischen drei Parteien: der Anwendung, die Daten in den Strom einspeist, dem LogStream-Objekt, das die Nutzdaten und Metadaten puffert, sowie dem unterlagernden Logging-Framework, an welches der Puffer zur endgültigen Verarbeitung übergeben wird. Eine direkte Instanziierung oder längere Haltung eines LogStream-Objekts ist ausschließlich dafür vorgesehen, Lognachrichten zeilen- oder anweisungsübergreifend zusammenzustellen.

Lebenszyklus und Besitzverhältnisse

Der Lebenszyklus von ara::log::LogStream ist auf strikte Bindung an den Erzeugungsscope und restriktive Besitzverhältnisse ausgelegt:

  • Erzeugung und Move-Semantik: Der Move-Konstruktor [SWS_LOG_00176] ist als noexcept deklariert, wird jedoch typischerweise nicht definiert. Diese Spezifikationsvorgabe erlaubt es einem C++14-konformen Compiler, Instanzen über Return Value Optimization (RVO) direkt aus Factory-Methoden der Logging-API an den Aufrufer zurückzugeben.
  • Kopier- und Zuweisungsbeschränkungen: Sowohl der Kopierkonstruktor [SWS_LOG_00174] als auch der Kopierzuweisungsoperator [SWS_LOG_00175] und der Move-Zuweisungsoperator [SWS_LOG_00177] sind gelöscht (= delete). Instanzen können daher weder dupliziert noch nachträglich verschoben werden.
  • Zerstörung und Pufferübergabe: Der Regelfall ist ein One-Statement-Scope, bei dem das temporäre Objekt am Ende der Anweisung zerstört wird. Der Destruktor [SWS_LOG_00262] ist als noexcept definiert und stellt sicher, dass der interne Nachrichtenpuffer an das Logging-Framework zur weiteren Verarbeitung übergeben wird.
  • Mehrzeilige Wiederverwendung via Flush: Wird ein LogStream-Objekt lokal über mehrere Anweisungen gehalten, muss die Methode Flush() [SWS_LOG_00039] aufgerufen werden, um den aktuellen Pufferinhalt an das Logging-Framework abzusenden und einen neuen Nachrichtenstrom zu initiieren. Zu beachten ist, dass Flush() den Puffer nicht leert, sondern dessen aktuellen Zustand weiterreicht.
  • Nebenläufigkeit: Gemäß den Schnittstellendefinitionen ist ara::log::LogStream nicht threadsicher (not thread-safe). Eine Instanz darf nicht ungeschützt nebenläufig aus mehreren Threads befüllt oder manipuliert werden.

Nutzungspfad und Operatorkettung

Der Standardnutzungspfad erfolgt über das Fluent-Interface der überladenen Schiebeoperatoren (operator<<) und Metadaten-Methoden, die jeweils eine Referenz auf *this zurückliefern:

  1. Anreicherung von Metadaten: Vor oder während des Streamings können Kontextinformationen angefügt werden. WithLocation() [SWS_LOG_00129] fügt Quelldatei und Zeilennummer ein, WithTag() [SWS_LOG_00132] hängt ein Tag an die Nachricht an, und WithPrivacy() [SWS_LOG_00258] konfiguriert den Datenschutz-Level.
  2. Einspeisen von Nutzdaten: Überladungen von operator<< nehmen Standarddatentypen entgegen:
    • Boolesche Werte über [SWS_LOG_00040].
    • Ganzzahlige Typen mit Vorzeichen (8 bis 64 Bit) über [SWS_LOG_00045], [SWS_LOG_00046], [SWS_LOG_00047] und [SWS_LOG_00048].
    • Vorzeichenlose Ganzzahlen (8 bis 64 Bit) über [SWS_LOG_00041], [SWS_LOG_00042], [SWS_LOG_00043] und [SWS_LOG_00044].
    • Gleitkommatypen (float, double) über [SWS_LOG_00049] und [SWS_LOG_00050].
    • Zeichenketten als nullterminierte UTF-8-Strings über [SWS_LOG_00051] oder als ara::core::StringView über [SWS_LOG_00062].
    • Binäre Sequenzen über ara::core::Span<const ara::core::Byte> über [SWS_LOG_00128].
    • Attributierte Argumente über ara::log::Argument<T> über [SWS_LOG_00203].
  3. Erweiterbarkeit: Anwendungsdefinierte Typen können nahtlos integriert werden, indem freie Stream-Operatoren bereitgestellt werden, die benutzerdefinierte Strukturen auf die bestehenden Basis-Operatoren abbilden.
  4. Abschluss: Beim Verlassen des Anweisungs- oder Funktionsbereichs stößt der Destruktor [SWS_LOG_00262] automatisch den Flush-Vorgang an das Logging-Framework an.

Fehlerszenarien und Randbedingungen

Die Schnittstellen von ara::log::LogStream werfen keine Ausnahmen und garantieren Exceptionsicherheit:

  • noexcept-Garantie: Sämtliche Methoden und Operatoren ([SWS_LOG_00039], [SWS_LOG_00129], [SWS_LOG_00132], [SWS_LOG_00258], [SWS_LOG_00262] sowie die Überladungen von operator<<) sind mit noexcept ausgezeichnet.
  • Typbeschränkung bei WithPrivacy: Das Template WithPrivacy<T>() [SWS_LOG_00258] verlangt zwingend einen Integral- oder Enum-Typen für T. Ein Aufruf mit abweichenden Typen führt zu einem fehlerhaften Programm (ill-formed) und bricht bereits zur Kompilierzeit ab. Zudem werden zur Laufzeit ausschließlich die niederwertigsten 8 Bit des übergebenen Werts ausgewertet; höherwertige Bits werden ignoriert.
  • Fehlende Synchronisation: Da die Klasse intern keine Synchronisationsmechanismen enthält, muss bei threadübergreifender Verwendung die Synchronisation zwingend auf Aufruferebene erfolgen, um Datenkorruption im internen Puffer zu verhindern.

<h4>Kontext und Rolle</h4>
<p>Die Klasse <code>ara::log::LogStream</code> repräsentiert eine formatierte Logging-Nachricht innerhalb der AUTOSAR Adaptive Platform und stellt Stream-Operatoren zur Assemblierung von Lognachrichten bereit. In der Regel interagieren Anwendungsprozesse nicht direkt über Konstruktoren mit dieser Klasse. Stattdessen stellen die primären Schnittstellen der Logging-API (beispielsweise ein <code>Logger</code>-Kontext) spezifische Logging-Methoden bereit, die temporäre Instanzen von <code>ara::log::LogStream</code> mit dem passenden Schweregrad (Severity Level) konfigurieren und zurückgeben.</p>
<p>Die Interaktion erfolgt typischerweise zwischen drei Parteien: der Anwendung, die Daten in den Strom einspeist, dem <code>LogStream</code>-Objekt, das die Nutzdaten und Metadaten puffert, sowie dem unterlagernden Logging-Framework, an welches der Puffer zur endgültigen Verarbeitung übergeben wird. Eine direkte Instanziierung oder längere Haltung eines <code>LogStream</code>-Objekts ist ausschließlich dafür vorgesehen, Lognachrichten zeilen- oder anweisungsübergreifend zusammenzustellen.</p>

<h4>Lebenszyklus und Besitzverhältnisse</h4>
<p>Der Lebenszyklus von <code>ara::log::LogStream</code> ist auf strikte Bindung an den Erzeugungsscope und restriktive Besitzverhältnisse ausgelegt:</p>
<ul>
  <li><strong>Erzeugung und Move-Semantik:</strong> Der Move-Konstruktor <a class="spec-record-ref" data-req="SWS_LOG_00176" href="../spec/record.html?id=SWS_LOG_00176">[SWS_LOG_00176]</a> ist als <code>noexcept</code> deklariert, wird jedoch typischerweise nicht definiert. Diese Spezifikationsvorgabe erlaubt es einem C++14-konformen Compiler, Instanzen über Return Value Optimization (RVO) direkt aus Factory-Methoden der Logging-API an den Aufrufer zurückzugeben.</li>
  <li><strong>Kopier- und Zuweisungsbeschränkungen:</strong> Sowohl der Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_LOG_00174" href="../spec/record.html?id=SWS_LOG_00174">[SWS_LOG_00174]</a> als auch der Kopierzuweisungsoperator <a class="spec-record-ref" data-req="SWS_LOG_00175" href="../spec/record.html?id=SWS_LOG_00175">[SWS_LOG_00175]</a> und der Move-Zuweisungsoperator <a class="spec-record-ref" data-req="SWS_LOG_00177" href="../spec/record.html?id=SWS_LOG_00177">[SWS_LOG_00177]</a> sind gelöscht (<code>= delete</code>). Instanzen können daher weder dupliziert noch nachträglich verschoben werden.</li>
  <li><strong>Zerstörung und Pufferübergabe:</strong> Der Regelfall ist ein One-Statement-Scope, bei dem das temporäre Objekt am Ende der Anweisung zerstört wird. Der Destruktor <a class="spec-record-ref" data-req="SWS_LOG_00262" href="../spec/record.html?id=SWS_LOG_00262">[SWS_LOG_00262]</a> ist als <code>noexcept</code> definiert und stellt sicher, dass der interne Nachrichtenpuffer an das Logging-Framework zur weiteren Verarbeitung übergeben wird.</li>
  <li><strong>Mehrzeilige Wiederverwendung via Flush:</strong> Wird ein <code>LogStream</code>-Objekt lokal über mehrere Anweisungen gehalten, muss die Methode <code>Flush()</code> <a class="spec-record-ref" data-req="SWS_LOG_00039" href="../spec/record.html?id=SWS_LOG_00039">[SWS_LOG_00039]</a> aufgerufen werden, um den aktuellen Pufferinhalt an das Logging-Framework abzusenden und einen neuen Nachrichtenstrom zu initiieren. Zu beachten ist, dass <code>Flush()</code> den Puffer nicht leert, sondern dessen aktuellen Zustand weiterreicht.</li>
  <li><strong>Nebenläufigkeit:</strong> Gemäß den Schnittstellendefinitionen ist <code>ara::log::LogStream</code> nicht threadsicher (<code>not thread-safe</code>). Eine Instanz darf nicht ungeschützt nebenläufig aus mehreren Threads befüllt oder manipuliert werden.</li>
</ul>
