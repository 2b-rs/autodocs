classe ara::log::LogStream

[SWS_LOG_00173] Upstream: RS_LT_00003, RS_LT_00046

class LogStream final {...};

Represents a Log message, allowing stream operators to be used for appending data. Note: Normally Application processes would not use this class directly. Instead one of the log methods provided in the main Logging API shall be used. Those methods automatically setup a temporary object of this class with the given log severity level. The only reason to use this class directly is, if the user wants to hold a ara::log::LogStream object longer than the default one-statement scope. This is useful in order to create log messages that are distributed over multiple code lines. See the ara::log::LogStream::Flush method for further information. Once this temporary object gets out of scope, its destructor takes care that the message buffer is ready to be processed by the Logging framework. Besides the existing supported operator<< overloads for ara::log::LogStream it can be easily extended for other derived types by providing a stream operator that makes use of already supported types.

Example: struct MyCustomType { int8_t foo; ara::core::String bar; };

LogStream& operator<<(LogStream& out, const MyCustomType& value) { return (out << value.foo << value.bar); }

// Producing the output "42 the answer is." Logger& ctx0 = CreateLogger("CTX0", "Context Description CTX0"); ctx0.LogDebug () << MyCustomType{42, " the answer is."};

Met en mémoire tampon les données de journalisation via des opérateurs de flux et transmet les messages formatés au framework de journalisation.

La classe ara::log::LogStream représente un message de journalisation formatable dont le tampon interne est rempli progressivement de données et de métadonnées via des opérateurs de flux. Les instances sont généralement obtenues de manière temporaire via des méthodes de journalisation et transmettent automatiquement le contenu collecté au framework de journalisation via le destructeur lorsqu'elles quittent la portée [SWS_LOG_00262]. Pour les messages multilignes ou réutilisés, la transmission peut être déclenchée explicitement via Flush() [SWS_LOG_00039]. Comme contrainte essentielle, la classe n'est pas thread-safe et empêche totalement les opérations de copie.

Contexte

La classe ara::log::LogStream représente un message de journalisation formatable dans le sous-système de journalisation adaptatif. Elle fournit une interface de tampon basée sur les messages, qui permet l'ajout progressif de données utiles hétérogènes à un tampon interne par l'intermédiaire d'opérateurs de flux surchargés.

Dans le cas d'usage régulier, les processus d'application n'interagissent pas directement avec LogStream par le biais d'une instanciation explicite. À la place, l'API de journalisation principale fournit (par exemple via des méthodes de journalisation telles que LogDebug()) des instances temporaires de cette classe, déjà initialisées avec le niveau de gravité requis. La seule raison prévue pour conserver un objet LogStream au-delà de la portée par défaut d'une seule instruction (One-Statement-Scope) consiste à composer des messages de journalisation sur plusieurs lignes de code. Dès que l'objet quitte sa portée ou qu'il est explicitement vidé, le contenu du tampon est transmis au framework de journalisation pour traitement ultérieur.

Cycle de vie

La création d'instances de LogStream s'effectue principalement sous la forme d'un objet temporaire via des méthodes fabriques de l'API de journalisation principale. Pour une mise à disposition efficace, la classe déclare un constructeur de déplacement en tant que noexcept [SWS_LOG_00176]. Ce constructeur de déplacement est typiquement seulement déclaré et non défini, ce qui autorise les compilateurs conformes à C++14 à utiliser l'optimisation de valeur de retour (RVO) lors du retour depuis des fonctions fabriques [SWS_LOG_00176]. Toute duplication ou affectation par déplacement d'instances est strictement exclue : le constructeur de copie [SWS_LOG_00174], l'opérateur d'affectation par copie [SWS_LOG_00175] et l'opérateur d'affectation par déplacement [SWS_LOG_00177] sont supprimés (=delete).

La fin de vie est gérée par le destructeur ~LogStream() [SWS_LOG_00262]. Lorsque l'objet quitte sa portée (par exemple à la fin d'un bloc de fonction ou d'une instruction), le destructeur veille en interne à ce que le contenu du tampon soit transmis au framework de journalisation pour traitement [SWS_LOG_00039], [SWS_LOG_00262].

Si une instance de LogStream est réutilisée dans la même portée pour plusieurs messages consécutifs, la fonction membre Flush() doit être appelée [SWS_LOG_00039]. Il est important de noter ici que Flush() ne vide pas le tampon, mais envoie les données actuelles au framework de journalisation et initie immédiatement un nouveau flux de messages [SWS_LOG_00039].

Concernant la concurrence, l'ensemble des fonctions membres est spécifié comme non thread-safe ([SWS_LOG_00039], [SWS_LOG_00040], [SWS_LOG_00129]). Un exemplaire de LogStream ne doit donc pas être utilisé en parallèle par plusieurs threads sans synchronisation externe.

Parcours d'utilisation

Un déroulement type de journalisation comprend les phases suivantes :

  1. Mise à disposition du flux : le processus applicatif appelle une méthode de journalisation qui crée une instance temporaire de LogStream et la renvoie via RVO [SWS_LOG_00176].
  2. Enrichissement en métadonnées : avant ou pendant la saisie des données, des attributs optionnels peuvent être ajoutés par chaînage de méthodes, notamment des emplacements dans le code source via WithLocation(file, line) [SWS_LOG_00129], des étiquettes via WithTag(tag) [SWS_LOG_00132] ou des niveaux de confidentialité via WithPrivacy(value) [SWS_LOG_00258]. Chacune de ces méthodes renvoie une référence à *this.
  3. Remplissage des données : des données utiles sont écrites dans le tampon interne via des opérateurs surchargés operator<<. L'interface prend en charge des types standard tels que des booléens [SWS_LOG_00040], des entiers de différentes largeurs [SWS_LOG_00041], [SWS_LOG_00044], des nombres à virgule flottante [SWS_LOG_00049], des chaînes de caractères et vues de chaînes [SWS_LOG_00051], [SWS_LOG_00062], des séquences d'octets via core::Span<const core::Byte> [SWS_LOG_00128] ainsi que des arguments structurés via Argument<T> [SWS_LOG_00203]. De plus, l'opérateur peut être étendu pour des types définis par l'utilisateur.
  4. Transmission au framework : lorsque la portée est quittée, le destructeur transmet le message [SWS_LOG_00262]. Si l'instance doit persister pour d'autres messages, Flush() est appelée explicitement [SWS_LOG_00039].

Diagramme de séquence : déroulement d'une journalisation, de la création du flux au remplissage des métadonnées et des données jusqu'à l'envoi via la sortie de portée ou Flush(). Sources : [SWS_LOG_00039], [SWS_LOG_00040], [SWS_LOG_00129], [SWS_LOG_00176], [SWS_LOG_00262]

Scénarios d'erreur

La classe suit une conception stricte sans exceptions. Toutes les fonctions membres, y compris les opérateurs de flux ([SWS_LOG_00040] à [SWS_LOG_00051], [SWS_LOG_00062], [SWS_LOG_00128], [SWS_LOG_00203]), WithLocation() [SWS_LOG_00129], WithTag() [SWS_LOG_00132], WithPrivacy() [SWS_LOG_00258], Flush() [SWS_LOG_00039] et le destructeur [SWS_LOG_00262], sont déclarées comme noexcept et sûres vis-à-vis des exceptions (« exception safe »).

Les conditions d'erreur et risques d'utilisation se limitent aux scénarios suivants :

  • Erreur de type avec WithPrivacy : le template WithPrivacy<T> exige impérativement que T soit un type entier ou un type énuméré. Si la fonction est instanciée avec un type différent, le programme est mal formé (ill-formed) et entraîne une erreur de compilation [SWS_LOG_00258]. De plus, seuls les 8 bits de poids faible de la valeur transmise sont exploités, les bits de poids fort étant ignorés [SWS_LOG_00258].
  • Absence de sécurité des threads : comme LogStream est définie comme non thread-safe ([SWS_LOG_00039], [SWS_LOG_00040]), des opérations concurrentes de lecture ou d'écriture sur la même instance sans synchronisation externe conduisent probablement à des incohérences de données ou à une corruption de tampon (interprétation).
  • Prise en charge du tampon lors d'un Flush : puisque Flush() ne vide pas physiquement le tampon mais transmet uniquement son contenu actuel au framework de journalisation [SWS_LOG_00039], il convient de garder à l'esprit, lors d'une réutilisation, qu'un nouveau message est sémantiquement commencé.
