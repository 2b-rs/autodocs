Sert à interroger et à définir les modes de rapport pour les événements de sécurité configurés dans l'IdsM.

La classe ara::idsm::ReportingModeProvider fournit des mécanismes permettant d'interroger et de définir des modes de rapport pour les événements relatifs à la sécurité dans l'Intrusion Detection System Manager [SWS_AIDSM_10600]. L'instanciation s'effectue de manière thread-safe via un ara::core::InstanceSpecifier pour un PPort modélisé [SWS_AIDSM_10601]. Au moment de l'exécution, les méthodes GetReportingMode et SetReportingMode permettent la lecture ainsi que la modification du mode d'un événement configuré. Ces méthodes n'étant pas thread-safe, un accès concurrent doit être synchronisé en externe. En cas d'identifiants d'événement inconnus, les méthodes renvoient l'erreur IdsmErrc::kUnknownEventId.

Contexte

La classe ara::idsm::ReportingModeProvider est définie dans l'en-tête ara/idsm/reporting_mode_provider.h et sert, au sein du module adaptatif idsm, à fournir et à contrôler dynamiquement les modes de rapport pour l'Intrusion Detection System Manager (IdsM) [SWS_AIDSM_10600]. Dans une architecture de véhicule interconnectée, l'IdsM surveille les événements relatifs à la sécurité (Security Events). Via le ReportingModeProvider, les applications ou les services de plateforme responsables peuvent s'adresser aux événements de sécurité configurés afin de déterminer ou de définir la manière dont un événement doit être signalé au système IdsM. La liaison à l'architecture s'effectue via un PPort modélisé qui est spécifié lors de l'instanciation [SWS_AIDSM_10601].

Cycle de vie

La classe est déclarée en tant que final [SWS_AIDSM_10600], ce qui exclut tout héritage ou toute spécialisation polymorphique. La création d'un objet s'effectue via le constructeur explicite ReportingModeProvider(const ara::core::InstanceSpecifier& instance) [SWS_AIDSM_10601]. La liaison au PPort modélisé concret est établie via le paramètre instance [SWS_AIDSM_10601]. Interprétation : la désignation d'instance transmise fait ici vraisemblablement référence au déploiement d'interface configuré dans le modèle AUTOSAR pour le service IdsM.

Concernant la concurrence, le constructeur est spécifié comme thread-safe (thread-safe) [SWS_AIDSM_10601]. En revanche, les deux méthodes opérationnelles de lecture et d'écriture des modes de rapport sont expressément désignées comme non thread-safe (not thread-safe) [SWS_AIDSM_10602], [SWS_AIDSM_10603]. Si plusieurs threads accèdent en parallèle à la même instance de ReportingModeProvider, l'appelant doit synchroniser cet accès en externe. Le cycle de vie de l'instance est typiquement lié à la durée de vie de l'application utilisatrice, qui crée l'objet, le gère et le détruit une fois l'interaction terminée.

Parcours d'utilisation

L'utilisation typique se divise en initialisation, interrogation de l'état actuel et adaptation au besoin du mode de rapport.

Tout d'abord, l'application instancie le fournisseur pour le port prévu en indiquant le InstanceSpecifier correspondant [SWS_AIDSM_10601]. Ensuite, la méthode GetReportingMode permet d'interroger le mode de rapport actuel pour un événement configuré donné [SWS_AIDSM_10602]. La méthode renvoie un ara::core::Result<ReportingModeType> qui encapsule le mode ou signale une erreur survenue [SWS_AIDSM_10602].

Si la situation de sécurité ou la configuration de diagnostic exige une modification, SetReportingMode est appelé [SWS_AIDSM_10603]. Cet appel reçoit l'identifiant eventId ainsi que le nouveau reportingMode et renvoie un ara::core::Result<void> [SWS_AIDSM_10603]. L'application vérifie le résultat pour s'assurer du bon déroulement du changement de configuration.

Diagramme de séquence : chemin d'utilisation typique pour l'interrogation et la mise à jour d'un mode de rapport via le fournisseur. Sources : [SWS_AIDSM_10601], [SWS_AIDSM_10602], [SWS_AIDSM_10603]

Scénarios d'erreur

Toutes les méthodes de la classe sont déclarées avec noexcept [SWS_AIDSM_10601], [SWS_AIDSM_10602], [SWS_AIDSM_10603]. Le traitement des erreurs s'effectue donc entièrement sans exceptions C++, via le modèle d'erreur propre à AUTOSAR ara::core::Result.

Aussi bien lors de la récupération via GetReportingMode [SWS_AIDSM_10602] que lors de la définition via SetReportingMode [SWS_AIDSM_10603], il est présupposé que le eventId transmis correspond à un événement de sécurité configuré. Si un identifiant d'événement inconnu ou non enregistré dans le système est transmis, l'opération échoue et le Result contient le code d'erreur IdsmErrc::kUnknownEventId [SWS_AIDSM_10602], [SWS_AIDSM_10603]. Les composants appelants doivent évaluer le Result avant d'accéder à la valeur et engager, en cas d'erreur, un traitement des erreurs ou une journalisation appropriée.

Ce guide repose exclusivement sur la spécification AUTOSAR pour le module adaptatif idsm dans la version R25-11.
