Fournit une vue structurée pour la gestion et la lecture par clés d'enregistrements de données de diagnostic SOVD.

La classe fournit une vue structurée sur des enregistrements de données SOVD de type RecordContentElementData pour le diagnostic de l'Adaptive Platform (SWS Diagnostics §8.60.11 « Class: DiagnosticSovdRecordContentElementDataView »). Elle permet l'ajout, la lecture et la gestion par clés d'éléments de diagnostic primitifs et complexes via des méthodes sûres pour les threads telles que Add ou operator[] ([SWS_DM_02288]). La condition préalable à toutes les opérations est que l'élément de données sous-jacent soit du type Record requis, faute de quoi les appels s'interrompent avec une erreur dans le Result de retour.

Contexte

Dans le contexte du Service-Oriented Vehicle Diagnostics (SOVD), la classe ara::diag::DiagnosticSovdRecordContentElementDataView agit comme une vue structurée (View) sur un élément de données de diagnostic de type RecordContentElementData ou ContentData (SWS Diagnostics §8.60.11 « Class: DiagnosticSovdRecordContentElementDataView », [SWS_DM_02270]). Elle permet aux applications de diagnostic et au système d'exécution de diagnostic de créer, lire et modifier des enregistrements de données (records) constitués de paires clé-valeur ([SWS_DM_02288]). Les partenaires d'interaction sont, d'une part, les implémentations de services de diagnostic qui fournissent ou consomment des données de diagnostic et, d'autre part, les objets conteneurs génériques sous-jacents de type DiagnosticSovdContentElementData. Grâce à des interfaces standardisées, la vue découple la manipulation propre à l'application de la forme de stockage physique des contenus de diagnostic.

Cycle de vie

Conformément à sa finalité de vue, l'instance ne conserve probablement qu'une référence vers un objet de données existant de type DiagnosticSovdContentElementData (Interprétation). Il en découle que la durée de vie de l'enregistrement de données référencé doit impérativement couvrir l'existence de la vue afin d'éviter les références pendantes. Selon la spécification, toutes les méthodes déclarées de la classe sont conçues pour être sûres pour les threads (thread-safe) et sûres face aux exceptions (exception safe) ([SWS_DM_02273], [SWS_DM_02288]). Le cycle de vie des éléments de données contenus dans l'enregistrement de données peut être géré de manière dynamique : les éléments existants peuvent être entièrement supprimés via Clear ([SWS_DM_02276]), effacés de manière ciblée via Remove d'après leur clé ([SWS_DM_02287]) ou retirés du conteneur par le biais d'un itérateur au moyen de Erase ([SWS_DM_02294]).

Parcours d'utilisation

Un flux d'utilisation typique comprend la préparation de la mémoire, l'ajout d'éléments, la navigation et la lecture de champs :

  • Préparation de la mémoire : afin d'éviter des réallocations lorsque le nombre d'éléments est connu, la capacité peut être définie par anticipation avec Reserve ([SWS_DM_02283]). La capacité actuelle peut être interrogée via Capacity ([SWS_DM_02274]).
  • Remplissage de l'enregistrement de données : des valeurs typées sont enregistrées en indiquant une clé (key) par le biais d'opérations surchargées Add. Les types de données primitifs tels que std::int64_t ([SWS_DM_02288]), std::uint64_t ([SWS_DM_02289]), double ([SWS_DM_02290]), bool ([SWS_DM_02291]) ainsi que les valeurs de chaîne via ara::core::StringView ([SWS_DM_02292]) sont pris en charge. De même, des éléments de diagnostic imbriqués de type DiagnosticSovdContentElementData peuvent être ajoutés ([SWS_DM_02293]).
  • Vérification et interrogation : avant l'accès, la vacuité peut être vérifiée avec Empty ([SWS_DM_02275]) et le nombre d'éléments présents avec Size ([SWS_DM_02273]). L'existence d'une clé est vérifiée au moyen de HasContentElement ([SWS_DM_02284]).
  • Accès et itération : l'accès aux éléments concrets s'effectue soit directement via l'opérateur d'indexation operator[], qui renvoie une référence vers l'élément cible ([SWS_DM_02277], [SWS_DM_02278]), soit via la méthode de recherche Find ([SWS_DM_02285], [SWS_DM_02286]). Pour les parcours, des itérateurs sont disponibles via Begin, End, CBegin et CEnd ([SWS_DM_02279], [SWS_DM_02280], [SWS_DM_02281], [SWS_DM_02282]).

Diagramme de séquence : déroulement typique lors du remplissage et de la lecture d'un élément d'enregistrement SOVD. Sources : [SWS_DM_02283], [SWS_DM_02288], [SWS_DM_02277], [SWS_DM_02271].

Scénarios d'erreur

Les opérations sur l'enregistrement de données sont soumises à de strictes préconditions quant au type de conteneur et à la validité des clés :

  • Conflits de types : toutes les méthodes d'accès, d'insertion et de suppression supposent que l'élément sous-jacent soit de type RecordContentElementData ou ContentData. Dans le cas contraire, des opérations telles que Add ([SWS_DM_02288]), operator[] ([SWS_DM_02277]), HasContentElement ([SWS_DM_02284]) et Remove ([SWS_DM_02287]) échouent et renvoient un ara::core::Result avec état d'erreur.
  • Clés non trouvées : un accès via operator[] ou une suppression via Remove renvoie une erreur si la clé demandée n'existe pas dans l'enregistrement de données ([SWS_DM_02277], [SWS_DM_02287]).
  • Itérateurs non valides lors de la suppression : la suppression par itérateur via Erase renvoie le code d'erreur DiagErrc::kInvalidArgument en cas de paramètres non valides ou de liaison de données incorrecte ([SWS_DM_02294]).
  • Traitement explicite des erreurs : outre les erreurs spécifiques aux méthodes, l'état global de l'enregistrement de données peut être explicitement marqué comme défectueux avec un ara::core::ErrorCode via SetError ([SWS_DM_02272]). Les appelants peuvent interroger l'existence d'une erreur via HasError, qui renvoie un ara::diag::DiagSovdErrc correspondant en cas d'erreur ([SWS_DM_02271]).

Utilisation

La fonction synchrone [SWS_DM_02288] insère une valeur entière signée (std::int64_t) sous la clé key indiquée (ara::core::StringView) dans une structure de données SOVD. Elle est déclarée en tant que méthode de la classe ara::diag::DiagnosticSovdRecordContentElementDataView et intégrée via l'en-tête ara/diag/diagnostic_sovd_content_element_data.h.

Prérequis et gestion des erreurs

Conformément à [SWS_DM_02288], l'objet DiagnosticSovdContentElementData sous-jacent doit être de type RecordContentElementData ou ContentData, tandis que l'élément à ajouter ne doit lui-même pas être un ContentData. La fonction est définie comme noexcept et renvoie un ara::core::Result<void>. Si l'opération échoue – par exemple parce que le conteneur cible possède un type incompatible ou que l'élément ne peut pas être ajouté –, le résultat contient un code d'erreur ; interprétation : cela devrait typiquement aussi être le cas lors de collisions de clés.

Concurrence et interaction

L'exécution est spécifiée comme sûre pour les threads et sans danger au niveau des exceptions [SWS_DM_02288]. Au sein de l'interface, il existe des surcharges de même type pour les entiers non signés ([SWS_DM_02289]), les nombres à virgule flottante ([SWS_DM_02290]), les valeurs booléennes ([SWS_DM_02291]), les chaînes de caractères ([SWS_DM_02292]) ainsi que les éléments de données imbriqués ([SWS_DM_02293]). La même méthode est par ailleurs fournie sur la classe porteuse DiagnosticSovdContentElementData ([SWS_DM_02368]).
