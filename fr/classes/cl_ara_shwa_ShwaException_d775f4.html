Contexte

La classe ara::shwa::ShwaException représente, au sein du module shwa de l'AUTOSAR Adaptive Platform, la classe d'exception spécialisée pour les cas d'erreur spécifiques au module. Conformément à la syntaxe de la classe, ShwaException dérive publiquement de la classe de base ara::core::Exception. Dans l'architecture d'AUTOSAR Adaptive, cet arbre d'héritage forme le lien fondamental entre le traitement synchrone des exceptions de C++ et le modèle d'erreur standardisé de la plateforme. Alors que les interactions régulières et les interfaces asynchrones de la plateforme reposent principalement sur le paradigme valeur-ou-erreur via ara::core::Result, ShwaException sert à transmettre les erreurs dans les contextes où les exceptions C++ sont autorisées ou explicitement requises.

Interprétation : ShwaException sert vraisemblablement de pont standardisé lorsque des opérations du module shwa échouent et que l'erreur ne doit pas être consommée sous forme de valeur de retour, mais propagée sur la pile d'appels en tant qu'exception. Les partenaires d'interaction comprennent ainsi les blocs fonctionnels internes du module shwa en tant que générateurs de l'exception ainsi que les applications utilisatrices ou les composants logiciels de niveau supérieur qui interceptent et analysent l'exception.

Cycle de vie

Le cycle de vie d'une instance de ara::shwa::ShwaException commence de manière déterministe par son instanciation explicite. Pour la création, [AP_SWS_SHWA_01303] spécifie le constructeur explicit ShwaException (ara::core::ErrorCode errorCode) noexcept;. Ce constructeur reçoit exactement un objet du type ara::core::ErrorCode, qui décrit précisément l'état d'erreur survenu.

Concernant le comportement en concurrence, [AP_SWS_SHWA_01303] stipule que le constructeur est sûr au niveau des threads (thread-safe). Cela permet la création sûre d'objets d'exception dans des flux de traitement parallèles sans mécanismes de synchronisation externes. Dans le même temps, la désignation comme sûr face aux exceptions (exception safe) et la déclaration noexcept explicite selon [AP_SWS_SHWA_01303] garantissent qu'en aucune circonstance une autre exception ne peut être levée pendant la construction de l'exception elle-même. Ceci est d'une importance cruciale pour la fiabilité du déroulement de pile dans les systèmes embarqués tolérants aux pannes.

Après la création, l'objet exception existe généralement comme une entité temporaire sur la pile ou dans l'espace de stockage des exceptions (exception-storage) de l'environnement d'exécution C++. Dès que l'exception est interceptée via un bloc catch et que le traitement de l'exception est terminé, la durée de vie de l'objet prend fin automatiquement par une destruction normale.

Parcours d'utilisation

Le déroulement typique lors de l'utilisation de ara::shwa::ShwaException suit le modèle de détection d'erreur, d'encapsulation, de déclenchement et de traitement :

  • Encapsulation de l'erreur : si une opération du module shwa rencontre une situation d'erreur non récupérable, la cause de l'erreur est enregistrée dans un ara::core::ErrorCode approprié.
  • Instanciation : le constructeur est appelé en transmettant le code d'erreur afin de préparer l'objet exception [AP_SWS_SHWA_01303]. Interprétation : le constructeur devrait typiquement être appelé dans des flux de contrôle en échec au sein de l'implémentation du service ou lors de la conversion de types de résultats erronés.
  • Déclenchement : l'instance de ShwaException est injectée dans le flux de contrôle au moyen de throw, à la suite de quoi l'environnement d'exécution déclenche le déroulement de la pile.
  • Capture et évaluation : les composants appelants interceptent l'exception, au choix sous la forme d'une référence concrète const ara::shwa::ShwaException& ou de manière polymorphe sous la forme de const ara::core::Exception&, afin d'inspecter le code d'erreur contenu et de prendre les mesures de compensation adaptées.

Scénarios d'erreur

Puisque ara::shwa::ShwaException représente elle-même le vecteur de signalement d'erreur, son profil d'erreur diffère des classes métier opérationnelles :

  • Sécurité vis-à-vis des exceptions à la création : le constructeur étant déclaré comme noexcept selon [AP_SWS_SHWA_01303], un échec de l'instanciation est exclu par la spécification. Il n'existe aucune précondition dont la violation pourrait entraîner une exception de construction.
  • Préconditions sémantiques : la précondition pour un appel pertinent est la transmission d'un code d'erreur valide et significatif. Interprétation : les scénarios d'erreur ne concernent pas la création de l'objet elle-même, mais reflètent la cause de l'erreur encodée dans le ara::core::ErrorCode transmis. La transmission d'un code d'erreur non initialisé ou inapproprié complique le diagnostic d'erreur en aval.
  • Postconditions : après une construction réussie, l'objet garantit l'intégrité des informations d'erreur pour leur traitement ultérieur par le bloc de capture.
