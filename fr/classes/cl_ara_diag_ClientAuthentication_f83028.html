Contexte

La classe ara::diag::ClientAuthentication [SWS_DM_01132] représente l’interface centrale par laquelle une application adaptative informe l’instance du serveur de diagnostic de l’état d’authentification ainsi que des rôles d’utilisateur actuellement authentifiés des clients de diagnostic externes (AUTOSAR_AP_SWS_Diagnostics, p. 130). La nécessité de cette interface découle du fait que le contrôle d’authentification proprement dit est pris en charge soit par des mécanismes de l’instance du serveur de diagnostic elle-même, soit par une logique applicative en amont [SWS_DM_01142].

Parmi les principaux partenaires d'interaction figurent :

  • Application adaptative : effectue des contrôles d’autorisation (par exemple par validation de jetons dans le contexte SOVD conformément à [SWS_DM_01470]) et signale les rôles d’utilisateur au serveur.
  • Diagnostic Server (Diagnostic Manager) : gère les états des sessions, contrôle l’accès aux ressources de diagnostic et surveille les durées d’inactivité [SWS_DM_01210].
  • Client de diagnostic : communique via UDS ou SOVD. Chaque instance de ClientAuthentication est associée via l’élément de modèle DiagnosticExternalAuthenticationIdentification à une adresse source fixe ou à une plage d’adresses d’un client de diagnostic (AUTOSAR_AP_SWS_Diagnostics, p. 129).

Diagramme de contexte : partenaires d’interaction d’ara::diag::ClientAuthentication lors de l’authentification de client. Sources : [SWS_DM_01132], [SWS_DM_01202], AUTOSAR_AP_SWS_Diagnostics, p. 129.

Cycle de vie

Les instances de ClientAuthentication ne sont pas librement instanciées directement par des constructeurs de l’application. L’application appelle plutôt l’une des méthodes de fabrique surchargées ara::diag::ExternalAuthentication::Get, après quoi le Diagnostic Manager retourne l’instance correspondante [SWS_DM_01202]. Alternativement, une instance est transmise à l’application dans le cadre de la validation d’autorisation [SWS_DM_01470]. Le nombre total d’instances dans le système est déterminé par les éléments DiagnosticExternalAuthenticationIdentification configurés dans le modèle (AUTOSAR_AP_SWS_Diagnostics, p. 129).

En ce qui concerne les relations de propriété, l’objet est conçu comme étant exclusivement déplaçable (move-only) : le constructeur de copie [SWS_DM_01139] et l’opérateur d’assignation par copie [SWS_DM_01140] sont explicitement supprimés (delete). Les instances peuvent toutefois être transmises efficacement via le constructeur de déplacement [SWS_DM_01137] et l’assignation par déplacement [SWS_DM_01138]. Le destructeur est déclaré comme noexcept [SWS_DM_01136]. La classe est spécifiée comme n’étant pas thread-safe ; des appels simultanés sur la même instance nécessitent une synchronisation externe.

Le cycle de vie logique de l’authentification repose sur l’énumération DiagnosticAuthState [SWS_DM_01133] :

  • kDeAuthenticated: État initial après le démarrage du système [SWS_DM_01205]. Seuls les rôles définis comme Default dans l'extrait de diagnostic (attribut isDefault = TRUE) sont attribués au client DEM [SWS_DM_01204]. À partir de cet état, les rôles standard peuvent être modifiés temporairement au moyen de OverrideDefaultRoles [SWS_DM_01209].
  • kAuthenticated : est pris dès que l’application appelle Authenticate avec succès [SWS_DM_01206]. Les rôles d’utilisateur explicitement transmis sont alors assignés au client.
  • Retour à kDeAuthenticated : si le client se trouve dans la session de diagnostic standard et qu’aucune autre requête n’arrive après la dernière confirmation de transmission, le Diagnostic Server réinitialise l’état à kDeAuthenticated en raison de l’inactivité [SWS_DM_01210] (par exemple à la suite d’un timeout S3 [SWS_DM_01144]).

Diagramme d’états : cycle de vie du DiagnosticAuthState et transitions d’état. Sources : [SWS_DM_01133], [SWS_DM_01204], [SWS_DM_01205], [SWS_DM_01206], [SWS_DM_01209], [SWS_DM_01210].

Parcours d'utilisation

L'utilisation typique de ClientAuthentication suit une séquence ordonnée comprenant l'obtention de l'instance, l'enregistrement du callback, l'attribution des rôles et l'extension optionnelle de la durée d'exécution :

  1. Obtenir l'instance : l'application appelle ara::diag::ExternalAuthentication::Get avec l'adresse source souhaitée afin d'obtenir l'objet ClientAuthentication associé [SWS_DM_01202].
  2. Enregistrer un observateur d'état : via SetNotifier [SWS_DM_01144], l'application enregistre un callback de fonction de type ClientAuthenticationSetNotifier [SWS_DM_02077]. Celui-ci est appelé par l'instance du serveur de diagnostic lors des changements d'état – en particulier lors du retour automatique à l'état kDeAuthenticated. Un nouvel appel écrase le notificateur précédemment enregistré [SWS_DM_01144].
  3. Interroger l'état : avec GetState [SWS_DM_01143], l'application peut vérifier de manière synchrone et à tout moment si le client est actuellement désauthentifié ou authentifié.
  4. Attribuer les rôles : dès que l'identité du client a été vérifiée, l'application signale les rôles à activer sous la forme d'un vecteur de DiagnosticAuthRole [SWS_DM_01134] via Authenticate [SWS_DM_01142]. L'instance du serveur de diagnostic passe à l'état kAuthenticated [SWS_DM_01206].
  5. Recevoir et réutiliser le handle : en cas de réussite, Authenticate renvoie un ClientAuthenticationHandle [SWS_DM_01142], [SWS_DM_01206]. Grâce à ce handle, l'application peut définir des listes d'accès supplémentaires via une DynamicAccessList [SWS_DM_01213] (AUTOSAR_AP_SWS_Diagnostics, p. 132). De plus, la création du handle entraîne le rafraîchissement du délai d'inactivité (AUTOSAR_AP_SWS_Diagnostics, p. 133).

Diagramme de séquence : séquence d'appels typique pour l'authentification et la surveillance de l'état. Sources : [SWS_DM_01142], [SWS_DM_01144], [SWS_DM_01202], [SWS_DM_01206], [SWS_DM_01210].

Scénarios d'erreur

Les méthodes de ClientAuthentication utilisent ara::core::Result pour renvoyer des résultats ou des codes d'erreur et sont systématiquement déclarées avec noexcept.

Méthode Code d'erreur Cause et gestion des erreurs

OverrideDefaultRoles [SWS_DM_01141] DiagErrc::kServiceNotAvailable Service non disponible. La méthode requiert en outre que le client se trouve à l'état kDeAuthenticated [SWS_DM_01209].

Interprétation : l'objet ClientAuthentication devrait agir comme un intermédiaire léger, tandis que la gestion autoritaire de l'état et la surveillance de l'inactivité demeurent entièrement dans le Diagnostic Manager.

<h4>Contexte</h4>
<p>La classe <code>ara::diag::ClientAuthentication</code> <a class="spec-record-ref" data-req="SWS_DM_01132" href="../spec/record.html?id=SWS_DM_01132">[SWS_DM_01132]</a> représente l’interface centrale par laquelle une application adaptative informe l’instance du serveur de diagnostic de l’état d’authentification ainsi que des rôles d’utilisateur actuellement authentifiés des clients de diagnostic externes (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=130">AUTOSAR_AP_SWS_Diagnostics, p. 130</a>). La nécessité de cette interface découle du fait que le contrôle d’authentification proprement dit est pris en charge soit par des mécanismes de l’instance du serveur de diagnostic elle-même, soit par une logique applicative en amont <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>.</p>
<p>Parmi les principaux partenaires d'interaction figurent :</p>
<ul>
<li><strong>Application adaptative :</strong> effectue des contrôles d’autorisation (par exemple par validation de jetons dans le contexte SOVD conformément à <a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>) et signale les rôles d’utilisateur au serveur.</li>
<li><strong>Diagnostic Server (Diagnostic Manager) :</strong> gère les états des sessions, contrôle l’accès aux ressources de diagnostic et surveille les durées d’inactivité <a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a>.</li>
<li><strong>Client de diagnostic :</strong> communique via UDS ou SOVD. Chaque instance de <code>ClientAuthentication</code> est associée via l’élément de modèle <code>DiagnosticExternalAuthenticationIdentification</code> à une adresse source fixe ou à une plage d’adresses d’un client de diagnostic (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics, p. 129</a>).</li>
</ul>

<h4>Cycle de vie</h4>
<p>Les instances de <code>ClientAuthentication</code> ne sont pas librement instanciées directement par des constructeurs de l’application. L’application appelle plutôt l’une des méthodes de fabrique surchargées <code>ara::diag::ExternalAuthentication::Get</code>, après quoi le Diagnostic Manager retourne l’instance correspondante <a class="spec-record-ref" data-req="SWS_DM_01202" href="../spec/record.html?id=SWS_DM_01202">[SWS_DM_01202]</a>. Alternativement, une instance est transmise à l’application dans le cadre de la validation d’autorisation <a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>. Le nombre total d’instances dans le système est déterminé par les éléments <code>DiagnosticExternalAuthenticationIdentification</code> configurés dans le modèle (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics, p. 129</a>).</p>
<p>En ce qui concerne les relations de propriété, l’objet est conçu comme étant exclusivement déplaçable (move-only) : le constructeur de copie <a class="spec-record-ref" data-req="SWS_DM_01139" href="../spec/record.html?id=SWS_DM_01139">[SWS_DM_01139]</a> et l’opérateur d’assignation par copie <a class="spec-record-ref" data-req="SWS_DM_01140" href="../spec/record.html?id=SWS_DM_01140">[SWS_DM_01140]</a> sont explicitement supprimés (<code>delete</code>). Les instances peuvent toutefois être transmises efficacement via le constructeur de déplacement <a class="spec-record-ref" data-req="SWS_DM_01137" href="../spec/record.html?id=SWS_DM_01137">[SWS_DM_01137]</a> et l’assignation par déplacement <a class="spec-record-ref" data-req="SWS_DM_01138" href="../spec/record.html?id=SWS_DM_01138">[SWS_DM_01138]</a>. Le destructeur est déclaré comme <code>noexcept</code> <a class="spec-record-ref" data-req="SWS_DM_01136" href="../spec/record.html?id=SWS_DM_01136">[SWS_DM_01136]</a>. La classe est spécifiée comme n’étant pas thread-safe ; des appels simultanés sur la même instance nécessitent une synchronisation externe.</p>
<p>Le cycle de vie logique de l’authentification repose sur l’énumération <code>DiagnosticAuthState</code> <a class="spec-record-ref" data-req="SWS_DM_01133" href="../spec/record.html?id=SWS_DM_01133">[SWS_DM_01133]</a> :</p>
<ul>
<li><strong><code>kDeAuthenticated</code>:</strong> État initial après le démarrage du système <a class="spec-record-ref" data-req="SWS_DM_01205" href="../spec/record.html?id=SWS_DM_01205">[SWS_DM_01205]</a>. Seuls les rôles définis comme Default dans l'extrait de diagnostic (attribut <code>isDefault = TRUE</code>) sont attribués au client DEM <a class="spec-record-ref" data-req="SWS_DM_01204" href="../spec/record.html?id=SWS_DM_01204">[SWS_DM_01204]</a>. À partir de cet état, les rôles standard peuvent être modifiés temporairement au moyen de <code>OverrideDefaultRoles</code> <a class="spec-record-ref" data-req="SWS_DM_01209" href="../spec/record.html?id=SWS_DM_01209">[SWS_DM_01209]</a>.</li>
<li><strong><code>kAuthenticated</code> :</strong> est pris dès que l’application appelle <code>Authenticate</code> avec succès <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>. Les rôles d’utilisateur explicitement transmis sont alors assignés au client.</li>
<li><strong>Retour à <code>kDeAuthenticated</code> :</strong> si le client se trouve dans la session de diagnostic standard et qu’aucune autre requête n’arrive après la dernière confirmation de transmission, le Diagnostic Server réinitialise l’état à <code>kDeAuthenticated</code> en raison de l’inactivité <a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a> (par exemple à la suite d’un timeout S3 <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>).</li>
</ul>

<h4>Parcours d'utilisation</h4>
<p>L'utilisation typique de <code>ClientAuthentication</code> suit une séquence ordonnée comprenant l'obtention de l'instance, l'enregistrement du callback, l'attribution des rôles et l'extension optionnelle de la durée d'exécution :</p>
<ol>
<li><strong>Obtenir l'instance :</strong> l'application appelle <code>ara::diag::ExternalAuthentication::Get</code> avec l'adresse source souhaitée afin d'obtenir l'objet <code>ClientAuthentication</code> associé <a class="spec-record-ref" data-req="SWS_DM_01202" href="../spec/record.html?id=SWS_DM_01202">[SWS_DM_01202]</a>.</li>
<li><strong>Enregistrer un observateur d'état :</strong> via <code>SetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>, l'application enregistre un callback de fonction de type <code>ClientAuthenticationSetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_02077" href="../spec/record.html?id=SWS_DM_02077">[SWS_DM_02077]</a>. Celui-ci est appelé par l'instance du serveur de diagnostic lors des changements d'état – en particulier lors du retour automatique à l'état <code>kDeAuthenticated</code>. Un nouvel appel écrase le notificateur précédemment enregistré <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>.</li>
<li><strong>Interroger l'état :</strong> avec <code>GetState</code> <a class="spec-record-ref" data-req="SWS_DM_01143" href="../spec/record.html?id=SWS_DM_01143">[SWS_DM_01143]</a>, l'application peut vérifier de manière synchrone et à tout moment si le client est actuellement désauthentifié ou authentifié.</li>
<li><strong>Attribuer les rôles :</strong> dès que l'identité du client a été vérifiée, l'application signale les rôles à activer sous la forme d'un vecteur de <code>DiagnosticAuthRole</code> <a class="spec-record-ref" data-req="SWS_DM_01134" href="../spec/record.html?id=SWS_DM_01134">[SWS_DM_01134]</a> via <code>Authenticate</code> <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>. L'instance du serveur de diagnostic passe à l'état <code>kAuthenticated</code> <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>.</li>
<li><strong>Recevoir et réutiliser le handle :</strong> en cas de réussite, <code>Authenticate</code> renvoie un <code>ClientAuthenticationHandle</code> <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>, <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>. Grâce à ce handle, l'application peut définir des listes d'accès supplémentaires via une <code>DynamicAccessList</code> <a class="spec-record-ref" data-req="SWS_DM_01213" href="../spec/record.html?id=SWS_DM_01213">[SWS_DM_01213]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=132">AUTOSAR_AP_SWS_Diagnostics, p. 132</a>). De plus, la création du handle entraîne le rafraîchissement du délai d'inactivité (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=133">AUTOSAR_AP_SWS_Diagnostics, p. 133</a>).</li>
</ol>
