Sert à la catégorisation, à la description textuelle et à la conversion en exceptions des erreurs de diagnostic de l'Adaptive Platform.

La classe ara::diag::DiagErrorDomain définit le domaine d'erreur pour les erreurs de diagnostic dans AUTOSAR Adaptive et dérive de ara::core::ErrorDomain ([SWS_DM_00517]). Elle traduit de manière thread-safe les valeurs d'erreur de diagnostic numériques en textes descriptifs sans renvoi de nullptr ([SWS_DM_00522]) et permet, lorsque les exceptions C++ sont activées, la conversion en exceptions typées ([SWS_DM_00523]). Lorsque les exceptions du compilateur sont désactivées, l'interface d'exception est omise au profit d'un traitement des erreurs purement basé sur les valeurs.

Contexte

La classe ara::diag::DiagErrorDomain représente le domaine d'erreur standardisé pour les erreurs de diagnostic au sein du module diag de l'AUTOSAR Adaptive Platform ([SWS_DM_00517]). Conformément à la définition de classe dans AUTOSAR_AP_SWS_Diagnostics §8.11.3 « Class: DiagErrorDomain », elle est déclarée comme final et dérive de la classe d'infrastructure de base ara::core::ErrorDomain. Sa responsabilité principale consiste à intégrer les codes d'erreur de diagnostic dans le modèle d'erreur unifié d'AUTOSAR Adaptive.

À cette fin, la classe associe le type d'énumération spécifique au domaine pour les valeurs d'erreur via l'alias de type Errc ([SWS_DM_00518]), fournit avec Exception un alias pour la classe de base d'exception associée DiagException ([SWS_DM_00519]) et traduit les codes d'erreur en messages textuels lisibles ([SWS_DM_00522]). Via la méthode Name(), elle renvoie le nom court du domaine spécifié dans [SWS_CORE_90023] ([SWS_DM_00521]), ce qui lui permet d'être identifiée de manière univoque par les composants de diagnostic et les applications.

Cycle de vie

L'instanciation de ara::diag::DiagErrorDomain s'effectue via le constructeur par défaut (AUTOSAR_AP_SWS_Diagnostics §8.11.3.2.1.1 « Default Constructor »). Celui-ci est défini comme constexpr et noexcept ([SWS_DM_00520]). En raison de ces propriétés, les instances devraient typiquement être construites dès la compilation et conservées dans l'espace d'adressage sous la forme d'objets singletons statiques ou à longue durée de vie, afin de permettre une résolution efficace des erreurs sans allocation dynamique de mémoire.

En ce qui concerne la concurrence, le constructeur par défaut ainsi que toutes les méthodes d'interface dérivées (Name(), Message() et ThrowAsException()) sont explicitement spécifiés comme thread-safe (thread-safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523]). Après la construction, l'objet ne conserve aucun état interne modifiable, de sorte que les accès concurrents en lecture à travers plusieurs threads d'application ou de diagnostic sont autorisés sans synchronisation externe supplémentaire. La destruction de l'objet ne requiert aucun nettoyage de ressources externes.

Parcours d'utilisation

Le chemin d'utilisation typique survient lorsqu'une opération de diagnostic échoue et qu'une erreur de type ara::core::ErrorCode doit être évaluée ou journalisée. L'application ou un framework de diagnostic accède au domaine d'erreur pour résoudre le texte de l'erreur ou, le cas échéant, lever une exception.

  1. Identification du domaine : l'appelant vérifie le domaine d'erreur à l'aide du nom court via Name() ([SWS_DM_00521]).
  2. Récupérer le message d'erreur : la valeur de code numérique est convertie en une description textuelle via Message(errorCode) ([SWS_DM_00522]).
  3. Lever une exception (optionnel) : si le flux de contrôle appelant prévoit un traitement des erreurs basé sur les exceptions, ara::core::ErrorCode délègue à ThrowAsException(), ce qui instancie et lève l'exception associée DiagException ([SWS_DM_00519], [SWS_DM_00523]).

Diagramme de séquence : déroulement de l'identification de l'erreur, de la résolution du texte et de la levée optionnelle d'une exception via DiagErrorDomain. Sources : [SWS_DM_00519], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523].

Scénarios d'erreur

Lors de l'utilisation de Message(), la fonction reçoit un code d'erreur du type de base ara::core::ErrorDomain::CodeType. Il est contractuellement garanti que la valeur de retour n'est jamais nullptr ([SWS_DM_00522]). Pour les valeurs de code invalides ou non spécifiées, l'implémentation renvoie vraisemblablement une chaîne de caractères de repli générique afin de respecter cette garantie.

Concernant la sécurité vis-à-vis des exceptions, le constructeur ainsi que les méthodes Name() et Message() sont déclarés comme noexcept et sont considérés comme sûrs du point de vue des exceptions (exception safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522]). En revanche, ThrowAsException() est explicitement annotée avec noexcept(false) et classée comme not exception safe ([SWS_DM_00523]), car le déclenchement ciblé d'une exception constitue sa fonction principale définie.

Une contrainte centrale concerne les chaînes d'outils sans prise en charge des exceptions C++ : si les exceptions C++ sont désactivées dans le compilateur, ThrowAsException() ne participe pas à la résolution de surcharge selon [SWS_CORE_10304] ([SWS_DM_00523]). Dans de tels environnements, les applications doivent traiter les erreurs de diagnostic de manière purement basée sur les valeurs via le type d'énumération de code d'erreur Errc ([SWS_DM_00518]).

Ce guide est basé sur la spécification AUTOSAR Adaptive Release R25-11 et résume les aspects essentiels d'ara::diag::DiagErrorDomain.

Des implémentations analogues de ThrowAsException se trouvent notamment dans ara::diag::DiagUdsNrcErrorDomain ([SWS_DM_00535], AUTOSAR_AP_SWS_Diagnostics §8.12.3.2.2.3 « ThrowAsException »), ara::diag::DiagOfferErrorDomain ([SWS_DM_00995]), ara::diag::DiagReportingErrorDomain ([SWS_DM_01002]) ainsi que ara::diag::DiagSovdErrorDomain ([SWS_DM_01815]). Interprétation : de par la spécification avec override, la méthode devrait représenter une opération d'interface commune pour le traitement polymorphe des exceptions.
