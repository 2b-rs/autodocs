Permet aux applications de traiter les requêtes de diagnostic du service UDS 0x28 pour le contrôle de la communication.

La classe ara::diag::CommunicationControl sert, dans AUTOSAR Adaptive, d'interface pour le traitement du service UDS 0x28 (CommunicationControl) dédié à la commutation des canaux de communication [SWS_DM_00808]. Après l'instanciation basée sur les modèles via un InstanceSpecifier, Offer() active le réacheminement des requêtes par le Diagnostic Manager, lesquelles sont ensuite traitées de manière asynchrone via CommCtrlRequest [SWS_DM_00806], [SWS_DM_00809]. En tant qu'élément strictement unique, la classe exclut les opérations de copie ainsi que de déplacement et requiert une désinscription via StopOffer() avant la terminaison [SWS_DM_00810].

Contexte

La classe ara::diag::CommunicationControl définit l'interface standardisée pour le déroulement du service de diagnostic UDS 0x28 (CommunicationControl) dans l'AUTOSAR Adaptive Platform AUTOSAR_AP_SWS_Diagnostics, p. 70. En tant que classe de base abstraite, elle sert d'intermédiaire entre le Diagnostic Manager (DM) et la fonctionnalité de diagnostic spécifique à l'application avec laquelle l'envoi ou la réception de certains messages de communication dans le réseau du véhicule est contrôlé. Le logiciel d'application dérive de cette classe et implémente la méthode purement virtuelle CommCtrlRequest afin de recevoir et d'exécuter les instructions de commande entrantes [SWS_DM_00808]. La liaison au modèle système AUTOSAR s'effectue via un ara::core::InstanceSpecifier qui référence un PortPrototype d'un DiagnosticComControlInterface [SWS_DM_00806].

Cycle de vie

Une instance est explicitement créée via le constructeur en indiquant le ara::core::InstanceSpecifier ainsi que le modèle de concurrence ConcurrencyType (kConcurrent ou kNotConcurrent) [SWS_DM_00806]. La classe possède une sémantique d'unicité stricte et n'est ni copiable ni déplaçable : le constructeur de copie [SWS_DM_01677] et le constructeur de déplacement [SWS_DM_01678] ainsi que l'opérateur d'assignation par copie [SWS_DM_01675] et l'opérateur d'assignation par déplacement [SWS_DM_01676] sont tous supprimés (=delete).

Après la création, l'instance reste d'abord inactive. Ce n'est que par l'appel de Offer() que le Diagnostic Manager est autorisé à réacheminer les requêtes de diagnostic entrantes vers le gestionnaire [SWS_DM_00809]. Inversement, StopOffer() retire cette autorisation et désactive le réacheminement [SWS_DM_00810]. La destruction s'effectue via le destructeur virtuel [SWS_DM_00807]. Interprétation : il devrait être nécessaire d'appeler StopOffer() avant la destruction de l'objet afin que le Diagnostic Manager ne maintienne pas de réacheminements orphelins.

En matière de concurrence, le constructeur est thread-safe [SWS_DM_00806], tandis que le destructeur [SWS_DM_00807], Offer() [SWS_DM_00809] et StopOffer() [SWS_DM_00810] ne sont pas thread-safe. L'exécution de CommCtrlRequest est conditionnellement thread-safe (conditional) : le ConcurrencyType défini dans le constructeur détermine si l'implémentation doit être thread-safe [SWS_DM_00808].

Parcours d'utilisation

Le flux régulier comprend l'instanciation de la classe dérivée, l'enregistrement du service, le traitement asynchrone des requêtes de diagnostic et la désinscription finale :

  1. Initialisation : l'application instancie le gestionnaire en spécifiant le InstanceSpecifier et le ConcurrencyType souhaité [SWS_DM_00806].
  2. Offre de service : le service est activé auprès du Diagnostic Manager via Offer() [SWS_DM_00809].
  3. Traitement de requête : si une requête UDS pour le service 0x28 arrive avec une sous-fonction quelconque, le Diagnostic Manager appelle CommCtrlRequest [SWS_DM_00808]. Les paramètres comprennent :
    • controlType (ComCtrlRequestParamsType) : tous les paramètres de requête UDS, y compris les éléments optionnels.
    • metaInfo (const MetaInfo&) : métadonnées relatives à la requête de diagnostic.
    • cancellationHandler (CancellationHandler) : sert à l'interrogation d'état via IsCanceled() ainsi qu'à l'enregistrement d'une fonction de rappel d'annulation via SetNotifier().
  4. Retour d'information : le traitement se termine de manière asynchrone et signale le résultat via ara::core::Future<void> [SWS_DM_00808].
  5. Désinscription : avant l'arrêt ou la terminaison, l'application arrête le réacheminement au moyen de StopOffer() [SWS_DM_00810].

Diagramme de séquence : déroulement typique depuis l'initialisation jusqu'à la désinscription en passant par le traitement de requêtes UDS 0x28. Sources : [SWS_DM_00806], [SWS_DM_00808], [SWS_DM_00809], [SWS_DM_00810].

Scénarios d'erreur

Dès la construction, des incohérences dans le modèle AUTOSAR peuvent conduire à des violations à l'exécution (violations) [SWS_DM_00806] :

  • InstanceSpecifierMappingIntegrityViolation : le InstanceSpecifier ne peut pas être résolu dans le contexte de l'exécutable ou ne renvoie pas à un PortPrototype.
  • PortInterfaceMappingViolation : le PortPrototype typé par DiagnosticComControlInterface n'est pas référencé par un DiagnosticServiceGenericMapping.
  • ProcessMappingViolation : une référence d'instance correspondante existe, mais il n'y a aucun processus modélisé qui corresponde au processus actuel.
  • InstanceSpecifierAlreadyInUseViolation : l'identifiant est déjà utilisé dans le même processus par une autre instance.

En cours d'exploitation, Offer() signale via la valeur de retour ara::core::Result<void> l'erreur DiagOfferErrc::kAlreadyOffered si le service a déjà été proposé auparavant et est toujours actif [SWS_DM_00809]. Si une requête de diagnostic ne peut pas être satisfaite d'un point de vue fonctionnel dans CommCtrlRequest, la méthode renvoie via le ara::core::Future<void> un Negative Response Code (NRC) conformément à l'ISO 14229-1 au moyen de DiagUdsNrcErrc [SWS_DM_00808].

La méthode purement virtuelle ara::diag::CommunicationControl::CommCtrlRequest ([SWS_DM_00808]) est appelée par l'instance de Diagnostic Server pour traiter les requêtes de diagnostic du service UDS 0x28 (CommunicationControl) ([SWS_DM_00865], SWS Diagnostics §7.3.2.8.10 « Service 0x28 – CommunicationControl »). Tous les paramètres de requête UDS, y compris la sous-fonction, sont transmis regroupés via la structure controlType ([SWS_DM_00808]). L'appel renvoie un ara::core::Future<void>, moyennant quoi le traitement s'effectue de manière asynchrone. Via le paramètre cancellationHandler, l'application peut interroger l'état d'interruption au moyen de IsCanceled() ou enregistrer via SetNotifier() un rappel pour l'interruption de la conversation ([SWS_DM_00808]).

Si l'application termine le traitement sans erreur, le Diagnostic Server envoie une réponse UDS positive ([SWS_DM_00199]). Si une erreur survient, celle-ci doit être signalée via ara::diag::DiagUdsNrcErrc sous forme de Negative Response Code (NRC) approprié selon l'ISO 14229-1 ([SWS_DM_00808]) ; le serveur répond alors négativement à la requête de service avec ce code d'erreur ([SWS_DM_00866]). Le serveur rejette par avance les sous-fonctions non configurées avec le NRC 0x12 (kSubFunctionNotSupported) ([SWS_DM_00252]).

La méthode est déclarée avec noexcept et sans exception ([SWS_DM_00808], SWS Diagnostics §8.7.1.1.3.1 « CommCtrlRequest »). Sa sécurité des threads est conditionnelle : le fait que la fonction doive être implémentée de manière thread-safe est déterminé via le paramètre de constructeur ConcurrencyType de l'instance ([SWS_DM_00808]). La commutation effective des modes de communication devrait s'effectuer de manière asynchrone en arrière-plan avant que le future ne soit résolu.

                  Utilisation
                  

                  La méthode Offer de la classe ara::diag::CommunicationControl (en-tête #include "ara/diag/communication_control.h") permet au Diagnostic Management (DM) de relayer les requêtes de diagnostic entrantes relatives au contrôle de la communication vers l'instance de gestionnaire qui les fournit [SWS_DM_00809]. L'appel s'effectue sans paramètre et renvoie le type ara::core::Result<void> [SWS_DM_00809]. Comme aucun ara::core::Future ni mécanisme de rappel n'est utilisé, l'exécution doit être interprétée comme étant synchrone.
                  


                  Gestion des erreurs
                  

                  En cas de succès, la fonction renvoie un ara::core::Result vide. Si le service a déjà été proposé auparavant pour cette instance, l'appel échoue et renvoie le code d'erreur DiagOfferErrc::kAlreadyOffered avec une sémantique de rollback [SWS_DM_00809]. Cet état d'erreur correspond au traitement d'erreur unifié pour les offres de diagnostic dans Adaptive AUTOSAR, tel qu'il est spécifié par exemple dans DiagErrc [SWS_DM_00514] ainsi que dans DiagReportingErrc [SWS_DM_00560].
                  


                  Concurrence et restrictions
                  

                  La fonction est déclarée comme noexcept et est sûre vis-à-vis des exceptions (exception safe), mais explicitement non sûre au niveau des threads (not thread-safe) [SWS_DM_00809]. Les appels sur une même instance doivent donc être synchronisés par l'application appelante afin d'éviter les conditions de concurrence lors de l'enregistrement.
                  


                  Interaction
                  

                  Le modèle d'enregistrement mis en œuvre par Offer constitue un idiome central au sein du Diagnostic Management et est utilisé de manière cohérente sur l'ensemble des gestionnaires, par exemple pour les routines [SWS_DM_00557], les services UDS généraux [SWS_DM_00619], les interfaces Security Access [SWS_DM_00766] ainsi que les services de téléversement et de téléchargement [SWS_DM_00792] [SWS_DM_00802]. Il convient de noter ici la distinction avec l'infrastructure de communication : comme le souligne AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 « Monitors », il s'agit d'une implémentation spécifique au diagnostic, qui ne doit pas être confondue avec ara::com.
