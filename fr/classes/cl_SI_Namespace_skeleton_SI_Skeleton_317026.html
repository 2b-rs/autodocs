But d'utilisation

<SI-Namespace>::skeleton::<SI>Skeleton est la classe de base Skeleton générée par la toolchain de génération à partir du modèle d’interface de service dans le Manifest ARXML. Le namespace SI hiérarchique et le nom de classe sont dérivés du Manifest ; le header généré suit le chemin <SiShortname>_skeleton.h dérivé du modèle [SWS_CM_00002]. Une implémentation de service propre hérite de cette classe et redéfinit les méthodes de service virtuelles pures ou les méthodes Fire-and-Forget [SWS_CM_00191] [SWS_CM_90434].

Création et destruction

L'implémentation dérivée peut créer le Skeleton avec ara::core::InstanceSpecifier, un seul InstanceIdentifier ou un conteneur d'identifiants ; le mode de traitement est par défaut kEvent [SWS_CM_00152] [SWS_CM_00130] [SWS_CM_00153]. Le destructeur virtuel permet la destruction via la classe de base [SWS_CM_11370].

Cycle de vie et propriété

La copie est interdite [SWS_CM_00134] [SWS_CM_11548]. La construction de déplacement et l'affectation de déplacement sont présentes ; la construction n'est pas sécurisée pour les exceptions, mais l'affectation est sécurisée pour les exceptions [SWS_CM_00135] [SWS_CM_11549].

Interaction avec d'autres classes

  • Après instanciation, OfferService() fournit le service ; StopOfferService() met fin à l'offre [SWS_CM_00101] [SWS_CM_00111].
  • Pour chaque modèle Event, il existe un membre events::<Event> ; l'implémentation envoie des valeurs via skeleton::events::<Event>::Send [SWS_CM_99557] [SWS_CM_00162].
  • Pour chaque champ, il existe un membre fields::<Field> ; Les valeurs des champs sont mises à jour via skeleton::fields::<Field>::Update [SWS_CM_99558] [SWS_CM_00119].
  • Les modes kEvent, kEventSingleThread et kPoll contrôlent le traitement des appels de méthode entrants [SWS_CM_00301]. En kPoll, ProcessNextMethodCall() exécute le prochain appel en attente dans le contexte de cette fonction [SWS_CM_00199].

Restrictions & traitement des erreurs

OfferService() peut échouer en raison de valeurs de Field non initialisées, de l’absence de Field Set Handler ou d’une erreur de communication [SWS_CM_00101]. Un gestionnaire d’erreurs E2E peut être redéfini, mais n’est pas réentrant ; pour les erreurs CRC, la DataID transmise n’est pas fiable [SWS_CM_10470]. Des gestionnaires d’erreurs de transport peuvent être enregistrés puis supprimés pour toutes les méthodes [SWS_CM_00093] [SWS_CM_00094] [SWS_CM_00095].

Intégration architecturale

Le Skeleton est l’adaptateur généré côté Provider : l’implémentation de service en dérive généralement et fournit ainsi ses méthodes, Events et Fields par Communication Management. L’interface est générée à partir de la description de l’interface de service ; la modélisation sous-jacente autorise des Events, Fields, Methods et Triggers dans une Service Interface. EXP ARAComAPI §4.1 « Proxy/Skeleton Architecture » TPS Manifest §4.2 « Service Interface »

Traitement des offres et des méthodes

Avant OfferService(), l'instance n'est pas visible pour les consommateurs. Après l'appel, les méthodes peuvent déjà être délivrées, même si l'appel n'est pas encore revenu ; Après StopOfferService(), aucun autre appel ne sera délivré. Le mode de traitement sélectionné lors de sa création s'applique pendant toute la durée de vie de l'instance squelette.
