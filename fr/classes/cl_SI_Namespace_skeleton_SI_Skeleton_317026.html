Sert à la mise à disposition côté serveur d'un service et au traitement des appels de méthode entrants.

La classe <SI-Namespace>::skeleton::<SI>Skeleton sert de base côté serveur pour la mise à disposition d'un service dans l'AUTOSAR Adaptive Platform et rattache les événements, les champs ainsi que les méthodes au middleware. Après l'instanciation avec un identifiant d'instance, le service est rendu disponible pour les consommateurs sur le réseau via OfferService() et peut être retiré avec StopOfferService() [SWS_CM_00101], [SWS_CM_00111]. Selon le mode de traitement configuré, les appels de méthode entrants sont soit traités de manière événementielle, soit doivent être déclenchés activement par l'application via scrutation (polling). Comme les opérations de copie sont supprimées, la propriété de l'instance reste strictement au sein de l'application de service créatrice.

Contexte

La classe modèle <SI-Namespace>::skeleton::<SI>Skeleton constitue le point de terminaison côté serveur pour la mise à disposition d'une Service Interface sur l'AUTOSAR Adaptive Platform. En tant que passerelle entre la logique applicative et la couche de communication, le squelette encapsule la liaison spécifique au middleware et fournit des éléments d'interface typés. Pour ce faire, la classe déclare des variables membres pour les événements via events::<Event> [SWS_CM_99557], pour les champs via fields::<Field> [SWS_CM_99558], pour les déclencheurs via triggers::<Trigger> [SWS_CM_99559] ainsi que pour les paramètres de sortie de méthode via <MethodOutArgType> [SWS_CM_11550]. Interprétation : pour fournir la fonctionnalité de service proprement dite, l'application de service dérive généralement une classe concrète de <SI>Skeleton afin d'implémenter les méthodes d'interface.

Cycle de vie

L'instanciation d'un squelette s'effectue en définissant l'attribution d'instance et le mode de traitement pour les appels de méthode (ara::com::MethodCallProcessingMode, par défaut kEvent). Les constructeurs valides acceptent un ara::core::InstanceSpecifier [SWS_CM_00152], un unique ara::com::InstanceIdentifier [SWS_CM_00130] ou un ensemble d'identifiants via un ara::com::InstanceIdentifierContainer [SWS_CM_00153]. La cardinalité du point de terminaison de service étant unique, le constructeur de copie [SWS_CM_00134] et l'opérateur d'assignation par copie [SWS_CM_11548] sont explicitement supprimés (delete). Les ressources peuvent toutefois être transférées via le constructeur de déplacement [SWS_CM_00135] ainsi que l'opérateur d'assignation par déplacement [SWS_CM_11549].

Directement après la construction, l'instance de service est créée localement, mais n'est pas encore visible sur le réseau de communication. La publication pour les consommateurs de service n'a lieu qu'avec l'appel de OfferService() [SWS_CM_00101], EXP_ARAComAPI p. 10. Si le service ne doit plus être proposé, StopOfferService() retire la mise à disposition [SWS_CM_00111], EXP_ARAComAPI p. 10. Le squelette peut ensuite être proposé à nouveau ou détruit via le destructeur virtuel ~<SI>Skeleton() [SWS_CM_11370].

Diagramme d'états : cycle de vie et transitions d'état d'un squelette de service, de l'instanciation à la libération. Sources : [SWS_CM_00101], [SWS_CM_00111], [SWS_CM_11370], EXP_ARAComAPI p. 10

Parcours d'utilisation

Le déroulement standard pour la mise à disposition d'un service s'articule selon les étapes suivantes :

  1. Configuration et enregistrement de gestionnaires : avant de proposer le service, des gestionnaires spécifiques à l'application peuvent être enregistrés. Via SetTransportFaultConditionHandler(), un gestionnaire d'erreurs de transport est enregistré soit directement [SWS_CM_00093], soit avec un exécuteur dédié pour les tâches asynchrones [SWS_CM_00094] ; il peut être retiré si nécessaire via UnsetTransportFaultConditionHandler() [SWS_CM_00095]. Les traitements d'erreurs de bout en bout (End-to-End) peuvent être surchargés via la méthode virtuelle E2EErrorHandler() [SWS_CM_10470].
  2. Mise à disposition du service : l'application de service appelle OfferService() [SWS_CM_00101]. Un appel réussi renvoie un ara::core::Result<void> vide et active l'instance de service sur le réseau.
  3. Traitement des requêtes entrantes : si le squelette a été instancié dans le mode MethodCallProcessingMode::kPoll, l'application doit exécuter activement les appels clients en attente en appelant ProcessNextMethodCall() [SWS_CM_00199]. L'appel de méthode est exécuté dans le contexte de ce thread ; la valeur de retour signale si d'autres appels sont en attente.
  4. Arrêt du service : avant la destruction de l'instance, l'offre est terminée avec StopOfferService() [SWS_CM_00111].

Diagramme de séquence : séquence d'interaction entre l'application serveur, le squelette de service et la couche de communication pendant le fonctionnement du service. Sources : [SWS_CM_00101], [SWS_CM_00111], [SWS_CM_00199], [SWS_CM_00093]

Scénarios d'erreur

Lors de l'utilisation de la classe squelette, plusieurs scénarios d'erreur et préconditions doivent être pris en compte :

  • Violations de construction : si l'autorisation échoue par Grant Enforcement, la construction s'interrompt avec InsufficientPermissionsViolation [SWS_CM_00130], [SWS_CM_00152], [SWS_CM_00153]. La transmission d'un mode de traitement non autorisé entraîne une WrongMethodCallProcessingModeViolation. Si un InstanceSpecifier est utilisé, des incohérences de modèle ou des affectations multiples peuvent provoquer les erreurs InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation ou InstanceSpecifierAlreadyInUseViolation [SWS_CM_00152].
  • Échec de la mise à disposition du service : si OfferService() échoue, un code d'erreur de ara::com::ComErrc est renvoyé [SWS_CM_00101] : ComErrc::kFieldValueNotInitialized (un champ n'a pas été initialisé au préalable via Update()), ComErrc::kFieldSetHandlerNotSet (un gestionnaire d'affectation requis d'un champ est manquant) ou ComErrc::kCommunicationFailure (erreur de connexion ou de sécurité de la liaison réseau).
  • Violation du mode de traitement : un appel de ProcessNextMethodCall() déclenche une WrongMethodCallProcessingModeViolation si le squelette n'a pas été configuré pour kPoll, mais pour kEvent ou kEventSingleThread [SWS_CM_00199].
  • Gestionnaires d'erreurs invalides : si un appelable inexistant ou vide est transmis à SetTransportFaultConditionHandler(), cela entraîne une InvalidHandlerViolation [SWS_CM_00093], [SWS_CM_00094].
  • Erreurs E2E et corruption de données : lors de la réception de messages erronés, E2EErrorHandler() est appelé avec un ComE2EErrc correspondant [SWS_CM_10470]. S'il s'agit d'une erreur CRC, l'identifiant DataID peut également être corrompu, de sorte que l'application ne doit pas considérer l'identifiant transmis comme fiable.
  • Erreur de destruction : s'il reste des échantillons de données en suspens lors de la destruction du squelette, le destructeur s'interrompt avec une DanglingSamplesViolation [SWS_CM_11370].

Ce guide repose exclusivement sur les prescriptions de spécification de l'AUTOSAR Adaptive Platform R25-11.

          La méthode ProcessNextMethodCall() sert aux fournisseurs de service dans le skeleton à traiter de manière déterministe les appels de méthode entrants en mode polling [SWS_CM_00199]. Elle ne doit être utilisée que si l'instance de skeleton a été configurée avec le mode ara::com::MethodCallProcessingMode::kPoll EXP ARAComAPI §2 « Polling ».
          
  
  
          Utilisation et sémantique
          
  
          La fonction ne prend aucun paramètre et exécute une requête d'appel de méthode en attente de façon synchrone dans le contexte de thread de l'appelant [SWS_CM_00199], [SWS_CM_00191]. Cela permet notamment aux applications temps réel de traiter les requêtes de service sans changements de contexte de thread incontrôlés dans les limites de leur budget de temps alloué EXP ARAComAPI §5.4 « ProcessNextMethodCall ». La valeur de retour signale le résultat de la récupération :
          
  
            
    
          • true : au moins une requête en attente se trouvait dans la file d'attente et a été traitée [SWS_CM_00199].
            • 
    
          • false : aucune requête n'était en attente ; la file d'attente était vide [SWS_CM_00199]. Un appel suivant direct après un false reste en règle générale sans effet EXP ARAComAPI §5.4 « ProcessNextMethodCall ».
            •
