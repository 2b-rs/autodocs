classe ara::per::WriteAccessor

[SWS_PER_00595] Upstream: RS_PER_00004, RS_AP_00122, RS_AP_00146

class WriteAccessor final :              public virtual FileAccessor {...};

WriteAccessor is used to write file data. It provides the WriteBinary and WriteText methods featuring a Result for controlled, unformatted writing, and the operator<< method for simple formatted writing. It also provides SyncToFile() to flush the buffer of the operating system to the physical storage.

Contexte

La classe ara::per::WriteAccessor représente l'interface pour l'accès en écriture aux fichiers au sein de l'AUTOSAR Adaptive Platform. Elle hérite virtuellement de FileAccessor et assume la responsabilité de la modification ciblée, de l'écrasement ainsi que de la réduction de contenus de fichiers persistants. Pour la transmission de données, elle fournit des méthodes d'écriture non formatées : WriteBinary accepte des données brutes sous la forme de ara::core::Span<const ara::core::Byte> ([SWS_PER_00423]), tandis que WriteText traite des chaînes de caractères sous la forme de ara::core::StringView ([SWS_PER_00166]). En complément, l'opérateur de flux surchargé operator<< offre une possibilité simplifiée pour les sorties de texte formatées ([SWS_PER_00125]).

Une caractéristique essentielle de WriteAccessor est le découplage entre l'écriture virtuelle et la persistance physique : lors des appels de WriteBinary ou WriteText, les données sont d'abord transférées dans des structures de tampon. Le moment exact auquel ces données sont stockées durablement sur le support de stockage dépend de l'implémentation ([SWS_PER_00423], [SWS_PER_00166]). Afin de forcer l'écriture immédiate depuis le tampon du système d'exploitation vers la mémoire physique, la classe fournit la méthode de synchronisation SyncToFile ([SWS_PER_00122]). En outre, SetFileSize permet de réduire des fichiers existants à une taille en octets prédéfinie ([SWS_PER_00428]).

Cycle de vie

Le constructeur par défaut de WriteAccessor est explicitement supprimé (WriteAccessor() = delete;, [SWS_PER_00596]). Une instanciation directe et non initialisée par l'application n'est donc pas autorisée ; les instances valides devraient typiquement être créées et transmises par des entités de gestion de persistance de niveau supérieur lors de l'ouverture de fichiers en mode écriture. La destruction et la libération des ressources s'effectuent de manière déterministe via le destructeur virtuel ~WriteAccessor() ([SWS_PER_00597]).

Concernant la concurrence, toutes les fonctions membres de WriteAccessor sont spécifiées comme non sécurisées pour les threads (« not thread-safe ») ([SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00125], [SWS_PER_00428], [SWS_PER_00122], [SWS_PER_00597]). Si plusieurs threads d'exécution accèdent simultanément à la même instance, la synchronisation entre threads incombe à l'application appelante. Toutes les opérations sont déclarées comme noexcept et garantissent la sécurité vis-à-vis des exceptions (« exception safe »), car les retours et les états d'erreur ne sont pas signalés par des exceptions C++, mais par le type de retour ara::core::Result<void>.

Parcours d'utilisation

L'utilisation typique de WriteAccessor se divise en transfert de données, ajustement facultatif de la taille et synchronisation explicite avec le support de stockage :

  1. Écriture de données : l'application transmet des blocs de données de manière séquentielle au moyen de WriteBinary ([SWS_PER_00423]) ou WriteText ([SWS_PER_00166]). Les deux méthodes renvoient un ara::core::Result<void> qui doit être vérifié quant à son succès. Pour les cas d'utilisation non critiques, operator<< peut être utilisé comme alternative ([SWS_PER_00125]).
  2. Ajustement de la taille du fichier (facultatif) : si le fichier doit être réduit, SetFileSize est appelée ([SWS_PER_00428]). Si la position actuelle dans le fichier se situe au-delà de la nouvelle taille cible, elle est définie sur la nouvelle fin de fichier ; pour une taille cible de 0, la position est également définie à 0.
  3. Forcer la persistance : afin de garantir que les données modifiées ne restent pas dans la mémoire tampon volatile en cas d'erreur ou de coupure de tension, l'application appelle SyncToFile ([SWS_PER_00122]), ce qui écrit de manière contraignante le contenu du tampon sur le support physique.

Scénarios d'erreur

En cas d'erreur, la spécification fait une distinction stricte selon l'interface utilisée ainsi qu'entre les erreurs avec et sans sémantique de rollback :

  • Ignorance silencieuse lors de l'utilisation de operator<< : si une erreur survient pendant l'utilisation de l'opérateur de flux, celle-ci est ignorée sans notification ([SWS_PER_00125]). Cet opérateur est expressément prévu comme fonction de confort pour les chemins non critiques et ne doit pas être utilisé dans des cas d'usage pertinents pour la sécurité.
  • Erreurs avec WriteBinary et WriteText : si une opération d'écriture échoue, le contenu du fichier peut être endommagé ([SWS_PER_00423], [SWS_PER_00166]). En cas de PerErrc::kPhysicalStorageFailure (« no_rollback_semantics »), l'état du fichier est indéfini ; il peut être totalement corrompu. En cas de PerErrc::kOutOfStorageSpace (« no_rollback_semantics »), le contenu du fichier est mis à jour, mais la partie dépassant l'espace de stockage disponible est rejetée ; la position dans le fichier se trouve à la fin du fichier. Si PerErrc::kEncryptionFailed (« rollback_semantics ») survient, le tampon et la position ont bien été mis à jour, mais les modifications n'ont pas pu être persistées, ce qui fait que le fichier enregistré reste dans un état plus ancien. D'autres erreurs possibles avec sémantique de rollback sont PerErrc::kQuotaExceeded (dépassement de la AllowedSize configurée du File Storage), PerErrc::kValidationFailed (échec de la validation) ainsi que PerErrc::kAuthenticationFailed (erreur lors du calcul ou de la vérification du MAC).
  • Erreur avec SetFileSize : la méthode sert exclusivement à réduire la taille du fichier. Si le paramètre size est supérieur à la taille actuelle du fichier, l'appel échoue avec PerErrc::kInvalidSize ([SWS_PER_00428]). De plus, PerErrc::kPhysicalStorageFailure, PerErrc::kValidationFailed, PerErrc::kEncryptionFailed et PerErrc::kAuthenticationFailed peuvent survenir.
  • Erreur lors de SyncToFile : lors du vidage du tampon sur le support, PerErrc::kPhysicalStorageFailure et PerErrc::kOutOfStorageSpace (sans rollback) ainsi que PerErrc::kEncryptionFailed, PerErrc::kQuotaExceeded et PerErrc::kAuthenticationFailed (avec rollback) peuvent être signalés ([SWS_PER_00122]).

WriteBinary fonction

Writes the content of a Span of Byte to the file. The time when the content is persisted depends on the implementation of Persistency. SyncTo File can be used to force Persistency to persist the file content. In case of an error, the file content might be corrupted, and the current position might or might not have changed. The expected state of the file for each supported error can be expected to be as follows: • kPhysicalStorageFailure: The state of the file is unknown. It could have been entirely destroyed. • kEncryptionFailed: The content of the file and the current position will have been updated, but could not be persisted. The persisted file will reflect an older version of the file. • kOutOfStorageSpace: The content of the file will have been updated, but the part of the operation that exceeded the quota will have been discarded. The current position will be at the end of the file.
