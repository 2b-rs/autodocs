Permet au State Management de demander et de surveiller les états de communication des réseaux logiques et physiques.

ara::nm::NetworkHandle représente un objet d'accès déplaçable et non copiable, avec lequel le State Management demande et surveille l'état de communication des réseaux via un identifiant d'instance [SWS_ANM_01000], [SWS_ANM_01001]. Outre les interrogations synchrones d'état, la classe permet de définir des demandes ainsi que d'enregistrer des notificateurs pour les états effectifs ou demandés [SWS_ANM_01007], [SWS_ANM_01009], [SWS_ANM_01010]. L'indisponibilité du service ou des notificateurs erronés sont alors signalés via des codes d'erreur standardisés dans l'objet de résultat.

Contexte

Dans le module nm, la classe ara::nm::NetworkHandle sert d'objet d'accès standardisé pour un handle de réseau logique ou physique concret, adressé via un ara::core::InstanceSpecifier d'un prototype de port [SWS_ANM_01000], [SWS_ANM_01001]. L'utilisateur principal de cette interface est le State Management fonctionnel (SM), qui déclare et surveille le besoin de communication pour des Partial Network Clusters (PNC), des VLAN ou des réseaux physiques via le handle [SWS_ANM_01000], [SWS_ANM_01009]. En tant que couche intermédiaire, l'objet encapsule l'interaction entre le groupe de fonctions demandeur et le sous-système NM sous-jacent.

Diagramme de contexte : intégration du NetworkHandle entre le State Management et la gestion de réseau. Sources : [SWS_ANM_01000], [SWS_ANM_01001], [SWS_ANM_01009], [SWS_ANM_01010], [SWS_ANM_01020], [SWS_ANM_01007]

Cycle de vie

Un ara::nm::NetworkHandle est explicitement instancié en spécifiant un ara::core::InstanceSpecifier valide pour un NetworkManagementPortInterface ; ce constructeur est spécifié comme étant thread-safe [SWS_ANM_01001]. L'instance possède une sémantique exclusive : le constructeur de copie et l'opérateur d'affectation par copie sont explicitement supprimés (= delete) [SWS_ANM_01005], [SWS_ANM_01006]. La classe prend en charge la sémantique de déplacement via un constructeur de déplacement et une affectation par déplacement, cette affectation n'étant pas sûre pour les threads [SWS_ANM_01003], [SWS_ANM_01004].

La destruction s'effectue via le destructeur non sûr pour les threads ~NetworkHandle() [SWS_ANM_01002]. Les notificateurs enregistrés avant la destruction devraient vraisemblablement être désinscrits par l'application afin d'éviter les accès asynchrones à des contextes non valides (interprétation). Question Q-7c4ae0961601196a (ouverte) Concernant les états de réseau, le handle modélise deux niveaux élémentaires via l'enum NetworkStateType : kNoCom (au moins un réseau associé ne se trouve pas dans l'état de communication totale) et kFullCom (tous les réseaux associés sont actifs) [SWS_ANM_01358].

Parcours d'utilisation

Le déroulement standard comprend l'instanciation, l'enregistrement optionnel de notificateurs, la demande de l'état de réseau ainsi que la libération ultérieure :

  • Instanciation : création du handle au moyen de l'identifiant d'instance [SWS_ANM_01001].
  • Enregistrement d'observateurs : enregistrement de fonctions de rappel de type NetworkStateChangeNotifier [SWS_ANM_01020] soit pour l'état effectif réel via RegisterNetworkStateChangeNotifier [SWS_ANM_01010], soit pour l'état demandé via RegisterNetworkRequestedStateChangeNotifier [SWS_ANM_01012]. Les deux méthodes existent également sous forme de variante template pour indiquer un contexte d'exécution personnalisé (ExecutorT) [SWS_ANM_01014], [SWS_ANM_01015]. Au maximum un notificateur par catégorie peut être actif par handle.
  • Demande d'état : demande de communication totale (NetworkStateType::kFullCom) ou de libération (NetworkStateType::kNoCom) via SetNetworkRequestedState [SWS_ANM_01009].
  • Interrogation d'état : lecture synchrone de l'état actuellement demandé avec GetNetworkRequestedState [SWS_ANM_01008] ou de l'état de réseau effectivement actif avec GetNetworkState [SWS_ANM_01007]. Les deux interrogations sont sûres pour les threads.
  • Nettoyage : désinscription explicite des gestionnaires de rappel via UnregisterNetworkStateChangeNotifier [SWS_ANM_01011] et UnregisterNetworkRequestedStateChangeNotifier [SWS_ANM_01013].

Diagramme de séquence : parcours d'utilisation typique pour l'enregistrement de notificateurs, la demande d'état et l'interrogation. Sources : [SWS_ANM_01001], [SWS_ANM_01007], [SWS_ANM_01009], [SWS_ANM_01010]

Scénarios d'erreur

Les appels de méthodes sur NetworkHandle signalent les erreurs via ara::core::Result. Les cas d'erreur suivants sont spécifiés :

  • NmErrc::kServiceNotAvailable : survient lors de SetNetworkRequestedState [SWS_ANM_01009], GetNetworkRequestedState [SWS_ANM_01008] et GetNetworkState [SWS_ANM_01007] lorsque le service de gestion de réseau sous-jacent est indisponible ou inaccessible.
  • NmErrc::kInvalidHandler : est renvoyé par les méthodes d'enregistrement de notificateurs [SWS_ANM_01010] [SWS_ANM_01012], [SWS_ANM_01014] [SWS_ANM_01015] si une fonction gestionnaire non valide est transmise ou si un notificateur est déjà enregistré.

En matière de concurrence, les interrogations de statut en lecture GetNetworkState et GetNetworkRequestedState sont thread-safe, tandis que les opérations de modification ainsi que les enregistrements ne sont pas sûrs pour les threads et nécessitent une synchronisation externe [SWS_ANM_01007], [SWS_ANM_01008], [SWS_ANM_01009], [SWS_ANM_01010].

Utilisation et cycle de vie

La classe NetworkHandle fait office d'objet d'accès à un handle réseau adressé via un ara::core::InstanceSpecifier et est prévue pour le State Management [SWS_ANM_01000]. L'instanciation s'effectue par la transmission de l'InstanceSpecifier d'un prototype de port NetworkManagementPortInterface [SWS_ANM_01001]. La classe étant déclarée comme final, elle ne peut pas être utilisée comme classe de base pour des dérivations [SWS_ANM_01000].

Sémantique de déplacement et concurrence

Les objets de cette classe possèdent une sémantique de déplacement pure : le constructeur de copie [SWS_ANM_01005] ainsi que l'opérateur d'affectation par copie [SWS_ANM_01006] sont supprimés (= delete). Les instances peuvent à la place être transférées via le constructeur de déplacement [SWS_ANM_01003] et l'opérateur d'affectation par déplacement [SWS_ANM_01004].

Concernant la sécurité des threads (thread safety), les exigences suivantes s'appliquent :

  • Le constructeur avec InstanceSpecifier est thread-safe (thread-safe) [SWS_ANM_01001].
  • Pour le constructeur de déplacement, la sécurité des threads est définie de manière spécifique à l'implémentation (implementation-defined) [SWS_ANM_01003].
  • Le destructeur [SWS_ANM_01002] et l'affectation par déplacement [SWS_ANM_01004] sont explicitement désignés comme non thread-safe (not thread-safe). Interprétation : aucune sécurité des threads n'étant garantie, le contexte appelant devrait être responsable d'une synchronisation externe si plusieurs threads utilisent le même handle.
