Contexte

La classe apext::diag::uds_transport::UdsTransportProtocolHandler est la classe de base abstraite pour les plug-ins de protocole de transport UDS spécifiques et propriétaires dans le Diagnostic Management (DM) d'AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer », [SWS_DM_00315]). Elle découple le cœur de diagnostic générique des spécificités des réseaux de transmission et des couches de transport concrets tels que DoIP ou les protocoles basés sur CAN.

Un gestionnaire de transport interagit principalement avec trois partenaires :

  • Diagnostic Management Core : Le DM gère l'ensemble du cycle de vie du gestionnaire et fournit, via la référence au manager apext::diag::uds_transport::UdsTransportProtocolMgr, l'entité correspondante pour les indications d'état et de données ([SWS_DM_09015], [SWS_DM_09025]).
  • Couche réseau et client de diagnostic : Le plug-in prend en charge l'échange de données physique ou logique avec le testeur de diagnostic externe ou interne au véhicule ([SWS_DM_00326], [SWS_DM_00351]).
  • Gestionnaire périodique (optionnel) : Si le protocole de transport respectif prend en charge les transmissions périodiques, le gestionnaire met à disposition une référence à un UdsTransportProtocolPeriodicHandler via GetPeriodicHandler() ([SWS_DM_01068]).

Cycle de vie

Le cycle de vie d'une implémentation de protocole de transport est strictement contrôlé par le DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 « Initialization, Starting and Stopping of a UDS TransportLayer », [SWS_DM_00329]). La création s'effectue via le constructeur UdsTransportProtocolHandler(handlerId, transportProtocolMgr), lors duquel le DM attribue au gestionnaire un identifiant unique de type UdsTransportProtocolHandlerID ainsi que la référence au UdsTransportProtocolMgr associé ([SWS_DM_09015], [SWS_DM_09025]). L'ID attribué peut être interrogé à tout moment via GetHandlerID() ([SWS_DM_00325]). Le constructeur est qualifié de thread-safe ([SWS_DM_09015]).

Afin de découpler du constructeur les initialisations de protocole complexes, le DM appelle ensuite Initialize() ([SWS_DM_00319], [SWS_DM_00329]). À l'exception de GetPeriodicHandler(), le DM ne doit appeler aucune autre méthode du gestionnaire avant un retour réussi de InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). Après une initialisation réussie, le DM démarre le protocole via Start() ([SWS_DM_00322]). Comme Start() est exécuté de manière asynchrone, le DM peut lancer plusieurs gestionnaires en parallèle afin de minimiser le temps de démarrage ([SWS_DM_00322]).

Lorsque l'application DM passe à l'état ApplicationState.kTerminating, elle appelle Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). Le DM attend que le gestionnaire confirme l'arrêt via UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). Après le retour de Stop(), le plug-in du gestionnaire ne doit plus appeler aucune méthode sur le manager – à la seule exception de l'acquittement HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). La destruction ultérieure s'effectue via le destructeur virtuel ([SWS_DM_09016]).

Diagramme d'états : Phases du cycle de vie et conditions de transition d'un gestionnaire de protocole de transport UDS. Sources : [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Parcours d'utilisation

En cours de fonctionnement, le gestionnaire prend en charge l'échange bidirectionnel de messages UDS :

  1. Réception de messages (indication) : Dès qu'un nouveau message UDS arrive sur un canal et que l'adresse source, l'adresse cible, le type d'adressage (physique ou fonctionnel), la longueur totale du message ainsi que les premiers octets de données utiles (au moins deux octets pour les messages de plus d'un octet) sont connus, le plug-in appelle UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 « Indication of UDS message reception », [SWS_DM_00342], [SWS_DM_00330]). Le gestionnaire transmet ici l'identification du canal dans le paramètre globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 « Channel Notifications »).
  2. Envoi de messages (transmission) : Le DM renvoie la réponse de diagnostic UDS associée via le même gestionnaire et le même canal (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 « UDS message transmission on a UDS TransportLayer », [SWS_DM_00348]). Pour ce faire, il appelle Transmit(message, channelId) ([SWS_DM_00327]). Le message est transmis au gestionnaire sous la forme d'un UdsMessageConstPtr à la manière d'un std::unique_ptr.
  3. Acquittement d'envoi : Dès que le message a été émis sur le réseau (ou qu'une erreur est survenue), le gestionnaire doit restituer la propriété de message au DM via UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). Le résultat est alors transmis sous forme de kTransmitOk ou kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Un autre chemin d'utilisation spécifique est la restauration de canaux après une réinitialisation de calculateur (service UDS 0x11 avec réponse positive après réinitialisation) : à cette fin, le DM appelle NotifyReestablishment(channelId) avant le redémarrage ([SWS_DM_00326]). Le plug-in enregistre de manière persistante les paramètres de connexion (par exemple les adresses IP et les ports). Après le redémarrage via Start(), le plug-in détecte la reconnexion du même client de diagnostic et informe le DM via UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Diagramme de séquence : Réception de messages UDS, transmission de réponse et acquittement consécutif. Sources : [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Scénarios d'erreur

L'interface traite différentes situations d'exception et d'erreur :

  • Échec de l'initialisation : Si Initialize() retourne la valeur InitializationResult::kInitializeFailed ([SWS_DM_09017]), le DM interrompt complètement le processus de démarrage de ce protocole de transport et n'appelle plus aucune méthode sur cette instance ([SWS_DM_01745]).
  • Transmissions périodiques non prises en charge : Si le protocole concret ne prend pas en charge les transmissions périodiques, l'appel de GetPeriodicHandler() retourne un ara::core::Result avec le code d'erreur kConfigurationMismatch ([SWS_DM_01068]).
  • Rejet de la restauration de canal : Si un plug-in ne peut pas satisfaire la réservation persistante pour un canal (par exemple en cas d'absence de possibilité de stockage non volatil ou d'affectation instable), NotifyReestablishment(channelId) retourne la valeur false ([SWS_DM_00326]).
  • Erreur de transmission sur le réseau : Si la couche réseau n'a pas pu envoyer un message commandé via Transmit(), le gestionnaire doit transmettre le résultat kTransmitFailed dans TransmitConfirmation ([SWS_DM_00351]). Le fait de ne pas restituer le tampon entraîne des fuites de ressources dans le DM.
  • Violation de séquence après l'arrêt : Si un plug-in appelle, après le retour de Stop(), une méthode autre que HandlerStopped() sur UdsTransportProtocolMgr, il s'agit d'une violation de la séquence de protocole ([SWS_DM_00323], [SWS_DM_01741]).

Ce guide de classe est basé sur la spécification AUTOSAR Adaptive R25-11.

              fonction NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
