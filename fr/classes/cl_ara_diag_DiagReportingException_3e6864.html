Contexte

La classe ara::diag::DiagReportingException représente un type d'exception spécifique au sein du module de diagnostic de l'AUTOSAR Adaptive Platform ([SWS_DM_00987], AUTOSAR_AP_SWS_Diagnostics §8.11.8 « Class: DiagReportingException »). Conformément à la définition syntaxique, la classe hérite publiquement de ara::core::Exception et sert à encapsuler et à signaler en tant qu'exception C++ les erreurs survenues dans le contexte de diagnostic. Elle est déclarée dans le fichier d'en-tête ara/diag/diag_error_domain.h ([SWS_DM_00988]).

En tant que dérivation de ara::core::Exception, DiagReportingException forme le lien entre les codes d'erreur relatifs au diagnostic (ara::core::ErrorCode) et le mécanisme de traitement des erreurs basé sur les exceptions d'AUTOSAR Adaptive. Les partenaires d'interaction typiques sont les classes de diagnostic ou les interfaces de rapport de diagnostic, qui instancient et lèvent l'exception, ainsi que les composants applicatifs ou de plateforme de niveau supérieur, qui interceptent et traitent ces exceptions dans des blocs try-catch correspondants.

Cycle de vie

Le cycle de vie de ara::diag::DiagReportingException correspond au cycle de vie standard des objets d'exception C++ dans le cadre du processus de déroulement de la pile (stack unwinding) :

  • Création : une instance est explicitement créée via le constructeur DiagReportingException(ara::core::ErrorCode err) lors de la survenue d'une erreur de notification correspondante ([SWS_DM_00988]). Le constructeur est déclaré comme explicit et noexcept. Cela garantit qu'aucune autre exception ne peut être levée lors de la construction de l'exception elle-même (sécurité vis-à-vis des exceptions : exception safe).
  • Possession et transmission : l'objet exception est transféré au système d'exécution C++ par l'appel de throw. Il demeure sous le contrôle de l'environnement d'exécution jusqu'à ce qu'il soit lié par une clause catch appropriée (habituellement par référence, p. ex. const ara::diag::DiagReportingException& ou const ara::core::Exception&).
  • Destruction : dès que le flux de contrôle quitte le bloc catch de traitement, l'objet exception est automatiquement libéré.
  • Concurrence : la construction est spécifiée comme sûre du point de vue des threads (thread-safe) conformément à la spécification ([SWS_DM_00988]).

Parcours d'utilisation

Le chemin d'utilisation typique comprend l'instanciation et le déclenchement par un composant de diagnostic notifiant, ainsi que l'interception et l'évaluation par l'appelant :

  1. Détection d'erreur : une opération de diagnostic échoue ou constate une condition de notification erronée et génère un ara::core::ErrorCode correspondant.
  2. Instanciation et levée : le composant instancie ara::diag::DiagReportingException avec ce code d'erreur et déclenche l'exception via throw ([SWS_DM_00988]). Vraisemblablement, cela s'effectue aussi de manière alternative en interne via des mécanismes d'encapsulation tels que ara::core::Result::ValueOrThrow().
  3. Interception : la logique applicative appelante intercepte l'exception dans un bloc try-catch.
  4. Évaluation : via les interfaces héritées de ara::core::Exception, le code d'erreur imbriqué ou son domaine d'erreur et son message peuvent être extraits puis journalisés ou traités.

Scénarios d'erreur

Étant donné que DiagReportingException constitue elle-même le support pour les informations d'erreur, les préconditions et postconditions pertinentes se situent au niveau de sa construction :

  • Code d'erreur valide comme précondition : un ara::core::ErrorCode valide doit être transmis au constructeur DiagReportingException(ara::core::ErrorCode err) ([SWS_DM_00988]). Le code d'erreur transmet la cause concrète de l'erreur issue du domaine d'erreur associé (déclaré via ara/diag/diag_error_domain.h).
  • Comportement lors de la construction : le constructeur est doté du spécificateur noexcept ([SWS_DM_00988]). Si la transmission ou l'initialisation venait à échouer, il est garanti qu'aucune autre exception ne sera levée, afin d'éviter une terminaison via std::terminate pendant un déroulement de pile (stack unwinding) déjà actif.
  • Exceptions non traitées : si une exception DiagReportingException levée n'est pas interceptée par un gestionnaire approprié le long de la pile d'appels, cela conduit à l'appel de std::terminate et ainsi à l'interruption du processus concerné.
