Reçoit les événements de sécurité qualifiés de l'IdsM via un P-Port modélisé et les transmet à des callbacks.

La classe abstraite permet la réception d'événements de sécurité qualifiés provenant de l'IdsM via un PPort modélisé [SWS_AIDSM_10800]. Les applications dérivent leur propre classe réceptrice, l'instancient avec un Instance-Specifier et activent la distribution des événements via Offer() [SWS_AIDSM_10801]. Les événements entrants sont réceptionnés via des méthodes de rappel abstraites avec des données de contexte et de temps facultatives. Étant donné que les principales méthodes d'état et de rappel ne sont pas thread-safe, l'instance nécessite une gestion coordonnée du cycle de vie.

Contexte

La classe ara::idsm::QualifiedEventsReceiver constitue, dans le module idsm de l'AUTOSAR Adaptive Platform, l'interface fonctionnelle pour la réception d'événements de sécurité qualifiés (Qualified Security Events, QSEv) [SWS_AIDSM_10800]. Elle sert de point de terminaison côté application pour un port fourni (Provided-Port, PPort) modélisé dans la conception logicielle [SWS_AIDSM_10801].

Le concept repose sur le principe d'une classe de base abstraite : ara::idsm::QualifiedEventsReceiver déclare des méthodes de rappel purement virtuelles [SWS_AIDSM_10807], [SWS_AIDSM_10810]. Les principaux partenaires d'interaction sont l'application adaptative, qui implémente une sous-classe spécialisée, ainsi que l'Intrusion Detection System Manager (IdsM), qui détecte les événements de sécurité qualifiés et les transmet à l'instance via le PPort.

Cycle de vie

La création d'un récepteur s'effectue par instanciation d'une classe dérivée de QualifiedEventsReceiver en indiquant un ara::core::InstanceSpecifier qui référence le PPort modélisé [SWS_AIDSM_10801]. Ce constructeur paramétré est spécifié comme thread-safe [SWS_AIDSM_10801].

En ce qui concerne la sémantique de possession et de valeur, la classe est strictement conçue en déplacement seul (Move-Only). Le constructeur de copie [SWS_AIDSM_10804] tout comme l'opérateur d'affectation par copie [SWS_AIDSM_10806] sont supprimés (= delete). Un transfert de propriété est cependant possible : le constructeur de déplacement est implémenté de manière thread-safe [SWS_AIDSM_10803], tandis que l'opérateur d'affectation par déplacement n'est pas thread-safe [SWS_AIDSM_10805].

Le cycle de vie fonctionnel se divise en deux phases principales :

  • Mise à disposition : immédiatement après l'instanciation, aucun événement n'est encore distribué. Seul l'appel de Offer() débloque l'acceptation des événements et autorise les appels des méthodes de rappel par l'IdsM [SWS_AIDSM_10808].
  • Désactivation : La réception d'autres événements est empêchée via la méthode StopOffer() [SWS_AIDSM_10809].

La destruction s'effectue via le destructeur virtuel ~QualifiedEventsReceiver() [SWS_AIDSM_10802]. Comme le destructeur n'est pas thread-safe, il convient de toujours exécuter StopOffer() avant la libération de l'objet récepteur, afin d'exclure avec certitude les exécutions parallèles de callbacks pendant le processus de destruction.

Parcours d'utilisation

Le déroulement typique pour l'utilisation du récepteur comprend la dérivation, la mise à disposition et la déconstruction ordonnée :

  1. Définition de classe : L'application définit une sous-classe et surcharge les deux méthodes purement virtuelles OnEventQualification() pour les événements avec des données de contexte non versionnées [SWS_AIDSM_10807] ainsi que pour les données de contexte versionnées ou vides [SWS_AIDSM_10810].
  2. Instanciation : La sous-classe est instanciée, l'identifiant d'instance du port étant transmis au constructeur de base [SWS_AIDSM_10801].
  3. Activation via Offer : L'application appelle Offer() pour démarrer la réception d'événements [SWS_AIDSM_10808]. Le ara::core::Result<void> retourné confirme la mise à disposition réussie.
  4. Réception d'événements : Si l'IdsM détecte un événement de sécurité qualifié, il appelle la méthode de callback appropriée selon le format des données :
    • OnEventQualification(EventIdType, ara::core::Optional<ContextDataType>, ara::core::Optional<TimestampType>) pour les données non versionnées [SWS_AIDSM_10807].
    • OnEventQualification(EventIdType, ara::core::Optional<VersionedContextDataType>, ara::core::Optional<TimestampType>) pour les données de contexte versionnées ou les données manquantes spécifiques à l'événement [SWS_AIDSM_10810].
  5. Désactivation et destruction : Avant l'arrêt de l'application, StopOffer() est appelé [SWS_AIDSM_10809] et l'objet est libéré normalement via le destructeur [SWS_AIDSM_10802].

Scénarios d'erreur

Lors de l'utilisation, diverses conditions d'erreur et conflits de concurrence peuvent survenir :

  • Échec lors d'Offer() : La méthode Offer() retourne un ara::core::Result<void> [SWS_AIDSM_10808]. Interprétation : si le port modélisé ne peut pas être lié dans le système ou si l'enregistrement auprès de l'IdsM échoue, l'objet Result renvoie une erreur. L'application ne doit supposer que des callbacks sont déclenchés qu'après une vérification réussie.
  • Valeurs de contexte ou d'horodatage manquantes : Dans les deux signatures de callback, les données de contexte et les horodatages sont encapsulés dans ara::core::Optional ([SWS_AIDSM_10807], [SWS_AIDSM_10810]). Un accès non vérifié sans validation (par exemple à des données de contexte vides) entraîne des erreurs dans la logique de traitement de l'application.
  • Opérations non thread-safe : À l'exception des constructeurs ([SWS_AIDSM_10801], [SWS_AIDSM_10803]), toutes les opérations – à savoir Offer() [SWS_AIDSM_10808], StopOffer() [SWS_AIDSM_10809], l'opérateur d'affectation [SWS_AIDSM_10805], le destructeur [SWS_AIDSM_10802] ainsi que les callbacks ([SWS_AIDSM_10807], [SWS_AIDSM_10810]) – ne sont pas thread-safe. Un appel non coordonné de Offer() ou StopOffer() à partir de threads différents entraîne un comportement imprévisible.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: b8f71cd4e8ed Provenance

La classe QualifiedEventsReceiver sert à recevoir des Security Events qualifiés provenant de l'Intrusion Detection System Manager (IdsM) [SWS_AIDSM_10800] dans le contexte de l'en-tête ara/idsm/qualified_events_receiver.h.

Utilisation et instanciation : une instance est créée via le constructeur QualifiedEventsReceiver(const ara::core::InstanceSpecifier& instance) pour un PPort modélisé [SWS_AIDSM_10801]. Le modèle de classe impose une sémantique de déplacement : le constructeur de copie [SWS_AIDSM_10804] ainsi que l'opérateur d'affectation par copie [SWS_AIDSM_10806] sont supprimés (= delete). Les instances peuvent à la place être transférées via le constructeur de déplacement [SWS_AIDSM_10803] ou l'affectation par déplacement [SWS_AIDSM_10805].

Concurrence et sécurité des threads (Thread Safety) : la création de l'instance via le constructeur paramétré [SWS_AIDSM_10801] ainsi que le déplacement au moyen du constructeur de déplacement [SWS_AIDSM_10803] sont spécifiés comme thread-safe. En revanche, la destruction via le destructeur virtuel [SWS_AIDSM_10802] et l'affectation par déplacement via operator= [SWS_AIDSM_10805] sont définies comme non thread-safe (not thread-safe). Les appelants doivent donc s'assurer que les opérations d'affectation et de destruction ne sont pas exécutées de manière concurrente sur le même objet.

Traitement des erreurs : toutes les fonctions de cycle de vie et d'affectation spécifiées – constructeurs, destructeur et affectation par déplacement – sont marquées avec noexcept et ne déclenchent donc aucune exception.
