Contexte

La classe ara::diag::GenericRoutine fournit une interface générique pour le traitement de routines de diagnostic dans le module de diagnostic (ara::diag) d'AUTOSAR Adaptive Platform. Elle encapsule au niveau applicatif l'interaction autour du service UDS RoutineControl (ISO 14229-1 Service 0x31). À la différence des interfaces de routines générées de manière spécifique au type, GenericRoutine traite les données de requête de façon générique sous forme de spans d'octets, de sorte que la même implémentation peut être utilisée de manière flexible pour différents identifiants de routine (routineId).

Les partenaires d'interaction centraux sont le Diagnostic Management (DM) de l'environnement d'exécution AUTOSAR et la logique de diagnostic spécifique à l'application. Le Diagnostic Management reçoit les requêtes de diagnostic de testeurs externes et transmet les requêtes RoutineControl entrantes à l'instance dès que celle-ci a été liée à un PortPrototype modélisé de type DiagnosticRoutineGenericInterface via un ara::core::InstanceSpecifier et activée [SWS_DM_00552], [SWS_DM_00557]. Le logiciel applicatif dérive sa propre classe de gestionnaire de GenericRoutine et implémente la logique d'exécution spécifique à l'application dans le calculateur du véhicule.

Cycle de vie

Le cycle de vie d'une instance de GenericRoutine comprend les phases de création, de mise à disposition du service, de traitement des requêtes, de désenregistrement et de destruction.

Lors de la création via le constructeur GenericRoutine(const ara::core::InstanceSpecifier &specifier, ConcurrencyType concurrencyType), l'objet est lié au port défini dans le modèle [SWS_DM_00552]. Le paramètre concurrencyType stipule de manière contraignante si l'interface est implémentée de manière thread-safe (kConcurrent) ou non thread-safe (kNotConcurrent), ce qui détermine si des méthodes de callback peuvent être appelées de façon concurrente par le DM [SWS_DM_00552].

En ce qui concerne les relations de propriété, GenericRoutine est conçue comme une instance unique stricte : les constructeurs et opérateurs d'affectation par copie et par déplacement sont tous supprimés (=delete) [SWS_DM_01635], [SWS_DM_01636], [SWS_DM_01637], [SWS_DM_01638]. Une instance reste ainsi attachée de façon fixe à son lieu de création.

Après l'instanciation, l'objet se trouve dans l'état Instancié. Le DM ne transmet aucun message à ce stade. Ce n'est que par l'appel synchrone de Offer() que la transmission est activée et que l'instance passe à l'état Mis à disposition [SWS_DM_00557]. La transmission des requêtes par le DM peut être désactivée à tout moment via StopOffer() [SWS_DM_00558].

La destruction s'effectue via le destructeur virtuel ~GenericRoutine() [SWS_DM_00553]. Les méthodes Offer(), StopOffer() et le destructeur ne sont pas thread-safe ; les transitions de cycle de vie doivent donc se dérouler de manière synchronisée dans le code applicatif [SWS_DM_00553], [SWS_DM_00557], [SWS_DM_00558].

Parcours d'utilisation

L'utilisation typique de GenericRoutine comprend les étapes suivantes :

  1. Instanciation et enregistrement : l'application crée une instance de la sous-classe dérivée en indiquant le InstanceSpecifier et le ConcurrencyType [SWS_DM_00552]. Elle active ensuite la réception via Offer() [SWS_DM_00557].
  2. Démarrage de routine (SubFunction 0x01) : Si le DM reçoit une requête RoutineControl avec la sous-fonction Start, il appelle la méthode purement virtuelle Start() [SWS_DM_00554]. À cette occasion, les routineId, les données brutes requestData sous forme de ara::core::Span<const std::uint8_t>, le contexte metaInfo ainsi qu'un CancellationHandler sont transmis [SWS_DM_00554]. Les données contenues dans requestData restent valides jusqu'à ce que la promesse résultante soit tenue ou que le traitement soit interrompu [SWS_DM_00554].
  3. Traitement asynchrone : la méthode renvoie immédiatement un ara::core::Future<OperationOutput> au DM [SWS_DM_00554]. Le traitement proprement dit s'effectue de manière asynchrone dans la logique applicative. Après achèvement, la promise associée est satisfaite avec le OperationOutput.
  4. Opérations optionnelles : selon la spécification de la routine, le testeur peut déclencher d'autres actions pendant ou après l'exécution :
    • Stop() (SubFunction 0x02) : est appelée pour arrêter de manière ciblée une routine en cours d'exécution [SWS_DM_00555].
    • RequestResults() (SubFunction 0x03) : sert à interroger les résultats intermédiaires ou finaux d'une routine [SWS_DM_00556].
    Les deux méthodes renvoient de manière analogue un ara::core::Future<OperationOutput> [SWS_DM_00555], [SWS_DM_00556].
  5. Arrêt du service : avant l'arrêt, l'application appelle StopOffer() afin de mettre fin au transfert par le DM [SWS_DM_00558].

Diagramme de séquence : séquence d'appel et d'exécution de Start et StopOffer. Sources : [SWS_DM_00554], [SWS_DM_00557], [SWS_DM_00558].

Scénarios d'erreur

Des erreurs peuvent survenir lors de la configuration, lors de l'enregistrement du service ainsi que pendant l'exécution :

  • Erreurs de configuration et d'instanciation : si la liaison du InstanceSpecifier échoue dans le constructeur, des violations d'exécution spécifiques sont déclenchées [SWS_DM_00552] :
    • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne fait pas référence à un PortPrototype.
    • PortInterfaceMappingViolation : un port typé par DiagnosticRoutineGenericInterface n'est associé à aucun DiagnosticServiceGenericMapping.
    • ProcessMappingViolation : aucun processus modélisé correspondant n'existe à l'exécution pour la référence d'instance existante.
    • InstanceSpecifierAlreadyInUseViolation : le InstanceSpecifier est déjà utilisé dans le processus actuel par une autre instance.
  • Erreur lors de la mise à disposition : si Offer() est appelé alors que le service est déjà activement proposé, l'appel échoue et renvoie dans le ara::core::Result<void> le code d'erreur DiagOfferErrc::kAlreadyOffered avec une sémantique de rollback [SWS_DM_00557].
  • Réponses de diagnostic négatives (UDS NRC) : si une erreur survient pendant l'exécution de la routine, le future n'est pas satisfait avec OperationOutput. À la place, un Negative Response Code approprié selon l'ISO 14229-1 doit être renvoyé via DiagUdsNrcErrc dans le chemin d'erreur [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556].
  • Interruption de la conversation de diagnostic : si une requête en cours est interrompue, l'application peut gérer cela via le cancellationHandler [SWS_DM_00554] : l'état peut être interrogé activement via cancellationHandler.IsCanceled() (renvoie TRUE en cas d'interruption), ou un callback de notification est préalablement enregistré via cancellationHandler.SetNotifier(), qui est déclenché en cas d'interruption [SWS_DM_00554].

<h4>Contexte</h4>
<p>La classe <code>ara::diag::GenericRoutine</code> fournit une interface générique pour le traitement de routines de diagnostic dans le module de diagnostic (<code>ara::diag</code>) d'AUTOSAR Adaptive Platform. Elle encapsule au niveau applicatif l'interaction autour du service UDS <em>RoutineControl</em> (ISO 14229-1 Service 0x31). À la différence des interfaces de routines générées de manière spécifique au type, <code>GenericRoutine</code> traite les données de requête de façon générique sous forme de spans d'octets, de sorte que la même implémentation peut être utilisée de manière flexible pour différents identifiants de routine (<code>routineId</code>).</p>
<p>Les partenaires d'interaction centraux sont le Diagnostic Management (DM) de l'environnement d'exécution AUTOSAR et la logique de diagnostic spécifique à l'application. Le Diagnostic Management reçoit les requêtes de diagnostic de testeurs externes et transmet les requêtes RoutineControl entrantes à l'instance dès que celle-ci a été liée à un PortPrototype modélisé de type <code>DiagnosticRoutineGenericInterface</code> via un <code>ara::core::InstanceSpecifier</code> et activée <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a>, <a class="spec-record-ref" data-req="SWS_DM_00557" href="../spec/record.html?id=SWS_DM_00557">[SWS_DM_00557]</a>. Le logiciel applicatif dérive sa propre classe de gestionnaire de <code>GenericRoutine</code> et implémente la logique d'exécution spécifique à l'application dans le calculateur du véhicule.</p>

<h4>Cycle de vie</h4>
<p>Le cycle de vie d'une instance de <code>GenericRoutine</code> comprend les phases de création, de mise à disposition du service, de traitement des requêtes, de désenregistrement et de destruction.</p>
<p>Lors de la création via le constructeur <code>GenericRoutine(const ara::core::InstanceSpecifier &amp;specifier, ConcurrencyType concurrencyType)</code>, l'objet est lié au port défini dans le modèle <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a>. Le paramètre <code>concurrencyType</code> stipule de manière contraignante si l'interface est implémentée de manière thread-safe (<code>kConcurrent</code>) ou non thread-safe (<code>kNotConcurrent</code>), ce qui détermine si des méthodes de callback peuvent être appelées de façon concurrente par le DM <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a>.</p>
<p>En ce qui concerne les relations de propriété, <code>GenericRoutine</code> est conçue comme une instance unique stricte : les constructeurs et opérateurs d'affectation par copie et par déplacement sont tous supprimés (<code>=delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01635" href="../spec/record.html?id=SWS_DM_01635">[SWS_DM_01635]</a>, <a class="spec-record-ref" data-req="SWS_DM_01636" href="../spec/record.html?id=SWS_DM_01636">[SWS_DM_01636]</a>, <a class="spec-record-ref" data-req="SWS_DM_01637" href="../spec/record.html?id=SWS_DM_01637">[SWS_DM_01637]</a>, <a class="spec-record-ref" data-req="SWS_DM_01638" href="../spec/record.html?id=SWS_DM_01638">[SWS_DM_01638]</a>. Une instance reste ainsi attachée de façon fixe à son lieu de création.</p>
<p>Après l'instanciation, l'objet se trouve dans l'état <em>Instancié</em>. Le DM ne transmet aucun message à ce stade. Ce n'est que par l'appel synchrone de <code>Offer()</code> que la transmission est activée et que l'instance passe à l'état <em>Mis à disposition</em> <a class="spec-record-ref" data-req="SWS_DM_00557" href="../spec/record.html?id=SWS_DM_00557">[SWS_DM_00557]</a>. La transmission des requêtes par le DM peut être désactivée à tout moment via <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_00558" href="../spec/record.html?id=SWS_DM_00558">[SWS_DM_00558]</a>.</p>
<p>La destruction s'effectue via le destructeur virtuel <code>~GenericRoutine()</code> <a class="spec-record-ref" data-req="SWS_DM_00553" href="../spec/record.html?id=SWS_DM_00553">[SWS_DM_00553]</a>. Les méthodes <code>Offer()</code>, <code>StopOffer()</code> et le destructeur ne sont pas thread-safe ; les transitions de cycle de vie doivent donc se dérouler de manière synchronisée dans le code applicatif <a class="spec-record-ref" data-req="SWS_DM_00553" href="../spec/record.html?id=SWS_DM_00553">[SWS_DM_00553]</a>, <a class="spec-record-ref" data-req="SWS_DM_00557" href="../spec/record.html?id=SWS_DM_00557">[SWS_DM_00557]</a>, <a class="spec-record-ref" data-req="SWS_DM_00558" href="../spec/record.html?id=SWS_DM_00558">[SWS_DM_00558]</a>.</p>

<h4>Parcours d'utilisation</h4>
<p>L'utilisation typique de <code>GenericRoutine</code> comprend les étapes suivantes :</p>
<ol>
  <li><strong>Instanciation et enregistrement :</strong> l'application crée une instance de la sous-classe dérivée en indiquant le <code>InstanceSpecifier</code> et le <code>ConcurrencyType</code> <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a>. Elle active ensuite la réception via <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_00557" href="../spec/record.html?id=SWS_DM_00557">[SWS_DM_00557]</a>.</li>
  <li><strong>Démarrage de routine (SubFunction 0x01)&#160;:</strong> Si le DM reçoit une requête RoutineControl avec la sous-fonction <em>Start</em>, il appelle la méthode purement virtuelle <code>Start()</code> <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>. À cette occasion, les <code>routineId</code>, les données brutes <code>requestData</code> sous forme de <code>ara::core::Span&lt;const std::uint8_t&gt;</code>, le contexte <code>metaInfo</code> ainsi qu'un <code>CancellationHandler</code> sont transmis <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>. Les données contenues dans <code>requestData</code> restent valides jusqu'à ce que la promesse résultante soit tenue ou que le traitement soit interrompu <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>.</li>
  <li><strong>Traitement asynchrone :</strong> la méthode renvoie immédiatement un <code>ara::core::Future&lt;OperationOutput&gt;</code> au DM <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>. Le traitement proprement dit s'effectue de manière asynchrone dans la logique applicative. Après achèvement, la promise associée est satisfaite avec le <code>OperationOutput</code>.</li>
  <li><strong>Opérations optionnelles :</strong> selon la spécification de la routine, le testeur peut déclencher d'autres actions pendant ou après l'exécution :
    <ul>
      <li><code>Stop()</code> (SubFunction 0x02) : est appelée pour arrêter de manière ciblée une routine en cours d'exécution <a class="spec-record-ref" data-req="SWS_DM_00555" href="../spec/record.html?id=SWS_DM_00555">[SWS_DM_00555]</a>.</li>
      <li><code>RequestResults()</code> (SubFunction 0x03) : sert à interroger les résultats intermédiaires ou finaux d'une routine <a class="spec-record-ref" data-req="SWS_DM_00556" href="../spec/record.html?id=SWS_DM_00556">[SWS_DM_00556]</a>.</li>
    </ul>
    Les deux méthodes renvoient de manière analogue un <code>ara::core::Future&lt;OperationOutput&gt;</code> <a class="spec-record-ref" data-req="SWS_DM_00555" href="../spec/record.html?id=SWS_DM_00555">[SWS_DM_00555]</a>, <a class="spec-record-ref" data-req="SWS_DM_00556" href="../spec/record.html?id=SWS_DM_00556">[SWS_DM_00556]</a>.</li>
  <li><strong>Arrêt du service :</strong> avant l'arrêt, l'application appelle <code>StopOffer()</code> afin de mettre fin au transfert par le DM <a class="spec-record-ref" data-req="SWS_DM_00558" href="../spec/record.html?id=SWS_DM_00558">[SWS_DM_00558]</a>.</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Des erreurs peuvent survenir lors de la configuration, lors de l'enregistrement du service ainsi que pendant l'exécution :</p>
<ul>
  <li><strong>Erreurs de configuration et d'instanciation :</strong> si la liaison du <code>InstanceSpecifier</code> échoue dans le constructeur, des violations d'exécution spécifiques sont déclenchées <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a> :
    <ul>
      <li><code>InstanceSpecifierMappingIntegrityViolation</code> : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne fait pas référence à un <code>PortPrototype</code>.</li>
      <li><code>PortInterfaceMappingViolation</code> : un port typé par <code>DiagnosticRoutineGenericInterface</code> n'est associé à aucun <code>DiagnosticServiceGenericMapping</code>.</li>
      <li><code>ProcessMappingViolation</code> : aucun processus modélisé correspondant n'existe à l'exécution pour la référence d'instance existante.</li>
      <li><code>InstanceSpecifierAlreadyInUseViolation</code> : le <code>InstanceSpecifier</code> est déjà utilisé dans le processus actuel par une autre instance.</li>
    </ul>
  </li>
  <li><strong>Erreur lors de la mise à disposition :</strong> si <code>Offer()</code> est appelé alors que le service est déjà activement proposé, l'appel échoue et renvoie dans le <code>ara::core::Result&lt;void&gt;</code> le code d'erreur <code>DiagOfferErrc::kAlreadyOffered</code> avec une sémantique de rollback <a class="spec-record-ref" data-req="SWS_DM_00557" href="../spec/record.html?id=SWS_DM_00557">[SWS_DM_00557]</a>.</li>
  <li><strong>Réponses de diagnostic négatives (UDS NRC) :</strong> si une erreur survient pendant l'exécution de la routine, le future n'est pas satisfait avec <code>OperationOutput</code>. À la place, un Negative Response Code approprié selon l'ISO 14229-1 doit être renvoyé via <code>DiagUdsNrcErrc</code> dans le chemin d'erreur <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>, <a class="spec-record-ref" data-req="SWS_DM_00555" href="../spec/record.html?id=SWS_DM_00555">[SWS_DM_00555]</a>, <a class="spec-record-ref" data-req="SWS_DM_00556" href="../spec/record.html?id=SWS_DM_00556">[SWS_DM_00556]</a>.</li>
  <li><strong>Interruption de la conversation de diagnostic :</strong> si une requête en cours est interrompue, l'application peut gérer cela via le <code>cancellationHandler</code> <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a> : l'état peut être interrogé activement via <code>cancellationHandler.IsCanceled()</code> (renvoie <code>TRUE</code> en cas d'interruption), ou un callback de notification est préalablement enregistré via <code>cancellationHandler.SetNotifier()</code>, qui est déclenché en cas d'interruption <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>.</li>
</ul>
