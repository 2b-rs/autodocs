Contexte

L'interface <ExtendedDataRecord-Namespace>::<ExtendedDataRecordElementInterface> sert, dans l'AUTOSAR Adaptive Platform au sein du cluster fonctionnel diag, à la fourniture de données pour ce qu'on appelle les Extended Data Records (AUTOSAR_AP_SWS_Diagnostics p. 68). Ces enregistrements de données sont collectés lors d'événements de diagnostic et sauvegardés de manière permanente par le Diagnostic Management (DM) dans une mémoire non volatile ([SWS_DM_02156]).

L'interface définit le rôle de fournisseur côté application : une application adaptative implémente la méthode purement virtuelle Read afin de transmettre les valeurs requises au Diagnostic Manager lors des requêtes de diagnostic correspondantes ([SWS_DM_02156]). Au moins trois composants système participent à l'interaction : l'implémentation d'interface spécifique à l'application, le Diagnostic Manager en tant qu'intermédiaire pour les requêtes de diagnostic entrantes ([SWS_DM_02152]) ainsi que la mémoire non volatile dans laquelle le DM persiste les données récupérées pour le contexte de diagnostic ([SWS_DM_02156]).

Diagramme de contexte : partenaires d'interaction de l'interface de fourniture d'enregistrements de données. Sources : [SWS_DM_02152], [SWS_DM_02156], AUTOSAR_AP_SWS_Diagnostics p. 68

Cycle de vie

L'instanciation s'effectue via le constructeur en spécifiant un ara::core::InstanceSpecifier et le mode de concurrence ara::diag::ConcurrencyType ([SWS_DM_02158]). Le paramètre concurrencyType détermine si l'implémentation fonctionne de manière sûre au niveau des threads (kConcurrent) ou non sûre au niveau des threads (kNotConcurrent) ([SWS_DM_02158]). La classe possède une liaison stricte à son identité : le constructeur de copie et l'opérateur d'assignation par copie sont supprimés ([SWS_DM_02147], [SWS_DM_02148]). De même, le constructeur de déplacement et l'opérateur d'assignation par déplacement sont supprimés ([SWS_DM_02149], [SWS_DM_02150]). Une instance est donc liée à son emplacement et ne peut pas être transférée.

Après une construction réussie, l'instance reste d'abord dans l'état inactif (NotOffered). L'appel de Offer() active le transfert des requêtes par le Diagnostic Management, ce qui fait passer l'instance à l'état Offered ([SWS_DM_02152]). Un nouvel appel de Offer() dans l'état Offered entraîne une erreur ([SWS_DM_02152]). La méthode StopOffer() permet de désactiver à nouveau le transfert et l'objet retourne à l'état NotOffered ([SWS_DM_02153]).

La destruction s'effectue via le destructeur virtuel ([SWS_DM_02151]). Alors que le constructeur est déclaré comme sûr au niveau des threads ([SWS_DM_02158]), le destructeur est expressément non sûr au niveau des threads ([SWS_DM_02151]). Interprétation : la fin de l'offre de service via StopOffer() devrait impérativement être terminée avant l'appel du destructeur afin d'empêcher les accès en lecture parallèles pendant la destruction de l'objet.

Diagramme d'états : cycle de vie et états de mise à disposition de l'instance d'interface. Sources : [SWS_DM_02151], [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02158]

Parcours d'utilisation

Le déroulement typique de la mise à disposition et du traitement des requêtes de diagnostic se présente comme suit :

  1. Instanciation : La classe fournisseur dérivée est créée en lui transmettant le ara::core::InstanceSpecifier ainsi que le concurrencyType souhaité ([SWS_DM_02158]).
  2. Annoncer la mise à disposition : L'application appelle Offer(). Ce n'est qu'après un retour réussi que les requêtes de diagnostic entrantes sont transmises par le DM à l'instance ([SWS_DM_02152]).
  3. Interroger l'enregistrement de données (Read) : si le Diagnostic Management demande l'élément de données, il appelle la méthode Read(metaInfo, cancellationHandler) ([SWS_DM_02156]) :
    • La requête fournit des informations de contexte via metaInfo ([SWS_DM_02156]).
    • Via cancellationHandler.IsCanceled() ou l'enregistrement d'une fonction de notification au moyen de cancellationHandler.SetNotifier(), l'application peut gérer une interruption prématurée de la conversation ([SWS_DM_02156]).
    • La méthode retourne un ara::core::Future avec la structure ReadOutput ([SWS_DM_02154], [SWS_DM_02156]). Si les données ne sont pas disponibles au moment de la consultation, l'implémentation doit toujours renvoyer une valeur et remplir les données avec un motif de remplissage (p. ex. 0xFF) ([SWS_DM_02156]).
  4. Retirer l'offre de service : avant l'arrêt ou en cas d'états de maintenance, l'application appelle StopOffer() pour interrompre le transfert des requêtes ([SWS_DM_02153]).

Diagramme de séquence : mise à disposition, consultation et arrêt du service de diagnostic. Sources : [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02156]

Scénarios d'erreur

Les conditions d'erreur et les violations sont associées aux phases respectives :

  • Violations lors de la construction : des liaisons de modèle non valides entraînent des messages d'erreur définis ([SWS_DM_02158]) :
    • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne référence aucun PortPrototype ([SWS_DM_02158]).
    • PortInterfaceMappingViolation : un port typé par DiagnosticExtendedDataRecordInterface n'est pas référencé par un DiagnosticDataPortMapping ([SWS_DM_02158]).
    • ProcessMappingViolation : aucun processus modélisé correspondant n'existe pour le processus d'exécution ([SWS_DM_02158]).
    • InstanceSpecifierAlreadyInUseViolation : l'identifiant est déjà utilisé par une autre instance dans le processus ([SWS_DM_02158]).
  • Erreur lors de l'enregistrement du service : un nouvel appel de Offer() sur une instance déjà proposée échoue avec le code d'erreur DiagOfferErrc::kAlreadyOffered ([SWS_DM_02152]).
  • Erreur pendant l'interrogation des données : si l'opération de lecture ne peut pas être effectuée correctement, le ara::core::Future renvoie un code négatif de diagnostic (DiagUdsNrcErrc) ou un code d'erreur spécifique à l'application (ApApplicationError) ([SWS_DM_02156]). Si seules les données brutes manquent, aucune erreur ne doit être signalée ; le jeu de données doit plutôt être rempli avec la valeur de remplacement (p. ex. 0xFF) ([SWS_DM_02156]).

  <h4>Contexte</h4>
  <p>L'interface <code>&lt;ExtendedDataRecord-Namespace&gt;::&lt;ExtendedDataRecordElementInterface&gt;</code> sert, dans l'AUTOSAR Adaptive Platform au sein du cluster fonctionnel <code>diag</code>, à la fourniture de données pour ce qu'on appelle les Extended Data Records (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=68">AUTOSAR_AP_SWS_Diagnostics p. 68</a>). Ces enregistrements de données sont collectés lors d'événements de diagnostic et sauvegardés de manière permanente par le Diagnostic Management (DM) dans une mémoire non volatile (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</p>
  <p>L'interface définit le rôle de fournisseur côté application : une application adaptative implémente la méthode purement virtuelle <code>Read</code> afin de transmettre les valeurs requises au Diagnostic Manager lors des requêtes de diagnostic correspondantes (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>). Au moins trois composants système participent à l'interaction : l'implémentation d'interface spécifique à l'application, le Diagnostic Manager en tant qu'intermédiaire pour les requêtes de diagnostic entrantes (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>) ainsi que la mémoire non volatile dans laquelle le DM persiste les données récupérées pour le contexte de diagnostic (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</p>

  <h4>Cycle de vie</h4>
  <p>L'instanciation s'effectue via le constructeur en spécifiant un <code>ara::core::InstanceSpecifier</code> et le mode de concurrence <code>ara::diag::ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>). Le paramètre <code>concurrencyType</code> détermine si l'implémentation fonctionne de manière sûre au niveau des threads (<code>kConcurrent</code>) ou non sûre au niveau des threads (<code>kNotConcurrent</code>) (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>). La classe possède une liaison stricte à son identité : le constructeur de copie et l'opérateur d'assignation par copie sont supprimés (<a class="spec-record-ref" data-req="SWS_DM_02147" href="../spec/record.html?id=SWS_DM_02147">[SWS_DM_02147]</a>, <a class="spec-record-ref" data-req="SWS_DM_02148" href="../spec/record.html?id=SWS_DM_02148">[SWS_DM_02148]</a>). De même, le constructeur de déplacement et l'opérateur d'assignation par déplacement sont supprimés (<a class="spec-record-ref" data-req="SWS_DM_02149" href="../spec/record.html?id=SWS_DM_02149">[SWS_DM_02149]</a>, <a class="spec-record-ref" data-req="SWS_DM_02150" href="../spec/record.html?id=SWS_DM_02150">[SWS_DM_02150]</a>). Une instance est donc liée à son emplacement et ne peut pas être transférée.</p>
  <p>Après une construction réussie, l'instance reste d'abord dans l'état inactif (<em>NotOffered</em>). L'appel de <code>Offer()</code> active le transfert des requêtes par le Diagnostic Management, ce qui fait passer l'instance à l'état <em>Offered</em> (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>). Un nouvel appel de <code>Offer()</code> dans l'état <em>Offered</em> entraîne une erreur (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>). La méthode <code>StopOffer()</code> permet de désactiver à nouveau le transfert et l'objet retourne à l'état <em>NotOffered</em> (<a class="spec-record-ref" data-req="SWS_DM_02153" href="../spec/record.html?id=SWS_DM_02153">[SWS_DM_02153]</a>).</p>
  <p>La destruction s'effectue via le destructeur virtuel (<a class="spec-record-ref" data-req="SWS_DM_02151" href="../spec/record.html?id=SWS_DM_02151">[SWS_DM_02151]</a>). Alors que le constructeur est déclaré comme sûr au niveau des threads (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>), le destructeur est expressément non sûr au niveau des threads (<a class="spec-record-ref" data-req="SWS_DM_02151" href="../spec/record.html?id=SWS_DM_02151">[SWS_DM_02151]</a>). Interprétation : la fin de l'offre de service via <code>StopOffer()</code> devrait impérativement être terminée avant l'appel du destructeur afin d'empêcher les accès en lecture parallèles pendant la destruction de l'objet.</p>

  <h4>Parcours d'utilisation</h4>
  <p>Le déroulement typique de la mise à disposition et du traitement des requêtes de diagnostic se présente comme suit :</p>
  <ol>
    <li><strong>Instanciation :</strong> La classe fournisseur dérivée est créée en lui transmettant le <code>ara::core::InstanceSpecifier</code> ainsi que le <code>concurrencyType</code> souhaité (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
    <li><strong>Annoncer la mise à disposition :</strong> L'application appelle <code>Offer()</code>. Ce n'est qu'après un retour réussi que les requêtes de diagnostic entrantes sont transmises par le DM à l'instance (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>).</li>
    <li><strong>Interroger l'enregistrement de données (Read) :</strong> si le Diagnostic Management demande l'élément de données, il appelle la méthode <code>Read(metaInfo, cancellationHandler)</code> (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>) :
      <ul>
        <li>La requête fournit des informations de contexte via <code>metaInfo</code> (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
        <li>Via <code>cancellationHandler.IsCanceled()</code> ou l'enregistrement d'une fonction de notification au moyen de <code>cancellationHandler.SetNotifier()</code>, l'application peut gérer une interruption prématurée de la conversation (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
        <li>La méthode retourne un <code>ara::core::Future</code> avec la structure <code>ReadOutput</code> (<a class="spec-record-ref" data-req="SWS_DM_02154" href="../spec/record.html?id=SWS_DM_02154">[SWS_DM_02154]</a>, <a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>). Si les données ne sont pas disponibles au moment de la consultation, l'implémentation doit toujours renvoyer une valeur et remplir les données avec un motif de remplissage (p. ex. <code>0xFF</code>) (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
      </ul>
    </li>
    <li><strong>Retirer l'offre de service :</strong> avant l'arrêt ou en cas d'états de maintenance, l'application appelle <code>StopOffer()</code> pour interrompre le transfert des requêtes (<a class="spec-record-ref" data-req="SWS_DM_02153" href="../spec/record.html?id=SWS_DM_02153">[SWS_DM_02153]</a>).</li>
  </ol>

  <h4>Scénarios d'erreur</h4>
  <p>Les conditions d'erreur et les violations sont associées aux phases respectives :</p>
  <ul>
    <li><strong>Violations lors de la construction :</strong> des liaisons de modèle non valides entraînent des messages d'erreur définis (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>) :
      <ul>
        <li><code>InstanceSpecifierMappingIntegrityViolation</code> : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne référence aucun <code>PortPrototype</code> (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
        <li><code>PortInterfaceMappingViolation</code> : un port typé par <code>DiagnosticExtendedDataRecordInterface</code> n'est pas référencé par un <code>DiagnosticDataPortMapping</code> (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
        <li><code>ProcessMappingViolation</code> : aucun processus modélisé correspondant n'existe pour le processus d'exécution (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
        <li><code>InstanceSpecifierAlreadyInUseViolation</code> : l'identifiant est déjà utilisé par une autre instance dans le processus (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
      </ul>
    </li>
    <li><strong>Erreur lors de l'enregistrement du service :</strong> un nouvel appel de <code>Offer()</code> sur une instance déjà proposée échoue avec le code d'erreur <code>DiagOfferErrc::kAlreadyOffered</code> (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>).</li>
    <li><strong>Erreur pendant l'interrogation des données :</strong> si l'opération de lecture ne peut pas être effectuée correctement, le <code>ara::core::Future</code> renvoie un code négatif de diagnostic (<code>DiagUdsNrcErrc</code>) ou un code d'erreur spécifique à l'application (<code>ApApplicationError</code>) (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>). Si seules les données brutes manquent, aucune erreur ne doit être signalée ; le jeu de données doit plutôt être rempli avec la valeur de remplacement (p. ex. <code>0xFF</code>) (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
  </ul>
