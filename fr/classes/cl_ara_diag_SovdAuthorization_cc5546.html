But d'utilisation

SovdAuthorization implémente l'autorisation SOVD au niveau de l'application. GetAuthorizationUrl() et GetTokenUrl() fournissent respectivement l'URL pour l'autorisation et la demande de jeton ; le DM répond à cela avec HTTP 307 et un en-tête Location avec cette URL. [SWS_DM_01485] [SWS_DM_01484] [SWS_DM_01472] [SWS_DM_01471] ValidateAuthorization() valide le jeton de l'en-tête d'autorisation HTTP et marque les rôles autorisés dans le ClientAuthentication passé. [SWS_DM_01483] [SWS_DM_01470]

Génération et cycle de vie

Le constructeur lie un PortPrototype au DiagnosticSovdAuthorizationInterface et accepte le ConcurrencyType. [SWS_DM_01489] Offer() active le renvoi, StopOffer() le désactive à nouveau. L'offre peut fournir kAlreadyOffered ou kConfigurationMismatch. [SWS_DM_01487] [SWS_DM_01486] Le destructeur est protégé contre les exceptions. [SWS_DM_01488]

Restrictions & traitement des erreurs

Après avoir fourni la Future, l’application ne doit plus utiliser l’objet ClientAuthentication référencé. [SWS_DM_01483] Une valeur de retour réussie permet au DM de considérer des rôles comme authentifiés jusqu’à validUntil pour le même token. [SWS_DM_01469] La validation peut signaler kInvalidAccessToken ou kTemporarilyNotAvailable. [SWS_DM_01483] Les opérations URL et de validation dépendent de ConcurrencyType ; Offer et StopOffer ne sont pas thread-safe. [SWS_DM_01470] Avec le même token jusqu’à validUntil et la même identité renvoyée, il peut traiter le client comme identique. Contexte d’accès SOVD

L’autorisation SOVD utilise des tokens OAuth dans l’en-tête de requête. Pour une telle demande, le Diagnostic Manager utilise SovdAuthorization afin de demander à l’application le rôle d’autorisation encodé ; il décide sur la base de ce rôle de l’autorisation pour l’opération SOVD demandée. virtual ara::core::Future< ValidateAuthorizationOutput > Validate Authorization (ara::core::StringView token, const MetaInfo &metaInfo, ClientAuthentication &clientAuthentication) noexcept=0;

This function validates the authorization token sent by the SOVD client. The application shall validate the authorization token according to the authorization protocol used in the system and then according to the outcome set the respective roles as authorized in the clientAuthentication that is passed as parameter. If OAuth 2.0 is used, this would implement the validation that is supposed to happen in the Resource Server.

La méthode virtuelle ValidateAuthorization valide le jeton (token) envoyé par un client SOVD dans l'en-tête HTTP Authorization, conformément au protocole d'autorisation utilisé dans le système ; dans le cas d'OAuth 2.0, cela correspond à la vérification par le Resource Server. En fonction du résultat, l'application marque comme autorisés les rôles correspondants dans l'objet transmis via le paramètre clientAuthentication [SWS_DM_01483]. La metaInfo du port de diagnostic est également transmise. Le ara::core::Future<ValidateAuthorizationOutput> renvoyé fournit le résultat de validation en cas de succès, ou une erreur dans le cas contraire.

Gestion des erreurs & concurrence

Si le jeton d'accès n'est pas valide, DiagSovdErrc::kInvalidAccessToken est renvoyé ; S'il ne peut pas être vérifié actuellement (par exemple parce qu'une vérification en ligne est nécessaire mais que le serveur d'authentification n'est pas accessible), DiagSovdErrc::kTemporarilyNotAvailable est livré. Une fois le futur réalisé, clientAuthentication ne pourra plus être utilisé par l'application. Le fait que l'implémentation doit être thread-safe ou non est déterminé par le ConcurrencyType passé dans le constructeur ; la méthode est sécurisée pour les exceptions.
