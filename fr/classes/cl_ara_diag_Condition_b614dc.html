Contexte

La classe ara::diag::Condition fournit sur l'AUTOSAR Adaptive Platform la représentation d'un DiagnosticConditionInterface modélisé [SWS_DM_00712]. Dans les systèmes de diagnostic automobile, certaines fonctionnalités de diagnostic ne doivent être exécutées conformément à l'ISO 14229-1 que si le véhicule complet ou des sous-systèmes se trouvent dans un état défini – par exemple lorsque le véhicule est à l'arrêt (AUTOSAR_AP_SWS_Diagnostics p. 141 §7.3.2.5.5 « Condition checks »). Le serveur de diagnostic effectue les contrôles correspondants avant le traitement des requêtes de diagnostic [SWS_DM_00111].

Les applications adaptatives utilisent Condition comme interface pour signaler ou lire l'état de conditions environnementales ou système pertinentes auprès du Diagnostic Management (DM). Dans le modèle, le prototype de port associé est assigné soit via un DiagnosticEnableConditionPortMapping pour les conditions d'activation générales, soit via un DiagnosticClearConditionPortMapping pour les conditions d'activation de l'effacement de données de diagnostic [SWS_DM_00712]. Les partenaires d'interaction essentiels sont l'application surveillant l'état, l'objet Condition local et le serveur de diagnostic central du DM.

Cycle de vie

L'instanciation de Condition s'effectue explicitement par la transmission d'un ara::core::InstanceSpecifier qui référence un prototype de port du DiagnosticConditionInterface [SWS_DM_00712]. Le constructeur est déclaré comme noexcept, garantit la sécurité vis-à-vis des exceptions (exception safe) et est sûr au niveau des threads (thread-safe) [SWS_DM_00712].

En ce qui concerne la relation de possession, Condition est conçue comme une instance liée de manière unique au port : le constructeur de copie, le constructeur de déplacement ainsi que tous les opérateurs d'affectation sont explicitement supprimés (= delete) [SWS_DM_01625], [SWS_DM_01626], [SWS_DM_01623], [SWS_DM_01624]. Une instance reste ainsi fixée à son adresse mémoire d'origine et ne peut être ni déplacée ni copiée.

En cours de fonctionnement, les méthodes d'état SetCondition() [SWS_DM_00715] et GetCondition() [SWS_DM_00714] ainsi que le destructeur ~Condition() [SWS_DM_00713] sont spécifiés comme non sûrs pour les threads. Les appels simultanés de la même instance sur plusieurs threads doivent donc être synchronisés par l'application. Lors de la destruction de l'instance par le destructeur, la liaison du InstanceSpecifier dans le contexte du processus est libérée [SWS_DM_00713].

Parcours d'utilisation

Le déroulement normal comprend la création au démarrage du composant, la définition de l'état lors de changements de statut ainsi que la consultation facultative du statut :

  • Initialisation : L'application crée l'instance de Condition en spécifiant le InstanceSpecifier approprié [SWS_DM_00712].
  • Définir l'état : Si l'application détecte un changement de la condition pertinente (par exemple arrêt atteint ou quitté), elle met à jour le statut via SetCondition(condition) [SWS_DM_00715]. L'appel renvoie un ara::core::Result<void>.
  • Interroger l'état : En cas de besoin, le statut actuel peut être interrogé via GetCondition() [SWS_DM_00714]. Étant donné que le retour s'effectue via un ara::core::Future<ConditionType>, la vérification du statut devrait être synchronisée en interne de manière asynchrone avec le Diagnostic Management.
  • Terminaison : Avant la fin de l'application ou du port, l'objet est détruit via le destructeur [SWS_DM_00713].

Diagramme de séquence : déroulement typique de la mise à jour et de l'interrogation de l'état via ara::diag::Condition. Sources : [SWS_DM_00712], [SWS_DM_00715], [SWS_DM_00714], [SWS_DM_00713]

Scénarios d'erreur

Les types d'erreurs se divisent en violations statiques de configuration lors de l'instanciation et en erreurs d'exécution dynamiques :

  • Erreurs de modélisation et d'instanciation : Si la résolution du InstanceSpecifier échoue, le framework signale des violations définies [SWS_DM_00712] :
    • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu dans le modèle de l'exécutable ou ne référence aucun élément de port.
    • PortInterfaceMappingViolation : le prototype de port est bien typé comme DiagnosticConditionInterface, mais ne possède ni un DiagnosticEnableConditionPortMapping ni un DiagnosticClearConditionPortMapping.
    • ProcessMappingViolation : aucun processus associé n'existe dans le modèle pour le processus d'exécution actuel.
    • InstanceSpecifierAlreadyInUseViolation : l'identifiant est déjà utilisé par une autre instance dans le même processus.
  • Défaillance de fonctions de diagnostic : L'appel de GetCondition() renvoie DiagErrc::kServiceNotAvailable en cas d'erreur [SWS_DM_00714], si des services d'arrière-plan essentiels du Diagnostic Management ne sont pas accessibles. Pour SetCondition(), aucun code d'erreur standardisé n'est spécifié [SWS_DM_00715].
  • Impacts sur les services UDS : Si une condition n'est pas remplie ou si la formule de condition s'évalue à FALSE, le Diagnostic Server n'exécute pas le service demandé et envoie le code NRC configuré [SWS_DM_00111], [SWS_DM_00289].

<h4>Contexte</h4>
<p>La classe <code>ara::diag::Condition</code> fournit sur l'AUTOSAR Adaptive Platform la représentation d'un <code>DiagnosticConditionInterface</code> modélisé <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. Dans les systèmes de diagnostic automobile, certaines fonctionnalités de diagnostic ne doivent être exécutées conformément à l'ISO 14229-1 que si le véhicule complet ou des sous-systèmes se trouvent dans un état défini – par exemple lorsque le véhicule est à l'arrêt (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=141">AUTOSAR_AP_SWS_Diagnostics p. 141 §7.3.2.5.5 « Condition checks »</a>). Le serveur de diagnostic effectue les contrôles correspondants avant le traitement des requêtes de diagnostic <a class="spec-record-ref" data-req="SWS_DM_00111" href="../spec/record.html?id=SWS_DM_00111">[SWS_DM_00111]</a>.</p>
<p>Les applications adaptatives utilisent <code>Condition</code> comme interface pour signaler ou lire l'état de conditions environnementales ou système pertinentes auprès du Diagnostic Management (DM). Dans le modèle, le prototype de port associé est assigné soit via un <code>DiagnosticEnableConditionPortMapping</code> pour les conditions d'activation générales, soit via un <code>DiagnosticClearConditionPortMapping</code> pour les conditions d'activation de l'effacement de données de diagnostic <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. Les partenaires d'interaction essentiels sont l'application surveillant l'état, l'objet <code>Condition</code> local et le serveur de diagnostic central du DM.</p>

<h4>Cycle de vie</h4>
<p>L'instanciation de <code>Condition</code> s'effectue explicitement par la transmission d'un <code>ara::core::InstanceSpecifier</code> qui référence un prototype de port du <code>DiagnosticConditionInterface</code> <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. Le constructeur est déclaré comme <code>noexcept</code>, garantit la sécurité vis-à-vis des exceptions (exception safe) et est sûr au niveau des threads (thread-safe) <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>.</p>
<p>En ce qui concerne la relation de possession, <code>Condition</code> est conçue comme une instance liée de manière unique au port : le constructeur de copie, le constructeur de déplacement ainsi que tous les opérateurs d'affectation sont explicitement supprimés (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01625" href="../spec/record.html?id=SWS_DM_01625">[SWS_DM_01625]</a>, <a class="spec-record-ref" data-req="SWS_DM_01626" href="../spec/record.html?id=SWS_DM_01626">[SWS_DM_01626]</a>, <a class="spec-record-ref" data-req="SWS_DM_01623" href="../spec/record.html?id=SWS_DM_01623">[SWS_DM_01623]</a>, <a class="spec-record-ref" data-req="SWS_DM_01624" href="../spec/record.html?id=SWS_DM_01624">[SWS_DM_01624]</a>. Une instance reste ainsi fixée à son adresse mémoire d'origine et ne peut être ni déplacée ni copiée.</p>
<p>En cours de fonctionnement, les méthodes d'état <code>SetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a> et <code>GetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a> ainsi que le destructeur <code>~Condition()</code> <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a> sont spécifiés comme non sûrs pour les threads. Les appels simultanés de la même instance sur plusieurs threads doivent donc être synchronisés par l'application. Lors de la destruction de l'instance par le destructeur, la liaison du <code>InstanceSpecifier</code> dans le contexte du processus est libérée <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a>.</p>

<h4>Parcours d'utilisation</h4>
<p>Le déroulement normal comprend la création au démarrage du composant, la définition de l'état lors de changements de statut ainsi que la consultation facultative du statut :</p>
<ul>
<li><strong>Initialisation :</strong> L'application crée l'instance de <code>Condition</code> en spécifiant le <code>InstanceSpecifier</code> approprié <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>.</li>
<li><strong>Définir l'état :</strong> Si l'application détecte un changement de la condition pertinente (par exemple arrêt atteint ou quitté), elle met à jour le statut via <code>SetCondition(condition)</code> <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a>. L'appel renvoie un <code>ara::core::Result&lt;void&gt;</code>.</li>
<li><strong>Interroger l'état :</strong> En cas de besoin, le statut actuel peut être interrogé via <code>GetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a>. Étant donné que le retour s'effectue via un <code>ara::core::Future&lt;ConditionType&gt;</code>, la vérification du statut devrait être synchronisée en interne de manière asynchrone avec le Diagnostic Management.</li>
<li><strong>Terminaison :</strong> Avant la fin de l'application ou du port, l'objet est détruit via le destructeur <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a>.</li>
</ul>

<h4>Scénarios d'erreur</h4>
<p>Les types d'erreurs se divisent en violations statiques de configuration lors de l'instanciation et en erreurs d'exécution dynamiques :</p>
<ul>
<li><strong>Erreurs de modélisation et d'instanciation :</strong> Si la résolution du <code>InstanceSpecifier</code> échoue, le framework signale des violations définies <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a> :
  <ul>
  <li><code>InstanceSpecifierMappingIntegrityViolation</code> : l'identifiant ne peut pas être résolu dans le modèle de l'exécutable ou ne référence aucun élément de port.</li>
  <li><code>PortInterfaceMappingViolation</code> : le prototype de port est bien typé comme <code>DiagnosticConditionInterface</code>, mais ne possède ni un <code>DiagnosticEnableConditionPortMapping</code> ni un <code>DiagnosticClearConditionPortMapping</code>.</li>
  <li><code>ProcessMappingViolation</code> : aucun processus associé n'existe dans le modèle pour le processus d'exécution actuel.</li>
  <li><code>InstanceSpecifierAlreadyInUseViolation</code> : l'identifiant est déjà utilisé par une autre instance dans le même processus.</li>
  </ul>
</li>
<li><strong>Défaillance de fonctions de diagnostic :</strong> L'appel de <code>GetCondition()</code> renvoie <code>DiagErrc::kServiceNotAvailable</code> en cas d'erreur <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a>, si des services d'arrière-plan essentiels du Diagnostic Management ne sont pas accessibles. Pour <code>SetCondition()</code>, aucun code d'erreur standardisé n'est spécifié <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a>.</li>
<li><strong>Impacts sur les services UDS :</strong> Si une condition n'est pas remplie ou si la formule de condition s'évalue à <code>FALSE</code>, le Diagnostic Server n'exécute pas le service demandé et envoie le code NRC configuré <a class="spec-record-ref" data-req="SWS_DM_00111" href="../spec/record.html?id=SWS_DM_00111">[SWS_DM_00111]</a>, <a class="spec-record-ref" data-req="SWS_DM_00289" href="../spec/record.html?id=SWS_DM_00289">[SWS_DM_00289]</a>.</li>
</ul>
