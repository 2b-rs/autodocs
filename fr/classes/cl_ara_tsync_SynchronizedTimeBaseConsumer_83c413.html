Permet aux applications d'interroger de manière sûre pour les threads des valeurs temporelles synchronisées et d'enregistrer des notificateurs d'état.

La classe ara::tsync::SynchronizedTimeBaseConsumer permet aux applications temporelles d'accéder à une base de temps synchronisée référencée par un ara::core::InstanceSpecifier ([SWS_TS_01001]). Au moyen de méthodes sûres pour les threads, les applications peuvent interroger des instantanés (snapshots) actuels de valeurs temporelles et d'indicateurs d'état (status flags) ainsi que l'écart de cadence de l'horloge ([SWS_TS_01009]). De plus, des notificateurs peuvent être enregistrés pour les changements d'état, les sauts temporels, les données de validation et les mesures de précision, au plus un enregistrement étant actif par type d'événement. Les opérations de copie sont interdites, de sorte que les instances peuvent uniquement être déplacées ou libérées via leur destructeur.

Contexte

Pour les applications temporelles sur l'Adaptive Platform, la classe ara::tsync::SynchronizedTimeBaseConsumer constitue l'interface avec une base de temps synchronisée, identifiée par un ara::core::InstanceSpecifier ([SWS_TS_01001]). Sa tâche principale consiste à mettre à disposition des applications l'instant d'interrogation actuel, l'écart de cadence de l'horloge ([SWS_TS_01008]) ainsi que des indicateurs d'état cohérents et les données utilisateur reçues ([SWS_TS_01009]). Les principaux partenaires d'interaction sont le logiciel applicatif appelant (Time Consumer Application), l'instance consommatrice elle-même ainsi que le sous-système Tsync, qui acquiert les données de synchronisation et déclenche les événements de notification ([SWS_TS_01016], [SWS_TS_01018]).

Cycle de vie

L'instanciation s'effectue via le constructeur explicite en indiquant un ara::core::InstanceSpecifier ([SWS_TS_01001]). Ce constructeur est classé comme sûr pour les threads et sûr du point de vue des exceptions. Pour la gestion des ressources, la classe implémente une sémantique de déplacement stricte : le constructeur de déplacement ([SWS_TS_01003]) et l'opérateur d'affectation par déplacement ([SWS_TS_01004]) permettent le transfert de propriété, tandis que le constructeur de copie ([SWS_TS_01005]) et l'opérateur d'affectation par copie ([SWS_TS_01006]) sont explicitement supprimés (=delete). Cela empêche les duplications accidentelles de l'accès à la même ressource de base de temps.

Le destructeur libère l'instance ([SWS_TS_01002]). Concernant la concurrence, une distinction claire s'applique : alors que le constructeur ([SWS_TS_01001]) ainsi que les méthodes d'interrogation GetRateDeviation ([SWS_TS_01008]) et GetTimeWithStatus ([SWS_TS_01009]) sont exécutés de façon sûre pour les threads, toutes les fonctions d'enregistrement et de désinscription ainsi que les opérations de déplacement et le destructeur sont spécifiés comme non sûrs pour les threads (non_threadsafe).

Parcours d'utilisation

Un déroulement d'utilisation standard comprend les phases d'initialisation, d'enregistrement des notificateurs pertinents, d'interrogations cycliques ou événementielles, ainsi que le nettoyage final :

  • Initialisation : l'application crée l'objet avec la spécification d'instance de port appropriée ([SWS_TS_01001]).
  • Enregistrement de notificateurs : l'application enregistre des fonctions de rappel ou des objets notificateurs pour des événements spécifiques :
    • Changements généraux d'indicateurs d'état via RegisterStatusChangeNotifier ([SWS_TS_01010]),
    • Changements de l'état de synchronisation via RegisterSynchronizationStateChangeNotifier ([SWS_TS_01012]),
    • Survenue d'un saut temporel via RegisterTimeLeapNotifier ([SWS_TS_01014]),
    • Réception de blocs de données de validation via RegisterTimeValidationNotification ([SWS_TS_01016]),
    • Disponibilité de mesures de précision temporelle via RegisterTimePrecisionMeasurementNotifier ([SWS_TS_01018]).
    Au maximum un enregistrement peut être actif par type de notificateur ; chaque nouvel enregistrement écrase le précédent ([SWS_TS_01010], [SWS_TS_01018]).
  • Interrogation en fonctionnement : via GetTimeWithStatus(), l'application récupère un instantané cohérent (SynchronizedTimeBaseStatus) avec les indicateurs d'état, la configuration d'horloge ainsi que les valeurs temporelles locales et synchronisées ([SWS_TS_01009]). L'écart de cadence actuel de l'horloge est déterminé au moyen de GetRateDeviation() ([SWS_TS_01008]).
  • Nettoyage : avant la suppression du consommateur, les notificateurs sont au besoin désinscrits via les appels correspondants tels que UnregisterStatusChangeNotifier ([SWS_TS_01011]), UnregisterSynchronizationStateChangeNotifier ([SWS_TS_01013]), UnregisterTimeLeapNotifier ([SWS_TS_01015]), UnregisterTimeValidationNotification ([SWS_TS_01017]) ou UnregisterTimePrecisionMeasurementNotifier ([SWS_TS_01019]), avant que l'objet ne soit détruit ([SWS_TS_01002]).

Scénarios d'erreur

Toutes les méthodes d'interface de la classe sont déclarées avec noexcept et spécifiées comme sûres du point de vue des exceptions (exception safe). Les erreurs ne sont donc pas signalées par des exceptions C++. Les conditions aux limites et violations de configuration suivantes doivent être prises en compte :

  • Erreurs de configuration du mappage de port : un PortPrototype référencé via un TimeSyncPortPrototypeToTimeBaseMapping doit impérativement être typé via un SynchronizedTimeBaseConsumerInterface ; dans le cas contraire, il s'agit d'une PortInterfaceMappingViolation ([SWS_TS_01001]).
  • Écrasement de callbacks existants : si une méthode d'enregistrement est appelée à nouveau, le nouveau notificateur écrase le rappel précédemment enregistré sans message d'erreur distinct ([SWS_TS_01010], [SWS_TS_01012], [SWS_TS_01014], [SWS_TS_01016], [SWS_TS_01018]).
  • Absence de mise en file d'attente (queuing) lors des mesures de précision : le sous-système Tsync n'effectue aucune mise en mémoire tampon intermédiaire (queuing) pour les données de mesure de la précision temporelle ([SWS_TS_01018]). Si le notificateur ne peut pas traiter les données à temps, les mesures suivantes seront vraisemblablement perdues si l'application ne prévoit pas sa propre mise en mémoire tampon dans le notificateur. Question Q-dd82872d44124973 (ouverte)
  • Risque de conditions de concurrence (data races) sur les méthodes de notificateur : les enregistrements et désinscriptions de notificateurs étant désignés comme non sûrs pour les threads, un appel concurrent depuis différents contextes d'exécution sans mécanismes de protection externes devrait conduire à des états incohérents (interprétation).
