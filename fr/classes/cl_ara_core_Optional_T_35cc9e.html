Contexte

La classe modèle ara::core::Optional<T&> fournit une spécialisation partielle de ara::core::Optional pour les références lvalue de type T&. Par le biais de l'alias de type défini value_type ([SWS_CORE_01151]), la spécialisation lie une référence optionnelle vers un objet existant. À la différence de la classe modèle primaire pour les types valeur, cette spécialisation permet de détenir de façon optionnelle une référence vers un objet externe sans devoir recourir à l'allocation dynamique de mémoire ni à des pointeurs C bruts dotés d'une sémantique de pointeur nul. Elle fait office, dans les architectures logicielles de l'AUTOSAR Adaptive Platform, d'enveloppe à sûreté de typage pour les interfaces où des valeurs de retour ou des paramètres peuvent faire référence de manière optionnelle à une instance déjà existante.

Cycle de vie

Le cycle de vie d'une instance de ara::core::Optional<T&> est caractérisé par deux états disjoints : l'état inoccupé (vide) et l'état occupé (référençant). L'objet peut par défaut être initialisé sans valeur assignée dans l'état inoccupé via le constructeur par défaut ([SWS_CORE_01152]) ou via le littéral nullopt_t ([SWS_CORE_01153]). Une transition directe vers l'état occupé s'effectue lors de la construction par transmission d'une valeur de référence via le modèle de constructeur ([SWS_CORE_01156]) ou par conversion à partir d'une autre instance compatible de Optional ([SWS_CORE_01157]). Les constructeurs de copie et de déplacement sont implémentés par défaut et déclarés comme noexcept ([SWS_CORE_01154], [SWS_CORE_01155]).

À l'exécution, une instance existante peut modifier son état de manière dynamique. Les méthodes emplace ([SWS_CORE_01164]) ainsi que les opérateurs d'affectation pour les types compatibles ([SWS_CORE_01162], [SWS_CORE_01163]) font passer l'objet à l'état occupé ou le relient à une nouvelle référence. Les affectations par copie et par déplacement sont également présentes sous forme d'implémentations standard ([SWS_CORE_01159], [SWS_CORE_01160]). La réinitialisation à l'état inoccupé s'effectue explicitement via reset() ([SWS_CORE_01165]) ou par affectation de nullopt ([SWS_CORE_01161]). De plus, swap ([SWS_CORE_01166]) permet d'échanger le contenu de deux instances. Le destructeur est spécifié comme noexcept=default ([SWS_CORE_01158]). Interprétation : comme il s'agit d'une spécialisation de référence, la classe ne gère probablement pas la durée de vie de l'objet cible ; l'objet cible devrait donc exister et être détruit indépendamment du conteneur.

Parcours d'utilisation

Un chemin d'utilisation typique comprend la création, la validation et l'accès conditionnel aux données de l'objet référencé :

  • Création et affectation : un composant crée l'objet soit initialement vide ([SWS_CORE_01152]), soit le lie directement à une instance ([SWS_CORE_01156]). Ultérieurement, la référence peut être redéfinie via emplace ([SWS_CORE_01164]) ou par affectation de valeur ([SWS_CORE_01162]).
  • Contrôle d'état : avant d'accéder à l'objet cible, l'appelant vérifie la présence d'une valeur. Pour cela, l'opérateur de conversion booléenne operator bool() ([SWS_CORE_01171]) ainsi que la méthode has_value() ([SWS_CORE_01172]) sont disponibles, tous deux étant spécifiés comme constexpr noexcept.
  • Déréférencement et accès : lorsque l'état est vérifié, il est possible d'accéder à la référence via operator* ([SWS_CORE_01169], [SWS_CORE_01170]) ou directement aux éléments de l'objet cible via l'opérateur flèche operator-> ([SWS_CORE_01167], [SWS_CORE_01168]). De plus, value() ([SWS_CORE_01173], [SWS_CORE_01174]) permet l'accès direct à T& ou const T&.
  • Valeur de repli : si une valeur de substitution est requise lorsqu'aucun objet n'est référencé, value_or ([SWS_CORE_01175]) peut être appelé pour retourner soit la valeur de la référence, soit une valeur de remplacement transmise.
  • Libération : si la référence n'est plus valide ou doit être réinitialisée, l'instance est ramenée à l'état inoccupé au moyen de reset() ([SWS_CORE_01165]).

Scénarios d'erreur

Les utilisations erronées proviennent principalement d'accès incorrects à un objet non initialisé ou vide (violation de précondition : If *this does not contain a value) :

  • Déclenchement de violations d'accès : l'appel non protégé de la méthode d'accès value() ([SWS_CORE_01173], [SWS_CORE_01174]) sur une instance inoccupée viole la précondition et conduit à une IsoStdBadOptionalAccessViolation. La spécification classe explicitement la méthode comme not exception safe.
  • Déréférencement sans valeur : pour les opérateurs operator* ([SWS_CORE_01169], [SWS_CORE_01170]) et operator-> ([SWS_CORE_01167], [SWS_CORE_01168]) également, la précondition stipule qu'une valeur doit être contenue. En cas de violation, une IsoStdBadOptionalAccessViolation est également documentée, bien que les opérateurs soient déclarés avec noexcept.

Pour éviter ces conditions d'erreur, l'appelant doit toujours effectuer une vérification avec has_value() ([SWS_CORE_01172]) avant le déréférencement ou recourir à l'alternative sûre value_or ([SWS_CORE_01175]).

Ce guide repose exclusivement sur la spécification AUTOSAR pour la release R25-11.
