classe ara::diag::TransmitCertificate

[SWS_DM_01961] Upstream: RS_Diag_04251

class TransmitCertificate {...};

Class to implement the subfunction TransmitCertificate (29 04) of UDS service Authentication as interface to application. This class implements a so called generic interface, where the application has means to handle one ore more certificateEvaluationId transferred certificates.

Contexte

La classe ara::diag::TransmitCertificate fournit l'interface de programmation pour la sous-fonction UDS TransmitCertificate (0x29 04) du service Authentication (0x29) AUTOSAR_AP_SWS_Diagnostics §8.26.1 « Class: TransmitCertificate ». Elle implémente une interface générique via laquelle une application Adaptive peut recevoir et évaluer un ou plusieurs certificats identifiés par un identifiant 16 bits (certificateEvaluationId).

Dans l'architecture système, ara::diag::TransmitCertificate fait office de liaison entre l'AUTOSAR Adaptive Diagnostic Manager (DM) ou la Diagnostic Server Instance et la logique applicative concrète. Un testeur de diagnostic externe envoie la demande d'authentification UDS au serveur, qui transmet la demande à l'application après activation [SWS_DM_01968], [SWS_DM_01251].

Diagramme de contexte : intégration de TransmitCertificate entre le testeur de diagnostic, le Diagnostic Manager et la logique applicative. Sources : [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01249].

Cycle de vie

L'instanciation s'effectue via le constructeur en spécifiant un [SWS_DM_01962] :

  • specifier : un ara::core::InstanceSpecifier qui référence un PortPrototype typé par un DiagnosticAuthenticationPortMapping [SWS_DM_01962].
  • concurrencyType : détermine si l'exécution ultérieure de Process est traitée comme thread-safe (kConcurrent) ou non thread-safe (kNotConcurrent) [SWS_DM_01962], [SWS_DM_01968].

Les opérations de copie et de déplacement sont totalement interdites : le constructeur de copie [SWS_DM_01964], le constructeur de déplacement [SWS_DM_01963], l'opérateur d'assignation par copie [SWS_DM_01966] et l'opérateur d'assignation par déplacement [SWS_DM_01965] sont déclarés comme supprimés (=delete). Une instance d'interface d'authentification existe donc en tant qu'objet lié de manière unique.

Après la construction, le cycle de vie se divise en deux phases de fonctionnement :

  1. Mise à disposition (Offered) : par l'appel de Offer(), le Diagnostic Manager est autorisé à transmettre les messages UDS entrants pour la sous-fonction à la méthode Process() [SWS_DM_01969].
  2. Retrait (Stopped) : l'appel de StopOffer() désenregistre à nouveau la transmission [SWS_DM_01970].

Le destructeur est virtuel et déclaré par défaut (noexcept = default) [SWS_DM_01967]. Alors que le constructeur est thread-safe, Offer() et StopOffer() sont spécifiés comme non thread-safe et ne doivent pas être appelés simultanément de manière non coordonnée [SWS_DM_01962], [SWS_DM_01969], [SWS_DM_01970].

Parcours d'utilisation

Le déroulement opérationnel régulier comprend l'enregistrement auprès du Diagnostic Manager, la réception asynchrone des données de certificat et la finalisation du traitement :

  1. Instanciation et mise à disposition : l'application instancie la classe dérivée et active l'acceptation via Offer() [SWS_DM_01962], [SWS_DM_01969].
  2. Empfang und Verarbeitung : Lors de la réception d'une requête UDS, le Diagnostic Server transmet les données via Process(certificateEvaluationId, certificateData, metaInfo, cancellationHandler) [SWS_DM_01968]. La méthode renvoie un ara::core::Future<void>, ce qui permet un traitement asynchrone. La sémantique concrète et l'évaluation du certificat incombent entièrement à l'application [SWS_DM_01968].
  3. Gestion de l'annulation : L'application peut vérifier via cancellationHandler.IsCanceled() si la conversation de diagnostic a été annulée, ou enregistrer via cancellationHandler.SetNotifier() un callback de notification pour les événements d'annulation [SWS_DM_01968].
  4. Réponse positive : Si l'exécution se termine avec succès sans code d'erreur, la Diagnostic Server Instance transmet une réponse UDS positive avec le paramètre de retour authenticationReturnParameter = 0x13 (CertificateVerified) au testeur [SWS_DM_01251].
  5. Nettoyage : Lors de la terminaison, la réception prend fin via StopOffer() [SWS_DM_01970].

Diagramme de séquence : déroulement type du transfert et du traitement de certificats. Sources : [SWS_DM_01969], [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01970].

Scénarios d'erreur

Des conditions d'erreur spécifiques sont définies aussi bien lors de l'initialisation que pendant le fonctionnement :

  • Erreurs de manifeste et de modélisation lors de la création : Le constructeur signale des violations lorsque le InstanceSpecifier ne peut pas être résolu (InstanceSpecifierMappingIntegrityViolation), que le PortPrototype référencé n'est pas typé par un DiagnosticTransmitCertificateInterface (PortInterfaceMappingViolation), qu'aucune affectation de processus n'existe (ProcessMappingViolation) ou que le InstanceSpecifier est déjà attribué dans le processus (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01962].
  • Enregistrement multiple : Un nouvel appel de Offer() alors que la mise à disposition est déjà active entraîne l'erreur DiagOfferErrc::kAlreadyOffered avec une sémantique de rollback [SWS_DM_01969].
  • Rejet in-process : Si la vérification du certificat échoue dans l'application ou si une erreur de traitement survient, Process() renvoie une erreur correspondante via le ara::core::Future. Dans ce cas, un Negative Response Code (NRC) UDS approprié selon l'ISO 14229-1 doit être utilisé via DiagUdsNrcErrc [SWS_DM_01968]. La Diagnostic Server Instance génère ensuite une réponse UDS négative (NRC) à destination du testeur externe [SWS_DM_01249].

Ce guide est basé sur la spécification AUTOSAR Adaptive Platform R25-11 pour le module Diagnostics.
