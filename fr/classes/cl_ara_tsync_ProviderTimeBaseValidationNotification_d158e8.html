Contexte

La classe ara::tsync::ProviderTimeBaseValidationNotification est une interface abstraite (interface de rappel) au sein du module AUTOSAR Adaptive tsync. Elle sert à notifier une application de validation de niveau supérieur (Validator Application) de la disponibilité de nouveaux blocs de données de mesure enregistrés pour une base de temps.

Dans un système global synchronisé dans le temps, trois composants clés interagissent typiquement :

  • Fournisseur tsync (base de temps) : le sous-système de synchronisation acquiert des données de protocole et de temporisation au moment de l'exécution. Dès qu'un nouveau bloc de mesure est disponible, le fournisseur appelle les méthodes de notification correspondantes.
  • ProviderTimeBaseValidationNotification : l'interface de rappel abstraite définit les contrats d'appel pour la transmission des données de mesure du maître et du répondeur ([SWS_TS_00421], [SWS_TS_00423]).
  • Application de validation : la logique spécifique à l'application implémente cette interface afin d'évaluer les blocs de mesure reçus, d'effectuer des contrôles de plausibilité et de surveiller la validité de la base de temps.

Diagramme de contexte : interaction entre le fournisseur tsync, l'interface de rappel et l'application de validation. Sources : [SWS_TS_00421], [SWS_TS_00423].

Cycle de vie

Comme ProviderTimeBaseValidationNotification constitue une classe de base purement abstraite comportant des fonctions membres virtuelles pures, elle ne peut pas être instanciée directement. Son cycle de vie se décompose selon les phases suivantes :

  • Création et propriété : l'application de validation dérive une classe observateur concrète de ProviderTimeBaseValidationNotification et l'instancie. La propriété (ownership) demeure auprès de l'application de validation.
  • Mise à disposition : interprétation : l'instance de rappel créée est enregistrée auprès de la base de temps à surveiller du fournisseur tsync afin que le fournisseur puisse conserver des références vers celle-ci et exécuter des appels de méthode.
  • États : l'interface elle-même ne possède aucune mémoire d'état interne. Après son enregistrement, l'objet reste en état d'attente de réception des données de mesure entrantes.
  • Destruction : la classe possède un destructeur virtuel par défaut ~ProviderTimeBaseValidationNotification() noexcept = default; ([SWS_TS_01301]). Cela garantit que les instances polymorphes sont correctement nettoyées lors de la libération via un pointeur vers l'interface. Avant la destruction de l'objet, il convient de s'assurer que le fournisseur tsync n'envoie plus aucune notification à cette instance.
  • Concurrence : conformément à la spécification, les méthodes de l'interface sont classées comme non_threadsafe ([SWS_TS_00421], [SWS_TS_00423]). L'application de validation ne doit donc pas présumer que des appels parallèles peuvent être traités de manière sûre vis-à-vis des threads sans mécanismes de synchronisation externes.

Parcours d'utilisation

Le chemin d'utilisation typique décrit la réception et la transmission de données de mesure temporelle pendant le fonctionnement actif de la base de temps :

  1. Implémentation du rappel : l'application redéfinit les deux méthodes d'interface SetMasterTimingData ([SWS_TS_00421]) et SetPdelayResponderData ([SWS_TS_00423]).
  2. Mise à disposition sur la base de temps : l'application transmet vraisemblablement une référence vers l'instance dérivée au sous-système tsync afin d'activer la surveillance.
  3. Réception de données de maître de temps : dès qu'un nouveau bloc de données de mesure est disponible pour le Time Master de la base de temps, le sous-système tsync appelle la méthode SetMasterTimingData ([SWS_TS_00421]). L'appelant transmet alors le paramètre measurementData de type const TimeMasterMeasurementType&, qui contient des données de validation détaillées du Time Master.
  4. Réception de données de répondeur pDelay : si des données de mesure enregistrées sont disponibles pour le répondeur pDelay de la base de temps, SetPdelayResponderData est appelée ([SWS_TS_00423]). Un bloc de données de type const PdelayResponderMeasurementType& est alors transmis pour évaluation.
  5. Évaluation et terminaison : l'application de validation vérifie la conformité des données de mesure obtenues et les écarts par rapport aux seuils. Lors de l'arrêt du système ou de la fin de la validation, l'instance est libérée via le destructeur virtuel ([SWS_TS_01301]).

Diagramme de séquence : mise à disposition de blocs de données de mesure via l'interface de notification. Sources : [SWS_TS_00421], [SWS_TS_00423], [SWS_TS_01301].

Scénarios d'erreur

Concernant la gestion des erreurs et les conditions aux limites, les exigences suivantes s'appliquent à ProviderTimeBaseValidationNotification :

  • Sécurité vis-à-vis des exceptions : l'ensemble des fonctions membres – SetMasterTimingData ([SWS_TS_00421]), SetPdelayResponderData ([SWS_TS_00423]) ainsi que le destructeur ([SWS_TS_01301]) – sont déclarées comme noexcept et spécifiées comme exception safe. Les implémentations de l'application de validation ne doivent laisser échapper aucune exception C++ des rappels, étant donné qu'un état d'exception dans une fonction noexcept entraîne immédiatement l'interruption du programme via std::terminate.
  • Valeurs de retour et signalement des erreurs : les méthodes possèdent le type de retour void. Un retour direct concernant le succès ou l'échec vers le fournisseur tsync n'est pas prévu via cette interface.
  • Validité des références : les structures de données de mesure transmises le sont sous forme de références constantes. L'application appelée doit partir du principe que la validité des données peut être limitée à la durée de l'appel de méthode, raison pour laquelle les valeurs devant être persistées devraient être copiées dans des structures applicatives propres.
  • Accès concurrent : comme les deux fonctions de notification sont identifiées comme non_threadsafe ([SWS_TS_00421], [SWS_TS_00423]), un appel simultané depuis plusieurs threads constitue une violation de précondition. Les appels devraient avoir lieu de manière synchrone par le framework ; si une implémentation modifie des structures de données internes, elle doit prendre ses propres dispositions de synchronisation.
