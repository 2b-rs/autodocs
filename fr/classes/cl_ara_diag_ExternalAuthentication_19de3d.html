Contexte et architecture

Dans l'Adaptive Platform, la classe ara::diag::ExternalAuthentication constitue l'interface permettant aux applications adaptatives de gérer et d'interroger les instances d'authentification des testeurs de diagnostic [SWS_DM_01191]. Dans une architecture AUTOSAR, elle fait office de portail d'accès (Port) au Diagnostic Manager (DM) afin de récupérer des instances de ara::diag::ClientAuthentication adaptées aux clients de diagnostic demandeurs AUTOSAR_AP_SWS_Diagnostics p. 129.

Dans le métamodèle AUTOSAR, l'élément DiagnosticExternalAuthenticationIdentification définit des adresses sources fixes ou des plages d'adresses pour les clients de diagnostic, desquelles découle le nombre d'objets ara::diag::ClientAuthentication disponibles AUTOSAR_AP_SWS_Diagnostics p. 129. Les adresses individuelles des testeurs sont ainsi représentées sous la forme d'un entier 16 bits via l'alias de type standardisé Address [SWS_DM_01192]. ExternalAuthentication assure ainsi une médiation directe entre l'application adaptative, le serveur de diagnostic ou Diagnostic Manager, et les états d'authentification client représentés.

Diagramme de contexte : interaction entre l'application adaptative, ExternalAuthentication, Diagnostic Manager et ClientAuthentication. Sources : [SWS_DM_01191], [SWS_DM_01202], AUTOSAR_AP_SWS_Diagnostics p. 129

Cycle de vie et concurrence

Les instances de ara::diag::ExternalAuthentication sont créées explicitement via un ara::core::InstanceSpecifier [SWS_DM_01193]. Cet identifiant doit faire référence à un PortPrototype défini dans le manifeste d'exécution, qui est typé par un DiagnosticExternalAuthenticationInterface [SWS_DM_01193]. La construction est spécifiée comme sûre du point de vue des exceptions (exception safe) et sûre au regard des threads (thread-safe) [SWS_DM_01193].

Concernant les relations de propriété, la classe possède une sémantique exclusive : le constructeur de copie [SWS_DM_01196] et l'opérateur d'assignation par copie [SWS_DM_01197] sont supprimés (=delete). Un objet peut toutefois être déplacé via le constructeur de déplacement [SWS_DM_01194] ou l'opérateur d'assignation par déplacement [SWS_DM_01195], les deux opérateurs étant déclarés comme noexcept.

La destruction s'effectue via le destructeur virtuel ou standard [SWS_DM_01198]. Contrairement aux appels de méthode réguliers, le destructeur est expressément classé comme non sûr au regard des threads (not thread-safe) [SWS_DM_01198] ; l'application doit donc s'assurer qu'aucun accès concurrent à la même instance n'a lieu pendant l'opération de destruction.

Chemin d'utilisation pour l'authentification client

Le déroulement standard de la gestion de l'authentification externe se divise dans les phases suivantes :

  1. Instanciation du port d'authentification : l'application instancie ExternalAuthentication en spécifiant le InstanceSpecifier manifesté [SWS_DM_01193].
  2. Récupération de l'instance d'authentification client : selon le contexte, deux surcharges de Get ainsi qu'une requête groupée sont à la disposition de l'application :
    • Via l'adresse source : Get(Address) récupère l'instance à partir de l'adresse du testeur (std::uint16_t) [SWS_DM_01192], [SWS_DM_01200].
    • Via les métadonnées de requête : Get(const MetaInfo&) détermine l'instance à l'aide des métadonnées UDS transportées d'une requête de diagnostic entrante [SWS_DM_01199].
    • Requête groupée : GetAll() renvoie toutes les instances de ClientAuthentication actuellement gérées par le Diagnostic Manager sous la forme d'un vecteur [SWS_DM_01201].
  3. Gestion de l'état dans le Diagnostic Manager\u202f: Le Diagnostic Manager transmet à l'application l'instance ClientAuthentication correspondante, qui est responsable de la gestion de l'état d'authentification du client respectif [SWS_DM_01202]. L'application utilise vraisemblablement cet objet par la suite afin d'effectuer des vérifications d'authentification et des autorisations de droits pour le testeur correspondant.

Diagramme de séquence\u202f: séquence d'appels pour l'instanciation et l'interrogation d'objets ClientAuthentication. Sources\u202f: [SWS_DM_01193], [SWS_DM_01200], [SWS_DM_01202]

Scénarios d'erreur et préconditions

Des erreurs peuvent survenir aussi bien lors de la résolution du modèle pendant l'instanciation que pendant le fonctionnement opérationnel\u202f:

  • Violations de modèle et de manifeste (constructeur)\u202f: Si la résolution du InstanceSpecifier échoue ou si la configuration du modèle ne correspond pas au processus d'exécution, des violations de temps d'exécution AUTOSAR standardisées se produisent [SWS_DM_01193]\u202f:
    • InstanceSpecifierMappingIntegrityViolation\u202f: L'identifiant ne fait pas référence à un PortPrototype ou ne peut pas être résolu dans le contexte de l'application [SWS_DM_01193].
    • PortInterfaceMappingViolation\u202f: Le port référencé n'est pas typé par un DiagnosticExternalAuthenticationInterface [SWS_DM_01193].
    • ProcessMappingViolation\u202f: Il n'existe aucun mappage de processus correspondant au processus modélisé au moment de l'exécution [SWS_DM_01193].
    • InstanceSpecifierAlreadyInUseViolation\u202f: Le InstanceSpecifier a déjà été utilisé au sein du même processus pour une instance de port existante [SWS_DM_01193].
  • Erreurs d'exécution lors des interrogations\u202f: Les méthodes Get(Address) et Get(const MetaInfo&) renvoient un ara::core::Result<ClientAuthentication> [SWS_DM_01199], [SWS_DM_01200]. Si la fonctionnalité essentielle du Diagnostic Manager n'est pas disponible pour le moment, l'appel échoue et renvoie le code d'erreur DiagErrc::kServiceNotAvailable avec une sémantique de rollback [SWS_DM_01199], [SWS_DM_01200].
  • Listes de résultats vides\u202f: GetAll() ne renvoie pas d'objet Result, mais directement un vecteur ara::core::Vector<ClientAuthentication>. Si aucun client n'est présent ou si aucune instance n'est enregistrée, une liste vide est renvoyée [SWS_DM_01201].

<h4>Contexte et architecture</h4>
<p>Dans l'Adaptive Platform, la classe <code>ara::diag::ExternalAuthentication</code> constitue l'interface permettant aux applications adaptatives de gérer et d'interroger les instances d'authentification des testeurs de diagnostic <a class="spec-record-ref" data-req="SWS_DM_01191" href="../spec/record.html?id=SWS_DM_01191">[SWS_DM_01191]</a>. Dans une architecture AUTOSAR, elle fait office de portail d'accès (Port) au Diagnostic Manager (DM) afin de récupérer des instances de <code>ara::diag::ClientAuthentication</code> adaptées aux clients de diagnostic demandeurs <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics p. 129</a>.</p>
<p>Dans le métamodèle AUTOSAR, l'élément <code>DiagnosticExternalAuthenticationIdentification</code> définit des adresses sources fixes ou des plages d'adresses pour les clients de diagnostic, desquelles découle le nombre d'objets <code>ara::diag::ClientAuthentication</code> disponibles <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics p. 129</a>. Les adresses individuelles des testeurs sont ainsi représentées sous la forme d'un entier 16 bits via l'alias de type standardisé <code>Address</code> <a class="spec-record-ref" data-req="SWS_DM_01192" href="../spec/record.html?id=SWS_DM_01192">[SWS_DM_01192]</a>. <code>ExternalAuthentication</code> assure ainsi une médiation directe entre l'application adaptative, le serveur de diagnostic ou Diagnostic Manager, et les états d'authentification client représentés.</p>

<h4>Cycle de vie et concurrence</h4>
<p>Les instances de <code>ara::diag::ExternalAuthentication</code> sont créées explicitement via un <code>ara::core::InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>. Cet identifiant doit faire référence à un <code>PortPrototype</code> défini dans le manifeste d'exécution, qui est typé par un <code>DiagnosticExternalAuthenticationInterface</code> <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>. La construction est spécifiée comme sûre du point de vue des exceptions (<em>exception safe</em>) et sûre au regard des threads (<em>thread-safe</em>) <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</p>
<p>Concernant les relations de propriété, la classe possède une sémantique exclusive : le constructeur de copie <a class="spec-record-ref" data-req="SWS_DM_01196" href="../spec/record.html?id=SWS_DM_01196">[SWS_DM_01196]</a> et l'opérateur d'assignation par copie <a class="spec-record-ref" data-req="SWS_DM_01197" href="../spec/record.html?id=SWS_DM_01197">[SWS_DM_01197]</a> sont supprimés (<code>=delete</code>). Un objet peut toutefois être déplacé via le constructeur de déplacement <a class="spec-record-ref" data-req="SWS_DM_01194" href="../spec/record.html?id=SWS_DM_01194">[SWS_DM_01194]</a> ou l'opérateur d'assignation par déplacement <a class="spec-record-ref" data-req="SWS_DM_01195" href="../spec/record.html?id=SWS_DM_01195">[SWS_DM_01195]</a>, les deux opérateurs étant déclarés comme <code>noexcept</code>.</p>
<p>La destruction s'effectue via le destructeur virtuel ou standard <a class="spec-record-ref" data-req="SWS_DM_01198" href="../spec/record.html?id=SWS_DM_01198">[SWS_DM_01198]</a>. Contrairement aux appels de méthode réguliers, le destructeur est expressément classé comme non sûr au regard des threads (<em>not thread-safe</em>) <a class="spec-record-ref" data-req="SWS_DM_01198" href="../spec/record.html?id=SWS_DM_01198">[SWS_DM_01198]</a> ; l'application doit donc s'assurer qu'aucun accès concurrent à la même instance n'a lieu pendant l'opération de destruction.</p>

<h4>Chemin d'utilisation pour l'authentification client</h4>
<p>Le déroulement standard de la gestion de l'authentification externe se divise dans les phases suivantes :</p>
<ol>
  <li><strong>Instanciation du port d'authentification :</strong> l'application instancie <code>ExternalAuthentication</code> en spécifiant le <code>InstanceSpecifier</code> manifesté <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</li>
  <li><strong>Récupération de l'instance d'authentification client :</strong> selon le contexte, deux surcharges de <code>Get</code> ainsi qu'une requête groupée sont à la disposition de l'application :
    <ul>
      <li>Via l'adresse source : <code>Get(Address)</code> récupère l'instance à partir de l'adresse du testeur (<code>std::uint16_t</code>) <a class="spec-record-ref" data-req="SWS_DM_01192" href="../spec/record.html?id=SWS_DM_01192">[SWS_DM_01192]</a>, <a class="spec-record-ref" data-req="SWS_DM_01200" href="../spec/record.html?id=SWS_DM_01200">[SWS_DM_01200]</a>.</li>
      <li>Via les métadonnées de requête : <code>Get(const MetaInfo&amp;)</code> détermine l'instance à l'aide des métadonnées UDS transportées d'une requête de diagnostic entrante <a class="spec-record-ref" data-req="SWS_DM_01199" href="../spec/record.html?id=SWS_DM_01199">[SWS_DM_01199]</a>.</li>
      <li>Requête groupée : <code>GetAll()</code> renvoie toutes les instances de <code>ClientAuthentication</code> actuellement gérées par le Diagnostic Manager sous la forme d'un vecteur <a class="spec-record-ref" data-req="SWS_DM_01201" href="../spec/record.html?id=SWS_DM_01201">[SWS_DM_01201]</a>.</li>
    </ul>
  </li>
  <li><strong>Gestion de l'état dans le Diagnostic Manager\u202f:</strong> Le Diagnostic Manager transmet à l'application l'instance <code>ClientAuthentication</code> correspondante, qui est responsable de la gestion de l'état d'authentification du client respectif <a class="spec-record-ref" data-req="SWS_DM_01202" href="../spec/record.html?id=SWS_DM_01202">[SWS_DM_01202]</a>. L'application utilise vraisemblablement cet objet par la suite afin d'effectuer des vérifications d'authentification et des autorisations de droits pour le testeur correspondant.</li>
</ol>

<h4>Scénarios d'erreur et préconditions</h4>
<p>Des erreurs peuvent survenir aussi bien lors de la résolution du modèle pendant l'instanciation que pendant le fonctionnement opérationnel\u202f:</p>
<ul>
  <li><strong>Violations de modèle et de manifeste (constructeur)\u202f:</strong> Si la résolution du <code>InstanceSpecifier</code> échoue ou si la configuration du modèle ne correspond pas au processus d'exécution, des violations de temps d'exécution AUTOSAR standardisées se produisent <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>\u202f:
    <ul>
      <li><code>InstanceSpecifierMappingIntegrityViolation</code>\u202f: L'identifiant ne fait pas référence à un <code>PortPrototype</code> ou ne peut pas être résolu dans le contexte de l'application <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</li>
      <li><code>PortInterfaceMappingViolation</code>\u202f: Le port référencé n'est pas typé par un <code>DiagnosticExternalAuthenticationInterface</code> <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</li>
      <li><code>ProcessMappingViolation</code>\u202f: Il n'existe aucun mappage de processus correspondant au processus modélisé au moment de l'exécution <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</li>
      <li><code>InstanceSpecifierAlreadyInUseViolation</code>\u202f: Le <code>InstanceSpecifier</code> a déjà été utilisé au sein du même processus pour une instance de port existante <a class="spec-record-ref" data-req="SWS_DM_01193" href="../spec/record.html?id=SWS_DM_01193">[SWS_DM_01193]</a>.</li>
    </ul>
  </li>
  <li><strong>Erreurs d'exécution lors des interrogations\u202f:</strong> Les méthodes <code>Get(Address)</code> et <code>Get(const MetaInfo&amp;)</code> renvoient un <code>ara::core::Result&lt;ClientAuthentication&gt;</code> <a class="spec-record-ref" data-req="SWS_DM_01199" href="../spec/record.html?id=SWS_DM_01199">[SWS_DM_01199]</a>, <a class="spec-record-ref" data-req="SWS_DM_01200" href="../spec/record.html?id=SWS_DM_01200">[SWS_DM_01200]</a>. Si la fonctionnalité essentielle du Diagnostic Manager n'est pas disponible pour le moment, l'appel échoue et renvoie le code d'erreur <code>DiagErrc::kServiceNotAvailable</code> avec une sémantique de rollback <a class="spec-record-ref" data-req="SWS_DM_01199" href="../spec/record.html?id=SWS_DM_01199">[SWS_DM_01199]</a>, <a class="spec-record-ref" data-req="SWS_DM_01200" href="../spec/record.html?id=SWS_DM_01200">[SWS_DM_01200]</a>.</li>
  <li><strong>Listes de résultats vides\u202f:</strong> <code>GetAll()</code> ne renvoie pas d'objet Result, mais directement un vecteur <code>ara::core::Vector&lt;ClientAuthentication&gt;</code>. Si aucun client n'est présent ou si aucune instance n'est enregistrée, une liste vide est renvoyée <a class="spec-record-ref" data-req="SWS_DM_01201" href="../spec/record.html?id=SWS_DM_01201">[SWS_DM_01201]</a>.</li>
</ul>
