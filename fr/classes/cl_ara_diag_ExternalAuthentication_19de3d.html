Sert à la récupération d'instances d'authentification pour la gestion de l'état de clients de diagnostic externes.

La classe ara::diag::ExternalAuthentication fournit une interface de port par laquelle une application adaptative interroge des instances de ara::diag::ClientAuthentication pour gérer l'état d'authentification de clients de diagnostic externes [SWS_DM_01191]. Après la liaison à un port de service modélisé, les objets d'authentification sont demandés de manière ciblée au Diagnostic Manager à partir de l'adresse source ou de méta-informations [SWS_DM_01200]. L'instance possède une sémantique de déplacement, interdit les opérations de copie et requiert une désallocation synchronisée en raison d'un destructeur non thread-safe.

Contexte

Dans l'AUTOSAR Adaptive Platform, la classe ara::diag::ExternalAuthentication fait office d'interface de port pour l'authentification de clients de diagnostic externes [SWS_DM_01191], AUTOSAR_AP_SWS_Diagnostics §8.17 « Header: ara/diag/external_authentication.h ». Via ce port, une application adaptative obtient l'accès à des instances spécifiques de ara::diag::ClientAuthentication, qui représentent et gèrent l'état d'authentification du client de diagnostic respectif [SWS_DM_01202].

L'association et le nombre d'instances de clients disponibles sont définis dans le modèle logiciel via l'élément DiagnosticExternalAuthenticationIdentification. Celui-ci permet à l'application de définir des adresses sources fixes ou des plages d'adresses configurées du type Address (alias pour std::uint16_t [SWS_DM_01192]) pour les testeurs de diagnostic lorsque l'adresse source finale n'est connue qu'au moment de l'exécution AUTOSAR_AP_SWS_Diagnostics §7.3.2.2 « Get ClientAuthentication Instance ».

Parmi les partenaires d'interaction impliqués figurent :

  • L'application adaptative, qui crée l'instance de port et interroge les états d'authentification.
  • Le Diagnostic Manager (DM), qui contrôle les connexions de diagnostic et gère les états d'authentification des clients [SWS_DM_01202].
  • Les objets ara::diag::ClientAuthentication, qui sont associés au client demandeur.
  • Le client de diagnostic externe, dont la connexion est identifiée par l'adresse source ou des méta-informations.

Diagramme de contexte : intégration de la classe de port entre l'application, le Diagnostic Manager et l'authentification de client. Sources : [SWS_DM_01191], [SWS_DM_01202], AUTOSAR_AP_SWS_Diagnostics §7.3.2.2 « Get ClientAuthentication Instance ».

Cycle de vie

La création d'une instance de ara::diag::ExternalAuthentication s'effectue explicitement par la transmission d'un ara::core::InstanceSpecifier au constructeur [SWS_DM_01193]. Cet identifiant lie l'objet au PortPrototype modélisé d'un DiagnosticExternalAuthenticationInterface.

Concernant les relations de propriété, la classe possède une sémantique exclusive de déplacement : le constructeur de déplacement [SWS_DM_01194] et l'opérateur d'affectation par déplacement [SWS_DM_01195] sont présents (default), tandis que le constructeur de copie [SWS_DM_01196] et l'opérateur d'affectation par copie [SWS_DM_01197] sont supprimés (delete). Un port représente ainsi un objet d'interface indivisible et non copiable.

Pour la destruction, le destructeur ~ExternalAuthentication() est disponible [SWS_DM_01198]. En ce qui concerne la concurrence, le constructeur ainsi que les méthodes d'interrogation sont spécifiés comme thread-safe (thread-safe) et protégés contre les exceptions (exception safe) [SWS_DM_01193], [SWS_DM_01199], [SWS_DM_01200], [SWS_DM_01201]. En revanche, le destructeur est expressément non thread-safe (not thread-safe) [SWS_DM_01198]. L'application doit donc s'assurer qu'aucun appel concurrent n'a plus lieu avant la destruction de l'objet.

Parcours d'utilisation

Le déroulement typique comprend l'initialisation du port puis la récupération des objets d'authentification :

  1. L'application instancie ExternalAuthentication en spécifiant l'identifiant d'instance [SWS_DM_01193].
  2. L'application demande l'instance d'authentification pour un client concret. Pour cela, les méthodes surchargées Get(Address) utilisant l'adresse de testeur [SWS_DM_01200] ou Get(const MetaInfo&) basée sur des métadonnées de requête reçues [SWS_DM_01199] sont disponibles. Alternativement, elle récupère au moyen de GetAll() une liste de toutes les instances actuellement gérées par le Diagnostic Manager [SWS_DM_01201].
  3. Le Diagnostic Manager détermine l'objet correspondant et renvoie un ara::core::Result<ClientAuthentication> ou un vecteur [SWS_DM_01202].
  4. L'application vérifie le résultat et interagit ensuite avec l'instance de ClientAuthentication obtenue, qui fait vraisemblablement office de descripteur (handle) côté application pour l'état de la session d'authentification.

Diagramme de séquence : séquence d'appels typique pour l'instanciation et l'interrogation d'une instance ClientAuthentication. Sources : [SWS_DM_01193], [SWS_DM_01200], [SWS_DM_01202].

Scénarios d'erreur

Lors de l'instanciation via le constructeur, des erreurs de configuration et de modélisation peuvent entraîner des violations définies [SWS_DM_01193] :

  • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne référence aucun PortPrototype.
  • PortInterfaceMappingViolation : le PortPrototype référencé n'est pas typé en tant que DiagnosticExternalAuthenticationInterface.
  • ProcessMappingViolation : il n'existe aucune définition de processus modélisée correspondante pour le processus d'exécution.
  • InstanceSpecifierAlreadyInUseViolation : l'identifiant est déjà utilisé dans le même processus par une autre instance de port.

Lors des appels de Get(const MetaInfo&) ou Get(Address), la valeur de retour via ara::core::Result peut contenir le code d'erreur DiagErrc::kServiceNotAvailable [SWS_DM_01199], [SWS_DM_01200]. Cela indique qu'une fonctionnalité essentielle du Diagnostic Manager est temporairement indisponible. En cas d'instances manquantes, l'appel GetAll() ne renvoie pas de code d'erreur, mais un vecteur vide [SWS_DM_01201].

La méthode synchrone ara::diag::ExternalAuthentication::Get permet à une application adaptative de récupérer l'instance de ara::diag::ClientAuthentication responsable d'une requête de diagnostic [SWS_DM_01199]. Une référence vers metaInfo (const ara::diag::MetaInfo&), qui fournit des métadonnées issues du contexte de la requête de diagnostic, est transmise comme paramètre SWS Diagnostics §7.3.1.1 « MetaInfo class ». La valeur de retour de type ara::core::Result<ClientAuthentication> encapsule l'objet d'authentification correspondant pour gérer l'état d'authentification du client [SWS_DM_01202].

              

              
Si une erreur survient, le Result renvoyé contient le code d'erreur spécifique DiagErrc::kServiceNotAvailable [SWS_DM_01199]. Celui-ci signale, avec une sémantique de rollback, que l'appel ne peut pas être exécuté parce que des fonctions essentielles du Diagnostic Manager (DM) ne sont pas disponibles au moment de l'appel [SWS_DM_01199].

              

              
Concernant la concurrence, la fonction est spécifiée comme thread-safe ainsi qu'exception safe et déclarée avec noexcept [SWS_DM_01199]. Elle peut donc être appelée de manière sûre depuis des threads parallèles sans mécanismes de verrouillage côté application.

              

              
La méthode interagit avec la variante surchargée Get(Address sourceAddress) [SWS_DM_01200], qui permet la même récupération directement via l'adresse source du client [SWS_DM_01202]. Le nombre d'instances disponibles est déterminé par les éléments de modèle DiagnosticExternalAuthenticationIdentification SWS Diagnostics « Get ClientAuthentication Instance ». Interprétation : la fonction devrait déterminer en interne l'adresse source nécessaire à l'affectation à partir des données de transport encapsulées dans metaInfo.
