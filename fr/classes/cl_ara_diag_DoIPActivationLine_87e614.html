Contexte

La classe ara::diag::DoIPActivationLine ([SWS_DM_00830]) définit l'interface de programmation pour le DiagnosticDoIPActivationLineInterface au sein du module diag de l'AUTOSAR Adaptive Platform. Dans les réseaux de véhicules, une ligne d'activation dédiée (DoIP Activation Line) sert à activer ou désactiver de manière ciblée la communication DoIP sur une interface réseau physique afin d'économiser le courant de repos ou de contrôler les connexions de diagnostic au plus près du matériel.

Via ara::diag::DoIPActivationLine, une Adaptive Application (AA) associe la détection et la commande de cette ligne d'activation au Diagnostic Management (DM). Une application peut ainsi demander indirectement l'émission de messages DoIP-Vehicle-Announcement (AUTOSAR_AP_SWS_Diagnostics p. 107), le DM réagissant aux changements d'état des interfaces réseau contrôlées par une ligne d'activation ([SWS_DM_00816]).

Diagramme de contexte : relations d'interaction de la classe DoIPActivationLine entre l'application, le Diagnostic Management et le réseau DoIP externe. Sources : [SWS_DM_00830], [SWS_DM_00816], AUTOSAR_AP_SWS_Diagnostics p. 107.

Cycle de vie

L'instanciation de ara::diag::DoIPActivationLine s'effectue via le constructeur paramétré en lui transmettant un ara::core::InstanceSpecifier ([SWS_DM_00831]). Cet identifiant associe l'objet à un PortPrototype du type DiagnosticDoIPActivationLineInterface déclaré dans le modèle AUTOSAR.

Concernant la sémantique d'appartenance et de cycle de vie, la classe est conçue comme une instance unique stricte par configuration d'interface. Le constructeur de copie ([SWS_DM_01633]) ainsi que l'opérateur d'affectation par copie ([SWS_DM_01631]) sont supprimés (=delete). De même, le constructeur de déplacement ([SWS_DM_01634]) et l'opérateur d'affectation par déplacement ([SWS_DM_01632]) sont explicitement supprimés. Une instance ne peut donc être ni copiée ni déplacée.

Après la création de l'objet, l'interface se trouve dans un état de repos. Via la méthode Offer() ([SWS_DM_00836]), l'application signale au DM la disponibilité de l'interface, afin que celui-ci puisse être à l'écoute des changements de la ligne. Avec StopOffer() ([SWS_DM_00837]), la mise à disposition de l'état de la ligne auprès du DM est à nouveau désactivée. Le nettoyage s'effectue via le destructeur virtuel ~DoIPActivationLine() ([SWS_DM_00832]).

Concernant la concurrence, le constructeur ([SWS_DM_00831]) ainsi que les méthodes d'interrogation GetActivationLineState() ([SWS_DM_00835]) et GetNetworkInterfaceId() ([SWS_DM_00833]) sont spécifiés comme thread-safe. En revanche, Offer() ([SWS_DM_00836]), StopOffer() ([SWS_DM_00837]) et UpdateActivationLineState() ([SWS_DM_00834]) sont déclarés non thread-safe et nécessitent une synchronisation côté application.

Parcours d'utilisation

Comme GetActivationLineState() ([SWS_DM_00835]) et GetNetworkInterfaceId() ([SWS_DM_00833]) sont des méthodes virtuelles pures, l'Adaptive Application dérive une classe d'implémentation concrète. Le flux d'appels typique comprend les étapes suivantes :

  1. Instanciation : l'objet dérivé est créé avec le ara::core::InstanceSpecifier du port cible ([SWS_DM_00831]).
  2. Offre de service : l'application appelle Offer() ([SWS_DM_00836]). Interprétation : après un enregistrement réussi, le DM interroge vraisemblablement de manière initiale l'ID d'interface via GetNetworkInterfaceId() ([SWS_DM_00833]) et l'état actuel via GetActivationLineState() ([SWS_DM_00835]) afin d'initialiser l'état réseau DoIP interne.
  3. Mise à jour de l'état : si le niveau physique de la ligne d'activation change, l'application le signale via UpdateActivationLineState(bool) ([SWS_DM_00834]). Le DM reçoit ce changement d'état ([SWS_DM_00816]) et commande ensuite l'activation de la connexion DoIP.
  4. Arrêt du service : avant l'arrêt, l'application appelle StopOffer() ([SWS_DM_00837]), de sorte que le DM ne traite plus aucune modification de la ligne, et détruit l'instance ([SWS_DM_00832]).

Diagramme de séquence : séquence typique d'interactions lors de la mise à disposition, de l'interrogation et de la mise à jour de la ligne d'activation DoIP. Sources : [SWS_DM_00831], [SWS_DM_00833], [SWS_DM_00834], [SWS_DM_00835], [SWS_DM_00836], [SWS_DM_00837].

Scénarios d'erreur

Dans le cadre de l'interaction avec le modèle AUTOSAR et les appels de méthode, les situations d'erreur suivantes sont spécifiées :

  • Violations de construction : lors de l'appel du constructeur ([SWS_DM_00831]), des erreurs de validation peuvent être déclenchées :
    • InstanceSpecifierMappingIntegrityViolation : l'InstanceSpecifier ne peut pas être résolu dans le contexte de l'Executable ou ne référence aucun élément PortPrototype.
    • PortInterfaceMappingViolation : le PortPrototype référencé n'est pas typé par un DiagnosticDoIPActivationLineInterface.
    • ProcessMappingViolation : il n'existe pour l'identifiant d'instance aucun processus modélisé concordant qui corresponde au processus d'exécution actuel.
    • InstanceSpecifierAlreadyInUseViolation : l'InstanceSpecifier a déjà été transmis à un autre constructeur au sein de ce processus.
  • Offre multiple : l'appel de Offer() retourne un ara::core::Result<void> ([SWS_DM_00836]). Si le service est déjà offert, l'appel échoue avec le code d'erreur DiagOfferErrc::kAlreadyOffered.
  • Incohérence de modèle pour les interfaces réseau : si l'implémentation signale via GetNetworkInterfaceId() ([SWS_DM_00833]) un ID dont la DoIpNetworkConfiguration associée possède la propriété isActivationLineDependent = 'FALSE', cela constitue une erreur de configuration.
  • Sécurité vis-à-vis des exceptions : alors que le constructeur, le destructeur, Offer() et les méthodes d'interrogation sont considérés comme sûrs vis-à-vis des exceptions (exception safe), UpdateActivationLineState() ([SWS_DM_00834]) est classé comme non sûr vis-à-vis des exceptions. Les appelants doivent donc s'assurer qu'aucun état de programme non valide n'est transmis à cette méthode.

Ce guide est basé sur les spécifications de l'AUTOSAR Adaptive Platform pour la version R25-11.

<h4>Contexte</h4>
<p>La classe <code>ara::diag::DoIPActivationLine</code> (<a class="spec-record-ref" data-req="SWS_DM_00830" href="../spec/record.html?id=SWS_DM_00830">[SWS_DM_00830]</a>) définit l'interface de programmation pour le <code>DiagnosticDoIPActivationLineInterface</code> au sein du module <code>diag</code> de l'AUTOSAR Adaptive Platform. Dans les réseaux de véhicules, une ligne d'activation dédiée (DoIP Activation Line) sert à activer ou désactiver de manière ciblée la communication DoIP sur une interface réseau physique afin d'économiser le courant de repos ou de contrôler les connexions de diagnostic au plus près du matériel.</p>
<p>Via <code>ara::diag::DoIPActivationLine</code>, une Adaptive Application (AA) associe la détection et la commande de cette ligne d'activation au Diagnostic Management (DM). Une application peut ainsi demander indirectement l'émission de messages DoIP-Vehicle-Announcement (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=107">AUTOSAR_AP_SWS_Diagnostics p. 107</a>), le DM réagissant aux changements d'état des interfaces réseau contrôlées par une ligne d'activation (<a class="spec-record-ref" data-req="SWS_DM_00816" href="../spec/record.html?id=SWS_DM_00816">[SWS_DM_00816]</a>).</p>

<h4>Cycle de vie</h4>
<p>L'instanciation de <code>ara::diag::DoIPActivationLine</code> s'effectue via le constructeur paramétré en lui transmettant un <code>ara::core::InstanceSpecifier</code> (<a class="spec-record-ref" data-req="SWS_DM_00831" href="../spec/record.html?id=SWS_DM_00831">[SWS_DM_00831]</a>). Cet identifiant associe l'objet à un PortPrototype du type <code>DiagnosticDoIPActivationLineInterface</code> déclaré dans le modèle AUTOSAR.</p>
<p>Concernant la sémantique d'appartenance et de cycle de vie, la classe est conçue comme une instance unique stricte par configuration d'interface. Le constructeur de copie (<a class="spec-record-ref" data-req="SWS_DM_01633" href="../spec/record.html?id=SWS_DM_01633">[SWS_DM_01633]</a>) ainsi que l'opérateur d'affectation par copie (<a class="spec-record-ref" data-req="SWS_DM_01631" href="../spec/record.html?id=SWS_DM_01631">[SWS_DM_01631]</a>) sont supprimés (<code>=delete</code>). De même, le constructeur de déplacement (<a class="spec-record-ref" data-req="SWS_DM_01634" href="../spec/record.html?id=SWS_DM_01634">[SWS_DM_01634]</a>) et l'opérateur d'affectation par déplacement (<a class="spec-record-ref" data-req="SWS_DM_01632" href="../spec/record.html?id=SWS_DM_01632">[SWS_DM_01632]</a>) sont explicitement supprimés. Une instance ne peut donc être ni copiée ni déplacée.</p>
<p>Après la création de l'objet, l'interface se trouve dans un état de repos. Via la méthode <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00836" href="../spec/record.html?id=SWS_DM_00836">[SWS_DM_00836]</a>), l'application signale au DM la disponibilité de l'interface, afin que celui-ci puisse être à l'écoute des changements de la ligne. Avec <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00837" href="../spec/record.html?id=SWS_DM_00837">[SWS_DM_00837]</a>), la mise à disposition de l'état de la ligne auprès du DM est à nouveau désactivée. Le nettoyage s'effectue via le destructeur virtuel <code>~DoIPActivationLine()</code> (<a class="spec-record-ref" data-req="SWS_DM_00832" href="../spec/record.html?id=SWS_DM_00832">[SWS_DM_00832]</a>).</p>
<p>Concernant la concurrence, le constructeur (<a class="spec-record-ref" data-req="SWS_DM_00831" href="../spec/record.html?id=SWS_DM_00831">[SWS_DM_00831]</a>) ainsi que les méthodes d'interrogation <code>GetActivationLineState()</code> (<a class="spec-record-ref" data-req="SWS_DM_00835" href="../spec/record.html?id=SWS_DM_00835">[SWS_DM_00835]</a>) et <code>GetNetworkInterfaceId()</code> (<a class="spec-record-ref" data-req="SWS_DM_00833" href="../spec/record.html?id=SWS_DM_00833">[SWS_DM_00833]</a>) sont spécifiés comme thread-safe. En revanche, <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00836" href="../spec/record.html?id=SWS_DM_00836">[SWS_DM_00836]</a>), <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00837" href="../spec/record.html?id=SWS_DM_00837">[SWS_DM_00837]</a>) et <code>UpdateActivationLineState()</code> (<a class="spec-record-ref" data-req="SWS_DM_00834" href="../spec/record.html?id=SWS_DM_00834">[SWS_DM_00834]</a>) sont déclarés non thread-safe et nécessitent une synchronisation côté application.</p>

<h4>Parcours d'utilisation</h4>
<p>Comme <code>GetActivationLineState()</code> (<a class="spec-record-ref" data-req="SWS_DM_00835" href="../spec/record.html?id=SWS_DM_00835">[SWS_DM_00835]</a>) et <code>GetNetworkInterfaceId()</code> (<a class="spec-record-ref" data-req="SWS_DM_00833" href="../spec/record.html?id=SWS_DM_00833">[SWS_DM_00833]</a>) sont des méthodes virtuelles pures, l'Adaptive Application dérive une classe d'implémentation concrète. Le flux d'appels typique comprend les étapes suivantes :</p>
<ol>
<li><strong>Instanciation :</strong> l'objet dérivé est créé avec le <code>ara::core::InstanceSpecifier</code> du port cible (<a class="spec-record-ref" data-req="SWS_DM_00831" href="../spec/record.html?id=SWS_DM_00831">[SWS_DM_00831]</a>).</li>
<li><strong>Offre de service :</strong> l'application appelle <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00836" href="../spec/record.html?id=SWS_DM_00836">[SWS_DM_00836]</a>). Interprétation : après un enregistrement réussi, le DM interroge vraisemblablement de manière initiale l'ID d'interface via <code>GetNetworkInterfaceId()</code> (<a class="spec-record-ref" data-req="SWS_DM_00833" href="../spec/record.html?id=SWS_DM_00833">[SWS_DM_00833]</a>) et l'état actuel via <code>GetActivationLineState()</code> (<a class="spec-record-ref" data-req="SWS_DM_00835" href="../spec/record.html?id=SWS_DM_00835">[SWS_DM_00835]</a>) afin d'initialiser l'état réseau DoIP interne.</li>
<li><strong>Mise à jour de l'état :</strong> si le niveau physique de la ligne d'activation change, l'application le signale via <code>UpdateActivationLineState(bool)</code> (<a class="spec-record-ref" data-req="SWS_DM_00834" href="../spec/record.html?id=SWS_DM_00834">[SWS_DM_00834]</a>). Le DM reçoit ce changement d'état (<a class="spec-record-ref" data-req="SWS_DM_00816" href="../spec/record.html?id=SWS_DM_00816">[SWS_DM_00816]</a>) et commande ensuite l'activation de la connexion DoIP.</li>
<li><strong>Arrêt du service :</strong> avant l'arrêt, l'application appelle <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_00837" href="../spec/record.html?id=SWS_DM_00837">[SWS_DM_00837]</a>), de sorte que le DM ne traite plus aucune modification de la ligne, et détruit l'instance (<a class="spec-record-ref" data-req="SWS_DM_00832" href="../spec/record.html?id=SWS_DM_00832">[SWS_DM_00832]</a>).</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Dans le cadre de l'interaction avec le modèle AUTOSAR et les appels de méthode, les situations d'erreur suivantes sont spécifiées :</p>
<ul>
<li><strong>Violations de construction :</strong> lors de l'appel du constructeur (<a class="spec-record-ref" data-req="SWS_DM_00831" href="../spec/record.html?id=SWS_DM_00831">[SWS_DM_00831]</a>), des erreurs de validation peuvent être déclenchées :
<ul>
<li><code>InstanceSpecifierMappingIntegrityViolation</code> : l'InstanceSpecifier ne peut pas être résolu dans le contexte de l'Executable ou ne référence aucun élément PortPrototype.</li>
<li><code>PortInterfaceMappingViolation</code> : le PortPrototype référencé n'est pas typé par un <code>DiagnosticDoIPActivationLineInterface</code>.</li>
<li><code>ProcessMappingViolation</code> : il n'existe pour l'identifiant d'instance aucun processus modélisé concordant qui corresponde au processus d'exécution actuel.</li>
<li><code>InstanceSpecifierAlreadyInUseViolation</code> : l'InstanceSpecifier a déjà été transmis à un autre constructeur au sein de ce processus.</li>
</ul>
</li>
<li><strong>Offre multiple :</strong> l'appel de <code>Offer()</code> retourne un <code>ara::core::Result&lt;void&gt;</code> (<a class="spec-record-ref" data-req="SWS_DM_00836" href="../spec/record.html?id=SWS_DM_00836">[SWS_DM_00836]</a>). Si le service est déjà offert, l'appel échoue avec le code d'erreur <code>DiagOfferErrc::kAlreadyOffered</code>.</li>
<li><strong>Incohérence de modèle pour les interfaces réseau :</strong> si l'implémentation signale via <code>GetNetworkInterfaceId()</code> (<a class="spec-record-ref" data-req="SWS_DM_00833" href="../spec/record.html?id=SWS_DM_00833">[SWS_DM_00833]</a>) un ID dont la <code>DoIpNetworkConfiguration</code> associée possède la propriété <code>isActivationLineDependent = 'FALSE'</code>, cela constitue une erreur de configuration.</li>
<li><strong>Sécurité vis-à-vis des exceptions :</strong> alors que le constructeur, le destructeur, <code>Offer()</code> et les méthodes d'interrogation sont considérés comme sûrs vis-à-vis des exceptions (exception safe), <code>UpdateActivationLineState()</code> (<a class="spec-record-ref" data-req="SWS_DM_00834" href="../spec/record.html?id=SWS_DM_00834">[SWS_DM_00834]</a>) est classé comme non sûr vis-à-vis des exceptions. Les appelants doivent donc s'assurer qu'aucun état de programme non valide n'est transmis à cette méthode.</li>
</ul>
