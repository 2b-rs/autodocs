Contexte

La classe ara::diag::ServiceValidation constitue l'élément d'interface fonctionnelle pour la validation spécifique au constructeur et au fournisseur des requêtes de diagnostic entrantes dans le module AUTOSAR Adaptive diag [SWS_DM_00772]. Selon la modélisation de l'attribut DiagnosticServiceValidationMapping.category, la validation s'effectue via la méthode Validate soit en tant que vérification constructeur, soit en tant que vérification fournisseur dans le cadre de l'ordre des Negative Response Codes (NRC) selon le chapitre 8.7 de l'ISO 14229-1 [SWS_DM_00772].

L'interaction implique principalement trois parties :

  • Application adaptative : implémente la logique de validation concrète par spécialisation des méthodes virtuelles Validate [SWS_DM_00774] et Confirmation [SWS_DM_00775].
  • Diagnostic Management (DM) : reçoit les requêtes UDS, les transmet à l'instance pour vérification préalable après une activation réussie par Offer [SWS_DM_00776] et notifie l'achèvement global via Confirmation [SWS_DM_00775].
  • Testeur de diagnostic : initialise les messages de diagnostic dont les données brutes et les méta-informations font l'objet de la vérification [SWS_DM_00774].

Cycle de vie

L'instanciation de ServiceValidation s'effectue explicitement par la transmission d'un ara::core::InstanceSpecifier, qui doit référencer un PortPrototype modélisé d'un DiagnosticServiceValidationInterface [SWS_DM_00772]. Le constructeur est spécifié comme thread-safe [SWS_DM_00772]. Une instance de ServiceValidation ne doit être ni copiée ni déplacée : le constructeur de copie [SWS_DM_01689], l'opérateur d'affectation [SWS_DM_01687], le constructeur de déplacement [SWS_DM_01690] et l'opérateur d'affectation par déplacement [SWS_DM_01688] sont explicitement supprimés (= delete).

Après la construction, l'instance se trouve dans l'état Non proposé. L'appel de Offer() active le transfert des requêtes entrantes par le Diagnostic Management [SWS_DM_00776]. Si le traitement doit être mis en pause ou terminé, l'appel de StopOffer() empêche le transfert d'autres messages de diagnostic [SWS_DM_00777]. L'activation peut être réactivée par un nouvel appel de Offer(). La destruction finale s'effectue via le destructeur virtuel ~ServiceValidation() [SWS_DM_00773].

En ce qui concerne la concurrence, les méthodes Offer, StopOffer, Validate, Confirmation ainsi que le destructeur sont classifiés comme non thread-safe [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Les appels de ces opérations doivent être synchronisés par l'application en cas d'accès concurrent.

Parcours d'utilisation

Le déroulement typique pour la sécurisation des services de diagnostic se divise selon les étapes suivantes :

  1. Instanciation : l'application crée l'instance en la liant au port modélisé [SWS_DM_00772].
  2. Activation : appel de Offer(). Le Diagnostic Management est instruit de transférer les messages de diagnostic entrants à cette instance [SWS_DM_00776].
  3. Validation : pour chaque requête de diagnostic entrante, le DM appelle la méthode Validate [SWS_DM_00774]. Les données de requête (y compris le Service Identifier) sont transmises en tant que ara::core::Span<const std::uint8_t> ainsi que le contexte via MetaInfo. La durée de vie des données de requête reste valide jusqu'à ce que la promesse associée soit remplie ou que le traitement soit interrompu via le CancellationHandler [SWS_DM_00774].
  4. Résultat asynchrone : la méthode renvoie un ara::core::Future<void> [SWS_DM_00774]. En cas de validation réussie, le future est résolu sans erreur. Si la requête est non autorisée, le future est terminé avec un Negative Response Code (NRC) approprié issu de DiagUdsNrcErrc selon l'ISO 14229-1 [SWS_DM_00774].
  5. Confirmation d'achèvement : dès que le traitement de la requête de diagnostic est entièrement terminé, le DM appelle Confirmation afin de transmettre le résultat global (status) et la metaInfo [SWS_DM_00775].
  6. Désenregistrement : avant l'arrêt, l'application appelle StopOffer() [SWS_DM_00777]. Interprétation : après l'appel de StopOffer(), les requêtes de validation en cours dont le future n'a pas encore été résolu devraient être soit rejetées, soit interrompues par le DM.

Diagramme de séquence : séquence d'interactions entre l'application, le gestionnaire ServiceValidation et Diagnostic Management (DM). Sources : [SWS_DM_00774], [SWS_DM_00775], [SWS_DM_00776], [SWS_DM_00777].

Scénarios d'erreur

Des situations d'erreur peuvent survenir lors de différentes phases et sont signalées par des mécanismes spécifiques :

  • Violations de construction et de modèle : si la liaison du InstanceSpecifier échoue, le framework signale des violations définies [SWS_DM_00772] :
    • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu ou ne référence pas un PortPrototype.
    • PortInterfaceMappingViolation : le PortPrototype n'est pas typé par un DiagnosticServiceValidationInterface.
    • ProcessMappingViolation : pour la référence, il n'existe aucun processus modélisé correspondant pour le processus d'exécution actuel.
    • InstanceSpecifierAlreadyInUseViolation : le InstanceSpecifier est déjà utilisé par une autre instance dans le processus en cours d'exécution.
  • Activation erronée : si Offer() est appelé alors que le service est déjà proposé, l'appel échoue et renvoie le code d'erreur DiagOfferErrc::kAlreadyOffered avec une sémantique de rollback dans la valeur de retour ara::core::Result<void> [SWS_DM_00776].
  • Erreur de validation : si la vérification détecte une condition enfreinte (par ex. des préconditions ou des exigences de sécurité insuffisantes), l'erreur est transmise via DiagUdsNrcErrc dans le ara::core::Future<void> [SWS_DM_00774]. Comme Validate est déclaré comme noexcept, aucune exception C++ ne doit être levée.
  • Sécurité vis-à-vis des exceptions : toutes les méthodes de la classe sont spécifiées comme sûres vis-à-vis des exceptions (exception safe) et annotées avec noexcept [SWS_DM_00772] [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Les états d'erreur sont sans exception représentés par des types de retour et des messages de la plateforme.

Ce guide de classe est basé sur les exigences de la spécification AUTOSAR Adaptive Platform R25-11.
