Contexte

Dans le module shwa (Shared Hardware Accelerator), la classe ara::shwa::Queue constitue l'interface centrale pour la planification de l'exécution sur des accélérateurs matériels. Une file d'attente encapsule la connexion à un appareil d'exécution concret (Device) ou à une unité matérielle adressée via un DeviceSelector, et coordonne la transmission ainsi que la synchronisation des tâches de travail.

Dans le système global, ara::shwa::Queue interagit avec les intervenants suivants :

  • Application : crée la file d'attente via des méthodes fabrique et pilote l'envoi des tâches ainsi que la synchronisation.
  • Device / DeviceSelector : représente l'appareil cible auquel la file d'attente est liée et dont elle reflète les propriétés [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00910].
  • ErrorHandler : reçoit les retours concernant les erreurs survenues de manière asynchrone pendant le traitement des tâches [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00912].
  • Event : est créé lors de la planification d'une tâche (Submit) et sert d'objet de contrôle et de synchronisation pour les opérations ultérieures [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913].
  • PropertyList : transmet des paramètres de configuration optionnels lors de la création de la file d'attente [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].

Diagramme de contexte : partenaires d'interaction de la classe ara::shwa::Queue. Sources : [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912]

Cycle de vie

La classe ara::shwa::Queue possède une sémantique d'instanciation et de possession strictement contrôlée :

  • Création : le constructeur par défaut est explicitement supprimé [AP_SWS_SHWA_00902]. Les nouvelles instances peuvent être créées exclusivement via les méthodes fabrique statiques Create, qui fournissent un ara::core::Result<std::unique_ptr<Queue>> [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]. La création lie la file d'attente à un Device ou à un DeviceSelector, associe un ErrorHandler et évalue des propriétés PropertyList optionnelles.
  • Possession et identité : ara::shwa::Queue n'est ni copiable ni déplaçable. Le constructeur de copie [AP_SWS_SHWA_00903] tout comme l'opérateur d'assignation par copie [AP_SWS_SHWA_00904], le constructeur de déplacement [AP_SWS_SHWA_00905] et l'opérateur d'assignation par déplacement [AP_SWS_SHWA_00906] sont supprimés. Le cycle de vie de l'instance est donc géré exclusivement via le std::unique_ptr renvoyé.
  • Destruction : si la file d'attente est libérée ou détruite, l'objet est considéré comme invalide. Les appels de méthodes sur des files d'attente détruites ou invalides sont rejetés avec l'erreur ShwaErrorCode::kInvalidObject [AP_SWS_SHWA_00913], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
  • Concurrence : les méthodes de création Create sont sûres au niveau des threads (thread-safe) [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]. En revanche, toutes les fonctions membres régulières de l'instance créée (GetDevice, GetProperty, HasProperty, IsInOrder, Submit, Wait, WaitFor) ne sont pas sûres au niveau des threads (not thread-safe). Un accès simultané à la même instance de file d'attente depuis plusieurs threads nécessite donc une synchronisation externe par l'application.

Parcours d'utilisation

Un déroulement typique lors de l'utilisation de ara::shwa::Queue comprend l'instanciation, la vérification des propriétés, la transmission des tâches et la synchronisation :

  1. Créer la file d'attente : l'application appelle Queue::Create avec le Device (ou DeviceSelector) souhaité, un ErrorHandler et éventuellement une PropertyList [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].
  2. Interroger les propriétés : avant la transmission des tâches, il est possible de vérifier si les tâches sont traitées de manière strictement séquentielle (IsInOrder [AP_SWS_SHWA_00911]), quel Device est associé (GetDevice [AP_SWS_SHWA_00910]) ou si certaines Feature-Properties sont présentes (HasProperty [AP_SWS_SHWA_00915], GetProperty [AP_SWS_SHWA_00916]).
  3. Mettre des tâches en file d'attente (Submit) : une tâche de travail est transmise à la file d'attente via Submit. La configuration cfg (interprétation : configuration de commande ou de noyau spécifique à la tâche) est alors soit transmise avec un ErrorHandler spécifique à la tâche [AP_SWS_SHWA_00912], soit couplée à une file d'attente secondaire (secondaryQueue) [AP_SWS_SHWA_00913]. Les deux variantes renvoient un ara::core::Result<Event>.
  4. Synchroniser la fin des tâches : l'application attend la fin des tâches mises en file d'attente, soit indéfiniment au moyen de Wait() [AP_SWS_SHWA_00914], soit pour une durée limitée avec un délai d'expiration en millisecondes via WaitFor(ms) [AP_SWS_SHWA_00917].

Diagramme de séquence : ordre d'appel typique, de la création de la file d'attente à la synchronisation en passant par Submit. Sources : [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00911], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00917]

Scénarios d'erreur

Les méthodes de ara::shwa::Queue utilisent ara::core::Result pour indiquer les erreurs, avec des codes d'erreur issus du domaine ShwaErrorCode :

  • Erreurs de création : Create échoue si les paramètres transmis sont non autorisés (ShwaErrorCode::kInvalidParameter), si une propriété demandée n'est pas prise en charge (ShwaErrorCode::kFeatureNotSupported), si la ressource matérielle est occupée (ShwaErrorCode::kResourceBusy) ou si une erreur d'exécution générale survient (ShwaErrorCode::kRuntime) [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].
  • Erreurs de transmission : avec Submit, l'opération peut échouer si des arguments invalides ont été transmis (ShwaErrorCode::kInvalidParameter), si la file d'attente est déjà détruite ou invalide (ShwaErrorCode::kInvalidObject), si la ressource est occupée (ShwaErrorCode::kResourceBusy) ou si l'exécution de la tâche échoue (ShwaErrorCode::kTaskExecutionFailure) [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913].
  • Erreurs de synchronisation et délais d'attente : pour Wait et WaitFor, en plus de kResourceBusy, kInvalidObject, kFeatureNotSupported et kTaskExecutionFailure, l'erreur ShwaErrorCode::kTimedOut peut survenir en particulier pour WaitFor si le délai spécifié expire avant la fin des tâches [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
  • Absence de sémantique de retour arrière : pour Submit, Wait et WaitFor, aucune garantie de retour arrière (no_rollback_semantics) ne s'applique expressément en cas d'erreur de kTaskExecutionFailure ou kRuntime. Les données et zones de mémoire référencées au sein de la tâche ayant échoué doivent être considérées comme modifiées involontairement [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
