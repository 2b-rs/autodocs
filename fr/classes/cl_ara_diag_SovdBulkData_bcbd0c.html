Permet aux applications de mettre à disposition et de transmettre des données volumineuses SOVD via le Diagnostic Management.

L'interface [SWS_DM_01841] relie les applications adaptatives au Diagnostic Management afin de fournir des opérations sur les données volumineuses basées sur SOVD. Des méthodes purement virtuelles permettent d'interroger des métadonnées, de gérer les téléversements et téléchargements de données volumineuses ainsi que de supprimer des jeux de données de manière ciblée ou par catégorie. Une instance est liée à un port modélisé, activée pour le réacheminement des requêtes de diagnostic via l'appel de Offer() et désenregistrée lors de l'arrêt via StopOffer() [SWS_DM_01857]. Selon la concurrence sélectionnée, les routines de rappel fournies doivent être conçues pour être sûres pour les threads.

Contexte

La classe d'interface ara::diag::SovdBulkData [SWS_DM_01841] met à disposition une interface de service générique pour l'accès aux données volumineuses (bulk data) conformément à Service-Oriented Vehicle Diagnostics (SOVD) SWS Diagnostics §8.53 « Class: SovdBulkData ». Elle sert de passerelle entre les sources de données spécifiques à l'application et le serveur de diagnostic central de l'Adaptive Platform.

Au moins trois composants participent au déroulement global :

  • Client SOVD : un outil de diagnostic externe qui récupère, téléverse ou supprime des données volumineuses. La communication devrait typiquement être traitée via des mécanismes HTTP/REST.
  • Diagnostic Management (DM) : la Diagnostic Server Instance reçoit les appels de service SOVD externes et les convertit en appels de méthodes locales SWS Diagnostics §7.x « SOVD Bulk Data Realization ».
  • Application adaptative : une application définie par l'utilisateur dérive de ara::diag::SovdBulkData, instancie la classe et fournit les flux de données effectifs ainsi que les métadonnées.

Diagramme de contexte : interaction entre le client SOVD, le Diagnostic Management et l'interface applicative ara::diag::SovdBulkData. Sources : [SWS_DM_01790], [SWS_DM_01841], [SWS_DM_01857].

Cycle de vie

L'instanciation de ara::diag::SovdBulkData s'effectue via le constructeur en transmettant un ara::core::InstanceSpecifier ainsi que l'indication du comportement de concurrence via ConcurrencyType [SWS_DM_01847]. Le InstanceSpecifier lie l'objet à un PortPrototype d'un DiagnosticSovdBulkDataInterface défini dans le modèle de conception.

En ce qui concerne les relations de possession, la classe est conçue comme un exemplaire unique : le constructeur de copie [SWS_DM_01848] et l'opérateur d'affectation par copie [SWS_DM_01850] sont explicitement supprimés (=delete). Le transfert d'instances est exclusivement prévu via des opérations de déplacement ; le constructeur de déplacement [SWS_DM_01849] et l'affectation par déplacement [SWS_DM_01851] sont implémentés de façon protégée.

Le cycle de vie fonctionnel se divise selon les phases suivantes :

  • Inactif : après la construction, l'objet est présent localement mais ne reçoit pas encore de requêtes de diagnostic de la part du Diagnostic Management.
  • Actif (Offered) : l'appel de la méthode Offer() [SWS_DM_01857] enregistre l'objet auprès du DM. Ce n'est qu'à partir de ce moment que le DM relaie les requêtes SOVD entrantes vers les méthodes de gestionnaire virtuelles.
  • Arrêté : l'appel de StopOffer() [SWS_DM_01858] désactive à nouveau le réacheminement des requêtes.
  • Destruction : le destructeur virtuel ~SovdBulkData() [SWS_DM_01852] met fin à la durée de vie de l'objet. Avant la destruction, il convient vraisemblablement d'appeler StopOffer() pour déconnecter proprement les accès en attente.

Concernant la concurrence, le ConcurrencyType transmis au constructeur détermine si les méthodes virtuelles de rappel doivent être exécutées de manière sûre pour les threads (kConcurrent) ou non sûre pour les threads (kNotConcurrent) [SWS_DM_01847]. Les méthodes de contrôle Offer() [SWS_DM_01857], StopOffer() [SWS_DM_01858] et le destructeur [SWS_DM_01852] ne sont eux-mêmes pas sûrs pour les threads.

Parcours d'utilisation

Un déroulement typique pour la mise à disposition et l'exécution d'opérations sur les données volumineuses SOVD comprend les étapes suivantes :

  1. Dérivation de classe : l'application implémente une classe concrète qui hérite de ara::diag::SovdBulkData et surcharge les méthodes virtuelles pures.
  2. Mise à disposition : après l'instanciation, l'application appelle Offer() [SWS_DM_01857] afin de proposer le service.
  3. Traitement des requêtes :
    • Si un client demande des métadonnées, le serveur de diagnostic appelle GetBulkDataMetaData [SWS_DM_01791], ce qui fournit un vecteur de BulkDataMetaDataDescriptor via ara::core::Future [SWS_DM_01853].
    • Lors d'un appel de téléchargement, le DM appelle RequestBulkDataDownload [SWS_DM_01792]. L'application répond par une session de lecture (DataTransferReadSession) accompagnée de métadonnées ou par une redirection HTTP (HttpRedirect) [SWS_DM_01873].
    • Pour les opérations de téléversement, le DM appelle RequestBulkDataUpload [SWS_DM_01793], à la suite de quoi une session d'écriture (DataTransferWriteSession) est fournie [SWS_DM_01854].
    • Le DM relaie les requêtes de suppression à DeleteSpecificBulkData (pour les ressources individuelles) [SWS_DM_01856] ou à DeleteAllBulkData (par catégorie) [SWS_DM_01855].
  4. Désinscription du service : dès que le traitement doit cesser, l'application appelle StopOffer() [SWS_DM_01858].

Diagramme de séquence : séquence d'interaction entre le client SOVD, le Diagnostic Management et le gestionnaire lors du téléchargement de Bulk Data. Sources : [SWS_DM_01792], [SWS_DM_01857], [SWS_DM_01858], [SWS_DM_01873].

Scénarios d'erreur

Lors de l'utilisation de ara::diag::SovdBulkData, plusieurs types d'erreurs doivent être distingués :

  • Violations de configuration lors de l'instanciation : si la résolution du modèle échoue ou si les mappages ne correspondent pas, le constructeur signale des violations spécifiques [SWS_DM_01847]. En font partie InstanceSpecifierMappingIntegrityViolation (modèle non valide ou absence de PortPrototype), PortInterfaceMappingViolation (typage incorrect du mappage de port), ProcessMappingViolation (aucun processus correspondant modélisé) et InstanceSpecifierAlreadyInUseViolation (specifier déjà occupé au sein du processus).
  • Erreurs d'enregistrement lors de Offer : l'appel de Offer() renvoie un ara::core::Result<void> [SWS_DM_01857]. Les erreurs possibles sont DiagOfferErrc::kAlreadyOffered, lorsque le service est déjà proposé, ainsi que DiagOfferErrc::kConfigurationMismatch, lorsque la configuration ne concorde pas avec les descriptions DEXT.
  • Codes d'erreur dans les opérations asynchrones : si une opération sur des données volumineuses demandée ne peut pas être menée à bien, l'erreur est acheminée dans le ara::core::Future renvoyé. L'application doit utiliser pour cela des codes d'erreur SOVD standardisés selon l'ISO 17978-3 ou l'ASAM SOVD 1.1 (en utilisant DiagSovdErrc) [SWS_DM_01854], [SWS_DM_01855], [SWS_DM_01856], [SWS_DM_01873]. En revanche, aucune erreur standardisée n'est spécifiée pour GetBulkDataMetaData [SWS_DM_01853].
  • Gestion des abandons : les méthodes de rappel reçoivent un objet CancellationHandler, qui signale si la conversation de diagnostic sous-jacente a été interrompue prématurément [SWS_DM_01853], [SWS_DM_01873].

Utilisation

La fonction virtuelle DeleteAllBulkData de la classe ara::diag::SovdBulkData est appelée pour exécuter la méthode SOVD « Delete All Bulk Data Defined by Category » [SWS_DM_01855]. La définition d'interface est déposée dans l'en-tête ara/diag/sovd_bulk_data.h AUTOSAR_AP_SWS_Diagnostics §8.53.1.1.3.1 « DeleteAllBulkData ».

La méthode reçoit les paramètres de transmission suivants :

  • bulkDataCategory (ara::core::String) : identifie la catégorie de données de masse dont toutes les instances doivent être supprimées [SWS_DM_01855].
  • metaInfo (MetaInfo const &) : transmet les métadonnées contextuelles de la requête en cours [SWS_DM_01855].
  • cancellationHandler (CancellationHandler) : informe de l'interruption prématurée de la conversation en cours [SWS_DM_01855].

Le résultat est mis à disposition de manière asynchrone via un ara::core::Future<DeleteByCategoryResult> [SWS_DM_01855]. Interprétation : le nettoyage de catégories entières de données de masse pouvant être long, l'application devrait vérifier périodiquement le cancellationHandler transmis afin de réagir immédiatement à d'éventuelles interruptions.

Gestion des erreurs et sécurité vis-à-vis des exceptions

La méthode est déclarée comme noexcept et sûre face aux exceptions (exception safe) [SWS_DM_01855]. Si la suppression échoue, un code d'erreur SOVD approprié selon ISO 17978-3 ou ASAM SOVD 1.1 doit être transmis dans le ara::core::Future [SWS_DM_01855].

concurrence

La sécurité vis-à-vis des threads est conditionnelle (conditional) : le fait que l'implémentation doive être conçue pour être thread-safe ou non thread-safe est défini via le ConcurrencyType transmis au constructeur [SWS_DM_01855].
