Permet de surveiller des cycles de fonctionnement de diagnostic ainsi que de déclencher un redémarrage de cycle via des ports modélisés.

La classe ara::diag::OperationCycle met à disposition de l’application des fonctions de contrôle et de surveillance des cycles de fonctionnement de diagnostic [SWS_DM_00752]. Les instances sont liées à un port modélisé via un ara::core::InstanceSpecifier, ne sont ni copiables ni déplaçables et ne doivent exister qu’une seule fois par identifiant dans le processus. SetNotifier permet de définir une notification pour les changements de cycle et RestartOperationCycle permet de déclencher un redémarrage du cycle de fonctionnement [SWS_DM_01102]. À l’exception du constructeur sûr pour les threads, toutes les méthodes ainsi que le destructeur ne sont pas sûrs pour les threads et nécessitent une synchronisation côté application en cas d’accès parallèle.

Contexte

La classe ara::diag::OperationCycle implémente le DiagnosticOperationCycleInterface au sein du diagnostic AUTOSAR Adaptive et fournit des fonctions pour la manipulation et le contrôle des cycles de fonctionnement. Elle sert d’interface entre l’application adaptative et le Diagnostic Management afin de surveiller les états des cycles de fonctionnement ou de les réinitialiser de manière ciblée.

Le raccordement au système global s’effectue via un ara::core::InstanceSpecifier, qui est transmis lors de l’appel du constructeur [SWS_DM_00752]. Cet identifiant référence un PortPrototype défini dans le modèle. Le modèle prescrit ici une affectation univoque : un PortPrototype référencé par un DiagnosticOperationCyclePortMapping doit être typé par le DiagnosticOperationCycleInterface [SWS_DM_00752]. En plus du contrôle, la classe interagit via une interface de rappel de type ara::diag::OperationCycle::OperationCycleSetNotifier (définie comme std::function<void(void)>), par laquelle les notifications lors d’un changement du cycle de fonctionnement sont transmises à l’application [SWS_DM_02078], [SWS_DM_00755].

Cycle de vie

La création de ara::diag::OperationCycle s’effectue explicitement en indiquant la spécification d’instance de port via le constructeur OperationCycle(const ara::core::InstanceSpecifier &specifier) [SWS_DM_00752]. Le constructeur est spécifié comme étant sans exception (exception safe) et sûr pour les threads (thread-safe) [SWS_DM_00752].

En matière de sémantique de possession et de copie, la classe est modélisée comme un objet unique strict, représentant une liaison 1:1 fixe avec le port modélisé. La copie et le déplacement sont totalement interdits :

  • Le constructeur de copie est supprimé (delete) afin d’exclure les duplications [SWS_DM_01598].
  • Le constructeur de déplacement est supprimé (delete) [SWS_DM_01599].
  • L’opérateur d’assignation par copie est supprimé (delete) [SWS_DM_01596].
  • L’opérateur d’assignation par déplacement est supprimé (delete) [SWS_DM_01597].

De plus, le framework interdit l’affectation multiple : un InstanceSpecifier ne doit pas être réutilisé pour une instanciation au sein du même processus [SWS_DM_00752]. La libération a lieu dans le destructeur ~OperationCycle() [SWS_DM_00753]. Contrairement au constructeur, le destructeur n’est pas sûr pour les threads (not thread-safe), bien qu’il soit déclaré comme étant sans exception [SWS_DM_00753]. Les autres méthodes de la classe ainsi que le type de rappel ne sont pas non plus sûrs pour les threads [SWS_DM_00755], [SWS_DM_01102], [SWS_DM_02078], de sorte que les accès parallèles à la même instance doivent être synchronisés côté application.

Parcours d'utilisation

Un chemin d’utilisation typique comprend l’instanciation, l’enregistrement optionnel d’un gestionnaire pour les changements de cycle, le déclenchement répété du redémarrage de cycle ainsi que la libération :

  1. Instanciation : l’application crée l’objet OperationCycle en transmettant le InstanceSpecifier correspondant [SWS_DM_00752].
  2. Enregistrer le notificateur : via la méthode SetNotifier, l’application enregistre une fonction de rappel de type OperationCycleSetNotifier [SWS_DM_00755], [SWS_DM_02078]. Cette fonction est appelée lorsque le cycle de fonctionnement change. Un appel successif de SetNotifier écrase entièrement le notificateur précédemment enregistré [SWS_DM_00755].
  3. Redémarrer le cycle de fonctionnement : au moyen de RestartOperationCycle(), l’application déclenche le redémarrage du cycle de fonctionnement [SWS_DM_01102]. Le Diagnostic Management met à jour le cycle et notifie le callback enregistré lors des changements d’état [SWS_DM_00755]. La notification devrait s’effectuer ici de manière asynchrone dans le contexte du Diagnostic Management.
  4. Destruction : lors de l’arrêt du composant logiciel, l’objet est détruit via le destructeur [SWS_DM_00753].

Diagramme de séquence : déroulement de l’instanciation, de l’enregistrement du notificateur et du redémarrage du cycle de fonctionnement. Sources : [SWS_DM_00752], [SWS_DM_00755], [SWS_DM_01102], [SWS_DM_02078].

Scénarios d'erreur

Les erreurs lors de l’initialisation sont signalées par le framework sous forme de violations, étant donné que le constructeur est déclaré comme noexcept [SWS_DM_00752] :

  • InstanceSpecifierMappingIntegrityViolation : le InstanceSpecifier ne peut pas être résolu dans le contexte de l’exécutable ou fait référence à un élément qui n’est pas un PortPrototype [SWS_DM_00752].
  • PortInterfaceMappingViolation : le PortPrototype référencé par DiagnosticOperationCyclePortMapping n’est pas typé par un DiagnosticOperationCycleInterface [SWS_DM_00752].
  • ProcessMappingViolation : une référence d’instance correspondante existe bien, mais aucun processus modélisé correspondant n’a été trouvé pour le processus d’exécution [SWS_DM_00752].
  • InstanceSpecifierAlreadyInUseViolation : le constructeur a été appelé avec un InstanceSpecifier qui est déjà utilisé au sein du processus actuel [SWS_DM_00752].

En fonctionnement normal, les méthodes SetNotifier et RestartOperationCycle renvoient un ara::core::Result<void> [SWS_DM_00755], [SWS_DM_01102]. Pour les deux fonctions, aucun code d’erreur spécifique n’est défini dans la norme (« This function does not specify any standardized errors. ») [SWS_DM_00755], [SWS_DM_01102]. L’utilisation du type Result devrait principalement servir à l’uniformité de la conception d’interface et offrir de l’espace pour des états d’erreur spécifiques à l’implémentation.

              La fonction membre RestartOperationCycle de la classe ara::diag::OperationCycle (fournie via #include "ara/diag/operation_cycle.h") sert à notifier au Diagnostic Management (DM) le redémarrage d'un cycle de fonctionnement [SWS_DM_01102]. Les cycles de fonctionnement tels que les cycles d'allumage (« Ignition on/off »), les cycles d'alimentation (« Power up/power down ») ou les durées de fonctionnement cumulées sont gérés par l'application adaptative et ont une influence directe sur l'octet d'état du DTC UDS ainsi que sur le comportement de la mémoire d'événements selon l'ISO 14229-1 SWS Diagnostics §7.3.4.3 « Operation Cycles Management ».
              

              Appel et sémantique
              

              La fonction est appelée sans paramètre et renvoie un ara::core::Result<void> [SWS_DM_01102]. Si le DM n'est pas encore prêt, au moment de l'appel, à traiter la notification de redémarrage, cette information n'est pas perdue : le DM met temporairement l'événement en mémoire tampon (mise en cache) et évalue le redémarrage du cycle dès que la connexion est rétablie [SWS_DM_01103].
              

              Gestion des erreurs et concurrence
              

              Aucun code d'erreur standardisé n'est spécifié pour RestartOperationCycle [SWS_DM_01102]. La fonction est spécifiée comme sûre vis-à-vis des exceptions (exception safe) et ne lève aucune exception C++ (noexcept) [SWS_DM_01102]. Cependant, l'interface étant explicitement désignée comme non thread-safe (not thread-safe) [SWS_DM_01102], les accès simultanés à la même instance par l'application appelante devraient devoir être synchronisés.

                  La méthode ara::diag::OperationCycle::SetNotifier ([SWS_DM_00755]) sert à enregistrer une fonction de rappel côté application de type OperationCycleSetNotifier. Cette fonction notificatrice est appelée par Diagnostic Management (DM) dès que l'état du cycle de fonctionnement surveillé change ([SWS_DM_00755]). Pour utiliser la méthode, le fichier d'en-tête ara/diag/operation_cycle.h doit être inclus ([SWS_DM_00755]).
                  

                  Si SetNotifier est appelée plusieurs fois sur la même instance de ara::diag::OperationCycle, le module DM écrase complètement la fonction notificatrice précédemment enregistrée ([SWS_DM_00755], [SWS_DM_01358], AUTOSAR_AP_SWS_Diagnostics §7.3.4.4 « Consecutive registration of notifier with OperationCycle::SetNotifier() »). Ce comportement suit le patron de conception cohérent pour les enregistrements de notificateurs dans le DM, tel qu'il est également défini de manière comparable pour ara::diag::CancellationHandler::SetNotifier ([SWS_DM_00615], [SWS_DM_01348]) et ara::diag::Indicator::SetNotifier ([SWS_DM_00745]).
                  

                  L'opération est déclarée comme noexcept et offre une sécurité vis-à-vis des exceptions (exception safe) ([SWS_DM_00755]). La valeur de retour synchrone fournie est ara::core::Result<void> ; aucun code d'erreur standardisé spécifique n'est cependant défini ([SWS_DM_00755]). D'éventuels états d'erreur dans l'objet Result devraient donc être spécifiques au constructeur ou à la plateforme. En ce qui concerne la concurrence, la méthode est spécifiée comme non sûre pour les threads (not thread-safe) ([SWS_DM_00755]), de sorte que les appels parallèles sur une même instance d'objet doivent obligatoirement être synchronisés par l'application.
