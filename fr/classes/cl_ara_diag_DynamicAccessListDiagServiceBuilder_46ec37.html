Contexte

La classe ara::diag::DynamicAccessListDiagServiceBuilder ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15 « Class: DynamicAccessListDiagServiceBuilder ») permet aux applications de définir et de sérialiser pas à pas une liste d'accès dynamique (DynamicAccessList) pour les services de diagnostic. Elle constitue l'outil central pour structurer de manière granulaire les motifs d'accès aux requêtes de diagnostic selon des octets individuels, des suites d'octets, des plages de valeurs ou des caractères génériques (wildcards).

Dans le système global, le builder interagit avec trois partenaires essentiels :

  • Application (Application) : configure les motifs de filtrage souhaités pour les requêtes de diagnostic entrantes via la Fluent API du builder.
  • DiagnosticServiceDynamicAccessList : fournit le point d'entrée via des méthodes de fabrique telles que MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) et accueille la liste d'accès définie.
  • Diagnostic Server Instance : l'instance du serveur de diagnostic évalue au moment de l'exécution les motifs d'octets, caractères génériques et motifs de fin transmis lors du Pattern Matching pour les droits d'accès aux services de diagnostic ([SWS_DM_01220], [SWS_DM_01221]).

Diagramme de contexte : interaction entre l'application, la liste d'accès, le builder et le serveur de diagnostic. Sources : [SWS_DM_01164], [SWS_DM_01166], [SWS_DM_01220].

Cycle de vie

La création d'une instance de builder s'effectue soit directement via le constructeur template en spécifiant une valeur initiale et une référence à un tampon de sérialisation (ara::core::Vector<std::uint8_t>& content) ([SWS_DM_01169]), soit via des fonctions utilitaires telles que MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]).

En matière de possession et de sémantique de copie, la classe impose une utilisation strictement linéaire :

  • Le constructeur de copie ([SWS_DM_01171]) ainsi que l'opérateur d'affectation par copie ([SWS_DM_01172]) sont tous deux déclarés comme supprimés (=delete).
  • L'opérateur d'affectation par déplacement est également supprimé ([SWS_DM_01173]). Une transmission peut s'effectuer exclusivement via le constructeur de déplacement ([SWS_DM_01170]).

Pour la destruction via le destructeur ([SWS_DM_01174]), un invariant strict s'applique : avant la destruction de l'objet, la méthode Build() doit impérativement être appelée ([SWS_DM_01181]) afin de finaliser la création de la liste.

En ce qui concerne la concurrence, le constructeur template et le constructeur de déplacement sont spécifiés comme étant sûrs pour les threads (thread-safe) ([SWS_DM_01169], [SWS_DM_01170]). En revanche, toutes les opérations de formation de motifs (Add, Any, EndsWith, Build) ainsi que le destructeur sont explicitement non sûrs pour les threads (not thread-safe) ([SWS_DM_01174], [SWS_DM_01175], [SWS_DM_01181]) et ne doivent pas être appelés de façon concurrente sur la même instance.

Parcours d'utilisation

Le déroulement typique de la configuration d'un motif d'accès de diagnostic se décompose en trois étapes :

  1. Initialisation : demande d'un builder via DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) avec l'identifiant du service ou directement via le constructeur ([SWS_DM_01169]).
  2. Construction du motif via la Fluent API :
    • Ajout d'octets individuels (Byte / std::uint8_t, [SWS_DM_01167]) via Add(Byte) ([SWS_DM_01175]), de séquences d'octets via Add(ByteString) ([SWS_DM_01168], [SWS_DM_01176]) ou de plages de valeurs via Add(ByteRange) ([SWS_DM_01177]).
    • Insertion de caractères génériques via Any(numberOfBytesToIgnore) ([SWS_DM_01178], [SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §7.1.3 « Adding wildcards to a DynamicAccessList »). Des octets qui seront ignorés lors de la comparaison ultérieure sont ainsi enregistrés dans le motif (par ex. 22F1XX pour les préfixes de DID).
    • Définition optionnelle d'un motif final au moyen de EndsWith(Byte) ([SWS_DM_01179]) ou de EndsWith(ByteRange) ([SWS_DM_01180], [SWS_DM_01221]).
  3. Finalisation : appel de Build() ([SWS_DM_01181]), ce qui finalise la liste.

Diagramme de séquence : configuration et finalisation typiques d'un motif via la Fluent API. Sources : [SWS_DM_01164], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Scénarios d'erreur

L'ensemble de l'interface de ara::diag::DynamicAccessListDiagServiceBuilder opère sans exception avec noexcept et est spécifié comme sûr vis-à-vis des exceptions (exception safe) ([SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181]). Aucune exception C++ n'est levée et aucun état d'erreur n'est retourné via ara::core::Result.

Les situations d'erreur résultent donc principalement de violations de préconditions :

  • Omission de l'appel de finalisation : si le builder est détruit sans que Build() ait été préalablement appelé, cela viole la précondition de [SWS_DM_01181]. Interprétation : dans ce cas, le motif d'accès devrait rester incomplet et ne pas être pris en compte par le serveur de diagnostic comme critère valide.
  • Concurrence non protégée : étant donné que l'ensemble des méthodes d'ajout d'éléments ainsi que Build() sont classifiés comme not thread-safe, un appel simultané depuis plusieurs threads conduit à une corruption de données dans le tampon référencé.

Ce guide repose sur les exigences de la spécification AUTOSAR Adaptive R25-11 pour le module Diagnostics.
