Contexte

La classe ara::com::ComErrorDomain représente le domaine d'erreur standardisé pour les erreurs générales de la gestion de communication (ara::com). Elle englobe les états d'erreur qui peuvent survenir lors d'appels de méthodes de service (ServiceInterface), mais qui ne sont pas définis spécifiquement pour une interface de service individuelle (SWS CommunicationManagement §7.5.22.6 [SWS_CM_11265]).

En tant que dérivation de la classe de base ara::core::ErrorDomain, ComErrorDomain intègre les erreurs de communication dans le modèle d'erreur unifié d'AUTOSAR Adaptive (EXP ARAComAPI §4.7). Les erreurs récupérables (Recoverable Errors) ne sont pas levées sous forme d'exceptions, mais sont renvoyées à l'application via des instances de ara::core::ErrorCode [SWS_CORE_00501] au sein d'un ara::core::Result (EXP ARAComAPI §4.7).

Les principaux partenaires d'interaction sont :

  • Adaptive Application : initie les appels de méthode, reçoit les objets ara::core::Result et évalue le code d'erreur qu'ils contiennent à l'aide du domaine d'erreur (EXP ARAComAPI §4.7).
  • Méthodes de service (classe Method) : l'environnement d'exécution ara::com exécute les appels distants via l'opérateur d'appel de fonction operator() [SWS_CM_00196] et, en cas d'erreur, termine le ara::core::Promise correspondant via SetError [SWS_CORE_00353] avec le domaine ComErrorDomain [SWS_CM_11329] (SWS CommunicationManagement §7.4.2).
  • Distinction par rapport à d'autres domaines : les erreurs générales de communication se distinguent des erreurs de bout en bout spécifiques du domaine ara::com::e2e::ComE2EErrorDomain ainsi que des erreurs applicatives métier (ApApplicationError) (SWS CommunicationManagement §7.5.22.6, EXP ARAComAPI §4.7).

Diagramme de contexte : intégration de ComErrorDomain dans l'architecture d'erreur d'ara::com et d'ara::core. Sources : EXP ARAComAPI §4.7, SWS CommunicationManagement §7.5.22.6.

Cycle de vie

La classe ComErrorDomain est déclarée comme final et hérite publiquement de ara::core::ErrorDomain. Son cycle de vie est soumis à des exigences architecturales fixes :

  • Création : le constructeur par défaut ComErrorDomain() est explicitement supprimé (= delete) [SWS_CM_11330]. Une création directe d'instances par la logique applicative est donc empêchée.
  • Gestion des instances : Interprétation : étant donné que les domaines d'erreur fonctionnent comme des descripteurs globaux par processus dans le standard AUTOSAR Adaptive, la plateforme devrait fournir une instance singleton persistante à laquelle accèdent les structures d'exécution internes et les codes d'erreur.
  • État et propriété : la classe encapsule des informations de type et de traduction purement statiques et ne gère aucun état modifiable d'instances de service individuelles.
  • Concurrence : les fonctions d'information Name() [SWS_CM_11331] et Message() [SWS_CM_11332] sont const, déclarées comme noexcept et spécifiées comme sûres vis-à-vis des exceptions (« exception safe »). Comme elles renvoient des chaînes de caractères constantes, elles peuvent être appelées simultanément depuis n'importe quel thread sans synchronisation supplémentaire.

Parcours d'utilisation

La séquence d'appels typique en cas d'erreur se divise selon les étapes suivantes :

  1. Appel de méthode : une application appelle une méthode de service via operator() de la classe Method [SWS_CM_00196] et reçoit un ara::core::Future en retour.
  2. Détection d'erreur : si une erreur générale survient pendant la communication – par exemple une erreur de transmission ou une erreur applicative non configurée [SWS_CM_00048] –, le Promise correspondant est placé à l'état d'erreur au moyen de SetError [SWS_CORE_00353] (SWS CommunicationManagement §7.4.2).
  3. Attribution du code d'erreur : le ara::core::ErrorCode [SWS_CORE_00501] transmis référence le domaine d'erreur ara::com::ComErrorDomain [SWS_CM_11329] et définit par exemple le code sur ComErrc::kCommunicationFailure (EXP ARAComAPI §2.1, SWS CommunicationManagement §7.4.2 [SWS_CM_10432]).
  4. Évaluation du résultat : l'application vérifie le ara::core::Result renvoyé (EXP ARAComAPI §4.7). Si celui-ci contient un code d'erreur, l'application peut :
    • interroger la désignation du domaine au moyen de Name() [SWS_CM_11331] ([SWS_CORE_90023]),
    • récupérer le message d'erreur en texte clair à des fins de journalisation via Message(errorCode) [SWS_CM_11332],
    • ou lever une exception via ThrowAsException(errorCode) [SWS_CM_11333].

Diagramme de séquence : déroulement du traitement des erreurs lors d'un appel de méthode avec ComErrorDomain. Sources : EXP ARAComAPI §4.7, SWS CommunicationManagement §7.4.2, [SWS_CM_11332], [SWS_CM_11333].

Scénarios d'erreur

La spécification du traitement des erreurs via ComErrorDomain comprend les détails suivants :

  • Énumération des codes d'erreur et alias de type : via l'alias de type Errc [SWS_CM_11336], la classe fournit l'énumération ComErrc, qui définit les codes d'erreur du domaine (SWS CommunicationManagement §8.2). L'alias de type Exception [SWS_CM_11337] renvoie à la classe de base ComException.
  • Codes d'erreur supplémentaires : outre les valeurs d'erreur standardisées telles que ComErrc::kCommunicationFailure [SWS_CM_10432], un fournisseur de pile peut définir dans ce domaine d'autres codes d'erreur spécifiques au fournisseur, qui doivent être pris en compte par l'application (EXP ARAComAPI §4.7).
  • Déclenchement d'exceptions : la méthode ThrowAsException() [SWS_CM_11333] crée un objet ara::com::ComException à partir d'un ara::core::ErrorCode transmis et le lève (noexcept(false)). Si les exceptions C++ sont désactivées dans le compilateur, cette fonction ne participe pas à la résolution de surcharge conformément à [SWS_CORE_10304] [SWS_CM_11333].
  • Classification du traitement des erreurs : l'API ara::com distingue strictement les erreurs récupérables (Recoverable Errors), transmises de manière déterministe via ara::core::Result, des erreurs de programmation graves (Violations ou Corruptions), pour lesquelles des exceptions sont utilisées (EXP ARAComAPI §4.7).

<h4>Contexte</h4>
<p>La classe <code>ara::com::ComErrorDomain</code> représente le domaine d'erreur standardisé pour les erreurs générales de la gestion de communication (<code>ara::com</code>). Elle englobe les états d'erreur qui peuvent survenir lors d'appels de méthodes de service (<code>ServiceInterface</code>), mais qui ne sont pas définis spécifiquement pour une interface de service individuelle (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=307">SWS CommunicationManagement §7.5.22.6</a> <a class="spec-record-ref" data-req="SWS_CM_11265" href="../spec/record.html?id=SWS_CM_11265">[SWS_CM_11265]</a>).</p>
<p>En tant que dérivation de la classe de base <code>ara::core::ErrorDomain</code>, <code>ComErrorDomain</code> intègre les erreurs de communication dans le modèle d'erreur unifié d'AUTOSAR Adaptive (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>). Les erreurs récupérables (Recoverable Errors) ne sont pas levées sous forme d'exceptions, mais sont renvoyées à l'application via des instances de <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="SWS_CORE_00501" href="../spec/record.html?id=SWS_CORE_00501">[SWS_CORE_00501]</a> au sein d'un <code>ara::core::Result</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</p>
<p>Les principaux partenaires d'interaction sont :</p>
<ul>
<li><strong>Adaptive Application</strong> : initie les appels de méthode, reçoit les objets <code>ara::core::Result</code> et évalue le code d'erreur qu'ils contiennent à l'aide du domaine d'erreur (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
<li><strong>Méthodes de service (classe <code>Method</code>)</strong> : l'environnement d'exécution <code>ara::com</code> exécute les appels distants via l'opérateur d'appel de fonction <code>operator()</code> <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a> et, en cas d'erreur, termine le <code>ara::core::Promise</code> correspondant via <code>SetError</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> avec le domaine <code>ComErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_11329" href="../spec/record.html?id=SWS_CM_11329">[SWS_CM_11329]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a>).</li>
<li><strong>Distinction par rapport à d'autres domaines</strong> : les erreurs générales de communication se distinguent des erreurs de bout en bout spécifiques du domaine <code>ara::com::e2e::ComE2EErrorDomain</code> ainsi que des erreurs applicatives métier (<code>ApApplicationError</code>) (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=307">SWS CommunicationManagement §7.5.22.6</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
</ul>

<h4>Cycle de vie</h4>
<p>La classe <code>ComErrorDomain</code> est déclarée comme <code>final</code> et hérite publiquement de <code>ara::core::ErrorDomain</code>. Son cycle de vie est soumis à des exigences architecturales fixes :</p>
<ul>
<li><strong>Création</strong> : le constructeur par défaut <code>ComErrorDomain()</code> est explicitement supprimé (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_CM_11330" href="../spec/record.html?id=SWS_CM_11330">[SWS_CM_11330]</a>. Une création directe d'instances par la logique applicative est donc empêchée.</li>
<li><strong>Gestion des instances</strong> : Interprétation : étant donné que les domaines d'erreur fonctionnent comme des descripteurs globaux par processus dans le standard AUTOSAR Adaptive, la plateforme devrait fournir une instance singleton persistante à laquelle accèdent les structures d'exécution internes et les codes d'erreur.</li>
<li><strong>État et propriété</strong> : la classe encapsule des informations de type et de traduction purement statiques et ne gère aucun état modifiable d'instances de service individuelles.</li>
<li><strong>Concurrence</strong> : les fonctions d'information <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> et <code>Message()</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a> sont <code>const</code>, déclarées comme <code>noexcept</code> et spécifiées comme sûres vis-à-vis des exceptions (« exception safe »). Comme elles renvoient des chaînes de caractères constantes, elles peuvent être appelées simultanément depuis n'importe quel thread sans synchronisation supplémentaire.</li>
</ul>

<h4>Parcours d'utilisation</h4>
<p>La séquence d'appels typique en cas d'erreur se divise selon les étapes suivantes :</p>
<ol>
<li><strong>Appel de méthode</strong> : une application appelle une méthode de service via <code>operator()</code> de la classe <code>Method</code> <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a> et reçoit un <code>ara::core::Future</code> en retour.</li>
<li><strong>Détection d'erreur</strong> : si une erreur générale survient pendant la communication – par exemple une erreur de transmission ou une erreur applicative non configurée <a class="spec-record-ref" data-req="SWS_CM_00048" href="../spec/record.html?id=SWS_CM_00048">[SWS_CM_00048]</a> –, le <code>Promise</code> correspondant est placé à l'état d'erreur au moyen de <code>SetError</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a>).</li>
<li><strong>Attribution du code d'erreur</strong> : le <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="SWS_CORE_00501" href="../spec/record.html?id=SWS_CORE_00501">[SWS_CORE_00501]</a> transmis référence le domaine d'erreur <code>ara::com::ComErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_11329" href="../spec/record.html?id=SWS_CM_11329">[SWS_CM_11329]</a> et définit par exemple le code sur <code>ComErrc::kCommunicationFailure</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=9">EXP ARAComAPI §2.1</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>).</li>
<li><strong>Évaluation du résultat</strong> : l'application vérifie le <code>ara::core::Result</code> renvoyé (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>). Si celui-ci contient un code d'erreur, l'application peut :
<ul>
<li>interroger la désignation du domaine au moyen de <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> (<a class="spec-record-ref" data-req="SWS_CORE_90023" href="../spec/record.html?id=SWS_CORE_90023">[SWS_CORE_90023]</a>),</li>
<li>récupérer le message d'erreur en texte clair à des fins de journalisation via <code>Message(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a>,</li>
<li>ou lever une exception via <code>ThrowAsException(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a>.</li>
</ul>
</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>La spécification du traitement des erreurs via <code>ComErrorDomain</code> comprend les détails suivants :</p>
<ul>
<li><strong>Énumération des codes d'erreur et alias de type</strong> : via l'alias de type <code>Errc</code> <a class="spec-record-ref" data-req="SWS_CM_11336" href="../spec/record.html?id=SWS_CM_11336">[SWS_CM_11336]</a>, la classe fournit l'énumération <code>ComErrc</code>, qui définit les codes d'erreur du domaine (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=439">SWS CommunicationManagement §8.2</a>). L'alias de type <code>Exception</code> <a class="spec-record-ref" data-req="SWS_CM_11337" href="../spec/record.html?id=SWS_CM_11337">[SWS_CM_11337]</a> renvoie à la classe de base <code>ComException</code>.</li>
<li><strong>Codes d'erreur supplémentaires</strong> : outre les valeurs d'erreur standardisées telles que <code>ComErrc::kCommunicationFailure</code> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>, un fournisseur de pile peut définir dans ce domaine d'autres codes d'erreur spécifiques au fournisseur, qui doivent être pris en compte par l'application (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
<li><strong>Déclenchement d'exceptions</strong> : la méthode <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a> crée un objet <code>ara::com::ComException</code> à partir d'un <code>ara::core::ErrorCode</code> transmis et le lève (<code>noexcept(false)</code>). Si les exceptions C++ sont désactivées dans le compilateur, cette fonction ne participe pas à la résolution de surcharge conformément à <a class="spec-record-ref" data-req="SWS_CORE_10304" href="../spec/record.html?id=SWS_CORE_10304">[SWS_CORE_10304]</a> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a>.</li>
<li><strong>Classification du traitement des erreurs</strong> : l'API <code>ara::com</code> distingue strictement les erreurs récupérables (Recoverable Errors), transmises de manière déterministe via <code>ara::core::Result</code>, des erreurs de programmation graves (Violations ou Corruptions), pour lesquelles des exceptions sont utilisées (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
</ul>
