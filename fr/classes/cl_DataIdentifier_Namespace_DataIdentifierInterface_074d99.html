Contexte

La classe C++ <DataIdentifierInterface> sert, dans le module diag de l'AUTOSAR Adaptive Platform, d'interface de base côté serveur pour les identifiants de données de diagnostic (Data Identifier, DID) conformément à l'ISO 14229-1 (UDS). L'interface définit la passerelle standardisée entre la gestion du diagnostic de la plateforme et les routines spécifiques à l'application destinées à fournir ou à mettre à jour des données de diagnostic.

L'interaction implique généralement trois composants clés :

  • Diagnostic Manager (DM) : reçoit les requêtes de service UDS (telles que le service 0x22 ReadDataByIdentifier ou le service 0x2E WriteDataByIdentifier) de testeurs de diagnostic externes et les transmet à l'instance d'interface enregistrée appropriée ([SWS_DM_00599], [SWS_DM_00600]).
  • Gestionnaire d'application : une classe d'application Adaptive concrète hérite de <DataIdentifierInterface> et implémente les méthodes virtuelles pures Read ([SWS_DM_00640]) ainsi que Write ([SWS_DM_00598]).
  • Testeur de diagnostic (client) : envoie des requêtes UDS au calculateur du véhicule et reçoit les réponses agrégées par le Diagnostic Manager.

Diagramme de contexte : interaction entre le testeur de diagnostic, le Diagnostic Manager et <DataIdentifierInterface>. Sources : [SWS_DM_00599], [SWS_DM_00600], [SWS_DM_00640], [SWS_DM_00598]

Cycle de vie

La création d'une instance s'effectue via le constructeur paramétré en passant un ara::core::InstanceSpecifier ainsi que le mode ara::diag::ConcurrencyType ([SWS_DM_00585]). Par le biais du type de concurrence, l'appelant spécifie si l'implémentation est conçue pour être sûre vis-à-vis des accès concurrents (kConcurrent) ou non sûre vis-à-vis des accès concurrents (kNotConcurrent) ([SWS_DM_00585]).

Les instances de <DataIdentifierInterface> possèdent une identité unique et ne doivent être ni copiées ni déplacées. Par conséquent, le constructeur de copie ([SWS_DM_01665]) et le constructeur de déplacement ([SWS_DM_01666]) ainsi que les opérateurs d'affectation associés ([SWS_DM_01663], [SWS_DM_01664]) sont supprimés (=delete).

Concernant les états de service, la classe distingue deux phases :

  • Inactif (non proposé) : après la construction, l'objet est présent localement, mais n'accepte aucune requête de diagnostic.
  • Actif (proposé) : seul l'appel explicite de la méthode Offer() ([SWS_DM_00599]) active le transfert des requêtes par le Diagnostic Manager vers cette instance.
  • Désactivé : l'appel de StopOffer() ([SWS_DM_00600]) interrompt le transfert, et l'instance repasse à l'état inactif.

La destruction s'effectue via le destructeur virtuel ~<DataIdentifierInterface>() ([SWS_DM_00586]). Celui-ci n'est ni sûr pour les threads ni sûr vis-à-vis des exceptions ; avant la destruction, il convient vraisemblablement d'appeler StopOffer() afin de terminer de manière ordonnée les transferts en attente dans le Diagnostic Manager.

Parcours d'utilisation

Le déroulement standard pour la mise à disposition et le traitement des requêtes de lecture de diagnostic suit une séquence d'étapes définie :

  1. Construction : l'application instancie la classe DID dérivée et la lie au prototype de port modélisé via le instanceSpec ([SWS_DM_00585]).
  2. Mise à disposition : l'application appelle Offer() ([SWS_DM_00599]). La méthode renvoie un ara::core::Result<void> qui indique le succès de l'enregistrement auprès du Diagnostic Manager.
  3. Traitement : si le Diagnostic Manager reçoit une requête de lecture UDS pour ce DID, il délègue l'appel à la méthode virtuelle Read(metaInfo, cancellationHandler) ([SWS_DM_00640]). Pour les requêtes d'écriture, le DM appelle de manière analogue Write(..., metaInfo, cancellationHandler) ([SWS_DM_00598]).
  4. Gestion de l'annulation et retour : pendant l'exécution asynchrone, l'implémentation peut vérifier via cancellationHandler.IsCanceled() si la conversation a été annulée, ou enregistrer un notificateur via cancellationHandler.SetNotifier(...) ([SWS_DM_00640], [SWS_DM_00598]). Le résultat est fourni sous la forme d'un ara::core::Future qui, en cas de succès, contient l'objet de sortie généré <DataIdentifier>ReadOutput avec les arguments de sortie ([SWS_DM_00579], [SWS_DM_80013]).
  5. Désenregistrement : lorsque le service n'est plus nécessaire, l'application appelle StopOffer() ([SWS_DM_00600]).

Diagramme de séquence : déroulement d'une requête de lecture UDS via Offer, Read et StopOffer. Sources : [SWS_DM_00599], [SWS_DM_00640], [SWS_DM_00600]

Scénarios d'erreur

Des erreurs peuvent survenir lors de l'initialisation, lors de la publication du service ainsi que pendant le traitement des méthodes :

  • Violations lors de la construction : si la résolution ou la liaison du InstanceSpecifier dans le modèle échoue, le framework lève des violations définies ([SWS_DM_00585]) :
    • InstanceSpecifierMappingIntegrityViolation : l'identifiant ne peut pas être résolu dans le contexte de l'exécutable ou ne référence aucun PortPrototype.
    • PortInterfaceMappingViolation : un PortPrototype typé par DiagnosticDataIdentifierInterface n'est pas référencé par un DiagnosticDataPortMapping.
    • ProcessMappingViolation : aucun processus modélisé correspondant n'existe à l'exécution pour la InstanceRef présente.
    • InstanceSpecifierAlreadyInUseViolation : le InstanceSpecifier est déjà utilisé au sein de ce processus par un autre appel de constructeur.
  • Erreur lors de l'Offer : si le service est déjà proposé, Offer() échoue et renvoie un ara::core::Result avec le code d'erreur ara::diag::DiagOfferErrc::kAlreadyOffered ([SWS_DM_00599]).
  • Erreurs de traitement et UDS : si une requête de lecture ou d'écriture ne peut pas être effectuée avec succès, le gestionnaire définit le ara::core::Future renvoyé sur un Negative Response Code (NRC) correspondant via ara::diag::DiagUdsNrcErrc selon l'ISO 14229-1 ou sur un ApApplicationError ([SWS_DM_00640], [SWS_DM_00598]).

Ce guide de classe est basé sur la spécification AUTOSAR Adaptive Platform R25-11 (module diag) et résume le contexte, le cycle de vie, les modèles d'interaction et les scénarios d'erreur.
