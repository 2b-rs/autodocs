Contexte

La classe template ara::core::Promise<T, E> fournit la variante spécifique à AUTOSAR Adaptive de la classe standard C++ std::promise. Sa tâche principale consiste à former l'extrémité d'écriture d'un canal de synchronisation asynchrone et à gérer un état partagé (Shared State). Via ce Shared State, un chemin d'exécution producteur transmet le résultat d'un calcul asynchrone – soit une valeur de type T, soit une erreur de type E, soit un ara::core::Result<T, E> cohérent – à son homologue en lecture ara::core::Future<T, E>, qui est obtenu via get_future() [SWS_CORE_00344].

Une prescription centrale d'AUTOSAR relative à la signature du template est la valeur par défaut E = ara::core::ErrorCode. Si l'instanciation s'en écarte (E != ara::core::ErrorCode), la spécification exige impérativement une erreur de compilation. Vraisemblablement, cette règle sert à appliquer strictement le modèle d'erreur standardisé de l'Adaptive Platform, afin que les interfaces asynchrones puissent coopérer de manière uniforme avec ara::core::Result. Trois entités participent généralement à cette collaboration : la partie du programme productrice en tant que propriétaire du Promise, le Shared State géré pour le couplage d'état entre threads, et un ou plusieurs consommateurs qui reçoivent le résultat asynchrone via ara::core::Future.

Cycle de vie

Le cycle de vie de ara::core::Promise suit une sémantique stricte « move-only » et contrôle l'existence du Shared State sous-jacent :

  • Création : Le constructeur par défaut Promise() construit une instance avec un nouveau Shared State encore non satisfait [SWS_CORE_00341]. Il est garanti sans exception en tant que noexcept et spécifié comme étant thread-safe [SWS_CORE_00341].
  • Protection contre la copie et transfert de propriété : Le constructeur de copie [SWS_CORE_00350] et l'opérateur d'affectation par copie [SWS_CORE_00351] sont explicitement supprimés (= delete). Un transfert de propriété n'est possible qu'au moyen d'opérations de déplacement (move). Le constructeur de déplacement reprend le Shared State de l'instance source et est noexcept, mais n'est pas thread-safe [SWS_CORE_00342]. L'opérateur d'affectation par déplacement abandonne tout Shared State précédemment détenu (abandons any shared state) et transfère l'état de l'autre instance de manière analogue à un swap consécutif [SWS_CORE_00343]. Deux instances peuvent en outre échanger leur état via swap() [SWS_CORE_00352].
  • Couplage de Future : Via get_future(), exactement une instance de ara::core::Future<T, E> est associée au même Shared State [SWS_CORE_00344]. Comme un seul Future ne peut exister par Promise, cet appel n'est autorisé qu'une seule fois [SWS_CORE_00344].
  • Transition d'état vers Ready : L'apport d'une valeur via set_value() [SWS_CORE_00345], [SWS_CORE_00346], d'une erreur via SetError() [SWS_CORE_00353], [SWS_CORE_00354] ou d'un résultat global via SetResult() [SWS_CORE_00355], [SWS_CORE_00356] fait basculer de manière irréversible le Shared State vers l'état ready. Toutes ces méthodes de satisfaction sont déclarées thread-safe.
  • Destruction : Le destructeur ~Promise() quitte et abandonne le Shared State (abandons any shared state) [SWS_CORE_00349]. Interprétation : si la destruction a lieu avant la définition d'une valeur ou d'une erreur, le Shared State orphelin devrait, de manière analogue au comportement de std::promise, être abandonné pour les Futures en attente.

Parcours d'utilisation

L'ordre d'appel typique pour la transmission asynchrone de valeurs ou d'erreurs comprend les étapes suivantes :

  1. Création : Le producteur instancie ara::core::Promise<T, E> via le constructeur par défaut [SWS_CORE_00341].
  2. Connexion du canal : Avant de confier la tâche asynchrone à un thread d'arrière-plan, le producteur appelle get_future() [SWS_CORE_00344] et transmet l'instance de ara::core::Future résultante au consommateur.
  3. Traitement asynchrone : Le producteur exécute le calcul ou l'opération d'E/S. Le consommateur peut continuer à travailler en parallèle ou attendre le Future.
  4. Définition du résultat : Une fois l'opération terminée, le producteur dépose le résultat dans le Shared State. Selon l'issue, il choisit :
    • Valeur de succès : set_value() par copie [SWS_CORE_00345] ou déplacement [SWS_CORE_00346].
    • État d'erreur : SetError() par déplacement [SWS_CORE_00353] ou copie [SWS_CORE_00354].
    • Objet Result existant : SetResult() par copie [SWS_CORE_00355] ou déplacement [SWS_CORE_00356].
  5. Libération : Par cette définition, le Shared State est marqué comme prêt ; le consommateur lit la valeur. Le Promise est détruit lorsqu'il quitte la portée [SWS_CORE_00349].

Diagramme de séquence : ordre d'appel et d'interaction typique pour la transmission asynchrone de valeurs ou d'erreurs. Sources : [SWS_CORE_00341], [SWS_CORE_00344], [SWS_CORE_00345], [SWS_CORE_00353], [SWS_CORE_00355].

Scénarios d'erreur

La spécification définit des conditions de violation (Violations) fixes pour les appels non autorisés ainsi que des exigences relatives à la sécurité face aux exceptions :

  • Récupération multiple de Future : Si get_future() est appelé plus d'une fois pour le même Shared State, la violation IsoStdFutureErrcFutureAlreadyRetrievedViolation se produit [SWS_CORE_00344].
  • Opérations sans Shared State : Si *this ne possède pas de Shared State (par exemple après une opération de déplacement), les appels de méthode entraînent des violations documentées :
    • get_future() signale IsoStdFutureErrcNoStateViolation [SWS_CORE_00344].
    • set_value(), SetError() et SetResult() déclenchent PromiseNoSharedStateToSetViolation ([SWS_CORE_00345], [SWS_CORE_00346], [SWS_CORE_00353], [SWS_CORE_00354], [SWS_CORE_00355], [SWS_CORE_00356]).
  • Satisfaction multiple (Double Satisfaction) : Si une valeur, une erreur ou un Result a déjà été déposé dans le Shared State, tout appel supplémentaire de set_value(), SetError() ou SetResult() entraîne la violation IsoStdFutureErrcPromiseAlreadySatisfiedViolation ([SWS_CORE_00345], [SWS_CORE_00346], [SWS_CORE_00353], [SWS_CORE_00354], [SWS_CORE_00355], [SWS_CORE_00356]).
  • Erreur de compilation en cas de type d'erreur divergent : Si le template de classe est instancié avec un type pour lequel E != ara::core::ErrorCode s'applique, le build s'interrompt obligatoirement avec une Compile Error.
  • Sécurité conditionnelle face aux exceptions : Les constructeurs, le destructeur, l'affectation, Move, Swap et get_future() sont sans restriction noexcept et sûrs face aux exceptions ([SWS_CORE_00341], [SWS_CORE_00342], [SWS_CORE_00343], [SWS_CORE_00344], [SWS_CORE_00349], [SWS_CORE_00352]). Les méthodes set_value(), SetError() et SetResult() sont en revanche conditionnellement sûres face aux exceptions (conditionally exception safe) ; leur propriété noexcept dépend du fait que les constructeurs de copie ou de déplacement de T et E soient déclarés comme ne levant pas d'exception (std::is_nothrow_*_constructible) ([SWS_CORE_00345], [SWS_CORE_00346], [SWS_CORE_00353], [SWS_CORE_00354], [SWS_CORE_00355], [SWS_CORE_00356]).

<h4>Contexte</h4>
<p>La classe template <code>ara::core::Promise&lt;T, E&gt;</code> fournit la variante spécifique à AUTOSAR Adaptive de la classe standard C++ <code>std::promise</code>. Sa tâche principale consiste à former l'extrémité d'écriture d'un canal de synchronisation asynchrone et à gérer un état partagé (Shared State). Via ce Shared State, un chemin d'exécution producteur transmet le résultat d'un calcul asynchrone – soit une valeur de type <code>T</code>, soit une erreur de type <code>E</code>, soit un <code>ara::core::Result&lt;T, E&gt;</code> cohérent – à son homologue en lecture <code>ara::core::Future&lt;T, E&gt;</code>, qui est obtenu via <code>get_future()</code> <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>.</p>
<p>Une prescription centrale d'AUTOSAR relative à la signature du template est la valeur par défaut <code>E = ara::core::ErrorCode</code>. Si l'instanciation s'en écarte (<code>E != ara::core::ErrorCode</code>), la spécification exige impérativement une erreur de compilation. Vraisemblablement, cette règle sert à appliquer strictement le modèle d'erreur standardisé de l'Adaptive Platform, afin que les interfaces asynchrones puissent coopérer de manière uniforme avec <code>ara::core::Result</code>. Trois entités participent généralement à cette collaboration : la partie du programme productrice en tant que propriétaire du <code>Promise</code>, le Shared State géré pour le couplage d'état entre threads, et un ou plusieurs consommateurs qui reçoivent le résultat asynchrone via <code>ara::core::Future</code>.</p>

<h4>Cycle de vie</h4>
<p>Le cycle de vie de <code>ara::core::Promise</code> suit une sémantique stricte « move-only » et contrôle l'existence du Shared State sous-jacent :</p>
<ul>
<li><strong>Création :</strong> Le constructeur par défaut <code>Promise()</code> construit une instance avec un nouveau Shared State encore non satisfait <a class="spec-record-ref" data-req="SWS_CORE_00341" href="../spec/record.html?id=SWS_CORE_00341">[SWS_CORE_00341]</a>. Il est garanti sans exception en tant que <code>noexcept</code> et spécifié comme étant thread-safe <a class="spec-record-ref" data-req="SWS_CORE_00341" href="../spec/record.html?id=SWS_CORE_00341">[SWS_CORE_00341]</a>.</li>
<li><strong>Protection contre la copie et transfert de propriété :</strong> Le constructeur de copie <a class="spec-record-ref" data-req="SWS_CORE_00350" href="../spec/record.html?id=SWS_CORE_00350">[SWS_CORE_00350]</a> et l'opérateur d'affectation par copie <a class="spec-record-ref" data-req="SWS_CORE_00351" href="../spec/record.html?id=SWS_CORE_00351">[SWS_CORE_00351]</a> sont explicitement supprimés (<code>= delete</code>). Un transfert de propriété n'est possible qu'au moyen d'opérations de déplacement (move). Le constructeur de déplacement reprend le Shared State de l'instance source et est <code>noexcept</code>, mais n'est pas thread-safe <a class="spec-record-ref" data-req="SWS_CORE_00342" href="../spec/record.html?id=SWS_CORE_00342">[SWS_CORE_00342]</a>. L'opérateur d'affectation par déplacement abandonne tout Shared State précédemment détenu (<em>abandons any shared state</em>) et transfère l'état de l'autre instance de manière analogue à un <code>swap</code> consécutif <a class="spec-record-ref" data-req="SWS_CORE_00343" href="../spec/record.html?id=SWS_CORE_00343">[SWS_CORE_00343]</a>. Deux instances peuvent en outre échanger leur état via <code>swap()</code> <a class="spec-record-ref" data-req="SWS_CORE_00352" href="../spec/record.html?id=SWS_CORE_00352">[SWS_CORE_00352]</a>.</li>
<li><strong>Couplage de Future :</strong> Via <code>get_future()</code>, exactement une instance de <code>ara::core::Future&lt;T, E&gt;</code> est associée au même Shared State <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>. Comme un seul Future ne peut exister par Promise, cet appel n'est autorisé qu'une seule fois <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>.</li>
<li><strong>Transition d'état vers Ready :</strong> L'apport d'une valeur via <code>set_value()</code> <a class="spec-record-ref" data-req="SWS_CORE_00345" href="../spec/record.html?id=SWS_CORE_00345">[SWS_CORE_00345]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00346" href="../spec/record.html?id=SWS_CORE_00346">[SWS_CORE_00346]</a>, d'une erreur via <code>SetError()</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00354" href="../spec/record.html?id=SWS_CORE_00354">[SWS_CORE_00354]</a> ou d'un résultat global via <code>SetResult()</code> <a class="spec-record-ref" data-req="SWS_CORE_00355" href="../spec/record.html?id=SWS_CORE_00355">[SWS_CORE_00355]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00356" href="../spec/record.html?id=SWS_CORE_00356">[SWS_CORE_00356]</a> fait basculer de manière irréversible le Shared State vers l'état <em>ready</em>. Toutes ces méthodes de satisfaction sont déclarées thread-safe.</li>
<li><strong>Destruction :</strong> Le destructeur <code>~Promise()</code> quitte et abandonne le Shared State (<em>abandons any shared state</em>) <a class="spec-record-ref" data-req="SWS_CORE_00349" href="../spec/record.html?id=SWS_CORE_00349">[SWS_CORE_00349]</a>. Interprétation : si la destruction a lieu avant la définition d'une valeur ou d'une erreur, le Shared State orphelin devrait, de manière analogue au comportement de <code>std::promise</code>, être abandonné pour les Futures en attente.</li>
</ul>

<h4>Parcours d'utilisation</h4>
<p>L'ordre d'appel typique pour la transmission asynchrone de valeurs ou d'erreurs comprend les étapes suivantes :</p>
<ol>
<li><strong>Création :</strong> Le producteur instancie <code>ara::core::Promise&lt;T, E&gt;</code> via le constructeur par défaut <a class="spec-record-ref" data-req="SWS_CORE_00341" href="../spec/record.html?id=SWS_CORE_00341">[SWS_CORE_00341]</a>.</li>
<li><strong>Connexion du canal :</strong> Avant de confier la tâche asynchrone à un thread d'arrière-plan, le producteur appelle <code>get_future()</code> <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a> et transmet l'instance de <code>ara::core::Future</code> résultante au consommateur.</li>
<li><strong>Traitement asynchrone :</strong> Le producteur exécute le calcul ou l'opération d'E/S. Le consommateur peut continuer à travailler en parallèle ou attendre le <code>Future</code>.</li>
<li><strong>Définition du résultat :</strong> Une fois l'opération terminée, le producteur dépose le résultat dans le Shared State. Selon l'issue, il choisit :
<ul>
<li>Valeur de succès : <code>set_value()</code> par copie <a class="spec-record-ref" data-req="SWS_CORE_00345" href="../spec/record.html?id=SWS_CORE_00345">[SWS_CORE_00345]</a> ou déplacement <a class="spec-record-ref" data-req="SWS_CORE_00346" href="../spec/record.html?id=SWS_CORE_00346">[SWS_CORE_00346]</a>.</li>
<li>État d'erreur : <code>SetError()</code> par déplacement <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> ou copie <a class="spec-record-ref" data-req="SWS_CORE_00354" href="../spec/record.html?id=SWS_CORE_00354">[SWS_CORE_00354]</a>.</li>
<li>Objet Result existant : <code>SetResult()</code> par copie <a class="spec-record-ref" data-req="SWS_CORE_00355" href="../spec/record.html?id=SWS_CORE_00355">[SWS_CORE_00355]</a> ou déplacement <a class="spec-record-ref" data-req="SWS_CORE_00356" href="../spec/record.html?id=SWS_CORE_00356">[SWS_CORE_00356]</a>.</li>
</ul>
</li>
<li><strong>Libération :</strong> Par cette définition, le Shared State est marqué comme prêt ; le consommateur lit la valeur. Le <code>Promise</code> est détruit lorsqu'il quitte la portée <a class="spec-record-ref" data-req="SWS_CORE_00349" href="../spec/record.html?id=SWS_CORE_00349">[SWS_CORE_00349]</a>.</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>La spécification définit des conditions de violation (Violations) fixes pour les appels non autorisés ainsi que des exigences relatives à la sécurité face aux exceptions :</p>
<ul>
<li><strong>Récupération multiple de Future :</strong> Si <code>get_future()</code> est appelé plus d'une fois pour le même Shared State, la violation <code>IsoStdFutureErrcFutureAlreadyRetrievedViolation</code> se produit <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>.</li>
<li><strong>Opérations sans Shared State :</strong> Si <code>*this</code> ne possède pas de Shared State (par exemple après une opération de déplacement), les appels de méthode entraînent des violations documentées :
<ul>
<li><code>get_future()</code> signale <code>IsoStdFutureErrcNoStateViolation</code> <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>.</li>
<li><code>set_value()</code>, <code>SetError()</code> et <code>SetResult()</code> déclenchent <code>PromiseNoSharedStateToSetViolation</code> (<a class="spec-record-ref" data-req="SWS_CORE_00345" href="../spec/record.html?id=SWS_CORE_00345">[SWS_CORE_00345]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00346" href="../spec/record.html?id=SWS_CORE_00346">[SWS_CORE_00346]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00354" href="../spec/record.html?id=SWS_CORE_00354">[SWS_CORE_00354]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00355" href="../spec/record.html?id=SWS_CORE_00355">[SWS_CORE_00355]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00356" href="../spec/record.html?id=SWS_CORE_00356">[SWS_CORE_00356]</a>).</li>
</ul>
</li>
<li><strong>Satisfaction multiple (Double Satisfaction) :</strong> Si une valeur, une erreur ou un Result a déjà été déposé dans le Shared State, tout appel supplémentaire de <code>set_value()</code>, <code>SetError()</code> ou <code>SetResult()</code> entraîne la violation <code>IsoStdFutureErrcPromiseAlreadySatisfiedViolation</code> (<a class="spec-record-ref" data-req="SWS_CORE_00345" href="../spec/record.html?id=SWS_CORE_00345">[SWS_CORE_00345]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00346" href="../spec/record.html?id=SWS_CORE_00346">[SWS_CORE_00346]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00354" href="../spec/record.html?id=SWS_CORE_00354">[SWS_CORE_00354]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00355" href="../spec/record.html?id=SWS_CORE_00355">[SWS_CORE_00355]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00356" href="../spec/record.html?id=SWS_CORE_00356">[SWS_CORE_00356]</a>).</li>
<li><strong>Erreur de compilation en cas de type d'erreur divergent :</strong> Si le template de classe est instancié avec un type pour lequel <code>E != ara::core::ErrorCode</code> s'applique, le build s'interrompt obligatoirement avec une Compile Error.</li>
<li><strong>Sécurité conditionnelle face aux exceptions :</strong> Les constructeurs, le destructeur, l'affectation, Move, Swap et <code>get_future()</code> sont sans restriction <code>noexcept</code> et sûrs face aux exceptions (<a class="spec-record-ref" data-req="SWS_CORE_00341" href="../spec/record.html?id=SWS_CORE_00341">[SWS_CORE_00341]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00342" href="../spec/record.html?id=SWS_CORE_00342">[SWS_CORE_00342]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00343" href="../spec/record.html?id=SWS_CORE_00343">[SWS_CORE_00343]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00344" href="../spec/record.html?id=SWS_CORE_00344">[SWS_CORE_00344]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00349" href="../spec/record.html?id=SWS_CORE_00349">[SWS_CORE_00349]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00352" href="../spec/record.html?id=SWS_CORE_00352">[SWS_CORE_00352]</a>). Les méthodes <code>set_value()</code>, <code>SetError()</code> et <code>SetResult()</code> sont en revanche conditionnellement sûres face aux exceptions (<em>conditionally exception safe</em>) ; leur propriété <code>noexcept</code> dépend du fait que les constructeurs de copie ou de déplacement de <code>T</code> et <code>E</code> soient déclarés comme ne levant pas d'exception (<code>std::is_nothrow_*_constructible</code>) (<a class="spec-record-ref" data-req="SWS_CORE_00345" href="../spec/record.html?id=SWS_CORE_00345">[SWS_CORE_00345]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00346" href="../spec/record.html?id=SWS_CORE_00346">[SWS_CORE_00346]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00354" href="../spec/record.html?id=SWS_CORE_00354">[SWS_CORE_00354]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00355" href="../spec/record.html?id=SWS_CORE_00355">[SWS_CORE_00355]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00356" href="../spec/record.html?id=SWS_CORE_00356">[SWS_CORE_00356]</a>).</li>
</ul>
