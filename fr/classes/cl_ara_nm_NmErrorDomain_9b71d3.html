Contexte

La classe ara::nm::NmErrorDomain définit le domaine d'erreur officiel pour le cluster fonctionnel Network Management (nm) au sein d'AUTOSAR Adaptive Platform [SWS_ANM_01101]. Conformément au modèle de traitement des erreurs à l'échelle de la plateforme, elle dérive de la classe de base ara::core::ErrorDomain et est déclarée comme final, ce qui clôt de manière définitive la hiérarchie d'héritage à cet endroit [SWS_ANM_01101].

Sa responsabilité principale consiste à intégrer de manière typée les états d'erreur spécifiques à la gestion de réseau dans le système d'erreur unifié d'AUTOSAR Adaptive. Pour cela, la classe fournit deux alias de types centraux : Errc référence l'énumération NmErrc avec les codes d'erreur concrets [SWS_ANM_01103], tandis que Exception est lié à la classe d'exception spécifique au type NmException [SWS_ANM_01104]. Le partenaire d'interaction le plus important dans le système d'exécution est ara::core::ErrorCode [SWS_ANM_01108], qui encapsule les valeurs d'erreur et délègue leur représentation textuelle ainsi que le traitement des exceptions à l'instance compétente de NmErrorDomain.

Cycle de vie

L'instanciation s'effectue via le constructeur par défaut NmErrorDomain() [SWS_ANM_01105]. Celui-ci est défini comme noexcept et exclut ainsi totalement les exceptions pendant la construction [SWS_ANM_01105]. La justification de la spécification prouve en outre expressément que le processus de construction est thread-safe [SWS_ANM_01105].

En ce qui concerne les relations de propriété et la gestion des instances, un domaine d'erreur agit généralement comme un objet descripteur immuable et durable. Dans les applications Adaptive, l'instance de NmErrorDomain est probablement conservée sous forme de singleton à l'échelle du processus ou de référence statique (interprétation), de sorte qu'un accès cohérent est garanti pendant toute la durée d'exécution d'une application.

La classe ne possède aucun état interne modifiable et est conçue sans état. Toutes les fonctions membres destinées à interroger des informations telles que Name() [SWS_ANM_01106], Message() [SWS_ANM_01107] ainsi que la routine ThrowAsException() [SWS_ANM_01108] sont déclarées comme const et désignées comme thread-safe [SWS_ANM_01106], [SWS_ANM_01107], [SWS_ANM_01108]. Cela permet un accès concurrent depuis un nombre quelconque de threads sans surcoût de synchronisation supplémentaire.

Parcours d'utilisation

Dans la pratique, l'utilisation de NmErrorDomain s'effectue principalement de manière indirecte via le modèle de traitement des erreurs de ara::core::Result et ara::core::ErrorCode. Si une opération de la gestion de réseau échoue, la couche génère un code d'erreur correspondant en l'associant au domaine.

Un déroulement typique de vérification et de traitement des erreurs se divise en les étapes suivantes :

  1. Vérification du résultat : après un appel NM, la logique applicative reçoit un objet d'erreur de type ara::core::ErrorCode qui est lié à NmErrorDomain.
  2. Identification du domaine : pour classer l'origine de l'erreur, l'identifiant du domaine d'erreur peut être interrogé via Name() [SWS_ANM_01106].
  3. Récupération du message d'erreur : pour la journalisation ou la sortie de diagnostic, Message() [SWS_ANM_01107] fournit une chaîne de caractères descriptive pour le code d'erreur spécifique.
  4. Déclenchement d'exception : si, en cas d'erreur, il convient de passer à un flux de contrôle basé sur les exceptions, ThrowAsException() [SWS_ANM_01108] est appelée, ce qui lève une exception associée au code d'erreur.

Diagramme de séquence : séquence d'interactions lors de l'interrogation du texte d'erreur et de la levée d'exceptions via le domaine d'erreur. Sources : [SWS_ANM_01106], [SWS_ANM_01107], [SWS_ANM_01108]

Scénarios d'erreur

La classe NmErrorDomain sert de cadre administratif pour les codes d'erreur et les exceptions du module nm. Les situations d'erreur sont représentées par l'énumération NmErrc, à laquelle on accède via l'alias de type Errc [SWS_ANM_01103].

Pour les différents appels de méthodes, les conditions et comportements suivants sont pertinents :

  • Interrogation du nom et du message : les méthodes Name() [SWS_ANM_01106] et Message() [SWS_ANM_01107] sont déclarées comme noexcept. Elles garantissent qu'aucune exception secondaire n'est levée, même lors de l'interrogation d'informations de diagnostic dans des états d'erreur critiques. Si une valeur d'erreur numérique inconnue devait être transmise à Message(), l'implémentation renverrait probablement une indication générique ou un texte standard (interprétation).
  • Traitement des exceptions : la méthode ThrowAsException() est explicitement qualifiée de noexcept(false) [SWS_ANM_01108]. La postcondition de l'appel est la levée de l'exception spécifique NmException (référencée via l'alias Exception [SWS_ANM_01104]), paramétrée avec le ErrorCode [SWS_ANM_01108] transmis. Si une application appelle cette méthode directement ou indirectement, un bloc catch correspondant pour NmException ou ara::core::Exception doit être présent afin d'empêcher une terminaison du processus.
