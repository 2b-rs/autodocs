Contexte

La classe ara::shwa::TaskHandler constitue, dans l'Adaptive Platform (module shwa), l'interface centrale pour la soumission et l'exécution de tâches de calcul sur des accélérateurs matériels spécialisés. Sa responsabilité première consiste à accepter des ordres d'exécution fonctionnels, puis à les mettre à disposition et à les exécuter sous la forme d'une soumission à une file d'attente (queue) sur un dispositif sélectionné. Au sein de l'architecture système, le gestionnaire sert d'intermédiaire entre le composant logiciel utilisateur et les files d'attente de traitement proches du matériel du sous-système d'accélération.

L'interaction s'effectue ici via des interfaces standardisées pour différents modèles d'exécution : d'une part, la classe permet l'exécution coordonnée de tâches de calcul individuelles via [AP_SWS_SHWA_01203], d'autre part, le traitement parallèle aux données de tampons structurés via [AP_SWS_SHWA_01204]. Grâce à cette encapsulation, le logiciel utilisateur est déchargé des détails spécifiques au système relatifs à la gestion de la file d'attente et à l'interaction avec le dispositif cible. Le dispositif sous-jacent est probablement défini dans le cadre de l'initialisation ou via la configuration du module, étant donné que les méthodes d'exécution elles-mêmes ne demandent aucune sélection de dispositif distincte en paramètre.

Cycle de vie et concurrence

La création d'une instance de ara::shwa::TaskHandler s'effectue exclusivement via la méthode de fabrique statique Create conformément à [AP_SWS_SHWA_01202]. Comme la classe est déclarée comme final, toute dérivation ou spécialisation via des hiérarchies d'héritage est exclue. L'appel de fabrique renvoie l'instance encapsulée dans un ara::core::Result<TaskHandler>, transférant ainsi directement la propriété à l'appelant. Cela impose simultanément une vérification pour déterminer si la création a réussi ou si des erreurs sont survenues.

En ce qui concerne la concurrence et la sécurité des threads, les responsabilités sont clairement séparées :

  • Instanciation : la méthode de création Create est spécifiée comme thread-safe [AP_SWS_SHWA_01202]. Elle peut être appelée en parallèle en toute sécurité depuis plusieurs threads et possède des sémantiques de rollback définies en cas d'erreur.
  • Soumission de tâches : les méthodes de transmission de tâches — SingleTask [AP_SWS_SHWA_01203] ainsi que ParallelFor [AP_SWS_SHWA_01204] — sont expressément spécifiées comme not thread-safe. Une instance de TaskHandler ne doit donc pas être utilisée de manière concurrente depuis plusieurs threads sans synchronisation externe. Si une soumission parallèle doit avoir lieu, l'appelant doit soit prévoir ses propres mécanismes de synchronisation, soit instancier un gestionnaire distinct pour chaque thread.
  • Sécurité vis-à-vis des exceptions : l'ensemble des interfaces (Create, SingleTask, ParallelFor) sont déclarées avec noexcept et spécifiées comme exception safe, ce qui empêche les exceptions C++ et permet d'acheminer les erreurs via les types d'erreur spécifiques à AUTOSAR.

Parcours d'utilisation

Le déroulement standard pour la soumission de tâches s'articule en trois phases consécutives : instanciation, paramétrage et transmission à la file d'attente du dispositif cible. Tout d'abord, l'application demande une instance via Create() [AP_SWS_SHWA_01202]. Après un retour réussi et la validation du ara::core::Result, le gestionnaire est disponible.

Ensuite, l'appelant choisit le modèle d'exécution adapté à la problématique :

  1. Tâche unique : en cas de calculs isolés ou de séquences de contrôle, l'application appelle SingleTask(cfg) [AP_SWS_SHWA_01203]. L'argument template cfg représente probablement un objet fonctionnel invocable ou un contexte de tâche qui définit la règle de calcul proprement dite sur l'accélérateur. L'appel provoque la soumission à la file d'attente sur le dispositif cible.
  2. Exécution parallèle de boucles : si des blocs de données homogènes doivent être traités de manière parallélisée, l'application utilise ParallelFor(bufferSize, cfg) [AP_SWS_SHWA_01204]. La taille de tampon bufferSize est transmise ici, de sorte que l'environnement d'exécution puisse distribuer les itérations sur les unités de calcul disponibles du dispositif cible.

Scénarios d'erreur

Le traitement des erreurs se concentre sur la phase d'instanciation. Comme les méthodes de soumission SingleTask [AP_SWS_SHWA_01203] et ParallelFor [AP_SWS_SHWA_01204] possèdent le type de retour void et sont définies comme noexcept, les erreurs d'appel lors de la soumission ne conduisent à aucun code d'erreur synchrone au niveau de cette interface.

Si la création via Create() échoue, la méthode de fabrique renvoie un ara::core::Result qui encapsule un code d'erreur [AP_SWS_SHWA_01202] :

Code d'erreur Signification Cause et mesure corrective
ShwaErrorCode::kRuntime Erreur générale d'exécution (General runtime error) Survient lorsque les ressources matérielles sont inaccessibles ou que l'initialisation du pilote échoue. L'application appelante doit vérifier le résultat via HasValue() et ne doit pas accéder à la valeur déréférencée.

En cas d'erreur, la sémantique de retour arrière (rollback) spécifiée [AP_SWS_SHWA_01202] garantit qu'aucune ressource partiellement allouée ne subsiste et que le système dans son ensemble demeure dans un état cohérent.
