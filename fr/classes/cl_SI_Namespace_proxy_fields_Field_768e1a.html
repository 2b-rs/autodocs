Permet aux applications clientes l'interrogation asynchrone, la modification et la surveillance sous forme d'abonnement d'un champ de service.

La classe sert d'interface côté client pour l'accès à un champ défini dans le ServiceInterface et regroupe des fonctions de getter, de setter ainsi que de notification. Via [SWS_CM_00112] et [SWS_CM_00113], des valeurs peuvent être interrogées et modifiées de manière asynchrone, pour autant que les opérations correspondantes soient modélisées. Pour les mises à jour de champs, un mécanisme de cache basé sur l'abonnement est utilisé, lequel met en mémoire tampon les notifications et les transmet via des gestionnaires de rappel. Le respect d'intervalles minimaux d'émission ainsi que l'absence de sémantique de rollback lors des accès en écriture constituent une contrainte essentielle.

Contexte

Dans la gestion de la communication de l'AUTOSAR Adaptive Platform (ara::com), la classe <SI-Namespace>::proxy::fields::<Field> représente un champ individuel modélisé dans le Service-Interface (Field) du côté client ou proxy. La classe regroupe l'accès aux valeurs d'attributs et associe trois rôles fonctionnels : l'interrogation de la valeur actuelle (getter), la modification de la valeur (setter) ainsi que la réception asynchrone des changements de valeur (notifier) (AUTOSAR_AP_EXP_ARAComAPI p. 10). Elle agit en tant qu'interface entre l'application cliente et la couche de communication sous-jacente (Network Binding).

La définition du Service-Interface détermine les opérations disponibles sur l'instance : la méthode Get() n'est générée que si Field.hasGetter == TRUE est configuré [SWS_CM_00112]. La méthode Set() n'est disponible que si Field.hasSetter == TRUE est vérifié [SWS_CM_00113]. Le type de données concret du champ est alors représenté avec sûreté de typage via l'alias de type fourni FieldType [SWS_CM_11403].

Cycle de vie

Les objets champ sont instanciés en tant que membres de la classe proxy de niveau supérieur. Leur durée de vie est donc probablement directement liée au cycle de vie de l'instance de proxy correspondante. Pour le mécanisme de notification événementiel, l'instance traverse un cycle de vie d'abonnement clairement défini :

  • Non abonné : initialement, le champ se trouve à l'état kNotSubscribed.
  • Abonnement demandé : par l'appel synchrone de Subscribe(maxSampleCount) [SWS_CM_11601], le tampon est configuré et l'enregistrement est démarré. Le notifier passe à kSubscriptionPending ou, après confirmation par la couche de communication, à kSubscribed, cette transition d'état étant probablement réalisée de manière asynchrone.
  • Abonnement terminé : par Unsubscribe() [SWS_CM_11602], le flux de notifications est arrêté et l'état revient à kNotSubscribed.

L'état actuel peut être interrogé à tout moment de manière synchrone avec GetSubscriptionState() [SWS_CM_11604]. Afin d'être averti de manière asynchrone des changements d'état, un rappel peut être défini avec SetSubscriptionStateChangeHandler() [SWS_CM_11607], optionnellement avec un contexte d'exécution dédié [SWS_CM_11608]. Avant la destruction de l'instance ou lors d'une désactivation, les rappels enregistrés doivent être explicitement retirés via UnsetReceiveHandler() [SWS_CM_11606], UnsetSubscriptionStateChangeHandler() [SWS_CM_11609] ainsi que UnsetTransportFaultConditionHandler() [SWS_CM_00126].

Diagramme d'états : cycle de vie de l'abonnement du notifier via ara::com::SubscriptionState. Sources : [SWS_CM_11601], [SWS_CM_11602], [SWS_CM_11604].

Parcours d'utilisation

Le chemin d'utilisation typique comprend l'enregistrement des notifications, la réception des nouvelles données ainsi que l'accès ponctuel en lecture et en écriture :

  1. Établir l'abonnement : l'application appelle Subscribe() avec la capacité de cache souhaitée [SWS_CM_11601] et enregistre au moyen de SetReceiveHandler() un callback de notification sans paramètre [SWS_CM_11605]. Pour les architectures concurrentes, l'exécution peut être déléguée via un exécuteur [SWS_CM_11611]. De plus, un gestionnaire pour les erreurs de transport peut être défini pour les événements de notification [SWS_CM_00109], [SWS_CM_00110].
  2. Traiter les échantillons : dès que la gestion de la communication reçoit de nouvelles données de champ, elle déclenche le gestionnaire de réception. Le gestionnaire détermine les emplacements de tampon disponibles via GetFreeSampleCount() [SWS_CM_11603] et traite les nouvelles valeurs via GetNewSamples() [SWS_CM_11610]. L'état E2E des notifications reçues peut être vérifié par GetE2EStateMachineStateNotifier() [SWS_CM_11612].
  3. Lecture explicite : la récupération de la valeur actuelle s'effectue de manière asynchrone via Get() [SWS_CM_00112] et renvoie un ara::core::Future<FieldType> [SWS_CM_11403]. Une fois terminée, l'état de contrôle E2E peut être vérifié avec GetE2EStateMachineStateGetter() [SWS_CM_00145].
  4. Écriture explicite : la modification de la valeur s'effectue via Set(value) [SWS_CM_00113]. Le ara::core::Future<FieldType> renvoyé fournit le résultat de l'opération de définition, dont l'état E2E peut être lu via GetE2EStateMachineStateSetter() [SWS_CM_00146].

Diagramme de séquence : déroulement typique de l'interaction avec les notifications ainsi que les opérations Get et Set. Sources : [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601], [SWS_CM_11605], [SWS_CM_11610].

Scénarios d'erreur

Différents états d'erreur peuvent survenir lors de l'utilisation des méthodes du champ :

  • Panne de communication : si la transmission réseau échoue lors de Get() ou Set(), l'erreur ComErrc::kCommunicationFailure est transmise dans le future [SWS_CM_00112], [SWS_CM_00113]. Pour Get(), la sémantique de rollback s'applique ; pour Set(), no_rollback_semantics s'applique, de sorte qu'un état indéterminé peut apparaître sur le serveur en cas de dépassement de délai [SWS_CM_00113].
  • Violation de l'intervalle d'émission : si des requêtes sont émises plus rapidement que configuré dans le déploiement, cela entraîne ComErrc::kMinimumSendIntervalViolationError [SWS_CM_00112], [SWS_CM_00113].
  • Limites de tampon : si la mémoire ne peut pas être allouée lors de Subscribe(), la méthode renvoie ComErrc::kMaxSampleCountNotRealizable [SWS_CM_11601]. Si un nombre trop élevé d'échantillons est récupéré lors de GetNewSamples(), l'appel échoue avec ComErrc::kMaxSamplesExceeded [SWS_CM_11610].
  • Violations d'accès et de gestionnaires : des droits d'exécution manquants conduisent à une InsufficientPermissionsViolation lors de Get(), Set() ou Subscribe() [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601]. La transmission d'objets invocables vides ou non valides aux enregistrements de gestionnaires déclenche une InvalidHandlerViolation [SWS_CM_11605], [SWS_CM_11607], [SWS_CM_00109].
  • Idempotence : un nouvel appel de Subscribe() avec une valeur de tampon identique dans les états kSubscribed ou kSubscriptionPending reste sans effet [SWS_CM_11601] ; de même, Unsubscribe() retourne sans effet en l'absence d'abonnement actif [SWS_CM_11602].

Utilisation

La méthode Get sert, dans la portée du proxy <SI-Namespace>::proxy::fields::<Field>, à la récupération asynchrone de la valeur actuelle du champ ([SWS_CM_00112] ; voir aussi AUTOSAR_AP_EXP_ARAComAPI §6 « FieldGet »). La fonction est mise à disposition via l'en-tête du proxy <SiNamespaceDerivedDirectoryPath>/<SiShortname>_proxy.h et n'existe que si Field.hasGetter == TRUE est modélisé pour le champ ([SWS_CM_00112]). Elle ne prend aucun paramètre et renvoie un ara::core::Future<FieldType> qui, après un transfert réussi, contient la valeur actuelle ([SWS_CM_00112]).

Gestion des erreurs et conditions limites

L'interface est définie comme noexcept et sûre vis-à-vis des exceptions ([SWS_CM_00112]). Si l'opération échoue, le ara::core::Future renvoyé contient un code d'erreur avec sémantique de rollback ([SWS_CM_00112]) :

  • ComErrc::kCommunicationFailure : le binding réseau signale une erreur de communication récupérable ou l'échec d'une communication sécurisée ([SWS_CM_00112]).
  • ComErrc::kMinimumSendIntervalViolationError : une demande d'envoi a eu lieu plus rapidement que ne l'autorise l'intervalle d'envoi minimal configuré pour l'élément (minimumSendInterval) ([SWS_CM_00112]).
  • InsufficientPermissionsViolation : l'exécution est rejetée par le Grant Enforcement ([SWS_CM_00112]).

Les erreurs applicatives (Application Errors) n'existent pas pour le getter ([SWS_CM_00113]).

Interaction

Côté squelette, le traitement de la requête du getter présuppose un callback enregistré via RegisterGetHandler ([SWS_CM_00114]). Chaque appel de Get() effectue un contrôle de bout en bout (E2E) ; l'état qui en résulte peut être interrogé de manière synchrone côté proxy via GetE2EStateMachineStateGetter ([SWS_CM_00145]).
