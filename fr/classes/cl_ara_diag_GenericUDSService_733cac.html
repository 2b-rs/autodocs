Contexte

La classe ara::diag::GenericUDSService représente une interface de service générique pour le traitement du diagnostic dans le standard AUTOSAR Adaptive. Elle sert de base côté application pour le traitement des requêtes de diagnostic UDS (Unified Diagnostic Services) pour lesquelles aucune classe de service spécialisée n'est modélisée ou utilisée.

Dans le système global, ara::diag::GenericUDSService agit à l'interface entre les composants suivants :

  • Diagnostic Management (DM) : le sous-système central de diagnostic de l'AUTOSAR Adaptive Platform reçoit les messages de diagnostic des testeurs de diagnostic externes et les transmet au gestionnaire de service enregistré une fois l'autorisation accordée [SWS_DM_00619] [SWS_DM_00620].
  • Gestionnaire de service spécifique à l'application : l'application concrète dérive de GenericUDSService et implémente la méthode virtuelle pure HandleMessage afin d'évaluer la charge utile effective de la requête UDS et d'y répondre [SWS_DM_00618].
  • Modélisation de la plateforme : l'affectation aux points de terminaison de communication s'effectue de manière déclarative via un ara::core::InstanceSpecifier qui fait référence à un PortPrototype modélisé d'un DiagnosticGenericUdsInterface [SWS_DM_00616].

Cycle de vie

La création d'une instance de GenericUDSService s'effectue via le constructeur explicite en spécifiant un ara::core::InstanceSpecifier ainsi que le comportement de concurrence ConcurrencyType [SWS_DM_00616] :

  • Mode de concurrence : via ConcurrencyType::kConcurrent ou ConcurrencyType::kNotConcurrent, l'appelant définit si le traitement ultérieur dans HandleMessage doit être thread-safe ou non thread-safe [SWS_DM_00616] [SWS_DM_00618].
  • Vérifications de modèle : le constructeur vérifie la validité du mapping de port, l'affectation de processus ainsi que l'utilisation éventuelle du spécificateur au sein du processus [SWS_DM_00616].

En ce qui concerne la sémantique et la propriété, GenericUDSService est définie comme une instance unique. Les constructeurs de copie et de déplacement ainsi que les opérateurs d'assignation correspondants sont explicitement supprimés (=delete) [SWS_DM_01657] [SWS_DM_01658] [SWS_DM_01655] [SWS_DM_01656].

Le cycle de vie opérationnel se divise en deux états principaux :

  1. NichtAngeboten (état initial) : Après la construction, l'acheminement par le Diagnostic Management est désactivé.
  2. Proposé : par l'appel de Offer(), l'instance autorise le DM à délivrer les messages UDS entrants [SWS_DM_00619].
  3. Retour à NichtAngeboten : Au moyen de StopOffer(), l'acheminement est de nouveau interrompu en cours de fonctionnement [SWS_DM_00620].

Le destructeur est virtuel et déclaré comme noexcept [SWS_DM_00584]. Alors que le constructeur lui-même est thread-safe, Offer(), StopOffer() et le destructeur ne sont pas thread-safe (not thread-safe) [SWS_DM_00616] [SWS_DM_00619] [SWS_DM_00620] [SWS_DM_00584]. Avant la destruction de l'objet de service, le transfert devrait probablement être arrêté explicitement via StopOffer() (interprétation).

Parcours d'utilisation

L'utilisation typique de GenericUDSService comprend la configuration, la mise à disposition et la réponse asynchrone aux requêtes UDS :

  1. Initialisation et démarrage : l'application instancie la classe dérivée avec le InstanceSpecifier approprié et démarre la disponibilité du service par Offer() [SWS_DM_00616] [SWS_DM_00619].
  2. Requête entrante : dès qu'une requête UDS arrive, le Diagnostic Management la délègue à HandleMessage(sid, requestData, metaInfo, cancellationHandler) [SWS_DM_00618] :
    • sid fournit l'identifiant de service UDS (Service Identifier).
    • requestData met à disposition les données de requête après le SID sous forme de ara::core::Span. Les données restent valides jusqu'à ce que la promesse associée soit remplie ou que le traitement soit interrompu [SWS_DM_00618].
    • metaInfo contient des informations de contexte sur la requête.
    • cancellationHandler permet la vérification d'une annulation via IsCanceled() ou l'enregistrement d'une fonction de notification via SetNotifier [SWS_DM_00618].
  3. Retour de résultat : la méthode renvoie un ara::core::Future<OperationOutput>. En cas d'exécution réussie, le résultat contient la charge utile de réponse dans OperationOutput, sinon un code d'erreur de diagnostic [SWS_DM_00618].
  4. Désenregistrement : lors de l'arrêt du composant, l'application appelle StopOffer() pour arrêter le transfert de messages [SWS_DM_00620].

Diagramme de séquence : ordre des appels et des interactions lors du traitement des messages UDS. Sources : [SWS_DM_00616], [SWS_DM_00618], [SWS_DM_00619], [SWS_DM_00620].

Scénarios d'erreur

Lors de l'utilisation de GenericUDSService, des erreurs spécifiques de configuration, de modèle et d'exécution peuvent survenir :

  • Mauvaise configuration lors de l'instanciation : le constructeur est déclaré comme noexcept, mais entraîne des violations d'architecture (Violations) en cas de configurations non valides [SWS_DM_00616] :
    • InstanceSpecifierMappingIntegrityViolation : L'identifiant ne peut pas être résolu dans le modèle ou ne référence aucun PortPrototype.
    • PortInterfaceMappingViolation : Le port de type DiagnosticGenericUdsInterface n'est pas relié par un DiagnosticServiceGenericMapping.
    • ProcessMappingViolation : aucun processus correspondant trouvé dans le modèle d'exécution.
    • InstanceSpecifierAlreadyInUseViolation : l'identifiant a déjà été utilisé pour un appel de constructeur au sein du même processus.
  • Service déjà proposé : si Offer() est appelé plusieurs fois sans StopOffer() intermédiaire, l'appel échoue et renvoie un ara::core::Result avec le code d'erreur DiagOfferErrc::kAlreadyOffered (tout en conservant la sémantique de rollback) [SWS_DM_00619].
  • Réponses négatives UDS (Negative Response Codes) : si le traitement d'un message UDS échoue dans HandleMessage, le gestionnaire doit transmettre dans le ara::core::Future renvoyé un NRC UDS approprié conformément à l'ISO 14229-1 via le type d'erreur DiagUdsNrcErrc [SWS_DM_00618].

Ce guide repose exclusivement sur la spécification AUTOSAR pour l'Adaptive Platform (Release R25-11, module diag).

<h4>Contexte</h4>
<p>La classe <code>ara::diag::GenericUDSService</code> représente une interface de service générique pour le traitement du diagnostic dans le standard AUTOSAR Adaptive. Elle sert de base côté application pour le traitement des requêtes de diagnostic UDS (Unified Diagnostic Services) pour lesquelles aucune classe de service spécialisée n'est modélisée ou utilisée.</p>
<p>Dans le système global, <code>ara::diag::GenericUDSService</code> agit à l'interface entre les composants suivants :</p>
<ul>
<li><strong>Diagnostic Management (DM) :</strong> le sous-système central de diagnostic de l'AUTOSAR Adaptive Platform reçoit les messages de diagnostic des testeurs de diagnostic externes et les transmet au gestionnaire de service enregistré une fois l'autorisation accordée <a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a> <a class="spec-record-ref" data-req="SWS_DM_00620" href="../spec/record.html?id=SWS_DM_00620">[SWS_DM_00620]</a>.</li>
<li><strong>Gestionnaire de service spécifique à l'application :</strong> l'application concrète dérive de <code>GenericUDSService</code> et implémente la méthode virtuelle pure <code>HandleMessage</code> afin d'évaluer la charge utile effective de la requête UDS et d'y répondre <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
<li><strong>Modélisation de la plateforme :</strong> l'affectation aux points de terminaison de communication s'effectue de manière déclarative via un <code>ara::core::InstanceSpecifier</code> qui fait référence à un <code>PortPrototype</code> modélisé d'un <code>DiagnosticGenericUdsInterface</code> <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a>.</li>
</ul>

<h4>Cycle de vie</h4>
<p>La création d'une instance de <code>GenericUDSService</code> s'effectue via le constructeur explicite en spécifiant un <code>ara::core::InstanceSpecifier</code> ainsi que le comportement de concurrence <code>ConcurrencyType</code> <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a> :</p>
<ul>
<li><strong>Mode de concurrence :</strong> via <code>ConcurrencyType::kConcurrent</code> ou <code>ConcurrencyType::kNotConcurrent</code>, l'appelant définit si le traitement ultérieur dans <code>HandleMessage</code> doit être thread-safe ou non thread-safe <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a> <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
<li><strong>Vérifications de modèle :</strong> le constructeur vérifie la validité du mapping de port, l'affectation de processus ainsi que l'utilisation éventuelle du spécificateur au sein du processus <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a>.</li>
</ul>
<p>En ce qui concerne la sémantique et la propriété, <code>GenericUDSService</code> est définie comme une instance unique. Les constructeurs de copie et de déplacement ainsi que les opérateurs d'assignation correspondants sont explicitement supprimés (<code>=delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01657" href="../spec/record.html?id=SWS_DM_01657">[SWS_DM_01657]</a> <a class="spec-record-ref" data-req="SWS_DM_01658" href="../spec/record.html?id=SWS_DM_01658">[SWS_DM_01658]</a> <a class="spec-record-ref" data-req="SWS_DM_01655" href="../spec/record.html?id=SWS_DM_01655">[SWS_DM_01655]</a> <a class="spec-record-ref" data-req="SWS_DM_01656" href="../spec/record.html?id=SWS_DM_01656">[SWS_DM_01656]</a>.</p>
<p>Le cycle de vie opérationnel se divise en deux états principaux :</p>
<ol>
<li><strong>NichtAngeboten (état initial) :</strong> Après la construction, l'acheminement par le Diagnostic Management est désactivé.</li>
<li><strong>Proposé :</strong> par l'appel de <code>Offer()</code>, l'instance autorise le DM à délivrer les messages UDS entrants <a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a>.</li>
<li><strong>Retour à NichtAngeboten :</strong> Au moyen de <code>StopOffer()</code>, l'acheminement est de nouveau interrompu en cours de fonctionnement <a class="spec-record-ref" data-req="SWS_DM_00620" href="../spec/record.html?id=SWS_DM_00620">[SWS_DM_00620]</a>.</li>
</ol>
<p>Le destructeur est virtuel et déclaré comme <code>noexcept</code> <a class="spec-record-ref" data-req="SWS_DM_00584" href="../spec/record.html?id=SWS_DM_00584">[SWS_DM_00584]</a>. Alors que le constructeur lui-même est thread-safe, <code>Offer()</code>, <code>StopOffer()</code> et le destructeur ne sont pas thread-safe (<code>not thread-safe</code>) <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a> <a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a> <a class="spec-record-ref" data-req="SWS_DM_00620" href="../spec/record.html?id=SWS_DM_00620">[SWS_DM_00620]</a> <a class="spec-record-ref" data-req="SWS_DM_00584" href="../spec/record.html?id=SWS_DM_00584">[SWS_DM_00584]</a>. Avant la destruction de l'objet de service, le transfert devrait probablement être arrêté explicitement via <code>StopOffer()</code> (interprétation).</p>

<h4>Parcours d'utilisation</h4>
<p>L'utilisation typique de <code>GenericUDSService</code> comprend la configuration, la mise à disposition et la réponse asynchrone aux requêtes UDS :</p>
<ol>
<li><strong>Initialisation et démarrage :</strong> l'application instancie la classe dérivée avec le <code>InstanceSpecifier</code> approprié et démarre la disponibilité du service par <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a> <a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a>.</li>
<li><strong>Requête entrante :</strong> dès qu'une requête UDS arrive, le Diagnostic Management la délègue à <code>HandleMessage(sid, requestData, metaInfo, cancellationHandler)</code> <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a> :
<ul>
<li><code>sid</code> fournit l'identifiant de service UDS (Service Identifier).</li>
<li><code>requestData</code> met à disposition les données de requête après le SID sous forme de <code>ara::core::Span</code>. Les données restent valides jusqu'à ce que la promesse associée soit remplie ou que le traitement soit interrompu <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
<li><code>metaInfo</code> contient des informations de contexte sur la requête.</li>
<li><code>cancellationHandler</code> permet la vérification d'une annulation via <code>IsCanceled()</code> ou l'enregistrement d'une fonction de notification via <code>SetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
</ul>
</li>
<li><strong>Retour de résultat :</strong> la méthode renvoie un <code>ara::core::Future&lt;OperationOutput&gt;</code>. En cas d'exécution réussie, le résultat contient la charge utile de réponse dans <code>OperationOutput</code>, sinon un code d'erreur de diagnostic <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
<li><strong>Désenregistrement :</strong> lors de l'arrêt du composant, l'application appelle <code>StopOffer()</code> pour arrêter le transfert de messages <a class="spec-record-ref" data-req="SWS_DM_00620" href="../spec/record.html?id=SWS_DM_00620">[SWS_DM_00620]</a>.</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Lors de l'utilisation de <code>GenericUDSService</code>, des erreurs spécifiques de configuration, de modèle et d'exécution peuvent survenir :</p>
<ul>
<li><strong>Mauvaise configuration lors de l'instanciation :</strong> le constructeur est déclaré comme <code>noexcept</code>, mais entraîne des violations d'architecture (Violations) en cas de configurations non valides <a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a> :
<ul>
<li><code>InstanceSpecifierMappingIntegrityViolation</code> : L'identifiant ne peut pas être résolu dans le modèle ou ne référence aucun <code>PortPrototype</code>.</li>
<li><code>PortInterfaceMappingViolation</code> : Le port de type <code>DiagnosticGenericUdsInterface</code> n'est pas relié par un <code>DiagnosticServiceGenericMapping</code>.</li>
<li><code>ProcessMappingViolation</code> : aucun processus correspondant trouvé dans le modèle d'exécution.</li>
<li><code>InstanceSpecifierAlreadyInUseViolation</code> : l'identifiant a déjà été utilisé pour un appel de constructeur au sein du même processus.</li>
</ul>
</li>
<li><strong>Service déjà proposé :</strong> si <code>Offer()</code> est appelé plusieurs fois sans <code>StopOffer()</code> intermédiaire, l'appel échoue et renvoie un <code>ara::core::Result</code> avec le code d'erreur <code>DiagOfferErrc::kAlreadyOffered</code> (tout en conservant la sémantique de rollback) <a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a>.</li>
<li><strong>Réponses négatives UDS (Negative Response Codes) :</strong> si le traitement d'un message UDS échoue dans <code>HandleMessage</code>, le gestionnaire doit transmettre dans le <code>ara::core::Future</code> renvoyé un NRC UDS approprié conformément à l'ISO 14229-1 via le type d'erreur <code>DiagUdsNrcErrc</code> <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>.</li>
</ul>
