Contexte

La classe <RoutineInterface-Namespace>::<RoutineInterface> constitue dans le module AUTOSAR Adaptive diag l'interface C++ centrale pour la mise à disposition et le contrôle de routines de diagnostic (AUTOSAR AP SWS Diagnostics p. 68). Dans le contexte du service UDS RoutineControl (service 0x31 selon l'ISO 14229-1), une dérivation spécifique à l'application de cette classe fait office de gestionnaire côté serveur. La classe accepte les requêtes qui sont transmises à l'application par le Diagnostic Management (DM) central ([SWS_DM_00594]). L'interface définit les trois opérations de contrôle essentielles d'une routine : le démarrage via Start ([SWS_DM_00591]), l'arrêt via Stop ([SWS_DM_00592]) ainsi que l'interrogation des résultats via RequestResult ([SWS_DM_00593]). La liaison fonctionnelle dans le système s'effectue via un PortPrototype de type DiagnosticRoutineInterface, qui doit être référencé dans le modèle via un DiagnosticServiceGenericMapping ([SWS_DM_00589]).

Cycle de vie

La création d'un gestionnaire de routine s'effectue via le constructeur paramétré en indiquant un ara::core::InstanceSpecifier et la concurrence souhaitée ara::diag::ConcurrencyType ([SWS_DM_00589]). Le paramètre concurrencyType détermine si l'interface est implémentée comme étant thread-safe (kConcurrent) ou non thread-safe (kNotConcurrent) ([SWS_DM_00589]). L'appel du constructeur lui-même est déclaré thread-safe et noexcept ([SWS_DM_00589]).

Concernant la sémantique de l'objet, <RoutineInterface> possède une identité univoque : le constructeur de copie ([SWS_DM_01669]), le constructeur de déplacement ([SWS_DM_01670]), l'opérateur d'assignation par copie ([SWS_DM_01667]) et l'opérateur d'assignation par déplacement ([SWS_DM_01668]) sont explicitement supprimés (=delete). Toute duplication ou tout déplacement d'instances est donc exclu.

Après la construction, l'instance se trouve à l'état inactif. Ce n'est que par l'appel de Offer() que la transmission des requêtes de diagnostic entrantes à ce gestionnaire par le Diagnostic Management est activée ([SWS_DM_00594]). L'appel de StopOffer() désactive à nouveau la transmission des requêtes ([SWS_DM_00595]). La libération de l'instance s'effectue via le destructeur virtuel ~<RoutineInterface>(), qui est spécifié comme noexcept et non thread-safe ([SWS_DM_00590]). Avant l'appel du destructeur, il conviendrait vraisemblablement d'appeler StopOffer() afin de désenregistrer proprement les transmissions en suspens du DM avant la destruction de l'objet.

Diagramme d'états : états du cycle de vie et d'activation de l'interface de routine. Sources : [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00595], [SWS_DM_00590].

Parcours d'utilisation

Le chemin d'utilisation typique se divise en initialisation, traitement des requêtes et terminaison :

  1. Instanciation : l'application dérive une classe d'implémentation de <RoutineInterface>, redéfinit les méthodes virtuelles pures et crée l'instance avec le InstanceSpecifier associé ainsi que l'indication de ConcurrencyType ([SWS_DM_00589]).
  2. Offre de service (Offer) : l'application appelle Offer() ([SWS_DM_00594]), ce qui autorise le DM à transmettre les requêtes de routine.
  3. Traitement des opérations de contrôle :
    • Démarrer la routine : si une requête de démarrage arrive, le DM appelle la méthode Start(...) avec les arguments d'entrée modélisés, ara::diag::MetaInfo et un ara::diag::CancellationHandler ([SWS_DM_00591]). La méthode renvoie un ara::core::Future avec l'objet StartOutput associé ([SWS_DM_00581], [SWS_DM_80003]).
    • Demander les résultats : les résultats intermédiaires ou finaux de la routine sont interrogés au moyen de RequestResult(...) ([SWS_DM_00593]). Le ara::core::Future renvoyé fournit l'objet RequestResultOutput ([SWS_DM_00583], [SWS_DM_80005]).
    • Arrêter la routine : une exécution active de routine est terminée par l'appel de Stop(...) ([SWS_DM_00592]), qui fournit un ara::core::Future avec l'objet StopOutput ([SWS_DM_00582], [SWS_DM_80004]).
    • Traitement d'interruption : via le cancellationHandler transmis, le gestionnaire peut interroger l'état d'interruption au moyen de IsCanceled() ou enregistrer un rappel via SetNotifier(...) si la conversation de diagnostic est interrompue prématurément ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).
  4. Mettre fin à l'offre de service (StopOffer) : si le gestionnaire ne doit plus traiter de requêtes, l'application appelle StopOffer() ([SWS_DM_00595]).

Diagramme de séquence : modèles d'interaction entre l'application, le gestionnaire de routine et le Diagnostic Management. Sources : [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00591], [SWS_DM_00593], [SWS_DM_00592], [SWS_DM_00595].

Scénarios d'erreur

Des situations d'erreur peuvent survenir aussi bien lors de l'instanciation et de la mise à disposition que pendant l'exécution proprement dite de la routine :

  • Violations d'intégrité et de modèle lors de la construction : Bien que le constructeur soit déclaré comme noexcept, des violations sont déclenchées en cas d'erreurs de configuration ([SWS_DM_00589]) :
    • InstanceSpecifierMappingIntegrityViolation : le InstanceSpecifier ne peut pas être résolu dans le contexte de modèle de l'exécutable ou ne pointe pas vers un PortPrototype ([SWS_DM_00589]).
    • PortInterfaceMappingViolation : le PortPrototype de type DiagnosticRoutineInterface n'est pas référencé par un DiagnosticServiceGenericMapping ([SWS_DM_00589]).
    • ProcessMappingViolation : une InstanceRef modélisée existe, mais aucun processus modélisé ne correspond au processus d'exécution actuel ([SWS_DM_00589]).
    • InstanceSpecifierAlreadyInUseViolation : le InstanceSpecifier indiqué est déjà utilisé dans ce processus par une autre instance ([SWS_DM_00589]).
  • Erreur lors de la mise à disposition (Offer) : Si Offer() est appelée alors que le service est déjà proposé, la méthode renvoie un ara::core::Result<void> avec le code d'erreur DiagOfferErrc::kAlreadyOffered ([SWS_DM_00594]). L'appel est spécifié comme non thread-safe ([SWS_DM_00594]).
  • Erreurs métier pendant l'exécution des opérations : Si les opérations Start, Stop ou RequestResult échouent, les méthodes ne lèvent pas d'exception (toutes les méthodes sont noexcept). À la place, l'erreur est transmise de manière asynchrone via le ara::core::Future renvoyé. L'implémentation doit fournir à cet effet un Negative Response Code (NRC) UDS approprié conformément à l'ISO 14229-1 via ara::diag::DiagUdsNrcErrc ou un Ap ApplicationError ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).

Ce guide est basé sur la spécification AUTOSAR Adaptive R25-11 pour le module diag.
