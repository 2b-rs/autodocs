The UdsTransportProtocolMgr class manages the interaction between the Diagnostic Server instance(s) and various UDS Transport Protocols (e.g., DoIP[2], CAN[21]). It provides a standard, extensible API for handling transport-specific message reception and optional early payload access.

Contexte

La classe apext::diag::uds_transport::UdsTransportProtocolMgr constitue l'interface standardisée de coordination entre les instances du Diagnostic Server (DM Core ou Session Layer) et divers protocoles de transport UDS tels que DoIP ou CAN (AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer »). Les protocoles de transport concrets sont réalisés sous forme de sous-classes de la classe de base abstraite apext::diag::uds_transport::UdsTransportProtocolHandler ([SWS_DM_00315], AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer »).

Dans cette fonction d'intermédiaire, la classe de gestionnaire interagit principalement avec trois composants :

  • UDS Transport Protocol Handler (Transport Layer) : signalent le début des messages entrants ([SWS_DM_00309]), transmettent les requêtes entièrement reçues ([SWS_DM_00311]), acquittent les demandes d'émission ([SWS_DM_00312]) et signalent les changements de canal ainsi que d'état ([SWS_DM_00313], [SWS_DM_00314]).
  • Diagnostic Server Core (Session Layer) : prend en charge les requêtes UDS valides pour la suite du traitement de diagnostic et gère l'allocation des tampons de messages ([SWS_DM_00309], [SWS_DM_00311]).
  • Handlers de transport périodiques : transmettent des confirmations relatives à la transmission réussie de chaînes de messages périodiques ([SWS_DM_01069]).

Diagramme de contexte : interaction de l'UdsTransportProtocolMgr avec les handlers de transport et la Session Layer. Sources : AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer », [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00314].

Cycle de vie

Le cycle de vie d'une implémentation de protocole de transport est contrôlé par le Diagnostic Manager (DM) selon un ordre strictement défini allant de la construction et l'initialisation jusqu'à l'arrêt ([SWS_DM_00329], AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 « Initialization, Starting and Stopping of a UDS TransportLayer »). La classe UdsTransportProtocolMgr déclare un destructeur virtuel par défaut ([SWS_DM_01524]).

En cours d'exploitation, les phases de désactivation sont synchronisées : lorsqu'un handler a fermé ses connexions réseau et libéré ses ressources en réaction à un arrêt, il notifie le manager via le rappel HandlerStopped en indiquant son handlerId ([SWS_DM_00314]).

En ce qui concerne la mémoire et la propriété, un modèle de transfert clair s'applique aux tampons de messages : au début d'une transmission, le DM-Core crée l'objet de message et transmet son pointeur au handler ([SWS_DM_00309]). Après réception complète, le handler transfère à nouveau la propriété du message au DM-Core générique via HandleMessage au moyen d'une sémantique unique_ptr ([SWS_DM_00311]).

Toutes les méthodes d'interface sont spécifiées comme sûres vis-à-vis des exceptions (noexcept), mais comme non sûres vis-à-vis des threads (not thread-safe) ([SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00312]). Interprétation : les appels au manager doivent donc probablement être synchronisés par les composants de transport et de session appelants.

Parcours d'utilisation

Le déroulement normal du traitement des requêtes de diagnostic UDS entrantes se divise selon les étapes suivantes :

  1. Indication de message : pour autant que le handler prenne en charge l'indication, il appelle IndicateMessage lors de l'arrivée des premières données ([SWS_DM_00309]). À cette occasion, l'adresse source et l'adresse de destination, le type d'adressage (physique ou fonctionnel), la taille totale attendue ainsi que le GlobalChannelIdentifier ([SWS_DM_09021]) sont transmis. Les premiers octets peuvent déjà être transmis via payloadInfo afin que le DM puisse, par exemple, détecter précocement des requêtes fonctionnelles Tester Present ([SWS_DM_00309]).
  2. Mise à disposition du tampon : le manager renvoie une paire constituée de IndicationResult et d'un UdsMessagePtr alloué ([SWS_DM_00309]). Si le résultat est IndicationResult::kIndicationOk ([SWS_DM_00384]), le handler remplit le tampon avec les données entrantes.
  3. Transmission à la Session Layer : après réception complète, le handler transmet le message au manager via HandleMessage ([SWS_DM_00311]), ce qui correspond au service T_Data.ind selon l'ISO 14229-2. L'appel retourne immédiatement ; l'évaluation ultérieure s'effectue de manière asynchrone dans la Session Layer ([SWS_DM_00311]).
  4. Acquittement d'envoi : pour les réponses UDS envoyées, le handler confirme ultérieurement le succès via TransmitConfirmation avec le résultat kTransmitOk ([SWS_DM_00312], [SWS_DM_00307]), conformément à T_Data.con selon l'ISO 14229-2.

Diagramme de séquence : déroulement de la réception de messages UDS, de l'indication à la transmission asynchrone à la Session Layer. Sources : [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00384].

Scénarios d'erreur

Les conditions d'erreur pendant le transport ou l'allocation de tampon sont interceptées via des valeurs d'état et des interfaces d'erreur définies :

  • Échec lors de l'indication : si le DM-Core ne peut pas accepter un message indiqué, il le signale via l'enum IndicationResult ([SWS_DM_00309], [SWS_DM_00384]) :
    • kIndicationOccupied : le serveur ou la session de diagnostic est actuellement occupé(e) ([SWS_DM_00384]).
    • kIndicationOverflow : la taille de message transmise dépasse la capacité du tampon ([SWS_DM_00384]).
    • kIndicationUnknownTargetAddress : l'adresse de destination ciblée n'est pas configurée ([SWS_DM_00384]).
  • Interruption de la réception : si une rupture de connexion ou une erreur de transmission survient après un IndicateMessage réussi, le handler appelle NotifyMessageFailure ([SWS_DM_00310]). L'objet UdsMessage obtenu précédemment est restitué au DM sans qu'un appel de HandleMessage n'ait lieu ([SWS_DM_00310]).
  • Erreur de transmission d'envoi : si un message sortant ne peut pas être envoyé au niveau du réseau, le handler signale via TransmitConfirmation le résultat TransmissionResult::kTransmitFailed ([SWS_DM_00312], [SWS_DM_00307]).
  • Réactivation de canal : après une perte temporaire de connexion, le handler signale la nouvelle disponibilité d'un canal via ChannelReestablished avec le GlobalChannelIdentifier ([SWS_DM_00313], [SWS_DM_09021]), pour autant que cette notification ait été demandée au préalable ([SWS_DM_00313]).

Réception des messages

HandleMessage fonction

Hands over a valid received UDS message (currently this is only a request type) from the Transport Layer to the Session Layer. This corresponds to T_Data.ind of Figure 2 from ISO 14229-2[25]. The behavior is asynchronously, i.e. the UDS Message is handed over to the Session Layer and it is expected, that it "instantly" returns, which means, that real processing of the message shall be done asynchronously by the Transport Layer!

virtual void HandleMessage (UdsMessagePtr message) noexcept=0;

<h4>Contexte</h4>
<p>La classe <code>apext::diag::uds_transport::UdsTransportProtocolMgr</code> constitue l'interface standardisée de coordination entre les instances du Diagnostic Server (DM Core ou Session Layer) et divers protocoles de transport UDS tels que DoIP ou CAN (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer »</a>). Les protocoles de transport concrets sont réalisés sous forme de sous-classes de la classe de base abstraite <code>apext::diag::uds_transport::UdsTransportProtocolHandler</code> (<a class="spec-record-ref" data-req="SWS_DM_00315" href="../spec/record.html?id=SWS_DM_00315">[SWS_DM_00315]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 « Support of UDS Transport Layer »</a>).</p>
<p>Dans cette fonction d'intermédiaire, la classe de gestionnaire interagit principalement avec trois composants&#x202f;:</p>
<ul>
<li><strong>UDS Transport Protocol Handler (Transport Layer)&#x202f;:</strong> signalent le début des messages entrants (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>), transmettent les requêtes entièrement reçues (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>), acquittent les demandes d'émission (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>) et signalent les changements de canal ainsi que d'état (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>, <a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>).</li>
<li><strong>Diagnostic Server Core (Session Layer)&#x202f;:</strong> prend en charge les requêtes UDS valides pour la suite du traitement de diagnostic et gère l'allocation des tampons de messages (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</li>
<li><strong>Handlers de transport périodiques&#x202f;:</strong> transmettent des confirmations relatives à la transmission réussie de chaînes de messages périodiques (<a class="spec-record-ref" data-req="SWS_DM_01069" href="../spec/record.html?id=SWS_DM_01069">[SWS_DM_01069]</a>).</li>
</ul>

<h4>Cycle de vie</h4>
<p>Le cycle de vie d'une implémentation de protocole de transport est contrôlé par le Diagnostic Manager (DM) selon un ordre strictement défini allant de la construction et l'initialisation jusqu'à l'arrêt (<a class="spec-record-ref" data-req="SWS_DM_00329" href="../spec/record.html?id=SWS_DM_00329">[SWS_DM_00329]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 « Initialization, Starting and Stopping of a UDS TransportLayer »</a>). La classe <code>UdsTransportProtocolMgr</code> déclare un destructeur virtuel par défaut (<a class="spec-record-ref" data-req="SWS_DM_01524" href="../spec/record.html?id=SWS_DM_01524">[SWS_DM_01524]</a>).</p>
<p>En cours d'exploitation, les phases de désactivation sont synchronisées&#x202f;: lorsqu'un handler a fermé ses connexions réseau et libéré ses ressources en réaction à un arrêt, il notifie le manager via le rappel <code>HandlerStopped</code> en indiquant son <code>handlerId</code> (<a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>).</p>
<p>En ce qui concerne la mémoire et la propriété, un modèle de transfert clair s'applique aux tampons de messages&#x202f;: au début d'une transmission, le DM-Core crée l'objet de message et transmet son pointeur au handler (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). Après réception complète, le handler transfère à nouveau la propriété du message au DM-Core générique via <code>HandleMessage</code> au moyen d'une sémantique <code>unique_ptr</code> (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</p>
<p>Toutes les méthodes d'interface sont spécifiées comme sûres vis-à-vis des exceptions (<code>noexcept</code>), mais comme non sûres vis-à-vis des threads (<em>not thread-safe</em>) (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>, <a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>). Interprétation&#x202f;: les appels au manager doivent donc probablement être synchronisés par les composants de transport et de session appelants.</p>

<h4>Parcours d'utilisation</h4>
<p>Le déroulement normal du traitement des requêtes de diagnostic UDS entrantes se divise selon les étapes suivantes&#x202f;:</p>
<ol>
<li><strong>Indication de message&#x202f;:</strong> pour autant que le handler prenne en charge l'indication, il appelle <code>IndicateMessage</code> lors de l'arrivée des premières données (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). À cette occasion, l'adresse source et l'adresse de destination, le type d'adressage (physique ou fonctionnel), la taille totale attendue ainsi que le <code>GlobalChannelIdentifier</code> (<a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>) sont transmis. Les premiers octets peuvent déjà être transmis via <code>payloadInfo</code> afin que le DM puisse, par exemple, détecter précocement des requêtes fonctionnelles Tester Present (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>).</li>
<li><strong>Mise à disposition du tampon&#x202f;:</strong> le manager renvoie une paire constituée de <code>IndicationResult</code> et d'un <code>UdsMessagePtr</code> alloué (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). Si le résultat est <code>IndicationResult::kIndicationOk</code> (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>), le handler remplit le tampon avec les données entrantes.</li>
<li><strong>Transmission à la Session Layer&#x202f;:</strong> après réception complète, le handler transmet le message au manager via <code>HandleMessage</code> (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>), ce qui correspond au service <code>T_Data.ind</code> selon l'ISO 14229-2. L'appel retourne immédiatement&#x202f;; l'évaluation ultérieure s'effectue de manière asynchrone dans la Session Layer (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</li>
<li><strong>Acquittement d'envoi&#x202f;:</strong> pour les réponses UDS envoyées, le handler confirme ultérieurement le succès via <code>TransmitConfirmation</code> avec le résultat <code>kTransmitOk</code> (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>, <a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>), conformément à <code>T_Data.con</code> selon l'ISO 14229-2.</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>Les conditions d'erreur pendant le transport ou l'allocation de tampon sont interceptées via des valeurs d'état et des interfaces d'erreur définies&#x202f;:</p>
<ul>
<li><strong>Échec lors de l'indication&#x202f;:</strong> si le DM-Core ne peut pas accepter un message indiqué, il le signale via l'enum <code>IndicationResult</code> (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>)&#x202f;:
  <ul>
  <li><code>kIndicationOccupied</code>&#x202f;: le serveur ou la session de diagnostic est actuellement occupé(e) (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  <li><code>kIndicationOverflow</code>&#x202f;: la taille de message transmise dépasse la capacité du tampon (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  <li><code>kIndicationUnknownTargetAddress</code>&#x202f;: l'adresse de destination ciblée n'est pas configurée (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  </ul>
</li>
<li><strong>Interruption de la réception&#x202f;:</strong> si une rupture de connexion ou une erreur de transmission survient après un <code>IndicateMessage</code> réussi, le handler appelle <code>NotifyMessageFailure</code> (<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>). L'objet <code>UdsMessage</code> obtenu précédemment est restitué au DM sans qu'un appel de <code>HandleMessage</code> n'ait lieu (<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>).</li>
<li><strong>Erreur de transmission d'envoi&#x202f;:</strong> si un message sortant ne peut pas être envoyé au niveau du réseau, le handler signale via <code>TransmitConfirmation</code> le résultat <code>TransmissionResult::kTransmitFailed</code> (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>, <a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>).</li>
<li><strong>Réactivation de canal&#x202f;:</strong> après une perte temporaire de connexion, le handler signale la nouvelle disponibilité d'un canal via <code>ChannelReestablished</code> avec le <code>GlobalChannelIdentifier</code> (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>, <a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>), pour autant que cette notification ait été demandée au préalable (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>).</li>
</ul>
