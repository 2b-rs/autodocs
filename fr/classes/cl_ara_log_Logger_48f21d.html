classe ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Contexte

La classe ara::log::Logger représente un contexte de journalisation au sein d'un processus d'application ou d'une zone de processus AUTOSAR Adaptive. Un tel contexte encapsule des propriétés centrales pour la journalisation : un ID de contexte, une description associée de l'ID de contexte ainsi qu'un niveau de journalisation par défaut configurable (Default Log Level). La sortie du journal au sein du système est différenciée et contrôlée par l'intermédiaire de ces contextes.

Dans l'architecture système, ara::log::Logger agit comme intermédiaire entre trois intervenants :

  • Processus d'application (Application Process) : utilise des instances de ara::log::Logger pour émettre des messages, interroger ou adapter dynamiquement des seuils de filtrage.
  • Framework de journalisation : conserve une propriété stricte (« strong ownership ») sur toutes les instances de logger, contrôle leur création par le biais de fonctions de fabrique telles que ara::log::CreateLogger et prend en charge le housekeeping.
  • Backend de journalisation : reçoit les données de journalisation effectives ; les contextes de logger sont automatiquement enregistrés auprès du backend pendant la phase d'initialisation et désenregistrés lors de l'arrêt ordonné du processus.

Cycle de vie

La gestion des instances de ara::log::Logger est soumise à un contrôle strict par le framework afin de garantir une synchronisation sans faille avec le backend de journalisation :

  • Création et propriété : le constructeur par défaut est explicitement supprimé (Logger() = delete, [SWS_LOG_00259]). Une instanciation directe par l'application est interdite. La création s'effectue de manière contrôlée via des fonctions telles que ara::log::CreateLogger. La propriété reste acquise au framework de journalisation.
  • Enregistrement et nettoyage : un contexte de logger est automatiquement enregistré auprès du backend de journalisation lors de sa création. Lors de l'arrêt du processus, la désinscription s'effectue automatiquement, ce qui décharge les développeurs d'applications de la gestion manuelle du cycle de vie.
  • Destruction : le destructeur ~Logger() est spécifié ([SWS_LOG_00260]). Il est déclaré comme thread-safe, mais indiqué comme non sûr vis-à-vis des exceptions (« not exception safe ») ([SWS_LOG_00260]).
  • Concurrence : toutes les méthodes de journalisation et d'interrogation de seuil sont spécifiées comme thread-safe ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). Plusieurs threads peuvent utiliser la même instance de logger en parallèle.

Parcours d'utilisation

Le déroulement typique lors de l'émission de messages de journalisation se divise en les phases suivantes :

  1. Vérifier ou configurer le seuil de filtrage : l'application peut définir le seuil de filtrage d'une instance au moment de l'exécution via SetThreshold(threshold) ([SWS_LOG_00255]). Avant des préparations de données de journalisation coûteuses en calcul, IsEnabled(logLevel) permet de vérifier si le niveau de journalisation souhaité satisfait le seuil de rapport configuré ([SWS_LOG_00070]). Si la vérification renvoie false, la préparation peut être ignorée.
  2. Initier une journalisation basée sur les flux : pour la journalisation textuelle, la classe fournit des méthodes spécifiques pour chaque niveau de gravité :
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • WithLevel(logLevel) ([SWS_LOG_00131]) pour déterminer par programmation le degré d'urgence.
    Chacune de ces méthodes retourne un objet LogStream qui accepte des arguments via l'opérateur de flux << ([SWS_LOG_00064]).
  3. Durée de vie du flux et émission : par défaut, la durée de vie de l'objet LogStream est limitée à une seule instruction et se termine par le point-virgule après le dernier argument ([SWS_LOG_00064]). En cas de besoin, le flux peut être affecté à une variable afin d'étendre sa durée de vie sur plusieurs instructions ([SWS_LOG_00064]).
  4. Émettre des messages modélisés : comme alternative au streaming, des messages préalablement modélisés peuvent être émis via Log(id, args...) ([SWS_LOG_00204]). Si des attributs supplémentaires doivent être transmis, l'appel s'effectue via LogWith(attrs, msgId, params...) avec un tuple d'attributs ([SWS_LOG_00133]).

Scénarios d'erreur

La gestion des erreurs dans ara::log::Logger repose principalement sur la vérification statique des types au moment de la compilation et sur une sécurité stricte vis-à-vis des exceptions :

  • Arguments incompatibles pour les messages modélisés : si la fonction template Log(id, args...) est appelée avec des paramètres qui ne correspondent pas exactement à la définition du message modélisé, le programme est mal formé (« ill-formed ») ([SWS_LOG_00204]). Cela entraîne une erreur lors de la compilation.
  • Attributs non valides pour LogWith : pour LogWith(attrs, msgId, params...), la fonction est exclue de la résolution de surcharge par SFINAE si un élément du tuple d'attributs ne constitue pas un attribut valide ([SWS_LOG_00133]).
  • Garanties relatives aux exceptions : toutes les fonctions de journalisation et d'interrogation (dont IsEnabled, SetThreshold, toutes les méthodes Log*, WithLevel, Log et LogWith) sont spécifiées comme sûres vis-à-vis des exceptions (« exception safe ») et déclarées avec noexcept ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). Le destructeur ~Logger() fait exception, étant répertorié comme non sûr vis-à-vis des exceptions (« not exception safe ») ([SWS_LOG_00260]). Interprétation : cela devrait signifier qu'en cas d'erreurs internes de nettoyage ou de libération dans le cadre du housekeeping du backend, les états d'erreur ne sont pas entièrement interceptés, raison pour laquelle le désenregistrement devrait avoir lieu lors de l'arrêt régulier du processus.

<h4>Contexte</h4>
<p>La classe <code>ara::log::Logger</code> représente un contexte de journalisation au sein d'un processus d'application ou d'une zone de processus AUTOSAR Adaptive. Un tel contexte encapsule des propriétés centrales pour la journalisation : un ID de contexte, une description associée de l'ID de contexte ainsi qu'un niveau de journalisation par défaut configurable (Default Log Level). La sortie du journal au sein du système est différenciée et contrôlée par l'intermédiaire de ces contextes.</p>
<p>Dans l'architecture système, <code>ara::log::Logger</code> agit comme intermédiaire entre trois intervenants :</p>
<ul>
<li><strong>Processus d'application (Application Process) :</strong> utilise des instances de <code>ara::log::Logger</code> pour émettre des messages, interroger ou adapter dynamiquement des seuils de filtrage.</li>
<li><strong>Framework de journalisation :</strong> conserve une propriété stricte (« strong ownership ») sur toutes les instances de logger, contrôle leur création par le biais de fonctions de fabrique telles que <code>ara::log::CreateLogger</code> et prend en charge le housekeeping.</li>
<li><strong>Backend de journalisation :</strong> reçoit les données de journalisation effectives ; les contextes de logger sont automatiquement enregistrés auprès du backend pendant la phase d'initialisation et désenregistrés lors de l'arrêt ordonné du processus.</li>
</ul>

<h4>Cycle de vie</h4>
<p>La gestion des instances de <code>ara::log::Logger</code> est soumise à un contrôle strict par le framework afin de garantir une synchronisation sans faille avec le backend de journalisation :</p>
<ul>
<li><strong>Création et propriété :</strong> le constructeur par défaut est explicitement supprimé (<code>Logger() = delete</code>, <a class="spec-record-ref" data-req="SWS_LOG_00259" href="../spec/record.html?id=SWS_LOG_00259">[SWS_LOG_00259]</a>). Une instanciation directe par l'application est interdite. La création s'effectue de manière contrôlée via des fonctions telles que <code>ara::log::CreateLogger</code>. La propriété reste acquise au framework de journalisation.</li>
<li><strong>Enregistrement et nettoyage :</strong> un contexte de logger est automatiquement enregistré auprès du backend de journalisation lors de sa création. Lors de l'arrêt du processus, la désinscription s'effectue automatiquement, ce qui décharge les développeurs d'applications de la gestion manuelle du cycle de vie.</li>
<li><strong>Destruction :</strong> le destructeur <code>~Logger()</code> est spécifié (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). Il est déclaré comme thread-safe, mais indiqué comme non sûr vis-à-vis des exceptions (« not exception safe ») (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>).</li>
<li><strong>Concurrence :</strong> toutes les méthodes de journalisation et d'interrogation de seuil sont spécifiées comme thread-safe (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). Plusieurs threads peuvent utiliser la même instance de logger en parallèle.</li>
</ul>

<h4>Parcours d'utilisation</h4>
<p>Le déroulement typique lors de l'émission de messages de journalisation se divise en les phases suivantes :</p>
<ol>
<li><strong>Vérifier ou configurer le seuil de filtrage :</strong> l'application peut définir le seuil de filtrage d'une instance au moment de l'exécution via <code>SetThreshold(threshold)</code> (<a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>). Avant des préparations de données de journalisation coûteuses en calcul, <code>IsEnabled(logLevel)</code> permet de vérifier si le niveau de journalisation souhaité satisfait le seuil de rapport configuré (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>). Si la vérification renvoie <code>false</code>, la préparation peut être ignorée.</li>
<li><strong>Initier une journalisation basée sur les flux :</strong> pour la journalisation textuelle, la classe fournit des méthodes spécifiques pour chaque niveau de gravité :
<ul>
<li><code>LogFatal()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>)</li>
<li><code>LogError()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00065" href="../spec/record.html?id=SWS_LOG_00065">[SWS_LOG_00065]</a>)</li>
<li><code>LogWarn()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00066" href="../spec/record.html?id=SWS_LOG_00066">[SWS_LOG_00066]</a>)</li>
<li><code>LogInfo()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00067" href="../spec/record.html?id=SWS_LOG_00067">[SWS_LOG_00067]</a>)</li>
<li><code>LogDebug()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00068" href="../spec/record.html?id=SWS_LOG_00068">[SWS_LOG_00068]</a>)</li>
<li><code>LogVerbose()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00069" href="../spec/record.html?id=SWS_LOG_00069">[SWS_LOG_00069]</a>)</li>
<li><code>WithLevel(logLevel)</code> (<a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>) pour déterminer par programmation le degré d'urgence.</li>
</ul>
Chacune de ces méthodes retourne un objet <code>LogStream</code> qui accepte des arguments via l'opérateur de flux <code>&lt;&lt;</code> (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>Durée de vie du flux et émission :</strong> par défaut, la durée de vie de l'objet <code>LogStream</code> est limitée à une seule instruction et se termine par le point-virgule après le dernier argument (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). En cas de besoin, le flux peut être affecté à une variable afin d'étendre sa durée de vie sur plusieurs instructions (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>Émettre des messages modélisés :</strong> comme alternative au streaming, des messages préalablement modélisés peuvent être émis via <code>Log(id, args...)</code> (<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). Si des attributs supplémentaires doivent être transmis, l'appel s'effectue via <code>LogWith(attrs, msgId, params...)</code> avec un tuple d'attributs (<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
</ol>

<h4>Scénarios d'erreur</h4>
<p>La gestion des erreurs dans <code>ara::log::Logger</code> repose principalement sur la vérification statique des types au moment de la compilation et sur une sécurité stricte vis-à-vis des exceptions :</p>
<ul>
<li><strong>Arguments incompatibles pour les messages modélisés :</strong> si la fonction template <code>Log(id, args...)</code> est appelée avec des paramètres qui ne correspondent pas exactement à la définition du message modélisé, le programme est mal formé (« ill-formed ») (<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). Cela entraîne une erreur lors de la compilation.</li>
<li><strong>Attributs non valides pour LogWith :</strong> pour <code>LogWith(attrs, msgId, params...)</code>, la fonction est exclue de la résolution de surcharge par SFINAE si un élément du tuple d'attributs ne constitue pas un attribut valide (<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
<li><strong>Garanties relatives aux exceptions :</strong> toutes les fonctions de journalisation et d'interrogation (dont <code>IsEnabled</code>, <code>SetThreshold</code>, toutes les méthodes <code>Log*</code>, <code>WithLevel</code>, <code>Log</code> et <code>LogWith</code>) sont spécifiées comme sûres vis-à-vis des exceptions (« exception safe ») et déclarées avec <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>). Le destructeur <code>~Logger()</code> fait exception, étant répertorié comme non sûr vis-à-vis des exceptions (« not exception safe ») (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). Interprétation : cela devrait signifier qu'en cas d'erreurs internes de nettoyage ou de libération dans le cadre du housekeeping du backend, les états d'erreur ne sont pas entièrement interceptés, raison pour laquelle le désenregistrement devrait avoir lieu lors de l'arrêt régulier du processus.</li>
</ul>
