classe ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Encapsule un contexte de journalisation pour la collecte thread-safe de messages de protocole formatés ou modélisés.

La classe ara::log::Logger représente un contexte pour la capture de messages de log au sein d'un processus applicatif via des flux temporaires ou des formats de messages modélisés [SWS_LOG_00064]. Le constructeur par défaut étant supprimé, la création et la gestion du cycle de vie sont entièrement assurées par le framework de journalisation [SWS_LOG_00259]. Avant la préparation chronophage des données de message, le niveau de journalisation actuellement actif peut être interrogé. Toutes les interfaces de la classe sont spécifiées comme thread-safe et autorisent l'appel sans synchronisation depuis plusieurs threads.

Contexte

La classe ara::log::Logger représente un contexte de logger au sein d'un processus applicatif ou d'une zone de processus dans le module log. Un tel contexte encapsule un ID de contexte spécifique, une description associée ainsi qu'un niveau de journalisation par défaut. Les développeurs d'applications interagissent avec les instances de logger pour transmettre des messages de log au framework de journalisation, soit via des objets de flux tels que LogStream [SWS_LOG_00064], soit sous forme de messages structurés et modélisés [SWS_LOG_00204]. Les instances agissent comme intermédiaires entre les threads internes à l'application et le backend de journalisation.

Diagramme de contexte : intégration du logger entre l'application, le framework de journalisation et LogStream. Sources : [SWS_LOG_00064], [SWS_LOG_00259].

Cycle de vie

La gestion des instances est soumise à une propriété stricte par le framework de journalisation. Afin de garantir l'enregistrement automatique auprès du backend de journalisation lors de la création et le désenregistrement lors de l'arrêt du processus applicatif, le constructeur par défaut est supprimé [SWS_LOG_00259]. Les applications ne doivent et ne peuvent pas instancier directement des objets Logger, mais doivent à la place utiliser les fonctions de création ara::log::CreateLogger. La destruction et la libération s'effectuent via le destructeur [SWS_LOG_00260], qui est contrôlé par le framework de journalisation, de sorte que les utilisateurs n'ont pas à se soucier de la durée de vie.

En ce qui concerne la concurrence, toutes les méthodes d'accès sont spécifiées comme thread-safe (thread-safe), notamment [SWS_LOG_00070], [SWS_LOG_00255] et [SWS_LOG_00260]. Cela permet à plusieurs threads concurrents d'utiliser simultanément le même contexte de logger sans que des mécanismes de synchronisation supplémentaires ne soient requis du côté de l'application.

Parcours d'utilisation

L'utilisation typique d'un logger comprend la vérification de la configuration actuelle, l'ajustement des seuils et l'émission de messages :

  • Vérification de l'autorisation d'émission : avant de procéder à des préparations complexes de données de journalisation, il est possible de vérifier avec IsEnabled si un niveau de log souhaité est activement consigné [SWS_LOG_00070].
  • Configuration : le seuil minimal de consignation d'une instance de logger peut être reconfiguré à l'exécution via SetThreshold [SWS_LOG_00255].
  • Journalisation basée sur des flux : via des méthodes spécifiques pour les différents niveaux de gravité – LogFatal [SWS_LOG_00064], LogError [SWS_LOG_00065], LogWarn [SWS_LOG_00066], LogInfo [SWS_LOG_00067], LogDebug [SWS_LOG_00068] ou LogVerbose [SWS_LOG_00069] – ainsi que via le WithLevel dynamique [SWS_LOG_00131], un objet LogStream est créé. Celui-ci reçoit des données via l'opérateur <<. Habituellement, la durée de vie de l'objet flux se termine avec le point-virgule de l'instruction [SWS_LOG_00064].
  • Messages modélisés : alternativement, des messages typés et modélisés peuvent être transmis directement avec Log [SWS_LOG_00204] ou en spécifiant des attributs avec LogWith [SWS_LOG_00133].

Diagramme de séquence : séquence typique lors de la vérification de seuil et de la journalisation basée sur des flux. Sources : [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064].

Scénarios d'erreur

Les interfaces de la classe sont pour la plupart spécifiées comme noexcept et sûres face aux exceptions (exception safe), ce qui minimise les interruptions d'exécution inattendues [SWS_LOG_00070], [SWS_LOG_00255]. Néanmoins, des conditions d'erreur formelles et des cas limites existent :

  • Paramètres de modèle incorrects : si Log est appelé avec des arguments qui ne correspondent pas à la spécification du message modélisé, le programme C++ est incorrectement structuré (ill-formed) et échoue à la compilation [SWS_LOG_00204].
  • Propriétés d'attributs manquantes : si le tuple pour LogWith contient des types qui ne satisfont pas aux critères d'attributs requis, la fonction ne participe pas à la résolution de surcharge [SWS_LOG_00133]. L'exclusion s'effectue probablement via SFINAE ou des concepts.
  • Sécurité face aux exceptions lors de la destruction : le destructeur ~Logger est déclaré comme not exception safe [SWS_LOG_00260]. Cela est probablement dû au fait que, lors du désenregistrement auprès du backend de journalisation, des erreurs peuvent survenir qui ne doivent pas être propagées via des exceptions.

Ce guide se base exclusivement sur la spécification AUTOSAR pour le module log dans Adaptive Release R25-11.
