क्लास ara::log::LogStream

[SWS_LOG_00173] Upstream: RS_LT_00003, RS_LT_00046

class LogStream final {...};

Represents a Log message, allowing stream operators to be used for appending data. Note: Normally Application processes would not use this class directly. Instead one of the log methods provided in the main Logging API shall be used. Those methods automatically setup a temporary object of this class with the given log severity level. The only reason to use this class directly is, if the user wants to hold a ara::log::LogStream object longer than the default one-statement scope. This is useful in order to create log messages that are distributed over multiple code lines. See the ara::log::LogStream::Flush method for further information. Once this temporary object gets out of scope, its destructor takes care that the message buffer is ready to be processed by the Logging framework. Besides the existing supported operator<< overloads for ara::log::LogStream it can be easily extended for other derived types by providing a stream operator that makes use of already supported types.

Example: struct MyCustomType { int8_t foo; ara::core::String bar; };

LogStream& operator<<(LogStream& out, const MyCustomType& value) { return (out << value.foo << value.bar); }

// Producing the output "42 the answer is." Logger& ctx0 = CreateLogger("CTX0", "Context Description CTX0"); ctx0.LogDebug () << MyCustomType{42, " the answer is."};

स्ट्रीम ऑपरेटरों के माध्यम से लॉग डेटा बफ़र करता है और लॉगिंग फ़्रेमवर्क को स्वरूपित संदेश पास करता है।

वर्ग ara::log::LogStream एक प्रारूपण योग्य लॉग संदेश (प्रोटोकॉल संदेश) का प्रतिनिधित्व करता है, जिसका आंतरिक बफ़र स्ट्रीम ऑपरेटरों के माध्यम से डेटा और मेटाडेटा से चरणबद्ध रूप से भरा जाता है। इसके इंस्टैंस आमतौर पर लॉगिंग विधियों के माध्यम से अस्थायी रूप से प्राप्त किए जाते हैं और स्कोप से बाहर निकलते समय डिस्ट्रक्टर के माध्यम से कैप्चर की गई सामग्री को स्वचालित रूप से लॉगिंग फ्रेमवर्क को अग्रेषित करते हैं [SWS_LOG_00262]। बहु-पंक्ति या पुन: प्रयोज्य संदेशों के लिए, Flush() के माध्यम से फ़ॉरवर्डिंग को स्पष्ट रूप से ट्रिगर किया जा सकता है [SWS_LOG_00039]। एक प्रमुख बाधा के रूप में, यह वर्ग थ्रेड-सुरक्षित नहीं है और कॉपी परिचालनों को पूरी तरह से रोकता है।

संदर्भ

वर्ग ara::log::LogStream एडेप्टिव लॉगिंग सबसिस्टम में एक फ़ॉर्मेट करने योग्य लॉग संदेश का प्रतिनिधित्व करता है। यह एक संदेश-आधारित बफ़र इंटरफ़ेस प्रदान करता है, जो ओवरलोड किए गए स्ट्रीम ऑपरेटरों के माध्यम से एक आंतरिक बफ़र में विषम पेलोड डेटा के चरणबद्ध रूप से जोड़ने में सक्षम बनाता है।

नियमित उपयोग के मामले में, एप्लिकेशन प्रक्रियाएं LogStream के स्पष्ट इंस्टेंसिएशन के माध्यम से सीधे इंटरैक्ट नहीं करती हैं। इसके बजाय, मुख्य लॉगिंग API (उदाहरण के लिए LogDebug() जैसी लॉगिंग विधियों के माध्यम से) इस वर्ग के अस्थायी इंस्टेंस प्रदान करती है, जो आवश्यक सेवेरिटी स्तर (severity level) के साथ पहले से ही आरंभ किए गए हैं। मानक एकल-कथन स्कोप (One-Statement-Scope) से परे LogStream ऑब्जेक्ट को बनाए रखने का एकमात्र इच्छित कारण कोड की कई पंक्तियों में लॉग संदेशों को संयोजित करना है। जैसे ही ऑब्जेक्ट अपने स्कोप से बाहर निकलता है या स्पष्ट रूप से खाली किया जाता है, बफ़र सामग्री को आगे के प्रसंस्करण के लिए लॉगिंग फ़्रेमवर्क को सौंप दिया जाता है।

जीवनचक्र

LogStream इंस्टेंस का निर्माण मुख्य रूप से मुख्य लॉगिंग API के फ़ैक्टरी विधियों के माध्यम से एक अस्थायी ऑब्जेक्ट के रूप में होता है। कुशल प्रावधान के लिए, वर्ग एक मूव कंस्ट्रक्टर को noexcept [SWS_LOG_00176] के रूप में घोषित करता है। यह मूव कंस्ट्रक्टर आमतौर पर केवल घोषित किया जाता है और परिभाषित नहीं किया जाता है, जो C++14-अनुपालन करने वाले कंपाइलरों को फ़ैक्टरी फ़ंक्शनों से रिटर्न करते समय Return Value Optimization (RVO) का उपयोग करने की अनुमति देता है [SWS_LOG_00176]। इंस्टेंस का दोहराव या मूव असाइनमेंट पूरी तरह से वर्जित है: कॉपी कंस्ट्रक्टर [SWS_LOG_00174], कॉपी असाइनमेंट ऑपरेटर [SWS_LOG_00175] और मूव असाइनमेंट ऑपरेटर [SWS_LOG_00177] हटा दिए गए हैं (=delete)।

जीवनकाल का अंत डिस्ट्रक्टर ~LogStream() द्वारा प्रबंधित किया जाता है [SWS_LOG_00262]। यदि ऑब्जेक्ट अपने स्कोप से बाहर निकल जाता है (उदाहरण के लिए फ़ंक्शन ब्लॉक या कथन के अंत में), तो डिस्ट्रक्टर आंतरिक रूप से यह सुनिश्चित करता है कि बफ़र सामग्री को प्रसंस्करण के लिए लॉगिंग फ़्रेमवर्क में अग्रेषित किया जाए [SWS_LOG_00039], [SWS_LOG_00262]।

यदि एक ही स्कोप में कई लगातार संदेशों के लिए LogStream इंस्टेंस का पुन: उपयोग किया जाता है, तो सदस्य फ़ंक्शन Flush() को कॉल किया जाना चाहिए [SWS_LOG_00039]। यहाँ यह महत्वपूर्ण है कि Flush() बफ़र को खाली नहीं करता है, बल्कि वर्तमान डेटा को लॉगिंग फ़्रेमवर्क में भेजता है और तुरंत एक नया संदेश स्ट्रीम शुरू करता है [SWS_LOG_00039]।

समवर्तीता (concurrency) के संबंध में, सभी सदस्य फ़ंक्शन गैर-थ्रेड-सुरक्षित के रूप में निर्दिष्ट हैं ([SWS_LOG_00039], [SWS_LOG_00040], [SWS_LOG_00129])। इसलिए, बिना किसी बाहरी सिंक्रोनाइज़ेशन के कई थ्रेड्स द्वारा समानांतर में LogStream इंस्टेंस का उपयोग नहीं किया जाना चाहिए।

उपयोग पथ

एक विशिष्ट लॉगिंग वर्कफ़्लो में निम्नलिखित चरण शामिल होते हैं:

  1. स्ट्रीम प्रावधान: एप्लिकेशन प्रक्रिया एक लॉगिंग विधि को कॉल करती है, जो एक अस्थायी LogStream इंस्टेंस बनाती है और इसे RVO के माध्यम से लौटाती है [SWS_LOG_00176]।
  2. मेटाडेटा संवर्धन: डेटा इनपुट से पहले या उसके दौरान, वैकल्पिक विशेषताओं को मेथड चेनिंग (method chaining) के माध्यम से जोड़ा जा सकता है, जिसमें WithLocation(file, line) [SWS_LOG_00129] के माध्यम से स्रोत कोड स्थान, WithTag(tag) [SWS_LOG_00132] के माध्यम से टैग, या WithPrivacy(value) [SWS_LOG_00258] के माध्यम से गोपनीयता स्तर शामिल हैं। इनमें से प्रत्येक विधि *this का एक संदर्भ लौटाती है।
  3. डेटा भरना: ओवरलोड किए गए ऑपरेटरों operator<< के माध्यम से पेलोड डेटा को आंतरिक बफ़र में लिखा जाता है। इंटरफ़ेस बूलियन मान [SWS_LOG_00040], विभिन्न बिट-चौड़ाई के पूर्णांक [SWS_LOG_00041], [SWS_LOG_00044], फ़्लोटिंग-पॉइंट संख्याएँ [SWS_LOG_00049], वर्ण स्ट्रिंग्स और स्ट्रिंग व्यू [SWS_LOG_00051], [SWS_LOG_00062], core::Span<const core::Byte> [SWS_LOG_00128] के माध्यम से बाइट अनुक्रम, साथ ही Argument<T> [SWS_LOG_00203] के माध्यम से संरचित तर्क जैसे मानक प्रकारों का समर्थन करता है। इसके अतिरिक्त, उपयोगकर्ता-परिभाषित प्रकारों के लिए ऑपरेटर को विस्तारित किया जा सकता है।
  4. फ़्रेमवर्क को सौंपना: स्कोप छोड़ते समय, डिस्ट्रक्टर संदेश को अग्रेषित करता है [SWS_LOG_00262]। यदि इंस्टेंस को आगे के संदेशों के लिए बनाए रखा जाना है, तो Flush() को स्पष्ट रूप से कॉल किया जाता है [SWS_LOG_00039]।

त्रुटि परिदृश्य

वर्ग एक सख्त No-Exception-Design का पालन करता है। स्ट्रीम ऑपरेटरों ([SWS_LOG_00040] से [SWS_LOG_00051], [SWS_LOG_00062], [SWS_LOG_00128], [SWS_LOG_00203]), WithLocation() [SWS_LOG_00129], WithTag() [SWS_LOG_00132], WithPrivacy() [SWS_LOG_00258], Flush() [SWS_LOG_00039] और डिस्ट्रक्टर [SWS_LOG_00262] सहित सभी सदस्य फ़ंक्शन noexcept के रूप में घोषित हैं और अपवाद-सुरक्षित (\"exception safe\") हैं।

त्रुटि स्थितियाँ और उपयोग के जोखिम निम्नलिखित परिदृश्यों तक सीमित हैं:

  • WithPrivacy में प्रकार त्रुटियाँ: टेम्पलेट WithPrivacy<T> को अनिवार्य रूप से आवश्यक है कि T एक पूर्णांक प्रकार या एक गणना प्रकार (enumeration type) हो। यदि फ़ंक्शन को किसी भिन्न प्रकार के साथ इंस्टेंसिएट किया जाता है, तो प्रोग्राम त्रुटिपूर्ण (ill-formed) होता है और संकलन त्रुटि (compilation error) का कारण बनता है [SWS_LOG_00258]। इसके अतिरिक्त, पास किए गए मान के केवल न्यूनतम महत्वपूर्ण 8 बिट्स (least significant 8 bits) का उपयोग किया जाता है, उच्च-क्रम बिट्स को अनदेखा कर दिया जाता है [SWS_LOG_00258]।
  • थ्रेड-सुरक्षा का अभाव: चूँकि LogStream को गैर-थ्रेड-सुरक्षित के रूप में परिभाषित किया गया है ([SWS_LOG_00039], [SWS_LOG_00040]), इसलिए बाहरी सिंक्रोनाइज़ेशन के बिना एक ही इंस्टेंस पर समवर्ती रीड या राइट संचालन संभवतः डेटा असंगति या बफ़र भ्रष्टाचार का कारण बन सकते हैं (व्याख्या)। प्रश्न Q-30a5037999c96fa2 (खुला)
  • फ़्लश पर बफ़र हैंडओवर: चूँकि Flush() बफ़र को भौतिक रूप से खाली नहीं करता है, बल्कि केवल लॉगिंग फ़्रेमवर्क को वर्तमान सामग्री सौंपता है [SWS_LOG_00039], पुन: उपयोग करते समय यह ध्यान में रखा जाना चाहिए कि अर्थगत रूप से एक नया संदेश शुरू हो गया है।

यह मार्गदर्शिका Adaptive Platform (रिलीज़ R25-11) के लिए AUTOSAR विनिर्देश पर आधारित है और स्वचालित रूप से तैयार की गई थी।

Flush फ़ंक्शन

Sends out the current log buffer and initiates a new message stream. Note: Calling ara::log::LogStream::Flush is only necessary if the ara::log::LogStream object is going to be re-used within the same scope. Otherwise, if the object goes out of scope (e.g. end of function block) then the flushing operation will be done internally by the destructor. It is important to note that the ara::log::LogStream::Flush command does not empty the buffer, but it forwards the buffer’s current contents to the Logging framework.

              हेडर ara/log/log_stream.h से क्लास ara::log::LogStream का मेंबर फ़ंक्शन WithLocation एक लॉग संदेश में सोर्स कोड स्थिति डेटा जोड़ने का काम करता है [SWS_LOG_00129]। यह कॉल सिंक्रोनस रूप से निष्पादित होती है और पैरामीटर के रूप में फ़ाइल पहचानकर्ता file को core::StringView के रूप में तथा लाइन संख्या line को एक पूर्णांक मान (int) के रूप में स्वीकार करती है [SWS_LOG_00129]। रिटर्न मान के रूप में संशोधित स्ट्रीम ऑब्जेक्ट (*this) का संदर्भ प्रदान किया जाता है, जो संभवतः आगे के स्ट्रीमिंग आउटपुट के फ़्लुएंट चेनिंग के काम आता है [SWS_LOG_00129]। प्रश्न Q-c65fe863c9b31f20 (खुला)
              

              त्रुटि प्रबंधन के लिए यह प्रासंगिक है कि फ़ंक्शन को पहचानकर्ता noexcept प्रदान किया गया है और इसे अपवाद-सुरक्षित (“exception safe”) के रूप में निर्दिष्ट किया गया है [SWS_LOG_00129]। न तो कोई विशिष्ट त्रुटि कोड और न ही अपवाद शर्तें परिभाषित हैं, इसलिए कॉल के दौरान किसी पृथक अपवाद प्रबंधन या त्रुटि जाँच की आवश्यकता नहीं है।
              

              समवर्तीता (concurrency) और निष्पादन प्रतिबंधों के संबंध में, WithLocation को स्पष्ट रूप से गैर-थ्रेड-सुरक्षित (“not thread-safe”) नामित किया गया है [SWS_LOG_00129]। यदि एकाधिक थ्रेड्स का उपयोग किया जाता है, तो LogStream के समान इंस्टेंस को बिना बाहरी सिंक्रोनाइज़ेशन के समानांतर संशोधित नहीं किया जाना चाहिए। आम तौर पर, इसलिए ऑब्जेक्ट का उपयोग संबंधित लॉगिंग प्रक्रिया के लिए विशुद्ध रूप से थ्रेड-लोकल रूप में किया जाता है।
