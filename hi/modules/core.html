पीढ़ी, जीवन चक्र एवं स्वामित्व

संपूर्ण ARA lifecycle को centrally दो free functions ara::core::Initialize और ara::core::Deinitialize द्वारा नियंत्रित किया जाता है। Initialize ARA framework शुरू करता है; इसमें internal data structures और system resources को initialize करना तथा background threads शुरू करना शामिल हो सकता है [SWS_CORE_15003]। यदि Initialize command-line arguments की injection उपयोग करता है, तो संबंधित arguments को पारदर्शी रूप से हटाना चाहिए ताकि application का argument parsing प्रभावित न हो [SWS_CORE_15006]। सफल call framework को ऐसी स्थिति में रखता है जिसमें सभी configured components तुरंत API calls संभाल सकें [SWS_CORE_90026]; पिछले Deinitialize के बिना दूसरा call चल रहे instance को प्रभावित किए बिना kAlreadyInitialized देता है [SWS_CORE_90029]। इसके विपरीत Deinitialize framework shutdown शुरू करता है, जिसमें शुरू किए गए background threads का अंत और dynamic memory तथा अन्य system resources को मुक्त करना शामिल है [SWS_CORE_15004]; framework सफलतापूर्वक initialized न हो या पहले deinitialized हो तो प्रत्येक call kNotInitialized देता है [SWS_CORE_90030]।

ara::core का केवल एक छोटा, स्पष्ट रूप से नामित उपसमुच्चय - दूसरों के बीच में। ErrorCode, StringView, Result (ValueOrThrow के बिना), ErrorDomain (ThrowAsException के बिना), Initialize, Abort, SetAbortHandler और AddAbortHandler - का उपयोग Initialize/Deinitialize [SWS_CORE_15002] से स्वतंत्र रूप से किया जा सकता है। Initialize से पहले अन्य सभी ARA फ़ंक्शंस का व्यवहार कार्यान्वयन-परिभाषित [SWS_CORE_15005] है, और इस उपसमूह के बाहर Deinitialize पर कॉल में भी कार्यान्वयन-परिभाषित व्यवहार होता है, क्योंकि प्रदर्शन कारणों से [SWS_CORE_90022] के लिए संबंधित रनटाइम जांच की जानबूझकर आवश्यकता नहीं थी। Guidelines for using Adaptive Platform interfaces इसे एक बाध्यकारी स्टार्टअप/शटडाउन अनुबंध के रूप में सारांशित करता है: Initialize को प्रवेश बिंदु, Deinitialize पर केवल सभी ARA संसाधनों को अन्य थ्रेड्स में जारी किए जाने के बाद ही कॉल किया जाना है; दोनों Result<void> लौटाते हैं, जिसे जांचना होगा, और एक त्रुटि को ठीक नहीं किया जा सकता है, इसलिए एप्लिकेशन को EXIT_FAILURE (EXP InterfacesGuidelines) के साथ समाप्त होना चाहिए। इसके अलावा, AUTOSAR AP RS General क्लस्टर-विशिष्ट इनिशियलाइज़ेशन फ़ंक्शंस को प्रतिबंधित करता है: यदि किसी फ़ंक्शन क्लस्टर को स्पष्ट इनिशियलाइज़ेशन या डी-इनिशियलाइज़ेशन की आवश्यकता होती है, तो उसे विशेष रूप से ara::core::Initialize/ara::core::Deinitialize का उपयोग करना होगा।

त्रुटि प्रबंधन, समवर्तीता और सीमाएँ

विनिर्देश थ्रेड सुरक्षा को सटीक रूप से परिभाषित करता है: एक गैर-स्थैतिक AUTOSAR-API सदस्य फ़ंक्शन थ्रेड-सुरक्षित है यदि इसे कॉलर द्वारा सिंक्रनाइज़ेशन के बिना एकाधिक थ्रेड से एक ही ऑब्जेक्ट पर एक साथ कॉल किया जा सकता है; डिस्ट्रक्टर और असाइनमेंट ऑपरेटर आमतौर पर थ्रेड-सुरक्षित नहीं होते हैं [SWS_CORE_13200]। यदि एक गैर-थ्रेड-सुरक्षित सदस्य फ़ंक्शन को एक ही ऑब्जेक्ट पर समवर्ती रूप से कॉल किया जाता है, तो व्यवहार अपरिभाषित होता है - भले ही इसमें शामिल अन्य फ़ंक्शन थ्रेड-सुरक्षित हो [SWS_CORE_13203]; हालाँकि, विभिन्न उदाहरणों पर प्रतिस्पर्धी कॉलों को सिंक्रनाइज़ेशन के बिना अनुमति दी जाती है [SWS_CORE_13205]। ARA कार्यान्वयन कॉलबैक या विशुद्ध रूप से आभासी कार्यों को विशेष रूप से अनुक्रमिक रूप से गैर-थ्रेड-सुरक्षित के रूप में निर्दिष्ट करता है, उदाहरण के लिए ara::tsync::SynchronizedTimeBaseNotifier, जबकि उदा। बी. ara::phm::RecoveryAction::RecoveryHandler थ्रेड-सुरक्षित है [SWS_CORE_13214]। सिग्नल हैंडलर के भीतर किसी भी ARA-APIs का उपयोग करने से अपरिभाषित व्यवहार होता है जब तक कि अन्यथा निर्दिष्ट न हो [SWS_CORE_13210] (EXP InterfacesGuidelines: एसिंक सिग्नल सुरक्षा)। इसके अलावा, AUTOSAR AP RS General के लिए आवश्यक है कि प्रत्येक API फ़ंक्शन अपने थ्रेड सुरक्षा स्तर को “thread-safe”, “not thread-safe” या “conditional” के रूप में निर्दिष्ट करे, और थ्रेड सुरक्षा अनुबंध द्विदिश रूप से लागू होता है: यदि एक API थ्रेड-सुरक्षित निर्दिष्ट किया गया है, तो विक्रेता या उपयोगकर्ता द्वारा प्रदान किया गया कार्यान्वयन, जैसे कॉलबैक या पूरी तरह वर्चुअल Skeleton फ़ंक्शन, इस वादे का अनुपालन करते हैं। (EXP InterfacesGuidelines).

पुनर्प्राप्त न की जा सकने वाली त्रुटियों के लिए, ara::core नियमित त्रुटि प्रबंधन से उल्लंघन को अलग करता है: एक उल्लंघन ढांचे की उल्लंघन की गई पूर्व या बाद की स्थितियों का परिणाम है और पुनर्प्राप्त करने योग्य नहीं है, एक असफल दावे [SWS_CORE_00021] के बराबर है। मानकीकृत उल्लंघन के मामले में, प्रक्रिया ara::core::Abort के माध्यम से असामान्य रूप से समाप्त हो जाती है; डीएलटी परिभाषा के अनुसार एक डिबग संदेश stderr पर आउटपुट होता है और इसे डिटेक्टिंग फ़ंक्शन क्लस्टर [SWS_CORE_00090] की संदर्भ आईडी के साथ लॉग सिंक पर लिखा जाना चाहिए। जबकि Abort पर कॉल प्रगति पर है, आगे की कॉलें कॉलिंग थ्रेड्स [SWS_CORE_12407] को ब्लॉक कर देती हैं; स्थापित एबॉर्ट हैंडलर्स को रिवर्स इंस्टॉलेशन क्रम में बुलाया जाता है; हैंडलर के बिना, std::abort() को [SWS_CORE_12404] कहा जाता है। Result/ErrorCode और गैर-वसूली योग्य उल्लंघन [SWS_CORE_00021] के माध्यम से पुनर्प्राप्त करने योग्य त्रुटियों का यह पृथक्करण सभी एपी फ़ंक्शन क्लस्टर के लिए एक सामान्य सिद्धांत के रूप में AUTOSAR AP RS General द्वारा समर्थित है।

प्रत्येक ARA Functional Cluster, ara::log के माध्यम से लॉगिंग करते समय, ara::core से मानकीकृत Log-and-Trace सेटिंग्स का उपयोग करता है, विशेषकर Context ID और Message-ID रेंज [SWS_CORE_00055] का। इसके लिए Specification प्रत्येक Functional Cluster हेतु मानकीकृत log-context IDs परिभाषित करती है, जैसे com के लिए #COM, core के लिए #COR, crypto के लिए #CRY, diag के लिए #DIA, exec के लिए #EXE, log के लिए #LOG और per के लिए #PER [SWS_CORE_90024]। आवश्यकता स्तर पर AUTOSAR AP RS General यह जोड़ता है कि ARA Interfaces को C++ standard types के स्थान पर ara::core types का उपयोग करना होगा, यदि ara::core समतुल्य type उपलब्ध कराता है। चूंकि namespace ara पूर्णतः AUTOSAR के लिए आरक्षित है, किसी Functional Cluster के सभी data types forwarding-header file <fc>_fwd.h के माध्यम से भी उपलब्ध हैं (EXP InterfacesGuidelines)।
