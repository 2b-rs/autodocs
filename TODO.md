# TODO — Open Point List

HOW TO USE:

- *Features* are represented as 2nd level Headings.
- New *Features* shall normally be added to the top of list
- Features have an ID. 
- They consist of *Tasks* whose prefix corresponds to the Feature's ID.
- a *Feature* is considered complete once all of its *Tasks* are complete.
- Complete *Features* shall be moved to DONE.md and marked with a completion date + time. TODO.md and DONE.md must be committed after each completed feature.

- *Tasks* are dashed items whose first line carries a completion marker and task ID. Supporting acceptance-criteria, Definition-of-Done, decision, and history bullets may follow.
  [ ] - open. No work has been done w/r to this item
  [u] - unclear. No agentic work can currently be performed on this item because user/manager discussion, authorization, or clarification is required before proceeding.
  [p] - partially implemented. The agent has started work on this item, but it is not yet complete; use this while work is in progress, including across conversations, so agents can determine the next best unfinished item.
  [?] - unknown - we simply don't know. Next step is to look into the repository and decide whether to amend TODO or promote to `[x]`.
  [w] - wontfix. Investigation is complete and the task is closed without code changes because the reported issue is invalid as written, no longer reproducible, superseded, or otherwise not worth fixing. `[w]` is a terminal state and shall be treated like `[x]` for dependency / feature-completion purposes. A `[w]` task must include a `Reason:` bullet explaining the disposition; add `REF: xxxxxx` when the disposition itself is committed.
  [x] - executed - task has been completed. If a task is completed, the results shall be checked in and `REF: xxxxxx` (git hash) shall be added.
- A task's imperative sentence and any **Acceptance criteria** bullets are normative. The sentence must identify an observable deliverable or result; add explicit acceptance criteria and a **Definition of Done** whenever completion, failure behavior, evidence, or review authority would otherwise be ambiguous.
- Unless a task states a stricter gate, `[x]` requires the committed deliverable, the specified validation or authorized review evidence, resolution or explicit disposition of material findings, and the commit `REF`.
- *Tasks* shall have a granularity so that they can be implemented in one go. If preparation or implementation is agentic but the final approval/rating/acceptance requires a named human authority, split the work or keep it `[p]`; set `[u]` only when that human decision is the next unresolved action. Do not copy `[u]` transitively to every dependent task: its explicit prerequisite already records the block.
- A task/subtask prerequisite is a **start gate** for that item. A Feature prerequisite is a **Feature-closure gate**: individual tasks may proceed when their own start gates permit, but the dependent Feature cannot move to `DONE.md` first. Conditional or alternative lifecycle dependencies must be materialized after the governing scope decision as explicit task prerequisites or as machine-enforced selected-profile edges; prose-only dependencies are not sufficient.
- Agents shall keep these markers up to date while working and in conversation hand-offs: set `[p]` once implementation/investigation has started, set `[u]` only as defined above, and avoid leaving active work as plain `[ ]` when a better state is known.

## ID scheme

- *Feature names* are kept consistent in English (translate on introduction if needed).

- Every *Feature* gets a unique **feature ID**: a 4-digit number with leading zeroes, e.g. `0001`. Feature headings are written as `## Feature: XXXX — <name>`.

- Every *Task* within a feature gets a **task ID** `XXXX-YY`, where `XXXX` is the feature ID and `YY` is a 2-digit task number, unique within that feature (e.g. `0001-01`, `0001-02`). Task IDs are rendered in bold right after the checkbox marker, e.g. `- [ ] **0001-01** ...`.

- A *Task* may be split into **subtasks**, identified as `XXXX-YY.ZZ`, where `ZZ` is a 2-digit subtask number unique within that task (e.g. `0001-01.01`, `0001-01.02`).

- *Tasks* and *Features* may declare **prerequisites** — other tasks/features that must be done first. One prerequisite relation is written as:

  `XXXX[-YY[.ZZ]]:AAAA[-BB[.CC]]`

  - `XXXX` — feature ID of the dependent item
  - `-YY` / `.ZZ` — optional dependent task/subtask; omitted means the whole feature depends on the prerequisite
  - `AAAA` — feature ID of the prerequisite
  - `-BB` / `.CC` — optional prerequisite task/subtask; omitted means the dependency is on the whole feature
  - Multiple prerequisites are a comma-separated list of complete relations; the dependent ID is repeated in each relation.

  Examples:
  - `0002:0001` — Feature `0002` as a whole depends on Feature `0001` as a whole.
  - `0002-09:0001` — Task `0002-09` depends on Feature `0001` as a whole.
  - `0002-09:0001-08` — Task `0002-09` depends specifically on Task `0001-08`.
  - `0006-04.02:0006-04.01` — Subtask `0006-04.02` depends on sibling Subtask `0006-04.01`.
  - `0014-13:0015-06, 0014-13:0016-01` — Task `0014-13` has two prerequisites.

  Prerequisites are noted inline in the task/feature text after `PREREQ:`.

## Feature: 0037 — Git-Native Issue Store, Provenance Graph, and Backlog Migration

**PREREQ:** 0037:0002, 0037:0006

**Decision — canonical paths (2026-08-16, user approved proposal):** A Feature is authoritative at `issues/XXXX/index.md`. Every Task or Subtask is authoritative in its own stable directory at `issues/XXXX/XXXX-YY[.ZZ]/index.md`; Task/Subtask directories stay flat beneath the Feature and use structured `parent` references rather than filesystem nesting. Item directories may additionally contain `claim.json`, terminal `closure.json`, `decisions/`, and `attachments/`. IDs, never titles or lifecycle states, determine paths. A same-directory `feature.md` plus many `task-*.md` files was rejected because it provides no isolated namespace for claims/closures/evidence and increases Feature-directory contention; deeply nesting Subtasks was rejected because hierarchy is already encoded by IDs and would make reclassification/moves unnecessarily disruptive.

**Goal:** Replace the merge-prone authoritative `TODO.md`/`DONE.md` database with one human-readable, schema-enforced Markdown item per Feature/Task/Subtask; generate legacy lists, query catalogs, dependency graphs, and published embeddings deterministically; and add typed provenance so reports, findings, fixes, re-scrapes, database snapshots, AI artifacts, diagrams, user guides, i18n outputs, HTML trees, validation evidence, and release decisions can be followed as one causal graph.

**Authority and migration boundary:** Until authorized cutover, committed `TODO.md`, `DONE.md`, and active claim files remain authoritative and `issues/` is a disposable shadow database. The migration implementation, schemas, Feature `0037` itself, and the legacy source database will all change while migration is developed. Therefore migration must operate from explicit Git source/cutover commits, support deterministic full shadow re-import plus schema-to-schema transformation, and reconcile every committed delta before cutover; agents must not hand-maintain both databases or treat an early import as frozen truth. At cutover, one reviewed commit atomically makes `issues/**/index.md` authoritative and turns `TODO.md`, `DONE.md`, catalogs, graphs, and website payloads into generated views. Uncommitted/staged backlog changes or unresolved live claims block the final import.

**Resolved architecture baseline for implementation planning (2026-08-16):**
- The issue parser will use a pinned `ruamel.yaml` release in safe YAML 1.2 mode, declared by a root `pyproject.toml` and reproducible `requirements.lock`. The accepted profile rejects duplicate keys, aliases/anchors, merge keys, custom tags, multiple documents, non-string mapping keys, implicit timestamps, non-finite numbers, and over-limit inputs; controlled writers preserve Markdown prose and canonically rewrite only structured regions.
- Acceptance criteria use immutable item-local IDs `AC-NNN`. New criteria receive the next unused number; deletion creates a retained tombstone; intent-preserving wording edits retain the ID; scope/verification changes supersede the old criterion with a new ID; moving a criterion to another item creates a new ID plus a typed derivation relation. IDs are never renumbered.
- A committed item-local `claim.json` is retained state, not a global mutex. Same-clone worktrees acquire `refs/autodocs/claims/<item-id>` by compare-and-swap; independent clones race to a protected, serialized integration branch, whose validator rejects stale-base, overlapping-scope, duplicate, or conflicting claims. Lease expiry never silently transfers ownership; a registered authority must approve takeover and preserve claim/release/recovery events.
- The complete issue store and maintainer graph are internal by default. Publication first creates a locale-neutral allowlisted projection containing only explicitly `public-summary` items and approved fields (ID, level, title key/source hash, coarse state, public prerequisites, public summary/link), then joins approved title/UI translations into per-language payloads. Claims, people, private paths, detailed findings/decisions/evidence, security labels, unreleased items, and incident edges to omitted nodes are excluded; output reports only an aggregate restricted-item count.
- Issue bodies remain canonical-only and are not automatically published or translated. Graph controls, legends, state/edge labels, and every explicitly public title are translated for the canonical language plus all targets from `_src/site.json`; IDs, refs, paths, hashes, code, and criterion IDs are never translated. Missing required public title/UI translations fail publication; maintainer tools may visibly fall back to the canonical English title.
- The graph pipeline is `issue Markdown → Python normalized catalog → graph-projection JSON → shared JavaScript graph-semantic core → DOT → Graphviz SVG`. Browser JavaScript never parses YAML/Markdown or reinfers lifecycle/dependency semantics. The website receives per-language sanitized payloads and generated SVG/no-JS summaries; the maintainer tool receives the internal projection. Graphviz, Node, font assets, locale/timezone, and SVG-normalization behavior are selected in the architecture package and installed by a locked toolchain Task.
- Version 1 deliberately has no SQLite view. `issues/_views/catalog.json`, `issues/_views/dependency-graph.json`, and `issuectl` queries are the supported disposable read model; SQLite requires a later measured-performance Feature.
- Immutable provenance uses one JSON object per file: `provenance/events/YYYY/MM/<event-id>.json`, content-addressed `provenance/artifact-sets/<sha256>.json`, `provenance/runs/<run-id>.json`, and `provenance/findings/YYYY/MM/<finding-id>.json`; disposable indexes live under `provenance/_views/`. Migration candidates use `_src/output/issue-migration/<run-id>/`; retained migration evidence uses `provenance/migrations/issue-store/<run-id>/`.
- Human approvals are machine-readable records tied to exact commits and artifact digests, stored as SSH-signed commits on dedicated immutable `refs/autodocs/approvals/<decision-id>` refs and verified against the policy revision in the approved package plus an owner fingerprint confirmed out of band. Approval refs do not advance the prepared integration parent. Author strings, `Signed-off-by`, requester authentication, tests, and self-approval are not authorization. Contract approval requires registered process, security/privacy, and release roles; Tasks `0037-32` and `0037-36` require an independent quality role that did not author the candidate/cutover under review; Task `0037-33` requires process, security/privacy, and release authority.
- `SANDBOX.md` and `AGENTS.md` are stable, canonical human bootstrap interfaces—not generated backlog views—and root `agent-workflow.json` is their machine-readable authority/version/capability selector. Agents are explicitly `sandboxed-grunt` or `privileged`; unknown means sandboxed. Feature `0037` assumes no privileged agent is available. Sandboxed agents read/write only through non-execution tools and submit every process/test/generator/browser/network/package/Git operation to the less-restricted runner. Before every pickup they read the bundle and obtain the runner-backed doctor result; it identifies authority, epoch, capability phase, runner protocol, and permitted claim/edit/close actions. No session crosses cutover: all agents/claims/runner requests quiesce first, the instruction bundle changes in the authority-switch tree, and stale or direct legacy writes fail with an actionable re-bootstrap diagnostic. Rollback restores the matching legacy instruction and runner profile.
