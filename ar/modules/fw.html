يبدل مجموعات قواعد Firewall المعتمدة على الحالة للمنصة ويبلغ عن الحزم المحظورة كـ Security Events.

يقوم Functional Cluster المسمى Firewall بفلترة حزم الشبكة وفقًا لمجموعات قواعد معتمدة على الحالة من البيان (manifest) ويبلغ عن الحزم المحظورة كـ Security Events إلى IdsM (EXP_PlatformDesign ص. 92). تختار التطبيقات حالة Firewall النشطة عبر FirewallStateSwitchInterface::SwitchFirewallState. تُرجع الدالة ara::core::Future<void> وتبلغ عن أخطاء مثل kServiceNotAvailable أو kInvalidStateDependentFirewall [AP_SWS_Fw_82008]. لا تمثل الحالات قائمة ثابتة، بل تُنشأ كترقيم (enumeration) لكل واجهة تمت نمذجتها. يمكن نقل مثيلات الواجهة فقط، ولا يمكن نسخها.

تحدد الوحدة النمطية fw الـ Functional Cluster المعتمد على برنامج خفي (daemon) والمسمى Firewall لـ Adaptive Platform. واجهة برمجة التطبيقات (API) الخاصة بتطبيقاته هي الواجهة FirewallStateSwitchInterface مع العملية SwitchFirewallState()، والتي يستخدمها Adaptive Application (EXP_SWArchitecture ص. 126). يمتلك الـ cluster مهمتين: تبديل حالة Firewall والإبلاغ عن Security Events إلى Intrusion Detection System Manager (EXP_SWArchitecture ص. 197).

مخطط السياق: يربط FC Firewall بين تكوين البيان (manifest)، وتحديد الحالة من التطبيق، وتطبيق القواعد في نظام التشغيل، وإرسال تقارير SEv إلى IdsM. المصادر: EXP_PlatformDesign ص. 97، EXP_SWArchitecture ص. 197

تعتمد الفلترة على الحالة. يحدد OEM حالات مثل القيادة، أو ركن السيارة، أو التشخيص، وتطبق على الحزمة القواعد الخاصة بالحالة النشطة فقط (EXP_PlatformDesign ص. 92). في البيان (manifest)، يجمع AdaptiveFirewallModuleInstantiation عناصر StateDependentFirewall لهذا الغرض. يحتوي كل منها على خصائص قواعد مرتبة، وdefaultAction اختياري، ومراجع إلى الحالات المرتبطة بها (TPS_ManifestSpecification ص. 679). تظهر الحالات في الكود كترقيم (enumeration) يتم إنشاؤه لكل واجهة في ara::fw::states [AP_SWS_Fw_81001].

يُنشئ التطبيق كائن الواجهة من ara::core::InstanceSpecifier. منشئ الفئة هذا آمن للخيوط (thread-safe) [AP_SWS_Fw_82002]. SwitchFirewallState هو noexcept ويُرجع ara::core::Future<void> [AP_SWS_Fw_82008]. داخليًا، يطبق الـ cluster وفقًا للسيناريو كل قاعدة Firewall بشكل فردي في نظام التشغيل (EXP_SWArchitecture ص. 232). لا يمكن نسخ المثيلات، ولكن يمكن نقلها بالتأكيد. عمليات النقل ومدمّر الكائن (destructor) ليست آمنة للخيوط [AP_SWS_Fw_82004] [AP_SWS_Fw_82006].

مخطط تسلسلي: يعود طلب تغيير الحالة كـ Future. بين ذلك، يتم تطبيق كل قاعدة بشكل فردي. المصادر: EXP_SWArchitecture ص. 232، [AP_SWS_Fw_82008]

في حالة الخطأ، يحتوي Future على FwErrc::kServiceNotAvailable أو FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_83001]. لا يمكن استنتاج المعنى إلا من الأسماء: يُرجح أن الخدمة غير متوفرة، أو أن الحالة المستهدفة تفتقر إلى تكوين قواعد صالح. عبر FwErrorDomain::ThrowAsException يمكن طرح خطأ كـ FwException [AP_SWS_Fw_83012]. لا تُعد الحزم المحظورة خطأ في API، بل يتم الإبلاغ عنها كـ Security Events إلى IdsM، مع التمييز في R23-11 إضافيًا وفقًا للبروتوكول المتباين (SWS_Firewall ص. 31).

دور FC Firewall بين التطبيق ونظام التشغيل وIdsM

تصف الوحدة النمطية fw الـ Functional Cluster المسمى Firewall لـ Adaptive Platform. وهو معتمد على برنامج خفي (daemon) ويحقق الواجهة FirewallStateSwitchInterface مع العملية SwitchFirewallState(). يستخدم Adaptive Application هذه الواجهة عبر علاقة «use» (EXP_SWArchitecture ص. 126). تقصر حالات الاستخدام الـ cluster على مهمتين: يتم تشغيل «Switch Firewall State» بواسطة Adaptive Application بمشاركة نظام التشغيل؛ وتتوجه «Report Security Event» إلى Intrusion Detection System Manager المعتمد بدوره على برنامج خفي (EXP_SWArchitecture ص. 197).

تفصل النظرة العامة على المعمارية بين التكوين والتحكم والتنفيذ:

  • يوفر Machine Manifest قواعد الفلترة.
  • يقوم FC Firewall بتهيئة Firewall Engine باستخدامه.
  • يقوم تطبيق OEM بضبط حالة Firewall.
  • يبلغ الـ cluster عن Security Events (SEvs) إلى IdsM (EXP_PlatformDesign ص. 97).

تبرز في المقدمة حالتا استخدام: الأولى هي الفلترة المعتمدة على الحالة مع حالات مخصصة لـ OEM مثل القيادة أو ركن السيارة أو جلسة التشخيص. والثانية هي دعم Intrusion Detection System عبر Security Events عند حظر الرسائل. يتولى IdsM التأهيل أو التمرير إلى SOC أو التخزين المستمر (EXP_PlatformDesign ص. 92). واجهة API التطبيقية الوحيدة للوحدة النمطية هي تغيير الحالة [AP_SWS_Fw_82008].

مخطط السياق: يتلقى FC Firewall التكوين من Machine Manifest وتوجيهات الحالة من التطبيق. ويتحكم في المحرك ونظام التشغيل ويبلغ عن SEvs إلى IdsM. المصادر: EXP_PlatformDesign ص. 97، EXP_SWArchitecture ص. 197، EXP_SWArchitecture ص. 232

حالات Firewall: من آلة الحالة في النموذج إلى الترقيم المُنشأ

في النموذج الفوقي (metamodel) للبيان، يخصص FirewallStateSwitchInterface عنصراً من نوع PortInterface. وعبر الدور firewallStateMachine، يُجمّع أي عدد (0..*) من عناصر ModeDeclarationGroupPrototype (TPS_ManifestSpecification ص. 263). الحالات الفردية هي ModeDeclarations مع السمة الاختيارية value: PositiveInteger (TPS_ManifestSpecification ص. 679).

لكل واجهة تمت نمذجتها، يتم إنشاء ترقيم (enumeration) مستقل enum class {<fwssi-sn>} : std::uint32_t في مساحة الاسم ara::fw::states. ويتم تضمينه عبر ara/fw/states/{<fwssi-sn>}.h [AP_SWS_Fw_81001]. لكل حالة Firewall تمت نمذجتها، ينشأ مُعَدِّد (enumerator) {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002].

بالنسبة للمستخدمين، يعني هذا: لا توجد قائمة حالات ثابتة على مستوى المنصة بأكملها. يحدد نموذج OEM الحالات الموجودة (EXP_PlatformDesign ص. 92). يتوقع SwitchFirewallState معلمة firewallState من النوع EnumT [AP_SWS_Fw_82008]. تفسير: يُرجح أن يتوافق EnumT مع ترقيم الحالة المُنشأ للواجهة المعنية؛ ومما يؤيد ذلك أن [AP_SWS_Fw_81001] يعرفها صراحة كحالات «for FirewallStateSwitchInterface».

مخطط السياق (النموذج–الكود): تنبع الحالات من آلة الحالة للواجهة في النموذج. لكل واجهة، يتم إنشاء ترقيم في ara::fw::states. المصادر: TPS_ManifestSpecification ص. 263، [AP_SWS_Fw_81001]، [AP_SWS_Fw_81002]، [AP_SWS_Fw_82008]

تكوين البيان (Manifest): مثيل الوحدة النمطية، ومجموعات القواعد المعتمدة على الحالة، وتعيين المنافذ

تُجمع الإعدادات الخاصة بالآلة لوحدة Firewall في AdaptiveFirewallModuleInstantiation. يحمل التحديد المقابل في R25-11 الحالة DRAFT (TPS_ManifestSpecification ص. 677). يخصص مثيل الوحدة النمطية NonOsModuleInstantiation ويشير عبر stateDepFirewall إلى أي عدد من عناصر StateDependentFirewall.

يحتوي StateDependentFirewall على:

  • اختياريًا defaultAction من النوع FirewallActionEnum،
  • firewallRuleProps مرتبة،
  • مراجع عبر firewallState (instanceRef) إلى ModeDeclarations التي يسري فيها (TPS_ManifestSpecification ص. 679).

يصفها System Template بإيجاز بأنها «Firewall rules that are defined in a firewall state» (TPS_SystemTemplate ص. 644).

القواعد نفسها هي عناصر FirewallRule ذات سمات مثل bucketSize وrefillAmount. بالإضافة إلى ذلك، يتضمن النموذج الفوقي NetworkLayerRule وTransportLayerRule، ويشمل الأخير من بين أمور أخرى نطاقات المنافذ وchecksumVerification. يمكن أيضًا لـ CouplingElement تجميع القواعد عبر firewallRule (TPS_ManifestSpecification ص. 679). للحصول على التفاصيل، يحيل System Template صراحة إلى مواصفة البيان (TPS_SystemTemplate ص. 644).

يُنشئ AdaptiveFirewallToPortPrototypeMapping الاتصال بالتطبيق. وهو يطابق مثيل الوحدة النمطية (المرجع firewall، 0..1) مع RPortPrototype الخاص بالتطبيق، والمكتوب بنوع واجهة تبديل الحالة (TPS_ManifestSpecification ص. 677). يسري قيدان:

  • تسمي ملاحظة الفئة الواجهة FirewallModeSwitchInterface، في حين يسميها عنوان الرسم وAPI بالاسم FirewallStateSwitchInterface. الاسم المعتمد للكود هو الاسم الوارد في [AP_SWS_Fw_82002].
  • تحمل فئة التعيين (mapping) ومرجعها الحالة candidate (TPS_ManifestSpecification ص. 677).

مخطط السياق (النموذج الفوقي): يجمع مثيل الوحدة النمطية مجموعات القواعد المعتمدة على الحالة. يربطها التعيين بمنفذ R-Port للتطبيق. المصادر: TPS_ManifestSpecification ص. 677، TPS_ManifestSpecification ص. 679، TPS_ManifestSpecification ص. 677

سير عملية تغيير الحالة باستخدام SwitchFirewallState

من جانب الكود، يُضمّن التطبيق ara/fw/firewall_state.h. ويُنشئ ara::fw::FirewallStateSwitchInterface عبر المنشئ الصريح من ara::core::InstanceSpecifier. هذا المنشئ هو noexcept وآمن بالنسبة للخيوط (thread-safe) [AP_SWS_Fw_82002].

يطلب SwitchFirewallState(EnumT firewallState) تغيير الحالة. والأسلوب هو noexcept ويُرجع ara::core::Future<void>. ولذلك، فإن الخطأين المحددين له FwErrc::kServiceNotAvailable وFwErrc::kInvalidStateDependentFirewall يرجعان عبر الـ Future وليس كاستثناء [AP_SWS_Fw_82008].

يُظهر سيناريو «Switch Firewall State» المسار الداخلي في ثلاث خطوات (EXP_SWArchitecture ص. 232):

  1. يستدعي التطبيق SwitchFirewallState() في FC Firewall.
  2. يستدعي الكتلة في حلقة تكرارية «foreach FirewallRule» الدالة applyRule() في نظام التشغيل في كل مرة.
  3. لا ترجع الاستجابة إلى التطبيق إلا بعد انتهاء الحلقة التكرارية.

تم تمييز applyRule() هناك على أنها «aapInformative». كيفية تفعيل القواعد في نظام التشغيل لم تُحدد كـ API للمنصة في حمولة البيانات (Payload). وأظهرت نسخة R22-11 المسار نفسه كسيناريو ناجح (EXP_SWArchitecture ص. 158). وبعد التغيير، لا تفحص القواعد الخاصة بالحالة النشطة ولا تقوم بالتصفية إلا هي فقط (EXP_PlatformDesign ص. 92).

مخطط تتابع: يتم الإبلاغ عن تغيير الحالة بشكل غير متزامن عبر Future. داخلياً، تطبق الكتلة كل قاعدة على حدة. المصادر: EXP_SWArchitecture ص. 232، [AP_SWS_Fw_82002]، [AP_SWS_Fw_82008]

تصفية الحزم في الحالة النشطة والإبلاغ عن Security Events

يمكن تعيين قواعد Firewall لحالة Firewall معينة. ولفحص حزمة ما، لا يتم الرجوع إلا إلى قواعد الحالة النشطة حالياً (EXP_PlatformDesign ص. 92). ولكل حالة، توفر StateDependentFirewall خصائص القواعد المرتبة والـ defaultAction الاختيارية (TPS_ManifestSpecification ص. 679).

تصف نسخة SWS ذات الإصدار R23-11 تعيين Security Events بمزيد من التفصيل (SWS_Firewall ص. 31):

  • إذا لم تتطابق الحزمة مع أي قاعدة، يتم تطبيق الإجراء الافتراضي (Default Action).
  • إذا حظر الإجراء الافتراضي الحزمة، تُحدد الكتلة البروتوكول المتباين. والمعيار الحاسم هو القاعدة ذات أكبر عدد من طبقات ISO/OSI المتطابقة، محسوبة ابتداءً من الطبقة الدنيا. وتحدد الطبقة غير المتطابقة الأولى فوقها البروتوكول.
  • لهذا البروتوكول، يتم الإبلاغ عن SEv إلى IdsM، مثل SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH (Ethernet) أو SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH أو SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH أو SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

هذه التفاصيل مستمدة من R23-11. والمتطلبات التابعة لها ليست جزءاً من حمولة بيانات R25-11، ولذلك فهي معروضة هنا بشكل توضيحي وليس معيارياً. والمبدأ القائل بأن الرسائل المحظورة تذهب كـ SEvs إلى IdsM يسري أيضاً على R25-11 وفقاً لوصف البنية المعمارية (EXP_PlatformDesign ص. 92).

مخطط نشاط: يتم فحص حزمة مقارنة بقواعد الحالة النشطة. يؤدي الحظر الافتراضي إلى SEv خاص بالبروتوكول إلى IdsM. المصادر: EXP_PlatformDesign ص. 92، SWS_Firewall ص. 31 (R23-11)

التصرف في حالة الخطأ

يُعرّف FwErrc رموز أخطاء الوحدة في الترويسة ara/fw/fw_error_domain.h: kServiceNotAvailable=1 وkInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]. كلاهما محدد لـ SwitchFirewallState كأخطاء محتملة [AP_SWS_Fw_82008]. تفسير الأسماء، نظراً لأن المتطلبات لا تذكر شروط الإطلاق:

  • من المرجح أن يُبلّغ kServiceNotAvailable بأن FC Firewall القائم على daemon لا يمكنه تقديم الخدمة.
  • من المرجح أن يُبلّغ kInvalidStateDependentFirewall بأنه لا توجد StateDependentFirewall صالحة للحالة المطلوبة.

يتبع نطاق الأخطاء نمط ara::core المعتاد:

  • يُرجع GetFwErrorDomain() النطاق بأمان بالنسبة للخيوط [AP_SWS_Fw_83002]. وقد تم حذف المنشئ الافتراضي لـ FwErrorDomain [AP_SWS_Fw_83009].
  • يُنشئ MakeErrorCode ara::core::ErrorCode [AP_SWS_Fw_83003].
  • يُرجع Name() وMessage() اسم النطاق ونص الخطأ [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • يشير الاسمان المستعاران Errc وException إلى FwErrc وFwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

من يعمل باستخدام الاستثناءات، يمكنه تحويل رمز خطأ عبر ThrowAsException إلى FwException. هذه الدالة هي noexcept(false) ومصنفة على أنها «not exception safe» [AP_SWS_Fw_83012] [AP_SWS_Fw_83005]. وفي المقابل، لا تُعد الحزم المحظورة خطأ API؛ فهي تظهر كـ Security Events لدى IdsM (EXP_PlatformDesign ص. 92).

مخطط نشاط: يتم تقييم نتيجة تغيير الحالة عبر Future. تمر الأخطاء عبر FwErrorDomain ويمكن رميها اختيارياً كـ FwException. المصادر: [AP_SWS_Fw_82008]، [AP_SWS_Fw_83001]، [AP_SWS_Fw_83011]، [AP_SWS_Fw_83012]

  • SWS_Firewall ص. 31: تعيين SEv عند الحظر الافتراضي، فقط في نسخة R23-11.
