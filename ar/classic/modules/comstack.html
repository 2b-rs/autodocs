دور ComStack_Types: مفردات الأنواع المشتركة لمكدس الاتصالات

إن الوحدة «comstack» ليست مكونًا تنفيذيًا. بل توفر عبر ComStack_Types.h أنواع البيانات التي تصف بها وحدات مكدس الاتصالات الكلاسيكي (Classic) وحدات PDU ومخازن التخزين المؤقت والقنوات. ووفقًا للمواصفات، فإن جميع الأنواع التسعة للإصدار هي «Available via ComStack_Types.h»، من PduInfoType إلى NetworkHandleType ([SWS_COMTYPE_00011]، [SWS_COMTYPE_00038]). ويجب استخدام PduLengthType في مكدس AUTOSAR-Com بأكمله لوحدة التحكم، باستثناء برامج تشغيل الناقل ([SWS_COMTYPE_00008]، SWS ComStackTypes ص. 16). وبذلك يتم رسم حدود النظام: أعلى برامج تشغيل الناقل، تستخدم الواجهات والموجهات وبروتوكولات النقل والطبقات العليا نفس الأنواع. كما تستورد RTE أيضًا لعمليات الاستدعاء الخاصة بالبيانات الكبيرة (Large-Data-Callbacks)، من بين أمور أخرى، BufReq_ReturnType وPduIdType وPduInfoType وPduLengthType وRetryInfoType من ComStack_Types.h (SWS RTE ص. 833).

حول حالة المصادر: تأتي مواضع التوثيق المقتبسة في الغالب من الإصدارات R23-11 إلى R25-11. الرسم البياني لإعادة المحاولة (Retry) الخاص بمواصفات J1939Tp هو الوحيد الموثق أيضًا للإصدار R20-11. وتعتبر المتطلبات هي المعيارية للإصدار R20-11. ويتم ذكر الاختلافات في النص، كما هو الحال مع PNCHandleType ([SWS_COMTYPE_00036]، SWS ComStackTypes ص. 17).

مخطط السياق: يزود ComStack_Types.h جميع وحدات المكدس أعلى برامج تشغيل الناقل بأنواع مشتركة؛ وتنشأ حدود النطاق من تكوين EcuC. المصادر: [SWS_COMTYPE_00005]، [SWS_COMTYPE_00008]، [SWS_COMTYPE_00038]، TPS EcuC ص. 205، SWS RTE ص. 833

هوية PDU: نوع PduIdType ومعرفات المقابض المحلية للوحدة

PduIdType قابل للتغيير في R20-11 كـ uint16 أو uint8. ويعتمد الحجم على أكبر عدد من وحدات PDU التي تستخدمها وحدة برمجية مفردة. يُنشئ المولد حد النطاق من تكوين EcuC في ComStack_Cfg.h ([SWS_COMTYPE_00005]). وفي EcuC، يقابل ذلك المعلمة PduIdTypeEnum بالقيمتين UINT8 وUINT16. وإذا كانت وحدة واحدة على الأقل تدير أكثر من 256 PDU، يلزم uint16 (ECUConfiguration ص. 153).

إن قيمة PduIdType ليست مفتاحًا على مستوى النظام، بل هي مقبض Handle داخل الوحدة التي يتم استدعاؤها في كل حالة: تحتفظ كل وحدة BSW ذات واجهة برمجة تطبيقات PDU-API بقائمتها الخاصة من معرّفات PDU ID كجدول بحث (SWS PduR ص. 33). ويحدد موجه PDU-Router مسار التوجيه عبر معرّف ID المصدر ومعرّفات ID الهدف، ويقوم بتحويل معرّف ID في مسار الإرسال وفي مسار التأكيد، ويمرر قيمة PduInfoType دون تغيير في أثناء ذلك (SWS PduR ص. 33). ولكي تقصد الوحدات المتجاورة نفس PDU، تحدد EcuC EcucPduCollection عابرة للوحدات مع كائنات Pdu عامة (TPS EcuC ص. 190).

مخطط تسلسل: تقوم PduR بتحويل قيم PduIdType لكل وحدة هدف، وتمرر PduInfoType دون تغيير، وتوجه التأكيد مع معرّف ID مُعاد ضبطه إلى Com. المصادر: SWS PduR ص. 33، SWS PduR ص. 33، [SWS_COMTYPE_00005]

محتوى PDU: نوع PduInfoType ونوع PduLengthType والبيانات الوصفية

يلخص PduInfoType المعلومات الأساسية لـ PDU من أي نوع. يشير SduDataPtr إلى البيانات المفيدة، وMetaDataPtr إلى البيانات الوصفية، ويحدد SduLength الطول بالبايت ([SWS_COMTYPE_00011]، SWS ComStackTypes ص. 17). الطول من النوع PduLengthType. ويتم إنشاؤه كـ uint8 أو uint16 أو uint32 اعتمادًا على أقصى طول لـ PDU في وحدة التحكم. وبدون تقسيم، يحدد حجم إطار الناقل العرض، وهو في FlexRay بحد أقصى 255 بايت وبالتالي uint8. ومع التقسيم، يحدد الحد الأقصى لطول N-PDU مقسمة العرض ([SWS_COMTYPE_00008]، SWS ComStackTypes ص. 16).

البيانات الوصفية هي على سبيل المثال CAN-ID أو Socket-ID أو عناوين التشخيص. وتتكون من تسلسل من العناصر المكونة بشكل ثابت لكل PDU. وتكون العناصر التي تزيد عن 8 بت بترتيب بايتات المنصة ([SWS_COMTYPE_00011]). وينتج ترتيب العناصر وموضعها من تكوين EcuC الخاص بـ PDU العامة. والفرز حسب الطول يجعل الحشو (Padding) غير ضروري (SWS BSWGeneral ص. 67). مثال تطبيقي: في مجموعة اتصالات المقابس، يرسل SoAd فقط عبر الاتصال الذي يحدده PduInfoType.MetaDataPtr (SWS SoAd ص. 30).

بالنسبة لعمر المؤشرات، تنطبق قاعدة تشغيلية: عند إشارة الاستلام، يكون مؤشر البيانات الممرر صالحًا فقط حتى عودة الإشارة (SWS CanNm ص. 73). وللطول 0 معانٍ خاصة متعددة. يستعلم استدعاء CopyRxData مع SduLength بقيمة 0 عن المخزن المؤقت للاستلام الخالي في الطبقة العليا؛ ويمكن أن يكون SduDataPtr حينئذٍ NULL_PTR (SWS DoIP ص. 77). وعند الإرسال، يشير SduLength بقيمة 0 إلى I-PDU ذات طول غير معروف. وتمرر PduR هذا الطول إلى جميع وحدات TP الوجهة (SWS PduR ص. 43).

مصافحة المخزن المؤقت أثناء استلام TP: نوع BufReq_ReturnType

يخزن BufReq_ReturnType نتيجة طلب المخزن المؤقت. والقيم محددة وثابتة: BUFREQ_OK (0) وBUFREQ_E_NOT_OK (1) وBUFREQ_E_BUSY (2) وBUFREQ_E_OVFL (3). وعند BUFREQ_E_BUSY، يجب على الطالب تكرار الطلب لفترة معينة من الوقت ([SWS_COMTYPE_00012]، SWS ComStackTypes ص. 19).

يتم استلام TP في ثلاث خطوات:

  1. يبلغ بروتوكول النقل عبر PduR_<User:LoTp>StartOfReception عن الطول الإجمالي TpSduLength وبيانات الإطار الأول. ويسترجع عبر bufferSizePtr المخزن المؤقت المتاح ويحسب منه حجم الكتلة.
  2. يمرر المقاطع عبر CopyRxData.
  3. ينهي الاستلام بواسطة RxIndication (SWS PduR ص. 92).

يعني BUFREQ_OK هنا «قبول الاتصال»، حتى لو تم الإبلاغ عن حجم المخزن المؤقت بقيمة 0 (SWS PduR ص. 92). لا يحتفظ FlexRay-AR-TP بمخازن مؤقتة للرسائل بنفسه. بل يتبادل البيانات تدريجيًا مع الطبقة العليا (SWS FrArTp ص. 50).

مخطط التتابع: يبدأ استلام TP بـ StartOfReception، ويسلم البيانات عبر CopyRxData وينتهي بـ RxIndication؛ في حال رفض بدء إطار مفرد، لا يتبع ذلك أي RxIndication. المصادر: SWS FrArTp ص. 50، SWS FrArTp ص. 50، SWS PduR ص. 92، [SWS_COMTYPE_00012]

الإرسال مع إعادة المحاولة: RetryInfoType وTpDataStateType

عند الإرسال المجزأ، يمرر بروتوكول النقل مع CopyTxData RetryInfoType. ويتكون من TpDataState وTxTpDataCnt؛ حيث يمثل الأخير إزاحة البايتات التي يجب إعادة إرسالها ([SWS_COMTYPE_00037]، SWS ComStackTypes ص. 20). وتعني الحالات الثلاث ما يلي ([SWS_COMTYPE_00027]، SWS ComStackTypes ص. 19):

  • TP_DATACONF: تم تأكيد جميع البيانات المنسوخة حتى الآن ويجوز إزالتها من مخزن TP المؤقت.
  • TP_DATARETRY: يجب توفير البيانات المنسوخة مسبقًا مرة أخرى بدءًا من الإزاحة TxTpDataCnt.
  • TP_CONFPENDING: يجب الاحتفاظ بالبيانات المنسوخة سابقًا.

يوضح الرسم البياني لإعادة المحاولة (Retry) في مواصفات SAE-J1939-TP هذا التفاعل. لكل كتلة، تُطلب الحزمة الأولى باستخدام TP_DATACONF، والحزم التالية باستخدام TP_CONFPENDING. وإذا فُقد TP.DT، يرجع TP إلى الحزمة الأولى من الكتلة. ثم يطلبها مجددًا باستخدام TP_DATARETRY؛ ويكون TxTpDataCnt هنا هو الإزاحة إلى بداية الكتلة (SWS J1939Tp ص. 55). يضبط FrArTp أيضًا TP_CONFPENDING عند الإرسال غير المجزأ مع تمكين إعادة المحاولة (SWS FrArTp ص. 50).

مخطط التتابع: يتحكم TpDataState لكل كتلة فيما إذا كان سيتم تأكيد البيانات، أو الاحتفاظ بها، أو إعادة نسخها بدءًا من بداية الكتلة. المصادر: SWS J1939Tp ص. 55، [SWS_COMTYPE_00027]، [SWS_COMTYPE_00037]

توضح بوابة TP المباشرة لـ PduR للأطر الفردية كيفية استجابة الطبقة العليا للحالة. عند TP_DATACONF أو TP_CONFPENDING أو في حالة غياب مؤشر RetryInfoType، تقوم بنسخ SduLength بايت. وعند TP_DATARETRY، تقوم مسبقًا بإرجاع الموضع بمقدار TxTpDataCnt بايت (SWS PduR ص. 57). ولا تقوم كل طبقة عليا بتقييم معلومات إعادة المحاولة: ففي عمليات استدعاء LdCom، لا يتم التعامل مع retry وفقًا لمواصفات LdCom وطبقته العليا (SWS LdCom ص. 34). ومنذ AUTOSAR 4.3.1، أصبحت المعلمة في PduR_<User:LoTp>CopyTxData مؤشرًا إلى const RetryInfoType (SWS PduR ص. 3).

مخطط النشاط: تقرر PduR بناءً على TpDataState ما إذا كانت ستنسخ مباشرة، أو تعيد ضبط الموضع، أو ترفض الطلب. المصادر: SWS PduR ص. 57، [SWS_COMTYPE_00027]، [SWS_COMTYPE_00012]

القنوات والشبكات الفرعية ومعلمات TP القابلة للتغيير

يخزن NetworkHandleType معرف قناة الاتصال. وهو uint8 ذو أساس صفري بنطاق قيم من 0..255 ([SWS_COMTYPE_00038]، SWS ComStackTypes ص. 20). وفي حالة Mirror_GetNetworkId، يمثل قناة ComM، وفي حالة CanSM_TxTimeoutException يمثل شبكة CAN المعنية (SWS Mirror ص. 78، SWS CanSM ص. 87). وتحدد عمليات استدعاء إدارة الشبكة مثل Nm_RemoteSleepIndication أيضًا قناة NM عبر هذا النوع (SWS Nm ص. 89).

يخزن PNCHandleType معرف عنقود الشبكة الجزئية (Partial-Network-Cluster). وفي R20-11، فهو مشتق من uint8 ([SWS_COMTYPE_00036]). في المقابل، يذكر موضع التوثيق الحالي من R23-11 أن uint16 هو النوع الأساسي (SWS ComStackTypes ص. 17). وبالنسبة لـ R20-11، يسري إصدار المتطلبات uint8.

يحدد TPParameterType المعلمة المراد تغييرها في وقت التشغيل. والقيم هي TP_STMIN (Separation Time) وTP_BS (Block Size) وTP_BC (التحكم في عرض النطاق الترددي لبروتوكول نقل FlexRay) ([SWS_COMTYPE_00031]، SWS ComStackTypes ص. 18). وتقيد الوحدات الاستخدام. حيث يقبل J1939Tp_ChangeParameter فقط TP_BS بقيم تصل إلى 255 (SWS J1939Tp ص. 42). ويرفض FrArTp التغييرات أثناء الاستلام الجاري باستخدام E_NOT_OK (SWS FrArTp ص. 49).

التصرف في حالة الخطأ

لا تمتلك الأنواع في حد ذاتها سلوك خطأ. ولكنها تنقل النتائج التي تتفاعل الوحدات وفقًا لها ([SWS_COMTYPE_00012]). وفي حالة إرسال FrArTp غير المجزأ، ينطبق ما يلي:

  • إذا أرجع PduR_FrArTpCopyTxData BUFREQ_E_BUSY، يكرر TP الاستدعاء حتى انتهاء FrArTpTimeCs.
  • عند BUFREQ_E_NOT_OK أو بعد انتهاء الوقت، يتم الإلغاء واستدعاء PduR_FrArTpTxConfirmation مع E_NOT_OK.
  • إذا أرجع PduR_FrArTpStartOfReception لإطار مفرد BUFREQ_E_NOT_OK أو BUFREQ_E_OVFL، ينتهي الاستلام على الفور دون PduR_FrArTpRxIndication (SWS FrArTp ص. 50).

مخطط النشاط: يؤدي BUFREQ_E_BUSY إلى إعادة المحاولة حتى انتهاء المهلة؛ ويؤدي كل من BUFREQ_E_NOT_OK وBUFREQ_E_OVFL إلى الإلغاء. المصادر: SWS FrArTp ص. 50، SWS FrArTp ص. 44، [SWS_COMTYPE_00012]

في بوابة TP المباشرة، تنطبق قاعدتان على TP_DATARETRY. إذا لم تتمكن PduR من إعادة ضبط الموضع، فإنها ترد بـ BUFREQ_E_NOT_OK وتترك الموضع والبيانات دون تغيير. وإذا كانت هناك بيانات مفقودة بعد إعادة الضبط، فإنها ترد بـ BUFREQ_E_BUSY (SWS PduR ص. 57). وفي بوابة On-the-fly، لا تدعم PduR إعادة محاولة إرسال البيانات المرسلة بالفعل (SWS PduR ص. 58). وفي توجيه Multicast-TP، ترجع E_NOT_OK استجابة لـ TP_DATARETRY وفقًا لموضع التوثيق (SWS PduR ص. 41).

علاوة على ذلك، لا تتخذ PduR أي تدابير خاصة بها حيال الأخطاء؛ فهي تُمرر الأخطاء الناتجة عن قيم الإرجاع إلى وحدة المصدر العليا المسؤولة عن معالجتها (SWS PduR ص. 46، SWS PduR ص. 49).

Communication Stack Types (ComStack_Types)

الأنواع القياسية ومعرفات PDU والأطوال وأنواع طلبات المخزن المؤقت (PduIdType، PduLengthType، PduInfoType، BufReq_ReturnType) المستخدمة عبر جميع طبقات الاتصال.

الأنواع – نظرة عامة

  • typedef PduIdType This type is used within the entire AUTOSAR Com Stack except for bus drivers.
  • typedef PduLengthType This type shall be used within the entire AUTOSAR Com Stack of an ECU except for bus drivers.
  • struct PduInfoType Variables of this type shall be used to store the basic information about a PDU of any type, namely a pointer variable...
  • typedef PNCHandleType Used to store the identifier of a partial network cluster.
  • enum TPParameterType Specify the parameter to which the value has to be changed (BS or STmin).
  • enum BufReq_ReturnType Variables of this type shall be used to store the result of a buffer request.
  • enum TpDataStateType Variables of this type shall be used to store the state of TP buffer.
  • struct RetryInfoType Variables of this type shall be used to store the information about Tp buffer handling.
  • typedef NetworkHandleType Variables of the type Network Handle Type shall be used to store the identifier of a communication channel.

الأنواع

BufReq_ReturnType نوع

يجب استخدام المتغيرات من هذا النوع لتخزين نتيجة طلب المخزن المؤقت.

typedef enum { BUFREQ_OK, BUFREQ_E_NOT_OK, BUFREQ_E_BUSY, BUFREQ_E_OVFL } BufReq_ReturnType;
NetworkHandleType نوع

يجب استخدام متغيرات من النوع Network Handle Type لتخزين معرف قناة الاتصال.

typedef uint8 NetworkHandleType;
PduIdType نوع

يستخدم هذا النوع ضمن كامل AUTOSAR Com المكدس باستثناء سائقي الحافلات.

typedef uint16 PduIdType;
PduInfoType نوع

يجب استخدام المتغيرات من هذا النوع لتخزين المعلومات الأساسية حول PDU من أي نوع، أي متغير مؤشر يشير إلى SDU (الحمولة)، ومؤشر إلى بيانات التعريف الخاصة بـ PDU، والطول المقابل لـ SDU بالبايت.

typedef struct { uint8* SduDataPtr; uint8* MetaDataPtr; PduLengthType SduLength; } PduInfoType;
PduLengthType نوع

يجب استخدام هذا النوع ضمن كامل AUTOSAR Com كومة ECU باستثناء سائقي الحافلات.

typedef uint16 PduLengthType;
PNCHandleType نوع

يستخدم لتخزين معرف مجموعة الشبكة الجزئية.

typedef uint8 PNCHandleType;
RetryInfoType نوع

يجب استخدام متغيرات من هذا النوع لتخزين المعلومات حول معالجة المخزن المؤقت Tp.

typedef struct { TpDataStateType TpDataState; PduLengthType TxTpDataCnt; } RetryInfoType;
TpDataStateType نوع

يجب استخدام متغيرات من هذا النوع لتخزين حالة المخزن المؤقت TP.

typedef enum { TP_DATACONF, TP_DATARETRY, TP_CONFPENDING } TpDataStateType;
TPParameterType نوع

حدد المعلمة التي يجب تغيير القيمة إليها (BS أو STmin).

typedef enum { TP_STMIN, TP_BS, TP_BC } TPParameterType;
