فئة ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Kontext

Die Klasse ara::log::Logger repräsentiert einen Logging-Kontext innerhalb eines AUTOSAR-Adaptive-Anwendungsprozesses oder Prozessbereichs. Ein solcher Kontext kapselt zentrale Eigenschaften für die Protokollierung: eine Kontext-ID, eine zugehörige Beschreibung der Kontext-ID sowie ein konfigurierbares Standard-Loglevel (Default Log Level). Über diese Kontexte wird die Protokollausgabe innerhalb des Systems differenziert und gesteuert.

In der Systemarchitektur fungiert ara::log::Logger als Vermittler zwischen drei Beteiligten:

  • Anwendungsprozess (Application Process): Nutzt Instanzen von ara::log::Logger, um Meldungen abzusetzen, Filterschwellen dynamisch abzufragen oder anzupassen.
  • Logging-Framework: Hält eine strikte Eigentümerschaft („strong ownership“) über alle Logger-Instanzen, steuert deren Erzeugung über Fabrikfunktionen wie ara::log::CreateLogger und übernimmt das Housekeeping.
  • Logging-Backend: Nimmt die eigentlichen Protokolldaten entgegen; Logger-Kontexte werden während der Initialisierungsphase automatisch beim Backend registriert und während des geordneten Prozess-Shutdowns deregistriert.

Lebenszyklus

Die Verwaltung der Instanzen von ara::log::Logger unterliegt einer strengen Kontrolle durch das Framework, um eine lückenlose Synchronisation mit dem Logging-Backend sicherzustellen:

  • Erzeugung und Besitzverhältnisse: Der Standardkonstruktor ist explizit gelöscht (Logger() = delete, [SWS_LOG_00259]). Ein direktes Instanziieren durch die Anwendung ist untersagt. Die Erzeugung erfolgt kontrolliert über Funktionen wie ara::log::CreateLogger. Die Eigentümerschaft verbleibt beim Logging-Framework.
  • Registrierung und Bereinigung: Ein Logger-Kontext wird bei seiner Erzeugung automatisch am Logging-Backend registriert. Bei der Prozessbeendigung erfolgt die Abmeldung automatisch, wodurch Anwendungsentwickler von der manuellen Lebenszyklusverwaltung entlastet werden.
  • Zerstörung: Der Destruktor ~Logger() ist spezifiziert ([SWS_LOG_00260]). Er ist als threadsicher deklariert, jedoch als nicht ausnahmesicher („not exception safe“) ausgewiesen ([SWS_LOG_00260]).
  • Nebenläufigkeit: Sämtliche Methoden zur Protokollierung und Schwellwertabfrage sind als threadsicher spezifiziert ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). Mehrere Threads können dieselbe Logger-Instanz parallel nutzen.

Nutzungspfad

Der typische Ablauf beim Absetzen von Logmeldungen gliedert sich in folgende Phasen:

  1. Filterschwelle prüfen oder konfigurieren: Die Anwendung kann die Filterschwelle einer Instanz über SetThreshold(threshold) zur Laufzeit festlegen ([SWS_LOG_00255]). Vor rechenintensiven Vorbereitungen von Protokolldaten kann mittels IsEnabled(logLevel) abgefragt werden, ob das gewünschte Loglevel die konfigurierte Berichtsschwelle erfüllt ([SWS_LOG_00070]). Liefert die Prüfung false, kann die Vorbereitung übersprungen werden.
  2. Stream-basiertes Logging initiieren: Für die Textprotokollierung stellt die Klasse spezifische Methoden für jeden Schweregrad bereit:
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • WithLevel(logLevel) ([SWS_LOG_00131]) zur programmatischen Bestimmung der Dringlichkeit.
    Jede dieser Methoden liefert ein LogStream-Objekt zurück, das Argumente über den Stream-Operator << entgegennimmt ([SWS_LOG_00064]).
  3. Stream-Lebensdauer und Ausgabe: Im Standardfall ist die Lebensdauer des LogStream-Objekts auf eine einzige Anweisung beschränkt und endet mit dem Semikolon nach dem letzten Argument ([SWS_LOG_00064]). Bei Bedarf kann der Stream einer Variablen zugewiesen werden, um dessen Lebensdauer über mehrere Anweisungen hinweg auszudehnen ([SWS_LOG_00064]).
  4. Modellierte Nachrichten ausgeben: Alternativ zum Streaming können vorab modellierte Nachrichten über Log(id, args...) ausgegeben werden ([SWS_LOG_00204]). Falls zusätzliche Attribute übergeben werden sollen, erfolgt der Aufruf über LogWith(attrs, msgId, params...) mit einem Attribut-Tupel ([SWS_LOG_00133]).

Fehlerszenarien

Die Fehlerbehandlung in ara::log::Logger basiert vorwiegend auf statischer Typprüfung zur Übersetzungszeit und strikter Ausnahmesicherheit:

  • Fehlpassende Argumente bei modellierten Nachrichten: Wird die Template-Funktion Log(id, args...) mit Parametern aufgerufen, die nicht exakt der Definition der modellierten Nachricht entsprechen, ist das Programm fehlerhaft gebildet („ill-formed“) ([SWS_LOG_00204]). Dies führt zu einem Fehler bei der Kompilierung.
  • Ungültige Attribute bei LogWith: Bei LogWith(attrs, msgId, params...) wird die Funktion per SFINAE aus der Überladungsauflösung ausgeschlossen, sofern ein Element des Attribut-Tupels kein gültiges Attribut darstellt ([SWS_LOG_00133]).
  • Ausnahmegarantien: Alle Logging- und Abfragefunktionen (darunter IsEnabled, SetThreshold, sämtliche Log*-Methoden, WithLevel, Log und LogWith) sind als ausnahmesicher („exception safe“) spezifiziert und mit noexcept deklariert ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). Eine Ausnahme bildet der Destruktor ~Logger(), welcher als nicht ausnahmesicher („not exception safe“) geführt wird ([SWS_LOG_00260]). Interpretation: Dies dürfte bedeuten, dass bei internen Bereinigungs- oder Freigabefehlern im Rahmen des Backend-Housekeepings Fehlerzustände nicht vollständig abgefangen werden, weshalb die Deregistrierung im regulären Prozess-Shutdown erfolgen sollte.

<h4>Kontext</h4>
<p>Die Klasse <code>ara::log::Logger</code> repräsentiert einen Logging-Kontext innerhalb eines AUTOSAR-Adaptive-Anwendungsprozesses oder Prozessbereichs. Ein solcher Kontext kapselt zentrale Eigenschaften für die Protokollierung: eine Kontext-ID, eine zugehörige Beschreibung der Kontext-ID sowie ein konfigurierbares Standard-Loglevel (Default Log Level). Über diese Kontexte wird die Protokollausgabe innerhalb des Systems differenziert und gesteuert.</p>
<p>In der Systemarchitektur fungiert <code>ara::log::Logger</code> als Vermittler zwischen drei Beteiligten:</p>
<ul>
<li><strong>Anwendungsprozess (Application Process):</strong> Nutzt Instanzen von <code>ara::log::Logger</code>, um Meldungen abzusetzen, Filterschwellen dynamisch abzufragen oder anzupassen.</li>
<li><strong>Logging-Framework:</strong> Hält eine strikte Eigentümerschaft („strong ownership“) über alle Logger-Instanzen, steuert deren Erzeugung über Fabrikfunktionen wie <code>ara::log::CreateLogger</code> und übernimmt das Housekeeping.</li>
<li><strong>Logging-Backend:</strong> Nimmt die eigentlichen Protokolldaten entgegen; Logger-Kontexte werden während der Initialisierungsphase automatisch beim Backend registriert und während des geordneten Prozess-Shutdowns deregistriert.</li>
</ul>

<h4>Lebenszyklus</h4>
<p>Die Verwaltung der Instanzen von <code>ara::log::Logger</code> unterliegt einer strengen Kontrolle durch das Framework, um eine lückenlose Synchronisation mit dem Logging-Backend sicherzustellen:</p>
<ul>
<li><strong>Erzeugung und Besitzverhältnisse:</strong> Der Standardkonstruktor ist explizit gelöscht (<code>Logger() = delete</code>, <a class="spec-record-ref" data-req="SWS_LOG_00259" href="../spec/record.html?id=SWS_LOG_00259">[SWS_LOG_00259]</a>). Ein direktes Instanziieren durch die Anwendung ist untersagt. Die Erzeugung erfolgt kontrolliert über Funktionen wie <code>ara::log::CreateLogger</code>. Die Eigentümerschaft verbleibt beim Logging-Framework.</li>
<li><strong>Registrierung und Bereinigung:</strong> Ein Logger-Kontext wird bei seiner Erzeugung automatisch am Logging-Backend registriert. Bei der Prozessbeendigung erfolgt die Abmeldung automatisch, wodurch Anwendungsentwickler von der manuellen Lebenszyklusverwaltung entlastet werden.</li>
<li><strong>Zerstörung:</strong> Der Destruktor <code>~Logger()</code> ist spezifiziert (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). Er ist als threadsicher deklariert, jedoch als nicht ausnahmesicher („not exception safe“) ausgewiesen (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>).</li>
<li><strong>Nebenläufigkeit:</strong> Sämtliche Methoden zur Protokollierung und Schwellwertabfrage sind als threadsicher spezifiziert (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). Mehrere Threads können dieselbe Logger-Instanz parallel nutzen.</li>
</ul>

<h4>Nutzungspfad</h4>
<p>Der typische Ablauf beim Absetzen von Logmeldungen gliedert sich in folgende Phasen:</p>
<ol>
<li><strong>Filterschwelle prüfen oder konfigurieren:</strong> Die Anwendung kann die Filterschwelle einer Instanz über <code>SetThreshold(threshold)</code> zur Laufzeit festlegen (<a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>). Vor rechenintensiven Vorbereitungen von Protokolldaten kann mittels <code>IsEnabled(logLevel)</code> abgefragt werden, ob das gewünschte Loglevel die konfigurierte Berichtsschwelle erfüllt (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>). Liefert die Prüfung <code>false</code>, kann die Vorbereitung übersprungen werden.</li>
<li><strong>Stream-basiertes Logging initiieren:</strong> Für die Textprotokollierung stellt die Klasse spezifische Methoden für jeden Schweregrad bereit:
<ul>
<li><code>LogFatal()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>)</li>
<li><code>LogError()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00065" href="../spec/record.html?id=SWS_LOG_00065">[SWS_LOG_00065]</a>)</li>
<li><code>LogWarn()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00066" href="../spec/record.html?id=SWS_LOG_00066">[SWS_LOG_00066]</a>)</li>
<li><code>LogInfo()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00067" href="../spec/record.html?id=SWS_LOG_00067">[SWS_LOG_00067]</a>)</li>
<li><code>LogDebug()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00068" href="../spec/record.html?id=SWS_LOG_00068">[SWS_LOG_00068]</a>)</li>
<li><code>LogVerbose()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00069" href="../spec/record.html?id=SWS_LOG_00069">[SWS_LOG_00069]</a>)</li>
<li><code>WithLevel(logLevel)</code> (<a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>) zur programmatischen Bestimmung der Dringlichkeit.</li>
</ul>
Jede dieser Methoden liefert ein <code>LogStream</code>-Objekt zurück, das Argumente über den Stream-Operator <code>&lt;&lt;</code> entgegennimmt (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>Stream-Lebensdauer und Ausgabe:</strong> Im Standardfall ist die Lebensdauer des <code>LogStream</code>-Objekts auf eine einzige Anweisung beschränkt und endet mit dem Semikolon nach dem letzten Argument (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). Bei Bedarf kann der Stream einer Variablen zugewiesen werden, um dessen Lebensdauer über mehrere Anweisungen hinweg auszudehnen (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>Modellierte Nachrichten ausgeben:</strong> Alternativ zum Streaming können vorab modellierte Nachrichten über <code>Log(id, args...)</code> ausgegeben werden (<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). Falls zusätzliche Attribute übergeben werden sollen, erfolgt der Aufruf über <code>LogWith(attrs, msgId, params...)</code> mit einem Attribut-Tupel (<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Die Fehlerbehandlung in <code>ara::log::Logger</code> basiert vorwiegend auf statischer Typprüfung zur Übersetzungszeit und strikter Ausnahmesicherheit:</p>
<ul>
<li><strong>Fehlpassende Argumente bei modellierten Nachrichten:</strong> Wird die Template-Funktion <code>Log(id, args...)</code> mit Parametern aufgerufen, die nicht exakt der Definition der modellierten Nachricht entsprechen, ist das Programm fehlerhaft gebildet („ill-formed“) (<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). Dies führt zu einem Fehler bei der Kompilierung.</li>
<li><strong>Ungültige Attribute bei LogWith:</strong> Bei <code>LogWith(attrs, msgId, params...)</code> wird die Funktion per SFINAE aus der Überladungsauflösung ausgeschlossen, sofern ein Element des Attribut-Tupels kein gültiges Attribut darstellt (<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
<li><strong>Ausnahmegarantien:</strong> Alle Logging- und Abfragefunktionen (darunter <code>IsEnabled</code>, <code>SetThreshold</code>, sämtliche <code>Log*</code>-Methoden, <code>WithLevel</code>, <code>Log</code> und <code>LogWith</code>) sind als ausnahmesicher („exception safe“) spezifiziert und mit <code>noexcept</code> deklariert (<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>). Eine Ausnahme bildet der Destruktor <code>~Logger()</code>, welcher als nicht ausnahmesicher („not exception safe“) geführt wird (<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). Interpretation: Dies dürfte bedeuten, dass bei internen Bereinigungs- oder Freigabefehlern im Rahmen des Backend-Housekeepings Fehlerzustände nicht vollständig abgefangen werden, weshalb die Deregistrierung im regulären Prozess-Shutdown erfolgen sollte.</li>
</ul>
