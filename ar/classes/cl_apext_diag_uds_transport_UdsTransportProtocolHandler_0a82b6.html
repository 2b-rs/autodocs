السياق

الفئة apext::diag::uds_transport::UdsTransportProtocolHandler هي الفئة الأساسية المجردة للمكونات الإضافية لبروتوكول نقل UDS المحددة والخاصة في Diagnostic Management (DM) لـ AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»، [SWS_DM_00315]). وهي تفصل نواة التشخيص العامة عن خصائص شبكات الإرسال وطبقات النقل الملموسة مثل DoIP أو البروتوكولات المعتمدة على CAN.

يتفاعل معالج النقل بصورة أساسية مع ثلاثة أطراف:

  • Diagnostic Management Core: يدير DM دورة حياة المعالج بأكملها، ويوفر عبر مرجع المدير apext::diag::uds_transport::UdsTransportProtocolMgr الطرف المقابل لإشارات الحالة والبيانات ([SWS_DM_09015]، [SWS_DM_09025]).
  • طبقة الشبكة وعميل التشخيص: يتولى المكون الإضافي معالجة تبادل البيانات المادي أو المنطقي مع فاحص التشخيص الخارجي أو الداخلي للمركبة ([SWS_DM_00326]، [SWS_DM_00351]).
  • المعالج الدوري (اختياري): إذا كان بروتوكول النقل المعني يدعم عمليات الإرسال الدورية، فإن المعالج يوفر مرجعًا إلى UdsTransportProtocolPeriodicHandler عبر GetPeriodicHandler() ([SWS_DM_01068]).

دورة الحياة

يتم التحكم في دورة حياة تنفيذ بروتوكول النقل بشكل صارم بواسطة DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer»، [SWS_DM_00329]). ويتم الإنشاء عبر المنشئ UdsTransportProtocolHandler(handlerId, transportProtocolMgr)، حيث يخصص DM للمعالج معرفًا فريدًا من النوع UdsTransportProtocolHandlerID بالإضافة إلى المرجع إلى UdsTransportProtocolMgr المقترن ([SWS_DM_09015]، [SWS_DM_09025]). ويمكن الاستعلام عن ID المخصص في أي وقت عبر GetHandlerID() ([SWS_DM_00325]). وقد تم تحديد المنشئ على أنه آمن لخيوط المعالجة ([SWS_DM_09015]).

من أجل فصل عمليات التهيئة المعقدة للبروتوكول عن المنشئ، يستدعي DM بعد ذلك Initialize() ([SWS_DM_00319]، [SWS_DM_00329]). وباستثناء GetPeriodicHandler()، لا يجوز لـ DM استدعاء أي دوال أخرى للمعالج قبل الإرجاع الناجح لـ InitializationResult::kInitializeOk ([SWS_DM_01746]، [SWS_DM_09017]). بعد التهيئة الناجحة، يبدأ DM البروتوكول عبر Start() ([SWS_DM_00322]). ونظرًا لأن Start() يُنفذ بشكل غير متزامن، يمكن لـ DM بدء تشغيل معالجات متعددة بالتوازي لتقليل وقت بدء التشغيل ([SWS_DM_00322]).

إذا انتقل تطبيق DM إلى الحالة ApplicationState.kTerminating، فإنه يستدعي Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1، [SWS_DM_00333]، [SWS_DM_00323]). وينتظر DM حتى يؤكد المعالج الإيقاف عبر UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). بعد العودة من Stop()، لا يجوز للمكون الإضافي للمعالج استدعاء أي دوال أخرى على المدير – مع الاستثناء الوحيد المتمثل في الإشعار HandlerStopped() ([SWS_DM_01741]، [SWS_DM_00323]). ويتم التفكيك اللاحق عبر المُدمِّر الافتراضي ([SWS_DM_09016]).

مخطط الحالة: مراحل دورة الحياة وشروط الانتقال لمعالج بروتوكول نقل UDS. المصادر: [SWS_DM_00329]، [SWS_DM_00319]، [SWS_DM_01746]، [SWS_DM_01745]، [SWS_DM_00322]، [SWS_DM_00323]، [SWS_DM_00340].

مسار الاستخدام

أثناء التشغيل المستمر، يتولى المعالج التبادل ثنائي الاتجاه لرسائل UDS:

  1. استلام الرسائل (الدلالة): بمجرد استلام رسالة UDS جديدة على قناة ما ومعرفة عنوان المصدر وعنوان الوجهة ونوع العنونة (مادي أو وظيفي) وإجمالي طول الرسالة بالإضافة إلى أول بايتات من بيانات الحمولة (بايتان على الأقل للرسائل التي يزيد حجمها عن بايت واحد)، يستدعي المكون الإضافي UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 «Indication of UDS message reception»، [SWS_DM_00342]، [SWS_DM_00330]). ويمرر المعالج هنا معرف القناة في المعلمة globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»).
  2. إرسال الرسائل (الإرسال): يرسل DM استجابة تشخيص UDS المقترنة عبر المعالج نفسه والقناة نفسها (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer»، [SWS_DM_00348]). ولهذا الغرض، يستدعي Transmit(message, channelId) ([SWS_DM_00327]). وتُسلم الرسالة إلى المعالج بصفتها UdsMessageConstPtr على نمط std::unique_ptr.
  3. إشعار الإرسال: بمجرد إرسال الرسالة عبر الشبكة (أو حدوث خطأ)، يجب على المعالج إعادة ملكية message إلى DM عبر UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). ويتم نقل النتيجة بصفتها kTransmitOk أو kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3، [SWS_DM_00351]).

مسار استخدام محدد آخر هو استعادة القنوات بعد إعادة ضبط وحدة التحكم الإلكترونية (خدمة UDS 0x11 مع استجابة إيجابية بعد إعادة الضبط): هنا يستدعي DM الدالة NotifyReestablishment(channelId) قبل إعادة التشغيل ([SWS_DM_00326]). ويحفظ المكون الإضافي معلمات الاتصال (مثل عناوين IP والمنافذ) بشكل دائم. بعد إعادة التشغيل عبر Start()، يكتشف المكون الإضافي إعادة اتصال عميل التشخيص نفسه ويُبلغ DM عبر UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326]، [SWS_DM_01744]).

مخطط تسلسلي: استلام رسالة UDS، ونقل الاستجابة، والإشعار اللاحق. المصادر: [SWS_DM_00342]، [SWS_DM_00348]، [SWS_DM_00327]، [SWS_DM_00351].

سيناريوهات الأخطاء

تتعامل الواجهة مع حالات استثنائية وأخطاء متنوعة:

  • فشل التهيئة: إذا أرجع Initialize() القيمة InitializationResult::kInitializeFailed ([SWS_DM_09017])، فإن DM يُلغي عملية بدء بروتوكول النقل هذا تمامًا ولا يستدعي أي دوال أخرى على هذا المثيل ([SWS_DM_01745]).
  • عمليات الإرسال الدورية غير المدعومة: إذا كان البروتوكول المحدد لا يدعم عمليات الإرسال الدورية، فإن استدعاء GetPeriodicHandler() يُرجع ara::core::Result مع رمز الخطأ kConfigurationMismatch ([SWS_DM_01068]).
  • رفض استعادة القناة: إذا لم يتمكن المكون الإضافي من تلبية الحفظ الدائم لقناة ما (على سبيل المثال بسبب عدم توفر إمكانية تخزين غير متطاير أو تعيين غير مستقر)، يُرجع NotifyReestablishment(channelId) القيمة false ([SWS_DM_00326]).
  • أخطاء الإرسال في الشبكة: إذا تعذر على طبقة الشبكة إرسال رسالة تم تكليفها عبر Transmit()، فيجب على المعالج تمرير النتيجة kTransmitFailed في TransmitConfirmation ([SWS_DM_00351]). ويؤدي عدم إرجاع المخزن المؤقت إلى تسريبات في موارد DM.
  • انتهاك التسلسل بعد الإيقاف: إذا استدعى مكون إضافي دالة أخرى غير HandlerStopped() على UdsTransportProtocolMgr بعد العودة من Stop()، فإن ذلك يُعد انتهاكًا لتسلسل البروتوكول ([SWS_DM_00323]، [SWS_DM_01741]).

يستند دليل الفئة هذا إلى مواصفة AUTOSAR Adaptive R25-11.

              دالة NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
