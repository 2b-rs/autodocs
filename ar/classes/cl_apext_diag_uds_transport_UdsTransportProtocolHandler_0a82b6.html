تُستخدم كفئة أساسية مجردة لمكونات UDS الإضافية للنقل لنقل رسائل التشخيص وإعادة توجيهها.

تُستخدم الفئة المجردة كواجهة أساسية لمكونات UDS الإضافية للنقل من أجل الربط القياسي مع Diagnostic Management المتكيف (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»). وتقوم عملية تنفيذ مشتقة بإعادة توجيه رسائل التشخيص المستلمة إلى مدير البروتوكول وتنقل رسائل الاستجابة المولدة عبر قنوات مخصصة للشبكة إلى جهاز اختبار التشخيص. وتخضع دورة الحياة لتسلسل صارم يتكون من الإنشاء، والتهيئة المنفصلة، والبدء اللاتزامني، والإيقاف المنظم ([SWS_DM_00329]). بعد إنشاء المثيل، تصبح استدعاءات الدوال التشغيلية غير آمنة لخيوط المعالجة وتتطلب تحكمًا منسقًا من خلال نواة التشخيص.

السياق

تعد الفئة apext::diag::uds_transport::UdsTransportProtocolHandler فئة أساسية مجردة ضمن الوحدة diag لـ AUTOSAR Adaptive Platform. وتحدد الواجهة القياسية التي يتم عبرها ربط مكونات UDS الإضافية للنقل الاحتكارية أو الخاصة ببروتوكول معين بـ Diagnostic Management (DM) المتكيف (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»، [SWS_DM_00315]). وينفذ كل بروتوكول نقل محدد — على سبيل المثال للتشخيص عبر وسائط شبكات المركبات — هذه الواجهة كفئة فرعية مشتقة. ويُرجح أن يمتلك DM ويدير مثيل المعالج المعني بصورة حصرية طوال فترة عمره التشغيلي بالكامل. ويتم التفاعل بين نواة التشخيص والمكون الإضافي عبر المرجع transportprotocolManager من النوع UdsTransportProtocolMgr&، والذي يُمرر في المنشئ ويُخزن بصورة محمية ([SWS_DM_09015]، [SWS_DM_09025]). ويتم تعريف كل معالج بواسطة UdsTransportProtocolHandlerID عددي، يمكن الاستعلام عنه عبر GetHandlerID() ([SWS_DM_00325]).

دورة الحياة

يتم التحكم في دورة حياة معالج بروتوكول نقل UDS بواسطة DM بصورة تتابعية صارمة ([SWS_DM_00329]). بعد إنشاء المثيل عبر المنشئ UdsTransportProtocolHandler ([SWS_DM_09015])، تفصل الدالة Initialize() تهيئة البروتوكول الفعلية عن إنشاء الكائن ([SWS_DM_00319]). وباستثناء استعلام اختياري عبر GetPeriodicHandler()، لا يُسمح لـ DM باستدعاء أي دوال على المعالج قبل الإرجاع الناجح لـ InitializationResult::kInitializeOk ([SWS_DM_01746]، [SWS_DM_09017]). وبعد التهيئة الناجحة، ينقل استدعاء Start() المعالج إلى حالة المعالجة النشطة ([SWS_DM_00322]). ولتقليل زمن بدء التشغيل، صُممت Start() كعملية لا تزامنية؛ ويُرجح أن ينسق DM داخليًا البدء المتوازي لمعالجات متعددة. وإذا انتقل DM أثناء إيقاف التشغيل إلى الحالة ApplicationState.kTerminating، فإنه يوجه المعالج عبر Stop() للإنهاء ([SWS_DM_00323]، [SWS_DM_00333]). وينتظر DM الاكتمال، وهو ما يؤكده المعالج باستدعاء UdsTransportProtocolMgr::HandlerStopped() ([SWS_DM_00340]). وبعد العودة من Stop()، يُحظر على المكون الإضافي إجراء أي استدعاء دالة إلى المدير باستثناء HandlerStopped() ([SWS_DM_01741]). ويتم تحرير الموارد أخيرًا عبر الهادم الافتراضي ([SWS_DM_09016]). وبينما يعد المنشئ آمنًا لخيوط المعالجة، فإن دوال الواجهة التشغيلية مُعلنة بأنها غير آمنة لخيوط المعالجة.

مخطط الحالة: مراحل دورة الحياة وانتقالات الحالة لمعالج نقل UDS. المصادر: [SWS_DM_00319]، [SWS_DM_00322]، [SWS_DM_00323]، [SWS_DM_00329]، [SWS_DM_01745]، [SWS_DM_01746]

مسار الاستخدام

في التشغيل التشخيصي المنتظم، يعالج المعالج الرسائل الواردة وينقل الاستجابات. بمجرد توفر عنوان المصدر، وعنوان الوجهة، ونوع العنوان (مادي أو وظيفي)، وإجمالي طول الرسالة على واجهة الشبكة كحد أدنى، وأول بايتين (payloadInfo) في حالة بيانات الحمولة متعددة البايتات، يبلغ التنفيذ عن الطلب عبر UdsTransportProtocolMgr::IndicateMessage() إلى المدير ([SWS_DM_00342]، AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer»). ويُخصص كل طلب لقناة فريدة (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»). وللرد، يمرر DM استجابة التشخيص إلى نفس المعالج والقناة بواسطة Transmit(message, channelId) ([SWS_DM_00327]، [SWS_DM_00348]). وبعد النقل المادي، يعيد المعالج كائن الرسالة الممرر إلى المدير عبر UdsTransportProtocolMgr::TransmitConfirmation() ([SWS_DM_00327]، [SWS_DM_00351]). ويخص مسار استخدام متخصص عمليات إعادة تعيين وحدة التحكم الإلكترونية (خدمة UDS رقم 0x11) مع استجابة إيجابية بعد إعادة التشغيل: هنا يطلب DM قبل إعادة التعيين عبر NotifyReestablishment(channelId) أن يحفظ المعالج معلومات الاتصال بصورة غير متطايرة؛ وبعد إعادة التشغيل وتنفيذ Start() مجددًا، يبلغ المعالج عن استعادة نفس القناة عبر ChannelReestablished() ([SWS_DM_00326]، [SWS_DM_01744]).

مخطط تسلسلي: مسار إشعار رسالة UDS ونقل الاستجابة. المصادر: [SWS_DM_00327]، [SWS_DM_00342]، [SWS_DM_00348]، [SWS_DM_00351]

سيناريوهات الأخطاء

إذا فشلت تهيئة طبقة النقل وأعادت Initialize() الحالة InitializationResult::kInitializeFailed، يوقف DM عملية بدء تشغيل هذا البروتوكول على الفور ولا يستدعي أي دوال إضافية على هذا المثيل ([SWS_DM_01745]، [SWS_DM_09017]). وإذا كانت عمليات النقل الدورية غير مدعومة في بروتوكول النقل، يعيد استدعاء GetPeriodicHandler() كائن ara::core::Result مع رمز الخطأ kConfigurationMismatch ([SWS_DM_01068]). وإذا تعذر ضمان استعادة القناة المطلوبة لإعادة تعيين ECU، تفشل NotifyReestablishment() وتشير إلى ذلك عبر القيمة المعادة false ([SWS_DM_00326]). وأخيرًا، إذا تعثرت عملية إرسال استجابة تشخيصية على طبقة الشبكة، يجب على المعالج إبلاغ المدير بذلك عند التأكيد، عن طريق ضبط المعامل result في TransmitConfirmation() على kTransmitFailed ([SWS_DM_00351]).

تم إنشاء هذا الدليل تلقائيًا استنادًا إلى مواصفة AUTOSAR رقم R25-11.

NotifyReestablishment دالة

Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().

virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;

          تُستخدم الطريقة الافتراضية البحتة Initialize للتهيئة الصريحة لمثيل من apext::diag::uds_transport::UdsTransportProtocolHandler وتفصل هذه العملية رسمياً عن بناء الكائن [SWS_DM_00319]. يتم استدعاؤها من قِبل Diagnostic Manager (DM) بشكل متزامن وبدون معلمات، ولا تطلق استثناءات (noexcept) وتُرجع InitializationResult [SWS_DM_00319] [SWS_DM_09017].
          

          دورة الحياة والتزامن
          

          الاستدعاء مدمج في إدارة دورة حياة طبقة نقل UDS AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer». يجب على DM إدارة المراحل بترتيب ثابت: البناء، استدعاء Initialize، البدء عبر Start والإنهاء عبر Stop [SWS_DM_00329]. الطريقة محددة على أنها غير آمنة لخيوط المعالجة (not thread-safe) [SWS_DM_00319]؛ لذلك من المفترض أن ينفذها DM في إطار مرحلة تهيئة متزامنة دون عمليات وصول متوازية.
          

          معالجة الأخطاء والتفاعل
          

          تشير الطريقة إلى النتيجة عبر العداد InitializationResult::kInitializeOk أو InitializationResult::kInitializeFailed [SWS_DM_09017]. يعتمد السلوك الإضافي لـ DM بشكل مباشر على قيمة الإرجاع:
          

            

          • عند الإرجاع بنجاح مع kInitializeOk، يُسمح لـ DM باستدعاء الطرق اللاحقة للمعالج؛ وقبل قيمة الإرجاع الناجحة هذه، لا يُسمح بأي استدعاء طريقة آخر باستثناء GetPeriodicHandler [SWS_DM_01746].
            • 

          • إذا أرجع المعالج kInitializeFailed، فإن DM يلغي عملية تهيئة بروتوكول النقل هذا تماماً ولا يستدعي أي طرق أخرى على المثيل المعني [SWS_DM_01745].
            • 

          


          

          تم إنشاء هذا النص بواسطة ذكاء اصطناعي استناداً إلى AUTOSAR R25-11.

              دالة NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
