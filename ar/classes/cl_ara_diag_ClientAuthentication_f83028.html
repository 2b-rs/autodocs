تُستخدم من قبل التطبيق للإبلاغ عن حالات المصادقة وأدوار المستخدم النشطة إلى Diagnostic Server.

تتيح الواجهة للتطبيق إبلاغ Diagnostic Server بحالة المصادقة وأدوار المستخدم النشطة لعميل تشخيص [SWS_DM_01132]. وعبر استدعاءات مثل Authenticate أو OverrideDefaultRoles، يتم التحكم في انتقالات الحالة وتوفير مقابض لإدارة قوائم الوصول الديناميكية [SWS_DM_01206]. ويمكن مراقبة تغيرات الحالة الناتجة عن انتهاء المهلات لا تزامنيًا عبر عنصر إشعار. ونظرًا لأن الفئة ليست آمنة لخيوط المعالجة ولا تسمح بالنسخ، يجب أن يتم الوصول داخل التطبيق بصورة متزامنة.

السياق

تُستخدم الفئة ara::diag::ClientAuthentication كواجهة مركزية للتطبيق لإعلام مثيل Diagnostic Server بحالات المصادقة وأدوار المستخدم المصادق عليها حاليًا [SWS_DM_01132]، SWS Diagnostics, ص. 129. ويشارك في هذا التفاعل ثلاثة أطراف رئيسية:

  • التطبيق (Application): ينفذ عمليات التحقق من المصادقة — إما باستخدام واجهات Diagnostic Server أو عبر آليات خاصة بالتطبيق — وينقل أدوار المستخدم إلى Diagnostic Server [SWS_DM_01142].
  • خادم التشخيص / مدير التشخيص (Diagnostic Server / Diagnostic Manager): يدير جلسات التشخيص ويفرض حقوق الوصول إلى موارد التشخيص استنادًا إلى الأدوار وحالة المصادقة [SWS_DM_01206].
  • عميل التشخيص (Diagnostic Client): جهاز اختبار خارجي أو عميل SOVD يوجه طلبات التشخيص إلى وحدة التحكم الإلكترونية [SWS_DM_01210]، [SWS_DM_01470].

يتحدد عدد مثيلات ClientAuthentication بواسطة عنصر النموذج DiagnosticExternalAuthenticationIdentification SWS Diagnostics, ص. 129. ويتيح هذا العنصر تهيئة المصادقة لعميل ذي عنوان مصدر ثابت أو عبر نطاق عناوين، إذا لم يكن عنوان المصدر النهائي معروفًا بعد في وقت التجميع SWS Diagnostics, ص. 129. تفسير: يتم تعيين عملاء التشخيص لمثيلات محددة من ClientAuthentication في وقت التشغيل استنادًا إلى نطاقات عناوين المصدر هذه. وفي حالة عملاء SOVD، يمرر Diagnostic Server كائن ClientAuthentication مباشرةً إلى التطبيق عند التحقق من صحة رمز التفويض عبر ara::diag::SovdAuthorization::ValidateAuthorization [SWS_DM_01470].

مخطط السياق: أطراف التفاعل لواجهة المصادقة. المصادر: [SWS_DM_01132]، [SWS_DM_01202]، [SWS_DM_01470]، SWS Diagnostics, ص. 129

دورة الحياة

يحصل التطبيق على مثيل من ClientAuthentication عبر دوال محملة بشكل زائد من ara::diag::ExternalAuthentication::Get [SWS_DM_01202] أو في سياق فحص رمز SOVD [SWS_DM_01470]. وتمتلك الفئة دلالات ملكية صارمة: فمنشئ النسخ [SWS_DM_01139] ومعامل تعيين النسخ [SWS_DM_01140] محذوفان (=delete). وعمليات النقل (منشئ النقل [SWS_DM_01137] ومعامل تعيين النقل [SWS_DM_01138]) محددة مسبقًا كافتراضية ومُعلنة كـ noexcept. والهادم أيضًا noexcept [SWS_DM_01136]. وجميع دوال الأعضاء بالإضافة إلى الهادم ليست آمنة لخيوط المعالجة (not thread-safe) [SWS_DM_01136]، [SWS_DM_01141]، [SWS_DM_01142]، [SWS_DM_01143]، [SWS_DM_01144].

يتم تمثيل حالة المصادقة عبر نوع التعداد DiagnosticAuthState [SWS_DM_01133]:

  • kDeAuthenticated (0x00): لا يوجد عميل تشخيص مصادق عليه. ويكون العميل افتراضيًا في هذه الحالة عند بدء تشغيل النظام [SWS_DM_01205]. وتعد تلك الأدوار (DiagnosticAuthRole) أدوارًا افتراضية التي ضُبطت خاصيتها isDefault على TRUE [SWS_DM_01204]، [SWS_DM_01134]. وعبر OverrideDefaultRoles، يمكن تجاوز هذه الأدوار الافتراضية مؤقتًا لمهلة محددة [SWS_DM_01141]، [SWS_DM_01209].
  • kAuthenticated (0x01): عميل تشخيص مصادق عليه. ويتم الوصول إلى هذه الحالة عبر استدعاء Authenticate، مما يؤدي إلى تنشيط أدوار المستخدم الممررة في Diagnostic Server [SWS_DM_01142]، [SWS_DM_01206].

يتم إطلاق انتقال تلقائي للحالة من kAuthenticated عودة إلى kDeAuthenticated إذا لم يرسل العميل في الجلسة الافتراضية أي طلبات أخرى بعد تأكيد النقل الأخير (TransmitConfirmation) وانتهت مهلة عدم النشاط [SWS_DM_01210]، أو عند حدوث مهلة S3 [SWS_DM_01144]، [SWS_DM_02077].

مخطط الحالة: دورة الحياة وانتقالات الحالة لمصادقة العميل. المصادر: [SWS_DM_01133]، [SWS_DM_01204]، [SWS_DM_01205]، [SWS_DM_01206]، [SWS_DM_01209]، [SWS_DM_01210]

مسار الاستخدام

يتضمن المسار المنتظم لإدارة مصادقة العميل الخطوات التالية:

  1. تسجيل عنصر الإشعار: يسجل التطبيق باستخدام SetNotifier دالة رد نداء من النوع ClientAuthenticationSetNotifier (std::function<void(DiagnosticAuthState)>) [SWS_DM_01144]، [SWS_DM_02077]. وبذلك يتم إبلاغه عند حدوث تغيرات في الحالة — على سبيل المثال الانتقال إلى kDeAuthenticated بسبب عدم النشاط أو مهلة S3 [SWS_DM_01144]. ويتجاوز الاستدعاء الجديد عنصر الإشعار المضبوط سابقًا [SWS_DM_01144].
  2. الاستعلام عن الحالة: عبر الدالة GetState()، يمكن للتطبيق الاستعلام تزامنيًا عن حالة المصادقة الحالية للعميل [SWS_DM_01143].
  3. الإبلاغ عن المصادقة: بمجرد اكتمال المصادقة بنجاح، يستدعي التطبيق Authenticate مع أدوار المستخدم المطلوب تفعيلها (ara::core::Vector<DiagnosticAuthRole>) [SWS_DM_01142]، [SWS_DM_01134]. ويضبط Diagnostic Server الحالة على kAuthenticated ويعيد ClientAuthenticationHandle [SWS_DM_01206].
  4. إدارة حقوق الوصول: عبر ClientAuthenticationHandle المستلم، يمكن للتطبيق تهيئة قائمة الوصول الديناميكية (DynamicAccessList) للعميل [SWS_DM_01213]، SWS Diagnostics, ص. 132. وفي الوقت نفسه، يتم تجديد نافذة وقت عدم نشاط العميل من خلال استخدام هذا المقبض SWS Diagnostics, ص. 133.

إذا كان العميل في الحالة kDeAuthenticated، يمكن للتطبيق بدلًا من ذلك استدعاء OverrideDefaultRoles(defaultRoles, timeout) لتنشيط أدوار افتراضية بديلة مؤقتًا؛ ويعيد هذا الاستدعاء أيضًا عند النجاح ClientAuthenticationHandle [SWS_DM_01141]، [SWS_DM_01209].

مخطط تسلسلي: مسار الاستدعاء والإشعار عند المصادقة. المصادر: [SWS_DM_01142]، [SWS_DM_01144]، [SWS_DM_01206]، [SWS_DM_01210]

سيناريوهات الأخطاء

تعيد الدوال Authenticate، وOverrideDefaultRoles، وGetState قيم الإرجاع الخاصة بها مغلفة في ara::core::Result، وهي محددة بأنها آمنة من حيث الاستثناءات (exception safe) وكذلك noexcept [SWS_DM_01141]، [SWS_DM_01142]، [SWS_DM_01143]. وفي حالة الخطأ، يتم الإبلاغ عن رمز الخطأ القياسي التالي:

  • DiagErrc::kServiceNotAvailable: يحدث عندما يتعذر تنفيذ الاستدعاء نظرًا لأن الوظائف الأساسية لـ Diagnostic Manager غير متوفرة حاليًا [SWS_DM_01141]، [SWS_DM_01142]، [SWS_DM_01143]. ويمتلك هذا الخطأ دلالات التراجع (rollback_semantics)، وبالتالي لا تتبقى أي تغييرات حالة غير مكتملة [SWS_DM_01141]، [SWS_DM_01142]، [SWS_DM_01143].

لم تُحدد رموز خطأ قياسية لـ SetNotifier [SWS_DM_01144]. وكشرط مسبق أساسي، يتطلب OverrideDefaultRoles أن يكون العميل في الحالة kDeAuthenticated وقت الاستدعاء [SWS_DM_01209].

الاستخدام والاستدعاء

يستدعي التطبيق الدالة ara::diag::ClientAuthentication::Authenticate لإبلاغ مثيل Diagnostic Server بنجاح مصادقة عميل التشخيص [SWS_DM_01142]. يمكن أن يتم ذلك بعد مصادقة عبر واجهات Diagnostic Server أو عبر آليات خاصة بالتطبيق [SWS_DM_01142].

تأخذ الدالة userRoles (من النوع ara::core::Vector<DiagnosticAuthRole>) كمعلمة إدخال. وعند نجاح الاستدعاء، تنتقل حالة مصادقة المثيل إلى kAuthenticated وتعتمد أدوار المستخدم الممررة بشكل دائم [SWS_DM_01206]. وتُرجع كقيمة إرجاع ara::core::Result<ClientAuthenticationHandle> [SWS_DM_01142]. وبما أنه يتم توفير كائن Result مباشرةً، فمن المرجح أن تتم المعالجة بشكل متزامن في سياق الاستدعاء.

معالجة الأخطاء والتزامن

الطريقة مصرّح عنها كـ noexcept وتُعتبر آمنة ضد الاستثناءات (exception safe) [SWS_DM_01142]. إذا حدث خطأ بسبب عدم توفر وظائف أساسية لـ Diagnostic Manager في وقت الاستدعاء، فإن العملية تفشل مع دلالات التراجع (Rollback Semantics) وتُرجع DiagErrc::kServiceNotAvailable في كائن Result [SWS_DM_01142].

فيما يتعلق بالتزامن، تم تحديد الطريقة صراحةً بأنها not thread-safe [SWS_DM_01142]. وبالتالي، فإن الاستدعاءات المتوازية على كائن ClientAuthentication نفسه غير مسموح بها ويجب مزامنتها بواسطة التطبيق.

التفاعل ودورة الحياة

يتيح كائن ClientAuthenticationHandle الذي تم الحصول عليه للتطبيق تعريف DynamicAccessList لعميل تمت مصادقته أو توسيعها [SWS_DM_01142]. بالإضافة إلى ذلك، يبدأ الاستدعاء أو يشير إلى مراقبة عدم نشاط العميل: إذا لم يَرِد أي طلب UDS آخر بعد نجاح المصادقة في حالة الجلسة الافتراضية طوال مدة authenticationTimeout، يعيد مثيل Diagnostic Server العميل تلقائيًا إلى kDeAuthenticated [SWS_DM_01210]. ولمنع انتهاء المهلة هذا، يمكن للتطبيق تحديث المؤقت عبر الطريقة Refresh للمقبض [SWS_DM_01155].

تم إنشاء هذا النص بواسطة ذكاء اصطناعي بناءً على مواصفات AUTOSAR.
