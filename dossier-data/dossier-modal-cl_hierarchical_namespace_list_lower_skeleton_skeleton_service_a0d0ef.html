  <h4>Context</h4>
  <p>
    The class <code>{&lt;hierarchical-namespace-list-lower-skeleton&gt;}::skeleton::{ &lt;service-interface-name&gt;}Skeleton</code> forms the server-side base abstraction for providing a service interface within the Communication Management module (<code>com</code>) of the AUTOSAR Adaptive Platform. As a generated interface skeleton, the skeleton assumes the intermediary role between the platform-specific communication infrastructure (such as a SOME/IP binding) and the application-specific service provider implementation. It decouples the service business logic from protocol details, message deserialization, and the underlying dispatching.
  </p>
  <p>
    In the overall system, the skeleton class interacts with three essential partners:
  </p>
  <ul>
    <li>
      <strong>Service application (Service Provider):</strong> The concrete application derives from the skeleton class and implements the pure virtual method functions for regular request-response patterns <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a> as well as fire-and-forget methods <a class="spec-record-ref" data-req="SWS_CM_90434" href="../spec/record.html?id=SWS_CM_90434">[SWS_CM_90434]</a>.
    </li>
    <li>
      <strong>Communication infrastructure (middleware):</strong> The runtime environment receives incoming request messages from service clients, deserializes the transmitted data, and forwards them to the skeleton for method execution <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=99">AUTOSAR_AP_SWS_CommunicationManagement p. 99</a>.
    </li>
    <li>
      <strong>Asynchronous execution context:</strong> Return types such as <code>ara::core::Future</code> decouple call acceptance from asynchronous result provision <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>.
    </li>
  </ul>

  <h4>Lifecycle</h4>
  <p>
    The derived skeleton object is instantiated explicitly by the service application. During creation via the constructor, the processing mode for method calls (<code>ara::com::MethodCallProcessingMode</code>) must be passed <a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>. This mode determines how incoming method calls are processed in terms of threading and execution flow:
  </p>
  <ul>
    <li>
      <strong>Event-driven processing (<code>kEvent</code> or <code>kEventSingleThread</code>):</strong> As soon as an incoming request message has been deserialized, the corresponding virtual method of the skeleton class is called directly as part of message reception <a class="spec-record-ref" data-req="SWS_CM_10306" href="../spec/record.html?id=SWS_CM_10306">[SWS_CM_10306]</a>.
    </li>
    <li>
      <strong>Buffered polling processing (<code>kPoll</code>):</strong> Incoming messages are buffered and only executed when the application actively triggers processing via the dedicated polling interface <a class="spec-record-ref" data-req="SWS_CM_10307" href="../spec/record.html?id=SWS_CM_10307">[SWS_CM_10307]</a>.
    </li>
  </ul>
  <p>
    The lifetime of the skeleton object is entirely the responsibility of the creating service application. Before destroying the instance, the service should be deregistered in an orderly manner (Interpretation: A controlled termination ensures that no further method calls access released resources of the service application and that pending asynchronous calculations can be completed cleanly).
  </p>

  <h4>Usage Path</h4>
  <p>
    The typical usage sequence for providing a service via the skeleton comprises the following steps:
  </p>
  <ol>
    <li>
      <strong>Interface implementation:</strong> The service application derives from <code>{&lt;hierarchical-namespace-list-lower-skeleton&gt;}::skeleton::{ &lt;service-interface-name&gt;}Skeleton</code> and implements the pure virtual methods:
      <ul>
        <li>Regular methods with a return value implement the signature <code>virtual ara::core::Future&lt;{&lt;method-name&gt;}Output&gt; {&lt;method-name&gt;}(...) noexcept = 0</code> <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>.</li>
        <li>One-way methods without a response implement <code>virtual void {&lt;fnfmethod-name&gt;}(...) noexcept = 0</code> <a class="spec-record-ref" data-req="SWS_CM_90434" href="../spec/record.html?id=SWS_CM_90434">[SWS_CM_90434]</a>.</li>
      </ul>
    </li>
    <li>
      <strong>Instantiation:</strong> The derived skeleton class is constructed with the desired <code>MethodCallProcessingMode</code> <a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>.
    </li>
    <li>
      <strong>Method execution:</strong> When requests arrive, the middleware calls the implemented method <a class="spec-record-ref" data-req="SWS_CM_10306" href="../spec/record.html?id=SWS_CM_10306">[SWS_CM_10306]</a>.
    </li>
    <li>
      <strong>Result return:</strong> For regular methods, the service application returns a <code>ara::core::Future</code> with the generated <code>Output</code> object <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>, <a class="spec-record-ref" data-req="SWS_CM_99556" href="../spec/record.html?id=SWS_CM_99556">[SWS_CM_99556]</a>, which is serialized by the middleware and sent to the client as a response message. For fire-and-forget methods, no response transmission takes place <a class="spec-record-ref" data-req="SWS_CM_90434" href="../spec/record.html?id=SWS_CM_90434">[SWS_CM_90434]</a>.
    </li>
  </ol>

  <h4>Error Scenarios</h4>
  <p>
    With regard to error behavior, method calls differ fundamentally based on their communication semantics:
  </p>
  <ul>
    <li>
      <strong>Regular methods:</strong> The interface is declared as <code>noexcept</code> and requires exception safety (<code>exception safe</code>) <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>. If method processing fails, the error is not reported via C++ exceptions, but is transported asynchronously via the returned <code>ara::core::Future</code>. In the event of an error, this contains either an error code from <code>ara::com::ComErrc</code> or a domain-specific application error of type <code>ApApplicationError</code> <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>.
    </li>
    <li>
      <strong>Fire-and-forget methods:</strong> These methods are also declared as <code>noexcept</code> and must be implemented to be exception-safe <a class="spec-record-ref" data-req="SWS_CM_90434" href="../spec/record.html?id=SWS_CM_90434">[SWS_CM_90434]</a>. Since by design no back-channel to the calling client exists, neither success nor error information can be transmitted. If an error occurs during processing, it must be handled internally within the service provider (Interpretation: Local logging or internal compensation measures are mandatory for fire-and-forget methods, as no error transmission to the client takes place).
    </li>
  </ul>
