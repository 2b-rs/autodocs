<h4>Role of FrTrcv between FlexRay Interface and transceiver hardware</h4>
<p>The FlexRay Transceiver Driver (FrTrcv) controls and monitors external FlexRay transceiver devices. It sets and reads their operating mode (<a class="spec-record-ref" data-req="SWS_FrTrcv_00323" href="../../spec/record.html?id=SWS_FrTrcv_00323">[SWS_FrTrcv_00323]</a>, <a class="spec-record-ref" data-req="SWS_FrTrcv_00324" href="../../spec/record.html?id=SWS_FrTrcv_00324">[SWS_FrTrcv_00324]</a>). It also determines the wake-up reason (<a class="spec-record-ref" data-req="SWS_FrTrcv_00325" href="../../spec/record.html?id=SWS_FrTrcv_00325">[SWS_FrTrcv_00325]</a>) and clears pending wake-up events (<a class="spec-record-ref" data-req="SWS_FrTrcv_00329" href="../../spec/record.html?id=SWS_FrTrcv_00329">[SWS_FrTrcv_00329]</a>). For active-star transceivers, it additionally provides the error status per branch and can enable and disable individual branches (<a class="spec-record-ref" data-req="SWS_FrTrcv_00419" href="../../spec/record.html?id=SWS_FrTrcv_00419">[SWS_FrTrcv_00419]</a>, <a class="spec-record-ref" data-req="SWS_FrTrcv_00442" href="../../spec/record.html?id=SWS_FrTrcv_00442">[SWS_FrTrcv_00442]</a>, <a class="spec-record-ref" data-req="SWS_FrTrcv_00443" href="../../spec/record.html?id=SWS_FrTrcv_00443">[SWS_FrTrcv_00443]</a>). <code>FrTrcv_GetVersionInfo</code> explicitly provides the version of the module and not that of the transceiver hardware (<a class="spec-record-ref" data-req="SWS_FrTrcv_00326" href="../../spec/record.html?id=SWS_FrTrcv_00326">[SWS_FrTrcv_00326]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_5_FrTrcv_GetVersionInfo.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_5_FrTrcv_GetVersionInfo">SWS FrTrcv p. 43</a>).</p>
<p>Towards the hardware, the driver accesses via the MCAL drivers Dio, Spi, and Icu. It reports events to DEM, DET, and EcuM. The required services and imported types are defined in <a class="spec-record-ref" data-req="SWS_FrTrcv_00334" href="../../spec/record.html?id=SWS_FrTrcv_00334">[SWS_FrTrcv_00334]</a> and <a class="spec-record-ref" data-req="SWS_FrTrcv_00321" href="../../spec/record.html?id=SWS_FrTrcv_00321">[SWS_FrTrcv_00321]</a>. It implements wait times during state changes using <code>Tm_BusyWait1us16bit</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00485" href="../../spec/record.html?id=SWS_FrTrcv_00485">[SWS_FrTrcv_00485]</a>).</p>
<p>Upwards, the FlexRay Interface calls <code>FrTrcv_SetTransceiverMode</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-6869a4c14c87fd16.html" data-snip="FIG-6869a4c14c87fd16">SWS FrTrcv p. 57</a>). The FlexRay State Manager controls the transceivers of both channels via <code>FrIf_SetTransceiverMode</code> and <code>FrIf_GetTransceiverWUReason</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_9_4_Dual_Channel_Wakeup.html" data-snip="SNIP_CLASSIC_COMM_SECTION_9_4_Dual_Channel_Wakeup">SWS FrSM p. 54</a>). Interpretation: FrIf is likely to map these calls to the FrTrcv services of the same name.</p>

<h4>From power-on to operating mode: initialization and mode changes</h4>
<p>After power-on, the driver is in the NOT_ACTIVE state and is not initialized. The call <code>FrTrcv_Init(ConfigPtr)</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00322" href="../../spec/record.html?id=SWS_FrTrcv_00322">[SWS_FrTrcv_00322]</a>) transitions it to ACTIVE, specifically into the mode defined by the configuration (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_FIGURE_Figure_7_1.html" data-snip="SNIP_CLASSIC_COMM_FIGURE_Figure_7_1">SWS FrTrcv p. 21</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-63e172ffa18e0e7b.html" data-snip="FIG-63e172ffa18e0e7b">SWS FrTrcv p. 23</a>). The structure of <code>FrTrcv_ConfigType</code> is implementation-specific (<a class="spec-record-ref" data-req="SWS_FrTrcv_00487" href="../../spec/record.html?id=SWS_FrTrcv_00487">[SWS_FrTrcv_00487]</a>). Drivers that serve wake-up sources must be reinitialized in the restart block of the EcuM; in doing so, the trigger mechanism for the wake-up notification is re-armed (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_8_3_1_FrTrcv_Init.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_8_3_1_FrTrcv_Init">SWS FrTrcv p. 37</a>).</p>
<p>Within ACTIVE, <code>FrTrcv_TrcvModeType</code> recognizes four modes (<a class="spec-record-ref" data-req="SWS_FrTrcv_00481" href="../../spec/record.html?id=SWS_FrTrcv_00481">[SWS_FrTrcv_00481]</a>):</p>
<ul>
<li><code>NORMAL</code>: full communication.</li>
<li><code>RECEIVEONLY</code>: like NORMAL, but receive only.</li>
<li><code>STANDBY</code>: no communication; the ECU remains powered if the transceiver controls the power supply.</li>
<li><code>SLEEP</code>: no communication; depending on the responsibility for the power supply, the ECU may be unpowered.</li>
</ul>
<p>In STANDBY and SLEEP, wake-up via the bus or locally is possible if the hardware supports this (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_FIGURE_Figure_7_1.html" data-snip="SNIP_CLASSIC_COMM_FIGURE_Figure_7_1">SWS FrTrcv p. 21</a>). For passive operation (Receive-Only), FrSM maintains the concurrent states <code>FRSM_ECU_ACTIVE</code> and <code>FRSM_ECU_PASSIVE</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRSM_SECTION_7_3_2_States.html" data-snip="SNIP_CLASSIC_FRSM_SECTION_7_3_2_States">SWS FrSM p. 18</a>).</p>
<p><code>FrTrcv_SetTransceiverMode</code> operates synchronously and is non-reentrant. Upon success, the service returns <code>E_OK</code>. In the case of <code>E_NOT_OK</code>, the previous state is retained; transitions into optional states may fail (<a class="spec-record-ref" data-req="SWS_FrTrcv_00323" href="../../spec/record.html?id=SWS_FrTrcv_00323">[SWS_FrTrcv_00323]</a>). When transitioning to STANDBY, the error history in the transceiver is cleared as far as the hardware supports this (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_2_FrTrcv_SetTransceiverMode.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_2_FrTrcv_SetTransceiverMode">SWS FrTrcv p. 39</a>). If <code>FrTrcvIcuChannelRef</code> is configured, the following applies to the wake-up notification via ICU channels:</p>
<ul>
<li>The channels are enabled upon the transition to STANDBY (<a class="spec-record-ref" data-req="SWS_FrTrcv_00491" href="../../spec/record.html?id=SWS_FrTrcv_00491">[SWS_FrTrcv_00491]</a>).</li>
<li>Upon the transition to NORMAL, they are disabled (<a class="spec-record-ref" data-req="SWS_FrTrcv_00492" href="../../spec/record.html?id=SWS_FrTrcv_00492">[SWS_FrTrcv_00492]</a>).</li>
<li>The driver uses <code>Icu_EnableNotification</code> and <code>Icu_DisableNotification</code> for this (<a class="spec-record-ref" data-req="SWS_FrTrcv_00490" href="../../spec/record.html?id=SWS_FrTrcv_00490">[SWS_FrTrcv_00490]</a>).</li>
</ul>
<p>The reentrant <code>FrTrcv_GetTransceiverMode</code> provides the current mode (<a class="spec-record-ref" data-req="SWS_FrTrcv_00324" href="../../spec/record.html?id=SWS_FrTrcv_00324">[SWS_FrTrcv_00324]</a>).</p>

<h4>Wakeup detection: polling, notification to EcuM, and wakeup reason</h4>
<p>For R20-11, only the signature is documented for <code>FrTrcv_MainFunction</code>: service ID 0x0d, available via <code>SchM_FrTrcv.h</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00330" href="../../spec/record.html?id=SWS_FrTrcv_00330">[SWS_FrTrcv_00330]</a>). The passage from R23-11 describes the task in more detail: the function polls all buses in STANDBY and SLEEP for wakeup events and stores them internally. Its period is defined by the configuration, and it is independent of the FlexRay bus schedule (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_5_1_FrTrcv_MainFunction.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_5_1_FrTrcv_MainFunction">SWS FrTrcv p. 49</a>). The period is set via <code>FrTrcvMainFunctionCycleTime</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-2da5c4ca912c9e8f.html" data-snip="FIG-2da5c4ca912c9e8f">ECUC-Parameter p. 250</a>).</p>
<p>If <code>FrTrcv_CheckWakeupByTransceiver</code> is called (<a class="spec-record-ref" data-req="SWS_FrTrcv_00331" href="../../spec/record.html?id=SWS_FrTrcv_00331">[SWS_FrTrcv_00331]</a>), the driver reports wakeup events to the ECU State Manager (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_7_FrTrcv_CheckWakeupByTransceiver.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_7_FrTrcv_CheckWakeupByTransceiver">SWS FrTrcv p. 46</a>). For this, it uses <code>EcuM_SetWakeupEvent</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00334" href="../../spec/record.html?id=SWS_FrTrcv_00334">[SWS_FrTrcv_00334]</a>). Presumably, this report concerns the events previously stored internally. For wakeup via the bus, there is additionally a notification that the driver triggers as soon as the SPI or DIO driver informs it. It runs in the caller's context, thus possibly in an interrupt context (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_7_FrTrcv_CheckWakeupByTransceiver.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_7_FrTrcv_CheckWakeupByTransceiver">SWS FrTrcv p. 46</a>).</p>
<p><code>FrTrcv_GetTransceiverWUReason</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00325" href="../../spec/record.html?id=SWS_FrTrcv_00325">[SWS_FrTrcv_00325]</a>) returns the wakeup reason as <code>FrTrcv_TrcvWUReasonType</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00074" href="../../spec/record.html?id=SWS_FrTrcv_00074">[SWS_FrTrcv_00074]</a>) with these values:</p>
<ul>
<li><code>FRTRCV_WU_NOT_SUPPORTED</code></li>
<li><code>FRTRCV_WU_BY_BUS</code></li>
<li><code>FRTRCV_WU_BY_PIN</code></li>
<li><code>FRTRCV_WU_INTERNALLY</code></li>
<li><code>FRTRCV_WU_RESET</code></li>
<li><code>FRTRCV_WU_POWER_ON</code></li>
</ul>
<p>The type definition is in <code>Fr_GeneralTypes.h</code> and can thus be shared by multiple transceiver drivers (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_2_3_FrTrcv_TrcvWUReasonType.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_2_3_FrTrcv_TrcvWUReasonType">SWS FrTrcv p. 34</a>). How exactly wakeup reasons can be distinguished depends heavily on the hardware (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_4_FrTrcv_GetTransceiverWUReason.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_4_FrTrcv_GetTransceiverWUReason">SWS FrTrcv p. 42</a>). <code>FrTrcv_ClearTransceiverWakeup</code> clears pending wakeup events of all types under control of the upper layer. The service can also be used when wakeup notification is disabled (<a class="spec-record-ref" data-req="SWS_FrTrcv_00329" href="../../spec/record.html?id=SWS_FrTrcv_00329">[SWS_FrTrcv_00329]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_6_FrTrcv_ClearTransceiverWakeup.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_6_FrTrcv_ClearTransceiverWakeup">SWS FrTrcv p. 44</a>).</p>
<p>In dual-channel wakeup, FrSM queries the wakeup reasons of both channels, such as <code>FRTRCV_WU_POWER_ON</code> or <code>FRTRCV_WU_BY_BUS</code>. Subsequently, it switches both transceivers to <code>FRTRCV_TRCVMODE_NORMAL</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_9_4_Dual_Channel_Wakeup.html" data-snip="SNIP_CLASSIC_COMM_SECTION_9_4_Dual_Channel_Wakeup">SWS FrSM p. 54</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_9_5_Dual_Channel_Wakeup_Forward.html" data-snip="SNIP_CLASSIC_COMM_SECTION_9_5_Dual_Channel_Wakeup_Forward">SWS FrSM p. 56</a>).</p>

<h4>Active star branches: error status and branch control</h4>
<p>The branch APIs are only available if branches of active stars are configured. Optional functionality is enabled or disabled at pre-compile time (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DEM_SECTION_8_6_3_Configurable_interfaces_FLEXRAYTRANSCEIVERDRIVER.html" data-snip="SNIP_CLASSIC_DEM_SECTION_8_6_3_Configurable_interfaces_FLEXRAYTRANSCEIVERDRIVER">SWS FrTrcv p. 52</a>). <code>FrTrcv_GetTransceiverError</code> returns a <code>uint32</code> error status for a pair of <code>FrTrcv_TrcvIdx</code> and <code>FrTrcv_BranchIdx</code>. The service is not reentrant (<a class="spec-record-ref" data-req="SWS_FrTrcv_00419" href="../../spec/record.html?id=SWS_FrTrcv_00419">[SWS_FrTrcv_00419]</a>). All mandatory errors of the FlexRay EPL supported by the hardware are accessible via it. In case of an invalid index or missing status, it returns <code>E_NOT_OK</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_8_FrTrcv_GetTransceiverError.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_8_FrTrcv_GetTransceiverError">SWS FrTrcv p. 48</a>).</p>
<p>Faulty branches are disabled with <code>FrTrcv_DisableTransceiverBranch</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00442" href="../../spec/record.html?id=SWS_FrTrcv_00442">[SWS_FrTrcv_00442]</a>). Switching back on with <code>FrTrcv_EnableTransceiverBranch</code> occurs synchronously with the FlexRay bus schedule (<a class="spec-record-ref" data-req="SWS_FrTrcv_00443" href="../../spec/record.html?id=SWS_FrTrcv_00443">[SWS_FrTrcv_00443]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_10_FrTrcv_EnableTransceiverBranch.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_10_FrTrcv_EnableTransceiverBranch">SWS FrTrcv p. 51</a>). If an index is out of range, the branch state remains unchanged. Without prior initialization, both services report <code>FRTRCV_E_UNINIT</code> when error detection is active (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_9_FrTrcv_DisableTransceiverBranch.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_9_FrTrcv_DisableTransceiverBranch">SWS FrTrcv p. 50</a>).</p>

<h4>Configuration, hardware access, and partitions</h4>
<p>The module supports only VARIANT-PRE-COMPILE and no post-build variants. The configuration consists of exactly one container <code>FrTrcvGeneral</code> and at least one container <code>FrTrcvChannel</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_10_2_2_FrTrcv.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_10_2_2_FrTrcv">SWS FrTrcv p. 59</a>). Per channel, the choice container <code>FrTrcvAccess</code> selects between pin access via Dio (<code>FrTrcvDioAccess</code>) and access via Spi (<code>FrTrcvSpiSequence</code>) (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-634d18cdc12dfabe.html" data-snip="FIG-634d18cdc12dfabe">SWS FrTrcv p. 59</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-3d07e06aacfb4684.html" data-snip="FIG-3d07e06aacfb4684">SWS FrTrcv p. 77</a>). These citations originate from R23-11 and later releases. Interpretation: The structure is likely essentially the same for R20-11.</p>
<p>The global parameters include:</p>
<ul>
<li><code>FrTrcvMainFunctionCycleTime</code></li>
<li><code>FrTrcvDevErrorDetect</code></li>
<li><code>FrTrcvGetVersionInfo</code></li>
<li><code>FrTrcvSleepSupported</code></li>

</ul>
<p>This list originates from <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-2da5c4ca912c9e8f.html" data-snip="FIG-2da5c4ca912c9e8f">ECUC-Parameter p. 250</a>. <p>In partitioned systems, the module operates as an independent instance in each partition; an API call affects only the calling partition (<a class="spec-record-ref" data-req="SWS_FrTrcv_00494" href="../../spec/record.html?id=SWS_FrTrcv_00494">[SWS_FrTrcv_00494]</a>). <h4>Behavior in the event of an error</h4>
<p>Development errors are specified in <a class="spec-record-ref" data-req="SWS_FrTrcv_00085" href="../../spec/record.html?id=SWS_FrTrcv_00085">[SWS_FrTrcv_00085]</a>:</p>
<ul>
<li><code>FRTRCV_E_FR_INVALID_TRCVIDX</code> (0x01): Transceiver index out of range.</li>
<li><code>FRTRCV_E_FR_INVALID_BRANCHIDX</code> (0x02): Branch index out of range.</li>
<li><code>FRTRCV_E_UNINIT</code> (0x10): Service called without initialization.</li>
<li><code>FRTRCV_E_PARAM_POINTER</code> (0x15): NULL pointer as parameter.</li>
</ul>
<p>For example, a NULL pointer at <code>FrTrcv_GetVersionInfo</code> leads to <code>FRTRCV_E_PARAM_POINTER</code> when error detection is active (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_5_FrTrcv_GetVersionInfo.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_5_FrTrcv_GetVersionInfo">SWS FrTrcv p. 43</a>).</p>
<p>Runtime errors describe two error patterns (<a class="spec-record-ref" data-req="SWS_FrTrcv_91001" href="../../spec/record.html?id=SWS_FrTrcv_91001">[SWS_FrTrcv_91001]</a>):</p>
<ul>
<li>Call in the wrong operating mode: <code>FRTRCV_E_FR_TRCV_NOT_STANDBY</code> (0x11) to <code>FRTRCV_E_FR_TRCV_NOT_RECEIVEONLY</code> (0x14).</li>
<li>Missing or incorrect communication with the transceiver: <code>FRTRCV_E_FR_NO_CONTROL_TRCV</code> (0x16).</li>
</ul>
<p><code>FrTrcv_GetTransceiverMode</code> reports <code>FRTRCV_E_FR_NO_CONTROL_TRCV</code> in the event of an error during transceiver access (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FRTRCV_SECTION_8_3_3_FrTrcv_GetTransceiverMode.html" data-snip="SNIP_CLASSIC_FRTRCV_SECTION_8_3_3_FrTrcv_GetTransceiverMode">SWS FrTrcv p. 41</a>). Runtime errors are reported via <code>Det_ReportRuntimeError</code>; if a callout is configured, it is called (<a class="spec-record-ref" data-req="SWS_FrTrcv_00493" href="../../spec/record.html?id=SWS_FrTrcv_00493">[SWS_FrTrcv_00493]</a>).</p>
<p>For production diagnosis, there are two DEM events per transceiver:</p>
<ul>
<li><code>FRTRCV_E_FR_BUSERROR_TRCV_&lt;TrcvIdx&gt;</code> for SPI-controlled class B transceivers. The event is considered failed as soon as one of the bits 1…9 is set (<a class="spec-record-ref" data-req="SWS_FrTrcv_00488" href="../../spec/record.html?id=SWS_FrTrcv_00488">[SWS_FrTrcv_00488]</a>).</li>
<li><code>FRTRCV_E_FR_ERRN_TRCV_&lt;TrcvIdx&gt;</code> for GPIO-controlled class A transceivers. The event is considered failed when the ERRN pin is active low (<a class="spec-record-ref" data-req="SWS_FrTrcv_00489" href="../../spec/record.html?id=SWS_FrTrcv_00489">[SWS_FrTrcv_00489]</a>).</li>
</ul>
<p>An unexpected HALT of the communication controller serves as the criterion for "error", NORMAL_ACTIVE as the criterion for "passed". In case of a short circuit on the bus, the driver's passed information alone is not sufficient (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DEM_SECTION_7_4_5_2_FRTRCV_E_FR_BUSERROR_TRCV__TrcvIdx.html" data-snip="SNIP_CLASSIC_DEM_SECTION_7_4_5_2_FRTRCV_E_FR_BUSERROR_TRCV__TrcvIdx">SWS FrTrcv p. 25</a>). Later releases write the event name without angle brackets; normative for R20-11 is the name from the requirement (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DEM_SECTION_7_4_4_2_FRTRCV_E_FR_BUSERROR_TRCV__TrcvIdx.html" data-snip="SNIP_CLASSIC_DEM_SECTION_7_4_4_2_FRTRCV_E_FR_BUSERROR_TRCV__TrcvIdx">SWS FrTrcv p. 27</a>).</p>
<p>The following applies consistently to the return values: <code>E_NOT_OK</code> leaves output parameters unchanged (<a class="spec-record-ref" data-req="SWS_FrTrcv_00324" href="../../spec/record.html?id=SWS_FrTrcv_00324">[SWS_FrTrcv_00324]</a>, <a class="spec-record-ref" data-req="SWS_FrTrcv_00325" href="../../spec/record.html?id=SWS_FrTrcv_00325">[SWS_FrTrcv_00325]</a>, <a class="spec-record-ref" data-req="SWS_FrTrcv_00419" href="../../spec/record.html?id=SWS_FrTrcv_00419">[SWS_FrTrcv_00419]</a>). The transceiver mode also remains unchanged with <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_FrTrcv_00323" href="../../spec/record.html?id=SWS_FrTrcv_00323">[SWS_FrTrcv_00323]</a>).</p>
