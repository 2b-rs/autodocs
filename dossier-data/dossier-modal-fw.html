<p class="ai-level ai-oneliner-lead" data-ai-level="1">Schaltet zustandsabhängige Firewall-Regelsätze der Plattform um und meldet blockierte Pakete als Security Events.</p>
<div class="ai-level" data-ai-level="2">
<p>Der Functional Cluster Firewall filtert Netzwerkpakete nach zustandsabhängigen Regelsätzen aus dem Manifest und meldet blockierte Pakete als Security Events an den IdsM (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>). Applikationen wählen den aktiven Firewall-Zustand über <code>FirewallStateSwitchInterface::SwitchFirewallState</code>. Die Methode liefert ein <code>ara::core::Future&lt;void&gt;</code> und meldet Fehler wie <code>kServiceNotAvailable</code> oder <code>kInvalidStateDependentFirewall</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. Die Zustände sind keine feste Liste, sondern werden je modelliertem Interface als Enumeration generiert. Instanzen der Schnittstelle lassen sich nur verschieben, nicht kopieren.</p>

</div>
<div class="ai-level" data-ai-level="3">
<p>Das Modul <code>fw</code> spezifiziert den daemon-basierten Functional Cluster Firewall der Adaptive Platform. Seine Anwendungs-API ist die Schnittstelle <code>FirewallStateSwitchInterface</code> mit der Operation <code>SwitchFirewallState()</code>, die eine Adaptive Application nutzt (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-4516a6bf4c192609.html" data-snip="FIG-4516a6bf4c192609">EXP_SWArchitecture S. 126</a>). Der Cluster hat zwei Aufgaben: Er schaltet den Firewall-Zustand um und meldet Security Events an den Intrusion Detection System Manager (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-de3679298f5ff97e.html" data-snip="FIG-de3679298f5ff97e">EXP_SWArchitecture S. 197</a>).</p>

<p class="diagram-note">Kontextdiagramm: Der FC Firewall verbindet Manifest-Konfiguration, Zustandsvorgabe der Applikation, Regelanwendung im Betriebssystem und SEv-Meldung an den IdsM. Quellen: <a class="docref internal-spec-ref" href="../../spec/figures/FIG-bb047d688191b634.html" data-snip="FIG-bb047d688191b634">EXP_PlatformDesign S. 97</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-de3679298f5ff97e.html" data-snip="FIG-de3679298f5ff97e">EXP_SWArchitecture S. 197</a></p>
<p>Die Filterung ist zustandsabhängig. Der OEM definiert Zustände wie Fahren, Parken oder Diagnose, und für ein Paket gelten nur die Regeln des aktiven Zustands (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>). Im Manifest bündelt <code>AdaptiveFirewallModuleInstantiation</code> dafür <code>StateDependentFirewall</code>-Elemente. Jedes davon enthält geordnete Regeleigenschaften, eine optionale <code>defaultAction</code> und Verweise auf die zugehörigen Zustände (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd43ae4af5fde911.html" data-snip="FIG-bd43ae4af5fde911">TPS_ManifestSpecification S. 679</a>). Im Code erscheinen die Zustände als je Interface generierte Enumeration in <code>ara::fw::states</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a>.</p>
<p>Die Applikation erzeugt das Schnittstellenobjekt aus einem <code>ara::core::InstanceSpecifier</code>. Dieser Konstruktor ist thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>. <code>SwitchFirewallState</code> ist <code>noexcept</code> und liefert ein <code>ara::core::Future&lt;void&gt;</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. Intern wendet der Cluster laut Szenario jede Firewall-Regel einzeln im Betriebssystem an (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP_SWArchitecture S. 232</a>). Instanzen lassen sich nicht kopieren, wohl aber verschieben. Move und Destruktor sind nicht thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_82004" href="../spec/record.html?id=AP_SWS_Fw_82004">[AP_SWS_Fw_82004]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82006" href="../spec/record.html?id=AP_SWS_Fw_82006">[AP_SWS_Fw_82006]</a>.</p>

<h4>Rolle des FC Firewall zwischen Applikation, Betriebssystem und IdsM</h4>
<p>Das Modul <code>fw</code> beschreibt den Functional Cluster Firewall der Adaptive Platform. Er ist daemon-basiert und realisiert die Schnittstelle <code>FirewallStateSwitchInterface</code> mit der Operation <code>SwitchFirewallState()</code>. Eine Adaptive Application nutzt diese Schnittstelle über eine «use»-Beziehung (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-4516a6bf4c192609.html" data-snip="FIG-4516a6bf4c192609">EXP_SWArchitecture S. 126</a>). Die Use Cases beschränken den Cluster auf zwei Aufgaben. „Switch Firewall State“ wird von der Adaptive Application ausgelöst, das Betriebssystem wirkt mit. „Report Security Event“ richtet sich an den ebenfalls daemon-basierten Intrusion Detection System Manager (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-de3679298f5ff97e.html" data-snip="FIG-de3679298f5ff97e">EXP_SWArchitecture S. 197</a>).</p>
<p>Die Architekturübersicht trennt Konfiguration, Steuerung und Ausführung voneinander:</p>
<ul>
<li>Das Machine Manifest liefert die Filterregeln.</li>
<li>Der FC Firewall konfiguriert damit eine Firewall Engine.</li>
<li>Eine OEM-Applikation setzt den Firewall-Zustand.</li>
<li>Der Cluster meldet Security Events (SEvs) an den IdsM (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bb047d688191b634.html" data-snip="FIG-bb047d688191b634">EXP_PlatformDesign S. 97</a>).</li>
</ul>
<p>Im Vordergrund stehen zwei Anwendungsfälle. Der erste ist die zustandsabhängige Filterung mit OEM-spezifischen Zuständen wie Fahren, Parken oder Diagnosesitzung. Der zweite ist die Unterstützung des Intrusion Detection System durch Security Events bei blockierten Nachrichten. Qualifizierung, Weitergabe an ein SOC oder persistente Ablage übernimmt der IdsM (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>). Die einzige Anwendungs-API des Moduls ist der Zustandswechsel <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>

<h4>Firewall-Zustände: vom Zustandsautomaten im Modell zur generierten Enumeration</h4>
<p>Im Manifest-Metamodell spezialisiert <code>FirewallStateSwitchInterface</code> ein <code>PortInterface</code>. Über die Rolle <code>firewallStateMachine</code> aggregiert es beliebig viele (0..*) <code>ModeDeclarationGroupPrototype</code>-Elemente (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-b3757549d69ff2c3.html" data-snip="FIG-b3757549d69ff2c3">TPS_ManifestSpecification S. 263</a>). Die einzelnen Zustände sind <code>ModeDeclaration</code>s mit dem optionalen Attribut <code>value: PositiveInteger</code> (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd43ae4af5fde911.html" data-snip="FIG-bd43ae4af5fde911">TPS_ManifestSpecification S. 679</a>).</p>
<p>Für jedes modellierte Interface wird daraus eine eigene Enumeration <code>enum class {&lt;fwssi-sn&gt;} : std::uint32_t</code> im Namensraum <code>ara::fw::states</code> generiert. Sie wird über <code>ara/fw/states/{&lt;fwssi-sn&gt;}.h</code> eingebunden <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a>. Je modelliertem Firewall-Zustand entsteht ein Enumerator <code>{&lt;symbol-fw-state&gt;} = {&lt;fw-state-value&gt;}</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a>.</p>
<p>Für Anwender heißt das: Es gibt keine plattformweit feste Zustandsliste. Welche Zustände existieren, legt das OEM-Modell fest (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>). <code>SwitchFirewallState</code> erwartet einen Parameter <code>firewallState</code> vom Typ <code>EnumT</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. Interpretation: <code>EnumT</code> dürfte der zum jeweiligen Interface generierten Zustands-Enumeration entsprechen. <a class="interp-q interp-q-open" data-q="Q-26dbe38f70cb0222" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-26dbe38f70cb0222" title="Frage Q-26dbe38f70cb0222 (offen): EnumT ist die zum Interface generierte Zustands-Enumeration">Frage Q-26dbe38f70cb0222 (offen)</a> Dafür spricht, dass <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a> sie ausdrücklich als Zustände „for FirewallStateSwitchInterface“ definiert.</p>

<h4>Manifest-Konfiguration: Modulinstanz, zustandsabhängige Regelsätze und Port-Zuordnung</h4>
<p>Die maschinenspezifischen Einstellungen des Firewall-Moduls werden in <code>AdaptiveFirewallModuleInstantiation</code> gesammelt. Die zugehörige Festlegung trägt in R25-11 den Status DRAFT (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58.html" data-snip="SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58">TPS_ManifestSpecification S. 677</a>). Die Modulinstanz spezialisiert <code>NonOsModuleInstantiation</code> und referenziert über <code>stateDepFirewall</code> beliebig viele <code>StateDependentFirewall</code>-Elemente.</p>
<p>Eine <code>StateDependentFirewall</code> enthält:</p>
<ul>
<li>optional eine <code>defaultAction</code> vom Typ <code>FirewallActionEnum</code>,</li>
<li>geordnete <code>firewallRuleProps</code>,</li>
<li>über <code>firewallState</code> (<code>instanceRef</code>) Verweise auf die <code>ModeDeclaration</code>s, in denen sie gilt (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd43ae4af5fde911.html" data-snip="FIG-bd43ae4af5fde911">TPS_ManifestSpecification S. 679</a>).</li>
</ul>
<p>Das System Template beschreibt sie knapp als „Firewall rules that are defined in a firewall state“ (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_PLATFORM_FIGURE_Figure_6_66.html" data-snip="SNIP_CLASSIC_PLATFORM_FIGURE_Figure_6_66">TPS_SystemTemplate S. 644</a>).</p>
<p>Die Regeln selbst sind <code>FirewallRule</code>-Elemente mit Attributen wie <code>bucketSize</code> und <code>refillAmount</code>. Daneben führt das Metamodell <code>NetworkLayerRule</code> und <code>TransportLayerRule</code>, Letztere unter anderem mit Portbereichen und <code>checksumVerification</code>. Auch ein <code>CouplingElement</code> kann über <code>firewallRule</code> Regeln aggregieren (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd43ae4af5fde911.html" data-snip="FIG-bd43ae4af5fde911">TPS_ManifestSpecification S. 679</a>). Für Details verweist das System Template ausdrücklich auf die Manifest-Spezifikation (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_PLATFORM_FIGURE_Figure_6_66.html" data-snip="SNIP_CLASSIC_PLATFORM_FIGURE_Figure_6_66">TPS_SystemTemplate S. 644</a>).</p>
<p>Die Verbindung zur Applikation stellt <code>AdaptiveFirewallToPortPrototypeMapping</code> her. Es bildet die Modulinstanz (Referenz <code>firewall</code>, 0..1) auf den <code>RPortPrototype</code> der Applikation ab, der durch das Zustandsschalt-Interface typisiert ist (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS_ManifestSpecification S. 677</a>). Zwei Einschränkungen gelten:</p>
<ul>
<li>Die Klassennotiz nennt das Interface <code>FirewallModeSwitchInterface</code>, Bildtitel und API dagegen <code>FirewallStateSwitchInterface</code>. Für den Code maßgeblich ist der Name aus <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>.</li>
<li>Die Mapping-Klasse und ihre Referenz tragen den Status <code>candidate</code> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58.html" data-snip="SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58">TPS_ManifestSpecification S. 677</a>).</li>
</ul>

<h4>Ablauf eines Zustandswechsels mit SwitchFirewallState</h4>
<p>Auf Code-Seite bindet die Applikation <code>ara/fw/firewall_state.h</code> ein. Sie erzeugt <code>ara::fw::FirewallStateSwitchInterface</code> über den expliziten Konstruktor aus einem <code>ara::core::InstanceSpecifier</code>. Dieser Konstruktor ist <code>noexcept</code> und thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>.</p>
<p>Den Zustandswechsel fordert <code>SwitchFirewallState(EnumT firewallState)</code> an. Die Methode ist <code>noexcept</code> und liefert ein <code>ara::core::Future&lt;void&gt;</code>. Die für sie festgelegten Fehler <code>FwErrc::kServiceNotAvailable</code> und <code>FwErrc::kInvalidStateDependentFirewall</code> kommen deshalb über das Future zurück und nicht als Ausnahme <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>Das Szenario „Switch Firewall State“ zeigt den internen Ablauf in drei Schritten (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP_SWArchitecture S. 232</a>):</p>
<ol>
<li>Die Applikation ruft <code>SwitchFirewallState()</code> am FC Firewall auf.</li>
<li>Der Cluster ruft in einer Schleife „foreach FirewallRule“ jeweils <code>applyRule()</code> am Betriebssystem auf.</li>
<li>Erst nach der Schleife kehrt die Antwort zur Applikation zurück.</li>
</ol>
<p><code>applyRule()</code> ist dort als «aapInformative» gekennzeichnet. Wie die Regeln im Betriebssystem aktiviert werden, ist im Payload nicht als Plattform-API festgelegt. Die R22-11-Fassung zeigte denselben Ablauf als erfolgreiches Szenario (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-826e9bb7c1d7761d.html" data-snip="FIG-826e9bb7c1d7761d">EXP_SWArchitecture S. 158</a>). Nach dem Wechsel prüfen und filtern nur noch die Regeln des aktiven Zustands (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>).</p>

<h4>Lebensdauer, Kopier- und Move-Regeln der Schnittstellenklasse</h4>
<p>Die Sonderfunktionen von <code>FirewallStateSwitchInterface</code> legen fest, wie Instanzen weitergegeben werden dürfen (<a class="spec-record-ref" data-req="AP_SWS_Fw_82003" href="../spec/record.html?id=AP_SWS_Fw_82003">[AP_SWS_Fw_82003]</a> bis <a class="spec-record-ref" data-req="AP_SWS_Fw_82007" href="../spec/record.html?id=AP_SWS_Fw_82007">[AP_SWS_Fw_82007]</a>):</p>
<table>
<thead><tr><th>Element</th><th>Festlegung</th><th>Thread-Sicherheit</th></tr></thead>
<tbody>
<tr><td>Konstruktor aus <code>InstanceSpecifier</code></td><td><code>explicit</code>, <code>noexcept</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a></td><td>thread-safe</td></tr>
<tr><td>Copy-Konstruktor / Copy-Zuweisung</td><td><code>=delete</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82004" href="../spec/record.html?id=AP_SWS_Fw_82004">[AP_SWS_Fw_82004]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82005" href="../spec/record.html?id=AP_SWS_Fw_82005">[AP_SWS_Fw_82005]</a></td><td>–</td></tr>
<tr><td>Move-Konstruktor / Move-Zuweisung</td><td><code>noexcept</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82006" href="../spec/record.html?id=AP_SWS_Fw_82006">[AP_SWS_Fw_82006]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82007" href="../spec/record.html?id=AP_SWS_Fw_82007">[AP_SWS_Fw_82007]</a></td><td>not thread-safe</td></tr>
<tr><td>Destruktor</td><td><code>noexcept</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82003" href="../spec/record.html?id=AP_SWS_Fw_82003">[AP_SWS_Fw_82003]</a></td><td>not thread-safe</td></tr>
</tbody>
</table>
<p>Daraus folgen drei Regeln für die Nutzung:</p>
<ul>
<li>Eine Instanz kann nicht dupliziert werden, sondern nur per Move weitergegeben werden <a class="spec-record-ref" data-req="AP_SWS_Fw_82004" href="../spec/record.html?id=AP_SWS_Fw_82004">[AP_SWS_Fw_82004]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82006" href="../spec/record.html?id=AP_SWS_Fw_82006">[AP_SWS_Fw_82006]</a>.</li>
<li>Move und Zerstörung muss die Applikation selbst gegen nebenläufige Zugriffe absichern <a class="spec-record-ref" data-req="AP_SWS_Fw_82003" href="../spec/record.html?id=AP_SWS_Fw_82003">[AP_SWS_Fw_82003]</a>.</li>
<li>Interpretation: Ein Quellobjekt nach einem Move sollte vermutlich nicht mehr für <code>SwitchFirewallState</code> verwendet werden, weil die Requirements nur die Übertragung, nicht aber den Restzustand beschreiben <a class="spec-record-ref" data-req="AP_SWS_Fw_82007" href="../spec/record.html?id=AP_SWS_Fw_82007">[AP_SWS_Fw_82007]</a>. <a class="interp-q interp-q-open" data-q="Q-ccf0737ee5133103" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-ccf0737ee5133103" title="Frage Q-ccf0737ee5133103 (offen): Ein Quellobjekt nach einem Move ist nicht weiter zu verwenden; das Zielobjekt übernimmt die Rolle">Frage Q-ccf0737ee5133103 (offen)</a></li>
</ul>
<p>Zur Thread-Sicherheit von <code>SwitchFirewallState</code> selbst macht der Requirement-Text keine Angabe <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>

<h4>Paketfilterung im aktiven Zustand und Meldung von Security Events</h4>
<p>Firewall-Regeln lassen sich einem Firewall-Zustand zuordnen. Zur Prüfung eines Pakets werden nur die Regeln des gerade aktiven Zustands herangezogen (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>). Pro Zustand stellt die <code>StateDependentFirewall</code> die geordneten Regeleigenschaften und die optionale <code>defaultAction</code> bereit (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd43ae4af5fde911.html" data-snip="FIG-bd43ae4af5fde911">TPS_ManifestSpecification S. 679</a>).</p>
<p>Die SWS-Fassung R23-11 beschreibt die Zuordnung von Security Events genauer (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3.html" data-snip="SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3">SWS_Firewall S. 31</a>):</p>
<ul>
<li>Passt ein Paket auf keine Regel, greift die Default-Aktion.</li>
<li>Blockiert die Default-Aktion das Paket, bestimmt der Cluster das abweichende Protokoll. Maßgeblich ist die Regel mit den meisten passenden ISO/OSI-Schichten, gezählt ab der untersten Schicht. Die erste nicht passende Schicht darüber legt das Protokoll fest.</li>
<li>Für dieses Protokoll wird ein SEv an den IdsM gemeldet, etwa <code>SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH</code> (Ethernet), <code>SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH</code>, <code>SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH</code> oder <code>SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH</code>.</li>
</ul>
<p>Diese Einzelheiten stammen aus R23-11. Die zugehörigen Requirements gehören nicht zum R25-11-Payload und sind hier deshalb erläuternd, nicht normativ wiedergegeben. Der Grundsatz, dass blockierte Nachrichten als SEvs an den IdsM gehen, gilt laut Architekturbeschreibung auch für R25-11 (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP_PlatformDesign S. 92</a>).</p>

<h4>Verhalten im Fehlerfall</h4>
<p>Die Fehlercodes des Moduls definiert <code>FwErrc</code> im Header <code>ara/fw/fw_error_domain.h</code>: <code>kServiceNotAvailable=1</code> und <code>kInvalidStateDependentFirewall=2</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83001" href="../spec/record.html?id=AP_SWS_Fw_83001">[AP_SWS_Fw_83001]</a>. Beide sind für <code>SwitchFirewallState</code> als mögliche Fehler festgelegt <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. Interpretation der Namen, da die Requirements keine Auslösebedingungen nennen:</p>
<ul>
<li><code>kServiceNotAvailable</code> dürfte melden, dass der daemon-basierte FC Firewall den Dienst nicht erbringen kann. <a class="interp-q interp-q-unmatched" data-q-status="unmatched" href="../versions.html?tab=q&amp;qsub=module:adaptive:fw&amp;qst=open" title="Annahmen und Fragen zu diesem Text (Versions- &amp; Provenienz-Explorer)">Frage (offen)</a></li>
<li><code>kInvalidStateDependentFirewall</code> dürfte melden, dass für den angeforderten Zustand keine gültige <code>StateDependentFirewall</code> vorliegt. <a class="interp-q interp-q-unmatched" data-q-status="unmatched" href="../versions.html?tab=q&amp;qsub=module:adaptive:fw&amp;qst=open" title="Annahmen und Fragen zu diesem Text (Versions- &amp; Provenienz-Explorer)">Frage (offen)</a></li>
</ul>
<p>Die Fehlerdomäne folgt dem üblichen <code>ara::core</code>-Muster:</p>
<ul>
<li><code>GetFwErrorDomain()</code> liefert die Domäne thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_83002" href="../spec/record.html?id=AP_SWS_Fw_83002">[AP_SWS_Fw_83002]</a>. Der Standardkonstruktor von <code>FwErrorDomain</code> ist gelöscht <a class="spec-record-ref" data-req="AP_SWS_Fw_83009" href="../spec/record.html?id=AP_SWS_Fw_83009">[AP_SWS_Fw_83009]</a>.</li>
<li><code>MakeErrorCode</code> erzeugt einen <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83003" href="../spec/record.html?id=AP_SWS_Fw_83003">[AP_SWS_Fw_83003]</a>.</li>
<li><code>Name()</code> und <code>Message()</code> liefern Domänenname und Fehlertext <a class="spec-record-ref" data-req="AP_SWS_Fw_83010" href="../spec/record.html?id=AP_SWS_Fw_83010">[AP_SWS_Fw_83010]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83011" href="../spec/record.html?id=AP_SWS_Fw_83011">[AP_SWS_Fw_83011]</a>.</li>
<li>Die Aliase <code>Errc</code> und <code>Exception</code> verweisen auf <code>FwErrc</code> und <code>FwException</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83007" href="../spec/record.html?id=AP_SWS_Fw_83007">[AP_SWS_Fw_83007]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83008" href="../spec/record.html?id=AP_SWS_Fw_83008">[AP_SWS_Fw_83008]</a>.</li>
