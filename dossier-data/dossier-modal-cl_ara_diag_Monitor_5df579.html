<h4>Context</h4>
<p>The class <code>ara::diag::Monitor</code> forms the primary interface for adaptive applications to implement diagnostic monitors in accordance with <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=69">AUTOSAR AP SWS Diagnostics p. 69</a>. Its main responsibility is to report the operational status of fault detection paths to the Diagnostic Management (DM) and to ensure synchronization between the application-internal monitoring logic and the higher-level diagnostic routines.</p>
<p>Essentially three parties are involved in the interaction:</p>
<ul>
<li><strong>Application (monitoring function):</strong> Executes application-specific sensor or system checks, determines fault states, and reports them via <code>ReportMonitorAction()</code> <a class="spec-record-ref" data-req="SWS_DM_00543" href="../spec/record.html?id=SWS_DM_00543">[SWS_DM_00543]</a>. In addition, it implements the optional initialization callback <code>initMonitor</code>.</li>
<li><strong>ara::diag::Monitor:</strong> Serves as a standardized service endpoint of the Adaptive Platform and encapsulates the connection to the modeled diagnostic port (<code>DiagnosticMonitorInterface</code>) <a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a>.</li>
<li><strong>Diagnostic Management (DM):</strong> Processes the reported states, controls event status bits, and, if required, forwards re-initialization requests via the DM to the application <a class="spec-record-ref" data-req="SWS_DM_01088" href="../spec/record.html?id=SWS_DM_01088">[SWS_DM_01088]</a>, <a class="spec-record-ref" data-req="SWS_DM_01089" href="../spec/record.html?id=SWS_DM_01089">[SWS_DM_01089]</a>.</li>
</ul>
<p>Depending on the diagnostic model, <code>ara::diag::Monitor</code> supports different debouncing strategies that are already firmly specified during instantiation:</p>
<ul>
<li><strong>Monitor-internal:</strong> Debouncing takes place entirely in the application; a callback for determining the Fault Detection Counter (FDC) is registered <a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a>.</li>
<li><strong>Counter-based:</strong> Uses preconfigured counter values (<code>CounterBased</code>) of the platform <a class="spec-record-ref" data-req="SWS_DM_00549" href="../spec/record.html?id=SWS_DM_00549">[SWS_DM_00549]</a>.</li>
<li><strong>Time-based:</strong> Uses time-controlled threshold values (<code>TimeBased</code>) <a class="spec-record-ref" data-req="SWS_DM_00550" href="../spec/record.html?id=SWS_DM_00550">[SWS_DM_00550]</a>.</li>
<li><strong>Without debouncing:</strong> Direct forwarding of unqualified test results to the DM <a class="spec-record-ref" data-req="SWS_DM_01972" href="../spec/record.html?id=SWS_DM_01972">[SWS_DM_01972]</a>.</li>
</ul>

<h4>Lifecycle</h4>
<p>Instances of <code>ara::diag::Monitor</code> are designed as indivisible units. The class is neither copyable nor movable; both the copy and move constructors as well as the corresponding assignment operators are explicitly deleted (<code>=delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01683" href="../spec/record.html?id=SWS_DM_01683">[SWS_DM_01683]</a>, <a class="spec-record-ref" data-req="SWS_DM_01684" href="../spec/record.html?id=SWS_DM_01684">[SWS_DM_01684]</a>, <a class="spec-record-ref" data-req="SWS_DM_01685" href="../spec/record.html?id=SWS_DM_01685">[SWS_DM_01685]</a>, <a class="spec-record-ref" data-req="SWS_DM_01686" href="../spec/record.html?id=SWS_DM_01686">[SWS_DM_01686]</a>. An instance therefore remains fixed at its memory address.</p>
<p>The lifecycle is divided into the following states:</p>
<ol>
<li><strong>Uninitialized:</strong> No object exists before the constructor is called.</li>
<li><strong>Instantiated:</strong> The application creates the monitor object via one of the four exception-safe constructors <a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a>, <a class="spec-record-ref" data-req="SWS_DM_00549" href="../spec/record.html?id=SWS_DM_00549">[SWS_DM_00549]</a>, <a class="spec-record-ref" data-req="SWS_DM_00550" href="../spec/record.html?id=SWS_DM_00550">[SWS_DM_00550]</a>, <a class="spec-record-ref" data-req="SWS_DM_01972" href="../spec/record.html?id=SWS_DM_01972">[SWS_DM_01972]</a> by specifying the <code>InstanceSpecifier</code>. At this point in time, no messages are accepted from the DM yet.</li>
<li><strong>Offered:</strong> By explicitly calling <code>Offer()</code>, the application declares its readiness to accept initialization calls (<code>initMonitor</code>) <a class="spec-record-ref" data-req="SWS_DM_01088" href="../spec/record.html?id=SWS_DM_01088">[SWS_DM_01088]</a>. Only in this state is the communication path to the DM fully active.</li>
<li><strong>Stopped:</strong> By means of <code>StopOffer()</code>, the application deactivates the forwarding of requests by the DM <a class="spec-record-ref" data-req="SWS_DM_01089" href="../spec/record.html?id=SWS_DM_01089">[SWS_DM_01089]</a>. After stopping, re-activation via <code>Offer()</code> is likely possible in order to resume forwarding if needed.</li>
</ol>
<p>With regard to concurrency, all member functions of <code>ara::diag::Monitor</code> are specified as not thread-safe (<code>not thread-safe</code>) <a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a>, <a class="spec-record-ref" data-req="SWS_DM_00543" href="../spec/record.html?id=SWS_DM_00543">[SWS_DM_00543]</a>, <a class="spec-record-ref" data-req="SWS_DM_01088" href="../spec/record.html?id=SWS_DM_01088">[SWS_DM_01088]</a>, <a class="spec-record-ref" data-req="SWS_DM_01089" href="../spec/record.html?id=SWS_DM_01089">[SWS_DM_01089]</a>. If multiple application threads access the same instance, an external synchronization mechanism is mandatory.</p>

<h4>Usage Path</h4>
<p>The typical use of <code>ara::diag::Monitor</code> follows a fixed sequence of initialization, readiness signaling, cyclic status reporting, and controlled deactivation:</p>
<ol>
<li><strong>Construction:</strong> The application selects the constructor that matches the DEXT modeling of the associated port (e.g., monitor-internal with FDC function <a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a> or counter-based <a class="spec-record-ref" data-req="SWS_DM_00549" href="../spec/record.html?id=SWS_DM_00549">[SWS_DM_00549]</a>) and passes the <code>initMonitor</code> callback function.</li>
<li><strong>Activate service:</strong> Prior to the first diagnostic processing, the application calls <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_01088" href="../spec/record.html?id=SWS_DM_01088">[SWS_DM_01088]</a>. The returned <code>ara::core::Result&lt;void&gt;</code> confirms error-free activation.</li>
<li><strong>Process re-initialization:</strong> In the event of changes to the system or monitor status, the DM can execute the registered callback <code>initMonitor</code> to reset the internal monitoring logic <a class="spec-record-ref" data-req="SWS_DM_01088" href="../spec/record.html?id=SWS_DM_01088">[SWS_DM_01088]</a>.</li>
<li><strong>Report actions and results:</strong> During normal monitoring operation, the application repeatedly calls <code>ReportMonitorAction()</code> <a class="spec-record-ref" data-req="SWS_DM_00543" href="../spec/record.html?id=SWS_DM_00543">[SWS_DM_00543]</a>. Here, test results (passed/failed) or control commands for debouncing are reported.</li>
<li><strong>Terminate service:</strong> When shutting down the component, <code>StopOffer()</code> is called <a class="spec-record-ref" data-req="SWS_DM_01089" href="../spec/record.html?id=SWS_DM_01089">[SWS_DM_01089]</a> before the object is finally destroyed.</li>
</ol>
