<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht der Applikation die Bereitstellung von Steuergerätedaten für UDS-Uploads an das Diagnostic Management.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>ara::diag::UploadService</code> dient als anwendungsseitige Serviceschnittstelle zur Bereitstellung von Steuergerätedaten für externe Diagnose-Uploads gemäß UDS <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Nach erfolgreicher Aktivierung über <code>Offer()</code> bearbeitet der Handler asynchron die aufeinanderfolgenden Anfragen zur Upload-Initiierung, Datenblockübertragung und Transferbeendigung <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>. Die nicht kopierbare Dienstinstanz unterstützt dabei sowohl blockweise Datenübergaben als auch den vorzeitigen Abbruch über einen Stornierungshandler. Fehlerhafte Anfragen quittiert der Handler über negative UDS-Rückgabecodes innerhalb der asynchronen Antwort-Futures.</p>

<h4>Kontext</h4>
<p>Die Klasse <code>ara::diag::UploadService</code> definiert die zentrale Dienstschnittstelle für Diagnose-Upload-Operationen innerhalb der AUTOSAR Adaptive Platform <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Sie fungiert als anwendungsseitiger Handler zur Auslesung und Bereitstellung fahrzeuginterner Daten an externe Prüfgeräte gemäß dem Diagnosestandard UDS (ISO 14229-1) <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>.</p>
<p>In der Systemarchitektur interagiert <code>ara::diag::UploadService</code> im Wesentlichen mit zwei Partnern: dem externen Diagnose-Client (Tester) und dem plattformseitigen Diagnose-Dämon <em>Diagnostic Management</em> (DM) <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>, <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>. Das DM nimmt eingehende UDS-Dienstanforderungen wie <em>RequestUpload</em>, <em>TransferData</em> und <em>RequestTransferExit</em> auf Protokollebene entgegen, validiert diese und leitet die fachlichen Abfragen an den registrierten Handler der Applikation weiter <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>, <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>, <a class="spec-record-ref" data-req="SWS_DM_00801" href="../spec/record.html?id=SWS_DM_00801">[SWS_DM_00801]</a>. Die Applikationsinstanz implementiert die virtuellen Methoden der Schnittstelle, um die eigentlichen Datenblöcke aus dem Speicher zu lesen und zurückzugeben <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>.</p>

<h4>Lebenszyklus</h4>
<p>Eine Instanz von <code>ara::diag::UploadService</code> wird unter Angabe eines <code>ara::core::InstanceSpecifier</code> sowie des Nebenläufigkeitsverhaltens <code>concurrencyType</code> konstruiert <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Der Spezifizierer verknüpft die Instanz mit einem modellierten Port-Prototyp des Typs <code>DiagnosticUploadInterface</code> <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Der Konstruktor ist ausnahmesicher und threadsicher spezifiziert <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Um eine eindeutige Zuordnung der Dienstinstanz zu garantieren, sind Kopier- und Verschiebekonstruktoren sowie Zuweisungsoperatoren explizit gelöscht <a class="spec-record-ref" data-req="SWS_DM_01671" href="../spec/record.html?id=SWS_DM_01671">[SWS_DM_01671]</a>, <a class="spec-record-ref" data-req="SWS_DM_01672" href="../spec/record.html?id=SWS_DM_01672">[SWS_DM_01672]</a>, <a class="spec-record-ref" data-req="SWS_DM_01673" href="../spec/record.html?id=SWS_DM_01673">[SWS_DM_01673]</a>, <a class="spec-record-ref" data-req="SWS_DM_01674" href="../spec/record.html?id=SWS_DM_01674">[SWS_DM_01674]</a>.</p>
<p>Nach der Instanziierung befindet sich der Dienst zunächst im inaktiven Zustand; das DM leitet noch keine Anfragen weiter. Erst durch den expliziten Aufruf von <code>Offer()</code> wird die Weiterleitung aktiviert <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>. Über <code>StopOffer()</code> kann das Weiterleiten von Anforderungen jederzeit wieder unterbunden werden <a class="spec-record-ref" data-req="SWS_DM_00803" href="../spec/record.html?id=SWS_DM_00803">[SWS_DM_00803]</a>. Sowohl <code>Offer()</code> als auch <code>StopOffer()</code> sind als nicht threadsicher definiert und bedürfen einer externen Synchronisation bei Aufrufen aus mehreren Threads <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>, <a class="spec-record-ref" data-req="SWS_DM_00803" href="../spec/record.html?id=SWS_DM_00803">[SWS_DM_00803]</a>.</p>
<p>Die Zerstörung erfolgt über den virtuellen Destruktor <code>~UploadService()</code>, welcher ebenfalls nicht threadsicher ist <a class="spec-record-ref" data-req="SWS_DM_00798" href="../spec/record.html?id=SWS_DM_00798">[SWS_DM_00798]</a>. Vor Freigabe des Objekts sollte der Dienst daher ordnungsgemäß via <code>StopOffer()</code> deregistriert werden <a class="spec-record-ref" data-req="SWS_DM_00803" href="../spec/record.html?id=SWS_DM_00803">[SWS_DM_00803]</a>. Ob die virtuellen Bearbeitungsmethoden intern threadsicher ausgeführt werden müssen, bestimmt der bei der Konstruktion konfigurierte <code>ConcurrencyType</code> (<code>kConcurrent</code> oder <code>kNotConcurrent</code>) <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>, <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>.</p>

<h4>Nutzungspfad</h4>
<p>Der reguläre Ablauf einer Upload-Sitzung vollzieht sich in mehreren aufeinanderfolgenden Schritten:</p>
<ol>
<li><strong>Dienstbereitstellung:</strong> Die Applikation initialisiert den Handler und ruft <code>Offer()</code> auf, um eingehende Diagnoseanfragen vom DM entgegenzunehmen <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>.</li>
<li><strong>Upload anfordern (RequestUpload):</strong> Trifft eine UDS-Anfrage zur Upload-Initiierung ein, ruft das DM die Methode <code>RequestUpload()</code> auf <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>. Der Handler prüft Datenformat, Adressierungsformat sowie Speicheradresse und -länge (<code>memoryAddressAndSize</code>). Der übergebene Speicherbereich bleibt gültig, bis das zurückgegebene <code>ara::core::Future&lt;void&gt;</code> erfüllt ist oder der Vorgang abgebrochen wird <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>.</li>
<li><strong>Datenblöcke übertragen (UploadData):</strong> Nach erfolgreicher Initiierung sendet der Tester UDS-<em>TransferData</em>-Anfragen. Das DM ruft daraufhin wiederholt <code>UploadData()</code> auf <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>. Die Applikation liest den angeforderten Datenblock und liefert ihn über ein <code>ara::core::Future&lt;OperationOutput&gt;</code> zurück; die Bytes in <code>OperationOutput.responseData</code> werden in der positiven Antwort hinter dem Blockzähler platziert <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>. Interpretation: Die Pufferbegrenzung <code>numBytesToReturn</code> dürfte hierbei als maximale Chunk-Größe für die interne Pufferung des DM fungieren, sodass umfangreichere Speicherbereiche sequenziell über aufeinanderfolgende Aufrufe segmentiert werden.</li>
<li><strong>Transfer beenden (RequestUploadExit):</strong> Zum Abschluss ruft das DM <code>RequestUploadExit()</code> auf und übergibt die herstellerspezifischen Transfer-Parameter im <code>transferRequestParameterRecord</code> <a class="spec-record-ref" data-req="SWS_DM_00801" href="../spec/record.html?id=SWS_DM_00801">[SWS_DM_00801]</a>. Der Handler validiert den Abschluss und liefert optionale Rückgabeparameter im <code>OperationOutput</code> zurück <a class="spec-record-ref" data-req="SWS_DM_00801" href="../spec/record.html?id=SWS_DM_00801">[SWS_DM_00801]</a>.</li>
<li><strong>Dienst deaktivieren:</strong> Nach Abschluss aller Upload-Transaktionen oder beim Herunterfahren beendet die Applikation die Weiterleitung mit <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_00803" href="../spec/record.html?id=SWS_DM_00803">[SWS_DM_00803]</a>.</li>
</ol>
<p>Während der gesamten Datenübertragung erhält der Handler ein <code>CancellationHandler</code>-Objekt. Über dieses kann mittels <code>IsCanceled()</code> aktiv der Stornierungsstatus abgefragt oder über <code>SetNotifier()</code> ein Callback registriert werden, falls der Tester den Dialog vorzeitig abbricht <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>, <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>, <a class="spec-record-ref" data-req="SWS_DM_00801" href="../spec/record.html?id=SWS_DM_00801">[SWS_DM_00801]</a>.</p>

<h4>Fehlerszenarien</h4>
<p>Fehlerzustände können bei der Konstruktion, während der Aktivierung sowie bei der eigentlichen Datenabwicklung auftreten:</p>
<ul>
<li><strong>Modell- und Konfigurationsverletzungen:</strong> Stimmt die Konfiguration nicht mit dem ARXML-Modell überein, treten beim Konstruktoraufruf Verletzungen auf <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>. Hierzu zählen <code>InstanceSpecifierMappingIntegrityViolation</code> (Spezifizierer verweist nicht auf einen <code>PortPrototype</code>), <code>PortInterfaceMappingViolation</code> (fehlende Verknüpfung via <code>DiagnosticServiceGenericMapping</code>), <code>ProcessMappingViolation</code> (keine Übereinstimmung mit dem modellierten Prozess) sowie <code>InstanceSpecifierAlreadyInUseViolation</code> (mehrfache Nutzung desselben Spezifizierers innerhalb eines Prozesses) <a class="spec-record-ref" data-req="SWS_DM_00797" href="../spec/record.html?id=SWS_DM_00797">[SWS_DM_00797]</a>.</li>
<li><strong>Mehrfache Dienstaktivierung:</strong> Wird <code>Offer()</code> aufgerufen, während der Dienst bereits angeboten wird, schlägt der Aufruf fehl und liefert im <code>ara::core::Result&lt;void&gt;</code> den Fehlercode <code>DiagOfferErrc::kAlreadyOffered</code> zurück <a class="spec-record-ref" data-req="SWS_DM_00802" href="../spec/record.html?id=SWS_DM_00802">[SWS_DM_00802]</a>.</li>
<li><strong>UDS-Fehlerantworten (Negative Response):</strong> Kann der Handler eine Anforderung in <code>RequestUpload()</code>, <code>UploadData()</code> oder <code>RequestUploadExit()</code> fachlich nicht bedienen (z. B. unzulässige Speicheradressen, Formatfehler oder ungültige Sequenzzähler), signalisiert er dies durch Bereitstellung eines Fehlercodes aus <code>DiagUdsNrcErrc</code> im zurückgegebenen <code>Future</code> <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>, <a class="spec-record-ref" data-req="SWS_DM_00800" href="../spec/record.html?id=SWS_DM_00800">[SWS_DM_00800]</a>, <a class="spec-record-ref" data-req="SWS_DM_00801" href="../spec/record.html?id=SWS_DM_00801">[SWS_DM_00801]</a>. Das DM generiert daraufhin eine standardkonforme negative UDS-Antwort (NRC) an das externe Prüfgerät <a class="spec-record-ref" data-req="SWS_DM_00799" href="../spec/record.html?id=SWS_DM_00799">[SWS_DM_00799]</a>.</li>
</ul>
