<h4>Context</h4>
<p>The class <code>ara::tsync::SynchronizedTimeBaseConsumer</code> forms the central interface for applications on the Adaptive Platform to access a synchronized time base addressed via an instance specifier (<code>ara::core::InstanceSpecifier</code>). The consumer enables reading the current point in time, clock rate deviation, current state, and received user data.</p>
<p>In the system architecture, the class mediates between the utilizing application software and the Tsync subsystem:</p>
<ul>
<li><strong>Application software:</strong> Uses the instance either for cyclic state and time queries or reacts asynchronously to configured time base events.</li>
<li><strong>SynchronizedTimeBaseConsumer:</strong> Manages the system-specific binding to the port and encapsulates the query and notifier logic.</li>
<li><strong>Tsync subsystem / time base:</strong> Provides the synchronized timestamps, status information, and validation data blocks.</li>
</ul>

<h4>Lifecycle</h4>
<p>An instance of <code>SynchronizedTimeBaseConsumer</code> is created via the explicit constructor <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a> specifying an <code>ara::core::InstanceSpecifier</code>. This constructor is specified as exception-safe (<code>exception safe</code>) and thread-safe (<code>thread-safe</code>).</p>
<p>With regard to object ownership, the class enforces strict move semantics:</p>
<ul>
<li>The copy constructor <a class="spec-record-ref" data-req="SWS_TS_01005" href="../spec/record.html?id=SWS_TS_01005">[SWS_TS_01005]</a> and the copy assignment operator <a class="spec-record-ref" data-req="SWS_TS_01006" href="../spec/record.html?id=SWS_TS_01006">[SWS_TS_01006]</a> are deleted (<code>=delete</code>), preventing duplication of consumer instances.</li>
<li>Move operations via the move constructor <a class="spec-record-ref" data-req="SWS_TS_01003" href="../spec/record.html?id=SWS_TS_01003">[SWS_TS_01003]</a> and the move assignment operator <a class="spec-record-ref" data-req="SWS_TS_01004" href="../spec/record.html?id=SWS_TS_01004">[SWS_TS_01004]</a> are supported. Both operations are <code>noexcept</code>, but classified as not thread-safe (<code>non_threadsafe</code>).</li>
</ul>
<p>Destruction is performed via the destructor <a class="spec-record-ref" data-req="SWS_TS_01002" href="../spec/record.html?id=SWS_TS_01002">[SWS_TS_01002]</a>, which is also <code>noexcept</code>, but <code>non_threadsafe</code>. Interpretation: To avoid concurrency conflicts during destruction or reallocation, registered callback functions will probably have to be explicitly unregistered via the respective unregister functions before the end of the instance's lifetime.</p>
<p>Regarding concurrency during operation, note that pure read accesses to the time base (<a class="spec-record-ref" data-req="SWS_TS_01008" href="../spec/record.html?id=SWS_TS_01008">[SWS_TS_01008]</a>, <a class="spec-record-ref" data-req="SWS_TS_01009" href="../spec/record.html?id=SWS_TS_01009">[SWS_TS_01009]</a>) are thread-safe, whereas all registration and deregistration calls for notifiers (e.g. <a class="spec-record-ref" data-req="SWS_TS_01010" href="../spec/record.html?id=SWS_TS_01010">[SWS_TS_01010]</a>, <a class="spec-record-ref" data-req="SWS_TS_01011" href="../spec/record.html?id=SWS_TS_01011">[SWS_TS_01011]</a>) are classified as <code>non_threadsafe</code> and require external synchronization.</p>

<h4>Usage Path</h4>
<p>The typical sequence for using a synchronized time base is divided into initialization, event configuration, operational queries, and cleanup:</p>
<ol>
<li><strong>Instantiation:</strong> Creating the object with the appropriate <code>InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a>.</li>
<li><strong>Event registration:</strong> The application registers callback functions as needed for relevant state changes:
<ul>
<li><code>RegisterStatusChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01010" href="../spec/record.html?id=SWS_TS_01010">[SWS_TS_01010]</a> for general changes to the status flags (synchronization status, time leaps, or user data).</li>
<li><code>RegisterSynchronizationStateChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01012" href="../spec/record.html?id=SWS_TS_01012">[SWS_TS_01012]</a> for pure changes of the synchronization state.</li>
<li><code>RegisterTimeLeapNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01014" href="../spec/record.html?id=SWS_TS_01014">[SWS_TS_01014]</a> for separate handling of occurred time leaps.</li>
<li><code>RegisterTimePrecisionMeasurementNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01018" href="../spec/record.html?id=SWS_TS_01018">[SWS_TS_01018]</a> upon availability of new time precision snapshots.</li>
<li><code>RegisterTimeValidationNotification</code> <a class="spec-record-ref" data-req="SWS_TS_01016" href="../spec/record.html?id=SWS_TS_01016">[SWS_TS_01016]</a> for receiving validation data blocks of the time base.</li>
</ul>
</li>
<li><strong>Operational time and status query:</strong> The application obtains a snapshot of the clock state via <code>GetTimeWithStatus</code> <a class="spec-record-ref" data-req="SWS_TS_01009" href="../spec/record.html?id=SWS_TS_01009">[SWS_TS_01009]</a>, which contains status flags, clock configuration, and local and synchronized time values. The current rate deviation of the clock can be queried via <code>GetRateDeviation</code> <a class="spec-record-ref" data-req="SWS_TS_01008" href="../spec/record.html?id=SWS_TS_01008">[SWS_TS_01008]</a>.</li>
<li><strong>Deregistration:</strong> Notifications that are no longer required are removed via the corresponding counterparts: <code>UnregisterStatusChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01011" href="../spec/record.html?id=SWS_TS_01011">[SWS_TS_01011]</a>, <code>UnregisterSynchronizationStateChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01013" href="../spec/record.html?id=SWS_TS_01013">[SWS_TS_01013]</a>, <code>UnregisterTimeLeapNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01015" href="../spec/record.html?id=SWS_TS_01015">[SWS_TS_01015]</a>, <code>UnregisterTimeValidationNotification</code> <a class="spec-record-ref" data-req="SWS_TS_01017" href="../spec/record.html?id=SWS_TS_01017">[SWS_TS_01017]</a>, and <code>UnregisterTimePrecisionMeasurementNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01019" href="../spec/record.html?id=SWS_TS_01019">[SWS_TS_01019]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>All member functions of <code>SynchronizedTimeBaseConsumer</code> are defined as <code>noexcept</code> and <code>exception safe</code>. Error conditions arise primarily from incorrect modeling or invalid call contexts:</p>
<ul>
<li><strong>Port interface misconfiguration:</strong> If an <code>PortPrototype</code> referenced by an <code>TimeSyncPortPrototypeToTimeBaseMapping</code> is not typed by the interface type <code>SynchronizedTimeBaseConsumerInterface</code>, an <code>PortInterfaceMappingViolation</code> is present during instantiation <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a>.</li>
<li><strong>Overwriting existing notifiers:</strong> For each event category, a maximum of one notifier can be registered at a time. Each renewed call to a registration function (<a class="spec-record-ref" data-req="SWS_TS_01010" href="../spec/record.html?id=SWS_TS_01010">[SWS_TS_01010]</a>, <a class="spec-record-ref" data-req="SWS_TS_01012" href="../spec/record.html?id=SWS_TS_01012">[SWS_TS_01012]</a>, <a class="spec-record-ref" data-req="SWS_TS_01014" href="../spec/record.html?id=SWS_TS_01014">[SWS_TS_01014]</a>, <a class="spec-record-ref" data-req="SWS_TS_01016" href="../spec/record.html?id=SWS_TS_01016">[SWS_TS_01016]</a>, <a class="spec-record-ref" data-req="SWS_TS_01018" href="../spec/record.html?id=SWS_TS_01018">[SWS_TS_01018]</a>) overwrites the existing registration without warning.</li>
<li><strong>Loss of measurement values due to lack of a queue:</strong> According to <a class="spec-record-ref" data-req="SWS_TS_01018" href="../spec/record.html?id=SWS_TS_01018">[SWS_TS_01018]</a>, Tsync does not perform any queue management (queuing) for time precision measurements. If the application cannot process consecutive snapshots immediately, they must be buffered within the notifier itself, as incoming new data would otherwise likely be discarded.</li>
<li><strong>Violation of thread safety:</strong> Because notifier registration and deregistration are declared as <code>non_threadsafe</code>, concurrent invocation of these methods leads to data inconsistencies in callback management.</li>
</ul>
