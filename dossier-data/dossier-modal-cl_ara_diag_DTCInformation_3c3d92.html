<h4>Context</h4>
<p>In AUTOSAR Adaptive (module <code>diag</code>), the class <code>ara::diag::DTCInformation</code> provides functional interfaces to perform operations and status queries on DTC (Diagnostic Trouble Code) information related to a configured diagnostic memory target (<code>DiagnosticMemoryDestination</code>) <a class="spec-record-ref" data-req="SWS_DM_00664" href="../spec/record.html?id=SWS_DM_00664">[SWS_DM_00664]</a>. It serves as a link between the application-specific diagnostic and monitoring logic and the underlying Diagnostic Management (DM).</p>
<p>The primary interaction partners include the Adaptive Application, the internal memory management of the DM, and external diagnostic testers. The latter interact with the ECU in a standardized manner via UDS services such as Service 0x19 (ReadDTCInformation) or Service 0x85 (ControlDTCSetting), with the DM defining specific restrictions regarding supported subfunctions and memory areas <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=63">AUTOSAR AP SWS Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”</a>. The application uses <code>ara::diag::DTCInformation</code> to query DTC states, receive notifications upon status changes, inspect control states, and, if necessary, delete fault memory entries in a targeted manner <a class="spec-record-ref" data-req="SWS_DM_00666" href="../spec/record.html?id=SWS_DM_00666">[SWS_DM_00666]</a> <a class="spec-record-ref" data-req="SWS_DM_00671" href="../spec/record.html?id=SWS_DM_00671">[SWS_DM_00671]</a> <a class="spec-record-ref" data-req="SWS_DM_00672" href="../spec/record.html?id=SWS_DM_00672">[SWS_DM_00672]</a>.</p>

<h4>Lifecycle</h4>
<p>The instantiation of <code>ara::diag::DTCInformation</code> takes place explicitly via passing a <code>ara::core::InstanceSpecifier</code>, which must reference a modeled <code>PortPrototype</code> of a <code>DiagnosticDTCInformationInterface</code> <a class="spec-record-ref" data-req="SWS_DM_00664" href="../spec/record.html?id=SWS_DM_00664">[SWS_DM_00664]</a>. The constructor is specified as <code>thread-safe</code> and exception-safe (<code>noexcept</code>) <a class="spec-record-ref" data-req="SWS_DM_00664" href="../spec/record.html?id=SWS_DM_00664">[SWS_DM_00664]</a>.</p>
<p>With regard to ownership, the class is designed as a strict single object: both the copy constructor and the move constructor, as well as the corresponding assignment operators, are deleted (<code>=delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01611" href="../spec/record.html?id=SWS_DM_01611">[SWS_DM_01611]</a> <a class="spec-record-ref" data-req="SWS_DM_01612" href="../spec/record.html?id=SWS_DM_01612">[SWS_DM_01612]</a> <a class="spec-record-ref" data-req="SWS_DM_01613" href="../spec/record.html?id=SWS_DM_01613">[SWS_DM_01613]</a> <a class="spec-record-ref" data-req="SWS_DM_01614" href="../spec/record.html?id=SWS_DM_01614">[SWS_DM_01614]</a>. An instance can therefore neither be copied nor moved, but remains at its original creation location throughout its entire lifetime.</p>
<p>Destruction is performed via the destructor <code>~DTCInformation()</code> <a class="spec-record-ref" data-req="SWS_DM_00665" href="../spec/record.html?id=SWS_DM_00665">[SWS_DM_00665]</a>. The destructor is classified as <code>not thread-safe</code>, which is why it must be ensured that no concurrent accesses to the same instance take place during teardown. The concurrency model distinguishes clearly between reading and modifying methods: Pure query methods such as <code>GetCurrentStatus</code> <a class="spec-record-ref" data-req="SWS_DM_00666" href="../spec/record.html?id=SWS_DM_00666">[SWS_DM_00666]</a>, <code>GetControlDTCStatus</code> <a class="spec-record-ref" data-req="SWS_DM_00672" href="../spec/record.html?id=SWS_DM_00672">[SWS_DM_00672]</a>, <code>GetNumberOfStoredEntries</code> <a class="spec-record-ref" data-req="SWS_DM_00669" href="../spec/record.html?id=SWS_DM_00669">[SWS_DM_00669]</a>, and <code>GetEventMemoryOverflow</code> <a class="spec-record-ref" data-req="SWS_DM_00919" href="../spec/record.html?id=SWS_DM_00919">[SWS_DM_00919]</a> are <code>thread-safe</code>. Modifying actions such as <code>Clear</code> <a class="spec-record-ref" data-req="SWS_DM_00671" href="../spec/record.html?id=SWS_DM_00671">[SWS_DM_00671]</a> and <code>EnableControlDtc</code> <a class="spec-record-ref" data-req="SWS_DM_00674" href="../spec/record.html?id=SWS_DM_00674">[SWS_DM_00674]</a>, as well as all registrations of notifier callbacks, are <code>not thread-safe</code> and require external synchronization in the case of shared access.</p>

<h4>Usage Path</h4>
<p>A typical usage path comprises the creation of the instance, the configuration of event-driven callback functions, periodic or event-driven querying of status values, as well as the execution of control or cleanup actions:</p>
<ol>
<li><strong>Initialization:</strong> The application instantiates <code>ara::diag::DTCInformation</code> by specifying the matching <code>InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_DM_00664" href="../spec/record.html?id=SWS_DM_00664">[SWS_DM_00664]</a>.</li>
<li><strong>Registration of notifiers:</strong> For reactive handling of diagnostic events, the application registers callback functions, such as via <code>SetDTCStatusChangedNotifier</code> with the type <code>DtcStatusChangedNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00667" href="../spec/record.html?id=SWS_DM_00667">[SWS_DM_00667]</a> <a class="spec-record-ref" data-req="SWS_DM_02122" href="../spec/record.html?id=SWS_DM_02122">[SWS_DM_02122]</a>, <code>SetNumberOfStoredEntriesNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00670" href="../spec/record.html?id=SWS_DM_00670">[SWS_DM_00670]</a> <a class="spec-record-ref" data-req="SWS_DM_02124" href="../spec/record.html?id=SWS_DM_02124">[SWS_DM_02124]</a>, <code>SetEventMemoryOverflowNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00918" href="../spec/record.html?id=SWS_DM_00918">[SWS_DM_00918]</a> <a class="spec-record-ref" data-req="SWS_DM_02076" href="../spec/record.html?id=SWS_DM_02076">[SWS_DM_02076]</a>, <code>SetControlDtcStatusNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00673" href="../spec/record.html?id=SWS_DM_00673">[SWS_DM_00673]</a> <a class="spec-record-ref" data-req="SWS_DM_02125" href="../spec/record.html?id=SWS_DM_02125">[SWS_DM_02125]</a>, or <code>SetSnapshotRecordUpdatedNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_00668" href="../spec/record.html?id=SWS_DM_00668">[SWS_DM_00668]</a> <a class="spec-record-ref" data-req="SWS_DM_02123" href="../spec/record.html?id=SWS_DM_02123">[SWS_DM_02123]</a>. A renewed call overwrites the previously registered callback.</li>
<li><strong>Status query:</strong> The application asynchronously queries the current UDS DTC status of a specific DTC via <code>GetCurrentStatus</code>, which returns a <code>ara::core::Future&lt;UdsDtcStatusByteType&gt;</code> <a class="spec-record-ref" data-req="SWS_DM_00666" href="../spec/record.html?id=SWS_DM_00666">[SWS_DM_00666]</a>. In addition, the number of stored entries (<a class="spec-record-ref" data-req="SWS_DM_00669" href="../spec/record.html?id=SWS_DM_00669">[SWS_DM_00669]</a>), the overflow status (<a class="spec-record-ref" data-req="SWS_DM_00919" href="../spec/record.html?id=SWS_DM_00919">[SWS_DM_00919]</a>), and the control status regarding UDS Service 0x85 (<a class="spec-record-ref" data-req="SWS_DM_00672" href="../spec/record.html?id=SWS_DM_00672">[SWS_DM_00672]</a>) can be queried.</li>
<li><strong>Control and cleanup:</strong> If application-side conditions require it, status control can be set to enabled via <code>EnableControlDtc</code> <a class="spec-record-ref" data-req="SWS_DM_00674" href="../spec/record.html?id=SWS_DM_00674">[SWS_DM_00674]</a>. To clear individual DTCs or a DTC group, the application calls <code>Clear</code> and receives a <code>ara::core::Future&lt;void&gt;</code> to monitor the process <a class="spec-record-ref" data-req="SWS_DM_00671" href="../spec/record.html?id=SWS_DM_00671">[SWS_DM_00671]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>Error conditions are divided into static configuration and instantiation violations as well as dynamic runtime errors via <code>ara::diag::DiagErrc</code>:</p>
<p>During creation of the instance via the constructor, the following violations can occur <a class="spec-record-ref" data-req="SWS_DM_00664" href="../spec/record.html?id=SWS_DM_00664">[SWS_DM_00664]</a>:</p>
<ul>
<li><code>InstanceSpecifierMappingIntegrityViolation</code>: The <code>InstanceSpecifier</code> cannot be resolved in the execution model or does not reference a <code>PortPrototype</code>.</li>
<li><code>PortInterfaceMappingViolation</code>: The referenced <code>PortPrototype</code> is not typed by a <code>DiagnosticDTCInformationInterface</code>.</li>
<li><code>ProcessMappingViolation</code>: No matching modeled process exists at runtime for the reference.</li>
<li><code>InstanceSpecifierAlreadyInUseViolation</code>: The <code>InstanceSpecifier</code> is already used by an existing instance within this process.</li>
</ul>
<p>During ongoing operation, asynchronous methods (via <code>ara::core::Future</code>) and synchronous calls (via <code>ara::core::Result</code>) return specific error codes:</p>
<ul>
<li><code>DiagErrc::kServiceNotAvailable</code>: The basic functionality of Diagnostic Management is temporarily or permanently unavailable.
