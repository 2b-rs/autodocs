<h4>Context</h4>
<p>The template class <code>ara::core::PolymorphicAllocator</code> provides an allocator interface for polymorphic memory resources in the AUTOSAR Adaptive module <code>core</code>. It implements the concept of <code>std::pmr::polymorphic_allocator</code> in accordance with ISO/IEC 14882 (<code>[mem.poly.allocator.class]</code>). The underlying element type is determined via the template specialization <code>value_type</code> <a class="spec-record-ref" data-req="SWS_CORE_06572" href="../spec/record.html?id=SWS_CORE_06572">[SWS_CORE_06572]</a>, defaulting to <code>ara::core::Byte</code>.</p>
<p>In the system architecture, <code>ara::core::PolymorphicAllocator</code> acts as a link between dynamically storing containers or application logic and concrete memory management strategies. For this purpose, the allocator encapsulates a pointer to an abstract <code>MemoryResource</code>, which can be queried via the method <code>resource()</code> <a class="spec-record-ref" data-req="SWS_CORE_06557" href="../spec/record.html?id=SWS_CORE_06557">[SWS_CORE_06557]</a>. This allows containers to obtain memory without being bound to a fixed implementation.</p>

<h4>Lifecycle</h4>
<p>The instantiation of <code>ara::core::PolymorphicAllocator</code> is performed either without parameters via the default constructor <a class="spec-record-ref" data-req="SWS_CORE_06541" href="../spec/record.html?id=SWS_CORE_06541">[SWS_CORE_06541]</a> or explicitly by passing a pointer to a <code>MemoryResource</code> <a class="spec-record-ref" data-req="SWS_CORE_06542" href="../spec/record.html?id=SWS_CORE_06542">[SWS_CORE_06542]</a>. Interpretation: With the parameterless default constructor <a class="spec-record-ref" data-req="SWS_CORE_06541" href="../spec/record.html?id=SWS_CORE_06541">[SWS_CORE_06541]</a>, the allocator presumably falls back on a default-defined runtime memory resource. Both constructors are specified as <code>noexcept</code> and thread-safe.</p>
<p>Regarding ownership, the allocator does not assume ownership of the passed <code>MemoryResource</code>; the validity of the memory resource must therefore be ensured externally throughout the entire lifetime of the allocator and the memory blocks allocated by it.</p>
<p>The following mechanisms are available for copy and conversion operations:</p>
<ul>
<li>Standardized copy constructor <a class="spec-record-ref" data-req="SWS_CORE_06543" href="../spec/record.html?id=SWS_CORE_06543">[SWS_CORE_06543]</a> as well as cross-type conversion constructor for differing element types <code>U</code> <a class="spec-record-ref" data-req="SWS_CORE_06544" href="../spec/record.html?id=SWS_CORE_06544">[SWS_CORE_06544]</a>.</li>
<li>Creation of allocator copies during container copy operations via <code>select_on_container_copy_construction()</code> <a class="spec-record-ref" data-req="SWS_CORE_06573" href="../spec/record.html?id=SWS_CORE_06573">[SWS_CORE_06573]</a>.</li>
<li>The copy assignment operator is explicitly deleted (<code>=delete</code>) <a class="spec-record-ref" data-req="SWS_CORE_06545" href="../spec/record.html?id=SWS_CORE_06545">[SWS_CORE_06545]</a>, so that allocator instances cannot subsequently be reassigned by copying.</li>
</ul>
<p>Deviating from the ISO standard ISO-14882, AUTOSAR explicitly defines move operations: a move constructor <a class="spec-record-ref" data-req="SWS_CORE_06546" href="../spec/record.html?id=SWS_CORE_06546">[SWS_CORE_06546]</a> and a move assignment operator <a class="spec-record-ref" data-req="SWS_CORE_00066" href="../spec/record.html?id=SWS_CORE_00066">[SWS_CORE_00066]</a>. While construction, conversion, and resource query are thread-safe, move operations as well as container copy selection are considered not thread-safe.</p>

<h4>Usage Path</h4>
<p>The typical workflow when working with <code>ara::core::PolymorphicAllocator</code> comprises two stages: the reservation of memory and the subsequent construction of objects in the reserved area (as well as their reverse cleanup).</p>
<ol>
<li><strong>Memory allocation:</strong> Callers reserve typed raw memory via <code>allocate(n)</code> <a class="spec-record-ref" data-req="SWS_CORE_06547" href="../spec/record.html?id=SWS_CORE_06547">[SWS_CORE_06547]</a>, byte-wise memory via <code>allocate_bytes()</code> <a class="spec-record-ref" data-req="SWS_CORE_06549" href="../spec/record.html?id=SWS_CORE_06549">[SWS_CORE_06549]</a>, or object-specific memory via <code>allocate_object()</code> <a class="spec-record-ref" data-req="SWS_CORE_06551" href="../spec/record.html?id=SWS_CORE_06551">[SWS_CORE_06551]</a>.</li>
<li><strong>Object construction:</strong> In-place construction is performed on the provided pointer using <code>construct(p, args...)</code> <a class="spec-record-ref" data-req="SWS_CORE_06555" href="../spec/record.html?id=SWS_CORE_06555">[SWS_CORE_06555]</a>. Alternatively, the helper method <code>new_object(ctor_args...)</code> combines allocation and construction into a single call <a class="spec-record-ref" data-req="SWS_CORE_06553" href="../spec/record.html?id=SWS_CORE_06553">[SWS_CORE_06553]</a>.</li>
<li><strong>Object destruction:</strong> After use has ended, the object is explicitly destroyed via <code>destroy(p)</code> <a class="spec-record-ref" data-req="SWS_CORE_06556" href="../spec/record.html?id=SWS_CORE_06556">[SWS_CORE_06556]</a>.</li>
<li><strong>Memory deallocation:</strong> Finally, the raw memory is returned to the memory resource via <code>deallocate(p, n)</code> <a class="spec-record-ref" data-req="SWS_CORE_06548" href="../spec/record.html?id=SWS_CORE_06548">[SWS_CORE_06548]</a>, <code>deallocate_bytes()</code> <a class="spec-record-ref" data-req="SWS_CORE_06550" href="../spec/record.html?id=SWS_CORE_06550">[SWS_CORE_06550]</a>, or <code>deallocate_object()</code> <a class="spec-record-ref" data-req="SWS_CORE_06552" href="../spec/record.html?id=SWS_CORE_06552">[SWS_CORE_06552]</a>. When using <code>delete_object(p)</code> <a class="spec-record-ref" data-req="SWS_CORE_06554" href="../spec/record.html?id=SWS_CORE_06554">[SWS_CORE_06554]</a>, destruction and deallocation are performed in combination.</li>
</ol>

<h4>Error Scenarios</h4>
<p>In the AUTOSAR Adaptive environment, the error handling of <code>ara::core::PolymorphicAllocator</code> deviates significantly from standard C++, as deterministic behavior without exceptions is required:</p>
<ul>
<li><strong>Allocation errors without exceptions:</strong> The allocation functions <code>allocate</code> <a class="spec-record-ref" data-req="SWS_CORE_06547" href="../spec/record.html?id=SWS_CORE_06547">[SWS_CORE_06547]</a>, <code>allocate_bytes</code> <a class="spec-record-ref" data-req="SWS_CORE_06549" href="../spec/record.html?id=SWS_CORE_06549">[SWS_CORE_06549]</a>, <code>allocate_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06551" href="../spec/record.html?id=SWS_CORE_06551">[SWS_CORE_06551]</a>, and <code>new_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06553" href="../spec/record.html?id=SWS_CORE_06553">[SWS_CORE_06553]</a> do not throw C++ exceptions. If not enough memory can be allocated, they mandatorily return <code>nullptr</code> instead. Callers must mandatorily validate return values before dereferencing or passing them to <code>construct</code>.</li>
<li><strong>Silent ignoring of deallocation errors:</strong> If a memory deallocation fails, the error is silently ignored (<em>silently ignored</em>) according to the specification for <code>deallocate</code> <a class="spec-record-ref" data-req="SWS_CORE_06548" href="../spec/record.html?id=SWS_CORE_06548">[SWS_CORE_06548]</a>, <code>deallocate_bytes</code> <a class="spec-record-ref" data-req="SWS_CORE_06550" href="../spec/record.html?id=SWS_CORE_06550">[SWS_CORE_06550]</a>, <code>deallocate_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06552" href="../spec/record.html?id=SWS_CORE_06552">[SWS_CORE_06552]</a>, and <code>delete_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06554" href="../spec/record.html?id=SWS_CORE_06554">[SWS_CORE_06554]</a>.</li>
<li><strong>Conditional exception safety:</strong> The operations <code>construct</code> <a class="spec-record-ref" data-req="SWS_CORE_06555" href="../spec/record.html?id=SWS_CORE_06555">[SWS_CORE_06555]</a>, <code>destroy</code> <a class="spec-record-ref" data-req="SWS_CORE_06556" href="../spec/record.html?id=SWS_CORE_06556">[SWS_CORE_06556]</a>, <code>new_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06553" href="../spec/record.html?id=SWS_CORE_06553">[SWS_CORE_06553]</a>, and <code>delete_object</code> <a class="spec-record-ref" data-req="SWS_CORE_06554" href="../spec/record.html?id=SWS_CORE_06554">[SWS_CORE_06554]</a> are conditionally <code>noexcept</code>. Their exception safety depends directly on whether the constructors or destructors of the managed payload types are declared as exception-free (checked via <code>std::is_nothrow_constructible</code> or <code>std::is_nothrow_destructible</code>).</li>
</ul>
