<h4>Role and system boundary: Ea between NvM/MemIf and the EEPROM driver</h4>
<p>The Ea (EEPROM Abstraction) module offers block-oriented services on an EEPROM to the NV memory stack. It reads, writes, invalidates, and erases logical blocks (<a class="spec-record-ref" data-req="SWS_Ea_00086" href="../../spec/record.html?id=SWS_Ea_00086">[SWS_Ea_00086]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00087" href="../../spec/record.html?id=SWS_Ea_00087">[SWS_Ea_00087]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00091" href="../../spec/record.html?id=SWS_Ea_00091">[SWS_Ea_00091]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00093" href="../../spec/record.html?id=SWS_Ea_00093">[SWS_Ea_00093]</a>). Downwards, Ea in R20-11 relies on the EEPROM driver Eep. Expected interfaces include <code>Eep_Read</code>, <code>Eep_Write</code>, <code>Eep_Erase</code>, <code>Eep_Cancel</code>, <code>Eep_GetStatus</code>, <code>Eep_GetJobResult</code>, and <code>Eep_SetMode</code> (<a class="spec-record-ref" data-req="SWS_Ea_00097" href="../../spec/record.html?id=SWS_Ea_00097">[SWS_Ea_00097]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_6_Expected_interfaces.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_6_Expected_interfaces">SWS Ea p. 37</a>). The imported types <code>Eep_AddressType</code> and <code>Eep_LengthType</code> originate from <code>Eep.h</code>, and the types <code>MemIf_StatusType</code>, <code>MemIf_JobResultType</code>, and <code>MemIf_ModeType</code> from <code>MemIf.h</code> (<a class="spec-record-ref" data-req="SWS_Ea_00083" href="../../spec/record.html?id=SWS_Ea_00083">[SWS_Ea_00083]</a>).</p>
<p>Ea is called by several modules:</p>
<ul>
<li>EcuM initializes the module (<a class="spec-record-ref" data-req="SWS_Ea_00084" href="../../spec/record.html?id=SWS_Ea_00084">[SWS_Ea_00084]</a>).</li>
<li>The job services arrive via the Memory Abstraction Interface. The sequence diagrams of the specification are binding only with respect to these calling modules (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_9_Sequence_diagrams_EEPROMABSTRACTION.html" data-snip="SNIP_CLASSIC_EA_SECTION_9_Sequence_diagrams_EEPROMABSTRACTION">SWS Ea p. 45</a>).</li>
<li>Notifications, on the other hand, go directly to NvM, namely <code>NvM_JobEndNotification</code> and <code>NvM_JobErrorNotification</code> (<a class="spec-record-ref" data-req="SWS_Ea_00099" href="../../spec/record.html?id=SWS_Ea_00099">[SWS_Ea_00099]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00100" href="../../spec/record.html?id=SWS_Ea_00100">[SWS_Ea_00100]</a>). The reason: MemIf itself does not provide any callbacks (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE">SWS MemIf p. 24</a>).</li>
<li>The Basic Software Scheduler calls <code>Ea_MainFunction</code> (<a class="spec-record-ref" data-req="SWS_Ea_00096" href="../../spec/record.html?id=SWS_Ea_00096">[SWS_Ea_00096]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_5_Scheduled_functions.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_5_Scheduled_functions">SWS Ea p. 36</a>).</li>
<li><code>Det_ReportError</code> is an optional interface (<a class="spec-record-ref" data-req="SWS_Ea_00098" href="../../spec/record.html?id=SWS_Ea_00098">[SWS_Ea_00098]</a>).</li>
</ul>
<p>Release boundary: Many document citations in the payload originate from R23-11 or later. According to the change history, R21-11 removed <code>Ea_SetMode</code>, made <code>Ea_Cancel</code> asynchronous, introduced buffer alignment, and replaced Eep with MemAcc. R20-11 itself only removed <code>EA_E_INIT_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_EA_SECTION_General_Overview">SWS Ea p. 1</a>). Later document citations are used here to the extent that they do not contradict the R20-11 requirements. Where they deviate, this is stated in each case.</p>

<h4>Startup via EcuM and the four module states</h4>
<p><code>Ea_Init</code> is synchronous and non-reentrant. Parameter <code>ConfigPtr</code> points to the selected configuration set (<a class="spec-record-ref" data-req="SWS_Ea_00084" href="../../spec/record.html?id=SWS_Ea_00084">[SWS_Ea_00084]</a>). <code>Ea_ConfigType</code> is a structure with implementation-specific elements (<a class="spec-record-ref" data-req="SWS_Ea_00190" href="../../spec/record.html?id=SWS_Ea_00190">[SWS_Ea_00190]</a>). The R20-11 diagram shows the call by EcuM as a simple synchronous call with return (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-11efe208d35add32.html" data-snip="FIG-11efe208d35add32">SWS Ea p. 47</a>). An error code for failed initialization no longer exists in R20-11 (<a class="spec-record-ref" data-req="SWS_Ea_91001" href="../../spec/record.html?id=SWS_Ea_91001">[SWS_Ea_91001]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_EA_SECTION_General_Overview">SWS Ea p. 1</a>).</p>
<p>The state is provided by the synchronous <code>Ea_GetStatus</code> (<a class="spec-record-ref" data-req="SWS_Ea_00089" href="../../spec/record.html?id=SWS_Ea_00089">[SWS_Ea_00089]</a>) with four values (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_5_Ea_GetStatus.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_5_Ea_GetStatus">SWS Ea p. 28</a>):</p>
<ul>
<li><code>MEMIF_UNINIT</code>: The module is not yet initialized.</li>
<li><code>MEMIF_IDLE</code>: Neither a job nor internal management is running.</li>
<li><code>MEMIF_BUSY</code>: An upper-layer job is being processed.</li>
<li><code>MEMIF_BUSY_INTERNAL</code>: An internal management operation is running, such as a reorganization (garbage collection). During this time, the driver may be temporarily busy.</li>
</ul>

<h4>Logical Blocks and Address Calculation</h4>
<p><code>BlockNumber</code> designates a logical block and also represents its start address in the EEPROM (<a class="spec-record-ref" data-req="SWS_Ea_00086" href="../../spec/record.html?id=SWS_Ea_00086">[SWS_Ea_00086]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00087" href="../../spec/record.html?id=SWS_Ea_00087">[SWS_Ea_00087]</a>). The services calculate the address differently:</p>
<ul>
<li><code>Ea_Read</code> calculates the read address from block number and offset. Offset and length may use the full type range. This allows any number of bytes to be read from any position within the block (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_2_Ea_Read.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_2_Ea_Read">SWS Ea p. 24</a>).</li>
<li><code>Ea_Write</code> calculates with an offset of zero. As the length, it sets the length configured for the block (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write">SWS Ea p. 25</a>).</li>
<li><code>Ea_InvalidateBlock</code> and <code>Ea_EraseImmediateBlock</code> also calculate the block address, the latter with an offset of zero (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_7_Ea_InvalidateBlock.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_7_Ea_InvalidateBlock">SWS Ea p. 31</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_9_Ea_EraseImmediateBlock.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_9_Ea_EraseImmediateBlock">SWS Ea p. 34</a>).</li>
</ul>
<p>The memory layout diagram contrasts a virtual address space consisting of a 16-bit block number and a 16-bit offset with the physical address space. Physically, the blocks are densely packed in pages (8 bytes in the example). A block with 100 bytes occupies 13 pages there, leaving a remainder of 4 bytes (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-556e8594370c39dd.html" data-snip="FIG-556e8594370c39dd">SWS Ea p. 20</a>). Ea passes the physical address and length to the driver in types <code>Eep_AddressType</code> and <code>Eep_LengthType</code> (<a class="spec-record-ref" data-req="SWS_Ea_00083" href="../../spec/record.html?id=SWS_Ea_00083">[SWS_Ea_00083]</a>). Rules for buffer alignment (<code>EaBufferAlignmentValueRef</code>, <code>EaMinimumReadPageSize</code>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_7_1_6_Buffer_Alignment.html" data-snip="SNIP_CLASSIC_EA_SECTION_7_1_6_Buffer_Alignment">SWS Ea p. 19</a>) were only added with R21-11 and do not apply to R20-11 (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_EA_SECTION_General_Overview">SWS Ea p. 1</a>).</p>

<h4>Job Processing: Acceptance, Ea_MainFunction, Notification</h4>
<p><code>Ea_Read</code>, <code>Ea_Write</code>, <code>Ea_InvalidateBlock</code>, and <code>Ea_EraseImmediateBlock</code> are asynchronous and non-reentrant. <code>E_OK</code> only means that the job was accepted (<a class="spec-record-ref" data-req="SWS_Ea_00086" href="../../spec/record.html?id=SWS_Ea_00086">[SWS_Ea_00086]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00087" href="../../spec/record.html?id=SWS_Ea_00087">[SWS_Ea_00087]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00091" href="../../spec/record.html?id=SWS_Ea_00091">[SWS_Ea_00091]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00093" href="../../spec/record.html?id=SWS_Ea_00093">[SWS_Ea_00093]</a>). <code>Ea_Write</code> accepts jobs in <code>MEMIF_IDLE</code> and in <code>MEMIF_BUSY_INTERNAL</code>, copying the parameters in the process (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write">SWS Ea p. 25</a>). A read operation is executed asynchronously in the main function (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_2_Ea_Read.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_2_Ea_Read">SWS Ea p. 24</a>). <code>Ea_MainFunction</code> processes the requested jobs and internal management operations (<a class="spec-record-ref" data-req="SWS_Ea_00096" href="../../spec/record.html?id=SWS_Ea_00096">[SWS_Ea_00096]</a>). The scheduler calls it without parameters, and it is non-reentrant (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_5_Scheduled_functions.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_5_Scheduled_functions">SWS Ea p. 36</a>).</p>

<p class="diagram-note">Activity diagram: Decisions upon acceptance of a <code>Ea_Write</code> job. The order of the checks and the assumption that the busy check is performed independently of development error detection are an interpretation. Sources: <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_3_Ea_Write">SWS Ea p. 25</a>, <a class="spec-record-ref" data-req="SWS_Ea_00087" href="../../spec/record.html?id=SWS_Ea_00087">[SWS_Ea_00087]</a>, <a class="spec-record-ref" data-req="SWS_Ea_91001" href="../../spec/record.html?id=SWS_Ea_91001">[SWS_Ea_91001]</a>, <a class="spec-record-ref" data-req="SWS_Ea_91002" href="../../spec/record.html?id=SWS_Ea_91002">[SWS_Ea_91002]</a></p>
<p>Job completion occurs in two stages. First, the driver reports to Ea, via <code>Ea_JobEndNotification</code> on success or <code>Ea_JobErrorNotification</code> on error (<a class="spec-record-ref" data-req="SWS_Ea_00094" href="../../spec/record.html?id=SWS_Ea_00094">[SWS_Ea_00094]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00095" href="../../spec/record.html?id=SWS_Ea_00095">[SWS_Ea_00095]</a>). Then Ea passes the notification on to the NvM (<a class="spec-record-ref" data-req="SWS_Ea_00099" href="../../spec/record.html?id=SWS_Ea_00099">[SWS_Ea_00099]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00100" href="../../spec/record.html?id=SWS_Ea_00100">[SWS_Ea_00100]</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-534aef3fc9afba24.html" data-snip="FIG-534aef3fc9afba24">SWS Eep p. 50</a>). <code>Ea_GetJobResult</code> returns the result of the last job requested by the NvM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_6_Ea_GetJobResult.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_6_Ea_GetJobResult">SWS Ea p. 30</a>). Possible values are <code>MEMIF_JOB_OK</code>, <code>MEMIF_JOB_PENDING</code>, <code>MEMIF_JOB_CANCELED</code>, <code>MEMIF_JOB_FAILED</code>, <code>MEMIF_BLOCK_INCONSISTENT</code>, and <code>MEMIF_BLOCK_INVALID</code> (<a class="spec-record-ref" data-req="SWS_Ea_00090" href="../../spec/record.html?id=SWS_Ea_00090">[SWS_Ea_00090]</a>). Callbacks can run at interrupt level. Ea must therefore keep them short, and the system design must align the configuration accordingly (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_4_Callback_notifications_EEPROMABSTRACTION.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_4_Callback_notifications_EEPROMABSTRACTION">SWS Ea p. 35</a>).</p>

<h4>Block Consistency, Invalidation, and Immediate Data</h4>
<p>Ea maintains internal consistency information for each block. It only affects the internal handling of the block, not its content. At the start of a write operation, Ea marks the block as inconsistent, and only upon successful completion as consistent again. Ea must be able to distinguish this marking from an intentional invalidation (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_7_1_5_Managing_block_consistency_information.html" data-snip="SNIP_CLASSIC_EA_SECTION_7_1_5_Managing_block_consistency_information">SWS Ea p. 19</a>, version R24-11, without contradiction to R20-11). The two cases are reflected in the job results <code>MEMIF_BLOCK_INCONSISTENT</code> and <code>MEMIF_BLOCK_INVALID</code> (<a class="spec-record-ref" data-req="SWS_Ea_00090" href="../../spec/record.html?id=SWS_Ea_00090">[SWS_Ea_00090]</a>).</p>
<p>Separate rules apply to invalidating and erasing:</p>
<ul>
<li>Depending on the implementation, <code>Ea_InvalidateBlock</code> calls the driver's erase function or modifies internal management information. This information must be stored non-volatilely (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_7_Ea_InvalidateBlock.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_7_Ea_InvalidateBlock">SWS Ea p. 31</a>).</li>
<li><code>Ea_EraseImmediateBlock</code> is intended for diagnostic or similar system services that erase the area for immediate data in advance. The service ensures that Ea can write immediate data. Whether physical erasing is performed for this purpose is left open (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_9_Ea_EraseImmediateBlock.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_9_Ea_EraseImmediateBlock">SWS Ea p. 34</a>).</li>
<li>Both services return <code>E_NOT_OK</code> only when development error detection is enabled (<a class="spec-record-ref" data-req="SWS_Ea_00091" href="../../spec/record.html?id=SWS_Ea_00091">[SWS_Ea_00091]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00093" href="../../spec/record.html?id=SWS_Ea_00093">[SWS_Ea_00093]</a>).</li>
</ul>

<h4>Cancellation and Mode Switch in R20-11</h4>
<p>In R20-11, <code>Ea_Cancel</code> is synchronous (<a class="spec-record-ref" data-req="SWS_Ea_00088" href="../../spec/record.html?id=SWS_Ea_00088">[SWS_Ea_00088]</a>). The document passage from R23-11 refers to the service as asynchronous. This change came with R21-11 (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_EA_SECTION_General_Overview">SWS Ea p. 1</a>); for R20-11, the requirement applies. The remaining rules from the same passage (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_4_Ea_Cancel.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_4_Ea_Cancel">SWS Ea p. 27</a>):</p>
<ul>
<li>When development error detection is active and the status is <code>MEMIF_UNINIT</code>, <code>Ea_Cancel</code> reports <code>EA_E_UNINIT</code> and returns without modifying internal variables.</li>
<li>In <code>MEMIF_BUSY</code>, <code>Ea_Cancel</code> calls the driver cancellation <code>Eep_Cancel</code> (<a class="spec-record-ref" data-req="SWS_Ea_00097" href="../../spec/record.html?id=SWS_Ea_00097">[SWS_Ea_00097]</a>). Afterwards, it resets the internal variables and sets the job result to <code>MEMIF_JOB_CANCELED</code>.</li>
<li>Without a pending job, <code>EA_E_INVALID_CANCEL</code> is intended (<a class="spec-record-ref" data-req="SWS_Ea_91002" href="../../spec/record.html?id=SWS_Ea_91002">[SWS_Ea_91002]</a>).</li>
</ul>
<p>The diagram of the Eep driver shows that a new write job can follow immediately after the cancellation (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-f4809ad3efbba192.html" data-snip="FIG-f4809ad3efbba192">SWS Eep p. 51</a>).</p>

<h4>Behavior in the event of an error</h4>
<p>When detection is enabled, Ea reports development errors via <code>Det_ReportError</code> (<a class="spec-record-ref" data-req="SWS_Ea_00098" href="../../spec/record.html?id=SWS_Ea_00098">[SWS_Ea_00098]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DET_SECTION_8_6_2_Optional_Interfaces_EEPROMABSTRACTION.html" data-snip="SNIP_CLASSIC_DET_SECTION_8_6_2_Optional_Interfaces_EEPROMABSTRACTION">SWS Ea p. 38</a>). The codes are <code>EA_E_UNINIT</code> (0x01), <code>EA_E_INVALID_BLOCK_NO</code> (0x02), <code>EA_E_INVALID_BLOCK_OFS</code> (0x03), <code>EA_E_PARAM_POINTER</code> (0x04), and <code>EA_E_INVALID_BLOCK_LEN</code> (0x05) (<a class="spec-record-ref" data-req="SWS_Ea_91001" href="../../spec/record.html?id=SWS_Ea_91001">[SWS_Ea_91001]</a>). Two examples:</p>
<ul>
<li>In state <code>MEMIF_UNINIT</code>, <code>Ea_GetJobResult</code> reports error <code>EA_E_UNINIT</code> and returns <code>MEMIF_JOB_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_6_Ea_GetJobResult.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_6_Ea_GetJobResult">SWS Ea p. 30</a>).</li>
<li>The reentrant <code>Ea_GetVersionInfo</code> (<a class="spec-record-ref" data-req="SWS_Ea_00092" href="../../spec/record.html?id=SWS_Ea_00092">[SWS_Ea_00092]</a>) reports <code>EA_E_PARAM_POINTER</code> for a NULL pointer (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_8_3_8_Ea_GetVersionInfo.html" data-snip="SNIP_CLASSIC_EA_SECTION_8_3_8_Ea_GetVersionInfo">SWS Ea p. 32</a>).</li>
</ul>
<p><code>EA_E_BUSY</code> (0x06, call while busy) and <code>EA_E_INVALID_CANCEL</code> (0x08) are listed in a separate table (<a class="spec-record-ref" data-req="SWS_Ea_91002" href="../../spec/record.html?id=SWS_Ea_91002">[SWS_Ea_91002]</a>). Interpretation: They are likely reported as runtime errors via <code>Det_ReportRuntimeError</code>, because Ea mandatorily expects this interface (<a class="spec-record-ref" data-req="SWS_Ea_00097" href="../../spec/record.html?id=SWS_Ea_00097">[SWS_Ea_00097]</a>).</p>
<p>The Eep driver detects memory errors. The response in Ea is implementation-specific. Depending on the configuration, the error is forwarded in one of two ways (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_6_2_3_EEPROM_Abstraction.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_6_2_3_EEPROM_Abstraction">ErrorDescription p. 48</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_8_2_3_EEPROM_Abstraction.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_8_2_3_EEPROM_Abstraction">ErrorDescription p. 52</a>):</p>
<ul>
<li>It is queried via polling with the job result <code>MEMIF_JOB_FAILED</code>.</li>
<li>It is reported via <code>NvM_JobErrorNotification</code> (<a class="spec-record-ref" data-req="SWS_Ea_00095" href="../../spec/record.html?id=SWS_Ea_00095">[SWS_Ea_00095]</a>, <a class="spec-record-ref" data-req="SWS_Ea_00100" href="../../spec/record.html?id=SWS_Ea_00100">[SWS_Ea_00100]</a>).</li>
</ul>
<p>Recovery is handled by the NvM. For one of the described error cases, no recovery is provided (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_9_2_3_EEPROM_Abstraction.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_9_2_3_EEPROM_Abstraction">ErrorDescription p. 55</a>). A cancelled job is considered failed (<a class="spec-record-ref" data-req="SWS_Ea_00090" href="../../spec/record.html?id=SWS_Ea_00090">[SWS_Ea_00090]</a>). A write operation that does not complete successfully leaves the block marked as inconsistent (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_EA_SECTION_7_1_5_Managing_block_consistency_information.html" data-snip="SNIP_CLASSIC_EA_SECTION_7_1_5_Managing_block_consistency_information">SWS Ea p. 19</a>).</p>
