<p class="ai-level ai-oneliner-lead" data-ai-level="1">Koordiniert Software-Cluster-Updates und Resets zwischen Update and Configuration Management und State Management.</p>
<div class="ai-level" data-ai-level="2">
<p>
Das Service-Interface UpdateRequest wird vom State Management bereitgestellt, um dem Update and Configuration Management die strukturierte Durchführung von Updates, Installationen und Deinstallationen von Software-Clustern zu ermöglichen <a class="spec-record-ref" data-req="SWS_SM_91016" href="../spec/record.html?id=SWS_SM_91016">[SWS_SM_91016]</a>.
Vor der Ausführung von Vorbereitungs- oder Verifikationsschritten muss zwingend eine aktive Update-Sitzung etabliert werden, da SM Anfragen andernfalls abweist.
Neben Schritten zur Vorbereitung und Prüfung gestattet die Schnittstelle auch das Zurücksetzen der Maschine sowie das Absichern gegen fehlerhafte Zustände mittels Rollback <a class="spec-record-ref" data-req="SWS_SM_91105" href="../spec/record.html?id=SWS_SM_91105">[SWS_SM_91105]</a>.
Wesentliche Randbedingung ist, dass stets nur eine einzelne Update-Sitzung parallel existieren darf.
</p>

</div>
<div class="ai-level" data-ai-level="4">
<h4>Rolle und Systemkontext der Service-Schnittstelle</h4>
<p>
Das Service-Interface <code>UpdateRequest</code> wird vom Modul State Management (SM) über den gleichnamigen Port bereitgestellt <a class="spec-record-ref" data-req="SWS_SM_91016" href="../spec/record.html?id=SWS_SM_91016">[SWS_SM_91016]</a> <a class="spec-record-ref" data-req="SWS_SM_91017" href="../spec/record.html?id=SWS_SM_91017">[SWS_SM_91017]</a>. Als zentraler Interaktionspartner und Service-Consumer fungiert das funktionale Cluster Update and Configuration Management (UCM), um Aktualisierungen, Installationen und Deinstallationen von Software-Clustern kontrolliert abzuwickeln <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=137">SWS StateManagement §9.2.1 „UpdateRequest“</a>. Im Systemkontext der AUTOSAR Adaptive Platform fungiert SM hierbei als Server (Skeleton-Bereitstellung), während UCM als Client (Proxy) auftritt, um Funktionsgruppen in sichere Betriebszustände zu versetzen und den Fahrzeugzustand vor Zustandswechseln zu schützen.
</p>

<h4>Methoden und Felder im Detail</h4>
<p>
Die Schnittstelle definiert sechs koordinierende Methoden sowie ein Status-Feld für die Interaktion zwischen UCM und SM:
</p>
<ul>
  <li><code>RequestUpdateSession()</code>: Initiiert eine Aktualisierungssitzung. Der Aufruf erfolgt mit synchroner Rückmeldung (<code>Fire &amp; Forget false</code>) <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a>.</li>
  <li><code>PrepareUpdate(IN FunctionGroupListType functionGroupList)</code>: Bereitet die übergebenen Funktionsgruppen innerhalb des betroffenen Software-Clusters auf das Update vor (<code>Fire &amp; Forget false</code>) <a class="spec-record-ref" data-req="SWS_SM_91103" href="../spec/record.html?id=SWS_SM_91103">[SWS_SM_91103]</a> <a class="spec-record-ref" data-req="SWS_SM_00206" href="../spec/record.html?id=SWS_SM_00206">[SWS_SM_00206]</a>.</li>
  <li><code>VerifyUpdate(IN FunctionGroupListType functionGroupList)</code>: Verifiziert die aktualisierten Funktionsgruppen nach erfolgreicher Vorbereitung (<code>Fire &amp; Forget false</code>) <a class="spec-record-ref" data-req="SWS_SM_91104" href="../spec/record.html?id=SWS_SM_91104">[SWS_SM_91104]</a>.</li>
  <li><code>PrepareRollback(IN FunctionGroupListType functionGroupList)</code>: Bereitet die Funktionsgruppen auf das Zurückrollen eines fehlgeschlagenen Updates vor (<code>Fire &amp; Forget false</code>) <a class="spec-record-ref" data-req="SWS_SM_91105" href="../spec/record.html?id=SWS_SM_91105">[SWS_SM_91105]</a>.</li>
  <li><code>ResetMachine()</code>: Fordert einen Neustart der Maschine an; dieser Aufruf ist als asynchrones Fire-and-Forget (<code>Fire &amp; Forget true</code>) modelliert <a class="spec-record-ref" data-req="SWS_SM_91100" href="../spec/record.html?id=SWS_SM_91100">[SWS_SM_91100]</a>.</li>
  <li><code>StopUpdateSession()</code>: Informiert SM über den Abschluss der Aktualisierung und die Rückkehr in einen stabilen Maschinenzustand (<code>Fire &amp; Forget false</code>) <a class="spec-record-ref" data-req="SWS_SM_91101" href="../spec/record.html?id=SWS_SM_91101">[SWS_SM_91101]</a> <a class="spec-record-ref" data-req="SWS_SM_00205" href="../spec/record.html?id=SWS_SM_00205">[SWS_SM_00205]</a>.</li>
  <li><code>ResetMachineNotifier</code>: Ein Feld vom Typ <code>UpdateStatusType</code> mit Getter und Notifier (ohne Setter), über das UCM den Status des Maschinen-Resets während und nach dessen Ausführung überwacht <a class="spec-record-ref" data-req="SWS_SM_91106" href="../spec/record.html?id=SWS_SM_91106">[SWS_SM_91106]</a> <a class="spec-record-ref" data-req="SWS_SM_00211" href="../spec/record.html?id=SWS_SM_00211">[SWS_SM_00211]</a>.</li>
</ul>
<p>
Interpretation: Für alle Methoden mit <code>Fire &amp; Forget false</code> dürfte die synchrone Ergebnislieferung über die standardmäßigen Zukunftsobjekte (wie <code>ara::core::Future</code>) an den Client übermittelt werden, während <code>ResetMachine</code> unverzüglich ohne Rückgabewert zurückkehrt und die Statusnachverfolgung stattdessen auf das Notifier-Feld auslagert <a class="spec-record-ref" data-req="SWS_SM_91100" href="../spec/record.html?id=SWS_SM_91100">[SWS_SM_91100]</a> <a class="spec-record-ref" data-req="SWS_SM_91106" href="../spec/record.html?id=SWS_SM_91106">[SWS_SM_91106]</a>.
</p>

<h4>Lebenszyklus, Sitzungsabläufe und Zustandsabhängigkeiten</h4>
<p>
Jegliche Interaktion zur Modifikation von Software-Clustern erfordert eine strikt sequenzierte Sitzung. State Management muss die Informationen über eine laufende Update-Sitzung persistent speichern, damit diese nach einem beliebigen Maschinen-Reset ausgelesen und fortgeführt werden kann <a class="spec-record-ref" data-req="SWS_SM_00204" href="../spec/record.html?id=SWS_SM_00204">[SWS_SM_00204]</a> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=31">SWS StateManagement §7.x</a>. UCM leitet den Zyklus über <code>RequestUpdateSession</code> ein. Erst wenn SM dieser Berechtigung zugestimmt hat, dürfen Vorbereitungs- oder Verifikationsschritte ausgeführt werden <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a> <a class="spec-record-ref" data-req="SWS_SM_91103" href="../spec/record.html?id=SWS_SM_91103">[SWS_SM_91103]</a>.
</p>
<p>
Wird im Verlauf ein Maschinen-Reset über <code>ResetMachine</code> ausgelöst, sichert SM zuvor alle Maschinendaten <a class="spec-record-ref" data-req="SWS_SM_91100" href="../spec/record.html?id=SWS_SM_91100">[SWS_SM_91100]</a>. Beim Hochlauf geht SM in den Zustand <code>ContinueUpdate</code> über, während UCM über das Feld <code>ResetMachineNotifier</code> den Wiederanlauf synchronisiert <a class="spec-record-ref" data-req="SWS_SM_00211" href="../spec/record.html?id=SWS_SM_00211">[SWS_SM_00211]</a> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=33">SWS StateManagement §7.x „ResetMachine notification“</a>. Sobald sämtliche Aktualisierungsschritte abgeschlossen sind und sich das Gesamtsystem wieder in einem konsistenten Zustand befindet, schließt UCM die Sitzung mit <code>StopUpdateSession</code> ab <a class="spec-record-ref" data-req="SWS_SM_91101" href="../spec/record.html?id=SWS_SM_91101">[SWS_SM_91101]</a> <a class="spec-record-ref" data-req="SWS_SM_00205" href="../spec/record.html?id=SWS_SM_00205">[SWS_SM_00205]</a>.
</p>

<h4>Fehlerbehandlung und Application Errors</h4>
<p>
Die Schnittstelle sichert den Ablauf über spezifische Application Errors ab. Werden die Methoden <code>PrepareUpdate</code>, <code>VerifyUpdate</code>, <code>PrepareRollback</code> oder <code>StopUpdateSession</code> außerhalb einer aktiven Update-Sitzung aufgerufen, weist SM diese mit dem Fehlercode <code>kOperationRejected</code> zurück <a class="spec-record-ref" data-req="SWS_SM_00213" href="../spec/record.html?id=SWS_SM_00213">[SWS_SM_00213]</a>. Ebenso wird <code>ResetMachine</code> abgelehnt, wenn zuvor keine Update-Sitzung erfolgreich eröffnet wurde oder interne Maschinenzustände den Reset verbieten <a class="spec-record-ref" data-req="SWS_SM_91100" href="../spec/record.html?id=SWS_SM_91100">[SWS_SM_91100]</a>.
</p>
<p>
Wird bei bereits bestehender Sitzung erneut <code>RequestUpdateSession</code> gerufen, erfolgt eine Zurückweisung mit <code>kNotAllowedMultipleUpdateSessions</code>, da architektonisch nur eine einzige aktive Update-Sitzung zulässig ist <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a>. Treten bei der Ausführung der Vorbereitungs-, Prüf- oder Rollback-Vorgänge funktionale Probleme auf, melden die Methoden <code>PrepareUpdate</code>, <code>VerifyUpdate</code> und <code>PrepareRollback</code> den Fehler <code>kOperationFailed</code> zurück <a class="spec-record-ref" data-req="SWS_SM_91103" href="../spec/record.html?id=SWS_SM_91103">[SWS_SM_91103]</a> <a class="spec-record-ref" data-req="SWS_SM_91104" href="../spec/record.html?id=SWS_SM_91104">[SWS_SM_91104]</a> <a class="spec-record-ref" data-req="SWS_SM_91105" href="../spec/record.html?id=SWS_SM_91105">[SWS_SM_91105]</a>.
</p>
