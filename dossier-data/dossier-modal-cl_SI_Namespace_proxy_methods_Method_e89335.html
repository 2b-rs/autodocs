<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht den asynchronen Aufruf von Service-Methoden mit Rückgabewert sowie die Prüfung des End-to-End-Status.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Proxy-Methodenklasse <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;Method&gt;</code> ermöglicht Client-Anwendungen die Durchführung von Methodenaufrufen mit Rückgabewert für im <code>ServiceInterface</code> definierte Client-Server-Operationen <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Der Aufruf erfolgt nicht-blockierend über <code>operator()</code>, welcher unmittelbar ein <code>ara::core::Future</code> zur flexiblen synchronen oder asynchronen Ergebnisabfrage zurückgibt <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Ergänzend erlaubt <code>GetE2EStateMachineState()</code> das Auslesen des Schutzstatus der zugehörigen End-to-End-Zustandsmaschine <a class="spec-record-ref" data-req="SWS_CM_00148" href="../spec/record.html?id=SWS_CM_00148">[SWS_CM_00148]</a>. Da die Operationen als ausnahmesicher spezifiziert sind, werden Übertragungs- und Laufzeitfehler über das <code>Future</code> mit standardisierten Fehlercodes gemeldet.</p>

<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Die Klasse <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;Method&gt;</code> stellt die clientseitige Schnittstelle für synchrone und asynchrone Methodenaufrufe innerhalb des AUTOSAR Adaptive Kommunikationsmanagements dar. Für jede im <code>ServiceInterface</code> deklarierte Client-Server-Operation, bei der das Attribut <code>ClientServerOperation.fireAndForget == FALSE</code> konfiguriert ist, generiert das Kommunikations-Framework genau eine eigene Proxy-Methodenklasse in der Rolle einer Methode. Die Klasse ist als <code>final</code> deklariert und über den Header <code>#include "&lt;SiNamespaceDerivedDirectoryPath&gt;/&lt;SiShortname&gt;_proxy.h"</code> eingebunden <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=39">SWS Communication Management, S. 39</a>. Als direkte Interaktionspartner fungieren die aufrufende Client-Anwendung sowie das Network Binding, welches die Methodenübertragung an die entfernte Service-Instanz weiterleitet und deren Rückmeldung entgegennimmt <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Die Proxy-Methode nimmt die Aufrufparameter entgegen und kapselt den asynchronen Ablauf über ein <code>ara::core::Future</code>-Objekt, über das der Client den Abschluss und das Ergebnis des Aufrufs abfragt.</p>

<h4>Lebenszyklus</h4>
<p>Die Instanziierung von <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;Method&gt;</code> erfolgt im Verbund mit dem übergeordneten Service-Proxy. Interpretation: Die Methodenklasse dürfte als fester Bestandteil des generierten Proxy-Objekts zusammen mit diesem instanziiert und zerstört werden, weshalb der Anwender die Instanz nicht separat allokiert. <a class="interp-q interp-q-open" data-q="Q-546c9b1bceedef6b" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-546c9b1bceedef6b" title="Frage Q-546c9b1bceedef6b (offen): Die Instanz von &lt;SI-Namespace&gt;::proxy::methods::&lt;Method&gt; dürfte fest an den Lebenszyklus des übergeordneten Service-Proxy gebunden sein.">Frage Q-546c9b1bceedef6b (offen)</a> Bezüglich der Nebenläufigkeit ist der Methodenaufruf über <code>operator()</code> nicht-blockierend ausgelegt; die Funktion initiiert die Übertragung und kehrt unverzüglich zum Aufrufer zurück <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Ein zentraler Zustand der Instanz ist die Absicherung durch End-to-End-Mechanismen (E2E). Über die Methode <code>GetE2EStateMachineState()</code> kann die Anwendung den aktuellen Status der methodenspezifischen Zustandsmaschine (<code>ara::com::e2e::SMState</code>) ermitteln <a class="spec-record-ref" data-req="SWS_CM_00148" href="../spec/record.html?id=SWS_CM_00148">[SWS_CM_00148]</a>. Dieser Zustand wird durch die interne Prüffunktion <code>E2E_Check()</code> bestimmt, die während der Abarbeitung des letzten Aufrufs von <code>operator()</code> ausgeführt wird <a class="spec-record-ref" data-req="SWS_CM_00148" href="../spec/record.html?id=SWS_CM_00148">[SWS_CM_00148]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=55">SWS Communication Management, S. 55</a>. Interpretation: Die Zustandsaktualisierung der E2E-Zustandsmaschine dürfte asynchron mit dem Eintreffen und Prüfen der Antwortnachricht wirksam werden. <a class="interp-q interp-q-open" data-q="Q-283a9927420e2952" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-283a9927420e2952" title="Frage Q-283a9927420e2952 (offen): Die interne Auswertung von E2E_Check() dürfte asynchron mit dem Eintreffen der Server-Antwortdaten erfolgen.">Frage Q-283a9927420e2952 (offen)</a></p>

<h4>Nutzungspfad</h4>
<p>Die typische Aufrufreihenfolge umfasst die Initiierung des Methodenaufrufs, die Synchronisation auf das Ergebnis sowie die anschließende Integritätsprüfung:</p>
<ol>
  <li><strong>Aufruf auslösen:</strong> Die Client-Anwendung ruft das Funktionsobjekt über <code>operator()</code> mit den deklarierten Eingabeparametern auf <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>, <a class="spec-record-ref" data-req="SWS_CM_00191" href="../spec/record.html?id=SWS_CM_00191">[SWS_CM_00191]</a>.</li>
  <li><strong>Unmittelbare Rückkehr:</strong> Der Aufruf blockiert den anfragenden Thread nicht, sondern gibt unverzüglich ein Objekt vom Typ <code>ara::core::Future&lt;Output&gt;</code> zurück <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li><strong>Ergebnisabfrage:</strong> Der Aufrufer entscheidet autonom über synchrones Warten (z. B. über das <code>Future</code>-Objekt) oder eine asynchrone Überwachung auf die Beendigung des Aufrufs <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Bei erfolgreichem Abschluss liefert das <code>Future</code> das <code>Output</code>-Objekt mit den Antwortwerten <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>, <a class="spec-record-ref" data-req="SWS_CM_99333" href="../spec/record.html?id=SWS_CM_99333">[SWS_CM_99333]</a>.</li>
  <li><strong>E2E-Schutzstatus prüfen:</strong> Nach Beendigung des Aufrufs kann die Anwendung über <code>GetE2EStateMachineState()</code> den Zustand der E2E-Zustandsmaschine abfragen, um die Gültigkeit der Datenübertragung sicherzustellen <a class="spec-record-ref" data-req="SWS_CM_00148" href="../spec/record.html?id=SWS_CM_00148">[SWS_CM_00148]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Die Operationen <code>operator()</code> und <code>GetE2EStateMachineState()</code> sind als ausnahmesicher (<code>exception safe</code>) spezifiziert und mit <code>noexcept</code> deklariert <a class="spec-record-ref" data-req="SWS_CM_00148" href="../spec/record.html?id=SWS_CM_00148">[SWS_CM_00148]</a>, <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Kommunikations- und Bereitstellungsfehler werden daher nicht über C++-Exceptions gemeldet, sondern über das resultierende <code>ara::core::Future</code>-Objekt transportiert, das im Fehlerfall ein entsprechendes <code>ara::core::FutureErrc</code> bzw. Fehlercodes kapselt <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>. Spezifizierte Fehlerursachen sind unter anderem:</p>
<ul>
  <li><code>CommunicationFailure</code>: Das Network Binding meldet einen behebbaren Kommunikationsfehler oder das Scheitern einer abgesicherten Verbindung; bei Kommunikations-Timeouts kann dies zu einem ungewissen Zustand auf dem entfernten Server führen <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li><code>ComErrc::kServiceNotAvailable</code>: Die Service-Instanz ist nach vorheriger Bereitstellung nicht mehr erreichbar <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li><code>ComErrc::kUnknownApplicationError</code>: Ein entfernter Dienst meldet einen nicht konfigurierten Anwendungsfehler <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li><code>ComE2EErrc::kUnspecifiedE2EError</code>: Der Remote-Service meldet einen unspezifizierten End-to-End-Fehler <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li><code>ComErrc::kMinimumSendIntervalViolationError</code>: Die Aufrufanforderung erfolgte schneller als das für das Schnittstellenelement konfigurierte minimale Sendeintervall <code>minimumSendInterval</code> zulässt <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
  <li>Berechtigungsverletzung (<code>InsufficientPermissionsViolation</code>): Fehlen dem Aufrufer erforderliche Berechtigungen, wird die Ausführung durch die Grant Enforcement verweigert <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</li>
</ul>
<p>Für diese Anwendungs- und Kommunikationsfehler sind gemäß Spezifikation Rollback-Semantiken (<code>rollback_semantics</code>) hinterlegt <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a>.</p>
