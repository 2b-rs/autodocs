<h4>Context</h4>
<p>The class <code>ara::diag::ClientAuthentication</code> <a class="spec-record-ref" data-req="SWS_DM_01132" href="../spec/record.html?id=SWS_DM_01132">[SWS_DM_01132]</a> represents the central interface via which an adaptive application informs the Diagnostic Server instance about the authentication status as well as the currently authenticated user roles of external diagnostic clients (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=130">AUTOSAR_AP_SWS_Diagnostics, p. 130</a>). The necessity of this interface results from the fact that the actual authentication check is handled either by mechanisms of the Diagnostic Server instance itself or by upstream application logic <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>.</p>
<p>The primary interaction partners include:</p>
<ul>
<li><strong>Adaptive application:</strong> Performs authorization checks (for example via token validation in the SOVD context according to <a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>) and reports user roles to the server.</li>
<li><strong>Diagnostic Server (Diagnostic Manager):</strong> Manages the session states, controls access to diagnostic resources, and monitors inactivity times <a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a>.</li>
<li><strong>Diagnostic client:</strong> Communicates via UDS or SOVD. Each instance of <code>ClientAuthentication</code> is assigned to a fixed source address or address range of a diagnostic client via the model element <code>DiagnosticExternalAuthenticationIdentification</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics, p. 129</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>Instances of <code>ClientAuthentication</code> are not freely instantiated directly by application constructors. Instead, the application calls one of the overloaded factory methods <code>ara::diag::ExternalAuthentication::Get</code>, whereupon the Diagnostic Manager returns the corresponding instance <a class="spec-record-ref" data-req="SWS_DM_01202" href="../spec/record.html?id=SWS_DM_01202">[SWS_DM_01202]</a>. Alternatively, an instance is passed to the application as part of authorization validation <a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>. The total number of instances in the system is determined by the <code>DiagnosticExternalAuthenticationIdentification</code> elements configured in the model (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=129">AUTOSAR_AP_SWS_Diagnostics, p. 129</a>).</p>
<p>In terms of ownership, the object is designed as move-only: The copy constructor <a class="spec-record-ref" data-req="SWS_DM_01139" href="../spec/record.html?id=SWS_DM_01139">[SWS_DM_01139]</a> and the copy assignment operator <a class="spec-record-ref" data-req="SWS_DM_01140" href="../spec/record.html?id=SWS_DM_01140">[SWS_DM_01140]</a> are explicitly deleted (<code>delete</code>). However, instances can be efficiently transferred via move constructor <a class="spec-record-ref" data-req="SWS_DM_01137" href="../spec/record.html?id=SWS_DM_01137">[SWS_DM_01137]</a> and move assignment <a class="spec-record-ref" data-req="SWS_DM_01138" href="../spec/record.html?id=SWS_DM_01138">[SWS_DM_01138]</a>. The destructor is declared as <code>noexcept</code> <a class="spec-record-ref" data-req="SWS_DM_01136" href="../spec/record.html?id=SWS_DM_01136">[SWS_DM_01136]</a>. The class is specified as not thread-safe; concurrent calls on the same instance require external synchronization.</p>
<p>The logical lifecycle of authentication is based on the enumeration <code>DiagnosticAuthState</code> <a class="spec-record-ref" data-req="SWS_DM_01133" href="../spec/record.html?id=SWS_DM_01133">[SWS_DM_01133]</a>:</p>
<ul>
<li><strong><code>kDeAuthenticated</code>:</strong> Initial state after system start <a class="spec-record-ref" data-req="SWS_DM_01205" href="../spec/record.html?id=SWS_DM_01205">[SWS_DM_01205]</a>. Only the roles defined as default in the diagnostic extract (attribute <code>isDefault = TRUE</code>) are assigned to the DEM client <a class="spec-record-ref" data-req="SWS_DM_01204" href="../spec/record.html?id=SWS_DM_01204">[SWS_DM_01204]</a>. From this state, the standard roles can be temporarily modified using <code>OverrideDefaultRoles</code> <a class="spec-record-ref" data-req="SWS_DM_01209" href="../spec/record.html?id=SWS_DM_01209">[SWS_DM_01209]</a>.</li>
<li><strong><code>kAuthenticated</code>:</strong> Is assumed as soon as the application successfully calls <code>Authenticate</code> <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>. In this case, the explicitly passed user roles are assigned to the client.</li>
<li><strong>Fallback to <code>kDeAuthenticated</code>:</strong> If the client is in the default diagnostic session and no further request arrives after the last transmission confirmation, the Diagnostic Server resets the status to <code>kDeAuthenticated</code> due to inactivity <a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a> (e.g., as a result of an S3 timeout <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>).</li>
</ul>

<h4>Usage Path</h4>
<p>The typical use of <code>ClientAuthentication</code> follows an orderly sequence of instance acquisition, callback registration, role setting, and optional runtime extension:</p>
<ol>
<li><strong>Obtain instance:</strong> The application calls <code>ara::diag::ExternalAuthentication::Get</code> with the desired source address to obtain the associated <code>ClientAuthentication</code> object <a class="spec-record-ref" data-req="SWS_DM_01202" href="../spec/record.html?id=SWS_DM_01202">[SWS_DM_01202]</a>.</li>
<li><strong>Register state observer:</strong> Via <code>SetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>, the application registers a function callback of type <code>ClientAuthenticationSetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_02077" href="../spec/record.html?id=SWS_DM_02077">[SWS_DM_02077]</a>. This is called by the diagnostic server instance upon state changes—in particular upon automatically falling back to state <code>kDeAuthenticated</code>. A subsequent call overwrites the previously registered notifier <a class="spec-record-ref" data-req="SWS_DM_01144" href="../spec/record.html?id=SWS_DM_01144">[SWS_DM_01144]</a>.</li>
<li><strong>Query state:</strong> Using <code>GetState</code> <a class="spec-record-ref" data-req="SWS_DM_01143" href="../spec/record.html?id=SWS_DM_01143">[SWS_DM_01143]</a>, the application can synchronously check at any time whether the client is currently deauthenticated or authenticated.</li>
<li><strong>Assign roles:</strong> As soon as the client identity has been verified, the application reports the roles to be enabled as a vector of <code>DiagnosticAuthRole</code> <a class="spec-record-ref" data-req="SWS_DM_01134" href="../spec/record.html?id=SWS_DM_01134">[SWS_DM_01134]</a> via <code>Authenticate</code> <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>. The diagnostic server instance transitions to state <code>kAuthenticated</code> <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>.</li>
<li><strong>Accept and reuse handle:</strong> Upon successful completion, <code>Authenticate</code> returns a <code>ClientAuthenticationHandle</code> <a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>, <a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>. Using this handle, the application can define further access lists via a <code>DynamicAccessList</code> <a class="spec-record-ref" data-req="SWS_DM_01213" href="../spec/record.html?id=SWS_DM_01213">[SWS_DM_01213]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=132">AUTOSAR_AP_SWS_Diagnostics, p. 132</a>). In addition, creating the handle refreshes the inactivity period (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=133">AUTOSAR_AP_SWS_Diagnostics, p. 133</a>).</li>
</ol>
