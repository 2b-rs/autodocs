<h4>Context</h4>
<p>The data structure <code>apext::com::secoc::FVContainer</code> is part of the normative Platform Extension Interfaces of the AUTOSAR Adaptive Platform in the Communication Management module (<a class="spec-record-ref" data-req="SWS_CM_11286" href="../spec/record.html?id=SWS_CM_11286">[SWS_CM_11286]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=536">AUTOSAR_AP_SWS_CommunicationManagement §C.1.1 “Struct: FVContainer”</a>). Platform Extension Interfaces are functional interfaces provided or used by a vehicle manufacturer (OEM) or system integrator to specifically extend the basic functionality of the Adaptive system (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=536">AUTOSAR_AP_SWS_CommunicationManagement §C.1.1 “Struct: FVContainer”</a>). Within this extension concept, <code>FVContainer</code> is defined via the header <code>apext/com/secoc/fvm.h</code> and assumes the role of a standardized transport container for freshness values (Freshness Values).</p>

<p>In the field of secure onboard communication (Secure Onboard Communication, SecOC), the verification and generation of freshness values is essential to effectively prevent replay attacks on transmitted messages. The structure <code>FVContainer</code> serves as a dedicated link between the communication services of the platform and the vendor-specific Freshness Value Manager (FVM). Instead of complex interface parameters, the struct encapsulates the freshness value information in two elementary components: the exact bit length of the value and the actual payload in byte form (<a class="spec-record-ref" data-req="SWS_CM_11344" href="../spec/record.html?id=SWS_CM_11344">[SWS_CM_11344]</a>, <a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>). This enables flexible passing regardless of whether complete or truncated values are exchanged.</p>

<h4>Lifecycle</h4>
<p>The structure <code>FVContainer</code> is designed as a purely passive data transfer object (Value Object) (<a class="spec-record-ref" data-req="SWS_CM_11286" href="../spec/record.html?id=SWS_CM_11286">[SWS_CM_11286]</a>). It possesses no state machine of its own and does not manage any active background resources or threads. Instantiation typically occurs directly in the context of an upcoming message transmission or message reception operation, either on the stack of the calling thread or as a temporary object within the processing pipeline.</p>

<p>With regard to ownership, <code>FVContainer</code> is subject to standard C++ value semantics. The instance owns its member variables exclusively. Upon assignment or passing to interface methods, the values are copied or transferred via move semantics. The element <code>value</code> encapsulates a vector of type <code>ara::core::Vector&lt;std::uint8_t&gt;</code> (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>) that manages its memory area dynamically. The destruction of <code>FVContainer</code> occurs deterministically upon leaving the enclosing scope according to RAII principles, with the dynamically allocated buffer of the vector being released automatically.</p>

<p>In terms of concurrency, <code>FVContainer</code> offers no inherent thread safety. Interpretation: Since the struct provides no internal synchronization mechanisms or mutexes, concurrent accesses by multiple threads to the same instance must be completely serialized by the calling component.</p>

<h4>Usage Path</h4>
<p>The primary usage flow of <code>FVContainer</code> comprises data exchange between the SecOC subsystem and the functions of the FVM during authentication or verification of messages. Depending on whether the container acts as an input or return value, it transports either complete or truncated freshness values (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=537">AUTOSAR_AP_SWS_CommunicationManagement §C.1.1.1.2 “value”</a>).</p>

<ol>
<li><strong>Instantiation and Preparation:</strong> Communication Management creates a local instance of <code>FVContainer</code> (<a class="spec-record-ref" data-req="SWS_CM_11286" href="../spec/record.html?id=SWS_CM_11286">[SWS_CM_11286]</a>). In the case of message verification, the subsystem extracts the truncated freshness value (Truncated Freshness Value) from the received message and populates the vector <code>value</code> as well as the bit length in <code>length</code> (<a class="spec-record-ref" data-req="SWS_CM_11344" href="../spec/record.html?id=SWS_CM_11344">[SWS_CM_11344]</a>, <a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>).</li>
<li><strong>Interface Call:</strong> The instance is passed to the corresponding FVM interface function (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=536">AUTOSAR_AP_SWS_CommunicationManagement §C.1.1 “Struct: FVContainer”</a>). Interpretation: The FVM reconstructs the complete freshness value based on the passed truncated value and internal counters.</li>
<li><strong>Return and Further Processing:</strong> The FVM returns the result either in the form of a newly created or modified <code>FVContainer</code> instance (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>). The calling system reads the actual bit length from <code>length</code> (<a class="spec-record-ref" data-req="SWS_CM_11344" href="../spec/record.html?id=SWS_CM_11344">[SWS_CM_11344]</a>) and the byte sequence from <code>value</code> (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>) in order to finally perform the cryptographic authentication (e.g. MAC calculation).</li>
</ol>

<h4>Error Scenarios</h4>
<p>As a pure data structure, <code>FVContainer</code> declares no member functions of its own and therefore neither defines specific error codes nor throws platform-specific exceptions (<a class="spec-record-ref" data-req="SWS_CM_11286" href="../spec/record.html?id=SWS_CM_11286">[SWS_CM_11286]</a>). Nevertheless, strict functional preconditions exist for the use of the contained attributes:</p>

<ul>
<li><strong>Inconsistent length specifications:</strong> The variable <code>length</code> precisely defines the length of the freshness value in bits (<a class="spec-record-ref" data-req="SWS_CM_11344" href="../spec/record.html?id=SWS_CM_11344">[SWS_CM_11344]</a>), while <code>value</code> holds the data in a byte vector (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>). The precondition applies that the size of the vector in bytes must correspond at least to the rounded-up number of bits. Interpretation: If <code>length</code> has a value of 0 or the vector capacity falls below the specified bit length, the called FVM function must reject the input as invalid.</li>
<li><strong>Memory allocation errors:</strong> When assigning or resizing the vector <code>value</code> (<a class="spec-record-ref" data-req="SWS_CM_11345" href="../spec/record.html?id=SWS_CM_11345">[SWS_CM_11345]</a>), an exception of type <code>std::bad_alloc</code> can occur in the event of exhausted system memory resources. The calling layer must ensure at platform level that such allocation errors are caught in a controlled manner.</li>
<li><strong>Invalid freshness values:</strong> If a freshness value cannot be successfully determined or verified by the FVM, the calling system must not reuse the raw data remaining in <code>FVContainer</code>, so as not to compromise the integrity of the security architecture.</li>
</ul>
