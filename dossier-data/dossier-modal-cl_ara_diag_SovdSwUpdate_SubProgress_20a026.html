<h4>Context</h4>
<p>The data structure <code>ara::diag::SovdSwUpdate::SubProgress</code> is part of Service-Oriented Vehicle Diagnostics (SOVD) within the Diagnostic Management functional cluster of the AUTOSAR Adaptive Platform <a class="spec-record-ref" data-req="SWS_DM_01896" href="../spec/record.html?id=SWS_DM_01896">[SWS_DM_01896]</a>. It is declared in the header file <code>ara/diag/sovd_sw_update.h</code> and, according to <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=748">AUTOSAR_AP_SWS_Diagnostics §8.58.3 “Struct: SubProgress”</a>, serves as a standardized data type for recording detailed progress information of software update operations. The definition addresses the overarching requirement RS_Diag_04265 for supporting structured update workflows via SOVD.</p>

<p>In modern vehicle architectures, a software update often consists of multiple sub-steps or comprises several independent software units. <code>SubProgress</code> assumes the role of a fine-grained status and progress report for a specific entity within the overall process. Via the attribute <code>entity</code> of type <code>ara::core::String</code>, the currently processed entity is identified <a class="spec-record-ref" data-req="SWS_DM_01898" href="../spec/record.html?id=SWS_DM_01898">[SWS_DM_01898]</a>. As a pure data transfer object, the structure mediates between the executing update routines of the platform and the diagnostic interface, which aggregates the status data and provides it for external diagnostic testers or cloud services.</p>

<h4>Lifecycle</h4>
<p>The structure <code>SubProgress</code> is declared as a simple C++ composite type <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=749">AUTOSAR_AP_SWS_Diagnostics §8.58.3 “struct ara::diag::SovdSwUpdate::SubProgress”</a>. This results in direct consequences for lifecycle and memory management:</p>
<ul>
<li><strong>Creation:</strong> Instances of <code>SubProgress</code> are typically instantiated by the responsible update handler on the stack or within dynamic containers as soon as an update phase is initiated for an entity or intermediate progress is to be reported.</li>
<li><strong>Ownership and transfer:</strong> As a regular value type, the structure follows standard C++ copy and move semantics. The creating component initially owns the object exclusively and passes it by value or constant reference to the higher-level management class <code>SovdSwUpdate</code>.</li>
<li><strong>Destruction:</strong> The lifetime ends automatically upon leaving the local scope or upon destruction of the enclosing data container. Dynamically allocated resources, such as the string in <code>entity</code>, are released via the destructors of the standard types of <code>ara::core</code>.</li>
<li><strong>Concurrency:</strong> <code>SubProgress</code> has no internal locking mechanisms. If progress data is collected asynchronously in separate threads and transmitted to diagnostic threads, thread-safe synchronization is the responsibility of the callers involved.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical sequence for using <code>SubProgress</code> is divided into initialization, continuous updating of the progress, and completion of the sub-update:</p>
<ol>
<li><strong>Entity initialization:</strong> At the beginning of the update of a sub-component, the update workflow instantiates a <code>SubProgress</code> structure and assigns the unique identifier of the entity to field <code>entity</code> <a class="spec-record-ref" data-req="SWS_DM_01898" href="../spec/record.html?id=SWS_DM_01898">[SWS_DM_01898]</a>.</li>
<li><strong>Status and progress reporting:</strong> During the process, field <code>status</code> is populated with the current operating state of type <code>SovdUpdateStatus</code> <a class="spec-record-ref" data-req="SWS_DM_01899" href="../spec/record.html?id=SWS_DM_01899">[SWS_DM_01899]</a>. If quantifiable progress exists, attribute <code>progress</code> of type <code>ara::core::Optional&lt;std::uint8_t&gt;</code> is written with the percentage progress value <a class="spec-record-ref" data-req="SWS_DM_01900" href="../spec/record.html?id=SWS_DM_01900">[SWS_DM_01900]</a>. Interpretation: If no percentage intermediate stage can be calculated for an operation, the optional field is likely to remain unset (corresponding to <code>ara::core::nullopt</code>).</li>
<li><strong>Successful completion:</strong> After error-free transmission or installation, <code>status</code> transitions to the corresponding completion state <a class="spec-record-ref" data-req="SWS_DM_01899" href="../spec/record.html?id=SWS_DM_01899">[SWS_DM_01899]</a>, and <code>progress</code> is set to the final maximum value.</li>
</ol>
<p>The diagnostic system reads out these fields in order to populate higher-level SOVD progress objects and enable transparent monitoring of individual update steps.</p>

<h4>Error Scenarios</h4>
<p>The specification provides for an explicit coupling between the execution status and occurred errors for the structure:</p>
<ul>
<li><strong>Error signaling via the status:</strong> If the update of an entity fails, this is indicated in attribute <code>status</code> by the error status <a class="spec-record-ref" data-req="SWS_DM_01899" href="../spec/record.html?id=SWS_DM_01899">[SWS_DM_01899]</a>.</li>
<li><strong>Detailing the cause of the error:</strong> Member <code>error</code> of type <code>ara::core::ErrorCode</code> specifies the error that occurred if and only if the status signals a failure <a class="spec-record-ref" data-req="SWS_DM_01901" href="../spec/record.html?id=SWS_DM_01901">[SWS_DM_01901]</a> according to <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=749">AUTOSAR_AP_SWS_Diagnostics §8.58.3.1.2 “error”</a>. This allows specific protocol- or hardware-specific error causes to be transmitted in a structured manner to the diagnostic system.</li>
<li><strong>Consistency requirements:</strong> Interpretation: For developers, this results in the precondition that in error-free states, no relevant error code may be evaluated in <code>error</code>, whereas in the event of an error, a valid <code>ara::core::ErrorCode</code> must presumably be stored in order to avoid misinterpretations on the receiver side.</li>
</ul>
