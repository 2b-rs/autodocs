<h4>Role of Diagnostic Management between tester, transport layer, and applications</h4>
<p>Module <code>diag</code> describes the Diagnostic Management (DM) of the Adaptive Platform. The DM receives UDS requests via a standardized C++ <em>Transport Protocol API</em>. Different UDS transport layers can be connected to this API. Currently, only the Ethernet connection with mandatory DoIP is described in detail; proprietary protocols are possible via the same API (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P94_127.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P94_127">SWS Diagnostics p. 94</a>). The DM instantiates an independent <em>Diagnostic Server instance</em> with its own resources for each <code>DiagnosticContributionSet</code>. All instances share the same UDS transport layer (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P112_147.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P112_147">SWS Diagnostics p. 112</a>).</p>
<p>The actual business logic resides in Adaptive Applications. They provide port interfaces such as <code>SecurityAccess</code>, <code>ServiceValidation</code>, <code>Authentication</code>, or <code>FileTransferService</code>. These interfaces consist of <code>Offer</code>/<code>StopOffer</code> and callback methods (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-dbe10d5d26d0b330.html" data-snip="FIG-dbe10d5d26d0b330">EXP SWArchitecture p. 158</a>, <a class="spec-record-ref" data-req="SWS_DM_00766" href="../spec/record.html?id=SWS_DM_00766">[SWS_DM_00766]</a>, <a class="spec-record-ref" data-req="SWS_DM_01336" href="../spec/record.html?id=SWS_DM_01336">[SWS_DM_01336]</a>). For ECU resets, the Diagnostic Server calls <code>EcuResetRequest::RequestReset</code> and <code>ExecuteReset</code> (<a class="spec-record-ref" data-req="SWS_DM_01013" href="../spec/record.html?id=SWS_DM_01013">[SWS_DM_01013]</a>, <a class="spec-record-ref" data-req="SWS_DM_01014" href="../spec/record.html?id=SWS_DM_01014">[SWS_DM_01014]</a>). In older architecture diagrams (R21-11 to R23-11), State Management is shown as the provider of this interface (<a class="docref internal-spec-ref" href="../../spec/figures/FIG-7991c9ebcc425bf5.html" data-snip="FIG-7991c9ebcc425bf5">EXP SWArchitecture p. 143</a>).</p>

<h4>Lifecycle of UDS Transport Plugins</h4>
<p>A transport plugin implements <code>UdsTransportProtocolHandler</code>. Upon construction, it receives a <code>UdsTransportProtocolHandlerID</code> and a reference to the <code>UdsTransportProtocolMgr</code> (<a class="spec-record-ref" data-req="SWS_DM_09015" href="../spec/record.html?id=SWS_DM_09015">[SWS_DM_09015]</a>, <a class="spec-record-ref" data-req="SWS_DM_00325" href="../spec/record.html?id=SWS_DM_00325">[SWS_DM_00325]</a>). The DM controls the plugin in fixed steps:</p>
<ol>
<li><code>Initialize</code> returns a <code>InitializationResult</code> (<a class="spec-record-ref" data-req="SWS_DM_00319" href="../spec/record.html?id=SWS_DM_00319">[SWS_DM_00319]</a>, <a class="spec-record-ref" data-req="SWS_DM_09017" href="../spec/record.html?id=SWS_DM_09017">[SWS_DM_09017]</a>).</li>
<li><code>Start</code> starts the protocol processing (<a class="spec-record-ref" data-req="SWS_DM_00322" href="../spec/record.html?id=SWS_DM_00322">[SWS_DM_00322]</a>).</li>
<li><code>Stop</code> requests termination (<a class="spec-record-ref" data-req="SWS_DM_00323" href="../spec/record.html?id=SWS_DM_00323">[SWS_DM_00323]</a>).</li>
<li>The plugin acknowledges with <code>HandlerStopped</code> (<a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>).</li>
</ol>

<h4>Acceptance and Processing of a UDS Request</h4>
<p>The reception of a request begins with <code>IndicateMessage</code>. The call passes source and target address, address type, and channel. Returned is a <code>std::pair</code> consisting of <code>IndicationResult</code> and <code>UdsMessagePtr</code> (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>, <a class="spec-record-ref" data-req="SWS_DM_00303" href="../spec/record.html?id=SWS_DM_00303">[SWS_DM_00303]</a>). In case of <code>kIndicationOk</code>, the DM provides a <code>UdsMessage</code> with at least one byte of capacity, whose payload is initially empty (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P98_131.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P98_131">SWS Diagnostics p. 98</a>). The plugin fills the message starting from the SID and forwards it with <code>HandleMessage</code>. With any other result, forwarding is omitted (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P100_133.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P100_133">SWS Diagnostics p. 100</a>).</p>
<p>Rejection reasons:</p>
<ul>
<li><strong>Busy:</strong> If the DM is busy with the same tester present conversation, it responds with <code>kIndicationOccupied</code>. An exception is a functional tester present <code>0x3E 0x80</code> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P99_132.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P99_132">SWS Diagnostics p. 99</a>). The DM only recognizes this exception if the plugin supplies the first bytes in <code>payloadInfo</code> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P94_127.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P94_127">SWS Diagnostics p. 94</a>).</li>
<li><strong>Unknown target address:</strong> The result is <code>kIndicationUnknownTargetAddress</code> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P100_133.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P100_133">SWS Diagnostics p. 100</a>).</li>
</ul>
<p>With each accepted indication, the S3 timer stops (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P145_179.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P145_179">SWS Diagnostics p. 145</a>).</p>

<h4>Application Interfaces: Offering, Callbacks, and Invocation Context</h4>
<p>Callback interfaces receive a <code>InstanceSpecifier</code> and a <code>ConcurrencyType</code> upon construction. Examples are <code>GenericUDSService</code>, <code>GenericDataIdentifier</code>, and <code>GenericRoutine</code> (<a class="spec-record-ref" data-req="SWS_DM_00616" href="../spec/record.html?id=SWS_DM_00616">[SWS_DM_00616]</a>, <a class="spec-record-ref" data-req="SWS_DM_00634" href="../spec/record.html?id=SWS_DM_00634">[SWS_DM_00634]</a>, <a class="spec-record-ref" data-req="SWS_DM_00552" href="../spec/record.html?id=SWS_DM_00552">[SWS_DM_00552]</a>). With <code>Offer</code>, the application enables the forwarding of requests, and disables it again with <code>StopOffer</code> (<a class="spec-record-ref" data-req="SWS_DM_00619" href="../spec/record.html?id=SWS_DM_00619">[SWS_DM_00619]</a>, <a class="spec-record-ref" data-req="SWS_DM_00620" href="../spec/record.html?id=SWS_DM_00620">[SWS_DM_00620]</a>). The callbacks return their results asynchronously as <code>ara::core::Future</code> (<a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>, <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a>, <a class="spec-record-ref" data-req="SWS_DM_00554" href="../spec/record.html?id=SWS_DM_00554">[SWS_DM_00554]</a>).</p>
<p>The <code>ConcurrencyType</code> specifies how the DM invokes callbacks (<a class="spec-record-ref" data-req="SWS_DM_00935" href="../spec/record.html?id=SWS_DM_00935">[SWS_DM_00935]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P116_151.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P116_151">SWS Diagnostics p. 116</a>):</p>
<ul>
<li><code>kConcurrent</code>: The DM may invoke a callback again before the previous result is available.</li>
<li><code>kNotConcurrent</code>: The DM blocks until the future is ready.</li>
</ul>
<p>For data identifiers, the value can be specified separately for reading, writing, and combined accesses (<a class="spec-record-ref" data-req="SWS_DM_00937" href="../spec/record.html?id=SWS_DM_00937">[SWS_DM_00937]</a>, <a class="spec-record-ref" data-req="SWS_DM_00938" href="../spec/record.html?id=SWS_DM_00938">[SWS_DM_00938]</a>, <a class="spec-record-ref" data-req="SWS_DM_00939" href="../spec/record.html?id=SWS_DM_00939">[SWS_DM_00939]</a>).</p>
<p>Each callback receives a <code>MetaInfo</code>. It provides values by key and a context, such as <code>kDiagnosticCommunication</code>, <code>kFaultMemory</code>, <code>kDoIP</code>, or <code>kSovd</code> (<a class="spec-record-ref" data-req="SWS_DM_00978" href="../spec/record.html?id=SWS_DM_00978">[SWS_DM_00978]</a>, <a class="spec-record-ref" data-req="SWS_DM_00979" href="../spec/record.html?id=SWS_DM_00979">[SWS_DM_00979]</a>, <a class="spec-record-ref" data-req="SWS_DM_01342" href="../spec/record.html?id=SWS_DM_01342">[SWS_DM_01342]</a>, <a class="spec-record-ref" data-req="SWS_DM_01343" href="../spec/record.html?id=SWS_DM_01343">[SWS_DM_01343]</a>, <a class="spec-record-ref" data-req="SWS_DM_01344" href="../spec/record.html?id=SWS_DM_01344">[SWS_DM_01344]</a>, <a class="spec-record-ref" data-req="SWS_DM_01818" href="../spec/record.html?id=SWS_DM_01818">[SWS_DM_01818]</a>). <strong>Important:</strong> The object is only valid during the call. Anyone storing it or reusing it later causes undefined behavior (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P116_151.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P116_151">SWS Diagnostics p. 116</a>). Via the <code>CancellationHandler</code>, the application detects a cancellation: <code>IsCanceled</code> queries the state, <code>SetNotifier</code> registers a notification (<a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a>, <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-ce869eaca7549641.html" data-snip="FIG-ce869eaca7549641">EXP SWArchitecture p. 152</a>).</p>

<h4>Conversations, Sessions, and Access Protection</h4>
<p>Applications view the state of a conversation via the class <code>Conversation</code>. <code>GetConversation</code> determines the conversation from a <code>MetaInfo</code>. Further methods return all or all active conversations as well as session and security level (<a class="spec-record-ref" data-req="SWS_DM_00692" href="../spec/record.html?id=SWS_DM_00692">[SWS_DM_00692]</a>, <a class="spec-record-ref" data-req="SWS_DM_00782" href="../spec/record.html?id=SWS_DM_00782">[SWS_DM_00782]</a>, <a class="spec-record-ref" data-req="SWS_DM_00783" href="../spec/record.html?id=SWS_DM_00783">[SWS_DM_00783]</a>, <a class="spec-record-ref" data-req="SWS_DM_00696" href="../spec/record.html?id=SWS_DM_00696">[SWS_DM_00696]</a>, <a class="spec-record-ref" data-req="SWS_DM_00698" href="../spec/record.html?id=SWS_DM_00698">[SWS_DM_00698]</a>). A notifier can be registered for session changes (<a class="spec-record-ref" data-req="SWS_DM_00697" href="../spec/record.html?id=SWS_DM_00697">[SWS_DM_00697]</a>). <code>ResetToDefaultSession</code> actively resets to <code>kDefaultSession</code> (0x01) (<a class="spec-record-ref" data-req="SWS_DM_00701" href="../spec/record.html?id=SWS_DM_00701">[SWS_DM_00701]</a>, <a class="spec-record-ref" data-req="SWS_DM_01278" href="../spec/record.html?id=SWS_DM_01278">[SWS_DM_01278]</a>). Without a configured <code>s3ServerTimeout</code>, an S3 timeout of 5000 ms applies (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P144_178.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P144_178">SWS Diagnostics p. 144</a>). Upon transition to the default session, the DM reactivates a deactivated DTC setting (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P145_179.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P145_179">SWS Diagnostics p. 145</a>).</p>
<p>For access protection, the DM delegates checks to the application:</p>
<ul>
<li><strong>SecurityAccess:</strong> <code>GetSeed</code> and <code>CompareKey</code> (<a class="spec-record-ref" data-req="SWS_DM_00764" href="../spec/record.html?id=SWS_DM_00764">[SWS_DM_00764]</a>, <a class="spec-record-ref" data-req="SWS_DM_00765" href="../spec/record.html?id=SWS_DM_00765">[SWS_DM_00765]</a>).</li>
<li><strong>ServiceValidation:</strong> <code>Validate</code> and <code>Confirmation</code> (<a class="spec-record-ref" data-req="SWS_DM_00774" href="../spec/record.html?id=SWS_DM_00774">[SWS_DM_00774]</a>, <a class="spec-record-ref" data-req="SWS_DM_00775" href="../spec/record.html?id=SWS_DM_00775">[SWS_DM_00775]</a>).</li>
<li><strong>Authentication (Service 0x29):</strong> The subfunctions lead to <code>VerifyCertificateUnidirectional</code>, <code>VerifyCertificateBidirectional</code>, and <code>VerifyOwnership</code>, respectively (<a class="spec-record-ref" data-req="SWS_DM_01126" href="../spec/record.html?id=SWS_DM_01126">[SWS_DM_01126]</a>, <a class="spec-record-ref" data-req="SWS_DM_01127" href="../spec/record.html?id=SWS_DM_01127">[SWS_DM_01127]</a>, <a class="spec-record-ref" data-req="SWS_DM_01128" href="../spec/record.html?id=SWS_DM_01128">[SWS_DM_01128]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P166_202.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P166_202">SWS Diagnostics p. 166</a>).</li>
</ul>
<p>A successful authentication assigns roles via <code>ClientAuthentication::Authenticate</code>. Permitted services are specified by a <code>DiagnosticServiceDynamicAccessList</code>, which is built with <code>Append</code> and <code>Build</code> (<a class="spec-record-ref" data-req="SWS_DM_01142" href="../spec/record.html?id=SWS_DM_01142">[SWS_DM_01142]</a>, <a class="spec-record-ref" data-req="SWS_DM_01152" href="../spec/record.html?id=SWS_DM_01152">[SWS_DM_01152]</a>, <a class="spec-record-ref" data-req="SWS_DM_01181" href="../spec/record.html?id=SWS_DM_01181">[SWS_DM_01181]</a>). The server compares incoming requests with the entries in this list using pattern matching (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P136_170.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P136_170">SWS Diagnostics p. 136</a>).</p>

<h4>Fault Memory: Monitors, Events, and Indicators</h4>
<p>A <code>Monitor</code> reports test results via <code>ReportMonitorAction</code> (<a class="spec-record-ref" data-req="SWS_DM_00543" href="../spec/record.html?id=SWS_DM_00543">[SWS_DM_00543]</a>, <a class="spec-record-ref" data-req="SWS_DM_00541" href="../spec/record.html?id=SWS_DM_00541">[SWS_DM_00541]</a>). Depending on the constructor variant, it selects a debouncing:</p>
<ul>
<li>counter-based (<a class="spec-record-ref" data-req="SWS_DM_00549" href="../spec/record.html?id=SWS_DM_00549">[SWS_DM_00549]</a>),</li>
<li>time-based (<a class="spec-record-ref" data-req="SWS_DM_00550" href="../spec/record.html?id=SWS_DM_00550">[SWS_DM_00550]</a>),</li>
<li>monitor-internal with callback <code>getFaultDetectionCounter</code> (<a class="spec-record-ref" data-req="SWS_DM_00548" href="../spec/record.html?id=SWS_DM_00548">[SWS_DM_00548]</a>).</li>
</ul>
<p>The reports <code>kPassed</code> and <code>kFailed</code> act directly as a test result. <code>kPrepassed</code> and <code>kPrefailed</code> trigger debouncing (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P249_290.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P249_290">SWS Diagnostics p. 249</a>). If the FDC equivalent reaches +127 or −128, the <code>DebouncingState</code> becomes <code>kFinallyDefective</code> or <code>kFinallyHealed</code>, respectively, and the status bit <code>kTestFailed</code> changes (<a class="spec-record-ref" data-req="SWS_DM_00645" href="../spec/record.html?id=SWS_DM_00645">[SWS_DM_00645]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P238_281.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P238_281">SWS Diagnostics p. 238</a>).</p>
<p>An event may only be reported from exactly one source. The reporting interface is explicitly non-reentrant (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P225_266.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P225_266">SWS Diagnostics p. 225</a>). The class <code>Event</code> provides status, status change notifiers, and Fault Detection Counter. The DM processes the status bits like UDS DTC status bits (<a class="spec-record-ref" data-req="SWS_DM_00649" href="../spec/record.html?id=SWS_DM_00649">[SWS_DM_00649]</a>, <a class="spec-record-ref" data-req="SWS_DM_00650" href="../spec/record.html?id=SWS_DM_00650">[SWS_DM_00650]</a>, <a class="spec-record-ref" data-req="SWS_DM_00656" href="../spec/record.html?id=SWS_DM_00656">[SWS_DM_00656]</a>, <a class="spec-record-ref" data-req="SWS_DM_00643" href="../spec/record.html?id=SWS_DM_00643">[SWS_DM_00643]</a>). For multiple monitors, events, or conditions behind a port, the variants <code>MultipleMonitor</code>, <code>MultipleEvent</code>, and <code>MultipleCondition</code> are available (<a class="spec-record-ref" data-req="SWS_DM_01695" href="../spec/record.html?id=SWS_DM_01695">[SWS_DM_01695]</a>, <a class="spec-record-ref" data-req="SWS_DM_01705" href="../spec/record.html?id=SWS_DM_01705">[SWS_DM_01705]</a>, <a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-0e230acf2dcb148d.html" data-snip="FIG-0e230acf2dcb148d">EXP SWArchitecture p. 153</a>).</p>
<p><code>GetIndicatorState</code> reports <code>kOnDemand</code> as soon as an event of the DTC is set to OnDemand, and <code>kOff</code> only if all are off (<a class="spec-record-ref" data-req="SWS_DM_00744" href="../spec/record.html?id=SWS_DM_00744">[SWS_DM_00744]</a>, <a class="spec-record-ref" data-req="SWS_DM_00740" href="../spec/record.html?id=SWS_DM_00740">[SWS_DM_00740]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P259_300.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P259_300">SWS Diagnostics p. 259</a>). A renewed call of <code>SetNotifier</code> overwrites the previous notifier. According to the R24-11 version, the method is not thread-safe (<a class="spec-record-ref" data-req="SWS_DM_00745" href="../spec/record.html?id=SWS_DM_00745">[SWS_DM_00745]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_OS_SECTION_8_44_2_1_3_2_SetNotifier.html" data-snip="SNIP_ADAPTIVE_OS_SECTION_8_44_2_1_3_2_SetNotifier">SWS Diagnostics R24-11 p. 633</a>).</p>

<h4>Behavior in the event of an error</h4>
<p>Errors are reported via dedicated error domains: <code>DiagErrc</code>, <code>DiagOfferErrc</code>, <code>DiagReportingErrc</code>, <code>DiagUdsNrcErrc</code>, and <code>DiagSovdErrc</code>. Error codes are created via the respective <code>MakeErrorCode</code> function (<a class="spec-record-ref" data-req="SWS_DM_00514" href="../spec/record.html?id=SWS_DM_00514">[SWS_DM_00514]</a>, <a class="spec-record-ref" data-req="SWS_DM_00559" href="../spec/record.html?id=SWS_DM_00559">[SWS_DM_00559]</a>, <a class="spec-record-ref" data-req="SWS_DM_00560" href="../spec/record.html?id=SWS_DM_00560">[SWS_DM_00560]</a>, <a class="spec-record-ref" data-req="SWS_DM_00526" href="../spec/record.html?id=SWS_DM_00526">[SWS_DM_00526]</a>, <a class="spec-record-ref" data-req="SWS_DM_01806" href="../spec/record.html?id=SWS_DM_01806">[SWS_DM_01806]</a>, <a class="spec-record-ref" data-req="SWS_DM_00537" href="../spec/record.html?id=SWS_DM_00537">[SWS_DM_00537]</a>). If a callback returns an error from the <code>DiagUdsNrcErrorDomain</code>, the server sends a negative response with this value as the NRC. Only values from 0x01 to 0xFE are valid (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P144_178.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P144_178">SWS Diagnostics p. 144</a>).</p>
<p>Further specified reactions:</p>
<ul>
<li><strong>Interface not offered:</strong> If a required interface is no longer provided via <code>Offer</code>, the DM responds with NRC 0x94 (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P143_177.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P143_177">SWS Diagnostics p. 143</a>).</li>
<li><strong>Too many response-pending responses:</strong> If their number reaches <code>maxNumberOfRequestCorrectlyReceivedResponsePending</code>, the server aborts and responds with NRC 0x10 (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P143_177.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P143_177">SWS Diagnostics p. 143</a>). Interpretation: This abort is likely to become visible to the application via <code>CancellationHandler::IsCanceled</code> (<a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a>).</li>
<li><strong>Missing access rights:</strong> NRC 0x34 for UDS or HTTP 401 for SOVD (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P136_170.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P136_170">SWS Diagnostics p. 136</a>).</li>
<li><strong>Transport error:</strong> The plugin reports errors during the reception of multi-part requests via <code>NotifyMessageFailure</code>; transmission errors via the <code>TransmissionResult</code> (<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>, <a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_diag_AUTOSAR_AP_SWS_D_P145_179.html" data-snip="SNIP_diag_AUTOSAR_AP_SWS_D_P145_179">SWS Diagnostics p. 145</a>).</li>
</ul>
