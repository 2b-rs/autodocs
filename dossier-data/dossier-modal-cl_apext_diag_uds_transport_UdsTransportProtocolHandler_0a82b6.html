  <h4>Context</h4>
  <p>
    The class <code>apext::diag::uds_transport::UdsTransportProtocolHandler</code> is the abstract base class for specific and proprietary UDS transport protocol plugins in Diagnostic Management (DM) of AUTOSAR Adaptive (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”</a>, <a class="spec-record-ref" data-req="SWS_DM_00315" href="../spec/record.html?id=SWS_DM_00315">[SWS_DM_00315]</a>). It decouples the generic diagnostic core from the peculiarities of concrete transmission networks and transport layers such as DoIP or CAN-based protocols.
  </p>
  <p>
    A transport handler essentially interacts with three partners:
  </p>
  <ul>
    <li>
      <strong>Diagnostic Management Core:</strong> The DM manages the entire lifecycle of the handler and provides the peer for status and data indications via the manager reference <code>apext::diag::uds_transport::UdsTransportProtocolMgr</code> (<a class="spec-record-ref" data-req="SWS_DM_09015" href="../spec/record.html?id=SWS_DM_09015">[SWS_DM_09015]</a>, <a class="spec-record-ref" data-req="SWS_DM_09025" href="../spec/record.html?id=SWS_DM_09025">[SWS_DM_09025]</a>).
    </li>
    <li>
      <strong>Network layer and diagnostic client:</strong> The plugin handles the physical or logical data exchange with the external or internal diagnostic tester (<a class="spec-record-ref" data-req="SWS_DM_00326" href="../spec/record.html?id=SWS_DM_00326">[SWS_DM_00326]</a>, <a class="spec-record-ref" data-req="SWS_DM_00351" href="../spec/record.html?id=SWS_DM_00351">[SWS_DM_00351]</a>).
    </li>
    <li>
      <strong>Periodic handler (optional):</strong> If the respective transport protocol supports periodic transmissions, the handler provides a reference to a <code>UdsTransportProtocolPeriodicHandler</code> via <code>GetPeriodicHandler()</code> (<a class="spec-record-ref" data-req="SWS_DM_01068" href="../spec/record.html?id=SWS_DM_01068">[SWS_DM_01068]</a>).
    </li>
  </ul>

  <h4>Lifecycle</h4>
  <p>
    The lifecycle of a transport protocol implementation is strictly controlled by the DM (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”</a>, <a class="spec-record-ref" data-req="SWS_DM_00329" href="../spec/record.html?id=SWS_DM_00329">[SWS_DM_00329]</a>). Creation takes place via the constructor <code>UdsTransportProtocolHandler(handlerId, transportProtocolMgr)</code>, in which the DM assigns the handler a unique identifier of type <code>UdsTransportProtocolHandlerID</code> and the reference to the associated <code>UdsTransportProtocolMgr</code> (<a class="spec-record-ref" data-req="SWS_DM_09015" href="../spec/record.html?id=SWS_DM_09015">[SWS_DM_09015]</a>, <a class="spec-record-ref" data-req="SWS_DM_09025" href="../spec/record.html?id=SWS_DM_09025">[SWS_DM_09025]</a>). The assigned ID can be queried at any time via <code>GetHandlerID()</code> (<a class="spec-record-ref" data-req="SWS_DM_00325" href="../spec/record.html?id=SWS_DM_00325">[SWS_DM_00325]</a>). The constructor is designated as thread-safe (<a class="spec-record-ref" data-req="SWS_DM_09015" href="../spec/record.html?id=SWS_DM_09015">[SWS_DM_09015]</a>).
  </p>
  <p>
    To decouple complex protocol initializations from the constructor, the DM subsequently calls <code>Initialize()</code> (<a class="spec-record-ref" data-req="SWS_DM_00319" href="../spec/record.html?id=SWS_DM_00319">[SWS_DM_00319]</a>, <a class="spec-record-ref" data-req="SWS_DM_00329" href="../spec/record.html?id=SWS_DM_00329">[SWS_DM_00329]</a>). Except for <code>GetPeriodicHandler()</code>, the DM must not call any other methods of the handler before a successful return of <code>InitializationResult::kInitializeOk</code> (<a class="spec-record-ref" data-req="SWS_DM_01746" href="../spec/record.html?id=SWS_DM_01746">[SWS_DM_01746]</a>, <a class="spec-record-ref" data-req="SWS_DM_09017" href="../spec/record.html?id=SWS_DM_09017">[SWS_DM_09017]</a>). After successful initialization, the DM starts the protocol via <code>Start()</code> (<a class="spec-record-ref" data-req="SWS_DM_00322" href="../spec/record.html?id=SWS_DM_00322">[SWS_DM_00322]</a>). Because <code>Start()</code> is executed asynchronously, the DM can start multiple handlers in parallel to minimize startup time (<a class="spec-record-ref" data-req="SWS_DM_00322" href="../spec/record.html?id=SWS_DM_00322">[SWS_DM_00322]</a>).
  </p>
  <p>
    When the DM application transitions to the <code>ApplicationState.kTerminating</code> state, it calls <code>Stop()</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=97">AUTOSAR_AP_SWS_Diagnostics §7.1.1.1</a>, <a class="spec-record-ref" data-req="SWS_DM_00333" href="../spec/record.html?id=SWS_DM_00333">[SWS_DM_00333]</a>, <a class="spec-record-ref" data-req="SWS_DM_00323" href="../spec/record.html?id=SWS_DM_00323">[SWS_DM_00323]</a>). The DM waits until the handler confirms the stop via <code>UdsTransportProtocolMgr::HandlerStopped(handlerId)</code> (<a class="spec-record-ref" data-req="SWS_DM_00340" href="../spec/record.html?id=SWS_DM_00340">[SWS_DM_00340]</a>). After the return from <code>Stop()</code>, the handler plugin must not call any further methods on the manager—with the sole exception of the acknowledgement <code>HandlerStopped()</code> (<a class="spec-record-ref" data-req="SWS_DM_01741" href="../spec/record.html?id=SWS_DM_01741">[SWS_DM_01741]</a>, <a class="spec-record-ref" data-req="SWS_DM_00323" href="../spec/record.html?id=SWS_DM_00323">[SWS_DM_00323]</a>). The subsequent teardown takes place via the virtual destructor (<a class="spec-record-ref" data-req="SWS_DM_09016" href="../spec/record.html?id=SWS_DM_09016">[SWS_DM_09016]</a>).
  </p>

  <h4>Usage Path</h4>
  <p>
    In ongoing operation, the handler performs the bidirectional exchange of UDS messages:
  </p>
  <ol>
    <li>
      <strong>Message reception (indication):</strong> As soon as a new UDS message is received on a channel and the source address, target address, addressing type (physical or functional), total message length, and the first payload bytes (at least two bytes for messages larger than one byte) are known, the plugin calls <code>UdsTransportProtocolMgr::IndicateMessage(...)</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=101">AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 “Indication of UDS message reception”</a>, <a class="spec-record-ref" data-req="SWS_DM_00342" href="../spec/record.html?id=SWS_DM_00342">[SWS_DM_00342]</a>, <a class="spec-record-ref" data-req="SWS_DM_00330" href="../spec/record.html?id=SWS_DM_00330">[SWS_DM_00330]</a>). In doing so, the handler passes the channel identification in parameter <code>globalChannelId</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=102">AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”</a>).
    </li>
    <li>
      <strong>Message transmission (transmission):</strong> The DM sends the associated UDS diagnostic response back via the same handler and the same channel (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=101">AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”</a>, <a class="spec-record-ref" data-req="SWS_DM_00348" href="../spec/record.html?id=SWS_DM_00348">[SWS_DM_00348]</a>). To do so, it calls <code>Transmit(message, channelId)</code> (<a class="spec-record-ref" data-req="SWS_DM_00327" href="../spec/record.html?id=SWS_DM_00327">[SWS_DM_00327]</a>). The message is passed to the handler as <code>UdsMessageConstPtr</code> in the manner of a <code>std::unique_ptr</code>.
    </li>
    <li>
      <strong>Transmission acknowledgement:</strong> As soon as the message has been sent over the network (or an error occurred), the handler must return ownership of <code>message</code> to the DM via <code>UdsTransportProtocolMgr::TransmitConfirmation(result, message)</code> (<a class="spec-record-ref" data-req="SWS_DM_00327" href="../spec/record.html?id=SWS_DM_00327">[SWS_DM_00327]</a>). The result is transmitted as <code>kTransmitOk</code> or <code>kTransmitFailed</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=102">AUTOSAR_AP_SWS_Diagnostics §7.1.1.3</a>, <a class="spec-record-ref" data-req="SWS_DM_00351" href="../spec/record.html?id=SWS_DM_00351">[SWS_DM_00351]</a>).
    </li>
  </ol>
  <p>
    Another specific usage path is the restoration of channels after an ECU reset (UDS service <code>0x11</code> with positive response after reset): Here, the DM calls <code>NotifyReestablishment(channelId)</code> before the restart (<a class="spec-record-ref" data-req="SWS_DM_00326" href="../spec/record.html?id=SWS_DM_00326">[SWS_DM_00326]</a>). The plugin persistently stores the connection parameters (for example, IP addresses and ports). After restarting via <code>Start()</code>, the plugin detects the reconnection of the same diagnostic client and informs the DM via <code>UdsTransportProtocolMgr::ChannelReestablished(...)</code> (<a class="spec-record-ref" data-req="SWS_DM_00326" href="../spec/record.html?id=SWS_DM_00326">[SWS_DM_00326]</a>, <a class="spec-record-ref" data-req="SWS_DM_01744" href="../spec/record.html?id=SWS_DM_01744">[SWS_DM_01744]</a>).
  </p>

  <h4>Error Scenarios</h4>
  <p>
    The interface handles various exception and error situations:
  </p>
  <ul>
    <li>
      <strong>Failed initialization:</strong> If <code>Initialize()</code> returns the value <code>InitializationResult::kInitializeFailed</code> (<a class="spec-record-ref" data-req="SWS_DM_09017" href="../spec/record.html?id=SWS_DM_09017">[SWS_DM_09017]</a>), the DM completely aborts the startup process of this transport protocol and does not call any further methods on this instance (<a class="spec-record-ref" data-req="SWS_DM_01745" href="../spec/record.html?id=SWS_DM_01745">[SWS_DM_01745]</a>).
    </li>
    <li>
      <strong>Unsupported periodic transmissions:</strong> If the concrete protocol does not support periodic transmissions, calling <code>GetPeriodicHandler()</code> returns a <code>ara::core::Result</code> with the error code <code>kConfigurationMismatch</code> (<a class="spec-record-ref" data-req="SWS_DM_01068" href="../spec/record.html?id=SWS_DM_01068">[SWS_DM_01068]</a>).
    </li>
    <li>
      <strong>Rejection of channel restoration:</strong> If a plugin cannot satisfy the persistent reservation for a channel (for example, in the absence of a non-volatile storage option or unstable mapping), <code>NotifyReestablishment(channelId)</code> returns the value <code>false</code> (<a class="spec-record-ref" data-req="SWS_DM_00326" href="../spec/record.html?id=SWS_DM_00326">[SWS_DM_00326]</a>).
    </li>
    <li>
      <strong>Transmission error in the network:</strong> If the network layer was unable to send a message requested via <code>Transmit()</code>, the handler must pass the result <code>kTransmitFailed</code> in <code>TransmitConfirmation</code> (<a class="spec-record-ref" data-req="SWS_DM_00351" href="../spec/record.html?id=SWS_DM_00351">[SWS_DM_00351]</a>). Failing to return the buffer leads to resource leaks in the DM.
    </li>
    <li>
      <strong>Sequence violation after stopping:</strong> If a plugin calls a method other than <code>HandlerStopped()</code> on <code>UdsTransportProtocolMgr</code> after returning from <code>Stop()</code>, this constitutes a violation of the protocol sequence (<a class="spec-record-ref" data-req="SWS_DM_00323" href="../spec/record.html?id=SWS_DM_00323">[SWS_DM_00323]</a>, <a class="spec-record-ref" data-req="SWS_DM_01741" href="../spec/record.html?id=SWS_DM_01741">[SWS_DM_01741]</a>).
    </li>
  </ul>
