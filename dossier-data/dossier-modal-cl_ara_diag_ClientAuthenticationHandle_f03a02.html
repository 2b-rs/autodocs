<h4>Context</h4>
<p>The class <code>ara::diag::ClientAuthenticationHandle</code> (<a class="spec-record-ref" data-req="SWS_DM_01145" href="../spec/record.html?id=SWS_DM_01145">[SWS_DM_01145]</a>) serves as a control interface for an active diagnostic authentication session. An instance of this handle is provided to an adaptive application by the <em>Diagnostic Server Instance</em> as soon as either an authentication via <code>ara::diag::ClientAuthentication::Authenticate</code> (<a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>) or a temporary override of default roles via <code>ara::diag::ClientAuthentication::OverrideDefaultRoles</code> (<a class="spec-record-ref" data-req="SWS_DM_01209" href="../spec/record.html?id=SWS_DM_01209">[SWS_DM_01209]</a>) has completed successfully (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=132">AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 “ClientAuthenticationHandle”</a>).</p>

<p>The Diagnostic Manager manages a dynamic access control list (<code>DynamicAccessList</code>) for each authenticated client. This list contains patterns for diagnostic requests that grant the authenticated client additional access rights to diagnostic resources beyond the configuration stored in the Diagnostic Extract (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=132">AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 “ClientAuthenticationHandle”</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=133">AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.4 “DynamicAccessList Creation and Update”</a>). Via <code>ClientAuthenticationHandle</code>, the application controls both these dynamic access rights as well as the authentication state and the associated inactivity and expiration timers with respect to the server instance (<a class="spec-record-ref" data-req="SWS_DM_01213" href="../spec/record.html?id=SWS_DM_01213">[SWS_DM_01213]</a>, <a class="spec-record-ref" data-req="SWS_DM_01155" href="../spec/record.html?id=SWS_DM_01155">[SWS_DM_01155]</a>).</p>

<h4>Lifecycle</h4>
<p>The creation of a valid handle typically does not occur via the default constructor, but as a return value of the authentication methods of class <code>ara::diag::ClientAuthentication</code> (<a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>, <a class="spec-record-ref" data-req="SWS_DM_01209" href="../spec/record.html?id=SWS_DM_01209">[SWS_DM_01209]</a>). Although the class provides a thread-safe, exception-safe default constructor (<a class="spec-record-ref" data-req="SWS_DM_01146" href="../spec/record.html?id=SWS_DM_01146">[SWS_DM_01146]</a>), this creates an uninitialized or empty handle. With regard to ownership, <code>ClientAuthenticationHandle</code> implements strict move-only semantics: the copy constructor (<a class="spec-record-ref" data-req="SWS_DM_01150" href="../spec/record.html?id=SWS_DM_01150">[SWS_DM_01150]</a>) and copy assignment operator (<a class="spec-record-ref" data-req="SWS_DM_01151" href="../spec/record.html?id=SWS_DM_01151">[SWS_DM_01151]</a>) are deleted (<code>=delete</code>). A handle can only be moved (move constructor <a class="spec-record-ref" data-req="SWS_DM_01148" href="../spec/record.html?id=SWS_DM_01148">[SWS_DM_01148]</a> and move assignment <a class="spec-record-ref" data-req="SWS_DM_01149" href="../spec/record.html?id=SWS_DM_01149">[SWS_DM_01149]</a>), ensuring a unique owner per authentication context.</p>

<p>Destruction of the object takes place via the destructor <code>~ClientAuthenticationHandle()</code> (<a class="spec-record-ref" data-req="SWS_DM_01147" href="../spec/record.html?id=SWS_DM_01147">[SWS_DM_01147]</a>). Regarding concurrency, it should be noted that neither the destructor nor the controlling member functions (<code>Set</code>, <code>Append</code>, <code>Refresh</code>, <code>Revoke</code>) are thread-safe (<a class="spec-record-ref" data-req="SWS_DM_01147" href="../spec/record.html?id=SWS_DM_01147">[SWS_DM_01147]</a>, <a class="spec-record-ref" data-req="SWS_DM_01152" href="../spec/record.html?id=SWS_DM_01152">[SWS_DM_01152]</a>, <a class="spec-record-ref" data-req="SWS_DM_01153" href="../spec/record.html?id=SWS_DM_01153">[SWS_DM_01153]</a>, <a class="spec-record-ref" data-req="SWS_DM_01154" href="../spec/record.html?id=SWS_DM_01154">[SWS_DM_01154]</a>, <a class="spec-record-ref" data-req="SWS_DM_01155" href="../spec/record.html?id=SWS_DM_01155">[SWS_DM_01155]</a>). If multiple threads of an application access the same handle, the access must be synchronized.</p>

<h4>Usage Path</h4>
<p>A typical usage path includes successful authentication, defining and expanding access rights, periodically extending validity, and finally revoking the rights:</p>
<ol>
  <li><strong>Obtaining the handle:</strong> The application calls <code>Authenticate</code> or <code>OverrideDefaultRoles</code> and, upon success, receives the <code>ClientAuthenticationHandle</code> (<a class="spec-record-ref" data-req="SWS_DM_01206" href="../spec/record.html?id=SWS_DM_01206">[SWS_DM_01206]</a>, <a class="spec-record-ref" data-req="SWS_DM_01209" href="../spec/record.html?id=SWS_DM_01209">[SWS_DM_01209]</a>).</li>
  <li><strong>Setting rights:</strong> Using <code>Set(dynamicAccessList)</code>, the application completely replaces the dynamic access list of the diagnostic client (<a class="spec-record-ref" data-req="SWS_DM_01153" href="../spec/record.html?id=SWS_DM_01153">[SWS_DM_01153]</a>, <a class="spec-record-ref" data-req="SWS_DM_01213" href="../spec/record.html?id=SWS_DM_01213">[SWS_DM_01213]</a>).</li>
  <li><strong>Extending rights:</strong> Via <code>Append(dynamicAccessList)</code>, further diagnostic service patterns can be appended incrementally to the existing <code>DynamicAccessList</code> as needed (<a class="spec-record-ref" data-req="SWS_DM_01152" href="../spec/record.html?id=SWS_DM_01152">[SWS_DM_01152]</a>).</li>
  <li><strong>Renewing timers:</strong> During ongoing diagnostic communication, the application calls <code>Refresh()</code> to reset inactivity or role timeout timers (<a class="spec-record-ref" data-req="SWS_DM_01155" href="../spec/record.html?id=SWS_DM_01155">[SWS_DM_01155]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=133">AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 “ClientAuthenticationHandle”</a>, <a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a>). If both authentication and role override were previously used, the call renews both timers simultaneously (<a class="spec-record-ref" data-req="SWS_DM_01155" href="../spec/record.html?id=SWS_DM_01155">[SWS_DM_01155]</a>).</li>
  <li><strong>Revoking rights:</strong> Using <code>Revoke()</code>, the application explicitly returns the client to the state <code>kDeAuthenticated</code>, discards the assigned <code>DynamicAccessList</code>, and revokes temporarily overridden roles (<a class="spec-record-ref" data-req="SWS_DM_01154" href="../spec/record.html?id=SWS_DM_01154">[SWS_DM_01154]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>All state-modifying methods of the handle (<code>Set</code>, <code>Append</code>, <code>Refresh</code>, and <code>Revoke</code>) are declared as <code>noexcept</code> and report errors via the return type <code>ara::core::Result&lt;void&gt;</code>:</p>
<ul>
  <li><code>DiagErrc::kServiceNotAvailable</code>: Occurs when the operation cannot be executed because essential functionalities of the Diagnostic Manager are currently unavailable (<a class="spec-record-ref" data-req="SWS_DM_01152" href="../spec/record.html?id=SWS_DM_01152">[SWS_DM_01152]</a>, <a class="spec-record-ref" data-req="SWS_DM_01153" href="../spec/record.html?id=SWS_DM_01153">[SWS_DM_01153]</a>, <a class="spec-record-ref" data-req="SWS_DM_01154" href="../spec/record.html?id=SWS_DM_01154">[SWS_DM_01154]</a>, <a class="spec-record-ref" data-req="SWS_DM_01155" href="../spec/record.html?id=SWS_DM_01155">[SWS_DM_01155]</a>). In this case, rollback semantics apply, leaving the previous state in the system untouched.</li>
  <li><strong>Timeout and automatic de-authentication:</strong> If the inactivity timer is not renewed in time via UDS requests or <code>Refresh()</code>, the Diagnostic Server Instance automatically transitions the client to the state <code>kDeAuthenticated</code> (<a class="spec-record-ref" data-req="SWS_DM_01210" href="../spec/record.html?id=SWS_DM_01210">[SWS_DM_01210]</a>). Interpretation: Subsequent control attempts on an expired context are likely to fail or remain ineffective.</li>
</ul>
