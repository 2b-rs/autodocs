<h4>Context</h4>
<p>The namespace <code>apext::tsync</code> provides platform-specific extensions (Platform Extensions) of the AUTOSAR Adaptive module <code>tsync</code> for Freshness Value Management (FVM). In distributed automotive ECU architectures, Freshness Value Management protects time-critical as well as security-relevant synchronization messages against replay and delay attacks by generating, managing, and verifying dynamic freshness values.</p>
<p>The primary task of the namespace lies in providing the central interface <code>FVM</code> for the module <code>ara::tsync</code> as well as the associated data structures. Freshness values are encapsulated by the container class <code>FVContainer</code>, which holds both the bit length of the value and the actual payload in the form of a vector. For standardized error handling, the namespace defines an independent error domain <code>TsyncFvmErrorDomain</code> with associated error enumerator <code>TsyncFvmErrc</code> <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>, the error factory function <code>MakeErrorCode</code> <a class="spec-record-ref" data-req="SWS_TS_14213" href="../spec/record.html?id=SWS_TS_14213">[SWS_TS_14213]</a>, and the exception class <code>TsyncFvmException</code>.</p>

<h4>Lifecycle</h4>

Via the function <code>GetTsyncFvmErrorDomain()</code>, a reference to the global instance object can be retrieved at any time. The function is specified as <code>constexpr</code>, thread-safe, and exception-safe <a class="spec-record-ref" data-req="SWS_TS_14212" href="../spec/record.html?id=SWS_TS_14212">[SWS_TS_14212]</a>, meaning that the error domain remains available across the entire runtime of the application.</li>
<li><strong>Manager instance:</strong> An initialization phase is designated for the Freshness Value Manager. <li><strong>Data container:</strong> Instances of <code>FVContainer</code> possess a call-specific lifecycle. They are created to hold freshness values, passed during verification or message creation, and can be destroyed again after completion of the operation.</li>
</ul>

<h4>Usage Path</h4>
<p>A typical usage path for securing synchronization messages is structured into the following interaction steps:</p>
<ol>
<li><strong>Request:</strong> Interpretation: The interface <code>FVM</code> is likely called by components within <code>ara::tsync</code> to request and verify freshness values. The higher-level time module integrates the interface <code>FVM</code> to provide freshness values for outgoing or incoming messages.</li>
<li><strong>Data handover:</strong> Upon successful determination, the Freshness Value Manager populates an instance of <code>FVContainer</code> with the bit length and the byte vector of the freshness value and hands it over to the calling time synchronization.</li>
<li><strong>Error signaling:</strong> If no valid value is available at runtime, the subsystem creates a standardized error code of type <code>ara::core::ErrorCode</code> via <code>MakeErrorCode</code> <a class="spec-record-ref" data-req="SWS_TS_14213" href="../spec/record.html?id=SWS_TS_14213">[SWS_TS_14213]</a> using <code>TsyncFvmErrc::kFVNotAvailable</code> <a class="spec-record-ref" data-req="SWS_TS_14202" href="../spec/record.html?id=SWS_TS_14202">[SWS_TS_14202]</a>.</li>
<li><strong>Error evaluation:</strong> The caller evaluates the result. Interpretation: Callers are likely able to make a retry attempt in the event of <code>kFVNotAvailable</code>, as this is a recoverable error condition.</li>
