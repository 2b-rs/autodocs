<h4>Role of the EcuM: phase manager between reset, BswM, and hardware</h4>
<p>The ECU State Manager (EcuM) handles startup and shutdown of OS, SchM, and BswM, manages shutdown targets, and monitors wakeup sources including their validation. In the flexible variant, it has no state machine of its own. BswM decides on transitions; EcuM executes the associated sequences and reports back the results (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_10_EcuM_Mode_Handling.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_10_EcuM_Mode_Handling">SWS EcuM p. 103</a>, <a class="spec-record-ref" data-req="SWS_EcuM_04116" href="../../spec/record.html?id=SWS_EcuM_04116">[SWS_EcuM_04116]</a>).</p>
<p>The EcuM offloads hardware-dependent steps to callouts. These are function stubs in the integration code that the system designer fills (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_GLOSSARY_SECTION_4_53_Callout.html" data-snip="SNIP_CLASSIC_GLOSSARY_SECTION_4_53_Callout">Glossary p. 42</a>). Examples are <code>EcuM_AL_DriverInitZero</code> <a class="spec-record-ref" data-req="SWS_EcuM_02905" href="../../spec/record.html?id=SWS_EcuM_02905">[SWS_EcuM_02905]</a> and <code>EcuM_AL_SwitchOff</code> <a class="spec-record-ref" data-req="SWS_EcuM_02920" href="../../spec/record.html?id=SWS_EcuM_02920">[SWS_EcuM_02920]</a>. The required external interfaces are listed in <a class="spec-record-ref" data-req="SWS_EcuM_02858" href="../../spec/record.html?id=SWS_EcuM_02858">[SWS_EcuM_02858]</a> and <a class="spec-record-ref" data-req="SWS_EcuM_02859" href="../../spec/record.html?id=SWS_EcuM_02859">[SWS_EcuM_02859]</a>. An overview is provided in the module relationships diagram (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-71c44c809a87837c.html" data-snip="FIG-71c44c809a87837c">SWS EcuM p. 33</a>).</p>

<h4>Startup: from EcuM_Init via StartOS to EcuM_StartupTwo</h4>
<p>Prior to <code>EcuM_Init</code>, stack and C variable initialization must be ready (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_3_1_Activities_before_EcuM_Init.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_3_1_Activities_before_EcuM_Init">SWS EcuM p. 39</a>). <code>EcuM_Init</code> never returns, because it ends with <code>StartOS</code> <a class="spec-record-ref" data-req="SWS_EcuM_02811" href="../../spec/record.html?id=SWS_EcuM_02811">[SWS_EcuM_02811]</a>. In between, it executes the StartPreOS sequence <a class="spec-record-ref" data-req="SWS_EcuM_02684" href="../../spec/record.html?id=SWS_EcuM_02684">[SWS_EcuM_02684]</a>, which initializes all modules necessary for the OS start <a class="spec-record-ref" data-req="SWS_EcuM_02603" href="../../spec/record.html?id=SWS_EcuM_02603">[SWS_EcuM_02603]</a>.</p>
<p>The StartPreOS sequence proceeds in the following steps:</p>
<ul>
<li>Init Block 0 contains only modules that are configured at pre-compile or link time <a class="spec-record-ref" data-req="SWS_EcuM_02905" href="../../spec/record.html?id=SWS_EcuM_02905">[SWS_EcuM_02905]</a>.</li>
<li><code>EcuM_DeterminePbConfiguration</code> selects the post-build configuration and returns a pointer to <code>EcuM_ConfigType</code>. This structure references the configurations of all further modules <a class="spec-record-ref" data-req="SWS_EcuM_02906" href="../../spec/record.html?id=SWS_EcuM_02906">[SWS_EcuM_02906]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02801" href="../../spec/record.html?id=SWS_EcuM_02801">[SWS_EcuM_02801]</a>.</li>
<li>Prior to the first BSW initialization, the EcuM checks the consistency of all post-build data via hash <a class="spec-record-ref" data-req="SWS_EcuM_02796" href="../../spec/record.html?id=SWS_EcuM_02796">[SWS_EcuM_02796]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02798" href="../../spec/record.html?id=SWS_EcuM_02798">[SWS_EcuM_02798]</a>.</li>
<li>Init Block 1 follows <a class="spec-record-ref" data-req="SWS_EcuM_02907" href="../../spec/record.html?id=SWS_EcuM_02907">[SWS_EcuM_02907]</a>. Order and parameters of the initialization originate from the configuration <a class="spec-record-ref" data-req="SWS_EcuM_02559" href="../../spec/record.html?id=SWS_EcuM_02559">[SWS_EcuM_02559]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02730" href="../../spec/record.html?id=SWS_EcuM_02730">[SWS_EcuM_02730]</a>.</li>
<li>The EcuM translates the reset reason into a wakeup source and remembers it <a class="spec-record-ref" data-req="SWS_EcuM_02623" href="../../spec/record.html?id=SWS_EcuM_02623">[SWS_EcuM_02623]</a>.</li>
<li>Optionally, <code>EcuM_LoopDetection</code> runs <a class="spec-record-ref" data-req="SWS_EcuM_04137" href="../../spec/record.html?id=SWS_EcuM_04137">[SWS_EcuM_04137]</a>.</li>
</ul>
<p><code>EcuM_StartupTwo</code> must be called from a task that starts as a consequence of <code>StartOS</code> <a class="spec-record-ref" data-req="SWS_EcuM_02806" href="../../spec/record.html?id=SWS_EcuM_02806">[SWS_EcuM_02806]</a>. The function executes the StartPostOS sequence: start SchM, initialize BswM, initialize SchM, and start the scheduler timing <a class="spec-record-ref" data-req="SWS_EcuM_02932" href="../../spec/record.html?id=SWS_EcuM_02932">[SWS_EcuM_02932]</a> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_3_3_Activities_in_the_StartPostOS_Sequence.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_3_3_Activities_in_the_StartPostOS_Sequence">SWS EcuM p. 42</a>). The remaining BSW modules are subsequently initialized by BswM via generated functions <code>EcuM_AL_DriverInitBswM_&lt;x&gt;</code> <a class="spec-record-ref" data-req="SWS_EcuM_04114" href="../../spec/record.html?id=SWS_EcuM_04114">[SWS_EcuM_04114]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04142" href="../../spec/record.html?id=SWS_EcuM_04142">[SWS_EcuM_04142]</a>.</p>

<h4>UP phase: RUN/POST_RUN requests and mode switches</h4>
<p>If <code>EcuMModeHandling</code> is active <a class="spec-record-ref" data-req="SWS_EcuM_04115" href="../../spec/record.html?id=SWS_EcuM_04115">[SWS_EcuM_04115]</a>, configured users can request and release RUN and POST_RUN <a class="spec-record-ref" data-req="SWS_EcuM_04130" href="../../spec/record.html?id=SWS_EcuM_04130">[SWS_EcuM_04130]</a>. For this purpose, <code>EcuM_RequestRUN</code>, <code>EcuM_ReleaseRUN</code>, <code>EcuM_RequestPOST_RUN</code>, and <code>EcuM_ReleasePOST_RUN</code> are available <a class="spec-record-ref" data-req="SWS_EcuM_04124" href="../../spec/record.html?id=SWS_EcuM_04124">[SWS_EcuM_04124]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04129" href="../../spec/record.html?id=SWS_EcuM_04129">[SWS_EcuM_04129]</a>. The EcuM tracks the requests per user <a class="spec-record-ref" data-req="SWS_EcuM_04126" href="../../spec/record.html?id=SWS_EcuM_04126">[SWS_EcuM_04126]</a> and separately for RUN and POST_RUN (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_8_3_3_4_EcuM_RequestPOST_RUN.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_8_3_3_4_EcuM_RequestPOST_RUN">SWS EcuM p. 116</a>). A user cannot place a request multiple times <a class="spec-record-ref" data-req="SWS_EcuM_04125" href="../../spec/record.html?id=SWS_EcuM_04125">[SWS_EcuM_04125]</a>.</p>
<p>The EcuM reports the arbitration result via <code>BswM_EcuM_RequestedState</code>:</p>
<ul>
<li>Upon the first request, it reports <code>ECUM_RUNSTATUS_REQUESTED</code> <a class="spec-record-ref" data-req="SWS_EcuM_04144" href="../../spec/record.html?id=SWS_EcuM_04144">[SWS_EcuM_04144]</a>.</li>
<li>Upon release of the last request, it reports <code>ECUM_RUNSTATUS_RELEASED</code> <a class="spec-record-ref" data-req="SWS_EcuM_04117" href="../../spec/record.html?id=SWS_EcuM_04117">[SWS_EcuM_04117]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04119" href="../../spec/record.html?id=SWS_EcuM_04119">[SWS_EcuM_04119]</a>.</li>
</ul>
<p>Thereupon, BswM sets the new state with <code>EcuM_SetState</code> <a class="spec-record-ref" data-req="SWS_EcuM_04122" href="../../spec/record.html?id=SWS_EcuM_04122">[SWS_EcuM_04122]</a>. The EcuM forwards the mode via the port <code>currentMode</code> to the RTE <a class="spec-record-ref" data-req="SWS_EcuM_04133" href="../../spec/record.html?id=SWS_EcuM_04133">[SWS_EcuM_04133]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04107" href="../../spec/record.html?id=SWS_EcuM_04107">[SWS_EcuM_04107]</a>. Following feedback from the RTE, it reports the state to BswM with <code>BswM_EcuM_CurrentState</code> <a class="spec-record-ref" data-req="SWS_EcuM_04143" href="../../spec/record.html?id=SWS_EcuM_04143">[SWS_EcuM_04143]</a>. Example rules for BswM are contained in the <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_1_3_Shutdown_and_Sleep.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_1_3_Shutdown_and_Sleep">Mode-Mgmt-Guide p. 34</a>.</p>
<p>As long as the OS is running, <code>EcuM_MainFunction</code> handles the ongoing tasks of the EcuM <a class="spec-record-ref" data-req="SWS_EcuM_02837" href="../../spec/record.html?id=SWS_EcuM_02837">[SWS_EcuM_02837]</a>. These include wakeup validation <a class="spec-record-ref" data-req="SWS_EcuM_02539" href="../../spec/record.html?id=SWS_EcuM_02539">[SWS_EcuM_02539]</a> and, if configured, the wakeup timer <a class="spec-record-ref" data-req="SWS_EcuM_04002" href="../../spec/record.html?id=SWS_EcuM_04002">[SWS_EcuM_04002]</a>.</p>

<h4>Shutdown targets and shutdown to OFF or RESET</h4>
<p>Shutdown targets are states in which no code is executed: Off, Sleep, and Reset (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_7_Shutdown_Targets.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_7_Shutdown_Targets">SWS EcuM p. 66</a>, <a class="spec-record-ref" data-req="SWS_EcuM_04136" href="../../spec/record.html?id=SWS_EcuM_04136">[SWS_EcuM_04136]</a>). <code>EcuM_SelectShutdownTarget</code> merely stores the target and initiates nothing on its own <a class="spec-record-ref" data-req="SWS_EcuM_02585" href="../../spec/record.html?id=SWS_EcuM_02585">[SWS_EcuM_02585]</a>. The mode parameter applies only to SLEEP and RESET <a class="spec-record-ref" data-req="SWS_EcuM_02979" href="../../spec/record.html?id=SWS_EcuM_02979">[SWS_EcuM_02979]</a>. Available reset modalities are at least <code>Mcu_PerformReset</code>, <code>WdgM_PerformReset</code>, and toggling an I/O pin <a class="spec-record-ref" data-req="SWS_EcuM_04005" href="../../spec/record.html?id=SWS_EcuM_04005">[SWS_EcuM_04005]</a>. Additionally, a shutdown cause can be recorded <a class="spec-record-ref" data-req="SWS_EcuM_04050" href="../../spec/record.html?id=SWS_EcuM_04050">[SWS_EcuM_04050]</a>.</p>

<p class="diagram-note">State diagram: The lifecycle passes through the phases STARTUP, UP, SLEEP, and SHUTDOWN. From SLEEP, a wakeup event leads back to UP, whereas a reset leads to STARTUP. Sources: <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_FIGURE_Figure_7_17.html" data-snip="SNIP_CLASSIC_ECUM_FIGURE_Figure_7_17">SWS EcuM p. 71</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_7_5_SLEEP_Phase.html" data-snip="SNIP_CLASSIC_STD_SECTION_7_5_SLEEP_Phase">SWS EcuM p. 54</a>, <a class="spec-record-ref" data-req="SWS_EcuM_02963" href="../../spec/record.html?id=SWS_EcuM_02963">[SWS_EcuM_02963]</a>, <a class="spec-record-ref" data-req="SWS_EcuM_04001" href="../../spec/record.html?id=SWS_EcuM_04001">[SWS_EcuM_04001]</a></p>
<p>Entry into SHUTDOWN is controlled by BswM. It is likely to occur via <code>EcuM_GoDownHaltPoll</code> as well, since the synchronization diagram mentions this call by BswM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_FIGURE_Figure_7_18.html" data-snip="SNIP_CLASSIC_ECUM_FIGURE_Figure_7_18">SWS EcuM p. 74</a>, <a class="spec-record-ref" data-req="SWS_EcuM_91002" href="../../spec/record.html?id=SWS_EcuM_91002">[SWS_EcuM_91002]</a>). The OffPreOS sequence calls <code>EcuM_OnGoOffOne</code> <a class="spec-record-ref" data-req="SWS_EcuM_02916" href="../../spec/record.html?id=SWS_EcuM_02916">[SWS_EcuM_02916]</a> and deinitializes BswM and SchM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_9_6_1_Master_Core_SHUTDOWN.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_9_6_1_Master_Core_SHUTDOWN">SWS EcuM p. 90</a>). As the last step, it calls <code>ShutdownOS</code> <a class="spec-record-ref" data-req="SWS_EcuM_02952" href="../../spec/record.html?id=SWS_EcuM_02952">[SWS_EcuM_02952]</a>. If a wakeup event occurs during this process, the EcuM must terminate shutdown and restart immediately <a class="spec-record-ref" data-req="SWS_EcuM_02756" href="../../spec/record.html?id=SWS_EcuM_02756">[SWS_EcuM_02756]</a>. Presumably, this occurs by switching the target to RESET.</p>
<p>The shutdown hook calls <code>EcuM_Shutdown</code>, which does not return <a class="spec-record-ref" data-req="SWS_EcuM_02953" href="../../spec/record.html?id=SWS_EcuM_02953">[SWS_EcuM_02953]</a>. The OffPostOS sequence follows: <code>EcuM_OnGoOffTwo</code>, then depending on the target <code>EcuM_AL_Reset</code> or <code>EcuM_AL_SwitchOff</code> <a class="spec-record-ref" data-req="SWS_EcuM_04074" href="../../spec/record.html?id=SWS_EcuM_04074">[SWS_EcuM_04074]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04075" href="../../spec/record.html?id=SWS_EcuM_04075">[SWS_EcuM_04075]</a>. If the reset mode originates from a <code>EcuM_ShutdownModeType</code>, it must be shifted right by one byte prior to handover (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_8_5_3_4_EcuM_AL_Reset.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_8_5_3_4_EcuM_AL_Reset">SWS EcuM p. 142</a>).</p>

<h4>Sleep phase: GoSleep, Halt or Poll, WakeupRestart</h4>
<p><code>EcuM_GoDownHaltPoll</code> with target SLEEP first starts the GoSleep sequence. Thereafter, depending on <code>EcuMSleepModeSuspend</code>, the Halt or the Poll sequence follows (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_7_5_SLEEP_Phase.html" data-snip="SNIP_CLASSIC_STD_SECTION_7_5_SLEEP_Phase">SWS EcuM p. 54</a>). The OS remains active in this phase <a class="spec-record-ref" data-req="SWS_EcuM_02951" href="../../spec/record.html?id=SWS_EcuM_02951">[SWS_EcuM_02951]</a>. GoSleep arms the wakeup sources configured for the sleep mode <a class="spec-record-ref" data-req="SWS_EcuM_02389" href="../../spec/record.html?id=SWS_EcuM_02389">[SWS_EcuM_02389]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02546" href="../../spec/record.html?id=SWS_EcuM_02546">[SWS_EcuM_02546]</a> and allocates the resource <code>RES_AUTOSAR_ECUM</code> per core <a class="spec-record-ref" data-req="SWS_EcuM_03010" href="../../spec/record.html?id=SWS_EcuM_03010">[SWS_EcuM_03010]</a>. If a wakeup event occurs already during GoSleep, Halt and Poll must no longer be entered <a class="spec-record-ref" data-req="SWS_EcuM_02188" href="../../spec/record.html?id=SWS_EcuM_02188">[SWS_EcuM_02188]</a>.</p>
<p>The two sleep variants differ as follows:</p>
<ul>
<li><strong>Halt:</strong> The microcontroller is halted, no code is executed <a class="spec-record-ref" data-req="SWS_EcuM_02960" href="../../spec/record.html?id=SWS_EcuM_02960">[SWS_EcuM_02960]</a>. Beforehand, <code>EcuM_GenerateRamHash</code> calculates a checksum over the RAM; after waking up, <code>EcuM_CheckRamHash</code> verifies it. In case of multiple cores, this occurs only on the master <a class="spec-record-ref" data-req="SWS_EcuM_02863" href="../../spec/record.html?id=SWS_EcuM_02863">[SWS_EcuM_02863]</a>.</li>
<li><strong>Poll:</strong> The controller continues to execute code <a class="spec-record-ref" data-req="SWS_EcuM_02962" href="../../spec/record.html?id=SWS_EcuM_02962">[SWS_EcuM_02962]</a>. In R20-11, the EcuM calls <code>EcuM_SleepActivity</code> and the callout <code>EcuM_CheckWakeup</code> in a blocking loop until a wakeup event is present <a class="spec-record-ref" data-req="SWS_EcuM_03020" href="../../spec/record.html?id=SWS_EcuM_03020">[SWS_EcuM_03020]</a>. Starting with R21-11, this callout is named <code>EcuM_CheckWakeupHook</code>, and <code>EcuM_CheckWakeup</code> becomes an EcuM function (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_8_5_4_5_EcuM_CheckWakeupHook.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_8_5_4_5_EcuM_CheckWakeupHook">SWS EcuM p. 145</a>).</li>
</ul>

<h4>Wakeup sources: bitmask, states, and validation protocol</h4>
<p>The EcuM manages up to 32 wakeup sources as bits in <code>EcuM_WakeupSourceType</code>. Five positions are predefined (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_6_3_Internal_Representation_of_Wakeup_States.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_6_3_Internal_Representation_of_Wakeup_States">SWS EcuM p. 63</a>, <a class="spec-record-ref" data-req="SWS_EcuM_04040" href="../../spec/record.html?id=SWS_EcuM_04040">[SWS_EcuM_04040]</a>). Further sources occupy bits 5 to 31 via <code>EcuMWakeupSourceId</code> <a class="spec-record-ref" data-req="SWS_EcuM_02165" href="../../spec/record.html?id=SWS_EcuM_02165">[SWS_EcuM_02165]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02166" href="../../spec/record.html?id=SWS_EcuM_02166">[SWS_EcuM_02166]</a>. Each source is in one of four states: NONE, PENDING, VALIDATED, or EXPIRED <a class="spec-record-ref" data-req="SWS_EcuM_04091" href="../../spec/record.html?id=SWS_EcuM_04091">[SWS_EcuM_04091]</a>. The EcuM reports every state change as a mode request to BswM <a class="spec-record-ref" data-req="SWS_EcuM_04003" href="../../spec/record.html?id=SWS_EcuM_04003">[SWS_EcuM_04003]</a>.</p>

<p class="diagram-note">State diagram: A source without validation requirement transitions directly to VALIDATED. All others wait in PENDING for confirmation or time out into EXPIRED. Sources: <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-407eea1386f12f08.html" data-snip="FIG-407eea1386f12f08">SWS EcuM p. 60</a>, <a class="spec-record-ref" data-req="SWS_EcuM_04091" href="../../spec/record.html?id=SWS_EcuM_04091">[SWS_EcuM_04091]</a>, <a class="spec-record-ref" data-req="SWS_EcuM_02566" href="../../spec/record.html?id=SWS_EcuM_02566">[SWS_EcuM_02566]</a>, <a class="spec-record-ref" data-req="SWS_EcuM_02683" href="../../spec/record.html?id=SWS_EcuM_02683">[SWS_EcuM_02683]</a></p>
<p>A driver reports a detected event once with <code>EcuM_SetWakeupEvent</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_6_4_4_Requirements_for_Drivers_with_Wakeup_Sources.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_6_4_4_Requirements_for_Drivers_with_Wakeup_Sources">SWS EcuM p. 71</a>). This is permitted from interrupts as well <a class="spec-record-ref" data-req="SWS_EcuM_02171" href="../../spec/record.html?id=SWS_EcuM_02171">[SWS_EcuM_02171]</a>. The function sets the pending bit <a class="spec-record-ref" data-req="SWS_EcuM_01117" href="../../spec/record.html?id=SWS_EcuM_01117">[SWS_EcuM_01117]</a> and ignores sources that do not belong to the selected sleep mode <a class="spec-record-ref" data-req="SWS_EcuM_04138" href="../../spec/record.html?id=SWS_EcuM_04138">[SWS_EcuM_04138]</a>. In addition, it starts the validation timer, but not again upon repeated calls for the same source <a class="spec-record-ref" data-req="SWS_EcuM_02709" href="../../spec/record.html?id=SWS_EcuM_02709">[SWS_EcuM_02709]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02712" href="../../spec/record.html?id=SWS_EcuM_02712">[SWS_EcuM_02712]</a>. If no validation is configured for a source, the event is considered validated immediately <a class="spec-record-ref" data-req="SWS_EcuM_02566" href="../../spec/record.html?id=SWS_EcuM_02566">[SWS_EcuM_02566]</a>. Reset and power sources are never validated <a class="spec-record-ref" data-req="SWS_EcuM_02625" href="../../spec/record.html?id=SWS_EcuM_02625">[SWS_EcuM_02625]</a>.</p>
<p>Validation runs in <code>EcuM_MainFunction</code> <a class="spec-record-ref" data-req="SWS_EcuM_02539" href="../../spec/record.html?id=SWS_EcuM_02539">[SWS_EcuM_02539]</a> and follows this protocol:</p>
<ul>
<li><code>EcuM_StartWakeupSources</code> prepares the sources, <code>EcuM_CheckValidation</code> subsequently queries them <a class="spec-record-ref" data-req="SWS_EcuM_02924" href="../../spec/record.html?id=SWS_EcuM_02924">[SWS_EcuM_02924]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02925" href="../../spec/record.html?id=SWS_EcuM_02925">[SWS_EcuM_02925]</a>.</li>
<li>If validation succeeds, the validating module calls <code>EcuM_ValidateWakeupEvent</code>. The EcuM then stops the timer, sets the validated bit, reports VALIDATED to BswM, and informs ComM <a class="spec-record-ref" data-req="SWS_EcuM_04078" href="../../spec/record.html?id=SWS_EcuM_04078">[SWS_EcuM_04078]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02710" href="../../spec/record.html?id=SWS_EcuM_02710">[SWS_EcuM_02710]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04079" href="../../spec/record.html?id=SWS_EcuM_04079">[SWS_EcuM_04079]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02645" href="../../spec/record.html?id=SWS_EcuM_02645">[SWS_EcuM_02645]</a>.</li>
<li>If the timer expires, the EcuM sets the expired bit, reports EXPIRED to BswM, and calls <code>EcuM_StopWakeupSources</code> <a class="spec-record-ref" data-req="SWS_EcuM_04081" href="../../spec/record.html?id=SWS_EcuM_04081">[SWS_EcuM_04081]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04082" href="../../spec/record.html?id=SWS_EcuM_04082">[SWS_EcuM_04082]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02926" href="../../spec/record.html?id=SWS_EcuM_02926">[SWS_EcuM_02926]</a>.</li>
<li>In the RUN state, validation is effective only for communication channels <a class="spec-record-ref" data-req="SWS_EcuM_02790" href="../../spec/record.html?id=SWS_EcuM_02790">[SWS_EcuM_02790]</a>.</li>
<li><code>EcuM_ClearWakeupEvent</code> clears the bits in all three internal variables <a class="spec-record-ref" data-req="SWS_EcuM_02683" href="../../spec/record.html?id=SWS_EcuM_02683">[SWS_EcuM_02683]</a>.</li>
<li>A running CheckWakeupTimer prevents shutdown before a source has been checked <a class="spec-record-ref" data-req="SWS_EcuM_04096" href="../../spec/record.html?id=SWS_EcuM_04096">[SWS_EcuM_04096]</a>. <code>EcuM_SetWakeupEvent</code> cancels it <a class="spec-record-ref" data-req="SWS_EcuM_04098" href="../../spec/record.html?id=SWS_EcuM_04098">[SWS_EcuM_04098]</a>.</li>
</ul>

<h4>Multicore operation, wakeup timer, and boot target</h4>
<p>On multicore ECUs, one EcuM instance runs per core. The master EcuM starts the remaining cores (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_FIGURE_Figure_7_17.html" data-snip="SNIP_CLASSIC_ECUM_FIGURE_Figure_7_17">SWS EcuM p. 71</a>). For each instance:</p>
<ul>
<li>The init callouts initialize only the MCAL modules of their own core <a class="spec-record-ref" data-req="SWS_EcuM_04145" href="../../spec/record.html?id=SWS_EcuM_04145">[SWS_EcuM_04145]</a>.</li>
<li>OS and SchM are started on each core <a class="spec-record-ref" data-req="SWS_EcuM_04093" href="../../spec/record.html?id=SWS_EcuM_04093">[SWS_EcuM_04093]</a>.</li>
<li>Each instance processes the wakeup events of its core <a class="spec-record-ref" data-req="SWS_EcuM_04012" href="../../spec/record.html?id=SWS_EcuM_04012">[SWS_EcuM_04012]</a>.</li>
<li>The SLEEP target puts all cores to sleep <a class="spec-record-ref" data-req="SWS_EcuM_04092" href="../../spec/record.html?id=SWS_EcuM_04092">[SWS_EcuM_04092]</a>.</li>
</ul>
<p>The optional wakeup timer counts seconds since the battery was connected <a class="spec-record-ref" data-req="SWS_EcuM_04069" href="../../spec/record.html?id=SWS_EcuM_04069">[SWS_EcuM_04069]</a>. Each user has at most one alarm <a class="spec-record-ref" data-req="SWS_EcuM_04070" href="../../spec/record.html?id=SWS_EcuM_04070">[SWS_EcuM_04070]</a>, and the master alarm follows the earliest user alarm <a class="spec-record-ref" data-req="SWS_EcuM_04072" href="../../spec/record.html?id=SWS_EcuM_04072">[SWS_EcuM_04072]</a>. A later alarm returns <code>ECUM_E_EARLIER_ACTIVE</code>, a past point in time <code>ECUM_E_PAST</code> <a class="spec-record-ref" data-req="SWS_EcuM_04059" href="../../spec/record.html?id=SWS_EcuM_04059">[SWS_EcuM_04059]</a> <a class="spec-record-ref" data-req="SWS_EcuM_04060" href="../../spec/record.html?id=SWS_EcuM_04060">[SWS_EcuM_04060]</a>. When alarms are cleared is governed by <a class="spec-record-ref" data-req="SWS_EcuM_04010" href="../../spec/record.html?id=SWS_EcuM_04010">[SWS_EcuM_04010]</a>. <code>EcuM_SelectBootTarget</code> stores the boot target so that the bootloader can read it <a class="spec-record-ref" data-req="SWS_EcuM_02247" href="../../spec/record.html?id=SWS_EcuM_02247">[SWS_EcuM_02247]</a>.</p>

<h4>Behavior in the event of an error</h4>
<p><strong>Unrecoverable errors:</strong> Here, the EcuM calls <code>EcuM_ErrorHook</code> <a class="spec-record-ref" data-req="SWS_EcuM_04033" href="../../spec/record.html?id=SWS_EcuM_04033">[SWS_EcuM_04033]</a>, specifically with <code>ECUM_E_CONFIGURATION_DATA_INCONSISTENT</code> or <code>ECUM_E_RAM_CHECK_FAILED</code> <a class="spec-record-ref" data-req="SWS_EcuM_91003" href="../../spec/record.html?id=SWS_EcuM_91003">[SWS_EcuM_91003]</a> <a class="spec-record-ref" data-req="SWS_EcuM_02987" href="../../spec/record.html?id=SWS_EcuM_02987">[SWS_EcuM_02987]</a>.</p>
<p><strong>Failed OS calls:</strong> According to R20-11, the state remains unchanged, and the EcuM reports the error via the ErrorHook <a class="spec-record-ref" data-req="SWS_EcuM_04139" href="../../spec/record.html?id=SWS_EcuM_04139">[SWS_EcuM_04139]</a>. The dedicated code <code>ECUM_E_OS_CALL_FAILED</code> and the assumption that the hook does not return are first mentioned in a later release (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_12_ErrorHook.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_12_ErrorHook">SWS EcuM p. 102</a>).</p>
<p><strong>Further rules:</strong></p>
<ul>
<li>The EcuM ignores errors during initialization <a class="spec-record-ref" data-req="SWS_EcuM_02980" href="../../spec/record.html?id=SWS_EcuM_02980">[SWS_EcuM_02980]</a>.</li>
<li>It maps an unknown reset reason to <code>ECUM_WKSOURCE_RESET</code> <a class="spec-record-ref" data-req="SWS_EcuM_02601" href="../../spec/record.html?id=SWS_EcuM_02601">[SWS_EcuM_02601]</a>.</li>
<li>A reset or power cycle during Halt or Poll leads back to STARTUP <a class="spec-record-ref" data-req="SWS_EcuM_04001" href="../../spec/record.html?id=SWS_EcuM_04001">[SWS_EcuM_04001]</a>.</li>
<li>If the ECU cannot de-energize itself in <code>EcuM_AL_SwitchOff</code>, a reset is the appropriate reaction. The integrator is permitted to limit the endless loop (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_8_5_3_3_EcuM_AL_SwitchOff.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_8_5_3_3_EcuM_AL_SwitchOff">SWS EcuM p. 141</a>).</li>
