<h4>Context</h4>
<p>The namespace <code>ara::com::e2e</code> provides data types, status enumerations, and error handling mechanisms for End-to-End protection (E2E) in the AUTOSAR Adaptive Platform. Its primary responsibility lies in providing standardized interfaces for evaluating the E2E integrity of transmitted data, as well as for reporting and handling transport-related error conditions in service-oriented communication.</p>
<p>The central interaction partners include skeleton and proxy instances of the communication layer as well as application-side error handling routines. On the server side, the interface enables the registration of an application-specific handler of type <code>TransportFaultConditionHandler</code> <a class="spec-record-ref" data-req="SWS_CM_00092" href="../spec/record.html?id=SWS_CM_00092">[SWS_CM_00092]</a> for all methods of a skeleton <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=68">AUTOSAR_AP_EXP_SWArchitecture p. 68</a> and dedicatedly for skeleton fields (Field Get/Set) <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=69">AUTOSAR_AP_EXP_SWArchitecture p. 69</a>. If a fault occurs in the transport channel, Communication Management notifies the registered handler, specifying the concrete error condition <code>TransportFaultCondition</code> <a class="spec-record-ref" data-req="SWS_CM_00091" href="../spec/record.html?id=SWS_CM_00091">[SWS_CM_00091]</a>.</p>

<h4>Usage Path</h4>
<p>The typical usage path when processing incoming event samples comprises a two-stage validation consisting of individual sample check and state monitoring:</p>
<ol>
<li><strong>Individual sample check:</strong> Upon receiving a sample, the result of the E2E profile check for the respective <code>ara::com::SamplePtr</code> is first evaluated via <code>ProfileCheckStatus</code> <a class="spec-record-ref" data-req="SWS_CM_90421" href="../spec/record.html?id=SWS_CM_90421">[SWS_CM_90421]</a>. In this process, checksums, data lengths, and counter values are analyzed. If the check is active and successful, the query returns the status <code>ProfileCheckStatus::kOk</code> <a class="spec-record-ref" data-req="SWS_CM_90421" href="../spec/record.html?id=SWS_CM_90421">[SWS_CM_90421]</a>.</li>
<li><strong>State check of the state machine:</strong> Subsequently, the higher-level state of the E2E monitoring state machine is checked using <code>SMState</code> <a class="spec-record-ref" data-req="SWS_CM_90422" href="../spec/record.html?id=SWS_CM_90422">[SWS_CM_90422]</a>. Only when <code>SMState::kValid</code> is present and the individual check <code>ProfileCheckStatus</code> has yielded no error may the checked sample be consumed and further processed by the application <a class="spec-record-ref" data-req="SWS_CM_90422" href="../spec/record.html?id=SWS_CM_90422">[SWS_CM_90422]</a>.</li>
<li><strong>Error registration on the skeleton:</strong> In parallel, a service provider registers a <code>TransportFaultConditionHandler</code> on the skeleton for methods <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=68">AUTOSAR_AP_EXP_SWArchitecture p. 68</a> or field accesses <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=69">AUTOSAR_AP_EXP_SWArchitecture p. 69</a> during initialization. Handlers that are no longer required can be deregistered again later <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=68">AUTOSAR_AP_EXP_SWArchitecture p. 68</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_SWArchitecture&amp;page=69">AUTOSAR_AP_EXP_SWArchitecture p. 69</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>In the event of an error, the namespace differentiates between protocol-related E2E check errors, states of the monitoring state machine, and transport-related errors:</p>
<ul>
<li><strong>E2E error codes (<code>ComE2EErrc</code>):</strong> Erroneous checks or incorrect counter sequences are mapped via the enumeration <code>ComE2EErrc</code> <a class="spec-record-ref" data-req="SWS_CM_10474" href="../spec/record.html?id=SWS_CM_10474">[SWS_CM_10474]</a>. These include repeated counters (<code>kRepeated</code>), invalid counter jumps (<code>kWrongSequence</code>), checksum or length errors (<code>kError</code>), the absence of new data (<code>kNoNewData</code>), and unspecified errors of remote services (<code>kUnspecifiedE2EError</code>) <a class="spec-record-ref" data-req="SWS_CM_10474" href="../spec/record.html?id=SWS_CM_10474">[SWS_CM_10474]</a>. For integration into the platform-wide error model, <code>GetComE2EErrorDomain()</code> provides a reference to the <code>ComE2EErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_12510" href="../spec/record.html?id=SWS_CM_12510">[SWS_CM_12510]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=9">AUTOSAR_AP_EXP_ARAComAPI p. 9</a>, while <code>MakeErrorCode()</code> generates standardized error codes <a class="spec-record-ref" data-req="SWS_CM_12511" href="../spec/record.html?id=SWS_CM_12511">[SWS_CM_12511]</a>. For exception handling, the exception class <code>ComE2EException</code> exists.</li>
<li><strong>State errors of the E2E monitoring (<code>SMState</code>):</strong> If the state machine after evaluation is not in the status <code>kValid</code>, but in the states <code>kInit</code> (not yet sufficient error-free data since initialization), <code>kInvalid</code> (too many erroneous or too few valid transmissions within the time window), or <code>kNoData</code>, the data must not be used <a class="spec-record-ref" data-req="SWS_CM_90422" href="../spec/record.html?id=SWS_CM_90422">[SWS_CM_90422]</a>. In the case of incompatible Quality of Service parameters, the state <code>kIncompatibleQoS</code> is signaled <a class="spec-record-ref" data-req="SWS_CM_90422" href="../spec/record.html?id=SWS_CM_90422">[SWS_CM_90422]</a>.</li>
<li><strong>Transport-related fault conditions (<code>TransportFaultCondition</code>):</strong> If a resource shortage occurs at layer 4 or higher, <code>kSampleRejected</code> is reported <a class="spec-record-ref" data-req="SWS_CM_00091" href="../spec/record.html?id=SWS_CM_00091">[SWS_CM_00091]</a>. When configured timeouts are exceeded, the system reports <code>kDeadlineMissed</code>, and when gaps in the packet sequence are detected, <code>kSampleLost</code> is reported <a class="spec-record-ref" data-req="SWS_CM_00091" href="../spec/record.html?id=SWS_CM_00091">[SWS_CM_00091]</a>. These conditions are passed to the application via the registered <code>TransportFaultConditionHandler</code> together with the number of occurred errors <a class="spec-record-ref" data-req="SWS_CM_00092" href="../spec/record.html?id=SWS_CM_00092">[SWS_CM_00092]</a>.</li>
</ul>
