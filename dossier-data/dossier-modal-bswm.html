<h4>Role of the BswM: Arbiter for the Basic Software Modes</h4>
<p>In the ECU, mode requests converge at the BSW Mode Manager (BswM), and it translates them into actions. It arbitrates based on incoming mode indications <a class="spec-record-ref" data-req="SWS_BswM_00035" href="../../spec/record.html?id=SWS_BswM_00035">[SWS_BswM_00035]</a>. The specification distinguishes between two types of inputs (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_3_Requirements_of_Mode_Arbitration.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_3_Requirements_of_Mode_Arbitration">SWS BswM p. 26</a>):</p>
<ul>
<li>Mode requests usually come from application SW-Cs, occasionally also from BSW modules such as the DCM.</li>
<li>Mode indications always come from BSW modules, such as the bus-specific state managers or the EcuM.</li>
</ul>
<p>In the component model, the BswM is a Service Component that only serves mode requests of its own ECU (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_6_4_Component_Type_and_Internal_Behavior.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_6_4_Component_Type_and_Internal_Behavior">SWS BswM p. 48</a>).</p>
<p>The BswM takes effect via actions. In principle, it is allowed to call any function of the AUTOSAR BSW (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_8_6_2_Optional_Interfaces_BSWMODEMANAGER.html" data-snip="SNIP_CLASSIC_COMM_SECTION_8_6_2_Optional_Interfaces_BSWMODEMANAGER">SWS BswM p. 92</a>). The specification mentions, among others, <code>Com_IpduGroupStart</code>, <code>Com_IpduGroupStop</code>, and <code>Com_EnableReceptionDM</code> <a class="spec-record-ref" data-req="SWS_BswM_00008" href="../../spec/record.html?id=SWS_BswM_00008">[SWS_BswM_00008]</a> as optional interfaces. In addition, the BswM can execute user callouts <a class="spec-record-ref" data-req="SWS_BswM_00270" href="../../spec/record.html?id=SWS_BswM_00270">[SWS_BswM_00270]</a>. Their parameters are defined at configuration time in the container <code>BswMUserCallout</code> <a class="spec-record-ref" data-req="SWS_BswM_00054" href="../../spec/record.html?id=SWS_BswM_00054">[SWS_BswM_00054]</a>. The BswM has no mandatory interfaces to other modules <a class="spec-record-ref" data-req="SWS_BswM_00007" href="../../spec/record.html?id=SWS_BswM_00007">[SWS_BswM_00007]</a>.</p>

<h4>Inputs: Indications, Requests, and Events</h4>
<p>For BSW modules, the BswM provides a C API for each source. Internally, it maps each call to a Mode Request Port (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_1_Interface_of_the_BSWM.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_1_Interface_of_the_BSWM">Guide Modemanagement p. 18</a>). For this purpose, the mapping table links an API parameter with a configuration reference in each case (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_8_API_to_Request_Port_Mappings.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_8_API_to_Request_Port_Mappings">SWS BswM p. 87</a>). An example: <code>BswM_CanSM_CurrentState</code> is mapped to the source <code>BswMCanSMIndication</code> via the pair <code>Network</code> / <code>BswMCanSMChannelRef</code> <a class="spec-record-ref" data-req="SWS_BswM_00049" href="../../spec/record.html?id=SWS_BswM_00049">[SWS_BswM_00049]</a>. This source is created once per CAN channel (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_3_2_2_2_4_BswMCanSMIndication.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_3_2_2_2_4_BswMCanSMIndication">Guide Modemanagement p. 24</a>).</p>
<p>The reporting APIs by origin:</p>
<ul>
<li><strong>Bus State Manager:</strong> CanSM, LinSM, FrSM, and EthSM report their state (<a class="spec-record-ref" data-req="SWS_BswM_00049" href="../../spec/record.html?id=SWS_BswM_00049">[SWS_BswM_00049]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00052" href="../../spec/record.html?id=SWS_BswM_00052">[SWS_BswM_00052]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00051" href="../../spec/record.html?id=SWS_BswM_00051">[SWS_BswM_00051]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00050" href="../../spec/record.html?id=SWS_BswM_00050">[SWS_BswM_00050]</a>). LinSM also reports the active schedule table <a class="spec-record-ref" data-req="SWS_BswM_00058" href="../../spec/record.html?id=SWS_BswM_00058">[SWS_BswM_00058]</a>, and LinTp requests a LIN TP mode <a class="spec-record-ref" data-req="SWS_BswM_00156" href="../../spec/record.html?id=SWS_BswM_00156">[SWS_BswM_00156]</a>.</li>
<li><strong>ComM:</strong> reports channel modes <a class="spec-record-ref" data-req="SWS_BswM_00047" href="../../spec/record.html?id=SWS_BswM_00047">[SWS_BswM_00047]</a> and PNC modes <a class="spec-record-ref" data-req="SWS_BswM_00148" href="../../spec/record.html?id=SWS_BswM_00148">[SWS_BswM_00148]</a> and signals a shutdown via <code>BswM_ComM_InitiateReset</code> <a class="spec-record-ref" data-req="SWS_BswM_00217" href="../../spec/record.html?id=SWS_BswM_00217">[SWS_BswM_00217]</a>.</li>
<li><strong>Network Management:</strong> Nm and J1939Nm report state changes (<a class="spec-record-ref" data-req="SWS_BswM_91002" href="../../spec/record.html?id=SWS_BswM_91002">[SWS_BswM_91002]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00194" href="../../spec/record.html?id=SWS_BswM_00194">[SWS_BswM_00194]</a>). </ul>
<p>If a BSW module does not have its own request interface, it uses the generic call <code>BswM_RequestMode</code> with the types <code>BswM_UserType</code> and <code>BswM_ModeType</code> (<a class="spec-record-ref" data-req="SWS_BswM_00046" href="../../spec/record.html?id=SWS_BswM_00046">[SWS_BswM_00046]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00216" href="../../spec/record.html?id=SWS_BswM_00216">[SWS_BswM_00216]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00214" href="../../spec/record.html?id=SWS_BswM_00214">[SWS_BswM_00214]</a>). SW-Cs reach the BswM via three port types:</p>
<ul>
<li><code>modeRequestPort</code>: Required Port for mode requests <a class="spec-record-ref" data-req="SWS_BswM_00201" href="../../spec/record.html?id=SWS_BswM_00201">[SWS_BswM_00201]</a>.</li>
<li><code>modeNotificationPort</code>: Required Port via which the BswM receives observed mode switches <a class="spec-record-ref" data-req="SWS_BswM_00200" href="../../spec/record.html?id=SWS_BswM_00200">[SWS_BswM_00200]</a>.</li>
<li><code>modeSwitchPort</code>: Provided Port via which the BswM itself switches modes <a class="spec-record-ref" data-req="SWS_BswM_00202" href="../../spec/record.html?id=SWS_BswM_00202">[SWS_BswM_00202]</a>.</li>
</ul>
<p>Events such as <code>BswM_ComM_InitiateReset</code> are configured as <code>BswMEventRequestPort</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_10_2_9_BswMEventRequestPort.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_10_2_9_BswMEventRequestPort">SWS BswM p. 102</a>). The arbitration considers both the occurrence of an event and its clearing (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_3_Requirements_of_Mode_Arbitration.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_3_Requirements_of_Mode_Arbitration">SWS BswM p. 26</a>).</p>
<p><strong>Release Reference R20-11:</strong> According to the change history (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_General_Overview">SWS BswM p. 2</a>), R20-11 introduced the following changes:</p>
<ul>
<li>Reintroduction of <code>BswM_EcuM_CurrentState</code> <a class="spec-record-ref" data-req="SWS_BswM_91003" href="../../spec/record.html?id=SWS_BswM_91003">[SWS_BswM_91003]</a> and <code>BswM_EcuM_RequestedState</code> <a class="spec-record-ref" data-req="SWS_BswM_91004" href="../../spec/record.html?id=SWS_BswM_91004">[SWS_BswM_91004]</a>.</li>
<li>Support for Ethernet switch port groups.</li>
<li>New action <code>BswMEthIfStartAllPorts</code> <a class="spec-record-ref" data-req="SWS_BswM_00286" href="../../spec/record.html?id=SWS_BswM_00286">[SWS_BswM_00286]</a>.</li>

</ul>
<p>Two later changes do not yet affect R20-11: <code>BswM_WdgM_RequestPartitionReset</code> <a class="spec-record-ref" data-req="SWS_BswM_00157" href="../../spec/record.html?id=SWS_BswM_00157">[SWS_BswM_00157]</a> was only marked as obsolete with R21-11, and the SoAd mode request was only added with R21-11 (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_General_Overview">SWS BswM p. 2</a>).</p>

<h4>Rules, Action Lists, and Evaluation Timing</h4>
<p>The behavior of the BswM is configured via rules and action lists (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior">Guide Modemanagement p. 32</a>):</p>
<ul>
<li>A rule is a logical expression over the current values of the Mode Request Ports.</li>
<li>Depending on the result, the BswM executes the True or the False action list.</li>
<li>An action list contains atomic actions, nested action lists, or references to further rules.</li>
</ul>
<p>Actions may only be called within the context of an action list <a class="spec-record-ref" data-req="SWS_BswM_00147" href="../../spec/record.html?id=SWS_BswM_00147">[SWS_BswM_00147]</a>.</p>
<p>When a rule is evaluated is determined by the parameter <code>BswMRequestProcessing</code> for each port:</p>
<ul>
<li><strong>IMMEDIATE:</strong> All rules that reference the port are evaluated immediately (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior">Guide Modemanagement p. 32</a>). For SW-C requests, the RTE must trigger an arbitration runnable via a <code>DataReceiveEvent</code> for this purpose (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_6_4_Component_Type_and_Internal_Behavior.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_6_4_Component_Type_and_Internal_Behavior">SWS BswM p. 48</a>).</li>
<li><strong>BSWM_DEFERRED:</strong> The rules are evaluated in <code>BswM_MainFunction</code> <a class="spec-record-ref" data-req="SWS_BswM_00053" href="../../spec/record.html?id=SWS_BswM_00053">[SWS_BswM_00053]</a> <a class="spec-record-ref" data-req="SWS_BswM_00075" href="../../spec/record.html?id=SWS_BswM_00075">[SWS_BswM_00075]</a>.</li>
</ul>
<p>Special rules apply to timers. Independent of its configuration, a <code>BswMTimer</code> is always treated as DEFERRED and arbitrated in the main function <a class="spec-record-ref" data-req="SWS_BswM_00220" href="../../spec/record.html?id=SWS_BswM_00220">[SWS_BswM_00220]</a>. In version R23-11, it can only be controlled via the action <code>BswMTimerControl</code>, and its resolution is a multiple of the cycle time of the main function (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_3_Waiting_Functionality.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_3_Waiting_Functionality">SWS BswM p. 37</a>).</p>
<p>Initial values influence which rules are arbitrated at all. If an initial value is missing (<code>BswMModeInitValue</code>), a mode condition is considered undefined until the first update. Rules with undefined conditions are not arbitrated (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_4_Arbitration_Behavior_after_Initialization.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_4_Arbitration_Behavior_after_Initialization">SWS BswM p. 30</a>). This clarification comes from version R23-11. It presumably applies analogously already to R20-11; however, a corresponding R20-11 requirement is not available here.</p>

<h4>Lifecycle and Startup under the Control of the EcuM</h4>
<p><code>BswM_Init</code> <a class="spec-record-ref" data-req="SWS_BswM_00002" href="../../spec/record.html?id=SWS_BswM_00002">[SWS_BswM_00002]</a> initializes all module-global variables. Afterwards, the BswM can arbitrate mode requests. Before the call, only OS and SchM must be initialized (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_3_16_BswM_Init.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_3_16_BswM_Init">SWS BswM p. 69</a>). The passed pointer points to the post-build data in <code>BswM_ConfigType</code> <a class="spec-record-ref" data-req="SWS_BswM_00213" href="../../spec/record.html?id=SWS_BswM_00213">[SWS_BswM_00213]</a>. <code>BswM_Init</code> is "Conditionally Reentrant" because the BswM can be instantiated in multiple partitions (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_3_16_BswM_Init.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_3_16_BswM_Init">SWS BswM p. 69</a>). Therefore, the EcuM calls <code>BswM_Init</code> in a loop for each BswM instance of a core (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_9_5_2_Slave_Core_STARTUP.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_9_5_2_Slave_Core_STARTUP">SWS EcuM p. 83</a>).</p>
<p>In the StartPostOS sequence, the EcuM first starts the BSW scheduler. Afterwards, it initializes the BswM and then concludes the SchM initialization (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ECUM_SECTION_7_3_3_Activities_in_the_StartPostOS_Sequence.html" data-snip="SNIP_CLASSIC_ECUM_SECTION_7_3_3_Activities_in_the_StartPostOS_Sequence">SWS EcuM p. 42</a>). From this point on, the BswM controls the further startup: it ensures that the init routines of the other BSW modules run and the RTE is started (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_2_Startup.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_2_Startup">Guide Modemanagement p. 36</a>). In the example of the guide, this proceeds as follows:</p>
<ol>
<li>A DEFERRED rule triggers <code>NvM_ReadAll</code>.</li>
<li>The NvM reports the completion via <code>BswM_NvM_CurrentJobMode</code> <a class="spec-record-ref" data-req="SWS_BswM_00152" href="../../spec/record.html?id=SWS_BswM_00152">[SWS_BswM_00152]</a>.</li>
<li>A subsequent rule then starts the RTE (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_NVDATAHANDLING_SECTION_4_3_Initialization_of_RAM_Blocks_from_NVRAM.html" data-snip="SNIP_CLASSIC_NVDATAHANDLING_SECTION_4_3_Initialization_of_RAM_Blocks_from_NVRAM">NV-Daten-Leitfaden p. 20</a>).</li>
</ol>

<h4>Interaction with EcuM, Wakeup Sources, and Ethernet Port Groups</h4>
<p>In ECU Mode Handling, the EcuM has no state machine of its own (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_10_EcuM_Mode_Handling.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_10_EcuM_Mode_Handling">SWS EcuM p. 99</a>). It arbitrates the RUN and POST_RUN requests of the SW-Cs and reports the result via <code>BswM_EcuM_RequestedState</code> <a class="spec-record-ref" data-req="SWS_BswM_91004" href="../../spec/record.html?id=SWS_BswM_91004">[SWS_BswM_91004]</a>, because only the BswM decides on transitions. The sequence is a cycle:</p>
<ol>
<li>The BswM sets the state with <code>EcuM_SetState</code>.</li>
<li>The EcuM passes the mode on to the RTE (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_10_EcuM_Mode_Handling.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_10_EcuM_Mode_Handling">SWS EcuM p. 99</a>).</li>
<li>After feedback from the RTE, the EcuM reports the new state to the BswM via <code>BswM_EcuM_CurrentState</code> <a class="spec-record-ref" data-req="SWS_BswM_91003" href="../../spec/record.html?id=SWS_BswM_91003">[SWS_BswM_91003]</a> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_1_ECU_Mode_Handling.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_3_1_ECU_Mode_Handling">Guide Modemanagement p. 34</a>).</li>
</ol>
<p>With this structure, legacy SW-Cs written for the EcuM with a fixed state machine can also continue to be used (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-f372e62ffe0460b6.html" data-snip="FIG-f372e62ffe0460b6">Guide Modemanagement p. 61</a>).</p>

<p>Ethernet switch port groups are new in R20-11. ComM reports the PNC mode via <code>BswM_ComM_CurrentPNCMode</code> <a class="spec-record-ref" data-req="SWS_BswM_00148" href="../../spec/record.html?id=SWS_BswM_00148">[SWS_BswM_00148]</a>. The BswM knows the mapping of PNC to port group and calls <code>EthIf_SwitchPortGroupRequestMode</code> with <code>ETH_MODE_ACTIVE</code> or <code>ETH_MODE_DOWN</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_4_6_Ethernet_switch_port_group_switching.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_4_6_Ethernet_switch_port_group_switching">Guide Modemanagement p. 49</a>). In the opposite direction, EthIf reports the accumulated link state of those port groups that are not assigned to an EthIfController via <code>BswM_EthIf_PortGroupLinkStateChg</code> <a class="spec-record-ref" data-req="SWS_BswM_91001" href="../../spec/record.html?id=SWS_BswM_91001">[SWS_BswM_91001]</a> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_10_1_1_Link_state_accumulation_of_EthIfSwitchPortGroup.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_10_1_1_Link_state_accumulation_of_EthIfSwitchPortGroup">SWS EthIf p. 29</a>). With action <code>BswMEthIfStartAllPorts</code>, the BswM starts all ports via <code>EthIf_StartAllPorts</code> <a class="spec-record-ref" data-req="SWS_BswM_00286" href="../../spec/record.html?id=SWS_BswM_00286">[SWS_BswM_00286]</a>.</p>

<h4>Configuration and instance reference of the request ports</h4>
<p>The configuration tool maps the API parameters to the referenced ECUC containers (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_2_3_Configuration_of_the_BswM_behavior">Guide Modemanagement p. 32</a>). Two examples:</p>
<ul>
<li><code>BswMDcmComModeRequest</code> connects argument <code>Network</code> of <code>BswM_Dcm_CommunicationMode_CurrentState</code> to a ComM channel <a class="spec-record-ref" data-req="SWS_BswM_00048" href="../../spec/record.html?id=SWS_BswM_00048">[SWS_BswM_00048]</a> via <code>BswMDcmComMChannelRef</code>.</li>
<li>With <code>BswM_J1939DcmBroadcastStatus</code>, the BswM evaluates the bit at the position of the referenced <code>ComMChannelId</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_3_17_BswM_J1939DcmBroadcastStatus.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_3_17_BswM_J1939DcmBroadcastStatus">SWS BswM p. 70</a>). Only the first 16 channels can be mapped <a class="spec-record-ref" data-req="SWS_BswM_00165" href="../../spec/record.html?id=SWS_BswM_00165">[SWS_BswM_00165]</a>.</li>
</ul>
<p>For J1939, the BswM switches three things depending on the J1939Nm state <a class="spec-record-ref" data-req="SWS_BswM_00194" href="../../spec/record.html?id=SWS_BswM_00194">[SWS_BswM_00194]</a>: COM I-PDU groups, PduR routing path groups, and the J1939Rm request handling (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_4_3_J1939_Networkmanagement.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_3_4_3_J1939_Networkmanagement">Guide Modemanagement p. 45</a>).</p>
<p>On the data types and helper interfaces:</p>
<ul>
<li><code>BswM_ModeType</code> and <code>BswM_UserType</code> are derived from <code>uint16</code> (<a class="spec-record-ref" data-req="SWS_BswM_00214" href="../../spec/record.html?id=SWS_BswM_00214">[SWS_BswM_00214]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00216" href="../../spec/record.html?id=SWS_BswM_00216">[SWS_BswM_00216]</a>).</li>
<li>The imported types of the neighboring modules are listed collectively <a class="spec-record-ref" data-req="SWS_BswM_00001" href="../../spec/record.html?id=SWS_BswM_00001">[SWS_BswM_00001]</a>.</li>
<li><code>BswM_GetVersionInfo</code> provides the version information <a class="spec-record-ref" data-req="SWS_BswM_00003" href="../../spec/record.html?id=SWS_BswM_00003">[SWS_BswM_00003]</a>.</li>
<li>The main function is available via <code>SchM_BswM.h</code> <a class="spec-record-ref" data-req="SWS_BswM_00053" href="../../spec/record.html?id=SWS_BswM_00053">[SWS_BswM_00053]</a>.</li>
</ul>

<h4>Behavior in the event of an error</h4>
<p>If <code>BswMDevErrorDetect</code> is active, the reporting APIs check two things:</p>
<ul>
<li><strong>Initialization:</strong> If the BswM is not initialized, the report is ignored and <code>BSWM_E_UNINIT</code> is reported to the DET. Examples are CanSM <a class="spec-record-ref" data-req="SWS_BswM_00080" href="../../spec/record.html?id=SWS_BswM_00080">[SWS_BswM_00080]</a>, EthSM <a class="spec-record-ref" data-req="SWS_BswM_00081" href="../../spec/record.html?id=SWS_BswM_00081">[SWS_BswM_00081]</a>, LinSM schedule <a class="spec-record-ref" data-req="SWS_BswM_00086" href="../../spec/record.html?id=SWS_BswM_00086">[SWS_BswM_00086]</a>, PNC <a class="spec-record-ref" data-req="SWS_BswM_00149" href="../../spec/record.html?id=SWS_BswM_00149">[SWS_BswM_00149]</a>, and NvM jobs <a class="spec-record-ref" data-req="SWS_BswM_00153" href="../../spec/record.html?id=SWS_BswM_00153">[SWS_BswM_00153]</a>.</li>
<li><strong>Value range:</strong> Values outside the permissible range are also discarded and reported with <code>BSWM_E_REQ_MODE_OUT_OF_RANGE</code>, such as in <a class="spec-record-ref" data-req="SWS_BswM_00095" href="../../spec/record.html?id=SWS_BswM_00095">[SWS_BswM_00095]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00150" href="../../spec/record.html?id=SWS_BswM_00150">[SWS_BswM_00150]</a>, <a class="spec-record-ref" data-req="SWS_BswM_00133" href="../../spec/record.html?id=SWS_BswM_00133">[SWS_BswM_00133]</a>, and <a class="spec-record-ref" data-req="SWS_BswM_00154" href="../../spec/record.html?id=SWS_BswM_00154">[SWS_BswM_00154]</a>.</li>
</ul>
<p>The main function behaves differently: if called before initialization, it returns immediately and reports no error <a class="spec-record-ref" data-req="SWS_BswM_00076" href="../../spec/record.html?id=SWS_BswM_00076">[SWS_BswM_00076]</a>.</p>
<p>The development error codes include, among others, <code>BSWM_E_UNINIT</code> (0x01), <code>BSWM_E_NULL_POINTER</code>, <code>BSWM_E_REQ_USER_OUT_OF_RANGE</code>, <code>BSWM_E_REQ_MODE_OUT_OF_RANGE</code>, and <code>BSWM_E_PARAM_CONFIG</code> <a class="spec-record-ref" data-req="SWS_BswM_00230" href="../../spec/record.html?id=SWS_BswM_00230">[SWS_BswM_00230]</a>. If an action returns <code>E_NOT_OK</code>, the BswM reports the runtime error <code>BSWM_E_ACTION_FAILED</code>. Its value is between 0x80 and 0xFF and is configured in <code>BswMReportFailRuntimeErrorId</code> <a class="spec-record-ref" data-req="SWS_BswM_00238" href="../../spec/record.html?id=SWS_BswM_00238">[SWS_BswM_00238]</a>.</p>
<p>System errors reach the BswM as ordinary mode indications. In the event of a bus-off, CanSM reports in this order (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_2_23_6_Effect_E_BUS_OFF.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_2_23_6_Effect_E_BUS_OFF">SWS CanSM p. 70</a>):</p>
<ol>
<li><code>CANSM_BSWM_BUS_OFF</code> to the BswM,</li>
<li><code>COMM_SILENT_COMMUNICATION</code> to ComM,</li>
<li>a PRE_FAILED event to the DEM.</li>
</ol>
<p>If the recovery succeeds, <code>CANSM_BSWM_FULL_COMMUNICATION</code> follows (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_2_23_13_Effect_E_TX_ON.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_2_23_13_Effect_E_TX_ON">SWS CanSM p. 65</a>). How the system reacts to this is entirely up to the rules via <code>BswMCanSMIndication</code> <a class="spec-record-ref" data-req="SWS_BswM_00049" href="../../spec/record.html?id=SWS_BswM_00049">[SWS_BswM_00049]</a>. Further error paths are the partition reset requested by the WdgM <a class="spec-record-ref" data-req="SWS_BswM_00157" href="../../spec/record.html?id=SWS_BswM_00157">[SWS_BswM_00157]</a> and the report of a partition restart <a class="spec-record-ref" data-req="SWS_BswM_00193" href="../../spec/record.html?id=SWS_BswM_00193">[SWS_BswM_00193]</a>.</p>
