<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht Anwendungen die generische Bearbeitung von UDS-Lese- und Schreibanfragen für Diagnose-Identifier.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>ara::diag::GenericDataIdentifier</code> dient als generische Schnittstelle zur asynchronen Bearbeitung von UDS-Lese- und Schreibanforderungen für Diagnose-Identifier in AUTOSAR Adaptive <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a>. Nach der Bindung an einen Port und der Freigabe über <code>Offer()</code> leitet das Diagnostic Management Anfragen an die implementierten Methoden weiter <a class="spec-record-ref" data-req="SWS_DM_00638" href="../spec/record.html?id=SWS_DM_00638">[SWS_DM_00638]</a>. Als singuläre Instanz kann das Objekt weder kopiert noch verschoben werden, während die Thread-Sicherheit der Anfragenbearbeitung über die beim Konstruktor gewählte Nebenläufigkeitskonfiguration gesteuert wird.</p>
<p class="ai-level-more-inline"><button type="button" class="ai-level-step ai-level-more" data-ai-level-step="1" title="Ausführlichere Fassung zeigen">mehr ›</button></p>
</div>
<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Die Klasse <code>ara::diag::GenericDataIdentifier</code> stellt eine generische Serviceschnittstelle innerhalb des Funktionsclusters Diagnostic Management (DM) der AUTOSAR Adaptive Platform dar <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=70">SWS Diagnostics §8.2 „GenericDataIdentifier“</a>. Während typspezifische Schnittstellen an fest modellierte Datentypen gebunden sind, dient <code>GenericDataIdentifier</code> der flexiblen Verarbeitung von Diagnose-Identifiern (Data Identifiers, DIDs), bei denen der 16-Bit-Identifier dynamisch als Parameter übergeben wird.</p>
<p>An der Diagnoseverarbeitung sind primär drei Rollen beteiligt:</p>
<ul>
<li>Der externe Diagnosetester, welcher standardisierte UDS-Dienste wie ReadDataByIdentifier (0x22) oder WriteDataByIdentifier (0x2E) an das Fahrzeug richtet.</li>
<li>Das Diagnostic Management (DM), das Diagnoseanfragen entgegennimmt, validiert und über definierte Port-Schnittstellen an die entsprechende Anwendungsinstanz weiterleitet, sofern diese zuvor über <code>Offer</code> aktiviert wurde <a class="spec-record-ref" data-req="SWS_DM_00638" href="../spec/record.html?id=SWS_DM_00638">[SWS_DM_00638]</a>.</li>
<li>Die anwendungsspezifische Implementierung von <code>GenericDataIdentifier</code>, welche die eigentliche Verarbeitungslogik kapselt, indem sie die Methoden <code>Read</code> <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a> und <code>Write</code> <a class="spec-record-ref" data-req="SWS_DM_00637" href="../spec/record.html?id=SWS_DM_00637">[SWS_DM_00637]</a> bereitstellt und die Daten asynchron zurückliefert.</li>
</ul>

<h4>Lebenszyklus</h4>
<p>Eine Instanz von <code>ara::diag::GenericDataIdentifier</code> wird explizit über ihren Konstruktor instanziiert <a class="spec-record-ref" data-req="SWS_DM_00634" href="../spec/record.html?id=SWS_DM_00634">[SWS_DM_00634]</a>. Dabei bindet der Aufrufer das Objekt an einen <code>ara::core::InstanceSpecifier</code>, der auf einen <code>PortPrototype</code> eines modellierten <code>DiagnosticDataIdentifierGenericInterface</code> verweist. Über das Argument <code>concurrencyType</code> (vom Typ <code>DataIdentifierConcurrencyType</code>) wird festgelegt, ob Anfragen nebenläufig (<code>kConcurrent</code>) oder sequenziell (<code>kNotConcurrent</code>) an den Handler übergeben werden <a class="spec-record-ref" data-req="SWS_DM_00634" href="../spec/record.html?id=SWS_DM_00634">[SWS_DM_00634]</a>.</p>
<p>Hinsichtlich Besitz und Lebensdauer ist <code>GenericDataIdentifier</code> als singuläre, nicht-kopierbare und nicht-verschiebbare Instanz modelliert:</p>
<ul>
<li>Der Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_DM_01653" href="../spec/record.html?id=SWS_DM_01653">[SWS_DM_01653]</a> sowie der Zuweisungsoperator <a class="spec-record-ref" data-req="SWS_DM_01651" href="../spec/record.html?id=SWS_DM_01651">[SWS_DM_01651]</a> sind gelöscht (<code>=delete</code>).</li>
<li>Ebenso sind der Move-Konstruktor <a class="spec-record-ref" data-req="SWS_DM_01654" href="../spec/record.html?id=SWS_DM_01654">[SWS_DM_01654]</a> und der Move-Zuweisungsoperator <a class="spec-record-ref" data-req="SWS_DM_01652" href="../spec/record.html?id=SWS_DM_01652">[SWS_DM_01652]</a> gelöscht.</li>
</ul>
<p>Nach der Instanziierung befindet sich das Objekt im inaktiven Zustand; das Diagnostic Management leitet noch keine Anfragen weiter. Erst durch den Aufruf von <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_00638" href="../spec/record.html?id=SWS_DM_00638">[SWS_DM_00638]</a> wird die Weiterleitung aktiviert. Um die Weiterleitung von Diagnoseanforderungen wieder zu deaktivieren, ruft die Anwendung <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_00639" href="../spec/record.html?id=SWS_DM_00639">[SWS_DM_00639]</a> auf. Die Zerstörung des Objekts erfolgt über den virtuellen Destruktor <a class="spec-record-ref" data-req="SWS_DM_00635" href="../spec/record.html?id=SWS_DM_00635">[SWS_DM_00635]</a>.</p>
<p>In Bezug auf Nebenläufigkeit ist der Konstruktor threadsicher (<code>thread-safe</code>) <a class="spec-record-ref" data-req="SWS_DM_00634" href="../spec/record.html?id=SWS_DM_00634">[SWS_DM_00634]</a>. Dagegen sind die administrativen Methoden <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_00638" href="../spec/record.html?id=SWS_DM_00638">[SWS_DM_00638]</a> und <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_00639" href="../spec/record.html?id=SWS_DM_00639">[SWS_DM_00639]</a> sowie der Destruktor <a class="spec-record-ref" data-req="SWS_DM_00635" href="../spec/record.html?id=SWS_DM_00635">[SWS_DM_00635]</a> als nicht threadsicher spezifiziert. Die Thread-Sicherheit der Methoden <code>Read</code> und <code>Write</code> hängt bedingt vom gewählten <code>concurrencyType</code> ab <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a>, <a class="spec-record-ref" data-req="SWS_DM_00637" href="../spec/record.html?id=SWS_DM_00637">[SWS_DM_00637]</a>.</p>

<h4>Nutzungspfad</h4>
<p>Ein typischer Durchstich zur Behandlung von Diagnoseanfragen gliedert sich in folgende Schritte:</p>
<ol>
<li><strong>Initialisierung:</strong> Die Anwendung instanziiert ihre abgeleitete Handler-Klasse unter Angabe des <code>InstanceSpecifier</code> sowie der Nebenläufigkeitskonfiguration <a class="spec-record-ref" data-req="SWS_DM_00634" href="../spec/record.html?id=SWS_DM_00634">[SWS_DM_00634]</a>. Interpretation: Dies dürfte in der Praxis typischerweise während der Initialisierungsphase des Anwendungsprozesses erfolgen. <a class="interp-q interp-q-open" data-q="Q-32596fba68253958" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-32596fba68253958" title="Frage Q-32596fba68253958 (offen): Die Instanziierung und Bereitstellung mittels Offer() erfolgt typischerweise während der Initialisierungsphase des jeweiligen Anwendungsprozesses.">Frage Q-32596fba68253958 (offen)</a></li>
<li><strong>Dienstbereitstellung:</strong> Die Anwendung ruft <code>Offer()</code> auf <a class="spec-record-ref" data-req="SWS_DM_00638" href="../spec/record.html?id=SWS_DM_00638">[SWS_DM_00638]</a>. Das Diagnostic Management aktiviert die Weiterleitung eingehender DID-Anfragen.</li>
<li><strong>Anfrageverarbeitung:</strong>
<ul>
<li>Geht ein Leseauftrag ein, ruft das DM die Methode <code>Read(dataIdentifier, metaInfo, cancellationHandler)</code> auf <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a>. Die Anwendung prüft den übergebenen 16-Bit-Identifier und liefert asynchron ein <code>ara::core::Future&lt;OperationOutput&gt;</code> zurück.</li>
<li>Trifft ein Schreibauftrag ein, ruft das DM <code>Write(dataIdentifier, requestData, metaInfo, cancellationHandler)</code> auf <a class="spec-record-ref" data-req="SWS_DM_00637" href="../spec/record.html?id=SWS_DM_00637">[SWS_DM_00637]</a>. Die Nutzdaten in <code>requestData</code> bleiben gültig, bis das zugehörige Promise erfüllt wird oder die Verarbeitung abgebrochen wird.</li>
</ul>
</li>
<li><strong>Abbruchprüfung:</strong> Während langwieriger Operationen kann der Handler über <code>cancellationHandler.IsCanceled()</code> prüfen, ob die Konversation abgebrochen wurde, oder via <code>cancellationHandler.SetNotifier</code> eine Benachrichtigungsfunktion registrieren <a class="spec-record-ref" data-req="SWS_DM_00636" href="../spec/record.html?id=SWS_DM_00636">[SWS_DM_00636]</a>, <a class="spec-record-ref" data-req="SWS_DM_00637" href="../spec/record.html?id=SWS_DM_00637">[SWS_DM_00637]</a>.</li>
<li><strong>Dienstabmeldung:</strong> Vor dem Beenden des Handlers ruft die Anwendung <code>StopOffer()</code> auf <a class="spec-record-ref" data-req="SWS_DM_00639" href="../spec/record.html?id=SWS_DM_00639">[SWS_DM_00639]</a>, wodurch das DM die Weiterleitung einstellt.</li>
</ol>
