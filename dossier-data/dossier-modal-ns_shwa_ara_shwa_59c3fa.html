  <h4>Context</h4>
  <p>
    The namespace <code>ara::shwa</code> (Safe Hardware Acceleration) provides interfaces for the discovery, allocation, and use of hardware accelerators (such as GPUs or CPUs) for compute-intensive tasks on the AUTOSAR Adaptive Platform. Structurally, the module separates system discovery, resource management, and actual asynchronous job processing.
  </p>
  <p>
    The central discovery entity is <code>Platform</code>, via which hardware accelerator platforms available in the system are determined and the connected <code>Device</code> instances are queried. For selecting specific execution targets, the namespace provides selectors such as <code>DeviceSelector</code>, <code>CpuSelector</code>, <code>GpuSelector</code>, and <code>AcceleratorSelector</code>, which are used to determine a suitable <code>Device</code> based on application-specific ranks or target architectures.
  </p>
  <p>
    Tasks are not started directly on the <code>Device</code>, but are coordinated via a <code>Queue</code>, which controls parallel processing on the selected target. Data is provided via <code>Buffer</code>, whose sizing is determined via <code>Range</code> and whose memory access is protected via <code>Accessor</code>. The interaction of the core components thus covers selection, memory management, and parallel execution.
  </p>

  <h4>Lifecycle</h4>
  <p>
    In the lifecycle of the involved objects, <code>ara::shwa</code> strictly distinguishes between resource-owning and non-owning entities:
  </p>
  <ul>
    <li>
      <strong>Resource-owning objects:</strong> <code>Queue</code>, <code>Buffer</code>, and <code>Accessor</code> own concrete hardware or memory resources. They are explicitly non-copyable and designed to be managed exclusively via <code>std::unique_ptr</code> and moved as needed.
    </li>
    <li>
      <strong>Resource-free reference objects:</strong> <code>Platform</code>, <code>Device</code>, <code>DeviceMonitor</code>, <code>Id</code>, and <code>Range</code> do not own the underlying resources themselves. They are designed as copyable descriptors and handles.
    </li>
    <li>
      <strong>Queue-bound objects:</strong> Instances of <code>Event</code> (for synchronization between host and HWA) and <code>TaskHandler</code> (for controlling task executions) can only be instantiated within a <code>Queue</code>; outside a queue, they have no functional significance.
    </li>
  </ul>
  <p>
    A <code>Device</code> reflects discrete operating states regarding its availability, which are mapped via the enumeration <code>DeviceStatus</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_00103" href="../spec/record.html?id=AP_SWS_SHWA_00103">[AP_SWS_SHWA_00103]</a>. Prior to task allocation, state <code>kReady</code> signals execution readiness, while <code>kNotAccesible</code>, <code>kFailure</code>, or <code>kUnknown</code> restrict or prevent use.
  </p>

  <h4>Usage Path</h4>
  <p>
    A typical processing workflow spans several classes of the namespace and follows a fixed sequence of device selection, creation of the execution pipeline, memory buffering, and synchronized execution:
  </p>
  <ol>
    <li>
      <strong>Platform and device selection:</strong> The application reads available devices via <code>Platform</code> or uses a <code>DeviceSelector</code> (or <code>GpuSelector</code>, <code>CpuSelector</code>, <code>AcceleratorSelector</code>) to select the most suitable <code>Device</code> instance with the highest rank.
    </li>
    <li>
      <strong>Queue instantiation:</strong> For parallel processing, a <code>Queue</code> is created as a <code>std::unique_ptr&lt;Queue&gt;</code> for the selected <code>Device</code>.
    </li>
    <li>
      <strong>Memory allocation and access management:</strong> The dimensions are defined via <code>Range</code>. Subsequently, a <code>Buffer</code> is created for memory allocation on the host or accelerator. For controlled read and write operations, a <code>Accessor</code> is instantiated whose mode is defined via <code>AccessMode</code> as <code>kRead</code>, <code>kWrite</code>, or <code>kReadWrite</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_00101" href="../spec/record.html?id=AP_SWS_SHWA_00101">[AP_SWS_SHWA_00101]</a>.
    </li>
    <li>
      <strong>Task submission and synchronization:</strong> Via the <code>Queue</code>, a <code>TaskHandler</code> is enqueued for execution on the target (specified via <code>Target::kDevice</code> or <code>Target::kHostTask</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_00102" href="../spec/record.html?id=AP_SWS_SHWA_00102">[AP_SWS_SHWA_00102]</a>). By means of a <code>Event</code> created within the queue, synchronization between host application and HWA processing takes place.
    </li>
  </ol>

  <h4>Error Scenarios</h4>
  <p>
    The API of Safe Hardware Acceleration is designed fundamentally exception-free. Operations signal errors via error codes of type <code>ara::core::ErrorCode</code>, which are assigned to the specific error domain <code>ShwaErrorDomain</code>.
  </p>
  <p>
    Access to the domain takes place via <code>GetShwaDomain()</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01311" href="../spec/record.html?id=AP_SWS_SHWA_01311">[AP_SWS_SHWA_01311]</a>, while standardized error codes are constructed via the helper function <code>MakeErrorCode()</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01312" href="../spec/record.html?id=AP_SWS_SHWA_01312">[AP_SWS_SHWA_01312]</a>. The enumeration <code>ShwaErrorCode</code> defines the following causes, among others <a class="spec-record-ref" data-req="AP_SWS_SHWA_01301" href="../spec/record.html?id=AP_SWS_SHWA_01301">[AP_SWS_SHWA_01301]</a>:
  </p>
  <ul>
    <li><code>kRuntime</code>: General runtime error during operation.</li>
    <li><code>kTaskExecutionFailure</code>: Execution error of a submitted task on the accelerator or host.</li>
    <li><code>kMemoryNotAllocated</code>: Allocation of main memory by <code>Buffer</code> failed.</li>
    <li><code>kIntegrityCorrupted</code>: The memory integrity of a <code>Buffer</code> could not be maintained.</li>
    <li><code>kResourceBusy</code>: A requested device or queue resource is busy.</li>
    <li><code>kInvalidAccessMode</code> and <code>kAccessorFailure</code>: Impermissible access mode for <code>AccessMode</code> or failure during creation or use of <code>Accessor</code>.</li>
    <li><code>kEventInvalidOperation</code>: Impermissible operation on a <code>Event</code> synchronization object.</li>
    <li><code>kFeatureNotSupported</code>: The requested hardware feature is not supported by the backend or driver.</li>
    <li><code>kInvalidIndex</code>, <code>kInvalidParameter</code>, and <code>kInvalidObject</code>: Erroneous input values, invalid indices, or the use of already destroyed or invalid objects.</li>
    <li><code>kTimedOut</code>: Timeout during execution or synchronization.</li>
  </ul>
  <p>
    For architectures based on C++ exceptions, the class <code>ShwaException</code> is available. The API itself does not throw this exception; however, applications can convert error codes into exceptions and forward them if necessary. For asynchronous error handling at the HWA level, the application also integrates <code>ErrorHandler</code>.
  </p>
  <p class="ai-note">This guide is based exclusively on the specification requirements of the module shwa in Release R25-11.</p>
