<h4>Context</h4>
<p>The data structure <code>ara::tsync::PdelayResponderMeasurementType</code> serves to capture and provide high-precision timestamps for the responder within the scope of the peer delay mechanism (Pdelay). Within the AUTOSAR Adaptive module <code>tsync</code> (Time Synchronization), it is declared in the header file <code>ara/tsync/time_validation_measurement_types.h</code> and forms a central building block for time validation (Time Validation). Its main task is to forward the measurement data of a responder cycle relevant for the propagation delay measurement between two neighboring network nodes in bundled form to higher-level analysis or validation instances.</p>

<p>Essentially three components are involved in this measurement and evaluation context:</p>
<ul>
  <li><strong>Pdelay Requester:</strong> An initiating network node that periodically transmits a delay request (<code>Pdelay_Req</code>) and awaits the corresponding response (<code>Pdelay_Resp</code>).</li>
  <li><strong>Pdelay Responder:</strong> The local protocol endpoint within the stack of <code>tsync</code> that receives the request, responds to it, and records the exact points in time at the local level.</li>
  <li><strong>Validation instance:</strong> A monitoring or diagnostic unit at the application level that receives the generated measurement structures to verify synchronization quality, network jitter, and protocol compliance.</li>
</ul>

<p>The structure encapsulates both protocol mapping parameters and temporal measurement points. Upon arrival of the request, the sequence number contained in the packet is recorded as <code>sequenceId</code> <a class="spec-record-ref" data-req="SWS_TS_14174" href="../spec/record.html?id=SWS_TS_14174">[SWS_TS_14174]</a> in order to uniquely assign the data record to the associated transaction. The associated ingress time is stored as <code>requestReceiptTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14170" href="../spec/record.html?id=SWS_TS_14170">[SWS_TS_14170]</a> in units of virtual local time (Virtual Local Time). When sending the response message, the egress time is also recorded as <code>responseOriginTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14171" href="../spec/record.html?id=SWS_TS_14171">[SWS_TS_14171]</a> in virtual local time. In order to be able to convert these local measured values into a standardized global time base, the structure additionally contains a reference time tuple: the local time value <code>referenceLocalTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14172" href="../spec/record.html?id=SWS_TS_14172">[SWS_TS_14172]</a> and the corresponding global time value <code>referenceGlobalTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14173" href="../spec/record.html?id=SWS_TS_14173">[SWS_TS_14173]</a> of type <code>ara::tsync::Timestamp</code>.</p>

  <li><strong>Assignment and consistency:</strong> The instance is populated with all measurement values in a single coherent step.   <li><strong>Concurrency:</strong> Since the structure does not have any internal locking mechanisms, it is not thread-safe for concurrent read and write accesses. However, after full initialization by the stack, the structure is immutable (effectively read-only) and can be evaluated in parallel across threads.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical usage and processing workflow of <code>PdelayResponderMeasurementType</code> follows a fixed sequence from hardware-related measurements to evaluation in the validation domain:</p>

<ol>
  <li><strong>Reception of Pdelay_Req:</strong> The responder receives the peer's request. The ingress timestamp is registered, converted to virtual local time, and stored in field <code>requestReceiptTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14170" href="../spec/record.html?id=SWS_TS_14170">[SWS_TS_14170]</a>. At the same time, the frame's sequence number is read out and saved as <code>sequenceId</code> <a class="spec-record-ref" data-req="SWS_TS_14174" href="../spec/record.html?id=SWS_TS_14174">[SWS_TS_14174]</a>. Presumably, this timestamp corresponds to the standardized PTP measurement point <em>t2</em>.</li>
  <li><strong>Transmission of Pdelay_Resp:</strong> The protocol stack generates the response message and transmits it to the network interface. When sending, the egress timestamp is registered, converted into virtual local time, and stored as <code>responseOriginTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14171" href="../spec/record.html?id=SWS_TS_14171">[SWS_TS_14171]</a>. This point in time presumably corresponds to the standardized PTP measurement point <em>t3</em>.</li>
  <li><strong>Coupling to the global time:</strong> The module determines the currently valid reference tuple of the time base and populates <code>referenceLocalTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14172" href="../spec/record.html?id=SWS_TS_14172">[SWS_TS_14172]</a> as well as <code>referenceGlobalTimestamp</code> <a class="spec-record-ref" data-req="SWS_TS_14173" href="../spec/record.html?id=SWS_TS_14173">[SWS_TS_14173]</a>. This documents the relationship that existed between virtual local time and global time at the time of measurement.</li>
  <li><strong>Export and time conversion:</strong> The aggregated data record is transmitted to the validation application. Based on the two reference timestamps, the consumer can accurately evaluate the difference between reception and transmission, check the residence time of the responder, or transform the timestamps into global time for further protocol verification.</li>
</ol>
