<h4>Context</h4>
<p>The data structure <code>ara::diag::SovdOperationExecution::GetStatusResponse</code> is defined as a C++ struct according to <a class="spec-record-ref" data-req="SWS_DM_02200" href="../spec/record.html?id=SWS_DM_02200">[SWS_DM_02200]</a> in <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=865">AUTOSAR_AP_SWS_Diagnostics §8.62.6 “Struct: GetStatusResponse”</a>. It acts as a standardized response container for querying the execution status of a diagnostic operation via the SOVD (Service-Oriented Vehicle Diagnostics) interface in the AUTOSAR Adaptive Platform.</p>
<p>Primarily three architectural components are involved in the interaction around <code>GetStatusResponse</code>:</p>
<ul>
<li><strong>External SOVD client:</strong> Initiates diagnostic operations and queries their current state via the standardized SOVD method <em>Read the Status of an operation</em> (<a class="spec-record-ref" data-req="SWS_DM_02180" href="../spec/record.html?id=SWS_DM_02180">[SWS_DM_02180]</a>).</li>
<li><strong>Diagnostic Management (DM):</strong> Processes the incoming SOVD request, performs required security checks, and addresses the responsible operation instance based on the transmitted <code>execution-id</code> (<a class="spec-record-ref" data-req="SWS_DM_02177" href="../spec/record.html?id=SWS_DM_02177">[SWS_DM_02177]</a>). After successful execution, the DM reads the attributes from <code>GetStatusResponse</code> and transfers them into the ASAM SOVD response body (<a class="spec-record-ref" data-req="SWS_DM_02181" href="../spec/record.html?id=SWS_DM_02181">[SWS_DM_02181]</a>).</li>
<li><strong>Application service (<code>SovdOperationExecution</code>):</strong> Implements the business logic of the diagnostic operation and provides the current processing status as well as any result data by implementing the pure virtual method <code>GetStatus</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=864">AUTOSAR_AP_SWS_Diagnostics §8.62</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>The struct <code>GetStatusResponse</code> has a clearly defined, short-lived value character and serves exclusively for data transport between the service application and the Diagnostic Management daemon:</p>
<ul>
<li><strong>Creation:</strong> The instance of <code>GetStatusResponse</code> is instantiated by the application software as soon as the DM queries the status of an ongoing or completed operation by means of <code>SovdOperationExecution::GetStatus</code>. According to the interface declaration in <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=864">AUTOSAR_AP_SWS_Diagnostics §8.62</a>, the return is encapsulated asynchronously via a <code>ara::core::Future&lt;GetStatusResponse&gt;</code>. For this purpose, the application populates the structure fields <code>status</code> and <code>Parameters</code>.</li>
<li><strong>Ownership and concurrency:</strong> Ownership is transferred to the calling Diagnostic Manager via the <code>ara::core::Promise</code> and <code>ara::core::Future</code> mechanism. This transfer presumably occurs via move semantics. Since the structure is passed to the future as a pure value object, read access by the DM requires no further synchronization within the structure.</li>
<li><strong>Destruction:</strong> As soon as the DM has extracted the values from <code>GetStatusResponse.status</code> and <code>GetStatusResponse.Parameters</code> and incorporated them into the SOVD serialization (<a class="spec-record-ref" data-req="SWS_DM_02181" href="../spec/record.html?id=SWS_DM_02181">[SWS_DM_02181]</a>), the functional lifetime of the object ends and the structure is presumably discarded.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical sequence for querying the operation status is divided into authorization, calling the diagnostic interface, and preparing the response data:</p>
<ol>
<li><strong>Request reception:</strong> An external client sends the SOVD method <em>Read the Status of an operation</em> with a specific <code>execution-id</code> to the vehicle gateway or the Diagnostic Manager (<a class="spec-record-ref" data-req="SWS_DM_02180" href="../spec/record.html?id=SWS_DM_02180">[SWS_DM_02180]</a>).</li>
<li><strong>Validation:</strong> If configured in the system, the DM first validates the <code>proximity_challenge</code> according to <a class="spec-record-ref" data-req="SWS_DM_02173" href="../spec/record.html?id=SWS_DM_02173">[SWS_DM_02173]</a>.</li>
<li><strong>Method call:</strong> After successful validation, the DM identifies the assigned instance of <code>SovdOperationExecution</code> based on <a class="spec-record-ref" data-req="SWS_DM_02177" href="../spec/record.html?id=SWS_DM_02177">[SWS_DM_02177]</a> and calls its method <code>GetStatus</code> (<a class="spec-record-ref" data-req="SWS_DM_02180" href="../spec/record.html?id=SWS_DM_02180">[SWS_DM_02180]</a>). In doing so, environmental information (<code>ara::diag::MetaInfo</code>) and a <code>ara::diag::CancellationHandler</code> are passed (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=864">AUTOSAR_AP_SWS_Diagnostics §8.62</a>).</li>
<li><strong>State provision:</strong> The application determines the progress, initializes an instance of <code>GetStatusResponse</code>, sets field <code>status</code> to the current operating state, and stores any output data in field <code>Parameters</code>. Subsequently, the returned <code>ara::core::Future</code> is fulfilled.</li>
<li><strong>SOVD response construction:</strong> If <code>GetStatus</code> has responded successfully, the DM constructs the response body according to ASAM SOVD with the following attributes (<a class="spec-record-ref" data-req="SWS_DM_02181" href="../spec/record.html?id=SWS_DM_02181">[SWS_DM_02181]</a>):
<ul>
<li><code>status</code>: Corresponds to the value stored in <code>GetStatusResponse.status</code>.</li>
<li><code>capability</code>: Is fixed to the value <code>execute</code>.</li>
<li><code>parameters</code>: Is generated from the parameters of <code>GetStatusResponse.Parameters</code> (derived from <code>DiagnosticSovdContentData</code>).</li>
</ul>
</li>
</ol>

<h4>Error Scenarios</h4>
<p>During status determination, various exception and error states can occur that affect the creation or evaluation of <code>GetStatusResponse</code>:</p>
<ul>
<li><strong>Security validation failure:</strong> If a required <code>proximity_challenge</code> fails according to <a class="spec-record-ref" data-req="SWS_DM_02173" href="../spec/record.html?id=SWS_DM_02173">[SWS_DM_02173]</a>, the call of <code>SovdOperationExecution::GetStatus</code> is omitted completely (<a class="spec-record-ref" data-req="SWS_DM_02180" href="../spec/record.html?id=SWS_DM_02180">[SWS_DM_02180]</a>). In this case, no instance of <code>GetStatusResponse</code> is created.</li>
<li><strong>Failed status determination:</strong> If the application instance cannot determine the status or <code>GetStatus</code> fails (for example, due to an error state in the asynchronous <code>ara::core::Future</code>), the specification from <a class="spec-record-ref" data-req="SWS_DM_02181" href="../spec/record.html?id=SWS_DM_02181">[SWS_DM_02181]</a> does not apply. In this case, the DM does not send a regular response body with the fields from <code>GetStatusResponse</code>, but signals an error to the SOVD client.</li>
<li><strong>Cancellation via CancellationHandler:</strong> The signature of <code>GetStatus</code> accepts a <code>ara::diag::CancellationHandler</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=864">AUTOSAR_AP_SWS_Diagnostics §8.62</a>). If the query is cancelled before completion, the future in the application use case is presumably resolved with a corresponding error code, so that no valid <code>GetStatusResponse</code> is produced.</li>
</ul>
