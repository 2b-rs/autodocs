<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht die asynchrone, thread-sichere Ausführung von aufrufbaren Objekten mit optionaler Rückgabe über Futures.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>ara::core::Executor</code> stellt eine Schnittstelle zur asynchronen Ausführung von aufrufbaren Objekten in einem garantierten thread-sicheren Kontext bereit. Aufgaben werden entweder ergebnisorientiert über <code>execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a> mit Rückgabe eines <code>ara::core::Future</code> für Werte oder Fehlercodes angestoßen oder statusunabhängig per <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> im Fire-and-Forget-Modus übergeben. Als zentrale Randbedingung ist zu beachten, dass <code>execute</code> selbst nicht thread-sicher ist und parallele Aufrufe auf derselben Instanz extern synchronisiert werden müssen, während die Ausführung des Callables im Hintergrund thread-sicher erfolgt.</p>

<h4>Kontext</h4>
<p>Die Klasse <code>ara::core::Executor</code> stellt eine Schnittstelle für einen Ausführungskontext bereit, der aufrufbare Einheiten (Callables) asynchron in einer garantierten, thread-sicheren Umgebung ausführt. Sie dient als Abstraktionsschicht zwischen dem aufrufenden Thread und der asynchronen Hintergrundverarbeitung. Für die Auftragsübergabe stehen zwei Mechanismen zur Verfügung: Die Methode <code>execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a> übergibt eine Aufgabe ergebnisorientiert und gibt ein <code>ara::core::Future</code>-Objekt zurück, über das der spätere Rückgabewert oder ein Fehlercode synchronisiert und abgefragt werden kann. Für reine Benachrichtigungen oder statusunabhängige Hintergrundoperationen stellt die Klasse die Methode <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> bereit, welche einer Fire-and-Forget-Semantik folgt und keinen asynchronen Kontext an den Aufrufer zurückliefert. Vermutlich kapselt die konkrete Implementierung im Hintergrund eine Thread-Verwaltung oder Aufgaben-Warteschlange, um die nebenläufige Abarbeitung zu koordinieren.</p>

<h4>Lebenszyklus</h4>
<p>Die Instanziierung und Lebensdauer eines <code>ara::core::Executor</code> unterliegt differenzierten Regeln hinsichtlich Ausnahme- und Thread-Sicherheit:</p>
<ul>
<li><strong>Kopieren:</strong> Der Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_CORE_00009" href="../spec/record.html?id=SWS_CORE_00009">[SWS_CORE_00009]</a> sowie der Kopierzuweisungsoperator <a class="spec-record-ref" data-req="SWS_CORE_00017" href="../spec/record.html?id=SWS_CORE_00017">[SWS_CORE_00017]</a> sind thread-sicher spezifiziert, jedoch nicht als ausnahmesicher (<em>not exception safe</em>) eingestuft. Ein Kopiervorgang kann daher fehlschlagen, wenn notwendige Ressourcen nicht alloziiert werden können.</li>
<li><strong>Verschieben:</strong> Der Move-Konstruktor <a class="spec-record-ref" data-req="SWS_CORE_00015" href="../spec/record.html?id=SWS_CORE_00015">[SWS_CORE_00015]</a> und die Move-Zuweisung <a class="spec-record-ref" data-req="SWS_CORE_00018" href="../spec/record.html?id=SWS_CORE_00018">[SWS_CORE_00018]</a> sind als <code>noexcept</code> deklariert und damit ausnahmesicher. Allerdings sind Verschiebeoperationen nicht thread-sicher (<em>not thread-safe</em>), weshalb gleichzeitige Zugriffe während des Verschiebens durch den Aufrufer synchronisiert werden müssen.</li>
<li><strong>Zerstörung:</strong> Der Destruktor <a class="spec-record-ref" data-req="SWS_CORE_00019" href="../spec/record.html?id=SWS_CORE_00019">[SWS_CORE_00019]</a> ist <code>noexcept</code> und thread-sicher ausgeführt, wodurch der Lebenszyklus einer Instanz sicher beendet werden kann.</li>
</ul>
<p>Hinsichtlich der Nebenläufigkeit während des Betriebs zeigt sich eine fundamentale Aufteilung: Während <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> thread-sicher ist, ist <code>execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a> als nicht thread-sicher eingestuft. Die fehlende Thread-Sicherheit bei <code>execute</code> dürfte auf die interne Erzeugung und Verwaltung des zugrunde liegenden Zustandsobjekts für das resultierende Future zurückzuführen sein, weshalb gleichzeitige Aufrufe von <code>execute</code> auf derselben Instanz extern synchronisiert werden müssen.</p>

<h4>Nutzungspfad</h4>
<p>Die Verwendung von <code>ara::core::Executor</code> gliedert sich in zwei wesentliche Pfade, je nachdem, ob ein Rückgabewert benötigt wird:</p>
<ol>
<li><strong>Ergebnisorientierter Pfad (<code>execute</code>):</strong> Der Aufrufer übergibt ein aufrufbares Objekt <code>f</code> sowie optionale Argumente <code>p...</code> an <code>execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a>. Die Methode liefert unmittelbar ein <code>ara::core::Future</code> zurück, dessen Ergebnistyp auf dem abgeleiteten Rückgabetyp des Aufrufs basiert. Das Callable wird asynchron im garantierten Kontext ausgeführt. Sobald die Verarbeitung abgeschlossen ist, kann der Aufrufer den Ergebniswert oder einen potenziellen Fehlercode aus dem Future extrahieren.</li>
<li><strong>Einweg-Pfad (<code>oneway_execute</code>):</strong> Benötigt der Aufrufer weder Rückmeldung noch Synchronisation, wird <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> aufgerufen. Das Callable wird ebenfalls asynchron ausgeführt, ein Rückgabewert existiert jedoch nicht (<code>void</code>).</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Die Aufrufmethoden <code>execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a> und <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> werfen keine C++-Ausnahmen; beide sind explizit als <code>noexcept</code> spezifiziert. Ebenso definiert die Spezifikation für <code>execute</code> keine standardisierten Fehlercodes für den Übergabeaufruf selbst <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a>.</p>
<p>Tritt jedoch während der asynchronen Abarbeitung des Callables ein Fehler auf, wird dieser über das von <code>execute</code> zurückgegebene <code>ara::core::Future</code> propagiert: Im Fehlerfall kapselt das Future einen Fehlercode, während im Erfolgsfall der Typ <code>ara::core::Result::value_type</code> mit dem Funktionsergebnis bereitgestellt wird <a class="spec-record-ref" data-req="SWS_CORE_00024" href="../spec/record.html?id=SWS_CORE_00024">[SWS_CORE_00024]</a>. Bei <code>oneway_execute</code> <a class="spec-record-ref" data-req="SWS_CORE_00025" href="../spec/record.html?id=SWS_CORE_00025">[SWS_CORE_00025]</a> besteht konstruktionsbedingt keine Möglichkeit zur Fehlerrückgabe an den Aufrufer; Fehler verbleiben im asynchronen Kontext.</p>
