<h4>Role: unified access of the NvM to Fee and Ea</h4>
<p>The Memory Abstraction Interface (MemIf) is the topmost layer of the Memory Hardware Abstraction. It conceals from the upper layers how many Fee and Ea modules lie beneath it, and provides them with virtual segmentation on a uniform linear address space (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYABSTRACTIONINTERFACE.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYABSTRACTIONINTERFACE">SWS MemIf p. 7</a>). According to the SRS, MemIf replaces the earlier driver interface layers for EEPROM and Flash. Via this interface, the NVRAM manager can address multiple abstraction modules without requiring modification when changing a memory driver or memory device (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER">SRS MemHwAb p. 5</a>).</p>
<p>MemIf has no memory behavior of its own. Its API is mapped to the API of the underlying abstraction modules. For the functional behavior, the specification refers to these modules or to the memory drivers (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf p. 17</a>). Accordingly, each service definition describes only the invocation of the function of the same name of the selected module, for example with <code>MemIf_Read</code> <a class="spec-record-ref" data-req="SWS_MemIf_00039" href="../../spec/record.html?id=SWS_MemIf_00039">[SWS_MemIf_00039]</a> and <code>MemIf_Write</code> <a class="spec-record-ref" data-req="SWS_MemIf_00040" href="../../spec/record.html?id=SWS_MemIf_00040">[SWS_MemIf_00040]</a>. The required Ea functions are listed as Required Interfaces <a class="spec-record-ref" data-req="SWS_MemIf_00047" href="../../spec/record.html?id=SWS_MemIf_00047">[SWS_MemIf_00047]</a>.</p>
<p>Diagrams of later releases additionally show MemAcc and Mem beneath Fee and Ea, respectively. The call <code>MemIf_Write</code> → <code>Fee_Write</code> remains unchanged there (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write">SWS Fee p. 48</a>). <h4>Device selection via DeviceIndex: macro or dispatch table</h4>
<p>The parameter <code>DeviceIndex</code> selects the abstraction module and thus the memory device. If only one abstraction module is configured, the parameter is ignored. In this case, MemIf shall be implemented as a set of macros that map directly to the module's API, e.g., <code>#define MemIf_Write(DeviceIndex, BlockNumber, DataPtr) Fee_Write(BlockNumber, DataPtr)</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf p. 17</a>, as of R24-11). The SRS follows the same direction: If a vendor library replaces all Fee and Ea modules, MemIf consists only of macros (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER.html" data-snip="SNIP_CLASSIC_MEMIF_FIGURE_Figure_1_1_MEMORYHWABSTRACTIONLAYER">SRS MemHwAb p. 5</a>).</p>
<p>If multiple modules are configured, MemIf shall map the calls to the appropriate module using efficient mechanisms. The specification mentions tables of function pointers for this purpose. Interpretation of the note truncated there: <code>DeviceIndex</code> is likely to serve as an index into these tables (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_Function_definitions">SWS MemIf p. 17</a>).</p>
<p>There is a release difference regarding the type of the parameter. In R20-11, <code>DeviceIndex</code> is of type <code>uint8</code> (<a class="spec-record-ref" data-req="SWS_MemIf_00039" href="../../spec/record.html?id=SWS_MemIf_00039">[SWS_MemIf_00039]</a>, <a class="spec-record-ref" data-req="SWS_MemIf_00041" href="../../spec/record.html?id=SWS_MemIf_00041">[SWS_MemIf_00041]</a>). The document passages from R23-11 et seq. show <code>uint16</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read">SWS MemIf p. 18</a>). For R20-11, <code>uint8</code> applies.</p>

<p>“Synchronous” refers only to the acceptance of the job. The actual work runs asynchronously in the cyclic main functions of the underlying modules. In the Ea_Write sequence, this takes place in a loop over <code>Eep_MainFunction</code> in a BSW task (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-5dcc697f7998a885.html" data-snip="FIG-5dcc697f7998a885">SWS Ea p. 41</a>). According to the specification, the Fee_Write sequence also applies to the remaining asynchronous services (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write">SWS Fee p. 48</a>). The return value of <code>MemIf_Write</code> is the return value of the called module function <a class="spec-record-ref" data-req="SWS_MemIf_00040" href="../../spec/record.html?id=SWS_MemIf_00040">[SWS_MemIf_00040]</a>.</p>
<p>The NvM learns of the completion of a job in one of two ways:</p>
<ul>
<li>The abstraction module calls <code>NvM_JobEndNotification</code> directly; MemIf is not involved (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_2_Fee_Write">SWS Fee p. 48</a>).</li>
<li>The NvM queries <code>MemIf_GetJobResult</code> in polling mode <a class="spec-record-ref" data-req="SWS_MemIf_00043" href="../../spec/record.html?id=SWS_MemIf_00043">[SWS_MemIf_00043]</a>.</li>
</ul>
<p>The MemIf API itself contains no callback function <a class="spec-record-ref" data-req="SWS_MemIf_00038" href="../../spec/record.html?id=SWS_MemIf_00038">[SWS_MemIf_00038]</a>.</p>

<h4>Device status, job result, and operating mode</h4>
<p><code>MemIf_GetStatus</code> <a class="spec-record-ref" data-req="SWS_MemIf_00042" href="../../spec/record.html?id=SWS_MemIf_00042">[SWS_MemIf_00042]</a> returns a value of <code>MemIf_StatusType</code> <a class="spec-record-ref" data-req="SWS_MemIf_00064" href="../../spec/record.html?id=SWS_MemIf_00064">[SWS_MemIf_00064]</a>. Possible values are <code>MEMIF_UNINIT</code>, <code>MEMIF_IDLE</code>, <code>MEMIF_BUSY</code>, and <code>MEMIF_BUSY_INTERNAL</code>. In the case of <code>MEMIF_BUSY_INTERNAL</code>, the abstraction module is busy with internal management; the driver beneath it may be busy or idle. Fee reports this value, for example, during a reorganization of the flash memory (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus">SWS Fee p. 30</a>). The drivers also use the same types, such as <code>Fls_GetStatus</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_5_Fls_GetStatus.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_5_Fls_GetStatus">SWS Fls p. 35</a>). The types from <code>MemIf.h</code> thus form the common vocabulary of the memory stack.</p>

<p><code>MemIf_SetMode</code> is the only job service that does not have a <code>DeviceIndex</code>. It calls the SetMode functions of all underlying modules <a class="spec-record-ref" data-req="SWS_MemIf_00038" href="../../spec/record.html?id=SWS_MemIf_00038">[SWS_MemIf_00038]</a>. The parameter <code>MemIf_ModeType</code> supports <code>MEMIF_MODE_SLOW</code> and <code>MEMIF_MODE_FAST</code> <a class="spec-record-ref" data-req="SWS_MemIf_00066" href="../../spec/record.html?id=SWS_MemIf_00066">[SWS_MemIf_00066]</a>. The drivers interpret this as normal SPI access or SPI burst, respectively (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_2_Eep_SetMode.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_2_Eep_SetMode">SWS Eep p. 34</a>). Eep_SetMode must not be called during an ongoing operation. Fls_SetMode rejects a mode change in the "busy" state (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_9_Fls_SetMode.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_9_Fls_SetMode">SWS Fls p. 42</a>). Interpretation: <code>MemIf_SetMode</code> is therefore likely only reasonably callable if no device is processing a job.</p>

<h4>Canceling ongoing jobs</h4>
<p><code>MemIf_Cancel</code> returns no value and forwards the cancellation to the selected module <a class="spec-record-ref" data-req="SWS_MemIf_00041" href="../../spec/record.html?id=SWS_MemIf_00041">[SWS_MemIf_00041]</a>. Fee_Cancel and Ea_Cancel themselves run synchronously, but are asynchronous with respect to the hardware (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel">SWS Fee p. 45</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_3_Ea_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_3_Ea_Cancel">SWS Ea p. 44</a>). In the flash path, the cancellation is passed on to <code>Fls_Cancel</code>. The error notification is returned to the NvM via <code>Fee_JobErrorNotification</code> and <code>NvM_JobErrorNotification</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job">SWS Fls p. 58</a>). After that, the job result reports <code>MEMIF_JOB_CANCELED</code>, which Fee classifies as "failed" (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult">SWS Fee p. 31</a>).</p>
<p>A constraint applies to scheduling: <code>Fls_Cancel</code> must not be called during an ongoing <code>Fls_MainFunction</code>. This can be ensured in two ways (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_4_Canceling_a_running_job">SWS Fls p. 58</a>):</p>
<ul>
<li>The job functions of NvM and driver run sequentially in the same task.</li>
<li>The task of the main function is non-interruptible.</li>
</ul>

<h4>Behavior in the event of an error</h4>
<p>MemIf defines two development errors <a class="spec-record-ref" data-req="SWS_MemIf_00006" href="../../spec/record.html?id=SWS_MemIf_00006">[SWS_MemIf_00006]</a>:</p>
<ul>
<li><code>MEMIF_E_PARAM_DEVICE</code> (0x01): incorrect device index.</li>
<li><code>MEMIF_E_PARAM_POINTER</code> (0x02): NULL pointer as argument.</li>
</ul>
<p>Presumably, the pointer error affects the parameters <code>DataBufferPtr</code> and <code>VersionInfoPtr</code>. Reporting takes place via <code>Det_ReportError</code> <a class="spec-record-ref" data-req="SWS_MemIf_00048" href="../../spec/record.html?id=SWS_MemIf_00048">[SWS_MemIf_00048]</a>. When error detection is active and an error is detected, the following applies:</p>
<ul>
<li>Read, Write, InvalidateBlock, and EraseImmediateBlock return <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_MemIf_00044" href="../../spec/record.html?id=SWS_MemIf_00044">[SWS_MemIf_00044]</a>, <a class="spec-record-ref" data-req="SWS_MemIf_00046" href="../../spec/record.html?id=SWS_MemIf_00046">[SWS_MemIf_00046]</a>).</li>
<li><code>MemIf_GetJobResult</code> returns <code>MEMIF_JOB_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_5_MemIf_GetJobResult.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_5_MemIf_GetJobResult">SWS MemIf p. 21</a>).</li>
</ul>
<p>The API does not return specific development error codes (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_Requirements_Tracing.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_Requirements_Tracing">SWS MemIf p. 12</a>).</p>
<p>MemIf does not handle runtime errors from Fee or Ea itself; the intended reaction is "N/A". Only in polling mode does the NvM learn of the error via <code>MemIf_GetJobResult</code> with the result <code>MEMIF_JOB_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_1_2_2_Memory_Abstraction_Interface.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_1_2_2_Memory_Abstraction_Interface">ErrorDescription p. 58</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_2_2_2_Memory_Abstraction_Interface.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_3_2_2_2_Memory_Abstraction_Interface">ErrorDescription p. 60</a>, each R20-11). An uninitialized Fee can be detected via its status query (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation">ErrorDescription p. 53</a>).</p>
<p>Recovery is handled by the NvM. If a write operation is affected, it increments a retry counter and aborts after exceeding the limit. It reports the error to the DEM; <code>NVM_REQ_NOT_OK</code> can then be queried via <code>NvM_GetErrorStatus</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_2_2_2_5_NVRAM_Manager.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_2_2_2_5_NVRAM_Manager">EXP ErrorDescription p. 45</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_6_2_7_2_5_NVRAM_Manager.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_6_2_7_2_5_NVRAM_Manager">EXP ErrorDescription p. 58</a>, as of R25-11). In contrast, <code>MEMIF_BLOCK_INCONSISTENT</code> and <code>MEMIF_BLOCK_INVALID</code> describe the state of the block content and are passed through unchanged <a class="spec-record-ref" data-req="SWS_MemIf_00065" href="../../spec/record.html?id=SWS_MemIf_00065">[SWS_MemIf_00065]</a>.</p>
