<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht Applikationen die Bereitstellung und Übertragung von SOVD-Massendaten über das Diagnostic Management.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Schnittstelle <a class="spec-record-ref" data-req="SWS_DM_01841" href="../spec/record.html?id=SWS_DM_01841">[SWS_DM_01841]</a> verbindet adaptive Applikationen mit dem Diagnostic Management, um SOVD-basierte Massendatenoperationen bereitzustellen. Über rein virtuelle Methoden werden Metadaten abgefragt, Up- und Downloads von Massendaten abgewickelt sowie Datenbestände gezielt oder kategorieweise gelöscht. Eine Instanz wird an einen modellierten Port gebunden, über den Aufruf von <code>Offer()</code> zur Weiterleitung von Diagnoseanfragen freigeschaltet und bei Beendigung über <code>StopOffer()</code> deregistriert <a class="spec-record-ref" data-req="SWS_DM_01857" href="../spec/record.html?id=SWS_DM_01857">[SWS_DM_01857]</a>. Je nach gewählter Nebenläufigkeit müssen die bereitgestellten Callback-Routinen threadsicher ausgelegt sein.</p>

<h4>Kontext</h4>
<p>Die Schnittstellenklasse <code>ara::diag::SovdBulkData</code> <a class="spec-record-ref" data-req="SWS_DM_01841" href="../spec/record.html?id=SWS_DM_01841">[SWS_DM_01841]</a> stellt eine generische Serviceschnittstelle für den Zugriff auf Massendaten (Bulk Data) gemäß Service-Oriented Vehicle Diagnostics (SOVD) bereit <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=701">SWS Diagnostics §8.53 „Class: SovdBulkData“</a>. Sie dient als Bindeglied zwischen anwendungsspezifischen Datenquellen und dem zentralen Diagnoseserver der Adaptive Platform.</p>

<p>An der Gesamtabwicklung sind mindestens drei Komponenten beteiligt:</p>
<ul>
<li><strong>SOVD-Client:</strong> Ein externes Diagnosetool, das Massendaten abruft, hochlädt oder löscht. Die Kommunikation dürfte typischerweise über HTTP/REST-Mechanismen abgewickelt werden.</li>
<li><strong>Diagnostic Management (DM):</strong> Die Diagnostic Server Instance nimmt externe SOVD-Dienstaufrufe entgegen und setzt diese in lokale Methodenaufrufe um <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=222">SWS Diagnostics §7.x „SOVD Bulk Data Realization“</a>.</li>
<li><strong>Adaptive Applikation:</strong> Eine benutzerdefinierte Anwendung leitet von <code>ara::diag::SovdBulkData</code> ab, instanziiert die Klasse und stellt die eigentlichen Datenströme und Metadaten bereit.</li>
</ul>

<h4>Lebenszyklus</h4>
<p>Die Instanziierung von <code>ara::diag::SovdBulkData</code> erfolgt über den Konstruktor unter Übergabe eines <code>ara::core::InstanceSpecifier</code> sowie der Angabe des Nebenläufigkeitsverhaltens via <code>ConcurrencyType</code> <a class="spec-record-ref" data-req="SWS_DM_01847" href="../spec/record.html?id=SWS_DM_01847">[SWS_DM_01847]</a>. Der <code>InstanceSpecifier</code> bindet das Objekt an einen im Entwurfsmodell definierten <code>PortPrototype</code> eines <code>DiagnosticSovdBulkDataInterface</code>.</p>

<p>Hinsichtlich der Besitzverhältnisse ist die Klasse als Einzelexemplar konzipiert: Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_DM_01848" href="../spec/record.html?id=SWS_DM_01848">[SWS_DM_01848]</a> und Kopierzuweisungsoperator <a class="spec-record-ref" data-req="SWS_DM_01850" href="../spec/record.html?id=SWS_DM_01850">[SWS_DM_01850]</a> sind explizit gelöscht (<code>=delete</code>). Ein Transfer von Instanzen ist ausschließlich über Move-Operationen vorgesehen; Move-Konstruktor <a class="spec-record-ref" data-req="SWS_DM_01849" href="../spec/record.html?id=SWS_DM_01849">[SWS_DM_01849]</a> und Move-Zuweisung <a class="spec-record-ref" data-req="SWS_DM_01851" href="../spec/record.html?id=SWS_DM_01851">[SWS_DM_01851]</a> sind geschützt implementiert.</p>

<p>Der funktionale Lebenszyklus gliedert sich in folgende Phasen:</p>
<ul>
<li><strong>Inaktiv:</strong> Nach der Konstruktion ist das Objekt lokal vorhanden, empfängt jedoch noch keine Diagnoseanfragen vom Diagnostic Management.</li>
<li><strong>Aktiv (Offered):</strong> Durch den Aufruf der Methode <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_01857" href="../spec/record.html?id=SWS_DM_01857">[SWS_DM_01857]</a> wird das Objekt beim DM registriert. Erst ab diesem Zeitpunkt leitet das DM eingehende SOVD-Anfragen an die virtuellen Handler-Methoden weiter.</li>
<li><strong>Gestoppt:</strong> Der Aufruf von <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_01858" href="../spec/record.html?id=SWS_DM_01858">[SWS_DM_01858]</a> deaktiviert die Weiterleitung von Anfragen wieder.</li>
<li><strong>Zerstörung:</strong> Der virtuelle Destruktor <code>~SovdBulkData()</code> <a class="spec-record-ref" data-req="SWS_DM_01852" href="../spec/record.html?id=SWS_DM_01852">[SWS_DM_01852]</a> beendet die Lebensdauer des Objekts. Vor der Zerstörung sollte vermutlich <code>StopOffer()</code> aufgerufen werden, um schwebende Zugriffe sauber zu trennen.</li>
</ul>

<p>Bezüglich der Nebenläufigkeit legt der im Konstruktor übergebene <code>ConcurrencyType</code> fest, ob die virtuellen Callback-Methoden threadsicher (<code>kConcurrent</code>) oder nicht-threadsicher (<code>kNotConcurrent</code>) ausgeführt werden müssen <a class="spec-record-ref" data-req="SWS_DM_01847" href="../spec/record.html?id=SWS_DM_01847">[SWS_DM_01847]</a>. Die Kontrollmethoden <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_01857" href="../spec/record.html?id=SWS_DM_01857">[SWS_DM_01857]</a>, <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_01858" href="../spec/record.html?id=SWS_DM_01858">[SWS_DM_01858]</a> und der Destruktor <a class="spec-record-ref" data-req="SWS_DM_01852" href="../spec/record.html?id=SWS_DM_01852">[SWS_DM_01852]</a> sind selbst nicht threadsicher.</p>

<h4>Nutzungspfad</h4>
<p>Ein typischer Ablauf zur Bereitstellung und Ausführung von SOVD-Massendatenoperationen umfasst folgende Schritte:</p>
<ol>
<li><strong>Klassenableitung:</strong> Die Applikation implementiert eine konkrete Klasse, die von <code>ara::diag::SovdBulkData</code> erbt, und überschreibt die reinen virtuellen Methoden.</li>
<li><strong>Bereitstellung:</strong> Nach der Instanziierung ruft die Anwendung <code>Offer()</code> auf <a class="spec-record-ref" data-req="SWS_DM_01857" href="../spec/record.html?id=SWS_DM_01857">[SWS_DM_01857]</a>, um den Dienst anzubieten.</li>
<li><strong>Anfragebearbeitung:</strong>
  <ul>
  <li>Fordert ein Client Metadaten an, ruft der Diagnoseserver <code>GetBulkDataMetaData</code> auf <a class="spec-record-ref" data-req="SWS_DM_01791" href="../spec/record.html?id=SWS_DM_01791">[SWS_DM_01791]</a>, was einen Vektor von <code>BulkDataMetaDataDescriptor</code> via <code>ara::core::Future</code> liefert <a class="spec-record-ref" data-req="SWS_DM_01853" href="../spec/record.html?id=SWS_DM_01853">[SWS_DM_01853]</a>.</li>
  <li>Bei einem Download-Aufruf ruft das DM <code>RequestBulkDataDownload</code> auf <a class="spec-record-ref" data-req="SWS_DM_01792" href="../spec/record.html?id=SWS_DM_01792">[SWS_DM_01792]</a>. Die Applikation antwortet mit einer Lese-Sitzung (<code>DataTransferReadSession</code>) samt Metadaten oder einer HTTP-Weiterleitung (<code>HttpRedirect</code>) <a class="spec-record-ref" data-req="SWS_DM_01873" href="../spec/record.html?id=SWS_DM_01873">[SWS_DM_01873]</a>.</li>
  <li>Für Upload-Operationen ruft das DM <code>RequestBulkDataUpload</code> auf <a class="spec-record-ref" data-req="SWS_DM_01793" href="../spec/record.html?id=SWS_DM_01793">[SWS_DM_01793]</a>, woraufhin eine Schreib-Sitzung (<code>DataTransferWriteSession</code>) bereitgestellt wird <a class="spec-record-ref" data-req="SWS_DM_01854" href="../spec/record.html?id=SWS_DM_01854">[SWS_DM_01854]</a>.</li>
  <li>Löschanfragen leitet das DM an <code>DeleteSpecificBulkData</code> (für einzelne Ressourcen) <a class="spec-record-ref" data-req="SWS_DM_01856" href="../spec/record.html?id=SWS_DM_01856">[SWS_DM_01856]</a> oder an <code>DeleteAllBulkData</code> (kategorieweise) <a class="spec-record-ref" data-req="SWS_DM_01855" href="../spec/record.html?id=SWS_DM_01855">[SWS_DM_01855]</a> weiter.</li>
  </ul>
</li>
<li><strong>Dienstabmeldung:</strong> Sobald die Bearbeitung eingestellt werden soll, ruft die Applikation <code>StopOffer()</code> auf <a class="spec-record-ref" data-req="SWS_DM_01858" href="../spec/record.html?id=SWS_DM_01858">[SWS_DM_01858]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Bei der Verwendung von <code>ara::diag::SovdBulkData</code> sind verschiedene Fehlerarten zu unterscheiden:</p>
<ul>
<li><strong>Konfigurationsverletzungen bei der Instanziierung:</strong> Schlägt das Auflösen des Modells fehl oder passen die Mappings nicht, meldet der Konstruktor spezifische Violations <a class="spec-record-ref" data-req="SWS_DM_01847" href="../spec/record.html?id=SWS_DM_01847">[SWS_DM_01847]</a>. Dazu gehören <code>InstanceSpecifierMappingIntegrityViolation</code> (ungültiges Modell oder kein PortPrototype), <code>PortInterfaceMappingViolation</code> (falsche Typisierung des Port-Mappings), <code>ProcessMappingViolation</code> (kein passender Prozess modelliert) und <code>InstanceSpecifierAlreadyInUseViolation</code> (Specifier innerhalb des Prozesses bereits belegt).</li>
