  <h4>Role and system context of the service interface</h4>
  <p>
    The service interface <code>VerificationStatusConfigurationByFreshnessId</code> is part of the module <strong>com</strong> (Communication Management) of the AUTOSAR Adaptive Platform in release R25-11 (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=56">AUTOSAR_AP_SWS_CommunicationManagement p. 56</a>). The primary task of this interface is to selectively override the default verification behavior of SecOC (Secure Onboard Communication) (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>). The control is carried out in a granular manner based on a concrete freshness value ID (<code>freshnessID</code>).
  </p>
  <p>
    In the system context, the SecOC subsystem component of Communication Management typically acts as a provider (skeleton), while authorized control or test entities act as consumers (proxies) (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=459">AUTOSAR_AP_SWS_CommunicationManagement p. 459</a>). The purpose of the interface is to accept incoming messages despite incorrect or missing authenticators, to skip regular verifications, or to selectively drop messages (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>). This mechanism presumably serves primarily diagnostic, testing, and fault simulation scenarios in order to test downstream application fault reaction paths under controlled conditions.
  </p>

  <h4>Methods, Events, and Interface Specification</h4>
  <p>
    The interface <code>VerificationStatusConfigurationByFreshnessId</code> is defined in version 1.0 and contains the synchronous method <code>VerifyStatusOverride</code> (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>). Since the <em>Fire &amp; Forget</em> property is set to <code>false</code>, the call provides feedback on the result of the configuration request to the caller (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=459">AUTOSAR_AP_SWS_CommunicationManagement p. 459</a>).
  </p>
  <p>
    The method accepts three input parameters (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>):
  </p>
  <ul>
    <li><code>freshnessID</code> (type <code>uint16_t</code>): Designates the specific ID of the freshness value to which the override is to be applied.</li>
    <li><code>overrideStatus</code> (type <code>OverrideStatus</code>): Determines the mode of the override – in particular, whether authenticator verification is executed, whether messages are forwarded or dropped, and how long the override remains active.</li>
    <li><code>numberOfMessagesToOverride</code> (type <code>uint8_t</code>): Specifies the number of sequential messages for which the verification status is overridden.</li>
  </ul>
  <p>
    The parameter <code>numberOfMessagesToOverride</code> is explicitly evaluated only when <code>overrideStatus</code> is set to a counter-limited value, namely <code>kSecOcOverrideDropUntilLimit</code>, <code>kSecOcOverrideSkipUntilLimit</code>, or <code>kSecOcOverridePassUntilLimit</code> (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>).
  </p>

  <h4>Lifecycle, session sequences, and state dependencies</h4>
  <p>
    At runtime, a client application binds to the service instance via the standard service discovery mechanisms of <code>ara::com</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=57">AUTOSAR_AP_SWS_CommunicationManagement p. 57</a>). As soon as the proxy is available, the call to <code>VerifyStatusOverride</code> can be issued (<a class="spec-record-ref" data-req="SWS_CM_10049" href="../spec/record.html?id=SWS_CM_10049">[SWS_CM_10049]</a>). The override directly influences the subsequent processing of messages with the specified <code>freshnessID</code> in SecOC.
