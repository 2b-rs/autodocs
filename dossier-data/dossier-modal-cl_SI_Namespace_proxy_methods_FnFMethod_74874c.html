<h4>Context</h4>
<p>The class <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;FnFMethod&gt;</code> represents the proxy-side interface for fire-and-forget method calls within Communication Management (<code>com</code>) of the AUTOSAR Adaptive Platform. According to the service definition, a corresponding method class is generated in the proxy namespace for each operation of type <code>ClientServerOperation</code> declared in <code>ServiceInterface</code> whose attribute <code>fireAndForget</code> is set to <code>TRUE</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=347">AUTOSAR_AP_SWS_CommunicationManagement p. 347 §8.3.4.1.2 “Service Communication”</a>). In contrast to regular client-server methods that feature return values or asynchronous future objects (such as <code>ara::core::Future</code>), a fire-and-forget method is designed purely unidirectionally. The interacting partners here are the calling application component, the local instance of <code>&lt;FnFMethod&gt;</code>, and the underlying communication binding, which handles transmission to the target service without a return channel (<a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>).</p>

<h4>Lifecycle</h4>
<p>The instance of class <code>&lt;FnFMethod&gt;</code> is likely to exist as a fixed component of the generated proxy object and share its lifecycle. Upon creation of the service proxy, the method object is also available; upon destruction of the proxy, the instance is released. Because fire-and-forget calls do not manage pending response messages, no complex internal state regarding open requests exists for the method itself. The call operator is declared with the identifier <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>), supporting robust and exception-safe handling throughout the entire operational cycle. The object itself stores the state of End-to-End protection (E2E), which is updated by successive calls (<a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>).</p>

<h4>Usage Path</h4>
<p>The typical sequence for using a fire-and-forget method comprises initializing the method call as well as optionally checking the E2E state:</p>
<ol>
<li><strong>Trigger method call:</strong> The application calls the function object via the overloaded call operator <code>operator()</code>, passing the defined input arguments (<a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>). Since no response is expected, the call does not block on network replies and immediately returns <code>void</code> to the caller.</li>
<li><strong>Network transmission:</strong> The communication binding serializes the payload data and transmits the message unidirectionally to the server.</li>
<li><strong>Read E2E status:</strong> To evaluate the validity of the last E2E check, the application can call the function <code>GetE2EStateMachineState()</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=346">AUTOSAR_AP_SWS_CommunicationManagement p. 346 §8.3.4.1.1 “E2E Protection”</a>). This returns the state <code>ara::com::e2e::SMState</code>, which was determined during the last call of <code>operator()</code> by the function <code>E2E_Check()</code> (<a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>With regard to error behavior, the fire-and-forget interface is characterized by specific specification guarantees and constraints:</p>
<ul>
<li><strong>Access violation (Grant Enforcement):</strong> If the client does not possess the necessary permissions for the method call, the call is rejected by the access control system and results in an access violation (<code>InsufficientPermissionsViolation</code>) (<a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>).</li>
<li><strong>No reporting of application errors:</strong> Because fire-and-forget methods have no return value and the specification does not provide a response channel for this type, application errors of the server cannot be reported to the proxy caller via mechanisms such as <code>ara::core::ErrorCode</code> (<a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>).</li>
<li><strong>E2E error detection:</strong> Transmission errors or discrepancies in message integrity are reflected via the status of the E2E state machine. A deviating state in <code>GetE2EStateMachineState()</code> signals to the application that protection of the last send operation was faulty (<a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>).</li>
</ul>
