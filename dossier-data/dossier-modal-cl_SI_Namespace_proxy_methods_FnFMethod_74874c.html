<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht den unbestätigten Aufruf von Einweg-Methoden einer Service-Schnittstelle ohne Rückgabewert auf Client-Ebene.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Proxy-Klasse ermöglicht der Client-Anwendung das Auslösen unbestätigter Methodenaufrufe für Service-Operationen mit Fire-and-Forget-Semantik <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>. Beim Aufruf des Funktionsoperators werden die Eingabeparameter übermittelt, ohne dass ein Rückgabewert oder ein Antwort-Future für ein Ergebnis erzeugt wird. Gleichzeitig wird bei jedem Methodenaufruf die Ende-zu-Ende-Absicherung ausgeführt, deren aktueller Prüfzustand separat abgefragt werden kann <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>. Ein Aufruf erfolgt ausnahmesicher, scheitert jedoch bei unzureichenden Zugriffsrechten mit einer Berechtigungsverletzung.</p>

<h4>Kontext</h4>
<p>Die Klasse <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;FnFMethod&gt;</code> repräsentiert eine Fire-and-Forget-Methode auf der Client- bzw. Proxy-Seite im Kommunikationsmanagement der AUTOSAR Adaptive Platform <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>. In einer serviceorientierten Architektur existiert für jede in der Schnittstelle definierte Operation (<code>ClientServerOperation</code>), bei der <code>ClientServerOperation.fireAndForget == TRUE</code> festgelegt ist, genau eine solche Instanz in der Proxy-Rolle <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=347">SWS CommunicationManagement §8.3.4.1.2.1 „operator()“</a>.</p>
<p>Ihre Kernverantwortung liegt in der Entgegennahme von Aufrufargumenten und deren Weiterleitung an die Übertragungsschicht. Anders als bei synchronen oder asynchronen bidirektionalen Aufrufen, die den Aufrufer über ein <code>ara::core::Future</code> benachrichtigen und etwaige Anwendungsfehler transportieren <a class="spec-record-ref" data-req="SWS_CM_00197" href="../spec/record.html?id=SWS_CM_00197">[SWS_CM_00197]</a>, verlangt ein Fire-and-Forget-Aufruf weder eine Antwort noch eine Bestätigung der Serverseite. Die Interaktionspartner umfassen die aufrufende Client-Anwendung, die Methodeninstanz des Service-Proxys sowie das nachgelagerte Kommunikations-Binding inklusive der E2E-Absicherung.</p>

<h4>Lebenszyklus</h4>
<p>Die Deklaration der Klasse erfolgt innerhalb der generierten Header-Datei <code>#include "&lt;SiNamespaceDerivedDirectoryPath&gt;/&lt;SiShortname&gt;_proxy.h"</code> im hierarchischen Scope <code>&lt;SI-Namespace&gt;::proxy::methods::&lt;FnFMethod&gt;</code> <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>. Die Lebensdauer der Methodeninstanz dürfte an die Lebensdauer des übergeordneten Service-Proxy-Objekts gekoppelt sein (Interpretation: Die Methode wird als Subobjekt zusammen mit dem Service-Proxy erzeugt und zerstört).</p>
<p>Über den reinen Aufruf hinaus besitzt die Klasse einen internen Status bezüglich des E2E-Schutzes (End-to-End-Protection). Dieser E2E-Zustand wird bei jedem Methodenaufruf über die Funktion <code>E2E_Check()</code> ermittelt und kann über <code>GetE2EStateMachineState()</code> abgefragt werden, welche den Statuswert vom Typ <code>ara::com::e2e::SMState</code> liefert <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=346">SWS CommunicationManagement §8.3.4.1.1.1 „GetE2EStateMachineState“</a>. Sämtliche Elementfunktionen sind als <code>noexcept</code> deklariert <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>, <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>; bei gleichzeitigem Aufruf aus mehreren Threads dürfte eine externe Synchronisation erforderlich sein, falls das Binding keine Reentrancy garantiert.</p>

<h4>Nutzungspfad</h4>
<p>Der typische Ablauf zur Nutzung einer Fire-and-Forget-Methode umfasst folgende Schritte:</p>
<ul>
<li><strong>Proxy-Bereitstellung:</strong> Die Anwendung instanziiert oder beschafft den generierten Service-Proxy über die definierte Header-Schnittstelle <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>.</li>
<li><strong>Methodenaufruf ausführen:</strong> Die Anwendung ruft das Methodenobjekt über <code>operator()</code> unter Übergabe der Eingabeparameter auf <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>. Die Funktion liefert keinen Rückgabewert (<code>void</code>) und kehrt sofort zurück, ohne auf eine Server-Reaktion zu warten <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=347">SWS CommunicationManagement §8.3.4.1.2.1 „operator()“</a>.</li>
<li><strong>E2E-Aktualisierung:</strong> Während des Aufrufs von <code>operator()</code> führt die Middleware intern die Schutzprüfung <code>E2E_Check()</code> durch und aktualisiert die interne Zustandsmaschine <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>.</li>
<li><strong>Zustandsprüfung (optional):</strong> Die Anwendung kann über <code>GetE2EStateMachineState()</code> den resultierenden Zustand <code>ara::com::e2e::SMState</code> der Zustandsmaschine einsehen <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=346">SWS CommunicationManagement §8.3.4.1.1.1 „GetE2EStateMachineState“</a>.</li>
</ul>

<h4>Fehlerszenarien</h4>
<p>Sowohl <code>operator()</code> als auch <code>GetE2EStateMachineState()</code> sind ausnahmesicher (exception safe) und als <code>noexcept</code> deklariert <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>, <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>. Es werden daher keine C++-Ausnahmen ausgelöst.</p>
<p>Bei fehlenden Zugriffsrechten greift die Rechteprüfung (Grant Enforcement): Fehlen dem aufrufenden Kontext die notwendigen Berechtigungen, wird der Aufruf verweigert und eine <code>InsufficientPermissionsViolation</code> registriert <a class="spec-record-ref" data-req="SWS_CM_90435" href="../spec/record.html?id=SWS_CM_90435">[SWS_CM_90435]</a>.</p>
<p>Da keine Rückgabe über ein <code>ara::core::Future</code> erfolgt und Fire-and-Forget-Operationen keine Übermittlung eines <code>ApApplicationError</code> oder <code>ara::core::ErrorCode</code> unterstützen <a class="spec-record-ref" data-req="SWS_CM_00197" href="../spec/record.html?id=SWS_CM_00197">[SWS_CM_00197]</a>, werden Übertragungsfehler nicht an den Aufrufer zurückgemeldet. Etwaige Fehler in der Datensicherheit oder im Übertragungskanal manifestieren sich ausschließlich im Zustand der E2E-Zustandsmaschine, der über <code>GetE2EStateMachineState()</code> diagnostiziert werden kann <a class="spec-record-ref" data-req="SWS_CM_00147" href="../spec/record.html?id=SWS_CM_00147">[SWS_CM_00147]</a>.</p>
