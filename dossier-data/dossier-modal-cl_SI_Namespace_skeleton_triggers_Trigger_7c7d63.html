<h4>Context</h4>
<p>The C++ class <code>&lt;SI-Namespace&gt;::skeleton::triggers::&lt;Trigger&gt;</code> represents the server-side representation of a trigger within the communication module <code>com</code> of the AUTOSAR Adaptive Platform. According to the model architecture, exactly one corresponding instance of this class exists in the generated service skeleton for each trigger defined in the ServiceInterface in the role <em>trigger</em>. Unlike classic events, a trigger serves purely to notify subscribing applications of the occurrence of an event or to request action execution, without any additional payload being transmitted (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">EXP ARAComAPI p. 10</a>).</p>
<p>The central interaction partners are the offering service application (skeleton implementation), the runtime environment of <code>ara::com</code>, and subscribing client applications on the proxy side. The offering application uses the trigger instance to send signals to all currently registered subscribers (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>). The middleware handles forwarding via the respective communication protocols, such as SOME/IP (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=95">SWS CommunicationManagement p. 95</a>).</p>

<h4>Lifecycle</h4>
<p>The trigger class is declared via the header <code>&lt;SiNamespaceDerivedDirectoryPath&gt;/&lt;SiShortname&gt;_skeleton.h</code>. Instances of the trigger class are likely created as member elements of the respective service skeleton and thus share the lifetime of the parent service object.</p>
<p>The lifecycle of the trigger instance is significantly shaped by the subscription status of the consumers. The offering application can query the current state of the subscription via <a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a> (<code>GetSubscriptionState()</code>). To be actively informed of state changes, a notification handler can be registered (<a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>). For scenarios with specific requirements regarding concurrency or thread allocation, the overload <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a> provides the option to pass a custom executor (<code>ExecutorT</code>) in whose context the handler is called. If monitoring of the subscriber status is no longer needed, the handler can be deregistered via <a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a> (<code>UnsetSubscriptionStateChangeHandler()</code>).</p>
<p>With regard to exception and error safety, all member functions of the trigger class are declared with the specifier <code>noexcept</code> and defined as exception safe (<em>exception safe</em>) (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>, <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>, <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>, <a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>).</p>

<h4>Usage Path</h4>
<p>A typical sequence for using a trigger instance on the server side comprises the following steps:</p>
<ol>
<li><strong>Setting up monitoring:</strong> The service application optionally registers a callback for changes in subscriber status via <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a> or with a specified execution context via <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>.</li>
<li><strong>Checking subscription status:</strong> Using <a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>, it can be synchronously determined whether clients have subscribed to the trigger. Requesting the transmission of a trigger requires that at least one active subscriber exists (<a class="spec-record-ref" data-req="SWS_CM_10518" href="../spec/record.html?id=SWS_CM_10518">[SWS_CM_10518]</a> in <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=154">SWS CommunicationManagement p. 154</a>).</li>
<li><strong>Triggering the trigger:</strong> The trigger is sent to all subscribing applications by calling <code>Send()</code> (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">EXP ARAComAPI p. 10</a>).</li>
<li><strong>Evaluating the result:</strong> The call to <code>Send()</code> returns a <code>ara::core::Result&lt;void&gt;</code>, which indicates whether the transmission was successfully initiated or an error occurred (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><strong>Removing the handler:</strong> Before destruction or when no longer needed, the registered callback is deleted via <a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>When working with the trigger class, specific error and violation states can occur:</p>
<ul>
<li><strong>Service not offered (<code>ComErrc::kServiceNotOffered</code>):</strong> If <a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a> is called before the associated service has been offered via <code>OfferService()</code>, the call fails and returns the error code <code>ComErrc::kServiceNotOffered</code> with rollback semantics in <code>ara::core::Result</code>.</li>
<li><strong>Minimum send interval undershot (<code>ComErrc::kMinimumSendIntervalViolationError</code>):</strong> If a minimum send interval was configured in the deployment (<code>ServiceInterfaceDeploymentElement.minimumSendInterval</code>) and <code>Send()</code> is called before this interval has elapsed, the method reports this error (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><strong>Network transmission error (<code>ComErrc::kCommunicationFailure</code>):</strong> If sending the SOME/IP trigger fails locally due to a network error reported to the middleware, <code>Send()</code> returns the error <code>ComErrc::kCommunicationFailure</code> in the result (<a class="spec-record-ref" data-req="SWS_CM_10517" href="../spec/record.html?id=SWS_CM_10517">[SWS_CM_10517]</a> in <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=95">SWS CommunicationManagement p. 95</a>).</li>
<li><strong>Invalid handler (<code>InvalidHandlerViolation</code>):</strong> If an empty, non-existent, or null callable object is passed to <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a> or <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>, a <code>InvalidHandlerViolation</code> is raised.</li>
</ul>
