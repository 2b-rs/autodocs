<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht Service-Skeletons das Aussenden von Trigger-Signalen und das Überwachen des Abonnentenstatus.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>&lt;SI-Namespace&gt;::skeleton::triggers::&lt;Trigger&gt;</code> ermöglicht einer Server-Anwendung das Versenden von Trigger-Signalen an abonnierende Clients über das Kommunikations-Management (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>). Zur Ablaufsteuerung können Abonnentenstatus überwacht und Benachrichtigungs-Handler registriert werden (<a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>, <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>). Das Auslösen via <code>Send()</code> erfordert ein angebotenes Service-Skeleton und quittiert Verstöße gegen Mindestsendeintervalle oder Netzwerkfehler mit entsprechenden Fehlercodes (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="spec-record-ref" data-req="SWS_CM_10517" href="../spec/record.html?id=SWS_CM_10517">[SWS_CM_10517]</a>).</p>

<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Die Template-Klasse <code>&lt;SI-Namespace&gt;::skeleton::triggers::&lt;Trigger&gt;</code> repräsentiert die serverseitige Schnittstelle eines Triggers, der innerhalb eines ServiceInterface in der Rolle <em>trigger</em> definiert ist. Als Bestandteil des Dienst-Skeletts (Skeleton) dient diese Klasse einer Service-Instanz dazu, asynchrone Benachrichtigungen oder Auslösesignale an abonnierende Client-Anwendungen im Gesamtsystem zu versenden. Ein Trigger unterscheidet sich von regulären Events dadurch, dass er primär als reines Signalisierungsereignis ohne komplexe Nutzdaten fungiert, wie die Einordnung in <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">EXP_ARAComAPI §3 „Trigger::Send“</a> und <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=154">SWS_CommunicationManagement §7.2.2.1.4 „Handling Triggers“</a> darlegt. Die Interaktionspartner umfassen die bereitstellende Server-Anwendung, die Middleware Communication Management (<code>ara::com</code>) sowie über das Netzwerk angebundene Subscriber-Clients.</p>

<h4>Lebenszyklus</h4>
<p>Die Instanziierung der Trigger-Objekte erfolgt typischerweise als integraler Bestandteil der Skeleton-Instanz des jeweiligen ServiceInterface. Vor der aktiven Nutzung muss das Skeleton über das Kommunikations-Management angeboten werden; wird versucht, einen Trigger vorher auszulösen, schlägt die Übertragung fehl (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>). Die Klasse verwaltet den Subskriptionszustand der Abonnenten über <code>ara::com::SubscriptionState</code>, der jederzeit mit <code>GetSubscriptionState()</code> abgefragt werden kann (<a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>). Zur asynchronen Zustandsüberwachung kann mittels <code>SetSubscriptionStateChangeHandler()</code> ein Callback registriert werden (<a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>). Für nebenläufige Architekturen existiert eine Überladung, die einen benutzerdefinierten Executor entgegennimmt, sodass Benachrichtigungen im gewünschten Thread- oder Aufgabenkontext ausgeführt werden (<a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>). Die Registrierung lässt sich über <code>UnsetSubscriptionStateChangeHandler()</code> wieder aufheben (<a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>). Alle Methoden der Klasse bieten die Ausnahme-Garantie <code>noexcept</code> (exception safe).</p>

<h4>Nutzungspfad</h4>
<p>Der typische Ablauf zur Nutzung eines Triggers umfasst die Beobachtung des Subskriptionsstatus sowie das eigentliche Auslösen der Übertragung an alle aktiven Abonnenten:</p>
<ul>
<li><strong>Handler-Registrierung:</strong> Die Service-Anwendung registriert optional einen Zustands-Handler über <code>SetSubscriptionStateChangeHandler()</code> (<a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>, <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>), um über neu hinzukommende Abonnenten informiert zu werden.</li>
<li><strong>Zustandsprüfung:</strong> Mit <code>GetSubscriptionState()</code> prüft der Server, ob mindestens ein aktiver Subscriber vorliegt (<a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>), was gemäß <a class="spec-record-ref" data-req="SWS_CM_10518" href="../spec/record.html?id=SWS_CM_10518">[SWS_CM_10518]</a> die Voraussetzung für die Sendeanforderung bildet.</li>
<li><strong>Senden des Triggers:</strong> Das Senden wird über den Aufruf von <code>Send()</code> initiiert (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">EXP_ARAComAPI §3 „Trigger::Send“</a>), woraufhin das Kommunikations-Management das Signal an alle subskribierten Anwendungen verteilt.</li>
<li><strong>Deregistrierung:</strong> Beim Herunterfahren oder wenn keine Zustandsbenachrichtigungen mehr gewünscht sind, wird <code>UnsetSubscriptionStateChangeHandler()</code> aufgerufen (<a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>).</li>
</ul>

<h4>Fehlerszenarien</h4>
<p>Die Methode <code>Send()</code> gibt ein <code>ara::core::Result&lt;void&gt;</code> zurück, über welches eventuelle Übertragungs- und Konfigurationsfehler transportiert werden (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>):</p>
<ul>
<li><code>ComErrc::kServiceNotOffered</code>: Tritt auf, wenn die Service-Instanz noch nicht über <code>OfferService()</code> bereitgestellt wurde (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><code>ComErrc::kMinimumSendIntervalViolationError</code>: Wird zurückgegeben, falls ein konfiguriertes Mindestsendeintervall (<code>minimumSendInterval</code>) zwischen aufeinanderfolgenden Übertragungen unterschritten wurde (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><code>ComErrc::kCommunicationFailure</code>: Wird gemeldet, wenn das Versenden des Triggers lokal aufgrund eines zugrundeliegenden Netzwerkfehlers scheitert (<a class="spec-record-ref" data-req="SWS_CM_10517" href="../spec/record.html?id=SWS_CM_10517">[SWS_CM_10517]</a>).</li>
<li>Ungültiger Handler (<code>InvalidHandlerViolation</code>): Das Übergeben eines nicht vorhandenen oder leeren Funktionsaufrufs (Callable) an <code>SetSubscriptionStateChangeHandler()</code> stellt eine Verletzung der API-Vertragsbedingungen dar (<a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>, <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>).</li>
</ul>
