<h4>Role in the LIN Stack: Master and Slave Channels Behind One Interface</h4>

<p>The LIN Interface (LinIf) is the abstraction layer above the LIN driver <code>Lin</code>. It accepts requests from upper layers, implements them on the bus, and additionally contains the LIN Transport Protocol (LinTp). The LIN State Manager forwards schedule requests (master only) as well as wakeup and sleep requests to LinIf (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_5_1_4_LIN_State_Manager.html" data-snip="SNIP_CLASSIC_LIN_SECTION_5_1_4_LIN_State_Manager">SWS LinIf p. 23</a>). The LIN driver reports its events exclusively to LinIf (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_6_3_Configurable_interfaces.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_6_3_Configurable_interfaces">SWS LIN-Treiber p. 53</a>). LinIf reaches upper users via configurable callouts (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_5_3_Configurable_interfaces.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_5_3_Configurable_interfaces">SWS LinIf p. 113</a>). In R20-11, these calls are named <code>&lt;User_TriggerTransmit&gt;</code>, <code>&lt;User_TxConfirmation&gt;</code>, and <code>&lt;User_RxIndication&gt;</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00528" href="../../spec/record.html?id=SWS_LinIf_00528">[SWS_LinIf_00528]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00529" href="../../spec/record.html?id=SWS_LinIf_00529">[SWS_LinIf_00529]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00530" href="../../spec/record.html?id=SWS_LinIf_00530">[SWS_LinIf_00530]</a>). More recent document passages and diagrams name <code>LSduR</code> in their place. According to the change history, this change was introduced only with R24-11 (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_General_Overview">SWS LinIf p. 1</a>).</p>

<p>The parameter <code>LinIfNodeType</code> specifies whether a channel operates as master or slave. Slave-specific services such as <code>LinIf_HeaderIndication</code>, <code>LinIf_RxIndication</code>, or <code>LinIf_SetPIDTable</code> exist only if at least one slave channel is configured. Conversely, <code>LinIf_ScheduleRequest</code> exists only with at least one master channel (<a class="spec-record-ref" data-req="SWS_LinIf_00858" href="../../spec/record.html?id=SWS_LinIf_00858">[SWS_LinIf_00858]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00860" href="../../spec/record.html?id=SWS_LinIf_00860">[SWS_LinIf_00860]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00863" href="../../spec/record.html?id=SWS_LinIf_00863">[SWS_LinIf_00863]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00864" href="../../spec/record.html?id=SWS_LinIf_00864">[SWS_LinIf_00864]</a>). Further components can be enabled or disabled prior to compilation:</p>
<ul>
<li>LinTp via <code>LinIfTpSupported</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_15_LinTp_Init.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_15_LinTp_Init">SWS LinIf p. 99</a>),</li>
<li>Bus Mirroring via <code>LinIfBusMirroringSupported</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00875" href="../../spec/record.html?id=SWS_LinIf_00875">[SWS_LinIf_00875]</a>),</li>
<li>the callout for the <code>response_error</code> signal (<a class="spec-record-ref" data-req="SWS_LinIf_00766" href="../../spec/record.html?id=SWS_LinIf_00766">[SWS_LinIf_00766]</a>).</li>
</ul>
<p>The structures <code>LinIf_ConfigType</code> and <code>LinTp_ConfigType</code> are implementation-specific (<a class="spec-record-ref" data-req="SWS_LinIf_00668" href="../../spec/record.html?id=SWS_LinIf_00668">[SWS_LinIf_00668]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00426" href="../../spec/record.html?id=SWS_LinIf_00426">[SWS_LinIf_00426]</a>). <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-ff23a58ff96a2c15.html" data-snip="FIG-ff23a58ff96a2c15">SWS LinIf p. 96</a> provides an overview of the parameters.</p>

<h4>Lifecycle: LinIf_Init, Channel States, and Main Function per Channel</h4>

<p>After reset, LinIf is in the <code>LINIF_UNINIT</code> state. <code>LinIf_Init</code> leads to <code>LINIF_INIT</code>. There, each channel has its own sub-state machine with the states <code>LINIF_CHANNEL_OPERATIONAL</code> and <code>LINIF_CHANNEL_SLEEP</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00198" href="../../spec/record.html?id=SWS_LinIf_00198">[SWS_LinIf_00198]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_4_1_1_LIN_Interface_state_machine.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_4_1_1_LIN_Interface_state_machine">SWS LinIf p. 47</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-f39a068cfdb57355.html" data-snip="FIG-f39a068cfdb57355">SWS LinIf p. 34</a>). On master channels, <code>LinIf_Init</code> sets the <code>NULL_SCHEDULE</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_1_LinIf_Init.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_1_LinIf_Init">SWS LinIf p. 90</a>). On slave channels, it loads initial NAD, configured NAD, and PIDs from the configuration (<a class="spec-record-ref" data-req="SWS_LinIf_00767" href="../../spec/record.html?id=SWS_LinIf_00767">[SWS_LinIf_00767]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00768" href="../../spec/record.html?id=SWS_LinIf_00768">[SWS_LinIf_00768]</a>).</p>

<h4>Master Channel: Schedule Tables Determine Bus Traffic</h4>

<p>On a master channel, the schedule table is the basis of all communication. The intervals between two frames are multiples of <code>LinIfMainFunctionPeriod</code>. The predefined <code>NULL_SCHEDULE</code> contains no entries (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_2_Schedules_Master_only.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_2_Schedules_Master_only">SWS LinIf p. 44</a>). Up to 255 tables per channel can be addressed using <code>LinIf_SchHandleType</code>; the value 0 stands for <code>NULL_SCHEDULE</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00197" href="../../spec/record.html?id=SWS_LinIf_00197">[SWS_LinIf_00197]</a>). <code>LinIf_ScheduleRequest</code> operates asynchronously. It rejects with <code>E_NOT_OK</code>, for example if the channel is sleeping or the table is unknown (<a class="spec-record-ref" data-req="SWS_LinIf_00202" href="../../spec/record.html?id=SWS_LinIf_00202">[SWS_LinIf_00202]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_4_LinIf_ScheduleRequest.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_4_LinIf_ScheduleRequest">SWS LinIf p. 86</a>). Once the switch is completed, <code>&lt;User&gt;_ScheduleRequestConfirmation</code> reports this (<a class="spec-record-ref" data-req="SWS_LinIf_00520" href="../../spec/record.html?id=SWS_LinIf_00520">[SWS_LinIf_00520]</a>). In R20-11, the parameter is still named <code>Schedule</code>; it was renamed only later (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_General_Overview.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_General_Overview">SWS LinIf p. 1</a>).</p>

<p><code>LinIf_Transmit</code> does not send anything directly onto the bus. It only marks a sporadic frame (master) or an event-triggered frame (slave) as pending. For other frame types, it nevertheless returns <code>E_OK</code> as long as the active schedule is not <code>NULL_SCHEDULE</code>; there it returns <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00201" href="../../spec/record.html?id=SWS_LinIf_00201">[SWS_LinIf_00201]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00700" href="../../spec/record.html?id=SWS_LinIf_00700">[SWS_LinIf_00700]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00719" href="../../spec/record.html?id=SWS_LinIf_00719">[SWS_LinIf_00719]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_9_4_Sporadic_frame_Master_only.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_9_4_Sporadic_frame_Master_only">SWS LinIf p. 125</a>).</p>

<p>When a transmit entry is due, the following happens:</p>
<ol>
<li>LinIf fetches the payload with <code>&lt;User_TriggerTransmit&gt;</code>.</li>
<li>It passes it to the driver using <code>Lin_SendFrame</code>. If the user returns <code>E_NOT_OK</code>, the frame is not sent (<a class="spec-record-ref" data-req="SWS_LinIf_00706" href="../../spec/record.html?id=SWS_LinIf_00706">[SWS_LinIf_00706]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_7_1_3_1_1_Header_and_response.html" data-snip="SNIP_CLASSIC_LIN_SECTION_7_1_3_1_1_Header_and_response">SWS LinIf p. 37</a>).</li>
<li>LinIf queries the status with <code>Lin_GetStatus</code> at the earliest after the maximum frame length (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_7_1_2_1_3_Status_check.html" data-snip="SNIP_CLASSIC_LIN_SECTION_7_1_2_1_3_Status_check">SWS LinIf p. 35</a>).</li>
<li>In case of <code>LIN_TX_ERROR</code> or <code>LIN_TX_BUSY</code>, <code>&lt;User_TxConfirmation&gt;</code> follows with <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00728" href="../../spec/record.html?id=SWS_LinIf_00728">[SWS_LinIf_00728]</a>).</li>
</ol>

<h4>Slave Channel: Processing in Step with Received Headers</h4>

<p>A slave does not know the master's schedule. It only reacts to headers reported by the LIN driver via <code>LinIf_HeaderIndication</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_7_1_2_2_Frame_reception_in_slave_nodes.html" data-snip="SNIP_CLASSIC_LIN_SECTION_7_1_2_2_Frame_reception_in_slave_nodes">SWS LinIf p. 38</a>, <a class="spec-record-ref" data-req="SWS_LinIf_91004" href="../../spec/record.html?id=SWS_LinIf_91004">[SWS_LinIf_91004]</a>). LinIf evaluates the PID and informs the driver via <code>PduPtr</code> whether it shall receive, transmit, or ignore the frame (<a class="spec-record-ref" data-req="SWS_LinIf_00733" href="../../spec/record.html?id=SWS_LinIf_00733">[SWS_LinIf_00733]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00739" href="../../spec/record.html?id=SWS_LinIf_00739">[SWS_LinIf_00739]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00748" href="../../spec/record.html?id=SWS_LinIf_00748">[SWS_LinIf_00748]</a>). For transmit frames, LinIf calls <code>&lt;User_TriggerTransmit&gt;</code> with the driver's buffer while still inside the callback. Copying the response is handled by the driver (<a class="spec-record-ref" data-req="SWS_LinIf_00738" href="../../spec/record.html?id=SWS_LinIf_00738">[SWS_LinIf_00738]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_9_1_2_Frame_transmission_in_slave_nodes.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_9_1_2_Frame_transmission_in_slave_nodes">SWS LinIf p. 121</a>).</p>

<p>The driver callbacks follow after the header:</p>
<ul>
<li>A received response is reported by <code>LinIf_RxIndication</code>; LinIf forwards it via <code>&lt;User_RxIndication&gt;</code> (<a class="spec-record-ref" data-req="SWS_LinIf_91005" href="../../spec/record.html?id=SWS_LinIf_91005">[SWS_LinIf_91005]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00734" href="../../spec/record.html?id=SWS_LinIf_00734">[SWS_LinIf_00734]</a>).</li>
<li>A transmitted response is confirmed by <code>LinIf_TxConfirmation</code>; this is followed by <code>&lt;User_TxConfirmation&gt;</code> with <code>E_OK</code> (<a class="spec-record-ref" data-req="SWS_LinIf_91006" href="../../spec/record.html?id=SWS_LinIf_91006">[SWS_LinIf_91006]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00741" href="../../spec/record.html?id=SWS_LinIf_00741">[SWS_LinIf_00741]</a>).</li>
<li>If these callbacks arrive without a preceding matching header, LinIf ignores them (<a class="spec-record-ref" data-req="SWS_LinIf_00848" href="../../spec/record.html?id=SWS_LinIf_00848">[SWS_LinIf_00848]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00852" href="../../spec/record.html?id=SWS_LinIf_00852">[SWS_LinIf_00852]</a>).</li>
</ul>

<h4>Sleep and Wakeup: Separate Paths for Master and Slave</h4>

<p><code>LinIf_GotoSleep</code> operates asynchronously. It returns <code>E_OK</code> even if the transition is already in progress or the channel is already sleeping (<a class="spec-record-ref" data-req="SWS_LinIf_00204" href="../../spec/record.html?id=SWS_LinIf_00204">[SWS_LinIf_00204]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_5_LinIf_GotoSleep.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_5_LinIf_GotoSleep">SWS LinIf p. 88</a>). For the master, the diagram shows the sequence: The main function sends the go-to-sleep command and then evaluates <code>Lin_GetStatus</code>. <code>&lt;User&gt;_GotoSleepConfirmation</code> reports the result (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-b155193ac6fb4731.html" data-snip="FIG-b155193ac6fb4731">SWS LinIf p. 136</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00521" href="../../spec/record.html?id=SWS_LinIf_00521">[SWS_LinIf_00521]</a>). If a slave requests a wakeup prior to this confirmation, the channel remains operational (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-072529f2d5a26f6f.html" data-snip="FIG-072529f2d5a26f6f">SWS LinIf p. 37</a>).</p>

<p>A slave enters sleep mode in two cases: It receives an MRF with NAD 0, or the bus idle timer (<code>LinIfBusIdleTimeoutPeriod</code>) expires. The timer runs only in <code>LINIF_CHANNEL_OPERATIONAL</code> and restarts with every driver callback (<a class="spec-record-ref" data-req="SWS_LinIf_00750" href="../../spec/record.html?id=SWS_LinIf_00750">[SWS_LinIf_00750]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00751" href="../../spec/record.html?id=SWS_LinIf_00751">[SWS_LinIf_00751]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00752" href="../../spec/record.html?id=SWS_LinIf_00752">[SWS_LinIf_00752]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00753" href="../../spec/record.html?id=SWS_LinIf_00753">[SWS_LinIf_00753]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00754" href="../../spec/record.html?id=SWS_LinIf_00754">[SWS_LinIf_00754]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00755" href="../../spec/record.html?id=SWS_LinIf_00755">[SWS_LinIf_00755]</a>). LinIf reports the sleep request with <code>&lt;User&gt;_GotoSleepIndication</code>. <p>There are two paths for wakeup (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_4_3_Wake_up_process.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_4_3_Wake_up_process">SWS LinIf p. 51</a>):</p>
<ul>
<li><strong>Bus wakeup:</strong> EcuM checks it via <code>LinIf_CheckWakeup</code>. LinIf calls <code>Lin_CheckWakeup</code> or <code>LinTrcv_CheckWakeup</code> depending on the source. The driver confirms via <code>LinIf_WakeupConfirmation</code>, and LinIf then sets the wakeup flag of the channel (<a class="spec-record-ref" data-req="SWS_LinIf_00378" href="../../spec/record.html?id=SWS_LinIf_00378">[SWS_LinIf_00378]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00715" href="../../spec/record.html?id=SWS_LinIf_00715">[SWS_LinIf_00715]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_20_LinIf_CheckWakeup.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_20_LinIf_CheckWakeup">SWS LinIf p. 112</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_3_1_LinIf_WakeupConfirmation.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_3_1_LinIf_WakeupConfirmation">SWS LinIf p. 98</a>).</li>
<li><strong>Internal wakeup:</strong> The user calls <code>LinIf_Wakeup</code>. If the channel is sleeping and the wakeup flag is not set, LinIf calls <code>Lin_Wakeup</code>. If the channel is awake, LinIf returns <code>E_OK</code> without calling the driver (<a class="spec-record-ref" data-req="SWS_LinIf_00205" href="../../spec/record.html?id=SWS_LinIf_00205">[SWS_LinIf_00205]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_6_LinIf_Wakeup.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_6_LinIf_Wakeup">SWS LinIf p. 89</a>). If the flag is set, <code>Lin_WakeupInternal</code> is likely used instead; this is indicated by the description of the return values (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_8_2_6_LinIf_Wakeup.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_8_2_6_LinIf_Wakeup">SWS LinIf p. 89</a>).</li>
</ul>
<p>In the slave, LinIf confirms the wakeup only with the first received header and the value <code>TRUE</code>. If <code>LinIf_Wakeup</code> returns <code>E_NOT_OK</code>, LinIf reports <code>FALSE</code> beforehand. If the first header does not occur, there is no confirmation, and the timeout expires in the LinSM (<a class="spec-record-ref" data-req="SWS_LinIf_00761" href="../../spec/record.html?id=SWS_LinIf_00761">[SWS_LinIf_00761]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00762" href="../../spec/record.html?id=SWS_LinIf_00762">[SWS_LinIf_00762]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_4_3_2_Wake_up_process_in_slave_nodes.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_4_3_2_Wake_up_process_in_slave_nodes">SWS LinIf p. 52</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests">SWS LinSM p. 27</a>).</p>

<h4>Diagnostics via LIN TP and Node Configuration According to ISO 17987-3</h4>

<p>LinTp implements the Diagnostic Transport Layer of ISO 17987, independently for each channel (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_6_3_Diagnostics_Transport_Protocol.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_6_3_Diagnostics_Transport_Protocol">SWS LinIf p. 61</a>). Each channel has its own LinTp state machine:</p>
<ul>
<li><code>LinTp_Init</code> sets the state <code>LINTP_INIT</code> with the sub-state <code>LINTP_CHANNEL_IDLE</code>.</li>
<li>A detected TP message leads to <code>LINTP_CHANNEL_BUSY</code>.</li>
<li><code>LinTp_Shutdown</code> closes all connections and leads back to <code>LINTP_UNINIT</code>.</li>
</ul>

<h4>Behavior in the event of an error</h4>

<p>If development error detection is active, LinIf reports errors to the DET. These include, among others, <code>LINIF_E_UNINIT</code>, <code>LINIF_E_NONEXISTENT_CHANNEL</code>, <code>LINIF_E_PARAM_POINTER</code>, and <code>LINIF_E_SCHEDULE_REQUEST_ERROR</code> (<a class="spec-record-ref" data-req="SWS_LinIf_00376" href="../../spec/record.html?id=SWS_LinIf_00376">[SWS_LinIf_00376]</a>). Such errors occur, for example, with an invalid channel or an invalid pointer in the slave callbacks (<a class="spec-record-ref" data-req="SWS_LinIf_00843" href="../../spec/record.html?id=SWS_LinIf_00843">[SWS_LinIf_00843]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00844" href="../../spec/record.html?id=SWS_LinIf_00844">[SWS_LinIf_00844]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00849" href="../../spec/record.html?id=SWS_LinIf_00849">[SWS_LinIf_00849]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00853" href="../../spec/record.html?id=SWS_LinIf_00853">[SWS_LinIf_00853]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00855" href="../../spec/record.html?id=SWS_LinIf_00855">[SWS_LinIf_00855]</a>). LinIf recognizes <code>LINIF_E_RESPONSE</code> and <code>LINIF_E_NC_NO_RESPONSE</code> as runtime errors (<a class="spec-record-ref" data-req="SWS_LinIf_00729" href="../../spec/record.html?id=SWS_LinIf_00729">[SWS_LinIf_00729]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_8_2_Runtime_Errors.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_8_2_Runtime_Errors">SWS LinIf p. 71</a>).</p>

<p>In the slave, a fault reported by <code>LinIf_LinErrorIndication</code> is considered a lost response. LinIf then reports <code>LINIF_E_RESPONSE</code>, except in case of <code>LIN_ERR_HEADER</code>. It confirms an affected transmit frame with <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_LinIf_91007" href="../../spec/record.html?id=SWS_LinIf_91007">[SWS_LinIf_91007]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00735" href="../../spec/record.html?id=SWS_LinIf_00735">[SWS_LinIf_00735]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00742" href="../../spec/record.html?id=SWS_LinIf_00742">[SWS_LinIf_00742]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00743" href="../../spec/record.html?id=SWS_LinIf_00743">[SWS_LinIf_00743]</a>). The same applies if a new header arrives while a receive indication is still expected (<a class="spec-record-ref" data-req="SWS_LinIf_00846" href="../../spec/record.html?id=SWS_LinIf_00846">[SWS_LinIf_00846]</a>).</p>

<p>Certain response errors set the <code>response_error</code> signal. LinIf maintains it autonomously via <code>Com_SendSignal</code> and clears it again after successful transmission. Any change in the signal can be reported by a callout (<a class="spec-record-ref" data-req="SWS_LinIf_00736" href="../../spec/record.html?id=SWS_LinIf_00736">[SWS_LinIf_00736]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00744" href="../../spec/record.html?id=SWS_LinIf_00744">[SWS_LinIf_00744]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00763" href="../../spec/record.html?id=SWS_LinIf_00763">[SWS_LinIf_00763]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00764" href="../../spec/record.html?id=SWS_LinIf_00764">[SWS_LinIf_00764]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00747" href="../../spec/record.html?id=SWS_LinIf_00747">[SWS_LinIf_00747]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00765" href="../../spec/record.html?id=SWS_LinIf_00765">[SWS_LinIf_00765]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_7_5_Status_Management.html" data-snip="SNIP_CLASSIC_LIN_SECTION_7_5_Status_Management">SWS LinIf p. 58</a>).</p>

<p>In the node configuration, the following applies (<a class="spec-record-ref" data-req="SWS_LinIf_00785" href="../../spec/record.html?id=SWS_LinIf_00785">[SWS_LinIf_00785]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00786" href="../../spec/record.html?id=SWS_LinIf_00786">[SWS_LinIf_00786]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00787" href="../../spec/record.html?id=SWS_LinIf_00787">[SWS_LinIf_00787]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00788" href="../../spec/record.html?id=SWS_LinIf_00788">[SWS_LinIf_00788]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00789" href="../../spec/record.html?id=SWS_LinIf_00789">[SWS_LinIf_00789]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00790" href="../../spec/record.html?id=SWS_LinIf_00790">[SWS_LinIf_00790]</a>, <a class="spec-record-ref" data-req="SWS_LinIf_00791" href="../../spec/record.html?id=SWS_LinIf_00791">[SWS_LinIf_00791]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_6_2_4_1_Node_Configuration_error.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_6_2_4_1_Node_Configuration_error">SWS LinIf p. 66</a>):</p>
