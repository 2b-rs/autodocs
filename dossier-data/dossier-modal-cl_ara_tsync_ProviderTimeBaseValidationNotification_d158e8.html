<h4>Context</h4>
<p>The class <code>ara::tsync::ProviderTimeBaseValidationNotification</code> is an abstract interface (callback interface) within the AUTOSAR Adaptive module <code>tsync</code>. It serves to notify a higher-level validator application of the availability of new measurement data blocks recorded for a time base.</p>
<p>In a time-synchronized overall system, typically three core components interact:</p>
<ul>
<li><strong>tsync provider (Time Base):</strong> The synchronization subsystem acquires protocol and timing data at runtime. As soon as a new measurement block is available, the provider calls the corresponding notification methods.</li>
<li><strong>ProviderTimeBaseValidationNotification:</strong> The abstract callback interface defines the invocation contracts for transmitting master and responder measurement data (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>, <a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>).</li>
<li><strong>Validator application:</strong> The application-specific logic implements this interface in order to evaluate the received measurement blocks, perform plausibility checks, and monitor the validity of the time base.</li>
</ul>

<h4>Lifecycle</h4>
<p>Since <code>ProviderTimeBaseValidationNotification</code> represents a purely abstract base class with pure virtual member functions, it cannot be directly instantiated. Its lifecycle is divided into the following phases:</p>
<ul>
<li><strong>Creation and ownership:</strong> The validator application derives a concrete observer class from <code>ProviderTimeBaseValidationNotification</code> and instantiates it. Ownership remains with the validator application.</li>
<li><strong>Provision:</strong> Interpretation: The created callback instance is registered at the time base of the tsync provider to be monitored, so that the provider can hold references to it and execute method calls.</li>
<li><strong>States:</strong> The interface itself has no internal state storage. After registration, the object remains in the ready-to-receive state for incoming measurement data.</li>
<li><strong>Destruction:</strong> The class has a virtual default destructor <code>~ProviderTimeBaseValidationNotification() noexcept = default;</code> (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>). This ensures that polymorphic instances are properly cleaned up upon deallocation via a pointer to the interface. Before destroying the object, it must be ensured that the tsync provider sends no further notifications to this instance.</li>
<li><strong>Concurrency:</strong> According to the specification, the interface methods are classified as <code>non_threadsafe</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>, <a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>). The validator application must therefore not assume that parallel calls can be processed thread-safely without external synchronization mechanisms.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical usage path describes the receipt and forwarding of timing measurement data during active operation of the time base:</p>
<ol>
<li><strong>Callback implementation:</strong> The application overrides the two interface methods <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>) and <code>SetPdelayResponderData</code> (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>).</li>
<li><strong>Provision at the time base:</strong> Presumably, the application passes a reference to the derived instance to the tsync subsystem in order to activate monitoring.</li>
<li><strong>Receipt of Time Master data:</strong> As soon as a new measurement data block is available for the Time Master of the time base, the tsync subsystem calls the method <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>). The caller passes the parameter <code>measurementData</code> of type <code>const TimeMasterMeasurementType&amp;</code>, which contains detailed validation data of the Time Master.</li>
<li><strong>Receipt of Pdelay Responder data:</strong> If recorded measurement data is available for the pDelay responder of the time base, <code>SetPdelayResponderData</code> is called (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>). In this case, a data block of type <code>const PdelayResponderMeasurementType&amp;</code> is passed for evaluation.</li>
<li><strong>Evaluation and termination:</strong> The validator application checks the received measurement data for conformity and threshold deviations. Upon system stop or termination of validation, the instance is released via the virtual destructor (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>With regard to error handling and boundary conditions, the following requirements apply to <code>ProviderTimeBaseValidationNotification</code>:</p>
<ul>
<li><strong>Exception safety:</strong> All member functions – <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>), <code>SetPdelayResponderData</code> (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>), and the destructor (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>) – are declared as <code>noexcept</code> and specified as <code>exception safe</code>. Implementations of the validator application must not allow C++ exceptions to escape from the callbacks, as an exception condition in a <code>noexcept</code> function directly leads to program termination via <code>std::terminate</code>.</li>
<li><strong>Return values and error signaling:</strong> The methods have the return type <code>void</code>. Direct feedback regarding success or failure to the tsync provider is not provided via this interface.</li>
<li><strong>Validity of references:</strong> The passed measurement data structures are passed as const references. The called application must assume that the validity of the data may be restricted to the duration of the method call, which is why values requiring persistence should be copied into custom application structures.</li>
<li><strong>Concurrent access:</strong> Since both notification functions are designated as <code>non_threadsafe</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>, <a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>), simultaneous invocation from multiple threads constitutes a precondition violation. The calls are likely made synchronously by the framework; if an implementation modifies internal data structures, it must make its own synchronization provisions.</li>
</ul>
