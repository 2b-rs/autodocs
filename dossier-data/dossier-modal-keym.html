<h4>Role of KeyM between key master, applications, and CSM</h4>
<p>The Key Manager (KeyM) consists of two submodules. The crypto key submodule initializes, updates, and maintains the cryptographic key material of an ECU, for example keys for Secured I-PDUs. These keys are provided by a key master, which can reside in the vehicle or in a backend. Communication with it usually takes place via diagnostic commands (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_1_Crypto_key_submodule.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_1_Crypto_key_submodule">SWS KeyM p. 24</a>). The certificate submodule holds the status of PKI certificates and provides their contents (<a class="spec-record-ref" data-req="SWS_KeyM_00066" href="../../spec/record.html?id=SWS_KeyM_00066">[SWS_KeyM_00066]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00083" href="../../spec/record.html?id=SWS_KeyM_00083">[SWS_KeyM_00083]</a>). KeyM does not store key material itself. It passes it to CSM keys via the mandatory interfaces <code>Csm_KeyElementSet</code>, <code>Csm_KeyElementGet</code>, and <code>Csm_KeySetValid</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00076" href="../../spec/record.html?id=SWS_KeyM_00076">[SWS_KeyM_00076]</a>). Further interfaces used are <code>Csm_KeyDerive</code>, <code>Csm_SignatureVerify</code>, <code>Det_ReportError</code>, and <code>IdsM_SetSecurityEvent</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00078" href="../../spec/record.html?id=SWS_KeyM_00078">[SWS_KeyM_00078]</a>).</p>
<p>Application SWCs access it via RTE ports. For each certificate there is a port <code>KeyMCertificate_{KeyMCertificate}</code>, for each certificate element a port <code>KeyMCertificateElement_…</code>, plus the ports <code>KeyMCryptoKey</code> and <code>KeyMCryptoKeyNotification</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00160" href="../../spec/record.html?id=SWS_KeyM_00160">[SWS_KeyM_00160]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00162" href="../../spec/record.html?id=SWS_KeyM_00162">[SWS_KeyM_00162]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00163" href="../../spec/record.html?id=SWS_KeyM_00163">[SWS_KeyM_00163]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00164" href="../../spec/record.html?id=SWS_KeyM_00164">[SWS_KeyM_00164]</a>). BSW modules also use KeyM:</p>
<ul>
<li>The TLS implementation of TcpIp retrieves certificates using <code>KeyM_GetCertificate</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_9_6_Connection_setup_for_a_TLS_server.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_9_6_Connection_setup_for_a_TLS_server">SWS TcpIp p. 134</a>).</li>
<li>The DCM reads whitelists using <code>KeyM_CertElementGetFirst</code>/<code>KeyM_CertElementGetNext</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_4_2_10_5_Definition_and_verification_of_white_lists.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_4_2_10_5_Definition_and_verification_of_white_lists">SWS DCM p. 162</a>).</li>
<li>The DCM receives verification results via the <code>Dcm_KeyMAsyncCertificateVerifyFinished</code> configured as a callback (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DCM_SECTION_8_4_11_Dcm_KeyMAsyncCertificateVerifyFinished.html" data-snip="SNIP_CLASSIC_DCM_SECTION_8_4_11_Dcm_KeyMAsyncCertificateVerifyFinished">SWS DCM p. 245</a>).</li>
</ul>

<h4>Certificate chain and its configuration</h4>
<p>Certificates are described in the configuration via <code>KeyMCertificate</code> containers. At runtime, they are addressed via the handles <code>KeyM_CertificateIdType</code> and <code>KeyM_CertElementIdType</code>, both of type <code>uint16</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00301" href="../../spec/record.html?id=SWS_KeyM_00301">[SWS_KeyM_00301]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00300" href="../../spec/record.html?id=SWS_KeyM_00300">[SWS_KeyM_00300]</a>). Each container contains three references:</p>
<ul>
<li>to the parent certificate; the root certificate references itself here,</li>
<li>to a CSM job for signature verification,</li>
<li>to a CSM key for the public key of the certificate.</li>
</ul>
<p><a class="docref internal-spec-ref" href="../../../spec/figures/FIG-184e708d9b59a652.html" data-snip="FIG-184e708d9b59a652">SWS KeyM (Fig. 7.3) p. 22</a> shows this structure. If all verification steps are error-free, KeyM sets the public key into the CSM key referenced via <code>KeyMCertCsmSignatureVerifyKeyRef</code> and validates it with <code>Csm_KeySetValid</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00170" href="../../spec/record.html?id=SWS_KeyM_00170">[SWS_KeyM_00170]</a>).</p>
<p>Certificate data is passed as <code>KeyM_CertDataType</code>. The structure consists of <code>certDataLength</code> and a pointer <code>certData</code> to a buffer of the caller (<a class="spec-record-ref" data-req="SWS_KeyM_00041" href="../../spec/record.html?id=SWS_KeyM_00041">[SWS_KeyM_00041]</a>). The sizes of the RTE data types result from the configuration: <code>KeyMKeyCertNameMaxLength</code> for names and <code>KeyMCertificateElementMaxLength</code> for element buffers (<a class="spec-record-ref" data-req="SWS_KeyM_91000" href="../../spec/record.html?id=SWS_KeyM_91000">[SWS_KeyM_91000]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_91004" href="../../spec/record.html?id=SWS_KeyM_91004">[SWS_KeyM_91004]</a>).</p>

<h4>Certificate status: from setting to validity</h4>
<p>Each certificate has a status of type <code>KeyM_CertificateStatusType</code>, which <code>KeyM_CertGetStatus</code> provides (<a class="spec-record-ref" data-req="SWS_KeyM_91003" href="../../spec/record.html?id=SWS_KeyM_91003">[SWS_KeyM_91003]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00066" href="../../spec/record.html?id=SWS_KeyM_00066">[SWS_KeyM_00066]</a>). The life cycle according to <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-8e89b05254c6216d.html" data-snip="FIG-8e89b05254c6216d">SWS KeyM (Fig. 7.4) p. 24</a>:</p>
<ul>
<li>After <code>KeyM_Init</code>, the certificate is set to <code>KEYM_CERTIFICATE_NOT_AVAILABLE</code>.</li>
<li><code>KeyM_SetCertificate</code> with length &gt; 0, <code>KeyM_ServiceCertificate</code>, or loading during startup leads to the transient status <code>KEYM_CERTIFICATE_NOT_PARSED</code>.</li>
<li>After successful parsing, <code>KEYM_CERTIFICATE_PARSED_NOT_VALIDATED</code> follows.</li>
<li><code>KeyM_SetCertificate</code> with length 0 resets the certificate and status.</li>
</ul>
<p>A certificate reaches <code>KEYM_CERTIFICATE_VALID</code> only after complete, error-free verification (<a class="spec-record-ref" data-req="SWS_KeyM_00170" href="../../spec/record.html?id=SWS_KeyM_00170">[SWS_KeyM_00170]</a>). If the check fails, a specific error status remains, such as <code>KEYM_E_CERTIFICATE_VALIDITY_PERIOD_FAIL</code>, <code>KEYM_E_CERTIFICATE_SIGNATURE_FAIL</code>, or <code>KEYM_E_CERTIFICATE_INVALID_CHAIN_OF_TRUST</code> (<a class="spec-record-ref" data-req="SWS_KeyM_91003" href="../../spec/record.html?id=SWS_KeyM_91003">[SWS_KeyM_91003]</a>).</p>

<p><code>KeyM_SetCertificate</code> stores a presented certificate only temporarily in the configured storage class, typically in RAM. For persistent storage, such as for the root certificate, <code>KeyM_ServiceCertificate</code> is provided (<a class="spec-record-ref" data-req="SWS_KeyM_00057" href="../../spec/record.html?id=SWS_KeyM_00057">[SWS_KeyM_00057]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_2_3_Certificate_configuration.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_2_3_Certificate_configuration">SWS KeyM p. 31</a>). For asynchronous verification, there are three variants:</p>
<ul>
<li><code>KeyM_VerifyCertificates</code> checks exactly one pair consisting of a lower and upper certificate (<a class="spec-record-ref" data-req="SWS_KeyM_00059" href="../../spec/record.html?id=SWS_KeyM_00059">[SWS_KeyM_00059]</a>).</li>
<li><code>KeyM_VerifyCertificate</code> determines the chain for a set certificate itself from the stored certificates (<a class="spec-record-ref" data-req="SWS_KeyM_00060" href="../../spec/record.html?id=SWS_KeyM_00060">[SWS_KeyM_00060]</a>).</li>
<li><code>KeyM_VerifyCertificateChain</code> checks a chain provided by the caller and sorted in PKI order (<a class="spec-record-ref" data-req="SWS_KeyM_00061" href="../../spec/record.html?id=SWS_KeyM_00061">[SWS_KeyM_00061]</a>).</li>
</ul>

<h4>Certificate services and access to certificate elements</h4>
<p>If <code>KeyMServiceCertificateFunctionEnabled</code> and <code>KeyMCertificateManagerEnabled</code> are set, the certificate submodule offers <code>KeyM_ServiceCertificate</code>. Via this, the key master introduces or updates persistently stored certificates (<a class="spec-record-ref" data-req="SWS_KeyM_00021" href="../../spec/record.html?id=SWS_KeyM_00021">[SWS_KeyM_00021]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00056" href="../../spec/record.html?id=SWS_KeyM_00056">[SWS_KeyM_00056]</a>). The operation is selected via <code>KeyM_ServiceCertificateType</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00039" href="../../spec/record.html?id=SWS_KeyM_00039">[SWS_KeyM_00039]</a>):</p>
<ul>
<li>request CSR or restore signed CSR,</li>
<li>set or update root or intermediate certificate,</li>
<li>provide revocation list,</li>
<li>vendor-specific extensions in the reserved range 0x80–0x9F.</li>
</ul>
<p>The operation runs asynchronously and ends with <code>KeyM_ServiceCertificateCallbackNotification</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00149" href="../../spec/record.html?id=SWS_KeyM_00149">[SWS_KeyM_00149]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00152" href="../../spec/record.html?id=SWS_KeyM_00152">[SWS_KeyM_00152]</a>). Optionally, the key handler <code>KeyM_KH_ServiceCertificate</code> can be integrated (<a class="spec-record-ref" data-req="SWS_KeyM_00072" href="../../spec/record.html?id=SWS_KeyM_00072">[SWS_KeyM_00072]</a>).</p>
<p>Differences from later releases: These add <code>KeyM_ServiceCertificateByCertId</code> and reduce the callback to <code>CertId</code> and <code>Result</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_8_7_3_10_KeyM_ServiceCertificateCallbackNotification.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_8_7_3_10_KeyM_ServiceCertificateCallbackNotification">SWS KeyM p. 92</a>). For R20-11, the signature with <code>ResultDataLength</code> and <code>ResultDataPtr</code> applies (<a class="spec-record-ref" data-req="SWS_KeyM_00147" href="../../spec/record.html?id=SWS_KeyM_00147">[SWS_KeyM_00147]</a>). Installation and update attempts for root and intermediate certificates are standardized as security events <code>KEYM_SEV_INST_ROOT_CERT_OP</code> through <code>KEYM_SEV_UPD_INTERMEDIATE_CERT_OP</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00172" href="../../spec/record.html?id=SWS_KeyM_00172">[SWS_KeyM_00172]</a>).</p>

<ul>
<li>using <code>KeyM_CertElementGetFirst</code>/<code>KeyM_CertElementGetNext</code> and a <code>KeyM_CertElementIteratorType</code> held by the caller, which must remain unchanged until the end (<a class="spec-record-ref" data-req="SWS_KeyM_00064" href="../../spec/record.html?id=SWS_KeyM_00064">[SWS_KeyM_00064]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00065" href="../../spec/record.html?id=SWS_KeyM_00065">[SWS_KeyM_00065]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00042" href="../../spec/record.html?id=SWS_KeyM_00042">[SWS_KeyM_00042]</a>),</li>
<li>index-based using <code>KeyM_CertificateElementGetCount</code> and <code>KeyM_CertificateElementGetByIndex</code> (<a class="spec-record-ref" data-req="SWS_KeyM_91015" href="../../spec/record.html?id=SWS_KeyM_91015">[SWS_KeyM_91015]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_91014" href="../../spec/record.html?id=SWS_KeyM_91014">[SWS_KeyM_91014]</a>).</li>
</ul>
<p>Iteration is permitted only for elements with <code>KeyMCertificateElementHasIteration</code> = TRUE (<a class="spec-record-ref" data-req="SWS_KeyM_00148" href="../../spec/record.html?id=SWS_KeyM_00148">[SWS_KeyM_00148]</a>).</p>

<h4>Key update as a Start–Prepare–Update–Finalize session</h4>
<p>The crypto key submodule can be operated in a session-like manner. <code>KeyM_Start</code> opens the session, <code>KeyM_Finalize</code> closes it; in between, operations such as <code>KeyM_Prepare</code> and <code>KeyM_Update</code> are accepted (<a class="spec-record-ref" data-req="SWS_KeyM_00050" href="../../spec/record.html?id=SWS_KeyM_00050">[SWS_KeyM_00050]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00053" href="../../spec/record.html?id=SWS_KeyM_00053">[SWS_KeyM_00053]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_1_1_General_behavior.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_1_1_General_behavior">SWS KeyM p. 25</a>). <code>KeyM_StartType</code> distinguishes the OEM production mode with higher privileges from the workshop mode (<a class="spec-record-ref" data-req="SWS_KeyM_00038" href="../../spec/record.html?id=SWS_KeyM_00038">[SWS_KeyM_00038]</a>).</p>
<p>If a key handler is activated, <code>KeyM_Start</code> passes the parameters to <code>KeyM_KH_Start</code> and adopts its return value. In this way, vendor-specific signature verifications can be implemented, for example (<a class="spec-record-ref" data-req="SWS_KeyM_00067" href="../../spec/record.html?id=SWS_KeyM_00067">[SWS_KeyM_00067]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_1_1_General_behavior.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_1_1_General_behavior">SWS KeyM p. 25</a>). Accordingly, <code>KeyM_Prepare</code> and <code>KeyM_Finalize</code> delegate to <code>KeyM_KH_Prepare</code> and <code>KeyM_KH_Finalize</code>, respectively (<a class="spec-record-ref" data-req="SWS_KeyM_00068" href="../../spec/record.html?id=SWS_KeyM_00068">[SWS_KeyM_00068]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00070" href="../../spec/record.html?id=SWS_KeyM_00070">[SWS_KeyM_00070]</a>). Completion of the finalization is reported by <code>KeyM_CryptoKeyFinalizeCallbackNotification</code> if <code>KeyMCryptoKeyStartFinalizeFunctionEnabled</code> is set (<a class="spec-record-ref" data-req="SWS_KeyM_00080" href="../../spec/record.html?id=SWS_KeyM_00080">[SWS_KeyM_00080]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00079" href="../../spec/record.html?id=SWS_KeyM_00079">[SWS_KeyM_00079]</a>).</p>

<p><code>KeyM_Update</code> operates asynchronously (<a class="spec-record-ref" data-req="SWS_KeyM_00052" href="../../spec/record.html?id=SWS_KeyM_00052">[SWS_KeyM_00052]</a>). KeyM finds the target key in one of two ways:</p>
<ul>
<li>via the name in <code>KeyMCryptoKeyName</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00091" href="../../spec/record.html?id=SWS_KeyM_00091">[SWS_KeyM_00091]</a>),</li>
<li>without a valid name, via bits 121..124 of the request data interpreted as SHE-M1M2M3, matched against <code>KeyMCryptoKeyCryptoProps</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00154" href="../../spec/record.html?id=SWS_KeyM_00154">[SWS_KeyM_00154]</a>).</li>
</ul>
<p>Without a match and without a key handler, the call ends with <code>KEYM_E_PARAMETER_MISMATCH</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00155" href="../../spec/record.html?id=SWS_KeyM_00155">[SWS_KeyM_00155]</a>). With a key handler, the update proceeds as follows:</p>
<ol>
<li>KeyM calls <code>KeyM_KH_Update</code> with the found key or <code>0xFFFFFFFFul</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00092" href="../../spec/record.html?id=SWS_KeyM_00092">[SWS_KeyM_00092]</a>), providing an internal buffer in the process (<a class="spec-record-ref" data-req="SWS_KeyM_00097" href="../../spec/record.html?id=SWS_KeyM_00097">[SWS_KeyM_00097]</a>).</li>
<li>If the handler reports <code>KEYM_KH_UPDATE_KEY_UPDATE_REPEAT</code> with data, KeyM stores or derives the key in the CSM and calls the handler again (<a class="spec-record-ref" data-req="SWS_KeyM_00096" href="../../spec/record.html?id=SWS_KeyM_00096">[SWS_KeyM_00096]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00055" href="../../spec/record.html?id=SWS_KeyM_00055">[SWS_KeyM_00055]</a>).</li>
<li>If the handler reports <code>KEYM_KH_UPDATE_FINISH</code>, KeyM copies the result into the buffer of the caller and calls <code>KeyM_CryptoKeyUpdateCallbackNotification</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00093" href="../../spec/record.html?id=SWS_KeyM_00093">[SWS_KeyM_00093]</a>).</li>
</ol>
<p>Until this callback, the caller must not modify the result buffer (<a class="spec-record-ref" data-req="SWS_KeyM_00156" href="../../spec/record.html?id=SWS_KeyM_00156">[SWS_KeyM_00156]</a>).</p>

<h4>Module operation: initialization, timing, and invocation rules</h4>
<p><code>KeyM_Init</code> initializes the module (<a class="spec-record-ref" data-req="SWS_KeyM_00043" href="../../spec/record.html?id=SWS_KeyM_00043">[SWS_KeyM_00043]</a>). The configuration pointer must always be <code>NULL_PTR</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00158" href="../../spec/record.html?id=SWS_KeyM_00158">[SWS_KeyM_00158]</a>), although the parameter description specifies a post-build configuration set. Interpretation: In R20-11, the configuration is therefore presumably not passed via this pointer in practice. <code>KeyM_Deinit</code> sets the module to the uninitialized state (<a class="spec-record-ref" data-req="SWS_KeyM_00047" href="../../spec/record.html?id=SWS_KeyM_00047">[SWS_KeyM_00047]</a>). The version starting from R23-11 additionally requires active erasing of key material in RAM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_8_3_1_2_KeyM_Deinit.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_8_3_1_2_KeyM_Deinit">SWS KeyM p. 49</a>).</p>
<p><code>KeyM_MainFunction</code> is called periodically at the configured interval (<a class="spec-record-ref" data-req="SWS_KeyM_00074" href="../../spec/record.html?id=SWS_KeyM_00074">[SWS_KeyM_00074]</a>). <code>KeyM_MainBackgroundFunction</code> runs during idle times of a preemptive operating system and is suitable for time-consuming synchronous functions such as <code>KeyM_KH_Update</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00075" href="../../spec/record.html?id=SWS_KeyM_00075">[SWS_KeyM_00075]</a>). Presumably, these functions advance the asynchronous services: the APIs report their acceptance with <code>E_OK</code>, and their completion via a callback (<a class="spec-record-ref" data-req="SWS_KeyM_00060" href="../../spec/record.html?id=SWS_KeyM_00060">[SWS_KeyM_00060]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00052" href="../../spec/record.html?id=SWS_KeyM_00052">[SWS_KeyM_00052]</a>). The services are entirely non-reentrant; the iterator functions are reentrant only per iterator (<a class="spec-record-ref" data-req="SWS_KeyM_00057" href="../../spec/record.html?id=SWS_KeyM_00057">[SWS_KeyM_00057]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00064" href="../../spec/record.html?id=SWS_KeyM_00064">[SWS_KeyM_00064]</a>). Callback names are configurable and are included via <code>KeyM_Externals.h</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00073" href="../../spec/record.html?id=SWS_KeyM_00073">[SWS_KeyM_00073]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_8_7_3_11_KeyM_CertificateVerifyCallbackNotification.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_8_7_3_11_KeyM_CertificateVerifyCallbackNotification">SWS KeyM p. 91</a>).</p>

<h4>Behavior in the event of an error</h4>
<p>With development error detection enabled, KeyM checks upon each call (<a class="spec-record-ref" data-req="SWS_KeyM_00144" href="../../spec/record.html?id=SWS_KeyM_00144">[SWS_KeyM_00144]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00145" href="../../spec/record.html?id=SWS_KeyM_00145">[SWS_KeyM_00145]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00146" href="../../spec/record.html?id=SWS_KeyM_00146">[SWS_KeyM_00146]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00036" href="../../spec/record.html?id=SWS_KeyM_00036">[SWS_KeyM_00036]</a>):</p>
<ul>
<li>the initialization (<code>KEYM_E_UNINIT</code>),</li>
<li>the buffer sizes (<code>KEYM_E_SMALL_BUFFER</code>),</li>
<li>unexpected NULL pointers (<code>KEYM_E_PARAM_POINTER</code>).</li>
</ul>
<p>If the referenced certificate has the storage class <code>KEYM_STORAGE_IN_CSM</code> or <code>KEYM_STORAGE_IN_NVM</code>, the specification requires <code>KEYM_E_CONFIG_FAILURE</code>, without development mode <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00166" href="../../spec/record.html?id=SWS_KeyM_00166">[SWS_KeyM_00166]</a>).</p>
<p>Synchronous return values use KeyM-specific values (<a class="spec-record-ref" data-req="SWS_KeyM_00040" href="../../spec/record.html?id=SWS_KeyM_00040">[SWS_KeyM_00040]</a>):</p>
<ul>
<li><code>KEYM_E_BUSY</code>: other jobs are still running,</li>
<li><code>KEYM_E_PENDING</code>: job accepted, processing asynchronous,</li>
<li><code>KEYM_E_KEY_CERT_SIZE_MISMATCH</code>, <code>KEYM_E_PARAMETER_MISMATCH</code>, and <code>KEYM_E_KEY_CERT_INVALID</code>.</li>
</ul>
<p>Certificate functions add further codes. <code>KEYM_E_KEY_CERT_EMPTY</code> stands for empty slots, <code>KEYM_E_KEY_CERT_READ_FAIL</code> for denied access, and <code>KEYM_E_CERT_INVALID_CHAIN_OF_TRUST</code> for an invalid parent certificate (<a class="spec-record-ref" data-req="SWS_KeyM_00058" href="../../spec/record.html?id=SWS_KeyM_00058">[SWS_KeyM_00058]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_00060" href="../../spec/record.html?id=SWS_KeyM_00060">[SWS_KeyM_00060]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_8_3_3_3_KeyM_GetCertificate.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_8_3_3_3_KeyM_GetCertificate">SWS KeyM p. 66</a>). Non-iterable elements return <code>KEYM_E_CERT_INVALID</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00148" href="../../spec/record.html?id=SWS_KeyM_00148">[SWS_KeyM_00148]</a>). In case of failure, <code>KeyM_CertElementGet</code> sets the output length to zero (<a class="spec-record-ref" data-req="SWS_KeyM_00063" href="../../spec/record.html?id=SWS_KeyM_00063">[SWS_KeyM_00063]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_8_3_3_7_KeyM_CertElementGet.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_8_3_3_7_KeyM_CertElementGet">SWS KeyM p. 71</a>).</p>
<p>Asynchronous errors arrive in the callback. <code>KeyM_ResultType</code> distinguishes, among others, <code>KEYM_RT_NOT_OK</code>, <code>KEYM_RT_KEY_CERT_INVALID</code>, <code>KEYM_RT_KEY_CERT_WRITE_FAIL</code>, <code>KEYM_RT_KEY_CERT_UPDATE_FAIL</code>, and <code>KEYM_RT_CERT_INVALID_CHAIN_OF_TRUST</code> (<a class="spec-record-ref" data-req="SWS_KeyM_91008" href="../../spec/record.html?id=SWS_KeyM_91008">[SWS_KeyM_91008]</a>). Certificate checks deliver the detailed status from <code>KeyM_CertificateStatusType</code> (<a class="spec-record-ref" data-req="SWS_KeyM_00073" href="../../spec/record.html?id=SWS_KeyM_00073">[SWS_KeyM_00073]</a>, <a class="spec-record-ref" data-req="SWS_KeyM_91003" href="../../spec/record.html?id=SWS_KeyM_91003">[SWS_KeyM_91003]</a>).</p>
<p>A failed chain check is additionally the security event <code>KEYM_SEV_CERT_VERIF_FAILED</code> (ID 5) (<a class="spec-record-ref" data-req="SWS_KeyM_00172" href="../../spec/record.html?id=SWS_KeyM_00172">[SWS_KeyM_00172]</a>). It is reported to the IdsM only if <code>KeyMEnableSecurityEventReporting</code> = TRUE. Later releases name the event <code>SEV_CERT_CHAIN_VERIFICATION_FAILED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_KEYM_SECTION_7_4_Security_Events.html" data-snip="SNIP_CLASSIC_KEYM_SECTION_7_4_Security_Events">SWS KeyM p. 38</a>); for R20-11, the name from <a class="spec-record-ref" data-req="SWS_KeyM_00172" href="../../spec/record.html?id=SWS_KeyM_00172">[SWS_KeyM_00172]</a> applies.</p>
