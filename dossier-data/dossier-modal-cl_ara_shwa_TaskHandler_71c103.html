<h4>Context</h4>
<p>In the Adaptive Platform (module <code>shwa</code>), the class <code>ara::shwa::TaskHandler</code> forms the central interface for submitting and executing computation tasks on specialized hardware accelerators. Its primary responsibility is to accept functional work orders and to provide and execute them as a queue submission on a selected device. Within the system architecture, the handler acts as an intermediary between the using software component and the hardware-level processing queues of the accelerator subsystem.</p>
<p>Interaction takes place via standardized interfaces for different execution patterns: on the one hand, the class enables the coordinated execution of individual compute tasks via <a class="spec-record-ref" data-req="AP_SWS_SHWA_01203" href="../spec/record.html?id=AP_SWS_SHWA_01203">[AP_SWS_SHWA_01203]</a>; on the other hand, it enables the data-parallel processing of structured buffers via <a class="spec-record-ref" data-req="AP_SWS_SHWA_01204" href="../spec/record.html?id=AP_SWS_SHWA_01204">[AP_SWS_SHWA_01204]</a>. Through this encapsulation, the using software is relieved of system-specific details of queue management and interaction with the target device. The underlying device is presumably defined during initialization or via the configuration of the module, since the execution methods themselves do not require a separate device selection as a parameter.</p>

<h4>Life cycle and concurrency</h4>
<p>Creation of an instance of <code>ara::shwa::TaskHandler</code> takes place exclusively via the static factory method <code>Create</code> according to <a class="spec-record-ref" data-req="AP_SWS_SHWA_01202" href="../spec/record.html?id=AP_SWS_SHWA_01202">[AP_SWS_SHWA_01202]</a>. Because the class is declared as <code>final</code>, derivation or specialization via inheritance hierarchies is precluded. The factory call returns the instance packaged in a <code>ara::core::Result&lt;TaskHandler&gt;</code>, whereby ownership is transferred directly to the caller. This simultaneously enforces a check as to whether creation was successful or errors occurred.</p>
<p>With regard to concurrency and thread safety, the responsibilities are clearly separated:</p>
<ul>
<li><strong>Instantiation:</strong> The creation method <code>Create</code> is specified as <em>thread-safe</em> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01202" href="../spec/record.html?id=AP_SWS_SHWA_01202">[AP_SWS_SHWA_01202]</a>. It can be safely called in parallel from multiple threads and has defined rollback semantics in the event of an error.</li>
<li><strong>Task submission:</strong> The methods for task transmission — <code>SingleTask</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01203" href="../spec/record.html?id=AP_SWS_SHWA_01203">[AP_SWS_SHWA_01203]</a> and <code>ParallelFor</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01204" href="../spec/record.html?id=AP_SWS_SHWA_01204">[AP_SWS_SHWA_01204]</a> — are explicitly specified as <em>not thread-safe</em>. An instance of <code>TaskHandler</code> must therefore not be used concurrently from multiple threads without external synchronization. If parallel submission is to occur, the caller must either provide custom synchronization mechanisms or instantiate a separate handler for each thread.</li>
<li><strong>Exception safety:</strong> All interfaces (<code>Create</code>, <code>SingleTask</code>, <code>ParallelFor</code>) are declared with <code>noexcept</code> and specified as <em>exception safe</em>, thereby preventing C++ exceptions and transporting errors via the AUTOSAR-specific error types.</li>
</ul>

<h4>Usage Path</h4>
<p>The regular flow for submitting tasks is divided into three consecutive phases: instantiation, parameterization, and transmission to the queue of the target device. First, the application requests an instance via <code>Create()</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01202" href="../spec/record.html?id=AP_SWS_SHWA_01202">[AP_SWS_SHWA_01202]</a>. After successful return and validation of the <code>ara::core::Result</code>, the handler is available.</p>
<p>Subsequently, the caller selects the execution model suitable for the problem at hand:</p>
<ol>
<li><strong>Single task:</strong> For isolated computations or control sequences, the application calls <code>SingleTask(cfg)</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01203" href="../spec/record.html?id=AP_SWS_SHWA_01203">[AP_SWS_SHWA_01203]</a>. The template argument <code>cfg</code> presumably represents a callable function object or a task context that defines the actual computation rule on the accelerator. The call effects the queue submission on the target device.</li>
<li><strong>Parallel loop execution:</strong> If homogeneous data blocks are to be processed in parallel, the application uses <code>ParallelFor(bufferSize, cfg)</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_01204" href="../spec/record.html?id=AP_SWS_SHWA_01204">[AP_SWS_SHWA_01204]</a>. Here, the buffer size <code>bufferSize</code> is passed, allowing the runtime environment to distribute the iterations across the available compute units of the target device.</li>
</ol>
