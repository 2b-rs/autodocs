<h4>Role in the memory stack: Fee between MemIf and flash driver</h4>
<p>The module Fee (Flash EEPROM Emulation) maps a block-wise addressed, EEPROM-like data storage onto flash memory. The NVRAM Manager accesses Fee via the Memory Abstraction Interface. Downwards, Fee in R20-11 relies on the flash driver Fls: Its services such as <code>Fls_Read</code>, <code>Fls_Write</code>, <code>Fls_Erase</code>, <code>Fls_Cancel</code>, and <code>Fls_SetMode</code> are in the list of required interfaces <a class="spec-record-ref" data-req="SWS_Fee_00105" href="../../spec/record.html?id=SWS_Fee_00105">[SWS_Fee_00105]</a>. Fee also imports <code>Fls_AddressType</code> and <code>Fls_LengthType</code> as well as the types <code>MemIf_StatusType</code>, <code>MemIf_JobResultType</code>, and <code>MemIf_ModeType</code> <a class="spec-record-ref" data-req="SWS_Fee_00084" href="../../spec/record.html?id=SWS_Fee_00084">[SWS_Fee_00084]</a>. The write sequence of the specification shows the chain NvM → MemIf → Fee → Fls with a cyclic BSW task (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-ffb4974f25ad8a96.html" data-snip="FIG-ffb4974f25ad8a96">SWS Fee Fig. 7 p. 40</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-1a7d7b45b1d8f184.html" data-snip="FIG-1a7d7b45b1d8f184">SWS Fee Fig. 6 p. 48</a>).</p>
<p>Release note: Newer specification versions replace Fls with MemAcc and Mem drivers. The module overview with MemAcc and the list of optional interfaces with <code>MemAcc_BlankCheck</code> therefore do not apply to R20-11 (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-614f27576c22eb7b.html" data-snip="FIG-614f27576c22eb7b">SWS Fee Fig. 1.1 p. 9</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_DET_SECTION_8_6_2_Optional_Interfaces_FLASHEEPROMEMULATION.html" data-snip="SNIP_CLASSIC_DET_SECTION_8_6_2_Optional_Interfaces_FLASHEEPROMEMULATION">SWS Fee p. 40</a>). In R20-11, <code>Det_ReportError</code> and <code>Fls_BlankCheck</code> are the optional interfaces <a class="spec-record-ref" data-req="SWS_Fee_00104" href="../../spec/record.html?id=SWS_Fee_00104">[SWS_Fee_00104]</a>.</p>
<p>Callbacks do not run via MemIf. Fee provides the callbacks <code>Fee_JobEndNotification</code> and <code>Fee_JobErrorNotification</code> to the lower layers <a class="spec-record-ref" data-req="SWS_Fee_00095" href="../../spec/record.html?id=SWS_Fee_00095">[SWS_Fee_00095]</a> <a class="spec-record-ref" data-req="SWS_Fee_00096" href="../../spec/record.html?id=SWS_Fee_00096">[SWS_Fee_00096]</a>. Fee itself calls <code>NvM_JobEndNotification</code> and <code>NvM_JobErrorNotification</code>, respectively <a class="spec-record-ref" data-req="SWS_Fee_00098" href="../../spec/record.html?id=SWS_Fee_00098">[SWS_Fee_00098]</a> <a class="spec-record-ref" data-req="SWS_Fee_00099" href="../../spec/record.html?id=SWS_Fee_00099">[SWS_Fee_00099]</a>. The MemIf does not define its own callbacks because the NVRAM Manager provides them for the abstraction modules (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE">SWS MemIf p. 24</a>).</p>

<h4>Startup: from Fee_Init via MEMIF_BUSY_INTERNAL to MEMIF_IDLE</h4>
<p><code>Fee_Init</code> receives a pointer to the selected configuration set and is specified as asynchronous in R20-11 <a class="spec-record-ref" data-req="SWS_Fee_00085" href="../../spec/record.html?id=SWS_Fee_00085">[SWS_Fee_00085]</a>. The corresponding diagram shows the sequence: The EcuM calls <code>Fee_Init</code>, and the module transitions to <code>MEMIF_BUSY_INTERNAL</code>. In this state, it can already accept jobs. The BSW Scheduler then cyclically calls <code>Fee_MainFunction</code> until internal management is completed (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-98bd11c74a10aad7.html" data-snip="FIG-98bd11c74a10aad7">SWS Fee Fig. 9.1 p. 42</a>). An older diagram (R18-10) additionally features a synchronous variant: There, initialization already ends in <code>Fee_Init</code>, and the status is directly <code>MEMIF_IDLE</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-653c1affef33740e.html" data-snip="FIG-653c1affef33740e">SWS Fee Fig. 4 p. 47</a>).</p>
<p><code>Fee_MainFunction</code> marks the completion. If no internal management operations are necessary or if they have completed, it sets the status from <code>MEMIF_BUSY_INTERNAL</code> to <code>MEMIF_IDLE</code>. The management can take several calls in the process (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction">SWS Fee p. 38</a>). The main function is called directly by the Basic Software Scheduler. <h4>Logical blocks, virtual addresses, and block correctness</h4>
<p>All job services address a logical block via <code>BlockNumber</code>. At the same time, this value designates the start address of the block <a class="spec-record-ref" data-req="SWS_Fee_00087" href="../../spec/record.html?id=SWS_Fee_00087">[SWS_Fee_00087]</a> <a class="spec-record-ref" data-req="SWS_Fee_00088" href="../../spec/record.html?id=SWS_Fee_00088">[SWS_Fee_00088]</a>. The memory mapping diagram divides the virtual address into a 16-bit block number and a 16-bit block offset; in virtual space, the pages are 64 KBytes in size. Physically, the blocks occupy whole flash pages, so that an unused remainder can occur (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-936ebf9e19ba7e52.html" data-snip="FIG-936ebf9e19ba7e52">SWS Fee Fig. 3 p. 20</a>). <p>Reading and writing differ in granularity:</p>
<ul>
<li><code>Fee_Read</code> calculates the read address from the block start and offset. Offset and length may take any values within their value range (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read">SWS Fee p. 26</a>).</li>
<li><code>Fee_Write</code> has no offset parameter; every write process begins at offset zero (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee p. 28</a>).</li>
</ul>
<p>The underlying requirement justifies the write rule with alignment to virtual 64K boundaries: A block is only erased or written completely or not at all (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_FIGURE_Figure_5_2.html" data-snip="SNIP_CLASSIC_FEE_FIGURE_Figure_5_2">RS MemHwAb p. 24</a>).</p>
<p>Regardless of the content, Fee maintains internal correctness information for each block. At the start of a write process, the block is considered "corrupted", and after successful completion, "not corrupted" again. This information must be strictly separated from the validity set by <code>Fee_InvalidateBlock</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_7_1_5_Managing_block_correctness_information.html" data-snip="SNIP_CLASSIC_FEE_SECTION_7_1_5_Managing_block_correctness_information">SWS Fee p. 21</a>, <a class="spec-record-ref" data-req="SWS_Fee_00092" href="../../spec/record.html?id=SWS_Fee_00092">[SWS_Fee_00092]</a>). Interpretation: A block marked in this way is likely reported as <code>MEMIF_BLOCK_INCONSISTENT</code> during reading. According to the return value description, this value represents inconsistent, possibly corrupt blocks <a class="spec-record-ref" data-req="SWS_Fee_00091" href="../../spec/record.html?id=SWS_Fee_00091">[SWS_Fee_00091]</a>.</p>

<h4>Asynchronous jobs: Acceptance, processing in Fee_MainFunction, feedback</h4>
<p><code>Fee_Read</code>, <code>Fee_Write</code>, <code>Fee_InvalidateBlock</code>, and <code>Fee_EraseImmediateBlock</code> are asynchronous and non-reentrant. Their return value only indicates whether the job was accepted (<code>E_OK</code>) or not (<code>E_NOT_OK</code>) <a class="spec-record-ref" data-req="SWS_Fee_00087" href="../../spec/record.html?id=SWS_Fee_00087">[SWS_Fee_00087]</a> <a class="spec-record-ref" data-req="SWS_Fee_00088" href="../../spec/record.html?id=SWS_Fee_00088">[SWS_Fee_00088]</a> <a class="spec-record-ref" data-req="SWS_Fee_00092" href="../../spec/record.html?id=SWS_Fee_00092">[SWS_Fee_00092]</a> <a class="spec-record-ref" data-req="SWS_Fee_00094" href="../../spec/record.html?id=SWS_Fee_00094">[SWS_Fee_00094]</a>. In status <code>MEMIF_IDLE</code> or <code>MEMIF_BUSY_INTERNAL</code>, Fee accepts the job: It accepts the parameters, initiates the job, sets the status to <code>MEMIF_BUSY</code> and the job result to <code>MEMIF_JOB_PENDING</code>, and returns with <code>E_OK</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee p. 28</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read">SWS Fee p. 26</a>). In <code>MEMIF_UNINIT</code> or <code>MEMIF_BUSY</code>, the job is likely rejected with <code>E_NOT_OK</code>; the rule in question is only touched upon in the payload (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee p. 28</a>).</p>
<p>The actual work is performed by <code>Fee_MainFunction</code>. It asynchronously processes read, write, erase, and invalidation jobs as well as internal management operations (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction">SWS Fee p. 38</a>). For read jobs, it checks whether the upper layer has invalidated the block. If this is the case, it sets the job result to <code>MEMIF_BLOCK_INVALID</code> and calls the error notification, if configured. If <code>Fls_BlankCheck</code> is configured in the flash driver, <code>Fee_Read</code> calls this function beforehand. In this way, ECC errors, for example, can be avoided when reading erased but unprogrammed cells <a class="spec-record-ref" data-req="SWS_Fee_00187" href="../../spec/record.html?id=SWS_Fee_00187">[SWS_Fee_00187]</a>.</p>

<h4>Special services: Cancellation, invalidation, immediate data, and mode change</h4>
<p><code>Fee_Cancel</code> is synchronous in R20-11 <a class="spec-record-ref" data-req="SWS_Fee_00089" href="../../spec/record.html?id=SWS_Fee_00089">[SWS_Fee_00089]</a>. Later versions list the service as asynchronous, but at the same time describe it as synchronous in itself and only asynchronous with respect to the hardware (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel">SWS Fee p. 29</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_9_3_Fee_Cancel">SWS Fee p. 45</a>). In status <code>MEMIF_BUSY</code>, <code>Fee_Cancel</code> calls the driver's cancel function and resets the internal variables. The module is thus ready for a new job in <code>MEMIF_IDLE</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel">SWS Fee p. 29</a>). The job result is then <code>MEMIF_JOB_CANCELED</code> <a class="spec-record-ref" data-req="SWS_Fee_00091" href="../../spec/record.html?id=SWS_Fee_00091">[SWS_Fee_00091]</a>. For a call without a pending job, the error code <code>FEE_E_INVALID_CANCEL</code> is defined <a class="spec-record-ref" data-req="SWS_Fee_91002" href="../../spec/record.html?id=SWS_Fee_91002">[SWS_Fee_91002]</a>.</p>

<p><code>Fee_InvalidateBlock</code> calculates the block address from the block number. It invalidates the block via the driver's erase function and/or via internal management information stored non-volatily (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_7_Fee_InvalidateBlock.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_7_Fee_InvalidateBlock">SWS Fee p. 32</a>). <code>Fee_EraseImmediateBlock</code> is intended for diagnostic or similar system services that erase the area for immediate data in advance. <p><code>Fee_SetMode</code> switches the operating mode of the underlying flash driver and is asynchronous in R20-11 <a class="spec-record-ref" data-req="SWS_Fee_00086" href="../../spec/record.html?id=SWS_Fee_00086">[SWS_Fee_00086]</a>. In contrast, the older diagram shows an end-to-end call chain <code>MemIf_SetMode</code> → <code>Fee_SetMode</code> → <code>Fls_SetMode</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-931d12f6005110fd.html" data-snip="FIG-931d12f6005110fd">SWS Fee Fig. 6 p. 44</a>). <code>Fee_GetVersionInfo</code> is the only reentrant Fee service <a class="spec-record-ref" data-req="SWS_Fee_00093" href="../../spec/record.html?id=SWS_Fee_00093">[SWS_Fee_00093]</a>. With DET activated, it checks the passed pointer and reports error <code>FEE_E_PARAM_POINTER</code> in case of <code>NULL</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_8_Fee_GetVersionInfo.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_8_Fee_GetVersionInfo">SWS Fee p. 34</a>).</p>

It contains parameters such as <code>FeeDevErrorDetect</code>, <code>FeeVersionInfoApi</code>, and <code>FeeVirtualPageSize</code> as well as the function names <code>FeeJobEndNotification</code> and <code>FeeJobErrorNotification</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-16f358d807706c2f.html" data-snip="FIG-16f358d807706c2f">ECUC-Parameter Fig. 7.7 p. 578</a>). <p>The configurable notifications explain the addition "if configured" in the sequences. Fee calls the upper layer's end or error notification only if such a routine is configured (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_4_1_Fee_JobEndNotification.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_4_1_Fee_JobEndNotification">SWS Fee p. 37</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction">SWS Fee p. 38</a>). Accordingly, the error description specifies two reporting mechanisms depending on the configuration: polling or callback (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation">ErrorDescription p. 40</a>).</p>

<h4>Behavior in the event of an error</h4>
<p>Fee defines the following error codes <a class="spec-record-ref" data-req="SWS_Fee_00010" href="../../spec/record.html?id=SWS_Fee_00010">[SWS_Fee_00010]</a> <a class="spec-record-ref" data-req="SWS_Fee_91002" href="../../spec/record.html?id=SWS_Fee_91002">[SWS_Fee_91002]</a>. <p>The flash driver detects hardware errors. It reports the failure of an asynchronous operation via <code>Fee_JobErrorNotification</code> <a class="spec-record-ref" data-req="SWS_Fee_00096" href="../../spec/record.html?id=SWS_Fee_00096">[SWS_Fee_00096]</a>. The reaction in Fee is implementation-specific. Depending on the configuration, MemIf queries the job result <code>MEMIF_JOB_FAILED</code> via <code>Fee_GetJobResult</code>, or Fee reports the error via <code>NvM_JobErrorNotification</code>. Recovery is the responsibility of NvM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation">ErrorDescription p. 40</a>, <a class="spec-record-ref" data-req="SWS_Fee_00099" href="../../spec/record.html?id=SWS_Fee_00099">[SWS_Fee_00099]</a>). MemIf can detect an uninitialized state via <code>Fee_GetStatus</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation">ErrorDescription p. 53</a>, <a class="spec-record-ref" data-req="SWS_Fee_00090" href="../../spec/record.html?id=SWS_Fee_00090">[SWS_Fee_00090]</a>).</p>
<p>In the event of consistency errors, Fee checks the read data and forwards a detected error to NvM. NvM reports <code>NVM_E_INTEGRITY_FAILED</code> to the DEM and, if configured, starts a recovery: re-reading, reading the redundant block, or reading the ROM block. If it fails, the job result is <code>NVM_REQ_INTEGRITY_FAILED</code>. The corresponding diagram originates from R22-11 (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_FIGURE_Figure_6_11.html" data-snip="SNIP_CLASSIC_FEE_FIGURE_Figure_6_11">ErrorDescription Fig. 6.11 p. 64</a>). In its job result, Fee itself additionally distinguishes invalidated (<code>MEMIF_BLOCK_INVALID</code>), inconsistent (<code>MEMIF_BLOCK_INCONSISTENT</code>), and canceled jobs (<code>MEMIF_JOB_CANCELED</code>) <a class="spec-record-ref" data-req="SWS_Fee_00091" href="../../spec/record.html?id=SWS_Fee_00091">[SWS_Fee_00091]</a>.</p>
