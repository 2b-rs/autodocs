<p class="ai-level ai-oneliner-lead" data-ai-level="1">Emuliert auf Flash-Speicher ein EEPROM mit logischen Blöcken und bedient asynchrone Lese- und Schreibaufträge.</p>
<div class="ai-level" data-ai-level="2">
<p>Fee bildet die logischen Blöcke eines emulierten EEPROMs auf Flash-Speicher ab und bedient die Aufträge, die der NVRAM Manager über MemIf stellt. Lese-, Schreib- und Löschaufträge werden nur angenommen und dann asynchron in <code>Fee_MainFunction</code> abgearbeitet <a class="spec-record-ref" data-req="SWS_Fee_00097" href="../../spec/record.html?id=SWS_Fee_00097">[SWS_Fee_00097]</a>. Fortschritt und Ergebnis zeigen <code>Fee_GetStatus</code> und <code>Fee_GetJobResult</code>. Nach <code>Fee_Init</code> kann das Modul zunächst mit interner Verwaltung beschäftigt sein (<code>MEMIF_BUSY_INTERNAL</code>), nimmt aber schon Aufträge an <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-98bd11c74a10aad7.html" data-snip="FIG-98bd11c74a10aad7">SWS Fee S. 42</a>. Schreibaufträge betreffen stets den ganzen Block.</p>

</div>
<div class="ai-level" data-ai-level="3">
<p>Fee bildet die logischen Blöcke eines emulierten EEPROMs auf Flash-Speicher ab. Die <code>BlockNumber</code> bezeichnet zugleich die Startadresse des Blocks <a class="spec-record-ref" data-req="SWS_Fee_00087" href="../../spec/record.html?id=SWS_Fee_00087">[SWS_Fee_00087]</a>. Aufrufe kommen vom NVRAM Manager über das Memory Abstraction Interface, das den passenden Dienst per <code>DeviceIndex</code> auswählt <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read">SWS MemIf S. 18</a>. Darunter arbeitet der Flash-Treiber Fls. Rückmeldungen gibt Fee über <code>NvM_JobEndNotification</code> und <code>NvM_JobErrorNotification</code> direkt an den NVRAM Manager <a class="spec-record-ref" data-req="SWS_Fee_00098" href="../../spec/record.html?id=SWS_Fee_00098">[SWS_Fee_00098]</a>, <a class="spec-record-ref" data-req="SWS_Fee_00099" href="../../spec/record.html?id=SWS_Fee_00099">[SWS_Fee_00099]</a>.</p>

<h4>Rolle im NV-Speicherstapel: Flash-Speicher als emuliertes EEPROM</h4>

<p>Die Flash EEPROM Emulation (Fee) stellt der oberen Schicht logische Blöcke bereit und bildet sie auf Flash-Speicher ab. Die <code>BlockNumber</code> bezeichnet dabei zugleich die Startadresse des Blocks im Speicher <a class="spec-record-ref" data-req="SWS_Fee_00087" href="../../spec/record.html?id=SWS_Fee_00087">[SWS_Fee_00087]</a>, <a class="spec-record-ref" data-req="SWS_Fee_00088" href="../../spec/record.html?id=SWS_Fee_00088">[SWS_Fee_00088]</a>. Der NVRAM Manager ruft Fee nicht direkt auf, sondern über das Memory Abstraction Interface. <code>MemIf_Read</code> und <code>MemIf_Write</code> rufen die Funktion des Abstraktionsmoduls auf, das per <code>DeviceIndex</code> gewählt ist, und geben deren Rückgabewert weiter <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_1_MemIf_Read">SWS MemIf S. 18</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_2_MemIf_Write.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_2_MemIf_Write">SWS MemIf S. 19</a>. Nach unten stützt sich Fee auf den Flash-Treiber Fls. Von dort importiert es <code>Fls_AddressType</code> und <code>Fls_LengthType</code>, von MemIf die Status-, Ergebnis- und Modustypen <a class="spec-record-ref" data-req="SWS_Fee_00084" href="../../spec/record.html?id=SWS_Fee_00084">[SWS_Fee_00084]</a>.</p>

<p>Rückmeldungen laufen am MemIf vorbei. MemIf selbst stellt keine Callbacks bereit; die Rückrufroutinen für die darunterliegenden Abstraktionsmodule liefert der NVRAM Manager <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_MEMORYABSTRACTIONINTERFACE">SWS MemIf S. 24</a>. Fee ruft dazu <code>NvM_JobEndNotification</code> und <code>NvM_JobErrorNotification</code> auf <a class="spec-record-ref" data-req="SWS_Fee_00098" href="../../spec/record.html?id=SWS_Fee_00098">[SWS_Fee_00098]</a>, <a class="spec-record-ref" data-req="SWS_Fee_00099" href="../../spec/record.html?id=SWS_Fee_00099">[SWS_Fee_00099]</a>. Umgekehrt meldet der Treiber das Ende seiner Aufträge über <code>Fee_JobEndNotification</code> und <code>Fee_JobErrorNotification</code> an Fee <a class="spec-record-ref" data-req="SWS_Fee_00095" href="../../spec/record.html?id=SWS_Fee_00095">[SWS_Fee_00095]</a>, <a class="spec-record-ref" data-req="SWS_Fee_00096" href="../../spec/record.html?id=SWS_Fee_00096">[SWS_Fee_00096]</a>. Initialisiert wird Fee vom EcuM, zyklisch angestoßen vom Basic Software Scheduler <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-98bd11c74a10aad7.html" data-snip="FIG-98bd11c74a10aad7">SWS Fee S. 42</a>.</p>

<h4>Hochlauf: von Fee_Init bis zur Annahmebereitschaft</h4>

<p>Der EcuM ruft <code>Fee_Init</code> mit einem Zeiger auf den gewählten Konfigurationssatz auf <a class="spec-record-ref" data-req="SWS_Fee_00085" href="../../spec/record.html?id=SWS_Fee_00085">[SWS_Fee_00085]</a>. Der Typ <code>Fee_ConfigType</code> ist eine Struktur mit implementierungsspezifischen Elementen <a class="spec-record-ref" data-req="SWS_Fee_00188" href="../../spec/record.html?id=SWS_Fee_00188">[SWS_Fee_00188]</a>. Bemerkenswert ist, dass R20-11 <code>Fee_Init</code> als asynchron führt <a class="spec-record-ref" data-req="SWS_Fee_00085" href="../../spec/record.html?id=SWS_Fee_00085">[SWS_Fee_00085]</a>. Laut Änderungshistorie muss die Initialisierung nicht innerhalb von <code>Fee_Init</code> abgeschlossen sein, und die Zustandsmaschine wurde entsprechend angepasst <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_General_Overview_FLASHEEPROMEMULATION.html" data-snip="SNIP_CLASSIC_FEE_SECTION_General_Overview_FLASHEEPROMEMULATION">SWS Fee S. 4</a>.</p>

<h4>Modulstatus und Auftragsergebnis als Steuergrößen</h4>

<p>Die obere Schicht steuert ihre Aufrufe über zwei synchrone Abfragen. <code>Fee_GetStatus</code> liefert einen von vier Werten <a class="spec-record-ref" data-req="SWS_Fee_00090" href="../../spec/record.html?id=SWS_Fee_00090">[SWS_Fee_00090]</a>:</p>
<ul>
<li><code>MEMIF_UNINIT</code>: Das Modul ist nicht initialisiert.</li>
<li><code>MEMIF_IDLE</code>: Das Modul ist untätig.</li>
<li><code>MEMIF_BUSY</code>: Ein Auftrag der oberen Schicht ist in Bearbeitung.</li>
<li><code>MEMIF_BUSY_INTERNAL</code>: Eine interne Verwaltungsoperation läuft.</li>
</ul>
<p>Als Beispiel für eine interne Verwaltungsoperation nennt die Spezifikation die Reorganisation des genutzten Flash-Speichers (Garbage Collection) <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_5_Fee_GetStatus">SWS Fee S. 30</a>. Neue Aufträge werden sowohl in <code>MEMIF_IDLE</code> als auch in <code>MEMIF_BUSY_INTERNAL</code> angenommen und führen nach <code>MEMIF_BUSY</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee S. 28</a>. Nach regulärem Auftragsende dürfte der Status wieder auf <code>MEMIF_IDLE</code> fallen. Ausdrücklich belegt ist die Rückkehr nach <code>MEMIF_IDLE</code> hier nur für den Abbruch <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel">SWS Fee S. 29</a>.</p>

<p><code>Fee_GetJobResult</code> bezieht sich auf den zuletzt angenommenen Auftrag <a class="spec-record-ref" data-req="SWS_Fee_00091" href="../../spec/record.html?id=SWS_Fee_00091">[SWS_Fee_00091]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_6_Fee_GetJobResult">SWS Fee S. 31</a>. Es unterscheidet sechs Ergebnisse:</p>
<ul>
<li><code>MEMIF_JOB_OK</code>: Der Auftrag wurde erfolgreich beendet.</li>
<li><code>MEMIF_JOB_PENDING</code>: Der Auftrag wartet oder läuft noch.</li>
<li><code>MEMIF_JOB_CANCELED</code>: Der Auftrag wurde abgebrochen.</li>
<li><code>MEMIF_JOB_FAILED</code>: Der Auftrag ist fehlgeschlagen.</li>

<li><code>MEMIF_BLOCK_INVALID</code>: Der Block wurde ungültig gesetzt; Lesen ist nicht möglich.</li>
</ul>
<p>Der Status beschreibt also das Modul, das Ergebnis den einzelnen Auftrag; beide sind getrennt abzufragen <a class="spec-record-ref" data-req="SWS_Fee_00090" href="../../spec/record.html?id=SWS_Fee_00090">[SWS_Fee_00090]</a>.</p>

<h4>Lese-, Schreib- und Blockverwaltungsaufträge</h4>

<p>Die Auftragsdienste arbeiten asynchron: <code>E_OK</code> bedeutet nur, dass der Auftrag angenommen wurde <a class="spec-record-ref" data-req="SWS_Fee_00087" href="../../spec/record.html?id=SWS_Fee_00087">[SWS_Fee_00087]</a>, <a class="spec-record-ref" data-req="SWS_Fee_00088" href="../../spec/record.html?id=SWS_Fee_00088">[SWS_Fee_00088]</a>. <code>Fee_Read</code> berechnet die Leseadresse aus Blockstartadresse und <code>BlockOffset</code>. Offset und Länge dürfen jeden Wert ihres Typbereichs annehmen. So lassen sich beliebig viele Bytes ab einer beliebigen Stelle eines Blocks lesen <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read">SWS Fee S. 26</a>. Ist im Flash-Treiber <code>Fls_BlankCheck</code> konfiguriert, prüft <code>Fee_Read</code> damit vorab, ob der Bereich lesbar ist. So wird etwa vermieden, dass gelöschte, aber nicht programmierte Zellen ECC-Fehler auslösen <a class="spec-record-ref" data-req="SWS_Fee_00187" href="../../spec/record.html?id=SWS_Fee_00187">[SWS_Fee_00187]</a>.</p>

<p><code>Fee_Write</code> schreibt dagegen immer den ganzen Block; der Offset ist auf null fixiert <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee S. 28</a>. Das folgt aus der übergeordneten Anforderung, dass Lösch- und Schreibaufträge stets an der virtuellen 64K-Grenze beginnen: Ein Block wird ganz oder gar nicht geschrieben <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_FIGURE_Figure_5_2.html" data-snip="SNIP_CLASSIC_FEE_FIGURE_Figure_5_2">RS MemHwAb S. 24</a>. Bei Annahme setzt Fee den Status auf <code>MEMIF_BUSY</code> und das Ergebnis auf <code>MEMIF_JOB_PENDING</code> und gibt <code>E_OK</code> zurück. Für <code>Fee_Read</code> gilt dieselbe Annahmebedingung <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_2_Fee_Read">SWS Fee S. 26</a>.</p>

<p>Damit unterbrochene Schreibvorgänge erkennbar bleiben, führt Fee für jeden Block eine interne Korrektheitsinformation <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_7_1_5_Managing_block_correctness_information.html" data-snip="SNIP_CLASSIC_FEE_SECTION_7_1_5_Managing_block_correctness_information">SWS Fee S. 21</a>. Beim Start eines Schreibvorgangs wird der Block als „corrupted“ markiert, nach erfolgreichem Ende wieder als „not corrupted“. Diese Information ist streng von der Gültigkeit zu trennen, die die obere Schicht mit <code>Fee_InvalidateBlock</code> setzt.</p>

<p><code>Fee_InvalidateBlock</code> erklärt einen logischen Block für ungültig <a class="spec-record-ref" data-req="SWS_Fee_00092" href="../../spec/record.html?id=SWS_Fee_00092">[SWS_Fee_00092]</a>. Falls konfiguriert, ruft sie außerdem die Fehlerbenachrichtigung der oberen Schicht auf <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_5_1_Fee_MainFunction">SWS Fee S. 38</a>.</p>

Sie löschen damit bei Bedarf den Bereich für Immediate-Daten vorab. Ob dabei physisch gelöscht wird, entscheidet die Implementierung <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_9_Fee_EraseImmediateBlock.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_9_Fee_EraseImmediateBlock">SWS Fee S. 35</a>. <h4>Rückmeldungen, Abbruch und Moduswechsel</h4>

<p>Der Flash-Treiber meldet das erfolgreiche Ende eines Treiberauftrags über <code>Fee_JobEndNotification</code> <a class="spec-record-ref" data-req="SWS_Fee_00095" href="../../spec/record.html?id=SWS_Fee_00095">[SWS_Fee_00095]</a>. Fee erledigt daraufhin die nötige Blockverwaltung und ruft dann, falls konfiguriert, die Job-End-Benachrichtigung der oberen Schicht auf. Ein noch auf <code>MEMIF_JOB_PENDING</code> stehendes Ergebnis setzt es auf <code>MEMIF_JOB_OK</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_4_1_Fee_JobEndNotification.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_4_1_Fee_JobEndNotification">SWS Fee S. 37</a>. Callbacks können je nach Aufbau des Speicherstapels auf Interrupt-Ebene laufen und sich über mehrere Schichten nach oben fortpflanzen. Ihre Laufzeit muss daher kurz bleiben; ob Aufrufe auf Interrupt-Ebene zulässig sind, entscheidet das Systemdesign <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_FLASHEEPROMEMULATION.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_4_Callback_notifications_FLASHEEPROMEMULATION">SWS Fee S. 36</a>.</p>

<p><code>Fee_Cancel</code> ruft die Abbruchfunktion des Flash-Treibers auf <a class="spec-record-ref" data-req="SWS_Fee_00089" href="../../spec/record.html?id=SWS_Fee_00089">[SWS_Fee_00089]</a>. Die obere Schicht erreicht den Dienst über <code>MemIf_Cancel</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MEMIF_SECTION_8_3_3_MemIf_Cancel.html" data-snip="SNIP_CLASSIC_MEMIF_SECTION_8_3_3_MemIf_Cancel">SWS MemIf S. 20</a>. Wirksam wird der Abbruch nur im Status <code>MEMIF_BUSY</code>: Fee ruft den Treiberabbruch auf, setzt seine internen Variablen zurück und kehrt nach <code>MEMIF_IDLE</code> zurück. Ist die DET aktiviert, prüft Fee vorher, ob das Modul initialisiert ist <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_4_Fee_Cancel">SWS Fee S. 29</a>.</p>

<p>Bei <code>Fee_Cancel</code> weichen die Releases voneinander ab. Die genannte spätere Fassung führt den Dienst als asynchron, R20-11 dagegen als synchron <a class="spec-record-ref" data-req="SWS_Fee_00089" href="../../spec/record.html?id=SWS_Fee_00089">[SWS_Fee_00089]</a>. Für R20-11 maßgeblich ist die synchrone Einordnung.</p>

<h4>Verhalten im Fehlerfall</h4>

<p>Als Entwicklungsfehler definiert Fee fünf Codes <a class="spec-record-ref" data-req="SWS_Fee_00010" href="../../spec/record.html?id=SWS_Fee_00010">[SWS_Fee_00010]</a>:</p>
<ul>
<li><code>FEE_E_UNINIT</code> (0x01): Dienst vor der Initialisierung aufgerufen.</li>
<li><code>FEE_E_INVALID_BLOCK_NO</code> (0x02): ungültige Blocknummer.</li>
<li><code>FEE_E_INVALID_BLOCK_OFS</code> (0x03): ungültiger Block-Offset.</li>
<li><code>FEE_E_PARAM_POINTER</code> (0x04): ungültiger Datenzeiger.</li>
<li><code>FEE_E_INVALID_BLOCK_LEN</code> (0x05): ungültige Längenangabe.</li>
</ul>
<p>R20-11 ergänzt zwei weitere Codes <a class="spec-record-ref" data-req="SWS_Fee_91002" href="../../spec/record.html?id=SWS_Fee_91002">[SWS_Fee_91002]</a>. <code>FEE_E_BUSY</code> (0x06) gilt für Aufrufe, während ein Nutzerauftrag bearbeitet wird. <code>FEE_E_INVALID_CANCEL</code> (0x08) gilt für <code>Fee_Cancel</code> ohne anhängigen Auftrag. Ein im Status <code>MEMIF_BUSY</code> gestellter neuer Auftrag dürfte demnach abgelehnt und mit <code>E_NOT_OK</code> beantwortet werden. Die zugehörige Regel liegt hier nur unvollständig vor <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write.html" data-snip="SNIP_CLASSIC_FEE_SECTION_8_3_3_Fee_Write">SWS Fee S. 28</a>.</p>

<p>Fehler des Flash-Speichers erkennt der Flash-Treiber; wie Fee darauf reagiert, ist implementierungsspezifisch <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_2_2_3_Flash_Eeprom_emulation">ErrorDescription S. 40</a>. Gemeldet wird je nach Konfiguration auf einem von zwei Wegen. Entweder fragt MemIf <code>Fee_GetJobResult</code> ab und erhält <code>MEMIF_JOB_FAILED</code>, oder Fee ruft aktiv <code>NvM_JobErrorNotification</code> auf. Die Wiederherstellung übernimmt der NVRAM Manager. Ein nicht initialisiertes Modul erkennt die obere Schicht an <code>MEMIF_UNINIT</code> in <code>Fee_GetStatus</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation.html" data-snip="SNIP_CLASSIC_ERRORDESCRIPTION_SECTION_6_2_5_2_2_Flash_Eeprom_emulation">ErrorDescription S. 53</a>, <a class="spec-record-ref" data-req="SWS_Fee_00090" href="../../spec/record.html?id=SWS_Fee_00090">[SWS_Fee_00090]</a>.</p>
