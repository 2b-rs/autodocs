<h4>The CSM as a service layer between users and crypto drivers</h4>
<p>The Crypto Service Manager provides cryptographic services to applications and BSW modules via a standardized API. These include hash, MAC, encryption and decryption, AEAD, signatures, random numbers, and key management, for example via <code>Csm_Hash</code> <a class="spec-record-ref" data-req="SWS_Csm_00980" href="../../spec/record.html?id=SWS_Csm_00980">[SWS_Csm_00980]</a>, <code>Csm_MacGenerate</code> <a class="spec-record-ref" data-req="SWS_Csm_00982" href="../../spec/record.html?id=SWS_Csm_00982">[SWS_Csm_00982]</a>, <code>Csm_AEADEncrypt</code> <a class="spec-record-ref" data-req="SWS_Csm_01023" href="../../spec/record.html?id=SWS_Csm_01023">[SWS_Csm_01023]</a>, or <code>Csm_SignatureVerify</code> <a class="spec-record-ref" data-req="SWS_Csm_00996" href="../../spec/record.html?id=SWS_Csm_00996">[SWS_Csm_00996]</a>. The CSM does not perform calculations itself. It forwards jobs via the Crypto Interface (CryIf) to Crypto Driver Objects, which can be hardware (e.g., HSM) or software. The path from a CSM queue via the CryIf to a Crypto Driver Object is called a channel (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing">SWS CSM p. 29</a>). <a class="spec-record-ref" data-req="SWS_Csm_91100" href="../../spec/record.html?id=SWS_Csm_91100">[SWS_Csm_91100]</a> lists the required CryIf functions. <code>Det_ReportError</code> is an optional interface <a class="spec-record-ref" data-req="SWS_Csm_91101" href="../../spec/record.html?id=SWS_Csm_91101">[SWS_Csm_91101]</a>.</p>
<p>Software components access via RTE service ports, which are formally defined in the chapter "Service Interfaces" (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_7_Service_Interfaces.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_7_Service_Interfaces">SWS CSM p. 85</a>). BSW modules use the C API directly. Two examples:</p>
<ul>
<li>The DCM checks Proof-of-Ownership with <code>Csm_SignatureVerify</code> in mode <code>CRYPTO_OPERATIONMODE_SINGLECALL</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_4_2_10_3_Proof_of_ownership_client.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_4_2_10_3_Proof_of_ownership_client">SWS DCM p. 152</a>).</li>
<li>The IdsM receives the result of asynchronous signature jobs via a callback configured in the CSM (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_4_8_IdsM_CsmNotification.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_4_8_IdsM_CsmNotification">SWS IdsM p. 77</a>).</li>
</ul>

<h4>Jobs, queues, and channels: how a service call is forwarded</h4>
<p>A job is an instance of a configured cryptographic primitive <a class="spec-record-ref" data-req="SWS_Csm_00941" href="../../spec/record.html?id=SWS_Csm_00941">[SWS_Csm_00941]</a>. For each job, only one instance is processed at a time. Different jobs may run in parallel (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior">SWS CSM p. 21</a>). At runtime, the structure <code>Crypto_JobType</code> carries the job. It contains <code>jobId</code>, <code>jobState</code>, the input/output structure <code>jobPrimitiveInputOutput</code>, the primitive information, and the key IDs <a class="spec-record-ref" data-req="SWS_Csm_01013" href="../../spec/record.html?id=SWS_Csm_01013">[SWS_Csm_01013]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01009" href="../../spec/record.html?id=SWS_Csm_01009">[SWS_Csm_01009]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01012" href="../../spec/record.html?id=SWS_Csm_01012">[SWS_Csm_01012]</a> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-8d1f4e5c2e81d382.html" data-snip="FIG-8d1f4e5c2e81d382">SWS CSM p. 20</a>).</p>
<p>Jobs can be queued in configured CsmQueues <a class="spec-record-ref" data-req="SWS_Csm_00940" href="../../spec/record.html?id=SWS_Csm_00940">[SWS_Csm_00940]</a>. The queues sort by job priority <a class="spec-record-ref" data-req="SWS_Csm_00944" href="../../spec/record.html?id=SWS_Csm_00944">[SWS_Csm_00944]</a>. Each queue is assigned to exactly one channel, and its size is configurable (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing">SWS CSM p. 29</a>). The specification explicitly regulates two cases (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior">SWS CSM p. 21</a>):</p>
<ul>
<li>If the job is already <code>ACTIVE</code>, the service call directly calls <code>CryIf_ProcessJob</code> and passes through its return value.</li>
<li>If a job must be queued and the queue is full, it is rejected with <code>CRYPTO_E_BUSY</code>.</li>
</ul>
<p>For synchronous jobs, the specification recommends a queue size of 0. However, synchronous and asynchronous jobs may use the same channel. For an active job, the CSM assumes that the caller intends to continue, for example with "update". The plausibility check is then located in the driver (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_FIGURE_Figure_7_5.html" data-snip="SNIP_CLASSIC_CSM_FIGURE_Figure_7_5">SWS CSM p. 29</a>).</p>

<h4>Synchronous and asynchronous processing in the cycle of Csm_MainFunction</h4>
<p>The job configuration specifies whether a data service operates synchronously or asynchronously. This is described, for example, for <code>Csm_Hash</code> and <code>Csm_Encrypt</code> <a class="spec-record-ref" data-req="SWS_Csm_00980" href="../../spec/record.html?id=SWS_Csm_00980">[SWS_Csm_00980]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00984" href="../../spec/record.html?id=SWS_Csm_00984">[SWS_Csm_00984]</a>. The choice is encoded in <code>Crypto_ProcessingType</code> <a class="spec-record-ref" data-req="SWS_Csm_01049" href="../../spec/record.html?id=SWS_Csm_01049">[SWS_Csm_01049]</a>.</p>
<p>If an asynchronous interface is configured, <code>Csm_MainFunction</code> is called cyclically. It checks the queues and passes jobs to CryIf <a class="spec-record-ref" data-req="SWS_Csm_00479" href="../../spec/record.html?id=SWS_Csm_00479">[SWS_Csm_00479]</a> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_General_Behavior">SWS CSM p. 21</a>). For multicore, the following applies:</p>
<ul>
<li>For each configured CsmMainFunction instance, one <code>Csm_MainFunction_&lt;shortName&gt;</code> exists <a class="spec-record-ref" data-req="SWS_Csm_00479" href="../../spec/record.html?id=SWS_Csm_00479">[SWS_Csm_00479]</a>.</li>
<li><code>Csm_Init</code> may be provided per partition <a class="spec-record-ref" data-req="SWS_Csm_00646" href="../../spec/record.html?id=SWS_Csm_00646">[SWS_Csm_00646]</a>.</li>
<li>Queues are processed in the MainFunction referenced via <code>CsmQueueMainFunctionRef</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_5_Multicore.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_5_Multicore">SWS CSM p. 36</a>).</li>
</ul>
<p>The result is returned via a callback chain. CryIf reports completion with <code>Csm_CallbackNotification(job, result)</code> <a class="spec-record-ref" data-req="SWS_Csm_00970" href="../../spec/record.html?id=SWS_Csm_00970">[SWS_Csm_00970]</a>. If the FINISH bit is set, the CSM calls the configured callback <a class="spec-record-ref" data-req="SWS_Csm_01044" href="../../spec/record.html?id=SWS_Csm_01044">[SWS_Csm_01044]</a>. Its signature is <code>&lt;Csm_ApplicationCallbackNotification&gt;(jobId, result)</code>, and its name is configurable <a class="spec-record-ref" data-req="SWS_Csm_00971" href="../../spec/record.html?id=SWS_Csm_00971">[SWS_Csm_00971]</a>. SW-Cs receive the notification via port <code>CallbackNotification_{Job}</code> <a class="spec-record-ref" data-req="SWS_Csm_00934" href="../../spec/record.html?id=SWS_Csm_00934">[SWS_Csm_00934]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00928" href="../../spec/record.html?id=SWS_Csm_00928">[SWS_Csm_00928]</a>. Lengths and verification results are returned asynchronously via <code>Csm_LengthPtr</code> and <code>Csm_VerifyResultPtr</code> <a class="spec-record-ref" data-req="SWS_Csm_91045" href="../../spec/record.html?id=SWS_Csm_91045">[SWS_Csm_91045]</a>, <a class="spec-record-ref" data-req="SWS_Csm_91046" href="../../spec/record.html?id=SWS_Csm_91046">[SWS_Csm_91046]</a>.</p>

<h4>Streaming, single call, and the lifecycle of a job</h4>
<p>The parameter <code>mode</code> is a flag field composed of "START", "UPDATE", and "FINISH". The flags can be combined so that a single call executes multiple operations <a class="spec-record-ref" data-req="SWS_Csm_01039" href="../../spec/record.html?id=SWS_Csm_01039">[SWS_Csm_01039]</a>. <code>Crypto_OperationModeType</code> defines the following values <a class="spec-record-ref" data-req="SWS_Csm_01029" href="../../spec/record.html?id=SWS_Csm_01029">[SWS_Csm_01029]</a>:</p>
<ul>
<li><code>CRYPTO_OPERATIONMODE_START</code>: resets the job.</li>
<li><code>…_UPDATE</code>: calculates intermediate results.</li>
<li><code>…_STREAMSTART</code>: start and update in a single call.</li>
<li><code>…_FINISH</code>: completes the calculation.</li>
</ul>
<p>With FINISH, the application can complete a calculation <a class="spec-record-ref" data-req="SWS_Csm_01046" href="../../spec/record.html?id=SWS_Csm_01046">[SWS_Csm_01046]</a>. START and FINISH without UPDATE results in <code>E_NOT_OK</code> <a class="spec-record-ref" data-req="SWS_Csm_01045" href="../../spec/record.html?id=SWS_Csm_01045">[SWS_Csm_01045]</a>. Streaming is suitable for very large data because UPDATE can be called any number of times. The single-call approach saves calling overhead for small data (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_UTILIZATIONOFCRYPTOSERVICES_SECTION_5_1_3_Streaming_Approach_vs_Single_Call_Approach.html" data-snip="SNIP_CLASSIC_UTILIZATIONOFCRYPTOSERVICES_SECTION_5_1_3_Streaming_Approach_vs_Single_Call_Approach">EXP Crypto Services p. 12</a>).</p>
<p>The job has two states <a class="spec-record-ref" data-req="SWS_Csm_01028" href="../../spec/record.html?id=SWS_Csm_01028">[SWS_Csm_01028]</a>:</p>
<ul>
<li><code>CRYPTO_JOBSTATE_IDLE</code> applies after <code>Csm_Init</code> and after a completed FINISH.</li>
<li><code>CRYPTO_JOBSTATE_ACTIVE</code> applies after START or UPDATE.</li>
</ul>
<p>The actual state transitions are performed by the Crypto Driver (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CRYIF_SECTION_7_2_1_Normal_Operation.html" data-snip="SNIP_CLASSIC_CRYIF_SECTION_7_2_1_Normal_Operation">SWS CSM p. 22</a>).</p>
<p>A running work context can be saved with <code>Csm_SaveContextJob</code> and restored with <code>Csm_RestoreContextJob</code> <a class="spec-record-ref" data-req="SWS_Csm_91063" href="../../spec/record.html?id=SWS_Csm_91063">[SWS_Csm_91063]</a>, <a class="spec-record-ref" data-req="SWS_Csm_91064" href="../../spec/record.html?id=SWS_Csm_91064">[SWS_Csm_91064]</a>. Key elements do not belong to the context. In two cases, the call returns immediately with <code>E_NOT_OK</code>: if the job is <code>IDLE</code> or if it is currently being processed by the driver (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_2_5_Job_context_interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_2_5_Job_context_interface">SWS CSM p. 35</a>).</p>

<h4>Keys: elements, validity, generation, and exchange</h4>
<p>A key consists of one or more key elements <a class="spec-record-ref" data-req="SWS_Csm_00954" href="../../spec/record.html?id=SWS_Csm_00954">[SWS_Csm_00954]</a>. Their IDs are predefined, such as <code>CRYPTO_KE_MAC_KEY</code> (1), <code>CRYPTO_KE_CIPHER_IV</code> (5), and <code>CRYPTO_KE_KEYGENERATE_SEED</code> (16) <a class="spec-record-ref" data-req="SWS_Csm_01022" href="../../spec/record.html?id=SWS_Csm_01022">[SWS_Csm_01022]</a>. Key services only offer the function <code>Csm_&lt;Service&gt;()</code> <a class="spec-record-ref" data-req="SWS_Csm_00950" href="../../spec/record.html?id=SWS_Csm_00950">[SWS_Csm_00950]</a>. The following functions operate synchronously:</p>
<ul>
<li><code>Csm_KeyElementSet</code> <a class="spec-record-ref" data-req="SWS_Csm_00957" href="../../spec/record.html?id=SWS_Csm_00957">[SWS_Csm_00957]</a></li>
<li><code>Csm_KeyElementGet</code> <a class="spec-record-ref" data-req="SWS_Csm_00959" href="../../spec/record.html?id=SWS_Csm_00959">[SWS_Csm_00959]</a></li>
<li><code>Csm_KeyCopy</code> <a class="spec-record-ref" data-req="SWS_Csm_01034" href="../../spec/record.html?id=SWS_Csm_01034">[SWS_Csm_01034]</a></li>
<li><code>Csm_KeyElementCopy</code> <a class="spec-record-ref" data-req="SWS_Csm_00969" href="../../spec/record.html?id=SWS_Csm_00969">[SWS_Csm_00969]</a></li>
<li><code>Csm_KeyElementCopyPartial</code> <a class="spec-record-ref" data-req="SWS_Csm_91025" href="../../spec/record.html?id=SWS_Csm_91025">[SWS_Csm_91025]</a></li>
</ul>
<p>Later document versions additionally require: After a key management function, the CSM does not process any new jobs from the queue until the next MainFunction (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_8_Key_Management_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_8_Key_Management_Interface">SWS CSM p. 60</a>, R24-11/R25-11). For R20-11, the payload contains no requirement on this.</p>
<p>The key status is <code>CRYPTO_KEYSTATUS_INVALID</code> or <code>CRYPTO_KEYSTATUS_VALID</code> <a class="spec-record-ref" data-req="SWS_Csm_91102" href="../../spec/record.html?id=SWS_Csm_91102">[SWS_Csm_91102]</a>. It is controlled using these functions:</p>
<ul>
<li><code>Csm_KeySetValid</code> <a class="spec-record-ref" data-req="SWS_Csm_00958" href="../../spec/record.html?id=SWS_Csm_00958">[SWS_Csm_00958]</a></li>
<li><code>Csm_KeySetInvalid</code> <a class="spec-record-ref" data-req="SWS_Csm_91075" href="../../spec/record.html?id=SWS_Csm_91075">[SWS_Csm_91075]</a></li>
<li><code>Csm_KeyGetStatus</code> <a class="spec-record-ref" data-req="SWS_Csm_91047" href="../../spec/record.html?id=SWS_Csm_91047">[SWS_Csm_91047]</a>, which calls <code>CryIf_KeyGetStatus</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_8_2_Key_Status_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_8_2_Key_Status_Interface">SWS CSM p. 63</a>)</li>
</ul>
<p>The job-based variants <code>Csm_JobKeySetValid</code> and <code>Csm_JobKeySetInvalid</code> run synchronously or asynchronously depending on the job configuration. In R20-11, they accept <code>jobId</code> and <code>keyId</code> <a class="spec-record-ref" data-req="SWS_Csm_91027" href="../../spec/record.html?id=SWS_Csm_91027">[SWS_Csm_91027]</a>, <a class="spec-record-ref" data-req="SWS_Csm_91002" href="../../spec/record.html?id=SWS_Csm_91002">[SWS_Csm_91002]</a>. The R20-11 signature is decisive.</p>

Their size results from configured maximum lengths, such as for <code>Csm_HashDataType_{Crypto}</code>, <code>Csm_HashResultType_{Crypto}</code>, and <code>Csm_MacGenerateDataType_{Crypto}</code> <a class="spec-record-ref" data-req="SWS_Csm_01920" href="../../spec/record.html?id=SWS_Csm_01920">[SWS_Csm_01920]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00912" href="../../spec/record.html?id=SWS_Csm_00912">[SWS_Csm_00912]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00935" href="../../spec/record.html?id=SWS_Csm_00935">[SWS_Csm_00935]</a>.</p>
<p>The content of <code>Csm_ConfigType</code> is implementation-specific <a class="spec-record-ref" data-req="SWS_Csm_01085" href="../../spec/record.html?id=SWS_Csm_01085">[SWS_Csm_01085]</a>. The <code>configPtr</code> of <code>Csm_Init</code> must be a null pointer (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_1_General_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_1_General_Interface">SWS CSM p. 48</a>). The most important configuration contents:</p>
<ul>
<li>A <code>CsmJob</code> carries <code>CsmJobId</code>, <code>CsmJobPriority</code>, <code>CsmJobPrimitiveRef</code>, and <code>CsmJobInterfaceUsePort</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-bca73536c803319f.html" data-snip="FIG-bca73536c803319f">SWS CSM p. 166</a>).</li>
<li>Primitives are implemented as constant <code>Crypto_PrimitiveInfoType</code> structures (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_1_1_Configuration.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_1_1_Configuration">SWS CSM p. 23</a>) <a class="spec-record-ref" data-req="SWS_Csm_01011" href="../../spec/record.html?id=SWS_Csm_01011">[SWS_Csm_01011]</a>.</li>
<li>A <code>CsmKey</code> references a CryIf key via <code>CsmKeyRef</code> (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-1356cde11ab9966a.html" data-snip="FIG-1356cde11ab9966a">SWS CSM p. 161</a>).</li>
<li>A <code>CsmQueue</code> buffers jobs when hardware is busy and determines the channel (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_10_6.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_10_6">SWS CSM p. 164</a>).</li>
</ul>
<p>With <code>Crypto_JobRedirectionInfoType</code>, inputs and outputs can be redirected to key elements <a class="spec-record-ref" data-req="SWS_Csm_91026" href="../../spec/record.html?id=SWS_Csm_91026">[SWS_Csm_91026]</a>, <a class="spec-record-ref" data-req="SWS_Csm_91024" href="../../spec/record.html?id=SWS_Csm_91024">[SWS_Csm_91024]</a>.</p>

<h4>Behavior in the event of an error</h4>
<p>Services report their result as <code>Std_ReturnType</code> or <code>Crypto_ResultType</code>. In addition to <code>E_OK</code> and <code>E_NOT_OK</code>, there are specific codes such as <code>CRYPTO_E_BUSY</code>, <code>CRYPTO_E_ENTROPY_EXHAUSTED</code>, and <code>CRYPTO_E_KEY_NOT_VALID</code> <a class="spec-record-ref" data-req="SWS_Csm_91044" href="../../spec/record.html?id=SWS_Csm_91044">[SWS_Csm_91044]</a>, <a class="spec-record-ref" data-req="SWS_Csm_91043" href="../../spec/record.html?id=SWS_Csm_91043">[SWS_Csm_91043]</a>. For verification services, <code>E_OK</code> only means that the request was successful. The actual verdict is in <code>verifyPtr</code> as <code>CRYPTO_E_VER_OK</code> or <code>CRYPTO_E_VER_NOT_OK</code> <a class="spec-record-ref" data-req="SWS_Csm_01050" href="../../spec/record.html?id=SWS_Csm_01050">[SWS_Csm_01050]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01024" href="../../spec/record.html?id=SWS_Csm_01024">[SWS_Csm_01024]</a>.</p>
<p>If development error detection is active, the CSM reports the following errors to DET <a class="spec-record-ref" data-req="SWS_Csm_91004" href="../../spec/record.html?id=SWS_Csm_91004">[SWS_Csm_91004]</a>:</p>
<ul>
<li><code>CSM_E_PARAM_POINTER</code></li>
<li><code>CSM_E_PARAM_HANDLE</code></li>
<li><code>CSM_E_UNINIT</code></li>
<li><code>CSM_E_INIT_FAILED</code>, in case of failed initialization (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_1_General_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_1_General_Interface">SWS CSM p. 48</a>)</li>
<li><code>CSM_E_PROCESSING_MODE</code></li>
</ul>
<p>A queue overflow is the runtime error <code>CSM_E_QUEUE_FULL</code> <a class="spec-record-ref" data-req="SWS_Csm_01089" href="../../spec/record.html?id=SWS_Csm_01089">[SWS_Csm_01089]</a>.</p>
<p>If <code>Csm_KeyElementSet</code> fails, the state of the element is unknown. The application can check it with <code>Csm_KeyGetStatus</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_8_1_Key_Setting_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_8_1_Key_Setting_Interface">SWS CSM p. 62</a>) <a class="spec-record-ref" data-req="SWS_Csm_00957" href="../../spec/record.html?id=SWS_Csm_00957">[SWS_Csm_00957]</a>. Derivation and copy can fail with <code>CRYPTO_E_KEY_READ_FAIL</code>, <code>…_WRITE_FAIL</code>, <code>…_SIZE_MISMATCH</code>, or <code>CRYPTO_E_KEY_EMPTY</code> <a class="spec-record-ref" data-req="SWS_Csm_00956" href="../../spec/record.html?id=SWS_Csm_00956">[SWS_Csm_00956]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00969" href="../../spec/record.html?id=SWS_Csm_00969">[SWS_Csm_00969]</a>.</p>
<p><code>Csm_CancelJob</code> cancels asynchronous or streaming jobs <a class="spec-record-ref" data-req="SWS_Csm_00968" href="../../spec/record.html?id=SWS_Csm_00968">[SWS_Csm_00968]</a>. The return values mean:</p>
<ul>
<li><code>E_OK</code>: The job is removed.</li>
<li><code>CRYPTO_E_JOB_CANCELED</code>: Cancellation only occurs at the next suitable step and is reported via a negative completion callback.</li>
</ul>
<p>The later document citation adds: For synchronous jobs, <code>Csm_CancelJob</code> reports <code>CSM_E_PROCESSING_MODE</code>. The CSM removes the job from the queue or calls <code>CryIf_CancelJob</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_3_11_Job_Cancellation_Interface.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_3_11_Job_Cancellation_Interface">SWS CSM p. 80</a>).</p>
