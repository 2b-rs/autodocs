<h4>Context</h4>
<p>The class <code>apext::com::secoc::FVM</code> provides the standardized interface for Freshness Value Management (FVM) within the Communication Management (CM) module (<a class="spec-record-ref" data-req="SWS_CM_11287" href="../spec/record.html?id=SWS_CM_11287">[SWS_CM_11287]</a>). It serves to protect service-oriented communication against replay attacks within the scope of Secure Onboard Communication (SecOC). The interface is implemented as a library specific to the manufacturer by the OEM or the stack supplier (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=537">AUTOSAR_AP_SWS_CommunicationManagement p. 537 “Class: FVM”</a>). Within Communication Management, exactly one central instance (singleton) of this class exists for managing the freshness values (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=537">AUTOSAR_AP_SWS_CommunicationManagement p. 537 “Class: FVM”</a>).</p>
<p>The main interaction partners are Communication Management (<code>ara::com</code>) as the controlling instance, the manufacturer-specific FVM library for calculating and synchronizing freshness values, and the secured communication channels (transmission and reception channels) for authenticated messages (<a class="spec-record-ref" data-req="SWS_CM_11272" href="../spec/record.html?id=SWS_CM_11272">[SWS_CM_11272]</a>, <a class="spec-record-ref" data-req="SWS_CM_11274" href="../spec/record.html?id=SWS_CM_11274">[SWS_CM_11274]</a>, <a class="spec-record-ref" data-req="SWS_CM_11276" href="../spec/record.html?id=SWS_CM_11276">[SWS_CM_11276]</a>).</p>

<h4>Lifecycle</h4>
<p>The lifecycle of the <code>FVM</code> implementation is fully managed by <code>ara::com</code> (<a class="spec-record-ref" data-req="SWS_CM_11272" href="../spec/record.html?id=SWS_CM_11272">[SWS_CM_11272]</a>). During initialization of the communication stack, Communication Management creates the singleton instance and explicitly calls the method <code>Initialize()</code> (<a class="spec-record-ref" data-req="SWS_CM_11273" href="../spec/record.html?id=SWS_CM_11273">[SWS_CM_11273]</a>, <a class="spec-record-ref" data-req="SWS_CM_11290" href="../spec/record.html?id=SWS_CM_11290">[SWS_CM_11290]</a>). Only after the successful return of <code>Initialize()</code> is the Freshness Value Manager in the operational state.</p>
<p>Ownership and control rights lie exclusively with Communication Management. Since the class is operated as a singleton and potentially multiple transmit and receive connections are processed in parallel, the thread safety of the method calls is likely ensured by the manufacturer-specific implementation of the FVM library (interpretation). An orderly shutdown takes place analogously via the lifecycle management of <code>ara::com</code> (<a class="spec-record-ref" data-req="SWS_CM_11272" href="../spec/record.html?id=SWS_CM_11272">[SWS_CM_11272]</a>).</p>

<h4>Usage Path</h4>
<p>After initialization, the typical interaction is divided into two operational paths: the transmit path (Tx) and the receive path (Rx).</p>
<ul>
  <li><strong>Initialization:</strong> Communication Management calls <code>Initialize()</code> to prepare internal structures, synchronization counters, or cryptographic timers of the FVM library (<a class="spec-record-ref" data-req="SWS_CM_11273" href="../spec/record.html?id=SWS_CM_11273">[SWS_CM_11273]</a>, <a class="spec-record-ref" data-req="SWS_CM_11290" href="../spec/record.html?id=SWS_CM_11290">[SWS_CM_11290]</a>).</li>
  <li><strong>Transmit path (Tx):</strong> If a message is to be sent secured via SecOC and a <code>freshnessValueId</code> is stored in the configuration, <code>ara::com</code> requests the current freshness value via <code>GetTxFreshness(SecOCFreshnessValueID)</code> (<a class="spec-record-ref" data-req="SWS_CM_11274" href="../spec/record.html?id=SWS_CM_11274">[SWS_CM_11274]</a>, <a class="spec-record-ref" data-req="SWS_CM_11289" href="../spec/record.html?id=SWS_CM_11289">[SWS_CM_11289]</a>). Authentication takes place in the processing order after the E2E protection calculations (<a class="spec-record-ref" data-req="SWS_CM_11274" href="../spec/record.html?id=SWS_CM_11274">[SWS_CM_11274]</a>). The obtained <code>FVContainer</code> is subsequently used to calculate the authenticator (<a class="spec-record-ref" data-req="SWS_CM_11289" href="../spec/record.html?id=SWS_CM_11289">[SWS_CM_11289]</a>).</li>
  <li><strong>Reception path (Rx):</strong> Upon arrival of a secured message, <code>ara::com</code> checks the attribute <code>securedRxVerification</code>. If this is activated or not explicitly defined, the freshness value is queried via <code>GetRxFreshness(SecOCFreshnessValueID, SecOCTruncatedFreshnessValue, SecOCAuthVerifyAttempts)</code> (<a class="spec-record-ref" data-req="SWS_CM_11276" href="../spec/record.html?id=SWS_CM_11276">[SWS_CM_11276]</a>, <a class="spec-record-ref" data-req="SWS_CM_11288" href="../spec/record.html?id=SWS_CM_11288">[SWS_CM_11288]</a>). The call passes the truncated freshness value from the received message as well as the verification attempt counter. After calculation and verification of the authenticator, <code>ara::com</code> reports the result back to the FVM via <code>SetVerificationStatus(secOCFreshnessValueID, secOCVerificationStatus)</code> (<a class="spec-record-ref" data-req="SWS_CM_19999" href="../spec/record.html?id=SWS_CM_19999">[SWS_CM_19999]</a>). If, on the other hand, <code>securedRxVerification</code> is configured to <code>false</code>, verification is bypassed and the message is forwarded without an FVM check (<a class="spec-record-ref" data-req="SWS_CM_11372" href="../spec/record.html?id=SWS_CM_11372">[SWS_CM_11372]</a>).</li>
</ul>

<h4>Error Scenarios</h4>
<p>All interface methods of <code>apext::com::secoc::FVM</code> are declared with <code>noexcept</code> and report error states deterministically via the error type <code>ara::core::Result</code> (<a class="spec-record-ref" data-req="SWS_CM_11288" href="../spec/record.html?id=SWS_CM_11288">[SWS_CM_11288]</a>, <a class="spec-record-ref" data-req="SWS_CM_11289" href="../spec/record.html?id=SWS_CM_11289">[SWS_CM_11289]</a>, <a class="spec-record-ref" data-req="SWS_CM_11290" href="../spec/record.html?id=SWS_CM_11290">[SWS_CM_11290]</a>, <a class="spec-record-ref" data-req="SWS_CM_19999" href="../spec/record.html?id=SWS_CM_19999">[SWS_CM_19999]</a>).</p>
<p>The following error and status codes are specified:</p>
<ul>
  <li><strong>Initialization failure:</strong> If the preparation of the FVM library fails, <code>Initialize()</code> returns the error code <code>ComSecOcFvmErrc::kFVInitializeFailed</code> (<a class="spec-record-ref" data-req="SWS_CM_11290" href="../spec/record.html?id=SWS_CM_11290">[SWS_CM_11290]</a>). In this case, the SecOC subsystem cannot process secured messages.</li>
  <li><strong>Unavailable freshness value (Tx):</strong> If <code>GetTxFreshness()</code> returns the error <code>ComSecOcFvmErrc::kFVNotAvailable</code> or calculation of the authenticator fails, <code>ara::com</code> increments the <code>Authentication Build Counter</code> for this message (<a class="spec-record-ref" data-req="SWS_CM_11275" href="../spec/record.html?id=SWS_CM_11275">[SWS_CM_11275]</a>, <a class="spec-record-ref" data-req="SWS_CM_11289" href="../spec/record.html?id=SWS_CM_11289">[SWS_CM_11289]</a>). The creation process is repeated in an implementation-specific manner. If the counter reaches the configured threshold <code>SecOCAuthenticationBuildAttempts</code>, the message is discarded (<a class="spec-record-ref" data-req="SWS_CM_11275" href="../spec/record.html?id=SWS_CM_11275">[SWS_CM_11275]</a>). Upon successful creation, the counter is reset to 0 (<a class="spec-record-ref" data-req="SWS_CM_11275" href="../spec/record.html?id=SWS_CM_11275">[SWS_CM_11275]</a>).</li>
  <li><strong>Unavailable freshness value (Rx):</strong> If the freshness value cannot be determined for a received message, <code>GetRxFreshness()</code> also returns <code>ComSecOcFvmErrc::kFVNotAvailable</code> (<a class="spec-record-ref" data-req="SWS_CM_11288" href="../spec/record.html?id=SWS_CM_11288">[SWS_CM_11288]</a>). This prevents successful verification of the authenticator.</li>
  <li><strong>Feedback of verification status:</strong> Via <code>SetVerificationStatus()</code>, <code>ara::com</code> transmits the result of the check to the FVM (<a class="spec-record-ref" data-req="SWS_CM_19999" href="../spec/record.html?id=SWS_CM_19999">[SWS_CM_19999]</a>). The enumeration <code>VerificationStatus</code> (<a class="spec-record-ref" data-req="SWS_CM_11378" href="../spec/record.html?id=SWS_CM_11378">[SWS_CM_11378]</a>) distinguishes between:
    <ul>
      <li><code>Success</code>: Verification successful.</li>
      <li><code>kSecOcVerificationFailure</code> (0x01): General verification error.</li>
      <li><code>kSecOcFreshnessFailure</code> (0x02): Verification failed due to an invalid freshness value.</li>
      <li><code>kSecOcAuthenticationBuildFailure</code> (0x03): Error generating the authentication code.</li>
      <li><code>kSecOcNoVerification</code> (0x04): Verification was skipped and data directly passed.</li>
      <li><code>kSecOcVerificationFailureOverwritten</code> (0x05): Verification failed; message was forwarded anyway due to override status.</li>
    </ul>
  </li>
</ul>
