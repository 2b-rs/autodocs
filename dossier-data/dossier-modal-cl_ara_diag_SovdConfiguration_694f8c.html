  <h4>Context</h4>
  <p>
    The class <code>ara::diag::SovdConfiguration</code> represents the generic interface for SOVD configurations (Service-Oriented Vehicle Diagnostics) on the AUTOSAR Adaptive Platform (<a class="spec-record-ref" data-req="SWS_DM_01860" href="../spec/record.html?id=SWS_DM_01860">[SWS_DM_01860]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=718">AUTOSAR_AP_SWS_Diagnostics §8.54.1 “Class: SovdConfiguration”</a>). As soon as at least one SOVD configuration is modeled in the system, the instance of the Diagnostic Server provides the standardized SOVD method for listing all provided configurations (<a class="spec-record-ref" data-req="SWS_DM_01429" href="../spec/record.html?id=SWS_DM_01429">[SWS_DM_01429]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=207">AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2 “SOVD API – Configuration”</a>).
  </p>
  <p>
    For explicitly modeled SOVD configurations, a derived instance of <code>ara::diag::SovdConfiguration</code> acts as an application handler. The Diagnostic Server (DM) functions as an intermediary: Incoming external requests for the SOVD methods <em>Read Configuration</em> and <em>Write Configuration</em> are received by the Diagnostic Server and forwarded to the application via the interface methods <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01787" href="../spec/record.html?id=SWS_DM_01787">[SWS_DM_01787]</a>) and <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01788" href="../spec/record.html?id=SWS_DM_01788">[SWS_DM_01788]</a>), respectively.
  </p>

  <h4>Lifecycle</h4>
  <p>
    Application classes derive from <code>ara::diag::SovdConfiguration</code> and instantiate the object via the constructor, which requires a <code>ara::core::InstanceSpecifier</code> as well as a <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>). The <code>InstanceSpecifier</code> links the object to a modeled port prototype.
  </p>
  <p>
    With regard to ownership, the class is designed as a single instance: Both the copy constructor (<a class="spec-record-ref" data-req="SWS_DM_01866" href="../spec/record.html?id=SWS_DM_01866">[SWS_DM_01866]</a>) and copy assignment operator (<a class="spec-record-ref" data-req="SWS_DM_01868" href="../spec/record.html?id=SWS_DM_01868">[SWS_DM_01868]</a>) are deleted (<code>delete</code>). Move operations (move constructor and move assignment) are declared as <code>protected</code> and <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_DM_01867" href="../spec/record.html?id=SWS_DM_01867">[SWS_DM_01867]</a>, <a class="spec-record-ref" data-req="SWS_DM_01869" href="../spec/record.html?id=SWS_DM_01869">[SWS_DM_01869]</a>).
  </p>
  <p>
    After instantiation, the object is initially in an inactive state. Only by calling <code>Offer()</code> is the Diagnostic Management daemon enabled to forward requests for this handler (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>). If the service is no longer to be available, forwarding is deactivated via <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>). The virtual destructor <code>~SovdConfiguration()</code> serves to destroy the object (<a class="spec-record-ref" data-req="SWS_DM_01865" href="../spec/record.html?id=SWS_DM_01865">[SWS_DM_01865]</a>). Interpretation: In the regular shutdown scenario, <code>StopOffer()</code> is presumably called before object destruction to prevent asynchronous access while the destructor is running.
  </p>
  <p>
    Regarding concurrency, the constructor is thread-safe (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>), whereas <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>), <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>), and the destructor (<a class="spec-record-ref" data-req="SWS_DM_01865" href="../spec/record.html?id=SWS_DM_01865">[SWS_DM_01865]</a>) are not thread-safe. The thread safety of the handler methods <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01870" href="../spec/record.html?id=SWS_DM_01870">[SWS_DM_01870]</a>) and <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01871" href="../spec/record.html?id=SWS_DM_01871">[SWS_DM_01871]</a>) is conditional: It depends on whether <code>ConcurrencyType::kConcurrent</code> or <code>ConcurrencyType::kNotConcurrent</code> was passed during construction.
  </p>

  <h4>Usage Path</h4>
  <p>
    A typical usage path for handling SOVD configuration queries includes the following phases:
  </p>
  <ol>
    <li>
      <strong>Initialization:</strong> The application instantiates the derived class with the appropriate <code>InstanceSpecifier</code> and the desired concurrency mode (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>).
    </li>
    <li>
      <strong>Service offering:</strong> Calling <code>Offer()</code> activates the forwarding of requests (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>).
    </li>
    <li>
      <strong>Request processing (read):</strong> If an SOVD read request is received by the Diagnostic Server (<a class="spec-record-ref" data-req="SWS_DM_01787" href="../spec/record.html?id=SWS_DM_01787">[SWS_DM_01787]</a>), it calls <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01870" href="../spec/record.html?id=SWS_DM_01870">[SWS_DM_01870]</a>). The application processes the passed <code>configurationId</code> and <code>MetaInfo</code>, monitors the <code>CancellationHandler</code>, and returns a <code>ara::core::Future</code> with a <code>std::tuple</code> consisting of <code>DataTransferReadSession</code> and <code>SovdConfigurationMetaInfo</code>.
    </li>
    <li>
      <strong>Request processing (write):</strong> In the case of a write request (<a class="spec-record-ref" data-req="SWS_DM_01788" href="../spec/record.html?id=SWS_DM_01788">[SWS_DM_01788]</a>), the server calls <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01871" href="../spec/record.html?id=SWS_DM_01871">[SWS_DM_01871]</a>), whereupon the application provides a <code>Future</code> with <code>DataTransferWriteSession</code> and meta-information.
    </li>
    <li>
      <strong>Service termination:</strong> Before terminating the component, the application deactivates the reception of further requests via <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>).
    </li>
  </ol>

  <h4>Error Scenarios</h4>
  <p>
    Error situations can occur in various phases of the interaction:
  </p>
  <ul>
    <li>
      <strong>Construction violations:</strong> When calling the constructor (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>), modeling and mapping errors can occur:
      <ul>
        <li><code>InstanceSpecifierMappingIntegrityViolation</code>: The identifier cannot be resolved in the context of the executable file or does not refer to a PortPrototype.</li>
        <li><code>PortInterfaceMappingViolation</code>: The PortPrototype is not typed by a <code>DiagnosticSovdConfigurationInterface</code>.</li>
        <li><code>ProcessMappingViolation</code>: No mapping to a matching modeled process exists.</li>
        <li><code>InstanceSpecifierAlreadyInUseViolation</code>: The <code>InstanceSpecifier</code> is already being used within the process.</li>
      </ul>
    </li>
    <li>
      <strong>Errors during offering (Offer):</strong> <code>Offer()</code> returns a <code>ara::core::Result&lt;void&gt;</code> (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>). Possible error codes are:
      <ul>
        <li><code>DiagOfferErrc::kConfigurationMismatch</code>: The monitoring configuration does not match the DEXT (rollback semantics).</li>
        <li><code>DiagOfferErrc::kAlreadyOffered</code>: The service was already offered previously (rollback semantics).</li>
      </ul>
    </li>
    <li>
      <strong>Errors during configuration processing:</strong> If reading or writing a configuration instance fails, the implementation transmits a standardized SOVD error code according to ISO 17978-3 / ASAM SOVD 1.1 via the <code>Future</code> returned by <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01870" href="../spec/record.html?id=SWS_DM_01870">[SWS_DM_01870]</a>) or <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01871" href="../spec/record.html?id=SWS_DM_01871">[SWS_DM_01871]</a>). In addition, the <code>CancellationHandler</code> signals if an ongoing conversation was aborted.
    </li>
  </ul>
