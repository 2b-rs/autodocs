<h4>Role and system context of the service interface</h4>
<p>The service interface <code>VerificationStatusConfigurationByDataId</code> serves in the Functional Cluster Communication Management (CM) for configuring and specifically influencing the SecOC verification (Secure Onboard Communication) for specific data identifiers (<a class="spec-record-ref" data-req="SWS_CM_11369" href="../spec/record.html?id=SWS_CM_11369">[SWS_CM_11369]</a>, <a class="spec-record-ref" data-req="SWS_CM_11279" href="../spec/record.html?id=SWS_CM_11279">[SWS_CM_11279]</a>). <p>On the consumer side, specialized applications such as security management systems, intrusion detection systems (IDS), or test and diagnostic tools interact with the service via the corresponding proxy class (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=227">AUTOSAR AP SWS CommunicationManagement §8.1 “SecOC VerificationStatus”</a>). While the complementary service <code>VerificationStatus</code> serves to continuously propagate verification results to applications, <code>VerificationStatusConfigurationByDataId</code> enables active control of the verification behavior (<a class="spec-record-ref" data-req="SWS_CM_11278" href="../spec/record.html?id=SWS_CM_11278">[SWS_CM_11278]</a>, <a class="spec-record-ref" data-req="SWS_CM_11279" href="../spec/record.html?id=SWS_CM_11279">[SWS_CM_11279]</a>). <h4>Methods, events, and fields</h4>
<p>The service interface has the version number 1.0 and provides only the method <code>VerifyStatusOverride</code>; events or fields are not defined in the interface (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>). For the method, the property <code>Fire &amp; Forget</code> is set to <code>false</code>, which is why calls do not occur unilaterally without acknowledgment, but require synchronous or asynchronous feedback to the caller (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>).</p>
<p>The method <code>VerifyStatusOverride</code> accepts three input parameters (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>):</p>
<ul>
<li><code>dataID</code> (IN, <code>uint16_t</code>): Specifies the data ID for which the override operation is to be applied (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>).</li>
<li><code>overrideStatus</code> (IN, <code>OverrideStatus</code>): An enumeration value defining whether verification is executed, whether the message is forwarded or discarded, and for what duration the override remains active (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>).</li>
<li><code>numberOfMessagesToOverride</code> (IN, <code>uint8_t</code>): Specifies the number of consecutive verification attempts to be overridden (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>). This counter is evaluated only when <code>overrideStatus</code> is set to one of the values <code>kSecOcOverrideDropUntilLimit</code>, <code>kSecOcOverrideSkipUntilLimit</code>, or <code>kSecOcOverridePassUntilLimit</code> (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>).</li>
</ul>
<p>Via these parameters, the SecOC subsystem can be instructed to accept or discard incoming messages regardless of the result of the authenticator check, to skip the calculation of the authenticator, and to specifically force a particular result for <code>VerificationStatusResult</code> (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>, <a class="spec-record-ref" data-req="SWS_CM_11278" href="../spec/record.html?id=SWS_CM_11278">[SWS_CM_11278]</a>).</p>

<p>If an invalid <code>dataID</code> or one not configured in the communication stack is passed, the call is likely rejected and reported to the calling application via the error concept of <code>ara::core::Result</code> (Interpretation: error handling for non-existent Data-ID via result types) (<a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=227">AUTOSAR AP SWS CommunicationManagement §8.1 “SecOC VerificationStatus”</a>). After successful acknowledgment, it is ensured that the override rules are active and subsequent verification results are mapped accordingly via the <code>VerificationStatus</code> service (<a class="spec-record-ref" data-req="SWS_CM_11278" href="../spec/record.html?id=SWS_CM_11278">[SWS_CM_11278]</a>, <a class="spec-record-ref" data-req="SWS_CM_10050" href="../spec/record.html?id=SWS_CM_10050">[SWS_CM_10050]</a>).</p>
