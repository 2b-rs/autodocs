<h4>Context</h4>
<p>
The data structure <code>ara::diag::DownloadService::OperationOutput</code> (<a class="spec-record-ref" data-req="SWS_DM_00785" href="../spec/record.html?id=SWS_DM_00785">[SWS_DM_00785]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=440">AUTOSAR_AP_SWS_Diagnostics §8.14.2 “Struct: OperationOutput”</a>) serves in the diagnostic module of AUTOSAR Adaptive as an output parameter for operations of the download service. It bundles the payload of a positive response message (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>) that a diagnostic application reports back to the Diagnostic Management Daemon (DM) after successful execution of a download operation. It is provided via the header <code>ara/diag/download.h</code> (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>).
</p>
<p>
Essentially three entities interact in the overall sequence:
</p>
<ul>
  <li>the external diagnostic tester, which requests diagnostic download services (e.g. data transfer or download termination),</li>
  <li>the Diagnostic Management Daemon (DM), which receives the incoming UDS request, validates it, and forwards it to the responsible service instance, and</li>
  <li>the actual application instance of <code>ara::diag::DownloadService</code>, which processes the operation, compiles the response data in <code>OperationOutput</code>, and returns it to the daemon.</li>
</ul>

<h4>Lifecycle</h4>
<p>
As a pure data transfer struct (Plain Old Data / Data Transfer Object), <code>OperationOutput</code> has no active lifecycle of its own or internal state machines (<a class="spec-record-ref" data-req="SWS_DM_00785" href="../spec/record.html?id=SWS_DM_00785">[SWS_DM_00785]</a>). An instance is instantiated locally by the application logic as soon as a download operation (such as in the context of <code>DownloadData</code> or <code>RequestDownloadExit</code>) has been successfully executed and a positive response is to be prepared (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>).
</p>
<p>
The lifetime of the object is bound to the creation and handover of the operation result. The application populates the member <code>responseData</code> of type <code>ara::core::Vector&lt;std::uint8_t&gt;</code> (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>) and passes the structure—typically embedded in a <code>ara::core::Future</code> or <code>ara::core::Result</code>—to the diagnostic infrastructure. After the serialization of the payload into the positive UDS response message, the lifetime of the object ends.
</p>

<h4>Usage Path</h4>
<p>
The typical invocation and processing path proceeds in the following steps:
</p>
<ol>
  <li><strong>Reception of the request:</strong> The diagnostic tester sends a download request, which is received by the DM and passed to the registered instance of <code>ara::diag::DownloadService</code>.</li>
  <li><strong>Instantiation and population:</strong> Upon successful processing, the application instantiates <code>OperationOutput</code> and populates <code>responseData</code> with the pure response payload (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>). In doing so, the service identifier (SID) is explicitly not stored in <code>responseData</code>, as it is prepended by the daemon (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>).</li>
  <li><strong>Handover of the result:</strong> The structure is returned to the diagnostic framework as the result of the operation.</li>
  <li><strong>Transmission to the tester:</strong> The diagnostic framework constructs the complete response telegram from the SID and the content of <code>responseData</code> and transmits it to the diagnostic tester.</li>
</ol>

<h4>Error Scenarios</h4>
<p>
The structure <code>OperationOutput</code> exclusively models the success case of a positive response (<em>positive response message</em>, <a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>). If a download operation fails or a precondition is violated, no valid <code>OperationOutput</code> object is processed; instead, the operation signals a corresponding error value (Negative Response Code / NRC) to the diagnostic framework.
</p>
<p>
An application-side configuration error consists in populating <code>responseData</code> with an incorrect data offset or redundant headers: Depending on the specific operation (such as <code>DownloadData</code> or <code>RequestDownloadExit</code>), the specification differs regarding the byte position at which the positive response begins after the SID (<a class="spec-record-ref" data-req="SWS_DM_00786" href="../spec/record.html?id=SWS_DM_00786">[SWS_DM_00786]</a>). If the SID is erroneously duplicated in <code>responseData</code>, this leads to an incorrectly formatted UDS telegram on the bus.
</p>
