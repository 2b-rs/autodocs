<h4>Systemarchitektur und funktionale Rolle von Log and Trace</h4>
<p>Das funktionale Cluster Log and Trace (<code>ara::log</code>) bildet das zentrale, querschnittliche Subsystem für die standardisierte Erfassung, Weiterleitung und Filterung von Diagnose-, Tracing- und Protokollmeldungen auf der AUTOSAR Adaptive Platform <a class="docref internal-spec-ref" href="../../spec/figures/FIG-2ae999b1b55c74dc.html" data-snip="FIG-2ae999b1b55c74dc">AUTOSAR AP SWS LogAndTrace S. 13</a>. Die Programmierschnittstelle <code>Logger</code> stellt die einheitliche C++-Plattform-API bereit, welche sowohl von anwendungsspezifischen Prozessen (Adaptive Applications) als auch von den grundlegenden funktionalen Plattform-Clustern als Basisinfrastruktur konsumiert wird <a class="docref internal-spec-ref" href="../../spec/figures/FIG-9fda63704abf4125.html" data-snip="FIG-9fda63704abf4125">AUTOSAR AP EXP SWArchitecture S. 58</a>. Zu diesen konsumierenden System-Daemons gehören unter anderem das Execution Management zur Prozesslebenszyklus-Dokumentation <a class="docref internal-spec-ref" href="../../spec/figures/FIG-8dbc7b9360a1911c.html" data-snip="FIG-8dbc7b9360a1911c">AUTOSAR AP EXP SWArchitecture S. 50</a>, das Platform Health Management zur Zustandsüberwachung <a class="docref internal-spec-ref" href="../../spec/figures/FIG-2bce48466bb4bedb.html" data-snip="FIG-2bce48466bb4bedb">AUTOSAR AP SWS PlatformHealthManagement S. 16</a>, Time Synchronization für hochpräzise Zeitbezüge <a class="docref internal-spec-ref" href="../../spec/figures/FIG-49207b6911bb8f46.html" data-snip="FIG-49207b6911bb8f46">AUTOSAR AP SWS TimeSynchronization S. 17</a> sowie das Update and Configuration Management während Software-Aktualisierungen <a class="docref internal-spec-ref" href="../../spec/figures/FIG-08f92a380f91aec1.html" data-snip="FIG-08f92a380f91aec1">AUTOSAR AP EXP SWArchitecture S. 141</a>.</p>

<p>Architektonisch kapselt jede Logger-Instanz einen eindeutigen Kontext (Context ID) innerhalb eines Anwendungs- oder Prozessbereichs, wobei sich dieser Kontext bei der Erzeugung selbsttätig beim Logging-Backend registriert und beim Herunterfahren der Anwendung automatisch deregistriert wird <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_9_15.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_9_15">EXP SWArchitecture S. 57</a>. Das Logging-Backend leitet formatierte Meldungen an projektierte Ausgabekanäle (z. B. DLT-Protokollsenken über Ethernet gemäß Machine-Manifest) oder an lokale Puffer weiter, wobei bei fehlendem Bereitstellungsmodell standardmäßig auf die Betriebssystem-Konsole zurückgegriffen wird <a class="spec-record-ref" data-req="SWS_LOG_00021" href="../spec/record.html?id=SWS_LOG_00021">[SWS_LOG_00021]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_7_1_LOGANDTRACE.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_7_1_LOGANDTRACE">SWS LogAndTrace S. 21</a>. Darüber hinaus gestattet eine entkoppelte Adapter-Architektur dem Betriebssystem (POSIX/OS), interne Kernel- und Scheduling-Metriken über das AUTOSAR Run-Time Interface (ARTI) synchronisiert mit den Meldungen von <code>ara::log</code> bereitzustellen <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e373fbe47b1f92fb.html" data-snip="FIG-e373fbe47b1f92fb">AUTOSAR AP SWS OperatingSystemInterface S. 21</a>.</p>

<h4>Instanziierung, Kontextverwaltung und Schwellwertsteuerung</h4>
<p>Die Bereitstellung eines Logger-Kontexts erfolgt über die Fabrikfunktionen <code>ara::log::CreateLogger</code>, da der Standardkonstruktor der Klasse <code>Logger</code> gelöscht ist <a class="spec-record-ref" data-req="SWS_LOG_00259" href="../spec/record.html?id=SWS_LOG_00259">[SWS_LOG_00259]</a>. Anwendungen können Logger entweder programmatisch unter Angabe einer Kontext-ID (<code>ctxId</code>), einer Beschreibung (<code>ctxDescription</code>) und optional eines Standard-Loglevels instanziieren <a class="spec-record-ref" data-req="SWS_LOG_00021" href="../spec/record.html?id=SWS_LOG_00021">[SWS_LOG_00021]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00263" href="../spec/record.html?id=SWS_LOG_00263">[SWS_LOG_00263]</a>, oder instanzbasiert über ein Modell-Element mittels <code>ara::core::InstanceSpecifier</code> ableiten <a class="spec-record-ref" data-req="SWS_LOG_00256" href="../spec/record.html?id=SWS_LOG_00256">[SWS_LOG_00256]</a>. Der Zerstörer von <code>Logger</code> wickelt die Entregistrierung thread-sicher ab <a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>.</p>

<p>Die Granularität und Priorität von Meldungen wird durch die Aufzählung <code>LogLevel</code> hierarchisch abgebildet: <code>kFatal</code> (nicht behebbarer Systemfehler), <code>kError</code> (Fehler mit Funktionsbeeinträchtigung), <code>kWarn</code> (Warnung bei gefährdetem Sollverhalten), <code>kInfo</code> (allgemeine Betriebsinformation), <code>kDebug</code> (Detaildiagnose) und <code>kVerbose</code> (ausführliche Ablaufverfolgung) <a class="spec-record-ref" data-req="SWS_LOG_00018" href="../spec/record.html?id=SWS_LOG_00018">[SWS_LOG_00018]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_MANIFESTSPECIFICATION_SECTION_10_3_3_SignalBasedMethod_Mapping.html" data-snip="SNIP_CLASSIC_MANIFESTSPECIFICATION_SECTION_10_3_3_SignalBasedMethod_Mapping">ManifestSpecification S. 416</a>. Zur Laufzeitoptimierung können rechenintensive Vorbereitungen von Protokolldaten vermieden werden, indem vorab über die Abfrage <code>IsEnabled(logLevel)</code> geprüft wird, ob das betreffende Loglevel am Kontext aktuell aktiv geschaltet ist <a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>. Der aktive Meldeschwellwert einer Logger-Instanz lässt sich bei Bedarf zur Laufzeit über <code>SetThreshold(threshold)</code> dynamisch anpassen <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>.</p>

<h4>Unmodellierte Protokollierung und Stream-basierte Nachrichtenkomposition</h4>
<p>Für unmodellierte Meldungen stellt <code>ara::log</code> ein an das Builder-Entwurfsmuster angelehntes Fluent-Interface bereit <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_16_1.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_16_1">PlatformDesign S. 74</a>. Der Einstieg erfolgt über Schweregrad-spezifische Elementfunktionen der <code>Logger</code>-Instanz, namentlich <code>LogFatal()</code>, <code>LogError()</code>, <code>LogWarn()</code>, <code>LogInfo()</code>, <code>LogDebug()</code> und <code>LogVerbose()</code>, oder über <code>WithLevel(logLevel)</code>, welche ein temporäres, leichtgewichtiges <code>LogStream</code>-Objekt zurückgeben <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00065" href="../spec/record.html?id=SWS_LOG_00065">[SWS_LOG_00065]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00066" href="../spec/record.html?id=SWS_LOG_00066">[SWS_LOG_00066]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00067" href="../spec/record.html?id=SWS_LOG_00067">[SWS_LOG_00067]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00068" href="../spec/record.html?id=SWS_LOG_00068">[SWS_LOG_00068]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00069" href="../spec/record.html?id=SWS_LOG_00069">[SWS_LOG_00069]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>. Daten werden anschließend über den typsicheren Stream-Einfügeoperator (<code>operator&lt;&lt;</code>) verkettet an den internen Nachrichtenpuffer angehängt <a class="spec-record-ref" data-req="SWS_LOG_00040" href="../spec/record.html?id=SWS_LOG_00040">[SWS_LOG_00040]</a>.</p>

<h4>Modellierte Protokollierung und Verzweigung zu ARTI-Tracing</h4>
<p>Im Gegensatz zum stufenweisen Aufbau unmodellierter Nachrichten definiert <code>ara::log</code> für im Manifest modellierte Nachrichten eine hocheffiziente Single-Call-Schnittstelle über <code>Logger::Log(id, args...)</code> sowie <code>Logger::LogWith(attrs, msgId, params...)</code> <a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>. Alle Argumente werden in einem einzigen Funktionsaufruf übergeben, wodurch der Laufzeit-Overhead im Falle unterdrückter Meldungen auf ein Minimum reduziert wird: Direkt nach Parameterübergabe prüft eine einzelne Bedingung den Schwellwert und kehrt sofort zurück, falls das konfigurierte Loglevel nicht erreicht ist <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_16_1.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_16_1">PlatformDesign S. 74</a>.</p>

<p>Innerhalb des Aufrufs von <code>Log</code> spaltet sich der Verarbeitungspfad auf: Neben dem klassischen Pfad der DLT-Serialisierung (<code>buildDltMessage()</code>, Filterung via Logmaske und Übergabe an die Senke) existiert ein dedizierter Pfad zur hardwarenahen Ablaufverfolgung über das AUTOSAR Run-Time Interface (ARTI) mittels <code>TraceArti(msg_id, params...)</code> <a class="spec-record-ref" data-req="SWS_LOG_20000" href="../spec/record.html?id=SWS_LOG_20000">[SWS_LOG_20000]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-5aae5d00cd13c25e.html" data-snip="FIG-5aae5d00cd13c25e">AUTOSAR AP SWS LogAndTrace S. 42</a>. Vermutlich wird die Weiterschaltung an <code>TraceArti</code> über statische Template-Spezialisierungen zur Übersetzungszeit aufgelöst, um den geforderten minimalen Laufzeit-Overhead sicherzustellen. <a class="interp-q interp-q-unmatched" data-q-status="unmatched" href="../versions.html?tab=q&amp;qsub=module:adaptive:log&amp;qst=open" title="Annahmen und Fragen zu diesem Text (Versions- &amp; Provenienz-Explorer)">Frage (offen)</a> Das ARTI-Backend filtert nach eigenen Kriterien basierend auf der <code>MsgId</code> und umgeht die DLT-Pufferung vollständig, was echtzeitkritisches Tracing ohne Störung des regulären Logging-Subsystems gestattet <a class="docref internal-spec-ref" href="../../spec/figures/FIG-5aae5d00cd13c25e.html" data-snip="FIG-5aae5d00cd13c25e">AUTOSAR AP SWS LogAndTrace S. 42</a>.</p>

<h4>Client-Verbindungsüberwachung und Diagnoseanbindung</h4>
<p>Log and Trace stellt nicht nur lokale Ausgabekanäle bereit, sondern überwacht auch den Zustand externer Diagnose-Clients (z. B. DLT-Viewer über Ethernet), repräsentiert durch die Aufzählung <code>ClientState</code>: <code>kUnknown</code> (-1, DLT-Backend noch nicht bereit), <code>kNotConnected</code> (kein entfernter Client erkannt) und <code>kConnected</code> (Verbindung zu externem Client aktiv) <a class="spec-record-ref" data-req="SWS_LOG_00098" href="../spec/record.html?id=SWS_LOG_00098">[SWS_LOG_00098]</a>. Dies erlaubt Anwendungen, aufwendiges Tracing an die physische Anwesenheit eines Analysetools zu koppeln.</p>

<p>Zur asynchronen Zustandsverfolgung registrieren Anwendungen eine Rückruffunktion über <code>ara::log::RegisterConnectionStateHandler</code> unter Verwendung des Funktionsaliasing <code>ConnectionStateHandler = std::function&lt;void(ClientState)&gt;</code> <a class="spec-record-ref" data-req="SWS_LOG_00205" href="../spec/record.html?id=SWS_LOG_00205">[SWS_LOG_00205]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00265" href="../spec/record.html?id=SWS_LOG_00265">[SWS_LOG_00265]</a>. Das Logging-Framework unterstützt hierbei exakt eine aktive Handler-Registrierung: Ein erneuter Aufruf von <code>RegisterConnectionStateHandler</code> überschreibt einen zuvor installierten Callback uneingeschränkt <a class="spec-record-ref" data-req="SWS_LOG_00205" href="../spec/record.html?id=SWS_LOG_00205">[SWS_LOG_00205]</a>.</p>

<h4>Verhalten im Fehlerfall</h4>
<p>Das Modul erzwingt funktionale Sicherheit und Robustheit primär durch statische Typprüfungen zur Übersetzungszeit und strikte Ausnahmegarantien:
<ul>
<li><strong>Übersetzungszeitfehler (ill-formed):</strong> Der Aufruf von <code>Logger::Log(id, args...)</code> ist unzulässig (ill-formed), wenn die übergebenen Argumente nicht exakt mit der im Manifest deklarierten Nachrichtensignatur übereinstimmen <a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>. Ebenso führt die Verwendung von <code>Arg()</code> mit Typen, die weder arithmetisch noch boolesch oder zu <code>StringView</code> bzw. <code>Span&lt;const Byte&gt;</code> konvertierbar sind, zu einem Übersetzungsabbruch <a class="spec-record-ref" data-req="SWS_LOG_00201" href="../spec/record.html?id=SWS_LOG_00201">[SWS_LOG_00201]</a>. Die Funktion <code>WithPrivacy(value)</code> erzwingt zudem, dass der Parametertyp ein ganzzahliger Typ oder eine Aufzählung ist <a class="spec-record-ref" data-req="SWS_LOG_00258" href="../spec/record.html?id=SWS_LOG_00258">[SWS_LOG_00258]</a>.</li>
<li><strong>Konstruktions- und Zuweisungsverbote:</strong> Um unbeabsichtigte Pufferduplizierungen oder Ressourcenkonflikte auszuschließen, sind Kopierkonstruktor und Kopierzuweisungsoperator von <code>LogStream</code> sowie der Move-Zuweisungsoperator explizit gelöscht <a class="spec-record-ref" data-req="SWS_LOG_00174" href="../spec/record.html?id=SWS_LOG_00174">[SWS_LOG_00174]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00175" href="../spec/record.html?id=SWS_LOG_00175">[SWS_LOG_00175]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00177" href="../spec/record.html?id=SWS_LOG_00177">[SWS_LOG_00177]</a>.</li>
<li><strong>Laufzeitintegrität bei Instanziierung:</strong> Schlägt die Auflösung des <code>ara::core::InstanceSpecifier</code> im Maschinen- oder Anwendungsmodell bei <code>CreateLogger(is)</code> fehl oder verweist dieser nicht auf ein zulässiges Modellelement, meldet das System eine <code>InstanceSpecifierMappingIntegrityViolation</code> <a class="spec-record-ref" data-req="SWS_LOG_00256" href="../spec/record.html?id=SWS_LOG_00256">[SWS_LOG_00256]</a>.</li>
<li><strong>Ausfallsichere Fallback-Senken:</strong> Steht zur Laufzeit kein Bereitstellungsmodell oder keine Netzwerkanbindung zum DLT-Dienst bereit, wechselt das Framework automatisch auf die lokale Konsole als Standard-Ausgabesenke, sodass keine Diagnoseinformationen lautlos verloren gehen <a class="spec-record-ref" data-req="SWS_LOG_00021" href="../spec/record.html?id=SWS_LOG_00021">[SWS_LOG_00021]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00263" href="../spec/record.html?id=SWS_LOG_00263">[SWS_LOG_00263]</a>. Bei Ausgabe eines <code>core::ErrorCode</code> auf der Konsole erfolgt die Darstellung über den Domänennamen und den numerischen Fehlerwert <a class="spec-record-ref" data-req="SWS_LOG_00124" href="../spec/record.html?id=SWS_LOG_00124">[SWS_LOG_00124]</a>.</li>
<li><strong>Exception-Sicherheit:</strong> Sämtliche Streaming-Operatoren, Schwellwertabfragen und der Destruktor <code>~LogStream()</code> sind als <code>noexcept</code> deklariert, um sicherzustellen, dass die Protokollierung zu keinem Zeitpunkt unbehandelte Ausnahmen in anwendende Funktionsblöcke propagiert <a class="spec-record-ref" data-req="SWS_LOG_00040" href="../spec/record.html?id=SWS_LOG_00040">[SWS_LOG_00040]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00262" href="../spec/record.html?id=SWS_LOG_00262">[SWS_LOG_00262]</a>; der Zerstörer <code>~Logger()</code> ist hingegen formal nicht als noexcept spezifiziert <a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>.</li>
</ul>
</p>
