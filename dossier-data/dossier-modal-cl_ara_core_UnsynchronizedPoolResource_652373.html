<h4>Context</h4>
<p>
The class <code>ara::core::UnsynchronizedPoolResource</code> implements a memory resource based on memory pools in accordance with <code>std::pmr::unsynchronized_pool_resource</code> from the C++ standard <code>[mem.res.pool]</code> and derives from <code>MemoryResource</code>. It manages memory blocks of different pool sizes and serves allocation requests efficiently without synchronization overhead for multithreading.
</p>
<p>
In the overall system, <code>ara::core::UnsynchronizedPoolResource</code> acts as an intermediary between users (such as containers or allocators), an optional higher-level memory resource (upstream resource), and configuration parameters for pool sizes and limits (<a class="spec-record-ref" data-req="SWS_CORE_00056" href="../spec/record.html?id=SWS_CORE_00056">[SWS_CORE_00056]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00057" href="../spec/record.html?id=SWS_CORE_00057">[SWS_CORE_00057]</a>). If the internally held pools are insufficient or if a request exceeds the maximum block size, the instance delegates to the upstream resource of type <code>MemoryResource</code> (<a class="spec-record-ref" data-req="SWS_CORE_00056" href="../spec/record.html?id=SWS_CORE_00056">[SWS_CORE_00056]</a>).
</p>

<h4>Lifecycle</h4>
<p>
An instance of <code>ara::core::UnsynchronizedPoolResource</code> can be initialized via various constructors:
</p>
<ul>
<li>Default constructor without an explicit upstream resource (<a class="spec-record-ref" data-req="SWS_CORE_00063" href="../spec/record.html?id=SWS_CORE_00063">[SWS_CORE_00063]</a>).</li>
<li>Explicit constructor with a pointer to a user-defined upstream <code>MemoryResource</code> (<a class="spec-record-ref" data-req="SWS_CORE_00064" href="../spec/record.html?id=SWS_CORE_00064">[SWS_CORE_00064]</a>).</li>
<li>Explicit constructor with specific <code>PoolOptions</code> (<a class="spec-record-ref" data-req="SWS_CORE_00068" href="../spec/record.html?id=SWS_CORE_00068">[SWS_CORE_00068]</a>).</li>
<li>Combined <code>noexcept</code> constructor with <code>PoolOptions</code> and upstream resource (<a class="spec-record-ref" data-req="SWS_CORE_00067" href="../spec/record.html?id=SWS_CORE_00067">[SWS_CORE_00067]</a>).</li>
</ul>
<p>
Copy operations are completely prevented: The copy constructor (<a class="spec-record-ref" data-req="SWS_CORE_00046" href="../spec/record.html?id=SWS_CORE_00046">[SWS_CORE_00046]</a>) and the copy assignment operator (<a class="spec-record-ref" data-req="SWS_CORE_00047" href="../spec/record.html?id=SWS_CORE_00047">[SWS_CORE_00047]</a>) are declared as deleted (<code>=delete</code>). In contrast, the class supports move operations by default via a defaulted move constructor (<a class="spec-record-ref" data-req="SWS_CORE_00048" href="../spec/record.html?id=SWS_CORE_00048">[SWS_CORE_00048]</a>) and a defaulted move assignment operator (<a class="spec-record-ref" data-req="SWS_CORE_00049" href="../spec/record.html?id=SWS_CORE_00049">[SWS_CORE_00049]</a>), both of which are defined as <code>noexcept</code>.
</p>
<p>
Via the method <code>release()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00065" href="../spec/record.html?id=SWS_CORE_00065">[SWS_CORE_00065]</a>), all allocated memory can be returned prematurely to the upstream resource without destroying the object itself. Upon destruction via the destructor (<a class="spec-record-ref" data-req="SWS_CORE_00062" href="../spec/record.html?id=SWS_CORE_00062">[SWS_CORE_00062]</a>), the remaining memory is released. An AUTOSAR-specific deviation from the standard is that the destructor is not virtual (<a class="spec-record-ref" data-req="SWS_CORE_00062" href="../spec/record.html?id=SWS_CORE_00062">[SWS_CORE_00062]</a>).
</p>
<p>
Regarding concurrency, it should be noted that allocations (<code>do_allocate</code>) and deallocations (<code>do_deallocate</code>) are explicitly <em>not thread-safe</em> (<a class="spec-record-ref" data-req="SWS_CORE_00058" href="../spec/record.html?id=SWS_CORE_00058">[SWS_CORE_00058]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00059" href="../spec/record.html?id=SWS_CORE_00059">[SWS_CORE_00059]</a>). Concurrent access from multiple threads therefore requires external synchronization or the use of thread-local instances. Queries such as <code>upstream_resource()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00056" href="../spec/record.html?id=SWS_CORE_00056">[SWS_CORE_00056]</a>), <code>options()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00057" href="../spec/record.html?id=SWS_CORE_00057">[SWS_CORE_00057]</a>) or comparisons via <code>do_is_equal()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00060" href="../spec/record.html?id=SWS_CORE_00060">[SWS_CORE_00060]</a>) are specified as thread-safe.
</p>

<h4>Usage Path</h4>
<p>
A typical flow includes the instantiation of the pool resource, repeated memory requests and releases, and the final cleanup:
</p>
<ol>
<li><strong>Initialization:</strong> The application instantiates <code>UnsynchronizedPoolResource</code>, optionally specifying <code>PoolOptions</code> and an upstream resource (<a class="spec-record-ref" data-req="SWS_CORE_00067" href="../spec/record.html?id=SWS_CORE_00067">[SWS_CORE_00067]</a>).</li>
<li><strong>Requesting memory:</strong> Via the interface of base class <code>MemoryResource</code>, <code>do_allocate(bytes, alignment)</code> is called internally (<a class="spec-record-ref" data-req="SWS_CORE_00058" href="../spec/record.html?id=SWS_CORE_00058">[SWS_CORE_00058]</a>). The pool resource serves the request from the matching pool or requests memory from the upstream resource if necessary.</li>
<li><strong>Releasing memory:</strong> Releases take place via <code>do_deallocate(p, bytes, alignment)</code> (<a class="spec-record-ref" data-req="SWS_CORE_00059" href="../spec/record.html?id=SWS_CORE_00059">[SWS_CORE_00059]</a>), making the memory block available again for future allocations in the pool.</li>
<li><strong>Resource release:</strong> Prior to destruction or for cyclic cleanup, <code>release()</code> can be called (<a class="spec-record-ref" data-req="SWS_CORE_00065" href="../spec/record.html?id=SWS_CORE_00065">[SWS_CORE_00065]</a>) to return all memory to the upstream resource.</li>
</ol>

<h4>Error Scenarios</h4>
<p>
In safety-critical and real-time systems, Adaptive AUTOSAR largely avoids C++ exceptions in memory management. <code>ara::core::UnsynchronizedPoolResource</code> therefore deviates in key areas from the behavior of the C++ standard <code>std::pmr::unsynchronized_pool_resource</code>:
</p>
<ul>
<li><strong>Allocation error:</strong> The method <code>do_allocate</code> is declared as <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CORE_00058" href="../spec/record.html?id=SWS_CORE_00058">[SWS_CORE_00058]</a>). If an allocation fails (for example, due to memory exhaustion in the upstream resource), no <code>std::bad_alloc</code> is thrown, but rather a null pointer (<code>nullptr</code>) is returned (<a class="spec-record-ref" data-req="SWS_CORE_00058" href="../spec/record.html?id=SWS_CORE_00058">[SWS_CORE_00058]</a>). Callers must therefore strictly check whether the returned pointer is not equal to <code>nullptr</code>.</li>
<li><strong>Deallocation error:</strong> <code>do_deallocate</code> is also defined as <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CORE_00059" href="../spec/record.html?id=SWS_CORE_00059">[SWS_CORE_00059]</a>). If an error occurs during deallocation, it is silently ignored (<em>silently ignored</em>) according to the specification (<a class="spec-record-ref" data-req="SWS_CORE_00059" href="../spec/record.html?id=SWS_CORE_00059">[SWS_CORE_00059]</a>).</li>
<li><strong>Equality check:</strong> Two instances are considered interchangeable via <code>do_is_equal</code> only if the underlying rules of <code>[mem.res.pool]</code> are met (<a class="spec-record-ref" data-req="SWS_CORE_00060" href="../spec/record.html?id=SWS_CORE_00060">[SWS_CORE_00060]</a>); typically, memory blocks allocated by one instance must not be deallocated on an unequal instance.</li>
</ul>
