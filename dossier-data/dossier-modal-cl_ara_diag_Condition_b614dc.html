<h4>Context</h4>
<p>The class <code>ara::diag::Condition</code> provides the representation of a modeled <code>DiagnosticConditionInterface</code> on the AUTOSAR Adaptive Platform <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. In vehicle diagnostic systems according to ISO 14229-1, certain diagnostic functionalities may only be executed if the overall vehicle or subsystems are in a defined state—for example, when the vehicle is stationary (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=141">AUTOSAR_AP_SWS_Diagnostics p. 141 §7.3.2.5.5 “Condition checks”</a>). The diagnostic server performs corresponding checks prior to processing diagnostic requests <a class="spec-record-ref" data-req="SWS_DM_00111" href="../spec/record.html?id=SWS_DM_00111">[SWS_DM_00111]</a>.</p>
<p>Adaptive Applications use <code>Condition</code> as an interface to report or read out the status of relevant environmental or system conditions to or from Diagnostic Management (DM). In the model, the associated port prototype is assigned either via a <code>DiagnosticEnableConditionPortMapping</code> for general enable conditions or via a <code>DiagnosticClearConditionPortMapping</code> for conditions enabling the clearing of diagnostic data <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. The main interaction partners are the state-monitoring application, the local <code>Condition</code> object, and the central diagnostic server of the DM.</p>

<h4>Lifecycle</h4>
<p>The instantiation of <code>Condition</code> takes place explicitly by passing an <code>ara::core::InstanceSpecifier</code> that references a port prototype of the <code>DiagnosticConditionInterface</code> <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>. The constructor is declared as <code>noexcept</code>, guarantees exception safety (exception safe), and is thread-safe <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>.</p>
<p>With regard to ownership, <code>Condition</code> is designed as an instance uniquely bound to the port: copy constructor, move constructor, and all assignment operators are explicitly deleted (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_DM_01625" href="../spec/record.html?id=SWS_DM_01625">[SWS_DM_01625]</a>, <a class="spec-record-ref" data-req="SWS_DM_01626" href="../spec/record.html?id=SWS_DM_01626">[SWS_DM_01626]</a>, <a class="spec-record-ref" data-req="SWS_DM_01623" href="../spec/record.html?id=SWS_DM_01623">[SWS_DM_01623]</a>, <a class="spec-record-ref" data-req="SWS_DM_01624" href="../spec/record.html?id=SWS_DM_01624">[SWS_DM_01624]</a>. An instance therefore remains fixed at its original memory address and can neither be moved nor copied.</p>
<p>During operation, the state methods <code>SetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a> and <code>GetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a> as well as the destructor <code>~Condition()</code> <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a> are specified as not thread-safe. Concurrent calls to the same instance across multiple threads must therefore be synchronized by the application. Upon destruction of the instance via the destructor, the binding of the <code>InstanceSpecifier</code> is released in the process context <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a>.</p>

<h4>Usage Path</h4>
<p>The regular sequence comprises creation at component startup, setting the state upon status changes, and optional status querying:</p>
<ul>
<li><strong>Initialization:</strong> The application creates the instance of <code>Condition</code> by specifying the matching <code>InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>.</li>
<li><strong>Set state:</strong> If the application detects a change in the relevant condition (for example, standstill reached or exited), it updates the status via <code>SetCondition(condition)</code> <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a>. The call returns a <code>ara::core::Result&lt;void&gt;</code>.</li>
<li><strong>Query state:</strong> If required, the current status can be queried via <code>GetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a>. Since the return takes place via a <code>ara::core::Future&lt;ConditionType&gt;</code>, the status check is likely synchronized asynchronously with Diagnostic Management internally.</li>
<li><strong>Termination:</strong> Prior to the termination of the application or the port, the object is destroyed via the destructor <a class="spec-record-ref" data-req="SWS_DM_00713" href="../spec/record.html?id=SWS_DM_00713">[SWS_DM_00713]</a>.</li>
</ul>

<h4>Error Scenarios</h4>
<p>Error patterns are divided into static configuration violations during instantiation and dynamic runtime errors:</p>
<ul>
<li><strong>Modeling and instantiation errors:</strong> If the resolution of the <code>InstanceSpecifier</code> fails, the framework reports defined violations <a class="spec-record-ref" data-req="SWS_DM_00712" href="../spec/record.html?id=SWS_DM_00712">[SWS_DM_00712]</a>:
  <ul>
  <li><code>InstanceSpecifierMappingIntegrityViolation</code>: The identifier cannot be resolved in the model of the executable or does not reference a port element.</li>
  <li><code>PortInterfaceMappingViolation</code>: Although the port prototype is typed as <code>DiagnosticConditionInterface</code>, it has neither a <code>DiagnosticEnableConditionPortMapping</code> nor a <code>DiagnosticClearConditionPortMapping</code>.</li>
  <li><code>ProcessMappingViolation</code>: In the model, no associated process exists for the current runtime process.</li>
  <li><code>InstanceSpecifierAlreadyInUseViolation</code>: The identifier is already used by another instance in the same process.</li>
  </ul>
</li>
<li><strong>Failure of diagnostic functions:</strong> In the event of an error, calling <code>GetCondition()</code> returns <code>DiagErrc::kServiceNotAvailable</code> <a class="spec-record-ref" data-req="SWS_DM_00714" href="../spec/record.html?id=SWS_DM_00714">[SWS_DM_00714]</a> if essential background services of Diagnostic Management are unreachable. No standardized error codes are specified for <code>SetCondition()</code> <a class="spec-record-ref" data-req="SWS_DM_00715" href="../spec/record.html?id=SWS_DM_00715">[SWS_DM_00715]</a>.</li>
<li><strong>Impact on UDS services:</strong> If a condition is not met or if the condition formula evaluates to <code>FALSE</code>, the Diagnostic Server does not execute the requested service and sends the configured NRC code <a class="spec-record-ref" data-req="SWS_DM_00111" href="../spec/record.html?id=SWS_DM_00111">[SWS_DM_00111]</a>, <a class="spec-record-ref" data-req="SWS_DM_00289" href="../spec/record.html?id=SWS_DM_00289">[SWS_DM_00289]</a>.</li>
</ul>
