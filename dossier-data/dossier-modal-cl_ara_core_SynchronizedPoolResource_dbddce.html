<h4>Context</h4>
<p>The class <code>ara::core::SynchronizedPoolResource</code> acts as a thread-safe polymorphic memory resource in the AUTOSAR Adaptive Platform. It is based on the specification pattern of <code>std::pmr::synchronized_pool_resource</code> from <code>[mem.res.pool]</code> and derives from the base interface <code>ara::core::MemoryResource</code>. Its primary task is to serve dynamic memory requests from predefined pools of memory blocks efficiently and in a synchronized manner in order to minimize fragmentation and allocation overhead in concurrent software components.</p>
<p>Typically, three parties are involved in the interaction: firstly, multiple requesting threads or containers that request memory via polymorphic allocators; secondly, the instance of <code>SynchronizedPoolResource</code> itself, which serializes access to the internal pools in a thread-safe manner; and finally, a higher-level memory resource (upstream resource) from which the pool instance requests larger memory chunks when needed (<a class="spec-record-ref" data-req="SWS_CORE_00038" href="../spec/record.html?id=SWS_CORE_00038">[SWS_CORE_00038]</a>).</p>

<h4>Lifecycle</h4>
<p>The lifecycle of a <code>SynchronizedPoolResource</code> begins with its instantiation via one of four constructors. Configuration can be performed via options (<code>PoolOptions</code>) and by specifying a higher-level memory resource (<code>MemoryResource*</code>):</p>
<ul>
<li>The default constructor <a class="spec-record-ref" data-req="SWS_CORE_00031" href="../spec/record.html?id=SWS_CORE_00031">[SWS_CORE_00031]</a> creates an instance with default parameters; it is classified as thread-safe, but formally as not exception-safe (<code>not exception safe</code>).</li>
<li>The constructor with explicit passing of an upstream resource <a class="spec-record-ref" data-req="SWS_CORE_00032" href="../spec/record.html?id=SWS_CORE_00032">[SWS_CORE_00032]</a> allows linking to a specific base memory manager.</li>
<li>Allocation limits and pool sizes can be adjusted by passing <code>PoolOptions</code> <a class="spec-record-ref" data-req="SWS_CORE_00033" href="../spec/record.html?id=SWS_CORE_00033">[SWS_CORE_00033]</a>.</li>
<li>The fully featured constructor, which accepts both <code>PoolOptions</code> and an upstream pointer <a class="spec-record-ref" data-req="SWS_CORE_00030" href="../spec/record.html?id=SWS_CORE_00030">[SWS_CORE_00030]</a>, is declared as <code>noexcept</code> and is completely exception-safe.</li>
</ul>
<p>Interpretation: If no upstream pointer is passed to the constructor (<a class="spec-record-ref" data-req="SWS_CORE_00031" href="../spec/record.html?id=SWS_CORE_00031">[SWS_CORE_00031]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00033" href="../spec/record.html?id=SWS_CORE_00033">[SWS_CORE_00033]</a>), the instance presumably falls back internally to the platform's default polymorphic memory resource.</p>
<p>Regarding ownership and copy semantics, the specification prohibits duplicating pool resources: Both the copy constructor <a class="spec-record-ref" data-req="SWS_CORE_00034" href="../spec/record.html?id=SWS_CORE_00034">[SWS_CORE_00034]</a> and the copy assignment operator <a class="spec-record-ref" data-req="SWS_CORE_00036" href="../spec/record.html?id=SWS_CORE_00036">[SWS_CORE_00036]</a> are deleted (<code>=delete</code>). A significant AUTOSAR-specific extension compared to the ISO/IEC 14882 standard is move semantics: Both the move constructor <a class="spec-record-ref" data-req="SWS_CORE_00043" href="../spec/record.html?id=SWS_CORE_00043">[SWS_CORE_00043]</a> and the move assignment operator <a class="spec-record-ref" data-req="SWS_CORE_00044" href="../spec/record.html?id=SWS_CORE_00044">[SWS_CORE_00044]</a> are provided as <code>noexcept = default</code> and are exception-safe.</p>
<p>During operation, all allocated memory can be returned to the upstream resource via the call to <code>release()</code> <a class="spec-record-ref" data-req="SWS_CORE_00037" href="../spec/record.html?id=SWS_CORE_00037">[SWS_CORE_00037]</a> without destroying the resource instance. Upon destruction via the destructor <code>~SynchronizedPoolResource()</code> <a class="spec-record-ref" data-req="SWS_CORE_00035" href="../spec/record.html?id=SWS_CORE_00035">[SWS_CORE_00035]</a>, which is declared as <code>noexcept override</code>, AUTOSAR exhibits a deviation from the C++ standard: The destructor function is not declared virtual.</p>

<h4>Usage Path</h4>
<p>In a typical usage scenario, the resource instance is created centrally and passed to polymorphic containers or memory requesters. Prior to allocation, properties such as the configured options can be inspected via <code>options()</code> <a class="spec-record-ref" data-req="SWS_CORE_00039" href="../spec/record.html?id=SWS_CORE_00039">[SWS_CORE_00039]</a> or the upstream resource via <code>upstream_resource()</code> <a class="spec-record-ref" data-req="SWS_CORE_00038" href="../spec/record.html?id=SWS_CORE_00038">[SWS_CORE_00038]</a>. In addition, <code>do_is_equal()</code> <a class="spec-record-ref" data-req="SWS_CORE_00042" href="../spec/record.html?id=SWS_CORE_00042">[SWS_CORE_00042]</a> allows checking for equality with another <code>MemoryResource</code>.</p>
<p>Memory requests are processed in a thread-safe manner via the protected interface <code>do_allocate()</code> <a class="spec-record-ref" data-req="SWS_CORE_00061" href="../spec/record.html?id=SWS_CORE_00061">[SWS_CORE_00061]</a>. If the internal pool for the requested size is exhausted, the instance requests additional memory block buffers from the upstream resource. Individual blocks are subsequently released via <code>do_deallocate()</code> <a class="spec-record-ref" data-req="SWS_CORE_00041" href="../spec/record.html?id=SWS_CORE_00041">[SWS_CORE_00041]</a>. At the end of a processing phase or prior to shutdown, <code>release()</code> <a class="spec-record-ref" data-req="SWS_CORE_00037" href="../spec/record.html?id=SWS_CORE_00037">[SWS_CORE_00037]</a> enables a complete release of all retained chunks to the upstream.</p>

<h4>Error Scenarios</h4>
<p>AUTOSAR defines a strict behavior without C++ exceptions (no-throw guarantee) for <code>ara::core::SynchronizedPoolResource</code>, which deviates significantly from <code>std::pmr::synchronized_pool_resource</code>:</p>
<ul>
<li><strong>Allocation errors:</strong> The allocation method <code>do_allocate()</code> is declared as <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CORE_00061" href="../spec/record.html?id=SWS_CORE_00061">[SWS_CORE_00061]</a>). If the memory resource cannot fulfill a request due to a lack of memory, no exception of type <code>std::bad_alloc</code> is thrown; instead, the function mandatorily returns a null pointer (<code>nullptr</code>). Calling components must therefore explicitly validate the return result for <code>nullptr</code>.</li>
<li><strong>Errors during deallocation:</strong> <code>do_deallocate()</code> is also declared with <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CORE_00041" href="../spec/record.html?id=SWS_CORE_00041">[SWS_CORE_00041]</a>). If errors occur when releasing a memory area, they are silently ignored according to the specification (<em>silently ignored</em>).</li>
<li><strong>Construction risks:</strong> While the complete constructor <a class="spec-record-ref" data-req="SWS_CORE_00030" href="../spec/record.html?id=SWS_CORE_00030">[SWS_CORE_00030]</a> is exception-safe and defined as <code>noexcept</code>, the alternative constructors (<a class="spec-record-ref" data-req="SWS_CORE_00031" href="../spec/record.html?id=SWS_CORE_00031">[SWS_CORE_00031]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00032" href="../spec/record.html?id=SWS_CORE_00032">[SWS_CORE_00032]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00033" href="../spec/record.html?id=SWS_CORE_00033">[SWS_CORE_00033]</a>) are marked as not exception-safe, as errors can occur during the initial reservation of internal pool structures.</li>
</ul>
