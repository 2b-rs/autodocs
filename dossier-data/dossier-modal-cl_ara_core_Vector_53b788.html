<h4>Context</h4>
<p>Within the AUTOSAR Adaptive Platform, <code>ara::core::Vector</code> represents a sequential, dynamically resizable storage container for homogeneous data elements. Conceptually, the implementation is modeled on the C++ standard template <code>std::pmr::vector</code> and interfaces directly with the allocator architecture of module <code>core</code>. Memory management is primarily controlled via the template parameter <code>Allocator</code> or the type alias <code>allocator_type</code> <a class="spec-record-ref" data-req="SWS_CORE_01303" href="../spec/record.html?id=SWS_CORE_01303">[SWS_CORE_01303]</a>, whose instance can be queried via <code>get_allocator()</code> <a class="spec-record-ref" data-req="SWS_CORE_01331" href="../spec/record.html?id=SWS_CORE_01331">[SWS_CORE_01331]</a>. In this way, the container interacts directly with application-specific or platform-wide memory resources, which is essential for deterministic allocation strategies in safety-critical automotive systems.</p>
<p>For integration into algorithms and data flows, the class declares standardized type aliases for values, pointers, references, and iterators: the payload data type <code>value_type</code> <a class="spec-record-ref" data-req="SWS_CORE_01302" href="../spec/record.html?id=SWS_CORE_01302">[SWS_CORE_01302]</a>, <code>pointer</code> <a class="spec-record-ref" data-req="SWS_CORE_01304" href="../spec/record.html?id=SWS_CORE_01304">[SWS_CORE_01304]</a>, and <code>const_pointer</code> <a class="spec-record-ref" data-req="SWS_CORE_01305" href="../spec/record.html?id=SWS_CORE_01305">[SWS_CORE_01305]</a>, as well as <code>reference</code> <a class="spec-record-ref" data-req="SWS_CORE_01306" href="../spec/record.html?id=SWS_CORE_01306">[SWS_CORE_01306]</a> and <code>const_reference</code> <a class="spec-record-ref" data-req="SWS_CORE_01307" href="../spec/record.html?id=SWS_CORE_01307">[SWS_CORE_01307]</a>. Access to element ranges is performed via standardized forward and reverse iterators (<a class="spec-record-ref" data-req="SWS_CORE_01310" href="../spec/record.html?id=SWS_CORE_01310">[SWS_CORE_01310]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01311" href="../spec/record.html?id=SWS_CORE_01311">[SWS_CORE_01311]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01312" href="../spec/record.html?id=SWS_CORE_01312">[SWS_CORE_01312]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01313" href="../spec/record.html?id=SWS_CORE_01313">[SWS_CORE_01313]</a>), while distances and sizes are captured via <code>difference_type</code> <a class="spec-record-ref" data-req="SWS_CORE_01309" href="../spec/record.html?id=SWS_CORE_01309">[SWS_CORE_01309]</a> and <code>size_type</code> <a class="spec-record-ref" data-req="SWS_CORE_01308" href="../spec/record.html?id=SWS_CORE_01308">[SWS_CORE_01308]</a>.</p>

<h4>Lifecycle</h4>
<p>The lifecycle of an instance of <code>ara::core::Vector</code> begins with buffer initialization via one of the constructors. In addition to default construction <a class="spec-record-ref" data-req="SWS_CORE_01318" href="../spec/record.html?id=SWS_CORE_01318">[SWS_CORE_01318]</a>, the container can be created specifically with an allocator instance <a class="spec-record-ref" data-req="SWS_CORE_01319" href="../spec/record.html?id=SWS_CORE_01319">[SWS_CORE_01319]</a>. Further initialization paths allow specifying an initial number of elements <a class="spec-record-ref" data-req="SWS_CORE_01320" href="../spec/record.html?id=SWS_CORE_01320">[SWS_CORE_01320]</a>, optionally pre-populated with a default value <a class="spec-record-ref" data-req="SWS_CORE_01321" href="../spec/record.html?id=SWS_CORE_01321">[SWS_CORE_01321]</a>, reading in an iterator range <a class="spec-record-ref" data-req="SWS_CORE_01322" href="../spec/record.html?id=SWS_CORE_01322">[SWS_CORE_01322]</a>, or initialization by means of <code>std::initializer_list</code> <a class="spec-record-ref" data-req="SWS_CORE_01325" href="../spec/record.html?id=SWS_CORE_01325">[SWS_CORE_01325]</a>.</p>
<p>Copy, move, and destruction operations exhibit specific ownership and exception conditions:</p>
<ul>
<li><strong>Copying:</strong> The copy constructor <a class="spec-record-ref" data-req="SWS_CORE_01314" href="../spec/record.html?id=SWS_CORE_01314">[SWS_CORE_01314]</a> is specified as <code>default</code>, but deviates from the standard by being conditionally declared as <code>noexcept</code> if <code>std::is_nothrow_copy_constructible&lt;T&gt;::value</code> holds. Correspondingly, the copy assignment <a class="spec-record-ref" data-req="SWS_CORE_01315" href="../spec/record.html?id=SWS_CORE_01315">[SWS_CORE_01315]</a> is conditionally <code>noexcept</code>. In addition, copies can be created by specifying a separate allocator <a class="spec-record-ref" data-req="SWS_CORE_01323" href="../spec/record.html?id=SWS_CORE_01323">[SWS_CORE_01323]</a>.</li>
<li><strong>Moving:</strong> The move constructor <a class="spec-record-ref" data-req="SWS_CORE_01316" href="../spec/record.html?id=SWS_CORE_01316">[SWS_CORE_01316]</a> and the move assignment operator <a class="spec-record-ref" data-req="SWS_CORE_01317" href="../spec/record.html?id=SWS_CORE_01317">[SWS_CORE_01317]</a> transfer the managed buffer efficiently. They are defined as conditionally <code>noexcept</code>, depending on whether the allocator supports buffer propagation during move operations (<code>propagate_on_container_move_assignment</code>) or allocators are always identical (<code>is_always_equal</code>). A move with allocator transfer is also provided for <a class="spec-record-ref" data-req="SWS_CORE_01324" href="../spec/record.html?id=SWS_CORE_01324">[SWS_CORE_01324]</a>.</li>
<li><strong>State swapping:</strong> The method <code>swap()</code> <a class="spec-record-ref" data-req="SWS_CORE_01374" href="../spec/record.html?id=SWS_CORE_01374">[SWS_CORE_01374]</a> swaps the container contents of two instances and is <code>noexcept</code> under the same allocator conditions (propagation or equality).</li>
<li><strong>Destruction:</strong> The destructor <code>~Vector()</code> <a class="spec-record-ref" data-req="SWS_CORE_01326" href="../spec/record.html?id=SWS_CORE_01326">[SWS_CORE_01326]</a> is explicitly specified as <code>noexcept</code>. It destroys all contained elements in an orderly manner and releases the allocated memory area.</li>
</ul>
<p><code>ara::core::Vector</code> owns its memory area exclusively; pointers to the buffer can be retrieved via <code>data()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01360" href="../spec/record.html?id=SWS_CORE_01360">[SWS_CORE_01360]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01361" href="../spec/record.html?id=SWS_CORE_01361">[SWS_CORE_01361]</a>). Regarding concurrency, the container provides no internal synchronization: Concurrent read accesses via const methods are safe, whereas concurrent write accesses require external protection.</p>

<h4>Usage Path</h4>
<p>Typical usage of <code>ara::core::Vector</code> is divided into allocator initialization, capacity reservation, population, and element evaluation:</p>
<ol>
<li><strong>Initialization and allocator assignment:</strong> Instantiation of the container with the designated memory manager (<a class="spec-record-ref" data-req="SWS_CORE_01319" href="../spec/record.html?id=SWS_CORE_01319">[SWS_CORE_01319]</a>).</li>
<li><strong>Pre-reservation:</strong> By calling <code>reserve()</code> <a class="spec-record-ref" data-req="SWS_CORE_01347" href="../spec/record.html?id=SWS_CORE_01347">[SWS_CORE_01347]</a>, capacity is specifically requested to avoid subsequent dynamic reallocations during insertion. The available buffer size can be verified via <code>capacity()</code> <a class="spec-record-ref" data-req="SWS_CORE_01348" href="../spec/record.html?id=SWS_CORE_01348">[SWS_CORE_01348]</a>.</li>
<li><strong>Element insertion:</strong> Elements are added at the end via <code>push_back()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01363" href="../spec/record.html?id=SWS_CORE_01363">[SWS_CORE_01363]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01364" href="../spec/record.html?id=SWS_CORE_01364">[SWS_CORE_01364]</a>) or through in-place construction via <code>emplace_back()</code> <a class="spec-record-ref" data-req="SWS_CORE_01362" href="../spec/record.html?id=SWS_CORE_01362">[SWS_CORE_01362]</a>. Alternatively, values can be placed at any position with <code>insert()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01367" href="../spec/record.html?id=SWS_CORE_01367">[SWS_CORE_01367]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01368" href="../spec/record.html?id=SWS_CORE_01368">[SWS_CORE_01368]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01369" href="../spec/record.html?id=SWS_CORE_01369">[SWS_CORE_01369]</a>) or <code>emplace()</code> <a class="spec-record-ref" data-req="SWS_CORE_01366" href="../spec/record.html?id=SWS_CORE_01366">[SWS_CORE_01366]</a>.</li>
<li><strong>Inspection and access:</strong> After checking the fill level via <code>empty()</code> <a class="spec-record-ref" data-req="SWS_CORE_01344" href="../spec/record.html?id=SWS_CORE_01344">[SWS_CORE_01344]</a> and <code>size()</code> <a class="spec-record-ref" data-req="SWS_CORE_01345" href="../spec/record.html?id=SWS_CORE_01345">[SWS_CORE_01345]</a>, elements are accessed via <code>operator[]</code> (<a class="spec-record-ref" data-req="SWS_CORE_01352" href="../spec/record.html?id=SWS_CORE_01352">[SWS_CORE_01352]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01353" href="../spec/record.html?id=SWS_CORE_01353">[SWS_CORE_01353]</a>), bounds-checked via <code>at()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01354" href="../spec/record.html?id=SWS_CORE_01354">[SWS_CORE_01354]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01355" href="../spec/record.html?id=SWS_CORE_01355">[SWS_CORE_01355]</a>), or at the buffer boundaries via <code>front()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01356" href="../spec/record.html?id=SWS_CORE_01356">[SWS_CORE_01356]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01357" href="../spec/record.html?id=SWS_CORE_01357">[SWS_CORE_01357]</a>) and <code>back()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01358" href="../spec/record.html?id=SWS_CORE_01358">[SWS_CORE_01358]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01359" href="../spec/record.html?id=SWS_CORE_01359">[SWS_CORE_01359]</a>). Sequential processing can be performed via iterators from <code>begin()</code> <a class="spec-record-ref" data-req="SWS_CORE_01332" href="../spec/record.html?id=SWS_CORE_01332">[SWS_CORE_01332]</a> to <code>end()</code> <a class="spec-record-ref" data-req="SWS_CORE_01334" href="../spec/record.html?id=SWS_CORE_01334">[SWS_CORE_01334]</a>.</li>
<li><strong>Cleanup:</strong> Individual elements can be erased via <code>pop_back()</code> <a class="spec-record-ref" data-req="SWS_CORE_01365" href="../spec/record.html?id=SWS_CORE_01365">[SWS_CORE_01365]</a> or <code>erase()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01372" href="../spec/record.html?id=SWS_CORE_01372">[SWS_CORE_01372]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01373" href="../spec/record.html?id=SWS_CORE_01373">[SWS_CORE_01373]</a>). With <code>clear()</code> <a class="spec-record-ref" data-req="SWS_CORE_01375" href="../spec/record.html?id=SWS_CORE_01375">[SWS_CORE_01375]</a>, the container is completely emptied; unused memory can be returned to the allocator via <code>shrink_to_fit()</code> <a class="spec-record-ref" data-req="SWS_CORE_01349" href="../spec/record.html?id=SWS_CORE_01349">[SWS_CORE_01349]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>In contrast to standard library behavior, <code>ara::core::Vector</code> relies on AUTOSAR-specific violations instead of classic standard exceptions to signal erroneous calls:</p>
<ul>
<li><strong>Index out of bounds:</strong> The access method <code>at()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01354" href="../spec/record.html?id=SWS_CORE_01354">[SWS_CORE_01354]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01355" href="../spec/record.html?id=SWS_CORE_01355">[SWS_CORE_01355]</a>) validates the passed index. If <code>n &gt;= size()</code> holds, a <code>IsoStdOutOfRangeViolation</code> is triggered (instead of <code>std::out_of_range</code>).</li>
<li><strong>Exceeding capacity limits:</strong> For calls to <code>reserve()</code> <a class="spec-record-ref" data-req="SWS_CORE_01347" href="../spec/record.html?id=SWS_CORE_01347">[SWS_CORE_01347]</a> and <code>resize()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01350" href="../spec/record.html?id=SWS_CORE_01350">[SWS_CORE_01350]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01351" href="../spec/record.html?id=SWS_CORE_01351">[SWS_CORE_01351]</a>), the request is checked against <code>max_size()</code> <a class="spec-record-ref" data-req="SWS_CORE_01346" href="../spec/record.html?id=SWS_CORE_01346">[SWS_CORE_01346]</a>. If this maximum limit is exceeded, a <code>IsoStdLengthErrorViolation</code> is triggered (instead of <code>std::length_error</code>).</li>
<li><strong>Unchecked direct access:</strong> The subscript operator <code>operator[]</code> (<a class="spec-record-ref" data-req="SWS_CORE_01352" href="../spec/record.html?id=SWS_CORE_01352">[SWS_CORE_01352]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01353" href="../spec/record.html?id=SWS_CORE_01353">[SWS_CORE_01353]</a>) and the boundary methods <code>front()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01356" href="../spec/record.html?id=SWS_CORE_01356">[SWS_CORE_01356]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01357" href="../spec/record.html?id=SWS_CORE_01357">[SWS_CORE_01357]</a>) and <code>back()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01358" href="../spec/record.html?id=SWS_CORE_01358">[SWS_CORE_01358]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01359" href="../spec/record.html?id=SWS_CORE_01359">[SWS_CORE_01359]</a>) perform no runtime checks. Calling these methods on an empty container or with out-of-range indices violates their preconditions and leads to undefined behavior.</li>
<li><strong>Exception safety of modifying operations:</strong> Numerous mutating operations such as <code>assign()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01328" href="../spec/record.html?id=SWS_CORE_01328">[SWS_CORE_01328]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01329" href="../spec/record.html?id=SWS_CORE_01329">[SWS_CORE_01329]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01330" href="../spec/record.html?id=SWS_CORE_01330">[SWS_CORE_01330]</a>), <code>insert()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01367" href="../spec/record.html?id=SWS_CORE_01367">[SWS_CORE_01367]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01368" href="../spec/record.html?id=SWS_CORE_01368">[SWS_CORE_01368]</a>), or <code>erase()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01372" href="../spec/record.html?id=SWS_CORE_01372">[SWS_CORE_01372]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01373" href="../spec/record.html?id=SWS_CORE_01373">[SWS_CORE_01373]</a>) are classified in the specification as <em>not exception safe</em>. Interpretation: If a buffer allocation fails or an element construction fails during size-increasing operations such as <code>push_back()</code> <a class="spec-record-ref" data-req="SWS_CORE_01363" href="../spec/record.html?id=SWS_CORE_01363">[SWS_CORE_01363]</a>, the container might possibly remain in a modified state due to the lack of a full strong exception guarantee.</li>
</ul>
