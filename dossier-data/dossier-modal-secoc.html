<h4>Role of SecOC: Securing I-PDUs Alongside the PDU Router</h4>
<p>SecOC (Secure Onboard Communication) protects I-PDUs against tampering and replay. When transmitting, SecOC appends authentication information to an <em>Authentic I-PDU</em>, consisting of an optionally truncated Freshness Value and an Authenticator. This results in a <em>Secured I-PDU</em>. Upon reception, this information is verified before the Authentic I-PDU is forwarded (<a class="spec-record-ref" data-req="SWS_SecOC_00040" href="../../spec/record.html?id=SWS_SecOC_00040">[SWS_SecOC_00040]</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-191c36f735f7b363.html" data-snip="FIG-191c36f735f7b363">SWS SecOC Fig. 7.2 p. 30</a>). The Authenticator is calculated over a concatenation of three parts: Data Identifier (<code>SecOCDataId</code>), secured part of the Authentic I-PDU, and complete Freshness Value (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_1_1_2_Data_covered_by_Authenticator.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_1_1_2_Data_covered_by_Authenticator">SWS SecOC p. 29</a>).</p>
<p>In the architecture, SecOC is located alongside the PduR. Upper layers such as Com transmit via <code>PduR_&lt;Up&gt;Transmit</code>. The PduR then calls <code>SecOC_[If|Tp]Transmit</code>, and SecOC passes the Secured I-PDU back via the PduR to a bus interface or a transport protocol (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_4_Authentication_of_outgoing_PDUs.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_4_Authentication_of_outgoing_PDUs">SWS SecOC p. 40</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-e944b43de9484e39.html" data-snip="FIG-e944b43de9484e39">SWS SecOC Fig. 1.1 p. 10</a>). MetaData of an Authentic PDU appear unchanged in the Secured PDU, and the same applies vice versa (<a class="spec-record-ref" data-req="SWS_SecOC_00212" href="../../spec/record.html?id=SWS_SecOC_00212">[SWS_SecOC_00212]</a>). No other module may depend on SecOC, so that a system can also be built without SecOC (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_2_Relationship_to_PduR.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_2_Relationship_to_PduR">SWS SecOC p. 39</a>).</p>
<p>SecOC works together with several other modules:</p>
<ul>
<li>Cryptography is provided by the CSM, among others via <code>Csm_MacGenerate</code> and <code>Csm_MacVerify</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00138" href="../../spec/record.html?id=SWS_SecOC_00138">[SWS_SecOC_00138]</a>). For asynchronous CSM jobs, SecOC provides vendor-specific callbacks (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_8_4_9_CSM_callback_interfaces.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_8_4_9_CSM_callback_interfaces">SWS SecOC p. 78</a>).</li>
<li>Freshness Values originate from a Freshness Manager. For <code>SecOCQueryFreshnessValue = RTE</code>, it is connected via port <code>FreshnessManagement</code> (<a class="spec-record-ref" data-req="SWS_SecOC_91001" href="../../spec/record.html?id=SWS_SecOC_91001">[SWS_SecOC_91001]</a>), for <code>CFUNC</code> via C functions (<a class="spec-record-ref" data-req="SWS_SecOC_00231" href="../../spec/record.html?id=SWS_SecOC_00231">[SWS_SecOC_00231]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00247" href="../../spec/record.html?id=SWS_SecOC_00247">[SWS_SecOC_00247]</a>).</li>
<li>SecOC reports errors to the DET (<a class="spec-record-ref" data-req="SWS_SecOC_00101" href="../../spec/record.html?id=SWS_SecOC_00101">[SWS_SecOC_00101]</a>).</li>
<li>Security Events go to the IdsM (<a class="spec-record-ref" data-req="SWS_SecOC_00273" href="../../spec/record.html?id=SWS_SecOC_00273">[SWS_SecOC_00273]</a>).</li>
</ul>

<h4>Module State and Cyclic Main Functions</h4>
<p>SecOC has two states, <code>SECOC_UNINIT</code> and <code>SECOC_INIT</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00162" href="../../spec/record.html?id=SWS_SecOC_00162">[SWS_SecOC_00162]</a>):</p>
<ul>
<li>A successful initialization with <code>SecOC_Init</code> leads to <code>SECOC_INIT</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00106" href="../../spec/record.html?id=SWS_SecOC_00106">[SWS_SecOC_00106]</a>).</li>
<li><code>SecOC_DeInit</code> stops the secured communication, discards all buffered I-PDUs, and sets the module to the uninitialized state (<a class="spec-record-ref" data-req="SWS_SecOC_00161" href="../../spec/record.html?id=SWS_SecOC_00161">[SWS_SecOC_00161]</a>). In doing so, internal global variables are also cleared (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_8_3_2_SecOC_DeInit.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_8_3_2_SecOC_DeInit">SWS SecOC p. 65</a>).</li>
<li>The error <code>SECOC_E_UNINIT</code> is intended for API calls without initialization, and <code>SECOC_E_INIT_FAILED</code> for a failed initialization (<a class="spec-record-ref" data-req="SWS_SecOC_00101" href="../../spec/record.html?id=SWS_SecOC_00101">[SWS_SecOC_00101]</a>).</li>
<li>If the module is not initialized, <code>SecOC_MainFunctionTx</code> returns immediately (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_8_6_2_SecOC_MainFunctionTx.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_8_6_2_SecOC_MainFunctionTx">SWS SecOC p. 84</a>).</li>
</ul>
<p>The actual cryptographic processing does not run in the call context of the transmit or receive functions, but cyclically. For each configured instance of <code>SecOCMainFunctionTx</code> or <code>SecOCMainFunctionRx</code>, there is a dedicated <code>SecOC_MainFunctionTx_&lt;shortName&gt;</code> or <code>SecOC_MainFunctionRx_&lt;shortName&gt;</code>, respectively (<a class="spec-record-ref" data-req="SWS_SecOC_00176" href="../../spec/record.html?id=SWS_SecOC_00176">[SWS_SecOC_00176]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00171" href="../../spec/record.html?id=SWS_SecOC_00171">[SWS_SecOC_00171]</a>). The respective period is set via <code>SecOCMainFunctionPeriodTx</code> or <code>SecOCMainFunctionPeriodRx</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_10_1_5_SecOCMainFunctionTx.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_10_1_5_SecOCMainFunctionTx">SWS SecOC p. 130</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_10_1_4_SecOCMainFunctionRx.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_10_1_4_SecOCMainFunctionRx">SWS SecOC p. 129</a>). A Tx PDU is processed in the main function referenced via <code>SecOCTxPduMainFunctionRef</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00276" href="../../spec/record.html?id=SWS_SecOC_00276">[SWS_SecOC_00276]</a>).</p>

<h4>Transmit Path: From Authentic to Secured I-PDU</h4>
<p>A transmission process begins with <code>SecOC_IfTransmit</code> or <code>SecOC_TpTransmit</code>, respectively (<a class="spec-record-ref" data-req="SWS_SecOC_00112" href="../../spec/record.html?id=SWS_SecOC_00112">[SWS_SecOC_00112]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91008" href="../../spec/record.html?id=SWS_SecOC_91008">[SWS_SecOC_91008]</a>). SecOC copies the complete Authentic I-PDU into its own memory before the transmission of the Secured I-PDU begins (<a class="spec-record-ref" data-req="SWS_SecOC_00252" href="../../spec/record.html?id=SWS_SecOC_00252">[SWS_SecOC_00252]</a>). The call then returns.</p>
<p>In the next call of <code>SecOC_MainFunctionTx</code>, all new Authentic I-PDUs are authenticated. Each completed Secured I-PDU is transmitted immediately via the PduR (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_8_6_2_SecOC_MainFunctionTx.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_8_6_2_SecOC_MainFunctionTx">SWS SecOC p. 84</a>). The generation comprises six steps, from preparing the Secured I-PDU to incrementing the Freshness Counter and transmitting (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_1_2_Authentication_of_I_PDUs.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_1_2_Authentication_of_I_PDUs">SWS SecOC p. 33</a>).</p>
<p>In mode <code>CFUNC</code>, the Freshness Value is provided by one of two functions, depending on <code>SecOCProvideTxTruncatedFreshnessValue</code>:</p>
<ul>
<li><code>SecOC_GetTxFreshnessTruncData</code>, which additionally provides the truncated value (<a class="spec-record-ref" data-req="SWS_SecOC_00230" href="../../spec/record.html?id=SWS_SecOC_00230">[SWS_SecOC_00230]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91003" href="../../spec/record.html?id=SWS_SecOC_91003">[SWS_SecOC_91003]</a>), or</li>
<li><code>SecOC_GetTxFreshness</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00231" href="../../spec/record.html?id=SWS_SecOC_00231">[SWS_SecOC_00231]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91004" href="../../spec/record.html?id=SWS_SecOC_91004">[SWS_SecOC_91004]</a>).</li>
</ul>
<p>SecOC reports to the Freshness Manager via <code>SecOC_SPduTxConfirmation</code> or <code>FreshnessManagement_SPduTxConfirmation</code> that the transmission of a Secured I-PDU has been initiated (<a class="spec-record-ref" data-req="SWS_SecOC_00232" href="../../spec/record.html?id=SWS_SecOC_00232">[SWS_SecOC_00232]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00233" href="../../spec/record.html?id=SWS_SecOC_00233">[SWS_SecOC_00233]</a>).</p>
<p>After transmission, SecOC assumes the role of an upper module toward the lower layer (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_4_Authentication_of_outgoing_PDUs.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_4_Authentication_of_outgoing_PDUs">SWS SecOC p. 40</a>):</p>
<ul>
<li><strong>Triggered transmission</strong> (e.g. FrIf): The lower layer fetches the data with <code>SecOC_TriggerTransmit</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00127" href="../../spec/record.html?id=SWS_SecOC_00127">[SWS_SecOC_00127]</a>). This requires a prior call of <code>SecOC_IfTransmit</code>; the AlwaysTransmit operating mode is not to be used (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_4_2_Authentication_during_triggered_transmission.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_4_2_Authentication_during_triggered_transmission">SWS SecOC p. 44</a>).</li>
<li><strong>Transport protocols</strong>: The data is retrieved with <code>SecOC_CopyTxData</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00129" href="../../spec/record.html?id=SWS_SecOC_00129">[SWS_SecOC_00129]</a>).</li>
<li><strong>Confirmation</strong>: SecOC forwards the result from <code>SecOC_[If|Tp]TxConfirmation</code> upward via <code>PduR_SecOC[If|Tp]TxConfirmation</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00063" href="../../spec/record.html?id=SWS_SecOC_00063">[SWS_SecOC_00063]</a>).</li>
</ul>
<p>If <code>SecOCPduType = SECOC_TPPDU</code> is configured, <code>SecOC_TpTransmit</code> triggers the transmission process. SecOC then fetches the Authentic I-PDU segment by segment from the upper layer via <code>PduR_SecOCTpCopyTxData</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00253" href="../../spec/record.html?id=SWS_SecOC_00253">[SWS_SecOC_00253]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00254" href="../../spec/record.html?id=SWS_SecOC_00254">[SWS_SecOC_00254]</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-b6cfb93c3bb2b48a.html" data-snip="FIG-b6cfb93c3bb2b48a">SWS SecOC Fig. 9.4 p. 109</a>).</p>

<h4>Receive Path: Buffer, Verify, Forward</h4>
<p>Upon reception, the same sequence always applies to SecOC: first transfer the complete Secured I-PDU into its own memory, then verify in the next <code>SecOC_MainFunctionRx</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_5_Verification_of_incoming_PDUs.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_5_Verification_of_incoming_PDUs">SWS SecOC p. 50</a>). The Authentic I-PDU is only copied once the Secured I-PDU is completely available (<a class="spec-record-ref" data-req="SWS_SecOC_00255" href="../../spec/record.html?id=SWS_SecOC_00255">[SWS_SecOC_00255]</a>).</p>
<ul>
<li><strong>Bus interfaces</strong>: Reception is reported via <code>SecOC_RxIndication</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00124" href="../../spec/record.html?id=SWS_SecOC_00124">[SWS_SecOC_00124]</a>).</li>
<li><strong>Transport protocols</strong>: Reception takes place via <code>SecOC_StartOfReception</code>, <code>SecOC_CopyRxData</code>, and <code>SecOC_TpRxIndication</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00130" href="../../spec/record.html?id=SWS_SecOC_00130">[SWS_SecOC_00130]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00128" href="../../spec/record.html?id=SWS_SecOC_00128">[SWS_SecOC_00128]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00125" href="../../spec/record.html?id=SWS_SecOC_00125">[SWS_SecOC_00125]</a>). For <code>SECOC_TPPDU</code>, SecOC forwards the start of reception to the upper layer via <code>PduR_SecOCTpStartOfReception</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_5_2_Verification_during_transport_protocol_reception.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_5_2_Verification_during_transport_protocol_reception">SWS SecOC p. 54</a>).</li>
</ul>
<p>The verification follows six fixed steps (<a class="spec-record-ref" data-req="SWS_SecOC_00040" href="../../spec/record.html?id=SWS_SecOC_00040">[SWS_SecOC_00040]</a>):</p>
<ol>
<li>Decompose Authentic I-PDU, Freshness Value, and Authenticator.</li>
<li>Obtain the Freshness Value from the Freshness Manager.</li>
<li>Construct the data to be authenticated.</li>
<li>Verify the Authenticator.</li>
<li>Confirm the result to the DEM Freshness Manager.</li>
<li>Forward the Authentic I-PDU to the upper layer.</li>
</ol>
<p>Which function provides the Freshness Value depends on <code>SecOCUseAuthDataFreshness</code>:</p>
<ul>
<li>For <code>FALSE</code>, SecOC calls <code>SecOC_GetRxFreshness</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00247" href="../../spec/record.html?id=SWS_SecOC_00247">[SWS_SecOC_00247]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91007" href="../../spec/record.html?id=SWS_SecOC_91007">[SWS_SecOC_91007]</a>).</li>
<li>For <code>TRUE</code>, SecOC calls <code>SecOC_GetRxFreshnessAuthData</code>, passing a portion of the Authentic I-PDU (<a class="spec-record-ref" data-req="SWS_SecOC_00246" href="../../spec/record.html?id=SWS_SecOC_00246">[SWS_SecOC_00246]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91006" href="../../spec/record.html?id=SWS_SecOC_91006">[SWS_SecOC_91006]</a>).</li>
<li>In RTE mode, the same rules apply to the operations of <code>FreshnessManagement</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00244" href="../../spec/record.html?id=SWS_SecOC_00244">[SWS_SecOC_00244]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00245" href="../../spec/record.html?id=SWS_SecOC_00245">[SWS_SecOC_00245]</a>).</li>
</ul>
<p>If the verification is successful, the result is <code>SECOC_VERIFICATIONSUCCESS</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00242" href="../../spec/record.html?id=SWS_SecOC_00242">[SWS_SecOC_00242]</a>), and the Authentic I-PDU goes to the upper layer (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_5_1_3_1_Successful_verification_of_I_PDUs.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_5_1_3_1_Successful_verification_of_I_PDUs">PRS SecOC p. 18</a>).</p>
<p>For gateways, SecOC supports re-authenticating paths, i.e. verification on the source bus and re-authentication for the target bus. \"Gatewaying-on-the-fly\" is not supported in this process (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_6_Gateway_functionality.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_6_Gateway_functionality">SWS SecOC p. 57</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-ccf7aba942c75947.html" data-snip="FIG-ccf7aba942c75947">SWS SecOC Fig. 9.9 p. 102</a>).</p>

<h4>Application Interfaces: Verification Status, Override, Default Pattern</h4>
<p><strong>Verification status.</strong> <code>SecOC_VerificationStatusType</code> summarizes the result of each verification: the Freshness Value ID and a result of type <code>SecOC_VerificationResultType</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00160" href="../../spec/record.html?id=SWS_SecOC_00160">[SWS_SecOC_00160]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00149" href="../../spec/record.html?id=SWS_SecOC_00149">[SWS_SecOC_00149]</a>). Where the status is reported is governed by the propagation mode:</p>
<ul>
<li>With <code>BOTH</code> or <code>FAILURE_ONLY</code>, it goes to the application via <code>VerificationStatusIndication</code>; with <code>NONE</code>, reporting is omitted (<a class="spec-record-ref" data-req="SWS_SecOC_00271" href="../../spec/record.html?id=SWS_SecOC_00271">[SWS_SecOC_00271]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91016" href="../../spec/record.html?id=SWS_SecOC_91016">[SWS_SecOC_91016]</a>).</li>
<li>With <code>SecOCPropagateOnlyFinalVerificationStatus = TRUE</code>, only the final status is reported; otherwise, each failed intermediate attempt is also reported (<a class="spec-record-ref" data-req="SWS_SecOC_00272" href="../../spec/record.html?id=SWS_SecOC_00272">[SWS_SecOC_00272]</a>).</li>
<li>The Freshness Manager receives the result via <code>SecOC_VerificationStatusCallout</code>, for example to synchronize counters (<a class="spec-record-ref" data-req="SWS_SecOC_00119" href="../../spec/record.html?id=SWS_SecOC_00119">[SWS_SecOC_00119]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00243" href="../../spec/record.html?id=SWS_SecOC_00243">[SWS_SecOC_00243]</a>).</li>
<li><code>SecOC_VerifyStatus</code> informs the application about the verification result (<a class="spec-record-ref" data-req="SWS_SecOC_91014" href="../../spec/record.html?id=SWS_SecOC_91014">[SWS_SecOC_91014]</a>).</li>
</ul>
<p><strong>Override.</strong> With <code>SecOC_VerifyStatusOverride</code>, the application can force the behavior for a Freshness Value ID or Data ID (<a class="spec-record-ref" data-req="SWS_SecOC_00122" href="../../spec/record.html?id=SWS_SecOC_00122">[SWS_SecOC_00122]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00142" href="../../spec/record.html?id=SWS_SecOC_00142">[SWS_SecOC_00142]</a>). The R20-11 values of <code>SecOC_OverrideStatusType</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00991" href="../../spec/record.html?id=SWS_SecOC_00991">[SWS_SecOC_00991]</a>) are:</p>
<ul>
<li><code>SECOC_OVERRIDE_DROP_UNTIL_NOTICE</code> and <code>SECOC_OVERRIDE_DROP_UNTIL_LIMIT</code>: no CSM verification, the I-PDU is discarded, the result is <code>SECOC_NO_VERIFICATION</code>.</li>
<li><code>SECOC_OVERRIDE_PASS_UNTIL_NOTICE</code>: The verification takes place, but the I-PDU is forwarded regardless of the result.</li>
<li><code>SECOC_OVERRIDE_CANCEL</code>: terminates an active override.</li>
</ul>
<p>The passage from R23-11 additionally mentions <code>SECOC_OVERRIDE_SKIP_UNTIL_LIMIT</code> and <code>SECOC_OVERRIDE_PASS_UNTIL_LIMIT</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_8_8_5_4_SecOC_OverrideStatusType.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_8_8_5_4_SecOC_OverrideStatusType">SWS SecOC p. 102</a>). The R20-11 requirement text is truncated at this point in the payload.</p>
<p><strong>Default pattern.</strong> <code>SecOC_SendDefaultAuthenticationInformation</code> enables or disables transmission with <code>SecOCDefaultAuthenticationInformationPattern</code> per Freshness Value ID (<a class="spec-record-ref" data-req="SWS_SecOC_91013" href="../../spec/record.html?id=SWS_SecOC_91013">[SWS_SecOC_91013]</a>). The interface exists only if this pattern is configured (<a class="spec-record-ref" data-req="SWS_SecOC_00002" href="../../spec/record.html?id=SWS_SecOC_00002">[SWS_SecOC_00002]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91020" href="../../spec/record.html?id=SWS_SecOC_91020">[SWS_SecOC_91020]</a>).</p>

<h4>Configuration, PDU Structure, and Separate Cryptographic I-PDUs</h4>
<p><strong>Configuration containers.</strong> Each Tx PDU to be secured is configured in <code>SecOCTxPduProcessing</code>, and each Rx PDU to be verified in <code>SecOCRxPduProcessing</code>. This includes the Data ID, Freshness Value ID, lengths, and retry counters in each case (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_10_1_14_SecOCTxPduProcessing.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_10_1_14_SecOCTxPduProcessing">SWS SecOC p. 155</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_10_1_7_SecOCRxPduProcessing.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_10_1_7_SecOCRxPduProcessing">SWS SecOC p. 140</a>).</p>
<p><strong>PDU structure.</strong> A Secured I-PDU consists of an optional header, the Authentic I-PDU, an optional Freshness Value, and the Authenticator. The Freshness Value and Authenticator can be transmitted in truncated form (<a class="docref internal-spec-ref" href="../../../spec/figures/FIG-81ea829466a9016a.html" data-snip="FIG-81ea829466a9016a">SWS SecOC Fig. 5 p. 29</a>). SecOC fills unused areas with <code>SecOCTxPduUnusedAreasDefault</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00269" href="../../spec/record.html?id=SWS_SecOC_00269">[SWS_SecOC_00269]</a>). How much the receiver extracts as the Authentic I-PDU depends on the header and the length type:</p>
<ul>
<li>Without header and with static length, the configured length of the global PDU applies (<a class="spec-record-ref" data-req="SWS_SecOC_00257" href="../../spec/record.html?id=SWS_SecOC_00257">[SWS_SecOC_00257]</a>).</li>
<li>Without header and with dynamic length, the length reported by the lower layer applies (<a class="spec-record-ref" data-req="SWS_SecOC_00258" href="../../spec/record.html?id=SWS_SecOC_00258">[SWS_SecOC_00258]</a>).</li>
<li>With header, the length from the header applies (<a class="spec-record-ref" data-req="SWS_SecOC_00259" href="../../spec/record.html?id=SWS_SecOC_00259">[SWS_SecOC_00259]</a>).</li>
</ul>
<p><strong>Separate Cryptographic I-PDU.</strong> With <code>SecOCTxSecuredPduCollection</code>, a Secured I-PDU is transmitted as two messages: as an Authentic I-PDU and as a separate Cryptographic I-PDU (<a class="spec-record-ref" data-req="SWS_SecOC_00201" href="../../spec/record.html?id=SWS_SecOC_00201">[SWS_SecOC_00201]</a>, <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-057c6cbba39ce7c3.html" data-snip="FIG-057c6cbba39ce7c3">TPS SystemTemplate Fig. 6.18 p. 244</a>). The following rules apply:</p>
<ul>
<li>Both messages are transmitted in the same main function cycle (<a class="spec-record-ref" data-req="SWS_SecOC_00202" href="../../spec/record.html?id=SWS_SecOC_00202">[SWS_SecOC_00202]</a>).</li>
<li>A Message Linker, i.e. a portion of the Authentic I-PDU repeated in the Cryptographic I-PDU, links the two messages (<a class="spec-record-ref" data-req="SWS_SecOC_00209" href="../../spec/record.html?id=SWS_SecOC_00209">[SWS_SecOC_00209]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00210" href="../../spec/record.html?id=SWS_SecOC_00210">[SWS_SecOC_00210]</a>).</li>
<li>The receiver only verifies when both messages with a matching linker are available (<a class="spec-record-ref" data-req="SWS_SecOC_00203" href="../../spec/record.html?id=SWS_SecOC_00203">[SWS_SecOC_00203]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00211" href="../../spec/record.html?id=SWS_SecOC_00211">[SWS_SecOC_00211]</a>).</li>
<li>Upon success, SecOC clears both buffers. After a failure, both remain buffered, and the verification is repeated when new data arrives (<a class="spec-record-ref" data-req="SWS_SecOC_00207" href="../../spec/record.html?id=SWS_SecOC_00207">[SWS_SecOC_00207]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00208" href="../../spec/record.html?id=SWS_SecOC_00208">[SWS_SecOC_00208]</a>).</li>
<li>The upper layer receives <code>E_OK</code> only if both transmit confirmations were <code>E_OK</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00270" href="../../spec/record.html?id=SWS_SecOC_00270">[SWS_SecOC_00270]</a>).</li>
<li>With the overflow strategy <code>QUEUE</code>, no Rx collection is permitted (<a class="spec-record-ref" data-req="SWS_SecOC_CONSTR_00265" href="../../spec/record.html?id=SWS_SecOC_CONSTR_00265">[SWS_SecOC_CONSTR_00265]</a>).</li>
</ul>

<h4>Behavior in the event of an error</h4>
<p><strong>Transmit side.</strong></p>
<ul>
<li>If the CSM reports a recoverable error (e.g. <code>E_BUSY</code>), SecOC does not transmit a Secured I-PDU. The Authentic I-PDU is retained and is authenticated again in the next main function (<a class="spec-record-ref" data-req="SWS_SecOC_00151" href="../../spec/record.html?id=SWS_SecOC_00151">[SWS_SecOC_00151]</a>).</li>
<li>If <code>SecOCAuthenticationBuildAttempts</code> is reached, SecOC reports <code>SECOC_E_CRYPTO_FAILURE</code> to the DET (<a class="spec-record-ref" data-req="SWS_SecOC_00155" href="../../spec/record.html?id=SWS_SecOC_00155">[SWS_SecOC_00155]</a>).</li>
<li>When the limit is reached, on <code>E_NOT_OK</code> of the freshness query, or on an unrecoverable CSM error, SecOC transmits with the default pattern if it is activated (<a class="spec-record-ref" data-req="SWS_SecOC_00229" href="../../spec/record.html?id=SWS_SecOC_00229">[SWS_SecOC_00229]</a>).</li>
<li>If the pattern is not configured, SecOC removes the Authentic I-PDU and aborts the transmit request (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_10_1_2_SecOCGeneral.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_10_1_2_SecOCGeneral">SWS SecOC p. 124</a>). A configured but not activated pattern is likely treated in the same way, because the rest of <a class="spec-record-ref" data-req="SWS_SecOC_00229" href="../../spec/record.html?id=SWS_SecOC_00229">[SWS_SecOC_00229]</a> is truncated in the payload.</li>
</ul>
<p><strong>Cancellation and errors during data transfer.</strong></p>
<ul>
<li>If the upper layer cancels via <code>SecOC_IfCancelTransmit</code> or <code>SecOC_TpCancelTransmit</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00113" href="../../spec/record.html?id=SWS_SecOC_00113">[SWS_SecOC_00113]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_91009" href="../../spec/record.html?id=SWS_SecOC_91009">[SWS_SecOC_91009]</a>), SecOC immediately informs the lower layer, stops all associated actions, and releases the buffers (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_4_4_Error_handling_and_cancelation_of_transmission.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_4_4_Error_handling_and_cancelation_of_transmission">SWS SecOC p. 48</a>).</li>
<li>If the lower layer reports a transmission error, SecOC handles it only by omitting the confirmation to the upper layer (ibid.).</li>
<li>If <code>PduR_SecOCTpCopyTxData</code> returns <code>BUFREQ_E_BUSY</code>, SecOC repeats the call in the next main function. In case of <code>BUFREQ_E_NOT_OK</code>, SecOC aborts immediately with <code>E_NOT_OK</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00260" href="../../spec/record.html?id=SWS_SecOC_00260">[SWS_SecOC_00260]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00266" href="../../spec/record.html?id=SWS_SecOC_00266">[SWS_SecOC_00266]</a>).</li>
<li>For reception, the same applies to <code>PduR_SecOCTpCopyRxData</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00267" href="../../spec/record.html?id=SWS_SecOC_00267">[SWS_SecOC_00267]</a>).</li>
</ul>
<p><strong>Receive side.</strong> SecOC maintains two counters per Secured I-PDU, which are set to 0 upon initial processing (<a class="spec-record-ref" data-req="SWS_SecOC_00234" href="../../spec/record.html?id=SWS_SecOC_00234">[SWS_SecOC_00234]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00235" href="../../spec/record.html?id=SWS_SecOC_00235">[SWS_SecOC_00235]</a>):</p>
<ul>
<li><strong>Build counter</strong>: increases on <code>E_BUSY</code> of the freshness query and on recoverable CSM errors (<a class="spec-record-ref" data-req="SWS_SecOC_00236" href="../../spec/record.html?id=SWS_SecOC_00236">[SWS_SecOC_00236]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00237" href="../../spec/record.html?id=SWS_SecOC_00237">[SWS_SecOC_00237]</a>). Below <code>SecOCAuthenticationBuildAttempts</code>, a retry is performed in the next Rx main function (<a class="spec-record-ref" data-req="SWS_SecOC_00238" href="../../spec/record.html?id=SWS_SecOC_00238">[SWS_SecOC_00238]</a>). At the limit, SecOC discards the PDU with <code>SECOC_AUTHENTICATIONBUILDFAILURE</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00240" href="../../spec/record.html?id=SWS_SecOC_00240">[SWS_SecOC_00240]</a>).</li>
<li><strong>Verify counter</strong>: increases on an actual verification failure, and the build counter is reset in the process (<a class="spec-record-ref" data-req="SWS_SecOC_00239" href="../../spec/record.html?id=SWS_SecOC_00239">[SWS_SecOC_00239]</a>). At the limit <code>SecOCAuthenticationVerifyAttempts</code> or in case of <code>E_NOT_OK</code>/<code>KEY_FAILURE</code>, SecOC discards the PDU with <code>SECOC_VERIFICATIONFAILURE</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00241" href="../../spec/record.html?id=SWS_SecOC_00241">[SWS_SecOC_00241]</a>).</li>
</ul>
<p>If the freshness query returns <code>E_NOT_OK</code>, the PDU is discarded with <code>SECOC_FRESHNESSFAILURE</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00256" href="../../spec/record.html?id=SWS_SecOC_00256">[SWS_SecOC_00256]</a>). In contrast, <a class="spec-record-ref" data-req="SWS_SecOC_00248" href="../../spec/record.html?id=SWS_SecOC_00248">[SWS_SecOC_00248]</a> describes the same case as a counted verification failure with DET report <code>SECOC_E_FRESHNESS_FAILURE</code> (<a class="spec-record-ref" data-req="SWS_SecOC_00114" href="../../spec/record.html?id=SWS_SecOC_00114">[SWS_SecOC_00114]</a>). Interpretation: Both requirements apply to R20-11. How they are delimited from each other is left open by the specification; the integration project should clarify this with the supplier.</p>
<p>An override can overrule the discard (<a class="spec-record-ref" data-req="SWS_SecOC_00240" href="../../spec/record.html?id=SWS_SecOC_00240">[SWS_SecOC_00240]</a>). If a statically long PDU turns out too short, SecOC discards it silently (<a class="spec-record-ref" data-req="SWS_SecOC_00268" href="../../spec/record.html?id=SWS_SecOC_00268">[SWS_SecOC_00268]</a>). R20-11 links this to the EcuC parameter <code>DynamicLength</code>; the R23-11 document passage uses <code>SecOCDynamicRuntimeLengthHandling</code> instead (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_SECOC_SECTION_7_5_1_Verification_during_bus_interface_reception.html" data-snip="SNIP_CLASSIC_SECOC_SECTION_7_5_1_Verification_during_bus_interface_reception">SWS SecOC p. 52</a>).</p>
<p><strong>Security Events.</strong> SecOC reports failed MAC checks and missing freshness values as <code>SECOC_SEV_MAC_VERIFICATION_FAILED</code> and <code>SECOC_SEV_FRESHNESS_NOT_AVAILABLE</code>, respectively, to the IdsM (<a class="spec-record-ref" data-req="SWS_SecOC_00274" href="../../spec/record.html?id=SWS_SecOC_00274">[SWS_SecOC_00274]</a>, <a class="spec-record-ref" data-req="SWS_SecOC_00275" href="../../spec/record.html?id=SWS_SecOC_00275">[SWS_SecOC_00275]</a>).</p>
