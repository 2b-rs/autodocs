<h4>Context</h4>
<p>Within the AUTOSAR Adaptive Platform (Release R25-11), the namespace <code>ara::rds</code> provides functional interfaces and data structures for streaming raw data (Raw Data Streams). The primary task of the module consists in efficiently transmitting and processing both generic binary data streams and specialized, typed stream datagrams over network connections. The namespace is divided into two main functional areas: generic client-server transmission of binary streams and standardized transmission according to the IEEE 1722 standard.</p>
<p>For generic communication, the namespace defines the central endpoints <code>RawDataStreamServer</code> and <code>RawDataStreamClient</code>. While the server is responsible for accepting incoming network connections and reading or writing data streams, the client acts as the active peer to establish the connection and perform subsequent read and write access. The result of a read operation is encapsulated in the helper class <code>ReadDataResult</code>.</p>
<p>For time-critical multimedia or time-sensitive data streams, <code>ara::rds</code> provides dedicated components for the IEEE 1722 protocol. The role of data transmission is assumed by <code>IEEE1722RawDataStreamProducer</code>, whereas reception and filtering are performed by <code>IEEE1722RawDataStreamConsumer</code>. The transmitted datagrams are mapped by a series of structured classes, including the base representation <code>IEEE1722Datagram</code>, common header structures such as <code>IEEE1722DatagramAVTPDUCommonHeaderFields</code> and <code>IEEE1722DatagramAVTPDUCommonStreamHeaderFields</code>, as well as format-specific derivatives like <code>IEEE1722DatagramAAF</code>, <code>IEEE1722DatagramRVF</code>, <code>IEEE1722DatagramCRF</code>, <code>IEEE1722DatagramTSCF</code>, <code>IEEE1722DatagramNTSCF</code>, and <code>IEEE1722Datagram61883_IIDC</code>.</p>

<h4>Usage Path</h4>
<p>A typical usage path in the namespace <code>ara::rds</code> differs depending on whether a generic point-to-point stream connection or IEEE 1722 typed streaming is implemented. In a generic transmission, the server application first initializes an instance of <code>RawDataStreamServer</code> and waits for incoming connection requests. Concurrently, the client application creates a <code>RawDataStreamClient</code>, which establishes a network connection to the server.</p>
<p>Following successful connection establishment, the bidirectional exchange of binary data takes place. Interpretation: Transmission of the binary data over the network connection is likely based on transport protocols such as TCP or UDP, with data exchange occurring either blockwise or buffered. Read operations on the endpoints return an instance of <code>ReadDataResult</code>, which provides the read payload data as well as status-related information about the read process. After completion of data transmission, the streams and connections are closed in an orderly manner by the participating parties.</p>
<p>In the use case of IEEE 1722 streaming, a sending application creates the <code>IEEE1722RawDataStreamProducer</code>. This is fed with structured datagrams whose headers are parameterized via <code>IEEE1722DatagramAVTPDUCommonHeaderFields</code> or <code>IEEE1722DatagramAVTPDUCommonStreamHeaderFields</code>. Interpretation: The specific datagram classes such as <code>IEEE1722DatagramAAF</code> (audio) or <code>IEEE1722DatagramRVF</code> (video) are likely to encapsulate standardized AVTP payloads to enable deterministic audio and video streaming in the vehicle network. On the receiver side, the <code>IEEE1722RawDataStreamConsumer</code> subscribes to the typed data streams and forwards the received datagrams to the processing application.</p>

<h4>Error Scenarios</h4>
<p>Error situations during initialization, connection establishment, or ongoing data transmission are signaled in the namespace <code>ara::rds</code> via the uniform error model of the AUTOSAR Adaptive Platform. This is based on the <code>ara::core::ErrorDomain</code> domain architecture and error codes of type <code>ara::core::ErrorCode</code>.</p>
<p>A central component is the enumeration <code>RdsErrc</code> <a class="spec-record-ref" data-req="SWS_RDS_12367" href="../spec/record.html?id=SWS_RDS_12367">[SWS_RDS_12367]</a>, which is defined as <code>enum class RdsErrc : ara::core::ErrorDomain::CodeType</code> and lists the module-specific error states of Raw Data Stream. The declarations are located in the header file <code>#include "ara/rds/rds_error_domain.h"</code>.</p>
<p>To map error codes to the RDS error domain, the header provides the function <code>GetRdsErrorDomain</code> <a class="spec-record-ref" data-req="SWS_RDS_11298" href="../spec/record.html?id=SWS_RDS_11298">[SWS_RDS_11298]</a>, which returns a reference to the global domain object <code>RdsErrorDomain</code>. To create a fully-fledged error code from an enumeration value and optional auxiliary data, the function <code>MakeErrorCode</code> <a class="spec-record-ref" data-req="SWS_RDS_11299" href="../spec/record.html?id=SWS_RDS_11299">[SWS_RDS_11299]</a> is used, which is declared as <code>constexpr ara::core::ErrorCode MakeErrorCode(RdsErrc code, ara::core::ErrorDomain::SupportDataType data) noexcept</code>.</p>
<p>Typical error scenarios comprise failed connection establishments, connection drops during the data stream, buffer overflows, or format errors when parsing IEEE 1722 headers. If such states occur, affected methods typically return a corresponding <code>ara::core::ErrorCode</code>. If exceptions are used on the caller side or errors need to be translated into an exception context, the class <code>RdsException</code> represents the associated exception type for the namespace.</p>
