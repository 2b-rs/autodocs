<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht Client-Anwendungen das Abonnieren von Service-Ereignissen und den typisierten Empfang neuer Datenproben.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Schnittstellenklasse <code>&lt;SI-Namespace&gt;::proxy::events::&lt;Event&gt;</code> ermöglicht Client-Anwendungen in der AUTOSAR Adaptive Platform den konsumentenseitigen Empfang von Service-Ereignissen über das Modul <code>com</code>. Der typische Ablauf umfasst das Anfordern des Abonnements über <code>Subscribe</code> <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>, die reaktive Benachrichtigung über registrierte Handler sowie den synchronen Probenabruf mittels <code>GetNewSamples</code> <a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a>. Dabei dürfen nicht mehr Probenzeiger gleichzeitig gehalten werden als beim Abonnement reserviert wurden, und vor der Abmeldung über <code>Unsubscribe</code> müssen alle Referenzen freigegeben sein.</p>

<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Die C++-Klasse <code>&lt;SI-Namespace&gt;::proxy::events::&lt;Event&gt;</code> repräsentiert die konsumentenseitige Schnittstelle für ein Service-Ereignis im Modul <code>com</code> der AUTOSAR Adaptive Platform (Release R25-11). Innerhalb des serviceorientierten Kommunikationsmusters dient diese generierte Klasse als lokaler Repräsentant eines vom Server-Skelett bereitgestellten Ereignisses. Client-Anwendungen nutzen Instanzen dieser Klasse, um Ereignisdaten zu abonnieren, eingehende Proben (Samples) aus dem Kommunikationsnetzwerk entgegenzunehmen und deren Lebenszyklus auf Konsumentenseite zu steuern <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">AUTOSAR_AP_EXP_ARAComAPI S. 10</a>.</p>
<p>Die wesentlichen Interaktionspartner der Klasse sind:</p>
<ul>
<li><strong>Anwendung (Subscriber):</strong> Initiiert die Registrierung des Ereignisabonnements über <code>Subscribe</code> <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>, hinterlegt Callback-Routinen für den Datenempfang sowie Statusänderungen und fragt neue Proben über <code>GetNewSamples</code> <a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a> ab.</li>
<li><strong>Communication Management:</strong> Koordiniert die Übertragung der Ereignisdaten über die zugrunde liegende Middleware, verwaltet den Netzwerkstatus und führt die registrierten Benachrichtigungshandler bei Eintreffen neuer Ereignisse oder Zustandsänderungen aus <a class="spec-record-ref" data-req="SWS_CM_00181" href="../spec/record.html?id=SWS_CM_00181">[SWS_CM_00181]</a>, <a class="spec-record-ref" data-req="SWS_CM_00333" href="../spec/record.html?id=SWS_CM_00333">[SWS_CM_00333]</a>.</li>
<li><strong>Ausführungskontext (Executor):</strong> Bei Verwendung überladener Registrierungsmethoden werden asynchrone Handler innerhalb eines explizit übergebenen Kontexts <code>ExecutorT</code> ausgeführt <a class="spec-record-ref" data-req="SWS_CM_11354" href="../spec/record.html?id=SWS_CM_11354">[SWS_CM_11354]</a>, <a class="spec-record-ref" data-req="SWS_CM_11356" href="../spec/record.html?id=SWS_CM_11356">[SWS_CM_11356]</a>, <a class="spec-record-ref" data-req="SWS_CM_00100" href="../spec/record.html?id=SWS_CM_00100">[SWS_CM_00100]</a>.</li>
</ul>

<h4>Lebenszyklus</h4>
<p>Die Instanziierung und Zerstörung von <code>&lt;SI-Namespace&gt;::proxy::events::&lt;Event&gt;</code> dürfte als Member der übergeordneten Proxy-Klasse fest an die Lebensdauer des Service-Proxy gebunden sein. <a class="interp-q interp-q-open" data-q="Q-6c591ea580278c12" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-6c591ea580278c12" title="Frage Q-6c591ea580278c12 (offen): Die Bindung des Lebenszyklus an die übergeordnete Proxy-Klasse ist eine Interpretation">Frage Q-6c591ea580278c12 (offen)</a> Nach der Erzeugung befindet sich das Ereignis zunächst im nicht abonnierten Zustand. Der aktuelle Abonnementsstatus kann jederzeit über <code>GetSubscriptionState</code> abgefragt werden, welche den Zustand als <code>ara::com::SubscriptionState</code> zurückgibt <a class="spec-record-ref" data-req="SWS_CM_00316" href="../spec/record.html?id=SWS_CM_00316">[SWS_CM_00316]</a>.</p>
<p>Der Übergang in den aktiven Abonnementszustand wird über <code>Subscribe</code> eingeleitet, wobei die maximale Anzahl gleichzeitig verfügbarer Cache-Slots über <code>maxSampleCount</code> festgelegt wird <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>. Befindet sich das Ereignis zum Aufrufzeitpunkt bereits in den Zuständen <code>kSubscribed</code> oder <code>kSubscriptionPending</code> und stimmt der übergebene Wert mit dem aktuellen überein, bleibt der Aufruf ohne Wirkung <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>. Zustandsänderungen des Abonnements meldet das Communication Management über einen Handler, der mittels <code>SetSubscriptionStateChangeHandler</code> <a class="spec-record-ref" data-req="SWS_CM_00333" href="../spec/record.html?id=SWS_CM_00333">[SWS_CM_00333]</a> oder mit Ausführungskontext via <code>SetSubscriptionStateChangeHandler</code> <a class="spec-record-ref" data-req="SWS_CM_11354" href="../spec/record.html?id=SWS_CM_11354">[SWS_CM_11354]</a> registriert wird. Diese Registrierung kann über <code>UnsetSubscriptionStateChangeHandler</code> aufgehoben werden <a class="spec-record-ref" data-req="SWS_CM_00334" href="../spec/record.html?id=SWS_CM_00334">[SWS_CM_00334]</a> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">AUTOSAR_AP_EXP_ARAComAPI S. 10</a>.</p>
<p>Zusätzlich verwaltet die Klasse den Zustand der End-to-End-Absicherung (E2E). Über <code>GetE2EStateMachineState</code> wird der Zustand <code>ara::com::e2e::SMState</code> der E2E-Zustandsmaschine ermittelt, wie er beim letzten internen Aufruf von <code>E2E_Check()</code> während <code>GetNewSamples()</code> festgestellt wurde <a class="spec-record-ref" data-req="SWS_CM_11554" href="../spec/record.html?id=SWS_CM_11554">[SWS_CM_11554]</a>. Fehlerhafte Übertragungsbedingungen können durch Handler überwacht werden, die über <code>SetTransportFaultConditionHandler</code> <a class="spec-record-ref" data-req="SWS_CM_00099" href="../spec/record.html?id=SWS_CM_00099">[SWS_CM_00099]</a> oder <a class="spec-record-ref" data-req="SWS_CM_00100" href="../spec/record.html?id=SWS_CM_00100">[SWS_CM_00100]</a> gesetzt und via <code>UnsetTransportFaultConditionHandler</code> <a class="spec-record-ref" data-req="SWS_CM_00105" href="../spec/record.html?id=SWS_CM_00105">[SWS_CM_00105]</a> entfernt werden.</p>
<p>Die Beendigung des Abonnements erfolgt über <code>Unsubscribe</code> <a class="spec-record-ref" data-req="SWS_CM_00151" href="../spec/record.html?id=SWS_CM_00151">[SWS_CM_00151]</a> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">AUTOSAR_AP_EXP_ARAComAPI S. 10</a>. Ist das Ereignis zu diesem Zeitpunkt nicht abonniert, kehrt die Methode ohne Aktion zurück <a class="spec-record-ref" data-req="SWS_CM_00151" href="../spec/record.html?id=SWS_CM_00151">[SWS_CM_00151]</a>. Sämtliche Elementfunktionen sind als <code>noexcept</code> deklariert und bieten vollständige Ausnahme-Sicherheit.</p>

<h4>Nutzungspfad</h4>
<p>Der typische Ablauf zur Nutzung des Proxy-Ereignisses gliedert sich in folgende aufeinanderfolgende Phasen:</p>
<ol>
<li><strong>Abonnement einleiten:</strong> Die Anwendung ruft <code>Subscribe(maxSampleCount)</code> auf <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>, um die Puffergröße für eingehende Proben zu reservieren.</li>
<li><strong>Benachrichtigung konfigurieren:</strong> Über <code>SetReceiveHandler</code> <a class="spec-record-ref" data-req="SWS_CM_00181" href="../spec/record.html?id=SWS_CM_00181">[SWS_CM_00181]</a> (oder mit Ausführungskontext via <a class="spec-record-ref" data-req="SWS_CM_11356" href="../spec/record.html?id=SWS_CM_11356">[SWS_CM_11356]</a>) wird ein parameterloser Callback registriert, der bei Eintreffen neuer Ereignisse vom Communication Management aufgerufen wird.</li>
<li><strong>Proben abrufen und verarbeiten:</strong> Im Callback ruft die Anwendung <code>GetNewSamples</code> <a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a> auf. Ein übergebenes Callable <code>f</code> mit der Signatur <code>void(ara::com::SamplePtr&lt;SampleType const&gt;)</code> verarbeitet jede Probe sequenziell. Hierbei entspricht <code>SampleType</code> dem typspezifischen Nutzdatentyp des Ereignisses <a class="spec-record-ref" data-req="SWS_CM_11401" href="../spec/record.html?id=SWS_CM_11401">[SWS_CM_11401]</a>. Der Rückgabewert liefert als <code>ara::core::Result&lt;std::size_t&gt;</code> die exakte Anzahl der an <code>f</code> übergebenen Proben <a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a>.</li>
<li><strong>Cache überwachen:</strong> Mittels <code>GetFreeSampleCount</code> <a class="spec-record-ref" data-req="SWS_CM_00705" href="../spec/record.html?id=SWS_CM_00705">[SWS_CM_00705]</a> kann die Anwendung die Anzahl ungenutzter Plätze im lokalen Cache prüfen, um Pufferengpässe frühzeitig zu erkennen.</li>
<li><strong>Dereferenzierung und Abmeldung:</strong> Nach Abschluss der Datenverarbeitung wird der Empfangstrigger mit <code>UnsetReceiveHandler</code> deaktiviert <a class="spec-record-ref" data-req="SWS_CM_00183" href="../spec/record.html?id=SWS_CM_00183">[SWS_CM_00183]</a> und das Abonnement über <code>Unsubscribe</code> beendet <a class="spec-record-ref" data-req="SWS_CM_00151" href="../spec/record.html?id=SWS_CM_00151">[SWS_CM_00151]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Bei der Verwendung der Klasse können spezifische Fehlercodes und Laufzeitverletzungen auftreten, die defensive Prüfungen erfordern:</p>
<ul>
<li><strong>Konfigurationsfehler beim Re-Subscription:</strong> Wird <code>Subscribe</code> aufgerufen, während das Ereignis bereits abonniert ist, und unterscheidet sich das neue <code>maxSampleCount</code> vom aktuellen Wert, schlägt der Aufruf mit dem Fehlercode <code>ComErrc::kMaxSampleCountNotRealizable</code> fehl <a class="spec-record-ref" data-req="SWS_CM_00141" href="../spec/record.html?id=SWS_CM_00141">[SWS_CM_00141]</a>. <li><strong>Überschreitung der Puffergrenzen:</strong> Hält die Anwendung mehr Instanzen von <code>ara::com::SamplePtr</code>, als im vorherigen Aufruf von <code>Subscribe</code> zugesichert wurden, gibt <code>GetNewSamples</code> den Fehlercode <code>ComErrc::kMaxSamplesExceeded</code> zurück; in diesem Fall können Datenproben verworfen worden sein <a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a>.</li>
