<h4>Context</h4>
<p>The template class <code>ara::core::Map</code> in the <code>core</code> module of the AUTOSAR Adaptive Platform provides an ordered associative container defined as an implementation of <code>std::pmr::map</code>. It manages key-value pairs of type <code>value_type</code> (<a class="spec-record-ref" data-req="SWS_CORE_01404" href="../spec/record.html?id=SWS_CORE_01404">[SWS_CORE_01404]</a>), which are composed of <code>key_type</code> (<a class="spec-record-ref" data-req="SWS_CORE_01402" href="../spec/record.html?id=SWS_CORE_01402">[SWS_CORE_01402]</a>) and <code>mapped_type</code> (<a class="spec-record-ref" data-req="SWS_CORE_01403" href="../spec/record.html?id=SWS_CORE_01403">[SWS_CORE_01403]</a>). The unique keys are sorted via the predicate <code>key_compare</code> (<a class="spec-record-ref" data-req="SWS_CORE_01405" href="../spec/record.html?id=SWS_CORE_01405">[SWS_CORE_01405]</a>), which defaults to <code>std::less&lt;Key&gt;</code>. For memory management, the class integrates a configurable allocator <code>allocator_type</code> (<a class="spec-record-ref" data-req="SWS_CORE_01406" href="../spec/record.html?id=SWS_CORE_01406">[SWS_CORE_01406]</a>). Interpretation: Since the container is based on <code>std::pmr::map</code>, allocation is likely based primarily on memory-monitored memory resources of the platform to avoid dynamic heap fragmentation in safety-related ECUs. Typical interaction partners include application modules that hold sorted tables or configuration data, as well as sorting and comparison operators via <code>key_comp()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01488" href="../spec/record.html?id=SWS_CORE_01488">[SWS_CORE_01488]</a>) and <code>value_comp()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01489" href="../spec/record.html?id=SWS_CORE_01489">[SWS_CORE_01489]</a>).</p>

<h4>Lifecycle</h4>
<p>The creation of a <code>ara::core::Map</code> is carried out flexibly via the default constructor <a class="spec-record-ref" data-req="SWS_CORE_01428" href="../spec/record.html?id=SWS_CORE_01428">[SWS_CORE_01428]</a>, by explicitly specifying an allocator (<a class="spec-record-ref" data-req="SWS_CORE_01431" href="../spec/record.html?id=SWS_CORE_01431">[SWS_CORE_01431]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01429" href="../spec/record.html?id=SWS_CORE_01429">[SWS_CORE_01429]</a>), or via iterator ranges (<a class="spec-record-ref" data-req="SWS_CORE_01430" href="../spec/record.html?id=SWS_CORE_01430">[SWS_CORE_01430]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01435" href="../spec/record.html?id=SWS_CORE_01435">[SWS_CORE_01435]</a>) as well as initializer lists (<a class="spec-record-ref" data-req="SWS_CORE_01434" href="../spec/record.html?id=SWS_CORE_01434">[SWS_CORE_01434]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01436" href="../spec/record.html?id=SWS_CORE_01436">[SWS_CORE_01436]</a>). These constructors are classified as not exception-safe (<em>not exception safe</em>), since memory allocations can fail. Regarding ownership, the container behaves like a regular value type: the copy and move constructors are defined as default implementations (<a class="spec-record-ref" data-req="SWS_CORE_01424" href="../spec/record.html?id=SWS_CORE_01424">[SWS_CORE_01424]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01426" href="../spec/record.html?id=SWS_CORE_01426">[SWS_CORE_01426]</a>). The copy assignment operator is also defined as <code>default</code> (<a class="spec-record-ref" data-req="SWS_CORE_01425" href="../spec/record.html?id=SWS_CORE_01425">[SWS_CORE_01425]</a>), while the move assignment <a class="spec-record-ref" data-req="SWS_CORE_01427" href="../spec/record.html?id=SWS_CORE_01427">[SWS_CORE_01427]</a> is conditionally exception-safe and depends on <code>std::allocator_traits&lt;Allocator&gt;::is_always_equal::value</code> as well as the noexcept moveability of the comparison predicate.</p>
<p>Two container instances can be swapped via <code>swap()</code> <a class="spec-record-ref" data-req="SWS_CORE_01484" href="../spec/record.html?id=SWS_CORE_01484">[SWS_CORE_01484]</a>. In deviation from the standard, AUTOSAR requires the use of <code>ara::core::is_nothrow_swappable&lt;Compare&gt;</code> instead of the standard library function here. At runtime, the container alternates between the empty state (<a class="spec-record-ref" data-req="SWS_CORE_01511" href="../spec/record.html?id=SWS_CORE_01511">[SWS_CORE_01511]</a>) and the populated state with up to <code>max_size()</code> elements (<a class="spec-record-ref" data-req="SWS_CORE_01453" href="../spec/record.html?id=SWS_CORE_01453">[SWS_CORE_01453]</a>). With <code>clear()</code> <a class="spec-record-ref" data-req="SWS_CORE_01485" href="../spec/record.html?id=SWS_CORE_01485">[SWS_CORE_01485]</a>, all elements are released in an exception-safe manner. The destructor <code>~Map()</code> <a class="spec-record-ref" data-req="SWS_CORE_01437" href="../spec/record.html?id=SWS_CORE_01437">[SWS_CORE_01437]</a> ends the lifecycle and destroys all contained nodes.</p>

<h4>Usage Path</h4>
<p>A typical usage path comprises instantiation, targeted insertion of elements, querying, and subsequent cleanup:</p>
<ol>
<li><strong>Population:</strong> New entries are preferably inserted via <code>try_emplace()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01472" href="../spec/record.html?id=SWS_CORE_01472">[SWS_CORE_01472]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01473" href="../spec/record.html?id=SWS_CORE_01473">[SWS_CORE_01473]</a>), since keys are not unnecessarily moved or constructed if entries already exist. Alternatively, <code>emplace()</code> <a class="spec-record-ref" data-req="SWS_CORE_01458" href="../spec/record.html?id=SWS_CORE_01458">[SWS_CORE_01458]</a>, <code>insert_or_assign()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01476" href="../spec/record.html?id=SWS_CORE_01476">[SWS_CORE_01476]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01477" href="../spec/record.html?id=SWS_CORE_01477">[SWS_CORE_01477]</a>), regular overloads of <code>insert()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01460" href="../spec/record.html?id=SWS_CORE_01460">[SWS_CORE_01460]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01461" href="../spec/record.html?id=SWS_CORE_01461">[SWS_CORE_01461]</a>), and the subscript operator <code>operator[]</code> (<a class="spec-record-ref" data-req="SWS_CORE_01454" href="../spec/record.html?id=SWS_CORE_01454">[SWS_CORE_01454]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01455" href="../spec/record.html?id=SWS_CORE_01455">[SWS_CORE_01455]</a>) are available.</li>
<li><strong>Lookup and access:</strong> The presence of a key can be checked via <code>contains()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01497" href="../spec/record.html?id=SWS_CORE_01497">[SWS_CORE_01497]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01510" href="../spec/record.html?id=SWS_CORE_01510">[SWS_CORE_01510]</a>) or <code>count()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01494" href="../spec/record.html?id=SWS_CORE_01494">[SWS_CORE_01494]</a>). <code>find()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01490" href="../spec/record.html?id=SWS_CORE_01490">[SWS_CORE_01490]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01491" href="../spec/record.html?id=SWS_CORE_01491">[SWS_CORE_01491]</a>) is used for direct iterator determination. Range queries are possible via <code>lower_bound()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01498" href="../spec/record.html?id=SWS_CORE_01498">[SWS_CORE_01498]</a>), <code>upper_bound()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01502" href="../spec/record.html?id=SWS_CORE_01502">[SWS_CORE_01502]</a>), and <code>equal_range()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01506" href="../spec/record.html?id=SWS_CORE_01506">[SWS_CORE_01506]</a>).</li>
<li><strong>Iteration and node extraction:</strong> Navigation over the elements is performed using forward and reverse iterators (<a class="spec-record-ref" data-req="SWS_CORE_01440" href="../spec/record.html?id=SWS_CORE_01440">[SWS_CORE_01440]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01442" href="../spec/record.html?id=SWS_CORE_01442">[SWS_CORE_01442]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01448" href="../spec/record.html?id=SWS_CORE_01448">[SWS_CORE_01448]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01449" href="../spec/record.html?id=SWS_CORE_01449">[SWS_CORE_01449]</a>). Individual nodes can be extracted as <code>node_type</code> (<a class="spec-record-ref" data-req="SWS_CORE_01417" href="../spec/record.html?id=SWS_CORE_01417">[SWS_CORE_01417]</a>) without memory reallocation using <code>extract()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01470" href="../spec/record.html?id=SWS_CORE_01470">[SWS_CORE_01470]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01471" href="../spec/record.html?id=SWS_CORE_01471">[SWS_CORE_01471]</a>) or spliced from another map with <code>merge()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01486" href="../spec/record.html?id=SWS_CORE_01486">[SWS_CORE_01486]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01487" href="../spec/record.html?id=SWS_CORE_01487">[SWS_CORE_01487]</a>).</li>
<li><strong>Deletion:</strong> Keys that are no longer needed are removed with <code>erase()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01480" href="../spec/record.html?id=SWS_CORE_01480">[SWS_CORE_01480]</a>–<a class="spec-record-ref" data-req="SWS_CORE_01483" href="../spec/record.html?id=SWS_CORE_01483">[SWS_CORE_01483]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>The most important platform-specific deviation concerns access via the member function <code>at()</code> (<a class="spec-record-ref" data-req="SWS_CORE_01456" href="../spec/record.html?id=SWS_CORE_01456">[SWS_CORE_01456]</a>, <a class="spec-record-ref" data-req="SWS_CORE_01457" href="../spec/record.html?id=SWS_CORE_01457">[SWS_CORE_01457]</a>):</p>
<ul>
<li>If a key is requested that does not exist in the container, <code>at()</code> does not throw a C++ standard exception <code>std::out_of_range</code>, but a <code>IsoStdOutOfRangeViolation</code>.</li>
<li>Both overloads of <code>at()</code> are declared with <code>noexcept</code>. Interpretation: Since the function is marked as <code>noexcept</code> and triggers a violation, the failed access is likely to directly activate the platform's AUTOSAR violation handler and terminate the program, instead of throwing a catchable exception.</li>
</ul>
<p>To avoid runtime errors, the existence of the key should be verified via <code>find()</code> or <code>contains()</code> before calling <code>at()</code>. For mutating operations such as <code>insert()</code>, <code>emplace()</code>, or <code>operator[]</code>, they may fail in case of insufficient memory (<em>not exception safe</em>). After removing entries via <code>erase()</code>, all iterators pointing to the deleted elements become invalid, while iterators pointing to remaining nodes and references remain valid.</p>
