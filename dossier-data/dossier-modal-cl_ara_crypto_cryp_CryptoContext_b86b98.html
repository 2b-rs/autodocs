<h4>Kontext</h4>
<p>Die Schnittstelle <code>ara::crypto::cryp::CryptoContext</code> definiert die grundlegende Abstraktion für veränderliche kryptografische Kontexte (mutable cryptographic contexts) innerhalb des Krypto-Moduls der AUTOSAR Adaptive Platform. Im Gegensatz zu statischen Krypto-Objekten ist ein solcher Kontext nicht starr an ein einzelnes kryptografisches Objekt gebunden. Er dient vielmehr als gemeinsame Basisklasse für verschiedene kryptografische Verarbeitungskontexte, deren interner Zustand sich während der Ausführung kryptografischer Operationen verändern kann.</p>
<p>Als zentrales Element dieser Basisschnittstelle fungiert die rein virtuelle Elementfunktion <code>GetAlgId()</code>. Sie ermöglicht es Interaktionspartnern, die Kennung des aktuell im Kontext konfigurierten kryptografischen Algorithmus abzufragen <a class="spec-record-ref" data-req="SWS_CRYPT_20411" href="../spec/record.html?id=SWS_CRYPT_20411">[SWS_CRYPT_20411]</a>. Konkrete kryptografische Berechnungs- und Transformationskontexte, wie beispielsweise für Hash-, Signatur- oder Verschlüsselungsdienste, dürften im System von <code>CryptoContext</code> abgeleitet werden, um spezifische Algorithmenfunktionalitäten bereitzustellen.</p>

<h4>Lebenszyklus</h4>
<p>Der Lebenszyklus von <code>CryptoContext</code> ist von einer eindeutigen Identität und strikten Besitzverhältnissen geprägt. Um unkontrolliertes Duplizieren oder inkonsistente Übertragungen von Kontextzuständen zur Übersetzungszeit zu verhindern, sind semantische Kopiervorgänge vollständig untersagt. Sowohl der Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_CRYPT_41003" href="../spec/record.html?id=SWS_CRYPT_41003">[SWS_CRYPT_41003]</a> als auch der Kopierzuweisungsoperator <a class="spec-record-ref" data-req="SWS_CRYPT_30214" href="../spec/record.html?id=SWS_CRYPT_30214">[SWS_CRYPT_30214]</a> sind explizit als gelöscht deklariert (<code>=delete</code>).</p>
<p>In gleicher Weise unterbindet die Schnittstellendefinition das Verschieben von Kontexten: Sowohl der Verschiebekonstruktor <a class="spec-record-ref" data-req="SWS_CRYPT_41004" href="../spec/record.html?id=SWS_CRYPT_41004">[SWS_CRYPT_41004]</a> als auch der Verschiebezuweisungsoperator <a class="spec-record-ref" data-req="SWS_CRYPT_30215" href="../spec/record.html?id=SWS_CRYPT_30215">[SWS_CRYPT_30215]</a> sind gelöscht (<code>=delete</code>). Instanzen von abgeleiteten Klassen verbleiben daher dauerhaft an ihrem ursprünglichen Speicherort. Die Zerstörung und Ressourcenfreigabe erfolgt deterministisch über den virtuellen Destruktor, der als <code>default</code> und <code>noexcept</code> definiert ist <a class="spec-record-ref" data-req="SWS_CRYPT_20401" href="../spec/record.html?id=SWS_CRYPT_20401">[SWS_CRYPT_20401]</a>. Dies stellt sicher, dass abgeleitete Kontextobjekte sicher und ohne Ressourcenlecks über Zeiger auf die Basisschnittstelle freigegeben werden können.</p>
<p>In Bezug auf die Nebenläufigkeit spezifiziert die Anforderung für <code>GetAlgId()</code> ausdrücklich Thread-Sicherheit <a class="spec-record-ref" data-req="SWS_CRYPT_20411" href="../spec/record.html?id=SWS_CRYPT_20411">[SWS_CRYPT_20411]</a>. Mehrere Threads können somit gleichzeitig und ohne externe Synchronisation den Algorithmusbezeichner desselben Kontexts auslesen.</p>

<h4>Nutzungspfad</h4>
<p>Da <code>CryptoContext</code> eine rein virtuelle Schnittstelle ist, können Anwendungsentwickler keine direkten Instanzen erzeugen. Instanzen spezialisierter Kontextklassen dürften typischerweise über Factory-Funktionen oder Provider-Komponenten des Krypto-Stacks instanziiert und dem Aufrufer über Zeiger oder Referenzen bereitgestellt werden. Der typische Nutzungsablauf auf Ebene der Basisschnittstelle umfasst folgende Phasen:</p>
<ul>
<li>Bereitstellung: Ein Aufrufer empfängt eine Referenz oder einen Zeiger auf einen konfigurierten Kontext von einem Krypto-Provider.</li>
<li>Algorithmenprüfung: Über den Aufruf von <code>GetAlgId()</code> wird die Algorithmuskennung abgefragt und ausgewertet <a class="spec-record-ref" data-req="SWS_CRYPT_20411" href="../spec/record.html?id=SWS_CRYPT_20411">[SWS_CRYPT_20411]</a>, um sicherzustellen, dass der Kontext die geforderten Spezifikationen erfüllt.</li>
<li>Operation und Bereinigung: Nach Durchführung der algorithmspezifischen Operationen über die abgeleitete Schnittstelle wird der Kontext über den virtuellen Destruktor automatisch freigegeben <a class="spec-record-ref" data-req="SWS_CRYPT_20401" href="../spec/record.html?id=SWS_CRYPT_20401">[SWS_CRYPT_20401]</a>.</li>

<h4>Fehlerszenarien</h4>
<p>Das Fehlerbehandlungskonzept von <code>CryptoContext</code> folgt dem allgemeinen fehlersicheren Design der AUTOSAR Adaptive Platform und verzichtet auf C++-Ausnahmen. Die Methode <code>GetAlgId()</code> ist als ausnahmesicher (<code>exception safe</code>) spezifiziert und liefert ihr Ergebnis in einem <code>ara::core::Result&lt;ara::crypto::AlgIdString&gt;</code> zurück <a class="spec-record-ref" data-req="SWS_CRYPT_20411" href="../spec/record.html?id=SWS_CRYPT_20411">[SWS_CRYPT_20411]</a>. Tritt bei der Bestimmung der Algorithmus-ID ein Fehler auf, wird dieser im Fehlerkanal des <code>Result</code>-Objekts transportiert.</p>
<p>Gemäß Spezifikation definiert <code>GetAlgId()</code> keine standardisierten Fehlercodes <a class="spec-record-ref" data-req="SWS_CRYPT_20411" href="../spec/record.html?id=SWS_CRYPT_20411">[SWS_CRYPT_20411]</a>. Aufrufer müssen daher primär prüfen, ob das <code>Result</code> einen gültigen Wert enthält, bevor sie auf die Zeichenkette der Algorithmus-ID zugreifen. Beim Abbau des Objekts gewährleistet der mit <code>noexcept</code> deklarierte virtuelle Destruktor, dass während der Zerstörung keine Ausnahmen propagiert werden und die Bereinigung stets zuverlässig abgeschlossen wird <a class="spec-record-ref" data-req="SWS_CRYPT_20401" href="../spec/record.html?id=SWS_CRYPT_20401">[SWS_CRYPT_20401]</a>.</p>
