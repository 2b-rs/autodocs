<h4>Kontext</h4>
<p>Die Klasse <code>apext::tsync::TsyncFvmException</code> ist eine spezialisierte Ausnahmeklasse innerhalb des Moduls <code>tsync</code> der AUTOSAR Adaptive Platform. Gemäß der Modulspezifikation dient sie der Kapselung und Weitergabe von Fehlerzuständen, die durch den Freshness Value Manager ausgelöst werden. Die Klasse ist als direkte Unterklasse von <code>ara::core::Exception</code> definiert und stellt somit die standardisierte C++-Ausnahmebehandlung für Fehler im Umfeld der Frischewert-Verwaltung sicher.</p>
<p>Zu den primären Interaktionspartnern zählen der Freshness Value Manager als werfende Instanz sowie anwendende Software-Komponenten und Synchronisationsdienste, welche Frischeprüfungen für gesicherte Kommunikationsbeziehungen anfordern. Tritt bei der Verifikation oder Berechnung eines Frischewerts eine Ausnahmebedingung auf, instanziiert der Freshness Value Manager dieses Objekt zur Benachrichtigung des Aufrufers. Die Deklaration und Schnittstellendefinition erfolgt über die Header-Datei <code>apext/tsync/fvm_error_domain.h</code> <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>.</p>

<h4>Lebenszyklus</h4>
<p>Der Lebenszyklus eines Objekts vom Typ <code>apext::tsync::TsyncFvmException</code> ist an den Lebenszyklus regulärer C++-Ausnahmen gebunden. Die Erzeugung erfolgt über den expliziten Konstruktor <code>TsyncFvmException</code>, welcher einen Fehlercode vom Typ <code>ara::core::ErrorCode</code> entgegennimmt <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>. Dieser Konstruktor ist mit der Spezifikation <code>noexcept</code> deklariert, wodurch garantiert wird, dass die Objekterzeugung selbst ausnahmesicher ist und unter keinen Umständen sekundäre Ausnahmen wirft <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>.</p>
<p>Die Klasse ist explizit als ausnahmesicher (<em>exception safe</em>) und threadsicher (<em>thread-safe</em>) spezifiziert <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>. Dies erlaubt die sichere Erzeugung und Weitergabe von Instanzen auch in komplexen, mehrfädigen Laufzeitumgebungen, ohne dass dabei Datenrennen entstehen können.</p>
<p>Interpretation: Hinsichtlich der Besitzverhältnisse wird die Ausnahme typischerweise per Wert geworfen und im Aufrufstapel per Referenz auf ein konstantes Objekt (<code>const apext::tsync::TsyncFvmException&amp;</code>) abgefangen. Nach der Konstruktion durchläuft das Objekt keine weiteren Zustandsänderungen; seine Zerstörung erfolgt automatisch beim Verlassen des behandelnden <code>catch</code>-Blocks.</p>

<h4>Nutzungspfad</h4>
<p>Der reguläre Nutzungspfad vollzieht sich im Rahmen einer vom Freshness Value Manager durchgeführten Validierung oder Aktualisierung von Frischewerten. Erkennt der Manager eine Verletzung der Frischeintegrität oder einen internen Verarbeitungsfehler, leitet er die Fehlerbehandlung ein:</p>
<ol>
<li>Fehleridentifikation: Der Freshness Value Manager stellt einen Fehlerzustand fest und erzeugt ein entsprechendes <code>ara::core::ErrorCode</code>-Objekt.</li>
<li>Instanziierung: Das Ausnahmeobjekt wird unter Übergabe des Fehlercodes über den Konstruktor initialisiert <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>.</li>
<li>Auslösen: Die Ausnahme wird mittels <code>throw</code> in den Aufrufkontext geworfen.</li>
<li>Auswertung: Die aufrufende Anwendung oder Schicht fängt die Ausnahme ab und greift auf den eingebetteten Fehlercode zu, um adäquate Fehlerbehebungs- oder Degradationsmaßnahmen einzuleiten.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Da <code>apext::tsync::TsyncFvmException</code> selbst als Fehlersignalisierungsmechanismus konzipiert ist, liegen funktionale Fehlerszenarien vor allem im fehlerhaften Umgang mit der Ausnahme begründet. Als Vorbedingung für die Erzeugung gilt die Übergabe eines gültigen <code>ara::core::ErrorCode</code> an den Konstruktor <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>. Weil der Konstruktor jedoch als <code>noexcept</code> definiert ist, bleibt die Objekterzeugung selbst bei unerwarteten Fehlerwerten stabil <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>.</p>
<p>Weil der Definitionsheader <code>apext/tsync/fvm_error_domain.h</code> vorgegeben ist, dürfte der gekapselte <code>errorCode</code> vorzugsweise der spezialisierten Fehlerdomäne des Freshness Value Managers entstammen <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a>. Ein schwerwiegendes Fehlerszenario entsteht, wenn die geworfene Ausnahme auf Systemebene von keinem <code>catch</code>-Block behandelt wird; dies führt nach C++-Standardsemantik unweigerlich zum Aufruf von <code>std::terminate</code> und damit zum Prozessabbruch. Durch die garantierte Threadsicherheit nach <a class="spec-record-ref" data-req="SWS_TS_14204" href="../spec/record.html?id=SWS_TS_14204">[SWS_TS_14204]</a> sind jedoch Fehler durch gleichzeitige Zugriffe aus parallelen Threads ausgeschlossen.</p>
