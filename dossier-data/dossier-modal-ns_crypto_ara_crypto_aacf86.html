<h4>Context</h4>
<p>The namespace <code>ara::crypto</code> forms the top interface layer of the cryptography architecture in AUTOSAR Adaptive (Release R25-11). It acts as a central entry point for applications and provides basic types, access factories, and the standardized error handling model. The actual cryptographic operations and certificate management are encapsulated in specialized sub-namespaces, while <code>ara::crypto</code> defines the higher-level constructs.</p>
<p>The core tasks of the namespace include:</p>
<ul>
<li><strong>Component factory functions:</strong> Provision of global loading functions for cryptographic providers (<a class="spec-record-ref" data-req="SWS_CRYPT_20099" href="../spec/record.html?id=SWS_CRYPT_20099">[SWS_CRYPT_20099]</a>), certificate providers (<a class="spec-record-ref" data-req="SWS_CRYPT_40099" href="../spec/record.html?id=SWS_CRYPT_40099">[SWS_CRYPT_40099]</a>), formatters (<a class="spec-record-ref" data-req="SWS_CRYPT_50200" href="../spec/record.html?id=SWS_CRYPT_50200">[SWS_CRYPT_50200]</a>), and persistent key slots (<a class="spec-record-ref" data-req="SWS_CRYPT_50004" href="../spec/record.html?id=SWS_CRYPT_50004">[SWS_CRYPT_50004]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50005" href="../spec/record.html?id=SWS_CRYPT_50005">[SWS_CRYPT_50005]</a>).</li>
<li><strong>Common memory and identification types:</strong> Abstraction of memory slices via <code>ReadOnlyMemRegion</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10033" href="../spec/record.html?id=SWS_CRYPT_10033">[SWS_CRYPT_10033]</a>) and <code>ReadWriteMemRegion</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10031" href="../spec/record.html?id=SWS_CRYPT_10031">[SWS_CRYPT_10031]</a>), definition of algorithm identifiers via <code>AlgId</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10014" href="../spec/record.html?id=SWS_CRYPT_10014">[SWS_CRYPT_10014]</a>) and <code>AlgIdString</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50000" href="../spec/record.html?id=SWS_CRYPT_50000">[SWS_CRYPT_50000]</a>), and timestamps via <code>Timestamp</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50003" href="../spec/record.html?id=SWS_CRYPT_50003">[SWS_CRYPT_50003]</a>).</li>
<li><strong>Policy and format constants:</strong> Definition of policy flags for key usages via <code>AllowedUsageFlags</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10015" href="../spec/record.html?id=SWS_CRYPT_10015">[SWS_CRYPT_10015]</a>), object types via <code>CryptoObjectType</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10016" href="../spec/record.html?id=SWS_CRYPT_10016">[SWS_CRYPT_10016]</a>), transformation directions with <code>CryptoTransform</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10019" href="../spec/record.html?id=SWS_CRYPT_10019">[SWS_CRYPT_10019]</a>), and serialization formats via <code>FormatId</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10701" href="../spec/record.html?id=SWS_CRYPT_10701">[SWS_CRYPT_10701]</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>The namespace <code>ara::crypto</code> itself has no global state machine or static initialization routine. Instead, the lifecycle model follows the on-demand retrieval of instances via stateless, thread-safe entry point factories:</p>
<ul>
<li><strong>Instantiation and ownership:</strong> Instances such as <code>cryp::CryptoProvider</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_20099" href="../spec/record.html?id=SWS_CRYPT_20099">[SWS_CRYPT_20099]</a>), <code>cryp::KeySlot</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50004" href="../spec/record.html?id=SWS_CRYPT_50004">[SWS_CRYPT_50004]</a>), <code>cryp::WriteableKeySlot</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50005" href="../spec/record.html?id=SWS_CRYPT_50005">[SWS_CRYPT_50005]</a>), and <code>Formatter</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50200" href="../spec/record.html?id=SWS_CRYPT_50200">[SWS_CRYPT_50200]</a>) are returned as shared pointers (<code>Sptr</code>) within an <code>ara::core::Result</code>. The lifetime of the objects is thus managed cooperatively via reference counting.</li>
<li><strong>Singleton pattern:</strong> For X.509 certificate management, <code>LoadX509Provider()</code> returns the existing or newly created instance of the singleton provider (<a class="spec-record-ref" data-req="SWS_CRYPT_40099" href="../spec/record.html?id=SWS_CRYPT_40099">[SWS_CRYPT_40099]</a>).</li>
<li><strong>Port binding:</strong> Providers and key slots are loaded via an <code>ara::core::InstanceSpecifier</code>. This binds the instantiation to the port prototypes of the current process modeled in the AUTOSAR manifest.</li>
<li><strong>Concurrency:</strong> All factory functions are specified as <code>noexcept</code> and thread-safe, so that concurrent instantiation calls from multiple threads are unproblematic.</li>
</ul>

<h4>Usage Path</h4>
<p>A typical usage path begins with obtaining the base instances via <code>ara::crypto</code> and subsequently leads to the preparation of operations and buffers using the basic types of the namespace:</p>
<ol>
<li><strong>Loading providers and key storage:</strong> The application calls <code>LoadCryptoProvider()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_20099" href="../spec/record.html?id=SWS_CRYPT_20099">[SWS_CRYPT_20099]</a>) with the <code>InstanceSpecifier</code> of the configured crypto port. If existing keys are to be loaded, <code>LoadKeySlot()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50004" href="../spec/record.html?id=SWS_CRYPT_50004">[SWS_CRYPT_50004]</a>) or <code>LoadWriteableKeySlot()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50005" href="../spec/record.html?id=SWS_CRYPT_50005">[SWS_CRYPT_50005]</a>) is used in parallel.</li>
<li><strong>Defining usage policies and transformation:</strong> Created keys and crypto objects are subject to permission masks of type <code>AllowedUsageFlags</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10015" href="../spec/record.html?id=SWS_CRYPT_10015">[SWS_CRYPT_10015]</a>). To safeguard operations, flags such as <code>kAllowDataEncryption</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13101" href="../spec/record.html?id=SWS_CRYPT_13101">[SWS_CRYPT_13101]</a>), <code>kAllowDataDecryption</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13102" href="../spec/record.html?id=SWS_CRYPT_13102">[SWS_CRYPT_13102]</a>), <code>kAllowMac</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50001" href="../spec/record.html?id=SWS_CRYPT_50001">[SWS_CRYPT_50001]</a>), <code>kAllowSigGeneration</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13103" href="../spec/record.html?id=SWS_CRYPT_13103">[SWS_CRYPT_13103]</a>), <code>kAllowSigVerification</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13104" href="../spec/record.html?id=SWS_CRYPT_13104">[SWS_CRYPT_13104]</a>), <code>kAllowKeyAgreement</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13105" href="../spec/record.html?id=SWS_CRYPT_13105">[SWS_CRYPT_13105]</a>), <code>kAllowKeyDerivation</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13106" href="../spec/record.html?id=SWS_CRYPT_13106">[SWS_CRYPT_13106]</a>), <code>kAllowKeyWrapping</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_13108" href="../spec/record.html?id=SWS_CRYPT_13108">[SWS_CRYPT_13108]</a>), or <code>kAllowKeyUnwrapping</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50002" href="../spec/record.html?id=SWS_CRYPT_50002">[SWS_CRYPT_50002]</a>) are checked. Policies for protection level export are controlled via <code>kAllowPlaintextExport</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_40992" href="../spec/record.html?id=SWS_CRYPT_40992">[SWS_CRYPT_40992]</a>) and <code>kAllowSecuredExport</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_40991" href="../spec/record.html?id=SWS_CRYPT_40991">[SWS_CRYPT_40991]</a>), respectively. The transformation direction for symmetric or asymmetric processing is specified via <code>CryptoTransform::kEncrypt</code> or <code>CryptoTransform::kDecrypt</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10019" href="../spec/record.html?id=SWS_CRYPT_10019">[SWS_CRYPT_10019]</a>).</li>
<li><strong>Providing memory buffers:</strong> Input data is passed as <code>ReadOnlyMemRegion</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10033" href="../spec/record.html?id=SWS_CRYPT_10033">[SWS_CRYPT_10033]</a>); output data or in-out buffers are declared as <code>ReadWriteMemRegion</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10031" href="../spec/record.html?id=SWS_CRYPT_10031">[SWS_CRYPT_10031]</a>).</li>
<li><strong>Serialization and formatting:</strong> For exporting or importing crypto objects, a <code>Formatter</code> is instantiated via <code>LoadFormatter()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50200" href="../spec/record.html?id=SWS_CRYPT_50200">[SWS_CRYPT_50200]</a>). The encoding is determined by <code>FormatId</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10701" href="../spec/record.html?id=SWS_CRYPT_10701">[SWS_CRYPT_10701]</a>): <code>kProprietaryFormat</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_60016" href="../spec/record.html?id=SWS_CRYPT_60016">[SWS_CRYPT_60016]</a>), <code>kFormatRawValueOnly</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_60017" href="../spec/record.html?id=SWS_CRYPT_60017">[SWS_CRYPT_60017]</a>), <code>kFormatDerEncoded</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_60018" href="../spec/record.html?id=SWS_CRYPT_60018">[SWS_CRYPT_60018]</a>), or <code>kFormatPemEncoded</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_60019" href="../spec/record.html?id=SWS_CRYPT_60019">[SWS_CRYPT_60019]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>Error handling in <code>ara::crypto</code> is based on the AUTOSAR standard <code>ara::core::ErrorCode</code>. A dedicated error domain is defined for the namespace, which is referenced via <code>GetCryptoErrorDomain()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_19952" href="../spec/record.html?id=SWS_CRYPT_19952">[SWS_CRYPT_19952]</a>) and instantiated with <code>MakeErrorCode()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_19951" href="../spec/record.html?id=SWS_CRYPT_19951">[SWS_CRYPT_19951]</a>). The enumeration <code>CryptoErrc</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10099" href="../spec/record.html?id=SWS_CRYPT_10099">[SWS_CRYPT_10099]</a>) classifies typical failure scenarios:</p>
<ul>
<li><strong>Configuration and port errors:</strong> If an <code>InstanceSpecifier</code> passed to <code>LoadCryptoProvider()</code>, <code>LoadKeySlot()</code>, or <code>LoadWriteableKeySlot()</code> does not point to a port prototype modeled for the current process, a <code>ProcessMappingViolation</code> is present (<a class="spec-record-ref" data-req="SWS_CRYPT_20099" href="../spec/record.html?id=SWS_CRYPT_20099">[SWS_CRYPT_20099]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50004" href="../spec/record.html?id=SWS_CRYPT_50004">[SWS_CRYPT_50004]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50005" href="../spec/record.html?id=SWS_CRYPT_50005">[SWS_CRYPT_50005]</a>).</li>
<li><strong>State and execution sequence:</strong> Incorrect operation sequences on crypto contexts are signaled by <code>CryptoErrc::kInvalidUsageOrder</code>, <code>CryptoErrc::kUninitializedContext</code>, <code>CryptoErrc::kProcessingNotStarted</code>, and <code>CryptoErrc::kProcessingNotFinished</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10099" href="../spec/record.html?id=SWS_CRYPT_10099">[SWS_CRYPT_10099]</a>).</li>
<li><strong>Buffer and parameter checks:</strong> Faulty arguments lead to <code>CryptoErrc::kInvalidArgument</code>, <code>CryptoErrc::kIncompatibleArguments</code>, or <code>CryptoErrc::kOutOfBounds</code>. If the output buffer is insufficient, <code>CryptoErrc::kInsufficientCapacity</code> is reported; the system acknowledges unsuitable input sizes with <code>CryptoErrc::kInvalidInputSize</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10099" href="../spec/record.html?id=SWS_CRYPT_10099">[SWS_CRYPT_10099]</a>).</li>
<li><strong>Integrity and policy violations:</strong> If verification of an authentication tag fails, the component reports <code>CryptoErrc::kAuthTagNotValid</code>. If the requested operation contradicts the <code>AllowedUsageFlags</code> stored in the key, <code>CryptoErrc::kUsageViolation</code> is triggered. Incompatible objects produce <code>CryptoErrc::kIncompatibleObject</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10099" href="../spec/record.html?id=SWS_CRYPT_10099">[SWS_CRYPT_10099]</a>).</li>
<li><strong>Container and storage issues:</strong> Access to unpopulated slots is indicated via <code>CryptoErrc::kEmptyKeySlot</code> and <code>CryptoErrc::kEmptyCertificateSlot</code>, respectively; unsupported serialization formats lead to <code>CryptoErrc::kUnsupportedFormat</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_10099" href="../spec/record.html?id=SWS_CRYPT_10099">[SWS_CRYPT_10099]</a>).</li>
</ul>
<p class="ai-note">This guide is based on the requirements of the AUTOSAR Adaptive specification for cryptography (Release R25-11).</p>
