<h4>Context</h4>
<p>The class <code>&lt;SI-Namespace&gt;::skeleton::events::&lt;Event&gt;</code> forms the server-side interface for providing and publishing events within AUTOSAR Adaptive Communication Management. Within a service-oriented system architecture, it functions as a channel of a service provider (Service Provider / Skeleton) through which data elements are propagated to interested service consumers (clients).</p>
<p>Essentially three parties are involved in the interaction:</p>
<ul>
<li><strong>Service provider application (skeleton):</strong> Creates or updates application data, requests memory buffers when needed, and initiates the transmission.</li>
<li><strong>Communication Management (ara::com):</strong> Executes the actual message transport over the underlying transmission media, manages allocation resources, and reports changes in subscription status to the provider.</li>
<li><strong>Service consumer applications (subscribers):</strong> Receive the event messages after successful subscription on the client side.</li>
</ul>
<p>The concrete payload data type for an event is specified via the type alias <code>SampleType</code>, which corresponds to the C++ implementation data type (<code>CppImplementationDataType</code>) of the underlying data prototype (<a class="spec-record-ref" data-req="SWS_CM_11400" href="../spec/record.html?id=SWS_CM_11400">[SWS_CM_11400]</a>).</p>

<h4>Lifecycle</h4>
<p>Instances of <code>&lt;SI-Namespace&gt;::skeleton::events::&lt;Event&gt;</code> are part of the generated service skeleton class. Their lifetime is bound to the parent skeleton instance that represents the service. Sending events is only permitted once the parent service has been offered in the communication network via <code>OfferService()</code> (<a class="spec-record-ref" data-req="SWS_CM_00162" href="../spec/record.html?id=SWS_CM_00162">[SWS_CM_00162]</a>, <a class="spec-record-ref" data-req="SWS_CM_90437" href="../spec/record.html?id=SWS_CM_90437">[SWS_CM_90437]</a>).</p>
<p>Regarding the memory and ownership semantics of the event data, the class provides two different mechanisms:</p>
<ul>
<li><strong>Value-based passing:</strong> When <code>Send(&lt;SSampleDerivedType&gt; data)</code> is called, management of the original instance remains with the application. Communication Management creates an internal copy of the passed value and transmits it to all subscribers (<a class="spec-record-ref" data-req="SWS_CM_00162" href="../spec/record.html?id=SWS_CM_00162">[SWS_CM_00162]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">AUTOSAR_AP_EXP_ARAComAPI p. 10</a>).</li>
<li><strong>Memory management by Communication Management (Zero-Copy):</strong> Via <code>Allocate()</code>, the application requests a memory area for the event and receives a <code>ara::com::SampleAllocateePtr&lt;SampleType&gt;</code> (<a class="spec-record-ref" data-req="SWS_CM_90438" href="../spec/record.html?id=SWS_CM_90438">[SWS_CM_90438]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">AUTOSAR_AP_EXP_ARAComAPI p. 10</a>). Responsibility for the buffer lies with the framework. As soon as the pointer is passed using <code>Send(ara::com::SampleAllocateePtr&lt;SampleType&gt; data)</code> (<a class="spec-record-ref" data-req="SWS_CM_90437" href="../spec/record.html?id=SWS_CM_90437">[SWS_CM_90437]</a>), ownership transfers completely to Communication Management; any further access to the data after sending is prohibited for the application.</li>
</ul>
<p>To track changes in the client subscription status asynchronously, a callback can be registered via <code>SetSubscriptionStateChangeHandler</code> (<a class="spec-record-ref" data-req="SWS_CM_12008" href="../spec/record.html?id=SWS_CM_12008">[SWS_CM_12008]</a>). For scenarios with dedicated execution contexts, an overload with <code>ExecutorT</code> exists (<a class="spec-record-ref" data-req="SWS_CM_12009" href="../spec/record.html?id=SWS_CM_12009">[SWS_CM_12009]</a>). Deregistration of the callback is performed via <code>UnsetSubscriptionStateChangeHandler</code> (<a class="spec-record-ref" data-req="SWS_CM_12010" href="../spec/record.html?id=SWS_CM_12010">[SWS_CM_12010]</a>). In addition, the status can be queried synchronously at any time with <code>GetSubscriptionState</code> (<a class="spec-record-ref" data-req="SWS_CM_12011" href="../spec/record.html?id=SWS_CM_12011">[SWS_CM_12011]</a>).</p>

<h4>Usage Path</h4>
<p>The typical interaction for publishing events comprises monitoring the subscription status, buffer reservation, and the actual send operation:</p>
<ol>
<li><strong>Register status handler (optional):</strong> The application registers a callback with <code>SetSubscriptionStateChangeHandler</code> (<a class="spec-record-ref" data-req="SWS_CM_12008" href="../spec/record.html?id=SWS_CM_12008">[SWS_CM_12008]</a>, <a class="spec-record-ref" data-req="SWS_CM_12009" href="../spec/record.html?id=SWS_CM_12009">[SWS_CM_12009]</a>) in order to be informed of state changes (such as the first incoming subscription).</li>
<li><strong>Check subscription:</strong> Before expensive data acquisition, <code>GetSubscriptionState()</code> can be used to check whether there are any active subscriptions at all (<a class="spec-record-ref" data-req="SWS_CM_12011" href="../spec/record.html?id=SWS_CM_12011">[SWS_CM_12011]</a>).</li>
<li><strong>Request buffer memory:</strong> When using zero-copy transmission, the application calls <code>Allocate()</code> and receives a <code>ara::com::SampleAllocateePtr&lt;SampleType&gt;</code> (<a class="spec-record-ref" data-req="SWS_CM_90438" href="../spec/record.html?id=SWS_CM_90438">[SWS_CM_90438]</a>).</li>
<li><strong>Populate payload:</strong> The application writes the payload data to be transmitted directly into the allocated memory area.</li>
<li><strong>Send event:</strong> The application calls <code>Send()</code> and passes the pointer (<a class="spec-record-ref" data-req="SWS_CM_90437" href="../spec/record.html?id=SWS_CM_90437">[SWS_CM_90437]</a>) or directly the value copy (<a class="spec-record-ref" data-req="SWS_CM_00162" href="../spec/record.html?id=SWS_CM_00162">[SWS_CM_00162]</a>). The method call confirms success via a <code>ara::core::Result&lt;void&gt;</code>.</li>
<li><strong>Cleanup:</strong> Upon termination of the provider, the callback is deregistered via <code>UnsetSubscriptionStateChangeHandler()</code> if necessary (<a class="spec-record-ref" data-req="SWS_CM_12010" href="../spec/record.html?id=SWS_CM_12010">[SWS_CM_12010]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>For the operations of the event class, specific error codes and specification violations must be observed:</p>
<ul>
<li><strong>Service not offered (<code>ComErrc::kServiceNotOffered</code>):</strong> If <code>Send()</code> is called before the service has been published via <code>OfferService()</code>, the call fails and returns this error code in <code>ara::core::Result</code> (<a class="spec-record-ref" data-req="SWS_CM_00162" href="../spec/record.html?id=SWS_CM_00162">[SWS_CM_00162]</a>, <a class="spec-record-ref" data-req="SWS_CM_90437" href="../spec/record.html?id=SWS_CM_90437">[SWS_CM_90437]</a>).</li>
<li><strong>Minimum send interval violation (<code>ComErrc::kMinimumSendIntervalViolationError</code>):</strong> Occurs if consecutive <code>Send()</code> calls are issued faster than configured in the deployment model via <code>ServiceInterfaceDeploymentElement.minimumSendInterval</code> (<a class="spec-record-ref" data-req="SWS_CM_00162" href="../spec/record.html?id=SWS_CM_00162">[SWS_CM_00162]</a>, <a class="spec-record-ref" data-req="SWS_CM_90437" href="../spec/record.html?id=SWS_CM_90437">[SWS_CM_90437]</a>).</li>
<li><strong>Insufficient memory resources (<code>SampleAllocationViolation</code>):</strong> If the provision of buffer memory fails during <code>Allocate()</code> due to a lack of resources, a violation is reported. The method is specified as not exception-safe (<code>not exception safe</code>) (<a class="spec-record-ref" data-req="SWS_CM_90438" href="../spec/record.html?id=SWS_CM_90438">[SWS_CM_90438]</a>).</li>
<li><strong>Faulty allocator (<code>AllocateUsageViolation</code>):</strong> Occurs if buffer allocation is erroneously performed via an impermissible user-defined allocator (<a class="spec-record-ref" data-req="SWS_CM_90438" href="../spec/record.html?id=SWS_CM_90438">[SWS_CM_90438]</a>).</li>
<li><strong>Invalid callback handler (<code>InvalidHandlerViolation</code>):</strong> Passing an empty or non-callable callback to <code>SetSubscriptionStateChangeHandler</code> results in this specification violation (<a class="spec-record-ref" data-req="SWS_CM_12008" href="../spec/record.html?id=SWS_CM_12008">[SWS_CM_12008]</a>, <a class="spec-record-ref" data-req="SWS_CM_12009" href="../spec/record.html?id=SWS_CM_12009">[SWS_CM_12009]</a>).</li>
</ul>
