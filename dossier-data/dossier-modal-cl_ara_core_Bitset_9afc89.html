  <h4>Context</h4>
  <p>
    The class template <code>ara::core::Bitset&lt;std::size_t N&gt;</code> provides an adaptation of the standard type <code>std::bitset</code> for safety-related automotive software in the <code>core</code> module of the AUTOSAR Adaptive Platform. It is declared via the header file <code>ara/core/bitset.h</code>. It serves for the efficient management and bitwise manipulation of fixed-length bit sequences <code>N</code>.
  </p>
  <p>
    Compared to the ISO C++ model, <code>ara::core::Bitset</code> features targeted adaptations to the fault-tolerant and exception-free programming model of AUTOSAR. This particularly concerns the interaction with platform-specific data types such as <code>ara::core::BasicString</code>, the return of <code>ara::core::Result</code> for synchronous error reporting in positional operations, as well as dedicated conversion functions to fixed widths of integer types.
  </p>

    Instances of <code>ara::core::Bitset</code> are characterized by strictly regulated lifecycle behavior without dynamic memory management for the bit vector. Initialization can occur via various paths:
  </p>
  <ul>
    <li>
      <strong>Default initialization:</strong> The parameterless default constructor <a class="spec-record-ref" data-req="SWS_CORE_01713" href="../spec/record.html?id=SWS_CORE_01713">[SWS_CORE_01713]</a> is declared as <code>constexpr</code> and <code>noexcept</code> and pre-initializes all <code>N</code> bits with the value zero.
    </li>
    <li>
      <strong>Integer initialization:</strong> Via the constructor <a class="spec-record-ref" data-req="SWS_CORE_01719" href="../spec/record.html?id=SWS_CORE_01719">[SWS_CORE_01719]</a>, a bitset can be created from a value of type <code>unsigned long long</code>, likewise as <code>constexpr</code> and <code>noexcept</code>.
    </li>
    <li>

In addition, there is a constructor for classic C strings via pointers of type <code>const CharT*</code> <a class="spec-record-ref" data-req="SWS_CORE_01750" href="../spec/record.html?id=SWS_CORE_01750">[SWS_CORE_01750]</a>, which is classified as not exception-safe (<em>not exception safe</em>).

  <h4>Error Scenarios</h4>

  <ul>
    <li>
      <strong>Position violations (out of range):</strong> The positioned modifiers <code>set(pos, val)</code> <a class="spec-record-ref" data-req="SWS_CORE_01726" href="../spec/record.html?id=SWS_CORE_01726">[SWS_CORE_01726]</a>, <code>reset(pos)</code> <a class="spec-record-ref" data-req="SWS_CORE_01728" href="../spec/record.html?id=SWS_CORE_01728">[SWS_CORE_01728]</a>, and <code>flip(pos)</code> <a class="spec-record-ref" data-req="SWS_CORE_01731" href="../spec/record.html?id=SWS_CORE_01731">[SWS_CORE_01731]</a> return a <code>ara::core::Result</code>. If <code>pos</code> does not represent a valid bit position, the violation <code>IsoStdOutOfRangeViolation</code> is triggered (instead of <code>std::out_of_range</code>). The query function <code>test(pos)</code> <a class="spec-record-ref" data-req="SWS_CORE_01743" href="../spec/record.html?id=SWS_CORE_01743">[SWS_CORE_01743]</a> also triggers <code>IsoStdOutOfRangeViolation</code> in case of an invalid position.
    </li>
    <li>

If the analyzed string contains a character that corresponds to neither zero nor one, <code>IsoStdInvalidArgumentViolation</code> is signaled (instead of <code>std::invalid_argument</code>).
    </li>
    <li>
      <strong>Conversion overflows:</strong> If the integer value represented in the bitset cannot be represented in the respective return type, the conversion functions <code>to_ulong()</code> <a class="spec-record-ref" data-req="SWS_CORE_01734" href="../spec/record.html?id=SWS_CORE_01734">[SWS_CORE_01734]</a>, <code>to_ullong()</code> <a class="spec-record-ref" data-req="SWS_CORE_01735" href="../spec/record.html?id=SWS_CORE_01735">[SWS_CORE_01735]</a> as well as <code>to_uint8t()</code> <a class="spec-record-ref" data-req="SWS_CORE_01736" href="../spec/record.html?id=SWS_CORE_01736">[SWS_CORE_01736]</a>, <code>to_uint16t()</code> <a class="spec-record-ref" data-req="SWS_CORE_01737" href="../spec/record.html?id=SWS_CORE_01737">[SWS_CORE_01737]</a>, <code>to_uint32t()</code> <a class="spec-record-ref" data-req="SWS_CORE_01738" href="../spec/record.html?id=SWS_CORE_01738">[SWS_CORE_01738]</a>, and <code>to_uint64t()</code> <a class="spec-record-ref" data-req="SWS_CORE_01739" href="../spec/record.html?id=SWS_CORE_01739">[SWS_CORE_01739]</a> trigger violation <code>IsoStdOverflowErrorViolation</code> (instead of <code>std::overflow_error</code>).
    </li>
    <li>
      <strong>Exception safety:</strong> While almost all functions of the class are specified as <code>exception safe</code>, the constructor from <code>const CharT*</code> <a class="spec-record-ref" data-req="SWS_CORE_01750" href="../spec/record.html?id=SWS_CORE_01750">[SWS_CORE_01750]</a> and <code>to_string()</code> <a class="spec-record-ref" data-req="SWS_CORE_01751" href="../spec/record.html?id=SWS_CORE_01751">[SWS_CORE_01751]</a> are explicitly classified as <em>not exception safe</em>, presumably due to dynamic memory allocations during string processing.
    </li>
  </ul>
