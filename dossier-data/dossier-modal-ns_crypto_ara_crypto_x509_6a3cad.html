<div class="ai-level" data-ai-level="2">
<p>Der Namespace <code>ara::crypto::x509</code> stellt Schnittstellen und Datentypen zur Verwaltung, Nutzungsdefinition und Validierung von X.509-Zertifikaten sowie OCSP-Antworten in AUTOSAR Adaptive bereit. Über den Validierungskontext <code>CertificateValidationCtx</code> werden Zertifikatspfade parametrisiert anhand von Optionen wie <code>CertificateValidationOptions</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50107" href="../spec/record.html?id=SWS_CRYPT_50107">[SWS_CRYPT_50107]</a> geprüft. Das Ergebnis wird strukturiert über Statuswerte wie <code>CertificateValidationStatus</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40203" href="../spec/record.html?id=SWS_CRYPT_40203">[SWS_CRYPT_40203]</a> zurückgemeldet, wobei Online-Widerrufsprüfungen per Voreinstellung inaktiv sind und explizit konfiguriert werden müssen.</p>

<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Der Namespace <code>ara::crypto::x509</code> stellt die zentralen Schnittstellen und Datentypen zur Verarbeitung und Validierung von X.509-Zertifikatsstrukturen in der AUTOSAR Adaptive Platform bereit. Das Schnittstellenmodell umfasst die Repräsentation digitaler Zertifikate (<code>Certificate</code>), Zertifikatssignierungsanfragen (<code>CertSignRequest</code>), Distinguished Names (<code>X509DN</code>) sowie OCSP-Antworten (<code>OcspResponse</code>). Die Instanziierung und Verwaltung dieser kryptografischen Artefakte erfolgt typischerweise über das Provider-Interface <code>X509Provider</code> (Interpretation: Der Provider fungiert als zentrale Fabrikinstanz für X.509-Objekte).</p>
<p>Für Zertifikate definiert der Namespace standardisierte Schlüsselverwendungszwecke über den Typ <code>X509KeyUsage</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40101" href="../spec/record.html?id=SWS_CRYPT_40101">[SWS_CRYPT_40101]</a>. Zu den Bit-Konstanten zählen die Erzeugung digitaler Signaturen <code>kConstrDigitalSignature</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40151" href="../spec/record.html?id=SWS_CRYPT_40151">[SWS_CRYPT_40151]</a>, Nicht-Abstreitbarkeit <code>kConstrNonRepudiation</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40152" href="../spec/record.html?id=SWS_CRYPT_40152">[SWS_CRYPT_40152]</a>, Schlüsselverschlüsselung <code>kConstrKeyEncipherment</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40153" href="../spec/record.html?id=SWS_CRYPT_40153">[SWS_CRYPT_40153]</a>, Datenverschlüsselung <code>kConstrDataEncipherment</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40154" href="../spec/record.html?id=SWS_CRYPT_40154">[SWS_CRYPT_40154]</a>, Schlüsselvereinbarung <code>kConstrKeyAgreement</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40155" href="../spec/record.html?id=SWS_CRYPT_40155">[SWS_CRYPT_40155]</a>, Zertifikatsignierung <code>kConstrKeyCertSign</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40156" href="../spec/record.html?id=SWS_CRYPT_40156">[SWS_CRYPT_40156]</a>, CRL-Signierung <code>kConstrCrlSign</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40157" href="../spec/record.html?id=SWS_CRYPT_40157">[SWS_CRYPT_40157]</a> sowie reine Verschlüsselung <code>kConstrEncipherOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40158" href="../spec/record.html?id=SWS_CRYPT_40158">[SWS_CRYPT_40158]</a> und Entschlüsselung <code>kConstrDecipherOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40159" href="../spec/record.html?id=SWS_CRYPT_40159">[SWS_CRYPT_40159]</a>. Ergänzend beschreibt <code>X509ExtendedKeyUsage</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50097" href="../spec/record.html?id=SWS_CRYPT_50097">[SWS_CRYPT_50097]</a> erweiterte Einsatzzwecke wie TLS-Server-Authentifizierung <code>kServerAuth</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50098" href="../spec/record.html?id=SWS_CRYPT_50098">[SWS_CRYPT_50098]</a>, TLS-Client-Authentifizierung <code>kClientAuth</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50099" href="../spec/record.html?id=SWS_CRYPT_50099">[SWS_CRYPT_50099]</a>, Codesignierung <code>kCodeSigning</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50100" href="../spec/record.html?id=SWS_CRYPT_50100">[SWS_CRYPT_50100]</a>, E-Mail-Schutz <code>kEmailProtection</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50101" href="../spec/record.html?id=SWS_CRYPT_50101">[SWS_CRYPT_50101]</a>, Zeitstempeldienste <code>kTimeStamping</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50102" href="../spec/record.html?id=SWS_CRYPT_50102">[SWS_CRYPT_50102]</a> und OCSP-Signierung <code>kOCSPSigning</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50103" href="../spec/record.html?id=SWS_CRYPT_50103">[SWS_CRYPT_50103]</a>.</p>

<h4>Nutzungspfad</h4>
<p>Der primäre operative Ablauf im Namespace besteht in der Prüfung von Zertifikatspfaden über <code>CertificateValidationCtx</code>. Das Validierungsverhalten wird über Bitmasken vom Typ <code>CertificateValidationOptions</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50107" href="../spec/record.html?id=SWS_CRYPT_50107">[SWS_CRYPT_50107]</a> parametrisiert. Standardmäßig erfolgt die Pfadprüfung ohne Einbindung von Online-Zertifikatsstatusabfragen über die Option <code>kOcspOff</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50114" href="../spec/record.html?id=SWS_CRYPT_50114">[SWS_CRYPT_50114]</a>. Soll die Gültigkeit online verifiziert werden, kann entweder die Prüfung der gesamten Kette über <code>kOcspResponseCompleteChain</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50112" href="../spec/record.html?id=SWS_CRYPT_50112">[SWS_CRYPT_50112]</a> oder ausschließlich für das Zielzertifikat mittels <code>kOcspResponseTargetOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50113" href="../spec/record.html?id=SWS_CRYPT_50113">[SWS_CRYPT_50113]</a> aktiviert werden.</p>
<p>Für spezifische Prüfszenarien erlauben weitere Validierungsoptionen das Übersteuern von Standardprüfungen: So können zeitliche Gültigkeitsgrenzen über <code>kIgnoreNotBefore</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50108" href="../spec/record.html?id=SWS_CRYPT_50108">[SWS_CRYPT_50108]</a> und <code>kIgnoreNotAfter</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50109" href="../spec/record.html?id=SWS_CRYPT_50109">[SWS_CRYPT_50109]</a> ignoriert werden. Ebenso lässt sich die Auswertung zuvor importierter Zertifikatswiderrufslisten (CRL) mit <code>kIgnoreCrl</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50111" href="../spec/record.html?id=SWS_CRYPT_50111">[SWS_CRYPT_50111]</a> abschalten oder die Fehlersignalisierung bei unbekannten kritischen Erweiterungen via <code>kIgnoreUnknownCriticalExtensions</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50110" href="../spec/record.html?id=SWS_CRYPT_50110">[SWS_CRYPT_50110]</a> unterdrücken. Nach Durchführung der Validierung liefert der Kontext ein Ergebnisobjekt <code>CertificateValidationResult</code> zurück (Interpretation: Der Validierungsaufruf bindet Zielzertifikat, Prüfoptionen und optionale OCSP-Antworten ein und kapselt das Resultat in der Ergebnisklasse).</p>

<h4>Fehlerszenarien</h4>
<p>Das Ergebnis einer Zertifikatspfadprüfung wird über die Enumeration <code>CertificateValidationStatus</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40203" href="../spec/record.html?id=SWS_CRYPT_40203">[SWS_CRYPT_40203]</a> detailliert aufgeschlüsselt. Eine erfolgreiche Validierung wird durch <code>kValid</code> (= 0) signalisiert. Schlägt die Prüfung fehl, kennzeichnen spezifische Statuswerte die genaue Ursache:</p>
<ul>
<li><code>kInvalidSignature</code> (= 1): Eine Signatur innerhalb des Zertifikatspfads konnte nicht erfolgreich verifiziert werden.</li>
<li><code>kNoPathToTrustedCertificate</code> (= 3): Es konnte kein Pfad zu einem als vertrauenswürdig eingestuften Wurzelzertifikat aufgebaut werden.</li>
<li><code>kExpired</code> (= 4): Das Zertifikat hat die Gültigkeitsdauer überschritten (Feld <code>notAfter</code>).</li>
<li><code>kFuture</code> (= 5): Die Gültigkeitsdauer des Zertifikats hat gemäß dem Feld <code>notBefore</code> noch nicht begonnen.</li>
<li><code>kRevoked</code> (= 6): Das Zertifikat wurde widerrufen; dieser Status resultiert aus importierten CRLs oder einer aktiven OCSP-Prüfung via <code>kOcspResponseCompleteChain</code> oder <code>kOcspResponseTargetOnly</code>.</li>
<li><code>kUnknownOcspStatus</code> (= 7): Eine eingebundene OCSP-Antwort liefert für das Zertifikat den Zustand „unknown“.</li>
<li><code>kUnknownCriticalExtension</code> (= 8): Ein Zertifikat enthält eine unbekannte kritische Erweiterung, die weder durch <code>kIgnoreUnknownCriticalExtensions</code> noch durch Vorab-Ausnahmebehandlung ignoriert wurde.</li>
</ul>
<p>Sofern im Validierungsprozess Online-Statusabfragen verarbeitet werden, signalisiert die Enumeration <code>OcspResponseStatus</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40001" href="../spec/record.html?id=SWS_CRYPT_40001">[SWS_CRYPT_40001]</a> das Resultat des Protokollabrufs. Neben einer erfolgreichen Antwortbestätigung (<code>kSuccessful</code> = 0) können protokollarische und serverseitige Fehler auftreten: ungültige Anfragen (<code>kMalformedRequest</code> = 1), interne Fehler des Ausstellers (<code>kInternalError</code> = 2), temporäre Überlastung (<code>kTryLater</code> = 3), die Notwendigkeit einer Signatur (<code>kSigRequired</code> = 5) oder fehlende Autorisierung (<code>kUnauthorized</code> = 6).</p>
