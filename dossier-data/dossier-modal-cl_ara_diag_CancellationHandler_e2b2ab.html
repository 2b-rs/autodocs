<h4>Context</h4>
<p>The class <code>ara::diag::CancellationHandler</code> provides a shared state within module <code>diag</code> of the AUTOSAR Adaptive Platform to signal whether the ongoing execution of a diagnostic service shall be canceled <a class="spec-record-ref" data-req="SWS_DM_00608" href="../spec/record.html?id=SWS_DM_00608">[SWS_DM_00608]</a>. It acts as a communication link between the central diagnostic management and the concrete service execution.</p>
<p>The primary interaction partners include the server instance of Diagnostic Management (DM), the superordinate diagnostic conversation (<code>Diagnostic Conversation</code>), and the respective service provider or service processor (such as for application-specific UDS services according to <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=191">AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.24 “Custom Diagnostic Services”</a> and <a class="spec-record-ref" data-req="SWS_DM_00983" href="../spec/record.html?id=SWS_DM_00983">[SWS_DM_00983]</a>). If a diagnostic conversation aborts while a service request is being processed internally or before a response has been sent, the specification requires the DM core to cancel the started activity as far as possible and to prevent responses from being sent <a class="spec-record-ref" data-req="SWS_DM_00278" href="../spec/record.html?id=SWS_DM_00278">[SWS_DM_00278]</a> <a class="spec-record-ref" data-req="SWS_DM_00279" href="../spec/record.html?id=SWS_DM_00279">[SWS_DM_00279]</a>. In this context, <code>CancellationHandler</code> serves as the interface through which this cancellation request is transmitted to the processing logic.</p>

<h4>Lifecycle</h4>
<p>The creation and management of <code>CancellationHandler</code> instances are subject to strict restrictions regarding ownership and instantiation:</p>
<ul>
<li><strong>Creation:</strong> The default constructor is deleted (<code>delete</code>). An instance must not be created by applications themselves, but is exclusively instantiated by the DM core <a class="spec-record-ref" data-req="SWS_DM_00609" href="../spec/record.html?id=SWS_DM_00609">[SWS_DM_00609]</a>.</li>
<li><strong>Copying and moving:</strong> Copy constructor <a class="spec-record-ref" data-req="SWS_DM_00611" href="../spec/record.html?id=SWS_DM_00611">[SWS_DM_00611]</a> and copy assignment operator <a class="spec-record-ref" data-req="SWS_DM_00613" href="../spec/record.html?id=SWS_DM_00613">[SWS_DM_00613]</a> are deleted, so that each instance exists as a unique instance. Move constructor <a class="spec-record-ref" data-req="SWS_DM_00610" href="../spec/record.html?id=SWS_DM_00610">[SWS_DM_00610]</a> and move assignment <a class="spec-record-ref" data-req="SWS_DM_00612" href="../spec/record.html?id=SWS_DM_00612">[SWS_DM_00612]</a>, on the other hand, are available as default implementations (<code>default</code>) and declared as <code>noexcept</code>.</li>
<li><strong>State transition:</strong> As long as the associated diagnostic conversation has not been cancelled in its current state, calling <code>IsCanceled()</code> returns the value <code>false</code> <a class="spec-record-ref" data-req="SWS_DM_00984" href="../spec/record.html?id=SWS_DM_00984">[SWS_DM_00984]</a>. If a cancellation of the conversation occurs, the state changes permanently: <code>IsCanceled()</code> returns <code>true</code> from then on until the <code>CancellationHandler</code> object is destroyed <a class="spec-record-ref" data-req="SWS_DM_00984" href="../spec/record.html?id=SWS_DM_00984">[SWS_DM_00984]</a>.</li>
<li><strong>Concurrency:</strong> The operations <code>IsCanceled()</code> <a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a> and <code>SetNotifier()</code> <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a> as well as the alias <code>CancellationHandlerSetNotifier</code> <a class="spec-record-ref" data-req="SWS_DM_02075" href="../spec/record.html?id=SWS_DM_02075">[SWS_DM_02075]</a> are explicitly specified as not thread-safe (<code>not thread-safe</code>).</li>
</ul>

<h4>Usage Path</h4>
<p>Interpretation: The instance of <code>CancellationHandler</code> is presumably typically passed to the service processor when service processing is invoked by the DM core. The processing application then has two complementary options for reacting to cancellation events:</p>
<ol>
<li><strong>Registration of a notification:</strong> A callback of type <code>CancellationHandlerSetNotifier</code> (corresponds to <code>std::function&lt;void(void)&gt;</code>) can be registered via <code>SetNotifier()</code> <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a> <a class="spec-record-ref" data-req="SWS_DM_02075" href="../spec/record.html?id=SWS_DM_02075">[SWS_DM_02075]</a>. This function is called as soon as the execution of the diagnostic service is cancelled in the DM.</li>
<li><strong>Polling the status:</strong> In the case of time-consuming computation steps or iterative processes, the application can synchronously query <code>IsCanceled()</code> <a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a>.</li>
<li><strong>Reaction to cancellation:</strong> As soon as the callback is triggered or <code>IsCanceled()</code> returns the value <code>true</code>, the application must terminate the started activity as soon as possible <a class="spec-record-ref" data-req="SWS_DM_00278" href="../spec/record.html?id=SWS_DM_00278">[SWS_DM_00278]</a>, because the overall system no longer performs any response transmission <a class="spec-record-ref" data-req="SWS_DM_00279" href="../spec/record.html?id=SWS_DM_00279">[SWS_DM_00279]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>In the context of errors and exceptions, the class exhibits the following characteristics:</p>
<ul>
<li><strong>Exception safety:</strong> The methods <code>IsCanceled()</code> and <code>SetNotifier()</code> as well as the move operations are specified as <code>noexcept</code> and exception-safe (<code>exception safe</code>) <a class="spec-record-ref" data-req="SWS_DM_00610" href="../spec/record.html?id=SWS_DM_00610">[SWS_DM_00610]</a> <a class="spec-record-ref" data-req="SWS_DM_00612" href="../spec/record.html?id=SWS_DM_00612">[SWS_DM_00612]</a> <a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a> <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a>. There are no dedicated error return values or fault memory entries.</li>
<li><strong>Multiple registration of notifiers:</strong> If an application calls <code>SetNotifier()</code> multiple times for the same instance, the DM silently overwrites the previously registered notifier <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a> <a class="spec-record-ref" data-req="SWS_DM_01348" href="../spec/record.html?id=SWS_DM_01348">[SWS_DM_01348]</a>. Earlier notifier callbacks are lost in the process.</li>
<li><strong>Violation of thread safety:</strong> Since the methods are not thread-safe <a class="spec-record-ref" data-req="SWS_DM_00614" href="../spec/record.html?id=SWS_DM_00614">[SWS_DM_00614]</a> <a class="spec-record-ref" data-req="SWS_DM_00615" href="../spec/record.html?id=SWS_DM_00615">[SWS_DM_00615]</a>, unprotected, concurrent access by multiple threads of execution to the same handler object leads to undefined behavior.</li>
</ul>
