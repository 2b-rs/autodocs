<p class="ai-level ai-oneliner-lead" data-ai-level="1">Stellt standardisierte kryptografische Rechen- und Schlüsselverwaltungsdienste über Hard- und Softwaretreiber bereit.</p>
<div class="ai-level" data-ai-level="2">
<p>Das Cluster bündelt die Module CSM, CryIf und Crypto Driver zur hardwareunabhängigen Bereitstellung kryptografischer Dienste und Schlüsselverwaltungsfunktionen in der AUTOSAR Classic Platform <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES">EXP_UtilizationOfCryptoServices S. 8</a>. Kryptografische Jobs werden über den CSM priorisiert, im CryIf auf logische Kanäle geroutet und im Crypto Driver synchron oder asynchron ausgeführt <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>. Schlüsselpersistierungen im NVM erfolgen aus Konsistenzgründen strikt erst nach erfolgreicher Validierung mittels KeySetValid <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM.html" data-snip="SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM">SWS_CryptoDriver S. 37</a>.</p>

</div>
<div class="ai-level" data-ai-level="3">
<p>Das Modulcluster „Crypto Services &amp; Hardware Abstraction“ umfasst die AUTOSAR Classic Module Crypto Service Manager (<code>csm</code>), Crypto Interface (<code>cryif</code>) und Crypto Driver (<code>crypto</code>) <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES">EXP_UtilizationOfCryptoServices S. 8</a>. Es stellt eine hardwareunabhängige Abstraktionsschicht für kryptografische Operationen (u.&nbsp;a. Verschlüsselung, Signaturen, MAC-Berechnung und Zufallszahlengenerierung) sowie für ein sicheres Schlüsselmanagement bereit <a class="spec-record-ref" data-req="SWS_Csm_00982" href="../spec/record.html?id=SWS_Csm_00982">[SWS_Csm_00982]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00984" href="../spec/record.html?id=SWS_Csm_00984">[SWS_Csm_00984]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER">SWS_CryptoDriver S. 15</a>.</p>

<p>Kryptografische Anforderungen werden als <code>Crypto_JobType</code> gekapselt, welcher Prioritäten, Ein- und Ausgabepuffer sowie Betriebsmodi (Start, Update, Finish für Streaming oder SingleCall) definiert <a class="spec-record-ref" data-req="SWS_Csm_01013" href="../spec/record.html?id=SWS_Csm_01013">[SWS_Csm_01013]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01039" href="../spec/record.html?id=SWS_Csm_01039">[SWS_Csm_01039]</a>. Der CSM nimmt Aufträge entgegen, ordnet sie softwareseitigen Warteschlangen zu und leitet sie über <code>CryIf_ProcessJob()</code> weiter <a class="spec-record-ref" data-req="SWS_Csm_00017" href="../spec/record.html?id=SWS_Csm_00017">[SWS_Csm_00017]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>. Das CryIf übernimmt das Kanal-Routing zu den Treibern und übersetzt CSM-Schlüsselkennungen in modulspezifische Treiber-Schlüssel-IDs <a class="spec-record-ref" data-req="SWS_CryIf_00133" href="../spec/record.html?id=SWS_CryIf_00133">[SWS_CryIf_00133]</a>.</p>

<h4>1. Systemarchitektur &amp; Rolle des Modulclusters</h4>
<p>Das Modulcluster „Crypto Services &amp; Hardware Abstraction“ bildet das funktionale Fundament für kryptografische Operationen, software- und hardwaregestützte Schlüsselverwaltung sowie sichere On-Board-Kommunikation in der AUTOSAR Classic Platform <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_4_1_UTILIZATIONOFCRYPTOSERVICES">EXP_UtilizationOfCryptoServices S. 8</a>. Die Architektur gliedert sich streng entlang des AUTOSAR-Schichtenmodells in drei standardisierte BSW-Module: den Crypto Service Manager (<code>csm</code>) in der Service-Schicht, das Crypto Interface (<code>cryif</code>) in der ECU Abstraction Layer sowie mindestens einen Crypto Driver (<code>crypto</code>) auf der Microcontroller Abstraction Layer (MCAL) <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER">SWS_CryptoDriver S. 15</a>. Dieses Schichtengefüge abstrahiert Sicherheitsanwendungen (beispielsweise SecOC, TLS-Verbindungsaufbauten und UDS-Diagnoseauthentifizierung) vollständig von proprietären Krypto-Coprozessoren wie Hardware Security Modules (HSM) oder Secure Hardware Extensions (SHE) <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_8_4_9_CSM_callback_interfaces.html" data-snip="SNIP_CLASSIC_CSM_SECTION_8_4_9_CSM_callback_interfaces">SWS_SecureOnboardCommunication S. 78</a>.</p>

<p>Der Crypto Service Manager (CSM) fungiert als primärer Diensteanbieter für Applikationskomponenten (SW-Cs) und höher gelagerte BSW-Module. Er stellt standardisierte Programmierschnittstellen für symmetrische und asymmetrische Algorithmen (z.&nbsp;B. AES, RSA), Hashing, Message Authentication Codes (MAC), Zufallszahlengenerierung (RNG) und AEAD-Verfahren bereit <a class="spec-record-ref" data-req="SWS_Csm_00980" href="../spec/record.html?id=SWS_Csm_00980">[SWS_Csm_00980]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00982" href="../spec/record.html?id=SWS_Csm_00982">[SWS_Csm_00982]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00984" href="../spec/record.html?id=SWS_Csm_00984">[SWS_Csm_00984]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01023" href="../spec/record.html?id=SWS_Csm_01023">[SWS_Csm_01023]</a>. Zudem realisiert der CSM softwareseitige Job-Warteschlangen und steuert die Priorisierung paralleler Krypto-Aufträge <a class="spec-record-ref" data-req="SWS_Csm_00022" href="../spec/record.html?id=SWS_Csm_00022">[SWS_Csm_00022]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing.html" data-snip="SNIP_CLASSIC_CSM_SECTION_7_2_2_2_2_Queuing">SWS_CryptoServiceManager S. 29</a>.</p>

<p>Das Crypto Interface (CryIf) stellt als Abstraktionsschicht eine einheitliche 1:n-Schnittstelle zwischen dem CSM und beliebig vielen Krypto-Treibern bereit. Seine zentrale Aufgabe ist das Dispatching: Es leitet Aufträge anhand konfigurierter logischer Kanäle (<code>channelId</code>) an die korrespondierende Crypto Driver Instanz weiter und transformiert logische Schlüsselreferenzen (<code>cryIfKeyId</code>) in treiberspezifische Identifikatoren (<code>cryptoKeyId</code>) <a class="spec-record-ref" data-req="SWS_CryIf_00133" href="../spec/record.html?id=SWS_CryIf_00133">[SWS_CryIf_00133]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>. Der Crypto Driver kapselt die physische Ausführungseinheit (Crypto Driver Object) und bedient entweder reine Software-Kryptoprimitive oder spezielle Hardware-Sicherheitsmodule <a class="spec-record-ref" data-req="SWS_Crypto_00224" href="../spec/record.html?id=SWS_Crypto_00224">[SWS_Crypto_00224]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER">SWS_CryptoDriver S. 15</a>.</p>

<h4>2. Zusammenspiel &amp; Interaktionspfade zwischen den Modulen</h4>
<p>Die Auftragsverarbeitung innerhalb des Clusters erfolgt primär über das job-basierte Modell mittels der Struktur <code>Crypto_JobType</code> <a class="spec-record-ref" data-req="SWS_Csm_01013" href="../spec/record.html?id=SWS_Csm_01013">[SWS_Csm_01013]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e39a11daf7b2d30c.html" data-snip="FIG-e39a11daf7b2d30c">AUTOSAR_CP_SWS_CryptoServiceManager S. 21</a>. Ein Krypto-Job bündelt die Job-ID, Prioritätsinformationen, Schlüsselreferenzen, primitive Metadaten und die Struktur <code>Crypto_JobPrimitiveInputOutputType</code> zur Zeigerverwaltung von Eingabe-, Ausgabe- und Längenparametern <a class="spec-record-ref" data-req="SWS_Csm_01012" href="../spec/record.html?id=SWS_Csm_01012">[SWS_Csm_01012]</a>. Durch das Bitmasken-Feld <code>Crypto_OperationModeType</code> (mit den Flags <code>START</code>, <code>UPDATE</code>, <code>FINISH</code>) wird gesteuert, ob ein Auftrag als zusammenhängender Einzelaufruf (<code>SINGLECALL</code>) oder inkrementell im Streaming-Modus berechnet wird <a class="spec-record-ref" data-req="SWS_Csm_01039" href="../spec/record.html?id=SWS_Csm_01039">[SWS_Csm_01039]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01029" href="../spec/record.html?id=SWS_Csm_01029">[SWS_Csm_01029]</a>.</p>

<p>Wird eine CSM-Dienstfunktion synchron aufgerufen, prüft der CSM den Jobstatus. Ist der Treiber frei oder der Auftrag als synchron konfiguriert, ruft der CSM direkt <code>CryIf_ProcessJob()</code> auf <a class="spec-record-ref" data-req="SWS_Csm_00017" href="../spec/record.html?id=SWS_Csm_00017">[SWS_Csm_00017]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>. Das CryIf mappt die Schlüssel-IDs und dispatcht den Job an die zugeordnete Treiberinstanz via <code>Crypto_ProcessJob()</code> <a class="spec-record-ref" data-req="SWS_CryIf_00133" href="../spec/record.html?id=SWS_CryIf_00133">[SWS_CryIf_00133]</a>. Bei asynchronen Anforderungen wird der Job bei belegtem Treiberobjekt in die CSM-Queue eingereiht <a class="spec-record-ref" data-req="SWS_Csm_00018" href="../spec/record.html?id=SWS_Csm_00018">[SWS_Csm_00018]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-0039ffd2482a3664.html" data-snip="FIG-0039ffd2482a3664">AUTOSAR_CP_SWS_CryptoServiceManager S. 30</a>. Nach Abschluss der asynchronen Treiberberechnung triggert der Treiber <code>CryIf_CallbackNotification()</code> <a class="spec-record-ref" data-req="SWS_CryIf_91013" href="../spec/record.html?id=SWS_CryIf_91013">[SWS_CryIf_91013]</a>, das CryIf leitet die Meldung an <code>Csm_CallbackNotification()</code> weiter <a class="spec-record-ref" data-req="SWS_Csm_00970" href="../spec/record.html?id=SWS_Csm_00970">[SWS_Csm_00970]</a>, und der CSM benachrichtigt schließlich die anfordernde Anwendung über deren konfigurierten Callback <a class="spec-record-ref" data-req="SWS_Csm_01044" href="../spec/record.html?id=SWS_Csm_01044">[SWS_Csm_01044]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00928" href="../spec/record.html?id=SWS_Csm_00928">[SWS_Csm_00928]</a>.</p>

<p>Neben der primären Krypto-Ausführung bildet das Schlüsselmanagement einen integralen Interaktionspfad des Clusters <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_SECTION_7_2_3_Design_Notes.html" data-snip="SNIP_CLASSIC_CRYPTO_SECTION_7_2_3_Design_Notes">SWS_CryptoDriver S. 24</a>. Der Zugriff auf Schlüsselelemente wird dabei streng anhand konfigurierter Zugriffsrechte (<code>CRYPTO_RA_ALLOWED</code>, <code>CRYPTO_RA_ENCRYPTED</code>, <code>CRYPTO_RA_INTERNAL_COPY</code>) überwacht <a class="spec-record-ref" data-req="SWS_Crypto_00219" href="../spec/record.html?id=SWS_Crypto_00219">[SWS_Crypto_00219]</a>.</p>

<h4>3. Synchronisation, Reentranz und Task-Kontexte</h4>
<p>Kryptografische Operationen variieren drastisch in ihrer Ausführungsdauer. Während schnelle Blockchiffren oder Hashberechnungen synchron im Task-Kontext des Aufrufers ausgeführt werden können, erfordern asymmetrische Berechnungen (z.&nbsp;B. RSA-Signaturgenerierung) oder zeitintensive Hardware-Abläufe eine asynchrone Bearbeitung <a class="spec-record-ref" data-req="SWS_Csm_00984" href="../spec/record.html?id=SWS_Csm_00984">[SWS_Csm_00984]</a>, <a class="spec-record-ref" data-req="SWS_Csm_00992" href="../spec/record.html?id=SWS_Csm_00992">[SWS_Csm_00992]</a>. Für die Entkopplung stellt der CSM die zyklisch aufgerufene Hauptfunktion <code>Csm_MainFunction()</code> bereit <a class="spec-record-ref" data-req="SWS_Csm_00479" href="../spec/record.html?id=SWS_Csm_00479">[SWS_Csm_00479]</a>. Diese überwacht Warteschlangen, dispatcht anstehende Jobs an das CryIf und treibt interne Zustandsmaschinen asynchroner Primitiven voran <a class="spec-record-ref" data-req="SWS_Csm_00019" href="../spec/record.html?id=SWS_Csm_00019">[SWS_Csm_00019]</a>.</p>

<p>In modernen Mehrkern- und Multisektor-Architekturen unterstützt der CSM mehrere Instanzen <code>Csm_MainFunction_&lt;shortName&gt;()</code>, die dedizierten OS-Partitionen zugeordnet werden <a class="spec-record-ref" data-req="SWS_Csm_00479" href="../spec/record.html?id=SWS_Csm_00479">[SWS_Csm_00479]</a>, <a class="docref internal-spec-ref" href="../../spec/figures/FIG-97ef3205b4db18da.html" data-snip="FIG-97ef3205b4db18da">AUTOSAR_SWS_CryptoServiceManager S. 170</a>. Bei asynchroner Treiberausführung werden die Berechnungen entweder durch Polling in der Treiber-MainFunction oder durch Interrupt Service Routinen (ISR) hardwarebasierter Krypto-Engines beendet <a class="spec-record-ref" data-req="SWS_Crypto_00027" href="../spec/record.html?id=SWS_Crypto_00027">[SWS_Crypto_00027]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00028" href="../spec/record.html?id=SWS_Crypto_00028">[SWS_Crypto_00028]</a>. Ein einzelnes Crypto Driver Object kann per Definition jeweils genau einen Krypto-Job zeitgleich bearbeiten; ein Treiber mit n Objekten verarbeitet n Aufträge echt parallel <a class="spec-record-ref" data-req="SWS_Crypto_00014" href="../spec/record.html?id=SWS_Crypto_00014">[SWS_Crypto_00014]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00117" href="../spec/record.html?id=SWS_Crypto_00117">[SWS_Crypto_00117]</a>.</p>

<p>Bezüglich der Reentranz sind Dienstschnittstellen wie <code>Csm_MacGenerate()</code> oder <code>CryIf_ProcessJob()</code> reentrant für unterschiedliche Jobs konzipiert, verbieten jedoch die parallele Mehrfachbeauftragung derselben Job-Instanz <a class="spec-record-ref" data-req="SWS_Csm_00016" href="../spec/record.html?id=SWS_Csm_00016">[SWS_Csm_00016]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>. Schlüsselverwaltungsfunktionen wie <code>Csm_KeyElementCopy()</code>, <code>CryIf_KeyElementCopy()</code> oder <code>Crypto_KeyCopy()</code> sind reentrant implementiert, dürfen jedoch nicht nebenläufig auf dieselbe Quell-Schlüsselkennung (<code>keyId</code> bzw. <code>cryptoKeyId</code>) angewendet werden, um Dateninkonsistenzen und Race Conditions zu vermeiden <a class="spec-record-ref" data-req="SWS_Csm_00969" href="../spec/record.html?id=SWS_Csm_00969">[SWS_Csm_00969]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91015" href="../spec/record.html?id=SWS_CryIf_91015">[SWS_CryIf_91015]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00155" href="../spec/record.html?id=SWS_Crypto_00155">[SWS_Crypto_00155]</a>. Hardwaretreiber dürften für die Modifikation interner Arbeitsbereiche und Schlüsselregister interne exklusive Bereiche (Exclusive Areas) nutzen, um Race Conditions zwischen ISR und Task-Ebene abzufangen <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_SECTION_7_2_2_2_Asynchronous_Job_Processing.html" data-snip="SNIP_CLASSIC_CRYPTO_SECTION_7_2_2_2_Asynchronous_Job_Processing">SWS_CryptoDriver S. 27</a>. <a class="interp-q interp-q-open" data-q="Q-b1e9578255723a0e" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-b1e9578255723a0e" title="Frage Q-b1e9578255723a0e (offen): Hardware-Kryptotreiber dürften interne Exclusive Areas verwenden, um Zugriffe auf Hardwareregister zwischen ISR und Task-Ebene abzusichern.">Frage Q-b1e9578255723a0e (offen)</a></p>

<h4>4. Typische Lebenszyklen und Betriebsmodi</h4>
<p>Die Initialisierung des Krypto-Clusters erfolgt während des BSW-Hochlaufs in hierarchischer Reihenfolge. Zunächst initialisiert der EcuM oder BswM die Treiberstufe via <code>Crypto_Init()</code> unter Übergabe der Konfiguration <code>Crypto_ConfigType</code> <a class="spec-record-ref" data-req="SWS_Crypto_91016" href="../spec/record.html?id=SWS_Crypto_91016">[SWS_Crypto_91016]</a>, gefolgt von der Schnittstellenschicht via <code>CryIf_Init()</code> mit <code>CryIf_ConfigType</code> <a class="spec-record-ref" data-req="SWS_CryIf_91118" href="../spec/record.html?id=SWS_CryIf_91118">[SWS_CryIf_91118]</a>. Schließlich wird der CSM mittels <code>Csm_Init()</code> gestartet, wobei dessen Konfigurationszeiger gemäß Spezifikation stets auf <code>NULL_PTR</code> gesetzt werden muss <a class="spec-record-ref" data-req="SWS_Csm_00646" href="../spec/record.html?id=SWS_Csm_00646">[SWS_Csm_00646]</a>. Erst nach vollständiger Initialisierung aller Schichten dürfen kryptografische Aufträge oder Schlüsselzugriffe angenommen werden <a class="spec-record-ref" data-req="SWS_CryIf_00076" href="../spec/record.html?id=SWS_CryIf_00076">[SWS_CryIf_00076]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00196" href="../spec/record.html?id=SWS_Crypto_00196">[SWS_Crypto_00196]</a>.</p>

<p>Ein zentraler Aspekt des Schlüssel-Lebenszyklus ist die Validierung und Persistierung in nichtflüchtigem Speicher (NVM). Nach dem Laden neuer Schlüsselwerte über <code>Csm_KeyElementSet()</code> verbleibt der Schlüssel im Status „unvollständig bzw. unbekannt“ <a class="spec-record-ref" data-req="SWS_Csm_00957" href="../spec/record.html?id=SWS_Csm_00957">[SWS_Csm_00957]</a>. Erst der explizite Aufruf von <code>Csm_JobKeySetValid()</code> bzw. <code>Crypto_KeySetValid()</code> prüft die Konsistenz und wechselt den Schlüsselstatus auf gültig <a class="spec-record-ref" data-req="SWS_Csm_91027" href="../spec/record.html?id=SWS_Csm_91027">[SWS_Csm_91027]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_91014" href="../spec/record.html?id=SWS_Crypto_91014">[SWS_Crypto_91014]</a>. Bei persistierten Schlüsseln löst ausschließlich diese Validierung die Speicherung im NVM aus <a class="spec-record-ref" data-req="SWS_Crypto_91026" href="../spec/record.html?id=SWS_Crypto_91026">[SWS_Crypto_91026]</a>, <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM.html" data-snip="SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM">SWS_CryptoDriver S. 37</a>. Dies verhindert mehrfache fragmentierte NVM-Schreibzyklen und schützt vor unvollständigen Schlüsselsätzen <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM.html" data-snip="SNIP_CLASSIC_CRYPTO_SECTION_7_2_6_1_Writing_keys_to_NVM">SWS_CryptoDriver S. 37</a>. Für die Synchronisation mit dem NVRAM Manager bedient sich der Crypto Driver der Callbacks <code>Crypto_&lt;vi&gt;_&lt;ai&gt;_NvBlock_ReadFrom_&lt;NvBlock&gt;()</code> und <code>Crypto_&lt;vi&gt;_&lt;ai&gt;_NvBlock_WriteTo_&lt;NvBlock&gt;()</code> sowie <code>NvM_WriteBlock()</code> <a class="spec-record-ref" data-req="SWS_Crypto_91024" href="../spec/record.html?id=SWS_Crypto_91024">[SWS_Crypto_91024]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_91025" href="../spec/record.html?id=SWS_Crypto_91025">[SWS_Crypto_91025]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_91017" href="../spec/record.html?id=SWS_Crypto_91017">[SWS_Crypto_91017]</a>.</p>

<p>Laufende Streaming-Aufträge können bei Bedarf über <code>Csm_SaveContextJob()</code> unterbrochen, in einem applikationseigenen Puffer gesichert und später per Kontext-Wiederherstellung fortgeführt werden <a class="spec-record-ref" data-req="SWS_Csm_91063" href="../spec/record.html?id=SWS_Csm_91063">[SWS_Csm_91063]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01029" href="../spec/record.html?id=SWS_Csm_01029">[SWS_Csm_01029]</a>. Vor einem Steuergeräte-Shutdown oder einem Übergang in Low-Power-Modi können asynchrone Aufträge kontrolliert via <code>Csm_CancelJob()</code> abgebrochen werden, wodurch das CryIf über <code>CryIf_CancelJob()</code> die Jobs aus Treiberwarteschlangen und Hardwarekanälen entfernt <a class="spec-record-ref" data-req="SWS_Csm_00968" href="../spec/record.html?id=SWS_Csm_00968">[SWS_Csm_00968]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91014" href="../spec/record.html?id=SWS_CryIf_91014">[SWS_CryIf_91014]</a>.</p>

<h4>5. Fehlerbehandlung, DET-Tracing und Degradation</h4>
<p>Das Cluster implementiert eine mehrstufige Fehlererkennungs- und Abwehrstrategie. Entwicklungsfehler werden bei aktiviertem Tracing direkt an das Default Error Tracer (DET) Modul gemeldet <a class="spec-record-ref" data-req="SWS_Csm_91101" href="../spec/record.html?id=SWS_Csm_91101">[SWS_Csm_91101]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_91017" href="../spec/record.html?id=SWS_Crypto_91017">[SWS_Crypto_91017]</a>. Zu den typischen DET-Ereignissen zählen Modulaufrufe vor erfolgter Initialisierung (<code>CRYIF_E_UNINIT</code>, <code>CRYPTO_E_UNINIT</code>), ungültige Handle- oder Schlüsselparameter (<code>CRYIF_E_PARAM_HANDLE</code>, <code>CRYPTO_E_PARAM_HANDLE</code>) sowie Nullzeiger-Übergaben <a class="spec-record-ref" data-req="SWS_CryIf_00076" href="../spec/record.html?id=SWS_CryIf_00076">[SWS_CryIf_00076]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_00134" href="../spec/record.html?id=SWS_CryIf_00134">[SWS_CryIf_00134]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00196" href="../spec/record.html?id=SWS_Crypto_00196">[SWS_Crypto_00196]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_00217" href="../spec/record.html?id=SWS_Crypto_00217">[SWS_Crypto_00217]</a>.</p>

<p>Laufzeitüberlastungen und Ressourcenengpässe werden deterministisch über definierte Rückgabewerte abgefangen. Ist die CSM-Warteschlange für einen asynchronen Job erschöpft, weist der CSM den Auftrag mit dem Statuscode <code>CRYPTO_E_BUSY</code> ab und generiert den Laufzeitfehler <code>CSM_E_QUEUE_FULL</code> <a class="spec-record-ref" data-req="SWS_Csm_00018" href="../spec/record.html?id=SWS_Csm_00018">[SWS_Csm_00018]</a>, <a class="spec-record-ref" data-req="SWS_Csm_01089" href="../spec/record.html?id=SWS_Csm_01089">[SWS_Csm_01089]</a>. Ist ein bereitgestellter Ergebnispuffer unzureichend dimensioniert, bricht der Treiber die Operation mit <code>CRYPTO_E_SMALL_BUFFER</code> ab <a class="spec-record-ref" data-req="SWS_Crypto_00195" href="../spec/record.html?id=SWS_Crypto_00195">[SWS_Crypto_00195]</a>. Verweist ein kryptografischer Dienst auf einen uninitialisierten oder explizit invalidierten Schlüssel (beispielsweise nach Aufruf von <code>Csm_JobKeySetInvalid()</code> oder <code>Crypto_KeySetInvalid()</code>), schlagen Serviceanforderungen kontrolliert mit <code>CRYPTO_E_KEY_NOT_VALID</code> oder <code>CRYPTO_E_KEY_EMPTY</code> fehl <a class="spec-record-ref" data-req="SWS_Csm_91002" href="../spec/record.html?id=SWS_Csm_91002">[SWS_Csm_91002]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91003" href="../spec/record.html?id=SWS_CryIf_91003">[SWS_CryIf_91003]</a>, <a class="spec-record-ref" data-req="SWS_Crypto_91020" href="../spec/record.html?id=SWS_Crypto_91020">[SWS_Crypto_91020]</a>.</p>

<p>Degradations- und Fallback-Mechanismen werden auf Systemebene ermöglicht: Anwendungen können über <code>Csm_KeyGetStatus()</code> den Integritätsstatus von Schlüsseln vor Auftragsübermittlung prüfen <a class="spec-record-ref" data-req="SWS_Csm_91047" href="../spec/record.html?id=SWS_Csm_91047">[SWS_Csm_91047]</a>, <a class="spec-record-ref" data-req="SWS_CryIf_91012" href="../spec/record.html?id=SWS_CryIf_91012">[SWS_CryIf_91012]</a>. Sollte ein Hardware-Krypto-Beschleuniger dauerhaft belegt sein oder ausfallen, erlaubt die CryIf-Kanalkonfiguration eine softwarebasierte Ausweichroute, sofern ein redundanter Software-Treiber integriert ist <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER.html" data-snip="SNIP_CLASSIC_CRYPTO_FIGURE_Figure_7_1_CRYPTODRIVER">SWS_CryptoDriver S. 15</a>.</p>
