<h4>Context</h4>
<p>The class <code>ara::diag::SovdAuthorization</code> provides the standardized interface through which an adaptive application implements authorization and authentication services for the Service-Oriented Vehicle Diagnostics (SOVD) protocol (<a class="spec-record-ref" data-req="SWS_DM_01490" href="../spec/record.html?id=SWS_DM_01490">[SWS_DM_01490]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=695">AUTOSAR AP SWS Diagnostics §8.52.1 “Class: SovdAuthorization”</a>). Within the AUTOSAR architecture, it acts as a link between the in-vehicle diagnostic server (Diagnostic Management, DM) and downstream authorization logic, such as an OAuth 2.0-based authorization or resource server (<a class="spec-record-ref" data-req="SWS_DM_01483" href="../spec/record.html?id=SWS_DM_01483">[SWS_DM_01483]</a>, <a class="spec-record-ref" data-req="SWS_DM_01484" href="../spec/record.html?id=SWS_DM_01484">[SWS_DM_01484]</a>, <a class="spec-record-ref" data-req="SWS_DM_01485" href="../spec/record.html?id=SWS_DM_01485">[SWS_DM_01485]</a>).</p>
<p>Essentially four parties are involved in the processes: the external SOVD client, the Diagnostic Server (DM) as intermediary, the application class <code>ara::diag::SovdAuthorization</code>, and an external or in-vehicle authorization server. The DM receives HTTP-based SOVD requests and delegates the provision of authorization and token URLs as well as the validation of transmitted access tokens to the mapped application instance (<a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>, <a class="spec-record-ref" data-req="SWS_DM_01471" href="../spec/record.html?id=SWS_DM_01471">[SWS_DM_01471]</a>, <a class="spec-record-ref" data-req="SWS_DM_01472" href="../spec/record.html?id=SWS_DM_01472">[SWS_DM_01472]</a>).</p>

<h4>Lifecycle</h4>
<p>Creation is performed by the constructor <code>SovdAuthorization(ara::core::InstanceSpecifier, ConcurrencyType)</code> (<a class="spec-record-ref" data-req="SWS_DM_01489" href="../spec/record.html?id=SWS_DM_01489">[SWS_DM_01489]</a>). The passed <code>instanceSpecifier</code> references a modeled PortPrototype of the interface <code>DiagnosticSovdAuthorizationInterface</code>, which must be mapped to a SoftwareCluster of category PLATFORM (<a class="spec-record-ref" data-req="SWS_DM_01471" href="../spec/record.html?id=SWS_DM_01471">[SWS_DM_01471]</a>, <a class="spec-record-ref" data-req="SWS_DM_01489" href="../spec/record.html?id=SWS_DM_01489">[SWS_DM_01489]</a>). The parameter <code>concurrencyType</code> configures whether the virtual callback methods of the instance are called concurrently (<code>kConcurrent</code>) or sequentially (<code>kNotConcurrent</code>) (<a class="spec-record-ref" data-req="SWS_DM_01489" href="../spec/record.html?id=SWS_DM_01489">[SWS_DM_01489]</a>).</p>
<p>After instantiation, the DM only forwards requests once the application explicitly enables the port using <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01487" href="../spec/record.html?id=SWS_DM_01487">[SWS_DM_01487]</a>). The forwarding of incoming requests can be suspended at any time via <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01486" href="../spec/record.html?id=SWS_DM_01486">[SWS_DM_01486]</a>). Resources are released in the virtual destructor <code>~SovdAuthorization()</code> (<a class="spec-record-ref" data-req="SWS_DM_01488" href="../spec/record.html?id=SWS_DM_01488">[SWS_DM_01488]</a>). The constructor, destructor, and <code>Offer()</code> and <code>StopOffer()</code> are specified as not thread-safe (<a class="spec-record-ref" data-req="SWS_DM_01486" href="../spec/record.html?id=SWS_DM_01486">[SWS_DM_01486]</a>, <a class="spec-record-ref" data-req="SWS_DM_01487" href="../spec/record.html?id=SWS_DM_01487">[SWS_DM_01487]</a>, <a class="spec-record-ref" data-req="SWS_DM_01488" href="../spec/record.html?id=SWS_DM_01488">[SWS_DM_01488]</a>, <a class="spec-record-ref" data-req="SWS_DM_01489" href="../spec/record.html?id=SWS_DM_01489">[SWS_DM_01489]</a>). Interpretation: The instance of <code>SovdAuthorization</code> is presumably typically created during the initialization phase of the respective process and held over the entire process lifetime.</p>

<h4>Usage Path</h4>
<p>During normal operation, the application class derived from <code>SovdAuthorization</code> serves two main use cases:</p>
<ol>
<li><strong>Client redirection (Redirection):</strong> If the DM receives a client request to verify credentials at the vehicle or to request a token, it calls <code>GetAuthorizationUrl()</code> (<a class="spec-record-ref" data-req="SWS_DM_01472" href="../spec/record.html?id=SWS_DM_01472">[SWS_DM_01472]</a>, <a class="spec-record-ref" data-req="SWS_DM_01485" href="../spec/record.html?id=SWS_DM_01485">[SWS_DM_01485]</a>) or <code>GetTokenUrl()</code> (<a class="spec-record-ref" data-req="SWS_DM_01471" href="../spec/record.html?id=SWS_DM_01471">[SWS_DM_01471]</a>, <a class="spec-record-ref" data-req="SWS_DM_01484" href="../spec/record.html?id=SWS_DM_01484">[SWS_DM_01484]</a>). The application evaluates the passed <code>queryParameters</code> and <code>metaInfo</code> and asynchronously returns the target URL as <code>ara::core::Future&lt;ara::core::String&gt;</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=194">AUTOSAR AP SWS Diagnostics §7.3.3.2.1 “SOVD – Authorization”</a>). The DM then responds to the SOVD client with HTTP status 307 (Temporary Redirect) and sets the <code>Location</code> header to the returned URL (<a class="spec-record-ref" data-req="SWS_DM_01471" href="../spec/record.html?id=SWS_DM_01471">[SWS_DM_01471]</a>, <a class="spec-record-ref" data-req="SWS_DM_01472" href="../spec/record.html?id=SWS_DM_01472">[SWS_DM_01472]</a>).</li>
<li><strong>Token-Validierung:</strong> If the SOVD client sends an HTTP header <code>Authorization</code> whose token is not yet or no longer stored as valid, the DM calls the method <code>ValidateAuthorization()</code> (<a class="spec-record-ref" data-req="SWS_DM_01470" href="../spec/record.html?id=SWS_DM_01470">[SWS_DM_01470]</a>, <a class="spec-record-ref" data-req="SWS_DM_01483" href="../spec/record.html?id=SWS_DM_01483">[SWS_DM_01483]</a>). The application verifies the token and sets the associated authorized roles in the passed object <code>ara::diag::ClientAuthentication</code> (<a class="spec-record-ref" data-req="SWS_DM_01483" href="../spec/record.html?id=SWS_DM_01483">[SWS_DM_01483]</a>). As soon as the returned <code>Future&lt;ValidateAuthorizationOutput&gt;</code> is provided, the application must no longer access the <code>ClientAuthentication</code> object (<a class="spec-record-ref" data-req="SWS_DM_01483" href="../spec/record.html?id=SWS_DM_01483">[SWS_DM_01483]</a>). The DM applies the set roles (<a class="spec-record-ref" data-req="SWS_DM_01469" href="../spec/record.html?id=SWS_DM_01469">[SWS_DM_01469]</a>) and uses the validity timestamp <code>validUntil</code> or the identity (<code>identity</code>) to recognize the client and for subsequent locking mechanisms (<a class="spec-record-ref" data-req="SWS_DM_01781" href="../spec/record.html?id=SWS_DM_01781">[SWS_DM_01781]</a>, <a class="spec-record-ref" data-req="SWS_DM_01782" href="../spec/record.html?id=SWS_DM_01782">[SWS_DM_01782]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=195">AUTOSAR AP SWS Diagnostics §7.3.3.2.1 “SOVD – Authorization”</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>Error conditions primarily occur during initialization, during service release, and in the context of validation:</p>
<ul>
<li><strong>Construction errors:</strong> The instantiation reports manifest and configuration violations (<a class="spec-record-ref" data-req="SWS_DM_01489" href="../spec/record.html?id=SWS_DM_01489">[SWS_DM_01489]</a>), including <code>InstanceSpecifierMappingIntegrityViolation</code> (InstanceSpecifier cannot be resolved or is not a PortPrototype), <code>PortInterfaceMappingViolation</code> (PortPrototype does not match the interface <code>DiagnosticSovdAuthorizationInterface</code>), <code>ProcessMappingViolation</code> (no matching process modeled), and <code>InstanceSpecifierAlreadyInUseViolation</code> (InstanceSpecifier already assigned in the process).</li>
<li><strong>Errors during Offer():</strong> The call returns a <code>ara::core::Result&lt;void&gt;</code> (<a class="spec-record-ref" data-req="SWS_DM_01487" href="../spec/record.html?id=SWS_DM_01487">[SWS_DM_01487]</a>). Possible error codes are <code>DiagOfferErrc::kAlreadyOffered</code> (interface has already been offered) and <code>DiagOfferErrc::kConfigurationMismatch</code> (monitor configuration deviates from the DEXT model data).</li>
