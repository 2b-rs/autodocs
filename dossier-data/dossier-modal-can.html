<h4>Role of the CAN driver between CanIf and controller hardware</h4>
<p>The CAN driver (<code>Can</code>) is the lowest, hardware-oriented layer of the Classic CAN stack. Any access to the CAN hardware is encapsulated in functions of this module. The driver itself does not track the state transitions of the controllers (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine">SWS CANDriver p. 30</a>). Upwards, it communicates exclusively with the CAN Interface. The callbacks that the driver calls are all implemented in CanIf and are not configurable: <code>CanIf_ControllerBusOff</code>, <code>CanIf_ControllerModeIndication</code>, <code>CanIf_RxIndication</code>, and <code>CanIf_TxConfirmation</code>. In addition, the driver requires <code>Det_ReportRuntimeError</code> and the OS service <code>GetCounterValue</code> (<a class="spec-record-ref" data-req="SWS_Can_00234" href="../../spec/record.html?id=SWS_Can_00234">[SWS_Can_00234]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_OS_SECTION_8_6_1_Mandatory_Interfaces_CANDRIVER.html" data-snip="SNIP_CLASSIC_OS_SECTION_8_6_1_Mandatory_Interfaces_CANDRIVER">SWS CANDriver p. 73</a>).</p>
<p>CanIf accesses the hardware only via abstract handles. Hardware Object Handles for transmission (HTH) and reception (HRH) reference mailbox structures whose layout is known only to the driver (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P29_347.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P29_347">SWS CANInterface p. 29</a>). The data type of these handles is <code>Can_HwHandleType</code>. It is based on <code>uint8</code>; with more than 255 hardware objects, the extended value range with <code>uint16</code> is used (<a class="spec-record-ref" data-req="SWS_Can_00429" href="../../spec/record.html?id=SWS_Can_00429">[SWS_Can_00429]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_2_4_Can_HwHandleType.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_2_4_Can_HwHandleType">SWS CANDriver p. 54</a>). Mode requests from the CanSM also reach the driver only via CanIf (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P20_343.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P20_343">SWS CANInterface p. 20</a>).</p>

<h4>Startup and lifecycle: Driver state and controller states</h4>
<p>The driver itself has only two states. After power-up or reset, it is in <code>CAN_UNINIT</code>. <code>Can_Init</code> initializes all controllers of the hardware unit according to their configuration and then transitions to <code>CAN_READY</code> (<a class="spec-record-ref" data-req="SWS_Can_00223" href="../../spec/record.html?id=SWS_Can_00223">[SWS_Can_00223]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine">SWS CANDriver p. 29</a>). The ECU State Manager calls <code>Can_Init</code> during the startup phase before any other driver function is used (<a class="spec-record-ref" data-req="SWS_Can_91012" href="../../spec/record.html?id=SWS_Can_91012">[SWS_Can_91012]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CAND_P41_097.html" data-snip="SNIP_Can_AUTOSAR_SWS_CAND_P41_097">SWS CANDriver p. 41</a>). According to an implementation note, this happens at most once at runtime. Register settings affecting all controllers of a hardware unit are possible only in <code>Can_Init</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine">SWS CANDriver p. 29</a>). The passed structure <code>Can_ConfigType</code> is hardware-specific. It contains the global settings and pointers to the controller configurations (<a class="spec-record-ref" data-req="SWS_Can_00413" href="../../spec/record.html?id=SWS_Can_00413">[SWS_Can_00413]</a>).</p>
<p>Per controller, the specification distinguishes four states in simplified form: <code>UNINIT</code>, <code>STOPPED</code>, <code>STARTED</code>, and <code>SLEEP</code>. They are represented as <code>Can_ControllerStateType</code> with the values <code>CAN_CS_UNINIT</code> through <code>CAN_CS_SLEEP</code> (<a class="spec-record-ref" data-req="SWS_Can_91013" href="../../spec/record.html?id=SWS_Can_91013">[SWS_Can_91013]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine">SWS CANDriver p. 30</a>). After initialization, CanIf expects the controller to remain in <code>STOPPED</code>. In this state, it can neither transmit nor receive (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P39_367.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P39_367">SWS CANInterface p. 39</a>). Each controller is started individually with <code>Can_SetControllerMode(CAN_CS_STARTED)</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_2_Driver_State_Machine">SWS CANDriver p. 29</a>). In doing so, it is reinitialized with the same configuration that was used previously (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_2_Can_SetControllerMode.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_2_Can_SetControllerMode">SWS CANDriver p. 59</a>).</p>
<p><code>Can_SetControllerMode</code> operates asynchronously and is non-reentrant. <code>E_OK</code> only means that the request was accepted; <code>E_NOT_OK</code> signals a development error (<a class="spec-record-ref" data-req="SWS_Can_00230" href="../../spec/record.html?id=SWS_Can_00230">[SWS_Can_00230]</a>). The driver reports the completed transition via <code>CanIf_ControllerModeIndication</code> (<a class="spec-record-ref" data-req="SWS_Can_00234" href="../../spec/record.html?id=SWS_Can_00234">[SWS_Can_00234]</a>). Without an interrupt, <code>Can_MainFunction_Mode</code> polls the status registers. The requirement text of the document reference mistakenly mentions <code>Can_MainFunction_Wakeup</code> here (<a class="spec-record-ref" data-req="SWS_Can_00368" href="../../spec/record.html?id=SWS_Can_00368">[SWS_Can_00368]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_5_Can_MainFunction_Mode.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_5_Can_MainFunction_Mode">SWS CANDriver p. 84</a>). <code>Can_GetControllerMode</code> provides the current mode (<a class="spec-record-ref" data-req="SWS_Can_91014" href="../../spec/record.html?id=SWS_Can_91014">[SWS_Can_91014]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_7_Can_GetControllerMode.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_7_Can_GetControllerMode">SWS CANDriver p. 65</a>). <code>Can_DeInit</code> handles the return path. It sets the driver to <code>CAN_UNINIT</code> and all controllers from <code>STOPPED</code> or <code>SLEEP</code> to <code>UNINIT</code>, thus preparing for a reconfiguration (<a class="spec-record-ref" data-req="SWS_Can_91002" href="../../spec/record.html?id=SWS_Can_91002">[SWS_Can_91002]</a>, <a class="spec-record-ref" data-req="SWS_Can_91010" href="../../spec/record.html?id=SWS_Can_91010">[SWS_Can_91010]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_3_7_State_transition_caused_by_function_Can_DeInit.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_3_7_State_transition_caused_by_function_Can_DeInit">SWS CANDriver p. 37</a>).</p>

<h4>Transmit path: from Can_Write to transmit confirmation</h4>
<p>CanIf passes each L-PDU using <code>Can_Write(Hth, PduInfo)</code>. The function is synchronous and thread-safe reentrant. Via the HTH, the controller is also determined, because HTH numbers are unique within a hardware unit (<a class="spec-record-ref" data-req="SWS_Can_00233" href="../../spec/record.html?id=SWS_Can_00233">[SWS_Can_00233]</a>). The structure <code>Can_PduType</code> combines <code>swPduHandle</code>, <code>length</code>, <code>id</code>, and the data pointer <code>sdu</code> (<a class="spec-record-ref" data-req="SWS_Can_00415" href="../../spec/record.html?id=SWS_Can_00415">[SWS_Can_00415]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_2_2_Can_PduType.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_2_2_Can_PduType">SWS CANDriver p. 53</a>). CanIf sets <code>swPduHandle</code> to the <code>CanTxPduId</code> that it expects later in <code>CanIf_TxConfirmation</code>. In addition, CanIf assigns the two most significant bits of the CanId with the Extended flag and the FD flag (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P80_435.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P80_435">SWS CANInterface p. 80</a>).</p>
<p>If no hardware transmit object is free, the driver returns the overlaid return value <code>CAN_BUSY</code> (<a class="spec-record-ref" data-req="SWS_Can_00039" href="../../spec/record.html?id=SWS_Can_00039">[SWS_Can_00039]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_2_6_Extension_to_Std_ReturnType.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_2_6_Extension_to_Std_ReturnType">SWS CANDriver p. 54</a>). If transmit buffering is enabled, CanIf then stores the L-PDU in a dedicated buffer, provided its size is greater than zero (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P43_371.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P43_371">SWS CANInterface p. 43</a>). After each confirmation, CanIf resubmits the highest-priority pending L-PDU via <code>Can_Write</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P45_373.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P45_373">SWS CANInterface p. 45</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_9_5_Transmit_confirmation_with_buffering.html" data-snip="SNIP_CLASSIC_STD_SECTION_9_5_Transmit_confirmation_with_buffering">SWS CANInterface p. 157</a>). Importantly: The driver does not check the controller state prior to <code>Can_Write</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine">SWS CANDriver p. 30</a>). CanIf therefore blocks transmit requests for controllers in <code>CAN_CS_STOPPED</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P53_381.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P53_381">SWS CANInterface p. 53</a>).</p>
<p>The confirmation comes either from the transmit interrupt or, in the case of polling, cyclically from <code>Can_MainFunction_Write</code>, which is called by the BSW Scheduler (<a class="spec-record-ref" data-req="SWS_Can_00225" href="../../spec/record.html?id=SWS_Can_00225">[SWS_Can_00225]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_9_4_Transmit_confirmation_polling_mode.html" data-snip="SNIP_CLASSIC_STD_SECTION_9_4_Transmit_confirmation_polling_mode">SWS CANInterface p. 156</a>). In both cases, the driver calls <code>CanIf_TxConfirmation</code> with the <code>swPduHandle</code> that was passed during <code>Can_Write</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P102_505.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P102_505">SWS CANInterface p. 102</a>).</p>

<h4>Receive path, L-PDU callout, and frame formats</h4>
<p>The driver reports received frames via interrupt or, in the case of polling, from <code>Can_MainFunction_Read</code> (<a class="spec-record-ref" data-req="SWS_Can_00226" href="../../spec/record.html?id=SWS_Can_00226">[SWS_Can_00226]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_2_Can_MainFunction_Read.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_2_Can_MainFunction_Read">SWS CANDriver p. 79</a>). With <code>CanIf_RxIndication</code>, CanIf receives HRH, CanId, data length, and a reference to the normalized data. The hardware receive object remains locked until the end of the copy process. After returning from <code>CanIf_RxIndication</code>, it is released immediately (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P47_375.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P47_375">SWS CANInterface p. 47</a>). Subsequently, CanIf executes the software filter and the Data Length Check and forwards the data to the upper layer (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P50_378.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P50_378">SWS CANInterface p. 50</a>).</p>
<p>Optionally, prior to forwarding, the driver calls a configurable L-PDU callout: <code>&lt;LPDU_CalloutName&gt;(Hrh, CanId, CanDataLegth, CanSduPtr)</code> with return type <code>boolean</code> (<a class="spec-record-ref" data-req="SWS_Can_00443" href="../../spec/record.html?id=SWS_Can_00443">[SWS_Can_00443]</a>). If the callout returns <code>false</code>, according to the document citation the L-PDU is not processed further (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_4_1_Call_out_function.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_4_1_Call_out_function">SWS CANDriver p. 77</a>). This section originates from R25-11. That the rule also applies to R20-11 is an interpretation that is presumably accurate.</p>
<p>The frame format is encoded in <code>Can_IdType</code>. The two most significant bits distinguish classical frames and CAN FD frames, in each case with standard or extended ID (values 00 to 11) (<a class="spec-record-ref" data-req="SWS_Can_00416" href="../../spec/record.html?id=SWS_Can_00416">[SWS_Can_00416]</a>). CAN FD is active for a controller if a baud rate with <code>CanControllerFdBaudrateConfig</code> applies. In this way, classical CAN 2.0 frames, for example for selective wake-up, can be mixed with FD frames (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_13_CAN_FD_Support.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_13_CAN_FD_Support">SWS CANDriver p. 49</a>). CanIf also evaluates the same bits for dynamic transmit L-PDUs (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_4_1_Dynamic_Transmit_L_PDUs.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_4_1_Dynamic_Transmit_L_PDUs">SWS CANInterface p. 34</a>).</p>

<h4>Polling main functions, configuration, and partitions</h4>
<p>For each event-driven path, there is a scheduled main function provided via <code>SchM_Can.h</code>: <code>Can_MainFunction_Write</code>, <code>Can_MainFunction_Read</code>, <code>Can_MainFunction_BusOff</code>, <code>Can_MainFunction_Wakeup</code>, and <code>Can_MainFunction_Mode</code> (<a class="spec-record-ref" data-req="SWS_Can_00225" href="../../spec/record.html?id=SWS_Can_00225">[SWS_Can_00225]</a>, <a class="spec-record-ref" data-req="SWS_Can_00226" href="../../spec/record.html?id=SWS_Can_00226">[SWS_Can_00226]</a>, <a class="spec-record-ref" data-req="SWS_Can_00227" href="../../spec/record.html?id=SWS_Can_00227">[SWS_Can_00227]</a>, <a class="spec-record-ref" data-req="SWS_Can_00228" href="../../spec/record.html?id=SWS_Can_00228">[SWS_Can_00228]</a>, <a class="spec-record-ref" data-req="SWS_Can_00368" href="../../spec/record.html?id=SWS_Can_00368">[SWS_Can_00368]</a>). In the R20-11 requirements, polling is tied to mode <code>POLLING</code>. Document passages from later releases extend this to <code>MIXED</code>: there, only hardware objects with <code>CanHardwareObjectUsesPolling = TRUE</code> are polled. Furthermore, they allow an empty definition of the main function if polling is not performed at all (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_1_Can_MainFunction_Write.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_1_Can_MainFunction_Write">SWS CANDriver p. 81</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_3_Can_MainFunction_BusOff.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_3_Can_MainFunction_BusOff">SWS CANDriver p. 83</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_4_Can_MainFunction_Wakeup.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_4_Can_MainFunction_Wakeup">SWS CANDriver p. 80</a>).</p>
<p>If multiple periods are configured via <code>CanMainFunctionRWPeriods</code>, the write main functions are named <code>Can_MainFunction_Write_&lt;ShortName&gt;()</code>. There is one function per period that is referenced by at least one TRANSMIT hardware object; for the read path, the same applies with RECEIVE objects (<a class="spec-record-ref" data-req="SWS_Can_00441" href="../../spec/record.html?id=SWS_Can_00441">[SWS_Can_00441]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_1_Can_MainFunction_Write.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_1_Can_MainFunction_Write">SWS CANDriver p. 81</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_5_1_2_Can_MainFunction_Read.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_5_1_2_Can_MainFunction_Read">SWS CANDriver p. 79</a>). The supporting passages originate from later releases, and the R20-11 text of <a class="spec-record-ref" data-req="SWS_Can_00441" href="../../spec/record.html?id=SWS_Can_00441">[SWS_Can_00441]</a> in the payload merely reflects the revision history. Therefore, the naming rule is likely to apply to R20-11 as well; this is an interpretation.</p>
<p>In multicore systems, the module operates as an independent instance in each partition. An API call only affects the partition in which it occurs (<a class="spec-record-ref" data-req="SWS_Can_CONSTR_00508" href="../../spec/record.html?id=SWS_Can_CONSTR_00508">[SWS_Can_CONSTR_00508]</a>). Three rules apply to the configuration:</p>
<ul>
<li>The partitions referenced via <code>CanControllerEcucPartitionRef</code> must be a subset of the partitions in <code>CanEcucPartitionRef</code> (<a class="spec-record-ref" data-req="SWS_Can_CONSTR_00509" href="../../spec/record.html?id=SWS_Can_CONSTR_00509">[SWS_Can_CONSTR_00509]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CAND_P99_300.html" data-snip="SNIP_Can_AUTOSAR_SWS_CAND_P99_300">SWS CANDriver p. 99</a>).</li>
<li>The controller and transceiver channel of a communication channel must reference the same partition (<a class="spec-record-ref" data-req="SWS_Can_CONSTR_00510" href="../../spec/record.html?id=SWS_Can_CONSTR_00510">[SWS_Can_CONSTR_00510]</a>).</li>
<li>The driver rejects partition assignments that the implementation does not support (<a class="spec-record-ref" data-req="SWS_Can_00507" href="../../spec/record.html?id=SWS_Can_00507">[SWS_Can_00507]</a>).</li>
</ul>

<h4>Operating rules: interrupt locks, wakeup, and error counters</h4>
<p><code>Can_DisableControllerInterrupts</code> and <code>Can_EnableControllerInterrupts</code> are reentrant and take effect in a nested manner (<a class="spec-record-ref" data-req="SWS_Can_00231" href="../../spec/record.html?id=SWS_Can_00231">[SWS_Can_00231]</a>, <a class="spec-record-ref" data-req="SWS_Can_00232" href="../../spec/record.html?id=SWS_Can_00232">[SWS_Can_00232]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_3_Can_DisableControllerInterrupts.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_3_Can_DisableControllerInterrupts">SWS CANDriver p. 61</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_4_Can_EnableControllerInterrupts.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_4_Can_EnableControllerInterrupts">SWS CANDriver p. 62</a>). If disabled multiple times, enabling must be performed just as many times. Enabling without prior disabling has no effect. Enabling only activates those interrupts that are permitted according to the current software state.</p>
<p><code>Can_CheckWakeup</code> checks whether wake-up via the bus is present. If the requested controller has detected a wakeup, the driver reports this via <code>EcuM_SetWakeupEvent</code> to EcuM (<a class="spec-record-ref" data-req="SWS_Can_00360" href="../../spec/record.html?id=SWS_Can_00360">[SWS_Can_00360]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_5_Can_CheckWakeup.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_5_Can_CheckWakeup">SWS CANDriver p. 63</a>). The caller is CanIf: during <code>EcuM_CheckWakeup</code>, it queries the affected drivers and transceivers via <code>CanIf_CheckWakeup</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P55_383.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P55_383">SWS CANInterface p. 55</a>). Wakeup events that are statically configured as 'to be polled' are captured by <code>Can_MainFunction_Wakeup</code> (<a class="spec-record-ref" data-req="SWS_Can_00228" href="../../spec/record.html?id=SWS_Can_00228">[SWS_Can_00228]</a>).</p>

<h4>Behavior in the event of an error</h4>
<p>The driver detects bus-off via interrupt or by polling in <code>Can_MainFunction_BusOff</code>. It only makes the necessary register settings and does not perform any hardware recovery. It then reports the event via <code>CanIf_ControllerBusOff</code>; the software state only changes within this callback (<a class="spec-record-ref" data-req="SWS_Can_00227" href="../../spec/record.html?id=SWS_Can_00227">[SWS_Can_00227]</a>, <a class="spec-record-ref" data-req="SWS_Can_00234" href="../../spec/record.html?id=SWS_Can_00234">[SWS_Can_00234]</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine.html" data-snip="SNIP_CLASSIC_CAN_SECTION_7_3_CAN_Controller_State_Machine">SWS CANDriver p. 30</a>). CanIf then sets the PDU channel to <code>CANIF_TX_OFFLINE</code> and notifies CanSM via <code>CanSM_ControllerBusOff</code>. Reinitialization and restart as part of the bus-off recovery only follow afterwards (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P59_388.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P59_388">SWS CANInterface p. 59</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P53_381.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P53_381">SWS CANInterface p. 53</a>, <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_Can_AUTOSAR_SWS_CANI_P121_558.html" data-snip="SNIP_Can_AUTOSAR_SWS_CANI_P121_558">SWS CANInterface p. 121</a>).</p>
