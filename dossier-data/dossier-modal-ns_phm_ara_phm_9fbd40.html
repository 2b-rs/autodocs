<h4>Context</h4>
<p>The namespace <code>ara::phm</code> provides the programming interface for Platform Health Management (PHM) in the AUTOSAR Adaptive Platform. Its core responsibility lies in the functional monitoring of processes and applications with regard to aliveness, timing deadlines, and logical program flows, as well as in the coordination of error reactions.</p>
<p>The architecture in the namespace relies on four central classes:</p>
<ul>
<li><code>SupervisedEntity</code>: Represents the monitored software entity within an application that reports status information.</li>
<li><code>RecoveryAction</code>: Abstract base class for recovery actions executed when errors are detected.</li>
<li><code>PhmErrorDomain</code>: Defines the error domain for error messages of the subsystem.</li>
<li><code>PhmException</code>: Standard exception type for exceptional cases in Platform Health Management.</li>
</ul>
<p>The supervision methods are specified via the enumeration <code>TypeOfSupervision</code> <a class="spec-record-ref" data-req="SWS_PHM_01138" href="../spec/record.html?id=SWS_PHM_01138">[SWS_PHM_01138]</a>. The platform distinguishes between <code>kAliveSupervision</code> (alive supervision), <code>kDeadlineSupervision</code> (compliance with defined time intervals), and <code>kLogicalSupervision</code> (checking the correct order of control flow points). PHM interacts closely with the PHM daemon and the State Management of the Adaptive Platform.</p>

<h4>Lifecycle</h4>
<p>The supervision lifecycle is represented by multi-stage status queries and transitions. At the lowest level, <code>ElementarySupervisionStatus</code> defines the state of an individual supervision function <a class="spec-record-ref" data-req="SWS_PHM_01358" href="../spec/record.html?id=SWS_PHM_01358">[SWS_PHM_01358]</a>:</p>
<ul>
<li><code>kDeactivated</code>: The elementary supervision is inactive.</li>
<li><code>kOK</code>: The supervision is active and no error is present.</li>
<li><code>kFailed</code>: An error has been registered, but is still within the tolerance or debouncing window.</li>
<li><code>kExpired</code>: An error has been finally qualified after the tolerance window expired.</li>
</ul>
<p>To assess the overall state, <code>GlobalSupervisionStatus</code> aggregates the results of corresponding elementary supervisions <a class="spec-record-ref" data-req="SWS_PHM_01137" href="../spec/record.html?id=SWS_PHM_01137">[SWS_PHM_01137]</a>. The global state changes from <code>kDeactivated</code> to <code>kOK</code> as soon as at least one elementary supervision is actively error-free. If errors occur, the status escalates via <code>kFailed</code> and <code>kExpired</code> up to <code>kStopped</code> if the grace period after error qualification is exceeded.</p>

<h4>Usage Path</h4>
<p>The typical sequence for safeguarding an adaptive application comprises several successive phases:</p>
<ol>
<li><strong>Configuration and connection:</strong> The application instantiates a <code>SupervisedEntity</code> for each of the components to be monitored. In doing so, the monitoring parameters are assigned to the modes from <code>TypeOfSupervision</code> (<code>kAliveSupervision</code>, <code>kDeadlineSupervision</code>, or <code>kLogicalSupervision</code>) <a class="spec-record-ref" data-req="SWS_PHM_01138" href="../spec/record.html?id=SWS_PHM_01138">[SWS_PHM_01138]</a>.</li>
<li><strong>Cyclic execution and reporting:</strong> During regular operation, the entity reports checkpoints to the subsystem. As long as the requirements are met, <code>ElementarySupervisionStatus</code> and <code>GlobalSupervisionStatus</code> remain in status <code>kOK</code> <a class="spec-record-ref" data-req="SWS_PHM_01358" href="../spec/record.html?id=SWS_PHM_01358">[SWS_PHM_01358]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01137" href="../spec/record.html?id=SWS_PHM_01137">[SWS_PHM_01137]</a>.</li>
<li><strong>Response handling:</strong> If a monitoring error is qualified (transition to <code>kExpired</code> or <code>kStopped</code>), a derived instance of <code>RecoveryAction</code> is used to initiate corrective actions such as restarts or state changes.</li>
</ol>

<h4>Error Scenarios</h4>
<p>Error states and exception conditions in namespace <code>ara::phm</code> are handled via standardized error structures:</p>
<ul>
<li>The error domain can be obtained via the free function <code>GetPhmDomain()</code>; the call is thread-safe and does not throw exceptions <a class="spec-record-ref" data-req="SWS_PHM_01251" href="../spec/record.html?id=SWS_PHM_01251">[SWS_PHM_01251]</a>.</li>
<li>Specific error causes are typed via the enumeration <code>PhmErrc</code> <a class="spec-record-ref" data-req="SWS_PHM_01240" href="../spec/record.html?id=SWS_PHM_01240">[SWS_PHM_01240]</a>:
  <ul>
  <li><code>kOfferFailed</code>: The service could not be offered because the connection to the PHM daemon failed.</li>
  <li><code>kSMCanNotHandleRecovery</code>: State Management cannot perform the recovery; Platform Health Management takes over the escalation and controls the watchdog.</li>
  <li><code>kServiceNotReady</code>: A concurrent enable or disable operation is already being processed.</li>
  </ul>
</li>
<li>With the helper function <code>MakeErrorCode()</code>, error messages of type <code>ara::core::ErrorCode</code> are created by combining a <code>PhmErrc</code> and vendor-specific additional data <a class="spec-record-ref" data-req="SWS_PHM_01244" href="../spec/record.html?id=SWS_PHM_01244">[SWS_PHM_01244]</a>. In the event of severe errors that require exception handling, <code>PhmException</code> is thrown.</li>
</ul>
