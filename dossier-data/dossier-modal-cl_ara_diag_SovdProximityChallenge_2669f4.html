<h4>Context</h4>
<p>
The class <a class="spec-record-ref" data-req="SWS_DM_01481" href="../spec/record.html?id=SWS_DM_01481">[SWS_DM_01481]</a> defines the application interface for providing and verifying SOVD proximity challenges (proofs of proximity) in the AUTOSAR Adaptive diagnostic module. It mediates directly between the Diagnostic Management (DM or Diagnostic Server) and the application-specific logic as soon as an SOVD operation requires proof of physical vehicle proximity via the model attribute <code>DiagnosticSovdOperation.proximityProofRequired = TRUE</code> <a class="spec-record-ref" data-req="SWS_DM_01398" href="../spec/record.html?id=SWS_DM_01398">[SWS_DM_01398]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=215">AUTOSAR_AP_SWS_Diagnostics, p. 215</a>).
</p>
<p>
Conceptually, the specification assumes that at any given time, only a single proximity challenge usually exists, which is valid across all requesting SOVD clients and all affected operations (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=215">AUTOSAR_AP_SWS_Diagnostics, p. 215</a>). An application therefore normally does not need to manage separate challenges per client. If advanced scenarios nevertheless require differentiated handling, the application can evaluate the passed metadata of type <code>ara::diag::MetaInfo</code> to implement operation- or client-specific checks (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=215">AUTOSAR_AP_SWS_Diagnostics, p. 215</a>).
</p>

<h4>Lifecycle</h4>
<p>
The creation of an object of <code>ara::diag::SovdProximityChallenge</code> takes place explicitly via the constructor <a class="spec-record-ref" data-req="SWS_DM_01480" href="../spec/record.html?id=SWS_DM_01480">[SWS_DM_01480]</a>. In doing so, an <code>ara::core::InstanceSpecifier</code> pointing to the modeled PortPrototype of the interface and the concurrency mode <code>ConcurrencyType</code> (<code>kConcurrent</code> or <code>kNotConcurrent</code>) are passed. After construction, the instance is in the <em>Unoffered</em> state and does not yet receive any messages from the Diagnostic Management.
</p>
<p>
Calling the method <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_01478" href="../spec/record.html?id=SWS_DM_01478">[SWS_DM_01478]</a> subsequently transitions the instance to the <em>Offered</em> state. Only then is the Diagnostic Management authorized and enabled to forward incoming challenge and validation requests to the virtual methods of the handler. Calling <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_01495" href="../spec/record.html?id=SWS_DM_01495">[SWS_DM_01495]</a> stops this forwarding again, and the state returns to <em>Unoffered</em>.
</p>
<p>
The destructor <code>~SovdProximityChallenge()</code> <a class="spec-record-ref" data-req="SWS_DM_01479" href="../spec/record.html?id=SWS_DM_01479">[SWS_DM_01479]</a> terminates the lifetime of the instance. Regarding thread safety, the constructor is specified as thread-safe, whereas <code>Offer()</code>, <code>StopOffer()</code>, and the destructor must not be called in a thread-safe manner (<em>not thread-safe</em>) <a class="spec-record-ref" data-req="SWS_DM_01478" href="../spec/record.html?id=SWS_DM_01478">[SWS_DM_01478]</a>, <a class="spec-record-ref" data-req="SWS_DM_01495" href="../spec/record.html?id=SWS_DM_01495">[SWS_DM_01495]</a>, <a class="spec-record-ref" data-req="SWS_DM_01479" href="../spec/record.html?id=SWS_DM_01479">[SWS_DM_01479]</a>. For the execution of the application-side callback methods, the <code>ConcurrencyType</code> selected in the constructor determines whether the DM invokes them concurrently or synchronized <a class="spec-record-ref" data-req="SWS_DM_01494" href="../spec/record.html?id=SWS_DM_01494">[SWS_DM_01494]</a>, <a class="spec-record-ref" data-req="SWS_DM_01493" href="../spec/record.html?id=SWS_DM_01493">[SWS_DM_01493]</a>.
</p>

<h4>Usage Path</h4>
<p>
The regular interaction is divided into the following phases:
</p>
<ol>
  <li><strong>Initialization and offering:</strong> The application instantiates its class derived from <code>SovdProximityChallenge</code> and activates forwarding via <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_01478" href="../spec/record.html?id=SWS_DM_01478">[SWS_DM_01478]</a>.</li>
  <li><strong>Challenge generation:</strong> If an SOVD client requests a protected operation, the Diagnostic Management calls the method <code>GetChallenge()</code> <a class="spec-record-ref" data-req="SWS_DM_01494" href="../spec/record.html?id=SWS_DM_01494">[SWS_DM_01494]</a>. The application generates the challenge, specifies its validity timestamp (<code>valid_until</code>), and returns the result asynchronously via <code>ara::core::Future&lt;SovdProximityChallengeType&gt;</code>. The DM embeds the challenge into the response body to the client <a class="spec-record-ref" data-req="SWS_DM_01398" href="../spec/record.html?id=SWS_DM_01398">[SWS_DM_01398]</a>.</li>
  <li><strong>Validation:</strong> If the client subsequently sends its response (<code>proximity_response</code>), the DM calls the callback method <code>ValidateResponse()</code> <a class="spec-record-ref" data-req="SWS_DM_01493" href="../spec/record.html?id=SWS_DM_01493">[SWS_DM_01493]</a>. The application logic verifies the passed byte data (<code>ara::core::Span&lt;const ara::core::Byte&gt;</code>) and returns the verification result asynchronously via <code>ara::core::Future&lt;ProximityChallengeValidationResultType&gt;</code>. The lifetime of the buffer data remains guaranteed until fulfillment of the associated promise <a class="spec-record-ref" data-req="SWS_DM_01493" href="../spec/record.html?id=SWS_DM_01493">[SWS_DM_01493]</a>.</li>
  <li><strong>Deactivation:</strong> Prior to shutdown or upon unavailability of the functionality, the application revokes forwarding using <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_01495" href="../spec/record.html?id=SWS_DM_01495">[SWS_DM_01495]</a>.</li>
</ol>
<p>
Interpretation: Managing the validity period (<code>valid_until</code>) and potential internal timeouts is entirely up to the application-specific implementation, since the specification only mentions guideline values such as two minutes (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=215">AUTOSAR_AP_SWS_Diagnostics, p. 215</a>).
</p>

<h4>Error Scenarios</h4>
<p>
During operation, specific error states and model violations can occur:
</p>
<ul>
  <li><strong>Modeling and instantiation errors:</strong> The constructor <a class="spec-record-ref" data-req="SWS_DM_01480" href="../spec/record.html?id=SWS_DM_01480">[SWS_DM_01480]</a> checks the validity of the <code>InstanceSpecifier</code>. If the resolution fails or the identifier does not refer to a <code>PortPrototype</code>, a <code>InstanceSpecifierMappingIntegrityViolation</code> is reported. If the referenced port is not typed by a <code>DiagnosticSovdProximityChallengeInterface</code>, this results in a <code>PortInterfaceMappingViolation</code>. If no modeled process matches the runtime process, a <code>ProcessMappingViolation</code> is present. If the identifier has already been used in the same process, a <code>InstanceSpecifierAlreadyInUseViolation</code> is triggered.</li>
  <li><strong>Offering errors:</strong> <code>Offer()</code> returns a <code>ara::core::Result&lt;void&gt;</code> <a class="spec-record-ref" data-req="SWS_DM_01478" href="../spec/record.html?id=SWS_DM_01478">[SWS_DM_01478]</a>. The call fails with <code>DiagOfferErrc::kAlreadyOffered</code> if the service is already offered, or with <code>DiagOfferErrc::kConfigurationMismatch</code> if the configuration does not match the DEXT model data.</li>
  <li><strong>Standardized error codes:</strong> AUTOSAR defines no standardized error codes for the methods <code>GetChallenge()</code> <a class="spec-record-ref" data-req="SWS_DM_01494" href="../spec/record.html?id=SWS_DM_01494">[SWS_DM_01494]</a> and <code>ValidateResponse()</code> <a class="spec-record-ref" data-req="SWS_DM_01493" href="../spec/record.html?id=SWS_DM_01493">[SWS_DM_01493]</a>; error conditions are handled via the return types or Future objects.</li>
</ul>
