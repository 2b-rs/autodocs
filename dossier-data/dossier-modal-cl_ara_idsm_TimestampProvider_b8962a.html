<p class="ai-level ai-oneliner-lead" data-ai-level="1">Ermöglicht Anwendungen die Bereitstellung systemspezifischer Zeitstempel für Sicherheitsereignisse des IdsM.</p>
<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>ara::idsm::TimestampProvider</code> stellt eine Schnittstelle bereit, über die Anwendungen Zeitstempel für das IdsM-Modul über einen modellierten PPort einspeisen können <a class="spec-record-ref" data-req="SWS_AIDSM_10400" href="../spec/record.html?id=SWS_AIDSM_10400">[SWS_AIDSM_10400]</a>. Die Aktivierung und Deaktivierung der Abfrage-Callbacks erfolgt über die Methoden <code>Offer()</code> und <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>. Instanzen sind unkopierbar, unterstützen Verschiebe-Semantik und erfordern externe Synchronisation bei Methoden ohne garantierte Threadsicherheit.</p>

<h4>Kontext</h4>
<p>Die Klasse <code>ara::idsm::TimestampProvider</code> dient als Schnittstelle zur Bereitstellung von Zeitstempeln für das Intrusion Detection System Manager (IdsM) Modul innerhalb der AUTOSAR Adaptive Platform <a class="spec-record-ref" data-req="SWS_AIDSM_10400" href="../spec/record.html?id=SWS_AIDSM_10400">[SWS_AIDSM_10400]</a>. Sicherheitsrelevante Ereignisse und Protokolle im IdsM erfordern verlässliche Zeitinformationen, die durch diese Provider-Klasse von der Plattform oder einer anwendungsspezifischen Zeitquelle bezogen werden. Eine Instanz von <code>TimestampProvider</code> wird an einen über ein <code>ara::core::InstanceSpecifier</code> modellierten PPort gebunden <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>. Da die Methode <code>GetTimestamp()</code> als rein virtuelle Callback-Funktion definiert ist <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a>, fungiert <code>TimestampProvider</code> als abstrakte Basisklasse, von der konkrete Implementierungen abgeleitet werden müssen.</p>

<h4>Lebenszyklus</h4>
<p>Die Erzeugung eines Zeitstempel-Providers erfolgt explizit über den Konstruktor unter Angabe des zugehörigen <code>ara::core::InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>. Dieser Konstruktor ist als threadsicher deklariert. Kopieroperationen sind vollständig unterbunden: Sowohl der Kopierkonstruktor <a class="spec-record-ref" data-req="SWS_AIDSM_10404" href="../spec/record.html?id=SWS_AIDSM_10404">[SWS_AIDSM_10404]</a> als auch der Kopierzuweisungsoperator <a class="spec-record-ref" data-req="SWS_AIDSM_10406" href="../spec/record.html?id=SWS_AIDSM_10406">[SWS_AIDSM_10406]</a> sind gelöscht (<code>= delete</code>). Instanzen besitzen somit eine eindeutige Identität und können nicht dupliziert werden.</p>
<p>Dagegen unterstützt die Klasse Move-Semantik: Der Verschiebekonstruktor überträgt bestehende Ressourcen threadsicher auf ein neues Objekt <a class="spec-record-ref" data-req="SWS_AIDSM_10403" href="../spec/record.html?id=SWS_AIDSM_10403">[SWS_AIDSM_10403]</a>. Die Verschiebezuweisung über <code>operator=</code> ist ebenfalls vorhanden, im Gegensatz zum Konstruktor jedoch nicht threadsicher <a class="spec-record-ref" data-req="SWS_AIDSM_10405" href="../spec/record.html?id=SWS_AIDSM_10405">[SWS_AIDSM_10405]</a>. Der Lebenszyklus der aktiven Dienstbereitstellung wird nach der Instanziierung explizit gesteuert: Über die Methode <code>Offer()</code> wird die Registrierung für den IdsM aktiviert <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>. Mit <code>StopOffer()</code> wird die Bereitstellung wieder unterbunden <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>. Die Freigabe der Instanz erfolgt über den virtuellen Destruktor <a class="spec-record-ref" data-req="SWS_AIDSM_10402" href="../spec/record.html?id=SWS_AIDSM_10402">[SWS_AIDSM_10402]</a>, welcher als nicht threadsicher spezifiziert ist. Interpretation: Vor der Zerstörung einer Instanz dürfte typischerweise <code>StopOffer()</code> aufgerufen werden, um sicherzustellen, dass keine ausstehenden Aufrufe durch den IdsM mehr erfolgen. <a class="interp-q interp-q-open" data-q="Q-fcf21d9d93d053a6" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-fcf21d9d93d053a6" title="Frage Q-fcf21d9d93d053a6 (offen): Zerstörungsabfolge: Vor der Freigabe über den Destruktor dürfte StopOffer() aufgerufen werden müssen.">Frage Q-fcf21d9d93d053a6 (offen)</a></p>

<h4>Nutzungspfad</h4>
<p>Die typische Nutzung erfordert die Ableitung einer anwendungsspezifischen Klasse, die die Methode <code>GetTimestamp()</code> überschreibt und den aktuellen Zeitstempel als <code>TimestampType</code> zurückliefert <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a>. Sobald die Instanz für den entsprechenden Port erzeugt wurde <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>, signalisiert die Anwendung über den Aufruf von <code>Offer()</code> die Betriebsbereitschaft <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>. Ab diesem Zeitpunkt kann der IdsM autonom die Callback-Methode <code>GetTimestamp()</code> abrufen, um Ereignisse zeitlich zu verorten. Soll der Dienst beendet oder die Komponente heruntergefahren werden, entzieht <code>StopOffer()</code> die Verfügbarkeit der Schnittstelle <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>.</p>

<h4>Fehlerszenarien</h4>
<p>Alle Methoden der Schnittstelle sind als <code>noexcept</code> deklariert und werfen keine C++-Ausnahmen. Fehler bei der Aktivierung der Dienstbereitstellung werden stattdessen über den Rückgabetyp <code>ara::core::Result&lt;void&gt;</code> von <code>Offer()</code> transportiert <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>. Interpretation: Schlägt die Registrierung am Kommunikations- oder Plattform-Framework fehl (beispielsweise aufgrund einer unpassenden Port-Konfiguration), enthält das zurückgegebene <code>Result</code> einen entsprechenden Fehlercode, der vor der Weiterverwendung geprüft werden muss. <a class="interp-q interp-q-open" data-q="Q-5a971906b458dd6f" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-5a971906b458dd6f" title="Frage Q-5a971906b458dd6f (offen): Registrierungsfehler: Das ara::core::Result&lt;void&gt; von Offer() dürfte Fehler bei ungültiger Instanzspezifikation oder interner Registrierung signalisieren.">Frage Q-5a971906b458dd6f (offen)</a></p>
<p>Besondere Aufmerksamkeit erfordert das Nebenläufigkeitsverhalten: Weder der Destruktor <a class="spec-record-ref" data-req="SWS_AIDSM_10402" href="../spec/record.html?id=SWS_AIDSM_10402">[SWS_AIDSM_10402]</a> noch die Methoden <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>, <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>, <code>operator=(&amp;&amp;)</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10405" href="../spec/record.html?id=SWS_AIDSM_10405">[SWS_AIDSM_10405]</a> oder <code>GetTimestamp()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a> sind als threadsicher eingestuft. Aufrufer müssen daher sicherstellen, dass Lebenszyklusoperationen und Callback-Verarbeitungen thread-synchronisiert ablaufen und keine Datenrennen entstehen.</p>
