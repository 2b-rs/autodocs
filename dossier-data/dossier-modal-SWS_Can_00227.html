<p>Die geplante Hauptfunktion <code>Can_MainFunction_BusOff</code> dient dem zyklischen Polling von Bus-Off-Ereignissen der CAN-Controller, sofern diese statisch als zu pollen konfiguriert sind <a class="spec-record-ref" data-req="SWS_Can_00227" href="../../spec/record.html?id=SWS_Can_00227">[SWS_Can_00227]</a>, <a class="spec-record-ref" data-req="SWS_Can_00109" href="../../spec/record.html?id=SWS_Can_00109">[SWS_Can_00109]</a>. Sie besitzt die Signatur <code>void Can_MainFunction_BusOff(void)</code>, nimmt keine Parameter entgegen, gibt keinen Wert zurück und wird über den Header <code>SchM_Can.h</code> für die Ablaufsteuerung bereitgestellt <a class="spec-record-ref" data-req="SWS_Can_00227" href="../../spec/record.html?id=SWS_Can_00227">[SWS_Can_00227]</a>.</p>

  <h4>Verwendung und Zusammenspiel</h4>
  <p>Hardware-Ereignisse können im CAN-Treiber entweder per Interrupt oder durch Polling entsprechender Statusflags erfasst werden, wobei die Konfiguration der Abfrage hardwareabhängig ist <a class="spec-record-ref" data-req="SWS_Can_00099" href="../../spec/record.html?id=SWS_Can_00099">[SWS_Can_00099]</a>. Der Treiber kann auch so konfiguriert werden, dass vollständig auf Interrupts verzichtet wird <a class="spec-record-ref" data-req="SWS_Can_00007" href="../../spec/record.html?id=SWS_Can_00007">[SWS_Can_00007]</a>. Wird systemweit überhaupt kein Polling eingesetzt, darf das Can-Modul die Funktion als leeres Makro implementieren <a class="spec-record-ref" data-req="SWS_Can_00183" href="../../spec/record.html?id=SWS_Can_00183">[SWS_Can_00183]</a>.</p>

  <p>Wird in <code>Can_MainFunction_BusOff</code> ein Bus-Off-Ereignis über Statusbits erkannt, nimmt das Modul notwendige Registereinstellungen vor – etwa zur Vermeidung einer automatischen Hardware-Erholung <a class="docref internal-spec-ref" href="../../spec/record.html?doc=SWS_CANDriver&amp;page=30">SWS_CANDriver §7.3 „CAN Controller State Machine“</a>, <a class="spec-record-ref" data-req="SWS_Can_91010" href="../../spec/record.html?id=SWS_Can_91010">[SWS_Can_91010]</a>. Anschließend benachrichtigt das Modul die übergeordnete Schicht <code>CanIf</code> über den zugehörigen Callback, in welchem die Software-Zustandsänderung des Controllers erfolgt <a class="docref internal-spec-ref" href="../../spec/record.html?doc=SWS_CANDriver&amp;page=30">SWS_CANDriver §7.3 „CAN Controller State Machine“</a>.</p>

  <h4>Aufrufkontext und Einschränkungen</h4>
  <p>Bei gepolltem Betrieb ist der Aufrufkontext der Callback-Benachrichtigung nicht die ISR, sondern die ausführende Task der <code>Can_MainFunction_BusOff</code>; dennoch müssen alle Callback-Funktionen so realisiert sein, als ob sie aus dem ISR-Kontext aufgerufen würden <a class="docref internal-spec-ref" href="../../spec/record.html?doc=SWS_CANDriver&amp;page=41">SWS_CANDriver §7.9 „Notification concept“</a>. Hinsichtlich der Reentranz enthält der Payload keine expliziten Angaben; vermutlich ist die Funktion nicht reentrant, da sie auf globale Controller-Register und Zustände zugreift.</p>
