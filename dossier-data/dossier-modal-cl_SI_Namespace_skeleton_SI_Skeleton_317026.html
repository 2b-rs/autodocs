<h4>Context</h4>
<p>The generated class <code>&lt;SI-Namespace&gt;::skeleton::&lt;SI&gt;Skeleton</code> forms the server-side foundation for providing an AUTOSAR Adaptive service interface within the module <code>com</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=39">SWS CommunicationManagement p. 39</a>). It accepts incoming method calls, manages outgoing events and fields, and controls the functional visibility of the service in the overall system.</p>
<p>As an interface instance, the skeleton interacts primarily with three roles:</p>
<ul>
<li><strong>Server application:</strong> Creates the skeleton instance, implements the service-relevant method bodies, and serves functional requirements.</li>
<li><strong>Communication infrastructure / bindings:</strong> The middleware handles the deserialization of requests, routing via protocol-specific bindings, as well as permission and grant checks (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=40">SWS CommunicationManagement p. 40</a>).</li>
<li><strong>Service consumers (Proxies):</strong> Call methods provided over the network or subscribe to provided events and fields.</li>
</ul>
<p>The skeleton aggregates type-dependent members such as events (<code>events::&lt;Event&gt;</code>, <a class="spec-record-ref" data-req="SWS_CM_99557" href="../spec/record.html?id=SWS_CM_99557">[SWS_CM_99557]</a>), fields (<code>fields::&lt;Field&gt;</code>, <a class="spec-record-ref" data-req="SWS_CM_99558" href="../spec/record.html?id=SWS_CM_99558">[SWS_CM_99558]</a>), and trigger elements (<code>triggers::&lt;Trigger&gt;</code>, <a class="spec-record-ref" data-req="SWS_CM_99559" href="../spec/record.html?id=SWS_CM_99559">[SWS_CM_99559]</a>). Furthermore, structures for output parameters in method calls (<code>&lt;MethodOutArgType&gt; &lt;MethodOutArg&gt;</code>, <a class="spec-record-ref" data-req="SWS_CM_11550" href="../spec/record.html?id=SWS_CM_11550">[SWS_CM_11550]</a>) are provided. For protection against transmission errors and end-to-end integrity violations, the class offers registration methods for error handlers (<a class="spec-record-ref" data-req="SWS_CM_00093" href="../spec/record.html?id=SWS_CM_00093">[SWS_CM_00093]</a>, <a class="spec-record-ref" data-req="SWS_CM_10470" href="../spec/record.html?id=SWS_CM_10470">[SWS_CM_10470]</a>).</p>

<h4>Lifecycle</h4>
<p>A skeleton is created via dedicated constructors of the server application. Depending on system design and mapping, three constructor variants are available:</p>
<ul>
<li>Instantiation via an explicit instance identifier <code>ara::com::InstanceIdentifier</code> (<a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>).</li>
<li>Model-based binding via a <code>ara::core::InstanceSpecifier</code> that references a PortPrototype (<a class="spec-record-ref" data-req="SWS_CM_00152" href="../spec/record.html?id=SWS_CM_00152">[SWS_CM_00152]</a>).</li>
<li>Instantiation via a <code>ara::com::InstanceIdentifierContainer</code> for simultaneously addressing multiple instances or bindings (<a class="spec-record-ref" data-req="SWS_CM_00153" href="../spec/record.html?id=SWS_CM_00153">[SWS_CM_00153]</a>).</li>
</ul>
<p>All constructors accept as an optional parameter the mode <code>ara::com::MethodCallProcessingMode</code>, which defaults to <code>kEvent</code> (<a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>, <a class="spec-record-ref" data-req="SWS_CM_00152" href="../spec/record.html?id=SWS_CM_00152">[SWS_CM_00152]</a>, <a class="spec-record-ref" data-req="SWS_CM_00153" href="../spec/record.html?id=SWS_CM_00153">[SWS_CM_00153]</a>).</p>
<p>Regarding ownership, a skeleton has a strict identity: copy constructor (<a class="spec-record-ref" data-req="SWS_CM_00134" href="../spec/record.html?id=SWS_CM_00134">[SWS_CM_00134]</a>) and copy assignment operator (<a class="spec-record-ref" data-req="SWS_CM_11548" href="../spec/record.html?id=SWS_CM_11548">[SWS_CM_11548]</a>) are deleted (<code>delete</code>). A transfer of resources is possible via the move constructor (<a class="spec-record-ref" data-req="SWS_CM_00135" href="../spec/record.html?id=SWS_CM_00135">[SWS_CM_00135]</a>) and move assignment operator (<a class="spec-record-ref" data-req="SWS_CM_11549" href="../spec/record.html?id=SWS_CM_11549">[SWS_CM_11549]</a>). Note that the move constructor is specified as not exception-safe, whereas the move assignment operator is declared as <code>noexcept</code>.</p>
<p>After successful construction, the skeleton initially remains in an inactive state. Only by calling <code>OfferService()</code> (<a class="spec-record-ref" data-req="SWS_CM_00101" href="../spec/record.html?id=SWS_CM_00101">[SWS_CM_00101]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">ARAComAPI p. 10</a>) is the service made visible on the network and opened for requests. Service provision can be paused or terminated at any time using <code>StopOfferService()</code> (<a class="spec-record-ref" data-req="SWS_CM_00111" href="../spec/record.html?id=SWS_CM_00111">[SWS_CM_00111]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">ARAComAPI p. 10</a>). Interpretation: Before the final destruction of the skeleton instance, <code>StopOfferService()</code> should be called to ensure proper deregistration before the virtual destructor <code>~&lt;SI&gt;Skeleton()</code> (<a class="spec-record-ref" data-req="SWS_CM_11370" href="../spec/record.html?id=SWS_CM_11370">[SWS_CM_11370]</a>) is called.</p>

<h4>Usage Path</h4>
<p>The typical use of a service skeleton is divided into the following successive phases:</p>
<ol>
<li><strong>Instantiation:</strong> Creation of the object while assigning the InstanceIdentifier or InstanceSpecifier and defining the processing mode (<a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>, <a class="spec-record-ref" data-req="SWS_CM_00152" href="../spec/record.html?id=SWS_CM_00152">[SWS_CM_00152]</a>).</li>
<li><strong>Configuration and handler registration:</strong> Registration of optional error handling routines for transport errors via <code>SetTransportFaultConditionHandler()</code> (<a class="spec-record-ref" data-req="SWS_CM_00093" href="../spec/record.html?id=SWS_CM_00093">[SWS_CM_00093]</a>, <a class="spec-record-ref" data-req="SWS_CM_00094" href="../spec/record.html?id=SWS_CM_00094">[SWS_CM_00094]</a>) or overriding the virtual <code>E2EErrorHandler()</code> (<a class="spec-record-ref" data-req="SWS_CM_10470" href="../spec/record.html?id=SWS_CM_10470">[SWS_CM_10470]</a>). Furthermore, any existing fields must be initialized in advance.</li>
<li><strong>Offering the service:</strong> Activation of the skeleton via <code>OfferService()</code> (<a class="spec-record-ref" data-req="SWS_CM_00101" href="../spec/record.html?id=SWS_CM_00101">[SWS_CM_00101]</a>). The method returns a <code>ara::core::Result&lt;void&gt;</code> indicating success or precondition errors.</li>
<li><strong>Method processing:</strong> If the skeleton is operated in <code>MethodCallProcessingMode::kPoll</code> mode, the application actively controls the execution of pending client calls via <code>ProcessNextMethodCall()</code> (<a class="spec-record-ref" data-req="SWS_CM_00199" href="../spec/record.html?id=SWS_CM_00199">[SWS_CM_00199]</a>). This executes the pending method directly in the context of the calling thread. For event-driven modes (<code>kEvent</code>), the middleware handles the dispatching.</li>
<li><strong>Stopping the service and termination:</strong> Calling <code>StopOfferService()</code> (<a class="spec-record-ref" data-req="SWS_CM_00111" href="../spec/record.html?id=SWS_CM_00111">[SWS_CM_00111]</a>) withdraws the visibility of the service on the network, followed by releasing the instance via the destructor (<a class="spec-record-ref" data-req="SWS_CM_11370" href="../spec/record.html?id=SWS_CM_11370">[SWS_CM_11370]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>Specific error conditions and runtime violations (violations) are specified for the operation and initialization of the skeleton:</p>
<p><strong>Error codes for OfferService (<a class="spec-record-ref" data-req="SWS_CM_00101" href="../spec/record.html?id=SWS_CM_00101">[SWS_CM_00101]</a>):</strong> In the event of an error, the return value <code>ara::core::Result&lt;void&gt;</code> conveys values of the enum <code>ara::com::ComErrc</code> with defined rollback semantics:</p>
<ul>
<li><code>ComErrc::kFieldValueNotInitialized</code>: A defined field has not yet been initialized prior to calling <code>OfferService()</code>.</li>
<li><code>ComErrc::kFieldSetHandlerNotSet</code>: No SetHandler was registered for a field with set functionality.</li>
<li><code>ComErrc::kCommunicationFailure</code>: A recoverable network or communication error occurred in the binding, or the secure connection failed.</li>
</ul>
<p><strong>Runtime violations (violations):</strong></p>
<ul>
<li><em>Construction errors:</em> If the permission check fails, <code>InsufficientPermissionsViolation</code> is triggered (<a class="spec-record-ref" data-req="SWS_CM_00130" href="../spec/record.html?id=SWS_CM_00130">[SWS_CM_00130]</a>, <a class="spec-record-ref" data-req="SWS_CM_00152" href="../spec/record.html?id=SWS_CM_00152">[SWS_CM_00152]</a>). Invalid processing modes result in <code>WrongMethodCallProcessingModeViolation</code>. When instantiating via <code>InstanceSpecifier</code> (<a class="spec-record-ref" data-req="SWS_CM_00152" href="../spec/record.html?id=SWS_CM_00152">[SWS_CM_00152]</a>), faulty mappings lead to <code>InstanceSpecifierMappingIntegrityViolation</code>, <code>PortInterfaceMappingViolation</code>, <code>ProcessMappingViolation</code>, or <code>InstanceSpecifierAlreadyInUseViolation</code>.</li>
<li><em>Errors during method processing:</em> If <code>ProcessNextMethodCall()</code> is called even though the skeleton is configured with <code>kEvent</code> or <code>kEventSingleThread</code>, this leads to the violation <code>WrongMethodCallProcessingModeViolation</code> (<a class="spec-record-ref" data-req="SWS_CM_00199" href="../spec/record.html?id=SWS_CM_00199">[SWS_CM_00199]</a>).</li>
<li><em>Invalid handlers:</em> If an empty or null handler is passed to <code>SetTransportFaultConditionHandler()</code>, <code>InvalidHandlerViolation</code> is signaled (<a class="spec-record-ref" data-req="SWS_CM_00093" href="../spec/record.html?id=SWS_CM_00093">[SWS_CM_00093]</a>).</li>
<li><em>Destruction errors:</em> If references are still held during the destruction of the skeleton, a <code>DanglingSamplesViolation</code> can be triggered (<a class="spec-record-ref" data-req="SWS_CM_11370" href="../spec/record.html?id=SWS_CM_11370">[SWS_CM_11370]</a>).</li>
<li><em>E2E error handling:</em> In the case of CRC errors in E2E monitoring, the server code must not trust the <code>DataID</code> passed to <code>E2EErrorHandler()</code>, as data integrity errors can affect the message headers (<a class="spec-record-ref" data-req="SWS_CM_10470" href="../spec/record.html?id=SWS_CM_10470">[SWS_CM_10470]</a>). In addition, this handler is not reentrant.</li>
</ul>
