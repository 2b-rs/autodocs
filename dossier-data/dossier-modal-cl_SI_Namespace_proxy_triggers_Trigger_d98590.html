<div class="ai-level" data-ai-level="2">
<p>Die Klasse <code>&lt;SI-Namespace&gt;::proxy::triggers::&lt;Trigger&gt;</code> ermöglicht Client-Anwendungen das Abonnieren datenloser Trigger-Impulse über das Communication Management <a class="spec-record-ref" data-req="SWS_CM_00723" href="../spec/record.html?id=SWS_CM_00723">[SWS_CM_00723]</a>. Nach Registrierung eines Callbacks via <code>SetReceiveHandler()</code> liest die Anwendung neu eingetroffene Impulse mit <code>GetNewTriggers()</code> ab <a class="spec-record-ref" data-req="SWS_CM_00226" href="../spec/record.html?id=SWS_CM_00226">[SWS_CM_00226]</a>, <a class="spec-record-ref" data-req="SWS_CM_00250" href="../spec/record.html?id=SWS_CM_00250">[SWS_CM_00250]</a>. Ausnahmesicherheit ist bis auf <code>UnsetReceiveHandler()</code> standardmäßig gewährleistet <a class="spec-record-ref" data-req="SWS_CM_11614" href="../spec/record.html?id=SWS_CM_11614">[SWS_CM_11614]</a>.</p>

<div class="ai-level" data-ai-level="4">
<h4>Kontext</h4>
<p>Die generierte Proxy-Klasse <code>&lt;SI-Namespace&gt;::proxy::triggers::&lt;Trigger&gt;</code> repräsentiert auf Client-Seite genau ein Trigger-Element, das in der Service-Schnittstelle in der Rolle <em>trigger</em> modelliert ist <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=39">AUTOSAR_AP_SWS_CommunicationManagement §8 „Service proxy Trigger class“</a>. Anders als ereignisbasierte Datenströme übermittelt ein Trigger reine Auslöseimpulse ohne Nutzdaten. Die Klasse dient als Vermittlungsinstanz zwischen der nutzenden Client-Anwendung, dem Communication Management (ara::com) sowie dem E2E-Überwachungssystem. Ihre Kernaufgabe besteht darin, das Abonnement für eingehende Trigger zu steuern, Benachrichtigungs-Callbacks für das Eintreffen von Impulsen oder Statusänderungen zu registrieren und die Anzahl eingetroffener Auslösungen über einen Zähler bereitzustellen <a class="spec-record-ref" data-req="SWS_CM_00226" href="../spec/record.html?id=SWS_CM_00226">[SWS_CM_00226]</a>, <a class="spec-record-ref" data-req="SWS_CM_00250" href="../spec/record.html?id=SWS_CM_00250">[SWS_CM_00250]</a>.</p>

<h4>Lebenszyklus</h4>
<p>Die Lebensdauer einer Instanz von <code>&lt;SI-Namespace&gt;::proxy::triggers::&lt;Trigger&gt;</code> ist an die Lebensdauer des übergeordneten Service-Proxy-Objekts gebunden, in dem sie als Klassenmitglied existiert. Zustandsbezogen durchläuft das Trigger-Abonnement mehrere Phasen, die durch <code>ara::com::SubscriptionState</code> abgebildet und über <code>GetSubscriptionState()</code> abgefragt werden können <a class="spec-record-ref" data-req="SWS_CM_01105" href="../spec/record.html?id=SWS_CM_01105">[SWS_CM_01105]</a>:</p>
<ul>
<li><strong>Nicht abonniert:</strong> Ausgangszustand vor dem Aufruf von <code>Subscribe()</code> oder nach einem erfolgreichen <code>Unsubscribe()</code> <a class="spec-record-ref" data-req="SWS_CM_00723" href="../spec/record.html?id=SWS_CM_00723">[SWS_CM_00723]</a>, <a class="spec-record-ref" data-req="SWS_CM_00810" href="../spec/record.html?id=SWS_CM_00810">[SWS_CM_00810]</a>.</li>
<li><strong>Abonnement schwebend (<code>kSubscriptionPending</code>):</strong> Zwischenzustand nach Auslösen von <code>Subscribe()</code> während der Bestätigung des Abonnements <a class="spec-record-ref" data-req="SWS_CM_00723" href="../spec/record.html?id=SWS_CM_00723">[SWS_CM_00723]</a>.</li>
<li><strong>Abonniert (<code>kSubscribed</code>):</strong> Das Abonnement ist aktiv; eintreffende Trigger-Impulse erhöhen den internen Zähler und führen zur Benachrichtigung des registrierten Handlers <a class="spec-record-ref" data-req="SWS_CM_00226" href="../spec/record.html?id=SWS_CM_00226">[SWS_CM_00226]</a>, <a class="spec-record-ref" data-req="SWS_CM_00250" href="../spec/record.html?id=SWS_CM_00250">[SWS_CM_00250]</a>.</li>
</ul>
<p>Ein erneuter Aufruf von <code>Subscribe()</code> in den Zuständen <code>kSubscribed</code> oder <code>kSubscriptionPending</code> bleibt wirkungslos und kehrt ohne Aktion zurück <a class="spec-record-ref" data-req="SWS_CM_00723" href="../spec/record.html?id=SWS_CM_00723">[SWS_CM_00723]</a>. Analog verhält sich <code>Unsubscribe()</code>, falls das Trigger-Abonnement zum Zeitpunkt des Aufrufs nicht besteht <a class="spec-record-ref" data-req="SWS_CM_00810" href="../spec/record.html?id=SWS_CM_00810">[SWS_CM_00810]</a>. Zur Beobachtung von Zustandswechseln kann die Anwendung mittels <code>SetSubscriptionStateChangeHandler()</code> einen entsprechenden Callback hinterlegen <a class="spec-record-ref" data-req="SWS_CM_01107" href="../spec/record.html?id=SWS_CM_01107">[SWS_CM_01107]</a> oder über <code>UnsetSubscriptionStateChangeHandler()</code> deregistrieren <a class="spec-record-ref" data-req="SWS_CM_01108" href="../spec/record.html?id=SWS_CM_01108">[SWS_CM_01108]</a>.</p>

<h4>Nutzungspfad</h4>
<p>Ein typischer Nutzungspfad zur ereignisgesteuerten Verarbeitung von Trigger-Signalen umfasst die Konfiguration der Callbacks, die Aktivierung des Abonnements und die Zählerabfrage:</p>
<ol>
<li><strong>Handler-Registrierung:</strong> Die Anwendung hinterlegt optional einen Zustandshandler via <code>SetSubscriptionStateChangeHandler()</code> <a class="spec-record-ref" data-req="SWS_CM_01107" href="../spec/record.html?id=SWS_CM_01107">[SWS_CM_01107]</a> sowie zwingend einen Empfangshandler via <code>SetReceiveHandler()</code> <a class="spec-record-ref" data-req="SWS_CM_00250" href="../spec/record.html?id=SWS_CM_00250">[SWS_CM_00250]</a>. Für nebenläufige Architekturen stehen Überladungen mit dediziertem <code>ExecutorT</code> bereit, die den Ausführungskontext für asynchrone Berechnungen festlegen <a class="spec-record-ref" data-req="SWS_CM_00352" href="../spec/record.html?id=SWS_CM_00352">[SWS_CM_00352]</a>, <a class="spec-record-ref" data-req="SWS_CM_01106" href="../spec/record.html?id=SWS_CM_01106">[SWS_CM_01106]</a>.</li>
<li><strong>Abonnement anfordern:</strong> Mittels <code>Subscribe()</code> wird das Trigger-Abonnement gestartet <a class="spec-record-ref" data-req="SWS_CM_00723" href="../spec/record.html?id=SWS_CM_00723">[SWS_CM_00723]</a>.</li>
<li><strong>Signalempfang und Zählerabruf:</strong> Sobald ein Trigger-Impuls eintrifft, ruft das Communication Management den <code>TriggerReceiveHandler</code> parameterlos auf <a class="spec-record-ref" data-req="SWS_CM_00250" href="../spec/record.html?id=SWS_CM_00250">[SWS_CM_00250]</a>. Innerhalb dieses Handlers ruft die Anwendung <code>GetNewTriggers()</code> auf, um den Trigger-Zähler zu aktualisieren und die Anzahl der seit dem letzten Aufruf eingetroffenen Impulse auszulesen <a class="spec-record-ref" data-req="SWS_CM_00226" href="../spec/record.html?id=SWS_CM_00226">[SWS_CM_00226]</a>. Der Wert <code>0</code> signalisiert dabei, dass keine neuen Impulse vorliegen.</li>
<li><strong>Beendigung:</strong> Zum geordneten Abbau ruft die Anwendung <code>Unsubscribe()</code> auf <a class="spec-record-ref" data-req="SWS_CM_00810" href="../spec/record.html?id=SWS_CM_00810">[SWS_CM_00810]</a> und entfernt gesetzte Handler über <code>UnsetReceiveHandler()</code> <a class="spec-record-ref" data-req="SWS_CM_11614" href="../spec/record.html?id=SWS_CM_11614">[SWS_CM_11614]</a> sowie <code>UnsetSubscriptionStateChangeHandler()</code> <a class="spec-record-ref" data-req="SWS_CM_01108" href="../spec/record.html?id=SWS_CM_01108">[SWS_CM_01108]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Die Spezifikation definiert spezifische Verletzungsbedingungen (Violations) und Ausnahme-Sicherheiten für die Schnittstellenmethoden:</p>
