<h4>Std_Types.h as a common type base of BSW, RTE, and application</h4>
<p>The module <code>std</code> does not provide any functions. It exclusively provides types and symbols, all of which are available via <code>Std_Types.h</code>. These include the return type <code>Std_ReturnType</code> <a class="spec-record-ref" data-req="SWS_Std_00005" href="../../spec/record.html?id=SWS_Std_00005">[SWS_Std_00005]</a>, the version structure <code>Std_VersionInfoType</code> <a class="spec-record-ref" data-req="SWS_Std_00015" href="../../spec/record.html?id=SWS_Std_00015">[SWS_Std_00015]</a>, and the function pointer type <code>Std_ExtractProtocolHeaderFieldsType</code> <a class="spec-record-ref" data-req="SWS_Std_91003" href="../../spec/record.html?id=SWS_Std_91003">[SWS_Std_91003]</a>. The system boundary defines the BSW requirement for the standard type header: all AUTOSAR standard types and constants belong in <code>Std_Types.h</code>. This header includes <code>Platform_Types.h</code> and <code>Compiler.h</code>. It defines <code>Std_ReturnType</code>, <code>E_OK</code>/<code>E_NOT_OK</code>, as well as <code>STD_ON</code>, <code>STD_OFF</code>, <code>STD_HIGH</code>, <code>STD_LOW</code>, <code>STD_ACTIVE</code>, and <code>STD_IDLE</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files.html" data-snip="SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files">SRS BSWGeneral p. 62</a>.</p>
<p>Every module that uses AUTOSAR integer types or the standard return type includes <code>Std_Types.h</code>. The goal is uniform, platform-wide access to the standard types <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files.html" data-snip="SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files">SRS BSWGeneral p. 62</a>. RTE and BSW modules explicitly share the same return type <a class="spec-record-ref" data-req="SWS_Std_00005" href="../../spec/record.html?id=SWS_Std_00005">[SWS_Std_00005]</a>. The BSW scheduler also returns it for <code>SchM_Call</code> across partition boundaries <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWDISTRIBUTIONGUIDE_SECTION_2_2_3_Using_the_BSW_Scheduler_for_Inter_Partition_Communication.html" data-snip="SNIP_CLASSIC_BSWDISTRIBUTIONGUIDE_SECTION_2_2_3_Using_the_BSW_Scheduler_for_Inter_Partition_Communication">BSWDistributionGuide p. 13</a>. In complex device drivers, the configuration headers with their <code>STD_ON</code>/<code>STD_OFF</code> switches also build on <code>Std_Types.h</code> <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-988a28fda6aee7a2.html" data-snip="FIG-988a28fda6aee7a2">CDD-Guideline p. 14</a>.</p>

<h4>Std_ReturnType: Value range, bit layout, and module-specific extensions</h4>
<p><code>Std_ReturnType</code> is defined as <code>typedef uint8 Std_ReturnType;</code>. <code>E_OK</code> (0) and <code>E_NOT_OK</code> (1) are pre-assigned. The range 0x02–0x3F is available for user-specific errors <a class="spec-record-ref" data-req="SWS_Std_00005" href="../../spec/record.html?id=SWS_Std_00005">[SWS_Std_00005]</a>. Normally, only <code>E_OK</code> and <code>E_NOT_OK</code> are to be used. If these values are not sufficient, a module may define additional values in the six low-order bits and names them with its module prefix. Bit 7 and Bit 8 are reserved and are defined by the RTE specification <a class="spec-record-ref" data-req="SWS_Std_00011" href="../../spec/record.html?id=SWS_Std_00011">[SWS_Std_00011]</a>.</p>
<p>The RTE justifies the base type <code>uint8</code> with compatibility. An <code>enum</code> could turn out to have different sizes in RTEs from different vendors. Therefore, the error values are declared via <code>#define</code>. In the reserved bits lie, for example, the overlayable error <code>RTE_E_LOST_DATA</code> (64) and the immediate infrastructure errors from 128 onward, for example <code>RTE_E_COM_STOPPED</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_1_Returned_by_AUTOSAR_Services_to_indicate_a.html" data-snip="SNIP_CLASSIC_STD_SECTION_1_Returned_by_AUTOSAR_Services_to_indicate_a">SWS RTE p. 586</a>. This table originates from R23-11. For R20-11, the bit reservation itself is normatively defined by <a class="spec-record-ref" data-req="SWS_Std_00011" href="../../spec/record.html?id=SWS_Std_00011">[SWS_Std_00011]</a>.</p>
<p>In the BSW UML model, a module-specific extension is modeled as a class <code>&lt;Ma&gt;_ReturnType</code> with the stereotype <code>«extra_literals»</code>. Its values bear the module prefix and lie in the range 0x02–0x3f. According to the same guide, <code>Std_ReturnType</code> is also the only permissible return type for operations in client/server service interfaces <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWUMLMODELMODELINGGUIDE_SECTION_2_3_8_3_Std_ReturnType_Extensions.html" data-snip="SNIP_CLASSIC_BSWUMLMODELMODELINGGUIDE_SECTION_2_3_8_3_Std_ReturnType_Extensions">BSWUMLModelModelingGuide p. 28</a>. Examples are <code>Csm_ReturnType</code> with <code>CSM_E_BUSY</code> = 2 <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-955033528fbb5cef.html" data-snip="FIG-955033528fbb5cef">TR BSWUMLModelModelingGuide p. 29</a> and the extension <code>CAN_BUSY</code> = 0x02 of the CAN driver for <code>Can_Write()</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_2_6_Extension_to_Std_ReturnType.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_2_6_Extension_to_Std_ReturnType">SWS CANDriver p. 54</a>.</p>

<h4>Version query via Std_VersionInfoType</h4>
<p><code>Std_VersionInfoType</code> is a structure with the fields <code>vendorID</code> and <code>moduleID</code> (each <code>uint16</code>) as well as <code>sw_major_version</code>, <code>sw_minor_version</code>, and <code>sw_patch_version</code> (each <code>uint8</code>). It is used to query the version of a BSW module via <code>&lt;Module name&gt;_GetVersionInfo()</code> <a class="spec-record-ref" data-req="SWS_Std_00015" href="../../spec/record.html?id=SWS_Std_00015">[SWS_Std_00015]</a>. The corresponding naming rule specifies <code>GetVersionInfo</code> as the service name. <code>void Eep_21_LDExt_GetVersionInfo(Std_VersionInfoType *versioninfo)</code> serves as an example <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_5_2_3_Software_Module_Design_Requirements.html" data-snip="SNIP_CLASSIC_STD_SECTION_5_2_3_Software_Module_Design_Requirements">SRS BSWGeneral p. 60</a>.</p>
<p>The function works synchronously and is reentrant. It has exactly one parameter of type <code>Std_VersionInfoType</code>, which is imported from <code>Std_Types.h</code>. Whether it is present is configured per module at pre-compile time via <code>&lt;Ma&gt;VersionInfoApi</code>. Published information of the module is delivered: Vendor Id, Module Id, and the vendor-specific version number <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_3_4_Get_Version_Information.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_3_4_Get_Version_Information">SWS BSWGeneral p. 76</a>. Interpretation: The fields are likely to correspond to the parameters <code>VendorId</code>, <code>ModuleId</code>, and <code>SwMajorVersion</code>/<code>SwMinorVersion</code>/<code>SwPatchVersion</code> from <code>CommonPublishedInformation</code> <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-5efb26dbadf8553e.html" data-snip="FIG-5efb26dbadf8553e">ECU ConfigurationParameters p. 14</a>. If development error detection is active, the modules check the pointer. In case of <code>NULL</code>, they report, for example, <code>CAN_E_PARAM_POINTER</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_1_2_Can_GetVersionInfo.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_1_2_Can_GetVersionInfo">SWS CANDriver p. 57</a> or <code>ADC_E_PARAM_POINTER</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_ADC_SECTION_8_3_13_Adc_GetVersionInfo.html" data-snip="SNIP_CLASSIC_ADC_SECTION_8_3_13_Adc_GetVersionInfo">SWS ADCDriver p. 80</a>.</p>

<h4>Transformer types: Errors, classes, and forward codes as of R20-11</h4>
<p>In R20-11, <code>Std_TransformerError</code> is a structure consisting of <code>errorCode</code> (type <code>uint8</code>) and <code>transformerClass</code> (type <code>Std_TransformerClass</code>) <a class="spec-record-ref" data-req="SWS_Std_00021" href="../../spec/record.html?id=SWS_Std_00021">[SWS_Std_00021]</a>. Although the API overview states <code>typedef uint8</code> as the signature, the structure definition of the requirement is decisive. Later releases type <code>errorCode</code> as <code>Std_TransformerErrorCode</code>. The meaning of the values applies there in each case to the specific transformer chain <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_1_3_Std_TransformerError.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_1_3_Std_TransformerError">SWS StandardTypes p. 16</a>. <code>Std_TransformerClass</code> is derived from <code>uint8</code> and has the following values: <code>STD_TRANSFORMER_UNSPECIFIED</code> (0x00), <code>STD_TRANSFORMER_SERIALIZER</code> (0x01), <code>STD_TRANSFORMER_SAFETY</code> (0x02), <code>STD_TRANSFORMER_SECURITY</code> (0x03), and <code>STD_TRANSFORMER_CUSTOM</code> (0xFF) <a class="spec-record-ref" data-req="SWS_Std_00024" href="../../spec/record.html?id=SWS_Std_00024">[SWS_Std_00024]</a>.</p>
<p>Both of the following types have Draft status in R20-11. <code>Std_TransformerForward</code> is a structure consisting of <code>errorCode</code> (type <code>Std_TransformerForwardCode</code>) and <code>transformerClass</code> <a class="spec-record-ref" data-req="SWS_Std_00027" href="../../spec/record.html?id=SWS_Std_00027">[SWS_Std_00027]</a>. <code>Std_TransformerForwardCode</code> has the values <code>E_OK</code> (0x00), <code>E_SAFETY_INVALID_REP</code> (0x01), <code>E_SAFETY_INVALID_SEQ</code> (0x02), and <code>E_SAFETY_INVALID_CRC</code> (0x03) <a class="spec-record-ref" data-req="SWS_Std_00029" href="../../spec/record.html?id=SWS_Std_00029">[SWS_Std_00029]</a>. With R22-11, <a class="spec-record-ref" data-req="SWS_Std_00027" href="../../spec/record.html?id=SWS_Std_00027">[SWS_Std_00027]</a> was removed <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_General_Overview_STANDARDTYPES.html" data-snip="SNIP_CLASSIC_STD_SECTION_General_Overview_STANDARDTYPES">SWS StandardTypes p. 1</a>. Later releases also use the literals <code>STD_E_FORWARDCODE_*</code>, whose descriptions cannot be mapped congruently to the R20-11 names <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_1_4_Std_TransformerForwardCode.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_1_4_Std_TransformerForwardCode">SWS StandardTypes p. 17</a>. For R20-11, the names from the requirement apply. Interpretation: The codes are likely intended to deliberately re-inject detected safety errors during forwarding. This is also indicated by the E2E forward functions, which reconstruct detected errors on the output data <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_3_4_3_E2E_P04mForward.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_3_4_3_E2E_P04mForward">SWS E2ELibrary p. 107</a>.</p>
<p>In the RTE specification of later releases, <code>Rte_Send</code> can have an optional input parameter <code>forwardedCode</code> and an optional output parameter <code>Std_TransformerError transformerError</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_5_6_5_Rte_Send.html" data-snip="SNIP_CLASSIC_STD_SECTION_5_6_5_Rte_Send">SWS RTE p. 704</a>. <code>Rte_Call</code> also has an optional <code>transformerError</code> as output <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_5_6_13_Rte_Call.html" data-snip="SNIP_CLASSIC_STD_SECTION_5_6_13_Rte_Call">SWS RTE p. 731</a>. For <code>Rte_Trigger</code>, this parameter is only generated if a <code>PortAPIOption</code> with <code>errorHandling</code> = <code>transformerErrorHandling</code> references the port <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_5_6_34_Rte_Trigger.html" data-snip="SNIP_CLASSIC_STD_SECTION_5_6_34_Rte_Trigger">SWS RTE p. 774</a>.</p>

<h4>Message type, message result, and header extraction in C/S transformer chains</h4>
<p><code>Std_MessageTypeType</code> is derived from <code>uint8</code>. It distinguishes between <code>STD_MESSAGETYPE_REQUEST</code> (0x00) and <code>STD_MESSAGETYPE_RESPONSE</code> (0x01); the range 0x02–0x3F is reserved for future types <a class="spec-record-ref" data-req="SWS_Std_91001" href="../../spec/record.html?id=SWS_Std_91001">[SWS_Std_91001]</a>. The type encodes the message types in AUTOSAR, currently restricted to requests and responses in C/S communication <a class="spec-record-ref" data-req="SWS_Std_00017" href="../../spec/record.html?id=SWS_Std_00017">[SWS_Std_00017]</a>. The API overview refers to the type in abbreviated form as <code>Std_MessageType</code>, but the name <code>Std_MessageTypeType</code> is authoritative. <code>Std_MessageResultType</code> distinguishes between <code>STD_MESSAGERESULT_OK</code> (0x00) and <code>STD_MESSAGERESULT_ERROR</code> (0x01); 0x02–0x3F are reserved <a class="spec-record-ref" data-req="SWS_Std_91002" href="../../spec/record.html?id=SWS_Std_91002">[SWS_Std_91002]</a> <a class="spec-record-ref" data-req="SWS_Std_00019" href="../../spec/record.html?id=SWS_Std_00019">[SWS_Std_00019]</a>. For both types, later releases announce possible further literals <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_1_5_Std_MessageTypeType.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_1_5_Std_MessageTypeType">SWS StandardTypes p. 18</a> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_1_6_Std_MessageResultType.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_1_6_Std_MessageResultType">SWS StandardTypes p. 19</a>.</p>
<p><code>Std_ExtractProtocolHeaderFieldsType</code> is a function pointer with the parameters <code>const uint8* buffer</code>, <code>uint32 bufferLength</code> as well as the outputs <code>messageType</code> and <code>messageResult</code>. The target function returns <code>Std_ReturnType</code> and is synchronous and reentrant <a class="spec-record-ref" data-req="SWS_Std_91003" href="../../spec/record.html?id=SWS_Std_91003">[SWS_Std_91003]</a>. Its purpose is currently limited to REQUEST/RESPONSE and OK/ERROR <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_1_7_Std_ExtractProtocolHeaderFieldsType.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_1_7_Std_ExtractProtocolHeaderFieldsType">SWS StandardTypes p. 20</a>. In <code>&lt;Mip&gt;_Inv_&lt;transformerId&gt;</code>, the optional argument <code>extractProtocolHeaderFields</code> points to the extraction function of a previous transformer in the chain. <h4>Behavior in the event of an error</h4>
<p>Only type and symbol definitions are available for <code>std</code>, starting at <a class="spec-record-ref" data-req="SWS_Std_00005" href="../../spec/record.html?id=SWS_Std_00005">[SWS_Std_00005]</a>. The error behavior therefore results from how the using modules employ these values:</p>
<ul>
<li><strong>Generic error:</strong> <code>E_NOT_OK</code> indicates the failure of a request. For example, <code>Can_GetControllerErrorState</code> reports <code>CAN_E_UNINIT</code> in case of missing initialization and returns <code>E_NOT_OK</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CAN_SECTION_8_3_2_6_Can_GetControllerErrorState.html" data-snip="SNIP_CLASSIC_CAN_SECTION_8_3_2_6_Can_GetControllerErrorState">SWS CANDriver p. 64</a>.</li>
<li><strong>Custom error values:</strong> Additional values are permitted only with a module prefix and only in the six least significant bits. Bits 7 and 8 remain reserved for the RTE <a class="spec-record-ref" data-req="SWS_Std_00011" href="../../spec/record.html?id=SWS_Std_00011">[SWS_Std_00011]</a>.</li>
<li><strong>Erroneous header:</strong> <code>SomeIpXf_ExtractProtocolHeaderFields</code> returns <code>E_NOT_OK</code> if the protocol version is incorrect or <code>bufferLength</code> is smaller than a minimum SOME/IP header <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_3_1_SomeIpXf_ExtractProtocolHeaderFields.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_3_1_SomeIpXf_ExtractProtocolHeaderFields">SWS SOMEIPTransformer p. 61</a>. The E2E transformer then branches to the FALSE path <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-127231d0a5c405e3.html" data-snip="FIG-127231d0a5c405e3">SWS E2ETransformer p. 38</a>.</li>
<li><strong>Transformer error:</strong> <code>transformerError</code> contains the error from the transformer chain, while the return value indicates communication errors <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_6_6_1_Severe_incompatibilities.html" data-snip="SNIP_CLASSIC_RTE_SECTION_6_6_1_Severe_incompatibilities">SwCluster-Guideline p. 245</a>. The RTE error table lists <code>RTE_E_HARD_TRANSFORMER_ERROR</code> (138) and <code>RTE_E_SOFT_TRANSFORMER_ERROR</code> (140) <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_1_Returned_by_AUTOSAR_Services_to_indicate_a.html" data-snip="SNIP_CLASSIC_STD_SECTION_1_Returned_by_AUTOSAR_Services_to_indicate_a">SWS RTE p. 586</a>.</li>
<li><strong>Callbacks:</strong> Callbacks that are AUTOSAR services return <code>Std_ReturnType</code>. The caller may assume <code>E_OK</code>, although errors can still occur in partitioned systems <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_8_4_Callback_notifications_BSWGENERAL.html" data-snip="SNIP_CLASSIC_STD_SECTION_8_4_Callback_notifications_BSWGENERAL">SWS BSWGeneral p. 69</a>.</li>
<li><strong>Type compatibility:</strong> BSW service APIs called via the RTE must return <code>Std_ReturnType</code>. A different type or <code>void</code> leads to incompatibility <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_3_3_Software_Module_Design_Requirements.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_3_3_Software_Module_Design_Requirements">RS BSWGeneral p. 63</a>. In addition, the return values must match on both sides <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_AUTOSARMODELCONSTRAINTS_SECTION_21_Depending_on_the_applicable_case_this_means_either_bitfieldTextTableMaskFirst_applies_if_TPS_SWCT_01163_is_in_place_or_bitfieldTextTableMaskSecond_for_the_case_of.html" data-snip="SNIP_CLASSIC_AUTOSARMODELCONSTRAINTS_SECTION_21_Depending_on_the_applicable_case_this_means_either_bitfieldTextTableMaskFirst_applies_if_TPS_SWCT_01163_is_in_place_or_bitfieldTextTableMaskSecond_for_the_case_of">ModelConstraints p. 197</a>.</li>
<li><strong>Name conflict with OSEK:</strong> <code>E_OK</code> is protected via <code>STATUSTYPEDEFINED</code> so that it is not defined twice <a class="spec-record-ref" data-req="SWS_Std_00006" href="../../spec/record.html?id=SWS_Std_00006">[SWS_Std_00006]</a> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files.html" data-snip="SNIP_CLASSIC_NVM_SECTION_5_2_3_4_Standard_header_files">SRS BSWGeneral p. 62</a>.</li>
</ul>
