<h4>Kontext</h4>
<p>Die Klasse <code>ara::crypto::CryptoErrorDomain</code> fungiert als spezialisierte Fehlerdomäne innerhalb der AUTOSAR-Adaptive-Plattform. Gemäß ihrer Klassendefinition leitet sie von <code>ara::core::ErrorDomain</code> ab und ist als <code>final</code> deklariert. Ihre zentrale Verantwortung besteht darin, sämtliche Fehler abzubilden, die von den öffentlichen Schnittstellen innerhalb des Namensraums <code>ara::crypto</code> gemeldet werden können. Sie ordnet den Fehlern eine eindeutige Domänenidentifikation zu, die über die Methode <code>Name</code> abgefragt werden kann <a class="spec-record-ref" data-req="SWS_CRYPT_19950" href="../spec/record.html?id=SWS_CRYPT_19950">[SWS_CRYPT_19950]</a>.</p>
<p>Zur einheitlichen Typbindung stellt die Klasse zwei typbezogene Aliase bereit: <code>Errc</code> verweist als Alias direkt auf die Aufzählung <code>CryptoErrc</code> für kryptografische Fehlercodes <a class="spec-record-ref" data-req="SWS_CRYPT_19903" href="../spec/record.html?id=SWS_CRYPT_19903">[SWS_CRYPT_19903]</a>, während <code>Exception</code> die Basisausnahmeklasse <code>CryptoException</code> referenziert <a class="spec-record-ref" data-req="SWS_CRYPT_19904" href="../spec/record.html?id=SWS_CRYPT_19904">[SWS_CRYPT_19904]</a>. Als Interaktionspartner treten primär die kryptografischen Funktionsbausteine auf, die Fehler dieser Domäne erzeugen, sowie die Anwendungssoftware, welche Fehler über die Basismechanismen von <code>ara::core</code> empfängt und auswertet.</p>

<h4>Lebenszyklus</h4>
<p>Die Erzeugung von Objekten der <code>CryptoErrorDomain</code> erfolgt über den standardmäßigen parameterlosen Konstruktor, welcher als <code>constexpr</code> und <code>noexcept</code> spezifiziert ist <a class="spec-record-ref" data-req="SWS_CRYPT_19902" href="../spec/record.html?id=SWS_CRYPT_19902">[SWS_CRYPT_19902]</a>. Durch die Deklaration als <code>constexpr</code> kann eine Instanz bereits zur Übersetzungszeit konstruiert werden. Interpretation: In typischen Plattform-Implementierungen dürfte die Fehlerdomäne als langlebiges oder statisches Singleton existieren, damit Fehlercodes im gesamten Prozessverlauf ohne dynamische Speicherallokation auf dieselbe Domäneninstanz verweisen können. <a class="interp-q interp-q-open" data-q="Q-eace74191b79fa03" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-eace74191b79fa03" title="Frage Q-eace74191b79fa03 (offen): Die Klasse CryptoErrorDomain dürfte typischerweise als langlebige statische Instanz (Singleton) vorgehalten werden.">Frage Q-eace74191b79fa03 (offen)</a></p>
<p>Nach der Instanziierung besitzt das Objekt einen konstanten, zustandslosen Charakter; eine Vererbungshierarchie unterhalb dieser Klasse ist durch das Schlüsselwort <code>final</code> ausgeschlossen. Hinsichtlich der Nebenläufigkeit sind sowohl der Konstruktor <a class="spec-record-ref" data-req="SWS_CRYPT_19902" href="../spec/record.html?id=SWS_CRYPT_19902">[SWS_CRYPT_19902]</a> als auch die Abfragemethoden <code>Name</code> <a class="spec-record-ref" data-req="SWS_CRYPT_19950" href="../spec/record.html?id=SWS_CRYPT_19950">[SWS_CRYPT_19950]</a>, <code>Message</code> <a class="spec-record-ref" data-req="SWS_CRYPT_19953" href="../spec/record.html?id=SWS_CRYPT_19953">[SWS_CRYPT_19953]</a> und <code>ThrowAsException</code> <a class="spec-record-ref" data-req="SWS_CRYPT_19954" href="../spec/record.html?id=SWS_CRYPT_19954">[SWS_CRYPT_19954]</a> explizit als threadsicher (thread-safe) klassifiziert. Instanzen können somit ohne externe Synchronisation von mehreren Threads parallel genutzt werden.</p>

<h4>Nutzungspfad</h4>
<p>Der reguläre Ablauf bei der Interaktion mit der <code>CryptoErrorDomain</code> gliedert sich in folgende Schritte:</p>
<ol>
<li>Eine Operation innerhalb des Namensraums <code>ara::crypto</code> schlägt fehl und erzeugt ein Fehlerobjekt vom Typ <code>ara::core::ErrorCode</code>, welches mit der <code>CryptoErrorDomain</code> verknüpft ist.</li>
<li>Die aufrufende Anwendung oder Fehlerbehandlungsroutine prüft die Herkunft des Fehlers und kann bei Bedarf mittels <code>Name()</code> den eindeutigen Namen der Domäne abrufen <a class="spec-record-ref" data-req="SWS_CRYPT_19950" href="../spec/record.html?id=SWS_CRYPT_19950">[SWS_CRYPT_19950]</a>.</li>
<li>Zur Erzeugung von Protokollausgaben oder Diagnosemeldungen wird die Methode <code>Message()</code> mit dem übergebenen <code>errorCode</code> aufgerufen, die den Code auflöst und die zugehörige Textmeldung als <code>const char*</code> zurückliefert <a class="spec-record-ref" data-req="SWS_CRYPT_19953" href="../spec/record.html?id=SWS_CRYPT_19953">[SWS_CRYPT_19953]</a>.</li>
<li>Möchte der Aufrufer den Fehler in eine C++-Ausnahme umwandeln, erfolgt der Aufruf von <code>ThrowAsException()</code>, wodurch eine passende Ausnahme auf Basis von <code>CryptoException</code> ausgelöst wird <a class="spec-record-ref" data-req="SWS_CRYPT_19954" href="../spec/record.html?id=SWS_CRYPT_19954">[SWS_CRYPT_19954]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_19904" href="../spec/record.html?id=SWS_CRYPT_19904">[SWS_CRYPT_19904]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Bei der Fehlerbehandlung weist die Klasse differenzierte Garantien hinsichtlich der Ausnahmesicherheit auf. Die Methoden <code>Name</code> <a class="spec-record-ref" data-req="SWS_CRYPT_19950" href="../spec/record.html?id=SWS_CRYPT_19950">[SWS_CRYPT_19950]</a> und <code>Message</code> <a class="spec-record-ref" data-req="SWS_CRYPT_19953" href="../spec/record.html?id=SWS_CRYPT_19953">[SWS_CRYPT_19953]</a> sind als <code>noexcept</code> deklariert und vollständig ausnahmesicher (exception safe). Sollte an <code>Message</code> ein numerischer Wert übergeben werden, der nicht in der Aufzählung <code>CryptoErrc</code> definiert ist, dürfte vermutlich eine generische Fallback-Nachricht geliefert werden; ein Abbruch durch Ausnahmen ist ausgeschlossen. <a class="interp-q interp-q-open" data-q="Q-6f2a8707283aa64e" data-q-status="open" href="../versions.html?tab=q&amp;id=Q-6f2a8707283aa64e" title="Frage Q-6f2a8707283aa64e (offen): Bei unbekannten Fehlercodes an Message() dürfte vermutlich eine standardisierte Fallback-Zeichenkette zurückgegeben werden.">Frage Q-6f2a8707283aa64e (offen)</a></p>
<p>Im Gegensatz dazu ist die Methode <code>ThrowAsException</code> als nicht ausnahmesicher (not exception safe) spezifiziert und mit dem Attribut <code>[[noreturn]]</code> versehen, da ihr bestimmungsgemäßer Zweck im Werfen einer Ausnahme liegt <a class="spec-record-ref" data-req="SWS_CRYPT_19954" href="../spec/record.html?id=SWS_CRYPT_19954">[SWS_CRYPT_19954]</a>. Eine wesentliche Randbedingung betrifft Plattformkonfigurationen ohne Exception-Unterstützung: Sind C++-Ausnahmen in der Compiler-Toolchain deaktiviert, nimmt <code>ThrowAsException</code> nicht an der Überladungsauflösung teil <a class="spec-record-ref" data-req="SWS_CRYPT_19954" href="../spec/record.html?id=SWS_CRYPT_19954">[SWS_CRYPT_19954]</a>. In solchen Systemen ist der Aufruf kompilierunfähig, und die Fehlerbehandlung muss zwingend über fehlerwertbasierte Mechanismen wie Ergebnisobjekte abgewickelt werden.</p>
