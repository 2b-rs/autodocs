Verwendungszweck

Für jedes als Event modellierte Service-Interface-Element erzeugt der Proxy einen Event-Wrapper. Nach dem Verbinden mit der Dienstinstanz abonniert der Consumer das Event; der Provider sendet Daten an Communication Management, das die Abonnenten benachrichtigt. Samples werden anschließend explizit über GetNewSamples() abgeholt. EXP ARAComAPI §4.3 „Event and Trigger based communication" §5.3.5 „Events"

Subscription, Cache und Empfangsmodell

Subscribe(maxSampleCount) richtet zugleich das maximale Budget des lokalen Sample-Caches ein. Der Aufruf akzeptiert den Auftrag asynchron; der Subscription-State kann abgefragt oder über einen State-Change-Handler beobachtet werden. Für zyklische Anwendungen genügt Polling mit GetNewSamples(); reaktive Anwendungen registrieren einen SetReceiveHandler(), der bei neuen Daten zur Abholung auffordert. EXP ARAComAPI §5.3.5.1 „Event Subscription and Local Cache" §5.3.5.2 „Monitoring Event Subscription" §5.3.5.5 „Event-Driven vs Polling-Based access"

Sample-Ownership

Die an den Callback übergebenen SamplePtr übertragen die Verantwortung für einen Cache-Slot auf die Anwendung. Solange ein SamplePtr gehalten wird, kann dieser Slot nicht wiederverwendet werden; das begrenzt die Zahl gleichzeitig zugänglicher Samples. EXP ARAComAPI §5.3.5.4 „Event Sample Management via SamplePtrs"
