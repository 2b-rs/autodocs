AUTOSAR Classic General & Standard Types

标准和平台类型定义了AUTOSAR Classic架构的基本C类型、返回值和通信数据结构。它们确保基本软件和应用程序SW-C 具有独立于硬件的可移植性。

1. 系统架构与模块集群的角色

“General & Standard Types”集群是 Classic Platform 的类型基础。它不提供运行时服务。它指定了数据类型、符号以及一个函数指针类型，BSW 模块、RTE 和 Transformer 共同基于这些内容构建。Std_ReturnType明确“在 RTE 与 BSW 模块之间共享”[SWS_Std_00005]。根据通用 BSW 需求，Std_Types.h包含头文件Platform_Types.h和Compiler.h。使用 AUTOSAR 整型类型或标准返回类型的每个模块都会包含Std_Types.h（SRS BSWGeneral 第62页）。

  • platform（Platform_Types.h）定义了平台相关的基础：
    • 从uint8到sint64的固定宽度整型类型[SWS_Platform_00013] [SWS_Platform_00067]，仅采用二进制补码[SWS_Platform_00061]。
    • 优化的*_least类型，例如用于循环计数器[SWS_Platform_00020]（SWS PlatformTypes 第17页）。
    • 符合 IEEE 754-2008 的float32/float64 [SWS_Platform_00041]。
    • boolean [SWS_Platform_00026].
    • 符号CPU_TYPE、CPU_BIT_ORDER和CPU_BYTE_ORDER [SWS_Platform_00064] [SWS_Platform_00038] [SWS_Platform_00039]。
    • 用于缓冲区的VoidPtr/ConstVoidPtr [SWS_Platform_91001] [SWS_Platform_91002]。
    • 不允许对该文件进行扩展[SWS_Platform_00002]。
  • std（Std_Types.h）定义了：
    • 带有E_OK/E_NOT_OK的Std_ReturnType [SWS_Std_00006]。
    • 开关符号STD_ON/OFF、STD_HIGH/LOW和STD_ACTIVE/IDLE [SWS_Std_00010] [SWS_Std_00007] [SWS_Std_00013]。
    • Std_VersionInfoType [SWS_Std_00015].
    • Transformer 类型Std_TransformerError、Std_TransformerClass、Std_MessageTypeType和Std_MessageResultType [SWS_Std_00021] [SWS_Std_00024] [SWS_Std_91001] [SWS_Std_91002]。
  • comstack（ComStack_Types.h）定义了通信类型：
    • PduIdType和PduLengthType [SWS_COMTYPE_00005] [SWS_COMTYPE_00008]。
    • PduInfoType [SWS_COMTYPE_00011].
    • BufReq_ReturnType [SWS_COMTYPE_00012].
    • TP 类型TpDataStateType、RetryInfoType和TPParameterType [SWS_COMTYPE_00027] [SWS_COMTYPE_00037] [SWS_COMTYPE_00031]。
    • 通道和网络句柄NetworkHandleType与PNCHandleType [SWS_COMTYPE_00038] [SWS_COMTYPE_00036]。

与外部标准的关联体现在 ISO 17356-3 (OSEK) 和 IEEE 754-2008。由于 ISO 17356-3，E_OK必须在STATUSTYPEDEFINED保护下进行定义[SWS_Std_00006]。IEEE 754-2008 适用于浮点类型[SWS_Platform_00042]。

2. 相互协作与交互路径

各模块分层逐级构建。ComStack 类型派生自平台类型：NetworkHandleType是介于 0..255 范围内的uint8，用于标识通信通道[SWS_COMTYPE_00038]。PduIdType的宽度根据 EcuC 配置在ComStack_Cfg.h中生成为uint8或uint16 [SWS_COMTYPE_00005]（ECUConfiguration 第153页）。

一条不起眼但重要的路径将PduInfoType与平台定义连接起来。大于 8 位的元数据元素以平台字节序存在[SWS_COMTYPE_00011]。该顺序由CPU_BYTE_ORDER确定：在 Big Endian 下为HIGH_BYTE_FIRST，在 Little Endian 下为LOW_BYTE_FIRST [SWS_Platform_00050] [SWS_Platform_00051]。在 Big Endian 布局中，最高有效字节位于地址 n（SWS PlatformTypes 第16页）。

寄存器中的位序是一个单独的主题。在 Big Endian 下，CPU_BIT_ORDER被设置为MSB_FIRST [SWS_Platform_00048]。规范警告不要混淆位命名与位权值（SWS PlatformTypes 第15页）。

指针类型规定了缓冲区方向。ConstVoidPtr代表传递给被调用者的缓冲区。VoidPtr代表包含返回给调用者的数据的缓冲区[SWS_Platform_91001] [SWS_Platform_91002]。一个示例是包含RequestData和ResponseData的 KeyM 服务接口（SWS KeyM 第111页）。

最复杂的路径涉及 Transformer 链。Std_ExtractProtocolHeaderFieldsType是一个函数指针，用于从协议头中提供规范值Std_MessageTypeType（Request/Response）和Std_MessageResultType（OK/ERROR）[SWS_Std_91003] [SWS_Std_00017] [SWS_Std_00019]。逆向 Transformer 可选地接收该指针作为参数（ASWS TransformerGeneral 第40页）。E2E 库处理提取出的值，例如在E2E_P04mSinkCheck中（SWS E2ELibrary 第109页）。这些文档出处源自后续 Release。对 R20-11 具有规范约束力的是类型定义本身。

3. 同步、可重入性与任务上下文

类型模块没有自己的 MainFunction，也没有互斥区。有效负载中唯一与行为相关的元素是函数指针类型，且它被规范为同步且可重入[SWS_Std_91003]。因此，为该指针提供函数的一方必须遵守这些特性。SomeIpXf_ExtractProtocolHeaderFields相应地也是同步且可重入的（SWS SomeIpXf 第61页）。

句柄类型在用户 API 中用作可重入性的区分特征：

  • 总线镜像服务“针对不同网络可重入”，即不同的NetworkHandleType值[SWS_COMTYPE_00038]（SWS BusMirroring 第77页）。
  • CanIf_TriggerTransmit针对不同的PduIdType值是可重入的[SWS_COMTYPE_00005]（SWS CanIf 第107页）。
  • Std_ReturnType也由运行在中断或任务级别的函数提供，例如CanIf_CheckWakeup（SWS CanIf 第101页）。

基于Std_VersionInfoType的 Get-Version-Information 函数必须是同步且可重入的[SWS_Std_00015]（SWS BSWGeneral 第76页）。

4. 生命周期与操作模式

该集群的大部分内容在编译和配置时生效：

  • CPU_TYPE描述了平台的寄存器宽度[SWS_Platform_00044] [SWS_Platform_00045]。
  • STD_ON/STD_OFF通过预处理器切换 API，例如<Ma>VersionInfoApi [SWS_Std_00010]（SWS BSWGeneral 第76页）。
  • TRUE/FALSE使用#ifndef进行保护，以防止编译器预定义冲突[SWS_Platform_00056] [SWS_Platform_00054]。

在运行时，这些类型描述逻辑状态。STD_ACTIVE/STD_IDLE标识逻辑状态[SWS_Std_00013]。STD_HIGH/STD_LOW标识物理电平[SWS_Std_00007]。

TP 缓冲区状态构成了真正的生命周期。RetryInfoType将TpDataStateType与偏移量TxTpDataCnt结合起来[SWS_COMTYPE_00037]：

  • TP_DATACONF确认迄今为止已复制的数据。
  • TP_DATARETRY请求从指定的偏移量开始重新复制[SWS_COMTYPE_00027]。

J1939Tp 图表还提到了TP_CONFPENDING，它未包含在删减的需求摘录中（SWS J1939Tp 第55页）。

5. 错误处理、DET 跟踪与降级

Std_ReturnType是核心错误通道。通常它与E_OK或E_NOT_OK一起使用。模块特定值位于低 6 位（0x02–0x3F）并带有模块前缀。高两位保留给 RTE [SWS_Std_00011] [SWS_Std_00005]（SWS StandardTypes 第15页）。示例：

  • RTE 将保留位用于 128 起的基础设施错误，以及值为 64 的叠加错误（SWS RTE 第586页）。
  • CAN 驱动补充了CAN_BUSY = 0x02（SWS CAN 第54页）。
  • 在 UML 模型中，此类扩展被建模为带有构造型 «extra_literals» 的<Ma>_ReturnType（BSW UML Modeling Guide 第28页）。

对于应用程序通过 RTE 调用的 BSW 服务，RTE 始终预期Std_ReturnType（RS BSWGeneral 第63页）。

缓冲区请求使用专用类型BufReq_ReturnType。在返回BUFREQ_E_BUSY时由请求方负责重试，BUFREQ_E_OVFL表示长度无法满足[SWS_COMTYPE_00012]。结合TP_DATARETRY，这构成了通信栈的降级策略：重试而非中止。

RTE 通过Std_TransformerError报告 Transformer 错误。该类型包含一个错误码和一个Std_TransformerClass（Serializer、Safety、Security、Custom）[SWS_Std_00021] [SWS_Std_00024]。例如，它作为Rte_Call的可选 OUT 参数出现（SWS RTE 第731页）。

与较新的文档出处相比存在 Release 差异。在这些情况下以 R20-11 为准：

  • errorCode在 R20-11 中是一个uint8 [SWS_Std_00021]。后续 Release 使用Std_TransformerErrorCode（SWS StandardTypes 第16页）。
  • 草案类型Std_TransformerForwardCode在 R20-11 中包含值E_SAFETY_INVALID_REP/SEQ/CRC [SWS_Std_00029]。较新的 Release 将其重命名为STD_E_FORWARDCODE_*（SWS StandardTypes 第17页）。
  • boolean在 R20-11 中是原生支持的最短无符号整型[SWS_Platform_00027]，而不是后来的 C99-_Bool（SWS PlatformTypes 第18页）。
  • PNCHandleType在 R20-11 中是一个uint8 [SWS_COMTYPE_00036]，后来则是一个uint16（SWS ComStackTypes 第17页）。

DET 跟踪间接影响该集群。带有Std_VersionInfoType*的用户 API 会检查指针是否为 NULL 并报告例如CAN_E_PARAM_POINTER [SWS_Std_00015]（SWS CAN 第57页）。对于boolean，禁止进行算术赋值，且该类型必须支持指针寻址[SWS_Platform_00034] [SWS_Platform_00060]。
