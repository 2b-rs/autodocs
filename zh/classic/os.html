系统架构与“Operating System”集群的角色

该集群仅包含模块 Os。它扩展了 OSEK OS，例如增加了作为报警动作的软件计数器以及自动启动的绝对报警 SWS OS 第38页。此外，它将 Task、ISR、Alarm、ScheduleTable、Counter 和 Hook 组合为 OS-Application。这些可以是 trusted 或 non-trusted SWS OS 第61页。配置的或当前正在执行的 OS-Application 由 GetApplicationID [SWS_Os_00016] 和 GetCurrentApplicationID [SWS_Os_00797] 提供。两个标识符空间均从零开始连续编号，Core-ID [SWS_Os_00826] [SWS_Os_00825] 也是如此。

在 BSW 架构中，OS 是一个具有明确访问权限的服务提供者。通用 BSW 规范中的一个表格规定了哪些模块组可以使用哪些 OS 服务：RTE/BSW-Scheduler、BswM、CDD、EcuM、MCAL、StbM 以及其余 BSW SWS BSWGeneral 第48页。例如，CDD 应当仅使用 GetCounterValue 和 GetElapsedValue CDD-Guideline 第21页。Inter-OS-Application Communicator（IOC）是 OS 的一部分。作为第三种通信方式，它补充了 RTE 内部通信和基于 COM 的通信 SWS OS 第119页。在 R20-11 中，IOC 和 OS 代码的分开生成被定为 DRAFT [SWS_Os_00831]。

协作与交互路径

与 StbM 的时间同步：针对 R20-11 的安全概述将 SyncScheduleTable、StartScheduleTableSynchron、GetScheduleTableStatus 和 SetScheduleTableAsync 归入同步时间基准与 OS-Counter 之间的耦合 FSM-Übersicht 第66页。其流程如下：在 StbM_MainFunction 中，StbM 首先查询 GetScheduleTableStatus [SWS_Os_00227]。仅在 WAITING、RUNNING 或 RUNNING_AND_SYNCHRONOUS 状态下，它随后才通过 SyncScheduleTable [SWS_Os_00199] SWS StbM 第220页 传递同步计数值。解释：该流程源自后续版本，推测其基本含义也适用于 R20-11。OS 根据同步计数值确定调度表时间与同步计数器之间的漂移 SWS OS 第52页。

时序图：StbM 仅在合适的状态下同步显式同步的 ScheduleTable。来源：SWS StbM 第220页、[SWS_Os_00199]、[SWS_Os_00227]

分区与 Core 之间的 IOC：对于“data”语义（LastIsBest），OS 生成 IocWrite/IocRead [SWS_Os_91003] [SWS_Os_91005]；对于“event”语义（Queue），则生成 IocSend/IocReceive [SWS_Os_00718] [SWS_Os_00738]。在 LastIsBest 情况下，RTE 将其缓冲区复制到 IOC 内部缓冲区中，接收端从中读取 SWS OS 第190页。若 Queue 已满，发送端报告 IOC_E_LIMIT，且接收端在下次读取时接收到 IOC_E_LOST_DATA SWS OS 第218页。作为可选项，IOC 每次接收可在接收端 Core 上调用一个 <ReceiverPullCB> [SWS_Os_00757]。

跨分区调用：通过 CallTrustedFunction [SWS_Os_00097]，调用者切换到提供服务的 OS-Application 的保护上下文中。存根为此将参数打包到一个结构体中。OS 检查权限，并在拒绝时返回 E_OS_SERVICEID SWS OS 第185页。作为异步替代方案，BSW-Distribution-Guide 提到了 ActivateTask 或对目标分区中 Task 的 SetEvent BSW-Distribution-Guide 第66页。对于跨 Core 调用，提供了 ActivateTaskAsyn 和 SetEventAsyn [SWS_Os_91022] [SWS_Os_91023]。

生命周期与运行模式

启动：在 Master-Core-StartPreOS 中，EcuM 首先通过 StartCore 在循环中启动所有已配置的 Core。之后它调用 StartOS(ECUM_DEFAULT_APP_MODE) SWS EcuM 第82页。在 StartOS 之后，不再允许调用 StartCore [SWS_Os_00676]。相反，GetCoreID [SWS_Os_00674] 允许在 StartOS 之前调用 SWS OS 第111页。在 StartOS 之后以及 StartupHook 之前，OS 将所有 OS-Application 置为 APPLICATION_ACCESSIBLE SWS OS 第62页。随后运行 StartupHook_<App> [SWS_Os_00539]。如果配置了 IOC，StartOS 在默认模式下通过 IocInit（DRAFT）初始化其数据结构 [SWS_Os_00830] [SWS_Os_91026]。

ScheduleTable：OS 以绝对方式 [SWS_Os_00358] 或相对于当前 Counter 计数值 [SWS_Os_00347] 启动 ScheduleTable。StopScheduleTable [SWS_Os_00006] 停止它。稍后重新启动时将再次从表头开始 SWS OS 第46页。NextScheduleTable [SWS_Os_00191] 链接两个调度表。在同步启动 [SWS_Os_00201] 时，调度表等待第一次同步计数，如有疑问则无限期等待 SWS OS 第49页。SetScheduleTableAsync [SWS_Os_00422] 终止同步，但 Expiry Point 仍会继续处理 SWS OS 第188页。[SWS_Os_00784] 定义了这五种状态。

状态图：显式同步的 ScheduleTable 的生命周期。来源：[SWS_Os_00784]、SWS OS 第49页、SWS OS 第188页

OS-Application：R20-11 的规范定义了三种状态 [SWS_Os_00773]。后续版本的类型中仅包含两个值 SWS OS 第161页。

  • APPLICATION_ACCESSIBLE：启动状态，OS-Application 的对象可从外部访问 SWS OS 第62页。
  • APPLICATION_RESTARTING：一直有效，直到 OS-Application 自身调用 AllowAccess 为止 [SWS_Os_00501]。
  • APPLICATION_TERMINATED：最终终止；该状态可通过 GetApplicationState 查询 [SWS_Os_00499]。

空闲与关闭：ControlIdle 为每个 Core 选择一个空闲动作，例如用于节能措施 [SWS_Os_00769]。默认值为 IDLE_NO_HALT [SWS_Os_00793]。同步关闭由 ShutdownAllCores [SWS_Os_00713] 触发。该调用不返回，且在 non-trusted 代码中被忽略 SWS OS 第204页。EcuM 在 Master-Core-OffPreOS 中于 BswM_Deinit 和 SchM_Deinit 之后发出该调用 SWS EcuM 第91页。之后在每个 Core 上运行特定于应用程序的 ShutdownHook，接着是同步屏障和全局 ShutdownHook SWS OS 第88页 SWS OS 第189页 [SWS_Os_00541]。

错误处理、保护冲突与降级

通过返回值和 Hook 报告错误：OS 通过 StatusType 返回值报告错误，其中许多仅在 Extended Status 下报告。AUTOSAR 特定的错误代码在 [SWS_Os_91025] 中定义。对于 NULL_PTR 的指针，OS 在 Extended Mode 下会以 E_OS_ILLEGAL_ADDRESS 予以拒绝 SWS OS 第38页。检测到的错误会传递给 ErrorHook 或 ErrorHook_<App> [SWS_Os_00540]，例如在中断源 API [SWS_Os_00810] 中。一个特例是 IncrementCounter：如果闹钟动作失败，OS 会调用 Error-Hook，但服务本身返回 E_OK SWS OS 第190页。对于 ActivateTaskAsyn，如果调用者已不存在，错误报告将会丢失 SWS OS 第203页。在现有材料中，未证实 OS 连接 DET。

访问保护：若缺少对 OS 对象的已配置访问权限，该服务将返回 E_OS_ACCESS SWS OS 第73页。为进行预防性检查，提供了 CheckObjectAccess [SWS_Os_00256]、CheckObjectOwnership [SWS_Os_00017] 以及内存检查 [SWS_Os_00512] [SWS_Os_00513]。宏 OSMEMORY_IS_* 会评估其结果 SWS OS 第160页。未配置的 Trusted-Function 索引会以 E_OS_SERVICEID 触发 ErrorHook SWS OS 第85页。即使是 trusted OS-Applications，也可以限制其写访问 [SWS_Os_00795]。

通过 ProtectionHook 进行升级：发生严重保护违规时，OS 会调用 ProtectionHook [SWS_Os_00538]。其 ProtectionReturnType [SWS_Os_00787] 决定了应对措施：终止 Task 或 ISR、终止 OS-Application（带或不带重启）或者关闭系统 SWS OS 第187页。

序列图：保护违规后的升级路径，由 ProtectionHook 的返回值控制。来源：SWS OS 第187页、[SWS_Os_00538]、[SWS_Os_00787]、ALEH 第69页

终止与重启：OS-Application 也可以通过 TerminateApplication [SWS_Os_00258] 被定向终止。随后 OS 会终止其 Task 和 ISR，禁用其中断，并停止其闹钟和 ScheduleTable SWS OS 第62页。在 R20-11 中，RestartType 通过 RESTART/NO_RESTART 控制重启 [SWS_Os_00788]。后续版本则改用 OS_OSAPPLICATION_RESTART 并忽略参数 SWS OS 第194页。对于外部触发的重启，该指南规定了以下步骤：通知 RTE、为 OSRestartTask 存储决定、调用 TerminateApplication(<partition>, RESTART) 并向 DEM 报告 ALEH 第75页。OSRestartTask 直接或通过 BswM 使用 CallTrustedFunction 触发清理。之后，AllowAccess 再次释放该 OS-Application ALEH 第76页 [SWS_Os_00501]。
