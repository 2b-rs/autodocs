与 BswM 协同控制 ECU 的启动、关断、休眠阶段及唤醒源。

ECU State Manager 控制 Classic ECU 的生命周期。它初始化基础软件直至 OS 启动，引导 ECU 进入关断目标 SLEEP、RESET 或 OFF，并管理唤醒源及其校验 [SWS_EcuM_04136]。硬件相关步骤由集成代码通过 callout 承担。EcuM 仲裁用户的 RUN 和 POST_RUN 请求，但状态转换由 BswM 决定并通过 EcuM_SetState 反馈 [SWS_EcuM_04116]。最重要的边界条件是在 SLEEP 阶段绝不能丢失任何唤醒事件。

ECU State Manager（EcuM）在 Classic Platform 中负责 ECU 的启动、关断和休眠阶段。EcuM_Init 执行包含初始化块 0 和 1 的 StartPreOS 序列。在此过程中，EcuM 选择并检查 Post-Build 配置，最终调用 StartOS。随后 EcuM_StartupTwo 启动 SchM 和 BswM [SWS_EcuM_02684] [SWS_EcuM_02906] [SWS_EcuM_02932]。底层硬件步骤由集成代码作为 callout 提供，例如 EcuM_AL_DriverInitZero [SWS_EcuM_02905]。

状态图：ECU 依次经历 STARTUP、UP、SHUTDOWN 和 SLEEP。从 SLEEP 经由 WakeupRestart 返回 UP。来源：RS ModeManagement 第15页、[SWS_EcuM_91005]、[SWS_EcuM_02963]

EcuM 自身并不决定状态转换。它收集已配置用户的 RUN 和 POST_RUN 请求，并将结果报告给 BswM。它通过 EcuM_SetState 接收 BswM 的状态转换，并将其转发给 RTE [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04116] SWS EcuM 第103页。EcuM_SelectShutdownTarget 仅将目标 SLEEP、RESET 或 OFF 保存以备后用 [SWS_EcuM_02585]。在关断时，OffPreOS 反初始化 BswM 和 SchM，检查唤醒事件并终止 OS。关断钩子随后调用 EcuM_Shutdown，该函数以 EcuM_AL_Reset 或 EcuM_AL_SwitchOff 结束 [SWS_EcuM_03021] [SWS_EcuM_04074] [SWS_EcuM_04075]。

SLEEP 阶段以 EcuM_GoDownHaltPoll 开始。首先，GoSleep 激活休眠模式的唤醒源。随后要么执行带 RAM 哈希检查的 Halt，要么执行通过 EcuM_SleepActivity 和 EcuM_CheckWakeup 轮询的循环。最后通过 EcuM_AL_DriverRestart [SWS_EcuM_91002] [SWS_EcuM_02389] [SWS_EcuM_02863] [SWS_EcuM_03020] [SWS_EcuM_02963] 进行 WakeupRestart。在此阶段绝不能丢失任何唤醒事件 [SWS_EcuM_02188]。

唤醒源是 EcuM_WakeupSourceType 中的单个位，且各自处于 NONE、PENDING、VALIDATED 或 EXPIRED 状态之一 [SWS_EcuM_04040] [SWS_EcuM_04091]。驱动程序使用 EcuM_SetWakeupEvent 报告事件。若配置了校验，EcuM 将启动超时。只有在超时到期前发生 EcuM_ValidateWakeupEvent 才会进入 VALIDATED；若配置了通道关联，届时还会通知 ComM。否则该源将变为 EXPIRED [SWS_EcuM_02709] [SWS_EcuM_02645] [SWS_EcuM_04082]。

活动图：唤醒事件立即得到校验，或者保持 PENDING，直到确认到达或超时到期。来源：SWS EcuM 第63页、[SWS_EcuM_02566]、[SWS_EcuM_04082]

在发生错误时，若配置不一致或 RAM 校验失败，EcuM 会调用 callout EcuM_ErrorHook [SWS_EcuM_04033] [SWS_EcuM_91003]。它向 DET 报告开发错误，如重复请求或未知唤醒源 [SWS_EcuM_03024] [SWS_EcuM_02867]。

ECU State Manager 的角色与系统边界

ECU State Manager（EcuM）在 Classic Platform 中规定了 ECU 生命周期的框架。它初始化基础软件直至操作系统启动。随后，它以受控方式引导 ECU 进入关断目标 SLEEP、RESET 或 OFF 之一 [SWS_EcuM_04136]。它的状态由 EcuM_StateType 确定：STARTUP、RUN、POST_RUN、SHUTDOWN 和 SLEEP [SWS_EcuM_91005]。它通过模式声明组 EcuM_Mode 向 SW-C 报告这些状态，该组的初始模式为 STARTUP [SWS_EcuM_04107] [SWS_EcuM_04132]。

状态图：ECU 依次经历 STARTUP、UP、SHUTDOWN 和 SLEEP。从 SLEEP 经由 WakeupRestart 返回 UP，在硬件复位或上电周期后在 STARTUP 中重新启动。来源：RS ModeManagement 第15页、[SWS_EcuM_91005]、[SWS_EcuM_02963]、[SWS_EcuM_04001]

状态转换并非由 EcuM 自身决定。它没有自己的状态机，仅对请求进行仲裁，并将转换交由 BSW Mode Manager（BswM）处理 SWS EcuM 第103页。它将硬件相关和项目特定的步骤外包给集成代码的 callout，这些 callout 通过 EcuM_Externals.h 提供。示例包括 EcuM_AL_DriverInitZero 和 EcuM_AL_SwitchOff [SWS_EcuM_02905] [SWS_EcuM_02920]。相邻模块的接口列在导入函数表中，例如 BswM_EcuM_CurrentWakeup、Can_Init 和 Det_ReportError [SWS_EcuM_02858] [SWS_EcuM_02859]。

上下文图：EcuM 位于 SW-C、BswM、集成代码、OS、MCAL 驱动程序与 ComM 之间。BswM 决定状态转换，硬件步骤由集成代码执行。来源：SWS EcuM 第34页、[SWS_EcuM_02858]、[SWS_EcuM_04135]

启动：StartPreOS、StartPostOS 与配置数据

在 EcuM_Init 之前，EcuM 仅要求进行最小程度的 MCU 初始化：已设置堆栈且 C 变量已初始化 SWS EcuM 第39页。EcuM_Init 执行 StartPreOS 序列且不返回，因为它会调用 StartOS [SWS_EcuM_02811] [SWS_EcuM_02684]。在此过程中，将初始化 OS 启动所需的所有模块 [SWS_EcuM_02603]。

Init Block 0（EcuM_AL_DriverInitZero）为加载 Post-Build 数据做准备。因此，它仅允许使用在预编译或链接时配置的模块 [SWS_EcuM_02905]。随后 EcuM_DeterminePbConfiguration 提供指向 EcuM_ConfigType 的指针。该结构体引用所有其他 BSW 模块的配置 [SWS_EcuM_02906] [SWS_EcuM_02801]。它包含变体标识符和哈希值。在初始化第一个 Post-Build 可配置模块之前，EcuM 针对所有此类模块对照 ECUM_CONFIGCONSISTENCY_HASH 校验该哈希值 [SWS_EcuM_02794] [SWS_EcuM_02798] [SWS_EcuM_02796]。

Init Block 1（EcuM_AL_DriverInitOne）在上电复位后初始化驱动程序，其中包括 MCU [SWS_EcuM_02907] SWS EcuM 第146页。两个块中的顺序由 EcuMDriverInitListZero 和 EcuMDriverInitListOne 确定。每个初始化函数均从其对应的 EcuMModuleService 容器获取参数 [SWS_EcuM_02559] [SWS_EcuM_02730]。EcuM 将 Mcu 驱动程序的复位原因转换为唤醒源并予以记录。若无法确定原因，则设置 ECUM_WKSOURCE_RESET [SWS_EcuM_02623] [SWS_EcuM_02601]。若置位了 EcuMResetLoopDetection，EcuM 会在每次启动时调用 callout EcuM_LoopDetection [SWS_EcuM_04137]。

时序图：EcuM_Init 依次经历 Init Block 0、配置的选择与检查、Init Block 1 以及复位评估，直到 StartOS。随后 EcuM_StartupTwo 启动 SchM 和 BswM。来源：SWS EcuM 第38页、SWS EcuM 第78页、[SWS_EcuM_02684]、[SWS_EcuM_02932]

OS 启动后，紧接着由 StartOS 启动的任务调用 EcuM_StartupTwo [SWS_EcuM_02806]。该函数执行 StartPostOS：它初始化并启动 SchM，并调用 BswM_Init [SWS_EcuM_02932] SWS EcuM 第42页。进一步的初始化由 BswM 通过生成的函数 EcuM_AL_DriverInitBswM_<x> [SWS_EcuM_04114] 承担。

在多核 ECU 上，每个核运行一个 EcuM 实例，主 EcuM 启动其余核。Init Block 0 和 1 在每个核上运行，但仅在相应核上初始化其 MCAL 模块。SchM、OS 和所有核本地 BswM 均在每个核上启动 [SWS_EcuM_04145] [SWS_EcuM_04093] [SWS_EcuM_04014] SWS EcuM 第71页。

RUN 和 POST_RUN：用户请求与同 BswM 的仲裁

若 EcuMModeHandling 处于激活状态，用户可以请求并重新释放 RUN 和 POST_RUN [SWS_EcuM_04115] [SWS_EcuM_04130]。为此使用 EcuM_RequestRUN、EcuM_ReleaseRUN、EcuM_RequestPOST_RUN 和 EcuM_ReleasePOST_RUN。所有这四个函数都需要类型为 EcuM_UserType 的已配置用户标识符 [SWS_EcuM_04124] [SWS_EcuM_04127] [SWS_EcuM_04128] [SWS_EcuM_04129]。EcuM 按用户跟踪请求，且单个用户无法对其进行嵌套。它在不同变量中分别维护 RUN 和 POST_RUN 请求 [SWS_EcuM_04126] [SWS_EcuM_04125] SWS EcuM 第116页。SW-C 通过端口 StateRequest_{UserName} 访问这些服务 [SWS_EcuM_04135]。

EcuM 使用 BswM_EcuM_RequestedState(ECUM_STATE_APP_RUN, ECUM_RUNSTATUS_REQUESTED) 向 BswM 报告首次 RUN 或 POST_RUN 请求。在最后一次释放 RUN 或 POST_RUN 时，它报告相应状态及 ECUM_RUNSTATUS_RELEASED [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04119]。BswM 评估其规则并使用 EcuM_SetState 设置新状态。EcuM 随后向 RTE 指示匹配的模式，并在收到其反馈后报告 BswM_EcuM_CurrentState [SWS_EcuM_04122] [SWS_EcuM_04116] [SWS_EcuM_04143]。模式管理指南展示了相应的 BswM 规则，例如一旦释放 RUN 就切换到 POST_RUN Mode-Management-Guide 第34页。

时序图：EcuM 仲裁用户的请求并将结果报告给 BswM。BswM 通过 EcuM_SetState 返回状态，EcuM 将其传递给 RTE。来源：[SWS_EcuM_04144]、[SWS_EcuM_04117]、[SWS_EcuM_04116]、[SWS_EcuM_04143]

关断目标以及通过 OffPreOS 和 OffPostOS 进行关断

EcuM_SelectShutdownTarget 仅将目标和模式保存用于随后的 SHUTDOWN 或 SLEEP 阶段，自身不触发任何操作 [SWS_EcuM_02822] [SWS_EcuM_00624] [SWS_EcuM_02585]。模式参数在目标为 SLEEP 时选择已配置的休眠模式，在目标为 RESET 时选择复位模式。当目标为 OFF 时该参数被忽略 [SWS_EcuM_02979] [SWS_EcuM_02185]。复位模式至少包括 Mcu_PerformReset、WdgM_PerformReset 以及切换 I/O 引脚 [SWS_EcuM_04005] [SWS_EcuM_04044]。关断原因通过 EcuM_SelectShutdownCause 记录 [SWS_EcuM_04007] [SWS_EcuM_04050]。EcuM_GetLastShutdownTarget 返回最近从中唤醒或启动的目标。该值在下一次关断前保持不变 [SWS_EcuM_02156]。

SHUTDOWN 阶段以 OFF 或 RESET 结束 [SWS_EcuM_03022]。何时设置该目标通常由 BswM 决定 SWS EcuM 第66页。在 OffPreOS 中反初始化 BswM 和 SchM 并检查唤醒事件。若有待处理事件，则将 RESET 设为目标。最后一个动作是 ShutdownOS [SWS_EcuM_03021] [SWS_EcuM_02952] SWS EcuM 第49页。

随后关断钩子调用 EcuM_Shutdown，该函数不返回。在 EcuM_OnGoOffTwo 之后，对于目标 RESET 执行 EcuM_AL_Reset，对于目标 OFF 执行 EcuM_AL_SwitchOff [SWS_EcuM_02953] [SWS_EcuM_02917] [SWS_EcuM_04074] [SWS_EcuM_04075]。解读：对于 RESET 和 OFF，BswM 大概率也是通过 EcuM_GoDownHaltPoll 触发该阶段，因为其返回值描述根据关断目标进行了区分 [SWS_EcuM_91002]。

时序图：OffPreOS 反初始化 BswM 和 SchM，检查唤醒事件并终止 OS。随后 OffPostOS 根据关断目标分支到复位或关断。来源：SWS EcuM 第49页、SWS EcuM 第49页、[SWS_EcuM_02953]、[SWS_EcuM_91002]

SLEEP 阶段：GoSleep、Halt 或 Poll 以及 WakeupRestart

若选择 SLEEP 作为目标，EcuM_GoDownHaltPoll 将启动 SLEEP 阶段。调用者必须预先设置匹配的目标 [SWS_EcuM_91002] SWS EcuM 第54页。在 GoSleep 中，EcuM 通过 EcuM_EnableWakeupSources 激活目标休眠模式下 EcuMWakeupSourceMask 中的所有唤醒源。在多核 ECU 上，它还会额外占用核专属资源 RES_AUTOSAR_ECUM。与关断不同，OS 保持活动状态 [SWS_EcuM_02389] [SWS_EcuM_03010] [SWS_EcuM_02951]。绝不能丢失任何唤醒事件。若在 GoSleep 期间已发生唤醒事件，则跳过 Halt 和 Poll [SWS_EcuM_02188]。

使微控制器停止的休眠模式经历 Halt 序列。在此之前 EcuM 调用 EcuM_GenerateRamHash，之后调用 EcuM_CheckRamHash [SWS_EcuM_02960] [SWS_EcuM_02863]。相反，采用降低时钟频率的休眠模式则使用 Poll 序列。该序列在阻塞循环中调用 EcuM_SleepActivity 和 EcuM_CheckWakeup，直到事件被报告为 pending 或已校验 [SWS_EcuM_02962] [SWS_EcuM_03020]。在 R20-11 中，EcuM_CheckWakeup 仍为一个 callout。自 R21-11 起，该 callout 才被称为 EcuM_CheckWakeupHook [SWS_EcuM_02929] SWS EcuM 第145页。

唤醒事件将进入 WakeupRestart 序列 [SWS_EcuM_02963] SWS EcuM 第56页：

  1. MCU 返回正常模式。
  2. EcuM_DisableWakeupSources 停用当前待处理的唤醒源；所有其他唤醒源保持就绪 [SWS_EcuM_02922]。
  3. EcuM_AL_DriverRestart 重新初始化受影响的驱动程序 [SWS_EcuM_02923]。
  4. 调度器被重新释放。

相反，若在休眠期间发生硬件复位或上电周期，ECU 将在 STARTUP 中重新开始 [SWS_EcuM_04001]。

时序图：GoSleep 准备唤醒源，Halt 或 Poll 实现休眠，WakeupRestart 返回 UP 状态。来源：SWS EcuM 第52页、SWS EcuM 第85页、SWS EcuM 第87页、SWS EcuM 第58页

可选地，EcuM 维护一个时钟，用于计算电池接通以来的秒数 [SWS_EcuM_04069]。每个用户最多可设置一个唤醒闹钟。主闹钟始终对应最早的用户闹钟 [SWS_EcuM_04070] [SWS_EcuM_04072]。EcuM_SetAbsWakeupAlarm 以 ECUM_E_EARLIER_ACTIVE 拒绝更晚的时间点，以 ECUM_E_PAST 拒绝已经过去的时间点 [SWS_EcuM_04059] [SWS_EcuM_04060]。离开 SLEEP 时，EcuM 丢弃所有闹钟 [SWS_EcuM_04009]。

唤醒源：状态、校验与查询

EcuM 将最多 32 个唤醒源作为类型为 EcuM_WakeupSourceType 的位掩码进行管理。预定义了 5 个位，包括 ECUM_WKSOURCE_POWER 和 ECUM_WKSOURCE_RESET。其他源通过 EcuMWakeupSourceId 分配位 5 至 31 [SWS_EcuM_04040] [SWS_EcuM_02165] [SWS_EcuM_02166] SWS EcuM 第63页。每个源处于 NONE、PENDING、VALIDATED 或 EXPIRED 状态之一 [SWS_EcuM_04091] [SWS_EcuM_04041]。EcuM 将每次状态转换作为模式请求报告给 BswM [SWS_EcuM_04003]。

状态图：唤醒源从 NONE 经由 PENDING 变为 VALIDATED 或 EXPIRED。每次状态转换均报告给 BswM，且 EcuM_ClearWakeupEvent 将唤醒源重置为 NONE。来源：SWS EcuM 第60页、[SWS_EcuM_04091]、[SWS_EcuM_02683]

驱动程序使用 EcuM_SetWakeupEvent 恰好报告一次检测到的事件 SWS EcuM 第71页。该函数也可以从中断上下文以及无 OS 上下文中调用。它通过“或”操作将传递的位设置到 Pending 变量中。它会忽略不属于所选休眠模式的源 [SWS_EcuM_02826] [SWS_EcuM_02171] [SWS_EcuM_01117] [SWS_EcuM_04138]。

若事件必须被校验，EcuM 会根据 EcuMValidationTimeout 启动源特定的超时。若再次报告同一源，超时不会重新启动 [SWS_EcuM_02975] [SWS_EcuM_02565] [SWS_EcuM_02709] [SWS_EcuM_02712]。若未为源配置校验，EcuM_SetWakeupEvent 的效果同时等同于 EcuM_ValidateWakeupEvent。5 个预定义的源从不进行校验 [SWS_EcuM_02566] [SWS_EcuM_02625]。

校验本身在 EcuM_MainFunction 中运行，该函数为此调用 callout EcuM_CheckValidation [SWS_EcuM_02539] [SWS_EcuM_02925] SWS EcuM 第64页。EcuM_ValidateWakeupEvent 具有以下效果 [SWS_EcuM_02710] [SWS_EcuM_04078] [SWS_EcuM_04079] [SWS_EcuM_02645] [SWS_EcuM_04140]：

  • 它停止超时并将各位置位在 Validated 变量中。
  • 它向 BswM 报告 ECUM_WKSTATUS_VALIDATED。
  • 若配置了通道或 PNC，它分别调用 ComM_EcuM_WakeUpIndication 或 ComM_EcuM_PNCWakeUpIndication。

若超时到期，主函数设置 Expired 位并报告 ECUM_WKSTATUS_EXPIRED [SWS_EcuM_04081] [SWS_EcuM_04082]。在 RUN 状态下，校验仅对通信通道起作用 [SWS_EcuM_02790] [SWS_EcuM_02791]。

活动图：对于无需校验的源，事件立即可被校验。对于其余源，事件保持 PENDING，直到 EcuM_ValidateWakeupEvent 到达或超时到期且源变为 EXPIRED。来源：SWS EcuM 第63页、SWS EcuM 第78页、[SWS_EcuM_02566]、[SWS_EcuM_04082]

当前状态由 EcuM_GetPendingWakeupEvents、EcuM_GetValidatedWakeupEvents 和 EcuM_GetExpiredWakeupEvents 查询。EcuM_ClearWakeupEvent 从所有三个变量中清除传入的位 [SWS_EcuM_01156] [SWS_EcuM_02533] [SWS_EcuM_04076] [SWS_EcuM_02683]。

某些唤醒源具有集成电源，因此其唤醒效果类似于上电复位。对于这些源，EcuM_StartCheckWakeup 启动 CheckWakeupTimer，以防止过早关断。EcuM_SetWakeupEvent 或 EcuM_EndCheckWakeup 再次终止该定时器 [SWS_EcuM_04096] [SWS_EcuM_04098] [SWS_EcuM_02927] SWS EcuM 第70页。

发生错误时的行为

不可恢复的错误由 EcuM 通过 callout EcuM_ErrorHook 连同对应的错误代码进行报告 [SWS_EcuM_04033] [SWS_EcuM_02904]。在 R20-11 中为此存在两个代码 [SWS_EcuM_91003] [SWS_EcuM_02987]：

  • Post-Build 数据不一致时为 ECUM_E_CONFIGURATION_DATA_INCONSISTENT。
  • 唤醒后 RAM 检查失败时为 ECUM_E_RAM_CHECK_FAILED。

EcuM_CheckRamHash 函数

此标注旨在提供 RAM 完整性测试。此测试的目标是确保在长时间的SLEEP持续时间后，RAM内容仍然一致。检查不需要详尽，因为这会在唤醒期间消耗相当多的处理时间。精心设计的检查将快速执行并以足够的概率检测RAM完整性缺陷。本规范不对为特定ECU选择的算法做出任何假设。必须仔细选择要检查的RAM区域。这取决于检查算法本身和任务结构。执行 RAM 检查的任务的堆栈内容，例如很可能无法检查。良好的做法是在同一任务中进行哈希生成和检查，并且该任务不可抢占，并且哈希生成和哈希检查之间只有很少的活动。 RAM 检查本身由系统设计者提供。如果应用多核且存在 Satellite-Ecu M(s)：此API将仅由 Master-EcuM 调用。

uint8 EcuM_CheckRamHash (void);
