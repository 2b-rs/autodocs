EcuM 的角色：复位、BswM 和硬件之间的阶段管理器

ECU 状态管理器（EcuM）负责 OS、SchM 和 BswM 的启动与关闭，管理停机目标，并监控唤醒源及其验证。在灵活变体中，它没有自身的状态机。BswM 决定状态转换，EcuM 执行相应的时序并返回结果（SWS EcuM 第103页、[SWS_EcuM_04116]）。

EcuM 将依赖于硬件的步骤外包给标注函数。它们是集成代码中由系统设计人员填充的函数存根（Glossary 第42页）。示例包括 EcuM_AL_DriverInitZero [SWS_EcuM_02905] 以及 EcuM_AL_SwitchOff [SWS_EcuM_02920]。所需的外来接口列于 [SWS_EcuM_02858] 和 [SWS_EcuM_02859] 中。模块关系图中提供了总览（SWS EcuM 第33页）。

上下文图：EcuM 控制 OS、SchM、BswM 和 Mcu，将底层硬件相关操作委托给标注函数，并接收驱动程序的唤醒通知以及 SW-C 的状态请求。来源：SWS EcuM 第33页、[SWS_EcuM_02858]、[SWS_EcuM_04122]、[SWS_EcuM_02826]

启动：从 EcuM_Init 经由 StartOS 到 EcuM_StartupTwo

在 EcuM_Init 之前，堆栈和 C 变量初始化必须准备就绪（SWS EcuM 第39页）。EcuM_Init 绝不返回，因为它是以 StartOS 结尾的 [SWS_EcuM_02811]。在此期间，它执行 StartPreOS 时序 [SWS_EcuM_02684]，该时序初始化启动 OS 所需的所有模块 [SWS_EcuM_02603]。

StartPreOS 时序按以下步骤运行：

  • Init Block 0 仅包含在预编译或链接时配置的模块 [SWS_EcuM_02905]。
  • EcuM_DeterminePbConfiguration 选择 Post-Build 配置并提供指向 EcuM_ConfigType 的指针。该结构引用所有其他模块的配置 [SWS_EcuM_02906] [SWS_EcuM_02801]。
  • 在首次 BSW 初始化之前，EcuM 通过哈希检查所有 Post-Build 数据的一致性 [SWS_EcuM_02796] [SWS_EcuM_02798]。
  • 接下来是 Init Block 1 [SWS_EcuM_02907]。初始化的顺序和参数来自配置 [SWS_EcuM_02559] [SWS_EcuM_02730]。
  • EcuM 将复位原因转换为唤醒源并对其进行记录 [SWS_EcuM_02623]。
  • 可选运行 EcuM_LoopDetection [SWS_EcuM_04137]。

EcuM_StartupTwo 必须从作为 StartOS 的结果而启动的任务中调用 [SWS_EcuM_02806]。该函数执行 StartPostOS 时序：启动 SchM、初始化 BswM、初始化 SchM 以及启动调度程序定时 [SWS_EcuM_02932]（SWS EcuM 第42页）。其余 BSW 模块随后由 BswM 通过生成的函数进行初始化 EcuM_AL_DriverInitBswM_<x> [SWS_EcuM_04114] [SWS_EcuM_04142]。

时序图：STARTUP 阶段分为两部分。在 OS 之前运行 Init 块 0/1 和一致性检查，在 OS 之后启动 SchM 和 BswM。来源：SWS EcuM 第38页、SWS EcuM Fixed 第32页、[SWS_EcuM_02684]、[SWS_EcuM_02932]

UP 阶段：RUN/POST_RUN 请求与模式切换

如果 EcuMModeHandling 处于激活状态 [SWS_EcuM_04115]，则已配置的用户可以请求并再次释放 RUN 和 POST_RUN [SWS_EcuM_04130]。为此提供了 EcuM_RequestRUN、EcuM_ReleaseRUN、EcuM_RequestPOST_RUN 和 EcuM_ReleasePOST_RUN [SWS_EcuM_04124] [SWS_EcuM_04129]。EcuM 按用户分别维护请求 [SWS_EcuM_04126]，并对 RUN 和 POST_RUN 进行区分（SWS EcuM 第116页）。单个用户不能重复发出请求 [SWS_EcuM_04125]。

EcuM 通过 BswM_EcuM_RequestedState 报告仲裁结果：

  • 在首次发出请求时，它报告 ECUM_RUNSTATUS_REQUESTED [SWS_EcuM_04144]。
  • 在释放最后一个请求时，它报告 ECUM_RUNSTATUS_RELEASED [SWS_EcuM_04117] [SWS_EcuM_04119]。

BswM 随后使用 EcuM_SetState 设置新状态 [SWS_EcuM_04122]。EcuM 通过端口 currentMode 将模式传递给 RTE [SWS_EcuM_04133] [SWS_EcuM_04107]。在收到 RTE 的反馈后，它使用 BswM_EcuM_CurrentState 向 BswM 报告状态 [SWS_EcuM_04143]。Mode-Mgmt-Guide 第34页 中包含 BswM 的示例规则。

只要 OS 处于运行状态，EcuM_MainFunction 就会处理 EcuM 的日常任务 [SWS_EcuM_02837]。其中包括唤醒验证 [SWS_EcuM_02539] 以及（如果已配置）唤醒时钟 [SWS_EcuM_04002]。

时序图：EcuM 收集请求并仅报告仲裁结果。状态转换由 BswM 触发，RTE 仅在此之后接收模式。来源：[SWS_EcuM_04144]、[SWS_EcuM_04117]、[SWS_EcuM_04116]、[SWS_EcuM_04143]、Mode-Mgmt-Guide 第34页

停机目标以及关闭到 OFF 或 RESET

停机目标是指不运行任何代码的状态：Off、Sleep 和 Reset（SWS EcuM 第66页、[SWS_EcuM_04136]）。EcuM_SelectShutdownTarget 仅保存该目标，本身不触发任何操作 [SWS_EcuM_02585]。模式参数仅适用于 SLEEP 和 RESET [SWS_EcuM_02979]。可用的复位类型至少包括 Mcu_PerformReset、WdgM_PerformReset 以及切换 I/O 引脚 [SWS_EcuM_04005]。此外还可以记录关闭原因 [SWS_EcuM_04050]。

状态图：生命周期跨越 STARTUP、UP、SLEEP 和 SHUTDOWN 阶段。唤醒事件从 SLEEP 引导返回 UP，而复位则引导返回 STARTUP。来源：SWS EcuM 第71页、SWS EcuM 第54页、[SWS_EcuM_02963]、[SWS_EcuM_04001]

进入 SHUTDOWN 由 BswM 控制。它可能同样通过 EcuM_GoDownHaltPoll 进行，因为同步图提到了 BswM 的这一调用（SWS EcuM 第74页、[SWS_EcuM_91002]）。OffPreOS 时序调用 EcuM_OnGoOffOne [SWS_EcuM_02916] 并对 BswM 和 SchM 取消初始化（SWS EcuM 第90页）。作为最后一步，它调用 ShutdownOS [SWS_EcuM_02952]。若在此期间发生唤醒事件，EcuM 必须终止关闭并立即重新启动 [SWS_EcuM_02756]。推测这是通过将其目标更改为 RESET 来实现的。

关闭钩子调用 EcuM_Shutdown，该函数不返回 [SWS_EcuM_02953]。接下来是 OffPostOS 时序：EcuM_OnGoOffTwo，然后根据目标执行 EcuM_AL_Reset 或 EcuM_AL_SwitchOff [SWS_EcuM_04074] [SWS_EcuM_04075]。如果复位模式来源于 EcuM_ShutdownModeType，则在传递之前必须将其向右移动一个字节（SWS EcuM 第142页）。

活动图：关闭过程分支两次。首先 OffPreOS 检查挂起的唤醒事件，然后 OffPostOS 在 RESET 和 OFF 之间进行选择。来源：SWS EcuM 第50页、SWS EcuM 第82页、[SWS_EcuM_02756]、[SWS_EcuM_02953]

睡眠阶段：GoSleep、Halt 或 Poll、WakeupRestart

目标为 SLEEP 的 EcuM_GoDownHaltPoll 首先启动 GoSleep 时序。之后根据 EcuMSleepModeSuspend 执行 Halt 或 Poll 时序（SWS EcuM 第54页）。OS 在此阶段保持活动状态 [SWS_EcuM_02951]。GoSleep 使为睡眠模式配置的唤醒源处于就绪状态 [SWS_EcuM_02389] [SWS_EcuM_02546]，并在每个内核上占用资源 RES_AUTOSAR_ECUM [SWS_EcuM_03010]。如果在 GoSleep 期间已经发生唤醒事件，则不得再进入 Halt 和 Poll [SWS_EcuM_02188]。

这两种睡眠变体的区别如下：

  • Halt：微控制器停机，不运行任何代码 [SWS_EcuM_02960]。在此之前，EcuM_GenerateRamHash 计算 RAM 上的校验和，唤醒后由 EcuM_CheckRamHash 对其进行校验。在多核情况下，这仅在主核上进行 [SWS_EcuM_02863]。
  • Poll：控制器继续执行代码 [SWS_EcuM_02962]。在 R20-11 中，EcuM 在阻塞循环中调用 EcuM_SleepActivity 和标注函数 EcuM_CheckWakeup，直到出现唤醒事件 [SWS_EcuM_03020]。从 R21-11 开始，该标注函数命名为 EcuM_CheckWakeupHook，并且 EcuM_CheckWakeup 成为一个 EcuM 函数（SWS EcuM 第145页）。

时序图：Halt 时序通过生成和校验 RAM 校验和来包裹停机阶段。此后，它将唤醒源以 PENDING 或 VALIDATED 形式报告给 BswM。来源：SWS EcuM 第85页、[SWS_EcuM_02863]、[SWS_EcuM_02987]、[SWS_EcuM_02963]

在唤醒事件发生后，EcuM 重新接管控制并执行 WakeupRestart 时序 [SWS_EcuM_02963]。它包括：

  • 恢复 MCU 正常模式，
  • 停用挂起的唤醒源 [SWS_EcuM_04084]，
  • 通过 EcuM_AL_DriverRestart 重新初始化驱动程序并重新使能其唤醒回调 [SWS_EcuM_02562]，
  • 释放调度程序（SWS EcuM 第56页）。

唤醒源：位掩码、状态和验证协议

EcuM 将多达 32 个唤醒源作为位管理在 EcuM_WakeupSourceType 中。其中五个位置是预定义的（SWS EcuM 第63页、[SWS_EcuM_04040]）。其他源通过 EcuMWakeupSourceId [SWS_EcuM_02165] [SWS_EcuM_02166] 占用位 5 至 31。每个源处于四种状态之一：NONE、PENDING、VALIDATED 或 EXPIRED [SWS_EcuM_04091]。EcuM 将每次状态变更作为模式请求报告给 BswM [SWS_EcuM_04003]。

状态图：无需验证的源直接跳转到 VALIDATED。所有其他源在 PENDING 中等待确认，或在超时后进入 EXPIRED。来源：SWS EcuM 第60页、[SWS_EcuM_04091]、[SWS_EcuM_02566]、[SWS_EcuM_02683]

驱动程序使用 EcuM_SetWakeupEvent 报告一次检测到的事件（SWS EcuM 第71页）。这在中断中也是允许的 [SWS_EcuM_02171]。该函数设置 Pending 位 [SWS_EcuM_01117] 并忽略不属于所选睡眠模式的源 [SWS_EcuM_04138]。此外，它会启动验证定时器，但对于同一源的重复调用则不会重新启动 [SWS_EcuM_02709] [SWS_EcuM_02712]。如果未为某个源配置验证，则该事件立即被视为已验证 [SWS_EcuM_02566]。复位源和电源源从不进行验证 [SWS_EcuM_02625]。

验证在 EcuM_MainFunction 中运行 [SWS_EcuM_02539]，并遵循此协议：

  • EcuM_StartWakeupSources 准备各源，随后 EcuM_CheckValidation 对其进行查询 [SWS_EcuM_02924] [SWS_EcuM_02925]。
  • 如果验证成功，验证模块将调用 EcuM_ValidateWakeupEvent。随后 EcuM 停止定时器，设置 Validated 位，向 BswM 报告 VALIDATED 并通知 ComM [SWS_EcuM_04078] [SWS_EcuM_02710] [SWS_EcuM_04079] [SWS_EcuM_02645]。
  • 如果定时器超时，EcuM 将设置 Expired 位，向 BswM 报告 EXPIRED 并调用 EcuM_StopWakeupSources [SWS_EcuM_04081] [SWS_EcuM_04082] [SWS_EcuM_02926]。
  • 在 RUN 状态下，验证仅对通信通道生效 [SWS_EcuM_02790]。
  • EcuM_ClearWakeupEvent 清除所有三个内部变量中的位 [SWS_EcuM_02683]。
  • 正在运行的 CheckWakeupTimer 可防止在源被检查之前发生关闭 [SWS_EcuM_04096]。EcuM_SetWakeupEvent 会将其终止 [SWS_EcuM_04098]。

时序图：验证是一个具有两个出口的循环：确认或超时。每个出口都会生成向 BswM 和 ComM 发送的各自通知。来源：SWS EcuM 第63页、SWS EcuM 第64页、[SWS_EcuM_02709]、[SWS_EcuM_04082]

多核运行、唤醒时钟和引导目标

在多核 ECU 上，每个内核运行一个 EcuM 实例。主 EcuM 启动其余内核（SWS EcuM 第71页）。对于每个实例，以下规则适用：

  • Init 标注函数仅初始化自身内核的 MCAL 模块 [SWS_EcuM_04145]。
  • OS 和 SchM 在每个内核上启动 [SWS_EcuM_04093]。
  • 每个实例处理其自身内核的唤醒事件 [SWS_EcuM_04012]。
  • 目标 SLEEP 使所有内核进入睡眠 [SWS_EcuM_04092]。

可选的唤醒时钟计算连接电池以来的秒数 [SWS_EcuM_04069]。每个用户最多具有一个警报 [SWS_EcuM_04070]，且主警报跟随最早的用户警报 [SWS_EcuM_04072]。较晚的警报返回 ECUM_E_EARLIER_ACTIVE，过去的时间点返回 ECUM_E_PAST [SWS_EcuM_04059] [SWS_EcuM_04060]。何时清除警报由 [SWS_EcuM_04010] 规定。EcuM_SelectBootTarget 存储引导目标，以便引导加载程序能够读取它 [SWS_EcuM_02247]。

发生错误时的行为

不可恢复错误：此时 EcuM 调用 EcuM_ErrorHook [SWS_EcuM_04033]，并携带 ECUM_E_CONFIGURATION_DATA_INCONSISTENT 或 ECUM_E_RAM_CHECK_FAILED [SWS_EcuM_91003] [SWS_EcuM_02987]。

失败的 OS 调用：根据 R20-11，状态保持不变，且 EcuM 通过 ErrorHook 报告该错误 [SWS_EcuM_04139]。其自身的代码 ECUM_E_OS_CALL_FAILED 以及该钩子不返回的假设仅在后续版本中提及（SWS EcuM 第102页）。

其他规则：

  • EcuM 忽略初始化期间的错误 [SWS_EcuM_02980]。
  • 它将未知的复位原因映射到 ECUM_WKSOURCE_RESET [SWS_EcuM_02601]。
  • 在 Halt 或 Poll 期间进行复位或电源循环会导致返回 STARTUP [SWS_EcuM_04001]。
  • 如果 ECU 在 EcuM_AL_SwitchOff 中无法下电断电，则复位是恰当的反应。集成商可以限制死循环（SWS EcuM 第141页）。

向 DET 报告的开发错误：

  • 常规代码 [SWS_EcuM_03009]，
  • 重复请求 [SWS_EcuM_03024] 以及未请求的释放 [SWS_EcuM_03023]，
  • 未知的唤醒源 [SWS_EcuM_02867]，
  • EcuM_SetState 中的无效状态 [SWS_EcuM_04123]。
