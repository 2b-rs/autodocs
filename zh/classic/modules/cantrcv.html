CanIf 与收发器硬件之间驱动程序的作用

CAN 收发器驱动程序封装了 CAN 通道的物理总线驱动芯片。它负责切换该芯片的操作模式，检测唤醒事件，并读取状态与诊断数据。其通用状态模型旨在尽可能涵盖更多可用的收发器，并将 ComM 及 EcuM 与具体硬件解耦（SWS CanTrcv 第19页）。为此，硬件必须提供能够映射到该模型的接口 [SWS_CanTrcv_00098]。在 CAN 协议栈的框图中，通往收发器的控制路径与经由 CAN 控制器和 CAN 驱动程序的数据路径是分离的（SWS CanTrcv 第9页）。

向上的交互伙伴是 CanIf。CanIf_SetTrcvMode 调用 CanTrcv_SetOpMode（SWS CanIf 第95页），CanIf_GetTrcvMode 调用 CanTrcv_GetOpMode（SWS CanIf 第97页），CanIf_SetTrcvWakeupMode 调用 CanTrcv_SetWakeupMode（SWS CanIf 第92页）。反馈通过回调发送给 CanIf。为此，CanTrcv 强制需要 CanIf_TrcvModeIndication 和 Det_ReportRuntimeError [SWS_CanTrcv_00085]。可选的包括 CanIf_CheckTrcvWakeFlagIndication 和 CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00086] 等。向下，驱动程序通过 Dio 和 Spi 控制硬件（SWS CanTrcv 第26页）。它从 DEM、Dio、EcuM、Icu 和 Spi 导入类型 [SWS_CanTrcv_00084]。

上下文图：CanTrcv 由 CanIf 调用，通过 Dio/Spi 控制硬件，并向上报至 CanIf、EcuM、DEM 和 DET。来源：[SWS_CanTrcv_00085]、[SWS_CanTrcv_00084]、SWS CanTrcv 第52页

生命周期：从 NOT_ACTIVE 经由 CanTrcv_Init 到 CanTrcv_DeInit

在调用 CanTrcv_Init [SWS_CanTrcv_00001] 之前，环境必须已初始化该驱动程序使用的所有 BSW 驱动程序 [SWS_CanTrcv_00099]。规范将其归因于时间要求，例如上电后尽早读取硬件（SWS CanTrcv 第26页）。Init 根据各个连接的收发器的初始化时序以及来自 ConfigPtr 的配置来初始化所有连接的收发器 [SWS_CanTrcv_00180]。该配置的类型为 CanTrcv_ConfigType [SWS_CanTrcv_00209]。Init 根据配置将每个收发器置于 CANTRCV_TRCVMODE_SLEEP 或 CANTRCV_TRCVMODE_STANDBY 状态 [SWS_CanTrcv_00148]。如果 Init 检测到由收发器活动引起的唤醒，它会使用来自 CanTrcvWakeupSourceRef 的源向 EcuM_SetWakeupEvent 报告 [SWS_CanTrcv_00167]。

各来源之间的差异：针对容器 CanTrcvChannel 的配置图针对 CanTrcvInitState 也列出了 CANTRCV_OP_MODE_NORMAL，且作为默认值（SWS CanTrcv 第54页）。对于 R20-11，仍以 [SWS_CanTrcv_00148] 为准，其中仅将 SLEEP 或 STANDBY 列为目标状态。

CanTrcv_DeInit [SWS_CanTrcv_91001] 将硬件置于 NOT_ACTIVE 状态 [SWS_CanTrcv_91003]。在该状态下，可以通过新的配置序列对其重新配置（SWS CanTrcv 第49页）。若开发错误检测处于激活状态且收发器未处于 CANTRCV_TRCVMODE_NORMAL，DeInit 会报告 CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005]。因此，DeInit 预期在 NORMAL 状态下被调用。

状态图：Init 根据配置从 NOT_ACTIVE 转换至 SLEEP 或 STANDBY。状态逐级降级（NORMAL → STANDBY → SLEEP），NORMAL 可从任意模式到达，DeInit 则返回至 NOT_ACTIVE。来源：[SWS_CanTrcv_00148]、[SWS_CanTrcv_00103]、[SWS_CanTrcv_00104]、[SWS_CanTrcv_91003]、SWS CanTrcv 第19页

切换工作模式 NORMAL、STANDBY 和 SLEEP

CanTrcv_SetOpMode [SWS_CanTrcv_00002] 为异步工作。E_OK 仅表示请求已被接受（SWS CanTrcv 第33页）。驱动程序将内部状态切换为 NORMAL、STANDBY 或 SLEEP [SWS_CanTrcv_00102]。一旦达到该模式，它便会携带抽象的 CanIf-TransceiverId 调用 CanIf_TrcvModeIndication [SWS_CanTrcv_00158]。状态转换时的等待时间由其通过 Tm_BusyWait1us16bit [SWS_CanTrcv_00230] 实现。

对于模式顺序适用以下规则：

  • 从 NORMAL 出发，用户仅允许请求 STANDBY 或 NORMAL [SWS_CanTrcv_00103]。
  • 从 STANDBY 出发，仅允许请求 SLEEP 或 STANDBY [SWS_CanTrcv_00104]。
  • 根据状态图图例，NORMAL 可从所有三种模式中请求（SWS CanTrcv 第19页）。
  • 对当前模式的请求是允许的，且不属于错误 [SWS_CanTrcv_00161]。
  • 如果硬件不支持所请求的模式，该调用将返回 E_NOT_OK [SWS_CanTrcv_00105]。

CanIf 本身不检查此顺序（SWS CanIf 第88页）。根据 CanSM 规范，仅由集成代码请求 SLEEP，而非 CanSM（SWS CanSM 第94页）。当前状态由 CanTrcv_GetOpMode [SWS_CanTrcv_00005] 同步提供给 OpMode [SWS_CanTrcv_00106]，其类型为 CanTrcv_TrcvModeType [SWS_CanTrcv_00163]。

时序图：模式切换被同步接受，并通过指示异步确认。来源：[SWS_CanTrcv_00002]、[SWS_CanTrcv_00158]、[SWS_CanTrcv_00230]、SWS CanTrcv 第56页

检测、缓冲并上报唤醒事件

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] 控制是否继续上报唤醒事件。该参数的类型为 CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164]：

  • CANTRCV_WUMODE_ENABLE 将已保存的事件上报为“present” [SWS_CanTrcv_00111]。
  • CANTRCV_WUMODE_DISABLE 禁用上报。收发器和驱动程序在内部继续检测并保存事件 [SWS_CanTrcv_00093]。
  • CANTRCV_WUMODE_CLEAR 清除已保存的事件 [SWS_CanTrcv_00094]。该模式适用于禁用上报阶段 [SWS_CanTrcv_00150]。

在禁用期间不得丢失任何事件 [SWS_CanTrcv_00095]。

活动图：在检查参数后，SetWakeupMode 分支至 ENABLE、DISABLE 和 CLEAR。来源：[SWS_CanTrcv_00111]、[SWS_CanTrcv_00093]、[SWS_CanTrcv_00094]、[SWS_CanTrcv_00117]、SWS CanTrcv 第37页

唤醒通过两种途径进行检测：

  • CanTrcv_MainFunction [SWS_CanTrcv_00013] 周期性轮询处于 STANDBY 和 SLEEP 状态的所有总线，并设置唤醒事件标志 [SWS_CanTrcv_00112]。
  • 在发生唤醒中断时，CanIf 会调用 CanTrcv_CheckWakeup [SWS_CanTrcv_00143]。在硬件支持的前提下，该函数检查收发器是否为唤醒原因，并使用 CanTrcvWakeupSourceRef 上报给 EcuM_SetWakeupEvent [SWS_CanTrcv_00146]。

第二种途径的入口为 CanIf_CheckWakeup，由集成代码在 EcuM_CheckWakeup 的上下文中调用（SWS CanIf 第56页、SWS EcuM 第163页）。解释：周期性轮询推测是针对无可用唤醒中断的情况对中断驱动途径的补充。

若配置了 CanTrcvIcuChannelRef，CanTrcv 会通过 Icu_EnableNotification 和 Icu_DisableNotification 切换唤醒通知 [SWS_CanTrcv_00171]。在转换至 STANDBY 时，它会激活 ICU 通道 [SWS_CanTrcv_00172]。较新的版本在转换至 NORMAL 时还会额外将其停用（SWS CanTrcv 第22页）。

唤醒原因由 CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] [SWS_CanTrcv_00107] 提供，例如 CANTRCV_WU_BY_BUS、CANTRCV_WU_INTERNALLY、CANTRCV_WU_RESET 或 CANTRCV_WU_NOT_SUPPORTED [SWS_CanTrcv_00165]。能否精确区分这些原因很大程度上取决于硬件（SWS CanTrcv 第35页）。

时序图：硬件中断通过 EcuM、集成代码和 CanIf 触发 CanTrcv_CheckWakeup，并在适当时触发 EcuM_SetWakeupEvent。来源：[SWS_CanTrcv_00143]、[SWS_CanTrcv_00146]、SWS EcuM 第176页、SWS EcuM 第163页

选择性唤醒（Partial Networking）与收发器标志

具备选择性唤醒功能的收发器不仅响应唤醒模式（Wake-up-Pattern）唤醒，还额外响应唤醒帧（简称 WUF）唤醒（SWS CanTrcv 第27页）。硬件是否具备该能力由 CanTrcvHwPnSupport 指示 [SWS_CanTrcv_00174]。仅当设置了此参数时，容器 CanTrcvPartialNetwork 以及标志和系统数据 API [SWS_CanTrcv_00175] 才存在。接受哪种唤醒帧由 CanTrcvPnFrameCanId、CanTrcvPnFrameCanIdMask 和 CanTrcvPnFrameDataMask 确定 [SWS_CanTrcv_00177]。CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] 使用 PN_ENABLED 或 PN_DISABLED [SWS_CanTrcv_00210] 开启或关闭 PN 功能 [SWS_CanTrcv_00221] [SWS_CanTrcv_00222]。

在关闭过程中，CanSM 使用 CanTrcv_ClearTrcvWufFlag [SWS_CanTrcv_00214]，以便在进入低功耗模式时不会丢失帧唤醒。随后收发器应转换至 STANDBY [SWS_CanTrcv_00194]。CanTrcv 通过 CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195] 报告该标志已被清除。异步的 CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223] 通过 CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224] 确认其检查结果。CanSM 在状态 S_PN_CLEAR_WUF 下重试清除 WUF 的请求（SWS CanSM 第37页）。

针对诊断和 PN 监控还提供了其他函数：

  • CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215]、CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216] 和 CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217] 使用 CanTrcv_TrcvFlagStateType [SWS_CanTrcv_00211]。
  • CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] 将配置和状态以原始形式作为 uint32 [SWS_CanTrcv_00189] 提供。

标志 POR 和 SYSERR 会在两处进行检查：

  • 对于支持 PN 的硬件，CanTrcv_SetOpMode 会检查这两个标志 [SWS_CanTrcv_00186]。若设置了 POR，则会重新执行配置序列 [SWS_CanTrcv_00187]。
  • 在初始化过程中，一旦设置了 POR 或 SYSERR，就会重新配置选择性唤醒功能 [SWS_CanTrcv_00182]。

被设置的 POR 还会通过 EcuM_SetWakeupEvent 连同来自 CanTrcvPorWakeupSourceRef 的源一起上报 [SWS_CanTrcv_00183]。

时序图：在 PN 关闭过程中，依次执行 WUF 清除、STANDBY 和唤醒标志检查，每次均通过指示返回反馈。来源：[SWS_CanTrcv_00194]、[SWS_CanTrcv_00195]、[SWS_CanTrcv_00224]、SWS CanTrcv 第57页、SWS CanTrcv 第53页

每个收发器通道的配置与实例化

对于每种收发器硬件类型，ECU 都具有一个驱动程序实例。该实例服务于此类型的所有芯片 [SWS_CanTrcv_00016]，通过参数 uint8 Transceiver 进行寻址。每个通道都在一个容器 CanTrcvChannel（多重度 1..*）中描述。它包括 CanTrcvChannelId、CanTrcvInitState、CanTrcvWakeupByBusUsed、CanTrcvHwPnSupport、CanTrcvIcuChannelRef 以及对唤醒、POR 和 SYSERR 唤醒源的引用（SWS CanTrcv 第67页）等。硬件访问通过对 Dio 通道或 Spi 序列的引用进行配置（SWS CanTrcv 第78页）。

驱动程序必须拒绝实现不支持的分区分配 [SWS_CanTrcv_00231]。如果硬件能够区分总线错误与其他硬件错误，则通过 CanTrcvBusErrFlag 指示 [SWS_CanTrcv_00178]。版本信息由 CanTrcv_GetVersionInfo [SWS_CanTrcv_00008] 提供。

发生错误时的行为

错误按照通用 BSW 模式进行分类（SWS CanTrcv 第23页）。定义为开发错误的内容包括 CANTRCV_E_INVALID_TRANSCEIVER（1）、CANTRCV_E_PARAM_POINTER（2）、CANTRCV_E_UNINIT（11）、CANTRCV_E_TRCV_NOT_STANDBY（21）、CANTRCV_E_TRCV_NOT_NORMAL（22）和 CANTRCV_E_PARAM_TRCV_WAKEUP_MODE（23）[SWS_CanTrcv_00050]。所有检查均遵循相同的模式：当 DET 处于激活状态时，报告该错误；当 DET 处于停用状态时，该函数返回 E_NOT_OK。示例包括 [SWS_CanTrcv_00122]、[SWS_CanTrcv_00123] 和 [SWS_CanTrcv_00132]。对于 CanTrcv_SetOpMode，特别适用以下规则：

  • 无效的 OpMode 会导致 CANTRCV_E_PARAM_TRCV_OPMODE [SWS_CanTrcv_00087]。
  • 不允许的模式序列会导致 CANTRCV_E_TRCV_NOT_NORMAL 或 CANTRCV_E_TRCV_NOT_STANDBY [SWS_CanTrcv_00120] [SWS_CanTrcv_00121]。

在 CanTrcv_Init 中，不支持的波特率会报告 CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168]。

活动图：该图展示了从 CanTrcv_SetOpMode 到接受请求的检查与错误路径。检查顺序在来源中未做规定，此处仅作清晰排列。来源：[SWS_CanTrcv_00122]、[SWS_CanTrcv_00123]、[SWS_CanTrcv_00087]、[SWS_CanTrcv_00120]、[SWS_CanTrcv_00121]、[SWS_CanTrcv_00105]、[SWS_CanTrcv_00186]、[SWS_CanTrcv_00114]

如果缺少与收发器的通信或通信存在故障，驱动程序会报告运行时错误 CANTRCV_E_NO_TRCV_CONTROL（26）[SWS_CanTrcv_91006]。这适用于 Init [SWS_CanTrcv_00113]、SetOpMode [SWS_CanTrcv_00114]、GetOpMode [SWS_CanTrcv_00115]、SetWakeupMode [SWS_CanTrcv_00117]、GetTrcvSystemData [SWS_CanTrcv_00190] 和 ClearTrcvWufFlag [SWS_CanTrcv_00196]。这些函数随后返回 E_NOT_OK。相比之下，在这种情况下 CanTrcv_GetBusWuReason 则返回 E_OK [SWS_CanTrcv_00116]。解释：因此该返回值在此处可能并不表示有效原因。对于错误情况，该类型规定了值 CANTRCV_WU_ERROR [SWS_CanTrcv_00165]。

CANTRCV_E_BUS_ERROR 被定义为 Extended Production Error [SWS_CanTrcv_00228]。当 BUSERR 标志被置位且该功能已被配置并受硬件支持时，它会被检测出来 [SWS_CanTrcv_00229]。周期性函数 CanTrcv_MainFunctionDiagnostics [SWS_CanTrcv_00218] 仅存在于 CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]。它通过 Dem_SetEventStatus 报告 FAILED [SWS_CanTrcv_00206] 或 PASSED [SWS_CanTrcv_00227]。相关事件通过 CanTrcvDemEventParameterRefs 引用（SWS CanTrcv 第78页）。
