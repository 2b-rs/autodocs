收集、过滤并缓冲来自 SW-C 和 BSW 的日志与跟踪消息，并将其发送至外部工具。

Dlt 模块收集来自 SW-C、BSW 模块、DET 以及 RTE VFB Hook 的日志与跟踪消息。它根据日志级别和跟踪状态对消息进行过滤，将其分配给 LogChannel 并进行缓冲。发送过程通过周期性 Dlt_TxFunction 和 PduR [SWS_Dlt_00241] 解耦进行。外部客户端可以在运行时更改过滤器和通道分配；已注册的 SW-C 会收到相应通知。最重要的约束条件：在 Dlt_Init 之前以及可选的启动延迟结束前，消息仅会被缓冲 [SWS_Dlt_00005]。

Dlt 模块是 ECU 上日志与跟踪消息的中央收集点。SW-C（通过 RTE 端口）和 BSW 模块通过 Dlt_SendLogMessage 和 Dlt_SendTraceMessage 提供消息 [SWS_Dlt_00241] [SWS_Dlt_00243]。DET 错误通过 Dlt_DetForwardErrorTrace 传入 [SWS_Dlt_00430]，SW-C 通信则通过生成的 RTE VFB 跟踪 Hook 传入 [SWS_Dlt_00027]。唯一的接收端是带有 PduR_DltTransmit 的 PduR [SWS_Dlt_00762]。每条消息均通过各占 4 字节的 ApplicationId 和 ContextId 元组进行标识；0x00000000 用作通配符 [SWS_Dlt_00226] [SWS_Dlt_00227]。

上下文图：围绕 Dlt 的源、辅助服务（NvM、Gpt/StbM、SchM）以及作为接收端的 PduR。来源：[SWS_Dlt_00762]、[SWS_Dlt_00763]、[SWS_Dlt_91005]。

早在初始化之前，Dlt 就会缓冲传入的消息 [SWS_Dlt_00003]。只有在 Dlt_Init 运行且可选的启动延迟定时器超时后，才会处理这些消息 [SWS_Dlt_00005]。在具备 NvRAM 支持的情况下，Dlt_Init 通过 NvM_ReadBlock 恢复运行时配置 [SWS_Dlt_00453]。仅在通过 Dlt_StoreConfiguration 提出明确请求时才会进行保存 [SWS_Dlt_00078]。

在调用上下文中，Dlt 执行过滤、通道选择、长度检查和缓冲区存储。发送过程从周期性 Dlt_TxFunction 中解耦执行，包括在收到否定确认后的重试 SWS DLT 第92页 [SWS_Dlt_91005]。

时序图：同步发送调用以存入缓冲区结束。Dlt_TxFunction 负责发送、确认和重试。来源：SWS DLT 第 92 页、[SWS_Dlt_91005]、[SWS_Dlt_00273]。

外部客户端通过经由 Dlt_RxIndication 接收的控制消息来控制日志级别、跟踪状态和 LogChannel 阈值 [SWS_Dlt_00272]。相同的控制变量也可以作为 API 提供，例如 Dlt_SetLogLevel [SWS_Dlt_00252]。为了使 Dlt 能够通过 LogLevelChangedNotification 通知已注册的 SW-C，它们先前需使用 Dlt_RegisterContext 注册其上下文 [SWS_Dlt_00245] [SWS_Dlt_00496]。

发生错误时，发送调用会报告 DLT_E_MSG_TOO_LARGE、DLT_E_NO_BUFFER 或 DLT_E_UNKNOWN_SESSION_ID [SWS_Dlt_00495]。发生缓冲区溢出时，消息将被丢弃，设置溢出标志，并根据配置发送 BufferOverflowNotification SWS DLT 第32页。

角色与系统边界：日志与跟踪数据的中央收集点

Diagnostic Log and Trace (Dlt) 模块接收来自软件组件 (SW-C) 和基础软件 (BSW) 的日志与跟踪消息。它对其进行过滤和缓冲，并作为 Dlt 消息转发给外部工具。两个发送接口 Dlt_SendLogMessage 和 Dlt_SendTraceMessage 明确适用于 BSW 模块以及 SW-C [SWS_Dlt_00241] [SWS_Dlt_00243]。数据路径的源是 SW-C 或 BSW 模块，接收端是 PDU Router SWS DLT 第26页。为此，Dlt 必须需要 PduR_DltTransmit [SWS_Dlt_00762]。与外部客户端的消息格式、命令和协议并非由 SWS 规定，而是由协议规范规定 SWS DLT 第9页。

除显式调用外，还存在固定的提供方：

  • DET：错误消息通过扇出函数 Dlt_DetForwardErrorTrace 进入 Dlt [SWS_Dlt_00430] [SWS_Dlt_00432]。它们带有 ApplicationID “DET” 和 ContextId “STD” [SWS_Dlt_00376]。
  • DEM：关于 DEM 事件的日志消息使用 “DEM”、“STD0” 和 MessageID 0x00000001 [SWS_Dlt_00377]。
  • RTE：它隐式地将 SW-C 通信作为 VFB 跟踪转发 [SWS_Dlt_00276] [SWS_Dlt_00284]。

Dlt 从 Gpt 或 StbM 获取时间戳，持久化由 NvM 负责 [SWS_Dlt_00763]。Dlt_DetForwardErrorTrace 在 R20-11 中属于 API，但在 R25-11 中被移除 SWS DLT 第1页。

上下文图：Dlt 介于消息源（通过 RTE 的 SW-C、BSW、DET）与作为唯一接收端的 PduR 之间。NvM、Gpt/StbM 和 SchM 为辅助服务。来源：[SWS_Dlt_00762]、[SWS_Dlt_00763]、[SWS_Dlt_00430]、[SWS_Dlt_91005]，SWS DLT 第 26 页。

从启动到运行：初始化前的缓冲、Dlt_Init 与持久化

SW-C 和 BSW 模块在 Dlt 初始化之前即可进行记录。因此，Dlt 必须在初始化之前就缓冲来自 Dlt_SendLogMessage 和 Dlt_SendTraceMessage 的数据 [SWS_Dlt_00003]。只有在满足两个条件后，才会对缓冲的数据进行常规处理：Dlt_Init 已运行，且可选的定时器 DltGeneralStartUpDelayTimer 已超时 [SWS_Dlt_00005]。若配置了该定时器，则在调用 Dlt_Init 时启动它 SWS DLT 第25页。

状态图：在初始化之前以及（若适用）在启动延迟结束之前，消息仅被缓冲，此后才进行处理。来源：[SWS_Dlt_00003]、[SWS_Dlt_00005]，SWS DLT 第 25 页。

Dlt_Init 是同步且不可重入的。该函数需要一个指向 Dlt_ConfigType 的指针，其内容是特定于实现的 [SWS_Dlt_00239] [SWS_Dlt_00437]。由于 Dlt 使用 NvM，因此初始化应在启动过程的后期且在 NvM 之后进行 [SWS_Dlt_00239]。若 DltGeneralNvRAMSupport = TRUE，则 Dlt 表现如下：

  • 它通过 NvM_ReadBlock 读取 Dlt_Init 中的运行时值 [SWS_Dlt_00453]。
  • 它检查块的有效性 [SWS_Dlt_00449]。
  • 它将保存的配置用作初始值 [SWS_Dlt_00350]。

若无 NvRAM 支持，则静态配置生效 SWS DLT 第25页。根据图示，调用方是 EcuM SWS DLT 第159页。

时序图：EcuM 同步调用 Dlt_Init。Dlt 根据 DltGeneralNvRAMSupport 从 NvM 或静态加载配置，并可选择启动启动延迟定时器。来源：[SWS_Dlt_00239]、[SWS_Dlt_00453]、[SWS_Dlt_00005]，SWS DLT 第 159 页，CP SWS DLT 第 90 页。

消息模型：标识符、日志级别和跟踪类型

每条日志消息均带有一个包含五个字段的结构体 Dlt_MessageLogInfoType：argCount、logLevel、options、contextId 和 appId [SWS_Dlt_00236]。跟踪消息使用 Dlt_MessageTraceInfoType，其包含字段 traceInfo 而非日志级别 [SWS_Dlt_00237]。ApplicationId 和 ContextId 是 4 字节数组；0x00000000 用作通配符 [SWS_Dlt_00226] [SWS_Dlt_00227]。Application ID 是 SW-C 的短名称。Context ID 按功能对其消息进行分组 EXP LSA 第159页。位域 Dlt_MessageOptionsType 在第 0 位编码详细模式，在第 1–3 位编码消息类型 [SWS_Dlt_00229]。

在非详细模式下，唯一的 Message ID 标识消息的静态部分 [SWS_Dlt_00228]。ID 0x00000001 (DEM)、0x00000002 (DET) 和 0x00000003 (Trace) 是保留的，不能供 SW-C 使用 [SWS_Dlt_00031]。在线路上，Message ID 紧随报头之后，随后是非静态数据 PRS DLT 第23页。报头字段 MTIN 根据消息类型 MSTP 由日志级别或跟踪类型组成 PRS DLT 第24页。

发送路径：过滤器、LogChannel 选择、缓冲和 Dlt_TxFunction

发送调用是同步且可重入的。它们接收 sessionId、信息结构体以及有效载荷连同长度 [SWS_Dlt_00241] [SWS_Dlt_00243]。R20-11 图示展示了调用上下文中的时序：

  1. 消息过滤
  2. 应用 LogChannel 阈值
  3. 选择目标 LogChannel
  4. 检查长度
  5. 将消息存入 LogChannel 缓冲区

稍后才由 Dlt_TxFunction 负责发送 SWS DLT 第92页。以下各个步骤在 R23-11 版本的文档段落中有详细阐述，并与该图示一致。Dlt 仅在配置时才获取时间戳：通过 Gpt_GetTimeElapsed 或通过 StbM_GetCurrentTime [SWS_Dlt_00654] [SWS_Dlt_00655]。

LogChannel 分三个阶段确定 SWS DLT 第32页：

  1. 分配与 ApplicationId/ContextId 元组精确匹配的通道。
  2. 具有匹配 ApplicationId 和通配符 ContextId 的通道。
  3. 如果列表仍为空，则为默认 LogChannel。

分配可以在运行时使用 Dlt_SetLogChannelAssignment 进行更改 [SWS_Dlt_00751]。仅当消息对所有分配的通道均超过 DltLogChannelMaxMessageLength 时，才会被丢弃 SWS DLT 第31页。否则，它将被复制到其长度足够短的所有通道的缓冲区中 SWS DLT 第32页。

活动图：一条消息经过过滤器、三级通道选择、长度检查和缓冲区存储。每个分支都可能导致带有独立返回值的丢弃。来源：SWS DLT 第 31 页、SWS DLT 第 32 页、[SWS_Dlt_00495]、[SWS_Dlt_00751]。

通过 PduR 的发送与发送调用解耦，并在 Dlt_TxFunction 的上下文中运行 [SWS_Dlt_91005]。报头在 PduR_DltTransmit 之前组装，并且每条消息都有一个发送计数器进行计数 SWS DLT 第35页。在三种情况下，消息会从缓冲区中移除 SWS DLT 第38页：

  • PduR_DltTransmit 返回 E_NOT_OK。
  • 收到肯定的发送确认。
  • 收到否定确认且已超过 DltLogChannelMaxNumOfRetries。

下层通过以下回调进行报告：

  • Dlt_TxConfirmation [SWS_Dlt_00273]
  • Dlt_TriggerTransmit [SWS_Dlt_00754]
  • 在 TP 路径上为 Dlt_CopyTxData 和 Dlt_TpTxConfirmation [SWS_Dlt_00516] [SWS_Dlt_00756]

时序图：同步发送调用以存入缓冲区结束。实际的发送、确认和重试由周期性 Dlt_TxFunction 处理。来源：SWS DLT 第 92 页、[SWS_Dlt_91005]、[SWS_Dlt_00273]、SWS DLT 第 35 页、SWS DLT 第 38 页。

通过生成的 RTE Hook 函数进行 VFB 跟踪

VFB 跟踪意味着：RTE 隐式地将 SW-C 通信转发给 Dlt，而无需 SW-C 本身进行调用 SWS DLT 第23页。为此，Dlt 针对由短名称为 “Rte_Dlt…” 的 BswModuleEntry 所描述的每个已配置事件实现 Hook 函数 [SWS_Dlt_00027]。原型由 RTE 描述提供 [SWS_Dlt_00335]。Dlt_SendTraceMessage 是 SW-C 接口。因此，Hook 会在非详细模式下 [SWS_Dlt_00277] 并将所有参数作为有效载荷 [SWS_Dlt_00278] 调用等效的内部函数 [SWS_Dlt_00285]。

Hook 适用其他规则：

  • 每个 Hook 函数获得一个单独的 ContextId。在信号非常多的情况下，允许对事件进行捆绑 [SWS_Dlt_00279]。
  • 在发送之前，每个 Hook 检查其 ContextId 的跟踪状态 [SWS_Dlt_00281]。
  • 该消息携带带有 DLT_TRACE_VFB [SWS_Dlt_00484] 的 DLT_TYPE_APP_TRACE 以及 ApplicationID “VFBT” SWS DLT 第23页。
  • Hook 的跟踪状态通过一个与 LogTraceSessionControl 保持协调的单独函数进行更改 [SWS_Dlt_00283]。

解释：由于内部函数对应于 Dlt_SendTraceMessage，因此 VFB 消息可能经过与显式跟踪消息相同的缓冲发送路径 [SWS_Dlt_00285]。 问题 Q-cb77a5e7bde21b01 (未决)

时序图：RTE Hook 仅在跟踪状态激活时发送带有 DLT_TRACE_VFB 的非详细跟踪消息。它使用共同的发送路径属于一种解释。来源：[SWS_Dlt_00027]、[SWS_Dlt_00281]、[SWS_Dlt_00285]、[SWS_Dlt_00484]，SWS DLT 第 33 页。

会话、注册以及外部客户端的运行时控制

SW-C 根据配置项通过以下端口进行绑定：

  • 用于注册和发送的 SwcMessageService_{SW-C} [SWS_Dlt_91001]
  • 用于控制的 ControlService_{SW-C} [SWS_Dlt_00499]
  • 回调端口 SessionControlCallback_{SW-C} 和 InjectCallback_{SW-C} [SWS_Dlt_00779] [SWS_Dlt_00778]

端口定义的参数值用作 SessionId [SWS_Dlt_00022]。它们从 0x1000 开始；BSW 模块使用其模块 ID [SWS_Dlt_00023]。每个端口的值是唯一且连续的 [SWS_Dlt_00332]。它们的类型是 Dlt_SessionIDType (uint32) [SWS_Dlt_00225]。如果一个 SW-C 被多次实例化，则每个实例获得一个独立的会话 EXP LSA 第159页。

模块使用 Dlt_RegisterContext 注册其 ApplicationId/ContextId 元组及描述 [SWS_Dlt_00245]。Dlt 记录该元组是通过哪个端口注册的 [SWS_Dlt_00021]。停止时，模块调用 Dlt_UnregisterContext [SWS_Dlt_00769]。注册实现了一个目的：使 Dlt 知道在日志级别或跟踪状态更改时必须通知哪个 SW-C SWS DLT 第20页。为此使用 LogLevelChangedNotification 和 TraceStatusChangedNotification [SWS_Dlt_00496]。

外部客户端的控制消息通过 PduR 到达 Dlt。对于单个 PDU，它们通过 Dlt_RxIndication 到达 [SWS_Dlt_00272]。通过 TP，它们通过 Dlt_StartOfReception、Dlt_CopyRxData 和 Dlt_TpRxIndication 到达 [SWS_Dlt_91006] [SWS_Dlt_91008] [SWS_Dlt_91007]。Dlt 随后更新过滤器，可选地通知已注册的 SW-C，并通过 PduR_DltTransmit 发送响应 SWS DLT 第93页。

时序图：SW-C 注册其上下文。外部 SetLogLevel 命令更新过滤器，可选地触发通知，并通过 PduR 进行应答。来源：SWS DLT 第 93 页、[SWS_Dlt_00245]、[SWS_Dlt_00272]、[SWS_Dlt_00496]。

相同的控制变量作为 API 提供：

  • 每个元组的日志级别和跟踪状态 [SWS_Dlt_00252] [SWS_Dlt_00254]
  • 默认日志级别 [SWS_Dlt_00740] [SWS_Dlt_00733]
  • 每个 LogChannel 的默认跟踪状态 [SWS_Dlt_00743] [SWS_Dlt_00746]
  • LogChannel 阈值 [SWS_Dlt_00752] [SWS_Dlt_00753]
  • 全局开启和关闭过滤 [SWS_Dlt_00770]
  • 查询 Dlt_GetLogInfo、Dlt_GetTraceStatus 和 Dlt_GetLogChannelNames [SWS_Dlt_00732] [SWS_Dlt_00750] [SWS_Dlt_00749]

  • 在 R20-11 中，Dlt_GetDefaultTraceStatus 具有参数 logChannelName。在 R25-11 中缺少该参数 SWS DLT 第56页。
  • Dlt_AssignmentOperation 在 R20-11 中编码 DLT_ASSIGN_ADD = 0x01 和 DLT_ASSIGN_REMOVE = 0x02 [SWS_Dlt_00730]。R25-11 对 REMOVE 使用值 0x00 SWS DLT 第87页。对于 R20-11，该需求有效。

发生错误时的行为

SW-C 接口的错误代码在接口 DltSwcMessageService 中定义 [SWS_Dlt_00495]。此外，文档段落描述了发送路径上的行为。

  • 消息过长：当消息对于所有分配的 LogChannels 均过长时，返回 DLT_E_MSG_TOO_LARGE [SWS_Dlt_00495] SWS DLT 第31页。
  • 缓冲区溢出：返回 DLT_E_NO_BUFFER。该消息被丢弃，置位溢出标志，并根据配置发送 BufferOverflowNotification。Dlt_TxFunction 检查标志与去抖时间 SWS DLT 第32页 SWS DLT 第95页。
  • 未知会话或注册错误：DLT_E_UNKNOWN_SESSION_ID、DLT_E_CONTEXT_ALREADY_REG 和 DLT_E_CONTEXT_NOT_YET_REG [SWS_Dlt_00495] [SWS_Dlt_00769]。
  • 时间戳不可用：时间戳被设为 0x00000000 SWS DLT 第30页。
  • 传输错误：负的 Dlt_TxConfirmation 会触发重试，直至达到 DltLogChannelMaxNumOfRetries。若 PduR_DltTransmit 返回 E_NOT_OK，则移除该消息 [SWS_Dlt_00273] SWS DLT 第38页。
  • 控制命令：SetLogLevel 中未知的元组将以 DLT_E_ERROR 响应 SWS DLT 第39页。配置 API 会报告 E_NOT_OK [SWS_Dlt_00252]。
  • 持久性：Dlt_StoreConfiguration 在 R20-11 中已知返回值 E_OK、E_NOT_OK 和 DLT_E_NOT_SUPPORTED [SWS_Dlt_00736]。DLT_E_ERROR 则是直到 R24-11 才新增 SWS DLT 第1页。
  • 开发与运行时错误：
    • 开发错误：DLT_E_PARAM、DLT_E_PARAM_POINTER、DLT_E_INIT_FAILED、DLT_E_REGISTRATION [SWS_Dlt_00727]
    • 运行时错误：DLT_E_SKIPPED_TRANSMISSION、DLT_E_DEPRECATED_PARAMETER、DLT_E_MULTIPLE_REQUESTS [SWS_Dlt_00728]
