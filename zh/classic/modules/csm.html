作为用户与加密驱动程序之间服务层的 CSM

Crypto Service Manager 通过统一的 API 为应用程序和 BSW 模块提供加密服务。这包括哈希、MAC、加解密、AEAD、签名、随机数和密钥管理，例如通过 Csm_Hash [SWS_Csm_00980]、Csm_MacGenerate [SWS_Csm_00982]、Csm_AEADEncrypt [SWS_Csm_01023] 或 Csm_SignatureVerify [SWS_Csm_00996]。CSM 本身不进行运算。它通过 Crypto Interface (CryIf) 将作业转发给 Crypto Driver Object，后者可以是硬件（例如 HSM）或软件。从 CSM 队列经由 CryIf 到 Crypto Driver Object 的路径称为通道（SWS CSM 第29页）。[SWS_Csm_91100] 列出了所需的 CryIf 函数。Det_ReportError 是一个可选接口 [SWS_Csm_91101]。

软件组件通过 RTE 服务端口进行访问，这些端口在“Service Interfaces”一章中进行了形式化规定（SWS CSM 第85页）。BSW 模块则直接使用 C-API。两个示例：

  • DCM 在模式 CRYPTO_OPERATIONMODE_SINGLECALL 下使用 Csm_SignatureVerify 验证 Proof-of-Ownership（SWS DCM 第152页）。
  • IdsM 通过在 CSM 中配置的回调获取异步签名作业的结果（SWS IdsM 第77页）。

作业、队列与通道：服务调用是如何传递的

作业是已配置的加密原语的一个实例 [SWS_Csm_00941]。对于每个作业，同一时刻仅处理一个实例。不同的作业允许并行运行（SWS CSM 第21页）。在运行时，结构 Crypto_JobType 承载该作业。它包含 jobId、jobState、输入/输出结构 jobPrimitiveInputOutput、原语信息以及密钥 ID [SWS_Csm_01013]、[SWS_Csm_01009]、[SWS_Csm_01012]（SWS CSM 第20页）。

作业可以在配置的 CsmQueue 中排队 [SWS_Csm_00940]。队列按作业优先级进行排序 [SWS_Csm_00944]。每个队列严格分配给一个通道，其大小是可配置的（SWS CSM 第29页）。规范明确规定了两种情况（SWS CSM 第21页）：

  • 若作业已处于 ACTIVE 状态，服务调用将直接调用 CryIf_ProcessJob 并传递其返回值。
  • 若作业必须排队且队列已满，则该作业会被拒绝并返回 CRYPTO_E_BUSY。

对于同步作业，规范建议队列大小为 0。但同步和异步作业允许使用相同的通道。当作业处于活动状态时，CSM 会假定调用者希望继续执行，例如使用“update”。合理性检查随后由驱动程序负责（SWS CSM 第29页）。

以 Csm_MainFunction 为周期的同步与异步处理

作业配置决定了数据服务是同步工作还是异步工作。例如对 Csm_Hash 和 Csm_Encrypt 就是如此描述的 [SWS_Csm_00980]、[SWS_Csm_00984]。该选择被编码在 Crypto_ProcessingType 中 [SWS_Csm_01049]。

若配置了异步接口，则会周期性调用 Csm_MainFunction。它检查队列并将作业移交给 CryIf [SWS_Csm_00479]（SWS CSM 第21页）。对于多核系统，以下规则适用：

  • 每个配置的 CsmMainFunction 实例都存在一个 Csm_MainFunction_<shortName> [SWS_Csm_00479]。
  • 每个分区均可提供 Csm_Init [SWS_Csm_00646]。
  • 队列在通过 CsmQueueMainFunctionRef 引用的 MainFunction 中进行处理（SWS CSM 第36页）。

结果通过回调链返回。CryIf 通过 Csm_CallbackNotification(job, result) 报告完成 [SWS_Csm_00970]。若设置了 FINISH 位，CSM 将调用配置的回调 [SWS_Csm_01044]。其签名为 <Csm_ApplicationCallbackNotification>(jobId, result)，名称可配置 [SWS_Csm_00971]。SW-C 通过端口 CallbackNotification_{Job} 接收该通知 [SWS_Csm_00934]、[SWS_Csm_00928]。长度与校验结果通过 Csm_LengthPtr 和 Csm_VerifyResultPtr 异步返回 [SWS_Csm_91045]、[SWS_Csm_91046]。

流式处理、单次调用与作业的生命周期

参数 mode 是由“START”、“UPDATE”和“FINISH”组成的标志字段。这些标志可以组合，从而使单次调用能够执行多项操作 [SWS_Csm_01039]。Crypto_OperationModeType 定义了以下值 [SWS_Csm_01029]：

  • CRYPTO_OPERATIONMODE_START：重置作业。
  • …_UPDATE：计算中间结果。
  • …_STREAMSTART：在单次调用中执行启动与更新。
  • …_FINISH：完成计算。

应用程序可以使用 FINISH 完成计算 [SWS_Csm_01046]。没有 UPDATE 的 START 和 FINISH 会导致 E_NOT_OK [SWS_Csm_01045]。流式处理非常适合超大数据，因为 UPDATE 可以被任意多次调用。单次调用方式在处理小数据时能够节省调用开销（EXP Crypto Services 第12页）。

作业具有两种状态 [SWS_Csm_01028]：

  • CRYPTO_JOBSTATE_IDLE 适用于 Csm_Init 之后以及完成 FINISH 之后。
  • CRYPTO_JOBSTATE_ACTIVE 适用于 START 或 UPDATE 之后。

实际的状态转换由 Crypto Driver 执行（SWS CSM 第22页）。

正在运行的工作上下文可以通过 Csm_SaveContextJob 保存并通过 Csm_RestoreContextJob 恢复 [SWS_Csm_91063]、[SWS_Csm_91064]。密钥元素不属于上下文。在两种情况下，调用会立即返回 E_NOT_OK：当作业处于 IDLE 状态时，或者当它正在驱动程序中处理时（SWS CSM 第35页）。

密钥：元素、有效性、生成与交换

一个密钥由一个或多个密钥元素组成 [SWS_Csm_00954]。它们的 ID 是固定的，例如 CRYPTO_KE_MAC_KEY (1)、CRYPTO_KE_CIPHER_IV (5) 和 CRYPTO_KE_KEYGENERATE_SEED (16) [SWS_Csm_01022]。密钥服务仅提供函数 Csm_<Service>() [SWS_Csm_00950]。以下函数同步工作：

  • Csm_KeyElementSet [SWS_Csm_00957]
  • Csm_KeyElementGet [SWS_Csm_00959]
  • Csm_KeyCopy [SWS_Csm_01034]
  • Csm_KeyElementCopy [SWS_Csm_00969]
  • Csm_KeyElementCopyPartial [SWS_Csm_91025]

密钥状态为 CRYPTO_KEYSTATUS_INVALID 或 CRYPTO_KEYSTATUS_VALID [SWS_Csm_91102]。它由以下函数控制：

  • Csm_KeySetValid [SWS_Csm_00958]
  • Csm_KeySetInvalid [SWS_Csm_91075]

Csm_KeyGenerate 生成密钥材料 [SWS_Csm_00955]。结果存入 CRYPTO_KE_KEYGENERATE_KEY 中，算法来自 CRYPTO_KE_KEYGENERATE_ALGORITHM。应用程序必须预先将种子存储在 CRYPTO_KE_KEYGENERATE_SEED 中，例如来自 Csm_RandomGenerate [SWS_Csm_01543]。种子的熵决定了密钥质量（SWS CSM 第67页）。随机数发生器如何设定种子取决于具体项目。但这必须在首次请求之前完成（SWS CSM 第59页）。Csm_RandomSeed 调用 CryIf_RandomSeed [SWS_Csm_01051]、[SWS_Csm_01052]。Csm_KeyDerive 调用 CryIf_KeyDerive [SWS_Csm_00956]、[SWS_Csm_01018]。

接口形式、数据类型与配置

除 Csm.h 中的 C 函数外，RTE 还会生成与作业相关的端口：

  • CsmJob_{Job} 用于 CRYPTO_USE_PORT 时的同步使用，固定使用 CRYPTO_OPERATIONMODE_SINGLECALL [SWS_Csm_91023]。
  • 在 CRYPTO_USE_PORT_OPTIMIZED 时的异步变体 [SWS_Csm_91062]。
  • 密钥端口 CsmKey_{Key} [SWS_Csm_01042]、[SWS_Csm_01905]。
  • 上下文端口 [SWS_Csm_91105]、[SWS_Csm_91106]。

每个服务都存在一个同步接口（如 CsmHash_{PrimitiveCfg}）和一个异步接口（如 CsmHash）[SWS_Csm_00946]、[SWS_Csm_91051]。缓冲区类型是来自 Rte_Csm_Type.h 的 uint8 数组。其大小由配置的最大长度决定，例如在 Csm_HashDataType_{Crypto}、Csm_HashResultType_{Crypto} 和 Csm_MacGenerateDataType_{Crypto} 处 [SWS_Csm_01920]、[SWS_Csm_00912]、[SWS_Csm_00935]。

Csm_ConfigType 的内容由具体实现决定 [SWS_Csm_01085]。Csm_Init 的 configPtr 必须为空指针（SWS CSM 第48页）。最重要的配置内容：

  • 一个 CsmJob 承载 CsmJobId、CsmJobPriority、CsmJobPrimitiveRef 和 CsmJobInterfaceUsePort（SWS CSM 第166页）。
  • 原语被实现为常量 Crypto_PrimitiveInfoType 结构（SWS CSM 第23页）[SWS_Csm_01011]。
  • 一个 CsmKey 通过 CsmKeyRef 引用一个 CryIf 密钥（SWS CSM 第161页）。
  • CsmQueue 在硬件繁忙时缓冲作业并确定通道（SWS CSM 第164页）。

使用 Crypto_JobRedirectionInfoType 可以将输入和输出重定向到密钥元素 [SWS_Csm_91026]、[SWS_Csm_91024]。

发生错误时的行为

服务将其结果作为 Std_ReturnType 或 Crypto_ResultType 进行报告。除了 E_OK 和 E_NOT_OK 之外，还存在特定代码，如 CRYPTO_E_BUSY、CRYPTO_E_ENTROPY_EXHAUSTED 和 CRYPTO_E_KEY_NOT_VALID [SWS_Csm_91044]、[SWS_Csm_91043]。对于校验服务，E_OK 仅表示请求成功。实际的判定结果位于 verifyPtr 中，表示为 CRYPTO_E_VER_OK 或 CRYPTO_E_VER_NOT_OK [SWS_Csm_01050]、[SWS_Csm_01024]。

若开发错误检测处于激活状态，CSM 会向 DET 报告以下错误 [SWS_Csm_91004]：

  • CSM_E_PARAM_POINTER
  • CSM_E_PARAM_HANDLE
  • CSM_E_UNINIT
  • CSM_E_INIT_FAILED，初始化失败时（SWS CSM 第48页）
  • CSM_E_PROCESSING_MODE

队列溢出属于运行时错误 CSM_E_QUEUE_FULL [SWS_Csm_01089]。

若 Csm_KeyElementSet 失败，则该元素的状态未知。应用程序可使用 Csm_KeyGetStatus 对其进行检查（SWS CSM 第62页）[SWS_Csm_00957]。派生与复制可能会因 CRYPTO_E_KEY_READ_FAIL、…_WRITE_FAIL、…_SIZE_MISMATCH 或 CRYPTO_E_KEY_EMPTY 而失败 [SWS_Csm_00956]、[SWS_Csm_00969]。

Csm_CancelJob 可中止异步或流式作业 [SWS_Csm_00968]。返回值的含义如下：

  • E_OK：作业已被移除。
  • CRYPTO_E_JOB_CANCELED：中止操作仅在下一个合适步骤中进行，并通过负向完成回调进行报告。

后续文档段落补充说明：对于同步作业，Csm_CancelJob 报告 CSM_E_PROCESSING_MODE。CSM 将该作业从队列中移除或调用 CryIf_CancelJob（SWS CSM 第80页）。

  • CRYPTO_KEYSTATUS_INVALID（0x00）：标识密钥无效。此状态通常在通过 Csm_KeyElementSet 修改或分配密钥元素后，密钥尚未通过调用 Csm_KeySetValid 进行验证时出现。
  • CRYPTO_KEYSTATUS_VALID（0x01）：标识密钥有效且可运行，例如在状态已通过 Csm_KeySetValid 成功设置之后。

交互和生命周期

根据 [SWS_Csm_91102]，该类型反映了密钥在配置和更新过程中的生命周期状态。如果密钥元素被重新写入，密钥将保持在状态 CRYPTO_KEYSTATUS_INVALID，直到通过 Csm_KeySetValid 进行了显式验证并将状态转换为 CRYPTO_KEYSTATUS_VALID。因此，调用方必须确保密钥操作仅在成功完成该验证序列之后才访问受影响的密钥。
