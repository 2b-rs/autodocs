连接各软件组件之间以及与基础软件的连接，并协调其执行。

Runtime Environment (RTE) 将 AUTOSAR 软件组件相互连接以及与基础软件模块连接，并通过 Basic Software Scheduler (SchM) 控制 Classic Platform 上的确定性调度规划 (SWS_RTE 第100页)。其生命周期通过从 SchM_Init 和 Rte_Start 到 Rte_Stop 和 SchM_Deinit 的标准化接口进行协调 [SWS_Rte_08060]、[SWS_Rte_03015]。除了客户端-服务器和发送者-接收者模式外，用于校准参数的软件指针方法以及分区边界处的内存保护检查确保了健壮的实时运行 [SWS_Rte_03914]、[SWS_Rte_02752]。

Runtime Environment (RTE) 将 AUTOSAR 软件组件与 ECU 硬件解耦，并与 Basic Software Scheduler (SchM) 共同协调所有应用和基础软件流程的执行 (SWS_RTE 第100页)。受控的启动过程通过 EcuStateManager 分步进行：首先，SchM_Init 初始化调度器结构，接着在调用 BswM_Init 之前执行 SchM_Start，以及执行 SchM_StartTiming 以使能周期性 BSW 事件 [SWS_Rte_08060]、[SWS_Rte_07273]、[SWS_Rte_04548]。随后通过 Rte_Start 启动应用 SW-C，并在关闭时于通过 SchM_Deinit 进行去初始化之前通过 Rte_Stop 停止 [SWS_Rte_03015]、[SWS_Rte_01262]、[SWS_Rte_04551]。

时序图：EcuM、SchM 与 RTE 之间的时间启动和关闭协调。来源：[SWS_Rte_08060]、[SWS_Rte_07273]、[SWS_Rte_04548]、[SWS_Rte_03015]、[SWS_Rte_01262]、[SWS_Rte_04551]、[SWS_Rte_89019]。

通信涵盖了 ECU 内以及 ECU 间的发送者-接收者和客户端-服务器模式 (SWS_RTE 第286页)。无缓冲数据元素通过 initValue 确保一致的初始值，而有缓冲事件则通过 FIFO 队列进行处理 [SWS_Rte_06009]、[SWS_Rte_02521]。在客户端-服务器交互中，两部分的事务句柄将异步请求与相应的响应关联起来 [SWS_Rte_02649]。通过 Rte_Switch 进行的模式切换遵循确定性的十步序列，其中 Distributed Shared Mode Queue 确保多个模式机严格的执行顺序 [SWS_Rte_02631]、[SWS_Rte_02665]、[SWS_Rte_91102]。

上下文图：Single Pointered 和 Double Pointered 校准方法的寻址与间接引用结构。来源：[SWS_Rte_03913]、[SWS_Rte_03914]、[SWS_Rte_03947]、AUTOSAR_SWS_RTE 第180页、AUTOSAR_SWS_RTE 第181页。

对于在线校准，RTE 根据 Single Pointered 或 Double Pointered 原理生成指针结构，从而无需硬件仿真即可在 RAM 中修改参数组 [SWS_Rte_03913]、[SWS_Rte_03914]。异常的范围越界或超时通过 Std_ReturnType 报告给调用组件，而分区边界处的内存保护检查可防止未经授权的篡改 [SWS_Rte_01034]、[SWS_Rte_03845]、[SWS_Rte_02752]。

Classic Platform 中 RTE 的角色和系统边界

Runtime Environment (RTE) 构成了 AUTOSAR Classic 架构的功能骨干，它将软件组件 (SW-C) 与底层计算硬件以及底层基础软件模块 (BSW) 完全解耦 (SWS_RTE 第100页)。RTE 生成器为每个 ECU 生成量身定制的接口，该接口通过统一的 API 调用（如 Rte_Read、Rte_Write 或 Rte_Call）解析所有通信关系——包括微控制器上的本地通信 (Intra-ECU) 以及跨通信总线的网络范围通信 (Inter-ECU) [SWS_Rte_01091]、[SWS_Rte_01102]。通过提供生成的 BswModuleDescription 元素以及相应的 BswInternalBehavior 描述，RTE 作为不可或缺的组成部分集成到 AUTOSAR 的配置和打包模式中 [SWS_Rte_05165]、[SWS_Rte_05166]。

同一软件组件的多实例化由 RTE 专门通过共享代码的可重入 Runnable Entities 来解决；明确不支持代码复制 [SWS_Rte_03015]、[SWS_Rte_02002]。在 C 代码中为每个实例传递唯一的实例标识符，或通过 Component Data Structure（CDS）进行寻址，从而确保在共享 Task 上下文中并行执行各实例时不会发生相互数据破坏（SWS_RTE 第126页、SWS_RTE 第804页）。作为应用 SWC 的补充，RTE 通过 Basic Software Scheduler（SchM）涵盖所有 BSW 模块的周期性调度与模式管理 [SWS_Rte_08060]、[SWS_Rte_07273]。

SchM 与 RTE 的生命周期及启动协调

系统启动要求 BSW 调度器（SchM）与面向应用的 RTE 之间遵循严格规定的顺序（SWS_RTE 第459页）。在 SchM 初始化之前，出于系统安全考虑，仅可使用锁定函数 SchM_Enter 和 SchM_Exit。EcuStateManager 首先调用函数 SchM_Init，从而初始化内部数据结构与模式机，并启动带有 Background-Events 的 BswSchedulableEntities [SWS_Rte_08060]、[SWS_Rte_07584]。在调用 BswM_Init 之前，必须先调用 SchM_Start [SWS_Rte_07273]、[SWS_Rte_04548]。随后通过 SchM_StartTiming 使能周期性 BSW 流程（BswTimingEvents）的激活 [SWS_Rte_04548]、[SWS_Rte_04551]、[SWS_Rte_07574]。

时序图：EcuM、SchM 与 RTE 之间的时间启动和关闭协调。来源：[SWS_Rte_08060]、[SWS_Rte_07273]、[SWS_Rte_04548]、[SWS_Rte_03015]、[SWS_Rte_01262]、[SWS_Rte_04551]、[SWS_Rte_89019]。

只有在所需的基础服务运行后，EcuStateManager 才会通过 Rte_Start 激活应用 SWC 的执行，并为未绑定的 On-Entry-Runnables 启动模式转换 [SWS_Rte_03015]、[SWS_Rte_06766]。若在 Rte_Start 处的资源分配失败，该函数将返回错误码 RTE_E_LIMIT [SWS_Rte_01262]。在 ECU 关闭时，Rte_Stop 首先终止应用执行，并从此时起忽略传入的请求和数据 [SWS_Rte_02538]、[SWS_Rte_02535]、[SWS_Rte_02536]。只有在 Rte_Stop 完全终止后，才允许调用 SchM_Deinit，后者释放调度器的所有系统资源并通过 Rte_Rips_SchM_Deinit 触发特定于插件的清理 [SWS_Rte_04551]、[SWS_Rte_07277]、[SWS_Rte_89019]。

通信模式：Sender-Receiver 与 Client-Server

在 Sender-Receiver 范式中，RTE 在数据语义与事件语义之间有着根本区别（SWS_RTE 第286页）。在数据语义（swImplPolicy != queued）下，缓冲区中始终保留最新写入的值，并通过 Rte_Read 显式消费或通过 Rte_IRead 隐式消费 [SWS_Rte_01091]、[SWS_Rte_06000]。在隐式读取时，RTE 保证在 Runnable Entity 的整个执行期间数据值保持一致副本 [SWS_Rte_06001]。在首次接收之前，RTE 提供配置的 initValue，从而不会处理未初始化的内存状态 [SWS_Rte_06009]、[SWS_Rte_06010]。

时序图：具有初始值保护的非缓冲信号的 Inter-ECU Sender-Receiver 通信。来源：[SWS_Rte_01091]、[SWS_Rte_06009]、[SWS_Rte_01289]、AUTOSAR_SWS_RTE 第148页。

与此相反，事件语义（swImplPolicy = queued）通过 FIFO 缓冲区结构无损处理数据序列，该缓冲区通过 Rte_Send 填充并通过 Rte_Receive 递减 [SWS_Rte_01072]、[SWS_Rte_01092]、[SWS_Rte_02521]。如果达到通过 RteQueuedReceiverQueueLength 设定的缓冲区上限，RTE 将丢弃新到达的数据并设置相应的错误标志 [SWS_Rte_08940]、[SWS_Rte_02523]。对于大数据量，RTE 使用专门的传输路径，如 LdCom 或带有信号缓冲区锁定的 Large-Data-COM [SWS_Rte_01376]、[SWS_Rte_01379]。

Client-Server 通信支持同步调用（Rte_Call）以及通过 Rte_Result 进行独立结果查询的异步交互 [SWS_Rte_01102]、[SWS_Rte_01111]。在服务器端，若未配置直接调用，RTE 会将传入的请求缓存在 FIFO 队列中，而在客户端，响应则暂存在长度为 1 的缓冲区中 [SWS_Rte_02527]、[SWS_Rte_02528]。在跨分区或跨 ECU 调用时，由 Client Identifier 和 Sequence Counter 组成的两部分 Transaction Handle 可确保响应数据包与原始请求的精确匹配 [SWS_Rte_02649]、[SWS_Rte_08711]。

模式管理、状态转换与 Distributed Shared Mode Queues

模式管理允许通过专用模式机（ModeMachineInstances）协调切换运行状态，这些模式机通过 Rte_Switch 进行控制 [SWS_Rte_02631]。每个状态转换都会经历由十个独立步骤组成的确定性序列，其中包括激活模式锁、受控等待受影响的 Runnables 终止，以及顺序执行 OnExit、OnTransition 和 OnEntry 实体等 [SWS_Rte_02665]。只有在所有阶段完全结束后，才会触发确认事件 ModeSwitchedAckEvent，其状态可通过 Rte_SwitchAck 查询 [SWS_Rte_02679]、[SWS_Rte_02725]、[SWS_Rte_02758]。

活动图：ModeMachineInstance 内部模式转换的确定性十阶段流程。来源：[SWS_Rte_02665]、[SWS_Rte_02679]、EXP_ModeManagementGuide 第16页。

为了在存在多个模式机时强制执行严格的模式切换顺序——例如点火状态与发动机状态之间——RTE 提供了 Distributed Shared Mode Queues（DSMQ）（SWS_RTE 第442页）。此类队列中入队与出队操作的状态通过类型 Rte_DsmqStatusType 来指示 [SWS_Rte_91102]。对于软件簇转换，Rte_Rips_SwitchNotificationStatusType 映射了相应的入队和出队状态 [SWS_Rte_91113]。解释：对于 BSW 调度器，可能倾向于选择在 Rte_Start 之前配置同步点，以便在使能周期性 Task 之前建立确定性的系统状态 [SWS_Rte_06767]。

标定、数据仿真与内存拓扑

标定参数由 RTE 集中定位在内存中，因为只有 RTE 生成器了解 ECU 上所有组件和分区的总体占用情况 [SWS_Rte_03961]。为了在无需专用仿真硬件的情况下实现在线标定，RTE 支持诸如 Single Pointered Method 和 Double Pointered Method 等软件仿真方法（SWS_RTE 第236页、SWS_RTE 第237页）。在 Single Pointered Method 中，RAM 中存在一个由指向 ParameterElementGroups 的 void* 条目组成的指针表（<RteParameterRefTab>）[SWS_Rte_03913]、[SWS_Rte_03947]。

上下文图：Single Pointered 和 Double Pointered 校准方法的寻址与间接引用结构。来源：[SWS_Rte_03913]、[SWS_Rte_03914]、[SWS_Rte_03947]、AUTOSAR_SWS_RTE 第180页、AUTOSAR_SWS_RTE 第181页。

相比之下，Double Pointered Method 采用二级间接寻址：存放于 ROM/Flash 中的参考表指向参数组，而 RAM 中可修改的基指针（Base reference）初始指向该 Flash 表，并在标定时可重定向至修改后的 RAM 副本 [SWS_Rte_03914]。在此方法中，ParameterDataPrototypes 根据其 swAddrMethod 被划分为不同的组 [SWS_Rte_03908]。RTE 生成器在容器 McSupportData 中通过 McSwEmulationMethodSupport 导出所有结构与指针信息，以便为标定工具（如 INCA 或 CANape）提供对 A2L 寻址的精确访问 [SWS_Rte_05118]、[SWS_Rte_05137]、[SWS_Rte_05138]。解释：对于高度集成的安全 ECU，可能会首选 Double Pointered Method，因为指针表本身主要保留在受保护的 Flash 中，仅在主动标定时才占用 RAM 缓冲区。

分区、内存保护与 Inter-OS-Application 通信

在多核及具有内存保护的架构中，RTE 通过 Inter-OS-Application Communication（IOC）跨分区边界（OS-Applications）连接软件组件（SWS_RTE 第372页）。在此过程中，RTE 将内部信号缓冲区替换为接近硬件的 IOC 缓冲区及生成的保护函数。对于临界区（ExclusiveAreas）的访问，集成商选择特定机制的配置参数（RteExclusiveAreaImplMechanism），范围涵盖从中断锁到用于跨核访问的 OS 自旋锁（SWS_RTE 第203页）。

若未经测试或不可信的分区（Non-Trusted）向可信的 BSW 或 SWC 分区传递指针参数，RTE 将强制执行地址和内存区域检查 [SWS_Rte_02752]、[SWS_Rte_02753]。仅当所引用的整个内存对象均属于调用分区时，才会转发指针，从而有效防止保护区违规以及对外部内存区域的非法覆盖（SWS_RTE 第378页）。

发生错误时的行为

RTE 的错误处理严格区分基础设施错误与应用错误（SWS_RTE 第579页）。所有错误状态均通过返回类型 Std_ReturnType 直接向调用者指示 [SWS_Rte_01034]。直接基础设施错误包括 RTE_E_TIMEOUT（129）、RTE_E_LIMIT（130）、RTE_E_NO_DATA（131）、RTE_E_UNCONNECTED（134）、RTE_E_IN_EXCLUSIVE_AREA（135）以及 RTE_E_SEG_FAULT（136）等（SWS_RTE 第586页）。

时序图：通过 Rte_Read 检测与传播值域错误。来源：[SWS_Rte_01091]、[SWS_Rte_01371]、[SWS_Rte_03845]、AUTOSAR_CP_SWS_RTE 第409页。

当使能数据校验（DataSemantics range check）时，RTE 会根据定义的值域检查传入的信号值 [SWS_Rte_01371]。若接收到的值超出边界，读取 API 将返回 RTE_E_OUT_OF_RANGE [SWS_Rte_03845]、[SWS_Rte_03846]。对于具有 Invalidation-Policy 的信号，RTE 在 replace 处将该值替换为 initValue，或者在 keep 处保留先前的值并设置错误事件 [SWS_Rte_05030]、[SWS_Rte_05049]。在通过 aliveTimeout 进行超时监控时，RTE 通过 Rte_COMCbkRxTOut 记录缺失，并将 RTE_E_TIMEOUT 传播给等待的 SWC [SWS_Rte_08061]、[SWS_Rte_03763]。

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 7e79d12edbc4 Provenance

函数 Rte_Start 分配并初始化 RTE 所使用的系统和通信资源 [SWS_Rte_03015]。该 API 始终生成 [SWS_Rte_01309]，具有签名 Std_ReturnType Rte_Start (void) [SWS_Rte_02569]，且必须在有限执行时间内返回而不得陷入死循环 [SWS_Rte_02585]。

在 RTE 所需的所有基础软件模块初始化完成之后，该函数在每个 Core 上只能由 EcuStateManager 从受信任的 OS 上下文中精确调用一次 [SWS_Rte_CONSTR_09035]。该调用在每个 Core 上独立执行 [SWS_Rte_07615]，并为分配给该 Core 的所有分区执行分区特定的启动活动 [SWS_Rte_07616]。

在执行流程中，RTE 根据配置的策略初始化为 RAM 块分配的变量 [SWS_Rte_07632]。在变量初始化之后、但在 Runnable 执行之前，RTE 调用所有相关 RTE Implementation Plug-In 的初始化函数 Rte_Rips_Rte_Start [SWS_Rte_80052]。随后，RTE 单次激活由 InitEvent 触发的所有 Runnable [SWS_Rte_06761]，并启动向初始模式的切换 [SWS_Rte_06766]。如果 API Rte_StartTiming 不存在，Rte_Start 还会启动由 TimingEvent [SWS_Rte_07575] 或 BackgroundEvent [SWS_Rte_07178] 触发的 Runnable 的激活。

对于错误处理，如果在启用 RteDevErrorDetectUninit 的情况下在 SchM_Init 之前调用了 Rte_Start，则 RTE 或 SchM 会报告错误 RTE_E_UNINIT (0x07) [SWS_Rte_07683]。在执行 Rte_Start 之前不得调用 RTE 的运行时 API，否则同样会导致 RTE_E_UNINIT [SWS_Rte_07682]；而 Rte_SetMirror 则允许在 Rte_Start 之前调用 [SWS_Rte_07319]。
