Classic OS 的角色及其在 BSW 堆栈中的相邻模块

os 模块是 Classic Platform 的实时内核。它管理 Counter、Schedule Table、OS-Application、内核和 Spinlock，并通过 Os.h 提供其服务，例如 StopScheduleTable [SWS_Os_00006] 或 GetSpinlock [SWS_Os_00686]。对于由 OS 直接使用且不由 GPT 驱动程序管理的定时器，OS 会自行进行初始化和配置（SWS OS 第39页）。IOC 也是操作系统的一部分。除 RTE 内部通信和跨 ECU 通信之外，它构成了第三种通信方式（SWS OS 第119页）。

其他 BSW 模块只能受限地使用 OS。通用 BSW 规范在表格中规定了哪些模块组可以调用哪些 OS 服务：RTE/BSW-Scheduler、BswM、EcuM、MCAL、StbM 以及其余模块（SWS BSW General 第48页）。

  • EcuM 使用 StartCore [SWS_Os_00676] 启动内核，并使用 ShutdownAllCores [SWS_Os_00713] 将其关闭（SWS EcuM 第82页）。
  • StbM 使用针对 Schedule Table 的同步服务（SWS StbM 第152页）。
  • Complex Driver 应仅限于 GetCounterValue 和 GetElapsedValue（CDD-Leitfaden 第21页）。

Counter 与 Schedule Table：从 Tick 到 Expiry Point

针对 Counter 提供了三个服务：

  • GetCounterValue [SWS_Os_00383] 返回 Counter 的当前 Tick。
  • GetElapsedValue [SWS_Os_00392] 返回与先前读取值之间的差值。在此过程中，硬件定时器经过调整，使得最小值始终为零，且后续读取的值递增直至溢出（SWS OS 第39页）。
  • IncrementCounter [SWS_Os_00399] 仅递增软件 Counter。对于硬件 Counter，它返回 E_OS_ID。如果由此触发的 Alarm 动作失败，它会调用 Error-Hook，但自身仍返回 E_OK（SWS OS 第190页）。

如果配置了 OsSecondsPerTick，OS 还会额外提供服务接口 OsService_{Counter}。它使用类型为 TimeInMicrosecondsType [SWS_Os_00560] [SWS_Os_00794] 的值。

应用程序负责 Schedule Table 的启动和停止（SWS OS 第46页）。存在两种启动变体：

  • 一旦 Counter 达到值 Start + InitialOffset，StartScheduleTableAbs [SWS_Os_00358] 便会处理 Initial Expiry Point。
  • StartScheduleTableRel [SWS_Os_00347] 进行相对计算：Now + Offset + InitialOffset。在 EXTENDED 状态下，它会以 E_OS_VALUE 拒绝为 0 或大于 OsCounterMaxAllowedValue − InitialOffset 的偏移量。对于隐式同步的表，它返回 E_OS_ID（SWS OS 第179页）。

如果该表已经启动，两种变体都会报告 E_OS_STATE [SWS_Os_00358]。

其他控制服务：

  • StopScheduleTable [SWS_Os_00006] 立即中止处理。稍后的重新启动将重新从表头开始（SWS OS 第46页）。
  • NextScheduleTable [SWS_Os_00191] 在当前运行的表结束后切换到后续表。在此之前，后续表报告 SCHEDULETABLE_NEXT。如果由另一个 Counter 驱动目标表，该服务将返回 E_OS_ID（SWS OS 第184页）。
  • GetScheduleTableStatus [SWS_Os_00227] 通过引用 [SWS_Os_00785] 将状态作为 ScheduleTableStatusType [SWS_Os_00784] 返回（SWS OS 第189页）。

状态图：Schedule Table 的生命周期，包含 ScheduleTableStatusType 的全部五个值，以及显式同步的状态。来源：SWS OS 第43页、SWS OS 第49页、[SWS_Os_00784]

与全局时基的显式同步

存在两种同步方式：

  • 隐式：同步计数器直接驱动表。仅出现状态 STOPPED、NEXT 和 RUNNING_AND_SYNCHRONOUS（SWS OS 第48页）。
  • 显式（OsScheduleTblSyncStrategy = EXPLICIT）：由另一个 OS Counter 驱动表。只有当存在同步值时，StartScheduleTableSynchron [SWS_Os_00201] 才会启动它。随后在驱动 Counter 达到 (Duration − Value) + InitialOffset 个 Tick 后处理 Initial Expiry Point（SWS OS 第49页）。对于未采用策略 EXPLICIT 的表，该服务会以 E_OS_ID 拒绝（SWS OS 第185页）。

SyncScheduleTable [SWS_Os_00199] 传递同步计数器的当前值。由于表持续时间与该计数器的模数相符，OS 能够确定漂移（SWS OS 第52页）。校正操作在可调整的 Expiry Point 处进行，且在所配置的缩短和延长限制范围内（SWS OS 第57页）。

SetScheduletableAsync [SWS_Os_00422] 终止同步，同时继续处理 Expiry Point。后续 Release 将该服务拼写为 SetScheduleTableAsync（SWS OS 第188页）。

典型的使用者是 StbM。在其 Main Function 中，它会查询表状态。它仅在状态为 WAITING、RUNNING 或 RUNNING_AND_SYNCHRONOUS 时调用 SyncScheduleTable（SWS StbM 第220页）。安全文档将这些服务归入安全要求“与全局时间同步”（Safety Concept Status Report 第49页，Functional Safety Measures 第66页）。

时序图：StbM 周期性地同步 Schedule Table，并且仅在其状态允许时才执行同步。来源：SWS StbM 第220页、[SWS_Os_00227]、[SWS_Os_00199]

OS-Application：分配、访问权限和 Trusted Function

OS-Application 将 Trusted Function、Task、ISR、Alarm、Schedule Table、Counter 和 Hook 组合为一个可配置的单元。它要么是 trusted，要么是 non-trusted（SWS OS 第61页）。用于标识的服务有两个：

  • GetApplicationID [SWS_Os_00016] 返回调用方配置的 OS-Application。
  • GetCurrentApplicationID [SWS_Os_00797] 返回调用方当前正在其中执行的 OS-Application。在 CallTrustedFunction 之外，这两个值一致。在 1 类 ISR 中，该值是未定义的 [SWS_Os_00798]。如果没有正在运行的 OS-Application，则其值为 INVALID_OSAPPLICATION [SWS_Os_00799]。

类型为 ApplicationType [SWS_Os_00772] 的 ID 从零开始且连续无间断 [SWS_Os_00826]。

CheckObjectOwnership [SWS_Os_00017] 确定某个对象属于哪个 OS-Application。CheckObjectAccess [SWS_Os_00256] 检查 OS-Application 是否被允许使用 Task、Resource、Counter、Alarm 或 Schedule Table 的 ID。当参数无效时，它返回 NO_ACCESS（SWS OS 第177页）。如果调用方向系统服务传递了未配置访问权限的对象 ID，则该服务将以 E_OS_ACCESS 结束。检查服务本身不受此规则限制（SWS OS 第73页）。

CheckTaskMemoryAccess [SWS_Os_00513] 和 CheckISRMemoryAccess [SWS_Os_00512] 用于查询内存权限。仅当针对整个请求区域都具备权限时，该权限才有效（SWS OS 第174页）。类型为 AccessType [SWS_Os_00777] 的结果使用诸如 OSMEMORY_IS_WRITEABLE 的宏进行评估（SWS OS 第160页）。trusted OS-Application 也可以在写限制模式下运行 [SWS_Os_00795]。

CallTrustedFunction [SWS_Os_00097] 调用通过 TrustedFunctionIndexType [SWS_Os_00775] 寻址的函数。该函数以提供该函数的 OS-Application 的保护设置运行。参数作为结构体通过 TrustedFunctionParameterRefType [SWS_Os_00776] 传递（SWS OS 第172页）。如果该索引未配置，OS 将调用带有 E_OS_SERVICEID 的 ErrorHook（SWS OS 第85页）。在 R20-11 中，根据被调用函数的行为，该服务可以是同步的也可以是异步的 [SWS_Os_00097]。BSW Distribution Guide 使用它在不同分区中的 BSW 模块之间传递调用（BSW Distribution Guide 第66页）。

时序图：对 Trusted Function 的调用经由 Stub 和 OS 检查，直至在提供该函数的 OS-Application 中执行。来源：SWS OS 第185页、SWS OS 第396页、[SWS_Os_00097]

Service Protection 下的外设访问和中断源

对于外设地址的访问，存在三个服务族。它们都寻址类型为 AreaIdType [SWS_Os_91000] 的区域：

  • ReadPeripheral8/16/32 [SWS_Os_91013] [SWS_Os_91015] [SWS_Os_91014]
  • WritePeripheral8/16/32 [SWS_Os_91010] [SWS_Os_91012] [SWS_Os_91011]
  • ModifyPeripheral8/16/32 [SWS_Os_91016] [SWS_Os_91018] [SWS_Os_91017]。Modify 服务计算 *Address = ((*Address & Clearmask) | Setmask)（SWS OS 第175页）。

在 EXTENDED 状态下，这些服务报告 E_OS_ID、E_OS_VALUE（地址超出范围）或 E_OS_CALLEVEL。如果调用 Task 或 ISR 没有访问权限，则会产生 E_OS_ACCESS（SWS OS 第195页）。

对于每个 2 类 ISR，OS 提供三个服务 [SWS_Os_00808]：DisableInterruptSource [SWS_Os_91019]、EnableInterruptSource [SWS_Os_91020] 和 ClearPendingInterrupt [SWS_Os_91021]。此时适用以下规则：

  • 若再次禁用已禁用的源，或再次使能已使能的源，在 EXTENDED 状态下将获得 E_OS_NOFUNC [SWS_Os_00809]。
  • 检测到的错误会被返回并报告给 ErrorHook [SWS_Os_00810]。
  • ClearPendingInterrupt 仅清除中断控制器中的 Pending 标志 [SWS_Os_00813] [SWS_Os_00814]。
  • 如果 OS-Application 为不属于它的 ISR 调用这些服务，它将获得 E_OS_ACCESS（SWS OS 第177页）。

注意，存在矛盾：[SWS_Os_00811] 要求在使能时清除 Pending 标志。而 API 定义 [SWS_Os_91020] 恰恰通过参数 ClearPending 使该操作可选。

多核运行：内核启动、Spinlock、IOC 和协调关闭

StartCore [SWS_Os_00676] 在 AUTOSAR OS 控制下启动另一个内核。在 StartOS 之后，调用将返回 E_OS_ACCESS。随后必须在以此方式启动的每个内核上调用 StartOS（SWS OS 第166页）。这些详细规则来自后续的规范版本。解读：它们大概也适用于 R20-11，因为 R20-11 定义中给出了相同的返回值 [SWS_Os_00676]。

其他内核服务：

  • StartNonAutosarCore [SWS_Os_00682] 启动 AUTOSAR OS 之外的内核。
  • GetCoreID [SWS_Os_00674] 返回类型为 CoreIdType [SWS_Os_00790] 的逻辑 ID。值范围从零开始且连续无间断 [SWS_Os_00825]。
  • 在 R20-11 中，GetNumberOfActivatedCores [SWS_Os_00672] 用于统计通过 StartCore 激活的内核数量。后续 Release 则改为表述为运行 AUTOSAR OS 的内核（SWS OS 第196页）。

Spinlock 用于跨越内核边界保护共享数据：

  • GetSpinlock [SWS_Os_00686] 进行忙等待，调用方不会被抢占（SWS OS 第199页）。
  • 当另一个内核上的 Task 持有该锁时，TryToGetSpinlock [SWS_Os_00703] 会立即返回，并通过 TryToGetSpinlockType [SWS_Os_00792] 报告结果（SWS OS 第203页）。
  • ReleaseSpinlock [SWS_Os_00695] 释放锁。
  • SpinlockIdType 的值 0 代表 INVALID_SPINLOCK [SWS_Os_00791]。

在 EXTENDED 状态下，OS 能识别两种死锁类型：同一内核上的抢占（E_OS_INTERFERENCE_DEADLOCK）和错误的嵌套（E_OS_NESTING_DEADLOCK）。通过 OsSpinlockLockMethod，OS 可以自动保护锁免受抢占（SWS OS 第101页）。

跨内核边界的 ActivateTask 表现为同步行为。异步变体 ActivateTaskAsyn [SWS_Os_91022] [SWS_Os_00816] 和 SetEventAsyn [SWS_Os_91023] [SWS_Os_00817] 仅通过全局 ErrorHook 报告错误（SWS OS 第103页）。它们仅在具有 OS-Application 的系统中可用 [SWS_Os_00818] [SWS_Os_00819]。

IOC 通过生成的函数传输数据（SWS OS 第218页）：

  • 用于无缓冲“data”语义的 IocWrite [SWS_Os_91003] 和 IocRead [SWS_Os_91005]。
  • 用于有缓冲“event”语义的 IocSend [SWS_Os_00718] 和 IocReceive [SWS_Os_00738]。
  • 组变体 [SWS_Os_00728] [SWS_Os_91004] [SWS_Os_00746] [SWS_Os_91006]、IocEmptyQueue [SWS_Os_00754] 以及可选的接收方回调 [SWS_Os_00757]。

作为 DRAFT，R20-11 还包含 IocInit [SWS_Os_91026] [SWS_Os_00835]，它在默认模式下调用 StartOS [SWS_Os_00830]。同样处于 DRAFT 状态的还有用于 OS 和 IOC 代码的独立生成器模式 [SWS_Os_00831] [SWS_Os_00833] [SWS_Os_00834]。

ControlIdle [SWS_Os_00769] 针对每个内核指定在空闲时间执行的操作。默认值为 IDLE_NO_HALT [SWS_Os_00793]。无效的内核或模式指定返回 E_OS_ID [SWS_Os_00771]，有效指定返回 E_OK [SWS_Os_00770]。

ShutdownAllCores 在所有内核上同步关闭 OS 且永不返回。来自 non-trusted 代码的调用将被忽略（SWS OS 第204页）。首先运行应用程序特定的 Shutdown-Hook [SWS_Os_00541]，在所有内核完成同步后，再运行全局 ShutdownHook（SWS OS 第98页）。

时序图：EcuM 在 StartOS 之前启动所有内核；ShutdownAllCores 将关闭操作分发到其余内核，并在执行 ShutdownHook 之前进行同步。来源：SWS EcuM 第82页、SWS EcuM 第91页、SWS OS 第98页、[SWS_Os_00713]

发生错误时的行为

许多检查仅在 EXTENDED 状态下存在，例如针对无效 ID 返回 E_OS_ID（SWS OS 第182页）。在此模式下，OS 还会检查指针参数是否为 NULL_PTR，并返回 E_OS_ILLEGAL_ADDRESS（SWS OS 第38页）。OS 特有的错误码（如 E_OS_PROTECTION_MEMORY、E_OS_STACKFAULT 或 E_OS_CORE）定义在 [SWS_Os_91025] 中。如果 Task 或 2 类 ISR 引发错误，则会调用其 OS-Application 的 ErrorHook，ErrorHook_<App> [SWS_Os_00540]。

诸如内存违规或时间违规等严重错误会触发 ProtectionHook [SWS_Os_00538]。其类型为 ProtectionReturnType [SWS_Os_00787] 的返回值决定了相应的响应行为。OS 随后会终止 Task 或 ISR、终止 OS-Application（附带或不附带重启），或者关闭系统（SWS OS 第187页）。

活动图：ProtectionHook 的返回值决定了 OS 对保护违规的响应行为。来源：SWS OS 第187页、EXP ALEH 第69页、[SWS_Os_00787]

如果 OS 终止某个 OS-Application，它将终止其运行中、就绪和等待状态的 Task 及 ISR。此外，它还会禁用其中断，并停止其 Alarm 和 Schedule Table（SWS OS 第62页）。

TerminateApplication [SWS_Os_00258] 会终止自身的 OS-Application。外部的 OS-Application 仅允许 trusted 调用者终止。在 R20-11 中，选项 RestartType [SWS_Os_00788] 包含值 RESTART 和 NO_RESTART。后续版本仅保留 OS_OSAPPLICATION_RESTART 并忽略该参数（SWS OS 第158页、SWS OS 第194页）。

符合 ApplicationStateType [SWS_Os_00773] 的 OS-Application 状态由 GetApplicationState [SWS_Os_00499] 提供。它通过 AllowAccess [SWS_Os_00501] 从 APPLICATION_RESTARTING 返回到 APPLICATION_ACCESSIBLE。

应用级错误处理指南中描述了该重启过程。OS 会激活 OSRestartTask。后者通过 CallTrustedFunction 触发其他分区中的清理工作（EXP ALEH 第69页、EXP ALEH 第76页）。

对于异步服务，错误不会传递给调用者。如果调用者已经终止，则 Error-Hook 调用也会被取消（SWS OS 第203页）。
