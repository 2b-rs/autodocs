CanIf 与控制器硬件之间的 CAN 驱动程序角色

CAN 驱动（Can）是 Classic CAN 栈最底层的硬件相关层。对 CAN 硬件的所有访问均封装在该模块的函数中。驱动自身不记录控制器的状态转换（SWS CANDriver 第30页）。向上它仅与 CAN Interface 通信。驱动调用的回调均在 CanIf 中实现且不可配置：CanIf_ControllerBusOff、CanIf_ControllerModeIndication、CanIf_RxIndication 和 CanIf_TxConfirmation。此外，驱动还需要 Det_ReportRuntimeError 以及 OS 服务 GetCounterValue（[SWS_Can_00234]、SWS CANDriver 第73页）。

CanIf 仅通过抽象句柄访问硬件。用于发送的硬件对象句柄（HTH）和用于接收的硬件对象句柄（HRH）指向邮箱结构，其布局仅驱动程序知晓（SWS CANInterface 第29页）。这些句柄的数据类型为 Can_HwHandleType。它基于 uint8；当硬件对象超过 255 个时，将使用带有 uint16 的扩展值范围（[SWS_Can_00429]、SWS CANDriver 第54页）。CanSM 的工作模式请求也仅通过 CanIf 到达驱动程序（SWS CANInterface 第20页）。

上下文图：驱动程序位于 CanIf、EcuM、BSW Scheduler、DET、Os 与控制器硬件之间；CanSM 仅通过 CanIf 间接访问它。来源：[SWS_Can_00234]、SWS CANInterface 第20页、SWS CANInterface 第156页、SWS CANDriver 第63页

启动与生命周期：驱动程序状态与控制器状态

驱动程序本身只有两种状态。在上电或复位后，它处于 CAN_UNINIT 状态。Can_Init 根据其配置初始化硬件单元的所有控制器，然后切换到 CAN_READY（[SWS_Can_00223]、SWS CANDriver 第29页）。ECU State Manager 在启动阶段调用 Can_Init，之后才会使用任何其他驱动程序函数（[SWS_Can_91012]、SWS CANDriver 第41页）。根据实现说明，这在运行时最多发生一次。涉及硬件单元所有控制器的寄存器设置仅在 Can_Init 中可行（SWS CANDriver 第29页）。传入的结构 Can_ConfigType 是特定于硬件的。它包含全局设置以及指向控制器配置的指针（[SWS_Can_00413]）。

针对每个控制器，规范简化区分了四种状态：UNINIT、STOPPED、STARTED 和 SLEEP。它们被映射为具有值 CAN_CS_UNINIT 到 CAN_CS_SLEEP 的 Can_ControllerStateType（[SWS_Can_91013]、SWS CANDriver 第30页）。初始化后，CanIf 期望控制器保持在 STOPPED。在该状态下，它既不能发送也不能接收（SWS CANInterface 第39页）。每个控制器使用 Can_SetControllerMode(CAN_CS_STARTED) 单独启动（SWS CANDriver 第29页）。在此过程中，它将使用先前使用的相同配置重新初始化（SWS CANDriver 第59页）。

Can_SetControllerMode 采用异步工作方式且不可重入。E_OK 仅表示请求已被接受；E_NOT_OK 表示开发错误（[SWS_Can_00230]）。驱动程序通过 CanIf_ControllerModeIndication 报告已完成的状态切换（[SWS_Can_00234]）。在没有中断的情况下，Can_MainFunction_Mode 轮询状态寄存器。文档出处的需求文本在此处误写为 Can_MainFunction_Wakeup（[SWS_Can_00368]、SWS CANDriver 第84页）。当前模式由 Can_GetControllerMode 提供（[SWS_Can_91014]、SWS CANDriver 第65页）。逆向操作由 Can_DeInit 负责。它将驱动程序设置为 CAN_UNINIT，并将所有处于 STOPPED 或 SLEEP 的控制器设置为 UNINIT，从而为重新配置做好准备（[SWS_Can_91002]、[SWS_Can_91010]、SWS CANDriver 第37页）。

状态图：驱动程序状态（CAN_UNINIT/CAN_READY）和四个控制器状态由 Can_Init、Can_SetControllerMode 和 Can_DeInit 控制。SLEEP 和 Bus-off 转换边标记为解释。来源：SWS CANDriver 第29页、SWS CANDriver 第30页、[SWS_Can_91013]、[SWS_Can_91010]、SWS CANInterface 第39页

发送路径：从 Can_Write 到发送确认

CanIf 通过 Can_Write(Hth, PduInfo) 传递每个 L-PDU。该函数是同步且线程安全可重入的。通过 HTH 同时确定了控制器，因为 HTH 编号在硬件单元内是唯一的（[SWS_Can_00233]）。结构体 Can_PduType 汇总了 swPduHandle、length、id 以及数据指针 sdu（[SWS_Can_00415]、SWS CANDriver 第53页）。CanIf 将 swPduHandle 设置为它稍后在 CanIf_TxConfirmation 中预期的 CanTxPduId。此外，CanIf 将 CanId 的最高两个有效位设置为 Extended 标志和 FD 标志（SWS CANInterface 第80页）。

若没有空闲的硬件发送对象，驱动程序将返回重载的返回值 CAN_BUSY（[SWS_Can_00039]、SWS CANDriver 第54页）。如果启用了发送缓冲，且其自身缓冲区大小大于零，CanIf 随后会将该 L-PDU 存入自己的缓冲区中（SWS CANInterface 第43页）。在每次确认后，CanIf 会通过 Can_Write 重新提交优先级最高的等待中 L-PDU（SWS CANInterface 第45页、SWS CANInterface 第157页）。重要的是：驱动程序在 Can_Write 之前不会检查控制器状态（SWS CANDriver 第30页）。因此，CanIf 会阻止针对处于 CAN_CS_STOPPED 状态的控制器的发送请求（SWS CANInterface 第53页）。

确认要么来自发送中断，要么在轮询时周期性地来自 BSW Scheduler 调用的 Can_MainFunction_Write（[SWS_Can_00225]、SWS CANInterface 第156页）。在这两种情况下，驱动程序都会使用在 Can_Write 中传递的 swPduHandle 来调用 CanIf_TxConfirmation（SWS CANInterface 第102页）。

时序图：发送请求要么直接进入硬件，要么在返回 CAN_BUSY 后缓冲在 CanIf 中；确认通过中断或轮询产生，并触发缓冲的 L-PDU 的后续发送。来源：[SWS_Can_00233]、[SWS_Can_00039]、[SWS_Can_00225]、SWS CANInterface 第157页、SWS CANInterface 第156页

接收路径、L-PDU Callout 与帧格式

驱动程序通过中断或者在轮询时从 Can_MainFunction_Read 报告接收到的帧（[SWS_Can_00226]、SWS CANDriver 第79页）。通过 CanIf_RxIndication，CanIf 获得 HRH、CanId、数据长度以及对归一化数据的引用。硬件接收对象在复制过程结束前保持锁定。从 CanIf_RxIndication 返回后，它会立即被释放（SWS CANInterface 第47页）。随后，CanIf 执行软件滤波和 Data Length Check，并将数据转发给上层（SWS CANInterface 第50页）。

作为可选操作，驱动程序在转发前调用可配置的 L-PDU Callout：返回类型为 boolean 的 <LPDU_CalloutName>(Hrh, CanId, CanDataLegth, CanSduPtr)（[SWS_Can_00443]）。如果该 Callout 返回 false，根据文档处的描述，该 L-PDU 将不会被进一步处理（SWS CANDriver 第77页）。该内容出自 R25-11。认为该规则同样适用于 R20-11 是一种解读，且推测属实。

帧格式编码在 Can_IdType 中。最高两个有效位用于区分经典帧和 CAN FD 帧，各自具有标准 ID 或扩展 ID（值 00 至 11）（[SWS_Can_00416]）。当采用带有 CanControllerFdBaudrateConfig 的波特率时，控制器的 CAN FD 处于激活状态。通过这种方式，可以将经典 CAN 2.0 帧（例如用于选择性唤醒）与 FD 帧混合使用（SWS CANDriver 第49页）。CanIf 还会对动态发送 L-PDU 的相同位进行解析（SWS CANInterface 第34页）。

时序图：接收通过中断或轮询被检测到，可选地由 L-PDU Callout 进行过滤，然后通过 CanIf_RxIndication 传递给 CanIf 及上层。之后释放硬件对象。Callout 丢弃是一种解读。来源：[SWS_Can_00226]、[SWS_Can_00443]、SWS CANInterface 第47页、SWS CANInterface 第103页

轮询主函数、配置与分区

对于每个事件驱动的路径，都存在一个通过 SchM_Can.h 提供的已调度主函数：Can_MainFunction_Write、Can_MainFunction_Read、Can_MainFunction_BusOff、Can_MainFunction_Wakeup 和 Can_MainFunction_Mode（[SWS_Can_00225]、[SWS_Can_00226]、[SWS_Can_00227]、[SWS_Can_00228]、[SWS_Can_00368]）。在 R20-11 需求中，轮询绑定到模式 POLLING。后续版本的文档内容将其扩展至 MIXED：在其中仅对具有 CanHardwareObjectUsesPolling = TRUE 的硬件对象进行轮询。此外，如果在完全不进行轮询的情况下，它们允许主函数的定义为空（SWS CANDriver 第81页、SWS CANDriver 第83页、SWS CANDriver 第80页）。

若通过 CanMainFunctionRWPeriods 配置了多个周期，则写入主函数被命名为 Can_MainFunction_Write_<ShortName>()。每个被至少一个 TRANSMIT 硬件对象引用的周期都对应一个函数；对于读取路径，包含 RECEIVE 对象的情况亦然（[SWS_Can_00441]、SWS CANDriver 第81页、SWS CANDriver 第79页）。引用出处源自后续版本，且 [SWS_Can_00441] 的 R20-11 文本在有效负载中仅反映了变更历史。因此该命名规则可能也适用于 R20-11；这是一种解读。

在多核系统中，该模块在每个分区中作为独立实例运行。API 调用仅对发生调用的分区生效（[SWS_Can_CONSTR_00508]）。对于配置适用三条规则：

  • 通过 CanControllerEcucPartitionRef 引用的分区必须是 CanEcucPartitionRef 中分区的子集（[SWS_Can_CONSTR_00509]、SWS CANDriver 第99页）。
  • 一个通信通道的控制器和收发器通道必须引用同一分区（[SWS_Can_CONSTR_00510]）。
  • 驱动程序会拒绝实现不支持的分区分配（[SWS_Can_00507]）。

运行规则：中断禁止、唤醒与错误计数器

Can_DisableControllerInterrupts 和 Can_EnableControllerInterrupts 是可重入的，且支持嵌套生效（[SWS_Can_00231]、[SWS_Can_00232]、SWS CANDriver 第61页、SWS CANDriver 第62页）。如果进行了多次禁止，则必须进行相同次数的使能。未经事先禁止而直接使能将不起作用。使能仅会激活根据当前软件状态所允许的中断。

Can_CheckWakeup 用于检查是否存在通过总线的唤醒。如果被请求的控制器检测到了唤醒，驱动程序会通过 EcuM_SetWakeupEvent 将此报告给 EcuM（[SWS_Can_00360]、SWS CANDriver 第63页）。调用方为 CanIf：在 EcuM_CheckWakeup 期间，它通过 CanIf_CheckWakeup 查询相关的驱动程序和收发器（SWS CANInterface 第55页）。静态配置为“需轮询”的唤醒事件由 Can_MainFunction_Wakeup 采集（[SWS_Can_00228]）。

时序图：唤醒检查从 EcuM 经由 CanIf 执行至驱动程序；驱动程序将检测到的唤醒直接报告给 EcuM。来源：[SWS_Can_00360]、SWS CANDriver 第63页、SWS CANInterface 第55页

用于诊断时，Can_GetControllerErrorState 提供错误状态 CAN_ERRORSTATE_ACTIVE、CAN_ERRORSTATE_PASSIVE 或 CAN_ERRORSTATE_BUSOFF（[SWS_Can_91004]、[SWS_Can_91003]、SWS CANDriver 第49页）。来自 Can_GetControllerRxErrorCounter 和 Can_GetControllerTxErrorCounter 的 Rx 与 Tx 错误计数器并非在所有硬件上都可用；此时这些函数将返回 E_NOT_OK。由于硬件进行异步计数，这些值不能作为评估总线状态的可靠依据（[SWS_Can_00511]、[SWS_Can_00516]、SWS CANDriver 第67页）。Can_ErrorType 描述了典型硬件错误的超集，例如位错误、ACK 错误、CRC 错误或填充错误（[SWS_Can_91021]、SWS CANDriver 第55页）。CanIf 从这些值中派生出安全事件（SWS CANInterface 第69页）。

发生错误时的行为

驱动程序通过中断或通过在 Can_MainFunction_BusOff 中轮询来检测 Bus-off。它仅执行必要的寄存器设置，而不执行硬件恢复。随后它通过 CanIf_ControllerBusOff 报告该事件；软件状态仅在此回调中发生改变（[SWS_Can_00227]、[SWS_Can_00234]、SWS CANDriver 第30页）。CanIf 随后将 PDU 通道设置为 CANIF_TX_OFFLINE，并通过 CanSM_ControllerBusOff 通知 CanSM。作为 Bus-off 恢复一部分的重新初始化和重启在此之后才会进行（SWS CANInterface 第59页、SWS CANInterface 第53页、SWS CANInterface 第121页）。

时序图：驱动程序在不进行硬件恢复的情况下将 Bus-off 报告给 CanIf；CanIf 将发送路径切换为离线并通知 CanSM。来源：[SWS_Can_00227]、SWS CANDriver 第30页、SWS CANInterface 第59页、SWS CANInterface 第53页

若启用了开发错误检测，驱动程序会向 DET 报告开发错误。其中包括 CAN_E_PARAM_POINTER、CAN_E_PARAM_HANDLE、CAN_E_PARAM_DATA_LENGTH、CAN_E_PARAM_CONTROLLER、CAN_E_UNINIT、CAN_E_TRANSITION、CAN_E_PARAM_BAUDRATE 和 CAN_E_INIT_FAILED 等（[SWS_Can_91019]）。从 DET 返回后，受影响的函数会立即返回。带有返回值的函数随后将返回 E_NOT_OK（SWS CANDriver 第48页）。对于不允许的状态转换，驱动程序以 CAN_E_TRANSITION 进行响应（SWS CANDriver 第30页）。

Can_DeInit 尤为严格。调用方必须确保不再有控制器处于 STARTED 状态。在启用了错误检测的情况下，如果驱动程序未处于 CAN_READY 状态或某个控制器仍在运行，该函数将报告 CAN_E_TRANSITION（[SWS_Can_91002]、[SWS_Can_91012]、SWS CANDriver 第59页、SWS CANDriver 第37页）。

活动图：在错误检测激活时，Can_DeInit 检查驱动程序状态以及正在运行的控制器。在此之后，它才将模块状态以及随后的所有控制器设置为 UNINIT。来源：SWS CANDriver 第59页、SWS CANDriver 第29页、SWS CANDriver 第48页、[SWS_Can_91010]

作为唯一的运行时错误，CAN_E_DATALOST 被定义为用于丢失的接收报文（[SWS_Can_91020]）。它通过 DET 服务 Det_ReportRuntimeError 进行报告（SWS CANDriver 第73页）。相比之下，CAN_BUSY 并不是错误。当没有空闲发送对象时，它是 Can_Write 的临时结果，CanIf 对此会通过缓冲做出响应（[SWS_Can_00039]、SWS CANInterface 第43页）。

类型

Can_ConfigType 类型

This is the type of the external data structure containing the overall initialization data for the CAN driver and SFR settings affecting all controllers.此外，它还包含指向控制器配置结构的指针。初始化数据结构的内容是CAN硬件特定的。

Can_ControllerStateType 类型

多个控制器模式功能使用的状态。

Can_ErrorStateType 类型

CAN 控制器的错误状态。

Can_ErrorType 类型

该枚举表示典型 CAN HW 能够报告的 CAN 错误类型的超集。这意味着并非所有 CAN HW 都能够支持完整的集合。

Can_HwHandleType 类型

表示 CAN 硬件单元的硬件对象句柄。对于具有超过 255 个 HW 对象的 CAN 硬件单元，请使用扩展范围。

Can_HwType 类型

该类型定义了一个数据结构，它清楚地提供了硬件对象句柄，包括其相应的CAN控制器，因此CanDrv以及特定的CanId。

Can_IdType 类型

代表 L 的标识符 - PDU。两个最高有效位指定帧类型： 00 CAN 标准消息 CAN ID 01 CAN FD 标准帧 CAN ID 10带有扩展 CAN 消息 CAN ID 11 CAN FD 带有扩展 CAN ID 的帧

Can_PduType 类型

该类型将任意 CAN L - SDU 的 Pdu Id (sw Pdu Handle)、Sdu Length (长度)、Sdu Data (sdu) 和 Can Id (id) 结合在一起。
