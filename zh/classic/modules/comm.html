ComM 在用户、Bus State Manager 与生命周期之间的角色

通信管理器（ComM）接收其用户的通信需求，并将其转换为物理通道的通信模式。用户可以是 Runnable、SW-C、BswM 或 DCM（SWS ComM 第30页）。向下，ComM 仅与 Bus State Manager 进行交互。它通过 <BusSm>_RequestComMode() 请求模式 [SWS_ComM_00958]，并通过 <BusSm>_GetCurrentComMode() 进行查询 [SWS_ComM_00963]。前缀（CanSM、LinSM、FrSM、EthSM）由 ComMBusType [SWS_ComM_00962] 确定。ComM 通过 ComM_BusSM_ModeIndication 获取报告的总线模式，并通过 RTE 和 BswM 将其传递给用户 [SWS_ComM_00675]。

其他伙伴模块包括：

  • Nm，通过 ComM_Nm_* 回调，
  • EcuM，用于报告唤醒，
  • NvM，用于持久化数据，
  • BswM，带有 BswM_ComM_CurrentPNCMode 和 BswM_ComM_InitiateReset [SWS_ComM_00829]。

上下文图：ComM 一方面在用户（RTE、DCM、BswM）之间，另一方面在 Nm 以及 Bus State Manager 之间进行协调。NvM、Com 和 SchM 是服务提供者。来源：SWS ComM (Abb.) 第17页、[SWS_ComM_00829]、[SWS_ComM_00871]。

初始化：ComM_Init 接管 Post-Build 结构 ComM_ConfigType 并重置内部状态机 [SWS_ComM_00146] [SWS_ComM_00162]。在此过程中，ComM 从 NVRAM 读取非易失性参数。如果读取失败，则使用默认值（SWS ComM 第97页）。

状态与运行：ComM_GetStatus 返回 COMM_UNINIT 或 COMM_INIT [SWS_ComM_00242] [SWS_ComM_00668]。在运行期间，每个通道运行一个独立的 ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429]。

分区：来自外部分区的调用必须通过卫星实现 [SWS_ComM_01019]。ComM 仅在其所在分区中调用 Bus State Manager API [SWS_ComM_01020]。

去初始化：ComM_DeInit [SWS_ComM_00147] 仅在所有通道均处于 COMM_NO_COMMUNICATION 时生效。在此过程中，ComM 保存 NV 参数（SWS ComM 第114页）。

通道状态机：No、Silent 与 Full Communication

ComM_ModeType 包含四个值 [SWS_ComM_00672]：

  • COMM_NO_COMMUNICATION,
  • COMM_SILENT_COMMUNICATION,
  • COMM_FULL_COMMUNICATION,
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST，仅限内部。

用户只能请求 No 和 Full。Silent 仅用于与 NM 的同步（SWS ComM 第30页、[SWS_ComM_00110]）。每个通道运行一个独立的状态机（SWS ComM 第65页）。ComM_StateType 对主状态和子状态进行编码 [SWS_ComM_00674]。

进入 Full Communication 的路径：

  • 没有活动限制的请求或活动的诊断将导致转入 COMM_NO_COM_REQUEST_PENDING（SWS ComM 第69页）。
  • 只有在 ComM_CommunicationAllowed 释放通道后，才会进一步进入 Full [SWS_ComM_00871]。如果请求在此之前消失，通道将返回基本状态（SWS ComM 第63页）。

按 ComMNmVariant 的变体释放：

  • PASSIVE 和 SLAVE_PASSIVE 无条件切换至 COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915]。
  • 一旦不再存在用户请求，SLAVE_ACTIVE 便切换至该状态 [SWS_ComM_01017]。
  • ComM_Nm_PrepareBusSleepMode 在 FULL 或 PASSIVE 时进入 Silent [SWS_ComM_00826]。在该状态下发送被关闭，接收保持活动（SWS ComM 第71页）。
  • 从通道通过 ComM_BusSM_BusSleepMode [SWS_ComM_01018] [SWS_ComM_91000] 终止通信。
  • LIGHT 通道在 ComMNmLightTimeout 超时后退出 Full（SWS ComM 第78页）。

状态图：ComM 通道的主状态和子状态，以及每种 NM 变体的触发事件。来源：SWS ComM (Abb.) 第46页、SWS ComM (Abb.) 第41页、[SWS_ComM_00826]、[SWS_ComM_00915]、[SWS_ComM_01017]、[SWS_ComM_01018]。

用户和诊断的通信请求

用户与分配：用户通过 ComM_UserHandleType 进行标识。有效值为 0..254；255 代表 COMM_NOT_USED_USER_ID [SWS_ComM_00670]。用户静态分配给通道 [SWS_ComM_00995] 或 PNC [SWS_ComM_00912]。同时分配给 PNC 及其对应通道是不允许的 [SWS_ComM_00996]。

通往 RTE 的端口：

  • UR_{user_name} 提供接口 ComM_UserRequest [SWS_ComM_01011] [SWS_ComM_01000]。
  • UM_{user_name} 提供模式切换接口 ComM_CurrentMode [SWS_ComM_01010] [SWS_ComM_01001]。模式组 ComMMode 在 COMM_NO_COMMUNICATION 中启动 [SWS_ComM_01012]。

协作图：用户 SW-C、Mode Manager 以及用于 PNC 映射的工具与 ComM 进行交互所通过的端口。来源：SWS ComM (Abb.) 第81页、[SWS_ComM_01006]、[SWS_ComM_01007]、[SWS_ComM_01008]、[SWS_ComM_01009]、[SWS_ComM_91107]。

请求与释放：请求可以通过 ComM_RequestComMode [SWS_ComM_00110] 或通过 ComM_DCM_ActiveDiagnostic [SWS_ComM_00873] 发出。诊断通过 ComM_DCM_InactiveDiagnostic 重新释放通道 [SWS_ComM_00874]。在活动诊断期间，限制暂时无效（SWS ComM 第69页）。

顺序图：以 CAN 为例从 No 转换到 Full Communication 的主动启动过程，取决于 NM 变体。来源：SWS ComM 第167页、SWS ComM (Abb.) 第107页、SWS ComM 第75页。

查询：

  • ComM_GetRequestedComMode 返回易失性保存在 ComM 中的用户请求 [SWS_ComM_00079]（SWS ComM 第118页）。
  • ComM_GetCurrentComMode 查询 Bus State Manager [SWS_ComM_00083]。
  • ComM_GetMaxComMode 考虑活动限制 [SWS_ComM_00085]。

唤醒、网络管理和有序关闭

被动启动：它始于 ComM_EcuM_WakeUpIndication [SWS_ComM_00275] 或 ComM_EcuM_PNCWakeUpIndication [SWS_ComM_91001]。在发生 PNC 唤醒时，其范围取决于 ComMSynchronousWakeUp：

  • 若使用 FALSE，则仅被引用的通道切换至 COMM_NO_COM_REQUEST_PENDING [SWS_ComM_01014]。
  • 若使用 TRUE，则所有通道均切换 [SWS_ComM_01015]。

在 Network Requested 状态下，ComM 随后请求 Nm_PassiveStartup。对于被管理的通道，这是在管理通道上执行的 [SWS_ComM_01016]。这同样适用于 ComM_Nm_RestartIndication [SWS_ComM_00792]（SWS ComM 第75页）之后的情况。

顺序图：对唤醒或 NM 重启的响应，直至进入 Full Communication。来源：SWS ComM (Abb.) 第104页、[SWS_ComM_00383]、[SWS_ComM_01016]、[SWS_ComM_00915]。

关闭：当最后一个用户释放 Full 或 ComM_LimitChannelToNoComMode 生效时，关闭开始（SWS ComM 第166页）。具体流程：

  1. 在 Ready Sleep 中，ComM 在 FULL 时调用 Nm_NetworkRelease（SWS ComM 第78页）。
  2. NM 报告 ComM_Nm_PrepareBusSleepMode [SWS_ComM_00391]；通道进入 Silent。
  3. NM 报告 ComM_Nm_BusSleepMode [SWS_ComM_00392]；通道进入 No Communication。

反之，ComM_Nm_NetworkMode 表示进入 Network Mode [SWS_ComM_00390]。

顺序图：经由 Ready Sleep 和 Silent 直至 Bus-Sleep 的释放或强制限制，可选带有 ECU 复位。来源：SWS ComM (Abb.) 第106页、SWS CanNm 第87页、SWS CanSM 第29页、[SWS_ComM_00826]、[SWS_ComM_00355]。

Partial Network Cluster 与动态 PNC 映射（Draft）

基本原理：PNC 唤醒逻辑 ECU 组而非整个总线（SWS ComM 第31页）。每个 PNC 都有一个独立的状态机；PNC 操作在通道操作之前执行（SWS ComM 第35页）。模式在 ComM_PncModeType [SWS_ComM_00673] 中进行了描述。

通道分配：

  • PNC 通过 ComMChannelPerPnc 映射到通道 [SWS_ComM_00913]。
  • PNC 的位位置根据 [SWS_ComM_00825] 计算。
  • 对于带有以太网交换机的主机，存在配置限制 [SWS_ComM_CONSTR_00001]。

R20-11 特殊之处：状态交换仍通过 Com 信号进行（Com_SendSignal，EIRA/ERA 回调 ComM_COMCbk_<sn>）[SWS_ComM_00164] [SWS_ComM_00959] [SWS_ComM_00819]。直到 R21-11 才将其替换为专用 API（SWS ComM 第2页）。

状态图：包含本地请求、网关 ERA 和唤醒触发源的 PNC 状态机。来源：SWS ComM 第37页、SWS ComM 第34页、SWS ComM 第43页、[SWS_ComM_00964]、[SWS_ComM_00165]、[SWS_ComM_01053]。

动态 PNC 到通道映射：该特性在 R20-11 中为新增，并标记为 Draft（SWS ComM 第2页）。

  • 学习阶段：ComM_PnLearningRequest 启动该阶段 [SWS_ComM_91019] [SWS_ComM_01026]。网关转发学习请求 [SWS_ComM_01028]。ComM_Nm_RepeatMessageLeftIndication 结束该阶段 [SWS_ComM_01029]。
  • 在学习阶段，ComM 将接收到的 ERA 位纳入映射 [SWS_ComM_01031]，并发送自己的 Membership [SWS_ComM_01032] [SWS_ComM_01033]。
  • 管理 API：ComM_GetPncToChannelMapping、ComM_UpdatePncToChannelMapping、ComM_ResetPncToChannelMapping 以及 ComM_UpdatePncMembership [SWS_ComM_91013] [SWS_ComM_91015] [SWS_ComM_91017] [SWS_ComM_91021]。

版本差异：

  • 在 R20-11 中，ComM_GetPncToChannelMapping 具有参数 boolean* MappingTable 和 PncCnt。后续版本使用带有 PNCBitVectorLength 的 uint8 位向量（SWS ComM 第122页）；此处以 [SWS_ComM_91013] 为准。
  • R20-11 需求中与此不同，称为 ComM_GetPncMappingTable [SWS_ComM_01034]。
  • ComM_Nm_ForwardSynchronizedPncShutdown 在 R20-11 中仅包含参数 Channel [SWS_ComM_91003]。后来增加了 PNC 位向量（SWS ComM 第137页）。

顺序图：从启动、映射更新直至离开 Repeat Message 的 PNC 学习阶段。来源：SWS ComM 第56页、SystemTemplate (Abb.) 第329页、[SWS_ComM_01026]、[SWS_ComM_01029]、[SWS_ComM_01031]、[SWS_ComM_01035]。

通信限制与持久化抑制状态

抑制状态：它是一个位字段 [SWS_ComM_00669]：

  • 位 0：Wake-up-Inhibition，
  • 位 1：Limit to No Com。

ComMEcuGroupClassification 用作掩码，用于确定究竟允许执行哪些抑制。它通过 ComM_SetECUGroupClassification 设置 [SWS_ComM_00552]（SWS ComM 第73页）。该状态以非易失性方式存储，并在启动时恢复（SWS ComM 第84页）。

控制 API：

  • ComM_LimitChannelToNoComMode [SWS_ComM_00163],
  • ComM_LimitECUToNoComMode [SWS_ComM_00124],
  • ComM_PreventWakeUp [SWS_ComM_00156],
  • ComM_GetInhibitionStatus 用于读取 [SWS_ComM_00619]。

Mode Manager SW-C 通过接口 ComM_ChannelLimitation、ComM_ChannelWakeup 和 ComM_ECUModeLimitation 访问这些函数 [SWS_ComM_00743] [SWS_ComM_00742] [SWS_ComM_00741]（SWS ComM (Abb.) 第68页）。

限制的作用：

  • 尽管存在用户请求，主动请求的通道仍会切换至 Ready Sleep。被动保持唤醒的通道不受影响（SWS ComM 第88页）。
  • 限制期间的请求会被丢弃。在解除限制后，用户必须重新请求（SWS ComM 第91页）。
  • 若 ComMResetAfterForcingNoComm 被设置，ComM 会通过 BswM 触发 ECU 复位 [SWS_ComM_00355]。
  • 被拒绝的 Full 请求由抑制计数器计数。ComM_ReadInhibitCounter 用于读取该计数器，ComM_ResetInhibitCounter 用于将其复位 [SWS_ComM_00224] [SWS_ComM_00108]。两者仅在具有 ComMModeLimitationEnabled 并配置了 NvM 块时才存在（SWS ComM 第130页）。

活动图：激活“Limit to No Com”直至可选复位的决策路径。来源：SWS ComM 第88页、SWS ComM 第84页、[SWS_ComM_00163]、[SWS_ComM_00110]、[SWS_ComM_00355]。

发生错误时的行为

未初始化模块：未经初始化时，除 ComM_Init、ComM_GetVersionInfo 和 ComM_GetStatus 之外的所有 API 均不执行正常操作，并返回 E_NOT_OK [SWS_ComM_00612]。

开发错误：开发错误包括 COMM_E_UNINIT、COMM_E_WRONG_PARAMETERS、COMM_E_PARAM_POINTER 和 COMM_E_INIT_FAILED [SWS_ComM_00234]。

业务返回值位于 [SWS_ComM_91027] 范围内：

情况响应出处
处于活动抑制时的 Full 请求COMM_E_MODE_LIMITATION[SWS_ComM_00110]

更新时通道或 PNC 数量错误DET 错误 COMM_E_WRONG_PARAMETERS、E_NOT_OK[SWS_ComM_01038]

NVRAM 读取错误：如果读取失败，ComM 将使用默认值（SWS ComM 第97页）。运行时错误 COMM_E_READ_NV_FAILED 来自后续版本，对 R20-11 而言不具有规范性（SWS ComM 第96页）。

Bus-Off：CanSM 通过 ComM_BusSM_ModeIndication 报告 COMM_SILENT_COMMUNICATION（EXP ErrorDescription 第19页）。ComM 将此模式传递给用户 [SWS_ComM_00675]。

去初始化：ComM_DeInit 无法报告错误。因此调用者必须预先确保所有通道均处于 No Communication（SWS ComM 第114页）。
