按通道将应用程序和诊断的通信愿望转换为总线状态与子网状态。

Communication Manager 按通道将 SW-C、BswM 和 DCM 的通信愿望转换为对总线状态管理器的请求，并将实际模式反馈给用户（[SWS_ComM_00958]）。为此，它为每个通道维护一个包含 No Communication、Silent Communication 和 Full Communication 的状态机。其转换取决于用户请求、唤醒通知、CommunicationAllowed 释放以及网络管理。它可以选择管理子网，在 R20-11 中还包含仍作为草案管理的动态 PNC 到通道映射。最重要的边界条件：用户仅能请求 No 或 Full，且处于激活状态的限制会以 COMM_E_MODE_LIMITATION 拒绝 Full 请求（[SWS_ComM_00110]）。

ComM 汇聚 SW-C、BswM 和 DCM 的通信愿望（SWS ComM 第30页）。它按通道将其转换为对 <BusSm>_RequestComMode() 的调用（[SWS_ComM_00958]）。它通过 RTE 和 BswM 将实际总线模式返回给用户（[SWS_ComM_00675]）。EcuM 或 BswM 通过 ComM_CommunicationAllowed 控制通信是否根本被允许（[SWS_ComM_00871]）。

上下文图：处于用户、EcuM/BswM、DCM、Nm 和总线状态管理器之间的 ComM。来源：SWS ComM 第17页、[SWS_ComM_00958]

每个通道拥有独立的状态机，包含 No Communication、Silent Communication 和 Full Communication 模式及其子状态（[SWS_ComM_00674]）。用户仅允许请求 No 和 Full；Silent 用于 NM 同步（SWS ComM 第30页）。状态转换取决于 ComMNmVariant。在 FULL 或 PASSIVE 下，Prepare-Bus-Sleep 会导致转换至 Silent（[SWS_ComM_00826]）。对于 SLAVE 通道，总线状态管理器的 Bus-Sleep 消息将终止通信（[SWS_ComM_01018]）。

状态图：通道从休眠状态到完全通信并返回的生命周期。来源：SWS ComM 第46页、[SWS_ComM_00826]

主动启动始于 ComM_RequestComMode（[SWS_ComM_00110]）或主动诊断。被动启动跟随来自 EcuM 的唤醒消息（[SWS_ComM_00275]）。在这种情况下，ComM 会请求 Nm_PassiveStartup，对于受管通道则是为其管理通道请求（[SWS_ComM_01016]）。

ComM 可选地管理子网（PNC），每个子网各有一个状态机（[SWS_ComM_00673]）。用户到子网和通道的分配遵循固定规则（[SWS_ComM_00996]）。动态 PNC 到通道分配在 R20-11 中是新增特性，目前仍标记为 DRAFT（[SWS_ComM_01026]）。

Mode Manager 可以将通道限制为 No Communication（[SWS_ComM_00163]）。此时用户对 Full Communication 的请求将失败并返回 COMM_E_MODE_LIMITATION（[SWS_ComM_00110]）。在 ComM_Init 之前，几乎所有函数都会返回 E_NOT_OK（[SWS_ComM_00612]）。

角色：通信用户与总线状态管理器之间的中介

ComM 为其用户简化了资源管理。这些用户包括 Runnable、SW-C、BswM，或者在需要通信进行诊断时的 DCM（SWS ComM 第30页）。用户仅需请求其需求。ComM 会针对每个通道将该需求转换为对 <BusSm>_RequestComMode() 的调用（[SWS_ComM_00958]）。前缀 CanSM、LinSM、FrSM 或 EthSM 取决于 ComMBusType（[SWS_ComM_00962]）。

在相反方向上，总线状态管理器通过 ComM_BusSM_ModeIndication 报告实际模式。ComM 通过 RTE 和 BswM 将其转发给用户（[SWS_ComM_00675]）。其他输入来自三个方面：

  • EcuM 或 BswM 允许使用 ComM_CommunicationAllowed 进行通信（[SWS_ComM_00871]）。
  • DCM 报告处于活动状态和已终止的诊断（[SWS_ComM_00873]，[SWS_ComM_00874]）。
  • Nm 报告其状态（[SWS_ComM_00390]，[SWS_ComM_00392]）。

ComM 通过 NvM 读取和写入持久化数据（SWS ComM 第144页）。

上下文图：ComM 位于用户与总线状态管理器之间，并受 EcuM/BswM、DCM 和 Nm 的影响。来源：SWS ComM 第17页、[SWS_ComM_00958]、[SWS_ComM_00675]、[SWS_ComM_00871]

通信模式与通道状态机

ComM_ModeType 具有四种模式（[SWS_ComM_00672]）：

  • COMM_NO_COMMUNICATION：既不发送也不接收。
  • COMM_SILENT_COMMUNICATION：仅接收。
  • COMM_FULL_COMMUNICATION：发送和接收。
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST.

用户仅允许请求 No 和 Full。Silent 仅用于 NM 同步（SWS ComM 第30页）。模式声明组 ComMMode 启动于 COMM_NO_COMMUNICATION（[SWS_ComM_01012]）。

每个通道都有一个独立的自身状态机（SWS ComM 第65页）。其状态由 ComM_StateType 提供（[SWS_ComM_00674]）。在进入 Full Communication 时，通道进入 COMM_FULL_COM_NETWORK_REQUESTED，并通过总线状态管理器开启发送和接收（SWS ComM 第64页）。

状态转换取决于 ComMNmVariant：

  • FULL 或 PASSIVE：ComM_Nm_PrepareBusSleepMode 导致进入 Silent（[SWS_ComM_00826]）。
  • PASSIVE 或 SLAVE_PASSIVE：通道直接进入 COMM_FULL_COM_READY_SLEEP（[SWS_ComM_00915]）。
  • SLAVE_ACTIVE：一旦不再存在用户请求，它即进入该状态（[SWS_ComM_01017]）。
  • SLAVE 变体：ComM_BusSM_BusSleepMode 终止通信（[SWS_ComM_01018]）。
  • LIGHT：退出由定时器 ComMNmLightTimeout 决定（SWS ComM 第78页）。

状态图：通道的生命周期及其取决于 NM 变体的状态转换。来源：SWS ComM 第46页、[SWS_ComM_00826]、[SWS_ComM_00915]、[SWS_ComM_01018]

从通信请求到总线并返回休眠

主动启动始于 ComM_RequestComMode（[SWS_ComM_00110]）或 ComM_DCM_ActiveDiagnostic。在没有限制的情况下，通道立即切换至 COMM_NO_COM_REQUEST_PENDING（SWS ComM 第69页）。它在此处等待，直到 CommunicationAllowed 标志为 TRUE（SWS ComM 第63页）。通常，BswM 规则会在启动过程中设置此标志（Mode-Management-Guide 第25页）。

时序图：主动启动直到模式报告，以 CAN 为例。来源：SWS ComM 第107页、SWS ComM 第75页、[SWS_ComM_00675]

被动启动紧随唤醒通知之后。触发源包括 ComM_EcuM_WakeUpIndication（[SWS_ComM_00275]）、ComM_EcuM_PNCWakeUpIndication 或 ComM_Nm_RestartIndication（[SWS_ComM_00792]）。PNC 唤醒通知会将该 PNC 引用的通道置于 COMM_NO_COM_REQUEST_PENDING。在同步唤醒时，这适用于所有通道（[SWS_ComM_01014]，[SWS_ComM_01015]）。随后，ComM 请求 Nm_PassiveStartup。对于受管通道（managed），这是针对管理通道执行的（[SWS_ComM_01016]）。

时序图：唤醒或重启通知后的被动启动。来源：SWS ComM 第104页、[SWS_ComM_91001]、[SWS_ComM_01016]

当最后一个用户释放其请求或限制生效时，关断开始（SWS ComM 第166页）。在 COMM_FULL_COM_READY_SLEEP 中，ComM 在 FULL 变体下调用 Nm_NetworkRelease()（SWS ComM 第78页）。随后，Prepare-Bus-Sleep 和 Bus-Sleep 通知经由 Silent 导向 No Communication（[SWS_ComM_00826]，[SWS_ComM_00392]）。

时序图：释放或强制直到 No Communication，以 CAN 为例。来源：SWS ComM 第106页、[SWS_ComM_00355]

有三个函数用于查询。ComM_GetRequestedComMode 返回已存储的用户请求（[SWS_ComM_00079]）。ComM_GetCurrentComMode 查询总线状态管理器（[SWS_ComM_00963]），并在存在多个通道时返回最低模式（SWS ComM 第119页）。ComM_GetMaxComMode 返回最高允许模式（[SWS_ComM_00085]）。

部分网络（PNC）与用户分配

PNC 是必须同时处于活动状态的 ECU 逻辑组（SWS ComM 第31页）。ComM 为每个 PNC 仅维护一个状态机，并在通道操作之前处理 PNC 操作（SWS ComM 第35页）。模式包含在 ComM_PncModeType 中（[SWS_ComM_00673]）。

最重要的状态转换：

  • PNC 唤醒通知导致从 COMM_PNC_NO_COMMUNICATION 转换至 COMM_PNC_PREPARE_SLEEP（[SWS_ComM_00964]）。
  • 用户请求或网关处置位的 ERA 位导致从 COMM_PNC_READY_SLEEP 转换至 COMM_PNC_REQUESTED（[SWS_ComM_00165]）。
  • 网关在此过程中置位或清除被动通道的 PNC 位（[SWS_ComM_00164]，[SWS_ComM_00959]）。

状态图：PNC 状态机。返回空闲状态为一种解释。来源：SWS ComM 第37页、[SWS_ComM_01053]、[SWS_ComM_00165]

用户可以分配给 PNC（[SWS_ComM_00912]）或直接分配给通道（[SWS_ComM_00995]）。额外分配给 PNC 已引用的通道是不允许的（[SWS_ComM_00996]）。对于带有以太网交换机的 ECU，适用进一步的限制（[SWS_ComM_CONSTR_00001]）。如果未向用户分配 PNC 或分配了多个 PNC，ComM_GetCurrentPNCComMode 会报告错误（[SWS_ComM_01022]，[SWS_ComM_01023]）。

上下文图：用户、PNC 与通道之间允许和不允许的分配。来源：SWS ComM 第59页、[SWS_ComM_00913]

R20-11 中的新功能是可选的动态 PNC 到通道分配。其需求仍标记为 DRAFT（SWS ComM 第2页）。学习阶段始于 Learning 位（[SWS_ComM_01026]）并结束于 ComM_Nm_RepeatMessageLeftIndication（[SWS_ComM_01029]）。在此期间，管理函数拒绝带有 COMM_E_LEARNING_ACTIVE 的调用（[SWS_ComM_01042]）。后续版本更改了 ComM_GetPncToChannelMapping 的签名。对于 R20-11，适用 [SWS_ComM_91013]（SWS ComM 第122页）。

通信限制与唤醒抑制

ComM 提供三种干预手段：

  • ComM_LimitChannelToNoComMode 将某个通道限制为 No Communication（[SWS_ComM_00163]）。
  • ComM_LimitECUToNoComMode 限制所有通道（[SWS_ComM_00124]）。
  • ComM_PreventWakeUp 切换唤醒抑制（[SWS_ComM_00156]）。

状态由位字段 ComM_InhibitionStatusType 保持（[SWS_ComM_00669]）。ECU 组分类作为掩码作用于其上，并进行非易失性存储（SWS ComM 第84页）。Mode Manager 通过端口 modeLimitation、CL_… 和 CW_… 访问这些函数（[SWS_ComM_01009]、[SWS_ComM_01006]、[SWS_ComM_01008]）。

当限制处于活动状态时，尽管存在用户请求，主动请求的通道仍会进入 COMM_FULL_COM_READY_SLEEP。新的请求将被忽略。仅保持被动唤醒的通道不受影响（SWS ComM 第87页）。此时 ComM_RequestComMode 返回 COMM_E_MODE_LIMITATION（[SWS_ComM_00110]）。解释：ComM_ReadInhibitCounter 计数的正是这些被拒绝的请求（[SWS_ComM_00224]）。活动诊断会暂时挂起限制（SWS ComM 第69页）。在强制进入 No Communication 之后，ComM 可以可选地强制执行 ECU 复位（[SWS_ComM_00355]）。

活动图：掩码、限制和诊断的作用。计数器步骤为一种解释。来源：[SWS_ComM_00163]、[SWS_ComM_00110]、SWS ComM 第87页

初始化、集成与端口

ComM_Init 重新启动状态机（[SWS_ComM_00146]）。在此过程中，ComM 读取非易失性参数，这以已初始化的 NvM 为前提条件（SWS ComM 第97页）。ComM_DeInit（[SWS_ComM_00147]）仅在所有通道均处于 No Communication 时有效，随后保存至 NVRAM（SWS ComM 第114页）。

每个通道都有其自身的 Main Function（[SWS_ComM_00429]）。在集成时必须注意其相对于 Nm 和总线特定 NM 模块的顺序（Mode-Management-Guide 第39页）。在存在多个分区的情况下，ComM 必须允许来自外部分区的调用（[SWS_ComM_01019]）。它仅在总线状态管理器自身的分区中调用它们（[SWS_ComM_01020]）。SW-C 使用端口 UR_… 和 UM_…（[SWS_ComM_01011]，[SWS_ComM_01010]）。

发生错误时的行为

在初始化之前，只有 ComM_Init、ComM_GetVersionInfo 和 ComM_GetStatus 正常工作。所有其他函数均返回 E_NOT_OK（[SWS_ComM_00612]）。开发错误（例如 COMM_E_UNINIT 或 COMM_E_WRONG_PARAMETERS）由 [SWS_ComM_00234] 定义。若从 NvM 读取失败，ComM 将使用默认值（SWS ComM 第97页）。

发生 Bus-off 时，CanSM 报告 Silent Communication（Error Description 第19页）。ComM 将此通知转发给用户（[SWS_ComM_00675]）。如果在协同关断期间 Nm 重新启动，则执行 ComM_Nm_RestartIndication（[SWS_ComM_00792]）。
