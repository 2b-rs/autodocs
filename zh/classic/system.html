EcuM_CheckRamHash 函数

此标注旨在提供 RAM 完整性测试。此测试的目标是确保在长时间的SLEEP持续时间后，RAM内容仍然一致。检查不需要详尽，因为这会在唤醒期间消耗相当多的处理时间。精心设计的检查将快速执行并以足够的概率检测RAM完整性缺陷。本规范不对为特定ECU选择的算法做出任何假设。必须仔细选择要检查的RAM区域。这取决于检查算法本身和任务结构。执行 RAM 检查的任务的堆栈内容，例如很可能无法检查。良好的做法是在同一任务中进行哈希生成和检查，并且该任务不可抢占，并且哈希生成和哈希检查之间只有很少的活动。 RAM 检查本身由系统设计者提供。如果应用多核且存在 Satellite-Ecu M(s)：此API将仅由 Master-EcuM 调用。

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation 函数

此标注由 EcuM 调用以验证唤醒源。如果检测到有效唤醒，应通过EcuM_ValidateWakeupEvent()报告给EcuM。

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup 函数

此标注由 EcuM 调用以轮询唤醒源。它还应由唤醒源的ISR 调用，以设置PLL 并检查可能连接到同一中断的其他唤醒源。

EcuM_DeterminePbConfiguration 函数

此标注应评估某些条件，例如端口引脚或NVRAM值，以确定在启动过程的其余部分中应使用哪个构建后配置。它将将此配置数据加载到所有BSW模块可访问的内存中，并返回指向EcuM构建后配置的指针，作为所有BSW模块构建后配置的基础。

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources 函数

ECU管理器模块调用EcuM_DisableWakeupSources来设置wakeupSource位字段中定义的唤醒源，以便它们无法唤醒ECU。

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources 函数

ECU管理器模块调用EcuM_EnableWakeupSource以允许系统设计者通知在wakeupSource位字段中定义的唤醒源将输入SLEEP并相应地调整其源。

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup 函数

此API由任何其唤醒源被异步检查的SW模块调用（例如异步CanTrcv驱动程序），并且唤醒检查返回负结果（此源没有唤醒）。 API取消了WakeupSource的CheckWakeupTimer。如果对应的CheckWakeupTimer被取消，则该唤醒源的检查结束。

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook 函数

如果出现错误代码“ECUM_E_RAM_CHECK_ FAILED”或“ECUM_E_CONFIGURATION_DATA_INCONSISTENT”，ECU State Manager将调用错误钩子。在这种情况下，无法继续处理，必须停止 ECU。集成商可以选择ECU停止的方式，即重置、暂停、重新启动、安全状态等。

系统架构与模块集群的角色

“系统服务”（System Services）集群包含支持 Classic Platform 控制器的启动、运行模式、睡眠/停机以及程序运行监控的模块。其中，ECU 状态管理器是在 OS 停机后建立最终硬件状态的系统服务（SWS EcuM 第82页、[SWS_EcuM_04020]）。这四个模块具有明确分工的角色：

  • BswM 仲裁传入的模式指示（[SWS_BswM_00035]）。规则对 ModeRequestPort 进行逻辑关联，并触发 True 或 False 操作列表（Mode Management Guide 第32页）。操作仅在操作列表的上下文中运行（[SWS_BswM_00147]）。
  • EcuM 初始化 BSW，启动和终止 OS，并管理唤醒源的状态（[SWS_EcuM_02811]、[SWS_EcuM_04091]）。它不具备自身的状态机。它从 BswM 接管状态转换（SWS EcuM 第99页、[SWS_EcuM_04116]）。
  • WdgM 通过检查点监控 Supervised Entity（[SWS_WdgM_00263]），并据此生成 Global Supervision Status（[SWS_WdgM_00360]）。它通过 WdgIf_SetMode 设置看门狗模式（[SWS_WdgM_00186]）。
  • Wdg 驱动内部或外部看门狗硬件（[SWS_Wdg_00161]、[SWS_Wdg_00076]）。只要触发条件有效，它就会对硬件进行服务（[SWS_Wdg_00144]）。

协作与交互路径

EcuM ↔ BswM（ECU 模式处理）：当配置了 EcuMModeHandling 时，该路径处于激活状态（[SWS_EcuM_04115]）。SW-C 分别通过 EcuM_RequestRUN 和 EcuM_RequestPOST_RUN 请求并再次释放 RUN 和 POST_RUN（[SWS_EcuM_04124]、[SWS_EcuM_04127]、[SWS_EcuM_04128]）。EcuM 通过 BswM_EcuM_RequestedState 报告仲裁结果（[SWS_BswM_91004]、[SWS_EcuM_04144]、[SWS_EcuM_04117]）。BswM 随后通过 EcuM_SetState 设置状态（[SWS_EcuM_04122]）。一旦 RTE 确认了该转换，EcuM 便通过 BswM_EcuM_CurrentState 反馈状态（[SWS_EcuM_04143]、[SWS_BswM_91003]）。

唤醒路径：驱动程序通过 EcuM_SetWakeupEvent 报告唤醒，该操作将事件标记为 pending（[SWS_EcuM_01117]）。如果需要验证，EcuM 会启动验证协议（[SWS_EcuM_02975]）。验证由恰好一个 BSW 模块承担（SWS EcuM 第69页）。其对 EcuM_ValidateWakeupEvent 的调用会通知 BswM 和 ComM（[SWS_EcuM_04079]、[SWS_EcuM_02645]）。唤醒源的每次状态变更都会作为模式请求报告给 BswM（[SWS_EcuM_04003]）。

WdgM → Wdg：Wdg_SetTriggerCondition 接收以毫秒为单位的超时时间，并在内部结合当前模式将其换算为计数器值（[SWS_Wdg_00155]、[SWS_Wdg_00138]、[SWS_Wdg_00139]）。驱动程序的服务例程表现如下：

  • 如果计数器大于零，它将对其递减并触发硬件（[SWS_Wdg_00134]）。
  • 为零时，它不再触发，看门狗超时溢出（[SWS_Wdg_00135]）。

解读：WdgIf 应将模式和触发条件转发给各自寻址的 Wdg 实例。多个实例具有唯一名称（[SWS_Wdg_00172]）。

EcuM → WdgM（复位）：WdgM_PerformReset 是强制性复位目标（[SWS_EcuM_04005]、[SWS_EcuM_04044]）。它将所有驱动程序的触发条件设置为 0，硬件看门狗由此触发复位（[SWS_WdgM_00264]、SWS WdgM 第82页）。ECUM_CAUSE_WDGM 可用作停机原因（[SWS_EcuM_04045]）。

同步、重入性与任务上下文

BswM_MainFunction：它评估所有使用带有 BSWM_DEFERRED 请求的规则（[SWS_BswM_00075]）。BswM 定时器始终作为延迟（deferred）处理（[SWS_BswM_00220]）。相反，带有“immediate”的请求会立即进行评估（Mode Management Guide 第32页）。

EcuM_MainFunction：它在所有 EcuM 实例中运行（[SWS_EcuM_04011]）。它监控验证超时（[SWS_EcuM_04082]）并在 WakeupRestart 之后验证唤醒候选对象（[SWS_EcuM_02539]）。

WdgM_MainFunction：它在 WdgM_Init 之后的首次调用时启动监控（[SWS_WdgM_00406]），并在之后的每个周期中计算 Global Supervision Status（SWS WdgM 第34页）。

中断上下文：唤醒服务可从中断、OS 和无 OS 上下文中调用（[SWS_EcuM_02171]、[SWS_EcuM_02807]、[SWS_EcuM_02532]）。但它们被规范定义为“Non-Reentrant, Non-Interruptible”（[SWS_EcuM_02826]、[SWS_EcuM_02828]）。一个例外是 EcuM_ValidateWakeupEvent：它是可重入的，且可从中断和任务上下文中调用（[SWS_EcuM_02829]、[SWS_EcuM_02345]）。

WdgM 与 Wdg 的重入性：

  • WdgM_SetMode、WdgM_DeInit 和 Wdg_SetTriggerCondition 是不可重入的（[SWS_WdgM_00154]、[SWS_WdgM_00261]、[SWS_Wdg_00155]）。

  • Wdg 仅通过预设的 BSW 机制禁用中断以确保数据一致性（[SWS_Wdg_00040]）。

多核：每个 Core 运行一个单独的 EcuM 实例。Master-EcuM 启动其余 Core（SWS EcuM 第71页）。由此产生以下职责：

  • 每个实例处理其自身 Core 的唤醒（[SWS_EcuM_04012]）。
  • 所有 Core 本地的 BswM 均被初始化（[SWS_EcuM_04014]）。
  • 每个 Core 预留一个资源 RES_AUTOSAR_ECUM（[SWS_EcuM_03010]）。

生命周期与运行模式

启动（StartPreOS）：EcuM_Init 执行 StartPreOS 时序（[SWS_EcuM_02684]）。它包括：

  • 按配置顺序执行的 Init 块 0 和 1（[SWS_EcuM_02559]、[SWS_EcuM_02905]、[SWS_EcuM_02907]），
  • 选择 Post-Build 配置（[SWS_EcuM_02906]），
  • 在首次 BSW 初始化之前对所有 Post-Build 配置进行一致性检查（[SWS_EcuM_02796]）。

根据结构描述，Wdg_Init 属于 EcuM 所使用的 Init 函数（SWS EcuM 第34页）。Wdg_Init 设置默认模式和超时时间（[SWS_Wdg_00001]）。

启动（StartPostOS）：EcuM_StartupTwo 在由 StartOS 启动的任务中运行（[SWS_EcuM_02806]）。它启动 SchM 并初始化 BswM（[SWS_EcuM_02932]）。BswM_Init 仅要求已初始化的 OS 和 SchM（SWS BswM 第69页）。BswM 可以在 UP 阶段初始化其他驱动程序，例如通过 EcuM_AL_DriverInitBswM_<x>（SWS EcuM 第46页、[SWS_EcuM_04114]）。

时序图：该时序图展示了 Master-Core 上 StartPreOS 和 StartPostOS 的顺序。来源：[SWS_EcuM_04015]、[SWS_EcuM_04016]、SWS EcuM 第82页、SWS EcuM 第42页

Sleep：在 EcuM_GoDownHaltPoll 之前，BswM 通常必须已选择一个 SLEEP 目标（SWS EcuM 第54页、[SWS_EcuM_91002]）。流程如下：

  1. GoSleep 激活唤醒源；在此期间 OS 保持活动状态（[SWS_EcuM_02389]、[SWS_EcuM_02951]）。
  2. 随后根据 Sleep 模式执行带 RAM 哈希的 Halt（[SWS_EcuM_02863]）或 Poll（[SWS_EcuM_02962]）。在此过程中不得丢失任何唤醒（[SWS_EcuM_02188]）。
  3. 唤醒会进入带有驱动程序重新初始化的 WakeupRestart 序列（[SWS_EcuM_02963]、[SWS_EcuM_02923]）。

在 R20-11 中，Poll Callout 称为 EcuM_CheckWakeup（[SWS_EcuM_02929]）。自 R21-11 起它才称为 EcuM_CheckWakeupHook（SWS EcuM 第145页）。

Sleep 中的看门狗：在进入 Sleep 之前，WdgM_DeInit 切换到具有兼容触发条件的 Sleep 模式并停止监控（SWS WdgM 第59页、[SWS_WdgM_00407]）。然而 EcuM 的结构描述中仅将 WdgM_PerformReset 列为 WdgM 依赖项。因此，WdgM_DeInit 的调用推测是通过 BswM 动作或集成代码进行的。

时序图：该时序图展示了带有 Halt 的 SLEEP 阶段：GoSleep、RAM 哈希、Wakeup 和 WakeupRestart。来源：SWS EcuM 第54页、SWS EcuM 第55页、SWS EcuM 第56页、[SWS_EcuM_04024]、[SWS_EcuM_02987]

Shutdown：流程如下：

  1. OffPreOS 去初始化 BswM 和 SchM（SWS EcuM 第90页）。此后 BswM 不再处理任何模式（[SWS_BswM_00120]）。
  2. 作为最后一项活动，EcuM 调用 ShutdownOS（[SWS_EcuM_02952]）。Shutdown-Hook 调用 EcuM_Shutdown（[SWS_EcuM_02953]）。
  3. 最后执行 EcuM_AL_Reset 或 EcuM_AL_SwitchOff（[SWS_EcuM_04074]、[SWS_EcuM_04075]）。

唤醒源在 Dem_Shutdown 和 NvM_WriteAll 之前须通过 BswM 用户 Callout 进行清除（SWS EcuM 第124页、[SWS_BswM_00054]）。在 Shutdown 期间发生的唤醒会导致在其完成后重新启动（[SWS_EcuM_02756]）。Wdg 没有自己的去初始化接口（[SWS_Wdg_00031]）。

错误处理、DET 跟踪与降级

开发错误（DET）：

  • BswM 在初始化之前会忽略指示并报告 BSWM_E_UNINIT（[SWS_BswM_00078]、[SWS_BswM_00230]）。它将失败的动作报告为运行时错误 BSWM_E_ACTION_FAILED（[SWS_BswM_00238]）。
  • EcuM 报告重复的 RUN 请求和不匹配的释放（[SWS_EcuM_03024]、[SWS_EcuM_03023]）以及未知的唤醒源（[SWS_EcuM_02867]）。
  • WdgM 和 Wdg 定义了各自的错误代码（[SWS_WdgM_00004]、[SWS_Wdg_00010]）。WdgM 将失败的 WdgIf_SetMode 报告为 WDGM_E_SET_MODE（[SWS_WdgM_00139]）。

不可恢复错误：EcuM 将其转发给 EcuM_ErrorHook（[SWS_EcuM_04033]）。示例包括不一致的配置数据或失败的 RAM 校验（[SWS_EcuM_91003]）。EcuM 会忽略初始化期间由 Init 函数返回的错误（[SWS_EcuM_02980]）。

监控降级：全局状态以 WDGM_GLOBAL_STATUS_DEACTIVATED 启动（[SWS_WdgM_00387]）。模式切换仅允许在 OK 和 FAILED 状态下进行（[SWS_WdgM_00145]）。可以通过配置禁止关闭看门狗（[SWS_WdgM_00031]）。升级过程如下：

  1. 在 EXPIRED 状态下，错误响应会延迟一个可配置的容限期（SWS WdgM 第34页）。
  2. 在 STOPPED 状态下，WdgM 报告 WDGM_E_SUPERVISION，随后发生看门狗复位（[SWS_WdgM_00375]）。
  3. 模式切换失败也会导致进入 STOPPED（SWS WdgM 第57页）。

复位后的诊断：最先超时的 SEID 以双重反转方式存储在未初始化的 RAM 中。在 WdgM_Init 之前即可对其进行读取（[SWS_WdgM_00348]、[SWS_WdgM_00349]）。WdgM 通过 Mode-Port 报告状态变化（[SWS_WdgM_00197]、[SWS_WdgM_00198]）。BswM_WdgM_RequestPartitionReset 在 R20-11 中仍然存在（[SWS_BswM_00157]），但自 R21-11 起废弃（SWS BswM 第2页）。

驱动程序错误与最终保障：Wdg 将生产错误 WDG_E_MODE_FAILED 和 WDG_E_DISABLE_REJECTED 报告给 DEM（[SWS_Wdg_00180]、[SWS_Wdg_00182]）。如果 EcuM_AL_SwitchOff 陷入死锁，硬件看门狗将复位 ECU（SWS EcuM 第141页）。
