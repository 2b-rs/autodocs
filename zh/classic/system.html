EcuM_CheckRamHash 函数

此标注旨在提供 RAM 完整性测试。此测试的目标是确保在长时间的SLEEP持续时间后，RAM内容仍然一致。检查不需要详尽，因为这会在唤醒期间消耗相当多的处理时间。精心设计的检查将快速执行并以足够的概率检测RAM完整性缺陷。本规范不对为特定ECU选择的算法做出任何假设。必须仔细选择要检查的RAM区域。这取决于检查算法本身和任务结构。执行 RAM 检查的任务的堆栈内容，例如很可能无法检查。良好的做法是在同一任务中进行哈希生成和检查，并且该任务不可抢占，并且哈希生成和哈希检查之间只有很少的活动。 RAM 检查本身由系统设计者提供。如果应用多核且存在 Satellite-Ecu M(s)：此API将仅由 Master-EcuM 调用。

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation 函数

此标注由 EcuM 调用以验证唤醒源。如果检测到有效唤醒，应通过EcuM_ValidateWakeupEvent()报告给EcuM。

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup 函数

此标注由 EcuM 调用以轮询唤醒源。它还应由唤醒源的ISR 调用，以设置PLL 并检查可能连接到同一中断的其他唤醒源。

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);
EcuM_ClearWakeupEvent 函数

清除唤醒事件。

void EcuM_ClearWakeupEvent (EcuM_WakeupSourceType sources);
EcuM_DeterminePbConfiguration 函数

此标注应评估某些条件，例如端口引脚或NVRAM值，以确定在启动过程的其余部分中应使用哪个构建后配置。它将将此配置数据加载到所有BSW模块可访问的内存中，并返回指向EcuM构建后配置的指针，作为所有BSW模块构建后配置的基础。

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources 函数

ECU管理器模块调用EcuM_DisableWakeupSources来设置wakeupSource位字段中定义的唤醒源，以便它们无法唤醒ECU。

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources 函数

ECU管理器模块调用EcuM_EnableWakeupSource以允许系统设计者通知在wakeupSource位字段中定义的唤醒源将输入SLEEP并相应地调整其源。

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup 函数

此API由任何其唤醒源被异步检查的SW模块调用（例如异步CanTrcv驱动程序），并且唤醒检查返回负结果（此源没有唤醒）。 API取消了WakeupSource的CheckWakeupTimer。如果对应的CheckWakeupTimer被取消，则该唤醒源的检查结束。

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook 函数

如果出现错误代码“ECUM_E_RAM_CHECK_ FAILED”或“ECUM_E_CONFIGURATION_DATA_INCONSISTENT”，ECU State Manager将调用错误钩子。在这种情况下，无法继续处理，必须停止 ECU。集成商可以选择ECU停止的方式，即重置、暂停、重新启动、安全状态等。

void EcuM_ErrorHook (uint16 reason);

模块集群 System Services 构成 AUTOSAR Classic Platform 的功能骨干。它包括 BSW Mode Manager（BswM）、ECU State Manager（EcuM）、Watchdog Manager（WdgM）以及底层 Watchdog Driver（Wdg）SWS_ECUStateManager 第35页。这些模块共同控制 ECU 的完整生命周期，协调底层硬件以及应用运行模式，并确保用于保障功能安全的时间和逻辑程序执行监控 SafetyConceptStatusReport 第15页。

在 AUTOSAR 分层架构中，BswM、EcuM 和 WdgM 位于抽象层和驱动层之上的 System Services 层，而 Watchdog Driver（Wdg）作为 Microcontroller Abstraction Layer（MCAL）的一部分操作看门狗定时器的硬件寄存器 [SWS_Wdg_00106]。其中，EcuM 在灵活形态（EcuM Flex）下充当操作系统启动前或启动后与硬件在早期启动和后期关断序列中的纽带。它不再具有用于应用模式的独立复杂状态机，而是将模式仲裁委托给 BswM SWS_ECUStateManager 第103页。外部诊断标准（如 ISO 14229 的 UDS）和网络管理协议通过定义的 BSW 接口（例如经由 Dcm 的服务 0x28 CommunicationControl）直接接入 BswM 的规则评估中 [SWS_BswM_00048]。

2. 模块间的相互协作与交互路径

集群内部的交互具有明确划分的控制和报告关系。在 ECU Mode Handling 范围内，EcuM 从软件组件（SW-C）接收诸如 RUN 或 POST_RUN 等状态的请求，并通过 [SWS_BswM_91004] 将汇总的仲裁结果转发给 BswM ModeManagementGuide 第34页。由于 EcuM 本身不做出转换决策，BswM 评估配置的逻辑规则，并通过 EcuM_SetState 同步下发目标状态指令给 [SWS_EcuM_04116]。随后 EcuM 通过 RTE 将该状态反映给应用程序，并通过 BswM_EcuM_CurrentState 向 BswM 确认当前执行状态 [SWS_BswM_91003]。

一条并行的交互路径连接 BswM、WdgM 和 Wdg。软件组件和 BSW 模块将达到已定义检查点的情况报告给 WdgM，后者据此确定局部和全局监控状态 SWS_WatchdogManager 第51页。WdgM 通过提供的模式端口提供局部监控的状态变化 [SWS_WdgM_00148]。BswM 根据上级系统状态通过 WdgM_SetMode 切换看门狗管理器的运行模式 [SWS_WdgM_00154]。随后 WdgM 通过看门狗接口（WdgIf）配置看门狗驱动程序（Wdg），并通过 Wdg_SetTriggerCondition 控制硬件触发 [SWS_Wdg_00155]。

3. 同步、可重入性与任务上下文

System Services 的执行确定性地分布在周期性任务级别、异步回调和中断上下文中。模式管理的主要周期性负载由 BswM_MainFunction 承担，它在 OS 任务上下文中由 BSW Scheduler（SchM）调用，并处理所有需要延迟评估的规则 [SWS_BswM_00053]。若出现需立即评估规则的事件，则直接在调用方 BSW 指示或 SW-C API 上下文中同步处理 ModemanagementGuide 第31页。

在多核系统中，规范要求对资源进行严格分配。BswM_Init 被设计为条件可重入，以支持每个分区或处理器内核的独立实例化 [SWS_BswM_00002]。在休眠和保持阶段，EcuM 保留核独占的 OS 资源（RES_AUTOSAR_ECUM_<core#>），以确保主核与从核之间的同步 [SWS_EcuM_03010]。通过 EcuM_AL_DriverInitZero 和 EcuM_AL_DriverInitOne 进行的驱动程序初始化在每个核上分别调用，且仅初始化核本地的 MCAL 模块 [SWS_EcuM_04145]。通过 EcuM_ClearWakeupEvent 清除唤醒事件显式为不可中断的，且允许从任务上下文和中断上下文发起 [SWS_EcuM_02807]。

4. 典型生命周期与运行模式

ECU 的生命周期在规范上划分为 STARTUP、UP、SHUTDOWN 和 SLEEP 阶段 [SWS_EcuM_91005]。STARTUP 阶段在操作系统启动前于序列 StartPreOS 中开始，伴随 EcuM_Init 的调用、复位原因评估以及通过 EcuM_DeterminePbConfiguration 加载 Post-Build 配置 AUTOSAR_SWS_ECUStateManager 第38页。通过 StartOS 将控制权移交给操作系统后，EcuM 在 StartPostOS 中初始化 SchM 以及 BswM [SWS_EcuM_02934]。随后 BswM 接管控制权并启动其余的 BSW 模块以及应用程序。

在运行状态（UP 阶段）下，EcuM 和 BswM 管理模式 RUN 和 POST_RUN 以及可选的 Alarm Clock 服务 SWS_ECUStateManager 第75页。在切换至休眠状态（SLEEP）时，集群在结构上区分 HALT（停止 CPU）和 POLL（降低 CPU 时钟）SWS_ECUStateManager 第54页。在此之前，调用 WdgM_DeInit 会去初始化 Watchdog Manager 并调整触发超时，以防止在关机过程中发生意外复位 [SWS_WdgM_00261]。在轮询序列中，EcuM 会阻塞在带有周期性调用 EcuM_SleepActivity 和 EcuM_CheckWakeupHook 的检查循环中，直到检测到唤醒事件 [SWS_EcuM_03020]。

检测到的唤醒事件经历从 ECUM_WKSTATUS_NONE 到 PENDING，再到 VALIDATED 或 EXPIRED 的严格状态管理 [SWS_EcuM_04091]。EcuM 通过 BswM_EcuM_CurrentWakeup 将每次状态变更同步指示给 BswM [SWS_BswM_00131]。唤醒验证可防止瞬态总线干扰，并通过可配置的验证定时器监控时间窗口 [SWS_EcuM_04004]。若生命周期在 SHUTDOWN 中结束，OffPreOS 会停用 BswM 和 SchM，随后 OffPostOS 通过诸如 EcuM_AL_Reset 或 EcuM_AL_SwitchOff 等集成标注（callout）复位 ECU 或切断电源 AUTOSAR_SWS_ECUStateManager 第49页。

5. 错误处理、DET 跟踪与降级

为了检测运行时和配置错误，该集群集成了向 Default Error Tracer（Det）的标准报告机制。若某个实体尝试通过 EcuM_ReleasePOST_RUN 发起未经事先请求的释放，EcuM 会向 Det 报告开发错误 ECUM_E_MISMATCHED_RUN_RELEASE [SWS_EcuM_03026]。同一用户的重复请求由 ECUM_E_MULTIPLE_RUN_REQUESTS 捕获 [SWS_EcuM_03025]。同样，WdgM 监控未初始化状态下的 API 调用，并在初始化完成前调用服务时报告 WDGM_E_UNINIT [SWS_WdgM_00288]。

安全监控基于 WdgM 的三级功能检查（Alive Supervision、Deadline Supervision 和逻辑控制流监控）SafetyConceptStatusReport 第47页。如果监控错误导致违反容错限制，全局监控状态会从 WDGM_GLOBAL_STATUS_OK 经由 FAILED 变为 WDGM_GLOBAL_STATUS_EXPIRED，最终变为 STOPPED [SWS_WdgM_00387]。在此状态下，WdgM 将所有看门狗驱动程序的触发条件设置为 0，从而使硬件看门狗立即复位微控制器 [SWS_WdgM_00232]。对于受控的紧急复位，WdgM 提供服务 WdgM_PerformReset，该服务停止持续补喂看门狗并强制执行硬件复位 [SWS_WdgM_00264]。为了在较长的休眠阶段后提供安全防护，EcuM 还通过 EcuM_CheckRamHash 检查易失性存储器的一致性，以拦截在 RAM 损坏时的异常重启 [SWS_EcuM_02921]。
