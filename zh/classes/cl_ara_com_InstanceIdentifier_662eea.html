类 ara::com::InstanceIdentifier

[SWS_CM_00302] Upstream: RS_CM_00101, RS_CM_00102, RS_AP_00114, RS_AP_00127

class InstanceIdentifier {...};

Unique identifier of a specific AdaptivePlatformServiceInstance, to distinguish different instances of exactly the same service. ara::com::InstanceIdentifier satisfies the [equalitycomparable], [lessthancomparable] and [copyassignable] requirements as per [30] to allow for logging of ara::com::InstanceIdentifiers as well as storing and managing ara::com::InstanceIdentifiers by the application (see operators). ara:: com::InstanceIdentifier does not contain a fully qualified name, which would also have service type information.

用于唯一定义技术服务实例，以区分同类服务。

类 ara::com::InstanceIdentifier 表示 AUTOSAR Adaptive Platform 中具体服务实例的唯一技术标识符，并支持通过特定的通信绑定进行寻址 (AUTOSAR_AP_EXP_ARAComAPI 第22页 §4.1 “InstanceIdentifier class”)。作为可序列化的值类型，它可以从字符串生成、进行比较并在容器中管理 ([SWS_CM_11520]、[SWS_CM_11523])。虽然标准应用程序主要使用抽象模型标识符，但直接使用该技术标识符适用于多绑定（Multi-Binding）和故障转移（Fail-over）解决方案等特殊情况 (AUTOSAR_AP_EXP_ARAComAPI 第25页 “InstanceIdentifier Usage”)。

上下文

类 ara::com::InstanceIdentifier 用于唯一定义 Adaptive Platform 上的具体服务实例（AdaptivePlatformServiceInstance），以区分完全相同服务的不同实例。它封装了所选通信绑定的技术特定寻址，但特意不包含带有服务类型信息的完全限定名称。对于常规软件开发人员而言，与 ara::com::InstanceIdentifier 的直接交互通常已被抽象化：虽然在软件组件模型中主要通过 ara::core::InstanceSpecifier 使用逻辑名称 (AUTOSAR_AP_EXP_ARAComAPI 第23页 §4.2 “InstanceSpecifier class”)，但集成商会通过清单文件将这些名称分配给技术绑定及其各自的实例 ID (AUTOSAR_AP_EXP_ARAComAPI 第23页 §4.2 “InstanceSpecifier class”)。

在所谓的 Multi-Binding 框架下，单个抽象标识符可以映射到多个技术绑定。因此，通过 ResolveInstanceIDs() 进行解析会返回一个聚合了多个 ara::com::InstanceIdentifier 的 ara::com::InstanceIdentifierContainer (ARAComAPI 第1页 “Figure 6.6: InstanceIdentifier Resolution”、AUTOSAR_AP_EXP_ARAComAPI 第24页 §4.3 “InstanceSpecifier Resolution”)。这使得服务器（Skeleton）能够通过不同的传输技术为客户端提供服务，或者允许客户端（Proxy）实现故障转移路径 (ARAComAPI 第1页 “Figure 6.6: InstanceIdentifier Resolution”)。

生命周期

ara::com::InstanceIdentifier 的实例具有完整的值语义。它们满足 ISO/IEC 14882:2014 的 equalitycomparable、lessthancomparable 以及 copyassignable 要求，从而可以在标准容器中进行管理、排序和记录。该类提供以下构造函数和生命周期函数：

  • 通过带有 noexcept 的静态工厂方法 Create ([SWS_CM_11520]) 进行无异常创建。
  • 基于字符串表示的显式构造函数 ([SWS_CM_11521])，该函数明确不具备异常安全性（not exception safe）。
  • 拷贝构造函数 ([SWS_CM_00056]) 和移动构造函数 ([SWS_CM_00053])，均指定为 noexcept。
  • 拷贝赋值运算符 ([SWS_CM_11525]) 和移动赋值运算符 ([SWS_CM_00054])，分别带有 noexcept。
  • 用于相等性和顺序检查的比较运算符 operator== ([SWS_CM_11523]) 和 operator< ([SWS_CM_11524])。
  • 带有 noexcept 的析构函数 ~InstanceIdentifier() ([SWS_CM_00055])。

通过字符串构造函数与方法 toString() ([SWS_CM_11522]) 的协同作用，该类是可序列化的 (AUTOSAR_AP_EXP_ARAComAPI 第22页 §4.1 “InstanceIdentifier class”)。这允许持久化、传输并在以后重用标识符。由于结构完全取决于中间件产品和绑定，因此应用逻辑不对序列化字符串进行内容解释（自省）(AUTOSAR_AP_EXP_ARAComAPI 第22页 §4.1 “InstanceIdentifier class”)。

使用路径

由于 ara::com 为常用方法提供了直接接受 ara::core::InstanceSpecifier 的重载，因此手动处理 ara::com::InstanceIdentifier 主要面向专用绑定或针对性故障转移等高级用例 (AUTOSAR_AP_EXP_ARAComAPI 第25页 “InstanceIdentifier Usage”)。典型流程分为以下步骤：

  1. 解析：应用程序使用 ResolveInstanceIDs() 将抽象模型标识符转换为分配的技术实例标识符 (AUTOSAR_AP_EXP_ARAComAPI 第24页 §4.3 “InstanceSpecifier Resolution”)。
  2. 选择：应用程序从生成的 ara::com::InstanceIdentifierContainer 中选择所需的 ara::com::InstanceIdentifier (ARAComAPI 第1页 “Figure 6.6: InstanceIdentifier Resolution”)。
  3. 服务搜索：将标识符传递给 Proxy 类的静态方法 FindService(ara::com::InstanceIdentifier instance) (ARAComAPI 第103页 “Figure 6.5: Service Discovery”)。
  4. 处理：服务搜索返回一个 ServiceHandleContainer，基于该对象实例化 Proxy (ARAComAPI 第103页 “Figure 6.5: Service Discovery”)。可以通过 GetInstanceId() 查询实例标识符 (AUTOSAR_AP_EXP_ARAComAPI 第30页 “GetInstanceId”)。

时序图：标识符解析以及通过技术 InstanceIdentifier 进行的针对性服务搜索。来源：ARAComAPI 第103页 “Figure 6.5: Service Discovery”、AUTOSAR_AP_EXP_ARAComAPI 第24页 §4.3 “InstanceSpecifier Resolution”

错误场景

在处理 ara::com::InstanceIdentifier 时，尤其需要考虑两种错误情况：

  • 无效的字符串格式 (InvalidInstanceIdentifierStringViolation)：如果将损坏、不合规或重复的序列化标识符传递给 Create ([SWS_CM_11520]) 或构造函数 ([SWS_CM_11521])，则存在此违规行为。解释：虽然无异常工厂方法 Create 预计会通过错误对象报告此情况，但非异常安全的构造函数在发生错误时可能会抛出异常。
  • 解析时缺少映射：如果集成商未在部署清单中为 ara::core::InstanceSpecifier 存储映射，则调用 ResolveInstanceIDs() 将返回一个空列表 (ARAComAPI 第1页 “Figure 6.6: InstanceIdentifier Resolution”、AUTOSAR_AP_EXP_ARAComAPI 第24页 §4.3 “InstanceSpecifier Resolution”)。这通常构成配置错误。
  • 缺少服务实例：如果未在 Skeleton 端为指定的标识符执行相应的 OfferService()，则由 FindService 提供的 ServiceHandleContainer 保持为空 (ARAComAPI 第103页 “Figure 6.5: Service Discovery”)。

使用

静态函数 ara::com::InstanceIdentifier::Create（[SWS_CM_11520]）代表了用于实例化 InstanceIdentifier 的无异常工厂方法。它接收一个类型为 ara::core::StringView 的字符串（serializedFormat）作为同步输入参数，并返回 InstanceIdentifier 的实例（[SWS_CM_11520]）。序列化字符串的具体格式未作标准化，而是由相应通信管理驱动程序进行特定于供应商的规定（[SWS_CM_00088]，AUTOSAR_AP_SWS_CommunicationManagement §7.5.22.1 “Service Identifier Data Types”）。

错误处理

该函数被指定为 noexcept 且为异常安全（[SWS_CM_11520]）。如果传入的字符串损坏、不合规或在系统中重复，则规范定义了违规 InvalidInstanceIdentifierStringViolation（[SWS_CM_11520]）。由于签名未返回诸如 ara::core::Result 之类的错误类型，因此推测违规大概率会通过平台内部错误处理或终止进程来拦截（解释）。

并发性与限制

ara::com::InstanceIdentifier 用于在系统中唯一标识并区分同一服务类型的不同实例（[SWS_CM_00302]）。调用方必须确保所提供的字符串代表有效且全系统唯一的实例，因为重复项会被明确视为违规（[SWS_CM_11520]）。

相互作用

生成的实例标识符与方法 ToString()（[SWS_CM_11522]）相对应，可通过该方法重新读出字符串表示（[SWS_CM_00088]）。此外，该对象用于寻址整个系统中的具体服务实例（[SWS_CM_00302]）。
