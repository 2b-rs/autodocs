上下文

结构体 ara::diag::DataIdentifierConcurrencyType 定义了提供 Data Identifier（DID）的诊断端口接口的并发特性（[SWS_DM_00936]、AUTOSAR_AP_SWS_Diagnostics §8.8.2 “Struct: DataIdentifierConcurrencyType”）。在 AUTOSAR Adaptive Platform 内，该结构体充当 Diagnostic Management（DM）与相应应用程序实例之间的接口约定。它告知 DM 应用程序侧的读取与写入 API 可以在何种程度上被并发调用。

若无显式的并行性允许，DM 将必须严格串行化对同一端口实例的所有访问。通过 DataIdentifierConcurrencyType，Adaptive Application 可以明确指示其内部数据结构已针对并发读取或写入访问进行了设计。

生命周期

DataIdentifierConcurrencyType 被设计为基本数据容器（struct），并通过头文件 ara/diag/concurrency.h 包含（[SWS_DM_00937]、[SWS_DM_00938]、[SWS_DM_00939]）。该结构体没有独立的内部状态机，也没有动态的生命阶段。所有属性均实现为公共变量，并默认采用保守预设值 ConcurrencyType::kNotConcurrent：

  • read：定义纯读操作的并发类型（[SWS_DM_00937]、AUTOSAR_AP_SWS_Diagnostics §8.8.2.1.1 “read”）。
  • write：确定关于同时写操作的行为（[SWS_DM_00938]、AUTOSAR_AP_SWS_Diagnostics §8.8.2.1.3 “write”）。
  • readWrite：规定读写方法是否允许同时调用；仅在 ConcurrencyType::kConcurrent 时，DM 才允许并发调用读写 API（[SWS_DM_00939]、AUTOSAR_AP_SWS_Diagnostics §8.8.2.1.2 “readWrite”）。

就生命周期而言，实例对象通常在 DID 端口初始化期间创建。解释：该对象可能在向 DM 提供端口实例时作为配置参数传递，并在端口可用期间保持有效且不发生变更。

使用路径

该结构体的典型使用分为 Adaptive Application 的配置以及随后 DM 的评估：

  1. 端口属性配置：应用程序实例化 DataIdentifierConcurrencyType。只要查询和修改 DID 的方法实现了线程安全，相应成员（例如 read 或 readWrite）就会被设置为 ConcurrencyType::kConcurrent。若某个字段保持不变，则自动采用默认配置 ConcurrencyType::kNotConcurrent（[SWS_DM_00937]、[SWS_DM_00938]、[SWS_DM_00939]）。
  2. 与端口关联：已配置的结构体被分配给与 DataIdentifier 相关的端口接口（[SWS_DM_00936]）。
  3. Diagnostic Management 执行：当有关该 DID 的诊断请求（例如读取或写入请求）到达时，DM 以该结构体的值为依据：
    • 若 readWrite 设置为 ConcurrencyType::kConcurrent，则允许 DM 并行于正在进行的读操作发出挂起的写操作（[SWS_DM_00939]）。
    • 若 readWrite 为 ConcurrencyType::kNotConcurrent，则 DM 会等待正在进行的读操作完全结束，才执行写方法（反之亦然）。
    • 以相同方式，变量 read（[SWS_DM_00937]）和 write（[SWS_DM_00938]）决定是否允许同类操作同时运行。

错误场景

由于 DataIdentifierConcurrencyType 是不包含逻辑方法的纯数据结构，因此不存在特定的错误码（ara::core::ErrorCode）或异常路径。错误来源主要产生于配置与实际线程安全之间的差异：

  • 异步与同步错误：若将 readWrite 或 write 配置为 ConcurrencyType::kConcurrent（[SWS_DM_00939]、[SWS_DM_00938]），而底层应用程序逻辑未配备锁机制，则推测会导致应用程序数据中出现数据不一致或竞态条件。
  • 意外串行化：若在应用程序本可支持并发访问的情况下保留了默认设置 ConcurrencyType::kNotConcurrent，DM 将按顺序处理请求。这虽然能防止数据冲突，但在并发诊断请求时可能会导致更高的响应延迟。
