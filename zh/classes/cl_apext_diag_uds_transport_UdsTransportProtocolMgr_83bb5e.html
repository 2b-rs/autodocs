上下文

类 apext::diag::uds_transport::UdsTransportProtocolMgr 构成了诊断服务器实例（DM Core 或 Session Layer）与各种 UDS 传输协议（如 DoIP 或 CAN）之间协调的标准化接口（AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”）。具体的传输协议被实现为抽象基类 apext::diag::uds_transport::UdsTransportProtocolHandler 的子类（[SWS_DM_00315]、AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”）。

在这种中介功能中，管理器类主要与三个组件交互：

  • UDS Transport Protocol Handler (Transport Layer): 通知传入消息的开始（[SWS_DM_00309]），传递完全接收的请求（[SWS_DM_00311]），确认发送作业（[SWS_DM_00312]），并通知通道及状态更改（[SWS_DM_00313]、[SWS_DM_00314]）。
  • Diagnostic Server Core (Session Layer): 接收有效的 UDS 请求以进行进一步的诊断处理，并管理消息缓冲区的分配（[SWS_DM_00309]、[SWS_DM_00311]）。
  • 周期性传输处理程序：传递有关成功传输周期性消息链的确认（[SWS_DM_01069]）。

上下文图：UdsTransportProtocolMgr 与传输处理程序及 Session Layer 的相互作用。来源：AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”、[SWS_DM_00309]、[SWS_DM_00311]、[SWS_DM_00314]。

生命周期

传输协议实现的生命周期由 Diagnostic Manager (DM) 按照从构造、初始化到停止的严格定义顺序进行控制（[SWS_DM_00329]、AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”）。类 UdsTransportProtocolMgr 声明了一个默认虚析构函数（[SWS_DM_01524]）。

在运行过程中，停用阶段是同步的：当处理程序响应停止操作关闭其网络连接并释放资源后，会通过指定其 handlerId 的回调 HandlerStopped 通知管理器（[SWS_DM_00314]）。

就内存和所有权关系而言，消息缓冲区遵循明确的转移模型：在传输开始时，DM-Core 创建消息对象并将其指针传递给处理程序（[SWS_DM_00309]）。完全接收后，处理程序通过 HandleMessage 使用 unique_ptr 语义将消息的所有权转移回通用 DM-Core（[SWS_DM_00311]）。

所有接口方法均被指定为异常安全（noexcept），但非线程安全（not thread-safe）（[SWS_DM_00309]、[SWS_DM_00311]、[SWS_DM_00312]）。Interpretation: 因此，对管理器的调用大概需要由调用的传输和会话组件进行同步。

使用路径

处理传入 UDS 诊断请求的常规流程分为以下步骤：

  1. 消息指示：如果处理程序支持指示，它会在第一批数据到达时调用 IndicateMessage（[SWS_DM_00309]）。在此过程中会传输源地址和目标地址、寻址类型（物理或功能）、预期的总大小以及 GlobalChannelIdentifier（[SWS_DM_09021]）。通过 payloadInfo 已经可以传递最初的几个字节，以便 DM 能够尽早识别例如功能性 Tester-Present 请求（[SWS_DM_00309]）。
  2. 缓冲区提供：管理器返回由 IndicationResult 和已分配的 UdsMessagePtr 组成的一对（[SWS_DM_00309]）。如果结果为 IndicationResult::kIndicationOk（[SWS_DM_00384]），处理程序将用传入的数据填充缓冲区。
  3. 移交给 Session Layer：完全接收后，处理程序通过 HandleMessage 将消息传递给管理器（[SWS_DM_00311]），这对应于符合 ISO 14229-2 的服务 T_Data.ind。该调用立即返回；进一步的评估在 Session Layer 中异步进行（[SWS_DM_00311]）。
  4. 发送确认：对于已发送的 UDS 响应，处理程序随后通过 TransmitConfirmation 确认成功，结果为 kTransmitOk（[SWS_DM_00312]、[SWS_DM_00307]），对应于符合 ISO 14229-2 的 T_Data.con。

顺序图：UDS 消息接收从指示到异步移交给 Session Layer 的流程。来源：[SWS_DM_00309]、[SWS_DM_00311]、[SWS_DM_00384]。

错误场景

传输或缓冲区分配期间的错误条件通过定义的状态值和错误接口进行捕获：

  • 指示失败：如果 DM-Core 无法接受指示的消息，它将通过枚举 IndicationResult 报告此情况（[SWS_DM_00309]、[SWS_DM_00384]）：
    • kIndicationOccupied：服务器或诊断会话当前正忙（[SWS_DM_00384]）。
    • kIndicationOverflow：传输的消息大小超出了缓冲区容量（[SWS_DM_00384]）。
    • kIndicationUnknownTargetAddress：寻址的目标地址未配置（[SWS_DM_00384]）。
  • 接收中止：如果在成功 IndicateMessage 后发生连接中断或传输错误，处理程序将调用 NotifyMessageFailure（[SWS_DM_00310]）。先前获取的 UdsMessage 对象将返回给 DM，而不会发生对 HandleMessage 的调用（[SWS_DM_00310]）。
  • 发送传输错误：如果出站消息在网络层无法发送，处理程序将通过 TransmitConfirmation 报告结果 TransmissionResult::kTransmitFailed（[SWS_DM_00312]、[SWS_DM_00307]）。
  • 通道重新激活：在暂时丢失连接后，如果之前请求了该通知（[SWS_DM_00313]），则处理程序通过带有 GlobalChannelIdentifier 的 ChannelReestablished 通知通道的重新可用性（[SWS_DM_00313]、[SWS_DM_09021]）。

Hands over a valid received UDS message (currently this is only a request type) from the Transport Layer to the Session Layer. This corresponds to T_Data.ind of Figure 2 from ISO 14229-2[25]. <h4>上下文</h4>
<p>类 <code>apext::diag::uds_transport::UdsTransportProtocolMgr</code> 构成了诊断服务器实例（DM Core 或 Session Layer）与各种 UDS 传输协议（如 DoIP 或 CAN）之间协调的标准化接口（<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”</a>）。具体的传输协议被实现为抽象基类 <code>apext::diag::uds_transport::UdsTransportProtocolHandler</code> 的子类（<a class="spec-record-ref" data-req="SWS_DM_00315" href="../spec/record.html?id=SWS_DM_00315">[SWS_DM_00315]</a>、<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”</a>）。</p>
<p>在这种中介功能中，管理器类主要与三个组件交互：</p>
<ul>
<li><strong>UDS Transport Protocol Handler (Transport Layer):</strong> 通知传入消息的开始（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>），传递完全接收的请求（<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>），确认发送作业（<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>），并通知通道及状态更改（<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>、<a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>）。</li>
<li><strong>Diagnostic Server Core (Session Layer):</strong> 接收有效的 UDS 请求以进行进一步的诊断处理，并管理消息缓冲区的分配（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>、<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>）。</li>
<li><strong>周期性传输处理程序：</strong>传递有关成功传输周期性消息链的确认（<a class="spec-record-ref" data-req="SWS_DM_01069" href="../spec/record.html?id=SWS_DM_01069">[SWS_DM_01069]</a>）。</li>
</ul>

<h4>生命周期</h4>
<p>传输协议实现的生命周期由 Diagnostic Manager (DM) 按照从构造、初始化到停止的严格定义顺序进行控制（<a class="spec-record-ref" data-req="SWS_DM_00329" href="../spec/record.html?id=SWS_DM_00329">[SWS_DM_00329]</a>、<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”</a>）。类 <code>UdsTransportProtocolMgr</code> 声明了一个默认虚析构函数（<a class="spec-record-ref" data-req="SWS_DM_01524" href="../spec/record.html?id=SWS_DM_01524">[SWS_DM_01524]</a>）。</p>
<p>在运行过程中，停用阶段是同步的：当处理程序响应停止操作关闭其网络连接并释放资源后，会通过指定其 <code>handlerId</code> 的回调 <code>HandlerStopped</code> 通知管理器（<a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>）。</p>
<p>就内存和所有权关系而言，消息缓冲区遵循明确的转移模型：在传输开始时，DM-Core 创建消息对象并将其指针传递给处理程序（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>）。完全接收后，处理程序通过 <code>HandleMessage</code> 使用 <code>unique_ptr</code> 语义将消息的所有权转移回通用 DM-Core（<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>）。</p>
<p>所有接口方法均被指定为异常安全（<code>noexcept</code>），但非线程安全（<em>not thread-safe</em>）（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>、<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>、<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>）。Interpretation: 因此，对管理器的调用大概需要由调用的传输和会话组件进行同步。</p>

<h4>使用路径</h4>
<p>处理传入 UDS 诊断请求的常规流程分为以下步骤：</p>
<ol>
<li><strong>消息指示：</strong>如果处理程序支持指示，它会在第一批数据到达时调用 <code>IndicateMessage</code>（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>）。在此过程中会传输源地址和目标地址、寻址类型（物理或功能）、预期的总大小以及 <code>GlobalChannelIdentifier</code>（<a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>）。通过 <code>payloadInfo</code> 已经可以传递最初的几个字节，以便 DM 能够尽早识别例如功能性 Tester-Present 请求（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>）。</li>
<li><strong>缓冲区提供：</strong>管理器返回由 <code>IndicationResult</code> 和已分配的 <code>UdsMessagePtr</code> 组成的一对（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>）。如果结果为 <code>IndicationResult::kIndicationOk</code>（<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>），处理程序将用传入的数据填充缓冲区。</li>
<li><strong>移交给 Session Layer：</strong>完全接收后，处理程序通过 <code>HandleMessage</code> 将消息传递给管理器（<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>），这对应于符合 ISO 14229-2 的服务 <code>T_Data.ind</code>。该调用立即返回；进一步的评估在 Session Layer 中异步进行（<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>）。</li>
<li><strong>发送确认：</strong>对于已发送的 UDS 响应，处理程序随后通过 <code>TransmitConfirmation</code> 确认成功，结果为 <code>kTransmitOk</code>（<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>、<a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>），对应于符合 ISO 14229-2 的 <code>T_Data.con</code>。</li>
</ol>

<h4>错误场景</h4>
<p>传输或缓冲区分配期间的错误条件通过定义的状态值和错误接口进行捕获：</p>
<ul>
<li><strong>指示失败：</strong>如果 DM-Core 无法接受指示的消息，它将通过枚举 <code>IndicationResult</code> 报告此情况（<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>、<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>）：
  <ul>
  <li><code>kIndicationOccupied</code>：服务器或诊断会话当前正忙（<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>）。</li>
  <li><code>kIndicationOverflow</code>：传输的消息大小超出了缓冲区容量（<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>）。</li>
  <li><code>kIndicationUnknownTargetAddress</code>：寻址的目标地址未配置（<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>）。</li>
  </ul>
</li>
<li><strong>接收中止：</strong>如果在成功 <code>IndicateMessage</code> 后发生连接中断或传输错误，处理程序将调用 <code>NotifyMessageFailure</code>（<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>）。先前获取的 <code>UdsMessage</code> 对象将返回给 DM，而不会发生对 <code>HandleMessage</code> 的调用（<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>）。</li>
<li><strong>发送传输错误：</strong>如果出站消息在网络层无法发送，处理程序将通过 <code>TransmitConfirmation</code> 报告结果 <code>TransmissionResult::kTransmitFailed</code>（<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>、<a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>）。</li>
<li><strong>通道重新激活：</strong>在暂时丢失连接后，如果之前请求了该通知（<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>），则处理程序通过带有 <code>GlobalChannelIdentifier</code> 的 <code>ChannelReestablished</code> 通知通道的重新可用性（<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>、<a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>）。</li>
</ul>
