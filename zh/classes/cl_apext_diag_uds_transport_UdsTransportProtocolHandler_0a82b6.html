上下文

类 apext::diag::uds_transport::UdsTransportProtocolHandler 是 AUTOSAR Adaptive 的 Diagnostic Management (DM) 中用于特定和专有 UDS 传输协议插件的抽象基类（AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”、[SWS_DM_00315]）。它将通用诊断内核与具体传输网络及传输层（如 DoIP 或基于 CAN 的协议）的特性解耦。

传输处理程序主要与三个参与方进行交互：

  • Diagnostic Management Core: DM 管理处理程序的整个生命周期，并通过管理器引用 apext::diag::uds_transport::UdsTransportProtocolMgr 提供用于状态和数据指示的对端（[SWS_DM_09015]、[SWS_DM_09025]）。
  • 网络层与诊断客户端：该插件负责处理与车载外部或内部诊断测试仪的物理或逻辑数据交换（[SWS_DM_00326]、[SWS_DM_00351]）。
  • 周期性处理程序（可选）：如果相应传输协议支持周期性传输，则处理程序通过 GetPeriodicHandler() 提供对 UdsTransportProtocolPeriodicHandler 的引用（[SWS_DM_01068]）。

生命周期

传输协议实现的生命周期由 DM 严格控制（AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”、[SWS_DM_00329]）。创建通过构造函数 UdsTransportProtocolHandler(handlerId, transportProtocolMgr) 进行，其中 DM 向处理程序分配类型为 UdsTransportProtocolHandlerID 的唯一标识符以及对关联 UdsTransportProtocolMgr 的引用（[SWS_DM_09015]、[SWS_DM_09025]）。分配的 ID 可随时通过 GetHandlerID() 查询（[SWS_DM_00325]）。该构造函数被标明为线程安全（[SWS_DM_09015]）。

为了将开销较大的协议初始化与构造函数解耦，DM 随后调用 Initialize()（[SWS_DM_00319]、[SWS_DM_00329]）。在 InitializationResult::kInitializeOk 成功返回之前，除 GetPeriodicHandler() 外，DM 不得调用该处理程序的任何其他方法（[SWS_DM_01746]、[SWS_DM_09017]）。成功初始化后，DM 通过 Start() 启动协议（[SWS_DM_00322]）。由于 Start() 是异步执行的，DM 可以并行启动多个处理程序，以最大程度缩短启动时间（[SWS_DM_00322]）。

当 DM 应用程序转换到状态 ApplicationState.kTerminating 时，它会调用 Stop()（AUTOSAR_AP_SWS_Diagnostics §7.1.1.1、[SWS_DM_00333]、[SWS_DM_00323]）。DM 等待处理程序通过 UdsTransportProtocolMgr::HandlerStopped(handlerId) 确认停止（[SWS_DM_00340]）。从 Stop() 返回后，处理程序插件不得调用管理器上的任何其他方法——唯一的例外是确认 HandlerStopped()（[SWS_DM_01741]、[SWS_DM_00323]）。随后的析构通过虚析构函数进行（[SWS_DM_09016]）。

状态图：UDS 传输协议处理程序的生命周期阶段与转换条件。来源：[SWS_DM_00329]、[SWS_DM_00319]、[SWS_DM_01746]、[SWS_DM_01745]、[SWS_DM_00322]、[SWS_DM_00323]、[SWS_DM_00340]。

使用路径

在运行过程中，处理程序负责 UDS 消息的双向交换：

  1. 消息接收（指示）：一旦在某个通道上收到新的 UDS 消息，并且源地址、目标地址、寻址类型（物理或功能）、总消息长度以及首批有效负载数据字节（对于大于一个字节的消息至少两个字节）已知，插件就会调用 UdsTransportProtocolMgr::IndicateMessage(...)（AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 “Indication of UDS message reception”、[SWS_DM_00342]、[SWS_DM_00330]）。在此，处理程序在参数 globalChannelId 中传递通道标识（AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”）。
  2. 消息发送（传输）：DM 通过相同的处理程序和相同的通道发回相应的 UDS 诊断响应（AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”、[SWS_DM_00348]）。为此，它调用 Transmit(message, channelId)（[SWS_DM_00327]）。消息以类似 std::unique_ptr 的方式作为 UdsMessageConstPtr 传递给处理程序。
  3. 发送确认：一旦消息通过网络发送完毕（或发生错误），处理程序必须通过 UdsTransportProtocolMgr::TransmitConfirmation(result, message) 将 message 的所有权归还给 DM（[SWS_DM_00327]）。在此过程中，结果作为 kTransmitOk 或 kTransmitFailed 进行传输（AUTOSAR_AP_SWS_Diagnostics §7.1.1.3、[SWS_DM_00351]）。

另一个特定的使用路径是在电子控制单元复位后恢复通道（复位后带有肯定响应的 UDS 服务 0x11）：在此，DM 在重启前调用 NotifyReestablishment(channelId)（[SWS_DM_00326]）。插件对连接参数（例如 IP 地址和端口）进行持久化存储。通过 Start() 重新启动后，插件会识别出相同诊断客户端的重新连接，并通过 UdsTransportProtocolMgr::ChannelReestablished(...) 通知 DM（[SWS_DM_00326]、[SWS_DM_01744]）。

时序图：UDS 消息接收、响应传输及随后的确认。来源：[SWS_DM_00342]、[SWS_DM_00348]、[SWS_DM_00327]、[SWS_DM_00351]。

错误场景

该接口处理各种异常和错误情况：

  • 初始化失败：如果 Initialize() 返回值 InitializationResult::kInitializeFailed（[SWS_DM_09017]），DM 将完全中止该传输协议的启动过程，并且不再在该实例上调用任何其他方法（[SWS_DM_01745]）。
  • 不支持周期性传输：如果具体协议不支持周期性传输，则对 GetPeriodicHandler() 的调用将返回带有错误代码 kConfigurationMismatch 的 ara::core::Result（[SWS_DM_01068]）。
  • 拒绝通道恢复：如果插件无法满足对通道的持久预留（例如在缺乏非易失性存储能力或映射不稳定的情况下），NotifyReestablishment(channelId) 将返回值 false（[SWS_DM_00326]）。
  • 网络中的传输错误：如果网络层无法发送通过 Transmit() 委托的消息，处理程序必须在 TransmitConfirmation 中传递结果 kTransmitFailed（[SWS_DM_00351]）。未归还缓冲区会导致 DM 中发生资源泄漏。
  • 停止后的时序违规：如果插件在从 Stop() 返回后调用 UdsTransportProtocolMgr 上除 HandlerStopped() 之外的其他方法，则构成对协议时序的违规（[SWS_DM_00323]、[SWS_DM_01741]）。

              函数 NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
