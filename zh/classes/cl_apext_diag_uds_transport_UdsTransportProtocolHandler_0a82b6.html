使用目的

UdsTransportProtocolHandler 是抽象基类，派生出具体的 UDS 传输协议实现作为插件。 DM使用处理程序ID创建Handler，该处理程序在所有实例化实现中都是唯一的，并且对DM提供的UdsTransportProtocolMgr进行引用。 [SWS_DM_00315][SWS_DM_09015][SWS_DM_00330]

生命周期和所有权

DM 按照构建顺序管理生命周期：Initialize()、Start() 和 Stop()。启动前必须调用Initialize；只有在kInitializeOk之后，DM才允许调用GetPeriodicHandler()以外的方法。对于 kInitializeFailed，DM 完成该处理程序的初始化，并且不会调用任何其他方法。 [SWS_DM_00329] [SWS_DM_00319] [SWS_DM_01746] [SWS_DM_01745]

Start()异步启动协议处理，返回后可以继续。 Transmit()和Stop()仅在比赛开始后才允许。 Stop之后，插件不允许调用除HandlerStopped()之外的任何其他管理器方法； DM 在最终终止之前等待这个 Callback 以及关联的处理程序 ID。 [SWS_DM_00322] [SWS_DM_01742] [SWS_DM_01743] [SWS_DM_00323] [SWS_DM_01741] [SWS_DM_00340]

与其他班级的互动

Transmit() 在通道上发送UdsMessageConstPtr。然后处理程序使用 UdsTransportProtocolMgr::TransmitConfirmation() 返回该指针以表示使用完成。如果支持定期传输，则GetPeriodicHandler()提供对定期处理程序的引用，否则kConfigurationMismatch。 [SWS_DM_00327][SWS_DM_01068]

NotifyReestablishment() 注册通道的恢复通知。如果Handler接受请求，则仅从下次出发到下一站有效；当通道再次可用时，Handler 通过ChannelReestablished() 报告此情况。 [SWS_DM_00326][SWS_DM_00356][SWS_DM_00357][SWS_DM_00358]

限制

抽象操作是异常安全的，但不是线程安全的。如果诊断对话被取消，则服务处理将在响应传输开始之前终止，并且不会为此响应调用 Transmit()。 [SWS_DM_00319][SWS_DM_00322][SWS_DM_00323][SWS_DM_00327][SWS_DM_00279]

函数 NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168

virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;

Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().

Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).

The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.

The general expectation is:

If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a

stable bijective mapping!

Small example:

The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.

Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:

• NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.

If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
