上下文

数据结构 ara::diag::TimeBased 表示 AUTOSAR Adaptive Platform 的 Diagnostic Management 中基于时间的消抖算法的配置参数（[SWS_DM_00539]、AUTOSAR_AP_SWS_Diagnostics §8.41.3 “Struct: TimeBased”）。它通过头文件 ara/diag/monitor_types.h 提供，并定义了时间限值 failedMs（[SWS_DM_00629]）以及 passedMs（[SWS_DM_00630]）。

在系统体系中，ara::diag::TimeBased 充当特定于应用的故障监控与 Diagnostic Management (DM) 之间的连接纽带。诊断应用功能利用该结构向类 ara::diag::Monitor 的构造函数传递基于时间的故障判定所需的阈值 ([SWS_DM_00550], AUTOSAR_AP_SWS_Diagnostics §8.40.1.1.2.3 “Monitor(...)”)。实际的去抖逻辑及内部定时器的维护由 DM 接管，前提是通过 DiagnosticEventToDebounceAlgorithmMapping 为相应事件建模了 DiagEventDebounceTimeBased ([SWS_DM_00015], AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.5.2 “Time-based debouncing”)。DM 根据配置的阈值计算状态 kTestFailed 以及 Fault Detection Counter (FDC) ([SWS_DM_00030])。

上下文图：基于时间的去抖中诊断应用、ara::diag::Monitor 与 Diagnostic Management 之间的交互。来源：[SWS_DM_00015]、[SWS_DM_00539]、[SWS_DM_00550]。

生命周期

作为纯数据结构（POD），ara::diag::TimeBased 不具有独立的动态生命周期，也不管理任何操作系统资源 ([SWS_DM_00539])。该结构通常在特定于应用的诊断 Monitor 的初始化阶段被实例化，填入以毫秒为单位的目标时间值，并通过值传递方式传递给 ara::diag::Monitor 的构造函数 ([SWS_DM_00550])。

解读：由于 ara::diag::TimeBased 仅用作配置容器，其实例在构造函数调用完成后不必保留在应用内存中，而是可以丢弃。时间阈值会在 DM 中持久注册给关联的 Event。在 DM 中维护的去抖定时器的功能生命周期始于系统启动时确定性地初始化为计数值 0 ([SWS_DM_00085])。在多线程场景中，该结构的实例化无需同步；通过在注册之前于初始化线程中本地创建，即可确保线程安全流程。

使用路径

ara::diag::TimeBased 的典型用法分为初始化时的配置以及随后运行时的事件上报：

  1. 配置：应用程序实例化 ara::diag::TimeBased 并设置 failedMs（判定为故障前的持续时间，以毫秒为单位）([SWS_DM_00629]) 与 passedMs（判定为恢复前的持续时间）([SWS_DM_00630])。
  2. Monitor 创建：该结构与 ara::core::InstanceSpecifier 及初始化回调一起传递给 ara::diag::Monitor::Monitor ([SWS_DM_00550])。
  3. 事件监控：在运行时，应用程序通过 ara::diag::Monitor::ReportMonitorAction 上报状态变更 (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.5.2 “Time-based debouncing”)：
    • 若上报 kPrepassed，DM 会启动去抖定时器，以便在 passedMs 超时后将事件判定为 kFinallyHealed ([SWS_DM_00878])。
    • 若上报 kFailed，DM 会将定时器直接设置为 failedMs（或 timeFailedThreshold）的值，并将该事件归类为 kFinallyDefective ([SWS_DM_00033])。
    • 在直接发生 kPassed 时，DM 会将定时器设置为相应的阈值 ([SWS_DM_00036])。
    • 如果存在不稳定的运行工况，可以通过操作 kFreezeDebouncing 暂停去抖 ([SWS_DM_00880])。若在冻结后收到新的上报 kPrepassed 或 kPrefailed，DM 将从冻结时的状态继续运行定时器 ([SWS_DM_00038])。

时序图：参数传递、Monitor 初始化与基于时间的去抖控制之间的交互。来源：[SWS_DM_00038]、[SWS_DM_00550]、[SWS_DM_00878]、[SWS_DM_00880]。

错误场景

在配置和执行基于时间的去抖时，必须注意特定的边界条件和保护机制：

  • 定时器启动限制：在报告 kPrepassed 时，仅当定时器尚未朝恢复方向运行且事件尚未被判定为 kFinallyHealed 时，用于判定为 kFinallyHealed 的定时器才会启动 ([SWS_DM_00878])。无状态变化的重复调用将不起作用。
  • 不支持计数器持久化：对于基于时间的去抖，不支持跨系统启动永久保存定时器值 (debounceCounterStorage is not supported for time-based debouncing) ([SWS_DM_00085])。DM 重启后，定时器始终强制从 0 开始。
  • 冻结请求的限制：通过 kFreezeDebouncing 进行冻结在技术和功能上仅允许用于具有基于时间的去抖的事件 ([SWS_DM_00880])。对于其他去抖方法，DM 将拒绝或不支持该操作。
  • 参数值范围：时间值 failedMs 和 passedMs 的选取必须与上级系统要求保持一致 ([SWS_DM_00629], [SWS_DM_00630])。不合理的小数值或设置为零的值可能会导致故障状态立即翻转。
