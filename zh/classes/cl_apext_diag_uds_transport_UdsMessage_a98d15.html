类 apext::diag::uds_transport::UdsMessage

[SWS_DM_00291] Upstream: RS_Diag_04147

class UdsMessage {...};

class represents an UDS message exchanged between DM generic core (UdsTransport ProtocolMgr) and a specific implementation of UdsTransportProtocolHandler on diagnostic request reception path or diagnostic response transmission path. UdsMessage provides the storage for UDS requests/responses.

Instances of UdsMessage (with optimized resource allocation) are only created by DM generic core, the UdsTransportProtocolHandler can read/write on it.

在 Adaptive 诊断管理器中进行数据交换时用作 UDS 消息的存储和信息载体。

类 apext::diag::uds_transport::UdsMessage 代表在通用诊断核心与传输特定 Handler 之间交换的诊断消息的标准化存储和传输对象。其实例仅由具有优化内存分配的通用核心创建，并通过 UdsMessagePtr 提供 [SWS_DM_09012]。在接收路径中，Handler 从服务 ID 开始填充提供的数据缓冲区，并在附加可能的通道元数据后转发该消息 [SWS_DM_00388]。如果核心因现有负载过高而无法处理消息，则拒绝分配并返回空指针 [SWS_DM_00386]。

上下文

类 apext::diag::uds_transport::UdsMessage 代表在 Diagnostic Management 通用核心（DM Generic Core 即 UdsTransportProtocolMgr）与 UdsTransportProtocolHandler 的特定实现之间交换的 UDS 消息的中心数据和存储对象。它用作传入 UDS 请求与传出 UDS 响应的封装和存储（Storage）。

除有效负载外，UdsMessage 还传输诊断通信的寻址参数：经由 GetSa() [SWS_DM_00297] 的源地址 Address [SWS_DM_00293]、经由 GetTa() [SWS_DM_00298] 的目标地址，以及经由 GetTaType() [SWS_DM_00299] 的地址类型 TargetAddressType（带有 kPhysical 的物理寻址或带有 kFunctional 的功能寻址）[SWS_DM_00296]。此外，还可以经由 AddMetaInfo() 附加通道特定的元信息，例如针对 DoIP 的连接参数 [SWS_DM_00294]，[SWS_DM_00302]。

上下文图：DM 核心、传输 Handler 与 UdsMessage 之间的相互作用。来源：[SWS_DM_09012]、[SWS_DM_00385]、[SWS_DM_00345]

生命周期

UdsMessage 的实例通过优化的资源分配仅由 Diagnostic Management 的通用核心创建。为了防止协议 Handler 进行不受控的实例化，默认构造函数被声明为受保护的（protected）[SWS_DM_09012]。Handler 仅通过类型为 apext::diag::uds_transport::UdsMessagePtr [SWS_DM_00303] 的所有权指针获取对消息对象的访问权，或者对于纯只读访问，通过 apext::diag::uds_transport::UdsMessageConstPtr [SWS_DM_00304]，AUTOSAR_AP_SWS_Diagnostics 第98页 获取。

对象的销毁通过虚析构函数 ~UdsMessage() [SWS_DM_09010] 进行。关于并发性，用于地址信息的查询方法（GetSa、GetTa、GetTaType）是可重入的（reentrant）且异常安全的（noexcept）[SWS_DM_00297]，[SWS_DM_00298]，[SWS_DM_00299]。相反，通过 GetPayload() 访问数据缓冲区以及通过 AddMetaInfo() 添加元数据被归类为非线程安全，因为实现在这些调用期间允许执行缓冲区与资源分配 [SWS_DM_00300]，[SWS_DM_00301]，[SWS_DM_00302]。

使用路径

在接收路径的常规流程中，UdsTransportProtocolHandler 通过 UdsTransportProtocolMgr::IndicateMessage() 向 DM 通告传入的 UDS 请求 [SWS_DM_00385]。如果 DM 准备好接收，它将以状态 kIndicationOk 进行确认，并传递一个最小大小为 1 个字节且具有 DM 所需缓冲区容量的 UdsMessagePtr [SWS_DM_00385]。

随后，协议 Handler 调用非常量方法 GetPayload()，以获取对基础存储区（uds_transport::ByteSpan&）的可写引用 [SWS_DM_00301]。它从服务标识符（SID）开始填充此缓冲区，直到达到 UdsMessage 对象的最大容量或完整消息长度 [SWS_DM_00388]。在可选地经由 AddMetaInfo() [SWS_DM_00302] 补充通道特定元数据后，Handler 通过 UdsTransportProtocolMgr::HandleMessage() 将填充后的对象转发给诊断核心 [SWS_DM_00345]。（解释：在诊断响应的传输路径中，UdsMessage 的提供可能类似地由通用核心执行。）

时序图：接收 UDS 消息时的交互序列。来源：[SWS_DM_00385]、[SWS_DM_00386]、[SWS_DM_00388]、[SWS_DM_00301]、[SWS_DM_00302]、[SWS_DM_00345]

错误场景

如果 DM 无法处理通过 IndicateMessage() 通告的消息（因为其正忙于主动处理同一 Tester-Present 会话的服务），它将返回状态 kIndicationOccupied 以及等于 nullptr 的 UdsMessagePtr [SWS_DM_00386]。在这种情况下，不提供 UdsMessage 并中止接收。同样，未知的目标地址会导致结果 kIndicationUnknownTargetAddress，且消息引用为空指针 AUTOSAR_AP_SWS_Diagnostics 第100页。

填充缓冲区时，协议 Handler 必须注意指定的缓冲区容量：超出 UdsMessage 所提供容量的传入请求将被截断至完整缓冲区大小 [SWS_DM_00388]。此外，从多个线程对 GetPayload() 或 AddMetaInfo() 进行并发、无保护的访问会导致未定义行为，因为这些接口被明确指定为非线程安全（unsafe）[SWS_DM_00300]，[SWS_DM_00301]，[SWS_DM_00302]。

类 apext::diag::uds_transport::UdsMessage 的虚成员函数 AddMetaInfo 用于为诊断报文分配新的元数据 [SWS_DM_00302]。它通常由传输协议插件调用，以向相应的诊断请求附加通道特定附加信息——例如针对 DoIP 的预定义元数据键 AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 “AddMetaInfo”。

使用该接口适用以下框架条件 [SWS_DM_00302]：

  • 调用上下文与头文件：声明通过头文件 apext/diag/uds_transport/uds_message.h 提供，并直接在 UdsMessage 的实例上执行 AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 “AddMetaInfo”。
  • 形参：类型为 MetaInfoMap 的输入参数 metaInfo 传递请求待添加的元信息 [SWS_DM_00302]。
  • 返回值：该同步函数无返回值（void）[SWS_DM_00302]。
  • 错误处理：该操作带有标识符 noexcept，并被指定为异常安全（exception safe）；不存在特定的错误代码 [SWS_DM_00302]。

关于并发性，该方法被声明为非线程安全（thread safety: unsafe）[SWS_DM_00302]。解释：调用方因此可能负责通过外部机制保护对 UdsMessage 的同一实例的并发访问，因为规范未提供内部同步 AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 “AddMetaInfo”。
