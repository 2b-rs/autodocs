上下文

类ara::diag::DataTransferReadByPullHandler用于标准化处理由诸如RequestReadFile或RequestReadDirectory等诊断请求触发的读取数据传输AUTOSAR_AP_SWS_Diagnostics §8.10.2 “Class: DataTransferReadByPullHandler”、[SWS_DM_01506]。它充当诊断框架 AraDiag 与实际应用程序实现之间的接口。

该传输概念基于拉取（Pull）机制：AraDiag 从应用程序实现中按序请求数据块，以便随后将其传输给 UDS 客户端（诊断测试仪）[SWS_DM_01513]。同时，该类在 UDS 传输服务的上下文中封装了文件或目录内容的应用特定提供。

生命周期

对于DataTransferReadByPullHandler的实例，在创建、所有权和销毁方面有着严格的规则：

  • 创建：默认构造函数被声明为protected与noexcept=default [SWS_DM_01507]。解释：由于该类包含纯虚接口方法，且默认构造函数是受保护的，应用软件大概需要实现并实例化其自定义的派生 Handler 类。
  • 不可复制性：复制构造函数[SWS_DM_01509]和复制赋值运算符[SWS_DM_01512]均已被显式删除（=delete）。Handler 专用于唯一次文件传输会话（single file transfer session），且不得被复制AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.2 “Constructors”。
  • 可移动性：移动构造函数[SWS_DM_01508]和移动赋值运算符[SWS_DM_01511]被定义为noexcept=default AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1 “Special Member Functions”，从而支持所有权转移。
  • 销毁条件：析构函数为虚函数且被指定为noexcept=default [SWS_DM_01510]。作为核心不变式，在调用ExitRead()之前，绝不允许销毁实例[SWS_DM_01510]、AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1.2 “Destructor”。
  • 并发性：虚接口方法Read()和ExitRead()被归类为非线程安全（not thread-safe）[SWS_DM_01513]、[SWS_DM_01514]。

使用路径

基于拉取的读取数据传输的典型调用序列包括两个主要阶段：

  1. 拉取读取循环：在传输进行期间，AraDiag 会重复调用 Handler 上的方法Read() [SWS_DM_01513]。在此过程中，AraDiag 会传入一个指向预分配缓冲区的内存视图response_data（类型为ara::core::Span<const ara::core::Byte>），以及meta_info和一个cancellation_handler。应用程序实现负责组织下一个数据块的内容，并将其复制到其中，最多达到该 span 的最大大小[SWS_DM_01513]。
  2. 分块返回：Read()返回一个ara::core::Future<std::uint32_t>。该 Future 将以实际写入缓冲区的字节数完成[SWS_DM_01513]。AraDiag 在 UDS 肯定响应中将这些有效负载数据直接嵌入在blockSequenceCounter之后作为transferResponseParameterRecord [SWS_DM_01513]、AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 “Read”。
  3. 会话结束：一旦所有数据传输完毕或传输应当终止，AraDiag 就会调用ExitRead() [SWS_DM_01514]。传入的参数包括终止原因（类型为DataTransferExitType的exit_type）、整车制造商特定参数（transfer_request_parameter_record）以及元数据和取消处理程序[SWS_DM_01514]。
  4. 事务结束：应用程序通过一个ara::core::Future<ara::core::Vector<ara::core::Byte>>确认会话结束。在肯定确认的情况下，vector 中包含的数据将在服务 ID（SID）之后作为transferResponseParameterRecord放入 UDS 肯定响应中[SWS_DM_01514]、AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 “ExitRead”。只有在此调用之后，才允许销毁该 Handler 实例[SWS_DM_01510]。

时序图：迭代拉取读取及随后的 ExitRead 调用序列。来源：[SWS_DM_01513]、[SWS_DM_01514]、AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 “ExitRead”、AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 “Read”

错误场景

规范针对错误状态和异常情况定义了明确的规定：

  • UDS 错误代码（NRC）：如果在读取数据块或终止传输时发生错误，对应的 Future 不会正常完成。相反，必须根据 ISO 14229-1 使用来自DiagUdsNrcErrc的相应否定响应码（NRC）将该 Future 作为错误状态结束[SWS_DM_01513]、[SWS_DM_01514]。AraDiag 据此生成一条 UDS 否定响应消息。
  • 取消处理：参数cancellation_handler允许应用程序通过cancellation_handler.IsCanceled()主动检查诊断会话是否已被取消[SWS_DM_01513]、[SWS_DM_01514]。或者，可以通过cancellation_handler.SetNotifier()注册一个回调，该回调在框架取消会话时被调用[SWS_DM_01513]、[SWS_DM_01514]。
  • 缓冲区有效期：AraDiag 在Read()中传入的缓冲区response_data以及在ExitRead()中的transfer_request_parameter_record具有有限的生命周期。它们仅在关联的 Promise 被完成或通过cancellation_handler取消处理之前有效[SWS_DM_01513]、[SWS_DM_01514]。
  • 过早销毁：如果在执行ExitRead()之前销毁DataTransferReadByPullHandler的实例，则构成对 API 契约条件的违反[SWS_DM_01510]。
