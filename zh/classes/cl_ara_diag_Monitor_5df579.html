用于执行诊断监控并向 Diagnostic Management 报告状态。

类 ara::diag::Monitor 提供了用于实现诊断监控功能并将其连接至 Diagnostic Management 的功能接口 [SWS_DM_00548]。在绑定到端口原型后，应用程序通过 Offer() 发出其准备接收的信号，并通过 ReportMonitorAction() 持续传输测试结果 [SWS_DM_01088]、[SWS_DM_00543]。Monitor 实例既不可复制也不可移动，且所有操作均被指定为非线程安全 [SWS_DM_01685]。

上下文

类 ara::diag::Monitor 代表了在 Adaptive Platform 内实现诊断监控功能（Monitor）的标准化 C++ 接口 [SWS_DM_00548]。Monitor 负责检测和报告功能软件组件中的故障症状，并将其状态传输至 Diagnostic Management（DM）模块。

与 AUTOSAR 系统模型的绑定通过 ara::core::InstanceSpecifier 进行，该参数必须强制引用由 DiagnosticMonitorInterface 定型的 PortPrototype [SWS_DM_00548]。整个处理过程主要涉及三个组件：特定于应用程序的功能监控（Application）、ara::diag::Monitor 的本地接口实例以及接收事件并请求重新初始化的平台模块 Diagnostic Management（DM）。

上下文图：应用软件、ara::diag::Monitor 与 Diagnostic Management 之间的交互关系。来源：[SWS_DM_00548]、[SWS_DM_00543]、[SWS_DM_01088]、[SWS_DM_01089]

生命周期

Monitor 的实例化取决于模型中定义的消抖机制（Debouncing）。Adaptive Platform 对此提供了四种构造函数变体：

  • 带有 InitMonitorNotifier 回调注册以及用于查询故障检测计数器（std::function<std::int8_t()> getFaultDetectionCounter）的函数指针的 Monitor 内部消抖 [SWS_DM_00548]。
  • 传递类型为 CounterBased 的参数的基于计数的消抖 [SWS_DM_00549]。
  • 传递类型为 TimeBased 的参数的基于时间的消抖 [SWS_DM_00550]。
  • 不带消抖算法的直接监控 [SWS_DM_01972]。

ara::diag::Monitor 的实例牢固绑定到其原始内存位置：复制构造函数 [SWS_DM_01685] 和复制赋值运算符 [SWS_DM_01683] 被删除（delete）。同样，移动构造函数 [SWS_DM_01686] 和移动赋值 [SWS_DM_01684] 也被显式删除。

创建之后，实例处于未提供（Unoffered）状态。只有通过显式调用 Offer()，应用程序才声明其准备好接收和处理诊断 Callout（例如 initMonitor）[SWS_DM_01088]。使用 StopOffer() 可以重新停用来自 DM 的诊断请求的转发 [SWS_DM_01089]。在调用 StopOffer() 之后，推测随后可以通过再次调用 Offer() 来恢复运行。 问题 Q-136565db34b28ae6 (未决)在最终销毁 Monitor 对象之前，应用程序推测必须执行 StopOffer()，以可靠阻止待处理的通知。

关于并发性，ara::diag::Monitor 的所有成员函数均被指定为非线程安全 [SWS_DM_00548]、[SWS_DM_01088]、[SWS_DM_00543]、[SWS_DM_01089]。如果应用软件的多个线程访问同一个 Monitor，则由应用程序负责同步。但是，所有方法均被声明为具备异常安全性（noexcept）[SWS_DM_00548]、[SWS_DM_01088]、[SWS_DM_00543]、[SWS_DM_01089]。

状态图：ara::diag::Monitor 服务提供时的生命周期状态与转换。来源：[SWS_DM_01088]、[SWS_DM_01089]

使用路径

用于监控故障路径的常规流程包括以下步骤：

  1. 实例化：应用程序通过指定 InstanceSpecifier、回调 initMonitor 以及可能需要的消抖参数或 FDC 回调来创建 Monitor 实例 [SWS_DM_00548]、[SWS_DM_00549]。
  2. 提供服务：通过 Offer()，Monitor 向 DM 注册为准备接收 [SWS_DM_01088]。
  3. 初始化：Diagnostic Management 通过已注册的 InitMonitorNotifier 回调将即将发生的初始化事件通知应用程序 [SWS_DM_01088]。
  4. 周期性/基于事件的报告：在运行期间，应用程序通过 ReportMonitorAction(action) 持续报告监控路径的状态 [SWS_DM_00543]。传入的操作要么包含测试结果（合格/不合格），要么包含用于消抖控制或预存储（Prestorage）的命令。如果配置了 Monitor 内部消抖，则 DM 会根据需要通过已注册的回调查询故障隔离值 [SWS_DM_00548]。
  5. 终止服务：在关闭之前或停用诊断功能时，应用程序调用 StopOffer() 以阻止传入的 DM 消息 [SWS_DM_01089]。

时序图：从初始化到状态报告再到停用的典型调用序列。来源：[SWS_DM_00548]、[SWS_DM_01088]、[SWS_DM_00543]、[SWS_DM_01089]

错误场景

ara::diag::Monitor 中的错误情况在两个不同层面上表现出来：作为通过 ara::core::Result 的错误代码，或者作为框架的运行时违规（Violations）。

方法 Offer() 返回一个 ara::core::Result<void>。如果 Monitor 已处于提供状态，则调用失败并返回错误代码 DiagOfferErrc::kAlreadyOffered [SWS_DM_01088]。

严重的配置或调用错误会触发已定义的违规通知：

  • InstanceSpecifierMappingIntegrityViolation：InstanceSpecifier 无法在进程的模型上下文中解析，或未引用 PortPrototype [SWS_DM_00548]。
  • PortInterfaceMappingViolation：引用的端口未通过 DiagnosticMonitorInterface 进行类型化 [SWS_DM_00548]。
  • ProcessMappingViolation：不存在与运行时实例匹配的建模进程 [SWS_DM_00548]。
  • InstanceSpecifierAlreadyInUseViolation：当前进程内的 InstanceSpecifier 已被另一个 Monitor 使用 [SWS_DM_00548]。
  • InvalidDebouncingAlgorithmViolation：在构造函数中选择的消抖机制与 DEXT 诊断描述中建模的消抖方法不一致 [SWS_DM_00548]、[SWS_DM_00549]、[SWS_DM_00550]。
  • UnexpectedMonitorActionHandlingViolation：向方法 ReportMonitorAction() 传递了配置的消抖算法不支持的操作值 [SWS_DM_00543]。

本指南基于 AUTOSAR Adaptive Platform 规范 Release R25-11。
