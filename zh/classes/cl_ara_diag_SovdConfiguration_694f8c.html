上下文

类 ara::diag::SovdConfiguration 代表 AUTOSAR Adaptive Platform 上 SOVD 配置（面向服务的车辆诊断，Service-Oriented Vehicle Diagnostics）的通用接口（[SWS_DM_01860]、AUTOSAR_AP_SWS_Diagnostics §8.54.1 “Class: SovdConfiguration”）。一旦系统中建模了至少一个 SOVD 配置，Diagnostic Server 实例就会提供用于列出所有已提供配置的标准化 SOVD 方法（[SWS_DM_01429]、AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2 “SOVD API – Configuration”）。

对于显式建模的 SOVD 配置，ara::diag::SovdConfiguration 的派生实例充当应用程序处理程序。Diagnostic Server (DM) 充当中介：传入的对 SOVD 方法 Read Configuration 和 Write Configuration 的外部请求由 Diagnostic Server 接收，并通过接口方法 RequestGetConfiguration（[SWS_DM_01787]）或 RequestPutConfiguration（[SWS_DM_01788]）转发给应用程序。

上下文图：ara::diag::SovdConfiguration 在外部 SOVD 客户端与 Diagnostic Server 之间的嵌入。来源：[SWS_DM_01787]、[SWS_DM_01788]、AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 “Configuration – Explicit Configurations”

生命周期

应用程序类继承自 ara::diag::SovdConfiguration，并通过需要 ara::core::InstanceSpecifier 以及 ConcurrencyType 的构造函数来实例化该对象（[SWS_DM_01864]）。InstanceSpecifier 将该对象与建模的端口原型关联起来。

在所有权方面，该类被设计为单实例：复制构造函数（[SWS_DM_01866]）和复制赋值运算符（[SWS_DM_01868]）均已删除（delete）。移动操作（移动构造函数和移动赋值）被声明为 protected 和 noexcept（[SWS_DM_01867]、[SWS_DM_01869]）。

实例化后，该对象最初处于非活动状态。只有通过调用 Offer()，Diagnostic Management 守护进程才能转发针对该处理程序的请求（[SWS_DM_01872]）。如果不再提供该服务，则通过 StopOffer() 停用转发（[SWS_DM_01930]）。虚析构函数 ~SovdConfiguration() 用于销毁对象（[SWS_DM_01865]）。解释：在常规关机场景下，推测很可能会在对象销毁前调用 StopOffer()，以排除析构函数执行期间的异步访问。

在并发性方面，构造函数是线程安全的（[SWS_DM_01864]），而 Offer()（[SWS_DM_01872]）、StopOffer()（[SWS_DM_01930]）和析构函数（[SWS_DM_01865]）不是线程安全的。处理程序方法 RequestGetConfiguration（[SWS_DM_01870]）和 RequestPutConfiguration（[SWS_DM_01871]）的线程安全性是有条件的：它取决于构造时传递的是 ConcurrencyType::kConcurrent 还是 ConcurrencyType::kNotConcurrent。

使用路径

处理 SOVD 配置查询的典型使用路径包括以下阶段：

  1. 初始化：应用程序使用匹配的 InstanceSpecifier 和所需的并发模式实例化派生类（[SWS_DM_01864]）。
  2. 服务提供：通过调用 Offer() 激活请求转发（[SWS_DM_01872]）。
  3. 请求处理（读取）：当 Diagnostic Server 收到 SOVD 读取请求时（[SWS_DM_01787]），它会调用 RequestGetConfiguration（[SWS_DM_01870]）。应用程序处理传入的 configurationId 以及 MetaInfo，监视 CancellationHandler 并返回一个包含由 DataTransferReadSession 和 SovdConfigurationMetaInfo 构成的 std::tuple 的 ara::core::Future。
  4. 请求处理（写入）：发生写入请求时（[SWS_DM_01788]），服务器会调用 RequestPutConfiguration（[SWS_DM_01871]），随后应用程序提供包含 DataTransferWriteSession 和元信息的 Future。
  5. 服务终止：在终止组件之前，应用程序通过 StopOffer() 停用对进一步请求的接收（[SWS_DM_01930]）。

时序图：服务的提供以及 SOVD 读取请求的异步处理。来源：[SWS_DM_01787]、[SWS_DM_01870]、[SWS_DM_01872]、[SWS_DM_01930]

错误场景

错误情况可能会在交互的不同阶段发生：

  • 构造违规：调用构造函数（[SWS_DM_01864]）时可能会发生建模和映射错误：
    • InstanceSpecifierMappingIntegrityViolation：该标识符在可执行文件上下文中无法解析，或未指向 PortPrototype。
    • PortInterfaceMappingViolation：PortPrototype 未由 DiagnosticSovdConfigurationInterface 进行类型化。
    • ProcessMappingViolation：不存在到匹配的已建模进程的映射。
    • InstanceSpecifierAlreadyInUseViolation：InstanceSpecifier 在进程内已被使用。
  • 提供（Offer）时的错误：Offer() 返回一个 ara::core::Result<void>（[SWS_DM_01872]）。可能的错误代码包括：
    • DiagOfferErrc::kConfigurationMismatch：监控配置与 DEXT 不一致（回滚语义）。
    • DiagOfferErrc::kAlreadyOffered：该服务之前已被提供（回滚语义）。
  • 配置处理时的错误：若读取或写入配置实例失败，实现会通过由 RequestGetConfiguration（[SWS_DM_01870]）或 RequestPutConfiguration（[SWS_DM_01871]）返回的 Future 传输符合 ISO 17978-3 / ASAM SOVD 1.1 的标准化 SOVD 错误代码。此外，如果正在进行的会话被中止，CancellationHandler 会发出信号。
