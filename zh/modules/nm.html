角色：State Management 与总线之间的网络请求

自适应 Network Management (NM) 协调底层物理网络和局部网络何时在正常运行和 Bus-Sleep 之间切换。它应当独立于所使用的通信栈工作 SWS NM 第5页。在专业规范上，它基于 PRS NetworkManagementProtocol。它使用通信栈发送和接收 NM 报文 SWS NM 第9页。根据限制说明，目前仅支持 UdpNM SWS NM 第8页。

对上而言，系统边界界定严格。应用程序不直接与 NM 交互。它们向 State Management 请求功能，而 State Management 则根据配置请求或释放逻辑网络 SWS NM 第14页 SWS NM 第29页。唯一的接口是头文件 ara/nm/network_handle.h 中的类 ara::nm::NetworkHandle [SWS_ANM_01000]。它明确仅供 State Management 使用 EXP SWArch 第77页。State Management 相应地将其列入其所需接口中 EXP SWArch 第56页。两个 Cluster 均基于守护程序：State Management 使用该接口，NM 实现该接口 SWS NM 第13页。

SWS 的早期文本部分（第 8/9 章）与此相反。其中提到 NM 不包含 API，而是通过服务提供所有功能 SWS NM 第26页。然而对于 R25-11 具有规范效力的是 C++ 类 NetworkHandle 及其方法 [SWS_ANM_01000] [SWS_ANM_01009]。Platform Design 概述描述了这种从 ara::com 接口到直接方法调用的转变 EXP PlatformDesign 第60页。

从逻辑网络到通道：句柄、Partial Networks 与 NM 实例

一个逻辑网络映射至恰好一个局部网络或物理网络。相比之下，一个局部网络可以分配给多个物理网络。NM 提供的每个端口恰好控制一个逻辑网络，且这些端口通过 Manifest 分配给逻辑网络。在使用 Partial Networking 时，还必须配置局部网络到物理网络的分配。在不使用 Partial Networking 的情况下，端口直接映射到物理网络 SWS NM 第14页。

SWS 概述展示了分层结构。Network Handle 实例作用于局部网络状态机。这些状态机控制通道专用的 NM 实例，每个实例具有一个在网络上运行的 Network State Machine SWS NM 第18页 EXP PlatformDesign 第60页。局部网络状态机是特定于实现的。但其行为必须符合 PRS 的 Partial Networking 要求 SWS NM 第24页。

使用 ara::nm::NetworkHandle：请求、查询、通知

句柄通过 NetworkManagementPortInterface 类型的端口原型的 InstanceSpecifier 创建。构造函数为 noexcept 且线程安全 [SWS_ANM_01001]。不可复制 [SWS_ANM_01005] [SWS_ANM_01006]，但可移动 [SWS_ANM_01003] [SWS_ANM_01004]。析构函数非线程安全 [SWS_ANM_01002]。

NetworkStateType 仅包含 kNoCom 和 kFullCom。当所有分配的网络均为 FULL_COM 时，kFullCom 适用，否则 kNoCom 适用 [SWS_ANM_01358]。句柄区分了两种视图：

  • 请求状态：SetNetworkRequestedState 请求或释放 PNC、VLAN 或物理网络 [SWS_ANM_01009]。GetNetworkRequestedState 读取该状态 [SWS_ANM_01008]。
  • 有效状态：GetNetworkState 读取当前网络状态 [SWS_ANM_01007]。

解释：有效状态 kFullCom 应当对应于所分配通道的 Network Mode。因为 Network Mode 意味着网络已被请求或处于活动状态 SWS NM 第15页。

对于两种视图，各有一个类型为NetworkStateChangeNotifier的 Notifier。它是一个接收新NetworkStateType的std::function[SWS_ANM_01020]。RegisterNetworkStateChangeNotifier和RegisterNetworkRequestedStateChangeNotifier分别最多接受一个 Notifier[SWS_ANM_01010][SWS_ANM_01012]。根据接口表，每次后续注册都会覆盖已有的注册EXP SWArch 第77页。带有ExecutorT的变体在传入的执行上下文中执行 Notifier[SWS_ANM_01014][SWS_ANM_01015]。使用UnregisterNetworkStateChangeNotifier或UnregisterNetworkRequestedStateChangeNotifier进行注销[SWS_ANM_01011][SWS_ANM_01013]。

关于线程安全性：只有两个 Getter [SWS_ANM_01007][SWS_ANM_01008]是线程安全的。SetNetworkRequestedState以及所有注册和注销函数均不是线程安全的[SWS_ANM_01009][SWS_ANM_01010][SWS_ANM_01013]。因此，调用者必须针对每个 Handle 自行串行化这些调用。

通道行为：分散式 NM 算法与运行模式

该算法以分散且直接的方式工作。每个节点仅根据接收和发送的 NM 报文做出决定。通过多播发送给所有节点的周期性 NM 报文使集群保持唤醒状态。能够进入睡眠的节点不再发送。但只要其他节点的报文仍在到达，它就会推迟睡眠SWS NM 第13页。每个节点都可以集成到已在运行的集群中SWS NM 第11页。

NM 针对每个物理通道实现 Network Mode、Prepare Bus-Sleep Mode 和 Bus-Sleep Mode。这些模式对应用程序不可见SWS NM 第15页。Network Mode 细分为 Repeat Message、Normal Operation 和 Ready SleepSWS NM 第16页。详细流程如下：

  • 进入 Network Mode 时，将进入 Repeat Message，并通过NmTimeoutTime启动 NM 超时定时器。每次成功接收或发送 NM 报文都会重启该定时器SWS NM 第17页。
  • 如果在 Normal Operation 中释放网络，NM 将切换到 Ready Sleep，并停止发送。接收到的 Repeat Message Request Bit 会导致返回 Repeat MessageSWS NM 第18页。
  • Prepare Bus-Sleep 持续NmWaitBusSleepTime并以 Bus-Sleep 结束。如果在此之前有 NM 报文到达，NM 将立即返回 Network ModeSWS NM 第19页。

在发送时，进入 Repeat Message 后的第一个报文会延迟NmMsgCycleOffset。此后，NM 以NmMsgCycleTime周期性发送SWS NM 第22页。在发送的消息中，Repeat Message Request Bit、Active Wakeup Bit 和 NM Coordinator Sleep Ready Bit 始终为 0SWS NM 第20页。不支持节点检测、主协调器角色、通过 CBV 进行协调关机以及 Passive ModeSWS NM 第8页。

Partial Networking：接收求值与聚合请求状态

NmPnEnabled开启或关闭接收时对 PN 信息的求值。启用 Partial Networking 时的规则SWS NM 第24页：

  • 如果 PNI 位为 1，一旦接收到的 BitVector 改变了相关 PN 或通道的请求状态，NM 就会调用 NetworkHandle-Notifier。
  • 如果 PNI 位为 0，NM 仍会处理有效负载数据。
  • 该 Getter 返回 PN 的聚合请求状态，而不反映最近接收到的信息。推测其指的是GetNetworkRequestedState[SWS_ANM_01008]。
  • NmPnResetTime必须大于NmMsgCycleTime。

PN 信息区域的每个位代表一个部分网络。NM 可以选择过滤掉不包含任何为该 ECU 配置且置为 1 的 PNC 位的消息SWS NM 第25页。同一位置提到了 Adaptive Application 的方法RequestNetwork/ReleaseNetwork。在 R25-11 中，由 State Management 调用的SetNetworkRequestedState取代了它们[SWS_ANM_01009]。

如果接收到的有效负载数据发生变化，NM 会调用一个通知SWS NM 第23页。有效负载数据与 PNI 不会重叠SWS NM 第21页。不再存在对有效负载数据的应用程序访问。未来是否应通过 State Management 进行访问尚不明确SWS NM 第8页。

发生错误时的行为

错误作为ara::core::Result报告。它们属于领域NmErrorDomain[SWS_ANM_01101]，该领域提供GetNmDomain[SWS_ANM_01109]。NmErrc包含kServiceNotAvailable = 1和kInvalidHandler = 2[SWS_ANM_01111]。错误分布如下：

  • Getter 和 Setter 报告kServiceNotAvailable[SWS_ANM_01007][SWS_ANM_01008][SWS_ANM_01009]。
  • 注册函数报告kInvalidHandler[SWS_ANM_01010][SWS_ANM_01012][SWS_ANM_01014][SWS_ANM_01015]。
  • 注销函数为void noexcept，且没有错误路径[SWS_ANM_01011][SWS_ANM_01013]。

如果 Getter 返回错误，则Result不包含任何NetworkStateType[SWS_ANM_01007]。因此，此类错误不应被解释为kNoCom。Interpretation：kServiceNotAvailable可能表明基于守护进程的 NM 集群SWS NM 第13页当前不可达。

倾向于使用异常的人可以使用MakeErrorCode生成一个ErrorCode[SWS_ANM_01110]。ThrowAsException由此抛出一个NmException[SWS_ANM_01108][SWS_ANM_01100][SWS_ANM_01102]。领域名称和通知文本由Name和Message提供[SWS_ANM_01106][SWS_ANM_01107]。

在协议层面上，NM 具有容错设计。如果在 Prepare Bus-Sleep 中仍接收到 NM 报文，它将返回 Network Mode，以便尽快恢复通信SWS NM 第19页。如果报文完全缺失，定时器会将所有节点引向睡眠SWS NM 第13页。
