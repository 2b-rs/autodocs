作为 Functional Cluster 的 Firewall：角色与系统边界

Functional Cluster Firewall（命名空间 ara::fw）为应用程序仅提供一个业务编程接口。即包含方法 SwitchFirewallState [AP_SWS_Fw_82008] 的类 ara::fw::FirewallStateSwitchInterface。根据架构描述，该集群是基于守护进程的。它实现了带有构造型 «aapAPI,aapPortInterface» 的接口 FirewallStateSwitchInterface，并且 Adaptive Application 通过 «use» 关系使用它 EXP SWArchitecture 第126页。用例图列出了两个用例。“Switch Firewall State”由 Adaptive Application 触发。Intrusion Detection System Manager 参与了“Report Security Event”。Operating System 作为另一个参与者出现 EXP SWArchitecture 第197页。

SWS 的架构草图明确划分了职责：

  • Machine Manifest 提供包含其过滤规则的 Firewall 配置。
  • FC Firewall 据此配置 Firewall Engine。
  • OEM 应用程序指定 Firewall 状态。
  • 安全事件 (SEv) 发送至 IdsM SWS Firewall 第16页。

平台设计展示了相同的划分 EXP PlatformDesign 第97页。因此实际的数据包检查位于 API 之外。状态切换场景将规则应用分配给 Operating System，并将其标记为 «aapInformative» EXP SWArchitecture 第232页。

上下文图：FC Firewall 在 Manifest 配置、指定状态的应用程序、执行引擎或操作系统以及 IdsM 之间进行协调。来源：SWS Firewall 第16页、EXP SWArchitecture 第126页、EXP SWArchitecture 第232页

基于状态的过滤：Firewall 状态和过滤规则

该概念的核心是基于状态的过滤。特定于 OEM 的 Firewall 状态反映了预期会有不同网络流量的情况，例如行驶、停车或诊断会话。过滤规则被分配给某个状态。Firewall 仅使用当前活动状态的规则来进行检查和过滤。应用程序通过 FC Firewall 的 API 设置当前状态 EXP PlatformDesign 第92页。在 C++ 中，这是方法 SwitchFirewallState(EnumT firewallState) [AP_SWS_Fw_82008]。

规则本身是 Manifest 的内容。Foundation 需求示意图显示了跨多个层的过滤链：

  • 具有 MAC 地址和 EtherType 的 Ethernet，
  • IPv4，
  • 具有通过标志进行状态检测的 TCP 或 ICMP，
  • 具有服务 ID、方法 ID 和客户端 ID 的 SOME/IP RS Firewall 第12页。

在传输层上，Manifest 对具有属性 bucketSize 和 refillAmount 的 FirewallRule 进行建模。此外还有具有端口范围和 checksumVerification 的 TransportLayerRule，该规则被特化为 UDP 和 TCP 规则 TPS Manifest 第687页。

如果数据包与任何定义的规则都不匹配，则默认操作 (Default Action) 生效。SWS 的 R23-11 版本还描述了对于以此方式阻止的数据包，如何确定不匹配 (Mismatch) 的协议层。从最低网络层算起具有最多连续匹配项的规则具有决定性。在第一个不匹配的层上会触发层特定的 SEv SWS Firewall 第31页。该处内容源自 R23-11，且在有效载荷中未被 R25-11 需求所覆盖。因此应将其理解为说明，而非规范性要求。

活动图：仅检查活动 Firewall 状态的规则。在缺少匹配项时默认操作生效，并且被阻止的数据包会导致触发层特定的 SEv（根据 R23-11 的表示法）。来源：EXP PlatformDesign 第92页、SWS Firewall 第31页

从 InstanceSpecifier 到状态切换

首先，应用程序创建 FirewallStateSwitchInterface 的实例。为此使用需要 ara::core::InstanceSpecifier 的显式构造函数。它是 noexcept，并且被指定为线程安全的 [AP_SWS_Fw_82002]。解释：InstanceSpecifier 应当表示应用程序的 RPortPrototype，其在 Manifest 中由 FirewallStateSwitchInterface 定型。Manifest 图正好建立了该端口关系，但未提及该说明符 TPS Manifest 第677页。

状态切换由 SwitchFirewallState(EnumT firewallState) 触发。该方法是 noexcept 并返回 ara::core::Future<void> [AP_SWS_Fw_82008]。“Switch Firewall State”场景分三步展示了该流程：

  1. Adaptive Application 在 FC Firewall 上调用 SwitchFirewallState()。
  2. FC Firewall 在循环中针对每个 FirewallRule 调用 Operating System 的 applyRule()。
  3. 随后响应返回给应用程序 EXP SWArchitecture 第232页。

针对相同场景的 R22-11 表示展示了相同的流程 EXP SWArchitecture 第158页。因为 applyRule() 被标记为 «aapInformative»，所以该循环仅描述了其原理。它并未定义具有约束力的操作系统接口 EXP SWArchitecture 第232页。

时序图：应用程序构造接口实例并请求状态切换。FC Firewall 应用每条规则，结果作为 ara::core::Future<void> 返回。来源：[AP_SWS_Fw_82002]、[AP_SWS_Fw_82008]、EXP SWArchitecture 第232页

生成的状态类型和 Manifest 连接

允许的 Firewall 状态不构成固定的平台类型。对于每个建模的接口，都会在命名空间 ara::fw::states 中生成一个专用的 enum class {<fwssi-sn>} : std::uint32_t。它通过 ara/fw/states/{<fwssi-sn>}.h 包含，枚举器列表来自模型 [AP_SWS_Fw_81001]。对于每个建模的 Firewall 状态，都会生成 {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002] 形式的枚举器。解读：SwitchFirewallState 的参数类型 EnumT 很可能代表该生成的状态类型，因为 [AP_SWS_Fw_81001] 将其明确定义为 FirewallStateSwitchInterface [AP_SWS_Fw_82008] 的状态类型。

在元模型中，FirewallStateSwitchInterface 是一个 PortInterface。它通过角色 firewallStateMachine 聚合 (0..*) 个类型为 ModeDeclarationGroupPrototype TPS Manifest 第263页 的元素。据推测，该组的 Mode 提供了 [AP_SWS_Fw_81002] 中的枚举器。然而，源文档并未明确描述这种映射。

在机器级别，AdaptiveFirewallModuleInstantiation 收集 Firewall 的机器特定设置（TPS_MANI_03296，状态 DRAFT）。元类 AdaptiveFirewallToPortPrototypeMapping 通过引用 firewall (0..1) 将该实例化与应用程序的 RPortPrototype 连接起来 TPS Manifest 第677页。该元类的 Note 在此提到了“FirewallModeSwitchInterface”。相比之下，示意图和 API 一致使用 FirewallStateSwitchInterface TPS Manifest 第677页。

接口实例的生命周期与并发性

FirewallStateSwitchInterface 的实例不可复制。复制构造函数和复制赋值运算符已被删除 [AP_SWS_Fw_82004] [AP_SWS_Fw_82005]。相比之下，移动是允许的，因为移动构造函数和移动赋值运算符为 noexcept [AP_SWS_Fw_82006] [AP_SWS_Fw_82007]。因此，实例可以转移给另一个所有者，但不能被复制。

线程安全性针对每个操作进行定义。下表总结了 [AP_SWS_Fw_82002] 至 [AP_SWS_Fw_82008] 中的规范：

发送至 Intrusion Detection System Manager 的 Security Events

除状态切换外，Firewall 还支持入侵检测系统。针对被阻止的报文，规范定义了一组上报给 IdsM 的 Security Events。IdsM 负责其认定和进一步处理。它将事件转发给 SOC 或持久化存储在 ECU EXP PlatformDesign 第92页 上。“Report Security Event”场景通过交互 packetBlocked()、handlePacketBlocked()、raiseSecurityEvent() 和 ReportEvent() 将 Operating System、FC Firewall 和 IdsM 连接起来。其中部分内容被标记为 «aapInformative» EXP SWArchitecture 第232页。

对于被 Default Action 阻止的数据包，R23-11-SWS 列出了特定于层级的事件 SWS Firewall 第31页：

  • 用于 Ethernet 的 SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH，
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

这些事件名称在有效载荷中未被 R25-11 需求覆盖。其针对 R25-11 的有效性需对照当前 SWS 进行核对 SWS Firewall 第31页。

发生错误时的行为

对于 SwitchFirewallState，规范定义了两个错误：FwErrc::kServiceNotAvailable 和 FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]。枚举 FwErrc 规定了它们的值，即 kServiceNotAvailable=1 和 kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]。该方法为 noexcept 并返回一个 ara::core::Future<void>。因此，调用方通过 Future 评估这些错误，而不是通过调用抛出的异常 [AP_SWS_Fw_82008]。

两个错误均属于 FwErrorDomain。该域提供以下构建块：

  • GetFwErrorDomain() 返回对域对象的引用；该函数为 constexpr 且 thread-safe [AP_SWS_Fw_83002]。
  • MakeErrorCode 根据 FwErrc 和附加数据创建 ara::core::ErrorCode [AP_SWS_Fw_83003]。
  • Name() 和 Message() 提供域名称和对应代码的消息文本；两者皆为 thread-safe [AP_SWS_Fw_83010] [AP_SWS_Fw_83011]。
  • 别名 Errc 和 Exception 指向 FwErrc 和 FwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008]。

尽管域的描述为“Constructs a new FwErrorDomain object” [AP_SWS_Fw_83009]，但其默认构造函数已被删除。因此，对域的访问通过 GetFwErrorDomain() 进行。

若要将错误作为异常传递，可使用 ThrowAsException。该函数创建并抛出 FwException。它为 noexcept(false) 且被归类为“not exception safe” [AP_SWS_Fw_83012]。异常本身通过显式的 thread-safe 构造函数 FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005] 创建。

在数据包级别，错误情况表现为数据包被阻止。没有匹配规则的数据包归入 Default Action，被阻止的报文作为 Security Events 上报给 IdsM EXP PlatformDesign 第92页。[AP_SWS_Fw_82008] 中的接口未为此类事件向应用程序提供返回通道。其处理由 IdsM 负责。

<h4>基于状态的过滤：Firewall 状态和过滤规则</h4>
<p>该概念的核心是基于状态的过滤。特定于 OEM 的 Firewall 状态反映了预期会有不同网络流量的情况，例如行驶、停车或诊断会话。过滤规则被分配给某个状态。Firewall 仅使用当前活动状态的规则来进行检查和过滤。应用程序通过 FC Firewall 的 API 设置当前状态 <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign 第92页</a>。在 C++ 中，这是方法 <code>SwitchFirewallState(EnumT firewallState)</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>。</p>
<p>规则本身是 Manifest 的内容。Foundation 需求示意图显示了跨多个层的过滤链：</p>
<ul>
<li>具有 MAC 地址和 EtherType 的 Ethernet，</li>
<li>IPv4，</li>
<li>具有通过标志进行状态检测的 TCP 或 ICMP，</li>
<li>具有服务 ID、方法 ID 和客户端 ID 的 SOME/IP <a class="docref internal-spec-ref" href="../../spec/figures/FIG-8d7d096012113639.html" data-snip="FIG-8d7d096012113639">RS Firewall 第12页</a>。</li>
</ul>
<p>在传输层上，Manifest 对具有属性 <code>bucketSize</code> 和 <code>refillAmount</code> 的 <code>FirewallRule</code> 进行建模。此外还有具有端口范围和 <code>checksumVerification</code> 的 <code>TransportLayerRule</code>，该规则被特化为 UDP 和 TCP 规则 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-465799fa260b6f07.html" data-snip="FIG-465799fa260b6f07">TPS Manifest 第687页</a>。</p>
<p>如果数据包与任何定义的规则都不匹配，则默认操作 (Default Action) 生效。SWS 的 R23-11 版本还描述了对于以此方式阻止的数据包，如何确定不匹配 (Mismatch) 的协议层。从最低网络层算起具有最多连续匹配项的规则具有决定性。在第一个不匹配的层上会触发层特定的 SEv <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3.html" data-snip="SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3">SWS Firewall 第31页</a>。该处内容源自 R23-11，且在有效载荷中未被 R25-11 需求所覆盖。因此应将其理解为说明，而非规范性要求。</p>

<h4>从 InstanceSpecifier 到状态切换</h4>
<p>首先，应用程序创建 <code>FirewallStateSwitchInterface</code> 的实例。为此使用需要 <code>ara::core::InstanceSpecifier</code> 的显式构造函数。它是 <code>noexcept</code>，并且被指定为线程安全的 <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>。解释：<code>InstanceSpecifier</code> 应当表示应用程序的 <code>RPortPrototype</code>，其在 Manifest 中由 <code>FirewallStateSwitchInterface</code> 定型。Manifest 图正好建立了该端口关系，但未提及该说明符 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest 第677页</a>。</p>
<p>状态切换由 <code>SwitchFirewallState(EnumT firewallState)</code> 触发。该方法是 <code>noexcept</code> 并返回 <code>ara::core::Future&lt;void&gt;</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>。“Switch Firewall State”场景分三步展示了该流程：</p>
<ol>
<li>Adaptive Application 在 FC Firewall 上调用 <code>SwitchFirewallState()</code>。</li>
<li>FC Firewall 在循环中针对每个 <code>FirewallRule</code> 调用 Operating System 的 <code>applyRule()</code>。</li>
<li>随后响应返回给应用程序 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP SWArchitecture 第232页</a>。</li>
</ol>
<p>针对相同场景的 R22-11 表示展示了相同的流程 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-826e9bb7c1d7761d.html" data-snip="FIG-826e9bb7c1d7761d">EXP SWArchitecture 第158页</a>。因为 <code>applyRule()</code> 被标记为 «aapInformative»，所以该循环仅描述了其原理。它并未定义具有约束力的操作系统接口 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP SWArchitecture 第232页</a>。</p>

<h4>生成的状态类型和 Manifest 连接</h4>
<p>允许的 Firewall 状态不构成固定的平台类型。对于每个建模的接口，都会在命名空间 <code>ara::fw::states</code> 中生成一个专用的 <code>enum class {&lt;fwssi-sn&gt;} : std::uint32_t</code>。它通过 <code>ara/fw/states/{&lt;fwssi-sn&gt;}.h</code> 包含，枚举器列表来自模型 <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a>。对于每个建模的 Firewall 状态，都会生成 <code>{&lt;symbol-fw-state&gt;} = {&lt;fw-state-value&gt;}</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a> 形式的枚举器。解读：<code>SwitchFirewallState</code> 的参数类型 <code>EnumT</code> 很可能代表该生成的状态类型，因为 [AP_SWS_Fw_81001] 将其明确定义为 <code>FirewallStateSwitchInterface</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a> 的状态类型。</p>
<p>在元模型中，<code>FirewallStateSwitchInterface</code> 是一个 <code>PortInterface</code>。它通过角色 <code>firewallStateMachine</code> 聚合 (0..*) 个类型为 <code>ModeDeclarationGroupPrototype</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-b3757549d69ff2c3.html" data-snip="FIG-b3757549d69ff2c3">TPS Manifest 第263页</a> 的元素。据推测，该组的 Mode 提供了 <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a> 中的枚举器。然而，源文档并未明确描述这种映射。</p>
<p>在机器级别，<code>AdaptiveFirewallModuleInstantiation</code> 收集 Firewall 的机器特定设置（<code>TPS_MANI_03296</code>，状态 DRAFT）。元类 <code>AdaptiveFirewallToPortPrototypeMapping</code> 通过引用 <code>firewall</code> (0..1) 将该实例化与应用程序的 <code>RPortPrototype</code> 连接起来 <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58.html" data-snip="SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58">TPS Manifest 第677页</a>。该元类的 Note 在此提到了“FirewallModeSwitchInterface”。相比之下，示意图和 API 一致使用 <code>FirewallStateSwitchInterface</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest 第677页</a>。</p>

<h4>接口实例的生命周期与并发性</h4>
<p><code>FirewallStateSwitchInterface</code> 的实例不可复制。复制构造函数和复制赋值运算符已被删除 <a class="spec-record-ref" data-req="AP_SWS_Fw_82004" href="../spec/record.html?id=AP_SWS_Fw_82004">[AP_SWS_Fw_82004]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82005" href="../spec/record.html?id=AP_SWS_Fw_82005">[AP_SWS_Fw_82005]</a>。相比之下，移动是允许的，因为移动构造函数和移动赋值运算符为 <code>noexcept</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82006" href="../spec/record.html?id=AP_SWS_Fw_82006">[AP_SWS_Fw_82006]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82007" href="../spec/record.html?id=AP_SWS_Fw_82007">[AP_SWS_Fw_82007]</a>。因此，实例可以转移给另一个所有者，但不能被复制。</p>

<h4>发送至 Intrusion Detection System Manager 的 Security Events</h4>
<p>除状态切换外，Firewall 还支持入侵检测系统。针对被阻止的报文，规范定义了一组上报给 IdsM 的 Security Events。IdsM 负责其认定和进一步处理。它将事件转发给 SOC 或持久化存储在 ECU <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign 第92页</a> 上。“Report Security Event”场景通过交互 <code>packetBlocked()</code>、<code>handlePacketBlocked()</code>、<code>raiseSecurityEvent()</code> 和 <code>ReportEvent()</code> 将 Operating System、FC Firewall 和 IdsM 连接起来。其中部分内容被标记为 «aapInformative» <a class="docref internal-spec-ref" href="../../spec/figures/FIG-b1273965639f62af.html" data-snip="FIG-b1273965639f62af">EXP SWArchitecture 第232页</a>。</p>

<h4>发生错误时的行为</h4>
<p>对于 <code>SwitchFirewallState</code>，规范定义了两个错误：<code>FwErrc::kServiceNotAvailable</code> 和 <code>FwErrc::kInvalidStateDependentFirewall</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>。枚举 <code>FwErrc</code> 规定了它们的值，即 <code>kServiceNotAvailable=1</code> 和 <code>kInvalidStateDependentFirewall=2</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83001" href="../spec/record.html?id=AP_SWS_Fw_83001">[AP_SWS_Fw_83001]</a>。该方法为 <code>noexcept</code> 并返回一个 <code>ara::core::Future&lt;void&gt;</code>。因此，调用方通过 Future 评估这些错误，而不是通过调用抛出的异常 <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>。</p>
<p>两个错误均属于 <code>FwErrorDomain</code>。该域提供以下构建块：</p>
<ul>
<li><code>GetFwErrorDomain()</code> 返回对域对象的引用；该函数为 <code>constexpr</code> 且 thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_83002" href="../spec/record.html?id=AP_SWS_Fw_83002">[AP_SWS_Fw_83002]</a>。</li>
<li><code>MakeErrorCode</code> 根据 <code>FwErrc</code> 和附加数据创建 <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83003" href="../spec/record.html?id=AP_SWS_Fw_83003">[AP_SWS_Fw_83003]</a>。</li>
<li><code>Name()</code> 和 <code>Message()</code> 提供域名称和对应代码的消息文本；两者皆为 thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_83010" href="../spec/record.html?id=AP_SWS_Fw_83010">[AP_SWS_Fw_83010]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83011" href="../spec/record.html?id=AP_SWS_Fw_83011">[AP_SWS_Fw_83011]</a>。</li>
<li>别名 <code>Errc</code> 和 <code>Exception</code> 指向 <code>FwErrc</code> 和 <code>FwException</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83007" href="../spec/record.html?id=AP_SWS_Fw_83007">[AP_SWS_Fw_83007]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83008" href="../spec/record.html?id=AP_SWS_Fw_83008">[AP_SWS_Fw_83008]</a>。</li>
</ul>
<p>尽管域的描述为“Constructs a new FwErrorDomain object” <a class="spec-record-ref" data-req="AP_SWS_Fw_83009" href="../spec/record.html?id=AP_SWS_Fw_83009">[AP_SWS_Fw_83009]</a>，但其默认构造函数已被删除。因此，对域的访问通过 <code>GetFwErrorDomain()</code> 进行。</p>
<p>若要将错误作为异常传递，可使用 <code>ThrowAsException</code>。该函数创建并抛出 <code>FwException</code>。它为 <code>noexcept(false)</code> 且被归类为“not exception safe” <a class="spec-record-ref" data-req="AP_SWS_Fw_83012" href="../spec/record.html?id=AP_SWS_Fw_83012">[AP_SWS_Fw_83012]</a>。异常本身通过显式的 thread-safe 构造函数 <code>FwException(ara::core::ErrorCode)</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83005" href="../spec/record.html?id=AP_SWS_Fw_83005">[AP_SWS_Fw_83005]</a> 创建。</p>
<p>在数据包级别，错误情况表现为数据包被阻止。没有匹配规则的数据包归入 Default Action，被阻止的报文作为 Security Events 上报给 IdsM <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign 第92页</a>。<a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a> 中的接口未为此类事件向应用程序提供返回通道。其处理由 IdsM 负责。</p>
