Platform Health Management 的角色与系统边界

Platform Health Management（PHM，命名空间ara::phm）通过两种方式监控应用程序：在时间上通过 Alive Supervision 和 Deadline Supervision，在逻辑上通过程序执行顺序（Logical Supervision）。PHM 将检测到的错误报告给 State Management。State Management 协调平台并决定应对措施。对于此类报告不足以应对的关键错误，PHM 还具有与硬件看门狗的接口SWS PHM 第22页。监控算法来自 Foundation 规范 Health Monitoring。Adaptive 规范主要补充了平台特性和接口SWS PHM 第8页。

PHM 提供两个公共 C++ API：

  • 用于报告检查点的ara::phm::SupervisedEntity [SWS_PHM_01127]。
  • ara::phm::RecoveryAction作为回调接口，State Management 通过它接收恢复指令[SWS_PHM_01142]。

不仅 Adaptive Applications 使用SupervisedEntity，Execution Management、State Management、Diagnostic Management 和 Time Synchronization 等平台守护进程也使用它SWS PHM 第15页。PHM 通过原生平台扩展apext::phm::WatchdogInterface以及AliveNotification [SWS_PHM_01255]和FireWatchdogReaction [SWS_PHM_01256]来控制看门狗。PHM 未定义 Adaptive Platform 的 Service Interfaces SWS PHM 第78页。

PHM 自身需要三项内容：

  • 来自 Execution Management 的进程状态：达到kRunning、终止以及即将到来的SIGTERM SWS PHM 第17页。
  • 用于报告自身执行状态的ExecutionClient。
  • 来自 Log and Trace 的Logger SWS PHM 第16页。

功能集群之间的接口仅作为参考性描述；其细节由平台供应商确定SWS PHM 第89页。有两项功能不在此范围内：Health Channels 被标记为已废弃，且不支持 Daisy Chaining SWS PHM 第13页 SWS PHM 第72页。

启动、Supervision Modes 以及监控的生命周期

在自身启动时，PHM 会尽早接管看门狗：它在向 Execution Management 上报 kRunning 之前调用 AliveNotification SWS PHM 第50页。随后，PHM 周期性地评估所有监控，并向 WatchdogInterface 上报其存活性 [SWS_PHM_01255] EXP SWArch 第233页。该上报的周期时间是可配置的，并且可以与真实硬件看门狗的触发时间不同。如果上报中断，WatchdogInterface 自身将触发看门狗响应 EXP SWArch 第130页。

时序图：PHM 在 kRunning 上报之前接管看门狗，并在之后对其进行周期性服务；State Management 通过 Offer() 启用 Recovery 回调。来源：SWS PHM 第50页、EXP SWArch 第215页、EXP SWArch 第233页、EXP SWArch 第200页

各个监控何时开始取决于其类型：

  • Alive Supervision 在关联进程上报 kRunning 后立即启动其首个参考周期。它会忽略此前上报的 Checkpoint SWS PHM 第26页。
  • Deadline Supervision 和 Logical Supervision 从为其上报的第一个 Checkpoint 开始 EXP SWArch 第219页。

所有时间均在报告进程的上下文中利用同一时钟源测量。这样进程间通信的延迟和抖动就不会产生影响 SWS PHM 第27页。

PHM 从 Function Group State 派生出 Supervision Mode SWS PHM 第19页。在状态变更时，进程适用以下规则 SWS PHM 第31页 SWS PHM 第32页：

  • 如果某个进程终止，PHM 会停止其监控并将其评估为正常。
  • 重启被视为终止后紧接着启动。
  • 继续运行的进程保留其原有的监控参数。

R23-11 的说明明确排除了在进程运行期间动态开启和关闭监控 SWS PHM 第32页。而 R25-11 则定义了 SupervisedEntity::Enable [SWS_PHM_01130] 和 Disable [SWS_PHM_01380]。两者均返回 ara::core::Future<void>，可能会因 PhmErrc::kServiceNotReady 而失败，且不是线程安全的。解释：该 API 可能会取代 R25-11 的早期限制；无论如何，规范均以 Requirements 为准。

基本监控状态与全局监控状态

PHM 为每个单独的 Alive、Deadline 和 Logical Supervision 维护其自身的 Elementary Supervision Status SWS PHM 第33页。在代码中与其对应的是 ElementarySupervisionStatus [SWS_PHM_01358]。所有状态机均在 kDEACTIVATED 中启动 SWS PHM 第34页。仅 Alive Supervision 具有容差状态 SWS PHM 第35页：

  • 达到限值 failedReferenceCyclesTolerance 的失败参考周期会导致转换至 kFAILED。
  • 如果超出该限值，状态将转换为 kEXPIRED，并且监控被停止。
  • 对于 Deadline Supervision 和 Logical Supervision，任何错误结果都会直接导致转换至 kEXPIRED。

当进程结束时，状态将返回到 kDEACTIVATED。操作系统、Execution Management 和 State Management 的监控除外；对于它们，预定通过看门狗进行恢复 SWS PHM 第36页 SWS PHM 第37页。

  1. 通过清单分配给 RecoveryAction 端口的 Global Supervision 转换为 kEXPIRED。随后 PHM 调用 RecoveryHandler SWS PHM 第46页。
  2. 由于 ISO 26262 要求安全响应，PHM 通过超时 recoveryNotificationTimeout 监控处理程序的返回 SWS PHM 第48页 SWS PHM 第85页。
  3. 该场景规定了三种结果 EXP SWArch 第234页：
    • State Management 处理该错误。
    • State Management 无法处理该错误并以 kSMCanNotHandleRecovery 响应 [SWS_PHM_01240] EXP SWArch 第220页。
