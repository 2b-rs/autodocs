ara::core 作为所有 Functional Clusters 共同基础的作用

Functional Cluster Core 具有两项任务。它规定了适用于 Adaptive Platform 的所有 Functional Clusters 的基本要求。此外，它还为整个框架提供功能，特别是多个 Functional Clusters 在其公共接口中使用的通用数据类型 (SWS Core 第8页)。Core 本身仅依赖于操作系统接口规范，其核心即 C++ 标准库 (SWS Core 第10页)。所有符号都位于命名空间 ara::core 中，并且除非另有说明，否则都是公开可见的 (SWS Core 第47页)。

这些横切规则同样适用于其他 Cluster 的实现：

  • Include 遵循模式 #include "ara/fc/header.h"。
  • 公共头文件需要尽量系统全局唯一的 Include Guard (SWS Core 第23页)。
  • 带有前缀 ARA 的符号由 AUTOSAR 保留。
  • 声明说明符只能补充 inline 和 friend (SWS Core 第24页)。

架构描述将两组列为原生接口：Initialize()/Deinitialize() 以及 Abort()/SetAbortHandler() (EXP SWArchitecture 第60页, [SWS_CORE_00051])。

上下文图：Core 是应用程序、其他 Functional Clusters 与 C++ 标准库之间的基础层。通过 std::abort 的中止会被 Execution Management 识别为 Abnormal Termination。来源：SWS Core 第8页、SWS Core 第10页、SWS Core 第187页、SWS Core 第39页、EXP SWArchitecture 第60页

ARA 运行时的启动与结束

ara::core::Initialize 是 ARA 框架的（预）初始化。在此之前，禁止与 ARA 进行任何交互。旨在独立于初始化使用的类型除外：

  • ErrorCode 和 StringView，
  • Result，但不含 ValueOrThrow ([SWS_CORE_00766])，
  • ErrorDomain 及其子类，但不含 ThrowAsException ([SWS_CORE_00154]) (SWS Core 第182页)。

该例外的理由是，初始化本身恰恰需要这些类型 (SWS Core 第46页)。Initialize 可以建立数据结构和系统资源，并启动后台线程 (SWS Core 第45页)。必要时，它还会初始化其他 Functional Clusters (SWS Core 第187页)。

ara::core::Deinitialize 用于有序关闭框架。这包括终止后台线程以及释放内存和其他系统资源。如果在此期间并发运行 ARA 调用，其行为是未定义的 (SWS Core 第45页)。在调用之前，必须结束对 ARA 接口的使用。建议的调用位置是在静态初始化之后且静态数据析构之前 (SWS Core 第182页)。

状态图：ARA 运行时通过 Initialize 和 Deinitialize 在三个阶段之间转换。在初始化阶段之外，仅有一组固定类型可用。来源：SWS Core 第182页、SWS Core 第182页、SWS Core 第45页

错误类别和错误值：ErrorCode、ErrorDomain、Result

Core 区分三种失败的操作类型 (SWS Core 第25页)：

  • Error 表示假定无错误的 API 函数无法实现其目的。Error 是可恢复的。
  • Violation 对应于失败的断言，且不可恢复。
  • Corruption 由受损的系统资源引起，同样不可恢复。

每种类型的处理方式均已确定 (SWS Core 第27页)：

  • Error 作为 Result 或 Future 返回。
  • Violation 要么通过未派生自 ara::core::Exception 的异常终止操作，要么通过 ara::core::Abort 终止操作 ([SWS_CORE_00052])。失败的默认分配同样视为 Violation。
  • Corruption 会导致非正常进程终止。

活动图：检测到的条件类型决定了是返回错误值，还是终止操作或进程。来源：SWS Core 第25页、SWS Core 第27页、[SWS_CORE_00052]

ErrorCode 包含三个组成部分：错误值、对错误域的引用以及可选的厂商特定附加数据。它们可以通过 Value() ([SWS_CORE_00514]) 和 SupportData() ([SWS_CORE_00516]) 检索。在进行比较 ([SWS_CORE_00571]) 时，仅考虑值和域，附加数据会被忽略。ErrorCode 通常通过 Result::FromError ([SWS_CORE_00736]) 的转发形式创建 (SWS Core 第28页)。

Result 遵循 ValueOrError 概念：它包含一个值或一个错误。ErrorType 默认为 ErrorCode (SWS Core 第30页)。典型的访问方式有：

  • HasValue() ([SWS_CORE_00751]),
  • Value() ([SWS_CORE_00755]),
  • Error() ([SWS_CORE_00757]),
  • ValueOrThrow() ([SWS_CORE_00766])。该函数将无异常方法与 C++ 异常结合起来。其基类型 ara::core::Exception ([SWS_CORE_00611]) 通过 Error() ([SWS_CORE_00613]) 提供 ErrorCode。

特化 Result<void, E> 省去了 operator-> 和 Bind (SWS Core 第70页, [SWS_CORE_00851])。

使用 Future 和 Promise 的异步结果

Future 和 Promise 紧密借鉴了 std::future 和 std::promise。两者共享一个 Shared State。差异仅源于与 Result 的集成 (SWS Core 第89页)。具体有两个区别：

  • SetError ([SWS_CORE_00353]) 替代了 set_exception。
  • GetResult() ([SWS_CORE_00336]) 返回一个 Result 且从不抛出异常。

分工很明确：Result 用于同步调用，Future 用于异步调用并在随后进行线程安全的检索 (SWS Core 第31页)。

提供方侧的流程：

  1. 提供方创建一个 Promise ([SWS_CORE_00341])。
  2. 它使用 get_future() ([SWS_CORE_00344]) 获取关联的 Future 并将其返回。
  3. 随后，它使用 set_value ([SWS_CORE_00345], [SWS_CORE_00346])、SetError 或 SetResult ([SWS_CORE_00355]) 履行该 Promise。

在 ara::com 中，绑定调用 set_value 或 SetError。阻塞调用 get()、wait()、wait_for() 和 wait_until() 随之返回 (SWS CM 第106页)。一个说明性示例展示了在 Future 已返回之后，在工作线程中完成履行 (EXP ARAComAPI 第59页)。

时序图：提供方立即返回 Future，并在随后异步地用值或错误履行共享状态。来源：[SWS_CORE_00341]、[SWS_CORE_00344]、[SWS_CORE_00345]、[SWS_CORE_00353]、[SWS_CORE_00326]、SWS CM 第106页、EXP ARAComAPI 第59页

消费方有多种访问模式：

  • get() ([SWS_CORE_00326]) 和 wait() ([SWS_CORE_00328]) 会阻塞。
  • wait_for() ([SWS_CORE_00329]) 和 wait_until() ([SWS_CORE_00330]) 返回一个 FutureStatus ([SWS_CORE_00361])。由此可以将就绪的结果与超时区分开来 (ARAComAPI (图 6.15) 第1页)。
  • then() ([SWS_CORE_00331]) 注册一个延续任务，可选带有 Executor ([SWS_CORE_00337])。
  • is_ready() ([SWS_CORE_00332]) 不阻塞，适用于通过轮询工作的实时应用程序 (EXP ARAComAPI 第58页)。

Future 不可复制 ([SWS_CORE_00334])。通过使用默认构造的 Future ([SWS_CORE_00322]) 覆盖该 Future，可以丢弃不再需要的结果 (EXP ARAComAPI 第59页)。此外还提供了一个 Executor。根据签名，execute 返回调用结果的 Future ([SWS_CORE_00024])，而 oneway_execute 不返回任何内容 ([SWS_CORE_00025])。

活动图：消费方在阻塞式检索、限时等待、延续任务和非阻塞式轮询之间进行选择。来源：[SWS_CORE_00326]、[SWS_CORE_00329]、[SWS_CORE_00331]、[SWS_CORE_00332]、[SWS_CORE_00336]、EXP ARAComAPI 第58页

数据类型、容器和内存资源

Core 重新定义了在 C++ 标准中几乎已等价存在的类型。原因在于：std:: 类型的分配行为通常不适合汽车领域。根据 C++ 标准抛出异常的函数，在这些类型中反而会引发 Violation (SWS Core 第41页)。具体而言：

  • Vector 的行为类似于 std::vector，仅默认分配器取决于实现 (SWS Core 第129页, [SWS_CORE_01390])。
  • Map 相应地表现得如同 std::map (SWS Core 第130页, [SWS_CORE_01496])。
  • String 被定义为具有固定字符类型 char 的 BasicString<> (SWS Core 第133页, [SWS_CORE_03001])，且可隐式转换为 StringView ([SWS_CORE_03301])。

规范本身承认，Map、Vector 和 String 的分配行为仅被描述为取决于实现 (SWS Core 第10页)。

其他类型源自较新的 C++ 标准 (SWS Core 第43页)：

  • Optional 映射可选的 Record 元素。是否包含值可通过 operator bool 或 has_value() 进行检查 ([SWS_CORE_01129], SWS Core 第131页, ARAComAPI (图 6.3) 第1页)。
  • StringView 是字符的纯只读视图 (SWS Core 第132页, [SWS_CORE_02112])。
  • Span 是外部对象连续序列的视图 (SWS Core 第137页, [SWS_CORE_01901])。as_bytes 是否可以在没有别名问题的情况下使用，取决于实现 (SWS Core 第155页, [SWS_CORE_01980])。
  • Byte 不是整型类型，且不允许隐式转换 (SWS Core 第44页)。
  • 对于 Array，将 get<I> 与 I >= N 一起使用会导致编译错误 (SWS Core 第127页, [SWS_CORE_01282])。

Release 差异：R21-11 摘录在两点上与 R25-11 需求不一致；一切以需求为准。

  • 根据 R21-11，省略了 Array::at (SWS Core 第41页)。而 R25-11 则将 at() 作为 noexcept 引入 ([SWS_CORE_01273])。
  • 根据 R21-11，Optional 没有 value 成员函数 (SWS Core 第131页)。R25-11 则对其进行了规范 ([SWS_CORE_01130])。

针对内存管理，提供了多态内存资源。基类 MemoryResource 公开提供 allocate/deallocate/is_equal 以及私有 do_* 钩子。其下包含 MonotonicBufferResource 以及同步和未同步的池资源 (EXP SWArchitecture 第61页)。池资源使用 PoolOptions 和上游资源构造 ([SWS_CORE_00030], [SWS_CORE_00067])。它们提供 release() ([SWS_CORE_00037]) 和 upstream_resource() ([SWS_CORE_00038])，且不可复制 ([SWS_CORE_00034], [SWS_CORE_00046])。

自定义错误域以及通过 InstanceSpecifier 进行的实例关联

具有独立逻辑的软件模块应定义其自有的错误域。错误域由五个部分组成，这些部分均位于该模块的命名空间中 (SWS Core 第32页)：

  • 错误枚举、
  • 异常基类、
  • ErrorDomain 子类、
  • 全局访问函数、
  • MakeErrorCode 重载。

这些部分遵循固定规则：

  • 该枚举名为 <SN>Errc，不包含成功值，并将 0 保持未占用 (SWS Core 第33页)。
  • 该子类为 final，并具有别名 Errc 和 Exception（SWS Core 第34页）。
  • 访问函数 Get<SN>ErrorDomain 为 constexpr 并返回一个单例（SWS Core 第35页）。
  • 域必须是字面量类型（SWS Core 第30页）。

域的标识基于唯一的 64 位 ID（[SWS_CORE_00121]、[SWS_CORE_00151]、[SWS_CORE_00137]）。值范围划分为（SWS Core 第37页）：

  • 位 63 = 1 且位 62 = 0：AUTOSAR 域，
  • 高 32 位 = 0xc000'0000：厂商域，
  • 位 63 = 0：用户域。

FutureErrorDomain 的 ID 为 0x8000'0000'0000'0013（[SWS_CORE_00480]）。所有其他 Core 错误均属于 CoreErrorDomain（SWS Core 第84页）。

InstanceSpecifier 建立与模型实例的关联。它通过从 Executable 到 PortPrototype 由“/”分隔的名称列表来标识 AUTOSAR 元模型中的端口原型实例。语法无效的路径会被拒绝。构造有两种途径：无异常的工厂方法 Create，或在输入无效时可能抛出异常的构造函数（SWS Core 第40页）。

发生错误时的行为

ara::core::Abort（[SWS_CORE_00052]）会立即异常终止进程，既不进行栈展开，也不调用静态对象的析构函数（SWS Core 第38页）。该函数具有以下属性：

  • 它永不返回。
  • 它将传入的文本作为日志消息写入标准错误流。
  • 并发的进一步调用将阻塞调用线程。

该调用被视为 Explicit Operation Abortion（SWS Core 第8页）。

通过 SetAbortHandler（[SWS_CORE_00051]）可以安装一个 AbortHandler（[SWS_CORE_00050]）。其类型派生自一个未实现的原型（[SWS_CORE_00053]、SWS Core 第183页）。用于终止进程的处理程序应为此使用 std::abort，以便 Execution Management 能够识别出 Abnormal Termination。如果处理程序返回或未安装处理程序，则 Abort 自身会调用 std::abort()（SWS Core 第39页）。R25-11 还引入了 AddAbortHandler（[SWS_CORE_00054]）。其语义在有效载荷中未作详细说明，因此在此不作展开阐述。

活动图：Abort 始终以进程终止结束，要么通过处理程序，要么通过 std::abort。解释：日志消息在调用处理程序之前输出。来源：SWS Core 第38页、SWS Core 第39页、[SWS_CORE_00051]、[SWS_CORE_00052]

在异步端，销毁的 Promise（[SWS_CORE_00349]）会导致就绪的 Future。该 Future 带有值为 FutureErrc::kBrokenPromise 的 FutureErrorDomain 的 ErrorCode（[SWS_CORE_00400]）。例如，在销毁 ServiceProxy 时会发生这种情况（SWS CM 第290页）。相比之下，ara::com 通过 SetError 报告 ComErrorDomain 的错误来报告通信错误（SWS CM 第300页）。

序列图：销毁代理会销毁 Promise，并使挂起的 Future 携带 kBrokenPromise 就绪。来源：SWS CM 第290页、[SWS_CORE_00349]、[SWS_CORE_00400]、[SWS_CORE_00336]

规定了另外两种错误情况：

  • 如果使用来自外部域的错误代码调用 Message()，则属于 Violation（[SWS_CORE_00153]、SWS Core 第51页）。
  • 来自 Deinitialize 的错误是唯一保证可用的报告途径，例如在 ara::log 已去初始化的情况下。该错误被视为不可恢复（SWS Core 第45页）。
