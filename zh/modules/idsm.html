作为 Adaptive Platform 的 Security Events 集中接收端的 IdsM

Intrusion Detection System Manager (IdsM) 处理安全传感器报告的 Security Events (SEv) (SWS IdsM 第9页)。在 Adaptive Platform 上，它是一个基于守护进程的 Functional Cluster。它提供接口 EventReporter，该接口在 ara::idsm 中实现为一个类 ([SWS_AIDSM_10101], SWS IdsM 第13页)。

用户分为两类：

  • 平台集群：Communication Management、Firewall 和 Diagnostic Management 通过 EventReporter 报告其事件 (EXP SWArchitecture 第124页, SWS Firewall 第11页, SWS Diagnostics 第67页, SWS CM 第34页)。
  • Adaptive Applications: 它们还使用 ReportingModeProvider (EXP SWArchitecture 第121页)。通过 TimestampProvider 和 ContextDataProvider 提供数据 (EXP SWArchitecture 第122页)。通过 QualifiedEventsReceiver 接收已限定事件 (EXP SWArchitecture 第123页)。

所有相关的 Port 接口在 Manifest 元模型中均派生自 IdsmAbstractPortInterface (TPS Manifest 第257页)。

系统边界划定得很窄。IdsM 不了解上下文数据的含义，因此无法自行判断系统是否遭到入侵。检测与响应位于外部，例如在 SOC 中 (SWS IdsM 第11页，截至 R20-11)。

此状态值得一提。来自 R20-11 的若干文档出处虽然带有 AP 文档标识，但根据其自身引言，它们仅涵盖 Classic Platform 的各方面 (SWS IdsM 第10页)。因此，本指南仅引用它们用于概念澄清。

报告 Security Events：EventReporter、重载与数据类型

Reporter 使用针对已建模 SecurityEventReportInterface 端口的 InstanceSpecifier 进行构造 ([SWS_AIDSM_10301])。ReportEvent 没有 Event-ID 参数。报告哪个 SEv 由模型确定：SecurityEventReportToSecurityEventDefinitionMapping 将该端口分配给 Security Extract 的 SecurityEventDefinition。该分配也可以根据特定项目或 OEM 进行补充 (TPS Manifest 第146页)。对于 Functional Cluster，由 FunctionalClusterToSecurityEventDefinitionMapping 承担此角色 (TPS Manifest 第873页)。

所有重载均为 noexcept 且是线程安全的（thread-safe）([SWS_AIDSM_10302]–[SWS_AIDSM_10307])。数据类型概览：

  • ContextDataType 是一个 ara::core::Span<const std::uint8_t> ([SWS_AIDSM_10201])。
  • VersionedContextDataType 将这些数据与一个 std::uint16_t 关联 ([SWS_AIDSM_10206])。
  • TimestampType 是 std::uint64_t ([SWS_AIDSM_10202])。
  • CountType 计算已预限定的出现次数，默认值为 1 ([SWS_AIDSM_10203])。

协议为长上下文数据规定了一个 4 字节的长度字段。以此可以传输多达 231−1 字节 (PRS IDS 第23页)。解释：版本部分大概对应于 SecurityEventContextDataDefinition 的 version，正如带有 version = 1 的示例所示 (TPS SecXT 第66页)。

一个典型的流程是 Firewall 场景：操作系统阻止一个数据包，Firewall 将其转换为 Security Event 并通过 ReportEvent() 进行上报 (EXP SWArchitecture 第232页)。Platform Health Management 也会调用 ReportEvent()，具体是在检查点上报时的访问检查范围内 (EXP SWArchitecture 第236页)。

时序图：从被阻止的数据包到向 IdsM 的上报；上报本身没有返回值。来源：EXP SWArchitecture 第232页、[SWS_AIDSM_10302]

丰富上报内容：TimestampProvider 与 ContextDataProvider

在内容丰富过程中，调用方向发生反转：应用程序是 Provider，IdsM 调用其回调 (EXP SWArchitecture 第122页)。

  • TimestampProvider ([SWS_AIDSM_10400]) 使用 InstanceSpecifier 创建 ([SWS_AIDSM_10401])。应用程序实现抽象回调 GetTimestamp() ([SWS_AIDSM_10407])。Offer() 允许 IdsM 调用它；StopOffer() 则再次阻止该调用 ([SWS_AIDSM_10408]、[SWS_AIDSM_10409])。
  • ContextDataProvider ([SWS_AIDSM_10500]) 在构造函数中还会额外接收 additionalBytes 和 originalContextDataOffset ([SWS_AIDSM_10501])。IdsM 调用 ModifyContextData(contextData, event)，它提供一个 Result<std::size_t> ([SWS_AIDSM_10509])。此处同样由 Offer() 和 StopOffer() 控制这些调用 ([SWS_AIDSM_10507]、[SWS_AIDSM_10508])。

这两个 Provider 均不可复制，但可以移动 ([SWS_AIDSM_10404]、[SWS_AIDSM_10403]、[SWS_AIDSM_10504]、[SWS_AIDSM_10503])。构造函数是线程安全的。而 Offer()、StopOffer() 以及各回调则不是线程安全的 ([SWS_AIDSM_10408]、[SWS_AIDSM_10407]、[SWS_AIDSM_10509])。

状态图：Provider 和 Receiver 的回调仅在 Offer() 与 StopOffer() 之间被允许调用。来源：[SWS_AIDSM_10408]、[SWS_AIDSM_10409]、[SWS_AIDSM_10507]、[SWS_AIDSM_10508]、[SWS_AIDSM_10808]、[SWS_AIDSM_10809]、[SWS_AIDSM_10402]

IdsM 何时调用 GetTimestamp()，有效负载中的 R25-11 需求并未规定。解释：这大概会在上报不带时间戳的 SEv 时发生。Classic Platform 的 R20-11 文本针对“Custom”选项也是这样描述的 (SWS IdsM 第34页)。

时序图：内容丰富回调的提供、使用与撤回。GetTimestamp() 的触发条件属于一种解释，且这两个可选回调的顺序未作规定。来源：EXP SWArchitecture 第122页、[SWS_AIDSM_10407]、[SWS_AIDSM_10509]、SWS IdsM 第34页

上报模式与过滤链：SEv 如何变为 QSEv

ReportingModeType 包含五个值 ([SWS_AIDSM_10207])。它们的含义已记录在文档中 (SWS IdsM 第91页)：

  • kOff：该 SEv 被丢弃。
  • kBrief：该 SEv 在不带上下文数据的情况下被转发。
  • kDetailed：该 SEv 带有上下文数据被转发。
  • kBriefBypassingFilters 和 kDetailedBypassingFilters：分别与 kBrief 和 kDetailed 相同，但会绕过其余的过滤链。

最终类 ReportingModeProvider ([SWS_AIDSM_10600]、[SWS_AIDSM_10601]) 读取并设置每个 Event-ID 的模式。GetReportingMode() 和 SetReportingMode() 用于此目的；两者都不是线程安全的 ([SWS_AIDSM_10602]、[SWS_AIDSM_10603])。

时序图：查询和更改上报模式，包括 Event-ID 未知时的错误情况。来源：[SWS_AIDSM_10601]、[SWS_AIDSM_10602]、[SWS_AIDSM_10603]、[SWS_AIDSM_10204]

Security Extract 将过滤链 SecurityEventFilterChain 建模为分别包含可选的过滤器 (TPS SecXT 第21页)：

  • state
  • 带有参数 n 的 oneEveryN
  • 带有 contextDataSource 和 minimumIntervalLength 的 aggregation
  • 带有 intervalLength 和 thresholdNumber 的 threshold

SecurityEventContextMapping 将事件与过滤链及上报模式相关联。在 Adaptive Platform 上，这是通过 IdsmModuleInstantiation 实现的 (TPS SecXT 第33页)。解释：求值顺序可能与 Classic Platform 的 R20-11 描述一致。据此，首先是上报模式，然后是按模型顺序排列的过滤器，且过滤链在首次丢弃时终止 (SWS IdsM 第25页)。

活动图：上报模式决定是丢弃、执行过滤链还是绕过。过滤器顺序属于一种解释，且未配置的过滤器将被省略。来源：[SWS_AIDSM_10207]、SWS IdsM 第91页、TPS SecXT 第21页、SWS IdsM 第25页

接收合格事件：QualifiedEventsReceiver

应用程序派生自 QualifiedEventsReceiver ([SWS_AIDSM_10800]、[SWS_AIDSM_10801])。它们必须实现 OnEventQualification() 的两个纯虚重载：一个带有未版本化的上下文数据，另一个带有已版本化的上下文数据。上下文数据和时间戳各自作为 ara::core::Optional 传入 ([SWS_AIDSM_10807]、[SWS_AIDSM_10810])。IdsM 调用这些回调 (EXP SWArchitecture 第123页)。Offer() 启用这些调用，StopOffer() 终止它们 ([SWS_AIDSM_10808]、[SWS_AIDSM_10809])。该回调不是线程安全的。

时序图：合格事件接收者的生命周期。来源：[SWS_AIDSM_10801]、[SWS_AIDSM_10807]、[SWS_AIDSM_10808]、[SWS_AIDSM_10809]、EXP SWArchitecture 第123页

实例关联：InstanceSpecifier 与清单映射

每个 API 类都通过一个 InstanceSpecifier 绑定到其建模的端口 ([SWS_AIDSM_10301]、[SWS_AIDSM_10401]、[SWS_AIDSM_10501]、[SWS_AIDSM_10601]、[SWS_AIDSM_10801])。在部署中，四个映射描述了这种绑定。它们都是 UploadableDeploymentElement (TPS Manifest 第881页)：

  • IdsmTimestampProviderMapping 指向 idsPlatformInstantiation、pPortPrototypeInExecutable 和 process (TPS Manifest 第664页)。
  • IdsmContextProviderMapping (TPS Manifest S. 665)
  • IdsmReportingModeProviderMapping (TPS Manifest S. 667)
  • IdsmQualifiedEventReceiverMapping (TPS Manifest S. 669)

IdsM 实例本身具有 idsmInstanceId 和 timestampFormat (TPS SecXT 第59页)。

需求与清单图示之间的差异：[SWS_AIDSM_10601] 和 [SWS_AIDSM_10801] 提到了“建模的 PPort”。而清单图示针对上报模式 Provider 和合格事件 Receiver 则引用了一个 RPortPrototype (TPS Manifest 第667页、第669页)。应以需求为准；在集成过程中应澄清这一差异。

发生错误时的行为

唯一指定的错误码是值为 3 的 IdsmErrc::kUnknownEventId ([SWS_AIDSM_10204])。对于未配置的 Event-ID，GetReportingMode() 和 SetReportingMode() 会返回该错误码 ([SWS_AIDSM_10602]、[SWS_AIDSM_10603])。外围的错误基础设施包括：

  • IdsmErrorDomain ([SWS_AIDSM_10706])，可通过 GetIdsmErrorDomain() 访问 ([SWS_AIDSM_10702])
  • MakeErrorCode() ([SWS_AIDSM_10703])
  • IdsmException ([SWS_AIDSM_10704], [SWS_AIDSM_10705])
  • ThrowAsException() ([SWS_AIDSM_10712])

ReportEvent() 是 void 且 noexcept，因此传感器不会收到有关接受或丢弃的反馈 ([SWS_AIDSM_10302]、[SWS_AIDSM_10307])。根据 R20-11，根据上报频率、关键程度或系统过载情况丢弃 SEv 是明确可接受的 (SWS IdsM 第11页)。

Offer() 的结果应作为 Result<void> 进行评估；StopOffer() 不返回任何内容 ([SWS_AIDSM_10408]、[SWS_AIDSM_10507]、[SWS_AIDSM_10808]、[SWS_AIDSM_10809])。ModifyContextData() 可以通过 Result<std::size_t> 报告错误 ([SWS_AIDSM_10509])。有效负载并未描述 IdsM 如何对此做出反应。非线程安全的操作必须由应用程序自行序列化。
