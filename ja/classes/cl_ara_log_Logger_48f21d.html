class ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Kapselt einen Logging-Kontext zur threadsicheren Erfassung formatierter oder modellierter Protokollnachrichten.

Die Klasse ara::log::Logger repräsentiert einen Kontext für das Erfassen von Log-Nachrichten innerhalb eines Anwendungsprozesses über temporäre Streams oder modellierte Nachrichtenformate [SWS_LOG_00064]. Da der Standardkonstruktor gelöscht ist, erfolgt die Erzeugung und Verwaltung des Lebenszyklus vollständig durch das Logging-Framework [SWS_LOG_00259]. Vor der zeitintensiven Aufbereitung von Meldungsdaten kann der aktuell aktive Meldegrad abgefragt werden. Sämtliche Schnittstellen der Klasse sind threadsicher spezifiziert und erlauben den synchronisationsfreien Aufruf aus mehreren Threads.

Kontext

Die Klasse ara::log::Logger repräsentiert einen Logger-Kontext innerhalb eines Anwendungsprozesses oder Prozessbereichs im Modul log. Ein solcher Kontext kapselt eine spezifische Kontext-ID, eine zugehörige Beschreibung sowie einen Standard-Log-Level. Anwendungsentwickler interagieren mit Logger-Instanzen, um Log-Nachrichten entweder über Stream-Objekte wie LogStream [SWS_LOG_00064] oder als strukturierte, modellierte Meldungen an das Logging-Framework zu übergeben [SWS_LOG_00204]. Die Instanzen agieren als Vermittler zwischen den anwendungsinternen Threads und dem Logging-Backend.

Kontextdiagramm: Einbindung des Loggers zwischen Anwendung, Logging-Framework und LogStream. Quellen: [SWS_LOG_00064], [SWS_LOG_00259].

Lebenszyklus

Die Verwaltung der Instanzen unterliegt einer strikten Eigentümerschaft durch das Logging-Framework. Um die automatische Registrierung am Logging-Backend bei der Erzeugung und die Deregistrierung beim Herunterfahren des Anwendungsprozesses sicherzustellen, ist der Standardkonstruktor gelöscht [SWS_LOG_00259]. Anwendungen dürfen und können Logger-Objekte nicht direkt instanziieren, sondern müssen stattdessen die Erzeugungsfunktionen ara::log::CreateLogger nutzen. Die Zerstörung und Freigabe erfolgt über den Destruktor [SWS_LOG_00260], der vom Logging-Framework gesteuert wird, sodass sich Anwender nicht um die Lebensdauer kümmern müssen.

Hinsichtlich der Nebenläufigkeit sind sämtliche Zugriffsmethoden als threadsicher (thread-safe) spezifiziert, unter anderem [SWS_LOG_00070], [SWS_LOG_00255] und [SWS_LOG_00260]. Dadurch können mehrere nebenläufige Threads denselben Logger-Kontext gleichzeitig verwenden, ohne dass zusätzliche Synchronisationsmechanismen auf Anwendungsseite erforderlich sind.

Nutzungspfad

Der typische Einsatz eines Loggers umfasst die Überprüfung der aktuellen Konfiguration, die Anpassung von Schwellwerten und das Absetzen von Meldungen:

  • Prüfung der Ausgabeberechtigung: Vor aufwendigen Vorbereitungen von Protokolldaten kann mit IsEnabled abgefragt werden, ob ein gewünschter Log-Level aktiv gemeldet wird [SWS_LOG_00070].
  • Konfiguration: Der minimale Melde-Schwellwert einer Logger-Instanz lässt sich zur Laufzeit über SetThreshold neu konfigurieren [SWS_LOG_00255].
  • Stream-basiertes Logging: Über spezifische Methoden für einzelne Schweregrade – LogFatal [SWS_LOG_00064], LogError [SWS_LOG_00065], LogWarn [SWS_LOG_00066], LogInfo [SWS_LOG_00067], LogDebug [SWS_LOG_00068] oder LogVerbose [SWS_LOG_00069] – sowie über das dynamische WithLevel [SWS_LOG_00131] wird ein LogStream-Objekt erzeugt. Dieses nimmt Daten über den Operator << entgegen. Üblicherweise endet die Lebensdauer des Stream-Objekts mit dem Semikolon der Anweisung [SWS_LOG_00064].
  • Modellierte Nachrichten: Alternativ können typisierte und modellierte Nachrichten direkt mit Log [SWS_LOG_00204] oder unter Angabe von Attributen mit LogWith [SWS_LOG_00133] übergeben werden.

Sequenzdiagramm: Typische Abfolge bei der Schwellwertprüfung und Stream-basierten Protokollierung. Quellen: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064].

Fehlerszenarien

Die Schnittstellen der Klasse sind weitgehend als noexcept und ausnahmesicher (exception safe) spezifiziert, was unerwartete Laufzeitunterbrechungen minimiert [SWS_LOG_00070], [SWS_LOG_00255]. Dennoch bestehen formale Fehlerbedingungen und Randfälle:

  • Inkorrekte Modellparameter: Wird Log mit Argumenten aufgerufen, die nicht zur Spezifikation der modellierten Nachricht passen, ist das C++-Programm fehlerhaft aufgebaut (ill-formed) und schlägt zur Übersetzungszeit fehl [SWS_LOG_00204].
  • Fehlende Attribut-Eigenschaften: Enthält das Tupel für LogWith Typen, die nicht den geforderten Attribut-Kriterien entsprechen, nimmt die Funktion nicht an der Überladungsauflösung teil [SWS_LOG_00133]. Die Ausblendung dürfte vermutlich über SFINAE oder Konzepte erfolgen. Question Q-e6179190587f11cb (open)
  • Ausnahmesicherheit beim Abbau: Der Destruktor ~Logger ist als not exception safe deklariert [SWS_LOG_00260]. Dies dürfte darauf zurückzuführen sein, dass beim Entregistrieren am Logging-Backend Fehler auftreten können, die nicht über Ausnahmen propagiert werden dürfen. Question Q-4ac2bed8a8ffd85a (open)
