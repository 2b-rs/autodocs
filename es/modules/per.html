Rol y límite del sistema de ara::per

Persistency ofrece a las Adaptive Applications y a otros Functional Clusters mecanismos para almacenar información en la memoria no volátil de una Machine. Los datos se conservan a través de ciclos de arranque y encendido. Por lo general, el módulo se ejecuta como biblioteca en el Process de la aplicación y con sus permisos SWS Persistency p. 10. Los datos persistentes son siempre locales a exactamente un Process. Persistency no ofrece deliberadamente ninguna vía de comunicación adicional entre Processes SWS Persistency p. 40, SWS Persistency p. 12 y no proporciona por sí misma ninguna Service Interface a través de ara::com SWS Persistency p. 155. Para un acceso remoto basado en servicios a Key-Value Storages, existe en R25-11 un clúster propio basado en daemon, Remote Persistency. Este utiliza, a su vez, la interfaz KeyValueStorage de Persistency SWS RemotePersistency p. 9, EXP SWArchitecture p. 95.

Además de las aplicaciones, los daemons de la plataforma también acceden directamente a Persistency:

  • Time Synchronization, Diagnostic Management y State Management utilizan KeyValueStorage EXP SWArchitecture p. 93.
  • Update and Configuration Management y Diagnostic Management necesitan FileStorage SWS UCM p. 18, EXP SWArchitecture p. 92.

Las partes de biblioteca de dichos clústeres utilizan información propia de Target-Configuration de Persistency SWS Persistency p. 35. Hacia abajo, Persistency se apoya en tres servicios:

  • el sistema operativo o hardware de almacenamiento direccionado directamente SWS Persistency p. 15,
  • Cryptography para todas las operaciones criptográficas SWS Persistency p. 44,
  • una base de tiempo para las marcas de tiempo de los archivos SWS Persistency p. 19.

Diagrama de contexto: Persistency es una biblioteca local al proceso. Las aplicaciones y los demonios de plataforma la utilizan; ella misma se apoya en el sistema operativo, Cryptography y una base de tiempo. Fuentes: EXP SWArchitecture p. 93, EXP SWArchitecture p. 92, SWS VUCM p. 11, SWS RemotePersistency p. 9, SWS Persistency p. 19

Tipos de almacenamiento, handles y referencia de instancia

Persistency ofrece dos formas de acceso independientes SWS Persistency p. 32:

  • Key-Value Storages: claves con valores asociados, similar a una base de datos.
  • File Storages: un conjunto de archivos, similar a un directorio.

Una aplicación puede combinar varios storages de ambos tipos. Las API de ambas formas están completamente separadas. Están diseñadas en torno a ara::per::SharedHandle y ara::per::UniqueHandle, que son proporcionados por funciones de fábrica. Las clases no se pueden construir directamente SWS Persistency p. 74, [SWS_PER_00459], [SWS_PER_00460].

Los dos tipos de handles se comportan de forma diferente:

  • OpenKeyValueStorage [SWS_PER_00052] y OpenFileStorage [SWS_PER_00116] devuelven un SharedHandle [SWS_PER_00369] copiable.
  • Los métodos OpenFile* devuelven un UniqueHandle a un accesor. No es copiable [SWS_PER_00373], sino únicamente movible [SWS_PER_00371].
  • Tras un movimiento, el handle de origen queda vacío. Antes de cada uso, se debe comprobar el estado con operator bool, ya que otros operadores sobre un handle vacío conducen a un comportamiento indefinido [SWS_PER_00398], [SWS_PER_00399].
  • Los propios objetos de almacenamiento no son copiables ni movibles [SWS_PER_00322], [SWS_PER_00324].

La referencia de instancia se realiza a través de ara::core::InstanceSpecifier. Contiene la ruta shortName de un PortPrototype, que está tipificado mediante un PersistencyKeyValueStorageInterface o bien PersistencyFileStorageInterface. Si no coincide con ninguna interfaz configurada para el ejecutable, se notifica un error SWS Persistency p. 100, SWS Persistency p. 114.

Como alternativa, un almacenamiento puede estar vinculado a través de un FunctionalClusterInteractsWithPersistencyDeploymentMapping. Los datos de despliegue se encuentran en PersistencyKeyValueStorage o bien PersistencyFileStorage SWS Persistency p. 34. A nivel de plataforma, R25-11 define el contenedor de configuración Persistency. Este contiene PersistencyGeneral (multiplicidad 1), así como las colecciones opcionales PersistencyKeyValueStorageCollection y PersistencyFileStorageCollection (cada una 0..1) SWS Persistency p. 219. Los textos normativos de R25-11 hablan de «Target Configuration» allí donde pasajes de documentos más antiguos utilizan «manifest» [SWS_PER_00334], [SWS_PER_00357].

Diagrama de colaboración: Desde el InstanceSpecifier, una función de fábrica conduce al handle de almacenamiento compartido y, desde allí, a accesores de archivo exclusivos. Fuentes: SWS Persistency p. 82, EXP SWArchitecture p. 87, [SWS_PER_00375], [SWS_PER_00376], [SWS_PER_00377]

Key-Value Storage: desde la apertura hasta la sincronización

Al abrirse, Persistency crea un almacenamiento temporal sobre el que operan todas las operaciones. La aplicación lo persiste con SyncToStorage o lo restablece con DiscardPendingChanges al último estado persistido SWS Persistency p. 63, [SWS_PER_00049], [SWS_PER_00365].

  • SetValue crea pares o los sobrescribe. Si el nuevo valor tiene un tipo de datos diferente, la función devuelve kDataTypeMismatch [SWS_PER_00046]. Un cambio de tipo solo tiene éxito si el par se elimina previamente SWS Persistency p. 65.
  • GetValue existe como variante con valor de retorno [SWS_PER_00332] y como variante con parámetro de salida para el acceso repetido a valores muy grandes [SWS_PER_00044].
  • Se pueden almacenar todos los tipos de datos de la plataforma, así como datos binarios serializados en forma de Vector o Span de ara::core::Byte SWS Persistency p. 66.

Consultas como GetAllKeys y KeyExists ven el estado de la transacción, no el almacenamiento físico. Solo son exactas si no hay modificaciones paralelas [SWS_PER_00042], [SWS_PER_00043]. GetCurrentValueSize devuelve el tamaño de un valor [SWS_PER_00554].

Incluso después de SyncToStorage, la escritura física puede retrasarse, según la implementación y el sistema de archivos. En caso de una pérdida inmediata de alimentación, los datos pueden perderse o corromperse si no hay redundancia SWS Persistency p. 64, SWS Persistency p. 15.

Diagrama de secuencia: Las modificaciones van a parar inicialmente al almacenamiento temporal. Solo SyncToStorage las cifra en caso necesario, añade redundancia y las escribe. Fuentes: EXP SWArchitecture p. 230, EXP SWArchitecture p. 228, SWS Persistency p. 42, [SWS_PER_00049]

Diagrama de estados: Un Key-Value Storage abierto alterna entre el estado sincronizado y modificaciones pendientes. Las operaciones de Recover y Reset solo son posibles en estado cerrado. Fuentes: SWS Persistency p. 63, SWS Persistency p. 99, SWS Persistency p. 100, [SWS_PER_00365]

File Storage: abrir, leer y escribir archivos

A través del handle FileStorage, la aplicación lista archivos [SWS_PER_00110], comprueba su existencia [SWS_PER_00112] o los elimina [SWS_PER_00111]. Cada tipo de acceso existe en tres sobrecargas: sin modo, con OpenMode y adicionalmente con búfer de usuario, p. ej., [SWS_PER_00376], [SWS_PER_00114], [SWS_PER_00430].

  • En modo lectura, se comienza al principio del archivo [SWS_PER_00376].
  • OpenFileWriteOnly trunca el archivo de forma predeterminada y lo crea en caso necesario [SWS_PER_00377].
  • OpenFileReadWrite también crea los archivos que falten [SWS_PER_00375].
  • Los valores OpenMode se pueden combinar con | y |=, siempre que no entren en conflicto [SWS_PER_00147], [SWS_PER_00144], [SWS_PER_00434].
  • Con kAppend, Persistency sitúa la posición al final del archivo antes de cada escritura SWS Persistency p. 71.

Funciones de lectura y escritura de los accesores:

  • Lectura carácter a carácter (PeekChar, GetChar), texto a texto (ReadText, ReadLine) o binaria (PeekByte, GetByte, ReadBinary) [SWS_PER_00167], [SWS_PER_00168], [SWS_PER_00420], [SWS_PER_00119], [SWS_PER_00421].
  • Las funciones de posición GetPosition, SetPosition, MovePosition y IsEof pertenecen en R25-11 a la clase ara::per::FileAccessor [SWS_PER_00162], [SWS_PER_00164], [SWS_PER_00107].
  • Escritura con WriteText o bien WriteBinary. El momento en que se persisten los datos lo determina la implementación; SyncToFile lo fuerza [SWS_PER_00166], [SWS_PER_00423], [SWS_PER_00122].
  • operator<< es solo una función de conveniencia e ignora los errores de forma silenciosa [SWS_PER_00125].
  • SetFileSize solo puede reducir el tamaño de un archivo [SWS_PER_00428], SWS Persistency p. 72.

Un archivo se cierra cuando su UniqueHandle sale del ámbito de validez. Sus modificaciones quedan persistidas a más tardar al volver a abrirlo o con ara::core::Deinitialize SWS Persistency p. 69. Si se cierra el File Storage, se cierran también todos los archivos aún abiertos. El uso posterior de un UniqueHandle conduce a un comportamiento indefinido SWS Persistency p. 41.

GetFileInfo proporciona la hora de creación, modificación y acceso en nanosegundos desde 1970, así como FileCreationState y FileModificationState [SWS_PER_00438], [SWS_PER_00441], [SWS_PER_00435], [SWS_PER_00436]. GetCurrentFileSize contabiliza únicamente el contenido del archivo. GetCurrentFileStorageSize contabiliza adicionalmente los metadatos, la redundancia y las copias de seguridad [SWS_PER_00407], [SWS_PER_00406], SWS Persistency p. 73.

Diagrama de secuencia: Un archivo se escribe a través de un accesor exclusivo y a continuación se lee línea por línea hasta el final del archivo. El cifrado/descifrado y la redundancia permanecen transparentes para la aplicación. Fuentes: EXP SWArchitecture p. 229, EXP SWArchitecture p. 227, [SWS_PER_00122], [SWS_PER_00107]

Instalación, actualización y restablecimiento de datos persistentes

Update and Configuration Management controla la instalación, la actualización, la finalización, el rollback y la eliminación de software. Los datos persistentes se procesan o bien explícitamente mediante UpdatePersistency en la fase de verificación, o bien implícitamente al abrir un almacenamiento SWS Persistency p. 51, [SWS_PER_00357]. En este proceso, Persistency compara dos versiones guardadas con la configuración actual: la contract version (disposición estructural) y la deployment version (contenido preinstalado) SWS Persistency p. 11, SWS Persistency p. 11.

  • Si faltan datos persistentes, se inicializan. En este proceso, las entradas reciben su initValue SWS Persistency p. 55, SWS Persistency p. 56.
  • Si la deployment version es superior, Persistency crea primero una copia de seguridad. Después, actualiza según la estrategia de actualización keepExisting, overwrite o delete SWS Persistency p. 57, SWS Persistency p. 53.

A través de RegisterApplicationDataUpdateCallback, la aplicación puede asumir sus propias migraciones de datos. El callback recibe el almacenamiento y la contract version utilizada por última vez. Se invoca desde UpdatePersistency, OpenKeyValueStorage o OpenFileStorage [SWS_PER_00356], SWS Persistency p. 75. Tras una verificación correcta, CleanUpPersistency elimina las copias de seguridad [SWS_PER_00567], SWS Persistency p. 61.

Novedades en R25-11:

  • Con CheckForManifestUpdate y ReloadPersistencyManifest, una aplicación en ejecución detecta una configuración instalada por UCM y la vuelve a leer. Los almacenamientos no se actualizan hasta después de cerrarse [SWS_PER_00576], [SWS_PER_00577].
  • RegisterDataUpdateIndication notifica actualizaciones de elementos supervisados [SWS_PER_00578].

Para el restablecimiento se utilizan ResetKeyValueStorage, ResetAllFiles, ResetKey y ResetFile. Estas restablecen el estado tal como tras una nueva instalación a partir de la Target Configuration actual [SWS_PER_00334], [SWS_PER_00336], [SWS_PER_00426], [SWS_PER_00338].

En ResetPersistency, R25-11 difiere del pasaje del documento de R23-11. Allí se describe un restablecimiento al estado de instalación SWS Persistency p. 54. Normativamente, en R25-11 rige lo siguiente: la función elimina todo el contenido de todos los almacenamientos, y estos no se vuelven a crear hasta la siguiente llamada a Open* [SWS_PER_00358].

Diagrama de actividades: Al abrir o en UpdatePersistency, la comparación de versiones decide entre instalación, actualización con copia de seguridad, rollback y acceso sin cambios. Fuentes: SWS Persistency p. 51, SWS Persistency p. 57, SWS Persistency p. 61, EXP SWArchitecture p. 92

Concurrencia, recursos y medidas de protección

Dentro de un Process, está previsto el acceso paralelo desde múltiples hilos. Un SharedHandle puede copiarse a otros hilos, o bien el almacenamiento se vuelve a abrir allí SWS Persistency p. 40. Un almacenamiento no se cierra hasta que todos los SharedHandle asociados hayan salido de su ámbito de validez [SWS_PER_00052].

Para los archivos y las operaciones de administración rigen reglas de exclusión:

  • Los archivos son exclusivos: abrir o modificar un archivo ya abierto devuelve kResourceBusy SWS Persistency p. 41.
  • Las funciones de Recover y Reset de un almacenamiento fallan mientras este permanezca abierto SWS Persistency p. 101, SWS Persistency p. 116.
  • UpdatePersistency falla mientras un SharedHandle esté en uso SWS Persistency p. 76.

Por cada almacenamiento, se pueden configurar un tamaño mínimo y un límite superior activamente supervisado maximumAllowedSize SWS Persistency p. 62. Si se supera, se produce kQuotaExceeded. Un número de archivos superior a maxNumberOfFiles provoca kTooManyFiles SWS Persistency p. 39. GetCurrentKeyValueStorageSize y GetCurrentFileStorageSize consultan el tamaño ocupado [SWS_PER_00405], [SWS_PER_00406].

Las medidas de protección se definen durante el despliegue:

  • El cifrado y la autenticación mediante MAC son transparentes para la aplicación SWS Persistency p. 42.
  • La redundancia mediante CRC, hash o copias es configurable SWS Persistency p. 45. Por lo general, solo la replicación permite una reparación SWS Persistency p. 12.
  • Para los accesos de configuración se han definido mensajes de registro DLT, actualmente en estado DRAFT SWS Persistency p. 104.

Comportamiento en caso de error

Los errores se notifican a través de ara::core::Result con códigos procedentes de ara::per::PerErrc. Los valores 0–255 están reservados para AUTOSAR; a partir de 256, los proveedores de la pila pueden añadir sus propios códigos [SWS_PER_00311], SWS Persistency p. 37. GetPerDomain proporciona el dominio de error global [SWS_PER_00352]. Quien prefiera excepciones puede utilizar ThrowAsException [SWS_PER_00350]. Si no se puede asignar memoria, Persistency finaliza el Process mediante ara::core::Abort SWS Persistency p. 74.

Errores funcionales típicos:

  • kKeyNotFound o bien kFileNotFound para elementos que faltan SWS Persistency p. 64, SWS Persistency p. 68
  • kInvalidOpenMode para modos no permitidos durante la apertura SWS Persistency p. 68
  • kIsEof al leer al final del archivo SWS Persistency p. 39
  • kInitValueNotAvailable cuando ResetKey no encuentra ningún valor inicial SWS Persistency p. 54

En caso de errores de escritura, la especificación define el estado del archivo para cada código de error [SWS_PER_00166], [SWS_PER_00423], SWS Persistency p. 152:

  • kPhysicalStorageFailure: El estado es desconocido.
  • kEncryptionFailed: Permanece persistida una versión anterior.
  • kOutOfStorageSpace: La parte que excede la cuota se descarta.

Los errores de datos que se pueden subsanar mediante redundancia son corregidos implícitamente por Persistency durante el acceso. Un error no llega a la aplicación hasta que la redundancia falla SWS Persistency p. 79. En ambos casos, RegisterRecoveryReportCallback informa a la aplicación. Un RecoveryReportKind distingue las recuperaciones correctas (p. ej., kKeyRecovered) de las fallidas (p. ej., kKeyRecoveryFailed). Además, se notifican los elementos afectados y las instancias redundantes afectadas [SWS_PER_00433], [SWS_PER_00432], SWS Persistency p. 47.

A continuación, la aplicación puede invocar de forma selectiva RecoverKey, RecoverFile, RecoverKeyValueStorage o RecoverAllFiles. Estas funciones operan según el principio de mejor esfuerzo (best effort): tras ello, los contenidos pueden estar desactualizados, restablecidos a valores iniciales o perdidos [SWS_PER_00427], [SWS_PER_00337], [SWS_PER_00333], [SWS_PER_00335]. Los archivos modificados por una reparación son identificables por su FileModificationState SWS Persistency p. 120.

Diagrama de actividades: Un problema de redundancia se corrige de forma transparente y se notifica, o bien se notifica como un error. En el segundo caso, la aplicación decide a través de funciones de Recover o Reset. Fuentes: SWS Persistency p. 79, SWS Persistency p. 47, SWS Persistency p. 48, [SWS_PER_00433]

OpenFileStorage función

Opens a File Storage. OpenFileStorage will fail with kResourceBusy when the File Storage is currently being modified by a call from another thread to UpdatePersistency, CleanUpPersistency, ResetPersistency, RecoverAllFiles, or ResetAllFiles. Because multiple threads can access the same File Storage concurrently, the File Storage might not be closed when the SharedHandle returned by this function goes out of scope. RecoverAllFiles función

Recovers a File Storage, including all files. RecoverAllFiles recovers a File Storage when the redundancy checks fail. It will fail with kResourceBusy when the File Storage is currently open, or when it is modified by a call from another thread to UpdatePersistency, CleanUpPersistency, ResetPersistency, RecoverAllFiles, or ResetAllFiles. This method does a best-effort recovery of all files. After recovery, files might show outdated or initial content, or might be lost.

ara::core::Result< void > RecoverAllFiles (const ara::core::Instance Specifier &fs) noexcept;
RecoverKeyValueStorage función

Recovers a Key-ValueStorage. RecoverKeyValueStorage allows to recover a Key-Value Storage when the redundancy checks fail.
