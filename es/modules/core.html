Papel de ara::core como base común de todos los Functional Clusters

El Functional Cluster Core tiene dos funciones. Establece requisitos básicos que se aplican a todos los Functional Clusters de la Adaptive Platform. Además, proporciona funcionalidad para todo el framework, sobre todo tipos de datos comunes que varios Functional Clusters utilizan en sus interfaces públicas (SWS Core p. 8). El propio Core depende únicamente de la especificación de la interfaz del sistema operativo; es decir, en esencia, de la biblioteca estándar de C++ (SWS Core p. 10). Todos los símbolos se encuentran en el namespace ara::core y son públicamente visibles a menos que se indique lo contrario (SWS Core p. 47).

Las reglas transversales también se aplican a la implementación de otros clusters:

  • Los includes siguen el patrón #include "ara/fc/header.h".
  • Las cabeceras públicas necesitan protectores de inclusión que sean lo más únicos posible en todo el sistema (SWS Core p. 23).
  • Los símbolos con el prefijo ARA están reservados para AUTOSAR.
  • Los especificadores de declaración solo pueden complementarse con inline y friend (SWS Core p. 24).

Como interfaces nativas, la descripción de la arquitectura menciona dos grupos: Initialize()/Deinitialize(), así como Abort()/SetAbortHandler() (EXP SWArchitecture p. 60, [SWS_CORE_00051]).

Diagrama de contexto: Core es la capa base entre las aplicaciones, otros Functional Clusters y la biblioteca estándar de C++. Una terminación mediante std::abort es reconocida por Execution Management como Abnormal Termination. Fuentes: SWS Core p. 8, SWS Core p. 10, SWS Core p. 187, SWS Core p. 39, EXP SWArchitecture p. 60

Inicio y fin del tiempo de ejecución de ARA

ara::core::Initialize es la (pre)inicialización del framework ARA. Antes de esto, cualquier interacción con ARA no está permitida. Se exceptúan los tipos que deben poder utilizarse con independencia de la inicialización:

  • ErrorCode y StringView,
  • Result, pero sin ValueOrThrow ([SWS_CORE_00766]),
  • ErrorDomain con sus subclases, pero sin ThrowAsException ([SWS_CORE_00154]) (SWS Core p. 182).

Esta excepción se justifica en que son precisamente estos tipos los que se necesitan para la propia inicialización (SWS Core p. 46). Initialize puede configurar estructuras de datos y recursos del sistema, así como iniciar hilos en segundo plano (SWS Core p. 45). Si es necesario, también inicializa otros Functional Clusters (SWS Core p. 187).

ara::core::Deinitialize apaga el framework de manera ordenada. Esto incluye finalizar los hilos en segundo plano y liberar memoria y otros recursos del sistema. Si se ejecutan llamadas de ARA en paralelo durante este proceso, el comportamiento es indefinido (SWS Core p. 45). Antes de la llamada, debe haber finalizado el uso de las interfaces de ARA. Se recomienda una ubicación de llamada posterior a la inicialización estática y previa a la destrucción de datos estáticos (SWS Core p. 182).

Diagrama de estados: el tiempo de ejecución de ARA cambia entre tres fases a través de Initialize y Deinitialize. Fuera de la fase inicializada, solo se puede utilizar un conjunto fijo de tipos. Fuentes: SWS Core p. 182, SWS Core p. 182, SWS Core p. 45

Clases de error y valores de error: ErrorCode, ErrorDomain, Result

Core distingue tres tipos de operaciones fallidas (SWS Core p. 25):

  • Un Error significa que una función de la API que se asumía libre de errores no puede cumplir su propósito. Un Error es subsanable.
  • Una Violation corresponde a una aserción fallida y no es subsanable.
  • Una Corruption se produce debido a recursos del sistema dañados y tampoco es subsanable.

Para cada tipo, el tratamiento está definido (SWS Core p. 27):

  • Los Errors se devuelven como Result o Future.
  • Las Violations finalizan la operación ya sea mediante una excepción que no deriva de ara::core::Exception o mediante ara::core::Abort ([SWS_CORE_00052]). Una asignación por defecto fallida también se considera una Violation.
  • Las Corruptions provocan una terminación fallida del proceso.

Diagrama de actividades: el tipo de condición detectada determina si se devuelve un valor de error o si se finaliza la operación o el proceso. Fuentes: SWS Core p. 25, SWS Core p. 27, [SWS_CORE_00052]

Un ErrorCode contiene tres componentes: el valor de error, una referencia al dominio de error y datos adicionales opcionales específicos del fabricante. Se pueden consultar mediante Value() ([SWS_CORE_00514]) y SupportData() ([SWS_CORE_00516]). En la comparación ([SWS_CORE_00571]) solo cuentan el valor y el dominio; los datos adicionales se ignoran. Un ErrorCode se crea normalmente mediante la forma de reenvío de Result::FromError ([SWS_CORE_00736]) (SWS Core p. 28).

Result sigue el concepto ValueOrError: contiene un valor o un error. ErrorType es por defecto ErrorCode (SWS Core p. 30). Los accesos típicos son:

  • HasValue() ([SWS_CORE_00751]),
  • Value() ([SWS_CORE_00755]),
  • Error() ([SWS_CORE_00757]),
  • ValueOrThrow() ([SWS_CORE_00766]). Esta función conecta el enfoque sin excepciones con las excepciones de C++. Su tipo base ara::core::Exception ([SWS_CORE_00611]) proporciona el ErrorCode mediante Error() ([SWS_CORE_00613]).

La especialización Result<void, E> prescinde de operator-> y Bind (SWS Core p. 70, [SWS_CORE_00851]).

Resultados asíncronos con Future y Promise

Future y Promise se basan estrechamente en std::future y std::promise. Ambos comparten un Shared State. Las diferencias surgen únicamente de la integración con Result (SWS Core p. 89). En concreto, existen dos diferencias:

  • SetError ([SWS_CORE_00353]) sustituye a set_exception.
  • GetResult() ([SWS_CORE_00336]) devuelve un Result y nunca lanza excepciones.

La división del trabajo es clara: Result sirve para llamadas síncronas, Future para llamadas asíncronas con recuperación posterior segura para hilos (SWS Core p. 31).

El flujo en la parte del proveedor:

  1. El proveedor crea un Promise ([SWS_CORE_00341]).
  2. Obtiene el Future correspondiente mediante get_future() ([SWS_CORE_00344]) y lo devuelve.
  3. Más adelante, cumple el Promise con set_value ([SWS_CORE_00345], [SWS_CORE_00346]), SetError o SetResult ([SWS_CORE_00355]).

En ara::com, el binding llama a set_value o SetError. Como resultado, las llamadas bloqueantes a get(), wait(), wait_for() y wait_until() retornan (SWS CM p. 106). Un ejemplo explicativo muestra el cumplimiento en un hilo de trabajo una vez que el Future ya ha sido devuelto (EXP ARAComAPI p. 59).

Diagrama de secuencia: el proveedor devuelve el Future inmediatamente y cumple el estado compartido más adelante de forma asíncrona con un valor o un error. Fuentes: [SWS_CORE_00341], [SWS_CORE_00344], [SWS_CORE_00345], [SWS_CORE_00353], [SWS_CORE_00326], SWS CM p. 106, EXP ARAComAPI p. 59

El consumidor tiene varios patrones de acceso:

  • get() ([SWS_CORE_00326]) y wait() ([SWS_CORE_00328]) bloquean.
  • wait_for() ([SWS_CORE_00329]) y wait_until() ([SWS_CORE_00330]) proporcionan un FutureStatus ([SWS_CORE_00361]). Esto permite distinguir un resultado disponible de un timeout (ARAComAPI (Fig. 6.15) p. 1).
  • then() ([SWS_CORE_00331]) registra una continuación, opcionalmente con un Executor ([SWS_CORE_00337]).
  • is_ready() ([SWS_CORE_00332]) no bloquea y es adecuado para aplicaciones de tiempo real que funcionan mediante sondeo (EXP ARAComAPI p. 58).

Los Futures no se pueden copiar ([SWS_CORE_00334]). Un resultado que ya no se necesita se descarta sobrescribiendo el Future con un Future construido por defecto ([SWS_CORE_00322]) (EXP ARAComAPI p. 59). De forma complementaria, existe un Executor. Según la firma, execute devuelve un Future del resultado de la llamada ([SWS_CORE_00024]), mientras que oneway_execute no devuelve nada ([SWS_CORE_00025]).

Diagrama de actividades: el consumidor elige entre recuperación bloqueante, espera con límite de tiempo, continuación y sondeo no bloqueante. Fuentes: [SWS_CORE_00326], [SWS_CORE_00329], [SWS_CORE_00331], [SWS_CORE_00332], [SWS_CORE_00336], EXP ARAComAPI p. 58

Tipos de datos, contenedores y recursos de memoria

Core redefine tipos que ya existen de forma casi equivalente en el estándar de C++. El motivo: el comportamiento de asignación de los tipos std:: a menudo no es adecuado para el sector de la automoción. Las funciones que, según el estándar de C++, lanzan excepciones, provocan en cambio una Violation en estos tipos (SWS Core p. 41). En detalle:

  • Vector se comporta como std::vector, solo que el Default-Allocator depende de la implementación (SWS Core p. 129, [SWS_CORE_01390]).
  • Map se comporta de manera correspondiente como std::map (SWS Core p. 130, [SWS_CORE_01496]).
  • String está definido como BasicString<> con un tipo de carácter fijo char (SWS Core p. 133, [SWS_CORE_03001]) y es convertible implícitamente a StringView ([SWS_CORE_03301]).

La propia especificación reconoce que el comportamiento de asignación de Map, Vector y String solo se describe como dependiente de la implementación (SWS Core p. 10).

Otros tipos proceden de estándares de C++ más recientes (SWS Core p. 43):

  • Optional representa elementos opcionales de Record. Si un valor está presente se comprueba con operator bool o has_value() ([SWS_CORE_01129], SWS Core p. 131, ARAComAPI (Fig. 6.3) p. 1).
  • StringView es una vista de solo lectura sobre caracteres (SWS Core p. 132, [SWS_CORE_02112]).
  • Span es una vista sobre una secuencia contigua de objetos externos (SWS Core p. 137, [SWS_CORE_01901]). Si as_bytes se puede utilizar sin problemas de aliasing depende de la implementación (SWS Core p. 155, [SWS_CORE_01980]).
  • Byte no es un tipo integral y no permite conversiones implícitas (SWS Core p. 44).
  • En Array, get<I> con I >= N da lugar a un error de compilación (SWS Core p. 127, [SWS_CORE_01282]).

Diferencias entre versiones: Los extractos de R21-11 no coinciden en dos puntos con los requisitos de R25-11; los requisitos son determinantes.

  • Según R21-11, se omite Array::at (SWS Core p. 41). En cambio, R25-11 introduce at() como noexcept ([SWS_CORE_01273]).
  • Según R21-11, Optional no tiene funciones miembro value (SWS Core p. 131). R25-11 las especifica ([SWS_CORE_01130]).

Para la gestión de memoria existen recursos de memoria polimórficos. La base MemoryResource ofrece públicamente allocate/deallocate/is_equal y hooks do_* privados. Por debajo se encuentran MonotonicBufferResource, así como recursos de pool sincronizados y no sincronizados (EXP SWArchitecture p. 61). Los recursos de pool se construyen con PoolOptions y un recurso upstream ([SWS_CORE_00030], [SWS_CORE_00067]). Ofrecen release() ([SWS_CORE_00037]) y upstream_resource() ([SWS_CORE_00038]) y no se pueden copiar ([SWS_CORE_00034], [SWS_CORE_00046]).

Dominios de error propios y referencia de instancia mediante InstanceSpecifier

Un módulo de software con lógica propia debe definir sus propios dominios de error. Un dominio de error consta de cinco partes, todas ellas ubicadas en el namespace del módulo (SWS Core p. 32):

  • una enumeración de errores,
  • una clase base de excepción,
  • una subclase de ErrorDomain,
  • una función de acceso global,
  • una sobrecarga de MakeErrorCode.

Para estas partes se aplican reglas fijas:

  • La enumeración se denomina <SN>Errc, no contiene valores de éxito y deja el 0 sin asignar (SWS Core p. 33).
  • La subclase es final y tiene los alias Errc y Exception (SWS Core p. 34).
  • La función de acceso Get<SN>ErrorDomain es constexpr y devuelve un singleton (SWS Core p. 35).
  • Los dominios deben ser tipos literales (SWS Core p. 30).

La identidad de un dominio se basa en un ID de 64 bits único ([SWS_CORE_00121], [SWS_CORE_00151], [SWS_CORE_00137]). El rango de valores está dividido (SWS Core p. 37):

  • Bit 63 = 1 y bit 62 = 0: dominios AUTOSAR,
  • 32 bits superiores = 0xc000'0000: dominios de fabricante,
  • Bit 63 = 0: dominios de usuario.

FutureErrorDomain tiene el ID 0x8000'0000'0000'0013 ([SWS_CORE_00480]). Todos los demás errores de Core pertenecen a CoreErrorDomain (SWS Core p. 84).

InstanceSpecifier establece la referencia a la instancia del modelo. Identifica instancias de prototipos de puerto en el metamodelo de AUTOSAR mediante una lista de nombres separada por «/» desde Executable hasta PortPrototype. Las rutas sintácticamente no válidas se rechazan. Para la construcción existen dos vías: el método de fábrica sin excepciones Create o el constructor, que puede lanzar una excepción en caso de entrada no válida (SWS Core p. 40).

Comportamiento en caso de error

ara::core::Abort ([SWS_CORE_00052]) finaliza el proceso de forma inmediata y anómala, sin desenrollado de pila y sin destructores de objetos estáticos (SWS Core p. 38). La función tiene las siguientes propiedades:

  • Nunca retorna.
  • Escribe el texto pasado como mensaje de registro en el flujo de error estándar.
  • Otras llamadas simultáneas bloquean los hilos llamantes.

La llamada se considera un Explicit Operation Abortion (SWS Core p. 8).

Con SetAbortHandler ([SWS_CORE_00051]) se puede instalar un AbortHandler ([SWS_CORE_00050]). Su tipo se deriva de un prototipo que no está implementado ([SWS_CORE_00053], SWS Core p. 183). Un manejador que finalice el proceso debe utilizar std::abort para ello, de modo que Execution Management reconozca una Abnormal Termination. Si el manejador retorna o no hay ninguno instalado, Abort llama él mismo a std::abort() (SWS Core p. 39). R25-11 introduce además AddAbortHandler ([SWS_CORE_00054]). Su semántica no se describe con más detalle en el payload y, por tanto, no se detalla aquí.

Diagrama de actividades: Abort termina siempre en una finalización del proceso, ya sea mediante el manejador o mediante std::abort. Interpretación: el mensaje de registro se emite antes de la llamada al manejador. Fuentes: SWS Core p. 38, SWS Core p. 39, [SWS_CORE_00051], [SWS_CORE_00052]

En la parte asíncrona, un Promise destruido ([SWS_CORE_00349]) da lugar a un future completado. Este contiene un ErrorCode de FutureErrorDomain con el valor FutureErrc::kBrokenPromise ([SWS_CORE_00400]). Esto ocurre, por ejemplo, cuando se destruye un ServiceProxy (SWS CM p. 290). En cambio, ara::com notifica los errores de comunicación mediante SetError con errores de ComErrorDomain (SWS CM p. 300).

Diagrama de secuencia: la destrucción del proxy destruye el promise y completa el future pendiente con kBrokenPromise. Fuentes: SWS CM p. 290, [SWS_CORE_00349], [SWS_CORE_00400], [SWS_CORE_00336]

Se definen otros dos casos de error:

  • Si se llama a Message() con un código de error de un dominio externo, es una Violation ([SWS_CORE_00153], SWS Core p. 51).
  • Un error de Deinitialize es la única vía de notificación con disponibilidad garantizada, por ejemplo si ara::log ya se ha desinicializado. Se considera no recuperable (SWS Core p. 45).
