Clasificación & Propósito

El módulo ara::core es la biblioteca base fundamental de AUTOSAR Adaptive Platform y se define en la especificación oficial AUTOSAR_AP_SWS_Core.pdf (R25-11). Proporciona el tipo de retorno sin errores ara::core::Result, así como la clase base de dominio de errores ara::core::ErrorDomain, que define el contexto para un conjunto de condiciones de error; las subclases de ErrorDomain son la raíz de todos los datos de error de [SWS_CORE_10303]. El tratamiento de errores en Adaptive Platform se realiza en principio sin C++ Exceptions mediante ara::core::ErrorCode y ara::core::Result conforme al concepto «ValueOrError» (EXP InterfacesGuidelines). Además, AUTOSAR reserva el Namespace ara y todos los Namespaces subordinados; si una Adaptive Application añade allí sus propias declaraciones, el comportamiento no está definido (EXP InterfacesGuidelines). Así, ara::core constituye la base común de la inicialización, el tratamiento de errores y las reglas de concurrencia para todos los Functional Clusters de AP.

Objetos clave y uso típico

ara::core::Result<T, E> contiene un valor o un error; el tipo de error debe ser ErrorCode, de lo contrario hay un error de compilación [SWS_CORE_00701], con especializaciones para tipos de referencia [SWS_CORE_00901] y para valores void [SWS_CORE_00801]. Un Result se crea mediante las funciones estáticas de fábrica FromValue [SWS_CORE_00733] o FromError [SWS_CORE_00736]. Bind aplica un invocable a un valor contenido y devuelve un nuevo Result; Si la instancia no contiene un valor, el error original se adopta sin cambios [SWS_CORE_00768]. Resolve devuelve el valor o llama a un invocable compatible en caso de un error [SWS_CORE_00767], mientras que ErrorOr [SWS_CORE_00764][SWS_CORE_00763] proporciona valores alternativos simples. Las instancias ErrorDomain son ​​iguales si y sólo si sus identificadores únicos de 64 bits coinciden; El acceso suele realizarse a través de accesores que no son miembros, como GetFutureErrorDomain [SWS_CORE_10401].

Para contenedores y procesamiento de texto, el módulo proporciona implementaciones habilitadas para PMR de la biblioteca estándar C++: ara::core::Vector [SWS_CORE_01301], ara::core::Map [SWS_CORE_01400], ara::core::StringView [SWS_CORE_02001], ara::core::BasicString [SWS_CORE_03000] y ara::core::Span [SWS_CORE_01900]. Generación, ciclo de vida y Propiedad

El ciclo de vida de todo el ARA se controla de forma centralizada mediante dos funciones libres ara::core::Initialize y ara::core::Deinitialize. Initialize inicia el marco ARA; esto puede incluir la inicialización de estructuras de datos internas y recursos del sistema, así como el inicio de subprocesos en segundo plano [SWS_CORE_15003]. Si Initialize utiliza la inyección de argumentos de línea de comando, los argumentos relevantes deben eliminarse de forma transparente para que el análisis de argumentos de la aplicación no se vea afectado [SWS_CORE_15006]. Una llamada exitosa coloca el marco en un estado en el que todos los componentes configurados pueden atender inmediatamente llamadas API [SWS_CORE_90026]; una segunda llamada sin previo Deinitialize devuelve kAlreadyInitialized sin perturbar la instancia en ejecución [SWS_CORE_90029]. Deinitialize por el contrario, inicia el cierre del marco, incluida la terminación de los subprocesos en segundo plano iniciados y la liberación de memoria dinámica y otros recursos del sistema [SWS_CORE_15004]; Si el marco no se inicializa correctamente o ya se ha desinicializado, cada llamada devuelve kNotInitialized [SWS_CORE_90030].

Sólo un pequeño subconjunto de ara::core, con nombre explícito, entre otros. ErrorCode, StringView, Result (sin ValueOrThrow), ErrorDomain (sin ThrowAsException), Initialize, Abort, SetAbortHandler y AddAbortHandler - se pueden utilizar independientemente de Initialize/Deinitialize [SWS_CORE_15002]. El comportamiento de todas las demás funciones ARA antes de Initialize está definido por la implementación [SWS_CORE_15005], y una llamada después de Deinitialize fuera de este subconjunto también tiene un comportamiento definido por la implementación, ya que no se requirió deliberadamente una verificación de tiempo de ejecución correspondiente por razones de rendimiento [SWS_CORE_90022]. El Guidelines for using Adaptive Platform interfaces resume esto como un contrato vinculante de inicio/apagado: Initialize debe llamarse en el punto de entrada, Deinitialize solo después de que todos los recursos ARA se hayan liberado en otros subprocesos; ambos devuelven Result<void>, que debe verificarse, y un error no se puede corregir, por lo que la aplicación debe terminar con EXIT_FAILURE (EXP InterfacesGuidelines). Además, AUTOSAR AP RS General prohíbe funciones de inicialización específicas del clúster: si un clúster de funciones requiere una inicialización o desinicialización explícita, debe utilizar exclusivamente ara::core::Initialize/ara::core::Deinitialize.

Manejo de errores, limitaciones de concurrencia &

La especificación define la seguridad de los subprocesos con precisión: una función miembro AUTOSAR-API no estática es thread-safe si se permite llamarla simultáneamente en el mismo objeto desde múltiples subprocesos sin sincronización por parte de el llamador; Los destructores y operadores de asignación generalmente no son thread-safe [SWS_CORE_13200]. Sin embargo, si una función miembro que no es thread-safe se llama simultáneamente en el mismo objeto, el comportamiento no está definido, incluso si la otra función involucrada es thread-safe [SWS_CORE_13203]; Sin embargo, se permiten llamadas competitivas en diferentes instancias sin sincronización [SWS_CORE_13205]. Las Callbacks o funciones puramente virtuales especificadas como non-thread-safe son llamadas por la implementación ARA exclusivamente de forma secuencial, por ejemplo ara::tsync::SynchronizedTimeBaseNotifier, mientras que, por ejemplo, P.ej. ara::phm::RecoveryAction::RecoveryHandler thread-safe es [SWS_CORE_13214]. El uso de cualquier ARA-APIs dentro de un controlador de señal da como resultado un comportamiento indefinido a menos que se especifique lo contrario [SWS_CORE_13210] (EXP InterfacesGuidelines: Seguridad de señal asíncrona). Además, el AUTOSAR AP RS General requiere que cada función API especifique su nivel de thread-safety como «thread-safe», «not thread-safe» o «conditional», y que el contrato de thread-safety se aplique bidireccionalmente: si se especifica un API thread-safe, la implementación proporcionada por el proveedor o usuario, por ejemplo Callbacks o puramente virtual Skeleton funciones cumplen esta promesa (EXP InterfacesGuidelines).

Para errores no recuperables, ara::core distingue la Violation del tratamiento de errores ordinario: una Violation es consecuencia de precondiciones o poscondiciones del framework vulneradas y no es recuperable, comparable a una Assertion fallida [SWS_CORE_00021]. Ante una Violation estandarizada, el proceso finaliza anómalamente mediante ara::core::Abort; se emite un mensaje de depuración conforme a la definición DLT en stderr y debe escribirse en los Log Sinks con el ID de contexto del Functional Cluster que la detectó [SWS_CORE_00090]. Mientras se ejecuta una llamada a Abort, las llamadas adicionales bloquean los hilos que las realizan [SWS_CORE_12407]; los manejadores Abort instalados se llaman en orden inverso al de instalación y, si no hay manejador, se llama a std::abort() [SWS_CORE_12404]. Esta separación entre errores recuperables mediante Result/ErrorCode y Violations no recuperables [SWS_CORE_00021] está respaldada por AUTOSAR AP RS General como principio general para todos los Functional Clusters de AP.

Integración y configuración

Cada Functional Cluster de ARA utiliza, para el logging mediante ara::log, los ajustes estandarizados de Log and Trace de ara::core, en particular el ID de contexto y el intervalo de ID de mensaje [SWS_CORE_00055]. Para ello, la especificación define ID de contexto de registro estandarizados para cada Functional Cluster, entre otros #COM para com, #COR para core, #CRY para crypto, #DIA para diag, #EXE para exec, #LOG para log y #PER para per [SWS_CORE_90024]. En el nivel de requisitos, AUTOSAR AP RS General añade que las interfaces ARA deben utilizar tipos ara::core en lugar de los tipos estándar de C++ si ara::core proporciona un tipo equivalente. Dado que el espacio de nombres ara está reservado íntegramente para AUTOSAR, todos los tipos de datos de un Functional Cluster también están disponibles mediante un archivo de cabecera de reenvío <fc>_fwd.h (EXP InterfacesGuidelines).
