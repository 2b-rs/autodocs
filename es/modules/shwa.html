Rol de Safe Hardware Acceleration y límite con el proceso de aplicación

Safe Hardware Acceleration (SHWA, espacio de nombres ara::shwa) permite utilizar la aceleración de hardware de forma estandarizada y portable para cálculos seguros y eficientes SWS SHWA p. 4. Según el resumen funcional, SHWA proporciona API para Adaptive Applications y otros Functional Clusters. El clúster cubre tres tareas:

  • ejecutar trabajo computacionalmente intensivo en paralelo en el acelerador de hardware (HWA),
  • detectar y corregir errores de las tareas que se ejecutan allí,
  • supervisar los estados de funcionamiento de los aceleradores SWS SHWA p. 7.

Los requirements del clúster deben tener en cuenta los requisitos de seguridad de AUTOSAR SWS SHWA p. 5.

El resumen de la arquitectura clasifica SHWA en la categoría Safety. A diferencia de Platform Health Management, allí SHWA no está identificado como daemon-based EXP SW-Architektur p. 127. Las interfaces son interfaces nativas de C++ que una Adaptive Application utiliza directamente EXP SW-Architektur p. 132. Otros Functional Clusters también pueden utilizar SHWA sin la intervención de una Adaptive Application. Su parte de biblioteca utiliza para ello su propia información de despliegue, y sus daemons se modelan como Adaptive Applications SWS SHWA p. 23.

En la parte del hardware, Device distingue el tipo de unidad de cálculo mediante IsCpu, IsGpu y IsAccelerator [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00311] [AP_SWS_SHWA_00312]. La enumeración Target designa dos ubicaciones de ejecución: kDevice para el dispositivo o acelerador y kHostTask para la CPU host [AP_SWS_SHWA_00102].

Diagrama de contexto: Adaptive Applications y otros Functional Clusters utilizan SHWA como interfaz nativa; SHWA conecta la CPU, la GPU y los aceleradores. Fuentes: SWS SHWA p. 23, EXP SW-Architektur p. 127, [AP_SWS_SHWA_00310]

Cuatro áreas de interfaz de ara::shwa

El diagrama de la especificación divide la API en cuatro áreas: gestión de datos, ejecución de tareas, gestión y supervisión de dispositivos, y tratamiento de errores SWS SHWA p. 17. La explicación de la API describe las tres primeras áreas como capas EXP SHWA-API p. 15.

  • Gestión de datos: Range y Id describen tamaños e índices de una a tres dimensiones [AP_SWS_SHWA_01009] [AP_SWS_SHWA_00709]. A esto se añaden Buffer [AP_SWS_SHWA_00209], Accessor [AP_SWS_SHWA_00007] y PropertyList [AP_SWS_SHWA_00802].
  • Ejecución de tareas: Queue [AP_SWS_SHWA_00908], TaskHandler [AP_SWS_SHWA_01202] y Event [AP_SWS_SHWA_00602].
  • Gestión y supervisión de dispositivos: Platform [AP_SWS_SHWA_01107] y Device [AP_SWS_SHWA_00308]. A esto se añade DeviceSelector con GpuSelector, CpuSelector y AcceleratorSelector [AP_SWS_SHWA_00403] [AP_SWS_SHWA_00407] [AP_SWS_SHWA_00410] [AP_SWS_SHWA_00413], así como DeviceMonitor [AP_SWS_SHWA_01407].
  • Tratamiento de errores: ErrorHandler [AP_SWS_SHWA_00507], ShwaErrorCode [AP_SWS_SHWA_01301], ShwaErrorDomain [AP_SWS_SHWA_01307] y ShwaException [AP_SWS_SHWA_01303].

Una aplicación puede combinar varias Queue, Device y Buffer. Lo mismo se aplica a otros Functional Clusters SWS SHWA p. 22. El diagrama correspondiente muestra dos grupos independientes. Cada grupo consta de una Queue con varias tareas, de Buffer y de un Device SWS SHWA p. 23.

Diagrama de colaboración: Así se relacionan las clases centrales a través de las distintas áreas: la Queue está vinculada a un Device, Submit proporciona un Event y el Accessor accede a un Buffer. Fuentes: SWS SHWA p. 17, [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01407]

Del dispositivo a la Queue: selección y configuración

Un Device se puede determinar de tres formas:

  1. Enumeración: Platform::GetPlatforms proporciona las plataformas disponibles, y GetDevices, sus Devices [AP_SWS_SHWA_01107] [AP_SWS_SHWA_01108].
  2. Sin argumento: Device::Create() [AP_SWS_SHWA_00308].
  3. Mediante un selector: Device::Create(deviceSelector) [AP_SWS_SHWA_00309].

Un DeviceSelector evalúa un Device con operator() y devuelve para ello un Result<int>. SelectDevice proporciona el Device seleccionado [AP_SWS_SHWA_00404] [AP_SWS_SHWA_00403]. GetInfo<InfoType> lee más datos sobre el dispositivo a partir de [AP_SWS_SHWA_00313].

La Queue se crea directamente a partir de un selector o a partir de un Device concreto. En ambas variantes, un ErrorHandler es un parámetro obligatorio y una PropertyList es opcional [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00909]. GetDevice devuelve el Device vinculado. IsInOrder indica si las tareas de la Queue se ejecutan de forma ordenada [AP_SWS_SHWA_00910] [AP_SWS_SHWA_00911] EXP SW-Architektur p. 133.

Diagrama de actividades: Tres vías conducen al Device, dos factorías a la Queue; cada resultado se comprueba como Result. Fuentes: [AP_SWS_SHWA_01107], [AP_SWS_SHWA_00308], [AP_SWS_SHWA_00309], [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]

Proporcionar datos y enviar tareas

Range describe tamaños de una a tres dimensiones [AP_SWS_SHWA_01007] [AP_SWS_SHWA_01009]. Buffer::Create existe en varias variantes [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00210] [AP_SWS_SHWA_00212] [AP_SWS_SHWA_00211] [AP_SWS_SHWA_00213] [AP_SWS_SHWA_00214]:

  • solo con Range,
  • con Range y un asignador adicional,
  • solo con asignador,
  • con datos de host modificables o constantes.

Un Accessor accede a un Buffer. Se crea sin o con TaskHandler [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00008]. Ofrece operator[] con Id o índice lineal [AP_SWS_SHWA_00009] [AP_SWS_SHWA_00010]. Además, ofrece Set y Get con valor de retorno Result [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012]. El acceso se rige por el AccessMode con los valores kRead, kWrite y kReadWrite. En kRead, ReferenceT es una referencia constante [AP_SWS_SHWA_00101] [AP_SWS_SHWA_00014].

Queue::Submit(cfg, ErrorHandler&&) envía una tarea y devuelve un Event [AP_SWS_SHWA_00912]. El TaskHandler ofrece dos modalidades de ejecución: SingleTask para una sola tarea y ParallelFor(bufferSize, cfg) para la ejecución en paralelo de datos [AP_SWS_SHWA_01203] [AP_SWS_SHWA_01204]. El diagrama de casos de uso cita como escenarios de uso «Single Instructions on Multiple Data» y «Multiple Instructions on Multiple Data» EXP SW-Architektur p. 203.

Interpretación: Es de suponer que cfg sea una configuración invocable. Probablemente recibe el TaskHandler, crea en él Accessors y llama a SingleTask o ParallelFor. A esto apunta la factoría de Accessor con parámetro TaskHandler [AP_SWS_SHWA_00008].

Diagrama de secuencias: Se proporcionan datos, se envía una tarea en paralelo de datos y se espera a su finalización. La llamada a cfg está marcada como interpretación. Fuentes: [AP_SWS_SHWA_01007], [AP_SWS_SHWA_00211], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01204], [AP_SWS_SHWA_00604]

Sincronización mediante Events y funciones de espera de la Queue

Cada Submit proporciona un Event [AP_SWS_SHWA_00912]. En el nivel de Event existen tres funciones de espera [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00605] [AP_SWS_SHWA_00606]:

  • Event::Wait() espera a la finalización de las tareas asociadas.
  • La variante estática con lista de eventos espera a varios Events.
  • WaitFor(ms) limita temporalmente la espera.

GetWaitList devuelve una lista de Events [AP_SWS_SHWA_00603]. En el nivel de Queue, Wait() espera de forma bloqueante a todas las tareas en cola, y WaitFor(ms) hace lo mismo con límite de tiempo [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] EXP SW-Architektur p. 133.

Los requirements indican la seguridad para subprocesos de cada función de forma individual:

  • Seguro para subprocesos: Queue::Create, Accessor::Create, Range::Create, así como Accessor::Set y Get [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00007] [AP_SWS_SHWA_01007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012].
  • No seguro para subprocesos: Queue::Submit, Queue::Wait, Event::Wait, Device::Create y Accessor::operator[] [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00308] [AP_SWS_SHWA_00009].
  • Diferencias dentro de una clase: Buffer::Create es seguro para subprocesos, mientras que la variante solo con asignador no lo es [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00212].

Una segunda variante de Submit acepta una secondaryQueue en lugar del ErrorHandler [AP_SWS_SHWA_00913]. Interpretación: Esta Queue probablemente sirva como Queue alternativa si falla la ejecución en la Queue primaria. La variante se remonta al mismo requisito ascendente que el ErrorHandler [AP_SWS_SHWA_00507].

Diagrama de secuencias: Dos Queues funcionan de forma independiente; la aplicación se sincroniza mediante listas de Events o las funciones de espera de la Queue. Fuentes: [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00605], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917], SWS SHWA p. 22

Propiedad de objetos, propiedades y estado del dispositivo

Para todas las clases se aplican tres reglas de diseño EXP SHWA-API p. 15:

  • Los constructores son privados; los objetos se crean mediante métodos Create() con nombre.
  • Las clases propietarias de datos proporcionan std::unique_ptr.
  • La mayoría de los valores de retorno están encapsulados en ara::core::Result.

Una versión R23-11 de la explicación mencionaba en este punto todavía ara::com::SamplePtr EXP Safe-API HWA p. 15. Para R25-11 son determinantes los requirements, y estos establecen std::unique_ptr [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00908].

Para la supervisión, se crea un DeviceMonitor a partir de un Device o de un selector [AP_SWS_SHWA_01407] [AP_SWS_SHWA_01408]. Status() devuelve un DeviceStatus con uno de estos valores [AP_SWS_SHWA_01409] [AP_SWS_SHWA_00103]:

  • kReady: listo para la ejecución de tareas,
  • kNotAccesible: inaccesible,
  • kFailure: estado de error,
  • kUnknown: estado no determinable.

Las fuentes disponibles no determinan si este estado se transmite a otros Functional Clusters.

Diagrama de actividades: El estado se consulta a través del DeviceMonitor y se bifurca según DeviceStatus; la reacción a valores distintos de kReady es una interpretación. Fuentes: [AP_SWS_SHWA_01407], [AP_SWS_SHWA_01409], [AP_SWS_SHWA_00103]

Comportamiento en caso de error

SHWA notifica errores a través de ara::core::Result con códigos de ShwaErrorCode. Entre ellos se incluyen kRuntime, kTaskExecutionFailure, kMemoryNotAllocated, kIntegrityCorrupted (no se puede restablecer la integridad de una memoria búfer), kResourceBusy y kInvalidAccessMode [AP_SWS_SHWA_01301]. Determinadas funciones indican códigos adicionales: kAccessorFailure, kInvalidIndex, kFeatureNotSupported y kEventInvalidOperation [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00313] [AP_SWS_SHWA_00603].

El dominio ShwaErrorDomain proporciona Name, Message y ThrowAsException. GetShwaDomain y MakeErrorCode vinculan los códigos con el dominio. ShwaException transmite un código como excepción [AP_SWS_SHWA_01308] [AP_SWS_SHWA_01309] [AP_SWS_SHWA_01310] [AP_SWS_SHWA_01311] [AP_SWS_SHWA_01312] [AP_SWS_SHWA_01303].

Los errores durante la ejecución y la espera tienen consecuencias especialmente graves. Si Submit, Queue::Wait, Queue::WaitFor o Event::Wait notifican el código kRuntime, los datos de la tarea fallida deben considerarse modificados involuntariamente. En el caso de Event::Wait, esto también se aplica a kTaskExecutionFailure [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] [AP_SWS_SHWA_00604]. Las indicaciones de error de Submit llevan la identificación no_rollback_semantics [AP_SWS_SHWA_00912].

Los recursos ocupados los notifican, entre otros, las consultas de dispositivos y Accessor::Get con kResourceBusy [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00012]. Una asignación fallida la notifica Buffer::Create con kMemoryNotAllocated [AP_SWS_SHWA_00212].

Un ErrorHandler encapsula una función std::function<void(ara::core::ErrorCode)> [AP_SWS_SHWA_00507]. HandleError(ShwaErrorCode) ejecuta el tratamiento y no es seguro para subprocesos [AP_SWS_SHWA_00508]. Cada cola recibe un ErrorHandler al crearse [AP_SWS_SHWA_00908]. Interpretación: es probable que la implementación notifique mediante HandleError errores de tareas enviadas que no se presenten directamente como valor de retorno de Submit; las fuentes no determinan quién invoca HandleError. A nivel de dispositivo, DeviceStatus::kFailure indica un estado de error [AP_SWS_SHWA_00103].

Diagrama de actividades: se evalúa un Result y se clasifican los códigos de error de SHWA, incluidas las consecuencias para los datos en caso de errores de tareas. Fuentes: [AP_SWS_SHWA_01301], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00604], [AP_SWS_SHWA_01310], [AP_SWS_SHWA_00508]

ara::shwa

AcceleratorSelector clase

AcceleratorSelector manages accelerator selection for operations on HWA if available.

Accessor clase

Accessor manages read and write access to allocated memory by Buffer. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

Buffer clase

Buffer manages memory allocation for operations on the host or/and HWA. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

CpuSelector clase

CpuSelector manages CPU selection for operations on HWA if available Allows to get a device from any supported backends for which the device type is CPU.

Device clase

Device class represents HWA device. Provides access to the device but not controlling it. Designed as copyable since not owning resources.

DeviceMonitor clase

DeviceMonitor API class. Designed as copyable since not owning resources.

DeviceSelector clase

Class allowing to choose the most appropriate device of the available ones. This is a callable object taking a device reference and returning an integer rank. One of the device with the highest non-negative value is selected.

ErrorHandler clase

ErrorHandler manages asynchronous error handling for operations on HWA.

Event clase

Event class helps to manage task execution synchronization between HWA and Host application. Can be created only inside of the Queue otherwise it’s meaningless.

GpuSelector clase

GpuSelector manages GPU selection for operations on HWA if available Select a device from any supported backends for which the device type is GPU.

Id clase

Id API class. Designed as copyable since not owning resources.

Platform clase

Platform class is responsible for extracting different HWA platforms available for current application and listing Devices bind to each platform. Designed as copyable since not owning resources.

PropertyList clase

Property List class is designed to enable vendor specific SHWA functionality extension and adjustment. Properties are not standardized and can be defined by Vendor. Class using Property list is obliged to have HasProperty() and GetProperty() methods defined.

Queue clase

Queue API provides the functionality for parallel processing on selected Device. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ ptr, which may be moved. ≙ std::unique_

Range clase

Defines size of Buffer for one, two or three dimensions. Designed as copyable since not owning resources.

ShwaErrorDomain clase

Defines the error domain for Safe Hardware Acceleration.

ShwaException clase

Exception type could be thrown by application or other FC using Safe Hardware Acceleration. Safe Hardware Acceleration API is exception free and can only return an ErrorCode, but user code can transform this error to exception and throw if it’s alligned with system error handling architecture.

TaskHandler clase

Handles tasks execution on the selected Device Can be created only inside of the Queue otherwise it’s meaningless.
