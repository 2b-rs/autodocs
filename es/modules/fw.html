La Firewall como Functional Cluster: rol y límite del sistema

El Functional Cluster Firewall (espacio de nombres ara::fw) proporciona a las aplicaciones exactamente una interfaz de programación funcional. Esta es la clase ara::fw::FirewallStateSwitchInterface con el método SwitchFirewallState [AP_SWS_Fw_82008]. Según la descripción de la arquitectura, el cluster está basado en demonios. Implementa la interfaz FirewallStateSwitchInterface con el estereotipo «aapAPI,aapPortInterface», y una Adaptive Application la utiliza mediante una relación «use» EXP SWArchitecture p. 126. El diagrama de casos de uso menciona dos casos de uso. Una Adaptive Application activa «Switch Firewall State». El Intrusion Detection System Manager participa en «Report Security Event». El Operating System actúa como un actor adicional EXP SWArchitecture p. 197.

El esquema de arquitectura de la SWS separa claramente las responsabilidades:

  • El Machine Manifest proporciona la configuración de la Firewall con sus reglas de filtrado.
  • El FC Firewall configura con ello el Firewall Engine.
  • Una aplicación OEM especifica el estado de la Firewall.
  • Los Security Events (SEvs) se envían al IdsM SWS Firewall p. 16.

La misma distribución muestra el diseño de la plataforma EXP PlatformDesign p. 97. La inspección de paquetes propiamente dicha queda, por tanto, fuera de la API. El escenario relativo al cambio de estado asigna la aplicación de reglas al Operating System y la marca como «aapInformative» EXP SWArchitecture p. 232.

Diagrama de contexto: el FC Firewall actúa de intermediario entre la configuración del manifiesto, la aplicación que especifica el estado, el motor de ejecución o sistema operativo y el IdsM. Fuentes: SWS Firewall p. 16, EXP SWArchitecture p. 126, EXP SWArchitecture p. 232

Filtrado dependiente del estado: estados de Firewall y reglas de filtrado

El núcleo del concepto es el filtrado dependiente del estado. Los estados de Firewall específicos del OEM representan situaciones en las que cabe esperar diferente tráfico de red, como por ejemplo conducción, estacionamiento o una sesión de diagnóstico. Las reglas de filtrado se asignan a un estado. Para la inspección y el filtrado, la Firewall recurre únicamente a las reglas del estado actualmente activo. Una aplicación establece el estado actual a través de la API del FC Firewall EXP PlatformDesign p. 92. En C++, este es el método SwitchFirewallState(EnumT firewallState) [AP_SWS_Fw_82008].

Las reglas en sí son contenido del manifiesto. El diagrama de requisitos de la Foundation muestra cadenas de filtrado a lo largo de varias capas:

  • Ethernet con direcciones MAC y EtherType,
  • IPv4,
  • TCP con detección de estado mediante flags o ICMP,
  • SOME/IP con Service-, Method- y Client-ID RS Firewall p. 12.

En la capa de transporte, el manifiesto modela una FirewallRule con los atributos bucketSize y refillAmount. A esto se añade una TransportLayerRule con rangos de puertos y checksumVerification, que se especializa en reglas UDP y TCP TPS Manifest p. 687.

Si un paquete no coincide con ninguna de las reglas definidas, se aplica la Default Action. La versión R23-11 de la SWS describe adicionalmente cómo se determina la capa de protocolo del mismatch en un paquete bloqueado de este modo. El criterio determinante es la regla con el mayor número de coincidencias consecutivas, contadas a partir de la capa de red más baja. En la primera capa que no coincida se activa un SEv específico de la capa SWS Firewall p. 31. Este pasaje procede de R23-11 y no está cubierto por ningún requisito de R25-11 en el payload. Por lo tanto, debe interpretarse como una aclaración y no como una obligación normativa.

Diagrama de actividades: solo se comprueban las reglas del estado activo de la Firewall. Si no hay coincidencia, se aplica la Default Action y un paquete bloqueado da lugar a un SEv específico de la capa (representación según R23-11). Fuentes: EXP PlatformDesign p. 92, SWS Firewall p. 31

Del InstanceSpecifier al cambio de estado

En primer lugar, una aplicación crea una instancia de FirewallStateSwitchInterface. Para ello sirve el constructor explícito, que espera un ara::core::InstanceSpecifier. Es noexcept y está especificado como thread-safe [AP_SWS_Fw_82002]. Interpretación: es probable que el InstanceSpecifier designe el RPortPrototype de la aplicación, el cual está tipificado en el manifiesto mediante FirewallStateSwitchInterface. El diagrama del manifiesto establece exactamente esta relación de puertos, pero no menciona el especificador TPS Manifest p. 677.

SwitchFirewallState(EnumT firewallState) activa el cambio de estado. El método es noexcept y devuelve un ara::core::Future<void> [AP_SWS_Fw_82008]. El escenario «Switch Firewall State» muestra la secuencia en tres pasos:

  1. La Adaptive Application invoca SwitchFirewallState() en el FC Firewall.
  2. El FC Firewall invoca en un bucle applyRule() en el Operating System para cada FirewallRule.
  3. A continuación, la respuesta regresa a la aplicación EXP SWArchitecture p. 232.

La representación de R22-11 de este mismo escenario muestra el mismo flujo EXP SWArchitecture p. 158. Dado que applyRule() está marcado como «aapInformative», el bucle describe el principio general. No define una interfaz vinculante del sistema operativo EXP SWArchitecture p. 232.

Diagrama de secuencias: la aplicación construye la instancia de la interfaz y solicita el cambio de estado. El FC Firewall aplica cada regla y el resultado se devuelve como ara::core::Future<void>. Fuentes: [AP_SWS_Fw_82002], [AP_SWS_Fw_82008], EXP SWArchitecture p. 232

Tipos de estado generados y vinculación con el manifiesto

Los estados permitidos de la Firewall no constituyen un tipo de plataforma fijo. Para cada interfaz modelada se genera un enum class {<fwssi-sn>} : std::uint32_t propio en el espacio de nombres ara::fw::states. Se incluye mediante ara/fw/states/{<fwssi-sn>}.h, y la lista de enumeradores procede del modelo [AP_SWS_Fw_81001]. Para cada estado de Firewall modelado se genera un enumerador de la forma {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002]. Interpretación: el tipo de parámetro EnumT de SwitchFirewallState probablemente represente este tipo de estado generado, ya que [AP_SWS_Fw_81001] lo define expresamente como tipo de estado para FirewallStateSwitchInterface [AP_SWS_Fw_82008].

En el metamodelo, FirewallStateSwitchInterface es un PortInterface. Agrega a través del rol firewallStateMachine (0..*) elementos del tipo ModeDeclarationGroupPrototype TPS Manifest p. 263. Es de suponer que los modos de este grupo proporcionan los enumeradores de [AP_SWS_Fw_81002]. Sin embargo, las fuentes no describen este mapeo de forma explícita.

A nivel de máquina, AdaptiveFirewallModuleInstantiation recopila la configuración específica de la máquina de la Firewall (TPS_MANI_03296, estado DRAFT). La metaclase AdaptiveFirewallToPortPrototypeMapping conecta esta instanciación mediante la referencia firewall (0..1) con el RPortPrototype de la aplicación TPS Manifest p. 677. La nota de esta metaclase habla en este contexto de un «FirewallModeSwitchInterface». En cambio, el diagrama y la API utilizan de manera uniforme FirewallStateSwitchInterface TPS Manifest p. 677.

Diagrama de colaboración: el diagrama muestra la cadena desde la instanciación de la Firewall, pasando por el mapeo y el puerto de aplicación, hasta el tipo de estado generado. Las aristas hacia InstanceSpecifier y hacia el enum generado son interpretaciones. Fuentes: TPS Manifest p. 263, TPS Manifest p. 677, [AP_SWS_Fw_81001], [AP_SWS_Fw_82002]

Ciclo de vida y concurrencia de la instancia de interfaz

Una instancia de FirewallStateSwitchInterface no es copiable. El constructor de copia y la asignación por copia están eliminados [AP_SWS_Fw_82004] [AP_SWS_Fw_82005]. Por el contrario, mover está permitido, ya que el constructor de movimiento y la asignación por movimiento están noexcept [AP_SWS_Fw_82006] [AP_SWS_Fw_82007]. Por lo tanto, una instancia puede transferirse a otro propietario, pero no duplicarse.

La seguridad para subprocesos está definida para cada operación. La siguiente tabla resume las indicaciones de [AP_SWS_Fw_82002] a [AP_SWS_Fw_82008]:

Destructor[AP_SWS_Fw_82003]not thread-safe
Constructor de movimiento[AP_SWS_Fw_82006]not thread-safe
Asignación por movimiento[AP_SWS_Fw_82007]not thread-safe
SwitchFirewallState[AP_SWS_Fw_82008]sin indicación en el payload

La destrucción y el movimiento deben protegerse externamente frente al uso simultáneo de la misma instancia [AP_SWS_Fw_82003] [AP_SWS_Fw_82006]. Para SwitchFirewallState, el payload no contiene ninguna indicación sobre la seguridad para subprocesos [AP_SWS_Fw_82008]. Por lo tanto, no deben asumirse llamadas paralelas a la misma instancia sin consultar previamente con el proveedor de la plataforma.

Security Events al Intrusion Detection System Manager

Además de la conmutación de estado, la Firewall admite el Intrusion Detection System. Para los mensajes bloqueados se especifica un conjunto de Security Events que se notifican al IdsM. El IdsM se encarga de su cualificación y tratamiento posterior. Los reenvía a un SOC o los almacena de forma persistente en la unidad de control EXP PlatformDesign p. 92. El escenario «Report Security Event» conecta el Operating System, el FC Firewall y el IdsM a través de las interacciones packetBlocked(), handlePacketBlocked(), raiseSecurityEvent() y ReportEvent(). Partes de este están marcadas como «aapInformative» EXP SWArchitecture p. 232.

Para los paquetes que bloquea la Default Action, la SWS de R23-11 indica eventos específicos de cada capa SWS Firewall p. 31:

  • SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH para Ethernet,
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

Estos nombres de eventos no están cubiertos en el payload por requisitos de R25-11. Su validez para R25-11 debe verificarse con respecto a la SWS actual SWS Firewall p. 31.

Diagrama de secuencia: el FC Firewall traduce un paquete bloqueado a un Security Event y lo notifica al IdsM. El orden de los pasos parciales se interpreta a partir de los textos de las figuras. Fuentes: EXP SWArchitecture p. 232, EXP PlatformDesign p. 92

Comportamiento en caso de error

Para SwitchFirewallState se especifican dos errores: FwErrc::kServiceNotAvailable y FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]. Sus valores los establece la enumeración FwErrc, concretamente kServiceNotAvailable=1 y kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]. El método es noexcept y devuelve un ara::core::Future<void>. Por lo tanto, el llamador evalúa estos errores a través del future y no mediante una excepción de la llamada [AP_SWS_Fw_82008].

Ambos errores pertenecen a FwErrorDomain. El dominio proporciona los siguientes bloques:

  • GetFwErrorDomain() devuelve una referencia al objeto de dominio; la función es constexpr y thread-safe [AP_SWS_Fw_83002].
  • MakeErrorCode crea un ara::core::ErrorCode a partir de un FwErrc y datos adicionales [AP_SWS_Fw_83003].
  • Name() y Message() proporcionan el nombre del dominio y el texto del mensaje para un código; ambos son thread-safe [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • Los alias Errc y Exception hacen referencia a FwErrc y FwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

El constructor por defecto del dominio está eliminado, aunque su descripción dice «Constructs a new FwErrorDomain object» [AP_SWS_Fw_83009]. Por tanto, el acceso al dominio se realiza a través de GetFwErrorDomain().

Quien desee propagar un error como excepción utiliza ThrowAsException. La función genera y lanza una FwException. Es noexcept(false) y está clasificada como «not exception safe» [AP_SWS_Fw_83012]. La excepción en sí se crea a través del constructor explícito y thread-safe FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005].

A nivel de paquete, el caso de error es el bloqueo de un paquete. Los paquetes sin una regla coincidente caen bajo la Default Action, y los mensajes bloqueados se notifican como Security Events al IdsM EXP PlatformDesign p. 92. La interfaz en [AP_SWS_Fw_82008] no prevé un canal de retorno a la aplicación para dichos eventos. Su tratamiento corresponde al IdsM.

Diagrama de actividades: el diagrama muestra la evaluación del resultado del future de SwitchFirewallState, la asignación de los dos valores de FwErrc y el relanzamiento opcional como FwException. Fuentes: [AP_SWS_Fw_82008], [AP_SWS_Fw_83001], [AP_SWS_Fw_83002], [AP_SWS_Fw_83012]
