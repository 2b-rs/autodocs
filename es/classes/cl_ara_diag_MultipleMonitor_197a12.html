Contexto

La clase ara::diag::MultipleMonitor sirve para la implementación de operaciones de monitor a través de interfaces de monitor agrupadas ([SWS_DM_01695]). Actúa como intermediario central entre la lógica funcional y de diagnóstico específica de la aplicación y el sistema de diagnóstico (Diagnostic Management, DM). Mientras que un monitor simple solo representa una única ruta de monitorización de fallos, MultipleMonitor permite gestionar y notificar el estado de múltiples monitores a través de un puerto de interfaz común ([SWS_DM_01695], [SWS_DM_01698]).

La vinculación al modelo de AUTOSAR se realiza a través de una instancia de puerto (PortPrototype) del tipo DiagnosticMultipleMonitorInterface ([SWS_DM_01695]). A través de este puerto, la instancia de monitorización se registra y reenvía comandos y respuestas, tales como controles de antirrebote y el estado de calificación, al DM, o bien recibe solicitudes del sistema de diagnóstico ([SWS_DM_01698], [SWS_DM_01699]).

Ciclo de vida

Una instancia de MultipleMonitor posee una identidad de objeto estricta y está vinculada a un contexto de ejecución firmemente definido. El constructor requiere un ara::core::InstanceSpecifier que direcciona el puerto correspondiente en el modelo del sistema ([SWS_DM_01695]). Para evitar efectos secundarios y vinculaciones múltiples, tanto el constructor de copia como el constructor de movimiento (Move) y los operadores de asignación asociados están explícitamente eliminados ([SWS_DM_02065], [SWS_DM_02066], [SWS_DM_02063], [SWS_DM_02064]). De este modo, se excluye la transferencia de la instancia entre ámbitos.

Tras la instanciación, el objeto se encuentra en estado de inicialización: cada monitor gestionado en él debe configurarse exactamente una vez antes de su primer uso mediante una de las sobrecargas de ConfigureMonitor ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). En cuanto los monitores están inicializados, una llamada a Offer() activa el reenvío de solicitudes por parte de Diagnostic Management ([SWS_DM_01699]). El reenvío se puede suspender de nuevo a través de StopOffer() ([SWS_DM_01700]). En cuanto a la seguridad de subprocesos, la construcción es thread-safe ([SWS_DM_01695]), mientras que los métodos de configuración y provisión (ConfigureMonitor, Offer, StopOffer) no son thread-safe ([SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700]). La notificación mediante ReportMonitorAction está protegida en función del modelo de concurrencia definido en el diseño o en el constructor ([SWS_DM_01698]).

Diagrama de estados: estados del ciclo de vida de una instancia de MultipleMonitor, desde la creación, pasando por la configuración y provisión, hasta la detención. Fuentes: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700].

Ruta de uso

El flujo habitual para el uso de MultipleMonitor se divide en las fases de creación, configuración individual de monitores, provisión y notificación continua de eventos:

  1. Creación: la aplicación instancia MultipleMonitor especificando el InstanceSpecifier ([SWS_DM_01695]).
  2. Configuración del monitor: para cada evento monitorizado o cada monitorHandle, se define la estrategia de antirrebote adecuada. AUTOSAR prevé para ello cuatro sobrecargas dedicadas de ConfigureMonitor:
    • Antirrebote interno del monitor con registro de un callback para determinar el Fault Detection Counter (FDC) ([SWS_DM_01696]).
    • Antirrebote basado en tiempo pasando parámetros del tipo TimeBased ([SWS_DM_01697]).
    • Antirrebote basado en contador mediante parámetros del tipo CounterBased ([SWS_DM_01702]).
    • Funcionamiento sin antirrebote, donde únicamente se registra el InitMonitorNotifier opcional ([SWS_DM_01973]).
    Cada sobrecarga solo debe llamarse exactamente una vez por handle de monitor ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]).
  3. Oferta de servicio: mediante la llamada a Offer() se activa la interfaz, de modo que el demonio de Diagnostic Management puede entregar solicitudes a este gestor ([SWS_DM_01699]).
  4. Notificación de estado: durante el funcionamiento, la lógica de la aplicación transmite resultados de comprobación, comandos de control de antirrebote o comandos de prealmacenamiento a través de ReportMonitorAction(monitorHandle, action) ([SWS_DM_01698]).
  5. Desactivación: antes del apagado o en caso de desactivación temporal del reenvío de diagnóstico, se llama a StopOffer() ([SWS_DM_01700]).

Diagrama de secuencia: orden de llamada típico para la configuración, provisión y notificación de estado de múltiples monitores de diagnóstico. Fuentes: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01698], [SWS_DM_01699], [SWS_DM_01700].

Escenarios de error

En MultipleMonitor, las situaciones de error se señalizan en parte a través de violaciones de plataforma estandarizadas (Violations) y en parte a través de ara::core::Result con códigos de error específicos:

  • Violaciones de modelo y de proceso durante la construcción: Si falla la asignación del InstanceSpecifier, se producen violaciones en tiempo de ejecución documentadas ([SWS_DM_01695]):
    • InstanceSpecifierMappingIntegrityViolation: el identificador no se puede resolver en el modelo del ejecutable o no hace referencia a un PortPrototype.
    • PortInterfaceMappingViolation: el puerto referenciado no está tipado mediante un DiagnosticMultipleMonitorInterface.
    • ProcessMappingViolation: no existe un contexto de proceso adecuado en tiempo de ejecución para el proceso modelado.
    • InstanceSpecifierAlreadyInUseViolation: el identificador ya está ocupado por otra instancia en el proceso en ejecución.
  • Error de configuración: En caso de error, una llamada a ConfigureMonitor devuelve DiagErrc::kInvalidArgument ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). Esto ocurre, por ejemplo, si se pasan parámetros no válidos o estados de antirrebote contradictorios (p. ej., kPreFailed en el antirrebote interno).
  • Error de provisión: Si se llama a Offer() mientras el servicio ya se está ofreciendo, la operación falla con el código de error DiagOfferErrc::kAlreadyOffered ([SWS_DM_01699]).
  • Handles de monitor no válidos durante la notificación: Si se pasa a ReportMonitorAction un monitorHandle no configurado o erróneo, la llamada no se cancela, sino que se ignora de forma silenciosa según la especificación ([SWS_DM_01698]).

Esta guía de clase se basa en los requisitos de AUTOSAR Adaptive Platform para el módulo Diag (Release R25-11).
