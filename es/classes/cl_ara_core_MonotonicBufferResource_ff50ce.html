Gestiona bloques de memoria en un búfer de crecimiento monótono con asignación sin excepciones y liberación colectiva.

La clase ara::core::MonotonicBufferResource proporciona un recurso de memoria especializado para asignaciones rápidas y monótonas a partir de un búfer de memoria fijo o a través de un recurso ascendente (upstream). La memoria solicitada se concede paso a paso y, en las desasignaciones individuales, no se libera de inmediato, sino que se restablece de forma agrupada mediante release() ([SWS_CORE_06530]). Todas las operaciones están declaradas completamente libres de excepciones, señalándose la falta de memoria mediante la devolución de nullptr en lugar de una excepción ([SWS_CORE_06569]). Las instancias no son copiables y requieren sincronización externa en caso de acceso concurrente desde múltiples subprocesos.

Contexto

La clase ara::core::MonotonicBufferResource es un recurso de memoria concreto dentro del módulo core de la plataforma AUTOSAR Adaptive y hereda de la clase base ara::core::MemoryResource. Adapta el concepto conocido del estándar C++ de std::pmr::monotonic_buffer_resource procedente de [mem.res.monotonic.buffer] para aplicaciones vehiculares deterministas y relevantes para la seguridad. La función principal de la clase consiste en atender solicitudes de asignación con un mínimo de sobrecarga de gestión a partir de un área de memoria continua, asignando memoria de forma monótona.

Como participantes en la interacción actúan, por un lado, componentes invocadores, asignadores polimórficos y contenedores que solicitan bloques de memoria en tiempo de ejecución. Por otro lado, la clase interactúa con un recurso de memoria upstream superior opcional (MemoryResource). Este recurso upstream puede transferirse a través de constructores como [SWS_CORE_06521] y consultarse mediante el método de acceso upstream_resource() ([SWS_CORE_06531]).

Ciclo de vida

La inicialización de ara::core::MonotonicBufferResource puede controlarse a través de varios constructores. Además de un constructor por defecto sin parámetros ([SWS_CORE_06524]), se dispone de sobrecargas que reciben un recurso upstream explícito ([SWS_CORE_06521]), definen un tamaño de búfer inicial ([SWS_CORE_06525], [SWS_CORE_06522]) o utilizan un área de memoria bruta proporcionada externamente (void* buffer, std::size_t buffer_size) como búfer inicial ([SWS_CORE_06526], [SWS_CORE_06523]).

En relación con las relaciones de propiedad, la clase está definida como estrictamente no copiable: el constructor de copia ([SWS_CORE_06527]) y el operador de asignación por copia ([SWS_CORE_06529]) están eliminados (=delete). A diferencia del estándar ISO-14882, la clase AUTOSAR implementa, sin embargo, semántica de movimiento explícita mediante el constructor de movimiento ([SWS_CORE_06576]) y el operador de asignación por movimiento ([SWS_CORE_06577]), definidos respectivamente como noexcept=default.

La destrucción tiene lugar a través del destructor ~MonotonicBufferResource() ([SWS_CORE_06528]). Una divergencia esencial de AUTOSAR respecto al estándar radica en que el destructor no está declarado como virtual. Mediante el método release() ([SWS_CORE_06530]) se puede restablecer toda la memoria asignada antes de que finalice la vida útil del objeto.

En lo que respecta a la concurrencia, debe observarse una estricta separación: el constructor sin parámetros ([SWS_CORE_06524]), la comprobación de igualdad do_is_equal() ([SWS_CORE_06571]) y la consulta upstream_resource() ([SWS_CORE_06531]) están declarados como seguros para subprocesos (thread-safe). Todos los constructores parametrizados ([SWS_CORE_06521], [SWS_CORE_06522], [SWS_CORE_06523], [SWS_CORE_06525], [SWS_CORE_06526]), las operaciones de asignación ([SWS_CORE_06569], [SWS_CORE_06570]), release() ([SWS_CORE_06530]) y el destructor ([SWS_CORE_06528]) no son seguros para subprocesos y requieren sincronización externa en caso de acceso paralelo.

Ruta de uso

Un flujo de aplicación típico comprende la provisión, la asignación continuada y la liberación colectiva:

  1. Instanciación: La aplicación crea una instancia, por ejemplo especificando un tamaño de búfer y un recurso upstream ([SWS_CORE_06522]) o un búfer fijo ([SWS_CORE_06526]).
  2. Asignación: Las solicitudes de memoria se atienden a través del método protegido do_allocate(bytes, alignment) ([SWS_CORE_06569]). Si el búfer existente no basta, la instancia obtiene nuevo búfer del recurso upstream.
  3. Desasignación: Las invocaciones de do_deallocate(p, bytes, alignment) ([SWS_CORE_06570]) no reducen el búfer de forma individual; el puntero interno de asignación avanza monótonamente.
  4. Restablecimiento del búfer: Con release() ([SWS_CORE_06530]) se liberan de una vez todos los bloques de memoria obtenidos a través de upstream, y el búfer queda disponible para nuevos ciclos.
  5. Comparación de recursos: A través de do_is_equal() ([SWS_CORE_06571]) se puede comprobar si dos recursos de memoria son idénticos.

Diagrama de secuencia: ciclo de memoria típico desde la asignación, pasando por la desasignación ignorada, hasta el restablecimiento colectivo mediante release(). Fuentes: [SWS_CORE_06522], [SWS_CORE_06569], [SWS_CORE_06570], [SWS_CORE_06530]

Escenarios de error

La clase sigue directrices estrictas para sistemas embebidos libres de excepciones: todas las funciones miembro, constructores y operadores están declarados como noexcept y ofrecen total seguridad frente a excepciones.

En caso de error, el comportamiento difiere deliberadamente de la biblioteca estándar:

  • Asignación fallida: Si una solicitud en do_allocate() ([SWS_CORE_06569]) no puede atenderse, no se lanza ninguna excepción std::bad_alloc, sino que se devuelve un nullptr. Los invocadores deben comprobar obligatoriamente si el valor de retorno es nullptr.
  • Error en la desasignación: Si se produjera un error durante la liberación en do_deallocate() ([SWS_CORE_06570]), este se ignora silenciosamente según la especificación.
  • Destrucción a través de un puntero base: Dado que el destructor ([SWS_CORE_06528]) no es virtual, es probable que una destrucción a través de un puntero a la clase base MemoryResource provoque un comportamiento indefinido (interpretación: la destrucción debe tener lugar a través del tipo concreto).
