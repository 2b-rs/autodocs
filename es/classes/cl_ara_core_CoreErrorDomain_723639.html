Contexto

La clase ara::core::CoreErrorDomain representa el dominio de error canónico para causas de error que proceden del Functional Cluster ara::core de la Adaptive Platform. Como especialización final de la clase base abstracta ara::core::ErrorDomain, encapsula la identificación específica de dominio, así como la representación textual y basada en excepciones de estados de error.

En el sistema de tipos de ara::core, la clase actúa como nexo central entre causas de error, códigos de error y tipos de excepción:

  • Clase base: hereda de ara::core::ErrorDomain e implementa su interfaz para el módulo core.
  • Códigos de error: a través del alias de tipo Errc [SWS_CORE_05231], el dominio incorpora la enumeración CoreErrc, que define los valores clave de error admisibles.
  • Excepciones: a través del alias de tipo Exception [SWS_CORE_05232], el dominio hace referencia a la clase de excepción CoreException, que se lanza en caso de tratamiento de excepciones sincrónico [SWS_CORE_05244].
  • Nombre de dominio: el método Name() [SWS_CORE_05242] devuelve el nombre corto simbólico del dominio.

Diagrama de contexto: clasificación de CoreErrorDomain en la estructura de tipos de ara::core. Fuentes: [SWS_CORE_05231], [SWS_CORE_05232], [SWS_CORE_05244]

Ciclo de vida

La creación de una CoreErrorDomain se realiza a través del constructor predeterminado sin parámetros CoreErrorDomain() [SWS_CORE_05241]. Este está especificado como constexpr y noexcept, por lo que las instancias ya pueden construirse en tiempo de compilación.

En cuanto a relaciones de propiedad, gestión de estados y concurrencia, se aplican las siguientes propiedades:

  • Sin estado: la clase no mantiene ningún estado mutable en tiempo de ejecución; todas las funciones de consulta y transformación están declaradas como const.
  • Mantenimiento de instancias: Interpretación: debido al constructor constexpr y a la funcionalidad pura de metadatos, es probable que en sistemas típicos baste una instancia proporcionada estáticamente para cubrir todas las traducciones de errores del dominio.
  • Concurrencia: todas las interfaces especificadas —constructor [SWS_CORE_05241], consulta de nombre [SWS_CORE_05242], consulta de texto de mensaje [SWS_CORE_05243] y lanzamiento de excepciones [SWS_CORE_05244]— están clasificadas explícitamente como seguras para subprocesos (thread-safe). Se pueden invocar en paralelo desde múltiples hilos de ejecución sin sincronización externa.

Ruta de uso

El uso típico de CoreErrorDomain se produce en la evaluación y propagación de errores encapsulados en instancias de ErrorCode:

  1. Identificación de dominio: los llamadores pueden comprobar a través de Name() [SWS_CORE_05242] si un error procede del dominio Core para seleccionar ramas de procesamiento específicas del dominio.
  2. Resolver mensaje de error textual: mediante Message() [SWS_CORE_05243], el valor numérico de error (ErrorDomain::CodeType) se traduce en una cadena de caracteres descriptiva. La especificación garantiza en este caso que el const char* devuelto nunca es nullptr. Interpretación: dado que la función es noexcept y no admite asignación dinámica, es probable que los punteros hagan referencia a literales de cadena estáticos.
  3. Lanzamiento sincrónico como excepción: si un objeto de error producido debe transferirse al flujo de control de excepciones, la aplicación invoca ThrowAsException() [SWS_CORE_05244]. El método genera un objeto CoreException adecuado y lo lanza directamente.

Escenarios de error

Al utilizar las interfaces, deben tenerse en cuenta condiciones específicas de excepciones y de la toolchain:

  • Excepciones de C++ desactivadas: si la compatibilidad con excepciones de C++ está desactivada en la toolchain del compilador, ThrowAsException() no debe participar en la resolución de sobrecarga según la especificación [SWS_CORE_05244]. Esto garantiza la compilabilidad del código en entornos embebidos sin excepciones.
  • Seguridad frente a excepciones de ThrowAsException: El método ThrowAsException() está documentado con noexcept(false) y como not exception safe [SWS_CORE_05244], ya que su comportamiento regular consiste en lanzar una CoreException.
  • Robustez de la resolución de texto: La función Message() [SWS_CORE_05243] está declarada como exception safe y noexcept. Dado que nunca se devuelve nullptr, el resultado se puede utilizar inmediatamente en mecanismos de registro (logging) o rastreo (tracing) sin verificación de puntero nulo. Interpretación: Al pasar un código de error no válido o sin nombre, probablemente se devuelva un texto de reserva estándar estático.
