Contexto

La clase de plantilla ara::rds::IEEE1722RawDataStreamProducer proporciona en el módulo rds (Raw Data Stream) de la AUTOSAR Adaptive Platform la interfaz para enviar paquetes de datos tipificados según el estándar IEEE 1722. Su responsabilidad principal radica en actuar como productor de datos (Producer) y proporcionar datagramas de un tipo específico de la aplicación a través de un flujo de datos configurado. El direccionamiento y la asignación de los puntos finales de comunicación se realiza mediante un ara::core::InstanceSpecifier que se transfiere durante la instanciación [SWS_RDS_90323].

Los interlocutores típicos son el componente de software del lado de la aplicación, que genera datos útiles en forma de datagramas, y la infraestructura de comunicación subyacente del sistema de tiempo de ejecución Adaptive. A través de esta infraestructura se opera el flujo de datos físico o lógico IEEE 1722. El Producer actúa aquí como enlace que encapsula los datos de la aplicación y los inyecta en el flujo.

Ciclo de vida

La creación de instancias de la clase ara::rds::IEEE1722RawDataStreamProducer se realiza de forma controlada mediante el patrón de fábrica a través del método estático Create [SWS_RDS_90323]. Dado que los constructores directos son privados o restringidos, se asegura que la creación solo se logre en función de una configuración válida de instancia de servicio. En cuanto a las relaciones de propiedad, el emisor de la llamada posee la instancia de manera exclusiva: el constructor de copia [SWS_RDS_90327] y el operador de asignación por copia [SWS_RDS_90328] están eliminados (delete), lo que impide la duplicación del flujo y de sus estados.

En cambio, la clase admite la semántica de movimiento: tanto el constructor de movimiento [SWS_RDS_90324] como el operador de asignación por movimiento [SWS_RDS_90326] están definidos como noexcept. Permiten la transferencia de la propiedad, por ejemplo a contenedores o transiciones de contexto asíncronas. No obstante, ambas operaciones de movimiento están especificadas expresamente como no seguras para subprocesos ([SWS_RDS_90324], [SWS_RDS_90326]), de modo que los accesos simultáneos desde múltiples subprocesos deben evitarse mediante sincronización externa.

El ciclo de vida finaliza con la destrucción del objeto mediante el destructor ~IEEE1722RawDataStreamProducer [SWS_RDS_90329]. Este también está marcado como no seguro para subprocesos. En el marco de las directrices RAII, el destructor garantiza que una conexión de flujo aún abierta en el momento de la destrucción se cierre automática y debidamente [SWS_RDS_90329].

Ruta de uso

El flujo de trabajo regular con un IEEE1722RawDataStreamProducer sigue una secuencia fija de fases: inicialización, establecimiento de la conexión, envío cíclico y desconexión.

  1. Creación: La aplicación inicia la instanciación a través de Create(instance) con el identificador de instancia adecuado [SWS_RDS_90323]. Tras un retorno exitoso, la aplicación conserva la instancia del Producer lista para el funcionamiento.
  2. Establecimiento de la conexión: Antes del intercambio de datos propiamente dicho, la conexión con el canal IEEE 1722 se establece mediante la llamada explícita a Connect() [SWS_RDS_90330].
  3. Transmisión de datos: En cuanto la conexión está activa, la aplicación transmite datos útiles estructurados mediante el método WriteData(std::vector<T>) [SWS_RDS_90332]. Esta llamada se produce habitualmente de forma periódica en el marco de la lógica de aplicación cíclica o activada por eventos ante nuevos datos de medición o de streaming.
  4. Desconexión: Una vez finalizada la transmisión de datos, la conexión se cierra de forma controlada mediante Shutdown() [SWS_RDS_90331]. Una llamada explícita a Shutdown antes de la destrucción probablemente sea opcional, ya que el destructor desconecta automáticamente los canales abiertos [SWS_RDS_90329], pero se recomienda para una supervisión selectiva de errores y estados.

Diagrama de secuencia: Flujo típico de creación, establecimiento de la conexión, envío repetido y cierre del Producer. Fuentes: [SWS_RDS_90323], [SWS_RDS_90330], [SWS_RDS_90332], [SWS_RDS_90331], [SWS_RDS_90329].

Escenarios de error

De conformidad con el modelo de errores de AUTOSAR Adaptive Platform, la interfaz prescinde por completo de las excepciones de C++. Todos los métodos están declarados con noexcept y señalan los fallos mediante el tipo de retorno genérico ara::core::Result ([SWS_RDS_90323], [SWS_RDS_90330], [SWS_RDS_90331], [SWS_RDS_90332]).

Las situaciones de error pueden producirse en diferentes fases:

  • Fallo durante la creación: Si Create falla, por ejemplo debido a un InstanceSpecifier defectuoso o desconocido en el sistema, el objeto de resultado devuelve un código de error específico del sistema en lugar de la instancia de producer [SWS_RDS_90323].
  • Error de conexión: Si Connect() [SWS_RDS_90330] falla (por ejemplo, debido a la falta de recursos de red o a interfaces inaccesibles), el producer no debe utilizarse para el envío. Antes de invocar WriteData, presumiblemente sea obligatorio establecer una conexión correcta mediante Connect.
  • Error de transmisión: Si durante WriteData se produce un desbordamiento de búfer o un problema en la capa de red, el ara::core::Result<void> devuelve un objeto de error [SWS_RDS_90332] correspondiente que debe ser gestionado por la aplicación.
  • Error durante el apagado: Shutdown() [SWS_RDS_90331] también devuelve un ara::core::Result<void> para notificar posibles errores durante la desconexión correcta.

Por consiguiente, el componente invocador está obligado a comprobar en cada paso el resultado del ara::core::Result mediante métodos como HasValue() antes de continuar.

Esta guía se basa exclusivamente en los requisitos de especificación de AUTOSAR Adaptive R25-11 para el módulo rds.
