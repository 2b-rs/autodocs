Contexto

La clase ara::diag::SovdConfiguration representa la interfaz genérica para configuraciones SOVD (Service-Oriented Vehicle Diagnostics) en la AUTOSAR Adaptive Platform ([SWS_DM_01860], AUTOSAR_AP_SWS_Diagnostics §8.54.1 «Class: SovdConfiguration»). En cuanto se modela al menos una configuración SOVD en el sistema, la instancia del Diagnostic Server pone a disposición el método SOVD estandarizado para enumerar todas las configuraciones proporcionadas ([SWS_DM_01429], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2 «SOVD API – Configuration»).

Para configuraciones SOVD modeladas explícitamente, una instancia derivada de ara::diag::SovdConfiguration actúa como manejador de aplicación. El Diagnostic Server (DM) actúa como intermediario: las solicitudes externas entrantes según los métodos SOVD Read Configuration y Write Configuration son recibidas por el Diagnostic Server y reenviadas a la aplicación a través de los métodos de interfaz RequestGetConfiguration ([SWS_DM_01787]) o bien RequestPutConfiguration ([SWS_DM_01788]).

Diagrama de contexto: integración de ara::diag::SovdConfiguration entre el cliente SOVD externo y el Diagnostic Server. Fuentes: [SWS_DM_01787], [SWS_DM_01788], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 «Configuration – Explicit Configurations»

Ciclo de vida

Las clases de aplicación derivan de ara::diag::SovdConfiguration e instancian el objeto a través del constructor, que requiere un ara::core::InstanceSpecifier y un ConcurrencyType ([SWS_DM_01864]). El InstanceSpecifier vincula el objeto con un prototipo de puerto modelado.

En cuanto a las relaciones de propiedad, la clase está diseñada como ejemplar único: tanto el constructor de copia ([SWS_DM_01866]) como el operador de asignación por copia ([SWS_DM_01868]) están eliminados (delete). Las operaciones de movimiento (constructor de movimiento y asignación por movimiento) están declaradas como protected y noexcept ([SWS_DM_01867], [SWS_DM_01869]).

Tras la instanciación, el objeto se encuentra inicialmente en un estado inactivo. Solo mediante la llamada a Offer(), el Diagnostic Management Daemon queda habilitado para reenviar solicitudes para este manejador ([SWS_DM_01872]). Si el servicio ya no debe estar disponible, el reenvío se desactiva mediante StopOffer() ([SWS_DM_01930]). La destrucción del objeto se realiza mediante el destructor virtual ~SovdConfiguration() ([SWS_DM_01865]). Interpretación: en un escenario de parada regular, probablemente se llamaría a StopOffer() antes de la destrucción del objeto para excluir accesos asíncronos durante la ejecución del destructor.

Con respecto a la concurrencia, el constructor es seguro frente a hilos ([SWS_DM_01864]), mientras que Offer() ([SWS_DM_01872]), StopOffer() ([SWS_DM_01930]) y el destructor ([SWS_DM_01865]) no son seguros frente a hilos. La seguridad frente a hilos de los métodos del manejador RequestGetConfiguration ([SWS_DM_01870]) y RequestPutConfiguration ([SWS_DM_01871]) es condicional: depende de si en la construcción se transfirió ConcurrencyType::kConcurrent o ConcurrencyType::kNotConcurrent.

Ruta de uso

Una ruta de uso típica para el manejo de consultas de configuración SOVD comprende las siguientes fases:

  1. Inicialización: la aplicación instancia la clase derivada con el InstanceSpecifier adecuado y el modo de concurrencia deseado ([SWS_DM_01864]).
  2. Suministro del servicio: mediante la llamada a Offer() se activa el reenvío de solicitudes ([SWS_DM_01872]).
  3. Procesamiento de solicitudes (lectura): si se recibe una solicitud de lectura SOVD en el Diagnostic Server ([SWS_DM_01787]), este llama a RequestGetConfiguration ([SWS_DM_01870]). La aplicación procesa la configurationId transferida, así como MetaInfo, supervisa el CancellationHandler y devuelve un ara::core::Future con un std::tuple de DataTransferReadSession y SovdConfigurationMetaInfo.
  4. Procesamiento de solicitudes (escritura): en caso de una solicitud de escritura ([SWS_DM_01788]), el servidor llama a RequestPutConfiguration ([SWS_DM_01871]), tras lo cual la aplicación proporciona un Future con DataTransferWriteSession e información de metadatos.
  5. Finalización del servicio: antes de finalizar el componente, la aplicación desactiva la recepción de más solicitudes a través de StopOffer() ([SWS_DM_01930]).

Diagrama de secuencia: puesta a disposición del servicio y procesamiento asíncrono de una solicitud de lectura SOVD. Fuentes: [SWS_DM_01787], [SWS_DM_01870], [SWS_DM_01872], [SWS_DM_01930]

Escenarios de error

Las situaciones de error pueden ocurrir en diferentes fases de la interacción:

  • Infracciones de construcción: al llamar al constructor ([SWS_DM_01864]), pueden producirse errores de modelado y de mapeo:
    • InstanceSpecifierMappingIntegrityViolation: el identificador no se puede resolver en el contexto del archivo ejecutable o no hace referencia a un PortPrototype.
    • PortInterfaceMappingViolation: el PortPrototype no está tipado mediante un DiagnosticSovdConfigurationInterface.
    • ProcessMappingViolation: no existe ninguna asignación a un proceso modelado adecuado.
    • InstanceSpecifierAlreadyInUseViolation: el InstanceSpecifier ya se está utilizando dentro del proceso.
  • Error en el suministro (Offer): Offer() devuelve un ara::core::Result<void> ([SWS_DM_01872]). Los posibles códigos de error son:
    • DiagOfferErrc::kConfigurationMismatch: la configuración de supervisión no coincide con el DEXT (semántica de rollback).
    • DiagOfferErrc::kAlreadyOffered: el servicio ya se ha ofrecido anteriormente (semántica de rollback).
  • Error en el procesamiento de la configuración: si falla la lectura o escritura de una instancia de configuración, la implementación transmite un código de error SOVD estandarizado según ISO 17978-3 / ASAM SOVD 1.1 a través del Future devuelto por RequestGetConfiguration ([SWS_DM_01870]) o bien RequestPutConfiguration ([SWS_DM_01871]). Además, el CancellationHandler señala si se ha cancelado una conversación en curso.

Esta guía se basa en la especificación AUTOSAR Adaptive R25-11 (módulo diag) y describe la integración, así como las reglas del ciclo de vida de la clase ara::diag::SovdConfiguration.

  <h4>Contexto</h4>
  <p>
    La clase <code>ara::diag::SovdConfiguration</code> representa la interfaz genérica para configuraciones SOVD (Service-Oriented Vehicle Diagnostics) en la AUTOSAR Adaptive Platform (<a class="spec-record-ref" data-req="SWS_DM_01860" href="../spec/record.html?id=SWS_DM_01860">[SWS_DM_01860]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=718">AUTOSAR_AP_SWS_Diagnostics §8.54.1 «Class: SovdConfiguration»</a>). En cuanto se modela al menos una configuración SOVD en el sistema, la instancia del Diagnostic Server pone a disposición el método SOVD estandarizado para enumerar todas las configuraciones proporcionadas (<a class="spec-record-ref" data-req="SWS_DM_01429" href="../spec/record.html?id=SWS_DM_01429">[SWS_DM_01429]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=207">AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2 «SOVD API – Configuration»</a>).
  </p>
  <p>
    Para configuraciones SOVD modeladas explícitamente, una instancia derivada de <code>ara::diag::SovdConfiguration</code> actúa como manejador de aplicación. El Diagnostic Server (DM) actúa como intermediario: las solicitudes externas entrantes según los métodos SOVD <em>Read Configuration</em> y <em>Write Configuration</em> son recibidas por el Diagnostic Server y reenviadas a la aplicación a través de los métodos de interfaz <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01787" href="../spec/record.html?id=SWS_DM_01787">[SWS_DM_01787]</a>) o bien <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01788" href="../spec/record.html?id=SWS_DM_01788">[SWS_DM_01788]</a>).
  </p>

  <h4>Ciclo de vida</h4>
  <p>
    Las clases de aplicación derivan de <code>ara::diag::SovdConfiguration</code> e instancian el objeto a través del constructor, que requiere un <code>ara::core::InstanceSpecifier</code> y un <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>). El <code>InstanceSpecifier</code> vincula el objeto con un prototipo de puerto modelado.
  </p>
  <p>
    En cuanto a las relaciones de propiedad, la clase está diseñada como ejemplar único: tanto el constructor de copia (<a class="spec-record-ref" data-req="SWS_DM_01866" href="../spec/record.html?id=SWS_DM_01866">[SWS_DM_01866]</a>) como el operador de asignación por copia (<a class="spec-record-ref" data-req="SWS_DM_01868" href="../spec/record.html?id=SWS_DM_01868">[SWS_DM_01868]</a>) están eliminados (<code>delete</code>). Las operaciones de movimiento (constructor de movimiento y asignación por movimiento) están declaradas como <code>protected</code> y <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_DM_01867" href="../spec/record.html?id=SWS_DM_01867">[SWS_DM_01867]</a>, <a class="spec-record-ref" data-req="SWS_DM_01869" href="../spec/record.html?id=SWS_DM_01869">[SWS_DM_01869]</a>).
  </p>
  <p>
    Tras la instanciación, el objeto se encuentra inicialmente en un estado inactivo. Solo mediante la llamada a <code>Offer()</code>, el Diagnostic Management Daemon queda habilitado para reenviar solicitudes para este manejador (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>). Si el servicio ya no debe estar disponible, el reenvío se desactiva mediante <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>). La destrucción del objeto se realiza mediante el destructor virtual <code>~SovdConfiguration()</code> (<a class="spec-record-ref" data-req="SWS_DM_01865" href="../spec/record.html?id=SWS_DM_01865">[SWS_DM_01865]</a>). Interpretación: en un escenario de parada regular, probablemente se llamaría a <code>StopOffer()</code> antes de la destrucción del objeto para excluir accesos asíncronos durante la ejecución del destructor.
  </p>
  <p>
    Con respecto a la concurrencia, el constructor es seguro frente a hilos (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>), mientras que <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>), <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>) y el destructor (<a class="spec-record-ref" data-req="SWS_DM_01865" href="../spec/record.html?id=SWS_DM_01865">[SWS_DM_01865]</a>) no son seguros frente a hilos. La seguridad frente a hilos de los métodos del manejador <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01870" href="../spec/record.html?id=SWS_DM_01870">[SWS_DM_01870]</a>) y <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01871" href="../spec/record.html?id=SWS_DM_01871">[SWS_DM_01871]</a>) es condicional: depende de si en la construcción se transfirió <code>ConcurrencyType::kConcurrent</code> o <code>ConcurrencyType::kNotConcurrent</code>.
  </p>

  <h4>Ruta de uso</h4>
  <p>
    Una ruta de uso típica para el manejo de consultas de configuración SOVD comprende las siguientes fases:
  </p>
  <ol>
    <li>
      <strong>Inicialización:</strong> la aplicación instancia la clase derivada con el <code>InstanceSpecifier</code> adecuado y el modo de concurrencia deseado (<a class="spec-record-ref" data-req="SWS_DM_01864" href="../spec/record.html?id=SWS_DM_01864">[SWS_DM_01864]</a>).
    </li>
    <li>
      <strong>Suministro del servicio:</strong> mediante la llamada a <code>Offer()</code> se activa el reenvío de solicitudes (<a class="spec-record-ref" data-req="SWS_DM_01872" href="../spec/record.html?id=SWS_DM_01872">[SWS_DM_01872]</a>).
    </li>
    <li>
      <strong>Procesamiento de solicitudes (lectura):</strong> si se recibe una solicitud de lectura SOVD en el Diagnostic Server (<a class="spec-record-ref" data-req="SWS_DM_01787" href="../spec/record.html?id=SWS_DM_01787">[SWS_DM_01787]</a>), este llama a <code>RequestGetConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01870" href="../spec/record.html?id=SWS_DM_01870">[SWS_DM_01870]</a>). La aplicación procesa la <code>configurationId</code> transferida, así como <code>MetaInfo</code>, supervisa el <code>CancellationHandler</code> y devuelve un <code>ara::core::Future</code> con un <code>std::tuple</code> de <code>DataTransferReadSession</code> y <code>SovdConfigurationMetaInfo</code>.
    </li>
    <li>
      <strong>Procesamiento de solicitudes (escritura):</strong> en caso de una solicitud de escritura (<a class="spec-record-ref" data-req="SWS_DM_01788" href="../spec/record.html?id=SWS_DM_01788">[SWS_DM_01788]</a>), el servidor llama a <code>RequestPutConfiguration</code> (<a class="spec-record-ref" data-req="SWS_DM_01871" href="../spec/record.html?id=SWS_DM_01871">[SWS_DM_01871]</a>), tras lo cual la aplicación proporciona un <code>Future</code> con <code>DataTransferWriteSession</code> e información de metadatos.
    </li>
    <li>
      <strong>Finalización del servicio:</strong> antes de finalizar el componente, la aplicación desactiva la recepción de más solicitudes a través de <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01930" href="../spec/record.html?id=SWS_DM_01930">[SWS_DM_01930]</a>).
