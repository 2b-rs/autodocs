clase apext::diag::uds_transport::UdsTransportProtocolMgr

[SWS_DM_00306] Upstream: RS_Diag_04147, RS_Diag_04168

class UdsTransportProtocolMgr {...};

The UdsTransportProtocolMgr class manages the interaction between the Diagnostic Server instance(s) and various UDS Transport Protocols (e.g., DoIP[2], CAN[21]). It provides a standard, extensible API for handling transport-specific message reception and optional early payload access.

Contexto

La clase apext::diag::uds_transport::UdsTransportProtocolMgr constituye la interfaz estandarizada para la coordinación entre instancias del Diagnostic Server (DM Core o Session Layer) y diversos protocolos de transporte UDS como DoIP o CAN (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»). Los protocolos de transporte concretos se implementan como subclases de la clase base abstracta apext::diag::uds_transport::UdsTransportProtocolHandler ([SWS_DM_00315], AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»).

En esta función mediadora, la clase gestora interactúa esencialmente con tres componentes:

  • UDS Transport Protocol Handler (Transport Layer): Notifican el inicio de mensajes entrantes ([SWS_DM_00309]), entregan solicitudes completamente recibidas ([SWS_DM_00311]), confirman órdenes de envío ([SWS_DM_00312]) y señalan cambios de canal y de estado ([SWS_DM_00313], [SWS_DM_00314]).
  • Diagnostic Server Core (Session Layer): Asume las solicitudes UDS válidas para su posterior procesamiento de diagnóstico y gestiona la asignación de búferes de mensajes ([SWS_DM_00309], [SWS_DM_00311]).
  • Manejadores periódicos de transporte: Transmiten confirmaciones sobre la transferencia exitosa de cadenas periódicas de mensajes ([SWS_DM_01069]).

Diagrama de contexto: Interacción de UdsTransportProtocolMgr con los manejadores de transporte y la Session Layer. Fuentes: AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00314].

Ciclo de vida

El ciclo de vida de una implementación de protocolo de transporte es controlado por el Diagnostic Manager (DM) en una secuencia firmemente definida de construcción, inicialización y detención ([SWS_DM_00329], AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer»). La clase UdsTransportProtocolMgr declara un destructor virtual estándar ([SWS_DM_01524]).

Durante el funcionamiento, se sincronizan las fases de desactivación: si un manejador ha cerrado sus conexiones de red y liberado recursos en respuesta a una detención, notifica al gestor mediante el callback HandlerStopped indicando su handlerId ([SWS_DM_00314]).

En cuanto a la memoria y la titularidad, para los búferes de mensajes rige un modelo de transferencia claro: al inicio de una transmisión, el DM Core crea el objeto de mensaje y entrega su puntero al manejador ([SWS_DM_00309]). Tras la recepción completa, el manejador transfiere la titularidad del mensaje mediante la semántica de unique_ptr a través de HandleMessage de vuelta al DM Core genérico ([SWS_DM_00311]).

Todos los métodos de la interfaz están especificados como seguros frente a excepciones (noexcept), pero no seguros para subprocesos (not thread-safe) ([SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00312]). Interpretación: por tanto, probablemente las llamadas al gestor deban sincronizarse mediante los componentes de transporte y de sesión llamantes.

Ruta de uso

El flujo regular para el procesamiento de solicitudes de diagnóstico UDS entrantes se divide en los siguientes pasos:

  1. Indicación de mensaje: Siempre que el manejador admita la indicación, llama a IndicateMessage cuando llegan los primeros datos ([SWS_DM_00309]). Con ello se transmiten la dirección de origen y de destino, el tipo de direccionamiento (físico o funcional), el tamaño total esperado así como el GlobalChannelIdentifier ([SWS_DM_09021]). A través de payloadInfo ya se pueden transferir los primeros bytes para que el DM pueda detectar a tiempo, por ejemplo, solicitudes funcionales Tester-Present ([SWS_DM_00309]).
  2. Provisión del búfer: El gestor devuelve un par compuesto por IndicationResult y un UdsMessagePtr asignado ([SWS_DM_00309]). Si el resultado es IndicationResult::kIndicationOk ([SWS_DM_00384]), el manejador llena el búfer con los datos entrantes.
  3. Transferencia a la Session Layer: Tras la recepción completa, el manejador entrega el mensaje mediante HandleMessage al gestor ([SWS_DM_00311]), lo que corresponde al servicio T_Data.ind según la norma ISO 14229-2. La llamada retorna de inmediato; la evaluación posterior tiene lugar de forma asíncrona en la Session Layer ([SWS_DM_00311]).
  4. Confirmación de envío: Para respuestas UDS enviadas, el manejador confirma posteriormente el éxito mediante TransmitConfirmation con el resultado kTransmitOk ([SWS_DM_00312], [SWS_DM_00307]), correspondiente a T_Data.con según la norma ISO 14229-2.

Diagrama de secuencia: Proceso de recepción de mensajes UDS desde la indicación hasta la transferencia asíncrona a la Session Layer. Fuentes: [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00384].

Escenarios de error

Las condiciones de error durante el transporte o la asignación de búferes se interceptan mediante valores de estado e interfaces de error definidos:

  • Fallo en la indicación: Si el DM Core no puede aceptar un mensaje indicado, lo notifica mediante el enum IndicationResult ([SWS_DM_00309], [SWS_DM_00384]):
    • kIndicationOccupied: El servidor o la sesión de diagnóstico está actualmente ocupado ([SWS_DM_00384]).
    • kIndicationOverflow: El tamaño de mensaje transmitido excede la capacidad del búfer ([SWS_DM_00384]).
    • kIndicationUnknownTargetAddress: La dirección de destino indicada no está configurada ([SWS_DM_00384]).
  • Cancelación de la recepción: Si se produce una desconexión o un error de transmisión tras un IndicateMessage correcto, el manejador llama a NotifyMessageFailure ([SWS_DM_00310]). El objeto UdsMessage recibido previamente se devuelve al DM sin que se produzca una llamada a HandleMessage ([SWS_DM_00310]).
  • Error de transmisión en el envío: Si un mensaje saliente no puede enviarse en el nivel de red, el manejador notifica el resultado TransmissionResult::kTransmitFailed mediante TransmitConfirmation ([SWS_DM_00312], [SWS_DM_00307]).
  • Reactivación del canal: Tras una pérdida temporal de conexión, el manejador señala la nueva disponibilidad de un canal mediante ChannelReestablished con el GlobalChannelIdentifier ([SWS_DM_00313], [SWS_DM_09021]), siempre que esta notificación se haya solicitado previamente ([SWS_DM_00313]).

Recepción de mensajes

HandleMessage función

Hands over a valid received UDS message (currently this is only a request type) from the Transport Layer to the Session Layer. This corresponds to T_Data.ind of Figure 2 from ISO 14229-2[25]. The behavior is asynchronously, i.e. the UDS Message is handed over to the Session Layer and it is expected, that it "instantly" returns, which means, that real processing of the message shall be done asynchronously by the Transport Layer!

virtual void HandleMessage (UdsMessagePtr message) noexcept=0;
