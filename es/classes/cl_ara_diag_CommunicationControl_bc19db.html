GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: ae3aac538bd3 Procedencia

Permite a las aplicaciones procesar solicitudes de diagnóstico del servicio UDS 0x28 para el control de la comunicación.

La clase ara::diag::CommunicationControl sirve en AUTOSAR Adaptive como interfaz para procesar el servicio UDS 0x28 (CommunicationControl) destinado a la conmutación de canales de comunicación [SWS_DM_00808]. Tras la instanciación basada en modelos a través de un InstanceSpecifier, Offer() activa el reenvío de solicitudes por parte del Diagnostic Manager, las cuales se procesan posteriormente de forma asíncrona mediante CommCtrlRequest [SWS_DM_00806], [SWS_DM_00809]. Al tratarse de una instancia única estricta, la clase excluye operaciones de copia y de movimiento, y exige una desregistración mediante StopOffer() antes de finalizar [SWS_DM_00810].

Contexto

La clase ara::diag::CommunicationControl define la interfaz estandarizada para la gestión del servicio de diagnóstico UDS 0x28 (CommunicationControl) en la AUTOSAR Adaptive Platform AUTOSAR_AP_SWS_Diagnostics, p. 70. Como clase base abstracta, actúa de intermediaria entre el Diagnostic Manager (DM) y la funcionalidad de diagnóstico específica de la aplicación con la que se controla el envío o la recepción de determinados mensajes de comunicación en la red del vehículo. El software de aplicación deriva de esta clase e implementa el método puramente virtual CommCtrlRequest para recibir y ejecutar instrucciones de control entrantes [SWS_DM_00808]. La vinculación con el modelo de sistema de AUTOSAR se realiza mediante un ara::core::InstanceSpecifier, el cual referencia un PortPrototype de un DiagnosticComControlInterface [SWS_DM_00806].

Ciclo de vida

Una instancia se crea explícitamente a través del constructor indicando el ara::core::InstanceSpecifier y el modelo de concurrencia ConcurrencyType (kConcurrent o kNotConcurrent) [SWS_DM_00806]. La clase cuenta con una semántica estricta de instancia única y no es copiable ni movible: tanto el constructor de copia [SWS_DM_01677] y el constructor de movimiento [SWS_DM_01678] como el operador de asignación por copia [SWS_DM_01675] y el operador de asignación por movimiento [SWS_DM_01676] están eliminados (=delete).

Tras su creación, la instancia permanece inicialmente inactiva. Solo mediante la llamada a Offer() se autoriza al Diagnostic Manager a reenviar las solicitudes de diagnóstico entrantes al manejador [SWS_DM_00809]. A la inversa, StopOffer() revoca esta autorización y desactiva el reenvío [SWS_DM_00810]. La destrucción se lleva a cabo mediante el destructor virtual [SWS_DM_00807]. Interpretación: es probable que sea necesario llamar a StopOffer() antes de destruir el objeto para que el Diagnostic Manager no mantenga reenvíos huérfanos.

En cuanto a la concurrencia, el constructor es seguro para subprocesos (thread-safe) [SWS_DM_00806], mientras que el destructor [SWS_DM_00807], Offer() [SWS_DM_00809] y StopOffer() [SWS_DM_00810] no son seguros para subprocesos. La ejecución de CommCtrlRequest es condicionalmente segura para subprocesos (conditional): el ConcurrencyType establecido en el constructor determina si la implementación debe ser segura para subprocesos [SWS_DM_00808].

Ruta de uso

El flujo regular comprende la instanciación de la clase derivada, el registro del servicio, el procesamiento asíncrono de solicitudes de diagnóstico y la desregistración final:

  1. Inicialización: La aplicación instancia el manejador indicando el InstanceSpecifier y el ConcurrencyType deseado [SWS_DM_00806].
  2. Oferta de servicio: Mediante Offer() se habilita el servicio en el Diagnostic Manager [SWS_DM_00809].
  3. Procesamiento de solicitudes: Si llega una solicitud UDS para el servicio 0x28 con cualquier subfunción, el Diagnostic Manager llama a CommCtrlRequest [SWS_DM_00808]. Los parámetros comprenden:
    • controlType (ComCtrlRequestParamsType): Todos los parámetros de solicitud UDS, incluidos los elementos opcionales.
    • metaInfo (const MetaInfo&): Metainformación sobre la solicitud de diagnóstico.
    • cancellationHandler (CancellationHandler): Sirve para la consulta de estado mediante IsCanceled(), así como para el registro de una función de devolución de llamada (callback) de cancelación vía SetNotifier().
  4. Respuesta: El procesamiento finaliza de forma asíncrona y notifica el resultado mediante ara::core::Future<void> [SWS_DM_00808].
  5. Desregistración: Antes de apagar o finalizar, la aplicación detiene el reenvío mediante StopOffer() [SWS_DM_00810].

Diagrama de secuencias: Flujo típico desde la inicialización y el procesamiento de la solicitud UDS 0x28 hasta la desregistración. Fuentes: [SWS_DM_00806], [SWS_DM_00808], [SWS_DM_00809], [SWS_DM_00810].

Escenarios de error

Ya durante la construcción, las incoherencias en el modelo AUTOSAR pueden provocar violaciones en tiempo de ejecución (violations) [SWS_DM_00806]:

  • InstanceSpecifierMappingIntegrityViolation: El InstanceSpecifier no se puede resolver en el contexto del ejecutable o no apunta a un PortPrototype.
  • PortInterfaceMappingViolation: El PortPrototype tipificado por DiagnosticComControlInterface no está referenciado por un DiagnosticServiceGenericMapping.
  • ProcessMappingViolation: Existe una referencia de instancia coincidente, pero no hay ningún proceso modelado que coincida con el proceso actual.
  • InstanceSpecifierAlreadyInUseViolation: el identificador ya está siendo utilizado en el mismo proceso por otra instancia.

Durante el funcionamiento normal, Offer() notifica mediante el valor de retorno ara::core::Result<void> el error DiagOfferErrc::kAlreadyOffered en caso de que el servicio ya se haya ofrecido con anterioridad y aún se encuentre activo [SWS_DM_00809]. Si una solicitud de diagnóstico no se puede satisfacer técnicamente en CommCtrlRequest, el método devuelve un Negative Response Code (NRC) conforme a ISO 14229-1 a través del ara::core::Future<void> mediante DiagUdsNrcErrc [SWS_DM_00808].

función CommCtrlRequest [SWS_DM_00808] Upstream: RS_AP_00119, RS_AP_00138, RS_Diag_04170, RS_Diag_04278

virtual ara::core::Future< void > CommCtrlRequest (ComCtrlRequest ParamsType controlType, const MetaInfo &metaInfo, CancellationHandler cancellationHandler) noexcept=0;

Called for CommunicationControl (0x28) with any subfunction as subfunction value is part of the argument list.

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 8fa21d673414 Procedencia

La instancia del Diagnostic Server llama al método puramente virtual ara::diag::CommunicationControl::CommCtrlRequest ([SWS_DM_00808]) para procesar peticiones de diagnóstico del servicio UDS 0x28 (CommunicationControl) ([SWS_DM_00865], SWS Diagnostics §7.3.2.8.10 «Service 0x28 – CommunicationControl»). Todos los parámetros de la petición UDS, incluida la subfunción, se transmiten agrupados a través de la estructura controlType ([SWS_DM_00808]). La llamada devuelve un ara::core::Future<void>, por lo que el procesamiento se realiza de forma asíncrona. A través del parámetro cancellationHandler, la aplicación puede consultar el estado de cancelación mediante IsCanceled() o registrar a través de SetNotifier() un callback para la cancelación de la conversación ([SWS_DM_00808]).

Si la aplicación finaliza el procesamiento sin errores, el Diagnostic Server envía una respuesta UDS positiva ([SWS_DM_00199]). Si se produce un error, este debe notificarse como un Negative Response Code (NRC) adecuado conforme a ISO 14229-1 a través de ara::diag::DiagUdsNrcErrc ([SWS_DM_00808]); a continuación, el servidor responde negativamente a la petición de servicio con este código de error ([SWS_DM_00866]). El servidor rechaza por adelantado las subfunciones no configuradas con el NRC 0x12 (kSubFunctionNotSupported) ([SWS_DM_00252]).

El método está declarado con noexcept y es seguro frente a excepciones ([SWS_DM_00808], SWS Diagnostics §8.7.1.1.3.1 «CommCtrlRequest»). Su seguridad para subprocesos es condicional: si la función debe implementarse de forma segura para subprocesos se determina mediante el parámetro de constructor ConcurrencyType de la instancia ([SWS_DM_00808]). La conmutación efectiva de los modos de comunicación probablemente se produzca de forma asíncrona en segundo plano antes de que se resuelva el future.

  Procedencia
  

                  

                  

                  usar
                  

                  El método Offer de la clase ara::diag::CommunicationControl (cabecera #include "ara/diag/communication_control.h") permite al Diagnostic Management (DM) reenviar peticiones de diagnóstico entrantes para el control de la comunicación a la instancia del manejador que las proporciona [SWS_DM_00809]. La llamada se realiza sin parámetros y devuelve el tipo ara::core::Result<void> [SWS_DM_00809]. Al no utilizarse ningún ara::core::Future ni mecanismo de devolución de llamada (callback), la ejecución debe interpretarse como síncrona.
                  


                  Manejo de errores
                  

                  En caso de éxito, la función devuelve un ara::core::Result vacío. Si el servicio ya se había ofrecido previamente para esta instancia, la llamada falla y devuelve el código de error DiagOfferErrc::kAlreadyOffered con semántica de reversión [SWS_DM_00809]. Este estado de error se corresponde con el tratamiento de errores uniforme para ofertas de diagnóstico en Adaptive AUTOSAR, tal y como está especificado, por ejemplo, en DiagErrc [SWS_DM_00514] así como en DiagReportingErrc [SWS_DM_00560].
                  


                  Concurrencia y restricciones
                  

                  La función está declarada como noexcept y es segura frente a excepciones (exception safe), aunque explícitamente no es segura para subprocesos (not thread-safe) [SWS_DM_00809]. Por lo tanto, las llamadas sobre la misma instancia deben ser sincronizadas por la aplicación llamadora para evitar condiciones de carrera durante el registro.
                  


                  Interacción
                  

                  El patrón de registro implementado mediante Offer es un modismo central en Diagnostic Management y se utiliza coherentemente a través de los manejadores, por ejemplo en rutinas [SWS_DM_00557], servicios UDS generales [SWS_DM_00619], interfaces de Security Access [SWS_DM_00766] así como servicios de subida y bajada (up- y download) [SWS_DM_00792] [SWS_DM_00802]. Cabe señalar aquí la distinción respecto a la infraestructura de comunicación: tal como se destaca en AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 «Monitors», se trata de una implementación específica de diagnóstico que no debe confundirse con ara::com.
