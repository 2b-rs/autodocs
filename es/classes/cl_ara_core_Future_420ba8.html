Permite la recepción síncrona o asíncrona de valores y errores procedentes de una operación concurrente.

La clase ara::core::Future sirve como identificador receptor para el resultado de una operación asíncrona y administra el acceso a un estado compartido [SWS_CORE_00327]. Los consumidores pueden comprobar el estado de forma no bloqueante, esperar de forma síncrona a la finalización o recibir el resultado a través de GetResult() libre de excepciones como ara::core::Result [SWS_CORE_00336]. Dado que las operaciones de copia están eliminadas, la propiedad se gestiona de forma exclusiva y, tras la recogida del resultado o su reenvío mediante una continuación, el objeto pasa a ser inválido de inmediato.

Contexto

La clase plantilla ara::core::Future representa el elemento final receptor para los resultados de operaciones asíncronas dentro de la AUTOSAR Adaptive Platform. Permite el acceso controlado a un estado compartido (Shared State) que una instancia generadora rellena de forma asíncrona [SWS_CORE_00327]. Conceptualmente, la clase implementa std::future del estándar C++17 ISO/IEC 14882:2017 [11], pero se integra a la perfección en el concepto basado en excepciones de error de la plataforma: para el parámetro de plantilla E se prescribe obligatoriamente el tipo de error ara::core::ErrorCode; cualquier especificación divergente da lugar a un error de compilación. Entre los interlocutores principales se encuentran el generador asíncrono (como una promesa asociada), que proporciona el valor o el error, la instancia de Future como receptor exclusivo, así como un consumidor o contexto de ejecución (ExecutorT) al que se transfieren las tareas posteriores [SWS_CORE_00331] [SWS_CORE_00337].

Ciclo de vida

La creación, gestión de estado y destrucción de ara::core::Future están sujetas a reglas estrictas para garantizar relaciones de propiedad deterministas:

  • Creación: El constructor predeterminado crea una instancia vacía sin Shared State, para la cual se cumple valid() == false [SWS_CORE_00322] [SWS_CORE_00327]. Interpretación: Las instancias válidas se originan de forma regular a través de interfaces de plataforma asíncronas o de objetos Promise acoplados.
  • Propiedad y transferencia: El constructor de copia y el operador de asignación por copia están explícitamente eliminados (delete), por lo que queda excluida la duplicación del identificador de acceso [SWS_CORE_00334] [SWS_CORE_00335]. El movimiento (Move) de instancias es posible a través del constructor de movimiento y del operador de asignación por movimiento, y transfiere la propiedad del Shared State por completo [SWS_CORE_00323] [SWS_CORE_00325].
  • Estados y transiciones: El estado se divide en inválido (valid() == false), válido-pendiente (valid() == true, is_ready() == false) y listo (valid() == true, is_ready() == true) [SWS_CORE_00327] [SWS_CORE_00332]. Tras la recogida exitosa del resultado mediante GetResult() o get(), así como tras el reenvío a través de then(), el objeto pierde su estado y pasa a ser inválido de inmediato (valid() == false) [SWS_CORE_00326] [SWS_CORE_00331] [SWS_CORE_00336] [SWS_CORE_00337].
  • Destrucción: El destructor ~Future() renuncia a un Shared State que aún mantenga retenido [SWS_CORE_00333]. Si se registraron continuaciones, el destructor de la instancia devuelta se bloquea hasta que una función de continuación ya en curso se haya ejecutado por completo [SWS_CORE_00331] [SWS_CORE_00337].
  • Concurrencia: Los métodos de estado valid() y is_ready() son seguros para subprocesos [SWS_CORE_00327] [SWS_CORE_00332]. Todas las demás interfaces, incluidas wait(), wait_for(), wait_until(), GetResult(), get(), then() y el destructor, no son seguras para subprocesos para una misma instancia [SWS_CORE_00323] [SWS_CORE_00325] [SWS_CORE_00326] [SWS_CORE_00328] [SWS_CORE_00329] [SWS_CORE_00330] [SWS_CORE_00331] [SWS_CORE_00333] [SWS_CORE_00336] [SWS_CORE_00337].

Diagrama de estados: Ciclo de vida y transiciones de estado de una instancia de Future respecto a la validez y disponibilidad del Shared State. Fuentes: [SWS_CORE_00322], [SWS_CORE_00326], [SWS_CORE_00327], [SWS_CORE_00331], [SWS_CORE_00332], [SWS_CORE_00333], [SWS_CORE_00336]

Ruta de uso

Una ruta de uso típica para el procesamiento de resultados se divide en las siguientes fases:

  1. Comprobación de estado y sincronización: Con is_ready() se puede determinar previamente si el resultado asíncrono ya está disponible [SWS_CORE_00332]. Si este es el caso, se garantiza que las consultas posteriores ya no se bloquearán [SWS_CORE_00332]. De lo contrario, se puede sincronizar de forma indefinida con wait() [SWS_CORE_00328] o con límite de tiempo mediante wait_for() o wait_until() [SWS_CORE_00329] [SWS_CORE_00330].
  2. Extracción del resultado: En aplicaciones de AUTOSAR Adaptive, la llamada a GetResult() es determinante: el método se bloquea si es necesario, pero nunca lanza excepciones y transfiere el valor o el error como ara::core::Result<T, E> mediante movimiento [SWS_CORE_00336]. El método get() ofrece conformidad con STL, lanza excepciones de C++ en caso de error y no participa en la resolución de sobrecargas si el manejo de excepciones de la cadena de herramientas está deshabilitado [SWS_CORE_00326].
  3. Encadenamiento asíncrono (Continuations): En lugar de un bloqueo síncrono, se puede registrar una retrollamada a través de then(), opcionalmente con asignación a un contexto de ejecución (Executor) [SWS_CORE_00331] [SWS_CORE_00337]. La retrollamada recibe el resultado como valor r (rvalue) de Result<T, E>. Si la propia función de continuación devuelve un Future o Result, then() realiza un desempaquetado automático y devuelve directamente el correspondiente Future<T2, E2> [SWS_CORE_00331] [SWS_CORE_00337].

Diagrama de secuencia: Flujo típico de la sincronización asíncrona y recogida del resultado a través de GetResult(). Fuentes: [SWS_CORE_00327], [SWS_CORE_00332], [SWS_CORE_00336]

Escenarios de error

Al trabajar con ara::core::Future, se especifican las siguientes situaciones de error:

  • Llamada sobre una instancia no válida: La invocación de is_ready(), wait(), wait_for(), wait_until(), GetResult() o then() sobre una instancia no válida (valid() == false) constituye una FutureInvalidViolation [SWS_CORE_00328] [SWS_CORE_00329] [SWS_CORE_00330] [SWS_CORE_00331] [SWS_CORE_00332] [SWS_CORE_00336] [SWS_CORE_00337]. Al invocar get(), en este caso se lanza una FutureException con el código de error kNoState [SWS_CORE_00326].
  • Shared State abandonado (Broken Promise): Si la promesa asociada abandona prematuramente el Shared State, GetResult() devuelve un Result con el código de error estandarizado FutureErrc::kBrokenPromise [SWS_CORE_00336]. Al invocar get() se activa la excepción correspondiente [SWS_CORE_00326].
  • Excepciones en funciones de continuación: Una continuación registrada no debe lanzar excepciones, excepto para implementar una Violation. Si a pesar de ello lanza una excepción, esto da lugar a una FutureContinuationHasThrownViolation [SWS_CORE_00331] [SWS_CORE_00337]. Las excepciones en clausuras deben capturarse y devolverse como un estado de error en forma de Result o Future [SWS_CORE_00331] [SWS_CORE_00337].

Esta guía se basa exclusivamente en los requisitos de especificación de AUTOSAR Adaptive Core (R25-11).

La función se comporta de forma idéntica a su homóloga en std::future; si el cómputo asincrónico aún continúa, la llamada se bloquea hasta su finalización o hasta que ocurra un error [SWS_CORE_00336]. Debido a la llamada, el objeto pierde su estado, de modo que el Future queda invalidado de inmediato (valid() == false) [SWS_CORE_00326]. Una llamada sin bloqueo puede asegurarse previamente mediante is_ready() [SWS_CORE_00332].

                    • 

                  • Si la operación asincrónica abandona prematuramente el Shared State, esto da lugar al error kBrokenPromise conforme a FutureErrc [SWS_CORE_00326], [SWS_CORE_00400].
