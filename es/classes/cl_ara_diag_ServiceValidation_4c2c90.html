Contexto

La clase ara::diag::ServiceValidation representa el elemento de interfaz funcional para la validación específica del fabricante y del proveedor de solicitudes de diagnóstico entrantes en el módulo AUTOSAR Adaptive diag [SWS_DM_00772]. En función del modelado del atributo DiagnosticServiceValidationMapping.category, la validación a través del método Validate se realiza como comprobación del fabricante o como comprobación del proveedor en el marco del orden del Negative Response Code (NRC) según el capítulo 8.7 de la norma ISO 14229-1 [SWS_DM_00772].

En la interacción participan esencialmente tres partes:

  • Aplicación Adaptive: implementa la lógica de validación concreta mediante la especialización de los métodos virtuales Validate [SWS_DM_00774] y Confirmation [SWS_DM_00775].
  • Diagnostic Management (DM): recibe solicitudes UDS, las reenvía a la instancia para su comprobación previa tras una activación correcta mediante Offer [SWS_DM_00776] y notifica la finalización global a través de Confirmation [SWS_DM_00775].
  • Comprobador de diagnóstico: inicia mensajes de diagnóstico cuyos datos sin procesar y metainformación son objeto de la comprobación [SWS_DM_00774].

Ciclo de vida

La instanciación de ServiceValidation se realiza explícitamente pasando un ara::core::InstanceSpecifier, que debe hacer referencia a un PortPrototype modelado de un DiagnosticServiceValidationInterface [SWS_DM_00772]. El constructor está especificado como seguro para hilos [SWS_DM_00772]. Una instancia de ServiceValidation no se debe copiar ni mover: el constructor de copia [SWS_DM_01689], el operador de asignación [SWS_DM_01687], el constructor de movimiento [SWS_DM_01690] y el operador de asignación por movimiento [SWS_DM_01688] están explícitamente eliminados (= delete).

Tras la construcción, la instancia se encuentra en el estado No ofrecido. Mediante la llamada a Offer() se habilita el reenvío de las solicitudes entrantes por parte de Diagnostic Management [SWS_DM_00776]. Si se desea pausar o finalizar el procesamiento, la llamada a StopOffer() impide el reenvío de más mensajes de diagnóstico [SWS_DM_00777]. La habilitación se puede reactivar mediante un nuevo Offer(). La destrucción final tiene lugar a través del destructor virtual ~ServiceValidation() [SWS_DM_00773].

En lo relativo a la concurrencia, los métodos Offer, StopOffer, Validate, Confirmation, así como el destructor, están clasificados como no seguros para hilos [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Las llamadas a estas operaciones deben ser sincronizadas por la aplicación en caso de acceso concurrente.

Diagrama de estados: ciclo de vida y transiciones de estado de una instancia de ServiceValidation. Fuentes: [SWS_DM_00772], [SWS_DM_00773], [SWS_DM_00776], [SWS_DM_00777].

Ruta de uso

El flujo típico para la protección de servicios de diagnóstico se divide en los siguientes pasos:

  1. Instanciación: la aplicación crea la instancia vinculándola al puerto modelado [SWS_DM_00772].
  2. Habilitación: llamada a Offer(). Se instruye a Diagnostic Management para que reenvíe los mensajes de diagnóstico entrantes a esta instancia [SWS_DM_00776].
  3. Validación: ante cada solicitud de diagnóstico entrante, el DM llama al método Validate [SWS_DM_00774]. Se transfieren los datos de la solicitud (incluido el Service Identifier) como ara::core::Span<const std::uint8_t>, así como el contexto a través de MetaInfo. El tiempo de vida de los datos de la solicitud sigue siendo válido hasta que se cumpla la promesa correspondiente o se cancele el procesamiento mediante el CancellationHandler [SWS_DM_00774].
  4. Resultado asíncrono: el método devuelve un ara::core::Future<void> [SWS_DM_00774]. Si la validación es correcta, el future se resuelve sin errores. Si la solicitud no es válida, el future finaliza con un Negative Response Code (NRC) adecuado de DiagUdsNrcErrc conforme a la norma ISO 14229-1 [SWS_DM_00774].
  5. Confirmación de finalización: tan pronto como el procesamiento de la solicitud de diagnóstico haya concluido por completo, el DM llama a Confirmation para transmitir el resultado global (status) y la metaInfo [SWS_DM_00775].
  6. Desregistro: antes del apagado, la aplicación llama a StopOffer() [SWS_DM_00777]. Interpretación: tras la llamada a StopOffer(), es probable que el DM descarte o cancele las solicitudes de validación en curso cuyo future aún no se haya cumplido.

Diagrama de secuencia: secuencia de interacción entre la aplicación, el manejador ServiceValidation y Diagnostic Management (DM). Fuentes: [SWS_DM_00774], [SWS_DM_00775], [SWS_DM_00776], [SWS_DM_00777].

Escenarios de error

Las situaciones de error pueden surgir en diferentes fases y se señalan mediante mecanismos específicos:

  • Infracciones de construcción y de modelo: si falla la vinculación del InstanceSpecifier, el framework notifica violaciones definidas [SWS_DM_00772]:
    • InstanceSpecifierMappingIntegrityViolation: el identificador no se puede resolver o no hace referencia a un PortPrototype.
    • PortInterfaceMappingViolation: el PortPrototype no está tipado mediante un DiagnosticServiceValidationInterface.
    • ProcessMappingViolation: no existe ningún proceso modelado adecuado a la referencia para el proceso de tiempo de ejecución actual.
    • InstanceSpecifierAlreadyInUseViolation: El InstanceSpecifier ya está siendo utilizado por otra instancia en el proceso en ejecución.
  • Habilitación errónea: si se llama a Offer() mientras el servicio ya se está ofreciendo, la llamada falla y devuelve el código de error DiagOfferErrc::kAlreadyOffered con semántica de reversión en el valor de retorno ara::core::Result<void> [SWS_DM_00776].
  • Error de validación: si la comprobación detecta una condición vulnerada (p. ej., condiciones previas o requisitos de seguridad insuficientes), el error se transmite mediante DiagUdsNrcErrc en el ara::core::Future<void> [SWS_DM_00774]. Puesto que Validate está declarado como noexcept, no se deben lanzar excepciones de C++.
  • Seguridad frente a excepciones: todos los métodos de la clase están especificados como seguros frente a excepciones (exception safe) y anotados con noexcept [SWS_DM_00772] [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Los estados de error se representan sin excepción mediante tipos de retorno y mensajes de la plataforma.
