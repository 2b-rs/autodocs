Ofrece una vista eficiente y sin posesión de áreas de memoria contiguas de contenedores o búferes arbitrarios.

La clase ara::core::Span proporciona una vista contigua y sin posesión sobre áreas de memoria y permite la encapsulación eficiente de arrays o búferes sin costes de copia [SWS_CORE_01942]. Las aplicaciones utilizan la clase típicamente para transferir ventanas de datos, así como para generar vistas parciales mediante operaciones de particionado (slicing). Quienes realizan llamadas deben asegurarse estrictamente de que la vida útil de la memoria subyacente sobreviva a la de la vista y de que en operaciones como subspan() se respeten los límites válidos, ya que las infracciones de límites provocan un comportamiento indefinido [SWS_CORE_01966].

Contexto

La clase ara::core::Span constituye una implementación conforme al estándar de una vista de secuencia contigua orientada a std::span de [views.span]. Como abstracción ligera, encapsula un puntero al primer elemento y el número de elementos disponibles, sin ser ella misma propietaria de los datos. Sirve como interfaz uniforme entre componentes que suministran datos y algoritmos que los procesan.

Entre los principales interlocutores de interacción se incluyen:

  • Lógica de aplicación invocadora: Utiliza la vista para accesos de lectura o escritura a áreas de memoria secuenciales sin asignaciones de memoria ni sobrecarga de copia.
  • Fuentes de memoria y contenedores: Cualquier región de memoria contigua, como arrays nativos de C [SWS_CORE_01944], contenedores estandarizados de la plataforma como ara::core::Array [SWS_CORE_01945] [SWS_CORE_01946], estructuras de contenedores genéricos [SWS_CORE_01947] [SWS_CORE_01948] o búferes en crudo con puntero e indicación de longitud [SWS_CORE_01942].
  • Vistas parciales (subspans): Otras instancias de ara::core::Span que surgen por descomposición a partir de una vista superior [SWS_CORE_01965] [SWS_CORE_01966].

Diagrama de contexto: integración de ara::core::Span como vista sin posesión entre la lógica de aplicación y el búfer de memoria. Fuentes: [SWS_CORE_01942], [SWS_CORE_01945], [SWS_CORE_01951]

Ciclo de vida

Las instancias de ara::core::Span están diseñadas como objetos de valor puro sin gestión de recursos propia. La creación se realiza opcionalmente como un span vacío mediante el constructor por defecto [SWS_CORE_01941], mediante la indicación directa de la dirección de inicio y el número de elementos [SWS_CORE_01942] o mediante un intervalo de punteros formado por inicio y fin [SWS_CORE_01943]. Además, se encuentran disponibles constructores tipados para arrays de C [SWS_CORE_01944], contenedores del tipo ara::core::Array [SWS_CORE_01945] [SWS_CORE_01946], así como contenedores genéricos [SWS_CORE_01947] [SWS_CORE_01948]. Los spans existentes se pueden duplicar mediante el constructor de copia estándar [SWS_CORE_01949] o a través de constructores de conversión con tipos de elementos y extensiones (extents) compatibles [SWS_CORE_01950].

Dado que ara::core::Span no asume posesión alguna sobre los datos referenciados, el destructor posee la implementación estándar y está especificado como noexcept=default [SWS_CORE_01951]. De ello se deduce la invariante fundamental (interpretación: asunción 1) de que la vida útil del búfer de memoria subyacente debe abarcar siempre al menos la vida útil de todos los objetos span que apuntan a él; al destruirse el búfer, los spans restantes quedan invalidados. La asignación a través del operador de asignación se realiza trivialmente por copia superficial [SWS_CORE_01952]. Dado que todas las funciones de acceso están declaradas como noexcept y no poseen mecanismos de sincronización interna, es de suponer que el acceso simultáneo de lectura a la misma instancia de span desde múltiples hilos es seguro, siempre que la región de memoria subyacente no se modifique en paralelo (interpretación: asunción 2).

Ruta de uso

Un caso de uso típico comprende la encapsulación de un bloque de datos existente, la comprobación de dimensiones, la extracción de secciones relevantes y el acceso a los elementos:

  1. Creación de la vista: La aplicación instancia ara::core::Span sobre un búfer contiguo, por ejemplo a partir de una instancia de ara::core::Array [SWS_CORE_01945] o mediante punteros de datos en crudo con indicación de longitud [SWS_CORE_01942].
  2. Comprobación de estado y dimensiones: Antes de proseguir con el procesamiento, se verifica el dimensionamiento mediante empty() [SWS_CORE_01969], size() [SWS_CORE_01967] o size_bytes() [SWS_CORE_01968], o bien se consulta la dirección base mediante data() [SWS_CORE_01971].
  3. Slicing / creación de subspans: Para centrarse en ventanas de datos relevantes, la aplicación crea vistas parciales mediante prefijos con first() [SWS_CORE_01961] [SWS_CORE_01962], sufijos con last() [SWS_CORE_01963] [SWS_CORE_01964] o subrangos arbitrarios mediante subspan() [SWS_CORE_01965] [SWS_CORE_01966].
  4. Procesamiento de elementos: El acceso a los datos propiamente dicho se realiza de forma aleatoria mediante el operador de índice operator[] [SWS_CORE_01970], accesos a elementos extremos mediante front() [SWS_CORE_01959] y back() [SWS_CORE_01960] o secuencialmente mediante iteradores desde begin() hasta end() [SWS_CORE_01972] [SWS_CORE_01973].

Diagrama de secuencia: secuencia de llamadas típica para la creación, partición y consulta de elementos de una vista. Fuentes: [SWS_CORE_01942], [SWS_CORE_01966], [SWS_CORE_01970]

Escenarios de error

Todos los métodos de ara::core::Span están declarados como seguros frente a excepciones y noexcept; no se lanzan excepciones de C++ ni se devuelven objetos de error como ara::core::ErrorCode. Los estados de error resultan principalmente de infracciones de precondiciones, las cuales conducen inmediatamente a un comportamiento indefinido (Undefined Behavior):

  • Rebase de tamaño en prefijos y sufijos: Si en first() se solicita una cantidad que supera el tamaño actual (Count > size() o count > size()), el comportamiento es indefinido [SWS_CORE_01961] [SWS_CORE_01962]. La misma infracción de precondición conduce en last() asimismo a un comportamiento indefinido [SWS_CORE_01963] [SWS_CORE_01964].
  • Parámetros de subrango no válidos en subspan: La llamada a subspan() exige obligatoriamente que se cumpla offset <= size() y, en caso de count indicado explícitamente (distinto de dynamic_extent), que se respete además count <= size() - offset. Su inobservancia conduce a un comportamiento indefinido [SWS_CORE_01966].
  • Rebase de límites en el acceso a elementos: El operador de índice operator[] [SWS_CORE_01970], así como las funciones de acceso front() [SWS_CORE_01959] y back() [SWS_CORE_01960] no realizan ninguna comprobación de límites (Bounds Checking). Es de suponer que un acceso fuera de los límites válidos conduce directamente a accesos a memoria indefinidos (interpretación: asunción 3).
