clase ara::diag::ClientAuthentication

[SWS_DM_01132] Upstream: RS_Diag_04251

Interface for the application to inform the Diagnostic Server instance about the authentication states and the user roles that are currently authenticated.

Contexto

La clase ara::diag::ClientAuthentication [SWS_DM_01132] representa la interfaz central a través de la cual una aplicación adaptativa informa a la instancia del Diagnostic Server sobre el estado de autenticación, así como sobre los roles de usuario actualmente autenticados de los clientes de diagnóstico externos (AUTOSAR_AP_SWS_Diagnostics, p. 130). La necesidad de esta interfaz radica en que la comprobación de autenticación propiamente dicha se gestiona bien mediante mecanismos de la propia instancia del Diagnostic Server, bien mediante lógica de aplicación previa [SWS_DM_01142].

Entre los principales interlocutores de interacción se incluyen:

  • Aplicación adaptativa: realiza comprobaciones de autorización (por ejemplo, mediante validación de tokens en el contexto SOVD según [SWS_DM_01470]) y notifica los roles de usuario al servidor.
  • Diagnostic Server (Diagnostic Manager): gestiona los estados de las sesiones, controla el acceso a los recursos de diagnóstico y supervisa los tiempos de inactividad [SWS_DM_01210].
  • Cliente de diagnóstico: se comunica a través de UDS o SOVD. Cada instancia de ClientAuthentication está asignada a una dirección de origen fija o a un rango de direcciones de un cliente de diagnóstico mediante el elemento de modelo DiagnosticExternalAuthenticationIdentification (AUTOSAR_AP_SWS_Diagnostics, p. 129).

Diagrama de contexto: interlocutores de ara::diag::ClientAuthentication en la autenticación del cliente. Fuentes: [SWS_DM_01132], [SWS_DM_01202], AUTOSAR_AP_SWS_Diagnostics, p. 129.

Ciclo de vida

Las instancias de ClientAuthentication no se instancian libremente de forma directa mediante constructores de la aplicación. En su lugar, la aplicación llama a uno de los métodos factoría sobrecargados ara::diag::ExternalAuthentication::Get, tras lo cual el Diagnostic Manager devuelve la instancia correspondiente [SWS_DM_01202]. De forma alternativa, se transfiere una instancia a la aplicación en el marco de la validación de autorización [SWS_DM_01470]. El número total de instancias en el sistema está determinado por los elementos DiagnosticExternalAuthenticationIdentification configurados en el modelo (AUTOSAR_AP_SWS_Diagnostics, p. 129).

En cuanto a la titularidad, el objeto está diseñado como «move-only»: el constructor de copia [SWS_DM_01139] y el operador de asignación por copia [SWS_DM_01140] están explícitamente eliminados (delete). No obstante, las instancias pueden transferirse eficientemente mediante el constructor de movimiento [SWS_DM_01137] y la asignación por movimiento [SWS_DM_01138]. El destructor está declarado como noexcept [SWS_DM_01136]. La clase está especificada como no segura para hilos; las llamadas simultáneas sobre una misma instancia requieren sincronización externa.

El ciclo de vida lógico de la autenticación se basa en la enumeración DiagnosticAuthState [SWS_DM_01133]:

  • kDeAuthenticated: Estado inicial tras el arranque del sistema [SWS_DM_01205]. Al cliente DEM se le asignan exclusivamente los roles definidos como Default en el extracto de diagnóstico (atributo isDefault = TRUE) [SWS_DM_01204]. A partir de este estado, los roles estándar pueden modificarse temporalmente mediante OverrideDefaultRoles [SWS_DM_01209].
  • kAuthenticated: se adopta en cuanto la aplicación llama con éxito a Authenticate [SWS_DM_01206]. En este caso, se asignan al cliente los roles de usuario transferidos explícitamente.
  • Retorno a kDeAuthenticated: si el cliente se encuentra en la sesión de diagnóstico estándar y no llega ninguna otra solicitud tras la última confirmación de transmisión, el Diagnostic Server restablece el estado a kDeAuthenticated por inactividad [SWS_DM_01210] (p. ej., a consecuencia de un timeout de S3 [SWS_DM_01144]).

Diagrama de estados: ciclo de vida de DiagnosticAuthState y transiciones de estado. Fuentes: [SWS_DM_01133], [SWS_DM_01204], [SWS_DM_01205], [SWS_DM_01206], [SWS_DM_01209], [SWS_DM_01210].

Ruta de uso

El uso típico de ClientAuthentication sigue una secuencia ordenada de obtención de la instancia, registro de callbacks, asignación de roles y ampliación opcional del tiempo de ejecución:

  1. Obtener la instancia: la aplicación invoca ara::diag::ExternalAuthentication::Get con la dirección de origen deseada para obtener el objeto ClientAuthentication correspondiente [SWS_DM_01202].
  2. Registrar observador de estado: a través de SetNotifier [SWS_DM_01144], la aplicación registra un callback de función de tipo ClientAuthenticationSetNotifier [SWS_DM_02077]. La instancia del servidor de diagnóstico lo invoca en caso de cambios de estado, en particular durante la reversión automática al estado kDeAuthenticated. Una nueva llamada sobrescribe el notificador registrado previamente [SWS_DM_01144].
  3. Consultar estado: mediante GetState [SWS_DM_01143], la aplicación puede comprobar sincrónicamente en cualquier momento si el cliente está actualmente desautenticado o autenticado.
  4. Asignar roles: una vez verificada la identidad del cliente, la aplicación notifica los roles que se deben habilitar como un vector de DiagnosticAuthRole [SWS_DM_01134] a través de Authenticate [SWS_DM_01142]. La instancia del servidor de diagnóstico cambia al estado kAuthenticated [SWS_DM_01206].
  5. Recibir y reutilizar el handle: en caso de finalización correcta, Authenticate devuelve un ClientAuthenticationHandle [SWS_DM_01142], [SWS_DM_01206]. Mediante este handle, la aplicación puede definir listas de acceso adicionales a través de una DynamicAccessList [SWS_DM_01213] (AUTOSAR_AP_SWS_Diagnostics, p. 132). Además, la creación del handle da lugar a la renovación del período de inactividad (AUTOSAR_AP_SWS_Diagnostics, p. 133).

Diagrama de secuencia: secuencia típica de llamadas para la autenticación y la supervisión del estado. Fuentes: [SWS_DM_01142], [SWS_DM_01144], [SWS_DM_01202], [SWS_DM_01206], [SWS_DM_01210].

Escenarios de error

Los métodos de ClientAuthentication utilizan ara::core::Result para devolver resultados o códigos de error y están declarados en su totalidad con noexcept.

Método código de error Causa y tratamiento de errores
Authenticate [SWS_DM_01142] DiagErrc::kServiceNotAvailable Las funciones esenciales del Diagnostic Manager no están disponibles temporalmente. Se aplica la semántica de reversión; el estado permanece inalterado.
OverrideDefaultRoles [SWS_DM_01141] DiagErrc::kServiceNotAvailable Servicio no disponible. El método requiere además que el cliente se encuentre en el estado kDeAuthenticated [SWS_DM_01209].
GetState [SWS_DM_01143] DiagErrc::kServiceNotAvailable El estado actual no se puede consultar debido a la no disponibilidad de funciones principales del DM.
SetNotifier [SWS_DM_01144] Ninguna No define códigos de error estandarizados; devuelve ara::core::Result<void>.

Interpretación: es probable que el objeto ClientAuthentication actúe como un intermediario ligero, mientras que el mantenimiento autoritativo del estado y la supervisión de la inactividad permanecen por completo en el Diagnostic Manager.

Esta guía se basa exclusivamente en los extractos de especificación del módulo diag en AUTOSAR AP R25-11.
