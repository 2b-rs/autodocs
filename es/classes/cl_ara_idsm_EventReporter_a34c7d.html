Contexto

La clase ara::idsm::EventReporter es el enlace central de una aplicación Adaptive para la detección y notificación de incidentes relevantes para la seguridad al Intrusion Detection System Manager (IdsM) de conformidad con [SWS_AIDSM_10101]. En una arquitectura de vehículo moderna, los componentes de software funcionales monitorizan sus respectivos dominios en busca de anomalías relevantes para la seguridad, infracciones de comunicación o intentos de acceso no autorizados. Si una aplicación detecta tal Security Event, EventReporter asume la notificación estandarizada al subsistema de seguridad.

La interacción se realiza a través de un puerto formalmente definido en el modelo de arquitectura de software del tipo de interfaz SecurityEventReportInterface. Al crear la instancia, este puerto se direcciona mediante un ara::core::InstanceSpecifier [SWS_AIDSM_10301]. De este modo, la clase actúa como una interfaz tipada entre la lógica específica de la aplicación y la pila IdsM de todo el vehículo.

Ciclo de vida

La aplicación instancia un objeto de la clase ara::idsm::EventReporter. El constructor parametrizado espera la referencia a un ara::core::InstanceSpecifier y está declarado como noexcept y thread-safe [SWS_AIDSM_10301]. Durante la inicialización, el objeto se vincula al puerto registrado en el modelo AUTOSAR. Tras la construcción correcta, esta vinculación de puerto permanece inalterada; una reconfiguración posterior no está prevista a nivel de API (Interpretación: un EventReporter permanece firmemente vinculado al puerto configurado durante todo su ciclo de vida).

En cuanto a la concurrencia, la clase está diseñada para el uso industrial con multithreading: tanto la creación [SWS_AIDSM_10301] como todas las variantes de la función de notificación ReportEvent están especificadas como plenamente thread-safe ([SWS_AIDSM_10302] a [SWS_AIDSM_10307]). Por lo tanto, varios hilos de un proceso pueden invocar la misma instancia en paralelo y sin mecanismos de sincronización externos. El objeto sigue el patrón RAII habitual y libera sus recursos de plataforma de manera determinista al salir del ámbito.

Ruta de uso

El flujo de trabajo habitual comprende la instanciación del reportero durante el inicio del sistema o la inicialización del componente, seguida de repetidas notificaciones de eventos durante el funcionamiento:

  1. Instanciar el reportero: a partir del InstanceSpecifier específico del modelo, la instancia se configura a través del constructor EventReporter(const ara::core::InstanceSpecifier&) [SWS_AIDSM_10301].
  2. Registrar datos del evento: si se produce una desviación relevante para la seguridad, la aplicación selecciona la sobrecarga adecuada de ReportEvent, en función de qué metadatos estén disponibles para el evento.
  3. Notificar el evento: mediante la invocación de ReportEvent, se transmiten los contadores, la información de contexto y las marcas de tiempo al IdsM.

Diagrama de secuencia: flujo típico desde la construcción hasta la notificación de eventos al IdsM. Fuentes: [SWS_AIDSM_10101], [SWS_AIDSM_10301], [SWS_AIDSM_10304]

La interfaz proporciona un total de seis sobrecargas escalonadas que cubren todas las variantes de los parámetros de evento modelados:

  • Sin contexto: los eventos de conteo puros sin carga útil se transmiten mediante ReportEvent(const CountType count = 1) [SWS_AIDSM_10302]. Si adicionalmente se debe registrar un momento específico de captura, está disponible la signatura con TimestampType [SWS_AIDSM_10303].
  • Con datos de contexto: los datos adicionales de diagnóstico o de trama se transmiten mediante ContextDataType, opcionalmente sin marca de tiempo [SWS_AIDSM_10304] o con marca de tiempo [SWS_AIDSM_10305].
  • Con datos de contexto versionados: en caso de que el esquema de los datos de contexto esté sujeto a cambios evolutivos, las signaturas aceptan VersionedContextDataType, también sin marca de tiempo [SWS_AIDSM_10306] así como con marca de tiempo [SWS_AIDSM_10307].

En todas las signaturas, el parámetro count tiene el valor predeterminado 1, de modo que se puede notificar una incidencia individual sin indicar explícitamente el contador.

Escenarios de error

La API de ara::idsm::EventReporter está diseñada de manera defensiva y estrictamente no bloqueante para rutas críticas de tiempo real. Todos los métodos —tanto el constructor [SWS_AIDSM_10301] como las seis variantes de ReportEvent ([SWS_AIDSM_10302] a [SWS_AIDSM_10307])— están declarados como noexcept y no tienen valor de retorno (void).

De ello se derivan condiciones marco arquitectónicas esenciales:

  • En la interfaz de llamada no se lanzan excepciones de C++ ni se devuelven códigos de error de ara::core::Result.
  • Una condición previa para un funcionamiento correcto es el suministro de un InstanceSpecifier válido y configurado en el modelo AUTOSAR durante la creación del objeto.
  • Los posibles errores de almacenamiento en búfer, la sobrecarga del canal de transmisión o la inaccesibilidad del servicio IdsM no se pueden comunicar al llamador de forma síncrona (interpretación: los desbordamientos internos de búfer o los fallos en la comunicación del IdsM se registran internamente en la pila de la plataforma o se descartan para no bloquear la aplicación de tiempo real que realiza la llamada).

<h4>Contexto</h4>
<p>La clase <code>ara::idsm::EventReporter</code> es el enlace central de una aplicación Adaptive para la detección y notificación de incidentes relevantes para la seguridad al Intrusion Detection System Manager (IdsM) de conformidad con <a class="spec-record-ref" data-req="SWS_AIDSM_10101" href="../spec/record.html?id=SWS_AIDSM_10101">[SWS_AIDSM_10101]</a>. En una arquitectura de vehículo moderna, los componentes de software funcionales monitorizan sus respectivos dominios en busca de anomalías relevantes para la seguridad, infracciones de comunicación o intentos de acceso no autorizados. Si una aplicación detecta tal Security Event, <code>EventReporter</code> asume la notificación estandarizada al subsistema de seguridad.</p>
<p>La interacción se realiza a través de un puerto formalmente definido en el modelo de arquitectura de software del tipo de interfaz <code>SecurityEventReportInterface</code>. Al crear la instancia, este puerto se direcciona mediante un <code>ara::core::InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>. De este modo, la clase actúa como una interfaz tipada entre la lógica específica de la aplicación y la pila IdsM de todo el vehículo.</p>

<h4>Ciclo de vida</h4>
<p>La aplicación instancia un objeto de la clase <code>ara::idsm::EventReporter</code>. El constructor parametrizado espera la referencia a un <code>ara::core::InstanceSpecifier</code> y está declarado como <code>noexcept</code> y thread-safe <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>. Durante la inicialización, el objeto se vincula al puerto registrado en el modelo AUTOSAR. Tras la construcción correcta, esta vinculación de puerto permanece inalterada; una reconfiguración posterior no está prevista a nivel de API (Interpretación: un <code>EventReporter</code> permanece firmemente vinculado al puerto configurado durante todo su ciclo de vida).</p>
<p>En cuanto a la concurrencia, la clase está diseñada para el uso industrial con multithreading: tanto la creación <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a> como todas las variantes de la función de notificación <code>ReportEvent</code> están especificadas como plenamente thread-safe (<a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a> a <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>). Por lo tanto, varios hilos de un proceso pueden invocar la misma instancia en paralelo y sin mecanismos de sincronización externos. El objeto sigue el patrón RAII habitual y libera sus recursos de plataforma de manera determinista al salir del ámbito.</p>

<h4>Ruta de uso</h4>
<p>El flujo de trabajo habitual comprende la instanciación del reportero durante el inicio del sistema o la inicialización del componente, seguida de repetidas notificaciones de eventos durante el funcionamiento:</p>
<ol>
<li><strong>Instanciar el reportero:</strong> a partir del <code>InstanceSpecifier</code> específico del modelo, la instancia se configura a través del constructor <code>EventReporter(const ara::core::InstanceSpecifier&amp;)</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>.</li>
<li><strong>Registrar datos del evento:</strong> si se produce una desviación relevante para la seguridad, la aplicación selecciona la sobrecarga adecuada de <code>ReportEvent</code>, en función de qué metadatos estén disponibles para el evento.</li>
<li><strong>Notificar el evento:</strong> mediante la invocación de <code>ReportEvent</code>, se transmiten los contadores, la información de contexto y las marcas de tiempo al IdsM.</li>
</ol>

<p>La interfaz proporciona un total de seis sobrecargas escalonadas que cubren todas las variantes de los parámetros de evento modelados:</p>
<ul>
<li><em>Sin contexto:</em> los eventos de conteo puros sin carga útil se transmiten mediante <code>ReportEvent(const CountType count = 1)</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a>. Si adicionalmente se debe registrar un momento específico de captura, está disponible la signatura con <code>TimestampType</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10303" href="../spec/record.html?id=SWS_AIDSM_10303">[SWS_AIDSM_10303]</a>.</li>
<li><em>Con datos de contexto:</em> los datos adicionales de diagnóstico o de trama se transmiten mediante <code>ContextDataType</code>, opcionalmente sin marca de tiempo <a class="spec-record-ref" data-req="SWS_AIDSM_10304" href="../spec/record.html?id=SWS_AIDSM_10304">[SWS_AIDSM_10304]</a> o con marca de tiempo <a class="spec-record-ref" data-req="SWS_AIDSM_10305" href="../spec/record.html?id=SWS_AIDSM_10305">[SWS_AIDSM_10305]</a>.</li>
<li><em>Con datos de contexto versionados:</em> en caso de que el esquema de los datos de contexto esté sujeto a cambios evolutivos, las signaturas aceptan <code>VersionedContextDataType</code>, también sin marca de tiempo <a class="spec-record-ref" data-req="SWS_AIDSM_10306" href="../spec/record.html?id=SWS_AIDSM_10306">[SWS_AIDSM_10306]</a> así como con marca de tiempo <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>.</li>
</ul>
<p>En todas las signaturas, el parámetro <code>count</code> tiene el valor predeterminado <code>1</code>, de modo que se puede notificar una incidencia individual sin indicar explícitamente el contador.</p>

<h4>Escenarios de error</h4>
<p>La API de <code>ara::idsm::EventReporter</code> está diseñada de manera defensiva y estrictamente no bloqueante para rutas críticas de tiempo real. Todos los métodos —tanto el constructor <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a> como las seis variantes de <code>ReportEvent</code> (<a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a> a <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>)— están declarados como <code>noexcept</code> y no tienen valor de retorno (<code>void</code>).</p>
<p>De ello se derivan condiciones marco arquitectónicas esenciales:</p>
<ul>
<li>En la interfaz de llamada no se lanzan excepciones de C++ ni se devuelven códigos de error de <code>ara::core::Result</code>.</li>
<li>Una condición previa para un funcionamiento correcto es el suministro de un <code>InstanceSpecifier</code> válido y configurado en el modelo AUTOSAR durante la creación del objeto.</li>
<li>Los posibles errores de almacenamiento en búfer, la sobrecarga del canal de transmisión o la inaccesibilidad del servicio IdsM no se pueden comunicar al llamador de forma síncrona (interpretación: los desbordamientos internos de búfer o los fallos en la comunicación del IdsM se registran internamente en la pila de la plataforma o se descartan para no bloquear la aplicación de tiempo real que realiza la llamada).</li>
</ul>
