Sirve para la provisión del lado del servidor de un servicio y para el procesamiento de invocaciones de métodos entrantes.

La clase <SI-Namespace>::skeleton::<SI>Skeleton sirve como base del lado del servidor para la provisión de un servicio en la AUTOSAR Adaptive Platform y vincula eventos, campos (fields) y métodos al middleware. Tras la instanciación con un identificador de instancia, el servicio se pone a disposición de los consumidores en la red mediante OfferService() y puede retirarse de nuevo con StopOfferService() [SWS_CM_00101], [SWS_CM_00111]. Según el modo de procesamiento configurado, las invocaciones de métodos entrantes se procesan bien basadas en eventos o bien deben iniciarse activamente por la aplicación mediante sondeo (polling). Dado que las operaciones de copia están eliminadas, la propiedad de la instancia permanece estrictamente en la aplicación de servicio creadora.

Contexto

La clase plantilla <SI-Namespace>::skeleton::<SI>Skeleton conforma el extremo del lado del servidor para la provisión de una Service Interface en la AUTOSAR Adaptive Platform. Como nexo de unión entre la lógica de aplicación y la capa de comunicación, el skeleton encapsula la vinculación específica del middleware y proporciona elementos de interfaz tipados. Para ello, la clase declara variables miembro para eventos mediante events::<Event> [SWS_CM_99557], para campos (fields) mediante fields::<Field> [SWS_CM_99558], para disparadores (triggers) mediante triggers::<Trigger> [SWS_CM_99559] así como para parámetros de salida de métodos mediante <MethodOutArgType> [SWS_CM_11550]. Interpretación: para proporcionar la funcionalidad real del servicio, la aplicación de servicio suele derivar una clase concreta de <SI>Skeleton para implementar los métodos de la interfaz.

Ciclo de vida

La instanciación de un skeleton se realiza especificando la asignación de instancia y el modo de procesamiento para invocaciones de métodos (ara::com::MethodCallProcessingMode, por defecto kEvent). Los constructores válidos aceptan un ara::core::InstanceSpecifier [SWS_CM_00152], un único ara::com::InstanceIdentifier [SWS_CM_00130] o un conjunto de identificadores a través de un ara::com::InstanceIdentifierContainer [SWS_CM_00153]. Dado que la identidad del extremo del servicio es unívoca, el constructor de copia [SWS_CM_00134] y el operador de asignación por copia [SWS_CM_11548] están explícitamente eliminados (delete). No obstante, los recursos pueden transferirse mediante el constructor de movimiento [SWS_CM_00135] así como el operador de asignación por movimiento [SWS_CM_11549].

Directamente tras la construcción, la instancia de servicio está creada localmente, pero aún no es visible en la red de comunicación. La publicación para los consumidores del servicio se produce únicamente mediante la invocación de OfferService() [SWS_CM_00101], EXP_ARAComAPI p. 10. Si el servicio ya no debe ofrecerse, StopOfferService() retira la provisión [SWS_CM_00111], EXP_ARAComAPI p. 10. A continuación, el skeleton puede ofrecerse de nuevo o destruirse mediante el destructor virtual ~<SI>Skeleton() [SWS_CM_11370].

Diagrama de estados: ciclo de vida y transiciones de estado de un skeleton de servicio desde la instanciación hasta la liberación. Fuentes: [SWS_CM_00101], [SWS_CM_00111], [SWS_CM_11370], EXP_ARAComAPI p. 10

Ruta de uso

El flujo regular para la provisión de un servicio se divide en los siguientes pasos:

  1. Configuración y registro de manejadores: antes de ofrecer el servicio, pueden depositarse manejadores específicos de la aplicación. Mediante SetTransportFaultConditionHandler() se registra un manejador de errores de transporte bien directamente [SWS_CM_00093] o bien con un ejecutor dedicado para tareas asíncronas [SWS_CM_00094]; puede eliminarse en caso necesario mediante UnsetTransportFaultConditionHandler() [SWS_CM_00095]. Los manejos de errores End-to-End pueden sobrescribirse mediante el método virtual E2EErrorHandler() [SWS_CM_10470].
  2. Oferta del servicio: la aplicación de servicio invoca OfferService() [SWS_CM_00101]. Una invocación exitosa devuelve un ara::core::Result<void> vacío y habilita la instancia de servicio en la red.
  3. Procesamiento de solicitudes entrantes: si el skeleton se instanció en el modo MethodCallProcessingMode::kPoll, la aplicación debe ejecutar activamente las llamadas de clientes pendientes invocando ProcessNextMethodCall() [SWS_CM_00199]. La invocación del método se ejecuta en el contexto de este hilo; el valor de retorno señala si hay más llamadas pendientes.
  4. Finalización del servicio: antes de destruir la instancia, la oferta se finaliza con StopOfferService() [SWS_CM_00111].

Diagrama de secuencia: secuencia de interacción entre la aplicación de servidor, el skeleton de servicio y la capa de comunicación durante el funcionamiento del servicio. Fuentes: [SWS_CM_00101], [SWS_CM_00111], [SWS_CM_00199], [SWS_CM_00093]

Escenarios de error

Al utilizar la clase skeleton deben tenerse en cuenta diversos escenarios de error y precondiciones:

  • Infracciones de construcción: si falla la autorización mediante Grant Enforcement, la construcción se interrumpe con InsufficientPermissionsViolation [SWS_CM_00130], [SWS_CM_00152], [SWS_CM_00153]. La transmisión de un modo de procesamiento no admisible da lugar a una WrongMethodCallProcessingModeViolation. Si se utiliza un InstanceSpecifier, las inconsistencias de modelo o las asignaciones múltiples pueden provocar los errores InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation o InstanceSpecifierAlreadyInUseViolation [SWS_CM_00152].
  • Fallo en la oferta del servicio: si OfferService() falla, se devuelve un código de error de ara::com::ComErrc [SWS_CM_00101]: ComErrc::kFieldValueNotInitialized (un campo no se inicializó previamente mediante Update()), ComErrc::kFieldSetHandlerNotSet (falta un manejador de establecimiento requerido de un campo) o ComErrc::kCommunicationFailure (error de conexión o de seguridad de la vinculación de red).
  • Infracción del modo de procesamiento: una invocación de ProcessNextMethodCall() desencadena una WrongMethodCallProcessingModeViolation si el skeleton no fue configurado para kPoll, sino para kEvent o kEventSingleThread [SWS_CM_00199].
  • Manejadores de errores no válidos: si se pasa a SetTransportFaultConditionHandler() un invocable (callable) inexistente o vacío, esto resulta en una InvalidHandlerViolation [SWS_CM_00093], [SWS_CM_00094].
  • Errores E2E y corrupción de datos: al recibir mensajes erróneos, se invoca E2EErrorHandler() con un correspondiente ComE2EErrc [SWS_CM_10470]. Si se trata de un error de CRC, también la DataID puede estar corrompida, por lo que la aplicación no debe considerar fiable el identificador transferido.
  • Errores de destrucción: si al destruir el skeleton aún existen muestras de datos abiertas, el destructor se interrumpe con una DanglingSamplesViolation [SWS_CM_11370].

Esta guía se basa exclusivamente en las prescripciones de especificación de la AUTOSAR Adaptive Platform R25-11.

  Procedencia
  

      

      

      El método OfferService() se invoca en una instancia de la clase Skeleton para ofrecer un servicio proporcionado en el sistema y hacerlo localizable para los consumidores a través de Service Discovery [SWS_CM_00101], ARAComAPI §6.5 «Service Discovery». La llamada se realiza sin parámetros y de forma síncrona tan pronto como la implementación del servicio se ha instanciado completamente y se ha colocado en un estado listo para operar AUTOSAR_AP_EXP_ARAComAPI §5.4.4 «Offering Service instance». La función está declarada como noexcept y devuelve un ara::core::Result<void> [SWS_CM_00101].
      
  
      El ofrecimiento es un requisito indispensable para la comunicación funcional a través de métodos, eventos, campos o disparadores (triggers) AUTOSAR_AP_EXP_ARAComAPI §4.2 «Means of Communication». Si, por ejemplo, se intenta enviar un trigger sin haberlo ofrecido previamente, la operación fallará con ComErrc::kServiceNotOffered [SWS_CM_00721]. En lo relativo a la concurrencia, se aplica lo siguiente: tan pronto como se invoca OfferService(), las llamadas a métodos entrantes ya pueden entregarse a la instancia del servicio, incluso si la llamada a OfferService() aún no ha retornado AUTOSAR_AP_EXP_ARAComAPI §5.4.4 «Offering Service instance».
      
  
      Si el ofrecimiento falla, el ara::core::Result devuelto contiene el código de error correspondiente de ComErrc [SWS_CM_00101], [SWS_CM_10432]:
      
  
        
    
      • ComErrc::kFieldValueNotInitialized: Al menos un valor de campo configurado aún no se había inicializado antes del ofrecimiento [SWS_CM_00101].
        • 
    
      • ComErrc::kFieldSetHandlerNotSet: Para un campo con soporte de setter todavía no se ha registrado ningún manejador mediante RegisterSetHandler() [SWS_CM_00101].
        • 
    
      • ComErrc::kCommunicationFailure: La vinculación de red notifica un error de comunicación subsanable o el fallo de la comunicación segura [SWS_CM_00101].
        • 
  
      
  
      Si se desea finalizar la provisión del servicio, debe invocarse StopOfferService() AUTOSAR_AP_EXP_ARAComAPI §5.4.4 «Offering Service instance».

          El método ProcessNextMethodCall() sirve a los proveedores de servicios en el Skeleton para procesar de forma determinista las llamadas a métodos entrantes en modo polling [SWS_CM_00199]. Solo debe utilizarse si la instancia de Skeleton ha sido configurada con el modo ara::com::MethodCallProcessingMode::kPoll EXP ARAComAPI §2 «Polling».
          
  
  
          Uso y semántica
          
  
          La función no toma parámetros y ejecuta una solicitud de llamada a método pendiente de forma síncrona en el contexto del hilo de quien la invoca [SWS_CM_00199], [SWS_CM_00191]. Esto permite en particular a las aplicaciones de tiempo real procesar solicitudes de servicio sin cambios de contexto de hilo incontrolados dentro de su presupuesto de tiempo asignado EXP ARAComAPI §5.4 «ProcessNextMethodCall». El valor de retorno señala el resultado de la consulta:
          
  
            
    
          • true: Al menos una solicitud pendiente se encontraba en la cola y ha sido procesada [SWS_CM_00199].
            • 
    
          • false: No había ninguna solicitud pendiente; la cola estaba vacía [SWS_CM_00199]. Una llamada subsiguiente directa tras un false suele ser ineficaz EXP ARAComAPI §5.4 «ProcessNextMethodCall».
            • 
  
          

  
          Tratamiento de errores y condiciones límite
          
  
          La función está especificada como noexcept y exception safe [SWS_CM_00199]. Una llamada a un Skeleton que ha sido instanciado con kEvent o kEventSingleThread representa una infracción (WrongMethodCallProcessingModeViolation) [SWS_CM_00199]. Interpretación: dado que las excepciones regulares de C++ quedan descartadas por noexcept, es probable que la plataforma trate dicha infracción como un error grave de tiempo de ejecución.
