Permite a las aplicaciones la provisión y respuesta a consultas de lectura de diagnóstico para el Diagnostic Manager.
GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 70357181b1bf Procedencia

Permite a las aplicaciones la provisión y respuesta a consultas de lectura de diagnóstico para el Diagnostic Manager.

La interfaz sirve a las aplicaciones Adaptive para proporcionar datos de diagnóstico para accesos de lectura de Diagnostic Management. Tras la instanciación mediante un especificador de instancia, la aplicación debe ofrecer activamente el servicio para que puedan recibirse peticiones de lectura entrantes [SWS_DM_00597]. Las peticiones entrantes se procesan a través del método de lectura asíncrono, que proporciona los datos de salida solicitados o códigos de respuesta negativos en un valor futuro [SWS_DM_00596]. Dado que las operaciones de copia y movimiento están eliminadas, cada instancia está vinculada de forma fija a su contexto.

Contexto

La clase C++ generada <DataElementInterface> actúa dentro del clúster funcional diag (AUTOSAR Adaptive Platform) como interfaz de servidor estandarizada para la provisión de datos de diagnóstico legibles AUTOSAR_AP_SWS_Diagnostics p. 68. Concretamente representa un DiagnosticDataElementInterface en el rol read, a través del cual una aplicación Adaptive transmite valores de datos para peticiones de diagnóstico (como por ejemplo UDS ReadDataByIdentifier) al Diagnostic Manager (DM) [SWS_DM_00596].

Los interlocutores de interacción esenciales son Diagnostic Management del demonio de plataforma, que coordina las peticiones de diagnóstico entrantes, así como la aplicación Adaptive implementadora, que hereda de esta interfaz y formula la lógica de provisión. La instanciación y la asignación a la arquitectura de software se realizan mediante un prototipo de puerto modelado que se vincula a través de un ara::core::InstanceSpecifier [SWS_DM_00587]. Los datos de salida se encapsulan en una estructura específica del tipo, cuyos argumentos están representados por los elementos de salida correspondientes [SWS_DM_80023], [SWS_DM_00581].

Ciclo de vida

La creación de una instancia se realiza mediante el constructor especificando el ara::core::InstanceSpecifier así como el modo de concurrencia ara::diag::ConcurrencyType [SWS_DM_00587]. Para mantener una asignación unívoca dentro del proceso, tanto el constructor de copia como el constructor de movimiento están eliminados [SWS_DM_01661], [SWS_DM_01662]. Del mismo modo, los operadores de asignación por copia y por movimiento están explícitamente eliminados [SWS_DM_01659], [SWS_DM_01660]. Por lo tanto, una instancia permanece fija en su dirección creada.

En cuanto a la operación, el objeto pasa por fases definidas:

  • No ofrecido (Not Offered): tras la construcción, el objeto se encuentra inicialmente en un estado inactivo en el que el DM no entrega peticiones de lectura.
  • Ofrecido (Offered): mediante la invocación de Offer() se activa el servicio en el DM, de modo que las peticiones de lectura entrantes se reenvían [SWS_DM_00597].
  • Dado de baja: la invocación de StopOffer() desactiva el reenvío de futuras peticiones de diagnóstico por parte del DM [SWS_DM_00617].
  • Destrucción: el destructor virtual ~<DataElementInterface>() finaliza el ciclo de vida de la instancia de la interfaz [SWS_DM_00588].

Mientras que el constructor está especificado como seguro para subprocesos [SWS_DM_00587], Offer(), StopOffer(), Read() y el destructor no son seguros para subprocesos [SWS_DM_00597], [SWS_DM_00617], [SWS_DM_00596], [SWS_DM_00588]. El parámetro concurrencyType en el constructor determina si la implementación del manejador está ejecutada como thread-safe (kConcurrent) o no thread-safe (kNotConcurrent) [SWS_DM_00587].

Diagrama de estados: fases de estado de una instancia de interfaz entre inicialización, estado de publicación y destrucción. Fuentes: [SWS_DM_00587], [SWS_DM_00597], [SWS_DM_00617], [SWS_DM_00588].

Ruta de uso

El flujo regular para la consulta de datos sigue una secuencia fija de pasos:

  1. Instanciación: La aplicación instancia la clase controladora derivada con el instanceSpec y concurrencyType deseados [SWS_DM_00587].
  2. Habilitación del servicio: La aplicación invoca Offer(), lo que capacita al DM para reenviar peticiones de lectura [SWS_DM_00597].
  3. Procesamiento de peticiones de lectura: Si llega una petición de lectura al DM, este invoca el método puramente virtual Read(metaInfo, cancellationHandler) en el controlador [SWS_DM_00596]. La aplicación evalúa metaInfo y puede comprobar mediante cancellationHandler.IsCanceled() si la conversación se ha cancelado, o registrar una retrollamada a través de cancellationHandler.SetNotifier [SWS_DM_00596].
  4. Respuesta: Interpretación: La determinación efectiva de los datos de salida debería llevarse a cabo típicamente de forma asíncrona; el resultado se proporciona en un ara::core::Future con el correspondiente objeto ReadOutput [SWS_DM_00596], [SWS_DM_00581].
  5. Finalización del servicio: Antes del apagado, la aplicación invoca StopOffer() para impedir el reenvío [SWS_DM_00617], seguido de la destrucción del objeto [SWS_DM_00588].

Diagrama de secuencia: Secuencia de llamadas desde el registro del servicio hasta la desinscripción, pasando por la lectura asíncrona. Fuentes: [SWS_DM_00597], [SWS_DM_00596], [SWS_DM_00617].

Escenarios de error

En caso de error, las diferentes fases de ciclo de vida deben considerarse de manera diferenciada:

Ya durante la construcción pueden producirse violaciones de integridad que se señalan mediante infracciones específicas [SWS_DM_00587]:

  • InstanceSpecifierMappingIntegrityViolation: El especificador de instancia no puede resolverse en el modelo del ejecutable o no hace referencia a un PortPrototype.
  • PortInterfaceMappingViolation: Un PortPrototype tipificado mediante el DiagnosticDataElementInterface no está referenciado por un DiagnosticDataPortMapping.
  • ProcessMappingViolation: Aunque existe una InstanceRef adecuada, no se ha encontrado ningún proceso modelado coincidente que se corresponda con el proceso en tiempo de ejecución.
  • InstanceSpecifierAlreadyInUseViolation: El constructor se invocó con un InstanceSpecifier que ya se está utilizando en el proceso actual.

Si se invoca Offer() para un servicio ya ofrecido, el método devuelve un ara::core::Result con el código de error DiagOfferErrc::kAlreadyOffered (semántica de reversión) [SWS_DM_00597].

Si una petición de lectura no puede responderse satisfactoriamente en Read(), el ara::core::Future devuelto debe contener un Negative Response Code (NRC) de ISO 14229-1 correspondiente a través de DiagUdsNrcErrc o un ApApplicationError [SWS_DM_00596].

Esta guía se basa en la especificación AUTOSAR AP Release R25-11 y resume los requisitos del módulo diag.

Uso y parámetros:

  • instanceSpec: Especifica la instancia concreta del servicio en el contexto del modelo.
  • concurrencyType: Determina el comportamiento de concurrencia y establece si la interfaz se ejecuta de forma segura para subprocesos (kConcurrent) o no segura para subprocesos (kNotConcurrent).

Concurrencia y seguridad frente a excepciones: La función está declarada como noexcept y clasificada en la especificación como thread-safe y exception-safe [SWS_DM_00587].

Tratamiento de errores y violaciones de modelado: Los errores no dan lugar a excepciones de C++, sino a violaciones especificadas:

  • InstanceSpecifierAlreadyInUseViolation: Se envía cuando el instanceSpec ya está ocupado en el mismo proceso por una llamada al constructor.

  Procedencia
  

              

              

              El método síncrono Offer de un DataElementInterface activa el reenvío de peticiones de diagnóstico entrantes por parte del Diagnostic Management Daemon (DM) al manejador correspondiente ([SWS_DM_00597]). No acepta parámetros, garantiza seguridad frente a excepciones (exception safe / noexcept) y devuelve un ara::core::Result<void> ([SWS_DM_00597]).
              

              Para el tratamiento de fallos, la concurrencia y el orden se aplican las siguientes prescripciones:
              

                

              • Tratamiento de fallos: Si el servicio ya se había ofrecido anteriormente, la llamada falla y proporciona el código de error DiagOfferErrc::kAlreadyOffered con semántica de reversión ([SWS_DM_00597]).
                • 

              • Concurrencia: La función está especificada como no segura para subprocesos (not thread-safe) ([SWS_DM_00597]). Las llamadas simultáneas en la misma instancia deben sincronizarse en la aplicación.
                • 

              • Condiciones de orden: Mientras la Adaptive Application no haya llamado a Offer, el DM no reenvía peticiones al manejador o utiliza valores de reserva internos ([SWS_DM_01525], [SWS_DM_01527]). La llamada debería tener lugar típicamente en la fase de inicio de la aplicación (interpretación).
                • 

              

              El concepto de puesta a disposición mediante Offer se utiliza de forma consistente también en otros manejadores del DM, como rutinas ([SWS_DM_00594]) e identificadores de datos ([SWS_DM_00599]). Aunque la denominación se basa en ara::com, constituye una implementación independiente del DM (SWS Diagnostics §7.3.4.1.2 «Monitors»).

  Procedencia
  

                  

                  

                  El método Read sirve para poner a disposición un elemento de datos dentro de una instancia de DiagnosticDataElementInterface en el rol read [SWS_DM_00596]. La llamada se realiza de forma asíncrona por parte del Diagnostic Manager para procesar peticiones de lectura de diagnóstico.
                  

                  Uso y signatura
                  

                  La interfaz devuelve un ara::core::Future con un objeto tipado ReadOutput conforme a [SWS_DM_00581] [SWS_DM_00596]. A través de los parámetros transferidos, la implementación procesa la petición:
                  

                    

                  • metaInfo: Transfiere metainformación sobre la petición de diagnóstico entrante [SWS_DM_00596].
                    •
