Coordina los estados de energía con el sistema operativo e informa a State Management sobre los eventos de reactivación.

Como envoltorio de OS (OS-Wrapper), la interfaz coordina los estados de energía entre State Management y el sistema operativo ([SWS_SM_71000]). State Management registra previamente a través de ella manejadores de devolución de llamada para eventos de reactivación y reenvía solicitudes de estado concretas al sistema operativo ([SWS_SM_71001]). Una vez completada la reactivación, el registro del manejador se puede anular de nuevo en el envoltorio de OS. Como condición de contorno funcional esencial, se aplica que todas las llamadas a métodos no son seguras frente a subprocesos y, por lo tanto, el llamador debe serializarlas obligatoriamente.

Contexto

La clase C++ apext::sm::PowerStateInterface actúa como interfaz funcional del módulo State Management para la coordinación de estados de energía con el sistema operativo ([SWS_SM_71000], SWS StateManagement §C.1.2 «Class: PowerStateInterface»). En la arquitectura del sistema, asume el rol de un envoltorio de OS (OS-Wrapper) que reenvía solicitudes de State Management al sistema operativo subyacente y recibe respuestas. En la interacción global participan tres componentes principales: State Management como instancia coordinadora, la clase PowerStateInterface como intermediaria y el sistema operativo host, que ejecuta la gestión de energía cercana al hardware ([SWS_SM_71001]).

Diagrama de contexto: coordinación de estados de energía y señales de reactivación entre State Management, el envoltorio de OS y el sistema operativo. Fuentes: [SWS_SM_71000], [SWS_SM_71001], [SWS_SM_71003].

Ciclo de vida

La creación y destrucción de instancias de la clase PowerStateInterface no está regulada en los documentos de especificación mediante métodos de fábrica explícitos. Según la interpretación, se asume que la instanciación la realiza State Management durante su fase de inicialización con el fin de proporcionar el envoltorio de OS. Para la inclusión de la clase está previsto el encabezado apext/sm/power_state_interface.h ([SWS_SM_71001], SWS StateManagement §C.1.2.1.1 «Member Functions»).

En cuanto al estado interno, el objeto gestiona el registro de un manejador para eventos de reactivación. Este estado permanece activo hasta que el manejador se elimina explícitamente ([SWS_SM_71005]). Respecto a la concurrencia, todas las funciones miembro están clasificadas como no seguras para subprocesos (not-threadsafe) ([SWS_SM_71001], [SWS_SM_71003], [SWS_SM_71005]). Por lo tanto, el State Management invocador debe garantizar bajo su propia responsabilidad que las llamadas a una instancia se serialicen estrictamente y que no se produzcan accesos paralelos no protegidos desde múltiples subprocesos.

Ruta de uso

Una ruta de uso típica para el control de estados de energía y para la recepción de señales de reactivación se desarrolla en varios pasos coordinados entre sí:

  • Handler-Registrierung: antes de iniciar un estado de ahorro de energía, State Management registra mediante RegisterWakeUpHandler una función de devolución de llamada del tipo apext::sm::WakeUpHandler en el wrapper del OS ([SWS_SM_71003], SWS StateManagement §C.1.2.1.1.1 «RegisterWakeUpHandler»). De este modo se determina cómo se informará a State Management sobre los procesos de reactivación posteriores.
  • Zustandsanforderung: a continuación, State Management invoca el método SetPowerState con el estado de destino deseado apext::sm::PowerState ([SWS_SM_71001], SWS StateManagement §C.1.2.1.1.2 «SetPowerState»). La interfaz reenvía esta solicitud inmediatamente al sistema operativo. La implementación técnica de la transición se realiza presumiblemente de forma específica para la plataforma en el sistema operativo.
  • Aufwachbenachrichtigung: si el sistema operativo detecta un evento de reactivación, la notificación se envía al wrapper del OS. Este ejecuta el WakeUpHandler registrado previamente. Según la interpretación, la llamada debería realizarse de forma asíncrona en el contexto de ejecución del proceso de reactivación.
  • Handler-Deregistrierung: tan pronto como el proceso de reactivación haya finalizado o State Management no requiera más notificaciones, la devolución de llamada registrada se elimina del wrapper del OS mediante UnregisterWakeUpHandler ([SWS_SM_71005], SWS StateManagement §C.1.2.1.1.3 «UnregisterWakeUpHandler»).

Diagrama de secuencia: secuencia típica del registro del manejador, reenvío del estado al sistema operativo y cancelación del registro. Fuentes: [SWS_SM_71001], [SWS_SM_71003], [SWS_SM_71005].

Escenarios de error

Los métodos de interfaz RegisterWakeUpHandler, SetPowerState y UnregisterWakeUpHandler tienen el tipo de retorno void y no definen códigos de retorno de error específicos ([SWS_SM_71001], [SWS_SM_71003], [SWS_SM_71005]). Todas las funciones están declaradas como noexcept y garantizan una seguridad total frente a excepciones (exception safe).

Los estados erróneos del sistema pueden originarse principalmente a partir de infracciones de las condiciones previas. Entre ellas se incluye el incumplimiento de la seguridad de subprocesos requerida debido a llamadas a métodos paralelas y desprotegidas. Además, el State Management debe garantizar, como condición previa para RegisterWakeUpHandler, que el objeto de función pasado sea válido y permanezca en la memoria hasta su revocación mediante UnregisterWakeUpHandler ([SWS_SM_71003], [SWS_SM_71005]).

Esta guía se basa exclusivamente en las especificaciones de AUTOSAR Adaptive Platform Release R25-11.

Tratamiento de errores y seguridad frente a excepciones

La interfaz está especificada como segura frente a excepciones (exception safe) y anotada con noexcept [SWS_SM_71003]. Por tanto, los invocadores no necesitan capturar excepciones de C++. Para esta API no se definen códigos de error específicos, valores de retorno para indicación de errores ni notificaciones a gestores de diagnóstico o de errores [SWS_SM_71003].

Interpretación: Es conveniente que el registro tenga lugar de manera única durante la fase secuencial de inicialización del envoltorio del OS, antes de que ocurran eventos de reactivación.
