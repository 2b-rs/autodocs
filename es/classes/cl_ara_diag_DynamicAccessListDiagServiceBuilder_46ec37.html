Permite la construcción paso a paso y la finalización de listas dinámicas de permisos de acceso para servicios de diagnóstico.

La clase sirve para la creación paso a paso de listas dinámicas de permisos de acceso para servicios de diagnóstico mediante una Fluent API encadenable ([SWS_DM_01166]). Las aplicaciones añaden bytes exactos, rangos de valores así como comodines para definir de forma flexible patrones de acceso para el Diagnostic Server ([SWS_DM_01175], [SWS_DM_01220]). Antes de destruir el objeto move-only no seguro para hilos, debe invocarse obligatoriamente el método Build() para concluir la configuración ([SWS_DM_01181]).

Contexto

La clase ara::diag::DynamicAccessListDiagServiceBuilder sirve a las aplicaciones de la AUTOSAR Adaptive Platform para la construcción paso a paso de listas dinámicas de permisos de acceso (DynamicAccessList) para servicios de diagnóstico ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15.1 «Class: DynamicAccessListDiagServiceBuilder»). A través de estas listas, una aplicación controla qué solicitudes de diagnóstico (por ejemplo, servicios UDS específicos con DID o subfunciones concretas) se autorizan dinámicamente en tiempo de ejecución (AUTOSAR_AP_SWS_Diagnostics §8.2 «Adding wildcards to a DynamicAccessList»).

Los interlocutores centrales son la propia aplicación, los métodos de fábrica de la clase ara::diag::DiagnosticServiceDynamicAccessList ([SWS_DM_01164], [SWS_DM_01165]), así como la instancia de Diagnostic Server, la cual evalúa los patrones de bits y bytes recopilados al verificar los derechos de servicio frente a solicitudes entrantes ([SWS_DM_01220], [SWS_DM_01221]). Para representar las estructuras de patrones, la clase proporciona los alias de tipo Byte para octetos individuales (std::uint8_t) y ByteString para secuencias de bytes (ara::core::Span<Byte>) ([SWS_DM_01167], [SWS_DM_01168], AUTOSAR_AP_SWS_Diagnostics §8.15.1.1 «Public Member Types»).

Ciclo de vida

Un objeto builder se instancia típicamente mediante DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) o directamente mediante el constructor, el cual recibe un valor inicial así como una referencia al búfer de serialización content (ara::core::Vector<std::uint8_t>&) ([SWS_DM_01169]). Interpretación: es probable que el parámetro content sirva como memoria que se llena de forma continua para la representación serializada que se entrega al Diagnostic Server tras la conclusión.

En lo que respecta a la propiedad y la copiabilidad, la clase impone una estricta semántica de solo movimiento (move-only) con asignación restringida: el constructor de copia ([SWS_DM_01171]) y el operador de asignación por copia ([SWS_DM_01172]) están eliminados (=delete). Asimismo, el operador de asignación por movimiento está eliminado ([SWS_DM_01173]). Únicamente el constructor de movimiento está implementado ([SWS_DM_01170]), de modo que las instancias pueden moverse si es necesario, pero no duplicarse ni reasignarse de forma incontrolada.

El ciclo de vida está sujeto a una poscondición obligatoria: antes de invocar el destructor ([SWS_DM_01174]), debe invocarse el método Build() para concluir la creación de la lista ([SWS_DM_01181]). Mientras que los constructores están especificados como seguros para hilos ([SWS_DM_01169], [SWS_DM_01170]), todos los métodos para la ampliación de patrones así como el destructor no son seguros para hilos (not thread-safe, [SWS_DM_01174]).

Diagrama de estados: fases del ciclo de vida del builder desde la creación pasando por la construcción paso a paso del patrón hasta la finalización obligatoria antes de la destrucción. Fuentes: [SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181], [SWS_DM_01174].

Ruta de uso

La configuración de un patrón se realiza a través de una Fluent API, en la que las invocaciones de métodos devuelven una referencia a la misma instancia del builder ([SWS_DM_01175]):

  1. Inicialización: la aplicación crea el builder, por ejemplo mediante DiagnosticServiceDynamicAccessList::MakeServiceBuilder con un byte o una cadena de bytes introductoria ([SWS_DM_01164], [SWS_DM_01165]).
  2. Ampliación del patrón: mediante métodos Add() sobrecargados se añaden bytes individuales ([SWS_DM_01175]), secuencias de bytes ([SWS_DM_01176]) o rangos cerrados de valores ByteRange ([SWS_DM_01177]). Estos valores se comprueban en cuanto a coincidencia exacta durante la evaluación posterior.
  3. Insertar comodines: con Any(numberOfBytesToIgnore) la aplicación define marcadores de posición ([SWS_DM_01178]). El Diagnostic Server ignora la cantidad especificada de bytes durante la comparación de patrones, lo que permite implementar filtros flexibles como 22F1XX para rangos de DID ([SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §8.2 «Adding wildcards to a DynamicAccessList»).
  4. Conclusión del patrón y finalización: mediante EndsWith() se puede especificar un byte de terminación o un rango ([SWS_DM_01179], [SWS_DM_01180], [SWS_DM_01221]). Por último, la invocación de Build() concluye definitivamente el proceso de creación ([SWS_DM_01181]).

Diagrama de secuencia: secuencia típica de interacción entre la aplicación, el método de fábrica y el builder durante la definición del patrón. Fuentes: [SWS_DM_01165], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Escenarios de error

Todos los métodos de la clase están declarados con noexcept y especificados como seguros frente a excepciones (exception safe) ([SWS_DM_01169], [SWS_DM_01174], [SWS_DM_01181]). A nivel de la API no se lleva a cabo tratamiento de errores mediante excepciones de C++ o valores de retorno de error.

La precondición contractual fundamental reside en la invocación de Build() antes de la destrucción del builder ([SWS_DM_01181]). Interpretación: si el objeto builder se destruye sin que se haya ejecutado Build(), es probable que la configuración de patrón iniciada se descarte o deje un estado no válido en la lista de acceso subyacente.

Además, las funciones de manipulación no son seguras para hilos ([SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181]). Un acceso paralelo desprotegido a la misma instancia del builder desde varios hilos provoca estados de memoria indefinidos (condiciones de carrera / data races).

El método está especificado como no seguro para hilos (not thread-safe) [SWS_DM_01175].
