Contexto

La clase ara::diag::DynamicAccessListDiagServiceBuilder ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15 «Class: DynamicAccessListDiagServiceBuilder») sirve para que las aplicaciones definan y serialicen paso a paso una lista de acceso dinámico (DynamicAccessList) para servicios de diagnóstico. Constituye la herramienta central para estructurar patrones de acceso para solicitudes de diagnóstico de forma granular según bytes individuales, secuencias de bytes, rangos de valores o comodines.

En el sistema global, el builder interactúa con tres entidades principales:

  • Aplicación (Application): configura los patrones de filtrado deseados para las solicitudes de diagnóstico entrantes a través de la Fluent API del builder.
  • DiagnosticServiceDynamicAccessList: proporciona el punto de entrada mediante métodos de fábrica como MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) y aloja la lista de acceso definida.
  • Diagnostic Server Instance: la instancia del servidor de diagnóstico evalúa en tiempo de ejecución los patrones de bytes, comodines y patrones finales transmitidos durante el pattern matching para los derechos de acceso a servicios de diagnóstico ([SWS_DM_01220], [SWS_DM_01221]).

Diagrama de contexto: interacción entre la aplicación, la lista de acceso, el builder y el servidor de diagnóstico. Fuentes: [SWS_DM_01164], [SWS_DM_01166], [SWS_DM_01220].

Ciclo de vida

La creación de una instancia del builder se realiza bien directamente a través del constructor de plantilla especificando un valor inicial y una referencia a un búfer de serialización (ara::core::Vector<std::uint8_t>& content) ([SWS_DM_01169]), o bien mediante funciones auxiliares como MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]).

En cuanto a la propiedad y la semántica de copia, la clase impone un uso estrictamente lineal:

  • Tanto el constructor de copia ([SWS_DM_01171]) como el operador de asignación por copia ([SWS_DM_01172]) están declarados como eliminados (=delete).
  • El operador de asignación por movimiento también está eliminado ([SWS_DM_01173]). Una transferencia solo puede realizarse a través del constructor de movimiento ([SWS_DM_01170]).

Para la destrucción a través del destructor ([SWS_DM_01174]), rige un invariante fijo: antes de destruir el objeto, debe llamarse obligatoriamente al método Build() ([SWS_DM_01181]) para finalizar la creación de la lista.

En cuanto a la concurrencia, el constructor de plantilla y el constructor de movimiento están especificados como seguros para subprocesos (thread-safe) ([SWS_DM_01169], [SWS_DM_01170]). Por el contrario, todas las operaciones de conformación de patrones (Add, Any, EndsWith, Build) y el destructor son explícitamente no seguros para subprocesos (not thread-safe) ([SWS_DM_01174], [SWS_DM_01175], [SWS_DM_01181]) y no deben invocarse de forma concurrente sobre la misma instancia.

Ruta de uso

El proceso típico para configurar un patrón de acceso de diagnóstico se divide en tres pasos:

  1. Inicialización: solicitud de un builder mediante DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) con el identificador del servicio o directamente a través del constructor ([SWS_DM_01169]).
  2. Construcción del patrón mediante Fluent API:
    • Adición de bytes individuales (Byte / std::uint8_t, [SWS_DM_01167]) mediante Add(Byte) ([SWS_DM_01175]), secuencias de bytes mediante Add(ByteString) ([SWS_DM_01168], [SWS_DM_01176]) o rangos de valores mediante Add(ByteRange) ([SWS_DM_01177]).
    • Inserción de comodines mediante Any(numberOfBytesToIgnore) ([SWS_DM_01178], [SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §7.1.3 «Adding wildcards to a DynamicAccessList»). Con ello se definen bytes en el patrón que se ignoran en la comparación posterior (p. ej., 22F1XX para prefijos de DID).
    • Definición opcional de un patrón final mediante EndsWith(Byte) ([SWS_DM_01179]) o EndsWith(ByteRange) ([SWS_DM_01180], [SWS_DM_01221]).
  3. Finalización: llamada a Build() ([SWS_DM_01181]), con lo cual se completa la lista.

Diagrama de secuencia: configuración típica y finalización de un patrón a través de la Fluent API. Fuentes: [SWS_DM_01164], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Escenarios de error

Toda la interfaz de ara::diag::DynamicAccessListDiagServiceBuilder opera sin excepción con noexcept y está especificada como segura ante excepciones (exception safe) ([SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181]). No se lanzan excepciones de C++ ni se devuelven estados de error mediante ara::core::Result.

Por lo tanto, las situaciones de error resultan principalmente de infracciones de las condiciones previas:

  • Omisión de la llamada de finalización: si se destruye el builder sin haber llamado antes a Build(), esto infringe la condición previa de [SWS_DM_01181]. Interpretación: en este caso, es probable que el patrón de acceso quede incompleto y el servidor de diagnóstico no lo tenga en cuenta como criterio válido.
  • Concurrencia desprotegida: dado que todos los métodos para añadir elementos, así como Build(), están clasificados como not thread-safe, una llamada simultánea desde múltiples subprocesos provoca la corrupción de datos en el búfer referenciado.

Esta guía se basa en los requisitos de la especificación AUTOSAR Adaptive R25-11 para el módulo Diagnostics.
