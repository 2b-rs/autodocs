Contexto

La estructura ara::diag::DiagnosticSovdContentData forma parte de AUTOSAR Adaptive Platform en el módulo diag y se proporciona a través del archivo de cabecera ara/diag/diagnostic_sovd_content_data.h ([SWS_DM_02385], AUTOSAR_AP_SWS_Diagnostics §8.59.1 «Struct: DiagnosticSovdContentData»). Sirve como contenedor de transferencia de datos estandarizado para contenidos del protocolo ASAM Service-Oriented Vehicle Diagnostics (SOVD) dentro del Diagnostic Management (DM).

Funcionalmente, la estructura de datos encapsula una colección de elementos de contenido SOVD mediante el miembro público elements de tipo ara::core::Vector<DiagnosticSovdContentElementData> ([SWS_DM_02386], AUTOSAR_AP_SWS_Diagnostics §8.59.1.1.1 «elements»). Esta estructura actúa en la interfaz entre tres actores principales: el cliente SOVD externo, el daemon Diagnostic Management interno del vehículo (DM) y los proveedores de servicios de diagnóstico concretos de la aplicación Adaptive (por ejemplo, instancias de ara::diag::GenericDiagnosticSovdOperation o SovdOperationExecution) ([SWS_DM_02174], [SWS_DM_02180], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»).

Diagrama de contexto: integración de DiagnosticSovdContentData en el intercambio de datos entre el cliente SOVD externo, Diagnostic Management y la lógica de la aplicación. Fuentes: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02385].

Ciclo de vida

Como estructura de datos pura (struct), ara::diag::DiagnosticSovdContentData está sujeta a la semántica de valor habitual de C++ ([SWS_DM_02385]). No posee un gestor de ciclo de vida ni un almacenamiento de estado independiente, sino que se instancia y se transporta según sea necesario.

Por lo general, la aplicación de diagnóstico en ejecución crea una instancia cuando ha finalizado una operación SOVD o se proporcionan datos para una solicitud de lectura (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»). La aplicación llena el vector elements con las entradas DiagnosticSovdContentElementData correspondientes ([SWS_DM_02386]). A continuación, la estructura se pasa al DM como valor de retorno o dentro de contenedores de respuesta (p. ej., retornos StartSynchronousExecution o GetStatusResponse.Parameters) ([SWS_DM_02176], [SWS_DM_02181]).

Diagnostic Management asume la propiedad o lee los valores contenidos para rellenar el atributo parameters del cuerpo de respuesta SOVD saliente de acuerdo con ASAM SOVD ([SWS_DM_02176], [SWS_DM_02181]). Una vez finalizada la serialización o la generación de la respuesta, la instancia se destruye según las reglas normales de ámbito de C++. Dado que se trata de una estructura de datos, no existe sincronización interna de subprocesos; el acceso entre distintos subprocesos requiere semántica de movimiento o coordinación externa por parte del llamador.

Ruta de uso

La ruta de uso principal de ara::diag::DiagnosticSovdContentData radica en la ejecución y la retroalimentación de estado de las operaciones SOVD, así como en consultas de lectura SOVD dedicadas:

  1. Recepción de la solicitud: un cliente externo envía el método SOVD «Start Execution of an Operation» al Diagnostic Server ([SWS_DM_01396], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»).
  2. Llamada a la operación de la aplicación: tras una validación correcta, Diagnostic Management reenvía la llamada a la aplicación a través de ara::diag::GenericDiagnosticSovdOperation::StartExecution ([SWS_DM_02174]).
  3. Llenado de la estructura de datos: la lógica de la aplicación procesa la operación y genera el resultado en forma de una instancia de DiagnosticSovdContentData, cuyo vector elements recibe los datos de salida ([SWS_DM_02386]).
  4. Preparación de la respuesta por parte del DM: el DM recibe el resultado, deduce a partir de él los valores para el atributo SOVD parameters y envía el cuerpo de respuesta SOVD conforme al cliente ([SWS_DM_02176]).

De forma análoga se realiza el uso en consultas de estado («Read the Status of an operation»): en caso de una llamada correcta a SovdOperationExecution::GetStatus, los valores para parameters en el cuerpo de respuesta se deducen a partir de la DiagnosticSovdContentData proporcionada en GetStatusResponse.Parameters ([SWS_DM_02180], [SWS_DM_02181], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operation Read the Status of an operation»). Además, la estructura se devuelve como resultado de interfaces asíncronas como Read(...) a través de ara::core::Future<DiagnosticSovdContentData> (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»).

Diagrama de secuencias: interacción durante una ejecución síncrona de una operación SOVD y devolución de los parámetros a través de DiagnosticSovdContentData. Fuentes: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176] [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02386].

Escenarios de error

Al utilizar y transmitir ara::diag::DiagnosticSovdContentData, son relevantes varias condiciones previas y modos de fallo:

  • Validación de seguridad fallida: tanto al iniciar una operación ([SWS_DM_02174]) como al consultar el estado de la operación ([SWS_DM_02180]), la validación correcta del proximity_challenge es una condición previa obligatoria. Si esta comprobación falla, el proceso se rechaza; las funciones de la aplicación no se invocan y no se produce la provisión ni la evaluación de DiagnosticSovdContentData.
  • Fallo de la consulta de estado: si SovdOperationExecution::GetStatus no se puede ejecutar correctamente, se omite el ensamblaje del cuerpo de respuesta SOVD regular y no se realiza la derivación de parameters a partir de DiagnosticSovdContentData ([SWS_DM_02181]).
  • Cancelación asíncrona en operaciones de lectura: si se solicita DiagnosticSovdContentData en el marco de Read(...), el sistema pasa un ara::diag::CancellationHandler (AUTOSAR_AP_SWS_Diagnostics §8.70 «virtual ara::core::Future<DiagnosticSovdContentData> Read»). Si este solicita una cancelación, la creación y el llenado de DiagnosticSovdContentData pueden o deben finalizarse de forma anticipada.

Esta guía se basa en la especificación AUTOSAR Adaptive R25-11. Todos los requisitos normativos proceden del módulo diag.
