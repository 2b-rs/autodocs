Contexto

La clase ara::diag::Authentication proporciona la interfaz para que las aplicaciones adaptativas actúen como gestores de servicio y procesen la autenticación del servicio UDS (servicio UDS 0x29 Authentication) AUTOSAR_AP_SWS_Diagnostics §4.1 «Limitations of sub-functions». La aplicación implementa los métodos puramente virtuales de esta clase para llevar a cabo comprobaciones criptográficas entrantes, mientras que el Diagnostic Manager (DM) controla el reenvío de las solicitudes de diagnóstico [SWS_DM_01130].

La interacción abarca tres partes principales: el comprobador de diagnóstico externo, el Diagnostic Manager como intermediario de los mensajes UDS y la aplicación adaptativa, que asume la comprobación propiamente dicha de certificados y propiedad a través de una subclase concreta de ara::diag::Authentication [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].

Diagrama de contexto: Integración de ara::diag::Authentication entre el comprobador de diagnóstico, el Diagnostic Manager y la aplicación. Fuentes: [SWS_DM_01130], [SWS_DM_01126], AUTOSAR_AP_SWS_Diagnostics §4.1

Ciclo de vida

La instanciación se realiza de forma explícita mediante la especificación de un ara::core::InstanceSpecifier y un ConcurrencyType [SWS_DM_01124]. El InstanceSpecifier hace referencia a un PortPrototype modelado de un DiagnosticAuthenticationInterface. A través del parámetro concurrencyType, la aplicación determina si las llamadas se procesan de forma segura para subprocesos (kConcurrent) o no segura para subprocesos (kNotConcurrent) [SWS_DM_01124]. Las instancias de ara::diag::Authentication están estrictamente vinculadas a su identidad: los constructores de copia y de movimiento, así como los operadores de asignación, están eliminados (=delete) [SWS_DM_01609], [SWS_DM_01610], [SWS_DM_01607], [SWS_DM_01608].

Tras la creación, el manejador se encuentra inicialmente en estado pasivo. Solo mediante la llamada a Offer() se autoriza al Diagnostic Manager a reenviar las solicitudes de diagnóstico entrantes a la instancia [SWS_DM_01130]. El método StopOffer() vuelve a desactivar este reenvío [SWS_DM_01131]. Al destruir la instancia mediante el destructor virtual ~Authentication(), finaliza el ciclo de vida; este destructor está especificado como not thread-safe [SWS_DM_01125].

Ruta de uso

El flujo típico de una autenticación de diagnóstico sigue una secuencia fija de preparación, verificación de certificados y prueba de posesión:

  1. Puesta a disposición: La aplicación instancia su clase derivada de Authentication y notifica la disponibilidad de recepción a través de Offer() al Diagnostic Manager [SWS_DM_01124], [SWS_DM_01130].
  2. Verificación de certificados: Al recibir una solicitud de autenticación, el Diagnostic Manager llama, según la configuración de diagnóstico, a VerifyCertificateUnidirectional() [SWS_DM_01126] o a VerifyCertificateBidirectional() [SWS_DM_01127]. La aplicación comprueba el certificado de cliente transferido y el challenge del tester. Como respuesta, devuelve de forma asíncrona a través de un ara::core::Future un challenge de servidor generado, así como el Ephemeral Public Key (en caso de autenticación bidireccional, adicionalmente el certificado del servidor y la propia prueba de posesión) [SWS_DM_01126], [SWS_DM_01127].
  3. Prueba de posesión (Proof of Ownership): En el paso siguiente, el DM llama al método VerifyOwnership() [SWS_DM_01128]. La aplicación comprueba la prueba de posesión (clientPOWN) transmitida por el tester frente a la clave pública del certificado recibido previamente y el challenge del servidor generado. En caso de éxito, devuelve la información de la clave de sesión en el Future [SWS_DM_01128].
  4. Cancelación del registro: Antes del apagado, la aplicación retira la oferta mediante StopOffer() [SWS_DM_01131].

Los callbacks se pueden invocar de forma reentrante ante solicitudes de diferentes clientes [SWS_DM_01126], [SWS_DM_01127]. A través del CancellationHandler transferido, la aplicación puede comprobar si se ha cancelado el procesamiento o registrar un notificador para cancelaciones [SWS_DM_01126], [SWS_DM_01128].

Diagrama de secuencia: Flujo típico de la autenticación a través del Diagnostic Manager. Fuentes: [SWS_DM_01130], [SWS_DM_01126], [SWS_DM_01128], [SWS_DM_01131]

Escenarios de error

Al utilizar ara::diag::Authentication, deben tenerse en cuenta las siguientes condiciones de error y comprobaciones previas:

  • Errores de construcción (Violations): Si falla el mapeo del InstanceSpecifier (p. ej., InstanceSpecifierMappingIntegrityViolation o PortInterfaceMappingViolation), el proceso no está configurado correctamente (ProcessMappingViolation) o se vuelve a especificar un identificador ya utilizado (InstanceSpecifierAlreadyInUseViolation), la plataforma notifica la infracción correspondiente [SWS_DM_01124].
  • Oferta múltiple: Si se llama a Offer() mientras el servicio ya se está ofreciendo, el método devuelve un error con el código de error DiagOfferErrc::kAlreadyOffered [SWS_DM_01130].
  • Errores de verificación y de protocolo: Si falla la comprobación del certificado o la verificación de la prueba de posesión (p. ej., firma no válida o certificado caducado), la aplicación devuelve en el Future un Negative Response Code (NRC) de ISO 14229-1 correspondiente utilizando DiagUdsNrcErrc [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].
  • Cancelación prematura: Si la conversación de diagnóstico se interrumpe por parte del tester o del DM, cancellationHandler.IsCanceled() notifica el valor TRUE; la aplicación debe cancelar las operaciones criptográficas para liberar recursos de cómputo [SWS_DM_01126].

Esta guía se basa en los requisitos de la especificación AUTOSAR Adaptive R25-11.
