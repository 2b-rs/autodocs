Contexto

La clase [SWS_DM_00529] ara::diag::DiagUdsNrcErrorDomain representa el dominio de errores estandarizado para errores de diagnóstico que proceden de diferentes clases e interfaces de diagnóstico de AUTOSAR Adaptive Platform. Según [SWS_DM_00529], deriva de la clase base ara::core::ErrorDomain y actúa como enlace primario entre las rutinas de diagnóstico del lado de la aplicación y la gestión de diagnóstico (Diagnostic Management, DM).

En el sistema global, el dominio de errores actúa en las interfaces de tres componentes centrales:

  • Diagnostic Server (DM): Instancia que procesa las solicitudes de diagnóstico del comprobador de diagnóstico del vehículo, verifica las condiciones del entorno y genera respuestas UDS conformes a la norma.
  • Aplicación de diagnóstico externa: Lógica de aplicación o procesador de diagnóstico externo que implementa servicios de diagnóstico específicos del vehículo y notifica resultados o errores a través de interfaces ara::diag.
  • Cliente de diagnóstico (Tester): Dispositivo de prueba externo que envía comandos de diagnóstico a la unidad de control y espera respuestas negativas estandarizadas (Negative Response Codes, NRC) si se producen errores.

Si una aplicación de diagnóstico devuelve, a través de una interfaz ara::diag, un resultado con un error del dominio ara::diag::DiagUdsNrcErrorDomain, el Diagnostic Server procesa este error de manera orientada: deriva el UDS Negative Response Code a partir del código de error notificado [SWS_DM_02059] y transmite una respuesta negativa con este código al cliente de diagnóstico [SWS_DM_02060]. Además, el dominio interactúa con la verificación de condiciones ambientales configurables: si la recuperación de un elemento de datos falla debido a un error de este dominio, el servidor clasifica la condición como no cumplida y emite un mensaje de registro y traza [SWS_DM_00970].

Diagrama de contexto: integración del dominio de errores en la interacción entre el tester, el Diagnostic Server y la aplicación. Fuentes: [SWS_DM_02059], [SWS_DM_02060], AUTOSAR_AP_SWS_Diagnostics p. 144

Ciclo de vida

El ciclo de vida de ara::diag::DiagUdsNrcErrorDomain sigue las especificaciones para dominios de errores sin estado de la plataforma:

  • Creación e inicialización: La clase proporciona un constructor predeterminado sin parámetros que está definido como constexpr y noexcept [SWS_DM_00532]. Interpretación: Las instancias de DiagUdsNrcErrorDomain se crean como constantes de larga duración u objetos singleton en tiempo de compilación o de carga, a fin de estar disponibles durante todo el tiempo de ejecución del proceso.
  • Propiedad: Por lo general, las aplicaciones no crean instancias dinámicas en el montón, sino que hacen referencia al dominio a través de referencias constantes al tipificar valores ara::core::ErrorCode.
  • Estados y transiciones: El dominio no posee estados internos variables y no requiere transiciones de estado. Las consultas de observación como Name() [SWS_DM_00533] o Message() [SWS_DM_00534] se comportan sin estado y de forma determinista.
  • Concurrencia: Todas las funciones miembro —el constructor [SWS_DM_00532], Name() [SWS_DM_00533], Message() [SWS_DM_00534] y ThrowAsException() [SWS_DM_00535]— están especificadas explícitamente como seguras para subprocesos. Se pueden invocar en paralelo desde diferentes contextos de ejecución sin bloqueos adicionales.

Ruta de uso

El flujo regular durante la señalización de errores de diagnóstico se divide en los siguientes pasos:

  1. Solicitud de servicio: El cliente de diagnóstico envía una solicitud de servicio UDS al Diagnostic Server.
  2. Invocación de la aplicación de diagnóstico: El Diagnostic Server delega el procesamiento a través de una interfaz ara::diag tipificada al procesador de diagnóstico externo responsable.
  3. Retorno de error: Si la aplicación de diagnóstico detecta una condición no válida, genera un código de error del tipo ara::diag::DiagUdsNrcErrorDomain::Errc [SWS_DM_00530] y lo devuelve dentro de un ara::core::Result.
  4. Derivación de NRC: Si el Diagnostic Server detecta un error del dominio ara::diag::DiagUdsNrcErrorDomain, deriva el UDS Negative Response Code a partir del valor DiagUdsNrcErrc [SWS_DM_02059]. Esto ocurre normalmente mediante una conversión de tipos (static_cast) a un valor de 1 byte en el rango permitido de 0x01 a 0xFE [SWS_DM_02059].
  5. Respuesta de protocolo: El Diagnostic Server genera una respuesta UDS negativa con el código de error determinado y la envía al cliente [SWS_DM_02060].
  6. Resolución de texto de error: Para registros de diagnóstico o mensajes del sistema, la descripción del error se puede consultar a través de Message(), la cual siempre proporciona un puntero de texto válido [SWS_DM_00534].

Diagrama de secuencia: propagación de errores y derivación de NRC de UDS en una operación de diagnóstico fallida. Fuentes: [SWS_DM_02059], [SWS_DM_02060]

Escenarios de error

Para el tratamiento controlado de estados de error, la clase proporciona tipos especializados y mecanismos de conversión:

  • Enumeración de códigos de error: El alias de tipo Errc hace referencia a la enumeración DiagUdsNrcErrc [SWS_DM_00530]. Interpretación: Los valores de enumeración reflejan los UDS Negative Response Codes normalizados. Los valores válidos para la derivación se sitúan en el rango de 0x01 a 0xFE [SWS_DM_02059].
  • Mapeo de excepciones: El alias Exception hace referencia a DiagUdsNrcException [SWS_DM_00531]. Mediante ThrowAsException() [SWS_DM_00535], un código de error se puede convertir en la excepción correspondiente y lanzarse. Si las excepciones de C++ están deshabilitadas en la cadena de herramientas, esta función no participa en la resolución de sobrecarga [SWS_DM_00535].
  • Error al recuperar el elemento de datos: Si la recuperación de un elemento de datos por parte de un procesador externo provoca un error del dominio ara::diag::DiagUdsNrcErrorDomain, la gestión de diagnóstico trata la parte de la fórmula correspondiente de la condición ambiental como no cumplida y desencadena un mensaje de registro y traza [SWS_DM_00970].
  • Comportamiento en solicitudes multi-DID: La presencia de ara::diag::DiagUdsNrcErrorDomain en el resultado señala un resultado parcial negativo del procesador externo. En solicitudes a través de múltiples DID, sin embargo, un error individual no conduce necesariamente a una respuesta negativa global, siempre que se admita al menos un DID en la sesión activa (AUTOSAR_AP_SWS_Diagnostics §7.3.x p. 160).

<p>La clase <a class="spec-record-ref" data-req="SWS_DM_00529" href="../spec/record.html?id=SWS_DM_00529">[SWS_DM_00529]</a> <code>ara::diag::DiagUdsNrcErrorDomain</code> representa el dominio de errores estandarizado para errores de diagnóstico que proceden de diferentes clases e interfaces de diagnóstico de AUTOSAR Adaptive Platform. Según <a class="spec-record-ref" data-req="SWS_DM_00529" href="../spec/record.html?id=SWS_DM_00529">[SWS_DM_00529]</a>, deriva de la clase base <code>ara::core::ErrorDomain</code> y actúa como enlace primario entre las rutinas de diagnóstico del lado de la aplicación y la gestión de diagnóstico (Diagnostic Management, DM).</p>
<p>En el sistema global, el dominio de errores actúa en las interfaces de tres componentes centrales:</p>
<ul>
<li><strong>Diagnostic Server (DM):</strong> Instancia que procesa las solicitudes de diagnóstico del comprobador de diagnóstico del vehículo, verifica las condiciones del entorno y genera respuestas UDS conformes a la norma.</li>
<li><strong>Aplicación de diagnóstico externa:</strong> Lógica de aplicación o procesador de diagnóstico externo que implementa servicios de diagnóstico específicos del vehículo y notifica resultados o errores a través de interfaces <code>ara::diag</code>.</li>
<li><strong>Cliente de diagnóstico (Tester):</strong> Dispositivo de prueba externo que envía comandos de diagnóstico a la unidad de control y espera respuestas negativas estandarizadas (Negative Response Codes, NRC) si se producen errores.</li>
</ul>
<p>Si una aplicación de diagnóstico devuelve, a través de una interfaz <code>ara::diag</code>, un resultado con un error del dominio <code>ara::diag::DiagUdsNrcErrorDomain</code>, el Diagnostic Server procesa este error de manera orientada: deriva el UDS Negative Response Code a partir del código de error notificado <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a> y transmite una respuesta negativa con este código al cliente de diagnóstico <a class="spec-record-ref" data-req="SWS_DM_02060" href="../spec/record.html?id=SWS_DM_02060">[SWS_DM_02060]</a>. Además, el dominio interactúa con la verificación de condiciones ambientales configurables: si la recuperación de un elemento de datos falla debido a un error de este dominio, el servidor clasifica la condición como no cumplida y emite un mensaje de registro y traza <a class="spec-record-ref" data-req="SWS_DM_00970" href="../spec/record.html?id=SWS_DM_00970">[SWS_DM_00970]</a>.</p>

<h4>Ciclo de vida</h4>
<p>El ciclo de vida de <code>ara::diag::DiagUdsNrcErrorDomain</code> sigue las especificaciones para dominios de errores sin estado de la plataforma:</p>
<ul>
<li><strong>Creación e inicialización:</strong> La clase proporciona un constructor predeterminado sin parámetros que está definido como <code>constexpr</code> y <code>noexcept</code> <a class="spec-record-ref" data-req="SWS_DM_00532" href="../spec/record.html?id=SWS_DM_00532">[SWS_DM_00532]</a>. Interpretación: Las instancias de <code>DiagUdsNrcErrorDomain</code> se crean como constantes de larga duración u objetos singleton en tiempo de compilación o de carga, a fin de estar disponibles durante todo el tiempo de ejecución del proceso.</li>
<li><strong>Propiedad:</strong> Por lo general, las aplicaciones no crean instancias dinámicas en el montón, sino que hacen referencia al dominio a través de referencias constantes al tipificar valores <code>ara::core::ErrorCode</code>.</li>
<li><strong>Estados y transiciones:</strong> El dominio no posee estados internos variables y no requiere transiciones de estado. Las consultas de observación como <code>Name()</code> <a class="spec-record-ref" data-req="SWS_DM_00533" href="../spec/record.html?id=SWS_DM_00533">[SWS_DM_00533]</a> o <code>Message()</code> <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a> se comportan sin estado y de forma determinista.</li>
<li><strong>Concurrencia:</strong> Todas las funciones miembro —el constructor <a class="spec-record-ref" data-req="SWS_DM_00532" href="../spec/record.html?id=SWS_DM_00532">[SWS_DM_00532]</a>, <code>Name()</code> <a class="spec-record-ref" data-req="SWS_DM_00533" href="../spec/record.html?id=SWS_DM_00533">[SWS_DM_00533]</a>, <code>Message()</code> <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a> y <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a>— están especificadas explícitamente como seguras para subprocesos. Se pueden invocar en paralelo desde diferentes contextos de ejecución sin bloqueos adicionales.</li>
</ul>

<h4>Ruta de uso</h4>
<p>El flujo regular durante la señalización de errores de diagnóstico se divide en los siguientes pasos:</p>
<ol>
<li><strong>Solicitud de servicio:</strong> El cliente de diagnóstico envía una solicitud de servicio UDS al Diagnostic Server.</li>
<li><strong>Invocación de la aplicación de diagnóstico:</strong> El Diagnostic Server delega el procesamiento a través de una interfaz <code>ara::diag</code> tipificada al procesador de diagnóstico externo responsable.</li>
<li><strong>Retorno de error:</strong> Si la aplicación de diagnóstico detecta una condición no válida, genera un código de error del tipo <code>ara::diag::DiagUdsNrcErrorDomain::Errc</code> <a class="spec-record-ref" data-req="SWS_DM_00530" href="../spec/record.html?id=SWS_DM_00530">[SWS_DM_00530]</a> y lo devuelve dentro de un <code>ara::core::Result</code>.</li>
<li><strong>Derivación de NRC:</strong> Si el Diagnostic Server detecta un error del dominio <code>ara::diag::DiagUdsNrcErrorDomain</code>, deriva el UDS Negative Response Code a partir del valor <code>DiagUdsNrcErrc</code> <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>. Esto ocurre normalmente mediante una conversión de tipos (<code>static_cast</code>) a un valor de 1 byte en el rango permitido de <code>0x01</code> a <code>0xFE</code> <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>.</li>
<li><strong>Respuesta de protocolo:</strong> El Diagnostic Server genera una respuesta UDS negativa con el código de error determinado y la envía al cliente <a class="spec-record-ref" data-req="SWS_DM_02060" href="../spec/record.html?id=SWS_DM_02060">[SWS_DM_02060]</a>.</li>
<li><strong>Resolución de texto de error:</strong> Para registros de diagnóstico o mensajes del sistema, la descripción del error se puede consultar a través de <code>Message()</code>, la cual siempre proporciona un puntero de texto válido <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a>.</li>
</ol>

<h4>Escenarios de error</h4>
<p>Para el tratamiento controlado de estados de error, la clase proporciona tipos especializados y mecanismos de conversión:</p>
<ul>
<li><strong>Enumeración de códigos de error:</strong> El alias de tipo <code>Errc</code> hace referencia a la enumeración <code>DiagUdsNrcErrc</code> <a class="spec-record-ref" data-req="SWS_DM_00530" href="../spec/record.html?id=SWS_DM_00530">[SWS_DM_00530]</a>. Interpretación: Los valores de enumeración reflejan los UDS Negative Response Codes normalizados. Los valores válidos para la derivación se sitúan en el rango de <code>0x01</code> a <code>0xFE</code> <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>.</li>
<li><strong>Mapeo de excepciones:</strong> El alias <code>Exception</code> hace referencia a <code>DiagUdsNrcException</code> <a class="spec-record-ref" data-req="SWS_DM_00531" href="../spec/record.html?id=SWS_DM_00531">[SWS_DM_00531]</a>. Mediante <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a>, un código de error se puede convertir en la excepción correspondiente y lanzarse. Si las excepciones de C++ están deshabilitadas en la cadena de herramientas, esta función no participa en la resolución de sobrecarga <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a>.</li>
<li><strong>Error al recuperar el elemento de datos:</strong> Si la recuperación de un elemento de datos por parte de un procesador externo provoca un error del dominio <code>ara::diag::DiagUdsNrcErrorDomain</code>, la gestión de diagnóstico trata la parte de la fórmula correspondiente de la condición ambiental como no cumplida y desencadena un mensaje de registro y traza <a class="spec-record-ref" data-req="SWS_DM_00970" href="../spec/record.html?id=SWS_DM_00970">[SWS_DM_00970]</a>.</li>
<li><strong>Comportamiento en solicitudes multi-DID:</strong> La presencia de <code>ara::diag::DiagUdsNrcErrorDomain</code> en el resultado señala un resultado parcial negativo del procesador externo. En solicitudes a través de múltiples DID, sin embargo, un error individual no conduce necesariamente a una respuesta negativa global, siempre que se admita al menos un DID en la sesión activa (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=160">AUTOSAR_AP_SWS_Diagnostics §7.3.x p. 160</a>).</li>
</ul>
