Contexto

La clase [SWS_DM_00529] ara::diag::DiagUdsNrcErrorDomain representa el dominio de errores estandarizado para errores de diagnóstico que proceden de diferentes clases e interfaces de diagnóstico de AUTOSAR Adaptive Platform. Según [SWS_DM_00529], deriva de la clase base ara::core::ErrorDomain y actúa como enlace primario entre las rutinas de diagnóstico del lado de la aplicación y la gestión de diagnóstico (Diagnostic Management, DM).

En el sistema global, el dominio de errores actúa en las interfaces de tres componentes centrales:

  • Diagnostic Server (DM): Instancia que procesa las solicitudes de diagnóstico del comprobador de diagnóstico del vehículo, verifica las condiciones del entorno y genera respuestas UDS conformes a la norma.
  • Aplicación de diagnóstico externa: Lógica de aplicación o procesador de diagnóstico externo que implementa servicios de diagnóstico específicos del vehículo y notifica resultados o errores a través de interfaces ara::diag.
  • Cliente de diagnóstico (Tester): Dispositivo de prueba externo que envía comandos de diagnóstico a la unidad de control y espera respuestas negativas estandarizadas (Negative Response Codes, NRC) si se producen errores.

Si una aplicación de diagnóstico devuelve, a través de una interfaz ara::diag, un resultado con un error del dominio ara::diag::DiagUdsNrcErrorDomain, el Diagnostic Server procesa este error de manera orientada: deriva el UDS Negative Response Code a partir del código de error notificado [SWS_DM_02059] y transmite una respuesta negativa con este código al cliente de diagnóstico [SWS_DM_02060]. Además, el dominio interactúa con la verificación de condiciones ambientales configurables: si la recuperación de un elemento de datos falla debido a un error de este dominio, el servidor clasifica la condición como no cumplida y emite un mensaje de registro y traza [SWS_DM_00970].

Diagrama de contexto: integración del dominio de errores en la interacción entre el tester, el Diagnostic Server y la aplicación. Fuentes: [SWS_DM_02059], [SWS_DM_02060], AUTOSAR_AP_SWS_Diagnostics p. 144

Ciclo de vida

El ciclo de vida de ara::diag::DiagUdsNrcErrorDomain sigue las especificaciones para dominios de errores sin estado de la plataforma:

  • Creación e inicialización: La clase proporciona un constructor predeterminado sin parámetros que está definido como constexpr y noexcept [SWS_DM_00532]. Interpretación: Las instancias de DiagUdsNrcErrorDomain se crean como constantes de larga duración u objetos singleton en tiempo de compilación o de carga, a fin de estar disponibles durante todo el tiempo de ejecución del proceso.
  • Propiedad: Por lo general, las aplicaciones no crean instancias dinámicas en el montón, sino que hacen referencia al dominio a través de referencias constantes al tipificar valores ara::core::ErrorCode.
  • Estados y transiciones: El dominio no posee estados internos variables y no requiere transiciones de estado. Las consultas de observación como Name() [SWS_DM_00533] o Message() [SWS_DM_00534] se comportan sin estado y de forma determinista.
  • Concurrencia: Todas las funciones miembro —el constructor [SWS_DM_00532], Name() [SWS_DM_00533], Message() [SWS_DM_00534] y ThrowAsException() [SWS_DM_00535]— están especificadas explícitamente como seguras para subprocesos. Se pueden invocar en paralelo desde diferentes contextos de ejecución sin bloqueos adicionales.

Ruta de uso

El flujo regular durante la señalización de errores de diagnóstico se divide en los siguientes pasos:

  1. Solicitud de servicio: El cliente de diagnóstico envía una solicitud de servicio UDS al Diagnostic Server.
  2. Invocación de la aplicación de diagnóstico: El Diagnostic Server delega el procesamiento a través de una interfaz ara::diag tipificada al procesador de diagnóstico externo responsable.
  3. Retorno de error: Si la aplicación de diagnóstico detecta una condición no válida, genera un código de error del tipo ara::diag::DiagUdsNrcErrorDomain::Errc [SWS_DM_00530] y lo devuelve dentro de un ara::core::Result.
  4. Derivación de NRC: Si el Diagnostic Server detecta un error del dominio ara::diag::DiagUdsNrcErrorDomain, deriva el UDS Negative Response Code a partir del valor DiagUdsNrcErrc [SWS_DM_02059]. Esto ocurre normalmente mediante una conversión de tipos (static_cast) a un valor de 1 byte en el rango permitido de 0x01 a 0xFE [SWS_DM_02059].
  5. Respuesta de protocolo: El Diagnostic Server genera una respuesta UDS negativa con el código de error determinado y la envía al cliente [SWS_DM_02060].
  6. Resolución de texto de error: Para registros de diagnóstico o mensajes del sistema, la descripción del error se puede consultar a través de Message(), la cual siempre proporciona un puntero de texto válido [SWS_DM_00534].

Diagrama de secuencia: propagación de errores y derivación de NRC de UDS en una operación de diagnóstico fallida. Fuentes: [SWS_DM_02059], [SWS_DM_02060]

Escenarios de error

Para el tratamiento controlado de estados de error, la clase proporciona tipos especializados y mecanismos de conversión:

  • Enumeración de códigos de error: El alias de tipo Errc hace referencia a la enumeración DiagUdsNrcErrc [SWS_DM_00530]. Interpretación: Los valores de enumeración reflejan los UDS Negative Response Codes normalizados. Los valores válidos para la derivación se sitúan en el rango de 0x01 a 0xFE [SWS_DM_02059].
  • Mapeo de excepciones: El alias Exception hace referencia a DiagUdsNrcException [SWS_DM_00531]. Mediante ThrowAsException() [SWS_DM_00535], un código de error se puede convertir en la excepción correspondiente y lanzarse. Si las excepciones de C++ están deshabilitadas en la cadena de herramientas, esta función no participa en la resolución de sobrecarga [SWS_DM_00535].
  • Error al recuperar el elemento de datos: Si la recuperación de un elemento de datos por parte de un procesador externo provoca un error del dominio ara::diag::DiagUdsNrcErrorDomain, la gestión de diagnóstico trata la parte de la fórmula correspondiente de la condición ambiental como no cumplida y desencadena un mensaje de registro y traza [SWS_DM_00970].
  • Comportamiento en solicitudes multi-DID: La presencia de ara::diag::DiagUdsNrcErrorDomain en el resultado señala un resultado parcial negativo del procesador externo. En solicitudes a través de múltiples DID, sin embargo, un error individual no conduce necesariamente a una respuesta negativa global, siempre que se admita al menos un DID en la sesión activa (AUTOSAR_AP_SWS_Diagnostics §7.3.x p. 160).
