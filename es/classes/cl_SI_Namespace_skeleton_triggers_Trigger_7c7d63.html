Contexto

La clase C++ <SI-Namespace>::skeleton::triggers::<Trigger> constituye la representación en el lado del servidor de un trigger dentro del módulo de comunicación com de AUTOSAR Adaptive Platform. De acuerdo con la arquitectura del modelo, en el skeleton de servicio generado existe exactamente una instancia correspondiente de esta clase para cada trigger definido en la ServiceInterface con el rol trigger. A diferencia de los eventos clásicos, un trigger sirve exclusivamente para notificar a las aplicaciones suscriptoras sobre la ocurrencia de un evento o la solicitud de ejecución de una acción, sin que se transmitan datos útiles adicionales (EXP ARAComAPI p. 10).

Como interlocutores principales actúan la aplicación de servicio proveedora (implementación del skeleton), el entorno de ejecución de ara::com y las aplicaciones cliente suscriptoras en el lado del proxy. La aplicación proveedora utiliza la instancia del trigger para enviar señales a todos los suscriptores actualmente registrados ([SWS_CM_00721]). En este proceso, el middleware se encarga del reenvío a través de los protocolos de comunicación correspondientes, como por ejemplo SOME/IP (SWS CommunicationManagement p. 95).

Ciclo de vida

La declaración de la clase trigger se realiza a través de la cabecera <SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h. Es de suponer que las instancias de la clase trigger se crean como elementos miembro del respectivo skeleton de servicio y comparten, por tanto, el tiempo de vida del objeto de servicio de nivel superior.

El ciclo de vida de la instancia del trigger está determinado en gran medida por el estado de suscripción de los consumidores. La aplicación proveedora puede consultar el estado actual de la suscripción mediante [SWS_CM_01109] (GetSubscriptionState()). Para recibir notificaciones activas sobre cambios de estado, se puede registrar un manejador de notificaciones ([SWS_CM_01110]). Para escenarios con requisitos específicos de concurrencia o asignación de hilos, la sobrecarga [SWS_CM_01111] ofrece la posibilidad de pasar un ejecutor personalizado (ExecutorT) en cuyo contexto se invoca el manejador. Si ya no se requiere la supervisión del estado del suscriptor, se puede cancelar el registro del manejador a través de [SWS_CM_01112] (UnsetSubscriptionStateChangeHandler()).

En lo referente a la seguridad ante excepciones y fallos, todas las funciones miembro de la clase trigger están declaradas con el especificador noexcept y definidas como seguras frente a excepciones (exception safe) ([SWS_CM_00721], [SWS_CM_01109], [SWS_CM_01110], [SWS_CM_01111], [SWS_CM_01112]).

Ruta de uso

Un flujo típico para el uso de una instancia de trigger en el lado del servidor comprende los siguientes pasos:

  1. Configurar supervisión: la aplicación de servicio registra opcionalmente una retrollamada para cambios en el estado del suscriptor a través de [SWS_CM_01110] o con un contexto de ejecución predefinido a través de [SWS_CM_01111].
  2. Comprobar estado de suscripción: mediante [SWS_CM_01109] se puede determinar de forma síncrona si los clientes se han suscrito al trigger. Solicitar el envío de un trigger requiere que exista al menos un suscriptor activo ([SWS_CM_10518] en SWS CommunicationManagement p. 154).
  3. Activar disparador: El envío del disparador a todas las aplicaciones suscriptoras se realiza mediante la llamada a Send() ([SWS_CM_00721], EXP ARAComAPI p. 10).
  4. Evaluar resultado: La llamada a Send() devuelve un ara::core::Result<void>, el cual indica si el envío se inició correctamente o si se produjo un error ([SWS_CM_00721]).
  5. Eliminar manejador: Antes de la destrucción o cuando ya no sea necesario, el callback registrado se elimina a través de [SWS_CM_01112].

Diagrama de secuencia: Flujo típico para el registro de cambios de estado y para el envío de un disparador a los suscriptores. Fuentes: [SWS_CM_00721], [SWS_CM_01109], [SWS_CM_01110], [SWS_CM_10518].

Escenarios de error

Al trabajar con la clase Trigger, pueden producirse estados específicos de error y de infracción:

  • Servicio no ofrecido (ComErrc::kServiceNotOffered): Si se llama a [SWS_CM_00721] antes de que el servicio correspondiente se haya proporcionado a través de OfferService(), la llamada falla y devuelve en ara::core::Result el código de error ComErrc::kServiceNotOffered con semántica de reversión.
  • Intervalo mínimo de envío no alcanzado (ComErrc::kMinimumSendIntervalViolationError): Si se ha configurado un intervalo mínimo de envío en el despliegue (ServiceInterfaceDeploymentElement.minimumSendInterval) y se llama a Send() antes de que haya transcurrido dicho intervalo, el método notifica este error ([SWS_CM_00721]).
  • Error de transmisión de red (ComErrc::kCommunicationFailure): Si el envío del disparador SOME/IP falla localmente debido a un error de red notificado al middleware, Send() devuelve el error ComErrc::kCommunicationFailure en el resultado ([SWS_CM_10517] en SWS CommunicationManagement p. 95).
  • Manejador no válido (InvalidHandlerViolation): Si se pasa a [SWS_CM_01110] o [SWS_CM_01111] un objeto invocable vacío, inexistente o nulo, se genera una InvalidHandlerViolation.

<p>En lo referente a la seguridad ante excepciones y fallos, todas las funciones miembro de la clase trigger están declaradas con el especificador <code>noexcept</code> y definidas como seguras frente a excepciones (<em>exception safe</em>) (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a>, <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a>, <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>, <a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>).</p>

<h4>Ruta de uso</h4>
<p>Un flujo típico para el uso de una instancia de trigger en el lado del servidor comprende los siguientes pasos:</p>
<ol>
<li><strong>Configurar supervisión:</strong> la aplicación de servicio registra opcionalmente una retrollamada para cambios en el estado del suscriptor a través de <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a> o con un contexto de ejecución predefinido a través de <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a>.</li>
<li><strong>Comprobar estado de suscripción:</strong> mediante <a class="spec-record-ref" data-req="SWS_CM_01109" href="../spec/record.html?id=SWS_CM_01109">[SWS_CM_01109]</a> se puede determinar de forma síncrona si los clientes se han suscrito al trigger. Solicitar el envío de un trigger requiere que exista al menos un suscriptor activo (<a class="spec-record-ref" data-req="SWS_CM_10518" href="../spec/record.html?id=SWS_CM_10518">[SWS_CM_10518]</a> en <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=154">SWS CommunicationManagement p. 154</a>).</li>
<li><strong>Activar disparador:</strong> El envío del disparador a todas las aplicaciones suscriptoras se realiza mediante la llamada a <code>Send()</code> (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=10">EXP ARAComAPI p. 10</a>).</li>
<li><strong>Evaluar resultado:</strong> La llamada a <code>Send()</code> devuelve un <code>ara::core::Result&lt;void&gt;</code>, el cual indica si el envío se inició correctamente o si se produjo un error (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><strong>Eliminar manejador:</strong> Antes de la destrucción o cuando ya no sea necesario, el callback registrado se elimina a través de <a class="spec-record-ref" data-req="SWS_CM_01112" href="../spec/record.html?id=SWS_CM_01112">[SWS_CM_01112]</a>.</li>
</ol>

<h4>Escenarios de error</h4>
<p>Al trabajar con la clase Trigger, pueden producirse estados específicos de error y de infracción:</p>
<ul>
<li><strong>Servicio no ofrecido (<code>ComErrc::kServiceNotOffered</code>):</strong> Si se llama a <a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a> antes de que el servicio correspondiente se haya proporcionado a través de <code>OfferService()</code>, la llamada falla y devuelve en <code>ara::core::Result</code> el código de error <code>ComErrc::kServiceNotOffered</code> con semántica de reversión.</li>
<li><strong>Intervalo mínimo de envío no alcanzado (<code>ComErrc::kMinimumSendIntervalViolationError</code>):</strong> Si se ha configurado un intervalo mínimo de envío en el despliegue (<code>ServiceInterfaceDeploymentElement.minimumSendInterval</code>) y se llama a <code>Send()</code> antes de que haya transcurrido dicho intervalo, el método notifica este error (<a class="spec-record-ref" data-req="SWS_CM_00721" href="../spec/record.html?id=SWS_CM_00721">[SWS_CM_00721]</a>).</li>
<li><strong>Error de transmisión de red (<code>ComErrc::kCommunicationFailure</code>):</strong> Si el envío del disparador SOME/IP falla localmente debido a un error de red notificado al middleware, <code>Send()</code> devuelve el error <code>ComErrc::kCommunicationFailure</code> en el resultado (<a class="spec-record-ref" data-req="SWS_CM_10517" href="../spec/record.html?id=SWS_CM_10517">[SWS_CM_10517]</a> en <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=95">SWS CommunicationManagement p. 95</a>).</li>
<li><strong>Manejador no válido (<code>InvalidHandlerViolation</code>):</strong> Si se pasa a <a class="spec-record-ref" data-req="SWS_CM_01110" href="../spec/record.html?id=SWS_CM_01110">[SWS_CM_01110]</a> o <a class="spec-record-ref" data-req="SWS_CM_01111" href="../spec/record.html?id=SWS_CM_01111">[SWS_CM_01111]</a> un objeto invocable vacío, inexistente o nulo, se genera una <code>InvalidHandlerViolation</code>.</li>
</ul>
