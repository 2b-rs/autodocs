Sirve para la categorización, la descripción textual y la conversión en excepciones de los errores de diagnóstico de Adaptive Platform.

La clase ara::diag::DiagErrorDomain define el dominio de error para errores de diagnóstico en AUTOSAR Adaptive y deriva de ara::core::ErrorDomain ([SWS_DM_00517]). Traduce valores numéricos de error de diagnóstico de forma segura para subprocesos a textos descriptivos sin devolver nullptr ([SWS_DM_00522]) y permite la conversión en excepciones tipificadas cuando las excepciones de C++ están habilitadas ([SWS_DM_00523]). Con las excepciones del compilador deshabilitadas, se suprime la interfaz de excepciones en favor de una gestión de errores puramente basada en valores.

Contexto

La clase ara::diag::DiagErrorDomain representa el dominio de error estandarizado para errores de diagnóstico dentro del módulo diag de AUTOSAR Adaptive Platform ([SWS_DM_00517]). Conforme a la definición de clase en AUTOSAR_AP_SWS_Diagnostics §8.11.3 «Class: DiagErrorDomain», está declarada como final y deriva de la clase de infraestructura base ara::core::ErrorDomain. Su responsabilidad principal consiste en integrar los códigos de error de diagnóstico en el modelo de errores unificado de AUTOSAR Adaptive.

Para ello, la clase vincula el tipo de enumeración específico del dominio para valores de error a través del alias de tipo Errc ([SWS_DM_00518]), proporciona con Exception un alias para la clase base de excepciones asociada DiagException ([SWS_DM_00519]) y traduce códigos de error en mensajes de texto legibles ([SWS_DM_00522]). A través del método Name() devuelve el nombre corto del dominio especificado en [SWS_CORE_90023] ([SWS_DM_00521]), lo que permite que sea identificada unívocamente por componentes de diagnóstico y aplicaciones.

Ciclo de vida

La instanciación de ara::diag::DiagErrorDomain se realiza a través del constructor predeterminado (AUTOSAR_AP_SWS_Diagnostics §8.11.3.2.1.1 «Default Constructor»). Este está definido como constexpr y noexcept ([SWS_DM_00520]). Debido a estas propiedades, las instancias típicamente deberían construirse ya en tiempo de compilación y mantenerse en el espacio de direcciones como objetos singleton estáticos o de larga vida, a fin de permitir una resolución eficiente de errores sin asignación dinámica de memoria.

En cuanto a la concurrencia, el constructor predeterminado, así como todos los métodos de interfaz derivados (Name(), Message() y ThrowAsException()), están especificados explícitamente como seguros para subprocesos (thread-safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523]). Tras la construcción, el objeto no mantiene ningún estado interno mutable, de modo que se permiten accesos de lectura concurrentes a través de múltiples subprocesos de la aplicación o de diagnóstico sin sincronización externa adicional. La destrucción del objeto no requiere la limpieza de recursos externos.

Ruta de uso

La ruta de uso típica se da cuando una operación de diagnóstico falla y debe evaluarse o registrarse un error del tipo ara::core::ErrorCode. La aplicación o un framework de diagnóstico accede al dominio de error para resolver el texto del error o, en su caso, lanzar una excepción.

  1. Identificación del dominio: el llamador verifica el dominio de error a partir del nombre corto a través de Name() ([SWS_DM_00521]).
  2. Obtener mensaje de error: a través de Message(errorCode) se transforma el valor numérico del código en una descripción textual ([SWS_DM_00522]).
  3. Lanzar excepción (opcional): si el flujo de control llamador prevé un manejo de errores basado en excepciones, ara::core::ErrorCode delega en ThrowAsException(), con lo que se instancia y lanza la excepción asociada DiagException ([SWS_DM_00519], [SWS_DM_00523]).

Diagrama de secuencia: flujo de identificación de error, resolución de texto y lanzamiento opcional de una excepción a través de DiagErrorDomain. Fuentes: [SWS_DM_00519], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523].

Escenarios de error

Al utilizar Message(), la función recibe un código de error del tipo base ara::core::ErrorDomain::CodeType. Está garantizado por contrato que el valor de retorno nunca es nullptr ([SWS_DM_00522]). Para valores de código no válidos o no especificados, la implementación devuelve presumiblemente una cadena genérica de reserva para cumplir la garantía.

En lo relativo a la seguridad frente a excepciones, el constructor así como los métodos Name() y Message() están declarados como noexcept y se consideran seguros frente a excepciones (exception safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522]). En cambio, ThrowAsException() está anotado explícitamente con noexcept(false) y clasificado como not exception safe ([SWS_DM_00523]), puesto que el lanzamiento deliberado de una excepción constituye su función principal definida.

Una condición de contorno fundamental afecta a las cadenas de herramientas sin compatibilidad con excepciones de C++: si las excepciones de C++ están deshabilitadas en el compilador, ThrowAsException() no participa en la resolución de sobrecarga conforme a [SWS_CORE_10304] ([SWS_DM_00523]). En tales entornos, las aplicaciones deben procesar los errores de diagnóstico de forma puramente basada en valores mediante el tipo de enumeración de códigos de error Errc ([SWS_DM_00518]).

Esta guía se basa en la especificación AUTOSAR Adaptive Release R25-11 y resume los aspectos clave de ara::diag::DiagErrorDomain.

El constructor por defecto DiagErrorDomain() inicializa una instancia del dominio de errores de diagnóstico ara::diag::DiagErrorDomain ([SWS_DM_00520], AUTOSAR_AP_SWS_Diagnostics §8.11.3.2.1.1 «Default Constructor»). Está declarado como constexpr y noexcept, no recibe parámetros y no devuelve ningún valor ([SWS_DM_00520]). La llamada se realiza de forma síncrona y puede ejecutarse tanto en tiempo de compilación como en tiempo de ejecución.

En cuanto a la seguridad de ejecución y la concurrencia, se aplican las siguientes propiedades:

  • Seguridad frente a fallos y excepciones: la función está especificada como exception safe y no puede lanzar ninguna excepción debido a noexcept ([SWS_DM_00520]). No se definen códigos de error específicos ni notificaciones a DET o DEM para la construcción.
  • Seguridad para subprocesos: la instanciación está clasificada como thread-safe ([SWS_DM_00520]) y no está sujeta a ninguna restricción respecto al contexto de llamada.

En interacción con el módulo Diagnostics, la clase DiagErrorDomain ([SWS_DM_00517], AUTOSAR_AP_SWS_Diagnostics §8.11.3 «Class: DiagErrorDomain») representa el dominio de errores de diagnóstico. Proporciona alias de tipos centrales como Errc ([SWS_DM_00518]) y Exception ([SWS_DM_00519]). Las instancias del dominio también ofrecen métodos para consultar el nombre ([SWS_DM_00521]), para traducir códigos de error a textos de mensaje mediante Message() ([SWS_DM_00522]), así como para lanzar excepciones específicas del dominio a través de ThrowAsException() ([SWS_DM_00523]).

En el uso práctico, es de prever que rara vez sea necesaria una instanciación manual directa mediante este constructor (interpretación), ya que con la función ara::diag::GetDiagDomain() ([SWS_DM_00524]) ya se dispone de una referencia global de instancia, que ara::diag::MakeErrorCode() ([SWS_DM_00525]), entre otros, utiliza para generar códigos de error.

              La función miembro ThrowAsException de la clase ara::diag::DiagErrorDomain sirve para el lanzamiento sincrónico de una excepción C++ a partir de un código de error transferido ([SWS_DM_00523], AUTOSAR_AP_SWS_Diagnostics §8.11.3.2.2.3 «ThrowAsException»). Se encuentran implementaciones análogas de ThrowAsException, entre otras, en ara::diag::DiagUdsNrcErrorDomain ([SWS_DM_00535], AUTOSAR_AP_SWS_Diagnostics §8.12.3.2.2.3 «ThrowAsException»), ara::diag::DiagOfferErrorDomain ([SWS_DM_00995]), ara::diag::DiagReportingErrorDomain ([SWS_DM_01002]) así como en ara::diag::DiagSovdErrorDomain ([SWS_DM_01815]). Interpretación: Mediante la especificación con override, el método presumiblemente representa una operación de interfaz común para el tratamiento polimórfico de excepciones.
