Contexto

La clase apext::diag::uds_transport::UdsTransportProtocolHandler es la clase base abstracta para complementos de protocolo de transporte UDS específicos y propietarios en el Diagnostic Management (DM) de AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00315]). Desacopla el Core de diagnóstico genérico de las particularidades de redes de transmisión y capas de transporte concretas como DoIP o protocolos basados en CAN.

Un manejador de transporte interactúa esencialmente con tres interlocutores:

  • Diagnostic Management Core: El DM gestiona todo el ciclo de vida del manejador y proporciona, a través de la referencia del gestor apext::diag::uds_transport::UdsTransportProtocolMgr, la contraparte para indicaciones de estado y de datos ([SWS_DM_09015], [SWS_DM_09025]).
  • Capa de red y cliente de diagnóstico: El complemento gestiona el intercambio físico o lógico de datos con el comprobador de diagnóstico externo o interno del vehículo ([SWS_DM_00326], [SWS_DM_00351]).
  • Manejador periódico (opcional): Si el protocolo de transporte correspondiente admite transmisiones periódicas, el manejador proporciona una referencia a un UdsTransportProtocolPeriodicHandler a través de GetPeriodicHandler() ([SWS_DM_01068]).

Ciclo de vida

El ciclo de vida de una implementación de protocolo de transporte está estrictamente controlado por el DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer», [SWS_DM_00329]). La creación se realiza mediante el constructor UdsTransportProtocolHandler(handlerId, transportProtocolMgr), en el cual el DM asigna al manejador un identificador único del tipo UdsTransportProtocolHandlerID, así como la referencia al UdsTransportProtocolMgr correspondiente ([SWS_DM_09015], [SWS_DM_09025]). El ID asignado puede consultarse en cualquier momento mediante GetHandlerID() ([SWS_DM_00325]). El constructor está designado como seguro para subprocesos ([SWS_DM_09015]).

Para desacoplar inicializaciones complejas del protocolo respecto del constructor, el DM llama a continuación a Initialize() ([SWS_DM_00319], [SWS_DM_00329]). A excepción de GetPeriodicHandler(), el DM no debe invocar ningún otro método del manejador antes de un retorno exitoso de InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). Tras una inicialización exitosa, el DM inicia el protocolo mediante Start() ([SWS_DM_00322]). Dado que Start() se ejecuta de forma asíncrona, el DM puede poner en marcha varios manejadores en paralelo para minimizar el tiempo de arranque ([SWS_DM_00322]).

Si la aplicación DM cambia al estado ApplicationState.kTerminating, invoca Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). El DM espera hasta que el manejador confirme la parada mediante UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). Tras el retorno de Stop(), el complemento del manejador no debe llamar a ningún otro método en el gestor, con la única excepción de la confirmación HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). El desmantelamiento posterior se realiza mediante el destructor virtual ([SWS_DM_09016]).

Diagrama de estados: fases del ciclo de vida y condiciones de transición de un manejador de protocolo de transporte UDS. Fuentes: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Ruta de uso

Durante el funcionamiento normal, el manejador asume el intercambio bidireccional de mensajes UDS:

  1. Recepción de mensajes (indicación): Tan pronto como se recibe un nuevo mensaje UDS en un canal y se conocen la dirección de origen, la dirección de destino, el tipo de direccionamiento (físico o funcional), la longitud total del mensaje y los primeros bytes de datos útiles (al menos dos bytes para mensajes de más de un byte), el complemento llama a UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 «Indication of UDS message reception», [SWS_DM_00342], [SWS_DM_00330]). En este proceso, el manejador transfiere la identificación del canal en el parámetro globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»).
  2. Envío de mensajes (transmisión): El DM devuelve la correspondiente respuesta de diagnóstico UDS a través del mismo manejador y del mismo canal (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer», [SWS_DM_00348]). Para ello, llama a Transmit(message, channelId) ([SWS_DM_00327]). El mensaje se transfiere al manejador como UdsMessageConstPtr a modo de std::unique_ptr.
  3. Confirmación de envío: Tan pronto como el mensaje se haya transmitido a través de la red (o se haya producido un error), el manejador debe devolver la propiedad de message al DM mediante UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). El resultado se transmite como kTransmitOk o kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Otra ruta de uso específica es la recuperación de canales tras un reinicio de la unidad de control (servicio UDS 0x11 con respuesta positiva tras el reinicio): en este caso, el DM llama a NotifyReestablishment(channelId) antes del reinicio ([SWS_DM_00326]). El complemento guarda de forma persistente los parámetros de conexión (por ejemplo, direcciones IP y puertos). Tras el reinicio mediante Start(), el complemento detecta la reconexión del mismo cliente de diagnóstico e informa al DM mediante UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Diagrama de secuencia: recepción de mensajes UDS, transmisión de respuesta y posterior confirmación. Fuentes: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Escenarios de error

La interfaz gestiona diversas situaciones de excepción y error:

  • Inicialización fallida: Si Initialize() devuelve el valor InitializationResult::kInitializeFailed ([SWS_DM_09017]), el DM cancela por completo el proceso de inicio de este protocolo de transporte y no invoca ningún otro método en esta instancia ([SWS_DM_01745]).
  • Transmisiones periódicas no admitidas: Si el protocolo concreto no admite transmisiones periódicas, la llamada a GetPeriodicHandler() devuelve un ara::core::Result con el código de error kConfigurationMismatch ([SWS_DM_01068]).
  • Rechazo de la recuperación de canal: Si un complemento no puede satisfacer la reserva persistente para un canal (por ejemplo, por falta de opción de almacenamiento no volátil o por una asignación inestable), NotifyReestablishment(channelId) devuelve el valor false ([SWS_DM_00326]).
  • Error de transmisión en la red: Si la capa de red no pudo enviar un mensaje solicitado a través de Transmit(), el manejador debe transferir el resultado kTransmitFailed en TransmitConfirmation ([SWS_DM_00351]). No devolver el búfer provoca fugas de recursos en el DM.
  • Infracción de secuencia tras la parada: Si un complemento invoca un método distinto de HandlerStopped() en UdsTransportProtocolMgr tras retornar de Stop(), se produce una infracción de la secuencia de protocolo ([SWS_DM_00323], [SWS_DM_01741]).

Esta guía de clases se basa en la especificación AUTOSAR Adaptive R25-11.

              función NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
