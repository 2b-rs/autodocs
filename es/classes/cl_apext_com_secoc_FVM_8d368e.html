Contexto

La clase apext::com::secoc::FVM proporciona la interfaz estandarizada para el Freshness Value Management (FVM) dentro del módulo Communication Management (CM) ([SWS_CM_11287]). Sirve para proteger la comunicación orientada a servicios frente a ataques de repetición en el marco de Secure Onboard Communication (SecOC). La interfaz es implementada de forma específica por el fabricante (OEM) o el proveedor de la pila como biblioteca (AUTOSAR_AP_SWS_CommunicationManagement p. 537 «Class: FVM»). Dentro del Communication Management existe exactamente una instancia central (singleton) de esta clase para la gestión de los valores de frescura (AUTOSAR_AP_SWS_CommunicationManagement p. 537 «Class: FVM»).

Los interlocutores principales son el Communication Management (ara::com) como instancia de control, la biblioteca FVM específica del fabricante para el cálculo y la sincronización de los valores de frescura, así como los canales de comunicación seguros (canales de transmisión y recepción) para mensajes autenticados ([SWS_CM_11272], [SWS_CM_11274], [SWS_CM_11276]).

Diagrama de contexto: Interacción entre el Communication Management, la biblioteca FVM y el canal SecOC. Fuentes: [SWS_CM_11272], [SWS_CM_11274], [SWS_CM_11276], AUTOSAR_AP_SWS_CommunicationManagement p. 224 «Lifecycle management of FVM».

Ciclo de vida

El ciclo de vida de la implementación de FVM es gestionado completamente por ara::com ([SWS_CM_11272]). Durante la inicialización de la pila de comunicación, el Communication Management crea la instancia singleton y llama explícitamente al método Initialize() ([SWS_CM_11273], [SWS_CM_11290]). Solo tras la devolución exitosa de Initialize(), el Freshness Value Manager se encuentra en estado operativo.

Los derechos de propiedad y control corresponden exclusivamente al Communication Management. Dado que la clase se opera como un singleton y potencialmente se procesan múltiples conexiones de transmisión y recepción en paralelo, es probable que la seguridad para subprocesos de las llamadas a métodos esté garantizada por la implementación específica del fabricante de la biblioteca FVM (interpretación). Un apagado controlado se realiza de forma análoga mediante la gestión del ciclo de vida de ara::com ([SWS_CM_11272]).

Ruta de uso

Tras la inicialización, la interacción típica se divide en dos rutas operativas: la ruta de transmisión (Tx) y la ruta de recepción (Rx).

  • Inicialización: El Communication Management llama a Initialize() para preparar estructuras internas, contadores de sincronización o temporizadores criptográficos de la biblioteca FVM ([SWS_CM_11273], [SWS_CM_11290]).
  • Ruta de transmisión (Tx): Si se va a enviar un mensaje protegido mediante SecOC y en la configuración se ha definido una freshnessValueId, ara::com solicita a través de GetTxFreshness(SecOCFreshnessValueID) el valor de frescura actual ([SWS_CM_11274], [SWS_CM_11289]). La autenticación se lleva a cabo en el orden de procesamiento tras los cálculos de protección E2E ([SWS_CM_11274]). El FVContainer obtenido se utiliza a continuación para el cálculo del autenticador ([SWS_CM_11289]).
  • Ruta de recepción (Rx): Al llegar un mensaje protegido, ara::com comprueba el atributo securedRxVerification. Si este está activado o no está definido explícitamente, se consulta el valor de frescura a través de GetRxFreshness(SecOCFreshnessValueID, SecOCTruncatedFreshnessValue, SecOCAuthVerifyAttempts) ([SWS_CM_11276], [SWS_CM_11288]). La llamada transfiere el valor de frescura truncado procedente del mensaje recibido, así como el contador de intentos de verificación. Tras el cálculo y la comparación del autenticador, ara::com notifica el resultado al FVM a través de SetVerificationStatus(secOCFreshnessValueID, secOCVerificationStatus) ([SWS_CM_19999]). Si, por el contrario, securedRxVerification está configurado como false, se omite la verificación y el mensaje se reenvía sin comprobación de FVM ([SWS_CM_11372]).

Diagrama de secuencia: secuencia de llamadas para inicialización, ruta de transmisión y de recepción entre Communication Management y FVM. Fuentes: [SWS_CM_11273], [SWS_CM_11274], [SWS_CM_11276], [SWS_CM_11288], [SWS_CM_11289], [SWS_CM_19999].

Escenarios de error

Todos los métodos de interfaz de apext::com::secoc::FVM están declarados con noexcept y notifican estados de error de forma determinista mediante el tipo de error ara::core::Result ([SWS_CM_11288], [SWS_CM_11289], [SWS_CM_11290], [SWS_CM_19999]).

Se especifican los siguientes códigos de error y de estado:

  • Fallo de inicialización: si la preparación de la biblioteca FVM falla, Initialize() devuelve el código de error ComSecOcFvmErrc::kFVInitializeFailed ([SWS_CM_11290]). En este caso, el subsistema SecOC no puede procesar mensajes protegidos.
  • Valor de frescura no disponible (Tx): si GetTxFreshness() devuelve el error ComSecOcFvmErrc::kFVNotAvailable o falla el cálculo del autenticador, ara::com incrementa el Authentication Build Counter para este mensaje ([SWS_CM_11275], [SWS_CM_11289]). El proceso de creación se repite de forma específica de la implementación. Si el contador alcanza el valor de umbral configurado SecOCAuthenticationBuildAttempts, el mensaje se descarta ([SWS_CM_11275]). En caso de creación correcta, el contador se restablece a 0 ([SWS_CM_11275]).
  • Valor de frescura no disponible (Rx): si no se puede determinar el valor de frescura para un mensaje recibido, GetRxFreshness() también devuelve ComSecOcFvmErrc::kFVNotAvailable ([SWS_CM_11288]). Esto impide una verificación satisfactoria del autenticador.
  • Notificación del estado de verificación: a través de SetVerificationStatus(), ara::com transmite el resultado de la comprobación al FVM ([SWS_CM_19999]). La enumeración VerificationStatus ([SWS_CM_11378]) distingue entre:
    • Success: verificación correcta.
    • kSecOcVerificationFailure (0x01): error general de verificación.
    • kSecOcFreshnessFailure (0x02): verificación fallida debido a un valor de frescura no válido.
    • kSecOcAuthenticationBuildFailure (0x03): error al generar el código de autenticación.
    • kSecOcNoVerification (0x04): la verificación se omitió y los datos se transfirieron directamente.
    • kSecOcVerificationFailureOverwritten (0x05): verificación fallida; el mensaje se reenvió de todos modos debido al estado de override.

Para SetVerificationStatus() en sí no hay definidos códigos de error estandarizados ([SWS_CM_19999]).

Esta guía se basa exclusivamente en la especificación de AUTOSAR para Communication Management (R25-11).
