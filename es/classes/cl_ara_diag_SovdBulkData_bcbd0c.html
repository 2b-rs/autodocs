Permite a las aplicaciones la puesta a disposición y transmisión de datos masivos de SOVD a través de Diagnostic Management.

La interfaz [SWS_DM_01841] conecta aplicaciones adaptativas con Diagnostic Management para proporcionar operaciones de datos masivos basadas en SOVD. A través de métodos puramente virtuales se consultan metadatos, se gestionan cargas y descargas de datos masivos y se eliminan fondos de datos de forma selectiva o por categorías. Una instancia se vincula a un puerto modelado, se habilita mediante la llamada a Offer() para el reenvío de solicitudes de diagnóstico y se desregistra al finalizar mediante StopOffer() [SWS_DM_01857]. En función de la concurrencia seleccionada, las rutinas de retrollamada proporcionadas deben diseñarse como seguras para subprocesos.

Contexto

La clase de interfaz ara::diag::SovdBulkData [SWS_DM_01841] proporciona una interfaz de servicio genérica para el acceso a datos masivos (Bulk Data) según Service-Oriented Vehicle Diagnostics (SOVD) SWS Diagnostics §8.53 «Class: SovdBulkData». Sirve como elemento de enlace entre fuentes de datos específicas de la aplicación y el servidor de diagnóstico central de la Adaptive Platform.

En la tramitación global participan al menos tres componentes:

  • Cliente SOVD: una herramienta de diagnóstico externa que consulta, carga o elimina datos masivos. La comunicación se gestionaría típicamente a través de mecanismos HTTP/REST.
  • Diagnostic Management (DM): la Diagnostic Server Instance recibe llamadas de servicio SOVD externas y las convierte en llamadas a métodos locales SWS Diagnostics §7.x «SOVD Bulk Data Realization».
  • Adaptive Application: una aplicación definida por el usuario deriva de ara::diag::SovdBulkData, instancia la clase y proporciona los flujos de datos y metadatos propiamente dichos.

Diagrama de contexto: interacción entre el cliente SOVD, Diagnostic Management y la interfaz de aplicación ara::diag::SovdBulkData. Fuentes: [SWS_DM_01790], [SWS_DM_01841], [SWS_DM_01857].

Ciclo de vida

La instanciación de ara::diag::SovdBulkData se realiza a través del constructor transfiriendo un ara::core::InstanceSpecifier así como la indicación del comportamiento de concurrencia mediante ConcurrencyType [SWS_DM_01847]. El InstanceSpecifier vincula el objeto a un PortPrototype de un DiagnosticSovdBulkDataInterface definido en el modelo de diseño.

En cuanto a las relaciones de propiedad, la clase está concebida como ejemplar único: el constructor de copia [SWS_DM_01848] y el operador de asignación por copia [SWS_DM_01850] están explícitamente eliminados (=delete). Una transferencia de instancias solo está prevista mediante operaciones de movimiento; el constructor de movimiento [SWS_DM_01849] y la asignación por movimiento [SWS_DM_01851] están implementados como protegidos.

El ciclo de vida funcional se divide en las siguientes fases:

  • Inactivo: tras la construcción, el objeto está presente localmente, pero aún no recibe solicitudes de diagnóstico de Diagnostic Management.
  • Activo (Offered): mediante la llamada al método Offer() [SWS_DM_01857], el objeto se registra en el DM. Solo a partir de este momento el DM reenvía las solicitudes SOVD entrantes a los métodos manejadores virtuales.
  • Detenido: la llamada a StopOffer() [SWS_DM_01858] desactiva de nuevo el reenvío de solicitudes.
  • Destrucción: el destructor virtual ~SovdBulkData() [SWS_DM_01852] finaliza la vida útil del objeto. Antes de la destrucción, presumiblemente debería llamarse a StopOffer() para desconectar limpiamente los accesos pendientes.

En lo relativo a la concurrencia, el ConcurrencyType transferido en el constructor determina si los métodos de retrollamada virtuales deben ejecutarse como seguros para subprocesos (kConcurrent) o no seguros para subprocesos (kNotConcurrent) [SWS_DM_01847]. Los métodos de control Offer() [SWS_DM_01857], StopOffer() [SWS_DM_01858] y el destructor [SWS_DM_01852] no son ellos mismos seguros para subprocesos.

Ruta de uso

Una secuencia típica para la puesta a disposición y ejecución de operaciones de datos masivos de SOVD comprende los siguientes pasos:

  1. Derivación de clase: la aplicación implementa una clase concreta que hereda de ara::diag::SovdBulkData y sobrescribe los métodos puramente virtuales.
  2. Puesta a disposición: tras la instanciación, la aplicación llama a Offer() [SWS_DM_01857] para ofrecer el servicio.
  3. Procesamiento de solicitudes:
    • Si un cliente solicita metadatos, el servidor de diagnóstico llama a GetBulkDataMetaData [SWS_DM_01791], lo que proporciona un vector de BulkDataMetaDataDescriptor a través de ara::core::Future [SWS_DM_01853].
    • En caso de una llamada de descarga, el DM llama a RequestBulkDataDownload [SWS_DM_01792]. La aplicación responde con una sesión de lectura (DataTransferReadSession) junto con metadatos o una redirección HTTP (HttpRedirect) [SWS_DM_01873].
    • Para operaciones de carga, el DM llama a RequestBulkDataUpload [SWS_DM_01793], tras lo cual se proporciona una sesión de escritura (DataTransferWriteSession) [SWS_DM_01854].
    • El DM reenvía las solicitudes de eliminación a DeleteSpecificBulkData (para recursos individuales) [SWS_DM_01856] o a DeleteAllBulkData (por categorías) [SWS_DM_01855].
  4. Cancelación del registro del servicio: en cuanto se deba suspender el procesamiento, la aplicación llama a StopOffer() [SWS_DM_01858].

Diagrama de secuencias: secuencia de interacción entre el cliente SOVD, Diagnostic Management y el manejador durante la descarga de Bulk Data. Fuentes: [SWS_DM_01792], [SWS_DM_01857], [SWS_DM_01858], [SWS_DM_01873].

Escenarios de error

Al utilizar ara::diag::SovdBulkData, deben distinguirse diferentes tipos de error:

  • Violaciones de configuración durante la instanciación: si la resolución del modelo falla o los mapeos no encajan, el constructor notifica violaciones específicas [SWS_DM_01847]. Entre ellas se encuentran InstanceSpecifierMappingIntegrityViolation (modelo no válido o sin PortPrototype), PortInterfaceMappingViolation (tipificación incorrecta del mapeo de puertos), ProcessMappingViolation (no se ha modelado ningún proceso adecuado) y InstanceSpecifierAlreadyInUseViolation (Specifier ya ocupado dentro del proceso).
  • Errores de registro en Offer: la llamada a Offer() devuelve un ara::core::Result<void> [SWS_DM_01857]. Los posibles errores son DiagOfferErrc::kAlreadyOffered, si el servicio ya se está ofreciendo, así como DiagOfferErrc::kConfigurationMismatch, si la configuración no coincide con las descripciones DEXT.
  • Códigos de error en operaciones asíncronas: si una operación de datos masivos solicitada no puede llevarse a cabo con éxito, el error se transporta en el ara::core::Future devuelto. Para ello, la aplicación debe utilizar códigos de error estandarizados de SOVD de acuerdo con ISO 17978-3 o ASAM SOVD 1.1 (haciendo uso de DiagSovdErrc) [SWS_DM_01854], [SWS_DM_01855], [SWS_DM_01856], [SWS_DM_01873]. Por el contrario, para GetBulkDataMetaData no hay especificados errores estandarizados [SWS_DM_01853].
  • Tratamiento de cancelaciones: los métodos de retrollamada reciben un objeto CancellationHandler que señala si la conversación de diagnóstico subyacente se canceló prematuramente [SWS_DM_01853], [SWS_DM_01873].

Esta guía se basa exclusivamente en la especificación AUTOSAR Adaptive R25-11 para el módulo diag.

Se llama a la función virtual DeleteAllBulkData de la clase ara::diag::SovdBulkData para ejecutar el método SOVD «Delete All Bulk Data Defined by Category» [SWS_DM_01855]. La definición de la interfaz se encuentra en el encabezado ara/diag/sovd_bulk_data.h AUTOSAR_AP_SWS_Diagnostics §8.53.1.1.3.1 «DeleteAllBulkData».

El método recibe los siguientes parámetros de transferencia:

  • bulkDataCategory (ara::core::String): identifica la categoría de datos masivos de la que se deben eliminar todas las instancias [SWS_DM_01855].
  • metaInfo (MetaInfo const &): transfiere metainformación contextual de la solicitud actual [SWS_DM_01855].
  • cancellationHandler (CancellationHandler): informa sobre la cancelación prematura de la conversación en curso [SWS_DM_01855].

El resultado se pone a disposición de forma asíncrona mediante un ara::core::Future<DeleteByCategoryResult> [SWS_DM_01855]. Interpretación: dado que la purga de categorías enteras de datos masivos puede requerir mucho tiempo, es probable que la aplicación deba comprobar periódicamente el cancellationHandler transferido para reaccionar de inmediato ante posibles cancelaciones.

Tratamiento de fallos y seguridad frente a excepciones

El método está declarado como noexcept y seguro frente a excepciones (exception safe) [SWS_DM_01855]. Si la eliminación falla, se debe transmitir en el ara::core::Future un código de error SOVD adecuado conforme a ISO 17978-3 o ASAM SOVD 1.1 [SWS_DM_01855].

concurrencia

La seguridad para hilos es condicional (conditional): el ConcurrencyType transferido al constructor determina si la implementación debe diseñarse como segura para hilos o no segura para hilos [SWS_DM_01855].
