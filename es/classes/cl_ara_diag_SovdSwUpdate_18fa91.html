Sirve como interfaz para la tramitación de actualizaciones de software a través del protocolo ASAM SOVD en el servidor de diagnóstico de AUTOSAR.

La clase proporciona la interfaz del lado de la aplicación para tramitar actualizaciones de software estandarizadas a través del protocolo SOVD de conformidad con ASAM SOVD [SWS_DM_01796]. Tras la instanciación, la aplicación activa el reenvío de solicitudes de diagnóstico a los manejadores de actualización específicos mediante el método Offer() [SWS_DM_01924]. A través de métodos asíncronos, los paquetes se registran, preparan, instalan de forma automatizada o manual y se vuelven a eliminar. Todos los procedimientos relevantes para la transferencia de datos y el ciclo de vida se procesan sin bloqueo mediante futuros.

Contexto

La clase ara::diag::SovdSwUpdate define la interfaz para la implementación de actualizaciones de software estandarizadas según ASAM SOVD dentro de la AUTOSAR Adaptive Platform [SWS_DM_01874]. Dado que la lógica de negocio propiamente dicha de las actualizaciones de software no se sitúa en el clúster funcional Diagnostic Management (DM), la ejecución permanece en la aplicación respectiva, mientras que ara::diag::SovdSwUpdate se centra en la tramitación conforme al estándar del protocolo SOVD subyacente AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept». Para la carga de archivos de actualización se emplean estrategias de transferencia tales como las especificadas para el servicio UDS 0x38 (RequestFileTransfer) AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept», [SWS_DM_01923].

En los flujos intervienen tres componentes esenciales: el cliente SOVD externo, la instancia del Diagnostic Server (DM) para la gestión de protocolos y rutas, así como la implementación del manejador específica de la aplicación de ara::diag::SovdSwUpdate [SWS_DM_01796], [SWS_DM_01924].

Diagrama de contexto: interacción entre el cliente SOVD, el Diagnostic Server (DM) y ara::diag::SovdSwUpdate. Fuentes: [SWS_DM_01796], [SWS_DM_01924], AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept»

Ciclo de vida

La instanciación de ara::diag::SovdSwUpdate se realiza a través del constructor indicando un ara::core::InstanceSpecifier, que hace referencia a un prototipo de puerto de un DiagnosticSovdUpdateInterface modelado, así como un modo de concurrencia (ConcurrencyType: kConcurrent o kNotConcurrent) [SWS_DM_01910]. El constructor está especificado como seguro para subprocesos y seguro frente a excepciones [SWS_DM_01910]. Como representante de una instancia de interfaz única, el constructor de copia y el operador de asignación por copia están eliminados (=delete) y protegidos [SWS_DM_01912], [SWS_DM_01914]. La construcción por movimiento y la asignación por movimiento están disponibles como protegidas, pero no son seguras para subprocesos [SWS_DM_01913], [SWS_DM_01915].

La destrucción del objeto se gestiona a través del destructor virtual ~SovdSwUpdate(), el cual se considera no seguro para subprocesos [SWS_DM_01911]. El hecho de si los métodos virtuales de retrollamada de la clase deben ejecutarse de forma concurrente depende directamente del ConcurrencyType pasado al constructor [SWS_DM_01910], [SWS_DM_01916].

Ruta de uso

Interpretación: dado que los métodos de interfaz proporcionados están declarados como puramente virtuales (=0), es de suponer que una clase de aplicación derivada implemente estos para llevar a cabo la ejecución real de la actualización, mientras que la clase base regula la vinculación con la plataforma.

El flujo regular se divide en las siguientes fases:

  • Puesta a disposición: tras la creación del objeto, la aplicación llama a Offer() para permitir al Diagnostic Management reenviar los mensajes SOVD entrantes a esta instancia [SWS_DM_01924].
  • Consulta y registro: a través de GetAllUpdates() se pueden consultar los paquetes de actualización existentes [SWS_DM_01797], [SWS_DM_01916]. Si se debe transferir un paquete nuevo, el Diagnostic Server solicita un registro mediante RequestUpdatePackageRegistration(), el cual proporciona de forma asíncrona una sesión de escritura (DataTransferWriteSession) junto con un ID de paquete de actualización [SWS_DM_01923]. Los detalles y el estado se determinan mediante GetUpdatePackageDetails() y GetUpdatePackageStatus() [SWS_DM_01802], [SWS_DM_01917], [SWS_DM_01921].
  • Instalación o eliminación: la instalación puede iniciarse de forma automatizada mediante PutUpdatePackageAutomated() [SWS_DM_01799], [SWS_DM_01918] o bien llevarse a cabo en dos pasos a través de PrepareUpdatePackage() [SWS_DM_01800], [SWS_DM_01919] seguido de ExecuteUpdatePackage() [SWS_DM_01801], [SWS_DM_01920]. Los paquetes que ya no se necesitan se eliminan mediante DeleteUpdatePackage() [SWS_DM_01922].
  • Finalización: antes del apagado, la aplicación desactiva el reenvío de mensajes llamando a StopOffer() [SWS_DM_01925].

Diagrama de secuencia: flujo típico de registro e instalación de paquetes a través de SOVD. Fuentes: [SWS_DM_01799], [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923], [SWS_DM_01924]

Escenarios de error

Al ofrecer los servicios mediante Offer() pueden producirse errores específicos en el tipo de retorno ara::core::Result<void>: DiagOfferErrc::kAlreadyOffered, en caso de que la instancia ya se esté ofreciendo, así como DiagOfferErrc::kConfigurationMismatch, si la configuración no coincide con el extracto de diagnóstico (DEXT) [SWS_DM_01924].

Si el constructor se invoca con un estado de modelo defectuoso, se notifican violaciones de arquitectura, entre ellas InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation o InstanceSpecifierAlreadyInUseViolation [SWS_DM_01910].

Todas las operaciones funcionales de actualización devuelven un ara::core::Future que, en caso de error, transporta códigos de error según ASAM SOVD 1.1 o ISO 17978-3 [SWS_DM_01917], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923]. Además, todos los métodos asíncronos reciben un CancellationHandler, a través del cual se señaliza una cancelación prematura de la conexión de diagnóstico en curso [SWS_DM_01916], [SWS_DM_01919], [SWS_DM_01923].

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 8b58fd563e10 Procedencia

La función virtual pura DeleteUpdatePackage de la clase ara::diag::SovdSwUpdate es llamada conforme a [SWS_DM_01803] por la instancia del Diagnostic Server cuando debe ejecutarse el método SOVD «Delete Update Package from an SOVD Server» ([SWS_DM_01922]). Esta inicia la eliminación de un paquete de actualización en el lado del servidor.

La llamada se realiza de forma asíncrona y devuelve un ara::core::Future<void>, el cual indica la finalización correcta o proporciona un objeto de error [SWS_DM_01922]. La signatura requiere los siguientes parámetros de entrada:

  • updatePackageId: designa como ara::core::String el ID unívoco del paquete de actualización a eliminar.
  • metaInfo: transfiere como MetaInfo const& información de contexto adicional de la solicitud.
  • cancellationHandler: transmite un objeto del tipo CancellationHandler que informa sobre si la conversación actual ha sido cancelada.

Si ocurre un error durante el procesamiento, el Future se rellena con un error de SOVD correspondiente. La especificación prescribe para ello el uso de códigos de error adecuados de ASAM SOVD 1.1 o ISO 17978-3 [SWS_DM_01922].

En relación con la concurrencia, el método está definido como condicionalmente seguro para subprocesos: si la implementación debe ser ejecutada como thread-safe o non-thread-safe se determina mediante el ConcurrencyType transferido en el constructor [SWS_DM_01922]. Además, la función está declarada como noexcept y segura frente a excepciones, por lo que no debe escapar ninguna excepción.

      usar
      
  
      El método virtual puro ExecuteUpdatePackage de la interfaz ara::diag::SovdSwUpdate sirve para ejecutar el método SOVD «Execute Installation of an Update» [SWS_DM_01920]. La declaración se encuentra en la cabecera ara/diag/sovd_sw_update.h AUTOSAR_AP_SWS_Diagnostics §8.58.2.1.3.2 «ExecuteUpdatePackage». Como parámetros de entrada se transfieren el identificador del paquete de actualización (updatePackageId), así como los datos de la solicitud (metaInfo) [SWS_DM_01920]. Adicionalmente, el objeto cancellationHandler informa si la conversación en curso ha sido cancelada [SWS_DM_01920]. La llamada se realiza de forma asíncrona y devuelve un ara::core::Future<void>, el cual suministra un resultado positivo o notifica un error de SOVD [SWS_DM_01920].
      
  
  
      Manejo de errores
      
  
      La interfaz está especificada como noexcept y segura frente a excepciones («exception safe») [SWS_DM_01920]. En consecuencia, los errores durante la ejecución no deben lanzarse mediante excepciones de C++, sino que deben devolverse de forma asíncrona a través del ara::core::Future con códigos de error aplicables de ASAM SOVD 1.1 o ISO 17978-3 [SWS_DM_01920].
      
  
  
      Concurrencia y condiciones de contorno
      
  
      En cuanto a la seguridad para subprocesos existe un requisito condicional («conditional»): si la función debe implementarse de manera segura o no segura para subprocesos se determina mediante el parámetro ConcurrencyType que fue transferido al constructor [SWS_DM_01920]. La implementación debería tener que evaluar el cancellationHandler para finalizar de forma ordenada la instalación del paquete ante una cancelación de la conversación [SWS_DM_01920].
