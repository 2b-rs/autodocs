Contexto

La clase ara::diag::SovdSwUpdate constituye la interfaz para la tramitación de actualizaciones de software a través del protocolo Service-Oriented Vehicle Diagnostics (SOVD) según ASAM SOVD e ISO 17978-3 ([SWS_DM_01874], [SWS_DM_01796]). Dentro de AUTOSAR Adaptive Platform existe una clara división funcional de tareas: la lógica de negocio propiamente dicha para la realización y gestión de actualizaciones de software permanece en la aplicación adaptativa, mientras que el clúster funcional Diagnostics (Diagnostic Server Instance o Diagnostic Management) asume la gestión del protocolo SOVD subyacente (AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»).

Como clase base abstracta, SovdSwUpdate define las interfaces de callback que deben ser implementadas por el software de aplicación. Las solicitudes entrantes de clientes SOVD externos son analizadas por la Diagnostic Server Instance y delegadas a la aplicación a través de los métodos correspondientes de SovdSwUpdate (AUTOSAR_AP_SWS_Diagnostics §7.3 «SOVD Software Update API»).

Diagrama de contexto: interlocutores de interacción y distribución de roles en la actualización de software mediante SOVD. Fuentes: [SWS_DM_01796], [SWS_DM_01874], AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»

Ciclo de vida

La creación de una instancia específica de la aplicación se realiza a través del constructor parametrizado, indicando un identificador de instancia (ara::core::InstanceSpecifier) y el modelo de concurrencia deseado (ConcurrencyType) ([SWS_DM_01910]). El InstanceSpecifier hace referencia a un PortPrototype declarado en el manifiesto de software, que debe estar tipificado a un DiagnosticSovdUpdateInterface ([SWS_DM_01910]). A través del concurrencyType se determina si los métodos de callback de la instancia deben ser invocados de manera segura para subprocesos (kConcurrent) o de forma secuencial o no segura para subprocesos (kNotConcurrent) en caso de solicitudes simultáneas ([SWS_DM_01910]).

Las instancias de SovdSwUpdate están vinculadas de forma biunívoca a un puerto de servicio. Por tanto, el constructor de copia y el operador de asignación están explícitamente eliminados (=delete) ([SWS_DM_01912], [SWS_DM_01914]). Las operaciones de movimiento están definidas como protegidas (protected) ([SWS_DM_01913], [SWS_DM_01915]).

Tras una inicialización correcta, la aplicación debe activar explícitamente el servicio mediante Offer() ([SWS_DM_01924]). Solo esta llamada hace que el Diagnostic Manager (DM) reenvíe las solicitudes SOVD entrantes a los métodos controladores registrados. Antes de destruir el objeto controlador, el servicio debe darse de baja a través de StopOffer() para evitar que se sigan reenviando solicitudes ([SWS_DM_01925]). El desmantelamiento concluye mediante el destructor virtual ~SovdSwUpdate() ([SWS_DM_01911]).

Ruta de uso

El flujo operativo típico comprende varias fases sucesivas de una actualización de software:

  1. Oferta del servicio: la aplicación instancia su derivación de SovdSwUpdate y llama a Offer() ([SWS_DM_01924]).
  2. Registro y transferencia de paquetes: el Diagnostic Server reenvía las solicitudes de registro entrantes de un cliente SOVD a RequestUpdatePackageRegistration() ([SWS_DM_01923]). El método devuelve un ara::core::Future con una tupla compuesta por una sesión de escritura (DataTransferWriteSession) y un identificador único de paquete (updatePackageId) ([SWS_DM_01923]). Interpretación: es de prever que la transferencia real de los datos útiles de la actualización se gestione a través de esta sesión de escritura proporcionada (AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»).
  3. Preparación del paquete: para preparar la instalación, el Diagnostic Server llama a PrepareUpdatePackage() ([SWS_DM_01800], [SWS_DM_01919]). De forma alternativa, se puede iniciar una instalación automatizada a través de PutUpdatePackageAutomated() ([SWS_DM_01799], [SWS_DM_01918]).
  4. Ejecución del paquete: la instalación del paquete de actualización preparado se inicia mediante la llamada a ExecuteUpdatePackage() ([SWS_DM_01801], [SWS_DM_01920]).
  5. Consulta de estado e inspección: durante o después del proceso, se pueden consultar informaciones detalladas y el estado a través de GetUpdatePackageStatus() ([SWS_DM_01802], [SWS_DM_01921]), GetUpdatePackageDetails() ([SWS_DM_01917]) o la lista completa mediante GetAllUpdates() ([SWS_DM_01797], [SWS_DM_01916]). Los paquetes que ya no sean necesarios se eliminan a través de DeleteUpdatePackage() ([SWS_DM_01922]).

Diagrama de secuencia: patrones de interacción para el registro, la instalación y la consulta de estado de un paquete de actualización. Fuentes: [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01802], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01923], [SWS_DM_01924]

Escenarios de error

Las condiciones de error se dividen en errores de configuración y de modelado, errores de estado del servicio y errores de ejecución específicos del protocolo:

  • Errores de modelo y de instanciación: si falla la resolución del InstanceSpecifier o si este hace referencia a un elemento inadecuado, se notifican violaciones específicas en tiempo de ejecución (Violations): InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, así como InstanceSpecifierAlreadyInUseViolation si el identificador ya se utiliza dentro del proceso ([SWS_DM_01910]).
  • Errores de oferta: la llamada a Offer() devuelve un ara::core::Result<void>. En caso de error, este contiene DiagOfferErrc::kAlreadyOffered si el servicio ya se está ofreciendo, o DiagOfferErrc::kConfigurationMismatch si la configuración no coincide con el extracto de diagnóstico (DEXT) ([SWS_DM_01924]).
  • Errores de ejecución y de protocolo: los métodos asíncronos de callback devuelven resultados como ara::core::Future. En caso de error, se debe consignar un código de error aplicable según ASAM SOVD 1.1 o ISO 17978-3 en el Future ([SWS_DM_01917], [SWS_DM_01918], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01922], [SWS_DM_01923]).
  • Tratamiento de cancelaciones: se pasa un CancellationHandler a todos los métodos asíncronos. La aplicación es responsable de consultarlo para finalizar de forma ordenada una conversación de cliente interrumpida prematuramente ([SWS_DM_01919], [SWS_DM_01920]).

<h4>Ciclo de vida</h4>
<p>La creación de una instancia específica de la aplicación se realiza a través del constructor parametrizado, indicando un identificador de instancia (<code>ara::core::InstanceSpecifier</code>) y el modelo de concurrencia deseado (<code>ConcurrencyType</code>) (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>). El <code>InstanceSpecifier</code> hace referencia a un <code>PortPrototype</code> declarado en el manifiesto de software, que debe estar tipificado a un <code>DiagnosticSovdUpdateInterface</code> (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>). A través del <code>concurrencyType</code> se determina si los métodos de callback de la instancia deben ser invocados de manera segura para subprocesos (<code>kConcurrent</code>) o de forma secuencial o no segura para subprocesos (<code>kNotConcurrent</code>) en caso de solicitudes simultáneas (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>).</p>
<p>Las instancias de <code>SovdSwUpdate</code> están vinculadas de forma biunívoca a un puerto de servicio. Por tanto, el constructor de copia y el operador de asignación están explícitamente eliminados (<code>=delete</code>) (<a class="spec-record-ref" data-req="SWS_DM_01912" href="../spec/record.html?id=SWS_DM_01912">[SWS_DM_01912]</a>, <a class="spec-record-ref" data-req="SWS_DM_01914" href="../spec/record.html?id=SWS_DM_01914">[SWS_DM_01914]</a>). Las operaciones de movimiento están definidas como protegidas (<code>protected</code>) (<a class="spec-record-ref" data-req="SWS_DM_01913" href="../spec/record.html?id=SWS_DM_01913">[SWS_DM_01913]</a>, <a class="spec-record-ref" data-req="SWS_DM_01915" href="../spec/record.html?id=SWS_DM_01915">[SWS_DM_01915]</a>).</p>
<p>Tras una inicialización correcta, la aplicación debe activar explícitamente el servicio mediante <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>). Solo esta llamada hace que el Diagnostic Manager (DM) reenvíe las solicitudes SOVD entrantes a los métodos controladores registrados. Antes de destruir el objeto controlador, el servicio debe darse de baja a través de <code>StopOffer()</code> para evitar que se sigan reenviando solicitudes (<a class="spec-record-ref" data-req="SWS_DM_01925" href="../spec/record.html?id=SWS_DM_01925">[SWS_DM_01925]</a>). El desmantelamiento concluye mediante el destructor virtual <code>~SovdSwUpdate()</code> (<a class="spec-record-ref" data-req="SWS_DM_01911" href="../spec/record.html?id=SWS_DM_01911">[SWS_DM_01911]</a>).</p>

<h4>Ruta de uso</h4>
<p>El flujo operativo típico comprende varias fases sucesivas de una actualización de software:</p>
<ol>
<li><strong>Oferta del servicio:</strong> la aplicación instancia su derivación de <code>SovdSwUpdate</code> y llama a <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>).</li>
<li><strong>Registro y transferencia de paquetes:</strong> el Diagnostic Server reenvía las solicitudes de registro entrantes de un cliente SOVD a <code>RequestUpdatePackageRegistration()</code> (<a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>). El método devuelve un <code>ara::core::Future</code> con una tupla compuesta por una sesión de escritura (<code>DataTransferWriteSession</code>) y un identificador único de paquete (<code>updatePackageId</code>) (<a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>). Interpretación: es de prever que la transferencia real de los datos útiles de la actualización se gestione a través de esta sesión de escritura proporcionada (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=223">AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»</a>).</li>
<li><strong>Preparación del paquete:</strong> para preparar la instalación, el Diagnostic Server llama a <code>PrepareUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01800" href="../spec/record.html?id=SWS_DM_01800">[SWS_DM_01800]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>). De forma alternativa, se puede iniciar una instalación automatizada a través de <code>PutUpdatePackageAutomated()</code> (<a class="spec-record-ref" data-req="SWS_DM_01799" href="../spec/record.html?id=SWS_DM_01799">[SWS_DM_01799]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>).</li>
<li><strong>Ejecución del paquete:</strong> la instalación del paquete de actualización preparado se inicia mediante la llamada a <code>ExecuteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01801" href="../spec/record.html?id=SWS_DM_01801">[SWS_DM_01801]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
<li><strong>Consulta de estado e inspección:</strong> durante o después del proceso, se pueden consultar informaciones detalladas y el estado a través de <code>GetUpdatePackageStatus()</code> (<a class="spec-record-ref" data-req="SWS_DM_01802" href="../spec/record.html?id=SWS_DM_01802">[SWS_DM_01802]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>), <code>GetUpdatePackageDetails()</code> (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>) o la lista completa mediante <code>GetAllUpdates()</code> (<a class="spec-record-ref" data-req="SWS_DM_01797" href="../spec/record.html?id=SWS_DM_01797">[SWS_DM_01797]</a>, <a class="spec-record-ref" data-req="SWS_DM_01916" href="../spec/record.html?id=SWS_DM_01916">[SWS_DM_01916]</a>). Los paquetes que ya no sean necesarios se eliminan a través de <code>DeleteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>).</li>
</ol>

<h4>Escenarios de error</h4>
<p>Las condiciones de error se dividen en errores de configuración y de modelado, errores de estado del servicio y errores de ejecución específicos del protocolo:</p>
<ul>
<li><strong>Errores de modelo y de instanciación:</strong> si falla la resolución del <code>InstanceSpecifier</code> o si este hace referencia a un elemento inadecuado, se notifican violaciones específicas en tiempo de ejecución (Violations): <code>InstanceSpecifierMappingIntegrityViolation</code>, <code>PortInterfaceMappingViolation</code>, <code>ProcessMappingViolation</code>, así como <code>InstanceSpecifierAlreadyInUseViolation</code> si el identificador ya se utiliza dentro del proceso (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>).</li>
<li><strong>Errores de oferta:</strong> la llamada a <code>Offer()</code> devuelve un <code>ara::core::Result&lt;void&gt;</code>. En caso de error, este contiene <code>DiagOfferErrc::kAlreadyOffered</code> si el servicio ya se está ofreciendo, o <code>DiagOfferErrc::kConfigurationMismatch</code> si la configuración no coincide con el extracto de diagnóstico (DEXT) (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>).</li>
<li><strong>Errores de ejecución y de protocolo:</strong> los métodos asíncronos de callback devuelven resultados como <code>ara::core::Future</code>. En caso de error, se debe consignar un código de error aplicable según ASAM SOVD 1.1 o ISO 17978-3 en el Future (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>, <a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>, <a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>).</li>
<li><strong>Tratamiento de cancelaciones:</strong> se pasa un <code>CancellationHandler</code> a todos los métodos asíncronos. La aplicación es responsable de consultarlo para finalizar de forma ordenada una conversación de cliente interrumpida prematuramente (<a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
</ul>
