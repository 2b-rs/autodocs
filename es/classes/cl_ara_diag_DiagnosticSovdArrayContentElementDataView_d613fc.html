Proporciona acceso tipificado de lectura y escritura a elementos de array de datos de diagnóstico SOVD mediante índices e iteradores.

La clase proporciona una interfaz estructurada para el acceso aleatorio e iterador a elementos de datos de diagnóstico basados en arrays de la Adaptive Platform ([SWS_DM_02227]). Permite a las aplicaciones anexar dinámicamente valores de datos primitivos y elementos de contenido complejos, así como reservar capacidad de memoria de forma preventiva. En caso de tipos de datos incompatibles, accesos por índice no válidos o estados de error establecidos explícitamente, los códigos de error se propagan al llamador mediante tipos Result ([SWS_DM_02228]). Según el estándar, todas las operaciones especificadas están implementadas de forma totalmente segura frente a excepciones y segura para subprocesos.

Contexto

La clase ara::diag::DiagnosticSovdArrayContentElementDataView está definida en AUTOSAR_AP_SWS_Diagnostics §8.60.5 «Class: DiagnosticSovdArrayContentElementDataView» bajo [SWS_DM_02227]. En el módulo de diagnóstico de AUTOSAR Adaptive, sirve como una vista tipificada de un elemento de contenido de diagnóstico (DiagnosticSovdContentElementData) con el tipo subyacente ArrayContentElementData. La declaración se realiza a través de la cabecera ara/diag/diagnostic_sovd_content_element_data.h.

Su responsabilidad principal radica en el encapsulamiento estructurado de operaciones de array para Service-Oriented Vehicle Diagnostics (SOVD). Actúan como interlocutores las aplicaciones de diagnóstico llamadoras que procesan o proporcionan estructuras de datos SOVD, así como los contenedores de datos genéricos subyacentes. El acceso a los elementos individuales del array se gestiona mediante iteradores dedicados o mediante operadores de índice tipificados.

Ciclo de vida

Como objeto de vista, es probable que la instancia no posea la propiedad exclusiva de los datos útiles reales, sino que se vincula a la memoria de un DiagnosticSovdContentElementData existente. El ciclo de vida de los datos pasa por las siguientes fases:

  • Reserva de memoria y capacidad: antes de insertar volúmenes de datos mayores, se puede definir preventivamente la capacidad de memoria interna mediante Reserve ([SWS_DM_02240]). La capacidad actual se puede determinar mediante Capacity ([SWS_DM_02231]).
  • Llenado: los nuevos elementos se anexan de forma secuencial a través de sobrecargas de PushBack. Se admiten tipos de datos primitivos como std::int64_t ([SWS_DM_02241]), std::uint64_t ([SWS_DM_02242]), double ([SWS_DM_02243]), bool ([SWS_DM_02244]) y ara::core::StringView ([SWS_DM_02245]), así como instancias anidadas de DiagnosticSovdContentElementData ([SWS_DM_02246]).
  • Inspección y limpieza: el estado de ocupación se puede consultar en cualquier momento mediante Size ([SWS_DM_02230]) y Empty ([SWS_DM_02232]). Los elementos individuales se pueden eliminar por iterador mediante Erase ([SWS_DM_02247]), mientras que Clear ([SWS_DM_02233]) restablece el array completo.

En cuanto a la concurrencia y el comportamiento ante excepciones, todas las funciones miembro de la clase están diseñadas según la especificación como seguras contra excepciones (declaradas con noexcept) y seguras para subprocesos («thread-safe»).

Ruta de uso

Una ruta de uso típica abarca la reserva preparatoria de capacidad, el llenado gradual de datos, la lectura de los elementos y la validación final en busca de estados de error:

  1. Reservar capacidad: la aplicación invoca Reserve para minimizar las reasignaciones dinámicas en accesos de escritura posteriores ([SWS_DM_02240]).
  2. Insertar elementos: los registros de datos se anexan mediante PushBack ([SWS_DM_02241]).
  3. Leer o recorrer elementos: el acceso se realiza de forma aleatoria mediante operator[] ([SWS_DM_02234], [SWS_DM_02235]) o secuencialmente mediante iteradores a través de Begin/End ([SWS_DM_02236], [SWS_DM_02237]) o bien CBegin/CEnd ([SWS_DM_02238], [SWS_DM_02239]).
  4. Comprobar estado: tras finalizar las operaciones, la aplicación comprueba mediante HasError si el contenido del array ha permanecido libre de errores ([SWS_DM_02228]).

Diagrama de secuencia: flujo típico para el llenado, indexación y comprobación de errores de un elemento de array SOVD. Fuentes: [SWS_DM_02240], [SWS_DM_02241], [SWS_DM_02234], [SWS_DM_02228].

Escenarios de error

Los métodos con potencial de error utilizan ara::core::Result para notificar condiciones previas defectuosas o interrupciones de ejecución en lugar de excepciones de C++:

  • Incongruencia de tipos: operaciones como PushBack ([SWS_DM_02241]) o operator[] ([SWS_DM_02234]) presuponen que el elemento encapsulado sea efectivamente del tipo ArrayContentElementData. En caso contrario, devuelven el error correspondiente en el objeto Result. Con PushBack, el tipo insertado debe coincidir además con el tipo de datos establecido en el constructor del elemento de array.
  • Borrado fallido: la llamada a Erase ([SWS_DM_02247]) devuelve un error en el Result si el destino no es del tipo ArrayContentElementData o si no se pudo eliminar el elemento a través del iterador especificado.
  • Estados de error explícitos: mediante SetError ([SWS_DM_02229]) se puede asignar un ara::core::ErrorCode al contenido del array. Si el contenido se marca de este modo como erróneo, la consulta HasError ([SWS_DM_02228]) devuelve el código de error como ara::diag::DiagSovdErrc.

                  Tratamiento de errores y condiciones límite

Dado que no se señalan errores, el cumplimiento de este tipo debería estar garantizado por la clase de vista ya en tiempo de construcción.

                  La especificación clasifica expresamente el método como seguro para subprocesos (thread-safe) ([SWS_DM_02233]). Por lo tanto, las llamadas a Clear se pueden realizar de forma concurrente desde varios subprocesos sin sincronización externa.
