Contexto

La clase ara::diag::DiagnosticSovdArrayContentElementDataView define una vista estructurada de las estructuras de datos de tipo ArrayContentElementData dentro de un DiagnosticSovdContentElementData [SWS_DM_02227] AUTOSAR_AP_SWS_Diagnostics §8.60.5 p. 776 superior. En el marco de Service-Oriented Vehicle Diagnostics (SOVD) de AUTOSAR Adaptive Platform, esta abstracción de vista permite a las aplicaciones de diagnóstico y componentes de servidor la manipulación con seguridad de tipos, el llenado y la evaluación de estructuras de array sin necesidad de analizar manualmente la representación de datos genérica subyacente.

Como interfaz de interacción, la vista encapsula operaciones para listas heterogéneas y homogéneas. Permite añadir tipos de datos elementales como valores enteros (std::int64_t, std::uint64_t), números de coma flotante (double), valores booleanos (bool) y estructuras de texto (ara::core::StringView), así como instancias de DiagnosticSovdContentElementData incrustadas [SWS_DM_02241] [SWS_DM_02242] [SWS_DM_02243] [SWS_DM_02244] [SWS_DM_02245] [SWS_DM_02246]. De este modo, la clase actúa como nexo central entre la representación interna de modelos de datos relevantes para el diagnóstico y las funciones de aplicación del módulo diag.

Ciclo de vida

La clase sigue la semántica de una envoltura sin propiedad (Interpretación: como vista, por lo general no posee los datos gestionados en sí misma, sino que hace referencia a un objeto DiagnosticSovdContentElementData existente). La validez de la vista está ligada a la vida útil del elemento de datos subyacente. Todas las funciones de elementos están declaradas según la especificación como noexcept y garantizan tanto seguridad frente a excepciones como seguridad para subprocesos [SWS_DM_02230] [SWS_DM_02231] AUTOSAR_AP_SWS_Diagnostics §8.60.5.1 p. 777.

En cuanto a la gestión interna de memoria y ciclo de vida, la clase admite reservas preparatorias de memoria: mediante Reserve se puede definir la capacidad objetivo de la estructura de array [SWS_DM_02240]. Las nuevas entradas se añaden a través de los métodos sobrecargados PushBack. Mediante Erase se pueden eliminar elementos individuales de forma selectiva [SWS_DM_02247], mientras que Clear libera todos los elementos contenidos y restablece el array [SWS_DM_02233].

Ruta de uso

Un caso de uso típico comprende la provisión de capacidad, la adición de elementos, la lectura mediante índice o iterador, así como la verificación del estado de consistencia:

  1. Comprobación de capacidad y preparación: antes de la inserción, la aplicación puede comprobar mediante Empty si hay datos presentes [SWS_DM_02232], consultar el tamaño existente a través de Size [SWS_DM_02230] e inspeccionar el búfer mediante Capacity [SWS_DM_02231]. La asignación se realiza mediante Reserve [SWS_DM_02240].
  2. Inserción de datos: la aplicación utiliza PushBack para añadir tipos de datos primitivos o nodos DiagnosticSovdContentElementData completos [SWS_DM_02241] [SWS_DM_02246].
  3. Acceso indexado e iteración: los elementos se pueden direccionar directamente de forma aleatoria mediante operator[]. Tanto la variante modificadora [SWS_DM_02234] como la variante constante [SWS_DM_02235] devuelven una referencia std::reference_wrapper dentro de un ara::core::Result. Para recorridos secuenciales, se dispone de iteradores compatibles con STL a través de Begin [SWS_DM_02236], End [SWS_DM_02237], así como de sus homólogos constantes CBegin [SWS_DM_02238] y CEnd [SWS_DM_02239] AUTOSAR_AP_SWS_Diagnostics §8.60.5.1 p. 778.
  4. Validación: la aplicación comprueba el estado de error del elemento mediante HasError [SWS_DM_02228].

Diagrama de secuencia: secuencia de llamadas para la configuración, el llenado, la indexación y la validación de un elemento de array SOVD. Fuentes: [SWS_DM_02240], [SWS_DM_02241], [SWS_DM_02234], [SWS_DM_02228].

Escenarios de error

Las condiciones de error se representan de manera consistente en la interfaz mediante el tipo de retorno ara::core::Result:

  • Incongruencia de tipos: casi todas las funciones de manipulación y consulta exigen como condición previa que el DiagnosticSovdContentElementData subyacente sea efectivamente de tipo ArrayContentElementData (Interpretación: una tipificación incorrecta se valida en tiempo de ejecución). Si esta comprobación falla, métodos como PushBack [SWS_DM_02241] o operator[] [SWS_DM_02234] devuelven un resultado de error en ara::core::Result.
  • Fallo al eliminar: la llamada a Erase requiere un iterador válido a un elemento contenido. Si el elemento no se puede eliminar o si el tipo de nodo es incorrecto, el error se señaliza en el valor de retorno [SWS_DM_02247].
  • Estados de error explícitos: un elemento de array se puede declarar activamente como erróneo asignando un ara::core::ErrorCode correspondiente mediante SetError [SWS_DM_02229]. Las entidades invocadoras determinan la existencia de dicho error a través de HasError, que devuelve el tipo ara::diag::DiagSovdErrc como valor de error cuando se ha establecido un código de error [SWS_DM_02228].

Esta guía se basa en la especificación AUTOSAR Adaptive Platform R25-11 (módulo diag) y resume los aspectos de arquitectura, ciclo de vida y uso de la clase DiagnosticSovdArrayContentElementDataView.
