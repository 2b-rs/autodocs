Contexto

La clase apext::tsync::TsyncFvmErrorDomain representa el dominio de error del Freshness Value Manager (FVM) dentro del módulo de sincronización de tiempo (tsync) de la AUTOSAR Adaptive Platform. Como especialización de la clase base estandarizada ara::core::ErrorDomain, integra las causas de error específicas del FVM en el marco uniforme de tratamiento de errores adaptativo.

Para el tipado y el tratamiento estructurado de errores, la clase proporciona dos alias de tipo centrales:

  • Errc: Alias para la enumeración de códigos de error TsyncFvmErrc ([SWS_TS_14206]), que representa las distintas causas de error del FVM.
  • Exception: Alias para la clase base de excepción correspondiente TsyncFvmException ([SWS_TS_14207]), que se lanza en caso de excepción.

Entre los interlocutores típicos se encuentran los componentes del FVM del módulo tsync, que encapsulan los errores ocurridos como ara::core::ErrorCode, así como los servicios de aplicación de nivel superior que diagnostican, registran o capturan estados de error mediante excepciones.

Ciclo de vida

La instanciación de TsyncFvmErrorDomain se realiza a través del constructor sin parámetros TsyncFvmErrorDomain() ([SWS_TS_14208]). Dado que este se especifica como constexpr y noexcept, el objeto de dominio de error puede crearse ya en tiempo de compilación. Presumiblemente, la clase se opera dentro de la plataforma como una instancia singleton global o estática de larga duración, ya que los dominios de error funcionan sin estado y son referenciados en todo el módulo por todos los códigos de error.

La liberación de la instancia queda garantizada por el destructor virtual predeterminado ~TsyncFvmErrorDomain() ([SWS_TS_14201]), que está declarado como noexcept=default y permite una destrucción polimórfica segura mediante punteros a la clase base ara::core::ErrorDomain.

Todas las operaciones de la clase —incluidos el constructor ([SWS_TS_14208]), la consulta de nombre ([SWS_TS_14209]), la resolución de mensajes ([SWS_TS_14210]) y la generación de excepciones ([SWS_TS_14211])— están designadas explícitamente como seguras para subprocesos (thread-safe). Dado que la clase no posee estados mutables, varios subprocesos pueden acceder en paralelo a la misma instancia de dominio.

Ruta de uso

Un flujo típico en el tratamiento de errores del Freshness Value Manager incluye la asignación, la evaluación textual y, en caso necesario, el lanzamiento de una excepción de C++:

  1. Identificación del dominio: El invocador o el sistema de diagnóstico identifica el dominio de error a través del método Name() ([SWS_TS_14209]), que proporciona una constante de cadena basada en punteros (const char*) del dominio.
  2. Consulta de mensajes: Mediante Message() ([SWS_TS_14210]) se recupera la descripción textual de un código de error específico (errorCode). Es probable que el código numérico transmitido se corresponda con los valores de la enumeración TsyncFvmErrc (alias de tipo Errc, [SWS_TS_14206]).
  3. Escalación a excepción: En caso de que se deba convertir un error en una excepción, se llama a ThrowAsException() ([SWS_TS_14211]). Este método instancia un objeto de la clase apext::tsync::TsyncFvmException (alias de tipo Exception, [SWS_TS_14207]) basándose en el ara::core::ErrorCode proporcionado y lo lanza.

Diagrama de secuencia: Secuencia típica de consulta de nombre, resolución de mensajes y lanzamiento de excepciones. Fuentes: [SWS_TS_14209], [SWS_TS_14210], [SWS_TS_14211]

Escenarios de error

Al utilizar la interfaz, deben tenerse en cuenta las distintas garantías relativas a la seguridad frente a excepciones, así como las particularidades de la cadena de herramientas:

  • Ausencia garantizada de excepciones: Los métodos Name() ([SWS_TS_14209]) y Message() ([SWS_TS_14210]), así como el constructor ([SWS_TS_14208]) y el destructor ([SWS_TS_14201]), están definidos como noexcept y exception safe. Quienes realizan las llamadas pueden confiar en que las consultas de nombres de dominio y mensajes de texto son a prueba de fallos.
  • Escalación no segura frente a excepciones: Según la especificación, la función ThrowAsException() ([SWS_TS_14211]) está clasificada como noexcept(false) y not exception safe, ya que lanza de manera deliberada una excepción del tipo apext::tsync::TsyncFvmException. Quien realiza la llamada debe garantizar un tratamiento adecuado en un nivel superior.
  • Comportamiento con excepciones de C++ desactivadas: Si las excepciones de C++ están desactivadas en el compilador, ThrowAsException() no participa en la resolución de sobrecargas de acuerdo con la especificación ([SWS_TS_14211]). Una llamada en una configuración de compilación libre de excepciones provoca un error de compilación; en tales entornos, la comprobación de errores debe realizarse de forma puramente basada en valores a través de códigos de error.

Esta guía se basa exclusivamente en los requisitos de especificación del release R25-11 de AUTOSAR.
