Contexto

La estructura ara::diag::GenericUDSService::OperationOutput representa, dentro del clúster funcional diag de la AUTOSAR Adaptive Platform, el contenedor de datos de respuesta estandarizado para respuestas positivas de servicio UDS. En la implementación de servicios UDS genéricos (definidos en la cabecera ara/diag/generic_uds_service.h), esta estructura sirve como elemento de interfaz entre la aplicación de servicio y el entorno de ejecución de diagnóstico. La especificación define OperationOutput como estructura de datos para los datos útiles de un mensaje de respuesta positiva («Response data of positive respose message»).

El elemento central de la estructura es el miembro público responseData de tipo ara::core::Vector<std::uint8_t> [SWS_DM_00632]. Este vector de bytes acoge los datos de respuesta de diagnóstico. Una directriz esencial de la especificación establece que los datos en responseData deben proporcionarse expresamente sin el identificador de servicio (SID) («without SID») [SWS_DM_00632] AUTOSAR_AP_SWS_Diagnostics p. 81. La responsabilidad del ID de servicio positivo antepuesto permanece, por tanto, en el componente de plataforma ara::diag. En la colaboración global participan tres componentes: el tester de diagnóstico externo, el middleware ara::diag y la implementación concreta del servicio.

Diagrama de secuencia: flujo de interacción durante la provisión de datos de respuesta a través de OperationOutput. Fuentes: [SWS_DM_00632], AUTOSAR_AP_SWS_Diagnostics p. 81

Ciclo de vida

Como estructura de datos pura (struct), OperationOutput no posee estados internos ni una máquina de estados compleja. La instanciación se realiza según demanda en el contexto de ejecución de la aplicación de servicio tan pronto como se ha recibido y procesado con éxito una solicitud UDS. La creación tiene lugar típicamente en la pila o en la memoria libre del hilo que realiza el procesamiento.

En cuanto a las relaciones de propiedad, la instancia es creada inicialmente por la aplicación de servicio y rellenada con los bytes de respuesta. Mediante el uso de ara::core::Vector<std::uint8_t> para responseData [SWS_DM_00632], la estructura se beneficia de las semánticas de movimiento de C++. Al devolverse a la plataforma ara::diag, el objeto puede transferirse por movimiento, evitándose así asignaciones costosas y duplicaciones de memoria.

Con respecto a la concurrencia, el objeto no está diseñado para ser seguro para hilos; para un objeto de transferencia puro esto tampoco está previsto. El acceso se realiza de manera síncrona dentro del procesador de servicio. Tras la transferencia al Diagnostic Management, la propiedad pasa a la plataforma, la cual envía los bytes serializados a través del protocolo de transporte. A continuación, el objeto se destruye, con lo cual la memoria dinámica del vector se libera automáticamente según RAII.

Ruta de uso

El flujo regular durante el uso de OperationOutput comprende los siguientes pasos:

  1. Recepción de solicitud: un tester de diagnóstico externo envía una solicitud de servicio UDS. La infraestructura de diagnóstico ara::diag recibe el telegrama y delega la llamada en el manejador GenericUDSService competente de la aplicación.
  2. Procesamiento: la aplicación de servicio decodifica la carga útil de UDS y ejecuta la operación de diagnóstico solicitada.
  3. Creación del objeto de respuesta: tras la ejecución correcta, la aplicación crea una instancia de OperationOutput.
  4. Relleno de los datos de respuesta: los parámetros que se deben devolver se escriben en el elemento vectorial responseData [SWS_DM_00632]. En este punto debe procurarse estrictamente no insertar ningún SID, ya que responseData, por definición, solo comprende el contenido sin SID [SWS_DM_00632].
  5. Transferencia al Diagnostic Management: la aplicación transfiere el objeto rellenado a ara::diag. Es de suponer que esto ocurra encapsulado en un tipo de resultado del núcleo como ara::core::Result.
  6. Envío de la respuesta positiva: Interpretación: dado que responseData exige el contenido explícitamente sin SID, es de suponer que la plataforma ara::diag anteponga automáticamente el SID de respuesta positiva conforme a UDS (SID de solicitud + 0x40) y transmita el telegrama UDS al tester de diagnóstico.

Escenarios de error

La estructura OperationOutput está especificada de forma específica exclusivamente para mensajes de respuesta positiva («positive respose message»). De ello se derivan condiciones previas concretas para su uso: la estructura solo debe instanciarse y devolverse si el procesamiento de UDS ha finalizado sin errores.

Si el procesamiento de la solicitud UDS falla —por ejemplo, debido a parámetros no permitidos, niveles de seguridad insuficientes o errores internos de procesamiento—, no se debe transmitir ningún OperationOutput regular al Diagnostic Management. En este caso, es de suponer que la aplicación notifique en su lugar un código de error de UDS correspondiente (Negative Response Code, NRC) a través de las interfaces de error de la plataforma. De esta manera, la plataforma se asegura de transmitir al tester una respuesta UDS negativa (telegrama NRC con SID 0x7F) en lugar de emitir datos útiles erróneos.

Además, se debe prestar atención a los límites de búfer y de transporte: si bien responseData gestiona memoria dinámica como vector [SWS_DM_00632], el telegrama UDS resultante está sujeto a los tamaños máximos de paquete del protocolo de transporte configurado (como DoIP o ISO-TP). Superar estos límites podría dar lugar a errores de tiempo de ejecución durante la transmisión por parte de la plataforma.
