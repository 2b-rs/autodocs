Contexto

La clase ara::diag::MultipleCondition ([SWS_DM_01730]) proporciona en el módulo diag de AUTOSAR Adaptive Platform una interfaz agrupada para la gestión de múltiples condiciones de diagnóstico (Diagnostic Conditions). Mientras que las condiciones individuales se representan habitualmente a través de la clase ara::diag::Condition, ara::diag::MultipleCondition permite el control y la consulta de varias condiciones a través de una interfaz de puerto común (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»).

Desde el punto de vista funcional, ambas interfaces poseen la misma semántica y ofrecen operaciones similares (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»). La diferencia esencial radica en que, en ara::diag::MultipleCondition, cada operación recibe un identificador adicional del tipo ConditionHandleType ([SWS_DM_01728], [SWS_DM_01729]).

Los interlocutores principales de la clase comprenden:

  • Adaptive Application: instancia la clase y controla los estados de las condiciones asignadas mediante SetCondition o los lee a través de GetCondition ([SWS_DM_01728], [SWS_DM_01729]).
  • Diagnostic Management (DM): actúa como subsistema de la plataforma, procesa los cambios de estado y suministra la información de las condiciones para los flujos de diagnóstico ([SWS_DM_01728]).
  • Modelado de manifiesto: cada DiagnosticCondition definida en el sistema requiere un mapeo a través de un DiagnosticMultipleConditionPortMapping para determinar que la interfaz de condición múltiple puede utilizarse para esta condición (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»). El PortPrototype asignado debe estar tipado obligatoriamente mediante un DiagnosticMultipleConditionInterface ([SWS_DM_01727]).

Diagrama de contexto: integración de ara::diag::MultipleCondition e interacción con la aplicación, el modelado y Diagnostic Management. Fuentes: [SWS_DM_01727], [SWS_DM_01730], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»

Ciclo de vida

La creación de una instancia se realiza a través del constructor explícito MultipleCondition(const ara::core::InstanceSpecifier &specifier) ([SWS_DM_01727]). En la instanciación, el objeto se vincula al PortPrototype referenciado por el InstanceSpecifier. El constructor está especificado como seguro frente a excepciones (exception safe) y seguro para subprocesos (thread-safe) ([SWS_DM_01727]).

En cuanto a la propiedad y transferibilidad, la clase está estrictamente ligada a su lugar de creación:

  • El constructor de copia está eliminado: MultipleCondition(MultipleCondition &) = delete ([SWS_DM_02072]).
  • El operador de asignación de copia está eliminado: operator=(MultipleCondition &) = delete ([SWS_DM_02073]).
  • El constructor de movimiento está eliminado: MultipleCondition(MultipleCondition &&) noexcept = delete ([SWS_DM_02071]).
  • El operador de asignación de movimiento está eliminado: operator=(MultipleCondition &&) = delete ([SWS_DM_02074]).

Por lo tanto, las instancias de ara::diag::MultipleCondition no se pueden copiar ni mover (pinned object). Deben permanecer en una dirección de memoria fija durante todo su periodo de uso.

La destrucción se realiza a través del destructor ~MultipleCondition() noexcept ([SWS_DM_01737]). Este es seguro frente a excepciones, pero está declarado explícitamente como not thread-safe ([SWS_DM_01737]). Por lo tanto, la aplicación que realiza la llamada debe garantizar que no se produzcan accesos concurrentes al objeto durante el proceso de destrucción.

Para la seguridad para subprocesos de las operaciones en curso (GetCondition y SetCondition) se aplica una sincronización condicional (conditional thread-safety): el hecho de que los métodos deban implementarse como seguros o no seguros para subprocesos viene determinado por el ConcurrencyType ([SWS_DM_01728], [SWS_DM_01729]). Interpretación: dado que el constructor de C++ en [SWS_DM_01727] no presenta ningún argumento ConcurrencyType, es probable que esta propiedad se configure en el diseño de software a través del modelo de puerto y se evalúe mediante el InstanceSpecifier.

Ruta de uso

El flujo típico para el uso de ara::diag::MultipleCondition se divide en las fases de instanciación, identificación de la condición individual y ejecución de operaciones de lectura y escritura:

  1. Instanciación y vinculación de puertos: la aplicación instancia MultipleCondition indicando el InstanceSpecifier adecuado ([SWS_DM_01727]).
  2. Direccionamiento de condiciones mediante handles: las condiciones individuales se direccionan mediante valores numéricos del tipo ConditionHandleType ([SWS_DM_01735]). A menos que se defina un DiagnosticMultipleConditionPortMapping.overrideId en el modelo, el Diagnostic Manager asigna handles en orden alfabético según el nombre corto de DiagnosticCondition, comenzando en 0x010000 (AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»).
  3. Establecer estado (SetCondition): la aplicación actualiza el estado de una condición de forma síncrona a través de SetCondition(conditionHandle, condition) ([SWS_DM_01729]). La llamada devuelve un ara::core::Result<void> que informa sobre el éxito o el fallo.
  4. Consultar estado (GetCondition): para leer el estado actual, la aplicación llama a GetCondition(conditionHandle) ([SWS_DM_01728]). La llamada devuelve un ara::core::Future<ConditionType>. A continuación, la aplicación puede resolver y evaluar el resultado de forma asíncrona.

Diagrama de secuencia: orden típico de llamadas para la gestión y consulta de condiciones mediante ara::diag::MultipleCondition. Fuentes: [SWS_DM_01727], [SWS_DM_01728], [SWS_DM_01729], AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»

Escenarios de error

Los casos de error al trabajar con ara::diag::MultipleCondition se dividen en infracciones de configuración y modelado durante la instanciación, así como errores en tiempo de ejecución en llamadas a métodos:

  • Errores de inicialización (Violations) ([SWS_DM_01727]):
    • InstanceSpecifierMappingIntegrityViolation: El InstanceSpecifier no se puede resolver en el contexto de modelo del Executable o hace referencia a un elemento de modelo que no es un PortPrototype.
    • PortInterfaceMappingViolation: El PortPrototype referenciado no está tipado conforme al tipo mediante un DiagnosticMultipleConditionInterface.
    • ProcessMappingViolation: Existe una InstanceRef coincidente en el modelo, pero no existe ningún proceso modelado adecuado para el proceso actual en tiempo de ejecución.
    • InstanceSpecifierAlreadyInUseViolation: El constructor se llamó con un InstanceSpecifier que ya está ocupado por otra instancia dentro del proceso actual.
  • Errores en tiempo de ejecución en SetCondition ([SWS_DM_01729]):
    • DiagErrc::kInvalidArgument: Señaliza argumentos no válidos (semántica de reversión, p. ej., en kPreFailed con debouncing interno).
  • Errores en tiempo de ejecución en GetCondition ([SWS_DM_01728]):
    • DiagErrc::kInvalidArgument: El conditionHandle especificado no es válido (semántica de reversión).
    • DiagErrc::kServiceNotAvailable: La llamada no se puede ejecutar porque la funcionalidad esencial de Diagnostic Management no está disponible actualmente (semántica de reversión).

<h4>Contexto</h4>
<p>La clase <code>ara::diag::MultipleCondition</code> (<a class="spec-record-ref" data-req="SWS_DM_01730" href="../spec/record.html?id=SWS_DM_01730">[SWS_DM_01730]</a>) proporciona en el módulo <em>diag</em> de AUTOSAR Adaptive Platform una interfaz agrupada para la gestión de múltiples condiciones de diagnóstico (Diagnostic Conditions). Mientras que las condiciones individuales se representan habitualmente a través de la clase <code>ara::diag::Condition</code>, <code>ara::diag::MultipleCondition</code> permite el control y la consulta de varias condiciones a través de una interfaz de puerto común (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>).</p>
<p>Desde el punto de vista funcional, ambas interfaces poseen la misma semántica y ofrecen operaciones similares (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>). La diferencia esencial radica en que, en <code>ara::diag::MultipleCondition</code>, cada operación recibe un identificador adicional del tipo <code>ConditionHandleType</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>).</p>
<p>Los interlocutores principales de la clase comprenden:</p>
<ul>
<li><strong>Adaptive Application</strong>: instancia la clase y controla los estados de las condiciones asignadas mediante <code>SetCondition</code> o los lee a través de <code>GetCondition</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>).</li>
<li><strong>Diagnostic Management (DM)</strong>: actúa como subsistema de la plataforma, procesa los cambios de estado y suministra la información de las condiciones para los flujos de diagnóstico (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>).</li>
<li><strong>Modelado de manifiesto</strong>: cada <code>DiagnosticCondition</code> definida en el sistema requiere un mapeo a través de un <code>DiagnosticMultipleConditionPortMapping</code> para determinar que la interfaz de condición múltiple puede utilizarse para esta condición (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>). El <code>PortPrototype</code> asignado debe estar tipado obligatoriamente mediante un <code>DiagnosticMultipleConditionInterface</code> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</li>
</ul>

<h4>Ciclo de vida</h4>
<p>La creación de una instancia se realiza a través del constructor explícito <code>MultipleCondition(const ara::core::InstanceSpecifier &amp;specifier)</code> (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>). En la instanciación, el objeto se vincula al <code>PortPrototype</code> referenciado por el <code>InstanceSpecifier</code>. El constructor está especificado como seguro frente a excepciones (<em>exception safe</em>) y seguro para subprocesos (<em>thread-safe</em>) (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</p>
<p>En cuanto a la propiedad y transferibilidad, la clase está estrictamente ligada a su lugar de creación:</p>
<ul>
<li>El constructor de copia está eliminado: <code>MultipleCondition(MultipleCondition &amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02072" href="../spec/record.html?id=SWS_DM_02072">[SWS_DM_02072]</a>).</li>
<li>El operador de asignación de copia está eliminado: <code>operator=(MultipleCondition &amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02073" href="../spec/record.html?id=SWS_DM_02073">[SWS_DM_02073]</a>).</li>
<li>El constructor de movimiento está eliminado: <code>MultipleCondition(MultipleCondition &amp;&amp;) noexcept = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02071" href="../spec/record.html?id=SWS_DM_02071">[SWS_DM_02071]</a>).</li>
<li>El operador de asignación de movimiento está eliminado: <code>operator=(MultipleCondition &amp;&amp;) = delete</code> (<a class="spec-record-ref" data-req="SWS_DM_02074" href="../spec/record.html?id=SWS_DM_02074">[SWS_DM_02074]</a>).</li>
</ul>
<p>Por lo tanto, las instancias de <code>ara::diag::MultipleCondition</code> no se pueden copiar ni mover (<em>pinned object</em>). Deben permanecer en una dirección de memoria fija durante todo su periodo de uso.</p>
<p>La destrucción se realiza a través del destructor <code>~MultipleCondition() noexcept</code> (<a class="spec-record-ref" data-req="SWS_DM_01737" href="../spec/record.html?id=SWS_DM_01737">[SWS_DM_01737]</a>). Este es seguro frente a excepciones, pero está declarado explícitamente como <em>not thread-safe</em> (<a class="spec-record-ref" data-req="SWS_DM_01737" href="../spec/record.html?id=SWS_DM_01737">[SWS_DM_01737]</a>). Por lo tanto, la aplicación que realiza la llamada debe garantizar que no se produzcan accesos concurrentes al objeto durante el proceso de destrucción.</p>
<p>Para la seguridad para subprocesos de las operaciones en curso (<code>GetCondition</code> y <code>SetCondition</code>) se aplica una sincronización condicional (<em>conditional thread-safety</em>): el hecho de que los métodos deban implementarse como seguros o no seguros para subprocesos viene determinado por el <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>, <a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>). Interpretación: dado que el constructor de C++ en <a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a> no presenta ningún argumento <code>ConcurrencyType</code>, es probable que esta propiedad se configure en el diseño de software a través del modelo de puerto y se evalúe mediante el <code>InstanceSpecifier</code>.</p>

<h4>Ruta de uso</h4>
<p>El flujo típico para el uso de <code>ara::diag::MultipleCondition</code> se divide en las fases de instanciación, identificación de la condición individual y ejecución de operaciones de lectura y escritura:</p>
<ol>
<li><strong>Instanciación y vinculación de puertos</strong>: la aplicación instancia <code>MultipleCondition</code> indicando el <code>InstanceSpecifier</code> adecuado (<a class="spec-record-ref" data-req="SWS_DM_01727" href="../spec/record.html?id=SWS_DM_01727">[SWS_DM_01727]</a>).</li>
<li><strong>Direccionamiento de condiciones mediante handles</strong>: las condiciones individuales se direccionan mediante valores numéricos del tipo <code>ConditionHandleType</code> (<a class="spec-record-ref" data-req="SWS_DM_01735" href="../spec/record.html?id=SWS_DM_01735">[SWS_DM_01735]</a>). A menos que se defina un <code>DiagnosticMultipleConditionPortMapping.overrideId</code> en el modelo, el Diagnostic Manager asigna handles en orden alfabético según el nombre corto de <code>DiagnosticCondition</code>, comenzando en <code>0x010000</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=237">AUTOSAR_AP_SWS_Diagnostics §[SWS_DM_01735] «MultipleCondition ConditionHandleType Generation»</a>).</li>
<li><strong>Establecer estado (SetCondition)</strong>: la aplicación actualiza el estado de una condición de forma síncrona a través de <code>SetCondition(conditionHandle, condition)</code> (<a class="spec-record-ref" data-req="SWS_DM_01729" href="../spec/record.html?id=SWS_DM_01729">[SWS_DM_01729]</a>). La llamada devuelve un <code>ara::core::Result&lt;void&gt;</code> que informa sobre el éxito o el fallo.</li>
<li><strong>Consultar estado (GetCondition)</strong>: para leer el estado actual, la aplicación llama a <code>GetCondition(conditionHandle)</code> (<a class="spec-record-ref" data-req="SWS_DM_01728" href="../spec/record.html?id=SWS_DM_01728">[SWS_DM_01728]</a>). La llamada devuelve un <code>ara::core::Future&lt;ConditionType&gt;</code>. A continuación, la aplicación puede resolver y evaluar el resultado de forma asíncrona.</li>
</ol>
