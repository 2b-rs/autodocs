Define el dominio de errores para errores de comprobación de la protección extremo a extremo en la comunicación de Adaptive.

La clase ara::com::e2e::ComE2EErrorDomain define el dominio de errores para fallos de la protección extremo a extremo en el Communication Management de AUTOSAR Adaptive y asigna códigos de error a la enumeración ComE2EErrc ([SWS_CM_12504]). Si falla una comprobación de E2E en el lado del servidor, se transporta un ara::core::ErrorCode de este dominio en la respuesta de error y se pone a disposición en el lado del cliente a través de ara::core::Result ([SWS_CM_00033]). La clase sin estado y segura frente a excepciones permite el tratamiento de errores, a elegir, basado en valores o a través de ThrowAsException(), no estando disponible este método de excepción cuando las excepciones del compilador de C++ están deshabilitadas ([SWS_CM_12509]).

Contexto

La clase ara::com::e2e::ComE2EErrorDomain define el dominio de error para la protección extremo a extremo (E2E) dentro del Communication Management (ara::com) de la AUTOSAR Adaptive Platform. Deriva de forma final de la clase base ara::core::ErrorDomain y encapsula errores específicos del dominio que se producen durante la validación de E2E de mensajes.

En el modelo de comunicación, ComE2EErrorDomain actúa como identificador y traductor central para estados de error en interacciones protegidas mediante E2E. A través de los alias de tipo Errc ([SWS_CM_12504]) y Exception ([SWS_CM_12505]), el dominio de errores vincula la enumeración específica del tipo ComE2EErrc y el tipo de excepción derivado ComE2EException al ecosistema específico de errores de ara::core. Si el entorno de ejecución del servidor detecta una protección defectuosa al comprobar una solicitud de método mediante E2E_check ([SWS_CM_90421]), se transmite una respuesta de error de E2E. Conforme a [SWS_CM_00033], la carga útil de este mensaje de respuesta transporta un ara::core::ErrorCode del dominio ara::com::e2e::ComE2EErrorDomain, cuyo valor de error se corresponde con el resultado de E2E_check (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.4 «Payload of the E2E Error Response»). En el lado del cliente, tras eliminar la cabecera de E2E ([SWS_CM_90475]), este error se deserializa ([SWS_CM_90476], [SWS_CM_10473]) y se entrega a la aplicación como estado de error dentro de un ara::core::Result (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5 «Deserializing the payload»).

Diagrama de contexto: Integración de ComE2EErrorDomain en el sistema de tipos de ara::core y ara::com. Fuentes: [SWS_CM_12504], [SWS_CM_12505], [SWS_CM_12506], [SWS_CM_00033].

Ciclo de vida

La creación de un objeto de instancia se realiza mediante el constructor por defecto constexpr ComE2EErrorDomain() noexcept ([SWS_CM_12506]). Gracias a la designación como constexpr, el dominio de errores puede construirse ya en tiempo de compilación. Típicamente debería proporcionarse como un singleton inmutable para todo el proceso, de modo que las referencias al dominio sigan siendo válidas durante todo el tiempo de ejecución del programa. Dado que la clase está declarada como final, no se permite ninguna derivación posterior.

La clase no gestiona ningún estado modificable y ofrece una seguridad total frente a excepciones ([SWS_CM_12506]). Los métodos de inspección Name() ([SWS_CM_12507]) y Message() ([SWS_CM_12508]) están declarados como const y noexcept. De este modo queda garantizado un acceso de lectura concurrente y seguro para subprocesos (thread-safe) a través de múltiples hilos de ejecución, libre de sobrecargas de sincronización.

Ruta de uso

La ruta de uso típica se desarrolla en el marco de la transmisión y de la evaluación en el lado del cliente de comprobaciones de E2E fallidas:

  1. Comprobación y generación de errores: Al recibir una solicitud protegida mediante E2E, el servidor realiza la validación mediante E2E_check ([SWS_CM_90421]). Si esta comprobación falla, el middleware serializa una respuesta de error cuya carga útil contiene un ara::core::ErrorCode con ara::com::e2e::ComE2EErrorDomain ([SWS_CM_00033]).
  2. Transmisión y deserialización: En el lado del cliente, tras el tratamiento del protocolo y la eliminación de la cabecera de protección ([SWS_CM_90475]), se deserializa la carga útil ([SWS_CM_90476]). El entorno de comunicación proporciona el resultado como ara::core::Result, el cual encapsula el código de error transmitido ([SWS_CM_10473], AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5 «Deserializing the payload»).
  3. Diagnóstico de errores: la Adaptive Application comprueba ara::core::Result. Para el registro de errores, Name() proporciona el identificador del dominio ([SWS_CM_12507]), mientras que Message() devuelve el texto legible para personas correspondiente al código numérico concreto ([SWS_CM_12508]).
  4. Tratamiento de errores: la aplicación puede evaluar el error basándose en su valor o, si el tratamiento de excepciones está habilitado, lanzar una excepción específica del tipo mediante ThrowAsException() ([SWS_CM_12509]).

Diagrama de secuencia: transmisión y procesamiento de un error de E2E durante una llamada a un método. Fuentes: [SWS_CM_00033], [SWS_CM_90421], [SWS_CM_90475], [SWS_CM_90476], [SWS_CM_10473], [SWS_CM_12509].

Escenarios de error

Si se produce un error de E2E durante la validación, este se identifica mediante la enumeración ComE2EErrc, la cual está disponible a través del alias de tipo Errc de la clase ([SWS_CM_12504]). Es probable que los códigos de error en ComE2EErrc se correspondan directamente con los valores de resultado definidos de E2E_check.

Para propagar el error mediante excepciones de C++, el método ThrowAsException() instancia una excepción del tipo ara::com::e2e::ComE2EException (alias Exception, [SWS_CM_12505]) y la lanza ([SWS_CM_12509]). El método está declarado como noexcept(false). Si las excepciones de C++ están deshabilitadas en la cadena de herramientas del compilador, ThrowAsException() no participa en la resolución de sobrecargas de conformidad con [SWS_CM_12509]. Por consiguiente, en sistemas sin soporte para excepciones, el tratamiento de errores debe realizarse obligatoriamente mediante la inspección basada en valores de ara::core::Result y ara::core::ErrorCode.

              Tratamiento de errores y condiciones límite
              

              El método está declarado con noexcept(false) y especificado explícitamente como no seguro frente a excepciones («not exception safe»), ya que su flujo regular consiste en lanzar la excepción. [SWS_CORE_10304] define una condición límite esencial por parte del compilador: si las excepciones de C++ están deshabilitadas en la cadena de herramientas del compilador, esta función no participa en la resolución de sobrecargas. Por lo tanto, los llamadores deben asegurarse de que el tratamiento de errores basado en excepciones esté soportado y activo en el sistema de destino.
              


              Interacción
              

              Interpretación: Al ser un método sobrescrito (override), la función probablemente forme parte del mecanismo polimórfico de dominios de error de AUTOSAR Adaptive para transformar códigos de error genéricos en objetos de excepción específicos. Se encuentran funciones análogas en los dominios de error relacionados de la gestión de comunicaciones: ComErrorDomain::ThrowAsException según [SWS_CM_11333] lanza una ara::com::ComException (AUTOSAR_AP_SWS_CommunicationManagement §8.12.4.2.2.3 «ThrowAsException»), mientras que ComSecOcFvmErrorDomain::ThrowAsException según [SWS_CM_12520] instancia y lanza una apext::com::secoc::ComSecOcFvmException (AUTOSAR_AP_SWS_CommunicationManagement §C.2.3.2.2.3 «ThrowAsException»).
