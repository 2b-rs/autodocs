Contexto

La clase ara::diag::DataTransferReadByPullHandler sirve para el procesamiento estandarizado de transferencias de datos de lectura iniciadas por solicitudes de diagnóstico como RequestReadFile o RequestReadDirectory AUTOSAR_AP_SWS_Diagnostics §8.10.2 «Class: DataTransferReadByPullHandler», [SWS_DM_01506]. Actúa como interfaz entre el framework de diagnóstico AraDiag y la implementación real de la aplicación.

El concepto de transmisión se basa en un mecanismo pull: AraDiag solicita secuencialmente bloques de datos de la implementación de la aplicación para transmitirlos posteriormente al cliente UDS (téster de diagnóstico) [SWS_DM_01513]. La clase encapsula así la provisión específica de la aplicación de contenidos de archivos o directorios en el contexto de los servicios de transferencia UDS.

Diagrama de contexto: Integración del handler entre el cliente UDS, el framework AraDiag y la aplicación. Fuentes: [SWS_DM_01506], AUTOSAR_AP_SWS_Diagnostics §8.10.2 «Class: DataTransferReadByPullHandler»

Ciclo de vida

Para las instancias de DataTransferReadByPullHandler se aplican reglas estrictas relativas a la creación, la propiedad y la destrucción:

  • Creación: El constructor por defecto está declarado como protected y noexcept=default [SWS_DM_01507]. Interpretación: Dado que la clase contiene métodos de interfaz puramente virtuales y el constructor por defecto está protegido, el software de aplicación debería implementar e instanciar su propia clase handler derivada.
  • Sin capacidad de copia: Tanto el constructor de copia [SWS_DM_01509] como el operador de asignación de copia [SWS_DM_01512] están explícitamente eliminados (=delete). Un handler está destinado exactamente a una única sesión de transferencia de archivos (single file transfer session) y no debe copiarse AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.2 «Constructors».
  • Capacidad de movimiento: El constructor de movimiento [SWS_DM_01508] y la asignación de movimiento [SWS_DM_01511] están definidos como noexcept=default AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1 «Special Member Functions», de modo que se admite la transferencia de propiedad.
  • Condición de destrucción: El destructor es virtual y está especificado como noexcept=default [SWS_DM_01510]. Como invariante central se aplica que una instancia no debe destruirse en ningún caso antes de que se haya llamado a ExitRead() [SWS_DM_01510], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1.2 «Destructor».
  • Concurrencia: Los métodos de interfaz virtuales Read() y ExitRead() están clasificados como no seguros para hilos (not thread-safe) [SWS_DM_01513], [SWS_DM_01514].

Ruta de uso

La secuencia típica de llamadas de una transferencia de datos de lectura basada en pull comprende dos fases principales:

  1. Bucle de lectura pull: Durante la transferencia en curso, AraDiag llama repetidamente al método Read() en el handler [SWS_DM_01513]. AraDiag pasa aquí una vista de memoria response_data (del tipo ara::core::Span<const ara::core::Byte>) a un búfer previamente asignado, así como meta_info y un cancellation_handler. La implementación de la aplicación compone el contenido del siguiente bloque de datos y lo copia hasta el tamaño máximo del span [SWS_DM_01513].
  2. Devolución del chunk: Read() devuelve un ara::core::Future<std::uint32_t>. El future se completa con el número de bytes realmente escritos en el búfer [SWS_DM_01513]. AraDiag incrusta estos datos útiles en la respuesta UDS positiva directamente detrás del blockSequenceCounter como transferResponseParameterRecord [SWS_DM_01513], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 «Read».
  3. Finalización de la sesión: Tan pronto como se hayan transmitido todos los datos o se deba finalizar la transferencia, AraDiag llama a ExitRead() [SWS_DM_01514]. Se pasan el motivo de finalización (exit_type del tipo DataTransferExitType), parámetros específicos del fabricante del vehículo (transfer_request_parameter_record), así como metadatos y el manejador de cancelación [SWS_DM_01514].
  4. Fin de la transacción: La aplicación confirma el fin de la sesión mediante un ara::core::Future<ara::core::Vector<ara::core::Byte>>. En caso de confirmación positiva, los datos contenidos en el vector se sitúan tras el ID de servicio (SID) como transferResponseParameterRecord en la respuesta UDS positiva [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 «ExitRead». La instancia del handler solo puede destruirse después de esta llamada [SWS_DM_01510].

Diagrama de secuencia: Secuencia de llamadas durante la lectura pull iterativa y posterior ExitRead. Fuentes: [SWS_DM_01513], [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 «ExitRead», AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 «Read»

Escenarios de error

La especificación define directrices claras para estados de error y situaciones excepcionales:

  • Códigos de error UDS (NRC): Si se produce un error al leer un bloque de datos o al finalizar la transferencia, el future correspondiente no se completa de forma regular. En su lugar, el future debe completarse como estado de error con un Negative Response Code (NRC) adecuado de DiagUdsNrcErrc según ISO 14229-1 [SWS_DM_01513], [SWS_DM_01514]. AraDiag genera a partir de ello un mensaje de respuesta UDS negativa.
  • Tratamiento de cancelación: Los parámetros cancellation_handler permiten a la aplicación comprobar activamente mediante cancellation_handler.IsCanceled() si se ha cancelado la conversación de diagnóstico [SWS_DM_01513], [SWS_DM_01514]. Como alternativa, mediante cancellation_handler.SetNotifier() se puede registrar un callback que se invoca cuando el framework cancela la conversación [SWS_DM_01513], [SWS_DM_01514].
  • Periodo de validez de los búferes: El búfer response_data pasado por AraDiag en Read(), así como el transfer_request_parameter_record en ExitRead(), tienen un tiempo de vida limitado. Solo son válidos hasta que se completa la promesa correspondiente o se cancela el procesamiento mediante el cancellation_handler [SWS_DM_01513], [SWS_DM_01514].
  • Destrucción prematura: Si se destruye la instancia de DataTransferReadByPullHandler antes de que se haya ejecutado ExitRead(), esto constituye una infracción de las condiciones del contrato de la API [SWS_DM_01510].

  <h4>Contexto</h4>
  <p>La clase <code>ara::diag::DataTransferReadByPullHandler</code> sirve para el procesamiento estandarizado de transferencias de datos de lectura iniciadas por solicitudes de diagnóstico como <code>RequestReadFile</code> o <code>RequestReadDirectory</code> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=367">AUTOSAR_AP_SWS_Diagnostics §8.10.2 «Class: DataTransferReadByPullHandler»</a>, <a class="spec-record-ref" data-req="SWS_DM_01506" href="../spec/record.html?id=SWS_DM_01506">[SWS_DM_01506]</a>.   <p>El concepto de transmisión se basa en un mecanismo pull: AraDiag solicita secuencialmente bloques de datos de la implementación de la aplicación para transmitirlos posteriormente al cliente UDS (téster de diagnóstico) <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>.   <h4>Ciclo de vida</h4>
  <p>Para las instancias de <code>DataTransferReadByPullHandler</code> se aplican reglas estrictas relativas a la creación, la propiedad y la destrucción:</p>
  <ul>
    <li><strong>Creación:</strong> El constructor por defecto está declarado como <code>protected</code> y <code>noexcept=default</code> <a class="spec-record-ref" data-req="SWS_DM_01507" href="../spec/record.html?id=SWS_DM_01507">[SWS_DM_01507]</a>. Interpretación: Dado que la clase contiene métodos de interfaz puramente virtuales y el constructor por defecto está protegido, el software de aplicación debería implementar e instanciar su propia clase handler derivada.</li>
    <li><strong>Sin capacidad de copia:</strong> Tanto el constructor de copia <a class="spec-record-ref" data-req="SWS_DM_01509" href="../spec/record.html?id=SWS_DM_01509">[SWS_DM_01509]</a> como el operador de asignación de copia <a class="spec-record-ref" data-req="SWS_DM_01512" href="../spec/record.html?id=SWS_DM_01512">[SWS_DM_01512]</a> están explícitamente eliminados (<code>=delete</code>). Un handler está destinado exactamente a una única sesión de transferencia de archivos (<em>single file transfer session</em>) y no debe copiarse <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=369">AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.2 «Constructors»</a>.</li>
    <li><strong>Capacidad de movimiento:</strong> El constructor de movimiento <a class="spec-record-ref" data-req="SWS_DM_01508" href="../spec/record.html?id=SWS_DM_01508">[SWS_DM_01508]</a> y la asignación de movimiento <a class="spec-record-ref" data-req="SWS_DM_01511" href="../spec/record.html?id=SWS_DM_01511">[SWS_DM_01511]</a> están definidos como <code>noexcept=default</code> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=368">AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1 «Special Member Functions»</a>, de modo que se admite la transferencia de propiedad.</li>
    <li><strong>Condición de destrucción:</strong> El destructor es virtual y está especificado como <code>noexcept=default</code> <a class="spec-record-ref" data-req="SWS_DM_01510" href="../spec/record.html?id=SWS_DM_01510">[SWS_DM_01510]</a>. Como invariante central se aplica que una instancia no debe destruirse en ningún caso antes de que se haya llamado a <code>ExitRead()</code> <a class="spec-record-ref" data-req="SWS_DM_01510" href="../spec/record.html?id=SWS_DM_01510">[SWS_DM_01510]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=368">AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1.2 «Destructor»</a>.</li>

  <h4>Ruta de uso</h4>
  <p>La secuencia típica de llamadas de una transferencia de datos de lectura basada en pull comprende dos fases principales:</p>
  <ol>
    <li><strong>Bucle de lectura pull:</strong> Durante la transferencia en curso, AraDiag llama repetidamente al método <code>Read()</code> en el handler <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>. AraDiag pasa aquí una vista de memoria <code>response_data</code> (del tipo <code>ara::core::Span&lt;const ara::core::Byte&gt;</code>) a un búfer previamente asignado, así como <code>meta_info</code> y un <code>cancellation_handler</code>. La implementación de la aplicación compone el contenido del siguiente bloque de datos y lo copia hasta el tamaño máximo del span <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>.</li>
    <li><strong>Devolución del chunk:</strong> <code>Read()</code> devuelve un <code>ara::core::Future&lt;std::uint32_t&gt;</code>. El future se completa con el número de bytes realmente escritos en el búfer <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>. AraDiag incrusta estos datos útiles en la respuesta UDS positiva directamente detrás del <code>blockSequenceCounter</code> como <code>transferResponseParameterRecord</code> <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=370">AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 «Read»</a>.</li>
    <li><strong>Finalización de la sesión:</strong> Tan pronto como se hayan transmitido todos los datos o se deba finalizar la transferencia, AraDiag llama a <code>ExitRead()</code> <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>. Se pasan el motivo de finalización (<code>exit_type</code> del tipo <code>DataTransferExitType</code>), parámetros específicos del fabricante del vehículo (<code>transfer_request_parameter_record</code>), así como metadatos y el manejador de cancelación <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>.</li>
    <li><strong>Fin de la transacción:</strong> La aplicación confirma el fin de la sesión mediante un <code>ara::core::Future&lt;ara::core::Vector&lt;ara::core::Byte&gt;&gt;</code>. En caso de confirmación positiva, los datos contenidos en el vector se sitúan tras el ID de servicio (SID) como <code>transferResponseParameterRecord</code> en la respuesta UDS positiva <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=369">AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 «ExitRead»</a>. La instancia del handler solo puede destruirse después de esta llamada <a class="spec-record-ref" data-req="SWS_DM_01510" href="../spec/record.html?id=SWS_DM_01510">[SWS_DM_01510]</a>.</li>
  </ol>

  <h4>Escenarios de error</h4>
  <p>La especificación define directrices claras para estados de error y situaciones excepcionales:</p>
  <ul>
    <li><strong>Códigos de error UDS (NRC):</strong> Si se produce un error al leer un bloque de datos o al finalizar la transferencia, el future correspondiente no se completa de forma regular. En su lugar, el future debe completarse como estado de error con un Negative Response Code (NRC) adecuado de <code>DiagUdsNrcErrc</code> según ISO 14229-1 <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>, <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>. AraDiag genera a partir de ello un mensaje de respuesta UDS negativa.</li>
    <li><strong>Tratamiento de cancelación:</strong> Los parámetros <code>cancellation_handler</code> permiten a la aplicación comprobar activamente mediante <code>cancellation_handler.IsCanceled()</code> si se ha cancelado la conversación de diagnóstico <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>, <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>. Como alternativa, mediante <code>cancellation_handler.SetNotifier()</code> se puede registrar un callback que se invoca cuando el framework cancela la conversación <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>, <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>.</li>
    <li><strong>Periodo de validez de los búferes:</strong> El búfer <code>response_data</code> pasado por AraDiag en <code>Read()</code>, así como el <code>transfer_request_parameter_record</code> en <code>ExitRead()</code>, tienen un tiempo de vida limitado. Solo son válidos hasta que se completa la promesa correspondiente o se cancela el procesamiento mediante el <code>cancellation_handler</code> <a class="spec-record-ref" data-req="SWS_DM_01513" href="../spec/record.html?id=SWS_DM_01513">[SWS_DM_01513]</a>, <a class="spec-record-ref" data-req="SWS_DM_01514" href="../spec/record.html?id=SWS_DM_01514">[SWS_DM_01514]</a>.</li>

  </ul>
