Contexto

La clase de interfaz ara::diag::FileTransferService ([SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §8.18 «Header: ara/diag/file_transfer.h») proporciona en AUTOSAR Adaptive la abstracción funcional para transferencias de diagnóstico basadas en archivos. Sirve para implementar el servicio UDS 0x38 (RequestFileTransfer) y permite el intercambio estandarizado de archivos e información de directorios a través de los límites del proceso (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»).

En los procesos de transferencia de archivos intervienen tres componentes principales:

  • Cliente de diagnóstico: inicia operaciones de archivo mediante llamadas estandarizadas al servicio UDS (RequestFileTransfer 0x38, TransferData 0x36 y RequestTransferExit 0x37).
  • Diagnostic Management (Diagnostic Server Instance): recibe los mensajes de diagnóstico del cliente, gestiona el protocolo y reenvía las solicitudes a la instancia de servicio registrada (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Realization of modeOfOperation»).
  • Adaptive Application: implementa los métodos de callback funcionales de ara::diag::FileTransferService, genera sesiones de datos y accede al sistema de archivos local.

La arquitectura admite diferentes estrategias para el intercambio de datos (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer»):

  • Simple: copia los datos entre la Adaptive Application y el Diagnostic Management; adecuado para tamaños de archivo más pequeños.
  • Zero Copy: evita copias de memoria entre la aplicación y el Diagnostic Management para lograr eficiencia de recursos con grandes volúmenes de datos.
  • OS File System Handle: transferencia de handles de archivos nativos del sistema operativo para una transmisión directa sin sobrecarga de copia en la pila de diagnóstico.

Diagrama de contexto: interlocutores de interacción y distribución de roles en la transferencia de diagnóstico basada en archivos. Fuentes: [SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 «Service 0x38 – RequestFileTransfer».

Ciclo de vida

La clase ara::diag::FileTransferService actúa como clase base para controladores de diagnóstico específicos de la aplicación. Durante la instanciación, el constructor espera un ara::core::InstanceSpecifier que haga referencia a un PortPrototype modelado de tipo DiagnosticRequestFileTransferInterface, así como la definición de la concurrencia mediante ConcurrencyType ([SWS_DM_01325]).

Las relaciones de instancia y de propiedad están estrictamente reguladas:

  • Protección contra copia: la clase representa una instancia única; el constructor de copia ([SWS_DM_01327]) y el operador de asignación por copia ([SWS_DM_01329]) están eliminados (delete).
  • Capacidad de movimiento: el constructor de movimiento ([SWS_DM_01328]) y el operador de asignación por movimiento ([SWS_DM_01330]) están definidos en el ámbito protected.
  • Destrucción: el destructor virtual ~FileTransferService() ([SWS_DM_01326]) garantiza la limpieza adecuada de las clases derivadas.

El ciclo de vida funcional es controlado activamente por la aplicación:

  1. Proporcionado: tras la creación, el Diagnostic Management todavía no reenvía ninguna solicitud a la instancia.
  2. Activo (ofrecido): mediante la llamada a Offer(), se autoriza al Diagnostic Management a transferir solicitudes al controlador de servicio ([SWS_DM_01336]).
  3. Desactivado: la llamada a StopOffer() revoca la habilitación e impide el reenvío de nuevas solicitudes ([SWS_DM_01337]).

En lo que respecta a la seguridad para subprocesos, AUTOSAR diferencia: los callbacks de la interfaz adaptan su comportamiento de concurrencia al ConcurrencyType (kConcurrent o kNotConcurrent) pasado en el constructor ([SWS_DM_01325]). Por el contrario, los métodos administrativos como Offer(), StopOffer() y el destructor están especificados como no seguros para subprocesos ([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

Diagrama de estados: fases del ciclo de vida de una instancia de FileTransferService. Fuentes: [SWS_DM_01325], [SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337].

Ruta de uso

La interfaz cubre todos los modos de funcionamiento definidos en el servicio UDS 0x38 a través de métodos puramente virtuales dedicados:

  • RequestReadFile: se invoca en caso de modeOfOperation ReadFile (0x04) ([SWS_DM_01314], [SWS_DM_01331]).
  • RequestWriteFile: se invoca en caso de modeOfOperation ReplaceFile (0x03) con WriteFileMode::kReplace ([SWS_DM_01313], [SWS_DM_01324], [SWS_DM_01333]), así como para kAdd.
  • RequestResumeWriteFile: se invoca en caso de modeOfOperation ResumeFile (0x06) ([SWS_DM_01316], [SWS_DM_01334]).
  • RequestReadDirectory: se invoca en caso de modeOfOperation ReadDir (0x05) ([SWS_DM_01315], [SWS_DM_01332]).
  • DeleteFile: realiza la eliminación completa de un archivo en caso de modeOfOperation DeleteFile ([SWS_DM_01335]).

Una ruta de uso típica para la lectura de un archivo (ReadFile) se lleva a cabo en los siguientes pasos:

  1. Puesta a disposición: la aplicación instancia su clase de servicio derivada y activa la interfaz mediante Offer() ([SWS_DM_01336]).
  2. Solicitud de transferencia inicial: el cliente de diagnóstico envía el comando UDS 0x38 (ReadFile). El Diagnostic Server reenvía la llamada a la aplicación a través de RequestReadFile(fileName, dataFormatIdentifier, metaInfo, cancellationHandler) ([SWS_DM_01314], [SWS_DM_01331]).
  3. Establecimiento de sesión: la aplicación comprueba la solicitud y devuelve de forma asíncrona un ara::core::Future que contiene una tupla compuesta por una DataTransferReadSession inicializada y los tamaños de archivo (FileSizes) ([SWS_DM_01331]). Diagnostic Management responde positivamente a la solicitud UDS.
  4. Transferencia de bloques: para cada solicitud TransferData (0x36) posterior del cliente, el Diagnostic Server invoca los métodos de lectura de los handlers registrados en la sesión ([SWS_DM_01317]).
  5. Finalización de la transferencia: una vez completada la transferencia, el cliente envía RequestTransferExit (0x37). A continuación, el Diagnostic Server llama al método Exit de la sesión ([SWS_DM_01318]) y concluye la operación.

Diagrama de secuencia: flujo de una operación de lectura de archivos según los servicios UDS 0x38, 0x36 y 0x37. Fuentes: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331], [SWS_DM_01336].

Escenarios de error

Las condiciones de error se interceptan y notifican en diferentes capas del sistema:

  • Errores de construcción y modelado: si la configuración no se corresponde con el modelo del sistema, la instanciación falla ([SWS_DM_01325]):
    • InstanceSpecifierMappingIntegrityViolation: el identificador no se puede resolver o no hace referencia a un PortPrototype.
    • PortInterfaceMappingViolation: Al puerto DEM tipificado por DiagnosticRequestFileTransferInterface le falta el DiagnosticServiceGenericMapping.
    • ProcessMappingViolation: no existe ningún proceso en tiempo de ejecución correspondiente para el proceso modelado.
    • InstanceSpecifierAlreadyInUseViolation: el InstanceSpecifier ya se está utilizando dentro del proceso.
  • Puesta a disposición múltiple: una nueva llamada a Offer() en una instancia ya activa devuelve un error con DiagOfferErrc::kAlreadyOffered ([SWS_DM_01336]).
  • Respuestas negativas de diagnóstico (NRC): si las operaciones de archivo no se pueden ejecutar con éxito en los métodos virtuales, la aplicación lo señala mediante el ara::core::Future devuelto con un UDS Negative Response Code (NRC) del dominio de errores DiagUdsNrcErrc conforme a ISO 14229-1 ([SWS_DM_01331], [SWS_DM_01332], [SWS_DM_01333], [SWS_DM_01334], [SWS_DM_01335]).
  • Cancelación de operaciones: mediante el parámetro CancellationHandler, la aplicación puede comprobar continuamente el estado de cancelación con cancellationHandler.IsCanceled() durante operaciones de archivo asíncronas o registrar una notificación a través de cancellationHandler.SetNotifier() para liberar recursos inmediatamente en caso de cancelación prematura de la sesión ([SWS_DM_01331], [SWS_DM_01335]).
