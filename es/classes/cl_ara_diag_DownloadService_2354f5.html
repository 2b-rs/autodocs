Contexto

La clase ara::diag::DownloadService proporciona en el módulo diag de AUTOSAR Adaptive Platform la interfaz C++ central para el procesamiento de descargas de diagnóstico AUTOSAR_AP_SWS_Diagnostics, p. 74. Sirve como manejador de servicio del lado de la aplicación que encapsula las operaciones de descarga para una interfaz de diagnóstico específica. La interacción principal tiene lugar entre AUTOSAR Diagnostic Management (DM) y la implementación concreta de la aplicación. Interpretación: Diagnostic Management recibe las solicitudes UDS de un tester de diagnóstico externo de conformidad con ISO 14229-1 y las reenvía a la instancia en cuanto se ofrece el servicio.

Tras su activación mediante Offer(), la clase actúa como interfaz para las fases estandarizadas de una descarga de diagnóstico: solicitud (RequestDownload), transferencia de datos segmentada (TransferData a través de DownloadData) y finalización (RequestTransferExit a través de RequestDownloadExit). La aplicación implementa los métodos virtuales puros [SWS_DM_00789], [SWS_DM_00790] y [SWS_DM_00791] para recibir bloques de datos, verificarlos y almacenarlos en la memoria de destino.

Ciclo de vida

Una instancia de DownloadService se crea mediante el constructor DownloadService(const ara::core::InstanceSpecifier&, ConcurrencyType) [SWS_DM_00787]. El InstanceSpecifier vincula la instancia con un PortPrototype definido en el modelo de diseño de un DiagnosticDownloadInterface. A través del argumento concurrencyType, se determina si los métodos de servicio implementados se invocan de forma concurrente (kConcurrent) o no concurrente (kNotConcurrent), lo que constituye la especificación para la seguridad para subprocesos de la lógica de la aplicación [SWS_DM_00787]. El propio constructor está implementado de forma segura para subprocesos.

En cuanto a la semántica de propiedad y copia, DownloadService está diseñada como única: tanto el constructor de copia [SWS_DM_01649] y el operador de asignación [SWS_DM_01647] como el constructor de movimiento [SWS_DM_01650] y el operador de asignación por movimiento [SWS_DM_01648] están eliminados (delete).

El ciclo de vida operativo se divide en los siguientes estados y transiciones:

  • Instanciado (inactivo): Tras la construcción, la instancia está lista, pero aún no reenvía solicitudes de diagnóstico.
  • Ofrecido (activo): La llamada a Offer() [SWS_DM_00792] autoriza al DM a reenviar las solicitudes entrantes de descarga de diagnóstico a los métodos virtuales del manejador de la instancia.
  • Detenido: Mediante StopOffer() [SWS_DM_00793] se desactiva el reenvío de solicitudes; la instancia regresa al estado inactivo.
  • Destrucción: El destructor virtual ~DownloadService() [SWS_DM_00788] libera los recursos. Dado que el destructor no es seguro para subprocesos, el servicio debería detenerse previamente.

Diagrama de estados: Fases de estado de una instancia de DownloadService desde la construcción, pasando por el ofrecimiento, hasta la finalización. Fuentes: [SWS_DM_00787], [SWS_DM_00792], [SWS_DM_00793], [SWS_DM_00788].

Ruta de uso

Tras una instanciación y puesta a disposición correctas mediante Offer(), un proceso de descarga pasa normalmente por tres pasos secuenciales a través de llamadas asíncronas a la interfaz:

  1. Inicialización de la descarga (RequestDownload): El DM llama a RequestDownload(...) [SWS_DM_00789]. Se transfieren el identificador de formato de datos (dataFormatIdentifier), el formato de dirección y longitud (addressAndLengthFormatIdentifier), la dirección y el tamaño de destino como intervalo de bytes (memoryAddressAndSize), así como metaInfo y un cancellationHandler. Los datos en memoryAddressAndSize permanecen válidos hasta que se cumpla la promesa asociada o se cancele el procesamiento. El método devuelve un ara::core::Future<void>, que se completa con éxito en caso de validación positiva.
  2. Transferencia de datos por bloques (DownloadData): Para cada solicitud de transferencia siguiente, el DM llama a DownloadData(...) [SWS_DM_00790]. Los datos útiles se transmiten en transferRequestParameterRecord. La aplicación procesa los datos y señaliza el resultado a través de un ara::core::Future<OperationOutput>. Los datos en OperationOutput.responseData se colocan en la respuesta UDS positiva detrás del contador de secuencia de bloques.
  3. Finalización de la transferencia (RequestDownloadExit): Para finalizar la descarga, el DM llama a RequestDownloadExit(...) [SWS_DM_00791]. Tras una comprobación final de integridad (p. ej., validación de suma de comprobación), la aplicación devuelve un ara::core::Future<OperationOutput>, cuyos datos de respuesta opcionales se colocan detrás del ID de servicio.

Los tres métodos reciben un cancellationHandler [SWS_DM_00789]. Mediante cancellationHandler.IsCanceled(), la aplicación puede comprobar el estado de cancelación; con cancellationHandler.SetNotifier(...) se puede registrar un callback para reaccionar de inmediato a una cancelación de la conversación de diagnóstico. Interpretación: En caso de una cancelación prematura, la aplicación finaliza el almacenamiento en búfer interno y cancela las operaciones de escritura en curso.

Diagrama de secuencia: Secuencia típica de interacción entre Diagnostic Management y DownloadService durante una descarga de diagnóstico. Fuentes: [SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791].

Escenarios de error

Los errores pueden producirse tanto durante la creación y configuración como durante la provisión del servicio y el procesamiento de datos:

  • Errores de modelado y de inicialización: Al llamar al constructor se pueden desencadenar infracciones de modelado [SWS_DM_00787]:
    • InstanceSpecifierMappingIntegrityViolation: El InstanceSpecifier no se puede resolver en el modelo dentro del contexto de ejecución o no hace referencia a un PortPrototype.
    • PortInterfaceMappingViolation: Un PortPrototype tipificado con DiagnosticDownloadInterface no está asignado conforme al tipo a un DiagnosticServiceGenericMapping.
    • ProcessMappingViolation: No existe ningún Process modelado adecuado para InstanceRef.
    • InstanceSpecifierAlreadyInUseViolation: El InstanceSpecifier ya está siendo utilizado por otra instancia dentro de este proceso.
  • Error al ofrecer el servicio: Una nueva llamada a Offer() cuando el servicio ya se ha ofrecido falla y devuelve el código de error DiagOfferErrc::kAlreadyOffered [SWS_DM_00792].
  • Errores de diagnóstico (Negative Response Codes): Si falla el procesamiento en RequestDownload, DownloadData o RequestDownloadExit (por ejemplo, en caso de formato defectuoso, área de memoria no válida o errores de escritura), el future devuelto se completa con un código de error correspondiente de DiagUdsNrcErrc de acuerdo con ISO 14229-1 [SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]. El DM genera a partir de ello la respuesta negativa (NRC) al tester.

Esta guía de clases se basa en la especificación AUTOSAR AP R25-11 (Diagnostics). Todos los datos se han verificado con respecto a los requisitos de la especificación.
