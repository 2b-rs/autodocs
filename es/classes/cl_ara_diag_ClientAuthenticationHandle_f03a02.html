Contexto

La clase ara::diag::ClientAuthenticationHandle ([SWS_DM_01145]) sirve como interfaz de control para una sesión activa de autenticación de diagnóstico. Una instancia de este handle se proporciona a una aplicación adaptativa mediante la Diagnostic Server Instance tan pronto como se completa con éxito una autenticación mediante ara::diag::ClientAuthentication::Authenticate ([SWS_DM_01206]) o una sobrescritura temporal de los roles predeterminados mediante ara::diag::ClientAuthentication::OverrideDefaultRoles ([SWS_DM_01209]) (AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 «ClientAuthenticationHandle»).

El Diagnostic Manager administra para cada cliente autenticado una lista de control de acceso dinámica (DynamicAccessList). Esta lista contiene patrones para solicitudes de diagnóstico que conceden al cliente autenticado derechos de acceso adicionales a los recursos de diagnóstico más allá de la configuración almacenada en el Diagnostic Extract (AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 «ClientAuthenticationHandle», AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.4 «DynamicAccessList Creation and Update»). A través de ClientAuthenticationHandle, la aplicación controla frente a la instancia del servidor tanto estos derechos de acceso dinámicos como el estado de autenticación y los temporizadores asociados de inactividad y expiración ([SWS_DM_01213], [SWS_DM_01155]).

Diagrama de contexto: Interacción entre la aplicación, el handle y la Diagnostic Server Instance. Fuentes: AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 «ClientAuthenticationHandle», [SWS_DM_01206], [SWS_DM_01209].

Ciclo de vida

La creación de un handle válido normalmente no se realiza a través del constructor por defecto, sino como valor de retorno de los métodos de autenticación de la clase ara::diag::ClientAuthentication ([SWS_DM_01206], [SWS_DM_01209]). Aunque la clase proporciona un constructor por defecto seguro para subprocesos y seguro frente a excepciones ([SWS_DM_01146]), este crea un handle no inicializado o vacío. En cuanto a la propiedad, ClientAuthenticationHandle implementa una semántica estricta de solo movimiento: el constructor de copia ([SWS_DM_01150]) y el operador de asignación por copia ([SWS_DM_01151]) están eliminados (=delete). Un handle únicamente puede moverse (constructor de movimiento [SWS_DM_01148] y asignación por movimiento [SWS_DM_01149]), lo que garantiza un propietario único por cada contexto de autenticación.

La destrucción del objeto se realiza a través del destructor ~ClientAuthenticationHandle() ([SWS_DM_01147]). Con respecto a la concurrencia, debe tenerse en cuenta que ni el destructor ni las funciones miembro de control (Set, Append, Refresh, Revoke) son seguros para subprocesos ([SWS_DM_01147], [SWS_DM_01152], [SWS_DM_01153], [SWS_DM_01154], [SWS_DM_01155]). Si varios subprocesos de una aplicación acceden al mismo handle, el acceso debe sincronizarse.

Ruta de uso

Una ruta de uso típica incluye la autenticación correcta, la definición y ampliación de los derechos de acceso, la renovación periódica de la validez y la revocación final de los derechos:

  1. Obtención del handle: La aplicación invoca Authenticate o OverrideDefaultRoles y, en caso de éxito, recibe el ClientAuthenticationHandle ([SWS_DM_01206], [SWS_DM_01209]).
  2. Establecimiento de derechos: Mediante Set(dynamicAccessList), la aplicación reemplaza por completo la lista de acceso dinámica del cliente de diagnóstico ([SWS_DM_01153], [SWS_DM_01213]).
  3. Ampliación de derechos: Mediante Append(dynamicAccessList), si es necesario, se pueden añadir de forma incremental más patrones de servicios de diagnóstico a la DynamicAccessList existente ([SWS_DM_01152]).
  4. Renovación de temporizadores: En caso de comunicación de diagnóstico continua, la aplicación invoca Refresh() para restablecer los temporizadores de inactividad o de tiempo de espera de roles ([SWS_DM_01155], AUTOSAR_AP_SWS_Diagnostics §7.3.2.3.3 «ClientAuthenticationHandle», [SWS_DM_01210]). Si previamente se utilizaron tanto la autenticación como la sobrescritura de roles, la invocación renueva ambos temporizadores simultáneamente ([SWS_DM_01155]).
  5. Revocación de derechos: Con Revoke(), la aplicación devuelve explícitamente el cliente al estado kDeAuthenticated, descarta la DynamicAccessList asignada y revoca los roles sobrescritos temporalmente ([SWS_DM_01154]).

Diagrama de secuencia: Secuencia típica de interacción para la gestión de derechos y la extensión de temporizadores mediante el handle. Fuentes: [SWS_DM_01152], [SWS_DM_01153], [SWS_DM_01154], [SWS_DM_01155], [SWS_DM_01206].

Escenarios de error

Todos los métodos modificadores de estado del handle (Set, Append, Refresh y Revoke) están declarados como noexcept y notifican errores a través del tipo de retorno ara::core::Result<void>:

  • DiagErrc::kServiceNotAvailable: Se produce cuando la operación no se puede ejecutar porque funcionalidades esenciales del Diagnostic Manager no están disponibles actualmente ([SWS_DM_01152], [SWS_DM_01153], [SWS_DM_01154], [SWS_DM_01155]). En este caso, se aplica una semántica de reversión, de modo que el estado anterior del sistema permanece intacto.
  • Tiempo de espera y desautenticación automática: Si el temporizador de inactividad no se renueva a tiempo mediante solicitudes UDS o Refresh(), la Diagnostic Server Instance cambia automáticamente el cliente al estado kDeAuthenticated ([SWS_DM_01210]). Interpretación: Es probable que los intentos de control posteriores en un contexto caducado fallen o no surtan efecto.

Esta guía se basa exclusivamente en las especificaciones de AUTOSAR Adaptive Platform R25-11.
