Contexto

La clase ara::diag::GenericDiagnosticSovdOperation define la interfaz de programación genérica para la ejecución de operaciones SOVD (Service-Oriented Vehicle Diagnostics) dentro de AUTOSAR Adaptive Platform ([SWS_DM_02203], AUTOSAR_AP_SWS_Diagnostics §8.62.2 «Class: GenericDiagnosticSovdOperation»). Como interfaz funcional, media entre el Diagnostic Management (DM) interno del servidor y las rutinas específicas de una Adaptive Application.

De acuerdo con la especificación, la instancia de servidor proporciona para operaciones SOVD configuradas el método «Start Execution of an Operation» según ASAM SOVD ([SWS_DM_01396]). Si se recibe una petición correspondiente de un cliente SOVD externo y se verifica con éxito un proximity challenge eventualmente requerido ([SWS_DM_02173]), el DM delega la llamada directamente en el método StartExecution de la instancia de clase registrada ([SWS_DM_02174], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»). La clase actúa así como punto final del lado de la aplicación para procesar operaciones de diagnóstico parametrizadas.

Diagrama de contexto: integración de la interfaz GenericDiagnosticSovdOperation entre el cliente SOVD, el Diagnostic Management y la lógica de aplicación. Fuentes: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02203], [SWS_DM_02210].

Ciclo de vida

La instanciación de ara::diag::GenericDiagnosticSovdOperation se realiza a través del constructor especificando un ara::core::InstanceSpecifier así como el modelo de concurrencia ConcurrencyType ([SWS_DM_02204]). Puesto que el constructor de movimiento ([SWS_DM_02206]) y el operador de asignación por movimiento ([SWS_DM_02207]) están declarados como protected y el método de ejecución central es puramente virtual, es de suponer que la clase esté concebida exclusivamente como clase base para manejadores derivados y específicos de la aplicación.

Tras la construcción, el objeto permanece inicialmente inactivo. Mediante la llamada explícita a Offer(), se habilita el reenvío de peticiones SOVD entrantes por parte del DM a la instancia ([SWS_DM_02211]). Si el servicio ya no debe estar disponible o si está próximo el apagado de la aplicación, StopOffer() desactiva nuevamente el reenvío ([SWS_DM_02212]). Durante la destrucción mediante el destructor virtual ([SWS_DM_02205]), todas las vinculaciones deben haberse eliminado debidamente. En cuanto a la seguridad para subprocesos, Offer() y StopOffer() están especificados como no seguros para subprocesos ([SWS_DM_02211], [SWS_DM_02212]), mientras que el método de ejecución StartExecution y el destructor están diseñados para ser seguros para subprocesos ([SWS_DM_02210], [SWS_DM_02205]).

Ruta de uso

El flujo habitual comprende la puesta a disposición, el procesamiento de una petición de diagnóstico y la posterior cancelación del registro:

  1. Instanciación y registro: La clase derivada se instancia especificando el prototipo de puerto de destino ([SWS_DM_02204]). A continuación, la aplicación activa el procesamiento de mensajes mediante Offer() ([SWS_DM_02211]).
  2. Solicitud entrante: Un cliente SOVD inicia una ejecución a través del DM ([SWS_DM_01396]). Tras comprobar eventuales condiciones de acceso, el DM llama a StartExecution ([SWS_DM_02174], [SWS_DM_02210]).
  3. Procesamiento: La aplicación recibe el nombre de la operación sovd_operation_name, los datos útiles sovd_content_data, información adicional meta_info así como un cancellation_handler ([SWS_DM_02210]). Los datos útiles permanecen válidos hasta que se cumple el ara::core::Promise devuelto o se cancela la operación.
  4. Devolución del resultado: La operación devuelve un ara::core::Future que contiene una variante de StartSynchronousExecutionResponse o StartAsynchronousExecutionResponse ([SWS_DM_02210]). En caso de procesamiento síncrono, el DM formula a partir de ello los datos de respuesta para el cliente SOVD ([SWS_DM_02176]).
  5. Cancelación del registro: Antes de finalizar, la aplicación llama a StopOffer() ([SWS_DM_02212]).

Diagrama de secuencia: patrón de interacción de registro, ejecución síncrona o asíncrona y cancelación del registro. Fuentes: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02210], [SWS_DM_02211], [SWS_DM_02212].

Escenarios de error

Los estados de error pueden producirse tanto durante el registro del servicio como durante el procesamiento de la operación:

  • Disponibilidad del servicio: Si se llama a Offer() a pesar de que el manejador ya está registrado, la llamada falla y devuelve el error DiagOfferErrc::kAlreadyOffered con semántica de rollback ([SWS_DM_02211]).
  • Fallo de la operación: si una operación no se puede ejecutar con éxito, el ara::core::Future devuelto debe completarse con un código de error de SOVD correspondiente según ISO 17978-3 o ASAM SOVD 1.1 ([SWS_DM_02210]).
  • Condición de cancelación: si se cancela una operación en curso, el DM lo señaliza a través del objeto cancellation_handler proporcionado ([SWS_DM_02210]). Este objeto no debe almacenarse ni utilizarse más allá del tiempo de vida de la operación ([SWS_DM_02210]).

<h4>Contexto</h4>
<p>La clase <code>ara::diag::GenericDiagnosticSovdOperation</code> define la interfaz de programación genérica para la ejecución de operaciones SOVD (Service-Oriented Vehicle Diagnostics) dentro de AUTOSAR Adaptive Platform (<a class="spec-record-ref" data-req="SWS_DM_02203" href="../spec/record.html?id=SWS_DM_02203">[SWS_DM_02203]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=856">AUTOSAR_AP_SWS_Diagnostics §8.62.2 «Class: GenericDiagnosticSovdOperation»</a>). Como interfaz funcional, media entre el Diagnostic Management (DM) interno del servidor y las rutinas específicas de una Adaptive Application.</p>
<p>De acuerdo con la especificación, la instancia de servidor proporciona para operaciones SOVD configuradas el método «Start Execution of an Operation» según ASAM SOVD (<a class="spec-record-ref" data-req="SWS_DM_01396" href="../spec/record.html?id=SWS_DM_01396">[SWS_DM_01396]</a>). Si se recibe una petición correspondiente de un cliente SOVD externo y se verifica con éxito un proximity challenge eventualmente requerido (<a class="spec-record-ref" data-req="SWS_DM_02173" href="../spec/record.html?id=SWS_DM_02173">[SWS_DM_02173]</a>), el DM delega la llamada directamente en el método <code>StartExecution</code> de la instancia de clase registrada (<a class="spec-record-ref" data-req="SWS_DM_02174" href="../spec/record.html?id=SWS_DM_02174">[SWS_DM_02174]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=217">AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 «Operations – Start execution of an operation»</a>). La clase actúa así como punto final del lado de la aplicación para procesar operaciones de diagnóstico parametrizadas.</p>

<h4>Ciclo de vida</h4>
<p>La instanciación de <code>ara::diag::GenericDiagnosticSovdOperation</code> se realiza a través del constructor especificando un <code>ara::core::InstanceSpecifier</code> así como el modelo de concurrencia <code>ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_02204" href="../spec/record.html?id=SWS_DM_02204">[SWS_DM_02204]</a>). Puesto que el constructor de movimiento (<a class="spec-record-ref" data-req="SWS_DM_02206" href="../spec/record.html?id=SWS_DM_02206">[SWS_DM_02206]</a>) y el operador de asignación por movimiento (<a class="spec-record-ref" data-req="SWS_DM_02207" href="../spec/record.html?id=SWS_DM_02207">[SWS_DM_02207]</a>) están declarados como <code>protected</code> y el método de ejecución central es puramente virtual, es de suponer que la clase esté concebida exclusivamente como clase base para manejadores derivados y específicos de la aplicación.</p>
<p>Tras la construcción, el objeto permanece inicialmente inactivo. Mediante la llamada explícita a <code>Offer()</code>, se habilita el reenvío de peticiones SOVD entrantes por parte del DM a la instancia (<a class="spec-record-ref" data-req="SWS_DM_02211" href="../spec/record.html?id=SWS_DM_02211">[SWS_DM_02211]</a>). Si el servicio ya no debe estar disponible o si está próximo el apagado de la aplicación, <code>StopOffer()</code> desactiva nuevamente el reenvío (<a class="spec-record-ref" data-req="SWS_DM_02212" href="../spec/record.html?id=SWS_DM_02212">[SWS_DM_02212]</a>). Durante la destrucción mediante el destructor virtual (<a class="spec-record-ref" data-req="SWS_DM_02205" href="../spec/record.html?id=SWS_DM_02205">[SWS_DM_02205]</a>), todas las vinculaciones deben haberse eliminado debidamente. En cuanto a la seguridad para subprocesos, <code>Offer()</code> y <code>StopOffer()</code> están especificados como no seguros para subprocesos (<a class="spec-record-ref" data-req="SWS_DM_02211" href="../spec/record.html?id=SWS_DM_02211">[SWS_DM_02211]</a>, <a class="spec-record-ref" data-req="SWS_DM_02212" href="../spec/record.html?id=SWS_DM_02212">[SWS_DM_02212]</a>), mientras que el método de ejecución <code>StartExecution</code> y el destructor están diseñados para ser seguros para subprocesos (<a class="spec-record-ref" data-req="SWS_DM_02210" href="../spec/record.html?id=SWS_DM_02210">[SWS_DM_02210]</a>, <a class="spec-record-ref" data-req="SWS_DM_02205" href="../spec/record.html?id=SWS_DM_02205">[SWS_DM_02205]</a>).</p>

<h4>Ruta de uso</h4>
<p>El flujo habitual comprende la puesta a disposición, el procesamiento de una petición de diagnóstico y la posterior cancelación del registro:</p>
<ol>
  <li><strong>Instanciación y registro:</strong> La clase derivada se instancia especificando el prototipo de puerto de destino (<a class="spec-record-ref" data-req="SWS_DM_02204" href="../spec/record.html?id=SWS_DM_02204">[SWS_DM_02204]</a>). A continuación, la aplicación activa el procesamiento de mensajes mediante <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_02211" href="../spec/record.html?id=SWS_DM_02211">[SWS_DM_02211]</a>).</li>
  <li><strong>Solicitud entrante:</strong> Un cliente SOVD inicia una ejecución a través del DM (<a class="spec-record-ref" data-req="SWS_DM_01396" href="../spec/record.html?id=SWS_DM_01396">[SWS_DM_01396]</a>). Tras comprobar eventuales condiciones de acceso, el DM llama a <code>StartExecution</code> (<a class="spec-record-ref" data-req="SWS_DM_02174" href="../spec/record.html?id=SWS_DM_02174">[SWS_DM_02174]</a>, <a class="spec-record-ref" data-req="SWS_DM_02210" href="../spec/record.html?id=SWS_DM_02210">[SWS_DM_02210]</a>).</li>
  <li><strong>Procesamiento:</strong> La aplicación recibe el nombre de la operación <code>sovd_operation_name</code>, los datos útiles <code>sovd_content_data</code>, información adicional <code>meta_info</code> así como un <code>cancellation_handler</code> (<a class="spec-record-ref" data-req="SWS_DM_02210" href="../spec/record.html?id=SWS_DM_02210">[SWS_DM_02210]</a>). Los datos útiles permanecen válidos hasta que se cumple el <code>ara::core::Promise</code> devuelto o se cancela la operación.</li>
  <li><strong>Devolución del resultado:</strong> La operación devuelve un <code>ara::core::Future</code> que contiene una variante de <code>StartSynchronousExecutionResponse</code> o <code>StartAsynchronousExecutionResponse</code> (<a class="spec-record-ref" data-req="SWS_DM_02210" href="../spec/record.html?id=SWS_DM_02210">[SWS_DM_02210]</a>). En caso de procesamiento síncrono, el DM formula a partir de ello los datos de respuesta para el cliente SOVD (<a class="spec-record-ref" data-req="SWS_DM_02176" href="../spec/record.html?id=SWS_DM_02176">[SWS_DM_02176]</a>).</li>
  <li><strong>Cancelación del registro:</strong> Antes de finalizar, la aplicación llama a <code>StopOffer()</code> (<a class="spec-record-ref" data-req="SWS_DM_02212" href="../spec/record.html?id=SWS_DM_02212">[SWS_DM_02212]</a>).</li>
</ol>

<h4>Escenarios de error</h4>
