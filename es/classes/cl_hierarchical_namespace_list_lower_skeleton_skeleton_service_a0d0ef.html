Contexto

La clase {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{ <service-interface-name>}Skeleton constituye la abstracción base del lado del servidor para la provisión de una Service Interface dentro del módulo de gestión de comunicaciones (com) de AUTOSAR Adaptive Platform. Como estructura de interfaz generada, el Skeleton asume el rol de mediador entre la infraestructura de comunicación específica de la plataforma (como una vinculación SOME/IP) y la implementación del proveedor de servicios específica de la aplicación. Desacopla la lógica de negocio del servicio de los detalles de protocolo, de la deserialización de mensajes y del despacho (dispatching) subyacente.

En el sistema global, la clase Skeleton interactúa con tres participantes clave:

  • Aplicación de servicio (Service Provider): la aplicación concreta deriva de la clase Skeleton e implementa las funciones de método virtuales puras para patrones regulares de solicitud-respuesta [SWS_CM_00191], así como métodos Fire-and-Forget [SWS_CM_90434].
  • Infraestructura de comunicación (middleware): el entorno de ejecución recibe mensajes de solicitud entrantes de clientes del servicio, deserializa los datos transmitidos y los transfiere al Skeleton para la ejecución del método AUTOSAR_AP_SWS_CommunicationManagement p. 99.
  • Contexto de ejecución asíncrono: mediante tipos de retorno como ara::core::Future se realiza el desacoplamiento entre la aceptación de la llamada y la provisión asíncrona del resultado [SWS_CM_00191].

Ciclo de vida

La instanciación del objeto Skeleton derivado la realiza explícitamente la aplicación de servicio. Durante la creación a través del constructor, es obligatorio pasar el modo de procesamiento para llamadas a métodos (ara::com::MethodCallProcessingMode) [SWS_CM_00130]. Este modo determina cómo se procesan las llamadas a métodos entrantes en lo referente a subprocesos y ejecución:

  • Procesamiento controlado por eventos (kEvent o kEventSingleThread): tan pronto como se deserializa un mensaje de solicitud entrante, el método virtual correspondiente de la clase Skeleton se invoca inmediatamente en el marco de la recepción del mensaje [SWS_CM_10306].
  • Procesamiento de sondeo en búfer (kPoll): los mensajes entrantes se retienen y solo se ejecutan cuando la aplicación inicia activamente el procesamiento a través de la interfaz de sondeo prevista para ello [SWS_CM_10307].

La vida útil del objeto Skeleton es responsabilidad exclusiva de la aplicación de servicio creadora. Antes de destruir la instancia, el servicio debería darse de baja de forma ordenada (interpretación: una finalización controlada garantiza que ya no haya llamadas a métodos que accedan a recursos liberados de la aplicación de servicio y que los cálculos asíncronos pendientes puedan completarse limpiamente).

Ruta de uso

El flujo de uso típico para la provisión de un servicio a través del Skeleton comprende los siguientes pasos:

  1. Implementación de la interfaz: la aplicación de servicio deriva de {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{ <service-interface-name>}Skeleton e implementa los métodos virtuales puros:
    • Los métodos regulares con valor de retorno implementan la firma virtual ara::core::Future<{<method-name>}Output> {<method-name>}(...) noexcept = 0 [SWS_CM_00191].
    • Los métodos unidireccionales sin respuesta implementan virtual void {<fnfmethod-name>}(...) noexcept = 0 [SWS_CM_90434].
  2. Instanciación: la clase Skeleton derivada se construye con el MethodCallProcessingMode deseado [SWS_CM_00130].
  3. Ejecución del método: al llegar las solicitudes, el middleware invoca el método implementado [SWS_CM_10306].
  4. Retorno de resultados: en métodos regulares, la aplicación de servicio devuelve un ara::core::Future con el objeto Output generado [SWS_CM_00191], [SWS_CM_99556], el cual es serializado por el middleware y enviado como mensaje de respuesta al cliente. En métodos Fire-and-Forget no se produce ninguna transmisión de respuesta [SWS_CM_90434].

Escenarios de error

En cuanto al comportamiento frente a errores, las llamadas a métodos se diferencian fundamentalmente según su semántica de comunicación:

  • Métodos regulares: la interfaz está declarada como noexcept y requiere seguridad frente a excepciones (exception safe) [SWS_CM_00191]. Si falla el procesamiento de un método, el error no se notifica mediante excepciones de C++, sino que se transporta de forma asíncrona a través del ara::core::Future devuelto. En caso de error, este contiene o bien un código de error de ara::com::ComErrc o un error de aplicación específico del dominio del tipo ApApplicationError [SWS_CM_00191].
  • Métodos Fire-and-Forget: estos métodos también están declarados como noexcept y deben implementarse de manera segura frente a excepciones [SWS_CM_90434]. Dado que por diseño no existe un canal de retorno hacia el cliente invocador, no se puede transmitir información ni de éxito ni de error. Si se produce un error durante el procesamiento, este debe tratarse internamente dentro del proveedor de servicios (interpretación: el registro local o las medidas de compensación internas son estrictamente necesarias para métodos Fire-and-Forget, ya que no se realiza ninguna transmisión de errores al cliente).
