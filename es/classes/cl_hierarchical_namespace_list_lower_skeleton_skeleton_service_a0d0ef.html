Sirve como clase base para la implementación en el lado del servidor y la provisión de métodos de una Service-Interface.

La clase sirve como clase base del lado del servidor para implementar una Service-Interface en ara::com, de la cual deriva la aplicación proveedora del servicio. Al crearla, se determina mediante el constructor si las llamadas a métodos entrantes se procesan controladas por eventos o por sondeo [SWS_CM_00130]. En los métodos declarados como seguros ante excepciones, las ejecuciones erróneas se señalan como código de error a través del ara::core::Future devuelto [SWS_CM_00191].

Contexto

La clase {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{ <service-interface-name>}Skeleton sirve en la Adaptive Platform, dentro del módulo com, como clase base abstracta generada para la provisión del lado del servidor de una Service-Interface. Un componente proveedor de servicios específico de la aplicación deriva de esta clase skeleton para implementar la lógica de negocio funcional del servicio. La clase intermedia entre la aplicación proveedora de servicios concreta y el middleware de comunicación o el binding de protocolo subyacente, como SOME/IP (SWS CommunicationManagement §8.1 «Method invocation»). Entre los interlocutores de interacción se encuentran la aplicación proveedora del servicio, que crea y posee la instancia, la propia clase skeleton, así como la infraestructura de comunicación, que recibe las solicitudes de servicio entrantes, las deserializa y las reenvía al skeleton ([SWS_CM_10306], [SWS_CM_10307]).

Diagrama de contexto: interacción entre la aplicación proveedora del servicio, ServiceSkeleton y el middleware de comunicación. Fuentes: [SWS_CM_10306], [SWS_CM_10307], SWS CommunicationManagement §8.1 «Method invocation».

Ciclo de vida

La creación de la instancia del skeleton se realiza a través del constructor, al que se transfiere el modo de procesamiento deseado ara::com::MethodCallProcessingMode [SWS_CM_00130]. Este modo establece la estrategia de concurrencia para las llamadas a métodos entrantes: si se configura kEvent o kEventSingleThread, las llamadas a métodos entrantes son invocadas inmediatamente y controladas por eventos por el middleware de comunicación [SWS_CM_10306]. Si en su lugar se transfiere kPoll, el procesamiento se realiza mediante sondeo por parte de la aplicación [SWS_CM_10307]. Interpretación: es de suponer que la instancia del skeleton permanezca bajo la posesión de la aplicación proveedora del servicio durante toda la provisión activa del servicio y solo se destruya al apagar el servicio.

Ruta de uso

El flujo típico comprende la implementación de los métodos puramente virtuales por parte de la clase proveedora derivada y la posterior ejecución al recibir solicitudes entrantes. Para llamadas regulares a métodos (Request-Response), el skeleton define una interfaz que devuelve un ara::core::Future con el objeto de salida correspondiente [SWS_CM_00191], [SWS_CM_99556]. Para métodos Fire-and-Forget sin respuesta, el skeleton proporciona operaciones puramente virtuales con el tipo de retorno void [SWS_CM_90434]. Ante solicitudes entrantes, el middleware de comunicación deserializa los datos útiles y reenvía la llamada a la implementación concreta de la clase skeleton según el modo de procesamiento configurado ([SWS_CM_10306], [SWS_CM_00191]).

Diagrama de secuencia: flujo de una llamada a método a través del skeleton. Fuentes: [SWS_CM_00191], [SWS_CM_10306], SWS CommunicationManagement §8.1 «Method invocation».

Escenarios de error

Tanto los métodos Request-Response como los métodos Fire-and-Forget están anotados a nivel de interfaz con noexcept y declarados como seguros ante excepciones ([SWS_CM_00191], [SWS_CM_90434]). Los errores al procesar llamadas a métodos regulares no se transmiten mediante excepciones de C++; en su lugar, el ara::core::Future devuelto transporta en caso de error un código de error correspondiente del tipo ara::com::ComErrc o un ApApplicationError [SWS_CM_00191]. Para los métodos Fire-and-Forget, según la especificación no se prevén valores de retorno ni códigos de error estandarizados [SWS_CM_90434].

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 93c9c81c8712 Procedencia

La función de la API [SWS_CM_90434] define la interfaz puramente virtual de un método fire-and-forget en el lado del servidor. Forma parte de la clase Skeleton generada {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{<service-interface-name>}Skeleton y se proporciona a través del archivo de encabezado {<si-namespace-derived-directory-path-lower>}/{<si-shortname-lower>}_skeleton.h (AUTOSAR_AP_SWS_CommunicationManagement §8.4.5.2.4.1 «{<fnfmethod-name>}»). La función se genera en cuanto se configura el atributo ClientServerOperation.fireAndForget == TRUE para una ClientServerOperation en el modelo de diseño.

Para la implementación y el comportamiento en tiempo de ejecución se aplican los siguientes aspectos esenciales:

  • Semántica de invocación y parámetros: El método recibe parámetros de entrada de manera análoga a los métodos regulares conforme a [SWS_CM_00191]. Al tratarse de una comunicación puramente unidireccional, la signatura posee el tipo de retorno void. No se transmiten ni parámetros de salida ni valores de retorno al cliente llamante.
  • Tratamiento de errores y seguridad frente a excepciones: La operación está declarada como noexcept=0 y, por tanto, especificada como estrictamente segura frente a excepciones (exception safe) ([SWS_CM_90434]). No existen códigos de error específicos de la aplicación ni otros canales de notificación; la implementación del servicio no debe permitir que se escapen excepciones C++ del método.
  • Contexto de ejecución y concurrencia: Si el Skeleton se opera en el modo ara::com::MethodCallProcessingMode == kPoll, el procesamiento de las invocaciones pendientes de [SWS_CM_90434] tiene lugar de forma determinista en el contexto de hilo de la invocación de ProcessNextMethodCall() (AUTOSAR_AP_SWS_CommunicationManagement p. 410). Fuera del modo de sondeo (polling), es de suponer que la ejecución tenga lugar de forma concurrente en un hilo de trabajo interno del middleware de comunicación.

  Procedencia
  

      

      

      
La función puramente virtual <Method> sirve para la provisión del lado del proveedor de un método dentro de una clase Skeleton para operaciones cliente-servidor sin semántica Fire-and-Forget [SWS_CM_00191]. Los desarrolladores de aplicaciones implementan esta interfaz en la clase skeleton derivada de la interfaz de servicio para recibir llamadas entrantes. Como parámetros de entrada se transfieren todos los argumentos modelados cuya dirección esté definida como in o inout [SWS_CM_00191].

      

      
La ejecución se lleva a cabo de forma asincrónica a través del tipo de retorno ara::core::Future, el cual, en caso de éxito, contiene el objeto tipado Output con los valores de resultado [SWS_CM_00191], [SWS_CM_99556]. El método está especificado como noexcept y seguro frente a excepciones; no se prescriben códigos de error sincrónicos estandarizados [SWS_CM_00191]. Si ocurre un error durante el procesamiento, la implementación lo proporciona de forma asincrónica a través del ara::core::Future, bien como un código de error de tipo ara::com::ComErrc o bien como un ApApplicationError específico del modelo [SWS_CM_00191].

      

      
El contexto de llamada y el comportamiento de concurrencia dependen del modo de procesamiento ara::com::MethodCallProcessingMode que se transfiere al constructor de ServiceSkeleton durante la instanciación [SWS_CM_00130]:

      

        

      • Si se configuró kEvent o kEventSingleThread, el método es invocado por el middleware guiado por eventos en cuanto se recibe y deserializa el mensaje de solicitud SOME/IP correspondiente [SWS_CM_10306].
        • 

      • En el modo kPoll, en cambio, la llamada se realiza de forma sincronizada en el subproceso de la aplicación de servicio cuando esta ejecuta explícitamente ProcessNextMethodCall() en la instancia del skeleton [SWS_CM_10307], [SWS_CM_00199].
