Contexto

La clase ara::tsync::SynchronizedTimeBaseConsumer constituye la interfaz central para que las aplicaciones en la Adaptive Platform accedan a una base de tiempo sincronizada direccionada mediante un identificador de instancia (ara::core::InstanceSpecifier). El consumidor permite la lectura del instante de tiempo actual, de la desviación de la tasa de reloj, del estado actual y de los datos de usuario recibidos.

En la arquitectura del sistema, la clase media entre el software de aplicación usuario y el subsistema Tsync:

  • Software de aplicación: Utiliza la instancia bien para la consulta cíclica de estado y tiempo, o bien reacciona de forma asíncrona a eventos configurados de la base de tiempo.
  • SynchronizedTimeBaseConsumer: Gestiona la vinculación específica del sistema al puerto y encapsula la lógica de consulta y de notificación.
  • Subsistema Tsync / base de tiempo: Proporciona las marcas de tiempo sincronizadas, la información de estado y los bloques de datos de validación.

Ciclo de vida

Una instancia de SynchronizedTimeBaseConsumer se crea mediante el constructor explícito [SWS_TS_01001] especificando un ara::core::InstanceSpecifier. Este constructor está especificado como seguro frente a excepciones (exception safe) y seguro para subprocesos (thread-safe).

En cuanto a la propiedad del objeto, la clase impone una semántica de movimiento estricta:

  • El constructor de copia [SWS_TS_01005] y el operador de asignación por copia [SWS_TS_01006] están eliminados (=delete), de modo que se impide la duplicación de instancias del consumidor.
  • Se admiten operaciones de movimiento a través del constructor de movimiento [SWS_TS_01003] y del operador de asignación por movimiento [SWS_TS_01004]. Ambas operaciones son noexcept, pero están clasificadas como no seguras para subprocesos (non_threadsafe).

La destrucción se realiza a través del destructor [SWS_TS_01002], que también es noexcept, pero non_threadsafe. Interpretación: Para evitar conflictos de concurrencia durante la destrucción o reasignación, es probable que las funciones de devolución de llamada registradas deban cancelarse explícitamente a través de las respectivas funciones de anulación de registro antes del final del ciclo de vida de la instancia.

En cuanto a la concurrencia durante el funcionamiento, cabe señalar que los accesos de solo lectura a la base de tiempo ([SWS_TS_01008], [SWS_TS_01009]) son seguros para subprocesos, mientras que todas las llamadas de registro y anulación de registro para notificadores (p. ej., [SWS_TS_01010], [SWS_TS_01011]) están clasificadas como non_threadsafe y requieren sincronización externa.

Ruta de uso

El flujo típico para el uso de una base de tiempo sincronizada se divide en inicialización, configuración de eventos, consultas operativas y limpieza:

  1. Instanciación: Creación del objeto con el InstanceSpecifier [SWS_TS_01001] adecuado.
  2. Registro de eventos: La aplicación registra según las necesidades funciones de devolución de llamada para los cambios de estado relevantes:
    • RegisterStatusChangeNotifier [SWS_TS_01010] para cambios generales de los indicadores de estado (estado de sincronización, saltos de tiempo o datos de usuario).
    • RegisterSynchronizationStateChangeNotifier [SWS_TS_01012] para cambios exclusivos del estado de sincronización.
    • RegisterTimeLeapNotifier [SWS_TS_01014] para el tratamiento diferenciado de los saltos de tiempo producidos.
    • RegisterTimePrecisionMeasurementNotifier [SWS_TS_01018] cuando haya disponibles nuevas instantáneas de precisión temporal.
    • RegisterTimeValidationNotification [SWS_TS_01016] para la recepción de bloques de datos de validación de la base de tiempo.
  3. Consulta operativa de tiempo y estado: La aplicación obtiene a través de GetTimeWithStatus [SWS_TS_01009] una instantánea del estado del reloj que contiene indicadores de estado, configuración del reloj, así como valores de tiempo locales y sincronizados. La desviación actual de la tasa del reloj se puede consultar mediante GetRateDeviation [SWS_TS_01008].
  4. Anulación de registro: Las notificaciones que ya no se necesitan se eliminan mediante las contrapartes correspondientes: UnregisterStatusChangeNotifier [SWS_TS_01011], UnregisterSynchronizationStateChangeNotifier [SWS_TS_01013], UnregisterTimeLeapNotifier [SWS_TS_01015], UnregisterTimeValidationNotification [SWS_TS_01017] y UnregisterTimePrecisionMeasurementNotifier [SWS_TS_01019].

Diagrama de secuencia: Flujo típico del registro de notificadores, la consulta de tiempo y la anulación de registro de un consumidor de tiempo. Fuentes: [SWS_TS_01001], [SWS_TS_01009], [SWS_TS_01010], [SWS_TS_01011]

Escenarios de error

Todas las funciones miembro de SynchronizedTimeBaseConsumer están definidas como noexcept y exception safe. Las condiciones de error surgen principalmente debido a un modelado incorrecto o a contextos de llamada no permitidos:

  • Configuración incorrecta de la interfaz de puerto: Si un PortPrototype referenciado por un TimeSyncPortPrototypeToTimeBaseMapping no está tipificado con el tipo de interfaz SynchronizedTimeBaseConsumerInterface, se produce una PortInterfaceMappingViolation durante la instanciación [SWS_TS_01001].
  • Sobrescritura de notificadores existentes: Para cada categoría de eventos solo se puede registrar como máximo un notificador al mismo tiempo. Cada nueva llamada a una función de registro ([SWS_TS_01010], [SWS_TS_01012], [SWS_TS_01014], [SWS_TS_01016], [SWS_TS_01018]) sobrescribe el registro existente sin previo aviso.
  • Pérdida de valores medidos por falta de cola: Conforme a [SWS_TS_01018], Tsync no realiza ningún tipo de gestión de colas (queuing) para las mediciones de precisión temporal. Si la aplicación no puede procesar instantáneas consecutivas de forma inmediata, estas deben almacenarse en búfer dentro del propio notificador, ya que, de lo contrario, es probable que los datos recién llegados se descarten.
  • Vulneración de la seguridad para subprocesos: Dado que el registro y la anulación de registro de notificadores están declarados como non_threadsafe, una llamada concurrente a estos métodos provoca inconsistencias de datos en la gestión de callbacks.

Esta guía se basa en la especificación para el release de AUTOSAR Adaptive R25-11.

<h4>Contexto</h4>
<p>La clase <code>ara::tsync::SynchronizedTimeBaseConsumer</code> constituye la interfaz central para que las aplicaciones en la Adaptive Platform accedan a una base de tiempo sincronizada direccionada mediante un identificador de instancia (<code>ara::core::InstanceSpecifier</code>). El consumidor permite la lectura del instante de tiempo actual, de la desviación de la tasa de reloj, del estado actual y de los datos de usuario recibidos.</p>
<p>En la arquitectura del sistema, la clase media entre el software de aplicación usuario y el subsistema Tsync:</p>
<ul>
<li><strong>Software de aplicación:</strong> Utiliza la instancia bien para la consulta cíclica de estado y tiempo, o bien reacciona de forma asíncrona a eventos configurados de la base de tiempo.</li>
<li><strong>SynchronizedTimeBaseConsumer:</strong> Gestiona la vinculación específica del sistema al puerto y encapsula la lógica de consulta y de notificación.</li>
<li><strong>Subsistema Tsync / base de tiempo:</strong> Proporciona las marcas de tiempo sincronizadas, la información de estado y los bloques de datos de validación.</li>
</ul>

<h4>Ciclo de vida</h4>
<p>Una instancia de <code>SynchronizedTimeBaseConsumer</code> se crea mediante el constructor explícito <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a> especificando un <code>ara::core::InstanceSpecifier</code>. Este constructor está especificado como seguro frente a excepciones (<code>exception safe</code>) y seguro para subprocesos (<code>thread-safe</code>).</p>
<p>En cuanto a la propiedad del objeto, la clase impone una semántica de movimiento estricta:</p>
<ul>
<li>El constructor de copia <a class="spec-record-ref" data-req="SWS_TS_01005" href="../spec/record.html?id=SWS_TS_01005">[SWS_TS_01005]</a> y el operador de asignación por copia <a class="spec-record-ref" data-req="SWS_TS_01006" href="../spec/record.html?id=SWS_TS_01006">[SWS_TS_01006]</a> están eliminados (<code>=delete</code>), de modo que se impide la duplicación de instancias del consumidor.</li>
<li>Se admiten operaciones de movimiento a través del constructor de movimiento <a class="spec-record-ref" data-req="SWS_TS_01003" href="../spec/record.html?id=SWS_TS_01003">[SWS_TS_01003]</a> y del operador de asignación por movimiento <a class="spec-record-ref" data-req="SWS_TS_01004" href="../spec/record.html?id=SWS_TS_01004">[SWS_TS_01004]</a>. Ambas operaciones son <code>noexcept</code>, pero están clasificadas como no seguras para subprocesos (<code>non_threadsafe</code>).</li>
</ul>
<p>La destrucción se realiza a través del destructor <a class="spec-record-ref" data-req="SWS_TS_01002" href="../spec/record.html?id=SWS_TS_01002">[SWS_TS_01002]</a>, que también es <code>noexcept</code>, pero <code>non_threadsafe</code>. Interpretación: Para evitar conflictos de concurrencia durante la destrucción o reasignación, es probable que las funciones de devolución de llamada registradas deban cancelarse explícitamente a través de las respectivas funciones de anulación de registro antes del final del ciclo de vida de la instancia.</p>
<p>En cuanto a la concurrencia durante el funcionamiento, cabe señalar que los accesos de solo lectura a la base de tiempo (<a class="spec-record-ref" data-req="SWS_TS_01008" href="../spec/record.html?id=SWS_TS_01008">[SWS_TS_01008]</a>, <a class="spec-record-ref" data-req="SWS_TS_01009" href="../spec/record.html?id=SWS_TS_01009">[SWS_TS_01009]</a>) son seguros para subprocesos, mientras que todas las llamadas de registro y anulación de registro para notificadores (p. ej., <a class="spec-record-ref" data-req="SWS_TS_01010" href="../spec/record.html?id=SWS_TS_01010">[SWS_TS_01010]</a>, <a class="spec-record-ref" data-req="SWS_TS_01011" href="../spec/record.html?id=SWS_TS_01011">[SWS_TS_01011]</a>) están clasificadas como <code>non_threadsafe</code> y requieren sincronización externa.</p>

<h4>Ruta de uso</h4>
<p>El flujo típico para el uso de una base de tiempo sincronizada se divide en inicialización, configuración de eventos, consultas operativas y limpieza:</p>
<ol>
<li><strong>Instanciación:</strong> Creación del objeto con el <code>InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a> adecuado.</li>
<li><strong>Registro de eventos:</strong> La aplicación registra según las necesidades funciones de devolución de llamada para los cambios de estado relevantes:
<ul>
<li><code>RegisterStatusChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01010" href="../spec/record.html?id=SWS_TS_01010">[SWS_TS_01010]</a> para cambios generales de los indicadores de estado (estado de sincronización, saltos de tiempo o datos de usuario).</li>
<li><code>RegisterSynchronizationStateChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01012" href="../spec/record.html?id=SWS_TS_01012">[SWS_TS_01012]</a> para cambios exclusivos del estado de sincronización.</li>
<li><code>RegisterTimeLeapNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01014" href="../spec/record.html?id=SWS_TS_01014">[SWS_TS_01014]</a> para el tratamiento diferenciado de los saltos de tiempo producidos.</li>
<li><code>RegisterTimePrecisionMeasurementNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01018" href="../spec/record.html?id=SWS_TS_01018">[SWS_TS_01018]</a> cuando haya disponibles nuevas instantáneas de precisión temporal.</li>
<li><code>RegisterTimeValidationNotification</code> <a class="spec-record-ref" data-req="SWS_TS_01016" href="../spec/record.html?id=SWS_TS_01016">[SWS_TS_01016]</a> para la recepción de bloques de datos de validación de la base de tiempo.</li>
</ul>
</li>
<li><strong>Consulta operativa de tiempo y estado:</strong> La aplicación obtiene a través de <code>GetTimeWithStatus</code> <a class="spec-record-ref" data-req="SWS_TS_01009" href="../spec/record.html?id=SWS_TS_01009">[SWS_TS_01009]</a> una instantánea del estado del reloj que contiene indicadores de estado, configuración del reloj, así como valores de tiempo locales y sincronizados. La desviación actual de la tasa del reloj se puede consultar mediante <code>GetRateDeviation</code> <a class="spec-record-ref" data-req="SWS_TS_01008" href="../spec/record.html?id=SWS_TS_01008">[SWS_TS_01008]</a>.</li>
<li><strong>Anulación de registro:</strong> Las notificaciones que ya no se necesitan se eliminan mediante las contrapartes correspondientes: <code>UnregisterStatusChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01011" href="../spec/record.html?id=SWS_TS_01011">[SWS_TS_01011]</a>, <code>UnregisterSynchronizationStateChangeNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01013" href="../spec/record.html?id=SWS_TS_01013">[SWS_TS_01013]</a>, <code>UnregisterTimeLeapNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01015" href="../spec/record.html?id=SWS_TS_01015">[SWS_TS_01015]</a>, <code>UnregisterTimeValidationNotification</code> <a class="spec-record-ref" data-req="SWS_TS_01017" href="../spec/record.html?id=SWS_TS_01017">[SWS_TS_01017]</a> y <code>UnregisterTimePrecisionMeasurementNotifier</code> <a class="spec-record-ref" data-req="SWS_TS_01019" href="../spec/record.html?id=SWS_TS_01019">[SWS_TS_01019]</a>.</li>
</ol>

<h4>Escenarios de error</h4>
<p>Todas las funciones miembro de <code>SynchronizedTimeBaseConsumer</code> están definidas como <code>noexcept</code> y <code>exception safe</code>. Las condiciones de error surgen principalmente debido a un modelado incorrecto o a contextos de llamada no permitidos:</p>
<ul>
<li><strong>Configuración incorrecta de la interfaz de puerto:</strong> Si un <code>PortPrototype</code> referenciado por un <code>TimeSyncPortPrototypeToTimeBaseMapping</code> no está tipificado con el tipo de interfaz <code>SynchronizedTimeBaseConsumerInterface</code>, se produce una <code>PortInterfaceMappingViolation</code> durante la instanciación <a class="spec-record-ref" data-req="SWS_TS_01001" href="../spec/record.html?id=SWS_TS_01001">[SWS_TS_01001]</a>.</li>
<li><strong>Sobrescritura de notificadores existentes:</strong> Para cada categoría de eventos solo se puede registrar como máximo un notificador al mismo tiempo. <li><strong>Pérdida de valores medidos por falta de cola:</strong> Conforme a <a class="spec-record-ref" data-req="SWS_TS_01018" href="../spec/record.html?id=SWS_TS_01018">[SWS_TS_01018]</a>, Tsync no realiza ningún tipo de gestión de colas (queuing) para las mediciones de precisión temporal. Si la aplicación no puede procesar instantáneas consecutivas de forma inmediata, estas deben almacenarse en búfer dentro del propio notificador, ya que, de lo contrario, es probable que los datos recién llegados se descarten.</li>
<li><strong>Vulneración de la seguridad para subprocesos:</strong> Dado que el registro y la anulación de registro de notificadores están declarados como <code>non_threadsafe</code>, una llamada concurrente a estos métodos provoca inconsistencias de datos en la gestión de callbacks.</li>
</ul>
