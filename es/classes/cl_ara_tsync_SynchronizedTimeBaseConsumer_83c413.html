Permite a las aplicaciones consultar valores de tiempo sincronizados de forma segura para subprocesos, así como registrar notificadores de estado.

La clase ara::tsync::SynchronizedTimeBaseConsumer permite a las aplicaciones de tiempo acceder a una base de tiempo sincronizada referenciada a través de un ara::core::InstanceSpecifier ([SWS_TS_01001]). A través de métodos seguros para subprocesos, las aplicaciones pueden consultar instantáneas actuales de valores de tiempo y flags de estado, así como la desviación de tasa del reloj ([SWS_TS_01009]). Además, pueden registrarse notificadores para cambios de estado, saltos temporales, datos de validación y mediciones de precisión, permaneciendo activo como máximo un registro por cada tipo de evento. Las operaciones de copia están impedidas, de modo que las instancias únicamente pueden moverse o liberarse a través de su destructor.

Contexto

La clase ara::tsync::SynchronizedTimeBaseConsumer constituye para aplicaciones de tiempo en la Adaptive Platform la interfaz con una base de tiempo sincronizada identificada mediante un ara::core::InstanceSpecifier ([SWS_TS_01001]). Su tarea principal consiste en proporcionar a las aplicaciones el momento de consulta actual, la desviación de tasa del reloj ([SWS_TS_01008]), así como flags de estado consistentes y datos de usuario recibidos ([SWS_TS_01009]). Los interlocutores principales son el software de aplicación invocador (Time Consumer Application), la propia instancia consumidora y el subsistema Tsync, que adquiere datos de sincronización y desencadena eventos de notificación ([SWS_TS_01016], [SWS_TS_01018]).

Ciclo de vida

La instanciación se realiza a través del constructor explícito indicando un ara::core::InstanceSpecifier ([SWS_TS_01001]). Este constructor está clasificado como seguro para subprocesos y a prueba de excepciones. Para gestionar los recursos, la clase implementa una semántica de movimiento estricta: el constructor de movimiento ([SWS_TS_01003]) y el operador de asignación por movimiento ([SWS_TS_01004]) permiten la transferencia de propiedad, mientras que el constructor de copia ([SWS_TS_01005]) y el operador de asignación por copia ([SWS_TS_01006]) están explícitamente eliminados (=delete). Esto evita duplicaciones involuntarias del acceso al mismo recurso de base de tiempo.

El destructor libera la instancia ([SWS_TS_01002]). En cuanto a la concurrencia, rige una clara separación: mientras que el constructor ([SWS_TS_01001]) así como los métodos de consulta GetRateDeviation ([SWS_TS_01008]) y GetTimeWithStatus ([SWS_TS_01009]) están implementados como seguros para subprocesos, todas las funciones de registro y cancelación de registro, así como las operaciones de movimiento y el destructor, están especificados como no seguros para subprocesos (non_threadsafe).

Ruta de uso

Una secuencia de uso regular comprende las fases de inicialización, registro de notificadores relevantes, consultas cíclicas o impulsadas por eventos, y la limpieza final:

  • Inicialización: la aplicación crea el objeto con la especificación de instancia de puerto adecuada ([SWS_TS_01001]).
  • Registro de notificadores: la aplicación registra funciones de retrollamada u objetos notificadores para eventos específicos:
    • cambios generales de flags de estado a través de RegisterStatusChangeNotifier ([SWS_TS_01010]),
    • cambios del estado de sincronización a través de RegisterSynchronizationStateChangeNotifier ([SWS_TS_01012]),
    • aparición de un salto temporal a través de RegisterTimeLeapNotifier ([SWS_TS_01014]),
    • recepción de bloques de datos de validación a través de RegisterTimeValidationNotification ([SWS_TS_01016]),
    • disponibilidad de mediciones de precisión temporal a través de RegisterTimePrecisionMeasurementNotifier ([SWS_TS_01018]).
    Por cada tipo de notificador puede estar activo como máximo un registro; cada nuevo registro sobrescribe el anterior ([SWS_TS_01010], [SWS_TS_01018]).
  • Consulta durante el funcionamiento: a través de GetTimeWithStatus(), la aplicación consulta una instantánea coherente (SynchronizedTimeBaseStatus) con flags de estado, configuración del reloj y valores de tiempo tanto locales como sincronizados ([SWS_TS_01009]). Mediante GetRateDeviation() se determina la desviación de tasa actual del reloj ([SWS_TS_01008]).
  • Limpieza: antes de desmontar el consumidor, los notificadores se desregistran según sea necesario a través de las llamadas correspondientes como UnregisterStatusChangeNotifier ([SWS_TS_01011]), UnregisterSynchronizationStateChangeNotifier ([SWS_TS_01013]), UnregisterTimeLeapNotifier ([SWS_TS_01015]), UnregisterTimeValidationNotification ([SWS_TS_01017]) o UnregisterTimePrecisionMeasurementNotifier ([SWS_TS_01019]), antes de que se destruya el objeto ([SWS_TS_01002]).

Diagrama de secuencias: secuencia típica de inicialización, registro de notificadores, consulta cíclica y limpieza. Fuentes: [SWS_TS_01001], [SWS_TS_01008], [SWS_TS_01009], [SWS_TS_01010], [SWS_TS_01011], [SWS_TS_01002].

Escenarios de error

Todos los métodos de interfaz de la clase están declarados con noexcept y especificados como a prueba de excepciones (exception safe). Por lo tanto, los errores no se señalan mediante excepciones de C++. Deben tenerse en cuenta las siguientes condiciones de contorno y violaciones de configuración:

  • Error de configuración de mapeo de puertos: un PortPrototype al que se hace referencia a través de un TimeSyncPortPrototypeToTimeBaseMapping debe estar tipificado obligatoriamente a través de un SynchronizedTimeBaseConsumerInterface; de lo contrario, se produce una PortInterfaceMappingViolation ([SWS_TS_01001]).
  • Sobrescritura de retrollamadas existentes: si se llama de nuevo a un método de registro, el nuevo notificador sobrescribe la retrollamada previamente depositada sin un mensaje de error específico ([SWS_TS_01010], [SWS_TS_01012], [SWS_TS_01014], [SWS_TS_01016], [SWS_TS_01018]).
  • Falta de puesta en cola en mediciones de precisión: el subsistema Tsync no realiza ningún almacenamiento intermedio (puesta en cola) para datos de medición de la precisión temporal ([SWS_TS_01018]). Si el notificador no puede procesar los datos a tiempo, las mediciones sucesivas presumiblemente se pierden en caso de que la aplicación no prevea un almacenamiento en búfer propio en el notificador.
  • Riesgo de carreras de datos en métodos de notificadores: puesto que los registros y cancelaciones de registro de notificadores están designados como no seguros para subprocesos, una llamada concurrente desde distintos contextos de ejecución sin mecanismos de protección externos daría lugar presumiblemente a estados inconsistentes (interpretación).
