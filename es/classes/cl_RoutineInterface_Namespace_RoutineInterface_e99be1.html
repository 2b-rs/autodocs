Contexto

La clase <RoutineInterface-Namespace>::<RoutineInterface> constituye en el módulo AUTOSAR Adaptive diag la interfaz C++ central para la provisión y el control de rutinas de diagnóstico (AUTOSAR AP SWS Diagnostics p. 68). En el contexto del servicio UDS RoutineControl (servicio 0x31 según ISO 14229-1), una derivación de esta clase específica de la aplicación actúa como manejador en el lado del servidor. La clase recibe solicitudes que son reenviadas a la aplicación por el Diagnostic Management (DM) central ([SWS_DM_00594]). La interfaz define las tres operaciones de control esenciales de una rutina: el inicio mediante Start ([SWS_DM_00591]), la detención mediante Stop ([SWS_DM_00592]), así como la consulta de resultados mediante RequestResult ([SWS_DM_00593]). La vinculación funcional en el sistema se realiza a través de un PortPrototype de tipo DiagnosticRoutineInterface, el cual debe referenciarse en el modelo mediante un DiagnosticServiceGenericMapping ([SWS_DM_00589]).

Ciclo de vida

La creación de un manejador de rutinas se realiza a través del constructor parametrizado especificando un ara::core::InstanceSpecifier y la concurrencia deseada ara::diag::ConcurrencyType ([SWS_DM_00589]). Mediante el parámetro concurrencyType se define si la interfaz está implementada como segura para subprocesos (kConcurrent) o no segura para subprocesos (kNotConcurrent) ([SWS_DM_00589]). La llamada al constructor en sí misma está declarada como segura para subprocesos y noexcept ([SWS_DM_00589]).

Con respecto a la semántica del objeto, <RoutineInterface> posee una identidad unívoca: el constructor de copia ([SWS_DM_01669]), el constructor de movimiento ([SWS_DM_01670]), el operador de asignación por copia ([SWS_DM_01667]) y el operador de asignación por movimiento ([SWS_DM_01668]) están explícitamente eliminados (=delete). Por lo tanto, queda excluida la duplicación o el movimiento de instancias.

Tras la construcción, la instancia se encuentra en estado inactivo. Solo mediante la llamada a Offer() se activa el reenvío de solicitudes de diagnóstico entrantes por parte del Diagnostic Management a este manejador ([SWS_DM_00594]). Mediante StopOffer() se vuelve a desactivar el reenvío de solicitudes ([SWS_DM_00595]). La liberación de la instancia se realiza a través del destructor virtual ~<RoutineInterface>(), el cual está especificado como noexcept y no seguro para subprocesos ([SWS_DM_00590]). Antes de llamar al destructor, presumiblemente debería llamarse a StopOffer() para anular de forma limpia los reenvíos pendientes del DM antes de la destrucción del objeto.

Diagrama de estados: Estados de ciclo de vida y de activación de la interfaz de rutina. Fuentes: [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00595], [SWS_DM_00590].

Ruta de uso

La ruta de uso típica se divide en inicialización, procesamiento de solicitudes y finalización:

  1. Instanciación: La aplicación deriva una clase de implementación a partir de <RoutineInterface>, sobrescribe los métodos virtuales puros y crea la instancia con el InstanceSpecifier correspondiente, así como la especificación de ConcurrencyType ([SWS_DM_00589]).
  2. Oferta de servicio (Offer): La aplicación llama a Offer() ([SWS_DM_00594]), con lo cual se autoriza al DM a reenviar solicitudes de rutina.
  3. Procesamiento de operaciones de control:
    • Iniciar rutina: Si llega una solicitud de inicio, el DM llama al método Start(...) con los argumentos de entrada modelados, ara::diag::MetaInfo y un ara::diag::CancellationHandler ([SWS_DM_00591]). El método devuelve un ara::core::Future con el objeto StartOutput correspondiente ([SWS_DM_00581], [SWS_DM_80003]).
    • Solicitar resultados: Mediante RequestResult(...) se consultan los resultados intermedios o finales de la rutina ([SWS_DM_00593]). El ara::core::Future devuelto proporciona el objeto RequestResultOutput ([SWS_DM_00583], [SWS_DM_80005]).
    • Detener rutina: Una ejecución activa de la rutina se finaliza mediante la llamada a Stop(...) ([SWS_DM_00592]), el cual devuelve un ara::core::Future con el objeto StopOutput ([SWS_DM_00582], [SWS_DM_80004]).
    • Tratamiento de cancelación: A través del cancellationHandler transmitido, el manejador puede consultar el estado de cancelación mediante IsCanceled() o registrar un callback mediante SetNotifier(...) en caso de que la conversación de diagnóstico se cancele prematuramente ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).
  4. Finalizar oferta de servicio (StopOffer): Si el manejador ya no debe atender más solicitudes, la aplicación llama a StopOffer() ([SWS_DM_00595]).

Diagrama de secuencia: Patrón de interacción entre la aplicación, el manejador de rutina y el Diagnostic Management. Fuentes: [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00591], [SWS_DM_00593], [SWS_DM_00592], [SWS_DM_00595].

Escenarios de error

Las situaciones de error pueden ocurrir tanto durante la instanciación y la provisión como durante la ejecución propiamente dicha de la rutina:

  • Vulneraciones de integridad y de modelo durante la construcción: Aunque el constructor está declarado como noexcept, se desencadenan violaciones en caso de errores de configuración ([SWS_DM_00589]):
    • InstanceSpecifierMappingIntegrityViolation: El InstanceSpecifier no se puede resolver en el contexto de modelo del ejecutable o no hace referencia a un PortPrototype ([SWS_DM_00589]).
    • PortInterfaceMappingViolation: El PortPrototype de tipo DiagnosticRoutineInterface no está referenciado por un DiagnosticServiceGenericMapping ([SWS_DM_00589]).
    • ProcessMappingViolation: Existe una InstanceRef modelada, pero ningún proceso modelado coincide con el proceso de tiempo de ejecución actual ([SWS_DM_00589]).
    • InstanceSpecifierAlreadyInUseViolation: El InstanceSpecifier especificado ya está siendo utilizado por otra instancia en este proceso ([SWS_DM_00589]).
  • Error durante la provisión (Offer): Si se llama a Offer() cuando el servicio ya se está ofreciendo, el método devuelve un ara::core::Result<void> con el código de error DiagOfferErrc::kAlreadyOffered ([SWS_DM_00594]). La llamada está especificada como no segura para subprocesos ([SWS_DM_00594]).
  • Errores funcionales durante la ejecución de las operaciones: Si las operaciones Start, Stop o RequestResult fallan, los métodos no lanzan excepciones (todos los métodos son noexcept). En su lugar, el error se transporta de forma asíncrona mediante el ara::core::Future devuelto. Para ello, la implementación debe proporcionar un UDS Negative Response Code (NRC) adecuado conforme a ISO 14229-1 mediante ara::diag::DiagUdsNrcErrc o un Ap ApplicationError ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).

Esta guía se basa en la especificación de AUTOSAR Adaptive R25-11 para el módulo diag.
