GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 7ece784e04d9 Procedencia

Permite al skeleton del servicio la provisión, actualización y procesamiento tipificado de peticiones de campo.

La clase <SI-Namespace>::skeleton::fields::<Field> proporciona en el lado del servidor un campo de una ServiceInterface y conecta funciones de obtención (getter), establecimiento (setter) y notificación para el servicio proporcionado. La aplicación proveedora registra controladores asíncronos ([SWS_CM_00114], [SWS_CM_00116]) para los accesos entrantes de lectura y escritura, y distribuye activamente los cambios de valor a los clientes suscritos mediante el método Update ([SWS_CM_00119]). Para ello, los controladores transferidos deben ser estrictamente válidos, mientras que las llamadas de envío deben respetar el tiempo mínimo de transmisión configurado a fin de evitar errores como kMinimumSendIntervalViolationError.

Contexto

La clase plantilla <SI-Namespace>::skeleton::fields::<Field> encapsula la representación del lado del servidor de un campo modelado en la ServiceInterface dentro de la gestión de comunicaciones de Adaptive. Para cada campo definido en la interfaz de servicio, el middleware genera una instancia de clase correspondiente en el espacio de nombres skeleton::fields utilizando la ruta de encabezado #include "<SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h". Un campo combina características funcionales de transmisiones de datos y llamadas a métodos, ya que dispone opcionalmente de un getter, un setter y una función de notificación. El tipo de datos asociado del valor de campo se proporciona mediante el alias de tipo FieldType ([SWS_CM_11402]). Entre los interlocutores centrales se encuentran la aplicación proveedora que lo suministra, la instancia de campo del skeleton como intermediario, los consumidores del servicio suscritos (proxies), así como contextos de ejecución opcionales en forma de un ejecutor ([SWS_CM_11360], [SWS_CM_11362]).

Diagrama de contexto: Interlocutores de la clase Field del skeleton en peticiones y notificaciones. Fuentes: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360].

Ciclo de vida

La vida útil de la instancia de campo está estrechamente vinculada a la instancia de skeleton del servicio de nivel superior. Interpretación: La instancia de Field debería instanciarse como objeto miembro de la clase skeleton correspondiente y compartir íntegramente su ciclo de vida. La disponibilidad de los métodos individuales de la interfaz depende directamente de la definición en el diseño de software: El método RegisterGetHandler existe únicamente si el campo se configuró con Field.hasGetter == TRUE ([SWS_CM_00114]), mientras que RegisterSetHandler presupone la presencia de un setter mediante Field.hasSetter == TRUE ([SWS_CM_00116]). Para proteger la comunicación frente a fallos de transporte extremo a extremo, la aplicación puede registrar un controlador específico mediante SetTransportFaultConditionHandler ([SWS_CM_00096]) y eliminarlo de nuevo cuando sea necesario a través de UnsetTransportFaultConditionHandler ([SWS_CM_00098]). En lo relativo a la concurrencia, las sobrecargas con el parámetro de plantilla ExecutorT (como ara::core::Executor) ofrecen la posibilidad de trasladar la ejecución de las funciones de retrollamada a un contexto de ejecución asíncrono definido ([SWS_CM_11360], [SWS_CM_11362], [SWS_CM_00097], AUTOSAR_AP_EXP_ARAComAPI p. 11).

Ruta de uso

El flujo operativo habitual se divide en la configuración de las funciones de retrollamada, el procesamiento de consultas y el envío activo de actualizaciones de datos:

Interpretación: El registro de los controladores debería realizarse convenientemente antes de ofrecer el servicio para poder atender las peticiones entrantes sin interrupciones. En caso de existir un getter, la aplicación vincula mediante RegisterGetHandler una función de retrollamada que devuelve un ara::core::Future<FieldType> ([SWS_CM_00114]). Para accesos modificadores, registra a través de RegisterSetHandler un controlador que recibe el nuevo valor, lo procesa y proporciona el estado resultante también de forma asíncrona a través de un future ([SWS_CM_00116]). Si el proveedor del servicio desea actualizar de manera autónoma el valor del campo, invoca el método Update con el nuevo valor ([SWS_CM_00119], AUTOSAR_AP_EXP_ARAComAPI p. 11). De este modo se vuelve a establecer el estado interno del campo. Siempre que el campo se haya modelado con función de notificación (Field.hasNotifier == TRUE), Update desencadena la transmisión inmediata del valor de datos modificado a todos los suscriptores registrados ([SWS_CM_00119], [SWS_CM_00120], [SWS_CM_00162]).

Diagrama de secuencia: Flujo típico del registro de controladores, procesamiento de peticiones y actualización de datos. Fuentes: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119].

Escenarios de error

Las condiciones de error se manifiestan o bien como infracciones de contratos de programación durante el registro, o bien como errores de transmisión en tiempo de ejecución. Todos los métodos de registro de controladores —RegisterGetHandler, RegisterSetHandler y SetTransportFaultConditionHandler— están especificados como noexcept y poseen la garantía de excepción exception safe ([SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00096]). Como precondición se establece que el objeto invocable (callable) transferido debe existir y no puede ser nulo; el incumplimiento desencadena una InvalidHandlerViolation ([SWS_CM_00114], [SWS_CM_11360], [SWS_CM_00116], [SWS_CM_11362], [SWS_CM_00096], [SWS_CM_00097]).

En caso de actualización activa a través de Update, la notificación de error se efectúa mediante el tipo de retorno ara::core::Result<void> ([SWS_CM_00119]). Si se produce un error, el objeto Result devuelve un código de error de ara::com::ComErrc. En particular, realizar envíos a intervalos más breves que los determinados por el atributo de despliegue ServiceInterfaceDeploymentElement.minimumSendInterval provoca la devolución del error ComErrc::kMinimumSendIntervalViolationError ([SWS_CM_00119]).

función RegisterGetHandler [SWS_CM_00114] Upstream: RS_CM_00218, RS_AP_00114, RS_AP_00120, RS_AP_00127, RS_AP_00128, RS_AP_00138

void RegisterGetHandler (std::function< ara::core::Future< FieldType >()> handler) noexcept;

Register a callback function to be invoked when a Get() request is received. The method exists only if the offered service contains a Field and Field.hasGetter ==TRUE

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 01ae49e1e2d8 Procedencia

usar

El método RegisterGetHandler se invoca en el lado del servidor sobre el objeto de campo de un skeleton ([SWS_CM_00114]). Solo existe en el código generado si en la descripción de interfaz se ha configurado un getter para el campo en cuestión (Field.hasGetter == TRUE) (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Se pasa un callback handler de tipo std::function<ara::core::Future<FieldType>()>, el cual es invocado por la implementación del binding ante una solicitud Get() entrante de un proxy.

El registro de dicho manejador es completamente opcional (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Por lo general, la implementación del servicio no requiere un manejador de getter, ya que Communication Management almacena en caché el último valor establecido mediante Update() y responde a las solicitudes de proxy de forma autónoma. Un manejador tiene sentido sobre todo si la determinación del valor del campo requiere mucho tiempo o cómputo y, por lo tanto, solo debe realizarse de forma asíncrona mediante el patrón promise/future ante una necesidad real.

Tratamiento de errores y condiciones límite

La función no tiene valor de retorno, está declarada como noexcept y es segura frente a excepciones (exception safe) ([SWS_CM_00114]). Si el invocable suministrado no existe o es null, se produce el error InvalidHandlerViolation ([SWS_CM_00114]).

Interacción

A diferencia de RegisterSetHandler, cuya invocación es obligatoria si hay un setter presente (EXP ARAComAPI §5.4.8.2 «Registering Setters»), RegisterGetHandler sigue siendo puramente opcional. Si el manejador se debe procesar de forma asíncrona en un contexto de ejecución específico, se encuentra disponible adicionalmente la función de plantilla sobrecargada con ExecutorT ([SWS_CM_11360]).

  Procedencia
  

      

      

      usar
      

      El método RegisterGetHandler en el espacio de nombres <SI-Namespace>::skeleton::fields::<Field> registra una devolución de llamada del lado de la aplicación (handler) que es invocada por la vinculación de comunicación ante una llamada Get() entrante de un proxy ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). A diferencia de la sobrecarga básica sin parámetros [SWS_CM_00114], el método recibe un contexto de ejecución executor de tipo ExecutorT, en el cual la ejecución del callback se efectúa de forma asíncrona ([SWS_CM_11360]). Como ejecutor se puede emplear el ara::core::Executor estandarizado o un tipo específico de usuario con la misma interfaz ([SWS_CM_11360]).
      

      El manejador registrado devuelve un ara::core::Future<FieldType>, desacoplando así el cálculo del valor del campo mediante el patrón promise/future ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). El registro es completamente opcional: si no hay ningún manejador registrado, Communication Management responde a las peticiones de forma autónoma con el último valor establecido mediante Update() (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Un manejador getter es adecuado principalmente para determinar bajo demanda valores de campo complejos o que requieren mucho tiempo (EXP ARAComAPI §5.4.8.1 «Registering Getters»).
      

      Restricciones y tratamiento de errores
      

      El método existe en el skeleton exclusivamente si se ha configurado un getter para el campo en el IDL (Field.hasGetter == TRUE, [SWS_CM_00114], EXP ARAComAPI §5.4.8.1 «Registering Getters»). RegisterGetHandler está declarado como noexcept; no obstante, si se proporciona un invocable (callable) no válido o vacío, se produce un InvalidHandlerViolation ([SWS_CM_11360]). Interpretación: el ejecutor proporcionado debería tener que permanecer válido durante todo el tiempo de uso del manejador, ya que las peticiones entrantes se dirigen de forma asíncrona a su contexto.

  Procedencia
  

          

          

          usar
          

          El método RegisterSetHandler sirve, en el lado del servidor (skeleton), para registrar una función de callback que se invoca al recibir una solicitud Set() de un cliente para un campo [SWS_CM_00116]. El método existe exclusivamente si el campo ofrecido está configurado con soporte para setter (Field.hasSetter == TRUE) [SWS_CM_00116]. A diferencia del registro del getter, la llamada a RegisterSetHandler es obligatoria, ya que la implementación del servidor debe validar previamente los valores de campo nuevos o actualizados de clientes anónimos EXP ARAComAPI §5.4.8.2 «Registering Setters».
          

          El manejador registrado recibe el nuevo valor como argumento y devuelve un ara::core::Future<FieldType> con el valor efectivo, eventualmente corregido [SWS_CM_00116], EXP ARAComAPI §5.4.8.2 «Registering Setters». Este valor efectivo es aceptado implícitamente por la gestión de comunicación y publicado a los clientes; por lo tanto, una llamada explícita a Update() dentro del manejador es superflua EXP ARAComAPI §5.4.8.2 «Registering Setters».
          

          Tratamiento de errores y condiciones límite
          

          La función está definida como noexcept y es segura frente a excepciones [SWS_CM_00116]. Si se transfiere un callable inexistente o no válido (null), se produce una vulneración de la especificación en forma de InvalidHandlerViolation [SWS_CM_00116]. Interpretación: Es de suponer que el registro debe realizarse antes de ofrecer el servicio mediante OfferService() para poder recibir solicitudes entrantes de clientes desde el principio.
          

          Interacción
          

          Además del método base, existe una sobrecarga de plantilla [SWS_CM_11362] con la que la ejecución del manejador puede vincularse a un contexto de ejecución específico (ExecutorT según [SWS_CM_11360]) EXP ARAComAPI.
