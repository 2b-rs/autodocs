Contexto

En AUTOSAR Adaptive (módulo diag), la clase ara::diag::DTCInformation proporciona interfaces funcionales para llevar a cabo operaciones y consultas de estado sobre información de DTC (Diagnostic Trouble Code) referidas a un destino de memoria de diagnóstico configurado (DiagnosticMemoryDestination) [SWS_DM_00664]. Sirve de enlace entre la lógica de diagnóstico y monitorización específica de la aplicación y el Diagnostic Management (DM) subyacente.

Entre los interlocutores principales se encuentran la Adaptive Application, la gestión de memoria interna del DM y los comprobadores de diagnóstico externos. Estos últimos interactúan de forma estandarizada con la unidad de control mediante servicios UDS como el Service 0x19 (ReadDTCInformation) o el Service 0x85 (ControlDTCSetting), donde el DM define restricciones específicas relativas a subfunciones y áreas de memoria admitidas AUTOSAR AP SWS Diagnostics §4.1 «Limitations of sub-functions of 0x19 ReadDTCInformation». La aplicación utiliza ara::diag::DTCInformation para consultar estados de DTC, recibir notificaciones en caso de cambios de estado, consultar estados de control y, en caso necesario, borrar de manera selectiva entradas de la memoria de averías [SWS_DM_00666] [SWS_DM_00671] [SWS_DM_00672].

Diagrama de contexto: relaciones de interacción de la clase ara::diag::DTCInformation en el sistema de diagnóstico global. Fuentes: [SWS_DM_00664], [SWS_DM_00672], AUTOSAR AP SWS Diagnostics §4.1 «Limitations of sub-functions of 0x19 ReadDTCInformation».

Ciclo de vida

La instanciación de ara::diag::DTCInformation se realiza explícitamente mediante la transferencia de un ara::core::InstanceSpecifier, que debe hacer referencia a un PortPrototype modelado de una DiagnosticDTCInformationInterface [SWS_DM_00664]. El constructor está especificado como thread-safe y seguro frente a excepciones (noexcept) [SWS_DM_00664].

En lo relativo a la propiedad, la clase está concebida como un objeto único estricto: tanto el constructor de copia como el constructor de movimiento, así como los operadores de asignación correspondientes, están eliminados (=delete) [SWS_DM_01611] [SWS_DM_01612] [SWS_DM_01613] [SWS_DM_01614]. Por consiguiente, una instancia no se puede copiar ni mover, sino que permanece en su lugar de creación original durante toda su vida útil.

La destrucción tiene lugar a través del destructor ~DTCInformation() [SWS_DM_00665]. El destructor está clasificado como not thread-safe, por lo que debe garantizarse que no se produzcan accesos concurrentes a la misma instancia durante su desmantelamiento. El modelo de concurrencia distingue claramente entre métodos de lectura y métodos de modificación: los métodos de consulta pura como GetCurrentStatus [SWS_DM_00666], GetControlDTCStatus [SWS_DM_00672], GetNumberOfStoredEntries [SWS_DM_00669] y GetEventMemoryOverflow [SWS_DM_00919] son thread-safe. Las acciones modificadoras como Clear [SWS_DM_00671] y EnableControlDtc [SWS_DM_00674], así como todos los registros de callbacks de notificación, son not thread-safe y requieren sincronización externa en caso de acceso compartido.

Ruta de uso

Una ruta de uso típica incluye la creación de la instancia, la configuración de funciones de callback dirigidas por eventos, la consulta periódica o puntual de valores de estado y la ejecución de acciones de control o purga:

  1. Inicialización: la aplicación instancia ara::diag::DTCInformation especificando el InstanceSpecifier correspondiente [SWS_DM_00664].
  2. Registro de notificadores: para el tratamiento reactivo de eventos de diagnóstico, la aplicación registra funciones de callback, por ejemplo a través de SetDTCStatusChangedNotifier con el tipo DtcStatusChangedNotifier [SWS_DM_00667] [SWS_DM_02122], SetNumberOfStoredEntriesNotifier [SWS_DM_00670] [SWS_DM_02124], SetEventMemoryOverflowNotifier [SWS_DM_00918] [SWS_DM_02076], SetControlDtcStatusNotifier [SWS_DM_00673] [SWS_DM_02125] o SetSnapshotRecordUpdatedNotifier [SWS_DM_00668] [SWS_DM_02123]. Una nueva llamada sobrescribe el callback registrado previamente.
  3. Consulta de estado: la aplicación consulta de forma asíncrona el estado de DTC UDS actual de un DTC determinado mediante GetCurrentStatus, lo que devuelve un ara::core::Future<UdsDtcStatusByteType> [SWS_DM_00666]. De forma complementaria, se pueden consultar el número de entradas almacenadas ([SWS_DM_00669]), el estado de desbordamiento ([SWS_DM_00919]) y el estado de control relativo al servicio UDS 0x85 ([SWS_DM_00672]).
  4. Control y limpieza: siempre que las condiciones de la aplicación así lo requieran, el control de estado se puede establecer en activado mediante EnableControlDtc [SWS_DM_00674]. Para borrar DTC individuales o un grupo de DTC, la aplicación llama a Clear y obtiene un ara::core::Future<void> para supervisar el proceso [SWS_DM_00671].

Diagrama de secuencia: secuencia de llamadas y notificaciones entre la aplicación, la instancia de DTCInformation y la memoria de averías del DM. Fuentes: [SWS_DM_00664], [SWS_DM_00666], [SWS_DM_00667], [SWS_DM_00671].

Escenarios de error

Las condiciones de error se dividen en infracciones estáticas de configuración e instanciación y errores dinámicos en tiempo de ejecución a través de ara::diag::DiagErrc:

Al crear la instancia mediante el constructor pueden producirse las siguientes infracciones [SWS_DM_00664]:

  • InstanceSpecifierMappingIntegrityViolation: el InstanceSpecifier no se puede resolver en el modelo de ejecución o no hace referencia a ningún PortPrototype.
  • PortInterfaceMappingViolation: el PortPrototype referenciado no está tipificado mediante un DiagnosticDTCInformationInterface.
  • ProcessMappingViolation: no existe ningún proceso modelado correspondiente a la referencia en tiempo de ejecución.
  • InstanceSpecifierAlreadyInUseViolation: el InstanceSpecifier ya está siendo utilizado por una instancia existente dentro de este proceso.

Durante el funcionamiento normal, los métodos asíncronos (mediante ara::core::Future) y las llamadas síncronas (mediante ara::core::Result) devuelven códigos de error específicos:

  • DiagErrc::kServiceNotAvailable: la funcionalidad básica de Diagnostic Management no está disponible de forma temporal o permanente. Afecta, entre otros, a GetCurrentStatus [SWS_DM_00666], GetNumberOfStoredEntries [SWS_DM_00669], Clear [SWS_DM_00671], GetControlDTCStatus [SWS_DM_00672] y GetEventMemoryOverflow [SWS_DM_00919].
  • DiagErrc::kNoSuchDTC: se produce en GetCurrentStatus si no existe ningún DTC asignado en el destino de memoria para el evento de diagnóstico solicitado [SWS_DM_00666].
  • DiagErrc::kBusy: la interfaz está ocupada actualmente con otra operación, p. ej., en caso de solicitarse simultáneamente Clear [SWS_DM_00671].
  • DiagErrc::kWrongDtc: se ha transferido un número de identificación de DTC no válido a Clear [SWS_DM_00671].
  • DiagErrc::kMemoryError o DiagErrc::kFailed: errores de hardware o de memoria interna, así como cancelaciones generales del procesamiento durante el proceso de borrado con semántica de rollback [SWS_DM_00671].
  • DiagErrc::kInvalidArgument: devuelto por métodos de registro de notificadores como SetSnapshotRecordUpdatedNotifier [SWS_DM_00668], SetNumberOfStoredEntriesNotifier [SWS_DM_00670], SetControlDtcStatusNotifier [SWS_DM_00673] o SetEventMemoryOverflowNotifier [SWS_DM_00918] cuando se transfieren parámetros erróneos.

Esta guía se basa en la especificación AUTOSAR Adaptive Platform R25-11 y resume los requisitos relativos a ara::diag::DTCInformation.
