Contexto

La clase ara::com::ComErrorDomain representa el dominio de error estandarizado para errores generales de la gestión de comunicación (ara::com). Comprende estados de error que pueden ocurrir durante las llamadas a métodos de servicio (ServiceInterface), pero que no están definidos específicamente para una interfaz de servicio individual (SWS CommunicationManagement §7.5.22.6 [SWS_CM_11265]).

Como derivación de la clase base ara::core::ErrorDomain, ComErrorDomain integra los errores de comunicación en el modelo de errores uniforme de AUTOSAR Adaptive (EXP ARAComAPI §4.7). Los errores recuperables (Recoverable Errors) no se lanzan como excepciones, sino que se devuelven a la aplicación mediante instancias de ara::core::ErrorCode [SWS_CORE_00501] dentro de un ara::core::Result (EXP ARAComAPI §4.7).

Los principales participantes en la interacción son:

  • Adaptive Application: Inicia llamadas a métodos, recibe objetos ara::core::Result y evalúa el código de error contenido en ellos basándose en el dominio de error (EXP ARAComAPI §4.7).
  • Métodos de servicio (clase Method): El entorno de ejecución ara::com ejecuta llamadas remotas a través del operador de llamada a función operator() de [SWS_CM_00196] y, en caso de errores, concluye el ara::core::Promise correspondiente a través de SetError [SWS_CORE_00353] con el dominio ComErrorDomain [SWS_CM_11329] (SWS CommunicationManagement §7.4.2).
  • Delimitación respecto a otros dominios: Los errores generales de comunicación se diferencian de los errores específicos End-to-End del dominio ara::com::e2e::ComE2EErrorDomain, así como de los errores funcionales de la aplicación (ApApplicationError) (SWS CommunicationManagement §7.5.22.6, EXP ARAComAPI §4.7).

Diagrama de contexto: Integración de ComErrorDomain en la arquitectura de errores de ara::com y ara::core. Fuentes: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.5.22.6.

Ciclo de vida

La clase ComErrorDomain está declarada como final y hereda públicamente de ara::core::ErrorDomain. Su ciclo de vida está sujeto a directrices arquitectónicas fijas:

  • Creación: El constructor por defecto ComErrorDomain() está explícitamente eliminado (= delete) [SWS_CM_11330]. Por lo tanto, se impide la creación directa de instancias por parte de la lógica de aplicación.
  • Gestión de instancias: Interpretación: dado que los dominios de error en el estándar AUTOSAR Adaptive funcionan como descriptores globales por proceso, es probable que la plataforma proporcione una instancia singleton duradera a la que accedan las estructuras internas de tiempo de ejecución y los códigos de error.
  • Estado y propiedad: La clase encapsula información de tipos y de traducción puramente estática y no gestiona ningún estado mutable de instancias de servicio individuales.
  • Concurrencia: Las funciones de información Name() [SWS_CM_11331] y Message() [SWS_CM_11332] son const, están declaradas como noexcept y están especificadas como seguras frente a excepciones («exception safe»). Dado que devuelven cadenas de caracteres constantes, se pueden invocar concurrentemente desde cualquier hilo sin sincronización adicional.

Ruta de uso

La secuencia de llamadas típica en caso de error se divide en los siguientes pasos:

  1. Llamada a método: Una aplicación llama a un método de servicio a través de operator() de la clase Method [SWS_CM_00196] y recibe un ara::core::Future de vuelta.
  2. Detección de errores: Si ocurre un error general durante la comunicación —por ejemplo, un error de transmisión o un error de aplicación no configurado [SWS_CM_00048]—, el Promise correspondiente pasa al estado de error mediante SetError [SWS_CORE_00353] (SWS CommunicationManagement §7.4.2).
  3. Asignación de código de error: El ara::core::ErrorCode [SWS_CORE_00501] transferido hace referencia al dominio de error ara::com::ComErrorDomain [SWS_CM_11329] y establece el código, por ejemplo, en ComErrc::kCommunicationFailure (EXP ARAComAPI §2.1, SWS CommunicationManagement §7.4.2 [SWS_CM_10432]).
  4. Evaluación del resultado: La aplicación comprueba el ara::core::Result devuelto (EXP ARAComAPI §4.7). Si este contiene un código de error, la aplicación puede:
    • consultar el nombre del dominio mediante Name() [SWS_CM_11331] ([SWS_CORE_90023]),
    • obtener el mensaje de error en texto legible a través de Message(errorCode) [SWS_CM_11332] para fines de registro,
    • o lanzar una excepción a través de ThrowAsException(errorCode) [SWS_CM_11333].

Diagrama de secuencia: Proceso del tratamiento de errores en una llamada a método con ComErrorDomain. Fuentes: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.4.2, [SWS_CM_11332], [SWS_CM_11333].

Escenarios de error

La especificación del tratamiento de errores a través de ComErrorDomain comprende los siguientes detalles:

  • Enumeración de códigos de error y alias de tipo: A través del alias de tipo Errc [SWS_CM_11336], la clase proporciona la enumeración ComErrc, que define los códigos de error del dominio (SWS CommunicationManagement §8.2). El alias de tipo Exception [SWS_CM_11337] hace referencia a la clase base ComException.
  • Códigos de error adicionales: Además de los valores de error estandarizados como ComErrc::kCommunicationFailure [SWS_CM_10432], un fabricante de la pila puede definir otros códigos de error específicos del fabricante en este dominio, los cuales deben ser tenidos en cuenta por la aplicación (EXP ARAComAPI §4.7).
  • Lanzamiento de excepciones: El método ThrowAsException() [SWS_CM_11333] crea un objeto ara::com::ComException a partir de un ara::core::ErrorCode pasado y lo lanza (noexcept(false)). Si las excepciones de C++ están deshabilitadas en el compilador, esta función no participa en la resolución de sobrecarga conforme a [SWS_CORE_10304] [SWS_CM_11333].
  • Clasificación del tratamiento de errores: La API ara::com distingue estrictamente entre errores recuperables (Recoverable Errors), que se propagan de forma determinista a través de ara::core::Result, y errores graves de programación (Violations o Corruptions), en los que se emplean excepciones (EXP ARAComAPI §4.7).

<h4>Contexto</h4>
<p>La clase <code>ara::com::ComErrorDomain</code> representa el dominio de error estandarizado para errores generales de la gestión de comunicación (<code>ara::com</code>). Comprende estados de error que pueden ocurrir durante las llamadas a métodos de servicio (<code>ServiceInterface</code>), pero que no están definidos específicamente para una interfaz de servicio individual (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=307">SWS CommunicationManagement §7.5.22.6</a> <a class="spec-record-ref" data-req="SWS_CM_11265" href="../spec/record.html?id=SWS_CM_11265">[SWS_CM_11265]</a>).</p>
<p>Como derivación de la clase base <code>ara::core::ErrorDomain</code>, <code>ComErrorDomain</code> integra los errores de comunicación en el modelo de errores uniforme de AUTOSAR Adaptive (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>). Los errores recuperables (Recoverable Errors) no se lanzan como excepciones, sino que se devuelven a la aplicación mediante instancias de <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="SWS_CORE_00501" href="../spec/record.html?id=SWS_CORE_00501">[SWS_CORE_00501]</a> dentro de un <code>ara::core::Result</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</p>
<p>Los principales participantes en la interacción son:</p>
<ul>
<li><strong>Adaptive Application</strong>: Inicia llamadas a métodos, recibe objetos <code>ara::core::Result</code> y evalúa el código de error contenido en ellos basándose en el dominio de error (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
<li><strong>Métodos de servicio (clase <code>Method</code>)</strong>: El entorno de ejecución <code>ara::com</code> ejecuta llamadas remotas a través del operador de llamada a función <code>operator()</code> de <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a> y, en caso de errores, concluye el <code>ara::core::Promise</code> correspondiente a través de <code>SetError</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> con el dominio <code>ComErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_11329" href="../spec/record.html?id=SWS_CM_11329">[SWS_CM_11329]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a>).</li>
<li><strong>Delimitación respecto a otros dominios</strong>: Los errores generales de comunicación se diferencian de los errores específicos End-to-End del dominio <code>ara::com::e2e::ComE2EErrorDomain</code>, así como de los errores funcionales de la aplicación (<code>ApApplicationError</code>) (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=307">SWS CommunicationManagement §7.5.22.6</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
</ul>

<h4>Ciclo de vida</h4>
<p>La clase <code>ComErrorDomain</code> está declarada como <code>final</code> y hereda públicamente de <code>ara::core::ErrorDomain</code>. Su ciclo de vida está sujeto a directrices arquitectónicas fijas:</p>
<ul>
<li><strong>Creación</strong>: El constructor por defecto <code>ComErrorDomain()</code> está explícitamente eliminado (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_CM_11330" href="../spec/record.html?id=SWS_CM_11330">[SWS_CM_11330]</a>. Por lo tanto, se impide la creación directa de instancias por parte de la lógica de aplicación.</li>
<li><strong>Gestión de instancias</strong>: Interpretación: dado que los dominios de error en el estándar AUTOSAR Adaptive funcionan como descriptores globales por proceso, es probable que la plataforma proporcione una instancia singleton duradera a la que accedan las estructuras internas de tiempo de ejecución y los códigos de error.</li>
<li><strong>Estado y propiedad</strong>: La clase encapsula información de tipos y de traducción puramente estática y no gestiona ningún estado mutable de instancias de servicio individuales.</li>
<li><strong>Concurrencia</strong>: Las funciones de información <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> y <code>Message()</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a> son <code>const</code>, están declaradas como <code>noexcept</code> y están especificadas como seguras frente a excepciones («exception safe»). Dado que devuelven cadenas de caracteres constantes, se pueden invocar concurrentemente desde cualquier hilo sin sincronización adicional.</li>
</ul>

<h4>Ruta de uso</h4>
<p>La secuencia de llamadas típica en caso de error se divide en los siguientes pasos:</p>
<ol>
<li><strong>Llamada a método</strong>: Una aplicación llama a un método de servicio a través de <code>operator()</code> de la clase <code>Method</code> <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a> y recibe un <code>ara::core::Future</code> de vuelta.</li>
<li><strong>Detección de errores</strong>: Si ocurre un error general durante la comunicación —por ejemplo, un error de transmisión o un error de aplicación no configurado <a class="spec-record-ref" data-req="SWS_CM_00048" href="../spec/record.html?id=SWS_CM_00048">[SWS_CM_00048]</a>—, el <code>Promise</code> correspondiente pasa al estado de error mediante <code>SetError</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a>).</li>
<li><strong>Asignación de código de error</strong>: El <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="SWS_CORE_00501" href="../spec/record.html?id=SWS_CORE_00501">[SWS_CORE_00501]</a> transferido hace referencia al dominio de error <code>ara::com::ComErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_11329" href="../spec/record.html?id=SWS_CM_11329">[SWS_CM_11329]</a> y establece el código, por ejemplo, en <code>ComErrc::kCommunicationFailure</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=9">EXP ARAComAPI §2.1</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>).</li>
<li><strong>Evaluación del resultado</strong>: La aplicación comprueba el <code>ara::core::Result</code> devuelto (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>). Si este contiene un código de error, la aplicación puede:
<ul>
<li>consultar el nombre del dominio mediante <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> (<a class="spec-record-ref" data-req="SWS_CORE_90023" href="../spec/record.html?id=SWS_CORE_90023">[SWS_CORE_90023]</a>),</li>
<li>obtener el mensaje de error en texto legible a través de <code>Message(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a> para fines de registro,</li>
<li>o lanzar una excepción a través de <code>ThrowAsException(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a>.</li>
</ul>
</li>
</ol>

<h4>Escenarios de error</h4>
<p>La especificación del tratamiento de errores a través de <code>ComErrorDomain</code> comprende los siguientes detalles:</p>
<ul>
<li><strong>Enumeración de códigos de error y alias de tipo</strong>: A través del alias de tipo <code>Errc</code> <a class="spec-record-ref" data-req="SWS_CM_11336" href="../spec/record.html?id=SWS_CM_11336">[SWS_CM_11336]</a>, la clase proporciona la enumeración <code>ComErrc</code>, que define los códigos de error del dominio (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=439">SWS CommunicationManagement §8.2</a>). El alias de tipo <code>Exception</code> <a class="spec-record-ref" data-req="SWS_CM_11337" href="../spec/record.html?id=SWS_CM_11337">[SWS_CM_11337]</a> hace referencia a la clase base <code>ComException</code>.</li>
<li><strong>Códigos de error adicionales</strong>: Además de los valores de error estandarizados como <code>ComErrc::kCommunicationFailure</code> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>, un fabricante de la pila puede definir otros códigos de error específicos del fabricante en este dominio, los cuales deben ser tenidos en cuenta por la aplicación (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
<li><strong>Lanzamiento de excepciones</strong>: El método <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a> crea un objeto <code>ara::com::ComException</code> a partir de un <code>ara::core::ErrorCode</code> pasado y lo lanza (<code>noexcept(false)</code>).
