Contexto

La clase ara::com::ComErrorDomain representa el dominio de error estandarizado para errores generales de la gestión de comunicación (ara::com). Comprende estados de error que pueden ocurrir durante las llamadas a métodos de servicio (ServiceInterface), pero que no están definidos específicamente para una interfaz de servicio individual (SWS CommunicationManagement §7.5.22.6 [SWS_CM_11265]).

Como derivación de la clase base ara::core::ErrorDomain, ComErrorDomain integra los errores de comunicación en el modelo de errores uniforme de AUTOSAR Adaptive (EXP ARAComAPI §4.7). Los errores recuperables (Recoverable Errors) no se lanzan como excepciones, sino que se devuelven a la aplicación mediante instancias de ara::core::ErrorCode [SWS_CORE_00501] dentro de un ara::core::Result (EXP ARAComAPI §4.7).

Los principales participantes en la interacción son:

  • Adaptive Application: Inicia llamadas a métodos, recibe objetos ara::core::Result y evalúa el código de error contenido en ellos basándose en el dominio de error (EXP ARAComAPI §4.7).
  • Métodos de servicio (clase Method): El entorno de ejecución ara::com ejecuta llamadas remotas a través del operador de llamada a función operator() de [SWS_CM_00196] y, en caso de errores, concluye el ara::core::Promise correspondiente a través de SetError [SWS_CORE_00353] con el dominio ComErrorDomain [SWS_CM_11329] (SWS CommunicationManagement §7.4.2).
  • Delimitación respecto a otros dominios: Los errores generales de comunicación se diferencian de los errores específicos End-to-End del dominio ara::com::e2e::ComE2EErrorDomain, así como de los errores funcionales de la aplicación (ApApplicationError) (SWS CommunicationManagement §7.5.22.6, EXP ARAComAPI §4.7).

Diagrama de contexto: Integración de ComErrorDomain en la arquitectura de errores de ara::com y ara::core. Fuentes: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.5.22.6.

Ciclo de vida

La clase ComErrorDomain está declarada como final y hereda públicamente de ara::core::ErrorDomain. Su ciclo de vida está sujeto a directrices arquitectónicas fijas:

  • Creación: El constructor por defecto ComErrorDomain() está explícitamente eliminado (= delete) [SWS_CM_11330]. Por lo tanto, se impide la creación directa de instancias por parte de la lógica de aplicación.
  • Gestión de instancias: Interpretación: dado que los dominios de error en el estándar AUTOSAR Adaptive funcionan como descriptores globales por proceso, es probable que la plataforma proporcione una instancia singleton duradera a la que accedan las estructuras internas de tiempo de ejecución y los códigos de error.
  • Estado y propiedad: La clase encapsula información de tipos y de traducción puramente estática y no gestiona ningún estado mutable de instancias de servicio individuales.
  • Concurrencia: Las funciones de información Name() [SWS_CM_11331] y Message() [SWS_CM_11332] son const, están declaradas como noexcept y están especificadas como seguras frente a excepciones («exception safe»). Dado que devuelven cadenas de caracteres constantes, se pueden invocar concurrentemente desde cualquier hilo sin sincronización adicional.

Ruta de uso

La secuencia de llamadas típica en caso de error se divide en los siguientes pasos:

  1. Llamada a método: Una aplicación llama a un método de servicio a través de operator() de la clase Method [SWS_CM_00196] y recibe un ara::core::Future de vuelta.
  2. Detección de errores: Si ocurre un error general durante la comunicación —por ejemplo, un error de transmisión o un error de aplicación no configurado [SWS_CM_00048]—, el Promise correspondiente pasa al estado de error mediante SetError [SWS_CORE_00353] (SWS CommunicationManagement §7.4.2).
  3. Asignación de código de error: El ara::core::ErrorCode [SWS_CORE_00501] transferido hace referencia al dominio de error ara::com::ComErrorDomain [SWS_CM_11329] y establece el código, por ejemplo, en ComErrc::kCommunicationFailure (EXP ARAComAPI §2.1, SWS CommunicationManagement §7.4.2 [SWS_CM_10432]).
  4. Evaluación del resultado: La aplicación comprueba el ara::core::Result devuelto (EXP ARAComAPI §4.7). Si este contiene un código de error, la aplicación puede:
    • consultar el nombre del dominio mediante Name() [SWS_CM_11331] ([SWS_CORE_90023]),
    • obtener el mensaje de error en texto legible a través de Message(errorCode) [SWS_CM_11332] para fines de registro,
    • o lanzar una excepción a través de ThrowAsException(errorCode) [SWS_CM_11333].

Diagrama de secuencia: Proceso del tratamiento de errores en una llamada a método con ComErrorDomain. Fuentes: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.4.2, [SWS_CM_11332], [SWS_CM_11333].

Escenarios de error

La especificación del tratamiento de errores a través de ComErrorDomain comprende los siguientes detalles:

  • Enumeración de códigos de error y alias de tipo: A través del alias de tipo Errc [SWS_CM_11336], la clase proporciona la enumeración ComErrc, que define los códigos de error del dominio (SWS CommunicationManagement §8.2). El alias de tipo Exception [SWS_CM_11337] hace referencia a la clase base ComException.
  • Códigos de error adicionales: Además de los valores de error estandarizados como ComErrc::kCommunicationFailure [SWS_CM_10432], un fabricante de la pila puede definir otros códigos de error específicos del fabricante en este dominio, los cuales deben ser tenidos en cuenta por la aplicación (EXP ARAComAPI §4.7).
  • Lanzamiento de excepciones: El método ThrowAsException() [SWS_CM_11333] crea un objeto ara::com::ComException a partir de un ara::core::ErrorCode pasado y lo lanza (noexcept(false)). Si las excepciones de C++ están deshabilitadas en el compilador, esta función no participa en la resolución de sobrecarga conforme a [SWS_CORE_10304] [SWS_CM_11333].
  • Clasificación del tratamiento de errores: La API ara::com distingue estrictamente entre errores recuperables (Recoverable Errors), que se propagan de forma determinista a través de ara::core::Result, y errores graves de programación (Violations o Corruptions), en los que se emplean excepciones (EXP ARAComAPI §4.7).
