Permite la creación de contextos de registro, flujos de mensajes formateados y la supervisión del estado del cliente.

El espacio de nombres ara::log proporciona servicios de registro adaptativos gestionando registradores de contexto y emitiendo flujos de mensajes tipificados hacia sumideros como el backend DLT o la consola [SWS_LOG_00021]. Las aplicaciones obtienen registradores a través de funciones factoría, preparan datos útiles formateados mediante contenedores de argumentos e introducen datos en los mensajes de registro de forma segura para subprocesos. Como restricción esencial, la propiedad de todas las instancias de registrador permanece en el framework, mientras que el registro del manejador del estado de conexión no es explícitamente seguro para subprocesos [SWS_LOG_00205].

Contexto

El espacio de nombres ara::log proporciona la infraestructura de registro central para aplicaciones adaptativas. Su responsabilidad principal abarca la gestión de contextos de registro a través de la clase Logger, la generación estructurada de mensajes de registro mediante LogStream, así como la transferencia tipificada de datos útiles formateados mediante Argument y Format. El framework actúa como enlace entre las llamadas de registro de la aplicación y los sumideros de destino: como sumidero primario sirve el backend DLT (Diagnostic Log and Trace), cuyo estado de conectividad se representa mediante la enumeración ClientState [SWS_LOG_00098]. Si no se dispone de ningún modelo, la consola actúa como sumidero por defecto [SWS_LOG_00021]. Los cambios de estado de los interlocutores externos pueden supervisarse mediante funciones de retrollamada del tipo ConnectionStateHandler [SWS_LOG_00265].

Diagrama de contexto: interlocutores del framework de registro entre la aplicación, la consola, el backend DLT y el cliente externo. Fuentes: [SWS_LOG_00021], [SWS_LOG_00098], [SWS_LOG_00205].

Ciclo de vida

Las instancias de Logger no son construidas directamente por la aplicación, sino que se instancian a través de las funciones factoría CreateLogger y se registran en el framework de registro [SWS_LOG_00021], [SWS_LOG_00263]. Las relaciones de propiedad están claramente definidas: la propiedad permanece completamente dentro del framework de registro («Ownership stays within the Logging framework»), el cual entrega referencias (Logger&) al invocador [SWS_LOG_00021]. Alternativamente, la creación puede realizarse basada en modelo a partir de un ara::core::InstanceSpecifier [SWS_LOG_00256]. Interpretación: dado que el framework conserva la propiedad, es de suponer que la vida útil de los registradores registrados esté vinculada al proceso de nivel superior. Pregunta Q-4b81e462cf2e43b1 (abierta)

En cuanto a la concurrencia, la creación de registradores mediante CreateLogger está especificada como segura para subprocesos [SWS_LOG_00021]. En cambio, el registro de manejadores de estado de conexión a través de RegisterConnectionStateHandler no es explícitamente seguro para subprocesos («not thread-safe») [SWS_LOG_00205]; por lo tanto, típicamente debe realizarse durante la fase de inicialización antes de iniciar actividades concurrentes. Además, solo puede haber un único manejador activo a la vez; un nuevo registro reemplaza inmediatamente las retrollamadas anteriores [SWS_LOG_00205]. El ciclo de vida de conexión de los interlocutores externos pasa por los estados kUnknown (backend DLT aún no activo), kNotConnected y kConnected [SWS_LOG_00098].

Ruta de uso

El flujo regular comprende la configuración de la supervisión, la obtención del registrador y la emisión formateada de mensajes:

  • Registro de la retrollamada de conexión mediante RegisterConnectionStateHandler [SWS_LOG_00205].
  • Obtención de la referencia de Logger a través de CreateLogger especificando un ID de contexto, una descripción y, opcionalmente, un nivel de gravedad predeterminado de LogLevel (p. ej., kWarn o kInfo) [SWS_LOG_00018], [SWS_LOG_00021].
  • Creación de argumentos estructurados mediante Arg adjuntando identificador, unidad e indicaciones de formato [SWS_LOG_00201]. Para ello están disponibles funciones auxiliares como Dflt [SWS_LOG_00208], formatos enteros como Dec [SWS_LOG_00211], Hex [SWS_LOG_00209], Bin [SWS_LOG_00215] y Oct [SWS_LOG_00213], así como formatos de coma flotante como DecFloat [SWS_LOG_00217], EngFloat [SWS_LOG_00219], HexFloat [SWS_LOG_00221] o AutoFloat [SWS_LOG_00223], los cuales encapsulan los especificadores de Fmt [SWS_LOG_00206].
  • Transferencia de datos útiles a LogStream mediante operadores sobrecargados operator<<, entre otros para LogLevel [SWS_LOG_00063], ara::core::ErrorCode [SWS_LOG_00124], std::chrono::duration [SWS_LOG_00125], ara::core::InstanceSpecifier [SWS_LOG_00126] y punteros const void* [SWS_LOG_00127].

Diagrama de secuencia: secuencia de interacción típica en la inicialización, creación de registradores y emisión de datos formateados a través de LogStream. Fuentes: [SWS_LOG_00021], [SWS_LOG_00063], [SWS_LOG_00124], [SWS_LOG_00201], [SWS_LOG_00205].

Escenarios de error

Las funciones del espacio de nombres están declaradas en su mayor parte con noexcept y ofrecen garantías de no lanzamiento de excepciones (no-throw), pero están sujetas a condiciones previas estrictas y reglas de violación:

  • Violaciones de manifiesto: al crear un registrador basado en modelo mediante CreateLogger(const ara::core::InstanceSpecifier&), pueden desencadenarse violaciones específicas en tiempo de ejecución: InstanceSpecifierMappingIntegrityViolation (el especificador no se puede resolver en el modelo o no hace referencia a un PortPrototype), PortInterfaceMappingViolation (el tipo de asignación no coincide con el PortInterface esperado), ProcessMappingViolation (no se encontró ningún proceso coincidente), así como InstanceSpecifierAlreadyInUseViolation (el especificador ya se utiliza en el proceso) [SWS_LOG_00256].
  • Tipificación de argumento no válida: la llamada a Arg es sintácticamente incorrecta («ill-formed») si el tipo T no es ni un tipo aritmético ni bool, y no se puede convertir ni a ara::core::StringView ni a ara::core::Span<const ara::core::Byte>. Asimismo, pasar un texto de unidad diferente de nullptr unit en cadenas de caracteres, intervalos de bytes (byte spans) o tipos booleanos provoca un error [SWS_LOG_00201].
  • Representación de errores: al emitir una instancia de core::ErrorCode a la consola, el código de error se formatea de manera específica de la implementación, debiendo incluirse el nombre de dominio (ErrorCode::Domain().Name()) y el número entero de error [SWS_LOG_00124].

Esta guía se basa en la especificación del módulo log en el release R25-11 de la Adaptive Platform.

La enumeración ara::log::ClientState representa el estado de conexión actual de un cliente externo con el backend de DLT [SWS_LOG_00098]. Se basa en el tipo de datos std::int8_t y se incluye a través del archivo de cabecera #include "ara/log/common.h" o del archivo de cabecera de reenvío #include "ara/log/log_fwd.h" [SWS_LOG_00098].

Estados y semántica

La enumeración define tres estados de conexión discretos [SWS_LOG_00098]:

  • kUnknown (-1): El backend de DLT aún no está listo para operar; el estado de conexión real no se puede determinar en este momento [SWS_LOG_00098].
  • kNotConnected: No se detectó ningún cliente externo [SWS_LOG_00098].
  • kConnected: Un cliente remoto está conectado correctamente [SWS_LOG_00098].

Interacción y concurrencia

La enumeración sirve principalmente como parámetro de transferencia para la retrollamada de función ConnectionStateHandler (definida como std::function<void(ClientState)>), que se registra a través de ara::log::RegisterConnectionStateHandler [SWS_LOG_00265]. Este manejador está declarado como seguro para subprocesos [SWS_LOG_00265]. Interpretación: Los manejadores registrados probablemente se llamen de manera asíncrona tan pronto como el backend de DLT detecte cambios de estado del cliente externo.
