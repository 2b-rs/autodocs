GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 05efd4a1afb9 Procedencia

Define interfaces para la gestión de valores de frescura y el tratamiento de errores en canales de comunicación protegidos.

El espacio de nombres define la interfaz específica del fabricante para gestionar valores de frescura en el marco de Secure Onboard Communication (SecOC) para el Communication Management de AUTOSAR Adaptive Platform (SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h»). El ciclo de vida y la inicialización del Freshness Value Manager están completamente controlados por la gestión de comunicación, la cual consulta valores de frescura a través de la interfaz durante los procesos de transmisión configurados ([SWS_CM_11272]). En caso de no disponibilidad temporal de valores de frescura, se realizan reintentos controlados hasta alcanzar un valor de umbral definido antes de descartar los mensajes erróneos. De forma complementaria, el espacio de nombres proporciona un dominio de error propio y códigos de error estandarizados para el diagnóstico y el tratamiento de excepciones.

Contexto

El espacio de nombres apext::com::secoc define interfaces normativas para extensiones de plataforma (Platform Extension Interfaces) dentro del clúster funcional Communication Management (ara::com) de la AUTOSAR Adaptive Platform (SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h»). El objetivo de estas interfaces de extensión es permitir a los OEM y a los fabricantes de pilas proporcionar un Freshness Value Manager (FVM) a medida que genere, gestione y verifique los valores de frescura requeridos para la protección contra ataques de repetición en Secure Onboard Communication (SecOC).

El espacio de nombres interactúa esencialmente con tres roles: la gestión de comunicación (ara::com), la definición de interfaz estandarizada (FVM) junto con contenedores de datos como FVContainer ([SWS_CM_11286], [SWS_CM_11344]), así como la implementación concreta del FVM del fabricante del vehículo o del proveedor de la pila. Interpretación: Se asume que la biblioteca de FVM específica del fabricante se vincula durante la integración del sistema como biblioteca estática o dinámica, dado que la especificación define la interfaz funcional, pero deja abierta la modalidad de integración de forma específica para cada pila.

Diagrama de contexto: Integración del espacio de nombres apext::com::secoc entre Communication Management y la implementación del FVM específica del fabricante. Fuentes: [SWS_CM_11272], SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h».

Ciclo de vida

La gestión del ciclo de vida de una realización del FVM está completamente controlada por la gestión de comunicación ara::com ([SWS_CM_11272]). Las aplicaciones y las instancias de servicio no crean ni gestionan el componente FVM directamente.

La puesta en servicio se realiza de forma determinista durante la inicialización de la pila de comunicación mediante la llamada a la API de biblioteca apext::com::secoc::FVM::Initialize ([SWS_CM_11273]). Si la inicialización no puede completarse correctamente por parte del fabricante, la capa del FVM señaliza este estado de error mediante el código de error definido kFVInitializeFailed ([SWS_CM_11342]). Tras una llamada de inicialización exitosa, el Freshness Value Manager permanece en estado operativo activo y responde a solicitudes síncronas de valores de frescura de transmisión y recepción.

Ruta de uso

La ruta de uso habitual se subdivide en la protección de transmisión y la verificación de recepción de mensajes:

  • Mensajes de transmisión: Si un mensaje está configurado para el envío mediante SecOC, se trata como un mensaje auténtico ([SWS_CM_11274]). La protección se lleva a cabo en un orden fijo tras concluir todos los cálculos de protección E2E ([SWS_CM_11274]). Si la configuración de la interfaz de servicio posee un atributo freshnessValueId, la gestión de comunicación invoca apext::com::secoc::FVM::GetTxFreshness ([SWS_CM_11274], [SWS_CM_11275]). El valor de frescura se suministra en una estructura FVContainer que almacena la longitud en bits en el atributo length y el valor en sí ([SWS_CM_11286], [SWS_CM_11344]).
  • Mecanismo de reintento de transmisión: Para cada mensaje protegido, el sistema mantiene un Authentication Build Counter ([SWS_CM_11275]). Tras una generación correcta, el contador se restablece a 0. Si GetTxFreshness devuelve el error recuperable kFVNotAvailable o si falla el cálculo del autenticador, se incrementa el contador y se repite la construcción ([SWS_CM_11275]). Si el contador alcanza el valor de umbral SecOCAuthenticationBuildAttempts, el mensaje se descarta ([SWS_CM_11275]).
  • Mensajes de recepción: En los mensajes SecOC entrantes con verificación activa (atributo securedRxVerification verdadero o no configurado), se extrae el autenticador y se verifica el mensaje antes de las comprobaciones E2E recalculando el MAC ([SWS_CM_11276], SWS Communication Management §8.1 «SecOC secure channel reception»). Por el contrario, si securedRxVerification se establece en falso, la verificación se elude (bypass) y el mensaje se procesa sin comprobación ([SWS_CM_11372]).

Diagrama de secuencia: Flujo de invocación y reintentos al proteger un mensaje de transmisión mediante FVM. Fuentes: [SWS_CM_11274], [SWS_CM_11275].

Escenarios de error

Las situaciones de error dentro de la interfaz del FVM se gestionan mediante el dominio de error con seguridad de tipos ComSecOcFvmErrorDomain, cuya instancia puede obtenerse a través de GetComSecOcFvmErrorDomain ([SWS_CM_12521]). Los códigos de error están definidos en el tipo de enumeración ComSecOcFvmErrc ([SWS_CM_11342]):

  • kFVNotAvailable (Código 1): El valor de frescura requerido no está disponible temporalmente. Esto señaliza a Communication Management un error recuperable que desencadena reintentos según el protocolo de transmisión ([SWS_CM_11275], [SWS_CM_11342]).
  • kFVInitializeFailed (Código 2): Falló la inicialización del Freshness Value Manager ([SWS_CM_11342]).

A través de la función auxiliar MakeErrorCode ([SWS_CM_12522]) es posible encapsular códigos de error junto con datos adicionales específicos del fabricante (SupportDataType) en objetos ara::core::ErrorCode convencionales. Para llamadas síncronas fallidas en entornos basados en excepciones se dispone de la clase de excepción ComSecOcFvmException.

Esta guía se basa en la especificación AUTOSAR Adaptive Platform R25-11 (Communication Management). Todas las afirmaciones se fundamentan exclusivamente en las referencias de especificación y documentación indicadas.
