Proporciona interfaces y tipos para notificar eventos relevantes para la seguridad al IdsM de manera estandarizada.

El espacio de nombres ara::idsm proporciona interfaces y tipos estandarizados con los que las aplicaciones adaptativas notifican eventos de seguridad de forma estructurada al Intrusion Detection System Management ([SWS_AIDSM_10205]). Mediante el EventReporter y los proveedores asociados de marcas de tiempo, datos de contexto y modos de transmisión, los incidentes pueden registrarse de forma detallada o filtrada ([SWS_AIDSM_10207]). En caso de identificadores de evento desconocidos, el IdsmErrorDomain proporciona códigos de error específicos para su posterior tratamiento.

Contexto

El espacio de nombres ara::idsm proporciona la interfaz de programación de la AUTOSAR Adaptive Platform para el Intrusion Detection System Management (IdsM). Su tarea central consiste en recopilar eventos relevantes para la seguridad (Security Events) a partir de procesos de aplicación e instancias de plataforma de manera estandarizada y reenviarlos al IdsM de nivel superior.

La interfaz de interacción principal para las aplicaciones que notifican la conforma la clase EventReporter. Este registro va acompañado de interfaces funcionales especializadas: el ReportingModeProvider gestiona el modo de transmisión actual ([SWS_AIDSM_10207]), el ContextDataProvider proporciona datos complementarios dinámicos ([SWS_AIDSM_10201], [SWS_AIDSM_10206]) y el TimestampProvider aporta información temporal ([SWS_AIDSM_10202]). En el lado del receptor, el QualifiedEventsReceiver procesa eventos ya cualificados. La interacción de estos roles vincula las aplicaciones adaptativas con la monitorización orientada a la seguridad.

Diagrama de contexto: interacción entre componentes de aplicación, interfaces ara::idsm e IdsM. Fuentes: [SWS_AIDSM_10205], [SWS_AIDSM_10207]

Ruta de uso

Un flujo típico para la señalización de un evento de seguridad se divide en la consulta del estado de notificación, la recopilación de información de contexto relevante y la transmisión al EventReporter.

Antes de emitir un evento, la aplicación consulta el modo de notificación activo a través del ReportingModeProvider ([SWS_AIDSM_10207]). La enumeración ReportingModeType distingue, entre otros, entre transmisión desactivada (kOff), notificaciones compactas (kBrief), informes detallados (kDetailed) y modos que omiten las reglas de filtrado locales (kBriefBypassingFilters, kDetailedBypassingFilters). Si la notificación no está desactivada, la aplicación prepara los datos útiles. Como identificación del evento se utiliza un identificador de tipo EventIdType ([SWS_AIDSM_10205]). Para análisis adicionales, el ContextDataProvider proporciona datos de contexto modificables en forma de tramo de bytes ContextDataType ([SWS_AIDSM_10201]) o como un par versionado VersionedContextDataType que incluye el contador de versión ([SWS_AIDSM_10206]). De forma complementaria, pueden integrarse un contador de tipo CountType ([SWS_AIDSM_10203]) para eventos precualificados, así como una marca de tiempo de tipo TimestampType ([SWS_AIDSM_10202]) a través del TimestampProvider. Por último, la aplicación transfiere los datos al EventReporter.

Diagrama de secuencia: orden de llamadas para comprobar el estado de notificación y transmitir un Security Event. Fuentes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10207]

Escenarios de error

Las operaciones erróneas dentro del espacio de nombres ara::idsm se señalan a través del dominio de errores IdsmErrorDomain y el tipo de código de error IdsmErrc ([SWS_AIDSM_10204]). Para una gestión de errores conforme al estándar existen las funciones GetIdsmErrorDomain ([SWS_AIDSM_10702]) y MakeErrorCode ([SWS_AIDSM_10703]), con las que se pueden construir instancias de ara::core::ErrorCode de manera segura para subprocesos.

Un escenario de error central se presenta cuando se utiliza un ID de evento desconocido. En este caso, el sistema notifica el error IdsmErrc::kUnknownEventId ([SWS_AIDSM_10204]). Esto ocurre cuando un invocador pasa un identificador de tipo EventIdType que no es conocido para el IdsM o no está configurado en el manifiesto. En interfaces síncronas con gestión de excepciones, este estado se representa mediante la clase IdsmException. Por lo tanto, una condición previa para cualquier notificación exitosa es la correspondencia de los valores EventIdType transferidos con la configuración del IdsM.

Esta guía se basa exclusivamente en las especificaciones del release R25-11 de AUTOSAR.

      Uso y finalidad
      

      La enumeración IdsmErrc representa los códigos de error del dominio de errores de IdsM (encabezado ara/idsm/idsm_error_domain.h) y se basa en el tipo base ara::core::ErrorDomain::CodeType [SWS_AIDSM_10204]. Para un manejo compacto en aplicaciones cliente, AUTOSAR proporciona el alias de tipo idéntico Errc [SWS_AIDSM_10707]. Para la integración en el modelo de tratamiento de errores estandarizado de AUTOSAR Adaptive sirve la función MakeErrorCode: convierte noexcept un código de error junto con datos adicionales específicos del fabricante (SupportDataType) en un objeto ara::core::ErrorCode [SWS_AIDSM_10703].
      


      Códigos de error e interacción
      

      La especificación define el valor de error concreto:
      

        

      • kUnknownEventId = 3: indica que una eventId transferida no es conocida por el Intrusion Detection System Manager como un evento de seguridad configurado [SWS_AIDSM_10204].
        • 

      

      Este código se transporta en interfaces síncronas como estado de error dentro del tipo de retorno ara::core::Result. Tanto la consulta del modo de reporte a través de GetReportingMode [SWS_AIDSM_10602] como su actualización vía SetReportingMode [SWS_AIDSM_10603] fallan con IdsmErrc::kUnknownEventId si se direcciona un evento no configurado. Interpretación: debido a la asignación explícita del valor 3, los valores 1 y 2 probablemente estén reservados para estados de error del dominio utilizados internamente o en el futuro. Pregunta Q-374e315b0ea6d0c7 (abierta)
      


      Concurrencia y restricciones
      

      La función auxiliar MakeErrorCode para crear objetos de error es segura para subprocesos (thread-safe) y está designada como constexpr [SWS_AIDSM_10703]. Por el contrario, las funciones operativas del reporting_mode_provider.h que devuelven estos estados de error (GetReportingMode [SWS_AIDSM_10602] y SetReportingMode [SWS_AIDSM_10603]) están declaradas explícitamente como no seguras para subprocesos (not thread-safe). Por lo tanto, las llamadas paralelas deben ser sincronizadas por el llamador.
