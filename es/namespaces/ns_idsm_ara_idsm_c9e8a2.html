Contexto

El espacio de nombres ara::idsm proporciona la interfaz para el Intrusion Detection System Management (IdsM) dentro de AUTOSAR Adaptive Platform. El IdsM sirve para la detección, captura y reenvío de incidentes relevantes para la seguridad (Security Events) en toda la red del vehículo. En este proceso, las aplicaciones adaptativas, las pilas de comunicación y los servicios de plataforma actúan como sensores de seguridad descentralizados que notifican actividades sospechosas o infracciones registradas de reglas al subsistema central de IdsM.

Dentro del espacio de nombres, la clase EventReporter asume el papel central en la transmisión de eventos de seguridad al IdsM. Para enriquecer las notificaciones de eventos con metadatos relevantes, el reporter colabora con otros componentes especializados:

  • ContextDataProvider proporciona datos de contexto modificables y específicos del sensor que se transfieren al IdsM como una secuencia de datos sin procesar mediante [SWS_AIDSM_10201] ContextDataType (alias de tipo para ara::core::Span<const std::uint8_t>) o en forma versionada como [SWS_AIDSM_10206] VersionedContextDataType.
  • TimestampProvider proporciona marcas de tiempo de alta precisión o específicas del sensor mediante el tipo [SWS_AIDSM_10202] TimestampType (entero de 64 bits) para poder correlacionar temporalmente los incidentes.
  • ReportingModeProvider controla el comportamiento de notificación de los sensores mediante la enumeración [SWS_AIDSM_10207] ReportingModeType.
  • QualifiedEventsReceiver permite a los módulos de análisis o de reacción de nivel superior recibir eventos de seguridad cualificados por el IdsM para su posterior procesamiento.
  • IdsmErrorDomain y IdsmException definen la semántica de errores del espacio de nombres.

Diagrama de contexto: interacción entre las aplicaciones de sensor, las clases de interfaz del espacio de nombres ara::idsm y el subsistema de IdsM. Fuentes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10207].

Ruta de uso

Un flujo de monitorización típico comprende la consulta del modo de funcionamiento activo, la preparación de los datos de eventos y la posterior notificación al IdsM:

  1. Consultar el modo de notificación: Antes de que una aplicación realice análisis de contexto computacionalmente intensivos o transmita eventos, lee el modo de notificación actual a través de ReportingModeProvider. Según [SWS_AIDSM_10207], están disponibles cinco modos de la enumeración ReportingModeType:
    • ReportingModeType::kOff: La notificación de eventos está completamente desactivada.
    • ReportingModeType::kBrief: Notificación de eventos reducida sin datos de contexto detallados.
    • ReportingModeType::kDetailed: Notificación detallada que incluye todos los datos de contexto disponibles.
    • ReportingModeType::kBriefBypassingFilters: Notificación reducida eludiendo los mecanismos de filtrado locales.
    • ReportingModeType::kDetailedBypassingFilters: Notificación completa eludiendo los mecanismos de filtrado locales.
    Interpretación: La diferenciación detallada de los modos de notificación presumiblemente permite al sistema global adaptar dinámicamente el volumen de transmisión a la carga actual del bus y a la situación de amenaza.
  2. Preparar los datos de eventos: El evento concreto se identifica mediante un entero de 16 bits del tipo [SWS_AIDSM_10205] EventIdType. Si se han precualificado varios eventos del mismo tipo, la cantidad se puede indicar mediante [SWS_AIDSM_10203] CountType. Además, se pueden determinar marcas de tiempo a través de TimestampProvider ([SWS_AIDSM_10202]) y datos útiles a través de ContextDataProvider ([SWS_AIDSM_10201] o [SWS_AIDSM_10206]).
  3. Notificar el evento: La aplicación transfiere los datos a EventReporter. Interpretación: La transferencia al subsistema de IdsM presumiblemente se realiza de forma asíncrona para no bloquear las rutas de ejecución de las aplicaciones de sensor críticas en el tiempo.
  4. Recibir eventos cualificados: Los módulos registrados reciben eventos cualificados a través de QualifiedEventsReceiver para iniciar reacciones de seguridad en todo el vehículo.

Diagrama de secuencia: secuencia de llamadas para comprobar el modo de notificación, preparar los datos de contexto y transmitir un evento de seguridad. Fuentes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10206], [SWS_AIDSM_10207].

Escenarios de error

El tratamiento de errores en el espacio de nombres ara::idsm sigue el estándar de AUTOSAR Adaptive mediante dominios de error y tipos de resultado:

  • Dominio de error y funciones de fábrica: La función [SWS_AIDSM_10702] GetIdsmErrorDomain() devuelve una referencia a la ara::core::ErrorDomain estática del dominio IdsmErrorDomain. Está especificada como constexpr, noexcept y segura para subprocesos. Los códigos de error se generan mediante [SWS_AIDSM_10703] MakeErrorCode() especificando un valor de IdsmErrc y datos de soporte opcionales (ara::core::ErrorDomain::SupportDataType).
  • Códigos de error específicos: De acuerdo con [SWS_AIDSM_10204], la enumeración IdsmErrc define el código kUnknownEventId = 3. Este error se produce cuando se notifica un evento con una EventIdType desconocida para el IdsM o no configurada en el manifiesto.
  • Tratamiento de excepciones: En caso de que las API del módulo lancen excepciones, se utiliza el error tipado IdsmException, que encapsula el ara::core::ErrorCode correspondiente.

<h4>Contexto</h4>
<p>El espacio de nombres <code>ara::idsm</code> proporciona la interfaz para el Intrusion Detection System Management (IdsM) dentro de AUTOSAR Adaptive Platform. El IdsM sirve para la detección, captura y reenvío de incidentes relevantes para la seguridad (Security Events) en toda la red del vehículo. En este proceso, las aplicaciones adaptativas, las pilas de comunicación y los servicios de plataforma actúan como sensores de seguridad descentralizados que notifican actividades sospechosas o infracciones registradas de reglas al subsistema central de IdsM.</p>

<p>Dentro del espacio de nombres, la clase <code>EventReporter</code> asume el papel central en la transmisión de eventos de seguridad al IdsM. Para enriquecer las notificaciones de eventos con metadatos relevantes, el reporter colabora con otros componentes especializados:</p>
<ul>
<li><code>ContextDataProvider</code> proporciona datos de contexto modificables y específicos del sensor que se transfieren al IdsM como una secuencia de datos sin procesar mediante <a class="spec-record-ref" data-req="SWS_AIDSM_10201" href="../spec/record.html?id=SWS_AIDSM_10201">[SWS_AIDSM_10201]</a> <code>ContextDataType</code> (alias de tipo para <code>ara::core::Span&lt;const std::uint8_t&gt;</code>) o en forma versionada como <a class="spec-record-ref" data-req="SWS_AIDSM_10206" href="../spec/record.html?id=SWS_AIDSM_10206">[SWS_AIDSM_10206]</a> <code>VersionedContextDataType</code>.</li>
<li><code>TimestampProvider</code> proporciona marcas de tiempo de alta precisión o específicas del sensor mediante el tipo <a class="spec-record-ref" data-req="SWS_AIDSM_10202" href="../spec/record.html?id=SWS_AIDSM_10202">[SWS_AIDSM_10202]</a> <code>TimestampType</code> (entero de 64 bits) para poder correlacionar temporalmente los incidentes.</li>
<li><code>ReportingModeProvider</code> controla el comportamiento de notificación de los sensores mediante la enumeración <a class="spec-record-ref" data-req="SWS_AIDSM_10207" href="../spec/record.html?id=SWS_AIDSM_10207">[SWS_AIDSM_10207]</a> <code>ReportingModeType</code>.</li>
<li><code>QualifiedEventsReceiver</code> permite a los módulos de análisis o de reacción de nivel superior recibir eventos de seguridad cualificados por el IdsM para su posterior procesamiento.</li>
<li><code>IdsmErrorDomain</code> y <code>IdsmException</code> definen la semántica de errores del espacio de nombres.</li>
</ul>

<h4>Ruta de uso</h4>
<p>Un flujo de monitorización típico comprende la consulta del modo de funcionamiento activo, la preparación de los datos de eventos y la posterior notificación al IdsM:</p>
<ol>
<li><strong>Consultar el modo de notificación:</strong> Antes de que una aplicación realice análisis de contexto computacionalmente intensivos o transmita eventos, lee el modo de notificación actual a través de <code>ReportingModeProvider</code>. Según <a class="spec-record-ref" data-req="SWS_AIDSM_10207" href="../spec/record.html?id=SWS_AIDSM_10207">[SWS_AIDSM_10207]</a>, están disponibles cinco modos de la enumeración <code>ReportingModeType</code>:
<ul>
<li><code>ReportingModeType::kOff</code>: La notificación de eventos está completamente desactivada.</li>
<li><code>ReportingModeType::kBrief</code>: Notificación de eventos reducida sin datos de contexto detallados.</li>
<li><code>ReportingModeType::kDetailed</code>: Notificación detallada que incluye todos los datos de contexto disponibles.</li>
<li><code>ReportingModeType::kBriefBypassingFilters</code>: Notificación reducida eludiendo los mecanismos de filtrado locales.</li>
<li><code>ReportingModeType::kDetailedBypassingFilters</code>: Notificación completa eludiendo los mecanismos de filtrado locales.</li>
</ul>
Interpretación: La diferenciación detallada de los modos de notificación presumiblemente permite al sistema global adaptar dinámicamente el volumen de transmisión a la carga actual del bus y a la situación de amenaza.</li>
<li><strong>Preparar los datos de eventos:</strong> El evento concreto se identifica mediante un entero de 16 bits del tipo <a class="spec-record-ref" data-req="SWS_AIDSM_10205" href="../spec/record.html?id=SWS_AIDSM_10205">[SWS_AIDSM_10205]</a> <code>EventIdType</code>. Si se han precualificado varios eventos del mismo tipo, la cantidad se puede indicar mediante <a class="spec-record-ref" data-req="SWS_AIDSM_10203" href="../spec/record.html?id=SWS_AIDSM_10203">[SWS_AIDSM_10203]</a> <code>CountType</code>. Además, se pueden determinar marcas de tiempo a través de <code>TimestampProvider</code> (<a class="spec-record-ref" data-req="SWS_AIDSM_10202" href="../spec/record.html?id=SWS_AIDSM_10202">[SWS_AIDSM_10202]</a>) y datos útiles a través de <code>ContextDataProvider</code> (<a class="spec-record-ref" data-req="SWS_AIDSM_10201" href="../spec/record.html?id=SWS_AIDSM_10201">[SWS_AIDSM_10201]</a> o <a class="spec-record-ref" data-req="SWS_AIDSM_10206" href="../spec/record.html?id=SWS_AIDSM_10206">[SWS_AIDSM_10206]</a>).</li>
<li><strong>Notificar el evento:</strong> La aplicación transfiere los datos a <code>EventReporter</code>. Interpretación: La transferencia al subsistema de IdsM presumiblemente se realiza de forma asíncrona para no bloquear las rutas de ejecución de las aplicaciones de sensor críticas en el tiempo.</li>
<li><strong>Recibir eventos cualificados:</strong> Los módulos registrados reciben eventos cualificados a través de <code>QualifiedEventsReceiver</code> para iniciar reacciones de seguridad en todo el vehículo.</li>
</ol>
