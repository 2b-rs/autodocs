Proporciona interfaces del lado del cliente y clases proxy para acceder a instancias de servicio en AUTOSAR Adaptive.

Dentro del módulo com, el namespace <SI-Namespace>::proxy proporciona la interfaz del lado del cliente para interactuar con un Service Interface. Su componente central es la clase proxy <SI>Proxy, que abstrae la comunicación del middleware y permite llamadas a métodos así como suscripciones a eventos. La instanciación del proxy presupone típicamente un handle válido procedente de la búsqueda de servicios. Como condición de contorno esencial, la aplicación llamante debe gestionar de forma robusta las interrupciones de conexión y los tiempos de respuesta asíncronos en llamadas remotas.

Contexto

Dentro del módulo de comunicación com de AUTOSAR Adaptive Platform, el namespace <SI-Namespace>::proxy representa la representación del lado del cliente de un Service Interface. Agrupa todos los artefactos y tipos requeridos por los consumidores de servicios para interactuar con un servicio ofrecido a través de la red de comunicación. En el centro de este espacio de nombres se encuentra la clase proxy generada <SI>Proxy. Esta clase abstrae la configuración de red y de comunicación interprocesos subyacente basada en mensajes, y proporciona una interfaz de C++ mediante la cual el software de aplicación puede invocar métodos, suscribirse a eventos, así como consultar y monitorizar campos.

Desde el punto de vista arquitectónico, el proxy actúa como intermediario entre la lógica de cliente específica de la aplicación y el entorno de ejecución de Adaptive Platform. En lugar de interacciones directas de red o de memoria compartida, el desarrollador de la aplicación interactúa exclusivamente con las instancias de <SI-Namespace>::proxy. De este modo se logra un desacoplamiento que permite que la plataforma middleware subyacente gestione de forma transparente los protocolos de comunicación, los formatos de transferencia de datos y los detalles de ubicación.

Ciclo de vida

El ciclo de vida de los objetos en el namespace <SI-Namespace>::proxy está estrechamente ligado a la disponibilidad de la instancia de servicio correspondiente. Antes de poder crear una instancia de proxy, debe tener lugar un reconocimiento de instancias. La instanciación del proxy <SI>Proxy suele requerir típicamente un handle que resulte de la búsqueda de servicios. Tras una instanciación correcta, el objeto proxy representa una conexión lógica con el proveedor de servicios respectivo.

Durante la fase operativa activa, la instancia de proxy gestiona los estados relativos a los eventos suscritos y a las llamadas asíncronas a métodos pendientes. En lo que respecta a la concurrencia, debe tenerse en cuenta que las llamadas al proxy deben diseñarse de forma segura para hilos o deben ser sincronizadas en consecuencia por el cliente si varios hilos utilizan el mismo objeto proxy. La liberación o destrucción del objeto proxy suele finalizar la vinculación con la instancia de servicio encontrada y resuelve las suscripciones activas.

Ruta de uso

Una ruta de uso típica para el empleo del proxy de Service Interface se divide en varias fases consecutivas:

  • Localización de la instancia de servicio: el cliente inicia una búsqueda de instancias disponibles del servicio mediante los mecanismos de plataforma del módulo com y recibe de vuelta las estructuras de handles correspondientes.
  • Construcción del proxy: utilizando un handle válido se instancia un objeto de <SI>Proxy, con lo cual se establece el canal de comunicación con el servidor.
  • Interacción con elementos de servicio: a través de la instancia se invocan métodos de forma síncrona o asíncrona, se suscriben eventos y se registran callbacks. Los patrones de comunicación asíncronos se plasman presumiblemente mediante wrappers tipados de eventos y métodos dentro de la instancia de proxy.
  • Finalización y limpieza: tras concluir la comunicación, se cancela la suscripción a los eventos y la instancia de proxy se destruye adecuadamente para liberar los recursos ocupados.

Escenarios de error

Durante la interacción con el espacio de nombres del proxy pueden producirse diversos patrones de error. Entre ellos se encuentran cortes de conexión con el servidor, tiempos de espera agotados (timeouts) en llamadas remotas, así como la falta de disponibilidad de las instancias de servicio solicitadas durante la inicialización. Dado que la comunicación tiene lugar a través de límites de procesos y de computadores, los fallos de infraestructura o las caídas del interlocutor se reflejan en los valores devueltos. Las llamadas anteriores a una vinculación correcta o posteriores a la destrucción de la instancia provocan estados no válidos, por lo que deben cumplirse estrictamente las precondiciones relativas a la validez del handle.
