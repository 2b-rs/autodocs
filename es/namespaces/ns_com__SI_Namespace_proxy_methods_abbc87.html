Contexto

Dentro del módulo com de AUTOSAR Adaptive Platform, el namespace <SI-Namespace>::proxy::methods proporciona los representantes de interfaz del lado del cliente para llamadas a métodos. En la arquitectura orientada a servicios de AUTOSAR Adaptive, las relaciones de comunicación se definen mediante interfaces de servicio (ServiceInterface). Si una interfaz de este tipo contiene operaciones del tipo ClientServerOperation, el generador de interfaces genera una clase de método especializada en el namespace de proxy para cada una de estas operaciones.

La arquitectura distingue fundamentalmente entre dos variantes de métodos, controladas por el atributo de metamodelo fireAndForget:

  • Clase <Method>: esta clase se genera para cada ClientServerOperation en la que esté configurado ClientServerOperation.fireAndForget == FALSE. Representa llamadas síncronas o asíncronas de tipo solicitud-respuesta (request-response), en las que el cliente espera una respuesta o un resultado del servidor.
  • Clase <FnFMethod>: esta clase se genera para operaciones en las que aplica ClientServerOperation.fireAndForget == TRUE. Implementa un patrón de mensajes puramente unidireccional (fire-and-forget), en el que se emite la llamada sin que se transmita al cliente ninguna confirmación o valor de retorno desde el servidor.

Dentro de la jerarquía global de <SI-Namespace>::proxy, estas clases encapsulan la serialización de los parámetros de entrada, la entrega a la infraestructura de comunicación subyacente y, en el caso de métodos regulares, la recepción de los datos de respuesta.

Ciclo de vida

El tiempo de vida de las clases en el namespace <SI-Namespace>::proxy::methods está estrechamente vinculado a la instancia de proxy de nivel superior de la interfaz de servicio correspondiente. Interpretación: es de prever que las instancias de <Method> y <FnFMethod> se instancien como miembros de la clase de proxy de servicio generada y, por lo tanto, compartan por completo su ciclo de vida.

Al instanciar el proxy de servicio (tras un descubrimiento de servicios satisfactorio y la vinculación a una instancia de servicio concreta), se inicializan los objetos de método integrados. Al hacerlo, obtienen el contexto de acceso al binding de comunicación subyacente. Mientras el proxy de servicio siga siendo válido, las instancias de método permanecen a disposición de la aplicación cliente. Si el proxy de servicio se destruye, también se extinguen los objetos de método asociados. Las llamadas asíncronas en curso o las respuestas aún pendientes deben procesarse o invalidarse antes de o durante la llamada al destructor del proxy.

En lo relativo a la concurrencia, las llamadas a métodos están diseñadas de modo que múltiples hilos del software de aplicación puedan invocar el mismo método del proxy, siempre que la implementación del middleware garantice la seguridad entre hilos para el envío. Dado que los objetos de método normalmente no almacenan un contexto de llamada con estado a lo largo de invocaciones sucesivas, actúan esencialmente como interfaces funcionales sin estado para el transporte de mensajes.

Ruta de uso

La secuencia típica al utilizar las clases de <SI-Namespace>::proxy::methods se divide en las siguientes fases:

  1. Provisión del proxy: la aplicación cliente localiza la instancia de servicio deseada mediante el descubrimiento de servicios del módulo com e instancia el proxy tipificado.
  2. Acceso a métodos: la aplicación accede al miembro de método específico del proxy. Interpretación: la invocación de un objeto de método se realizaría típicamente a través de un operador de llamada a función sobrecargado (operator()) del objeto correspondiente.
  3. Ejecución de métodos regulares (<Method>): en una operación regular, la aplicación pasa los parámetros de entrada declarados. El objeto de método reenvía la solicitud al servidor a través del middleware y devuelve a la aplicación invocadora un objeto que encapsula el resultado asíncrono. A continuación, la aplicación puede bloquearse de forma síncrona hasta disponer del resultado o registrar una notificación asíncrona.
  4. Ejecución de métodos Fire-and-Forget (<FnFMethod>): en una operación unidireccional, la aplicación también pasa los parámetros de entrada al objeto de método. Este inicia la transmisión y regresa inmediatamente a la aplicación, sin proporcionar ningún objeto de retorno o de estado para un resultado.

Escenarios de error

Al invocar clases de <SI-Namespace>::proxy::methods, deben tenerse en cuenta diferentes niveles de error, que varían según la semántica de la llamada:

  • Errores de comunicación y de vinculación: una precondición para cualquier llamada a un método es disponer de un canal de transporte operativo hacia la instancia de servicio. Si la conexión de red se interrumpe o la instancia de servicio deja de estar accesible, las llamadas fallan. En las clases regulares <Method>, el error correspondiente se transmite a través del objeto de resultado.
  • Errores de aplicación: si el servidor no puede procesar con éxito una <Method> regular, se devuelve al cliente un error de aplicación definido en la interfaz de servicio.
  • Comportamiento ante errores en Fire-and-Forget: Interpretación: en <FnFMethod>, no se comunicarían los errores de procesamiento del lado del servidor al invocador, ya que, semánticamente, fire-and-forget no contempla ningún mensaje de respuesta. Para la aplicación, esto significa que las excepciones o errores de cálculo del lado del servidor pasan desapercibidos, a menos que se utilice un canal de retorno independiente (como un evento) para este propósito. Por el contrario, los errores locales al aceptar parámetros o durante el envío pueden señalarse inmediatamente en el contexto invocador.
