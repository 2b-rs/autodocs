Contexto

El namespace <DataElement-Namespace> está asignado al módulo de diagnóstico (diag) de AUTOSAR Adaptive Platform en el Release R25-11. Su responsabilidad funcional primordial consiste en la provisión y encapsulación de interfaces para el manejo de elementos de datos de diagnóstico individuales. El componente central dentro de este namespace es la clase de interfaz <DataElementInterface> (representada como DiagnosticDataElementInterface).

En la arquitectura global de la Adaptive Platform, este namespace actúa como capa de abstracción y desacoplamiento entre el sistema de tiempo de ejecución de diagnóstico genérico y el software específico de la aplicación, el cual almacena datos de medición, parámetros o información de estado de la unidad de control. El identificador <DataElement-Namespace> funcionaría como comodín para un espacio de nombres específico del modelo que se genera durante la generación de código a partir del puerto de software configurado o del Diagnostic Data Identifier (DID) asociado. Entre los interlocutores principales figura, en el nivel superior, el servidor de diagnóstico del módulo diag, el cual recibe y procesa peticiones de diagnóstico de testers externos a través de protocolos estandarizados (como UDS). En el nivel inferior, la interfaz interactúa con la lógica de aplicación específica del vehículo, que adquiere los datos útiles solicitados a partir de sensores, actuadores o componentes internos de software. Gracias a esta división de roles, los protocolos de transporte, la gestión de sesiones de diagnóstico y la seguridad permanecen en el subsistema de diagnóstico, mientras que la provisión de los datos útiles se realiza de forma específica en la aplicación.

Ciclo de vida

El ciclo de vida de las estructuras dentro de <DataElement-Namespace> está estrechamente vinculado a la fase de inicialización y al tiempo de funcionamiento de las instancias de puertos de diagnóstico asignadas en el proceso respectivo. Antes de que un servicio de diagnóstico pueda reenviar peticiones externas a un elemento de datos, la interfaz subyacente debe haberse instanciado por completo y haberse dado a conocer al sistema de tiempo de ejecución de diagnóstico.

La creación de instancias de la clase <DataElementInterface> tiene lugar típicamente durante la fase de inicialización del software de aplicación. La aplicación asume aquí la propiedad y la gestión del ciclo de vida del objeto. La interfaz atraviesa una fase de inicialización y registro, una fase de funcionamiento activo para atender consultas en curso, así como una fase de liberación y destrucción controlada al finalizar el proceso ejecutor. Mientras el proceso de Adaptive permanezca activo, el objeto de interfaz continúa en estado operativo y a disposición de los accesos de la pila de diagnóstico.

Dado que las solicitudes de diagnóstico llegan de forma asíncrona a través del sistema de comunicación, las instancias de <DataElementInterface> están sujetas a requisitos especiales de concurrencia. La realización específica de la aplicación debe estar diseñada para ser segura para hilos, a fin de procesar sin inconsistencias los accesos concurrentes de lectura o escritura de la pila de diagnóstico y las actualizaciones paralelas procedentes de otros hilos de la aplicación. Al apagar el sistema, debe garantizarse que las operaciones de diagnóstico pendientes hayan concluido antes de liberar la instancia de interfaz.

Ruta de uso

La ruta típica de uso va desde la provisión de la instancia de interfaz pasando por el registro en el sistema de diagnóstico hasta la tramitación continua de operaciones de diagnóstico de lectura y escritura. Los desarrolladores de aplicaciones presumiblemente derivan de <DataElementInterface> o integran la interfaz para vincular la fuente de datos específica del vehículo con el subsistema de diagnóstico.

En un primer paso, la aplicación implementa la lógica de consulta concreta para el elemento de datos. Esto incluye la lectura de valores de medición internos, la conversión de valores brutos o el acceso a estructuras de almacenamiento. Tras la instanciación, la interfaz se registra a través del framework de diagnóstico, de modo que el módulo diag pueda reenviar de manera selectiva a la instancia correspondiente los comandos de diagnóstico entrantes (por ejemplo, ReadDataByIdentifier o WriteDataByIdentifier).

En el modo de funcionamiento regular, la pila de diagnóstico recibe una petición del tester e invoca la operación correspondiente en <DataElementInterface>. Acto seguido, la interfaz recupera los datos específicos de la aplicación, los formatea con arreglo a las directrices de configuración y devuelve los datos útiles al sistema de diagnóstico. El sistema de tiempo de ejecución de diagnóstico incrusta los datos en el mensaje de respuesta estandarizado y lo transmite al equipo de prueba externo. Tras completarse la respuesta, la interfaz permanece en estado de espera para subsiguientes peticiones de diagnóstico.

Escenarios de error

Durante el funcionamiento pueden producirse, en interacción con el namespace <DataElement-Namespace>, situaciones de error funcionales y temporales que exigen un tratamiento controlado de errores. Si los datos solicitados no están disponibles, no son válidos o no pueden leerse debido a fallos temporales de sensores, la interfaz debe señalar este estado de forma determinista.

Interpretación: dado que en el conjunto de datos de especificación no figuran códigos de error ni tipos de excepción específicos del sistema, la señalización de errores se efectúa a través de los mecanismos de retorno de errores estandarizados en el entorno de Adaptive (por ejemplo, tipos Result), los cuales notifican al sistema de tiempo de ejecución de diagnóstico el fallo de la operación. Entre las causas de error típicas figuran fallos de sensores subyacentes, rangos de valores no válidos en accesos de escritura o la superación de los plazos de ejecución definidos.

Como precondición para llamadas de lectura y escritura satisfactorias rige la inicialización completa de las fuentes de datos y la validez de las estructuras de búfer transferidas. Como poscondición, debe haberse proporcionado el valor de datos útiles correcto o haberse notificado un estado de error inequívoco. Con base en el estado de error notificado, el sistema de diagnóstico genera una respuesta negativa estandarizada (Negative Response Code, NRC) hacia el tester externo, preservándose así la estabilidad del sistema y la trazabilidad en la operación de diagnóstico.
