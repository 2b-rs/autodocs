Proporciona planificación determinista en tiempo real, protección de memoria, sincronización multinúcleo y contención de errores.

El clúster de módulos Operating System proporciona la planificación determinista en tiempo real para tareas e ISRs, así como protección de memoria y encapsulación de errores en OS-Applications particionadas [SWS_Os_00445]. Admite sistemas multinúcleo mediante spinlocks entre núcleos, activación asíncrona de tareas y el Inter-OS-Application Communicator (IOC) [SWS_Os_00686], [SWS_Os_00824]. Al producirse violaciones de protección, el OS permite, mediante hooks configurables, la finalización selectiva o el reinicio controlado de particiones individuales en tiempo de ejecución ApplicationLevelErrorHandling p. 53.

El clúster de módulos «Operating System» proporciona en AUTOSAR Classic la infraestructura fundamental de ejecución y protección para componentes de software y módulos de software básico. El sistema operativo encapsula recursos como tareas, ISRs, alarmas y contadores en OS-Applications [SWS_Os_00445], diferenciando entre particiones confiables (trusted) y no confiables [SWS_Os_00446] para garantizar una estricta contención de errores basada en la protección de memoria por MPU SafetyConceptStatusReport p. 49. En sistemas multinúcleo, el OS gestiona núcleos lógicos mediante IDs de núcleo estandarizados [SWS_Os_00790] y proporciona el Inter-OS-Application Communicator (IOC) para el intercambio basado en datos y eventos entre núcleos y particiones [SWS_Os_00824].

Diagrama de contexto: Integración del clúster de OS en la arquitectura de software básico de AUTOSAR e interfaces con EcuM, StbM, RTE y hardware. Fuentes: [SWS_Os_00445], [SWS_Os_00790], SWS_BSWGeneral p. 48.

Además de la planificación de tareas dirigida por eventos, el OS permite el seguimiento de la ejecución controlado por tiempo mediante Schedule Tables [SWS_Os_00783]. Estas se pueden ajustar a bases de tiempo globales del vehículo a través del Synchronized Time-Base Manager (StbM) mediante SyncScheduleTable [SWS_Os_00199], SWS_SynchronizedTimeBaseManager p. 220. Para la sincronización a través de los límites entre núcleos, el módulo ofrece spinlocks cercanos al hardware con detección integrada de interbloqueos [SWS_Os_00686], mientras que las activaciones de tareas entre núcleos pueden ejecutarse de forma asíncrona con ActivateTaskAsyn [SWS_Os_91022].

En caso de error (por ejemplo, ante desbordamientos de memoria), el OS activa el ProtectionHook [SWS_Os_00538]. A través de su valor de retorno se puede aislar una OS-Application errónea y terminarla de manera controlada o reinicializarla mediante una tarea de reinicio dedicada, sin reiniciar el sistema completo [SWS_Os_00787], ApplicationLevelErrorHandling p. 53.

Diagrama de estados: Ciclo de vida y estados de particionamiento de una OS-Application de AUTOSAR en caso de error. Fuentes: [SWS_Os_00773], [SWS_Os_00258], ApplicationLevelErrorHandling p. 53.

1. Arquitectura del sistema y rol del clúster de módulos

El clúster de módulos «Operating System» constituye en el modelo de capas de AUTOSAR el fundamento esencial de los System Services para la ejecución y coordinación de todos los componentes de software de tiempo real y módulos de software básico. El módulo principal [SWS_Os_00445] encapsula tareas, rutinas de servicio de interrupción (ISRs), alarmas, contadores (Counter) y tablas de seguimiento de ejecución (Schedule Tables) en unidades de ejecución configurables, las denominadas OS-Applications. En este sentido, el sistema operativo distingue estrictamente entre OS-Applications confiables (trusted) y no confiables (non-trusted) [SWS_Os_00446] para proporcionar seguridad funcional y protección de memoria de acuerdo con las clases de escalabilidad requeridas SafetyConceptStatusReport p. 49.

En arquitecturas multinúcleo, el OS gestiona núcleos lógicos que se referencian mediante identificadores unívocos de tipo CoreIdType [SWS_Os_00790]. Los IDs de núcleo son de base cero y están ordenados de forma correlativa [SWS_Os_00825], donde la constante OS_CORE_ID_MASTER identifica al núcleo maestro SWS_OS p. 111. A través del Inter-OS-Application Communicator (IOC) integrado, el sistema operativo proporciona mecanismos para la transmisión segura de datos entre particiones y núcleos [SWS_Os_00824]. Mediante la estandarización de las interfaces según OSEK OS y sus ampliaciones específicas de AUTOSAR, el OS garantiza un comportamiento determinista en tiempo real para módulos de nivel superior como el ECU State Manager (EcuM), el Synchronized Time-Base Manager (StbM) y el entorno de ejecución RTE SWS_BSWGeneral p. 48.

Diagrama de contexto: Integración del clúster de OS en la arquitectura de software básico de AUTOSAR e interfaces con EcuM, StbM, RTE y hardware. Fuentes: [SWS_Os_00445], [SWS_Os_00790], SWS_BSWGeneral p. 48.

2. Interacción y rutas de comunicación entre los módulos

La interacción entre los objetos de OS y las capas de la arquitectura AUTOSAR se realiza a través de rutas de control y de datos claramente delimitadas. Para el intercambio de datos entre particiones, el IOC genera funciones de comunicación tipadas con semántica no encolada («data», IocWrite / IocRead) o encolada («event», IocSend / IocReceive) [SWS_Os_00718], [SWS_Os_00738]. En transmisiones grupales se emplean los servicios IocSendGroup o bien IocReceiveGroup [SWS_Os_00728], [SWS_Os_00746]. Si un búfer interno del receptor se llena, el IOC lo señaliza al emisor con el estado IOC_E_LIMIT y registra un IOC_E_LOST_DATA para operaciones de lectura subsiguientes SWS_OS p. 225.

Cuando una OS-Application no confiable debe acceder a servicios privilegiados de una partición confiable, el cambio de contexto controlado se efectúa a través del servicio de sistema CallTrustedFunction [SWS_Os_00097]. En este caso, los parámetros se transmiten mediante una estructura de puntero de tipo TrustedFunctionParameterRefType [SWS_Os_00776]. El sistema operativo cambia temporalmente los privilegios de la MPU a los de la aplicación de destino SWS_OS p. 172. Durante esta ejecución, la función GetCurrentApplicationID devuelve el identificador de la Trusted Application invocada, mientras que GetApplicationID proporciona la aplicación emisora de la llamada original [SWS_Os_00797].

Para la coordinación temporal con bases de tiempo externas, el módulo StbM sincroniza Schedule Tables configuradas explícitamente a través de las interfaces del OS. StbM consulta primero cíclicamente el estado de sincronización mediante GetScheduleTableStatus [SWS_Os_00227] y luego transmite el valor de sincronización actual al OS mediante SyncScheduleTable [SWS_Os_00199]. A continuación, el sistema operativo calcula la desviación con respecto a los puntos de expiración (Expiry Points) y ajusta gradualmente los tiempos de retardo hasta que la tabla se ejecuta de forma síncrona con la base de tiempo global SWS_OS p. 57, SWS_SynchronizedTimeBaseManager p. 220.

Diagrama de secuencia: Sincronización explícita de una Schedule Table del OS por parte del Synchronized Time-Base Manager (StbM). Fuentes: [SWS_Os_00199], [SWS_Os_00227], SWS_SynchronizedTimeBaseManager p. 220.

3. Sincronización, reentrancia y contextos de tareas

El modelo de tiempo de ejecución distingue claramente entre el nivel de tareas, los niveles de interrupción de categoría 1 (Cat 1 ISR) y categoría 2 (Cat 2 ISR), y las rutinas de hook. Mientras que las Cat 1 ISRs se ejecutan sin sobrecarga del sistema operativo y no tienen permitido invocar servicios del OS, las Cat 2 ISRs son gestionadas íntegramente por el OS [SWS_Os_00782]. El identificador de la ISR activa se puede determinar mediante GetISRID; en caso de invocación fuera de una Cat 2 ISR, el servicio devuelve INVALID_ISR [SWS_Os_00511]. Las fuentes de interrupción individuales se pueden controlar de forma específica a nivel del controlador de interrupciones mediante EnableInterruptSource, DisableInterruptSource así como ClearPendingInterrupt [SWS_Os_91020], [SWS_Os_91019], [SWS_Os_91021].

Para la sincronización de secciones críticas a través de los límites de los núcleos del procesador, el OS proporciona spinlocks [SWS_Os_00791]. Un spinlock se adquiere de forma síncrona y bloqueante con GetSpinlock [SWS_Os_00686] o se consulta de forma no bloqueante mediante TryToGetSpinlock [SWS_Os_00703]. La liberación se efectúa mediante ReleaseSpinlock [SWS_Os_00695]. Para excluir interbloqueos, el OS comprueba en el estado extendido si existen errores de anidamiento y de solapamiento (E_OS_INTERFERENCE_DEADLOCK, E_OS_NESTING_DEADLOCK) SWS_OS p. 199.

Para activaciones de tareas y asignaciones de eventos entre núcleos, el OS proporciona variantes asíncronas de la API: ActivateTaskAsyn y SetEventAsyn retornan inmediatamente al llamador sin esperar a la ejecución en el núcleo de destino [SWS_Os_91022], [SWS_Os_91023]. Los posibles errores no se devuelven al llamador, sino que se registran mediante Error Hooks configurados [SWS_Os_00816], SWS_OS p. 203.

4. Ciclos de vida típicos y modos de funcionamiento

El arranque del sistema está coordinado principalmente por el ECU State Manager (EcuM). En el núcleo maestro, el EcuM inicia los núcleos subordinados antes del arranque del sistema operativo a través del servicio de OS StartCore [SWS_Os_00676], SWS_ECUStateManager p. 82. A continuación, cada núcleo iniciado invoca StartOS de manera autónoma. Tras la llamada a StartOS, el sistema operativo cambia todas las OS-Applications configuradas al estado APPLICATION_ACCESSIBLE antes de ejecutar los Startup Hooks SWS_OS p. 62. El número de núcleos iniciados con éxito se puede consultar en tiempo de ejecución con GetNumberOfActivatedCores SWS_OS p. 196.

Las Schedule Tables están sujetas a una máquina de estados claramente definida. Se pueden iniciar de forma absoluta mediante StartScheduleTableAbs [SWS_Os_00358], relativa mediante StartScheduleTableRel [SWS_Os_00347] o síncrona mediante StartScheduleTableSynchron [SWS_Os_00201]. Las tablas se pueden encadenar (NextScheduleTable, estado SCHEDULETABLE_NEXT) [SWS_Os_00191] o pasar inmediatamente al estado inactivo SCHEDULETABLE_STOPPED con StopScheduleTable [SWS_Os_00006]. Una sincronización explícita en curso puede cancelarse mediante SetScheduleTableAsync, continuándose con el procesamiento de los Expiry Points [SWS_Os_00422].

Para los modos de ahorro de energía en reposo, el OS ofrece la interfaz ControlIdle, con la cual el EcuM puede configurar el estado inactivo de núcleos individuales [SWS_Os_00769]. Durante el apagado, el EcuM coordina la desinicialización de todas las capas y llama finalmente a ShutdownAllCores o ShutdownOS para detener el sistema global de forma controlada SWS_ECUStateManager p. 90.

5. Tratamiento de errores, rastreo de DET y degradación

Las violaciones de protección (como desbordamientos de memoria o violaciones de temporización) conducen a la activación del ProtectionHook global [SWS_Os_00538]. En función del error, el hook decide sobre la estrategia de recuperación mediante un valor de retorno de tipo ProtectionReturnType [SWS_Os_00787]: terminación de la entidad causante (PRO_TERMINATETASKISR), terminación completa de la partición afectada (PRO_TERMINATEAPPL), inicio de un reinicio controlado de la partición (PRO_TERMINATEAPPL_RESTART) o apagado de la ECU (PRO_SHUTDOWN) ApplicationLevelErrorHandling p. 60.

Si una OS-Application se finaliza o se reinicia, el OS la transfiere desde el estado APPLICATION_ACCESSIBLE a APPLICATION_RESTARTING o APPLICATION_TERMINATED [SWS_Os_00773]. Todas las tareas, ISRs, alarmas y Schedule Tables activas de la partición se detienen de inmediato y todas las interrupciones se desactivan [SWS_Os_00447]. En el estado APPLICATION_RESTARTING se ejecuta exclusivamente el OsRestartTask para llevar a cabo tareas de limpieza antes de que se vuelva a habilitar el funcionamiento normal ApplicationLevelErrorHandling p. 53, ApplicationLevelErrorHandling p. 76.

Diagrama de estados: Ciclo de vida y estados de particionamiento de una OS-Application de AUTOSAR en caso de error. Fuentes: [SWS_Os_00773], [SWS_Os_00258], ApplicationLevelErrorHandling p. 53.

Para la prevención proactiva de errores, el sistema operativo ofrece funciones de comprobación de la protección de memoria como CheckTaskMemoryAccess y CheckISRMemoryAccess [SWS_Os_00512], [SWS_Os_00513], así como comprobaciones de permisos de acceso mediante CheckObjectAccess y CheckObjectOwnership [SWS_Os_00256], [SWS_Os_00017]. Mediante estas comprobaciones estandarizadas se puede garantizar que los componentes no confiables no realicen accesos no autorizados de escritura o ejecución en la memoria SWS_OS p. 73.

Contexto de esta guía: elaborada sobre la base de las especificaciones de AUTOSAR Classic para la versión R20-11. Todas las interfaces y transiciones de estado están estrictamente respaldadas por los requisitos SWS referenciados.
