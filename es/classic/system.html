EcuM_CheckRamHash función

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

uint8 EcuM_CheckRamHash (void);

Coordina los ciclos de vida de las ECU, arbitra modos de funcionamiento y garantiza la supervisión funcional por watchdog.

El clúster de módulos System Services controla el ciclo de vida de la ECU desde las fases tempranas de arranque hasta el apagado, arbitra modos de funcionamiento y asegura la supervisión de la ejecución del programa para cumplir los requisitos de seguridad funcional SafetyConceptStatusReport p. 15. El ECU State Manager agrupa las solicitudes de modo y delega las decisiones de estado en el BSW Mode Manager, mientras que el Watchdog Manager monitoriza la ejecución y comanda el Watchdog Driver SWS_ECUStateManager p. 103. En caso de violaciones graves del flujo de control, el clúster detiene el servicio al watchdog y fuerza un reinicio de hardware seguro [SWS_WdgM_00232].

El clúster de módulos System Services controla el ciclo de vida de la ECU, conmuta modos de funcionamiento y asegura la supervisión de la ejecución del programa conforme a los requisitos de seguridad funcional SafetyConceptStatusReport p. 15. El BSW Mode Manager (BswM) actúa como instancia de decisión central, mientras que el ECU State Manager (EcuM) coordina fases específicas de hardware como StartPreOS, Sleep y Shutdown y propaga solicitudes al BswM SWS_ECUStateManager p. 103. La supervisión de la ejecución del programa se implementa mediante el Watchdog Manager (WdgM), que realiza supervisiones Alive, Deadline y de flujo de control, y dispara el hardware a través del Watchdog Driver (Wdg) [SWS_Wdg_00155].

Diagrama de contexto: arquitectura y colaboración de los System Services con BSW, RTE y hardware. Fuentes: SWS_ECUStateManager p. 34, AUTOSAR_EXP_ModeManagementGuide p. 61.

Durante el funcionamiento continuo, solicitudes como RUN o POST_RUN se recopilan en el EcuM, el cual las notifica de forma agregada al BswM [SWS_BswM_91004]. Tras evaluar las reglas configuradas, el BswM establece el estado mediante EcuM_SetState, lo cual se notifica a los componentes a través de la RTE [SWS_EcuM_04116]. En las fases de reposo, los eventos de despertar se procesan mediante una máquina de estados estandarizada (NONE, PENDING, VALIDATED, EXPIRED) y se señalan sincrónicamente al BswM [SWS_BswM_00131].

Diagrama de secuencias: ruta de interacción de ECU Mode Handling entre SW-C, EcuM, BswM y RTE. Fuentes: SWS_ECUStateManager p. 103, ModeManagementGuide p. 34.

Si se produce un error crítico de supervisión en el WdgM, el estado de supervisión cambia a WDGM_GLOBAL_STATUS_STOPPED, tras lo cual se detiene el disparo del watchdog y el hardware provoca un reinicio del sistema [SWS_WdgM_00232]. El clúster notifica los errores de configuración o de invocación de forma estandarizada al Default Error Tracer (Det) [SWS_EcuM_03026].

1. Arquitectura del sistema y rol del clúster de módulos

El clúster de módulos System Services constituye la columna vertebral funcional de la AUTOSAR Classic Platform. Comprende el BSW Mode Manager (BswM), el ECU State Manager (EcuM), el Watchdog Manager (WdgM) y el hardware cercano Watchdog Driver (Wdg) SWS_ECUStateManager p. 35. Conjuntamente, estos módulos controlan el ciclo de vida integral de la ECU, coordinan los modos de funcionamiento cercanos al hardware y aplicativos, y garantizan la supervisión temporal y lógica de la ejecución del programa para asegurar la seguridad funcional SafetyConceptStatusReport p. 15.

En la arquitectura en capas de AUTOSAR, BswM, EcuM y WdgM se ubican en la capa de System Services por encima de las capas de abstracción y controladores, mientras que el Watchdog Driver (Wdg), como parte del Microcontroller Abstraction Layer (MCAL), atiende los registros de hardware del temporizador de watchdog [SWS_Wdg_00106]. El EcuM actúa en su variante flexible (EcuM Flex) como nexo con el hardware para secuencias tempranas de arranque y tardías de desconexión antes o después del inicio del sistema operativo. Ya no posee una máquina de estados compleja propia para modos de aplicación, sino que delega el arbitraje de modos en el BswM SWS_ECUStateManager p. 103. Estándares externos de diagnóstico como UDS (ISO 14229) y protocolos de Network Management se acoplan directamente a la evaluación de reglas del BswM a través de interfaces BSW definidas (como el servicio 0x28 CommunicationControl mediante Dcm) [SWS_BswM_00048].

Diagrama de contexto: arquitectura y colaboración de los System Services con BSW, RTE y hardware. Fuentes: SWS_ECUStateManager p. 34, AUTOSAR_EXP_ModeManagementGuide p. 61.

2. Interacción y rutas de comunicación entre los módulos

La interacción dentro del clúster se caracteriza por relaciones de control y notificación claramente delimitadas. En el marco del ECU Mode Handling, el EcuM recibe solicitudes para estados como RUN o POST_RUN procedentes de componentes de software (SW-Cs) y reenvía el resultado de arbitraje agregado mediante [SWS_BswM_91004] al BswM ModeManagementGuide p. 34. Dado que el EcuM no toma decisiones de transición propias, el BswM evalúa reglas lógicas configuradas e instruye el estado de destino sincrónicamente mediante EcuM_SetState [SWS_EcuM_04116]. A continuación, el EcuM refleja este estado a la aplicación a través de la RTE y confirma al BswM el estado de ejecución actual mediante BswM_EcuM_CurrentState [SWS_BswM_91003].

Una ruta de interacción paralela conecta BswM, WdgM y Wdg. Componentes de software y módulos BSW notifican la llegada a puntos de control definidos al WdgM, el cual determina a partir de ello el estado de supervisión local y global SWS_WatchdogManager p. 51. El WdgM pone a disposición las modificaciones de estado de la supervisión local a través de puertos de modo proporcionados [SWS_WdgM_00148]. En función del estado del sistema de orden superior, el BswM cambia el modo de funcionamiento del Watchdog Manager mediante WdgM_SetMode [SWS_WdgM_00154]. 3. Sincronización, reentrancia y contextos de tareas

La ejecución de los System Services se distribuye de forma determinista entre niveles de tareas periódicas, retrollamadas asíncronas y contextos de interrupción. La carga periódica principal de la gestión de modos la soporta BswM_MainFunction, que se invoca en el contexto de una tarea del sistema operativo mediante el BSW Scheduler (SchM) y procesa todas las reglas cuya evaluación deba diferirse [SWS_BswM_00053]. Si se producen eventos con evaluación inmediata de reglas, estos se procesan sincrónicamente de forma directa en el contexto de la indicación BSW o de la API de la SW-C invocadora ModemanagementGuide p. 31.

En sistemas multinúcleo, la normalización exige una asignación estricta de recursos. BswM_Init está diseñado de forma condicionalmente reentrante para permitir instanciaciones separadas por partición o núcleo de procesador [SWS_BswM_00002]. Durante las fases de reposo y retención, el EcuM reserva recursos del sistema operativo propios del núcleo (RES_AUTOSAR_ECUM_<core#>) para asegurar la sincronización entre núcleos maestro y esclavo [SWS_EcuM_03010]. La inicialización de controladores mediante EcuM_AL_DriverInitZero y EcuM_AL_DriverInitOne se invoca por separado en cada núcleo e inicializa exclusivamente módulos MCAL locales del núcleo [SWS_EcuM_04145]. El borrado de eventos de despertar mediante EcuM_ClearWakeupEvent es explícitamente no interrumpible y puede realizarse tanto desde contextos de tarea como de interrupción [SWS_EcuM_02807].

4. Ciclos de vida típicos y modos de funcionamiento

El ciclo de vida de una ECU se divide normativamente en las fases STARTUP, UP, SHUTDOWN y SLEEP [SWS_EcuM_91005]. La fase STARTUP comienza antes del inicio del sistema operativo en la secuencia StartPreOS con la invocación de EcuM_Init, la evaluación de la causa del reinicio y la carga de la configuración post-build mediante EcuM_DeterminePbConfiguration AUTOSAR_SWS_ECUStateManager p. 38. Tras transferir el control al sistema operativo mediante StartOS, el EcuM inicializa en StartPostOS el SchM y el BswM [SWS_EcuM_02934]. A continuación, el BswM asume el control e inicia los módulos BSW restantes así como la aplicación.

Durante el funcionamiento continuo (fase UP), EcuM y BswM gestionan los modos RUN y POST_RUN, así como el servicio opcional Alarm Clock SWS_ECUStateManager p. 75. Al cambiar al estado de reposo (SLEEP), el clúster distingue estructuralmente entre HALT (detiene la CPU) y POLL (frecuencia de reloj de CPU reducida) SWS_ECUStateManager p. 54. Previamente, la invocación WdgM_DeInit desinicializa el Watchdog Manager y adapta los tiempos de espera de disparo para evitar reinicios no deseados durante el apagado [SWS_WdgM_00261]. En la secuencia de sondeo, el EcuM se bloquea en un bucle de comprobación con llamadas periódicas de EcuM_SleepActivity y EcuM_CheckWakeupHook hasta que se detecta un evento de despertar [SWS_EcuM_03020].

Los eventos de despertar detectados pasan por una estricta gestión de estados desde ECUM_WKSTATUS_NONE a través de PENDING hasta VALIDATED o EXPIRED [SWS_EcuM_04091]. El EcuM señala sincrónicamente cada cambio de estado mediante BswM_EcuM_CurrentWakeup al BswM [SWS_BswM_00131]. La validación de despertar protege frente a perturbaciones transitorias del bus y monitoriza la ventana temporal mediante temporizadores de validación configurables [SWS_EcuM_04004]. Si el ciclo de vida concluye en SHUTDOWN, OffPreOS desactiva el BswM y SchM antes de que OffPostOS reinicie la ECU o la desenergice mediante callouts de integración como EcuM_AL_Reset o EcuM_AL_SwitchOff AUTOSAR_SWS_ECUStateManager p. 49.

5. Tratamiento de errores, rastreo de DET y degradación

Para la detección de errores de tiempo de ejecución y configuración, el clúster integra mecanismos de notificación estandarizados al Default Error Tracer (Det). Si una entidad intenta emitir una liberación mediante EcuM_ReleasePOST_RUN sin una solicitud previa, el EcuM notifica el error de desarrollo ECUM_E_MISMATCHED_RUN_RELEASE al Det [SWS_EcuM_03026]. Las solicitudes múltiples de un mismo usuario se registran con ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03025]. Asimismo, el WdgM monitoriza las llamadas a la API en estado no inicializado y notifica WDGM_E_UNINIT en caso de que se invoquen servicios antes de completar la inicialización [SWS_WdgM_00288].

La supervisión de seguridad se fundamenta en el control funcional de tres etapas del WdgM (Alive Supervision, Deadline Supervision y supervisión lógica del flujo de control) SafetyConceptStatusReport p. 47. Si un fallo de supervisión provoca la superación de las tolerancias de error, el estado de supervisión global cambia de WDGM_GLOBAL_STATUS_OK a través de FAILED hacia WDGM_GLOBAL_STATUS_EXPIRED y, finalmente, STOPPED [SWS_WdgM_00387]. En este estado, el WdgM establece la condición de disparo en 0 para todos los controladores de watchdog, con lo que el watchdog de hardware reinicia de inmediato el microcontrolador [SWS_WdgM_00232]. Para reinicios de emergencia controlados, el WdgM proporciona el servicio WdgM_PerformReset, que detiene el redisparo continuo y fuerza el reinicio de hardware [SWS_WdgM_00264]. Para la protección tras fases de reposo prolongadas, el EcuM comprueba además mediante EcuM_CheckRamHash la consistencia de la memoria volátil para interceptar reinicios erróneos en caso de corrupción de la RAM [SWS_EcuM_02921].
