EcuM_CheckRamHash función

Este callout es intended a proporcionar un RAM integridad test. el goal de este test es a garantizar que después de un largo SLEEP duración, RAM contenidos es todavía coherente. el comprobar no necesitar a ser exhaustive desde este would consume quite algún procesamiento tiempo durante wakeups. A bien designed comprobar va a execute quickly y detect RAM integridad defects con un suficiente probability. este specification no make cualquier suposición sobre el algoritmo elegido para un particular ECU. el areas de RAM que será comprobado tienen a ser elegido carefully. ello depende en el comprobar algoritmo itself y el tarea estructura. pila contenidos del tarea que ejecuta el RAM comprobar e.g. muy likely no puede ser comprobado. ello es good practice a tienen el hash generation y checking en el mismo tarea y que este tarea no es preemptible y que allí es solo little activity entre hash generation y hash comprobar. el RAM comprobar itself se proporciona por el sistema designer. en caso de applied multi core y existence de Satellite-Ecu M(s): Esta API será llamado por el maestro-EcuM solo.

uint8 EcuM_CheckRamHash (void);

EcuM_EndCheckWakeup función

Esta API es llamada por cualquier SW módulo whose despertar fuente es comprobado asynchronously (e.g. asíncrono Can Trcv controlador) y el comprobar del despertar devuelve un negativo resultado (ningún despertar por este fuente). el API cancela el CheckWakeupTimer para el WakeupSource. si el correponding CheckWakeupTimer es cancelado el comprobar de este despertar fuente es finalizado.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);

Arquitectura del sistema y rol del clúster de módulos

El clúster «System Services» comprende los módulos que sustentan el arranque, los modos de operación, el sleep/shutdown y la supervisión del flujo de ejecución del programa de una ECU de Classic Platform. En este contexto, el ECU State Manager es el servicio del sistema que establece el estado de hardware final tras el apagado del OS (SWS EcuM p. 82, [SWS_EcuM_04020]). Los cuatro módulos tienen funciones claramente diferenciadas:

  • El BswM arbitra las indicaciones de modo entrantes ([SWS_BswM_00035]). Las reglas vinculan lógicamente ModeRequestPorts y activan listas de acciones True o False (Mode Management Guide p. 32). Las acciones se ejecutan exclusivamente en el contexto de una lista de acciones ([SWS_BswM_00147]).
  • El EcuM inicializa la BSW, inicia y finaliza el OS y gestiona los estados de las fuentes de reactivación ([SWS_EcuM_02811], [SWS_EcuM_04091]). No dispone de una máquina de estados propia. Asume los cambios de estado del BswM (SWS EcuM p. 99, [SWS_EcuM_04116]).
  • El WdgM supervisa Supervised Entities mediante Checkpoints ([SWS_WdgM_00263]) y forma a partir de ellas un Global Supervision Status ([SWS_WdgM_00360]). Establece los modos de watchdog mediante WdgIf_SetMode ([SWS_WdgM_00186]).
  • El Wdg controla el hardware de watchdog interno o externo ([SWS_Wdg_00161], [SWS_Wdg_00076]). Atiende el hardware mientras la condición de disparo sea válida ([SWS_Wdg_00144]).

Diagrama de contexto: el diagrama de contexto muestra al BswM como decisor sobre los modos, al EcuM como ejecutor de las secuencias del ciclo de vida y la cadena de supervisión WdgM → WdgIf → Wdg → Hardware. Fuentes: SWS EcuM p. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Interacción y rutas de comunicación

EcuM ↔ BswM (ECU Mode Handling): esta ruta está activa si EcuMModeHandling está configurado ([SWS_EcuM_04115]). Las SW-C solicitan RUN y POST_RUN a través de EcuM_RequestRUN o EcuM_RequestPOST_RUN respectivamente, y los liberan nuevamente ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). El EcuM notifica el resultado del arbitraje a través de BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). A continuación, el BswM establece el estado mediante EcuM_SetState ([SWS_EcuM_04122]). Tan pronto como la RTE confirma el cambio, el EcuM devuelve el estado a través de BswM_EcuM_CurrentState ([SWS_EcuM_04143], [SWS_BswM_91003]).

Ruta de reactivación: los controladores notifican reactivaciones mediante EcuM_SetWakeupEvent, que marca el evento como pendiente ([SWS_EcuM_01117]). Si se requiere una validación, el EcuM inicia el protocolo de validación ([SWS_EcuM_02975]). La validación la asume exactamente un módulo BSW (SWS EcuM p. 69). Su llamada a EcuM_ValidateWakeupEvent notifica al BswM y al ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). Cada cambio de estado de una fuente de reactivación se notifica al BswM como solicitud de modo ([SWS_EcuM_04003]).

Diagrama de estados: el diagrama de estados muestra los ciclos de vida de una fuente de reactivación (NONE, PENDING, VALIDATED, EXPIRED) y la notificación al BswM al entrar en cada estado. Fuentes: [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM p. 64

WdgM → Wdg: Wdg_SetTriggerCondition recibe un timeout en milisegundos y lo convierte internamente en un valor de contador teniendo en cuenta el modo actual ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). La rutina de mantenimiento del controlador se comporta de la siguiente manera:

  • Si el contador es mayor que cero, lo decrementa y activa el hardware ([SWS_Wdg_00134]).
  • En cero, ya no lo activa y el watchdog expira ([SWS_Wdg_00135]).

Interpretación: es probable que WdgIf reenvíe el modo y la condición de disparo a la instancia de Wdg direccionada en cada caso. Varias instancias llevan nombres únicos ([SWS_Wdg_00172]).

EcuM → WdgM (Reset): WdgM_PerformReset es un destino de reset obligatorio ([SWS_EcuM_04005], [SWS_EcuM_04044]). Establece la condición de disparo de todos los controladores en 0, y los watchdogs de hardware provocan por ello un reset ([SWS_WdgM_00264], SWS WdgM p. 82). Como causa de shutdown está disponible ECUM_CAUSE_WDGM ([SWS_EcuM_04045]).

Sincronización, reentrancia y contextos de tareas

BswM_MainFunction: Evalúa todas las reglas que utilizan una solicitud con BSWM_DEFERRED ([SWS_BswM_00075]). Los temporizadores de BswM siempre se procesan como deferred ([SWS_BswM_00220]). Por el contrario, las solicitudes con «immediate» se evalúan de inmediato (Mode Management Guide p. 32).

EcuM_MainFunction: Se ejecuta en todas las instancias de EcuM ([SWS_EcuM_04011]). Supervisa los timeouts de validación ([SWS_EcuM_04082]) y valida los candidatos de wakeup tras el WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction: Inicia la supervisión en la primera llamada tras WdgM_Init ([SWS_WdgM_00406]) y calcula después en cada período el Global Supervision Status (SWS WdgM p. 34).

Contexto de interrupción: Los servicios de wakeup pueden invocarse desde contexto de interrupción, de OS y sin OS ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). Sin embargo, están especificados como «Non-Reentrant, Non-Interruptible» ([SWS_EcuM_02826], [SWS_EcuM_02828]). Una excepción es EcuM_ValidateWakeupEvent: es reentrante y puede invocarse desde contexto de interrupción y de tarea ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Reentrancia de WdgM y Wdg:

  • WdgM_SetMode, WdgM_DeInit y Wdg_SetTriggerCondition no son reentrantes ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • WdgM_GetMode aún devuelve el modo anterior durante un cambio de modo en curso ([SWS_WdgM_00168], SWS WdgM p. 77).
  • Wdg deshabilita las interrupciones para la consistencia de datos únicamente mediante los mecanismos previstos de la BSW ([SWS_Wdg_00040]).

Multicore: En cada Core se ejecuta una instancia propia de EcuM. El EcuM maestro inicia los demás Cores (SWS EcuM p. 71). De ello se derivan las siguientes obligaciones:

  • Cada instancia procesa los wakeups de su propio Core ([SWS_EcuM_04012]).
  • Se inicializan todos los BswM locales al Core ([SWS_EcuM_04014]).
  • Se reserva un recurso RES_AUTOSAR_ECUM por cada Core ([SWS_EcuM_03010]).
  • Las C-API están disponibles en cada partición en la que se ejecuta un EcuM ([SWS_EcuM_04095]).

El BswM es condicionalmente reentrante para sistemas multipartición ([SWS_BswM_00002]).

Ciclos de vida y modos de funcionamiento

Arranque (StartPreOS): EcuM_Init ejecuta la secuencia StartPreOS ([SWS_EcuM_02684]). Esta incluye:

  • los bloques de inicialización 0 y 1 en el orden configurado ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • la selección de la configuración post-build ([SWS_EcuM_02906]),
  • la comprobación de consistencia de todas las configuraciones post-build antes de la primera inicialización de la BSW ([SWS_EcuM_02796]).

Según la descripción de la estructura, Wdg_Init pertenece a las funciones de inicialización utilizadas por el EcuM (SWS EcuM p. 34). Wdg_Init establece el modo predeterminado y el timeout ([SWS_Wdg_00001]).

Arranque (StartPostOS): EcuM_StartupTwo se ejecuta en una tarea iniciada por StartOS ([SWS_EcuM_02806]). Inicia SchM e inicializa BswM ([SWS_EcuM_02932]). BswM_Init solo requiere un OS y un SchM inicializados (SWS BswM p. 69). El BswM puede inicializar otros controladores en la fase UP, por ejemplo mediante EcuM_AL_DriverInitBswM_<x> (SWS EcuM p. 46, [SWS_EcuM_04114]).

Diagrama de secuencia: el diagrama de secuencia muestra el orden de StartPreOS y StartPostOS en el Core maestro. Fuentes: [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM p. 82, SWS EcuM p. 42

Sleep: Antes de EcuM_GoDownHaltPoll, típicamente el BswM debe haber seleccionado un destino SLEEP (SWS EcuM p. 54, [SWS_EcuM_91002]). El procedimiento:

  1. GoSleep activa las fuentes de wakeup; el OS permanece activo durante ello ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. A continuación sigue, según el modo Sleep, Halt con hash de RAM ([SWS_EcuM_02863]) o Poll ([SWS_EcuM_02962]). No debe perderse ningún wakeup durante este proceso ([SWS_EcuM_02188]).
  3. Un wakeup conduce a la secuencia WakeupRestart con reinicialización de controladores ([SWS_EcuM_02963], [SWS_EcuM_02923]).

En R20-11, el callout de Poll se denomina EcuM_CheckWakeup ([SWS_EcuM_02929]). Solo a partir de R21-11 se denomina EcuM_CheckWakeupHook (SWS EcuM p. 145).

Watchdog en Sleep: Antes del Sleep, WdgM_DeInit cambia a un modo Sleep con condiciones de disparo compatibles y detiene la supervisión (SWS WdgM p. 59, [SWS_WdgM_00407]). Sin embargo, la descripción de la estructura del EcuM solo menciona WdgM_PerformReset como dependencia de WdgM. Por lo tanto, la llamada a WdgM_DeInit probablemente se realiza mediante una acción de BswM o código de integración.

Diagrama de secuencia: el diagrama de secuencia muestra la fase SLEEP con Halt: GoSleep, hash de RAM, Wakeup y WakeupRestart. Fuentes: SWS EcuM p. 54, SWS EcuM p. 55, SWS EcuM p. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown: La secuencia:

  1. OffPreOS desinicializa BswM y SchM (SWS EcuM p. 90). Después de esto, el BswM ya no procesa ningún modo ([SWS_BswM_00120]).
  2. Como última actividad, el EcuM llama a ShutdownOS ([SWS_EcuM_02952]). El hook de shutdown llama a EcuM_Shutdown ([SWS_EcuM_02953]).
  3. Por último, siguen EcuM_AL_Reset o EcuM_AL_SwitchOff ([SWS_EcuM_04074], [SWS_EcuM_04075]).

Las fuentes de wakeup deben borrarse antes de Dem_Shutdown y NvM_WriteAll mediante callouts de usuario de BswM (SWS EcuM p. 124, [SWS_BswM_00054]). Un wakeup durante el shutdown conduce al reinicio tras la finalización del mismo ([SWS_EcuM_02756]). Wdg no posee una interfaz de desinicialización propia ([SWS_Wdg_00031]).

Tratamiento de errores, rastreo en DET y degradación

Errores de desarrollo (DET):

  • BswM ignora las indicaciones antes de la inicialización y notifica BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). Las acciones fallidas las notifica como error de tiempo de ejecución BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • EcuM notifica solicitudes de RUN duplicadas y liberaciones inadecuadas ([SWS_EcuM_03024], [SWS_EcuM_03023]), así como fuentes de wakeup desconocidas ([SWS_EcuM_02867]).
  • WdgM y Wdg definen códigos de error propios ([SWS_WdgM_00004], [SWS_Wdg_00010]). Un WdgIf_SetMode fallido lo notifica WdgM como WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Errores no recuperables: EcuM los reenvía a EcuM_ErrorHook ([SWS_EcuM_04033]). Ejemplos de ello son datos de configuración inconsistentes o una comprobación de RAM fallida ([SWS_EcuM_91003]). EcuM ignora los errores devueltos por las funciones de inicialización durante la inicialización ([SWS_EcuM_02980]).

Degradación de la supervisión: El estado global se inicia como WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Los cambios de modo solo están permitidos en los estados OK y FAILED ([SWS_WdgM_00145]). La desactivación del watchdog se puede prohibir mediante configuración ([SWS_WdgM_00031]). La escalada se produce de la siguiente manera:

  1. En el estado EXPIRED, la reacción ante el error se pospone un margen de tolerancia configurable (SWS WdgM p. 34).
  2. En el estado STOPPED, WdgM notifica WDGM_E_SUPERVISION y sigue un reset del watchdog ([SWS_WdgM_00375]).
  3. Un cambio de modo fallido también conduce a STOPPED (SWS WdgM p. 57).

Diagnóstico tras el reset: La SEID que expiró primero se almacena de forma doble invertida en RAM no inicializada. Ya se puede leer antes de WdgM_Init ([SWS_WdgM_00348], [SWS_WdgM_00349]). WdgM notifica los cambios de estado mediante Mode Ports ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset todavía existe en R20-11 ([SWS_BswM_00157]), pero queda obsoleto a partir de R21-11 (SWS BswM p. 2).

Errores de controladores y última protección: Wdg notifica los errores de producción WDG_E_MODE_FAILED y WDG_E_DISABLE_REJECTED al DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). Si EcuM_AL_SwitchOff se queda bloqueado en un deadlock, el watchdog de hardware reinicia la unidad de control (SWS EcuM p. 141).
