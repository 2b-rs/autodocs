Reenvía solicitudes de almacenamiento del administrador de NVRAM a la emulación de Flash EEPROM o a la abstracción de EEPROM mediante el índice de dispositivo.

MemIf reenvía las solicitudes de almacenamiento del NVRAM Manager a módulos Fee o Ea y oculta su cantidad tras una API unificada SWS MemIf p. 7. El parámetro DeviceIndex selecciona el módulo; si solo hay uno configurado, se ignora y MemIf se implementa como un conjunto de macros SWS MemIf p. 17. Los servicios aceptan solicitudes de forma síncrona y transmiten el valor de retorno, mientras que la operación de almacenamiento se ejecuta por debajo de forma asíncrona. El estado y el resultado los proporcionan MemIf_GetStatus y MemIf_GetJobResult. Con la detección de errores de desarrollo activa, las llamadas erróneas devuelven E_NOT_OK o MEMIF_JOB_FAILED.

El Memory Abstraction Interface sustituye a las capas de interfaz de controlador anteriores para Flash y EEPROM. Permite al NVRAM Manager comunicarse con múltiples módulos de abstracción a través de una API unificada: la Flash EEPROM Emulation (Fee) y la EEPROM Abstraction (Ea) SRS MemHwAb p. 5. MemIf oculta el número de estos módulos y proporciona una segmentación virtual sobre un espacio de direcciones lineal SWS MemIf p. 7.

Diagrama de contexto: MemIf media entre NvM y Fee/Ea; las notificaciones de finalización van directamente de Fee/Ea al NvM. Fuentes: SWS Fee p. 6, [SWS_MemIf_00047]

MemIf no dispone de lógica de almacenamiento propia. El parámetro DeviceIndex selecciona el módulo; si solo hay uno configurado, se ignora y MemIf se implementa como un conjunto de macros. En caso de múltiples módulos, la distribución se efectúa, por ejemplo, mediante tablas de punteros a función SWS MemIf p. 17. En R20-11, DeviceIndex es de tipo uint8 [SWS_MemIf_00039]; versiones posteriores utilizan uint16.

Los servicios aceptan solicitudes de forma síncrona y transmiten el valor de retorno del módulo [SWS_MemIf_00040]. A continuación, la operación de almacenamiento se ejecuta de forma asíncrona en la función principal de la capa inferior. El NvM se entera de la finalización mediante callback desde Fee/Ea o mediante sondeo de MemIf_GetJobResult SWS Fee p. 48. MemIf_GetStatus notifica UNINIT, IDLE, BUSY o BUSY_INTERNAL [SWS_MemIf_00064]. El resultado del trabajo se refiere siempre a la última solicitud y distingue, entre otros, bloques cancelados, inconsistentes e inválidos [SWS_MemIf_00065]. MemIf_SetMode tiene efecto sobre todos los módulos al mismo tiempo [SWS_MemIf_00038].

Diagrama de secuencias: aceptación síncrona a través de MemIf, ejecución asíncrona en el controlador, finalización mediante callback o sondeo. Fuentes: SWS Ea p. 41, [SWS_MemIf_00040]

En caso de error, MemIf notifica índices de dispositivo no válidos y punteros NULL como errores de desarrollo [SWS_MemIf_00006]. En tales casos, los servicios devuelven E_NOT_OK, y MemIf_GetJobResult devuelve MEMIF_JOB_FAILED SWS MemIf p. 21. Fee y Ea detectan los errores de tiempo de ejecución de la memoria; el NvM los lee en modo de sondeo como MEMIF_JOB_FAILED y es responsable de su subsanación ErrorDescription p. 58.

Función en la pila de memoria: distribuidor entre NvM y Fee/Ea

El Memory Abstraction Interface (MemIf) sustituye a las capas de interfaz de controlador anteriores para Flash y EEPROM. Permite al NVRAM Manager (NvM) acceder a múltiples módulos de abstracción de memoria a través de una única API: la Flash EEPROM Emulation (Fee) y la EEPROM Abstraction (Ea) SRS MemHwAb p. 5. Hacia las capas superiores, MemIf oculta cuántos módulos Fee y Ea se encuentran por debajo. Ofrece una segmentación virtual sobre un espacio de direcciones lineal unificado SWS MemIf p. 7. Fee y Ea proporcionan el direccionamiento basado en bloques y un número «virtualmente ilimitado» de ciclos de borrado y escritura. Por ello, no es necesario modificar el NvM cuando cambian el controlador o el componente SRS MemHwAb p. 5.

MemIf no contiene en sí ninguna lógica de almacenamiento. Su API debe mapearse a la API de los módulos de abstracción, y el comportamiento funcional queda definido por las especificaciones de estos o por las de los controladores de memoria SWS MemIf p. 17. En consecuencia, MemIf requiere los servicios de los módulos de abstracción, para Ea por ejemplo Ea_Read, Ea_Cancel, Ea_GetStatus y Ea_GetJobResult [SWS_MemIf_00047]. De forma opcional utiliza Det_ReportError [SWS_MemIf_00048]. Los tipos MemIf_StatusType, MemIf_JobResultType y MemIf_ModeType definidos en MemIf.h constituyen el vocabulario común de la pila [SWS_MemIf_00064] [SWS_MemIf_00065] [SWS_MemIf_00066]. Así, por ejemplo, Fls_GetJobResult devuelve directamente MemIf_JobResultType SWS Fls p. 36.

Las figuras de versiones más recientes muestran adicionalmente por debajo de Ea y Fee los módulos MemAcc y Mem SWS Ea p. 42. Para R20-11 probablemente sea determinante la vista general más antigua, en la que Fee se basa en el controlador de Flash y Ea en el controlador de EEPROM SWS Fee p. 6. Para MemIf, la diferencia carece de relevancia, ya que solo reenvía hasta el nivel de abstracción SWS MemIf p. 17.

Diagrama de contexto: MemIf se sitúa entre NvM y los módulos de abstracción Fee/Ea; las notificaciones de finalización llegan al NvM directamente desde Fee/Ea. Fuentes: SWS Fee p. 6, SRS MemHwAb p. 5, [SWS_MemIf_00047], [SWS_MemIf_00048]

Selección de dispositivo mediante DeviceIndex: macros o tabla de distribución

El parámetro DeviceIndex selecciona el módulo de abstracción y, con ello, el componente de memoria. Si solo se ha configurado un módulo, este parámetro se ignora SWS MemIf p. 17. En tal caso, MemIf debe implementarse como un conjunto de macros, como #define MemIf_Write(DeviceIndex, BlockNumber, DataPtr) Fee_Write(BlockNumber, DataPtr). Si hay varios módulos, las llamadas deben distribuirse mediante mecanismos eficientes; como una de las soluciones, la especificación menciona tablas de punteros a función indexadas mediante DeviceIndex SWS MemIf p. 17. Si una biblioteca específica del fabricante sustituye a todos los módulos Fee y Ea necesarios, MemIf consta únicamente de macros SRS MemHwAb p. 5.

En R20-11, DeviceIndex es de tipo uint8 [SWS_MemIf_00039] [SWS_MemIf_00041]. Versiones posteriores de la especificación lo indican como uint16 SWS MemIf p. 18. Lo normativo para esta versión es uint8.

Diagrama de actividades: la cantidad de módulos de abstracción configurados determina si se utiliza el mapeo mediante macros o la distribución por DeviceIndex. Fuentes: SWS MemIf p. 17, SRS MemHwAb p. 5

Flujo de solicitudes: aceptación síncrona, ejecución asíncrona

Todos los servicios de MemIf están especificados de forma síncrona. Cada uno llama a la función homónima del módulo seleccionado y devuelve su valor de retorno, como ocurre con Read, Write e InvalidateBlock [SWS_MemIf_00039] [SWS_MemIf_00040] [SWS_MemIf_00044]. La operación de almacenamiento propiamente dicha se ejecuta a continuación de forma asíncrona en la función principal llamada cíclicamente de la capa inferior. La secuencia de Ea muestra para ello un bucle sobre Eep_MainFunction en la tarea BSW SWS Ea p. 41. Según la especificación de Fee, este patrón es válido también para los demás servicios asíncronos SWS Fee p. 48.

El NvM se entera del final del trabajo a través de una de dos vías, según la configuración de la pila. O bien el módulo de abstracción llama a un callback como NvM_JobEndNotification o NvM_JobErrorNotification, o bien el NvM realiza un sondeo de MemIf_GetJobResult SWS Fee p. 48 EXP ErrorDescription p. 45. MemIf propiamente dicho no proporciona ninguna función de callback; su API consta de los siguientes servicios [SWS_MemIf_00038] [SWS_MemIf_00046].

Estado, resultado del trabajo y modo de operación

MemIf_GetStatus proporciona el estado del módulo seleccionado [SWS_MemIf_00042]. Los posibles valores son MEMIF_UNINIT, MEMIF_IDLE, MEMIF_BUSY y MEMIF_BUSY_INTERNAL. Con MEMIF_BUSY_INTERNAL, el módulo de abstracción está ocupado con la gestión interna, mientras que el controlador puede estar ocupado o inactivo (busy o idle) [SWS_MemIf_00064]. La especificación de Fee concreta las condiciones y cita como ejemplo de gestión interna la reorganización de la memoria Flash (Garbage Collection) SWS Fee p. 30. En el controlador de Flash, el estado puede consultarse incluso antes de la inicialización y entonces es MEMIF_UNINIT SWS Fls p. 35.

Diagrama de estados: ciclo de vida del estado de módulo visible a través de MemIf_GetStatus. Fuentes: [SWS_MemIf_00064], SWS Fee p. 30

MemIf_GetJobResult proporciona el resultado del último trabajo [SWS_MemIf_00043] [SWS_MemIf_00065]. La lectura, la escritura y el borrado comparten un único resultado de trabajo, de modo que solo se puede consultar el del último trabajo. Con la aceptación de un nuevo trabajo, este se establece en MEMIF_JOB_PENDING SWS Fls p. 36; Fee habla del último trabajo aceptado SWS Fee p. 31. Además de OK, FAILED y CANCELED, existen dos resultados relacionados con el bloque. MEMIF_BLOCK_INCONSISTENT significa que el bloque está corrupto o no se ha encontrado; MEMIF_BLOCK_INVALID significa que está marcado como no válido [SWS_MemIf_00065].

Diagrama de estados: un trabajo aceptado se encuentra en PENDING y finaliza exactamente en uno de los resultados finales. Fuentes: [SWS_MemIf_00065], SWS Fls p. 36, SWS Fee p. 31

MemIf_SetMode es el único servicio que no tiene DeviceIndex y llama a SetMode de todos los módulos de abstracción [SWS_MemIf_00038]. Los modos son MEMIF_MODE_SLOW y MEMIF_MODE_FAST [SWS_MemIf_00066]. En los controladores, esto representa el acceso de lectura lento o el acceso SPI normal, por un lado, y el acceso de lectura rápido o la ráfaga SPI (SPI burst), por otro. Eep_SetMode no debe llamarse durante una operación en curso SWS Eep p. 34. Fls_SetMode rechaza una solicitud en estado ocupado si la comprobación está activa SWS Fls p. 42. Interpretación: dado que MemIf_SetMode llega a todos los módulos, solo debería llamarse cuando todos los dispositivos notifiquen MEMIF_IDLE.

Cancelación de trabajos en curso

MemIf_Cancel llama a la función Cancel del módulo seleccionado [SWS_MemIf_00041]. La cancelación en sí es síncrona, pero asíncrona respecto al hardware: el hardware aún puede seguir funcionando cuando la llamada ya ha retornado SWS Fee p. 45 SWS Ea p. 44. El resultado del trabajo pasa a ser MEMIF_JOB_CANCELED [SWS_MemIf_00065], lo que Fee considera expresamente como un fallo SWS Fee p. 31.

Para la ruta Flash, la especificación del controlador muestra la cadena MemIf_Cancel → Fee_Cancel → Fls_Cancel con notificaciones de error posteriores. Además, exige no invocar Fls_Cancel durante una Fls_MainFunction en curso. Para ello existen dos vías: se sincronizan las funciones de trabajo de NvM y del controlador Flash, o bien no se interrumpe la tarea de Fls_MainFunction SWS Fls p. 58.

Diagrama de secuencia: la cancelación se ejecuta de forma síncrona a través de todas las capas, sigue la notificación de error y, a continuación, GetJobResult notifica CANCELED. Fuentes: SWS Fls p. 58, SWS Fee p. 45, [SWS_MemIf_00041]

Reglas de llamada, reentrancia e integración en la BSW

A excepción de MemIf_GetVersionInfo, todos los servicios son no reentrantes [SWS_MemIf_00045] [SWS_MemIf_00040]. Por lo tanto, deben excluirse las llamadas paralelas desde múltiples contextos. Dado que el estado y el resultado del trabajo por módulo solo reflejan el último trabajo, el llamante solo debería emitir un nuevo trabajo tras finalizar el anterior SWS Fls p. 36.

El ejemplo de mapeo de memoria de un clúster ICC2 «MEM» incluye MemIf junto con NvM. Allí, MemIf_SetMode está modelado como BswCalledEntity, y MemIf tiene el prefijo de sección MEMIF SWS MemoryMapping p. 50. La BSW Distribution Guide cita MEMIF junto a FLS y FEE como ejemplo de «Type I»; el ámbito de validez puede limitarse a un núcleo mediante SwAddrMethod con alcance local EXP BSWDistributionGuide p. 31. Probablemente, en sistemas multinúcleo, MemIf deba operarse de forma local al núcleo.

Comportamiento en caso de error

MemIf contempla dos errores de desarrollo. MEMIF_E_PARAM_DEVICE (0x01) representa un DeviceIndex incorrecto, MEMIF_E_PARAM_POINTER (0x02) un puntero NULL [SWS_MemIf_00006]. Se notifican a través del módulo opcional Det_ReportError [SWS_MemIf_00048]. Según la tabla de trazabilidad, los códigos de error específicos no se devuelven a través de la API SWS MemIf p. 12.

Si la detección de errores de desarrollo está activa y se detecta un error, Read, Write, InvalidateBlock y EraseImmediateBlock devuelven E_NOT_OK [SWS_MemIf_00039] [SWS_MemIf_00040] [SWS_MemIf_00044] [SWS_MemIf_00046]. En este caso, MemIf_GetJobResult devuelve MEMIF_JOB_FAILED SWS MemIf p. 21. De lo contrario, el valor del módulo se transmite sin modificaciones.

Diagrama de actividades: comprobación de parámetros con la detección de errores de desarrollo activa y transmisión directa del resultado del módulo. Fuentes: [SWS_MemIf_00006], [SWS_MemIf_00048], SWS MemIf p. 18, SWS MemIf p. 21

Los errores de tiempo de ejecución de la memoria no los detecta MemIf, sino Fee o Ea; MemIf no reacciona a ellos («N/A»). En modo de sondeo (polling), NvM lee el error a través de MemIf_GetJobResult como MEMIF_JOB_FAILED, y la subsanación corresponde a NvM ErrorDescription p. 58 ErrorDescription p. 60. Una versión más reciente describe esta subsanación con más detalle. Según esta, NvM incrementa un contador de reintentos en los trabajos de escritura, cancela tras superarlo y notifica NVM_E_REQ_FAILED a DEM EXP ErrorDescription p. 45. Para R20-11, este detalle no está respaldado aquí de forma normativa.

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: e9d6121ccdfc Procedencia

La función MemIf_SetMode sirve para el cambio síncrono del modo de funcionamiento a través de la interfaz de memoria [SWS_MemIf_00038]. En la llamada, reenvía el modo solicitado a las funciones individuales «Set Mode» de todos los módulos de abstracción de memoria subyacentes [SWS_MemIf_00038]. Como parámetro se transfiere el modo de destino Mode, mientras que la función no proporciona ningún valor de retorno [SWS_MemIf_00038]. La interfaz está definida con el Service ID 0x01 en la cabecera MemIf.h [SWS_MemIf_00038].

En lo relativo a la concurrencia, MemIf_SetMode está especificada como no reentrante (Non Reentrant) [SWS_MemIf_00038]. Interpretación: Es de suponer que los llamadores probablemente no deben invocar la función de forma simultánea o discontinua desde varias tareas o rutinas de servicio de interrupción, motivo por el cual un acceso concurrente probablemente debería coordinarse mediante mecanismos de protección externos en caso de ser necesario.

Debido a la semántica de ejecución síncrona, la llamada no regresa al llamador hasta después de reenviar la solicitud a los módulos de abstracción de memoria [SWS_MemIf_00038]. En la especificación del elemento no se contemplan valores de retorno específicos para la indicación de errores ni mensajes de error DET o DEM independientes para esta función [SWS_MemIf_00038].

función MemIf_Read [SWS_MemIf_00039] 📄 PDF

Std_ReturnType MemIf_Read (uint8 Device Index, uint16 Block Number, uint16 Block Offset, uint8* DataBufferPtr, uint16 Length);

Invokes el "leer" función del underlying memoria abstracción módulo seleccionado por el parámetro dispositivo índice.

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 9f6882978f36 Procedencia

La función MemIf_Read reenvía una solicitud de lectura de forma síncrona al módulo de abstracción de memoria subyacente seleccionado a través del parámetro DeviceIndex [SWS_MemIf_00039]. Está declarada en la cabecera MemIf.h y sirve para leer datos de un bloque de memoria lógico.

Parámetros e interfaz

La llamada a MemIf_Read incluye los siguientes parámetros de entrada y salida [SWS_MemIf_00039]:

  • DeviceIndex: Índice del dispositivo de destino para seleccionar el módulo de destino.
  • BlockNumber: Número de bloque lógico del bloque de memoria que se va a leer.
  • BlockOffset: Desplazamiento en bytes (byte offset) dentro del bloque lógico a partir del cual se lee.
  • DataBufferPtr: Puntero al búfer para almacenar los datos leídos.
  • Length: Número de bytes de datos que se van a leer.

Tratamiento de errores y valores de retorno

Si la detección de errores de desarrollo (Development Error Detection) está activa y se detecta un error de desarrollo, la función devuelve E_NOT_OK [SWS_MemIf_00039]. De lo contrario, el valor de retorno de la función de lectura invocada del módulo subyacente se reenvía como Std_ReturnType [SWS_MemIf_00039].

Concurrencia y restricciones

La función está especificada como síncrona y no reentrante (Non Reentrant) [SWS_MemIf_00039]. Por tanto, una llamada debería producirse típicamente en contexto de tarea; el llamante debe evitar o serializar las llamadas paralelas o anidadas.

GENERADO POR IA no revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 88682d2af3e3 Procedencia

Uso y contexto de llamada

La función de interfaz MemIf_Write sirve como capa de abstracción y llama a la función Write del módulo de abstracción de memoria subyacente que se selecciona mediante el parámetro DeviceIndex [SWS_MemIf_00040]. En la llamada síncrona se pasan tres parámetros de entrada: el índice de dispositivo DeviceIndex para seleccionar el controlador de destino, el número de bloque lógico BlockNumber así como el puntero DataBufferPtr al búfer con los datos que se van a escribir [SWS_MemIf_00040]. La función está especificada bajo el Service ID 0x03 y disponible a través del archivo de cabecera MemIf.h [SWS_MemIf_00040].

Tratamiento de errores y valores de retorno

El valor de retorno es de tipo Std_ReturnType [SWS_MemIf_00040]. Si la detección de errores de desarrollo (Development Error Detection) para la Memory Abstraction Interface está activa y se detecta un error de desarrollo según [SWS_MemIf_00022], MemIf_Write devuelve el código de error E_NOT_OK [SWS_MemIf_00040].
