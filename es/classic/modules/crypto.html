Ofrece primitivas criptográficas y gestión de claves para la pila criptográfica de AUTOSAR Classic cercana al hardware.

Como módulo MCAL, el Crypto Driver proporciona cálculos criptográficos cercanos al hardware, así como la gestión de claves para la pila criptográfica de AUTOSAR Classic (EXP_UtilizationOfCryptoServices p. 8). Encapsula módulos de seguridad de hardware (HSM) o bibliotecas de software en Driver Objects y procesa trabajos tanto síncronos como asíncronos a través de la interfaz central Crypto_ProcessJob ([SWS_Crypto_91003]). Los accesos a claves están sujetos a derechos configurables, y el almacenamiento permanente en NVM solo se desencadena tras una validación correcta de la clave (SWS_CryptoDriver p. 37).

El Crypto Driver (módulo Crypto) constituye, como controlador MCAL, el fundamento inferior de la pila criptográfica de AUTOSAR Classic y conecta módulos de seguridad de hardware (HSM), aceleradores criptográficos y rutinas de software directamente a la interfaz de criptografía (CryIf) (EXP_UtilizationOfCryptoServices p. 8, SWS_CryptoDriver p. 15). En implementaciones múltiples, las instancias se denominan de manera específica del fabricante siguiendo el esquema Crypto_<vi>_<ai> ([SWS_Crypto_00012]). La inicialización se realiza de forma síncrona mediante [SWS_Crypto_91000] con un puntero nulo obligatorio para [SWS_Crypto_91016] ([SWS_Crypto_00215]). Internamente, el módulo encapsula unidades de cálculo independientes en Crypto Driver Objects, de los cuales cada uno puede ejecutar exactamente un trabajo al mismo tiempo ([SWS_Crypto_00014]), mientras que n objetos permiten cálculos paralelos ([SWS_Crypto_00117]). En este marco, el Driver Object 0 actúa como generador aleatorio central para necesidades internas de todos los demás objetos de controlador de la misma instancia ([SWS_Crypto_00224], [SWS_Crypto_00225]).

Diagrama de contexto: integración del Crypto Driver en la pila criptográfica de AUTOSAR con Driver Objects e interfaces hacia NvM y DET. Fuentes: SWS_CryptoDriver p. 15, SWS_Crypto_00012, SWS_Crypto_91017

Los trabajos criptográficos se procesan mediante [SWS_Crypto_91003] (Crypto_ProcessJob), unificando el streaming y las llamadas globales a través de un campo de bits de modo (START, UPDATE, FINISH) (SWS_CryptoDriver p. 25, [SWS_Crypto_00017]). Los trabajos asíncronos se calculan a través de la función periódica [SWS_Crypto_91012] (Crypto_MainFunction) y, tras su finalización, se notifican a CryIf mediante CRYIF_CallbackNotification ([SWS_Crypto_00027], [SWS_Crypto_00028]). Los trabajos en ejecución se pueden cancelar de forma síncrona mediante [SWS_Crypto_00122] ([SWS_Crypto_00183], [SWS_Crypto_00214]), mientras que las redirecciones directas de búfer hacia elementos de clave reducen las operaciones de copia ([SWS_Crypto_00203], [SWS_Crypto_00221]).

Diagrama de secuencia: flujo de procesamiento asíncrono a través de Crypto_ProcessJob, ciclo en Crypto_MainFunction y notificación mediante CRYIF_CallbackNotification. Fuentes: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

La gestión de claves comprende el establecimiento ([SWS_Crypto_91004]), la lectura ([SWS_Crypto_91006]), el copiado ([SWS_Crypto_00155], [SWS_Crypto_91015]), la generación ([SWS_Crypto_91007]) y la derivación ([SWS_Crypto_91008]) de elementos de clave bajo un estricto control de derechos de acceso ([SWS_Crypto_00219], [SWS_Crypto_00220]). Por razones de coherencia, la persistencia en el Non-Volatile RAM Manager (NvM) nunca se desencadena con escrituras individuales, sino exclusivamente durante la validación de claves mediante [SWS_Crypto_91014] (Crypto_KeySetValid) (SWS_CryptoDriver p. 37, [SWS_Crypto_91025]). En entornos multinúcleo, el módulo actúa de forma aislada en cada partición ([SWS_Crypto_CONSTR_00001]), no pudiendo asignarse los objetos HSM a más de una partición ([SWS_Crypto_CONSTR_00003]).

Rol y límites del sistema del Crypto Driver en la pila criptográfica Classic

El Crypto Driver (abreviatura de módulo Crypto) se sitúa en la capa inferior del software básico de AUTOSAR Classic, dentro de la Microcontroller Abstraction Layer (MCAL) (EXP_UtilizationOfCryptoServices p. 8). Se ubica directamente por debajo de la interfaz criptográfica (Crypto Interface, CryIf) y, a través de esta, da servicio al Crypto Service Manager (CSM) (SWS_CryptoDriver p. 15). Su tarea principal consiste en encapsular las unidades de cálculo criptográfico concretas —ya sean módulos de seguridad basados en hardware (Hardware Security Modules, HSM), aceleradores criptográficos dedicados como motores AES o bibliotecas puramente de software (SWS_CryptoDriver p. 15). Además del cálculo propiamente dicho de primitivas criptográficas, su alcance funcional abarca el almacenamiento, la configuración y la gestión de claves criptográficas (SWS_CryptoDriver p. 24).

En una unidad de control pueden coexistir en paralelo varias instancias de controladores de diferentes fabricantes; en este caso, los identificadores de archivo, API y configuración se diferencian de manera inequívoca mediante un infijo específico del fabricante según el esquema Crypto_<vi>_<ai> ([SWS_Crypto_00012]). La inicialización del módulo se efectúa mediante la función [SWS_Crypto_91000] (Crypto_Init). Como particularidad, para el puntero de configuración del tipo [SWS_Crypto_91016] (Crypto_ConfigType) se aplica que este debe pasarse siempre como un puntero nulo ([SWS_Crypto_00215]). La información de versión puede consultarse de forma síncrona mediante [SWS_Crypto_91001] (Crypto_GetVersionInfo), notificándose al DET el paso de un puntero nulo con el error CRYPTO_E_PARAM_POINTER si la detección de desarrollo está activa (SWS_CryptoDriver p. 56).

Gestión de Crypto Driver Objects y abstracción de hardware

Cada instancia del Crypto Driver se subdivide internamente en uno o varios objetos de controlador lógicos (Crypto Driver Objects) (SWS_CryptoDriver p. 15). Un Crypto Driver Object constituye el extremo funcional de un canal criptográfico y representa una unidad de cómputo de hardware independiente o una implementación de software (SWS_CryptoDriver p. 15). Por principio, un Driver Object individual solo puede ejecutar activamente exactamente un trabajo (job) en un momento dado ([SWS_Crypto_00014]). Por consiguiente, un Crypto Driver con n Driver Objects posee la capacidad de calcular en paralelo n trabajos criptográficos ([SWS_Crypto_00117]). Las primitivas matemáticas y de seguridad compatibles quedan determinadas por la capacidad del objeto asignado ([SWS_Crypto_00013]).

Si un objeto de controlador requiere números aleatorios internos (por ejemplo, para el cálculo de valores públicos en el marco del intercambio de claves mediante [SWS_Crypto_91009]) y no dispone de un generador aleatorio propio, recurre obligatoriamente al Crypto Driver Object 0 del mismo controlador ([SWS_Crypto_00224], [SWS_Crypto_00225]). En ningún caso se permite que los objetos de controlador direccionen generadores aleatorios de instancias de controladores criptográficos externas ([SWS_Crypto_00226]). Interpretación: el Driver Object 0 actúa, por tanto, como generador aleatorio de referencia interno central para todos los demás objetos de controlador de la misma partición.

Procesamiento de trabajos entre llamada directa síncrona y streaming asíncrono

Los procesamientos criptográficos se transfieren al módulo como estructuras de trabajo del tipo Crypto_JobType a través de la interfaz central [SWS_Crypto_91003] (Crypto_ProcessJob) ([SWS_Crypto_00042], AUTOSAR_CP_SWS_CryptoServiceManager p. 21). La interfaz unifica las llamadas globales basadas en bloques y el streaming continuo de datos a través de un campo de bits específico del modo: las operaciones START, UPDATE y FINISH se pueden transferir individualmente o de forma combinada (SWS_CryptoDriver p. 25). El establecimiento del indicador START marca un nuevo trabajo y cancela todas las instancias previas del mismo trabajo ([SWS_Crypto_00017]). En transferencias combinadas, los pasos se ejecutan siempre en el orden fijo START, UPDATE y, por último, FINISH (SWS_CryptoDriver p. 25).

El hecho de que un trabajo se procese de manera síncrona o asíncrona forma parte de la configuración de metadatos en Crypto_JobType (SWS_CryptoDriver p. 26). En modo asíncrono, [SWS_Crypto_91003] se limita a recibir los datos del trabajo; la ejecución real se inicia o procesa mediante la función principal periódica [SWS_Crypto_91012] (Crypto_MainFunction) ([SWS_Crypto_00027], [SWS_Crypto_91012]). Tras completarse el cálculo asíncrono, el Crypto Driver notifica de forma vinculante a la capa superior CryIf mediante la llamada a la función de retrollamada CRYIF_CallbackNotification, devolviendo el estado y los punteros de resultado ([SWS_Crypto_00028]). Interpretación: las llamadas síncronas, por el contrario, ejecutan la operación criptográfica de forma bloqueante en el contexto del llamador, sin desacoplarse a través de la función principal.

Diagrama de secuencia: flujo de procesamiento asíncrono a través de Crypto_ProcessJob, ciclo en Crypto_MainFunction y notificación mediante CRYIF_CallbackNotification. Fuentes: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

Los trabajos criptográficos en curso o pendientes pueden cancelarse mediante la función [SWS_Crypto_00122] (Crypto_CancelJob). Si el trabajo solicitado no se encuentra en procesamiento activo por parte del objeto de controlador, se elimina de inmediato y la invocación devuelve E_OK ([SWS_Crypto_00214]). No obstante, si el hardware no puede interrumpir inmediatamente el proceso de cálculo activo, la API responde al intento con CRYPTO_E_JOB_CANCELED y la cancelación se completará en el siguiente paso alcanzable ([SWS_Crypto_00183]).

Diagrama de secuencia: cancelación síncrona de trabajos criptográficos a través de Crypto_CancelJob con distinción de casos durante la ejecución activa en hardware. Fuentes: SWS_Crypto_00122, SWS_Crypto_00183, SWS_Crypto_00214

Para evitar operaciones de copia innecesarias entre las memorias de aplicación y de hardware, el Crypto Driver admite la redirección directa de búferes (Job Redirection): los datos de entrada y salida pueden referenciarse directamente a elementos de clave internos mediante jobRedirectionInfoRef ([SWS_Crypto_00203], [SWS_Crypto_00204]). Para evitar fugas de datos, se aplican aquí estrictas comprobaciones de derechos: en las redirecciones de entrada para servicios de cifrado y descifrado, el elemento de clave debe presentar al menos el derecho CRYPTO_RA_ENCRYPTED; para redirecciones de solo lectura, se requiere al menos CRYPTO_RA_INTERNAL_COPY ([SWS_Crypto_00221]).

Gestión de claves, derechos de acceso y operaciones criptográficas con claves

En el Crypto Driver, una clave lógica (Key) consta de uno o varios elementos de clave (Key Elements) que alojan el material de clave propiamente dicho, vectores de inicialización (IV), semillas aleatorias o pruebas SHE (Proof) (SWS_CryptoDriver p. 28). El acceso a cada elemento individual está estrictamente reglamentado: los accesos de lectura y escritura se supervisan mediante jerarquías de derechos configuradas (p. ej., CRYPTO_RA_ALLOWED, CRYPTO_RA_ENCRYPTED, CRYPTO_RA_INTERNAL_COPY), donde un valor de enumeración menor representa un derecho de acceso superior (SWS_CryptoDriver p. 28, [SWS_Crypto_00219]). Las operaciones de lectura directa solo están permitidas con CRYPTO_RA_ALLOWED o CRYPTO_RA_ENCRYPTED ([SWS_Crypto_00222]); los accesos de escritura requieren al menos CRYPTO_WA_ALLOWED o CRYPTO_WA_ENCRYPTED ([SWS_Crypto_00223]). Al copiar, el elemento de origen debe poseer al menos CRYPTO_RA_INTERNAL_COPY y no debe presentar derechos inferiores a los del elemento de destino ([SWS_Crypto_00220]).

Para la manipulación directa de claves y sus elementos, el Crypto Driver proporciona una serie de API síncronas: el establecimiento y la lectura de datos se realizan a través de [SWS_Crypto_91004] (Crypto_KeyElementSet) o [SWS_Crypto_91006] (Crypto_KeyElementGet). Los identificadores de elementos existentes de una clave pueden determinarse a través de [SWS_Crypto_00160] (Crypto_KeyElementIdsGet). Las claves completas o los elementos individuales se duplican mediante [SWS_Crypto_00155] (Crypto_KeyCopy) o [SWS_Crypto_00148] (Crypto_KeyElementCopy). Para copias parciales existe [SWS_Crypto_91015] (Crypto_KeyElementCopyPartial), que impone comprobaciones precisas de longitud y desplazamiento en los búferes de origen y destino ([SWS_Crypto_00207], [SWS_Crypto_00208], [SWS_Crypto_00209]) y ajusta dinámicamente la longitud de destino ([SWS_Crypto_00210], [SWS_Crypto_00211]).

Además, el módulo admite operaciones de clave complejas: la generación de claves se realiza mediante [SWS_Crypto_91007] (Crypto_KeyGenerate) sobre la base de datos de entropía previamente inicializados mediante [SWS_Crypto_91013] (Crypto_RandomSeed). De la derivación de nuevo material de claves se encarga [SWS_Crypto_91008] (Crypto_KeyDerive). Para protocolos de intercambio de claves Diffie-Hellman están disponibles las funciones [SWS_Crypto_91009] (Crypto_KeyExchangeCalcPubVal) para generar el valor público, así como [SWS_Crypto_91010] (Crypto_KeyExchangeCalcSecret) para determinar el secreto compartido (SWS_CryptoServiceManager p. 70).

Cada clave lógica mantiene un estado que puede consultarse mediante [SWS_Crypto_91019] (Crypto_KeyGetStatus). Las claves recién escritas se encuentran inicialmente en el estado invalid y solo se liberan como valid tras una validación exitosa mediante [SWS_Crypto_91014] (Crypto_KeySetValid), mientras que [SWS_Crypto_91020] (Crypto_KeySetInvalid) bloquea la clave explícitamente. En cuanto a los formatos de datos, el controlador procesa claves asimétricas según RFC 5958 en codificación ASN.1-PKCS#8 ([SWS_Crypto_00184]), estructuras de clave RSA según RFC 8017 con OID de algoritmo fijo 1.2.840.113549.1.1.1 ([SWS_Crypto_00185], [SWS_Crypto_00186], [SWS_Crypto_00187], [SWS_Crypto_00188]), así como datos de curvas ECC (NIST, Brainpool, ED25519) en coordenadas de punto little-endian ([SWS_Crypto_00189], [SWS_Crypto_00190], [SWS_Crypto_00191], [SWS_Crypto_00192], [SWS_Crypto_00193]). Las claves SHE cercanas al hardware se transfieren en formato M1M2M3; su comprobante de verificación M4M5 puede leerse temporalmente en el elemento de clave 2 inmediatamente después de la validación ([SWS_Crypto_00255]).

Persistencia de elementos de clave mediante el Non-Volatile RAM Manager

Si las claves deben conservarse de forma no volátil a lo largo de ciclos de alimentación, el Crypto Driver se conecta al Non-Volatile RAM Manager (NvM) (SWS_CryptoDriver p. 35, AUTOSAR_CP_SWS_CryptoDriver p. 37). Un principio arquitectónico central establece que las operaciones de escritura en el NvM nunca se desencadenan directamente al llenar un elemento individual mediante Crypto_KeyElementSet (SWS_CryptoDriver p. 37). En su lugar, la persistencia se inicia exclusivamente mediante la validación de estado KEYSETVALID a través de [SWS_Crypto_91014] (Crypto_KeySetValid) o un trabajo criptográfico equivalente (SWS_CryptoDriver p. 37). Esto garantiza que los elementos de clave interdependientes se comprueben de forma coherente y se almacenen en un único acceso de escritura al NvM, lo que preserva los ciclos de flash (SWS_CryptoDriver p. 37).

La interacción con el NvM se realiza a través de interfaces de retrollamada dedicadas: durante el arranque de la ECU, el NvM proporciona el bloque de inicialización a través de [SWS_Crypto_91023] (Crypto_<vi>_<ai>_NvBlock_Init_<NvBlock>). La carga de datos persistidos desde el espejo de RAM del NvM se efectúa mediante [SWS_Crypto_91024] (Crypto_<vi>_<ai>_NvBlock_ReadFrom_<NvBlock>). Antes de escribir, el NvM invoca [SWS_Crypto_91025] (Crypto_<vi>_<ai>_NvBlock_WriteTo_<NvBlock>) para que el controlador criptográfico copie sus datos de clave internos en el búfer de NvM; la finalización de la transferencia asíncrona de bloques se notifica mediante [SWS_Crypto_91026] (Crypto_<vi>_<ai>_NvBlock_Callback_<NvBlock>). Para el control, el controlador utiliza los servicios de NvM NvM_SetRamBlockStatus y NvM_WriteBlock ([SWS_Crypto_91017]). Si la carga de una clave persistente falla durante el arranque, el controlador marca esta clave de forma vinculante como invalid ([SWS_Crypto_00198]).

Particionamiento y reglas operativas multinúcleo

Para distribuir de forma eficiente las operaciones criptográficas en sistemas multinúcleo, la pila criptográfica puede dividirse en varias particiones de software (BSWDistributionGuide p. 59). El módulo Crypto opera en cada partición como una instancia completamente independiente: cada llamada a la API procesa datos exclusivamente dentro de la partición en la que se emitió ([SWS_Crypto_CONSTR_00001]). El particionamiento de los objetos de controlador está sujeto a reglas fijas de configuración: las particiones referenciadas por CryptoDriverObjectEcucPartitionRef deben formar obligatoriamente un subconjunto propio de las particiones asignadas al módulo (CryptoEcucPartitionRef) ([SWS_Crypto_CONSTR_00002]). Si un Crypto Driver Object está acoplado a un módulo de seguridad de hardware (HSM), por motivos de aislamiento de hardware solo puede asignarse exactamente a 0 o 1 partición ([SWS_Crypto_CONSTR_00003]).

Comportamiento en caso de error

El Crypto Driver implementa una supervisión de errores de dos niveles compuesta por detección durante el desarrollo (Development Errors) y errores de tiempo de ejecución (Runtime Errors). Con el modo de seguridad de desarrollo (DET) activado, las violaciones formales de interfaz se transmiten a Det_ReportError ([SWS_Crypto_91017]). Entre estas se incluyen llamadas antes de la inicialización del controlador (CRYPTO_E_UNINIT, 0x00) ([SWS_Crypto_00040], [SWS_Crypto_00196], [SWS_Crypto_00205]), datos de inicialización no válidos (CRYPTO_E_INIT_FAILED, 0x01), así como punteros nulos no permitidos (CRYPTO_E_PARAM_POINTER, 0x02) ([SWS_Crypto_00040]). Si los identificadores de clave o los identificadores de clave de destino se encuentran fuera del rango de valores permitido, el controlador cancela la llamada con E_NOT_OK y notifica CRYPTO_E_PARAM_HANDLE (0x04) ([SWS_Crypto_00040], [SWS_Crypto_00180], [SWS_Crypto_00197], [SWS_Crypto_00202], [SWS_Crypto_00217]).

Si los búferes de entrada o salida proporcionados para una operación no son suficientes, se rechaza la ejecución y, con el DET activo, se notifica el error CRYPTO_E_SMALL_BUFFER ([SWS_Crypto_00195], SWS_CryptoDriver p. 49). Se aplica una excepción normativa para los servicios CRYPTO_HASH y CRYPTO_MACGENERATE: si el búfer de salida es menor que la longitud nativa de hash o MAC, el resultado no se descarta, sino que se escribe en el búfer truncado en forma de los bits más significativos (MSB) ([SWS_Crypto_00065]). En el funcionamiento operativo, el controlador notifica errores de tiempo de ejecución específicos a través del valor de retorno: [SWS_Crypto_91003] responde al agotamiento de la entropía aleatoria con el código de retorno CRYPTO_E_ENTROPY_EXHAUSTED y notifica el error de tiempo de ejecución CRYPTO_E_RE_ENTROPY_EXHAUSTED (0x03) ([SWS_Crypto_00141], [SWS_Crypto_00194], [SWS_Crypto_91018]). Si fallan los accesos de lectura o escritura a la NVM, se señaliza CRYPTO_E_RE_NVM_ACCESS_FAILED (0x04) ([SWS_Crypto_00194]). Otros valores de retorno de API estandarizados son CRYPTO_E_BUSY, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, CRYPTO_E_KEY_NOT_VALID, CRYPTO_E_KEY_SIZE_MISMATCH y CRYPTO_E_KEY_EMPTY ([SWS_Crypto_00155], [SWS_Crypto_00207], [SWS_Crypto_91018]).
