Función de Platform_Types.h: base común de tipos del software base Classic

El módulo «platform» consta del archivo de encabezado Platform_Types.h. A través de él están disponibles todos los tipos básicos estandarizados y los símbolos de plataforma, tales como uint8 [SWS_Platform_00013], boolean [SWS_Platform_00026] y CPU_TYPE [SWS_Platform_00064]. El módulo no contiene funciones. Determina qué rangos de valores, anchos de bits y codificaciones puede asumir el código en una plataforma. El motivo es el requisito de que todos los módulos de software base utilicen únicamente tipos de datos AUTOSAR. Los tipos nativos de C como char, int o long están prohibidos porque su tamaño, su signo y su precisión dependen de la plataforma (RS_BSWGeneral p. 65).

Por lo general, los módulos no incluyen los tipos directamente. En el ejemplo de la especificación de requisitos, Eep.h incluye el archivo Std_Types.h, y este a su vez incluye automáticamente Platform_Types.h (RS_BSWGeneral p. 65). Bibliotecas como Bfx derivan expresamente sus abreviaturas u8, u16, s32 y boolean a partir de los tipos de plataforma (SWS_BFXLibrary p. 8). El propio archivo no debe modificarse: cualquier extensión anula la conformidad con AUTOSAR [SWS_Platform_00002].

Diagrama de contexto: Platform_Types.h es la base común de tipos. Los módulos BSW acceden a ella a través de Std_Types.h; las bibliotecas, las interfaces de servicio y los blueprints de modelos hacen referencia directa a ella. Fuentes: RS_BSWGeneral p. 65, SWS_BFXLibrary p. 8, StandardizationTemplate p. 77, [SWS_Platform_00002]

Tipos enteros: ancho exacto o rango mínimo optimizado para la plataforma

Los tipos enteros estándar tienen anchos de bits y rangos de valores fijos. uint8, uint16, uint32 y uint64 son sin signo con 8, 16, 32 y 64 bits ([SWS_Platform_00013], [SWS_Platform_00014], [SWS_Platform_00015], [SWS_Platform_00066]). De sint8 a sint64 son las contrapartes con signo ([SWS_Platform_00016], [SWS_Platform_00017], [SWS_Platform_00018], [SWS_Platform_00067]). Sus rangos, como -128..+127 para sint8, se derivan de que AUTOSAR solo admite aritmética de complemento a dos para el compilador y el sistema de destino [SWS_Platform_00061].

Los tipos optimizados, en cambio, solo garantizan un rango mínimo. uint8_least, uint16_least y uint32_least tienen al menos 8, 16 y 32 bits respectivamente y derivan de uint ([SWS_Platform_00020], [SWS_Platform_00021], [SWS_Platform_00022]). De sint8_least a sint32_least son las variantes con signo y derivan de sint ([SWS_Platform_00023], [SWS_Platform_00024], [SWS_Platform_00025]). La especificación menciona dos casos de uso típicos: contadores de bucle con un máximo de 124 iteraciones y argumentos de switch con 17 estados. En ambos casos se debe elegir uint8_least (SWS_PlatformTypes p. 17).

En el payload figuran declaraciones como typedef unsigned int uint8_least; o typedef unsigned long uint32;. Interpretación: se trata de asignaciones para un compilador determinado. Solo el ancho o ancho mínimo requerido es normativo ([SWS_Platform_00015], [SWS_Platform_00020]).

Tipos de coma flotante y de puntero para valores y búferes de datos

Para los valores de coma flotante se aplican los formatos según IEEE 754-2008:

  • float32 sigue el formato binary32, rango ±3.4028235e+38 [SWS_Platform_00041].
  • float64 sigue el formato binary64, rango ±1.7976931348623157e+308 [SWS_Platform_00042].

Para búferes de datos sin tipo fijo existen dos tipos de puntero con dirección definida:

  • VoidPtr (void*) está concebido para búferes que devuelven datos al llamador [SWS_Platform_91001] (SWS_PlatformTypes p. 27).
  • ConstVoidPtr (const void*) está concebido para búferes que se pasan al llamado [SWS_Platform_91002] (SWS_PlatformTypes p. 28).

Diagrama de actividades: así se selecciona el tipo de plataforma adecuado, desde boolean pasando por punteros a búfer y coma flotante hasta enteros optimizados o de ancho exacto. Fuentes: [SWS_Platform_00026], [SWS_Platform_91001], [SWS_Platform_91002], [SWS_Platform_00041], [SWS_Platform_00042], SWS_PlatformTypes p. 17

boolean, TRUE y FALSE: representación y expresiones permitidas

En R20-11, boolean se implementa como un tipo entero sin signo, concretamente con la longitud de bits más corta que la plataforma admita de forma nativa, por lo general 8 bits [SWS_Platform_00027]. La declaración almacenada es typedef unsigned char boolean; [SWS_Platform_00026].

Divergencia en versiones posteriores: la versión para R24-11/R25-11 exige el tipo C99 _Bool y ya no fija el tamaño del objeto (SWS_PlatformTypes p. 18). Para R20-11 se aplica el requisito anterior.

Además, boolean debe asignarse a un tipo al que puedan apuntar punteros. Por ello quedan excluidos los tipos de bits eficientes de determinado hardware [SWS_Platform_00060]. Este es un requisito previo para interfaces como CanNm_CheckRemoteSleepIndication, que devuelven un resultado a través de boolean* (SWS_CANNetworkManagement p. 68).

TRUE (1) y FALSE (0) solo se definen si aún no existen (#ifndef TRUE) [SWS_Platform_00056]. Solo se permite utilizarlos junto con boolean [SWS_Platform_00055]. Para el manejo de variables boolean se aplican estas reglas [SWS_Platform_00034]:

  • Las asignaciones solo están permitidas con TRUE, FALSE, comparaciones o expresiones lógicas (&&, ||, !).
  • Los operadores aritméticos y bit a bit como +, ++, <<, ~ o & están prohibidos.
  • Las comparaciones están limitadas a == TRUE, == FALSE, != TRUE, != FALSE, if (var) y if (!var) (SWS_PlatformTypes p. 18).

Diagrama de actividades: comprobación de si es admisible una asignación o una comparación con una variable boolean. Fuentes: [SWS_Platform_00034], [SWS_Platform_00055], SWS_PlatformTypes p. 18

Símbolos de plataforma CPU_TYPE, CPU_BIT_ORDER y CPU_BYTE_ORDER

Platform_Types.h indica para cada plataforma tres propiedades de la CPU, cada una como #define:

  • El ancho de registro mediante CPU_TYPE [SWS_Platform_00044]. Se admiten CPU_TYPE_8, CPU_TYPE_16, CPU_TYPE_32 y CPU_TYPE_64 ([SWS_Platform_00045], [SWS_Platform_00064]).
  • El orden de bits a nivel de registro mediante CPU_BIT_ORDER ([SWS_Platform_00043], [SWS_Platform_00038]).
  • El orden de bytes en memoria mediante CPU_BYTE_ORDER ([SWS_Platform_00046], [SWS_Platform_00039]).

La asignación a la endianness es unívoca. El orden de bits big-endian da como resultado MSB_FIRST, y el orden de bits little-endian da como resultado LSB_FIRST ([SWS_Platform_00048], [SWS_Platform_00049]). El orden de bytes big-endian da como resultado HIGH_BYTE_FIRST, y el orden de bytes little-endian da como resultado LOW_BYTE_FIRST ([SWS_Platform_00050], [SWS_Platform_00051]).

La especificación advierte de no mezclar la numeración de bits con la significancia. En arquitecturas Motorola con orden de bits big-endian, Bit0 designa el bit más significativo; en todas las demás, el menos significativo. En el acumulador, en cambio, el MSB siempre está situado en el extremo izquierdo (SWS_PlatformTypes p. 15).

Diagrama de actividades: flujo para determinar los tres símbolos de plataforma para una plataforma de destino sin ampliar el archivo. Fuentes: [SWS_Platform_00045], [SWS_Platform_00048], [SWS_Platform_00049], [SWS_Platform_00050], [SWS_Platform_00051], [SWS_Platform_00002]

En relación con el orden de bytes, la especificación muestra un valor de 16 bits. Su byte más significativo se denomina Byte1, y el menos significativo, Byte0. En HIGH_BYTE_FIRST, Byte1 se ubica en la dirección n y Byte0 en n+1; en LOW_BYTE_FIRST es a la inversa (SWS_PlatformTypes p. 16). Esta denominación no es unívoca y puede diferir en la documentación de los fabricantes (SWS_PlatformTypes p. 16). El orden de bytes reviste importancia práctica allí donde los datos se convierten entre la representación del bus y la del procesador. Por ejemplo, AUTOSAR COM debe admitir la conversión de endianness para uint16 a float64 (evidencia de R25-11: RS_COM p. 14).

Diagrama de actividades: almacenamiento en memoria de un valor uint16 según CPU_BYTE_ORDER, basado en Figure 7.2/7.3 de la especificación. Fuentes: SWS_PlatformTypes p. 16, [SWS_Platform_00039]

Tipos de plataforma en interfaces de servicio y modelos

Otras especificaciones basan sus firmas en estos tipos. Dos ejemplos de R24-11/R25-11 muestran la regla de dirección de los punteros a búfer ([SWS_Platform_91001], [SWS_Platform_91002]):

  • El Key Manager transfiere en KeyM_ServiceCertificateByCertId los datos de solicitud como ConstVoidPtr con una longitud del tipo uint32. Recibe los resultados a través de un búfer VoidPtr, cuyo tamaño disponible es indicado por ResponseDataLength (INOUT) (SWS_KeyManager p. 111).
  • La operación CSM RandomSeed pasa el seed como ConstVoidPtr (SWS_CryptoServiceManager p. 124).

Diagrama de secuencia: el llamador proporciona datos de solicitud de solo lectura a través de ConstVoidPtr y recibe datos de vuelta a través de un búfer VoidPtr. El valor de retorno informa si el servicio ha aceptado la solicitud. Fuentes: SWS_KeyManager p. 111, SWS_KeyManager p. 97, [SWS_Platform_91001], [SWS_Platform_91002]

Los tipos también están firmemente arraigados en el modelo. A partir del blueprint /AUTOSAR/Platform/ImplementationDatatypes_Blueprint/uint8 se deriva el elemento /AUTOSAR_Platform/ImplementationDatatypes/uint8. De este modo, los proveedores de software lo encuentran a través de una ruta predecible (StandardizationTemplate p. 77). Los Record Layouts hacen referencia a tipos base como /AUTOSAR/Platform/BaseTypes_Blueprint/sint16 (GeneralBlueprintsSupplement p. 47). Bibliotecas como Crc utilizan uint8, uint32 y boolean directamente en sus API (SWS_CRCLibrary p. 41).

Comportamiento en caso de error

Platform_Types.h solo proporciona tipos y símbolos disponibles a través de este archivo ([SWS_Platform_00013], [SWS_Platform_00038]). Por tanto, no debería existir un comportamiento de error en tiempo de ejecución con valores de retorno o mensajes de error. En su lugar, los errores surgen durante la integración y el uso:

  • Archivo ampliado o complementado: cualquier ampliación anula la conformidad con AUTOSAR [SWS_Platform_00002].
  • Definiciones duplicadas: si el compilador ya incluye los símbolos, deben evitarse redefiniciones mediante una comprobación condicional ([SWS_Platform_00054], [SWS_Platform_00056]).
  • Símbolos de plataforma incorrectos: un CPU_BYTE_ORDER o CPU_BIT_ORDER que no coincida con el hardware infringe de [SWS_Platform_00048] a [SWS_Platform_00051]. Interpretación: el código que bifurque en función de estos símbolos compondría incorrectamente los valores multibyte (cf. SWS_PlatformTypes p. 16).
  • Tipo de bit para boolean: sin capacidad de puntero, no se pueden pasar parámetros mediante punteros [SWS_Platform_00060].
  • Las expresiones no permitidas como var++ o var = a & b infringen [SWS_Platform_00034].
  • AUTOSAR no admite representaciones de números negativos distintas del complemento a dos [SWS_Platform_00061].

<h4>Función de Platform_Types.h: base común de tipos del software base Classic</h4>
<p>El módulo «platform» consta del archivo de encabezado <code>Platform_Types.h</code>. A través de él están disponibles todos los tipos básicos estandarizados y los símbolos de plataforma, tales como <code>uint8</code> <a class="spec-record-ref" data-req="SWS_Platform_00013" href="../../spec/record.html?id=SWS_Platform_00013">[SWS_Platform_00013]</a>, <code>boolean</code> <a class="spec-record-ref" data-req="SWS_Platform_00026" href="../../spec/record.html?id=SWS_Platform_00026">[SWS_Platform_00026]</a> y <code>CPU_TYPE</code> <a class="spec-record-ref" data-req="SWS_Platform_00064" href="../../spec/record.html?id=SWS_Platform_00064">[SWS_Platform_00064]</a>. El módulo no contiene funciones. Determina qué rangos de valores, anchos de bits y codificaciones puede asumir el código en una plataforma. El motivo es el requisito de que todos los módulos de software base utilicen únicamente tipos de datos AUTOSAR. Los tipos nativos de C como <code>char</code>, <code>int</code> o <code>long</code> están prohibidos porque su tamaño, su signo y su precisión dependen de la plataforma (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_4_3_3_Software_Module_Design_Requirements.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_4_3_3_Software_Module_Design_Requirements">RS_BSWGeneral p. 65</a>).</p>
<p>Por lo general, los módulos no incluyen los tipos directamente. En el ejemplo de la especificación de requisitos, <code>Eep.h</code> incluye el archivo <code>Std_Types.h</code>, y este a su vez incluye automáticamente <code>Platform_Types.h</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_4_3_3_Software_Module_Design_Requirements.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_4_3_3_Software_Module_Design_Requirements">RS_BSWGeneral p. 65</a>). Bibliotecas como Bfx derivan expresamente sus abreviaturas <code>u8</code>, <code>u16</code>, <code>s32</code> y <code>boolean</code> a partir de los tipos de plataforma (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_2_Acronyms_and_Abbreviations_BFXLIBRARY.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_2_Acronyms_and_Abbreviations_BFXLIBRARY">SWS_BFXLibrary p. 8</a>). El propio archivo no debe modificarse: cualquier extensión anula la conformidad con AUTOSAR <a class="spec-record-ref" data-req="SWS_Platform_00002" href="../../spec/record.html?id=SWS_Platform_00002">[SWS_Platform_00002]</a>.</p>

<h4>Tipos enteros: ancho exacto o rango mínimo optimizado para la plataforma</h4>
<p>Los tipos enteros estándar tienen anchos de bits y rangos de valores fijos. <code>uint8</code>, <code>uint16</code>, <code>uint32</code> y <code>uint64</code> son sin signo con 8, 16, 32 y 64 bits (<a class="spec-record-ref" data-req="SWS_Platform_00013" href="../../spec/record.html?id=SWS_Platform_00013">[SWS_Platform_00013]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00014" href="../../spec/record.html?id=SWS_Platform_00014">[SWS_Platform_00014]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00015" href="../../spec/record.html?id=SWS_Platform_00015">[SWS_Platform_00015]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00066" href="../../spec/record.html?id=SWS_Platform_00066">[SWS_Platform_00066]</a>). De <code>sint8</code> a <code>sint64</code> son las contrapartes con signo (<a class="spec-record-ref" data-req="SWS_Platform_00016" href="../../spec/record.html?id=SWS_Platform_00016">[SWS_Platform_00016]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00017" href="../../spec/record.html?id=SWS_Platform_00017">[SWS_Platform_00017]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00018" href="../../spec/record.html?id=SWS_Platform_00018">[SWS_Platform_00018]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00067" href="../../spec/record.html?id=SWS_Platform_00067">[SWS_Platform_00067]</a>). Sus rangos, como <code>-128..+127</code> para <code>sint8</code>, se derivan de que AUTOSAR solo admite aritmética de complemento a dos para el compilador y el sistema de destino <a class="spec-record-ref" data-req="SWS_Platform_00061" href="../../spec/record.html?id=SWS_Platform_00061">[SWS_Platform_00061]</a>.</p>
<p>Los tipos optimizados, en cambio, solo garantizan un rango mínimo. <code>uint8_least</code>, <code>uint16_least</code> y <code>uint32_least</code> tienen al menos 8, 16 y 32 bits respectivamente y derivan de <code>uint</code> (<a class="spec-record-ref" data-req="SWS_Platform_00020" href="../../spec/record.html?id=SWS_Platform_00020">[SWS_Platform_00020]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00021" href="../../spec/record.html?id=SWS_Platform_00021">[SWS_Platform_00021]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00022" href="../../spec/record.html?id=SWS_Platform_00022">[SWS_Platform_00022]</a>). De <code>sint8_least</code> a <code>sint32_least</code> son las variantes con signo y derivan de <code>sint</code> (<a class="spec-record-ref" data-req="SWS_Platform_00023" href="../../spec/record.html?id=SWS_Platform_00023">[SWS_Platform_00023]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00024" href="../../spec/record.html?id=SWS_Platform_00024">[SWS_Platform_00024]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00025" href="../../spec/record.html?id=SWS_Platform_00025">[SWS_Platform_00025]</a>). La especificación menciona dos casos de uso típicos: contadores de bucle con un máximo de 124 iteraciones y argumentos de <code>switch</code> con 17 estados. En ambos casos se debe elegir <code>uint8_least</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_7_4_Optimized_integer_data_types.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_7_4_Optimized_integer_data_types">SWS_PlatformTypes p. 17</a>).</p>
<p>En el payload figuran declaraciones como <code>typedef unsigned int uint8_least;</code> o <code>typedef unsigned long uint32;</code>. Interpretación: se trata de asignaciones para un compilador determinado. Solo el ancho o ancho mínimo requerido es normativo (<a class="spec-record-ref" data-req="SWS_Platform_00015" href="../../spec/record.html?id=SWS_Platform_00015">[SWS_Platform_00015]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00020" href="../../spec/record.html?id=SWS_Platform_00020">[SWS_Platform_00020]</a>).</p>

<h4>boolean, TRUE y FALSE: representación y expresiones permitidas</h4>
<p>En R20-11, <code>boolean</code> se implementa como un tipo entero sin signo, concretamente con la longitud de bits más corta que la plataforma admita de forma nativa, por lo general 8 bits <a class="spec-record-ref" data-req="SWS_Platform_00027" href="../../spec/record.html?id=SWS_Platform_00027">[SWS_Platform_00027]</a>. La declaración almacenada es <code>typedef unsigned char boolean;</code> <a class="spec-record-ref" data-req="SWS_Platform_00026" href="../../spec/record.html?id=SWS_Platform_00026">[SWS_Platform_00026]</a>.</p>
<p>Divergencia en versiones posteriores: la versión para R24-11/R25-11 exige el tipo C99 <code>_Bool</code> y ya no fija el tamaño del objeto (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_7_5_Boolean_data_type.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_7_5_Boolean_data_type">SWS_PlatformTypes p. 18</a>). Para R20-11 se aplica el requisito anterior.</p>
<p>Además, <code>boolean</code> debe asignarse a un tipo al que puedan apuntar punteros. Por ello quedan excluidos los tipos de bits eficientes de determinado hardware <a class="spec-record-ref" data-req="SWS_Platform_00060" href="../../spec/record.html?id=SWS_Platform_00060">[SWS_Platform_00060]</a>. Este es un requisito previo para interfaces como <code>CanNm_CheckRemoteSleepIndication</code>, que devuelven un resultado a través de <code>boolean*</code> (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_8_3_18_CanNm_CheckRemoteSleepIndication.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_8_3_18_CanNm_CheckRemoteSleepIndication">SWS_CANNetworkManagement p. 68</a>).</p>
<p><code>TRUE</code> (1) y <code>FALSE</code> (0) solo se definen si aún no existen (<code>#ifndef TRUE</code>) <a class="spec-record-ref" data-req="SWS_Platform_00056" href="../../spec/record.html?id=SWS_Platform_00056">[SWS_Platform_00056]</a>. <h4>Símbolos de plataforma CPU_TYPE, CPU_BIT_ORDER y CPU_BYTE_ORDER</h4>
<p><code>Platform_Types.h</code> indica para cada plataforma tres propiedades de la CPU, cada una como <code>#define</code>:</p>
<ul>
<li>El ancho de registro mediante <code>CPU_TYPE</code> <a class="spec-record-ref" data-req="SWS_Platform_00044" href="../../spec/record.html?id=SWS_Platform_00044">[SWS_Platform_00044]</a>. Se admiten <code>CPU_TYPE_8</code>, <code>CPU_TYPE_16</code>, <code>CPU_TYPE_32</code> y <code>CPU_TYPE_64</code> (<a class="spec-record-ref" data-req="SWS_Platform_00045" href="../../spec/record.html?id=SWS_Platform_00045">[SWS_Platform_00045]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00064" href="../../spec/record.html?id=SWS_Platform_00064">[SWS_Platform_00064]</a>).</li>
<li>El orden de bits a nivel de registro mediante <code>CPU_BIT_ORDER</code> (<a class="spec-record-ref" data-req="SWS_Platform_00043" href="../../spec/record.html?id=SWS_Platform_00043">[SWS_Platform_00043]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00038" href="../../spec/record.html?id=SWS_Platform_00038">[SWS_Platform_00038]</a>).</li>
<li>El orden de bytes en memoria mediante <code>CPU_BYTE_ORDER</code> (<a class="spec-record-ref" data-req="SWS_Platform_00046" href="../../spec/record.html?id=SWS_Platform_00046">[SWS_Platform_00046]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00039" href="../../spec/record.html?id=SWS_Platform_00039">[SWS_Platform_00039]</a>).</li>
</ul>
<p>La asignación a la endianness es unívoca. El orden de bits big-endian da como resultado <code>MSB_FIRST</code>, y el orden de bits little-endian da como resultado <code>LSB_FIRST</code> (<a class="spec-record-ref" data-req="SWS_Platform_00048" href="../../spec/record.html?id=SWS_Platform_00048">[SWS_Platform_00048]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00049" href="../../spec/record.html?id=SWS_Platform_00049">[SWS_Platform_00049]</a>). El orden de bytes big-endian da como resultado <code>HIGH_BYTE_FIRST</code>, y el orden de bytes little-endian da como resultado <code>LOW_BYTE_FIRST</code> (<a class="spec-record-ref" data-req="SWS_Platform_00050" href="../../spec/record.html?id=SWS_Platform_00050">[SWS_Platform_00050]</a>, <a class="spec-record-ref" data-req="SWS_Platform_00051" href="../../spec/record.html?id=SWS_Platform_00051">[SWS_Platform_00051]</a>).</p>
<p>La especificación advierte de no mezclar la numeración de bits con la significancia. En arquitecturas Motorola con orden de bits big-endian, Bit0 designa el bit más significativo; en todas las demás, el menos significativo. En el acumulador, en cambio, el MSB siempre está situado en el extremo izquierdo (<a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_PLATFORM_SECTION_7_3_1_Bit_Ordering_Register.html" data-snip="SNIP_CLASSIC_PLATFORM_SECTION_7_3_1_Bit_Ordering_Register">SWS_PlatformTypes p. 15</a>).</p>
