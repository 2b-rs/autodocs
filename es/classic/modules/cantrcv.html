Controla transceptores CAN externos: modos de funcionamiento, detección de reactivación y reactivación selectiva mediante tramas de reactivación.

CanTrcv controla transceptores CAN externos y los mapea a un modelo de modos genérico con NORMAL, STANDBY y SLEEP. CanIf solicita los cambios de modo de forma asíncrona; el controlador notifica los modos alcanzados mediante una indicación [SWS_CanTrcv_00158]. Además, detecta reactivaciones, las notifica a EcuM y, con el hardware adecuado, admite la reactivación selectiva mediante tramas de reactivación. Condición de contorno fundamental: a SLEEP solo se puede acceder desde STANDBY [SWS_CanTrcv_00104], y mientras la notificación esté bloqueada no se debe perder ninguna reactivación.

El controlador de transceptores CAN (CanTrcv) encapsula transceptores CAN externos tras un modelo de modos genérico. De este modo, ComM y EcuM permanecen desacoplados del hardware concreto (SWS CanTrcv p. 19). Existe una instancia de controlador para cada tipo de hardware de transceptor [SWS_CanTrcv_00016]. Se accede al controlador a través de CanIf y este controla el hardware mediante Dio y Spi, que deben estar inicializados antes de CanTrcv_Init [SWS_CanTrcv_00099]. Tras la inicialización, cada transceptor se encuentra en STANDBY o SLEEP según lo configurado por canal [SWS_CanTrcv_00148]. CanTrcv_DeInit conduce a NOT_ACTIVE [SWS_CanTrcv_91003].

CanTrcv_SetOpMode conmuta entre NORMAL, STANDBY y SLEEP [SWS_CanTrcv_00102]. SLEEP solo está permitido desde STANDBY [SWS_CanTrcv_00104]. Un cambio al modo actual no constituye un error [SWS_CanTrcv_00161]. La función opera de forma asíncrona: en cuanto se alcanza el modo de destino, CanTrcv lo notifica mediante CanIf_TrcvModeIndication [SWS_CanTrcv_00158].

Diagrama de estados: Init conduce a STANDBY o SLEEP, a SLEEP solo se puede acceder mediante STANDBY, DeInit conduce a NOT_ACTIVE. Fuentes: SWS CanTrcv p. 19, [SWS_CanTrcv_00148]

CanIf comprueba las reactivaciones mediante CanTrcv_CheckWakeup. Esta función notifica las reactivaciones detectadas mediante EcuM_SetWakeupEvent [SWS_CanTrcv_00146]. CanTrcv_MainFunction examina los buses en STANDBY y SLEEP [SWS_CanTrcv_00112]. CanTrcv_SetWakeupMode puede bloquear la notificación, habilitarla o borrar reactivaciones almacenadas. Al hacerlo, no debe perderse ninguna reactivación [SWS_CanTrcv_00095].

Los transceptores compatibles con PN (CanTrcvHwPnSupport) reactivan adicionalmente mediante tramas de reactivación configuradas [SWS_CanTrcv_00175]. Durante el apagado, CanSM borra primero el flag WUF y luego conmuta a STANDBY [SWS_CanTrcv_00194]. A continuación, CanSM solicita la comprobación asíncrona del flag de reactivación [SWS_CanTrcv_00224].

En caso de error aplica lo siguiente:

  • Con DET activado se notulan errores de desarrollo; con DET desactivado las API devuelven E_NOT_OK [SWS_CanTrcv_00050].
  • El controlador notifica una comunicación de hardware defectuosa como error de tiempo de ejecución CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006].
  • CanTrcv_MainFunctionDiagnostics notifica errores de bus como CANTRCV_E_BUS_ERROR a DEM [SWS_CanTrcv_00206].

Diagrama de secuencia: durante el apagado de PN se borra el flag WUF, se conmuta el transceptor a STANDBY y se comprueba el flag de reactivación de forma asíncrona. Fuentes: SWS CanTrcv p. 55, [SWS_CanTrcv_00194]

Rol: controlador para transceptores CAN externos situado bajo CanIf

El controlador de transceptores CAN (CanTrcv) controla componentes de transceptores CAN externos. Mapea sus estados de hardware a un modelo de modos de funcionamiento genérico. Este modelo pretende cubrir de forma uniforme numerosos transceptores disponibles. Según la especificación, para lograrlo asume tener uno o dos estados de más para un componente concreto, pero con ello desacopla ComM y EcuM del hardware (SWS CanTrcv p. 19). Para ello, el hardware del transceptor debe ofrecer una interfaz que permita ser mapeada a este modelo [SWS_CanTrcv_00098].

Hacia arriba, CanIf es el interlocutor directo:

  • CanIf_SetTrcvMode invoca CanTrcv_SetOpMode (SWS CanIf p. 95).
  • CanIf_GetTrcvMode invoca CanTrcv_GetOpMode (SWS CanIf p. 97).
  • CanIf_GetTrcvWakeupReason invoca CanTrcv_GetBusWuReason (SWS CanIf p. 98).

Las respuestas transcurren mediante CanIf_TrcvModeIndication, que pertenece a las interfaces obligatorias [SWS_CanTrcv_00085]. Para las indicaciones de PN se enumeran callbacks adicionales de CanIf [SWS_CanTrcv_00086]. Hacia abajo, CanTrcv utiliza Dio y Spi para el control de hardware, así como tipos de Icu, DEM y EcuM, tal como muestra la lista de importación [SWS_CanTrcv_00084]. El controlador implementa tiempos de espera en los cambios de estado con Tm_BusyWait1us16bit [SWS_CanTrcv_00230]. El BSW Scheduler invoca CanTrcv_MainFunction y CanTrcv_MainFunctionDiagnostics (SWS CanTrcv p. 47).

Diagrama de contexto: CanTrcv es operado por CanIf, EcuM y el planificador, y accede al hardware mediante Dio, Spi e Icu. Notifica errores a DET y DEM. Fuentes: [SWS_CanTrcv_00084], [SWS_CanTrcv_00085], [SWS_CanTrcv_00146], SWS EcuM p. 35

Inicialización, ciclo de vida y desinicialización

Antes de invocar CanTrcv_Init [SWS_CanTrcv_00001], el entorno debe haber inicializado todos los controladores utilizados, en particular Spi y Dio [SWS_CanTrcv_00099]. El pasaje del documento añade dos requisitos temporales: la inicialización debe realizarse poco después del encendido y los servicios subyacentes deben ser cortos y síncronos (SWS CanTrcv p. 26).

CanTrcv_Init inicializa todos los transceptores conectados de acuerdo con sus secuencias de inicialización y la configuración de ConfigPtr [SWS_CanTrcv_00180]. El contenido de CanTrcv_ConfigType es específico del hardware [SWS_CanTrcv_00209]. Después, cada transceptor se encuentra en CANTRCV_TRCVMODE_SLEEP o CANTRCV_TRCVMODE_STANDBY; esto se puede configurar por cada transceptor [SWS_CanTrcv_00148].

Al mismo tiempo, la inicialización comprueba si existen reactivaciones:

  • Si el hardware lo admite, CanTrcv_Init comprueba si la actividad del transceptor ha disparado la reactivación. Notifica el resultado mediante EcuM_SetWakeupEvent con la fuente de CanTrcvWakeupSourceRef [SWS_CanTrcv_00167].
  • En transceptores compatibles con PN, además se vuelve a ejecutar la secuencia de configuración si el flag POR o SYSERR está activado. De lo contrario, la configuración guardada en el transceptor sigue siendo válida [SWS_CanTrcv_00182].
  • Un flag POR activado se notifica además a través de CanTrcvPorWakeupSourceRef como reactivación [SWS_CanTrcv_00183].

La notificación de POR se adecua a transceptores con alimentación integrada. En ellos, una reactivación pasiva se manifiesta ante la ECU como un reinicio por encendido (SWS EcuM p. 70).

Diagrama de actividades: la inicialización comprueba la accesibilidad del hardware, trata POR/SYSERR, notifica reactivaciones a EcuM y finaliza por canal en STANDBY o SLEEP. El orden de las comprobaciones es una interpretación. Fuentes: [SWS_CanTrcv_00180], [SWS_CanTrcv_00182], [SWS_CanTrcv_00183], [SWS_CanTrcv_00167], [SWS_CanTrcv_00148]

CanTrcv_DeInit [SWS_CanTrcv_91001] establece el hardware del transceptor en el estado NOT_ACTIVE [SWS_CanTrcv_91003]. En este estado se puede configurar con una nueva secuencia de configuración (SWS CanTrcv p. 49). El estado inicial esperado es CANTRCV_TRCVMODE_NORMAL; de lo contrario, la comprobación de errores de desarrollo notifica CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005].

Modos de funcionamiento NORMAL, STANDBY y SLEEP

CanTrcv_TrcvModeType define los tres modos [SWS_CanTrcv_00163]. CanTrcv_SetOpMode [SWS_CanTrcv_00002] conmuta el estado interno del transceptor direccionado a uno de estos modos [SWS_CanTrcv_00102]. Para las transiciones aplica lo siguiente:

  • Desde NORMAL, el usuario solo solicita STANDBY o NORMAL [SWS_CanTrcv_00103].
  • Desde STANDBY, solo solicita SLEEP o STANDBY [SWS_CanTrcv_00104].
  • Según el esquema, a NORMAL se puede acceder desde los tres modos (SWS CanTrcv p. 19).
  • Un cambio al modo actual está permitido y no constituye un error [SWS_CanTrcv_00161].
  • Si el hardware no admite el modo solicitado, la función devuelve E_NOT_OK [SWS_CanTrcv_00105].

Diagrama de estados: tras Init, el transceptor se encuentra en STANDBY o SLEEP. A SLEEP solo se puede acceder desde STANDBY; a NORMAL, desde todos los modos. DeInit conduce a NOT_ACTIVE. Fuentes: SWS CanTrcv p. 19, [SWS_CanTrcv_00148], [SWS_CanTrcv_00103], [SWS_CanTrcv_00104], [SWS_CanTrcv_91003]

CanTrcv_SetOpMode opera de forma asíncrona: E_OK solo significa que la solicitud ha sido aceptada (SWS CanTrcv p. 33). CanTrcv solo invoca CanIf_TrcvModeIndication con el TransceiverId abstracto de CanIf una vez alcanzado el modo de destino [SWS_CanTrcv_00158]. CanSM ignora dicha notificación para SLEEP, ya que SLEEP solo es solicitado por el código de integración (SWS CanSM p. 94).

En hardware compatible con PN, CanTrcv_SetOpMode comprueba adicionalmente los flags POR y SYSERR [SWS_CanTrcv_00186]. Tras un POR, reinicializa el transceptor [SWS_CanTrcv_00187]. CanTrcv_GetOpMode [SWS_CanTrcv_00005] proporciona de forma síncrona el estado actual [SWS_CanTrcv_00106].

Diagrama de secuencia: un cambio de modo se acepta de forma síncrona y posteriormente se confirma mediante indicación a CanSM a través de CanIf. Fuentes: SWS CanTrcv p. 52, [SWS_CanTrcv_00158], [SWS_CanTrcv_00186]

Wake-up: detección, causa y control de notificaciones

Un wake-up se detecta mediante interrupción o mediante polling (SWS EcuM p. 179). Durante este proceso, CanIf consulta a través de CanIf_CheckWakeup la función CanTrcv_CheckWakeup [SWS_CanTrcv_00143] (SWS CanIf p. 56). Si el hardware lo admite, esta función valida un wake-up mediante actividad del transceptor y lo notifica a través de EcuM_SetWakeupEvent [SWS_CanTrcv_00146].

CanTrcv_MainFunction [SWS_CanTrcv_00013] busca wake-ups en todos los buses en STANDBY y SLEEP y establece un flag de wake-up [SWS_CanTrcv_00112]. Es de suponer que sea relevante sobre todo en configuraciones de polling; el diagrama de configuración prevé para ello el valor CanTrcvWakeUpByPolling (ECUC-Parameter p. 185).

CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] proporciona la causa de wake-up detectada por el transceptor [SWS_CanTrcv_00107]. Entre los valores posibles se encuentran CANTRCV_WU_BY_BUS, CANTRCV_WU_INTERNALLY o CANTRCV_WU_RESET [SWS_CanTrcv_00165]. El nivel de detalle con el que se pueden distinguir las causas depende en gran medida del hardware (SWS CanTrcv p. 35).

El controlador utiliza canales ICU para las interrupciones de wake-up. Solo invoca Icu_EnableNotification y Icu_DisableNotification si CanTrcvIcuChannelRef está configurado [SWS_CanTrcv_00171]. Al cambiar a STANDBY, activa los canales [SWS_CanTrcv_00172]. El pasaje del documento de R24-11 menciona adicionalmente la desactivación al cambiar a NORMAL (SWS CanTrcv p. 23).

Diagrama de secuencia: se comprueba un wake-up en el transceptor mediante interrupción o polling a través de CanIf, se notifica a EcuM y posteriormente se consulta su causa. Fuentes: SWS EcuM p. 179, SWS EcuM p. 138, SWS EcuM p. 140, [SWS_CanTrcv_00146], [SWS_CanTrcv_00112]

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] controla la notificación de wake-up a través de CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164]:

  • CANTRCV_WUMODE_DISABLE: los wake-ups no se notifican, pero se almacenan internamente [SWS_CanTrcv_00093].
  • CANTRCV_WUMODE_ENABLE: un wake-up almacenado se notifica como «present» [SWS_CanTrcv_00111].
  • CANTRCV_WUMODE_CLEAR: se borra un wake-up almacenado [SWS_CanTrcv_00094].

En la fase deshabilitada no debe perderse ningún wake-up [SWS_CanTrcv_00095]. El borrado sirve para descartar wake-ups almacenados cuando la notificación está deshabilitada bajo el control de la capa superior [SWS_CanTrcv_00150]. CanIf reenvía la solicitud a CanTrcv a través de CanIf_SetTrcvWakeupMode (SWS CanIf p. 100).

Despertar selectivo (Partial Networking)

En Partial Networking, los nodos permanecen en modo de bajo consumo hasta que tramas de wake-up (WUF) predefinidas los despiertan. Por tanto, los transceptores compatibles con PN no solo reaccionan al patrón de wake-up (WUP), sino también a estas tramas (SWS CanTrcv p. 27). CanTrcvHwPnSupport indica si el hardware es capaz de hacerlo [SWS_CanTrcv_00174]. El contenedor CanTrcvPartialNetwork y cinco API (CanTrcv_GetTrcvSystemData, CanTrcv_ClearTrcvWufFlag, CanTrcv_ReadTrcvTimeoutFlag, CanTrcv_ClearTrcvTimeoutFlag y CanTrcv_ReadTrcvSilenceFlag) solo existen si este parámetro es TRUE [SWS_CanTrcv_00175].

CanTrcvPnFrameCanId, CanTrcvPnFrameCanIdMask y CanTrcvPnFrameDataMask determinan a qué tramas reacciona el transceptor [SWS_CanTrcv_00177]. CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] activa la función de wake-up por PN con PN_ENABLED [SWS_CanTrcv_00221] y la desactiva con PN_DISABLED [SWS_CanTrcv_00222].

La secuencia de shutdown es fundamental:

  1. CanSM borra el flag WUF a través de CanTrcv_ClearTrcvWufFlag para que no se pierda ningún wake-up por trama al entrar en el modo de bajo consumo. A continuación, el transceptor pasa a STANDBY [SWS_CanTrcv_00194].
  2. CanTrcv confirma el borrado con CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195].
  3. Por último, CanSM solicita la comprobación asíncrona CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223]. CanTrcv notifica el resultado mediante CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224].

Para la conexión SPI, la especificación describe una variante asíncrona (SWS CanTrcv p. 55) y una síncrona (SWS CanTrcv p. 57).

Diagrama de secuencia: durante el shutdown de PN, se borra el flag WUF, el transceptor se conmuta a STANDBY y, tras el sleep del controlador, se comprueba asíncronamente el flag de wake-up. Fuentes: SWS CanTrcv p. 55, SWS CanTrcv p. 56, SWS CanSM p. 36, [SWS_CanTrcv_00194], [SWS_CanTrcv_00224]

Para el diagnóstico, CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] lee la configuración y el estado del transceptor como uint32 [SWS_CanTrcv_00189]. Los flags de timeout y de silence se leen y se borran a través de CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215], CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216] y CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217]. CanTrcv_TrcvFlagStateType indica su estado [SWS_CanTrcv_00211].

Configuración y referencia de instancia

Para cada tipo de hardware de transceptor existe una instancia de controlador que atiende a todos los componentes de dicho tipo [SWS_CanTrcv_00016]. El diagrama de CanIf muestra el caso de controladores idénticos con diferentes tipos de transceptor, lo que requiere entonces dos controladores de transceptor (SWS CanIf p. 34). Un contenedor CanTrcvChannel describe cada canal (multiplicidad 1..*). Contiene, entre otros, CanTrcvHwPnSupport, CanTrcvInitState, CanTrcvWakeupByBusUsed y las referencias a las fuentes de wake-up (SWS CanTrcv p. 70).

Una diferencia entre las fuentes atañe al estado tras Init. El diagrama de configuración indica CanTrcvOpModeNormal como valor por defecto de CanTrcvInitState (ECUC-Parameter p. 187). Sin embargo, la referencia normativa para R20-11 es [SWS_CanTrcv_00148], que tras Init solo prevé SLEEP o STANDBY. El controlador debe rechazar las configuraciones con asignaciones de partición no compatibles [SWS_CanTrcv_00231].

Comportamiento en caso de error

Los errores de desarrollo de [SWS_CanTrcv_00050] siguen un patrón uniforme. Con DET activado, las API notifican:

  • CANTRCV_E_UNINIT en caso de llamada previa a Init, como [SWS_CanTrcv_00122] y [SWS_CanTrcv_00124];
  • CANTRCV_E_INVALID_TRANSCEIVER en caso de ID no válida, como [SWS_CanTrcv_00123] y [SWS_CanTrcv_00129];
  • CANTRCV_E_PARAM_POINTER en caso de punteros NULL, como [SWS_CanTrcv_00132] y [SWS_CanTrcv_00133];
  • CANTRCV_E_TRCV_NOT_NORMAL o CANTRCV_E_TRCV_NOT_STANDBY en caso de transiciones no permitidas [SWS_CanTrcv_00120] [SWS_CanTrcv_00121];
  • errores de parámetro en caso de modo no válido [SWS_CanTrcv_00087] o modo de wake-up no válido [SWS_CanTrcv_00089].

Si DET está desactivado, las API devuelven E_NOT_OK en estos casos.

Si la comunicación con el transceptor está perturbada, el controlador notifica el error de tiempo de ejecución CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006] a través de Det_ReportRuntimeError [SWS_CanTrcv_00085]. Esto se aplica, por ejemplo, en Init [SWS_CanTrcv_00113], SetOpMode [SWS_CanTrcv_00114], GetOpMode [SWS_CanTrcv_00115], SetWakeupMode [SWS_CanTrcv_00117], GetTrcvSystemData [SWS_CanTrcv_00190] y ClearTrcvWufFlag [SWS_CanTrcv_00196]. Una excepción es CanTrcv_GetBusWuReason: en este caso, según [SWS_CanTrcv_00116], devuelve E_OK. Init notifica una velocidad en baudios no compatible como CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168].

Diagrama de actividades: las llamadas a la API pasan por comprobaciones de errores de desarrollo y, a continuación, por el acceso al hardware con gestión de errores de tiempo de ejecución. El orden de comprobación es una interpretación. Fuentes: [SWS_CanTrcv_00050], [SWS_CanTrcv_00122], [SWS_CanTrcv_00123], [SWS_CanTrcv_00132], [SWS_CanTrcv_00114], [SWS_CanTrcv_00116]

Los errores de bus se tratan como errores de producción. El requisito previo es que el hardware pueda distinguir los errores de bus de otros errores [SWS_CanTrcv_00178] y que CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. Entonces, CanTrcv_MainFunctionDiagnostics [SWS_CanTrcv_00218] lee cíclicamente el flag BUSERR. Notifica CANTRCV_E_BUS_ERROR como DEM_EVENT_STATUS_FAILED [SWS_CanTrcv_00206] o DEM_EVENT_STATUS_PASSED [SWS_CanTrcv_00227] a DEM [SWS_CanTrcv_00228] [SWS_CanTrcv_00229]. El evento de DEM se referencia a través de CanTrcvDemEventParameterRefs (SWS CanTrcv p. 78).
