Rol de BswM: árbitro para los modos del software básico

En la unidad de control, las solicitudes de modo convergen en el BSW Mode Manager (BswM), que las traduce en acciones. Realiza el arbitraje basándose en las indicaciones de modo entrantes [SWS_BswM_00035]. La especificación distingue dos tipos de entradas (SWS BswM p. 26):

  • Las peticiones de modo proceden en su mayoría de SW-C de aplicación y, en ocasiones, también de módulos BSW como DCM.
  • Las indicaciones de modo proceden siempre de módulos BSW, como los State Managers específicos del bus o EcuM.

En el modelo de componentes, BswM es un componente de servicio que solo atiende Mode Requests de la propia unidad de control (SWS BswM p. 48).

BswM se vuelve operativo mediante acciones. En principio, puede llamar a cualquier función de la BSW de AUTOSAR (SWS BswM p. 92). Como interfaces opcionales, la especificación menciona, entre otras, Com_IpduGroupStart, Com_IpduGroupStop y Com_EnableReceptionDM [SWS_BswM_00008]. Además, BswM puede ejecutar callouts de usuario [SWS_BswM_00270]. Sus parámetros se definen en tiempo de configuración en el contenedor BswMUserCallout [SWS_BswM_00054]. BswM no tiene interfaces obligatorias con otros módulos [SWS_BswM_00007].

Diagrama de contexto: las API de notificación de los módulos BSW y los puertos de las SW-C convergen en BswM; a partir de reglas, este actúa mediante acciones sobre Com, PduR, EthIf, EcuM, J1939Rm y callouts. Fuentes: SWS BswM p. 87, [SWS_BswM_00008], [SWS_BswM_00201], [SWS_BswM_00202], Guide Modemanagement p. 45, Guide Modemanagement p. 61

Entradas: indicaciones, peticiones y eventos

Para los módulos BSW, BswM ofrece una API en C para cada fuente. Internamente, asigna cada llamada a un Mode Request Port (Guide Modemanagement p. 18). Para ello, la tabla de asignación vincula un parámetro de la API con una referencia de configuración (SWS BswM p. 87). Un ejemplo: BswM_CanSM_CurrentState se asigna mediante el par Network / BswMCanSMChannelRef a la fuente BswMCanSMIndication [SWS_BswM_00049]. Esta fuente se crea una vez por cada canal CAN (Guide Modemanagement p. 24).

Las API de notificación según su origen:

  • Bus State Manager: CanSM, LinSM, FrSM y EthSM notifican su estado ([SWS_BswM_00049], [SWS_BswM_00052], [SWS_BswM_00051], [SWS_BswM_00050]). LinSM notifica además la tabla de planificación activa [SWS_BswM_00058], y LinTp solicita un modo LIN-TP [SWS_BswM_00156].
  • ComM: notifica modos de canal [SWS_BswM_00047] y modos PNC [SWS_BswM_00148] y señaliza un shutdown mediante BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Gestión de red: Nm y J1939Nm notifican cambios de estado ([SWS_BswM_91002], [SWS_BswM_00194]). Nm indica adicionalmente un CarWakeUp [SWS_BswM_00235].
  • Memoria y diagnóstico: las notificaciones proceden de NvM ([SWS_BswM_00104], [SWS_BswM_00152]), DCM ([SWS_BswM_00048], [SWS_BswM_00158]) y J1939Dcm [SWS_BswM_00165].
  • Service Discovery: notifica a través de tres callbacks ([SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]).
  • EthIf y WdgM: EthIf notifica estados de enlace de grupos de puertos de switch [SWS_BswM_91001]. WdgM solicita un reinicio de partición [SWS_BswM_00157].

Si un módulo BSW no dispone de una interfaz de petición propia, utiliza la llamada genérica BswM_RequestMode con los tipos BswM_UserType y BswM_ModeType ([SWS_BswM_00046], [SWS_BswM_00216], [SWS_BswM_00214]). Las SW-C acceden a BswM mediante tres tipos de puertos:

  • modeRequestPort: Required Port para peticiones de modo [SWS_BswM_00201].
  • modeNotificationPort: Required Port a través del cual BswM recibe los cambios de modo observados [SWS_BswM_00200].
  • modeSwitchPort: Provided Port a través del cual el propio BswM conmuta modos [SWS_BswM_00202].

Los eventos como BswM_ComM_InitiateReset se configuran como BswMEventRequestPort (SWS BswM p. 102). El arbitraje tiene en cuenta tanto la ocurrencia de un evento como su borrado (SWS BswM p. 26).

Referencia al release R20-11: según el historial de cambios (SWS BswM p. 2), R20-11 introdujo los siguientes cambios:

  • Reintroducción de BswM_EcuM_CurrentState [SWS_BswM_91003] y BswM_EcuM_RequestedState [SWS_BswM_91004].
  • Soporte para grupos de puertos de switch Ethernet.
  • Nueva acción BswMEthIfStartAllPorts [SWS_BswM_00286].
  • Eliminación de Pretended Networking.

Dos cambios posteriores no afectan todavía a R20-11: BswM_WdgM_RequestPartitionReset [SWS_BswM_00157] no se marcó como obsoleto hasta R21-11, y la petición de modo de SoAd no se incorporó hasta R21-11 (SWS BswM p. 2).

Reglas, listas de acciones y momento de la evaluación

El comportamiento de BswM se configura mediante reglas y listas de acciones (Guide Modemanagement p. 32):

  • Una regla es una expresión lógica sobre los valores actuales de los Mode Request Ports.
  • Según el resultado, BswM ejecuta la lista de acciones True o False.
  • Una lista de acciones contiene acciones atómicas, listas de acciones anidadas o referencias a otras reglas.

Las acciones solo pueden invocarse en el contexto de una lista de acciones [SWS_BswM_00147].

El momento en que se evalúa una regla lo determina el parámetro BswMRequestProcessing para cada puerto:

  • IMMEDIATE: todas las reglas que hacen referencia al puerto se evalúan de inmediato (Guide Modemanagement p. 32). En el caso de peticiones de SW-C, la RTE debe activar para ello una runnable de arbitraje mediante un DataReceiveEvent (SWS BswM p. 48).
  • BSWM_DEFERRED: las reglas se evalúan en BswM_MainFunction [SWS_BswM_00053] [SWS_BswM_00075].

Para los temporizadores se aplican reglas especiales. Independientemente de su configuración, un BswMTimer siempre se trata como DEFERRED y se arbitra en la Main Function [SWS_BswM_00220]. En la versión R23-11, solo se puede controlar mediante la acción BswMTimerControl, y su resolución es un múltiplo del tiempo de ciclo de la Main Function (SWS BswM p. 37).

Los valores iniciales influyen en qué reglas se arbitran. Si falta un valor inicial (BswMModeInitValue), una condición de modo se considera indefinida hasta la primera actualización. Las reglas con condiciones indefinidas no se arbitran (SWS BswM p. 30). Esta precisión procede de la versión R23-11. Probablemente ya se aplique en sentido análogo a R20-11; sin embargo, aquí no se dispone del requisito correspondiente de R20-11.

Diagrama de actividades: se comprueba una notificación, se almacena y, según el tipo de procesamiento, se evalúa de inmediato o en la Main Function; a continuación sigue la lista de acciones True o False. Fuentes: [SWS_BswM_00080], [SWS_BswM_00095], [SWS_BswM_00075], [SWS_BswM_00147], [SWS_BswM_00238], Guide Modemanagement p. 32, SWS BswM p. 30

Ciclo de vida y arranque bajo el control de EcuM

BswM_Init [SWS_BswM_00002] inicializa todas las variables globales del módulo. A continuación, BswM puede arbitrar las peticiones de modo. Antes de la llamada, solo deben estar inicializados OS y SchM (SWS BswM p. 69). El puntero pasado apunta a los datos post-build en BswM_ConfigType [SWS_BswM_00213]. BswM_Init es «Conditionally Reentrant», porque BswM puede estar instanciado en varias particiones (SWS BswM p. 69). Por ello, EcuM llama a BswM_Init en un bucle para cada instancia de BswM de un núcleo (SWS EcuM p. 83).

En la secuencia StartPostOS, EcuM inicia primero el BSW Scheduler. Después inicializa BswM y, a continuación, concluye la inicialización de SchM (SWS EcuM p. 42). A partir de este punto, BswM controla el resto del arranque: se encarga de que se ejecuten las rutinas de inicialización de los demás módulos BSW y de que se inicie la RTE (Guide Modemanagement p. 36). En el ejemplo de la guía, esto sucede del siguiente modo:

  1. Una regla DEFERRED activa NvM_ReadAll.
  2. NvM notifica la finalización mediante BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. A continuación, una regla subsiguiente inicia la RTE (NV-Daten-Leitfaden p. 20).

Diagrama de secuencia: EcuM inicializa BswM en StartPostOS; después, las reglas de BswM impulsan el arranque a través de NvM_ReadAll y Rte_Start. Fuentes: SWS EcuM p. 42, Guide Modemanagement p. 36, NV-Daten-Leitfaden p. 20, [SWS_BswM_00002]

Durante el apagado, EcuM llama a BswM_Deinit [SWS_BswM_00119] en la secuencia OffPreOS para cada instancia de BswM del núcleo (SWS EcuM p. 90). A partir de entonces, BswM ya no procesa modos, aun cuando sigan llegando peticiones o se llame a la Main Function [SWS_BswM_00120]. Si se reinicia la partición de BswM, RestartTask lo notifica mediante BswM_BswMPartitionRestarted [SWS_BswM_00193].

Diagrama de estados: BswM solo arbitra entre BswM_Init y BswM_Deinit; antes y después no tiene lugar ningún procesamiento de modos. Fuentes: [SWS_BswM_00002], [SWS_BswM_00119], [SWS_BswM_00120], [SWS_BswM_00076], [SWS_BswM_00078], SWS BswM p. 69

Interacción con EcuM, fuentes de despertar y grupos de puertos Ethernet

En el ECU Mode Handling, EcuM no dispone de una máquina de estados propia (SWS EcuM p. 99). Arbitra las peticiones RUN y POST_RUN de las SW-C y notifica el resultado mediante BswM_EcuM_RequestedState [SWS_BswM_91004], ya que solo BswM decide sobre las transiciones. El flujo es un ciclo:

  1. BswM establece el estado con EcuM_SetState.
  2. EcuM transmite el modo a la RTE (SWS EcuM p. 99).
  3. Tras la respuesta de la RTE, el EcuM notifica el nuevo estado al BswM a través de BswM_EcuM_CurrentState [SWS_BswM_91003] (Guide Modemanagement p. 34).

Con esta estructura también se pueden seguir utilizando Legacy-SW-Cs que se escribieron para el EcuM con máquina de estados fija (Guide Modemanagement p. 61).

Diagrama de secuencia: El EcuM notifica el resultado del RUN Request Protocol, el BswM decide y establece el estado, y solo tras la respuesta de la RTE sigue BswM_EcuM_CurrentState. Fuentes: SWS EcuM p. 99, Guide Modemanagement p. 34, Guide Modemanagement p. 61, [SWS_BswM_91003], [SWS_BswM_91004]

Las fuentes de reactivación pasan en el EcuM por los estados NONE, PENDING, VALIDATED y EXPIRED. El EcuM notifica cada entrada en uno de estos estados mediante BswM_EcuM_CurrentWakeup [SWS_BswM_00131] (SWS EcuM p. 64). En el BswM le corresponde la fuente BswMEcuMWakeupSource con el valor inicial ECUM_WKSTATUS_NONE, que se crea una vez para cada fuente de reactivación (Guide Modemanagement p. 29).

Diagrama de estados: Cada cambio de estado de una fuente de reactivación llega al BswM como indicación de modo. Fuentes: SWS EcuM p. 60, SWS EcuM p. 63, SWS EcuM p. 64, [SWS_BswM_00131]

Los grupos de puertos de switch Ethernet son nuevos en R20-11. ComM notifica el modo PNC mediante BswM_ComM_CurrentPNCMode [SWS_BswM_00148]. El BswM conoce la asignación de PNC a grupo de puertos y llama a EthIf_SwitchPortGroupRequestMode con ETH_MODE_ACTIVE o ETH_MODE_DOWN (Guide Modemanagement p. 49). En la dirección opuesta, EthIf notifica mediante BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001] el estado de enlace acumulado de aquellos grupos de puertos que no están asignados a ningún EthIfController (SWS EthIf p. 29). Con la acción BswMEthIfStartAllPorts, el BswM inicia todos los puertos mediante EthIf_StartAllPorts [SWS_BswM_00286].

Diagrama de secuencia: El modo PNC controla el grupo de puertos y el estado de enlace acumulado fluye de vuelta al BswM. Fuentes: Guide Modemanagement p. 49, SWS EthIf p. 92, SWS EthIf p. 29, [SWS_BswM_00148], [SWS_BswM_91001]

Configuración y referencia de instancia de los Request Ports

La herramienta de configuración asigna los parámetros de la API a los contenedores ECUC referenciados (Guide Modemanagement p. 32). Dos ejemplos:

  • BswMDcmComModeRequest conecta mediante BswMDcmComMChannelRef el argumento Network de BswM_Dcm_CommunicationMode_CurrentState con un canal ComM [SWS_BswM_00048].
  • En BswM_J1939DcmBroadcastStatus, el BswM evalúa el bit en la posición del ComMChannelId referenciado (SWS BswM p. 70). Solo se pueden asignar los primeros 16 canales [SWS_BswM_00165].

En J1939, el BswM conmuta tres elementos en función del estado J1939Nm [SWS_BswM_00194]: grupos de COM-I-PDU, grupos de rutas de enrutamiento de PduR y el tratamiento de solicitudes de J1939Rm (Guide Modemanagement p. 45).

En cuanto a los tipos de datos e interfaces auxiliares:

  • BswM_ModeType y BswM_UserType se derivan de uint16 ([SWS_BswM_00214], [SWS_BswM_00216]).
  • Los tipos importados de los módulos vecinos se enumeran de forma recopilada [SWS_BswM_00001].
  • BswM_GetVersionInfo proporciona la información de versión [SWS_BswM_00003].
  • La Main Function está disponible mediante SchM_BswM.h [SWS_BswM_00053].

Comportamiento en caso de error

Si BswMDevErrorDetect está activa, las API de notificación comprueban dos cosas:

  • Inicialización: Si el BswM no está inicializado, se ignora la notificación y se notifica BSWM_E_UNINIT al DET. Son ejemplos CanSM [SWS_BswM_00080], EthSM [SWS_BswM_00081], LinSM-Schedule [SWS_BswM_00086], PNC [SWS_BswM_00149] y trabajos de NvM [SWS_BswM_00153].
  • Rango de valores: Los valores fuera del rango admisible también se descartan y se notifican con BSWM_E_REQ_MODE_OUT_OF_RANGE, por ejemplo en [SWS_BswM_00095], [SWS_BswM_00150], [SWS_BswM_00133] y [SWS_BswM_00154].

La Main Function se comporta de forma diferente: si se llama antes de la inicialización, regresa inmediatamente y no notifica ningún error [SWS_BswM_00076].

Entre los códigos de error de desarrollo se incluyen, entre otros, BSWM_E_UNINIT (0x01), BSWM_E_NULL_POINTER, BSWM_E_REQ_USER_OUT_OF_RANGE, BSWM_E_REQ_MODE_OUT_OF_RANGE y BSWM_E_PARAM_CONFIG [SWS_BswM_00230]. Si una acción devuelve E_NOT_OK, el BswM notifica el error de tiempo de ejecución BSWM_E_ACTION_FAILED. Su valor se encuentra entre 0x80 y 0xFF y se configura en BswMReportFailRuntimeErrorId [SWS_BswM_00238].

Los errores del sistema llegan al BswM como indicaciones de modo ordinarias. En caso de Bus-Off, CanSM notifica en este orden (SWS CanSM p. 70):

  1. CANSM_BSWM_BUS_OFF al BswM,
  2. COMM_SILENT_COMMUNICATION a ComM,
  3. un evento PRE_FAILED al DEM.

Si la recuperación tiene éxito, sigue CANSM_BSWM_FULL_COMMUNICATION (SWS CanSM p. 65). Cómo reacciona el sistema ante ello es asunto exclusivo de las reglas mediante BswMCanSMIndication [SWS_BswM_00049]. Otras rutas de error son el reinicio de partición solicitado por el WdgM [SWS_BswM_00157] y la notificación de un reinicio de partición [SWS_BswM_00193].

Diagrama de secuencia: En caso de Bus-Off, CanSM informa al BswM antes que a ComM y DEM; tras la recuperación, CanSM notifica de nuevo comunicación completa. Fuentes: SWS CanSM p. 70, SWS CanSM p. 65, Fehlerbeschreibung p. 19, [SWS_BswM_00049]
