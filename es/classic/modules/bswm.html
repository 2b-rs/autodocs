Arbitra solicitudes e indicaciones de modo mediante reglas y desencadena a partir de ellas acciones en el Basic Software.

El BSW Mode Manager recibe indicaciones de modo procedentes de módulos BSW y solicitudes de modo de SW-C. Las arbitra mediante reglas configuradas cuyo resultado desencadena listas de acciones True o False [SWS_BswM_00035]. Según BswM_Init, controla de este modo la inicialización posterior del Basic Software, el ECU Mode Handling con el EcuM y la habilitación de la comunicación, como la de grupos de I-PDU o grupos de puertos Ethernet. BswM_MainFunction evalúa periódicamente las reglas con entradas BSWM_DEFERRED, y todas las demás de forma inmediata [SWS_BswM_00075]. Con el DET activo, las solicitudes no válidas o que llegan antes de la inicialización se ignoran y se notifican.

El BSW Mode Manager (BswM) es la entidad de arbitraje central del Basic Software. Recibe indicaciones de modo de módulos BSW como EcuM, ComM, los gestores de estado de bus, NvM, DCM o Sd, así como solicitudes de modo de SW-C. A partir de ellas, decide mediante reglas configuradas qué debe suceder [SWS_BswM_00035], SWS BswM p. 26. Las entradas llegan como API de C, como puertos de SW-C o como eventos. Cada API de C está asignada a un puerto de solicitud concreto mediante parámetros de referencia SWS BswM p. 87.

Diagrama de contexto: Múltiples notificadores alimentan al BswM; este actúa a través de acciones sobre Com, EthIf, EcuM, RTE y callouts. Fuentes: [SWS_BswM_00035], [SWS_BswM_00008], Mode-Mgmt-Guide p. 18

Una regla es una expresión lógica sobre los valores actuales de los puertos. Según el resultado, ejecuta la lista de acciones True o la False. Las listas de acciones contienen acciones, listas anidadas u otras reglas Mode-Mgmt-Guide p. 32. Con BSWM_IMMEDIATE, una regla se evalúa inmediatamente. Con BSWM_DEFERRED, esto tiene lugar en BswM_MainFunction [SWS_BswM_00075]. Las reglas con condiciones aún no definidas no se arbitran SWS BswM p. 30.

Diagrama de actividades: Una solicitud se comprueba, se almacena y, según el tipo de procesamiento, se evalúa frente a las reglas de forma inmediata o cíclica. Fuentes: [SWS_BswM_00075], SWS BswM p. 30

El EcuM llama a BswM_Init [SWS_BswM_00002] en la secuencia StartPostOS SWS EcuM p. 42. A continuación, el BswM controla mediante reglas la inicialización posterior hasta el inicio de la RTE, en el ejemplo con NvM_ReadAll y BswM_NvM_CurrentJobMode [SWS_BswM_00152], Mode-Mgmt-Guide p. 36. En el ECU Mode Handling, solo el BswM decide sobre las transiciones del EcuM SWS EcuM p. 99. Desde R20-11, conmuta además grupos de puertos Ethernet en función de los estados de PNC Mode-Mgmt-Guide p. 49. Tras BswM_Deinit ya no tiene lugar ningún procesamiento de modo [SWS_BswM_00120].

Con el DET activo, las API de entrada ignoran las llamadas previas a la inicialización y notifican BSWM_E_UNINIT [SWS_BswM_00080]. Los valores fuera del rango permitido se tratan del mismo modo y notifican BSWM_E_REQ_MODE_OUT_OF_RANGE [SWS_BswM_00095]. Si una acción falla, el BswM notifica el error de tiempo de ejecución configurable BSWM_E_ACTION_FAILED [SWS_BswM_00238].

Rol del BswM: arbitraje de modo central del Basic Software

El BSW Mode Manager (BswM) recibe solicitudes de modo e indicaciones de modo. A partir de ellas, arbitra mediante reglas configuradas qué acciones deben ejecutarse [SWS_BswM_00035], SWS BswM p. 26. Las solicitudes de modo proceden en su mayoría de SW-C de aplicación, pero también pueden provenir de módulos BSW como el DCM. Las indicaciones de modo las proporcionan siempre otros módulos BSW, como los gestores de estado específicos del bus y el EcuM. El BswM trata ambos tipos por igual y los agrupa bajo el término «mode arbitration request» SWS BswM p. 26.

El BswM está modelado como un componente de servicio que atiende Mode Requests locales de la ECU SWS BswM p. 48. No tiene interfaces obligatorias hacia otros módulos [SWS_BswM_00007]. Sus acciones llaman a funciones de otros módulos BSW. Para ello, la especificación menciona una lista de interfaces opcionales, como Com_IpduGroupStart, Com_IpduGroupStop o el control de la monitorización de recepción de grupos de I-PDU [SWS_BswM_00008], SWS BswM p. 93. Con ello, el límite del sistema queda delimitado claramente: los módulos notificadores solo informan de su estado. La reacción ante ello la determina exclusivamente la lógica configurada en el BswM Mode-Mgmt-Guide p. 32.

Diagrama de contexto: Numerosos módulos BSW y SW-C envían notificaciones al BswM; este repercute mediante acciones sobre Com, EthIf, EcuM, RTE y callouts de usuario. Fuentes: [SWS_BswM_00035], [SWS_BswM_00008], [SWS_BswM_00202], [SWS_BswM_00270], Mode-Mgmt-Guide p. 18, SWS EcuM p. 99

Entradas: Indicaciones de modo mediante API de C, puertos y eventos

El contenedor BswMModeRequestSource especifica cómo llega una entrada. Existen tres tipos Mode-Mgmt-Guide p. 18:

  • una API de C que un módulo BSW llama directamente y que el BswM traduce internamente en una Mode Request,
  • un RPort con SenderReceiverInterface (BswMSwcModeRequest),
  • un RPort con ModeSwitchInterface (BswMSwcModeNotification).

Para los tipos de puerto, el BswM genera puertos según patrones de nomenclatura fijos [SWS_BswM_00201], [SWS_BswM_00200]. Las API de C en R20-11 se pueden agrupar según su procedencia:

  • Estado de ECU y Wakeup: BswM_EcuM_CurrentState [SWS_BswM_91003], BswM_EcuM_RequestedState [SWS_BswM_91004], BswM_EcuM_CurrentWakeup [SWS_BswM_00131].
  • Comunicación: BswM_ComM_CurrentMode [SWS_BswM_00047], BswM_ComM_CurrentPNCMode [SWS_BswM_00148], BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Bus State Managers y LinTp: CanSM [SWS_BswM_00049], EthSM [SWS_BswM_00050], FrSM [SWS_BswM_00051], LinSM [SWS_BswM_00052] junto con indicación de schedule [SWS_BswM_00058] así como BswM_LinTp_RequestMode [SWS_BswM_00156].
  • Gestión de red y Ethernet: BswM_Nm_StateChangeNotification [SWS_BswM_91002], BswM_Nm_CarWakeUpIndication [SWS_BswM_00235], BswM_J1939Nm_StateChangeNotification [SWS_BswM_00194], BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001].
  • Diagnóstico: BswM_Dcm_CommunicationMode_CurrentState [SWS_BswM_00048], BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], BswM_J1939DcmBroadcastStatus [SWS_BswM_00165].
  • Memoria: BswM_NvM_CurrentBlockMode [SWS_BswM_00104], BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  • Service Discovery: BswM_Sd_* [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210].
  • Particiones: BswM_WdgM_RequestPartitionReset [SWS_BswM_00157], BswM_BswMPartitionRestarted [SWS_BswM_00193].
  • Genérico: BswM_RequestMode [SWS_BswM_00046] está concebido únicamente para módulos BSW sin interfaz propia. Opera con BswM_UserType [SWS_BswM_00216] y BswM_ModeType [SWS_BswM_00214], ambos derivados de uint16.

Cada API está asignada exactamente a un tipo de request port. Parámetros como Network se asignan a un puerto concreto mediante parámetros de referencia como BswMCanSMChannelRef o BswMComMChannelRef SWS BswM p. 87. Por este motivo, se crea por ejemplo un BswMCanSMIndication por canal CAN Mode-Mgmt-Guide p. 24. Todas las API de notificación son síncronas. Con excepción de BswM_ComM_InitiateReset, que no es reentrante, son reentrantes [SWS_BswM_00217], [SWS_BswM_00049].

Junto a los mode request ports con estado, existen event request ports. A través de ellos, los módulos BSW envían eventos, por ejemplo mediante BswM_ComM_InitiateReset() SWS BswM p. 102. El BswM arbitra tanto sobre tales eventos como sobre su restablecimiento SWS BswM p. 26. Según el historial de cambios, R20-11 introdujo las siguientes novedades SWS BswM p. 2:

  • Reanudación de BswM_EcuM_CurrentState y BswM_EcuM_RequestedState,
  • nueva notificación BswMNmStateChangeNotification,
  • soporte de la conmutación de grupos de puertos Ethernet.

BswM_WdgM_RequestPartitionReset no queda obsoleto hasta R21-11 SWS BswM p. 2.

Reglas y listas de acciones: de la entrada a la acción

El comportamiento del BswM se configura mediante reglas y listas de acciones. Una regla es una expresión lógica sobre los valores actuales de los mode request ports. En función del resultado, su evaluación ejecuta la lista de acciones True o False Mode-Mgmt-Guide p. 32. Una lista de acciones puede contener SWS BswM p. 31:

  • acciones atómicas,
  • listas de acciones anidadas,
  • referencias a reglas que se evalúan a continuación en el contexto de esta lista.

Las acciones solo deben invocarse en el contexto de una lista de acciones [SWS_BswM_00147]. Un diagrama de la especificación muestra una regla de ejemplo. Vincula mediante AND una condición de modo (MyModeRequestPort igual a MODE_A) con el event port ComMInitiateReset SWS BswM p. 25.

El momento en que se evalúa una regla lo determina BswMRequestProcessing por cada puerto:

  • BSWM_IMMEDIATE: cada regla que referencia el puerto se procesa de inmediato Mode-Mgmt-Guide p. 32. Para los puertos de SW-C, el BswM registra para ello un runnable que la RTE inicia al recibir datos SWS BswM p. 48.
  • BSWM_DEFERRED: el BswM lee el valor cíclicamente. BswM_MainFunction [SWS_BswM_00053] evalúa todas las reglas que utilizan al menos una de tales entradas [SWS_BswM_00075].

Diagrama de actividades: Una solicitud entrante se comprueba, se almacena y, en función del tipo de procesamiento, se evalúa frente a las reglas de forma inmediata o en la MainFunction; las reglas con condiciones indefinidas no se tienen en cuenta. Fuentes: [SWS_BswM_00075], [SWS_BswM_00080], [SWS_BswM_00095], SWS BswM p. 30, Mode-Mgmt-Guide p. 32

Mediante BswMModeInitValue, un puerto recibe un valor inicial durante la inicialización. Si este falta, la condición se considera indefinida hasta la primera actualización. Las reglas con condiciones indefinidas no se arbitran SWS BswM p. 30. Por ello, los ejemplos de la guía establecen valores iniciales, como CANSM_BSWM_NO_COMMUNICATION para indicaciones de CanSM Mode-Mgmt-Guide p. 24.

Para tiempos de espera, el BswM ofrece temporizadores. Un BswMTimer es una Mode Request Source interna y solo puede controlarse mediante la acción BswMTimerControl; no dispone de interfaz externa SWS BswM p. 37. Su secuencia SWS BswM p. 37:

  • Durante la inicialización se detienen todos los temporizadores.
  • BSWM_TIMER_START carga el temporizador con BswMTimerValue y establece BSWM_TIMER_STARTED.
  • En cada ciclo de BswM_MainFunction se decrementa según su tiempo de ciclo.

Los temporizadores siempre se procesan como DEFERRED, con independencia de su configuración [SWS_BswM_00220]. Es probable que el valor BSWM_TIMER_EXPIRED identifique la cuenta atrás expirada. Se trata de una interpretación, ya que la sección está abreviada en el payload SWS BswM p. 37.

Diagrama de estados: Ciclo de vida de un BswMTimer desde STOPPED a través de STARTED hasta EXPIRED, controlado exclusivamente por acciones y la MainFunction. Fuentes: [SWS_BswM_00220], SWS BswM p. 37.

Además de las funciones de la lista de interfaces opcionales [SWS_BswM_00008], existen acciones específicas. Así, BswMEthIfStartAllPorts invoca EthIf_StartAllPorts al ejecutarse [SWS_BswM_00286]. Las funciones libremente definidas se configuran como BswMUserCallout. En tal caso, el nombre y los parámetros se definen en el tiempo de configuración de la ECU [SWS_BswM_00054], [SWS_BswM_00270].

Arranque, cadenas de inicialización y apagado

BswM_Init [SWS_BswM_00002] recibe un puntero a la configuración post-build BswM_ConfigType [SWS_BswM_00213]. La función inicializa todas las variables globales. A partir de ese momento, el BswM está listo para arbitrar solicitudes. Solo se presuponen el OS y el SchM SWS BswM p. 69. El EcuM invoca BswM_Init en la secuencia StartPostOS tras SchM_Start(); a continuación siguen SchM_Init y SchM_StartTiming SWS EcuM p. 42. En sistemas multinúcleo, la llamada tiene lugar en un bucle sobre cada instancia de BswM del núcleo SWS EcuM p. 81. Para tales instancias múltiples en varias particiones o núcleos, BswM_Init es condicionalmente reentrante SWS BswM p. 69.

Diagrama de secuencias: Secuencia StartPostOS con inicialización de cada instancia de BswM entre SchM_Start y SchM_Init; después, la MainFunction se ejecuta cíclicamente. Fuentes: [SWS_BswM_00002], SWS EcuM p. 42, SWS EcuM p. 78, SWS BswM p. 37

A partir de este punto, el BswM asume el control del flujo. Se encarga de invocar las rutinas de inicialización restantes del software básico y de iniciar la RTE Mode-Mgmt-Guide p. 36. Los módulos que debe inicializar vienen descritos por el contenedor de EcuM EcuMDriverInitListBswM SWS EcuM p. 224. En el ejemplo de la guía, la inicialización se desarrolla del siguiente modo Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20:

  1. Una regla DEFERRED inicializa los controladores de NVRAM y desencadena NvM_ReadAll.
  2. El NvM notifica el fin de la orden a través de BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. Esta notificación desencadena el resto de la inicialización y el cambio a ECU_RUN.

Para esta API, la guía muestra aún un parámetro uint8 ServiceId Mode-Mgmt-Guide p. 26. Sin embargo, para R20-11 resulta determinante la signatura con NvM_MultiBlockRequestType [SWS_BswM_00152].

Diagrama de secuencias: Segunda fase de inicialización controlada por reglas con NvM_ReadAll, respuesta del NvM y posterior inicio de la RTE. Fuentes: [SWS_BswM_00152], [SWS_BswM_00075], Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20

Durante el apagado, y según la guía de NV, el BswM es responsable de escribir los bloques modificados; en el ejemplo, mediante NvM_WriteAll NV-Data-Guide p. 41. El NvM también le notifica la cancelación de un WriteAll a través de la indicación de modo de trabajo SWS NvM p. 155. En la secuencia OffPreOS, el EcuM desinicializa el BswM como primer paso SWS EcuM p. 50. Tras BswM_Deinit [SWS_BswM_00119] ya no tiene lugar ningún procesamiento de modo, incluso si llegan solicitudes o se invoca la MainFunction [SWS_BswM_00120].

Interacción con el EcuM: ECU Mode Handling y fuentes de wakeup

En el ECU Mode Handling, el EcuM arbitra las solicitudes RUN y POST_RUN de las SW-C. No dispone de una máquina de estados propia; únicamente el BswM decide cuándo tiene lugar una transición SWS EcuM p. 99. La secuencia Mode-Mgmt-Guide p. 34:

  1. El EcuM notifica el resultado del RUN Request Protocol mediante BswM_EcuM_RequestedState [SWS_BswM_91004].
  2. El BswM establece el estado mediante EcuM_SetState.
  3. El EcuM notifica el modo correspondiente a la RTE.
  4. Tras la confirmación de la RTE, el EcuM invoca BswM_EcuM_CurrentState [SWS_BswM_91003].

Los estados son ECUM_STATE_STARTUP, ECUM_STATE_APP_RUN, ECUM_STATE_APP_POST_RUN, ECUM_STATE_SHUTDOWN y ECUM_STATE_SLEEP Mode-Mgmt-Guide p. 34. Este acoplamiento permite reutilizar SW-C diseñadas para el EcuM con máquina de estados fija. Para ello no es necesaria una SW-C de compatibilidad Mode-Mgmt-Guide p. 61.

Diagrama de secuencias: El EcuM arbitra las solicitudes RUN, el BswM decide sobre la transición, la RTE es informada y la confirmación regresa al BswM como CurrentState. Fuentes: [SWS_BswM_91004], [SWS_BswM_91003], SWS EcuM p. 99, Mode-Mgmt-Guide p. 34, Mode-Mgmt-Guide p. 61

El EcuM notifica los cambios de estado de las fuentes de wakeup a través de BswM_EcuM_CurrentWakeup [SWS_BswM_00131]. En la máquina de estados de las fuentes de wakeup, cada uno de los estados NONE, PENDING, VALIDATED y EXPIRED invoca esta API al entrar en él SWS EcuM p. 60. En detalle:

  • Si el EcuM valida un evento, notifica VALIDATED SWS EcuM p. 134.
  • Si la validación no tiene éxito antes del timeout, notifica EXPIRED SWS EcuM p. 63.
  • En la secuencia GoSleep, restablece las fuentes con ECUM_WKSTATUS_NONE SWS EcuM p. 54.
  • En la secuencia Poll, notifica PENDING o VALIDATED según las necesidades de validación SWS EcuM p. 57.

Por cada fuente de wakeup se crea una BswMEcuMWakeupSource Mode-Mgmt-Guide p. 29.

Diagrama de estados: Estados de una fuente de wakeup en el EcuM; cada entrada genera una notificación al BswM. Fuentes: [SWS_BswM_00131], SWS EcuM p. 60, SWS EcuM p. 57, SWS EcuM p. 63

Control de la comunicación: buses, Partial Networks, diagnóstico y servicios

Un caso de uso típico es la habilitación de grupos de I-PDU. En la guía, una regla sobre una indicación de CanSM activa los grupos de I-PDU de un canal CAN Mode-Mgmt-Guide p. 32. Para ello, CanSM notifica los estados CANSM_BSWM_NO_COMMUNICATION, CANSM_BSWM_SILENT_COMMUNICATION, CANSM_BSWM_FULL_COMMUNICATION y CANSM_BSWM_BUS_OFF [SWS_BswM_00049], Mode-Mgmt-Guide p. 22. Notifica el estado FULL_COMMUNICATION, por ejemplo, ante el efecto E_TX_ON SWS CanSM p. 65.

Para Partial Networks, ComM notifica cada cambio de estado de un PNC a través de BswM_ComM_CurrentPNCMode [SWS_BswM_00148], SWS ComM p. 35. Con ello, el BswM conmuta grupos de puertos de switch Ethernet Mode-Mgmt-Guide p. 49:

  • Conoce la asignación de PNC a EthIfSwitchPortGroup.
  • Invoca EthIf_SwitchPortGroupRequestMode con ETH_MODE_ACTIVE o ETH_MODE_DOWN.
  • EthIf devuelve el estado de enlace resultante del grupo mediante BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001], SWS EthIf p. 92.

Diagrama de secuencias: La solicitud y liberación de PNC conmutan un grupo de puertos Ethernet mediante reglas del BswM; EthIf devuelve el estado de enlace determinado al BswM. Fuentes: [SWS_BswM_00148], [SWS_BswM_91001], Mode-Mgmt-Guide p. 49, SWS EthIf p. 92

El diagnóstico también realiza notificaciones al BswM:

  • Servicio UDS 0x28 (CommunicationControl): el DCM invoca BswM_Dcm_CommunicationMode_CurrentState por cada red afectada [SWS_BswM_00048], SWS DCM p. 147. El comportamiento se configura mediante BswMDcmComModeRequest; su BswMDcmComMChannelRef corresponde al argumento Network SWS BswM p. 64.
  • Salto al bootloader: si durante el proceso se actualizó la aplicación, el DCM notifica BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], SWS DCM p. 231.
  • J1939: BswM_J1939DcmBroadcastStatus transfiere una máscara de bits por ComMChannelId que solo cubre los primeros 16 canales [SWS_BswM_00165], SWS BswM p. 70. En función de los estados de J1939Nm, el BswM conmuta grupos de I-PDU de Com, grupos de rutas de enrutamiento de PduR y el procesamiento de peticiones del J1939Rm Mode-Mgmt-Guide p. 45.

Service Discovery notifica los estados de Client Services, Consumed Eventgroups y Event Handlers [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]. Para el Sd, estas llamadas son interfaces opcionales SWS Sd p. 122.

Comportamiento en caso de error

Si BswMDevErrorDetect está activo, las API de entrada comprueban en primer lugar si el BswM está inicializado. En caso contrario, ignoran la solicitud y notifican BSWM_E_UNINIT al DET, por ejemplo [SWS_BswM_00080], [SWS_BswM_00081], [SWS_BswM_00149], [SWS_BswM_00112], [SWS_BswM_00086], [SWS_BswM_00132]. Además, comprueban si los valores transferidos se encuentran dentro del rango permitido. En caso de infracción, la solicitud también se ignora y se notifica BSWM_E_REQ_MODE_OUT_OF_RANGE, como por ejemplo [SWS_BswM_00095], [SWS_BswM_00097], [SWS_BswM_00150], [SWS_BswM_00113], [SWS_BswM_00110], [SWS_BswM_00154]. Si se invoca BswM_MainFunction antes de la inicialización, regresa de inmediato sin notificar ningún error [SWS_BswM_00076].

Los códigos de error de desarrollo del BswM según [SWS_BswM_00230]:

ErrorCódigoValor
Llamada antes de la inicializaciónBSWM_E_UNINIT0x01
Puntero nulo transferidoBSWM_E_NULL_POINTER0x02
Parámetro no válido (no específico)BSWM_E_PARAM_INVALID0x03
Usuario solicitante fuera de rangoBSWM_E_REQ_USER_OUT_OF_RANGE0x04
Modo solicitado fuera de rangoBSWM_E_REQ_MODE_OUT_OF_RANGE0x05
Configuración incoherenteBSWM_E_PARAM_CONFIG0x06

Si una acción devuelve E_NOT_OK, el BswM notifica el error de tiempo de ejecución BSWM_E_ACTION_FAILED. El valor se encuentra entre 0x80 y 0xFF y se configura en BswMReportFailRuntimeErrorId [SWS_BswM_00238]. El BswM rechaza configuraciones que para un BswMModeInitValue contienen tanto BswMBswModeInitValue como BswMCompuScaleModeValue SWS BswM p. 30. Es probable que el código BSWM_E_REQ_USER_OUT_OF_RANGE sirva para la comprobación de requesting_user en BswM_RequestMode. Se trata de una interpretación, ya que el pasaje correspondiente está cortado en el payload [SWS_BswM_00230], SWS BswM p. 86.

Los errores de otros módulos llegan al BswM como entradas normales:

  • Bus-off: CanSM notifica primero CANSM_BSWM_BUS_OFF al BswM y, a continuación, COMM_SILENT_COMMUNICATION a ComM. Además, establece un evento DEM en PRE_FAILED SWS CanSM p. 70, Error-Description p. 19.
  • Reinicio de partición: el WdgM lo solicita mediante BswM_WdgM_RequestPartitionReset [SWS_BswM_00157], Mode-Mgmt-Guide p. 30.
  • Reinicio de la partición de BswM: después se invoca BswM_BswMPartitionRestarted [SWS_BswM_00193]. Las reglas pueden reinicializar entonces de forma selectiva los módulos de esta partición Mode-Mgmt-Guide p. 38.
