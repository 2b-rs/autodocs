Gestiona bloques de datos no volátiles y los sincroniza de forma asíncrona entre la RAM y la memoria NV.

El NVRAM Manager (NvM) es el único acceso a la memoria no volátil. Copia bloques de NVRAM de forma implícita entre la RAM y la memoria NV [SWS_NvM_00038]. En el arranque, NvM_ReadAll, iniciado por el BswM, llena los bloques de RAM; en el shutdown, NvM_WriteAll guarda los bloques modificados. Las peticiones individuales como NvM_WriteBlock se encolan de forma asíncrona, se procesan por prioridad y se confirman mediante estado o callback [SWS_NvM_00185]. El NvM subsana los errores de lectura mediante reintentos, copias redundantes y datos por defecto; no obstante, los usuarios deben comprobar ellos mismos el estado del bloque.

El NVRAM Manager (NvM) es el único acceso a la memoria no volátil [SWS_NvM_00384]. Copia bloques de forma implícita entre la NVRAM y la RAM; la aplicación trabaja directamente con los datos de la RAM [SWS_NvM_00038]. Hacia abajo utiliza la Memory Abstraction Interface con Fee o Ea [SWS_NvM_00051]. Notifica los estados al BswM y los errores al DEM y al DET [SWS_NvM_00745] [SWS_NvM_00592].

Diagrama de contexto: integración del NvM entre usuarios, BswM, MemIf/Fee/Ea así como DEM y DET. Fuentes: [SWS_NvM_00384] [SWS_NvM_00465] [SWS_NvM_00746]

Cada bloque de NVRAM consta de un bloque NV, un bloque de RAM y un Administrative Block, complementado opcionalmente con un bloque ROM con datos por defecto [SWS_NvM_00138]. Existen los tipos Native, Redundant y Dataset; se diferencian en el número de bloques NV y ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559]. El NvM sincroniza el bloque de RAM de forma implícita directamente o de forma explícita a través de un RAM mirror con callbacks [SWS_NvM_00511].

El ciclo de vida transcurre en tres pasos:

  • El BswM llama a NvM_Init en exclusiva [SWS_NvM_00693].
  • NvM_ReadAll comprueba primero el ID de configuración y después llena los bloques de RAM [SWS_NvM_00073] [SWS_NvM_00718].
  • Para el shutdown, NvM_WriteAll guarda los bloques modificados [SWS_NvM_00092]. NvM_CancelWriteAll se cancela de forma no destructiva [SWS_NvM_00238].

Las peticiones individuales como NvM_WriteBlock se encolan y pasan a estar en NVM_REQ_PENDING [SWS_NvM_00185]. Opcionalmente, el NvM utiliza una cola propia para peticiones Immediate [SWS_NvM_00378]. El resultado lo proporciona NvM_GetErrorStatus o un callback configurado [SWS_NvM_00015] [SWS_NvM_00740].

Diagrama de secuencia: se encola una petición de escritura asíncrona, se procesa en NvM_MainFunction y se confirma mediante callback, notificación al BswM y consulta de estado. Fuentes: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00891], SWS NvM p. 160

El NvM subsana los errores de lectura a través de tres niveles:

  • reintentos de lectura configurados [SWS_NvM_00526],
  • la segunda copia de bloques redundantes [SWS_NvM_00199],
  • datos por defecto con el resultado NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202].

Interpretación: es probable que el orden de los niveles siga la enumeración de la Error Description. El NvM reintenta los errores de escritura hasta NVM_MAX_NUM_OF_WRITE_RETRIES y después notifica NVM_E_REQ_FAILED al DEM [SWS_NvM_00684]. Los usuarios comprueban ellos mismos el estado de sus bloques [SWS_NvM_00694].

Rol en la pila de memoria: único acceso a la memoria no volátil

El NVRAM Manager (NvM) centraliza el acceso a los datos no volátiles. El entorno accede a la memoria no volátil exclusivamente a través del NvM, que proporciona para ello una interfaz de callback [SWS_NvM_00384]. El acceso es implícito: el NvM copia bloques entre la NVRAM y la RAM compartida. La aplicación trabaja directamente con los datos de la RAM respetando las reglas de sincronización [SWS_NvM_00038] [SWS_NvM_00692]. Un bloque se selecciona mediante su Block ID configurado [SWS_NvM_00069] [SWS_NvM_00471]. Las capas superiores solo incluyen para ello NvM.h [SWS_NvM_00691]. El gráfico sobre la actualización implícita muestra la división del trabajo: otras partes del software básico activan el guardado y la restauración de todos los bloques en función del estado de la ECU. La SW-C solo accede al contenido de sus bloques de RAM (SWS NvM p. 121).

Hacia abajo, el NvM trabaja contra la Memory Abstraction Interface. Junto con Fee o Ea, proporciona un espacio de direcciones virtual lineal de 32 bits [SWS_NvM_00051] [SWS_NvM_00465]. El NvM genera sumas de comprobación a través del módulo Crc [SWS_NvM_00466]. Se informa de la finalización de un trabajo de la capa inferior por dos vías:

  • por sondeo mediante MemIf_GetJobResult,
  • con el sondeo desactivado, a través de NvM_JobEndNotification y NvM_JobErrorNotification [SWS_NvM_00440] [SWS_NvM_00441] (Error Description p. 43).

Los errores de producción se envían al DEM [SWS_NvM_00592] y los errores de desarrollo al DET [SWS_NvM_00614]. El NvM notifica los estados de las peticiones al BswM [SWS_NvM_00745] [SWS_NvM_00746].

Diagrama de contexto: el NvM intermedia entre los usuarios y el BswM por un lado y MemIf/Fee/Ea por el otro. Notifica los errores a DEM y DET. Fuentes: [SWS_NvM_00384] [SWS_NvM_00745] [SWS_NvM_00746] [SWS_NvM_00465] [SWS_NvM_00466], Error Description p. 43

Estructura de un bloque de NVRAM y los tres tipos de gestión

Un bloque de NVRAM consta de los componentes obligatorios bloque NV, bloque de RAM y Administrative Block. Un bloque ROM con datos por defecto es opcional [SWS_NvM_00138] [SWS_NvM_00139] [SWS_NvM_00020]. La composición la define el descriptor de bloque en tiempo de configuración [SWS_NvM_00140]. Los componentes individuales:

  • El bloque NV contiene los datos útiles y, opcionalmente, CRC y cabecera [SWS_NvM_00125] (SWS NvM p. 39).
  • El bloque de RAM puede ubicarse sin restricción de direcciones en la RAM global [SWS_NvM_00088].
  • El Administrative Block es invisible para la aplicación. Contiene el índice de dataset, los atributos y el campo de error/estado [SWS_NvM_00134] [SWS_NvM_00135] [SWS_NvM_00136].

El NvM admite los tipos NVM_BLOCK_NATIVE, NVM_BLOCK_REDUNDANT y NVM_BLOCK_DATASET [SWS_NvM_00137]. Se diferencian en el número de bloques NV y ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559] (SWS NvM p. 10). En los bloques de Dataset se aplica lo siguiente:

  • NvM_SetDataIndex selecciona el elemento. Los índices a partir de NvMNvBlockNum direccionan bloques ROM [SWS_NvM_00014] [SWS_NvM_00445] (NV Data Handling p. 10).
  • El índice no se guarda de forma persistente; NvM_Init lo pone a cero [SWS_NvM_00160] [SWS_NvM_00192].
  • La SW-C es responsable de configurarlo correctamente [SWS_NvM_00695].

Ciclo de vida: NvM_Init, NvM_ReadAll y NvM_WriteAll

El BswM llama a NvM_Init en exclusiva [SWS_NvM_00693]. NvM_Init restablece colas y máquinas de estados y señaliza internamente «INIT DONE» [SWS_NvM_00399]. No inicializa ni bloques de RAM ni módulos subordinados [SWS_NvM_00091] [SWS_NvM_00193]. El puntero de configuración es siempre NULL_PTR [SWS_NvM_00881]. Solo después de esto NvM_MainFunction procesa peticiones [SWS_NvM_00257].

A continuación, NvM_ReadAll llena los bloques de RAM [SWS_NvM_00718]. La llamada solo señaliza la petición. El procesamiento se pospone hasta que se completen las peticiones de bloque individuales [SWS_NvM_00243]. Después, el trabajo se ejecuta en tres pasos:

  1. Primero compara el ID de configuración guardado con el compilado [SWS_NvM_00073]. En caso de discrepancia, el comportamiento depende de NvMDynamicConfiguration: con NvMDynamicConfiguration == FALSE se ignora la discrepancia [SWS_NvM_00248]. De lo contrario, los bloques no resistentes a cambios reciben datos por defecto [SWS_NvM_00249] [SWS_NvM_00674] (NV Data Handling p. 15).
  2. Luego itera sobre los bloques de usuario excepto los Block ID 0 y 1 [SWS_NvM_00244]. Durante esto, solo procesa bloques con bloque de RAM permanente o sincronización explícita [SWS_NvM_00118].
  3. Por último, establece el resultado global en NVM_REQ_OK o NVM_REQ_NOT_OK [SWS_NvM_00895] [SWS_NvM_00301].

En el ejemplo de gestión de modos, la regla de BswM NvMReadAllFinished inicia el resto de la inicialización solo tras finalizar NvM_ReadAll (Mode Management Guide p. 31).

Diagrama de secuencia: inicio asíncrono con NvM_Init, NvM_ReadAll y notificación del estado multibloque al BswM. Fuentes: [SWS_NvM_00693] [SWS_NvM_00243] [SWS_NvM_00073] [SWS_NvM_00888] [SWS_NvM_00889], NV Data Handling p. 20

Para el shutdown, el BswM llama a NvM_WriteAll [SWS_NvM_00092]. El trabajo se comporta de la siguiente manera:

  • Escribe bloques de RAM permanentes u obtiene datos sincronizados explícitamente mediante NvM_WriteRamBlockToNvm [SWS_NvM_00252].
  • Previamente comprueba el estado «valid/modified» [SWS_NvM_00682].
  • Omite los bloques protegidos y bloqueados sin notificación de error [SWS_NvM_00434] [SWS_NvM_00750].
  • Otras peticiones no lo interrumpen [SWS_NvM_00567].

Los usuarios marcan los bloques modificados con NvM_SetRamBlockStatus(…, TRUE), siempre que la API esté habilitada [SWS_NvM_00406] [SWS_NvM_00408]. En los bloques con dirty flag, la RTE asume esta llamada (NV Data Handling p. 41).

NvM_CancelWriteAll está reservado para el BswM [SWS_NvM_00703] y no tiene efecto si no hay un NvM_WriteAll en ejecución [SWS_NvM_00233]. El bloque actual se finaliza de forma no destructiva [SWS_NvM_00238]. Los bloques restantes y el resultado multibloque reciben NVM_REQ_CANCELED [SWS_NvM_00236] [SWS_NvM_00237] (SWS NvM p. 161).

Otras dos peticiones multibloque complementan el ciclo de vida:

  • NvM_ValidateAll establece los bloques con validación automática en «VALID / CHANGED» [SWS_NvM_00856].
  • NvM_FirstInitAll sobrescribe los bloques con datos por defecto o los invalida si no hay ninguno disponible [SWS_NvM_00913] [SWS_NvM_00919].

Para todas las peticiones multibloque se aplica una longitud de cola de uno [SWS_NvM_00380].

Diagrama de secuencia: shutdown con NvM_WriteAll y cancelación opcional mediante NvM_CancelWriteAll. Fuentes: [SWS_NvM_00092] [SWS_NvM_00682] [SWS_NvM_00238] [SWS_NvM_00237] [SWS_NvM_00889], Mode Management Guide p. 37

Peticiones individuales: colas, prioridades y confirmación

Las peticiones de bloque individual como NvM_ReadBlock, NvM_WriteBlock o NvM_RestoreBlockDefaults son asíncronas. La función toma los parámetros, encola la petición y retorna [SWS_NvM_00195] [SWS_NvM_00208] [SWS_NvM_00224]. Después, el resultado del bloque se encuentra en NVM_REQ_PENDING [SWS_NvM_00185]. En caso de desbordamiento de la cola, la función devuelve E_NOT_OK [SWS_NvM_00184]. Un bloque solo se encola si no está ya pendiente o siendo procesado [SWS_NvM_00385].

Otros servicios operan de forma síncrona en el contexto del llamante, como NvM_SetDataIndex [SWS_NvM_00448] y NvM_GetErrorStatus (SWS NvM p. 158). NvM_CancelJobs elimina las peticiones pendientes de un bloque; sin embargo, un trabajo en ejecución continúa [SWS_NvM_00536] [SWS_NvM_00537].

El procesamiento se realiza serializado según la prioridad [SWS_NvM_00162]. Si NvMJobPrioritization está activo, el NvM utiliza dos colas, una de ellas para peticiones de escritura Immediate (datos de colisión) [SWS_NvM_00564] [SWS_NvM_00378]. Dicho NvM_WriteBlock cancela destructivamente un trabajo pendiente [SWS_NvM_00300]. A continuación, NvM_MainFunction reinicia el trabajo cancelado [SWS_NvM_00258]. Sin priorización, el NvM trabaja en orden de llegada, sin trabajos Immediate [SWS_NvM_00379]. Las peticiones que llegan durante una petición multibloque se encolan y se ejecutan a continuación [SWS_NvM_00568] [SWS_NvM_00569].

Cada petición asíncrona guarda su resultado en el campo de error/estado [SWS_NvM_00175]. NvM_GetErrorStatus lee este campo [SWS_NvM_00015]. Además, existen dos vías de notificación opcionales:

  • Si hay un callback configurado, NvM_MainFunction llama a NvM_SingleBlockCallbackFunction [SWS_NvM_00740] [SWS_NvM_00347]. Sin callback no hay notificación asíncrona [SWS_NvM_00742] (SWS NvM p. 160).
  • Con NvMBswMBlockStatusInformation, el NvM notifica la aceptación y el resultado al BswM [SWS_NvM_00890] [SWS_NvM_00891] (SWS NvM p. 162).

Diagrama de secuencia: petición de escritura asíncrona con notificaciones de estado al BswM, callback y consulta de estado. Fuentes: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00740] [SWS_NvM_00890] [SWS_NvM_00891], SWS NvM p. 160

Sincronización del bloque de RAM y estado del bloque

El NvM dispone de dos formas de sincronizar datos con el bloque de RAM de la aplicación. Con la sincronización implícita, opera directamente sobre este bloque de RAM. La aplicación proporciona el bloque y no accede a él hasta el final de la petición [SWS_NvM_00698] [SWS_NvM_00699]. Si pasa NULL_PTR, el NvM utiliza el bloque de RAM permanente [SWS_NvM_00898] [SWS_NvM_00900]. Aun así, es posible utilizar un bloque temporal mediante puntero [SWS_NvM_00278]. Los servicios PRAM operan siempre sobre el bloque de RAM permanente [SWS_NvM_00765] [SWS_NvM_00794]. En el escenario RTE, este bloque es una Per-Instance-Memory (NV Data Handling p. 32).

Con la sincronización explícita (NvMBlockUseSyncMechanism), el intercambio se realiza a través de un RAM mirror interno [SWS_NvM_00511]. Existe exactamente uno de ellos, dimensionado según el bloque afectado más grande [SWS_NvM_00513]. El NvM llama a NvMWriteRamBlockToNvCallback o NvMReadRamBlockFromNvCallback [SWS_NvM_00515] [SWS_NvM_00516]. Si un callback devuelve E_NOT_OK, repite la llamada en el siguiente ciclo, hasta NvMRepeatMirrorOperations veces [SWS_NvM_00579] [SWS_NvM_00840]. Hasta el callback, la aplicación aún puede modificar el bloque de RAM [SWS_NvM_00705]. Un bloque utiliza o bien sincronización explícita o bien un bloque de RAM permanente, no ambos [SWS_NvM_00904]. El mecanismo permite bloques compartidos a través de un NvBlockSwComponentType (NV Data Handling p. 12).

Diagrama de secuencia: petición de escritura con sincronización explícita a través del RAM mirror, incluida la repetición en caso de E_NOT_OK. Fuentes: [SWS_NvM_00515] [SWS_NvM_00705] [SWS_NvM_00579] [SWS_NvM_00840], NV Data Handling p. 27

Para los bloques de RAM permanentes o el mirror, el NvM mantiene un estado «valid»/«invalid» [SWS_NvM_00128] [SWS_NvM_00132]. Las transiciones en detalle:

  • NvM_ReadBlock invalida el bloque de RAM permanente ya en el momento de encolarlo [SWS_NvM_00198].
  • Tras una lectura correcta, pasa a estar «valid/unchanged» [SWS_NvM_00200].
  • Tras cargar datos por defecto, pasa a estar «valid/changed» [SWS_NvM_00366].
  • NvM_SetRamBlockStatus(…, TRUE) lo marca como modificado y desencadena un nuevo cálculo del CRC en segundo plano [SWS_NvM_00406] [SWS_NvM_00121].
  • Tras una escritura correcta, se considera «valid/unmodified» [SWS_NvM_00472].

Diagrama de estados: estados del bloque de RAM y los eventos desencadenantes. Fuentes: [SWS_NvM_00198] [SWS_NvM_00200] [SWS_NvM_00366] [SWS_NvM_00406] [SWS_NvM_00472] [SWS_NvM_00856]

Configuración, mecanismos de protección y relación con particiones

Para recursos limitados existen tres clases de configuración de la API [SWS_NvM_00149]. La clase 1 no admite bloques Dataset [SWS_NvM_00365]. Las tablas de descriptores se generan [SWS_NvM_00143]. Los usuarios declaran las necesidades de memoria en tiempo de configuración [SWS_NvM_00030]. Los módulos BSW lo hacen a través de NvBlockNeeds (BSWMD Template p. 241). El integrador de la ECU deriva de ello la configuración del NvM (Methodology p. 444).

Para bloques individuales se dispone de varios mecanismos de protección:

  • Un campo de atributos gestiona la protección contra escritura [SWS_NvM_00054]; NvMBlockWriteProt la activa por defecto [SWS_NvM_00326].
  • Los bloques con NvMWriteBlockOnce solo se escriben una vez [SWS_NvM_00397]. El NvM rechaza las peticiones de escritura anteriores a la primera lectura [SWS_NvM_00952].
  • Para bloques bloqueados (NvM_SetBlockLockStatus), NvM_WriteBlock devuelve E_NOT_OK [SWS_NvM_00749]. El bloqueo no lo modifican ni NvM_SetRamBlockStatus ni NvM_SetBlockProtection [SWS_NvM_00754].
  • También son opcionales una cabecera Static Block ID [SWS_NvM_00522], una comparación de CRC para evitar escrituras innecesarias [SWS_NvM_00849] y cifrado a través del CSM [SWS_NvM_00976].

En caso de particionamiento, el NvM llama a las interfaces en el contexto de la partición asignada respectivamente. Las funciones generales se ejecutan en la partición maestra [SWS_NvM_00969]. NvM_ReadAll y NvM_WriteAll solo las ofrece el maestro [SWS_NvM_00970] [SWS_NvM_00971] [SWS_NvM_CONSTR00974]. Las SW-C acceden al NvM a través de puertos vinculados a bloques:

  • PS_{Block} (Service) [SWS_NvM_00847]
  • PAdmin_{Block} (Administration) [SWS_NvM_00843]
  • PM_{Block} (Mirror) [SWS_NvM_00844]
  • PNJF_{Block} (notificación de fin de trabajo) [SWS_NvM_00846]

Comportamiento en caso de error

Durante la lectura, el NvM evalúa los mensajes de la MemIf de forma diferenciada:

  • Notifica una discrepancia de CRC como NVM_E_INTEGRITY_FAILED [SWS_NvM_00203].
  • Notifica MEMIF_JOB_FAILED como NVM_E_REQ_FAILED [SWS_NvM_00654].
  • MEMIF_BLOCK_INVALID solo da lugar a NVM_REQ_NV_INVALIDATED, sin notificación al DEM [SWS_NvM_00341] [SWS_NvM_00652].

A continuación intervienen varios niveles de recuperación:

  1. En caso de errores de CRC, se producen los reintentos de lectura configurados [SWS_NvM_00526].
  2. En los bloques redundantes, el NvM lee la segunda copia e intenta restaurar la redundancia [SWS_NvM_00199] [SWS_NvM_00531]. Si esto falla, notifica NVM_E_LOSS_OF_REDUNDANCY [SWS_NvM_00546].
  3. Por último, el NvM carga datos por defecto con el resultado NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202]. El contenido de NV permanece inalterado [SWS_NvM_00172].

Si faltan datos por defecto, el bloque de RAM permanece no válido [SWS_NvM_00658] [SWS_NvM_00204]. Interpretación: es probable que el orden de los niveles siga la enumeración de la Error Description (Error Description p. 62). Esta fuente discrepa en dos puntos respecto a los requisitos. Menciona NVM_REQ_RESTORED_FROM_ROM en lugar de NVM_REQ_RESTORED_DEFAULTS. Además, resume el fallo definitivo de forma genérica como NVM_E_REQ_FAILED. Tienen carácter normativo los requisitos citados anteriormente.

Diagrama de actividades: tratamiento de errores de lectura desde el reintento hasta los datos por defecto, pasando por la copia redundante. Interpretación: el orden sigue la enumeración de la Error Description. Fuentes: [SWS_NvM_00526] [SWS_NvM_00199] [SWS_NvM_00202] [SWS_NvM_00341] [SWS_NvM_00658], Error Description p. 62

Durante la escritura, el NvM cuenta las respuestas negativas hasta NVM_MAX_NUM_OF_WRITE_RETRIES [SWS_NvM_00213] [SWS_NvM_00216]. Si se supera el límite, establece NVM_REQ_NOT_OK y notifica NVM_E_REQ_FAILED [SWS_NvM_00683] [SWS_NvM_00684] (Error Description p. 43). Otros dos patrones de error:

  • Si falla la verificación de escritura, el NvM notifica NVM_E_VERIFY_FAILED y repite la escritura [SWS_NvM_00528] [SWS_NvM_00529].
  • Un bloque redundante se considera escrito en cuanto una copia ha sido correcta [SWS_NvM_00284].

En caso de manejo incorrecto, el NvM notifica al DET si la detección de errores de desarrollo está habilitada. Ejemplos de ello son NVM_E_UNINIT y NVM_E_BLOCK_PENDING [SWS_NvM_00614] [SWS_NvM_00615], así como NVM_E_WRITE_PROTECTED [SWS_NvM_00962]. Una petición multibloque finaliza con NVM_REQ_NOT_OK en cuanto falla un solo bloque [SWS_NvM_00318]. Los usuarios comprueban ellos mismos el estado de sus bloques [SWS_NvM_00694]. Tras una lectura fallida, proporcionan datos válidos antes de la siguiente escritura [SWS_NvM_00696].
