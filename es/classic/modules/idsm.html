Función y límite del sistema: del evento de sensor al Security Event cualificado

El Intrusion Detection System Manager (IdsM) es el módulo BSW de la Classic Platform que recibe eventos de seguridad integrados (SEv) a través de una interfaz estandarizada. Los filtra según reglas configurables para convertirlos en eventos cualificados (QSEv) y a continuación los almacena o envía SWS IdsM p. 7. Como sensores emiten notificaciones módulos BSW, CDDs propietarios y SW-Cs. Los sumideros son el IDS Reporter (IdsR), alcanzado a través de PduR, así como DEM/Sem para el almacenamiento local SWS IdsM p. 16 [SWS_IdsM_01202] [SWS_IdsM_01601].

El IdsM no evalúa expresamente si un sistema está realmente comprometido. Desconoce el significado de los datos de contexto; la detección y la reacción se sitúan fuera del módulo, por ejemplo en un SOC [SWS_IdsM_CONSTR_00001]. La especificación asume además que los SEvs se descarten en función de la frecuencia de notificación o la carga del sistema SWS IdsM p. 11.

Otros módulos vecinos y sus funciones:

  • DET: errores de desarrollo
  • DCM: acceso de diagnóstico al Reporting Mode
  • NvM: persistencia del Reporting Mode
  • BswM: suministrador del Block State
  • StbM o bien una SW-C: fuente de marcas de tiempo
  • CSM: firmas
  • BSW Scheduler: llamada cíclica

Referencias: SWS IdsM p. 13. La inclusión de unos u otros encabezados depende de los correspondientes conmutadores de configuración, p. ej., Det.h con IdsMDevErrorDetect y PduR.h con IdsMSinkIdsR [SWS_IdsM_00101] [SWS_IdsM_00105].

Diagrama de contexto: el IdsM se sitúa entre los sensores (BSW/CDD directamente, SW-C a través de la RTE) y los sumideros IdsR (a través de PduR) o DEM/Sem. Los módulos de control y soporte son BswM, DCM, NvM, StbM, CSM y DET. Fuentes: SWS IdsM p. 20, SWS IdsM p. 13, [SWS_IdsM_91027], [SWS_IdsM_91028].

Ciclo de vida: inicialización y procesamiento cíclico

IdsM_Init inicializa todas las variables internas y pone el módulo en el estado «inicializado» [SWS_IdsM_00202] [SWS_IdsM_91001]. Una nueva llamada en el estado inicializado no reinicializa. Con IdsMDevErrorDetect activo, notifica en su lugar IDSM_E_ALREADY_INITIALIZED [SWS_IdsM_00204]. En estado no inicializado, cualquier API salvo IdsM_Init y IdsM_GetVersionInfo genera un error de DET [SWS_IdsM_00203].

El trabajo real transcurre de forma asíncrona. IdsM_MainFunction se llama periódicamente y procesa los eventos que se pusieron en cola durante las llamadas a la API [SWS_IdsM_91000] SWS IdsM p. 19. El periodo IdsMMainFunctionPeriod es a la vez la base temporal de todos los filtros de intervalo. Sus intervalos deben ser múltiplos de este periodo y comienzan con la primera llamada a la MainFunction [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01064] [SWS_IdsM_01065].

Diagrama de estados: solo IdsM_Init hace que el módulo sea utilizable. Las llamadas erróneas en ambos estados se notifican a DET sin cambiar de estado. Fuentes: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], [SWS_IdsM_91000].

Notificación de Security Events: identidad, variantes de API y almacenamiento en búfer

Cada instancia de SEv se describe mediante cuatro datos: IdsMExternalEventId, IdsMSensorInstanceId, un IdsMInternalEventId calculado internamente y el nombre del evento [SWS_IdsM_00600] [SWS_IdsM_00601]. Para su utilización rigen las siguientes reglas (SWS IdsM p. 21):

  • Los sensores utilizan exclusivamente la constante simbólica del contenedor IdsMEvent, nunca el valor numérico interno [SWS_IdsM_00602] [SWS_IdsM_00607].
  • El ID externo 0xFFFF no es válido [SWS_IdsM_00604].
  • Si solo existe una instancia del módulo, la instancia del sensor es 0 por defecto [SWS_IdsM_00608].

Para la notificación se dispone de seis servicios síncronos y no reentrantes. Se diferencian por los datos adicionales facilitados. Las variantes con contador y marca de tiempo están orientadas a Smart Sensors (SW-C o CDD) que determinan estos valores por sí mismos SWS IdsM p. 19. Si solo se dispone de una marca de tiempo sin contador propio, se transfiere count = 1 [SWS_IdsM_00405].

Los datos de contexto se transfieren como puntero a una matriz de bytes y pueden tener una longitud de hasta 1500 bytes [SWS_IdsM_00501] [SWS_IdsM_00502]. Para los sensores SW-C se aplican dos parámetros adicionales SWS IdsM p. 37:

  • IdsMEventMaxContextDataSize limita la cantidad de datos de contexto [SWS_IdsM_01300].
  • IdsMAdditionalParameterOption (None, Count, CountTimestamp) determina qué parámetros ofrece la Service-Port-Interface [SWS_IdsM_01301] [SWS_IdsM_01303].

Al recibirlos, el IdsM almacena el SEv en un Event Buffer [SWS_IdsM_00702]. Los datos de contexto se guardan en un Context Data Buffer del mismo tamaño o inmediatamente superior, que se vincula con el Event Buffer [SWS_IdsM_00705] [SWS_IdsM_00706]. Sin datos de contexto no se ocupa ningún búfer de contexto [SWS_IdsM_00709]. La cantidad y los tamaños de los búferes son configurables [SWS_IdsM_00701] [SWS_IdsM_00704]. Para la cantidad de Event Buffers, la especificación recomienda: número de instancias de filtros de agregación más el límite superior de eventos procesados en paralelo SWS IdsM p. 22.

Diagrama de secuencia: la notificación en el contexto del sensor solo almacena el SEv en el búfer. La marca de tiempo, el filtrado y la cualificación solo tienen lugar en la llamada cíclica a IdsM_MainFunction (variante con StbM como fuente de tiempo). Fuentes: SWS IdsM p. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01104].

Diagrama de actividades: la falta de un Event Buffer desencadena un SEv interno. La falta de un Context Data Buffer hace que el evento se siga procesando sin datos de contexto. Fuentes: SWS IdsM p. 27, [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708].

Cualificación: Reporting Mode y cadena de filtros

Cada SEv cuenta con un filtro de Reporting Mode obligatorio. No forma parte de la cadena de filtros, sino que está vinculado directamente al evento; su valor predeterminado procede de IdsMReportingModeFilter [SWS_IdsM_01010] [SWS_IdsM_01011] [SWS_IdsM_01012]. Los valores de IdsM_Filters_ReportingModeType significan [SWS_IdsM_91013] SWS IdsM p. 91:

  • IDSM_REPORTING_MODE_OFF: el evento se descarta.
  • IDSM_REPORTING_MODE_BRIEF / IDSM_REPORTING_MODE_DETAILED: notificación sin o con datos de contexto.
  • …_BYPASSING_FILTERS: notificación eludiendo la cadena de filtros.

La cadena de filtros asignada al SEv solo se evalúa después del Reporting Mode [SWS_IdsM_01001] [SWS_IdsM_01002]. Los filtros activados se ejecutan en un orden fijo: Block State, Forward Every Nth, Event Aggregation, Event Threshold [SWS_IdsM_01004]. Si un filtro descarta el SEv, se omite cualquier evaluación posterior [SWS_IdsM_01005] SWS IdsM p. 25. Una cadena de filtros requiere al menos un filtro [SWS_IdsM_CONSTR_00002]. Los distintos filtros funcionan del siguiente modo:

  • Block State: el BswM notifica el estado actual mediante IdsM_BswM_StateChanged. Si este estado pertenece a los IdsMBlockState referenciados, el SEv se descarta [SWS_IdsM_01022] [SWS_IdsM_01023] SWS IdsM p. 28.
  • Forward Every Nth: el primer SEv y, a partir de entonces, cada n-ésimo SEv se reenvían sin modificaciones [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  • Aggregation: los SEvs se retienen durante IdsMEventAggregationTimeInterval. Al final del intervalo sigue adelante un SEv con la suma de todos los contadores; los datos de contexto y la marca de tiempo proceden a elección del primer o del último SEv [SWS_IdsM_01043] [SWS_IdsM_01046] [SWS_IdsM_01047] [SWS_IdsM_01048] [SWS_IdsM_01049] SWS IdsM p. 40.
  • Threshold: mientras la suma de los contadores en el intervalo esté por debajo de IdsMEventThresholdNumber, se descarta; una vez alcanzado el valor umbral, se reenvía. Al finalizar el intervalo, el contador se restablece [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063] SWS IdsM p. 41.

Diagrama de actividades: en primer lugar, el Reporting Mode decide sobre el descarte, la elusión o el filtrado. A continuación, el SEv recorre los filtros activados en un orden fijo hasta que se descarta o se convierte en un QSEv. Fuentes: SWS IdsM p. 35, SWS IdsM p. 24, [SWS_IdsM_01004], [SWS_IdsM_01005], [SWS_IdsM_91013].

Enriquecimiento y reenvío de eventos cualificados

Los QSEvs tienen una estructura fija según el protocolo IDS, con independencia del sumidero [SWS_IdsM_01200]. La configuración determina por cada IdsMEvent qué sumideros se utilizan [SWS_IdsM_01201] SWS IdsM p. 35. Con IdsMSinkIdsR, el QSEv se envía como IDS Message a través de PduR_IdsMTransmit [SWS_IdsM_01203] [SWS_IdsM_01498]. Antes del envío a IdsR intervienen limitaciones a nivel de instancia: la limitación de tasa restringe el número de QSEvs por intervalo, y la limitación de tráfico los bytes por intervalo [SWS_IdsM_01070] [SWS_IdsM_01081] [SWS_IdsM_01091] SWS IdsM p. 32.

La vía de transmisión depende del tamaño SWS IdsM p. 38:

  • Si el IDS Message cabe con firma incluida en una PDU de bus, se utiliza una IF-PDU [SWS_IdsM_01400]; la confirmación llega a través de IdsM_TxConfirmation [SWS_IdsM_01500].
  • En caso contrario, se utilizan TP-PDUs [SWS_IdsM_01401]. El PduR recupera los datos por segmentos a través de IdsM_CopyTxData [SWS_IdsM_01501] y confirma a través de IdsM_TpTxConfirmation [SWS_IdsM_01502].
  • Antes de la confirmación, el IdsM no vuelve a llamar a PduR_IdsMTransmit [SWS_IdsM_01499].

Diagrama de secuencia: tras la limitación, un QSEv se transmite según su tamaño como IF- o TP-PDU. La siguiente transmisión solo puede comenzar tras la confirmación. Fuentes: [SWS_IdsM_01070], [SWS_IdsM_01400], [SWS_IdsM_01401], [SWS_IdsM_01499], [SWS_IdsM_01501], [SWS_IdsM_01502].

Opcionalmente, el IdsM firma cada QSEv. Esto se activa globalmente mediante un trabajo de CSM referenciado a través de IdsMCsmJobReference. La firma se genera a través de Csm_SignatureGenerate; en el caso de trabajos asíncronos, el CSM notifica el resultado a través de IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01208] SWS IdsM p. 36. El sumidero DEM/Sem está identificado en R20-11 como DRAFT; almacena el IDS Message completo [SWS_IdsM_01600] [SWS_IdsM_01602].

Las marcas de tiempo se conmutan globalmente a través de IdsMTimestampOption [SWS_IdsM_01100] [SWS_IdsM_01103] SWS IdsM p. 33. Se aplican las siguientes reglas SWS IdsM p. 34:

  • Si el sensor no proporciona ninguna marca de tiempo, el IdsM la obtiene por sí mismo: en caso de «AUTOSAR» a través de StbM_GetCurrentTime, en caso de «Custom» a través de la interfaz IdsM_CustomTimestamp procedente de una SW-C [SWS_IdsM_01104] [SWS_IdsM_01107] [SWS_IdsM_01109] [SWS_IdsM_01111].
  • Las marcas de tiempo notificadas por el sensor tienen prioridad y se acortan a los 62 bits de menor peso [SWS_IdsM_01108] [SWS_IdsM_01110].
  • Con «None», también se ignoran las marcas de tiempo transferidas [SWS_IdsM_01106].

Un punto abierto de la especificación: [SWS_IdsM_01112] exige el bit de opción de marca de tiempo 0 si las APIs de marca de tiempo se utilizan sin parámetro de marca de tiempo. Cómo se relaciona esto con [SWS_IdsM_01101] es algo que el texto deja sin aclarar.

Diagrama de actividades: la fuente de marcas de tiempo se determina a partir de IdsMTimestampOption y del parámetro notificado. Fuentes: SWS IdsM p. 87, [SWS_IdsM_01104], [SWS_IdsM_01106], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110].

Reporting Mode en tiempo de ejecución: diagnóstico y persistencia de NvM

Si IdsMDiagnosticSupport está activo, el Reporting Mode puede leerse y modificarse a través de DCM [SWS_IdsM_01800] [SWS_IdsM_01900] [SWS_IdsM_02000] SWS IdsM p. 40:

  • La lectura se realiza en dos fases: IdsM_Dcm_GetReportingMode_Start inicia la rutina, IdsM_Dcm_GetReportingMode_RequestResults suministra el resultado a través de un puntero [SWS_IdsM_02001] [SWS_IdsM_02002].
  • La modificación se realiza a través de IdsM_Dcm_SetReportingMode_Start. Un modo no válido o un ID de evento no válido conducen a E_NOT_OK con DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01901] [SWS_IdsM_01902] [SWS_IdsM_01903].

Tras una modificación satisfactoria, el IdsM inicia NvM_WriteBlock [SWS_IdsM_01701]. Si la persistencia falla, restablece el modo al valor anterior y responde con DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905]. En el arranque lee el modo persistido. El bloque NvM debe estar incluido para ello en NvM_ReadAll; si faltan valores de NvM, rige la configuración [SWS_IdsM_01703] [SWS_IdsM_01704] [SWS_IdsM_01705] SWS IdsM p. 39.

Diagrama de secuencia: la lectura se efectúa en dos fases mediante Start y RequestResults. En la modificación se comprueba primero, luego se persiste y, en caso de error, se revierte. Fuentes: [SWS_IdsM_02001], [SWS_IdsM_02002], [SWS_IdsM_01902], [SWS_IdsM_01903], [SWS_IdsM_01701], [SWS_IdsM_01904], [SWS_IdsM_01905].

Comportamiento en caso de error

Con IdsMDevErrorDetect activo, el IdsM notifica errores de desarrollo a DET. Los códigos de error son IDSM_E_PARAM_INVALID (0x0A), IDSM_E_PARAM_POINTER (0x0B), IDSM_E_PARAM_LENGTH (0x0C), IDSM_E_UNINIT (0x0D) y IDSM_E_ALREADY_INITIALIZED (0x0E) [SWS_IdsM_02003]. Atención: [SWS_IdsM_00203] indica IDSM_E_PARAM_UNINIT para llamadas en estado no inicializado. La tabla de errores no incluye este código; en su lugar figura IDSM_E_UNINIT. Las comprobaciones de parámetros en detalle:

  • securityEventId desconocidos en las APIs de notificación, así como count = 0 en las variantes con contador dan lugar a IDSM_E_PARAM_INVALID [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106] SWS IdsM p. 42.
  • Un contextDataSize mayor que el IdsMContextDataBufferSize más grande da lugar a IDSM_E_PARAM_LENGTH [SWS_IdsM_02107] [SWS_IdsM_02108] [SWS_IdsM_02109] SWS IdsM p. 43.
  • Un NULL_PTR no permitido da lugar a IDSM_E_PARAM_POINTER SWS IdsM p. 42.

El IdsM notifica los cuellos de botella en tiempo de ejecución a través de SEvs internos propios, siempre que estén configurados. Disponen de búferes propios y no son filtrados por filtros a nivel de instancia [SWS_IdsM_91015] [SWS_IdsM_00802] [SWS_IdsM_00803] SWS IdsM p. 24. Existen tres SEvs internos:

  • ningún Event Buffer disponible [SWS_IdsM_00703]
  • ningún Context Data Buffer disponible; el SEv se sigue procesando entonces sin datos de contexto [SWS_IdsM_00707] [SWS_IdsM_00708]
  • limitación de tráfico superada [SWS_IdsM_01094]

Si en una modificación de diagnóstico falla la persistencia, se aplica la reversión descrita anteriormente [SWS_IdsM_01905].

El tipo IdsM_Filters_ReportingModeType ([SWS_IdsM_91013]) define los modos de reporte que utiliza el filtro de modo de reporte (reporting mode filter) del módulo IdsM. El tipo base se deriva de uint8 y se proporciona a través del encabezado IdsM_Types.h.

Rango de valores y semántica

El tipo determina cómo o si se reporta un evento de seguridad detectado:

  • IDSM_REPORTING_MODE_OFF (0x00): El evento no se reporta.
  • IDSM_REPORTING_MODE_BRIEF (0x01): El evento se reporta de forma compacta sin datos de contexto.
  • IDSM_REPORTING_MODE_DETAILED (0x02): El evento se reporta detalladamente con datos de contexto incluidos.
  • IDSM_REPORTING_MODE_BRIEF_BYPASSING_FILTERS (0x03): El evento se reporta sin filtrar y sin datos de contexto, eludiendo los filtros.
  • IDSM_REPORTING_MODE_DETAILED_BYPASSING_FILTERS (0x04): El evento se reporta sin filtrar junto con los datos de contexto, eludiendo los filtros.
  • IDSM_REPORTING_MODE_INVALID (0xFF): Identifica un modo de reporte no válido.

Uso y restricciones

Como enumeración o tipo de configuración, IdsM_Filters_ReportingModeType controla la lógica de filtrado y reenvío de eventos de seguridad dentro de la cadena de filtros del IdsM. Al tratarse de una definición de tipo pura, no existen parámetros directos, valores de retorno ni códigos de error específicos de DET/DEM.
