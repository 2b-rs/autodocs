El Adaptive Platform en una oración

La plataforma adaptativa AUTOSAR es un entorno de ejecución orientado a servicios para potentes ordenadores de vehículos: las aplicaciones adaptativas se ejecutan como procesos POSIX independientes, se inician y supervisan dinámicamente y se comunican a través de servicios definidos contractualmente en lugar de señales cableadas estáticamente (EXP PlatformDesign §3.3 «Adaptive Platform – Characteristics», §8.2 «Service Oriented Communication»).

ARA: la interfaz de programación de esta referencia

Todos los espacios de nombres ara::* documentados aquí juntos forman la interfaz ARA (AUTOSAR Runtime for Adaptive Applications). Cada grupo funcional de la plataforma exporta su API C++ en su propio espacio de nombres, desde los tipos básicos en ara::core hasta la comunicación de servicios en ara::com y servicios de plataforma como ara::exec, ara::per o ara::crypto (EXP PlatformDesign §4.1 «Logical view», EXP SWArchitecture §9.1 «Building Block View – Overview»).

Conceptos generales

  • Máquina y amplificador Clúster de software: A Machine es el entorno de ejecución (posiblemente virtualizado); El software se empaqueta como Software Cluster instalable y se actualiza a través de ara::ucm (EXP SWArchitecture §13.4 «Software Cluster», §13.5 «Machine»).
  • Grupos y estados de funciones: Los procesos se asignan a Function Groups; ara::sm indica al Execution Management que inicie/detenga procesos a través de estados del grupo de funciones (EXP SWArchitecture §13.2 «Function Group», EXP PlatformDesign cap. 7 «State Management»).
  • Manifests: La ejecución, la instancia de servicio y el manifiesto de máquina configuran la implementación, el comportamiento de inicio y el enlace del servicio de forma declarativa (EXP PlatformDesign §4.4 «Manifest», EXP SWArchitecture §13.6 «Manifest»).
  • Manejo de errores sin excepciones: Los errores en toda la plataforma se devuelven como ara::core::Result/ErrorCode (EXP PlatformDesign §18.1 «Error Handling», EXP SWArchitecture §13.12 «Error Handling»).
  • Seguridad y seguridad Seguridad como sección transversal: Protección E2E, monitoreo de salud (ara::phm), criptopila, identidad y seguridad. La gestión de acceso, la detección de intrusiones (ara::idsm) y el firewall (ara::fw) protegen la plataforma y la comunicación (EXP PlatformDesign cap. 17 «Safety», EXP SWArchitecture §13.13 «Trusted Platform»).

Interconexiones entre los módulos

Marcos redondeados = módulos; nodos = subámbitos de un módulo (Namespaces o grupos funcionales). Flecha A → B: los puntos de API del subámbito A (firmas, Fields, parámetros) hacen referencia a tipos del subámbito B — determinados a partir de las declaraciones enlazadas de esta referencia; el grosor de la línea corresponde al número de puntos de referencia (número exacto como Tooltip en la flecha). Etiqueta de arista = tipo de interacción con el destino: valores de retorno, resultados asíncronos, gestión de errores, tipos de datos, direccionamiento de instancias, funciones auxiliares; «usa» indica otras referencias de tipos. Flechas gris claro: modelado de servicio mediante ara::com. Todos los nodos están enlazados a las correspondientes páginas de Namespace/clase.

Los fondos son muy pálidos de forma predeterminada para garantizar una buena legibilidad y se vuelven algo más intensos al pasar el cursor:
