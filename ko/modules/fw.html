Functional Cluster로서의 Firewall: 역할 및 시스템 경계

Functional Cluster Firewall(네임스페이스 ara::fw)은 애플리케이션에 정확히 하나의 기능적 프로그래밍 인터페이스를 제공합니다. 이는 메서드 SwitchFirewallState을(를) 포함하는 클래스 ara::fw::FirewallStateSwitchInterface입니다 [AP_SWS_Fw_82008]. 아키텍처 설명에 따르면 이 클러스터는 데몬 기반입니다. 스테레오타입 «aapAPI,aapPortInterface»를 갖는 인터페이스 FirewallStateSwitchInterface을(를) 구현하며, Adaptive Application은 «use» 관계를 통해 이를 사용합니다 EXP SWArchitecture 126쪽. 유스케이스 다이어그램에서는 두 가지 유스케이스를 언급합니다. “Switch Firewall State”는 Adaptive Application에 의해 트리거됩니다. “Report Security Event”에는 Intrusion Detection System Manager가 관여합니다. Operating System은 또 다른 액터로 등장합니다 EXP SWArchitecture 197쪽.

SWS의 아키텍처 개요는 책임을 명확히 구분합니다:

  • Machine Manifest는 필터 규칙을 포함한 Firewall 구성을 제공합니다.
  • FC Firewall은 이를 사용하여 Firewall Engine을 구성합니다.
  • OEM 애플리케이션이 Firewall 상태를 지정합니다.
  • 보안 이벤트(SEv)는 IdsM으로 전달됩니다 SWS Firewall 16쪽.

동일한 구분이 플랫폼 디자인에도 나타납니다 EXP PlatformDesign 97쪽. 따라서 실제 패킷 검사는 API 외부에 위치합니다. 상태 변경 시나리오는 규칙 적용을 Operating System의 작업으로 할당하고 이를 «aapInformative»로 표시합니다 EXP SWArchitecture 232쪽.

컨텍스트 다이어그램: FC Firewall은 매니페스트 구성, 상태를 지정하는 애플리케이션, 실행 엔진 또는 운영체제, 그리고 IdsM 사이를 중재합니다. 출처: SWS Firewall 16쪽, EXP SWArchitecture 126쪽, EXP SWArchitecture 232쪽

상태 종속적 필터링: Firewall 상태 및 필터 규칙

이 개념의 핵심은 상태 종속적 필터링입니다. OEM별 Firewall 상태는 주행, 주차 또는 진단 세션과 같이 서로 다른 네트워크 트래픽이 예상되는 상황을 나타냅니다. 필터 규칙은 하나의 상태에 할당됩니다. 검사 및 필터링을 위해 Firewall은 현재 활성 상태의 규칙만 참조합니다. 애플리케이션은 FC Firewall의 API를 통해 현재 상태를 설정합니다 EXP PlatformDesign 92쪽. C++에서는 이것이 메서드 SwitchFirewallState(EnumT firewallState)입니다 [AP_SWS_Fw_82008].

규칙 자체는 매니페스트의 내용입니다. Foundation 요구사항 다이어그램은 여러 계층에 걸친 필터 체인을 보여줍니다:

  • MAC 주소 및 EtherType을 포함하는 Ethernet,
  • IPv4,
  • 플래그를 통한 상태 감지 기능이 있는 TCP 또는 ICMP,
  • Service ID, Method ID 및 Client ID를 포함하는 SOME/IP RS Firewall 12쪽.

전송 계층에서 매니페스트는 속성 bucketSize 및 refillAmount을(를) 갖는 FirewallRule을(를) 모델링합니다. 여기에 포트 범위 및 checksumVerification을(를) 갖는 TransportLayerRule이(가) 추가되며, 이는 UDP 및 TCP 규칙으로 특화됩니다 TPS Manifest 687쪽.

패킷이 정의된 규칙 중 어느 것과도 일치하지 않으면 Default Action이 적용됩니다. SWS의 R23-11 버전에서는 이렇게 차단된 패킷에 대해 불일치(Mismatch) 프로토콜 계층이 어떻게 결정되는지 추가로 설명합니다. 최하위 네트워크 계층부터 카운트하여 가장 많은 연속 일치 항목을 가진 규칙이 기준이 됩니다. 처음으로 일치하지 않는 계층에서 계층별 SEv가 트리거됩니다 SWS Firewall 31쪽. 이 부분은 R23-11에서 가져온 것이며 페이로드에서 R25-11 요구사항에 의해 다루어지지 않습니다. 따라서 규범적 의무가 아닌 설명으로 읽어야 합니다.

활동 다이어그램: 활성 Firewall 상태의 규칙만 검사됩니다. 일치하는 항목이 없으면 Default Action이 적용되며, 차단된 패킷은 계층별 SEv를 발생시킵니다(R23-11에 따른 표현). 출처: EXP PlatformDesign 92쪽, SWS Firewall 31쪽

InstanceSpecifier에서 상태 변경까지

먼저 애플리케이션이 FirewallStateSwitchInterface의 인스턴스를 생성합니다. 이를 위해 ara::core::InstanceSpecifier을(를) 필요로 하는 명시적 생성자가 사용됩니다. 이는 noexcept이며 스레드 안전(thread-safe)한 것으로 명시되어 있습니다 [AP_SWS_Fw_82002]. 해석: InstanceSpecifier은(는) 매니페스트에서 FirewallStateSwitchInterface(으)로 유형화된 애플리케이션의 RPortPrototype을(를) 나타내는 것으로 보입니다. 매니페스트 다이어그램은 바로 이러한 포트 관계를 설정하지만, 해당 Specifier를 언급하지는 않습니다 TPS Manifest 677쪽.

상태 변경은 SwitchFirewallState(EnumT firewallState)이(가) 트리거합니다. 이 메서드는 noexcept이며 ara::core::Future<void>을(를) 반환합니다 [AP_SWS_Fw_82008]. “Switch Firewall State” 시나리오는 세 단계로 진행 과정을 보여줍니다:

  1. Adaptive Application은 FC Firewall에서 SwitchFirewallState()을(를) 호출합니다.
  2. FC Firewall은 루프 내에서 각 FirewallRule에 대해 Operating System의 applyRule()을(를) 호출합니다.
  3. 그 후 응답이 애플리케이션으로 반환됩니다 EXP SWArchitecture 232쪽.

동일한 시나리오의 R22-11 표현에서도 동일한 프로세스를 보여줍니다 EXP SWArchitecture 158쪽. applyRule()이(가) «aapInformative»로 표시되어 있으므로, 이 루프는 원리를 설명하는 것입니다. 구속력 있는 운영체제 인터페이스를 정의하지는 않습니다 EXP SWArchitecture 232쪽.

시퀀스 다이어그램: 애플리케이션은 인터페이스 인스턴스를 생성하고 상태 변경을 요청합니다. FC Firewall은 각 규칙을 적용하며, 그 결과는 ara::core::Future<void>(으)로 반환됩니다. 출처: [AP_SWS_Fw_82002], [AP_SWS_Fw_82008], EXP SWArchitecture 232쪽

생성된 상태 타입 및 매니페스트 연동

허용되는 Firewall 상태는 고정된 플랫폼 타입을 형성하지 않습니다. 모델링된 각 인터페이스에 대해 네임스페이스 ara::fw::states에 고유한 enum class {<fwssi-sn>} : std::uint32_t이(가) 생성됩니다. 이는 ara/fw/states/{<fwssi-sn>}.h을(를) 통해 포함되며, 열거자 목록은 모델 [AP_SWS_Fw_81001]에서 가져옵니다. 모델링된 각 Firewall 상태에 대해 {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002] 형태의 열거자가 생성됩니다. 해석: [AP_SWS_Fw_81001]에서 이를 FirewallStateSwitchInterface [AP_SWS_Fw_82008]용 상태 타입으로 명시적으로 정의하고 있으므로, SwitchFirewallState의 매개변수 타입 EnumT은(는) 이 생성된 상태 타입을 나타내는 것으로 보입니다.

머신 레벨에서 AdaptiveFirewallModuleInstantiation은(는) Firewall의 머신별 설정을 수집합니다(TPS_MANI_03296, DRAFT 상태). 메타클래스 AdaptiveFirewallToPortPrototypeMapping은(는) 참조 firewall(0..1)을 통해 이 인스턴스화를 애플리케이션 TPS Manifest 677쪽의 RPortPrototype와(과) 연결합니다. 이때 이 메타클래스의 Note에서는 “FirewallModeSwitchInterface”를 언급합니다. 반면 다이어그램과 API에서는 일관되게 FirewallStateSwitchInterface TPS Manifest 677쪽을(를) 사용합니다.

Intrusion Detection System Manager로의 Security Events

Firewall은 상태 전환 외에도 Intrusion Detection System을 지원합니다. 차단된 메시지에 대해 IdsM으로 보고되는 일련의 Security Events가 지정되어 있습니다. IdsM은 이러한 이벤트의 적격성 심사 및 추가 처리를 담당합니다. IdsM은 이를 SOC로 전달하거나 제어기에 영구 저장합니다 EXP PlatformDesign 92쪽. “Report Security Event” 시나리오는 상호 작용 packetBlocked(), handlePacketBlocked(), raiseSecurityEvent() 및 ReportEvent()을(를) 통해 Operating System, FC Firewall 및 IdsM을 연결합니다. 이 중 일부는 «aapInformative»로 표시되어 있습니다 EXP SWArchitecture 232쪽.

Default Action에 의해 차단된 패킷에 대해 R23-11 SWS는 계층별 이벤트를 명시합니다 SWS Firewall 31쪽:

  • Ethernet의 경우 SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

이러한 이벤트 이름은 페이로드에서 R25-11 요구사항에 의해 다루어지지 않습니다. R25-11에 대한 유효성은 최신 SWS와 비교하여 확인해야 합니다 SWS Firewall 31쪽.

시퀀스 다이어그램: 차단된 패킷은 FC Firewall에 의해 Security Event로 변환되어 IdsM에 보고됩니다. 세부 단계의 순서는 다이어그램 텍스트로부터 해석된 것입니다. 출처: EXP SWArchitecture 232쪽, EXP PlatformDesign 92쪽

오류가 발생한 경우의 동작

SwitchFirewallState에 대해 FwErrc::kServiceNotAvailable 및 FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]의 두 가지 오류가 지정되어 있습니다. 해당 값은 열거형 FwErrc, 구체적으로는 kServiceNotAvailable=1 및 kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]에 의해 정의됩니다. 이 메서드는 noexcept이며 ara::core::Future<void>을(를) 반환합니다. 따라서 호출자는 호출 시의 예외가 아닌 Future를 통해 이러한 오류를 평가합니다 [AP_SWS_Fw_82008].

두 오류 모두 FwErrorDomain에 속합니다. 이 도메인은 다음 구성 요소를 제공합니다:

  • GetFwErrorDomain()은(는) 도메인 객체에 대한 참조를 반환합니다. 이 함수는 constexpr이며 thread-safe합니다 [AP_SWS_Fw_83002].
  • MakeErrorCode은(는) FwErrc 및 추가 데이터로부터 ara::core::ErrorCode을(를) 생성합니다 [AP_SWS_Fw_83003].
  • Name() 및 Message()은(는) 도메인 이름과 코드에 대한 메시지 텍스트를 반환합니다. 둘 다 thread-safe합니다 [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • 별칭 Errc 및 Exception은(는) FwErrc 및 FwException을(를) 참조합니다 [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

도메인의 기본 생성자는 해당 설명이 “Constructs a new FwErrorDomain object” [AP_SWS_Fw_83009]임에도 불구하고 삭제되었습니다. 따라서 도메인에 대한 접근은 GetFwErrorDomain()을(를) 통해 이루어집니다.

오류를 예외로 전달하려는 경우 ThrowAsException을(를) 사용합니다. 이 함수는 FwException을(를) 생성하고 발생시킵니다. 이는 noexcept(false)이며 “not exception safe”로 분류됩니다 [AP_SWS_Fw_83012]. 예외 자체는 명시적인 thread-safe 생성자 FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005]을(를) 통해 생성됩니다.

패킷 레벨에서 오류 사례는 패킷 차단입니다. 일치하는 규칙이 없는 패킷은 Default Action에 해당하며, 차단된 메시지는 Security Events로서 IdsM에 보고됩니다 EXP PlatformDesign 92쪽. [AP_SWS_Fw_82008]의 인터페이스는 이러한 이벤트에 대해 애플리케이션으로의 반환 채널을 제공하지 않습니다. 해당 처리는 IdsM의 몫입니다.

활동 다이어그램: 이 다이어그램은 SwitchFirewallState의 Future 결과 평가, 두 FwErrc 값의 매핑 및 FwException(으)로서의 선택적 재전달을 보여줍니다. 출처: [AP_SWS_Fw_82008], [AP_SWS_Fw_83001], [AP_SWS_Fw_83002], [AP_SWS_Fw_83012]

<h4>Functional Cluster로서의 Firewall: 역할 및 시스템 경계</h4>
<p>Functional Cluster Firewall(네임스페이스 <code>ara::fw</code>)은 애플리케이션에 정확히 하나의 기능적 프로그래밍 인터페이스를 제공합니다. 이는 메서드 <code>SwitchFirewallState</code>을(를) 포함하는 클래스 <code>ara::fw::FirewallStateSwitchInterface</code>입니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. 아키텍처 설명에 따르면 이 클러스터는 데몬 기반입니다. 스테레오타입 «aapAPI,aapPortInterface»를 갖는 인터페이스 <code>FirewallStateSwitchInterface</code>을(를) 구현하며, Adaptive Application은 «use» 관계를 통해 이를 사용합니다 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-4516a6bf4c192609.html" data-snip="FIG-4516a6bf4c192609">EXP SWArchitecture 126쪽</a>. 유스케이스 다이어그램에서는 두 가지 유스케이스를 언급합니다. “Switch Firewall State”는 Adaptive Application에 의해 트리거됩니다. “Report Security Event”에는 Intrusion Detection System Manager가 관여합니다. Operating System은 또 다른 액터로 등장합니다 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-de3679298f5ff97e.html" data-snip="FIG-de3679298f5ff97e">EXP SWArchitecture 197쪽</a>.</p>

<h4>상태 종속적 필터링: Firewall 상태 및 필터 규칙</h4>
<p>이 개념의 핵심은 상태 종속적 필터링입니다. OEM별 Firewall 상태는 주행, 주차 또는 진단 세션과 같이 서로 다른 네트워크 트래픽이 예상되는 상황을 나타냅니다. 필터 규칙은 하나의 상태에 할당됩니다. 검사 및 필터링을 위해 Firewall은 현재 활성 상태의 규칙만 참조합니다. 애플리케이션은 FC Firewall의 API를 통해 현재 상태를 설정합니다 <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign 92쪽</a>. C++에서는 이것이 메서드 <code>SwitchFirewallState(EnumT firewallState)</code>입니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>규칙 자체는 매니페스트의 내용입니다. Foundation 요구사항 다이어그램은 여러 계층에 걸친 필터 체인을 보여줍니다:</p>
<ul>
<li>MAC 주소 및 EtherType을 포함하는 Ethernet,</li>
<li>IPv4,</li>
<li>플래그를 통한 상태 감지 기능이 있는 TCP 또는 ICMP,</li>

<h4>InstanceSpecifier에서 상태 변경까지</h4>
<p>먼저 애플리케이션이 <code>FirewallStateSwitchInterface</code>의 인스턴스를 생성합니다. 이를 위해 <code>ara::core::InstanceSpecifier</code>을(를) 필요로 하는 명시적 생성자가 사용됩니다. 이는 <code>noexcept</code>이며 스레드 안전(thread-safe)한 것으로 명시되어 있습니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>. 해석: <code>InstanceSpecifier</code>은(는) 매니페스트에서 <code>FirewallStateSwitchInterface</code>(으)로 유형화된 애플리케이션의 <code>RPortPrototype</code>을(를) 나타내는 것으로 보입니다. 매니페스트 다이어그램은 바로 이러한 포트 관계를 설정하지만, 해당 Specifier를 언급하지는 않습니다 <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest 677쪽</a>.</p>
<p>상태 변경은 <code>SwitchFirewallState(EnumT firewallState)</code>이(가) 트리거합니다. 이 메서드는 <code>noexcept</code>이며 <code>ara::core::Future&lt;void&gt;</code>을(를) 반환합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. “Switch Firewall State” 시나리오는 세 단계로 진행 과정을 보여줍니다:</p>

<h4>생성된 상태 타입 및 매니페스트 연동</h4>
<p>허용되는 Firewall 상태는 고정된 플랫폼 타입을 형성하지 않습니다. 모델링된 각 인터페이스에 대해 네임스페이스 <code>ara::fw::states</code>에 고유한 <code>enum class {&lt;fwssi-sn&gt;} : std::uint32_t</code>이(가) 생성됩니다. 이는 <code>ara/fw/states/{&lt;fwssi-sn&gt;}.h</code>을(를) 통해 포함되며, 열거자 목록은 모델 <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a>에서 가져옵니다. 모델링된 각 Firewall 상태에 대해 <code>{&lt;symbol-fw-state&gt;} = {&lt;fw-state-value&gt;}</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a> 형태의 열거자가 생성됩니다. 해석: [AP_SWS_Fw_81001]에서 이를 <code>FirewallStateSwitchInterface</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>용 상태 타입으로 명시적으로 정의하고 있으므로, <code>SwitchFirewallState</code>의 매개변수 타입 <code>EnumT</code>은(는) 이 생성된 상태 타입을 나타내는 것으로 보입니다.</p>
<p>메타모델에서 <code>FirewallStateSwitchInterface</code>은(는) <code>PortInterface</code>입니다. 이는 <code>firewallStateMachine</code> 역할(0..*)을 통해 <code>ModeDeclarationGroupPrototype</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-b3757549d69ff2c3.html" data-snip="FIG-b3757549d69ff2c3">TPS Manifest 263쪽</a> 타입의 요소를 집합합니다. 아마도 이 그룹의 Mode들이 <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a>의 열거자를 제공하는 것으로 보입니다. 그러나 출처에서는 이러한 매핑을 명시적으로 설명하지 않습니다.</p>
<p>머신 레벨에서 <code>AdaptiveFirewallModuleInstantiation</code>은(는) Firewall의 머신별 설정을 수집합니다(<code>TPS_MANI_03296</code>, DRAFT 상태). 메타클래스 <code>AdaptiveFirewallToPortPrototypeMapping</code>은(는) 참조 <code>firewall</code>(0..1)을 통해 이 인스턴스화를 애플리케이션 <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58.html" data-snip="SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58">TPS Manifest 677쪽</a>의 <code>RPortPrototype</code>와(과) 연결합니다. 이때 이 메타클래스의 Note에서는 “FirewallModeSwitchInterface”를 언급합니다. 반면 다이어그램과 API에서는 일관되게 <code>FirewallStateSwitchInterface</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest 677쪽</a>을(를) 사용합니다.</p>

<p><code>SwitchFirewallState</code>에 대해 <code>FwErrc::kServiceNotAvailable</code> 및 <code>FwErrc::kInvalidStateDependentFirewall</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>의 두 가지 오류가 지정되어 있습니다. 해당 값은 열거형 <code>FwErrc</code>, 구체적으로는 <code>kServiceNotAvailable=1</code> 및 <code>kInvalidStateDependentFirewall=2</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83001" href="../spec/record.html?id=AP_SWS_Fw_83001">[AP_SWS_Fw_83001]</a>에 의해 정의됩니다. 이 메서드는 <code>noexcept</code>이며 <code>ara::core::Future&lt;void&gt;</code>을(를) 반환합니다. 따라서 호출자는 호출 시의 예외가 아닌 Future를 통해 이러한 오류를 평가합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>두 오류 모두 <code>FwErrorDomain</code>에 속합니다. 이 도메인은 다음 구성 요소를 제공합니다:</p>
<ul>
<li><code>GetFwErrorDomain()</code>은(는) 도메인 객체에 대한 참조를 반환합니다. 이 함수는 <code>constexpr</code>이며 thread-safe합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_83002" href="../spec/record.html?id=AP_SWS_Fw_83002">[AP_SWS_Fw_83002]</a>.</li>
<li><code>MakeErrorCode</code>은(는) <code>FwErrc</code> 및 추가 데이터로부터 <code>ara::core::ErrorCode</code>을(를) 생성합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_83003" href="../spec/record.html?id=AP_SWS_Fw_83003">[AP_SWS_Fw_83003]</a>.</li>
<li><code>Name()</code> 및 <code>Message()</code>은(는) 도메인 이름과 코드에 대한 메시지 텍스트를 반환합니다. 둘 다 thread-safe합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_83010" href="../spec/record.html?id=AP_SWS_Fw_83010">[AP_SWS_Fw_83010]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83011" href="../spec/record.html?id=AP_SWS_Fw_83011">[AP_SWS_Fw_83011]</a>.</li>
<li>별칭 <code>Errc</code> 및 <code>Exception</code>은(는) <code>FwErrc</code> 및 <code>FwException</code>을(를) 참조합니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_83007" href="../spec/record.html?id=AP_SWS_Fw_83007">[AP_SWS_Fw_83007]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83008" href="../spec/record.html?id=AP_SWS_Fw_83008">[AP_SWS_Fw_83008]</a>.</li>
</ul>
<p>도메인의 기본 생성자는 해당 설명이 “Constructs a new FwErrorDomain object” <a class="spec-record-ref" data-req="AP_SWS_Fw_83009" href="../spec/record.html?id=AP_SWS_Fw_83009">[AP_SWS_Fw_83009]</a>임에도 불구하고 삭제되었습니다. 따라서 도메인에 대한 접근은 <code>GetFwErrorDomain()</code>을(를) 통해 이루어집니다.</p>
<p>오류를 예외로 전달하려는 경우 <code>ThrowAsException</code>을(를) 사용합니다. 이 함수는 <code>FwException</code>을(를) 생성하고 발생시킵니다. 이는 <code>noexcept(false)</code>이며 “not exception safe”로 분류됩니다 <a class="spec-record-ref" data-req="AP_SWS_Fw_83012" href="../spec/record.html?id=AP_SWS_Fw_83012">[AP_SWS_Fw_83012]</a>. 예외 자체는 명시적인 thread-safe 생성자 <code>FwException(ara::core::ErrorCode)</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83005" href="../spec/record.html?id=AP_SWS_Fw_83005">[AP_SWS_Fw_83005]</a>을(를) 통해 생성됩니다.</p>
<p>패킷 레벨에서 오류 사례는 패킷 차단입니다. 일치하는 규칙이 없는 패킷은 Default Action에 해당하며, 차단된 메시지는 Security Events로서 IdsM에 보고됩니다 <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign 92쪽</a>. <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>의 인터페이스는 이러한 이벤트에 대해 애플리케이션으로의 반환 채널을 제공하지 않습니다. 해당 처리는 IdsM의 몫입니다.</p>
