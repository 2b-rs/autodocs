State Management의 역할 및 Execution Management와의 구분

State Management는 플랫폼의 동작 상태를 결정합니다. Execution Management는 상태 간 전이를 실행합니다(SWS EM 51쪽). State Management는 애플리케이션별 입력으로부터 활성 Function Group States의 목표 세트를 도출합니다. 그런 다음 StateClient API를 통해 Execution Management에 해당 전환을 요청합니다(EXP SWArch 50쪽; SWS SM 40쪽). StateMachine 접근 방식은 선택 사항입니다. 이는 프로젝트별 중재를 구성된 전이만을 요청하는 SMControlApplication(으)로 이전합니다(SWS SM 28쪽; SWS SM 42쪽).

State Management는 다음 ara::com 서비스를 제공합니다:

  • Update and Configuration Management를 위한 UpdateRequest ([SWS_SM_91102]).
  • SMControlApplication을 위한 StateMachineService 및 UpdateAllowedService ([SWS_SM_91107], [SWS_SM_91108]).
  • 임의의 Adaptive Applications를 위한 StateMachineNotification::CurrentState ([SWS_SM_91109]).

Suspend-to-RAM을 위해 S2RHub 및 S2RSatellite이(가) 추가되며, 운영체제를 위해 플랫폼 확장 PowerStateInterface이(가) 추가됩니다(EXP SWArch 51쪽; SWS SM 163쪽). State Management는 자체적으로 Execution Management, Platform Health Management 및 Network Management의 인터페이스를 필요로 합니다(SWS SM 17쪽; EXP SWArch 77쪽).

컨텍스트 다이어그램: State Management는 제어 애플리케이션, 플랫폼 클러스터 및 운영체제 사이에 위치합니다. 출처: SWS SM 16쪽, EXP SWArch 51쪽, EXP SWArch 52쪽, [SWS_SM_71001]

머신 시동에서 컨트롤러 StateMachine까지

운영체제는 Execution Management를 첫 번째 프로세스로 시작합니다. Execution Management는 Machine Function Group State Startup을(를) 활성화하며, State Management는 이 상태의 일부여야 합니다(EXP SWArch 216쪽). 자체 시작된 이 전이의 결과는 GetInitialMachineStateTransitionResult이(가) 제공합니다. 그 이후 상태 변경에 대한 책임은 State Management에 있습니다(SWS EM 48쪽; SWS EM 56쪽). Startup에 도달하지 못하는 경우, State Management는 SetState을(를) 통해 전이를 중단할 수 있습니다. 이 경우 초기 결과는 kOperationCanceled이(가) 됩니다(SWS EM 57쪽).

StateMachine 방식에서는 Controller 타입의 StateMachine이 먼저 시작된다. 이는 MachineFG를 관리하고 Agents을(를) 시작한다(SWS SM 46쪽). 업데이트 세션이 활성 상태인 경우, 컨트롤러는 초기 상태 대신 ContinueUpdate 상태로 진입한다(SWS SM 91쪽). 'StartStateMachine'이 성공한 후에는 StateMachineService 및 StateMachineNotification이(가) 제공된다. 컨트롤러는 초기 ActionList의 종료를 기다리지 않는다(SWS SM 45쪽; SWS SM 59쪽).

시퀀스 다이어그램: Execution Management가 Startup 이후 제어권을 넘겨주고, 컨트롤러가 에이전트를 시작한다. 출처: SWS SM 93쪽, SWS EM 56쪽, SWS SM 45쪽

중지는 에이전트 StateMachine을 해당 'Off' 상태를 거치도록 하며, 그 이후에는 더 이상 존재하지 않는다. 이미 실행 중인 에이전트는 매개변수가 포함된 'StartStateMachine' 호출 시 전달된 상태로 전환된다(SWS SM 63쪽; SWS SM 60쪽).

상태 다이어그램: 시작부터 서비스 소멸까지 에이전트 StateMachine의 라이프사이클. 출처: SWS SM 10쪽, SWS SM 62쪽, SWS SM 63쪽

상태 전환: RequestTransition 및 ActionLists

RequestTransition은(는) TransitionRequestTable에서 전달된 값을 현재 상태와 비교하여 평가한다([SWS_SM_91107]; SWS SM 50쪽). 이 호출은 다음과 같은 경우에 오류를 반환한다:

  • kInvalidValue: 값이 구성되지 않았다.
  • kTransitionNotAllowed: 현재 상태에 대해 값이 구성되지 않았다.
  • kRecoveryTransitionOngoing: 오류 복구가 진행 중이다.
  • kUpdateInProgress: StateMachine이 'ImpactedByUpdate'로 표시되어 있다.

근거: SWS SM 49쪽; SWS SM 83쪽. 요청이 수락되면 보류 중인 요청은 kOperationCanceled을(를) 받는다. 실행 중인 ActionList는 중지되고 목표 상태의 ActionList가 즉시 시작된다(SWS SM 50쪽).

ActionListItems는 구성된 순서대로 시작되어 SYNC이(가) 나타날 때까지 병렬로 실행된다. 각 ActionList의 끝에는 암시적 SYNC가 적용된다(SWS SM 55쪽). Function Group States, Sleep, SetNetworkHandle, Start/Stop StateMachine 및 Suspend-to-RAM을 위한 항목들이 있다(SWS SM 54쪽). Sleep은 들어오는 트리거를 차단하지 않는다(SWS SM 64쪽). 처리 중 오류가 발생하면 kTransitionFailed이(가) 된다(SWS SM 51쪽). 전환 중에는 CurrentState이(가) 'InTransition' 상태에 있다([SWS_SM_91109]). NetworkHandle이 FullCom 또는 NoCom으로 변경되는 경우에도 테이블 제어 전환이 트리거된다(SWS SM 52쪽).

액티비티 다이어그램: RequestTransition 호출의 검사 항목 및 결과; 검사 순서는 해석에 해당함. 출처: [SWS_SM_91107], SWS SM 49쪽, SWS SM 50쪽, SWS SM 83쪽

Update and Configuration Management를 통한 업데이트 세션

세션은 RequestUpdateSession(으)로 시작된다. 머신을 업데이트할 수 없는 경우 State Management는 이를 거부할 수 있다. 두 번째 병렬 세션은 kNotAllowedMultipleUpdateSessions(으)로 거부한다([SWS_SM_91102]; SWS SM 30쪽). 업데이트 허용 여부는 SMControlApplication이 UpdateAllowed 필드를 통해 결정한다. 머신당 최대 하나의 UpdateRequest 포트만 존재하며, 컨트롤러 프로세스만이 이를 인스턴스화한다([SWS_SM_91108]; SWS SM 79쪽).

PrepareUpdate, VerifyUpdate 및 PrepareRollback은(는) 영향을 받는 Function Group 목록을 수신한다. 이 중 하나를 관리하는 각 StateMachine은 'ImpactedByUpdate'로 표시된다. 에이전트가 영향을 받는 경우 컨트롤러도 표시된다([SWS_SM_91103], [SWS_SM_91104], [SWS_SM_91105]; SWS SM 82쪽). 활성 세션 외부에서 이들 메서드와 StopUpdateSession은(는) kOperationRejected을(를) 반환한다(SWS SM 31쪽). 영향을 받는 에이전트는 메서드에 따라 다르게 처리된다:

  • PrepareUpdate 및 PrepareRollback의 경우 에이전트가 중지된다.
  • VerifyUpdate의 경우 에이전트가 VerifyUpdate 상태로 전환된다.

근거: SWS SM 84쪽; SWS SM 85쪽; SWS SM 89쪽. StopUpdateSession은(는) 컨트롤러를 AfterUpdate(으)로 이끌고 RequestTransition을(를) 다시 해제한다([SWS_SM_91101]; SWS SM 95쪽).

시퀀스 다이어그램: 컨트롤러 관점에서의 업데이트 세션 진행 과정. 출처: SWS SM 81쪽, SWS SM 84쪽, SWS SM 89쪽, [SWS_SM_91102]

ResetMachine은(는) Fire&Forget이다. 재부팅 후 머신과 UCM이 다시 동기화되어야 하므로 Update and Configuration Management는 ResetMachineNotifier을(를) 통해 진행 상황을 추적한다([SWS_SM_91100], [SWS_SM_91106]; SWS SM 33쪽).

상태 다이어그램: 지정되지 않은 중간값을 제외한 ResetMachineNotifier 필드의 값. 출처: SWS SM 33쪽, SWS SM 90쪽, SWS SM 93쪽, SWS SM 95쪽

S2R Hub, 새틀라이트 및 PowerStateInterface를 통한 Suspend-to-RAM

애플리케이션은 suspendToRamAwareness에 따라 다르게 처리된다(SWS SM 109쪽):

  • suspendToRamNotSupported의 경우 Function Group 전환을 통해 종료된다.
  • suspendToRamAware의 경우 S2R Satellite로서 통지받는다.

새틀라이트는 Create 또는 InstanceSpecifier을(를) 받는 생성자를 통해 생성되며 Offer(으)로 등록한다([SWS_SM_81014], [SWS_SM_81003], [SWS_SM_81012]). StopOffer은(는) 이를 등록 해제하고, 실행 중인 콜백이 완료될 때까지 블록하며, 소멸 전에 호출되어야 한다([SWS_SM_81013]; SWS SM 38쪽). 콜백 EnterSuspendMode 및 LeaveSuspendMode은(는) 순수 가상이며 ara::core::Future<void>을(를) 반환한다([SWS_SM_81010], [SWS_SM_81011]).

RequestToEnterSuspendMode 및 RequestToLeaveSuspendMode은(는) 활성 등록되어 IAM 인증을 거친 모든 새틀라이트를 호출한다. 모든 새틀라이트가 응답했거나, 등록 해제했거나, 타임아웃(기본값 1000)이 만료되면 즉시 반환된다([SWS_SM_81110], [SWS_SM_81111]; SWS SM 36쪽). 그 후 EnterSuspendToRamOs이(가) 운영체제의 Suspend를 트리거한다. 해석: 이는 kPmSuspendToRam을(를) 갖는 PowerStateInterface::SetPowerState을(를) 통해 발생할 것으로 보인다([SWS_SM_81112], [SWS_SM_71001], [SWS_SM_71002]).

운영체제는 RegisterWakeUpHandler(으)로 등록된 WakeUpHandler을(를) 통해 웨이크업을 알린다. 그러면 컨트롤러는 자체적으로 LeaveSuspend(으)로 전환하며, 해당 ActionList에는 LeaveSuspendToRam이 포함되어야 한다([SWS_SM_71003], [SWS_SM_71004]; SWS SM 103쪽). StateMachine 방식에서 컨트롤러는 내부적으로 Hub를 사용한다. 따라서 애플리케이션은 S2RHub을(를) 사용할 수 없다(SWS SM 96쪽). 모든 S2R API는 DRAFT 상태이다.

시퀀스 다이어그램: Suspend-to-RAM 진입 및 웨이크업 후 복귀; 운영체제로 향하는 단계는 해석임. 출처: SWS SM 36쪽, SWS SM 37쪽, SWS SM 98쪽, [SWS_SM_81112]

구성 규칙 및 책임

Off를 제외한 모든 MachineFG 상태에서 STATE_MANAGEMENT 친화도를 가진 프로세스가 실행되어야 한다. 그렇지 않으면 머신이 예를 들어 Startup에 멈추게 된다(SWS SM 146쪽). Function Group 및 NmNetworkHandle에 대해 고유성 규칙이 적용된다:

  • 각 Function Group 및 각 NmNetworkHandle은 정확히 하나의 StateMachine에 의해서만 참조된다.
  • StateMachine의 모든 ActionList는 동일한 Function Group 및 NmNetworkHandle 집합을 포함한다.

근거: SWS SM 48쪽; SWS SM 66쪽; SWS SM 57쪽; SWS SM 58쪽. 컨트롤러만 Start/StopStateMachine을 사용한다. 에이전트는 동일한 claimedFunctionGroups 집합의 Function Group만 관리하며 'Off' 상태가 필요하다(SWS SM 58쪽; SWS SM 47쪽; SWS SM 48쪽). ActionList의 지속 시간은 maxActionListDuration에 의해 제한된다. 이 값이 없으면 모듈 인스턴스의 전역 값이 적용된다(SWS SM 68쪽).

오류가 발생한 경우의 동작

Platform Health Management 또는 Execution Management가 오류를 보고하고 StateMachine이 'ImpactedByUpdate' 상태가 아니면, StateMachine은 Recovery 플래그를 설정한다. 이는 ErrorRecoveryTable을(를) 평가하고 즉시 목표 상태로 전환한다. 필수 항목 ANY는 구성되지 않은 ErrorCode를 포착한다(SWS SM 69쪽; SWS SM 70쪽). 업데이트의 영향을 받는 StateMachine은 이러한 요청을 무시하고 로그로만 기록한다(SWS SM 82쪽). Recovery가 진행 중일 때 발생하는 새로운 오류는 'nested recovery'로 간주된다. 그러면 모든 관련 RecoveryHandler() 호출은 동일한 결과를 받는다(SWS SM 29쪽). 이 플래그는 Recovery-ActionList가 성공적으로 처리된 후에만 재설정된다(SWS SM 72쪽).

기타 오류 원인은 자체 ErrorCode를 형성함

  • SetState 오류 kNoCommunication, kInvalidTransition 및 kInvalidMetaModelIdentifier은(는) functionGroupTransitionRequestFailedError(으)로 매핑된다.
  • ActionList 타임아웃, 에이전트 시작 및 중지, LeaveSuspendToRam은 기본값 1을 갖는 자체 ErrorCode를 갖는다.

근거: SWS SM 73쪽; SWS SM 74쪽; SWS SM 76쪽. kIntegrityOrAuthenticityCheckFailed은(는) 매 추가 시도마다 반복되며, 해결은 State Management 외부의 영역이다(SWS SM 40쪽). State Management가 RecoveryHandler()에 제때 응답하지 않으면 Platform Health Management가 FireWatchdogReaction()을(를) 호출한다. State Management 자체의 모니터링 오류는 머신의 재부팅으로 이어진다(EXP SWArch 234쪽; EXP SWArch 235쪽).

API 수준에서 State Management는 'Sm'이라는 이름의 SmErrorDomain과 kOfferFailed 또는 kCommunicationFailed과(와) 같은 SmErrc 값을 통해 오류를 보고한다([SWS_SM_81240], [SWS_SM_81248]). MakeErrorCode 및 GetSmDomain이(가) 코드를 생성한다([SWS_SM_81244], [SWS_SM_81251]). C++ 예외가 활성화된 경우 SmException이(가) 이를 전달한다([SWS_SM_81243], [SWS_SM_81250]). Hub는 새틀라이트의 응답을 kAtLeastOneRejected, kAtLeastOneHadIssuesToLeave, kCommunicationTimeout 또는 kCommunicationFailed(으)로 취합한다(SWS SM 37쪽).

시퀀스 다이어그램: ErrorRecoveryTable을 통한 오류 처리 및 워치독 반응으로의 폴백. 출처: EXP SWArch 220쪽, EXP SWArch 220쪽, SWS SM 69쪽, SWS SM 82쪽
