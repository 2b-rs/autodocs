하드웨어 기반 AUTOSAR Classic 암호화 스택을 위한 암호화 프리미티브 및 키 관리를 제공합니다.

Crypto Driver는 MCAL 모듈로서 AUTOSAR Classic 암호화 스택을 위한 하드웨어 기반 암호화 계산 및 키 관리를 제공합니다(EXP_UtilizationOfCryptoServices 8쪽). 하드웨어 보안 모듈(HSM) 또는 소프트웨어 라이브러리를 Driver Object로 캡슐화하고 중앙 인터페이스인 Crypto_ProcessJob을 통해 동기 및 비동기 작업을 처리합니다([SWS_Crypto_91003]). 키 액세스는 구성 가능한 권한의 적용을 받으며, 키 유효성 검사가 성공한 경우에만 NVM에 영구 저장이 트리거됩니다(SWS_CryptoDriver 37쪽).

Crypto Driver(모듈 Crypto)는 MCAL 드라이버로서 AUTOSAR Classic 암호화 스택의 최하위 기반을 형성하며 하드웨어 보안 모듈(HSM), 암호화 가속기 및 소프트웨어 루틴을 암호화 인터페이스(CryIf)에 직접 연결합니다(EXP_UtilizationOfCryptoServices 8쪽, SWS_CryptoDriver 15쪽). 다중 구현의 경우 인스턴스는 Crypto_<vi>_<ai> 체계에 따라 공급업체별로 이름이 지정됩니다([SWS_Crypto_00012]). 초기화는 [SWS_Crypto_91016]에 대한 필수 널 포인터와 함께 [SWS_Crypto_91000]를 통해 동기적으로 수행됩니다([SWS_Crypto_00215]). 내부적으로 모듈은 독립적인 계산 단위를 Crypto Driver Object로 캡슐화하며, 이들 각각은 한 번에 정확히 하나의 작업만 실행할 수 있는 반면([SWS_Crypto_00014]), n개의 객체는 병렬 계산을 가능하게 합니다([SWS_Crypto_00117]). 이때 Driver Object 0은 동일한 인스턴스의 다른 모든 드라이버 객체의 내부 요구를 위한 중앙 난수 생성기 역할을 합니다([SWS_Crypto_00224], [SWS_Crypto_00225]).

컨텍스트 다이어그램: Driver Object 및 NvM과 DET 인터페이스를 포함한 AUTOSAR 암호화 스택 내 Crypto Driver의 임베딩. 출처: SWS_CryptoDriver 15쪽, SWS_Crypto_00012, SWS_Crypto_91017

암호화 작업은 [SWS_Crypto_91003](Crypto_ProcessJob)을 통해 처리되며, 모드 비트 필드(START, UPDATE, FINISH)는 스트리밍 및 단일 호출을 통합합니다(SWS_CryptoDriver 25쪽, [SWS_Crypto_00017]). 비동기 작업은 주기 함수 [SWS_Crypto_91012](Crypto_MainFunction)을 통해 계산되며 완료 후 CRYIF_CallbackNotification를 통해 CryIf로 보고됩니다([SWS_Crypto_00027], [SWS_Crypto_00028]). 실행 중인 작업은 [SWS_Crypto_00122]를 사용하여 동기적으로 취소할 수 있으며([SWS_Crypto_00183], [SWS_Crypto_00214]), 키 요소로의 직접 버퍼 리디렉션은 복사 작업을 줄여줍니다([SWS_Crypto_00203], [SWS_Crypto_00221]).

시퀀스 다이어그램: Crypto_ProcessJob을 통한 비동기 처리 흐름, Crypto_MainFunction 내 주기 및 CRYIF_CallbackNotification을 통한 콜백. 출처: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

키 관리는 엄격한 액세스 권한 제어하에 키 요소의 설정([SWS_Crypto_91004]), 판독([SWS_Crypto_91006]), 복사([SWS_Crypto_00155], [SWS_Crypto_91015]), 생성([SWS_Crypto_91007]) 및 유도([SWS_Crypto_91008])를 포함합니다([SWS_Crypto_00219], [SWS_Crypto_00220]). Non-Volatile RAM Manager(NvM)로의 영속화는 일관성을 위해 단일 쓰기 시에는 트리거되지 않으며, [SWS_Crypto_91014](Crypto_KeySetValid)를 통한 키 검증 시에만 트리거됩니다(SWS_CryptoDriver 37쪽, [SWS_Crypto_91025]). 멀티코어 환경에서 모듈은 각 파티션에서 격리되어 작동하며([SWS_Crypto_CONSTR_00001]), HSM 객체는 최대 하나의 파티션에만 할당될 수 있습니다([SWS_Crypto_CONSTR_00003]).

Classic 암호화 스택에서 Crypto Driver의 역할 및 시스템 경계

Crypto Driver(모듈 약칭 Crypto)는 AUTOSAR Classic 기본 소프트웨어의 최하위 계층인 Microcontroller Abstraction Layer(MCAL)에 위치합니다(EXP_UtilizationOfCryptoServices 8쪽). 이 드라이버는 암호화 인터페이스(Crypto Interface, CryIf) 바로 아래에 위치하며 이를 통해 Crypto Service Manager(CSM)에 서비스를 제공합니다(SWS_CryptoDriver 15쪽). 주요 임무는 하드웨어 보안 모듈(Hardware Security Module, HSM), AES 엔진과 같은 전용 암호화 가속기 또는 순수 소프트웨어 라이브러리 등 구체적인 암호화 연산 장치를 캡슐화하는 것입니다(SWS_CryptoDriver 15쪽). 암호화 프리미티브의 실제 계산 외에도 기능 범위에는 암호화 키의 저장, 구성 및 관리가 포함됩니다(SWS_CryptoDriver 24쪽).

하나의 ECU 내에 서로 다른 공급업체의 여러 드라이버 인스턴스가 병렬로 존재할 수 있으며, 이 경우 파일, API 및 구성 식별자는 Crypto_<vi>_<ai> 체계에 따른 공급업체별 인픽스(infix)를 통해 고유하게 구분됩니다([SWS_Crypto_00012]). 모듈 초기화는 [SWS_Crypto_91000] 함수를 통해 수행됩니다(Crypto_Init). 특별한 규칙으로 [SWS_Crypto_91016] 유형의 구성 포인터(Crypto_ConfigType)는 항상 널 포인터로 전달되어야 합니다([SWS_Crypto_00215]). 버전 정보는 [SWS_Crypto_91001](Crypto_GetVersionInfo)을 통해 동기적으로 쿼리할 수 있으며, 개발 오류 감지가 활성화된 상태에서 널 포인터를 전달하면 DET에 오류 CRYPTO_E_PARAM_POINTER로 보고됩니다(SWS_CryptoDriver 56쪽).

컨텍스트 다이어그램: Driver Object 및 NvM과 DET 인터페이스를 포함한 AUTOSAR 암호화 스택 내 Crypto Driver의 임베딩. 출처: SWS_CryptoDriver 15쪽, SWS_Crypto_00012, SWS_Crypto_91017

Crypto Driver Object 관리 및 하드웨어 추상화

Crypto Driver의 각 인스턴스는 내부적으로 하나 이상의 논리적 드라이버 객체(Crypto Driver Objects)로 세분화됩니다(SWS_CryptoDriver 15쪽). 하나의 Crypto Driver Object는 암호 채널의 기능적 종단점을 구성하며 독립적인 하드웨어 연산 장치 또는 소프트웨어 구현을 나타냅니다(SWS_CryptoDriver 15쪽). 단일 Driver Object는 원리상 주어진 시점에 항상 정확히 하나의 작업(Job)만 능동적으로 실행할 수 있습니다([SWS_Crypto_00014]). 따라서 n개의 Driver Object를 가진 Crypto Driver는 n개의 암호 작업을 병렬로 연산할 수 있는 용량을 갖습니다([SWS_Crypto_00117]). 지원되는 수학적 및 보안 관련 프리미티브는 할당된 객체의 성능에 따라 결정됩니다([SWS_Crypto_00013]).

드라이버 객체가 (예를 들어 [SWS_Crypto_91009]를 통한 키 교환의 맥락에서 공개 값을 계산하기 위해) 내부 난수를 필요로 하고 자체 난수 생성기를 보유하고 있지 않은 경우, 동일한 드라이버의 Crypto Driver Object 0을 의무적으로 사용합니다([SWS_Crypto_00224], [SWS_Crypto_00225]). 이때 드라이버 객체는 어떠한 경우에도 외부 암호 드라이버 인스턴스의 난수 생성기에 접근해서는 안 됩니다([SWS_Crypto_00226]). 해석: 따라서 Driver Object 0은 동일한 파티션의 다른 모든 드라이버 객체를 위한 중앙 내부 참조 난수 생성기로 기능합니다. 질문 Q-4e8e30714cbc9c80 (열림)

동기식 Direct-Call과 비동기식 스트리밍 간의 작업 처리

암호화 처리는 중앙 인터페이스 [SWS_Crypto_91003](Crypto_ProcessJob)을 통해 Crypto_JobType 타입의 Job 구조체로서 모듈에 전달됩니다([SWS_Crypto_00042], AUTOSAR_CP_SWS_CryptoServiceManager 21쪽). 이 인터페이스는 모드별 비트 필드를 통해 블록 기반 전체 호출과 연속적인 데이터 스트리밍을 결합합니다: 연산 START, UPDATE 및 FINISH은 개별적으로 또는 조합하여 전달될 수 있습니다(SWS_CryptoDriver 25쪽). START 플래그를 설정하면 새 작업으로 표시되고 동일한 작업의 모든 이전 인스턴스를 중단합니다([SWS_Crypto_00017]). 조합하여 전달할 경우 단계들은 항상 START, UPDATE 및 최종적으로 FINISH의 고정된 순서로 실행됩니다(SWS_CryptoDriver 25쪽).

작업이 동기식으로 처리되는지 비동기식으로 처리되는지 여부는 Crypto_JobType의 메타데이터 구성의 일부입니다(SWS_CryptoDriver 26쪽). 비동기 모드에서 [SWS_Crypto_91003]는 단지 작업 데이터를 수신할 뿐이며, 실제 수행은 주기적 메인 함수 [SWS_Crypto_91012](Crypto_MainFunction)에 의해 트리거되거나 처리됩니다([SWS_Crypto_00027], [SWS_Crypto_91012]). 비동기 계산이 완료된 후 Crypto Driver는 상태 및 결과 포인터를 반환하면서 콜백 함수 CRYIF_CallbackNotification을 호출하여 상위 계층인 CryIf에 필수적으로 통지합니다([SWS_Crypto_00028]). 해석: 반면에 동기식 호출은 메인 함수를 통해 분리되지 않고 호출자의 컨텍스트에서 암호화 연산을 블로킹 방식으로 수행합니다. 질문 Q-0447ed9db11aa30b (열림)

시퀀스 다이어그램: Crypto_ProcessJob을 통한 비동기 처리 흐름, Crypto_MainFunction 내 주기 및 CRYIF_CallbackNotification을 통한 콜백. 출처: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

실행 중이거나 대기 중인 암호 작업은 함수 [SWS_Crypto_00122](Crypto_CancelJob)을 통해 취소할 수 있습니다. 요청된 작업이 드라이버 객체에 의해 활성 처리 중이 아닌 경우 즉시 제거되고 호출은 E_OK를 반환합니다([SWS_Crypto_00214]). 그러나 하드웨어가 활성 연산 프로세스를 즉시 중단할 수 없는 경우 API는 이 시도를 CRYPTO_E_JOB_CANCELED로 확인 응답하며, 중단은 다음 도달 가능한 단계에서 완료됩니다([SWS_Crypto_00183]).

시퀀스 다이어그램: 활성 하드웨어 실행 시 케이스 구분을 포함하는 Crypto_CancelJob을 통한 암호화 작업의 동기식 취소. 출처: SWS_Crypto_00122, SWS_Crypto_00183, SWS_Crypto_00214

애플리케이션 메모리와 하드웨어 메모리 간의 불필요한 복사 작업을 방지하기 위해 Crypto Driver는 직접 버퍼 리디렉션(Job Redirection)을 지원합니다: 입력 및 출력 데이터는 jobRedirectionInfoRef을 통해 내부 키 요소로 직접 참조될 수 있습니다([SWS_Crypto_00203], [SWS_Crypto_00204]). 데이터 유출을 방지하기 위해 엄격한 권한 검사가 적용됩니다: 암호화 및 복호화 서비스를 위한 입력 리디렉션의 경우 키 요소가 최소 CRYPTO_RA_ENCRYPTED 권한을 보유해야 하며, 순수 읽기 리디렉션의 경우 최소 CRYPTO_RA_INTERNAL_COPY가 요구됩니다([SWS_Crypto_00221]).

키 관리, 접근 권한 및 암호화 키 연산

Crypto Driver에서 논리적 키(Key)는 실제 키 자료, 초기화 벡터(IV), 난수 시드 또는 SHE 증명(Proof)을 저장하는 하나 이상의 키 요소(Key Elements)로 구성됩니다(SWS_CryptoDriver 28쪽). 각 개별 요소에 대한 접근은 엄격하게 규제됩니다: 읽기 및 쓰기 접근은 구성된 권한 계층 구조(예: CRYPTO_RA_ALLOWED, CRYPTO_RA_ENCRYPTED, CRYPTO_RA_INTERNAL_COPY)를 기반으로 모니터링되며, 열거형 값이 작을수록 더 높은 접근 권한을 나타냅니다(SWS_CryptoDriver 28쪽, [SWS_Crypto_00219]). 직접 읽기 연산은 CRYPTO_RA_ALLOWED 또는 CRYPTO_RA_ENCRYPTED에서만 허용됩니다([SWS_Crypto_00222]). 쓰기 접근은 최소 CRYPTO_WA_ALLOWED 또는 CRYPTO_WA_ENCRYPTED을 필요로 합니다([SWS_Crypto_00223]). 복사 시 소스 요소는 최소 CRYPTO_RA_INTERNAL_COPY를 보유해야 하며 대상 요소보다 낮은 권한을 가져서는 안 됩니다([SWS_Crypto_00220]).

키 및 키 요소의 직접 조작을 위해 Crypto Driver는 일련의 동기식 API를 제공합니다: 데이터 설정 및 판독은 [SWS_Crypto_91004](Crypto_KeyElementSet) 또는 [SWS_Crypto_91006](Crypto_KeyElementGet)를 통해 수행됩니다. 키의 기존 요소 식별자는 [SWS_Crypto_00160](Crypto_KeyElementIdsGet)를 통해 결정할 수 있습니다. 전체 키 또는 개별 요소는 [SWS_Crypto_00155](Crypto_KeyCopy) 또는 [SWS_Crypto_00148](Crypto_KeyElementCopy)을 사용하여 복제됩니다. 부분 복사를 위해 [SWS_Crypto_91015](Crypto_KeyElementCopyPartial)이 존재하며, 이는 소스 및 대상 버퍼에 대한 정밀한 길이 및 오프셋 검사를 강제하고([SWS_Crypto_00207], [SWS_Crypto_00208], [SWS_Crypto_00209]) 대상 길이를 동적으로 조정합니다([SWS_Crypto_00210], [SWS_Crypto_00211]).

또한 모듈은 복합적인 키 연산을 지원합니다: 키 생성은 사전에 [SWS_Crypto_91013](Crypto_RandomSeed)를 통해 초기화된 엔트로피 데이터를 기반으로 [SWS_Crypto_91007](Crypto_KeyGenerate)을 통해 수행됩니다. 새로운 키 자료의 파생은 [SWS_Crypto_91008](Crypto_KeyDerive)가 담당합니다. Diffie-Hellman 키 교환 프로토콜의 경우 공개 값 생성을 위한 함수 [SWS_Crypto_91009](Crypto_KeyExchangeCalcPubVal)과 공유 비밀 결정을 위한 함수 [SWS_Crypto_91010](Crypto_KeyExchangeCalcSecret)을 사용할 수 있습니다(SWS_CryptoServiceManager 70쪽).

각 논리적 키는 [SWS_Crypto_91019](Crypto_KeyGetStatus)을 통해 쿼리할 수 있는 상태를 유지합니다. 새로 작성된 키는 처음에 invalid 상태이며 [SWS_Crypto_91014](Crypto_KeySetValid)를 통한 검증이 성공한 후에만 valid로 해제되는 반면, [SWS_Crypto_91020](Crypto_KeySetInvalid)는 키를 명시적으로 잠급니다. 데이터 형식과 관련하여 드라이버는 ASN.1-PKCS#8 인코딩의 RFC 5958에 따른 비대칭 키([SWS_Crypto_00184]), 고정 알고리즘 OID 1.2.840.113549.1.1.1을 포함하는 RFC 8017에 따른 RSA 키 구조체([SWS_Crypto_00185], [SWS_Crypto_00186], [SWS_Crypto_00187], [SWS_Crypto_00188]) 및 리틀 엔디언 포인트 좌표의 ECC 곡선 데이터(NIST, Brainpool, ED25519)([SWS_Crypto_00189], [SWS_Crypto_00190], [SWS_Crypto_00191], [SWS_Crypto_00192], [SWS_Crypto_00193])를 처리합니다. 하드웨어 밀접 SHE 키는 M1M2M3 형식으로 전달되며, 해당 검증 증명 M4M5은 검증 직후 키 요소 2에서 일시적으로 읽을 수 있습니다([SWS_Crypto_00255]).

상태 다이어그램: 채우기부터 검증, 영속화 및 오류 처리까지의 키 상태 전이. 출처: SWS_Crypto_00198, SWS_Crypto_00242, SWS_Crypto_91014, SWS_Crypto_91019, SWS_Crypto_91020

Non-Volatile RAM Manager를 통한 키 요소 영속화

전원 사이클 전반에 걸쳐 키를 비휘발성으로 유지해야 하는 경우, Crypto Driver는 Non-Volatile RAM Manager(NvM)에 연결됩니다(SWS_CryptoDriver 35쪽, AUTOSAR_CP_SWS_CryptoDriver 37쪽). 핵심 아키텍처 원칙에 따르면, Crypto_KeyElementSet를 통해 개별 요소를 채울 때 NvM으로의 쓰기 작업이 직접 트리거되지 않습니다(SWS_CryptoDriver 37쪽). 대신 영속화는 오직 [SWS_Crypto_91014](Crypto_KeySetValid)를 통한 상태 검증 KEYSETVALID 또는 동등한 암호 작업에 의해서만 시작됩니다(SWS_CryptoDriver 37쪽). 이는 상호 의존적인 키 요소들이 일관되게 검사되고 단일 NvM 쓰기 접근으로 저장되도록 보장하여 플래시 사이클을 절약합니다(SWS_CryptoDriver 37쪽).

NvM과의 상호작용은 전용 콜백 인터페이스를 통해 수행됩니다: 제어기 시작(startup) 동안 NvM은 [SWS_Crypto_91023](Crypto_<vi>_<ai>_NvBlock_Init_<NvBlock>)을 통해 초기화 블록을 제공합니다. NvM의 RAM 미러에서 영속화된 데이터를 로드하는 작업은 [SWS_Crypto_91024](Crypto_<vi>_<ai>_NvBlock_ReadFrom_<NvBlock>)를 통해 수행됩니다. 쓰기 전에 NvM은 암호 드라이버가 내부 키 데이터를 NvM 버퍼에 복사할 수 있도록 [SWS_Crypto_91025](Crypto_<vi>_<ai>_NvBlock_WriteTo_<NvBlock>)를 호출하며, 비동기 블록 전송 완료는 [SWS_Crypto_91026](Crypto_<vi>_<ai>_NvBlock_Callback_<NvBlock>)을 통해 보고됩니다. 제어를 위해 드라이버는 NvM 서비스 NvM_SetRamBlockStatus 및 NvM_WriteBlock를 사용합니다([SWS_Crypto_91017]). 시작 시 영속 키 로드에 실패하면 드라이버는 이 키를 필수적으로 invalid로 표시합니다([SWS_Crypto_00198]).

시퀀스 다이어그램: NvM_WriteBlock 및 드라이버 특정 콜백을 통한 검증 시 NVM으로의 키 요소 영속화. 출처: SWS_Crypto_00242, SWS_Crypto_91017, SWS_Crypto_91025, SWS_Crypto_91026

파티셔닝 및 멀티코어 동작 규칙

멀티코어 시스템에서 암호 연산을 효율적으로 분할하기 위해 암호 스택을 여러 소프트웨어 파티션에 분산할 수 있습니다(BSWDistributionGuide 59쪽). Crypto 모듈은 각 파티션에서 완전히 독립적인 인스턴스로 작동합니다: 각 API 호출은 호출이 발행된 파티션 내에서만 배타적으로 데이터를 처리합니다([SWS_Crypto_CONSTR_00001]). 드라이버 객체의 파티셔닝은 엄격한 구성 규칙을 따릅니다: CryptoDriverObjectEcucPartitionRef에 의해 참조되는 파티션은 모듈에 할당된 파티션(CryptoEcucPartitionRef)의 진부분집합을 의무적으로 형성해야 합니다([SWS_Crypto_CONSTR_00002]). Crypto Driver Object가 하드웨어 보안 모듈(HSM)에 결합된 경우 하드웨어 격리를 이유로 정확히 0개 또는 1개의 파티션에만 할당될 수 있습니다([SWS_Crypto_CONSTR_00003]).

오류가 발생한 경우의 동작

Crypto Driver는 개발 감지(Development Errors)와 런타임 오류(Runtime Errors)로 구성된 2단계 오류 모니터링을 구현합니다. 개발 보안 모드(DET)가 활성화되면 정형 인터페이스 위반이 Det_ReportError으로 전송됩니다([SWS_Crypto_91017]). 여기에는 드라이버 초기화 이전의 호출(CRYPTO_E_UNINIT, 0x00)([SWS_Crypto_00040], [SWS_Crypto_00196], [SWS_Crypto_00205]), 유효하지 않은 초기화 데이터(CRYPTO_E_INIT_FAILED, 0x01) 및 허용되지 않은 널 포인터(CRYPTO_E_PARAM_POINTER, 0x02)가 포함됩니다([SWS_Crypto_00040]). 키 식별자 또는 대상 키 핸들이 허용된 값 범위를 벗어나는 경우 드라이버는 E_NOT_OK로 호출을 중단하고 CRYPTO_E_PARAM_HANDLE(0x04)을 보고합니다([SWS_Crypto_00040], [SWS_Crypto_00180], [SWS_Crypto_00197], [SWS_Crypto_00202], [SWS_Crypto_00217]).

연산에 전달된 입력 또는 출력 버퍼가 충분하지 않은 경우 실행이 거부되고 활성 DET에서 오류 CRYPTO_E_SMALL_BUFFER이 보고됩니다([SWS_Crypto_00195], SWS_CryptoDriver 49쪽). 서비스 CRYPTO_HASH 및 CRYPTO_MACGENERATE에는 표준 예외가 적용됩니다: 여기서 출력 버퍼가 네이티브 해시 또는 MAC 길이보다 작은 경우 결과가 삭제되지 않고 최상위 비트(MSB) 형태로 잘려서 버퍼에 기록됩니다([SWS_Crypto_00065]). 운영 동작에서 드라이버는 반환값을 통해 특정 런타임 오류를 보고합니다: 난수 엔트로피가 고갈되면 [SWS_Crypto_91003]은 리턴 코드 CRYPTO_E_ENTROPY_EXHAUSTED로 응답하고 런타임 오류 CRYPTO_E_RE_ENTROPY_EXHAUSTED(0x03)을 보고합니다([SWS_Crypto_00141], [SWS_Crypto_00194], [SWS_Crypto_91018]). NVM에 대한 읽기 또는 쓰기 접근이 실패하면 CRYPTO_E_RE_NVM_ACCESS_FAILED(0x04)가 신호됩니다([SWS_Crypto_00194]). 추가적인 표준화된 API 반환값은 CRYPTO_E_BUSY, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, CRYPTO_E_KEY_NOT_VALID, CRYPTO_E_KEY_SIZE_MISMATCH 및 CRYPTO_E_KEY_EMPTY입니다([SWS_Crypto_00155], [SWS_Crypto_00207], [SWS_Crypto_91018]).
