소프트웨어 컴포넌트와 Basic Software 사이에서 RTE의 역할

RTE는 각 ECU 인스턴스에 대해 개별적으로 구성되고 생성되는 런타임 계층이다 [SWS_Rte_05000] [SWS_Rte_01316]. 이는 ECU 구성에 설명된 통신 경로를 구현하고 소프트웨어 컴포넌트의 통신 속성 시맨틱을 실현한다 [SWS_Rte_02200] [SWS_Rte_02201]. 애플리케이션 소프트웨어와 Basic Software 사이에서의 위치는 아키텍처 다이어그램(SWS_RTE 113쪽)에 나와 있다. 구현을 위해 RTE는 AUTOSAR OS, COM 및 Efficient COM for Large Data를 포함하여 정의된 기본 서비스만을 사용한다 [SWS_Rte_02250]. 이 모듈에는 BSW 모듈의 실행을 스케줄링하는 Basic Software Scheduler(SchM)도 포함된다 (SWS_RTE 459쪽).

컨텍스트 다이어그램: RTE는 SW-C, BSW 모듈, OS, COM/LdCom 및 NvM 사이를 중재한다. EcuM이 그 라이프사이클을 제어한다. 출처: [SWS_Rte_02250] [SWS_Rte_03530] [SWS_Rte_89015] SWS_RTE 259쪽 SWS_RTE 928쪽

RTE는 C로 생성된다. 해당 코드는 MISRA-C 표준을 준수해야 하며, 외부에 노출되는 모든 심볼은 접두사 Rte_ [SWS_Rte_01167] [SWS_Rte_01168] [SWS_Rte_01171]을 갖는다. 각 컴포넌트 유형마다 해당 컴포넌트와 관련된 정보만 포함하는 Application Header File Rte_[Byps_]<name>.h이 생성된다. 라이프사이클 API는 Rte_Main.h에 선언되어 있으며, 유형은 Rte_Type.h [SWS_Rte_01000] [SWS_Rte_01003] [SWS_Rte_01004] [SWS_Rte_01158] [SWS_Rte_01161]에 선언되어 있다.

라이프사이클: RTE 및 BSW 스케줄러의 시작과 종료

BSW 스케줄러가 초기화되지 않은 동안에는 SchM_Enter 및 SchM_Exit만 사용할 수 있다. EcuM은 첫 번째 BSW 모듈을 스케줄링해야 하기 전에 SchM_Init를 호출한다. SchM_Init은 구성 포인터 [SWS_Rte_08060]를 받고, 유한한 시간 내에 반환하며 [SWS_Rte_07273] 초기 모드의 on-entry-ExecutableEntity를 포함하여 할당된 mode machine instances를 초기화한다 [SWS_Rte_02544]. SchM_Init과 함께 BswBackgroundEvents를 통한 활성화가 시작되고, SchM_StartTiming과 함께 BswTimingEvents를 통한 활성화가 시작된다 (SWS_RTE 459쪽).

SchM_Start 및 SchM_StartTiming의 경우에도 동일하게 적용된다: 두 API 모두 항상 생성되며 유한한 시간 내에 반환해야 한다 [SWS_Rte_04546] [SWS_Rte_04547] [SWS_Rte_04548] [SWS_Rte_04549] [SWS_Rte_04550] [SWS_Rte_04551]. 이후 릴리스의 문서 구절에는 세 가지 규칙이 추가되어 있다 (SWS_RTE 927쪽, SWS_RTE 928쪽):

  • SchM_Start은 BswM_Init보다 먼저 호출된다.
  • SchM_Init은 SchM_StartTiming보다 먼저 호출된다.
  • EcuM은 코어당 세 함수를 모두 정확히 한 번만 호출하며, OS와 같이 필요한 모듈이 초기화된 후에만 호출한다.

Rte_Start은 시작 단계 II의 끝에서 이어진다. 이 시점에는 OS와 모든 BSW 모듈이 준비되어 있다 (SWS_RTE 460쪽). 이 API는 항상 생성되며 유한한 시간 내에 반환해야 한다 [SWS_Rte_01309] [SWS_Rte_02569] [SWS_Rte_02585]. Rte_Start는 RTE의 모드 머신을 초기화하고 ECU 간 클라이언트-서버 연결의 시퀀스 카운터를 0으로 설정한다 [SWS_Rte_02544] [SWS_Rte_02655]. TimingEvents 또는 BackgroundEvents를 통해 트리거되는 Runnable은 Rte_StartTiming가 없는 경우에만 Rte_Start이 시작한다 (SWS_RTE 460쪽). 해석: Rte_StartTiming이 존재하는 경우, 이 활성화는 Rte_StartTiming 호출 시에만 시작될 것으로 추정된다 [SWS_Rte_06753].

종료 시 EcuM은 OS를 여전히 사용할 수 있는 동안 종료 단계 I의 시작 부분에서 Rte_Stop을 호출한다 [SWS_Rte_02570] [SWS_Rte_01310] [SWS_Rte_02584] (SWS_RTE 461쪽). 이 호출 이후 RTE는 해당 코어에서 더 이상 Runnable을 활성화하지 않는다. 그러나 이미 실행 중인 Runnable은 중단하지 않는다 [SWS_Rte_02538]. 그 후 SchM_Deinit이 이어지며, 이는 두 가지 조건에 묶여 있다: Rte_Stop이 종료된 후에만 호출될 수 있고, OS가 종료되기 전에 호출되어야 한다. SchM_Deinit은 스케줄러 부분의 리소스를 해제하고 유한한 시간 내에 반환한다 [SWS_Rte_07277] (SWS_RTE 951쪽). R23-11 이후의 문서 구절에 따르면 SchM_Deinit은 이때 관련된 모든 플러그인의 Rte_Rips_SchM_Deinit도 호출한다 [SWS_Rte_89019] (SWS_RTE 1028쪽).

상태 다이어그램: 스케줄러 부분과 RTE 부분은 코어별로 별도의 상태를 거친다. SchM_Deinit은 Rte_Stop이 종료되었음을 전제로 한다. 출처: [SWS_Rte_02535] [SWS_Rte_02536] [SWS_Rte_02538] SWS_RTE 459쪽 SWS_RTE 951쪽

시퀀스 다이어그램: 시작 및 종료 시 EcuM의 호출과 각각 트리거되는 활성화. 다이어그램의 두 순서는 해석된 것이며 그에 따라 표시되어 있다. 출처: [SWS_Rte_07273] [SWS_Rte_02569] [SWS_Rte_02570] SWS_RTE 927쪽 SWS_RTE 460쪽 SWS_RTE 461쪽

Runnable의 실행 및 다중 인스턴스

소프트웨어 컴포넌트는 여러 RunnableEntity로 구성된다. 이들은 OS 태스크 또는 ISR2에서 실행되며 RTEEvents에 의해 트리거된다 [SWS_Rte_02202] [SWS_Rte_02203] (SWS_RTE 119쪽). 하나의 태스크 내에서는 구성된 실행 순서가 적용된다. 태스크 본체는 제너레이터가 직접 생성한다 [SWS_Rte_02207] [SWS_Rte_06200] [SWS_Rte_06201]. 동일한 Runnable 인스턴스가 여러 RTEEvents에 의해 활성화될 수 있으며, 서로 다른 유형의 이벤트에 의해서도 활성화될 수 있다 [SWS_Rte_03520] [SWS_Rte_03524].

인터럽트 컨텍스트에 대해서는 다음 규칙이 적용된다:

  • 기본적으로 RTE는 컴포넌트의 Runnable이 인터럽트 컨텍스트에서 실행되는 것을 방지한다 [SWS_Rte_03600].
  • 카테고리 1 인터럽트는 RTE에 도달해서는 안 된다 [SWS_Rte_03594].
  • 이벤트가 ISR2에 매핑된 경우, 해당 위치에서의 활성화가 명시적으로 의도된 것이다 [SWS_Rte_04564] (SWS_RTE 182쪽).

RTE는 컴포넌트 유형의 다중 인스턴스를 코드 복제가 아닌 공유 코드를 통해서만 지원한다 [SWS_Rte_02002] [SWS_Rte_03015] (SWS_RTE 126쪽). 각 인스턴스는 인스턴스 핸들을 통해 고유하게 식별할 수 있다. Runnable의 진입점은 이 핸들을 첫 번째 파라미터로 받는다 [SWS_Rte_02015] [SWS_Rte_01012] [SWS_Rte_01016]. 인스턴스는 서로 독립적으로 스케줄링되므로 진입점은 재진입 가능해야 한다 (SWS_RTE 804쪽). 동일한 Runnable 인스턴스는 canBeInvokedConcurrently이 TRUE로 설정된 경우에만 동시에 여러 번 활성화될 수 있다 [SWS_Rte_03523] [SWS_Rte_05083] (SWS_RTE 208쪽).

버퍼를 포함한 Sender-Receiver 및 Client-Server 통신

Sender-Receiver 통신을 위해 RTE는 명시적 및 암시적 액세스를 지원한다 [SWS_Rte_06011]. 암시적 읽기 시 RTE는 Runnable이 시작되기 전에 데이터를 읽어 복사본으로 제공한다. 이 복사본은 실행 내내 변경되지 않은 상태로 유지된다 [SWS_Rte_06000] [SWS_Rte_06001] [SWS_Rte_06004] (SWS_RTE 286쪽). 버퍼링은 수신자 측에서 수행되며 [SWS_Rte_02515] 시맨틱에 따라 달라진다:

  • 데이터 시맨틱의 경우 RTE는 단일 데이터 레코드를 유지한다. 새로운 각 값은 이전 값을 덮어쓰며, 처음 수신될 때까지는 초깃값이 유효하다 [SWS_Rte_02516] [SWS_Rte_02518] [SWS_Rte_02520] [SWS_Rte_06010].
  • 이벤트 시맨틱(queued)의 경우 RTE는 이벤트를 FIFO 큐에 저장한다 [SWS_Rte_02521] [SWS_Rte_02522]. 그 길이는 RteQueuedReceiverQueueLength 또는 대체하여 queueLength에서 결정된다 (SWS_RTE 320쪽).

액티비티 다이어그램: 이벤트가 추가되거나 큐가 가득 찬 경우 폐기된다. 다음 명시적 읽기 액세스는 손실을 보고하고 오류 플래그를 재설정한다. 출처: [SWS_Rte_02522] [SWS_Rte_02523] [SWS_Rte_02524] [SWS_Rte_02525] [SWS_Rte_02572]

ECU 간에 RTE는 COM을 통해 신호를 전송한다. 복합 데이터는 신호 그룹으로서 원자적으로 처리한다 [SWS_Rte_04527] (SWS_RTE 326쪽). COM 콜백을 통해 COM은 Runnable을 활성화할 수 있다 [SWS_Rte_03530] [SWS_Rte_03531]. 대형 바이트 배열의 경우 RTE는 R20-11에서 LdCom을 통해 송수신한다 [SWS_Rte_01376] [SWS_Rte_01377] (SWS_RTE 350쪽). R25-11의 문서 구절에서는 이를 대신하여 “Large Data Path in COM”으로 설명한다 (SWS_RTE 343쪽). R20-11의 경우 해당 요구사항이 적용된다.

Client-Server 호출은 서버 호출 지점에 따라 RTE가 동기식 또는 비동기식 Rte_Call으로 생성한다 [SWS_Rte_01102] [SWS_Rte_01293] [SWS_Rte_01294]. 작업의 파라미터는 원자적으로 처리된다 [SWS_Rte_04518]. 호출이 직접 호출 또는 Trusted-Function 호출로 구현되지 않은 경우, RTE는 두 위치에서 버퍼링한다 [SWS_Rte_02527] [SWS_Rte_02528] (SWS_RTE 358쪽):

  • 서버 측의 요청을 FIFO 큐에,
  • 클라이언트 측의 응답을 길이 1의 큐에.

RTE는 수신 모드와 관계없이 타임아웃을 모니터링한다. 값 0은 모니터링을 비활성화한다 [SWS_Rte_03763] [SWS_Rte_03767] (SWS_RTE 355쪽).

시퀀스 다이어그램: 비동기 Client-Server 호출 시 요청과 응답은 두 개의 버퍼를 거친다. 클라이언트는 Rte_Result을 사용하여 결과를 가져오며, 이는 시간 초과 시 RTE_E_TIMEOUT을 반환한다. 출처: [SWS_Rte_01109] [SWS_Rte_02527] [SWS_Rte_02528] [SWS_Rte_01111] [SWS_Rte_01114] SWS_RTE 750쪽

모드 머신 및 모드 전이 절차

각 모드 관리자의 ModeDeclarationGroupPrototypes에 대해 RTE는 mode machine instances에서 활성 모드를 유지 관리한다 [SWS_Rte_02546]. 모드 변경은 ModeSwitchInterfaces를 통해 1:n 통신으로 비동기 보고된다. 해당 보고는 다음 모드만을 지정한다 [SWS_Rte_02508] [SWS_Rte_02566] [SWS_Rte_02567]. 동일한 모드 머신에 대한 여러 발신자는 RTE에서 지원하지 않는다 [SWS_Rte_02670]. 각 모드 머신에는 변경 보고를 위한 FIFO 큐가 있다. 큐가 가득 차면 RTE는 새 보고를 폐기한다. 보고는 변경이 완료될 때까지 큐에 남아 있다 [SWS_Rte_02718] [SWS_Rte_02719] [SWS_Rte_02720] [SWS_Rte_02721] (SWS_RTE 322쪽).

전이는 10단계로 진행된다 [SWS_Rte_02665]:

  1. Mode Disablings가 활성화된다 [SWS_Rte_02661].
  2. RTE가 on-exit-ExecutableEntity를 실행한다 [SWS_Rte_02562].
  3. RTE는 on-transition-ExecutableEntity를 실행하고 그 종료를 기다린다 [SWS_Rte_02707] [SWS_Rte_02708].
  4. RTE가 on-entry-ExecutableEntity를 실행한다 [SWS_Rte_02564].
  5. 이전 Disablings를 해제한다 [SWS_Rte_02563].
  6. 마지막으로 ModeSwitchedAckEvents를 트리거한다 [SWS_Rte_02587].

1단계부터 9단계까지는 각 코어에서 병렬로 실행될 수 있다. 10단계는 전체 모드 머신에 대해 나머지 단계가 완료된 후에만 이어진다 (ModemanagementGuide 15쪽). 새 모드가 이전 모드와 동일하더라도 전이가 실행된다 [SWS_Rte_02669]. 모드 이벤트에 카테고리 2 Runnable이 연결된 구성은 제너레이터가 거부한다 [SWS_Rte_02500] [SWS_Rte_02662] (SWS_RTE 426쪽).

액티비티 다이어그램: 모드 전이의 10단계. 1~9단계는 코어별로 실행되며, 10단계는 모든 코어에서 완료된 후에만 실행된다. 출처: [SWS_Rte_02665] [SWS_Rte_02708] [SWS_Rte_02721] ModemanagementGuide 15쪽

모드 관리자는 Rte_SwitchAck을 통해 변경 완료를 확인할 수 있다. 이 API는 변경이 완료되는 즉시 RTE_E_TRANSMIT_ACK를 반환하고, 시간을 초과한 경우 RTE_E_TIMEOUT을 반환한다 [SWS_Rte_02725] [SWS_Rte_02729] [SWS_Rte_02728] (SWS_RTE 716쪽). 활성 모드에 따라 RTE는 OS-Schedule-Tables를 활성화할 수 있다 [SWS_Rte_05146]. Rte_Rips_SwitchNotificationStatusType 및 Rte_DsmqStatusType 유형은 변경 보고를 큐에 넣고 뺄 때의 상태를 설명한다 [SWS_Rte_91113] [SWS_Rte_91102]. 그러나 관련 문서 구절은 R24-11 및 R25-11에서 비롯된 것이다 (SWS_RTE 980쪽, SWS_RTE 982쪽).

생성, 변형 바인딩, 그리고 측정 및 캘리브레이션

방법론에서 RTE는 “Generate BSW and RTE” 액티비티에서 생성된다. 입력은 ECU Extract 및 ECU Configuration Values이다 (Methodology 103쪽). 바인딩 시점이 SystemDesignTime 및 CodeGenerationTime인 가변성은 제너레이터가 Contract 단계 및 Generation 단계에서 이미 바인딩한다. 명확하게 선택된 변형이 없는 입력은 거부된다 [SWS_Rte_06501] [SWS_Rte_06502] [SWS_Rte_06507] [SWS_Rte_06509] (SWS_RTE 467쪽). PreCompileTime 가변성은 생성된 코드에서 구현한다. RTE 관련 LinkTime 가변성은 거부한다 [SWS_Rte_06510] [SWS_Rte_06511]. 스위치 strictConfigurationCheck은 제너레이터가 누락된 구성 부분을 직접 보완할 수 있는지를 제어한다 [SWS_Rte_05148] [SWS_Rte_05150]. 생성된 RTE는 제너레이터 자체가 BSW 모듈로 설명한다. 여기에는 BswModuleDescription, BswInternalBehavior, BswImplementation 및 라이프사이클 API용 BswModuleEntrys가 포함된다 [SWS_Rte_05165] [SWS_Rte_05166] [SWS_Rte_05167] [SWS_Rte_05177] (SWS_RTE 101쪽).

캘리브레이션 파라미터용 메모리는 RTE가 직접 생성한다 [SWS_Rte_03961]. 소프트웨어 지원을 통한 데이터 에뮬레이션의 경우 single pointered, double pointered 및 initRam 변형을 선택할 수 있다. RTE 빌드당 정확히 하나만 활성화된다 [SWS_Rte_03943] [SWS_Rte_03909] [SWS_Rte_03913] [SWS_Rte_03914] [SWS_Rte_03915]. 에뮬레이션은 전체 RTE 코드에 대해 비활성화할 수도 있다 [SWS_Rte_03942] (SWS_RTE 232쪽). 캘리브레이션 지원 활성화 여부는 컴포넌트 유형별로 정의할 수 있다 [SWS_Rte_05145]. 측정 및 캘리브레이션 도구를 위해 제너레이터는 McSupportData를 생성한다. 그 안에서 McSwEmulationMethodSupport 요소가 선택된 방법을 문서화한다 [SWS_Rte_05118] [SWS_Rte_05137] [SWS_Rte_05138] (SWS_RTE 258쪽). 이 데이터는 A2L 생성에 반영된다 (Methodology 414쪽).

컨텍스트 다이어그램: A2L 생성을 위한 측정 및 캘리브레이션 데이터를 포함한 통합 방법론에서의 RTE 생성 입력 및 출력. 출처: Methodology 103쪽 Methodology 106쪽 Methodology 414쪽 [SWS_Rte_05118]

  • void Rte_StartTiming (void); Rte_StartTiming API is intended to release the activation of RunnableEntitys triggered by TimingEvents and BackgroundEvents...

Rte_Start은 RTE에서 사용하는 시스템 자원과 통신 자원을 할당하고 초기화하기 위한 것입니다.

사용

항상 생성되는([SWS_Rte_01309]) 함수 Rte_Start([SWS_Rte_02569])은 RTE에서 사용하는 시스템 및 통신 리소스를 할당하고 초기화합니다([SWS_Rte_03015]). 전달 매개변수가 없고 Std_ReturnType를 반환하며, 무한 루프 없이 유한한 실행 시간 내에 종료되어야 합니다([SWS_Rte_02585]).

호출 컨텍스트 및 동시성

Rte_Start은 RTE에 필요한 모든 기본 소프트웨어 모듈이 초기화된 후 신뢰할 수 있는 OS 컨텍스트에서 EcuStateManager에 의해 각 Core에서 정확히 한 번만 호출될 수 있습니다([SWS_Rte_CONSTR_09035]). 호출은 각 Core에서 독립적으로 이루어지며([SWS_Rte_07615]), 해당 Core에 할당된 모든 파티션에 대한 파티션별 시작 활동을 다룹니다([SWS_Rte_07616]).

초기화 순서 및 상호 작용

Rte_Start의 프레임워크 내에서 조정된 시작 시퀀스가 실행됩니다:

  • ramBlock을 위해 할당된 변수는 구성된 RteInitializationStrategy에 따라 초기화됩니다([SWS_Rte_07632]).
  • 변수 초기화 후, 그러나 Runnable Entities의 실행 전에 RTE는 관련된 모든 RTE Implementation Plug-In의 초기화 함수 Rte_Rips_Rte_Start을 호출합니다([SWS_Rte_80052]).
  • InitEvent에 의해 트리거된 Runnable은 1회 활성화되며([SWS_Rte_06761]), 초기 모드로의 전환이 시작됩니다([SWS_Rte_06766]).
  • 별도의 Rte_StartTiming이 존재하지 않는 경우, Rte_Start은 TimingEvent([SWS_Rte_07575]) 또는 BackgroundEvent([SWS_Rte_07178])에 의해 제어되는 Runnable의 활성화도 추가로 시작합니다.

Rte_SetMirror과 같은 특정 함수는 명시적으로 Rte_Start 이전에도 호출될 수 있습니다([SWS_Rte_07319]).

오류 처리

SchM_Init 전에 Rte_Start을 호출하는 경우, RteDevErrorDetectUninit가 활성화되어 있으면 기본 소프트웨어 스케줄러 또는 RTE가 오류 RTE_E_UNINIT (0x07)을 보고합니다([SWS_Rte_07683]). 마찬가지로 Rte_Start 전에 모니터링되는 RTE API를 유효하지 않게 호출하면 RTE_E_UNINIT이 보고됩니다([SWS_Rte_07682]).

이 텍스트는 AUTOSAR Classic R20-11의 명세 요구사항을 기반으로 AI에 의해 생성되었습니다.

사용법 및 의미론

함수 Rte_Stop([SWS_Rte_02570])은 호출 Core에서 RTE를 종료하는 역할을 하며, 이 Core에서 RTE가 점유하고 있는 모든 시스템 및 통신 리소스를 해제합니다([SWS_Rte_01262]). 이 인터페이스는 항상 제공되며([SWS_Rte_01310]), 매개변수가 없고, Std_ReturnType를 반환하며 유한한 실행 시간 내에 반환합니다([SWS_Rte_02584]).

순서 조건 및 동시성

  • 한 Core에서 Rte_Stop을 호출한 후 RTE는 해당 Core에서 더 이상 RunnableEntity을 활성화, 시작 또는 해제해서는 안 됩니다([SWS_Rte_02538]).
  • Rte_Stop은 RTE에 필요한 기본 소프트웨어 모듈이 종료되기 전에 EcuStateManager에 의해 호출되어야 합니다([SWS_Rte_CONSTR_09038]).
  • API SchM_Deinit은 Rte_Stop이 완전히 종료된 후에만 호출할 수 있습니다([SWS_Rte_CONSTR_09056]).
  • 함수 Rte_GetMirror은 Rte_Stop에 의해 RTE가 중지된 후에도 계속 호출 가능하며 실행 중인 운영체제(OS)에 의존합니다([SWS_Rte_07350]).

상호 작용 및 오류 처리

  • Rte_Stop 내에서 RTE는 관련된 모든 RTE Implementation Plug-In의 중지 함수 Rte_Rips_Rte_Stop을 호출하며([SWS_Rte_80053]), 이는 다른 라이프사이클 API와 함께 의무적으로 제공되어야 합니다([SWS_Rte_70047]).
  • RteDevErrorDetectUninit이 활성화된 경우, Rte_Stop 이후에 특정 RTE API가 호출되면 오류 RTE_E_UNINIT (0x07)이 보고됩니다([SWS_Rte_07682]).
  • 명세 컨텍스트에서는 내부 제한을 초과했거나 필요한 리소스 할당에 실패한 경우 오류 상태 RTE_E_LIMIT도 언급됩니다([SWS_Rte_01262]).

이 사용 지침은 AUTOSAR R20-11 명세를 기반으로 자동 생성되었습니다.

데이터 타입 Rte_Rips_SwitchNotificationStatusType([SWS_Rte_91113])은 uint8에서 파생되어 헤더 파일 Rte_Type.h을 통해 제공되며, 모드 큐(Mode Queue)와 관련된 큐 삽입(Enqueue) 및 큐 인출 작업(Dequeue)의 상태를 나타냅니다.

사용법 및 상호작용

이 타입은 RTE Implementation Plug-In(RIPS)의 맥락에서 사용됩니다:

  • Enqueue 알림: 모드 큐에 큐잉할 때 상태는 입력 매개변수 switchNotificationStatus을 통해 동기 서비스 Rte_Rips_<PlugIn>_Switch_<BswSwcI>_<MMI>로 전달됩니다([SWS_Rte_91114]). 여기서 관련 값은 이전에 비어 있던 큐에 삽입하는 경우 RTE_SWITCH_NOTIFICATION_ENQUEUED_FIRST(0x01)이며, 이미 채워져 있는 큐의 경우 RTE_SWITCH_NOTIFICATION_ENQUEUED_NOT_FIRST(0x02)입니다([SWS_Rte_91113]).
  • Dequeue 작업: 인출 시 이 타입은 서비스 Rte_Rips_<PlugIn>_DequeueModeSwitch_<MMI>_<OsTask>([SWS_Rte_91115])의 반환값 역할을 하며, 이 서비스는 마지막 On-Entry ExecutableEntity가 종료되는 즉시 호출됩니다. 이 서비스는 RTE_SWITCH_NOTIFICATION_DEQUEUED_LAST(0x04)을 통해 마지막 알림이 인출되었음을 보고하거나, RTE_SWITCH_NOTIFICATION_DEQUEUED_NOT_LAST(0x05)를 통해 큐에 추가 알림이 남아 있음을 보고합니다([SWS_Rte_91113]).

오류 처리 및 특수 상태

[SWS_Rte_91113]에 따른 값 범위는 특정한 오류 및 예외 지표를 정의합니다:

  • RTE_SWITCH_NOTIFICATION_ENQUEUE_FAILED(0x03): 비어 있지 않은 큐로의 큐잉에 실패했습니다.
  • RTE_SWITCH_NOTIFICATION_SKIP(0x00): 모드 전환 알림을 디큐할 수 없습니다.

사용

타입 Rte_DsmqStatusType([SWS_Rte_91102])은 uint8에서 파생되었으며 분산 공유 모드 큐(Distributed Shared Mode Queue, DSMQ)의 작업 상태를 나타냅니다. [SWS_Rte_80085]에 따라 이 타입은 연관된 리터럴과 함께 헤더 Rte_Type.h에 정의됩니다.

값 범위에는 정의된 다섯 가지 상태가 포함됩니다([SWS_Rte_91102]):

  • RTE_DSMQ_ENQUEUED_FIRST(0x01): 이전에 비어 있던 DSMQ에 모드 전환 알림이 큐잉(enqueue)되었습니다.
  • RTE_DSMQ_ENQUEUED_NOT_FIRST(0x02): 비어 있지 않은 DSMQ에 알림이 큐잉되었습니다.
  • RTE_DSMQ_ENQUEUE_FAILED(0x03): 비어 있지 않은 DSMQ로의 큐잉에 실패했습니다.
  • RTE_DSMQ_DEQUEUED_LAST(0x04): DSMQ에서 마지막 모드 전환 알림이 디큐(dequeue)되었습니다.
  • RTE_DSMQ_DEQUEUED_NOT_LAST(0x05): 큐에 추가 알림이 남아 있는 상태에서 DSMQ로부터 모드 전환 알림 하나가 디큐되었습니다.

오류 처리

비어 있지 않은 DSMQ로의 모드 전환 알림 큐잉에 실패하면 상태 값 RTE_DSMQ_ENQUEUE_FAILED(0x03)을 통해 표시됩니다([SWS_Rte_91102]). 이 데이터 타입에 대해 정의된 특정 DET 또는 DEM 메시지는 없습니다.

상호작용 및 동시성

이 타입의 값은 RTE Implementation Plug-In(RIPS)의 인터페이스에 입력 매개변수 dsmqstatus(으)로 전달됩니다:

  • Rte_Rips_<PlugIn>_DsmqSwitch_<BswSwcI>_<MMI>([SWS_Rte_91103])은 DSMQ로의 큐잉에 대해 플러그인에 동기식으로 알립니다.
  • Rte_Rips_<PlugIn>_DsmqTransitionEnd_<BswSwcI>_<MMI>([SWS_Rte_91106])은 DSMQ 전이 OsTask에서 특정 모드 전이의 종료를 플러그인에 동기식으로 알립니다.

호출하는 두 RIPS 서비스는 모두 동기식이며 재진입 가능하도록 명세되어 있습니다([SWS_Rte_91103], [SWS_Rte_91106]).
