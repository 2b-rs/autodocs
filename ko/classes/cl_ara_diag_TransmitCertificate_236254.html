애플리케이션이 UDS 서비스 Authentication에서 진단 인증서를 수신하고 검증할 수 있도록 지원합니다.

클래스 ara::diag::TransmitCertificate은 서비스 Authentication [SWS_DM_01961]의 UDS 하위 기능 TransmitCertificate(0x29 0x04)를 위한 애플리케이션 인터페이스를 구현합니다. Offer()을 통한 활성화 후, 애플리케이션은 비동기 메서드 Process()에서 전송된 인증서 데이터를 수신하고 애플리케이션별 검증을 시작합니다 [SWS_DM_01968]. 검증에 성공하면 Diagnostic Management가 반환 매개변수 0x13(CertificateVerified)을 포함하는 긍정 UDS 응답을 트리거하는 반면, 오류는 해당하는 NRC와 함께 부정 응답으로 회신됩니다. 이 인스턴스는 포트 인터페이스에 영구적으로 바인딩되며 복사하거나 이동할 수 없습니다.

컨텍스트

헤더 ara/diag/transmit_certificate.h(AUTOSAR_AP_SWS_Diagnostics §8.26 “Header: ara/diag/transmit_certificate.h”)의 클래스 ara::diag::TransmitCertificate [SWS_DM_01961]은 서비스 Authentication의 UDS 하위 기능 TransmitCertificate(0x29 0x04)를 실현하기 위한 Adaptive 애플리케이션의 인터페이스를 나타냅니다. 일반화된 인터페이스로서 애플리케이션이 16비트 식별자(certificateEvaluationId)를 기반으로 하나 이상의 전송된 인증서를 수신하고 처리할 수 있도록 지원합니다.

상호작용에는 세 가지 주요 컴포넌트가 관여합니다:

  • 인증서 전송을 위한 UDS 요청을 차량으로 전송하는 외부 진단 테스터 [SWS_DM_01968].
  • 수신된 진단 요청을 필터링하고 전달하며 최종 UDS 응답을 생성하는 Adaptive Platform의 Diagnostic Server(Diagnostic Management, DM) [SWS_DM_01251], [SWS_DM_01969].
  • ara::diag::TransmitCertificate에서 파생된 인스턴스를 제공하고, 인증서 검증을 수행하며, 그 결과를 서버에 비동기적으로 반환하는 Adaptive 애플리케이션 [SWS_DM_01968].

컨텍스트 다이어그램: UDS 0x29 04를 통한 인증서 전송에 관여하는 컴포넌트. 출처: [SWS_DM_01968], [SWS_DM_01969], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Successful verification of transmitCertificate”.

수명 주기

ara::diag::TransmitCertificate의 인스턴스는 ara::core::InstanceSpecifier 및 동시성 모드 ConcurrencyType를 지정하여 생성자를 통해 생성됩니다 [SWS_DM_01962]. InstanceSpecifier는 매니페스트에서 DiagnosticTransmitCertificateInterface으로 유형화된 PortPrototype를 참조해야 합니다 [SWS_DM_01962]. 이 매핑에 실패하거나 현재 프로세스에서 인스턴스 식별자가 중복 사용되는 경우 InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation 또는 InstanceSpecifierAlreadyInUseViolation과 같은 런타임 위반이 발생합니다 [SWS_DM_01962].

이 클래스에는 엄격한 소유권 및 인스턴스화 규칙이 적용됩니다. 인증 핸들러는 고유하며 복사 불가능하고 이동 불가능한 인스턴스로 설계되었습니다. 따라서 복사 생성자 [SWS_DM_01964], 복사 할당 연산자 [SWS_DM_01966], 이동 생성자 [SWS_DM_01963] 및 이동 할당 연산자 [SWS_DM_01965]은 명시적으로 삭제되었습니다(=delete).

생성자 자체는 스레드 안전하고 예외 안전하도록 명시되어 있습니다 [SWS_DM_01962]. 해제는 가상 표준 소멸자 [SWS_DM_01967]을 통해 수행됩니다. 실제 실행 메서드 Process를 스레드 안전하게 구현해야 하는지 여부는 선택된 concurrencyType(kConcurrent 또는 kNotConcurrent)에 따라 달라집니다 [SWS_DM_01962], [SWS_DM_01968].

사용 경로

일반적인 흐름에는 핸들러 등록, 수신 인증서 처리 및 이후 등록 취소가 포함됩니다:

  1. 서비스 제공(Offer): 구성된 인터페이스에 대한 요청을 이 핸들러로 전달해도 됨을 Diagnostic Management에 알리기 위해 애플리케이션이 Offer()을 호출합니다 [SWS_DM_01969].
  2. 요청 수신(Process): Diagnostic Server에 하위 기능 TransmitCertificate의 UDS 요청이 수신되면, 서버는 데이터를 애플리케이션의 순수 가상 메서드 Process()로 전달합니다 [SWS_DM_01968]. 이 메서드는 16비트 식별자 certificateEvaluationId, 인증서 원시 데이터를 나타내는 ara::core::Span<ara::core::Byte const>, 메타데이터(metaInfo) 및 cancellationHandler을 수신합니다 [SWS_DM_01968].
  3. 평가 및 조치: AUTOSAR는 인증서에 대한 고정된 시맨틱을 규정하지 않으므로 검증 및 필요한 조치 도출은 전적으로 애플리케이션의 책임입니다 [SWS_DM_01968]. 해석: 애플리케이션은 일반적으로 전송된 인증서를 암호화 방식으로 검증하거나 내부 키 저장소를 업데이트하는 데 사용할 것으로 보입니다.
  4. 결과 전달: 메서드는 ara::core::Future<void>을 반환합니다 [SWS_DM_01968]. 애플리케이션이 오류 없이 Future를 성공적으로 완료하면 Diagnostic Server는 테스터에게 긍정 UDS 응답을 전송하며, 이때 매개변수 authenticationReturnParameter(RV)는 값 0x13(CertificateVerified)으로 설정됩니다 [SWS_DM_01251](AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Successful verification of transmitCertificate”).
  5. 서비스 중지(StopOffer): 핸들러가 더 이상 요청을 수신하지 않도록 하려면 애플리케이션이 StopOffer()을 호출하여 전달을 종료합니다 [SWS_DM_01970].

시퀀스 다이어그램: Offer부터 UDS 응답까지의 일반적인 인증서 전송 흐름. 출처: [SWS_DM_01968], [SWS_DM_01969], [SWS_DM_01970], [SWS_DM_01249], [SWS_DM_01251].

오류 시나리오

오류 상태는 라이프사이클의 여러 단계에서 발생할 수 있습니다:

  • 이미 활성화된 제공: 이 인스턴스에 대해 서비스가 이미 활발히 제공되고 있음에도 Offer()을 호출하면 호출이 실패하고 ara::core::Result<void>에 롤백 시맨틱과 함께 오류 코드 DiagOfferErrc::kAlreadyOffered가 반환됩니다 [SWS_DM_01969]. Offer() 및 StopOffer()는 스레드 안전하지 않으며 동시에 호출할 수 없습니다 [SWS_DM_01969], [SWS_DM_01970].
  • 인증서 검증 실패: 애플리케이션이 Process()에서 평가 중 오류를 감지하면 ISO 14229-1에 따라 DiagUdsNrcErrc의 해당 오류 코드로 Future를 완료합니다 [SWS_DM_01968]. Diagnostic Server는 이 반환값을 가로채 테스터에게 부정 진단 응답(Negative Response)을 전송하며, 이 부정 응답 코드(NRC)는 전송된 오류 코드와 정확히 일치합니다 [SWS_DM_01249](AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Handling Negative return values of ara::diag::TransmitCertificate::Process method”).
  • 진행 중인 대화 중단: 비동기 처리 중에 애플리케이션은 cancellationHandler.IsCanceled()을 통해 상태를 조회하여 진단 대화가 중단되었는지 확인할 수 있습니다 [SWS_DM_01968]. 또한 중단 시 즉시 알림을 받을 수 있도록 cancellationHandler.SetNotifier(...)를 통해 콜백 함수를 등록할 수 있습니다 [SWS_DM_01968].

Adaptive Application은 Offer 메서드를 통해 Diagnostic Management (DM)에 의한 진단 요청 전달을 ara::diag::TransmitCertificate [SWS_DM_01969] 클래스의 담당 핸들러로 활성화합니다. 호출은 동기식으로 매개변수 없이 이루어지며, 인터페이스는 예외 안전(noexcept)(으)로 정의되어 있습니다 [SWS_DM_01969]. 반환 타입으로는 ara::core::Result<void>이(가) 사용되며, 이를 통해 등록 성공 여부 또는 오류 상태가 호출자에게 전달됩니다 [SWS_DM_01969].

해당 핸들러 인스턴스에 대해 이 함수가 이미 이전에 호출된 경우 재호출은 실패하고 롤백 시맨틱을 갖는 특정 오류 DiagOfferErrc::kAlreadyOffered을(를) 반환하며 [SWS_DM_01969], 이는 DiagErrc의 표준화된 오류 값에 해당합니다 [SWS_DM_00514]. 이 메서드는 명시적으로 스레드 안전하지 않은 것으로 지정되어 있으므로 [SWS_DM_01969] 동일한 인스턴스에 대한 병렬 접근은 방지되어야 합니다(해석: 동시 호출로부터의 보호는 애플리케이션 소프트웨어의 책임입니다).

Offer의 함수 패턴은 ara::diag::Authentication::Offer [SWS_DM_01130], ara::diag::CommunicationControl::Offer [SWS_DM_00809] 또는 ara::diag::GenericRoutine::Offer [SWS_DM_00557]에도 적용되는 진단 핸들러의 일관된 제공 개념을 따릅니다. AUTOSAR는 이름이 ara::com과(와) 유사하게 지정되었음에도 독립적인 진단 구현이 존재함을 명확히 합니다(AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”). Offer을(를) 통한 제공 이전에는 호출 전에 준비되지 않은 것으로 간주되는 DoIP 서비스와 유사하게 DM이 핸들러로 요청을 전달하지 않습니다 [SWS_DM_01525].

이 사용 지침은 자동으로 생성되었으며 릴리스 R25-11의 사양을 기반으로 합니다.
