컨텍스트

클래스 ara::sm::s2r::S2RHub은(는) 함수형 클러스터 State Management(SM)에서 Suspend-to-RAM 시퀀스를 위한 중앙 중개 및 조정 인스턴스를 형성합니다(EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”, SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). 머신의 종료 및 기동 시간을 최적화하기 위해 전체 시스템 재부팅 대신 Suspend-to-RAM 상태로의 전환을 수행할 수 있습니다(SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). S2RHub은(는) 일반적인 Adaptive Applications에서 사용하도록 의도된 것이 아니며, State Management 구현체 또는 전용 제어 애플리케이션(SMControlApplication)에서만 독점적으로 사용됩니다(EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).

Suspend-to-RAM의 조정은 State Management의 StateMachine 접근 방식을 통해 선언적으로 수행되거나, SMControlApplication 내에서 S2RHub의 C++ API를 통해 명령형으로 수행될 수 있습니다. 두 사용 방식은 상호 배타적입니다([SWS_SM_00684], SWS StateManagement §7.5.1 “S2R Hub”, SWS StateManagement §7.7.15). 주요 상호작용 대상은 다음과 같습니다:

  • SMControlApplication / State Management: 허브의 C++ 인터페이스를 통해 일시 중단(Suspend) 및 재개(Resume) 절차를 시작하고, 준비 작업이 확인된 후 운영체제의 Suspend를 트리거합니다([SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]).
  • S2R Satellites: Executable이 suspendToRamAware(으)로 구성된 Adaptive Applications 프로세스 내의 ara::sm::s2r::S2RSatellite 인스턴스입니다(SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). 이들은 Offer을(를) 통해 허브에 등록되고 영구 데이터 저장 및 서비스 중지를 위한 지침을 수신합니다([SWS_SM_00701], [SWS_SM_00710], EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).
  • Identity and Access Management (IAM): 등록하는 새틀라이트를 인증하고, 허브 생성을 배포 모델에서 참조된 프로세스로 제한합니다([SWS_SM_00706], [SWS_SM_00714], [SWS_SM_00715]).
  • Betriebssystem (OS): 허브에 의해 저전력 Suspend 상태로 전환됩니다([SWS_SM_81112]).

컨텍스트 다이어그램: S2RHub의 임베딩 및 SMControlApplication, S2RSatelliten, 운영체제와의 상호작용. 출처: EXP SWArchitecture §9.2.2.1.4, SWS StateManagement §7.5.1, [SWS_SM_81112].

수명 주기

허브 인스턴스 생성은 생성자 S2RHub(const ara::core::InstanceSpecifier &instance)을(를) 통해 명시적으로 수행됩니다([SWS_SM_81103]). 생성 중에 허브는 반드시 IAM 검사를 수행합니다. 현재 프로세스의 컨텍스트가 SuspendToRamHubMapping.process의 모델링과 일치하지 않으면 생성이 거부됩니다([SWS_SM_00706], [SWS_SM_00714]).

이 클래스는 이동 시맨틱을 가지며 복사 작업을 완전히 금지합니다:

  • 복사 생성자와 복사 대입 연산자는 삭제되었습니다(=delete)([SWS_SM_81107], [SWS_SM_81109]).
  • 이동 생성자와 이동 대입 연산자는 리소스를 새 인스턴스로 전달하며 스레드 안전(thread-safe)으로 선언되어 있습니다([SWS_SM_81106], [SWS_SM_81108]).
  • 소멸자 ~S2RHub()은(는) 가상이며 스레드 안전하지 않음(not thread-safe)으로 명시되어 있습니다([SWS_SM_81105]).

동시성과 관련하여, 동작 메서드들(RequestToEnterSuspendMode, RequestToLeaveSuspendMode, EnterSuspendToRamOs)은 스레드 안전하지 않음으로 분류됩니다([SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]). 따라서 호출자는 동일한 인스턴스에 대한 제어 호출이 순차적으로 또는 외부에서 동기화되어 수행되도록 보장해야 합니다.

사용 경로

일반적인 사용 과정은 새틀라이트의 등록 단계, Suspend 상태로의 조정된 종료 및 이후의 재활성화를 포함합니다:

  1. 초기화 및 등록: SMControlApplication이(가) S2RHub을(를) 인스턴스화합니다([SWS_SM_81103]). 이와 병행하여 참여하는 새틀라이트들이 ara::sm::s2r::S2RSatellite::Offer을(를) 통해 허브에 등록하며, 발생 가능한 StopOffer 전까지 활성 등록 상태로 간주됩니다([SWS_SM_00710], [SWS_SM_00713]). 허브는 각 새틀라이트의 IAM 진위 여부를 검증합니다([SWS_SM_00715]).
  2. Suspend 요청: Suspend 과정을 준비하기 위해 제어 애플리케이션이 RequestToEnterSuspendMode(timeout)을(를) 호출합니다([SWS_SM_81110]). 허브는 활성 등록된 모든 새틀라이트에 메시지를 전송하고, 이에 따라 새틀라이트는 콜백 EnterSuspendMode을(를) 실행하며([SWS_SM_00701], [SWS_SM_00711]) 동결 준비를 합니다(영구 데이터 저장, 서비스 제공 및 안전 활동 종료)(EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).
  3. 준비 상태 대기: RequestToEnterSuspendMode이(가) 반환한 ara::core::Future<void>은(는) 주소 지정된 모든 새틀라이트가 긍정적으로 응답했거나, 등록 해제되었거나, 타임아웃이 발생하면 해결됩니다([SWS_SM_00702], [SWS_SM_81110]).
  4. OS Suspend 시작: Future가 성공적으로 반환된 후, 애플리케이션은 EnterSuspendToRamOs()을(를) 통해 운영체제의 Suspend-to-RAM 전환을 트리거합니다([SWS_SM_81112]).
  5. 웨이크업 및 정상 동작: 운영체제가 다시 깨어난 후 제어 애플리케이션은 RequestToLeaveSuspendMode(timeout)을(를) 호출합니다([SWS_SM_81111]). 허브는 등록된 모든 새틀라이트가 콜백 LeaveSuspendMode을(를) 실행하고 정상 작동 기능을 복원하도록 요청합니다([SWS_SM_00703], [SWS_SM_00707], [SWS_SM_00711]).

시퀀스 다이어그램: 준비부터 OS Suspend 및 재활성화에 이르는 Suspend-to-RAM 주기의 일반적인 흐름. 출처: [SWS_SM_00701], [SWS_SM_00702], [SWS_SM_00703], [SWS_SM_00707], [SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112].

오류 시나리오

모든 생성자 및 인터페이스 메서드는 noexcept(으)로 선언되어 있으며 완전한 예외 안전성(exception safe)을 제공합니다([SWS_SM_81103], [SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]). 오류 상태는 반환된 ara::core::Future 내의 보안 위반(Violations) 또는 특정 오류 코드를 통해 신호됩니다.

객체 생성 시 다음과 같은 위반(Violations)이 발생할 수 있습니다([SWS_SM_81103]):

  • InsufficientPermissionsViolation: 호출하는 프로세스에 충분한 권한이 없거나 모델링된 SuspendToRamHubMapping.process과(와) 일치하지 않습니다. 추가로 보안 이벤트 SEV_ACCESS_CONTROL_SM_IAM_ACCESS_DENIED이(가) 트리거됩니다([SWS_SM_00706]).
  • InstanceSpecifierMappingIntegrityViolation: 전달된 InstanceSpecifier을(를) 모델에서 확인할 수 없거나 PortPrototype 요소를 참조하지 않습니다.
  • PortInterfaceMappingViolation: 매핑 유형이 포트 인터페이스의 예상 유형과 일치하지 않습니다.
  • ProcessMappingViolation: 일치하는 InstanceRef이(가) 존재하지만, 모델링된 프로세스 중 현재 런타임 프로세스와 일치하는 프로세스가 없습니다.
  • InstanceSpecifierAlreadyInUseViolation: 해당 프로세스 내에서 이미 기존 인스턴스에 의해 InstanceSpecifier이(가) 사용 중입니다.
  • AraNotInitializedViolation: 호출 시점에 Adaptive Platform의 런타임 환경(ara)이 아직 초기화되지 않았습니다.

비동기 Suspend 및 Resume 요청 중에는 Future 객체에 다음과 같은 오류가 보고될 수 있습니다:

  • SmErrc::kCommunicationFailed: 하위 전송 계층에서 새틀라이트와의 통신이 실패했습니다(롤백 시맨틱 포함)([SWS_SM_81110], [SWS_SM_81111]).
  • SmErrc::kCommunicationTimeout: 하나 이상의 새틀라이트가 지정된 timeout 이내에 응답하지 않았습니다(롤백 시맨틱 포함)([SWS_SM_00707], [SWS_SM_81110], [SWS_SM_81111]).
  • SmErrc::kAtLeastOneRejected: RequestToEnterSuspendMode 시 일부 새틀라이트가 Suspend 상태로 진입했으나, 하나 이상의 새틀라이트가 요청을 거부했습니다(롤백 시맨틱 없음)([SWS_SM_81110]).
  • SmErrc::kAtLeastOneHadIssuesToLeave: RequestToLeaveSuspendMode 시 하나 이상의 새틀라이트가 kRejected(으)로 응답하여 모든 새틀라이트가 정상 상태로 올바르게 복귀하지 못했습니다(롤백 시맨틱 없음)([SWS_SM_00707], [SWS_SM_81111]).

이 가이드는 전적으로 AUTOSAR Adaptive Platform 릴리스 R25-11의 사양을 기반으로 합니다.
