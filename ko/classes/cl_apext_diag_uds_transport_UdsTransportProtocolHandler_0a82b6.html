컨텍스트

apext::diag::uds_transport::UdsTransportProtocolHandler 클래스는 AUTOSAR Adaptive의 Diagnostic Management(DM)에서 특정 및 독점 UDS 전송 프로토콜 플러그인을 위한 추상 기본 클래스입니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). 이 클래스는 일반 진단 코어를 DoIP 또는 CAN 기반 프로토콜과 같은 구체적인 전송 네트워크 및 전송 계층의 특성으로부터 분리합니다.

전송 핸들러는 기본적으로 세 파트너와 상호작용합니다:

  • Diagnostic Management Core: DM은 핸들러의 전체 라이프사이클을 관리하고 매니저 참조 apext::diag::uds_transport::UdsTransportProtocolMgr을(를) 통해 상태 및 데이터 인디케이션을 위한 대응부를 제공합니다([SWS_DM_09015], [SWS_DM_09025]).
  • 네트워크 계층 및 진단 클라이언트: 플러그인은 차량 외부 또는 내부 진단 테스터와의 물리적 또는 논리적 데이터 교환을 처리합니다([SWS_DM_00326], [SWS_DM_00351]).
  • 주기적 핸들러(선택 사항): 해당 전송 프로토콜이 주기적 전송을 지원하는 경우, 핸들러는 GetPeriodicHandler()을(를) 통해 UdsTransportProtocolPeriodicHandler에 대한 참조를 제공합니다([SWS_DM_01068]).

수명 주기

전송 프로토콜 구현의 라이프사이클은 DM에 의해 엄격하게 제어됩니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”, [SWS_DM_00329]). 생성은 생성자 UdsTransportProtocolHandler(handlerId, transportProtocolMgr)을(를) 통해 이루어지며, 이때 DM은 핸들러에 UdsTransportProtocolHandlerID 타입의 고유 식별자와 관련 UdsTransportProtocolMgr에 대한 참조를 할당합니다([SWS_DM_09015], [SWS_DM_09025]). 할당된 ID는 언제든지 GetHandlerID()을(를) 통해 조회할 수 있습니다([SWS_DM_00325]). 생성자는 스레드 안전한 것으로 명시되어 있습니다([SWS_DM_09015]).

비용이 많이 드는 프로토콜 초기화를 생성자로부터 분리하기 위해 DM은 이후 Initialize()을(를) 호출합니다([SWS_DM_00319], [SWS_DM_00329]). GetPeriodicHandler()을(를) 제외하고, DM은 InitializationResult::kInitializeOk이(가) 성공적으로 반환되기 전까지 핸들러의 다른 어떤 메서드도 호출해서는 안 됩니다([SWS_DM_01746], [SWS_DM_09017]). 초기화가 성공하면 DM은 Start()을(를) 통해 프로토콜을 시작합니다([SWS_DM_00322]). Start()은(는) 비동기식으로 실행되므로 DM은 기동 시간을 최소화하기 위해 여러 핸들러를 병렬로 시작할 수 있습니다([SWS_DM_00322]).

DM 애플리케이션이 ApplicationState.kTerminating 상태로 전환되면 Stop()을(를) 호출합니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). DM은 핸들러가 UdsTransportProtocolMgr::HandlerStopped(handlerId)을(를) 통해 중지를 확인할 때까지 대기합니다([SWS_DM_00340]). Stop()에서 반환된 후에는 확인 응답 HandlerStopped()을(를) 유일한 예외로 하여 핸들러 플러그인이 매니저의 다른 메서드를 호출해서는 안 됩니다([SWS_DM_01741], [SWS_DM_00323]). 이후 정리는 가상 소멸자([SWS_DM_09016])를 통해 수행됩니다.

상태 다이어그램: UDS 전송 프로토콜 핸들러의 라이프사이클 단계 및 전이 조건. 출처: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

사용 경로

작동 중에 핸들러는 UDS 메시지의 양방향 교환을 담당합니다:

  1. 메시지 수신(인디케이션): 채널에서 새 UDS 메시지가 수신되고 소스 주소, 대상 주소, 어드레싱 유형(물리적 또는 기능적), 전체 메시지 길이 및 첫 번째 페이로드 바이트(1바이트보다 큰 메시지의 경우 최소 2바이트)를 알게 되면 플러그인은 UdsTransportProtocolMgr::IndicateMessage(...)을(를) 호출합니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 “Indication of UDS message reception”, [SWS_DM_00342], [SWS_DM_00330]). 이때 핸들러는 globalChannelId 파라미터로 채널 식별자를 전달합니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”).
  2. 메시지 전송(트랜스미션): DM은 동일한 핸들러 및 동일한 채널을 통해 관련 UDS 진단 응답을 다시 전송합니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”, [SWS_DM_00348]). 이를 위해 DM은 Transmit(message, channelId)을(를) 호출합니다([SWS_DM_00327]). 메시지는 std::unique_ptr 방식에 따라 UdsMessageConstPtr(으)로 핸들러에 전달됩니다.
  3. 전송 확인 응답: 네트워크를 통해 메시지가 전송되었거나(또는 오류가 발생한 경우), 핸들러는 UdsTransportProtocolMgr::TransmitConfirmation(result, message)을(를) 통해 message의 소유권을 DM에 반환해야 합니다([SWS_DM_00327]). 이때 결과는 kTransmitOk 또는 kTransmitFailed(으)로 전달됩니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

또 다른 특정 사용 경로는 ECU 리셋 후 채널 복구(리셋 후 긍정 응답을 수반하는 UDS 서비스 0x11)입니다: 이 경우 DM은 재시작 전에 NotifyReestablishment(channelId)을(를) 호출합니다([SWS_DM_00326]). 플러그인은 연결 파라미터(예: IP 주소 및 포트)를 영구적으로 저장합니다. Start()을(를) 통한 재기동 후 플러그인은 동일한 진단 클라이언트의 재연결을 감지하고 UdsTransportProtocolMgr::ChannelReestablished(...)을(를) 통해 DM에 알립니다([SWS_DM_00326], [SWS_DM_01744]).

시퀀스 다이어그램: UDS 메시지 수신, 응답 전송 및 후속 확인 응답. 출처: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

오류 시나리오

인터페이스는 다양한 예외 및 오류 상황을 처리합니다:

  • 초기화 실패: Initialize()이(가) InitializationResult::kInitializeFailed 값을 반환하면([SWS_DM_09017]), DM은 이 전송 프로토콜의 시작 프로세스를 완전히 중단하고 해당 인스턴스에서 더 이상 어떠한 메서드도 호출하지 않습니다([SWS_DM_01745]).
  • 지원되지 않는 주기적 전송: 구체적인 프로토콜이 주기적 전송을 지원하지 않는 경우, GetPeriodicHandler() 호출은 오류 코드 kConfigurationMismatch와(과) 함께 ara::core::Result을(를) 반환합니다([SWS_DM_01068]).
  • 채널 복구 거부: 플러그인이 채널에 대한 영구 예약을 충족할 수 없는 경우(예: 비휘발성 저장 공간이 없거나 매핑이 불안정한 경우), NotifyReestablishment(channelId)은(는) false 값을 반환합니다([SWS_DM_00326]).
  • 네트워크 전송 오류: 네트워크 계층이 Transmit()을(를) 통해 위임된 메시지를 전송하지 못한 경우, 핸들러는 TransmitConfirmation에 결과 kTransmitFailed을(를) 전달해야 합니다([SWS_DM_00351]). 버퍼를 반환하지 않으면 DM에서 리소스 누수가 발생합니다.
  • 중지 후 시퀀스 위반: 플러그인이 Stop()에서 반환된 후 UdsTransportProtocolMgr에서 HandlerStopped() 이외의 다른 메서드를 호출하면 프로토콜 시퀀스 위반에 해당합니다([SWS_DM_00323], [SWS_DM_01741]).

이 클래스 가이드는 AUTOSAR Adaptive R25-11 사양을 기반으로 합니다.

Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().

              함수 NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
