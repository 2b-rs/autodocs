진단 메시지의 전송 및 전달을 위한 UDS 전송 플러그인의 추상 기본 클래스 역할을 합니다.

이 추상 클래스는 UDS 전송 플러그인이 적응형 진단 관리(AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”)에 표준화된 방식으로 연결하기 위한 기본 인터페이스 역할을 합니다. 파생 구현은 수신된 진단 메시지를 프로토콜 관리자에게 전달하고, 생성된 응답 메시지를 네트워크별 채널을 통해 진단 테스터로 전송합니다. 수명 주기는 생성, 별도 초기화, 비동기 시작 및 질서 있는 중지([SWS_DM_00329])의 엄격한 순서를 따릅니다. 인스턴스화 후 운영 메서드 호출은 스레드 안전하지 않으며 진단 코어의 조정된 제어가 필요합니다.

컨텍스트

클래스 apext::diag::uds_transport::UdsTransportProtocolHandler는 AUTOSAR Adaptive Platform의 diag 모듈 내에 있는 추상 기본 클래스입니다. 이는 독점적 또는 프로토콜별 UDS 전송 플러그인이 적응형 진단 관리(DM)에 연결되는 표준화된 인터페이스를 정의합니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). 자동차 네트워크 매체를 통한 진단 등 각각의 구체적인 전송 프로토콜은 이 인터페이스를 파생 서브클래스로 구현합니다. DM은 전체 운영 수명 주기 동안 각 핸들러 인스턴스를 독점적으로 소유하고 관리할 것으로 추정됩니다. 진단 코어와 플러그인 간의 상호작용은 생성자에서 전달되어 보호되어 저장되는 UdsTransportProtocolMgr& 타입의 참조 transportprotocolManager를 통해 발생합니다([SWS_DM_09015], [SWS_DM_09025]). 각 핸들러는 GetHandlerID()를 통해 쿼리할 수 있는 숫자 UdsTransportProtocolHandlerID로 식별됩니다([SWS_DM_00325]).

수명 주기

UDS 전송 프로토콜 핸들러의 수명 주기는 DM에 의해 엄격하게 순차적으로 제어됩니다([SWS_DM_00329]). 생성자 UdsTransportProtocolHandler([SWS_DM_09015])을 통한 인스턴스화 후 메서드 Initialize()는 실제 프로토콜 초기화를 객체 생성과 분리합니다([SWS_DM_00319]). GetPeriodicHandler()를 통한 선택적 쿼리를 제외하고, DM은 InitializationResult::kInitializeOk가 성공적으로 반환되기 전에 핸들러에서 메서드를 호출해서는 안 됩니다([SWS_DM_01746], [SWS_DM_09017]). 성공적인 초기화 후 Start() 호출은 핸들러를 활성 처리 상태로 전환합니다([SWS_DM_00322]). 시작 시간을 최소화하기 위해 Start()는 비동기 작업으로 설계되었으며, DM은 내부적으로 여러 핸들러의 병렬 시작을 조정할 것으로 추정됩니다. DM이 종료 시 ApplicationState.kTerminating 상태로 전환되면 Stop()를 통해 핸들러에 종료를 지시합니다([SWS_DM_00323], [SWS_DM_00333]). DM은 완료를 기다리고, 핸들러는 UdsTransportProtocolMgr::HandlerStopped()를 호출하여 이를 확인합니다([SWS_DM_00340]). Stop()에서 반환된 후 플러그인은 HandlerStopped()를 제외하고 관리자에 대한 어떠한 메서드 호출도 금지됩니다([SWS_DM_01741]). 리소스 해제는 최종적으로 가상 소멸자([SWS_DM_09016])를 통해 수행됩니다. 생성자는 스레드 안전하지만 운영 인터페이스 메서드는 스레드 안전하지 않은 것으로 선언되어 있습니다.

상태 다이어그램: UDS 전송 핸들러의 수명 주기 단계 및 상태 전이. 출처: [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00329], [SWS_DM_01745], [SWS_DM_01746]

사용 경로

정규 진단 작업에서 핸들러는 수신 메시지를 처리하고 응답을 전송합니다. 네트워크 인터페이스에 최소한 소스 주소, 대상 주소, 주소 유형(물리적 또는 기능적), 총 메시지 길이 및 다중 바이트 페이로드의 경우 처음 2바이트(payloadInfo)가 제공되는 즉시 구현은 UdsTransportProtocolMgr::IndicateMessage()를 통해 관리자에게 요청을 보고합니다([SWS_DM_00342], AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”). 각 요청은 고유한 채널에 할당됩니다(AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”). 응답하기 위해 DM은 Transmit(message, channelId)를 사용하여 동일한 핸들러 및 채널에 진단 응답을 전달합니다([SWS_DM_00327], [SWS_DM_00348]). 물리적 전송 후 핸들러는 전달받은 메시지 객체를 UdsTransportProtocolMgr::TransmitConfirmation()를 통해 관리자에게 반환합니다([SWS_DM_00327], [SWS_DM_00351]). 특수한 사용 경로는 재부팅 후 긍정 응답이 있는 ECU 리셋(UDS 서비스 0x11)과 관련됩니다. 여기서 DM은 리셋 전에 NotifyReestablishment(channelId)를 통해 핸들러가 연결 정보를 비휘발성으로 저장하도록 요청하며, 재부팅 및 새로운 Start() 후 핸들러는 ChannelReestablished()를 통해 동일한 채널의 복원을 보고합니다([SWS_DM_00326], [SWS_DM_01744]).

시퀀스 다이어그램: UDS 메시지 표시 및 응답 전송 흐름. 출처: [SWS_DM_00327], [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00351]

오류 시나리오

전송 계층의 초기화가 실패하고 Initialize()가 상태 InitializationResult::kInitializeFailed를 반환하면, DM은 이 프로토콜의 시작 프로세스를 즉시 중단하고 이 인스턴스에서 더 이상 메서드를 호출하지 않습니다([SWS_DM_01745], [SWS_DM_09017]). 전송 프로토콜에서 주기적 전송이 지원되지 않는 경우 GetPeriodicHandler() 호출은 오류 코드 kConfigurationMismatch가 포함된 ara::core::Result를 반환합니다([SWS_DM_01068]). ECU 리셋을 위해 요청된 채널 복원을 보장할 수 없는 경우 NotifyReestablishment()가 실패하고 반환 값 false를 통해 이를 알립니다([SWS_DM_00326]). 마지막으로 네트워크 계층에서 진단 응답의 전송 프로세스가 실패하면 핸들러는 관리자에게 확인 시 TransmitConfirmation()의 인수 result를 kTransmitFailed로 설정하여 이를 알려야 합니다([SWS_DM_00351]).

이 가이드는 AUTOSAR 사양 R25-11을 기반으로 자동 생성되었습니다.

          순수 가상 메서드 Initialize은(는) apext::diag::uds_transport::UdsTransportProtocolHandler 인스턴스를 명시적으로 초기화하는 데 사용되며 이 과정을 객체 생성과 형식적으로 분리합니다 [SWS_DM_00319]. 이 메서드는 Diagnostic Manager(DM)에 의해 매개변수 없이 동기적으로 호출되며, 예외를 발생시키지 않고(noexcept) InitializationResult을(를) 반환합니다 [SWS_DM_00319] [SWS_DM_09017].
          

          수명주기 및 동시성
          

          이 호출은 UDS 트랜스포트 레이어의 수명 주기 관리에 포함되어 있습니다 AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”. DM은 정해진 순서대로 단계를 관리해야 합니다: 생성, Initialize 호출, Start을(를) 통한 시작 및 Stop을(를) 통한 종료 [SWS_DM_00329]. 이 메서드는 스레드 안전하지 않은 것(not thread-safe)으로 명시되어 있으며 [SWS_DM_00319]; 따라서 DM은 병렬 접근이 없는 동기 초기화 단계의 일환으로 이를 실행할 것으로 추정됩니다.
          

          오류 처리 및 상호 작용
          

          이 메서드는 열거자 InitializationResult::kInitializeOk 또는 InitializationResult::kInitializeFailed을(를) 통해 결과를 알립니다 [SWS_DM_09017]. DM의 추가 동작은 반환 값에 직접적으로 의존합니다:

              함수 NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.

                          메소드 Transmit은(는) 전송 프로토콜의 특정 채널을 통해 UDS 진단 메시지를 네트워크로 전송하기 위해 호출됩니다([SWS_DM_00327], SWS Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”). 이는 ISO 14229-2에 따른 서비스 T_Data.req을(를) 매핑합니다([SWS_DM_00327]). 호출자는 전송할 메시지를 unique_ptr의 소유권 스타일을 갖는 UdsMessageConstPtr(으)로 전달하고, 이전에 수신된 요청의 채널과 일치해야 하는 channelId을(를) 전달합니다([SWS_DM_00327], [SWS_DM_00348], SWS Diagnostics §7.1.1.4 “Channel Notifications”).
                          


                          순서 및 수명 주기와 관련하여, Diagnostic Manager는 핸들러 초기화가 kInitializeOk(으)로 완료되고([SWS_DM_01746]) 메소드 Start이(가) 호출된([SWS_DM_01743]) 후에만 Transmit을(를) 호출할 수 있습니다. 해당 연산은 not thread-safe 및 exception safe(으)로 지정되어 있으므로([SWS_DM_00327]), 해석상 병렬 전송 요청의 조정은 호출자 측인 Diagnostic Manager에서 수행되어야 할 것으로 보입니다.
                          


                          이 함수는 동기식으로 반환값을 제공하지 않습니다. 트랜스포트 핸들러는 전송 후 메시지 포인터를 apext::diag::uds_transport::UdsTransportProtocolMgr::TransmitConfirmation을(를) 통해 Diagnostic Manager로 비동기식으로 반환해야 할 의무가 있습니다([SWS_DM_00327], [SWS_DM_00312]). 네트워크 레벨에서 전송이 성공하면 결과 kTransmitOk이(가) 보고되고, 그렇지 않으면 kTransmitFailed이(가) 보고됩니다([SWS_DM_00351]).
                          


                          

                          이 사용 지침은 AUTOSAR Adaptive R25-11 사양을 기반으로 합니다.
