사용 목적

<SI-Namespace>::skeleton::<SI>Skeleton는 ARXML-Manifest의 서비스 인터페이스 모델에서 생성 도구 체인에 의해 생성된 Skeleton 기본 클래스이다. 계층적 SI 네임스페이스와 클래스 이름은 Manifest에서 파생된다. 생성된 헤더는 모델에서 파생된 <SiShortname>_skeleton.h 경로 [SWS_CM_00002]를 따릅니다. 별도의 서비스 구현은 이 클래스에서 상속되며 순수 가상 서비스 메서드 또는 Fire-and-forget 메서드 [SWS_CM_00191] [SWS_CM_90434]를 덮어씁니다.

창조와 파괴

파생된 구현은 ara::core::InstanceSpecifier, 단일 InstanceIdentifier 또는 식별자 컨테이너를 사용하여 뼈대를 생성할 수 있다. 기본적으로 처리 모드는 kEvent [SWS_CM_00152] [SWS_CM_00130] [SWS_CM_00153]이다. 가상 소멸자는 기본 클래스 [SWS_CM_11370]를 통한 소멸을 허용한다.

  • 각 모델 Event에는 멤버 events::<Event>이 있습니다. 구현은 skeleton::events::<Event>::Send [SWS_CM_99557] [SWS_CM_00162] 이상의 값을 전송합니다.

제한 사항 및 오류 처리

초기화되지 않은 필드 값, 필드 세트 핸들러 누락 또는 통신 오류 OfferService()로 인해 [SWS_CM_00101]가 실패할 수 있다. E2E 오류 핸들러는 재정의될 수 있지만 재진입이 불가능한다. CRC 오류가 발생한 경우 통과된 DataID는 신뢰할 수 없는 [SWS_CM_10470]이다. 모든 메소드 [SWS_CM_00093] [SWS_CM_00094] [SWS_CM_00095]에 대해 전송 오류 핸들러를 등록하고 제거할 수 있다.

건축적 임베딩

Skeleton는 Provider 측에서 생성된 어댑터이다. 서비스 구현은 일반적으로 이 어댑터에서 파생되므로 Communication Management를 통해 메서드, 이벤트 및 필드를 제공한다. 인터페이스는 서비스 인터페이스 설명에서 생성된다. 기본 모델링은 Service Interface에서 이벤트, 필드, 메소드 및 트리거를 허용한다. EXP ARAComAPI §4.1 “Proxy/Skeleton Architecture” TPS Manifest §4.2 “Service Interface”

오퍼링 및 메소드 처리

OfferService() 이전에는 Consumer에 대한 인스턴스가 표시되지 않는다. 호출이 아직 반환되지 않은 경우에도 호출 후에 메서드가 이미 전달될 수 있다. StopOfferService() 이후에는 더 이상 통화가 전달되지 않는다. 생성 시 선택한 처리 모드는 Skeleton 인스턴스의 전체 수명 동안 적용된다. EXP ARAComAPI §5.4.4 “Offering Service instance” §5.4.5 “Polling and event-driven processing modes”

활동 다이어그램: 서비스 인스턴스는 OfferService() 이후에만 표시됩니다. 생성자에서 선택한 모드에 따라 처리가 결정됩니다. 출처: EXP ARAComAPI §5.4.4 “Offering Service instance” 및 §5.4.5 “Polling and event-driven processing modes”.

함수 E2EErrorHandler [SWS_CM_10470] Upstream: RS_CM_00401, RS_CM_00402

virtual void E2EErrorHandler (ara::com::e2e::ComE2EErrc errorCode, ara::com::e2e::DataID dataID, ara::com::e2e::MessageCounter message Counter);

Implementation may be overridden by the actual ServiceSkeleton implementation and it is not required to be reentrant. If the E2E error is a CRC error then some parts of the received message are faulty. If this part is the DataID then the E2E error handler is called with a faulty DataID. Consequently, in case of CRC error the server application can not rely on the DataID received by its error handler.
