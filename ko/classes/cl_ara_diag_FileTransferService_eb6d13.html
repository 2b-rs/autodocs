어댑티브 애플리케이션이 UDS 진단 서비스를 위한 파일 및 디렉터리 작업을 제공할 수 있도록 합니다.

이 서비스 인터페이스는 UDS 서비스 RequestFileTransfer([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”)을 위해 애플리케이션별 파일 전송을 Diagnostic Management에 연결하는 역할을 합니다. 인스턴스화 후 애플리케이션은 Offer()을 사용하여 들어오는 파일 요청의 전달을 활성화하고, 특수 핸들러 메서드([SWS_DM_01336])를 통해 읽기, 쓰기 또는 삭제와 같은 파일 작업을 비동기식으로 처리합니다. 읽기 및 쓰기 작업의 경우 서비스는 실제 데이터 전송이 처리되는 세션 객체를 제공합니다. 이 클래스의 인스턴스는 복사할 수 없으며 인스턴스 지정자를 통한 고정 바인딩이 필요합니다.

컨텍스트

클래스 ara::diag::FileTransferService은 AUTOSAR Adaptive Platform([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”)에서 UDS 서비스 RequestFileTransfer(0x38)을 구현하기 위한 진단 인터페이스를 정의합니다. 이 클래스는 프로세스 경계를 넘어 파일 또는 디렉터리의 읽기, 쓰기, 이어받기 및 삭제를 유연하게 처리하기 위해 Diagnostic Management(DM 또는 Diagnostic Server)와 구체적인 진단 애플리케이션 사이의 ServiceInterface 역할을 합니다(SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”).

파일 전송 시나리오에는 일반적으로 세 당사자가 관여합니다. 외부 UDS 클라이언트(진단 테스터), 중개자로서의 Diagnostic Server, FileTransferService을 상속받는 어댑티브 애플리케이션입니다. 진단 요청이 수신되면 Diagnostic Server는 서비스의 구현된 가상 메서드로 요청을 위임합니다([SWS_DM_01313], [SWS_DM_01314]). 후속 데이터 전송(UDS 0x36 TransferData) 및 완료(UDS 0x37 RequestTransferExit)를 위해 Diagnostic Management는 세션 객체(DataTransferReadSession 또는 DataTransferWriteSession)를 통해 제공되는 핸들러 클래스에 직접 액세스합니다([SWS_DM_01317], [SWS_DM_01318]).

컨텍스트 다이어그램: UDS 클라이언트, Diagnostic Management, 서비스 구현 및 전송 세션 간의 상호 작용. 출처: [SWS_DM_01317], [SWS_DM_01318], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”.

수명 주기

FileTransferService의 인스턴스는 모델링된 ara::core::InstanceSpecifier 및 동시성 모델 ConcurrencyType를 지정하여 생성됩니다([SWS_DM_01325]). ConcurrencyType를 통해 클래스의 콜백 메서드가 스레드 안전(kConcurrent)하게 구현되어야 하는지 아니면 스레드 안전하지 않게(kNotConcurrent) 구현되어야 하는지가 결정됩니다([SWS_DM_01325], [SWS_DM_01331]). 이 클래스는 보호된 단일 기능으로서 복사할 수 없으나([SWS_DM_01327], [SWS_DM_01329]), 이동 시맨틱을 지원합니다([SWS_DM_01328], [SWS_DM_01330]).

인스턴스화 후, Diagnostic Management가 들어오는 요청을 전달하도록 하려면 메서드 Offer()을 통해 서비스를 명시적으로 활성화해야 합니다([SWS_DM_01336]). StopOffer()를 사용하면 전달을 언제든지 다시 비활성화할 수 있습니다([SWS_DM_01337]). 해석: Diagnostic Management의 고아 콜백 액세스를 방지하기 위해 가상 소멸자 ~FileTransferService()에 의해 객체가 파괴되기 전에 StopOffer()를 호출해야 할 것으로 보입니다([SWS_DM_01326]). 질문 Q-3c5c406a144ced0c (열림) Offer(), StopOffer() 및 소멸자 모두 스레드 안전하지 않습니다([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

상태 다이어그램: 인스턴스화, 제공 및 종료 사이의 FileTransferService 인스턴스 상태 전이. 출처: [SWS_DM_01325], [SWS_DM_01336], [SWS_DM_01337], [SWS_DM_01326].

사용 경로

파일 작업의 일반적인 흐름은 구성, 작업 트리거 및 후속 블록 전송으로 나뉩니다. 먼저 모드 ReadFile(0x04)을 갖는 UDS 요청 0x38이 발생하면 Diagnostic Management는 RequestReadFile로 호출을 전달합니다([SWS_DM_01314], [SWS_DM_01331]). 애플리케이션은 파일 이름과 형식 및 메타 정보를 처리하고, ara::core::Future를 통해 DataTransferReadSession와 파일 크기(FileSizes)로 구성된 튜플을 비동기식으로 반환합니다([SWS_DM_01331]). 해석: 어떠한 전송 전략(예: 복사, 제로 카피 또는 파일 시스템 핸들)을 사용할지는 애플리케이션이 각 세션 클래스를 인스턴스화할 때 결정하는 것으로 추정됩니다(SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”, [SWS_DM_01317]). 질문 Q-80b541ae6dd7cc34 (열림)

긍정 응답 후 클라이언트는 TransferData(0x36)을 통해 데이터 블록을 요청합니다. 그러면 Diagnostic Server는 DataTransferReadSession의 등록된 핸들러의 Read 메서드를 직접 호출합니다([SWS_DM_01317]). 모든 블록이 전송되면 클라이언트는 RequestTransferExit(0x37)로 트랜잭션을 완료하며, 그 후 Diagnostic Server는 핸들러의 Exit 메서드를 호출합니다([SWS_DM_01318]). 모드 WriteFileMode([SWS_DM_01324])을 사용하는 RequestWriteFile([SWS_DM_01313], [SWS_DM_01333])을 통한 쓰기, RequestResumeWriteFile([SWS_DM_01316], [SWS_DM_01334])를 통한 이어받기, RequestReadDirectory([SWS_DM_01315], [SWS_DM_01332])를 통한 디렉터리 읽기 또는 DeleteFile([SWS_DM_01335])을 통한 직접 삭제에도 유사한 패턴이 적용됩니다.

시퀀스 다이어그램: UDS 0x38, 0x36 및 0x37을 통한 읽기 작업 흐름. 출처: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331].

오류 시나리오

오류는 여러 단계에서 발생할 수 있습니다:

  • 생성 위반: InstanceSpecifier의 확인 또는 매핑에 실패하면 InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation 또는 InstanceSpecifierAlreadyInUseViolation와 같은 모델링 오류가 발생합니다([SWS_DM_01325]).
  • 활성화 오류: 서비스가 이미 활성화된 상태에서 Offer()을 반복 호출하면 오류 DiagOfferErrc::kAlreadyOffered이 반환됩니다([SWS_DM_01336]).
  • 진단 오류 코드(NRC): 작업을 성공적으로 실행할 수 없는 경우, 콜백 메서드는 ara::core::Future에서 DiagUdsNrcErrc을 통해 적절한 부정 UDS 응답 코드(ISO 14229-1에 따른 NRC)를 반환합니다([SWS_DM_01331], [SWS_DM_01333], [SWS_DM_01335]).
  • 중단 처리: 전달된 CancellationHandler 객체를 통해 애플리케이션은 대화가 중단되었는지 IsCanceled로 확인하거나, SetNotifier를 통해 비동기 중단에 대한 알림 함수를 등록할 수 있습니다([SWS_DM_01331], [SWS_DM_01335]).

이 가이드는 전적으로 AUTOSAR 사양 R25-11을 기반으로 하며 자동으로 작성되었습니다.

                                      클래스 ara::diag::FileTransferService의 함수 StopOffer은(는) Diagnostic Management에서 서비스를 등록 취소하는 데 사용됩니다([SWS_DM_01337]; AUTOSAR_AP_SWS_Diagnostics §8.18.1.2.3.7 “StopOffer”). 그 호출은 DM이 이 시점부터 해당 서비스 인스턴스로 수신 진단 요청을 더 이상 전달하지 않도록 합니다. 해당 인터페이스는 헤더 #include "ara/diag/file_transfer.h"에 정의되어 있고 시그니처 void StopOffer() const noexcept;을(를) 가지며, 매개변수를 요구하지 않고 반환값을 갖지 않습니다. 호출은 동기적으로 실행됩니다.
                                      

                                      StopOffer에는 오류 메커니즘이 제공되지 않습니다. 이 메서드는 예외 안전(exception safe) 및 식별자 noexcept(으)로 선언되어 있습니다([SWS_DM_01337]). 예외가 발생하지도 않고 오류 코드가 애플리케이션에 반환되지도 않습니다. 전달 비활성화는 API 관점에서 실패하지 않습니다.
                                      

                                      명세에 따라 StopOffer은(는) 스레드 안전하지 않은 것(not thread-safe)으로 분류되어 있습니다([SWS_DM_01337]). 따라서 ara::diag::FileTransferService의 동일한 인스턴스에 대한 병렬 접근은 애플리케이션 측에서 동시성에 대해 보호되어야 합니다. 해석: 더 이상 작동 준비가 되지 않은 루틴으로 요청이 유입되지 않도록 하기 위해, 비활성화는 일반적으로 객체가 파괴되기 전이나 처리 애플리케이션의 정상적인 종료 중에 수행될 것으로 추정됩니다. 질문 Q-e7bb2a5621c39160 (열림)
                                      

                                      StopOffer을(를) 통한 비활성화는 제공되는 진단 서비스에 대한 AUTOSAR Adaptive의 통합 아키텍처 패턴을 따릅니다. 이는 ara::diag::DownloadService([SWS_DM_00793]), ara::diag::UploadService([SWS_DM_00803]), ara::diag::CommunicationControl([SWS_DM_00810]) 및 ara::diag::Monitor([SWS_DM_01089]; AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”)과(와) 같은 관련 클래스의 동등한 비활성화 함수와 일치합니다.
