서비스 스켈레톤이 필드 요청을 제공, 업데이트 및 타입 안전하게 처리할 수 있도록 지원합니다.

클래스 <SI-Namespace>::skeleton::fields::<Field>은(는) 서버 측에서 ServiceInterface의 필드를 제공하고 제공된 서비스에 대한 getter, setter 및 알림 기능을 연결합니다. 공급자 애플리케이션은 수신되는 읽기 및 쓰기 접근을 위해 비동기 핸들러([SWS_CM_00114], [SWS_CM_00116])를 등록하고, 메서드 Update([SWS_CM_00119])을(를) 통해 구독 중인 클라이언트에 값 변경 사항을 적극적으로 배포합니다. 이때 전달되는 핸들러는 반드시 유효해야 하며, kMinimumSendIntervalViolationError와(과) 같은 오류를 방지하기 위해 송신 호출은 구성된 최소 송신 시간을 준수해야 합니다.

컨텍스트

템플릿 클래스 <SI-Namespace>::skeleton::fields::<Field>은(는) Adaptive Communication Management 내에서 ServiceInterface에 모델링된 필드의 서버 측 표현을 캡슐화합니다. 서비스 인터페이스에 정의된 각 필드에 대해 미들웨어는 헤더 경로 #include "<SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h"을(를) 사용하여 네임스페이스 skeleton::fields에 해당 클래스 인스턴스를 생성합니다. 필드는 선택적으로 getter, setter 및 알림 기능을 가짐으로써 데이터 전송과 메서드 호출의 기능적 특징을 결합합니다. 필드 값의 관련 데이터 유형은 타입 별칭 FieldType을(를) 통해 제공됩니다([SWS_CM_11402]). 주요 상호작용 파트너로는 서비스를 제공하는 공급자 애플리케이션, 중개자 역할을 하는 스켈레톤 필드 인스턴스, 구독하는 서비스 소비자(Proxy), 그리고 Executor 형태의 선택적 실행 컨텍스트가 있습니다([SWS_CM_11360], [SWS_CM_11362]).

컨텍스트 다이어그램: 요청 및 알림 시 스켈레톤 필드 클래스의 상호작용 파트너. 출처: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360].

수명 주기

필드 인스턴스의 수명은 상위 서비스 스켈레톤 인스턴스와 밀접하게 연결되어 있습니다. 해석: Field 인스턴스는 연결된 스켈레톤 클래스의 멤버 객체로 인스턴스화되어 해당 수명 주기를 완전히 공유할 것으로 추정됩니다. 개별 인터페이스 메서드의 가용성은 소프트웨어 설계의 정의에 직접적으로 의존합니다: 메서드 RegisterGetHandler은(는) 필드가 Field.hasGetter == TRUE(으)로 구성된 경우에만 존재하며([SWS_CM_00114]), RegisterSetHandler은(는) Field.hasSetter == TRUE을(를) 통한 setter의 존재를 전제로 합니다([SWS_CM_00116]). E2E 전송 오류로부터 통신을 보호하기 위해 애플리케이션은 SetTransportFaultConditionHandler을(를) 통해 특정 핸들러를 등록할 수 있으며([SWS_CM_00096]), 필요한 경우 UnsetTransportFaultConditionHandler을(를) 사용하여 이를 다시 제거할 수 있습니다([SWS_CM_00098]). 동시성과 관련하여, 템플릿 매개변수 ExecutorT을(를) 갖는 오버로드(예: ara::core::Executor)는 콜백 함수의 실행을 정의된 비동기 실행 컨텍스트로 이전할 수 있는 가능성을 제공합니다([SWS_CM_11360], [SWS_CM_11362], [SWS_CM_00097], AUTOSAR_AP_EXP_ARAComAPI 11쪽).

사용 경로

정규 작동 절차는 콜백 함수의 구성, 쿼리 처리 및 데이터 업데이트의 능동적 전송으로 구분됩니다:

해석: 들어오는 요청을 빈틈없이 처리할 수 있도록, 핸들러 등록은 서비스 제공 전에 수행되는 것이 적절할 것으로 추정됩니다. 애플리케이션은 getter가 존재하는 경우 RegisterGetHandler을(를) 통해 ara::core::Future<FieldType>을(를) 반환하는 콜백 함수를 바인딩합니다([SWS_CM_00114]). 수정 접근을 위해 애플리케이션은 RegisterSetHandler을(를) 통해 새 값을 수신 및 처리하고 결과 상태를 Future를 통해 마찬가지로 비동기식으로 제공하는 핸들러를 등록합니다([SWS_CM_00116]). 서비스 제공자가 필드 값을 자체적으로 업데이트하려는 경우, 새 값과 함께 메서드 Update을(를) 호출합니다([SWS_CM_00119], AUTOSAR_AP_EXP_ARAComAPI 11쪽). 이를 통해 필드의 내부 상태가 새로 설정됩니다. 필드가 알림 기능과 함께 모델링된 경우(Field.hasNotifier == TRUE), Update은(는) 변경된 데이터 값을 등록된 모든 구독자에게 즉시 전송하도록 트리거합니다([SWS_CM_00119], [SWS_CM_00120], [SWS_CM_00162]).

시퀀스 다이어그램: 핸들러 등록, 요청 처리 및 데이터 업데이트의 전형적인 절차. 출처: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119].

오류 시나리오

오류 조건은 등록 시 프로그래밍 계약 위반 또는 런타임 시 전송 오류로 나타납니다. 핸들러를 위한 모든 등록 메서드(RegisterGetHandler, RegisterSetHandler 및 SetTransportFaultConditionHandler)는 noexcept(으)로 지정되어 있으며 예외 안전(exception safe) 보장을 갖습니다([SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00096]). 사전 조건으로 전달된 호출 가능 객체(Callable)가 존재해야 하며 null이 아니어야 합니다. 이를 준수하지 않으면 InvalidHandlerViolation이(가) 발생합니다([SWS_CM_00114], [SWS_CM_11360], [SWS_CM_00116], [SWS_CM_11362], [SWS_CM_00096], [SWS_CM_00097]).

Update을(를) 통한 능동적 업데이트 시 오류 피드백은 반환 유형 ara::core::Result<void>을(를) 통해 이루어집니다([SWS_CM_00119]). 오류가 발생하면 Result 객체는 ara::com::ComErrc의 오류 코드를 제공합니다. 특히 배포 속성 ServiceInterfaceDeploymentElement.minimumSendInterval에 지정된 것보다 짧은 간격으로 전송하면 오류 ComErrc::kMinimumSendIntervalViolationError이(가) 반환됩니다([SWS_CM_00119]).

사용

RegisterGetHandler 메서드는 서버 측에서 Skeleton의 필드 객체에 대해 호출됩니다([SWS_CM_00114]). 해당 필드의 인터페이스 설명에 Getter가 구성된 경우에만 생성된 코드에 존재합니다(Field.hasGetter == TRUE)(EXP ARAComAPI §5.4.8.1 “Registering Getters”). Proxy의 수신 Get() 요청 시 바인딩 구현에 의해 호출되는 std::function<ara::core::Future<FieldType>()> 타입의 콜백 handler이(가) 전달됩니다.

이러한 핸들러의 등록은 완전히 선택 사항입니다(EXP ARAComAPI §5.4.8.1 “Registering Getters”). 일반적으로 Communication Management가 Update()을(를) 통해 마지막으로 설정된 값을 캐시하고 Proxy 요청에 자체적으로 응답하므로, 서비스 구현에는 Getter 핸들러가 필요하지 않습니다. 핸들러는 필드 값 조회가 많은 시간을 소요하거나 연산 부하가 커서 실제 필요할 때만 Promise/Future 패턴을 통해 비동기적으로 수행해야 하는 경우에 특히 유용합니다.

오류 처리 및 제약 조건

해당 함수는 반환값이 없으며, noexcept(으)로 선언되어 있고 예외에 안전(exception safe)합니다([SWS_CM_00114]). 전달된 Callable이 존재하지 않거나 null인 경우 오류 InvalidHandlerViolation이(가) 발생합니다([SWS_CM_00114]).

상호 작용

Setter가 존재할 때 호출이 의무적인 RegisterSetHandler(EXP ARAComAPI §5.4.8.2 “Registering Setters”)과 달리, RegisterGetHandler은(는) 순수하게 선택 사항입니다. 핸들러를 특정 실행 컨텍스트에서 비동기적으로 처리해야 하는 경우, ExecutorT을(를) 사용하는 오버로드된 템플릿 함수를 추가로 사용할 수 있습니다([SWS_CM_11360]).

이 사용 지침은 AUTOSAR R25-11 명세를 바탕으로 AI에 의해 생성되었습니다.

      사용
      

      네임스페이스 <SI-Namespace>::skeleton::fields::<Field>의 RegisterGetHandler 메서드는 프록시의 수신 Get() 호출 시 통신 바인딩에 의해 호출되는 애플리케이션 측 콜백(handler)을 등록합니다([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 “Registering Getters”). 매개변수가 없는 기본 오버로드 [SWS_CM_00114]과(와) 달리, 이 메서드는 콜백 실행이 비동기적으로 수행되는 ExecutorT 타입의 실행 컨텍스트 executor을(를) 받습니다([SWS_CM_11360]). 실행자로는 표준화된 ara::core::Executor 또는 동일한 인터페이스를 가진 사용자 정의 타입을 사용할 수 있습니다([SWS_CM_11360]).
