클래스 ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

포맷팅되거나 모델링된 로그 메시지를 스레드 안전하게 수집하기 위한 로깅 컨텍스트를 캡슐화합니다.

ara::log::Logger 클래스는 임시 스트림 또는 모델링된 메시지 포맷을 통해 애플리케이션 프로세스 내에서 로그 메시지를 수집하기 위한 컨텍스트를 나타냅니다 [SWS_LOG_00064]. 기본 생성자가 삭제되었으므로 생성 및 수명 주기 관리는 로깅 프레임워크에 의해 전적으로 수행됩니다 [SWS_LOG_00259]. 시간 소모적인 메시지 데이터 준비 전에 현재 활성화된 보고 수준을 조회할 수 있습니다. 해당 클래스의 모든 인터페이스는 스레드 안전하게 명세되어 있어 여러 스레드에서의 동기화 없는 호출을 허용합니다.

컨텍스트

ara::log::Logger 클래스는 log 모듈 내의 애플리케이션 프로세스 또는 프로세스 영역 내에서 로거 컨텍스트를 나타냅니다. 이러한 컨텍스트는 특정 컨텍스트 ID, 연관된 설명 및 기본 로그 레벨을 캡슐화합니다. 애플리케이션 개발자는 LogStream [SWS_LOG_00064]과(와) 같은 스트림 객체를 통하거나 구조화된 모델링 메시지로서 로그 메시지를 로깅 프레임워크에 전달하기 위해 로거 인스턴스와 상호작용합니다 [SWS_LOG_00204]. 이 인스턴스들은 애플리케이션 내부 스레드와 로깅 백엔드 사이의 중재자 역할을 합니다.

컨텍스트 다이어그램: 애플리케이션, 로깅 프레임워크 및 LogStream 간의 로거 통합. 출처: [SWS_LOG_00064], [SWS_LOG_00259].

수명 주기

인스턴스 관리는 로깅 프레임워크의 엄격한 소유권을 따릅니다. 생성 시 로깅 백엔드로의 자동 등록 및 애플리케이션 프로세스 종료 시의 등록 해제를 보장하기 위해 기본 생성자는 삭제되었습니다 [SWS_LOG_00259]. 애플리케이션은 Logger 객체를 직접 인스턴스화할 수 없으며 허용되지도 않으므로, 대신 생성 함수 ara::log::CreateLogger을(를) 사용해야 합니다. 소멸 및 해제는 로깅 프레임워크에 의해 제어되는 소멸자 [SWS_LOG_00260]을(를) 통해 수행되므로, 사용자는 수명 주기를 신경 쓸 필요가 없습니다.

동시성과 관련하여 [SWS_LOG_00070], [SWS_LOG_00255] 및 [SWS_LOG_00260]을(를) 포함한 모든 접근 메서드는 스레드 안전(thread-safe)으로 명세되어 있습니다. 이를 통해 애플리케이션 측의 추가 동기화 메커니즘 없이도 여러 동시 스레드가 동일한 로거 컨텍스트를 동시에 사용할 수 있습니다.

사용 경로

로거의 일반적인 사용법에는 현재 구성 확인, 임계값 조정 및 메시지 전송이 포함됩니다:

  • 출력 권한 확인: 복잡한 로그 데이터 준비 전에 IsEnabled을(를) 사용하여 원하는 로그 레벨이 활성 보고되는지 조회할 수 있습니다 [SWS_LOG_00070].
  • 구성: 로거 인스턴스의 최소 보고 임계값은 런타임에 SetThreshold을(를) 통해 재구성할 수 있습니다 [SWS_LOG_00255].
  • 스트림 기반 로깅: 개별 심각도 레벨을 위한 특정 메서드들 – LogFatal [SWS_LOG_00064], LogError [SWS_LOG_00065], LogWarn [SWS_LOG_00066], LogInfo [SWS_LOG_00067], LogDebug [SWS_LOG_00068] 또는 LogVerbose [SWS_LOG_00069] – 및 동적 WithLevel [SWS_LOG_00131]을(를) 통해 LogStream 객체가 생성됩니다. 이는 연산자 <<을(를) 통해 데이터를 수신합니다. 일반적으로 스트림 객체의 수명은 명령문의 세미콜론과 함께 끝납니다 [SWS_LOG_00064].
  • 모델링된 메시지: 대안적으로 타입화되고 모델링된 메시지를 Log [SWS_LOG_00204]을(를) 사용하여 직접 전달하거나, 속성을 지정하여 LogWith [SWS_LOG_00133]을(를) 통해 전달할 수 있습니다.

시퀀스 다이어그램: 임계값 확인 및 스트림 기반 로깅 시의 일반적인 순서. 출처: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064].

오류 시나리오

해당 클래스의 인터페이스는 대부분 noexcept 및 예외 안전(exception safe)(으)로 명세되어 있어 예기치 않은 런타임 중단을 최소화합니다 [SWS_LOG_00070], [SWS_LOG_00255]. 그럼에도 불구하고 정형 오류 조건과 에지 케이스가 존재합니다:

  • 잘못된 모델 매개변수: 모델링된 메시지의 명세와 일치하지 않는 인수를 사용하여 Log을(를) 호출하는 경우, C++ 프로그램이 잘못 구성된 것이며(ill-formed) 컴파일 시점에 실패합니다 [SWS_LOG_00204].
  • 누락된 속성 특성: LogWith의 튜플에 요구되는 속성 기준을 충족하지 않는 타입이 포함되어 있는 경우, 해당 함수는 오버로드 해결에 참여하지 않습니다 [SWS_LOG_00133]. 이러한 제외는 아마도 SFINAE 또는 개념을 통해 수행될 것으로 추정됩니다.
  • 해제 시 예외 안전성: 소멸자 ~Logger은(는) not exception safe(으)로 선언되어 있습니다 [SWS_LOG_00260]. 이는 로깅 백엔드 등록 해제 시 예외를 통해 전파되어서는 안 되는 오류가 발생할 수 있기 때문인 것으로 추정됩니다.

이 가이드는 Adaptive Release R25-11의 log 모듈에 대한 AUTOSAR 명세만을 기반으로 합니다.
