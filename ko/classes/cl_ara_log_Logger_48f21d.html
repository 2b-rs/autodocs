클래스 ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

컨텍스트

ara::log::Logger 클래스는 AUTOSAR Adaptive 애플리케이션 프로세스 또는 프로세스 영역 내의 로깅 컨텍스트를 나타냅니다. 이러한 컨텍스트는 로깅을 위한 핵심 속성인 컨텍스트 ID, 관련된 컨텍스트 ID 설명, 구성 가능한 기본 로그 레벨(Default Log Level)을 캡슐화합니다. 이러한 컨텍스트를 통해 시스템 내에서 로그 출력이 차별화되고 제어됩니다.

시스템 아키텍처에서 ara::log::Logger은(는) 세 참여자 사이의 중재자 역할을 합니다:

  • 애플리케이션 프로세스(Application Process): ara::log::Logger 인스턴스를 사용하여 메시지를 출력하거나, 필터링 임계값을 동적으로 조회 또는 조정합니다.
  • 로깅 프레임워크: 모든 Logger 인스턴스에 대한 강력한 소유권(“strong ownership”)을 유지하고, ara::log::CreateLogger과(와) 같은 팩토리 함수를 통해 생성을 제어하며 하우스키핑을 수행합니다.
  • 로깅 백엔드: 실제 로그 데이터를 수신합니다. Logger 컨텍스트는 초기화 단계 동안 백엔드에 자동으로 등록되고, 정상적인 프로세스 종료 중에 등록 해제됩니다.

컨텍스트 다이어그램: 애플리케이션, 로깅 프레임워크 및 백엔드와의 상호작용에서 Logger 클래스의 배치. 출처: [SWS_LOG_00259]

수명 주기

로깅 백엔드와의 완벽한 동기화를 보장하기 위해 ara::log::Logger 인스턴스 관리는 프레임워크의 엄격한 제어를 받습니다:

  • 생성 및 소유권 관계: 기본 생성자는 명시적으로 삭제되었습니다(Logger() = delete, [SWS_LOG_00259]). 애플리케이션의 직접 인스턴스화는 금지됩니다. 생성은 ara::log::CreateLogger와(과) 같은 함수를 통해 통제된 방식으로 이루어집니다. 소유권은 로깅 프레임워크에 남아 있습니다.
  • 등록 및 정리: Logger 컨텍스트는 생성 시 로깅 백엔드에 자동으로 등록됩니다. 프로세스 종료 시 등록 해제가 자동으로 이루어지므로, 애플리케이션 개발자는 수동 수명 주기 관리 부담을 덜 수 있습니다.
  • 소멸: 소멸자 ~Logger()이(가) 지정되어 있습니다([SWS_LOG_00260]). 이는 스레드 안전(thread-safe)으로 선언되었지만, 예외에 안전하지 않음(“not exception safe”)으로 명시되어 있습니다([SWS_LOG_00260]).
  • 동시성: 로깅 및 임계값 조회를 위한 모든 메서드는 스레드 안전으로 지정되어 있습니다([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). 여러 스레드가 동일한 Logger 인스턴스를 병렬로 사용할 수 있습니다.

사용 경로

로그 메시지를 전송하는 일반적인 절차는 다음 단계로 나뉩니다:

  1. 필터 임계값 확인 또는 구성: 애플리케이션은 SetThreshold(threshold)을(를) 통해 런타임에 인스턴스의 필터 임계값을 설정할 수 있습니다([SWS_LOG_00255]). 연산 집약적인 로그 데이터 준비 전에, 원하는 로그 레벨이 구성된 보고 임계값을 충족하는지 IsEnabled(logLevel)을(를) 통해 조회할 수 있습니다([SWS_LOG_00070]). 검사 결과 false이(가) 반환되면 준비 작업을 건너뛸 수 있습니다.
  2. 스트림 기반 로깅 시작: 텍스트 로깅을 위해 클래스는 각 심각도 수준에 대한 특정 메서드를 제공합니다:
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • 긴급도를 프로그래밍 방식으로 결정하기 위한 WithLevel(logLevel)([SWS_LOG_00131]).
    이러한 각 메서드는 스트림 연산자 <<을(를) 통해 인수를 받는 LogStream 객체를 반환합니다([SWS_LOG_00064]).
  3. 스트림 수명 및 출력: 기본적으로 LogStream 객체의 수명은 단일 구문으로 제한되며 마지막 인수 뒤의 세미콜론에서 종료됩니다([SWS_LOG_00064]). 필요한 경우 스트림을 변수에 할당하여 여러 구문에 걸쳐 수명을 연장할 수 있습니다([SWS_LOG_00064]).
  4. 모델링된 메시지 출력: 스트리밍 대신 사전에 모델링된 메시지를 Log(id, args...)을(를) 통해 출력할 수 있습니다([SWS_LOG_00204]). 추가 속성을 전달해야 하는 경우 속성 튜플과 함께 LogWith(attrs, msgId, params...)을(를) 통해 호출이 이루어집니다([SWS_LOG_00133]).

시퀀스 다이어그램: 필터링된 스트림 로깅 작업의 호출 순서. 출처: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064]

오류 시나리오

ara::log::Logger의 오류 처리는 주로 컴파일 시점의 정적 타입 검사와 엄격한 예외 안전성을 기반으로 합니다:

  • 모델링된 메시지에서 일치하지 않는 인수: 템플릿 함수 Log(id, args...)이(가) 모델링된 메시지의 정의와 정확히 일치하지 않는 매개변수로 호출되면 프로그램은 잘못 형성(“ill-formed”)됩니다([SWS_LOG_00204]). 이는 컴파일 오류로 이어집니다.
  • LogWith의 유효하지 않은 속성: LogWith(attrs, msgId, params...)의 경우, 속성 튜플의 요소가 유효한 속성이 아니면 해당 함수는 SFINAE를 통해 오버로드 확인에서 제외됩니다([SWS_LOG_00133]).
  • 예외 보증: 모든 로깅 및 조회 함수(IsEnabled, SetThreshold, 모든 Log* 메서드, WithLevel, Log 및 LogWith 포함)는 예외에 안전(“exception safe”)한 것으로 지정되어 있으며 noexcept(으)로 선언되어 있습니다([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). 예외는 소멸자 ~Logger()(으)로, 예외에 안전하지 않음(“not exception safe”)으로 기재되어 있습니다([SWS_LOG_00260]). 해석: 이는 백엔드 하우스키핑 과정에서 내부 정리 또는 해제 오류가 발생할 때 오류 상태가 완전히 가로채지지 않음을 의미하는 것으로 추정되며, 따라서 등록 해제는 정상적인 프로세스 셧다운 과정에서 수행되어야 합니다.

<h4>컨텍스트</h4>
<p><code>ara::log::Logger</code> 클래스는 AUTOSAR Adaptive 애플리케이션 프로세스 또는 프로세스 영역 내의 로깅 컨텍스트를 나타냅니다. 이러한 컨텍스트는 로깅을 위한 핵심 속성인 컨텍스트 ID, 관련된 컨텍스트 ID 설명, 구성 가능한 기본 로그 레벨(Default Log Level)을 캡슐화합니다. 이러한 컨텍스트를 통해 시스템 내에서 로그 출력이 차별화되고 제어됩니다.</p>
<p>시스템 아키텍처에서 <code>ara::log::Logger</code>은(는) 세 참여자 사이의 중재자 역할을 합니다:</p>
<ul>
<li><strong>애플리케이션 프로세스(Application Process):</strong> <code>ara::log::Logger</code> 인스턴스를 사용하여 메시지를 출력하거나, 필터링 임계값을 동적으로 조회 또는 조정합니다.</li>
<li><strong>로깅 프레임워크:</strong> 모든 Logger 인스턴스에 대한 강력한 소유권(“strong ownership”)을 유지하고, <code>ara::log::CreateLogger</code>과(와) 같은 팩토리 함수를 통해 생성을 제어하며 하우스키핑을 수행합니다.</li>
<li><strong>로깅 백엔드:</strong> 실제 로그 데이터를 수신합니다. Logger 컨텍스트는 초기화 단계 동안 백엔드에 자동으로 등록되고, 정상적인 프로세스 종료 중에 등록 해제됩니다.</li>
</ul>

<p>로깅 백엔드와의 완벽한 동기화를 보장하기 위해 <code>ara::log::Logger</code> 인스턴스 관리는 프레임워크의 엄격한 제어를 받습니다:</p>
<ul>
<li><strong>생성 및 소유권 관계:</strong> 기본 생성자는 명시적으로 삭제되었습니다(<code>Logger() = delete</code>, <a class="spec-record-ref" data-req="SWS_LOG_00259" href="../spec/record.html?id=SWS_LOG_00259">[SWS_LOG_00259]</a>). 애플리케이션의 직접 인스턴스화는 금지됩니다. 생성은 <code>ara::log::CreateLogger</code>와(과) 같은 함수를 통해 통제된 방식으로 이루어집니다. 소유권은 로깅 프레임워크에 남아 있습니다.</li>
<li><strong>등록 및 정리:</strong> Logger 컨텍스트는 생성 시 로깅 백엔드에 자동으로 등록됩니다. 프로세스 종료 시 등록 해제가 자동으로 이루어지므로, 애플리케이션 개발자는 수동 수명 주기 관리 부담을 덜 수 있습니다.</li>
<li><strong>소멸:</strong> 소멸자 <code>~Logger()</code>이(가) 지정되어 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). 이는 스레드 안전(thread-safe)으로 선언되었지만, 예외에 안전하지 않음(“not exception safe”)으로 명시되어 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>).</li>
<li><strong>동시성:</strong> 로깅 및 임계값 조회를 위한 모든 메서드는 스레드 안전으로 지정되어 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). 여러 스레드가 동일한 Logger 인스턴스를 병렬로 사용할 수 있습니다.</li>
</ul>

<h4>사용 경로</h4>
<p>로그 메시지를 전송하는 일반적인 절차는 다음 단계로 나뉩니다:</p>
<ol>
<li><strong>필터 임계값 확인 또는 구성:</strong> 애플리케이션은 <code>SetThreshold(threshold)</code>을(를) 통해 런타임에 인스턴스의 필터 임계값을 설정할 수 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>). 연산 집약적인 로그 데이터 준비 전에, 원하는 로그 레벨이 구성된 보고 임계값을 충족하는지 <code>IsEnabled(logLevel)</code>을(를) 통해 조회할 수 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>). 검사 결과 <code>false</code>이(가) 반환되면 준비 작업을 건너뛸 수 있습니다.</li>
<li><strong>스트림 기반 로깅 시작:</strong> 텍스트 로깅을 위해 클래스는 각 심각도 수준에 대한 특정 메서드를 제공합니다:
<ul>
<li><code>LogFatal()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>)</li>
<li><code>LogError()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00065" href="../spec/record.html?id=SWS_LOG_00065">[SWS_LOG_00065]</a>)</li>
<li><code>LogWarn()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00066" href="../spec/record.html?id=SWS_LOG_00066">[SWS_LOG_00066]</a>)</li>
<li><code>LogInfo()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00067" href="../spec/record.html?id=SWS_LOG_00067">[SWS_LOG_00067]</a>)</li>
<li><code>LogDebug()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00068" href="../spec/record.html?id=SWS_LOG_00068">[SWS_LOG_00068]</a>)</li>
<li><code>LogVerbose()</code> (<a class="spec-record-ref" data-req="SWS_LOG_00069" href="../spec/record.html?id=SWS_LOG_00069">[SWS_LOG_00069]</a>)</li>
<li>긴급도를 프로그래밍 방식으로 결정하기 위한 <code>WithLevel(logLevel)</code>(<a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>).</li>
</ul>
이러한 각 메서드는 스트림 연산자 <code>&lt;&lt;</code>을(를) 통해 인수를 받는 <code>LogStream</code> 객체를 반환합니다(<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>스트림 수명 및 출력:</strong> 기본적으로 <code>LogStream</code> 객체의 수명은 단일 구문으로 제한되며 마지막 인수 뒤의 세미콜론에서 종료됩니다(<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>). 필요한 경우 스트림을 변수에 할당하여 여러 구문에 걸쳐 수명을 연장할 수 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>).</li>
<li><strong>모델링된 메시지 출력:</strong> 스트리밍 대신 사전에 모델링된 메시지를 <code>Log(id, args...)</code>을(를) 통해 출력할 수 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). 추가 속성을 전달해야 하는 경우 속성 튜플과 함께 <code>LogWith(attrs, msgId, params...)</code>을(를) 통해 호출이 이루어집니다(<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
</ol>

<h4>오류 시나리오</h4>
<p><code>ara::log::Logger</code>의 오류 처리는 주로 컴파일 시점의 정적 타입 검사와 엄격한 예외 안전성을 기반으로 합니다:</p>
<ul>
<li><strong>모델링된 메시지에서 일치하지 않는 인수:</strong> 템플릿 함수 <code>Log(id, args...)</code>이(가) 모델링된 메시지의 정의와 정확히 일치하지 않는 매개변수로 호출되면 프로그램은 잘못 형성(“ill-formed”)됩니다(<a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>). 이는 컴파일 오류로 이어집니다.</li>
<li><strong>LogWith의 유효하지 않은 속성:</strong> <code>LogWith(attrs, msgId, params...)</code>의 경우, 속성 튜플의 요소가 유효한 속성이 아니면 해당 함수는 SFINAE를 통해 오버로드 확인에서 제외됩니다(<a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>).</li>
<li><strong>예외 보증:</strong> 모든 로깅 및 조회 함수(<code>IsEnabled</code>, <code>SetThreshold</code>, 모든 <code>Log*</code> 메서드, <code>WithLevel</code>, <code>Log</code> 및 <code>LogWith</code> 포함)는 예외에 안전(“exception safe”)한 것으로 지정되어 있으며 <code>noexcept</code>(으)로 선언되어 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00070" href="../spec/record.html?id=SWS_LOG_00070">[SWS_LOG_00070]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00255" href="../spec/record.html?id=SWS_LOG_00255">[SWS_LOG_00255]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00064" href="../spec/record.html?id=SWS_LOG_00064">[SWS_LOG_00064]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00131" href="../spec/record.html?id=SWS_LOG_00131">[SWS_LOG_00131]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00204" href="../spec/record.html?id=SWS_LOG_00204">[SWS_LOG_00204]</a>, <a class="spec-record-ref" data-req="SWS_LOG_00133" href="../spec/record.html?id=SWS_LOG_00133">[SWS_LOG_00133]</a>). 예외는 소멸자 <code>~Logger()</code>(으)로, 예외에 안전하지 않음(“not exception safe”)으로 기재되어 있습니다(<a class="spec-record-ref" data-req="SWS_LOG_00260" href="../spec/record.html?id=SWS_LOG_00260">[SWS_LOG_00260]</a>). 해석: 이는 백엔드 하우스키핑 과정에서 내부 정리 또는 해제 오류가 발생할 때 오류 상태가 완전히 가로채지지 않음을 의미하는 것으로 추정되며, 따라서 등록 해제는 정상적인 프로세스 셧다운 과정에서 수행되어야 합니다.</li>
</ul>
