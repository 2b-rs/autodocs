ara::core::SynchronizedPoolResource 클래스는 내부 풀을 통해 할당을 처리하고 상위 업스트림 리소스에 추가 메모리를 요청하는 스레드 안전 메모리 리소스를 제공합니다([SWS_CORE_00030]). C++ 표준과 달리 메모리 할당 실패 시 예외를 던지지 않고 대신 nullptr를 반환합니다([SWS_CORE_00061]). 복사 연산은 완전히 금지되는 반면 이동 연산은 명시적으로 지원됩니다. 또한 소멸자는 가상이 아니므로 인스턴스를 기본 클래스 포인터를 통해 다형적으로 해제해서는 안 됩니다.

컨텍스트

ara::core::SynchronizedPoolResource 클래스는 core 모듈 내에서 AUTOSAR Adaptive Platform을 위한 스레드 안전 메모리 리소스를 제공합니다. 이 클래스는 C++ 표준 [mem.res.pool]에 따른 std::pmr::synchronized_pool_resource의 개념을 기반으로 하며, 기본 클래스 MemoryResource로부터 공개 상속받습니다. 주요 역할은 반복적인 할당을 효율적이고 동시적으로 처리하기 위해 내부 풀을 통해 크기 클래스별로 메모리 블록을 관리하는 것입니다. 내부 보유량이 충분하지 않은 경우 인스턴스는 상위 업스트림 메모리 리소스([SWS_CORE_00038])로부터 더 큰 메모리 블록을 가져옵니다.

일반적인 상호작용 대상으로는 할당을 요청하는 애플리케이션의 동시성 스레드, 중개 풀 관리자로서의 SynchronizedPoolResource, 업스트림 소스로서의 기본 MemoryResource이 포함됩니다. do_allocate, do_deallocate, options 및 release와 같은 모든 핵심 접근 및 관리 함수는 스레드 안전하도록 설계되었습니다([SWS_CORE_00061], [SWS_CORE_00041], [SWS_CORE_00039], [SWS_CORE_00037]).

컨텍스트 다이어그램: 동시성 애플리케이션 스레드, 풀 리소스 및 업스트림 메모리 소스의 상호작용. 출처: [SWS_CORE_00030], [SWS_CORE_00038].

수명 주기

SynchronizedPoolResource의 인스턴스화는 여러 생성자 오버로드를 통해 수행될 수 있습니다. 할당 옵션(PoolOptions)과 업스트림 리소스를 모두 사용할 수 있는 경우 초기화는 완전한 예외 안전성을 보장하며 noexcept로 선언됩니다([SWS_CORE_00030]). 그 외에도 매개변수가 없는 생성자([SWS_CORE_00031]), 업스트림 포인터만 있는 생성자([SWS_CORE_00032]) 또는 순수 풀 옵션만 있는 생성자([SWS_CORE_00033])가 존재합니다. 해석: 업스트림 포인터가 전달되지 않는 경우 구현은 플랫폼별 표준 메모리 리소스를 대체하여 사용할 것으로 추정됩니다.

소유권 관계와 관련하여 이 클래스는 복사를 엄격히 배제합니다. 복사 생성자([SWS_CORE_00034])와 복사 대입 연산자([SWS_CORE_00036])가 모두 삭제되어 있습니다(=delete). 그러나 ISO C++17 표준과 달리 AUTOSAR는 이 클래스에 대해 이동 시맨틱을 명시적으로 정의합니다. 이동 생성자([SWS_CORE_00043])와 이동 대입 연산자([SWS_CORE_00044])가 각각 noexcept=default로 제공됩니다.

소멸의 핵심적인 측면은 표준 동작과의 차이점입니다. 소멸자 ~SynchronizedPoolResource()은 명시적으로 비가상입니다([SWS_CORE_00035]). 해석: 소멸자가 가상이 아니므로 기본 클래스 MemoryResource*의 포인터를 통한 다형적 소멸은 정의되지 않은 동작으로 이어질 것으로 추정되며, 따라서 인스턴스는 항상 구체적인 타입을 통해 해제되어야 합니다. 또한 release()을 호출하면 리소스 객체는 그대로 유지하면서 할당된 모든 메모리를 업스트림 리소스에 반환할 수 있습니다([SWS_CORE_00037]).

사용 경로

일반적인 흐름에는 초기화, 메모리 블록의 반복적인 할당 및 해제, 최종 정리가 포함됩니다:

  1. 초기화: 애플리케이션은 구성 매개변수와 상위 메모리 리소스를 지정하여 인스턴스를 생성합니다([SWS_CORE_00030]). 활성 설정은 options()을 통해 확인할 수 있고([SWS_CORE_00039]), 업스트림 포인터는 upstream_resource()을 통해 확인할 수 있습니다([SWS_CORE_00038]).
  2. 메모리 할당: 메모리 요청은 do_allocate을(를) 통해 보호되어 처리됩니다 ([SWS_CORE_00061]). 해석: 애플리케이션 코드에서의 호출은 일반적으로 보호된 메서드 do_allocate을(를) 직접 통하지 않고, 기본 클래스 MemoryResource의 상속된 공개 인터페이스 allocate을(를) 통해 수행됩니다.
  3. 동일성 검사: do_is_equal을(를) 통해 두 메모리 리소스가 서로 동등한지 확인할 수 있습니다 ([SWS_CORE_00042]).
  4. 해제: 개별 메모리 영역은 do_deallocate을(를) 통해 풀로 반환됩니다 ([SWS_CORE_00041]). 필요한 경우 release()을(를) 통해 모든 풀의 전체 메모리를 묶어서 업스트림 리소스에 반환할 수 있습니다 ([SWS_CORE_00037]).

시퀀스 다이어그램: 업스트림 리소스를 통한 초기화, 메모리 요청, 해제 및 정리의 일반적인 순서. 출처: [SWS_CORE_00030], [SWS_CORE_00061], [SWS_CORE_00041], [SWS_CORE_00037].

오류 시나리오

AUTOSAR Adaptive Platform은 오류 처리 시 C++ 표준의 예외 규칙에서 의도적으로 벗어납니다:

  • 할당 오류: ISO-C++에서는 메모리 고갈 시 std::bad_alloc을(를) 던지도록 규정하고 있는 반면, AUTOSAR에서 do_allocate은(는) noexcept(으)로 정의됩니다. 적합한 메모리 블록을 제공할 수 없는 경우, 이 메서드는 대신 반드시 널 포인터(nullptr)를 반환합니다 ([SWS_CORE_00061]). 따라서 호출자는 모든 할당 반환값을 nullptr에 대해 확인해야 합니다.
  • 할당 해제 오류: 메서드 do_deallocate 역시 noexcept입니다. 메모리 블록 반환 시 오류가 발생하더라도 사양에 따라 이는 조용히 무시됩니다 ([SWS_CORE_00041]).
  • 생성 위험: 옵션과 업스트림 리소스를 사용하는 생성자는 예외에 안전하지만([SWS_CORE_00030]), 업스트림 지정이 없거나 옵션이 없는 생성자는 예외에 안전하지 않음(“not exception safe”)으로 분류됩니다 ([SWS_CORE_00031], [SWS_CORE_00032], [SWS_CORE_00033]). 해석: 이러한 생성자에서 풀 관리 구조체의 내부 프로비저닝이 실패하면 객체 생성이 실패할 수 있습니다.

이 클래스 가이드는 AUTOSAR Adaptive Release R25-11용 ara::core::SynchronizedPoolResource의 사양을 요약합니다.
