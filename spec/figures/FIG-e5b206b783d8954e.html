1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm zur Spezifikation des ECU-Konfigurationsmodells (ECUC-Parameterdefinition) im AUTOSAR-Classic-Standard für das BSW-Modul Diagnostic Communication Manager (Dcm). Es beschreibt die metamodellbasierte Parametrierung von Fahrzeuginformationen (VehInfo, typischerweise OBD-Service $09 / Vehicle Information) innerhalb des Submoduls Diagnostic Service Processing (DcmDsp).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm spezifiziert folgende Konfigurationscontainer und Parameter:

  • DcmDsp (EcucParamConfContainerDef): Wurzelcontainer mit Multiplizität [0..1].
  • DcmDspVehInfo (EcucParamConfContainerDef): Subcontainer unter DcmDsp (Rolle +subContainer, Multiplizität [0..\*]).
    • DcmDspVehInfoInfoType (EcucIntegerParamDef): Parameter (+parameter, Multiplizität [1..1], Wertebereich min = 0, max = 255) zur Festlegung der InfoType-Kennung.
    • DcmDspVehInfoNODIProvResp (EcucBooleanParamDef): Parameter (+parameter, Multiplizität [0..1], defaultValue = false) zur Steuerung des NODI-Verhaltens (Number of Data Items).
  • DcmDspVehInfoData (EcucParamConfContainerDef): Subcontainer unter DcmDspVehInfo (Rolle +subContainer, Multiplizität [1..\*]) zur Definition der einzelnen Datenelemente:
    • DcmDspVehInfoDataReadFnc (EcucFunctionNameDef): Parameter (+parameter, Multiplizität [0..1]) zur Angabe des Funktionsnamens für das Auslesen der Daten.
    • DcmDspVehInfoDataSize (EcucIntegerParamDef): Parameter (+parameter, Multiplizität [1..1], Wertebereich min = 0, max = 255) für die Datengröße in Byte.
    • DcmDspVehInfoDataOrder (EcucIntegerParamDef): Parameter (+parameter, Multiplizität [1..1], Wertebereich min = 0, max = 255) zur Festlegung der Reihenfolge der Datenelemente.
    • DcmDspVehInfoDataUsePort (EcucBooleanParamDef): Parameter (+parameter, Multiplizität [1..1]) zur Selektion, ob die Daten über einen AUTOSAR-Port oder eine direkte C-Funktion bezogen werden.

3. Dynamisches Verhalten & Sequenzablauf

Statische Konfigurationsstruktur ohne Laufzeitsequenzen oder Zustandsübergänge. Die Beziehungen definieren die hierarchische Schachtelung für den ECU-Konfigurations- und Codegenerierungsprozess: Ein DcmDsp-Container kann mehrere Fahrzeug-InfoTypes instanziieren, die jeweils aus mindestens einem geordneten Datenelement (DcmDspVehInfoData) zusammengesetzt sind.

4. Normative Relevanz & Entwickler-Hinweise

Normative Vorgabe für BSW-Generatoren und Konfigurationswerkzeuge zur Abbildung von Service 09 (Request Vehicle Information):

  • Jeder DcmDspVehInfo-Eintrag erfordert genau einen InfoType-Identifier im Bereich [0..255] (1 Byte).
  • Für jedes Datenelement DcmDspVehInfoData ist die Bytegröße über DcmDspVehInfoDataSize auf maximal 255 Byte limitiert.
  • Wenn DcmDspVehInfoDataUsePort auf true konfiguriert ist, wird das Daten-Interface typischerweise über AUTOSAR-Ports angebunden, andernfalls über den in DcmDspVehInfoDataReadFnc definierten Funktionsnamen.
  • Bei Konfiguration von DcmDspVehInfoNODIProvResp auf true stellt der DCM die Bereitstellung des NODI-Bytes gemäß Diagnoseprotokoll sicher.
