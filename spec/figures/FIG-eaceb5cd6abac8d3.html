1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm zur Darstellung des AUTOSAR ECU-Configuration-Metamodells (ECUC Parameter Definition).
  • Technischer Zweck: Definition der Konfigurationsstruktur für die Filterung und den Berichtsmodus von Security-Events im Intrusion Detection System Manager (IdsM, BSW-Sicherheitsarchitektur nach ISO/SAE 21434). Es modelliert die Zuweisung eines Reporting-Modus (IdsMReportingModeFilter, ECUC_IdsM_00018) pro konfiguriertem Security Event (IdsMEvent) innerhalb der Basiskonfiguration (IdsMConfiguration).

2. Komponenten, Entitäten & Schnittstellen

  • Container & Parameter-Entitäten:
  • IdsMConfiguration (EcucParamConfContainerDef): Wurzel-Konfigurationscontainer des IdsM-Moduls [Kardinalität: 1..1].
  • IdsMEvent (EcucParamConfContainerDef): Repräsentiert die Definition eines einzelnen Security Events, das von Sensor-SWCs oder BSW-Modulen via IdsM_SetEventStatus() bzw. IdsM_SetEventData() gemeldet werden kann [Kardinalität: 1..65535, Subcontainer via +subContainer].
  • IdsMReportingModeFilter (EcucEnumerationParamDef): Aufzählungsparameter zur Festlegung des Reporting- und Filterverhaltens für das jeweilige Event [Kardinalität: 1..1, Assoziation via +parameter].
  • Enumeration Literals (EcucEnumerationLiteralDef, via +literal):
  • OFF: Unterdrückt die Berichterstattung vollständig; das Event wird verworfen.
  • BRIEF: Kompakte Meldung (Header/Event-ID ohne erweiterte Kontextdaten), unterliegt den nachgelagerten IdsM-Filterketten (z. B. Threshold-, Rate-Limiting- oder Aggregationsfilter).
  • DETAILED: Vollständige Meldung (inklusive kontextueller Payload/Debug-Informationen), unterliegt den nachgelagerten IdsM-Filtern.
  • BRIEF_BYPASSING_FILTERS: Kompakte Meldung unter Umgehung/Bypass aller nachgelagerten Filterketten (sofortige Qualifizierung).
  • DETAILED_BYPASSING_FILTERS: Vollständige Meldung unter Umgehung/Bypass aller nachgelagerten Filterketten (für hochkritische Security-Vorfälle).
  • Beziehungen & Kardinalitäten:
  • Strenge Komposition (*--): IdsMConfiguration aggregiert 1 bis maximal 65.535 IdsMEvent-Instanzen (entspricht der Adressierbarkeit über uint16 / IdsM_EventIdType).
  • Jedes IdsMEvent besitzt exakt einen (1..1) IdsMReportingModeFilter.
  • Der Enum-Parameter aggregiert disjunkt genau eines der 5 definierten Literale.

3. Dynamisches Verhalten & Sequenzablauf

Statische Konfigurationsdefinition; die Laufzeit-Auswertung erfolgt ereignisgesteuert im BSW-Stack:

  1. Trigger: Eine Software-Komponente (SWC) oder ein BSW-Treiber (z. B. CanSM, EthSM, SecOC) meldet ein Ereignis synchron über IdsM_SetEventStatus(EventId, ...) oder IdsM_SetEventData(EventId, ...).
  2. Evaluierung des Reporting-Modus:
  • Falls OFF: Früher Ausstieg / Abbruch. Keine Pufferung, kein Zählerinkrement, kein Overhead.
  • Falls *_BYPASSING_FILTERS: Event überspringt Algorithmen zur Ratenbegrenzung/Filterung und wird direkt als qualifiziertes Security-Event (QSEv) an den Event-Buffer bzw. das Protokollierungs-Backend (IdsR / Crypto-Signierung / PDU-Router) übergeben.
  • Falls BRIEF oder DETAILED: Event wird an die konfigurierten Filter-Stufen (Sampling, Aggregation, State-abhängige Filter) weitergereicht.
  1. Formatierung: Bei positivem Filter-Durchlauf erzeugt der IdsM basierend auf der Auswahl (BRIEF vs. DETAILED) entweder eine komprimierte oder eine vollständige Event-PDU für die Übertragung.

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher- und Bandbreiten-Optimierung:
  • BRIEF spart CAN/LIN/Ethernet-Bandbreite und Pufferressourcen im IdsM-Ringbuffer (IdsMEventBuffer).
  • DETAILED bindet zusätzlichen RAM für Context-Payloads und sollte hochkritischen Vektoren vorbehalten sein.
  • DDoS-/Flooding-Schutz:
  • Die Modi *_BYPASSING_FILTERS hebeln Schutzmechanismen wie Rate-Limiting aus. Bei hochfrequenten Trigger-Quellen (z. B. fehlerhafte Frame-Zähler im Bus-Interface) drohen Pufferüberläufe und Denial-of-Service auf dem internen Security-Logging-Kanal.
  • Konfigurationskonsistenz (ARXML/BSW-Generierung):
  • Jedes im System vorkommende IdsMEvent benötigt zwingend diesen Parameter (lowerMultiplicity = 1). Ein fehlender Parameter führt zu Validierungsfehlern des BSW-Code-Generators.
  • Generierte Datenstrukturen (z. B. Lookup-Tables über Event-IDs im Flash) nutzen den Enum typischerweise als bitkodiertes Flag-Feld zur verzweigungsfreien Auswertung im Task-Kontext.
