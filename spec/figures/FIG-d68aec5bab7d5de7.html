1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Ausschnitt / UML-Klassendiagramm zur AUTOSAR BSW-Parameterdefinition (ECUC-Definition gemäß AUTOSAR BSW Parameter Definition Model).
  • Architektur-Kontext:
    • Modul: PduR (PDU Router, AUTOSAR Classic Platform, Communication Services / BSW).
    • Funktionaler Zweck: Festlegung der ECU-Konfigurationsparameter für Transportprotokoll-Puffer (PduRTpBufferTable). Diese Puffer dienen im PduR der Zwischenspeicherung und Ratenentkopplung beim gateway-seitigen Routing von TP-PDUs (z. B. CanTp ↔ FrTp / LinTp / DoIP) bei asynchroner Segmentierung und unterschiedlichen Blockgrößen (ST_min, Block Size).

2. Komponenten, Entitäten & Schnittstellen

  • PduRGlobalConfig : ParamConfContainerDef
    • Attribut: multipleConfigurationContainer = True (erlaubt Post-Build-Selectable bzw. Multiple-Configuration-Sets für unterschiedliche ECU-Varianten).
    • Rolle: Wurzelcontainer der versionsspezifischen Gesamtkonfiguration des PDU-Routers.
  • PduRTpBufferTable : ParamConfContainerDef
    • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = 1 (optionaler Sub-Container via Komposition +subContainer unter PduRGlobalConfig).
    • Rolle: Zentraler Tabellen-Container für die statisch allozierten TP-Pufferstrukturen im RAM.
    • Enthaltene Parameter & Sub-Container:
      • PduRMaxTpBufferNumber : IntegerParamDef (über Komposition +parameter):
        • Wertebereich: min = 0, max = 65535 (Datentyp uint16).
        • Semantik: Definiert die maximale Obergrenze der gleichzeitig verwaltbaren oder vorgehaltenen TP-Puffer im PduR.
      • PduRTpBuffer : ParamConfContainerDef (über Komposition +subContainer):
        • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = * (beliebig viele Puffer-Instanzen definierbar).
        • Length : IntegerParamDef (über Komposition +parameter):
          • Wertebereich: min = 1, max = 65535 (Datentyp uint16).
          • Semantik: Statische Bytegröße des jeweiligen Puffers im RAM zur Aufnahme der vollständigen oder segmentierten TP-Payload.

3. Dynamisches Verhalten & Sequenzablauf

(Statisches Konfigurationsmodell – dynamische Ausprägung zur Laufzeit im PduR-Stack:)

  1. Puffer-Allokation bei Übertragungsstart:
    • Empfang von PduR_<Tp>StartOfReception() aus dem Quell-TP (z. B. CanTp).
    • PduR prüft verfügbare Pufferinstanzen in der PduRTpBufferTable. Ist die geforderte TpSduLength ≤ Length eines freien Puffers, wird der Puffer reserviert (BUFREQ_OK); andernfalls Rückgabe von BUFREQ_E_OVFL bzw. BUFREQ_E_NOT_OK.
  2. Datenübertragung (Copy-Vorgang):
    • Sukzessive Bereitstellung von Pufferausschnitten via PduR_<Tp>CopyRxData() auf Empfangsseite und Weiterleitung via PduR_<Tp>Transmit() an das Ziel-TP.
    • Bereitstellung der Daten an das Ziel-TP über PduR_<Tp>CopyTxData().
  3. Puffer-Freigabe:
    • Nach Bestätigung über PduR_<Tp>RxIndication() (Quell-TP) und erfolgreicher PduR_<Tp>TxConfirmation() (Ziel-TP) bzw. bei Abbruchfehlern erfolgt die atomare Freigabe des Puffers in den PduR-Pufferpool.

4. Normative Relevanz & Entwickler-Hinweise

  • Generierung & Speicherabbild:
    • Der BSW-Codegenerator erzeugt aus PduRTpBuffer typischerweise ein Array von uint8-Arrays samt Zustandsdeskriptoren (PduR_TpBufferType / PduR_PBConfigType) im RAM (.bss / .data).
    • PduRMaxTpBufferNumber limitiert den Overhead der Puffer-Verwaltungsstrukturen (Deskriptoren, Mutex/Locks, Zähler).
  • Dimensionierung & Worst-Case-Szenarien:
    • Pufferlängen (Length) müssen auf die maximale SDU-Länge der konfigurierten TP-Routen abgestimmt sein (z. B. bis zu 4095 Bytes bei Standard-ISO-15765-2 CanTp). Unterdimensionierung führt zu direktem BUFREQ_E_OVFL und Abbruch von UDS-Diagnose- oder Flashing-Sessions.
  • Mehrfachkonfiguration (Post-Build):
    • Da multipleConfigurationContainer = True an PduRGlobalConfig gesetzt ist, können verschiedene Pufferlayouts je nach Fahrzeugvariante / PB-Konfigurationsset referenziert werden; die Link-Time/Post-Build-Zeiger müssen die jeweilige PduRTpBufferTable validieren.
