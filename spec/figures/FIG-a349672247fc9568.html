1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / Metamodell-Ausschnitt (M2-Ebene gemäß AUTOSAR-Metamodell).
  • Technischer Zweck: Spezifikation der System-Template-Datenstrukturen zur Modellierung des UDP-basierten Netzwerkmanagements (UdpNm) auf Ethernet-Netzwerken.
  • Architektur-Einordnung: Verortet im System Template (AUTOSAR_TPS_SystemTemplate, Cluster/NM-Kapitel). Es definiert die standardisierte ARXML-Repräsentation, aus der während der EcuExtract-/BSW-Generierung die BSW-Konfiguration für den UdpNm-Stack, den generischen Nm-Manager sowie die Bindung an SoAd, TcpIp und EthIf abgeleitet wird.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten und Stereotypen

  • CommunicationCluster (abstrakt, FibexElement, Stereotyp: «atpVariation»):
  • Basisklasse aller Kommunikationsnetzwerke (CAN, LIN, FlexRay, Ethernet).
  • Attribute: baudrate (PositiveUnlimitedInteger [0..1]), protocolName (String [0..1]), protocolVersion (String [0..1]).
  • NmCluster (abstrakt, Identifiable):
  • Generische Basisklasse für busspezifische NM-Cluster.
  • Attribute:
  • nmChannelSleepMaster (Boolean [0..1]): Legt fest, ob der Kanal als Sleep-Master agiert.
  • nmNodeDetectionEnabled (Boolean [0..1]): Aktiviert Node-Detection-Mechanismus.
  • nmNodeIdEnabled (Boolean [0..1]): Aktiviert Übertragung der Knoten-ID.
  • nmPncParticipation (Boolean [0..1]): Schaltet Partial-Networking-Unterstützung (PNC) frei.
  • nmRepeatMsgIndEnabled (Boolean [0..1]): Aktiviert Repeat-Message-Indication.
  • nmSynchronizingNetwork (Boolean [0..1]): Definiert, ob das Netzwerk als Synchronisationsnetzwerk dient.
  • pncClusterVectorLength (PositiveInteger [0..1]): Länge des PNC-Vektors für das Cluster in Bytes.
  • UdpNmCluster (konkret, abgeleitet von NmCluster):
  • Ethernet/UDP-spezifische NM-Cluster-Konfiguration.
  • Attribute:
  • nmCbvPosition (Integer [0..1]): Byte-Offset des Control Bit Vector (CBV) in der NM-PDU (typischerweise Byte 0 oder Byte 1).
  • nmImmediateNmCycleTime (TimeValue [0..1]): Zykluszeit für schnelle Burst-Übertragungen beim Aufstarten.
  • nmImmediateNmTransmissions (PositiveInteger [0..1]): Anzahl der Burst-NM-Botschaften.
  • nmMessageTimeoutTime (TimeValue [0..1]): Timeout-Überwachung für Tx-Bestätigungen.
  • nmMsgCycleTime (TimeValue [0..1]): Periodische Zykluszeit im Normal Operation State.
  • nmNetworkTimeout (TimeValue [0..1]): Timeout bis zum Übergang in den Ready Sleep State bei ausbleibenden NM-Botschaften.
  • nmNidPosition (Integer [0..1]): Byte-Offset des Node Identifier (NID) in der NM-PDU.
  • nmRemoteSleepIndicationTime (TimeValue [0..1]): Zeitfenster zur Erkennung, dass alle anderen Netzwerkknoten schlaffähig sind.
  • nmRepeatMessageTime (TimeValue [0..1]): Verweildauer im Repeat Message State.
  • nmWaitBusSleepTime (TimeValue [0..1]): Verweildauer im Prepare Bus-Sleep Mode.
  • PhysicalChannel (abstrakt, Identifiable):
  • Physischer Kommunikationskanal.
  • Assoziationen: +managedPhysicalChannel (0..*) verweist reflexiv auf verwaltete physische Kanäle.
  • EthernetPhysicalChannel (konkret, abgeleitet von PhysicalChannel):
  • Repräsentiert ein konkretes Ethernet-Subnetz / VLAN.

#### Beziehungen & Kardinalitäten

  • *CommunicationCluster $\blacklozenge\xrightarrow{\text{+physicalChannel [1..]}}$ PhysicalChannel:**
  • Komposition mit Stereotyp «atpVariation, atpSplitable» (variabel bezüglich Variantenmanagement und aufteilbar über mehrere ARXML-Dateien).

  • Generalisierungsbeziehung (UdpNmCluster erbt von NmCluster).
  • PhysicalChannel $\triangle\text{---}$ EthernetPhysicalChannel:
  • Generalisierungsbeziehung (EthernetPhysicalChannel erbt von PhysicalChannel).

3. Dynamisches Verhalten & Sequenzablauf

Obgleich ein statisches Strukturmodell vorliegt, determinieren die Attribute von UdpNmCluster direkt den UdpNm-Zustandsautomaten (SWS UdpNm):

  • Aufstarten / Wakeup:
  • Bei Netzwerkanforderung startet der Repeat Message State. Ist nmImmediateNmTransmissions > 0, wird der Übertragungsburst mit nmImmediateNmCycleTime getriggert, bevor auf nmMsgCycleTime gewechselt wird.
  • Verweildauer im Zustand wird durch nmRepeatMessageTime vorgegeben.
  • *Zyklischer Betrieb (Normal Operation):*
  • Senden von NM-PDUs mit Periode nmMsgCycleTime.
  • Empfangsüberwachung: Jeder Empfang einer gültigen NM-PDU setzt den Timer für nmNetworkTimeout zurück.
  • *Einschlafsequenz (Ready Sleep $\to$ Prepare Bus-Sleep $\to$ Bus-Sleep):*
  • Werden keine Kommunikationsbedarfe mehr gemeldet, wechselt die Node in den Ready Sleep State.
  • Läuft nmNetworkTimeout ohne Empfang externer NM-Botschaften ab, erfolgt der Übergang in Prepare Bus-Sleep.
  • Nach Ablauf von nmWaitBusSleepTime ohne erneuten Wakeup schaltet der Kanal in den Bus-Sleep Mode (Freigabe des Transceivers/Controllers für Sleep).
  • Timeout & Fehlerüberwachung:
  • Bleibt die Bestätigung (SoAdIf_TxConfirmation) für eine gesendete UDP-NM-PDU länger als nmMessageTimeoutTime aus, meldet der Stack einen Transmit-Timeout (UDPNM_E_NET_START_IND / Fehler-Callback an den generischen Nm).

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsableitung:
  • Die Parameter des UdpNmCluster und NmCluster werden direkt in die Konfigurationsmodule UdpNm und Nm transformiert (z. B. UdpNmCbvPosition, UdpNmMsgCycleOffset, UdpNmNetworkTimeout).
  • Integrationsregeln:
  • Die Zuordnung über +vlan koppelt den logischen NM-Cluster an den korrekten virtuellen Ethernet-Kanal (EthernetPhysicalChannel).
