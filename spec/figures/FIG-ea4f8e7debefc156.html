1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Schichtenmodell / Funktionscluster-Architekturdiagramm (High-Level Block Diagram).
  • Kontext: AUTOSAR Adaptive Platform (AP Release 17-10 / v1.2.0, EXP_PlatformDesign), Spezifikation des Funktionsclusters Time Synchronization (ara::tsync).
  • Technischer Zweck: Das Diagramm abstrahiert die Zeitsynchronisation heterogener automobiler Bussysteme gegenüber der Applikationsebene. Es visualisiert:
  1. Die Kapselung bus- und protokollspezifischer Zeitübertragungsmechanismen hinter einer standardisierten C++-API (Time Synchronization API).
  2. Die Koexistenz mehrerer unabhängiger, synchronisierter Zeitbasen (Time Domains / Clock Domains) innerhalb einer Adaptive-Instanz.
  3. Den vertikalen Signal-/Datenfluss von physischen Netzwerkprotokollen zur Konsumation in Adaptive Applications (z. B. für koordinierte Sensorfusion, deterministisches Scheduling und verteilte Event-Korrelation).

2. Komponenten, Entitäten & Schnittstellen

  • Application (Adaptive Application, AA):
  • Consumer-Entität im POSIX-User-Space.
  • Greift über typsichere C++-Interfaces des Namespaces ara::tsync auf definierte Zeitbasen zu.
  • Time Synchronization API (ara::tsync):
  • Abstraktions- und Middleware-Schicht des Functional Clusters.
  • Kapselt OS-spezifische Timersubsysteme (z. B. POSIX Clocks, /dev/ptp*), Hardware-Timestamping-Einheiten (MII/GMII) und Synchronisationsalgorithmen.
  • Stellt Clocks bereit, die typischerweise semantisch an die C++ Standardbibliothek (std::chrono::Clock-Konzept) angelehnt sind.
  • Zeitbasen / Time Domains (symbolisiert durch 3 Uhren-Piktogramme):
  • Repräsentieren logisch getrennte Zeitdomänen (Synchronized Time Bases / Pure Time Bases).
  • Koexistenz ermöglicht z. B. die parallele Haltung von:
  • Globaler UTC/TAI-Fahrzeugzeit (z. B. via Ethernet-Grandmaster).
  • Lokaler Clusterzeit (z. B. FlexRay-Kommunikationszykluszeit).
  • Monotoner relativer Zeitbasis für Safety-relevante Timeout-Überwachungen.
  • Jede Zeitbasis verwaltet intern Statusattribute (u. a. SynchronizationStatus: Synchronized, Unsynchronized, Timeout sowie Drift- und Offset-Parameter).
  • Netzwerk-Eingangsvektoren (Zeitsynchronisations-Quellen):
  • ETH (PTP): Ethernet-basierte Synchronisation via Precision Time Protocol (IEEE 802.1AS / gPTP bzw. IEEE 1588). Nutzt Hardware-Timestamping auf MAC/PHY-Ebene für Sub-Mikrosekunden-Genauigkeit.
  • CAN: Zeitsynchronisation über CAN/CAN-FD unter Verwendung des CAN-TSyn-Protokolls (Synchronized Time-Base Manager / StbM-Äquivalent via SYNC- und FUP-PDUs).
  • FR: Synchronisation über FlexRay (FlexRay-interne Synchronisationsmechanismen über Sync-Frames, Microticks/Macroticks bzw. FrTSyn).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm impliziert zwei gekoppelte dynamische Pfade (Ingress-Aktualisierung und Egress-Abfrage):

  1. Ingress-Synchronisationspfad (Bus $\rightarrow$ Time Synchronization Cluster):
  • Trigger: Periodischer Empfang von Synchronisationsnachrichten (z. B. gPTP Sync + Follow_Up, CAN SYNC + FUP).
  • Berechnung: Der Protokoll-Stack bzw. Daemon ermittelt Message Latency, Propagation Delay, Path Delay und Frequenzabweichung (Rate Ratio / Drift).
  • Clock Discipline: Die zugeordnete interne Zeitbasis wird kontinuierlich diszipliniert (Slewing via Phasenregelschleife / PLL oder diskreter Offset-Sprung bei Systeminitialisierung).
  • Degradierung/Timeout: Bleiben Synchronisationsbotschaften aus, wechselt die Zeitbasis in den Zustand Timeout / Flywheel-Modus (Weiterlauf über lokalen Quarzoszillator unter Annahme der zuletzt geschätzten Drift).
  1. Egress-Abfragepfad (Time Synchronization API $\rightarrow$ Application):
  • Synchrone Abfrage (Non-blocking): Applikation ruft Methoden wie GetCurrentTime() der jeweiligen TimeBase ab. Die Operation liefert Nanosekunden-Zeitstempel inklusive des aktuellen Synchronisationsstatus.
  • Asynchrone Events / Timer: Registrierung von Alarmschwellen oder Wait-Operationen, die bezogen auf eine spezifische synchronisierte Zeitbasis feuern.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Nutzung & Gültigkeitsprüfung:
  • Zeitstempel dürfen in Applikationen nicht unkritisch konsumiert werden. Die Applikationssoftware muss stets den zurückgegebenen Synchronisationszustand (ara::tsync::SynchronizationStatus) evaluieren, um Fehlentscheidungen bei Signalverlust oder degradierter Ganggenauigkeit (Flywheel) abzufangen.
  • Manifest-Modellierung (ARXML / Execution Manifest):
  • Die Zuordnung von Adaptive Applications zu spezifischen Zeitbasen erfolgt deklarativ im Service Instance Manifest bzw. Execution Manifest.
  • Die Rolle der Plattforminstanz (Time Master, Time Slave oder Time Gateway / Bridge zwischen ETH, CAN und FR) wird über die Maschinen- und Kommunikationskonfiguration parametriert.
  • Architekturrolle als Time Gateway:
  • Die Adaptive Platform fungiert in modernen E/E-Architekturen häufig als Gateway: Sie bezieht die Referenzzeit über ETH (PTP) (High-Performance-Backbone) und treibt als Master abgeleitete Zeitdomänen auf Sub-Bussen (CAN, FR) an. Hierbei müssen Jitter, Scheduling-Latenzen des POSIX-OS und Gateway-Offsets exakt berücksichtigt werden.
  • POSIX-/Kernel-Ebene:
  • Für Entwickler hardwarenaher Plattform-Stacks bedeutet dies: Anbindung an PTP-Hardware-Clocks (PHC, /dev/ptpX) via SO_TIMESTAMPING bzw. clock_gettime-Systemcalls. Reines CLOCK_REALTIME reicht nicht aus, um Sprünge durch NTP/Schaltsekunden ohne Beeinflussung monotoner Zeitbasen sicher abzufangen.
