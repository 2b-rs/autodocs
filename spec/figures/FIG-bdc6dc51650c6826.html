1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Objektdiagramm (M1-Instanzebene des AUTOSAR-Metamodells).
  • Technischer Zweck: Spezifikation der M1-Modellierungssemantik für heterogene C-Union-Typen mit eingebetteten Strukturen im RTE-Kontext (AUTOSAR_SWS_RTE, Release 4.0.3).
  • Architektur-Einordnung: Schnittstelle zwischen AUTOSAR-Software-Komponenten (SWC) und RTE-Codegenerierung. Definiert das formale Mapping von ARXML-Typdefinitionen (ImplementationDataType) auf den generierten C-Code in Rte_Type.h.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Stereotypen
  • UnionFoo (ImplementationDataType):
    • Attribut: category = UNION
    • Repräsentiert die äußerste Typdefinition (C-union).
  • TheWord (ImplementationDataTypeElement):
    • Attribut: category = VALUE
    • Erstes Member der Union (16-Bit-Ganzzahl).
  • TheBytes (ImplementationDataTypeElement):
    • Attribut: category = STRUCTURE
    • Zweites Member der Union; kapselt eine anonyme/eingebettete Struktur.
  • FirstByte, SecondByte (ImplementationDataTypeElement):
    • Attribute: jeweils category = VALUE
    • Strukturelemente innerhalb von TheBytes.
  • «atpVariation» :SwDataDefProps:
    • Stereotyp: «atpVariation» (AUTOSAR Template Profile – Kennzeichnung variabilitätsfähiger Eigenschaften für Pre-Compile- oder Post-Build-Bindung).
    • Spezifiziert typbezogene Attribute und verknüpft die ImplementationDataTypeElement-Instanzen mit Basistypen.
  • MyUint16Base, MyUint8Base (SwBaseType):
    • Attribute: jeweils category = FIXED_LENGTH sowie nativeDeclaration = unsigned short (16 Bit) bzw. nativeDeclaration = unsigned char (8 Bit).
    • Spezifizieren Basistypen mit fester Bitbreite und verankern die hardware- und compilerspezifische Implementierungsbreite.
Beziehungen & Kardinalitäten
  • Komposition +subElement:
    • UnionFoo aggregiert TheWord und TheBytes (Komposition 1 → n).
    • TheBytes aggregiert FirstByte und SecondByte (Komposition 1 → n).
  • Komposition +swDataDefProps:
    • Jedes Blatt-Element (TheWord, FirstByte, SecondByte) besitzt eine eigene Kompositionsinstanz von SwDataDefProps.
  • Assoziation +baseType:
    • SwDataDefProps von TheWord referenziert gerichtet MyUint16Base.
    • SwDataDefProps von FirstByte und SecondByte referenzieren jeweils gerichtet MyUint8Base.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Typdefinitionsmodell existiert kein Laufzeit-Zustandsübergang. Der Codegenerierungs- und Speicherzugriffsablauf gliedert sich wie folgt:

  1. Generierungszeit (RTE Contract / Generation Phase):
    • Traversierung von UnionFoo: Detektion von category = UNION führt zur C-Schlüsselwort-Emission typedef union { ... } UnionFoo;.
    • Auflösung von TheWord: category = VALUE → Auflösung über SwBaseType.nativeDeclaration → unsigned short TheWord;.
    • Auflösung von TheBytes: category = STRUCTURE → rekursives Absinken → Emission der eingebetteten Struktur struct { ... } TheBytes;.
    • Auflösung der Blattknoten FirstByte und SecondByte zu unsigned char.
  2. Laufzeitverhalten (Speicherzugriff im Task-Kontext):
    • Speicherüberlagerung: TheWord und TheBytes teilen denselben Speicherbereich (2 Bytes).
    • Byte-Reihenfolge: Der Zugriff auf TheBytes.FirstByte vs. TheBytes.SecondByte ist plattformabhängig (Little-Endian vs. Big-Endian) und erfordert architekturelle Übereinstimmung von Hardware-Target und SWC-Algorithmus.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Typenvertrag (Rte_Type.h): Der RTE-Generator emittiert exakt folgende C90/C99-Deklaration: 
    typedef union {
    unsigned short TheWord;
    struct {
        unsigned char FirstByte;
        unsigned char SecondByte;
    } TheBytes;
} UnionFoo;
  • MISRA-Konformität: MISRA C:2012 Richtlinie 19.2 (sowie MISRA C:2004 Regel 18.4) verbietet oder limitiert die Verwendung von Unions in sicherheitskritischem Code (Überlappung von Objekt-Repräsentationen). Der Einsatz von UnionFoo erfordert im Safety-Case ein formales MISRA-Deviation-Dokument.
  • Port-Schnittstellen & Serialisierung:
    • Bei Inter-ECU-Kommunikation (COM/PDU-Router) oder RTE-Transformer-Ketten ist category = UNION problematisch, da Datengröße und aktive Varianten nicht implizit typgesichert übertragen werden. Unions werden primär für Inter-Runnable- oder Intra-ECU-Datenaustausch innerhalb derselben Speichereinheit eingesetzt.
  • Variabilitätsbindung («atpVariation»): Da SwDataDefProps variant ist, können Basistyp-Zuordnungen über System-Constants (SwcImplementations-Varianten) gesteuert werden, sofern die Evaluierung zum Pre-Compile-Zeitpunkt erfolgt.
