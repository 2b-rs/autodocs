1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Komponentendiagramm (Component Diagram) mit Service-/Port-Schnittstellen in Ball-and-Socket-Notation (Provided/Required Interfaces).
  • Technischer Zweck: Spezifikation der architektonischen Systemgrenzen und Schnittstellen des System Health Monitor (SHM) zur plattformübergreifenden Laufzeit-, Fehler- und Modusüberwachung.
  • Architektur-Kontext: Dargestellt ist das Zusammenspiel zwischen Classic Platform (CP), Adaptive Platform (AP) und Hardware-Watchdogs in heterogenen E/E-Architekturen (z. B. High-Performance Controller / Zonen-ECUs). Der SHM fungiert als übergeordnete Instanz zur Aggregation lokaler Health-Zustände und Koordination koordinierter Recovery-Maßnahmen über Plattformgrenzen hinweg.

2. Komponenten, Entitäten & Schnittstellen

#### Zentrale Instanz

  • «component» System Health Monitor (SHM): Plattformübergreifender Monitor, der Health-Status-Informationen sammelt, auswertet und Korrekturmaßnahmen an die zuständigen Mode Manager delegiert.

#### Adaptive Platform (AP, linke Seite)

  • «component» State Manager (SM):
  • FunctionGroupState (Provided Port / Ball): Liefert den aktuellen Zustand aktiver Funktionsgruppen (Function Groups) parallel an den SHM und an das PHM.
  • HealthChannel (Required Port / Socket): Empfängt Health-Status-Events und Eskalationsanforderungen vom SHM.
  • «component» Platform Health Management (PHM):
  • FunctionGroupState (Required Port / Socket): Empfängt Funktionsgruppenzustände vom SM zur Aktivierung/Deaktivierung spezifischer Überwachungsregeln.
  • HealthChannel (Provided Port / Ball): Meldet lokale Überwachungsergebnisse (Alive-, Deadline-, Logical-Supervision) an den SHM.
  • HealthChannel (Required Port / Socket): Empfängt Synchronisations- und Steuerbefehle vom SHM.
  • Implementor specific (Abhängigkeitspfeil): Spezifische Anbindung an den lokalen «component» HW Watchdog.
  • «component» HW Watchdog (AP): Physischer Watchdog (SoC-interner Timer, externer Safety-PMIC oder Hypervisor-Watchdog-Service).

#### Classic Platform (CP, rechte Seite)

  • «component» Basic Software Mode Manager (BswM):
  • ModeSwitchPort (Provided Port / Ball): Signalisiert BSW- und ECU-Modi an den Port Mode (Required Port / Socket) des SHM.
  • ModeNotificationPort (Required Port / Socket): Empfängt Health-Ereignisse vom Port HealthNotification (Provided Port / Ball) des SHM zur Triggerung von BswM-Regeln und Aktionslisten.
  • «component» Watchdog Manager (WdgM):
  • WdgM_LocalMode (Provided Port / Ball): Übergibt lokale Überwachungsmodi/Zustände einzelner Supervised Entities an den Port WdgLocalSupervision (Required Port / Socket) des SHM.
  • WdgM_GlobalMode (Provided Port / Ball): Übergibt den globalen Status (WDGM_GLOBAL_STATUS_OK, FAILED, EXPIRED, STOPPED) an den Port WdgGlobalSupervision (Required Port / Socket) des SHM.
  • Implementor specific (Abhängigkeitspfeil): MCAL-spezifische Anbindung (über WdgIf / Wdg-Treiber) an den lokalen «component» HW Watchdog.
  • «component» HW Watchdog (CP): Dedizierter physischer Hardware-Watchdog der Microcontroller-Einheit.

3. Dynamisches Verhalten & Sequenzablauf

  1. Zustands- & Modusinitialisierung:
  • Auf CP-Ebene schaltet der BswM Betriebsmodi (z. B. STARTUP, RUN) und meldet den Status über ModeSwitchPort $\rightarrow$ Mode an den SHM.
  • Auf AP-Ebene setzt der State Manager Funktionsgruppen aktiv und propagiert FunctionGroupState synchron/asynchron an PHM und SHM.
  1. Zyklische Überwachung & Statusmeldung:
  • Der WdgM überwacht Classic-SW-Cs und meldet lokale sowie globale Zustandsänderungen über WdgM_LocalMode / WdgM_GlobalMode an den SHM.
  • Das PHM überwacht adaptive Anwendungen (Checkpoints, Deadlines) und meldet Fehlerzustände über den HealthChannel an den SHM.
  1. Fehleraggregation & Eskalationspfad:
  • Erkennt der SHM eine plattformrelevante Degradation oder einen Fehler im WdgM/PHM, interveniert er nicht direkt auf Task-/Prozessebene, sondern benachrichtigt die zuständigen Mode Manager:
  • CP-Recovery: Signal über HealthNotification $\rightarrow$ ModeNotificationPort an BswM. Der BswM evaluiert konfigurierte Rules und schaltet z. B. in Safe-State, initiiert Reset oder deaktiviert Partitionen.
  • AP-Recovery: Signal über HealthChannel an den State Manager. Der SM triggert State Transitions der betroffenen Function Groups (z. B. Restart einzelner Prozesse, Fallback-Betrieb).
  1. Ultimativer Hardware-Fallback:
  • Versagt die Software-Eskalationskette (BswM/SM bzw. SHM blockiert), unterbleibt das Triggern des jeweiligen HW Watchdog über die Implementor specific-Pfade von WdgM bzw. PHM, was den hardwareseitigen Reset erzwingt.

4. Normative Relevanz & Entwickler-Hinweise

  • Architektonische Trennung (Separation of Concerns): Der SHM ist ein reiner Monitor und Koordinator; er besitzt keine direkte Steuerungsautorität über Prozesse oder BSW-Module. Modusänderungen und Reinitialisierungen verbleiben strikt in der Hoheit von BswM (Classic) und State Manager (Adaptive).
  • Konfigurationsanforderungen (Classic Platform):
  • Im BswM müssen entsprechende BswMModeRequestPort-Instanzen für die Entgegennahme der HealthNotification und BswMModeSwitchPort-Instanzen für das Reporting an den SHM definiert werden.
  • Im WdgM ist die Bereitstellung der Schnittstellen via RTE bzw. BSW-Scheduler für WdgM_LocalMode und WdgM_GlobalMode als Sender-Receiver- oder C-API-Interface zu konfigurieren.
  • Konfigurationsanforderungen (Adaptive Platform):
  • FunctionGroupState erfordert die korrekte Definition von Function Groups im Execution Manifest und Modellierung der Zustandsübergänge im SM.
  • Der HealthChannel erfordert eine modellierte Service-Schnittstelle (ara::com / IPC) inklusive End-to-End-Absicherung (E2E), falls SHM und PHM auf unterschiedlichen Cores oder Virtual Machines (VMs) laufen.
  • Echtzeit- & Safety-Budgetierung (FHTI):
  • Die Kaskadierung PHM/WdgM -> SHM -> SM/BswM -> Recovery Action erzeugt Latenzen über IPC/Inter-Core-Kommunikation. Die Summe dieser Signallaufzeiten und Zustandswechsel muss strikt innerhalb des geforderten Fault Handling Time Interval (FHTI) liegen.
  • Watchdog-Treiber-Schnittstelle: Die Kennzeichnung Implementor specific unterstreicht, dass AUTOSAR an dieser Stelle keine plattformübergreifend standardisierte API vorschreibt. Im CP-Stack erfolgt die Bindung normativ über MCAL (Wdg_ChannelType), im AP-Stack über OS-spezifische Watchdog-Devices (z. B. Linux /dev/watchdog oder QNX devb-wdog) bzw. SPI-Treiber zu externen SBC/PMIC-Bausteinen.
