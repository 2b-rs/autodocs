1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (AUTOSAR M2-Metamodell-Ausschnitt, Execution / Machine Manifest).
  • Technischer Zweck: Spezifikation der Ausführungsstrukturen für Aktionen des State Managements (ara::sm) auf der AUTOSAR Adaptive Platform (Release R23-11). Es modelliert die strukturierte, geordnete Abarbeitung von Steuerungsbefehlen (StateManagementActionList) zur Koordination von Funktionsgruppen (Function Groups in ara::exec), Zustandsautomaten, Netzwerkmanagement (ara::nm), zeitlichen Verzögerungen (Sleep) und Synchronisationspunkten innerhalb eines Software-Clusters.

3. Dynamisches Verhalten & Sequenzablauf

  • Aktionslisten-Trigger: Eine StateManagementActionList wird bei Eintritt in oder Aktivierung des durch +affectedState referenzierten Zielzustands (ModeDeclaration) abgearbeitet.
  • Erweiterte sequentielle Ausführung: Die geordnete Komposition +actionItem [0..*] {ordered} steuert die Abarbeitung deterministisch:
  1. Funktionsgruppen-Steuerung (StateManagementSetFunctionGroupStateActionItem): State Management fordert über portPrototype einen Zustandswechsel für eine Funktionsgruppe via Execution Management an (setFunctionGroupState).
  2. Zustandsautomaten-Steuerung (StateManagementStateMachineActionItem): Startet (startStateMachine) oder stoppt (stopStateMachine) Zustandsautomaten. Über overrideInitialState kann beim Start gezielt ein von initialMode abweichender Zustand als Einstiegszustand vorgegeben werden.
  3. Netzwerkmanagement-Steuerung (StateManagementNmActionItem): Fordert im Ablauf den Übergang des Netzwerks in fullCom oder noCom an.
  4. Wartezeiten (StateManagementSleepActionItem): Pausiert die Ausführung der Aktionsliste für die definierte Dauer sleepTime.
  5. Synchronisation (StateManagementSyncActionItem): Dient als Synchronisationsbarriere, um asynchrone Anforderungen vor Ausführung nachfolgender Schritte abzuwarten.
  • Statusbenachrichtigung: Umschaltungen von Funktionsgruppen werden über StateManagementFunctionGroupSwitchNotificationInterface unter Bezug auf ModeDeclarationGroup im System propagiert.

4. Normative Relevanz & Entwickler-Hinweise

  • Port-Rollenwechsel (PPort zu RPort): In Release R24-11 wurde die Modellierung von StateManagementSetFunctionGroupStateActionItem normativ korrigiert. Die Assoziation +rPortPrototype verweist nun auf einen RPortPrototype (requiredInterface), da das State Management als Client fungiert, der die Umschaltung von Funktionsgruppen beim Execution Management anfordert bzw. konsumiert, anstatt den Dienst selbst bereitzustellen (PPortPrototype).
  • Deterministische Orchestrierung: Die Sequenzierung via {ordered} an +actionItem bleibt verbindlich für die deterministische Abarbeitung in ara::sm.
  • Instanzreferenzen («instanceRef»): affectedState, setFunctionGroupState und rPortPrototype sind als M2-Instanzreferenzen modelliert und müssen im Manifest auf konkrete Software-Cluster-Elemente aufgelöst werden.
  • Zustandsautomaten- und NM-Steuerung: Direkte Assoziationen startStateMachine und stopStateMachine auf ModeDeclarationGroupPrototype, Übersteuerung des Initialzustands via overrideInitialState, sowie Netzwerk-Umschaltungen (NmStateRequestEnum) und explizite Wartezeiten (StateManagementSleepActionItem).
  • Aktualisierbarkeit & Modularisierung: «UploadableDesignElement» an ModeDeclarationGroup unterstützt dynamische Updates im Software Package Management; «atpSplitable» ermöglicht ARXML-Splitting.
