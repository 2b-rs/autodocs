1. Diagrammtyp & Architektur-Kontext

Protokoll- und Datenstruktur-Spezifikation (Binärframe-Layout / Byte-Level-Protokolldiagramm) im Kontext des AUTOSAR Log and Trace Protocols (AUTOSAR_PRS_LogAndTraceProtocol). Das Diagramm visualisiert den Aufbau des optionalen „Extension Header“ (bzw. Extended Header), der im PDU-Payload dynamische Metadatenfelder für Protokollnachrichten kapselt.

2. Komponenten, Entitäten & Schnittstellen

Der Extension Header umfasst sequenziell angeordnete, optional vorhandene Metadaten-Felder, deren relative Offsets dynamisch berechnet werden (dyn0 bis dyn11):

  • ECU (ECU-ID): Offset dyn0 (8-Bit Längenangabe in Bytes), gefolgt von dyn0 + 1 bis dyn0 + ... (ASCII-Zeichenkette der ECU-ID).
  • APID (Application-ID): Offset dyn1 (8-Bit Längenangabe in Bytes), gefolgt von dyn1 + 1 bis dyn1 + ... (ASCII-Zeichenkette der APID).
  • CTID (Context-ID): Offset dyn2 (8-Bit Längenangabe in Bytes), gefolgt von dyn2 + 1 bis dyn2 + ... (ASCII-Zeichenkette der CTID).
  • SEID (Session ID): Offsets dyn3 bis dyn3 + 3 (32-Bit Unsigned Integer, 4 Bytes).
  • FINA (Source File Name): Offset dyn4 (8-Bit Längenangabe in UTF-8 Code Units), gefolgt von dyn4 + 1 bis dyn4 + ... (UTF-8 Code Units des Dateinamens).
  • LINR (Line Number): Offsets dyn5 bis dyn5 + 3 (32-Bit Unsigned Integer, 4 Bytes).
  • TAGS:
    • NOTG (Offset dyn6): uint8 Anzahl der enthaltenen Tags.
    • Sequenz von Tag-Elementen (Tag_1, Tag_2, ..., Tag_<n>): Jeweils 8-Bit Längenfeld (Bytes) gefolgt von der entsprechenden Anzahl ASCII-Zeichen für den Tag-Namen (Offsets dyn6 + 1 ff., dyn8 ff., dyn9 ff.).
  • PRLV (PrivacyLevel): Offset dyn10 (Wert des PrivacyLevel).
  • Erweiterungsschema (<future_field>): Offset dyn11 (Längenfeld), gefolgt von dyn11 + 1 ff. (Wert des künftigen Felds) als generisches Erweiterungstemplate („Template for future extensions“).

3. Dynamisches Verhalten & Sequenzablauf

Serialisierungs- und Parsing-Ablauf:

  1. Das Vorhandensein der jeweiligen Felder wird typischerweise über Header-Flags/Konfigurationsbits im übergeordneten Protokollheader gesteuert.
  2. Felder fester Größe (SEID, LINR) belegen deterministisch jeweils 4 Bytes (32-Bit vorzeichenlose Ganzzahlen), PRLV belegt ein Feld an Offset dyn10.
  3. Felder variabler Länge (ECU, APID, CTID, FINA, einzelne Tags) beginnen mit einem 1-Byte-Längenindikator, der die Anzahl der nachfolgenden Bytes bzw. UTF-8 Code Units festlegt; der Parser iteriert dynamisch um Length + 1 Bytes zum nächsten Feld-Offset weiter.
  4. Das TAGS-Feld liest an dyn6 (NOTG) die Gesamtzahl an Tags ein und verarbeitet anschließend in einer Schleife NOTG-mal die Längen- und ASCII-Zeichenkettenstrukturen für Tag_1 bis Tag_<n>.
  5. Das System unterstützt Vorwärtskompatibilität über das strukturierte Template für künftige Erweiterungsfelder (Length + Value).

4. Normative Relevanz & Entwickler-Hinweise

Normative Relevanz für Dlt-/LogAndTrace-Protokoll-Implementierungen:

  • Byte-Reihenfolge und Ausrichtung: Felder wie SEID und LINR sind 32-Bit vorzeichenlose Integer und folgen den Endianness-Vorgaben des Protokolls.
  • Enkodierung: ECU-ID, APID, CTID und Tag-Namen sind strikt als ASCII spezifiziert; Dateinamen (FINA) sind explizit als UTF-8 Code Units kodiert.
  • Eindeutigkeit & Konsistenz: Längenangaben sind 8-Bit-Werte, wodurch Nutzlasten dieser Zeichenketten auf maximal 255 Bytes bzw. UTF-8-Einheiten limitiert sind. Die ECU-ID muss zur eindeutigen Zuordnung fahrzeugweit unik sein.
  • Erweiterbarkeit: Parser müssen in der Lage sein, unbekannte optionale Folgefelder anhand des generischen Längen-Werte-Schemas (dyn11) zu überspringen, sofern dies im Standard spezifiziert ist.
