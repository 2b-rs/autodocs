1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR Methodology Workflow / Prozessdiagramm (angelehnt an das SPEM-Metamodell / UML-Aktivitätendiagramm mit Partitionen/Swimlanes).
  • Architektur-Kontext: Übergreifende Definition des AUTOSAR-Entwicklungsprozesses gemäß AUTOSAR Methodology (TPS_ECUConfiguration / TPS_Methodology, Release R25-11). Das Diagramm visualisiert den Top-down- und komponentenorientierten Datenfluss von der VFB-Spezifikation und Systembeschreibung über die Generierung von System-/ECU-Extrakten bis zur finalen BSW-, SWC- und ECU-Software-Integration.
  • Technischer Zweck: Formale Trennung von Verantwortlichkeiten (OEM vs. Tier-1/Zulieferer), Entkopplung der Applikationssoftware von der Zielhardware (über das VFB-Konzept) und Definition der normativen Ein- und Ausgangsartefakte für Generatoren, Konfiguratoren und Integrationswerkzeuge.

2. Komponenten, Entitäten & Schnittstellen

Partitionen (Domänen / Disziplinen)
  • Virtual Functional Bus (VFB): Frühe funktionale Modellierung unabhängig von Netzwerktopologie und Hardware-Zuordnung.
  • System: Topologie- und Netzwerkdesign, Allokation von SWCs auf ECUs, PDU-/Signal-Routing und Subsystem-Dekomposition.
  • Basic Software (BSW): Konfiguration, Portierung und Bereitstellung der standardisierten Basissoftwaremodule (MCAL, Services, BSW-Stack).
  • Software Component (SWC): Spezifikation und Implementierung der Applikationslogik als atomare Komponenten.
  • ECU: Physische Ziel-Steuergeräteebene für Konfiguration, Code-Generierung und finales Linken.
Aktivitäten (Prozessschritte)
  • Develop an Abstract System Description: Erstellung grobgranularer Systemmodelle unter Berücksichtigung von Randbedingungen.
  • Develop a VFB System Description: Detaillierte Spezifikation der Softwarekomponenten-Typen, Ports und Interfaces.
  • Develop System: Gesamtnetzwerk-Design, Bus-Konfiguration (CAN/LIN/FlexRay/Ethernet), Signal-Mapping und Mapping von SWC-Prototypen auf ECUs.
  • Develop Sub-System: Kaskadierte Verfeinerung für hierarchische Systemstrukturen (z. B. Sub-Bordnetze/Domänenrechner).
  • Develop Application Software: Implementierung der internen Runnable-Logik und Generierung der SWC-Implementierungsbeschreibungen.
  • Develop Basic Software: Implementierung/Anpassung von Treibern, Stacks und Transformern für die Zielplattform.
  • Integrate Software for ECU: ECU-Konfiguration (BSW/RTE), Generierung der Glue-Logik (RTE-Header, BSW-Tabellen) und finales Kompilieren/Linken.

3. Dynamisches Verhalten & Sequenzablauf

Der Ablauf folgt einem datenflussgetriebenen, iterativen Phasenmodell:

  1. Abstraktions- & Spezifikationsphase:
    • Basisstandards (VFB AUTOSAR Standard Package) und optionale Randbedingungen (System Constraint Description) steuern die Erstellung der Abstract System Description.
    • Parallel oder nachgelagert wird die VFB-Architektur (Overall VFB System) ausdefiniert.
  2. System-Partitionierung & Extraktion:
    • Develop System konsumiert das Overall VFB System, optionale Abstract System Descriptions und Constraints.
    • Ausgabe von drei Branching-Pfaden:
      • Subsystem-Pfad: Erzeugung eines System Extract (0..*), um Sub-Systeme (Develop Sub-System) rekursiv auszulegen, welche wiederum ECU Extracte erzeugen.
      • Transformer-Pfad: Bereitstellung von Transformer Design Bundlen (z. B. SOME/IP-Serializer, E2E-Transformer).
      • Direkter ECU-Pfad: Direkte Erzeugung des normativen ECU Extract (1..*).
  3. Parallele Entwicklungszweige (Entkopplung):
    • Applikation: Develop Application Software benötigt strikt das Overall VFB System (1) und liefert die Delivered Atomic Software Components (SWC-ARXMLs, C-Code/Objektdateien).
    • Basissoftware: Develop Basic Software verarbeitet das statische BSW Standard Package (1) und optionale Transformer Design Bundle (0..*), um die BSW Module Delivered Bundles (Treiber, BSW-C-Dateien, BswModuleDescription BSWMD) zu paketieren.
  4. ECU-Synthese & Integration:
    • Integrate Software for ECU synchronisiert die drei Zuflüsse: BSW Module Delivered Bundle (1..*), ECU Extract (1) und Delivered Atomic Software Components (1..*).
    • Erzeugt als finales Zielartefakt ECU Software Delivered (Executable, Map-Files, A2L).

4. Normative Relevanz & Entwickler-Hinweise

  • ECU Extract (ECUExtractOfSystemDescription) als Integrations-Dreh- und Angelpunkt:
    • Der OEM bzw. Systemintegrator liefert den ECU Extract. Dieser enthält die vollständige Kommunikationsmatrix (Com-Signale, PDUs, Frames, Cluster), die instanziierten SWCs auf der Ziel-ECU und das Signal-to-PDU-Mapping.
    • Hinweis für Integratoren: Ohne validen ECU Extract können EcuC-Generatoren (z. B. für Com, PduR, CanIf, CanNm) und der RTE-Generator keine konsistente Konfiguration erzeugen.
  • Applikationsentwickler (SWC):
    • Arbeiten hardwareunabhängig ausschließlich gegen das Overall VFB System.
    • Das Lieferartefakt (Delivered Atomic Software Components) muss zwingend die SoftwareComponentDescription (InternalBehavior, Runnables, Events, PortAPIOptions) sowie den Quell-/Objektcode enthalten. Ein Zugriff auf BSW-APIs außerhalb der definierten Service-Ports (z. B. NvM, Dem) ist methodisch verboten.
  • BSW- & Treiber-Entwickler (MCAL / Stack):
    • Verwenden das BSW Module Delivered Bundle (bestehend aus Quellcode und .arxml-Metamodellbeschreibungen in Form von BswModuleDescription und EcucModuleDef).
    • Werden datenstromorientierte Serialisierungen genutzt (z. B. SOME/IP, E2E), ist das Transformer Design Bundle zwingend für die Konfiguration der Transformer-Kette im BSW-Stack (Com/RTE) erforderlich.
  • Hierarchische Dekomposition (System Extract):
    • Für komplexe Domänencontroller oder HPC-Systeme erlaubt der Workflow über Develop Sub-System das Splitten des Gesamtsystems in Teilsysteme, ohne dass der Zulieferer Einblick in das Gesamtfahrzeug-Systemmodell benötigt.
