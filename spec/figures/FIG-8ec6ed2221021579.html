1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schichtenmodell-basiertes Architektur- und Informationsflussdiagramm (BSW Information Path) gemäß AUTOSAR Classic Platform (R4.0.3, AUTOSAR_EXP_ErrorDescription).
  • Technischer Zweck: Spezifikation des Signal-, Diagnose- und Wiederherstellungspfades bei Auftreten eines Static Block Check Errors (z. B. CRC-Inkonsistenz, ungültige Block-Header-Informationen oder Längen-Mismatch) während persistenter Leseoperationen im NVRAM-Stack.
  • Funktionale Einordnung: Verknüpft die Erkennung innerhalb des NVRAM Managers (NvM) mit dem diagnostischen Fehlerspeicher (DEM), der hardwarenahen Wiederherstellung über die Speicherabstraktion (MemIf, Fee/Ea, MCAL-Treiber) und der Benachrichtigung der Applikation (RTE, Polling/Notification).

2. Komponenten, Entitäten & Schnittstellen

  • Application Layer:
    • Software-Components (SW-Cs) als Konsumenten der Non-Volatile Data Blocks.
  • AUTOSAR Runtime Environment (RTE):
    • Vermittelt Service-Ports und Callbacks zwischen SW-Cs und NvM.
  • System Services:
    • DEM (Diagnostic Event Manager): Empfängt Integritäts- und Request-Fehler (Dem_SetEventStatus / Dem_ReportErrorStatus).
    • DET (Default Error Tracer) & FIM (Function Inhibition Manager): Im Schichtenmodell präsent; DEM triggert bei qualifizierten Fehlern Inhibitionsmasken im FIM.
  • Memory Services:
    • NVRAM Manager (NvM): Zentrale BSW-Komponente für Blockverwaltung; agiert als Detektionsstelle (Detection) und Auslöser der Recovery (Recovery Initiator).
  • Memory Hardware Abstraction Layer:
    • Mem Abstraction Interface (MemIf): 1:n-Abstraktionsschicht zur Adressierung konkreter Speichertreiber via Device-Index.
    • EEPROM Abstraction (Ea) & Flash EEPROM Emulation (Fee): Virtualisierung von Blöcken auf physischen Sektoren/Seiten.
    • Ext. EEPROM Driver & Ext. Flash Driver: Abstraktion bordexterner Speicherbausteine.
  • Communication & Memory Drivers (MCAL / Hardware Abstraction):
    • SPI Handler / Driver (Spi): Bus-Treiber zur Kommunikation mit externen Speicherbausteinen (External EEPROM).
    • Int. EEPROM Driver (Eep) & Int. Flash Driver (Fls): Direkte Registertreiber für Mikrocontroller-interne Speicherressourcen (µC).

3. Dynamisches Verhalten & Sequenzablauf

  1. (1) Detection (Erkennung):
    • Beim Einlesen eines Blocks (z. B. während NvM_ReadAll beim Start oder asynchronem NvM_ReadBlock) verifiziert der NvM die Blockintegrität. Weicht die berechnete Prüfsumme vom gespeicherten CRC ab oder ist der statische Block-Header korrupt, wird der Fehler intern detektiert.
  2. (2) Error Reporting & Recovery Initiation:
    • Diagnosemeldung (Notification): Der NvM meldet das Fehlerereignis (z. B. NVM_E_INTEGRITY_FAILED bzw. blockbezogenes DEM-Event) an das DEM.
    • Recovery Initiator: Der NvM initiiert die hinterlegte Wiederherstellungsstrategie (z. B. Wechsel auf redundanten Block NVM_BLOCK_REDUNDANT oder Laden vorkonfigurierter ROM-Standardwerte).
  3. (3) Recovery Execution (Wiederherstellung):
    • Die Wiederherstellung wird nach unten durchgereicht: NvM → MemIf → Ea/Fee → interner/externer Speichertreiber (Int. EEPROM Driver / Int. Flash Driver bzw. SPI).
    • Physisches Nachladen redundanter Daten oder persistentes Überschreiben mit Default-Daten zur Wiederherstellung der Speicherintegrität.
  4. (4) Application Interaction & Diagnostic Update:
    • Statusupdate an DEM: Nach Abschluss des Recovery-Versuchs aktualisiert der NvM den Event-Status im DEM (z. B. Fehlereingrenzung, Bestätigung oder DEM_EVENT_STATUS_PASSED bei erfolgreicher Wiederherstellung).
    • Notification (Push): Der NvM informiert die Applikation asynchron über das Ergebnis (via RTE-Callback NvM_SingleBlockCallbackFunction).
    • Polling (Pull): Die Applikation fragt den Block-Status zyklisch über die RTE per API ab (NvM_GetErrorStatus, Rückgabewerte wie NVM_REQ_OK, NVM_REQ_NOT_OK, NVM_REQ_INTEGRITY_FAILED).

4. Normative Relevanz & Entwickler-Hinweise

  • NvM-Block-Konfiguration (NvMBlockDescriptor):
    • NvMBlockUseCrc: Muss zwingend auf TRUE stehen (mit passendem NvMBlockCrcType: 8, 16 oder 32 Bit), um statische Blockprüfungen überhaupt zu aktivieren.
    • NvMBlockManagementType: Bei kritischen Daten NVM_BLOCK_REDUNDANT wählen, um der Recovery-Logik den Fallback auf eine intakte Spiegelkopie im Flash/EEPROM zu ermöglichen.
    • NvMRomBlockDataAddress / NvMInitBlockCallback: Konfiguration valider ROM-Ersatzwerte, damit der NvM bei Integritätsverlust den RAM-Mirror mit deterministischen Daten initialisieren kann.
  • DEM-Parametrierung:
    • Jeder sicherheits- oder betriebsrelevante NVRAM-Block muss auf ein passendes DemEventParameter gemappt sein, um DTC-Qualifikation und Freeze-Frame-Ablage zu gewährleisten.
  • Applikations-Design:
    • Applikationen dürfen während laufender Recovery (NvM_GetErrorStatus == NVM_REQ_PENDING) nicht auf den RAM-Block zugreifen.
    • Auswertung von Rückgabewerten: Ein NVM_REQ_RESTORED_FROM_ROM signalisiert der SW-C, dass Default-Daten geladen wurden und Systemparameter ggf. neu kalibriert/initialisiert werden müssen.
