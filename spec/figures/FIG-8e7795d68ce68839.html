1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm zur Spezifikation des AUTOSAR ECU Configuration Parameter Definition Metamodells (AR_EcucDef).
  • Architektur-Kontext: Definiert das standardisierte Konfigurationsschema (EcucModuleDef) für AUTOSAR-Transformer-Module (Xfrm) gemäß AUTOSAR_ASWS_TransformerGeneral (Release R4.2.2).
  • Funktionaler Zweck: Schließt die Lücke zwischen der abstrakten Systembeschreibung (VFB/SWC-Ebene mit DataTransformation, TransformationTechnology und VariableDataPrototype) und der konkreten BSW-C-Implementierung auf Steuergeräte-Ebene (BswModuleEntry). Es parametriert, welche C-Funktionen des Transformer-Stacks zur Laufzeit von der RTE für das Transformieren (z. B. SOME/IP-Serialisierung, E2E-Protection) bzw. inverse Transformieren spezifischer Signale aufgerufen werden.

  • System Template: DataTransformation (Identifiable) $\xrightarrow{\text{+transformerChain 1..* \{ordered\}}}$ TransformationTechnology (Identifiable).
  • Software Component Template: SwComponentPrototype (AtpPrototype), PortPrototype (AtpBlueprintable, AtpPrototype), VariableDataPrototype (AutosarDataPrototype).

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Konfigurationsmetamodell besitzt das Diagramm keinen sequenziellen Kontrollfluss. Es definiert jedoch die deterministische Auflösung für die Generierungs- und Laufzeitphase:

  1. Generierungsphase (RTE-/BSW-Generator):
    • Der Generator liest XfrmImplementationMapping aus.
    • Er ermittelt über XfrmVariableDataPrototypeInstanceRef den Kommunikationsendpunkt (Port/Signal) und bindet die über XfrmTransformerBswModuleEntryRef bzw. XfmInvTransformerBswModuleEntryRef konfigurierten C-Funktionen in den Sende- bzw. Empfangspfad der RTE ein.
  2. Laufzeit-Pfad (Senden):
    • Aufruf von Rte_Write_* / Rte_Send_* → RTE leitet Daten an die durch XfrmTransformerBswModuleEntryRef referenzierte Funktion weiter → serialisierter/transformierter Puffer wird an den Kommunikationsstack (Com/SoAd) übergeben.
  3. Laufzeit-Pfad (Empfang):
    • Eingehende PDU von Com/SoAd → RTE ruft die durch XfmInvTransformerBswModuleEntryRef definierte inverse Funktion auf → deserialisierte Daten werden in den SWC-Puffer geschrieben.
  4. Fehlerpfade:
    • Tritt während der Transformation ein Fehler auf, wird bei XfrmDevErrorDetect == TRUE DET aufgerufen; bei transienten/permanenten Fehlern erfolgt der Eintrag über die in XfrmDemEventParameterRefs hinterlegten Event-IDs.

4. Normative Relevanz & Entwickler-Hinweise

  • Protokoll-Header-Extraktion: Über den neu eingeführten Parameter XfrmTransformerClassExtractProtocolHeaderFields wird spezifiziert, welcher Transformer-Typ (Serializer für z. B. SOME/IP, Safety für E2E oder Security für SecOC) Protokoll-Header-Felder aus dem Datenstrom extrahiert. Dies ist essenziell für die koordinierte Deserialisierung und Weiterleitung von Metadaten durch die RTE.
  • Client/Server Transaction Handles: Die Foreign Reference XfrmCSTansactionHandleImplementationDataTypeRef ermöglicht die formale typisierte Bindung von Transaction Handles bei trafo-unterstützter Client/Server-Kommunikation an konkrete ImplementationDataType-Definitionen.
  • Tippfehler im Metamodell: Der Bezeichner der Transaction-Handle-Referenz weist in dieser Fassung den Schreibfehler XfrmCSTansactionHandleImplementationDataTypeRef (fehlendes „r“ in „Transaction“) auf. Integratoren müssen sicherstellen, dass Werkzeugketten und Generatoren exakt diesen Bezeichner unterstützen.
