1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Aktivitätsdiagramm der AUTOSAR-Methodik (basierend auf dem SPEM 2.0-Profil / Software & Systems Process Engineering Metamodel für AUTOSAR M2-Prozessmodelle).
  • Architektur-Kontext & Zweck: Das Diagramm spezifiziert die Entwurfszeit-Aktivität (Design-Time Activity) Define BSW Interfaces im AUTOSAR Classic Platform Methoden-Workflow (TR Methodology, Kapitel 3). Zweck ist die formale, maschinenlesbare Deklaration aller Schnittstellen, Funktionssignaturen und Datentypen eines Basissoftware-Moduls (BSW) vor der Definition des internen Verhaltens (BswInternalBehavior) und vor der eigentlichen BSW-Code-Implementierung bzw. -Konfiguration.

2. Komponenten, Entitäten & Schnittstellen

#### Akteure / Rollen

  • Basic Software Designer (Stereotyp «performs», Kardinalität 1): Primäre Rolle; verantwortlich für die architektonische Spezifikation der Modulschnittstellen, Standardkonformität und Protokoll-Zuweisung.
  • Basic Software Module Developer (Stereotyp «performs», Kardinalität 0..1): Unterstützende/optionale Rolle (Stack-Vendor/Tier-1); steuert modulspezifische Besonderheiten, Hardware-Treiber-Schnittstellen und herstellerspezifische APIs bei.

#### Aktivität

  • Define BSW Interfaces: Zentraler Prozessschritt (Chevron-Symbol), der Eingangsartefakte aggregiert und die formalen Modulschnittstellen erzeugt.

#### Eingangsartefakte (Work Products mit Stereotyp «input»)

  • BSW Types (Kardinalität 1, Dokument-Work-Product): ARXML-Beschreibungen der grundlegenden Datentypen (ImplementationDataType, SwBaseType, CompuMethod, DataConstr), die modulintern oder modulübergreifend an den APIs verwendet werden.
  • Basic Software Entries (Kardinalität 1, Dokument-Work-Product): ARXML-Deklarationen (BswModuleEntry), welche die C-Funktionsprototypen (Signaturen, Rückgabetypen, Argumente, Reentrancy-Attribute, Call-Contexts) definieren.
  • BSW Standard Package (Kardinalität 0..1, Package-Work-Product): Normatives, von AUTOSAR bereitgestelltes Basispaket mit standardisierten Schnittstellendefinitionen und Templates für standardisierte BSW-Module.
  • ECU Resources Description (Kardinalität 0..1, Dokument-Work-Product): Hardware- und MCU-Ressourcenbeschreibung (Register, Takt, Interrupt-Vektoren, Memory-Layout); erforderlich bei hardwarenahen BSW-Modulen (z. B. MCAL-Treiber).

#### Ausgangsartefakt (Work Product mit Stereotyp «output»)

  • Basic Software Module Description (BSWMD / BswModuleDescription, Kardinalität 1): Formale AUTOSAR-XML-Beschreibung, die das BSW-Modul auf Schnittstellenebene deklariert (u. a. providedEntry, requiredEntry, Abhängigkeiten zu anderen BSW-Modulen und Schnittstellen-Katalog).

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein Entwurfszeit-Methodologie-Diagramm handelt, beschreibt der Ablauf keinen Laufzeit-Callstack, sondern die Phasenabfolge im Entwicklungszyklus:

  1. Input-Bereitstellung:
  • Das AUTOSAR BSW Standard Package wird als Basis importiert (sofern ein Standard-BSW-Modul spezifiziert wird).
  • Für hardwareabhängige Module (MCAL) werden H/W-Restriktionen über die ECU Resources Description geladen.
  1. Typ- und Funktionsdeklaration:
  • Bereitstellung der BSW Types zur typkonsistenten Parametrisierung aller Schnittstellen.
  • Modellierung der C-Signaturen als Basic Software Entries (BswModuleEntry).
  1. Schnittstellen-Synthese:
  • Der Basic Software Designer (ggf. unterstützt durch den Basic Software Module Developer) verknüpft die BswModuleEntry-Definitionen als bereitgestellte (providedEntry) oder benötigte (requiredEntry) Schnittstellen mit dem Modul.
  • Festlegung von Reentrancy (isReentrant), Ausführungskontext (executionContext: Task, ISR, Unspecified) und Synchronisationsverhalten.
  1. Erzeugung des Deliverables:
  • Export der konsolidierten Basic Software Module Description (BSWMD).
  • Das Dokument dient als Pflicht-Input für nachfolgende Aktivitäten: Define BSW Behavior (Zuordnung zu Tasks, Events, Exclusive Areas) und Configure BSW.

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung Interface vs. Internal Behavior: In AUTOSAR (ab 4.0) trennt das Metamodell strikt zwischen der Modulschnittstelle (BswModuleDescription) und dem internen Ablauf (BswInternalBehavior). Dieser Prozessschritt erzeugt ausschließlich den Schnittstellenvertrag (Header-Ebene), noch keine Scheduling-Entitäten (BswSchedulableEntity).
  • Verbindlichkeit von BswModuleEntry: Jeder C-API-Header eines BSW-Moduls muss eins-zu-eins mit den definierten BswModuleEntry-Instanzen übereinstimmen. Generator-Tools (z. B. für RTE/SchM und BSW-Treiber) validieren Typen, Argumente (SwServiceArg) und Modul-Präfixe strikt gegen dieses ARXML-Artefakt.
  • Konsequenz für MCAL- und Stack-Entwickler: Fehlen herstellerspezifische Erweiterungen (Vendor-Specific API Extensions) im BSW Standard Package, müssen diese als eigene Basic Software Entries und BSW Types definiert und in die BSWMD eingebunden werden, bevor die BSW-Konfiguration (ECUC) oder SchM-Generierung gestartet werden kann.
