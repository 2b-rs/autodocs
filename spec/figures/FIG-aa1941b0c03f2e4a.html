1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Schichtenmodell / Blockschaltbild der AUTOSAR Classic Platform Communication Architecture mit speziellem Fokus auf den CAN-Stack (AUTOSAR Release R25-11, AUTOSAR_CP_SWS_CANTransportLayer).
  • Technischer Zweck: Detaillierte Darstellung der vertikalen und horizontalen Architektur des CAN-Kommunikationssystems. Zeigt die Integration von Standard-CAN, CAN FD und CAN XL von den oberen Kommunikationsdiensten über die Hardware-Abstraktion und MCAL-Treiberschicht bis zur physischen Mikrocontroller-Hardware ($\mu\text{C}$) und externen CAN-Controllern via SPI.

2. Komponenten, Entitäten & Schnittstellen

Schichten & Komponenten (Top-Down)
  • Communication Services (Hellblau / BSW):
    • Busunabhängige Module (Orange):
      • Large Data COM (LdCom): Effiziente Datenübertragung für unsegmentierte Großdaten (z. B. CAN XL / Ethernet) unter Umgehung komplexer Signal-Packings.
      • AUTOSAR COM: Signal-Packing/-Unpacking und Signalrouting.
      • Diagnostic Com. Manager (DCM): UDS/OBD-Diagnosedienste.
      • Diagnostic Log and Trace (DLT): Logging- und Tracing-Framework.
      • Communication Secure Onboard (SecOC): Kryptografische Absicherung von PDUs.
      • IPDU Multiplexer (IpduM): Multiplexen mehrerer Layouts in eine I-PDU.
      • PDU Router (PduR): Zentrales PDU-Routing zwischen oberen Diensten und TP bzw. CanIf.
      • Generic NM Interface: Busunabhängige Verwaltung des Netzwerkmanagements.
    • CAN-spezifische Module (Dunkelblau):
      • CAN Transport Protocol (CanTp): Segmentierte Datenübertragung nach ISO 15765-2.
      • CAN State Manager (CanSM): Steuerung der CAN-Betriebszustände.
      • CAN NM: CAN-spezifisches Netzwerkmanagement.
  • Communication Hardware Abstraction (Grün / BSW):
    • L-SDU Router: Routing von L-SDUs auf Abstraktionsebene.
    • CAN Interface (CanIf): Zentrale Schnittstelle für PDU-Handling, Pufferung und Controller-Abstraktion.
    • CAN Transceiver Driver (CanTrcv): Ansteuerung des physischen Transceivers; enthält gestrichelte Erweiterung für CAN XL.
    • Driver for ext. CAN ASIC: Abstraktion und Treiberlogik für extern angebundene CAN-Controller.
  • MCAL / Treiberschicht (Rot):
    • I/O Drivers:
      • DIO Driver (Orange): Digitale Ein-/Ausgänge zur diskreten Transceiver-/ASIC-Steuerung (z. B. Standby-, Enable-Pins).
    • Communication Drivers:
      • SPIHandler Driver (Orange): SPI-Treiber zur Kommunikation mit externen CAN-Controllern.
      • CAN Driver (Dunkelblau): MCAL-Treiber für On-Chip-CAN-Controller; enthält gestrichelte Erweiterung für CAN XL.
  • Hardware-Ebene ($\mu\text{C}$ & Extern, Schwarz):
    • µC: Mikrocontroller mit Hardware-Peripherieblöcken SPI und On-Chip CAN.
    • External CAN Controller: Externer Standalone-CAN-Controller/ASIC, über den SPI-Bus an den $\mu\text{C}$ angebunden.
Daten- und PDU-Ebenen
  • Signale & Large Data: RTE-Datenaustausch über AUTOSAR COM bzw. Direktübertragung über LdCom.
  • I-PDUs & N-PDUs: Kapselung über PduR und Segmentierung im CanTp.
  • L-SDU / L-PDU: Vermittlung im L-SDU Router sowie Weiterleitung über CanIf an interne (CAN Driver) oder externe (Driver for ext. CAN ASIC via SPIHandler) Pfade.
  • CAN XL Payloads: Erweiterte Frame-Nutzdatenlängen bis 2048 Byte durchgängig über CAN XL Komponenten unterstützt.

3. Dynamisches Verhalten & Sequenzablauf

Dynamisches Verhalten & Sequenzablauf
  1. On-Chip CAN Übertragungspfad (Classic CAN / CAN FD / CAN XL):
    • TX: AUTOSAR COM / LdCom / DCM → PduR → (CanTp bei Segmentierung) → CanIf → CAN Driver (inkl. CAN XL) → interner CAN-Controller auf dem $\mu\text{C}$.
    • RX: Interner CAN-Controller → CAN Driver ISR → CanIf_RxIndication → L-SDU Router / PduR → obere Schichten (COM, LdCom, CanTp → DCM).
  2. Pfad für externe CAN-Controller (ASIC über SPI):
    • TX: CanIf erkennt Zielkanal auf externem ASIC → Aufruf Driver for ext. CAN ASIC → Weiterleitung an SPIHandler Driver → physische SPI-Übertragung an External CAN Controller.
    • Hardware-Steuerung: Diskrete Pins (Mode Switch, Wakeup, Reset) werden parallel über den DIO Driver geschaltet.
    • RX: External CAN Controller meldet Daten (z. B. via Interrupt an DIO) → SPIHandler Driver liest Frame aus → Weiterleitung an Driver for ext. CAN ASIC → CanIf_RxIndication.
  3. LdCom Großdatenpfad:
    • Für große CAN XL Payloads umgeht LdCom das Signal-Packing und übergibt serialisierte Datenblöcke direkt als PDU an den PduR.
  4. State- & Mode-Management:
    • CanSM koordiniert die Zustandsübergänge (z. B. Start, Stop, Sleep) synchron über CanIf, welches sowohl den CAN Driver, den Transceiver (CanTrcv) als auch den externen ASIC steuert.

4. Normative Relevanz & Entwickler-Hinweise

  • CAN XL Standardisierung: Die Einführung von CAN XL (gestrichelte Boxen in CAN Driver und CAN Transceiver Driver) erweitert die nutzbare Nutzdatenlänge auf bis zu 2048 Byte und erfordert angepasste Transceiver- und Controller-Treiberarchitekturen.
  • Architektur externer CAN-ASICs: Die Auslagerung von CAN-Kanälen auf externe ASICs wird durch die Kombination aus Driver for ext. CAN ASIC, SPIHandler Driver und DIO Driver nahtlos unterhalb des CanIf abstrahiert. Höhere Schichten (PduR, CanTp, COM) operieren kanalinvariant.
  • Einsatz von Large Data COM (LdCom): Dient insbesondere in Verbindung mit CAN XL zur Vermeidung des Signal-Routing-Overheads und ermöglicht Zero-Copy- bzw. Stream-basierte Kommunikationsmuster in der Classic Platform.
  • Spezifikationsfokus: Die Reduktion des Gesamtschaubilds auf den CAN-Stack in AUTOSAR_CP_SWS_CANTransportLayer dient der präzisen Normierung der CAN-spezifischen Schichten und Schnittstellen, ohne Redundanzen zu anderen Bustechnologien mitzuführen.

Begleitender Spezifikationstext:

Specification of CAN Transport Layer AUTOSAR CP R25-11 1 Introduction and functional overview This specification defines the functionality, API and the configuration of the AUTOSAR Basic Software module CAN Transport Layer (CanTp). CanTp is the module between the PDU Router and the L-SDU Router module (see Figure 1.1). The main purpose of the CAN TP module is to segment and reassemble CAN I-PDUs longer than 8 bytes or longer than 64 bytes in case of CAN FD. The PDU Router deploys AUTOSAR COM and DCM I-PDUs onto different communication protocols. The routing through a network system type (e.g. CAN, LIN and Flex Ray) depends on the I-PDU identifier. The PDU Router also determines if a transport protocol has to be used or not. Lastly, this module carries out gateway functionality, when there is no rate conversion. L-SDU Router Module (LSduR) provides equal mechanisms to access a CAN bus channel regardless of its location (µC internal/external). From the location of CAN controllers (on chip / onboard), it extracts the ECU hardware layout and the number of CAN drivers. Because CanTp only handles transport protocol frames (i.e. SF, FF, CF and FC PDUs), depending on the N-PDU ID, the L-SDU Router module has to forward an I-PDU to CanTp or PduR.
