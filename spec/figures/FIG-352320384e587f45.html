1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: SPEM 2.0 (Software & Systems Process Engineering Metamodel) Arbeitsergebnis-Strukturdiagramm / Deliverable-Kompositionsdiagramm (UML-Profil für SPEM 2.0).
  • Technischer Zweck & Einordnung:
  • Das Diagramm definiert den normativen Aufbau des Arbeitsergebnisses (Deliverable) VFB System innerhalb der AUTOSAR-Methodik (Release R4.0.3, AUTOSAR TR Methodology, Kapitel 3, Aktivität Develop VFB System).
  • Es kapselt die vollständige, hardwareunabhängige funktionale Systemarchitektur auf Ebene des Virtual Function Bus (VFB). Es bündelt sämtliche Software-Komponententypen, Kompositionen, Schnittstellen, Typen, Mapping-Restriktionen und Variantendefinitionen vor deren Bindung an eine konkrete Topologie und ECU-Hardware im späteren System Design.

2. Komponenten, Entitäten & Schnittstellen

#### Zentrales Aggregat (Deliverable)

  • VFB System («SPEM_Deliverable» / Briefumschlag-Icon): Zentrales Container-Artefakt, das alle VFB-relevanten Teilbeschreibungen über Aggregationen («SPEM_Aggregation») zusammenfasst.

#### Aggregierte Entitäten («SPEM_WorkProductUse» / Dokument-Icons)

  • Systemkomposition & Struktur:
  • VFB Top Level System Composition (Kardinalität: 1): Die zwingend erforderliche Wurzelkomposition (RootSwCompositionPrototype), welche die hierarchische Instanziierung aller SWC-Prototypen und deren VFB-Konnektoren auf Gesamtsystemebene abbildet.
  • *Software-Komponentenbeschreibungen (SWC Types, Kardinalität jeweils 0..):**
  • VFB Atomic Software Component: Standard-Applikationssoftwarekomponenten (ApplicationSwComponentType).
  • VFB Sensor Actuator Component: SensorActuatorSwComponentType zur Anbindung peripherer Sensorik/Aktorik.
  • ECU Abstraction Component: EcuAbstractionSwComponentType zur VFB-seitigen Kapselung von Hardware-Abstraktionen.
  • Complex Driver: Kapselung komplexer Gerätetreiber (ComplexDeviceDriverSwComponentType).
  • VFB Parameter Component: ParameterSwComponentType zur Bereitstellung von Kalibrier- und Konfigurationsparametern.
  • VFB Non AUTOSAR Component: Repräsentanz von Nicht-AUTOSAR- bzw. Legacy-Systemen im VFB-Verbund.
  • *Schnittstellen- und Datendefinitionen (Kardinalität jeweils 0..):**
  • VFB Interfaces: Port-Schnittstellen (Sender-Receiver-, Client-Server-, Trigger-, Mode-Switch- und Parameter-Interfaces).
  • VFB Modes: Modusdeklarationsgruppen (ModeDeclarationGroup) für das System- und Komponenten-Zustandsmanagement.
  • VFB Types: AUTOSAR-Datentypen (ApplicationDataType, ImplementationDataType, BaseType).
  • VFB Data Type mapping Set: DataTypeMappingSet zur formalen Zuordnung von Anwendungs- zu Implementierungsdatentypen.
  • Variantenmanagement, Konsistenz & Schutzattribute:
  • System Constant Value Set (Kardinalität: 0..*): Bereitstellung von Systemkonstanten zur Auswertung von Variationspunkten.
  • Predefined Variant (Kardinalität: 0..*): Statische Festlegung von Variantenkombinationen.
  • Evaluated Variant Set (Kardinalität: 0..*): Evaluierte Variantenausprägungen.
  • Postbuild Variant Set (Kardinalität: 0..*): Festlegungen für Post-Build-Varianten.
  • E2E Protection Set (Kardinalität: 0..*): Konfigurationen für End-to-End-Kommunikationsabsicherung.
  • VFB Software Component Mapping Constraints (Kardinalität: 0..*): Restriktionen für das spätere Komponenten-Mapping auf Steuergeräte.
  • Consistency Needs (ohne explizite Kardinalitätsangabe aggregiert): Anforderungen an die datentechnische Konsistenz und zeitliche Synchronisation über VFB-Verbindungen.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Deliverable-Strukturmodell handelt, existiert kein Laufzeit-Kontrollfluss. Der methodische Verwendungsablauf im AUTOSAR-Prozess gestaltet sich wie folgt:

  1. Erzeugung / Synthese: Im Prozessschritt Develop VFB System generieren Autorenwerkzeuge (System-Authoring-Tools) die atomaren SWCs, Typen, Interfaces und Kompositionen.
  2. Assemblierung: Das Deliverable VFB System bündelt diese Fragmente zu einem konsistenten Systemmodell.
  3. Validierungsgate:
  • Prüfung der Wurzeleigenschaft: Exakt eine Instanz von VFB Top Level System Composition muss vorhanden sein.
  • Typ- und Schnittstellen-Integrität: Vollständigkeit der DataTypeMappingSets für alle Ports der Komponenten in der Komposition.
  1. Übergabe an Downstream-Aktivität: Das fertige VFB System dient zusammen mit der System Topologie / System Description als verbindlicher Input für die Aktivität Map Software Components to ECUs (Verteilung der SWCs auf physische Steuergeräte).

4. Normative Relevanz & Entwickler-Hinweise

  • System- & Software-Architekten:
  • Das Vorhandensein von exakt einer VFB Top Level System Composition ist formaler Prüfpunkt jedes AUTOSAR-ARXML-Schemas für Systembeschreibungen. Fehlende oder mehrfache Top-Level-Kompositionen führen zum Abbruch der Systemtool-Kette.
  • Hardware-spezifische SWC-Typen (SensorActuator, EcuAbstraction, ComplexDeviceDriver) werden bereits auf VFB-Ebene als abstrakte Software-Komponenten geführt, bevor sie im System-Mapping an konkrete Mikrocontroller/ECUs gebunden werden.
  • RTE- und Stack-Generierung:
  • Fehlt ein gültiges VFB Data Type mapping Set, schlägt die spätere Generierung der RTE-Typen (Rte_Type.h) fehl, da abstrakte Applikationsdatentypen nicht auf Plattform-Primitiven (Platform_Types.h, Std_Types.h) aufgelöst werden können.
  • Einträge im E2E Protection Set steuern die automatische Codegenerierung für E2E-Library-Aufrufe innerhalb der RTE-Schnittstellen (Rte_Read_, Rte_Write_) bzw. der COM-Signal-Transformation.
  • Varianten- & Build-Management:
  • Die Aufteilung in System Constant Value Set, Predefined Variant und Postbuild Variant Set erzwingt die strikte Trennung von Compile-Time- (Präprozessor #if) und Post-Build- Konfigurationsstrukturen im Quellcode der SWCs und der generierten BSW.
