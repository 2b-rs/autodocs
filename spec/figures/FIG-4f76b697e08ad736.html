1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR M2-Metamodell-Ausschnitt (UML-Klassendiagramm) gemäß AUTOSAR_TPS_SoftwareComponentTemplate (Release R4.1.3).
  • Architektur-Kontext: Formalisierung der semantischen Struktur von Client-Server-Schnittstellen (ClientServerInterface) auf VFB- (Virtual Function Bus) und RTE-Ebene. Definiert den statischen Kontrakt für synchrone und asynchrone Funktionsaufrufe zwischen Software-Components (SWCs) sowie BSW-Services (z. B. NvM, Dem) über RTE-APIs (Rte_Call, Rte_Result).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Spezialisierungen
  • PortInterface (Abstrakte Basisklasse; erbt von ARElement, AtpBlueprint, AtpBlueprintable, AtpType):
    • isService: Boolean: Kennzeichnung standardisierter AUTOSAR-Basis-Software-Dienste.
    • serviceKind: ServiceProviderEnum [0..1]: Typisierung des bereitstellenden BSW-Stacks.
  • ClientServerInterface (Spezialisierung von PortInterface):
    • Wurzelelement des C/S-Kontrakts im ARXML-Paketbaum.
  • ClientServerOperation (Spezialisierung von AtpStructureElement, Identifiable):
    • Repräsentiert eine konkrete Funktion bzw. Methoden-Signatur innerhalb des Interfaces.
  • ArgumentDataPrototype (Spezialisierung von AutosarDataPrototype → DataPrototype):
    • Modelliert die formalen Parameter der Operation.
    • Attribute:
      • direction: ArgumentDirectionEnum: Datenflussrichtung (in, out, inout).
      • serverArgumentImplPolicy: ServerArgumentImplPolicyEnum [0..1]: Steuerung der C-Signaturen-Generierung (useArgumentType, useArrayBaseType, useVoid).
  • AutosarDataType (Realisiert ARElement, AtpType):
    • Konkreter Typbezeichner für Argumente (z. B. ApplicationPrimitiveDataType, ImplementationDataType).
Enumerationen
  • ArgumentDirectionEnum:
    • in: Call-by-Value / Übergabe per Zeiger auf konstante Eingangsdaten.
    • out: Rückgabe über Zeiger / Referenz.
    • inout: Bidirektionaler Wertübergabepuffer über Zeiger / Referenz.
  • ServerArgumentImplPolicyEnum:
    • useArgumentType: Standardmäßige Typabbildung.
    • useArrayBaseType: Array-Argumente werden als Zeiger auf das Basiselement übergeben.
    • useVoid: Argument wird als untypisierter Speicherzeiger (void*) generiert.
Assoziationen, Stereotypen & Kardinalitäten
  • **ClientServerInterface $\blacklozenge\xrightarrow{\text{+operation}}$ ClientServerOperation [1..\*]:**
    • Strenge Komposition ([TPS_SWCT_01118]). Eine Operation kann nicht zwischen verschiedenen Interfaces wiederverwendet werden.
    • Stereotyp «atpVariation»: Variantenbildung möglich; vh.latestBindingTime = blueprintDerivationTime.
  • **ClientServerOperation $\blacklozenge\xrightarrow{\text{+argument}}$ ArgumentDataPrototype [\* {ordered}]:**
    • Komposition mit expliziter Reihenfolgegarantie ({ordered}) zur deterministischen Parameterliste in der C-Signatur ([TPS_SWCT_01106], [RS_SWCT_03141]).
    • Stereotyp «atpVariation»: Argumente sind über Variantenpunkte steuerbar (vh.latestBindingTime = blueprintDerivationTime).
  • ArgumentDataPrototype $\xrightarrow{\text{+type}}$ AutosarDataType [1]:
    • Stereotyp «isOfType», redefiniert atpType. Verbindliche Typisierung jedes Arguments.
  • ArgumentDataPrototype $\xrightarrow{\text{+typeBlueprint}}$ AutosarDataType [0..1]:
    • Stereotyp «atpVariation»: Optionaler Verweis auf Blueprint-Datentypen während der Entwurfsphase.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein strukturelles Metamodell handelt, ist kein Sequenzfluss direkt abgebildet; das Diagramm determiniert jedoch zwingend die Laufzeit-Dynamik der RTE:

[Client SWC]                          [RTE / VFB]                          [Server SWC]
      |                                    |                                     |
      |--- Rte_Call_<p>_<op>(in, &inout) ->|                                     |
      |    (synchron blockierend           |--- Invocation Event --------------->|
      |     oder asynchron aufgesetzt)     |    (Task Dispatch / Direct Call)    |
      |                                    |                                     |
      |                                    |<-- Rückkehr Operation / Return -----|
      |<-- Std_ReturnType -----------------|    (Ergebnisse in out, inout)       |
      |    (RTE_E_OK / RTE_E_TIMEOUT /     |                                     |
      |     Application Errors)            |                                     |
  • Trigger & Synchronisation:
    • Synchrone Operation: Client ruft Rte_Call_<p>_<op> auf und blockiert (WaitPoint) oder läuft im selben Task-Kontext (Direktaufruf bei Intra-ECU ohne OS-Scheduling), bis der Server die Operation beendet hat.
    • Asynchrone Operation: Client setzt Rte_Call_<p>_<op> ab und holt Ergebnisse zeitverzögert über Rte_Result_<p>_<op> ab.
  • Fehlerpfade:
    • Infrastructure Errors (Std_ReturnType): z. B. RTE_E_TIMEOUT, RTE_E_COM_STOPPED.
    • Application Errors (Std_ReturnType): Nutzerdefinierte Fehlercodes, die zusätzlich zu den ArgumentDataPrototype-Parametern aus der Operation zurückgegeben werden.

4. Normative Relevanz & Entwickler-Hinweise

  • C-API-Generierung (RTE Contract):
    • Die Reihenfolge in {ordered} bestimmt die Signatur: 
      Std_ReturnType Rte_Call_<Port>_<Operation>(
    [IN Arguments (Wert oder const Type*)],
    [INOUT Arguments (Type*)],
    [OUT Arguments (Type*)]
);
    • ServerArgumentImplPolicyEnum greift primär bei Service-Ports und komplexen Typen: useArrayBaseType dereferenziert statische C-Arrays auf flache Zeiger (uint8* statt ArrayType*), um C-Compiler-Inkompatibilitäten und Pufferübergaben an BSW-Treiber zu vereinheitlichen.
  • Entkopplung & Lebenszyklus ([TPS_SWCT_01118]):
    • Da ClientServerOperation exklusiv im Besitz des jeweiligen ClientServerInterface ist, dürfen ARXML-Autoren Operationen nicht per Referenz in mehreren Interfaces teilen; Änderungen an einer Operation bedingen eine Neudefinition oder Interface-Vererbung.
  • Variantenbildung (vh.latestBindingTime = blueprintDerivationTime):
    • Schnittstellenoperationen und -argumente dürfen nur bis zur Ableitung der konkreten Typen aus Blueprints variiert werden. Zur RTE-Generierungs- bzw. Compile-Time ist die Signatur unveränderlich fixiert (keine Post-Build-Variation von Argumentlisten).
