1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Methodik-Aktivitätendiagramm (SPEM 2.0-basiert, Software Process Engineering Metamodel) gemäß AUTOSAR_TR_Methodology (Release R4.0.3, Figure 3.70).
  • Funktionale Einordnung: Spezifikation der Contract Phase im Software-Component-Entwicklungsprozess. Zweck ist die Entkopplung der atomaren SWC-Implementierung von der späteren ECU-Integration (Virtual Functional Bus / VFB-Prinzip). Es definiert die Werkzeugkette zur Erzeugung der C-Schnittstellenverträge (Contract Headers) vor der Verfügbarkeit von Systemkonfiguration, Task-Mapping oder RTE-Implementierungscode.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Werkzeuge
  • Software Component Developer (Rolle, Stereotyp «performs»): Führt die Entwurfs- und Generierungsaktivität aus.
  • Component API Generator Tool (Werkzeug, Stereotyp «used tool»): RTE-Generator im Contract-Phase-Modus zur Transformation von ARXML-Beschreibungen in C-Header.
  • Generate Atomic Software Component Contract Header Files: Zentrale Methodik-Aktivität.
Eingangsartefakte («input»)
  • VFB Atomic Software Component [1]: ARXML-Beschreibung der atomaren SWC (Ports, Prototypen, Interface-Referenzen).
  • Software Component Internal Behavior [1]: Spezifikation des internen Verhaltens (Runnable Entities, RTE Events, Inter-Runnable Variables, PIMs, Port-API-Optionen).
  • VFB Types [0..*]: Definitionen von Application Data Types, Implementation Data Types und Base Types.
  • VFB Interfaces [0..*]: Schnittstellendefinitionen (Sender-Receiver, Client-Server, Parameter, Non-Volatile).
  • VFB Modes [0..*]: Modus-Deklarationen und Mode-Switch-Interfaces (ModeDeclarationGroup).
  • VFB Data Type Mapping Set [0..1]: Mapping-Definitionen zur Übersetzung semantischer Application Data Types in compilerfähige Implementation Data Types.
  • Software [0..1]: Übergeordnetes Software-Paket bzw. Software-Definition.
  • VFB AUTOSAR Standard Package [0..1]: Standard-Definitionen (z. B. Plattformtypen Std_Types.h, Error-Codes).
  • Variabilitätsartefakte (Variantenauflösung):
    • Postbuild Variant Set [0..1]: Definition möglicher Post-Build-Varianten.
    • Predefined Variant [0..1]: Auswahl einer konkreten Ausprägung für Build-Time-Variabilität.
    • System Constant Value Set [0..1]: Konkrete Wertebelegung für SwcSystemConstant-Ausdrücke zur Bindung von Variation Points.
Ausgangsartefakte («output»)
  • Application Header File [1]: Komponentenspezifischer Header (Rte_<SWC>.h). Enthält Deklarationen der RTE-APIs (Rte_Read_*, Rte_Write_*, Rte_Call_*), Runnable-Prototypen und Instanzstrukturen (Rte_Instance).
  • Software Component Data Types Header [1]: Typdefinitions-Header (SWC-spezifisch bzw. Rte_Type.h) mit C-typedefs, Aufzählungen und Datenstrukturen.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um einen statischen Werkzeug- und Entwurfsprozess der Build-Chain handelt, beschreibt der Ablauf die Transformationsschritte zur Entwicklungszeit:

[SWCD: VFB Component + Internal Behavior + Types/Interfaces]
                         │
                         ▼
        [Bindung von System Constants / Varianten]
                         │
                         ▼
   [Ausführung: Component API Generator Tool]
      ├── 1. Validierung Port-Signaturen gegen Internal Behavior
      ├── 2. Auflösung DataTypeMapping (AppType -> ImplType)
      ├── 3. Auswertung von Variation Points (Conditional Compiling)
      └── 4. Generierung der Contract Header
                         │
                         ▼
       [Rte_<SWC>.h]  &  [Rte_Type.h / SWC Types]
                         │
                         ▼
[Kompilierung & Unittest der Runnables (ohne BSW/OS-Stack)]
  • Trigger: Initiierung der Header-Generierung durch den SWC-Entwickler nach Fertigstellung oder Änderung der Software Component Description (SWCD).
  • Verarbeitung: Konsistenzprüfung der Port-Signaturen gegen das interne Verhalten; Transformation von M1-Metamodell-Elementen in normative C-Signaturen; Auflösung der Variation Points (0..1-Varianteninputs) zu festen Präprozessor-Strukturen oder festen Funktionsdeklarationen.
  • Abbruch-/Fehlerbedingungen: Fehlende Typ-Mappings für Application Data Types, nicht auflösbare Interface-Referenzen oder unvollständige Signatur-Definitionen führen zum Abbruch des Generatorlaufs.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE Contract Phase vs. Generation Phase (SWS RTE):
    • Die Contract Header enthalten noch keine Implementierungsdetails der RTE (Rte.c existiert nicht).
    • Funktionsprototypen und Makro-Mappings genügen rein dem C-Syntax- und Typ-Vertrag.
  • Isolierte Kompilierbarkeit:
    • Der C-Quellcode der SWC (<SWC>.c) darf ausschließlich gegen den generierten Rte_<SWC>.h und den Datentypen-Header inkludieren.
    • Direkte Inklusionen von BSW-Headern (z. B. Can.h, Os.h) oder generierten System-Headern verletzen die VFB-Konformität und Portabilität.
  • DataTypeMapping-Zwang (AUTOSAR 4.x):
    • Werden in VFB Interfaces rein funktionale ApplicationDataTypes verwendet, ist die Eingabe VFB Data Type mapping obligatorisch, da der C-Compiler konkrete ImplementationDataTypes (z. B. uint8, float32) für die Prototypensignaturen benötigt.
  • Variantenbindung (Compile-Time / Link-Time):
    • Fehlen Predefined Variant oder System Constant Value Set, müssen alle Variation Points über Präprozessordirektiven (#if, #ifdef) im generierten Application Header abgebildet werden, sofern das Generator-Tool dies unterstützt. Andernfalls bindet der Generator eine Default-Konfiguration.
  • Mocking im Unit-Test:
    • Die Contract Header dienen als primäre Basis für Host-basierte Software-in-the-Loop-Tests (SiL) und statische Code-Analysen (MISRA, Polyspace), da RTE-APIs als Stubs bereitgestellt werden können, ohne die Ziel-Hardware oder das finale OS-Task-Mapping zu kennen.
