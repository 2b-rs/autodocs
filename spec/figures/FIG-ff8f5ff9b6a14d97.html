1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / AUTOSAR M2-Metamodell-Ausschnitt aus dem Security Extract Template (AUTOSAR_FO_TPS_SecurityExtractTemplate).
  • Funktionale Einordnung: Metamodellierung der Netzwerkanbindung und Plattform-Instanziierung einer Intrusion Detection System Manager-Instanz (IdsmInstance) auf der AUTOSAR Adaptive Platform. Es schlägt die Brücke zwischen der plattformunabhängigen, logischen Sicherheitskonfiguration (IdsM Security Extract) und dem physischen Deployment auf Ethernet-Endpunkte einer konkreten Adaptive Machine.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Vererbungsstrukturen
  • IdsmInstance (erbt von IdsCommonElement):
    • Repräsentiert die logische IdsM-Instanz im System.
    • Attribute:
      • idsmInstanceId: PositiveInteger [0..1]: Eindeutiger Identifikator der IdsM-Instanz zur Differenzierung im Gesamtfahrzeugnetzwerk.
      • timestampFormat: String [0..1]: Formatdefinition der Zeitstempel für qualifizierte Sicherheitsereignisse (Qualified Security Events – QSEv).
  • IdsmModuleInstantiation:
    • Konkrete Instanziierung des IdsM-Dienstes auf einer Adaptive Platform Machine.
    • Generalisierung: Spezialisiert IdsPlatformInstantiation.
  • IdsPlatformInstantiation (erbt von NonOsModuleInstantiation):
    • Plattformspezifische Basisklasse zur Instanziierung von Nicht-OS-Modulen bzw. Plattform-Diensten der Adaptive Platform.
  • PlatformModuleEndpointConfiguration (erbt von ARElement):
    • Generisches Metamodell-Element zur Definition von Plattform-Modul-Netzwerkendpunkten.
  • PlatformModuleEthernetEndpointConfiguration:
    • Spezialisierung von PlatformModuleEndpointConfiguration für Ethernet-basierte Kommunikation.
    • Attribute:
      • ipv4MulticastIpAddress: Ip4AddressString [0..1]: Optionale IPv4-Multicast-Adresse für netzwerkbasierte IdsM-Kommunikation.
      • ipv6MulticastIpAddress: Ip6AddressString [0..1]: Optionale IPv6-Multicast-Adresse für netzwerkbasierte IdsM-Kommunikation.
Assoziationen, Kardinalitäten & Stereotypen
  • IdsmInstance → IdsmModuleInstantiation:
    • Rollenname: +idsmModuleInstantiation
    • Kardinalität: 0..1
    • Stereotyp: «atpSplitable» – erlaubt das Splitten des Modells über mehrere physische ARXML-Dateien/Packages hinweg (Entkopplung von generischem Security Extract und maschinenspezifischem Deployment Manifest).
  • IdsPlatformInstantiation → PlatformModuleEthernetEndpointConfiguration:
    • Rollenname: +networkInterface
    • Kardinalität: 0..* – ein IdsM kann auf der Adaptive Platform an null, eine oder mehrere Ethernet-Endpunkt-Konfigurationen gebunden werden.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Konfigurations-Metamodell handelt, ist kein Sequenzfluss dargestellt. Aus dem Modell leitet sich folgendes Laufzeitverhalten für den IdsM-Stack ab:

  1. Initialisierung & Interface-Binding:
    • Während des Starts des IdsM-Prozesses via Execution Management wertet der Stack die Manifest-Zuweisung IdsmModuleInstantiation aus.
    • Pro zugewiesenem networkInterface bindet der IdsM Netzwerk-Sockets an die aufgelösten physischen Ethernet-Interfaces und tritt den ggf. konfigurierten Multicast-Gruppen (ipv4MulticastIpAddress bzw. ipv6MulticastIpAddress) bei.
  2. Event-Reporting & Multicast-Propagation:
    • Erkannte oder weitergeleitete Security Events werden gemäß timestampFormat serialisiert und unter Einbettung der idsmInstanceId über die konfigurierten Ethernet-Endpunkte via Unicast oder Multicast an übergeordnete Aggregatoren (z. B. Smart-Logging-Knoten, On-Board SIEM oder Telematik-Gateway) übertragen.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurations- und Generator-Vertrag (TPS_SECXT_01044, TPS_SECXT_01048):
    • Durch «atpSplitable» an +idsmModuleInstantiation müssen Toolchains unterstützen, dass die logische Definition (IdsmInstance) im zentralen Security Extract verbleibt, während die Zuordnung zur konkreten IdsmModuleInstantiation im Machine-Manifest der Zielplattform hinterlegt wird.
  • Multicast-Routing & Socket-Konfiguration:
    • Die Attribute ipv4MulticastIpAddress und ipv6MulticastIpAddress determinieren, ob und welche IGMP-/MLD-Gruppenbeitritte der IdsM-Daemon beim Netzwerk-Stack (Linux/POSIX/QNX) anfordern muss.
    • Systemintegratoren müssen sicherstellen, dass die zugrunde liegenden Ethernet-Switch-Konfigurationen (VLANs, Multicast-Filtering/Snooping) sowie lokale Paketfilter (z. B. iptables/nftables) diesen Multicast-Verkehr nicht verwerfen.
  • Instanz-Eindeutigkeit (RS_SECXT_00002):
    • idsmInstanceId dient im Security Event PDU-Header als eindeutiger Originator-Tag. Entwickler von Backend-Korrelations-Engines und Central-IdsM-Instanzen hängen davon ab, dass diese ID systemweit kollisionsfrei vergeben ist.
  • Kardinalität networkInterface [0..*]:
    • Eine Kardinalität von 0 bedeutet, dass der IdsM auf dieser Adaptive-Instanz rein IPC-basiert (z. B. via ara::com / Shared Memory) arbeitet und keine direkten Ethernet-Frames oder Raw-Multicasts selbst aussendet oder empfängt.
