1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hybrides Architektur- und Mapping-Diagramm. Die obere Hälfte stellt ein physikalisch-elektrisches Blockschaltbild dar; die untere Hälfte ein AUTOSAR-VFB-/Komponentendiagramm in Anlehnung an die UML-2.0-Port-Konnektornotation (Ball-and-Socket).
  • Technischer Zweck: Abbildung der physischen Signal- und Messkette (physikalische Messgröße → Sensor-Hardware → elektrisches Signal → Steuergeräte-Elektronik) auf die AUTOSAR-Schichtenarchitektur. Es demonstriert die funktionale Schnittstellenteilung zwischen hardwarenaher Treiber-/Abstraktionsebene (ECU Abstraction) und sensorspezifischer Transformationslogik (Sensor SW-C).

2. Komponenten, Entitäten & Schnittstellen

Physische Domäne (Oberhalb der Trennlinie)
  • Physikalische Eingangsgröße: velocity (z. B. Geschwindigkeit in m/s oder km/h).
  • Sensor: Diskreter physischer Messwertaufnehmer; wandelt die Eingangsgröße in eine elektrische Messgröße.
  • Elektrisches Zwischensignal: current (z. B. analoges Stromsignal in mA oder pulsstrommoduliert).
  • ECU Electronics: Physische Steuergeräte-Hardware (Shunt, Verstärker, Tiefpassfilter, ADC-Eingangspin).
Software-Domäne (Unterhalb der Trennlinie)
  • ECU Abstraction (ECU Abstraction Layer / Software-Komponente):
    • Kapselt die Microcontroller-Peripherie (MCAL) und die Signalaufbereitung der ECU-Elektronik.
    • P-Port (Provided Port / Ball / IF_1): Bereitstellung des digitalisierten elektrischen Messwerts über die Operation bzw. das Datum get_velocity_current().
  • Sensor SW-C (Spezialisierter Komponententyp SensorActuatorSoftwareComponentType):
    • Entkoppelt sensorspezifische Berechnungen von der Steuergeräte-Hardware.
    • R-Port (Required Port / Socket / IF_2): Konsumiert das elektrische Messsignal get_velocity_current() von der ECU Abstraction.
    • P-Port (Provided Port / Ball / IF_3): Bereitstellung der physikalisch konvertierten Messgröße über get_velocity() an überlagerte Application-SW-Cs (ApplicationSoftwareComponentType).
  • Beziehungen & Konnektoren:
    • VFB-Assembly-Connector verbindet den P-Port IF_1 der ECU Abstraction mit dem R-Port IF_2 der Sensor SW-C zur Übertragung des Signals get_velocity_current().

3. Dynamisches Verhalten & Sequenzablauf

  1. Signalerfassung Hardware: Die physikalische Größe velocity induziert eine proportionale Änderung des elektrischen Stroms current am Eingang der ECU Electronics.
  2. Digitalisierung & BSW-Abstraktion: Die Hardware wandelt den Strom (z. B. über Shunt-Spannungsabfall via ADC-Treiber). Die ECU Abstraction rechnet den ADC-Raw-Value in die standardisierte elektrische Größe (Ampere/Milliampere) um.
  3. Signalabruf / Messwertübergabe (IF_2):
    • Synchroner/Asynchroner Aufruf: Sensor SW-C ruft via RTE get_velocity_current() auf (Client-Server-Pattern: Rte_Call_<p>_<o>()) oder liest das Datum per zyklischem Task (Sender-Receiver-Pattern: Rte_Read_<p>_<d>()).
  4. Physikalische Skalierung & Plausibilisierung:
    • Innerhalb des Runnables der Sensor SW-C erfolgt die sensorabhängige Kennlinienumrechnung (Linearisierung, Temperaturkompensation, Offset-Korrektur) von current → velocity.
    • Plausibilitätsprüfungen (Out-of-Range, Signal-Degradation, Gradientenüberwachung).
  5. Bereitstellung für Applikation (IF_3):
    • Applikations-SW-Cs rufen get_velocity() ab bzw. empfangen den physikalischen Wert zyklisch über den RTE-P-Port IF_3.

4. Normative Relevanz & Entwickler-Hinweise

  • Entkopplungsprinzip (ECU vs. Sensor):
    • Änderung der ECU-Elektronik: Ändert sich das Messprinzip der Platine (z. B. anderer ADC, geänderter Shunt, Umstieg von Strom- auf Frequenzmessung), wird ausschließlich die ECU Abstraction modifiziert. Sensor SW-C und Applikation bleiben unverändert.
    • Änderung des Sensors: Wird ein anderer Sensortyp (z. B. andere Stromkennlinie, anderer Hersteller) verbaut, wird ausschließlich die Sensor SW-C angepasst/reparametriert; die BSW-Treiber und die ECU-Hardwareabstraktion bleiben identisch.
  • Allokations- und Mapping-Restriktion:
    • Die ECU Abstraction ist hardwaregebunden und zwingend auf dem lokalen Steuergerät verortet.
    • Die Sensor SW-C muss aufgrund der direkten Port-Verbindung zu IF_2 der ECU Abstraction auf derselben ECU allokiert werden (Local-to-ECU Constraint). Ein netzwerkweites VFB-Routing über CAN/FlexRay für IF_2 ist normativ unzulässig bzw. architektonisch kontraproduktiv.
  • RTE-API-Vertrag:
    • IF_2 operiert als ClientServerInterface (Operation: get_velocity_current(OUT current)) oder SenderReceiverInterface (Datenelement mit physikalischer Einheit Ampere).
    • IF_3 liefert standardisierte physikalische SI-Einheiten (Datenelement/Rückgabewert mit PhysicalDimension Geschwindigkeit, z. B. m/s).
  • Fehlerbehandlung (DEM/DET):
    • Elektrische Hardware-Fehler (Kurzschluss nach Masse/VCC, Leitungsbruch) werden von der ECU Abstraction direkt an das DEM (Dem_SetEventStatus) gemeldet.
    • Funktions- und Messbereichsfehler (z. B. unplausible Sensordaten trotz intakter Elektrik) obliegen der Diagnose-Überwachung innerhalb der Sensor SW-C.

Software Component Template V4.5.0 R4.1 Rev 3 10.3 Interfaces and APIs Two fundamentally different interfaces are involved when converting from sensors/actuators to software components, see markers "4" and "5" in Figure 10.2. The interface between the Microcontroller Abstraction and the ECU Abstraction is a Standardized Interface (see AUTOSAR Glossary [38]). This interface is not visible on the Virtual Function Bus and therefore the MCAL and ECU Abstraction have to be present on the same ECU. For further description of this interface please refer to the ECU Resource Template documentation. The interface to the SensorActuatorSwComponentTypes is visible on the Virtual Function Bus. In general the SensorActuatorSwComponentType should be on the same ECU as the ECU hardware abstraction. Also the interface between the SensorActuatorSwComponentTypes and the actual AtomicSwComponentTypes representing the application is visible on the VFB.
