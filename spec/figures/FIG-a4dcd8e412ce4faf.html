1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schematisches Topologie- und Deployment-Diagramm (AUTOSAR System Scope / System Design View).
  • Technischer Zweck & Einordnung:
    • Visualisiert den Übergang von der rein funktionalen Abstraktion des Virtual Functional Bus (VFB, [TR_METH_01045]) zur konkreten physischen Realisierung im Gesamtsystem ([TR_METH_01046]).
    • Definiert die Allokation von Software-Komponenten (SwComponentPrototype) auf vernetzte Steuergeräte (EcuInstance) sowie die Aufteilung der VFB-Kommunikationsbeziehungen in lokale (Intra-ECU via RTE) und verteilte (Inter-ECU via RTE, BSW-Com-Stack und physikalischen Bus) Kommunikationspfade.

2. Komponenten, Entitäten & Schnittstellen

  • EcuInstance (ECU 1, ECU 2, ECU 3): Physische Steuergeräte-Knoten der Netzwerk-Topologie (RootSwCompositionPrototype → SystemMapping → SwcToEcuMapping).
  • SwComponentPrototype (SW-C 1 bis SW-C 4):
    • ECU 1: Beherbergt SW-C 1 und SW-C 2 (Co-Location auf demselben Knoten).
    • ECU 2: Beherbergt SW-C 3.
    • ECU 3: Beherbergt SW-C 4.
    • Metamodell-Bezug: Instanziiert aus AtomicSwComponentType (Application-SWC, Sensor-Actuator-SWC etc.).
  • RTE (Runtime Environment): ECU-individuell generierte Abstraktionsschicht. Realisiert Port-Verbindungen (AssemblySwConnector intra-ECU bzw. DelegationSwConnector / Signale inter-ECU) und entkoppelt SW-Cs von der Hardware.
  • BSW (Basic Software): Enthält standardisierte Services, den Kommunikationsstack (Com, PduR, CanIf/LinIf/FrIf/SoAd, Treiber), den OS-/Task-Scheduler sowie optionale Transformer (z. B. SOME/IP-Serialization, E2E, SecOC).
  • Communication Bus (PhysicalChannel / CommunicationCluster): Physisches Übertragungsmedium (z. B. CAN-FD, FlexRay, Automotive Ethernet, LIN), das an die CommunicationController der ECUs gekoppelt ist.
  • Beziehungen & Metamodell-Kardinalitäten:
    • SwcToEcuMapping (1 … * SwComponentPrototype → 1 EcuInstance): N-zu-1-Zuordnung von SW-Cs auf ein Steuergerät.
    • System aggregiert EcuInstance [1 … *], CommunicationCluster [1 … *] und SystemMapping [1].

3. Dynamisches Verhalten & Sequenzablauf

Obgleich es sich um ein statisches Allokationsdiagramm handelt, leiten sich daraus zwei distinkte dynamische Laufzeitpfade ab:

  • Intra-ECU-Kommunikation (SW-C 1 ↔ SW-C 2 auf ECU 1):
    • Ablauf: Funktionsaufruf an RTE-API (Rte_Write / Rte_Read bzw. Rte_Call / Rte_Result).
    • Laufzeit-Pfad: Direkter Speicherzugriff (Global Variable, Buffer) oder OS-Task-Aktivierung / Event-Triggerung durch die RTE. Kein Durchlaufen des BSW-Kommunikationsstacks; minimale Latenz ohne Serialisierungs-Overhead.
  • Inter-ECU-Kommunikation (SW-C 1/2 ↔ SW-C 3 / SW-C 4):
    • Sende-Sequenz: SW-C ruft Rte_Write_<p>_<o>() auf → RTE übergibt an BSW Com via Com_SendSignal() / Com_SendSignalGroup() → PDU Router (PduR_ComTransmit()) leitet I-PDU an Interface-Modul (z. B. CanIf) → MCAL-Treiber (Can_Write()) sendet CAN-Frame über Bus-Hardware.
    • Optionale Transformer: Gemäß [TR_METH_01046] werden Daten vor Übergabe an das Kommunikationsmodul via Data Transformation serialisiert/transformiert (z. B. End-to-End-Prüfsummen E2E, kryptografische Signaturen SecOC).
    • Empfangs-Sequenz: ISR/Polling im MCAL-Treiber → Interface → PduR → Com (Entpacken der Signale, Fristenüberwachung/Deadline Monitoring) → RTE signalisiert Datenverfügbarkeit via Event (DataReceivedEvent) oder Cache-Update → SW-C liest Daten via Rte_Read().

4. Normative Relevanz & Entwickler-Hinweise

  • Applikationsentwickler (SW-C-Ebene):
    • Vollständige Entkopplung: Der Quellcode der SW-C bleibt identisch, unabhängig davon, ob die Ziel-SW-C auf derselben ECU oder einer Remote-ECU allokiert ist (VFB-Transparenz).
    • API-Vertrag: C-Signaturen (Rte_Read, Rte_Write) hängen ausschließlich von den Port-Interfaces ab, nicht von der Bus-Technologie.
  • System-Integrator & BSW-/RTE-Entwickler:
    • Artefakt-Abhängigkeit: Das SwcToEcuMapping in der SystemDescription.arxml ist die primäre Eingangsgröße für den ECU-Extract (EcuExtract.arxml) jedes einzelnen Steuergeräts.
    • RTE-Generierung: Das Mapping entscheidet, ob der RTE-Generator internen Glue-Code (Shared RAM / Ringbuffer) generiert oder die Signale an Com_SendSignal / Com_ReceiveSignal routet.
    • Kommunikationsmatrix & Bus-Last: Für jede Inter-ECU-Beziehung müssen Signal-to-PDU-Mappings, PDU-Triggerungsmodi (PERIODIC, TRIGGERED), Zykluszeiten und Bus-Identifier (CanId, FlexRay-Slots) definiert werden.
    • Laufzeit- & Safety-Implikationen: Bei Verschiebung einer SW-C auf eine andere ECU (z. B. SW-C 2 von ECU 1 nach ECU 2) wandelt sich eine synchrone, deterministische Intra-ECU-Verbindung in eine asynchrone, netzwerkbehaftete Inter-ECU-Kommunikation. Dies erfordert Anpassungen an Timeout-Konfigurationen, E2E-Protection-Wrappern und Task-Scheduling-Fristen.
