3. Dynamisches Verhalten & Sequenzablauf

  • Provider-Serialisierung:
  • Vor dem Senden (Send(), Update eines Fields oder Method-Return) entscheidet die Applikation, ob optionale Member gesetzt sind (.emplace() bzw. Wertzuweisung) oder leer bleiben (ara::com::nullopt).
  • Die Serialisierungsschicht serialisiert gesetzte optionale Member über das Tag-Length-Value (TLV)-Prinzip (wire_type, tlvDataId, Länge, Wert).
  • Nicht gesetzte Member werden im Datenstrom vollständig ausgelassen; Pflichtfelder (voltage, temperature) werden positionsbasiert (ohne Tag-Overhead) übertragen, sofern die Struktur keine vollständige TLV-Vorschrift erzwingt.
  • Consumer-Deserialisierung:
  • Die empfangende Middleware instanziiert BatteryState. Fehlt ein Tag im Datenstrom, wird das entsprechende Feld als unbesetzt markiert.
  • Runtime-Check: Die Consumer-Applikation muss vor Feldzugriffen zwingend das Vorhandensein prüfen:

```cpp

if (batteryState.current.has_value()) {

processCurrent(*batteryState.current);

}

```

  • Ein ungültiger Zugriff (z. B. Dereferenzierung bei leerem optional) terminiert applikatorisch oder wirft je nach Stack-Implementierung eine Exception (ara::core::bad_optional_access).

4. Normative Relevanz & Entwickler-Hinweise

  • Schnittstellen-Evolution: Ermöglicht Vorwärts- und Rückwärtskompatibilität (Forward/Backward Compatibility). Neuere Service-Versionen können optionale Record-Elemente ergänzen, ohne dass ältere Consumer neu kompiliert oder angepasst werden müssen (unbekannte TLV-Tags werden serverseitig/clientseitig übersprungen).
  • Konfigurationspflicht im Metamodell: Jedem optionalen Element muss im ARXML-Deployment ein deterministischer Bezeichner (tlvDataId) zugewiesen sein.
  • Laufzeit- & Speicher-Overhead:
  • TLV-Encoding erzeugt Protokoll-Overhead (Tag + Length Header pro optionalem Feld) auf dem Bus.
  • ara::com::optional<T> allokiert Speicherplatz für den Wert plus ein boolesches Gültigkeits-Flag (has_value), unterliegt Compiler-Alignment/Padding und verbraucht im C++-Stack mehr RAM als der Rohdatentyp T.
  • API-Vertrag: Der Zustand „nicht vorhanden“ (!has_value()) darf von Applikations-Entwicklern niemals semantisch mit einem Default-Wert (z. B. 0 oder 0.0V) gleichgesetzt werden; er repräsentiert explizit das Fehlen des Datums.
