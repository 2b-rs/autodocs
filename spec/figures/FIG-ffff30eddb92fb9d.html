1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturelles Kontrollfluss- und Schichteninteraktionsdiagramm (Blockschaltbild) für das AUTOSAR Classic Platform (CP) Mode Management.
  • Funktionaler Kontext: Darstellung des bidirektionalen Steuer- und Rückmeldeflusses zwischen Anwendungssoftware-Komponenten (SWCs), der RTE, dem BSW Mode Manager (BswM) und dem Kommunikations-Subsystem für SOME/IP Service Discovery (Sd) über den Socket Adaptor (SoAd).
  • Technischer Zweck: Entkopplung der anwendungsseitigen Service-Bedarfsanforderungen (Client/Server Service Requests) von der tatsächlichen Netzwerkaktivierung via SOME/IP-SD durch zentrale BswM-Arbitrierung sowie die propagierte Rückmeldung des aktuellen Service-Verfügbarkeitsstatus über RTE-Moden an konsumierende SWCs.

2. Komponenten, Entitäten & Schnittstellen

  • Akteure & BSW-Module:
    • Swc1, Swc2: Application Software Components, fungieren als Service-Konsumenten/-Provider bzw. Modus-Anforderer und -Beobachter.
    • RTE: Laufzeitumgebung; vermittelt API-Aufrufe (Rte_ModeSend / Mode Switch Interfaces / Mode Notification) und entkoppelt BSW von der Applikationsebene. Enthält das Mode Declaration Group Management (symbolisiert durch das Zustandswechselsymbol).
    • BswM (Basic Software Mode Manager): Zentrale Steuerinstanz mit internen Regelsätzen:
      • Mode Request Port: BswM-Eingangsschnittstelle für SWC-Requests via RTE (z. B. BswM_RequestMode).
      • Arbitration (highest wins): Prioritätsbasierte Arbitrierungslogik (Regel-/Expressionsauswertung) zur Konsolidierung konkurrierender SWC-Anforderungen auf denselben Dienst.
      • Actionlist: Konfigurierte Sequenz von BswM-Aktionen bei erfüllter Regel (Auslöser für BSW-APIs).
      • Event Request Source: BswM-Indikationsquelle für asynchrone Ereignisse aus BSW-Modulen (hier: Statusänderungen aus Sd).
      • Arbitration (1:1): Direkte 1-zu-1-Abbildung/Evaluierung des SD-Zustands auf einen korrespondierenden Modus.
    • Service Discovery (Sd): BSW-Modul des Ethernet-Stacks zur dynamischen Dienstsuche/Bereitstellung (SOME/IP-SD Messages).
    • Socket Adaptor (SoAd): Unterlagerte Transportschicht zur PDU-/Socket-Abstraktion (TCP/UDP-Verbindungen).
  • Beziehungen & Kardinalitäten:
    • Swc1, Swc2 → BswM (N:1): Mehrere SWCs fordern über separate Mode Request Ports denselben Service an; BswM bündelt diese via Prioritätsarbitrierung (highest wins).
    • BswM → Sd (1:1): Actionlist steuert den Zustand einer SD-Instanz (Client Service State / Server Service State) via BSW-API.
    • Sd → SoAd (1:N / 1:1): SD nutzt Socket Connections / PDUs zur Übertragung von Find/Offer/Subscribe-Nachrichten.
    • Sd → BswM (1:1): Rückmeldung über Statuswechsel via Event Request Source (Callback/Indication).
    • BswM → RTE → Swc1, Swc2 (1:N Broadcast): BswM triggert Moduswechsel via Rte_Switch; RTE benachrichtigt alle registrierten SWCs über Mode Switch Ports.

3. Dynamisches Verhalten & Sequenzablauf

Pfad A: Service-Anforderung (Top-Down, Request-Pfad)
  1. Trigger: Swc1 und/oder Swc2 fordern die Freigabe/Nutzung eines Netzwerkdienstes an (z. B. Aufruf von Rte_Call / Rte_Switch / Mode Request Service).
  2. Eingang: Signal erreicht BswM über dedizierte Mode Request Ports (BswM_RequestMode).
  3. Arbitrierung: BswM führt Regelauswertung gemäß Konfiguration durch (Arbitration (highest wins)). Die Anforderung mit der höchsten Priorität determiniert das Regelergebnis.
  4. Aktionsausführung: Bei Zustandswechsel führt die BswM-Regel die verknüpfte Actionlist aus.
  5. BSW-Kommando: Die Actionlist ruft die Steuer-API des Service-Discovery-Treibers auf (z. B. Sd_ClientServiceSetState(..., SD_CLIENT_SERVICE_REQUESTED)).
  6. Netzwerkübertragung: Sd triggert über SoAd das Versenden der entsprechenden SOME/IP-SD-Nachrichten (z. B. FindService oder SubscribeEventgroup).
Pfad B: Statusrückmeldung & Verfügbarkeit (Bottom-Up, Event-Pfad)
  1. Trigger: Sd empfängt über SoAd eine SOME/IP-SD-Antwort (z. B. OfferService, SubscribeAck) oder registriert ein Timeout/Link-Down.
  2. Indikation: Sd meldet den neuen Zustand asynchron an den BswM (Aufruf von BswM_Sd_ClientServiceCurrentState bzw. BswM_Sd_ServerServiceCurrentState).
  3. Event-Verarbeitung: Das Ereignis geht in die BswM Event Request Source ein.
  4. Arbitrierung: BswM evaluiert die Regel über Arbitration (1:1) (direkte Transformation des BSW-Zustands in einen Anwendungsmodus).
  5. Mode Switch: BswM ruft die RTE-API Rte_Switch_<p>_<modeGroup>(RTE_MODE_<Group>_<STATE>) auf.
  6. SWC-Notifikation: Die RTE schaltet den Modus der Mode Declaration Group um und informiert abhängige Runnables in Swc1 und Swc2 (Triggerung via ModeSwitchEvent On-Entry/On-Exit oder Polling via Rte_Mode).

4. Normative Relevanz & Entwickler-Hinweise

  • BswM-Konfiguration (BswMGeneral, BswMRules):
    • Definition präziser BswMModeRequestPort-Instanzen für die SWC-Interaktion.
    • Konfiguration von BswMRule mit logischen Ausdrücken (highest wins) für Mehrfachnutzer desselben SD-Clientservices, um Race Conditions und vorzeitiges De-Allokieren zu verhindern.
    • Zuordnung der BswM-Aktion BswMSdClientServiceSetState / BswMSdServerServiceSetState zur BswMActionList.
  • API-Verträge & RTE-Schnittstellen:
    • SWCs dürfen Sd niemals direkt aufrufen; die Kommunikation ist strikt über RTE Mode Request / Mode Switch Ports bzw. Standard Interfaces gekapselt.
    • Status-Rückmeldungen erfordern ein konfiguriertes ModeDeclarationGroupPrototype in der Software-Architektur (z. B. Moden SERVICE_AVAILABLE, SERVICE_DOWN).
  • Einschränkungen & Fehlerszenarien:
    • Asynchrones Verhalten: Ein erfolgreicher Request (Pfad A) bedeutet keine sofortige Service-Verfügbarkeit. Applikationslogik muss zwingend auf die Mode-Switch-Rückmeldung warten (Pfad B), bevor Payload-Kommunikation über SOME/IP gestartet wird.
    • Timeout & Link-Loss: Schlägt das SD-Handshake im Netzwerk fehl, bleibt die Rückmeldung auf BswM/RTE-Ebene im Fehler-/Down-Zustand. Applikationsentwickler müssen entsprechende Fallback-Zustände bei SERVICE_DOWN implementieren.
