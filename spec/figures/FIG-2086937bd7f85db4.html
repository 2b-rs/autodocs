1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm).
  • Technischer Zweck: Spezifikation des Lebenszyklus und Steuerungsflusses von Kanal-Benachrichtigungen (Notification Mechanism) im AUTOSAR Classic MCAL ICU-Treiber (Icu).
  • Architektur-Einordnung:
    • System Services / BSW Mode Management: EcuM (ECU State Manager) übernimmt die zentrale statische Initialisierungsphase der BSW.
    • MCAL (Microcontroller Abstraction Layer): ICU Driver kapselt Timer-/Input-Capture-Hardware-Module des Mikrocontrollers.
    • Upper Layer / BSW / Application: ICU User (z. B. IoHwAb, Sensor-Treiber, CDD oder PWM/Wiegand-Signalverarbeitung) konsumiert Flankenevents über konfigurierte Callbacks.

2. Komponenten, Entitäten & Schnittstellen

  • Akteure / Lifelines:
    • EcuM (System Service): Ruft BSW-Initialisierungsroutinen während der Start-up-Phase auf.
    • ICU User (Treiber-Nutzer): Übergeordnete Software-Entität, die Benachrichtigungen dynamisch aktiviert/deaktiviert und Event-Callbacks empfängt.
    • ICU Driver (MCAL-Modul): Verwaltet Kanalzustände, Capture-Register und Interrupt Service Routinen (ISRs).
  • Konfigurations-Parameter (Post-Build / Pre-Compile):
    • Channel #1: Eindeutiger Kanalbezeichner (IcuChannelId).
    • IcuWakeupCapable = TRUE: Kanal ist für Wake-up-Ereignisse ausgelegt.
    • IcuDefaultStartEdge = ICU_BOTH_EDGES: Detektion sowohl steigender als auch fallender Flanken aktiv.
    • IcuSignalNotification: Konfigurierter Funktionszeiger auf Icu_SignalNotification_Channel1().
  • APIs & Signaturen:
    • Icu_Init(const Icu_ConfigType* ConfigPtr): Synchroner Treiber-Initialisierungsaufruf.
    • Icu_EnableNotification(Icu_ChannelType Channel): Synchroner Aufruf zur Freigabe von Callback-Meldungen für den spezifizierten Kanal.
    • Icu_DisableNotification(Icu_ChannelType Channel): Synchroner Aufruf zum Sperren von Callback-Meldungen für den spezifizierten Kanal.
    • Icu_SignalNotification_Channel1(void): Asynchroner Benachrichtigungs-Callback vom Treiber an den Nutzer (i. d. R. im ISR-Kontext ausgeführt).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierungsphase (Init):
    • EcuM setzt den Aufruf Icu_Init(ConfigPtr) ab.
    • Der ICU Driver initialisiert die Hardware-Register (Kanal 1: beide Flanken aktiv, Wakeup-Fähigkeit scharf).
    • Normativer Zustand nach Init: Alle Benachrichtigungen (Notifications) sind treiberweit per Default deaktiviert. Der Aufruf kehrt synchron via return() zu EcuM zurück.
  2. Aktivierung der Benachrichtigung:
    • ICU User ruft Icu_EnableNotification(Channel #1) auf.
    • Der Treiber schaltet softwareseitig das Weiterleiten von Flanken-Events an den User frei (Rückkehr synchron).
  3. Flankentriggerung & Callback-Ausführung:
    • Hardware-Event 1 (Falling Edge): Physische fallende Flanke an Pin Channel #1 löst Interrupt aus. ICU Driver führt den Callback Icu_SignalNotification_Channel1() synchron im ISR-Kontext aus.
    • Hardware-Event 2 (Rising Edge): Physische steigende Flanke an Pin Channel #1 löst Interrupt aus. ICU Driver führt erneut Icu_SignalNotification_Channel1() aus.
  4. Deaktivierung der Benachrichtigung:
    • ICU User ruft Icu_DisableNotification(Channel #1) auf.
    • Der Treiber sperrt alle weiteren Notification-Aufrufe dieses Kanals.
  5. Unterdrückung weiterer Benachrichtigungen:
    • Nachfolgende Flankenwechsel an Channel #1 führen zu keiner Ausführung von Icu_SignalNotification_Channel1().

4. Normative Relevanz & Entwickler-Hinweise

  • Default-Zustand nach Icu_Init:
    • Flanken-Notifications sind nach dem Icu_Init-Aufruf prinzipbedingt deaktiviert (DISABLED). Ein expliziter Aufruf von Icu_EnableNotification() ist zwingend erforderlich, bevor Callbacks empfangen werden können.
  • Semantische Trennung (Signal Measurement vs. Notification):
    • Icu_DisableNotification() stoppt nur die Ausführung des Benachrichtigungs-Callbacks (IcuSignalNotification).
    • Laufende Messmodi (z. B. ICU_MODE_SIGNAL_MEASUREMENT, ICU_MODE_EDGE_COUNTER) oder Timestamp-Pufferung laufen im Hintergrund weiter, sofern sie nicht über Icu_StopSignalMeasurement() / Icu_DisableEdgeCount() gestoppt werden.
    • Wake-up-Events (Icu_EnableWakeup()) werden durch Icu_DisableNotification() nicht beeinflusst.
  • Kontext & Reentrancy:
    • Icu_EnableNotification und Icu_DisableNotification sind reentrant für unterschiedliche Kanäle, jedoch nicht reentrant für denselben Kanal.
    • Die Callback-Funktion Icu_SignalNotification_<Channel>() läuft im ISR-Kontext (CAT2 ISR) des Microcontrollers: Sie muss strikt nicht-blockierend gehalten werden (kein Polling, keine langlaufenden Schleifen, minimale Ausführungszeit).
  • Konfigurationsanforderung (IcuNotificationSupported):
    • Das Feature erfordert IcuNotificationSupported = TRUE im Pre-Compile-Parameterbaum (IcuGeneral), andernfalls stehen die APIs Icu_EnableNotification / Icu_DisableNotification im Quellcode nicht zur Verfügung.
