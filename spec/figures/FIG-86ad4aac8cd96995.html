1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Speicherabbildungs- und Adressierungsdiagramm (Memory Location & Resolution Mapping) der AUTOSAR Runtime Environment (RTE).
  • Technischer Zweck: Spezifikation der kombinierten zweistufigen Adressauflösung beim Zugriff auf Kalibrier- und Konfigurationsparameter (Calibration Data / Parameters) unter simultanem Einfluss von Mehrfachinstanziierung (Multi-Instance Software Components, supportsMultipleInstantiation = true) und Post-Build-Variabilität (Post-Build Selectable/Loadable Variation, Kriterium Z0/Z1).
  • Funktionale Einordnung: Veranschaulicht, wie die generierten RTE-Zugriffs-APIs (Rte_Cdata_*, Rte_Prm_*) zur Laufzeit die konkreten Speicherorte im ROM/Flash oder RAM auflösen – gesteuert durch das Software-Komponenten-Instanzhandle (Rte_Instance) sowie den aktiven Post-Build-Variantenindex.

2. Komponenten, Entitäten & Schnittstellen

  • **Speicherbereiche (Memory Locations):**
    • SWC_A_PIP_Z0 & SWC_A_PIP_Z1: Variantenspezifische Speicherbereiche für den internen Instanzparameter (Per-Instance Parameter, PIP) des Komponenten-Prototyps SWC_A unter den Post-Build-Varianten Z0 und Z1.
    • SWC_B_PIP: Invarianter instanzspezifischer Speicherort für Prototyp SWC_B (ohne Post-Build-Varianz).
    • SWC_A_SWC_B_SP_Z0 & SWC_A_SWC_B_SP_Z1: Komponenten-übergreifend geteilte Speicherbereiche (Shared Parameter, SP) für SWC_A und SWC_B, selektiert anhand der Post-Build-Variante (Z0 bzw. Z1).
    • SWC_PA_EP_Prm1_Z0 & SWC_PA_EP_Prm1_Z1: Variantenspezifische Speicherorte für den Port-basierten Parameter Prm1 (Port EP) des Prototyps SWC_PA unter Varianten Z0 und Z1.
    • SWC_PB_EP_Prm1: Invarianter Speicherort für den Port-basierten Parameter Prm1 des Prototyps SWC_PB.
  • RTE-Zugriffs-APIs (C-Schnittstellen / Makros):
    • Rte_Cdata_PIP(Rte_Instance): API für instanzspezifische Kalibrierdaten (CData).
    • Rte_Cdata_SP(Rte_Instance): API für gemeinsam genutzte Kalibrierdaten (Shared CData).
    • Rte_Prm_EP_Prm1(Rte_Instance): API für Port-basierte Parameter (ParameterInterface EP, Datenelement Prm1).
  • Entscheidungsknoten / Selektionsmechanismen:
    • Depends on instance handle: Auflösung anhand des übergebenen Instanzdeskriptors (Rte_Instance).
    • Depends on post build variant: Auflösung anhand der aktiven Post-Build-Konfiguration (z. B. via Post-Build-Kriterium Z mit Ausprägungen Z0 und Z1).

3. Dynamisches Verhalten & Sequenzablauf

  • Auflösung von Rte_Cdata_PIP(Rte_Instance):
    • Die RTE wertet zunächst das Instanzhandle aus (Depends on instance handle).
    • Für Instanz SWC_B erfolgt die Dereferenzierung direkt auf den invarianten Speicherort SWC_B_PIP.
    • Für Instanz SWC_A erfolgt eine nachgelagerte Variantenprüfung (Depends on post build variant): Je nach aktivem Post-Build-Kriterium wird auf SWC_A_PIP_Z0 oder SWC_A_PIP_Z1 zugegriffen.
  • Auflösung von Rte_Cdata_SP(Rte_Instance):
    • Die API verlangt zwar formell das Instanzhandle Rte_Instance, das Ziel ist jedoch typweit geteilt (keine Verzweigung nach Instanzhandle).
    • Die RTE verzweigt ausschließlich nach der aktiven Post-Build-Variante (Depends on post build variant) und adressiert entweder SWC_A_SWC_B_SP_Z0 oder SWC_A_SWC_B_SP_Z1.
  • Auflösung von Rte_Prm_EP_Prm1(Rte_Instance):
    • Erste Stufe wertet das Instanzhandle aus (Depends on instance handle).
    • Prototyp SWC_PB führt direkt zu SWC_PB_EP_Prm1.
    • Prototyp SWC_PA verzweigt variantenabhängig (Depends on post build variant) auf SWC_PA_EP_Prm1_Z0 bzw. SWC_PA_EP_Prm1_Z1.
  • Laufzeitcharakteristik: Synchrone Leseoperationen (typischerweise direkte Zeiger-Indirektion über Konfigurationsdeskriptoren der RTE). Vollkommen reentrant und blockierungsfrei.

4. Normative Relevanz & Entwickler-Hinweise

  • Kombinierte Indirektion (Multi-Instanziierung + Post-Build):
    • Bei Komponenten mit supportsMultipleInstantiation = true und Post-Build-Variabilität generiert die RTE Pointer-Tabellen oder zweistufige Deskriptoren. Der RTE-Code navigiert zuerst über den Rte_Instance-Zeiger zum instanzspezifischen Kontext und indexiert anschließend anhand der Post-Build-Konfigurationsstruktur (z. B. Root-Pointer des Post-Build-Konfigurationssatzes).
  • Asymmetrische Variabilität:
    • Das Diagramm zeigt normativ, dass Post-Build-Variabilität asymmetrisch modelliert werden kann: Während Prototyp A (SWC_A bzw. SWC_PA) variantenabhängig ist (_Z0/_Z1), bleibt Prototyp B (SWC_B bzw. SWC_PB) varianteninvariant und belegt nur einen einzigen Speicherort.
  • Speicher-Allokation & Linker-Platzierung:
    • Variantenspezifische Kalibrierdaten (_Z0, _Z1) werden in separaten Flash-/ROM-Blöcken oder über Post-Build-Loadable-Segmente platziert. Das Basissoftware-Modul EcuM bzw. BswM wählt beim Systemstart den aktiven Konfigurationssatz.
  • A2L- und Tool-Integration (ASAM MCD-2 MC):
    • Kalibriertools müssen sowohl Instanz-Offsets als auch Varianten-Kriterien (PostBuildVariantCriterion) auflösen können. Bei variablen Parametern verweisen symbolische Beschreibungen auf variantenspezifische Adressen oder indirekte Adressierungsmodi.
