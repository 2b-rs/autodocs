1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Strukturelles Datenstruktur- und Serialisierungs-Layout (PDU-/Datenelement-Puffer-Komposition).
  • Architektur-Kontext:
    • Verortet im AUTOSAR Classic Platform Dokument Explanation of Functional Safety Measures (AUTOSAR_CP_EXP_FunctionalSafetyMeasures) im Themenfeld der End-to-End (E2E) Communication Protection (ISO 26262, ASIL A–D).
    • Beschreibt das Aggregationsprinzip eines sicherheitsrelevanten Datenelements auf Ebene der Runtime Environment (RTE), wenn der E2E-Schutz oberhalb der Transportschichten (COM/PduR) auf VFB-/RTE-Ebene gekapselt wird (SW-C-E2E-Wrapper oder E2E-Transformer).
  • Funktionaler Zweck: Darstellung der Hüllung (Envelope Pattern), bei der ein ungeschütztes Anwendungsdatum (App data element) mit sicherheitsgerichteten Metadaten (E2E Header) zu einem einheitlichen Datenelement für den RTE-Transport (Data element for RTE) zusammengeführt wird.

2. Komponenten, Entitäten & Schnittstellen

  • App data element (VariableDataPrototype):
    • Originäre Anwendungsnutzlast (Payload) einer Software-Component (SW-C), deklariert innerhalb eines SenderReceiverInterface.
    • Repräsentiert die reinen Prozess-/Steuerungsdaten (z. B. Sensorwerte, Stellgrößen) ohne sicherheitstechnische Steuerungsfelder.
  • E2E Header:
    • Sicherheits-Header gemäß gewähltem AUTOSAR E2E-Profil (z. B. Profile 1, 2, 4, 5, 7, 8, 11, 22).
    • Wird der Payload vorangestellt, angehängt (Trailer) oder an einer fest definierten Offset-Position innerhalb des Puffers abgelegt.
  • Control Fields (CF1, CF2, ..., CF(x)):
    • Spezifische Steuerfelder des E2E-Headers zur Absicherung gegen Kommunikationsfehler nach ISO 26262-6 (Annex D):
      • Counter / Sequence Counter (CF_Counter): Zykluszähler zur Erkennung von Nachrichtenverlust, Wiederholung, Einfügung und fehlerhafter Reihenfolge.
      • CRC (Cyclic Redundancy Check) (CF_CRC): Prüfsumme (z. B. CRC-8, CRC-16, CRC-32, CRC-64) zur Erkennung von Datenkorruption und Bitfehlern.
      • Data ID / Message ID (CF_DataID): Identifikator zur Erkennung von Adressierungsfehlern, Fehlinjektion und Masquerading (je nach Profil explizit im Header übertragen oder implizit in die CRC eingerechnet).
      • Length (CF_Length): Dynamische Längenangabe bei variabler Nutzdatenlänge.
  • Data element for RTE:
    • Aggregierter Gesamtdatentyp (typischerweise modelliert als AUTOSAR ApplicationRecordDataType / ImplementationDataType oder serialisierter Byte-Array-Puffer uint8[]).
    • Bildet den formalen API-Vertrag an den Ports (ProvidedOuterPort, RequiredOuterPort) der beteiligten SW-Cs.
  • Kardinalitäten & Relationen:
    • Komposition: $1 \times \text{App data element} + 1 \times \text{E2E Header} \rightarrow 1 \times \text{Data element for RTE}$.
    • Der E2E-Header besteht aus n Kontrollfeldern CF_1 … CF_x (x ≥ 2, minimal Counter + CRC).

3. Dynamisches Verhalten & Sequenzablauf

[SW-C (Sender)]
      │  App Data
      ▼
[E2E Library / Transformer] ── E2E_PxxProtect() ──► Berechnet CF_Counter, CF_CRC (inkl. DataID)
      │
      ▼
[Puffer-Assemblierung] ── App data element + E2E Header ──► "Data element for RTE"
      │
      ▼
[RTE Communication API] ── Rte_Write_<p>_<o>() / Rte_Send_<p>_<o>()
      │
      ▼ (VFB Intra-ECU via Shared Memory / Inter-ECU via COM -> PduR -> CAN/LIN/FlexRay/Ethernet)
      │
[RTE Communication API] ── Rte_Read_<p>_<o>() / Rte_Receive_<p>_<o>()
      │
      ▼
[SW-C (Receiver) / Transformer] ── E2E_PxxCheck() ──► Validiert CRC, Counter, DataID
      │
      ├── [Status == OK / VALID] ──► Extrahiere App data element & verarbeite Payload
      └── [Status != OK]         ──► Fehlerreaktion (Safe State, Default-Werte, Dem/Det Event)
  1. Sende-Sequenz (Protection Path):
    • SW-C berechnet die Anwendungsdaten.
    • Aufruf von E2E_PxxProtect() (gemäß SWS_E2E_00221): Inkrementierung des Zählers, Serialisierung der Daten und Berechnung der Prüfsumme über Nutzdaten sowie statische/dynamische Kontrollfelder.
    • Generierung des zusammengesetzten Data element for RTE und Übergabe an die RTE via Rte_Write_<p>_<o>().
  2. Empfangs-Sequenz (Validation Path):
    • Empfänger liest Data element for RTE via Rte_Read_<p>_<o>().
    • Aufruf von E2E_PxxCheck(): Prüfung des Zählers auf Sequenzfehler und Neuberechnung der CRC.
    • Auswertung der E2E-Zustandsmaschine (E2E_PxxCheckStatusType / State Machine gemäß ISO 26262).
    • Bei Fehlern (CRC-Mismatch, Sequence Error, Timeout): Verwerfen der Daten, Aktivierung deterministischer Ersatzwerte und Meldung an Sicherheitsüberwachung/DEM.

4. Normative Relevanz & Entwickler-Hinweise

  • Normativer Bezug (SWS_E2E_00221):
    • Legt fest, wie E2E-Profile auf Datenelemente angewendet werden, wenn die Übertragung auf RTE-Ebene erfolgt. Das resultierende Datenelement muss das Anwendungsdatum und die Kontrollfelder vollständig kapseln.
  • Architektur-Varianten in der Umsetzung:
    • E2E Wrapper (SW-C-Ebene, klassischer Ansatz): Die Applikation definiert explizit einen Record-Datentyp in ARXML (AppPayload + E2EHeader). Die SW-C ruft E2E_PxxProtect() / E2E_PxxCheck() manuell auf. Nachteil: SW-C verliert Plattformunabhängigkeit („E2E-aware“).
    • E2E Transformer (RTE-Ebene ab AUTOSAR 4.2.1+): Die SW-C bleibt rein nutzdatenbezogen (App data element). Ein konfigurierter E2E_Transformer im Datentransformations-Pfad (DataTransformationSet) serialisiert die Nutzdaten und fügt den E2E-Header automatisch beim Aufruf der RTE-APIs (Rte_Write / Rte_Read) hinzu.
  • Konfigurations- & Alignment-Fallen für Embedded-Entwickler:
    • Padding & Byte-Alignment: Compiler-spezifisches Struct-Packing (z. B. #pragma pack) oder 32-/64-Bit-Alignment-Gaps zwischen App data element und E2E Header führen zu Bit-Offsets, die bei der E2E-CRC-Berechnung im Empfänger zu persistenten E2E_E_CRC-Fehlern führen. Der gesamte Puffer muss strikt typisiert und paddingfrei serialisiert sein.
    • Endianness: Beim Übertragen von Control Fields (CFx) über Busgrenzen hinweg ist auf die im E2E-Profil definierte Bytereihenfolge (meist Little-Endian / LOW_BYTE_FIRST oder profilabhängiges Network Byte Order) zu achten.
