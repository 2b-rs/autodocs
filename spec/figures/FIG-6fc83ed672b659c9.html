1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-2.0-Metamodell-Klassendiagramm (M2-Metamodellausschnitt aus der AUTOSAR-Spezifikation Software Component Template, Release R3.2.3).
  • Technischer Zweck & Einordnung: Definition der statischen Struktur für den expliziten Datenzugriff (DataReadAccess, DataWriteAccess) von Ausführungseinheiten (RunnableEntity) auf Datenelemente (DataElementPrototype) innerhalb des internen Verhaltens (InternalBehavior) einer atomaren Software-Komponente (AtomicSoftwareComponentType). Es bildet das Bindeglied zwischen Implementierungsebene und Virtual Function Bus (VFB) für die Generierung der RTE-Kommunikations-APIs.

2. Komponenten, Entitäten & Schnittstellen

  • Klassen & Stereotypen:
    • AtomicSoftwareComponentType (Spezialisierung von ComponentType): Nicht weiter dekomponierbare Basis-Software-Komponente.
    • InternalBehavior (Spezialisierung von ARElement): Spezifiziert das Ausführungsverhalten der Komponente.
      • Attribut: + supportsMultipleInstantiation :Boolean (steuert Mehrfachinstanziierbarkeit derselben SWC).
    • RunnableEntity (Spezialisierung von ExecutableEntity): Kleinste atomare, durch RTE-Events triggerbare Ausführungseinheit.
      • Attribute:
        • + canBeInvokedConcurrently :Boolean (Reentranz-Flag für parallele Task-Ausführung).
        • + minimumStartInterval :Float (Mindestzeitabstand zwischen aufeinanderfolgenden Aktivierungen).
        • + symbol :CIdentifier (C-Bezeichner des Einsprungspunkts/Entry-Point-Funktion).
    • DataReadAccess (Spezialisierung von Identifiable): Modelliert den expliziten Lesezugriff einer Runnable auf ein Datenelement.
    • DataWriteAccess (Spezialisierung von Identifiable): Modelliert den expliziten Schreibzugriff einer Runnable auf ein Datenelement.
    • DataElementPrototype (Spezialisierung von DataPrototype, Stereotyp «atpPrototype»): Einzelnes, typisiertes Datenelement innerhalb eines Sender-Receiver-Interfaces.
  • Beziehungen & Kardinalitäten:
    • InternalBehavior → AtomicSoftwareComponentType: Gerichtete Assoziation (+component 1 zu *). Genau ein Komponenten-Typ referenziert sein Verhalten.
    • InternalBehavior ◆\!⟶ RunnableEntity: Starke Komposition (+behavior zu +runnable 1..*). Ein InternalBehavior muss mindestens eine RunnableEntity besitzen.
    • RunnableEntity ◆\!⟶ DataReadAccess: Starke Komposition (+runnable zu +dataReadAccess *). Eine Runnable besitzt 0 bis n Lesezugriffe.
    • RunnableEntity ◆\!⟶ DataWriteAccess: Starke Komposition (+runnable zu +dataWriteAccess *). Eine Runnable besitzt 0 bis n Schreibzugriffe.
    • DataReadAccess / DataWriteAccess ⇢ DataElementPrototype: Stereotypierte Assoziation «instanceRef» (0..* zu +dataElement 1). Realisiert eine kontextuelle Instanzreferenz auf das Datenelement über den jeweiligen Port der Komponente.

3. Dynamisches Verhalten & Sequenzablauf

  • Metamodell-Transformation (Generierungszeit):
    • Für jeden deklarierten DataReadAccess generiert der RTE-Generator das explizite Lese-API: Rte_Read_<port>_<dataElement>().
    • Für jeden deklarierten DataWriteAccess generiert der RTE-Generator das explizite Schreib-API: Rte_Write_<port>_<dataElement>().
  • Laufzeit-Ablauf:
    1. Die RTE aktiviert die C-Funktion der RunnableEntity gemäß dem in symbol hinterlegten CIdentifier.
    2. Innerhalb der Funktion werden die generierten APIs zur Interaktion mit den Datenelementen aufgerufen.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Bindung: Das Attribut symbol muss dem Typ CIdentifier entsprechen, wodurch der Funktionsname den syntaktischen C-Sprachkonventionen genügen muss.
  • Mehrfachinstanziierung: supportsMultipleInstantiation steuert, ob die RTE Instanzzeiger (Rte_Instance) an die generierten Funktionen übergeben muss.
