3. Dynamisches Verhalten & Sequenzablauf

Das Metamodell definiert die statische Struktur für folgende BSW-Laufzeitabläufe im SecOC-Subsystem:

```

[PduR] [SecOC] [CSM / FVM] [If-Layer (CanIf/EthIf)]

| | | |

|--- Tx: Payload ----->| | |

| |-- Get Freshness ----->| |

| |<-- Complete Value ----| |

| |-- Calc MAC (dataId) ->| |

| |<-- Full MAC ----------| |

| |-- Truncate & Assemble | |

| |-- Transmit SecuredIPdu --------------------------->|

| | | |

| |<-- Rx: SecuredIPdu --------------------------------|

| |-- Reconstruct FV ---->| |

| |<-- Full FV -----------| |

| |-- Verify MAC -------->| |

| |<-- Result (OK/NOK) ---| |

|<- Rx: Payload (OK) --| | |

| (Drop if NOK) |-- Report Error (DEM/DET) |

```

  1. Sendepfad (Tx):
  • PduR übergibt die ungesicherte Payload-PDU an SecOC.
  • SecOC fragt anhand freshnessValueId den vollständigen Frischewert (freshnessValueLength) beim FVM ab.
  • Übergabe von Payload, dataId und vollständigem Frischewert an das CSM zur MAC-Berechnung unter Nutzung des Schlüssels (keyId).
  • Bitweises Abschneiden: MAC auf authInfoTxLength und Frischewert auf freshnessValueTxLength.
  • Serialisierung der SecuredIPdu (Payload + Tx-Freshness + Truncated MAC) und Weiterleitung an das unterlagerte Transport-Interface (PduTriggering).
  1. Empfangspfad (Rx):
  • Das Bus-Interface signalisiert den Empfang der SecuredIPdu.
  • Falls rxSecurityVerification == TRUE: Rekonstruktion des vollen Frischewerts anhand des empfangenen Teilwerts (freshnessValueTxLength) und des lokalen FVM-Zustands bzw. Zeitstempelfensters (timestampRxAcceptanceWindow).
  • Übergabe an das CSM zur Verifikation gegen den empfangenen Truncated MAC (authInfoTxLength).
  • Positivfall: Weiterleitung der entschachtelten Payload an PduR / COM.
  • Negativfall: PDU wird verworfen; Fehlermeldung via DEM/DET; ggf. Neu-Synchronisation gemäss freshnessCounterSyncAttempts und authenticationRetries.

4. Normative Relevanz & Entwickler-Hinweise

  • ECU-Extrakt & BSW-Konfiguration (SecOC / PduR / CSM):
  • Die Entität SecuredIPdu steuert im BSW-Generator die Erstellung der Container SecOCSamePduConfig, SecOCTxPduProcessing bzw. SecOCRxPduProcessing.
  • authInfoTxLength und freshnessValueTxLength sind Bit-Längen. Für Treiber- und Hardwareabstraktions-Entwickler gilt: Ergibt die Summe aus Payload, Authentifizierungs- und Frische-Bits keine ganzzahlige Byte-Grenze, fordert SecOC ein definiertes Bit-Packing bzw. Zero-Padding bis zur nächsten Byte-Grenze.
  • PDU-Größenlimits der Transportschicht:
  • Die Gesamtlänge (SecuredIPdu.length) muss auf die maximale MTU des Trägerbusses abgestimmt sein (z. B. klassisches CAN: max. 8 Bytes; bei CAN FD: bis 64 Bytes). Reicht der Platz nicht, ist TP-Segmentierung (CanTp) oder Kürzung (authInfoTxLength / Weglassen von freshnessValueTxLength) erforderlich.
  • Entkopplung über PduTriggering:
  • Im Metamodell R4.2.2 referenziert SecuredIPdu die Nutzlast nicht direkt via Pdu, sondern über PduTriggering (+payload [1]). Entwickler von Generatoren und Validierungswerkzeugen müssen sicherstellen, dass das referenzierte PduTriggering aufgelöst und konsistent zum Routing des Signal-Subsystems konfiguriert ist.
  • Kryptografische Rollentrennung:
  • IPduPort.keyId korreliert mit den Csm-Job- und Key-IDs. Über KeyUsageRestrictionEnum wird bereits auf Architekturebene vorgegeben, ob eine ECU hardwarebeschleunigte private/symmetrische Keys zum Generieren oder ausschließlich zum Verifizieren (z. B. reine Diagnose- oder Gateway-Monitore) vorhalten muss.
