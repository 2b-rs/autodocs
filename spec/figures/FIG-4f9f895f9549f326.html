1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schichtenbasiertes Allokations- und Speicherlayout-Diagramm (Memory Allocation / Deployment View).
  • Technischer Zweck & Einordnung: Spezifikation des Allokationsmodells für NvM Use Case 1a gemäß AUTOSAR CP NVDataHandling (R23-11 bis R25-11). Dargestellt ist die Entkopplung von Applikations-RAM (SWC RAM Data) und NVRAM-Manager (NvM) bei Verzicht auf fest konfigurierte permanente RAM-Spiegelblöcke (NvMRamBlockDataAddress == NULL).

2. Komponenten, Entitäten & Schnittstellen

  • Akteure & Schichten:
  • SWC (Software Component Layer): Applikationsinstanzen (z. B. SWC1, SWC2), welche die Eigentümer des Nutzdaten-Arbeitsspeichers (SWC RAM Data) sind.
  • RTE (Runtime Environment): Vermittlungsschicht für Client/Server-Aufrufe. Beherbergt statische Konstantenstrukturen (ROM Block Data) im Flash/ROM.
  • NvMBlockConfiguration (NvM Service Layer): Deskriptorstrukturen der NVRAM-Blöcke innerhalb des BSW-Moduls NvM:
  • RAM Block (Block Not Present / gepunktetes Rechteck): Kein statischer RAM-Block im NvM alloziert (NvMRamBlockDataAddress nicht konfiguriert).
  • ROM Block (Optional Block / gestricheltes Rechteck): Verweist per Konfigurationszeiger (NvMRomBlockDataAddress) auf die ROM Block Data in der RTE/Konstanten-Sektion.
  • NV Block (Memory Block / durchgezogenes Rechteck): Logische Blockrepräsentation im NvM, verweist auf die Treiberinstanz.
  • Flash / EEPROM (Memory Abstraction & Driver Layer): Physischer Speicherort, repräsentiert als FLS Block (Zugriff via MemIf $\rightarrow$ Fee/Ea $\rightarrow$ Fls/Eep).
  • Schnittstellen & Relationen:
  • Client/Server-Kopplung (SWC $\leftrightarrow$ NvM via RTE): Der Datenzeiger auf SWC RAM Data wird als Übergabeparameter (DstPtr bei Read, SrcPtr bei Write) in den C/S-Operationen übergeben.
  • Kardinalität: 1:1-Zuordnung je Block-Konfiguration zwischen logischem NV Block und physischem FLS Block; 1:0..1-Zuordnung zwischen ROM Block und ROM Block Data.

3. Dynamisches Verhalten & Sequenzablauf

  • Trigger & synchroner Einstieg:
  1. Die SW-C initiiert die Operation über das Port-Interface NvM_Service via Rte_Call_<port>_ReadBlock(DstPtr) bzw. WriteBlock(SrcPtr).
  2. Der NvM führt synchrone Vorprüfungen aus (DET: Validierung von BlockId, Null-Pointer-Prüfung, Modul-Initialisierungszustand).
  3. Der Job wird mit dem übergebenen Pointer in die NvM-Warteschlange eingereiht; Rückgabe von E_OK (bzw. E_NOT_OK) an die SW-C.
  • Asynchrone Verarbeitung (NvM_MainFunction):
  • Read-Pfad: Der NvM liest Daten über MemIf aus dem FLS Block. Nach erfolgreicher CRC-Verifikation werden die Nutzdaten direkt in die Adresse von SWC RAM Data transferiert.
  • Write-Pfad: Die Nutzdaten werden direkt aus SWC RAM Data gelesen, mit Header/CRC versehen und via MemIf asynchron in den persistenten Speicher geschrieben.
  • Default-Wiederherstellung (Fallback): Schlägt das Lesen des NV-Blocks fehl (z. B. CRC-Fehler, Hardwarefehler), kopiert der NvM die Daten aus ROM Block Data (falls konfiguriert) in das SWC RAM Data.
  • Terminierung & Benachrichtigung:
  • Status wechselt von NVM_REQ_PENDING auf NVM_REQ_OK bzw. NVM_REQ_NOT_OK/NVM_REQ_INTEGRITY_FAILED.
  • Benachrichtigung der SW-C asynchron über Callback (NvM_SingleBlockCallbackNotification) oder synchron via Polling über NvM_GetErrorStatus().

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (NvM.epc):
  • NvMRamBlockDataAddress darf nicht konfiguriert werden (Wert NULL).
  • NvMBlockUseSyncMechanism muss auf FALSE verbleiben, da kein Spiegelpuffer für synchrone Kopier-Callbacks (NvM_ReadRamBlockFromNvM / NvM_WriteRamBlockToNvM) vorhanden ist.
  • NvMRomBlockDataAddress ist optional parametrierbar für automatischen ROM-Restore.
  • API-Vertrag & Puffer-Integrität (Crucial Rule für Applikationsentwickler):
  • Lebensdauer: Der übergebene Zeiger (SWC RAM Data) muss bis zum endgültigen Abschluss des Jobs (NVM_REQ_PENDING wird verlassen) im Speicher gültig bleiben (keine Stack-Variablen lokaler Funktionen verwenden; Allokation im globalen/statischen RAM zwingend).
  • Datenkonsistenz / Concurrency: Der NvM implementiert in Use Case 1a keine interne Pufferung. Schreibzugriffe der SW-C auf SWC RAM Data während eines laufenden NvM_WriteBlock-Jobs führen zu inkonsistenten/korrupten NV-Daten oder CRC-Fehlern. Lesezugriffe während NvM_ReadBlock lesen unvollständige Zwischenzustände.
  • Speicherschutz (OS-Applications / MPU / ASIL-D):
  • Liegen SW-C und NvM in getrennten OS-Applikationen bzw. Speicherschutzdomänen (unterschiedliche ASIL-Einstufungen), muss sichergestellt sein, dass der NvM (BSW) Lese-/Schreibberechtigung auf die Speicherregion von SWC RAM Data besitzt, um Memory-Protection-Traps (MPU Violations) zu verhindern.
