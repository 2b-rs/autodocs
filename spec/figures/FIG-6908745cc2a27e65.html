1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Informelles Architektur- und Strukturdiagramm (Konzeptskizze zur BSW-Interaktion).
  • Architektur-Kontext: Modussteuerung innerhalb der AUTOSAR Classic Platform (System Services Layer).
  • Funktionaler Zweck: Veranschaulichung des BswM-Ausführungsmodells (Mode Control). Nach erfolgter Regelauswertung (Mode Arbitration) stößt der BswM vorkonfigurierte Aktionslisten (Action Lists) an. Diese triggern synchrone Funktionsaufrufe über Direktaufrufe in darunterliegende BSW-Module oder propagieren Moduswechsel über die RTE/SchM an Application-SW-Cs und andere BSW-Module.

2. Komponenten, Entitäten & Schnittstellen

  • Zentrale Entität:
    • BswM (Basic Software Mode Manager): Kapselt logische Regeln (BswMRule) und zugeordnete Aktionslisten (BswMActionList). Dargestellt sind zwei voneinander unabhängige oder kaskadierbare Aktionslisten.
  • Interne Datenstrukturen / Konfigurationselemente:
    • BswMActionList: Sequenzielle Liste von Einträgen (BswMActionListItem).
    • Action #1 .. #n (BswMAction): Konkrete Instanzen vordefinierter BswM-Aktionstypen (oder Referenzen auf Sub-Aktionslisten bzw. Regeln).
  • Ziel-Komponenten & Schnittstellen (APIs):
    • RTE (bzw. SchM): Schnittstelle zur Applikationsschicht und BSW. Typischerweise Aufruf von Rte_Switch_<p>_<m>() bzw. SchM_Switch_<bswm>_<mode>() zur Modus-Signalisierung.
    • EcuM (ECU State Manager): Steuerung von Shutdown-, Sleep- und Reset-Zuständen (z. B. EcuM_SelectShutdownTarget(), EcuM_GoDown()).
    • COM (AUTOSAR COM): I-PDU-Gruppenverwaltung (z. B. Com_IpduGroupControl(), Com_IpduGroupStart(), Com_IpduGroupStop()).
    • ComM (Communication Manager): Anforderung von Kommunikationsmodi (z. B. ComM_RequestComMode()).
    • <Bus>SM (Bus State Manager wie CanSM, LinSM, FrSM): Direkte Bus-Zustandswechsel (z. B. <Bus>SM_RequestComMode()).
    • PduR (PDU Router): Aktivierung/Deaktivierung des Routings einzelner Routing-Pfade (z. B. PduR_EnableRouting(), PduR_DisableRouting()).
  • Kardinalitäten & Beziehungen:
    • BswM 1 → n BswMActionList
    • BswMActionList 1 → n BswMActionListItem (Indexierung bestimmt Ausführungsreihenfolge: Action #1, #2, etc.)
    • Eine Aktion referenziert genau ein Modul-API-Target oder bildet eine Kaskadierung (action / reference / rule).

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger: Eine Aktionsliste wird entweder ereignisgesteuert (Immediate Mode Processing direkt im Kontext eines Mode-Request-Callbacks) oder zyklisch (Deferred Mode Processing im Kontext der BswM_MainFunction()) aktiviert, sobald die zugehörige BswMRule den Zustand BSWM_TRUE oder BSWM_FALSE annimmt.
  2. Sequenzielle Ausführung:
    • Action List 1: Führt synchron Action #1 (RTE Switch) → Action #2 (EcuM API) → Action #3 (COM API) → Action #4 (ComM API) aus.
    • Action List 2: Führt synchron Action #1 (ComM API) → Action #2 (<Bus>SM API) → Action #3 (PduR API) aus.
  3. Ausführungsmodi (BswMActionListExecution):
    • TRIGGERED: Ausführung erfolgt exakt einmal beim Zustandswechsel des Regel-Ergebnisses.
    • CONDITIONAL: Ausführung erfolgt bei jeder Evaluierung, solange die Bedingung erfüllt bleibt.
  4. Synchronizität: Aktionen innerhalb einer Liste sind strikt blockierende, synchrone Aufrufe (Blocking Call Tree). Rückgabewerte (z. B. Std_ReturnType) werden intern verarbeitet; Fehler melden typischerweise Det/Dem-Ereignisse, unterbrechen jedoch nicht zwingend die nachfolgenden Aktionen der Liste, sofern nicht über Kaskadierung anders modelliert.

4. Normative Relevanz & Entwickler-Hinweise

  • Laufzeit & Task-Kontext (Stack-Verbrauch):
    • Werden Aktionslisten im Immediate-Kontext ausgeführt (z. B. im ISR- oder Callback-Kontext eines Treibers), muss die Kette aller synchron aufgerufenen APIs (Rte_Switch, Com_IpduGroupControl, etc.) bezüglich Ausführungszeit (WCET) und Stack-Tiefe strikt begrenzt sein.
    • Komplexe Listen mit vielen Inter-Modul-Aufrufen müssen als DEFERRED konfiguriert werden, um im deterministischen Task-Kontext von BswM_MainFunction() zu laufen.
  • Konfigurationsverträge (ARXML / BswM-Parametrierung):
    • Die Reihenfolge (bswmActionListIndex) ist strikt bindend. Abhängigkeiten (z. B. PDU-Gruppen über COM starten erst, nachdem die Kommunikationsfreigabe im ComM erfolgt ist) müssen zwingend über den Listenindex abgesichert werden.
    • Zirkuläre Referenzen bei kaskadierten Aktionslisten (reference) sind verboten und werden durch Konfigurationsvalidatoren als fataler Fehler abgewiesen.
  • RTE/SchM-Kopplung:
    • Aktionen, die auf die RTE zielen, lösen asynchrone oder synchrone Mode Switches aus (Rte_Switch). Die Reaktionszeit von SW-Cs auf diese Moduswechsel unterliegt der Task-Schedule-Latenz und erfolgt nicht zwingend im selben Ausführungsschritt wie die direkten BSW-Aufrufe (ComM, PduR).

Specification of Basic Software Mode Manager AUTOSAR CP R25-11 Figure 7.2: Example showing two action lists As shown in Figure 7.2, the BswM may contain multiple Action Lists, and a single Action List can hold multiple actions. To reduce the overall number of action lists, it shall be possible to cascade them. An element of an action list can either be a concrete action or a reference to another action list, or as stated above, a rule to be executed by the mode arbitration. The BswM evaluates its rules either as a result of a received mode arbitration request, or cyclically during the execution of the BswM main function. 3.
