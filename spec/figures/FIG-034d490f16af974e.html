1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Anwendungsfalldiagramm (Use Case Diagram) mit funktionalen Systemgrenzen (Diagnostic Execution, Fault Reaction) und annotierten Constraints/Notizen.
  • Technischer Zweck: Spezifikation des Orchestrierungs- und Integrationskonzepts für Hardwarediagnosen (Pre-OS und Startup-Tests) innerhalb der AUTOSAR-Classic-Architektur über den BSW-Dienst Hardware Test Manager (HTM / HTMSS, Document ID 804).
  • Architektonische Einordnung: Bindeglied zwischen hardwarenaher Ausführung (BIST, µC Safety Library, MCAL) und übergeordneter Safety-Logik (Safety SW-C). Es definiert das Vertrauensmodell (Trust Awareness) bezüglich der MCU-Ressourcen vor und nach dem Start des AUTOSAR OS.

2. Komponenten, Entitäten & Schnittstellen

Akteure (Actors)
  • µC Hardware BIST: Hardware-integrierter Built-In Self-Test der MCU (z. B. LBIST für Logik, MBIST für SRAMs).
  • µC Safety Library (non AUTOSAR) or MSTP: Halbleiterhersteller-spezifische Testbibliothek (Microcontroller Software/Self-Test Package, z. B. Core-Tests, Peripherie-Selbsttests).
  • MCAL Driver & Complex Device Driver: Basissoftware-Treiber mit dedizierten Diagnose-Schnittstellen (außerhalb der Standard-Init-Funktionen).
  • Custom Integrator Code: Kundenspezifischer Startup-/Integrationscode (Bootcode vor oder während der BSW-Initialisierungssequenz).
  • HTM (Hardware Test Manager): System Service Modul im BSW-Service-Layer zur Testorchestrierung und Ergebnisaggregation.
  • Safety SW-C: Sicherheitsrelevante Software-Komponente oberhalb der RTE zur Festlegung deterministischer Systemreaktionen.
Anwendungsfälle (Use Cases) & Beziehungen
  • Execution of Diagnostics: Wird von Custom Integrator Code über die Beziehung «invokes» aufgerufen; interagiert direkt mit µC Safety Library / MSTP, MCAL Driver und Complex Device Driver.
  • Critical Fault Detected: Ausgelöst durch µC Hardware BIST oder Custom Integrator Code. Führt via Abhängigkeit «invokes» direkt zu Fail-Safe State (Non-Operational State).
  • Test Result Collection: Zentraler Sammelpunkt; aggregiert Testergebnisse aus µC Hardware BIST und Custom Integrator Code zur Übergabe an den HTM.
  • Representation of MCU State w.r.t diagnostics: Abstrahiertes Zustandsmodell des HTM; stellt den Diagnose-/Integritätsstatus der MCU für die Safety SW-C bereit.
  • Functional Degradation / Limp Home & Fail-Safe State (Non-Operational State): Reaktionspfade der Safety SW-C bei erkannten Fehlern.

3. Dynamisches Verhalten & Sequenzablauf

[Power-On / Reset]
       │
       ▼
[Pre-AUTOSAR Boot: Custom Integrator Code]
  ├─ Trigger: µC Hardware BIST / Safety Lib / MCAL Diag
  ├─ Fehlerfall (Kritisch): ──► Impliziter Reset / Execution Halt ──► [Fail-Safe State]
  └─ Gutfall / Non-Critical:
       │
       ▼
[AUTOSAR Start: EcuM / BSW Init / OS Start]
       │
       ▼
[HTM Initialisierung]
  └─ Test Result Collection (Ergebnisübernahme aus Pre-OS-Puffer/BIST-Registern)
       │
       ▼
[RTE Start]
  └─ HTM stellt Status via RTE bereit ──► [Safety SW-C]
                                              ├─ Non-Critical: ──► [Degradation / Limp Home]
                                              └─ Fatal/Critical: ──► [Fail-Safe State]
  1. Pre-OS / Pre-AUTOSAR Phase:
    • Vor Ausführung der MCAL_Init()-Routinen führt der Custom Integrator Code synchrone Basistests aus (µC Hardware BIST, µC Safety Library).
    • Kritischer Abbruch: Tritt ein unüberwindbarer Hardwaredefekt auf, greift das Implicit Fault Reporting: Der Controller verharrt im Reset oder hält die Befehlsausführung an. AUTOSAR wird nicht gestartet; das System befindet sich unmittelbar im Fail-Safe State.
  2. BSW-Initialisierungsphase:
    • Werden keine fatalen Fehler erkannt, startet die BSW-Init-Kaskade.
    • Der HTM wird im System Service Layer initialisiert und holt die Diagnosedaten (Test Result Collection) aus Hardwareregistern oder flüchtigen Übergabespeichern des Integratorcodes ab.
  3. Post-OS / RTE-Laufzeit:
    • Nach dem Start des AUTOSAR OS steht die Service-Port-Schnittstelle des HTM an der RTE zur Verfügung.
    • Die Safety SW-C liest den aggregierten Hardware-Zustand (Representation of MCU State w.r.t diagnostics) zyklisch oder ereignisorientiert aus und steuert das System:
      • Limp Home: Bei tolerierbaren Teilausfällen werden degraded Betriebsmodi aktiviert.
      • Fail-Safe: Bei funktional nicht kompensierbaren Fehlern wird ein kontrollierter Übergang in den sicheren Zustand erzwungen.

4. Normative Relevanz & Entwickler-Hinweise

  • MCAL-Initialisierungsvertrag (Integrator-Constraint): Diagnosetests dürfen nicht innerhalb der standardisierten Driver_Init()-Funktionen der MCAL ausgeführt werden. Zeitintensive oder destruktive Tests (z. B. RAM-Pattern-Tests, Register-Mirror-Checks) müssen zwingend vor dem MCAL-Init über herstellerspezifische MCAL-Diagnose-Interfaces oder Safety-Libraries ausgeführt werden.
  • Ergebnis-Persistierung über Reset-Grenzen: Da der HTM erst nach dem OS verfügbar ist, muss der Custom Integrator Code Diagnoseergebnisse aus der Pre-OS-Phase in reset-festen, nicht-initialisierten RAM-Sektionen (z. B. .noinit) oder dedizierten Hardware-Statusregistern puffern.
  • RTE-Verfügbarkeit & Schichtenentkopplung: Direkte Zugriffe von SW-Cs auf den HTM vor Abschluss des RTE-Starts sind architektonisch unzulässig. Der HTM fungiert als AUTOSAR-Standard-System-Service; die Anbindung an die Application-Layer-Safety-SW-C erfolgt ausschließlich über standardisierte Client/Server- oder Sender/Receiver-Ports via RTE.
  • ISO 26262 Asymmetrie: Das Konzept trennt harte Hardwarefehler (Fail-Silent vor Boot) von applikativ behandelbaren Fehlern (Graceful Degradation / Limp-Home nach Boot), um die Sicherheitsziele (ASIL) ohne Deadlocks bei Systemstart zu erreichen.

Begleitender Spezifikationstext:

4 Motivation The motivation of HTMSS concept is to support awareness of the system that given functionality is trusted. E.g. resources are available, under operational conditions and no faults were detected. Even if certain faults are detected, still the system may be capable to perform certain activities with trust of their results. The determinism of how the system shall react on these faults has to be implemented based on system analysis and recommendations. The HTMSS concept shall provide support to achieve this awareness. Collecting results from a number of tests can provide facts on conditions and aspects of the resources in the system. The concept shall meet the following requirements: • It shall be possible to run tests before Autosar. • It shall be possible to run tests at Autosar start up and shutdown, and to propagate their results. • Test results shall be propagated for later analysis 5 Use Case Diagnostic of potential faults, in the context of a safety critical system, is essential for functional safety goal achievement. It requires integration of tests, their execution and results propagation in parallel to the intended functionality. This implies the necessity to introduce a new component in system service layer, a basic software module called Hardware Test Manager (HTMSS). It implements the tests and monitoring orchestration, and propagates results to stakeholder software components - Figure 2.
