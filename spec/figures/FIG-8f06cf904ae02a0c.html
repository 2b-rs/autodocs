1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB-Komponentendiagramm (Architektursicht auf Ebene des Virtual Function Bus).
  • Technischer Zweck & Einordnung: Definition des fundamentalen Architekturmusters für das AUTOSAR Mode Management. Das Diagramm etabliert eine strikte funktionale Entkopplung zwischen der Anforderung eines Betriebsmodus, der zentralen Entscheidungsinstanz (Arbitrierung/Zustandsübergang) und den letztendlichen Nutzern bzw. Ausführungseinheiten, deren Scheduling oder Verhalten vom aktiven Modus abhängt.

2. Komponenten, Entitäten & Schnittstellen

Dargestellt sind drei Software-Komponenten-Rollen (AtomicSwcPrototype bzw. BSW-Modul-Abstraktionen) und deren Port-Verbindungen:

  1. Mode Requester:
  • Rolle: Entität, die einen Zustandswechsel anfordert (z. B. Application-SWC, Diagnostic-SWC, Sensor/Actuator-SWC).
  • Ports für Mode Request:
  • Client-Port: RPortPrototype (Socket-Symbol) für RPC-basierte synchrone/asynchrone Anforderung.
  • Sender-Port: PPortPrototype (Pfeil nach außen) für daten-/signalbasierte Anforderung.
  1. Mode Manager:
  • Rolle: Zentrale Kontroll- und Arbitrierungsinstanz (typischerweise BswM – Basic Software Mode Manager, oder anwendungsbezogene Mode-Manager-SWC).
  • Ports für Mode Request:
  • Server-Port: PPortPrototype (Ball/Lollipop-Symbol) zur Bereitstellung der Client-Server-Schnittstelle.
  • Receiver-Port: RPortPrototype (Pfeil nach innen) zum Empfang der Sender-Receiver-Anforderung.
  • Port für Mode Switch:
  • Mode-Providing Port: PPortPrototype mit Mode-Switch-Symbol (gefülltes Dreieck) zur Signalisierung des Moduswechsels.
  1. Mode User (Mode Consumer):
  • Rolle: Entität, deren Verhalten (Aktivierung, Deaktivierung, Task-Trigger) vom aktuellen System- oder Partitionsmodus abhängt.
  • Port für Mode Switch:
  • Mode-Requiring Port: RPortPrototype mit Mode-Switch-Symbol (gefülltes Dreieck) zum Empfang der Modenänderung.

Schnittstellentypen (PortInterface):

  • ClientServerInterface (Mode Request): Definiert Operationen (ClientServerOperation) zur Modenanforderung mit synchroner Rückmeldung (Std_ReturnType).
  • SenderReceiverInterface (Mode Request): Definiert Datenelemente (VariableDataPrototype) zur kontinuierlichen oder ereignisbasierten Übertragung von Modenwünschen.
  • ModeSwitchInterface (Mode Switch): Deklariert eine ModeDeclarationGroup (Gruppe möglicher Modi wie RUN, POST_RUN, SHUTDOWN).

3. Dynamisches Verhalten & Sequenzablauf

  1. Mode Request (Anforderung):
  • Der Mode Requester initiiert den Wunsch nach einem Modenwechsel via RTE:
  • Pfad A (Client-Server): Aufruf von Rte_Call_<port>_<operation>().
  • Pfad B (Sender-Receiver): Aufruf von Rte_Write_<port>_<data>().
  1. Arbitrierung & Transition (Mode Manager):
  • Der Mode Manager evaluiert eingehende Requests gegen Regeln, Vorbedingungen (z. B. Busruhe, Spannungslevel, Fehlerspeicherzustände via Dem) und Prioritäten.
  • Bei positivem Evaluierungsergebnis leitet er den Übergang über die RTE ein: Aufruf von Rte_Switch_<port>_<mdgroup>(<TargetMode>).
  1. Mode Switch (Benachrichtigung & RTE-Dispatching):
  • Die RTE übernimmt die Zustandsmaschine der ModeDeclarationGroup.
  • Moden-abhängige RunnableEntity-Instanzen im Mode User werden über RTE-Events gesteuert:
  • SwcModeSwitchEvent auf ON_EXIT (beim Verlassen des alten Modus).
  • SwcModeSwitchEvent auf ON_TRANSITION (während des Wechsels).
  • SwcModeSwitchEvent auf ON_ENTRY (beim Eintritt in den neuen Modus).
  • Alternativ fragt der Mode User den Zustand synchron über Rte_Mode_<port>_<mdgroup>() ab.

4. Normative Relevanz & Entwickler-Hinweise

  • Strikte Trennung von Request und Switch: Applikationskomponenten dürfen niemals als Mode Manager direkt einen Modus schalten, sofern sie nicht explizit als Master-Mode-Manager konzipiert sind. Sie sind rein als Mode Requester zu modellieren.
  • RTE-API-Vertrag:
  • Rte_Switch liefert RTE_E_OK oder RTE_E_LIMIT. Wenn bereits ein Modusübergang auf derselben Modengruppe aktiv ist, blockiert der Aufruf oder liefert einen Fehler (abhängig von modeSwitchAckTimeout und synchroner/asynchroner Konfiguration).
  • Entwickler müssen modeErrorBehavior konfigurieren, um das Verhalten bei ungültigen Modusübergängen oder Timeouts deterministisch abzusichern.
  • Runnable-Scheduling-Einschränkungen:
  • Runnables, die durch ON_EXIT getriggert werden, müssen vollständig terminieren, bevor die RTE ON_ENTRY-Runnables des Zielmodus startet, um Race Conditions bei geteilten Hardware-/Speicher-Ressourcen zu verhindern.
  • BSW-Zuordnung: In der AUTOSAR Classic BSW übernimmt der BswM typischerweise die Rolle des Mode Manager. Er sammelt Requests aus SWCs sowie aus BSW-Modulen (ComM, Dcm, EcuM) und steuert über BSW-Action-Lists und RTE-Mode-Switches die Peripherie- und Stack-Zustände.
