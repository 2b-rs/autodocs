1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Erweitertes UML-Zustandsdiagramm (State Transition Model) des AUTOSAR OS Task-Lebenszyklus mit annotierten Steuerungsaktionen für das Subsystem Time Protection (Zeitüberwachung).
  • Architektur-Einordnung: Verortet im AUTOSAR Classic Platform OS (gemäß SWS OS, Kapitel 7.9 Time Protection). Es erweitert das klassische OSEK/VDX-Zustandsmodell um deterministische Timing-Überwachungsmechanismen (Echtzeitgarantie, Interferenzfreiheit nach ISO 26262 bis ASIL-D, Vermeidung von CPU-Monopolisierung durch defekte oder hängende Tasks).

2. Komponenten, Entitäten & Schnittstellen

  • Task-Zustände (Zustandsknoten):
    • SUSPENDED: Task ist passiv, belegt keine CPU-Ressourcen und ist nicht eingeplant.
    • READY: Task ist aktivierungsbereit in der Scheduler-Ready-Queue eingereiht und wartet auf CPU-Zuteilung.
    • RUNNING: Task wird aktuell auf dem zugewiesenen CPU-Kern ausgeführt.
    • WAITING: Nur für Extended Tasks: Task ist blockiert und wartet auf das Eintreffen mindestens eines Events (WaitEvent).
  • Time-Protection-Überwachungsgrößen (Konfigurations-Container OsTaskTimeProtection):
    • OsTaskExecutionBudget: Konfigurierte maximale Netto-Ausführungszeit (WCET-Budget) eines Tasks pro Aktivierungsinstanz bzw. zwischen zwei Wartezuständen.
    • OsTaskTimeFrame: Konfiguriertes Mindest-Aktivierungsintervall (Inter-Arrival Time / Ratenbegrenzung) zur Begrenzung der Aktivierungs- und Freigabefrequenz.
  • Zustandsübergänge & Service-Trigger:
    • Activate: API ActivateTask() oder ChainTask() (führt von SUSPENDED nach READY).
    • Start: Scheduler-Dispatching (führt von READY nach RUNNING).
    • Preempt: Verdrängung durch höherprioren Task oder Cat-2-ISR (führt von RUNNING nach READY).
    • Wait: API WaitEvent() (führt von RUNNING nach WAITING).
    • Release: API SetEvent() (führt von WAITING nach READY).
    • Terminate: API TerminateTask() oder ChainTask() (führt von RUNNING nach SUSPENDED).

3. Dynamisches Verhalten & Sequenzablauf

A. Steuerung des OsTaskExecutionBudget (Netto-Laufzeitüberwachung)
  1. Start (READY → RUNNING): Beim Dispatching (Start) startet der OS-Hardwaretimer/Budgetzähler die Messung der verbrauchten CPU-Zeit für diesen Task.
  2. Pause/Stopp (RUNNING → READY): Bei Verdrängung (Preempt) wird die Budget-Zeitmessung angehalten (stopped). Die verbleibende Restzeit bleibt konserviert; Fremdcode (höherpriorer Task / unterbrechende ISRs) verbraucht nicht das Budget des verdrängten Tasks.
  3. Fortsetzung (READY → RUNNING): Bei Wiederaufnahme läuft die Restbudget-Messung nahtlos weiter.
  4. Reset/Neuinitialisierung (RUNNING → SUSPENDED oder RUNNING → WAITING):
    • Bei Terminierung (TerminateTask) wird das Budget auf den vollen Nennwert zurückgesetzt (reset).
    • Bei Blockade (WaitEvent) wird das Budget ebenfalls zurückgesetzt (reset). Eine Wiederaufnahme nach Event-Eintreffen startet stets mit einem vollen Ausführungsbudget.
B. Steuerung des OsTaskTimeFrame (Aktivierungsraten- / Mindestabstandsüberwachung)
  1. Initiale Aktivierung: Activate (SUSPENDED → READY) startet das Intervall OsTaskTimeFrame.
  2. Mehrfachaktivierung (Queueing / Mehrfachinstanzen):
    • Trifft ein erfolgreicher Aktivierungsaufruf für einen Task ein, der sich bereits im Zustand READY befindet, startet sofort ein neuer OsTaskTimeFrame.
    • Trifft ein Aktivierungsaufruf für einen Task ein, der sich im Zustand RUNNING befindet, startet ebenfalls sofort ein neuer OsTaskTimeFrame.
  3. Event-Freigabe: Bei Release (WAITING → READY) via SetEvent() wird ein neuer OsTaskTimeFrame gestartet.
C. Sonderfall & Fehlerpfade
  • Virtueller Wartezustand: Ruft ein Task WaitEvent() auf ein Event auf, welches bereits gesetzt (set) ist, wechselt der Task konzeptionell/normativ dennoch kurzfristig in den Zustand WAITING und unmittelbar zurück. Folge: Das OsTaskExecutionBudget wird zwingend zurückgesetzt (reset).
  • Budget- bzw. Raten-Verletzung:
    • Überschreitet die Netto-Laufzeit das OsTaskExecutionBudget oder erfolgt eine Aktivierung/Freigabe vor Ablauf des OsTaskTimeFrame, detektiert das OS eine Time-Protection-Verletzung.
    • Synchroner Fehlerpfad: Ausführung stoppt sofort; OS ruft ProtectionHook(E_OS_PROTECTION_TIME) bzw. ProtectionHook(E_OS_PROTECTION_ARRIVAL) auf.
    • Reaktionskaskade (je nach Rückgabewert des Protection Hooks): Task terminieren (PRO_TERMINATETASKISR), OS-Application terminieren (PRO_TERMINATEAPPL), Partition neu starten (PRO_TERMINATEAPPL_RESTART) oder Shutdown (PRO_SHUTDOWN).

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Basic und Extended Tasks:
    • Basic Tasks durchlaufen nur den linken Zyklus (SUSPENDED ↔ READY ↔ RUNNING). Ihr Budget gilt exakt für eine vollständige Instanzausführung.
    • Extended Tasks nutzen den Pfad über WAITING. WaitEvent() dient als systematischer Rekalibrierungspunkt für das Ausführungsbudget in Endlosschleifen (while(1)-Server-Tasks).
  • Auslegung von OsTaskExecutionBudget (WCET-Absicherung):
    • Entwickler müssen das Budget strikt oberhalb der worst-case Netto-Laufzeit dimensionieren (inklusive CPU-Pipelines, Cache-Misses und OS-System-Call-Overhead).
    • Werden OS-Ressourcen (GetResource) oder Spinlocks gehalten, greifen zusätzliche separate Schranken (OsTaskResourceLockBudget), die parallel zum ExecutionBudget überwacht werden.
  • Dimensionierung von OsTaskTimeFrame:
    • Verhindert DoS-Zustände (Task-Aktivierungsfluten durch prellende externe Interrupts oder Amok laufende Softwarekomponenten).
    • Bei Tasks mit zulässigen Mehrfachaktivierungen (OsTaskActivation > 1) muss sichergestellt sein, dass Burst-Aktivierungen nicht gegen OsTaskTimeFrame verstoßen, andernfalls wird die Aktivierung abgewiesen bzw. führt zur Protection-Reaktion.
  • Gefahr von "Budget-Exploits" via WaitEvent:
    • Da WaitEvent das OsTaskExecutionBudget bedingungslos zurücksetzt, kann ein Task durch zyklisches Abfragen/Warten auf dauerhaft anstehende Events sein Ausführungsbudget künstlich erneuern, ohne tatsächlich suspendiert zu werden. Dies muss im Architektur-Review ausgeschlossen werden.
