1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Objektdiagramm / Instanzendiagramm der AUTOSAR ECU Configuration Value Description (ECUC-Werte-Modell gemäß AUTOSAR_TPS_ECUConfiguration).
  • Technischer Zweck: Spezifikationsbeispiel zur Veranschaulichung der modulübergreifenden PDU-Verknüpfung für einen Sendevorgang (Transmission, Tx) vom AUTOSAR COM-Modul über den PDU Router (PduR) zum CAN Interface (CanIf).
  • Architektur-Einordnung: Kommunikationsstack der AUTOSAR Classic Platform (BSW Com-Stack). Zeigt das Architekturprinzip der losen Kopplung: BSW-Module referenzieren nicht direkt die Konfigurationscontainer anderer Module, sondern binden sich über eine gemeinsame, zentrale System-PDU (System_Pdu im globalen EcuC-Modul).

2. Komponenten, Entitäten & Schnittstellen

Dargestellt sind konkrete Instanzen (EcucContainerValue), deren Konfigurationsparameter (EcucNumericalParamValue) sowie Referenzen (EcucReferenceValue):

  • ComIPdu : EcucContainerValue (AUTOSAR COM):
    • Repräsentiert die I-PDU im COM-Modul.
    • Aggregiert per Komposition (black diamond) die Referenz PduIdRef : EcucReferenceValue, welche gerichtet auf System_Pdu verweist.
  • PduRRoutingPath : EcucContainerValue (PDU Router):
    • Aggregiert die Quell- und Ziel-PDU-Definitionen des Routing-Pfads:
      1. PduRSrcPdu : EcucContainerValue (Ingress-Seite des PduR):
        • SrcPduRef : EcucReferenceValue: Referenziert System_Pdu.
        • HandleId : EcucNumericalParamValue (value = 23): Numerische PDU-ID, unter welcher der PduR die Sendeanforderung vom COM-Modul entgegennimmt.
      2. PduRDestPdu : EcucContainerValue (Egress-Seite des PduR):
        • DestPduRef : EcucReferenceValue: Referenziert dieselbe System_Pdu.
  • CanIfTxPduConfig : EcucContainerValue (CAN Interface):
    • Repräsentiert die PDU-Konfiguration auf Treiberschnittstellenebene.
    • Aggregiert:
      • PduIdRef : EcucReferenceValue: Referenziert System_Pdu.
      • CanIfCanTxPduId : EcucNumericalParamValue (value = 6): Numerische ID der Tx-PDU im CanIf.
  • System_Pdu : EcucContainerValue (Globales EcuC-Modul):
    • Zentrale EcuC-PDU (/AUTOSAR/EcucDefs/EcuC/EcucPduCollection/Pdu), die als Bindeglied (Indirektionsanker) fungiert.
  • Kardinalitäten & Beziehungen:
    • Komposition: 1 PduRRoutingPath besitzt genau 1 PduRSrcPdu und ≥ 1 PduRDestPdu (hier 1 dargestellt).
    • Assoziationen / Referenzen: N:1-Bindung aller beteiligten Modul-PDUs (ComIPdu, PduRSrcPdu, PduRDestPdu, CanIfTxPduConfig) auf die identische System_Pdu.

3. Dynamisches Verhalten & Sequenzablauf

Aus den dargestellten Konfigurationswerten resultiert zur Laufzeit folgende synchrone Tx-Aufrufkette:

  1. Trigger COM: Das COM-Modul initiiert das Senden (z. B. zyklisch über Com_MainFunctionTx() oder ereignisbasiert via Com_SendSignal()).
  2. Schnittstelle COM → PduR:
    • COM ruft PduR_ComTransmit(23, &PduInfo) auf.
    • Der Parameter PduId = 23 entspricht exakt der in PduRSrcPdu.HandleId konfigurierten ID.
  3. Routing im PDU Router:
    • PduR schlägt in seiner statisch generierten Routing-Tabelle anhand der ID 23 den Pfad nach.
    • Über die identische System_Pdu-Referenz ist die Destination als CanIfTxPduConfig aufgelöst.
  4. Schnittstelle PduR → CanIf:
    • PduR ruft unmittelbar synchron CanIf_Transmit(6, &PduInfo) auf.
    • Der Parameter TxPduId = 6 entspricht exakt dem Wert aus CanIfTxPduConfig.CanIfCanTxPduId.
  5. Rückmeldekette (Tx-Confirmation, asynchron):
    • Nach erfolgreichem CAN-Frame-Versand: Can_TxConfirmation() → CanIf_TxConfirmation() → PduR_CanIfTxConfirmation() → Com_TxConfirmation().

4. Normative Relevanz & Entwickler-Hinweise

  • EcuC Global PDU Indirektion: Modul-Generatoren (Com, PduR, CanIf) dürfen keine direkten Modul-Container-Referenzen aufeinander halten. Die Konsistenzprüfung des Kommunikationspfads erfolgt zur Generierungszeit ausschließlich über die Identität der referenzierten EcucPduCollection/Pdu.
  • Handle-ID-Separation:
    • HandleId = 23 ist ein PduR-lokaler Ingress-Handle (Sicht COM → PduR).
    • CanIfCanTxPduId = 6 ist ein CanIf-lokaler Ingress-Handle (Sicht PduR → CanIf).
    • Beide IDs sind voneinander entkoppelt und dürfen im Integrations-Projekt nicht verwechselt werden.
  • Zero-Cost Routing Optimierung:
    • Ist im PduR für diesen Pfad PduRZeroCostOperation = true konfiguriert (Single-Source, Single-Destination, kein PduR-Puffer/Gateway), kann der PduR-Code als C-Präprozessor-Makro generiert werden: #define PduR_ComTransmit(id, info) CanIf_Transmit(6, info)
    • Dadurch entfallen der PduR-Funktionsaufruf und der Lookup-Overhead zur Laufzeit.
  • Integrations-Fallstrick: Weisen SrcPduRef und DestPduRef versehentlich auf unterschiedliche EcucContainerValue-Instanzen der System-PDU, bricht der BSW-Generator die Tabellen-Generierung ab oder generiert einen toten Routing-Pfad ohne Ziel.
