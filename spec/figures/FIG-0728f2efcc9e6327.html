1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECUC-Metamodell / UML-Klassendiagramm für die BSW-Modulkonfigurationsdefinition (ECU Configuration Parameter Definition).
  • Technischer Zweck: Definition der Persistenz-Schnittstelle des Key Managers (KeyM) zur persistenten Speicherung kryptografischer Schlüssel, Zertifikate und Zustandsdaten über den NVRAM Manager (NvM).
  • Architektonische Einordnung: Verortung im Security-Cluster der AUTOSAR Classic Platform. Das Diagramm spezifiziert die Metadatenstruktur, mit der KeyM-Instanzen an konkrete NVRAM-Blöcke im Speicher-Stack gekoppelt werden.

2. Komponenten, Entitäten & Schnittstellen

  • KeyM (EcucModuleDef):
    • Wurzel-Konfigurationsdefinition des Key-Manager-Moduls.
    • Kardinalität: 0..1 (Singleton-Charakter pro BSW-Konfiguration).
    • Hält via Komposition (+container) die KeyMNvmBlock-Definitionen.
  • KeyMNvmBlock (EcucParamConfContainerDef):
    • Konfigurationscontainer für einen einzelnen, dem KeyM zugeordneten NvM-Block.
    • Multiplizität: 0..65535 (uint16-adressierbar); erlaubt feingranulare Partitionierung verschiedener Schlüsselbestände auf separate NVRAM-Blöcke.
  • KeyMNvmBlockDescriptorRef (EcucReferenceDef, ECUC_KeyM_00079):
    • Multiplizität: 0..1.
    • Attribut: requiresSymbolicNameValue = true (erfordert die Auflösung als symbolische Konstante im generierten Code).
    • Assoziation (+destination): Typisierte Referenz auf den externen Container NvMBlockDescriptor aus dem Modulpaket Nvm.
    • Funktion: Bindeglied zwischen KeyM-Block-ID und NvM-Block-ID.
  • NvMBlockDescriptor (EcucParamConfContainerDef, Paket Nvm):
    • Multiplizität: 1..65536.
    • Repräsentiert die Ziel-Blockkonfiguration im NVRAM Manager (inkl. Blockgröße, CRC, Redundanz und Speicherort im NV-Speicher).
  • KeyMNvmBlockWriteDelayed (EcucIntegerParamDef, ECUC_KeyM_00084):
    • Multiplizität: 1..1 (Pflichtparameter innerhalb von KeyMNvmBlock).
    • Wertebereich: min = 0, max = 65535.
    • Semantik: Konfiguriert die Schreibverzögerung (in KeyM_MainFunction-Perioden bzw. Zeiteinheiten) vor dem Auslösen eines NvM-Schreibvorgangs, um Schreibzyklen auf dem Flash/EEPROM bei sequentiellen Updates zusammenzufassen (Write-Buffering).

3. Dynamisches Verhalten & Sequenzablauf

Aus dem Konfigurationsmodell resultiert folgendes Laufzeitverhalten im BSW-Stack:

[KeyM Client / Crypto Engine]
       │ (1) Update Key / Cert
       ▼
   [KeyM RAM] ──────── (2) Start WriteDelayed Counter (KeyMNvmBlockWriteDelayed)
       │
       │ (3) Timer expired / Counter == 0
       ▼
[KeyM_MainFunction]
       │ (4) NvM_WriteBlock(NvMBlockDescriptorRef, KeyM_RAM_Buffer)
       ▼
     [NvM] ── (asynchron) ──> Flash/EEPROM Write
       │
       │ (5) Single-Block Callback / NvM_GetErrorStatus
       ▼
[KeyM_MainFunction]
       ├── NVM_REQ_OK: Update persistent state flag
       └── NVM_REQ_NOT_OK: Det_ReportError / Dem_SetEventStatus
  • Schreib-Debouncing: Bei KeyMNvmBlockWriteDelayed > 0 triggert eine Modifikation von Schlüsseln im RAM nicht unmittelbar NvM_WriteBlock(). Der KeyM akkumuliert Änderungen und setzt den asynchronen Schreibauftrag erst nach Ablauf der definierten Verzögerung ab.
  • Sofortschreiben: Bei KeyMNvmBlockWriteDelayed = 0 wird die NvM-Schreibanforderung im selben oder nächsten Main-Zyklus ohne Verzögerungsintervall angestoßen.
  • Lesephase: Beim BSW-Start erfolgt das Laden via NvM_ReadAll oder gezieltes NvM_ReadBlock auf die über KeyMNvmBlockDescriptorRef aufgelöste Block-ID.

4. Normative Relevanz & Entwickler-Hinweise

  • Symbolische Referenzierung (requiresSymbolicNameValue = true):
    • Der BSW-Generator erzeugt Verweise auf das symbolische Literal (z. B. NvMConf_NvMBlockDescriptor_<Name>). Im Quellcode darf keine numerische Block-ID hartkodiert werden.
  • Pufferabstimmung (KeyM vs. NvM):
    • Die im Ziel-NvMBlockDescriptor definierte NvMBlockLength muss exakt mit der Serialisierungsgröße der zugewiesenen Key-Container (inkl. kryptografischer Metadaten, Flags und Header) übereinstimmen. Unterdimensionierte NvM-Blöcke führen zu Datenkorruption oder NVM_REQ_INTEGRITY_FAILED.
  • Einschränkung der Multiplizität (KeyMNvmBlockDescriptorRef: 0..1):
    • Ist die Referenz 0, fungiert der KeyMNvmBlock rein als RAM-basierter Puffer ohne Persistierung oder die Bindung wird post-build/variantenabhängig erst zur Link-Time/Post-Build-Loadable-Zeit über alternative Deskriptoren vervollständigt.
  • Endurance & Timing:
    • KeyMNvmBlockWriteDelayed muss in Abstimmung mit der Task-Zykluszeit der KeyM_MainFunction parametriert werden. Zu kleine Werte gefährden die Flash-Lebensdauer bei häufigen Schlüssel-Updates; zu große Werte erhöhen das Risiko von Datenverlust bei plötzlichem Spannungsabfall (Undervoltage / Power-Off), sofern kein Emergency-Flush im KeyM-Shutdown-Pfad konfiguriert ist.
