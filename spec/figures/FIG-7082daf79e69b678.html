1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU- / Wire-Format-Layout (Bit-Level-Framing im 32-Bit-Wort-Raster, Big-Endian / Network Byte Order).
  • Technischer Zweck: Spezifikation des Paketaufbaus für das letzte Segment (Last Segment) einer fragmentierten SOME/IP-Nachricht unter Verwendung des SOME/IP Transport Protocols (SomeIpTp).
  • Architektur-Kontext:
  • Einsatzbereich: AUTOSAR Classic (CP) und Adaptive Platform (AP) im Kommunikations-Stack (Schichtenfolge: PduR $\leftrightarrow$ SomeIpTp $\leftrightarrow$ SoAd).
  • Funktionale Einordnung: Ermöglicht die Übertragung von SOME/IP-Nachrichten, deren Gesamtlänge das Maximum Transmission Unit (MTU)- bzw. PDU-Limit überschreitet (insb. UDP-Begrenzung auf 1400/1472 Bytes), ohne den Overhead einer TCP-Verbindung zu erfordern.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in den standardisierten 16-Byte SOME/IP-Basis-Header, den 4-Byte SOME/IP-TP-Zusatz-Header sowie den Nutzdatenbereich:

  • SOME/IP-Basis-Header (Byte 0–15):
  • Message ID [32 bit] (0x0101 0009):
  • Service ID (Bit 0–15): 0x0101
  • Method ID (Bit 16–31): 0x0009 (Bit 16 = 0 kennzeichnet eine Methode; 1 wäre ein Event).
  • Length [32 bit] (0x00000144 = 324 Bytes):
  • Definiert als verbleibende PDU-Größe ab Offset 8 (nach dem Length-Feld): $8\text{ Bytes (SOME/IP-Rest)} + 4\text{ Bytes (TP-Header)} + 312\text{ Bytes (Payload)} = 324\text{ Bytes}$.
  • Request ID [32 bit] (0x0001 0005):
  • Client ID (Bit 0–15): 0x0001
  • Session ID (Bit 16–31): 0x0005 (dient zusammen mit Message ID der Zuordnung bei der Reassemblierung).
  • Protocol Version [8 bit]: 0x01
  • Interface Version [8 bit]: 0x01
  • Message Type [8 bit]: b00100000 (0x20):
  • Bit 5 (TP-Flag) ist auf 1 gesetzt.
  • Bit 0–3 (0x00 = REQUEST): Kombination aus Request-Typ und aktivem TP-Flag (REQUEST_WITH_TP).
  • Return Code [8 bit]: 0x00 (E_OK).
  • SOME/IP-TP-Zusatz-Header (Byte 16–19, hervorgehoben):
  • Offset [28 bit] (Bit 0–27): Gibt den Startoffset der Nutzdaten bezogen auf die unfragmentierte Gesamtnachricht an. Einheit: 16-Byte-Blöcke (physikalischer Byte-Offset = $\text{Offset} \times 16$).
  • RES [3 bit] (Bit 28–30): Reserviert für zukünftige Protokollerweiterungen; zwingend 000b.
  • M [1 bit] (Bit 31): More Segments Flag:
  • Wert 0: Kennzeichnet das vorliegende Segment deterministisch als das finale Segment der Nachricht.
  • Payload (Byte 20–331):
  • Payload [312 bytes]: Abschluss-Nutzdatenfragment (hier im ASCII-Beispiel: 0x4d 0x65 0x67 0x61 = "Mega", 0x6e 0x46 0x6f 0x78 = "nFox").

3. Dynamisches Verhalten & Sequenzablauf

  1. Rx-Indication & Header-Parsing:
  • SoAd signalisiert den Empfang via SomeIpTp_RxIndication().
  • SomeIpTp prüft Bit 5 des Message Type. Ist das TP-Flag gesetzt, werden die 4 Bytes unmittelbar nach dem Return Code als TP-Header interpretiert.
  1. Reassemblierungs-Steuerung (SWS_SomeIpTp_00090):
  • Zuordnung des Segments zu einem Rx-Puffer anhand des Tupels [Message ID, Request ID].
  • Letztes Segment ($M=0$):
  • Auswertung des Offset-Felds: Bestimmt die Zielposition im Gesamtreassemblierungs-Puffer ($\text{Offset} \times 16$).
  • Ermittlung der finalen Gesamtlänge der PDU: $\text{TotalLength} = (\text{Offset} \times 16) + 312\text{ Bytes}$.
  1. Abschluss & Fehlerbehandlung:
  • Sobald alle Fragmente (von Offset 0 bis zum letzten Segment mit $M=0$) vollständig und lückenlos vorliegen, übergibt SomeIpTp die zusammengesetzte PDU mittels PduR_SomeIpTpRxIndication() an den PDU-Router.
  • Abbruchkriterien: Läuft der Reassemblierungs-Timer (SomeIpTpRxTimeoutTime) vor Eintreffen des Segments $M=0$ oder bei verbleibenden Lücken ab, wird der Reassemblierungspuffer verworfen (MEM_CORRUPTION / TIMEOUT), und es erfolgt ggf. ein Det-Aufruf (SOMEIPTP_E_TIMEOUT).

4. Normative Relevanz & Entwickler-Hinweise

  • Sonderregel für Payload-Größen (16-Byte-Alignment):
  • Intermediäre Segmente ($M=1$): Die Payload-Länge muss zwingend ein ganzzahliges Vielfaches von 16 Bytes sein (Payload_Length % 16 == 0).
  • Letztes Segment ($M=0$, wie dargestellt): Die Payload-Länge unterliegt nicht der 16-Byte-Restriktion (im Diagramm: $312 \pmod{16} = 8 \neq 0$). Stack-Parser dürfen hier kein Vielfaches von 16 erzwingen.
  • Längenberechnung (Length-Feld):
  • Entwickler von Serialisierern/Generatoren müssen beachten, dass der 4-Byte-TP-Header in das SOME/IP-Feld Length eingerechnet wird: $\text{Length} = 8 + 4 + \text{PayloadLength}$. Bei Standard-SOME/IP (ohne TP) gilt hingegen $\text{Length} = 8 + \text{PayloadLength}$.
  • Message-Type-Maskierung:
  • Der Empfänger muss den Message Type vor der Übergabe an höhere Schichten maskieren: Effective_Type = Message_Type & ~0x20, um den ursprünglichen Diensttyp (REQUEST, NOTIFICATION etc.) wiederherzustellen.
  • PduR-Kopplung (Zero-Copy / Buffer Allocation):
  • Da die Gesamtlänge der Nachricht erst mit dem Eintreffen des letzten Segments ($M=0$) exakt bekannt ist (vorher nur als untere Schranke via $\text{Offset} \times 16$), muss der Reassemblierungs-Puffer entweder für die maximal konfigurierte PDU-Größe (SomeIpTpRxMaximumLength) allokiert oder dynamisch verwaltet werden.
