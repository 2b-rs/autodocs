1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Aktivitätsdiagramm (Kontrollfluss-/Ablaufdiagramm zur Funktionsspezifikation).
  • Funktionaler Kontext: Spezifiziert den normativen Vorprüfungs-Schritt („Verify inputs of the check function“ gemäß [PRS_E2E_01196], abgeleitet aus RS_E2E_08539) der API-Funktion E2E_PXXmSinkCheck().
  • Architektur-Einordnung:
    • Teil der AUTOSAR Foundation E2E-Protokollspezifikation (AUTOSAR_FO_PRS_E2EProtocol), gültig für Classic und Adaptive Platform (R22-11, R23-11).
    • Gehört zu den E2E-Methoden-Profilen (Kennzeichnung PXXm, wobei XX den Profil-Algorithmus wie z. B. Profile 04, 07 oder 22 repräsentiert und m für RPC-/Methodenkommunikation wie SOME/IP steht).
    • Die Funktion wird im Sink-Endpunkt (Consumer/Empfänger von Request- oder Response-Nachrichten) aufgerufen, um vor der eigentlichen kryptographischen/zyklischen E2E-Prüfung (CRC, Counter, Data-ID) die formale Gültigkeit aller Aufrufparameter sicherzustellen.

2. Komponenten, Entitäten & Schnittstellen

  • Funktions-Schnittstelle:
    • E2E_PXXmSinkCheck(const E2E_PXXmConfigType* Config, E2E_PXXmCheckStateType* State, const uint8* Data, LengthType Length, MessageType, MessageResult)
  • Eingangsdatenstrukturen & Parameter:
    • Config (IN): Zeiger auf konstante Profil-Konfigurationsstruktur (E2E_PXXmConfigType), enthält u. a. MinDataLength und MaxDataLength (spezifiziert in Bits).
    • State (IN/OUT): Zeiger auf Zustandsspeicher des Empfängers (E2E_PXXmCheckStateType).
    • Data (IN): Zeiger auf das serialisierte Nutzdaten-Array (const uint8*).
    • Length (IN): Länge des Puffers Data in Bytes.
    • MessageType (IN): Enumeration/Ganzzahlwert für den Nachrichtentyp (Wertebereich [0, 1], z. B. Request vs. Response).
    • MessageResult (IN): Enumeration/Ganzzahlwert für das RPC-Ergebnis (Wertebereich [0, 1], z. B. OK vs. ERROR).
  • Lokale Variablen:
    • NewDataAvailable (boolean): Lokale Ablaufvariable (muss explizit nicht in State persistiert werden).
  • Terminale Ausgangsknoten (Activity Final Nodes):
    • null: Schwerwiegender Zeigerfehler (E2E_E_INPUTERR_NULL).
    • wrong input: Parameterwert außerhalb der Spezifikation (E2E_E_INPUTERR_WRONG).
    • input ok: Parameterprüfung erfolgreich; Verzweigung in die nachfolgende E2E-Header- und Checksummenverifikation.

3. Dynamisches Verhalten & Sequenzablauf

Der Prüfpfad wird synchron bei jedem Aufruf von E2E_PXXmSinkCheck() durchlaufen:

  1. Initialisierung:
    • Setzen der lokalen Kontrollvariable: NewDataAvailable = FALSE.
  2. Zeiger-Validierung (Null-Pointer-Schutz):
    • Bedingung: (Config != NULL) && (State != NULL).
    • [FALSE]: Sofortiger Abbruch zum Endzustand null (Rückgabewert: E2E_E_INPUTERR_NULL).
    • [TRUE]: Übergang zur Daten-/Längenkonsistenzprüfung.
  3. Puffer-Konsistenzprüfung:
    • Bedingung: (Data != NULL && Length != 0) || (Data == NULL && Length == 0).
    • [FALSE]: Abbruch zu wrong input (inkonsistente Pufferdeskriptoren, z. B. Zeiger gültig bei Länge 0 oder Nullzeiger bei Länge > 0; Rückgabewert: E2E_E_INPUTERR_WRONG).
    • [TRUE]: Prüfung auf Datenpräsenz.
  4. Verzweigung Queued Communication / Empty Buffer:
    • Bedingung: Data != NULL.
    • [FALSE] (Data == NULL && Length == 0): Gültiger Laufzeitpfad bei gepufferter/queuender Kommunikation, wenn keine Nachricht im Empfangspuffer ansteht. Direkter Übergang zu input ok mit beibehaltenem NewDataAvailable = FALSE (keine Signalauswertung erforderlich).
    • [TRUE]: Daten vorhanden; Fortführung der Wertebereichsprüfungen.
  5. Längenprüfung gegen Konfigurationsgrenzen:
    • Bedingung: (Length >= Config->MinDataLength / 8) && (Length <= Config->MaxDataLength / 8).
    • Hinweis: Umrechnung der Konfigurationswerte von Bits in Bytes.
    • [FALSE]: Abbruch zu wrong input (E2E_E_INPUTERR_WRONG).
    • [TRUE]: Nächste Prüfung.
  6. Validierung von MessageType:
    • Bedingung: (MessageType >= 0) && (MessageType <= 1).
    • [FALSE]: Abbruch zu wrong input (E2E_E_INPUTERR_WRONG).
    • [TRUE]: Nächste Prüfung.
  7. Validierung von MessageResult:
    • Bedingung: (MessageResult >= 0) && (MessageResult <= 1).
    • [FALSE]: Abbruch zu wrong input (E2E_E_INPUTERR_WRONG).
    • [TRUE]: NewDataAvailable = TRUE, regulärer Übergang zu input ok.

4. Normative Relevanz & Entwickler-Hinweise

  • Rückgabewerte & Fehlerbehandlung:
    • Pfad null mappt auf den Standard-Fehlercode E2E_E_INPUTERR_NULL (0x13).
    • Pfad wrong input mappt auf E2E_E_INPUTERR_WRONG (0x17).
    • Weder Det (Det_ReportError) noch Dem werden innerhalb des E2E-Library-Kerns aufgerufen; die Signalisierung erfolgt ausschließlich über den Funktionsrückgabewert an den Aufrufer (z. B. SOME/IP-Transformer, RTE oder Com-Stack).
  • Bit-zu-Byte-Skalierung:
    • Config->MinDataLength und Config->MaxDataLength sind in der E2E-Konfiguration in Bits definiert. Die Implementierung muss zwingend die Division / 8 vorsehen. Ein Überlauf oder Restwert bei unvollständigen Bytes muss profilabhängig beachtet werden (i. d. R. sind E2E-Methodenprofile byteweise ausgerichtet).
  • Handhabung von Empty Reads:
    • Der Pfad Data == NULL && Length == 0 ist explizit erlaubt und als input ok eingestuft. Er signalisiert gepufferten Empfängern (Queued Communication), dass kein Element abgeholt werden konnte, ohne dass dies als E2E-Schutzfehler gewertet wird. Die E2E-Zustandsmaschine wertet in diesem Fall keine Prüfsummen aus.
  • Stack- & Speicheroptimierung:
    • NewDataAvailable darf nicht im persistenten RAM (E2E_PXXmCheckStateType) abgelegt werden, sondern muss rein register-/stackbasiert innerhalb des Ausführungskontexts von E2E_PXXmSinkCheck() verwaltet werden.
