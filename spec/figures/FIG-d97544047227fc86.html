1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Statisches Allokations- und Schichtenmodell (Memory Mapping / Structural Architecture Diagram).
  • Technischer Zweck: Visualisierung des AUTOSAR NV-Data-Handling Use Case 3 (Verwendung eines NvBlockSwComponentType mit expliziter Synchronisation über den NvM-internen RAM Mirror).
  • Funktionale Einordnung:
    • Entkopplung des persistenten Speichers (Flash/EEPROM via MemHwA: Fee/Ea und Fls/Eep) von der Applikationsschicht (SWC) über die RTE.
    • Verlagerung der Datenhaltung (RAM Block 0, RAM Block 1) in den Kontext des NvBlockSwComponentType (RTE-verwaltet).
    • Im NvM (BSW) ist kein permanenter RAM-Block allokiert (Block Not Present / NvMBlockUseSyncMechanism = TRUE); stattdessen puffert ein globaler/konfigurierter RAM Mirror Daten temporär während NVRAM-Lese- und Schreiboperationen.

2. Komponenten, Entitäten & Schnittstellen

  • Schichten & Akteure:
    • Application Layer (SWC): Drei Software-Components greifen nebenläufig oder sequenziell auf die Datenblöcke zu:
      • Linke SWC: Lese-/Schreibzugriff (read/write) auf RAM Block 0.
      • Mittlere und rechte SWC: Lese-/Schreibzugriff (read/write) gemeinsam auf RAM Block 1 (Shared NV-Data-Pattern).
    • Runtime Environment (RTE) / NvBlockSwComponentType:
      • Beherbergt die Deskriptoren NvBlockDescriptor0 und NvBlockDescriptor1 (M2-Stereotyp «NvBlockDescriptor»).
      • Verwaltet die physischen Arbeitsdaten im RAM: RAM Block 0, RAM Block 1.
      • Verwaltet Referenzen auf statische Standardwerte: ROM Block Data (Flash/ROM).
    • Basic Software (NvM) / NvMBlockConfiguration:
      • Zwei Instanzen von NvMBlockDescriptor (Block 0 und Block 1):
        • RAM Block (gepunktet dargestellt): Nicht im NvM allokiert (NvMBlockUseSyncMechanism = true, NvMRamBlockDataAddress = NULL_PTR).
        • ROM Block (gestrichelt dargestellt): Optionaler ROM-Default-Block (NvMRomBlockDataAddress referenziert ROM Block Data).
        • NV Block (durchgezogen): Logische Blockrepräsentation im NV-Speicher.
      • RAM Mirror: Zentraler Arbeitspuffer im NvM für Serialisierung/Deserialisierung und CRC-Berechnung.
    • Hardware / Abstraction Layer (Flash / EEPROM):
      • Physische FLS Block-Partitionen auf dem Speichermedium, referenziert durch den jeweiligen logischen NV Block via Unterbau (MemIf -> Fee/Ea -> Fls/Eep).
  • Schnittstellen & Kopplungen:
    • SWC ↔ RTE: Standard-RTE-Ports (SenderReceiverInterface oder ClientServerInterface für NvDataInterface).
    • RTE ↔ NvM (Synchronisation): Bidirektionaler Pfad Data Access using Callback:
      • RTE stellt Synchronisations-Callbacks bereit: Rte_SetMirror / Rte_GetMirror (entsprechend NvMReadRamBlockFromNvM und NvMWriteRamBlockToNvM).
    • ROM-Kopplung: Refer to-Verbindung vom NvM-Deskriptor auf die Compile-Time-Konstanten ROM Block Data innerhalb der RTE/SWC-Generierungsartefakte zur Wiederherstellung von Defaults (NvM_RestoreBlockDefaults).

3. Dynamisches Verhalten & Sequenzablauf

  • Schreibpfad (Write Transaction / NvM_WriteBlock / NvM_WritePRAMBlock):
    1. SWC modifiziert RAM Block via RTE-API synchron im RAM.
    2. NvM-Schreibauftrag wird getriggert (asynchroner Request via BSW/NVM-Queue).
    3. Bei Block-Bearbeitung im NvM-MainFunction-Zyklus ruft NvM den Callback NvMWriteRamBlockToNvM (Rte_GetMirror) auf.
    4. Die RTE kopiert atomar/geschützt (z. B. via Exclusive Area / OS-Interrupt-Sperre) die Nutzdaten aus RAM Block in den NvM RAM Mirror.
    5. NvM berechnet ggf. CRC und schreibt die Daten asynchron über MemIf in den FLS Block.
  • Lesepfad (Read Transaction / Startup / NvM_ReadBlock / NvM_ReadAll):
    1. NvM liest Daten aus FLS Block über MemIf in den RAM Mirror.
    2. Validierung von Header, Block-Header und CRC im RAM Mirror.
    3. NvM ruft den Callback NvMReadRamBlockFromNvM (Rte_SetMirror) auf.
    4. RTE kopiert Daten aus dem RAM Mirror atomar in den RAM Block des NvBlockSwComponentType.
    5. SWCs lesen fortan konsistente Werte aus dem RAM-Block.
  • Fallback auf ROM (Recovery):
    • Schlägt CRC/Lesen fehl, referenziert der NvM die ROM Block Data und kopiert diese (oder triggert die RTE-Init-Funktion), um den RAM Block zu initialisieren.
  • Precedence-Regel bei temporären Puffern:
    • Übergibt ein Aufrufer explizit einen Pufferpointer via NvM_ReadBlock(BlockId, NvM_DstPtr) bzw. NvM_WriteBlock(BlockId, NvM_SrcPtr), umgeht der NvM die Mirror-Callbacks und nutzt direkt die übergebene Adresse. Diese Aufrufe besitzen Priorität über NvM_ReadPRAMBlock/NvM_WritePRAMBlock.

4. Normative Relevanz & Entwickler-Hinweise

  • Synchronisationsmechanismus & Race Conditions:
    • Einschränkung: Implizite Synchronisation (Implicit synchronization) ist in Verbindung mit NvBlockSwComponentType nicht empfohlen/unzulässig, da Konsistenz zwischen NvM-Zyklus und asynchroner Task-Ausführung der SWCs ohne Mirror-Locks verletzt werden kann.
    • Konfiguration: NvMBlockUseSyncMechanism = TRUE ist für diese Blöcke obligatorisch.
  • Exklusive Bereiche (Exclusive Areas):
    • Während der Ausführung von Rte_GetMirror und Rte_SetMirror muss die RTE Interrupt- bzw. Task-Sperren (SchM_Enter_NvM_*, Rte_Enter_*) etablieren, um Inkonsistenzen durch gleichzeitige Schreibzugriffe der SWCs auf den RAM-Block zu verhindern.
  • RAM-Footprint-Optimierung:
    • NvM spart RAM ein, da kein dedizierter permanenter RAM-Puffer pro Block im NvM-Treiber allokiert wird (NvMRamBlockDataAddress = NULL). Der RAM Mirror muss lediglich so groß dimensioniert sein wie der größte konfigurierte NVRAM-Block, der diesen Mechanismus nutzt (NvM_MirrorSize).
  • Multi-Client-Zugriff:
    • Wie für RAM Block 1 dargestellt, können mehrere SWCs auf denselben RAM-Block mappen. Datenintegrität auf RTE-Ebene erfordert zwingend konsistente Sender/Receiver-Semantik oder Inter-Runnable-Variablen mit geeigneter Concurrency-Policy.

NV Data Handling Guideline AUTOSAR CP R25-11 As explained above in section 4.1.3.2, whenever NvM is triggered to write or read data from the NVRAM, it fetches/updates the RAM block via callbacks (Rte_GetMirror/Rte_SetMirror) which are implemented in RTE. Additionally, if the User has a need to provide temporary RAM blocks even though mirrors are configured in the system, NvM_ReadBlock/NvM_WriteBlock API are used to provide the temporary RAM block address and in that case NvM uses the RAM block argument instead of the mirror. Such API’s have precedence over NvM_ReadPRAMBlock/NvM_WritePRAMBlock. Note: Implicit synchronization is not recommendable while using NvBlockSwComponentType.
