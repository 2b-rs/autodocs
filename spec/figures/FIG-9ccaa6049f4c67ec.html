1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm zur Modellierung der CAN-Bustopologie im Metamodell der AUTOSAR System Template Spezifikation (Subpaket Fibex4Can_Topology bzw. Ableitungen aus CoreTopology). Das Diagramm definiert die statischen Entitäten und Beziehungen zur Spezifikation von CAN-Clustern, CAN-Controllern, deren Bit-Timing-Konfiguration sowie der systemspezifischen CAN-Konnektoren im Kontext der AUTOSAR Classic Platform (Release 3.2.x). Es erweitert generische FIBEX- bzw. Topologie-Basiselemente (FibexElement, Identifiable) um CAN-spezifische Kommunikations- und Netzwerkmanagement-Attribute (CanNm) sowie Parameter für Partial Networking (PNC).

2. Komponenten, Entitäten & Schnittstellen

Das Klassendiagramm gliedert sich in drei Kernbereiche:

  1. Controller-Hierarchie & Bit-Timing:
  • CoreTopology::CommunicationController (spezialisiert Identifiable): Basisklasse für Kommunikationscontroller; deklariert das Attribut wakeUpByControllerSupported : Boolean.
  • CanCommunicationController (spezialisiert CommunicationController): CAN-spezifischer Controller mit NM-Parametern nmMsgCycleOffset : Float [0..1], nmMsgReducedTime : Float [0..1] und nmUserDataEnabled : Boolean [0..1]. Besitzt eine 1:1-Komposition (+canControllerAttributes 1) auf die abstrakte Klasse AbstractCanCommunicationControllerAttributes.
  • AbstractCanCommunicationControllerAttributes (abstrakt): Gemeinsame Basis für konkrete Konfigurationen und Konfigurationsanforderungen.
  • CanControllerConfiguration (spezialisiert AbstractCanCommunicationControllerAttributes): Konkrete Bit-Timing-Parameter mit numberOfSamples : Integer [0..1], propagationDelay : Integer [0..1], syncJumpWidth : Integer, timeSeg1 : Integer und timeSeg2 : Integer.
  • CanControllerConfigurationRequirements (spezialisiert AbstractCanCommunicationControllerAttributes): Wertebereiche für Timing-Synthesewerkzeuge mit minNumberOfTimeQuantaPerBit : Integer [0..1], maxNumberOfTimeQuantaPerBit : Integer [0..1], minSamplePoint : Float [0..1], maxSamplePoint : Float [0..1], minSyncJumpWidth : Float [0..1] und maxSyncJumpWidth : Float [0..1].
  1. Connector-Hierarchie:
  • CoreTopology::CommunicationConnector (spezialisiert Identifiable): Generischer Anschluss; besitzt eine Assoziation +commController 1 zu * auf CommunicationController sowie die Attribute nmAddress : Integer [0..1], nmEnabled : Boolean [0..1] und pncGatewayType : PncGatewayTypeEnum [0..1].
  • CanCommunicationConnector (spezialisiert CommunicationConnector): CAN-spezifischer Anschluss mit Partial-Networking-Weckparametern pncWakeupCanId : Integer [0..1], pncWakeupCanIdExtended : Boolean [0..1], pncWakeupCanIdMask : Integer [0..1], pncWakeupDataMask : Integer [0..1] und pncWakeupDlc : Integer [0..1].
  1. Cluster-Hierarchie:
  • CoreTopology::CommunicationCluster (spezialisiert FibexElement): Generisches Kommunikationscluster mit Übertragungs- und NM-Parametern (speed : Integer [0..1], protocolName : String [0..1], protocolVersion : String [0..1], maxFrameLength : Integer [0..1], nmCoordinatorSyncPrio : Integer [0..1], nmGlobalCoordinatorTime : Float [0..1], nmNodeDetectionEnabled : Boolean [0..1], nmNodeIdEnabled : Boolean [0..1], nmRepeatMessageSupport : Boolean [0..1]).
  • CanCluster (spezialisiert CommunicationCluster): CAN-spezifisches Cluster mit CanNm-Parametern (nmBusLoadReductionActive : Boolean [0..1], nmBusLoadReductionEnabled : Boolean [0..1], nmImmediateNmCycleTime : Float [0..1], nmImmediateNmTransmissions : Integer [0..1], nmImmediateRestartEnabled : Boolean [0..1], nmLowerCanId : Integer [0..1], nmUpperCanId : Integer [0..1], nmMsgCycleTime : Float [0..1], nmRemoteSleepIndicationTime : Float [0..1], nmRepeatMessageStateTime : Float [0..1], nmTimeoutTime : Float [0..1], nmWaitBusSleepTime : Float [0..1]).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert eine rein statische Metamodell-Struktur ohne explizite Ablauf- oder Interaktionspfade. Die abgebildeten Attribute determinieren jedoch direkt das dynamische Verhalten der CAN-Kommunikation und der BSW-Stack-Zustandsmaschinen zur Laufzeit:

  • Bit-Timing & Synchronisation: Die Attribute in CanControllerConfiguration (timeSeg1, timeSeg2, syncJumpWidth, numberOfSamples) bzw. CanControllerConfigurationRequirements steuern die Phaseneinteilung (Prop_Seg, Phase_Seg1, Phase_Seg2) und Bit-Resynchronisation auf dem physikalischen CAN-Bus.
  • CanNm-Zustandsmaschine: Die Attribute in CanCluster und CanCommunicationController konfigurieren die standardisierten Zustandsübergänge des AUTOSAR CAN Network Managements (Repeat Message State, Normal Operation State, Ready Sleep State, Prepare Bus-Sleep Mode, Bus-Sleep Mode), einschließlich Fast-Transmit-Zyklen (nmImmediateNmCycleTime, nmImmediateNmTransmissions), Buslastreduktion und Message-Zyklus-Offsets.
  • PNC-Wakeup-Filterung: Die Attribute in CanCommunicationConnector definieren den dynamischen Wakeup-Filtermechanismus für selektives Aufwecken (Partial Networking) anhand ID-Maskierung (pncWakeupCanIdMask) und Payload-Datenmaskierung (pncWakeupDataMask).

4. Normative Relevanz & Entwickler-Hinweise

Die Metaklassen bilden die normative Grundlage für die AUTOSAR-Systembeschreibung (System Description) sowie den daraus abgeleiteten ECU Extract (z. B. für CanIf, CanNm, Can-Treiber und ComM):

  • Timing-Spezifikation (Exakt vs. Anforderung): Durch das Polymorphie-Muster über AbstractCanCommunicationControllerAttributes ist es modellseitig verbindlich vorgegeben, dass ein CanCommunicationController exakt eine Konfigurationsausprägung besitzt – entweder eine strikte Register-Parametrisierung (CanControllerConfiguration) oder einen Anforderungsraum (CanControllerConfigurationRequirements), der erst im Systemgenerierungsschritt zu konkreten Controller-Registern aufgelöst werden muss.
  • Strikte Trennung von Bus- und Knoteneigenschaften: Busweite Timing-Vorgaben für das Netzwerkmanagement gehören normativ auf Clusterebene (CanCluster), während kanten- bzw. knotenindividuelle Eigenschaften (z. B. Sende-Offset nmMsgCycleOffset, Wakeup-Fähigkeiten) am Controller bzw. Connector verankert sind.
  • Konnektivitätsregel: Ein CommunicationController kann über 1:n mit mehreren CommunicationConnector-Instanzen verknüpft sein, was die physische Anbindung eines Controllers an unterschiedliche Kanäle oder Subnetze ermöglicht.
