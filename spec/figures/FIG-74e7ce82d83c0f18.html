1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Zustandsdiagramm (State Machine Diagram) nach OSEK/VDX- bzw. AUTOSAR-OS-Standard.
  • Architektur-Kontext: AUTOSAR Classic Platform (CP), Basishardware-Abstraktion / System Services (AUTOSAR OS, SWS OS). Im Kontext von AUTOSAR_CP_EXP_ARTI (AUTOSAR Run-Time Interface) dient das Modell AR_CP_OS_TASK als normatives Referenz-Zustandsmodell zur standardisierten Instrumentierung, Profiling- und Trace-Erfassung des Task-Schedulings für Extended Tasks (ECC1/ECC2-Konformitätsklassen).

2. Komponenten, Entitäten & Schnittstellen

  • Zustandsentitäten (AR_CP_OS_TASK):
  • Suspended: Task ist passiv, belegt keine CPU-Zeit und wartet auf Initialisierung/Aktivierung durch das Betriebssystem.
  • Ready: Task ist im Scheduling-Bereitschaftspool eingereiht; alle Ausführungsbedingungen sind erfüllt, er wartet ausschließlich auf CPU-Zuweisung durch den Scheduler.
  • Running: Task besitzt den Prozessorkontext (Instruktionszeiger, Registersatz) und führt Code aus. Pro Prozessorkern kann sich zeitgleich maximal ein Task in diesem Zustand befinden.
  • Waiting: Task ist blockiert und wartet auf mindestens ein definiertes Betriebssystem-Ereignis (OS Event). Exklusiv für Extended Tasks zulässig.
  • Architektonische Einordnung & Task-Klassen:
  • Basic Task (BCC1 / BCC2): Durchläuft lediglich den Zyklus Suspended $\rightarrow$ Ready $\rightarrow$ Running $\rightarrow$ Suspended (ggf. Präemption). Kann den Zustand Waiting konstruktionsbedingt nicht annehmen.
  • Extended Task (ECC1 / ECC2): Unterstützt das vollständige 4-Zustände-Modell inklusive Event-Handling (Waiting).

3. Dynamisches Verhalten & Sequenzablauf

Die Transitionen entsprechen konkreten OS-Systemaufrufen (APIs) oder internen Dispatcher-Ereignissen:

  • Activate (Suspended $\rightarrow$ Ready):
  • Trigger: API-Aufruf ActivateTask(TaskID), ChainTask(TaskID) aus anderem Task/ISR oder Ablauf eines Alarms (AlarmCallback / Counter-Aktion) bzw. einer ScheduleTable.
  • Verhalten: OS legt Task-Kontrollblock (TCB) in der Ready-Queue der konfigurierten Prioritätsebene ab. Bei Mehrfachaktivierung (BCC2/ECC2) inkrementiert das OS den Aktivierungszähler (bis OsTaskActivationOrder).
  • Start (Ready $\rightarrow$ Running):
  • Trigger: Scheduler-Entscheidung (Dispatchen).
  • Verhalten: Der Scheduler wählt den bereitstehenden Task mit der höchsten statischen Priorität. Kontextwechsel stellt Stack- und CPU-Register wieder her.
  • Preempt (Running $\rightarrow$ Ready):
  • Trigger: Asynchron (höherpriorisierter Task wird durch ISR/Event geweckt) oder synchron via Schedule() bei kooperativem/non-preemptive Scheduling.
  • Verhalten: Task-Kontext wird auf dem Task-Stack gesichert; Task verbleibt an vorderster Stelle seiner Prioritätsstufe in der Ready-Queue.
  • Wait (Running $\rightarrow$ Waiting):
  • Trigger: Synchroner Aufruf von WaitEvent(EventMask) durch den laufenden Extended Task.
  • Bedingung: Die übergebene Event-Maske ist aktuell nicht gesetzt ((CurrentEvents & Mask) == 0).
  • Verhalten: CPU-Freigabe, Kontext-Sicherung, Überführung in die Warteliste; Scheduler wählt neuen Ready-Task.
  • Release (Waiting $\rightarrow$ Ready):
  • Trigger: Asynchron via SetEvent(TaskID, Mask) durch einen anderen Task oder eine ISR (Kat. 2).
  • Verhalten: Treffen gesetzte und erwartete Events zusammen, überführt das OS den Task zurück in die Ready-Queue. Sofern die Priorität höher ist als die des aktuellen Tasks, erfolgt ein Rescheduling.
  • Terminate (Running $\rightarrow$ Suspended):
  • Trigger: Expliziter API-Aufruf TerminateTask() oder ChainTask(TaskID) am Ende der Task-Funktion.
  • Verhalten: Freigabe von internen OS-Strukturen, Rücksetzen des Ausführungszustands. Ein implizites Verlassen über das Funktionsende (return) ist im AUTOSAR OS unzulässig und führt zum OS-Error.

4. Normative Relevanz & Entwickler-Hinweise

  • Stack- und Speicher-Dimensionierung:
  • Basic Tasks können im OSEK/AUTOSAR OS einen gemeinsamen Stack nutzen (Single-Stack Architecture), da sie nicht blockieren können (Waiting existiert nicht).
  • Extended Tasks erfordern zwingend einen persistenten, dedizierten Stack, da der Zustand Waiting den lokalen Stack-Frame einfriert. Übermäßiger Einsatz führt zu signifikantem RAM-Overhead.
  • API-Einschränkungen & Fehler-Prävention (SWS OS):
  • WaitEvent() darf ausschließlich in Extended Tasks aufgerufen werden. Aufruf in Basic Tasks oder ISRs führt zu E_OS_CALLEVEL bzw. E_OS_ACCESS.
  • Vor Aufruf von TerminateTask() oder WaitEvent() müssen alle reservierten Standard-Ressourcen (GetResource()) und Spinlocks freigegeben sein. Verletzung triggert den ErrorHook mit E_OS_RESOURCE.
  • ARTI-Tracing & Debugging (AR_CP_OS_TASK):
  • Die Kanten des Automaten definieren die normativen Trace-Hooks für Timing-Messungen (Laufzeit, Latenz, Blockadezeiten).
  • Übergang Suspended $\rightarrow$ Ready bis Start misst die Task-Aktivierungslatenz (Response Time Jitter).
  • Verweildauer in Waiting quantifiziert Abhängigkeiten von externen Events / Inter-Runnable-Kommunikation via RTE.

Explanatory Document for Usage of AUTOSAR Run-Time Interface AUTOSAR CP R25-11 3 OS To achieve a vendor-independent interpretation of the run-time behavior of an AUTOSAR ECU, ARTI defines state machines. The transitions between these states indicate the OS scheduling at run-time. In other words, the state transitions can be understood as the implementation of the OS hooks. Each time an OS task is preempted by another task, for example, the ARTI hook macro indicates a OS task state transition. This has two advantages: software-based tracing can be used as well as Hardware Tracing, and the result is the same. 3.1 State Model The OS State Model, described in [1, CP-SWS-OS], is supported by ARTI. However, for a proper view with a timing tool, additional state information is necessary. Since there is no distinction between preempted, released, and activated OS task states in the standard model, an enhanced state machine is introduced. Depending on the features provided by the OS vendor, either the standard OS model can be used or the enhanced one for more detailed analysis. To distinguish between both state diagrams, the hook macro, and therefore the available state transitions, shall use a different state machine description (Class Name). The ARTI Class Name AR_CP_OS_TASK (see Figure 3.1) is to be used for the standard OS task states, and AR_CP_OSARTI_TASK (see Figure 3.2) for the enhanced state machine.
