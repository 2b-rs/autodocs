1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Ausschnitt als UML-Klassendiagramm (M2-Ebene) aus der AUTOSAR Software Component Template (TPS_SWCTemplate, Release R4.2.2).
  • Funktionale Einordnung: Definiert die formalen Diagnosedienst-Bedarfe (ServiceNeeds) einer Software-Komponente (SWC) gegenüber dem Diagnostic Event Manager (Dem) und Function Inhibition Manager (FiM).
  • Architekturzweck: Dient im Entwurfsprozess als maschinenlesbarer Vertrag (ARXML-Deklaration) zwischen Anwendungssoftware und Basissoftware (BSW). Anhand dieser Metaklassen generieren Konfigurationswerkzeuge die RTE-Ports, Service-Schnittstellen (DiagnosticMonitor, DiagnosticInfo, etc.) sowie die zugehörigen BSW-Konfigurationen (DemEventParameter, FiMFunctionId).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Vererbungshierarchie
  • SwcServiceDependency (Generalisiert von AtpStructureElement, Identifiable, ServiceDependency):
    • Aggregiert per Komposition optional ein ServiceNeeds-Element (+serviceNeeds 0..1).
  • ServiceNeeds (Abstrakt, erbt von Identifiable):
    • Basisklasse aller BSW-Dienstbedarfe einer SWC.
    • Spezialisiert sich direkt in:
      • FunctionInhibitionNeeds
      • DiagnosticCapabilityElement
  • DiagnosticCapabilityElement (Abstrakt, erbt von ServiceNeeds):
    • Zentrale Basisklasse für diagnosebezogene Servicebedarfe.
    • Attribute:
      • audience: DiagnosticAudienceEnum [0..*] (Zielgruppe der Diagnoseinformation).
      • diagRequirement: DiagRequirementIdString [0..1] (Referenz auf Spezifikations-/Anforderungs-ID).
      • securityAccessLevel: PositiveInteger [0..1] (Gefordertes Security-Level gemäß UDS $27).
Spezialisierungen von DiagnosticCapabilityElement
  1. DiagnosticEventNeeds (Spezifischer Event-Meldebedarf an den Dem):
    • Attribute:
      • prestoredFreezeframeStoredInNvm: Boolean [0..1] (Ablage vorübergehend gespeicherter Freeze-Frames im NvM).
      • usesMonitorData: Boolean [0..1] (Nutzung von Monitor-Daten bei der Fehlererfassung).
    • Assoziationen zu FunctionInhibitionNeeds:
      • +inhibitingSecondaryFid 0..*: Sekundäre FIDs, die durch dieses Event gehemmt werden.
      • +inhibitingFid 0..1: Primäre FID-Hemmung.
      • +deferringFid 0..*: FIDs, deren Testausführung verzögert wird, solange das Event aktiv gehemmt ist.
  2. DiagnosticEventInfoNeeds (Lesezugriff auf Event-Status ohne Entprellung/Meldung):
    • Attribute:
      • obdDtcNumber: PositiveInteger [0..1] (OBD-DTC-Codierung).
      • udsDtcNumber: PositiveInteger [0..1] (UDS-DTC-Codierung).
  3. DiagnosticEventManagerNeeds (Allgemeiner Verwaltungszugriff auf Dem-Funktionalitäten).
  4. DiagnosticEnableConditionNeeds (Bedingung zur Freigabe der Event-Entprellung/Fehlererfassung):
    • Attribut: initialStatus: EventAcceptanceStatusEnum [0..1] (eventAcceptanceEnabled, eventAcceptanceDisabled).
  5. DiagnosticStorageConditionNeeds (Bedingung zur Speicherung von Fehlern im FreezeFrame/NVRAM):
    • Attribut: initialStatus: StorageConditionStatusEnum [0..1] (eventStorageEnabled, eventStorageDisabled).
  6. DtcStatusChangeNotificationNeeds (Notification-Hook bei Löschung von DTC-Statusinformationen):
    • Attribut: notificationTime: DiagnosticClearDtcNotificationEnum [0..1] (start, finish).
  7. DiagnosticOperationCycleNeeds (Bedarf zur Definition und Steuerung eines Diagnose-Betriebszyklus):
    • Attribut: operationCycle: OperationCycleTypeEnum [0..1].
  8. WarningIndicatorRequestedBitNeeds (Bedarf bzgl. Anforderung von Warnanzeigen/MIL).
Enumerationen
  • OperationCycleTypeEnum: ignition, obdDcy, warmup, power, time, other.
  • DiagnosticClearDtcNotificationEnum: start, finish.
  • EventAcceptanceStatusEnum: eventAcceptanceEnabled, eventAcceptanceDisabled.
  • StorageConditionStatusEnum: eventStorageEnabled, eventStorageDisabled.

3. Dynamisches Verhalten & Sequenzablauf

Obwohl das Diagramm statische Metaklassen darstellt, leiten sich daraus deterministische Laufzeitpfade ab:

[SWC Monitor] ──SetEventStatus()──> [Dem] ──StatusChanged──> [FiM] ──Inhibition──> [SWC Function]
      │                                │
      ├──Enable/StorageCondition───────┤
      └──DTC Notification Callback <───┘
  • Event-Reporting-Pfad (Synchron/Asynchron):
    • SWC triggert via RTE SetEventStatus(EventStatus) am Port DiagnosticMonitor.
    • Ist reportBeforeInit konfiguriert, muss der Dem Event-Meldungen puffern, noch bevor der Dem-Vollbetrieb (Dem_Init) erreicht ist (z. B. Pre-OS- oder frühe Initialisierungsfehler).
  • Funktionshemmung (Dem → FiM Kopplung):
    • Erreicht ein Event den Status FAILED, evaluiert der Dem die hinterlegten Masken und informiert den FiM.
    • Der FiM blockiert über die zugeordneten FIDs (inhibitingFid, inhibitingSecondaryFid) abhängige Software-Funktionen (Abfrage über FiM_GetFunctionPermission()).
    • deferringFid unterdrückt die Testausführung anderer Diagnosen, um Fehlalarme bei instabilen Systemzuständen (z. B. Unterspannung) zu verhindern.
  • Enable- & Storage-Conditions:
    • SWCs steuern über Service-Ports Freigaben ein (Dem_SetEnableCondition, Dem_SetStorageCondition). Deaktivierte Enable-Conditions frieren die Fehlerentprellung ein; deaktivierte Storage-Conditions verhindern NVRAM-Einträge trotz aktivem Fehlersetzens.

4. Normative Relevanz & Entwickler-Hinweise

  • SWC-Entwickler (Contract Phase):
    • DiagnosticEventNeeds erzwingt die Deklaration von Ports mit DiagnosticMonitor-Schnittstelle. Fehlt das Element, darf die RTE keine typisierten Diagnoseschnittstellen generieren.
    • Unterscheidung zwischen DiagnosticEventNeeds (aktives Melden mit Debouncing) und DiagnosticEventInfoNeeds (reines passives Abfragen via DiagnosticInfo).
  • BSW- & Integrations-Ingenieure (ECU Configuration):
    • Mapping: Jedes DiagnosticEventNeeds muss auf genau einen DemEventParameter in der BSW-Konfiguration abgebildet werden. DTC-Nummern (udsDtcNumber, obdDtcNumber) im SWC-D dienen als Vorgabe für den BSW-Integrator zur Konsistenzprüfung.
    • FiM-Integration: Die Rollen inhibitingFid, inhibitingSecondaryFid und deferringFid determinieren direkt die Parametrierung der FiMInhibitionConfiguration (LAST_FAILED, NOT_TESTED, etc.).
    • Initialisierungsreihenfolge: Wird reportBeforeInit verwendet, muss der BSW-Stack (Dem-Puffer) so ausgelegt sein, dass Aufrufe vor Dem_Init() nicht in Det-Fehlern (DEM_E_UNINIT) enden.
  • Einschränkungen:
    • Metamodell-Toleranz: Der Bezeichner nonEmmissionRelatedDtc enthält den AUTOSAR-spezifischen Typo (Doppel-m) im Standard-Enum und muss exakt so in ARXML-Serialisierungen verwendet werden.
