  • Spezifikation des Systemtests STS_TS_00005 im Rahmen der AUTOSAR Adaptive Platform (AUTOSAR_AP_TR_SystemTests).
  • Verifikation des Time Synchronization Clusters (ara::ts) bei verteilter Zeitsynchronisation über Netzwerkgrenzen (z. B. Ethernet/PTP, CAN-TSyn).
  • Spezifischer Testfokus: Validierung einer Offset Time Base (Offset TB) zwischen Master- und Slave-Knoten, inklusive:
  • Propagation von anwenderspezifischen Zusatzdaten (User Data) im Synchronisationsrahmen.
  • Absoluter Zeitinitialisierung über SetTime.
  • Relativer Zeitanpassung über UpdateTime.

  • Automatisierte Ergebnisvalidierung über ein Continuous-Integration-Framework.

2. Komponenten, Entitäten & Schnittstellen

  • ECU1 (Time-Slave-Knoten):
  • APP1: Adaptive Test-Applikation auf ECU1. Konsumiert die synchronisierte Zeitbasis und empfängt Referenzwerte von APP2.
  • Offset Slave TB: Instanz der synchronisierten Offset-Zeitbasis (ara::ts) im Plattform-Stack von ECU1.
  • ECU2 (Time-Master-Knoten):
  • APP2: Adaptive Test-Applikation auf ECU2. Initiiert Zeit- und User-Data-Modifikationen und dient als Referenzgeber.
  • Offset Master TB: Instanz der Master-Offset-Zeitbasis (ara::ts) auf ECU2. Generiert und versendet die Zeitsynchronisationsnachrichten.
  • Jenkins (CI/CD-Testumgebung):
  • TS Tester: Automatisierter Test-Runner / Test-Harness zur Orchestrierung und Ergebnisabfrage.
  • Schnittstellen & Interaktionspfade:
  • ara::ts API (Applikation ↔ Zeitbasis):
  • Set User Data / Get User Data
  • Get Time Base Status
  • Set Global Time by SetTime
  • Set Global Time by UpdateTime
  • Get current time
  • Netzwerkprotokoll (Offset Master TB ↔ Offset Slave TB): Send Timesync messages to ECU1 (unterlagerte Bus-PDUs, z. B. IEEE 802.1AS / gPTP oder AUTOSAR TimeSync-PDUs).
  • Inter-ECU Applikationskanal (APP2 ↔ APP1): z. B. via ara::com zur Übermittlung von Sollwerten und Synchronisations-Handshakes.
  • Test-Automation-Interface (TS Tester ↔ APP1/APP2): Synchrones Polling/Abfragen von Testergebnissen (Check results... / Return results).

3. Dynamisches Verhalten & Sequenzablauf

#### Phase 1: User-Data-Konfiguration & Absolute Zeiteinstellung (SetTime)

  1. [step 6] APP2 setzt anwenderspezifische Nutzdaten auf dem Master (Offset Master TB::Set User Data).
  2. [step 7] APP2 fragt den Status der Master-Zeitbasis ab (Get Time Base Status) und empfängt den Zustand.
  3. [step 8] APP2 verifiziert lokal die gesetzten User Data (Get User Data).
  4. [step 9] APP2 setzt die globale Zeit absolut (Set Global Time by SetTime).
  5. Netzwerk-Event: Offset Master TB sendet TimeSync-Nachrichten an Offset Slave TB auf ECU1.
  6. [step 10] APP2 fragt die aktuelle Zeit auf dem Master ab (Get current time).
  7. [step 11] & [step 12] APP2 sendet die Soll-Zeit aus Schritt 9 sowie die User Data aus Schritt 6 an APP1 und wartet auf Quittierung; APP1 empfängt die Referenzdaten.
  8. [step 13] – [step 15] APP1 fragt auf ECU1 den Status der Slave-Zeitbasis ab (Get Time Base Status), validiert die übertragenen User Data (Get User Data) und liest die synchronisierte Zeit (Get current time).

#### Phase 2: Relative Zeitkorrektur (UpdateTime)

  1. [step 16] APP2 passt die Zeitbasis inkrementell/relativ an (Set Global Time by UpdateTime).
  2. [step 17] APP2 liest die aktualisierte Master-Zeit aus (Get current time).
  3. [step 18] & [step 19] APP2 übermittelt den neuen Zeitstempel an APP1; APP1 blockiert/wartet, bis die Aktualisierung über den TimeSync-Stack wirksam wird.
  4. Netzwerk-Event: Offset Master TB übermittelt neue TimeSync-Nachrichten an Offset Slave TB.
  5. [step 20] APP1 liest nach erfolgtem Update die neue Zeit vom Slave aus (Get current time).

#### Phase 3: Ergebnisvalidierung durch Test-Harness

  1. TS Tester fragt synchron die Testergebnisse von APP2 ab (Check results of [APP2] / Return results).
  2. TS Tester fragt synchron die Testergebnisse von APP1 ab (Check results of [APP1] / Return results) zur Verifikation von Offset-Drift, Jitter-Grenzwerten und Statusflags.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Semantik (SetTime vs. UpdateTime):
  • SetTime erzwingt einen absoluten Zeitsprung der Offset-Zeitbasis. Entwickler müssen beachten, dass hierbei Statusflags (z. B. Sprungdetektion/Diskontinuität) gesetzt werden können.
  • UpdateTime dient der stetigen oder offsetbasierten Nachführung. Der Stack muss sicherstellen, dass beide Methoden unverzüglich die Generierung bzw. Aktualisierung ausgehender TimeSync-PDUs veranlassen.
  • User Data Handling:
  • User Data werden Huckepack im TimeSync-Frame transportiert. Der Slave-Stack muss sicherstellen, dass geänderte User Data synchron mit dem zugehörigen Zeitstempel im Slave-Kontext (Get User Data) bereitgestellt werden, ohne Race Conditions zwischen Zeitbasis-Update und Datenbyte-Extraktion.
  • Asynchronität & Latenzüberwachung:
  • Zwischen SetTime/UpdateTime am Master und der Verfügbarkeit am Slave liegt eine deterministische Latenz (Buszyklus, Sync-Intervall, Filterzeit des Slaves). Applikationen dürfen Messwerte erst nach Verifikation des Time Base Status (z. B. Flag SYNC_TO_GATEWAY bzw. äquivalenter AP-Synchronisationsstatus) als zeitsynchron werten (ersichtlich an der Wartebedingung in Schritt 19).
  • Testautomatisierbarkeit:
  • Für HIL-/Systemtests im AUTOSAR-Umfeld müssen Testapplikationen standardisierte Diagnose- oder Kommunikations-Endpunkte bereitstellen, über die CI-Server (Jenkins) Pass/Fail-Kriterien, Zeitabweichungen und Statusregister deterministisch extrahieren können.
