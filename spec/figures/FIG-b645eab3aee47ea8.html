1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Klassendiagramm (UML 2.0 Profil für AUTOSAR XML / MSR-FIBEX-Kompatibilität).
  • Paket / Modellbereich: AUTOSAR_SystemTemplate::FibexCore::Communication (Release-Stand AUTOSAR Classic R3.0.7 / R3.1.5).
  • Architektur-Kontext:
  • Vertikale Gliederung des Kommunikations-Metamodells in drei funktionale Schichten:
  1. Application Layer: Signal-Definitionen auf VFB-/Softwarekomponenten-Ebene (SystemSignal, SystemSignalGroup).
  2. Interaction & Network Layer: Netzwerk- und PDU-Abstraktion (COM-Stack, PduR, NM, DCM; Signal-zu-PDU-Serialisierung, PDU-Typisierung, PDU-Gruppen, ECU-Instanz-Zuordnung).
  3. Data Link Layer: Physische Busabstraktion (Bus-Frames, PDU-zu-Frame-Verschachtelung, Timing-Vorgaben sowie Frame-/PDU-/Signal-Triggering auf PhysicalChannel).
  • Funktionaler Zweck: Formale Beschreibung des Signal- und PDU-Flusses vom anwendungsnahen Signal über die PDU-Kapselung bis zur physikalischen Übertragung im Kommunikationsnetzwerk (CAN, LIN, FlexRay). Bildet die autoritative Eingangsbasis für AUTOSAR-System- und ECU-Generatoren (z. B. Generierung von Com-, PduR- und Bus-Interface-Konfigurationen).

2. Komponenten, Entitäten & Schnittstellen

#### Schichten & Enthaltene Klassen

##### A. Application Layer

  • AbstractSignal (abstrakte Basisklasse, Stereotyp ARElement):
  • Abstrakter Vorgänger für anwendungsbezogene Signale.
  • SystemSignal (Spezialisierung von AbstractSignal):
  • Repräsentiert das anwendungsnahe Datum / Signal.
  • Attribut: + length: Int (Signalbreite in Bits).
  • SystemSignalGroup (Spezialisierung von AbstractSignal):
  • Aggregation zusammengehöriger atomarer Signale zur Gewährleistung von Signal-Konsistenz.
  • Aggregation: +systemSignal * $\rightarrow$ SystemSignal.

##### B. Interaction & Network Layer

  • ISignal (Stereotyp FibexElement):
  • Interaction-Layer-Signal (Repräsentant des SystemSignal im Kommunikations-Stack).
  • Assoziation: +systemSignal 1 $\rightarrow$ AbstractSignal (Kardinalität 1..* an ISignal).
  • ISignalToIPduMapping (Stereotyp Identifiable):
  • Definiert das Packing/Serialisieren eines ISignal in eine SignalIPdu.
  • Attribute:
  • + packingByteOrder: ByteOrderEnum (Endianness: MOST-SIGNIFICANT-BYTE-FIRST / LEAST-SIGNIFICANT-BYTE-FIRST).
  • + startPosition: Int [0..1] (Bit-Offset innerhalb der PDU).
  • + transferProperty: TransferPropertyEnum (z. B. TRIGGERED, PENDING, TRIGGERED_ON_CHANGE).
  • + updateIndicationBitPosition: Int [0..1] (Position des Update-Bits zur Validierung neuer Nutzdaten).
  • Assoziationen:
  • Referenziert +signal 1 $\rightarrow$ ISignal (Kardinalität 1..* an Mapping).
  • Komposition durch SignalIPdu via +signalToPduMapping 0..*.
  • Pdu (abstrakte Basisklasse, Stereotyp FibexElement):
  • Generische Protocol Data Unit.
  • IPdu (Spezialisierung von Pdu):
  • Interaktions-PDU (Basis für COM/PduR-Verarbeitung).
  • Attribute:
  • + length: Int (Länge in Bytes).
  • + unusedBitPattern: Int [0..1] (Auffüllmuster für ungenutzte Bits).
  • Spezialisierungen von IPdu:
  • SignalIPdu: Standard-PDU des AUTOSAR COM, enthält ISignalToIPduMapping (0..*).
  • MultiplexedIPdu: Unterstützt PDU-Multiplexing über dynamische Selektoren.
  • Attribute: + selectorFieldByteOrder: ByteOrderEnum, + selectorFieldLength: Int, + selectorFieldStartPosition: Int, + triggerMode: TriggerMode.
  • DcmIPdu: Diagnose-PDU für UDS/KWP-Kommunikation via DCM.
  • NPdu: Transport-Layer-PDU (z. B. für CanTp / FrTp Segmentierung).
  • NmPdu (Spezialisierung von Pdu):
  • Netzwerkmanagement-PDU (Autosar NM).
  • Attribute:
  • + length: Int
  • + nmCbvPosition: Int [0..1] (Position des Control Bit Vector).
  • + nmNidPosition: Int [0..1] (Position der Node Identifier).
  • + nmUserDataLength: Int [0..1] (Länge der nutzbaren NM-Nutzdaten).
  • IPduGroup (Stereotyp FibexElement):
  • Gruppiert IPdus für gemeinsame Steuerung (Start/Stop via COM API).
  • Attribute:
  • + communicationDirection: communicationDirectionType (IN / OUT).
  • + communicationMode: String.
  • Assoziationen:
  • Rekursive Aggregation: +containedIPduGroups 0..* (Hierarchie von PDU-Gruppen).
  • Referenz auf SignalIPdu: +iPdu 0.. (Kardinalität 1.. an IPduGroup).
  • CoreTopology::EcuInstance (Stereotyp FibexElement):
  • Repräsentation des Steuergeräts im Netzwerk.
  • Attribute:
  • + comConfigurationId: Int [0..1], + comProcessingPeriod: Float (zyklischer COM-Task-Tick).
  • + diagnosticAddress: Int [0..1], + pduRConfigurationId: Int [0..1].
  • + responseAddress: Int [0..*], + sleepModeSupported: Boolean, + wakeUpOverBusSupported: Boolean.
  • Assoziation: 1 $\rightarrow$ +associatedIPduGroup * (Zuordnung konfigurierter PDU-Gruppen zu einer ECU).

  • Busspezifischer physikalischer Datenrahmen (CAN-Message, FlexRay-Frame, LIN-Frame).
  • Attribut: + frameLength: Int (Länge in Bytes, z. B. max. 8 Byte für Classic CAN, 64 Byte für FlexRay/CAN FD).
  • Komposition: Enthält +pduToFrameMapping 0..*.
  • PduToFrameMapping (Stereotypen Identifiable, «atpPrototype»):
  • Platziert PDUs in Frames (Mehrfachkapselung / PDU-Container / Gateways).
  • Attribute:
  • + packingByteOrder: ByteOrderEnum.
  • + startPosition: Int (Bit-Offset des PDU-Payloads im Frame).
  • + updateIndicationBitPosition: Int [0..1].
  • Assoziation: +pdu 1 $\rightarrow$ Pdu (Kardinalität 1..* an Mapping).
  • IPduTiming:
  • Timing-Anforderungen für die PDU-Aussendung auf dem Bus.
  • Attribut: + minimumDelay: Float [0..1] (Mindestabstand zwischen zwei Sendevorgängen / Transmission Deadline Monitoring / MinDelayTimer).
  • Assoziation: +timingRequirement 0..1 $\rightarrow$ IPduTriggering.
  • Triggering-Klassen auf dem physischen Kanal:
  • CoreTopology::PhysicalChannel (Stereotyp Identifiable): Physischer Kommunikationskanal (z. B. CAN-Cluster-Kanal). Besitzt per Komposition mit Stereotyp «splitable»:
  • +iSignalTriggering 0..* $\rightarrow$ ISignalTriggering.
  • +iPduTriggering 0..* $\rightarrow$ IPduTriggering.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die statische Konfigurationsbasis für folgende Laufzeit-Sequenzen im AUTOSAR BSW-Stack:

```

[SW-C / RTE]

│ (Write SystemSignal / SystemSignalGroup)

▼

[AUTOSAR COM]

│ 1. ISignalToIPduMapping: Packing in SignalIPdu (Startpos, Endianness)

│ 2. Setzen von updateIndicationBitPosition

│ 3. Auswertung TransferProperty (TRIGGERED -> Sendeanforderung; PENDING -> Warten auf Zyklus)

│ 4. Validierung IPduTiming (minimumDelay Prüfen / MinDelayTimer)

│ 5. PduR_ComTransmit(SignalIPduId)

▼

[PDU Router (PduR)]

│ 6. Routing der IPdu zu Interface-Modul (z. B. CanIf, FrIf, LinIf)

▼

[Bus Interface / Driver (CanIf / FlexRay)]

│ 7. PduToFrameMapping / FrameTriggering: Zusammenbau des Frame-Payloads

│ 8. Zuordnung zu Mailbox / Hardware Transmit Handle via PhysicalChannel-Konfiguration

│ 9. Physikalische Bus-Transmission

```

  • Dynamische Steuerung über IPduGroup:
  • Start/Stopp von Kommunikationspfaden zur Laufzeit über Com_IpduGroupStart() bzw. Com_IpduGroupStop(), gesteuert durch den ComM (Communication Manager) anhand des Netzwerkzustands (Full Comm / Silent / No Comm).
  • Multiplexing-Pfad (MultiplexedIPdu):
  • selectorFieldStartPosition bestimmt das dynamische Switch-Feld. Je nach Wert werden alternative Signallayouts in denselben PDU-Payload gemappt.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfigurationsgenerierung (Com, PduR, CanIf/FrIf, CanNm):
  • Parameter wie comProcessingPeriod definieren direkt die zyklische Task-Periode für Com_MainFunctionTx() / Com_MainFunctionRx().
  • unusedBitPattern (z. B. 0xFF oder 0xAA) wird von COM-Generatoren in die Initialisierungs-Buffer eincodiert, um deterministisches Busverhalten zu gewährleisten.
  • Endianness- und Alignment-Fallen:
  • packingByteOrder: Bei LEAST-SIGNIFICANT-BYTE-FIRST (Intel) vs. MOST-SIGNIFICANT-BYTE-FIRST (Motorola) muss die Adressierung von startPosition exakt dem AUTOSAR-Bitnummerierungsschema (Bit 0 = LSB vs. MSB) entsprechen; Diskrepanzen führen zu Signal-Korruption beim Byte-Packing.
  • Update-Bit-Verarbeitung:
  • Wenn updateIndicationBitPosition gesetzt ist, generiert COM senderseitig das Setzen des Bits vor dem Senden und empfängerseitig die Prüfung. Fehlt das Bit beim Empfang, wird der Wert vom COM-Stack verworfen und kein RTE-Indication-Callback ausgelöst.
  • Filterung & Mindestverzögerung (minimumDelay):
  • Schützt den Bus vor Überlast bei Burst-Ereignissen (transferProperty: TRIGGERED). Der Generator konfiguriert den Parameter ComMinimumDelayFactor.
  • Splitable-Metaklassen («splitable»):
  • Die Kompositionen von PhysicalChannel zu ISignalTriggering, IPduTriggering und FrameTriggering sind «splitable». Das bedeutet für Tool-Entwickler: Diese Zuordnungen können auf mehrere ARXML-Dateien aufgeteilt sein (z. B. System-Description vs. ECU-Extract), ohne die Gültigkeit des Metamodells zu verletzen.
