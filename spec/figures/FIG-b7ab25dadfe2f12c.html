1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Service-Interface-Modell (AUTOSAR Adaptive Service Interface Definition nach ara::com-Semantik).
  • Technischer Zweck: Spezifikation der Schnittstelle VehicleStateManagerInterface des Funktionsclusters Vehicle Update and Configuration Management (VUCM).
  • Funktionale Einordnung: Dient der sicherheitskritischen Koordination zwischen dem Update-Orchestrator (VUCM, Subkomponente VSM / Vehicle State Manager Interface) und dem fahrzeugweiten Zustandsmanagement (Vehicle State Manager). Stellt sicher, dass Software-Transfers, Flash- und Aktivierungsvorgänge (OTA) nur dann initiiert bzw. vollzogen werden, wenn sich das Gesamtfahrzeug in einem definierten, sicheren Zustand befindet (z. B. Stillstand, Zündung aus, Parkbremse aktiv).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Komponenten
  • Vehicle State Manager: Externer Service-Consumer (Client), der den fahrzeugweiten Gesamtzustand aggregiert und über eine «use»-Beziehung an die Service-Schnittstelle der VUCM angebunden ist.
  • «service» VUCM: Service-Provider (Server). Kapselt die Update-Logik und stellt über den logischen Port VSM die Schnittstelle VehicleStateManagerInterface bereit. Weitere Ports:
    • VPM (Vehicle Package Manager – Paketbehandlung/Distribution).
    • VDI (Vehicle Driver Interface – Interaktion mit Fahrer/HMI).
Service-Schnittstelle (VehicleStateManagerInterface)
  • Vollständiger Namensraum: Vehicle::ECU::Machine::AUTOSAR Adaptive Platform::VUCM::VSM::VehicleStateManagerInterface (Anforderung: SWS_VUCM_00183).
  • Felder / Events:
    • + CampaignState: CampaignStateType: Überträgt den aktuellen Fortschritt/Zustand der Update-Kampagne.
    • + VehicleConditionCollection: VehicleConditionCollectionType: Satz der für die aktuelle Phase definierten Sicherheitsbedingungen.
  • Methoden:
    • + PublishSafetyState(VehicleConditionCollectionType): void: Übermittelt die vom Vehicle State Manager verifizierten Sicherheitszustände zurück an die VUCM.
    • + VehicleCheck(bool): void: Triggert bzw. quittiert fahrzeugspezifische Vorabprüfungen (Pre-Check-Status).
Datenstrukturen, Typen & Kardinalitäten
  • «enumeration» CampaignStateType (SWS_VUCM_01177):
    • Literale (literals):
      • kIdle = 0x00: Keine aktive Kampagne.
      • kSyncing = 0x01: Synchronisation mit Backend/Speichern.
      • kVehiclePackageTransferring = 0x02: Transfer des Gesamtfahrzeug-Pakets.
      • kSoftwarePackageTransferring = 0x03: Transfer zu Ziel-Steuergeräten.
      • kProcessing = 0x04: Aufbereitung/Entpacken/Pre-Installation.
      • kActivating = 0x05: Sicheres Umschalten/Aktivieren (Reboot/Partition Switch).
      • kVehicleChecking = 0x06: Pre-/Post-Update-Fahrzeugdiagnose.
      • kCancelling = 0x07: Abbruch/Rollback der Kampagne.
  • «dataType» VehicleConditionCollectionType (SWS_VUCM_01309):
    • Aggregation (1..n): vehicleConditionCollection: VehicleConditionType [1..n].
  • «dataType» VehicleConditionType (SWS_VUCM_01310):
    • Verbund aus:
      • condition: SafetyConditionType (Prüfkriterium).
      • safetyState: SafetyStateType (Zugehörige Sicherheitsbewertung).
  • «primitive» SafetyConditionType (SWS_VUCM_01114):
    • Plattform-spezifischer Identifikator für die auszuwertende Sicherheitsbedingung (z. B. String-Token oder numerische Kennung).
  • «enumeration» SafetyStateType (SWS_VUCM_01138):
    • Literale (literals):
      • Safe = 0x00: Bedingung strikt erfüllt, Update zulässig.
      • NotSafe = 0x01: Bedingung verletzt, Phase muss blockiert/abgebrochen werden.
      • NotSupported = 0x02: Steuergerät/Fahrzeug kann Bedingung nicht bewerten.

3. Dynamisches Verhalten & Sequenzablauf

  1. Phasen-Initialisierung: VUCM aktualisiert bei Phasenwechsel das Feld CampaignState (z. B. Wechsel von kIdle auf kProcessing oder kActivating).
  2. Kriterien-Definition: VUCM setzt über das Feld/Event VehicleConditionCollection die Liste der zu prüfenden Bedingungen (SafetyConditionType) für die jeweilige Phase.
  3. Zustandsprüfung (Trigger & Evaluation):
    • Der Vehicle State Manager reagiert auf Event-Notifikationen oder ruft via VehicleCheck(bool) den Initialstatus ab.
    • Der Vehicle State Manager bewertet jede geforderte Bedingung gegen die fahrzeugeigene Sensorik/Bussignale (z. B. ESP-Raddrehzahl = 0, Getriebestufe = P, Batterieladezustand ausreichend).
  4. Rückmeldung (Asynchron/Event):
    • Aufruf von PublishSafetyState(VehicleConditionCollectionType) durch den Client. Jede VehicleConditionType-Instanz ist nun mit Safe, NotSafe oder NotSupported annotiert.
  5. Entscheidung & Abbruchbedingungen:
    • Liefert mindestens eine zwingende Bedingung NotSafe oder NotSupported, verbleibt VUCM in Wartehaltung oder leitet über kCancelling den Kampagnenabbruch ein (Safety Gate).
    • Nur wenn alle geforderten Bedingungen Safe melden, schaltet VUCM in den geschützten Ausführungspfad (kProcessing / kActivating).

4. Normative Relevanz & Entwickler-Hinweise

  • ara::com-Mapping & Code-Generierung:
    • Die Schnittstelle wird im AUTOSAR-Modell als ServiceInterface modelliert.
    • Der Methodenaufruf PublishSafetyState ist typischerweise Fire-and-Forget (void Rückgabetyp ohne Output-Argumente) oder generiert ein ara::core::Future<void>, das asynchron aufgelöst wird.
    • CampaignState und VehicleConditionCollection erfordern Deployment als ara::com::Field (inkl. HasGetter und HasNotifier).
  • ASIL- & ISO 26262-Einstufung:
    • Dieses Interface bildet das primäre Interlock zur Vermeidung von Fehlaktivierungen während der Fahrt. Die Implementierung des Vehicle State Manager-Clients unterliegt typischerweise ASIL-B oder ASIL-D-Anforderungen.
  • Eigenheiten & Stolperfallen bei der Integration:
    • Bezeichner-Korrektur: Der vormalige Schreibfehler im Bezeichner kVehiclePackageTransferring (SWS_VUCM_01177) wurde auf die reguläre Schreibweise mit zwei „r“ bereinigt; bei Migrationen von R23-11 ist die geänderte Benennung in generierten Headern (ara::vucm::vsm::CampaignStateType) zu berücksichtigen.
    • Kardinalität 1..n: VehicleConditionCollectionType bildet einen dynamischen Container (ara::core::Vector). Auf speicherbegrenzten Adaptive-Instanzen sind statische Allokatoren (ara::core::Array) bzw. konfigurierte Obergrenzen für Serialisierungspuffer (SOME/IP-Payload-Größe) zu beachten.
