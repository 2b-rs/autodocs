1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration (ECUC) Metamodell-Ausschnitt (UML-Klassendiagramm zur Parameter- und Referenzdefinition).
  • Technischer Zweck: Konfiguration der kryptografischen Schnittstelle zwischen dem Transport Layer Security (TLS)-Submodul des BSW-Moduls TcpIp und dem Crypto Service Manager (Csm).
  • Funktionale Einordnung: Spezifiziert die Zuordnung der für den TLS-Handshake (Schlüsselaustausch, Zertifikatsprüfung, PRF-Berechnung, Integritätssicherung) benötigten kryptografischen Operationen auf konkrete CsmJob-Instanzen im Crypto-Stack (Csm → CryIf → Crypto-Treiber/HSM).

2. Komponenten, Entitäten & Schnittstellen

Container & Basis-Entitäten
  • TcpIpTlsHandshake (EcucParamConfContainerDef):
    • Kardinalität: 1..* (mindestens eine Handshake-Konfiguration pro TLS-Instanz/Verbindungskonfiguration erforderlich).
Parameter (Enumerationen)
  • TcpIpTlsCsmPRFSupportType (EcucEnumerationParamDef):
    • Kardinalität: 0..1 (optional).
    • Definiert die Auslagerung und das Betriebsmodell der TLS Pseudorandom Function (PRF) an den CSM.
    • Literale (EcucEnumerationLiteralDef):
      • TLS_PRF_CSM_FULL_SUPPORT: Die vollständige PRF-Berechnung wird als nativer CSM-Job ausgeführt.
      • TLS_PRF_CSM_INOUT_REDIRECT_SUPPORT: CSM unterstützt PRF mit Ein-/Ausgabe-Redirection (z. B. Key-Derivation direkt in Key-Elemente).
      • TLS_PRF_CSM_NO_SUPPORT / TLS_PRF_NO_SUPPORT: Keine native PRF-Unterstützung im CSM; die PRF wird im TCP/IP-Stack softwareseitig abgewickelt (unter Nutzung elementarer Hash/MAC-Jobs).
Referenzen (EcucReferenceDef → Ziel: CsmJob [1..*] aus Paket Csm)

Alle Referenzen fordern requiresSymbolicNameValue = true zur compile-/linkzeitfesten Auflösung von Symbolbezeichnern.

  • Mandatorische Jobs (Kardinalität 1..1):
    • TcpIpTlsCsmPrfMacJobRef: Referenz auf den CsmJob zur MAC-/HMAC-Generierung innerhalb der PRF.
    • TcpIpTlsCsmHashVerifyJobRef: Referenz auf den CsmJob zur Verifikation von Hashes (z. B. Finished-Nachrichten, Transcript-Hashing).
  • Optionale Jobs (Kardinalität 0..1, abhängig von der konfigurierten Cipher Suite):
    • Schlüsselaustausch & Public Key:
      • TcpIpTlsCsmKeyExchangeCalcPubValJobRef: Berechnung des eigenen öffentlichen Schlüssels (z. B. Ephemeral Diffie-Hellman / ECDH Public Key).
      • TcpIpTlsCsmKeyExchangeCalcSecretJobRef: Berechnung des gemeinsamen Geheimnisses (Pre-Master Secret via DH/ECDH Shared Secret).
    • Authentifizierung & Signaturen:
      • TcpIpTlsCsmKeyExchangeSignatureGenerateJobRef: Erzeugung von Signaturen (Client Authentication / CertificateVerify).
      • TcpIpTlsCsmKeyExchangeSignatureVerifyJobRef: Verifikation der Gegenstellen-Signatur (Server Key Exchange / Zertifikatsprüfung).
    • Asymmetrische Verschlüsselung (z. B. RSA-Handshake):
      • TcpIpTlsCsmKeyExchangeEncryptJobRef: Asymmetrische Verschlüsselung des Pre-Master Secrets (RSA Client Key Exchange).
      • TcpIpTlsCsmKeyExchangeDecryptJobRef: Entschlüsselung des empfangenen Pre-Master Secrets (serverseitiger RSA-Handshake).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm selbst bildet eine statische Daten-/Konfigurationsstruktur ab. Das daraus resultierende Laufzeitverhalten während der TLS-Handshake-Phase ist folgendes:

  1. ClientHello / ServerHello Negotiation: Auswahl von Cipher Suite und Key Exchange-Verfahren bestimmt, welche der konfigurierten CsmJob-Referenzen getriggert werden.
  2. Asynchrone/Synchrone Job-Ausführung:
    • Der TCP/IP-Stack triggert Operationen über Csm_JobKeyExchangeCalcPubVal(), Csm_JobKeyExchangeCalcSecret(), Csm_JobHashVerify(), etc.
    • Je nach Konfiguration des referenzierten CsmJob (CsmJobSyncVerify = TRUE/FALSE) erfolgt die Abarbeitung synchron im Kontext der TcpIp_MainFunction() oder asynchron via Callback (Csm_CallbackNotification).
  3. Fehlerpfade:
    • Scheitert ein CSM-Job (z. B. Signaturprüfung schlägt fehl, Krypto-Hardware ausgelastet oder Key-ID ungültig), bricht der TLS-Handshake via fataler Alert-PDU ab; die TCP-Verbindung wird geschlossen.
    • Parameter- oder Referenzierungsfehler bei unvollständiger Cipher-Suite-Abdeckung führen zu DET-Fehlern bei der Stack-Initialisierung bzw. beim Verbindungsaufbau.

4. Normative Relevanz & Entwickler-Hinweise

  • Cipher-Suite-Konsistenz: Die Konfiguration von TcpIpTlsHandshake muss strikt auf die in TcpIpTlsCipherSuite aktivierten Suites abgestimmt sein. Wird beispielsweise eine ECDHE-Suite konfiguriert, müssen TcpIpTlsCsmKeyExchangeCalcPubValJobRef und TcpIpTlsCsmKeyExchangeCalcSecretJobRef instanziiert und gültigen CSM-Jobs zugeordnet sein, obwohl ihre Metamodell-Kardinalität syntaktisch 0..1 ist.
  • CSM-Job-Konfiguration:
    • Jeder referenzierte CsmJob muss im Csm-Modul mit den passenden primitiven Algorithmen (CsmPrimitive), Schlüssellängen und Kanälen parametriert werden.
    • Synchronizität beachten: Werden asynchrone HSM-Jobs referenziert, muss der TLS-Zustandsautomat im TcpIp-Stack auf entsprechende CSM-Callbacks warten können (nicht-blockierendes State-Polling in TcpIp_MainFunction()).
  • Schlüssel-Kapselung & Security:
    • Durch Nutzung von TLS_PRF_CSM_FULL_SUPPORT oder TLS_PRF_CSM_INOUT_REDIRECT_SUPPORT verbleiben sensible Key-Materialien (Pre-Master Secret, Master Secret, abgeleitete Session Keys) vollständig innerhalb gesicherter Speicherbereiche (Crypto Key Storage / HSM) und werden nicht im flüchtigen RAM des Host-Cores exponiert.
