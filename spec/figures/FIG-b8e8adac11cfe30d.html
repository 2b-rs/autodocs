1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Entscheidungsbaum / Flussdiagramm (UML Activity / Decision Tree) zur Darstellung deterministischer Ausführungs- und Verzweigungslogik.
  • Architektur-Kontext: AUTOSAR Adaptive Platform (AP), Functional Cluster State Management (SM) (AUTOSAR_AP_SWS_StateManagement, Kapitel 7 / Aktionen).
  • Funktionaler Zweck: Festlegung der normativen Ablaufsemantik für die Aktion StartStateMachine (SWS_SM_00601, SWS_SM_00614 ff.). Das Diagramm definiert, wie State Management das Starten bzw. Umschalten einer internen/externen Zustandsmaschine handhabt – in Abhängigkeit vom aktuellen Ausführungsstatus (running vs. not running) und dem Vorhandensein eines optionalen Zielzustands-Parameters (parameter).

2. Komponenten, Entitäten & Schnittstellen

  • Aktions-/Einstiegsknoten:
  • StartStateMachine: Auszuführende Aktion innerhalb einer SM-Aktionsliste (ActionList), typischerweise getriggert durch die Auswertung logischer Bedingungen (Rule Evaluation, RS_SM_00001, RS_SM_00005).
  • Entscheidungsknoten (Decision Diamonds):
  • Status-Prüfung: Evaluierung des aktuellen Laufzeitstatus der adressierten StateMachine (StateMachine not running vs. StateMachine running).
  • Parameter-Prüfung: Prüfung auf Vorhandensein eines Zielzustandsarguments (No parameter vs. parameter).
  • Endzustände / Folgeaktionen (Leaf Nodes):
  • Start StateMachine; Enter state : Init: Instanziierung/Aktivierung der Zustandsmaschine und Übergang in den statisch konfigurierten Initialzustand (Init, SWS_SM_00615).
  • Start StateMachine; Enter state: parameter: Instanziierung/Aktivierung und direkter Eintritt in den übergebenen Zielzustand (parameter, SWS_SM_00620).
  • No action: Idempotentes Verhalten; Vermeidung redundanter Re-Initialisierungen (SWS_SM_00621).
  • Enter state: parameter: Ausführung einer regulären Zustandstransition innerhalb der bereits aktiven Maschine auf den Zielzustand (SWS_SM_00623).
  • Metamodell-Bezug: Adressiert ARXML-Elemente wie StateMachine, StateMachineState, ActionList, StateTransition und korreliert funktional mit dem ara::exec::StateClient (bzw. Function Group States über Execution Management).

3. Dynamisches Verhalten & Sequenzablauf

  • Trigger: Auswertung einer Rule ergibt true $\rightarrow$ SM triggert die zugeordnete ActionList, welche die Direktive StartStateMachine enthält.
  • Pfade im Detail:
  1. Kaltstart / Default (StateMachine not running $\rightarrow$ No parameter):
  • Automat wird gestartet.
  • Automatischer Eintritt in den modellierten Default-Initialzustand (Init).
  1. Kaltstart / Parametrisiert (StateMachine not running $\rightarrow$ parameter):
  • Automat wird gestartet.
  • Unmittelbarer Übergang in den als Argument übergebenen Zielzustand (parameter), unter Umgehung des reinen Ruhezustands.
  1. Idempotenter Aufruf (StateMachine running $\rightarrow$ No parameter):
  • Maschine ist bereits aktiv; Aufruf ohne Parameter führt zu keiner Zustandsänderung (No action). Kein Fehler, kein Reset.
  1. Laufzeit-Transition (StateMachine running $\rightarrow$ parameter):
  • Maschine läuft bereits; der Aufruf wirkt als Zustandstransitions-Trigger (Enter state: parameter).
  • Abbruchbedingungen & Validierung (SWS_SM_00607, SWS_SM_00651):
  • Ist der übergebene parameter im Zustandsraum der Ziel-StateMachine nicht definiert oder die Transition ungültig/blockiert, bricht die Ausführung ab und löst den definierten Fehlerpfad im State Management aus (Logging via ara::log, ggf. Reporting via ara::phm oder Recovery-Action).

4. Normative Relevanz & Entwickler-Hinweise

  • API- & Semantik-Vertrag:
  • StartStateMachine dient als duales Primitiv: Es fungiert sowohl als Lifecycle-Starter (not running) als auch als Transition-Trigger (running mit Parameter). Entwickler müssen keine vorherige Statusabfrage via API implementieren.
  • Konfigurationsanforderungen (Manifest/ARXML):
  • Jede im SM modellierte StateMachine muss zwingend einen gültigen Init-Zustand deklarieren, da dieser als Fallback für parameterlose Kaltstarts dient.
  • Modellierte Transitionen müssen vom Init-Zustand sowie zwischen den über Parameter adressierten Zuständen formal zulässig sein.
  • Echtzeit- & Threading-Aspekte:
  • Die Auswertung erfolgt deterministisch und atomar innerhalb des SM-Worker-Threads.
  • Das Verhalten running + No parameter $\rightarrow$ No action stellt Idempotenz sicher und verhindert Race Conditions bei wiederholter Regelauswertung innerhalb desselben Verarbeitungszyklus.
