1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR M2-Metamodell (UML-Klassendiagramm) gemäß Foundation-Spezifikation (AUTOSAR_FO_TPS_SecurityExtractTemplate, Release R23-11).
  • Architektur-Kontext: Intrusion Detection System Manager (IdsM). Das Metamodell definiert die statische Klassenhierarchie zur Zuordnung von Sicherheitsereignissen (Security Events) zu ihrem konkreten Ursprung bzw. Wirkungsbereich (Context Mapping) über Plattformgrenzen hinweg (Classic Platform, Adaptive Platform und Kommunikationsinfrastruktur).
  • Technischer Zweck: Bereitstellung standardisierter Kontextinformationen (BSW-Modul, Functional Cluster, Applikation oder Kommunikations-Connector) zur Anreicherung qualifizierter Sicherheitsereignisse (Qualified Security Events, QSEv) für die On-Board-Filterung im IdsM und die spätere Off-Board-Analyse (SIEM / VSOC).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen der Design- und Mapping-Ebene
  • IdsDesign (Stereotypen: ARElement, UploadableDesignElement):
    • Repräsentiert den Container für das sicherheitsbezogene Gesamtdesign.
    • Hält eine Komposition/Aggregation +element mit Kardinalität 0..* auf IdsCommonElement.
    • Eigenschaften der Assoziation: «atpVariation, atpSplitable».
      • atp.Status = candidate
      • vh.latestBindingTime = systemDesignTime (Variabilität muss spätestens zur System-Designzeit aufgelöst sein; ARXML-Splitting über mehrere Dokumente/Lieferanten ist zulässig).
  • IdsCommonElement (Stereotypen: ARElement, UploadableDesignElement):
    • Abstrakte Basisklasse für gemeinsame IDS-Elemente.
  • IdsMapping:
    • Abstrakte Metaklasse; spezialisiert IdsCommonElement via Generalisierung.
  • SecurityEventContextMapping:
    • Abstrakte Basis-Metaklasse für alle Kontextzuordnungen von Security Events; erbt von IdsMapping.
Spezifische Kontext-Metaklassen (Spezialisierungen von SecurityEventContextMapping)
  1. SecurityEventContextMappingBswModule:
    • Adressiert die AUTOSAR Classic Platform (CP).
    • Attribut: + affectedBswModule: String [0..1] (symbolischer Name bzw. Modulkürzel des betroffenen BSW-Stacks, z. B. CanSM, TcpIp, SecOC).
  2. SecurityEventContextMappingFunctionalCluster:
    • Adressiert die AUTOSAR Adaptive Platform (AP) Basissystem-Ebene.
    • Attribut: + affectedFunctionalCluster: String [1] (Name des auslösenden/betroffenen funktionalen Clusters, z. B. IAM, UCM, SM).
  3. SecurityEventContextMappingApplication:
    • Adressiert die Applikationsebene (CP Software Components bzw. AP Adaptive Applications / OS-Prozesse).
    • Attribut: + affectedApplication: String [1] (eindeutiger Bezeichner/Executable-Name der Applikation).
  4. SecurityEventContextMappingCommConnector:
    • Adressiert netzwerk- und busbezogene Schnittstellen (z. B. Ethernet-Controller, CAN-Channels, FlexRay-Cluster).
    • Hält im dargestellten Ausschnitt keine eigenen Primitiv-Attribute, sondern dient als typspezifischer Mapping-Knoten auf physische/logische Schnittstellenbeschreibungen.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Da es sich um ein rein strukturelles M2-Metamodell handelt, existiert kein direkter Laufzeit-Kontrollfluss. Für die Toolchain und Laufzeitintegration gilt folgender Ablauf:

  1. Design- & Konfigurationsphase (Designtime):
    • Der Security-Architekt instanziiert im Security Extract (.arxml) ein IdsDesign und verknüpft ein Security Event über die jeweilige Subklasse von SecurityEventContextMapping.
    • Bindung von Varianten erfolgt zur systemDesignTime; ARXML-Splitter (atpSplitable) führen fragmentierte Teilsysteme zusammen.
  2. Generierungsphase:
    • Der IdsM-Code-Generator überführt die Mappings in statische Lookup-Tabellen bzw. ROM-Konfigurationsstrukturen (Mapping von interner Event-ID auf statischen Kontext-Deskriptor).
  3. Laufzeit-Trigger (IdsM Sensor Reporting):
    • Sensor meldet Event via API (IdsM_SetSecurityEvent im CP bzw. ReportSecurityEvent im AP).
    • Der IdsM schlägt anhand der Mapping-Konfiguration den Kontext (affectedBswModule, affectedFunctionalCluster, etc.) nach und packt diesen in den serialisierten Security-Event-Frame, bevor Filter-, Zähler- und Schwellwert-Logiken greifen.

4. Normative Relevanz & Entwickler-Hinweise

  • Plattformübergreifende Abstraktion: Das Modell vereinheitlicht die Sicherheitsüberwachung; Entwickler müssen bei Multi-Core- oder heterogenen Systemen (AP + CP auf einem SoC/HPC) die korrekte Subklasse wählen:
    • CP-Treiber- und BSW-Entwickler referenzieren ausschließlich SecurityEventContextMappingBswModule.
    • AP-Plattform-Entwickler binden Core-Dienste via SecurityEventContextMappingFunctionalCluster an.
    • SWC- und Adaptive-Application-Entwickler nutzen SecurityEventContextMappingApplication.
  • String-Attributierung vs. Typensicherheit: Attribute wie affectedBswModule oder affectedApplication sind als generische String-Typen modelliert. Es findet auf Metamodellebene keine zwingende Referenzauflösung (Referenz-Link auf M2-Ebene) gegen bestehende BswModuleDescription- oder AdaptiveApplication-Elemente statt. Dies erfordert nachgelagerte Validierungsprüfungen im Konfigurations-Tooling (Linter/Consistency Checks), um Schreibfehler in Modul- und Applikationsnamen zu verhindern.
  • Variabilität (atpVariation): Da latestBindingTime = systemDesignTime, sind Post-Build-Änderungen an Kontext-Mappings normativ unzulässig. Mappings müssen final in den Basissoftware-Build eincompiliert werden.
