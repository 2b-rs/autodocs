1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Wire-Format / PDU-Bitfeld-Layout (32-Bit-Raster, Big-Endian / Network Byte Order).
  • Protokoll & Schicht: SOME/IP Service Discovery (AUTOSAR_FO_PRS_SOMEIPServiceDiscoveryProtocol, Schicht 5/6 Session/Presentation über UDP/IP).
  • Funktionaler Zweck: Standardisierte Serialisierung der Configuration Option (Option-Typ 0x01). Dient der dynamischen Übermittlung von generischen Dienst- und Instanz-Attributen (Key-Value-Paare nach DNS-SD/DNS-TXT-Vorbild gemäß RFC 1464 / RFC 6763) innerhalb von SOME/IP-SD-Nachrichten (OfferService, FindService, SubscribeEventgroup).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert den 4-Byte-Options-Header sowie den variablen Nutzdatenbereich:

| Bit-Offset | Feldbezeichnung | Datentyp / Länge | Wertebereich / Semantik |

| :--- | :--- | :--- | :--- |

| 0 – 15 | Length | uint16 (16 Bit) | Gesamtlänge des nachfolgenden Options-Payloads in Bytes (inklusive Disc. Flag und Reserved, exklusive Length und Type). Entspricht 1 + len(Configuration String). |

| 16 – 23 | Type | uint8 (8 Bit) | Options-Identifier; konstant 0x01 (Configuration Option). |

| 24 | Disc. Flag | uint1 (1 Bit) | Discardable Flag: Steuert Fehlertoleranz. 1 = Option darf ignoriert/verworfen werden, falls Parser sie nicht auswerten kann; 0 = Option ist mandatory für den übergeordneten SD-Eintrag. |

| 25 – 31 | Reserved | uint7 (7 Bit) | Reserviert für zukünftige Protokollerweiterungen; senderseitig zwingend 0x00, empfängerseitig ohne Validierungsabbruch zu ignorieren. |

| 32 – ... | Zero-terminated Configuration String | Byte-Array (variabel) | Sequenz von Längen-Präfix-Strings im Format: [Length_1]Key1=Value1[Length_2]Key2=Value2...[0x00]. |

#### Struktureller Aufbau des Configuration Strings:

  • Chunk-Längenfeld: 1 Byte (uint8), gibt exakt die Anzahl der folgenden Bytes des Chunks an (max. 255 Bytes pro Key-Value-Paar).
  • Payload-Format je Chunk:
  • Key=Value: Schlüssel und Wert getrennt durch ASCII-Gleichheitszeichen (=, 0x3D).
  • Key: Mindestens 1 druckbares US-ASCII-Zeichen (0x20–0x7E), exklusive =. Kein führendes = zulässig ([PRS_SOMEIPSD_00283], [PRS_SOMEIPSD_00284]).
  • Value: Beliebige Byte-Folge innerhalb der Chunk-Grenzen; darf weitere = enthalten.
  • Boolean-Flag-Semantik: Fehlt das Trennzeichen =, gilt der deklarierte Key als existent/aktiv ([PRS_SOMEIPSD_00285]).
  • Terminierung: Ein Längenbyte mit dem Wert 0x00 markiert das reguläre Ende des gesamten Konfigurationsblocks; danach dürfen keine weiteren Bytes folgen ([PRS_SOMEIPSD_00279], [PRS_SOMEIPSD_00280]).

3. Dynamisches Verhalten & Sequenzablauf

Der Parsing- und Serialisierungsprozess auf Stack-Ebene folgt einem deterministischen Finite-State-Verfahren:

  1. Header-Validierung:
  • Lese Type. Ist Type != 0x01, verzweige in spezifischen Option-Handler.
  • Lese Length. Allokiere Lesefenster: Payload_Length = Length - 1 (Abzug des Disc. Flag/Reserved-Bytes).
  1. Chunk-Dekodierschleife:
  • Lese 1-Byte Längenpräfix L.
  • Terminierungs-Prüfung: Ist L == 0x00, terminiere Parsing erfolgreich. Verbleiben noch Bytes innerhalb des durch Length aufgespannten Rahmens, liegt ein Formatfehler vor ([PRS_SOMEIPSD_00280]).
  • Grenzwert-Prüfung: Übersteigt L die verbleibende Pufferrestlänge, breche mit Parsing-Fehler ab (Buffer-Overflow-Schutz).
  • Tokenisierung:
  • Suche Index des ersten =, getrennt in Key (Index 0 bis i-1) und Value (Index i+1 bis L-1).
  • Ist Index == 0, Parse-Fehler (Schlüssel darf nicht leer sein).
  • Ist kein = vorhanden, annotiere Key als boolean präsent.
  • Dekrementiere verbleibende Puffergröße um 1 + L Bytes; wiederhole Schleife.
  1. Fehlerbehandlung:
  • Tritt ein Formatfehler (Malformed Key, Pufferüberlauf, fehlende 0x00-Terminierung) auf:
  • Bei Disc. Flag == 1: Verwerfe ausschließlich diese Configuration Option, setze Verarbeitung der verbleibenden SD-Optionen fort.
  • Bei Disc. Flag == 0: Verwerfe den gesamten zugeordneten SOME/IP-SD-Eintrag (Entry Invalid).

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher- und Parsing-Optimierung (AUTOSAR Classic Bsw / Adaptive ara::com):
  • Zero-Copy In-Place Parsing: Da alle Chunks längenpräfigiert sind, ist kein Null-Terminieren einzelner Strings im Puffer erforderlich. Implementierungen sollten String-Views / Pointerscheiben (const char*, size_t) direkt auf den Empfangspuffer legen, um dynamische Allokationen im Core-Stack zu vermeiden.
  • Längenfeld-Berechnung (Offset-Falle):
  • Das 16-Bit-Feld Length misst nicht ausschließlich den String-Bereich, sondern schließt das Byte für Disc. Flag/Reserved mit ein. Formel für Serialisierer:

$$\text{Option-Length} = 1 + \sum_{k} (1 + \text{len}(\text{chunk}_k)) + 1_{\text{Terminierung (0x00)}}$$

  • MTU- und PDU-Budgetierung:
  • SD-Nachrichten laufen typischerweise unfragmentiert über UDP (Standard-MTU $\le$ 1500 Bytes). Exzessive Name-Value-Paare vergrößern den Options-Array-Block signifikant und führen bei Überschreitung des UDP-PDU-Limits zum Verwerfen oder zur PDU-Segmentierung.
  • Robustheit & Validierungspflicht:
  • Eingangsdaten dürfen niemals ungeprüft an Applikationen übergeben werden. Stacks müssen strikt auf ASCII-Konformität (0x20–0x7E), verbotene Zeichen im Key und Out-of-Bounds-Längen prüfen (Schutz gegen Endlosschleifen bei fehlendem 0x00).
