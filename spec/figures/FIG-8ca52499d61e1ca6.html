1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / AUTOSAR ECUC-Metamodell (ECU Configuration Parameter Definition).
  • Architektur-Kontext: MCAL (Microcontroller Abstraction Layer) – Can-Treiber (AUTOSAR_CP_SWS_CANDriver, Release R23-11).
  • Funktionaler Zweck: Formale Definition des Konfigurations-Containers CanHardwareObject. Es modelliert die hardwarenahe Abstraktion der CAN-Controller-Mailboxen/Puffer (Message Buffer, FIFOs) für Sende- und Empfangsoperationen, deren Hardware-Filterung, Puffergrößen (CAN-FD) sowie die Anbindung an Controller-Instanzen und zyklische Main-Functions.

2. Komponenten, Entitäten & Schnittstellen

Zentraler Konfigurations-Container
  • CanHardwareObject (EcucParamConfContainerDef, Multiplizität: 0..*): Repräsentiert ein logisches Hardware-Objekt (oder einen Pool identischer Objekte) im CAN-Controller.
Parameter (EcucParameterDef via +parameter)
  • CanObjectId (EcucIntegerParamDef):
    • Wertebereich: 0 .. 65535, Multiplizität: 1..1, withAuto = true, symbolicNameValue = true.
    • Eindeutiger Identifikator; dient dem BSW-Stack (insb. CanIf) als symbolischer Bezeichner für Hardware Transmit Handles (HTH) bzw. Hardware Receive Handles (HRH).
  • CanObjectType (EcucEnumerationParamDef):
    • Literale: TRANSMIT, RECEIVE.
    • Legt fest, ob das Objekt als Sende- (HTH) oder Empfangspuffer (HRH) agiert.
  • CanHandleType (EcucEnumerationParamDef):
    • Literale: BASIC, FULL.
    • BASIC: Hardware-Objekt empfängt/sendet mehrere CAN-IDs (Shared Mailbox / FIFO); erfordert ggf. Software-Filterung im BSW.
    • FULL: Hardware-Objekt ist exakt einer CAN-ID fest zugeordnet.
  • CanIdType (EcucEnumerationParamDef):
    • Literale: STANDARD (11-Bit), EXTENDED (29-Bit), MIXED (Unterstützung beider Formate).
  • CanHwObjectCount (EcucIntegerParamDef):
    • Wertebereich: 1 .. 65535, Multiplizität: 1..1, defaultValue = 1.
    • Anzahl physischer Mailboxen, die zu einem logischen FIFO oder Puffer-Array zusammengefasst sind.
  • CanHardwareObjectUsesPolling (EcucBooleanParamDef):
    • Multiplizität: 0..1, defaultValue = false.
    • Schaltet für dieses Objekt zwischen interruptgetriebener Verarbeitung (false) und Polling-Betrieb (true) um.
  • CanTriggerTransmitEnable (EcucBooleanParamDef):
    • Multiplizität: 0..1, defaultValue = false.
    • Aktiviert das AUTOSAR TriggerTransmit-Verfahren (pull-basiertes Abrufen der PDU-Daten unmittelbar vor dem Versand).
  • CanFdPaddingValue (EcucIntegerParamDef):
    • Wertebereich: 0 .. 255, Multiplizität: 0..1, defaultValue = 0.
    • Füllbyte für ungenutzte Datenbytes in diskreten CAN-FD-Payload-Stufen (z. B. DLC-Sprünge > 8 Byte).
  • CanObjectPayloadLength (EcucEnumerationParamDef):
    • Multiplizität: 0..1.
    • Literale: CAN_OBJECT_PL_8, CAN_OBJECT_PL_12, CAN_OBJECT_PL_16, CAN_OBJECT_PL_20, CAN_OBJECT_PL_24, CAN_OBJECT_PL_32, CAN_OBJECT_PL_48, CAN_OBJECT_PL_64.
    • Maximale konfigurierte Nutzdatenlänge (DLC) für klassisches CAN bzw. CAN-FD-Payload-Größen.
Sub-Container (+subContainer)
  • CanHwFilter (EcucParamConfContainerDef, Multiplizität: 0..*):
    • Enthält Filterkriterien für Acceptance-Filterung auf Hardware-Ebene.
    • CanHwFilterCode (EcucIntegerParamDef): Wertebereich: 0 .. 4294967295 (32-Bit Bitmuster für CAN-ID).
    • CanHwFilterMask (EcucIntegerParamDef): Wertebereich: 0 .. 4294967295 (32-Bit Bitmaske; 1 = relevant, 0 = don't care).
Referenzen (EcucReferenceDef via +reference)
  • CanControllerRef:
    • Ziel (+destination): CanController (EcucParamConfContainerDef, Multiplizität: 1..*).
    • Ordnet das CanHardwareObject genau dem physischen CAN-Controller zu, auf dem die Mailbox physikalisch existiert.
  • CanMainFunctionRWPeriodRef:
    • Multiplizität: 0..1.
    • Ziel (+destination): CanMainFunctionRWPeriods (EcucParamConfContainerDef, Multiplizität: 0..*).
    • Bindet das Objekt an eine spezifische Ausführungsperiode von Can_MainFunction_Read bzw. Can_MainFunction_Write bei konfigurierter Polling-Verarbeitung.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert statische Konfigurationsparameter, determiniert jedoch direkt die Laufzeitpfade des Treibers:

  1. Sende-Pfad (TRANSMIT):
    • Direkter Versand: Aufruf von Can_Write(Hth, PduInfo). Ist CanTriggerTransmitEnable == true, ruft der Treiber synchron CanIf_TriggerTransmit() auf, um Nutzdaten direkt in den Message Buffer zu kopieren.
    • Bestätigung (Confirmation):
      • Bei Interrupt-Betrieb (CanHardwareObjectUsesPolling == false): Auslösung des Tx-Interrupts → Aufruf von CanIf_TxConfirmation().
      • Bei Polling-Betrieb (CanHardwareObjectUsesPolling == true): Abfrage des Tx-Status zyklisch in Can_MainFunction_Write() basierend auf der Periode aus CanMainFunctionRWPeriodRef.
  2. Empfangs-Pfad (RECEIVE):
    • Hardware empfängt Frame → Abgleich gegen CanHwFilterCode unter Berücksichtigung von CanHwFilterMask.
    • Weiterleitung (Indication):
      • Bei Interrupt-Betrieb: Rx-Interrupt → Auslesen der Mailbox → Aufruf von CanIf_RxIndication().
      • Bei Polling-Betrieb: Zyklisches Auslesen in Can_MainFunction_Read() (gemäß CanMainFunctionRWPeriodRef).
    • Bei CanHandleType == BASIC: Nachgelagerte Software-Filterung im CanIf notwendig, falls mehrere IDs dieselbe Mailbox passieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Generierte Symbolische Namen: Da CanObjectId.symbolicNameValue = true gesetzt ist, generiert der Konfigurator C-Makros (z. B. CanConf_CanHardwareObject_<Name>), die im CanIf als HRH- bzw. HTH-IDs verwendet werden müssen.
  • Controller-Bindung: Ein Hardware-Objekt darf immer nur genau einem CanController zugeordnet sein (CanControllerRef bindet das Hardware-Objekt exklusiv an eine Controller-Instanz).
  • CAN-FD Validierung:
    • Wird CAN-FD genutzt, muss CanObjectPayloadLength entsprechend auf Werte > 8 (bis 64 Byte) gesetzt werden.
    • Übermittelt die obere Schicht eine unvollständige DLC-Länge (nicht deckungsgleich mit diskreten CAN-FD-Längenstufen 12, 16, 20, 24, 32, 48, 64), muss der CAN-Treiber ungenutzte Bytes zwingend mit dem in CanFdPaddingValue hinterlegten Byte auffüllen.
  • Ressourcenoptimierung: Über CanHwObjectCount lassen sich Hardware-FIFOs abbilden. Ist CanHwObjectCount > 1, verwaltet der Treiber intern mehrere zusammenhängende Mailboxen unter einem gemeinsamen CanObjectId, was FIFO-Überläufe bei Burst-Empfang (BASIC-CAN) hardwareseitig verhindert.
