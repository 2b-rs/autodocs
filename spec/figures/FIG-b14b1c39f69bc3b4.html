1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (Ausschnitt aus dem AUTOSAR-M2-Metamodell).
  • Architektur-Kontext: Spezifiziert im AUTOSAR Basic Software Module Description Template (BSWMDT) ([TPS_BSWMDT_04040]). Es definiert das strukturelle Bindeglied zwischen Implementierungsartefakten (Quellcode/Objektcode, Linker-Symbole) und den verhaltensbeschreibenden Metamodellelementen für Software-Components (SWC) sowie Basissoftware-Module (BSW).
  • Funktionaler Zweck: Festlegung der Bindungsregeln: Jedes reale Code-Artefakt (Implementation) ist an ein abstraktes Ausführungsverhalten (InternalBehavior) gebunden, welches seinerseits in die übergeordnete Komponenten- bzw. Modulstruktur eingebettet ist.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • Implementation (abstrakt, «ARElement»): Basisklasse für alle konkreten Code-Implementierungen (Compiler-Abstraktionen, Quellcodedateien, Resource-Bedarfe).
  • SwcImplementation (Spezialisierung von Implementation): Repräsentiert die Implementierung einer atomaren Applikations-Software-Komponente.
  • BswImplementation (Spezialisierung von Implementation): Repräsentiert die Implementierung eines BSW-Moduls bzw. BSW-Treibers.
  • InternalBehavior (abstrakt, «AtpStructureElement»): Abstrakte Basisklasse für interne Verhaltensbeschreibungen (Runnables, Schedulable Entities, Events).
  • SwcInternalBehavior (Spezialisierung von InternalBehavior): Verhaltensmodell der SWC (definiert Runnable Entities, RTE-Events, interne Puffer).
  • BswInternalBehavior (Spezialisierung von InternalBehavior): Verhaltensmodell eines BSW-Moduls (definiert BSW-Schedulable Entities, Main Functions, Interrupt-Routinen, Exclusive Areas).
  • AtomicSwComponentType («SwComponentType»): Definition des atomaren Komponententyps (Ports, Schnittstellen).
  • BswModuleDescription («ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpStructureElement»): Top-Level-Beschreibung eines BSW-Moduls im BSW-Katalog.
Assoziationen, Kardinalitäten & Kompositionen
  • Generalisierungen (Vererbung):
    • SwcImplementation → Implementation
    • BswImplementation → Implementation
    • SwcInternalBehavior → InternalBehavior
    • BswInternalBehavior → InternalBehavior
  • Implementierungs-Referenzen (behavior):
    • SwcImplementation $\xrightarrow{\text{+behavior [0..1]}}$ SwcInternalBehavior: Eine SWC-Implementierung referenziert optional bis zu ein SwcInternalBehavior (Multiplizität 0..1).
    • BswImplementation $\xrightarrow{\text{+behavior [0..1]}}$ BswInternalBehavior: Eine BSW-Implementierung referenziert optional bis zu ein BswInternalBehavior (Multiplizität 0..1).
  • Container-Kompositionen (internalBehavior):
    • AtomicSwComponentType ▶ SwcInternalBehavior: Komposition mit Rolle +internalBehavior, Multiplizität 0..1, annotiert mit Stereotypen «atpVariation,atpSplitable». Ein angehefteter Notizkommentar spezifiziert den Variationspunkt mit «atpVariation» Tags: vh.latestBindingTime = preCompileTime.
    • BswModuleDescription ▶ BswInternalBehavior: Komposition mit Rolle +internalBehavior, Multiplizität 0..*, annotiert mit Stereotyp «atpSplitable».

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein rein deklaratives Metamodell (Strukturmodell zur Entwurfs-/Generierungszeit) handelt, existieren keine Laufzeit-Zustandsübergänge oder Sequenz-Trigger im Diagramm selbst. Das Modell steuert die Tool-Chain-Phasen:

  1. Entwurfsphase (Contract Phase): Definition von AtomicSwComponentType bzw. BswModuleDescription samt internem Verhalten (SwcInternalBehavior / BswInternalBehavior).
  2. Implementierungsphase (Generation Phase): Erzeugung oder manuelle Bereitstellung des C-Codes. Die Bindung erfolgt strikt über behavior (Multiplizität 1) auf das entsprechende InternalBehavior.
  3. Integrationsphase (RTE/SchM-Generierung):
    • Bei reinen SWCs oder reinen BSW-Modulen generiert der RTE- bzw. SchM-Generator die Glue-Code-Header basierend auf dem referenzierten Verhalten.
    • Liegt ein CDD oder ein BSW-Dienst mit SWC-Schnittstelle vor, wertet der Generator das referenzierte SwcBswMapping aus, um API-Signaturen und Task-Mappings zwischen SchM (BSW-Scheduler) und RTE (SWC-Scheduler) konfliktfrei abzustimmen.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Bindung (TPS_BSWMDT_04040):
    • Eine Implementierung (BswImplementation oder SwcImplementation) darf niemals lose im ARXML existieren; sie erfordert zwingend die Referenzierung von genau einer Verhaltensbeschreibung (+behavior 1).
    • Es ist unzulässig, eine Implementierung direkt an mehrere Verhaltensinstanzen zu binden. Unterschiedliche Konfigurationen/Verhalten erfordern separate Implementation-Instanzen.
  • BSW- vs. SWC-Kardinalitätsunterschiede:
    • Ein AtomicSwComponentType besitzt maximal ein Verhalten (0..1), welches durch «atpVariation» post-build- oder systemkonfigurationsabhängig variiert werden kann.
    • Eine BswModuleDescription kann mehrere Verhaltensweisen (0..*) aggregieren (z. B. unterschiedliche Funktionsumfänge je nach Sub-Modul-Konfiguration).
  • Entwickler-Regel für CDD & Service-Komponenten:
    • Entwickler von Complex Device Drivern müssen sowohl BswInternalBehavior (für Hardware-Interrupts, Main-Functions via SchM) als auch SwcInternalBehavior (für Port-Zugriffe via RTE) beschreiben.
    • Die Kohärenz zwischen beiden Welten muss durch die Bereitstellung eines validen SwcBswMapping abgesichert werden, wenn eine gemeinsame Implementation referenziert wird.
  • Dateiaufteilung («atpSplitable»):
    • SwcInternalBehavior und BswInternalBehavior müssen nicht zwingend in derselben ARXML-Datei wie die übergeordneten Typen (AtomicSwComponentType bzw. BswModuleDescription) persistiert werden. AUTOSAR-Authoring-Tools dürfen diese Elemente in getrennten XML-Paketstrukturen ablegen.
