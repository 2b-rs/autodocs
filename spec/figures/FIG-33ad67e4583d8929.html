Figure 4.5: Modeling of DiagnosticProtocol

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt der AUTOSAR-Systembeschreibung (Diagnostic Extract Template, DEXT, bezogen auf AUTOSAR System Template).
  • Funktionaler Kontext: Modellierung des Diagnoseprotokolls (DiagnosticProtocol) zur formalen Beschreibung von Diagnose-Schnittstellen (UDS, OBD, WWH-OBD) auf ECU-Ebene.
  • Architektonische Einordnung: DEXT bildet die herstellerübergreifende Schnittstelle (OEM zu Tier-1) für die automatisierte BSW-Generierung des AUTOSAR Diagnostic Stacks – primär des DCM (Diagnostic Communication Manager, Schichten DSL und DSD) sowie der Anbindung an die PDU-/Transport-Layer (CanTp, DoIP, PduR).

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Attribute

  • DiagnosticProtocol (Stereotyp: «DiagnosticCommonElement»):
  • priority : PositiveInteger: Priorisierung bei konkurrierenden Diagnoseanfragen im DCM (z. B. Konfliktauflösung zwischen parallelen Requests).
  • protocolKind : NameToken: Spezifiziert den Protokolltyp (z. B. UDS_ON_CAN, OBD, ROE).
  • sendRespPendOnTransToBoot : Boolean [0..1]: Steuert, ob vor der Transition in den Bootloader (z. B. Session Control oder EcuReset) zwingend ein Response Pending (NRC 0x78) an den Tester gesendet werden muss.
  • DiagnosticServiceTable (Stereotyp: «DiagnosticCommonElement»):
  • protocolKind : NameToken: Zuordnung des Protokolltyps zur Servicetabelle. Repräsentiert die Zusammenstellung aller unterstützten Diagnose-Services.
  • DiagnosticServiceInstance (Stereotyp: «DiagnosticCommonElement»):
  • Repräsentiert die konkrete Instanz eines Diagnosedienstes (z. B. Service 0x22 ReadDataByIdentifier für eine spezifische DID).
  • DiagnosticConnection (Stereotyp: «ARElement»):
  • Beschreibt die logische/physikalische Diagnoseverbindung (Tester-Request, ECU-Response, Functional/Physical Addressing über TP-Kanäle).
  • EcuInstance (Stereotyp: «FibexElement»):
  • Instanz des Steuergeräts im System mit Kommunikations- und Netzwerkparametern (u. a. diagnosticAddress : Integer [0..1], comConfiguration*TimeBase, sleepModeSupported, wakeUpOverBusSupported).

#### Beziehungen & Kardinalitäten

  • DiagnosticProtocol $\rightarrow$ DiagnosticServiceTable:
  • Rolle: +serviceTable, Kardinalität 0..1.
  • Stereotypen: «atpVariation», «atpSplitable».
  • DiagnosticProtocol $\rightarrow$ DiagnosticConnection:
  • Rolle: +diagnosticConnection, Kardinalität 0..*.
  • Stereotypen: «atpVariation», «atpSplitable».
  • DiagnosticServiceTable $\rightarrow$ DiagnosticConnection:
  • Rolle: +diagnosticConnection, Kardinalität 0..*.
  • Stereotypen: «atpVariation», «atpSplitable».
  • DiagnosticServiceTable $\rightarrow$ DiagnosticServiceInstance:
  • Rolle: +serviceInstance, Kardinalität 1..* (unidirektionale Komposition/Aggregation). Mindestens ein Service muss in einer Tabelle deklariert sein.
  • DiagnosticServiceTable $\rightarrow$ EcuInstance:
  • Rolle: +ecuInstance, Kardinalität 0..1 (optionale Zuordnung der Servicetabelle zu einer ECU-Instanz).

#### Variationspunkte

  • Assoziationen mit «atpVariation» tragen den Tag:

vh.latestBindingTime = postBuild.

Die Bindung der Servicetabellen und Verbindungen an Protokolle kann bis zur Post-Build-Phase (PB-S / PB-L) verzögert werden.

  • «atpSplitable»: Erlaubt die Deklaration und Aufteilung der XML-Fragmente über mehrere Dateien bzw. ARXML-Pakete.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches ARXML-Metamodell definiert das Diagramm die Konfigurationsbasis für folgende Laufzeit-Sequenzen im DCM:

```

[Tester] --(Diagnostic Request)--> [PduR/CanTp/DoIP]

│

▼

[DCM : DslLayer]

┌────────────────────────────┴───────────────────────────┐

│ 1. Identifikation DiagnosticConnection │

│ 2. Arbitrierung via DiagnosticProtocol.priority │

└────────────────────────────┬───────────────────────────┘

▼

[DCM : DsdLayer]

┌────────────────────────────┴───────────────────────────┐

│ 3. Dispatching an DiagnosticServiceTable │

│ 4. Verifikation Service / DiagnosticServiceInstance │

└────────────────────────────┬───────────────────────────┘

▼

[Bootloader-Übergang?] ──(Ja: sendRespPendOnTransToBoot==true)

│

├──> Sende NRC 0x78 via DSL

└──> Übergabe an BswM/Mcu_PerformReset

```

  • Protokoll-Arbitrierung (DSL): Eintreffende Requests auf einer DiagnosticConnection werden anhand der DiagnosticProtocol.priority aufgelöst, falls konkurrierende Sessions (z. B. gesetzliches OBD vs. proprietäres UDS) aktiv sind.
  • Service-Dispatching (DSD): Der DSL leitet validierte PDUs an den DSD weiter, der sie gegen die im DiagnosticServiceTable registrierten DiagnosticServiceInstance-Elemente abgleicht.
  • Transition to Boot: Bei Services, die einen Sprung in den Bootloader erfordern (0x10 0x02 ProgrammingSession oder 0x11 0x01 HardReset), triggert ein gesetztes Flag sendRespPendOnTransToBoot = true das asynchrone Absenden einer NRC 0x78 (RequestCorrectlyReceived-ResponsePending) via DSL/PduR, bevor die Steuergeräte-Rücksetzsequenz (Dcm_SetProgConditions(), Aufruf von BswM) eingeleitet wird.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration & Codegenerierung (Dcm):
  • DiagnosticProtocol parametriert direkt den Container DcmDslProtocol / DcmDslProtocolRow. protocolKind mappt auf DcmDslProtocolID (z. B. DCM_UDS_ON_CAN).
  • priority generiert den Parameter DcmDslProtocolPriority.
  • sendRespPendOnTransToBoot mappt direkt auf den BSW-Parameter DcmSendRespPendOnTransToBoot. Fehlt dieser Wert ([0..1]), greift der Default des BSW-Stacks (oft herstellerspezifisch FALSE).
  • Service-Tabellen (DcmDsd):
  • DiagnosticServiceTable erzeugt DcmDsdServiceTable. Die enthaltenen DiagnosticServiceInstance-Elemente generieren die DcmDsdService- und DcmDsdSubService-Konfigurationseinträge samt Funktionspointern zu den Callbacks (Dcm_<DiagnosticService>).
  • Post-Build-Bindung (latestBindingTime = postBuild):
  • Erfordert im DCM-Treiber indirekte Deskriptoren-Tabellen (ROM-Pointer oder RAM-Konfigurationsstrukturen Dcm_ConfigType), sofern Protokolle oder Verbindungen für unterschiedliche Fahrzeugvarianten erst nach dem Kompilieren verknüpft werden.
  • EcuInstance-Kopplung:
  • Die Kardinalität 1 erzwingt eine eindeutige Auflösung der DiagnosticServiceTable zu einer spezifischen EcuInstance. Dies verhindert ambivalente Service-Tabellen bei Multi-ECU-Systembeschreibungen in einem ARXML-Lieferpaket.
