1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR-Architektur- und Komponenten-Interaktionsdiagramm (VFB- und BSW-Schichtenmodell mit Port-Topologie und State-Machine-Instanziierung).
  • Technischer Zweck: Visualisierung des Entkopplungsprinzips im AUTOSAR Mode Management zwischen Mode Managern, Mode Usern und der Runtime Environment (RTE / SchM).
  • Architektonische Einordnung:
    • Verdeutlicht, dass Mode-Switch-Ports (ModeSwitchInterface) von Mode Usern niemals direkt („point-to-point“) mit dem P-Port des Mode Managers verdrahtet sind.
    • Zeigt die Rolle der RTE als zentraler Vermittler: Die RTE instanziiert pro ModeDeclarationGroupPrototype eine dedizierte ModeMachineInstance. Diese hält den aktuellen Modus-Zustand, führt Transitionen aus und verteilt Statusänderungen (Mode Switch Events, Modusabfragen) an konsumierende Entitäten (1:n-Entkopplung).
    • Unterscheidung der Interaktionsebenen: Anwendungs-Ebene (SW-C-Ebene über VFB/RTE) und Basissoftware-Ebene (BSW-Ebene via System Services / BswM und SchM).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Schichten
  • Application Layer (SW-C):
    • application mode manager: Besitzt den ModeDeclarationGroupPrototype auf Applikationsebene. Trägt die Schalt-Autorität für den Modus.
    • application mode user: Konsumiert den Modus oder fordert Modusänderungen an.
  • Runtime Environment (RTE / SchM, orangefarbene Schicht):
    • Beinhaltet zwei mode machine Instance-Zustandsautomaten. Jede Instanz repräsentiert die Laufzeitabbildung einer ModeDeclarationGroup mit ihren definierten ModeDeclarations (Zuständen und Transitionen).
  • System Services (BSW, blaue Schicht):
    • basic software mode manager (z. B. BswM – Basic Software Mode Manager): Zentraler Schieds- und Schaltpunkt für System- und BSW-Modi.
    • basic software mode user (z. B. ComM, EcuM, CanSM oder BSW-Treiber/Stacks): Nutzer von BSW-Zuständen.
Schnittstellen & Port-Typen
  • Mode Switch Ports (Dargestellt durch Quadrate mit 3 Punkten):
    • Weiße Symbole: SW-C-Ports (ModeSwitchInterface).
      • P-Port (application mode manager): Schnittstelle zur Initiierung von Moduswechseln (Rte_Switch_<p>_<o>()).
      • R-Port (application mode user): Schnittstelle zum Empfang von Modusänderungen oder Abfrage des aktuellen Modus (Rte_Mode_<p>_<o>()).
    • Schwarze Symbole: BSW-Service-Ports bzw. C-Module-Schnittstellen (SchM/BSW-interne Mode-Switch-Schnittstellen, z. B. SchM_Switch, SchM_Mode).
    • Kardinalität: 1 (Mode Manager P-Port) zu 1 (ModeMachineInstance) zu N (Mode User R-Ports).
  • Mode Request Ports (Dargestellt durch Quadrate mit Dreieckssymbolen):
    • Repräsentieren Standard-Kommunikationsbeziehungen (Client/Server oder Sender/Receiver) zur Übermittlung von Modusanforderungen:
      • Sender/Client (Dreieck zeigt nach außen / nach unten): mode user sendet Request.
      • Receiver/Server (Dreieck zeigt nach innen / nach oben): mode manager empfängt Request zur Verrechnung (Arbitrierung).

3. Dynamisches Verhalten & Sequenzablauf

  1. Modusanforderung (Request-Phase):
    • Ein mode user (SW-C oder BSW) besitzt keine Berechtigung zum direkten Moduswechsel.
    • Er sendet über seinen mode request port eine Anforderung (asynchron oder synchron via S/R oder C/S) an den zuständigen mode manager (z. B. BswM über Rule Evaluation).
  2. Modusentscheidung & Initiierung (Switch-Phase):
    • Der mode manager evaluiert Regeln/Bedingungen. Ist ein Wechsel zulässig, ruft er an seinem mode switch port die API Rte_Switch() bzw. SchM_Switch() auf.
  3. Zustandsübergang in der RTE (ModeMachineInstance):
    • Der Aufruf geht nicht an die Konsumenten, sondern triggert die interne ModeMachineInstance.
    • Die ModeMachineInstance wechselt den Zustand von der alten zur neuen ModeDeclaration unter Einhaltung konfigurierter Transitionszeiten oder Transition-Modes.
  4. Modusverteilung & Event-Triggering (Notification-Phase):
    • Die ModeMachineInstance benachrichtigt alle verbundenen mode user (Broadcast/Verteilung).
    • Trigger: Auslösung von ModeSwitchEvents (z. B. ON_ENTRY, ON_EXIT, ON_TRANSITION), welche die Ausführung konfigurierter Runnables / BSW-Schedulable-Entities in den Mode Usern anstoßen.
    • Polling: Mode User können synchron über Rte_Mode() bzw. SchM_Mode() den aktuellen Zustand jederzeit abfragen.

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur-Entkopplung:
    • Mode Manager und Mode User dürfen im System Description / Composition Schema (ARXML) niemals über ModeSwitchInterface direkt per Assembly Connector verbunden werden. Die Verbindung erfolgt formal gegen das RTE-generierte Modell bzw. den P-Port des Managers; der RTE-Generator synthetisiert daraus die Zustandsmaschine und die R-Port-Verbindungen.
  • API-Vertrag:
    • Mode Manager: Nutzt Rte_Switch_<p>_<o>(Rte_ModeType_<group> mode) (bzw. SchM_Switch). Rückgabewert ist standardmäßig RTE_E_OK oder RTE_E_LIMIT (falls bereits eine Transition läuft).
    • Mode User: Nutzt Rte_Mode_<p>_<o>() für den synchronen Lesezugriff oder registriert Runnables an RteEvents vom Typ SwcModeSwitchEvent.
  • Asynchronität & Quittierung:
    • Moduswechsel über die RTE laufen typischerweise asynchron zum Manager ab (modeSwitchAckTimeout, Ack-Mechanismus konfigurierbar, falls der Manager auf den Vollzug der Transition warten muss).
  • BSW-Integration (BswM & SchM):
    • Für BSW-Module übernimmt der BswM die Rolle des BSW-Mode-Managers.
    • BSW-Moduswechsel greifen direkt in das Task-Scheduling des Betriebssystems / der SchM ein (z. B. Aktivieren/Deaktivieren von zyklischen Tasks oder Ausführen von Initialisierungs-Listen über Action Lists des BswM).
