3. Dynamisches Verhalten & Sequenzablauf

  1. Task-Aktivierung (loop Cyclic Task of Interface):
  • Der BSW Scheduler ruft synchron Can_MainFunction_Read() auf.
  • Das Modul Can fragt via Check for pending Rx indication() den Hardware-Status des CanController ab.
  1. Entscheidungszweig alt Pending Rx indication:
  • Fall [No Rx indication pending]: Funktion terminiert unmittelbar ohne weitere Interaktion.
  • Fall [Rx indication pending]:
  1. Hardware-Lock: Can ruft Invalidation of hardware object() am CanController auf, um ein Überschreiben des Hardware-Objekts durch nachfolgenden Busverkehr während des Lesens zu sperren.
  2. Puffer-Entscheidung (alt Temporary buffer usage):
  • Bedingung [Temp. buffer used = Data normalization necessary]: Treibereigener RAM-Schattenpuffer wird genutzt; Daten werden via Copy received L-PDU into temporary buffer() in den RAM kopiert (z. B. zur Linearisierung von Endianness, Word-Alignment oder nicht-linearem Message-RAM).
  • Bedingung [Temp. buffer not used = Data normalization not necessary]: Verzicht auf Zwischenpuffer; Zeiger im PduInfoType verweisen direkt auf Hardwareregister/Controller-RAM (Zero-Copy-Pfad).
  1. Übergabe an Abstraktionsschicht: Aufruf von CanIf_RxIndication(Mailbox, PduInfoPtr).
  2. CanIf-Interne Verarbeitung:
  • Ausführung von Software filtering (optional): Relevanzprüfung bei BasicCAN-Mailboxen (Filterung gegen Maske/ID) und Ermittlung der logischen Ziel-ID (CanIfRxPduId).
  • Bedingung [CAN L-PDU ID was found]: Ausführung des Data Length Check (optional).
  1. Dispatch an Upper Layer: Aufruf von <User_RxIndication>(RxPduId, PduInfoPtr).
  2. Nutzdatenübernahme (alt Temporary buffer usage):
  • Temp. buffer used: Der User kopiert die Daten via Copy data() aus dem MCAL-Puffer (Can).
  • Temp. buffer not used: Der User kopiert die Daten via Copy data() direkt aus dem CanController.
  1. Rückkehr & Revalidierung:
  • Kaskadiertes Return: <User_RxIndication> $\rightarrow$ CanIf_RxIndication.
  • Das Modul Can reaktiviert das Hardware-Empfangsobjekt via Validation of hardware object().
  • Return von Can_MainFunction_Read() an den BSW Scheduler.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsabhängigkeiten (ECUC):
  • Treiber-Modus: Wird gesteuert über den Parameter CanRxProcessing (POLLING vs. INTERRUPT). Bei POLLING bestimmt die Periodendauer der Triggertask im BSW Scheduler direkt die Rx-Latenz und das Risiko von Hardware-Pufferüberläufen (Rx-Overrun-Flags).
  • Filterung & Validierung: CanIfPrivateSoftwareFilter steuert die Aktivierung der Softwarefilterung (zwingend erforderlich bei Hardware-Objekten vom Typ BASIC_CAN). CanIfPrivateDlcCheck aktiviert den DLC-Check. Schlägt der DLC-Check fehl, wird die PDU verworfen und optional CANIF_E_INVALID_DLC an das DET gemeldet.
  • Hardware-Blockade & Latenz-Budget:
  • Zwischen Invalidation und Validation ist das betroffene Hardware-Objekt blockiert. Da die gesamte Sequenz (Can_MainFunction_Read $\rightarrow$ CanIf_RxIndication $\rightarrow$ <User_RxIndication>) synchron abläuft, dürfen Callbacks in oberen Schichten (z. B. im PduR oder CanTp) niemals blockieren oder rechenintensive Operationen durchführen, da dies zum Verlust nachfolgender CAN-Frames auf demselben Hardware-Objekt führt.
  • Speicher- und Alignment-Strategie (Data Normalization):
  • Auf Mikrocontrollern mit unaligned Memory-Mapped I/O oder 16/32-Bit-Zugriffsbeschränkungen muss die Treiber-Implementierung Daten normalisieren (Temp. buffer used). Entwickler müssen den Trade-off beachten: Temporäre Puffer erhöhen den RAM-Bedarf und die CPU-Last durch redundantes Kopieren (Copy received L-PDU + Copy data), schützen aber vor Hard-Faults bei unaligned Speicherzugriffen der oberen Schichten.
  • Kontext-Invarianz:
  • Im Gegensatz zum Interrupt-Pfad läuft <User_RxIndication> hier im Task-Kontext der Can_MainFunction_Read(). Dies entlastet das Interrupt-System, erlaubt jedoch keine Annahmen über ISR-Sperrzeiten innerhalb der User-Callbacks.
