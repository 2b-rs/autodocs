1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / AUTOSAR ECUC-Parametermetamodell-Fragment (BSW Parameter Configuration Metamodel).
  • Funktionale Einordnung: Definiert die Konfigurationsstruktur des Containers ComMUser innerhalb des Communication Managers (ComM, System Services Layer, Classic AUTOSAR R4.0.3). Es modelliert die logischen Anforderer von Kommunikationsmodi (Software-Components via RTE, BswM, DCM) und deren Zuordnung zu Kommunikationskanälen sowie OS-Partitionen.

2. Komponenten, Entitäten & Schnittstellen

  • ComMUser (EcucParamConfContainerDef):
    • Multiplizität: 1..* (Mindestens ein User muss pro ECU konfiguriert sein).
    • Repräsentiert eine logische Nutzer-Entität, die Kommunikationsmodi (COMM_NO_COMMUNICATION, COMM_SILENT_COMMUNICATION, COMM_FULL_COMMUNICATION) anfordert.
  • ComMUserIdentifier (EcucIntegerParamDef):
    • Beziehung: Komposition (+parameter) unter ComMUser.
    • Attribute: min = 0, max = 255, symbolicNameValue = true.
    • Eindeutige numerische ID des Nutzers (Kardinalität implizit 1..1, Datentyp uint8 / ComM_UserHandleType). Dient der Generierung typsicherer symbolischer Header-Konstanten.
  • ComMUserEcucPartitionRef (EcucReferenceDef):
    • Beziehung: Komposition (+reference) unter ComMUser.
    • Multiplizität: 0..1 (Optional).
    • Ziel (+destination): Referenziert EcucPartition ([0..*] aus Package EcucPartition).
    • Dient der Verankerung des Users in einer spezifischen Core-/Memory-Partition für Multicore- und Speicherschutz-Architekturen.
  • ComMUserPerChannel (EcucParamConfContainerDef):
    • Multiplizität: 0..*.
    • Sub-Container (üblicherweise unterhalb von ComMChannel angesiedelt), der die Zuordnung zwischen physischen/logischen Kanälen und Nutzern abbildet.
  • ComMUserChannel (EcucReferenceDef):
    • Beziehung: Komposition (+reference) unter ComMUserPerChannel.
    • Ziel (+destination): Verweist zurück auf ComMUser.
    • Schließt die M:N-Kanal-Nutzer-Relation: Ein Kanal verweist über diese Instanz auf die zugehörigen Nutzer, wodurch ein User gleichzeitig mehrere Kanäle steuern kann und umgekehrt.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches ECUC-Metamodell-Diagramm bildet das Schaubild keinen sequenziellen Kontrollfluss ab; aus der Parameterstruktur resultiert jedoch folgende Laufzeitdynamik:

  1. Modusanforderung: Ein Nutzer ruft synchron ComM_RequestComMode(User, ComM_Mode) auf. Die Zuordnung erfolgt über den aufgelösten ComMUserIdentifier.
  2. Kanalauflösung: Der ComM ermittelt über die durch ComMUserPerChannel und ComMUserChannel generierten Lookup-Tabellen alle zugehörigen Kanäle (ComMChannel) bzw. Channel-Bitmasken.
  3. Zustandsaggregation: Für alle referenzierten Kanäle wird die Modus-Schiedslogik (Mode Arbitration) durchlaufen; der höchste geforderte Kommunikationsmodus setzt sich durch.
  4. Partition-Boundary-Crossing: Ist ComMUserEcucPartitionRef gesetzt und weicht die Partition des Aufrufers von der Master-Partition des ComM ab, vermittelt die SchM (BSW-Scheduler) den Aufruf inter-core über Cross-Core-Interrupts, Satelliten oder RPC.

4. Normative Relevanz & Entwickler-Hinweise

  • Symbolic Name Generation: Da symbolicNameValue = true gesetzt ist, generiert der BSW-Konfigurator Makros nach dem Schema ComMConf_ComMUser_<ContainerName>. Entwickler müssen zwingend diese Makros für Aufrufe von ComM_RequestComMode(), ComM_GetMaxComMode() und ComM_GetCurrentComMode() nutzen.
  • Ressourcenbegrenzung: Der Parameterbereich 0..255 beschränkt die maximale Useranzahl auf 256. Dies erlaubt stack-intern eine speichereffiziente Repräsentation via uint8 (ComM_UserHandleType).
  • Verbindliche Mindestkonfiguration: Aufgrund von lowerMultiplicity = 1 für ComMUser schlägt die Validierung fehl, wenn keine User-Instanz definiert ist (selbst bei reinen Gateway- oder Diagnose-Steuergeräten ist mindestens ein Standard-User, z. B. für den DCM, vorgeschrieben).
  • M:N-Zuordnungsmatrix: Die Verknüpfung erfolgt invertiert (der Kanal referenziert den Nutzer via ComMUserChannel). Fehlkonfigurationen (z. B. unreferenzierte User) führen zu totem Code bzw. wirkungslosen ComM_RequestComMode()-Aufrufen, die zur Laufzeit E_NOT_OK oder DET COMM_E_WRONG_PARAMETERS werfen können.
