1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR EcuC-Metamodell-Diagramm (UML-Klassendiagramm zur Definition der Modulkonfigurationsstruktur).
  • Technischer Zweck & Einordnung: Definiert das formale Konfigurationsschema (EcucModuleDef) für den BSW-Treiber WEthTrcv (Wireless Ethernet Transceiver Driver) gemäß AUTOSAR_SWS_WirelessEthernetTransceiverDriver (R22-11).
  • Architektur-Kontext: Das Modul gehört zur Hardware-Abstraktionsschicht (MCAL / BSW Hardware Interface) für drahtlose Ethernet-Kommunikation (z. B. IEEE 802.11p / V2X / Wireless Ethernet). Es abstrahiert PHY-/Transceiver-Hardwarechips über standardisierte APIs gegenüber dem Wireless Ethernet Interface (WEthIf). Das Schema steuert den Generierungsprozess der statischen (WEthTrcv_Cfg.h) und Post-Build- bzw. Link-Time-Konfigurationsstrukturen (WEthTrcv_PBcfg.c).

2. Komponenten, Entitäten & Schnittstellen

Wurzel- und Struktur-Container
  • WEthTrcv (EcucModuleDef, Multiplizität: 0..*): Modul-Wurzelelement. Erlaubt theoretisch mehrere Instanzen der Moduldefinition.
  • WEthTrcvGeneral (EcucParamConfContainerDef, Multiplizität: 1 [über Komposition +container]): Zentraler Container für globale Pre-Compile-Parameter, API-Freigaben und Laufzeitumgebungseigenschaften.
  • WEthTrcvConfigSet (EcucParamConfContainerDef): Wurzelcontainer für treiberspezifische Initialisierungsdaten.
    • Aggregiert per +subContainer WEthTrcvConfig (EcucParamConfContainerDef, Multiplizität: 1..*).
  • WEthTrcvRadioConfigSet (EcucParamConfContainerDef, Multiplizität: 1..*): Aggregiert funk- und bandspezifische Parameter.
    • Aggregiert per +subContainer WEthTrcvRadioConfig (EcucParamConfContainerDef, Multiplizität: 1..*) zur Parametrierung von Frequenzbändern, Kanälen und Modulationsparametern.
  • WEthTrcvAntennaConfigSet (EcucParamConfContainerDef): Wurzelcontainer für RF-Frontend- und Antenneneigenschaften.
    • Aggregiert per +subContainer WEthTrcvAntennaConfig (EcucParamConfContainerDef, Multiplizität: 1..*) für Antennenpfade, Gain und Diversitätskonfigurationen.
Parameter in WEthTrcvGeneral
  • Numerische Parameter (EcucIntegerParamDef / EcucFloatParamDef):
    • WEthTrcvMaxTrcvsSupported (EcucIntegerParamDef): Bereich 0..255, Default 1. Definiert die maximale Anzahl parallel verwalteter Transceiver-Instanzen.
    • WEthTrcvIndex (EcucIntegerParamDef): Bereich 0..255. Eindeutige numerische Treiber-/Transceiver-ID.
    • WEthTrcvMainFunctionPeriod (EcucFloatParamDef): Bereich 0..INF, Multiplizität 0..1. Zykluszeit für die periodische Taskfunktion WEthTrcv_MainFunction() in Sekunden.
  • API-Konfigurationsschalter (EcucBooleanParamDef):
    • WEthTrcvDevErrorDetect: Default false. Aktiviert DET-Fehlerprüfung (Det_ReportError).
    • WEthTrcvVersionInfoApi: Default false. Schaltet API WEthTrcv_GetVersionInfo() frei.
    • WEthTrcvVersionInfoApiMacro: Default false. Ermöglicht die Bereitstellung der Versionsinfo als prekompiliertes C-Makro statt Funktionsaufruf.
    • WEthTrcvSetTransceiverModeApi: Schaltet WEthTrcv_SetTransceiverMode() frei.
    • WEthTrcvGetTransceiverModeApi: Schaltet WEthTrcv_GetTransceiverMode() frei.
    • WEthTrcvGetLinkStateApi: Schaltet WEthTrcv_GetLinkState() frei.

  • WEthTrcvEcucPartitionRef (EcucReferenceDef, Multiplizität: 0..*): Referenziert per +destination die Zielentität EcucPartition (EcucParamConfContainerDef, Multiplizität: 0..*). Dient der Zuordnung des Moduls bzw. seiner Transceiver zu OS-Partitions in Multicore-/Safety-Systemen.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein metamodellbasiertes Konfigurationsdiagramm handelt, wird kein Kontrollfluss modelliert. Die abgebildeten Parameter bedingen jedoch das Laufzeitverhalten direkt:

  1. Zyklische Zustandsüberwachung:
    • Falls WEthTrcvMainFunctionPeriod definiert ist (> 0), generiert der BSW-Scheduler (SchM / Os) zyklische Aufrufe von WEthTrcv_MainFunction().
    • Die Funktion pollt Hardware-Register, überwacht den RF-Link-State und propagiert Statusänderungen an das übergeordnete WEthIf.
  2. Synchrone Schnittstellenabwicklung:
    • Aufrufe von WEthTrcv_SetTransceiverMode(), WEthTrcv_GetTransceiverMode() und WEthTrcv_GetLinkState() verlangen blockierende oder deterministische SPI-/Register-Zugriffe auf den Funk-Transceiver.
    • Der Zugriff wird nur einkompiliert, wenn der jeweilige Boolean-Parameter im Konfigurationssatz auf true steht.
  3. Fehlerbehandlung (DET):
    • Wenn WEthTrcvDevErrorDetect == true, prüfen alle Schnittstellen den Parameter TrcvIdx gegen WEthTrcvMaxTrcvsSupported bzw. WEthTrcvIndex und melden Bereichsüberschreitungen synchron an den DET (WETHTRCV_E_INV_TRCV_IDX).

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Footprint & Pre-Compile Optimization: Sämtliche *Api-Flags (WEthTrcvGetLinkStateApi, WEthTrcvSetTransceiverModeApi, etc.) müssen als Pre-Processor-Makros (STD_ON / STD_OFF) ausgewertet werden, um ungenutzte Treiber-APIs vollständig zu strippen.
  • RF-Differenzierung gegenüber Ethernet (EthTrcv): Anders als beim kabelgebundenen EthTrcv verlangt das WEthTrcv-Schema getrennte Konfigurationspfade für Funk (WEthTrcvRadioConfigSet) und Antennen (WEthTrcvAntennaConfigSet). Treiberentwickler müssen hier herstellerspezifische RF-Eigenschaften (Kanalbänder, RSSI-Schwellen, Antennen-Diversity) einkapseln.
  • Kardinalitätsrestriktionen:
    • WEthTrcvRadioConfigSet erfordert zwingend mindestens ein Set (lowerMultiplicity = 1). Ein WEthTrcv ohne Funkkonfiguration ist unvollständig und invalidiert die Generierung.
    • WEthTrcvMaxTrcvsSupported begrenzt hardcodierte Tabellengrößen und statische RAM-Puffer für Treiber-Instanzdaten.
  • Multicore / Memory Protection: Liegt WEthTrcvEcucPartitionRef vor, muss der Treiber partitionsübergreifende Aufrufe (z. B. via SchM/BswM) unterstützen und sicherstellen, dass Hardware-Zugriffe nur aus autorisierten Kernen/Partitionen erfolgen.
