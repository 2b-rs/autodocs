1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-2.0-Klassendiagramm (AUTOSAR-M2-Metamodellansicht).
  • Technischer Zweck & Einordnung: Definition des strukturellen Metamodells für hierarchische Software-Kompositionen (CompositionType) und deren Import in das Verhaltensmodellierungs-Paket BM Software-Component (Behavior Modeling).
  • Architektur-Rolle: Implementierung des klassischen GoF-Composite-Musters sowie des AUTOSAR Type-Prototype-Patterns auf Software-Architektur-Ebene: Ermöglicht die hierarchische Aggregation von atomaren Komponenten (AtomicSoftwareComponentType) oder Sub-Compositions zu übergeordneten logischen Einheiten sowie die Spezifikation ihrer Verbindungstopologie für Verhaltens- und Interaktionsanalysen.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • Components::ComponentType (Abstract ARElement):
    • Oberste Abstraktion für alle AUTOSAR-Softwarekomponententypen.
    • Spezialisiert ARElement (Root-Element im AUTOSAR-ARXML-Paketbaum).
  • Composition::CompositionType («atpType»):
    • Konkreter Kompositionstyp; spezialisiert ComponentType (Generalisierung).
    • Trägt das Stereotyp «atpType» (Kennzeichnung als instanziierbarer Typ im AUTOSAR Type-Prototype-Pattern).
  • Composition::ComponentPrototype (Identifiable):
    • Repräsentiert die Verwendung/Instanz eines ComponentType innerhalb des Scopes einer CompositionType.
  • Composition::ConnectorPrototype (Identifiable, abstrakt):
    • Basis-Metaklasse für Schnittstellenverbindungen zwischen Komponenten.
  • Composition::AssemblyConnectorPrototype:
    • Konkrete Spezialisierung von ConnectorPrototype; verbindet Ports zweier ComponentPrototype-Instanzen innerhalb derselben Composition (Peer-to-Peer auf gleicher Hierarchieebene).
  • Composition::DelegationConnectorPrototype:
    • Konkrete Spezialisierung von ConnectorPrototype; verbindet einen äußeren Port der umschließenden CompositionType mit einem Port eines internen ComponentPrototype (Hierarchieüberbrückung nach außen/innen).
  • BM Software-Component (Package from Behavior Modeling):
    • Importiert die strukturellen Entitäten mittels «import»-Abhängigkeiten, um Interaktions- und Verhaltensmodelle an Typ-, Prototyp- und Connector-Instanzen zu binden.
Assoziationen, Aggregationen & Kardinalitäten
  • **CompositionType $\blacklozenge\xrightarrow{\text{+components}\ [1..*]}$ ComponentPrototype:**
    • Strenge Komposition. Eine Composition muss mindestens einen (1..*), typischerweise mehrere Komponenten-Prototypen enthalten.
  • **CompositionType $\blacklozenge\xrightarrow{\text{+connectors}\ [*]}$ ConnectorPrototype:**
    • Strenge Komposition. Eine Composition aggregiert 0 bis n (*) Konnektoren (+connectors).
  • ComponentPrototype $\xrightarrow{\text{«isOfType»}\ \text{+type}\ [1]}$ ComponentType:
    • Typisierungsassoziation («isOfType»). Jeder Prototyp referenziert exakt einen (1) Typ; ein ComponentType kann in beliebig vielen (*) Prototypen wiederverwendet werden.
  • Generalisierungen ($\triangle$):
    • CompositionType → ComponentType (Ermöglicht rekursive Schachtelung: Eine Composition kann selbst Prototyp einer übergeordneten Composition sein).
    • AssemblyConnectorPrototype → ConnectorPrototype.
    • DelegationConnectorPrototype → ConnectorPrototype.

3. Dynamisches Verhalten & Sequenzablauf

  • Diagrammcharakteristik: Rein statisches M2-Strukturmetamodell; kein direkter dynamischer Ablauf dargestellt.
  • Semantische Verhaltensrelevanz für das Runtime-System:
    • Signal-/Datenfluss über Connectors:
      • AssemblyConnector: Löst bei VFB-/RTE-Generierung intra-ECU-Funktionsaufrufe (synchron über Direct Function Calls / OS-Events) oder Inter-Runnable-Kommunikation aus. Bei ECU-übergreifender Verteilung führt er zur Allokation von Signalen auf Bus-Frames (CAN/LIN/FlexRay).
      • DelegationConnector: Reine Schnittstellendurchreichung ohne eigenen RTE-Code-Overhead; eliminiert Hierarchiegrenzen zur Compile-Zeit durch Inlining der Port-Referenzen auf die inneren atomaren Prototypen.
    • Verhaltensmodellierung (BM Software-Component): Definiert Kausalitätsketten, Interaktionsabfolgen (Message Sequences) und End-to-End-Latenzen über Ketten von Prototypen und Konnektoren hinweg.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE- & Code-Generierung:
    • Für CompositionType wird kein eigener C-Code oder Speicher generiert; sie ist ein reines Modellierungs- und Entwurfsartefakt zur architektonischen Kapselung.
    • Die RTE generiert Code ausschließlich für AtomicSoftwareComponentType-Instanzen (RTE Application Header, Rte_<swc>.c).
  • Vollständigkeits- und Konsistenzregeln (Metamodell-Constraints):
    • Dangling Ports: Jeder über einen AssemblyConnector verbundene P-Port und R-Port muss typkompatibel sein (identisches PortInterface).
    • Delegation-Zwang: Externe Ports einer Composition, die nicht über DelegationConnectorPrototype an einen inneren Prototyp angebunden sind, bleiben unversorgt und führen zu RTE-Generierungsfehlern.
    • Instanziierungsregeln: Da ComponentPrototype via «isOfType» auf ComponentType verweist, müssen Multi-Instanziierungen (SupportsMultipleInstantiation = true) vom Komponenten-Entwickler zwingend reentrant implementiert werden (Rte_Instance-Handle als Übergabeparameter).
  • System-Extrakt & ECU-Mapping:
    • Vor der RTE-Generierung flacht der System-Extractor (System Description → ECU Extract) alle CompositionType-Hierarchien ab. Alle enthaltenen atomaren SWC-Prototypen werden flach auf Tasks und ECUs gemappt.

Begleitender Spezifikationstext:

V1.0.6 R4.0 Rev 1 4.2.4 Composition For modeling compositions within a BMT, the AssemblyConnectorPrototype is also required (see Figure 7) to connect a p-port to an r-port. When modeling a Composition within a BMT it has to preserve typing constraints. The Assembly- ConnectorPrototype does not contain any information about the execution behavior of the underlying communication, e.g. blocking/non-blocking, synchronous/asynchronous etc., nor about the underlying communication characteristics, e.g. the bus protocol, bus bandwidth, etc. In some BMTs the port connectors may contain information and refinement regarding different layers of communication. In this case the relevant elements of the AUTOSAR description should be used to retrieve the required information for the BMT or to import the information from the BMT to the AUTOSAR description. On the other hand AssemblyConnectorPrototype may contain some data to exchange attributes concerning the communication between sender and receiver ports, e.g. encryption of the transmitted information, maximum transfer time for DataElementPrototypes, etc., these attributes should be considered with care for proper exchange between the BMT and the AUTOSAR description.
