2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Klassifikation

  • Standardized Header (Normativ festgelegt, weiß hinterlegt):
  • Rte.h: Standardisierte Basis-Headerdatei der RTE mit plattformweiten Statuscodes, Fehlertypen (Std_ReturnType, RTE-Fehlercodes) und grundlegenden Makros.
  • Generated Header & Source (RTE-Generator-Erzeugnisse, grau hinterlegt):
  • Rte.c: Generiertes Kern-C-Modul der RTE (Generated RTE), enthält die Implementierung von Runnable-Triggern, Inter-Runnable-Variablen (IRV), RTE-Puffern, Modus-Management und BSW-Schnittstellenkopplung.
  • Rte_Main.h: Lifecycle-Header mit Deklarationen für Initialisierungs-, Start- und Stop-Funktionen (Rte_Init, Rte_Start, Rte_Stop) sowie Partition-Lifecycle-APIs.
  • Rte_Cbk.h: Generierter Callback-Header; deklariert COM-Callback-Funktionen und Benachrichtigungs-Schnittstellen für die Interaktion zwischen COM-Modul und RTE.
  • Rte_Type.h: Zentraler Typ-Header; aggregiert generierte Datentypen (Implementation Data Types, Mode Declaration Groups, Enumerationen, Ranges).
  • Rte_Cfg.h: Generierte Konfigurationskonstanten, Makrodefinitionen und Feature-Schalter (z. B. Aktivierung von Optimierungen oder Multi-Core-Zuordnungen).
  • VFB Tracing Header File (multipel/gestapelt): Deklaration von VFB-Tracing- und Hook-Routinen für Software-Komponenten zur Laufzeitverfolgung von Task- und Runnable-Aktivierungen sowie Datenflüssen.
  • Rte_DataHandleType.h: Generierte Handle-Typen für Datenzugriffe (z. B. Zeigerstrukturen für implizite/explizite Kommunikation, Calibration Parameters).
  • Application Header File (Rte_<swc>.h, multipel/gestapelt): Komponentenspezifischer Contract-Header für jede Software-Komponente; enthält Port-APIs (Rte_Read_, Rte_Write_, Rte_Call_*) und Component Data Structures (CDS).
  • Application Types Header File (Rte_Type_<swc>.h, multipel/gestapelt): Typschnittstelle pro Software-Komponente für typsichere Deklarationen der Schnittstellendaten.

#### Abhängigkeiten & Kardinalitäten (Inklusionspfade via #include)

  • Direkte Inklusionen von Rte.c:
  • Rte.c $\rightarrow$ Rte_Main.h (1): Bindet Lifecycle-Funktionssignaturen ein.
  • Rte.c $\rightarrow$ Rte_Cbk.h (1): Bindet generierte COM-Callback-Deklarationen ein.
  • Rte.c $\rightarrow$ Rte_Type.h (1): Direkter Zugriff auf systemweite RTE-Datentypen.
  • Rte.c $\rightarrow$ Application Header File (*): Einbindung aller Rte_<swc>.h zur Auflösung der Component Data Structures (CDS), Puffer und Runnable-Signaturen aller auf dem Steuergerät allokierten SWCs.
  • Rte.c $\rightarrow$ VFB Tracing Header File (*): Einbindung der VFB-Tracing-Header aller instrumentierten Komponenten.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um eine statische Header-Hierarchie handelt, greift die Compile-Time-Sequenz:

  1. Include-Guard-Traversierung (Präprozessor):
  • Beim Kompilieren von Rte.c werden die Header inkludiert. Über transitive Pfade (Application Header File $\rightarrow$ Application Types Header File $\rightarrow$ Rte_Type.h $\rightarrow$ Rte.h) wird sichergestellt, dass Basisdatentypen und Standard-Rückgabewerte vor allen komplexen SWC-spezifischen Typen definiert sind.
  1. Namensraum- und Symbolisolation:
  • Mehrfache Inklusionen von Rte_Type.h und Rte.h werden über idempotente Include-Guards (#ifndef RTE_..._H / #define RTE_..._H) abgefangen.
  1. Auflösung von Daten-Handles:
  • Rte_DataHandleType.h stellt sicher, dass Pufferzeiger und Port-Datenstrukturen im Application-Header typisiert aufgelöst werden können, bevor Rte.c Runnable-Wrapper instanziiert.

4. Normative Relevanz & Entwickler-Hinweise

  • Vermeidung von Name Clashes (SWS_Rte_01169 / SWS_Rte_01168):
  • Werden mehrere Application Header Files in Rte.c zusammengeführt, müssen SWC-lokale Symbole, Makros und Typen strikt mit dem Namensraum-Präfix der SWC versehen sein (<swc>_ bzw. Rte_<swc>_), um Mehrfachdeklarationen oder Symbolkollisionen im globalen Scope von Rte.c zu verhindern.
  • Duplikations-Dilemma bei Nicht-Inklusion:
  • Schließt der Generator die Application Header Files nicht in Rte.c ein, müssen alle komponentenspezifischen Typen und CDS-Strukturen redundant in Rte.c oder internen RTE-Headern generiert werden, was Wartbarkeit und Typkonsistenz gefährdet.
  • Partitionierte & Multi-Core-Systeme ([SWS_Rte_02712], [SWS_Rte_02713], [SWS_Rte_02740]):
  • Bei partitionierten RTE-Implementierungen (z. B. auf Multi-Core-ECUs oder bei Memory Protection) kann die RTE in partitionsbezogene C-Module aufgeteilt werden (z. B. Rte_<PartitionName>.c). Die Inklusionsregeln gelten partitionslokal; der Zugriff auf kreuzpartitionierte Datenstrukturen erfordert die getrennte Erzeugung partitionsbezogener Typ- und Konfigurationsheader.
  • Hook-Konfiguration (Rte_Hook.h):
  • Tracing-Hooks hängen von Rte_Cfg.h ab. Werden VFB-Tracing-Features im RTE-Generator deaktiviert, müssen Hook-Makros leer expandiert werden (inline oder No-Op-Makros), um keinen Laufzeit-Overhead im generated C-Code zu erzeugen.
