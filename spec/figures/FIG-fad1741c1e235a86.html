3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die statische Konfiguration für folgenden deterministischen Laufzeitablauf in der RTE:

```

[Sender-SWC / Com]

│

│ Signal empfangen mit Payload == SwDataDefProps.invalidValue

▼

[RTE: RPort / NonqueuedReceiverComSpec]

│

├─► Prüfung InvalidationPolicy.handleInvalid:

│ ├─ [replace] ──► Puffer mit NonqueuedReceiverComSpec.initValue überschreiben;

│ │ Rte_Read liefert initValue und Return RTE_E_INVALID.

│ ├─ [keep] ──► Vorherigen Wert im Puffer beibehalten (nicht überschreiben);

│ │ Rte_Read liefert alten Wert und Return RTE_E_INVALID.

│ └─ [dontInvalidate] ──► invalidValue wird wie reguläre Nutzlast behandelt;

│ Rte_Read liefert empfangenen Wert und Return RTE_E_OK.

▼

[Empfänger-SWC via Rte_Read()]

```

  • Trigger: Empfang eines Signals über das Com-Modul oder Intra-ECU-Übertragung via Rte_Write / Rte_Invalidate.
  • Auswertung: Stimmt der empfangene Roh-/Netzwerkwert mit dem über networkRepresentation.invalidValue definierten Muster überein, greift die an der Interface-Instanz definierte InvalidationPolicy.
  • Fehlerpfade & Prioritäten: Die Invalidierung interagiert mit aliveTimeout (NonqueuedReceiverComSpec). Tritt gleichzeitig ein Timeout ein, greift vorrangig die Timeout-Behandlung (handleTimeoutType).

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Konsistenzbedingungen:
  • Wenn für ein VariableDataPrototype eine InvalidationPolicy mit handleInvalid = replace konfiguriert ist, muss im korrespondierenden NonqueuedReceiverComSpec zwingend ein gültiger initValue definiert sein.
  • SwDataDefProps.invalidValue muss typkompatibel zu der durch das AutosarDataPrototype referenzierten ImplementationDataType / ApplicationDataType bzw. deren Netzwerk-Repräsentation (Com-Signal) sein.
  • RTE-API-Vertrag (Applikationsentwickler):
  • Bei konfiguriertem Invalidation-Handling (replace oder keep) liefert Rte_Read_<p>_<o>(...) den Rückgabewert RTE_E_INVALID (0x02), sobald ungültige Daten erkannt wurden.
  • SWC-Code muss den Rückgabewert zwingend abfangen:

```c

Std_ReturnType status = Rte_Read_RPort_DataElement(&data);

if (status == RTE_E_INVALID) {

/ Degradierungsstrategie / Failsafe-Zustand /

}

```

  • Bei dontInvalidate generiert der RTE-Generator keinen Code zur Prüfung des invalidValue; die Applikation sieht niemals RTE_E_INVALID.
  • Com-Stack- & BSW-Konfiguration:
  • networkRepresentation.invalidValue korreliert mit dem BSW-Parameter ComSignalDataInvalidValue im Modul Com. Bei Signal-Invalidierung über den Bus sorgt das Com-Modul bzw. die RTE anhand dieser Metamodell-Einträge für das Signal-Routing und die Maskierung.
