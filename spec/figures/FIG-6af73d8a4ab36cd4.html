1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR BSW-Schichtenarchitektur / Schichtenmodell (Blockdiagramm mit Schichtenzuordnung und Controller-Topologien).
  • Technischer Zweck: Spezifikation der Einbettung von CAN XL (Payload bis zu 2048 Byte, Baudraten bis zu 10+ Mbit/s, VCID-Routing) in den AUTOSAR Classic Platform Kommunikations-Stack (Releases R24-11 / R25-11).
  • Funktionale Einordnung:
    • Erweiterung des klassischen CAN/CAN-FD-Stacks um den L-SDU Router in der Communication Hardware Abstraction Layer.
    • Anbindung von Großdaten-Pfaden (Large Data COM / LdCom) direkt über den PDU Router (PduR) unter Umgehung von TP-Segmentierungen.
    • Koexistenz zweier Hardware-Integrationspfade: On-Chip CAN-XL-Controller vs. extern angebundener CAN-XL-ASIC via SPI/DIO.

2. Komponenten, Entitäten & Schnittstellen

Schichten & Module (Top-Down):
  • Communication Services (Dienstschicht):
    • Large Data COM (LdCom): Direkte Serialisierung/Deserialisierung großer Signale/PDUs bis 2048 Byte ohne TP-Fragmentierungs-Overhead.
    • AUTOSAR COM (Com): Signalbasiertes Routing für Standard-PDUs.
    • Diagnostic Communication Manager (Dcm) & Diagnostic Log and Trace (Dlt): Diagnose- und Trace-Services.
    • Secure Onboard Communication (SecOC) & IPDU Multiplexer (IpduM): Authentifizierung/Kryptografie bzw. Multiplexing von PDU-Layouts.
    • PDU Router (PduR): Zentrales statisches Routing von I-PDUs zwischen oberen Services, CanTp und dem Abstraktions-Layer.
    • CAN Transport Protocol (CanTp): Klassische Segmentierung/Reassemblierung (ISO 15765-2), relevant für Legacy-Kommunikation oder wenn PDUs das CAN-XL-Maximum überschreiten.
    • CAN State Manager (CanSM) & CAN Network Management (CanNm) / Generic NM Interface (Nm): Netzwerk- und Buszustandsverwaltung sowie Sleep/Wakeup-Handling.
  • Communication Hardware Abstraction (Hardware-Abstraktionsschicht):
    • L-SDU Router (LSduR): Schlüsselelement für CAN XL. Führt Header-Inspektion und Demultiplexing/Routing von Data-Link-Layer SDUs (L-SDUs) anhand von VCID (Virtual CAN Network ID), SDT (SDU Type) und Acceptance Fields durch.
    • CAN Interface (CanIf): Vereinheitlichte Schnittstelle für obere Schichten; abstrahiert verschiedene Controller-Typen.
    • CAN Transceiver Driver (CanTrcv): Steuert CAN-XL-Transceiver (Unterstützung von SIC-XL-, FAST-TX/RX-Modi und PWM-Kodierung).
    • Driver for ext. CAN ASIC: Abstraktionstreiber für externe Standalone-CAN-XL-Controller.
  • Microcontroller Abstraction Layer (MCAL):
    • CAN Driver (Can / inkl. CAN XL Erweiterung): Direkter hardwarenaher Registertreiber für On-Chip CAN-XL-IP-Cores (Message RAM, FIFO/Dedicated Tx Buffers).
    • SPIHandler Driver (Spi): Synchrone/asynchrone Datenübertragung zum externen CAN-XL-ASIC.
    • DIO Driver (Dio): Hardware-Pins für Transceiver-Steuerung (Standby/Normal), Interrupt-Signalisierung und Reset-Leitungen des externen ASICs.
  • Hardware-Ebene ($\mu\text{C}$ & Extern):
    • Integrierte CAN-XL-Hardware-Peripherie auf dem Mikrocontroller.
    • Externer CAN-XL-Controller, angebunden über SPI-Bus und diskrete Steuerleitungen.

3. Dynamisches Verhalten & Sequenzablauf

Datenpfad (Senden / Empfangen):
  1. LdCom / COM → PduR → LSduR → CanIf:
    • Großdaten (bis 2048 Byte) fließen von LdCom direkt über PduR zum LSduR.
    • Der LSduR bindet Metadaten (VCID, AF - Acceptance Field, SDT) an die L-SDU und übergibt an CanIf.
  2. CanIf → Treiber:
    • On-Chip: Direkter Call Can_Write() in den internen CAN-XL-Treiber; Speicherung im Message-RAM/TX-FIFO.
    • Externer Controller: CanIf ruft den ASIC-Treiber auf → PDU wird über Spi_AsyncTransmit() an den externen Controller übertragen.
  3. Rx-Indication:
    • Hardware-Interrupt → Can_RxIndication (bzw. SPI-Rx-Complete) → CanIf_RxIndication → LSduR wertet VCID/SDT aus und routet an PduR → LdCom / Com / CanTp.
Kontrollpfad (Modi & Fehlerbehandlung):
  • Zustandsübergänge: CanSM triggert Moduswechsel (Wakeup, Sleep, Normal) koordiniert über CanIf an CanTrcv und Can.
  • SIC/XL-Transceiver Umschaltung: Zur Laufzeit dynamischer Wechsel zwischen Arbitrations-Phase (NRZ) und Datenphase (PWM / Fast Mode) über Hardware/Transceiver-Modi.
  • Diagnose/Fehler: Asynchrone Benachrichtigung bei Bus-Off oder Protocol Exception via CanIf_ControllerBusOff() an CanSM; Detektion via Det / Dem.

4. Normative Relevanz & Entwickler-Hinweise

  • Puffer- und RAM-Dimensionierung:
    • CAN XL erlaubt Nutzlasten von 1 bis 2048 Byte. Statische Bufferpools in CanIf, LSduR, PduR und LdCom müssen explizit für maximale XL-Framegrößen konfiguriert werden; unbedachte Allokation führt zu massivem RAM-Verbrauch im BSW-Stack.
  • L-SDU Router Konfiguration:
    • Obligatorische Parametrierung der Routing-Tabellen im LSduR basierend auf VCID (Virtual CAN Network ID) und SDT (Payload Type). Das L-SDU-Header-Handling erfordert exakte Abstimmung mit der Netzwerk-Matrix (ARXML/Fibex).
  • Treiber-Architektur & Latenz (SPI vs. On-Chip):
    • Bei Einsatz eines externen CAN-XL-ASIC via SPI entsteht signifikanter Latenz- und CPU-Overhead für DMA/SPI-Transfers bei 2048-Byte-Frames. Deadlines für zeitkritische Signale müssen in den Task-Prioritäten (SpiHandler, Polling/ISR) explizit berechnet werden.
  • Transceiver-Konfiguration (CiA 610-1 / ISO 11898-2:2024):
    • CanTrcv muss zwingend für CAN-XL-fähige Transceiver parametriert werden, um Tx-Bit-Shaping, FAST-Mode-Umschaltung und Rx-Empfindlichkeit im High-Speed-Bereich (z. B. bis 10/20 Mbit/s) korrekt anzusteuern.
  • TP-Bypass:
    • Klassisches CanTp entfällt für Nutzlasten ≤ 2048 Byte. Software-Architekten müssen Signalgruppen von Com/CanTp auf LdCom migrieren, um die volle Bandbreite ohne Protokoll-Overhead zu nutzen.
