1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptuelles Schichten- und Isolationsmodell (Blockdiagramm mit Sicherheitsdomänen-Segmentierung gemäß GlobalPlatform-Spezifikation).
  • Architektur-Kontext:
    • Systemweite Partitionierung eines Steuergeräts (SoC/Microcontroller) in zwei hardware- und software-isolierte Ausführungsumgebungen: REE (Rich Execution Environment, z. B. POSIX OS/Linux für AUTOSAR Adaptive oder Standard-RTOS) und GPD TEE (GlobalPlatform Device Trusted Execution Environment für sicherheitskritische Dienste, Crypto-Workloads und Key-Storage).
    • Funktionale Einordnung in AUTOSAR (AUTOSAR_FO_EXP_SecurityOverview, R24-11 / R25-11): Basis-Sicherheitsarchitektur zur Kapselung von Crypto-Primitives, Secure Key Management, Secure Boot Verifikation und Identity Management jenseits ungeschützter Applikations-Stacks (Abgrenzung/Ergänzung zu SHE/HSM und AUTOSAR Crypto Stack Crypto / CSM / SecOC / vSecM).

2. Komponenten, Entitäten & Schnittstellen

Sicherheitsdomänen & Trennlinien (TEE Isolation Boundary)
  • Fixed Isolation Boundary (durchgezogene rote Linie): Durch Hardware-Sicherheitsmechanismen (z. B. Arm TrustZone, Memory Protection Units, Stage-2-Paging) realisierte statische Trennung gemäß GPD TEE Protection Profile (TEE PP). Verhindert unautorisierten Direktzugriff aus der REE auf GPD-TEE-Ressourcen.
  • Transferable Isolation (gestrichelte rote Linie): Dynamische/übertragbare Isolation für Shared Trusted Peripherals. Zugriffsumschaltung unterliegt strikt der Hardwarerechteverwaltung unter permanenter Kontrolle der Trusted-Domäne.
Entitäten der REE (Normal World / Rich Execution Environment)
  • Normal REE Application(s): Nicht-vertrauenswürdige Standardanwendungen ohne direkte TEE-Interaktion.
  • Client Application(s): REE-Anwendungen (z. B. AUTOSAR Adaptive Application oder Classic BSW/SecOC-Stack), die TEE-Dienste konsumieren. Enthalten dedizierte Puffer für Shared Memory.
  • GPD TEE Client API: Standardisierte User-Space-Bibliothek (GPD_SPE_007) zur Sitzungs- und Kontextverwaltung mit dem TEE.
  • GPD TEE Protocol Specs: Protokollschicht für den strukturierten Befehls- und Datenaustausch über die Domänengrenze.
  • Regular OS Components:
    • Public Device Drivers: Treiber für ungesicherte Peripherie.
    • REE Communication Agent: OS-spezifischer Treiber/Kernel-Modul (z. B. Linux /dev/tee*, ARM SMC/HVC Dispatcher) zur Übermittlung von Messages an den Trusted Monitor/Kernel.
  • Public Peripherals: Hardware-Peripherie ohne Sicherheitsbeschränkung.
Entitäten des GPD TEE (Secure World / Trusted Execution Environment)
  • Trusted Application(s) (TA): Isolierte, verifizierte Softwaremodule im TEE (z. B. Key Provisioning, Signature Generation, Secure Storage). Kommunizieren untereinander über Internal Client API und verwalten einen synchronisierten Shared Memory View.
  • GPD TEE Internal Core API & Extensions: Native POSIX-nahe bzw. GP-spezifische Systemschnittstelle (GPD_SPE_010) für TAs (Crypto, Secure Storage, Time, Memory).
  • Trusted OS Components:
    • TEE Communication Agent: Gegenstelle im Trusted OS zur Annahme von REE-Aufträgen.
    • Trusted Core Framework & Trusted Kernel: Privilegierter Kern mit Prozessisolation, Scheduling und MMU-/MPU-Verwaltung für TAs.
    • Trusted Device Drivers: Exklusive Treiber für sicherheitskritische Hardware.
  • Trusted Peripherals / Shared Trusted Peripherals: Exklusive Hardware-Einheiten (z. B. True-RNG, Crypto-Beschleuniger, eFuses/OTP) bzw. zeitweilig geteilte I/O.
Schnittstellen & Kantenmetrik (Key)
  • Application Interfaces (hellblaue Konturpfeile): Funktionsaufrufe innerhalb des jeweiligen OS-User-/Kernel-Space (z. B. POSIX/GP-APIs).
  • Low-Level Message Routing (dunkelblaue Vollpfeile): IPC/HW-Kanäle (Inter-World Callbacks, SMC/SVC-Traps, Secure Mailboxes, Driver-Access).
  • Shared / Synchronized Memory (schwarze Doppelpfeile): Zero-Copy-Datenübertragung via gemeinsam genutztem, vom TEE validiertem RAM (Shared Memory vs. Shared Memory View).

3. Dynamisches Verhalten & Sequenzablauf

  1. Context Initialization & Session Open:
    • Eine Client Application instanziiert über die GPD TEE Client API eine Verbindung (TEEC_InitializeContext) und fordert eine Session zu einer spezifischen TA per UUID an (TEEC_OpenSession).
  2. Buffer Registration / Parameter Marshaling:
    • Registrierung oder Allokation von Shared Memory im REE-User-Space (TEEC_RegisterSharedMemory / TEEC_AllocateSharedMemory).
    • Bereitstellung von Input-/Output-Parametern; Mappen des Speichers in den Shared Memory View der Ziel-TA durch den Trusted Kernel.
  3. Command Invocation (World Switch):
    • Client Application triggert TEEC_InvokeCommand.
    • REE Communication Agent initiiert einen synchronen CPU-Trapping-Befehl (z. B. SMC / HVC).
    • Hardware vollzieht den World-Switch; Eintritt in den Trusted Kernel via Secure Monitor.
  4. Execution & TA Internal Processing:
    • TEE Communication Agent empfängt die deserialisierte Nachricht und routet sie via Trusted Core Framework zur adressierten Trusted Application.
    • TA verarbeitet die Daten über die GPD TEE Internal Core API (Zugriff auf Trusted Peripherals wie Hardware-Kryptoeinheiten). Optional: Aufruf weiterer TAs.
  5. Completion & World Return:
    • TA setzt Rückgabestatus und beschreibt den Shared Memory View.
    • Trusted OS gibt die Kontrolle über Monitor-Trap an den REE Communication Agent zurück; Rückkehr in die GPD TEE Client API zur Client Application.

4. Normative Relevanz & Entwickler-Hinweise

  • Crypto-Treiber-Entwicklung (CSM/Crypto Interface in AUTOSAR):
    • Wird ein TEE als Crypto-Backend angebunden, implementiert der AUTOSAR Crypto Driver (Crypto_30_xxx bzw. ara::crypto) die Rolle der Client Application und nutzt die GPD TEE Client API.
    • Synchrone World-Switches (SMC) erzeugen CPU-Stalls in der REE: Zeitkritische Crypto-Jobs (z. B. SecOC-Signaturprüfung im CAN/Ethernet-Pfad) erfordern asynchrone Auftragsverarbeitung über Queues im Shared Memory, um Task-Blockaden der AUTOSAR-OS-Tasks zu vermeiden.
  • Memory Integrity & Cache Coherency (Shared Memory):
    • Entwickler müssen Cache-Flush- und Invalidate-Operationen vor und nach dem World-Switch strikt einhalten. Der REE-Pointer darf innerhalb der TA niemals dereferenziert werden, ohne dass die Grenzen gegen den autorisierten Shared Memory View validiert wurden (Schutz vor Time-of-Check to Time-of-Use / TOCTOU-Angriffen).
  • API-Verträge & Fehlerbehandlung:
    • Fehler im TEE führen zu standardisierten GlobalPlatform-Return-Codes (z. B. TEEC_ERROR_ACCESS_DENIED, TEEC_ERROR_COMMUNICATION). Diese müssen im AUTOSAR-Stack auf AUTOSAR-konforme Rückgabewerte (E_NOT_OK, CRYPTO_E_BUSY) gemappt und bei Sicherheitsverletzungen an das Intrusion Detection System (IDS / IdsM) weitergeleitet werden.
  • Shared Peripherals:
    • Nutzt die Applikation Shared Trusted Peripherals, muss hardwareseitig sichergestellt sein, dass Umschaltvorgänge (Ownership Transfer) atomar erfolgen und vor der Rückgabe an die REE alle Registerinhalte und Puffer sicher durch das Trusted OS gelöscht werden (Sanitization).
