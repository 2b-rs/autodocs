1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR VFB-/RTE-Architektur- und Interaktionsdiagramm (Schichten- und Datenflussmodell).
  • Funktionale Einordnung & Zweck: Darstellung der warteschlangenbasierten Sender-Empfänger-Kommunikation (Queued Sender-Receiver Communication) über Software-Cluster-Grenzen hinweg unter Verwendung eines Cross Software Cluster Communication Plug-Ins (XCC-Plug-In nach SRS_Rte_00300, SRS_Rte_00306).
  • Architektonischer Schwerpunkt: Realisierung eines N:1-Kommunikationsmusters (Fan-In / Merge), bei dem sowohl ein cluster-interner Sender (SWCA) als auch eine cluster-externe Quelle (über den Begrenzungs-/Delegations-Port des Clusters) asynchron Daten in dieselbe FIFO-Warteschlange einspeisen, welche von einer cluster-lokalen Empfänger-Komponente (SWCB) konsumiert wird.

2. Komponenten, Entitäten & Schnittstellen

  • Software Cluster Root Composition (CompositionSwComponent „rootSwc“):
  • Kapselt den Software-Cluster als eigenständige Deployment- und Update-Einheit.
  • Besitzt einen externen R-Port (Delegationsport zur Cluster-Umgebung) für eingehende, externe Queued-Nachrichten.
  • Software-Komponenten (SWCs):
  • Atomic Software Component „SWCA“ (Lokaler Sender):
  • Enthält die RunnableEntity swcaRun1.
  • Greift über einen dataSendPoint auf ihren P-Port zu.
  • Atomic Software Component „SWCB“ (Lokaler Empfänger):
  • Enthält die RunnableEntity swcbRun1.
  • Greift über einen dataReceivePoint auf ihren R-Port zu.
  • RTE-Schicht (Standard Runtime Environment):
  • Stellt die standardisierten VFB-APIs für die SWCs bereit:
  • Rte_Send_pQDat_QDat(): Standard-Schnittstelle für SWCA.
  • Rte_Receive_rQDat_QDat(): Standard-Schnittstelle für SWCB.
  • Cross Software Cluster Communication Plug-In (XCC-Schicht):
  • Cross Cluster Communication of Software Cluster Connection:
  • Vermittlungsschicht/Treiber zur Kapselung des clusterübergreifenden IPC-/Shared-Memory-Transports.
  • Generierte XCC-Schnittstellen (gemäß SWS_Rte_70090):
  • Rte_MyXcc_Write_SWCA_QDat(): Plug-In-Write-Hook für lokale Sender.
  • Rte_MyXcc_Read_SWCB_QDat(): Plug-In-Read-Hook für lokale Empfänger.
  • Warteschlangen-Instanz (FIFO Buffer):
  • Entkopplungselement für die N:1-Kommunikation.
  • Schnittstellenpfade:
  • local enqueue access: Lokaler Schreibpfad von SWCA via RTE und XCC-Write-Hook.
  • external enqueue access: Cluster-externer Schreibpfad direkt über den XCC-Transportmechanismus.
  • local dequeue access: Lokaler Lesepfad aus der Queue via XCC-Read-Hook in die RTE zur SWCB.

3. Dynamisches Verhalten & Sequenzablauf

#### Lokaler Sendepfad (SWCA $\rightarrow$ Queue)

  1. swcaRun1 führt eine Schreiboperation am konfigurierten dataSendPoint aus.
  2. Aufruf der Standard-API Rte_Send_pQDat_QDat(&data).
  3. Die RTE delegiert den Schreibaufruf an den XCC-Hook Rte_MyXcc_Write_SWCA_QDat(&data).
  4. Das Plug-In reiht das Datenelement atomar via local enqueue access in die FIFO-Warteschlange ein.

#### Externer Sendepfad (Cross-Cluster $\rightarrow$ Queue)

  1. Ein externer Cluster sendet das Datenelement über das zugrunde liegende Transportmedium (z. B. Shared Memory, IPC oder Inter-OS-Communication).
  2. Der XCC-Treiber des Ziel-Clusters empfängt die Daten und reiht sie via external enqueue access direkt in denselben FIFO-Puffer ein.

#### Lokaler Empfangspfad (Queue $\rightarrow$ SWCB)

  1. swcbRun1 initiiert den Lesezugriff am dataReceivePoint (zyklisch/polling-basiert via Rte_Receive oder getriggert durch ein DataReceivedEvent).
  2. Aufruf der Standard-API Rte_Receive_rQDat_QDat(&data).
  3. Die RTE ruft den XCC-Hook Rte_MyXcc_Read_SWCB_QDat(&data) auf.
  4. Das älteste Element wird via local dequeue access aus der Queue entnommen und an den Empfänger übergeben.

#### Fehler- und Abbruchverhalten (gemäß SWS_Rte_70107)

  • Queue Overflow: Ist die Warteschlange voll, schlägt local enqueue access bzw. external enqueue access fehl. Rte_Send gibt RTE_E_LIMIT zurück; der externe Sender erhält den entsprechenden clusterübergreifenden Fehlerstatus.
  • Queue Empty: Ist die Warteschlange leer, liefert Rte_Receive den Rückgabewert RTE_E_NO_DATA.

4. Normative Relevanz & Entwickler-Hinweise

  • VFB-Transparenz für Applikationsentwickler:
  • Für SWCA und SWCB bleibt die Cluster-Grenze vollständig abstrahiert. Es werden ausschließlich klassische VFB-APIs (Rte_Send, Rte_Receive) verwendet. Ein Redesign der SWCs bei Cluster-Reallokation entfällt.
  • XCC-Plug-In-Implementierung & Konfiguration (SWS_Rte_70090, SWS_Rte_70107):
  • Die RTE instanziiert für Queued-Verbindungen über Clustergrenzen hinweg keine RTE-internen Ringpuffer, sondern delegiert die Pufferverwaltung vollständig an das XCC-Modul.
  • Das Plug-In muss threadsichere und ggf. multicore-/partitionssichere Enqueue- und Dequeue-Operationen garantieren (z. B. über lockfreie Ringpuffer oder atomare Mutex-Mechanismen im Shared Memory).
  • Dimensionierung der Queue:
  • Da es sich um ein N:1-Merge-Szenario handelt, muss queueLength in der Software-Komponenten-Beschreibung unter Berücksichtigung der addierten Erzeugungsraten (lokaler Sender + externe Sender) und der Abarbeitungsfrequenz von swcbRun1 ausgelegt werden, um Pufferüberläufe (RTE_E_LIMIT) zu vermeiden.
  • Speicher- und Schutzbereichskonfiguration:
  • Der Puffer muss in einem Speichersegment platziert werden, auf das der XCC-Treiber (oft mit BSWM-/OS-Privilegien) zugreifen kann. Befindet sich der externe Cluster in einer separaten MPU/MMU-Domäne, ist sicherzustellen, dass Zugriffsrechte für den externen Enqueue-Pfad hardwareseitig isoliert und validiert sind.
