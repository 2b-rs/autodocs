1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Metamodell-Klassendiagramm (AUTOSAR M2/M1-Metamodell-Ausschnitt des Security Extract Templates).
  • Technischer Zweck: Formale Spezifikation der Metaklassen zur eindeutigen Identifikation und Modellierung von Kontextdaten für Sicherheitsereignisse (TPS_SECXT_03000 zu RS_SECXT_00009).
  • Funktionale Einordnung: Dient im AUTOSAR IdsM (Intrusion Detection System Manager) der modularen Entkopplung standardisierbarer, herstellerweiter Ereignis-/Kontextdefinitionen (M1-Standard-Artefakte) von projektspezifischen Instanziierungen und Modell-Referenzen (ECU-/Projekt-Artefakte).

2. Komponenten, Entitäten & Schnittstellen

Das Metamodell trennt strikt zwischen zwei Domänen:

Standardizable Model Elements (Plattform-/OEM-Ebene)
  • SecurityEventDefinition (IdsCommonElement):
    • Attribut: id: PositiveInteger [0..1] (eindeutige Security-Event-Kennung).
    • Assoziation: +securityEventContextDataDefinition (0..*, «atpVariation, atpSplitable») zu Kontextdaten-Containern.
  • SecurityEventContextDataDefinition (IdsCommonElement):
    • Attribut: version: PositiveInteger [0..1] (Schema-Versionierung der Kontextdefinition).
    • Komposition: +contextDataElement (0..*, {ordered}, «atpVariation, atpSplitable») auf Feldelemente.
  • SecurityEventContextDataElement (Identifiable):
    • Attribut: maxLength: PositiveInteger [0..1] (maximale Bytegröße des Nutzdatenfelds).
    • Assoziation: +securityEventReportInstanceDefinition (0..1, «atpSplitable») zur Typdefinition.
  • SecurityEventReportInstanceDefinition (IdsCommonElement):
    • Attribute: contextTypeList: String [0..*] {ordered}, targetType: String [0..1] (definiert den semantischen Typ der Zielinstanz).
Project-specific Model Elements (ECU-/Integrations-Ebene)
  • SecurityEventContextMapping (IdsMapping):
    • Aggregations-Root für projektspezifische Zuordnungen.
    • Komposition: +mappedSecurityEvent (0..*, «atpVariation, atpSplitable») auf Eigenschaften.
  • SecurityEventContextProps (Identifiable):
    • Attribute: defaultReportingMode: SecurityEventReportingModeEnum [0..1], persistentStorage: Boolean [0..1], sensorInstanceId: PositiveInteger [0..1], severity: PositiveInteger [0..1].
    • Assoziation: +securityEvent (0..1, «atpVariation, atpSplitable») referenziert die abstrakte SecurityEventDefinition.
  • SecurityEventReportInstanceValue (IdsCommonElement):
    • Attribut: id: PositiveInteger [0..1] (konkrete Instanz-ID zur Laufzeit).
    • Assoziation: +contextDataElementIdentification (0..1, «atpVariation, atpSplitable») verknüpft auf das generische SecurityEventContextDataElement.
    • Instanzierungs-Referenzen:
      • +flatObject (0..1, «atpUriDef») auf Referrable (mit shortName: Identifier, «atpIdentityContributor»): Direkte flache URI-Referenzierung.
      • +object (0..1, «instanceRef, atpUriDef») auf AtpFeature (Identifiable): Hierarchische Modell-Instanzreferenz (z. B. konkreter Port, Interface oder BSW-Instanz).
Stereotypen & Modellierungs-Semantik
  • «atpVariation»: Unterstützt AUTOSAR Variant Handling (Pre-Compile, Link-Time, Post-Build Bindungszeiten).
  • «atpSplitable»: Ermöglicht die Aufteilung der Datenstrukturen über separate ARXML-Liefereinheiten.
  • «instanceRef» / «atpUriDef»: Formale AUTOSAR-Instanzpfad-Auflösung zur exakten Lokalisierung der Event-Quelle im Gesamtsystemmodell.

3. Dynamisches Verhalten & Sequenzablauf

Aus dem Metamodell resultiert folgender Verarbeitungs- und Zuordnungsablauf im IdsM-Stack:

[Security Sensor / SWC / BSW]
              │
              │ 1. IdsM_SetSecurityEvent(EventId, ContextData, Length)
              ▼
           [IdsM]
              │
              ├── 2. Validierung: ContextData.Length <= SecurityEventContextDataElement.maxLength
              │
              ├── 3. Filterung / Props-Check:
              │      Prüfung gegen SecurityEventContextProps
              │      (severity, defaultReportingMode, persistentStorage)
              │
              ├── 4. Instanz-Auflösung:
              │      Auflösung der Event-Quelle über SecurityEventReportInstanceValue.id
              │      (korreliert via contextDataElementIdentification mit Zielobjekt)
              │
              ▼
   [QSEv Dispatch / Persistierung]
   (Optional: NvM-Schreibzugriff bei persistentStorage == TRUE; Weiterleitung an IdsR / VSOC)
  • Trigger: Sicherheits-Sensor (z. B. CanSM, SecOC, Firewall, Applikations-SWC) detektiert eine Anomalie und meldet das Event via IdsM-API.
  • Synchroner Pfad: Validierung der Pufferlänge gegen maxLength und Zuordnung zur registrierten sensorInstanceId. Bei Längenüberschreitung greift der DET-Fehlerpfad (IDSM_E_PARAM_INVALID).
  • Asynchroner Pfad: Sofern persistentStorage == true, wird das qualifizierte Event (QSEv) zur nicht-flüchtigen Speicherung an den NvM übergeben; parallele Pufferung für Reporting/Telematik (IdsR/VSOC).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur- und OEM/Tier-1-Schnittstelle:
    • Standardisierbare Pakete (OEM-Basis) können unverändert in Projekten wiederverwendet werden.
    • Tier-1-Integratoren müssen ausschließlich den Block Project-specific model elements ausprägen, um SecurityEventContextProps (ECU-spezifische Sensor-IDs, Severity) und SecurityEventReportInstanceValue (konkrete Ports/Features via URI/InstanceRef) zu binden.
  • Puffer- und Memory-Dimensionierung:
    • Die BSWM- bzw. IdsM-Codegenerierung leitet aus SecurityEventContextDataElement.maxLength die statischen RAM-Puffergrößen für die Kontext-Frames ab. Dynamische Speicherallokation ist im Classic Platform IdsM unzulässig.
    • Durch das Constraint {ordered} an contextDataElement ist die Serialisierungsreihenfolge im Übergabepuffer binär strikt vorgegeben.
  • Eindeutigkeit & Konsistenz:
    • SecurityEventReportInstanceValue.id muss im Kontext der jeweiligen sensorInstanceId eindeutig sein, um im Backend (VSOC) eine kollisionsfreie Rückauflösung auf das referenzierte Modellelement (AtpFeature bzw. Referrable) zu garantieren.
