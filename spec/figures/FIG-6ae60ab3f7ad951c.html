1. Diagrammtyp & Architektur-Kontext

Das Diagramm kombiniert ein UML-Klassendiagramm/Metamodell-Ausschnitt für ein Modus-Deklarationsmodell mit einem UML-Zustandsdiagramm, das das Mapping der internen Zustände der EcuM-Hauptzustandsmaschine (ECU State Manager) auf deklarierte RTE-Modi abbildet. Es gehört zur AUTOSAR Classic Platform (ECU State Manager, EcuM) und beschreibt, wie die BSW-internen Sub-Zustände der Hauptzustandsmaschine zu übergeordneten RTE-Modi zusammengefasst und über das Mode Management an Software-Komponenten (SW-Cs) und BSW-Module propagiert werden.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in zwei Hauptpakete bzw. -rahmen:

  • Mode Declaration Model:
  • EcuM_Mode : ModeDeclarationGroup: Verwaltet die Modusgruppe mit der Initialmodus-Referenz +initialMode auf STARTUP sowie Kompositionsbeziehungen +modeDeclarations zu den Deklarationen:
  • STARTUP : ModeDeclaration
  • RUN : ModeDeclaration
  • POST_RUN : ModeDeclaration
  • WAKE_SLEEP : ModeDeclaration
  • SLEEP : ModeDeclaration
  • SHUTDOWN : ModeDeclaration
  • Mapping of States to Mode Declarations:
  • Modusbereiche (gestrichelte Hüllzustände/Grenzen), die jeweils einer ModeDeclaration zugeordnet sind:
  • Mode Startup: enthält den internen Zustand STARTUP II (from Main State Machine).
  • Mode Run: umfasst RUN II (from Main State Machine) innerhalb des übergeordneten Zustands RUN.
  • Mode Post Run: umfasst RUN III (from Main State Machine) innerhalb von RUN sowie Perform PREP SHUTDOWN (from Main State Machine) innerhalb von SHUTDOWN.
  • Mode WakeSleep: umfasst Time Triggered Increased Inoperation (from Main State Machine).
  • Mode Sleep: umfasst WAKEUP (from Main State Machine), SLEEP (from Main State Machine) und Perform GO SLEEP (from Main State Machine).
  • Mode Shutdown: umfasst Perform GO OFF I (from Main State Machine) innerhalb von SHUTDOWN.
  • Schnittstellen & Aktionen: Benachrichtigungsaktionen (/notify) bei Moduswechseln sowie interne Trigger/Bedingungen (Run-Requests, Wakeup-Events, Reset/Off).

3. Dynamisches Verhalten & Sequenzablauf

Das dynamische Verhalten folgt den Transitionen der EcuM-Hauptzustandsmaschine und deren Benachrichtigungstriggern:

  • Startup-Phase:
  • Aus STARTUP II erfolgt bei normal startup /notify der Übergang nach RUN II (Eintritt in Mode Run).
  • Alternativ führt wakeup source with integrated power control /notify direkt von STARTUP II nach WAKEUP in Mode Sleep.
  • Run- & Post-Run-Phase:
  • Innerhalb des Zustands RUN wechselt die Maschine bei all RUN requests released /notify von RUN II nach RUN III (Eintritt in Mode Post Run).
  • Ein erneuter RUN requested /notify führt von RUN III zurück nach RUN II.
  • Wenn all applications have shut down, geht RUN III über in Perform PREP SHUTDOWN (weiterhin in Mode Post Run).
  • Shutdown- & Sleep-Pfade:
  • Aus Perform PREP SHUTDOWN:
  • Bei [Reset or Off requested] /notify erfolgt der Übergang nach Perform GO OFF I (Eintritt in Mode Shutdown).
  • Bei [other] /notify wechselt der Ablauf nach Perform GO SLEEP (Eintritt in Mode Sleep).
  • Aus Perform GO SLEEP:
  • Bei Bedingung immediate direkter Übergang nach SLEEP.
  • Bei Wakeup Event direkter Rücksprung nach WAKEUP.
  • Aus SLEEP:
  • Bei Wakeup event Übergang nach WAKEUP.
  • Aus WAKEUP:
  • Bei No Wakeup Event Rückkehr nach Perform GO SLEEP.
  • Bei immediate /notify Übergang zu Time Triggered Increased Inoperation (Eintritt in Mode WakeSleep).
  • Aus Time Triggered Increased Inoperation führt TTII /notify zurück zu WAKEUP.
  • Bei else /notify führt der Pfad von WAKEUP nach RUN II (Wechsel in Mode Run).
  • Re-Init/Abschluss:
  • Aus Perform GO OFF I führt der Pfad trough OFF or RESET zurück nach STARTUP II.

4. Normative Relevanz & Entwickler-Hinweise

Für die Systemintegration und BSW-Konfiguration ist dieses Mapping normativ verbindend:

  • Moduswechsel müssen atomar und konsistent über den RTE-Modus-Manager an abhängige SW-Cs und BSW-Module per Benachrichtigung (/notify) gemeldet werden.
  • Modusgrenzen decken sich nicht 1:1 mit den Hauptzuständen: Insbesondere erstreckt sich Mode Post Run über zwei verschiedene EcuM-Zustände (RUN III in RUN und Perform PREP SHUTDOWN in SHUTDOWN), was bedeutet, dass der BSW-interne Übergang zwischen diesen beiden Zuständen keinen extern sichtbaren RTE-Moduswechsel auslöst.
  • Entwickler müssen sicherstellen, dass Wakeup-Validierungen und Power-Control-Quellen die entsprechenden Verzweigungen (normal startup vs. wakeup source with integrated power control) korrekt bedienen und Wakeup-Ereignisse während der Sleep-Vorbereitung (Perform GO SLEEP) unverzüglich den Rücksprung nach WAKEUP triggern.
