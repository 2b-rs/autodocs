2. Komponenten, Entitäten & Schnittstellen

Komponenten (Akteure / Functional Clusters)
  • DSA (Diagnostic Server Application): Adaptive Application (Client-Rolle), die als Orchestrator für Diagnose- und Update-Prozesse agiert.
  • UCM (Update and Configuration Management): Plattform-Cluster zur Entgegennahme, Validierung, Installation und Aktivierung von Software-Paketen.
  • SM (State Management): Plattform-Cluster zur Steuerung von Plattform- und Function-Group-Zuständen (Deterministische Zustandsübergänge).
  • EM (Execution Management): Basis-Plattform-Cluster für Prozess-Lifecycle, Start-/Stopp-Reihenfolgen und Ressourcenmanagement basierend auf Ausführungsmanifesten.
Schnittstellen & Ports
  • Port UcmClient (DSA ↔ UCM):
    • Stereotyp: «ara::com» (Service-Oriented Communication).
    • Service Interface: UCM::UCM (DSA = Required Port -(, UCM = Provided Port -o).
    • Methoden:
      • + TransferData(): Übertragen von Software-Paket-Chunks.
      • + ProcessSwPackage(): Validierung, Entpacken und Staging des Software-Pakets.
      • + Activate(): Umschalten auf die neuen Software-Artefakte (z. B. A/B-Partition, Symlinks).
      • + Finish(): Persistente Bestätigung (Commit) des erfolgreichen Updates.
      • + Rollback(): Revertierung auf den vorherigen Stand bei Fehlern.
      • + Cancel(): Vorzeitiger Abbruch des laufenden Update-Vorgangs.
  • Port StateClient (DSA ↔ SM):
    • Stereotyp: «ara::com».
    • Service Interface: SM::StateManagement (DSA = Required Port, SM = Provided Port).
    • Methoden:
      • + SetState(): Anfordern eines Zustandswechsels (z. B. updateState, verificationState, defaultState).
      • + GetState(): Polling/Abfrage des aktuellen System- bzw. Funktionszustands.
    • Events:
      • «event» + runningState: Asynchrones Event (DSA abonniert via subscribe event), das signalisiert, dass alle Prozesse im verifizierten Zustand betriebsbereit sind.
  • Port StateTransitions (SM ↔ EM):
    • Stereotyp: «IFC interface» (Inter-Functional Cluster Interface, platform-intern / IPC).
    • Service Interface: EM::Request State Transitions (SM = Required Port, EM = Provided Port).
    • Methode:
      • + ReadUpdatedManifests(): Weist EM an, geänderte oder gelöschte Execution-Manifeste im Dateisystem neu einzulesen.

3. Dynamisches Verhalten & Sequenzablauf

Der Update-Workflow folgt einer strikt deterministischen Schrittfolge, gesteuert durch die DSA:

  1. Paketübertragung: DSA ruft UCM::TransferData() auf, um das Update-Paket im UCM-Pufferspeicher abzulegen.
  2. Umschaltung in Update-Modus: DSA fordert via SM::SetState(updateState) den Plattformzustand an, der für Software-Updates freigegeben ist (Abschaltung/Einschränkung nicht-relevanter Applikationen zur Ressourcensicherung).
  3. Paketverarbeitung: DSA triggert UCM::ProcessSwPackage() (Integritätsprüfung, Signaturprüfung, Dekompression, Ablage).
  4. Aktivierung: DSA ruft UCM::Activate() auf (Bereitstellung des neuen Softwarestands).
    • Flankierender Schritt: SM informiert EM via ReadUpdatedManifests() über modifizierte/entfernte Manifeste, damit EM die Prozessdefinitionsbasis aktualisiert.
  5. Verifikations-Zustand: DSA initiiert SM::SetState(verificationState). EM startet die neuen Prozesse gemäß aktualisierter Manifeste.
  6. Zustandsüberwachung & Event: DSA wartet auf das Event runningState von SM bzw. validiert mittels GetState() == runningState, ob alle definierten Prozesse ordnungsgemäß gestartet wurden.
  7. Verzweigung (Commit vs. Fallback):
    • Erfolgsfall (runningState bestätigt): DSA führt UCM::Finish() aus → persistenter Commit des Updates.
    • Fehlerfall (Timeout, Crash, Fehlschlag der Verifikation): DSA führt UCM::Rollback() aus → Revertierung der Softwareartefakte auf die vorherige Baseline.
  8. Rückkehr zum Normalbetrieb: DSA schaltet via SM::SetState(defaultState) das System in den regulären Betriebsmodus zurück.

4. Normative Relevanz & Entwickler-Hinweise

  • Architektonische Entkopplung (Separation of Concerns): UCM besitzt keinen direkten Kommunikationskanal zu EM. Die Prozesskontrolle und das Manifest-Neu-Einlesen laufen zwingend über State Management (SM). Applikationen manipulieren EM niemals direkt.
  • API-Design & Asynchronität (ara::core::Future): Die UCM-Methoden TransferData(), ProcessSwPackage() und Activate() sind zeitintensive Operationen. In der C++-Implementierung der Adaptive Platform (ara::ucm) liefern diese Aufrufe ara::core::Future-Objekte zurück; synchrones Blockieren ist im DSA-Thread unzulässig.
  • Event-Synchronisation: Die DSA darf Finish() erst absetzen, wenn das Event runningState eintrifft und durch GetState() konsistent verifiziert wurde. Ein implementiertes Watchdog-/Timeout-Handling auf DSA-Ebene ist verpflichtend, um bei Hängern im verificationState zwingend den Rollback() auszulösen.
  • Manifest-Konsistenz: ReadUpdatedManifests() bedingt atomare Dateioperationen bei der Paketaktivierung. Werden Manifeste während Activate() unvollständig auf das Dateisystem geschrieben, schlägt der EM-Parsingprozess fehl und die Zustandsverifikation scheitert.
