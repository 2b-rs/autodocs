1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt des AUTOSAR Software Component Template (Paket cd RTEEvent kinds).
  • Funktionale Einordnung: Definiert die abstrakte Metaklasse RTEEvent und ihre konkreten Spezialisierungen innerhalb des SwcInternalBehavior. Die Events spezifizieren auf VFB-Ebene (Virtual Function Bus) die kausalen Auslösebedingungen für die Aktivierung bzw. das Aufwecken von RunnableEntity-Instanzen durch die generierte Laufzeitumgebung (RTE).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Vererbung
  • RTEEvent (erbt von Identifiable): Abstrakte Basisklasse aller RTE-Ereignisse.
  • Spezialisierungen von RTEEvent:
    • AsynchronousServerCallReturnsEvent: Triggert eine Runnable bei Eintreffen des Rückgabewerts bzw. Abschlusses eines zuvor asynchron initiierten Server-Aufrufs.
    • DataSendCompletedEvent: Meldet die erfolgreiche Übertragung/Pufferung von Daten eines asynchronen Sendevorgangs.
    • DataReceivedEvent: Triggert eine Runnable bei Ankunft eines neuen Datenelements an einem Sender-Receiver-Port.
    • DataReceiveErrorEvent: Triggert eine Runnable bei Empfangsfehlern (z. B. Alive-Timeout, E2E-Validierungsfehler oder Signal-Inkonsistenz).
    • OperationInvokedEvent: Triggert die Server-Runnable bei Anforderung einer Operation durch einen Client (Client-Server-Kommunikation).
    • TimingEvent: Zyklischer Trigger für periodische Runnables.
      • Attribut: + period: Float (Ausführungsintervall in Sekunden).
    • ModeSwitchEvent: Triggert Runnables bei Zustandsübergängen von Mode-Managern.
      • Attribut: + activation: ModeActivationKind (z. B. ON_ENTRY, ON_EXIT, ON_TRANSITION).
Referenzierte Zielelemente & Assoziationen
  • AsynchronousServerCallPoint (spezialisiert ServerCallPoint):
    • Assoziation +event 1 ↔ +eventSource 1. Eine eindeutige 1:1-Zuordnung zwischen asynchronem Aufrufpfad der Client-Runnable und dem korrespondierenden Return-Event.
  • DataSendPoint (spezialisiert Identifiable):
    • Assoziation +event 0..1 ↔ +eventSource 1. Maximal ein Quittierungs-Event pro Sendepunkt.
  • DataElementPrototype (spezialisiert DataPrototype):
    • Ziel für DataReceivedEvent via Stereotyp «instanceRef» (+event * → +data 1): Mehrere Runnables können auf dasselbe Datenelement lauschen.
    • Ziel für DataReceiveErrorEvent via Stereotyp «instanceRef» (+event 0..1 → +data 1): Maximal ein Fehler-Event pro Datenelement.
  • OperationPrototype (spezialisiert Identifiable):
    • Ziel für OperationInvokedEvent via Stereotyp «instanceRef» (+event 1 → +operation 1): Eindeutige Bindung der Server-Operation an das Auslöse-Event.
  • ModeDeclaration (spezialisiert Identifiable):
    • Ziel für ModeSwitchEvent via Stereotyp «instanceRef» (0..* → +mode 1): Beliebig viele Mode-Switch-Events können an eine Modus-Deklaration gekoppelt werden.
  • Metamodell-Stereotyp «instanceRef»: Repräsentiert eine typisierte AUTOSAR-Instanzreferenz (InstanceRef). Sie löst den Kontextpfad über Port- und Prototyp-Hierarchien auf, um das Zielelement eindeutig innerhalb der SWC-Komposition zu identifizieren.

3. Dynamisches Verhalten & Sequenzablauf

Die dargestellten RTEEvent-Klassen steuern das Aktivierungsmodell der RTE für Runnables:

  1. Zeitgesteuerter Pfad (TimingEvent):
    • RTE nutzt OS-Alarme oder OS-Schedule-Tables. Nach Ablauf von period aktiviert das OS den Task der zugeordneten Runnable (ActivateTask) bzw. setzt ein OS-Event (SetEvent).
  2. Datengetriebener Empfang (DataReceivedEvent / DataReceiveErrorEvent):
    • Ablauf: Empfang via Com/CanIf → Signal-Indikation an RTE → RTE prüft Puffer/Filter/Alive-Counter.
    • Gutfall: Auslösung DataReceivedEvent → Task-Aktivierung der Empfänger-Runnable (Push-Modell).
    • Fehlerfall: Timeout/E2E-Fehler → Auslösung DataReceiveErrorEvent zur Ausführung von Ersatzwert- oder Degradationsstrategien.
  3. Client-Server-Interaktion:
    • Aufruf (OperationInvokedEvent): Ein Client ruft synchron oder asynchron via Rte_Call_* an. RTE fängt den Aufruf ab und triggert die Server-Runnable.
    • Asynchrone Rückkehr (AsynchronousServerCallReturnsEvent): Nach Beendigung des asynchronen Servers setzt die RTE das Callback-Event am Client; die Auswertung erfolgt typischerweise über Rte_Result_*.
  4. Zustandsübergänge (ModeSwitchEvent):
    • Modusänderung durch Mode-Manager (z. B. BswM) → RTE evaluiert Transitionsregeln (ModeActivationKind) → Aktivierung spezifischer Setup-, Shutdown- oder Umschalt-Runnables (ON_ENTRY / ON_EXIT).

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Task-Mapping & Ressourcen-Footprint:
    • Runnables, die auf mehrere RTEEvents reagieren (oder blockierende Aufrufe nutzen), erzwingen die Zuweisung zu einem Extended Task (OS-Events, separater Task-Stack nötig).
    • Runnables mit ausschließlich TimingEvent können effizient in geteilten Basic Tasks (gleicher Stack) sequenziell ausgeführt werden.
  • ASCET-Modellierung (Dokument-Kontext):
    • ASCET-Prozesse müssen exakt auf die Metamodell-Typen abgebildet werden:
      • Periodische Prozesse → TimingEvent. Die Modellierungszeit muss ein ganzzahliges Vielfaches des OS-Basis-Ticks sein, um Jitter zu vermeiden.
      • Nachrichten-getriebene Prozesse → DataReceivedEvent.
      • Init-/Shutdown-Routinen → ModeSwitchEvent (ON_ENTRY von Run-Modes bzw. Start-up/Shutdown-Modes).
  • API-Verträge & Einschränkungen (R2.1 bis R3.2):
    • DataSendCompletedEvent setzt voraus, dass der unterlagerte COM-Stack Sendequittungen bereitstellt (Tx-Confirmation). Fehlt diese, kann das Event zur Laufzeit nicht feuern.
    • Fehlende DataReceiveErrorEvent-Konfiguration führt dazu, dass Runnables veraltete Pufferdaten verarbeiten, sofern die Software nicht aktiv Rte_IStatus / Return-Codes abfragt.
