1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR VFB Software Component Description Diagram (UML 2.0 Composite Structure / Komponentendiagramm).
  • Technischer Zweck: Spezifikation des Strukturmusters zur horizontalen Entkopplung von physischen HMI-Eingabe-/Ausgabegeräten (Taster, Drehregler, Indikatoren) von anwendungsspezifischen Domänen-Funktionen (z. B. Fahrerassistenz, Innenraumbeleuchtung) über eine vermittelnde Steuerungsinstanz (InterDomainControllerComposition).
  • Architektonische Einordnung: Darstellung auf VFB-Ebene (Virtual Function Bus) im Dokument AUTOSAR_CP_EXP_AIHMIMultimediaAndTelematics. Die Komponente ButtonPanel SWC dient als normativer Platzhalter (virtuelle Hilfs-SWC), um standardisierte, funktionell neutrale UI-Elemente zu kapseln und proprietäre Bediengeräte-Implementierungen zu abstrahieren.

2. Komponenten, Entitäten & Schnittstellen

#### Software-Komponenten (SWCs) & Compositions

  • ButtonPanel SWC: Virtual Helper Application-SWC zur Bündelung generischer, hardwarenaher Ein- und Ausgabe-Ports.
  • InterDomainControllerComposition: Nicht-standardisierte (OEM-spezifische) Vermittlungs-Composition für Signalrouting, Zustandskonsolidierung, Mehrfachbelegungen und kontextabhängiges Mapping.
  • CrsCtrlAndAccComposition: Nicht-standardisierte Composition der Domäne Längsführung/Assistenzsysteme (Cruise Control & Adaptive Cruise Control).
  • InteriorLightComposition: Nicht-standardisierte Composition der Domäne Karosserie/Beleuchtung (Interior Light).
  • ... (Ellipsis): Offene Kardinalität für beliebige weitere Domänen-Compositions (z. B. Infotainment, HVAC).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt ein statisches Sender-Receiver-Kommunikationsmuster (VFB Sender-Receiver Interfaces, asynchron datengetrieben bzw. periodisch abgetastet):

  1. Ereigniserfassung (Input-Pfad): Physische Betätigung löst über Treiber/IoHwAb eine Zustandsänderung in ButtonPanel SWC aus. Diese publiziert Rohdaten über die standardisierten P-Ports (Btn, Knob).
  2. Mediation & Abstraktion: Die InterDomainControllerComposition empfängt die Rohzustände. Hier erfolgt die funktionale Schichtung:
  • Zeitbasierte Filterung (z. B. Unterscheidung Kurz-/Langdruck hold-long nach $N\,\text{ms}$).
  • Kontextsensitive Zuordnung (z. B. derselbe Drehknopf bedient je nach Menü-Modus die Innenraumhelligkeit BriReq1 oder die ACC-Wunschgeschwindigkeit).
  1. Domänen-Triggerung: Die konsolidierten Anforderungen werden an die Ziel-Compositions (CrsCtrlAndAccComposition, InteriorLightComposition) weitergeleitet.
  2. Zustandsrückmeldung (Feedback-Pfad): Domänen melden Betriebsmodi (AccCtrlActv1, CrsCtrlCtrlActv1) an den IDC zurück. Der IDC steuert die Rückmelde-Ports (TogSt1, OutpMplSt*) am ButtonPanel an, um HMI-Aktoren (z. B. Tastenbeleuchtung, Funktions-LEDs) zu aktualisieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Nicht-Normativität der ButtonPanel SWC: Die Komponente ist ein didaktisches Konstrukt der Spezifikation (virtual helper SWC). Sie darf in Serien-ECUs nicht als monolithische SWC implementiert werden, sondern wird im Systementwurf durch konkrete Sensor-/Aktor-SWCs (z. B. Multifunktionslenkrad-SWC, Mittelkonsolen-SWC via LIN/CAN-Botschaften oder Direct-I/O via IoHwAb) ersetzt.
  • Architekturprinzip der HMI-Schnittstellen:
  • UI-Device-Interfaces müssen strikt funktionsneutral und auf niedrigstem Abstraktionsgrad gehalten werden (Primitive: binär, Multi-State, Drehschritte).
  • Keine Funktionsspezifika in Treiber- oder UI-SWCs: Zeitbasierte Erkennungen (Long-Press, Double-Click) oder logische Bindungen an Applikationen gehören zwingend in übergeordnete Funktionsmodule (z. B. IDC / HMI-Manager).
  • Port-Kompatibilität & ARXML-Konfiguration: Obwohl InterDomainControllerComposition proprietär ist, müssen die Ports an den Systemgrenzen typgleich zu den standardisierten AUTOSAR SenderReceiverInterface-Definitionen modelliert werden (isOfType-Kompatibilität im Metamodell), um fehlerfreie VFB-Assembly-Connectoren im RTE-Generierungsprozess zu gewährleisten.

Explanation of Application Interfaces of the HMI, Multimedia and Telematics Domain AUTOSAR CP R25-11 Figure 5.3: Architecture with the InterDomainController and ButtonPanel 5.1 Button Panel Component The ButtonPanel is a “virtual helper SWC” acting as a placeholder for all the system specific UI Device SWCs which a real-world system would include (see Figure 5.3). The ButtonPanel aggregates a set of standardized Ports and Interfaces for simple UI Devices like hard buttons, switches, LEDs etc. The UI-Device Interfaces are standardized with the following principles in mind: • A UI-Device interface should never be specific to certain functionality. • A UI-Device interface should be standardized on the most fundamental level possible. If more advanced functionality is required (e.g. a hold long signal after N ms), then that functionality must be layered on top of the UI-Device. Please Note: The Button Panel Component is not intended to be taken as is for a real system.
