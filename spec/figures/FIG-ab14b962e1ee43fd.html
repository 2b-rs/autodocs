Figure 4.55: Can Hardware Object

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration Metamodell (UML-Klassendiagramm auf M2-Ebene gem. AUTOSAR Generic Structure Definition).
  • Technischer Zweck: Definition des Konfigurationsschemas für Hardware-Objekte (Mailboxen/Puffer) des CAN-Treibers (Can-Modul innerhalb der MCAL / Microcontroller Abstraction Layer).
  • Funktionale Einordnung: Modellierung der Hardware Object Handles (HOH – unterteilt in HTH für Sende- und HRH für Empfangsobjekte) inklusive deren Bindung an dedizierte CAN-Controller (CanController), ID-Bereiche, Identifier-Formate und Akzeptanzfilter (CanFilterMask).

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Container

  • Can (:ModuleDef [1..1]): Wurzelknoten der BSW-Modulbeschreibung des CAN-Treibers.
  • CanConfigSet (:ParamConfContainerDef): Post-Build- bzw. Multiple-Configuration-Container (multipleConfigurationContainer = true), aggregiert über +container [1..1].
  • *CanHardwareObject (:ParamConfContainerDef [1..]):** Zentraler Container zur Repräsentation einer konkreten CAN-Hardware-Mailbox bzw. eines FIFO-Puffers; aggregiert durch CanConfigSet via +subContainer.
  • *CanController (:ParamConfContainerDef [1..]):** Repräsentiert den physikalischen CAN-Controller-Kanal.
  • *CanFilterMask (:ParamConfContainerDef [0..]):** Kind-Container von CanController (+subContainer), welcher Hardware-Filtermasken definiert.

#### Parameter von CanHardwareObject (Aggregiert via +parameter)

  • CanObjectId (:IntegerParamDef [1..1]): Eindeutige numerische Kennung des Hardware-Objekts (symbolicNameValue = true). Laut Annotation (Bug #10906) dient primär der SHORT-NAME des CanHardwareObject-Containers als symbolischer Bezeichner im Quellcode.
  • CanObjectType (:EnumerationParamDef [1..1]): Bestimmt die Pufferrichtung:
  • Transmit (:EnumerationLiteralDef): Hardware Transmit Handle (HTH).
  • Receive (:EnumerationLiteralDef): Hardware Receive Handle (HRH).
  • CanIdValue (:IntegerParamDef [1..1]): Konfigurierter CAN-Identifier (Basiswert für Filterung oder fester TX-Identifier).
  • CanIdType (:EnumerationParamDef [1..1]): Adressierungsformat:
  • Standard (:EnumerationLiteralDef): 11-Bit-Identifier (CAN 2.0A).
  • Extended (:EnumerationLiteralDef): 29-Bit-Identifier (CAN 2.0B).
  • Mixed (:EnumerationLiteralDef): Dynamische Unterstützung beider Formate auf demselben Objekt.

#### Referenzen (Aggregiert via +reference)

  • CanControllerRef (:ReferenceDef [1..1]): Verweist über +destination auf den zugehörigen CanController, auf dessen Hardware-Ressourcen das Objekt allokiert ist.
  • CanFilterMaskRef (:ReferenceDef [0..1]): Verweist über +destination optional auf eine definierte CanFilterMask des referenzierten Controllers (primär relevant für CanObjectType == Receive).

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Das Diagramm ist ein statisches Konfigurationsmodell; dynamische Interaktionen leiten sich aus der Zuordnung zur Laufzeit ab:

  • TX-Pfad (HTH):
  1. Aufruf von Can_Write(Hth, PduInfo) durch das CanIf.
  2. Der Treiber identifiziert über Hth das konfigurierte CanHardwareObject und den referenzierten CanController.
  3. Validierung gegen CanIdType (Standard/Extended).
  4. Übertragung der Datenbytes in die Hardware-Mailbox; Rückmeldung asynchron via Can_MainFunction_Write() oder TX-Interrupt an CanIf_TxConfirmation().
  • RX-Pfad (HRH):
  1. Frame-Empfang triggert Hardware-Akzeptanzfilter basierend auf CanFilterMaskRef, CanIdValue und CanIdType.
  2. Bei erfolgreichem Match wird das Frame im CanHardwareObject abgelegt.
  3. Übergabe an den oberen Layer via RX-Interrupt oder Can_MainFunction_Read() mittels CanIf_RxIndication(Hrh, CanId, CanDlc, CanSduPtr).

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Generierung (Can_Cfg.h / Can_PBcfg.c):
  • Generierung der HOH-Symbolkonstanten (z. B. #define CanHardwareObject_Tx_0 (0U)), die als Parameter für Can_Write() verwendet werden.
  • Generierung kompakter Look-up-Tabellen zur Laufzeitauflösung (Mailbox-Index -> Controller-Kanal-Index).
  • Puffer-Optimierung:
  • Die Trennung in Standard, Extended oder Mixed bestimmt, ob Hardware-Filter im Controller homogen konfiguriert werden können oder Software-Filtering im Treiber greifen muss (Overhead-Vermeidung).
  • Kopplungsregeln:
  • Jedes CanHardwareObject muss zwingend genau einem CanController zugeordnet sein (lowerMultiplicity = 1).
  • Eine CanFilterMask darf nur für Receive-Objekte zugewiesen werden; bei Zuweisung an Transmit-Objekte muss der Konfigurations-Validator einen Validierungsfehler werfen.
