1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU- / Wire-Format-Layout (Bit-/Byte-Strukturdiagramm auf Netzwerkebene), strukturiert in 32-Bit-Wortgrenzen (Big-Endian / Network Byte Order).
  • Technischer Zweck: Spezifikation des On-Wire-Serialisierungsformats für das SOME/IP Service Discovery Protokoll (AUTOSAR_FO_PRS_SOMEIPServiceDiscoveryProtocol).
  • Architektur-Einordnung:
  • Bindeglied zwischen dynamischer Dienst- bzw. Ereignisverwaltung (Client/Server-Bindings in AUTOSAR Classic Sd / BswM bzw. AUTOSAR Adaptive ara::com / Communication Management Daemon) und dem Socket-basierten Transportlayer (SoAd / TCP/IP-Stack).
  • Paketierung erfolgt typischerweise über unzuverlässiges UDP (Standard-Multicast-Port 30490 an IPv4 224.0.0.17 oder IPv6 Link-Local FF02::FB sowie Unicast).

2. Komponenten, Entitäten & Schnittstellen

Das Format gliedert sich in den standardisierten 16-Byte-SOME/IP-Header und den nachfolgenden SOME/IP-SD-Nutzlastbereich:

#### A. SOME/IP Basis-Header (Byte-Offset 0..15)

  • Message ID [32 Bit] (Fixwert 0xFFFF8100):
  • Service ID [16 Bit]: 0xFFFF gem. [PRS_SOMEIPSD_00151]. Reserviert für Service Discovery.
  • Method ID [16 Bit]: 0x8100 gem. [PRS_SOMEIPSD_00152]. Bit 15 = 1 kennzeichnet ein Event/Notification-Format.
  • Length [32 Bit]:
  • Spezifiziert die kumulierte Bytegröße der nachfolgenden Daten ab Offset 8 bis Paketende:

$$\text{Length} = 8 \text{ Bytes (Rest-SOME/IP-Header)} + 4 \text{ (Flags+Res)} + 4 \text{ (Len Entries)} + N_{\text{Entries}} + 4 \text{ (Len Opts)} + M_{\text{Opts}}$$

  • Request ID [32 Bit]:
  • Aufgeteilt in Client ID [16 Bit] (i. d. R. 0x0000 im SD-Kontext) und Session ID [16 Bit] (Monoton inkrementierender Sequenzzähler zur Erkennung von Paketverlusten/Duplikaten).
  • Protocol Version [8 Bit]: Fixwert 0x01.
  • Interface Version [8 Bit]: Fixwert 0x01.
  • Message Type [8 Bit]: Fixwert 0x02 (NOTIFICATION).
  • Return Code [8 Bit]: Fixwert 0x00 (E_OK).

#### B. SOME/IP-SD Spezifischer Header & Payload (ab Byte-Offset 16)

  • Flags [8 Bit]:
  • Bit 7: Reboot Flag (Signalisierung eines Neustarts der sendenden Instanz).
  • Bit 6: Unicast Flag (Anforderung/Möglichkeit von Unicast-Antworten).
  • Bit 5..0: Reserviert (Initialisierung mit 0).
  • Reserved [24 Bit]: Füll-Bits zur Gewährleistung des 32-Bit-Alignments; zwingend 0x000000.
  • Length of Entries Array [32 Bit]: Länge des nachfolgenden Entries-Blocks in Bytes.
  • Entries Array [variabel, $N \times 16$ Bytes]:
  • Sequenz strukturierter 16-Byte-Einträge: FindService, OfferService, StopOfferService, SubscribeEventgroup, StopSubscribeEventgroup.
  • Length of Options Array [32 Bit]: Länge des nachfolgenden Options-Blocks in Bytes.
  • Options Array [variabel, $M$ Bytes]:
  • Typ-Längen-codierte Konfigurationsoptionen (z. B. IPv4/IPv6-Endpunktadresse, Portnummern, Protocol Layer4 UDP/TCP).

#### Beziehungen und Kardinalitäten:

  • SOME/IP Header 1 : 1 SOME/IP-SD Payload.
  • SD Message 1 : 1 Entries Array (Kardinalität: $0..n$ Einträge, typischerweise begrenzt durch MTU).
  • SD Message 1 : 1 Options Array (Kardinalität: $0..m$ Optionen).
  • Entry 1 : $0..2$ Option (Indirekte Adressierung: Einträge referenzieren über 1-Byte-Array-Indizes die zugehörigen Einträge im Options Array).

3. Dynamisches Verhalten & Sequenzablauf

  • Trigger:
  • Zyklische Timer der SD-Zustandsmaschine (z. B. Cyclic Offer Delay in der Main Phase).
  • Statuswechsel der lokalen Services (z. B. BswM fordert Service-Verfügbarkeit an $\rightarrow$ Initial Wait Phase $\rightarrow$ Repetition Phase).
  • Eintreffende Unicast-/Multicast-Pakete (z. B. Remote FindService triggert Unicast OfferService).
  • Empfangs-Validierung (Synchroner Verwerfungspfad):
  1. Header-Prüfung ([PRS_SOMEIPSD_00250]): Stimmen Service ID (0xFFFF), Method ID (0x8100), Protocol Version (0x01), Interface Version (0x01), Message Type (0x02) und Return Code (0x00) nicht exakt überein, wird das Paket stillschweigend verworfen (Silent Discard).
  2. Längenkonsistenz:

$$\text{Length} \stackrel{?}{=} 16 + \text{Length of Entries} + \text{Length of Options}$$

Bei Mismatch $\rightarrow$ Paketverwerfung, optional Meldung an Det (Development Error Tracer) mit Fehlercode SD_E_MALFORMED_MESSAGE.

  1. Index-Gültigkeit: Verweist ein Entry auf einen Options-Index außerhalb von [0, Length of Options Array), ist die gesamte Nachricht ungültig.
  • Asynchroner Dispatch:
  • Nach erfolgreicher Validierung iteriert der Stack über das Entries Array, löst die Endpunkte im Options Array auf und aktualisiert die internen Routing-Tabellen (z. B. Aktivierung von Socket-Routen im SoAd).

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher-Alignment & Zero-Copy:
  • Durch das konsequente 32-Bit-Alignment können BSW-Treiber und Protokoll-Parser C-Strukturen mit festen Breiten (uint32_t, uint16_t, uint8_t) direkt auf Socket-Empfangspuffer abbilden, sofern Packing/Alignment (#pragma pack(1)) und Endianness-Konvertierung (ntohl(), ntohs()) beachtet werden.
  • Puffer-Dimensionierung & MTU-Grenzen:
  • SOME/IP-SD unterstützt kein SOME/IP-TP (Transport Protocol für Fragmentierung). Nachrichten müssen zwingend in eine Ethernet-MTU passen (in der Regel max. 1400–1472 Bytes Nutzdaten bei UDP), um IP-Fragmentierung zu verhindern.
  • Entwickler müssen sicherstellen, dass bei hoher Service-/Eventgruppen-Dichte die Einträge stackseitig auf mehrere getrennte SOME/IP-SD-Nachrichten aufgeteilt werden.
  • Kompaktierung von Optionen:
  • Mehrere Einträge im Entries Array müssen identische Endpunkte (z. B. IP/Port für denselben Server) auf denselben Optionseintrag verweisen lassen (Option Consolidation), um die PDU-Größe zu minimieren.
