1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptuelles Schichten- und Isolationsmodell (Blockdiagramm mit hardwarebasierter Domänentrennung nach GlobalPlatform-TEE-Spezifikation).
  • Architektur-Kontext: AUTOSAR Foundation (AUTOSAR_FO_EXP_SecurityOverview, Release R24-11, Kap. 4). Das Schaubild definiert die Referenzarchitektur zur Anbindung einer software- oder hardwareisolierten vertrauenswürdigen Ausführungsumgebung (TEE, z. B. Arm TrustZone) an standardisierte AUTOSAR-Stacks (Classic Platform Crypto Stack via CSM/Crypto Driver sowie Adaptive Platform via ara::crypto). Es etabliert die Koexistenz von Standard-Applikationen in der Normal World (REE) und sicherheitskritischen Krypto- bzw. Authentifizierungs-Diensten in der Secure World (TEE).

2. Komponenten, Entitäten & Schnittstellen

Das Modell gliedert sich in zwei streng isolierte Ausführungsdomänen auf einer gemeinsamen Hardware-Plattform:

#### REE (Rich Execution Environment / Non-Secure World)

  • Application: Client-Anwendungen (AUTOSAR Classic SW-Cs, Adaptive Applications oder native POSIX-Prozesse).
  • Service Layer: Krypto- und Sicherheits-Dienstschicht (AUTOSAR CSM – Crypto Service Manager, Key Manager, SecOC oder ara::crypto).
  • TEE Access Layer (TEE Client API): Standardisierte Kommunikationsschnittstelle gemäß GlobalPlatform TEE Client API (z. B. TEEC_Context, TEEC_Session, TEEC_Operation). Dient als Middleware-/Treiber-Abstraktion im Non-Secure OS.
  • Regular OS: Standard-Betriebssystemkernel (z. B. AUTOSAR OS, POSIX-OS wie Linux/QNX) inklusive TEE-Kernel-Treiber zur Steuerung der Inter-World-Kommunikation.

#### TEE (Trusted Execution Environment / Secure World)

  • SHE Trusted App: TA-basierte Emulation einer Secure Hardware Extension (SHE nach HIS-Standard). Kapselt symmetrische Krypto-Routinen (AES-128, CMAC, Secure Boot/Boot-Mac, Key-Update-Protokoll), um Legacy-ECU-Anforderungen auf TEE-fähigen Microcontrollern/SoCs zu bedienen.
  • Trusted App (TA): Sicherheitskritische Applikationen/Trustlets (z. B. PKI-Handler, Zertifikatsspeicher, SecOC-MAC-Berechnung, Flash-Signaturverifikation).
  • TEE Core API: Standardisierte Laufzeitschnittstelle gemäß GlobalPlatform TEE Internal Core API für TAs (Zugriff auf Krypto-Primitive, Zeitfunktionen, Secure Storage und flüchtigen Shared Memory).
  • Trusted Management Framework (TMF): Administrativer Framework-Stack zur sicheren Lebenszyklusverwaltung (Installation, Löschung, Autorisierung und Update von TAs).
  • Trusted OS: Isoliertes Sicherheits-Microkernel-Betriebssystem (z. B. OP-TEE, seL4-basiert oder proprietär) in Secure EL1/S-Mode.

#### Hardware Platform

  • Physische Ausführungsplattform mit Sicherheitsisolations-Mechanismen (z. B. TrustZone, Memory Firewalls, MPU/MMU-Isolation, SMMU).
  • Trusted User Interface & Secure Peripherals: Exklusiv an das TEE angebundene Hardware-Ressourcen (Krypto-Coprozessoren, True Random Number Generators [TRNG], eFuses/Monotonic Counters, isolierte Display-/Input-Pfade).

3. Dynamisches Verhalten & Sequenzablauf

Die Ausführung von Sicherheitsdiensten folgt einem synchronen oder asynchronen Inter-World-RPC-Muster über Prozessorgrenzen:

  1. Kontext- und Sitzungsaufbau:
  • REE-Applikation triggert Krypto-Job über den Service Layer.
  • TEE Access Layer instanziiert Kontext via TEEC_InitializeContext() und öffnet eine Session zur Ziel-TA via TEEC_OpenSession() unter Übergabe der TA-UUID (z. B. UUID der SHE Trusted App).
  1. Kommando-Übergabe & World Switch:
  • Parameter, IVs und Datenzeiger werden im Non-Secure RAM als Shared Memory registriert (TEEC_RegisterSharedMemory() / TEEC_AllocateSharedMemory()).
  • Aufruf von TEEC_InvokeCommand().
  • Der REE-OS-Treiber triggert einen Hardware-Trap (z. B. ARM SMC - Secure Monitor Call / HVC), der die Ausführung an den Secure Monitor (EL3) übergibt.
  1. Ausführung in der Secure World:
  • Secure Monitor wechselt Prozessorkontext (World Switch, Non-Secure Register-Sicherung) und reicht Execution an das Trusted OS (S-EL1) weiter.
  • Trusted OS ruft über die TEE Core API den Entry Point der Ziel-TA auf (TA_InvokeCommandEntryPoint()).
  • Die TA verarbeitet die Payload (z. B. AES-CMAC über Secure Peripherals oder SHE-Schlüsseltabelle im geschützten NVM).
  1. Rückkehrpfad & Fehlerbehandlung:
  • Result-Status (TEEC_SUCCESS oder spezifischer GlobalPlatform Error Code) wird über Register an den Secure Monitor und zurück in den REE-Treiber propagiert.
  • Bei Hardware-Fehlern, illegalen Speicherzugriffen (z. B. Bounds-Violation des Shared Memory) oder TA-Panics erfolgt ein geordneter Fehlerabstieg: Der Service Layer transformiert TEE-Fehlercodes in AUTOSAR-konforme Rückgabewerte (E_NOT_OK, CRYPTO_E_BUSY, CRYPTO_E_KEY_NOT_AVAILABLE) und triggert ggf. Det (Det_ReportError) bzw. Dem-Events.

4. Normative Relevanz & Entwickler-Hinweise

  • Treiber- & Stack-Implementierung (Classic Platform):
  • TEE fungiert als Krypto-Hardware-Abstraktion: Der AUTOSAR Crypto Driver (unterhalb des CSM) kapselt die TEE Client API.
  • Eine SHE Trusted App erlaubt die direkte Weiterverwendung von standardisierten SHE-Treiber-Schnittstellen (She.h) auf modernen Multicore-SoCs ohne dezidiertes HSM-Silizium.
  • Adaptive Platform (ara::crypto):
  • Krypto-Provider im POSIX-Userland mappen ara::crypto::keys und Operations-Pipelines direkt auf GlobalPlatform TEE Sessions. Schlüsselmaterial verbleibt persistent und unextrahierbar im isolierten TEE-Storage.
  • Entwickler-Fallstricke & Restriktionen:
  • Latenzbudgets: Jeder Wechsel zwischen REE und TEE erfordert Context Switches im Secure Monitor, TLB-Invalidierungen und Cache-Barrieren. Für harte Echtzeitpfade (z. B. Frame-by-Frame SecOC-Verifikation im CAN-FD/Ethernet-Interrupt) müssen synchrone SMC-Aufrufe zwingend gegen die WCET evaluiert werden.
  • Speicher-Konsistenz: Shared Memory zwischen REE und TEE erfordert striktes Cache-Flushing/Invalidieren vor und nach dem World Switch, um Data Coherency Errors und Time-of-Check-to-Time-of-Use (TOCTOU)-Vulnerabilitäten zu verhindern.
  • Pointer-Validierung: TAs dürfen niemals ungeprüfte REE-Adressräume dereferenzieren. Alle Ein-/Ausgabepuffer müssen über die TEE Core API validiert und in den TEE-eigenen Sicherheitsbereich kopiert werden.
