1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Funktionales Architektur- und Schnittstellen-Partitionierungsmodell (Blockschaltbild mit Scope- und Schnittstellentrennung).
  • Architektur-Kontext: AUTOSAR Classic Platform (AUTOSAR_EXP_BSWDistributionGuide, R21-11), Multi-Core BSW-Verteilungskonzepte.
  • Technischer Zweck: Spezifikation des Multi-Core-Type IV Treiber-Patterns. Typ IV beschreibt eine hybride Treiberarchitektur zur Optimierung von Cross-Core-Latenzen:
    • Entkopplung von Local Scope (Kern-gebundener Ausführungskontext, typischerweise der Core mit physischem Peripheriezugriff) und Global Scope (Core-übergreifend sichtbare Schnittstellen für Software-Components oder BSW-Module auf beliebigen Cores).
    • Zweipfadige Abarbeitung: Aufwendige Kontroll-/Hardware-Aktionen (Trigger) laufen über Inter-Core-Kommunikation (IPC/IOC), während Status- und Datenabfragen (Get/Set) zur Vermeidung von IPC-Overhead über gesperrten Shared Memory direkt ausgeführt werden.

2. Komponenten, Entitäten & Schnittstellen

Scopes & Partitionierung
  • Local Scope: Privater Ausführungs- und Speicherbereich des Core-lokalen Treibers (z. B. Core 0 / Master-Core). Beherbergt die Registerzugriffe und die Kernel-Zustandsmaschine.
  • Global Scope: Partitionsübergreifender Bereich, der für alle Cores (Satellite-Cores) aufrufbar und zugänglich ist.
Komponenten & Software-Bausteine
  • Local Kernel: Kern-Modul des Treibers im Local Scope. Führt physische HW-Zugriffe aus und verwaltet den treiberinternen Status.
  • Interface Code: Client-seitige Stub-/Proxy-Schicht im Global Scope. Läuft im Thread- bzw. Task-Kontext des aufrufenden Cores.
  • Multi-Core Mechanism: Kommunikationsinfrastruktur zur Überwindung von Kerngrenzen (z. B. AUTOSAR Inter-OS-Application Communicator [IOC], Inter-Core-Interrupts [ICI] oder hardwarebasierte Mailboxen).
  • Data Access: Abstrahierte Zugriffslogik (z. B. Inline-Funktionen, Macros, Memory-Barriers) im Local Kernel und im Interface Code zur thread-/core-sicheren Manipulation geteilter Daten.
Datenstrukturen & Speicherklassen
  • XXX_KERNEL_Data: Lokale Treiberdaten (privates BSS/DATA), allokiert im Core-lokalen RAM; nur dem Local Kernel zugänglich.
  • XXX_Data: Geteilte Nutz-/Zustandsdaten im Shared RAM (Global Scope), les- und schreibbar von allen berechtigten Cores.
  • XXX_Lock: Synchronisationsprimitiv im Shared RAM (z. B. AUTOSAR Spinlock GetSpinlock() / ReleaseSpinlock() oder Hardware-Semaphor), das den Zugriff auf XXX_Data serialisiert.
Schnittstellen & APIs
  • XXX_Init(), XXX_Deinit(): Lifecycle-APIs. Ausschließlich im Local Scope am Local Kernel bereitgestellt.
  • XXX_Trigger(): Globale Steuerungs-API (blau). Wird vom Aufrufer am Interface Code initiiert und via Multi-Core Mechanism geroutet.
  • XXX_KERNEL_Rcv(): Empfangsschnittstelle/Dispatcher des Local Kernel zur Entgegennahme von Trigger-Aufträgen aus dem Multi-Core Mechanism.
  • XXX_Get(), XXX_Set(): Globale Nutzdaten-APIs (gelb). Umgehen den Local Kernel und greifen direkt über Data Access auf XXX_Data zu.

3. Dynamisches Verhalten & Sequenzablauf

Pfad A: Asynchroner/Gepufferter Steuerpfad (XXX_Trigger())
  1. Trigger-Aufruf: Eine Entität auf einem beliebigen Core ruft XXX_Trigger() im Global Scope auf.
  2. IPC-Routing: Der Interface Code leitet den Aufruf über den Multi-Core Mechanism weiter (z. B. Queued IOC-Kanal, Setzen eines Inter-Core-Events oder Interrupts).
  3. Kontextwechsel / Signalierung: Der Mechanismus überträgt die Parameter über Kerngrenzen in den Local Scope.
  4. Kernel-Dispatch: Die Empfangsfunktion XXX_KERNEL_Rcv() wird im Kontext des Local Kernel (Task oder ISR) aktiviert.
  5. Abarbeitung: Der Local Kernel führt die Operation auf XXX_KERNEL_Data bzw. den Peripherie-Registern aus und aktualisiert bei Bedarf XXX_Data.
Pfad B: Direkter Lese-/Schreibpfad (XXX_Get() / XXX_Set())
  1. API-Aufruf: Aufrufer auf einem beliebigen Core ruft XXX_Get() oder XXX_Set() auf.
  2. Lock-Akquisition: Interface Code fordert über Data Access die Ressource XXX_Lock an (Spinlock).
  3. Shared Data Access: Direkter Lese- oder Schreibzugriff auf XXX_Data im globalen Speicher.
  4. Lock-Freigabe: XXX_Lock wird sofort freigegeben.
  5. Return: Rückkehr zum Aufrufer ohne IPC-Overhead, ohne Kontextwechsel und ohne Beteiligung des Local Kernel-Tasks.
Pfad C: Lifecycle-Steuerung (XXX_Init() / XXX_Deinit())
  • Ausschließlich lokal im Boot-/Initialisierungs-Kontext des Master-Cores (z. B. via EcuM / BswM) getriggert; keine Bereitstellung über Kerngrenzen hinweg.

4. Normative Relevanz & Entwickler-Hinweise

  • Treiber-Klassifikation (Typ-I bis Typ-IV):
    • Typ I: Rein Core-lokal ohne Multi-Core-Unterstützung.
    • Typ II: Reiner Shared-Memory-Treiber mit Lock-Schutz für sämtliche APIs.
    • Typ III: Reines Master-Satellite-Modell (alle APIs werden via IPC an den Master geroutet).
    • Typ IV (vorliegend): Hybrides Modell. Minimiert die Bus- und IPC-Last drastisch bei hochfrequenten Statusabfragen (Get/Set), schützt aber die Registerintegrität komplexer Operationen über den Local Kernel.
  • Speicher-Mapping & Cache-Kohärenz:
    • XXX_Data und XXX_Lock müssen über Linker-Symbole in Non-Cached Memory oder strikt Cache-kohärente Shared-RAM-Bereiche gemappt werden (START_SEC_VAR_CLEARED_SHARED_...).
    • False-Sharing-Vermeidung: XXX_Data und XXX_Lock müssen auf Cache-Line-Grenzen ausgerichtet werden (Alignment ALIGN(CACHE_LINE_SIZE)), um Cache-Thrashing zwischen Cores zu unterbinden.
    • Data Access muss architekturabhängige Speicherbarrieren (z. B. DSB, DMB bei ARM Cortex-R/M) implementieren.
  • Synchronisationsverträge & Spinlocks:
    • Haltezeiten für XXX_Lock müssen auf ein Minimum an Instruktionen beschränkt sein (harte OSEK/AUTOSAR-Spinlock-Regeln zur Vermeidung von Core-Starvation und Priority Inversion).
    • Nesting: Keine verschachtelten Locks innerhalb von Data Access.
  • API-Rückgabewerte & Fehlerbehandlung:
    • XXX_Trigger() signalisiert via Rückgabewert (z. B. E_OK / E_NOT_OK) primär die Annahme durch den Multi-Core Mechanism (z. B. Queue voll), nicht die erfolgreiche physikalische Beendigung im Local Kernel.
    • Asynchrone Fehlerzustände aus dem Local Kernel müssen bei Bedarf über XXX_Data gespiegelt oder via Callback/Det gemeldet werden.
