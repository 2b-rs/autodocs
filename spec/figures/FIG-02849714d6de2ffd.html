1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR VFB / Software Component Template Architekturdiagramm (Struktur- und Dekompositionsmodell gemäß AUTOSAR-Standardnotation für Software-Komponenten).
  • Technischer Zweck: Darstellung des Problemfalls und Ausgangsszenarios (Use Case I), das die normative Einführung des PassThroughSwConnector in AUTOSAR_TPS_SoftwareComponentTemplate (Kapitel Connectors) motiviert.
  • Architektonische Einordnung: Zeigt das Durchschleifen von Triggern und Daten durch eine hierarchische Kapselungsgrenze (CompositionSwComponentType). Ohne PassThroughSwConnector erzwingt die AUTOSAR-Metamodell-Hierarchie eine intermediäre atomare Software-Komponente (ApplicationSwComponentType) mit eigener RunnableEntity (RunA1) und RTE-Laufzeitobjekt (RTO), lediglich um ein Ereignis an nachgelagerte Empfänger außerhalb der Komposition weiterzuleiten.

2. Komponenten, Entitäten & Schnittstellen

  • Komponenten (SwComponentType / SwComponentPrototype):
  • Composition SW Component (CompositionSwComponentType): Hierarchische Hülle, aggregiert interne Prototypen und exponiert Ports an den VFB.
  • Application SW Component (ApplicationSwComponentType, instanziiert als SwComponentPrototype): Intermediäre atomare Ausführungseinheit.
  • Externe Komponenten (blau umrandet): Externe SwComponentPrototype-Instanzen (Trigger-Quelle links oben, Datenquelle links unten, Trigger-Senke rechts).
  • Ports (PortPrototype):
  • Trigger-Ports (TriggerInterface, Symbol >>):
  • P-Port an der externen Trigger-Quelle.
  • Äußerer R-Port an Composition SW Component (links oben).
  • Innerer R-Port an Application SW Component (links oben).
  • Innerer P-Port an Application SW Component (rechts, annotiert mit Trigger).
  • Äußerer P-Port an Composition SW Component (rechts).
  • R-Port an der externen Senke (rechts).
  • Daten-Ports (SenderReceiverInterface, Symbol ▷):
  • P-Port der externen Datenquelle (links unten).
  • Äußerer R-Port an Composition SW Component (links unten).
  • Innerer R-Port an Application SW Component (links unten).
  • Konnektoren (SwConnector):
  • DelegationSwConnector: Verbindet jeweils die Außenports der Composition mit den Innenports der Application SW Component (Outer R-Port $\rightarrow$ Inner R-Port bzw. Inner P-Port $\rightarrow$ Outer P-Port).
  • AssemblySwConnector: Verbindet externe Komponenten auf Top-Level-VFB-Ebene mit den Außenports der Composition.
  • Verhaltensmodellierung (SwcInternalBehavior):
  • RTO (RTE Trigger Object / Run-Time Object): Repräsentiert das auslösende RTE-Ereignis (konkret ExternalTriggerOccurredEvent), das an den R-Port gebunden ist.
  • RunA1 (RunnableEntity): Ausführbare C-Funktion im internen Verhalten der Application SW Component.
  • Interne Zugriffspfade:
  • Ereignisbindung: ExternalTriggerOccurredEvent $\rightarrow$ RunA1.
  • Datenzugriff: RunA1 greift lesend auf den Daten-R-Port zu (dataReceivePointByValue / dataReadAccess).
  • Trigger-Generierung: RunA1 steuert den P-Port Trigger an (externalTriggeringPoint).

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger-Auslösung: Die externe Quelle emittiert einen Trigger über ihren Trigger-P-Port.
  2. Kaskadierte Weiterleitung: Der Trigger passiert den AssemblySwConnector zum R-Port der Composition und den DelegationSwConnector zum R-Port der Application SW Component.
  3. RTE-Event-Dispatching (RTO): Das Eintreffen des Triggers instanziiert im RTE das ExternalTriggerOccurredEvent, wodurch die zugewiesene OS-Task für RunA1 aktiviert oder aus dem Wartezustand entblockt wird.
  4. Ausführung von RunA1:
  • Eintritt in den Task-Kontext von RunA1.
  • Leseoperation über den Daten-R-Port (Rte_Read_<p>_<d>() oder Rte_IRead_<re>_<p>_<d>()).
  • Explizites Absetzen eines neuen Triggers über die RTE-API (Rte_Trigger_<p>_<t>()).
  1. Re-Emission an den VFB: Der neu generierte Trigger wird über den P-Port via DelegationSwConnector an den Außenport der Composition und von dort zur externen Senke weitergeleitet.

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur-Defizit des abgebildeten Musters:
  • Laufzeit- & Speicher-Overhead: Die Zwischenschaltung einer dedizierten Application SW Component bindet unnötig Task-Slots, Stack, OS-Aktivierungszeiten und RTE-Generat-Code (Rte_Trigger, Task-Prolog/-Epilog), obwohl rein funktionell nur eine Signal- bzw. Trigger-Durchleitung beabsichtigt ist.
  • Latenz & Jitter: Das Weitertriggern ist taskprioritätsabhängig und unterliegt Scheduling-Latenzen.
  • Normative Lösung via PassThroughSwConnector:
  • Ein PassThroughSwConnector verbindet einen RPortPrototype einer CompositionSwComponentType direkt mit einem PPortPrototype derselben CompositionSwComponentType.
  • Die Application SW Component, RunA1 sowie das RTO entfallen vollständig, sofern keine algorithmische Modifikation des Nutzsignals zwingend im Zwischenschritt erforderlich ist.
  • Auswirkungen auf RTE-Generierung & Stack:
  • Bei Einsatz eines PassThroughSwConnector entfällt jeglicher RTE-Code innerhalb der Komposition; der RTE-Generator verbindet die externe Quelle und die externe Senke direkt (Short-Circuit auf VFB-Ebene), was Null-Overhead-Durchschleifung ermöglicht.
  • Port-Kompatibilität:
  • Voraussetzung für das Ersetzen durch einen PassThroughSwConnector: Beide Außenports der Composition müssen kompatible Schnittstellen besitzen (identisches TriggerInterface bzw. identische Typdefinitionen).
