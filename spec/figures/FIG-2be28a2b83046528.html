1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Strukturelles Hardware-Abstraktions- und Mapping-Diagramm (Mailbox-zu-Handle-Zuordnungsmodell).
  • Technischer Zweck & Einordnung: Das Diagramm spezifiziert die Entkopplung physischer Controller-Ressourcen von der BSW-Schnittstelle im AUTOSAR MCAL CAN-Treiber (Can). Es visualisiert die Abbildung von Hardware Message Objects (physische Sende-/Empfangspuffer) auf standardisierte Hardware Object Handles (HOH: HRH und HTH) gemäß [SWS_Can_00403].
  • Architektur-Fokus: Darstellung der Multiplexed Transmission ([SRS_Can_01059], [SWS_Can_00011]), bei der ein einzelnes logisches Sendehandle (HTH) einen Pool aus mehreren physischen Sende-Mailboxen bündelt, um Head-of-Line-Blocking und Prioritätsinversion auf Hardware-Ebene zu eliminieren.

2. Komponenten, Entitäten & Schnittstellen

  • Message Objects of CAN Hardware (Physische Ebene):
    • Acht dargestellte Hardware-Mailboxen im On-Chip-CAN-Controller-RAM.
    • Jedes Message Object kapselt:
      • ID: CAN-Identifier (11-Bit Standard oder 29-Bit Extended Identifier inkl. IDE-/RTR-Bits und Akzeptanzmasken bei Rx).
      • DLC: Data Length Code (0 bis 8 Bytes für Classic CAN bzw. bis 64 Bytes bei CAN FD).
      • SDU: Service Data Unit (Payload-Datenbytes).
  • Hardware Object Handles (HOH – Abstraktionsebene):
    • HRH (Hardware Receive Handle): Logische Empfangs-Identifier (HRH = 0, HRH = 1, HRH = 2, HRH = 3), genutzt durch das CAN Interface (CanIf) via CanIf_RxIndication().
    • HTH (Hardware Transmit Handle): Logischer Sende-Identifier (HTH = 4), übergeben vom CanIf an Can_Write().
    • unused: Physische Controller-Mailbox (Objekt Index 2), die im Treiber unkonfiguriert bleibt.
  • Kardinalitäten & Zuordnungen:
    • HRH → Message Object (1:1): Jedes HRH adressiert genau eine Hardware-Mailbox (konfigurierbar als Full-CAN für Einzel-IDs oder Basic-CAN für ID-Bereiche über Hardware-Filtermasken).
    • HTH → Message Object (1:n, hier 1:3): HTH = 4 spannt über die drei untersten physischen Mailboxen. Dies bildet die AUTOSAR-Konfiguration CanMultiplexedTransmission = TRUE ab.
    • Nicht-kontinuierliches Mapping: Das Vorhandensein der unused-Mailbox belegt, dass logische HOH-Indizes nicht zwingend mit den physischen Mailbox-Registern übereinstimmen müssen.

3. Dynamisches Verhalten & Sequenzablauf

  • Sendeanforderung (Multiplexed Tx Path):
    1. CanIf ruft Can_Write(Hth = 4, PduInfo) auf.
    2. Der CAN-Treiber prüft intern synchron den Belegungsstatus der dem HTH zugeordneten Mailboxen (Objekte 5, 6, 7).
    3. Mailbox-Allokation:
      • Mindestens eine Mailbox frei: Der Treiber selektiert die nächste freie Mailbox (z. B. nach Round-Robin oder absteigender Hardware-Priorität), schreibt ID, DLC, SDU, setzt das Tx-Request-Flag im Controller-Register und quittiert synchron mit E_OK.
      • Alle drei Mailboxen belegt: Can_Write() bricht ab und liefert synchron CAN_BUSY an das CanIf zurück.
  • Bus-Arbitrierung & Tx Confirmation:
    1. Bei mehreren belegten Sende-Mailboxen arbitriert der CAN-Controller intern hardwareseitig nach der Priorität der CAN-ID (niedrigste ID gewinnt den Buszugriff zuerst).
    2. Nach erfolgreichem Senden löst die jeweilige Mailbox einen Interrupt aus (oder wird in Can_MainFunction_Write() gepollt).
    3. Der Treiber ermittelt das übergeordnete HTH (HTH = 4), gibt die physische Mailbox frei und benachrichtigt die obere Schicht asynchron via CanIf_TxConfirmation(CanTxPduId).
  • Empfangspfad (Rx Path):
    1. Ein eintreffender CAN-Frame matcht auf die Filterkriterien einer Rx-Mailbox (z. B. MO 0 für HRH = 0).
    2. Der Treiber liest ID, DLC und SDU aus dem Register und leitet die Daten via CanIf_RxIndication(Hrh, CanId, CanDlc, CanSduPtr) asynchron/interrupt-getrieben oder im Kontext von Can_MainFunction_Read() weiter.

4. Normative Relevanz & Entwickler-Hinweise

  • Vermeidung von Prioritätsinversion ([SRS_Can_01059], [SWS_Can_00011]):
    • Ohne Multiplexing blockiert ein niederpriores Paket in einer einzelnen Tx-Mailbox alle nachfolgenden höherprioren Pakete desselben HTHs, falls der Bus belegt ist.
    • Durch den Mailbox-Pool (1:n) können höherpriore PDUs in parallele freie Hardware-Objekte geladen werden; die interne Controller-Logik sendet automatisch das Frame mit der höchsten Priorität zuerst.
  • Konfigurations-Auswirkung (CanHardwareObject):
    • Im BSW-Konfigurator (ECUC) müssen für ein multiplexendes HTH mehrere CanHardwareObject-Instanzen demselben logischen Handle zugewiesen werden (oder ein CanHardwareObject mit CanObjectId und entsprechender Mailbox-Anzahl/Range konfiguriert werden).
    • CanHandleType wird typischerweise auf BASIC gesetzt.
  • API-Transparenz für obere Schichten:
    • Das CanIf besitzt keine Kenntnis über die 1:n-Hardwareaufteilung. Es operiert strikt gegen den abstrakten Bezeichner HTH = 4.
    • Das FIFO-Verhalten ist bei Multiplexed Transmission über CAN-IDs hinweg nicht garantiert, da die Hardware-Arbitrierung Frames anhand der Identifier-Priorität und nicht anhand der Eintreffreihenfolge auf den Bus treibt.
  • Handle-Nummerierung ([SWS_Can_00403]):
    • Die Zuweisung der ID-Werte für HRH und HTH ist herstellerspezifisch (Vendor Specific). Gemäß AUTOSAR-Empfehlung sollten Handles jedoch controllerweit lückenlos von 0 bis N-1 durchnummeriert werden, um Sprungtabellen (Lookup-Arrays) im Treiber und CanIf effizient zu halten.
