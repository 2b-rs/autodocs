1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB-Kompositionsdiagramm (UML-Objekt-/Komponentendiagramm-Notation) mit überlagerter System-Mapping-Sicht (SwcToEcuMapping).
  • Technischer Zweck: Modellierung von Client-Server-Szenario 3 gemäß AUTOSAR_TPS_SystemTemplate (Kapitel 12 Communication). Es demonstriert eine logische 1:n-Client-Server-Beziehung über Kompositionshierarchiegrenzen hinweg, bei der zwei Clients auf unterschiedlichen Steuergeräten (ECU B, ECU C) denselben Server auf einem zentralen Steuergerät (ECU A) über ein gemeinsames Interface konsumieren.
  • Funktionale Einordnung: Entkopplung der hierarchischen VFB-Softwarearchitektur (DelegationSwConnector, AssemblySwConnector) von der physischen Buskommunikation (SystemMapping, Inter-ECU Client-Server Communication).

2. Komponenten, Entitäten & Schnittstellen

  • Architektur-Container & Komponenten:
    • RootTopLevelComposition (CompositionSwComponentType): Wurzelcontainer der Systemarchitektur.
    • ServerComposition (CompositionSwComponentType): Kapselt den Server auf VFB-Ebene.
    • ClientComposition (CompositionSwComponentType): Kapselt jeweils die Client-Softwarekomponenten.
    • Server (AtomicSwComponentType): Allokiert auf ECU A via SwcToEcuMapping.
    • Client1 (AtomicSwComponentType): Allokiert auf ECU B via SwcToEcuMapping.
    • Client 2 (AtomicSwComponentType): Allokiert auf ECU C via SwcToEcuMapping.
  • Ports & Schnittstellen:
    • PPortPrototype (P auf Server, P1 auf ServerComposition): Bietet das gemeinsame ClientServerInterface an (isOfType).
    • RPortPrototype (R auf Client1 und Client 2, R1 bzw. R2 auf den ClientComposition-Instanzen): Fordert das ClientServerInterface an.
    • ClientServerInterface: Definiert Operationen (ClientServerOperation), In-/Out-Argumente (ArgumentDataPrototype) und anwendungsspezifische Fehler (ApplicationError).
  • Konnektoren & Topologie:
    • DelegationSwConnector: Verbindet kompositionsinterne Ports mit den Außen-Ports (Server.P → ServerComposition.P1; ClientComposition.R1 → Client1.R; ClientComposition.R2 → Client 2.R).
    • AssemblySwConnector: Realisiert das 1:n Fan-Out auf Wurzelebene (ServerComposition.P1 → ClientComposition.R1 und ServerComposition.P1 → ClientComposition.R2).
    • Kardinalität: 1 Server-Port bedient n=2 Client-Ports auf disjunkten ECUs.

3. Dynamisches Verhalten & Sequenzablauf

  • 1. Operationsaufruf (Request-Phase):
    • Client1 (ECU B) oder Client 2 (ECU C) ruft synchron (Rte_Call) oder asynchron (Rte_Call mit Polling/Callback via Rte_Result) eine Operation am Port R auf.
    • Die lokale RTE verpackt Argumente in COM-Signale (ClientServerToSignalMapping) oder serialisiert sie über einen Transformer (z. B. SOME/IP). Die Request-PDU wird über den Kommunikationsstack (PduR, CanTp/SoAd) an den Bus übergeben.
  • 2. Empfang & Dispatching auf ECU A:
    • ECU A empfängt die Request-PDU. Das COM/Transformer-Modul übergibt die Daten an die RTE.
    • Ein OperationInvokedEvent triggert das zuständige Runnable des Server SW-C.
    • Adressierungs-/Routen-Korrelation: Die Server-RTE bzw. der BSW-Stack identifiziert die anfragende Quell-ECU (über dedizierte CAN-IDs / Signal Groups oder via Client-ID/Session-ID im SOME/IP-Header), um den Rückkanal zuzuordnen.
  • 3. Server-Ausführung & Concurrency:
    • Bei simultanen Zugriffen von ECU B und ECU C bestimmt das Attribut canBeInvokedConcurrently des Server-Runnables das Verhalten:
      • false: Sequenzielle Abarbeitung (RTE puffert/serialisiert die Aufrufe).
      • true: Parallele Ausführung im Kontext mehrerer OS-Tasks (Reentrancy-Anforderung an den C-Code des Runnables).
  • 4. Rückmeldung (Response-Phase):
    • Der Server beendet die Operation, setzt Rückgabewerte (OUT/INOUT) und meldet RTE_E_OK oder einen definierten ApplicationError.
    • Die RTE auf ECU A erzeugt die Response-PDU und sendet sie punktgenau an die anfordernde ECU (Unicast an ECU B oder ECU C).
    • Die RTE der empfangenden Client-ECU entpackt die Daten und deblockiert den Client (Rte_Call kehrt zurück bzw. aktiviert das Callback-Runnable).

4. Normative Relevanz & Entwickler-Hinweise

  • System-Extrakt & Bus-Mapping:
    • Da die Clients auf unterschiedlichen ECUs liegen, dürfen Response-Signale nicht gebroadcastet werden. Im System-Template müssen für den Link ECU A $\leftrightarrow$ ECU B und ECU A $\leftrightarrow$ ECU C getrennte Signal-Gruppen, PDUs oder SOME/IP-Instanzen konfiguriert werden (ClientServerToSignalGroupMapping).
  • RTE-Vertrag & Concurrency:
    • Applikationsentwickler des Servers müssen das Runnable strikt reentrant implementieren (keine ungeschützten globalen/statischen Variablen, thread-sichere PIM-Nutzung via OS-Interrupt-Sperren oder ExclusiveArea), falls canBeInvokedConcurrently = true konfiguriert ist.
  • Timeout- & Fehlerbehandlung:
    • Da Aufrufe über Netzwerk-Busse (CAN, FlexRay, Ethernet) laufen, müssen in den ClientServerAnnotation der Client-Ports zwingend timeout-Werte konfiguriert werden.
    • Der Client-Code muss neben RTE_E_OK und fachlichen ApplicationErrors stets Transportfehler wie RTE_E_TIMEOUT, RTE_E_LOST_DATA oder Stack-Rückgabewerte (RTE_E_COM_STOPPED) abfangen.
