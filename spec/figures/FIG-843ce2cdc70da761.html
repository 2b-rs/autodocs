1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Anwendungsfalldiagramm (Use Case Diagram) mit AUTOSAR Adaptive Platform Profil-Stereotypen («aapUseCase», «aapFunctionalCluster», «aapTriggers», «aapParticipates»).
  • Technischer Zweck: Spezifikation der funktionalen Kern-Anwendungsfälle für den Functional Cluster Persistency (ara::per) der AUTOSAR Adaptive Platform (R22-11) im Dokument AUTOSAR_EXP_SWArchitecture.
  • Systemische Einordnung: Modellierung der Mechanismen zur persistenten, spannungsausfallsicheren Datenspeicherung für Adaptive Applications, der Abstraktion gegenüber dem Betriebssystem sowie der Interaktion mit dem Functional Cluster Cryptography (ara::crypto).

2. Komponenten, Entitäten & Schnittstellen

  • Akteure (Actors):
    • Adaptive Application (Primärer Akteur): Triggert Persistierungsoperationen («aapTriggers»).
    • Operating System (Sekundärer Akteur): Partizipiert an der Speicherung («aapParticipates»), stellt Dateisystemtreiber, POSIX-Systemaufrufe und Speichermedium-Zugriff bereit.
  • Systemgrenzen & Cluster:
    • Adaptive Platform: Plattformgrenze des Adaptive-Laufzeitsystems.
    • Persistency: Ausführender Functional Cluster (ara::per), kapselt Zugriffsmodi und Redundanz-/Konsistenzmechanismen.
    • «aapFunctionalCluster» Cryptography (Attribut: daemon-based): Externer Functional Cluster (ara::crypto), der kryptografische Operationen bereitstellt.
  • Anwendungsfälle («aapUseCase») & Beziehungen:
    • Store Persistent Data: Abstrakter Basis-Anwendungsfall.
    • Store Persistent Data with Unique ID: Konkrete Spezialisierung (Generalisierungsbeziehung auf Basis-Use-Case) zur schlüsselbasierten Datenspeicherung (Key-Value Storage via ara::per::KeyValueStorage).
    • Store Persistent Data in File: Konkrete Spezialisierung (Generalisierungsbeziehung auf Basis-Use-Case) zur dateibasierten Speicherung (File Storage via ara::per::FileStorage).
    • Encrypt Persistent Data: Erweiterung über «extend»-Beziehung an Store Persistent Data. Wird konditionell ausgeführt, wenn Verschlüsselung/Integritätsschutz konfiguriert ist. Nutzt via «aapParticipates» das Cryptography-Cluster.

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger & API-Aufruf: Die Adaptive Application initiiert über C++-Schnittstellen (ara::per) eine Schreiboperation (entweder atomarer Key-Value-Eintrag oder Dateizugriff über Streams).
  2. Konditionale Verschlüsselung («extend»):
    • Falls in der Manifest-Konfiguration Verschlüsselung definiert ist, verzweigt der Kontrollfluss in Encrypt Persistent Data.
    • Persistency fordert über IPC/Bibliotheksaufrufe vom daemon-based Cryptography-Cluster (ara::crypto) die Verschlüsselung (z. B. symmetrische Algorithmen via CryptoKeySlot) und/oder Hash-/AEAD-Berechnung an.
  3. Persistierung im Betriebssystem:
    • Persistency schreibt die Nutz- oder Cipher-Daten über standardisierte OS-Schnittstellen (POSIX File I/O wie write(), fsync(), atomares Umbenennen) auf das nichtflüchtige Speichermedium (Flash/eMMC).
  4. Fehlerpfade: Rückmeldung von Fehlern (z. B. Speicher voll, Integritätsprüfung fehlgeschlagen, Krypto-Schlüssel nicht verfügbar) über ara::core::Result bzw. ara::core::ErrorCode an die aufrufende Applikation.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Vertrag (ara::per):
    • Direkte Zugriffe der Applikation auf das native POSIX-Dateisystem verstoßen gegen die AUTOSAR-Architekturvorgaben. Der Zugriff muss ausschließlich über ara::per::OpenKeyValueStorage() bzw. ara::per::OpenFileStorage() erfolgen.
  • Modellierung & Deployment (ARXML):
    • Zuordnung von PersistencyPortPrototype zu PersistencyKeyValueStorageInterface oder PersistencyFileStorageInterface.
    • Bei Nutzung von Encrypt Persistent Data ist im Deployment ein Mapping auf CryptoKeySlot und CryptoProvider erforderlich. Die Schlüsselverwaltung erfolgt getrennt von der Applikationslogik.
  • Plattform- & Stack-Implementierung:
    • Da Cryptography als daemon-based deklariert ist, müssen Stack-Entwickler IPC-Overheads bei häufigen oder großen Persistierungszyklen berücksichtigen.
    • Implementierungen von Persistency müssen Crash-Konsistenz (Power-Fail-Safety) gewährleisten, typischerweise realisiert über Copy-on-Write-, Journaling- oder atomare Rename-Strategien auf OS-Ebene.
