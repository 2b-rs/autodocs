1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess-Aktivitätsdiagramm nach dem AUTOSAR-Methodologie-Metamodell (basiert auf dem OMG SPEM 2.0-Profil / Software & Systems Process Engineering Metamodel).
  • Technischer Zweck: Spezifikation des Übergangsprozesses von der fahrzeugweiten Gesamtsystem-Ebene auf die steuergerätespezifische Systemebene. Es formalisiert die Erzeugung der ECU System Description aus einem vom OEM bereitgestellten System Extract.
  • Funktionale Einordnung: Kernbestandteil der Vorentwicklung bzw. Integrationsphase im klassischen AUTOSAR-Workflow (AUTOSAR_TR_Methodology, R4.1.3). Markiert die formale Nahtstelle zwischen Fahrzeughersteller (OEM / Gesamtsystem-Auslegung) und Tier-1-Zulieferer (ECU-Design).

2. Komponenten, Entitäten & Schnittstellen

  • Work Products (Artefakte / Deliverables):
    • System Extract (Eingangs-Artefakt):
      • Rolle: Definiert die gefilterte Systemsicht für genau ein Ziel-Steuergerät (ECU-Instanz) basierend auf der fahrzeugweiten Gesamt-Systembeschreibung (System Description).
      • Inhalt: Kapselt die zugewiesenen Software-Component-Instanzen (SWC-Mappings), Kommunikationsmatrizen (Frames, I-PDUs, System Signals), Bus-Topologie-Zuordnungen sowie ECU-relevante Timing-Vorgaben.
      • Stereotyp & Multiplizität: «input» mit Kardinalität 1 (präzise ein System Extract erforderlich).
    • ECU System Description (Ausgangs-Artefakt):
      • Rolle: Vollständig konsolidierte, ECU-lokale Systemspezifikation im ARXML-Format.
      • Inhalt: Ergänzte und verfeinerte Systemsicht für das Steuergerät, die als normative Basis für die nachgelagerte BSW- und RTE-Konfiguration dient.
      • Stereotyp & Multiplizität: «output» mit Kardinalität 1..* (mindestens eine oder mehrere versionierte/partielle Ausprägungen).
  • Aktivitäten (Process Tasks):
    • Create ECU System Description (Compound Activity): Übergeordnete Aktivität zur Synthese und Transformation des System Extracts in die finale ECU System Description.
    • Define System View (Sub-Aktivität / Task):
      • Beziehung: Durch Komposition/Aggregation («nesting») in die Hauptaktivität eingebunden; Kardinalität 0..*.
      • Funktion: Optionale bzw. iterative Anreicherung der Systemsicht auf Steuergeräte-Ebene, beispielsweise das Hinzufügen steuergerätespezifischer SWCs (Sensor-/Aktuator-SWCs, herstellerspezifische Diagnose- oder Kalibrier-Komponenten) sowie ECU-interner Signalpfade.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um einen methodischen Workflow (Process Engineering) und nicht um eine Laufzeit-Zustandsmaschine handelt, gilt folgender Ablauf:

  1. Trigger / Vorbedingung:
    • Bereitstellung und erfolgreiche Schema-Validierung des formalen System Extract (ARXML gemäß AUTOSAR R4.1.3) durch den Gesamtsystem-Integrator. Erfüllung von RS_METH_00002 und RS_METH_00077.
  2. Prozessstart:
    • Instanziierung der Aktivität Create ECU System Description im Engineering-Tooling (z. B. System Authoring Tool).
  3. Iterative Verfeinerung (Define System View):
    • Ausführung der Sub-Aktivität mit Multiplizität 0..* (kann entfallen, falls der Extract bereits vollständig ist, oder mehrfach durchlaufen werden).
    • Detaillierung der ECU-Systemgrenzen: Einbindung lokaler Komponenten, Definition lokaler Connectors, Zuweisung von Port Interfaces.
  4. Validierung & Artefakt-Generierung:
    • Konsistenzprüfung bezüglich Namensräumen, Datentypen und Referenzintegrität zwischen System Extract und ECU-spezifischen Erweiterungen.
    • Persistierung der ECU System Description (1..*), womit die Aktivität terminologisch abschließt (RS_METH_00005).
  5. Nachbedingung / Pipeline-Fortsetzung:
    • Die resultierende ECU System Description ist zwingender Input für die Folgeaktivität Extract ECU Configuration Values (Erzeugung der initialen ECU Configuration Description / EcuExtract).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW- & Stack-Entwicklung:
    • Die ECU System Description determiniert die Parametrierung des Kommunikationsstacks (Com, PduR, CanIf/LinIf/FrIf, Bus-Driver). Ohne diesen Schritt fehlen die zwingend benötigten Signal-zu-PDU-Zuordnungen, I-PDU-Gruppen und Trigger-Eigenschaften.
    • System-Signale und Signalgruppen müssen semantisch exakt auf BSW-Com-Signale abgebildet werden können.
  • Applikations- & RTE-Entwicklung:
    • Der Output fixiert die SWC-Typen, Prototypen, Ports (Sender-Receiver, Client-Server) und deren Mappings auf die Ziel-ECU.
    • Constraint: Lokale Anpassungen im Schritt Define System View dürfen die vom OEM im System Extract verbindlich vorgegebenen externen System-Interfaces und Timing-Constraints (z. B. End-to-End-Schutz, Sendeperioden) nicht modifizieren oder invalidieren.
  • Tooling- & Konfigurations-Restriktionen:
    • Konfigurationswerkzeuge müssen beim Import sicherstellen, dass die im System Extract definierten UUIDs (AR-PACKAGE, SYSTEM, ROOT-SW-COMPOSITION-PROTOTYPE) über den Schritt Define System View hinweg erhalten bleiben, um Roundtrip-Engineering und Re-Extracts bei OEM-Änderungen zu ermöglichen.
