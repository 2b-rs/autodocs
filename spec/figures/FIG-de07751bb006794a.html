1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm zur Definition des ECU-Konfigurations-Metamodells (EcucModuleDef).
  • Funktionale Einordnung: Definiert die statische Konfigurationsstruktur des BSW-Moduls CnV2xNet (AUTOSAR Classic Platform, Release R24-11, SWS ChineseV2XNetwork).
  • Architektur-Kontext: Das Modul CnV2xNet implementiert den chinesischen V2X-Netzwerk- und Transport-Layer (insb. DSMP – Dedicated Short Message Protocol gemäß C-V2X / CSIG-Standards) oberhalb des AUTOSAR-Ethernet-Stacks. Es vermittelt zwischen oberen V2X-Applikations-/Facilities-Schichten und dem darunterliegenden EthIf (Ethernet Interface) bzw. PduR.

2. Komponenten, Entitäten & Schnittstellen

#### Modul-Wurzel

  • CnV2xNet (EcucModuleDef): Multiplizität 0..1 (optionales Modul auf ECU-Ebene).

#### Container 1: Allgemeinkonfiguration (CnV2xNetGeneral)

Aggregiert über Assoziation +container (Komposition):

  • CnV2xNetMainFunctionPeriod (EcucFloatParamDef): Multiplizität 1..1, Wertebereich [0.0, 1.0], Default 0.1 s. Zykluszeit der zyklischen Scheduling-Funktion CnV2xNet_MainFunction().
  • CnV2xNetDevErrorDetect (EcucBooleanParamDef): Default false. Schaltet DET-Fehlererkennung und -Reporting per Pre-Compile-Schalter frei.
  • CnV2xNetVersionInfoApi (EcucBooleanParamDef): Default false. Aktiviert die API CnV2xNet_GetVersionInfo().
  • CnV2xNetTxConfirmation (EcucBooleanParamDef): Default false. Steuert, ob Sendebestätigungen (TxConfirmation) an obere Schichten weitergemeldet werden.

#### Container 2: Instanz-/Verbindungskonfiguration (CnV2xNetConfig)

3. Dynamisches Verhalten & Sequenzablauf

Aus den Parametern abgeleitete Ablaufmechanismen:

  1. Zyklische Verarbeitung:
  • Der BSW-Scheduler (SchM / Os) ruft CnV2xNet_MainFunction() periodisch gemäß CnV2xNetMainFunctionPeriod (Default: 100 ms) auf. Dient internen Timeouts, Buffer-Flushes und zyklischem State-Handling.
  1. Sendepfad (Tx):
  • Obere Schicht übergibt SDU via Tx-API -> Validierung gegen CnV2xNetDSMPSduSize -> DSMP-Header-Generierung mit CnV2xNetDSMPprotocolVersion -> Weiterleitung an EthIf über den durch CnV2xNetEthIfRef adressierten Controller unter Nutzung der durch CnV2xNetTxPduRef definierten PDU-ID.
  • Callback: Falls CnV2xNetTxConfirmation == true, löst die Bestätigung von EthIf_TxConfirmation einen Aufruf der oberen TxConfirmation-Schnittstelle aus.
  1. Empfangspfad (Rx):
  • EthIf_RxIndication triggert CnV2xNet anhand der referenzierten Pdu -> Demultiplexing des DSMP-Headers -> Weiterleitung an die Zielschicht über das CnV2xNetRxPduId-Handle.
  1. Fehlerbehandlung:
  • Wenn CnV2xNetDevErrorDetect == true, führen ungültige PDU-IDs, Buffer-Überläufe (> CnV2xNetDSMPSduSize) oder ungültige Versionsangaben zum synchronen Det-Aufruf (Det_ReportError).

4. Normative Relevanz & Entwickler-Hinweise

  • Codegenerator-Einfluss:
  • symbolicNameValue = true für CnV2xNetRxPduId und CnV2xNetTxPduId erzwingt die Generierung typisierter Literale/Makros in CnV2xNet_Cfg.h (z. B. CnV2xNetConf_CnV2xNetRxPdu_<ShortName>), welche als PduIdType-Eingangsparameter für APIs dienen.
  • requiresSymbolicNameValue = true an CnV2xNetEthIfRef erfordert die Auflösung auf die symbolische Controller-ID des Moduls EthIf.
  • Topologische Beschränkung:
  • Sowohl CnV2xNetRxPdu als auch CnV2xNetTxPdu besitzen eine strikte Kardinalität von 1..1 unterhalb von CnV2xNetConfig. Das Metamodell in dieser Fassung unterstützt pro CnV2xNetConfig exakt einen dedizierten Rx- und einen Tx-PDU-Kanal.
  • Speicher- und Payload-Dimensionierung:
  • CnV2xNetDSMPSduSize legt die Puffergrößen im Modul fest. Bei R24-11 muss der zugrunde liegende Ethernet-Treiber/EthIf MTU-Größen unterstützen, die zur konfigurierten SDU-Größe inklusive DSMP-Header-Overhead passen (typisch 1500 Byte bei Standard-Ethernet-Frames, bis zu 64 KiB bei Fragmentierung/Jumbo-Frames).
