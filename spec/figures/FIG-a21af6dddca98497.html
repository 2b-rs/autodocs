1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptuelles Methodik- und Mapping-Diagramm (Hierarchische Abstraktionsebenen und Allokationsmodell).
  • Technischer Zweck: Visualisierung des AUTOSAR-Timing-Designprozesses gemäß AUTOSAR_FO_TR_TimingAnalysis (Kapitel 3.2). Dargestellt wird die Dekomposition und Allokation eines abstrakten, funktionalen Wirkketten-Netzwerks (Function Network) auf ein physisches, vernetztes Steuergerätesystem (Component Network).
  • Systemeinordnung: Dient als methodische Grundlage für die Definition von AUTOSAR Timing Extensions (TIMEX). Es adressiert den Übergang von kundenrelevanten Ende-zu-Ende-Latenzanforderungen (Functional Cause-Effect Chains) auf verteilte Classic/Adaptive Plattform-Architekturen unter Vermeidung des Decomposition Gap (mittels Konzepten wie SL-LET – System Level Logical Execution Time).

2. Komponenten, Entitäten & Schnittstellen

A. Gesamtsystemische Abstraktionsebenen (Linke Spalte)
  • Function Network: Logische Funktionsknoten (Sensoren, logische Verarbeitungsfunktionen, Aktoren) und deren theoretische Datenabhängigkeiten, unabhängig von Hardware-Bindungen.
  • Component Network: Physische/Logische Systemkomponenten (ECUs, Bussysteme, Sensoren, Aktoren), erzeugt/gemappt über den Signal Router.
  • Schematic: Detaillierte elektromechanische Verschaltung (Schaltplan, Schalter/Relais, Pins), abgeleitet via Schematic Synthesis.
  • Wiring Harness: Physikalische Kabelbaum-Topologie (Leitungsbündel, Steckverbinder, Massepunkte), erzeugt via Wiring Harness Synthesis.
  • Topology: Geometrische Bauräume und physische Verlegepfade im Fahrzeug (z. B. Body, Door), abgebildet über den Wiring Harness Router.
B. Detailliertes Mapping (Rechte Detailansicht)
  • Function Network (Logische Ebene):
    • F1.1, F1.2: Lokale funktionale Wirkkette (z. B. Sensorvorverarbeitung zu Regelfunktion).
    • F2, F4, F5: Unabhängige bzw. orthogonale Funktionsbausteine.
    • F3.1, F3.2, F3.3: Komplexe, interaktive Wirkkette mit zyklischen/bidirektionalen Datenflüssen (F3.1 → F3.2, F3.2 ⇄ F3.3).
  • Component Network (Topologische/Physische Ebene):
    • Subnet 1 / Bus type 1: Bus-Segment (z. B. CAN-FD / FlexRay) mit den Knoten ECU 1, ECU 2, ECU 3, ECU 4.
    • Subnet 2 / Bus type 2: Bus-Segment (z. B. Automotive Ethernet / CAN) mit den Knoten ECU 5, ECU 6, ECU 7, ECU 8.
    • Gateway: Zentraler Vermittlungsknoten zur Protokoll- und Signalumsetzung zwischen Subnet 1 und Subnet 2.
  • Allokationsbeziehungen (Mapping-Pfade):
    • Intra-Subnet-Allokation: Wirkkette F1.1 → F1.2 wird direkt auf ECU 1 → ECU 3 innerhalb von Subnet 1 abgebildet.
    • Inter-Subnet- / Gateway-Allokation: Die verteilte Kette F3.x wird über Domain-Grenzen gespreizt: F3.1 residiert auf ECU 2 (Subnet 1), sendet über das Gateway auf Subnet 2 an ECU 8 (F3.2), welches wiederum mit ECU 5 (F3.3) interagiert.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm definiert die Pfade für die statische und dynamische Ende-zu-Ende-Latenzanalyse (End-to-End Timing Analysis / Cause-Effect Chains):

  1. Intra-Bus Latenzpfad (F1.1 → F1.2 über ECU 1 → ECU 3):
    • Ablauf: Task-Aktivierung auf ECU 1 → RTE-Pufferung → COM/PDU-Assemblierung → Bus-Arbitrierung auf Subnet 1 → Frame-Transfer → Interrupt/Rx-Handling auf ECU 3 → Runnable-Ausführung.
    • Latenz-Charakteristik: Deterministisch, gebunden an Task-Jitter, Sendeperioden und Bus-Arbitrierung.
  2. Inter-Bus / Gateway Latenzpfad (F3.1 → F3.2 → F3.3 über ECU 2 → Gateway → ECU 8 → ECU 5):
    • Ablauf:
      1. F3.1 schreibt Inter-ECU-Signal auf ECU 2.
      2. COM sendet Tx-PDU an Subnet 1.
      3. Gateway empfängt Frame (Rx-Interrupt, PduR-Routing/Signal-Routing).
      4. Gateway puffert und serialisiert Signal in Tx-PDU für Subnet 2 (PduR-Gateway-Verzögerung).
      5. Transfer über Subnet 2 zu ECU 8 (F3.2).
      6. ECU 8 verarbeitet Signal, triggert Folgesignal über Subnet 2 an ECU 5 (F3.3), inkl. Rückkopplung.
    • Latenz-Charakteristik: Asynchroner Mehrebenen-Transfer; Akkumulation von Sampling Delay, Routing Delay (PduR), Gateway-Queueing-Jitter und Bus-Latenzen beider Busdomänen.

4. Normative Relevanz & Entwickler-Hinweise

  • TIMEX-Metamodellierung (AUTOSAR_TPS_TimingExtensions):
    • Logische Wirkketten im Function Network müssen als EventChainDescription modelliert werden, bestehend aus EventChain mit definiertem Stimulus (z. B. Sensorevent) und Response (z. B. Aktoransteuerung).
    • Das Mapping auf das Component Network erfordert das Herabbrechen der Gesamtlatenz in relationierte Teil-Constraints: LatencyTimingConstraint (max. Reaktionszeit), AgeTimingConstraint (Signalaktualität) und SynchronizationTimingConstraint.
  • BSW- & RTE-Konfiguration (Classic Platform):
    • PduR / Com: Gateway-Pfade (ECU 2 → GW → ECU 8) erfordern präzise Konfiguration der Routing-Policies im PduR (PDUR_DIRECT vs. PDUR_DEFERRED). Deferred Routing fügt Task-Perioden-Jitter hinzu; Direct Routing erhöht die ISR-Laufzeit.
    • OS / Task-Scheduling: Zur Vermeidung des Decomposition Gap (Dateninkonsistenz und Jitter durch asynchrone Sampling-Punkte) empfiehlt die Spezifikation die Implementierung von LET (Logical Execution Time) bzw. SL-LET. Dies erzwingt deterministische I/O-Zeitpunkte am Task-Start und Task-Ende über die RTE.
  • Signal- und Bus-Design:
    • Der Gateway-Knoten bildet ein potenzielles Bottleneck. Entwickler müssen sicherstellen, dass PDU-Zykluszeiten und PduR-Puffergrößen so dimensioniert sind, dass kein PDU-Verlust oder Priority-Inversion-Effekt bei Buslastspitzen auftritt.

An other example is a powertrain or chassis control function which can cause inconveniences like bucking during shifting or braking.
