1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / AUTOSAR-Metamodell-Ausschnitt (ECUC Parameter Definition Model gemäß AUTOSAR_TPS_ECUConfiguration).
  • Technischer Zweck & Einordnung:
    • Definition des Bindeglieds zwischen der funktionalen Software-Architektur (VFB/SWC-Template), den Basissoftware-Modulen (BSWMD-Template) und der realen Hardware-Topologie (Multicore / OS-Applications).
    • Formalisierung der Zuordnung von Software-Komponenten-Instanzen (SwComponentPrototype) und BSW-Ausführungskontexten (BswDistinguishedPartition) zu virtuellen Ausführungseinheiten (EcucPartition) sowie deren hardwareseitige Abbildung auf physische CPU-Cores (EcucCoreDefinition) über das Betriebssystem (OsApplication).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Parameter-Definitionen
  • EcuC (EcucModuleDef, [0..1]): Zentrales Konfigurationsmodul für übergreifende ECU-Konfigurationen. Enthält als Aggregation (+container [0..1]) die EcucPartitionCollection.
  • EcucPartitionCollection (EcucParamConfContainerDef, [0..1]): Aggregiert (+subContainer [0..*]) sämtliche im System definierten EcucPartition-Container.
  • **EcucPartition (EcucParamConfContainerDef, [0..*]):** Repräsentiert eine logische Speicher- und Privilegien-Partition auf ECU-Ebene.
    • PartitionCanBeRestarted (EcucBooleanParamDef): Gibt an, ob die Partition zur Laufzeit neu gestartet werden darf (Restart-Fähigkeit via OS/RTE).
    • EcucPartitionBswModuleExecution (EcucBooleanParamDef): Flag, ob BSW-C-Code/Treiber in dieser Partition ausgeführt werden dürfen.
    • EcucPartitionBswModuleDistinguishedPartition (EcucForeignReferenceDef, [0..*]): Fremdschlüssel-Referenz (destinationType = BSW-DISTINGUISHED-PARTITION) auf eine «Referrable» BswDistinguishedPartition aus dem BSW Module Description Template.
    • EcucPartitionSoftwareComponentInstanceRef (EcucInstanceReferenceDef, [0..*]): Instanzreferenz (destinationType = SW-COMPONENT-PROTOTYPE, destinationContext = ROOT-SW-COMPOSITION-PROTOTYPE) auf einen «AtpPrototype» SwComponentPrototype aus dem SW Component Template.
  • **OsApplication (EcucParamConfContainerDef, [0..*]):** OS-Container für Speicher- und Timing-Schutzbereiche.
    • OsAppEcucPartitionRef (EcucReferenceDef, [0..1]): Verweist per +destination direkt auf die zugeordnete EcucPartition.
    • OsApplicationCoreRef (EcucReferenceDef, [0..1]): Verweist per +destination direkt auf die physische Core-Definition.
  • **EcucCoreDefinition (EcucParamConfContainerDef, [0..*]):** Repräsentiert einen physikalischen Prozessorkern.
    • EcucCoreId (EcucIntegerParamDef, min = 0, max = 65535): Numerische Hardware-Core-ID.
Strukturelle Beziehungen & Kardinalitäten
  • Zuweisung SWC/BSW → Partition: 1:n (EcucPartition bündelt 0..* SWCs und 0..* BswDistinguishedPartitions).
  • Zuweisung Partition → Core: Erfolgt indirekt über das Betriebssystem: $$\text{EcucPartition} \xleftarrow{[0..1]\ \text{OsAppEcucPartitionRef}} \text{OsApplication} \xrightarrow{[0..1]\ \text{OsApplicationCoreRef}} \text{EcucCoreDefinition}$$
  • Constraint: Eine EcucPartition kann maximal einer OsApplication zugeordnet sein (OsAppEcucPartitionRef ist [0..1]), wodurch die Partition eindeutig an den durch OsApplicationCoreRef referenzierten physischen Core gebunden wird.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches ECUC-Metamodell handelt, existiert kein prozedurales Sequenzdiagramm. Die Laufzeitsemantik manifestiert sich in folgenden Mechanismen:

  • Initialisierungs- & Startphasen-Bindung: Vor dem OS-Start (StartOS()) bindet der Startup-Code die Tasks, ISRs und Speicherregionen der OsApplication an den durch EcucCoreId spezifizierten Core.
  • Partition Restart: Ist PartitionCanBeRestarted == true, kann nach einem Partitionsfehler (z. B. MPU-Trap, Speicherverletzung) die betroffene OsApplication isoliert über OS- und RTE-Dienste heruntergefahren, zurückgesetzt und re-initialisiert werden (Rte_RestartPartition()), ohne den gesamten Core oder die ECU neu zu starten.
  • Inter-Partition- / Inter-Core-Kommunikation:
    • Läuft die Kommunikation zwischen SWCs innerhalb derselben EcucPartition, generiert die RTE direkte In-Memory-/Makro-Zugriffe ohne Speicherschutz-Overhead.
    • Überqueren Sender/Empfänger Partitionen derselben Core-Zuweisung, werden OS-Trap- bzw. Speichergrenzen-Übergänge nötig (Non-Trusted zu Trusted).
    • Gehen Referenzen über unterschiedliche EcucCoreDefinition-Ziele, erzwingt die RTE Inter-Core-Kommunikationskanäle (Shared Memory mit Spinlocks oder hardwarebasierte Inter-Core-Interrupts / IOC).

4. Normative Relevanz & Entwickler-Hinweise

  • RTE- & OS-Codegenerierung:
    • Die Zuordnung von SWC-Prototypen via EcucPartitionSoftwareComponentInstanceRef bestimmt die Zuordnung von Runnables zu OS-Tasks und damit die Task-Affinität zur jeweiligen OsApplication und CPU-Core.
    • Fehlt eine OsAppEcucPartitionRef für eine EcucPartition, sind die darin platzierten SWCs/BSWs nicht schedulbar (Generierungsfehler).
  • BSW-Verteilung (EcucPartitionBswModuleExecution):
    • Steht das Flag auf false, dürfen auf dieser Partition ausschließlich Applikations-SWCs laufen. Dies schützt sicherheitskritische Kerne vor nicht-reentrantem BSW-Code.
    • Steht das Flag auf true, müssen alle darin instanziierten BSW-Module (BswDistinguishedPartition) für Multicore-Ausführung reentrant ausgelegt oder gegen Nebenläufigkeit geschützt sein.
  • Post-Build-Restriktion:
    • Durch postBuildChangeable = false bei EcucPartition ist die Partitionsaufteilung und Core-Zuweisung strikt zur Compile-/Linkzeit festzulegen; eine dynamische Verschiebung von Komponenten auf andere Cores nach dem Flashvorgang ist unzulässig.
