1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Informelles Block- und Interaktionsdiagramm (AUTOSAR Component & Interface Architecture).
  • Architektur-Kontext: AUTOSAR Classic Platform (Release 4.2.2 / 4.3.1), Schichtenarchitektur im Bereich System Services und Application Layer unter Verwendung des flexiblen ECU-Zustandsmanagements (EcuM Flexible).
  • Funktionaler Zweck: Darstellung der Entkopplung von Zustandserfassung/-anforderung und Ausführungsentscheidung: Der EcuM fungiert als Zustandsakteur und Melder (Reporter), während der BswM (Basic Software Mode Manager) als zentrale Entscheidungsinstanz (Arbiter/Rule Engine) die Zustandsübergänge des Steuergeräts steuert und zurück auf den EcuM anwendet.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Akteure
  • SWC 1 (EcuM User): Application/Sensor-Actuator Software Component mit EcuM-Benutzerberechtigung (EcuM User), die aktiv Betriebsmodi anfordert/freigibt.
  • SWC 2: Reguläre Application Software Component, die ausschließlich als Mode-Consumer auf ECU-Moduswechsel reagiert.
  • RTE (Runtime Environment): Abstraktions- und Vermittlungsschicht für Mode-Switch-Events und Client-Server-Kommunikation.
  • EcuM (ECU State Manager): BSW-Dienstkomponente zur Verwaltung grundlegender Steuergerätephasen mit Submodul RUN Request Protocol und den definierten EcuM-Modi:
    • STARTUP, RUN, POST_RUN, SHUTDOWN, SLEEP
  • BswM (Basic Software Mode Manager): Zentrale Modus-Management-Engine mit regelseitig konfigurierten Rules, Expressions, Actions und Notifications.
Schnittstellen & Interaktionen
  • SWC → EcuM (RUN Request Protocol):
    • AUTOSAR Client-Server-Schnittstelle über RTE bzw. direkte C-API: EcuM_RequestRUN() / EcuM_ReleaseRUN() (sowie EcuM_RequestPOST_RUN() / EcuM_ReleasePOST_RUN()) unter Angabe des konfigurierten EcuM_UserType.
  • EcuM → RTE / SWCs (EcuM Mode):
    • AUTOSAR Mode Switch Interface (Mode Declaration Group EcuM_Mode). Der EcuM agiert als Mode Manager (PPortPrototype), die SWCs als Mode Users (RPortPrototype). Schaltet Rte_Switch_<p>_<o>() zur Triggerung von On-Entry-/On-Exit-Runnables in SWC 1 und SWC 2.
  • EcuM → BswM (Status- & Anforderungs-Benachrichtigung):
    • Synchroner C-API-Aufruf: BswM_EcuM_CurrentState(EcuM_StateType State) (SWS_EcuM_04115 / SWS_BswM_00030) zur Indikation des tatsächlich erreichten Zustands.
    • Synchroner C-API-Aufruf: BswM_EcuM_RequestedState(EcuM_StateType State, EcuM_RunStatusType Status) (SWS_EcuM_04116) zur Übergabe aggregierter Benutzeranforderungen (ECUM_RUNSTATUS_REQUESTED, ECUM_RUNSTATUS_RELEASED).
  • BswM → EcuM (Zustandsumschaltung):
    • Synchroner C-API-Aufruf: EcuM_SetState(EcuM_StateType State) (SWS_EcuM_04117 / Action BswM_EcuM_SetState).

3. Dynamisches Verhalten & Sequenzablauf

  1. Modusanforderung:
    • Ein autorisierter User (SWC 1) fordert über die Service-Schnittstelle den Zustand RUN an (EcuM_RequestRUN).
  2. Indikation an BswM:
    • Das RUN Request Protocol wertet die User-Anforderungen aus und meldet Statusänderungen via BswM_EcuM_RequestedState(ECUM_STATE_RUN, ECUM_RUNSTATUS_REQUESTED) unverzüglich an den BswM.
  3. Regel-Evaluierung & Arbitrierung (BswM):
    • Der BswM empfängt die Notification, evaluiert die zugehörigen Mode Arbitration Rules (logische Verknüpfung aus EcuM-Requests, ComM-Kanälen, Dcm-Zuständen etc.).
  4. Zustandsbefehl an EcuM:
    • Ergibt die BswM-Regelauswertung eine Zustandsänderung, feuert die Action-List die hinterlegte BswM-Aktion Set EcuM State und ruft EcuM_SetState(ECUM_STATE_RUN) auf.
  5. Zustandsübergang & Quittierung:
    • Der EcuM führt interne Aktionen des Zielzustands aus und quittiert den Vollzug über BswM_EcuM_CurrentState(ECUM_STATE_RUN).
  6. Propagation an die Applikation (RTE Mode Switch):
    • Der EcuM initiiert den Mode-Switch über die RTE (Rte_Switch). Die RTE benachrichtigt registrierte SWCs (SWC 1, SWC 2) und startet ggf. modustriggerte Executable Entities (Runnables).

4. Normative Relevanz & Entwickler-Hinweise

  • **Architekturparadigma EcuM Flexible (SWS_EcuM_04115–04119):**
    • Der EcuM besitzt im flexiblen Modus keine autonome Entscheidungslogik mehr für Zustandsübergänge zwischen RUN, POST_RUN, SLEEP und SHUTDOWN. Zustandsautomaten dürfen nicht im EcuM fest verdrahtet werden; sämtliche Übergangsbedingungen müssen als BswM-Rules/Expressions konfiguriert werden.
  • Konfigurationspflichten (BswM & EcuM BswMD):
    • BswM: BswMModeRequestPort für EcuM-CurrentState und EcuM-RequestedState anlegen. Mapping auf BswMRule sicherstellen. Entsprechende BswMAction vom Typ BswMEcuMSetState verknüpfen.
    • EcuM: EcuMCommonConfiguration muss für jeden anfordernden Software-Baustein einen eindeutigen EcuMUser deklarieren. Modusanforderungen ohne gültigen User-Handle werden mit ECUM_E_INVALID_PAR an das DET abgewiesen.
  • Einschränkungen & API-Vertrag:
    • EcuM_SetState() darf ausschließlich vom BswM aufgerufen werden. Aufrufe durch SWCs oder andere BSW-Module verletzen die Systemarchitektur.
    • Das Rücksetzen von Anforderungscountern erfolgt erst nach explizitem EcuM_ReleaseRUN(). Vergisst ein SWC-User das Release, verbleibt der EcuM_RequestedState dauerhaft aktiv und verhindert über die BswM-Regeln das Erreichen von POST_RUN, SLEEP oder SHUTDOWN.
  • Multicore-Aspekt:
    • Der EcuM operiert primär auf dem Master-Core. Laufen Benutzer-SWCs auf Satellite-Cores, müssen die RTE-Ports für das RUN-Request-Protokoll und Mode-Indikationen zwingend Inter-Core-fähig konfiguriert sein (RTE-IOC-Pufferung).
