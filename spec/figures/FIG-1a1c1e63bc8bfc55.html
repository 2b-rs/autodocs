1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR BSW-Architekturdiagramm / Schichtenmodell (Darstellung der statischen Komponentenintegration und PDU-Routingpfade).
  • Technischer Zweck: Spezifiziert die funktionale Eingliederung des BSW-Moduls SecOC (Secure Onboard Communication) in den Kommunikations- und System-Service-Stack der AUTOSAR Classic Platform.
  • Architektur-Einordnung:
    • SecOC ist auf der Ebene der Communication Services als PDU-Transformator parallel zum PDU Router (PduR) platziert.
    • Es kapselt die kryptografische Authentifizierung (MAC-Generierung/-Verifikation, Replay-Schutz via Freshness Values) für I-PDUs, agiert transparent zwischen oberen Schichten (AUTOSAR COM) und unteren Transportschichten (CanIf, FrIf, CanTp, FrTp), und koppelt an kryptografische Basisservices (CSM) sowie applikatives Schlüssel-/Zählermanagement über die RTE.

2. Komponenten, Entitäten & Schnittstellen

Schichten & Komponenten
  • Application Layer:
    • SW-C: Reguläre Applikationskomponente; kommuniziert signalspezifisch über die RTE mit AUTOSAR COM.
    • Key & Counter Management SW-C: Spezialisierte Applikations-/Service-Komponente zur Bereitstellung, Rekonstruktion und Synchronisation von Zählern/Zeitstempeln (Freshness Values) sowie zur Verwaltung kryptografischer Schlüssel.
  • Runtime Environment (RTE):
    • Bindeglied zwischen Software-Komponenten und den BSW-Service-Schnittstellen.
  • Communication Services (BSW):
    • AUTOSAR COM: Signal- und I-PDU-Management (Packen/Entpacken von Signalen in Authentic I-PDUs).
    • PDU Router (PduR inkl. Routing Table): Zentraler Verteiler für I-PDUs. Realisiert ein Loopback-Routing über SecOC.
    • SecOC BSW: Kernmodul zur Sicherung (Authentic I-PDU + Freshness Value + MAC = Secured I-PDU) und Authentizitätsprüfung eingehender Nachrichten.
    • TP (FrTp, CanTp): Transportprotokoll-Module zur Segmentierung/Reassemblierung übergroßer PDUs.
    • Bus-Interfaces (FrIf, CanIf): Hardwarenahe Abstraktionsschichten für FlexRay und CAN.
  • System Services (BSW):
    • Crypto Service Manager (CSM): Standardisierte Abstraktion für kryptografische Operationen (Weiterleitung an Krypto-Treiber/HSM via Crypto Interface/Crypto Driver).
    • Diagnostic Event Manager (Dem): Modul zur Erfassung diagnostischer Events und Fehlerspeicherung.
Schnittstellen & Beziehungen (gemäß Legende)
  • PDU-Routing (schwarze Doppelpfeile):
    • AUTOSAR COM ↔ PduR: Austausch ungesicherter I-PDUs (Authentic I-PDUs).
    • PduR ↔ SecOC BSW: Bidirektionale Injektion/Rückführung; SecOC fungiert als PduR-Ziel- und PduR-Quellmodul.
    • PduR ↔ TP (FrTp, CanTp) bzw. PduR ↔ FrIf/CanIf: Weiterleitung der Secured I-PDUs.
  • Cryptographic Services (blauer Pfeil):
    • SecOC BSW → CSM: Dienstaufrufe zur MAC-Berechnung und MAC-Verifikation (Csm_MacGenerate, Csm_MacVerify).
  • Key & Counter Management Services (grüner Doppelpfeil):
    • SecOC BSW ↔ RTE ↔ Key & Counter Management SW-C: Synchroner/asynchroner Austausch von Freshness-Informationen (z. B. Port-Interface SecOC_FreshnessManagement).
  • Key Management (optional, gestrichelter grüner Doppelpfeil):
    • Key & Counter Management SW-C ↔ RTE ↔ CSM: Optionales Einspielen/Aktualisieren von Krypto-Schlüsseln in den Krypto-Stack.
  • Error Reporting (roter Pfeil):
    • CSM → Dem: Meldung von Fehlern der Krypto-Engine/HSM an das Diagnosesystem.

3. Dynamisches Verhalten & Sequenzablauf

A. Sende-Pfad (Tx-Sequenz)
  1. Trigger: AUTOSAR COM stößt Sendeanforderung an → PduR_ComTransmit().
  2. PDU-Loopback: Die Routing Table des PduR routet die Authentic I-PDU via SecOC_Transmit() an das SecOC BSW.
  3. Freshness Value Retrieval: SecOC fragt den aktuellen Zähler/Timestamp synchron oder asynchron über die RTE bei der Key & Counter Management SW-C ab (GetTxFreshnessTruncatedData / GetTxFreshnessValue).
  4. Krypto-Primitiv: SecOC triggert den CSM via Csm_MacGenerate() (Authentic Data + vollständiger Freshness Value).
  5. PDU-Assemblierung: SecOC baut die Secured I-PDU zusammen (Authentic Payload + konfigurierter Truncated Freshness Value + getruncater MAC).
  6. Einspeisung ins Routing: SecOC übergibt die finale PDU via PduR_SecOCTransmit() zurück an den PduR.
  7. Bus-Egress: PduR leitet die Secured I-PDU an CanIf/FrIf bzw. CanTp/FrTp weiter.
B. Empfangs-Pfad (Rx-Sequenz)
  1. Trigger: CanIf/FrIf (oder TP) meldet Empfang via PduR_RxIndication().
  2. Routing: PduR delegiert die empfangene Secured I-PDU an SecOC_RxIndication().
  3. Freshness Value Rekonstruktion: SecOC extrahiert den übermittelten Truncated Freshness Value und fordert über die RTE von der Key & Counter Management SW-C den vollen Zählerstand zur Verifikation an (GetRxFreshnessAuthDataStruct).
  4. Verifikation: SecOC ruft Csm_MacVerify().
  5. Verzweigung:
    • Erfolg: SecOC leitet die extrahierte Authentic I-PDU über PduR_SecOCRxIndication() zurück an den PduR, welcher sie an AUTOSAR COM übergibt.
    • Fehler (MAC ungültig / Replay): PDU wird verworfen; Fehlermeldung an Dem (DTC-Setzung) und optional an IdsM (Security Event Reporting) sowie Det.

4. Normative Relevanz & Entwickler-Hinweise

  • PduR-Konfiguration (Zwei-Schritt-Routing):
    • Für jede gesicherte Botschaft müssen im PduR zwei getrennte Routing-Pfade konfiguriert werden:
      1. Obere Pfad-Ebene: AUTOSAR COM ↔ SecOC (PduR-intern für Authentic I-PDU).
      2. Untere Pfad-Ebene: SecOC ↔ Bus-Interface/TP (für Secured I-PDU).
    • Eine Fehlkonfiguration der PDU-IDs im PduR führt zu Endlosschleifen (Rekursionen) oder PDU-Verlust.
  • CSM-Ausführungsmodi & Puffer-Dimensionierung:
    • Krypto-Operationen über den CSM laufen typischerweise asynchron (Offloading in Hardware-Security-Module / HSM).
    • SecOC muss gepuffert werden (SecOCBufferLength, PDU-Queues). Bei asynchronem CSM-Modus sind Latenzzeiten zwingend bei der Bus-Zykluszeit und PduR-Puffergröße zu berücksichtigen, um PDU-Überschreibungen (Buffer Overflows) zu verhindern.
  • Entkopplung des Freshness Management:
    • SecOC enthält normativ keine feste Frische-Zähler-Logik. Das Freshness Management (FVM) ist zwingend über SW-C (oder ab R20-11 optional über C-APIs) zu implementieren. Schnittstellenverträge bezüglich Ausführungszeit (Synchrone Rückgabe vs. Asynchrone Callbacks) müssen strikt eingehalten werden.
  • PDU-Längenrestriktionen:
    • Durch Hinzufügen von Freshness Bits und MAC-Bytes überschreitet die Payload klassischer CAN-Frames (8 Byte) schnell das Limit. Entwickler müssen entweder CAN FD vorsehen oder zwingend das Routing über CanTp konfigurieren.

Specification of Secure Onboard Communication AUTOSAR CP R25-11 1 Introduction and functional overview This specification is the AUTOSAR Secure Onboard Communication (SecOC) module Software Specification. It is based on AUTOSAR SecOC [1] and specifies how the requirements of the AUTOSAR SecOC SRS shall be realized. It describes the basic security features, the functionality and the API of the AUTOSAR SecOC module. The SecOC module aims for resource-efficient and practicable authentication mechanisms for critical data on the level of PDUs. The authentication mechanisms shall be seamlessly integrated with the current AUTOSAR communication systems. The impact with respect to resource consumption should be as small as possible in order to allow protection as add-on for legacy systems. The specification is based on the assumption that mainly symmetric authentication approaches with message authentication codes (MACs) are used. They achieve the same level of security with much smaller keys than asymmetric approaches and can be implemented compactly and efficiently in software and in hardware. However, the specification provides the necessary level of abstraction so that both, symmetric approaches as well as asymmetric authentication approaches can be used. The SecOC module integrates on the level of the AUTOSAR PduR. Figure 1.1 shows the integration of the SecOC module as part of the Autosar communication stack.
