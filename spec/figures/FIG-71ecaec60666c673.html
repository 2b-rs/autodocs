1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hybrides Architektur- und Signalflussdiagramm (Hard-/Software-Co-Design mit Schichtenmodell und Schnittstellen-Mapping).
  • Kontext: AUTOSAR Classic Platform (Release R2.1.20, Spezifikation AUTOSAR_SoftwareComponentTemplate, Kap. Sensor/Actuator-Entkopplung).
  • Technischer Zweck: Abbildung der durchgängigen Signalwandlungskette zwischen physikalischer Umgebung, Steuergeräte-Hardware und AUTOSAR-Software-Schichten. Das Modell visualisiert die formale Zweiteilung der Signaltransformation:
    1. ECU Abstraction: Kapselung der board-spezifischen Schaltung (Wandlung zwischen Controller-I/O-Registern und elektrischer Repräsentation am ECU-Pin).
    2. Sensor/Actuator SW-C: Kapselung der Aktor-/Sensorkennlinie (Wandlung zwischen elektrischer Repräsentation und physikalischer SI-Größe).

2. Komponenten, Entitäten & Schnittstellen

Hardware-Ebene
  • Sensor / Actuator: Externe physikalische Wandler (z. B. Raddrehzahlsensor, Scheinwerfer/Glühlampe).
  • ECU Electronics: Diskrete Analog-/Treiberschaltung auf dem PCB (Pegelanpassung, Shunts, Transistortreiber/High-Side-Switches, Filter).
  • µC Peripherals: On-Chip-Peripheriemodule des Mikrocontrollers (DIO, ADC, PWM, Timer-Capture).
Software-Ebene
  • µCAL (Microcontroller Abstraction Layer / MCAL Driver): Unterste BSW-Schicht. Direkter Registerzugriff auf die µC-Peripherie über standardisierte Treiber-APIs (DIO_get(), DIO_set()).
  • ECU Abstraction (IoHwAb): BSW-Abstraktionsschicht für ECU-spezifische Hardware. Bildet Treiber-Rohwerte auf elektrische Größen ab.
  • Sensor SW-C (SensorActuatorSwComponentType): Wandelt den elektrischen Zwischenwert in eine physikalische Größe um.
  • Actuator SW-C (SensorActuatorSwComponentType): Wandelt den physikalischen Sollwert in eine elektrische Stellgröße um.
  • Application SW-C 1 & 2 (ApplicationSwComponentType): Reine Funktions-/Regellogik, vollständig hardware- und schaltungsunabhängig.
Schnittstellen & Domänen-Grenzen
  • Physical Interface: Mess- und Stellgrößen der Umwelt/Fahrzeugdynamik (z. B. v in m/s bzw. km/h, Lichtstrom/Lumen).
  • Electrical Interface (Steckerebene):
    • Sensoreingang: Stromsignal I_sensor ∈ [0..200\,mA].
    • Aktorausgang: Laststrom I_ECU ∈ [0..2\,A].
  • Electrical Interface (Mikrocontroller-Pins):
    • ADC/DIO-Spannungsbereich: U_ECU ∈ [0..5\,V] bzw. $U_{\mu\text{C}} \in [0..5\,\text{V}]$.
  • AUTOSAR Software-Interfaces:
    • Applikation ↔ Sensor/Actuator SW-C: Physikalische Schnittstellen (get_v(), set_lamp()), typischerweise mit typisierten physikalischen Einheiten.
    • Sensor/Actuator SW-C ↔ ECU Abstraction: Elektrische Schnittstellen (get_I_ECU(velocity_sensor), set_I_ECU(light_actuator)), bereitgestellt über die RTE als AUTOSAR-Port-Schnittstelle.
    • ECU Abstraction ↔ µCAL: BSW-interne C-Funktionsaufrufe ohne RTE-Overhead (DIO_get(), DIO_set()).

3. Dynamisches Verhalten & Sequenzablauf

Eingangspfad (Sensor Signal Flow)
  1. Physikalische Stimulanz: Physikalische Größe (Geschwindigkeit) steuert den Sensor an.
  2. Elektrische Stromwandlung: Der Sensor prägt einen Strom I_sensor ∈ [0..200\,mA] auf der Leitung zum Steuergerät ein.
  3. Konditionierung (ECU Electronics): Shunt-/Bürdenwiderstände und Operationsverstärker wandeln den Strom in eine proportionale Spannung U_ECU ∈ [0..5\,V] um.
  4. Digitale Abtastung: Das Peripheriemodul (µC Peripherals) erfasst das Signal. µCAL liefert über DIO_get() (bzw. ADC-Read) den Register-/Quantisierungswert an die ECU-Abstraktion.
  5. Elektrische Transformation: ECU Abstraction rechnet den gemessenen Spannungs-/Digitalwert anhand der Hardwareschaltung in den Sensorstrom zurück und übergibt I_ECU via get_I_ECU(...).
  6. Physikalische Skalierung: Sensor SW-C führt Kennlinieninterpolation, Filterung und Fehlerbehandlung durch und stellt den physikalischen Geschwindigkeitswert v via get_v() für Application SW-C 1 bereit.
Ausgangspfad (Actuator Signal Flow)
  1. Funktionale Anforderung: Application SW-C 2 fordert via set_lamp() einen logischen/physikalischen Aktorstatus an (z. B. Ein/Aus oder Dimmwert).
  2. Aktor-Parametrierung: Actuator SW-C bestimmt den notwendigen elektrischen Ansteuerwert und übergibt den Sollstrom via set_I_ECU(light_actuator).
  3. Treiber-Mapping: ECU Abstraction mappt diesen Sollwert auf das konkrete Ansteuerverfahren (z. B. Ausgangs-Pin High/Low oder PWM-Duty-Cycle) und triggert DIO_set() in der µCAL.
  4. Pegelwandlung: Der Mikrocontroller-Pin treibt $U_{\mu\text{C}} \in [0..5\,\text{V}]$ an die Gate-/Treiberstufe der ECU-Elektronik.
  5. Leistungsausgabe: Die ECU-Elektronik schaltet den Lastkreis für das Leuchtmittel mit I_ECU ∈ [0..2\,A].

4. Normative Relevanz & Entwickler-Hinweise

  • Restriktion der SW-C-Allokation (Deployment Constraint):
    • Obwohl die Schnittstelle zwischen ECU Abstraction (IoHwAb) und Sensor/Actuator SW-C als standardisiertes AUTOSAR-Interface modelliert ist, verbietet die Spezifikation faktisch eine verteilte Allokation über Bus-Netzwerke (CAN/LIN).
    • Begründung: Hoher Kommunikations-Overhead und Buslast durch zyklische elektrische Rohdaten sowie Latenzverzug bei Regelungen. Sensor- und Actuator-SW-Cs müssen zwingend auf demselben Steuergerät wie die zugehörige IoHwAb gebunden sein.
  • Separation of Concerns:
    • Treiber-/Board-Portierung: Modifikationen am Schaltplan (z. B. anderer Shunt-Widerstand, geänderte Pin-Zuordnung) erfordern ausschließlich Anpassungen in µCAL und ECU Abstraction.
    • Sensor-/Aktorwechsel: Ändert sich der externe Sensortyp (z. B. andere Kennlinie, geänderter Widerstandsverlauf), muss ausschließlich die Sensor SW-C / Actuator SW-C angepasst werden.
    • Applikations-Wiederverwendbarkeit: Die Application SW-C bleibt vollständig unabhängig von Steuergeräte- und Sensorvarianten.
  • RTE- und API-Design:
    • Das Diagramm zeigt vereinfachte synchrone Client-Server-Aufrufe (get_..., set_...). In Serienimplementierungen erfolgt der Signalfluss für I/O in der Regel über asynchrone, nicht-blockierende Sender-Receiver-Kommunikation (Rte_Read, Rte_Write) innerhalb periodischer Tasks.
    • In AUTOSAR XML (ARXML) ist die Datentransformation zwischen Rohdaten und physikalischen Werten normativ über CompuMethod (z. B. LINEAR oder SCALE_LINEAR_AND_TEXTTABLE) sowie DataFilter zu beschreiben.

Software Component Template AUTOSAR CP R25-11 So if the input to the ECU is an electrical current and the ECU Electronics has converted this current into a voltage (from 2 to 3), the ECU Abstraction will convert the data value voltage into an AUTOSAR signal representing a current (from 4 to 5). This AUTOSAR signal represents the actual current that was provided by the sensor (2). Now the first step in the conversion has to be reversed: the sensor has converted a physical value into an electrical signal. And so the Sensor Software Component has to reverse this again. The Sensor Software Component will read the AUTOSAR signal representing the electrical value and transform it into an AUTOSAR signal representation of the physical value (from 5 to 6). Now this physical value is available on the RTE and can be consumed or read by other SW-Components. Although the interface between the ECU Abstraction and the Sensor Software Component is also an AUTOSAR interface and could be routed through some communication-bus, it will not be practical to separate the ECU Abstraction and the corresponding SensorActuatorSwComponentType due to potentially high communication effort.
