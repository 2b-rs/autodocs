1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Datenfluss- und Schichtenarchitektur-Diagramm (AUTOSAR Classic Platform BSW Layering & PDU/Signal-Flow).
  • Technischer Zweck: Darstellung der Inter-ECU-Kommunikation über Data Distribution Service (DDS) / Real-Time Publish-Subscribe (RTPS) für Sender-Receiver- und Client-Server-Szenarien.
  • Architektur-Einordnung: Veranschaulichung der Zweiteilung der DDS-Integration in der AUTOSAR Classic Platform (R25-11):
  • Signalebene/RTE: Linearer Transformer DdsXf innerhalb der RTE-Transformer-Kette zur serialisierungsnahen Pufferaufbereitung.
  • BSW-PDU-Ebene: Das Basissoftware-Modul Dds, angebunden als I-PDU-Verarbeiter über Schleifenpfade im PduR (PDU Router), zur Erzeugung normativer RTPS-Nachrichtenstrukturen vor der Übergabe an SoAd (Socket Adaptor).

2. Komponenten, Entitäten & Schnittstellen

  • Anwendungsschicht (ASW):
  • Swc Sender / Swc Receiver: AUTOSAR Software-Components mit standardisierten Ports (SenderReceiverInterface oder ClientServerInterface).
  • RTE- & Signal-Ebene:
  • SystemSignalTx / SystemSignalRx: VFB-Datenelemente/Systemsignale.
  • RTE: Stellt Ausführungskontext, Pufferverwaltung und Transformer-Orchestrierung bereit.
  • DdsISignalTx / DdsISignalRx: Interaktionssignale zwischen RTE-Transformer-Engine und DdsXf.
  • Transformer-Schicht:
  • DdsXf (DDS Transformer): Modul zur Überführung von typisierten SW-C-Datenstrukturen in flache, PDU-taugliche Byte-Arrays innerhalb eines von der RTE allokierten Puffers.
  • Kommunikationsdienste & Routing (BSW):
  • Com: Signal-zu-PDU-Assemblierung, PDU-Übertragungsmodi, I-PDU-Triggering.
  • PduR (PDU Router): Zentraler Dispatcher; realisiert Loop-Through-Routing zwischen Applikations-PDUs und RTPS-Netzwerk-PDUs.
  • Dds (DDS BSW-Modul): Kapselt DDS-Entities (DomainParticipant, DataWriter, DataReader, Topic), führt RTPS-Serialisierung/Deserialisierung, Header-Erstellung und Fragmentierung durch.
  • PDU-Entitäten:
  • DdsAppTxPdu / DdsAppRxPdu: Nutzdaten-I-PDUs zwischen Com und PduR.
  • DdsRtpsTxPdu: RTPS-gekapselte Protokoll-PDU aus dem Dds-Modul.
  • SoAdDdsTxPdu / SoAdDdsRxPdu: An den Socket-Adapter übergebene Transport-PDUs.
  • Netzwerkanbindung:
  • SoAd (Socket Adaptor): Abbildung der PDUs auf TCP/UDP-Sockets über TcpIp.
  • Externe Kanäle: TO Dds receiver (Tx via Ethernet/IP/UDP), FROM Dds sender (Rx via Ethernet/IP/UDP).

3. Dynamisches Verhalten & Sequenzablauf

#### Sende-Pfad (Tx, rechts dargestellt):

  1. Trigger: Swc Sender ruft RTE-Sende-API auf (Rte_Write oder Rte_Call).
  2. Transformation: RTE aktiviert die konfigurierte Transformer-Kette; DdsXf kopiert die strukturierten Anwendungsdaten in den RTE-Zielpuffer.
  3. Signalübergabe: RTE reicht das resultierende DdsISignalTx an Com weiter.
  4. PDU-Assemblierung: Com packt das Signal in die DdsAppTxPdu und initiiert PduR_ComTransmit().
  5. Loop-Through Routing (PduR -> Dds): PduR leitet DdsAppTxPdu an das Modul Dds weiter (Dds_Transmit()).
  6. RTPS-Serialisierung: Dds fügt RTPS-Metadaten/Header hinzu, generiert DdsRtpsTxPdu und übergibt diese via PduR_DdsTransmit() zurück an den PduR.
  7. Netzwerkabgabe: PduR routet die PDU als SoAdDdsTxPdu an SoAd (SoAd_IfTransmit()), wo sie über den Ethernet-Treiber auf das Netzwerk gesendet wird (TO Dds receiver).

#### Empfangs-Pfad (Rx, links dargestellt):

  1. Netzwerkeingang: Ethernet-Frame trifft an SoAd ein (FROM Dds sender).
  2. Rx-Indikation (Netzwerk): SoAd meldet Empfang via PduR_SoAdRxIndication() mit der PDU SoAdDdsRxPdu.
  3. Loop-Through Routing (PduR -> Dds): PduR routet die PDU an das Modul Dds (Dds_RxIndication()).
  4. RTPS-Parsing: Dds validiert RTPS-Submessages, extrahiert die Nutzdaten-PDU DdsAppRxPdu und signalisiert diese via PduR_DdsRxIndication() zurück an den PduR.
  5. Weiterleitung an COM: PduR übergibt DdsAppRxPdu an Com (Com_RxIndication()).
  6. Signal-Entpackung & Inverse Transformation: Com extrahiert DdsISignalRx; die RTE triggert die inverse Ausführung von DdsXf.
  7. Zustellung: DdsXf rekonstruiert die typisierte Datenstruktur; die RTE benachrichtigt Swc Receiver (z. B. via DataReceivedEvent).

4. Normative Relevanz & Entwickler-Hinweise

  • Transparenzgebot für SW-Cs: Für die Applikationsebene ist das Übertragungsmedium vollkommen abstrahiert; es werden keine DDS-spezifischen APIs auf SW-C-Ebene verwendet.
  • PduR-Konfiguration: Erfordert zwingend eine bidirektionale Schleifenkonfiguration (Com $\rightarrow$ Dds $\rightarrow$ SoAd und SoAd $\rightarrow$ Dds $\rightarrow$ Com). Fehlkonfigurationen in den Routing-Pfaden führen zu Deadlocks oder PDU-Verlust.
  • Puffer- und Speichermanagement:
  • DdsXf operiert auf statisch generierten RTE-Puffern. Variable Datengrößen (Dynamic Arrays/Strings) müssen im System Extract mit konservativen Worst-Case-Größen dimensioniert werden.
  • Durch die Kaskade (DdsXf-Puffer $\rightarrow$ Com-Puffer $\rightarrow$ Dds-Serialisierung $\rightarrow$ SoAd-Socket-Buffer) entsteht ein mehrfacher Kopier-Overhead; Latenzbudgets bei Fast-Ethernet/Gigabit-Ethernet müssen eng überwacht werden.
  • ID-Trennung: Applikations-PDUs (DdsAppTxPdu/DdsAppRxPdu) und Netzwerk-RTPS-PDUs (SoAdDdsTxPdu/SoAdDdsRxPdu) müssen im EcuC strikt über separate PDU-IDs entkoppelt werden.

Specification of Data Distribution Service Transformer AUTOSAR CP R25-11 7 Functional specification Figure 7.1: Overview of DDS Transformer Figure 7.1 shows the AUTOSAR Classic Platform communication stack where the DDS Transformer is used together with the Dds in a ClientServerInterface application example on server side. When a SW-C initiates an inter-ECU communication which is configured to be transformed, the SW-C hands the data over to the RTE. The RTE executes the configured transformer chain which contains the DDS Transformer. First, the RTE executes the application sample through DdsXf, which creates a copy of the SW-C data (note: the data is copied into a memory buffer provided by the RTE) and sends it as a PDU to Dds. Subsequently, Dds extracts the data from the PDU, serializes it, and packages it into one or more DDS-RTPS message PDUs. Finally, the PDU is sent to the network stack (SoAd, TcpIp, etc.). The DDS Transformer on the receiver side copies the data back from the received PDU into the original data structure in a symmetrical way. These are handed over to the receiving SW-C.
