1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Metamodell-Ausschnitt (UML-Klassendiagramm) gemäß AUTOSAR_TPS_SoftwareComponentTemplate (Release R4.0.3).
  • Technischer Zweck: Formale Definition der Kommunikationsattribute (ComSpec) für Empfangsports (RPortPrototype) im Rahmen der Sender-Receiver-Kommunikation über den Virtual Function Bus (VFB). Es spezifiziert die geforderten Quality-of-Service- (QoS), Pufferungs-, Filter-, E2E- und Plausibilisierungsanforderungen, welche die RTE bei der Codegenerierung für die SWC-Schnittstelle umsetzen muss (Anforderung TPS_SWCT_1219).

3. Dynamisches Verhalten & Sequenzablauf

Beim Eintreffen eines Datenelements aus der BSW (z. B. Com-Stack oder Inter-Runnable-Transport) führt die RTE folgende sequenzielle Verarbeitungsstufen aus:

```

[Netzwerk-/Com-Signal]

│

▼

[E2E-Validierung] (falls usesEndToEndProtection == true; Auswertung maxDeltaCounterInit)

│

▼

[Wertebereichsprüfung] (Prüfung gegen Limits aus SwDataDefProps)

├── Außerhalb: Ausführung handleOutOfRange (saturate, default, invalid, externalReplacement)

└── Statusrückmeldung: indicate (Fehlerstatus an API) oder silent (keine API-Meldung)

│

▼

[Filterung] (nur NonqueuedReceiverComSpec via DataFilter)

├── Filter verwirft: Datenwert wird nicht in Anwenderpuffer übernommen

└── Filter passiert: Pufferaktualisierung

│

┌─────┴──────────────────────────────────────────────────────┐

▼ ▼

[Nonqueued-Pfad] [Queued-Pfad]

  • Überschreibt RAM-Puffer ("Last is Best") - Schiebt Element in FIFO-Puffer
  • Setzt Update-Flag (wenn enableUpdate == true) - Bei Pufferüberlauf (queueLength):
  • Reset des aliveTimeout-Timers Verwerfen & RTE_E_LOST_DATA
  • Bei Timeout-Ablauf: - SWC holt Daten via Rte_Receive
  • handleTimeoutType == replace: Puffer = initValue
  • handleTimeoutType == none: Puffer unverändert
  • API liefert RTE_E_TIMEOUT

```

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-API-Vertrag:
  • NonqueuedReceiverComSpec generiert die API Std_ReturnType Rte_Read_<p>_<o>(<DataType>* data). Bei gesetztem enableUpdate = true wird zusätzlich boolean Rte_IsUpdated_<p>_<o>(void) bereitgestellt.
  • QueuedReceiverComSpec generiert Std_ReturnType Rte_Receive_<p>_<o>(<DataType>* data) mit Rückgabewerten wie RTE_E_OK, RTE_E_NO_DATA (Queue leer) oder RTE_E_LOST_DATA (Queue-Überlauf).
  • Speicher- und RAM-Allokation:
  • queueLength determiniert statisch die Puffergröße des durch den RTE-Generator instantiierten Ringpuffers im RAM.
  • initValue muss zwingend zum C-Datentyp des VariableDataPrototype kompatibel sein; die RTE nutzt diesen Wert zur Initialisierung der globalen Puffer beim Systemstart (Rte_Start).
  • End-to-End (E2E) Integration:
  • Ist usesEndToEndProtection = true, generiert die RTE Aufrufe in die AUTOSAR E2E-Library (E2E_P0xCheck), um Sequence-Counter, CRC und Alive-Zähler vor Bereitstellung der Daten an die SWC zu prüfen.
  • Signal-Transformation (networkRepresentation):
  • Weicht die Netzwerkrepräsentation vom Applikationsdatentyp ab, generiert die RTE Konvertierungsroutinen (Typ-Casting oder Skalierungsfunktionen gemäß CompuMethod), bevor die Daten die Schnittstelle der SWC erreichen.
