1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm mit synchronen/asynchronen Funktionsaufrufen, OS-Taskkontext und Callbacks).
  • Technischer Zweck & funktionale Einordnung: Detaillierung des AUTOSAR Non-Volatile Data Handling Use Case 3a („Store at shutdown“) innerhalb der AUTOSAR Classic Platform. Das Diagramm spezifiziert die vollständige vertikale Interaktion zwischen Application Layer (SW-C), RTE, BSW Mode Manager (BswM), NVRAM Manager (NvM) sowie der Memory Abstraction Layer (Fee/Ea).
  • Architekturziel: Vollständige Entkopplung der Applikationslaufzeit von langsamen Flash-/EEPROM-Schreibzyklen:
    1. Zyklisches Schreiben von Daten im Normalbetrieb erfolgt ausschließlich in den RAM-Spiegel der RTE.
    2. Physische Persistierung erfolgt gesammelt und gesteuert durch den BswM während der ECU-Shutdown-Phase via NvM_WriteAll().
    3. Absicherung der Datenkonsistenz über den synchronen RAM-Spiegel-Mechanismus (NvMUseSyncMechanism bzw. RTE-Mirror-Callback).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Lebenslinien
  • SWC1: Application Software Component (Quelle der NV-Nutzdaten).
  • Rte: AUTOSAR Runtime Environment (Verwalter des Applikations-RAM-Blocks und Puffer-Synchronisation).
  • BswM: Basic Software Mode Manager (Zustands- und Ablaufsteuerung für ECU-Zustände, hier: Shutdown-Koordination).
  • NvM: Non-Volatile Memory Manager (BSW-Dienst zur Verwaltung und Abarbeitung blockbasierter NV-Aufträge).
  • Ea/Fee: Memory Hardware Abstraction Layer (Fee: Flash EEPROM Emulation / Ea: EEPROM Abstraction; Ansteuerung der MemIf/Treiber).
  • BSW Cyclic Task: Betriebssystem-Task (AUTOSAR OS), in dessen Kontext die periodischen Hauptfunktionen der BSW-Module schedult werden.
Schnittstellen & Datenstrukturen
  • Rte_Write_NvData_VDP0(SWC1_VDP0): Synchroner RTE-API-Aufruf über ein NV-Data-Interface (Variable Data Prototype VDP0).
  • Rte_RamBlock0: Von der RTE allokierte RAM-Struktur für den NV-Block; Rte_RamBlock0.Elm0 adressiert das konkrete Datenelement.
  • NvM_SetRamBlockStatus(NvMBlock0, TRUE): NvM-API-Funktion zur Kennzeichnung des RAM-Blocks als geändert (dirty/valid).
  • [Request for Shutdown]:BswM_MainFunction(): Zyklischer Einstiegspunkt des BswM mit Auswertung der Shutdown-Bedingung.
  • NvM_WriteAll(): Asynchroner Multi-Block-Schreibauftrag des NvM zur Persistierung aller geänderten Blöcke im Shutdown.
  • NvM_MainFunction(): Periodische Abarbeitung der internen NvM-Zustandsmaschine (Job-Scheduler).
  • Rte_GetMirror_NvMB_BlkDesc0(&NvMBuffer): Expliziter Synchronisations-Callback der RTE (NvMUseSyncMechanism), um Daten atomar aus Rte_RamBlock0 in den NvM-Arbeitspuffer NvMBuffer zu transferieren.
  • Fee_Write() / Ea_Write(): Asynchrone Treiberaufrufe zur physischen Programmierung der Speicherzellen via MemIf.
  • NvM_JobEndNotification(): Asynchroner Callback der Abstraktionsschicht zur Signalisierung des Schreibendes an den NvM.

3. Dynamisches Verhalten & Sequenzablauf

  1. Phase 1: Applikativer Schreibzugriff zur Laufzeit (Dirty Marking)
    • SWC1 übergibt Nutzdaten per Rte_Write_NvData_VDP0(SWC1_VDP0) an die RTE.
    • Die RTE schreibt den Wert synchron in ihren internen Puffer (Rte_RamBlock0.Elm0 = SWC1_VDP0).
    • Die RTE informiert den NvM über den geänderten Zustand via NvM_SetRamBlockStatus(NvMBlock0, TRUE) und erhält E_OK.
    • Die RTE kehrt sofort zu SWC1 zurück; es erfolgt kein physischer Schreibvorgang auf das Medium.
  2. Phase 2: Shutdown-Trigger via BswM
    • Im Kontext des BSW Cyclic Task wird BswM_MainFunction() aufgerufen und erkennt eine Shutdown-Anforderung ([Request for Shutdown]).
    • Der BswM triggert die Shutdown-Persistierung über NvM_WriteAll(). Der Aufruf schlägt den Auftrag in der NvM-Queue an und kehrt unmittelbar zum BswM zurück.
  3. Phase 3: Zyklische Abarbeitung & Puffer-Spiegelung (NVM Synchronization Mechanism)
    • In einem Folgetakt des BSW Cyclic Task ruft das OS NvM_MainFunction() auf.
    • Der NvM verarbeitet NvMBlock0, prüft dessen Status (durch Phase 1 auf valid/changed gesetzt) und benötigt einen stabilen Datenstand.
    • Zur Vermeidung von Inkonsistenzen bei parallelen Task-Zugriffen ruft der NvM Rte_GetMirror_NvMB_BlkDesc0(&NvMBuffer) auf.
    • Die RTE kopiert den Inhalt von Rte_RamBlock0 in den übergebenen Zeiger &NvMBuffer (Ram Block Provided -> NvMBuffer).
    • Der NvM leitet den Schreibauftrag über Fee_Write() bzw. Ea_Write() an die darunterliegende Speicherschicht weiter.
  4. Phase 4: Physischer Abschluss (Job Completion)
    • Nach Fertigstellung des Hardware-Schreibvorgangs meldet Ea/Fee das Ergebnis asynchron über NvM_JobEndNotification() an den NvM zurück.
    • Der NvM setzt das interne Resultat des Blocks auf NVM_REQ_OK.

4. Normative Relevanz & Entwickler-Hinweise

  • NvM-Block-Konfiguration (NvMBlockDescriptor):
    • NvMSelectBlockForWriteAll = TRUE: Zwingend erforderlich, da der Block sonst bei NvM_WriteAll() ignoriert und Datenverlust beim Abschalten auftreten würde.
    • NvMSetRamBlockStatusApi = TRUE: Muss aktiviert sein, damit die RTE NvM_SetRamBlockStatus() aufrufen darf.
    • NvMBlockManagementType: Typisch NVM_BLOCK_NATIVE oder NVM_BLOCK_REDUNDANT.
    • NvMBlockUseSyncMechanism = TRUE: Zwingend für dieses Sequenzmuster. Erzwingt die Bereitstellung des NvM-internen Spiegels (NvMBuffer) und die Generierung der Mirror-Lese- und Schreib-Callbacks durch die RTE (Rte_GetMirror_* / Rte_SetMirror_*).
  • RTE-Konfiguration:
    • Das NvDataInterface muss mit RteInitializationStrategy und RteRamBlockRef auf den entsprechenden NvM-Block gemappt werden, damit die RTE den Aufruf von NvM_SetRamBlockStatus automatisch kapselt.
  • BswM & ECU-State-Manager (EcuM) Integration:
    • Der BswM darf die ECU-Stromversorgung (bzw. den Übergang in SLEEP/OFF) erst freigeben, wenn NvM_WriteAll() vollständig terminiert ist. Dies erfordert das Polling von NvM_GetErrorStatus(0) (Multi-Block-ID 0) auf ungleich NVM_REQ_PENDING über BswM-Rules oder EcuM-Shutdown-Hooks.
  • Laufzeit- & Pufferanforderungen:
    • Durch NvMUseSyncMechanism = TRUE wird prozessorseitig zusätzlicher RAM für den NvM-Spiegelpuffer alloziert (RAM-Overhead = Blockgröße), jedoch wird die Blockade-Dauer der Quell-RAM-Blöcke auf die reine Kopierzeit innerhalb von Rte_GetMirror_* minimiert.
