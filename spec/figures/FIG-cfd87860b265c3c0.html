Figure 3.40: Modeling of the PersistencyFileStorageInterface

1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (AUTOSAR M2-Metamodell-Ausschnitt).
  • Architektur-Kontext: AUTOSAR Adaptive Platform (Release R22-11), Spezifikation AUTOSAR_TPS_ManifestSpecification.
  • Funktionale Einordnung: Modellierung der Port-Schnittstellen für den Functional Cluster Persistency (ara::per). Das Metamodell definiert die deklarative Konfiguration für dateibasierten Speicher (PersistencyFileStorageInterface) zur Entkopplung der Applikationslogik von der physischen Dateisystem- und Speicherverwaltung (Flash, eMMC, NVRAM) sowie zur Festlegung von Redundanz- und Update-Strategien bei Software-Aktualisierungen via UCM (Update and Configuration Management).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen
  • PersistencyInterface (abstrakt, Package PortInterface):
    • Basisklasse aller Persistenz-Schnittstellen (FileStorage und KeyValueStorage).
    • Attribute:
      • contractVersion: StrongRevisionLabelString [0..1] – Streng typisierte Versionsbezeichnung der Schnittstellenvereinbarung (Contract Versioning).
      • minimumSustainedSize: PositiveInteger [0..1] – Garantiertes Speichervolumen in Bytes, das das System für diese Schnittstelle vorhalten muss.
      • redundancy: PersistencyRedundancyEnum [0..1] – Redundanzkonfiguration auf Speichergesamt-Ebene.
      • updateStrategy: PersistencyCollectionLevelUpdateStrategyEnum [0..1] – Verhalten bei Software-Updates auf Ebene des Gesamtspeichers.
  • PersistencyFileStorageInterface:
    • Konkrete Spezialisierung von PersistencyInterface (Generalisierungsbeziehung).
    • Attribute:
      • maxNumberOfFiles: PositiveInteger [0..1] – Obergrenze der gleichzeitig verwaltbaren Dateien im File Storage.
    • Assoziationen:
      • Komposition +fileElement: PersistencyFileElement [0..*] – Aggregiert 0 bis n vorab deklarierte Dateielemente.
  • PersistencyInterfaceElement (abstrakt, Package Identifiable):
    • Basisklasse für einzelne Elemente innerhalb einer Persistenz-Schnittstelle; erbt Identifizierbarkeit (shortName).
    • Attribute:
      • updateStrategy: PersistencyElementLevelUpdateStrategyEnum [0..1] – Granulare Update-Strategie für das einzelne Element.
  • PersistencyFileElement:
    • Spezialisierung von PersistencyInterfaceElement (Generalisierungsbeziehung).
    • Repräsentiert eine konkrete, im Manifest definierte Datei.
    • Attribute:
      • contentUri: UriString [0..1] – Pfad/URI zum initialen Dateiinhalt im Software-Paket.
      • fileName: String [0..1] – Logischer Dateiname innerhalb des Dateispeichers.
Enumerationen
  • PersistencyRedundancyEnum:
    • none – Keine softwareseitige Redundanz.
    • redundant – Gesamter Speicher wird redundant/gespiegelt vorgehalten (z. B. M-out-of-N, Duplizierung).
    • redundantPerElement – Redundanz wird granular auf Dateiebene gesteuert.
  • PersistencyCollectionLevelUpdateStrategyEnum:
    • keepExisting – Bei Aktualisierung des Software-Clusters bleibt der bestehende Dateispeicher unverändert.
    • delete – Der gesamte Speicherbereich wird bei einem Update geleert/gelöscht.
  • PersistencyElementLevelUpdateStrategyEnum:
    • overwrite – Bestehende Zieldatei wird mit dem Stand aus contentUri überschrieben.
    • keepExisting – Existierende Zieldatei bleibt unberührt; fehlt sie, wird sie initial angelegt.
    • delete – Datei wird im Rahmen des Updates gezielt entfernt.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches M2-Strukturdiagramm bildet die Grafik keine Laufzeitsequenzen ab; das dynamische Verhalten manifestiert sich in zwei Phasen:

  1. Software-Update & Deployment (UCM-Verhalten):
    • Trigger: Aktivierung eines neuen Software-Cluster-Pakets via ara::ucm.
    • Evaluierungshierarchie:
      1. Auswertung von PersistencyInterface.updateStrategy: Bei delete wird der physische Speicherordner komplett zurückgesetzt.
      2. Bei keepExisting: Iteration über alle fileElement-Instanzen. Ist für ein PersistencyFileElement eine updateStrategy definiert, überschreibt sie das Collection-Verhalten (overwrite, keepExisting, delete) und synchronisiert den Inhalt über contentUri.
  2. Laufzeit-Zugriff (ara::per-Stack):
    • Applikation öffnet den Storage über ara::per::OpenFileStorage(...) via Port-Referenz.
    • Der Persistency-Stack prüft Quotas (maxNumberOfFiles, minimumSustainedSize) gegen das Dateisystem und erzwingt bei I/O-Operationen transparent die konfigurierte Redundanz (PersistencyRedundancyEnum).

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurations- und Manifestbindung (TPS_MANI_01142, RS_MANI_00027):
    • PersistencyFileStorageInterface dient als Typ für PRPortPrototype, PPortPrototype oder RPortPrototype im Application Design Manifest.
    • Das Deployment-Mapping verknüpft dieses Interface mit physischen Speicherpfaden im Ausführungsmanifest (PersistencyFileStorageDeployment).
  • Schnittstellen-Versionierung (contractVersion):
    • Mit contractVersion: StrongRevisionLabelString [0..1] wird die formale Versionierung der Persistenz-Schnittstelle gemäß AUTOSAR-Revisionsetikett eingeführt. Integratoren und UCM können damit zur Entwurfs- und Update-Zeit prüfen, ob die Softwareversion einer Applikation mit dem Datenmodell und Speicherinhalt der Schnittstelle kompatibel ist.
  • Ressourcenallokation & Quotas:
    • minimumSustainedSize und maxNumberOfFiles sind bindende Vorgaben für Integratoren. Sie bestimmen Partitionsgrößen, POSIX-Quotas und Inode-Reservierungen im Zielbetriebssystem (z. B. QNX, Linux).
    • Überschreitet eine Applikation zur Laufzeit maxNumberOfFiles, muss der Stack Operationen wie OpenFileWrite() mit dem Fehler ara::per::PerErrc::kOutOfStorage bzw. kQuotaExceeded ablehnen.
  • Integrität & ASIL-Anforderungen:
    • Ist redundancy auf redundant konfiguriert, implementiert der ara::per-Stack automatische Prüfsummen (CRC32/CRC64), Shadow-Files oder Block-Level-Replikation zur Erkennung und Behebung von Bitkippern/Flash-Degradation, ohne dass die Applikation eigene Redundanzlogik implementieren muss.
  • Release-Gültigkeit: Vollständig konform zu AUTOSAR Adaptive Platform R23-11.
