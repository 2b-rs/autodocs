1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Methodik-Aktivitätsdiagramm / Datenfluss-Prozessdiagramm (SPEM/BPMN-angelehnt).
  • Technischer Zweck: Dekomposition des ECU-Konfigurationsprozesses (ECU Configuration) in drei standardisierte Teilaktivitäten gemäß AUTOSAR-Methodik (Classic Platform, R2.1.20 / Folge-Releases).
  • Funktionale Einordnung: Bildet das Bindeglied zwischen der systemweiten Architekturphase (System Configuration / ECU Extract) und der Build-Phase (Kompilierung von BSW-Stacks, RTE und Applikations-SWCs).

2. Komponenten, Entitäten & Schnittstellen

Datenartefakte (Dateisymbole)
  • ECU Extract of System Configuration (.XML / ARXML):
    • Rolle: Formaler Eingangsvektor aus dem Gesamtsystem-Design (: System).
    • Inhalt: Kommunikationsmatrix (Frames, Signale, PDUs, Bus-Topologie), Software-Component-Instanziierung und Mapping auf die Ziel-ECU.
  • ECU Configuration Description (.XML / ARXML, EcucDescription):
    • Rolle: Zentrales, modulspezifisches Konfigurationsmodell der BSW-Module und der RTE für die spezifische ECU.
    • Inhalt: Konkrete Parameter-Container (EcucContainerValue), modulspezifische Konfigurationsparameter (EcucParameterValue) und Referenzen (EcucReferenceValue).
  • AUTOSAR Parameter Definition (Lineal-/Zeichendreieck-Symbol):
    • Rolle: Normatives Metamodell / Schablone (EcucParameterDefinition).
    • Inhalt: Definiert Struktur, Typen, Wertebereiche, Defaultwerte und Multiplizitäten aller konfigurierbaren Parameter für die BSW-Module.
  • Module Code (.c) & Module Headers (.h):
    • Rolle: Generierte Implementierungs- und Konfigurationsartefakte.
    • Inhalt: Typischerweise <Mip>_Cfg.h / <Mip>_PBcfg.c sowie RTE-Generierungsartefakte (Rte.c, Rte_<swc>.h).
Aktivitäten & Werkzeuge (Chevron-Operatoren)
  • Generate Base ECU Configuration Description:
    • Automatisierter Extraktions- und Initialisierungsschritt. Wandelt die Systemvorgaben des ECU Extract unter Einhaltung der Parameter Definition in eine BSW-Basis-Konfiguration um (z. B. Initial-Setup von Com, PduR, CanIf).
  • Edit ECU Configuration:
    • Werkzeuggestützter Konfigurationsschritt (ECU-Konfigurator-GUI/Toolchain). Anreicherung, Validierung und Modifikation der Modulparameter.
  • Generate Configured Module Code:
    • Modulspezifische Codegeneratoren (BSW-Generatoren der Tier-1/Stack-Zulieferer und RTE-Generator).
Beziehungen & Kontroll-/Datenflüsse
  • Solide gerichtete Kanten: Direkter Artefaktfluss (Erzeugung / Konsumierung).
  • Bidirektionale Kanten: Iterativer Lese- und Schreibzugriff zwischen ECU Configuration Description und Edit ECU Configuration.
  • Gestrichelte Kanten:
    • Führungsgröße: Zuweisung der normativen Regeln (AUTOSAR Parameter Definition) an die Generierungs- und Editiertätigkeiten.
    • Rückkopplungspfad (Dashed Return Arrow): Re-Synchronisation von der Konfigurationsebene zurück auf den ECU Extract (Feedback-Loop bei Anpassungsbedarf auf Netzwerk-/Systemebene).

3. Dynamisches Verhalten & Sequenzablauf

  1. Ingestion & Base Generation:
    • Trigger: Bereitstellung des finalen oder inkrementellen ECU Extract of System Configuration.
    • Das Generierungs-Tool erzeugt automatisch die minimale, konsistente Basiskonfiguration (ECU Configuration Description), basierend auf der normativen Parameter Definition.
  2. Refinement & Iterative Parameterisierung:
    • Der Entwickler/Integrator parametriert modulspezifische Details via Edit ECU Configuration (z. B. OS-Task-Layout, Treiber-Hardwarekanäle, Timeout-Zeiten, Puffergrößen).
    • Bei architekturellen Konflikten (z. B. unzureichende PDU-Puffergröße für geforderte Signalgrößen) triggert die gestrichelte Feedback-Linie eine Änderungsmeldung/Neugenerierung des System-Extracts.
  3. Artefakt-Generierung (Code & Header):
    • Nach bestandener Konsistenzprüfung (Rule-Checking) parsen die BSW- und RTE-Codegeneratoren die ECU Configuration Description.
  4. Code-Ausgabe:
    • Ausgabe der modulspezifischen Header (.h) und Quelldateien (.c), die deterministisch die Pre-Compile- und Post-Build-Strukturen für die Toolchain (Compiler/Linker) bereitstellen.

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von statischem und generiertem Code:
    • BSW-Treiber und Stacks bestehen aus statischem Quellcode (vom Zulieferer implementiert) und den hier generierten Artefakten (.c/.h). Entwickler dürfen generierten Code nicht manuell modifizieren; Änderungen müssen zwingend auf Modellebene in der ECU Configuration Description erfolgen.
  • Konfigurationsklassen-Mapping (Binding Times):
    • Pre-Compile Time (.h): Schalter und Konstanten (z. B. #define CAN_DEV_ERROR_DETECT STD_ON, Feature-Flags, feste Pufferdimensionierungen).
    • Link-Time / Post-Build Time (.c): Datenstrukturen und Deskriptor-Tabellen (z. B. const Can_ConfigType Can_Config, Routing-Tabellen des PduR), die getrennt gelinkt oder zur Laufzeit als Flash-Datenblock initialisiert werden.
  • Konformität & Toolchain-Voraussetzungen:
    • Jedes Konfigurations-Tool muss das AUTOSAR XML-Schema (AUTOSAR_ECU_Configuration) validieren. Ein Generatorlauf darf erst starten, wenn alle Pflichtparameter (minMultiplicity >= 1) belegt und Referenzen aufgelöst sind.
  • Roundtrip- und Integrationsrisiko:
    • Bei System-Extract-Updates muss das Tooling inkrementelles Merging unterstützen, um manuell eingepflegte BSW-Werte in der ECU Configuration Description vor Überschreibung zu schützen.
