1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptuelles Schachtelungs- und Strukturdiagramm (Containment/Packaging Model).
  • Architektur-Kontext: AUTOSAR Adaptive Platform (Releases R19-03, R19-11, R20-11), Spezifikation AUTOSAR_TPS_ManifestSpecification (Kapitel Update & Configuration Management) in Verbindung mit AUTOSAR_SWS_UpdateAndConfigurationManagement (UCM).
  • Technischer Zweck: Formale Trennung zwischen der transienten Transport-/Auslieferungseinheit (SoftwarePackage) und der persistenten Deployment-/Laufzeiteinheit auf der Ziel-Machine (SoftwareCluster) inklusive eines zweistufigen Sicherheits- und Manifestmodells. Adressiert die Anforderungen RS_MANI_00035 (Software Packaging) und TPS_MANI_01225 (Konzeptionelle Beziehung von Software Package und Software Cluster).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert eine hierarchische Kapselung:

  • Software Package (Transiente Hülle):
  • Das transportierbare Artefakt (z. B. TAR-/ZIP-basiertes Containerformat oder proprietäres Image), das über OTA-Backends oder Diagnoseschnittstellen an den UCM übertragen wird.
  • Umfasst exakt einen SoftwareCluster, das zugehörige SoftwarePackageManifest sowie die SoftwarePackageSignature.
  • Software Package Manifest (UCM-Metadaten):
  • Steuerungsdeskriptor für den UCM-Update-Prozess.
  • Spezifiziert Paketversion, Ziel-Cluster-Kennung, Installationsaktion (kInstall, kUpdate, kRemove), Ziel-Hardware/Machine-Kompatibilität, Abhängigkeiten (Dependencies), Pre-/Post-Actions sowie Hashwerte des Inhalts.
  • Software Package Signature (Transportsicherung):
  • Äußere digitale Signatur (kryptografisches Siegel) über das gesamte Paket (inkl. SoftwarePackageManifest und SoftwareCluster).
  • Sichert Authentizität und Integrität auf dem Transportweg vom Backend bis zur UCM-Instanz.
  • Software Cluster (Persistente Funktionseinheit):
  • Die kleinste unabhängig installierbare, aktualisierbare und versionierbare Funktionseinheit auf einer Adaptive Machine (z. B. Adaptive Core Platform, Base Services oder Applikations-Cluster).
  • Kapselt die ausführbaren Binaries, Bibliotheken, Ressourcen sowie seine eigene Manifest- und Signaturstruktur.
  • Software Cluster Manifest (Plattform-Deskriptor):
  • Maschinenspezifische ARXML-Modellierung, die nach der Aktivierung für das Execution Management (EM), State Management (SM) und die Platform-Dienste relevant ist (z. B. Prozessdefinitionen, Startup-Konfigurationen, Resource-Group-Zuweisungen).
  • Software Cluster Signature (Laufzeit-/Payload-Sicherung):
  • Innere digitale Signatur ausschließlich über den Payload des Software Clusters (Binaries, Konfigurationen und SoftwareClusterManifest).
  • Dient dem Integritäts- und Herkunftsnachweis des Clusters unabhängig vom Transportcontainer; verbleibt persistent auf dem Steuergerät zur Re-Validierung vor oder während des Boot-/Startvorgangs.

3. Dynamisches Verhalten & Sequenzablauf

Der Lebenszyklus im UCM gliedert sich entlang der Kapselungsebenen in folgende Phasen:

  1. Transfer-Phase (TransferStart / TransferData / TransferExit):
  • Das SoftwarePackage wird als Stream an den UCM übertragen und im Zwischenspeicher abgelegt.
  1. Paket-Validierung (Äußere Stufe):
  • UCM validiert die Software Package Signature via Crypto-Stack / Key Storage Provider.
  • Schlägt die Prüfung fehl: Abbruch mit entsprechendem UCM-Fehlercode (z. B. PackageIntegrityFailed); der Inhalt wird nicht entpackt.
  1. Parsing & Vorbereitung (ProcessPackage):
  • Auslesen des Software Package Manifest.
  • Validierung von Abhängigkeiten, Versionskompatibilitäten und Hardware-Targets.
  • Entpacken des eingebetteten SoftwareCluster in den Staging-Bereich (z. B. inaktive A/B-Partition oder dediziertes Cluster-Dateisystem).
  1. Cluster-Validierung (Innere Stufe):
  • Verifikation der Software Cluster Signature über den entpackten Payload und das Software Cluster Manifest.
  • Absicherung gegen Manipulation im lokalen Staging-Bereich vor der Freigabe.
  1. Aktivierung & Commit (Activate / Finish / Rollback):
  • Das State Management synchronisiert den Funktionswechsel; Execution Management übernimmt die Konfiguration aus dem Software Cluster Manifest.
  • Nach erfolgreicher Validierung (Finish) wird das äußere SoftwarePackage samt temporärem Software Package Manifest gelöscht; der SoftwareCluster verbleibt aktiv. Bei Fehlern greift der atomare Rollback.

4. Normative Relevanz & Entwickler-Hinweise

  • Zweistufiger CI/CD-Signing-Workflow:
  • Build-Toolchains dürfen Payload und Package nicht in einem monolithischen Schritt signieren. Erst muss der SoftwareCluster gebaut und mit dem privaten Schlüssel der Funktionsdomäne/des Zulieferers signiert werden (Software Cluster Signature). Anschließend schnürt der Fahrzeughersteller (OEM) oder Integrator das SoftwarePackage mit dem SoftwarePackageManifest und signiert dieses mit dem Flotten-/Transport-Key (Software Package Signature).
  • Trennung der ARXML-Artefakte (TPS_MANI_01225):
  • Modellierer müssen streng zwischen SoftwareCluster (Package: AUTOSAR::AdaptivePlatform::SoftwareCluster) und SoftwarePackage (Package: AUTOSAR::AdaptivePlatform::Deployment::SoftwarePackage) unterscheiden.
  • Prozess- und Ausführungsmodelle gehören ausschließlich in das Software Cluster Manifest, nicht in das Software Package Manifest.
  • Lebenszyklus- und Speicher-Management (UCM-Entwicklung):
  • Storage-Budgetierung: Embedded-Dateisysteme müssen temporär den Overhead von SoftwarePackage (Archiv) + extrahiertem SoftwareCluster (Staging) parallel vorhalten können.
  • Persistenzregel: Nach Abschluss des Updates existiert auf dem Target nur noch der SoftwareCluster. Das SoftwarePackage ist ein rein transientes Transportartefakt.
