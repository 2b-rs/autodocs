1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Methodik-Aktivitätendiagramm (basierend auf SPEM 2.0 / Software & Systems Process Engineering Metamodel-Notation).
  • Technischer Zweck: Definition der Methodik-Aktivität „Set System Root“ innerhalb des Entwurfsprozesses eines Gesamtsystems (System Design Phase).
  • Architekturale Einordnung: Verknüpft dezentral erstellte Entwurfs- und Konfigurationsfragmente (Software-Architektur, Netzwerktopologie, Mappings und Constraints) zu einem formal konsistenten Einstiegspunkt des AUTOSAR-Datenmodells: dem Wurzelelement der Systembeschreibung (System-Element in ARXML).

2. Komponenten, Entitäten & Schnittstellen

  • Akteur / Rolle:
  • System Engineer (Kardinalität 1, Beziehung: «performs»): Verantwortliche Ingenieursrolle für die Ausführung der Modellintegration und Definition des Systemrahmens.
  • Prozess-Aktivität:
  • Set System Root: Kernaktivität zur Instanziierung und Aggregation des AUTOSAR-Systemmodells.
  • Eingangs-Artefakte («input»):
  1. Topology (Kardinalität 1): Physische Netzwerktopologie (Cluster, ECUs, Gateways, physikalische Kanäle wie CAN, LIN, FlexRay, Ethernet).
  2. Software Component Mapping Constraints (Kardinalität 1): Randbedingungen für die Allokation von SWC-Prototypen auf bestimmte ECUs (z. B. Co-Location, Anti-Affinity, Speicher-/Sicherheitsanforderungen).
  3. Mapping of Software Components to ECUs (Kardinalität 1): Explizite Zuweisung von atomaren SWCs bzw. Component Prototypes auf konkrete Steuergeräte (SwcToEcuMapping).
  4. Signal Path Constraints (Kardinalität 1): Latenz-, Routing- und Integritätsrestriktionen für Signalübertragungswege über Busgrenzen hinweg.
  5. Communication Layers (Kardinalität 1): Kommunikationsmatrix-Artefakte (Frames, PDUs, Signale, Timing-Parameter, Network Management).
  6. VFB Composition (Kardinalität 1): Hierarchische Top-Level-Software-Komposition der VFB-Architektur (RootSwCompositionPrototype).
  7. Data Mapping (Kardinalität 1..*): Mapping von VFB-Port-Elementen (Sender-Receiver-Variablen / Client-Server-Operationen) auf System-Signale bzw. I-Signals und Signal Groups (SenderReceiverToSignalMapping, ClientServerToSignalMapping).
  • Ausgangs-Artefakt («output»):
  • System Description Root Element (Kardinalität 1): Vollständig referenziertes Metamodell-Element System im ARXML-Dokumentenbaum (definiert u. a. rootSoftwareComposition, fibexElementRef, systemMapping).

3. Dynamisches Verhalten & Sequenzablauf

  1. Artefakt-Bereitstellung (Preconditions):
  • Die logische Funktionsarchitektur (VFB Composition) sowie die E/E-Infrastruktur (Topology) müssen als abgeschlossene Entwurfsschritte vorliegen.
  • Sämtliche Zuordnungsartefakte (Mapping of Software Components to ECUs, Data Mapping) und Restriktionen (Signal Path Constraints, Software Component Mapping Constraints) werden aggregiert.
  1. Ausführungsschritt (Set System Root):
  • Der System Engineer erzeugt das MSR/AUTOSAR-Wurzelelement (<SYSTEM>).
  • Zuweisung der Referenzen: Verknüpfung der RootSwCompositionPrototype zur VFB-Topologie sowie Verknüpfung aller System-Cluster zu den FibexElements.
  • Konsolidierung des SystemMapping: Einbettung der SWC-zu-ECU-Mappings und Signal-Mappings unterhalb des System-Knotens.
  1. Validierung & Abbruchbedingungen:
  • Validierung auf Vollständigkeit und Widerspruchsfreiheit gegen die Mapping- und Pfad-Constraints (z. B. unvollständige Signal-Mappings, Mapping verwaister SWCs oder Verletzung von Bus-Bandbreitenlimits).
  • Bei Constraint-Verletzungen: Iterativer Rücksprung in die Mapping- und Topologie-Definition.

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Struktur (Meta-Model):
  • Das Ergebnis manifestiert sich direkt in der ARXML-Struktur als Tag <SYSTEM> unterhalb von <AR-PACKAGE>.
  • Fehlt dieses Wurzelelement oder enthält es inkonsistente Referenzen (z. B. defekte UUID-/ShortName-Pfade zu den EcuInstance- oder SwComponentPrototype-Instanzen), scheitert der nachfolgende ECU Extract Creator.
  • Downstream-Abhängigkeiten (BSW- & Applikations-Entwicklung):
  • System Extract / ECU Extract: Die erzeugte Systembeschreibung ist die normative Pflichteingabe für die Generierung des EcuExtract (AR-EXTRACT).
  • RTE- & Com-Stack-Konfiguration:
  • Aus Data Mapping leiten RTE- und Com-Generatoren die COM-Signal-PDU-Zuordnungen, Inter-ECU-Kommunikation und RTE-Buffer ab.
  • Intra-ECU-Kommunikation wird anhand des SwcToEcuMapping identifiziert (Direktaufrufe/Shared Memory statt COM-Stack).
  • Toolchain-Einschränkungen:
  • Kardinalität von Data Mapping (1..*) verlangt von System-Authoring-Tools (DBC-/ARXML-Importeuren) die Unterstützung partieller/inkrementeller Mappings über mehrere Datenquellen hinweg, die erst im System Root final aufgelöst werden.
