1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Wire-Format- / Serialisierungslayout (PDU-Payload-Struktur auf Byte-Ebene).
  • Technischer Zweck: Spezifikation der On-Wire-Repräsentation eines eindimensionalen Arrays fester Elementanzahl (Static Array [n]) gemäß [PRS_SOMEIP_00099].
  • Architektur-Einordnung:
    • Verortung in der Kommunikationsschicht (SOME/IP-Protokoll, Service-Oriented Architecture).
    • Classic AUTOSAR (CP): Definiert die Serialisierungslogik des SomeIpXf (SOME/IP Transformer) bzw. SomeIpTp unterhalb des RTE-Signal-/Parameter-Routings.
    • Adaptive AUTOSAR (AP): Definiert das On-Wire-Layout der Kommunikations-Middleware (ara::com SOME/IP-Binding) für Payload-Daten über UDP/TCP-Sockets.

2. Komponenten, Entitäten & Schnittstellen

  • Static Array [n]: Repräsentiert einen sequenziellen, homogenen Datentyp fixer Kardinalität n ≥ 1 (ImplementationDataType mit Kategorie ARRAY bzw. std::array<T, n>).
  • LengthField (optional):
    • Optionales Längenfeld mit konfigurierbarer Breite (0, 8, 16 oder 32 Bit; definiert via ARXML-Transformationsbeschreibung SomeIpTransformationDescription.lengthFieldSize).
    • Kodiert die Gesamtlänge des nachfolgenden Payloads in Bytes: Wert = n · e.
  • Element_1 bis Element_n:
    • Homogene Nutzdatenelemente eines identischen Datentyps mit jeweils fixer Größe e Bytes (element size e).
  • Kardinalitäten & Größenmetriken:
    • Anzahl der Elemente: statisch n (Compile-Zeit-Invariant).
    • Gesamte Nutzdatenlänge: n · e.
    • Gesamte Wire-Größe: sizeof(LengthField) + (n · e) (bzw. n · e falls lengthFieldSize == 0).
    • Die Elemente werden direkt aneinandergereiht (kein inter-elementares Alignment-Padding auf SOME/IP-Ebene, sofern nicht explizit im Typenmodell definiert).

3. Dynamisches Verhalten & Sequenzablauf

  • Serialisierung (TX-Pfad):
    1. Der Transformer ermittelt die statische Nutzdatenlänge n · e.
    2. Falls lengthFieldSize > 0: Serialisierung des Längenfeldes mit Wert n · e in der konfigurierten Byte-Order (Default: Big-Endian / Network Byte Order).
    3. Sequenzielle Serialisierung der Elemente Element_1 … Element_n unmittelbar anschließend.
  • Deserialisierung & Validierung (RX-Pfad):
    1. Falls ein Längenfeld konfiguriert ist, liest der Deserializer das Feld und prüft: $$\text{LengthField} \stackrel{!}{=} n \cdot e$$
    2. Plausibilisierung gegen die verbleibende PDU-Restlänge.
  • Fehlerpfade & Abbruchbedingungen:
    • Weicht der Wert des Längenfelds von n · e ab oder ist die PDU kürzer als LengthField + n · e, bricht die Deserialisierung ab.
    • Fehlerreaktion: SOME/IP-ReturnCode 0x07 (MALFORMED_MESSAGE) bzw. Rückgabe von E_NOT_OK / Transformer-Fehler an die RTE / ara::com.
    • Optionales Logging über DET (Development Error Tracer) in CP.

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Konfiguration:
    • Parameter lengthFieldSize: Bei fixed-length Arrays kann das Längenfeld zur Overhead-Reduktion entfallen (lengthFieldSize = 0). Eine Abweichung zwischen Sender und Empfänger führt zwangsläufig zu Framing-/Parsing-Fehlern.
    • Konsistente Endianness-Definition (SomeIpTransformationDescription.byteOrder) für Längenfeld und Basiselemente sicherstellen.
  • Speicherallokation & Determinismus:
    • Da die Gesamtgröße LengthField + n · e a priori zur Compile-Zeit fixiert ist, kann im Embedded-Treiber/Stack statischer Pufferplatz alloziert werden (keine dynamische Heap-Nutzung, ASIL/ISO 26262-konform).
  • Multi-dimensionale Arrays ([PRS_SOMEIP_00101]):
    • Für mehrdimensionale statische Arrays gilt Row-Major-Order (C/C++-Standard-Layout). Jede Dimension kann bei entsprechender ARXML-Parametrierung rekursiv ein eigenes Längenfeld aufweisen.
