1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess-/Aktivitätsdiagramm nach dem Software Process Engineering Metamodel (SPEM 2.0 / AUTOSAR Methodology Activity & Work Product Flow).
  • Funktionale Einordnung: Verortet in der AUTOSAR-Entwicklungsmethodik (AUTOSAR_TR_Methodology, R4.0.3) innerhalb des Teilprozesses Component Development. Es definiert den Build-Schritt zur Übersetzung des C-Quellcodes einer atomaren Software-Komponente (Atomic Software Component, SW-C) in ein relocatable Objektmodul vor der ECU-Integration.
  • Architektur-Kontext: Entkopplung der Komponenten-Implementierung von der Ziel-ECU. Das Diagramm modelliert das Einbinden von generierten Schnittstellenheadern (Contract Phase oder Generation Phase), standardisierten Plattform-Definitionen und optionalen Funktionswrappern gegen den Compiler.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Werkzeuge
  • Software Component Developer (Rolle): Führt die Aktivität aus («performs»). Verantwortlich für Quellcode, Runnable-Logik und Einhaltung der RTE-Verträge.
  • Compiler (Werkzeug / Tool): Zielplattform- oder Host-spezifischer C-Compiler, eingebunden via «used tool».
Aktivität
  • Compile Atomic Software Component (Zentrale SPEM-Task/Aktivität): Kompilierungsschritt der SW-C.
Ausgangsartefakt («output»)
  • Atomic Software Component Object Code [Kardinalität 1]: Generierte Objektdatei (.o / .obj), die später vom Linker im Schritt Build ECU Executable mit der BSW und dem RTE-Core zusammengebunden wird.
Eingangsartefakte («input»)
  • Atomic Software Component Source Code [Kardinalität 1]: Handgeschriebener oder modellbasiert generierter C-Code (<swc>.c), der die Runnable-Entities implementiert.
  • Application Header File [Kardinalität 1]: Komponentenspezifischer Application Header (Rte_<swc>.h). Deklariert die typsicheren RTE-APIs (Rte_Read_*, Rte_Write_*, Rte_Call_*, Rte_IRead_*, Port-bezogene Return-Codes).
  • Software Component Data Types Header [Kardinalität 1]: Typdefinitions-Header (Rte_Type.h). Enthält die Definitionen der Implementation Data Types (IDTs), Mode-Declaration-Groups und Limits.
  • Standard Header Files [Kardinalität 1]: AUTOSAR-Standardbasisheader (Std_Types.h, Platform_Types.h, Compiler.h).
  • Component RTE Prebuild Configuration Header [Kardinalität 0..1]: Generierter Header für Vorkompilierungs-Konfigurationen der RTE auf Komponentenebene (z. B. Makros zur Deaktivierung ungenutzter API-Pfade, unverbundener Ports oder statische Kalibrier-Parameter im Single-Component-Scope).
  • E2E Protection Wrapper Header File [Kardinalität 0..1]: Schnittstellendefinition für sicherheitsrelevante Ports gem. ISO 26262. Kapselt Prüfsummen-, Alive-Counter- und Datumsvalidierungs-Routinen der E2E-Bibliothek gegenüber dem SW-C-Code.
  • Library Header Files [Kardinalität 0..*]: Schnittstellen zu statischen Hilfs- und Mathematik-Bibliotheken (z. B. BF-X, IFL, MFX) oder applikationsspezifischen C-Bibliotheken.
  • Unbeschriftetes Dokumenten-Artefakt [Kardinalität 0..1]: Spezifikations-Artefakt in Figure 3.75 (fehlende Beschriftung im Original-Vector). Repräsentiert im AUTOSAR-Methodenkontext typischerweise den Memory-Mapping-Header (<swc>_MemMap.h) zur Compiler-gesteuerten Sektionsallokation oder Rapid-Prototyping-/Hook-Header.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein methodisches Artefakt-Flussdiagramm handelt, bildet es die Abhängigkeiten der Übersetzungskette ab:

  1. Header-Generierungsphase (Voraussetzung):
    • Contract Phase: Aus dem SWC-ARXML (SoftwareComponentDescription) erzeugt der RTE-Generator Rte_Type.h und den Vertragskopf Rte_<swc>.h.
    • Alternativ Generation Phase: Vollständige Generierung nach System Configuration und ECU Extract.
  2. Kompilierungsdurchlauf (Synchron):
    • Der Entwickler triggert den Aufruf des Compilers über Make/CMake/Build-Environment.
    • Include-Kaskade im Präprozessor: $$\text{Source } (<\!swc\!>.c) \longrightarrow \text{Includes: } Rte\_<\!swc\!>.h \longrightarrow Rte\_Type.h \longrightarrow Std\_Types.h \longrightarrow Platform\_Types.h + Compiler.h$$ Optionale Inklusion von E2E-Headern und Prebuild-Konfigurationen je nach Port-Konfiguration.
  3. Symbolbindung & Syntaxprüfung:
    • Der Compiler prüft Funktionsprototypen gegen die deklarierten RTE-APIs.
    • Fehlende Header führen zum harten Abbruch (Exit-Code ≠ 0).
  4. Artefakt-Erzeugung:
    • Bei fehlerfreier Syntax und Typkompatibilität wird Atomic Software Component Object Code emittiert.

4. Normative Relevanz & Entwickler-Hinweise

  • **Kompilierbarkeit in der Contract Phase (OEM/Tier-1-Schnittstelle):**
    • SW-C-Code muss gegen die Rte_<swc>.h der Contract Phase ohne Kenntnis der tatsächlichen ECU-Konfiguration und ohne Vorhandensein des BSW-Stacks fehlerfrei kompilieren.
    • Entwickler dürfen keine direkten BSW-Header (wie Can.h, Det.h, Os.h) inkludieren. Jede Interaktion mit der Basissoftware muss über Service-Ports und die RTE laufen.
  • Compiler-Abstraktion gem. AUTOSAR Compiler.h:
    • Variablen-, Zeiger- und Funktionsdefinitionen im SW-C Source Code müssen zwingend den Compiler-Abstraktionsmakros folgen (FUNC(...), P2VAR(...), P2CONST(...), VAR(...), CONST(...)), um Cross-Platform-Portabilität zwischen unterschiedlichen Toolchains (z. B. Tasking, HighTec, Green Hills) zu sichern.
  • Speicher-Mapping-Disziplin (MemMap.h):
    • Jedes Code- und Daten-Segment muss über die standardisierten Präprozessor-Abschnitte eingerahmt sein: 
      #define <SWC>_START_SEC_CODE
#include "<SWC>_MemMap.h"
FUNC(void, <SWC>_CODE) Runnable_Entity(void) { ... }
#define <SWC>_STOP_SEC_CODE
#include "<SWC>_MemMap.h"
  • E2E-Wrapper-Besonderheit:
    • Wird E2E-Schutz über Wrapper implementiert (im Gegensatz zur E2E-Integration direkt im RTE-Transform-Layer ab 4.x), muss die SW-C gegen die generierte Wrapper-API kompilieren, welche serialisierte Datenblöcke vor der Übergabe an Rte_Write manipuliert/überprüft.
  • Prebuild-Konfigurations-Einschränkungen:
    • Der Component RTE Prebuild Configuration Header bindet compile-time Schalter ein. Eine Änderung an Parametern dieses Headers erfordert zwingend das Re-Kompilieren der SW-C (keine Post-Build-Variabilität für diese Macros).
