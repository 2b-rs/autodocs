1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Sequenzdiagramm (Interaktionsdiagramm) mit asynchronem Ausführungs- und Pufferungsverhalten.
  • Architektur-Kontext: AUTOSAR Foundation (AUTOSAR_FO_PRS_VDP – Protocol Requirements Specification for Vehicle Data Provider).
  • Funktionale Einordnung: Spezifikation des Zusammenspiels zwischen dem fahrzeuginternen Datenbereitstellungsdienst (VDP-CM Remote) und der Datenerfassungslogik (DCA Remote) auf einem AUTOSAR-Classic-Platform-Mikrocontroller ($\mu\text{C}$). Das Diagramm illustriert eines von zwei normativ zulässigen Ausführungsszenarien für zeitgleiche bzw. kombinierte Sampling- und Übertragungs-Trigger (TX_TRIG = 1): Die asynchrone Abtastung (sampling) der Zielressource wird vor dem Auslesen des Sendepuffers und dem Versenden der Datennachricht abgeschlossen.

2. Komponenten, Entitäten & Schnittstellen

  • Externer Master / VDP Client (außerhalb der $\mu\text{C}$-Boundary):
    • Initiator von Konfigurations- und Trigger-Telegrammen über den VDP-Protokollkanal (z. B. Ethernet/SOME/IP oder CAN-FD).
    • Empfänger von Protokoll-Acknowledge (ACK) und Nutzdaten (data message).
  • VDP-CM Remote (Vehicle Data Provider – Configuration Manager Remote):
    • Protokoll-Endpunkt auf dem Classic-Platform-Knoten.
    • Verwaltet Slot-Konfigurationen, vermittelt Trigger an DCA-Instanzen, puffert Messwerte und steuert die Netznachrichten-Serialisierung.
    • Zustandsführung via internal triggered flag für anstehende Übertragungsaufgaben.
  • DCA Remote (DCA_REM_ID = 1):
    • Lokale Instanz der Data Collection Application auf dem $\mu\text{C}$.
    • Verwaltet Messzeitpläne für logische Slots (VDP_SLOT_ID = 1) und führt die Hardware-/Signal-Abtastung durch.
    • Zustandsführung via internal triggered flag für anstehende Sampling-Jobs.
  • Data resource:
    • Datenquelle auf dem Steuergerät (z. B. RTE-Signalpuffer, BSW-Statusvariable, Port-Schnittstelle oder Sensor-Treiberregister).
  • Konfigurations- und Kontrollparameter:
    • DCA_REM_ID = 1: Adressiert die Zielinstanz der Remote-DCA.
    • VDP_SLOT_ID = 1: Identifiziert den logischen Sampling-/Streaming-Kanal.
    • SCYCLIC = 0: Zyklische Abtastung deaktiviert.
    • SCHANGE = 0: Wertänderungs-Abtastung (Sampling on change) deaktiviert.
    • INIT_ACT = 0: Slot nach Konfiguration nicht initial aktiv (wartet auf expliziten Trigger).
    • TX_TRIG = 1: Löst das Senden der gepufferten Daten über den Bus aus.

3. Dynamisches Verhalten & Sequenzablauf

  1. Dynamische Konfiguration (Dynamic configuration request):
    • Externer Client sendet Konfigurations-PDU mit Parametern (DCA_REM_ID=1, VDP_SLOT_ID=1, SCYCLIC=0, SCHANGE=0, INIT_ACT=0) an VDP-CM Remote.
    • VDP-CM Remote delegiert Konfiguration via synchronem/internem Aufruf hand over sampling configuration an DCA Remote.
    • DCA Remote quittiert; VDP-CM Remote sendet ACK an den Client.
  2. Kombinierter Trigger-Empfang (Trigger request):
    • Client sendet Trigger (TX_TRIG = 1, VDP_SLOT_ID = 1).
    • VDP-CM Remote fordert die Abtastung an (trigger sampling of VDP slot ID = 1).
    • DCA Remote setzt sein internal triggered flag und quittiert an VDP-CM Remote.
    • VDP-CM Remote setzt sein eigenes internal triggered flag für die anstehende Übertragung.
    • VDP-CM Remote sendet ACK an den Client (Entkopplung: Empfang quittiert, Verarbeitung asynchron).
  3. Sampling-Ausführung (Prioritär vor Transmission):
    • DCA Remote liest die Datenquelle aus (retrieve current value von Data resource).
    • DCA Remote löscht sein internal triggered flag (remove internal triggered flag).
    • DCA Remote übergibt den Messwert an den Puffer des Kommunikationsmanagers (add data point sample to buffer).
  4. Transmission-Ausführung:
    • VDP-CM Remote verarbeitet den Übertragungsauftrag (transmit data message as currently buffered).
    • VDP-CM Remote löscht sein Übertragungsflag (remove internal triggered flag).
    • Datennachricht (data message) wird auf den Bus emittiert.
    • Kritischer Zustand (Annotiertes Callout): Da das Sampling vor dem Sendevorgang abgeschlossen wurde, enthält die übertragene data message bereits den im aktuellen Trigger-Zyklus frisch erfassten Messwert (kein Phasenversatz/Latenz von N-1).

4. Normative Relevanz & Entwickler-Hinweise

  • Nicht-Determinismus im VDP-Protokollvertrag: Die Spezifikation erlaubt zwei Sequenzen (Figure 6.24 vs. alternative Ausführung). Abhängig von Task-Prioritäten, OS-Scheduling und BSW-MainFunction-Zyklen kann die Übertragung vor oder nach dem Sampling erfolgen. Entwickler dürfen sich auf Empfängerseite nicht darauf verlassen, ob ein kombinierter Trigger sofort den aktuellen oder noch den vorherigen Messwert liefert.
  • Puffer- und Synchronisations-Design:
    • add data point sample to buffer erfordert Reentrancy-Schutz bzw. atomare Semaphore zwischen dem DCA-Abtast-Task (z. B. schnelles Zyklus-Event oder ISR/Timer) und dem VDP-CM-Sende-Task (Com/PduR-Kontext).
    • Der Puffer muss für den Fall ausgelegt sein, dass bei TX_TRIG = 1 keine neuen Daten vorliegen (Übertragung von Alt-Daten oder Markierung als "kein neuer Abtastwert vorhanden").
  • Flag-Handling (internal triggered flag): Die Flags dienen der Entkopplung der Bus-Quittierung (ACK) von der asynchronen Ausführung. Treffen neue Trigger ein, während ein Flag noch aktiv ist, muss die Stack-Implementierung gemäß Spezifikation Überlauf- bzw. Verwerfungsstrategien (Overrun/Discard) vorsehen.
