1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt des AUTOSAR System Template (AUTOSAR_TPS_SystemTemplate, Release R4.3.1), Package TransportProtocols: NmUdpConfiguration.
  • Funktionale Einordnung: Definiert die formalen System-Description-Strukturen (FIBEX-Ebene) zur Konfiguration des UDP Network Management (UdpNm). Es beschreibt die Spezialisierung der generischen, busunabhängigen NM-Klassen (NmCluster, NmEcu, NmNode, NmClusterCoupling) auf UDP/IP-basierte Ethernet-Netzwerke sowie deren Verknüpfung zur Kommunikationsmatrix (CommunicationCluster, EthernetPhysicalChannel, NmPdu, ISignalToIPduMapping).

3. Dynamisches Verhalten & Sequenzablauf

Das Metamodell parametriert das dynamische Verhalten der UdpNm-Zustandsmaschine (SWS UdpNm):

```

[Bus-Sleep Mode]

│ Network Request (Active Wakeup) / Rx NM-PDU (Passive Wakeup)

▼

[Repeat Message State]

│ - Sende bis zu nmImmediateNmTransmissions PDUs im Zyklus nmImmediateNmCycleTime (Fast TX)

│ - Normaler Zyklus: nmMsgCycleTime mit Phasenversatz nmMsgCycleOffset

│ - Ablauf Timer nmRepeatMessageTime

▼

[Normal Operation State] ◄───────────────────────────┐

│ │ Network Request

│ Network Released (Nm_PassiveStartUp etc.) │

▼ │

[Ready Sleep State] ──────────────────────────────────┘

│ Ablauf Timer nmNetworkTimeout (Keine Rx/Tx-Aktivität)

▼

[Prepare Bus-Sleep Mode]

│ Ablauf Timer nmWaitBusSleepTime (Verhinderung vorzeitigen Schlafens)

│ Sonderpfad: Neuer Request -> Bei nmImmediateRestartEnabled == TRUE sofortiges Senden

▼

[Bus-Sleep Mode]

```

  • PDU-Serialisierung & Remote-Erkennung:
  • Byte-Positionen nmCbvPosition (Control Bit Vector, z. B. PNC-Bits, Active Sleep Bit) und nmNidPosition (Node ID) steuern die dynamische Payload-Erzeugung/-Auswertung im UDP-Paket.
  • nmRemoteSleepIndicationTime: Schwellwert für den Übergang in den Remote Sleep Status, wenn im Cluster keine Aktivität anderer Knoten mehr detektiert wird.
  • Koordination:
  • Bei Multicluster-Gateways synchronisiert NmCoordinator über nmCoordCluster und nmGlobalCoordinatorTime das koordinierte Herunterfahren gekoppelter Busse (UdpNmClusterCoupling).

4. Normative Relevanz & Entwickler-Hinweise

  • ECUC-Mapping (System Description zu BSW):
  • UdpNmCluster mappt direkt auf den BSW-Container UdpNmCluster / UdpNmGlobalConfig.
  • UdpNmNode und NmPdu parametrieren die Zuordnung von SoAdRxPduId / SoAdTxPduId im Socket Adapter (SoAd) sowie Socket-Verbindungen (UDP Multicast-IP / Port-Paare).
  • Variantenbildung («atpVariation»):
  • NmCluster, NmClusterCoupling und CommunicationCluster unterstützen postBuild-Bindungszeit: Erlaubt PB-Selektion von Clustern/VLANs und Routing-Topologien.
  • NmEcu ist strikt auf preCompileTime limitiert: ECU-Basiskonfigurationen (Buffer, Callbacks, Indication-APIs) sind hardcodiert und können zur Laufzeit nicht strukturell variiert werden.
  • Einschränkungen & Stolperfallen für Embedded-Entwickler:
  • Burst-Vermeidung: nmMsgCycleOffset muss netzwerkweit koordiniert vergeben werden, um gleichzeitige UDP-Transfers mehrerer Steuergeräte nach dem synchronen Aufwachen zu entzerren.
  • Tx-Monitoring: nmMessageTimeoutTime überwacht die asynchrone Bestätigung via SoAd_IfTransmit() bzw. UdpNm_TxConfirmation(). Ein zu knapp gewählter Wert führt bei Ethernet-Bufferengpässen fälschlich zu UDPNM_E_NET_START_IND / Fehlereinträgen.
  • VLAN-Bindung: Fehlt die vlan-Referenz zu EthernetPhysicalChannel, kann der Stack die NM-Frames keinem konkreten virtuellen Netzwerk zuordnen, was zu Verwerfungen im TCPIP/EthIf führt.
