1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptionelles Datenfluss- und Filterschichten-Modell (Deep Packet Inspection & Rule Execution Pipeline).
  • Technischer Zweck: Spezifiziert die mehrstufige Struktur von Firewall-Filterregeln über den gesamten Protokollstack (OSI-Schichten 2 bis 7 inklusive applikationsspezifischer Nutzlasten) innerhalb der AUTOSAR Foundation (AUTOSAR_FO_RS_Firewall).
  • Funktionale Einordnung: Dient als normative Vorgabe für Paketfilter-Engines in Classic und Adaptive Plattformen zur statischen und zustandsbehafteten Inspektion (Stateful Inspection), DoS-Abwehr sowie zur sicherheitsrelevanten Ereignismeldung an den Intrusion Detection System Manager (IdsM).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm differenziert zwei beispielhafte Filterketten (Service-orientierte Kommunikation vs. Netzwerk-Diagnose) und deren Konfigurationsattribute:

Protokollschichten und Filterkriterien
  • Layer 2 (Ethernet / Data Link):
    • Parameter: Source MAC, Destination MAC, EtherType.
  • Layer 3 (Network / IPv4):
    • Parameter: Source IP Address, Destination IP Address, Version, Flags, Protocol.
  • Layer 4 (Transport / TCP bzw. ICMP):
    • TCP: Zustandserkennung via Flags (State Management based on TCP flags (as per RFC 793)).
    • ICMP: Steuer- und Diagnosefelder (Type, Code, Checksum).
  • Layer 7 / Middleware (SOME/IP):
    • Protokollspezifische Header-Felder: Service ID, Method ID, Client ID.
  • Generic Inspection (Payload-Parsing):
    • Vektorbasierte Byte-Offset-Prüfung: [(Offset, Data), (Offset, Data), ...]. Erlaubt deterministisches Pattern-Matching an definierten Positionen innerhalb der Nutzlast.
Regelaktionen & Parameter (Action)

Jede Filterregel aggregiert die Kriterien zu einer atomaren Entscheidung:

  • Allow/Block: Dispositive Aktion (Paketweiterleitung oder Paketverwerfung / Drop).
  • Alert: Generierung eines Security Events (SEv) an den IdsM.
  • Rate limit: Bandbreiten- und Frequenzbegrenzung zur Erkennung und Dämpfung von Denial-of-Service-Angriffen.
  • Vehicle state: Kontextuelle Aktivierungsbedingung; bindet die Gültigkeit der Regel an definierte Fahrzeugmodi (z. B. Normalfahrt, Werkstatt-/Diagnosemodus, Update/Flashing).

3. Dynamisches Verhalten & Sequenzablauf

  1. Paket-Ingress & Header-Extraktion: Einlaufendes Frame wird im Kommunikationsstack (z. B. EthIf, TCP/IP-Stack oder OS-Netzwerk-Subsystem) erfasst; Header-Felder von L2 bis L7 werden dekapselfrei oder per Streaming-Parser bereitgestellt.
  2. Sequenzielles Matching (First-Match-Prinzip):
    • Die Firewall evaluiert eine geordnete Liste konfigurierter Filterregeln streng sequenziell.
    • Alle definierten Kriterien einer Regel (Layer 2 bis Layer 7 + Payload-Offsets) sind logisch UND-verknüpft.
  3. Zustands- & Kontextprüfung:
    • Vehicle State Gate: Befindet sich das Fahrzeug nicht im referenzierten Zustand, wird die Regel übersprungen.
    • TCP State Check: Abgleich gegen den internen TCP-Verbindungszustandsautomaten (SYN, ESTABLISHED, FIN/RST gemäß RFC 793).
  4. Regeldurchsetzung (Enforcement):
    • Bei erstem vollständigen Match wird die konfigurierte Action sofort ausgeführt; die Auswertung weiterer Regeln bricht ab.
    • Rate Limiting Check: Bei Überschreiten konfigurierter Token-Bucket-Schwellwerte wird die Aktion auf Block forciert.
    • IdsM-Meldung: Löst bei gesetztem Alert-Flag synchron oder entkoppelt einen SEv aus.
  5. Default-Behandlung (No-Match):
    • Greift keine der definierten Regeln, wird die globale Default Action (Allow oder Block) angewendet.
    • Optional wird ein separater No-Match-SEv an den IdsM abgesetzt.

4. Normative Relevanz & Entwickler-Hinweise

  • Stack-Integration:
    • Classic Platform: Platzierung der Filterlogik primär in/an EthIf, TcpIp oder dedizierten Firewall-BSW-Modulen. Die Auswertung tiefer Layer (SOME/IP, Generic Offset) erfordert Zero-Copy-Pufferzugriff (z. B. auf PduInfoType), um Stack-Laufzeiten nicht zu degradieren.
    • Adaptive Platform: Typische Realisierung im Linux-Kernelspace (z. B. über nftables / eBPF) für L2–L4 sowie im Userspace (ara::com / Daemon) für SOME/IP- und Payload-Inspektion.
  • Worst-Case Execution Time (WCET):
    • Die Auswertung komplexer Generic inspection-Tupelarrays erzeugt linearen Rechenzeitaufwand proportional zur Regeltiefe. In harten Echtzeitsystemen müssen Payload-Prüfungen auf minimale Offsets begrenzt und deterministisch konfiguriert werden.
  • Speicherbedarf für Stateful Inspection:
    • Das TCP-Zustandsmanagement erfordert dynamische oder statisch vorallozierte Tabellen zur Verbindungsverfolgung. Entwickler müssen Vorkehrungen gegen Tabellenerschöpfung (SYN-Flooding) treffen.
  • IdsM-Überlastschutz:
    • Die Kopplung von Alert mit hochfrequenten Block-Aktionen kann den IdsM-Puffer überfluten. Ein nachgeschaltetes Event-Throttling bzw. Event-Aggregation im IdsM/Firewall-Interface ist zwingend auszulegen.
  • Modus-Umschaltung:
    • Die Abhängigkeit von Vehicle state verlangt eine echtzeitfähige Benachrichtigungsschnittstelle (z. B. Anbindung an den BswM bzw. Adaptive State Management), um Regelsätze bei Statuswechseln ohne Re-Initialisierungs-Latenzen umzuschalten.
