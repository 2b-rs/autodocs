1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Komponentendiagramm / Informationsflussdiagramm (class HM_OverallFlow) zur Black-Box-Funktions- und Schnittstellenübersicht.
  • Architektur-Kontext: AUTOSAR Foundation (AUTOSAR_FO_ASWS_HealthMonitoring), plattformübergreifend gültig für Classic Platform (WdgM/BswM) und Adaptive Platform (PHM / Execution Management). Definiert den normativen Grenzbereich (Scope) einer Health-Monitoring-Instanz zur Laufzeitüberwachung bezüglich Kontrollfluss, Zeitschranken und Systemzustand.

2. Komponenten, Entitäten & Schnittstellen

Dargestellt sind vier Systeminstanzen (Komponenten) und vier gerichtete Informationsflüsse mit Stereotyp «flow»:

  • :Supervised Entity (Quelle für Monitoring-Daten):
  • Repräsentiert die überwachte Software-Einheit (z. B. SW-C Runnable, BSW-Modul, Adaptive Process/Thread).
  • Schnittstellen (Eingang nach :Health Monitoring):
  • Checkpoint ID («flow»): Kontrollfluss- und Ereignismeldung zur logischen Sequenzüberwachung (Logical Supervision), Deadline-Überwachung (Deadline Supervision) und Lebendigkeitsprüfung (Alive Supervision).
  • Health Status («flow»): Zustandsindikation oder Health-Kanal-Meldung über den internen System- bzw. Funktionszustand der Entity.
  • :Health Monitoring (Zentrale Verarbeitungs- und Bewertungsinstanz):
  • Evaluiert eingehende Checkpoints und Health-Zustände gegen statisch konfigurierte temporale, logische und qualitative Constraints.
  • Kann kaskadiert als Daisy Chain (z. B. Core-lokal, OS-Level, System-Level) instanziiert werden.
  • :Error handling (Fehlerreaktionssenke):
  • Zielkomponente für koordinierte Fehlerreaktionen (z. B. BswM, Dem, Det im Classic-Stack bzw. Execution Management / Recovery Action im Adaptive-Stack).
  • Schnittstelle (vom Monitor getriggert):
  • Error handler ID to be triggered («flow»): Übermittlung eines spezifischen Aktions- oder Fehlerbezeichners zur Ausführung softwarebasierter Wiederanlauf-, Degradations- oder Notfallpfade.
  • :Watchdog (Hardware-/Safety-Rückfallebene):
  • Hardware-Watchdog oder Watchdog-Stack (z. B. WdgIf / Wdg-Treiber bzw. Watchdog-Dienst).
  • Schnittstelle (vom Monitor bedient):
  • Triggering of watchdog («flow»): Zyklisches Servicing / Bedienen des Watchdog-Schalters, solange alle überwachten Bedingungen im Sollbereich liegen.

3. Dynamisches Verhalten & Sequenzablauf

  1. Nominalbetrieb (Überwachungszyklus):
  • Die :Supervised Entity meldet das Erreichen definierter Programmpunkte via Checkpoint ID.
  • Die :Supervised Entity meldet periodisch oder ereignisgesteuert ihren aktuellen Health Status.
  • Das :Health Monitoring prüft Zeitdifferenzen (Min/Max-Deadlines), Alive-Zähler innerhalb eines Überwachungsfensters und gültige Zustandsübergänge (Graphenprüfung).
  • Bei fehlerfreiem Gesamtstatus triggert :Health Monitoring aktiv den :Watchdog (Triggering of watchdog), um einen Timeout-Reset des Prozessors zu verhindern.
  1. Fehlerpfad & Eskalation:
  • Constraint-Verletzung: Verpassen einer Deadline, fehlerhafte Alive-Rate, unzulässiger Sprung im Kontrollflussgraph oder unzulässiger Health Status.
  • Software-Reaktion: :Health Monitoring signalisiert unverzüglich die konfigurierte Error handler ID to be triggered an :Error handling (z. B. Auslösen einer Partition-Restart-Routine, Wechsel in einen Safe State oder Logging via Dem).
  • Hardware-Reaktion: Das zyklische Triggering of watchdog wird gezielt unterdrückt (oder auf falsche Sequenzen gesetzt), sodass nach Ablauf der Watchdog-Toleranzzeit ein Hardware-Reset initiiert wird, falls das Software-Error-Handling fehlschlägt.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Vertrag & Instrumentierung: Applikations- und BSW-Entwickler müssen Checkpoints minimal-invasiv in kritische Codepfade einbetten (CP: WdgM_CheckpointReached(SEID, CPID), AP: ara::phm::SupervisedEntity::ReportCheckpoint).
  • Deterministische Konfiguration: Checkpoint-IDs, erlaubte Transitionsgraphen, Toleranzschwellen (Failed Supervision Reference Cycles) sowie Handler-IDs müssen zur Entwurfszeit im AUTOSAR-Modell (ARXML / Execution Manifest) exakt aufeinander abgestimmt sein.
  • Entkopplung von Recovery und Fail-Safe: Die explizite Trennung zwischen :Error handling (Software-Degradation/-Recovery) und :Watchdog (letzte Instanz gegen Hänger/Glitches) erzwingt ein zweistufiges Safety-Konzept nach ISO 26262.
  • Kaskadierung (Daisy Chain): Bei Multi-Core- oder Multi-Partition-Systemen sendet eine untergeordnete Monitoring-Instanz aggregierte Health-Ergebnisse und Checkpoint-Kontextdaten an die übergeordnete Instanz weiter; das endgültige Watchdog-Triggering erfolgt typischerweise erst auf der höchsten Aggregationsebene.

Specification of Health Monitoring AUTOSAR FO R24-11 6 Functional specification 6.1 Functional Overview This section presents black-box functional overview of the Health Monitoring. It does not define any requirements nor details on the functionality. 6.1.1 Functional Interfaces The Health Monitoring supervises the execution of a configurable number of Supervised Entitys and it also supervises their Health Status. When it detects a violation of the configured temporal and/or logical constraints on program execution or a violation of the configured health constraints, it triggers the appropriate error handlers. Health Monitoring controls also the Watchdogs correspondingly, see Figure 6.1. Figure 6.1: Scope of Health Monitoring The Health Monitoring function can be split as a daisy chain. Each Health Monitoring instance has the same interface to Supervised Entitys, Error handling and Watchdog. In addition, the interface between the instances of Health Monitoring is standardized as well - it carries the results of Health Monitoring as well as "raw data" (Checkpoint IDs, Health Status together with necessary context information). Each instance adds some context-specific data to Checkpoints (e.g. process/task id).
