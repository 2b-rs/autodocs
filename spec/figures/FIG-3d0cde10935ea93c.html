1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm zur Darstellung des AUTOSAR ECU Configuration (ECUC) Parameter-Metamodells gemäß BSW-Modellierungsrichtlinien.
  • Architektur-Kontext: AUTOSAR Classic Platform (CP), Modul CanNm (CAN Network Management, Communication Services / System Services Layer).
  • Funktionaler Zweck: Festlegung der statischen Konfigurationsstruktur (CanNmChannelConfig, Teil 2) zur Parametrierung einzelner CAN-Netzwerkmanagement-Kanäle. Kapselt PDU-Referenzen, ComM-Kopplung, Node-Identifikation, Teilnetzwerk-Steuerung (PNC) und spezifische State-Machine-Timing-Parameter.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Container-Definitionen

  • CanNmChannelConfig (EcucParamConfContainerDef):
  • Kardinalität: 1..* (mindestens ein Kanal muss pro CanNm-Instanz konfiguriert werden; Multichannel-fähig).
  • CanNmTxPdu (EcucParamConfContainerDef):
  • Kardinalität: 0..1 (optional; ermöglicht reine Rx-/Passive-NM-Knoten ohne eigene Sende-PDU).
  • Enthält die Referenz CanNmTxPduRef (EcucReferenceDef) mit Multiplizität 1..1 (Referenziert die globale EcuC-PDU für NM-Tx).
  • CanNmRxPdu (EcucParamConfContainerDef):
  • Kardinalität: 1..* (mindestens eine Rx-PDU erforderlich; unterstützt mehrere NM-Rx-PDUs pro Kanal).
  • Enthält die Referenz CanNmRxPduRef (EcucReferenceDef) mit Multiplizität 1..1.
  • ComMChannel (EcucParamConfContainerDef aus Paket ComM):
  • Externe Entität des Communication Managers mit Multiplizität 1..256.

#### Assoziationen & Referenzen

  • CanNmComMNetworkHandleRef (EcucReferenceDef):
  • Kanalbezogene Referenzierung (+reference / +destination) auf den korrespondierenden ComMChannel.
  • Eigenschaft: requiresSymbolicNameValue = true (erzwingt die Verwendung eines symbolischen Namens / Channel-Handles zur konsistenten kanalübergreifenden Adressierung via NetworkHandleType).

3. Dynamisches Verhalten & Sequenzablauf (Einfluss auf die State Machine)

Obgleich es sich um ein statisches Konfigurationsmodell handelt, determinieren die Parameter direkt die Transitionen und Timer der CanNm-Zustandsmaschine:

  1. Immediate Transmission Phase (Netzwerk-Start):
  • Trigger: Aufruf von CanNm_NetworkRequest().
  • Ist CanNmImmediateNmTransmissions > 0 und CanNmImmediateNmCycleTime konfiguriert, wird die State-Machine sofort getriggert: Es werden $n$ Telegramme im Intervall CanNmImmediateNmCycleTime asynchron über die CanIf_Transmit() abgesetzt, bevor in die reguläre NM-Sendesperre bzw. den Normal Operation Zyklus übergegangen wird.
  1. Tx-Timeout-Überwachung:
  • Nach dem Senden einer NM-PDU wird der Timer CanNmMsgTimeoutTime gestartet.
  • Bleibt der Callback CanNm_TxConfirmation() vor Ablauf von CanNmMsgTimeoutTime aus, meldet das Modul je nach Konfiguration einen Fehler an das DEM/DET und triggert Recovery-Mechanismen.
  1. Bus-Sleep Vorbereitung (Prepare Bus-Sleep Mode - PBS):
  • CanNmStayInPbsEnabled == true verhindert den automatischen Übergang in den Bus-Sleep Mode, solange die Applikation oder der ComM den Bus aktiv im Bereitschaftszustand halten muss.
  1. Repeat Message & Node Detection:
  • Das gesetzte Repeat Message Bit im CBV einer empfangenen NM-Rx-PDU löst bei CanNmRepeatMsgIndEnabled == true die Notification Nm_RepeatMessageIndication() an das Interface-Modul aus und zwingt den Kanal zurück in den Zustand Repeat Message State.

4. Normative Relevanz & Entwickler-Hinweise

  • Pre-Compile vs. Link-Time/Post-Build Schalter:
  • Boolean-Parameter wie CanNmNodeIdEnabled, CanNmRepeatMsgIndEnabled und CanNmNodeDetectionEnabled dienen typischerweise als Code-Generatorschalter (#if (CANNM_NODE_ID_ENABLED == STD_ON)), um nicht benötigten Code zur Optimierung von ROM/RAM-Footprint aus der BSW-Kompilierung zu entfernen.
  • ComM-Synchronisation:
  • CanNmComMNetworkHandleRef erzwingt die exakte Kopplung zwischen ComM-Kanal-Index und CanNm-Kanal-Index (NetworkHandleType). Eine Diskrepanz führt zu Fehlleitungen von Netzwerk-Requests oder ungültigen Channel-Lookups in CanNm_MainFunction().
  • PDU-Router & CanIf-Bindung:
  • Da CanNmTxPdu die Multiplizität 0..1 besitzt, muss der BSW-Treiber passive Nodes unterstützen. Fehlt CanNmTxPdu, dürfen im generierten C-Code keine Sende-Timer-Arrays oder Tx-Kontexte für diesen Kanal allokiert werden.
  • Mehrere CanNmRxPdu (1..*) erfordern im CanNm-Rx-Pfad (CanNm_RxIndication) ein PDU-ID-Demultiplexing, falls ein Kanal mehrere PDU-Quellen (z. B. Extended/Standard IDs) empfangen kann.
  • Quantisierung von Float-Parametern:
  • Floating-Point-Werte (CanNmImmediateNmCycleTime, CanNmMsgTimeoutTime, CanNmMsgReducedTime) müssen durch den Konfigurationsgenerator anhand der Zykluszeit von CanNmMainFunctionPeriod in ganzzahlige MainFunction-Ticks (OS-Ticks) umgerechnet werden. Rundungsfehler führen hierbei zu Timing-Jitter auf dem CAN-Bus.
