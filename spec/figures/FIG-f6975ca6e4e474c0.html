1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Binäres Protokoll- und PDU-/Paket-Layout (Bit-/Byte-Feld-Spezifikation im RFC-Stil, 32-Bit-Raster).
  • Architektur-Kontext: AUTOSAR Classic & Adaptive Platform, SOME/IP Service Discovery (Sd / SOME/IP-SD).
  • Funktionaler Zweck: Standardisiertes Serialisierungsformat der IPv4 Multicast Option (Option Type 0x14). Dient innerhalb einer SOME/IP-SD-PDU dem Transport von Multicast-IP-Endpunkten (Zieladresse und L4-Transportport), primär für Eventgroup-Publish/Subscribe-Mechanismen (z. B. in SubscribeEventgroupAck- oder OfferService-Nachrichten zur Ankündigung von Multicast-Event-Streams via UDP).

2. Komponenten, Entitäten & Schnittstellen

Das Layout umfasst exakt 12 Byte (96 Bit), strukturiert in 32-Bit-Worten (Big-Endian / Network Byte Order):

  • Option Header:
    • Length (Bit 0–15, 16 Bit): Fester Wert 0x0009 (9 Byte). Gibt die Byte-Länge der Option ab dem ersten Reserved-Feld (exklusive Length und Type) an.
    • Type (Bit 16–23, 8 Bit): Identifikator der Option; normativ 0x14 für IPv4 Multicast Option.
    • Reserved (Bit 24–31, 8 Bit): Reserviert für zukünftige Protokollerweiterungen; muss Sender-seitig auf 0x00 gesetzt werden.
  • Payload / Adressinformationen (von Length abgedeckt):
    • IPv4-Address (Bit 32–63 / Wort 2, 32 Bit): Multicast-IPv4-Adresse (Klasse D: 224.0.0.0 bis 239.255.255.255).
    • Reserved (Bit 64–71, 8 Bit): Zweites Reserviert-Byte; muss Sender-seitig auf 0x00 gesetzt werden.
    • L4-Proto (Bit 72–79, 8 Bit): IANA-Transportprotokoll-Nummer (standardmäßig 0x11 für UDP, da Multicast über TCP nicht unterstützt wird).
    • Port Number (Bit 80–95, 16 Bit): Ziel-Portnummer (Layer 4) des Multicast-Endpunkts.

3. Dynamisches Verhalten & Sequenzablauf

  • Trigger & Erzeugung:
    • Tritt bei der SD-Antwortphase auf: Ein Server-Knoten bestätigt ein SubscribeEventgroup eines Clients mit einem SubscribeEventgroupAck.
    • Ist für die Eventgroup eine Multicast-Kommunikation konfiguriert, referenziert der entsprechende Entry über Index of 1st options bzw. Index of 2nd options und Number of initial options dieses IPv4-Multicast-Optionsfeld im Option-Array der SD-PDU.
  • Verarbeitung & Routing:
    • Der Client-Stack (SOME/IP-SD) parst die Option, validiert Length == 0x0009 sowie Type == 0x14 und triggert den lokalen TCP/IP-Stack (TcpIp / OS-Socket), der via IGMP dem Multicast-Stream (IPv4-Address + Port Number) beitritt.
  • Fehlerbehandlung:
    • Abweichende Längen (Length != 0x0009) oder ungültige IP-Bereiche führen zum Verwerfen der Option bzw. des zugehörigen Entrys (Fehlermeldung an Det bzw. Logging im Diagnostic-Log-and-Trace-Framework).

4. Normative Relevanz & Entwickler-Hinweise

  • Endianness: Alle Multibyte-Felder (Length, IPv4-Address, Port Number) sind zwingend in Network Byte Order (Big Endian) zu serialisieren und zu deserialisieren (htons/ntohs, htonl/ntohl).
  • Längenberechnung: Die Längenangabe Length deckt gemäß AUTOSAR PRS/SWS-Spezifikation nicht die gesamte Option ab, sondern zählt ab dem ersten Reserved-Byte nach Type: $$\text{Length} = 1\,\text{Byte (Reserved)} + 4\,\text{Byte (IPv4)} + 1\,\text{Byte (Reserved)} + 1\,\text{Byte (Proto)} + 2\,\text{Byte (Port)} = 9\,\text{Byte} = \mathtt{0x0009}$$
  • Konfigurations-Binding:
    • Im AUTOSAR Classic BSW (Sd): Gemappt über SdInstanceConfiguration → SdServerServiceInstance → SdEventGroup → SdMulticastEventGroupRef bzw. Verweis auf einen SoAdSocketConnectionGroup-Endpunkt.
    • Im AUTOSAR Adaptive Core: Konfiguriert über das Service-Instance-Manifest (SomeipServiceInstanceToMachineMapping mit serviceDiscovery Multicast-Zuordnung).
  • Protokollrestriktion: Für L4-Proto ist im Multicast-Kontext normativ nur UDP (0x11) zulässig. Parsing-Code muss Nicht-UDP-Werte als ungültige Konfiguration/PDU abweisen. Reservierte Bytes (0x00) dürfen beim Empfänger die Interpretation nicht blockieren (Robustness-Prinzip), müssen jedoch vom Sender strikt als 0x00 geschrieben werden.
