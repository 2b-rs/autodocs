1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schematisches Wire-Format- und Serialisierungs-Layout (SOME/IP PDU Data Stream Layout / Nested Structural Serialization Mapping).
  • Technischer Zweck & Einordnung: Veranschaulicht in AUTOSAR_FO_PRS_SOMEIPProtocol (Kapitel Serialization of Structures) die selektive Anwendung der Tag-Length-Value (TLV)-Codierung innerhalb komplex verschachtelter Datenstrukturen. Das Diagramm demonstriert das Zusammenspiel von:
    • klassischer positionsbasierter Serialisierung (feste Feldreihenfolge ohne Metadaten-Overhead) auf den oberen Hierarchieebenen (myStruct, c, c3, e) und
    • tag-basierter TLV-Serialisierung auf einer isolierten Substrukturebene (c32), um feldspezifische Erweiterbarkeit, optionale Attribute und Rückwärtskompatibilität ohne globalen Protokoll-Overhead zu ermöglichen.

2. Komponenten, Entitäten & Schnittstellen

  • Hierarchischer Datenstrukturbaum (C/ARXML-Spezifikationsebene):
    • myStruct (Root-Record): Enthält a (uint8), b (uint8), struct c, d (uint8), struct e, f (uint8), g (uint8).
    • struct c (Substruktur): Enthält c1 (uint8), c2 (uint8), struct c3, dynamisches Array c4 (uint8[]), c5 (uint8).
    • struct c3 (Substruktur): Enthält c1 (uint8), struct c32, c33 (uint8).
    • struct c32 (Getaggte TLV-Substruktur):
      • c321 (uint8): Konfiguriert mit Data ID = 2.
      • c322 (uint8[]): Dynamisches Array, konfiguriert mit Data ID = 1.
      • c323 (uint8): Konfiguriert mit Data ID = 0.
    • struct e (Substruktur): Enthält e1 (uint8), e2 (uint8).
  • On-the-Wire PDU Payload (Flacher Big-Endian-Bytestrom):
    • Längenfelder (*_length): Statisch konfigurierte Längenindikatoren für myStruct_length, c_length, c3_length, c32_length, c4_length und e_length.
    • 16-Bit-Tags (Wire Type + Data ID):
      • c321_tag = 0x0002: Wire Type 0 (8-Bit Basisdatentyp, Bits 15..12 = 0000b) + Data ID 2 (Bits 11..0 = 0x002). Unmittelbar gefolgt vom Nutzdatenbyte c321.
      • c322_tag = 0x4001: Wire Type 4 (dynamische Länge, Bits 15..12 = 0100b) + Data ID 1 (Bits 11..0 = 0x001). Gefolgt von c322_length und dem Nutzdaten-Array c322 ….
      • c323_tag = 0x0000: Wire Type 0 (8-Bit Basisdatentyp, Bits 15..12 = 0000b) + Data ID 0 (Bits 11..0 = 0x000). Unmittelbar gefolgt vom Nutzdatenbyte c323.
    • Nicht-getaggte Datenelemente: Werden als reine Rohdaten ohne Tag-Präfix direkt an ihren berechneten Byte-Offsets übertragen (a, b, c1, c2, c31, c33, c5, d, e1, e2, f, g).

3. Dynamisches Verhalten & Sequenzablauf

  • Serialisierungsabfolge (Sender-Pipeline):
    1. Längenfeld-Reservierung: Allokation der konfigurierten Längenfeldbreite (typischerweise 16 oder 32 Bit) für myStruct_length, c_length, c3_length.
    2. Positionsbasiertes Streaming: Schreiben von a, b, c1, c2, c31.
    3. TLV-Strukturserialisierung (c32):
      • Reservierung von c32_length.
      • Codierung von c321 über Tag 0x0002 + 1 Byte Payload.
      • Codierung von c322 über Tag 0x4001 + c322_length + n Bytes Array-Payload.
      • Codierung von c323 über Tag 0x0000 + 1 Byte Payload.
      • Backpatching: Ermittlung der Gesamtlänge von c32 und Eintrag in c32_length.
    4. Fortsetzung regulärer Payload: Serialisierung von c33, Längenfeld + Bytes für Array c4, c5, d, Struktur e (e_length + e1 + e2), f, g.
    5. Top-Level Backpatching: Rekursive Aktualisierung der übergeordneten Längenfelder bis myStruct_length.
  • Deserialisierungsabfolge & Fehlertoleranz (Receiver-Pipeline):
    • Der Empfänger parst äußere Strukturen streng über relative Offsets und konfigurierte Längenfelder.
    • Beim Erreichen von c32_length wechselt der Deserialisierer in den TLV-Parser-Modus.
    • Skip-Logik für unbekannte Tags: Trifft der Deserialisierer auf eine unbekannte Data ID innerhalb von c32, wertet er den 4-Bit-Wire-Type aus:
      • Wire Type 0: Exakt 1 Byte überspringen.
      • Wire Type 4: Folgendes Längenfeld auslesen und die entsprechende Byte-Anzahl überspringen.
    • Nach Ablauf von c32_length Bytes synchronisiert der Parser unmittelbar auf das nächste deterministische Feld c33.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative AUTOSAR-Vorgaben (PRS SOME/IP Protocol):
    • [PRS_SOMEIP_00075]: Serialisierung von Datenstrukturen mit optionalen/getaggten Feldern mittels TLV.
    • [PRS_SOMEIP_00076]: 16-Bit-Tag-Codierung: Bit 15..12 = Wire Type, Bit 11..0 = Data ID (0x000 bis 0xFFF reserviert/gültig).
    • [PRS_SOMEIP_00077]: Wire-Type-Klassifikation:
      • 0: 8-Bit Datentyp
      • 1: 16-Bit Datentyp
      • 2: 32-Bit Datentyp
      • 3: 64-Bit Datentyp
      • 4: Dynamische Länge (Längenfeld folgt dem Tag)
    • [PRS_SOMEIP_00078]: Strukturen, die getaggte Elemente enthalten, müssen zwingend ein eigenes Längenfeld besitzen (lengthFieldSize > 0).
    • [PRS_SOMEIP_00080]: Deserialisierer müssen unbekannte Tags ohne Abbruch der gesamten PDU verwerfen können.
  • Entwickler- & Konfigurations-Hinweise:
    • ARXML-Datenmodellierung: Die Aktivierung des TLV-Mechanismus erfolgt granular pro Strukturebene über die Zuordnung von dataId an den jeweiligen ImplementationDataTypeElement bzw. ApplicationRecordElement. Besitzt ein Element keine dataId, wird es standardmäßig im positionsbasierten Modus serialisiert.
    • Homogenitätsregel: Innerhalb derselben Strukturebene dürfen getaggte und ungetaggte Felder nicht gemischt werden. Das Diagramm belegt die konforme Architektur: Nur die Substruktur c32 ist getaggt; alle direkten Geschwisterelemente auf Ebene c3 (c31, c32, c33) verbleiben ungetaggt.
    • Performance & Bandbreiten-Optimierung: Der gezielte Einsatz von TLV ausschließlich auf hochvolatilen oder erweiterbaren Teilbäumen (c32) spart gegenüber einer vollständigen TLV-Codierung 2 Bytes Tag-Overhead pro unveränderlichem Primitivfeld ein.
