1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU-Configuration-Metamodell (UML-Klassendiagramm / ECUC Parameter Configuration Definition).
  • Technischer Zweck: Definition der XML/ARXML-Konfigurationsstrukturen für den Container ComMNetworkManagement innerhalb eines Kommunikationskanals (ComMChannel) im Communication Manager (ComM, BSW System Service, AUTOSAR Classic R4.0.3).
  • Funktionale Einordnung: Steuert pro Kanal die Anbindung an den AUTOSAR Network Management Stack (Nm / BusNm wie CanNm, LinNm, FrNm), das Verhalten beim Herunterfahren des Busses (NM-Light) sowie die Kopplung an das Partial Networking (PNC).

2. Komponenten, Entitäten & Schnittstellen

Container & Multiplizitäten
  • ComMChannel (EcucParamConfContainerDef, Multiplizität 1..256):
    • Repräsentiert die physikalischen/logischen Kommunikationskanäle der BSW (maximal 256 Kanäle konfigurierbar).
    • Besitzt über die Komposition +subContainer exakt einen Sub-Container für das Netzwerkmanagement.
  • ComMNetworkManagement (EcucParamConfContainerDef, Multiplizität 1..1):
    • Obligatorischer Sub-Container je Kanal zur Spezifikation des Kanal-NM-Verhaltens.
Parameter & Literale
  • ComMNmVariant (EcucEnumerationParamDef, Default: FULL):
    • Bestimmt die NM-Integrationsstrategie des Kanals über +literal-Zuordnungen (EcucEnumerationLiteralDef):
      • NONE: Keine NM-Instanz vorhanden. Kanal schaltet direkt zwischen Kommunikationsmodi.
      • LIGHT: Kein AUTOSAR-NM-Busprotokoll; ComM steuert den Shutdown autonom über einen Software-Timer.
      • PASSIVE: Knoten empfängt NM-Nachrichten über Nm, sendet jedoch selbst keine Network-Management-Frames (Nm_PassiveStartUp).
      • FULL: Vollständige NM-Unterstützung mit aktivem Bustoken-/Heartbeat-Mechanismus via Nm_NetworkRequest() / Nm_NetworkRelease().
      • SLAVE_ACTIVE: Kanal agiert als Slave-Knoten mit aktiver Aufweckfähigkeit bei Kommunikationsbedarf.
      • SLAVE_PASSIVE: Kanal agiert als rein passiver Slave-Knoten ohne eigene Aufweckinitiierung.
  • ComMNmLightTimeout (EcucFloatParamDef, Multiplizität 0..1, Default: 10 s, Min: 0, Max: 255):
    • Kanalbezogene Nachlaufzeit in Sekunden für die Variante LIGHT, bevor der Bus in COMM_NO_COMMUNICATION versetzt wird.
  • ComMPncNmRequest (EcucBooleanParamDef, Default: false):
    • Flag zur Steuerung, ob ein Kanal-Request, der aus einer PNC-Zuweisung (Partial Network Cluster) resultiert, eine aktive NM-Anforderung (Nm_NetworkRequest) auslöst.

3. Dynamisches Verhalten & Sequenzablauf

Die Parameter determinieren die Zustandsübergänge des kanalspezifischen ComM-Zustandsautomaten:

  • Pfad ComMNmVariant == FULL:
    • Kommunikationsanforderung (ComM_RequestComMode): ComM ruft Nm_NetworkRequest(nmChannelHandle) auf.
    • Freigabe: ComM ruft Nm_NetworkRelease(nmChannelHandle) auf.
    • Der Übergang von COMM_FULL_COMMUNICATION nach COMM_NO_COMMUNICATION wird asynchron durch Callbacks aus der NM-Schicht getriggert (Nm_BusSleepMode(), Nm_PrepareBusSleepMode()).
  • Pfad ComMNmVariant == LIGHT:
    • Keine Interaktion mit dem Nm-Modul.
    • Sobald alle Nutzeranforderungen (ComM_UserHandleType) freigegeben sind, startet ein interner Timer mit der Dauer ComMNmLightTimeout.
    • Nach Ablauf des Timers schaltet ComM die unteren Treiber (CanSM/LinSM/FrSM) direkt in den Silent- bzw. No-Communication-Modus.
  • Pfad ComMNmVariant == PASSIVE:
    • ComM initiiert den Kanal bei Anforderung über Nm_PassiveStartUp(); es erfolgen keine eigenen Keep-Alive-Requests.
  • Pfad ComMNmVariant == SLAVE_ACTIVE:
    • Kanal arbeitet im Slave-Modus, initiiert jedoch bei lokaler Kommunikationsanforderung (ComM_RequestComMode) aktiv einen Bus-Wakeup-Vorgang über den State Manager.
  • Pfad ComMNmVariant == SLAVE_PASSIVE:
    • Kanal arbeitet als rein passiver Slave; Modusübergänge erfolgen ausschließlich reaktiv auf externe Busaktivitäten ohne eigene Wakeup-Signale.
  • Einfluss von ComMPncNmRequest:
    • Bei PNC-Aktivierung prüft ComM pro zugeordnetem Kanal dieses Flag: Ist es true, wird die NM-Botschaft für den Cluster auf diesem Kanal gesendet; ist es false, wird die Kommunikation auf dem Bus ohne NM-PDU aktiv gehalten.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Codegenerierung & Speicherfootprint:
    • Kanäle mit ComMNmVariant == NONE oder LIGHT kompilieren Schnittstellenaufrufe zu Nm.h über Pre-Compile-Schalter (#if (COMM_NM_SUPPORT == STD_ON)) heraus, was ROM/RAM-Ressourcen schont.
  • Konfigurationsvalidierung:
    • Konsistenzregel: Ist ComMNmVariant == LIGHT gewählt, muss der Generator das Vorhandensein von ComMNmLightTimeout erzwingen (trotz formaler Metamodell-Multiplizität 0..1).
    • Bei ComMNmVariant != LIGHT ist ComMNmLightTimeout semantisch ungültig und muss vom Generator ignoriert bzw. als Warnung/Fehler gemeldet werden.
  • Partial Networking:
    • Bei ECUs in Teilnetzen (CAN-Transceiver mit selektivem Weckruf / WUF) steuert ComMPncNmRequest, ob das PNC-Bitfeld im NM-Frame gesetzt/gesendet werden muss, um benachbarte Knoten im Cluster wachzuhalten.
