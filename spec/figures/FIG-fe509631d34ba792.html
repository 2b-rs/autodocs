2. Komponenten, Entitäten & Schnittstellen

Test-Knoten (Nodes & IP-Topologie)
  1. ECU 2 (System Under Test – SUT):
    • Netzwerkkonfiguration: IP 192.168.7.12 (dediziertes Testnetzwerk /24).
    • Schichtenaufbau:
      • Application Layer (User Space): PHM Test Application(s) – Adaptive Applications (AA) zur Generierung von Kontrollflüssen, Prüfpunkten (Checkpoints) und Fehlzuständen.
      • Middleware / Platform Layer:
        • ARA (AUTOSAR Runtime for Adaptive Applications): Stellt funktionale Cluster bereit, primär ara::phm (Supervision Interfaces, Health Channels) sowie Schnittstellen zu ara::exec (Execution Management) und ara::per (Persistency).
        • POSIX libs (libc, ...): Standard-OS-Laufzeitumgebung (IEEE Std 1003.13 PSE51/PSE52 Profil) für Threading, IPC, System Calls.
      • OS Layer: Linux with Real-time Patches (PREEMPT_RT gepatchter Kernel für deterministisches Scheduling und hochpräzise Zeitgeber/Deadline-Überwachung).
      • Hardware Layer: Reale Ziel-ECU-Hardware inklusive Nonvolatile memory (Flash/EEPROM/NVRAM zur Verifikation persistenter Health-Zustände, Crash-Dumps oder Fehlerzähler).
  2. Jenkins (Test Controller / Orchestrator):
    • Netzwerkkonfiguration: IP 192.168.7.10.
    • Schichtenaufbau:
      • Application Layer: PHM Tester – Test-Execution-Skripte / Test-Harness (z. B. Python, Robot Framework, C++ Runner).
      • Automation Service: Jenkins Server (CI-Engine zur Job-Steuerung und Ergebnisaggregation).
      • OS Layer: Linux (Standard-Host-Kernel).
      • Hardware Layer: Host-PC.
Physische & logische Schnittstellen
  • Ethernet-Backbone (192.168.7.0/24): Punkt-zu-Punkt- bzw. Switch-Verbindung zwischen Jenkins (192.168.7.10) und ECU2 (192.168.7.12) für Teststeuerung (SSH, REST, gRPC oder proprietäres Test-IPC) sowie Telemetrie-/Log-Streaming.
  • SUT-Interne Pfade:
    • Top-Down-Stimulation/Persistierung: PHM Test Application(s) → ARA (ara::phm) → POSIX libs → Linux Kernel → Nonvolatile memory.
    • Bottom-Up-Rückkopplung/Instrumentation: Hardware/OS → POSIX libs → PHM Test Application(s) (Bypassing ARA zur Verifikation von Reboots, Low-Level-Watchdog-Resets oder Kernel-Signalen).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Bereitstellung:
    • Der Jenkins Server triggert über den PHM Tester via IP-Verbindung (192.168.7.10 → 192.168.7.12) den Start der Testumgebung auf ECU 2.
    • Execution Management startet die PHM Test Application(s) und den PHM Daemon (ara::phm).
  2. Stimulation & Supervision-Trigger:
    • Die PHM Test Application(s) meldet Checkpoints zyklisch oder ereignisbasiert an ara::phm (Synchroner IPC-Aufruf).
    • Gezielte Fehlereinspeisung:
      • Alive-Verletzung: Auslassen eines Checkpoint-Zyklus (ReportCheckpoint).
      • Deadline-Verletzung: Überschreiten/Unterschreiten des konfigurierten Zeitfensters zwischen zwei Checkpoints.
      • Logical-Supervision-Verletzung: Ungültige Transition im Checkpoint-Transition-Graphen.
  3. Reaktionspfad & Verifikation (Nonvolatile Memory):
    • Bei determinierter Fehlererkennung löst ara::phm die konfigurierte Recovery Action aus:
      • Übermittlung an State Management (ara::sm) zum Wechsel in den Safe State / Recovery Mode.
      • Triggerung eines kontrollierten Resets oder Watchdog-Timeouts.
    • Speicherung von Status-/Recovery-Evidenz direkt im Nonvolatile memory (über Persistency oder Low-Level-Storage-Treiber).
  4. Feedback-Schleife & Test-Verdict:
    • Nach System-Neustart oder Recovery liest die PHM Test Application bzw. der Test-Agent über die POSIX-Schicht den Status aus dem Nonvolatile memory sowie OS-Bootzähler aus.
    • Die Testergebnisse werden über das Netzwerk an Jenkins zurückgesendet; der PHM Tester verifiziert Soll- vs. Ist-Verhalten und schließt den Testlauf ab.

4. Normative Relevanz & Entwickler-Hinweise

  • Deterministische Testumgebung: Die Verwendung von Linux with Real-time Patches (PREEMPT_RT) ist zwingend erforderlich, um Jitter bei Deadline- und Alive-Supervision-Tests unterhalb der geforderten Fehlertoleranzen (Sub-Millisekundenbereich) zu halten.
  • Bypass-Testpfad: Die direkte Schnittstelle zwischen Hardware/POSIX und der Testapplikation (ohne ARA) verdeutlicht, dass Systemtests für Health Management externe Kontrollpfade (z. B. sysfs, Watchdog-Device-Nodes /dev/watchdog, Persistenzprüfungen im Flash) benötigen, um ARA-unabhängige Verifikationen (Ground Truth) durchzuführen.
  • Netzwerktrennung: Feste IP-Zuordnungen (192.168.7.10 / 192.168.7.12) erfordern für automatisierte CI-Pipelines isolierte Subnetze, um Interferenzen durch parallele Testausführungen oder externe Broadcast-Stürme auf das Timing auszuschließen.
  • Persistenz-Audit: Für Plattform- und Integrationsentwickler bedeutet dies: Recovery-Zustände müssen zwingend stromausfallsicher bzw. reset-resistent im Nonvolatile memory abgelegt werden, da Systemtests den Erfolg von Recovery-Actions primär über Post-Mortem-Daten in der Nonvolatile Memory validieren.
