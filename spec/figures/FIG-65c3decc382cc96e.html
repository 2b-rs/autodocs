1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / Metamodell-Abbildungsdiagramm zur konzeptionellen Transformation (Typ- zu Instanzebene).
  • Architektur-Kontext: AUTOSAR Classic Platform, BSW-Modul Service Discovery (Sd), Layer: Communication Services (AUTOSAR COM-Stack, direkt oberhalb von SoAd und PduR, koordiniert über BswM).
  • Funktionaler Zweck: Visualisierung des Übergangs von der abstrakten Servicedefinition (Software-Design-/VFB-Ebene) zur konkreten Runtime- und Deployment-Konfiguration im SOME/IP-SD-Stack. Es verdeutlicht die Architekturprinzipien gemäß:
    • SWS_Sd_00004: Unterstützung mehrerer Instanzen eines Service-Interfaces auf einer oder mehreren ECUs.
    • SWS_Sd_00005: Unterstützung mehrerer Eventgroups innerhalb eines Service-Interfaces.
    • SWS_Sd_00400: Zuordnung und Handhabung instanziierter Service- und Eventgroup-Instanzen im SOME/IP-SD-Protokollrahmen.

2. Komponenten, Entitäten & Schnittstellen

Abstrakte Interface-Ebene (Definitionsraum, links)
  • «interface» Service: Repräsentiert den typisierten Service-Vertrag (Kombination aus Methoden, Events und Fields mit eindeutiger ServiceID).
  • «interface» Eventgroup: Logische Gruppierung von Events und/oder Fields innerhalb des Service-Interfaces zum Zwecke des gemeinsamen Publish/Subscribe-Handlings.
  • Beziehung:
    • **Komposition (1 → *):** Ein Service-Interface kapselt 0..* bzw. 1..* Eventgroup-Definitionen. Die Lebensdauer der Eventgroup ist strikt an das Service-Interface gekoppelt.
Instanz-Ebene (Deployment- & Runtime-Objekte, rechts)
  • Server Service (SdServerService im BSW-Modell):
    • Konkrete Runtime-Instanz eines Service-Anbieters auf einer ECU. Identifiziert über das Tupel (ServiceID, InstanceID).
    • Verknüpft mit lokalen Socket-Verbindungen (SoAdSocketConnectionGroup) für Unicast-Schnittstellen.
  • Client Service (SdClientService im BSW-Modell):
    • Konkrete Konsumenten-Instanz auf einer anfragenden ECU. Referenziert eine Ziel-ServiceID und entweder eine explizite InstanceID oder den Wildcard-Wert 0xFFFF (Any-Instance).
  • EventHandler (SdEventHandler im BSW-Modell):
    • Server-seitige Verwaltungseinheit einer konkreten Eventgroup-Instanz.
    • Verwaltet Abonnentenlisten, Subscription-Leases und ordnet den Datenverkehr Unicast- bzw. Multicast-Endpoints zu.
  • ConsumedEventgroup (SdConsumedEventGroup im BSW-Modell):
    • Client-seitige Abonnenten-Instanz. Steuert die Anforderung, das Halten und das Erneuern des Abonnements für eine bestimmte Eventgroup.
Beziehungen & Kardinalitäten auf Instanzebene
  • **Server Service → Client Service (Assoziation 1 : *):**
    • Genau ein Server-Service bedient 0..n verteilte Client-Service-Instanzen netzwerkweit.
  • **Server Service → EventHandler (Komposition 1 : *):**
    • Ein Server Service aggregiert exklusiv 0..n EventHandler.
  • **Client Service → ConsumedEventgroup (Komposition 1 : *):**
    • Ein Client Service aggregiert exklusiv 0..n ConsumedEventgroup-Instanzen.
  • **EventHandler → ConsumedEventgroup (Assoziation 1 : *):**
    • Ein EventHandler auf Serverseite verarbeitet Subscriptions von 0..n ConsumedEventgroup-Instanzen über das Netzwerk (1:n-Publish/Subscribe-Relation).

3. Dynamisches Verhalten & Sequenzablauf

Das Strukturmodell determiniert das zweistufige SOME/IP-SD-Zustands- und Nachrichtenmodell:

[BswM] -> Sd_ServerServiceSetState(AVAILABLE)
   │
   ├─► Server Service: Sendet SOME/IP-SD "OfferService" (Initial / Repetition / Main Phase)
   │      ▲
   │      │ Match ServiceID & InstanceID
   │      ▼
   ├─► Client Service: Empfängt Offer (bzw. sendet "FindService") -> Wechsel zu AVAILABLE
   │      │
   │      └─► ConsumedEventgroup: Initiiert Subscribe
   │             │
   │             ├─► Sendet "SubscribeEventgroup" (TTL > 0, Endpoint Options)
   │             ▼
   └─► EventHandler: Prüft Subscription (ggf. Applikations-Callout)
          │
          ├─► Positiv: Antwortet mit "SubscribeEventgroupAck" (+ optional Multicast-IP/Port)
          └─► Negativ: Antwortet mit "SubscribeEventgroupNack"
  1. Phase 1: Service Discovery (Dienst-Ebene)
    • Trigger: Mode-Management (BswM) signalisiert Dienstverfügbarkeit via Sd_ServerServiceSetState() bzw. Bedarf via Sd_ClientServiceSetState().
    • Ablauf: Server Service sendet zyklisch/phasengesteuert OfferService. Der Client Service wechselt bei Treffer auf AVAILABLE und öffnet über SoAd die IP-Routingpfade (SoAd_EnableRouting).
  2. Phase 2: Eventgroup Subscription (Eventgroup-Ebene)
    • Trigger: RTE/Applikation fordert Event-Empfang an; Bindung an ConsumedEventgroup wird aktiv.
    • Ablauf: ConsumedEventgroup sendet asynchron einen SubscribeEventgroup-Entry inklusive gewünschter TTL.
    • Verarbeitung: Der korrespondierende EventHandler registriert den Client-Endpoint. Bei erfolgreicher Validierung erfolgt ein synchroner/asynchroner SubscribeEventgroupAck.
    • Lease-Management & Abbruch: Rechtzeitig vor Ablauf der Lease-Time muss die ConsumedEventgroup ein Renewal senden. Sendet der Client ein StopSubscribeEventgroup (TTL = 0) oder läuft der Timer ab, deregistriert der EventHandler den Konsumenten.

4. Normative Relevanz & Entwickler-Hinweise

  • ECUC-Konfigurationskonsistenz (Sd.epc / ARXML):
    • Für jeden im VFB instanziierten Provided-Port mit SOME/IP-Deployment muss zwingend ein Container SdServerService mit untergeordneten SdEventHandler-Containern konfiguriert werden.
    • Für Required-Ports korrespondieren SdClientService und SdConsumedEventGroup.
    • Eindeutigkeit des Schlüssels (ServiceID, InstanceID) muss clusterweit garantiert sein; Fehlkonfigurationen führen zu Silent Drops im SoAd oder DET-Meldungen (SD_E_INV_ID).
  • Ressourcenallokation & Multicast-Optimierung:
    • Jeder EventHandler muss im Stack mit einer maximalen Subscriber-Anzahl (SdServerService/SdEventHandler/SdEventHandlerMaxSubscriptions) ausgelegt werden (statischer Puffer / deterministischer Speicherbedarf im Embedded-RAM).
    • Bei n > 1 Abonnenten entscheidet die Konfiguration (SdMulticastEventgroupOption), ob Events ressourcenschonend via Multicast oder redundant per Unicast dupliziert werden.
  • API- und Initialisierungssequenz:
    • Datenübertragung (PduR_Transmit / SoAd_IfTransmit) für Events darf erst nach erfolgreichem State-Change des EventHandler auf Subscribed erfolgen. Vorherige Sendeaufrufe werden vom SoAd verworfen oder führen zu Fehlern.
    • Integration des BswM: Das Triggern der SD-Zustände (Sd_ServerServiceSetState, Sd_ClientServiceSetState) muss exakt an die Network-Management- (ComM) und IP-Interface-Zustände gekoppelt sein.
