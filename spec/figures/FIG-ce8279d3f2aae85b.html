1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (AUTOSAR M2-Metamodell-Ausschnitt).
  • Technischer Zweck & Einordnung: Spezifikation des deklarativen Mappings im Manifest der AUTOSAR Adaptive Platform (TPS Manifest Specification, Release R25-11). Das Metamodell definiert die Bindung zwischen standardisierten Diagnose-Diensten nach ASAM SOVD (Service-Oriented Vehicle Diagnostics, REST/HTTP-basiert) und den Service-Ports (PPortPrototype) der ausführenden Applikationsprozesse (ProcessDesign).

    • ARElement (Wurzelelement des AUTOSAR-Metamodells) → DiagnosticCommonElement → DiagnosticMapping → DiagnosticSwMapping → DiagnosticSovdOperationPortMapping.
    • DiagnosticSovdOperationPortMapping: Zentrales Konfigurationselement zur Zuordnung einer SOVD-Operation zu einer Applikations-Schnittstelle.
  • SOVD-Dienst-Zweig:
    • DiagnosticCommonElement → DiagnosticSovdServiceInstance → DiagnosticSovdOperation.
    • DiagnosticSovdOperation: Modelliert die konkrete funktionale SOVD-Operation innerhalb einer Service-Instanz.
  • Port- & Interface-Zweig:
    • ARElement, AtpBlueprint, AtpBlueprintable, AtpType → PortInterface → DiagnosticPortInterface → DiagnosticSovdPortInterface → DiagnosticSovdOperationInterface.
    • AbstractProvidedPortPrototype → PPortPrototype: Ausprägung eines Service-Bereitstellungs-Ports an einer Software-Komponente.
  • Prozess-Kontext:
    • ARElement → ProcessDesign: Repräsentiert den Entwurfskontext eines Prozesses auf Architekturebene.
    • AbstractExecutionContext → Process: Konkrete Deployment- und Ausführungseinheit auf Betriebssystemebene.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Das Diagramm ist ein deklaratives Konfigurationsmodell zur Entwurfszeit. Für die Laufzeit leitet sich daraus folgendes Bindungs- und Aufrufmuster ab:

  1. Request-Eingang: Ein externer SOVD-Client sendet eine REST/HTTP-Anforderung (z. B. POST/GET auf eine SOVD-Operations-URI) an den Adaptive Diagnostic Server / SOVD-Daemon.
  2. Operations-Resolution: Der Diagnose-Stack identifiziert die angesprochene DiagnosticSovdOperation und löst über das DiagnosticSovdOperationPortMapping das Mapping-Tripel auf: $$\text{DiagnosticSovdOperation} \xrightarrow{\text{Mapping}} (\text{ProcessDesign}, \text{PPortPrototypeInExecutable})$$
  3. IPC-Routing (ara::com / Functional Cluster): Der Aufruf wird an den konkreten Process delegiert, der das entsprechende ProcessDesign instanziiert. Die Übergabe erfolgt typisiert über das generierte Service-Skeleton am PPortPrototype (DiagnosticSovdOperationInterface).
  4. Ausführung & Response: Die Anwendungslogik führt die Operation (z. B. Routine Control, Test, IO-Operation) synchron oder asynchron aus. Das Ergebnis wird über das Port-Interface an den SOVD-Daemon zurückgemeldet und dort in den standardisierten SOVD/JSON-Response-Payload serialisiert.

4. Normative Relevanz & Entwickler-Hinweise

  • Diagnostic & Execution Manifest Konfiguration:
    • Jede über SOVD exponierte Applikationsoperation benötigt im Manifest ein valides DiagnosticSovdOperationPortMapping.
    • Die Verwendung des Stereotyps «instanceRef,atpUriDef» bei pPortPrototypeInExecutable erzwingt eine vollständige Instance-Path-Auflösung (Root-SwComponentPrototype → SwComponentPrototype → PPortPrototype) innerhalb des Executables.
  • Typkonsistenz: Der zugewiesene PPortPrototype darf nicht mit generischen Classic-/Adaptive-Interfaces typisiert werden, sondern muss zwingend ein DiagnosticSovdOperationInterface (bzw. dessen Ableitung) implementieren.
  • Entkopplung über ProcessDesign: Das Mapping referenziert ProcessDesign anstelle der konkreten Process-Instanz. Dies ermöglicht die Wiederverwendung desselben Service-Designs über mehrere Prozess-Instanziierungen hinweg, setzt aber voraus, dass der ausführende Process über seine +design-Referenz eindeutig zugeordnet werden kann.
  • Generatorkonsequenz: Stack-Generatoren (Adaptive Core / Diagnostic Management Daemon) generieren aus diesen Mappings die interne Dispatching-Tabelle für den HTTP/REST-Endpunkt auf die ara::com-Skeletons. Fehlerhafte Kardinalitäten (0 statt 1 zur Generierungszeit) führen zu unvollständigen Routing-Tabellen und zur Nichterreichbarkeit der SOVD-Ressource (HTTP 404 / 500).
