1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsdiagramm (State Machine) mit hierarchisch verschachtelten zusammengesetzten Zuständen (Composite States).
  • Technischer Zweck: Definition des übergeordneten Lebenszyklus-Zustandsautomaten des AUTOSAR Basic Software Moduls ECU State Manager (EcuM, SWS Document ID 78) der AUTOSAR Classic Platform.
  • Funktionale Einordnung: Der EcuM bildet den zentralen Einstiegspunkt der BSW-Initialisierung nach dem Reset-Vektor. Er steuert den Übergang von primitiver HW-Initialisierung zum koordinierten Betriebssystem- und BSW-Scheduler-Start, übergibt die Laufzeitkontrolle im Zustand UP an den Basic Software Mode Manager (BswM) und wickelt synchronisierte Low-Power- (SLEEP) sowie geregelte Herunterfahr- bzw. Reset-Szenarien (SHUTDOWN -> OFF) ab.

2. Komponenten, Entitäten & Schnittstellen

  • Hauptzustände (Top-Level Composite States):
    • STARTUP: Initialisierungsphase vor und unmittelbar nach OS-Start.
    • UP: Operative Betriebsphase (Laufzeit-Modusverwaltung durch Applikation/BswM).
    • SLEEP: Energiesparphase mit reduzierter Stromaufnahme.
    • SHUTDOWN: Kontrollierte Sequenz zur Außerbetriebnahme vor Reset oder Power-Off.
    • OFF: Terminaler Endzustand (Spannungslosigkeit bzw. HW-Abschaltung).
  • Subzustände (Verschachtelte Zustände):
    • Unterhalb STARTUP: StartPreOs, StartPostOs.
    • Unterhalb SLEEP: GoSleep, Poll, Halt, WakeUpRestart.
    • Unterhalb SHUTDOWN: OffPreOs, OffPostOs.
  • Beteiligte System-Akteure & BSW-Schnittstellen:
    • OS (Operating System): Wird in StartPreOs via StartOS() gestartet; wird in OffPreOs via ShutdownOS() beendet.
    • SchM (Schedule Manager / BSW Scheduler): Initialisierung in StartPostOs (SchM_Init), Deinitialisierung in OffPreOs (SchM_Deinit).
    • BswM (BSW Mode Manager): Start in StartPostOs (BswM_Init), Deinitialisierung in OffPreOs (BswM_Deinit); übernimmt in UP Regelung von Zustandswechseln (Arbitrierung von Mode Requests).
    • Mcu / Hardware-Treiber: Takt-, Sleep- und Reset-Steuerung (Mcu_SetMode, Low-Power-Modes).
    • Wakeup Sources (z. B. Can, Lin, Fr, Gpt, EcuM-interne Pins): Aktivierung/Deaktivierung über Peripherie-/Transceiver-Treiber.

3. Dynamisches Verhalten & Sequenzablauf

A. Initialisierungspfad (STARTUP -> UP)
  1. Reset -> STARTUP -> StartPreOs: Einstieg über EcuM_Init(). Ausführung primitiver Treiberinitialisierungen (Callout EcuM_AL_DriverInitZero(), Auslesen des Reset-Grunds, EcuM_AL_DriverInitOne()).
  2. Transition OS started -> StartPostOs: Aufruf von StartOS(). Der OS-Start hookt in einen Autostart-/Startup-Task ein, welcher EcuM_StartupTwo() aufruft.
  3. Transition BswM, Os and SchM initialized -> UP: Initialisierung von SchM und BswM. Sobald der BswM betriebsbereit ist und die Task-Planung läuft, wechselt der EcuM autonom in den Zustand UP.
B. Energiesparpfad (UP <-> SLEEP)
  1. Eintritt UP -> SLEEP (GoSleep): BswM fordert Sleep-Target an. Der EcuM konfiguriert Wakeup-Quellen (WakeUpSources will be enabled), sperrt Scheduler-Aktivitäten und bereitet Low-Power-Target vor.
  2. Verzweigung:
    • Halt: CPU-Core wird über MCU-Treiber angehalten (Clock Gating / Deep Sleep). CPU stoppt Programmausführung; Reaktivierung erfolgt ereignisgesteuert via Hardware-Interrupt.
    • Poll: CPU verbleibt mit reduziertem Takt aktiv oder wacht zyklisch auf; EcuM pollt Wakeup-Quellen via EcuM_CheckWakeup().
  3. Erwachen & Rückkehr (WakeUpRestart -> UP):
    • Bei erkanntem Wakeup-Event wechselt der Automat zu WakeUpRestart.
    • Wakeup-Quellen werden temporär deaktiviert (WakeUpSources will be disabled) bzw. in den Standardbetrieb überführt.
    • Rücksprung in UP. Gemäß Diagramm-Annotation wird nach Rückkehr bei Bedarf die Validierung eingeleitet ("After Sleep the WakeupValidation is started if needed" über EcuM_ValidateWakeupEvent()).
C. Abschaltpfad (UP -> SHUTDOWN -> OFF / Reset)
  1. UP -> OffPreOs: Initiiert durch BswM-Entscheidung bei Shutdown-Request. De-Initialisierung von BSW-Modulen, BswM und SchM (SchM and BswM deinitialized; OS will be shutdown).
  2. OffPreOs -> OffPostOs: Aufruf von ShutdownOS(). Eintritt in Shutdown-Hook des OS.
  3. Verzweigung am Ausgang von OffPostOs:
    • Pfad 1 (Reset): Transition "Reset if Shutdown Target is RESET" triggert HW-Reset (z. B. EcuM_AL_Reset()) und führt direkt zurück zum Startzustand von STARTUP.
    • Pfad 2 (Power Off): Transition in den terminalen Zustand OFF via EcuM_AL_SwitchOff().

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsaspekte (ECUC):
    • Die Zuweisung von Treiber-Initialisierungslisten zu StartPreOs (Init Block 0/1) vs. StartPostOs (Init Block 2/3) bestimmt, welche BSW-Treiber noch ohne Interrupts/OS-Ressourcen laufen müssen.
    • Definition von EcuMDefaultShutdownTarget (RESET, SLEEP, OFF) und zugehörigem EcuMDefaultSleepMode.
  • Einschränkungen für Treiber- und Stack-Entwickler:
    • Keine OS-Dienste vor StartPostOs: In StartPreOs dürfen keine blockierenden APIs, OS-Events oder Schedule-Manager-Funktionen genutzt werden.
    • Asynchrone Wakeup-Validierung: Bei Übergang von SLEEP nach UP dürfen Kommunikations-Stacks erst senden, wenn die Wakeup-Quelle via EcuM_ValidateWakeupEvent() validiert wurde (Verhinderung unnötigen Aufwachens bei Spikes/Bussprüngen; Timeout-Überwachung via EcuM_MainFunction()).
    • Deterministische De-Initialisierung: Treiber, die in OffPreOs deinitialisiert werden, müssen vor dem finalen ShutdownOS() in einen sicheren Hardware-Zustand (Fail-Silent) versetzt sein.
