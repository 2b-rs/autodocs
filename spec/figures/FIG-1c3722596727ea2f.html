1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hierarchisches UML-Zustandsdiagramm (State Machine Diagram / Harel Statechart) mit Composite States, Pseudozuständen (Initial-, Choice- und Final-Nodes) und Guard-Bedingungen.
  • Technischer Zweck & Einordnung: Spezifikation des Kernalgorithmus des Moduls CanNm (CAN Network Management, Schicht: Communication Services / System Services) gemäß AUTOSAR_CP_SWS_CANNetworkManagement (Release R23-11). Das Diagramm definiert die Betriebsmodi (Bus-Sleep Mode, Prepare Bus-Sleep Mode, Network Mode) sowie die Sub-Zustände des Network Mode zur dezentralen Steuerung des Bus-Wachzustands, des NM-PDU-Sendeverhaltens und der Buslastreduzierung bei CAN- und Teilnetzwerk-Clustern (Partial Networking).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Module
  • CanNm: Ausführendes BSW-Modul (Zustandsautomat).
  • Nm (Generic NM Interface): Übergeordnete Schicht; empfängt Moduswechsel- und Exception-Benachrichtigungen.
  • CanIf (CAN Interface): Untergeordnete Schicht; liefert Frame-Empfangs- und Sende-Bestätigungen.
  • EcuM / BswM: Initialisierungs- und Deinitialisierungs-Trigger.
Zustände & Hierarchien
  • Top-Level Modi:
    • Bus-Sleep Mode: Ruhezustand; keine Kommunikation, Transceiver im Standby/Sleep.
    • Prepare Bus-Sleep Mode: Pufferzustand zur Sicherstellung der Busruhe vor dem Schlafen.
    • Network Mode (Composite State): Aktiver Kommunikationsmodus.
  • Sub-Zustände im Network Mode:
    • Repeat Message State: Sicherstellung der Knotenerkennung / Synchronisation im Cluster; Entry-Aktion: Stop Bus Load Reduction.
    • Normal Operation State: Regulärer Wachzustand mit aktiver Netzwerkanforderung; Entry-Aktion: Start Bus Load Reduction.
    • Ready Sleep State: Passive Wachhaltung; Knoten benötigt das Netzwerk nicht mehr, hält den Bus aber offen, solange andere Knoten aktiv sind.
  • Pseudozustände:
    • Initialzustand (PowerOn) und Endzustand (PowerOff).
    • Junction Point: Network Mode Entry.
    • Choice Point: Repeat Message Decision Node (Verzweigung nach Ablauf des Repeat Message Timer).
Datenstrukturen, Timer & Parameter
  • Timer: NM-Timeout Timer, Repeat Message Timer, Wait Bus-Sleep Timer, Tx Timeout Timer.
  • Konfigurationsschalter & Guards:
    • CanNmPnHandleMultipleNetworkRequests (BOOLEAN): Steuert den Wiedereintrittspfad bei Mehrfachanforderung aus dem Ready Sleep State.
    • [Network Requested] / [Network Released]: Zustandsvariablen über lokale Netzwerkfreigaben.
    • Repeat Message Bit: NM-PDU-Steuerbit zur Anforderung der Cluster-Synchronisation.
    • Partial Network Learning: Erkennung/Anforderung von PN-Lernphasen (CanNm_PnLearningRequest).
Service-APIs & Callbacks
  • Eingehende Service-APIs (von Nm / Management):
    • CanNm_Init()
    • CanNm_DeInit()
    • CanNm_NetworkRequest()
    • CanNm_NetworkRelease()
    • CanNm_PassiveStartup()
    • CanNm_RepeatMessageRequest()
    • CanNm_PnLearningRequest
  • Eingehende Treiber-Callbacks (von CanIf):
    • CanNm_RxIndication()
    • CanNm_TxConfirmation(Result: E_OK)
  • Ausgehende Notifications (an Nm):
    • Nm_NetworkMode()
    • Nm_PrepareBusSleepMode()
    • Nm_BusSleepMode()
    • Nm_NetworkStartIndication()
    • Nm_TxTimeoutException()

3. Dynamisches Verhalten & Sequenzablauf

Startup & Aufwecksequenzen
  1. Initialisierung: PowerOn → CanNm_Init() → Übergang in Bus-Sleep Mode.
  2. Aktives Aufwecken:
    • Aufruf von CanNm_NetworkRequest() in Bus-Sleep Mode oder Prepare Bus-Sleep Mode.
    • Aktionen: Start NM-Timeout Timer, Start Repeat Message Timer, Callback Nm_NetworkMode().
    • Zielzustand: Network Mode → Repeat Message State.
  3. Passives Aufwecken:
    • Eintreffen externer NM-Nachricht (CanNm_RxIndication()) im Bus-Sleep Mode führt zu Nm_NetworkStartIndication().
    • Bei Aufruf von CanNm_PassiveStartup() (oder CanNm_RxIndication() im Prepare Bus-Sleep Mode): Transition über den Junction Point nach Repeat Message State mit identischem Timer- und Notification-Muster.
Ablauf innerhalb des Network Mode
  1. Zustandserhalt (Composite-Ebene):
    • Jede erfolgreiche Bestätigung (CanNm_TxConfirmation(Result: E_OK)) oder gültige NM-Nachricht (CanNm_RxIndication()) setzt den NM-Timeout Timer zurück (Restart).
  2. Phasenübergang aus Repeat Message State:
    • Nach Ablauf von Repeat Message Timer: Evaluation am Choice Point.
    • Wenn [Network Requested] wahr: Transition nach Normal Operation State (Aktion: Start Bus Load Reduction).
    • Wenn [Network Released] wahr: Transition nach Ready Sleep State.
  3. Betrieb im Normal Operation State:
    • Solange lokal angefordert, zyklisches Senden von NM-PDUs. Bei Timer-Ablauf von NM-Timeout Timer wird dieser neu gestartet.
    • Tritt ein Sendeüberhang auf (Tx Timeout Timer has expired), wird synchron/asynchron Nm_TxTimeoutException() aufgerufen.
    • Aufruf von CanNm_NetworkRelease() führt direkt in den Ready Sleep State.
  4. Wiedereintritt in Repeat Message State:
    • Empfang von Repeat Message Bit == 1, Aufruf von CanNm_RepeatMessageRequest() oder PN-Lernanforderung (CanNm_PnLearningRequest).
    • Aus Ready Sleep State via CanNm_NetworkRequest(), falls CanNmPnHandleMultipleNetworkRequests == TRUE. Falls FALSE, direkter Wechsel nach Normal Operation State.
Shutdown-Sequenz (Einschlafen)
  1. Vorbereitung:
    • Im Ready Sleep State werden keine eigenen NM-PDUs mehr gesendet.
    • Läuft der NM-Timeout Timer ab (kein anderer Knoten hält den Bus aktiv):
      • Start Wait Bus-Sleep Timer.
      • Benachrichtigung: Nm_PrepareBusSleepMode().
      • Zielzustand: Prepare Bus-Sleep Mode.
  2. Abschaltung:
    • Nach Ablauf von Wait Bus-Sleep Timer: Callback Nm_BusSleepMode() und Wechsel in Bus-Sleep Mode.
    • Shutdown des BSW-Stacks über CanNm_DeInit() → PowerOff.

4. Normative Relevanz & Entwickler-Hinweise

  • Teilnetzwerk-Konfiguration (CanNmPnHandleMultipleNetworkRequests):
    • Muss auf TRUE konfiguriert werden, wenn Teilnetzwerk-Cluster zur Laufzeit dynamisch über Re-Requests neu synchronisiert werden müssen. Dies erzwingt die erneute Durchquerung des Repeat Message State zur vollständigen PNC-Bitvektor-Verbreitung.
  • Timer-Abstimmung (CanNm.epc vs. Netzwerk-Cluster-Design):
    • CanNmTimeoutTime muss strikt größer sein als CanNmMessageCycleTime plus maximaler CAN-Jitter/Arbitrierungsverzögerung, um Timeouts im Normal Operation State zu verhindern.
    • CanNmWaitBusSleepTime muss auf allen ECUs im Cluster identisch und groß genug gewählt werden, damit alle Steuergeräte den Zustand Prepare Bus-Sleep Mode synchron erreichen, bevor der erste Transceiver in den Schlafmodus wechselt.
  • Task-Kontext & Reentrancy:
    • Timer-Dekremente und Timeouts werden im Kontext der periodischen CanNm_MainFunction() ausgewertet.
    • CanNm_RxIndication() und CanNm_TxConfirmation() werden aus dem CanIf-Kontext (oft ISR) getriggert. Schutz kritischer Abschnitte (Schutz vor Race Conditions bei Timer-Resets und Zustandsübergängen) ist im Treiber/BSW-Stack zwingend erforderlich.
  • Exception-Handling:
    • Nm_TxTimeoutException() signalisiert Sendeausfälle (z. B. Bus-Off, Hardware-Queue-Überlauf im CAN-Controller). Die Fehlerreaktion (z. B. Dem-Event, Bus-Off Recovery via CanSM) wird in den übergeordneten Modulen koordiniert.
  • Bus Load Reduction:
    • Bei aktiviertem Feature (CanNmBusLoadReductionEnabled == TRUE) reduziert CanNm im Normal Operation State die Sendeaktivität (z. B. Unterdrückung von zyklischen PDUs nach fremden NM-Frames), wohingegen im Repeat Message State ausnahmslos mit voller Zyklusrate gesendet werden muss (Stop Bus Load Reduction).
