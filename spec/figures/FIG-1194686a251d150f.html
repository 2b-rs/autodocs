1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Informelles End-to-End-Architektur- und Datenflussdiagramm (Deployment- und OTA-Verteilungskette) mit integrierter Client-Server-Protokollsequenz.
  • Architektur-Kontext: Spezifiziert die Packaging-, Rollout- und Distributionsarchitektur des Update and Configuration Management (UCM) gemäß AUTOSAR_EXP_PlatformDesign (Kapitel Update & Configuration Management / Vehicle Update). Das Diagramm definiert die Trennung zwischen komponentenorientierter Tier-1-Paketierung und fahrzeugweiter OEM-Kampagnenorchestrierung zur Aktualisierung heterogener Bordnetze (Adaptive Platform, Classic Platform, COTS/Non-AUTOSAR).

2. Komponenten, Entitäten & Schnittstellen

Upstream / Tier-Zulieferer & Integrator
  • Vendor B / Vendor C: Liefern funktionale Teilartefakte:
    • Executable: Kompilierte Binärdateien für Adaptive Applications.
    • Configuration files: Anwendungs- und Plattform-Manifeste (ARXML, JSON).
    • Persistency: Initialdatenbestände für Key-Value-Storage (KVS) oder File-Storage (FS).
  • Integrator: Führt Artefakte im Software Cluster (SWCL) zusammen.
  • Packager: Generierungs-Tool (bereitgestellt durch UCM-Entwickler), welches das komprimierte Backend package (Software Package) samt zugehörigem Software Package manifest generiert.
  • Integrator signature: Kryptografische Signatur über das Software Package zur Gewährleistung von Traceability, Integrität und Authentizität der Lieferkette.
  • Integrator repository (Repo A/B): Bereitstellungspunkt der signierten Software Packages für das OEM-Backend.
OEM-Backend
  • Software catalog: Zentrales Backend-Repository zur Erfassung, Versionierung und Validierung aller eingehenden Software Packages und Software Package manifests.
  • VIN database: Datenbank für fahrzeugspezifische As-Built-Stände, Zuordnung von Hardware-Konfigurationen und Ziel-Softwareständen anhand der Vehicle Identification Number (VIN).
  • EE System engineer: Konfiguriert die Update-Kampagne über Entwicklungsschnittstellen (@dev).
  • Campaign orchestrator: Bestimmt kampagnenspezifische UCM-Zielidentifikatoren (Campaign orchestration UCM identifier) und definiert Update-Reihenfolge und Abhängigkeiten.
  • Key manager: Backend-PKI/HSM zur Verwaltung privater OEM-Schlüssel für die Gesamtfahrzeug-Signierung.
  • Vehicle packager: Aggregiert mehrere Software Packages verschiedener Domänen/Integratoren mit einem übergeordneten Vehicle Package manifest zu einem Vehicle package und signiert dieses mit der OEM signature.
In-Vehicle-Domäne
  • Telematik-/Gateway-Knoten: Drahtlose Kommunikationsschnittstelle (Internet / ETSI) zum Empfang des Vehicle Packages.
  • Adaptive AUTOSAR: Hostet das zentrale Vehicle UCM (Orchestrierung) sowie lokale Target UCMs für Software Cluster.
  • Classic AUTOSAR: Steuergeräte, die über Diagnoseschnittstellen (z. B. UDS over DoIP) angebunden und geflasht werden.
  • IVI / COTS (Non-AUTOSAR): Infotainment- und Fremdsysteme, die über spezifische Update-Agenten in die Kampagne eingebunden sind.

3. Dynamisches Verhalten & Sequenzablauf

Phase 1: Upstream Packaging & Backend-Ingestion (Offline/Build-Time)
  1. Zulieferer stellen Binaries, Persistenzdaten und Konfigurationen bereit.
  2. Der Integrator assembliert den Software Cluster (SWCL).
  3. Das Packager-Tool generiert das Backend package inklusive Software Package manifest und bringt die Integrator-Signatur an.
  4. Das Paket wird in das Integrator-Repository übertragen und in den OEM Software catalog importiert.
  5. Der Systemingenieur stößt eine Kampagne an; der Campaign orchestrator gleicht die Ziel-Softwarestände mit der VIN database ab.
  6. Der Vehicle packager zieht die Schlüssel aus dem Key manager, bündelt die geforderten Software Packages und erzeugt das OEM-signierte Vehicle package.
Phase 2: Fahrzeug-Backend-Interaktion (Online / OTA-Laufzeit)
  • Pfad 1 (Vehicle-driven Query / Pull):
    • 1. Q: Fahrzeug meldet aktuellen Versionsstatus inklusive VIN an das Backend (These are my versions statuses + VIN).
    • 1. A: Backend prüft Soll-/Ist-Stand und überträgt das assemblierte Vehicle package.
  • Pfad 2 (Backend-driven Query / Push):
    • 2. Q: Backend fragt den Fahrzeugstatus ab (Or what are your versions? / Please upload versions list).
    • 2. A: Backend sendet Soll-Versionen (My last versions for your VIN) und liefert das Vehicle package aus.
  • In-Vehicle Execution:
    • Das primäre UCM validiert die OEM signature des Vehicle Packages.
    • Die enthaltenen Software Packages werden an die jeweiligen Target UCMs bzw. Classic-ECU-Updatemanager verteilt.
    • Durchführung des UCM-Zustandsübergangs (Transfer → Process → Activate).
  • Phase 3: Kampagnen-Abschluss (Reporting):
    • 3. Activation(s) result(s): Fahrzeug meldet den aggregierten Erfolgs-, Fehler- oder Rollback-Status aller beteiligten Cluster/ECUs an das Backend zurück zur Synchronisation der VIN database.

4. Normative Relevanz & Entwickler-Hinweise

  • Zweistufige Paketierungshierarchie:
    • Software Package: Gekapselte Einheit für ein spezifisches Target UCM (enthält Manifest, Executables, Konfigurations- und Persistenzdaten; signiert vom Tier-1/Integrator).
    • Vehicle Package: Aggregat-Container für das gesamte Fahrzeug (enthält mehrere Software Packages, globale Kampagnen-Metadaten und die OEM-Signatur).
  • Manifest-Konfiguration:
    • Entwickler müssen im Software Package manifest exakte Abhängigkeiten (SoftwareCluster.dependencies), Ziel-UCM-Routen (ucmIdentifier), Versionsnummern nach Semantic Versioning und Ziel-Prozessorarchitekturen hinterlegen.
  • Kryptografische Signaturkette:
    • Jede Adaptive-Instanz benötigt im Crypto-Stack / Key Storage Manager (KSM) konfigurierte Trust-Anchors:
      • Das Vehicle UCM / Gateway benötigt das OEM-Wurzelzertifikat zur Verifikation des Vehicle package.
      • Das lokale Target UCM benötigt das Integrator-Zertifikat zur Validierung des einzelnen Software package.
  • Persistenz-Migration:
    • Werden im Software Package Daten für ara::per aktualisiert, müssen Applikationsentwickler über das Manifest Migrationsstrategien (Reset, Update-Skripte oder abwärtskompatible Schemata) deklarieren, um Datenverlust beim Aktivieren des neuen Software Clusters zu verhindern.
  • Heterogene Bus-Schnittstellen (Classic AUTOSAR):
    • Für Classic-ECUs erfordert der Workflow standardisierte UDS-Routinen (ISO 14229 / Flash-Bootloader). Das Adaptive System fungiert als UDS-Master; Entwickler auf Classic-Seite müssen sicherstellen, dass Übertragungszeiten und Session-Timeouts mit den Timeout-Budgets des UCM-Aktivierungsprozesses konform sind.
