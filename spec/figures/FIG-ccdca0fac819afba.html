1. Diagrammtyp & Architektur-Kontext

Informelles Architektur- und Interaktionsdiagramm im Kontext des AUTOSAR Adaptive Platform Update and Configuration Management (UCM). Das Diagramm illustriert das Entwurfsmuster zur dynamischen Identifikation und gezielten Adressierung mehrerer verteilter Slave-UCM-Instanzen durch einen zentralen Master UCM bzw. Vehicle Update Manager (VUM) über serviceorientierte Kommunikation (ara::com).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm umfasst folgende Komponenten und Schnittstellen:

  • Master UCM/VUM: Zentrale Komponente (Client), die über einen RPort (Required Port) verfügt und intern Proxy-Instanzen (Proxy id = 1, Proxy id = 2, Proxy id = 3) zur Repräsentation der Remote-Dienste hält.
  • Slave UCM: Drei separate Server-Instanzen (UcmModuleInstantiation), jeweils mit konfigurierter Kennung:
    • identifier = 1
    • identifier = 2
    • identifier = 3
  • PPort: Jede Slave-UCM-Instanz stellt ihren Dienst über einen PPort (Provided Port) bereit.
  • Verbindungen: Punktierte Linien verbinden den zentralen RPort des Master UCM mit den jeweiligen PPort-Schnittstellen der Slave-Instanzen.
  • Code-Snippet: Pseudocode innerhalb des Master UCM: 
    container = FindService();
proxies = CreateProxies(container);
for (proxy p : proxies) {
    if (2 == p.GetId()) {
        ...
    }
}

3. Dynamisches Verhalten & Sequenzablauf

Der Ablauf zur Dienstfindung und selektiven Interaktion gliedert sich wie folgt:

  1. Service Discovery: Der Master UCM führt FindService() aus, um alle verfügbaren Instanzen des Slave-UCM-Service im Fahrzeugnetzwerk aufzufinden.
  2. Proxy-Instanziierung: Aus dem zurückgegebenen Service-Handle-Container werden über CreateProxies(container) clientseitige Proxies instanziiert.
  3. Identifikation: Der Master iteriert über die erzeugten Proxies (for (proxy p : proxies)).
  4. Instanzfilterung: Über die Methode p.GetId() wird die im Manifest über UcmModuleInstantiation.identifier konfigurierte ID der jeweiligen Slave-UCM-Instanz abgefragt. Stimmt die ID mit dem gewünschten Ziel überein (im Beispiel 2 == p.GetId()), wird die modulspezifische Kommunikation für diese Zielinstanz fortgesetzt.

4. Normative Relevanz & Entwickler-Hinweise

  • Manifest-Modellierung: Für jede Slave-UCM-Instanz muss im Manifest ein eindeutiger Wert für UcmModuleInstantiation.identifier hinterlegt werden, um Mehrdeutigkeiten bei der Fahrzeugaktualisierung zu verhindern.
  • Service-Design: Die Service-Schnittstelle des Slave UCM muss einen Mechanismus (z. B. Methode oder Feld GetId()) bereitstellen, der die konfigurierte Instanz-ID an den Master meldet.
  • ara::com Implementierung: Der Master UCM bindet nicht statisch an eine einzelne Instanz-ID zur Compile-Zeit, sondern nutzt 1:n-Service-Discovery (FindService) und filtert zur Laufzeit dynamisch über die Instanz-Kennung.
