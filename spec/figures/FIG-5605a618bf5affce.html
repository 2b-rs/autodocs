1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm der AUTOSAR BSW-Parameterdefinition (ECU Configuration Parameter Definition Metamodel, EcucParameterDef).
  • Architektur-Kontext: Repräsentiert die strukturelle Definition des obligatorischen globalen Konfigurationscontainers CanGeneral innerhalb des Moduls Can (CAN-Treiber, MCAL). Es definiert die modulgültigen Parameter, Subcontainer und BSW-/OS-Referenzen zur statischen Codegenerierung (Can_Cfg.h, Can_PBcfg.c) sowie zur Einbettung in das AUTOSAR-Basissoftware-Stack-Ökosystem (CanIf, SchM/OS, Det, IdsM, StbM).

2. Komponenten, Entitäten & Schnittstellen

#### Übergeordnete Metamodell-Entitäten

  • Can: EcucModuleDef (Multiplizität: 0..*): Wurzel-Moduldefinition des CAN-Treibers.
  • CanGeneral: EcucParamConfContainerDef (Multiplizität: 1..1, Relation: +container via Komposition): Zentraler Konfigurationscontainer für modultreiberweite Eigenschaften.

#### Enthaltene Parameter (+parameter)

  • CanDevErrorDetect: EcucBooleanParamDef: Aktivierung der Development-Error-Erkennung (Default: false).
  • CanMultiplexedTransmission: EcucBooleanParamDef: Freigabe von Multiplexed Transmission (parallele Nutzung mehrerer Hardware-TX-Mailboxen für erhöhten PDU-Durchsatz/Out-of-Order-Pufferung).
  • CanTimeoutDuration: EcucFloatParamDef: Hardware-Timeout-Dauer in Sekunden für synchrone Wartezyklen / Controller-Transitions (min = 0.000001 [1 µs], max = 65.535 s).
  • CanMainFunctionWakeupPeriod: EcucFloatParamDef (Multiplizität: 0..1): Zykluszeit für Can_MainFunction_Wakeup() in Sekunden (min = 0, max = INF).
  • CanMainFunctionModePeriod: EcucFloatParamDef: Zykluszeit für Zustandsabfragen via Can_MainFunction_Mode() in Sekunden (min = 0, max = INF).
  • CanMainFunctionBusoffPeriod: EcucFloatParamDef (Multiplizität: 0..1): Zykluszeit für Bus-Off-Abfragen via Can_MainFunction_Busoff() in Sekunden (min = 0, max = INF).
  • CanSetBaudrateApi: EcucBooleanParamDef (Multiplizität: 0..1): Freigabe der API Can_SetBaudrate() (Default: False).
  • CanIndex: EcucIntegerParamDef: Eindeutige Treiber-Instanz-ID (min = 0, max = 255) zur Unterscheidung bei Mehrfachtreiber-Installationen.
  • CanVersionInfoApi: EcucBooleanParamDef: Aktiviert die API Can_GetVersionInfo() bzw. das entsprechende Pre-Compile-Makro (Default: false).
  • CanLPduReceiveCalloutFunction: EcucFunctionNameDef (Multiplizität: 0..1): Symbolischer Bezeichner einer herstellerspezifischen L-PDU-Empfangs-Callback-Funktion vor dem Weiterreichen an die CanIf.
  • CanEnableSecurityEventReporting: EcucBooleanParamDef: Aktiviert die Weiterleitung von sicherheitsrelevanten CAN-Ereignissen an den Intrusion Detection System Manager (IdsM, Default: false).
  • CanGlobalTimeSupport: EcucBooleanParamDef: Schaltet Hardware-/Treiber-Timestamping frei (Schnittstelle zu StbM / CanTSyn für globale Zeitsynchronisation).

#### Subcontainer (+subContainer)

  • CanMainFunctionRWPeriods: EcucParamConfContainerDef (Multiplizität: 0..*):
  • Beinhaltet via +parameter: CanMainFunctionPeriod: EcucFloatParamDef (min = 0, max = INF). Ermöglicht die Definition individueller Polling-/Zykluszeiten für getrennte Lese- und Schreib-MainFunctions (Can_MainFunction_Read_<x>, Can_MainFunction_Write_<x>).

#### Referenzen (+reference / +destination)

  • CanOsCounterRef: EcucReferenceDef (Multiplizität: 0..1):
  • Ziel: OsCounter: EcucParamConfContainerDef (Multiplizität: 0..*). Bindet einen Hardware-/OS-Timer zur präzisen internen Zeitbasis (z. B. Timeout-Überwachung, Timestamping).
  • CanEcucPartitionRef: EcucReferenceDef (Multiplizität: 0..*):
  • Ziel: EcucPartition: EcucParamConfContainerDef (Multiplizität: 0..*). Ordnet den Treiber einer oder mehreren Software-Partitionen zu (Multi-Core-/Partitionierungs-Unterstützung).

3. Dynamisches Verhalten & Sequenzablauf (abgeleitete BSW-Semantik)

Da es sich um ein statisches Metamodell handelt, stellt das Diagramm selbst keinen Kontrollfluss dar. Die Konfiguration induziert jedoch folgendes Laufzeitverhalten:

  1. Zyklische Task-Trigger (SchM / BSW Scheduler):
  • Die Parameter CanMainFunction*Period sowie die Instanzen in CanMainFunctionRWPeriods steuern die Aufrufraten der zyklischen Funktionen im BSW-Scheduler.
  • Can_MainFunction_Mode() und optional Can_MainFunction_Busoff(), Can_MainFunction_Wakeup(), Can_MainFunction_Read() / Write() werden exakt in diesen definierten Zeitrastern aufgerufen, um Statusregister und Mailboxen per Polling zu verarbeiten.
  1. Synchroner Pfad & Hardware-Timeouts:
  • Bei internen Zustandswechseln (z. B. Transitionen in den Stop-/Sleep-Mode) fungiert CanTimeoutDuration als Abbruchkriterium für blockierendes Polling auf Hardware-Flags. Ist CanOsCounterRef konfiguriert, erfolgt die Zeiterfassung über den OS-Counter.
  1. Eingehender PDU-Filterpfad (Callout):
  • Bei RX-Interrupt/Polling führt der Treiber vor Aufruf von CanIf_RxIndication() die konfigurierte Funktion CanLPduReceiveCalloutFunction synchron aus. Gibt diese FALSE zurück, wird die L-PDU unmittelbar verworfen.
  1. Fehler- und Security-Meldepfade:
  • Ist CanDevErrorDetect == TRUE, schlägt jede API-Inkonsistenz (Nullpointer, falscher Controller-Index) synchron via Det_ReportError() fehl.
  • Ist CanEnableSecurityEventReporting == TRUE, werden Bus-/Controller-Anomalien asynchron via IdsM_ReportSecurityEvent() signalisiert.

4. Normative Relevanz & Entwickler-Hinweise

  • Code- und ROM-Optimierung:
  • Parameter wie CanDevErrorDetect, CanVersionInfoApi und CanSetBaudrateApi wirken als strikte Compile-Time-Schalter (#define). Sie entfernen ungenutzte APIs und Validierungs-Overhead vollständig aus dem Treiber-Binary.
  • Mailbox-Dimensionierung & TX-Jitter:
  • Ist CanMultiplexedTransmission == TRUE, muss der MCAL-Treiber hardwareseitig mehrere Mailboxen für denselben PDU-Buffer verwalten. Entwickler müssen sicherstellen, dass die Priorisierungshardware des CAN-Controllers korrekt konfiguriert ist, um Out-of-Order-Transmission von Frames derselben CAN-ID zu verhindern.
  • Multi-Core & MPU-Schutz:
  • Durch CanEcucPartitionRef generiert das Konfigurations-Tool die Zuordnung der ISRs und BSW-MainFunctions zu OS-Applications. Bei Multi-Core-Verteilung müssen Zugriffe auf Treiberdatenstrukturen über memory-geschützte Zonen (Memory Mapping) und hardwarenahe Cross-Core-Synchronisation abgesichert werden.
  • Schnittstellenvertrag Callout:
  • Die via CanLPduReceiveCalloutFunction definierte Funktion muss strikt reentrant und blockierungsfrei sein, da sie typischerweise im ISR- oder High-Priority-Task-Kontext der CAN-RX-Abarbeitung ausgeführt wird.
