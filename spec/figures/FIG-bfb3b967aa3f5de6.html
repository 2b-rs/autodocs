1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / AUTOSAR ECUC Parameter Definition Metamodel (gemäß AUTOSAR TPS ECU Configuration).
  • Architektur-Kontext: Spezifiziert die Konfigurationsstruktur des Moduls LinTp (LIN Transport Protocol) innerhalb der Kommunikationsschicht (Communication Services / BSW) nach AUTOSAR Classic Platform Release R23-11.
  • Funktionale Einordnung: LinTp ist architektonisch Teil des LIN-Interfaces (LinIf), agiert jedoch als Transportprotokollschicht zwischen dem PDU-Router (PduR) und der LIN-Treiber-/Interface-Abstraktion (LinIf). Es steuert die Segmentierung, Reassemblierung und Flusskontrolle für Diagnose (UDS on LIN, ISO 17987 / LIN 2.1/2.2) und strukturierte Payload-Übertragung über Master-Request- (0x3C) und Slave-Response-Frames (0x3D).

2. Komponenten, Entitäten & Schnittstellen

Modul-Wurzelknoten
  • LinTp (EcucModuleDef):
    • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = 1 (Modul ist optional pro ECU, maximal einmal instanziierbar).
Container & Parameter (1. Ebene: Modul-Ebene)
  • LinTpGeneral (EcucParamConfContainerDef via Komposition +container):
    • Beherbergt modulglobale Pre-Compile-Schalter.
    • LinTpVersionInfoApi (EcucBooleanParamDef via +parameter):
      • defaultValue = false.
      • Aktiviert/deaktiviert das Makro bzw. die API-Funktion LinTp_GetVersionInfo().
    • LinTpChangeParameterApi (EcucBooleanParamDef via +parameter):
      • Aktiviert/deaktiviert die API LinTp_ChangeParameter() zur dynamischen Laufzeit-Modifikation von TP-Parametern.
  • LinTpGlobalConfig (EcucParamConfContainerDef via Komposition +container):
    • Root-Container für die Link-Time- bzw. Post-Build-fähige Strukturkonfiguration von Kanälen, SDUs und Limits.
Sub-Container & Parameter (2. Ebene: unter LinTpGlobalConfig)
  • LinTpRxNSdu (EcucParamConfContainerDef via +subContainer):
    • Kardinalität: 0..*.
    • Definiert die Empfangs-Transport-PDUs (N-SDUs) inklusive N-Ar-, N-Cr-Timings und Zuordnung zu PduR-Ziel-IDs.
  • LinTpTxNSdu (EcucParamConfContainerDef via +subContainer):
    • Kardinalität: 0..*.
    • Definiert die Sende-Transport-PDUs (N-SDUs) inklusive N-As-, N-Bs-Timings und Bestätigungs-Handles.
  • LinTpChannelConfig (EcucParamConfContainerDef via +subContainer):
    • Kardinalität: 0..*.
    • Konfiguriert kanalbezogene State-Machines, Timeout-Parameter (z. B. P2-, P2*-Max) und die Zuordnung zum korrespondierenden LinIfChannel.
  • LinTpMaxRxNSduCnt (EcucIntegerParamDef via +parameter):
    • Wertebereich: min = 0, max = 65535, lowerMultiplicity = 0.
    • Obere Schranke für die zur Laufzeit/Compile-Zeit allozierte Anzahl an Rx-N-SDU-Deskriptoren.
  • LinTpMaxTxNSduCnt (EcucIntegerParamDef via +parameter):
    • Wertebereich: min = 0, max = 65535, lowerMultiplicity = 0.
    • Obere Schranke für Tx-N-SDU-Deskriptoren.
  • LinTpDemEventParameterRefs (EcucParamConfContainerDef via +subContainer):
    • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = 1.
    • Kapselt standardisierte Fehlermeldereferenzen an das Diagnostic Event Manager (Dem)-Modul (z. B. LINTP_E_TIMEOUT_A, LINTP_E_TIMEOUT_CR).

3. Dynamisches Verhalten & Sequenzablauf

Als statisches ECUC-Metamodell definiert das Diagramm die Deskriptor-Topologie für die Laufzeitumgebung:

[ PduR ]
   │  ▲
   │  │ LinTp_Transmit / PduR_LinTp[CopyTxData|TxConfirmation]
   ▼  │ PduR_LinTp[StartOfReception|CopyRxData|RxIndication]
[ LinTp ]  ◄── Parametriert durch: LinTpChannelConfig (P2/P2*, N-As/N-Cr)
   │  ▲
   │  │ LinIf_Transmit / LinIf_LinTp[TxConfirmation]
   ▼  │ LinIf_LinTp[RxIndication]
[ LinIf ]
  • Puffer- und Routing-Lifecycle:
    1. LinTpMaxTxNSduCnt und LinTpMaxRxNSduCnt dimensionieren die internen Ring- bzw. Verwaltungsstrukturen im RAM (LinTp_ChannelContextType).
    2. Bei segmentierter Übertragung (SF, FF, CF) triggert jeder Frame Callbacks in die PduR-Schicht (PduR_LinTpCopyTxData / PduR_LinTpCopyRxData).
  • Fehlerpfade:
    • Überschreiten der N-As/N-Ar/N-Bs/N-Cr-Timer triggert einen Verbindungsabbruch und optional einen Event-Report über die in LinTpDemEventParameterRefs definierten Dem-Ereignisse.

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Generierung & Footprint:
    • Fehlt LinTpChangeParameterApi oder steht auf false, entfällt der Code für LinTp_ChangeParameter(), was Flash-Speicher spart.
    • Wenn LinTpMaxRxNSduCnt / LinTpMaxTxNSduCnt nicht gesetzt sind, generiert der BSW-Konfigurator Array-Dimensionen strikt aus der Zählung der tatsächlich vorhandenen LinTpRxNSdu- / LinTpTxNSdu-Instanzen.
  • RAM-Optimierung:
    • Die Kardinalität 0..* für LinTpChannelConfig erlaubt Multi-Kanal-Systeme (mehrere LIN-Cluster an einem Gateway-Knoten). Kanäle ohne TP-Bedarf erhalten keine LinTpChannelConfig, wodurch RAM-Puffer pro physischem LIN-Kanal isoliert bleiben.
  • API-Integrität:
    • Das Flag LinTpVersionInfoApi muss in sicherheitskritischen Projekten (ASIL) projektiert werden, um statische Versionsprüfungen gegen LinIf und PduR während der BSW-Initialisierungsphase (LinTp_Init) abzusichern.
