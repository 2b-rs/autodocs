1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schichten- und Datenflussdiagramm (Communication Stack Slice / Metamodell-Abstraktion) aus dem AUTOSAR System Template (AUTOSAR_TPS_SystemTemplate).
  • Technischer Zweck: Spezifikation des alternativen, schlanken Kommunikationspfads für Complex Device Driver (CDD) direkt über die Hardware-Abstraktionsschicht des Busses (Bus Interface), unter vollständiger Umgehung von Interaction Layer (Com) und Routing-Schicht (PduR).
  • Funktionale Einordnung: Dient im AUTOSAR-Systementwurf der Modellierung von proprietären, latenzkritischen, streaming-basierten oder nicht-signalorientierten Nutzlasten (UserDefinedPdu) auf ECU- und Netzwerkebene.

2. Komponenten, Entitäten & Schnittstellen

  • Schichten (Layers):
    • Oberste Ebene (Application / CDD Layer): Beherbergt den CDD, der applikationsspezifische oder komplexe Treiberlogik ausführt.
    • Communication HW Abstraction: Bus-spezifische Abstraktionsmodule (z. B. CanIf, LinIf, FrIf, EthIf).
    • Communication Drivers (MCAL): Mikrocontroller-nahe Hardware-Treiber (z. B. Can, Lin, Fr, Eth).
  • Module & Entitäten:
    • CDD (Complex Device Driver): BSW-Modul mit Zugriff auf Standard-BSW-Schnittstellen bei gleichzeitiger Freiheit zur Implementierung nicht-standardisierter Funktionalität.
    • Bus Interface: Modul zur Entkopplung der oberen Schichten von Hardware-Details, Controller-Instanzen und Transceivern; verwaltet PDU-Filterung, Sendeanforderungen und PDU-Routing.
    • Bus Driver: MCAL-Treiber zur direkten Registerbedienung der Kommunikations-Controller (Mailboxen, Puffer, Hardware-Filter).
  • PDU-Entitäten & Datenbeziehungen:
    • UserDefinedPdu (Stereotyp: Metaklasse im System Template): Repräsentiert eine Rohdaten-PDU, deren interner Aufbau nicht durch Signal-Mappings des Standard-COM-Stacks zerlegt wird. Bildet die logische Schnittstelle zwischen CDD und Bus Interface.
    • L-PDU (Data Link Layer PDU): Protokollspezifische Frame-Einheit des jeweiligen Busses (z. B. CAN-Frame mit CAN-ID/DLC, FlexRay-Slot-Payload). Wird zwischen Bus Interface und Bus Driver ausgetauscht.
    • Kardinalität/Mapping: In der Regel 1:1-Abbildung der UserDefinedPdu-Payload auf die Nutzdaten einer L-PDU (Data Link Layer SDU), optional n:1 bei spezifischen Multiplex-Mechanismen.

3. Dynamisches Verhalten & Sequenzablauf

Sendepfad (TX):
  1. PDU-Übergabe: Der CDD initiiert den Sendeauftrag durch direkten Aufruf der Bus-Interface-Transmit-API: 
    Std_ReturnType <Bus>If_Transmit(PduIdType TxPduId, const PduInfoType* PduInfoPtr);
  2. Hardware-Pufferung: Das Bus Interface validiert die TxPduId, wählt das entsprechende Hardware Transmit Handle (HTH) des Ziel-Treibers und delegiert den Aufruf synchron an den Bus Driver: 
    Std_ReturnType <Bus>_Write(<Bus>_HwHandleType Hth, const <Bus>_PduType* PduInfo);
  3. TX-Confirmation (asynchron): Nach erfolgreichem Versand auf dem Bus meldet der Bus Driver (via ISR oder Polling) <Bus>If_TxConfirmation() an das Bus Interface. Dieses ruft die konfigurierte Bestätigungs-Callback-Funktion des CDD auf: 
    void <Cdd>_TxConfirmation(PduIdType TxPduId);
Empfangspfad (RX):
  1. Frame-Detektion: Der Bus Driver empfängt die L-PDU via Hardware Receive Handle (HRH) und benachrichtigt das Bus Interface via <Bus>If_RxIndication().
  2. PDU-Filterung: Das Bus Interface prüft die Identifier- bzw. Mailbox-Zuordnung, identifiziert die konfigurierte Ziel-PDU als UserDefinedPdu und stellt fest, dass der Empfänger ein CDD ist (Upper Layer = CDD).
  3. Indikation: Das Bus Interface leitet die Payload direkt an den CDD weiter: 
    void <Cdd>_RxIndication(PduIdType RxPduId, const PduInfoType* PduInfoPtr);
Fehler- und Abbruchpfade:
  • Rückgabewert E_NOT_OK bei überlasteten Treiber-Hardware-Mailboxen erfordert Retry- oder Queue-Handling im CDD.
  • Parameterprüfungen im Bus Interface erzeugen bei ungültiger PDU-ID oder NULL-Zeigern entsprechende DET-Fehler (z. B. CANIF_E_PARAM_PDU_ID).

4. Normative Relevanz & Entwickler-Hinweise

  • Wegfall von BSW-Standarddiensten:
    • Es existiert keine automatische Signalverarbeitung, Byte-Order-Konvertierung (Endianness) oder Inhaltsvalidierung durch die Com-Schicht.
    • Kein automatisches E2E-Handling oder PDU-Gateway-Routing durch den PduR. Der CDD muss Integritätsprüfungen (CRC, Sequence Counter) sowie PDU-Serialisierung eigenständig ausführen.
  • Konfigurationsverpflichtung im BSW-Stack:
    • System Description (ARXML): Die PDU muss explizit als UserDefinedPdu instanziiert und dem System/ECU-Port des CDD zugewiesen werden.
    • Bus-Interface-Modulkonfiguration: Im Interface-Modul (z. B. CanIf) muss die entsprechende PDU als Typ USER_DEFINED mit Upper-Layer-Referenz CDD konfiguriert werden. Die Funktionsnamen für <Cdd>_RxIndication bzw. <Cdd>_TxConfirmation müssen als konfigurierbare Funktionszeiger (CanIfRxPduUserRxIndicationName / CanIfTxPduUserTxConfirmationName) statisch hinterlegt sein.
  • Echtzeiteigenschaften:
    • Reduzierter Call-Stack und minimaler Overhead; prädestiniert für hochfrequente oder latenzkritische Protokolle (z. B. Messdatenstreaming, XCP über CAN/Eth via CDD, kundenspezifische Bootloader-Kommunikation).
  • Speicher- und Reentrancy-Regeln:
    • Der CDD muss sicherstellen, dass Pufferdaten (PduInfoPtr->SduDataPtr) bis zum Abschluss des synchronen <Bus>If_Transmit()-Aufrufs stabil bleiben. Das Bus Interface übernimmt standardmäßig kein Zwischenbuffering für TX-PDUs.
