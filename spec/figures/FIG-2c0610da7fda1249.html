1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Metamodell (UML-Klassendiagramm), spezifiziert im Diagnostic Extract Template (DEXT, AUTOSAR Classic R4.2.2).
  • Technischer Zweck: Formale semantische Modellierung des UDS-Diagnosedienstes CommunicationControl (0x28) nach ISO 14229-1 zur hersteller- und werkzeugübergreifenden Parametrierung des Diagnose-Basissoftware-Stacks (DCM, BswM, ComM).
  • Funktionale Einordnung: DEXT überbrückt die Lücke zwischen OEM-Diagnosespezifikation (ODX/Authoring) und der AUTOSAR-ECU-Konfiguration (DcmDsd, DcmDsp). Das Diagramm definiert das zweistufige Entwurfsmuster aus generischer Service-Klasse (DiagnosticServiceClass) und zielsteuergerätespezifischer Instanz (DiagnosticServiceInstance) sowie die Bindung an physische Kommunikationskanäle der Systembeschreibung (CommunicationCluster aus FIBEX).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Klassenhierarchie
  • DiagnosticCommonElement (Paket/Basis-Namespace):
    • DiagnosticAccessPermission: Definiert Sicherheitsstufen, Session-Zustände und Authentifizierungsregeln zur Ausführung des Diagnosedienstes.
    • DiagnosticServiceClass (abstract): Abstrakte Basisklasse aller Diagnosedienst-Klassen ohne Attribute.
    • DiagnosticServiceInstance (abstract): Abstrakte Basisklasse für die konkrete Ausprägung eines Dienstes auf einem Steuergerät.
  • CommunicationControl-Spezialisierungen:
    • DiagnosticComControl (erbt von DiagnosticServiceInstance):
      • Attribut: customSubFunctionNumber : PositiveInteger [0..1] (OEM-spezifische Erweiterung der standardisierten UDS-Subfunktionen 0x00–0x05).
    • DiagnosticComControlClass (erbt von DiagnosticServiceClass):
      • Bündelt die Konfigurationsdaten zur Steuerung von Sende- und Empfangspfaden auf Netzwerkebene.
    • DiagnosticComControlSubNodeChannel:
      • Attribut: subNodeNumber : PositiveInteger [0..1] (Adressiert Knoten an untergeordneten Subbussen/Gateways gemäß ISO 14229-1 Parameter nodeNumber).
    • DiagnosticComControlSpecificChannel:
      • Attribut: subnetNumber : PositiveInteger [0..1] (Definiert die Teilnetzwerknummer gemäß UDS Parameter communicationType, Bits 0–3, Wertebereich 0x1–0xE).
  • System- & Netzwerkintegration:
    • CommunicationCluster (abstract): Stammt aus dem FIBEX-/System-Template (FibexElement), annotiert mit dem Stereotyp «atpVariation».
      • Attribute: baudrate : PositiveUnlimitedInteger [0..1], protocolName : String [0..1], protocolVersion : String [0..1].
Beziehungen & Kardinalitäten
  • Instanz-zu-Klasse:
    • DiagnosticServiceInstance → DiagnosticServiceClass: Assoziation +serviceClass [0..1] (Stereotyp «atpAbstract»).
    • DiagnosticComControl → DiagnosticComControlClass: Assoziation +comControlClass [0..1] mit {redefines serviceClass} (optionale Bindung an die spezialisierte Dienstklasse).
  • Zugriffsberechtigungen:
    • DiagnosticServiceInstance → DiagnosticAccessPermission: Assoziation +accessPermission [0..1].
  • Kanal-Kompositionen (DiagnosticComControlClass):
    • ◆ → DiagnosticComControlSubNodeChannel: Komposition +subNodeChannel [0..*] zur Einbindung von Subknotenkanälen.
    • ◆ → DiagnosticComControlSpecificChannel: Komposition +specificChannel [0..*] zur Einbindung spezifischer Teilnetzkanäle.
  • Cluster-Referenzen:
    • DiagnosticComControlClass → CommunicationCluster: Assoziation +allChannels [0..*] zur Adressierung aller Kommunikationscluster.
    • DiagnosticComControlSubNodeChannel → CommunicationCluster: Assoziation +subNodeChannel [0..1] zur Anbindung an ein Kommunikationscluster.
    • DiagnosticComControlSpecificChannel → CommunicationCluster: Assoziation +specificChannel [0..1] zur Anbindung an ein Kommunikationscluster.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein Metamodell handelt, manifestiert sich das statische Schema zur Laufzeit im AUTOSAR BSW-Stack in folgendem Signal- und Steuerungsablauf:

Tester           Dcm (Dsd/Dsp)                   BswM / ComM                  CanIf/FrIf/EthIf
  |                    |                              |                              |
  |-- UDS 0x28 Req --->|                              |                              |
  |   (subFunc,        |-- Session/Security Check --->|                              |
  |    comType)        |   (via DiagnosticAccess-     |                              |
  |                    |    Permission)               |                              |
  |                    |                              |                              |
  |                    |-- Decode comType:            |                              |
  |                    |   0x0: +allChannels          |                              |
  |                    |   0x1-0xE: +specificChannel  |                              |
  |                    |   0xF: +subNodeChannel       |                              |
  |                    |                              |                              |
  |                    |-- Mode Request ------------->|                              |
  |                    |   (BswM_Dcm_Communication-   |                              |
  |                    |    Mode_CurrentState)        |-- Deactivate/Activate PDU -->|
  |                    |                              |   Transmission/Reception     |
  |<-- UDS 0x28 Pos ---|                              |                              |
  1. Trigger & Zugriffskontrolle: Ein UDS-Request 0x28 trifft im PduR/DCM ein. DcmDsd validiert die Zulässigkeit anhand der im Metamodell verankerten DiagnosticAccessPermission (aktuelle Diagnostic Session, Security Access Level). Bei Nichterfüllung erfolgt NRC 0x7F (ServiceNotSupportedInActiveSession) bzw. 0x33 (SecurityAccessDenied).
  2. Subfunktions- & Parameterauswertung:
    • Auswertung des subFunction-Bytes: Standardisiert (z. B. 0x00 enableRxAndTx, 0x01 enableRxAndDisableTx, 0x03 disableRxAndTx) oder über customSubFunctionNumber.
    • Auswertung des Parameters communicationType:
      • Wert 0x0 (All Channels): Verweist auf die Liste der mit +allChannels assoziierten CommunicationCluster.
      • Werte 0x1 bis 0xE (Subnet): Lookup über DiagnosticComControlSpecificChannel.subnetNumber zur Selektion des Ziel-Clusters.
      • Wert 0xF (Sub-Node): Lookup über DiagnosticComControlSubNodeChannel.subNodeNumber zur Adressierung spezifischer Knoten an externen Schnittstellen (z. B. LIN-Slaves hinter einem Master-Gateway).
  3. BSW-Interaktion & Abbruchbedingungen:
    • Dcm setzt interne Zustände und triggert über standardisierte BSW-Schnittstellen den BswM (z. B. via BswM_Dcm_CommunicationMode_CurrentState).
    • BswM evaluiert hinterlegte Regeln (BswMRule) und steuert den ComM (ComM_RequestComMode) bzw. sperrt/entsperrt IPDU-Gruppen via PduR / Hardware-Interface (CanIf_SetPduMode).
    • Abbruch: Ist eine angeforderte subnetNumber oder subNodeNumber im DEXT nicht parametriert, generiert der DCM synchron den NRC 0x31 (RequestOutOfRange / DCM_E_REQUESTOUTOFRANGE).

4. Normative Relevanz & Entwickler-Hinweise

  • Generatorkonfiguration (DEXT-to-ECUC Transformation):
    • Die Kardinalität +allChannels [0..*] erzwingt im BSW-Konfigurator die Zuordnung zu mehreren ComMChannel-Referenzen in DcmDspComControlAllChannelsRef.
    • DiagnosticComControlSpecificChannel und DiagnosticComControlSubNodeChannel müssen 1:1 auf die entsprechenden ECUC-Container (DcmDspComControlSpecificChannel, DcmDspComControlSubNodeChannel) und deren ComMChannel-Mapping abgebildet werden.
  • Variantenmanagement:
    • Das Stereotyp «atpVariation» an CommunicationCluster erfordert vom BSW-Konfigurator die Auflösung post-build- oder pre-compile-abhängiger Systemvarianten (SystemTemplate). Ändert sich die Bus-Topologie je Derivat, werden ungenutzte Kanäle zur Compile-Zeit aus dem Dcm-Mapping exkludiert.
  • Redefinitions-Zwang:
    • Durch {redefines serviceClass} an der Assoziation +comControlClass darf eine DiagnosticComControl-Instanz ausschließlich auf eine Instanz von DiagnosticComControlClass (und keine generische DiagnosticServiceClass) verweisen; Generatoren müssen dies via OCL-Constraint/Schema-Validierung syntaktisch vorab prüfen (TPS_DEXT_01029, TPS_DEXT_01057).
  • Stack-Einschränkungen (Classic Platform):
    • Sollen Sub-Node-Kommunikationen (z. B. LIN-Cluster) unterbunden werden, muss sichergestellt sein, dass das LIN-Interface bzw. der LinSM die Deaktivierung des Sub-Node-Traffics unterstützt, da der ISO-14229-Parameter nodeNumber im DCM ansonsten ins Leere läuft oder im Applikations-SWC-Handler abgefangen werden muss.
