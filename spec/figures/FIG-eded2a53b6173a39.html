Figure 4.2: SOME/IP Header and E2E header Format

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Layout / Wire-Format-Diagramm (Bit-/Byte-Level-Paketstruktur im Big-Endian / Network-Byte-Order-Raster über 32 Bit).
  • Technischer Zweck: Definition des On-Wire-Serialisierungsformats einer SOME/IP-Nachricht bei aktiver End-to-End-(E2E)-Absicherung gemäß AUTOSAR Foundation (AUTOSAR_FO_PRS_SOMEIPProtocol).
  • Funktionale Einordnung: Bildet die Schnittstelle zwischen der Transport-/Netzwerkschicht (UDP/TCP via SoAd/Socket-API) und der Service-Kommunikation (Classic Platform SomeIpXf / Adaptive Platform ara::com). E2E fungiert als funktionale Sicherheitsschicht (ISO 26262 bis ASIL D), eingebettet unmittelbar zwischen dem standardisierten SOME/IP-Header und den serialisierten Anwendungs-Payloads.

2. Komponenten, Entitäten & Schnittstellen

Strukturaufbau des Datagramms (Bit 0 bis 31 je Zeile):

  1. Message ID (32 Bit):
    • Bits [0:15]: Service ID (16 Bit) – Eindeutiger Identifikator des angebotenen Services.
    • Bit [16]: Sub-Identifier-Flag (0 = Method, 1 = Event/Notification).
    • Bits [17:31]: Method ID bzw. Event ID (15/16 Bit).
  2. Length (32 Bit):
    • Gesamtlänge in Bytes, gezählt ab dem ersten Byte des Request ID-Feldes bis zum Ende der Payload (Header-Rest: 8 Bytes + E2E-Header-Größe + Payload-Größe). Schließt Message ID und Length selbst nicht ein (PRS_SOMEIP_00034).
  3. Request ID (32 Bit):
    • Bits [0:15]: Client ID (16 Bit) – Eindeutige Kennung des aufrufenden Clients/ECU-Endpoints.
    • Bits [16:31]: Session ID (16 Bit) – Transaktions-/Aufruf-Zähler zur Korrelation von Request/Response bzw. Detektion von Replay/Out-of-Order.
  4. Protokoll- & Routing-Parameter (je 8 Bit):
    • Protocol Version (8 Bit): SOME/IP-Standardversion (z. B. 0x01).
    • Interface Version (8 Bit): Major-Version der Service-Schnittstelle.
    • Message Type (8 Bit): Kennung des Nachrichtentyps (0x00 REQUEST, 0x01 REQUEST_NO_RETURN, 0x02 NOTIFICATION, 0x80 RESPONSE, 0x81 ERROR; ggf. mit TP-Flag 0x20).
    • Return Code (8 Bit): Status des Methodenaufrufs (0x00 E_OK, bis hin zu protokollspezifischen Fehlern 0x01–0x0F oder anwendungsdefinierten Fehlern).
  5. E2E Header (variable Größe):
    • Format und Länge hängen vom konfigurierten E2E-Profil ab (z. B. E2E Profile 04, 07 oder 11 mit typischerweise CRC32/CRC64, Length-Field und Message Counter / Sequence Counter).
    • Position: Unmittelbar nach dem SOME/IP-Header (PRS_SOMEIP_00245).
  6. Payload (variable Größe):
    • Die serialisierten Anwendungsdaten (über SOME/IP-Serializer generiert).

3. Dynamisches Verhalten & Sequenzablauf

  • Senderpfad (TX-Serialisierung & Schutz):
    1. Serialisierung der Anwendungsdaten in die Payload via SOME/IP-Transformer (SomeIpXf).
    2. Berechnung des E2E-Schutzes über E2E-Transformer (E2EXf) bzw. E2E-Library (E2E_PxxProtect): Einbindung von Data ID, Counter und CRC in den E2E Header.
    3. Assemblierung des 16-Byte SOME/IP-Headers (Message ID, Length, Request ID, Protocol/Interface Version, Message Type, Return Code).
    4. Übergabe an SoAd / Socket-Layer via PDU-Router.
  • Empfängerpfad (RX-Deserialisierung & Verifikation):
    1. Extraktion des SOME/IP-Headers; Plausibilisierung von Protocol Version, Interface Version, Length (PRS_SOMEIP_00031) und Mapping auf Client/Service-Instanz.
    2. E2E-Verifikation (E2E_PxxCheck): Validierung von Sequenzzähler, Data ID und CRC über den E2E Header und die Payload.
    3. Bei E2E-Fehler (z. B. CRC-Mismatch, Sequenzfehler, Replay): Verwerfen der Nachricht oder Weitergabe des Fehlerstatus an die Applikation (via E2E-Status-Byte); Abbruch der Funktionsverarbeitung.
    4. Bei E2E-Erfolg (E2E_P_OK / E2E_P_VALID): Deserialisierung der Payload und Dispatch an den RTE-Run-Time-Kontext bzw. Service-Skeleton.

4. Normative Relevanz & Entwickler-Hinweise

  • Längenberechnung (PRS_SOMEIP_00034): $$\text{Length-Feldwert} = 8\text{ Bytes (ab Request ID bis Return Code)} + \text{sizeof(E2E\_Header)} + \text{sizeof(Payload)}$$ Eine Fehlkonfiguration dieses Offsets führt zum sofortigen Verwerfen des Pakets durch den Empfänger-Stack.
  • Header-Platzierung & E2E-Offset (PRS_SOMEIP_00245, PRS_SOMEIP_00755):
    • Der E2E-Header liegt aus Sicht des SOME/IP-Stacks im Nutzdatenbereich (SOME/IP-Payload beginnt bei Byte-Offset 16).
    • Der E2E-Transformer muss mit einem statischen Offset konfiguriert werden, damit er den E2E-Header an Byte 16 einfügt/ausliest und die CRC über die definierten Header-Anteile (teilweise inkl. Message ID, Length, Request ID) und/oder die Payload berechnet (profilabhängige E2E-Header-Konfiguration).
  • Fragmentierung (SOME/IP-TP):
    • Wird SOME/IP-TP (Transport Protocol) über UDP genutzt, muss der E2E-Header vor der Fragmentierung berechnet werden (Schutz auf logischer Message-Ebene, nicht Fragment-Ebene). Das TP-Flag im Message Type beeinflusst das Offset hinter dem 16-Byte-Header nicht (TP-Header schiebt sich ggf. ein).
  • Endianness:
    • Der SOME/IP-Header ist strikt Big-Endian (Network Byte Order). Die Byte-Reihenfolge innerhalb des E2E-Headers (CRC, Counter) richtet sich exakt nach der Definition des verwendeten E2E-Profils (oftmals Little-Endian oder profil-spezifisch fixiert).
