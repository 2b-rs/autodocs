1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Metamodell / Klassendiagramm aus dem AUTOSAR System Template (AUTOSAR_TPS_SystemTemplate, Release R4.3.1).
  • Architektur-Kontext: Spezifikation der AUTOSAR Data Transformation Pipeline. Es definiert das Metamodell zur Konfiguration modularer Transformer (Serialization, Safety/E2E, Security/SecOC, Custom) und deren Verkettung (transformerChain) für die Inter- und Intra-ECU-Kommunikation. Das Modell verbindet System-Signale (ISignal, ISignalGroup) sowie Port-Ebene-Mappings (DataPrototypeMapping) mit den Ausführungs- und Puffereigenschaften der Transformations-Engines (RTE/BSW).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen und Attribute
  • DataTransformationSet («ARElement»):
    • Wurzelelement zur Bündelung aller Transformationstechnologien und Kettenkonfigurationen eines Systems.
    • Komposition zu TransformationTechnology (0..*, «atpVariation, atpSplitable»).
    • Komposition zu DataTransformation (0..*, «atpVariation, atpSplitable», Binding Time: codeGenerationTime).
  • DataTransformation («Identifiable»):
    • Repräsentiert eine spezifische Kette oder Einzeltransformation.

    • Aggregation +transformerChain: 0..* {ordered} geordnete Liste von TransformationTechnology-Instanzen.
  • TransformationTechnology («Identifiable»):
    • Deklariert das eingesetzte Transformationsmodul bzw. Protokoll.
    • Attribute:
      • hasInternalState : Boolean [0..1]: Gibt an, ob der Transformer zustandsbehaftet ist.
      • needsOriginalData : Boolean [0..1]: Kennzeichnet, ob für den Transformationsschritt Zugriff auf die unmodifizierten Originaldaten nötig ist.
      • protocol : String [0..1]: Name des Protokolls.
      • transformerClass : TransformerClassEnum [0..1]: Klassifikation via Enumeration (serializer, safety, security, custom).
      • version : String [0..1]: Protokoll-/Transformer-Versionsstand.
    • Kompositionen:

      • +transformationDescription: 0..1 TransformationDescription («Describable», «atpVariation, atpSplitable», Binding Time: postBuild).
  • BufferProperties:

    • inPlace : Boolean [0..1]: In-Place-Überschreibung oder separater Puffer.
  • CompuScale («atpVariation»):

  • TransformationISignalProps («Describable», «atpVariation», Binding Time: postBuild):
    • Signal- bzw. signalspezifische Parametrierung für eine bestimmte TransformationTechnology.
    • csErrorReaction : CSTransformerErrorReactionEnum [0..1]: Fehlerreaktionsstrategie bei Client-Server-Aufrufen.
    • Assoziation +transformer: 0..1 TransformationTechnology.

3. Dynamisches Verhalten & Sequenzablauf

Obwohl als statisches Strukturdiagramm dargestellt, erzwingen die Metaklassen eine strikte Laufzeit-Ausführungsreihenfolge:

  1. Serialisierungs- und Enkodierungspfad (Sender / Client):
    • Strikte Sequenz: Durch {ordered} an transformerChain werden Daten linear transformiert.
    • Typische Kaskadierung: Applikations-Datentyp → serializer (SOME/IP) → safety (E2E CRC/Counter) → security (SecOC MAC).
    • Pufferallokation: Vor Ausführung evaluiert die RTE die BufferProperties. Falls inPlace == false, wird ein neuer Puffer der berechneten Größe (ggf. unter Berücksichtigung von headerLength und bufferComputation) bereitgestellt.
    • Sonderpfad: Bei fehlenden Daten entscheidet executeDespiteDataUnavailability, ob die Kette abgebrochen wird oder mit Dummy-/Default-Payload ausgeführt wird (z. B. zur Aufrechterhaltung des zyklischen E2E-Alive-Counters).
  2. Deserialisierungs- und Prüfpfad (Empfänger / Server):
    • Die Kette wird invers durchlaufen: Validierung security → Prüfung safety → Deserialisierung via serializer.
    • Tritt während der Transformation ein Verifikationsfehler auf, greift für Client-Server-Calls die in TransformationISignalProps.csErrorReaction definierte Strategie (z. B. Rückgabe eines spezifischen RTE-Transformationsfehlers an den Aufrufer).

4. Normative Relevanz & Entwickler-Hinweise

  • Optionale Kardinalitäten:
    • Kettenordnung transformerChain besitzt Kardinalität 0..* {ordered} (leere Kettenkonfiguration zulässig).
    • BufferProperties an TransformationTechnology ist optional (0..1).
    • Assoziation transformer an TransformationISignalProps ist optional (0..1).
    • Attribute wie executeDespiteDataUnavailability, protocol, transformerClass, version, headerLength, inPlace, dataTypePolicy und length sind optional ([0..1]).
  • Designelement-Klassifikation:
    • ISignal und ISignalGroup tragen zusätzlich die Klassifikation UploadableDesignElement.
  • Variabilität & Spaltbarkeit:
    • Spaltung und späte Bindung (codeGenerationTime) für Transformation-Zuordnungen an ISignal und ISignalGroup.
    • Post-Build-Bindung für TransformationISignalProps und TransformationDescription.
    • Kompositionen transformationISignalProps und transformationDescription sind «atpSplitable».
