1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / AUTOSAR ECU Configuration Parameter Definition Metamodell (BSW Module Configuration Definition, EcucModuleDef).
  • Architektur-Ebene: Basic Software (BSW), Microcontroller Abstraction Layer (MCAL) / Diagnostic Services (RamTst-Treiber).
  • Technischer Zweck: Formale Strukturierung der XML-Konfigurationsparameter (ARXML) für das BSW-Modul RamTst. Definiert die strukturelle Schachtelung der Konfigurationscontainer, deren Kardinalitäten und Abhängigkeiten als Basis für Validierungstools und C-Code-Generatoren (Generierung von RamTst_Cfg.h, RamTst_PBcfg.c / RamTst_Lcfg.c).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Stereotypen
  • RamTst : ModuleDef
    • Rolle: Wurzelknoten der BSW-Moduldefinition.
    • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = 1 (Modul ist optional pro ECU-Konfiguration, darf maximal einmal instanziiert werden).
  • RamTstCommon : ParamConfContainerDef
    • Rolle: Top-Level-Konfigurationscontainer für modulweite, globale Grundeinstellungen (Pre-Compile-Parameter, z. B. Versionsabfrage, DevErrorDetect, globale Handler).
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = 1.
  • RamTstAlgorithms : ParamConfContainerDef
    • Rolle: Subcontainer zur Auswahl und Aktivierung der hardware- bzw. treiberseitig verfügbaren RAM-Test-Algorithmen (z. B. March-Tests, Checkerboard, Walkpath).
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = 1.
  • RamTstConfigParams : ParamConfContainerDef
    • Rolle: Subcontainer zur Definition der konkreten Test-Konfigurationssätze (Configuration Sets / Post-Build- bzw. Link-Time-Parameterstrukturen).
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = 1.
  • RamTstAlgParams : ParamConfContainerDef
    • Rolle: Parametrisierung eines spezifischen Testalgorithmus innerhalb des Konfigurationssatzes (Algorithmus-ID, Ausführungsmodus destruktiv/nicht-destruktiv).
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = * (mindestens ein parametrisierter Algorithmus erforderlich).
  • RamTstBlockParams : ParamConfContainerDef
    • Rolle: Konfiguration konkreter RAM-Speicherblöcke (physische Start-/Endadresse, Blocklänge, Testmuster, Iterationsschrittweiten, Ausführungsintervall).
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = * (pro Algorithmus muss mindestens ein physischer Block zugewiesen sein).
Beziehungen & Aggregationshierarchie
  • Alle Beziehungen sind als strikte Kompositionen (+container bzw. +subContainer) modelliert: $$\text{RamTst [0..1]} \xrightarrow{\text{+container}} \text{RamTstCommon [1..1]}$$
  • RamTstCommon verzweigt orthogonal in zwei Pflichtstränge (+subContainer):
    1. $\text{RamTstCommon} \xrightarrow{\text{+subContainer [1..1]}} \text{RamTstAlgorithms}$ (Funktionsumfang/Algorithmen-Pool).
    2. $\text{RamTstCommon} \xrightarrow{\text{+subContainer [1..1]}} \text{RamTstConfigParams}$ (Ausführungsparameter).
  • Kaskadierte 1:n-Beziehung im Ausführungsstrang: $$\text{RamTstConfigParams} \xrightarrow{\text{+subContainer [1..]}} \text{RamTstAlgParams} \xrightarrow{\text{+subContainer [1..]}} \text{RamTstBlockParams}$$

3. Dynamisches Verhalten & Sequenzablauf

  • Laufzeit-Dynamik im Diagramm: Keine (statisches Metamodell für Konfigurationsdeskriptoren).
  • Abgeleitete BSW-Laufzeitauswirkung:
    • Init-Phase: RamTst_Init(&RamTst_Config) wertet die über RamTstConfigParams generierten Datenstrukturen aus.
    • Scheduler/Task-Ebene: RamTst_MainFunction() iteriert sequenziell oder zeitgeteilt (Slice-based) über die in RamTstAlgParams definierten Algorithmen und arbeitet die in RamTstBlockParams hinterlegten Speicherbereiche ab.
    • Fehlerpfade & Benachrichtigung: Bei Detektion eines Bitkippers / RAM-Fehlers während der Blockabarbeitung wird ein konfigurierter Notification-Callback aufgerufen bzw. der Fehler an das DEM (Diagnostic Event Manager) oder DET (Default Error Tracer) gemeldet.

4. Normative Relevanz & Entwickler-Hinweise

  • Generierungsvertrag:
    • Die Schachtelungshierarchie erzwingt im C-Header ein geschachteltes Typedef-Konstrukt: 
      typedef struct {
    uint32 RamTstStartAddress;
    uint32 RamTstEndAddress;
    /* weitere Block-Parameter */
} RamTst_BlockConfigType;

typedef struct {
    RamTst_AlgorithmIdType RamTstAlgorithmId;
    uint32 RamTstNumberOfBlocks;
    const RamTst_BlockConfigType* RamTstBlockParams;
} RamTst_AlgConfigType;

typedef struct {
    uint32 RamTstNumberOfAlgorithms;
    const RamTst_AlgConfigType* RamTstAlgParams;
} RamTst_ConfigType;
  • Kardinalitäts-Restriktionen:
    • Kein Algorithmus darf ohne mindestens einen zugeordneten Block definiert werden (RamTstBlockParams Multiplicity 1..*).
    • Konfigurationen ohne aktiven Testalgorithmus sind schema-ungültig (RamTstAlgParams Multiplicity 1..*).
  • Embedded- & Safety-Constraints:
    • Adressvalidierung: Bei destruktiven Tests müssen die in RamTstBlockParams konfigurierten Bereiche strikt gegen Stack-, OS-Kontext- und MPU-geschützte Regionen gegengeprüft werden (Gefahr von HardFaults / Memory Overwrites).
    • Cache-Kohärenz: Bei Controllern mit D-Cache müssen Adressgrenzen in RamTstBlockParams an Cache-Line-Größen ausgerichtet werden (Cache Invalidation / Flush vor/nach Testlauf).
