1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (M2-Metamodell-Ausschnitt der AUTOSAR Software Component Template, TPS SWCT).
  • Technischer Zweck: Spezifikation der strukturellen Kopplung zwischen dem internen Verhalten einer atomaren Software-Komponente (SwcInternalBehavior), ihren ausführbaren Code-Einheiten (RunnableEntity) und den Steuerungsereignissen der Laufzeitumgebung (RTEEvent).
  • Architektur-Einordnung: Schnittstelle zwischen AUTOSAR-Authoring (M1-ARXML-Modell) und RTE-Code-Generierung. Es definiert das Ausführungs- und Synchronisationsmodell für C-Funktionen (RunnableEntity) unter Berücksichtigung von asynchroner Ereignissteuerung (startOnEvent) und synchronem Blockieren (WaitPoint) für Kategorie-1- und Kategorie-2-Runnables im OSEK/VDX- bzw. AUTOSAR-OS-Task-Kontext.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen und Attribute
  • SwcInternalBehavior (erbt von InternalBehavior):
    • Aggregationswurzel für das Komponentenverhalten.
    • handleTerminationAndRestart: HandleTerminationAndRestartEnum [0..1]: Definiert das optionale Verhalten bei Terminierung und Neustart der Instanz.
    • supportsMultipleInstantiation: Boolean [0..1]: Steuert optional, ob mehrere Instanzen des Komponenten-Typs auf einem oder mehreren ECUs parallel allokiert werden dürfen.
  • RunnableEntity (erbt von ExecutableEntity, AtpStructureElement):
    • Kleinste ausführbare C-Code-Einheit einer SW-C.
    • canBeInvokedConcurrently: Boolean [0..1]: Signalisiert optional Reentranzfähigkeit; bestimmt, ob die Funktion nebenläufig mehrfach aktiv sein darf.
    • symbol: CIdentifier [0..1]: Optionaler generierter C-Funktionsname (Entry-Point).
  • RTEEvent (erbt von AbstractEvent, AtpStructureElement):
    • Abstrakte Basisklasse für alle RTE-Aktivierungsereignisse (z. B. TimingEvent, DataReceivedEvent, OperationInvokedEvent).
  • WaitPoint (erbt von Identifiable):
    • Blockierpunkt innerhalb einer RunnableEntity.
    • timeout: TimeValue [0..1]: Maximal zulässige Wartezeit auf das auslösende Ereignis vor Rückkehr mit Timeout-Fehlercode.
Beziehungen, Kardinalitäten & Stereotypen
  • SwcInternalBehavior → RunnableEntity:
    • Komposition, Rollenname +runnable, Kardinalität 0..*.
    • Stereotypen: «atpVariation, atpSplitable» (Variation bis vh.latestBindingTime = preCompileTime; Definition kann über mehrere ARXML-Dateien gesplittet werden).
  • SwcInternalBehavior → RTEEvent:
    • Komposition, Rollenname +event, Kardinalität *.
    • Stereotypen: «atpVariation, atpSplitable» (Variation bis vh.latestBindingTime = preCompileTime).
  • RTEEvent → RunnableEntity (+startOnEvent):
    • Assoziation von RTEEvent auf RunnableEntity, Kardinalität 0..1.
    • Semantik ([TPS_SWCT_1317]): Tritt das RTEEvent auf, stößt die RTE die zugeordnete RunnableEntity an. Ein RTEEvent triggert maximal eine RunnableEntity.
  • RunnableEntity → WaitPoint (+waitPoint):
    • Komposition von RunnableEntity auf WaitPoint, Kardinalität *.
    • Existenz mindestens eines WaitPoint klassifiziert die RunnableEntity formal als Kategorie-2-Runnable.
  • WaitPoint → RTEEvent (+trigger):
    • Gerichtete Assoziation von WaitPoint auf RTEEvent, Kardinalität 0..1 am Event, * am WaitPoint.
    • Semantik ([TPS_SWCT_1318]): Ein optional referenziertes RTEEvent dient als Weck-Trigger zur Deblockierung des spezifischen WaitPoint.

3. Dynamisches Verhalten & Sequenzablauf

Asynchroner Triggerpfad (Start-Triggering via startOnEvent)
  1. Ereigniseintritt: Ein konkretes RTEEvent (z. B. periodischer Alarm über OS-Counter für TimingEvent oder PDU-Empfang via Com/RTE für DataReceivedEvent) tritt ein.
  2. Task-Aktivierung / Dispatch:
    • Ist das Event einer Kategorie-1-Runnable zugeordnet, aktiviert die RTE den zugeordneten OS-Basic- oder Extended-Task (ActivateTask()) bzw. führt die Funktion direkt aus dem Task-Körper sequenziell aus.
    • Bei canBeInvokedConcurrently == false stellt die RTE sicher, dass keine parallele Instanz ausgeführt wird (Reentranz-Schutz).
Synchroner Warte- und Deblockierungspfad (Blocking via WaitPoint)
  1. Initialisierung/Start: Die Runnable wird initial über ein startOnEvent gestartet (Extended Task erforderlich).
  2. Blockierphase: Die Runnable ruft die generierte RTE-API (z. B. Rte_WaitGetClearEvent(...)) auf. Die RTE versetzt den Extended Task via WaitEvent() in den OS-Zustand WAITING.
  3. Timeout-Überwachung: Zeitgleich startet die RTE die Timeout-Überwachung mit der Dauer timeout: TimeValue.
  4. Deblockierungs-Kriterien:
    • Pfad A (Trigger feuert): Das über +trigger verknüpfte RTEEvent tritt ein → RTE setzt das entsprechende OS-Event (SetEvent()) → OS versetzt Task in READY → Runnable erwacht und setzt Ausführung mit Rückgabewert RTE_E_OK fort.
    • Pfad B (Timeout): Das Ereignis bleibt aus und timeout läuft ab → RTE deblockiert die Runnable mit Rückgabewert RTE_E_TIMEOUT.

4. Normative Relevanz & Entwickler-Hinweise

  • Kategorie-1 vs. Kategorie-2 Runnables:
    • Besitzt eine RunnableEntity keine WaitPoint-Instanzen (waitPoint-Multiplizität 0), handelt es sich um eine Kategorie-1-Runnable. Sie darf in Basic Tasks ohne Wartezustand ausgeführt werden und kehrt nach Abarbeitung stets vollständig zur RTE zurück.
    • Besitzt eine RunnableEntity mindestens einen WaitPoint, wird sie zwingend als Kategorie-2-Runnable eingestuft. Sie erfordert die Zuordnung zu einem Extended Task des AUTOSAR OS, da sie den Task-Kontext durch Warten auf Events synchron suspendieren kann.
  • Restriktionen & Kardinalitäten:
    • Eine SwcInternalBehavior kann auch ohne RunnableEntity-Instanzen definiert werden (0..*), beispielsweise bei reinen Kalibrier- oder Parameter-Komponenten.
    • Ein RTEEvent kann höchstens eine RunnableEntity über +startOnEvent (0..1) starten. Mehrere Events können jedoch dieselbe RunnableEntity aktivieren.
    • Ein WaitPoint kann optional ein RTEEvent (+trigger: 0..1) referenzieren. Ist kein Event hinterlegt, fungiert der WaitPoint als reines zeitgesteuertes Warten über das timeout-Attribut.
  • Timeout-Handhabung:
    • Das Attribut timeout am WaitPoint ist mit [0..1] modelliert und definiert die obere Zeitschranke. Läuft die Wartezeit ohne Eintreffen des RTEEvent ab, generiert die RTE eine Timeout-Rückmeldung an die aufrufende C-Funktion.
  • Multi-Instanziierung und Reentranz:
    • Ist supportsMultipleInstantiation == true, müssen alle Runnables reentrant programmiert sein. Dies erfordert canBeInvokedConcurrently == true oder die strikte Vermeidung gemeinsam genutzter statischer C-Variablen.
