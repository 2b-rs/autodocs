1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Objektdiagramm / Metamodell-Instanzdiagramm der AUTOSAR ECU Configuration (ECUC).
  • Technischer Zweck: Spezifikationsbeispiel für das PDU-Referenzierungs- und Kopplungskonzept (PDU Linking) im Empfangspfad (Rx) von CanIf über PduR zu Com.
  • Architektonische Einordnung: Veranschaulicht, wie die modular isolierten BSW-Konfigurationscontainer (CanIf, PduR, Com) über eine gemeinsame abstrakte System-PDU (System_Pdu) aus dem System Description / ECU Extract konsistent verknüpft und zur Generierung statischer Routing- und Handle-Tabellen aufgelöst werden.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Container & Instanzen
  • System_Pdu : Container:
    • Globales PDU-Objekt auf System-/ECU-Extract-Ebene. Dient als systemweiter Ankerpunkt und eindeutiger Identifikator zur Kopplung aller modulspezifischen PDU-Sichten.
  • ComIPdu : Container (Modul Com):
    • Repräsentiert die I-PDU im AUTOSAR COM-Stack.
    • PduIdRef : ReferenceValue → Referenziert System_Pdu.
    • ComRxIPduHandleId : IntegerValue (Wert = 3) → Lokale Modul-Handle-ID, mit welcher das COM-Modul die PDU bei Com_RxIndication identifiziert.
  • PduRRoutingPath : Container (Modul PduR):
    • Kapselt den Routing-Pfad zwischen Quell- und Ziel-PDU.
    • PduRSrcPdu : Container:
      • SrcPduRef : ReferenceValue → Referenziert System_Pdu.
      • HandleId : IntegerValue (Wert = 17) → PduR-interne Rx-PDU-ID, die von der unteren Schicht (CanIf) beim Aufruf übergeben wird.
    • PduRDestPdu : Container:
      • DestPduRef : ReferenceValue → Referenziert System_Pdu. Bestimmt das Routing-Ziel (Com).
  • CanIfCanRxPduId : Container (Modul CanIf):
    • Repräsentiert die empfangene CAN-PDU im CAN Interface.
    • PduIdRef : ReferenceValue → Referenziert dieselbe System_Pdu.
Beziehungen & Stereotypen
  • Kompositionen (ausgefüllte Rauten): Strikte Eigentümerbeziehung der Konfigurationsparameter (ReferenceValue, IntegerValue) und Sub-Container (PduRSrcPdu, PduRDestPdu) zu ihren übergeordneten Modul-Containern.
  • Referenzen (offene Pfeilspitzen): M:1-Beziehungen der modulspezifischen Referenzwerte (PduIdRef, SrcPduRef, DestPduRef) auf die gemeinsame Instanz System_Pdu.

3. Dynamisches Verhalten & Sequenzablauf

Aus der dargestellten Konfiguration resultiert zur Laufzeit folgende synchrone Rx-Aufrufkette:

[CAN Controller] 
       │ (Interrupt / Polling)
       ▼
[CanIf]  CanIf_RxIndication(CanId / HRH)
       │  Resolviert CanIfCanRxPduId -> verknüpft mit PduRSrcPdu.HandleId = 17
       ▼
[PduR]   PduR_CanIfRxIndication(RxPduId = 17, PduInfoPtr)
       │  Lookup in PduR-Routing-Table über Index 17:
       │  Zielmodul = COM, Ziel-ID = ComRxIPduHandleId (3)
       ▼
[Com]    Com_RxIndication(RxPduId = 3, PduInfoPtr)
       │  Entpacken der Signale in I-PDU- / Shadow-Buffer
       ▼
[RTE / SWC] (Signalbasierte Benachrichtigung / Data Read)
  1. CAN-Empfang & ID-Mapping (CanIf): CAN-Treiber meldet Frame an CanIf. CanIf filtert Hardware Receive Handle (HRH)/CAN-ID und ordnet den Frame CanIfCanRxPduId zu.
  2. Aufruf PduR: Der BSW-Generator generiert im CanIf für diese PDU die Ziel-ID 17. CanIf ruft synchron PduR_CanIfRxIndication(17, &PduInfo) auf.
  3. PduR-Routing: Der PduR nutzt die ID 17 als Direktindex in seine Routing-Tabelle. Er liest das konfigurierte Ziel Com und die Ziel-Handle-ID 3 aus.
  4. Aufruf COM: PduR dispatcht synchron zu Com_RxIndication(3, &PduInfo).
  5. Fehlerbehandlung: Stimmt die PDU-Länge nicht mit der konfigurierten DLC/Länge überein oder ist der Handle-Index ≥ konfigurierter Maximalanzahl, erfolgt ein Aufruf von Det_ReportError(..., PDUR_E_PDU_ID_INVALID).

4. Normative Relevanz & Entwickler-Hinweise

  • Entkopplung der BSW-Generatoren:
    • Weder Entwickler noch Generator-Tools müssen herstellerspezifische Abhängigkeiten zwischen Modulen pflegen. Das BSW-Generator-Framework (z. B. Tresos, DaVinci, DaVinci Configurator) löst Abhängigkeiten vollautomatisch über den gemeinsamen Verweis auf System_Pdu auf.
  • Zero-Based Contiguous Indexing (Array-Optimierung):
    • ComRxIPduHandleId (value = 3) und HandleId (value = 17) müssen im jeweiligen Modul fortlaufend ab 0 vergeben werden (0 .. N-1). Dies ermöglicht performante O(1)-Direktzugriffe über Lookup-Tables (LUT) in C ohne Sparse-Array-Overhead.
  • Statische Tabellengenerierung im PduR:
    • Im generierten Code von PduR_PBcfg.c / PduR_Lcfg.c existiert ein Array von Funktionszeigern/Routing-Deskriptoren, bei dem Position 17 fest mit dem Funktionspointer &Com_RxIndication und dem Parameter 3 initialisiert ist: 
      /* Beispielhafte PduR-Routingtabelle */
const PduRRoutingPathType PduR_RxRoutingTable[NUM_RX_PDUS] = {
    /* ... */
    [17] = {
        .TargetFctPtr = &Com_RxIndication,
        .TargetPduId  = 3
    },
    /* ... */
};
  • Release-spezifischer Kontext (R3.x vs. R4.x):
    • Das Diagramm repräsentiert die vereinfachte Metamodellstruktur aus AUTOSAR R3.0/R3.1. In AUTOSAR 4.x wurde die Metamodell-Hierarchie weiter aufgeteilt (ISignalIPdu, PduRRoutingTable, PduRSrcPdu / PduRDestPdu mit PduRef statt reinem System_Pdu). Das Prinzip der ID-Auflösung über referenzierte System-PDUs blieb jedoch identisch.
