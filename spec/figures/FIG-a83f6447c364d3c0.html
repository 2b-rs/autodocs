1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / AUTOSAR-Metamodellausschnitt (M2) der System Template Spezifikation (AUTOSAR_TPS_SystemTemplate).
  • Funktionale Einordnung: Definiert die formalen Datenstrukturen zur Konfiguration der Timing- und State-Machine-Parameter für den SOME/IP Service Discovery (SD) Server. Das Metamodell bildet die Brücke zwischen der logischen Servicebereitstellung (ProvidedServiceInstance), dem Event-Handling (EventHandler) und den deterministischen Netzwerk-Timing-Parametern der SD-Nachrichten auf Ethernet/UDP.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • AbstractServiceInstance (abstrakt, «Identifiable»): Basisklasse für Service-Instanzen; kapselt majorVersion: PositiveInteger [0..1]. Besitzt eine Komposition +capabilityRecord (0..*, «atpVariation,atpSplitable») auf TagWithOptionalValue (key: String, sequenceOffset: Integer [0..1], value: String [0..1]) für optionale Key-Value-Metadaten inklusive Reihenfolgeversatz.
  • ProvidedServiceInstance (spezialisiert AbstractServiceInstance): Repräsentiert die server- bzw. anbieterseitige Service-Instanz.
    • Attribute: autoAvailable: Boolean [0..1], instanceIdentifier: PositiveInteger [0..1], serviceIdentifier: PositiveInteger [0..1], minorVersion: PositiveInteger [0..1], priority: PositiveInteger [0..1], loadBalancingPriority: PositiveInteger [0..1], loadBalancingWeight: PositiveInteger [0..1].
    • Assoziation: +sdServerTimerConfig (0..1, «atpVariation,atpSplitable») referenziert SomeipSdServerServiceInstanceConfig.
    • Komposition: +eventHandler (0..*, «atpVariation,atpSplitable») besitzt EventHandler.
  • EventHandler («Identifiable»): Kapselt die serverseitige Event-Verwaltung einer Service-Eventgruppe.
    • Attribute: eventGroupIdentifier: PositiveInteger [0..1], multicastThreshold: PositiveInteger [0..1] (Schwellwert zur Umschaltung von Unicast- auf Multicast-Übertragung).
    • Assoziation: +sdServerEgTimingConfig (0..1, «atpVariation,atpSplitable») referenziert SomeipSdServerEventGroupTimingConfig.
  • SomeipSdServerServiceInstanceConfig («ARElement»): Eigenständiges, paketierbares Konfigurationselement für Service-Instanz-Timing.
    • Attribute: offerCyclicDelay: TimeValue [0..1] (Zykluszeit im Repetition/Main-Phase-Zustand), priority: PositiveInteger [0..1], serviceOfferTimeToLive: PositiveInteger (Gültigkeitsdauer des Offers in Sekunden, Pflichtfeld).
    • Komposition: +initialOfferBehavior (0..1) bindet InitialSdDelayConfig; +requestResponseDelay (0..1) bindet RequestResponseDelay.
  • SomeipSdServerEventGroupTimingConfig («ARElement»): Paketierbares Konfigurationselement für das Eventgruppen-spezifische Server-Timing.
    • Komposition: +requestResponseDelay (0..1) bindet RequestResponseDelay.
  • InitialSdDelayConfig: Definiert das Verteilungsintervall vor dem ersten Senden sowie Repetitions.
    • Attribute: initialDelayMinValue: TimeValue, initialDelayMaxValue: TimeValue, initialRepetitionsBaseDelay: TimeValue [0..1], initialRepetitionsMax: PositiveInteger [0..1].
  • RequestResponseDelay: Definiert Jitter-/Antwortzeitfenster für asynchrone Antworten.
    • Attribute: minValue: TimeValue, maxValue: TimeValue.
Metamodell-Beziehungen & Variationspunkte
  • Sowohl SomeipSdServerServiceInstanceConfig als auch SomeipSdServerEventGroupTimingConfig sind wiederverwendbare ARElement-Objekte (M:N-Wiederverwendung über mehrere Service-Instanzen hinweg).
  • Alle wesentlichen Assoziationen und aggregierten Rollen (+capabilityRecord, +eventHandler, +sdServerTimerConfig, +sdServerEgTimingConfig) sind als splitbare Variationspunkte («atpVariation,atpSplitable») ausgelegt.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die Konfigurationsbasis für die standardisierte SOME/IP-SD Server State Machine (gemäß AUTOSAR SWS Service Discovery):

stateDiagram-v2
    [*] --> DownPhase: Service Unavailable
    DownPhase --> InitialPhase: Service Available (autoAvailable=true / API)
    
    state InitialPhase {
        [*] --> InitialWait: Random Delay [initialDelayMinValue, initialDelayMaxValue]
        InitialWait --> RepetitionPhase: Send 1st Offer
        RepetitionPhase --> RepetitionPhase: Exponential Backoff (initialRepetitionsBaseDelay * 2^n)\nbis initialRepetitionsMax
    }

    InitialPhase --> MainPhase: initialRepetitionsMax erreicht
    
    state MainPhase {
        [*] --> CyclicOffer: Sende OfferService alle offerCyclicDelay mit TTL
    }

    state "Request-Response Handling" as Async {
        RxFindService --> TxOfferService: Delay t in [minValue, maxValue] (InstanceConfig)
        RxSubscribe --> TxSubscribeAck: Delay t in [minValue, maxValue] (EventGroupConfig)
    }

    MainPhase --> DownPhase: StopOffer / Service Down
    InitialPhase --> DownPhase: Service Down
  1. Initial Phase (Phasenverschiebung / Anti-Burst):
    • Sobald die Service-Instanz verfügbar wird (autoAvailable == true oder via Sd_ServerServiceSetState(..., SD_SERVER_SERVICE_AVAILABLE)), wartet der Server eine pseudo-zufällige Zeitspanne im Intervall [initialDelayMinValue, initialDelayMaxValue]. Dies verhindert Broadcast-Spitzen/Synchronisation beim gleichzeitigen Hochlauf mehrerer Steuergeräte.
    • Falls konfiguriert (initialRepetitionsMax > 0), schließt sich eine Repetition-Phase an: OfferService-Nachrichten werden mit exponentiellem Backoff basierend auf initialRepetitionsBaseDelay versendet.
  2. Main Phase (Zyklisches Halten der Session):
    • Periodischer Versand von OfferService-Nachrichten mit Periode offerCyclicDelay.
    • Jede Nachricht transportiert im Header den Eintrag serviceOfferTimeToLive (TTL). Empfangende Clients verwerfen die Routen nach Ablauf dieses Timers, falls keine Erneuerung eintrifft.
  3. Reaktive Antwortpfade (Request-Response Delays):
    • Eingehendes FindService (Unicast oder Multicast) vom Client → Antwort (OfferService) erfolgt verzögert nach einer randomisierten Zeitspanne [minValue, maxValue] aus SomeipSdServerServiceInstanceConfig.requestResponseDelay.
    • Eingehendes SubscribeEventgroup vom Client → Antwort (SubscribeEventgroupAck bzw. Nack) erfolgt verzögert nach einer Zeitspanne [minValue, maxValue] aus SomeipSdServerEventGroupTimingConfig.requestResponseDelay.
  4. Multicast-Umschaltung:
    • Sobald die Anzahl registrierter Abonnenten einer Eventgruppe den Wert multicastThreshold erreicht, wird für nachfolgende Event-Aussendungen anstelle individueller Unicasts die konfigurierte Multicast-Adresse genutzt.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Stack-Konfiguration (Classic Platform - Modul Sd):
    • Die Metaklassen werden im System-Extract zu den EcuC-Containern SdServerServiceInstance und SdServerEventGroup aufgelöst.
    • serviceOfferTimeToLive muss zwingend konsistent zu offerCyclicDelay konfiguriert werden (Regel: $\text{serviceOfferTimeToLive} \ge 3 \times \text{offerCyclicDelay}$), um Link-Loss / Service-Flapping bei Paketverlust auf Ethernet-Ebene zu vermeiden.
  • Validierungs- und Konsistenzregeln:
    • Für alle Delay-Elemente gilt formal: minValue ≤ maxValue bzw. initialDelayMinValue ≤ initialDelayMaxValue. Eine Verletzung muss vom Generator/Config-Validator als fataler Konfigurationsfehler abgewiesen werden.
    • Wenn initialRepetitionsMax > 0, muss initialRepetitionsBaseDelay konfiguriert sein.
  • Adaptive Platform (ara::com / Daemon):
    • Entspricht den JSON/ARXML-Deployment-Attributen für das SOME/IP-Binding des Service-Daemons (SomeipSdServerTimingConfig).
  • Echtzeit- und Latenz-Einfluss:
    • Zu große maxValue-Werte im requestResponseDelay führen zu langen Verbindungsaufbau-Latenzen auf Client-Seite (IPC-/RPC-Timeouts beachten).
    • Ein Wert von 0 für minValue und maxValue erzwingt die sofortige Antwortverarbeitung im Task-Kontext des SD-Stacks, birgt jedoch die Gefahr von Ethernet-Kollisionen bei gleichzeitigen Anfragen multipler ECUs.
