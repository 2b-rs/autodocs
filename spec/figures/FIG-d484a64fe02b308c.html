1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: SPEM 2.0 (Software & Systems Process Engineering Metamodel) Activity Breakdown / Process Decomposition Diagram innerhalb der AUTOSAR-Methodologie (AUTOSAR TR Methodology, R4.0.3, Kap. 2.9.3).
  • Technischer Zweck: Formale hierarchische Dekomposition des Use Cases Memory Mapping Overview in diskrete Arbeitsschritte (Tasks) zur modellbasierten Generierung von Memory-Mapping-Headern (MemMap.h) sowie der anschließenden Source-Kompilierung.
  • Architektonische Einordnung: Löst die hardware- und compilerspezifische Allokation von Code- und Datensektionen von der Implementierung der BSW-Module und Software Components (SWC). Die AUTOSAR-Methodologie endet normativ mit der Übersetzung der Quelltexte (Compile ECU Source Code); die nachgelagerte physische Sektionsplatzierung via Linker-Skripte ist explizit herstellerspezifisch und nicht Bestandteil der AUTOSAR-Standard-Methodologie.

2. Komponenten, Entitäten & Schnittstellen

  • Aktivitäts-Container (Composite Activity):
    • Memory Mapping Overview: Wurzelaktivität des Use Cases, dargestellt als SPEM-Aktivitäts-Icon (Rolle, Artefakt, Task).
  • Tasks / Arbeitsschritte (SPEM Task Definitions / TaskUses):
    • Define Memory Addressing Modes: Festlegung der compiler- und zielplattformspezifischen Adressierungsmodi (z. B. NEAR, FAR, bitadressierbar).
    • Configure Memmap Allocation: Zuordnung logischer Speichersektionen (SwAddrMethod, MemorySection) zu realen Speicher- und Adressierungsarten im Modell.
    • Generate BSW Memory Mapping Header: Generierung der BSW-spezifischen Mapping-Header (z. B. <BswModule>_MemMap.h) aus der BSW Module Description (BSWMD).
    • Generate SWC Memory Mapping Header: Generierung der komponentenspezifischen Mapping-Header aus der Software Component Description (SWCD / SwcInternalBehavior).
    • Compile BSW Core Code: Kompilierung der Basissoftware-C-Dateien unter Einbindung der generierten BSW-MemMap-Header.
    • Compile Atomic Software Component: Kompilierung des SWC-Applikationscodes gegen die generierten SWC-MemMap-Header und RTE-Schnittstellen.
    • Compile ECU Source Code: Gesamtheitliche Kompilierung/Aggregation aller ECU-Quellen als finaler Schritt des Use Cases.
  • Beziehungen & Stereotypen:
    • Stereotyp «nesting»: Gerichtete Aggregationsbeziehungen (gekennzeichnet durch offene Rauten an Memory Mapping Overview). Modelliert die formale Zerlegung der übergeordneten Aktivität in sieben Teiltasks ohne direkte Datenfluss- oder Kontrollflusssemantik auf dieser Abstraktionsebene.

3. Dynamisches Verhalten & Sequenzablauf

Obgleich das Diagramm eine statische Strukturzerlegung darstellt, leitet sich der methodische Workflow (gemäß TR Methodology Kap. 2.9.3 / Folgediagramm Fig. 2.47) chronologisch ab:

[Define Memory Addressing Modes] 
           │
           ▼
[Configure Memmap Allocation]
           │
     ┌─────┴────────────────────────────────┐
     ▼                                      ▼
[Generate BSW Memory Mapping Header]   [Generate SWC Memory Mapping Header]
     │                                      │
     ▼                                      ▼
[Compile BSW Core Code]                [Compile Atomic Software Component]
     └──────────────────────┬───────────────┘
                            ▼
               [Compile ECU Source Code]
  1. Konfigurationsphase (Vorbereitung): Definition der hardwareabhängigen Adressierungsmodi gefolgt von der Modell-Konfiguration der MemMap-Allokation (SwAddrMethod).
  2. Generierungsphase (Parallelisierbar): Generatoren leiten die BSW- bzw. SWC-spezifischen Header-Dateien aus den XML-Artefakten ab (ab R4.0.2 nativer Standardbestandteil).
  3. Build-Phase:
    • Modul- bzw. komponentenweises Kompilieren (Compile BSW Core Code, Compile Atomic Software Component).
    • Abschluss auf Systemebene mit Compile ECU Source Code.
  4. Abbruchkriterium / Scope-Ende: Der Use Case terminiert mit fehlerfreier Objekterzeugung. Erzeugung von Linker-Command-Files / Scatter-Loading-Dateien und das finale Linken erfolgen außerhalb dieses Use Cases.

4. Normative Relevanz & Entwickler-Hinweise

  • Präprozessor-Mechanismus: C-Quelltexte von BSW und SWCs dürfen keine direkten Compiler-Pragmas (z. B. #pragma section) enthalten. Sämtlicher Code und alle Daten müssen zwingend über standardisierte Klammerungen eingebunden werden: 
    #define <PREFIX>_START_SEC_<SECTION_NAME>
#include "<Prefix>_MemMap.h"

/* Variablen- oder Funktionsdeklaration / -definition */

#define <PREFIX>_STOP_SEC_<SECTION_NAME>
#include "<Prefix>_MemMap.h"
  • XML-Artefakt-Synchronisation (ab R4.0.2): Sektionsbezeichner (MemorySection) in BSWMD bzw. SWCD müssen exakt mit den in Configure Memmap Allocation referenzierten SwAddrMethod-Instanzen übereinstimmen. Inkonsistenzen führen zu fehlenden Makro-Zweigen in den generierten Headern (#error "No section found").
  • BSW vs. SWC Trennung: BSW-Treiber/Stacks und SWC-Applikationen besitzen getrennte Generierungspfade. Dies ermöglicht die getrennte Auslieferung von Vorkompilaten (z. B. BSW Core Code) bei gleichzeitiger Bindung an ECU-spezifische Memory-Maps.
  • Linker-Abgrenzung: Das Memory-Mapping-Konzept steuert lediglich die Zuordnung zu abstrakten Sektionsnamen (z. B. VAR_CLEARED_16, CODE_FAST). Die Zuordnung zu physikalischen Speicherbereichen (RAM, Flash, Core-spezifischer Speicher bei Multicore-ECUs) muss im build-system-spezifischen Linker-Skript vorgenommen werden.
