1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm für AUTOSAR Classic Platform, R23-11).
  • Technischer Zweck: Spezifikation der End-to-End-Absicherung (E2E) im Kontext eines Signal-to-Service-Gateways bzw. einer Signal-zu-Service-Übersetzungsapplikation (Translation application).
  • Architektonische Einordnung: Darstellung der durch die RTE orchestrierten Transformationskette (Transformer Chain Execution) an Schnittstellen zwischen signalbasierter Legacy-/CAN-/LIN-Kommunikation (Com) und serviceorientierter Kommunikation (z. B. SOME/IP über SomeIpXf). Das Diagramm illustriert das Zusammenspiel von inversen Transformern (*_Inv_*), Zustandsmaschinenabbildung (E2E_PXXMapStatusToSM), Re-Serialisierung und der E2E-Weiterleitungsfunktion (E2E_PXXForward()).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Module (Lifelines)
  • Translation application: Application Software Component (SW-C), implementiert die Gateway-/Mapping-Logik von signalbasierten Nutzdaten auf Service-Events/Methoden.
  • «module» Rte: Runtime Environment; orchestriert synchrone API-Calls, COM-Callbacks und die Ausführung konfigurierter Transformer-Ketten (invers und regulär).
  • «module» Com: AUTOSAR Classic Communication Stack (Signal- und I-PDU-Handling).
  • «module» E2EXf: E2E-Transformer gemäß SWS E2ETransformer; führt profilbasierte E2E-Prüfung (Inv) bzw. Schutzgenerierung/Weiterleitung durch.
  • «module» E2E: AUTOSAR E2E Library; zustandslose/zustandsbehaftete Prüf- und Absicherungsalgorithmen für definierte Profile (P01, P02, P04, P07, P11, P22 etc.).
  • «module» ComBasedXf: Deserialisierungs-/Serialisierungs-Transformer für signal-/COM-basierte Datenstrukturen.
  • «module» SomeIpXf: SOME/IP-Transformer; serialisiert strukturierte C-Datentypen in das SOME/IP-On-Wire-Payload-Format.
Schnittstellen & Datentypen
  • COM-to-RTE Callback: Rte_COMCbk(ComUserCbkHandleId)
  • COM-Pufferzugriff: Com_ReceiveSignal(SignalId, SignalDataPtr) / Com_SendSignal(SignalId, SignalDataPtr)
  • SW-C API:
    • Rx: Rte_Read_<p>_<o>(...) (liefert deserialisierte Daten + E2E-Status)
    • Tx: Rte_Send_<p>_<o>(...)
  • Transformer APIs:
    • E2EXf_Inv_<transformerId>(...) / E2EXf_<transformerId>(...)
    • ComBasedXf_Inv_<transformerId>(...)
    • SomeIpXf_<transformerId>(...)
  • E2E Library APIs & Typen:
    • E2E_PXXCheck(...) → Rückgabe: :E2E_PXXCheckState (enthält Profilstatus und Sequenzzähler)
    • E2E_PXXMapStatusToSM(...) → Rückgabe: :E2E_SMState (Zustand der E2E State Machine, z. B. E2E_SM_VALID, E2E_SM_DEGRADED)
    • E2E_PXXForward(...) → Parameter/Rückgabe: :E_OK

3. Dynamisches Verhalten & Sequenzablauf

Phase 1: Signal-Ingress (Rx-Pfad)
  1. Asynchroner I-PDU/Signal-Empfang: Com empfängt eine geschützte PDU und triggert die RTE via Rte_COMCbk(ComUserCbkHandleId).
  2. Signal-Abholung: Die RTE holt das Rohdaten-Signal synchron via Com_ReceiveSignal() ab (:E_OK). Der Callback terminiert mit :(void).
Phase 2: Inverses E2E-Checking & Deserialisierung (SW-C Read)
  1. Leseanforderung: Translation application ruft synchron Rte_Read_<p>_<o>() auf.
  2. E2E-Validierung (Inverser Transformer):
    • RTE ruft E2EXf_Inv_<transformerId>() auf.
    • E2EXf delegiert an E2E_PXXCheck(), welches Header, Prüfsumme (CRC) und Alive-Counter prüft (:E2E_PXXCheckState).
    • E2EXf delegiert an E2E_PXXMapStatusToSM(), um den Check-Status in den globalen Zustand der State Machine zu überführen (:E2E_SMState).
    • E2EXf übergibt :E2E result + buffer of received data an die RTE zurück.
  3. Nutzdaten-Deserialisierung:
    • RTE ruft ComBasedXf_Inv_<transformerId>() mit dem geprüften Puffer auf.
    • Rückgabe: :E_OK.
  4. Abschluss Read: RTE übergibt :E2E result + deserialized data an die Translation application.
Phase 3: Semantische Signal-zu-Service-Übersetzung
  1. Verarbeitung: Die Translation application mappt die dekodierten Signale auf serviceorientierte Datenelemente und evaluiert den E2E-Status.
Phase 4: Service-Egress & E2E-Forwarding (Tx-Pfad)
  1. Sendeanforderung: Die Applikation triggert Rte_Send_<p>_<o>().
  2. SOME/IP-Serialisierung:
    • RTE ruft SomeIpXf_<transformerId>() auf, um die Servicedaten (oder eine Fehlerbotschaft) in den Übertragungspuffer zu serialisieren (:E_OK).
  3. E2E-Absicherung via Forward-Funktion:
    • RTE ruft E2EXf_<transformerId>() auf.
    • Anstelle einer Standard-E2E_PXXProtect()-Generierung ruft der Transformer E2E_PXXForward() auf.
    • Semantik von E2E_PXXForward():
      • War die Quellnachricht intakt (E2E_SM_VALID), generiert die Funktion gültige E2E-Schutzdaten für das Ziel-Serviceformat.
      • War die Quellnachricht korrupt/ungültig, injiziert die Funktion gezielt ungültige E2E-Felder (z. B. fehlerhafte CRCs oder Counter-Muster), um beim finalen Service-Empfänger deterministisch einen E2E-Fehler auszulösen (Erhalt der Sicherheitskette gemäß ISO 26262 / ASIL).
    • E2E liefert :E_OK, E2EXf liefert :E_OK.
  4. COM-Versand: RTE übergibt den fertig serialisierten und abgesicherten Puffer an Com_SendSignal().
  5. Abschluss Send: RTE signalisiert :RTE_E_OK an die Applikation.

4. Normative Relevanz & Entwickler-Hinweise

  • E2E Forwarding vs. Re-Protecting: Entwickler von Gateway-Funktionen dürfen Quellfehler nicht verschlucken. Durch den Einsatz von E2E_PXXForward() wird sichergestellt, dass Signalverfälschungen auf dem CAN-Bus bis zum SOME/IP-Consumer durchpropagiert werden (Verhinderung von Fault Masking).
  • Transformer-Reihenfolge (Transformation Chains):
    • Rx-Kette: Zuerst Integritätsprüfung via E2EXf_Inv, erst bei Gültigkeit/Auswertung Deserialisierung via ComBasedXf_Inv.
    • Tx-Kette: Zuerst Payload-Serialisierung via SomeIpXf, danach E2E-Header-/CRC-Berechnung über das serialisierte On-Wire-Layout via E2EXf.
  • BSW-Konfiguration (ARXML):
    • Für den E2E-Transformer muss im Tx-Pfad die Forwarding-Semantik aktiviert sein (E2EXfEnableForward = true bzw. entsprechende Zuordnung im Mapping der TransformationTechnology).
    • Korrekte Konfiguration der ComUserCbkHandleId in Com für die Weiterschaltung an die RTE.
  • Fehlerbehandlung in der Applikation: Die SW-C muss in der Lage sein, den rückgemeldeten E2E-Status (E2E_SMState) aus Rte_Read auszuwerten und im Bedarfsfall via Fehlermeldungen oder durch Anstoßen der Invalidierungs-Pfade von E2E_PXXForward() auf defekte Eingangsdaten zu reagieren.
