1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm zur Spezifikation des Metamodells für das BSW-Modulbeschreibungs-Template (AUTOSAR Basic Software Module Description Template, TPS BSW Module Description Template). Das Diagramm definiert die Variationspunkte («atpVariation») innerhalb des BSW-Verhaltens (BswInternalBehavior), das von der generischen Basisklasse InternalBehavior erbt. Es adressiert den Kontext der AUTOSAR-Systemmodellierung, Variantenkonfiguration und BSW-Scheduler-Generierung, indem es festlegt, welche Verhaltensbestandteile, Entitäten, Speicherobjekte, Trigger, Events, Modi und Service-Abhängigkeiten zur Konfigurationszeit variiert werden können.

2. Komponenten, Entitäten & Schnittstellen

Zentrales Element ist die Metaklasse BswInternalBehavior (Spezialisierung von InternalBehavior::InternalBehavior, welches das Stereotyp «AtpStructureElement» trägt).

Von InternalBehavior ausgehende Kompositionen mit Stereotyp «atpVariation»:

  • +exclusiveArea: Komposition von 0..* InternalBehavior::ExclusiveArea («Identifiable»).
  • +staticMemory: Komposition von 0..* DataPrototypes::VariableDataPrototype («AutosarDataPrototype»).
  • +constantMemory: Komposition von 0..* DataPrototypes::ParameterDataPrototype («AutosarDataPrototype»).

Von BswInternalBehavior ausgehende Kompositionen:

  • +perInstanceParameter: Komposition von 0..* DataPrototypes::ParameterDataPrototype («AutosarDataPrototype», mit «atpVariation»).
  • +entity: Komposition von 1..* BswModuleEntity («ExecutableEntity», mit «atpVariation»).
  • +internalTriggeringPoint: Komposition von 0..* BswInternalTriggeringPoint («Identifiable», mit Attribut swImplPolicy: SwImplPolicyEnum [0..1], mit «atpVariation»).
  • +event: Komposition von 0..* BswEvent («Identifiable», mit «atpVariation»).
  • +triggerDirectImplementation: Komposition von 0..* BswTriggerDirectImplementation (mit «atpVariation»).
  • +modeSenderPolicy: Komposition von 0..* BswModeSenderPolicy (mit «atpVariation»).
  • +modeReceiverPolicy: Komposition von 0..* BswModeReceiverPolicy (mit «atpVariation»).
  • +serviceDependency: Komposition von 0..* BswServiceDependency («ServiceDependency», annotiert mit «atpVariation,atpSplitable»).
  • +schedulerNamePrefix: Komposition von 0..* BswSchedulerNamePrefix («ImplementationProps», mit «atpVariation»).

Assoziationen ausgehend von BswModuleEntity:

  • +issuedTrigger: Assoziation zu 0..* TriggerDeclaration::Trigger («AtpStructureElement», «Identifiable», mit Attribut swImplPolicy: SwImplPolicyEnum [0..1], mit «atpVariation»).
  • +managedModeGroup: Assoziation zu 0..* ModeDeclaration::ModeDeclarationGroupPrototype («AtpPrototype», mit Attribut swCalibrationAccess: SwCalibrationAccessEnum [0..1], mit «atpVariation»).
  • +accessedModeGroup: Assoziation zu 0..* ModeDeclaration::ModeDeclarationGroupPrototype (mit «atpVariation»).
  • +calledEntry: Assoziation zu 0..* BswInterfaces::BswModuleEntry («ARElement», «AtpBlueprint», «AtpBlueprintable», mit «atpVariation»).
  • +activationPoint: Assoziation zu 0..* BswInternalTriggeringPoint (mit «atpVariation»).

Eine zentrale Kommentar-Note spezifiziert für alle Variationspunkte das Tag: «atpVariation» Tags: Vh.latestBindingTime = PreCompileTime. Gestrichelte Abhängigkeitslinien verbinden die Note mit sämtlichen «atpVariation»-Markierungen der Rollen.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Strukturdiagramm des Metamodells modelliert die Darstellung keine Laufzeitsequenzen. Das dynamische Verhalten wird zur Entwurfs- bzw. Generierungszeit determiniert:

  1. Variantenbildung: Sämtliche mit «atpVariation» annotierten Relationen (Entitäten, Events, Trigger, Modusdeklarationen, Exklusivbereiche und Speicherprototypen) werden spätestens zur Vorkompilierzeit (PreCompileTime) durch den Varianten-Handling-Mechanismus aufgelöst bzw. gebunden.
  2. Scheduler-Aktivierung: Zur Laufzeit wird die Ausführung von BswModuleEntity-Instanzen über konfigurierte BswEvent-Ereignisse (z. B. Zeit- oder Modusereignisse) oder über BswInternalTriggeringPoint (als Aktivierungspunkt via +activationPoint) getriggert.
  3. Modusverwaltung und Triggering: Eine ausführende BswModuleEntity kann über +managedModeGroup Modi schalten oder über +accessedModeGroup lesend darauf zugreifen. Ebenso können über +issuedTrigger Trigger ausgelöst oder über +calledEntry Schnittstellenfunktionen des Moduls synchron aufgerufen werden.
  4. Synchronisation und Ressourcen: Der Zugriff auf gemeinsame Ressourcen und Speicher (+staticMemory, +constantMemory, +perInstanceParameter) wird über +exclusiveArea gegen Nebenläufigkeit abgesichert.

4. Normative Relevanz & Entwickler-Hinweise

Normative Festlegungen und Implementierungsvorgaben:

  • Bindungszeit: Alle gezeigten Variationspunkte unterliegen der strikten Restriktion Vh.latestBindingTime = PreCompileTime. Eine spätere Variantenbindung (wie LinkTime oder PostBuild) ist für diese spezifischen Metamodellelemente im BSW-Verhalten unzulässig.
  • Kardinalität von entity: Ein BswInternalBehavior muss mindestens eine ausführbare Entität enthalten (1..*), wobei das Vorhandensein konkreter Entitäten selbst variiert werden kann.
  • Splitbarkeit: Die Beziehung +serviceDependency zu BswServiceDependency ist zusätzlich mit «atpSplitable» versehen, was ein modulares Splitten über mehrere Beschreibungsdateien hinweg (z. B. getrennte ARXML-Dateien für Service-Instanzen) erlaubt.
  • Attribute: Trigger und BswInternalTriggeringPoint besitzen optional die Implementierungsrichtlinie swImplPolicy (SwImplPolicyEnum [0..1]). ModeDeclarationGroupPrototype unterstützt optional die Kalibrierbarkeitsangabe swCalibrationAccess (SwCalibrationAccessEnum [0..1]).
  • BSW-Scheduler-Konfiguration: Modellierer und Werkzeughersteller müssen sicherstellen, dass Codegeneratoren (RTE/BswScheduler) variabilitätsabhängig nur die nach der PreCompileTime-Auflösung verbleibenden Entitäten, Events, Prefix-Definitionen und Policies instanziieren.
