1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Ausschnitt / UML-Klassendiagramm der formalen ECU-Konfigurationsparameter-Definition (BSW Parameter Definition, ParamConfContainerDef / ParamDef).
  • Architektur-Kontext: AUTOSAR Classic Platform, Kommunikationsstack (ComStack), System Services / Communication Services.
  • Funktionaler Zweck: Strukturelle und typisierte Spezifikation der kanalspezifischen Konfigurationscontainer (CNmChannelConfig) des CAN Network Management (CanNm / historisch CNm) unterhalb des globalen Konfigurationscontainers (CNmGlobalConfig). Definiert Identifikatoren, Betriebsmodi sowie normative Timer-Grenzwerte für die CAN-NM-Zustandsmaschine.

2. Komponenten, Entitäten & Schnittstellen

Container-Definitionen & Hierarchie
  • CNmGlobalConfig (ParamConfContainerDef):
    • Wurzelcontainer des Moduls mit Attribut multipleConfigurationContainer = true (ermöglicht Post-Build-Selectable Konfigurationssätze).
    • Komposition: Aggregiert über Rolle +subContainer den Kanalcontainer CNmChannelConfig.
  • CNmChannelConfig (ParamConfContainerDef):
    • Kardinalität: lowerMultiplicity = 1, upperMultiplicity = * (mindestens ein CAN-NM-Kanal muss existieren; beliebig viele Kanäle instanziierbar).
    • Aggregiert über die Rolle +parameter sämtliche kanalspezifischen Konfigurationsparameter.
Konfigurationsparameter (ParamDef)
  • Identifikatoren & Modi:
    • CNmChannelId : DerivedIntegerParamDef: Eindeutiger Kanalbezeichner (Bereich: 0 … 254). Typisiert als abgeleiteter Parameter (calculationLanguage = informal), gekoppelt an die Kanalindizes von ComM/CanIf.
    • CNmInstanceId : DerivedIntegerParamDef: Instanzbezeichner (Bereich: 7680 … 7934 bzw. 0x1E00 … 0x1EFE). Dient der Zuordnung der BSW-Modulinstanz (z. B. für Fehlerlogging/Det).
    • CNmChannelActive : BooleanParamDef: Schaltet den jeweiligen NM-Kanal im Build aktiv/inaktiv.
    • CNmBusLoadReductionActive : DerivedBooleanParamDef: Steuert die Aktivierung des Algorithmus zur Buslastreduktion (calculationLanguage = informal).
  • Zustandsmaschinen-Timer (16-Bit Integer, Einheit bezogen auf die Modulbasiszeit/ms):
    • CNmTimeoutTime : IntegerParamDef: Min = 1, Max = 65535. NM-Nachrichten-Überwachungszeit.
    • CNmWaitBusSleepTime : IntegerParamDef: Min = 1, Max = 65535. Verweildauer im Prepare Bus-Sleep Mode.
    • CNmRepeatMessageTime : IntegerParamDef: Min = 0, Max = 65535. Verweildauer im Repeat Message State.
    • CNmRemoteSleepIndTime : IntegerParamDef: Min = 1, Max = 65535. Timeout-Schwelle zur Detektion des Remote Sleep.

3. Dynamisches Verhalten & Sequenzablauf

Die konfigurierten Integer-Parameter steuern unmittelbar die Übergänge der zyklischen State Machine in der CanNm_MainFunction():

  1. Netzwerkstart / Wakeup:
    • Nach Netzanforderung verweilt der Kanal für die Dauer CNmRepeatMessageTime im Repeat Message State, um sicherzustellen, dass alle Knoten aufwachen und NM-PDUs austauschen. Bei Konfiguration auf 0 wird dieser Zustand unmittelbar verlassen.
  2. Normalbetrieb & Timeout-Überwachung:
    • Empfängt der Kanal innerhalb von CNmTimeoutTime keine gültige NM-PDU mehr, feuert der NM-Timeout-Trigger (Übergang in Richtung Bus-Ruhevorbereitung).
    • Verbleibt der eigene Knoten im Zustand Normal Operation, empfängt aber über CNmRemoteSleepIndTime keine Fremd-NM-PDUs, meldet der Treiber via Callback Nm_RemoteSleepIndication() an das NmInterface, dass alle anderen Knoten einschlafwillig sind.
  3. Übergang in den Bus-Sleep:
    • Nach Wegfall aller internen und externen Netzanforderungen wechselt der Kanal in den Prepare Bus-Sleep Mode.
    • Läuft dort der Timer CNmWaitBusSleepTime ohne erneute RX-/TX-Aktivität vollständig ab, erfolgt der synchrone Aufruf von Nm_BusSleepMode() und der Übergang in den Ruhezustand (Bus-Sleep Mode).
  4. Buslastreduktion:
    • Bei CNmBusLoadReductionActive = true unterdrückt die State Machine das periodische Senden eigener NM-PDUs, sobald der Knoten sich im Zustand Ready Sleep befindet, wodurch unnötige Buslast vor dem Einschlafen vermieden wird.

4. Normative Relevanz & Entwickler-Hinweise

  • Timer-Granularität vs. MainFunction-Periodizität: Sämtliche Timer (CNmTimeoutTime, CNmWaitBusSleepTime, etc.) müssen als ganzzahlige Vielfache des Aufrufintervalls der CanNm_MainFunction() konfiguriert werden. Bruchteile führen im BSW-Stack zu Quantisierungsfehlern oder vorzeitigen Timeouts.
  • Behandlung abgeleiteter Parameter (DerivedParamDef): Parameter mit calculationLanguage = informal (CNmChannelId, CNmInstanceId, CNmBusLoadReductionActive) dürfen von Generatoren nicht isoliert interpretiert werden. Der Konfigurationsgenerator muss Plausibilitätsprüfungen gegen die System Description, die ComMChannelId und das CanIfCtrlId-Mapping erzwingen.
  • Reservierte Werte: CNmChannelId = 255 (0xFF) ist per AUTOSAR-Konvention als ungültiger Kanal/Broadcast reserviert und liegt außerhalb des zulässigen Max-Bereichs (254).
  • Speicher-Layout (Post-Build): Durch multipleConfigurationContainer = true an CNmGlobalConfig muss die BSW-Implementierung so ausgelegt sein, dass die Kanalstrukturen CNmChannelConfig[1..*] über einen Root-Konfigurationszeiger (CanNm_ConfigType) referenziert werden (ROM-/Flash-Layout für PB-Varianten).
