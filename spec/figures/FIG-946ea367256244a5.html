1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Zweiteiliges Architektur- und Detaildiagramm (AUTOSAR Classic Platform, Gesamtschichtenmodell und BSW Communication Services).
  • Technischer Zweck: Spezifikationsgemäße Positionierung des BSW-Moduls J1939Nm innerhalb der Kommunikationsdienste sowie Verortung der Schicht Communication Services im hierarchischen Gesamtgefüge der AUTOSAR-Architektur.
  • Funktionale Einordnung:
    • Der obere Bildteil zeigt die Makro-Architektur von der Application Layer über die RTE und die BSW-Schichten bis zum Microcontroller (µC).
    • Der hervorgehobene Service-Block Communication Services wird im unteren Bildabschnitt detailliert als BSW-Stack aufgeschlüsselt.
    • Zeigt die funktionale Kapselung von J1939Nm unter dem Generic NM Interface in Relation zu ComM, CanSM, AUTOSAR COM, DCM Diagnostic Com. Manager, PDU Router, J1939 Request Manager sowie Transportprotokollen (CAN TP, J1939 TP).

2. Komponenten, Entitäten & Schnittstellen

  • Dargestellte BSW-Module & Architekturschichten:
    • AUTOSAR-Gesamtarchitektur (oberer Bildteil): Application Layer, RTE (Runtime Environment), BSW Services Layer (mit hervorgehobenen Communication Services), ECU Abstraction Layer (mit Onboard Dev. Abstraction, Memory HW Abstraction, COM HW Abstraction, I/O HW Abstraction), Microcontroller Abstraction Layer (mit Microcontroller Drivers, Memory Drivers, Communication Drivers, I/O Drivers), Complex Drivers sowie Hardware-Ebene Microcontroller (µC).
    • Komponenten der Kommunikationsdienste (unterer Detailbereich):
      • J1939 NM (gelb hervorgehoben): BSW-Modul zur Realisierung des Address Claiming Protokolls nach SAE J1939-81.
      • Generic NM Interface (Nm): Busunabhängige Abstraktionsschicht des Netzwerkmanagements.
      • COM Manager (ComM): Koordinator für Kommunikationsanforderungen der Anwendungs- und Diagnoseschichten.
      • CAN State Manager (CanSM): Controller- und Transceiver-Zustandsmaschine.
      • J1939 Request Manager (J1939Rm): Vermittler und Dispatcher für J1939 PGN-Anfragen.
      • AUTOSAR COM: Signalbasierter Datenaustausch und Signal-to-PDU-Mapping.
      • DCM Diagnostic Com. Manager: Diagnosedienst-Verarbeitung.
      • PDU Router (PduR): Routing von I-PDUs zwischen oberen und unteren Schichten.
      • CAN TP & J1939 TP: Transportprotokolle für segmentierte Übertragungen.
  • Schnittstellen & Kopplungen:
    • Nm ↔ J1939Nm: Service- und Callback-Schnittstellen (Nm_NetworkMode(), J1939Nm_NetworkRequest()).
    • J1939Nm ↔ CanIf: Direkter PDU-Austausch für PGN 60928 unter Umgehung des PduR.
    • Vertikale Schichtenverbindung der Kommunikationsdienste nach oben über die RTE zur Applikation und nach unten via COM HW Abstraction und Communication Drivers zur physikalischen CAN-Hardware.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm impliziert die dynamische Einbettung in das SAE J1939-81 Address Claiming Verfahren:

  1. Initialisierungs- & Anforderungs-Trigger:
    • ComM fordert COMM_FULL_COMMUNICATION über Nm an → Aufruf von J1939Nm_NetworkRequest().
  2. Address Claiming Phase (asynchron / Event-getrieben):
    • J1939Nm sendet eine Address Claimed PDU (PGN 60928, Quelladresse = bevorzugte Adresse) via CanIf.
    • Start des standardisierten 250 ms Arbitrierungstimers (J1939NmDelayTime).
  3. Konfliktbehandlung & Arbitrierung:
    • Kein Konflikt nach 250 ms: Adresse gilt als beansprucht; Meldung via Nm_NetworkMode() an Nm/ComM. Freigabe der Applikationskommunikation.
    • Adresskollision: Empfang einer identischen Quelladresse triggert den lexikografischen Vergleich des 64-Bit J1939 NAME:
      • Eigene Priorität höher (NAME-Wert niedriger): Erneutes Senden der Address Claimed PDU.
      • Eigene Priorität niedriger: Adressverlust. Falls Arbitrary Address Capable = TRUE, Versuch einer Alternativadresse; andernfalls Aussenden von Cannot Claim Address (Quelladresse 254 / 0xFE).
  4. Asynchrone Request-Bearbeitung:
    • Eingehende Request for Address Claimed (PGN 59904, über J1939Rm oder Rx-PDU) veranlassen J1939Nm zur unmittelbaren Beantwortung mit der aktuellen Status-PDU.

4. Normative Relevanz & Entwickler-Hinweise

  • Kein zyklisches NM-Token-Verfahren:
    • Im Gegensatz zu CanNm arbeitet J1939Nm nicht mit Ring-Tokens oder periodischen Wakeup-Keep-Alive-Paketen. Es dient primär der dynamischen/statischen Knotenadressvergabe im Nutzfahrzeugumfeld.
  • Konfigurationsverpflichtungen (Ecuc / DBC / ARXML):
    • Exakte Parametrierung des 64-Bit-NAME (J1939NmNodeName: u. a. IdentityNumber, ManufacturerCode, Function, VehicleSystem, ArbitraryAddressCapable).
    • Zuordnung von J1939NmChannel zu NmChannel und Definition der Tx-/Rx-PDU-Referenzen auf CanIf.
  • Tx-Inhibition bei fehlender Adresse:
    • Bis zum erfolgreichen Abschluss des Address Claimings müssen nachgelagerte Module (COM, J1939Tp, J1939Rm) für die reguläre Übertragung blockiert bleiben. Entwickler müssen sicherstellen, dass die I-PDU-Groups erst nach Bestätigung durch Nm aktiviert werden.
  • Multi-NM-Betrieb:
    • Bei Mischtopologien (z. B. Gateway mit Classic AUTOSAR CAN-Subnetz via CanNm und Powertrain-/Trailer-Netz via J1939Nm) muss das Generic NM Interface (Nm) für heterogene Kanal-Konfigurationen parametriert werden.
