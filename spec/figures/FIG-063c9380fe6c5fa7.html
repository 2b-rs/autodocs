1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Sequenzdiagramm (Interaktionsdiagramm).
  • Technischer Zweck: Spezifikation der Inter-ECU Sender-Receiver-Kommunikation mit ereignisgesteuerter Semantik (queued communication) und nachgelagerter Aktivierung einer Empfänger-Runnable (RunnableEntity) über das AUTOSAR OS.
  • Architektur-Einordnung: Horizontale Interaktion über Steuergerätegrenzen hinweg im AUTOSAR Classic Stack (V3.5.0 / R4.0.3, R4.1.3): Applikationsschicht (SWC) → RTE (Sender) → BSW COM → Bus/Netzwerk → BSW COM → RTE (Receiver) → Applikationsschicht (Receiver Runnable). Verknüpft die ereignisbasierte Datenübertragung (swImplPolicy = queued) mit dem Dispatching-Mechanismus des AUTOSAR OS.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Lifelines
  • Sender Application: Sende-SWC, instanziiert einen Sender-Port (PPortPrototype) mit Interface-Definition.
  • Sender's RTE / Receiver's RTE: Generierte Laufzeitumgebungen zur Kapselung von Hardware-/Stack-Details und Signal-Routing.
  • Sender's COM / Network / Receiver's COM: AUTOSAR Communication Stack (COM-Modul) inkl. physikalischer Transceiver/Busse (CAN, LIN, FlexRay, Ethernet) für signalbasiertes I-PDU-Handling.
  • Receiver runnable: Ausführbare Einheit (RunnableEntity) der Empfänger-SWC.
Datenmodell-Entitäten & Mappings (Meta-Modell-Bezug)
  • Port / DataElement:
    • Port: p (PortPrototype).
    • Datenelement: e (VariableDataPrototype).
  • Implementierungspolice:
    • VariableDataPrototype.swDataDefProps.swImplPolicy = queued.
  • Sender-Konfiguration:
    • Referenziert über VariableAccess in der Rolle dataSendPoint (asynchroner bzw. nicht-blockierender Pufferzugriff).
  • Empfänger-Konfiguration:
    • VariableDataPrototype wird referenziert durch ein DataReceivedEvent.
    • DataReceivedEvent referenziert direkt die Ziel-RunnableEntity.
  • RTE-interne Datenstrukturen:
    • RTE-Event-Queue: FIFO-Warteschlange für Datenelement e auf Empfängerseite (konfiguriert via queueLength).
Schnittstellen & APIs
  • Rte_Send_<p>_<e>(data): RTE-Schnittstelle zum Einstellen des Datenwerts in den Sendepuffer (Rückgabewert: RTE_E_OK bzw. RTE_E_LIMIT).
  • Com_SendSignal(SignalId, &SignalData): Synchroner BSW-COM-Aufruf zur Übergabe des Signals an die I-PDU-Verarbeitung (Rückgabe: E_OK).
  • Rte_COMCbk_<sn>(): COM-Signalbenachrichtigung (Callback-Funktion im RTE-Kontext, konfiguriert im COM-Modul über ComNotification).
  • Com_ReceiveSignal(SignalId, &SignalData): Synchroner Abruf der Nutzdaten aus dem COM-Signalpuffer durch die Empfänger-RTE (Rückgabe: E_OK).
  • ActivateTask(TaskId) / OS-Task-Aktivierung: Systemaufruf an das AUTOSAR OS zur Einplanung des Ausführungskontextes.
  • ReceiversRunnable(): Einstiegspunkt der C-Funktion der Empfänger-Runnable.

3. Dynamisches Verhalten & Sequenzablauf

        |--- Rte_Send_p_e ----->|                  |                   |                      |
        |                       |--Com_SendSignal->|                   |                      |
        |                       |<- E_OK ----------|                   |                      |
        |<-- RTE_E_OK ----------|                  |                   |                      |

        |                       |                  |--- E_OK --------->|                      |

        |                       |                  |                   |--(3) Activate Task ->|
        |                       |                  |<-- return --------|                      |
        |                       |                  |                   |                      |

        |                       |                  |                   |--- ReceiversRunnable>|
        |                       |                  |                   |    ((4) fetch queue) |
        |                       |                  |                   |<-- return (5) -------|
  1. Sende-Trigger:
    • Sender Application ruft synchron Rte_Send_p_e auf.
    • Sender's RTE delegiert unverzüglich via Com_SendSignal an das lokale COM-Modul und gibt nach erfolgreicher Pufferung RTE_E_OK an die Applikation zurück.
  2. Netzwerktransport:
    • COM puffert/packt das Signal in eine I-PDU; asynchrone Übertragung über den Bus zum Ziel-ECU.
  3. Empfangsmeldung (Interrupt-/Task-Ebene BSW):
    • Bei I-PDU-Eingang und Signal-Extraktion ruft Receiver's COM den konfigurierten Callback Rte_COMCbk_<sn> der Receiver's RTE auf (Schritt 1).
  4. Queueing & Entkopplung:
    • Die RTE holt das Signal sofort synchron via Com_ReceiveSignal aus dem COM-Puffer ab.
    • RTE legt das Datenelement e in der RTE-internen FIFO-Queue ab (Schritt 2).
    • RTE triggert die Entkopplung vom BSW-Kontext durch Aktivierung des zugeordneten OS-Tasks (ActivateTask bzw. Event-Setting bei Extended Tasks) (Schritt 3).
    • Der Callback Rte_COMCbk_<sn> terminiert und kehrt zu COM zurück.
  5. Runnable-Ausführung:
    • Der AUTOSAR OS-Scheduler startet den aktivierten Task gemäß Priorität.
    • Im Kontext dieses Tasks entnimmt die RTE das nächste Element aus der Queue (Schritt 4) und ruft die ReceiversRunnable auf.
    • Mit Rückkehr der Runnable endet der Taskzyklus (Schritt 5).

4. Normative Relevanz & Entwickler-Hinweise

  • Puffer- und Überlaufbehandlung (SWS_Rte_07381, SWS_Rte_07382, SRS_Rte_00184):
    • Da swImplPolicy = queued konfiguriert ist, muss für das Datenelement im RTE-Generatorkonfigurationsmodell eine explizite Queue-Tiefe (queueLength) definiert werden.
    • Läuft die RTE-Queue auf Empfängerseite voll (z. B. wenn Task-Aktivierungen verzögert werden oder PDU-Bursts eintreffen), droht Datenverlust (RTE_E_LOSTDATA). Die Dimensionierung von queueLength muss auf die Worst-Case Execution Time (WCET) und Task-Periodizität/Priorität abgestimmt sein.
  • Kontexttrennung & Interrupt-Laufzeiten:
    • Der COM-Callback Rte_COMCbk_<sn> läuft typischerweise im ISR- oder COM-MainFunction-Kontext. Er führt nicht direkt die Applikations-Runnable aus, sondern minimalinvasiv nur Com_ReceiveSignal, das Queueing und ActivateTask.
    • Das Scheduling der Applikationslogik wird sauber in den OS-Task-Kontext entkoppelt (Verhinderung von Blockaden im BSW-Treiberstack).
  • Task-Mapping-Restriktionen:
    • Wenn das DataReceivedEvent auf einen Basic Task gemappt wird, führt jedes empfangene Queue-Element zu einer Taskaktivierung. Hierbei ist das OS-Attribut OsTaskActivation (Anzahl Mehrfachaktivierungen) entsprechend abzusichern (E_OS_LIMIT-Vermeidung).
    • Alternativ kann die Runnable auf einen Extended Task gemappt werden, bei dem die RTE ein OS-Event (SetEvent) setzt und die Runnable in einer Dispatcher-Schleife mit Rte_Receive die Queue abarbeitet.
  • API-Semantik:
    • Senderseitig liefert Rte_Send bei voller COM-Sende-Warteschlange RTE_E_LIMIT. Der Rückgabewert muss zwingend im Applikationscode evaluiert werden.
