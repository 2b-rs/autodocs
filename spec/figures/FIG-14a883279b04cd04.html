1. Diagrammtyp & Architektur-Kontext

UML-Sequenzdiagramm zur Spezifikation des Startvorgangs eines CAN-Netzwerks (Figure 9.11: Start CAN network) innerhalb der AUTOSAR Classic Platform. Dargestellt wird die Interaktion zwischen der oberen Schicht (CanIf User), dem CAN-Interface (CanIf), dem CAN-Treiber (Can) und dem CAN-Hardware-Controller (CanController) zur Anforderung und Rückmeldung des Controller-Moduswechsels nach START.

2. Komponenten, Entitäten & Schnittstellen

Beteiligte Entitäten (Lebenslinien):

  • CanIf User: Software-Komponente bzw. Modul der oberen Schicht (z. B. CanSM).
  • CanIf: AUTOSAR-Modul «module» CAN Interface.
  • Can: AUTOSAR-Modul «module» CAN Driver.
  • CanController: Hardware-Peripherie «Peripheral».

Schnittstellen und Operationen:

  • Can_MainFunction_Mode(): Zyklische Polling-Funktion im CAN-Treiber.
  • CanIf_SetControllerMode(Std_ReturnType, uint8, CanIf_ControllerModeType): API-Aufruf zur Modusanforderung an das CAN-Interface.
  • Can_SetControllerMode(Can_ReturnType, uint8, Can_StateTransitionType): Treiber-API zur Anforderung der Zustandsänderung am Controller; liefert CAN_OK oder CAN_NOT_OK.
  • CanIf_ControllerModeIndication(uint8, CanIf_ControllerModeType) bzw. CanIf_ControllerModeIndication(Controller, ControllerMode): Indikations-Callback vom CAN-Treiber an CanIf.
  • <User_ControllerModeIndication>(uint8, CanIf_ControllerModeType): Konfigurierbare Callback-Benachrichtigung von CanIf an den CanIf-Benutzer.
  • Interne Hardware-Aktionen / Rückgabewerte: Disable Wakeup interrupt, if supported(), request CAN controller mode transition to START(), Can_SetControllerMode returns with CAN_OK() / CAN_NOT_OK(), CanIf_SetControllerMode returns with E_OK() / E_NOT_OK().

3. Dynamisches Verhalten & Sequenzablauf

  1. Vorlauf / Hintergrund: In einem loop-Kombinationsfragment ruft Can zyklisch Can_MainFunction_Mode() auf, um Moduswechsel des Controllers zu pollen und ggf. via CanIf_ControllerModeIndication() weiterzuleiten.
  2. Initialer Aufruf: CanIf User ruft CanIf_SetControllerMode(Std_ReturnType, uint8, CanIf_ControllerModeType) auf. CanIf leitet dies synchron als Can_SetControllerMode(Can_ReturnType, uint8, Can_StateTransitionType) an Can weiter.
  3. Hardware-Trigger: Can deaktiviert ggf. Wakeup-Interrupts (Disable Wakeup interrupt, if supported()) und sendet request CAN controller mode transition to START() an den CanController.
  4. Fallunterscheidung (alt CAN Controller Mode):
  • Fall [STOPPED]: Can_SetControllerMode kehrt synchron mit CAN_OK() zurück, CanIf_SetControllerMode antwortet dem Benutzer mit E_OK(). Zeitversetzt vollzieht der Controller den Wechsel (CAN controller mode changes to START). Beim nächsten Can_MainFunction_Mode() erkennt Can die Transition und ruft CanIf_ControllerModeIndication(uint8, CanIf_ControllerModeType) auf. CanIf setzt intern Change to CANIF_CS_STARTED(), benachrichtigt den Benutzer via <User_ControllerModeIndication>(uint8, CanIf_ControllerModeType) und kehrt zum Treiber zurück.
  • Fall [STOPPED with direct indication]: Die Hardware wechselt unmittelbar während des Aufrufs in START. Noch im Kontext von Can_SetControllerMode() ruft Can die Indikation CanIf_ControllerModeIndication(Controller, ControllerMode) auf. CanIf wechselt intern auf CANIF_CS_STARTED(), ruft synchron <User_ControllerModeIndication>(uint8, CanIf_ControllerModeType) auf und kehrt zurück. Anschließend kehren Can_SetControllerMode mit CAN_OK() und CanIf_SetControllerMode mit E_OK() zurück.
  • Fall [STARTED]: Der Controller befindet sich bereits im Zustand STARTED. Can löst direkt CanIf_ControllerModeIndication(uint8, CanIf_ControllerModeType) aus, CanIf wechselt intern auf CANIF_CS_STARTED(), benachrichtigt den Benutzer über <User_ControllerModeIndication>, und beide Set-Funktionen kehren mit CAN_OK() bzw. E_OK() zurück.
  • Fall [SLEEP]: Im Zustand SLEEP darf der Controller nicht direkt nach START wechseln. Can fordert keine Hardware-Transition an, Can_SetControllerMode schlägt fehl mit CAN_NOT_OK(), und CanIf_SetControllerMode kehrt synchron mit E_NOT_OK() zurück.

4. Normative Relevanz & Entwickler-Hinweise

  • Zeigt die standardkonforme Asynchronität bzw. optionale direkte Synchronität von Moduswechseln im CAN-Subsystem.
  • Verdeutlicht, dass ein Modusübergang von SLEEP direkt nach START unzulässig ist und synchron abgewiesen wird (E_NOT_OK).
  • Zeigt die Entkopplung über Polling (Can_MainFunction_Mode) im asynchronen Normalfall gegenüber direkter Callback-Ausführung bei schneller Hardware-Reaktion.
  • Entwickler müssen sicherstellen, dass <User_ControllerModeIndication> sowohl synchron während CanIf_SetControllerMode als auch asynchron im Kontext der Main-Function aufgerufen werden kann (Wiedereintrittsfähigkeit und Sperrmechanismen beachten).
