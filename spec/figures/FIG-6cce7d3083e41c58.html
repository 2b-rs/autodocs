1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt aus der AUTOSAR-Spezifikation Diagnostic Extract Template (DEXT, TPS DEXT, R4.3.1).
  • Technischer Zweck & Einordnung: Formale Beschreibung der Metadaten für On-Board-Monitoring-Testergebnisse (Diagnostic Test Results / DTR). Dient dem herstellerübergreifenden Datenaustausch zur Konfiguration der AUTOSAR-Basissoftware (insb. Dem – Diagnostic Event Manager und Dcm – Diagnostic Communication Manager) für OBD-II/WWH-OBD Services (speziell OBD Service $06 Request On-Board Monitoring Test Results for Specific Monitored Systems nach SAE J1979 / ISO 15031-5 bzw. UDS Service $19 Subfunktion 0x1A).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Stereotypen
  • DiagnosticCommonElement (Basisklasse, kursiv): Abstrakte Basisklasse aller identifizierbaren DEXT-Diagnose-Elemente.
  • DiagnosticTestResult: Zentrales Modellelement eines Monitor-Testergebnisses (DTR).
    • + updateKind : DiagnosticTestResultUpdateEnum: Bestimmt die Aktualisierungssemantik im Puffer.
  • DiagnosticTestIdentifier: Repräsentiert die Test-Identifikation innerhalb eines Monitors.
    • + id : PositiveInteger: Test-ID (TID).
    • + uasId : PositiveInteger: Unit- and Scaling-ID (definiert physikalische Einheit, Auflösung und Berechnungsformel der Rohwerte).
  • DiagnosticMeasurementIdentifier: Repräsentiert die On-Board-Monitor-ID (OBDMID).
    • + obdMid : PositiveInteger: Standardisierte Kennung des überwachten Teilsystems (0x01–0xFE).
  • DiagnosticEvent: Repräsentiert das korrespondierende Dem-Ereignis (DTC/Event-Kontext).
    • + clearEventBehavior : DiagnosticClearEventBehaviorEnum [0..1]: Verhalten beim Löschen des Fehlerspeichers.
    • + eventClearAllowed : DiagnosticEventClearAllowedEnum [0..1]: Berechtigung zum Löschen.
    • + eventKind : DiagnosticEventKindEnum: Art des Events (BSW- vs. SW-C-Event).
    • + prestorageFreezeFrame : Boolean: Unterstützung für Freeze-Frame-Vorspeicherung.
    • + prestoredFreezeframeStoredInNvm : Boolean [0..1]: Gibt an, ob vorgespeicherte Freeze-Frames im NvM persistent gesichert werden.
    • + recoverableInSameOperationCycle : Boolean [0..1]: Heilung innerhalb desselben Fahrzyklus zulässig.
    • «atpVariation» + eventFailureCycleCounterThreshold : PositiveInteger [0..1]: Zyklenschwelle für Fehlerqualifikation, varianzfähig über AUTOSAR-Variantenmanagement.
  • DiagnosticTestResultUpdateEnum («enumeration»):
    • always: DTR-Puffer wird bei jedem Messzyklus überschrieben.
    • steady: DTR-Puffer wird erst bei Vorliegen stabiler Bedingungen bzw. einmalig pro Operationszyklus fixiert.
Beziehungen & Kardinalitäten
  • DiagnosticTestResult ◆ → DiagnosticTestIdentifier (+testIdentifier, Kardinalität 1): Komposition. Ein DTR kapselt genau eine TID inklusive Skalierungsdefinition.
  • DiagnosticTestResult → DiagnosticMeasurementIdentifier (+monitoredIdentifier, Kardinalität 1): Unidirektionale Assoziation. Genau eine OBDMID pro DTR.
  • DiagnosticTestResult → DiagnosticEvent (+event, Kardinalität 0..1): Optionale Assoziation. Koppelt das DTR an ein konkretes Dem-Event (DTC) oder belässt es event-unabhängig.
  • Generalisierung: DiagnosticTestResult, DiagnosticMeasurementIdentifier und DiagnosticEvent erben von DiagnosticCommonElement.

3. Dynamisches Verhalten & Sequenzablauf

  1. Testdurchführung (Monitor-Lauf): Eine Diagnose-SW-C führt eine Überwachungsroutine aus (z. B. Katalysator-, Lambdasonden- oder Tankentlüftungsprüfung).
  2. Datenübergabe an BSW: Die SW-C meldet Testergebnis, Minimal- und Maximalgrenzwert über die API Dem_DtrSetData() (bzw. Port-Interface DiagnosticMonitor) unter Angabe der konfigurierten DtrId an das Dem.
  3. Puffer-Aktualisierung (updateKind):
    • Ist updateKind == always, werden Messwert, Min- und Max-Limit im Dem-DTR-Puffer bei jedem Aufruf direkt aktualisiert.
    • Ist updateKind == steady, verwirft oder ignoriert das Dem Zwischenergebnisse, sobald das Testergebnis für den aktuellen Fahrzyklus als stabil/abgeschlossen gilt.
  4. Tester-Anfrage (OBD Service $06):
    • Ein externer Tester fordert Daten via Dcm an.
    • Dcm fragt die gepufferten DTR-Werte über BSW-interne Schnittstellen vom Dem ab.
    • Die Rückgabe-PDU wird gemäß DEXT-Parametrierung aus obdMid, id (TID), Testwerten und uasId assembliert und gesendet.
  5. Zykluswechsel & Event-Reset: Bei Fahrzyklus-Neustart (Dem_SetOperationCycleState) oder Fehlerspeicherlöschung (Dem_ClearDTC) werden die DTR-Puffer entsprechend der Konfiguration von clearEventBehavior reinitialisiert.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Generierung (Dem / Dcm): Die Modellierung in DEXT überführt direkt in die BSW-Konfigurationscontainer DemDtr (DemDtrMidRef, DemDtrTid, DemDtrUasid, DemDtrUpdateKind, DemDtrEventRef).
  • Skalierung & Datentypen: Die Applikations-SW-C muss Rohwerte exakt auf die durch uasId festgelegte Auflösung berechnen, bevor sie an Dem_DtrSetData() übergeben werden. Eine fehlerhafte uasId führt zu falscher Interpretation durch den OBD-Scan-Tool-Tester.
  • Entkopplung über Multiplizität 0..1: Ein DTR erfordert nicht zwingend ein DiagnosticEvent. Wird kein Event referenziert, agiert der DTR als reiner Messwert-Monitor ohne direkten Fehlerspeichereintrag (DTC-Statusbits bleiben unbeeinflusst).
  • Variantenbindung: Über das Stereotyp «atpVariation» an eventFailureCycleCounterThreshold muss der Integrator beachten, dass Event-Schwellen post-build oder pre-compile abhängig von Fahrzeugvarianten/Märkten abweichen können, während die DTR-Identifier-Struktur (obdMid, uasId) normiert stabil bleibt.
