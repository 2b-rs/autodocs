1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturelles Schichten- und Dekompositionsmodell (Metamodell-Mapping / Abstraktionsebenen-Diagramm) mit integrierter Datenfluss- und Allokationsdarstellung.
  • Technischer Zweck: Das Diagramm aus AUTOSAR_FO_TR_TimingAnalysis (Foundation, R23-11/R24-11) spezifiziert das normative Vorgehensmodell zur hierarchischen Verfeinerung und Transformation von Timing-Anforderungen (insb. End-to-End-Latenzen und Event Chains / Wirkketten) über drei Systemebenen:
    1. Functional Level: Reine funktionale Wirkkette (Sensor-to-Actuator), plattform- und allocationsunabhängig.
    2. Platform Abstract Level: Logische Systemarchitektur, zerlegt in abstrakte Systemkomponenten (Abstract Component) mit generischen Ports.
    3. Concrete Platforms Level: Zielplattform-spezifische Realisierung, getrennt nach Classic Platform (CP) (SWC/RTE-Metamodell) und Adaptive Platform (AP) (Service-orientierte POSIX-Applikationen / ara::com).

2. Komponenten, Entitäten & Schnittstellen

  • Ebene 1: Functional
    • Grobrepräsentation: Sensor → Processing → Actuator.
    • Dekomposition (Decomposition): Verfeinerung des Verarbeitungsblocks in eine lineare Kette: SensorPreProcessing → PreProcessingA → MainProcessing → PostProcessing.
    • Schnittstellen: Direkte, unidirektionale funktionale Datenflüsse (symbolisiert durch Dreiecke an den Blockkanten).
  • Ebene 2: Platform Abstract
    • Komponenten (Stereotyp/Klasse Abstract Component, Symbol X): Sensor, SensorProcessor, DataProcessor, MainProcessor, PostProcessor, Action.
    • Ports: Generische Schnittstellenpunkte; schwarze Dreiecke kennzeichnen die Richtung:
      • Dreieck aufwärts im Kasten: Eingangsport (In-Port).
      • Dreieck abwärts im Kasten: Ausgangsport (Out-Port).
  • Ebene 3: Concrete Platforms
    • Split Classic vs. Adaptive:
      • Classic Platform (CP):
        • SensorProcessor realisiert als SWC Composition (Symbol C, Metaklasse CompositionSwComponentType).
        • Dekomposition in Atomic SWC (Symbol A, Metaklasse AtomicSwComponentType): Filter (A) und Adjustment (A).
        • Interne Verbindung: VFB-Verbindung über R-Ports/P-Ports (Assembly Connector zwischen Filter-Ausgang und Adjustment-Eingang).
      • Adaptive Platform (AP):
        • PostProcessor realisiert als Adaptive Application (Symbol AA, Instanziierung als OS-Prozess im Kontext des Execution Managements).
        • Ports: Service-Interfaces (Methoden/Events via ara::com Skeleton/Proxy-Strukturen).
  • Relationen:
    • Horizontale Dekomposition (Decomposition): 1:n-Zerlegung einer Entität in Sub-Entitäten zur Budgetierung von Timing-Constraints.
    • Vertikale Transformation (Transformation T): 1:1- oder 1:n-Projektion von funktionalen Anforderungen auf abstrakte Entitäten und weiter auf konkrete Plattform-Artefakte.

3. Dynamisches Verhalten & Sequenzablauf

  • Transformationsfluss & Timing-Chain-Propagation:
    • Das Diagramm stellt keinen sequenziellen Laufzeit-Trace dar, sondern den statischen Allokations- und Zerlegungsfluss für Timing-Analysen gemäß AUTOSAR TIMEX (Timing Extensions):
      1. Top-Down-Budgetierung: Eine End-to-End-Latenzanforderung (L_E2E) über die Kette Sensor → Actuator wird auf funktionaler Ebene auf die Teilblöcke (SensorPreProcessing, PreProcessingA, etc.) als Teilbudgets verteilt: $$L_{\text{E2E}} \ge L_{\text{Sensor}} + L_{\text{SensorPre}} + L_{\text{PreA}} + L_{\text{Main}} + L_{\text{Post}} + L_{\text{Actuator}}$$
      2. Transformation (T): Jedes Budget wird über die abstrakte Komponentenebene (X) an die konkrete Zielplattform übergeben.
      3. CP-Laufzeitdynamik:
        • Filter und Adjustment enthalten jeweils RunnableEntity-Instanzen.
        • Die Kommunikation erfolgt synchron oder asynchron über die RTE (Sender-Receiver).
        • Zusätzliche Latenzen entstehen durch Task-Scheduling (Perioden, Preemption, Offset) und RTE-Overhead.
      4. AP-Laufzeitdynamik:
        • PostProcessor läuft als POSIX-Prozess.
        • Kommunikation erfolgt asynchron über IPC/SOME/IP (ara::com). Zusätzliche Latenzfaktoren sind Thread-Scheduling-Jitter und Middleware-Serialisierung.

4. Normative Relevanz & Entwickler-Hinweise

  • TIMEX-Metamodell-Konformität:
    • Timing-Anforderungen müssen über TimingExtension mit EventChain, EventChainReference, LatencyTimingConstraint und ExecutionOrderConstraint formal erfasst werden.
    • Traceability ist zwingend: Jede atomare Komponente/Runnable auf CP bzw. jeder Prozess/Service auf AP muss auf das entsprechende Teilbudget der abstrakten Ebene (Abstract Component) referenzieren.
  • Relevanz für Classic-Platform-Entwickler:
    • VFB/RTE-Konfiguration: Die Dekomposition von SensorProcessor in Filter und Adjustment erfordert ein explizites SwComponentType-Metamodell. Die Verbindung zwischen beiden SWCs muss im System Description Manifest über SwcToEcuMapping ggf. als intra-ECU oder inter-ECU Routing konfiguriert werden.
    • Task-Mapping: Die Runnables beider atomarer SWCs müssen Tasks zugewiesen werden, deren Aktivierungsintervalle und Prioritäten die abgeleitete Latenzgrenze einhalten (Worst-Case Execution Time, Blocking Time durch OS-Ressourcen/Spinlocks).
  • Relevanz für Adaptive-Platform-Entwickler:
    • Execution Manifest: Die Adaptive Application erfordert die Definition von StartupConfig und Scheduling-Parametern (z. B. SCHED_FIFO, Priorität, Core-Pinning) im Machine-/Execution-Manifest, um das geforderte Latenzbudget deterministisch einzuhalten.
    • Service Design: Das Interface von PostProcessor muss auf Message-Latenz und PDU-Queueing ausgelegt sein (z. B. PTP/Time-Synchronization gemäß IEEE 802.1AS für Event-Timestamping).
  • Plattformübergreifende Wirkketten (CP ↔ AP Bridge):
    • Werden CP- und AP-Knoten in einer gemeinsamen Event-Chain gekoppelt (heterogenes System), bildet das Kommunikations-Gateway (z. B. SOME/IP zu CAN/FlexRay bzw. Signal-to-Service-Mapping via AUTOSAR Classic PduR/SoAd) ein eigenständiges Timing-Glied, das zwingend im Gesamtlatenzbudget berücksichtigt werden muss.
