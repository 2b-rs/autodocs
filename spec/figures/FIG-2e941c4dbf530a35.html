1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm) mit eingebetteten Zustandsmarkern (State Invariants: GOSLEEP, SLEEP, HALT, WAKEUP I) und annotierten Constraints.
  • Funktionale Einordnung: AUTOSAR Classic Platform, Modul ECU State Manager (AUTOSAR_SWS_ECUStateManager, Release R20-11, Sleep & Wakeup Management).
  • Technischer Zweck: Spezifikation des standardisierten sequenziellen Ablaufs für den Übergang eines Steuergeräts in den Schlafmodus (Sleep Sequence via Halt-Instruktion) sowie der anschließenden asynchronen Aufwecksequenz über einen externen Interrupt der Input Capture Unit (ICU Wakeup by ISR Cat 2) und die Rückkehr in den aktiven Betriebsmodus.

2. Komponenten, Entitäten & Schnittstellen

#### Akteure & Lifelines

  • «module» EcuM: BSW-Modul ECU State Manager (System Service; Träger des Task-/Thread-Kontexts der Zustandsmaschine).
  • Integration Code: ECU-spezifischer Callout- und Glue-Code (zuständig für die Vermittlung hardwarenaher Konfigurationsschritte und Taktstabilisierung).
  • «module» Os: AUTOSAR Operating System (Verwaltung von Scheduler-Ressourcen und globaler Interrupt-Sperre).
  • «module» Mcu: MCAL-Treiber Microcontroller (Steuerung der Core-Power-Modes und PLL-Zustände).
  • «module» Wakeup Source: Abstrahierter Peripherie-Treiber / Kommunikationsstack (z. B. Can, Lin, Fr oder generic <Module>).
  • «module» Icu: MCAL-Treiber Input Capture Unit (Erfassung externer Flanken/Pegel als Wakeup-Quelle).
  • «Peripheral» ICU Hardware: Physischer Peripherie-Pin / Interrupt-Controller der MCU.

3. Dynamisches Verhalten & Sequenzablauf

#### Phase 1: Vorbereitung und Eintritt in den Schlafmodus (GOSLEEP $\to$ SLEEP)

  1. Wakeup-Aktivierung: Im Status GOSLEEP ruft EcuM den Callout EcuM_EnableWakeupSources(EcuM_WakeupSourceType) auf. Der Integration Code delegiert via Icu_EnableWakeup(Icu_ChannelType) an den ICU-Treiber.
  2. Scheduler-Blockierung: EcuM belegt die systemweite Ressource RES_AUTOSAR_ECUM_<core#>.
  • Zweck: Verhindert ein präemptives Rescheduling nach Abarbeitung nachfolgender ISRs (Kategorie 2), damit der Kontrollfluss nach dem CPU-Wakeup garantiert in der EcuM-Task verbleibt.
  1. Interrupt-Maskierung: EcuM ruft DisableAllInterrupts() auf, um Race Conditions vor dem Mode-Switch auszuschließen.
  2. Halt-Zustand: EcuM ruft Mcu_SetMode(Mcu_ModeType). Der MCU-Treiber setzt das Register für den Low-Power-Modus und führt den CPU-Stopp-Befehl aus (HALT / WFI / SLEEP). Der CPU-Core verharrt im stromsparenden Wartezustand.

#### Phase 2: Asynchrones Wakeup & ISR-Abarbeitung (im Status HALT)

  1. Hardware-Trigger: ICU Hardware erkennt das Wecksignal und triggert Wakeup interrupt(). Die Hardware verlässt HALT.
  2. ISR Cat 2 Execution: Die CPU verzweigt in die ISR des ICU-Treibers.
  3. EcuM-Weckprüfung: Icu ruft EcuM_CheckWakup(EcuM_WakeupSourceType) direkt am EcuM auf.
  4. Callout-Hook & Takt-Reaktivierung:
  • EcuM ruft den Hook EcuM_CheckWakeupHook(EcuM_WakeupSourceType) im Integration Code auf.
  • Integration Code führt unmittelbar activate PLL() aus, um den Mikrocontroller auf den für Peripheriezugriffe erforderlichen Takt einzuschwingen.
  1. Validierung & Event-Meldung:
  • Integration Code fragt über <Module>_CheckWakeup(EcuM_WakeupSourceType) das Quellmodul ab.
  • Wakeup Source verifiziert die Anforderung und meldet das valide Event direkt via EcuM_SetWakeupEvent(EcuM_WakeupSourceType) an den EcuM.
  1. ISR-Exit: Die Call-Kaskade kehrt zurück, und die ICU-ISR endet mit Return from interrupt().

#### Phase 3: Fortsetzung des EcuM-Kontrollflusses (WAKEUP I)

  1. Un-Halt der Task: Da RES_AUTOSAR_ECUM_<core#> aktiv ist, wird kein Task-Wechsel initiiert. Die Programmausführung setzt unmittelbar nach der HALT-Instruktion im blockierten Mcu_SetMode() fort und kehrt zum EcuM zurück.
  2. Interrupt-Wiederherstellung: EcuM öffnet mit EnableAllInterrupts() kurzzeitig die Interrupt-Sperre.
  3. Modus-Restaurierung (WAKEUP I):
  • Unter geschütztem Kontext (DisableAllInterrupts()) stellt EcuM via Mcu_SetMode(Mcu_ModeType) den regulären MCU-Normalmodus (Run Mode) wieder her und hebt die Sperre via EnableAllInterrupts() wieder auf.
  1. Wakeup-Deaktivierung: EcuM ruft EcuM_DisableWakeupSources(EcuM_WakeupSourceType), woraufhin der Integration Code via Icu_DisableWakeup(Icu_ChannelType) den ICU-Kanal dekonfiguriert, um Folgeinterrupts im Normalbetrieb zu unterbinden.
  2. Scheduler-Freigabe: EcuM ruft ReleaseResource(RES_AUTOSAR_ECUM_<core#>). Das reguläre OS-Scheduling ist reaktiviert; nachgelagerte Tasks können ausgeführt werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Kritische OS-Ressourcen-Bindung (RES_AUTOSAR_ECUM_<core#>):
  • Der Standard erzwingt die Nutzung dieser Standard-OS-Ressource. Wird sie im GOSLEEP nicht akquiriert, führt das Verlassen der Cat-2-ISR (Return from interrupt()) zu einem OS-Rescheduling. Höher- oder gleichpriorisierte Anwendungs-Tasks würden starten, bevor der MCU-Takt, die Peripherie-Betriebsmodi und die Interrupt-Vektoren im WAKEUP I wiederhergestellt sind.
  • Hardware-Interrupt-Design bei globaler Maskierung:
  • Das Diagramm verlangt DisableAllInterrupts() vor Mcu_SetMode(). Der Mikrocontroller bzw. Interrupt-Controller (NVIC, GIC etc.) muss zwingend hardwareseitig unterstützen, dass maskierte oder privilegierte Wakeup-Interrupts den Core aus dem Schlafzustand wecken (Wakeup Event vs. Interrupt Request).
  • Takt-Reihenfolge im Integration Code (activate PLL()):
  • Vor dem Aufruf von <Module>_CheckWakeup() muss der Systemtakt stabilisiert werden. MCAL-Treiber (z. B. SPI, CAN, FlexRay) dürfen nicht mit unzulässigem oder instabilem Takt angesprochen werden, da dies Hard-Faults oder Bus-Errors auslöst.
  • Flanken- und Pegelentprellung:
  • Die Trennung von Icu_EnableWakeup() und der späteren Validierung über EcuM_CheckWakeup() / <Module>_CheckWakeup() stellt sicher, dass Spikes auf dem ICU-Pin nicht unmittelbar zu einem vollen System-Hochlauf führen, falls die Validierung fehlschlägt.
  • Multi-Core-Konformität:
  • Die Spezifikation nutzt den Platzhalter <core#>. Auf Multi-Core-Systemen muss die Schlafsequenz core-spezifisch synchronisiert werden (EcuM Master/Slave-Core-Handling gemäß AUTOSAR Multi-Core-Sleep-Konzept).
