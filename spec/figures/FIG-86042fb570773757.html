1. Diagrammtyp & Architektur-Kontext

Konzeptionelles Daten- und Mapping-Diagramm im Kontext der AUTOSAR Adaptive Platform (Manifest Specification, Service-to-Signal Translation). Das Schaubild visualisiert die Transformation von serviceorientierten Ereignisdaten (ServiceInterface.event) in signalbasierte Kommunikationsstrukturen (ISignalIPdu, ISignal, ISignalGroup) unter Berücksichtigung von optionalen Elementen und Update-Bits. Links wird die Definitions- bzw. Entwurfszeitebene dargestellt, rechts ein konkretes Instanz- bzw. Laufzeitszenario.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm umfasst zwei Hauptblöcke (Typdefinition links, Instanzwerte rechts):

  • Serviceorientierte Ebene (graue Boxen, Sender-Seite):
    • Links: Typdefinition von event klm mit den Elementen k [optional] (komplexer Datentyp / Struct mit Sub-Elementen g : uint8, h : uint16), l [optional] : uint8 sowie dem obligatorischen Element m : sint16.
    • Rechts: Laufzeitinstanz von event klm, in der nur das optionale Element l (Wert 78) und das obligatorische Element m (Wert -23) belegt sind; das optionale Element k ist nicht gesetzt.
  • Signalbasierte Ebene (grüne Boxen, Empfänger- / PDU-Ebene):
    • Links: Zielstruktur mit signal group k (enthaltend die Einzelsignale g : uint8, h : uint16), Einzelsignal signal l : uint8, Einzelsignal signal m : sint16 sowie den zugeordneten Update-Bits updateBit_k und updateBit_l.
    • Rechts: PDU-Belegung zur Laufzeit mit Default-/Restwerten für signal group k (g : 5, h : 2), übertragenen Werten signal l : 78 und signal m : -23 sowie gesetzten Update-Bits updateBit_k = 0 und updateBit_l = 1.
  • Verbindungen: Gerichtete Pfeile markieren das Signal-Mapping von Event-Elementen auf die korrespondierenden Signale bzw. Signal-Gruppen-Elemente.

3. Dynamisches Verhalten & Sequenzablauf

  1. Definitionszeit / Mapping: Für jedes als [optional] markierte Datenelement im Service-Event (k, l) wird in der korrespondierenden ISignalIPdu ein Update-Bit (updateBit_k, updateBit_l) definiert. Obligatorische Elemente (m) erhalten kein Update-Bit.
  2. Laufzeit-Serialisierung:
    • Bei der Service-Signal-Translation wird zur Laufzeit geprüft, welche optionalen Elemente in der Event-Instanz vorhanden sind.
    • Da k nicht vorhanden ist, wird updateBit_k = 0 gesetzt; die Signale in signal group k behalten unberücksichtigte bzw. statische PDU-Vorbelegungen (5, 2).
    • Da l vorhanden ist, wird der Wert 78 in signal l übertragen und updateBit_l = 1 gesetzt.
    • Das obligatorische Element m wird stets übertragen (signal m : -23).
  3. PDU-Übertragung: Die resultierende Signal-PDU wird inklusive der gesetzten Update-Bits über das zugrundeliegende Netzwerk versendet.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Relevanz: Die Modellierung spezifiziert die Übersetzungsvorschrift für die Service-Signal-Translation (AUTOSAR_TPS_ManifestSpecification). Jedes Service-Event-Element mit CppImplementationDataTypeElement.isOptional = true erfordert zwingend die Konfiguration eines zugehörigen Update-Bits für das jeweilige ISignal bzw. die ISignalGroup.
  • Implementierungshinweise:
    • Der Kommunikationsstack (Translation-Layer) muss vor der Signal-Serialisierung das Vorhandensein optionaler Event-Elemente (z. B. via std::optional / has_value()) abfragen.
    • Fehlt ein optionales Element, muss das zugehörige Update-Bit auf 0 gesetzt bleiben, damit signalbasierte Empfänger das Signal verwerfen bzw. nicht als gültig interpretieren.
    • Für zusammengesetzte optionale Strukturen (ISignalGroup) genügt ein einzelnes Update-Bit auf Gruppenebene.
