1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Tabellarische Spezifikationsmatrix / Metamodell-Eingabeformat (Auszug aus Excel-Sheet 09_DataTypes_Array der AUTOSAR Application Interfaces (AI) Table Suite).
  • Architektur-Kontext: Normative Definition standardisierter Anwendungs-Array-Datentypen (ApplicationArrayDataType) für die Domäne Fahrzeugdynamik/Chassis (unter Bezug auf ISO 8855). Dient als standardisierte Quelle zur modellbasierten automatisierten Ableitung von AUTOSAR-ARXML-Schnittstellendeskriptoren für Software-Components (SWCs) im AUTOSAR Classic Platform (CP) Ökosystem.

2. Komponenten, Entitäten & Schnittstellen

  • Tabellenstruktur & Metamodell-Elemente:
    • Data Type Name (Metamodell: SHORT-NAME): Eindeutiger Bezeichner des ApplicationArrayDataType.
      • Dargestellt: VehBodyAVert1 (Aufbau-Vertikalbeschleunigung) und das rot hervorgehobene WhlAVert1 (Rad-Vertikalbeschleunigung).
    • Long Name (LONG-NAME): Menschenlesbare Langbezeichnung (VehicleBodyAccelerationVertical1, WheelAccelerationVertical1).
    • Description (DESC): Semantische Typdefinition und normative Index-Konvention gem. ISO 8855:
      • Index 0: Rad/Ecke vorne links (Front left, FL)
      • Index 1: Rad/Ecke vorne rechts (Front right, FR)
      • Index 2: Rad/Ecke hinten links (Rear left, RL)
      • Index 3: Rad/Ecke hinten rechts (Rear right, RR)
    • Initiator WP & Milestone: Prozessmetadaten der AUTOSAR-Arbeitsgruppe (Work Package 10.3 Chassis, Milestone S3MS4).
    • Type Name (Metamodell: TYPE-TREF auf Elementtyp): Referenzierter Basistyp der einzelnen Array-Elemente (ApplicationPrimitiveDataType).
      • VehBodyAVert1 referenziert Basistyp A2.
      • WhlAVert1 referenziert den rot markierten Basistyp A5 (skalierter physikalischer Beschleunigungstyp mit zugeordneter CompuMethod / physikalischer Einheit).
    • Number of Element (Metamodell: MAX-NUMBER-OF-ELEMENTS / ARRAY-SIZE): Statische Array-Größe; für beide Typen fest auf 4 dimensioniert (rot markiert bei WhlAVert1).
  • Beziehungen & Kardinalitäten:
    • Komposition: 1 ApplicationArrayDataType besteht aus genau 4 homogenen Elementen des jeweils referenzierten Elementtyps (A2 bzw. A5). Feste Größe, keine variable Array-Länge (ARRAY-SIZE-SEMANTICS = FIXED-SIZE).

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

  • Laufzeit-Dynamik: Nicht zutreffend, da es sich um ein rein deklaratives Datentyp-Metamodell handelt.
  • Toolchain- & Codegenerierungs-Sequenz:
    1. ARXML-Generierung: Die AI-Tabelle wird vom AUTOSAR-Tooling in standardisierte ARXML-Pakete transformiert (<APPLICATION-ARRAY-DATA-TYPE> mit Kindelement <APPLICATION-COMPOSITE-ELEMENT-DATA-PROTOTYPE>).
    2. DataType-Mapping: Ein DataTypeMappingSet verknüpft den ApplicationArrayDataType mit einem plattformspezifischen ImplementationDataType (z. B. typedef float32 WhlAVert1[4] oder typedef sint16 WhlAVert1[4]).
    3. RTE-API-Generierung: Die RTE generiert typisierte Sender-Receiver-Schnittstellen (Rte_Read_<port>_<data>, Rte_Write_<port>_<data>), die typischerweise per Zeigerübergabe (const WhlAVert1* bzw. WhlAVert1*) abgewickelt werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Semantische Index-Integrität:
    • Entwickler von Fahrdynamik-SWCs (z. B. Dämpferregelung, ESP, Fahrwerksregelung) müssen die Indexreihenfolge 0..3 strikt einhalten. Eine Vertauschung von FL/FR/RL/RR führt zu Fehlinterpretationen der Radkinematik mit potenziell sicherheitskritischen Regelfehlern (ASIL-relevant).
  • COM- und Signal-Mapping:
    • Beim Mapping über den COM-Stack auf Busnachrichten (CAN/CAN FD/FlexRay/Ethernet) muss das Array entweder als geschlossenes PDU-Array-Signal oder über 4 separate Signale (GroupSignals innerhalb einer SignalGroup) mit identischer Byte-Reihenfolge abgebildet werden.
  • Speicher-Layout & Alignment:
    • Die 4 Elemente liegen im generierten C-Code lückenlos hintereinander im Speicher. Compiler-Pragmas oder Struktur-Paddings zwischen den Elementen sind unzulässig.
