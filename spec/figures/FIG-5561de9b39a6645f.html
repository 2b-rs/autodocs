1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (cd Data Model), metamodellgetriebenes Daten- und Strukturmodell.
  • Funktionaler Kontext: Spezifiziert die statische Zuordnung und Kardinalitäten zwischen Dienstdateneinheiten der Vermittlungsschicht (Network Service Data Unit, N-SDU) und Protokolldateneinheiten (Network Protocol Data Unit, N-PDU) innerhalb des AUTOSAR Classic BSW-Moduls J1939Tp (gemäß ISO 11783-3 / SAE J1939-21).
  • Architektonische Einordnung: Verortet an der Grenze zwischen oberen Kommunikationsschichten (PduR, J1939Rm, Com, Dcm) und der CAN-Treiberschicht (CanIf). Das Diagramm formalisiert die Multiplexing-/Demultiplexing-Regeln für Single-Frame- und fragmentierte Multi-Packet-Übertragungsverfahren.

2. Komponenten, Entitäten & Schnittstellen

  • Klassen / Entitäten:
    • N-SDU / NSduId: Repräsentiert die logische Nutzlastbotschaft an der oberen Transportschicht-Schnittstelle. Jede N-SDU besitzt eineindeutig (Kardinalität 1:1) eine NSduId.
    • N-PDU / NPduId: Repräsentiert den konkreten CAN-Frame (max. 8 Byte Payload) an der unteren Schnittstelle (CanIf). Jede N-PDU besitzt eineindeutig (Kardinalität 1:1) eine NPduId.
    • Spezialisierungen von N-PDU (Generalisierungs-Hierarchie):
      • J1939PGN (Stereotyp/Zuordnung <Direct>): Direkte CAN-PDU ohne Transport-Protocol-Header (Nutzdaten ≤ 8 Byte).
      • TP.CM Tx (Zuordnung <CMDT>, <BAM>): Connection Management Transmit PDU (PGN 0x00EC00 / 60416; BAM Broadcast Announce oder RTS, CTS, End-of-Message ACK, ConnAbort).
      • TP.CM Rx (Zuordnung <CMDT>): Connection Management Receive PDU (PGN 0x00EC00 / 60416; Handshake-Rückkanal für Peer-to-Peer).
      • TP.DT (Zuordnung <CMDT>, <BAM>): Data Transfer PDU (PGN 0x00EB00 / 60160; transportiert Sequenznummer 1 Byte + 7 Byte segmentierte Nutzlast).
  • Assoziationen & Kardinalitäten (NSduId → NPduId):
    • <Direct> (1 : 1): Genau 1 NPduId pro NSduId (Klasse J1939PGN).
    • <BAM> (1 : 2): Genau 2 NPduIds pro NSduId (TP.CM Tx für BAM-Header und TP.DT für die Datensegmente). Unidirektionaler Broadcast/Global Destination (0xFF).
    • <CMDT> (1 : 3): Genau 3 NPduIds pro NSduId (TP.CM Tx, TP.CM Rx und TP.DT). Bidirektionaler Point-to-Point-Verbindungsaufbau und Flusssteuerung.

3. Dynamisches Verhalten & Sequenzablauf

  • Pfad 1: Direkte Übertragung (<Direct>, ≤ 8 Bytes)
    • Aufruf von J1939Tp_Transmit() leitet die N-SDU ohne TP-Zustandsmaschine synchron/asynchron als einzelne N-PDU (J1939PGN) an CanIf_Transmit() weiter.
    • Abschluss via CanIf_TxConfirmation() → PduR_J1939TpTxConfirmation(E_OK).
  • Pfad 2: Broadcast Announce Message (<BAM>, 9 bis 1785 Bytes)
    • Trigger: J1939Tp_Transmit() an Zieladresse 0xFF.
    • J1939Tp sendet zuerst TP.CM Tx (Control Byte 32 / BAM mit Angabe der Gesamtlänge, Paketanzahl und Ziel-PGN).
    • Nach Inter-Frame-Verzögerung T_BAM (50\,ms ≤ T_r ≤ 200\,ms) sequentielles Aussenden der Segmente über TP.DT (Sequenznummern 1 … n).
    • Kein Empfänger-Handshake; Terminierung nach dem letzten DT-Frame.
  • Pfad 3: Connection Mode Data Transfer (<CMDT>, 9 bis 1785 Bytes)
    • Trigger: J1939Tp_Transmit() an spezifische Zieladresse (Peer-to-Peer).
    • Handshake-Sequenz:
      1. Sender initiiert via TP.CM Tx (Control Byte 16 / RTS).
      2. Empfänger antwortet auf TP.CM Rx mit CTS (Control Byte 17 / CTS mit erlaubter Paketanzahl und Start-Sequenznummer).
      3. Sender feuert das vereinbarte Paket-Burst über TP.DT.
      4. Empfänger bestätigt nach vollständigem Empfang via TP.CM Rx mit End-of-Message ACK (Control Byte 19 / EOM-ACK).
    • Fehler-/Abbruchpfade: Bei Timeout (T_1, T_2, T_3, T_4) oder Protokollverletzung Übertragung von Connection Abort (Control Byte 255 / ConnAbort) via TP.CM Tx, Abbruch der Session und Meldung via PduR_J1939TpTxConfirmation(E_NOT_OK) bzw. PduR_J1939TpRxIndication(E_NOT_OK).

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsmodell (SWS_J1939Tp_00057, SWS_J1939Tp_00199):
    • Im BSW-Konfigurator (J1939Tp.epc / ARXML) bestimmt der Parameter J1939TpTxChannelType / J1939TpRxChannelType zwingend die Anzahl der zu konfigurierenden N-PDU-Referenzen:
      • DIRECT: Exakt 1 PduRef (J1939TpDirectNPdu).
      • BAM: Exakt 2 PduRefs (J1939TpCmNPdu, J1939TpDtNPdu).
      • CMDT: Exakt 3 PduRefs (J1939TpCmTxNPdu, J1939TpCmRxNPdu, J1939TpDtNPdu).
  • CanIf- & PduR-Routing:
    • J1939Tp empfängt Frames aus der CanIf über J1939Tp_RxIndication(CanIfRxPduId, PduInfoPtr). Der Treiber/Dispatcher muss anhand der konfigurierten NPduId erkennen, ob es sich um CM-Steuerframes oder DT-Datenframes handelt.
    • Das Routing im PduR muss für CMDT zwingend bidirektionale Signalwege vorsehen, selbst wenn die eigentliche Nutzdaten-SDU eine reine Tx- bzw. Rx-Verbindung ist.
  • Pufferverwaltung & Copy-Schnittstelle:
    • Für segmentierte Modi (BAM, CMDT) fordert J1939Tp die Daten dynamisch über PduR_J1939TpCopyTxData() bzw. übergibt sie via PduR_J1939TpCopyRxData(). Bei Pufferunterlauf (BUFREQ_E_BUSY) pausiert die Aussendung unter Berücksichtigung der SAE-J1939-Timeout-Schranken.
