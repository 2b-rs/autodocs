1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozessorientiertes Datenfluss- und Aktivitätsdiagramm (AUTOSAR Methodology Flowchart, angelehnt an SPEM/UML-Prozessmodellierung).
  • Architektur-Kontext: Schematische Gesamtdarstellung der klassischen AUTOSAR-Methodologie (AUTOSAR Classic Platform, Referenz R2.1.20 / Dokument AUTOSAR_ECU_Configuration).
  • Technischer Zweck: Definition der normativen Kette von Spezifikations-, Konfigurations- und Generierungsschritten vom fahrzeugweiten Systementwurf (OEM-Ebene) bis zur kompilierten Binärdatei für ein einzelnes Steuergerät (Tier-1-/Integrator-Ebene).

2. Komponenten, Entitäten & Schnittstellen

Datenartefakte (Blue Documents)
  • System Configuration Input : System (.XML / ARXML):
    • Enthält die Basiseingaben: Software Component Descriptions (SWC-D: Ports, Interfaces, Internal Behavior), System Constraints und ECU Resource Descriptions (Hardware-Topologie, Mikrocontroller-Ressourcen).
  • System Configuration Description : System (.XML / ARXML):
    • Vollständiges fahrzeugweites Systemmodell. Enthält das SWC-to-ECU-Mapping, Bus-Topologien (CAN/LIN/FlexRay), Signal-zu-PDU-Mappings und globale Kommunikationsmatrizen.
  • **ECU Extract of System Configuration : System (.XML / ARXML, kurz ECU Extract):**
    • Auf eine spezifische ECU projizierter Teilausschnitt der System Configuration Description. Enthält ausschließlich die für dieses Zielsteuergerät relevanten SWCs, Netzwerk-Frames, Kommunikationsbeziehungen und HW-Ressourcen.
  • ECU Configuration Description (.XML / ARXML, EcucValueCollection):
    • Steuergerätespezifische Detailkonfiguration. Beinhaltet konkrete Parameterwerte für alle BSW-Module (z. B. OS, Com, CanIf, Can, PduR, Dem, Det), RTE-Settings sowie Vendor-spezifische Treiberkonfigurationen.
  • ECU Executable (.exe / ELF / HEX):
    • Lauffähiges Maschinenabbild für den Mikrocontroller, bestehend aus kompiliertem/gelinktem Plattformcode (BSW, MCAL), generiertem Glue-Code (RTE, BSW-Konfigurationsstrukturen) und SWC-Objektdateien.
Prozessaktivitäten / Transformationen (Yellow Process Arrows)
  • Configure System:
    • System-Design-Phase: Definition der Netzwerkarchitektur und Zuordnung (Mapping) logischer Software-Komponenten auf physikalische Steuergeräte.
  • Extract ECU-Specific Information:
    • Filter- und Extraktionsschritt: Formale Generierung des ECU Extracts aus der Gesamtsystembeschreibung.
  • Configure ECU:
    • Steuergeräte-Parametrierung: Manuelle und teilautomatisierte Ausprägung der Parameter aller BSW-Module und der RTE anhand des BSW Module Parameter Definition Meta-Modells.
  • Generate Executable:
    • Werkzeuggestützte Code-Generierung (RTE-Generator, BSW-/MCAL-Generatoren), anschließende Kompilierung des statischen C-Codes sowie der generierten Quell- und Header-Dateien (*_Cfg.c, *_PBcfg.c, Rte.c) und finales Linken.

3. Dynamisches Verhalten & Sequenzablauf

Linearer, artefaktgesteuerter Top-Down-Transformationspfad:

  1. System Definition Phase (OEM-Domäne):
    • Trigger: Vorliegen von SWC-Entwürfen und Netzwerk-/Topologievorgaben.
    • Aktion: Ausführen von Configure System.
    • Ergebnis: Übergang von fragmentierten Eingangsmodellen in die konsolidierte System Configuration Description.
  2. ECU Extraction Phase (OEM-to-Tier-1 Boundary):
    • Aktion: Werkzeuggestützte Ausführung von Extract ECU-Specific Information.
    • Synchronisationspunkt: Formaler Übergabepunkt (Vertragsschnittstelle) zwischen Fahrzeughersteller und Steuergeräte-Zulieferer über den ECU Extract.
  3. ECU Configuration Phase (Tier-1 / Stack-Integrator):
    • Trigger: Import des ECU Extract in das ECU-Konfigurationswerkzeug.
    • Aktion: Durchführung von Configure ECU (Ergänzung von MCAL-, BSW-, OS- und BswM/EcuM-Parametern).
    • Ergebnis: Persistierung der vollständigen ECU Configuration Description.
  4. Build & Link Phase (Target Toolchain):
    • Aktion: Durchführung von Generate Executable:
      1. Aufruf der BSW- und RTE-Generatoren (Generierung von typisiertem C-Code und Pre-Compile/Link-Time-Datenstrukturen).
      2. C-Compilation von statischem BSW-Sourcecode, SWC-Implementierungen und Generaten.
      3. Target-Linker-Lauf gegen Linker-Skripte und Memory-Layouts.
    • Ergebnis: ECU Executable.
  5. Rückkopplungs- und Iterationsschleifen (nicht im Diagramm, prozessual inhärent):
    • Validierungsfehler in Configure ECU (z. B. unzureichende OS-Tasks oder PDU-Fehlanpassungen) erzwingen Korrekturschleifen zurück zur ECU-Parametrierung bzw. Nachforderungen an den System Extract.

4. Normative Relevanz & Entwickler-Hinweise

  • Schnittstellendisziplin & Rollentrennung: Der ECU Extract of System Configuration markiert die normative Trennlinie zwischen Systemintegration und ECU-Softwareentwicklung. Modifikationen an Signallaufzeiten, CAN-IDs oder SWC-Port-Interfaces dürfen nicht lokal in der ECU-Konfiguration vorgenommen werden, sondern müssen über eine Iteration des System Extracts aktualisiert werden.
  • Codegenerierung vs. Quellcode-Pflege: Entwickler dürfen generierte Artefakte (Rte_*.c/h, *_Cfg.h, *_PBcfg.c) unter keinen Umständen manuell patchen. Alle architekturellen Anpassungen erfolgen ausschließlich deklarativ in der ECU Configuration Description (Ecuc) und werden durch erneute Generatorläufe konsistent gehalten.
  • Konfigurationsklassen (Binding Times):
    • Pre-Compile-Time: Konfigurationsparameter steuern Präprozessor-Makros in generierten Headern (führt bei Änderungen zu vollständiger Neukompilierung des Stacks).
    • Link-Time / Post-Build: Konfigurationsparameter erzeugen separate C-Tabellen (PBcfg), die ohne Re-Kompilierung der BSW-C-Dateien gebunden oder re-flasht werden können.
  • Applikations-Entwicklung (SWC): Applikationsentwickler implementieren ausschließlich gegen die virtuellen funktionalen Schnittstellen (VFB / RTE-APIs wie Rte_Read_*, Rte_Write_*), die erst im letzten Prozessschritt durch die Bindung der ECU Configuration Description konkretisiert werden.
