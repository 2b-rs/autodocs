1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm des AUTOSAR M2-Metamodells (Package DOC_SenderReceiverInterface, Software Component Template / VFB-Schnittstellendefinition).
  • Technischer Zweck: Definition der Metaklassen-Struktur des SenderReceiverInterface zur Modellierung asynchroner, datenorientierter 1:n- und n:1-Kommunikationsbeziehungen zwischen Software-Components (SWCs) über den Virtual Functional Bus (VFB) bzw. die Runtime Environment (RTE).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • PortInterface (abstrakt):
    • Stereotypen / Tags: «ARElement» (eigenständig im ARXML-Paketbaum instanziierbares Element), «AtpType» (AUTOSAR Template Type / typisierendes Modellelement).
    • Attribute: + isService: Boolean (Kennzeichnung, ob das Interface einen BSW-Basissoftware-Dienst bereitstellt/konsumiert).
  • DataInterface (abstrakt):
    • Generalisiert PortInterface; Zwischenabstraktion für datenelementbasierte Schnittstellen.
  • SenderReceiverInterface:
    • Spezialisiert DataInterface.
    • Konkrete Schnittstellendefinition für Sender-Receiver-Kommunikation.
    • Komposition +dataElement (1..*) zu VariableDataPrototype: Ein Interface kapselt zwingend mindestens ein Datenelement.
    • Komposition +invalidationPolicy (0..*) zu InvalidationPolicy: Optionale Festlegung von Invalidierungsregeln pro Datenelement.
  • VariableDataPrototype:
    • Spezialisiert AutosarDataPrototype (mit Metaklassen-Basis DataPrototype).
    • Repräsentiert das typisierte Nutzlastelement innerhalb des Interfaces (Payload).
  • InvalidationPolicy:
    • Assoziation +dataElement mit Kardinalität 1 auf ein bestimmtes VariableDataPrototype.
    • Attribute: + handleInvalid: HandleInvalidEnum [0..1] (Reaktion der RTE bei Erkennung eines ungültigen Signalwerts).
  • «enumeration» HandleInvalidEnum:
    • keep: Der zuletzt gültige Wert verbleibt im Empfangspuffer; die RTE signalisiert den Status über den API-Rückgabewert (RTE_E_INVALID).
    • replace: Der ungültige Wert wird im Puffer automatisch durch den im Metamodell definierten Initialwert (initValue) ersetzt.
    • dontInvalidate: Keine Sonderbehandlung; der empfangene Rohwert wird ungefiltert an die Applikation durchgereicht bzw. Invalidation ist deaktiviert.

3. Dynamisches Verhalten & Sequenzablauf

Die Metaklassen steuern die Codegenerierung für die Laufzeitinteraktion über die RTE:

  1. Sende-Pfad (Invalidierung):
    • Sender-SWC ruft Rte_Invalidate_<p>_<o>() auf.
    • RTE setzt das im Metamodell/Signal-Layout konfigurierte Invalidierungsbit/-muster (z. B. ComSignalDataInvalidValue) und delegiert an den COM-Stack (Com_SendSignal()).
  2. Empfangs-Pfad (Auswertung & Filterung):
    • Signal erreicht den COM-Layer / die RTE.
    • RTE prüft das Datum gegen den Invalidierungswert:
      • Bedingung handleInvalid == replace: Pufferinhalt wird auf initValue zurückgesetzt; optionales Auslösen eines DataReceiveErrorEvent.
      • Bedingung handleInvalid == keep: Puffer bleibt unverändert; Rte_Read_<p>_<o>() gibt RTE_E_INVALID zurück.
      • Bedingung handleInvalid == dontInvalidate: Wert wird als reguläres Datum behandelt.
  3. Runnable-Aktivierung:
    • Ungültige Daten triggern abhängig von der SWC-Konfiguration entweder ein DataReceivedEvent (bei Weiterleitung) oder ein DataReceiveErrorEvent zur Fehlerbehandlung im Task-Kontext.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-API-Vertrag:
    • Jedes aggregierte VariableDataPrototype führt zur Generierung der typisierten RTE-Schnittstellen:
      • Nicht-gepuffert (last-is-best): Rte_Write_<p>_<d>(), Rte_Read_<p>_<d>(), Rte_Invalidate_<p>_<d>().
      • Gepuffert (FIFO/queued): Rte_Send_<p>_<d>(), Rte_Receive_<p>_<d>().
  • Modellierungsrestriktion:
    • Kardinalität 1..* erzwingt: Ein SenderReceiverInterface ohne mindestens ein definiertes VariableDataPrototype ist syntaktisch ungültig (Schema-Validierungsfehler im ARXML).
  • Konsistenzanforderung InvalidationPolicy:
    • Wird handleInvalid = replace konfiguriert, muss am assoziierten VariableDataPrototype zwingend ein kompatibler initValue definiert sein; andernfalls bricht der RTE-Generator mit einem Validierungsfehler ab.
  • COM-/Signal-Mapping:
    • Jedes VariableDataPrototype wird in der Systembeschreibung (System Extract) auf ein ISignal abgebildet. Die InvalidationPolicy muss mit der COM-Konfiguration (ComSignalDataInvalidValue, ComRxDataTimeoutAction) harmonisiert werden, um divergierendes Verhalten zwischen COM-Stack und RTE auszuschließen.
