1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Binäres Protokoll- und PDU-Header-Layout (Byte-Stream-Spezifikation mit variablen und konditionalen Feldern).
  • Technischer Zweck: Spezifikation der Serialisierungsreihenfolge, Bitbreiten und Längenindikatoren für optionale Metadaten im Extension Header des AUTOSAR Log and Trace Protocols (AUTOSAR_FO_PRS_LogAndTraceProtocol, R24-11 / R25-11).
  • Architektur-Einordnung:
    • Standardisiert den transportunabhängigen Austausch von Logging- und Tracing-Nachrichten über Plattformgrenzen hinweg (Classic Platform via DLT-Modul / Adaptive Platform via ara::log).
    • Erweitert den Standard-Header um dynamische Kontext-, Debug-, Filter- und Transportinformationen (z. B. ECU-, Applikations- und Thread-Kontexte, Quellcode-Orte, Security/Privacy-Level sowie nachrichtenbasierte Segmentierung).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert eine sequenzielle Kette von TLV-ähnlichen (Type-Length-Value bzw. Length-Value) Feldern. Die Byte-Offsets sind dynamisch (dyn, dyn1 bis dyn10), da jedes Feld optional ist und die Existenz über Bit-Flags im vorangehenden Header gesteuert wird:

  • ECU (ECU-ID):
    • Offset 0: 8-Bit-Längenfeld (Länge der ECU-ID in Bytes).
    • Offset 1 .. dyn: ECU-ID als ASCII-Zeichenkette.
  • APID (Application-ID):
    • Offset dyn1: 8-Bit-Längenfeld (Anzahl Bytes).
    • Offset dyn1+1 ..: Application-ID als ASCII-Zeichenkette.
  • CTID (Context-ID):
    • Offset dyn2: 8-Bit-Längenfeld (Anzahl Bytes).
    • Offset dyn2+1 ..: Context-ID als ASCII-Zeichenkette.
  • SEID (Session-ID):
    • Offset dyn3 .. dyn3+3: 32-Bit Unsigned Integer (uint32) zur Identifikation der Logging-Session.
  • FINA (File Name):
    • Offset dyn4: 8-Bit-Längenfeld (Anzahl UTF-8 Code Units).
    • Offset dyn4+1 ..: UTF-8 codierter Quellcode-Dateiname.
  • LINR (Line Number):
    • Offset dyn5 .. dyn5+3: 32-Bit Unsigned Integer (uint32) für die Zeilennummer im Quelltext.
  • TAGS (Structured Tags):
    • Offset dyn6: NOTG (uint8) – Gesamtzahl der enthaltenen Tags.
    • Wiederholte Struktur für Tag_1 bis Tag_<n>:
      • 8-Bit-Längenfeld (Länge des Tag-Namens in Bytes).
      • Nutzdaten als UTF-8 Code Units.
  • PRIV (Privacy Level):
    • Offset dyn9: 8-Bit Unsigned Integer (uint8) zur Kennzeichnung von Datenschutz-/Klassifizierungsstufen (z. B. GDPR/DSGVO-Filterung).
  • SGMT (Segmentation-Info):
    • Offset dyn10: 8-Bit-Längenfeld für die gesamte Segmentierungs-Information.
    • Offset dyn10+1: 8-Bit FrameType-Enumeration:
      • FirstFrame: Nachfolgend 64-Bit Gesamtlänge (uint64, Offsets dyn10+2 .. dyn10+9).
      • ConsecutiveFrame: Nachfolgend 32-Bit Sequenzzähler (uint32, Offsets dyn10+2 .. dyn10+5).
      • LastFrame: 0 Bit / keine zusätzlichen Parameter.
      • AbortFrame: 8-Bit Abbruchgrund (Abort-Reason, Offset dyn10+2).
  • XYZ (Future Extension Template):
    • Generisches Schema für künftige Erweiterungen: Length of <future_field> gefolgt von Value of <future_field>.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

  • Serialisierung & Deserialisierung:
    • Kein klassischer synchroner Call-Ablauf, sondern nachrichtenbasierte Zustandskodierung.
    • Der Deserializer parst den Stream streng sequenziell: Jedes Feld liest zunächst die dynamische Länge aus, um den Startoffset des Folgefeldes (dyn_next = dyn_current + length + header_overhead) zu berechnen.
  • Segmentierungs-Zustandsmaschine (SGMT):
    1. Start: Übertragung größerer Log-Payloads beginnt mit FirstFrame (übermittelt die Gesamtpuffergröße via 64-bit Total Length).
    2. Fortschritt: Sukzessive Übermittlung von ConsecutiveFrame (fortlaufender 32-Bit Sequence Counter zur Erkennung von Paketverlusten oder Fehlordnungen im Transportkanal).
    3. Abschluss / Abbruch: Erfolgreiches Ende via LastFrame (ohne Payload-Overhead) oder vorzeitiger Abbruch via AbortFrame mit normiertem 8-Bit-Fehlercode.

4. Normative Relevanz & Entwickler-Hinweise

  • Endianness: Numerische Multibyte-Felder (SessionID, LineNumber, 64-Bit Total Length, 32-Bit Sequence Counter) unterliegen der im Standard-Header definierten Endianness (typischerweise Big-Endian/Network Byte Order bzw. per Header-Flag umschaltbar).
  • String-Codierung:
    • ECU, APID, CTID sind als ASCII spezifiziert. Im Gegensatz zu älteren DLT-Standards (Classic AUTOSAR mit festen 4-Byte-Identifiern) sind diese IDs hier durch vorangestellte 8-Bit-Längenfelder variabel bis maximal 255 Bytes dimensionierbar.
    • FINA und TAGS verwenden explizit UTF-8 Code Units; Parser müssen ungültige UTF-8-Sequenzen robust abfangen.
  • Puffer- und Zero-Copy-Strategien:
    • Wegen variabler Offset-Verschiebungen (dynX) kann im Embedded-Treiber kein C-Struct-Casting (packed struct) verwendet werden. Das Framing erfordert positionsbasiertes Byte-Packing/-Unpacking (Pointer-Arithmetik).
    • Maximallänge von Metadaten-Strings ist hardwarenah zu begrenzen (Stack-Overflow-Vermeidung bei Reassembly).
  • SGMT im IP-Transport:
    • Dient der Fragmentierung auf Anwendungsebene, wenn das unterlagerte Transportprotokoll (z. B. UDP-Datagramme oder CAN-FD PDUs) keine ausreichende MTU bietet oder TCP-Streaming segmentiert analysiert werden muss.
