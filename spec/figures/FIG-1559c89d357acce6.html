1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Komponentendiagramm / Port-Strukturmodell gemäß AUTOSAR_TPS_SoftwareComponentTemplate (Kapitel 13: Service-oriented Communication, Figure 13.5: Client examples).
  • Architektur-Kontext: AUTOSAR Classic Platform (R22-11, R23-11). Spezifikation des Strukturmusters für Service-Konsumenten (Client-SWCs) zur Anbindung an serviceorientierte Kommunikation (SOME/IP über Service Discovery / BswM).
  • Technischer Zweck: Gegenüberstellung zweier standardisierter Client-Entwurfsmuster (Client_SWC_1 vs. Client_SWC_2) zur Modellierung von:
  • Empfang von SOME/IP-Events via Sender-Receiver-Kommunikation.
  • Methodenaufrufen (Request-Response via Client-Server-R-Port vs. Fire-and-Forget via Sender-Receiver-P-Port).
  • Interaktion mit dem Basic Software Mode Manager (BswM) zur dynamischen Subskriptions- und Verfügbarkeitssteuerung von SOME/IP-Eventgroups und Services.

2. Komponenten, Entitäten & Schnittstellen

Dargestellt sind zwei atomare Softwarekomponenten-Typen (ApplicationSwComponentType) mit ihren Port-Prototypen:

#### Client_SWC_1 (Aggregiertes Subskriptionsmodell)

  • Event1 [R], Event2 [R]: RPortPrototype, typisiert über SenderReceiverInterface. Dienen dem konsumierenden Empfang deserialisierter SOME/IP-Events.
  • Method [R]: RPortPrototype, typisiert über ClientServerInterface. Realisiert synchrone oder asynchrone Client-Server-Aufrufe mit Antwortpfad (Request-Response).
  • EventSubscription_ModeRequestPort [P]: PPortPrototype, typisiert über ModeSwitchInterface. Sendet Modusanforderungen an den BswM zur Aktivierung/Deaktivierung der Eventgruppen-Subskription (SubscribeEventgroup).
  • SubscriptionStatus_Events [R]: RPortPrototype, typisiert über ModeSwitchInterface. Empfängt Modus-Umschaltungen vom BswM zur Signalisierung des Subskriptionszustands (z. B. SUBSCRIPTION_ACK oder Timeout/Nack).

#### Client_SWC_2 (Feingranulares / orthogonales Subskriptionsmodell mit Fire-and-Forget)

  • Event1 [R], Event2 [R]: RPortPrototype, identisch zu Client_SWC_1.
  • Method [R]: RPortPrototype (Client-Server) für bidirektionale Request-Response-Methoden.
  • Fire-and-Forget_Method [P]: PPortPrototype, typisiert über SenderReceiverInterface. AUTOSAR-konforme Modellierung von One-Way-Methodenaufrufen: Der Client sendet die Aufrufparameter ohne Blockieren und ohne Erwartung einer Rückmeldung/Rückgabewerts an den Server.
  • Event12Subscription_ModeRequestPort [P]: PPortPrototype (Mode Request) zur gezielten Subskriptionsanforderung für die Eventgruppe von Event1 und Event2.
  • SubscriptionStatus_Event12 [R]: RPortPrototype (Mode Switch) zur Statusrückmeldung der Eventgruppe 1 & 2.
  • MethodSubscription_ModeRequestPort [P]: PPortPrototype (Mode Request) zur expliziten Anforderung/Freigabe der Methoden-Service-Nutzung (Client Service Handling via SOME/IP-SD FindService).
  • SubscriptionStatus_Methods [R]: RPortPrototype (Mode Switch) zur Rückmeldung der Dienstverfügbarkeit für Methodenaufrufe.

3. Dynamisches Verhalten & Sequenzablauf

```

[Client SWC] [RTE / BswM] [SOME/IP-SD / SoAd]

| | |

|-- Rte_Write_ModeRequestPort ->| |

| (Request: SUBSCRIBED) |-- BswMSdClientServiceRequest --->|

| | |-- SOME/IP-SD SubscribeEventgroup ->

| |<-- SD Eventgroup Ack ------------|

|<-- SwcModeSwitchEvent --------| |

| (Status: SUBSCRIBED) | |

| | |

|<------------------------------+-- Rte_Read_Event1/2 -------------| (SOME/IP Event empfangen)

| | |

|-- Rte_Call_Method() --------->|--------------------------------->| (Request-Response)

|<-- Callback / Return ---------|<---------------------------------|

| | |

|-- Rte_Write_FireAndForget() ->|--------------------------------->| (One-Way, non-blocking)

```

  1. Subskriptions-Trigger:
  • Client initiiert Subskription über EventSubscription_ModeRequestPort (Aufruf von Rte_Write_<port>_<modeGroup>()).
  • BswM empfängt den Request und stößt im Service-Discovery-Modul (Sd) das Senden der SubscribeEventgroup-Nachricht an.
  1. Status-Rückmeldung (Asynchron):
  • Nach Erhalt des SubscribeEventgroupAck bzw. Find/OfferService-Status schaltet BswM den Modus des korrespondierenden SubscriptionStatus-Ports um.
  • RTE feuert ein SwcModeSwitchEvent in der Client-SWC; Runnables zur Event-Verarbeitung werden freigegeben.
  1. Nutzdaten-Austausch:
  • Events: Eintreffende SOME/IP-Nachrichten passieren SOME/IP-Transformer, PduR und RTE; Abruf über Rte_Read() (Polling) oder getriggert über DataReceivedEvent.
  • Method (Request-Response): Aufruf über Rte_Call_<port>_<operation>(). Blockierend synchron oder asynchron mit Rte_Result().
  • Fire-and-Forget: Aufruf über Rte_Write_<port>_<dataElement>(). Rein asynchron ohne Rückkanal, direktes Verlassen des Aufrufs nach PDU-Übergabe an den Stack.
  1. Fehler- und Abbruchverhalten:
  • Bei SD-Timeout (TTL abgelaufen) oder Link-Down wechselt der Modus an SubscriptionStatus_* auf NOT_SUBSCRIBED. Die SWC muss Methodenaufrufe unterbinden und Event-Caches invalidieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Keine direkte SWC-zu-SWC-Verbindung für Mode-Ports: Die Ports Subscription_ModeRequestPort [P] und SubscriptionStatus_ [R] dürfen im System-Composition-Diagramm nicht direkt zwischen Client und Server verbunden werden. Sie sind zwingend über Assembly-Connectors mit den Service-Ports des BswM zu verbinden.
  • Fire-and-Forget Semantik: Für Fire-and-Forget-Methoden wird in AUTOSAR Classic kein ClientServerInterface mit Void-Return verwendet, sondern ein SenderReceiverInterface am P-Port des Clients. Entwickler müssen beachten: Es existiert kein Rückgabewert, kein RTE-Fehlerstatus über Server-Exceptions (Std_ReturnType spiegelt nur PDU-Pufferung wider) und kein ClientServer-Callout-Context.
  • Granularität vs. Overhead:
  • Muster Client_SWC_1 minimiert den BswM- und RTE-Konfigurationsaufwand, da Events und Methoden als monolithische Service-Instanz behandelt werden.
  • Muster Client_SWC_2 erlaubt selektives Powermanagement und Bandbreitenoptimierung im Fahrzeugnetzwerk (z. B. Aktivierung rechenintensiver/zyklischer Event-Streams nur dann, wenn die spezifische Applikationsfunktion aktiv ist, während Methodenkanäle separat offen gehalten werden).
  • RTE-API-Vertrag:
  • Für Method: Generierung von Rte_Call_<Port>_<Operation>().
  • Für Fire-and-Forget_Method: Generierung von Rte_Write_<Port>_<DataElement>().
  • Für Status-Ports: Konfiguration von ModeAccessPoints oder ModeSwitchEvent-Triggern in der InternalBehavior-Beschreibung der Client-SWC.
