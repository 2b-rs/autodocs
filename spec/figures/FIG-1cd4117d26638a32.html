Figure 4.17: Software Cluster Overview

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR M2-Metamodell-Ausschnitt (UML-Klassendiagramm), spezifiziert in AUTOSAR_TPS_TimingExtensions (R20-11).
  • Technischer Zweck & Einordnung:
  • Modellierung der strukturellen Integration von Software-Clustern der Classic Platform (CpSoftwareCluster) in das Gesamtsystem (System).
  • Dient der logischen und physikalischen Kapselung von Software-Komponenten (SWCs) für modulare Update-Konzepte (OTA / Software Cluster Updates), Multicore-/Partitionierungs-Strategien und herstellerübergreifendes Deployment.
  • Ermöglicht sowohl eine grobgranulare Zuweisung kompletter Kompositionen als auch eine instanzgenaue Zuweisung einzelner SWC-Prototypen zu separaten Clustern.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Stereotypen

  • System («ARElement», «AtpStructureElement», «UploadableDesignElement»):

Wurzelelement der Systemkonfiguration.

  • Attribute:
  • containerIPduHeaderByteOrder: ByteOrderEnum [0..1] – Endianness des Headers für Container-I-PDUs.
  • ecuExtractVersion: RevisionLabelString [0..1] – Versionsstand des abgeleiteten ECU-Extracts.
  • pncVectorLength: PositiveInteger [0..1] & pncVectorOffset: PositiveInteger [0..1] – Dimensionierung und Offset des Partial-Network-Cluster-Bitvektors.
  • systemVersion: RevisionLabelString [0..1] – Optionale Version der System Description.
  • RootSwCompositionPrototype («AtpPrototype», «Identifiable»):

Top-Level-Prototyp der gesamten Software-Architektur des Systems.

  • CompositionSwComponentType («SwComponentType»):

Hierarchischer Kompositionstyp, der Sub-Komponenten bündelt.

  • SwComponentPrototype («AtpPrototype»):

Konkrete Komponenten-Instanz innerhalb einer Komposition.

  • CpSoftwareCluster («ARElement»):

Repräsentiert die Kapselungseinheit für Classic Platform Software-Cluster (mmt.RestrictToStandards = CP).

  • Attribute:
  • softwareClusterId: PositiveInteger [0..1] – Optionale eindeutige numerische Kennung des Software-Clusters.
  • SwComponentPrototypeAssignment:

Dediziertes Mapping-Element zur feingranularen Zuweisung eines Komponenten-Prototyps zu einem Cluster via Instanzreferenz.

#### Beziehungen, Kardinalitäten & Stereotypen

  • System ➔ RootSwCompositionPrototype (+rootSoftwareComposition, 0..1):

Komposition mit «atpVariation, atpSplitable». Definiert die primäre Software-Komposition des Systems.

  • RootSwCompositionPrototype ➔ CompositionSwComponentType (+softwareComposition, 0..1):

Typisierung via «isOfType» unter {redefines atpType} mit Multiplizität 0..1.

  • *CompositionSwComponentType ➔ SwComponentPrototype (+component, 0..):**

Komposition mit «atpVariation, atpSplitable». Enthält die Komponentenprototypen des Software-Designs.

  • *System ➔ CpSoftwareCluster (+swCluster, 0..):**

Referenzierende Aggregation mit «atpSplitable, atpVariation». Bindet beliebig viele Cluster an das System.

  • *CpSoftwareCluster ➔ CompositionSwComponentType (+swComposition, 0..):**

Assoziation mit «atpVariation, atpSplitable».

  • Tag: vh.latestBindingTime = systemDesignTime. Ganze Kompositionsstrukturen werden früh zur Systementwurfszeit an den Cluster gebunden.
  • *CpSoftwareCluster ➔ SwComponentPrototypeAssignment (+swComponentAssignment, 0..):**

Komposition mit «atpVariation, atpSplitable».

  • Tag: vh.latestBindingTime = postBuild. Erlaubt späte, instanzbezogene Cluster-Zuordnungen bis zur Post-Build-Phase.
  • SwComponentPrototypeAssignment ➔ SwComponentPrototype (+swComponent, 0..1):

Gerichtete Assoziation via Instanzreferenz («instanceRef»). Referenziert den spezifischen Komponenten-Prototyp im Architekturbaum.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein M2-Klassendiagramm der Informationsarchitektur handelt, existiert kein Ausführungsablauf zur CPU-Laufzeit. Der methodische Verarbeitungsablauf im AUTOSAR-Workflow gestaltet sich wie folgt:

  1. System Design Time:
  • Modellierung der VFB-Architektur (RootSwCompositionPrototype, CompositionSwComponentType).
  • Grobe Cluster-Zuweisung vollständiger Funktionsbündel über CpSoftwareCluster.swComposition.
  1. ECU Partitioning & Post-Build Configuration:
  • Granulare Bindung einzelner Komponentenprototypen über SwComponentPrototypeAssignment («instanceRef»).
  • Auflösung von Varianten (atpVariation) bis zur Bindungszeit postBuild.
  1. Build & Toolchain:
  • Extraktion der Cluster-Artefakte für getrennte RTE-, OS- und Memory-Protection-Generierung pro Cluster.

4. Normative Relevanz & Entwickler-Hinweise

  • Metamodell-Gültigkeit & Normativer Kontext: Die Modellierung definiert die formale Struktur zur Abbildung von Software-Clustern der Classic Platform (mmt.RestrictToStandards = CP) innerhalb einer AUTOSAR-Systembeschreibung (System). Das System ist zudem als «UploadableDesignElement» qualifiziert.
  • Optionale Wurzelelemente: Sowohl die Versionsangabe des Gesamtsystems (systemVersion) als auch die Typisierung der Software-Wurzelkomposition (+softwareComposition) besitzen die Kardinalität 0..1, was eine flexible, schrittweise Befüllung des Metamodells im Systementwurf erlaubt.
  • Variabilitätsmanagement: Sowohl die Aggregation der Cluster am System (+swCluster) als auch die Zuordnungen von Kompositionen (+swComposition) und Komponenten-Prototypen (+swComponentAssignment) sind als «atpSplitable» und «atpVariation» modelliert. Cluster-Definitionen können somit über mehrere ARXML-Dateien fragmentiert und über Systemvarianten hinweg konditioniert werden.
  • Instanzreferenzen: Bei SwComponentPrototypeAssignment handelt es sich um eine Instanzreferenz («instanceRef») auf einen SwComponentPrototype, die den vollen hierarchischen Kontext innerhalb der Wurzelkomposition auflösen muss.

Begleitender Spezifikationstext:

Specification of Timing Extensions for Classic Platform AUTOSAR CP R23-11 During system design software clusters are defined. Software clusters consist of an arbitrary number of software components as sketched in Figure 4.17. The internal structure of those software clusters, like further composition software components and atomic software components, are not known at system design time. Typically, those internals, especially the internal behaviors of the atomic software components along with runnable entities, are the result of further steps taken during the development of the software components. Eventually, the runnable entities need to be assigned to appropriate operating system tasks to ensure the proper execution and therefore a correct provision of the expected functionality realized by the runnable entities. Or, in other words, the operating system being used must provide the needed execution contexts for the runnable entities of a software cluster, if the software cluster is supposed to provide such temporal and dynamic resources.
