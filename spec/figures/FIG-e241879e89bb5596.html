1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR BSW-Schichtenarchitekturmodell (Blockdiagramm) mit detailliertem Fokus-Zoom auf die Subkomponenten der Communication Services.
  • Funktionale Einordnung: Verortung des BSW-Moduls J1939Nm (SAE J1939 Network Management) innerhalb der AUTOSAR Classic Platform (CP) Release R24-11 / R25-11.
  • Architektonischer Zweck:
    • Das Gesamtmodell veranschaulicht die Einbettung der Communication Services zwischen RTE (oben) und der Communication Hardware Abstraction (unten).
    • Die Detailansicht spezifiziert die vertikale und horizontale Eingliederung des J1939Nm in den fahrzeugspezifischen Kommunikationsstack (Commercial Vehicles / Heavy Duty).
    • J1939Nm realisiert das dezentrale Adressierungs- und Netzwerkmanagement nach SAE J1939/81 (Address Claiming) und adaptiert dieses an das standardisierte AUTOSAR NM-Konzept.

2. Komponenten, Entitäten & Schnittstellen

  • Ebenen (Top-Level):
    • Application Layer: Software-Komponenten (SWCs), Sensor-/Aktorkomponenten.
    • RTE (Runtime Infrastructure / Runtime Environment): Entkopplung von Applikation und Basissoftware.
    • BSW-Schichten: Services (inkl. Communication Services), HW-Abstraktion (Onboard Dev., Memory, COM, I/O), Treiber (Microcontroller, Memory, Communication, I/O), Complex Drivers (CDD) mit direktem Hardware- und RTE-Zugriff.
    • Microcontroller (µC): Physische Ausführungseinheit.
  • Module der Communication Services (Detailansicht):
    • Generic NM Interface (Nm): Zentraler Abstraktionslayer für plattformweites Netzwerkmanagement; leitet generische NM-Befehle an bus-spezifische NM-Module weiter.
    • J1939 NM (J1939Nm): Spezifisches NM-Modul zur Ausführung des Address-Claiming-Verfahrens gemäß SAE J1939/81 (im Diagramm optisch hervorgehoben).
    • COM Manager (ComM): Koordiniert Kommunikationszustände (No Comm, Silent Comm, Full Comm) und verwaltet Bus-Validierungsanforderungen.
    • AUTOSAR COM (Com): Signalbasiertes Packing/Unpacking von I-PDUs.
    • J1939 Diagnostic Comm. Manager (J1939Dcm): Behandelt J1939-spezifische Diagnoseprotokolle (DM1 bis DM3x gem. SAE J1939/73).
    • CAN State Manager (CanSM): Zustandsmaschine für CAN-Controller und Transceiver via CanIf.
    • PDU Router (PduR): Zentrales Gateway für I-PDUs zwischen oberen Kommunikationsmodulen (Com, Dcm, J1939Dcm, J1939Rm) und Transportprotokollen bzw. Schnittstellen.
    • J1939 Funct.-Safety-Comm.-Protocol: Modul für sicherheitsgerichtete Kommunikation (J1939-76).
    • J1939 Req.-Manager (J1939Rm): Bearbeitet Requests (PGN 59904) und Acknowledgments (PGN 59392).
    • CAN TP (CanTp) & J1939 TP (J1939Tp): Transportprotokolle für segmentierte Übertragungen (BAM – Broadcast Announce Message, RTS/CTS – Connection Mode Data Transfer).
  • Beziehungen und Schnittstellen-Hierarchie bezüglich J1939Nm:
    • Obere Schnittstelle: Direkte vertikale Anbindung an das Generic NM Interface (Nm). Nm ruft J1939Nm-Dienste auf (J1939Nm_NetworkRequest(), J1939Nm_NetworkRelease()) und empfängt Statusänderungen (Nm_NetworkMode(), Nm_BusSleepMode()).
    • Untere/Horizontale Schnittstelle: Interaktion mit dem PDU-Router (PduR) bzw. CanIf zum Senden und Empfangen von Address-Claiming-Frames (PGN 60928) und Cannot-Claim-Address-Frames (Source Address 254).
    • Koordination mit ComM: Indirekt über das Nm gesteuert; ComM fordert Communication Modes über Nm an.

3. Dynamisches Verhalten & Sequenzablauf

Obwohl als statisches Architekturdiagramm dargestellt, erzwingt die Topologie folgenden normativen dynamischen Ablauf für J1939Nm:

  1. Trigger & Initialisierung:
    • ComM fordert COMM_FULL_COMMUNICATION über Nm_NetworkRequest() an.
    • Nm ruft synchron J1939Nm_NetworkRequest() auf.
  2. Address Claiming Phase (SAE J1939/81):
    • J1939Nm initiiert das Address Claiming und sendet ein Address Claim PDU (PGN 60928) via CanIf/PduR.
    • Start des internen Timers für die Bus-Arbitrierung (Wait-Time 10\,ms / 250\,ms je nach Adresstyp).
    • Arbitrierungsfall (Konflikt): Empfängt J1939Nm via Rx-Indication dieselbe Adresse von einem externen Steuergerät, vergleicht es den 64-Bit NAME (Priorität):
      • Eigener NAME höherwertig (numerisch kleiner): Eigene Adresse wird verteidigt; erneutes Address Claim PDU wird abgesetzt.
      • Eigener NAME niederwertig (numerisch größer): Eigene Adresse verloren. Sofern konfiguriert, wird eine Alternativadresse claimed (Arbitrary Address Capable) oder ein "Cannot Claim Address" (Null-Adresse 0xFE) gemeldet.
  3. Statusrückmeldung & Validierung:
    • Nach erfolgreichem Claiming meldet J1939Nm die Betriebsbereitschaft asynchron via Callback an das Generic NM Interface zurück.
    • Das Nm schaltet die übergeordneten Kanäle für reguläre I-PDUs im PduR und ComM frei.
  4. Fehlerpfade:
    • Schlägt das Address Claiming fehl, erfolgt Meldung an das Dem (Diagnostic Event Manager) sowie Rückmeldung über Nm an den ComM zur Einleitung von Fallback- bzw. Silent-Zuständen.

4. Normative Relevanz & Entwickler-Hinweise

  • Stack-Konfiguration & Parameter:
    • Das Generic NM Interface (Nm) muss für Multiplexing über NmChannelConfig konfiguriert werden, wobei der Bus-Typ explizit auf NM_BUSNM_J1939NM eingestellt ist (im Gegensatz zu CanNm oder UdpNm).
    • Konfiguration des eindeutigen 64-Bit J1939-NAME (J1939NmNode Container in ARXML/AUTOSAR BSW-Konfiguration): Identity Number, Manufacturer Code, ECU Instance, Function Instance, Function, Vehicle System, System Instance, Industry Group, Arbitrary Address Capable Bit.
  • PDU-Routing & Adressauflösung:
    • J1939Nm steuert die dynamische Source-Adresse des Steuergeräts. Entwickler von J1939Tp, J1939Rm und J1939Dcm müssen sicherstellen, dass deren ausgehende Metadaten (Source Address in der PDU-Header-ID) mit der von J1939Nm verifizierten Adresse synchronisiert werden (J1939Nm_GetLocalAddress()).
  • Einschränkungen:
    • J1939Nm implementiert kein koordiniertes Partial Networking (CAN PN) oder Synchronized Sleep wie das klassische OSEK/AUTOSAR CanNm. Es dient primär der dynamischen logischen Knotenadressierung und Bus-Präsenzanzeige im Nutzfahrzeugbereich.
    • Das Modul blockiert regulären Sende-Traffic über den PduR, bis das Address Claiming erfolgreich abgeschlossen ist. Treiber und Applikationen müssen Latenzen während der Claiming-Phase (>250\,ms) fehlertolerant behandeln.
