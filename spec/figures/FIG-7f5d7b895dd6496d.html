1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt des AUTOSAR System Template (FibexCore: PDUOverview), Release R3.0.7.
  • Zweck & Einordnung: Definition des abstrakten Kommunikationsmodells für Protocol Data Units (PDUs), deren Typisierungen/Spezialisierungen, die Aggregation in PDU-Gruppen, das zeitliche Übertragungsverhalten (IPduTiming) sowie die physische Einbettung (PduToFrameMapping, IPduTriggering) in Bus-Frames auf Netzwerkkanälen (PhysicalChannel). Bildet das verbindliche Bindeglied zwischen Interaktionsschicht (COM/DCM/NM) und Transportschicht/Bus-Treibern (CanIf, FrIf, LinIf).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Spezialisierungshierarchie
  • Pdu (spezialisiert FibexElement, abstract base):
    • Wurzel aller Protokolldateneinheiten im Systemmodell.
  • NmPdu (spezialisiert Pdu):
    • PDU für das AUTOSAR Network Management.
    • Attribute: length: Int, nmCbvPosition: Int [0..1] (Offset des Control Bit Vectors), nmNidPosition: Int [0..1] (Offset der Node Identifier), nmUserDataLength: Int [0..1].
  • IPdu (spezialisiert Pdu, Interaction-Layer PDU):
    • Basisklasse für COM-, Diagnose- und Transport-PDUs.
    • Attribute: length: Int, unusedBitPattern: Int [0..1] (Füllmuster ungenutzter Bits).
    • Spezialisierungen von IPdu:
      • SignalIPdu: Standard-PDU zur Kapselung von Applikationssignalen.
      • MultiplexedIPdu: PDU mit dynamischem Layout anhand eines Selektorfeldes.
        • Attribute: selectorFieldStartPosition: Int, selectorFieldLength: Int, selectorFieldByteOrder: ByteOrderEnum, triggerMode: TriggerMode.
      • NPdu: Network-PDU für Transportprotokolle (z. B. CanTp, FrTp).
      • DcmIPdu: Diagnose-PDU für den Diagnostic Communication Manager (UDS/OBD).
Strukturelle Beziehungen, Mappings & Topologie
  • Frame (spezialisiert FibexElement):
    • Physischer Bus-Frame (z. B. CAN-/FlexRay-Frame) mit Attribut frameLength: Int.
    • Komposition (+pduToFrameMapping 0..*): Enthält 0..n Instanzen von PduToFrameMapping.
  • PduToFrameMapping (Stereotyp: «atpPrototype», spezialisiert Identifiable):
    • Definiert die Lage und Kodierung einer PDU innerhalb des Frames.
    • Attribute: startPosition: Int (Bit-/Byte-Offset), packingByteOrder: ByteOrderEnum, updateIndicationBitPosition: Int [0..1] (Position des Update-Bits im Frame).
    • Assoziation: Referenziert genau eine Pdu (+pdu 1).
  • IPduGroup (spezialisiert FibexElement):
    • Laufzeit-schaltbare PDU-Gruppierung.
    • Attribute: communicationDirection: communicationDirectionType (IN/OUT), communicationMode: String.
    • Assoziationen: Rekursive Selbstreferenz (+containedIPduGroups 0..*), Aggregation von IPdus (+iPdu 0..*).
  • CoreTopology::PhysicalChannel (spezialisiert Identifiable):
    • Physischer Kommunikationskanal (CAN, LIN, FlexRay).
    • Komposition («splitable», +iPduTriggering 0..*): Enthält Trigger-Definitionen für PDUs.
  • IPduTriggering (spezialisiert Identifiable):
    • Repräsentiert das Ankoppeln einer PDU an einen physischen Buskanal.
    • Multiplizitäten: 1..* Triggerings referenzieren genau eine IPdu (+iPdu 1).
    • Assoziation: Referenziert optional +timingRequirement 0..1 (IPduTiming).
  • IPduTiming (spezialisiert Identifiable):
    • Definiert Übertragungsmetriken; Komposition von SignalIPdu (+iPduTimingSpecification 1).
    • Attribut: minimumDelay: Float [0..1] (Mindestabstand zwischen zwei Sendevorgängen).
Enumerationen
  • Enumerations::ByteOrderEnum: mostSignificantByteFirst (Big-Endian/Motorola), mostSignificantByteLast (Little-Endian/Intel).
  • TriggerMode: Bestimmt das Sende-Triggerverhalten von MultiplexedIPdu: none, staticPartTrigger, dynamicPartTrigger, staticOrDynamicPartTrigger.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein Metamodell handelt, ist das Verhalten deklarativ für die BSW-Generierung festgelegt:

  1. PDU-Assemblierung & Signal-Multiplexing (SignalIPdu / MultiplexedIPdu):
    • AUTOSAR COM serialisiert Signale in die PDU-Payload. Bei MultiplexedIPdu wertet der Stack das Selektorfeld (selectorFieldStartPosition, selectorFieldLength) aus.
    • Sendeauslösung richtet sich nach triggerMode: Bei staticPartTrigger löst nur eine Signaländerung im statischen Teil den PDU-Versand aus, bei dynamicPartTrigger nur der geschaltete dynamische Teil, bei staticOrDynamicPartTrigger beide.
  2. PDU-zu-Frame-Serialisierung (PduToFrameMapping):
    • Das Interface-Modul (z. B. CanIf, FrIf) platziert die PDU an startPosition im Frame unter Berücksichtigung von packingByteOrder.
    • Ist updateIndicationBitPosition definiert, setzt COM/Interface das Update-Bit vor dem Senden, um dem Empfänger die Gültigkeit/Aktualität der PDU anzuzeigen.
  3. Kanal-Dispatching & Ratenbegrenzung (IPduTriggering, IPduTiming):
    • Vor der Übergabe an den Treiber überwacht COM den minimumDelay-Timer. Erst nach Ablauf der Mindestverzögerung wird die PDU für die Transportschicht freigegeben (Schutz vor Bus-Flooding).
  4. Laufzeit-Steuerung (IPduGroup):
    • BSW Mode Manager (BswM) bzw. ComM aktivieren/deaktivieren PDU-Gruppen über Com_IpduGroupStart() bzw. Com_IpduGroupStop() synchron basierend auf communicationDirection.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfigurationsgenerierung (ARXML -> C-Code):
    • PduToFrameMapping steuert direkt die Generierung der PDU-Deskriptortabellen in den Interface-Modulen (CanIf_TxPduConfig, FrIf_FrameConfig). Bei FlexRay ermöglicht dies das Multiplexing mehrerer PDUs in einen einzelnen statischen oder dynamischen Slot.
    • Das Vorhandensein von updateIndicationBitPosition generiert bitweise Maskierungsoperationen im COM-Empfangspfad (Com_RxIndication); Signale ohne gesetztes Update-Bit werden verworfen.
  • Netzwerkmanagement (NmPdu):
    • nmCbvPosition und nmNidPosition sind zwingend für die statische PDU-Struktur von Generic NM / CAN NM. Falsche Offsets führen zu korrumpierten CBV-Flags (z. B. Active Wakeup Bit) und Fehlern in der Ring-/Teilnetzüberwachung.
  • Diagnose & Routing (DcmIPdu, NPdu):
    • DcmIPdu und NPdu umgehen den Signal-Packing-Layer von COM und werden im PDU-Router (PduR) direkt an DCM bzw. Transport-Stacks (CanTp, FrTp) übergeben.
  • Endianness-Fallstrick:
    • packingByteOrder (Mapping in Frame) und selectorFieldByteOrder (Multiplexing-Selektor) können theoretisch unabhängig spezifiziert sein. Entwickler von Generatoren und Treibern müssen sicherstellen, dass die Bit-Nummerierungsschemata (Sawtooth vs. Linear) im Tooling konsistent auf die Zielarchitektur abgebildet werden.
