Figure 4: Overview about the System Template The ECU Resource Template deals with the description of the hardware resources of an ECU. The collection of all ECUs, which are integrated in the car, are described in the topology part of the System Configuration Description/System Constraint Description. Each of these ECUInstances uses the ECU Resource Template to describe the hardware resources. That’s the reason, why the topology part has a reference to the ECU Resource Description. Furthermore, also the communication links between the ECUInstances are described in the topology part. The data frames that will be transferred via these communication links are described in the communication part. Also the gateway tables, which define the copying of frames or signals from one bus to another bus, are covered in this part. The SW component description describes the SW components as well as their communication by logical signals. The top-level software composition is part of the System Template (Software). This top-level software composition contains the functionality of the full system and describes the complete application software architecture of this system.

1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm / Metamodell-Übersichtsdiagramm zur Strukturierung des AUTOSAR System Templates. Das Diagramm gliedert die Systembeschreibung auf oberster Ebene ausgehend vom zentralen Wurzelelement System in vier Hauptdomänen des System Templates (Software, Mapping, Topology, Communication) sowie zwei externe Referenzdomänen (SW Component WP 2.1.1.1 und ECU Resource WP 2.1.1.2). Es beschreibt die kompositionellen Abhängigkeiten, Typ-Instanz-Beziehungen und Vererbungsstrukturen zwischen Software-Architektur, Hardware-Topologie, Kommunikationsmatrix und den verbindenden Abbildungsvorschriften (Mappings und Constraints).

2. Komponenten, Entitäten & Schnittstellen

Das Wurzelelement System aggregiert per Komposition vier Hauptblöcke:

  • Software: Enthält SoftwareComposition, welches auf CompositionType im externen Paket SW Component WP 2.1.1.1 referenziert.
  • Mapping: Enthält SystemMapping. Dieses aggregiert:
    • SwCompToEcuMapping: Zuordnung von Software-Komponenten zu Steuergeräte-Instanzen.
    • DataMapping: Basisklasse für Datenabbildungen mit Spezialisierungen SenderReceiverToUnspecifiedConnectionMapping, SenderReceiverToSignalMapping, SenderReceiverToSignalGroupMapping, ClientServerToSignalGroupMapping, ClientServerPrimitiveTypeMapping sowie CompositeTypeMapping (aggregiert wiederum Kindelemente).
    • MappingConstraint: Basisklasse für Zuordnungsbeschränkungen mit Spezialisierungen ComponentSeparation, ComponentCluster, FreeTextMappingConstraint und SignalPathConstraint. Letzteres spezialisiert sich weiter in CommonSignalPath, ForbiddenSignalPath, PermissibleSignalPath und SeparateSignalPath.
  • Topology: Enthält SystemTopologyInstance, welches auf SystemTopologyType verweist. SystemTopologyType aggregiert:
    • TopologyElement: Abstrakte Basisklasse, spezialisiert durch Hub, Connector und ECUInstance. ECUInstance aggregiert ECUCommunicationPortInstance (referenziert von Connector) und verweist extern auf ECU (aggregiert ECUCommunicationPort) im Paket ECU Resource WP 2.1.1.2.
    • CommunicationCluster: Aggregiert PhysicalChannel, welches wiederum PhysicalMediumSegment sowie Referenzen auf ECUCommunicationPortInstance aggregiert bzw. verbindet.
  • Communication: Enthält SystemCommunication. Dieses aggregiert:
    • CommunicationMatrixInstance: Verweist auf CommunicationMatrixType, welches LinSchedulingTable und Frame aggregiert. Frame aggregiert Timing und PDUPrototype. Letzteres referenziert PDUType, welches wiederum SystemSignal aggregiert.
    • GatewayInstance: Verweist auf GatewayType, welches GatewayEntry aggregiert.
    • CommProtocolInstance: Verweist auf CommProtocolType.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Metamodell-Klassendiagramm bildet die Darstellung keine Laufzeitsequenzen oder Signalflüsse ab. Das funktionale Zusammenspiel erfolgt deklarativ über Mappings und Konfigurationsschritte:

  1. Definition der logischen Software-Architektur ausgehend von CompositionType über SoftwareComposition.
  2. Definition der physikalischen Topologie über Steuergeräte (ECUInstance), Bussysteme (CommunicationCluster, PhysicalChannel) und Ports (ECUCommunicationPortInstance).
  3. Definition der Netzwerk-Kommunikation über Frames, PDUs (PDUPrototype zu PDUType), Signale (SystemSignal), Protokolle und Gateways (GatewayEntry).
  4. Verknüpfung der Ebenen über SystemMapping: Allokation von SW-Komponenten auf ECUs (SwCompToEcuMapping) und logischer Schnittstellendaten auf Bussignale (DataMapping) unter Einhaltung topologischer und sicherheitsbezogener Randbedingungen (MappingConstraint, z. B. SignalPathConstraint, ComponentSeparation).

4. Normative Relevanz & Entwickler-Hinweise

Das Diagramm definiert die normative Architekturgliederung und Paketstruktur für AUTOSAR-Systembeschreibungen (System Description bzw. System Extract). Werkzeugketten und Generatoren müssen die strikte Trennung von logischer Funktionsarchitektur (Software), Topologie (Topology), Netzwerkmatrix (Communication) und deren Verknüpfung (SystemMapping) einhalten. Besondere Implementierungsaspekte:

  • Konsequente Trennung nach dem Type-Instance-Muster (SystemTopologyType/Instance, CommunicationMatrixType/Instance, GatewayType/Instance, CommProtocolType/Instance).
  • Vollständige Validierung von Entflechtungs- und Routing-Regeln über die Subklassen von MappingConstraint (insb. ForbiddenSignalPath, PermissibleSignalPath, ComponentSeparation).
  • Trennung von hardwarenaher ECU-Ressourcenbeschreibung (ECU Resource WP 2.1.1.2) und systemweiter Topologieinstanziierung (Topology).
  • Signalbasierte Datenabbildung (DataMapping) unterscheidet strikt zwischen Sender/Receiver- und Client/Server-Mustern sowie primitiven und zusammengesetzten Datentypen (CompositeTypeMapping).
