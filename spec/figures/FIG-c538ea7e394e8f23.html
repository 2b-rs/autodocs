1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Ausschnitt / UML-Klassendiagramm aus dem Diagnostic Extract Template (DEXT, AUTOSAR_TPS_DiagnosticExtractTemplate, R4.3.1).
  • Architektur-Kontext & Zweck:
    • Formales Metamodell zur Konfiguration und Beschreibung von OBD- bzw. UDS-Fahrzeuginformationen (Vehicle Information, Service $09 gemäß ISO 14229-1 / SAE J1979 / ISO 15031-5).
    • Dient als standardisierter Austauschmechanismus (ARXML) zwischen OEM, Diagnose-Authoring-Systemen und Tier-1-Zulieferern zur automatisierten Codegenerierung des AUTOSAR Diagnostic Communication Managers (Dcm / Submodul Dsp) und zur Parametrierung des PDU-Serialisierers/Deserialisierers für InfoType-Anfragen und -Antworten.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Attribute
  • DiagnosticInfoType (spezialisiert von DiagnosticCommonElement):
    • Repräsentiert einen konkreten InfoType-Service.
    • Attribut:
      • + id : PositiveInteger [0..1]: Die numerische Kennung des InfoTypes.
  • DiagnosticAbstractParameter (abstrakte Klasse):
    • Basisklasse für Diagnoseparameter zur Definition der Felder innerhalb der PDU.
    • Attribute:
      • + parameterSize : PositiveInteger [0..1]: Größe des Parameters.
      • «atpIdentityContributor» + bitOffset : PositiveInteger [0..1]: Startposition des Datenfelds innerhalb des PDU-Datenpuffers in Bits als Identitätsbestandteil.
  • DiagnosticParameter (spezialisiert von DiagnosticAbstractParameter):
    • Konkrete Ausprägung eines Parameters im InfoType-Kontext; erbt parameterSize und bitOffset.
  • DiagnosticDataElement (spezialisiert von Identifiable und DiagnosticServiceMappingDiagTarget):
    • Typisierter Datenbehälter für die Diagnoseausgabe.
    • Attribute:
      • + arraySizeSemantics : ArraySizeSemanticsEnum [0..1]: Semantik variabler oder fixer Feldgrößen (FIXED_SIZE, VARIABLE_SIZE).
      • + maxNumberOfElements : PositiveInteger [0..1]: Maximale Anzahl von Elementen bei Array-Strukturen.
      • + scalingInfoSize : PositiveInteger [0..1]: Größe der Skalierungsinformation in Bits oder Bytes.
  • SwDataDefProps (Stereotyp «atpVariation»):
    • Spezifikation der Software-Dateneigenschaften ohne im Diagramm dargestellte Attribute.
Beziehungen & Stereotypen
  • DiagnosticParameter ⟶ DiagnosticAbstractParameter:
    • Generalisierung / Vererbung.
  • DiagnosticInfoType ◆⟶ DiagnosticParameter:
    • Komposition mit Rollenname +dataElement, Multiplizität 0..*.
    • Stereotyp «atpSplitable»: Verteilung über ARXML-Fragmente.
  • DiagnosticAbstractParameter ◆⟶ DiagnosticDataElement:
    • Komposition mit Rollenname +dataElement, Multiplizität 0..1.
    • Stereotyp «atpVariation, atpSplitable»:
      • «atpVariation»: Kopplung an Varianten mit Bindungszeitpunkt vh.latestBindingTime = postBuild.
      • «atpSplitable»: ARXML-Fragmentierungsunterstützung.
  • DiagnosticDataElement ◆⟶ SwDataDefProps:
    • Komposition mit Rollenname +swDataDefProps, Multiplizität 0..1.
    • Stereotyp «atpSplitable»: Fragmentierungsunterstützung bei der Verknüpfung von Datendefinitionseigenschaften.

3. Dynamisches Verhalten & Sequenzablauf

(Als Metamodell-Strukturdiagramm bildet die Abbildung statische Konfigurationsstrukturen ab; dynamische Laufzeitsequenz im BSW-Stack):

Tester                     Dcm (Dsl / Dsd)                 Dcm (Dsp)                Application / Dem / NvM
  |                               |                            |                               |
  |--- Request Service $09 ------>|                            |                               |
  |    (InfoType id, e.g. 0x02)   |--- Dispatch $09 ---------->|                               |
  |                               |                            |--- Read InfoType Data ------->|
  |                               |                            |    (R-Port / Dcm_Get<Info>)   |
  |                               |                            |<-- Return Data Buffer --------|
  |                               |                            |                               |
  |                               |                            |-- Serialisiere Parameter gem. |
  |                               |                            |   DiagnosticParameter-Layout  |
  |                               |                            |   (bitOffset, arraySize)      |
  |                               |<-- Response PDU -----------|                               |
  |<-- Positive Response ($49) ---|                            |                               |
  1. Trigger: Tester sendet UDS/OBD-Request Service $09 mit Ziel-InfoType id.
  2. Dispatch & Routing: Dcm_Dsd verifiziert die id gegen konfigurierte DiagnosticInfoType-Instanzen.
  3. Puffer-Assemblierung: Dcm_Dsp ruft die angebundenen SW-C-Ports oder BSW-Module (z. B. Dem, NvM) auf. Die Rückgabewerte werden gemäß den DiagnosticParameter.bitOffset-Offsets und den arraySizeSemantics in den PDU-Sendepuffer gemappt.
  4. Fehlerpfade:
    • Unbekannter/nicht unterstützter id → NRC $12 (SubFunctionNotSupported) bzw. $31 (RequestOutOfRange).
    • Datenelement inkonsistent/nicht verfügbar → NRC $22 (ConditionsNotCorrect) oder NRC $78 (ResponsePending bei asynchronem Auslesen).

4. Normative Relevanz & Entwickler-Hinweise

  • Codegenerierung & BSW-Konfiguration (Dcm):
    • Die Entitäten übersetzen direkt in die BSW-Konfigurationsparameter des DCM (DcmDspVehicleInfo, DcmDspVehicleInfoData).
    • bitOffset erzwingt die Byte-/Bit-Serialisierungsreihenfolge in der generierten Dcm_Lcfg.c / Dcm_PBcfg.c. Entwickler müssen darauf achten, dass unvollständige Byte-Paddings und Endianness-Regeln (Big Endian standardmäßig bei UDS) konsistent mit den RTE-Port-Datentypen übereinstimmen.
  • Applikations-Interface (RTE & SW-C):
    • Für jedes DiagnosticDataElement generiert der DEXT-Importer typisierte Port-Interfaces (z. B. Client-Server-Interfaces DataServices_DiagnosticInfoType_<id>_<name> mit Operation ReadData).
    • Über SwDataDefProps (z. B. displayFormat, stepSize, swImplPolicy) wird festgelegt, ob Festkomma-Skalierungen zur Laufzeit durch die Applikation oder durch externe Diagnosetester berechnet werden.
  • Variantenhandling («atpVariation»):
    • Parameter und deren Datenelemente können an System-Konstanten (SwSystemconst) gebunden sein. Dies führt je nach Binding-Time (Pre-Compile vs. Post-Build-Selectable) dazu, dass InfoType-Payloads entweder via #ifdef im generierten C-Code exkludiert oder dynamisch über Konfigurationstabellen mit variabler PDU-Länge abgearbeitet werden.
  • Speicher- und Alignment-Restriktionen:
    • swAlignment und swValueBlockSize müssen mit den CPU- und Bus-Puffer-Alignments (z. B. 32-Bit Alignment im CAN-FD/FlexRay/Ethernet-Diagnosepuffer) harmonieren, um unaligned memory access Traps auf MCUs ohne Hardware-Support zu vermeiden.
