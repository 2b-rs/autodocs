1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm des AUTOSAR-Metamodells (M2-Ebene) aus AUTOSAR_TPS_ECUConfiguration.
  • Architektur-Kontext & Zweck:
    • Definiert die formale Struktur für Parameter-Container innerhalb der BSW-Modul-Beschreibung (BSW Module Parameter Definition, BSWMD).
    • Bildet das Metaschema ab, über welches BSW-Module (z. B. CAN, Lin, Com, Os, PduR) ihre Konfigurationsparameter hierarchisch kapseln, typisieren und variantenabhängig beschränken.
    • Dient ECU-Konfigurationstools (z. B. DaVinci Configurator, EB tresos) als normative Validierungsgrundlage für Instanziierung, Multiplizitätsprüfung und Codegenerierung (Generierung von .c/.h-Artefakten).

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Hierarchie
  • EcucDefinitionElement (abstrakt, spezialisiert AtpDefinition, Identifiable):
    • Basisklasse aller Definitionselemente im Konfigurationsmodell.
    • Attribute:
      • scope: EcucScopeEnum [0..1]: Gültigkeitsbereich der Definition.
      • «atpVariation» lowerMultiplicity: PositiveInteger [0..1]: Minimale Instanzanzahl (varianzfähig).
      • «atpVariation» upperMultiplicity: PositiveInteger [0..1]: Maximale Instanzanzahl (varianzfähig).
      • «atpVariation» upperMultiplicityInfinite: Boolean [0..1]: Flag für unbeschränkte Multiplizität (*).
    • Assoziationen:
      • +relatedTraceItem (0..1, Stereotyp «atpUriDef») → MultilanguageReferrable / Traceable: Anbindung an Requirements-Tracing (SWS-Traceability). Traceable besitzt eine reflexive Relation +trace 0..*.
  • EcucContainerDef (abstrakt, generalisiert von EcucDefinitionElement):
    • Abstrakte Basisklasse für Konfigurations-Container.
    • Attribute:
      • origin: String [0..1]: Gibt den Ursprung bzw. die Quelle der Definition an.
      • postBuildVariantMultiplicity: Boolean [0..1]: Definiert, ob die Instanzanzahl über Post-Build-Varianten hinweg variieren darf.
      • requiresIndex: Boolean [0..1]: Erzwingt eine fortlaufende Indexierung instanziierter Container.
    • Komposition:
      • +multiplicityConfigClass (0..*) → EcucMultiplicityConfigurationClass: Verknüpft Multiplizitäten mit Bindungszeit- und Konfigurationsklassen.
  • EcucParamConfContainerDef (konkret, erbt von EcucContainerDef):
    • Standard-Container zur Aufnahme von Parametern, Referenzen und Sub-Containern.
    • Kompositionen:
      • +parameter (0..*, Stereotyp «atpSplitable») → EcucParameterDef: Konkrete skalare/aggregierte Konfigurationsparameter (implementiert EcucCommonAttributes).
      • +reference (0..*, Stereotyp «atpSplitable») → EcucAbstractReferenceDef: Konfigurationsreferenzen auf andere Container/Definitionen (implementiert EcucCommonAttributes).
      • +subContainer (0..*, Stereotyp «atpSplitable») → EcucContainerDef: Rekursive Einbettung beliebiger Container (EcucParamConfContainerDef oder EcucChoiceContainerDef).
  • EcucChoiceContainerDef (konkret, erbt von EcucContainerDef):
    • Container zur Modellierung exklusiver Alternativen (Choice).
    • Komposition:
      • +choice (0..*, Stereotyp «atpSplitable») → EcucParamConfContainerDef: Menge der zur Auswahl stehenden alternativen Parameter-Container.
  • EcucParameterDef (implementiert EcucCommonAttributes):
    • Beschreibt konkrete Konfigurationsparameter.
    • Attribute:
      • symbolicNameValue: Boolean [0..1]: Bestimmt, ob der Containerwert als C-Bezeichner (#define) für symbolische Namen exportiert wird.
      • withAuto: Boolean [0..1]: Gibt an, ob der Wert vom Konfigurationswerkzeug automatisch bestimmt werden kann.
  • EcucAbstractReferenceDef (implementiert EcucCommonAttributes):
    • Abstrakte Basisklasse für Referenzdefinitionen auf andere Konfigurationselemente.
    • Attribute:
      • withAuto: Boolean [0..1]: Gibt an, ob die Referenz vom Konfigurationswerkzeug automatisch aufgelöst bzw. bestimmt werden kann.
  • EcucMultiplicityConfigurationClass (spezialisiert EcucAbstractConfigurationClass):
    • Bindet Multiplizitäten an Bindungszeitpunkte und Konfigurationsvarianten.
  • EcucAbstractConfigurationClass (abstrakt):
    • Attribute:
      • configClass: EcucConfigurationClassEnum [0..1]: Bindungszeitpunkt bzw. Konfigurationsklasse.
      • configVariant: EcucConfigurationVariantEnum [0..1]: Konfigurationsvariante.
Aufzählungstypen (Enumerations)
  • «enumeration» EcucConfigurationClassEnum:
    • Literale: PublishedInformation, PreCompile, Link, PostBuild.
  • «enumeration» EcucConfigurationVariantEnum:
    • Literale: PreconfiguredConfiguration, RecommendedConfiguration, VariantPreCompile, VariantLinkTime, VariantPostBuild.

3. Dynamisches Verhalten & Sequenzablauf

  • Klassifikation: Reines Entwurfs- und Konfigurations-Metamodell (M2/M1-Ebene). Keine Laufzeitdynamik (keine Task-Zyklen, kein OS-Scheduling, keine Det/Dem-Laufzeitaufrufe auf dem Mikrocontroller).
  • Tooling- & Transformationsablauf (Design-Time / Build-Prozess):
    1. Schema-Parsing: Der BSW-Generator liest die BSWMD (EcucDefinitionElement).
    2. Konfigurationsauflösung: Das Konfigurationstool prüft die Instanzen (EcucContainerValue):
      • Validierung von lowerMultiplicity und upperMultiplicity je gewählter Variante (configVariant).
      • Auflösung von EcucChoiceContainerDef: Genau eine Alternative aus +choice wird für die Konfiguration aktiviert.
    3. Multi-File-Merge («atpSplitable»): Zusammenführen fragmentierter XML-Knoten aus OEM- und Tier-1-Lieferungen.
    4. Code-Synthese:
      • PreCompile: Containerstrukturen werden als C-Makros (#define) oder feste const-Strukturen im ROM/Flash erzeugt.
      • Link: Definition von externen Deskriptoren, die beim Linken gebunden werden.
      • PostBuild: Erzeugung von ladbaren/flashbaren Konfigurations-Arrays und Deskriptortabellen im RAM/Flash.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Treiber- & Modulentwicklung:
    • Array-Dimensionierung: postBuildVariantMultiplicity = false erlaubt statische Array-Größen im Treiber-Header (#define CAN_NUM_CONTROLLERS 2u). Ist das Flag true, muss der Treiber dynamische Iteration über Pointer-Tabellen oder Worst-Case-Größen unterstützen.
    • Indizierung: requiresIndex = true erzwingt in der Konfiguration lückenlose Index-Werte (0..N-1), relevant für direkte Array-Zugriffe im Treiber (Can_Config.Controllers[Index]).
  • Symbolische Namen:
    • symbolicNameValue = true generiert C-Literale der Form <Modul>Conf_<ContainerDef>_<ContainerInstance> (z. B. CanConf_CanController_CanController_0). Dient auf Anwenderebene als ID für Treiber-APIs (z. B. Can_SetControllerMode(CanConf_CanController_CanController_0, ...)).
  • Choice-Container:
    • Verhindert redundanten ROM-Footprint. Treiberentwickler implementieren bedingte Kompilierung (#if defined(...)), da inaktive Choices weder Datenstrukturen noch RAM im Zielsystem belegen dürfen.
