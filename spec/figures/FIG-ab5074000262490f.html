1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: PDU-Wire-Format / Bit-Layout-Diagramm (32-Bit-Word-Alignment, Big-Endian / Network Byte Order).
  • Funktionale Einordnung: Definiert die Serialisierungsstruktur des Service Discovery Protokolls (SOME/IP-SD) gemäß [PRS_SOMEIPSD_00252]. Die Kapselung erfolgt direkt in einer Standard-SOME/IP-Nachricht auf Schicht 5–7, transportiert über UDP (typischerweise Multicast 224.0.0.17 bzw. Unicast auf Port 30490).
  • Zweck im Gesamtsystem:
  • Classic AUTOSAR: BSW-Modul Sd (Service Discovery) zwischen BswM/RTE und SoAd/TcpIp.
  • Adaptive AUTOSAR: Platform Foundation / ara::com-Daemon zur dynamischen Dienstsuche (FindService), Dienstbekanntgabe (OfferService) und Endpunkt-Konfiguration.

2. Komponenten, Entitäten & Schnittstellen

Das Schaubild gliedert sich in den standardisierten SOME/IP-Header (16 Byte) und die dynamische SOME/IP-SD-Nutzlast (52 Byte; Gesamt-PDU = 68 Byte):

#### A. SOME/IP Header (Bytes 0..15)

  • Message ID (0xFFFF 8100):
  • Service ID (0xFFFF): Reservierter Identifikator für SOME/IP-SD.
  • Method/Event ID (0x8100): Kennzeichnet SD-Nachrichten (Bit 15 = 1 indiziert Event/Notification).
  • Length (32 Bit = 64 / 0x00000040): Länge der verbleibenden PDU ab Byte 8 (8 Byte Rest-Header + 56 Byte SD-Payload).
  • Request ID (32 Bit): Client ID (16 Bit) + Session ID (16 Bit) zur Erkennung von Duplikaten und Reordering.
  • Protocol Version (0x01): SOME/IP-Protokollversion 1.
  • Interface Version (0x01): SD-Interface-Hauptversion.
  • Message Type (0x02): NOTIFICATION (unbestätigte Broadcast-/Multicast-Übertragung).
  • Return Code (0x00): E_OK (kein Fehler).

#### B. SOME/IP-SD Header (Bytes 16..19)

  • Flags (8 Bit = 0x80):
  • Bit 7 (Reboot Flag = 1): Signalisiert Neustart der Node (Session-IDs wurden zurückgesetzt).
  • Bit 6 (Unicast Flag = 0): Antwortverhalten / Multicast-Modus.
  • Bits 5..0: Reserviert (0x00).
  • Reserved (24 Bit = 0x000000): Auffüllbytes zur Einhaltung des 32-Bit-Alignments.

#### C. Entries Array (Bytes 20..55)

  • Length of Entries Array (32 Bit = 32 / 0x00000020): Definiert exakt 2 Entries à 16 Byte.
  • Entry 1 (FindService, Type 0x00):
  • Type: 0x00 (FindService).
  • Index 1st/2nd options: 0 / 0; # of opt 1/2: 0 / 0 (referenziert keine Optionen).
  • Service ID: 0x4711.
  • Instance ID: 0xFFFF (Wildcard: Sucht alle Instanzen von 0x4711).
  • Major Version: 0xFF (Wildcard: Beliebige Major Version akzeptiert).
  • TTL: 3600 (Gültigkeit des Suchauftrags: 3600 Sekunden / 1 Stunde).
  • Minor Version: 0xFFFFFFFF (Wildcard: Beliebige Minor Version).
  • Entry 2 (OfferService, Type 0x01):
  • Type: 0x01 (OfferService).
  • Index 1st options: 0 (verweist auf Offset-Index 0 im Options Array).
  • # of opt 1: 1 (bindet exakt eine Option aus dem 1st-Set ein).
  • Index/Count 2nd options: 0 / 0 (kein 2nd-Set genutzt).
  • Service ID: 0x1234.
  • Instance ID: 0x0001 (Konkrete Instanz 1).
  • Major Version: 0x01.
  • TTL: 3 (Gültigkeitsdauer des Angebots: 3 Sekunden bis zum zyklischen Refresh).
  • Minor Version: 0x00000032 (Dezimal 50).

#### D. Options Array (Bytes 56..71)

  • Length of Options Array (32 Bit = 12 / 0x0000000C): Definiert exakt eine 12-Byte-Option.
  • Option 0 (IPv4 Endpoint Option, Type 0x04):
  • Length (16 Bit = 0x0009): 9 Byte verbleibend nach dem Length-Feld.
  • Type (8 Bit = 0x04): IPv4 Endpoint Option.
  • DF (1 Bit = 1): Discardable Flag gesetzt (Option darf ignoriert werden, falls Empfänger sie nicht unterstützt).
  • IPv4-Address (32 Bit = 192.168.0.1 / 0xC0A80001).
  • L4-Proto (8 Bit = 0x11): Transportprotokoll UDP (17 dezimal).
  • Port Number (16 Bit = 0xD903 / 55555 dezimal).

3. Dynamisches Verhalten & Sequenzablauf

  • Multi-Entry-Aggregation: Das SD-Protokoll bündelt heterogene Aktionen in einem Transportrahmen: Eine Node sucht parallel nach Service 0x4711 und publiziert das Vorhandensein von Service 0x1234.
  • Indirekte Optionsreferenzierung: Entries enthalten keine IP-/Port-Informationen direkt, sondern nutzen Zeiger (Index 1st options = 0) auf das globale Options-Array. Dies minimiert Redundanzen, wenn mehrere Entries denselben Endpunkt teilen.
  • Reboot- und Session-Handling:
  • Da Reboot Flag = 1, müssen Empfänger alle zuvor gecachten Instanzzustände der Quell-Node invalidieren.
  • Die Session ID im Request ID-Feld muss pro gesendeter SD-Nachricht inkrementiert werden (Bereich 0x0001 bis 0xFFFF, 0x0000 ist unzulässig).
  • Timer & Refresh-Zyklen:
  • Der Server für Service 0x1234 muss spätestens alle < 3 Sekunden ein neues OfferService senden. Bleibt dieses aus, schlägt beim Client der SD-Timeout zu.
  • Ein expliziter Abbruch des Angebots erfolgt durch Senden desselben Entries mit TTL = 0 (StopOfferService).

4. Normative Relevanz & Entwickler-Hinweise

  • PDU-Längen-Validierung:
  • Implementierende BSW/Daemon-Parser müssen vor dem Zugriff prüfen: $\text{Length}_{\text{SOME/IP}} == 8 + 4 + 4 + \text{Length}_{\text{Entries}} + 4 + \text{Length}_{\text{Options}}$.
  • Diskrepanzen deuten auf PDU-Korruption hin und müssen zum Verwerfen der PDU führen (DET-Meldung: SD_E_INV_PDU).
  • Out-of-Bounds (OOB) Schutz bei Options-Indizes:
  • Validierung: $(\text{Index 1st options} + \#\text{ of opt 1}) \times \text{Size}_{\text{Option}} \le \text{Length of Options Array}$. Fehlerhafte Indizes dürfen keinen Speicherzugriffsfehler auslösen.
  • Discardable Flag (DF):
  • DF == 1: Erkennt ein Stack-Parser den Option Type nicht, darf die Option stillschweigend verworfen werden, der zugehörige Service-Entry bleibt gültig.
  • DF == 0: Ein unbekannter Optionstyp erzwingt das Verwerfen des gesamten referenzierenden Entrys.
  • MTU- und Fragmentierungs-Restriktionen:
  • SD-PDUs dürfen das MTU-Limit des Layer-2-Netzwerks (typischerweise 1500 Byte bei Automotive Ethernet) niemals überschreiten, da UDP-Fragmentierung im Automotive-Umfeld herstellerseitig verboten ist. Das Sd-Modul muss bei vielen Diensten die Entries auf mehrere separate SD-PDUs verteilen.
