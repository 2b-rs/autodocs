1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Methodisches Dekompositions- und Allokationsdiagramm für Timing-Budgets (Hierarchical Top-Down Latency Budgeting Model) im Kontext der AUTOSAR Timing Extensions (TIMEX / AUTOSAR_TPS_TimingExtensions).
  • Technischer Zweck: Visualisierung des iterativen Top-Down-Dekompositionsprozesses von System-End-to-End-Latenzanforderungen (Response Times / Functional Event Chains) über die Netzwerkinfrastruktur und Steuergerätegrenzen hinweg bis auf Ebene einzelner Software-Komponenten (SW-Cs) und deren RunnableEntity-Instanzen.
  • Funktionale Einordnung: Dient in frühen Entwurfsphasen (System Design & V&V) der Machbarkeitsanalyse (Feasibility Assessment, Bus- und CPU-Auslastung) und bildet die normative Brücke zwischen OEM-Gesamtfahrzeuganforderungen, V-Modell-Systemallokation und der feingranularen RTE-/OS-Konfiguration der Tier-1-Zulieferer.

2. Komponenten, Entitäten & Schnittstellen

  • Dargestellte Ebenen & Entitäten:
    • System Level (End-to-End Path): Repräsentiert die globale funktionale Ereigniskette (TimingDescriptionEventChain) vom initialen Stimulus (Sensor/System-Event, Symbol Blitz) bis zur Zielreaktion (Aktorik/Event, Symbol Zielflagge).
    • Communication Path (communication 1, communication 2): Deterministische Busübertragungsstrecken (CAN, CAN FD, FlexRay, Automotive Ethernet/TSN) basierend auf Netzwerkmatrix/FIBEX/ARXML-Systembeschreibung.
    • Component Level / Node Level: Steuergeräte- und SW-C-Grenzen (SW-C mit function 1 bis function 5). Hierarchische Zerlegung des Komponentenbudgets in Einzelfunktionen (function 3, function 4).
    • Runnable Entity Level: Detaillierte Realisierung innerhalb einer SW-C (hier function 4 zerlegt in Sub-Runnables function 4a, function 4b, function 4c1, function 4c2, funktion 4d).
  • Metriken & Zeitbudgets:
    • End-to-End Timing Budget: Maximal zulässige Latenz (LatencyTimingConstraint), abgeleitet aus funktionalen Sicherheits- oder Performance-Zielen (ASIL/Quality of Service).
    • Communication Time Demand: Vorgegebene Buslaufzeit (Frame-Transmission, Arbitration, Gatewaying, Physical Layer).
    • Remaining Component Budget: Verbleibendes Berechnungszeitbudget für die allokierten SW-Cs auf den jeweiligen ECUs.
    • Execution Time (Usage of timing budgets): Tatsächliche Ausführungszeit der Runnables (Core Execution Time / WCET).
    • Overhead: Latenzen durch OS-Task-Aktivierung, Scheduling/Preemption, Kontextwechsel, Inter-Runnable- bzw. Inter-Task-Kommunikation und RTE-Wrapper-Laufzeiten.
    • % free: Sicherheitsmarge (Design Slack) zur Kompensation von Jitter und künftigen Funktionserweiterungen.
  • Hierarchische Beziehungen:
    • EventChain besteht aus einer Komposition von Sub-Event-Chains: $\text{EventChain}_{\text{Total}} = \sum \text{SubChain}_{\text{SW-C}} + \sum \text{SubChain}_{\text{Bus}}$.
    • N-zu-1- und 1-zu-N-Mappierbarkeit: Funktionen mappen auf AtomicSwComponentType, deren internes Verhalten über SwcInternalBehavior definiert und in sequenzielle/parallele RunnableEntity-Elemente aufgeteilt wird.

3. Dynamisches Verhalten & Sequenzablauf

  1. Stimulus-Erzeugung: Ein externes physikalisches oder systemisches Ereignis triggert die erste Kette in ECU 1 (function 1 → function 2).
  2. Netzwerk-Übertragung 1 (communication 1): Datenbereitstellung über AUTOSAR COM, PDU-Router (PduR), Interface-Treiber (CanIf/EthIf) auf den Bus; Empfang und Dekapsulierung auf ECU 2.
  3. Komponenteninterne Verarbeitung (ECU 2):
    • Ausführung von function 3, Übergabe an function 4.
    • Gabelung/Parallelpfad in function 4: function 4a stößt nach Ausführung zwei parallele bzw. alternative Ausführungspfade an:
      • Pfad A: Asynchrone/Ereignisgesteuerte Ausführung (Rte_Event, Blitz) von function 4c1 gefolgt von function 4c2.
      • Pfad B: Parallele Abarbeitung von function 4b.
    • Synchronisation/Join: Beide Pfade münden über ein Event (Blitz) in die finale Stufe funktion 4d.
  4. Netzwerk-Übertragung 2 (communication 2): Senden der resultierenden Signale an ECU 3.
  5. Reaktion: Abarbeitung in function 5 bis zum finalen Wirksamwerden an der Aktorik (Terminierung der EventChain).
  6. Latenzkomposition: Die Gesamtverzugszeit ist die Summe aller Worst-Case Execution Times (WCET), der OS-/RTE-Overheads (Blocking Time, Preemption Time, Task Switching) und der Worst-Case Response Times (WCRT) auf den Bussystemen.

4. Normative Relevanz & Entwickler-Hinweise

  • TIMEX-Modellierung (AUTOSAR ARXML):
    • Definition von TimingDescriptionEventChain mit eindeutigen EventChainSubChain-Verknüpfungen für System-, Bus- und Runnable-Ebene.
    • Festlegung von LatencyTimingConstraint (Nominal, Minimum, Maximum) auf System- und Komponenten-Ebene zur formalen Verifikation gegen gemessene Traces.
  • RTE- und OS-Konfiguration:
    • Task-Mapping: Runnables mit strikten Budgetgrenzen und minimalem Overhead müssen in gemeinsame Tasks konsolidiert werden, um Kontextwechsel- und Inter-Task-Overhead (oranger Overhead-Pfeil) zu eliminieren.
    • Aktivierungsart: Die Blitz-Symbole auf Runnable-Ebene fordern konkrete RTEEvent-Typen (TimingEvent für periodische, DataReceivedEvent oder OperationInvokedEvent für aperiodische Runnables).
    • Pufferung & Konsistenz: Vermeidung von Blockierzeiten bei Inter-Runnable-Kommunikation (InterRunnableVariable) durch adäquate Locking-Mechanismen oder lock-freie Warteschlangen.
  • Stack- & Bus-Parametrierung (BSW):
    • Busbudgets (grün) bedingen feste Frame-Zykluszeiten und Prioritäten im CAN/FlexRay/Ethernet-Stack (ComTxMode, PDU-Perioden, TSN-Shaping/VLAN-Priorisierung).
    • PDU-Payloads müssen so gepackt werden, dass Latenzketten nicht über multiple Übertragungszyklen zerfallen (Signal-to-PDU-Mapping).
  • Verifikation & Toolchain:
    • Das Budgetmodell erzwingt statische Schedulability-Analysen (CPA/WCRT-Berechnung) sowie dynamisches Hardware-Tracing (z. B. via OTRC/ETM, BSWM/RTE-Hooks gemäß AUTOSAR_SWS_DiagnosticLogAndTrace oder Timing Measurement Pins).
    • Ein Nichteinhalten des freien Budgets (% free ≤ 0) blockiert die funktionale Freigabe auf Integrationsstufe.
