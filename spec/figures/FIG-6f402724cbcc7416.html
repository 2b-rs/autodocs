1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsautomat (Hierarchisches State-Machine-Diagramm nach OMG UML 2.5) zur Modellierung des Makro-Lebenszyklus des ECU State Managers (EcuM, Spezifikationsvariante Flexible Management).
  • Technischer Zweck: Definition der normativen Betriebsphasen (STARTUP, UP, SLEEP, SHUTDOWN, OFF) eines AUTOSAR-Classic-ECU. Das Diagramm kapselt die Übergänge zwischen uninitialisiertem Hardwarezustand, Bare-Metal-Initialisierung, preemptivem OS/BSW-Scheduler-Betrieb, Low-Power-Modi und kontrolliertem System-Down/Reset.
  • Funktionale Einordnung: Zentrale Instanz der Basic Software (BSW) im System Services Layer (AUTOSAR CP). Der EcuM koordiniert die Boot-Sequenz, übergibt die modale Steuerung im Zustand UP an den Basic Software Mode Manager (BswM) und führt hardwarenahe Sleep-/Shutdown-Sequenzen über den Microcontroller Driver (MCU) und Peripherietreiber durch.

2. Komponenten, Entitäten & Schnittstellen

  • Zustandsentitäten (Composite & Leaf States):
    • STARTUP (Composite State): Kapselt Pre-OS- und Post-OS-Bootphasen. Sub-Zustände: StartPreOs, StartPostOs.
    • UP (Operational State): Stationärer Normalbetrieb. Die BSW- und SWC-Modusverwaltung liegt hier dezentral beim BswM und Rte.
    • SLEEP (Composite State): Kapselt Low-Power-Sequenzen. Sub-Zustände: GoSleep, orthogonale/alternative Wartezustände Poll vs. Halt, sowie WakeUpRestart.
    • SHUTDOWN (Composite State): Kapselt den geregelten Rückbau der BSW. Sub-Zustände: OffPreOs, OffPostOs.
    • OFF (Final State): Zielzustand bei Power-Cut oder extern getriggertem Klemmenabfall (z. B. KL30/KL31 stromlos).
  • Beteiligte System-Akteure & BSW-Module:
    • EcuM (ECU State Manager): Verantwortlich für Zustandsführung, Wakeup-Source-Tracking und Shutdown-Targets (ECUM_SHUTDOWN_TARGET_OFF, _RESET, _SLEEP).
    • OS (AUTOSAR OS): Stellt Task-Scheduling, Ressourcen und Kern-Synchronisation bereit (StartOS(), ShutdownOS()).
    • SchM (Schedule Manager) & BswM (BSW Mode Manager): Orchestrieren BSW-Main-Functions und Mode-Arbitration.
    • MCU Driver: Hardwareabstraktion für CPU-Takte, Power-Modes (Mcu_SetMode()) und Reset-Auslösung (Mcu_PerformReset()).
  • Annotationen / Constraints im Diagramm:
    • Note an UP: „After Sleep the WakeupValidation is started if needed“ (Validierung der Weckquelle über EcuM_ValidateWakeupEvent()).
    • Note an GoSleep: „WakeUpSources will be enabled“ (Aufruf von EcuM_EnableWakeupSources()).
    • Note an WakeUpRestart: „WakeUpSources will be disabled“ (Aufruf von EcuM_DisableWakeupSources()).

3. Dynamisches Verhalten & Sequenzablauf

A. Initialisierungspfad (STARTUP → UP)
  1. Entry STARTUP / StartPreOs: Einstieg via Reset-Vektor in EcuM_Init(). Ausführung von DriverInitZero und DriverInitOne (nicht-preemptiv, IRQs global gesperrt; Init von Basis-Treibern wie Det, Dem, Port, Mcu).
  2. Transition StartPreOs → StartPostOs: Getriggert durch synchronen Aufruf von StartOS(). Das OS übernimmt die CPU-Kontrolle und startet die BSW-Initialisierungs-Task (üblicherweise Autostart-Task).
  3. Execution StartPostOs: Aufruf von EcuM_StartupTwo(). Initialisierung von SchM und BswM.
  4. Transition STARTUP → UP: Wächterbedingung: „BswM, Os and SchM initialized“. Übergabe der Mode-Control-Hoheit an den BswM.
B. Low-Power-Zyklus (UP ↔ SLEEP)
  1. Transition UP → SLEEP: Anforderung durch BswM via EcuM_GoHalt() bzw. EcuM_GoPoll().
  2. Phase GoSleep: BSW-Stacks werden eingefroren/deinitialisiert; EcuM_EnableWakeupSources() schärft konfigurierte Weckquellen (z. B. CanWakeup, LinWakeup).
  3. Verzweigung (Branching):
    • Halt: CPU wechselt in statischen Tiefschlaf (Mcu_SetMode(MCU_MODE_HALT)); CPU-Clock gestoppt; Reaktivierung erfolgt asynchron via Hardware-Interrupt (Wakeup-ISR).
    • Poll: CPU verbleibt in Low-Power-Polling-Schleife (EcuM_SleepActivity()); periodische Abfrage unmaskierter Weckquellen via EcuM_CheckWakeup().
  4. Phase WakeUpRestart: Unmittelbar nach Weckereignis. MCU-Takt wird restauriert (Mcu_DistributePllClock()); EcuM_DisableWakeupSources() deaktiviert Schärfung; periphere Treiber werden minimal reinitialisiert.
  5. Rückkehr nach UP: BswM übernimmt erneut; asynchrone Validierung der Weckquelle (WakeupValidation) wird gestartet, um Spurious Wakeups (Glitches) abzufangen. Schlägt die Validierung fehl, leitet BswM Rückkehr nach SLEEP ein.
C. Shutdown- & Reset-Sequenz (UP → SHUTDOWN → OFF / STARTUP)
  1. Transition UP → SHUTDOWN: Initiiert durch BswM via EcuM_GoDown().
  2. Phase OffPreOs: De-Initialisierung von SchM und BswM; Speichern persistenter NvM-Datenblöcke (NvM_WriteAll()).
  3. Transition OffPreOs → OffPostOs: Aufruf von ShutdownOS(). Deaktivierung des OS-Schedulers; Rückkehr in den Bare-Metal-Kontext (ShutdownHook).
  4. Terminierung:
    • Pfad nach STARTUP: Wächterbedingung: „Reset if Shutdown Target is RESET“. Ausführung von Mcu_PerformReset() führt zum Hardware-Neustart (Warmstart/Software-Reset).
    • Pfad nach OFF: Wächterbedingung: Shutdown-Target ist ECUM_SHUTDOWN_TARGET_OFF. Ansteuerung der Basis-Spannungsversorgung (z. B. Power-Hold-Pin via Dio/Sbc auf LOW) oder Endlosschleife bis zum externen Spannungsabfall.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurations- und API-Vertrag:
    • Treiber-Initialisierung: Treiber, die vor dem OS laufen müssen (StartPreOs), dürfen weder SchM-Locks, OS-Ressourcen, noch Det-Runtime-Checks nutzen. Callback-Hooks (EcuM_AL_DriverInitZero, _One) müssen streng deterministisch sein.
    • BswM-Interaktion: Im Zustand UP existiert kein autonomer Zustandswechsel im EcuM. Jeder Wechsel nach SLEEP oder SHUTDOWN muss explizit durch BswM_RequestMode() angefordert und über konfigurierte BswM-Actions (EcuM_SelectShutdownTarget, EcuM_GoDown) orchestriert werden.
  • Echtzeit- und Latenzanforderungen (Wakeup):
    • Während WakeUpRestart ist die Interrupt-Latenz kritisch: Es dürfen hier nur zeitsensitive Treiber re-initialisiert werden (z. B. Basistakt, Transceiver-Treiber). Umfangreiche Stack-Restaurierungen gehören in nachgelagerte BSW-Tasks im Zustand UP.
  • Reset-Handling:
    • Wird ein Shutdown-Target auf RESET gesetzt, muss über EcuM_SetShutdownTarget(ECUM_SHUTDOWN_TARGET_RESET, resetMode) der spezifische Modus (z. B. MCU_RESET_MCU, MCU_RESET_WDG) mitgeführt werden, um Bootloader-relevante Flags im uninitialisierten RAM (.noinit) sauber auswerten zu können.
