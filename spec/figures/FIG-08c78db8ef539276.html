1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Informelles Block- und Architektur-Strukturdiagramm (Komponenten- und Kapselungsmodell der AUTOSAR Adaptive Platform).
  • Technischer Zweck & Einordnung: Illustration der Speicherabstraktion innerhalb des Functional Clusters Persistency (ara::per) für eine Adaptive Application (AdaptiveApplicationSwComponentType). Es visualisiert die Koexistenz und logische Kapselung der beiden komplementären Persistenzmechanismen – schlüsselbasierter strukturierter Datenzugriff (Key-Value Storage) und dateibasierter Bytestream-Zugriff (File Storage).

2. Komponenten, Entitäten & Schnittstellen

  • Adaptive Application (AdaptiveApplicationSwComponentType): Der ausführende Anwendungsprozess im Userspace des POSIX-Betriebssystems, in dessen Kontext die Persistenzinstanzen instanziiert und betrieben werden.
  • Persistency (ara::per): Das funktionale Persistenz-Cluster, das als anwendungslokale C++-Bibliothek realisiert ist und die Low-Level-Interaktion mit dem darunterliegenden Dateisystem bzw. Flash/NVRAM kapselt.
  • Key-Value Storage (A & B):
  • Repräsentiert diskrete Schlüssel-Wert-Datenbanken (ara::per::KeyValueStorage).
  • Modellierung im AUTOSAR-Manifest über PortPrototype (P-Port / R-Port), typisiert durch ein PersistencyKeyValueDatabaseInterface.
  • Hält typisierte Schlüssel-Wert-Paare (Key_A1 = Value_A1, Key_A2 = Value_A2, Key_B1 = Value_B1, etc.), serialisiert über AUTOSAR-Datentypen.
  • Kardinalität: $1 \dots n$ Key-Value-Datenbanken pro Softwarekomponente (visualisiert durch Storage A und B mit vertikalen Auslassungspunkten ...); jede Datenbank verwaltet $0 \dots m$ Schlüssel-Wert-Paare.
  • File Storage (C & D):
  • Repräsentiert isolierte virtuelle Dateicontainer (ara::per::FileStorage).
  • Modellierung im AUTOSAR-Manifest über PortPrototype, typisiert durch ein PersistencyFileStorageInterface.
  • Verwaltet raw Byte-Streams bzw. diskrete Dateien (File_C1, File_C2, File_D1, File_D2, etc.).
  • Kardinalität: $1 \dots n$ File Storages pro Komponente (visualisiert durch Storage C und D mit vertikalen Auslassungspunkten ...); jeder Speicher kapselt $0 \dots k$ Dateien (ara::per::ReadAccessor, ara::per::ReadWriteAccessor).

3. Dynamisches Verhalten & Sequenzablauf

  • Initialisierung & Pre-Deployment:
  • Vordefinierte Key-Value-Paare und Init-Dateien werden während der Installations- bzw. Updatephase durch das Update and Configuration Management (UCM) auf Basis des Deployments und Manifests auf dem persistenten Speicher bereitgestellt.
  • Laufzeit-Zugriff (CRUD-Operationen):
  • Key-Value Storage: Synchrone/asynchrone API-Calls (GetValue, SetValue, SyncToStorage). Modifikationen im RAM-Cache werden synchron oder verzögert über SyncToStorage() redundant und transaktionssicher (Crash-Konsistenz) auf den persistenten Speicher geflusht.
  • File Storage: Öffnen und Modifizieren via Stream-Operatoren (OpenFileReadStream, OpenFileWriteStream). Sperren/Locks auf File-Ebene verhindern nebenläufige Konflikte innerhalb desselben Prozesses.
  • Fehler- und Abbruchverhalten:
  • Fehler (z. B. I/O-Fehler, Quota-Überschreitung, Korruption) werden über ara::core::Result<T> mit spezifischen PerErrc-Fehlercodes zurückgegeben.
  • Bei Datenkorruption greifen persistenzspezifische Integritätsprüfungen (CRC/Redundanz gemäß Redundancy Handling).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur- und Spezifikationsbezug: Das Diagramm veranschaulicht die funktionale Kapselung persistenter Datenzugriffe auf Anwendungsebene. Es besitzt informativen Charakter und definiert die logische Koexistenz von KeyValueStorage und FileStorage innerhalb eines Prozesses.
  • Port- und Manifest-Modellierung: Entwickler müssen jede Key-Value-Datenbank und jedes File-Storage im Software-Component-Description-Manifest über separate PortPrototype-Elemente mit PersistencyKeyValueDatabaseInterface bzw. PersistencyFileStorageInterface deklarieren.
  • Ressourcenallokation & Isolation: Persistente Speicherbereiche sind pro Instanz streng isoliert; Zugriffe erfordern die Konfiguration entsprechender Speicher- und Quota-Limits im Deployment-Manifest.

Specification of Persistency AUTOSAR AP R20-11 7 Functional Specification 7.1 The Architecture of Persistency The functional cluster Persistency offers two different mechanisms to access persistent memory: Key-Value Storages offer access to a set of keys with associated values (similar to a database), while File Storages offer access to a set of files (similar to a directory of a file system). The typical usage of the Persistency within an Adaptive Application is depicted in Figure 7.1. As shown there, an Adaptive Application can use a combination of multiple Key-Value Storages and multiple File Storages. Figure 7.1: Typical usage of Persistency within an Adaptive Application 7.1.1 Persistency in the Manifest The Persistency usage of an Adaptive Application is modeled in the Execution Manifest (furtheron simply referred to as the “manifest”) as part of the AdaptiveApplicationSwComponentTypes of an Executable. The model has two principal parts: The application design information, aggregated by the PersistencyKeyValueStorageInterface and the PersistencyFileStorageInterface, and the deployment information, aggregated by the PersistencyKeyValueStorage and the PersistencyFileStorage. 23 of 150 Document ID 858: AUTOSAR_SWS_Persistency
