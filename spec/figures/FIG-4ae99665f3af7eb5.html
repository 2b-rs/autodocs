1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Datenflussdiagramm nach SPEM 2.0 (Software & Systems Process Engineering Metamodel), adaptiert für die AUTOSAR-Methodologie (Activity & Work Product Flow).
  • Technischer Zweck: Spezifikation des methodischen Teilprozesses „Develop an Atomic Software Component“ (Fortsetzung/Detailansicht 2). Das Diagramm modelliert die Transformation von Modellartefakten (Internal Behavior, Timing Extensions, Variantenmodelle) und generierten RTE-Schnittstellen (Contract Phase) in konkreten C-Quellcode, Objektcode sowie die begleitenden ARXML-Implementierungsbeschreibungen und Ressourcenmessungen.

2. Komponenten, Entitäten & Schnittstellen

#### Aktivitäten (SPEM Tasks / Prozess-Schritte)

  • Implement Atomic Software Component: Manuelle oder modellbasierte Codegenerierung/Implementierung der SWC-Runnables gegen das RTE-Contract-Interface.
  • Compile Atomic Software Component: Übersetzung des Quellcodes mittels zielplattformspezifischem Cross-Compiler in Objektcode.
  • Measure Component Resources: Statische/dynamische Analyse von Ressourcenbedarf (Stack, Heap, ROM/RAM-Sektionsgrößen, WCET/Laufzeiten) basierend auf Binärartefakten und Metadaten.
  • Evaluate Variant: Vor- bzw. nachgelagerter Prozessschritt zur Auflösung modellierter Variationspunkte (Variation Points) vor der Codegenerierung oder Kompilierung.

3. Dynamisches Verhalten & Sequenzablauf

  1. Variantenauflösung (Evaluate Variant):
  • Bindung von Variationspunkten über PredefinedVariant oder SystemConstantValueSet. Bestimmt, welche Software-Elemente (z. B. optionale Ports, Runnables) in den nachfolgenden Schritten aktiv sind.
  1. Implementierungsphase (Implement Atomic Software Component):
  • Der Anwendungsentwickler realisiert die im SwcInternalBehavior deklarierten Runnable-Entities.
  • Der Code nutzt ausschließlich die im Application Header File (Rte_<SWC>.h) definierten Contract-APIs (Rte_Read_, Rte_Write_, Rte_Call_*) und Typen aus Rte_Type.h.
  • Ergebnis: C-Sourcedatei(en) und das Metadaten-Artefakt Atomic Software Component Implementation (enthält Mapping auf Code-Dateien, Speichereigenschaften, Compiler-Abstraktion).
  1. Übersetzungsphase (Compile Atomic Software Component):
  • Der C-Compiler übersetzt den Source Code zusammen mit den Standard-Headern, RTE-Contract-Headern, optionalen Bibliotheken und dem Component RTE Prebuild Configuration Header (Auflösung von Compile-Time-Varianten per #ifdef).
  • Atomic Software Component Implementation agiert als «inoutput»: Das ARXML-Artefakt wird während des Build-Schritts um compilerspezifische Symbol- und Linker-Informationen ergänzt.
  • Ergebnis: Maschinencode (Atomic Software Component Object Code).
  1. Ressourcenbewertung (Measure Component Resources):
  • Post-Compile-Verifikation: Abgleich des Objektcodes gegen Anforderungen aus Software Component Timing (Execution Times, Worst-Case Timing) und Auslesen von Code-/Daten-Größen zur Dokumentation im Implementierungs-Deskriptor.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE Contract Phase vs. Generation Phase: Das Diagramm zeigt die isolierte Komponentenentwicklung in der Contract Phase. Der Code wird gegen generierte Mock/Contract-Header (Rte_<SWC>.h) kompiliert, bevor die finale RTE-Generierung (ECU Integration Phase) stattfindet.
  • Rolle von SwcImplementation: Der Entwickler bzw. das Generierungs-Toolchain muss zwingend ein valides SwcImplementation-ARXML erzeugen. Dieses bindet den Source- und Objektcode an das SwcInternalBehavior und spezifiziert Memory-Mapping-Symbole (SwAddrMethod, z. B. für MEMMAP_CODE, MEMMAP_VAR), Compiler-Optionen und Ressourceneigenschaften.
  • Varianten-Handling:
  • Pre-compile: Über PredefinedVariant / Component RTE Prebuild Configuration Header fließen Schalter als Preprozessor-Makros in die Kompilierung ein.
  • Post-build: Postbuild Variant Set verbleibt als modellarische Vorgabe, erfordert aber zur Laufzeit konfigurierbare Strukturen (Datenvektoren/Pointersätze).
  • Plattformunabhängigkeit: Durch die verpflichtende Einbindung der Standard Header Files (Compiler.h, Platform_Types.h) muss der Komponenten-Quellcode zwingend AUTOSAR-konforme Datentypen (uint8, boolean) und Makros (FUNC, VAR, CONST) nutzen, um portabel auf unterschiedlichen Zielcontrollern übersetzbar zu sein.
