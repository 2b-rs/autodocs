1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm der AUTOSAR Adaptive Platform (System Design / Manifest Specification). Das Diagramm stellt das Metamodell für die Konfiguration von IPsec-Verbindungen auf Netzwerkendpunktebene sowie deren Abbildung auf kryptografische Schlüssel und Zertifikate über zwei Hauptdomänen dar: das übergeordnete System Design (System Design) und das maschinenspezifische Manifest (MachineManifest).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in zwei Pakete:

System Design:

  • NetworkEndpoint (Identifiable): Repräsentiert den Netzwerk-Endpunkt mit den Attributen fullyQualifiedDomainName: String [0..1] und priority: PositiveInteger [0..1]. Komponiert über +networkEndpointAddress (Kardinalität 0..) Instanzen von NetworkEndpointAddress, referenziert über +remoteIpAddress (Kardinalität 0..) andere NetworkEndpoint-Elemente und besitzt eine mit «atpSplitable» versehene Komposition +ipSecConfig (Kardinalität 0..1) zu IPSecConfig.
  • NetworkEndpointAddress: Ziel der Adresskomposition aus NetworkEndpoint.
  • IPSecConfig: Bündelt die IPsec-Regeln und Konfigurationsparameter. Besitzt eine Aggregation +ipSecConfigProps (Kardinalität 0..1) zu IPSecConfigProps sowie eine Komposition +ipSecRule (Kardinalität 0..*) zu IPSecRule.
  • IPSecConfigProps (ARElement, UploadableDesignElement): Enthält globale IPsec- und IKE-Parameter: ahCipherSuiteName: String [0..], dpdAction: IPsecDpdActionEnum [0..1], dpdDelay: TimeValue [0..1], espCipherSuiteName: String [0..], ikeCipherSuiteName: String [0..1], ikeOverTime: TimeValue [0..1], ikeRandTime: PositiveInteger [0..1], ikeReauthTime: TimeValue [0..1], ikeRekeyTime: TimeValue [0..1], saOverTime: PositiveInteger [0..1], saRandTime: TimeValue [0..1], saRekeyTime: TimeValue [0..1].
  • IPSecRule (Identifiable): Definiert individuelle Sicherheitsregeln mit Attributen: direction: CommunicationDirectionType [0..1], headerType: IPsecHeaderTypeEnum [0..1], ipProtocol: IPsecIpProtocolEnum [0..1], localId: String [0..1], localPortRangeEnd: PositiveInteger [0..1], localPortRangeStart: PositiveInteger [0..1], mode: IPsecModeEnum [0..1], policy: IPsecPolicyEnum [0..1], priority: PositiveInteger [0..1], remoteId: String [0..1], remotePortRangeEnd: PositiveInteger [0..1], remotePortRangeStart: PositiveInteger [0..1]. Referenziert optional über +preSharedKey (Kardinalität 0..1) ein CryptoServiceKey sowie über +localCertificate (0..) und +remoteCertificate (0..) Instanzen von CryptoServiceCertificate.
  • CryptoServiceKey (ARElement, UploadableDesignElement): Spezifiziert kryptografische Schlüssel mit algorithmFamily: String [0..1], keyGeneration: CryptoServiceKeyGenerationEnum [0..1], keyStorageType: String [0..1], length: PositiveInteger [0..1].
  • CryptoServiceCertificate (ARElement, UploadableDesignElement): Spezifiziert Zertifikate mit algorithmFamily: CryptoCertificateAlgorithmFamilyEnum [0..1], format: CryptoCertificateFormatEnum [0..1], maximumLength: PositiveInteger [0..1], serverNameIdentification: String [0..1]. Kann über +nextHigherCertificate (0..1) rekursiv auf übergeordnete Zertifikate verweisen.
  • ComKeyToCryptoKeySlotMapping (FunctionalClusterInteractsWithFunctionalClusterMapping): Bildet über +cryptoServiceKey (0..1) einen logischen Schlüssel auf einen physischen Key-Slot im Manifest ab.
  • ComCertificateToCryptoCertificateMapping (FunctionalClusterInteractsWithFunctionalClusterMapping): Bildet über +cryptoServiceCertificate (0..1) ein logisches Zertifikat auf ein Zertifikat im Manifest ab.

MachineManifest:

  • CryptoKeySlot (Identifiable): Physischer Schlüsselsteckplatz mit Attributen allocateShadowCopy: Boolean [0..1], cryptoAlgId: String [0..1], cryptoObjectType: CryptoObjectTypeEnum [0..1], slotCapacity: PositiveInteger [0..1], slotType: CryptoKeySlotTypeEnum [0..1]. Wird von ComKeyToCryptoKeySlotMapping über +keySlot (0..1) referenziert.
  • CryptoCertificate (Identifiable): Zertifikatselement der Maschine mit isPrivate: Boolean [0..1]. Wird von ComCertificateToCryptoCertificateMapping über +cryptoCertificate (0..1) referenziert.

3. Dynamisches Verhalten & Sequenzablauf

Statisches Strukturdiagramm ohne Ablauf- oder Sequenzdarstellung. Die funktionale Kette verläuft deklarativ von der Konfiguration der Netzwerkendpunkte (NetworkEndpoint) über Sicherheitsrichtlinien (IPSecRule) zu den logischen kryptografischen Elementen (CryptoServiceKey, CryptoServiceCertificate) und wird über Zuordnungselemente (FunctionalClusterInteractsWithFunctionalClusterMapping) mit den maschinenspezifischen Speicherorten (CryptoKeySlot, CryptoCertificate) im Manifest verknüpft.

4. Normative Relevanz & Entwickler-Hinweise

Das Metamodell definiert die verbindliche Struktur zur Spezifikation von IPsec-Kommunikationsbeziehungen in AUTOSAR Adaptive. Es trennt die funktionale Systemmodellierung (Dienst- und Protokollebene im System Design) von der maschinenspezifischen Realisierung (physische Schlüsselspeicher und Zertifikatsstrukturen im Machine Manifest). Für Entwickler und Konfiguratoren ist sicherzustellen, dass jede konfigurierte IPSecRule mit den passenden Zertifikatsketten bzw. Pre-Shared Keys verknüpft und über die Mapping-Klassen gültigen Slots und Zertifikaten im Maschinenspeicher zugeordnet ist.
