1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Komponentendiagramm / Deployment-Diagramm mit Schichtenarchitektur (AUTOSAR Adaptive Platform Execution Environments & Systemgrenzen).
  • Technischer Zweck: Spezifikation der fahrzeugweiten Over-The-Air- (OTA) und Tester-basierten Update-Architektur (Vehicle Update Management) gemäß AUTOSAR Adaptive Platform (EXP_PlatformDesign, R23-11).
  • Funktionale Einordnung: Orchestrierung verteilter Software-Updates über heterogene Steuergeräte hinweg. Das Diagramm definiert das Zusammenspiel zwischen fahrzeugexternen Quellen (Cloud-Backend, Diagnosetester), fahrzeuginterner Koordination (VUCM), fahrzeugeigenen Zustands-/Fahrersicherheitsinstanzen (VSM, VDI), knotenlokalem Update-Management (UCM, SM, EM) sowie der Flash-Anbindung von Classic AUTOSAR ECUs über ISO 22900-2 (D-PDU API).

2. Komponenten, Entitäten & Schnittstellen

Externe Entitäten & Artefakte
  • Backend: Cloud-Infrastruktur; liefert das Gesamt-Artefakt «deployment...» VehiclePackage aus, welches einzelne SoftwarePackage A und SoftwarePackage B aggregiert («deploy»-Beziehung).
  • Diagnostic Client: Stationärer Diagnosetester (Werkstatttester); kann alternativ/ergänzend SoftwarePackage C über einen fahrzeugseitigen DoIP socket («optional») einbringen.
  • Driver HMI (from V-UCM sequences): Physischer Fahrer/Bediener; interagiert mit der Vehicle Driver Interface-Applikation (Einwilligung, Installationsbestätigung, Countdown).
Fahrzeuginterne Hardware- und Laufzeitumgebungen
  • Vehicle: Physische Fahrzeugbegrenzung.
  • «device» ECU (Adaptive Platform ECU): Zentrales Steuergerät / HPC-Knoten.
    • «executionEnvironment» Machine: Host-Betriebssystem / POSIX-Instanz.
      • «executionEnvironment» Autosar Adaptive Application layer (Applikationsebene):
        • OTA Client: Adaptive Application; terminiert die Backend-Verbindung via Backend-Port, extrahiert das VehiclePackage und übergibt es an das VUCM über VehiclePackageManagement («use»).
        • Vehicle State Manager (VSM): Adaptive Application; prüft/garantiert Fahrzeugsicherheitszustände (z. B. Stillstand, Ladezustand, Parkbremse) und stellt Status via VSM-Port über ara::com bereit («use»).
        • Vehicle Driver Interface (VDI): Adaptive Application; Benutzeroberfläche zur Einholung von Fahrer-Zustimmungen; angebunden an das VUCM via VDI-Port über ara::com («use»).
        • Flashing Adapter: Adaptive Application; Brücke zu Classic ECUs. Konsumiert PackageManagement (UCM Sub-Rolle) über ara::com und spricht die D-PDU API ISO22900-2 an.
        • Diagnostic Application: Adaptive Application zur Verarbeitung von Diagnose-Update-Pfaden über den Diagnostic Manager.
      • «executionEnvironment» AUTOSAR Adaptive Platform (Plattform-Dienste/Foundation):
        • «service» VUCM: Zentrale Orchestrierungsinstanz für das Fahrzeug-Update (Vehicle Update and Configuration Management). Exponiert Services:
          • VPM (VehiclePackageManagement): Interface für OTA Client.
          • VSM (VehicleStateManagerInterface): Schnittstelle zur Abfrage von Sicherheitsbedingungen beim Vehicle State Manager.
          • VDI (VehicleDriverApplicationInterface): Schnittstelle zur Fahrerinteraktion mit dem Vehicle Driver Interface.
          • UCM Sub: Steuerkanal zur Verteilung von Teilpaketen an lokale UCMs und Flashing Adapter.
        • «service» UCM (Update and Configuration Management - Subordinate): Knotenlokaler Dienst zur Paketverwaltung und -installation auf der Machine; stellt das Interface PackageManagement bereit (konsumiert von VUCM via UCM Sub und Diagnostic Manager) und triggert Zustandswechsel über die Schnittstelle UpdateRequest an SM.
        • SM (State Management): Plattformdienst zur Koordination von Funktionsgruppen- und Maschinenzuständen; empfängt UpdateRequest vom UCM und steuert EM.
        • EM (Execution Management): Plattforminstanz zur Prozessverwaltung und Zustandsaktivierung gemäß Steuerung durch SM.
        • Diagnostic Manager: Plattformdienst für UDS-Diagnose über DoIP; angebunden an den fahrzeugseitigen DoIP socket und interagiert mit Diagnostic Application sowie PackageManagement am lokalen UCM.
        • D-PDU API ISO22900-2: Plattformmodul zur hardwarenahen PDU-Abstraktion mit DoIP socket zur Diagnose- und Flashkommunikation mit weiteren Steuergeräten.
Unterlagerte Steuergeräte
  • «device» Classic AUTOSAR ECU: Über Netzwerk angebundenes Classic-Steuergerät; wird über den Flashing Adapter via D-PDU API ISO22900-2 geflasht.

3. Dynamisches Verhalten & Sequenzablauf

  • Pakettransfer & Entgegennahme:
    • OTA-Pfad: Der OTA Client empfängt das ganzheitliche VehiclePackage vom Cloud-Backend via «deploy»-Verbindung am Port Backend.
    • Werkstatt-Pfad: Ein externer Diagnostic Client kann alternativ Softwarepakete (SoftwarePackage C) über einen fahrzeugseitigen DoIP socket («optional») und den Diagnostic Manager einbringen.
  • Orchestrierung durch das VUCM:
    • Der OTA Client übergibt das VehiclePackage über die Service-Schnittstelle VehiclePackageManagement (VPM) via ara::com an das VUCM.
    • Das VUCM analysiert das Manifest des VehiclePackage und partitioniert die Zielpakete für die Ziel-Steuergeräte.
  • Fahrzeugzustands- und Fahrerkoordination:
    • Vor und während des Installationsprozesses fragt das VUCM über den Port VSM (VehicleStateManagerInterface) Sicherheitsbedingungen (z. B. Parkzustand, Ladezustand) beim Vehicle State Manager ab.
    • Über den Port VDI (VehicleDriverApplicationInterface) interagiert das VUCM mit dem Vehicle Driver Interface, um die Zustimmung des Fahrers (Driver HMI) einzuholen und Fortschritt oder Warnungen darzustellen.
  • Verteilung und Installation:
    • Das VUCM verteilt Teilpakete über die UCM Sub-Rolle an das Interface PackageManagement:
      • An den lokalen UCM der Adaptive-Maschine für adaptive Software-Cluster.
      • An den Flashing Adapter zur Aktualisierung von Classic AUTOSAR Steuergeräten.
    • Der lokale UCM koordiniert die lokale Paketaktivierung über UpdateRequest mit dem State Management (SM), welches wiederum den Execution Management (EM) zur Ausführung oder Umschaltung von Prozessen anweist.
    • Der Flashing Adapter transferiert die Update-Daten über die D-PDU API ISO22900-2 (DoIP) direkt auf die Classic AUTOSAR ECU.

4. Normative Relevanz & Entwickler-Hinweise

  • AUTOSAR-Spezifikationsbezug:
    • Relevante Standardspezifikationen: AUTOSAR_EXP_PlatformDesign, AUTOSAR_SWS_VehicleUpdateAndConfigurationManagement (VUCM ab R23-11), AUTOSAR_SWS_UpdateAndConfigurationManagement (UCM) und AUTOSAR_SWS_StateManagement.
    • Definition der serviceorientierten Schnittstellen über ara::com:
      • VehiclePackageManagement (VPM): Übertragung, Statusabfrage und Orchestrierung des Gesamtpakets.
      • VehicleStateManagerInterface (VSM): Validierung des sicheren Fahrzeugzustands (Safe State) vor Beginn kritischer Flash- und Aktivierungsphasen.
      • VehicleDriverApplicationInterface (VDI): HMI-Kopplung zur Einholung der Nutzerzustimmung (Driver Consent) und Abbruchbehandlung.
      • PackageManagement: Einheitliche Client-Server-Schnittstelle für knotenlokale UCMs und Gateway-Adapter.
  • Architekturprinzipien & heterogene Integration:
    • Kapselung von Classic ECUs: Classic AUTOSAR ECUs verfügen über keinen standardisierten Adaptive-UCM. Der Flashing Adapter fungiert als Brücke zwischen der ara::com-Serviceebene und standardisierten Diagnoseroutinen über die D-PDU API ISO22900-2 (UDS/DoIP).
    • Atomarität und Rollback: Das VUCM überwacht das synchrone Ausrollen über alle Knoten; bei Fehlschlag eines Teilpakets muss ein fahrzeugweites Rollback-Verfahren initiiert werden.
