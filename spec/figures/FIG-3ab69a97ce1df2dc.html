  • Klassifikation: Architekturelles Schichten- und Komponentenmodell (Blockdiagramm mit Daten-/Kontrollfluss).
  • Technischer Zweck: Spezifikation des Aufbaus und der Integrationsgrenzen des OS/ARTI Drivers innerhalb der AUTOSAR Adaptive Platform (AP). Das Diagramm definiert die Entkopplung zwischen OS-internen Ereignissen (POSIX-Ebene), dem herstellerspezifischen OS-Trace-Adapter, der standardisierten ARTI-Schnittstelle (OS/ARTI API) und dem Tracing-Tool-Vendor-spezifischen Backend (ARTI light weight C API). Es ermöglicht die standardisierte Erfassung, Verifikation und Visualisierung des Laufzeit- und Scheduling-Verhaltens (Prozesse, Threads/Tasks).

2. Komponenten, Entitäten & Schnittstellen

  • Operating System (OS-Domäne):
  • POSIX/OS (Komponente): Das zugrundeliegende Echtzeitbetriebssystem (z. B. QNX, Linux/PREEMPT_RT, PikeOS), das native OS-Events (Scheduling, Context Switches, Process/Thread-Lifecycle) erzeugt.
  • OS/ARTI Driver (Integrations-Container):
  • Umspannt die OS-Domäne und ragt in die Domäne des Tracing-Tools hinein. Kapselt die Tracepoint-Logik.
  • OS/ARTI Adapter (Komponente): Fängt OS-spezifische POSIX-Events ab, transformiert diese in AUTOSAR-konforme Trace-Semantik (Mapping von Thread $\rightarrow$ Task, POSIX Process $\rightarrow$ AUTOSAR Process).
  • OS/ARTI API (Schnittstelle / Abstraktionsschicht): Standardisierte C-Schnittstelle, die Trace-Hooks/Macros definiert.
  • Trace Tool (Tooling-Domäne):
  • ARTI (light weight C API) (Bibliothek / Sink): Tool-Hersteller-spezifische Implementierung der ARTI-Hooks. Nimmt Trace-Payloads entgegen und leitet sie über Hardware-Trace-Ports, Ringbuffer oder Speicherkanäle nach außen (roter Pfeil nach rechts).
  • Beziehungen & Verbindungen:
  • POSIX/OS $\rightarrow$ OS/ARTI Adapter: Event-Trigger / Kontrollfluss (OS-Hook/Interception).
  • OS/ARTI Adapter $\rightarrow$ OS/ARTI API: Aufruf standardisierter ARTI-Trace-Funktionen bzw. Makros.
  • OS/ARTI API $\bullet\hspace{-1.5mm}-$ ARTI (light weight C API): Schnittstellenkopplung (Lollipop-/Socket-Bindung; Header-Definition vs. herstellerspezifische Implementierung/Makro-Expansion).
  • ARTI (light weight C API) $\rightarrow$ (extern): Serialisierung / Trace-Stream-Ausgabe an das Analyse-Tool.

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger: Ein OS-internes Zustandsereignis tritt auf (z. B. Thread-Statuswechsel RUNNING $\rightarrow$ BLOCKED, Fork/Exec, IPC-Aktivität).
  2. Adapter-Verarbeitung (synchron): Das POSIX/OS ruft den OS/ARTI Adapter auf. Der Adapter filtert und konvertiert die OS-spezifischen Deskriptoren (TID, PID, Priorität) in standardisierte ARTI-Parameter.
  3. API-Aufruf: Der Adapter feuert die dedizierte Trace-Hook-Funktion/das Makro über die OS/ARTI API.
  4. Tool-Payload-Generierung (asynchron/synchron): Die ARTI (light weight C API) expandiert den Hook:
  • Aktiviertes Tracing: Minimalinvasives Schreiben in hardwaregestützte Trace-Buffer (z. B. CoreSight, NEXUS) oder RAM-Puffer.
  • Deaktiviertes Tracing: Zero-Overhead-Pfad via Makro-Expansion auf (void)0 oder Aufruf eines leeren Inline-Stubs (NOP).

4. Normative Relevanz & Entwickler-Hinweise

  • Zwei-Ebenen-Abstraktionsmodell: Entwickler müssen das AUTOSAR-Modell beachten: Ein POSIX-Prozess entspricht dem Process, schedulbare POSIX-Threads entsprechen Tasks.
  • Zero-Overhead & Determinismus: Die OS/ARTI API ist zwingend als leichtgewichtige C-API (Macro oder Inline-C-Funktion) auszulegen, um die Latenz im OS-Kernel bzw. im Scheduler auf ein absolutes Minimum zu beschränken und Heisenbugs zu vermeiden.
  • Liefergrenzen & Tool-Entkoppelung:
  • Der OS-Hersteller liefert den OS/ARTI Adapter passend zu seinem POSIX-Kernel.
  • Der Trace-Tool-Vendor liefert die Header/Implementierung der ARTI (light weight C API).
  • Das OS bleibt dadurch unabhängig vom konkreten Analysewerkzeug (Lauterbach, iSYSTEM, etc.) kompilier- und austauschbar.

Technical Report on Operating System Tracing Interface AUTOSAR AP R24-11 4 Functional Specification 4.1 ARTI Tracing Interface 4.1.1 OS/ARTI Adapter The so-called “OS/ARTI Adapter” provides the trace points at OS level. It is used to understand, verify and visualize the timing behavior of the OS. The ARTI trace hooks themselves form a standardized interface that is specified by the API below. Figure 4.1 illustrates the Layout of the OS/ARTI driver containing the OS/ARTI Adapter. POSIX/OS OS/ARTI Adapter ARTI (light weight C API) OS/ARTI API OS/ARTI Driver Operating System Trace Tool Figure 4.1: Layout of the OS/ARTI Driver The implementation of the ARTI hooks themselves depends on the tracing mechanism and shall be provided by the tracing tool vendor. The ARTI hook interface is designed to be usable as a C macro expansion or as a C function. If no tracing mechanism is available, the ARTI hooks may be expanded to nothing (in case of a macro) or call an empty function. The ARTI interface follows the two-level approach of AUTOSAR, where a “task” is a schedulable unit (in OSes often called “thread”), and a “process” is a mandatory environment holding several tasks.
