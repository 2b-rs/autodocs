1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Schichten- und Blockarchitekturdiagramm (Functional Block Architecture) der AUTOSAR Adaptive Platform (AP).
  • Technischer Zweck: Spezifikatorische Abgrenzung der Laufzeitumgebung AUTOSAR Runtime for Adaptive Applications (ARA) gegenüber dem unterlagerten Betriebssystem (POSIX PSE51 / C++ STL) und den darüberliegenden Benutzerapplikationen (User Applications).
  • Architektur-Einordnung: Visualisiert die duale Integrationsstrategie der funktionalen Cluster (FCs) in Bibliotheks-Cluster (API Functional Clusters) und daemon-basierte Plattformdienste (Service Functional Clusters) gemäß AUTOSAR Release R18-03 (v1.4.0).

2. Komponenten, Entitäten & Schnittstellen

#### 1. Schichtung & Basisinfrastruktur

  • (Virtual) Machine / Container / Hardware: Hardware-Ausführungsumgebung inklusive Hypervisor-, Virtualisierungs- oder Container-Schicht mit MMU-basiertem Speicherschutz.
  • POSIX PSE51 / C++ STL Operating System: Betriebssystem-Schnittstelle gemäß POSIX PSE51-Profil (Single-Process, Multi-Threaded Ausführungseinheit per Prozess) inklusive C++-Standard-Template-Library.

#### 2. API Functional Clusters (In-Process / Link-Time Integration)

Werden als Shared/Static Libraries direkt in den Adressraum der Adaptive Application eingebunden:

  • ara::core: Fundamentale Typdefinitionen, STL-Erweiterungen und fehlertolerante Datentypen (ara::core::Result<T, E>, ara::core::Span, ara::core::InstanceSpecifier).
  • ara::com: Serviceorientierte Kommunikations-Middleware mit austauschbaren Protokoll-Bindings:
  • SOME/IP (netzwerkweit, ECU-übergreifend)
  • IPC (local) (Host-interne Shared-Memory/Socket-Interprozesskommunikation)
  • DDS (Data Distribution Service)
  • ara::exec: Schnittstelle zum Execution Management (Start-/Laufzeitkonfiguration, deterministic client control).
  • ara::per: Persistenzschicht (Key-Value-Storage und dateibasierter Zugriff mit Integritäts-/Redundanzschutz).
  • ara::log: Logging- und Tracing-Framework (Schnittstelle zu DLT / Konsolenbackends).
  • ara::crypto: Kryptografische Primitiven, Zertifikats- und Schlüsselverwaltung (PKI, X.509, Crypto-Provider).
  • ara::phm: Client-Interface für das Platform Health Management (Alive-, Deadline- und Logical Supervision via Checkpoint-Reporting).
  • ara::time: Zeitsynchronisations-Interface (PTP/IEEE 802.1AS, Clock-Abstraktionen).
  • ara::iam: Identity and Access Management (Zugriffsrechteverwaltung für Adaptive Services und Schnittstellen).
  • ara::rest: RESTful-Webservice-Schnittstelle für web- und cloudbasierte Interaktion.

#### 3. Service Functional Clusters (Daemon-Prozesse / Service-Orientiert)

Werden als eigenständige POSIX-Betriebssystemprozesse instanziiert und ausschließlich über ara::com-Proxies/Skeletons konsumiert:

  • ara::state service: State Management zur Maschinen- und Funktionsgruppen-Zustandssteuerung (FunctionGroupStates).
  • ara::diag service: Diagnoseserver für UDS (ISO 14229-1) und DoIP (ISO 13400-2).
  • ara::s2s service: Signal-to-Service-Mapping (Gateway zur Transformation von signalbasierten CAN/LIN/FlexRay-Frames in serviceorientierte Events/Methods).
  • ara::nm service: Netzwerkmanagement (Koordination der partiellen Vernetzung und Busruhe).
  • ara::ucm service: Update and Configuration Management (Validierung, Entpackung und Einspielen von Softwarepaketen / OTA-Updates).

#### 4. Applikationsschicht (User Applications)

  • Adaptive Application: Standard-Anwendungsprozesse (native C++-Binaries im User-Space).
  • ASW::XYZ / ASW::ABC Non-PF Service: Anwendungsdefinierte Services, die Nicht-Plattform-Funktionalitäten über ara::com anderen Applikationen bereitstellen.

3. Dynamisches Verhalten & Sequenzablauf

#### Interaktionsmuster

  1. In-Process-Aufrufpfade (Synchron / Deterministisch):
  • Aufrufe an API Functional Clusters (ara::core, ara::per, ara::crypto, ara::log) erfolgen über direkte synchrone C++-Methodenaufrufe im Adressraum des aufrufenden Prozesses.
  • Keine IPC-Kontextwechsel, wodurch geringe Latenzen und strikter Determinismus gewährleistet sind.
  1. Serviceorientierte Interprozess-Kommunikation (Brokerless / Proxy-Skeleton Pattern):
  • Aufrufe an Service-Cluster (ara::state, ara::diag, ara::ucm, ara::nm, ara::s2s) oder Non-PF Services laufen zwingend über generierte ara::com-Bindings.
  • Service Discovery: FindService/OfferService via IPC oder SOME/IP-SD.
  • Kommunikationsparadigmen:
  • Asynchron über Events (ara::com::Event / Observer Pattern).
  • Synchron/Asynchron über Methods (ara::core::Future / ara::core::Promise).
  • Zustandsbehaftet über Fields (Getter, Setter, Notifier).
  1. Plattform-Lifecycle & Supervision:
  • Initialisierung: ara::exec instanziiert Prozesse anhand des Execution Manifests.
  • Überwachung: Prozesse melden periodisch Kontrollflüsse über die ara::phm-API; bei Abweichungen leitet ara::phm Fehlerreaktionen via ara::state ein (Recovery Actions, Neustart oder Fallback-State).

4. Normative Relevanz & Entwickler-Hinweise

  • Exception-Handling: AUTOSAR AP verbietet in sicherheitsrelevanten Partitionen C++-Exceptions. APIs von ara::* verwenden normativ ara::core::Result<T, E>. Entwickler müssen Rückgabewerte explizit prüfen (.HasValue(), .Value(), .Error()).
  • POSIX-Restriktionen: Implementierungen sind strikt auf das POSIX PSE51-Profil limitiert (kein dynamisches Laden via dlopen(), kein unkontrolliertes fork() / Multi-Processing außerhalb der Kontrolle von ara::exec).
  • Freedom From Interference (FFI nach ISO 26262):
  • Räumliche Trennung (Spatial Isolation): Durch MMU-gestützte POSIX-Prozesse und optionale Container/VMs.
  • Zeitliche Trennung (Temporal Isolation): Prioritätsgesteuertes Scheduling (SCHED_FIFO, SCHED_RR), deterministische Event-Loops und Budget-Überwachung via ara::phm.
  • Binding-Transparenz: Applikationscode darf nicht hart an SOME/IP oder IPC gebunden werden; die Bindung erfolgt modellgetrieben im Service Instance Deployment und wird zur Generierungszeit über ara::com injiziert.
