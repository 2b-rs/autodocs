1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (Metamodell-Ausschnitt des AUTOSAR BSW Module Description Template, BSW-MDT).
  • Architektur-Kontext: Formales Metamodell zur statischen und empirischen Charakterisierung des Stack-Speicherbedarfs (StackUsage) innerhalb des Ressourcenmodells (ResourceConsumption). Es dient Integratoren, Timing-/Stack-Analyse-Tools und OS-Konfiguratoren dazu, den Worst-Case-, geschätzten oder gemessenen Stack-Bedarf von BSW-Funktionen (ExecutableEntity) in Abhängigkeit von Hardware-Plattform (HwElement, HardwareConfiguration) und Ausführungskontext (SoftwareContext) präzise zu deklarieren, ohne die OS-Task-Stack-Allokation selbst vorwegzunehmen.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Vererbungshierarchien
  • ResourceConsumption (Spezialisierung von Identifiable):
    • Container für Ressourcenmetriken eines BSW-Moduls/Clusters.
    • Komposition zu StackUsage (+stackUsage, Kardinalität 0..*), annotiert mit den Stereotypen «atpVariation,atpSplitable» (unterstützt AUTOSAR-Post-Build/Pre-Compile-Variantenbildung sowie Aufteilung über ARXML-Dateigrenzen hinweg).
  • StackUsage (abstrakt, Kennzeichnung A / kursiv, Spezialisierung von Identifiable):
    • Abstrakte Basisklasse für alle Stack-Bedarfsmetriken.
    • Referenziert optional eine ausführende Entität: +executableEntity (0..1) auf ExecutableEntity (Spezialisierung von Identifiable).
    • Referenziert optional das Zielhardware-Element: +hwElement (0..1) auf HwElement (Spezialisierung von ARElement, HwDescriptionEntity).
    • Komposition +softwareContext (0..1) auf SoftwareContext:
      • +input: String [0..1]: Repräsentiert funktionale Eingabeparameter/Stimuli (optional).
      • +state: String [0..1]: Modulinterner Zustand/Modus während der Messung/Berechnung (optional).
    • Komposition +hardwareConfiguration (0..1) auf HardwareConfiguration:
      • +additionalInformation: String [0..1]: Ergänzende Hardware-Bedingungen (z. B. Cache-Status, Waitstates) (optional).
      • +processorMode: String [0..1]: CPU-Privilegien/Modus (z. B. User/Supervisor, Thumb/ARM) (optional).
      • +processorSpeed: String [0..1]: Taktfrequenz/Core-Geschwindigkeit (optional).
Konkrete Subklassen von StackUsage (Generalisierung)
  • WorstCaseStackUsage:
    • Garantierte analytische Obergrenze des Stack-Verbrauchs (z. B. via statischer Call-Tree-/Stack-Analyse / WCET/WCSA-Tools ermittelt).
    • +memoryConsumption: PositiveInteger [0..1] (in Bytes, optional).
  • RoughEstimateStackUsage:
    • Heuristische oder grobe Schätzung vor detaillierter Implementierung/Messung.
    • +memoryConsumption: PositiveInteger [0..1] (in Bytes, optional).
  • MeasuredStackUsage:
    • Empirisch ermittelte Messwerte (z. B. über Stack-Painting, Hardware-Debugger, Profiler).
    • +averageMemoryConsumption: PositiveInteger [0..1]: Arithmetischer Mittelwert (optional).
    • +maximumMemoryConsumption: PositiveInteger [0..1]: Gemessenes Maximum (optional).
    • +minimumMemoryConsumption: PositiveInteger [0..1]: Gemessenes Minimum (optional).
    • +testPattern: String [0..1]: Verwendetes Testmuster/Stimulusszenario (optional).

3. Dynamisches Verhalten & Sequenzablauf

  • Statische Modellstruktur: Das Diagramm modelliert keine Laufzeit-Sequenzen, sondern statische Metadaten-Deskriptoren für den Engineering-Workflow.
  • Parametrierungspfad im Tooling:
    1. Einspeisung / Deklaration: Modulentwickler/Tier-1 instanziiert für eine ExecutableEntity (z. B. Can_MainFunction_Write) eine oder mehrere StackUsage-Spezifikationen.
    2. Kontextbindung: Zuordnung von Ziel-Core/Controller (HwElement), Frequenz/Modus (HardwareConfiguration) und Betriebszustand (SoftwareContext).
    3. Stack-Synthese: Der System-/OS-Integrator bzw. der Stack-Synthesizer aggregiert die deklarierten Verbräuche über den OS-Task-Aufrufbaum (Call-Tree-Analyse inkl. lokaler Variablen, Register-Pushs, Alignment-Overhead und Interrupt-Verschachtelungen).

4. Normative Relevanz & Entwickler-Hinweise

  • Trennungsprinzip BSW vs. OS: Ein BSW-Modul spezifiziert ausschließlich seinen eigenen lokalen Stack-Verbrauch pro Entity, niemals die Größe des OS-Task-Stacks. Die finale Dimensionierung der OS-Task-Stacks (OsTaskStackSize in Os.arxml) obliegt dem Systemintegrator unter Berücksichtigung von Preemption, ISR-Verschachtelung und Call-Hierarchien.
  • Konfigurationsverbindlichkeit (PositiveInteger): Werte werden als dimensionslose positive Ganzzahlen modelliert, repräsentieren im AUTOSAR-Standard jedoch Byte-Werte. Alignment-Restriktionen (z. B. 4-Byte- oder 8-Byte-Alignment auf 32/64-Bit-Architekturen) müssen bereits im gemeldeten Wert berücksichtigt sein.
  • Variantenmanagement («atpVariation»): Da Compiler-Optimierungen (-O2, -O3, Inlining) und plattformspezifische ABIs (Register-Parameter vs. Stack-Spilling) den Stackbedarf drastisch verändern, erlaubt «atpVariation» die Definition separater Stack-Deskriptoren für unterschiedliche Build- und Plattform-Varianten.
  • Tool-Interoperabilität: Analyse-Tools (z. B. AbsInt StackAnalyzer) importieren die ARXML-Beschreibungen von WorstCaseStackUsage und ExecutableEntity, um automatisiert Stack-Overflow-Freiheit für Safety-relevante Systeme (ISO 26262 ASIL A-D) formal nachzuweisen.

Begleitender Spezifikationstext:

Basic Software Module Description Template AUTOSAR CP R24-11 Dynamic memory consumption is heavily dependent on the actual code being executed which is dependent on the state of the software and the parameters. With the introduction of recursive concepts the uncertainty is even higher. Therefore the approach for dynamic memory consumption is far more related to the description of the execution time introduced in chapter 8.5. 8.4.2 Stack The stack is an area in memory that is used to store temporary information like parameters and local variables of function calls. Therefore the stack usage is highly dependent on the calling hierarchy and the nesting level of function calls. The stack is organized in a LIFO (last in first out) manner. So each time a function is called the necessary stack memory is occupied. After leaving the function also the associated memory area is freed again and can be used for the next function call. Among tasks, that do not interrupt each other, fragmentation is not a problem for a stack. Only the available amount of stack memory is relevant from the software point of view. However, there can be several stacks in a concurrent task environment. Note that it is not in the scope of a module or component to define the number of stacks, only the amount of used stack memory can be given. Different mechanisms can be used to describe the stack memory needs of software. Needed stack size can either be calculated, measured or estimated. This is shown in Figure 8.
