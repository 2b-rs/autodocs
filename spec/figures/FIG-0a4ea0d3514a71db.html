1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Protokoll-Wire-Format / Bit-Level PDU-Layout (32-Bit-Rasterdarstellung).
  • Technischer Zweck: Normative Definition der On-the-Wire-Serialisierung des SOME/IP-Nachrichtenheaders (16 Bytes / 128 Bits Basis-Header) über transportierende Protokolle (UDP/TCP, IPv4/IPv6).
  • Architektonische Einordnung:
    • AUTOSAR Classic Platform (CP): Schnittstelle zwischen RTE/Transformer-Kette (SomeIpXf, optional vorgeschaltet E2EXf) und der Kommunikationsinfrastruktur via PDU-Router (PduR) an den Socket-Adapter (SoAd).
    • AUTOSAR Adaptive Platform (AP): Protokoll-Binding-Schicht der Kommunikations-Middleware (ara::com / SOME/IP-Daemon / Binding) zur serviceorientierten Inter-ECU-Kommunikation.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in ein 32-Bit-Wort-Raster (Offsets 0 bis 31):

  • Message ID [32 Bit] (Offset 0x00–0x03):
    • Service ID [Bits 0–15]: Eindeutige Kennung des angebotenen Services.
    • Method ID / Event ID [Bits 16–31]: Kennung der Operation/des Events; Bit 16 (MSB dieses Subfelds) dient als Diskriminator (0 = Method ID, 1 = Event ID).
  • Length [32 Bit] (Offset 0x04–0x07):
    • Gibt die Bytezahl der Nachricht an, beginnend nach dem Length-Feld bis zum Ende der gesamten PDU (inklusive verbleibender 8 Header-Bytes: Request ID bis Return Code + Payload).
  • Request ID [32 Bit] (Offset 0x08–0x0B):
    • Client ID [Bits 0–15]: Eindeutige ID des aufrufenden Clients/ECU-Endpunkts.
    • Session ID [Bits 16–31]: Sequenzzähler zur Korrelation von Request/Response bzw. Erkennung von Duplikaten/Paketverlusten.
  • Header-Steuerfelder [jeweils 8 Bit] (Offset 0x0C–0x0F):
    • Protocol Version [8 Bit, Offset 0x0C]: Version des SOME/IP-Protokolls (normativ 0x01).
    • Interface Version [8 Bit, Offset 0x0D]: Major-Version des Service-Interfaces (Schnittstellenkompatibilität).
    • Message Type [8 Bit, Offset 0x0E]: Typ der PDU (z. B. 0x00 REQUEST, 0x01 REQUEST_NO_RETURN, 0x02 NOTIFICATION, 0x80 RESPONSE, 0x81 ERROR; Bit 5 markiert TP-Segmentierung).
    • Return Code [8 Bit, Offset 0x0F]: Status der Operationsabarbeitung (0x00 E_OK, 0x01 E_NOT_OK, 0x02 E_UNKNOWN_SERVICE, etc.).
  • Payload [variable size] (ab Offset 0x10):
    • Serialisierte Methodenargumente, Eventdaten oder Fehlerinformationen.
  • Strukturelle Klammern (Scopes):
    • SOME/IP Header: Umfasst exakt die ersten 16 Bytes (128 Bits) bis einschließlich Return Code.
    • Covered by Length: Umfasst semantisch Request ID (4 Bytes) + Steuerfelder (4 Bytes) + Payload (N Bytes), formal: Length = N + 8.

3. Dynamisches Verhalten & Sequenzablauf

  1. PDU-Assemblierung (Sender-Pfad):
    • Der Sender (SomeIpXf bzw. ara::com) serialisiert Datenargumente in den Payload-Puffer.
    • Der Header wird erzeugt: Message ID und Interface Version werden aus der Service-Konfiguration abgeleitet; Session ID wird inkrementiert (bei Request/Response mandatorisch, bei Events optional); Length wird auf sizeof(Payload) + 8 gesetzt.
    • Übergabe als PDU an SoAd zur Socket-Übertragung (UDP/TCP).
  2. PDU-Dissecting & Validierung (Empfänger-Pfad):
    • Stufe 1 (Header-Plausibilisierung): Prüfung, ob empfangene PDU ≥ 16 Byte ist. Validierung Protocol Version == 0x01. Bei Diskrepanz: Verwerfen der PDU und Det-Meldung (SOMEIPXF_E_WRONG_PROTOCOL_VERSION).
    • Stufe 2 (Längen-Verifikation): Abgleich der tatsächlich empfangenen PDU-Länge mit dem Header-Feld Length. Ist PduInfoPtr->SduLength < Length + 8, wird die PDU als malformed verworfen.
    • Stufe 3 (Dispatching): Lookup von Service ID / Method ID. Ist der Service unbekannt, sendet der Stack autonom eine Response mit Message Type = 0x81 (ERROR) und Return Code = 0x02 (E_UNKNOWN_SERVICE).
    • Stufe 4 (Korrelation): Bei RESPONSE ordnet der Client die eingehende Antwort anhand von Client ID und Session ID dem wartenden Aufrufkontext zu.

4. Normative Relevanz & Entwickler-Hinweise

  • Endianness-Invariante: Alle Header-Felder müssen ausnahmslos in Network Byte Order (Big-Endian) serialisiert werden (PRS_SOMEIP_00030), unabhängig von der Endianness der Host-CPU (Little-Endian MCUs erfordern Byte-Swapping via Intrinsic/Driver-Optimierung).
  • Längenberechnungs-Falle: Length darf niemals auf die Gesamt-PDU-Länge gesetzt werden. Eine fehlerhafte Berechnung (+16 statt +8) führt serverseitig zu Buffer-Overread-Fehlern oder PDU-Verwurf.
  • E2E-Schutzplatzierung (PRS_SOMEIP_00941):
    • Wird E2E-Absicherung verwendet, liegt der E2E-Header standardmäßig bei einem Offset von 64 Bits (8 Bytes) relativ zum Ende des Feldes Length.
    • Dies platziert den E2E-Header exakt ab Offset 16 (zwischen Return Code und Nutzdaten-Payload). Der E2E-Header zählt datentechnisch zur Payload und ist somit vollständig in Length eingerechnet.
  • TP (SOME/IP-Transport Protocol):
    • Überschreitet die PDU die MTU (vor allem bei UDP), wird Bit 5 im Message Type gesetzt.
    • Achtung: In diesem Fall fügt der Stack unmittelbar nach Return Code (vor der Payload bzw. dem E2E-Header) ein zusätzliches 4-Byte SOME/IP-TP Header-Feld ein (Offset, More-Segments-Flag). Der Basis-Header bleibt in seiner 16-Byte-Struktur unverändert.
  • Zero-Copy-Optimierung: Aufgrund der 32-Bit-Ausrichtung jedes Headerfelds können Treiber-Stacks (EthIf, SoAd) Puffer direkt über 32-Bit-Zeigerstrukturen mappen, ohne Alignment-Faults zu provozieren.
