1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturschaubild / Schichten- und Deployment-Modell (Software Cluster & Cross-Partition Deployment Overview).
  • Technischer Zweck: Das Diagramm spezifiziert die Entkopplung von Nutzern des Large Data COM (LdCom)-Moduls (RTE, Applikations-SWCs, Serialisierungs-/E2E-Transformer) über Cluster-Grenzen (Applicative SW Cluster vs. Host SW Cluster) und Speicherschutz-/Kern-Partitionsgrenzen (EcucPartition X vs. EcucPartition Y) hinweg.
  • Funktionale Einordnung: Mit der Einführung von Software-Clustern (SWCL) in AUTOSAR CP (ab R22-11) ermöglicht dieses High-Proxy/Low-Proxy-Design in Verbindung mit binären Manifesten die asynchrone oder synchrone PDU-Weiterleitung an eine zentralisierte BSW-Instanz (LdCom auf EcucPartition Y), ohne dass der anwendende Cluster hardcodierte Adressen oder Bindungen an die Ziel-Partition besitzen muss.

2. Komponenten, Entitäten & Schnittstellen

  • Cluster-Ebenen:
    • Applicative SW Cluster: Eigenständig kompilierbare und separat ladbare Anwendungs-Software-Cluster (oberer Bereich), instanziiert über EcucPartition X und EcucPartition Y.
    • Host SW Cluster: Plattform-Basissoftware-Cluster (unterer Bereich), der die BSW-Treiber, das OS und die zentrale Kommunikationsschicht bereitstellt.
  • Partitions-Domänen:
    • EcucPartition X: LdCom-externe Client-Partition (weder LdCom noch dessen direkte BSW-Ausführungsumgebung laufen hier).
    • EcucPartition Y: LdCom-Host-Partition, auf der das BSW-Modul LdCom allokiert und ausgeführt wird.
  • Architektur-Entitäten & Proxies:
    • Application Software Component (SWC) & RTE: Anwendungssoftware gekoppelt über standardisierte AUTOSAR Interfaces an die lokale Runtime Environment.
    • Transformer-Kette: SOME/IP Transformer, ComBased Transformer, E2E Transformer zur PDU-Serialisierung, Signal-Transformation und E2E-Absicherung. Vorhanden sowohl im Applicative SW Cluster als auch im Host SW Cluster.
    • LdCom High Proxy: Im Applicative SW Cluster verortete Abstraktionsschicht, die Aufrufe der RTE/Transformer kapselt und über das lokale Binary Manifest exportiert.
    • Binary Manifest: Adress- und Funktionszeiger-Tabelle (Symbolauflösung zur Lade-/Link-Zeit zwischen Clustern), die die Schnittstellen zwischen Applicative SW Cluster und Host SW Cluster herstellt.
    • LdCom Low Proxy: Im Host SW Cluster verankerte Proxy-Schicht. Sie überspannt beide Partitionen (X und Y) und enthält:
      • LowProxy_Y: Partitionslokaler Dispatcher/Router auf der Ziel-Partition Y, der eingehende PDU-Übertragungsanfragen entgegennimmt und an LdCom übergibt.
      • LowProxy_<Cbk>_Y: Callback-Proxy-Entität auf Partition Y zur Entgegennahme von Modul-Callbacks (<Cbk>) aus LdCom.
    • LdCom (BSW-Modul): Physische Modul-Instanz der Large Data COM im Communication Layer von EcucPartition Y.

3. Dynamisches Verhalten & Sequenzablauf

  1. Cross-Cluster / Cross-Partition Tx-Pfad (Partition X Applicative → Partition Y Host):
    • Schritt 1 (SWC/RTE): SWC in Partition X generiert Daten; Transformer transformieren Payload.
    • Schritt 2 (High Proxy): LdCom High Proxy auf Partition X nimmt die PDU entgegen und routet den Call über das Binary Manifest nach unten in den Host SW Cluster.
    • Schritt 3 (Cross-Partition Transit): Der Low Proxy im Host SW Cluster transportiert die Anfrage über die Partitionsgrenze von X nach Y (gelber Pfad).
    • Schritt 4 (Low Proxy Forwarding): LowProxy_Y empfängt die Anfrage im Kontext von Partition Y und leitet sie per nativer BSW-API (LdCom_Transmit()) an das Modul LdCom weiter.
  2. Cluster-übergreifender, partitionsinterner Tx-Pfad (Partition Y Applicative → Partition Y Host):
    • Verläuft vertikal (hellbraune/orange Pfeile) via LdCom High Proxy → Binary Manifest → LowProxy_Y → LdCom ohne Inter-Partition-Crossing.
  3. Rx- / Tx-Confirmation / Copy-Callback-Pfad (<Cbk>):
    • LdCom triggert Callback-Schnittstellen (<User>_TxConfirmation, <User>_RxIndication, CopyTxData, etc.) an LowProxy_<Cbk>_Y.
    • LowProxy_<Cbk>_Y routet die Callbacks zurück:
      • Partitionslokal nach oben zum LdCom High Proxy in Partition Y.
      • Partitionsübergreifend zurück über das Binary Manifest zum LdCom High Proxy in Partition X.
      • Bei Bedarf über die RTE des Host SW Clusters an lokale Empfänger (oranger Rückführungspfad).

4. Normative Relevanz & Entwickler-Hinweise

  • Binary Manifest ABI-Vertrag:
    • Das Binary Manifest fungiert als strikte Entkopplungsschnittstelle. Entwickler von Applikations-Clustern müssen sicherstellen, dass LdCom-API-Signaturen und Datenstrukturen exakt mit den Manifest-Einträgen des Host-Clusters übereinstimmen; Re-Linking des Host-Stacks bei SWCL-Updates entfällt.
  • ECUC-Partitioning & Inter-OS-Application-Kommunikation:
    • Da LdCom exklusiv in EcucPartition Y instanziiert ist, muss der Low-Proxy-Mechanismus für Aufrufer aus EcucPartition X Cross-Core-/Cross-Partition-Mechanismen (z. B. OS-IOC, Trusted Functions oder Non-Blocking Ringpuffer) nutzen.
    • Speicherschutzgrenzen (MPU/MMU) werden durch den Low Proxy gewahrt; PDU-Zeiger dürfen nicht ohne Validierung bzw. Kopierschutz über unprivilegierte Partitionsgrenzen übergeben werden.
  • PDU-Größen & Zero-Copy-Restriktionen:
    • Bei Large-Data-Übertragungen (typischerweise Payload > CAN-FD-Frame-Größe, z. B. Ethernet/SOME/IP) führen Cross-Partition-Aufrufe bei unbedachter Konfiguration zu hohem Kopier-Overhead. Die Pufferallokation (LdComTxBuffer, LdComRxBuffer) muss performant im Shared Memory oder über spezialisierte Inter-Partition-Mechanismen projektiert werden.
