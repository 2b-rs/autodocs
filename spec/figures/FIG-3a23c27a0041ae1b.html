1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Metamodell-Ausschnitt (UML2-Klassendiagramm / MSR-Klassendiagramm).
  • Kontext: AUTOSAR_FO_TPS_SecurityExtractTemplate (Foundation, Release R23-11), Metamodell für den Security Extract (SECXT).
  • Technischer Zweck: Modellierung der kryptografischen Signaturunterstützung für eine Instanz des Intrusion Detection System Managers (IdsmInstance). Es definiert die plattformspezifische Bindung zur Absicherung von Sicherheitsereignis-Nachrichten (Qualified Security Events – QSEv) gegen Manipulation und zur Authentizitätsprüfung auf der Classic Platform (CP) und der Adaptive Platform (AP).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen und Attribute
  • IdsmInstance (Generalisierung: IdsCommonElement):
    • Repräsentiert die logische Instanz des Intrusion Detection System Managers.
    • idsmInstanceId: PositiveInteger [0..1]: Eindeutige Kennung der IdsM-Instanz.
    • timestampFormat: String [0..1]: Formatdefinition für Zeitstempel in gemeldeten Sicherheitsereignissen.
  • IdsmSignatureSupportCp:
    • CP-spezifische Signaturkonfiguration.
    • Komposition von IdsmInstance über die Rolle +signatureSupportCp mit Multiplizität [0..1], ausgezeichnet mit dem Stereotyp «atpSplitable» (Erlaubt die Definition über verteilte ARXML-Dateien hinweg).
  • SecureCommunication::CryptoServicePrimitive (Stereotypen: ARElement, UploadableDesignElement):
    • Assoziiert von IdsmSignatureSupportCp über +authentication [0..1].
    • Konfiguriert das kryptografische Primitiv des Classic-Crypto-Stacks (CSM).
    • Attribute:
      • algorithmFamily: String [0..1] (z. B. RSA, ED25519, AES).
      • algorithmMode: String [0..1] (z. B. CMAC, HMAC, PKCS1_V1_5).
      • algorithmSecondaryFamily: String [0..1] (z. B. Hashfunktion wie SHA2_256).
  • SecureCommunication::CryptoServiceKey (Stereotypen: ARElement, UploadableDesignElement):
    • Assoziiert von IdsmSignatureSupportCp über +cryptoServiceKey [0..1].
    • Repräsentiert den kryptografischen Schlüssel im CP-Katalog.
    • Attribute:
      • algorithmFamily: String [0..1].
      • keyGeneration: CryptoServiceKeyGenerationEnum [0..1].
      • keyStorageType: String [0..1].
      • length: PositiveInteger [0..1] (Schlüssellänge in Bit).
  • IdsmSignatureSupportAp:
    • AP-spezifische Signaturkonfiguration.
    • Komposition von IdsmInstance über die Rolle +signatureSupportAp mit Multiplizität [0..1], ausgezeichnet mit «atpSplitable».
    • Attribut:
      • cryptoPrimitive: String: Textuelle Spezifikation des Algorithmus für ara::crypto.
  • CryptoDeployment::CryptoKeySlot (Generalisierung: Identifiable):
    • Assoziiert von IdsmSignatureSupportAp über +keySlot [0..1].
    • Bindeglied zur Schlüsselverwaltung der Adaptive Platform.
    • Attribute:
      • allocateShadowCopy: Boolean [0..1].
      • cryptoAlgId: String [0..1].
      • cryptoObjectType: CryptoObjectTypeEnum [0..1].
      • slotCapacity: PositiveInteger [0..1].
      • slotType: CryptoKeySlotTypeEnum [0..1].

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um eine statische Metamodell-Definition für den Security Extract handelt, ist kein explizites Sequenzdiagramm dargestellt. Das abgeleitete Laufzeitverhalten teilt sich plattformabhängig wie folgt auf:

  1. Ereignis-Erzeugung & Pufferung: Die IdsmInstance aggregiert Sicherheitsereignisse (QSEv) in internen Puffern.
  2. Kryptografische Signierung vor Export:
    • Pfad Classic Platform (IdsmSignatureSupportCp):
      • IdsM ruft den Crypto Service Manager (CSM) über standardisierte C-APIs auf (Csm_SignatureGenerate bzw. Csm_MacGenerate).
      • Der CSM instanziiert den Job über das referenzierte CryptoServicePrimitive und adressiert den CryptoServiceKey über CryIf/Crypto Driver.
      • Ergebnisbehandlung erfolgt synchron oder asynchron via Callback.
    • Pfad Adaptive Platform (IdsmSignatureSupportAp):
      • IdsM öffnet über die Schnittstelle ara::crypto::keys den über keySlot zugeordneten Schlüssel.
      • Initialisierung des Signer-Contexts (ara::crypto::cryp::SignerPrivateCtx) gemäß dem String cryptoPrimitive.
      • Asynchrone oder synchrone Ausführung der Signatur über die serialisierte Nachricht; Anhängen des Signaturwerts an die ausgehende Protokollnachricht.
  3. Fehlerbehandlung:
    • CP: Bei kryptografischen Fehlern (Key ungültig, HW-Fehler) Absetzen von Det-Fehlern oder Dem-Events; Verwerfen des Events gemäß IdsM-Sicherheitsrichtlinie.
    • AP: Fehlerübermittlung über ara::core::Result bzw. ara::core::ErrorCode; System-Logging über ara::log.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Referenzen:
    • RS_SECXT_00016: Anforderung zur Unterstützung von Signaturen für Sicherheitsmeldungen des IdsM.
    • TPS_SECXT_01032: Spezifikationsvorgabe zur Signatur-Modellierung auf der Classic Platform über CSM-Elemente (CryptoServicePrimitive, CryptoServiceKey).
    • TPS_SECXT_01033: Spezifikationsvorgabe zur Signatur-Modellierung auf der Adaptive Platform über ara::crypto-Deployment-Strukturen (CryptoKeySlot, cryptoPrimitive).
  • Multi-Platform Split («atpSplitable»):
    • Entwickler von Autorensystemen müssen beachten, dass signatureSupportCp und signatureSupportAp getrennt vom Rumpf der IdsmInstance in separaten ARXML-Dateien abgelegt werden können (z. B. plattformübergreifendes Kern-Modell vs. plattformspezifisches Crypto-Deployment).
  • Konfigurations- und Integrationspflichten:
    • Classic Stack: Der Generator muss sicherstellen, dass die im SECXT definierten CryptoServicePrimitive und CryptoServiceKey kongruent auf die BSW-Konfiguration von CSM (CsmPrimitives, CsmKeys) und CryIf abgebildet werden.
    • Adaptive Stack: Der Manifest-Generator für AP muss sicherstellen, dass der referenzierte CryptoKeySlot im Execution Manifest bzw. Crypto Deployment Manifest der entsprechenden Machine existiert und die Zugriffsrechte (ara::crypto Access Control List / Manifest-Berechtigung) für den IdsM-Prozess freigegeben sind.
