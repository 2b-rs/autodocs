1. Diagrammtyp & Architektur-Kontext

Paketstruktur- und Protokoll-Formatdiagramm (Bit-Offset-Darstellung von 0 bis 31 Bit pro Zeile). Es spezifiziert die Serialisierungsstruktur einer SOME/IP-Service-Discovery-Nachricht (SOME/IP-SD), eingebettet in ein standardkonformes SOME/IP-Nachrichtenformat. Der Kontext umfasst die fahrzeuginterne Ethernet-Kommunikation in AUTOSAR-Systemen zur dynamischen Dienstsuche (FindService), Dienstveröffentlichung (OfferService) und Ereignis-Abonnementverwaltung (SubscribeEventgroup).

2. Komponenten, Entitäten & Schnittstellen

Das Format gliedert sich in zwei vertikale Hauptbereiche:

  • SOME/IP-Header (16 Byte):
    • Message ID (Service ID / Method ID) [32 Bit]: Belegt mit dem fixen Wert 0xFFFF 8100 zur eindeutigen Kennzeichnung von Service Discovery Nachrichten.
    • Length [32 Bit]: Gesamtlänge der Nachricht ab dem Byte nach dem Längenfeld (umfasst Request ID, Standard-Header-Felder und die gesamte SOME/IP-SD-Payload).
    • Request ID (Client ID / Session ID) [32 Bit]: Zur Identifikation von Anfrager und Sitzung.
    • Protocol Version [8 Bit]: Fester Wert = 0x01.
    • Interface Version [8 Bit]: Fester Wert = 0x01.
    • Message Type [8 Bit]: Fester Wert = 0x02 (Notification).
    • Return Code [8 Bit]: Fester Wert = 0x00 (E_OK).
  • SOME/IP-SD Payload:
    • Flags [8 Bit]: Steuerflags für das Service Discovery.
    • Reserved [24 Bit]: Reserviertes Feld zur Wortausrichtung.
    • Length of Entries Array [32 Bit]: Länge des folgenden Eintrags-Arrays in Byte.
    • Entries Array [variable Länge]: Enthält die eigentlichen SD-Einträge (z. B. FindService-, OfferService- oder Subscribe-Einträge); die Gesamtlänge ist durch das Feld Length of Entries Array abgedeckt („Covered by Length“).
    • Length of Options Array [32 Bit]: Länge des folgenden Options-Arrays in Byte.
    • Options Array [variable Länge]: Enthält zugehörige Optionen (z. B. IPv4/IPv6-Endpunktoptionen); die Gesamtlänge ist durch das Feld Length of Options Array abgedeckt („Covered by Length“).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt ein statisches Daten- und Serialisierungsformat ohne Zeit- oder Zustandsübergänge. Die Übertragung erfolgt typischerweise zyklisch oder ereignisgesteuert via UDP über den fahrzeuginternen Ethernet-Stack. Ein SD-Teilnehmer (Client oder Server) stellt die SD-Einträge zusammen, berechnet deren Länge (Length of Entries Array), fügt referenzierte Optionen im Options Array hinzu, trägt dessen Länge (Length of Options Array) ein, setzt die SD-Flags sowie die fixen SOME/IP-Header-Werte und berechnet das SOME/IP-Feld Length, welches die gesamte nachfolgende Nachricht bis zum Ende des Options Array umfasst. Der Empfänger parst sequenziell anhand der Offset- und Längenfelder.

4. Normative Relevanz & Entwickler-Hinweise

Das Diagramm definiert das zwingend einzuhaltende Serialisierungsformat für SOME/IP-SD-Nachrichten im Netzwerk. Zu beachten für Protokollstapel-Implementierer:

  • Byte-Reihenfolge: Gemäß SOME/IP-Spezifikation gilt Big-Endian (Network Byte Order) für alle Header-Felder.
  • Identifikation: Eine SOME/IP-SD-Nachricht muss zwingend mit Message ID = 0xFFFF8100, Message Type = 0x02 und Return Code = 0x00 übertragen werden; abweichende Werte führen zum Verwerfen oder fehlerhafter Interpretation.
  • Längenberechnung: Das Feld Length im SOME/IP-Header umfasst 8 Byte (Request ID bis Return Code) plus die Größe der gesamten SD-Payload (Flags/Reserved + Length of Entries Array + Entries Array + Length of Options Array + Options Array).
  • Konsistenz: Entries Array und Options Array müssen exakt mit den in Length of Entries Array bzw. Length of Options Array angegebenen Bytezahlen übereinstimmen. In den Optionen referenzierte Indizes aus den Entries müssen innerhalb des deklarierten Options-Arrays liegen.
