1. Diagrammtyp & Architektur-Kontext

Protokoll- und Paketlayout-Diagramm zur Spezifikation des SOME/IP-Headers (Scalable service-Oriented MiddlewarE over IP). Im Kontext von AUTOSAR Classic und Adaptive Platform stellt das Schaubild die konkrete Belegung der SOME/IP Magic Cookie Message für die Übertragungsrichtung Server zu Client dar, welche als standardisierter Heartbeat bzw. Synchronisations- und Keep-Alive-Mechanismus auf Transportprotokollebene (typischerweise über TCP/UDP) fungiert.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm spezifiziert ein 32-Bit breites SOME/IP-Header-Layout ohne Payload mit folgenden Feldern und festen Werten:

  • Bit-Offset-Leiste: 0 bis 31 Bit zur Kennzeichnung der Wortbreite.
  • Message ID (Service ID / Method ID) [32 bit]: Gesamtwert 0xFFFF 8000, aufgeteilt in Service ID 0xFFFF (Bit 0–15) und Method ID 0x8000 (Bit 16–31).
  • Length [32 bit]: Wert 0x0000 0008 (8 Bytes), welcher die ab dem Request-ID-Feld folgenden Header-Bytes quantifiziert.
  • Request ID (Client ID / Session ID) [32 bit]: Zusammengesetzter Wert 0xDEAD BEEF, bestehend aus Client ID 0xDEAD (Bit 0–15) und Session ID 0xBEEF (Bit 16–31).
  • Protocol Version [8 bit]: Wert 0x01 (Bit 0–7).
  • Interface Version [8 bit]: Wert 0x01 (Bit 8–15).
  • Message Type [8 bit]: Hervorgehobener Wert =0x02 (Bit 16–23, Kennzeichnung als Response/Server-to-Client).
  • Return Code [8 bit]: Wert 0x00 (Bit 24–31, E_OK).
  • Covered by Length: Vertikale Bemaßungsanzeige, die explizit die Felder Request ID, Protocol Version, Interface Version, Message Type und Return Code (insgesamt 8 Bytes) umfasst. Payload ist keine vorhanden.

3. Dynamisches Verhalten & Sequenzablauf

Dargestellt ist die statische Protokollstruktur einer Magic Cookie Nachricht in Richtung Server -> Client:

  1. Der Server sendet ein unsegmentiertes SOME/IP-Paket zur Überprüfung der Verbindung bzw. als Synchronisationssignal an den Client.
  2. Das Paket verwendet den Message Type 0x02 (Response), korrespondierend zur Method ID 0x8000.
  3. Die Session- und Client-Bezeichner (0xDEAD BEEF) identifizieren die Nachricht fest als Magic Cookie.
  4. Es folgt keine Nutzlastdatenphase; nach dem Return Code endet das Paket bei Byte-Offset 16 (Bit-Länge 128).

4. Normative Relevanz & Entwickler-Hinweise

Für Implementierer von SOME/IP-Stacks gelten folgende Vorgaben:

  • Längenberechnung: Das Feld Length deckt gemäß Bemaßung exakt die verbleibenden 8 Bytes des SOME/IP-Headers ab (Request ID bis Return Code); die Message ID und das Length-Feld selbst zählen nicht in die Längenangabe hinein.
  • Filterung & Validierung: Server-to-Client Magic Cookies müssen strikt auf Message Type 0x02, Method ID 0x8000 und Service ID 0xFFFF validiert werden.
  • Endianness: Alle Multi-Byte-Felder (Message ID, Length, Request ID) unterliegen der SOME/IP-Netzwerk-Byte-Reihenfolge (Big-Endian / Network Byte Order).
  • Header-Vollständigkeit: Da keine Payload angehängt ist (Length = 8), muss der Parser nach exakt 16 Gesamtbytes die Nachricht erfolgreich abschließen und darf keine weiteren Daten für dieses Paket erwarten.
