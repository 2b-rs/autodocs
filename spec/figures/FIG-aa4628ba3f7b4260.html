1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Gantt-basiertes Zeitablauf- und Trace-Diagramm (Scheduling Trace) gemäß AUTOSAR Foundation Technical Report Timing Analysis (AUTOSAR_FO_TR_TimingAnalysis, Kap. 9 Timing Parameters).
  • Technischer Zweck: Formale Definition und visuelle Abgrenzung normativer Zeitmetriken (Execution Times, Latencies, Slack Times, Periods) einer Task-Instanz (Task B) unter verdrängendem Festprioritäten-Scheduling (Fixed-Priority Preemptive Scheduling) im AUTOSAR/OSEK-OS. Dient als Referenzmodell für die Worst-Case Response Time Analysis (RTA) sowie für das Run-Time Tracing (ARTI/ORTI).

2. Komponenten, Entitäten & Schnittstellen

  • Scheduling-Akteure & Prioritätenordnung:
    • Task A: Höchste Priorität (prio_TaskA > prio_TaskB). Verdrängt Task B.
    • Task B: Mittlere Priorität; dediziertes Analyseobjekt aller annotierten Metriken.
    • Task C: Niedrigste Priorität (prio_TaskB > prio_TaskC). Erhält CPU-Zeit nur bei Untätigkeit oder Blockade von A und B.
  • Zustandsrepräsentationen (Trace-Balken):
    • Hellgrau: Zustand READY (aktiviert/lauffähig, aber wartend auf Zuteilung) bzw. PREEMPTED.
    • Dunkelgrau: Zustand RUNNING (aktive Instruktionsausführung auf dem CPU-Core).
    • Ocker/Gold (in Task B): Zustand WAITING / BLOCKED (Freigabe des Cores durch Ressourcensperre, Spinlock oder WaitEvent() bei Extended Tasks).
  • Annotierte Timing-Parameter (Metriken bezüglich Task B):
    • IPT (Initial Pending Time): Latenz von der Task-Aktivierung (Activation/Release) bis zum ersten Ausführungsstart auf der CPU.
    • CET1, CET2, CET3 (Core Execution Times): Disjunkte Abschnitte der tatsächlichen Netto-Rechenzeit auf dem Core (CET = CET_1 + CET_2 + CET_3).
    • PRE (Preemption Time): Zeitspanne, in der Task B durch den höherprioren Task A verdrängt wird.
    • GET (Gross Execution Time): Brutto-Ausführungszeit ab erstem Dispatch (CET_1) bis zur finalen Terminierung (CET_3), inklusive PRE und Blockadephasen.
    • RT (Response Time): Gesamte System-Antwortzeit ab Aktivierung bis zur Terminierung (RT = IPT + GET).
    • DL (Deadline): Konfigurierte relative Frist/Zeitschranke, gerechnet ab Aktivierungszeitpunkt (RT ≤ DL).
    • PER (Period): Zykluszeit zwischen zwei aufeinanderfolgenden Aktivierungs-Triggern von Task B.
    • DT (Distance Time / Inter-Start Time): Zeitintervall zwischen dem ersten Rechenbeginn (CET_1) zweier konsekutiver Task-Instanzen.
    • ST (Slack Time / Gross Slack Time): Brutto-Restzeitspanne von der Beendigung von Task B bis zu dessen nächster periodischer Aktivierung (ST = PER - RT).
    • NST1, NST2 (Net Slack Time): Tatsächliche CPU-Restzeit/Reserve innerhalb der Slack Time abzüglich der Interferenz durch höherpriore Last (Task A): NST = NST_1 + NST_2.

3. Dynamisches Verhalten & Sequenzablauf

  1. Aktivierung (t_0): Task B wird aktiviert (via OS-Alarm, Cycle-Timer oder RTE-Event) und geht in den Zustand READY. Phase IPT läuft.
  2. Dispatch & Start (CET_1): Der Dispatcher weist Task B die CPU zu. Task B wechselt nach RUNNING und führt CET_1 aus.
  3. Preemption (PRE): Task A wird getriggert. Aufgrund höherer Priorität verdrängt Task A Task B. Task B wechselt zurück nach READY.
  4. Resumption (CET_2): Nach Terminierung von Task A wechselt Task B wieder nach RUNNING und führt CET_2 aus.
  5. Blockade / Wartezustand (Goldener Block): Task B blockiert (z. B. Aufruf von WaitEvent(), Warten auf Shared Resource). Task B wechselt in den Zustand WAITING.
  6. Ausführung von Task C: Da Core frei, schaltet der Scheduler auf den niederprioren Task C (RUNNING).
  7. Reaktivierung & Verdrängung von C (CET_3): Das erwartete Event für Task B tritt ein. Task B wird sofort wieder READY, verdrängt Task C (welcher in READY geht) und beendet seine Berechnungen in CET_3.
  8. Terminierung & Slack Time (ST): Task B ruft TerminateTask() auf. Die Antwortzeit RT endet vor Erreichen der Deadline DL (Deadline Met). Der Zeitraum bis zur nächsten Periode ist die Slack Time ST.
  9. Slack-Fragmentierung (NST): Während der Slack Time läuft Task C weiter, wird aber erneut von Task A unterbrochen. Dadurch fragmentiert die Brutto-Slack-Time ST in die Netto-Pufferzeiten NST1 und NST2.
  10. Folgezyklus: Nach Ablauf von PER erfolgt der nächste Release von Task B; nach Ablauf von DT startet die nächste Ausführung.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfiguration im AUTOSAR OS & Timing Extensions (TIMEX):
    • In AUTOSAR-Modellen (ARXML) werden diese Parameter über ExecutionOrderConstraint, LatencyTimingConstraint und EventTriggeringConstraint formal spezifiziert.
    • Das Vorhandensein des Blockade-Zustands klassifiziert Task B architektonisch zwingend als Extended Task (OsTaskType = EXTENDED), da Basic Tasks nicht in den Zustand WAITING gehen dürfen (WaitEvent() nicht zulässig).
  • Echtzeit-Sicherheitsnachweis (ISO 26262 & WCET-Analyse):
    • Für ASIL-relevante Funktionen muss analytisch und messtechnisch nachgewiesen werden: $$\text{WCRT} = \max(IPT) + \max(CET) + \max(PRE) + \max(BT) \le DL \le PER$$
    • Jitter-Berechnungen: Der Aktivierungsjitter ergibt sich aus der Varianz von IPT, der Start-zu-Start-Jitter aus der Varianz von DT.
  • Debugging & Tracing (ARTI / ORTI):
    • Profiling-Tools (Trace32, Vector CANoe.AMD, iSYSTEM) nutzen genau diese Tracing-Hooks. Entwickler müssen bei der CPU-Load-Kalkulation beachten: Die Kernauslastung durch Task B berechnet sich strikt über $\frac{CET}{PER}$, während Integratoren zur Schedule-Validierung das Budget über $\frac{GET}{PER}$ bzw. die verbleibende Reserve NST heranziehen müssen.
