1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Layout / Protokoll-Header-Bitfeld-Spezifikation (32-Bit Big-Endian / Network Byte Order Raster).
  • Technischer Zweck: Definition der On-the-Wire-Serialisierung eines segmentierten SOME/IP-Datenpakets unter Verwendung des SOME/IP Transport Protocols (SOME/IP-TP) zur Übertragung von Payloads, die die MTU des Transportkanals (typischerweise UDP über Ethernet, MTU ≤ 1500 Bytes) überschreiten.
  • Architektur-Einordnung:
  • Eingebettet im AUTOSAR Classic BSW-Stack als Modul SomeIpTp zwischen PduR (oberhalb) und SoAd / Socket Adapter (unterhalb).
  • In AUTOSAR Adaptive als TP-Mechanismus innerhalb des Kommunikations-Subsystems (ara::com / SOME/IP-Binding).
  • Ergänzt den 16-Byte SOME/IP-Standard-Header um einen 4-Byte SOME/IP-TP-Zusatz-Header, der unmittelbar vor der Nutzlast platziert wird.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm schlüsselt die 32-Bit-Wortgrenzen (Bit 0 bis 31) der PDU auf:

#### A. Standard SOME/IP-Header (Bytes 0 bis 15)

  • Message ID [32 Bit] (0x01010009):
  • Service ID [Bit 0–15]: 0x0101
  • Method ID [Bit 16–31]: 0x0009 (Bit 16 = 0 kennzeichnet eine Methode; 1 kennzeichnet ein Event).
  • Length [32 Bit] (Wert: 1404 / 0x0000057C):
  • Spezifiziert die Bytezahl ab dem Request-ID-Feld bis zum Ende des aktuellen Segments.
  • Berechnung: $8\,\text{Byte (SOME/IP-Restheader)} + 4\,\text{Byte (TP-Header)} + 1392\,\text{Byte (Payload)} = 1404\,\text{Bytes}$.
  • Request ID [32 Bit] (0x00010005):
  • Client ID [Bit 0–15]: 0x0001
  • Session ID [Bit 16–31]: 0x0005 (bleibt für alle Segmente derselben Gesamtnachricht zwingend identisch).
  • Protocol Version [8 Bit]: 0x01.
  • Interface Version [8 Bit]: 0x01.
  • Message Type [8 Bit] (0x20 / b00100000):
  • Bit 5 (Wertigkeit 0x20) ist das normative TP-Flag; 1 signalisiert das Vorhandensein des TP-Headers.
  • Bits 0–3 (0x00): Basistyp REQUEST. Ergibt in Kombination REQUEST_WITH_TP (0x20).
  • Return Code [8 Bit]: 0x00 (E_OK).

#### B. SOME/IP-TP-Zusatz-Header (Bytes 16 bis 19, hervorgehoben)

  • Offset [28 Bit] (Bit 0 bis 27):
  • Startposition des Segment-Payloads in der Gesamt-PDU in Einheiten von 16 Bytes ($\text{Byte-Offset} = \text{Offset-Feld} \times 16$). Im gezeigten ersten Segment: Wert 0.
  • RES (Reserved) [3 Bit] (Bit 28 bis 30):
  • Reservierte Bits, normativ zwingend mit 000 zu belegen.
  • M (More Segments Flag) [1 Bit] (Bit 31):
  • 1: Weitere Segmente folgen.
  • 0: Letztes Segment der Gesamtnachricht.

#### C. Payload (ab Byte 20)

  • Payload-Daten: 1392 Bytes im gezeigten Beispiel ($1392 / 16 = 87$ Blöcke, exaktes 16-Byte-Alignment).
  • Gesamtlänge des IP-Pakets: $20\,\text{Byte (IP)} + 8\,\text{Byte (UDP)} + 16\,\text{Byte (SOME/IP)} + 4\,\text{Byte (TP)} + 1392\,\text{Byte (Payload)} = 1440\,\text{Bytes} \le 1500\,\text{Bytes (Ethernet-MTU)}$.

3. Dynamisches Verhalten & Sequenzablauf

#### Senderseite (Segmentation, SomeIpTp_Transmit)

  1. Trigger: PduR fordert das Senden einer SOME/IP-Nachricht an, deren Länge die MTU (SomeIpTpTxPduLength) überschreitet.
  2. Segment-Generierung:
  • Kopieren von Message ID, Request ID (identische Session ID!), Protocol- und Interface-Version.
  • Setzen des TP-Flags im Message Type (Bit 5 = 1).
  • Einfügen des 4-Byte TP-Headers:
  • Segment 0: $\text{Offset} = 0$, $M = 1$.
  • Segment $n$: $\text{Offset} = (\sum_{i=0}^{n-1} \text{Payload-Länge}_i) / 16$.
  • Letztes Segment: $\text{Offset} = \text{End-Offset} / 16$, $M = 0$.
  1. PDU-Ausgabe: Jedes Fragment wird über SoAd_IfTransmit() als eigenständiges UDP-Paket dispatcht.

#### Empfängerseite (Reassembly, SomeIpTp_RxIndication)

  1. Identifikation: Detektion von TP-Flag == 1 im Message Type. Zuordnung zum Reassembly-Kontext über das Tupel {Message ID, Client ID, Session ID}.
  2. Buffer-Management & Assembly:
  • Initialisierung des Reassembly-Puffers und Start des Reassembly-Timers (SomeIpTpRxTimeoutTime).
  • Platzierung der Nutzdaten an Adresse RxBuffer + (Offset * 16).
  1. Abschluss:
  • Nach vollständigem Empfang aller Daten bis zum Paket mit $M = 0$ ohne Lücken: Entfernen des TP-Headers (4 Bytes), Rücksetzen des TP-Flags im Message Type (Bit 5 = 0), Korrektur des Length-Feldes auf die unfragmentierte Gesamtlänge.
  • Weitergabe der reassemblierten PDU an PduR_SomeIpTpRxIndication().
  1. Fehler- und Abbruchbedingungen:
  • Timeout vor Eintreffen aller Fragmente $\rightarrow$ Verwerfen des Reassembly-Puffers, Meldung an DET (SOMEIPTP_E_TIMEOUT).
  • Out-of-Order-Eintreffen wird gepuffert; überlappende Offsets oder falsche Segmentlängen führen zum Abbruch.

4. Normative Relevanz & Entwickler-Hinweise

  • Zwingendes 16-Byte-Raster (Alignment-Constraint):
  • Alle Fragmente mit gesetztem More-Segments-Flag ($M = 1$) müssen zwingend ein ganzzahliges Vielfaches von 16 Bytes Payload transportieren ($\text{Payload-Länge} \pmod{16} == 0$).
  • Lediglich das finale Fragment ($M = 0$) darf eine beliebige Bytezahl aufweisen.
  • Transparenz für Applikationsschichten:
  • Der 4-Byte TP-Header existiert ausschließlich „On-the-Wire“.
  • Obere Schichten (RTE, SomeIpXf, SWCs) sehen stets nur die vollständige, defragmentierte SOME/IP-PDU mit maskiertem TP-Flag (0x00 statt 0x20).
  • Bit-Packung des TP-Headers (Big-Endian-Serialisierung):
  • Byte 0: Offset[27:20]
  • Byte 1: Offset[19:12]
  • Byte 2: Offset[11:4]
  • Byte 3: Offset[3:0] (Bits 7..4) | RES[2:0] (Bits 3..1) | M (Bit 0)
  • Konfigurationsaspekte (SomeIpTp.epc):
  • SomeIpTpRxTimeoutTime: Muss ausreichend bemessen sein, um Netzwerk-Jitter und Segmentverzug über Switches hinweg zu tolerieren.
  • SomeIpTpRxBuffer: Da Fragmente via UDP verloren gehen oder vertauscht ankommen können, erfordert die Pufferverwaltung im Treiber statisch allokierte RAM-Bereiche für die maximale PDU-Größe je concurrent Session.
