1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-2.0-Metamodell-Ausschnitt (Klassendiagramm auf M2-Ebene gemäß AUTOSAR-Metamodell-Architektur).
  • Architektur-Kontext: Definition des Modemanagements im Software Component Template (SWCT) für AUTOSAR Classic (Release R2.1.20).
  • Funktionaler Zweck: Modellierung von Betriebsmodi (Modes), Modegruppen, deren Koppelung an Port-Schnittstellen (SenderReceiverInterface), die Bindung an das Komponentenverhalten (InternalBehavior) sowie die Steuerung von ausführbaren Einheiten (RunnableEntity) über modusspezifische RTE-Events (ModeSwitchEvent) und Modus-Deaktivierungsregeln (ModeDisablingDependency).

3. Dynamisches Verhalten & Sequenzablauf

Aus dem statischen Metamodell resultieren folgende deterministische RTE-Abläufe:

```

[Modus-Manager / SWC]

│

▼ (Mode Switch Request über P-Port)

RTE Mode Machine

│

├──► 1. Evaluierung Modus-Transition (Alter Modus -> Neuer Modus)

│

├──► 2. Auswertung ModeDisablingDependency:

│ Sperrt/Deaktiviert Triggern der abhängigen RunnableEntities

│ für alle in 'dependentOnMode' gelisteten Zustände.

│

└──► 3. Triggerung ModeSwitchEvent (ON_ENTRY / ON_EXIT / ON_TRANSITION):

Aktiviert verknüpfte RunnableEntity (+startOnEvent)

unter Einhaltung von 'minimumStartInterval' und 'canBeInvokedConcurrently'.

```

  1. Modus-Umschaltung: Ein Modus-Manager fordert via Port (ModeDeclarationGroupPrototype) einen Moduswechsel an.
  2. Event-Aktivierung (ModeSwitchEvent): Die RTE prüft die Konfiguration von ModeActivationKind (typischerweise ON_ENTRY oder ON_EXIT). Stimmt die Transition mit +mode überein, wird die referenzierte RunnableEntity in den OS-Task-Kontext eingesteuert (startOnEvent).
  3. Ausführungsverhinderung (ModeDisablingDependency): Trifft ein beliebiges anderes Event (z. B. TimingEvent, DataReceivedEvent) für eine RunnableEntity ein, prüft der RTE-Dispatcher, ob der aktuelle Modus in +dependentOnMode enthalten ist. Falls zutreffend, wird der Aufruf der Runnable verworfen bzw. unterdrückt.

4. Normative Relevanz & Entwickler-Hinweise

  • Release-Besonderheit (R2.1.20 vs. R4.x):

Modegruppen sind hier noch Bestandteil von SenderReceiverInterface. In R4.x-Metamodellen ist dies deprecated/entfallen und durch eigenständige ModeSwitchInterface-Klassen ersetzt. Für Legacy-Generatoren (R2.1.x/R3.x) müssen Modegruppen innerhalb des ARXML-Elements <SENDER-RECEIVER-INTERFACE> geparst werden.

  • Semantik von «instanceRef»:

Da ModeDeclaration ein M2-Metamodellelement innerhalb einer wiederverwendbaren ModeDeclarationGroup ist, erfordern ModeSwitchEvent und ModeDisablingDependency vollständige Instanzpfade im ARXML (Auflösung über Software-Component-Instanz, Port-Prototyp und Modusgruppe).

  • RTE-API und Codegenerierung:
  • Für Modus-Anbieter (P-Port): Generierung von Rte_Switch_<p>_<m>().
  • Für Modus-Nutzer (R-Port): Generierung von Rte_Mode_<p>_<m>() zur Modusabfrage.
  • ModeDisablingDependency erfordert RTE-interne Modusmaskierungs-Flags, die im Task-Body vor dem Call des Funktionssymbols (+symbol) abgefragt werden.
  • Concurrency & Scheduling:
  • Ist canBeInvokedConcurrently == false, muss die RTE Race Conditions via OS-Ressourcen, Semaphoren oder Zuweisung zu einer gemeinsamen sequentiellen Task verhindern.
  • minimumStartInterval erzwingt im RTE-Dispatcher einen Zeitstempel-Abgleich zur Begrenzung der Interrupt-/Event-Burst-Last auf dem Core.
