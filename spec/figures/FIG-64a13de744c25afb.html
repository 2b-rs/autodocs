1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptionelles Modellierungs- und Workflow-Diagramm (Kombination aus UML-Paket-/Objektstruktur, Traceability-Beziehungen und Aktivitätsknoten innerhalb horizontaler Partitions-/Swimlane-Strukturen).
  • Architektur-Kontext: AUTOSAR Authoring Tool Interoperability (AUTOSAR_TR_InteroperabilityAuthoringTools, Releases R2.1.x bis R3.2.x).
  • Funktionaler Zweck: Spezifikation des Verfahrens zum synchronisierten Update von ARXML-Modellelementen im verteilten, parallelen Entwicklungsprozess (Concurrent Engineering zwischen OEM, Tier-1 oder parallelen Entwicklungszweigen). Das Diagramm illustriert den Erhalt von Modellintegrität und Referenzen bei Modifikation oder Umbenennung (z. B. Korrektur eines Tippfehlers von BrakControl zu BrakeControl) eines Quell-Elements, auf das in einer getrennten Remote-Umgebung bereits Abhängigkeiten existieren.

2. Komponenten, Entitäten & Schnittstellen

  • Partitionen (Swimlanes):
    • Obere Partition (Source / Authoring Environment): Lokale Umgebung des Autors/Lieferanten von Model A.
    • Untere Partition (Remote / Integration Environment): Verteilte Integrationsumgebung, in der Model A importiert wurde und von einem weiteren Modell (Model B) konsumiert wird.
  • Modell-Container & Entitäten (UML-Packages / Identifiables):
    • Model A [source]: Ursprüngliches Quell-AR-Package mit dem Modellelement BrakControl [source] (z. B. SoftwareComponentType, PortInterface oder DataType mit Tippfehler).
    • Update: Transformationsprozess bzw. Modellierungsaktion im Quell-Tool.
    • Model A [updated]: Modifiziertes Quell-Package mit aktualisiertem Modellelement BrakeControl [updated].
    • Model A [remote]: Importierte Referenzkopie von Model A in der Remote-Umgebung mit BrakControl [remote].
    • Model B: Eigenständiges Remote-Package, enthält Entität X (unterstrichen dargestellt als konkrete Instanz oder referenzierendes Modellelement, z. B. SwComponentPrototype oder instanziierende Komponente).
    • Model A [merged]: Durch Merge-Operation synchronisiertes Modell A im Zielkontext mit BrakeControl [merged].
    • Model B [merged]: Aktualisiertes Zielmodell mit bereinigter Referenzentität X [merged] (annotiert mit (from Model B [merged])).
  • Beziehungen & Stereotypen:
    • «trace» (Gestrichelte gerichtete Pfeile über Partitionsgrenzen): Normative UML-Rückverfolgbarkeitsbeziehung zur Identitätsverfolgung replizierter Entitäten zwischen Quell- und Remote-Repository (Model A [source] → Model A [remote] und Model A [updated] → Model A [merged]).
    • Referenzassoziation (Durchgezogene Linien): Modellinterne Referenzierung (X → BrakControl [remote] bzw. X [merged] → BrakeControl [merged]). Repräsentiert im AUTOSAR-Metamodell eine typisierte Referenz (z. B. TYPE-TREF).
    • Kontroll-/Datenfluss (Gestrichelte Pfeile): Sequentieller Fluss Model A [source] → Update → Model A [updated].

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialer Modell-Export (Baseline-Trace):
    • Bereitstellung von Model A [source] an die Remote-Umgebung via ARXML-Export/Import.
    • Instanziierung als Model A [remote]; Etablierung des semantischen Trace-Links («trace»).
    • Element X in Model B bindet sich referenziell an BrakControl [remote].
  2. Entkoppeltes Update in der Quellumgebung:
    • Ausführung der Modifikation (Update): Das Element wird inhaltlich verändert oder umbenannt (BrakControl → BrakeControl).
    • Überführung in den Artefaktstatus Model A [updated].
  3. Synchronisations- & Merge-Phase (3-Wege-Abgleich):
    • Re-Import von Model A [updated] in die Remote-Umgebung.
    • Das Authoring-/Merge-Tool nutzt die Identitätsinformationen (Trace-Historie bzw. Metamodell-UUIDs), um zu erkennen, dass BrakeControl [updated] die neue Revision von BrakControl [remote] darstellt.
    • Referenzreparatur: Das Tool führt Model A und Model B in [merged]-Zustände über und biegt die bestehende Referenz von X [merged] automatisch auf das umbenannte/aktualisierte Ziel BrakeControl [merged] um, ohne dass es zu einer „Dangling Reference“ kommt.

4. Normative Relevanz & Entwickler-Hinweise

  • UUID- vs. SHORT-NAME-Auflösung:
    • Das Schaubild visualisiert eine Namensänderung (BrakControl → BrakeControl). Werden AUTOSAR-Modelle ausschließlich über ShortName-Pfade referenziert, bricht die Assoziation von X beim Update unwiderruflich ab.
    • Authoring-Tools müssen nach AUTOSAR-Interoperabilitätsrichtlinie eindeutige, invariante Identifikatoren (UUID gemäß Identifiable.uuid) oder externe Mapping-/Trace-Tabellen führen, um Three-Way-Merges und automatische Referenzanpassungen robust zu unterstützen.
  • Auswirkungen auf RTE- und Stack-Generierung:
    • Bei Typ- oder Namensänderungen von Software-Komponenten ändern sich C-Bezeichner, generierte RTE-APIs (Rte_Read_<p>_<o>, Rte_Write_<p>_<o>) und Datenstrukturdeklarationen im Applikations-Header (Rte_<swc>.h).
    • Integratoren müssen sicherstellen, dass nach dem Merge von Model B mit Model A [merged] der RTE-Generator neu aufgerufen wird, um Inkonsistenzen zwischen C-Implementierung von Komponente X und den geänderten RTE-Schnittstellen zu verhindern.
  • Modularisierung & Splitable Packages («atpSplitable»):
    • Werden Modellelemente über mehrere ARXML-Dateien aufgeteilt ausgeliefert, verlangt der AUTOSAR-Standard, dass partiale Updates konsumierbar bleiben, ohne dass intakte Projektkonfigurationen (z. B. ECU-Extracts oder System-Descriptions) manuell neu verdrahtet werden müssen.
