1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt zur Spezifikation von AUTOSAR-ECU-Konfigurationsparametern (ECUC-Metamodell) und deren Verknüpfung mit dem AUTOSAR-Software-Component-Template (M2-Metamodell) über Foreign References.
  • Funktionale Einordnung: Definition der Konfigurationsstruktur für die RTE-Generierung (AUTOSAR_SWS_RTE, Release R4.3.1). Das Diagramm spezifiziert, wie abstrakte, im Software-Design definierte kritische Abschnitte (ExclusiveArea einer SWC) bei der ECU-Integration instanzspezifisch auf konkrete Synchronisations- und Schutzmechanismen des AUTOSAR OS bzw. der Hardware abgebildet werden.

2. Komponenten, Entitäten & Schnittstellen

#### A. ECU-Konfigurationsebene der RTE (from RTE)

  • RteSwComponentInstance: EcucParamConfContainerDef (Multiplizität: 0..*):
  • Repräsentiert die Konfigurationsinstanz einer SWC auf der ECU.
  • Besitzt über +reference eine RteSoftwareComponentInstanceRef: EcucForeignReferenceDef (0..1, destinationType = SW-COMPONENT-PROTOTYPE) zur Bindung an die Systembeschreibung.
  • Hält via Komposition (+subContainer) den Container RteExclusiveAreaImplementation.
  • RteExclusiveAreaImplementation: EcucParamConfContainerDef (Multiplizität: 0..*):
  • Zentraler Konfigurationsknoten für die Implementierung eines exklusiven Bereichs.
  • Verknüpft über +reference die RteExclusiveAreaRef: EcucForeignReferenceDef (destinationType = EXCLUSIVE-AREA) direkt mit dem M2-Element.
  • Enthält über +parameter den Enumerationsparameter RteExclusiveAreaImplMechanism: EcucEnumerationParamDef mit folgenden Literalen (EcucEnumerationLiteralDef):
  • NONE: Kein Schutzmechanismus durch die RTE (z. B. bei kooperativem Task-Design oder exklusivem Zugriff durch genau eine Ausführungseinheit).
  • ALL_INTERRUPT_BLOCKING: Globales Sperren aller Interrupts (Hardware/Global).
  • OS_INTERRUPT_BLOCKING: Sperren von OS-Interrupts (Cat-2-ISRs).
  • OS_RESOURCE: Synchronisation über eine standardisierte OSEK/AUTOSAR-OS-Ressource.
  • OS_SPINLOCK: Synchronisation über einen Mehrkern-Spinlock.
  • RTE_PLUGIN: Synchronisation bzw. Schutzmechanismus wird über ein RTE-Plugin realisiert.
  • Enthält über +reference die optionale Referenz RteExclusiveAreaOsResourceRef: EcucReferenceDef (0..1), die mit +destination auf einen OS-Konfigurationscontainer verweist.
  • Enthält über +reference die optionale Referenz RteExclusiveAreaResponsibleRipsPluginRef: EcucUriReferenceDef (0..1), die mit +destinationUri auf die Plugin-Definition verweist.

#### C. ECU-Konfigurationsebene von RteRips (from RteRips)

  • SwComponentPrototype (Stereotyp AtpPrototype):

  • AtomicSwComponentType (Generalisierung von SwComponentType):
  • Konkreter atomarer Komponententyp, aggregiert über +internalBehavior (0..1, Stereotypen «atpVariation, atpSplitable») das Verhalten.

3. Dynamisches Verhalten & Sequenzablauf

Das Klassendiagramm bildet statische Konfigurationsstrukturen ab. Zur Laufzeit steuert diese Konfiguration den durch den RTE-Generator emittierten Code für die APIs Rte_Enter_<name>() und Rte_Exit_<name>():

```

SWC-Runnable

│

├──> Rte_Enter_() ───> [Generierter Schutzcode je nach RteExclusiveAreaImplMechanism]

│ │

│ ├── NONE : No-op / Inlined leer

│ ├── ALL_INTERRUPT_BLOCKING : SuspendAllInterrupts() / DisableAllInterrupts()

│ ├── OS_INTERRUPT_BLOCKING : SuspendOSInterrupts()

│ ├── OS_RESOURCE : GetResource(OsResource)

│ └── OS_SPINLOCK : GetSpinlock(OsSpinlock)

│

│ [Kritischer Abschnitt / Datenzugriff]

│

└──> Rte_Exit_() ───> [Freigabecode korrespondierend zum Einstiegsmechanismus]

│

├── NONE : No-op

├── ALL_INTERRUPT_BLOCKING : ResumeAllInterrupts() / EnableAllInterrupts()

├── OS_INTERRUPT_BLOCKING : ResumeOSInterrupts()

├── OS_RESOURCE : ReleaseResource(OsResource)

└── OS_SPINLOCK : ReleaseSpinlock(OsSpinlock)

```

  • Synchron vs. Asynchron: Alle Rte_Enter/Rte_Exit-Aufrufe sind streng synchrone Blockieraufrufe im Kontext des aufrufenden Tasks bzw. der aufrufenden ISR.
  • Abbruch-/Fehlerbedingungen: OS-Fehler (z. B. Ressourcenzuweisungsfehler, Deadlocks durch falsche Ressourcenschachtelung oder Spinlock-Fehlschläge) werden je nach OS-Statuskonfiguration über den OS-Errorhook abgefangen.

4. Normative Relevanz & Entwickler-Hinweise

  • Entkopplung SWC vs. BSW: Die SWC bleibt frei von OS-spezifischem Code. Der Entwickler implementiert ausschließlich Rte_Enter_<name>() und Rte_Exit_<name>(). Die Festlegung des physischen Schutzmechanismus erfolgt erst bei der ECU-Integration über ECUC_Rte_09030 (RteExclusiveAreaImplementation).
  • Instanzbezug bei Multi-Instantiation (supportsMultipleInstantiation = true):
  • Da RteExclusiveAreaImplementation ein Sub-Container von RteSwComponentInstance ist, kann für verschiedene Prototypen (SwComponentPrototype) desselben Typs ein abweichender Schutzmechanismus oder eine separate OS-Ressource konfiguriert werden (z. B. wenn Instanz A auf Core 0 und Instanz B auf Core 1 allokiert ist).
  • Semantische Validierungsregeln für Integratoren:
  • Wird RteExclusiveAreaImplMechanism = OS_RESOURCE gewählt, muss RteExclusiveAreaOsResourceRef zwingend auf eine gültige OsResource verweisen; andernfalls bricht der RTE-Generator mit einem Validierungsfehler ab.
  • Bei OS_RESOURCE muss die Deckenpriorität (Ceiling Priority) der OS-Ressource mindestens so hoch sein wie die höchste Priorität aller Tasks, die Zugriff auf diese ExclusiveArea haben (OSEK Priority Ceiling Protocol zur Vermeidung von Priority Inversion und Deadlocks).
  • Echtzeit- und Latenz-Einschränkungen:
  • ALL_INTERRUPT_BLOCKING sperrt auch Cat-1-ISRs und High-Priority-Hardware-Interrupts; der Einsatz ist auf minimale Befehlssequenzen zu beschränken, um Interrupt-Jitter im Gesamtsystem zu minimieren.
  • OS_INTERRUPT_BLOCKING sperrt Cat-2-ISRs bis zur OS-Sperrebene.
  • OS_SPINLOCK darf nur bei Multicore-Konfigurationen eingesetzt werden, bei denen Tasks/ISRs auf unterschiedlichen Cores synchronisiert werden müssen; auf demselben Core ist zur Vermeidung von Busy-Waiting eine OS_RESOURCE vorzuziehen.
