1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR BSW-Konfigurationsmetamodell (UML-Klassendiagramm auf Basis von EcucParamConfContainerDef / ECUC-Metamodell).
  • Technischer Zweck: Definition der channelspezifischen PDU-Identifikatoren, Referenzen und Car-Wakeup-(CWU)-Filterparameter für das FlexRay Network Management (FrNm) gemäß AUTOSAR_CP_SWS_FlexRayNetworkManagement (R23-11).
  • Architektur-Einordnung: Schnittstellenkonfiguration zwischen FrNm und dem FlexRay-Interface (FrIf) sowie dem PDU-Router (PduR). Das Metamodell legt fest, wie NM-Botschaften (Vote-, User-Data- und gemischte PDUs) empfangen, gesendet und zur Auswertung an den NM-Zustandsautomaten bzw. den Car-Wakeup-Manager übergeben werden.

2. Komponenten, Entitäten & Schnittstellen

Container-Hierarchie & Multiplizitäten
  • FrNmChannel (EcucParamConfContainerDef [1..*]): Wurzelcontainer je logischem FlexRay-NM-Kanal.
  • FrNmChannelIdentifiers (EcucParamConfContainerDef [1..1]): Aggregierter Sub-Container zur Bündelung aller PDU-Deskriptoren und Wakeup-Parameter.
Sub-Container & PDU-Definitionen
  1. FrNmTxPdu (EcucParamConfContainerDef [0..4]):
    • Unterstützt bis zu 4 Sende-PDUs pro Kanal (FlexRay-spezifisch für redundante Slots bzw. Multi-Slot-NM-Übertragung).
    • FrNmTxConfirmationPduId (EcucIntegerParamDef [0..65535], withAuto=true, symbolicNameValue=true): Handle-ID für den Sende-Bestätigungs-Callback FrNm_TxConfirmation() aus dem FrIf.
    • FrNmTxPduRef (EcucReferenceDef [1..1]): Referenz auf die System-PDU (Pdu in EcuC).
    • FrNmTxPduContainsVote (EcucBooleanParamDef): Flag, ob die PDU Abstimmungsdaten (Vote Bits zur Cluster-Abschaltung / State Machine Transition) enthält.
    • FrNmTxPduContainsData (EcucBooleanParamDef): Flag, ob die PDU Anwenderdaten (UserData) transportiert.
  2. FrNmRxPdu (EcucParamConfContainerDef [1..*]):
    • Mindestens eine Empfangs-PDU erforderlich.
    • FrNmRxPduId (EcucIntegerParamDef [0..65535], withAuto=true, symbolicNameValue=true): Handle-ID für FrNm_RxIndication(), aufgerufen durch das FrIf.
    • FrNmRxPduRef (EcucReferenceDef [1..1]): Referenz auf das globale Empfangs-PDU-Metamodell.
    • FrNmRxPduContainsVote (EcucBooleanParamDef): Steuert die Auswertung der PDU im NM-Voting-Algorithmus.
    • FrNmRxPduContainsData (EcucBooleanParamDef): Steuert die Extraktion von User-Data zur Weiterleitung an Nm / PduR.
  3. FrNmUserDataTxPdu (EcucParamConfContainerDef [0..1]):
    • Optionaler Container für entkoppelte Anwenderdaten-Sende-PDUs.
    • FrNmTxUserDataPduId (EcucIntegerParamDef [0..65535], withAuto=true, symbolicNameValue=true): Handle-ID für Bestätigungen separater User-Data-PDUs.
    • FrNmTxUserDataPduRef (EcucReferenceDef [1..1]): Exakte Referenz auf die zugehörige User-Data-PDU.
Car-Wakeup (CWU) Parameter (FrNmChannelIdentifiers)

Konfiguriert die hardwarenahe / protokollintegrierte Fahrzeug-Weckfunktion (RS_Nm_00149):

  • FrNmCarWakeUpRxEnabled (EcucBooleanParamDef [1..1]): Aktiviert/deaktiviert die CWU-Erkennung auf dem Kanal.
  • FrNmCarWakeUpBytePosition (EcucIntegerParamDef [0..1], Wertebereich 2..7): Byte-Offset des CWU-Bits im User-Data-Feld (Bytes 0 und 1 sind standardmäßig für Quell-Knoten-ID und Control Bit Vector reserviert).
  • FrNmCarWakeUpBitPosition (EcucIntegerParamDef [0..1], Wertebereich 0..7): Bit-Position innerhalb des definierten Bytes.
  • FrNmCarWakeUpFilterEnabled (EcucBooleanParamDef [0..1]): Aktiviert Knoten-ID-basierte Filterung von CWU-Signalen.
  • FrNmCarWakeUpFilterNodeId (EcucIntegerParamDef [0..1], Wertebereich 0..255): Ziel-Knoten-ID für die Filterprüfung.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt die statische Generierungsbasis für folgende Laufzeitpfade:

FrIf_RxIndication(FrNmRxPduId, PduInfoPtr)
  │
  ├──> FrNmRxPduContainsVote == TRUE  ──> FrNm-Voting-/Zustandslogik (Cluster Shutdown Vote)
  ├──> FrNmRxPduContainsData == TRUE  ──> FrNm_GetUserData() Puffer / Nm_PduRxIndication()
  │
  └──> FrNmCarWakeUpRxEnabled == TRUE
         │
         ├── Byte/Bit-Position auswerten
         └── Filter: falls FilterEnabled == TRUE && PduInfoPtr->NodeId != FilterNodeId
               ├── Match: Nm_CarWakeUpIndication()
               └── Miss: Drop CWU-Event
  • Tx-Pfad (FrNm_Transmit / Schedule): Entsprechend FrNmTxPduContainsVote und FrNmTxPduContainsData assembliert FrNm im FlexRay-Zyklus die Sende-Payload und triggert FrIf_Transmit(FrNmTxPduRef).
  • Tx-Confirmation: FrIf ruft nach Busübertragung FrNm_TxConfirmation(FrNmTxConfirmationPduId) auf, um Sende-Timer und Zustand zu synchronisieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Symbolic Name Generation (symbolicNameValue = true): Die PDU-IDs erzeugen C-Makros (z. B. FrNmConf_FrNmTxPdu_<ShortName>), welche als numerische Handle-IDs direkt im Interface-Code zwischen FrIf und FrNm eingebunden werden.
  • SWS_FrNm_00036 Konformität: Mindestens eine Empfangs-PDU (FrNmRxPdu) muss konfiguriert sein (lowerMultiplicity = 1). Die Obergrenze von 4 Sende-PDUs (FrNmTxPdu, Multiplizität 0..4) ist eine harte Architekturrestriktion des AUTOSAR-FlexRay-NM-Stacks.
  • PDU-Aufteilung (Vote vs. Data): Werden Vote- und Data-Bits auf unterschiedliche PDUs verteilt (ContainsVote = true / ContainsData = false oder umgekehrt), muss die PDU-Länge und Slot-Konfiguration im FIBEX/ARXML exakt auf das Kommunikationsraster der FlexRay-Slots abgestimmt sein.
  • Car-Wakeup Constraints: FrNmCarWakeUpBytePosition erzwingt einen Mindestoffset von 2 (min = 2), da Byte 0 (NID - Node Identifier) und Byte 1 (CBV - Control Bit Vector) des NM-Formats protokollgebunden sind. Ein Wert < 2 führt zu statischen EcuC-Validierungsfehlern im Generator.
