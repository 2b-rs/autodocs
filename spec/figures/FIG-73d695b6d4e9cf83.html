1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-2.x-Aktivitätsdiagramm (Control Flow / Activity Diagram mit Actions, Decision Nodes, Merge Nodes und Call-Behavior-Action).
  • Architektur-Kontext:
    • Eingebettet in die funktionale Sicherheit (ISO 26262 ASIL D tauglich) innerhalb der AUTOSAR-Basissoftware (BSW E2E Library / E2E Protection Wrapper) bzw. der AUTOSAR Foundation (AUTOSAR_FO_PRS_E2EProtocol).
    • Spezifiziert den internen Verifikationsschritt E2E_P01_CRCAndDataIDNibble der Empfängerfunktion E2E_P01Check() für E2E-Profil 1.
    • Prüft die Datenintegrität (CRC-8) und Authentizität der PDU bei aktivierter Nibble-Übertragung (E2E_P01_DATAID_NIBBLE) gegen Manipulation, Verfälschung und Fehlrouting.

2. Komponenten, Entitäten & Schnittstellen

  • Eingangsdatenstrukturen & Parameter (C-Pointer / Konfigurationsmodell):
    • Data (const uint8*): Rohdatenpuffer der empfangenen PDU/Payload.
    • Config (const E2E_P01ConfigType*): Konfigurationsstruktur des E2E-Profils 1 mit Parametern:
      • CRCOffset (uint16): Bit-Offset der CRC-Prüfsumme in Data (muss durch 8 teilbar sein).
      • DataIDMode (E2E_P01DataIDMode): Betriebsmodus der Daten-ID-Absicherung (u. a. E2E_P01_DATAID_BOTH, E2E_P01_DATAID_ALT, E2E_P01_DATAID_LOW, E2E_P01_DATAID_NIBBLE).
      • DataIDNibbleOffset (uint16): Bit-Offset des im Datenfeld übertragenen Nibbles (muss 0 oder 4 modulo 8 sein).
      • DataID (uint16): Konfigurierter 16-Bit-Identifikator der Nachricht.
  • Interne Variablen:
    • ReceivedCRC (uint8): Aus dem Puffer extrahierter CRC-Wert.
    • CalculatedCRC (uint8): Lokal berechnete CRC-8-Prüfsumme (im Diagramm-Text als Tippfehler: CalculatedRCR).
    • ReceivedDataIDNibble (uint8): Aus Data ausgelesenes 4-Bit-Nibble.
    • DataIDNibble (uint8): Erwartetes 4-Bit-Nibble (Low-Nibble des High-Bytes von Config->DataID).
  • Aufgerufene Subroutinen:
    • E2E_P01_Calculate CRC over DataId and Data: Aufruf der normierten CRC-Berechnungsroutine für Profil 1 (CRC-8-SAE J1850; Polynom 0x1D).
  • Rückgabewert:
    • boolean: TRUE (Prüfung erfolgreich / CRC und Nibble konsistent), FALSE (Integritäts- oder Identifikationsfehler).

3. Dynamisches Verhalten & Sequenzablauf

  1. CRC-Extraktion:
    • Ermittlung des Byte-Index via Config->CRCOffset / 8.
    • Zuweisung: ReceivedCRC = *(Data + (Config->CRCOffset / 8)).
  2. Evaluation DataID-Modus (Decision Node):
    • Bedingung: Config->DataIDMode == E2E_P01_DATAID_NIBBLE.
    • [FALSE]: Nibble-Extraktion wird übersprungen; direkter Übergang zur CRC-Berechnung.
    • [TRUE]: Prüfung der Nibble-Ausrichtung (Config->DataIDNibbleOffset % 8 == 0).
      • [TRUE] (Low-Nibble, Bit 0..3): ReceivedDataIDNibble = (*(Data + (Config->DataIDNibbleOffset / 8))) & 0x0F.
      • [FALSE] (High-Nibble, Bit 4..7): ReceivedDataIDNibble = (*(Data + (Config->DataIDNibbleOffset / 8)) >> 4) & 0x0F.
  3. CRC-Berechnung (Call-Behavior-Action):
    • Ausführung der synchronen Berechnung CalculatedCRC über Payload (Data) und relevante Anteile der DataID gemäß Profil-1-Vorschrift des Senders.
  4. Validierung & Status-Rückgabe (Decision Node):
    • Bedingungsprüfung: (ReceivedCRC == CalculatedCRC) && (ReceivedDataIDNibble == DataIDNibble).
    • [TRUE]: return TRUE (PDU ist intakt und stammt vom erwarteten Sender).
    • [FALSE]: return FALSE (führt in E2E_P01Check() zu E2E_P01STATUS_WRONGCRC oder Fehler-Statusinkrementierung).

4. Normative Relevanz & Entwickler-Hinweise

  • PDU-Layout-Restriktionen:
    • CRCOffset muss stets byte-aligned sein (CRCOffset % 8 == 0).
    • DataIDNibbleOffset unterstützt ausschließlich Nibble-Alignments: Entweder Bits 0..3 (Offset % 8 == 0) oder Bits 4..7 (Offset % 8 == 4). Beliebige Bit-Verschiebungen (z. B. unaligned Bit 1..4) sind gemäß Spezifikation unzulässig und führen bei fehlender Validierung zu undefiniertem Verhalten.
  • Architektur-Implikation bei Nicht-Nibble-Modus:
    • Wird ein anderer Modus verwendet (z. B. E2E_P01_DATAID_BOTH), wird ReceivedDataIDNibble in diesem Zweig nicht gesetzt; die nachgelagerte Bedingung ReceivedDataIDNibble == DataIDNibble darf im Code nur dann ausgewertet werden, wenn DataIDMode == E2E_P01_DATAID_NIBBLE aktiv ist (im abstrakten Diagramm durch Zusammenführung vereinfacht dargestellt).
  • Endianness & Bitreihenfolge:
    • Die Shift-Operation >> 4 setzt die kanonische AUTOSAR-Little-Endian/Big-Endian-Interpretation für Byte-Offsets voraus: Byte-Index wird ganzzahlig geteilt; Bit 0..3 repräsentiert das niederwertige Nibble des adressierten Bytes.
  • Echtzeit & Performance:
    • Die Funktion ist strikt synchron, reentrant, blockierungsfrei und allokiert keinen dynamischen Speicher. Sie eignet sich für Ausführungskontexte in ISRs oder hochpriore periodische BSW-Tasks (z. B. im Com- bzw. Rte_COMCbk-Pfad).
