1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Komponenten-Strukturdiagramm (Port- & Interface-View) für eine Test-Harness-Architektur.
  • Funktionale Einordnung: Dargestellt ist die Client-Sicht der Testsuite (NvMTestCases) im Rahmen der AUTOSAR Conformance Test Specification (AUTOSAR_CTSpec_Creation_Validation, R3.0.7) für den NVRAM Manager (BSW-Modul NvM).
  • Technischer Zweck: Definition der Schnittstellen-Entkopplung für automatisierte Modul-Konformitätstests. Das Diagramm spezifiziert, über welche Interaktionspunkte die Testfälle das System Under Test (SUT: NvM) stimulieren und die Reaktionen an den umgebenden Schnittstellen (Unterbau: MemIf, Hilfsbibliotheken: Crc, Fehlerbehandlung: Det, Dem, sowie Applikations-Callbacks: AppCb) über spezialisierte Test-Interfaces überwachen, konfigurieren und verifizieren (Mocking/Spying).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Ports
  • NvMTestCases: Zentrale Test-Client-Komponente (Test-Treiber/Harness), die 6 dedizierte Client-Ports deklariert:
    • appCbTest: Zugriff auf die Applikations-Callback-Prüfung.
    • crcTest: Zugriff auf CRC-Generierungs- und Validierungs-Stubs.
    • detTest: Zugriff auf den Default Error Tracer-Monitor.
    • demTest: Zugriff auf den Diagnostic Event Manager-Monitor.
    • memIfTest: Zugriff auf den Memory Abstraction Interface-Stub/Mock.
    • nvmIf: Direkte funktionale BSW-API des SUT (NvM).
Interfaces («interface») & Abhängigkeiten

Alle Beziehungen sind gerichtete Abhängigkeiten («use» / Usage Dependency, gestrichelte Pfeile) vom jeweiligen Port der Komponente NvMTestCases auf das entsprechende Test-/Treiber-Interface:

  1. NvMInterface (Funktionale SUT-Schnittstelle):
    • Standard-BSW-Service-APIs gemäß NvM-Spezifikation:
      • Lifecycle/Scheduling: NvM_Init(), NvM_MainFunction().
      • Multi-Block-Operationen: NvM_ReadAll(), NvM_WriteAll(), NvM_CancelWriteAll().
      • Single-Block-Operationen: NvM_ReadBlock(), NvM_WriteBlock(), NvM_RestoreBlockDefaults(), NvM_EraseNvBlock(), NvM_InvalidateNvBlock().
      • Administrative Services: NvM_SetRamBlockStatus(), NvM_SetBlockProtection(), NvM_GetErrorStatus(), NvM_SetDataIndex(), NvM_GetDataIndex(), NvM_GetVersionInfo().
  2. MemIfTestInterface (Unterbau-Mock / Test-Interface für Memory Abstraction Interface):
    • Steuerung und Beobachtung des unteren Hardware-Abstraktions-Layers:
      • Validierung & Status: CompareContents() : boolean, GetIsInvalid() : boolean, GetErasedImmediately() : boolean, GetMode() : MemIf_TestModeType.
      • Zähler & Verifikation: GetUseCount() : int, GetWriteCount() : int, GetCancelCount() : int.
      • Test-Ablaufsteuerung: FinishJob() : void, SetExpectMode() : void, SetExpectOrdering() : void, Reset() : void.
  3. AppCbTestInterface (Applikations-Callback-Monitor):
    • Verifikation von Single-Block- und Multi-Block-Callback-Benachrichtigungen an SW-Cs:
      • ArmCallback(), DisarmCallback(): Aktivierung/Deaktivierung der Callback-Erwartung.
      • ArmedCount(), GetUseCount(), InitCalled(): Zähler- und Statusabfragen.
      • Reset(): Zurücksetzen des Monitor-Zustands.
  4. CRCTestInterface (CRC-Service-Stub):
    • Überprüfung der Datenintegritätslogik (z. B. 8/16/32-Bit CRC):
      • ValidateCRC(), InvalidateCRC(): Gezielte Injektion von intakten oder korrupten Prüfsummen.
      • VerifyCRC() : boolean, GetUseCount() : void: Validierung des Aufrufverhaltens.
  5. DETTestInterface (Development Error Tracer-Monitor):
    • Abfangen und Validieren von Entwicklungsfehlern (z. B. uninitialisierter Aufruf, Null-Pointer, ungültige Block-ID):
      • ConfirmError() : boolean: Prüft, ob ein erwarteter DET-Fehler gemeldet wurde.
      • GetUseCount() : int, Reset() : void.
  6. DEMTestInterface (Diagnostic Event Manager-Monitor):
    • Überwachung von Produktionsfehlern (z. B. NVM_E_REQ_FAILED, Hardware-Fehler im Nv-Speicher):
      • GetEventStatus() : EventStatusType: Abfrage des Event-Status (z. B. PASSED, FAILED).
      • GetUseCount() : int, Reset() : void.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm definiert die statischen Zugriffspfade für folgenden typischen Testablauf:

  1. Test-Initialisierung (Setup):
    • NvMTestCases setzt über Reset() an detTest, demTest, memIfTest und appCbTest alle Zähler und Status zurück.
    • Konfiguration der Erwartungswerte am Stub (z. B. memIfTest.SetExpectMode(), appCbTest.ArmCallback(), crcTest.InvalidateCRC()).
  2. Stimulation (Synchroner Aufruf):
    • Aufruf einer NvM-API über nvmIf (z. B. NvM_ReadBlock(BlockId, RamPtr) oder NvM_WriteBlock(BlockId, RamPtr)).
    • NvM prüft Parameter; bei ungültigen Parametern erfolgt ein synchroner Aufruf an DET, verifizierbar über detTest.ConfirmError().
  3. Asynchrone Abarbeitung & Queue-Verarbeitung:
    • Periodischer Aufruf von nvmIf.NvM_MainFunction().
    • NvM beauftragt MemIf mit Lese-/Schreibvorgängen; memIfTest protokolliert GetWriteCount() und Zustand.
    • Simulation des Hardware-Endes via memIfTest.FinishJob().
  4. Validierung & Assertions (Teardown):
    • Testfall verifiziert Rückgabewerte über nvmIf.NvM_GetErrorStatus().
    • Testfall prüft via appCbTest.GetUseCount() und ArmedCount(), ob der konfigurierte Block-Callback ausgelöst wurde.
    • Testfall verifiziert via demTest.GetEventStatus(), ob Speicherfehler korrekt an das DEM gemeldet wurden.

4. Normative Relevanz & Entwickler-Hinweise

  • Konformitätsnachweis (Conformance Testing): Dieses Modell erzwingt, dass ein AUTOSAR-NvM vollständig gegen standardisierte Schnittstellen isoliert testbar ist. BSW-Zulieferer müssen sicherstellen, dass ihr NvM keine proprietären Abhängigkeiten zu Treibern unterhalb von MemIf oder abweichende Signaturen aufweist.
  • Mocking/Stubbing-Vorgabe: Die Test-Interfaces spiegeln die geforderte Kontrollierbarkeit und Beobachtbarkeit wider:
    • Asynchrone Jobs müssen deterministisch über FinishJob() abgeschlossen werden können, um Race Conditions in automatisierten Testumgebungen zu eliminieren.
    • Gezielte Fehlerüberprüfung via DET/DEM verlangt, dass die Fehler-IDs und Parameter exakt den normativen SWS-Anforderungen (z. B. SWS_NvM_00021 ff. für DET-Fehler) entsprechen.
  • CRC-Integritätstests: Durch ValidateCRC() / InvalidateCRC() muss die Wiederherstellungsstrategie des NvM (z. B. Rückfall auf ROM-Default-Daten via NvM_RestoreBlockDefaults()) automatisiert provozierbar sein.
  • API-Vertrag: Die in NvMInterface deklarierten Methoden stellen die verbindliche OSEK/AUTOSAR-C-Schnittstelle dar (Std_ReturnType, void). Die Modellierung als objektorientiertes Interface dient der formalen Testfall-Spezifikation und Abstraktion im Testframework (z. B. CANoe, vTESTstudio oder proprietäre xUnit-Harnesses).
