1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR ECUC Metamodell-Diagramm (UML 2.0 Klassendiagramm zur Definition des ECU-Konfigurationsschemas / EcucDefinitionCollection).
  • Architektur-Kontext: AUTOSAR Classic Platform, Memory Hardware Abstraction Layer (MemHwA, Layer 3). Das Diagramm definiert die Konfigurationsstruktur des BSW-Moduls Fee (Flash EEPROM Emulation, Modul-ID 40).
  • Funktionaler Zweck: Abstraktion der physikalischen Flash-Speichereigenschaften (Sektorlöschung, Write-Page-Grenzen) gegenüber dem MemIf (Memory Abstraction Interface) und dem NvM (Non-Volatile Memory Manager) durch Emulation eines adressierbaren 32-Bit-EEPROM-Speichers mit Blockstruktur, Wear-Leveling und Garbage Collection.

3. Dynamisches Verhalten & Sequenzablauf

Aus den dargestellten Konfigurationsparametern leitet sich folgende BSW-Laufzeitdynamik ab:

[NvM / MemIf]                [Fee Core]                 [Fls Driver]
      |                           |                           |
      |-- Fee_WriteBlock(...) --->| (Asynchroner Jobstart)    |
      |                           |-- Fls_Write(...) -------->|
      |                           |                           |
      |                 [Fee_MainFunction()]                  |
      |                  (Period: FeeMainFunctionPeriod)      |
      |                           |                           |
      |                           |-- (FeePollingMode=true) ->|
      |                           |    Fls_GetJobResult()     |
      |                           |<-- MEMIF_JOB_OK ----------|
      |                           |                           |
      |<-- JobEnd/ErrorCallback --|                           |
      |    (FeeNvmJobEnd/Error)   |                           |
  1. Job-Triggering (asynchron): Lese-, Schreib- und Invalidierungs-Aufträge gelangen über Fee_Read(), Fee_Write(), Fee_InvalidateBlock() synchron in den Puffer; die eigentliche Abarbeitung erfolgt asynchron in der internen State-Machine.
  2. Fortschaltung via Task: Fee_MainFunction() wird gemäß FeeMainFunctionPeriod vom OS-Task zyklisch aktiviert, treibt Block-Verlagerungen (Garbage Collection / Swap) voran und überwacht Flash-Schreib-/Löschvorgänge.
  3. Treiber-Kopplung (Polling vs. Callback):
    • FeePollingMode == true: Fee_MainFunction() ruft zyklisch Fls_GetJobResult() auf.
    • FeePollingMode == false: Fls benachrichtigt das Fee über Fee_JobEndNotification() / Fee_JobErrorNotification().
  4. Job-Terminierung: Nach Beendigung des Gesamtauftrags feuert das Fee synchron aus dem Kontext der Fee_MainFunction() die konfigurierten Callbacks FeeNvmJobEndNotification oder FeeNvmJobErrorNotification an den NvM.
  5. Fehlerbehandlung: Wenn FeeDevErrorDetect == true, melden ungültige Parameterwerte (z. B. uninitialisierter Aufruf FEE_E_UNINIT oder ungültige Blocknummer FEE_E_INVALID_BLOCK_NO) direkt synchron via Det_ReportError() an das Default Error Tracer Modul.

4. Normative Relevanz & Entwickler-Hinweise

  • Hardware-Alignment (FeeVirtualPageSize):
    • FeeVirtualPageSize muss zwingend ein ganzzahliges Vielfaches der physikalischen Flash-Programmiergröße (FlsPageSize) sein.
    • Nutzdatenlängen der NvM-Blöcke werden auf Vielfache der virtuellen Page-Größe aufgerundet.
  • Speicherbedarfsberechnung (FeeBlockOverhead, FeePageOverhead):
    • Die physikalische Belegung im Flash-Sektor pro Block berechnet sich aus: $$\text{FlashSize} = \text{FeeBlockOverhead} + \left\lceil \frac{\text{NvMBlockLength} + \text{FeePageOverhead}}{\text{FeeVirtualPageSize}} \right\rceil \times \text{FeeVirtualPageSize}$$
    • Diese Werte müssen im System-/NvM-Konfigurations-Tooling eingepflegt werden, um ein Sektorüberlaufen bei Flash-Bank-Swaps zu verhindern.
  • Modus-Synchronisation (FeeSetModeSupported):
    • Wenn FeeSetModeSupported = true, muss auch der darunterliegende Flash-Treiber FlsSetModeApi = true unterstützen.
    • Typischer Einsatz: MEMIF_MODE_FAST während Startup/Shutdown (erhöht Fls-Burst/Page-Größen oder Taktraten), MEMIF_MODE_SLOW während des Normalbetriebs zur CPU-/Bus-Entlastung.
  • Konfigurationsintegrität:
    • Da FeeBlockConfiguration die Multiplizität 1..* besitzt, ist ein generierter Fee-Treiber ohne mindestens einen deklarierten Block ungültig und führt zum Abbruch der BSW-Generierung.
