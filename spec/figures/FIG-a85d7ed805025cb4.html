1. Diagrammtyp & Architektur-Kontext

Architektur- und Bereitstellungsdiagramm (Deployment- und Kommunikationssicht) für die signal-zu-dienst-basierte Übersetzung zwischen AUTOSAR Adaptive Platform und AUTOSAR Classic Platform. Das Diagramm illustriert das architektonische Muster, bei dem eine Signal-to-Service-Translation in einem separaten Applikationsprozess auf einer Adaptive Machine gekapselt ist, um eine Brücke zwischen der dienstorientierten Kommunikation einer Adaptive Application und der signalbasierten Kommunikation einer Classic SWC über Netzwerk-Gateways zu schlagen.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in drei physische/logische Knoten sowie Kommunikationsmedien:

  • Adaptive Machine: Beherbergt zwei separate Prozesse (Process):
    • Erster Prozess mit der Adaptive Application, ausgestattet mit einem dienstorientierten Port (Service oriented communication).
    • Zweiter Prozess mit der Übersetzungskomponente Signal / Service Translation, die an der Oberseite über einen Dienstport und an der Unterseite über eine PDU-Schnittstelle (PDU, gegliedert in Signalfelder) verfügt.
    • Zwischen den beiden Prozessen vermittelt die Zwischenschicht ara::com über gepunktete Verbindungslinien zwischen den Ports.
  • Gateway ECU (Classic AUTOSAR): Klassisches Steuergerät, das als Netzwerkübergang zwischen Ethernet und CAN fungiert.
  • Classic ECU: Beherbergt eine klassische Software-Komponente (Classic SWC) mit signalbasiertem Port (Signal based communication).
  • Netzwerke und Artefakte:
    • Ethernet verbindet die Adaptive Machine mit dem Gateway ECU (Classic AUTOSAR).
    • CAN verbindet das Gateway ECU (Classic AUTOSAR) mit der Classic ECU.
    • Communication Matrix + signal-service Mapping: Dateisymbol/Konfigurationsartefakt, das der Ethernet-Verbindung der Adaptive Machine zugeordnet ist.
  • Logische Assoziation: Eine breite, hellblaue gestrichelte Linie visualisiert den logischen End-to-End-Kommunikationspfad zwischen dem Port der Adaptive Application und dem Port der Classic SWC.

3. Dynamisches Verhalten & Sequenzablauf

  • Signal- und Nachrichtenfluss: Signale aus der Classic SWC werden über den CAN-Bus in PDUs übertragen.
  • Das Gateway ECU (Classic AUTOSAR) leitet die CAN-Frames/PDUs über die Ethernet-Verbindung an die Adaptive Machine weiter.
  • Auf der Adaptive Machine empfängt der Übersetzungsprozess (Signal / Service Translation) die PDU über das Netzwerk.
  • Die Komponente Signal / Service Translation wandelt die PDU-Signale anhand der bereitgestellten Communication Matrix + signal-service Mapping in dienstorientierte Events, Methoden oder Felder um.
  • Über ara::com wird die übersetzte Service-Instanz prozessübergreifend an die Adaptive Application bereitgestellt.
  • Aus Sicht der Anwendungsentwicklung kommunizieren Adaptive Application und Classic SWC logisch transparent miteinander, abstrahiert über Dienst- bzw. Signalgrenzen hinweg.

4. Normative Relevanz & Entwickler-Hinweise

  • Die Signal-zu-Service-Übersetzung wird als reguläre Software-Lösung auf Anwendungsebene realisiert, nicht zwingend im AUTOSAR-Basis-Stack integriert.
  • Erfordert eine duale Bereitstellungskonfiguration: Einerseits PDU-Beschreibungen aus der klassischen Kommunikationsmatrix (System Description), andererseits Manifest-Definitionen für das Signal-Service-Mapping (signal-service Mapping) sowie Service-Schnittstellenbeschreibungen für ara::com.
  • Die Entkopplung in zwei separate OS-Prozesse erfordert IPC-Mechanismen über ara::com innerhalb der Machine sowie die Handhabung von PDU-Empfang/Versand auf Socket- bzw. Ethernet-Ebene im Translationsprozess.
