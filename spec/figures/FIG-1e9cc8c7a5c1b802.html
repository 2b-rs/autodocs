1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hybrides AUTOSAR-Schichtenarchitektur- und Kontroll-/Informationsflussdiagramm (Information Flow & Error Propagation Path).
  • Technischer Zweck: Spezifikationskonforme Darstellung der Fehlererkennung (Detection), der Autorecovery-Kette (Recovery) sowie der Fehlersignalisierung (Notification / Polling) bei Fehlschlagen einer asynchronen NvM-Anforderung (NVM API request failure) gemäß AUTOSAR_EXP_ErrorDescription (R4.0.3).
  • Systemeinordnung: Zeigt das Zusammenspiel zwischen Application Layer, RTE, Memory Services (NvM), System Services (DEM, DET, FiM), Memory Hardware Abstraction (MemIf, Fee, Ea) und der MCAL-Treiberschicht (Fls, Eep, Spi) bei persistenten Fehlern auf Block- oder Hardware-Ebene.

2. Komponenten, Entitäten & Schnittstellen

  • Application Layer & RTE:
  • Application Layer (SWCs): Initiiert NvM-Jobs und konsumiert Fehlerzustände.
  • AUTOSAR Runtime Environment (RTE): Entkopplungs- und Vermittlungsschicht für Service-Ports (Client/Server für APIs, Callbacks für Notifications).
  • Services Layer:
  • NVRAM Manager (NvM): Zentrales BSW-Modul; fungiert hier als Detection Point (1) und Recovery Initiator (2). Verwaltet RAM/ROM-Block-Mirror, Konsistenz (CRC) und Queuing.
  • Diagnostic Event Manager (DEM): Nimmt qualifizierte Fehler via Dem_ReportErrorStatus() entgegen; setzt DTCs.
  • Default Error Tracer (DET): Protokolliert Entwicklungsfehler (z. B. ungültige Block-IDs, Null-Pointer).
  • Function Inhibition Manager (FiM): Auswertung des DEM-Zustands zur Deaktivierung funktionaler SW-Pfade (im Diagramm als System Service flankierend dargestellt).
  • Memory Hardware Abstraction Layer:
  • Memory Abstraction Interface (MemIf): 1:n-Routing von Speicherzugriffen auf Fee oder Ea anhand des Parameters DeviceIndex.
  • EEPROM Abstraction (Ea): Lineare Adressierung auf physikalische EEPROM-Bereiche.
  • Flash EEPROM Emulation (Fee): Logische Sektor-/Blockverwaltung auf Flash-Speichern (Wear-Leveling, Swapping).
  • Ext. EEPROM / Flash Driver: BSW-Treiber zur Kapselung extern angebundener Bausteine.
  • Communication & Memory Drivers (MCAL):
  • SPI Handler/Driver (Spi): Bus-Kommunikation zum External EEPROM.
  • Internal EEPROM Driver (Eep) & Internal Flash Driver (Fls): Direkter hardwarenaher Registerzugriff auf On-Chip-Speicher.
  • Hardware Layer (µC & Peripherie):
  • SPI-Hardware, On-Chip RAM-Test-Einheit, interner EEPROM, interner Flash sowie externer SPI-EEPROM.

3. Dynamisches Verhalten & Sequenzablauf

Die Sequenz visualisiert den Fehlerverarbeitungspfad eines asynchronen NvM-Jobs (Read, Write, Erase oder Restore):

  1. (1) Detection (NvM-intern):
  • Die NvM_MainFunction() stellt bei der Abarbeitung fest, dass die Anforderung fehlgeschlagen ist (z. B. Lese-/Schreibfehler von MemIf, Timeout, Hardware-Fehlermeldung des MCAL-Treibers oder CRC-Integritätsverletzung im RAM/NV-Block).
  1. (2) Recovery Initiator (NvM):
  • Der NvM übernimmt autark die Fehlerbehandlung gemäß Blockkonfiguration (NvMBlockType, Redundanz- und Wiederholparameter).
  1. (3) Recovery (Grüne Pfade über Memory Stack):
  • Der NvM steuert Ersatzstrategien über den Hardware-Abstraktions-Stack an:
  • Redundanter Block: Leseversuch des zweiten Blocks über MemIf $\rightarrow$ Fee/Ea $\rightarrow$ Treiber $\rightarrow$ Hardware.
  • ROM-Default-Fallback: Rekonstruktion der RAM-Daten aus dem ROM-Block (NvMRomBlockNum bzw. Default-Pointer).
  • Schreib-/Lese-Wiederholungen: Parametrierbare Retry-Zyklen (NvMMaxNumOfReadRetries, NvMMaxNumOfWriteRetries).
  1. (4) Reporting & Notification (Rote & Blaue Pfade):
  • Pfad zur Diagnose (DEM): Nach Scheitern der internen Recovery-Versuche meldet der NvM das Produktionsfehlerevent via Dem_ReportErrorStatus(NVM_E_REQ_FAILED, DEM_EVENT_STATUS_FAILED). Der FiM inhibiert ggf. abhängige Applikationsfunktionen.
  • Pfad zur Applikation:
  • Asynchrone Notification (Roter Pfeil nach oben): Auslösen des konfigurierten Callbacks (NvMSingleBlockCallbackFunction bzw. Multi-Block-Callback) über die RTE mit Ergebnisstatus NVM_REQ_NOT_OK oder NVM_REQ_INTEGRITY_FAILED.
  • Synchrones Polling (Blauer Pfeil nach unten): Die Applikation fragt den Job-Status zyklisch über die RTE mittels NvM_GetErrorStatus(BlockId, &RequestResultPtr) ab.

4. Normative Relevanz & Entwickler-Hinweise

  • Asynchroner API-Vertrag:
  • Der synchrone Rückgabewert von NvM-APIs (z. B. NvM_ReadBlock(), NvM_WriteBlock()) vom Typ Std_ReturnType signalisiert ausschließlich die Annahme/Einreihung in die Job-Queue (E_OK), nicht den Operationserfolg.
  • Echte Verarbeitungsfehler treten erst zeitverzögert im Kontext der NvM_MainFunction() auf und müssen zwingend über Schritt (4) abgefangen werden.
  • Konfigurationsaspekte (NvM.epc / ECU-C):
  • NvMBlockUseCrc: Aktivierung zwingend erforderlich, damit Bitkipper als NVM_REQ_INTEGRITY_FAILED detektiert werden.
  • NvMRomBlockDataAddress: Muss bei sicherheitskritischen Parametern hinterlegt sein, um einen deterministischen Zustand bei Recovery-Schritt (3) zu garantieren.
  • NvMJobEndNotification / NvMJobErrorNotification: Festlegung, ob SWCs via Callback geweckt werden oder Polling-Mechanismen implementieren müssen.
  • Stack-Einschränkungen:
  • Die MemIf-/MCAL-Schichten dürfen während Recovery-Operationen (3) nicht blockieren; langwierige Flash-Lösch-/Schreibzyklen dürfen die Zykluszeit der Task, in der NvM_MainFunction() läuft, nicht verletzen.
  • Bei Auswahl von Polling im Application Layer muss die Polling-Frequenz an das Zyklusintervall der NvM_MainFunction() angepasst werden, um Busy-Waiting auf der RTE zu vermeiden.
