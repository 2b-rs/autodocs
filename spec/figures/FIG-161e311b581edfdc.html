1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (sd Scenario3a_NoDirtyFlag).
  • Technischer Zweck: Spezifikation des nichtflüchtigen Speicherzugriffs (NV Data Handling) gemäß AUTOSAR Classic Platform für Use Case 3a (Explicit Synchronization via RTE RAM Mirror without Dirty Flag Support).
  • Architektonische Einordnung: Darstellung des horizontalen und vertikalen Durchstichs von der Applikationsschicht (SW-C) über die RTE und die Memory Services (NvM) bis zur Memory Abstraction Layer (Fee/Ea) unter Koordination des AUTOSAR OS/Schedulers. Der Use Case adressiert Blöcke mit explizitem Synchronisationsmechanismus (NvMBlockUseSyncMechanism == TRUE), bei denen die RTE den Arbeits-RAM-Puffer hält, ohne dass Schreiboperationen durch Dirty-Flags gefiltert werden.

2. Komponenten, Entitäten & Schnittstellen

  • Akteure / Lifelines:
  • Scheduler/OS: AUTOSAR OS / Task-Management zur zyklischen Aktivierung von BSW-MainFunctions und ereignisgesteuerten Tasks (SetEvent).
  • SWC1: Applikationskomponente (AtomicSwComponentType), Besitzer der NV-Daten.
  • Rte: AUTOSAR Runtime Environment; fungiert als Speicherhalter des Applikations-Spiegels (Rte_RamBlock0) und Vermittler zwischen Port-Schnittstellen und BSW-Services.
  • NvM: Non-Volatile RAM Manager (BSW-Modul der Service-Schicht).
  • Ea/Fee: Hardware-Abstraktionsschicht (Fee = Flash EEPROM Emulation, Ea = EEPROM Abstraction, via Memory Interface MemIf).
  • Schnittstellen & Datenstrukturen:
  • Sender-Receiver / NV Data Interface: Rte_Write_NvData_VDP0(SWC1_VDP0) zum Aktualisieren des Dateninhalts im RAM (Rte_RamBlock0.Elm0).
  • Client-Server Service Port: Rte_Call_NvM_Service_WriteBlock(NULL_PTR) (typisiert über AUTOSAR-Standard-Interface NvM_Service).
  • Mirror-Callback: Rte_GetMirror_NvMB_BlkDesc0(&NvMBuffer) (NvM_ReadRamBlockFromNvM / NvM-Mirror-Interface).
  • Job-End-Callback: Rte_NvMNotifyJobFinished_NvMB_BlkDesc0(SID_WriteBlock, NVM_REQ_OK) (NvM_JobEndNotification).
  • OS-Objekte: Task SWC1_EvTask, Event OpInvokedEv_NJF (Operation Invoked Event).

3. Dynamisches Verhalten & Sequenzablauf

  1. Lokale RAM-Aktualisierung (Synchron):
  • SWC1 schreibt Nutzdaten via Rte_Write_NvData_VDP0(SWC1_VDP0).
  • Die RTE speichert das Datenelement im RTE-eigenen Puffer (Rte_RamBlock0.Elm0 = SWC1_VDP0) und kehrt sofort zurück.
  1. Asynchrone Schreibanforderung (Job Queuing):
  • SWC1 fordert den NV-Speichervorgang explizit an über Rte_Call_NvM_Service_WriteBlock(NULL_PTR).
  • Die RTE setzt Rte_SrcPtr = NULL_PTR und ruft die synchrone API NvM_WriteBlock(NvMBlock0, Rte_SrcPtr) auf.
  • NvM validiert Parameter, reiht den Job in die interne Warteschlange ein und quittiert synchron mit E_OK.
  • Der Aufruf kehrt zu SWC1 zurück; der eigentliche Schreibvorgang erfolgt verzögert im Hintergrund.
  1. Explizite Synchronisation & Hardware-Schreibvorgang:
  • Scheduler/OS ruft zyklisch NvM_MainFunction() auf.
  • NvM holt die Daten konsistent aus dem RTE-Mirror über den Callback Rte_GetMirror_NvMB_BlkDesc0(&NvMBuffer).
  • Die RTE kopiert atomar/geschützt Rte_RamBlock0 in den Modulpuffer NvMBuffer.
  • Da kein Dirty-Flag-Mechanismus konfiguriert ist, erfolgt keine Differenzprüfung: NvM stößt den Schreibzugriff bedingungslos über Fee_Write() bzw. Ea_Write() an den Abstraction-Layer an.
  1. Abschlussbenachrichtigung (Bottom-Up Callback-Kette):
  • Nach physischem Schreiben meldet der Treiber/Abstraction-Layer den Status über NvM_JobEndNotification() an den NvM.
  • NvM benachrichtigt die RTE über den projektspezifischen Block-Callback Rte_NvMNotifyJobFinished_NvMB_BlkDesc0(SID_WriteBlock, NVM_REQ_OK).
  • Zur Vermeidung von blockierenden Kontextwechseln setzt die RTE ein OS-Event: SetEvent(SWC1_EvTask, OpInvokedEv_NJF).
  1. Asynchrone Event-Verarbeitung in der SW-C:
  • Der OS-Scheduler aktiviert SWC1_EvTask basierend auf dem gesetzten Event (Operation Invoked Event).
  • Die RTE dispatcht die Callback-Runnable SWC1_NvMJobFinishedNotification(SID_WriteBlock, NVM_REQ_OK) in der Applikationskomponente.

4. Normative Relevanz & Entwickler-Hinweise

  • Puffer-Konsistenz & Kopier-Overhead: Durch NvMBlockUseSyncMechanism == TRUE ist der SW-C-Puffer entkoppelt; während des Transfers via Rte_GetMirror müssen Applikationszugriffe auf Rte_RamBlock0 durch RTE-Exklusivbereiche (ExclusiveArea) geschützt werden, um Dateninkonsistenzen während des Kopiervorgangs zu verhindern.
  • NV-Speicher-Verschleiß (Endurance & Buslast): In Use Case 3a fehlt das Dirty-Flag-Handling (NvMSetRamBlockStatus wird nicht ausgewertet). Jeder Aufruf von NvM_WriteBlock triggert unweigerlich einen Flash/EEPROM-Schreibzyklus, selbst wenn die Nutzdaten in SWC1_VDP0 identisch geblieben sind. Für verschleißsensitive Speicherblöcke ist Use Case 3b (mit Dirty Flag) zwingend vorzuziehen.
  • API-Vertrag (NULL_PTR Übergabe): Bei expliziter Synchronisation muss Rte_Call_NvM_Service_WriteBlock mit NULL_PTR parametriert werden, da die Quelldaten nicht über den API-Pointer, sondern über den GetMirror-Callback abgeholt werden. Ein nicht-NULL-Zeiger würde die explizite Synchronisation für diesen Aufruf unterlaufen oder abgewiesen.
  • Konfigurations-Mapping:
  • NvM: NvMBlockUseSyncMechanism = TRUE, Zuweisung von NvMBlockJobEndNotification auf die RTE-Generatsfunktion.
  • RTE: Konfiguration des NvBlockNeeds mit Mirror-Bereitstellung und Verknüpfung des JobFinishedNotification-Ports mit einem entsprechenden Asynchronous-Server-Call-Returns-Event bzw. Operation-Invoked-Event.
