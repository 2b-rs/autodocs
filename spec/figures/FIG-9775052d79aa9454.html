1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Activity/Work-Product-Diagramm (SPEM-basiertes Prozess- und Artefaktendiagramm).
  • Technischer Zweck: Spezifikation der Entwurfsphase zur Generierung der typ- und instanzspezifischen Software-Component-(SWC)-Header im Vendor Mode (herstellerspezifischer Generierungsmodus des RTE-Generators).
  • Architektur-Einordnung: Verortet in der Komponenten- und RTE-Entwicklungsmethodik (AUTOSAR Classic Platform, Release R4.0.3). Im Gegensatz zum generischen Compatibility Mode (standardisierte Contract Phase zur plattformunabhängigen SWC-Kompilierung) erzeugt der Vendor Mode optimierte, hersteller- und werkzeugspezifische Header (Rte_<swc>.h, Rte_Type.h), die Makro-Inlining, typspezifische Funktionsabstraktionen und ECU-spezifische Mappings für die finale C-Kompilierung bereitstellen.

2. Komponenten, Entitäten & Schnittstellen

Akteure (Rollen & Werkzeuge)
  • Software Component Developer (Rolle, Kardinalität: 1, Beziehung: «performs»): Primär ausführende Rolle bei der Komponentenentwicklung und Schnittstellendefinition.
  • ECU Integrator (Rolle, Kardinalität: 0..1, Beziehung: «performs»): Optionaler Akteur während der BSW-/ECU-Integrationsphase, falls Header bei der ECU-Konfiguration neu generiert oder angepasst werden.
  • Component API Generator Tool (Werkzeug, Kardinalität: 1, Beziehung: «used tool»): Der herstellerspezifische RTE-/Component-Code-Generator.
Eingangs-Artefakte («input»)
  • VFB Atomic Software Component [1]: ARXML-Beschreibung des Software-Component-Typs (ApplicationSwComponentType, SensorActuatorSwComponentType etc.) inklusive Port-Deklarationen (P-Ports, R-Ports).
  • Software Component Internal Behavior [1]: Beschreibt Runnables, Events, Inter-Runnable Variables (IRVs), Per-Instance Memories (PIM) und exclusive Bereiche.
  • Atomic Software Component Implementation [1]: Verknüpft das interne Verhalten mit C-Code-Artefakten, Speicherabschnitten (SwcImplementations) und Code-Deskriptoren (essentiell für den Vendor Mode, da implementationsspezifische Details einfließen).
  • VFB Types [0..*]: Definition der AUTOSAR-Datentypen (ApplicationDataType, ImplementationDataType, Base Types).
  • VFB Data Type Mapping Set [0..1]: Mappings zwischen Application- und Implementation-DataTypes.
  • VFB Interfaces [0..*]: Schnittstellendefinitionen (Sender-Receiver, Client-Server, Parameter, etc.).
  • VFB Modes [0..*]: Definition von Mode-Deklarationsgruppen (ModeDeclarationGroup) und Modimanagement-Interfaces.
  • VFB AUTOSAR Standard Package [0..1]: Standardisierte Plattform-Basisdatentypen (Std_Types.h), System-Limits und globale Typdefinitionen.
Ausgangs-Artefakte («output»)
  • Optimized Application Header File [1]: Das komponenten-spezifische Header-File Rte_<swc>.h. Enthält optimierte API-Deklarationen (Funktionsprototypen oder direkte Makro-Auflösungen wie Rte_Read_*, Rte_Write_*, Rte_Call_*), PIM-Strukturen und Runnable-Signaturen.
  • Software Component Data Types Header [1]: Generiertes Rte_Type.h mit sämtlichen Typdefinitionen, Aufzählungen, Enumerators und Datenstrukturen, die von der SWC referenziert werden.

3. Dynamisches Verhalten & Sequenzablauf

  1. ARXML-Konsolidierung & Parsing: Der Component API Generator Tool liest die VFB-Beschreibungen (Ports, Interfaces, Types, Modes) zusammen mit dem Internal Behavior und der Implementation.
  2. Type Mapping & Typ-Synthese: Auflösung von ApplicationDataType auf ImplementationDataType anhand des VFB Data Type mapping Set sowie Import der Basis-Datentypen aus dem Standard-Package; Generierung des Rte_Type.h.
  3. Optimierte API-Generierung (Vendor Mode):
    • Abhängig von der internen Konfiguration werden VFB-Zugriffe nicht zwangsläufig als Standard-Funktionsaufrufe angelegt, sondern herstellerspezifisch als performante Inlines/Makros aufgelöst (sofern keine Inter-ECU- oder RTE-Task-Entkopplung erforderlich ist).
    • Generierung von Instanz-Identifikatoren, PIM-Zeigern und Runnable-Deklarationen in Rte_<swc>.h.
  4. Trigger & Abhängigkeiten: Der Prozess wird ausgelöst, sobald sich Schnittstellen, Datentypen oder das interne Verhalten der SWC ändern. Da der Vendor Mode implementationsspezifisch ist (Atomic Software Component Implementation [1]), führt jede Änderung der Implementierungs-ARXML zu einer Re-Generierung der Header vor dem C-Compile-Schritt.

4. Normative Relevanz & Entwickler-Hinweise

  • Vendor Mode vs. Compatibility Mode:
    • Der Compatibility Mode generiert strikt standardisierte, neutrale C-Contracts, die SWCs compiler- und toolchain-portabel halten.
    • Der hier gezeigte Vendor Mode bindet den generierten C-Header an das spezifische RTE-Generierungswerkzeug eines Tool-Vendors (z. B. Vector DaVinci, ETAS ISOLAR, Elektrobit Tresos). Das erzeugte Rte_<swc>.h ist in der Regel nicht zwischen verschiedenen RTE-Implementierungen austauschbar.
  • Kompilier- und Linker-Auswirkungen:
    • Applikations-Entwickler müssen Rte_<swc>.h in ihren C-Quelldateien inkludieren.
    • Makrobasierte Optimierungen im Vendor Mode reduzieren den Call-Stack-Overhead bei Intra-ECU-Kommunikation, erfordern jedoch bei Änderungen am Datenfluss oder an den OS-Task-Mappings zwingend eine Neu-Kompilierung der SWC-Source-Dateien (keine binäre ABI-Stabilität gegen geänderte RTE-Generierung).
  • Einschränkung der Portabilität: Wird die SWC als vorkompilierte Object-Library ausgeliefert, darf der Vendor Mode nur dann genutzt werden, wenn die Ziel-ECU exakt denselben RTE-Vendor und dieselbe Generatorkonfiguration verwendet; andernfalls ist normativ der Compatibility Mode vorgeschrieben.
