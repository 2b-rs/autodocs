1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Protokoll-Header-Layout / PDU-Bitfeld-Spezifikation (Wire-Format, 32-Bit-aligned, Big-Endian / Network Byte Order).
  • Technischer Zweck: Definition der Struktur des SOME/IP Transport Protocol (SOME/IP-TP) Headers zur Segmentierung und Reassemblierung von SOME/IP-Nachrichten über UDP gemäß AUTOSAR_FO_PRS_SOMEIPProtocol.
  • Funktionale Einordnung:
  • Classic Platform (CP): Das Modul SomeIpTp ist zwischen PduR (PDU Router) und SoAd (Socket Adaptor) angesiedelt. Es kapselt die Segmentierungslogik unterhalb der Service-Schicht transparent für RTE und Application Layer.
  • Adaptive Platform (AP): Bestandteil der Kommunikations-Middleware (ara::com / SOME/IP-Binding bzw. Daemon-Layer) zur Übertragung von Payloads, die die IP-/UDP-MTU (typisch > 1400 Byte) überschreiten, ohne auf verbindungsorientiertes TCP ausweichen zu müssen.

2. Komponenten, Entitäten & Schnittstellen

Das Protokoll-Layout setzt sich aus dem 16-Byte-Standard-SOME/IP-Header, dem eingeschobenen 4-Byte-TP-Header sowie der variablen Payload zusammen:

  1. Standard SOME/IP-Header (16 Byte, Bits 0–31):
  • Message ID [32 bit]: Aufgeteilt in Service ID [16 bit] und Method ID [16 bit] (bzw. Event ID / Field ID).
  • Length [32 bit]: Gesamtlänge in Bytes ab Bit 0 des Feldes Request ID bis zum Ende des aktuellen Segments (beim TP-Segment: $8\,\text{Byte}\,\text{SOME/IP-Restheader} + 4\,\text{Byte}\,\text{TP-Header} + \text{Länge}(\text{Payload-Segment})$).
  • Request ID [32 bit]: Zusammengesetzt aus Client ID [16 bit] und Session ID [16 bit]. Alle Segmente derselben Gesamtnachricht teilen sich zwingend dieselbe Session ID.
  • Protocol Version [8 bit]: Protokollversion (0x01).
  • Interface Version [8 bit]: Major-Version des Service-Interfaces.
  • Message Type [8 bit] (farblich hervorgehoben): Bit 5 (0x20) fungiert als TP-Flag (PRS_SOMEIP_00724). Ist dieses Bit gesetzt (TP = 1), folgt nach dem Return Code unmittelbar der SOME/IP-TP-Header (z. B. 0x20 = REQUEST_TP, 0x21 = REQUEST_NO_RETURN_TP, 0x22 = NOTIFICATION_TP, 0x23 = RESPONSE_TP, 0x24 = ERROR_TP).
  • Return Code [8 bit]: Signalisiert Fehlerzustände (z. B. 0x00 = E_OK).
  1. SOME/IP-TP Header (4 Byte / 32 Bit, orange hinterlegt, PRS_SOMEIP_00725):
  • Offset [28 bit] (Bits 0–27): Offset der im Segment enthaltenen Payload bezogen auf die originale, unfragmentierte Gesamtnutzlast. Skalierungsfaktor: Der Wert ist in Einheiten von 16 Bytes kodiert (PRS_SOMEIP_00726). Der reale Byte-Offset berechnet sich als $\text{Byte-Offset} = \text{Offset} \times 16$.
  • RES [3 bit] (Bits 28–30): Reservierte Bits (PRS_SOMEIP_00727). Zwingend auf 0b000 zu setzen.
  • M [1 bit] (Bit 31, More Segments Flag, PRS_SOMEIP_00728):
  • M = 1: Weitere Fragmente folgen.
  • M = 0: Letztes Fragment der Nachricht (End of Message).
  1. Segmentierte Nutzdaten:
  • Payload [variable size]: Nutzdaten-Teilstück.

3. Dynamisches Verhalten & Sequenzablauf

#### TX-Pfad (Segmentierung, Sender):

  1. Trigger: Übergabe einer PDU via SomeIpTp_Transmit(), deren Gesamtlänge den für den Channel konfigurierten Schwellenwert (SomeIpTpTxFragmentLength) übersteigt.
  2. Header-Generierung: Kopieren der Standard-Header-Felder; Setzen von Bit 5 (TP-Flag) im Feld Message Type.
  3. Payload-Zerlegung:
  • Zwischensegmente ($M = 1$): Payload-Größe muss zwingend ein ganzzahliges Vielfaches von 16 Bytes sein (PRS_SOMEIP_00931). Offset inkrementiert je Segment um $\text{Länge}(\text{Payload}) / 16$.
  • Endsegment ($M = 0$): Transportiert den verbleibenden Rest der Payload; muss kein Vielfaches von 16 Bytes sein.
  1. Längenanpassung: Aktualisierung des SOME/IP-Feldes Length für jedes TP-Paket.
  2. Bursts/Inter-Frame Gap: Übergabe der Segmente an den SoAd-Treiber unter Beachtung von SomeIpTpSeparationTime (Vermeidung von Empfängerüberlastung).

#### RX-Pfad (Reassemblierung, Empfänger):

  1. Erkennung: Auswertung des Message Type: Ist Bit 5 gesetzt, liest der Stack die Bytes 16–19 als TP-Header aus.
  2. Session-Tracking: Identifikation des Datenstroms anhand des 4-Tupels {Source IP, Source Port, Message ID, Request ID}.
  3. Buffer-Management & Reassemblierung:
  • Platzierung der Segment-Payload im Reassembly-Buffer an Position Offset * 16.
  • Start/Refresh des Reassembly-Timers (SomeIpTpRxTimeoutTime).
  1. Abschluss: Empfang des Segments mit $M = 0$ und Prüfung auf Lückenfreiheit.
  2. Weiterleitung: Entfernen des 4-Byte-TP-Headers, Löschen des TP-Bits (Bit 5) im Message Type, Neuberechnung des ursprünglichen Length-Feldes und Weitergabe der reassemblierten PDU an PduR / obere Schichten.

#### Abbruchkriterien & Fehlerbehandlung:

  • Timeout (SOMEIPTP_E_TIMEOUT): Erreichen von SomeIpTpRxTimeoutTime vor Eintreffen aller Fragmente führt zum Verwerfen des gesamten Puffers.
  • Alignment-Verletzung: Empfang eines Segments mit $M = 1$, dessen Payload-Länge nicht durch 16 teilbar ist $\rightarrow$ Verwerfen der Nachricht.
  • Session-Diskontinuität: Empfang eines neuen Segments mit identischem Tupel, aber abweichender Session ID bricht laufende Reassemblierung ab.

4. Normative Relevanz & Entwickler-Hinweise

  • 16-Byte-Grenze (Zero-Padding & PDU-Zuschnitt): Bei der Implementierung von Streaming-/Pack-Algorithmen muss die Tx-Fragmentgröße (SomeIpTpTxFragmentLength) als Vielfaches von 16 Byte konfiguriert sein (z. B. 1392 Bytes = $87 \times 16$).
  • Memory Footprint & Buffer Allocation:
  • Im Classic AUTOSAR allokiert SomeIpTp statische Rx-Buffer (SomeIpTpRxBufferSize). Bei unvollständigen Bursts oder verlorenen UDP-Paketen belegt eine Nachricht bis zum Timeout einen Rx-Kanal (SomeIpTpChannel).
  • Schutz vor DoS / Puffererschöpfung durch Lost Packets über restriktive Auslegung von SomeIpTpRxTimeoutTime.
  • Bit-Masking im Message Type:
  • Low-Level-Filter dürfen den Message Type nicht nur auf Gleichheit prüfen (type == 0x00), sondern müssen Bit 5 maskieren (type & 0xDF == 0x00), sofern TP transparent abgefangen oder geroutet wird.
  • Header-Offset-Shift: Durch das Einfügen des 4 Byte großen TP-Headers verschiebt sich der Beginn der Nutzdaten von Byte 16 auf Byte 20. Parser müssen bei gesetztem TP-Flag zwingend einen 20-Byte-Offset für die Deserialisierung ansetzen.
