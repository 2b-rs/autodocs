1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB- & Schichtenarchitektur-Diagramm (Component- & Inter-ECU-Communication-View) zur Darstellung verteilter Modemanagement-Topologien über Steuergerätegrenzen hinweg.
  • Technischer Zweck: Visualisierung des standardisierten Musters zur Übertragung von Mode-Requests und Mode-Switches über ECU-Grenzen hinweg mittels einer ServiceProxySwComponentType.
  • Funktionale Einordnung: In AUTOSAR Classic (R4.0.3) sind ModeSwitchInterface und interne RTE-Modemaschinen (ModeDeclarationGroupPrototype) strikt ECU-lokal. Eine direkte VFB-Verbindung eines Mode-Ports über das Fahrzeugnetzwerk (CAN/LIN/FlexRay/Ethernet via Com-Stack) ist metamodell- und laufzeitbedingt unzulässig. Die ServiceProxySwComponent fungiert auf der Empfänger-ECU (ECU2) als Adaptionsschicht, um netzwerkbasierte Sender-Receiver-Signale in lokale BswM-Mode-Requests zu wandeln.

2. Komponenten, Entitäten & Schnittstellen

  • Steuergeräte (ECUs):
    • ECU1 (Mode-Master / Initiator): Beherbergt Applikationskomponenten (SWC1, SWC2), lokale RTE und den BswM (basic software mode manager).
    • ECU2 (Mode-Slave / Target): Beherbergt eine Proxy-Komponente (service proxy software component), Konsumenten (SWC3), lokale RTE und den lokalen BswM.
  • Software-Komponenten & BSW-Module:
    • SWC1, SWC3: Standard-Applikationskomponenten (ApplicationSwComponentType).
    • SWC2: Applikationskomponente, die als Applikations-Mode-Manager agiert und eine Modemaschinen-Instanz (mode machine Instance) kapselt.
    • service proxy software component: Spezialisierte Software-Komponente des Metamodell-Typs ServiceProxySwComponentType. Bildet einen BSW-Dienst (hier Mode Management) für externe Kommunikation ab.
    • basic software mode manager (BswM): Zentrales BSW-Modul (System Services) auf beiden ECUs zur Auswertung von Mode-Arbitrierungsregeln und Ausführung von Aktionslisten (BswMActionList).
  • Port-Klassifikation & Interface-Typen:
    • Mode-Switch-Ports (schwarzes Quadrat mit weißem Dreieck nach unten):
      • ECU1 (SWC2): PPortPrototype mit ModeSwitchInterface (stellt die mode machine Instance bereit).
      • ECU1 (BswM): RPortPrototype (mode switch port) empfängt Modewechsel-Benachrichtigungen von SWC2.
      • ECU2 (BswM): PPortPrototype (mode switch port) zur Steuerung lokaler Modemaschinen in der RTE.
    • Mode-Request- / Mode-User-Ports (schwarzes Quadrat mit 3 weißen Punkten):
      • ECU1 (BswM): mode request port zur Einbindung von/zu SWC1 und SWC2.
      • ECU2 (SWC3): RPortPrototype (Mode User / Mode-abhängiges Verhalten via SwcModeSwitchEvent oder modeAccessPoints).
    • Inter-ECU Kommunikationsports (weißes Quadrat mit schwarzem Dreieck):
      • ECU1 (SWC2): PPortPrototype mit SenderReceiverInterface (Datenübertragung an das Netzwerk).
      • ECU2 (Service Proxy): RPortPrototype mit SenderReceiverInterface (Empfang der Netzwerkdaten via Com/RTE).
    • Proxy-zu-BswM Port (ECU2):
      • Service Proxy: PPortPrototype für Mode Requests.
      • ECU2 (BswM): RPortPrototype (mode request port), empfängt lokale Mode Requests der Proxy-SWC.

3. Dynamisches Verhalten & Sequenzablauf

  1. Lokaler Modewechsel / Modustrigger auf ECU1:
    • SWC2 ändert seinen Modus über die interne mode machine Instance und meldet dies lokal an den BswM (mode switch port).
    • Parallel oder folgend verpackt SWC2 die Modusinformation in ein Standard-Signal eines SenderReceiverInterface und triggert Rte_Write_<p>_<dataElement>().
  2. Inter-ECU-Transport (Bus-Ebene):
    • Die RTE auf ECU1 leitet das Signal an den COM-Stack weiter (Com_SendSignal() / I-PDU-Generierung).
    • Übertragung über den Fahrzeugbus (CAN/LIN/FlexRay/Ethernet).
    • COM-Stack auf ECU2 empfängt die I-PDU, entpackt das Signal und stellt es der lokalen RTE bereit.
  3. Proxy-Verarbeitung auf ECU2:
    • service proxy software component liest den Zustand via Rte_Read_<p>_<dataElement>() (oder wird ereignisgesteuert durch ein DataReceivedEvent aktiviert).
    • Die Proxy-SWC übersetzt das Datum in einen Mode-Request und setzt einen Aufruf an die RTE ab (z. B. Rte_Write auf einem Mode-Request-Port oder Funktionsaufruf an den BswM).
  4. Arbitrierung & Umschaltung im BswM (ECU2):
    • Der BswM auf ECU2 erfasst die Anfrage über seine konfigurierte BswMModeRequestSource (z. B. BswMGenericRequest oder BswMSwcModeRequest).
    • Arbitrierung: BswM evaluiert die zugehörige BswMRule.
    • Bei positivem Ergebnis triggert die BswMActionList eine BswMModeSwitch-Aktion.
  5. RTE-Dispatch an Applikation (ECU2):
    • Der BswM stößt den Modewechsel via Rte_Switch_<p>_<modeGroup>() an seinem mode switch port an.
    • Die RTE schaltet den Zustand der lokalen Modemaschine um und feuert synchron/asynchron konfigurierte SwcModeSwitchEvents (On-Entry / On-Exit) an SWC3.
    • Ggf. Deaktivierung/Aktivierung von zyklischen Runnables in SWC3 durch RTE modeDisablingDependencies.

4. Normative Relevanz & Entwickler-Hinweise

  • Verbot von netzwerkweiten Mode-Switches: Ein ModeSwitchInterface kann im System-Description-Manifest (.arxml) niemals direkt über ein SystemSignal im COM gemappt werden. Ein Versuch, eine inter-ECU-Verbindung zwischen Mode-Ports zu modellieren, führt zu Validierungsfehlern im VFB-Generator / ECU-Extractor.
  • Konfiguration der ServiceProxySwComponent:
    • Im Komponentenmodell muss die Entität zwingend als ServiceProxySwComponentType deklariert sein.
    • Sie entkoppelt die standardisierte BSW-Schnittstelle von der anwendungsspezifischen Bus-Signal-Definition.
  • BswM-Parametrierung (ECU2):
    • BswMModeRequestSource: Muss als Port-Interface-Request konfiguriert werden, verknüpft mit dem R-Port des BswM.
    • BswMRule / BswMLogicalExpression: Definiert die Bedingung, ab wann der externe Request wirksam wird (z. B. Validierung gegen lokale Systemzustände wie Bordnetzspannung oder Diagnose-Session).
    • BswMActionList / BswMModeSwitch: Verweist auf den P-Port des BswM (ModeDeclarationGroupPrototype), welcher an die RTE gebunden ist.
  • API-Verträge & RTE-Generierung:
    • BswM nutzt Rte_Switch_<port>_<modeGroup>(<Mode>) (Rückgabewert: RTE_E_OK oder RTE_E_LIMIT).
    • SWC3 benötigt im SwcInternalBehavior entsprechende SwcModeSwitchEvent-Triggereinstellungen für Runnables oder disabledModeGroup-Zuordnungen.
  • Timing & Fehlerbehandlung:
    • Das Inter-ECU-Routing führt zu inhärenten Latenzen (Buslaufzeit, COM-Filter, Task-Jitter der Proxy-SWC). Zeitkritische Mode-Transitions müssen diese Totzeit im Timeout-Management (z. B. via Com-Signal-Deadline-Monitoring / E2E-Protection) berücksichtigen.
