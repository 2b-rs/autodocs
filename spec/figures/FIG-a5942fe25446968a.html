1. Diagrammtyp & Architektur-Kontext

Simulink-Blockschaltbild eines AUTOSAR-Software-Components bzw. eines Runnable-Subsystems auf Modellebene (AUTOSAR_SWC_and_Runnables/Software Component/Runnable_Simple). Das Diagramm illustriert das architektonische Muster für den internen Aufbau einer einfachen Runnable Entity (Runnable_Simple) innerhalb einer AUTOSAR-Softwarekomponente (SW-C) ohne Status-, Feedback- oder Invalidierungslogik.

2. Komponenten, Entitäten & Schnittstellen

  • Trigger/Event: RteEvent (Trigger-Block / Funktionsaufruf-Port zur Aktivierung der Runnable Entity durch die RTE).
  • Eingangsschnittstellen (Inports):
    • Inport 1 (DE_1): Empfängt das Datenelement DE_1 über RTE-Sender-Receiver-Kommunikation.
    • Inport 2 (DE_5): Empfängt das Datenelement DE_5 über RTE-Sender-Receiver-Kommunikation.
  • Funktionale Kernlogik (gelb hinterlegtes Subsystem / Berechnungsbereich):
    • Subtraktionsknoten (Sum / +-): Verrechnet DE_1 mit der zeitverzögerten Rückführung.
    • Zeitdiskreter Differenzblock (Difference, Übertragungsfunktion (z-1)/z): Verarbeitet das Ausgangssignal des Summierers zum Signal DE_a.
    • Vorzeichenblock (Sign): Ermittelt das Vorzeichen des Eingangswerts DE_5 und führt es zu DE_e.
    • Verstärkungsblock (Gain, Faktor 2): Skaliert den Eingangswert DE_5 für die Ausgabe an eine Inter-Runnable-Variable.
  • Ausgangsschnittstellen (Outports):
    • Outport 1 (DE_a): Sendet das Datenelement DE_a über RTE-Sender-Receiver-Kommunikation.
    • Outport 2 (DE_e): Sendet das Datenelement DE_e über RTE-Sender-Receiver-Kommunikation.
    • Outport 3 (IRV): Schreibt auf eine Inter-Runnable-Variable (IRV) zur komponenteninternen Kommunikation zwischen Runnables.

3. Dynamisches Verhalten & Sequenzablauf

  1. Die Runnable Entity wird durch ein Ereignis der RTE (RteEvent, z. B. periodischer Zeitgeber oder Datenempfangsereignis) getriggert.
  2. Eingangsdaten (DE_1, DE_5) werden an den Inports bereitgestellt (im impliziten Modus vorab von der RTE eingelesen oder im expliziten Modus abgerufen).
  3. Parallele Signalverarbeitungspfade innerhalb des Funktionsblocks:
    • Pfad 1: Differenzbildung des Signals DE_1 über den Summierer und den diskreten Übertragungsblock (z-1)/z; das berechnete Signal wird an Outport 1 (DE_a) weitergeleitet und auf den Minusschnittpunkt des Summierers rückgekoppelt.
    • Pfad 2: DE_5 wird dem Sign-Block zugeführt und das Vorzeichen an Outport 2 (DE_e) ausgegeben.
    • Pfad 3: DE_5 wird mit Faktor 2 im Gain-Block multipliziert und als IRV über Outport 3 bereitgestellt.
  4. Nach Durchlaufen der Berechnungen werden die Ergebnisdaten über die RTE bzw. im Inter-Runnable-Speicher der Komponente aktualisiert.

4. Normative Relevanz & Entwickler-Hinweise

Das Schaubild dient als Modellierungsvorlage im AUTOSAR-Simulink-Styleguide für minimale, zustandsfreie Runnables ohne erweiterte Fehlerbehandlung (Simple runnable without status / feedback / invalidate logic). Es demonstriert die saubere funktionale Trennung zwischen RTE-Kommunikationsgrenzen (Inports/Outports) und Kernalgorithmen (gelber Funktionsblock) sowie die Differenzierung zwischen Sender-Receiver-Datenelementen (DE_1, DE_5, DE_a, DE_e) und komponenteninternen Variablen (IRV). Entwickler müssen sicherstellen, dass Portbezeichnungen, Signalnamen und Abtastzeiten konsistent zu den AUTOSAR-Softwarekomponentenbeschreibungen (SWC-ARXML) konfiguriert sind.

Begleitender Spezifikationstext:

Figure 9 shows an example of a runnable with some functional behavior (highlighted in yellow). The data for the function is passed into and out of the function by senderreceiver communication over the RTE (inports 1/2 and outports 1/2) and also via an inter-runnable variable (outport 3). For sender-receiver communication there are two modes of operation: • Implicit: The RTE automatically reads a specified set of data elements before a runnable is invoked and automatically writes (a different) set of data elements after the runnable entity has terminated. This mode is termed “implicit” since the runnable takes no explicit action to inform the RTE to read or write data. • Explicit: A component uses explicit RTE API calls to send and receive data elements before the runnable has terminated.
