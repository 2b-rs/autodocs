1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsautomat (State Machine Diagram) mit drei orthogonalen (nebenläufigen) Regionen (Main, Activation und ModeDisabling) innerhalb des übergeordneten Composite States ExecutableEntity execution-instance is schedulable.
  • Technischer Zweck: Formale Definition des Lebenszyklus, Aktivierungs- und Deaktivierungsverhaltens einer Instanz einer ExecutableEntity (z. B. RunnableEntity eines SWC oder BswSchedulableEntity des BSW-Schedulers SchM) in der AUTOSAR Runtime Environment (RTE).
  • Architektonische Einordnung: Bindeglied zwischen RTE-Aktivierungstriggern (Events, Timer, Data-Received-Events), Modusverwaltung (ModeDeclarationGroup, Modus-Deaktivierung) und dem AUTOSAR-OS-Taskmanagement. Das Modell bildet ab, wie Aktivierungsanforderungen gepuffert, entprellt (minimumStartInterval), durch Betriebsmodi freigegeben oder gesperrt (ModeDisabling) und auf die Betriebssystem-Taskzustände (suspended, ready, running, waiting) synchronisiert werden.

2. Komponenten, Entitäten & Schnittstellen

  • Zustandsraum-Variablen & Timer:
    • activations: int = 0: Zähler für anstehende Ausführungsanforderungen (Aktivierungs-Queue).
    • «continuously increasing timer» - debounceTimer: float = minimumStartInterval: Kontinuierlich laufender Hardware-/OS-Timer zur Durchsetzung des Mindestabstands aufeinanderfolgender Starts (minimumStartInterval).
  • Orthogonale Region Main (Ausführungszustände im OS-Kontext):
    • suspended: Entität ist inaktiv; keine Ausführungsanforderung aktiv.
    • to be started: Aktivierung liegt vor (Activation in activated), Entität wartet auf Dispatching durch das OS.
    • started (Composite State):
      • running: Entität belegt aktuell den Prozessorkern (führt Code aus).
      • waiting: Entität blockiert auf ein OS-Event (wait, z. B. Rte_Receive/Rte_Feedback bei Server-Calls/Inter-Runnable-Synchronisation).
      • preempted: Unterbrochen durch höher priorisierten Task oder ISR (preempt).
    • OS-Zuordnung: Die Zustände to be started und preempted korrespondieren direkt mit dem OSEK/AUTOSAR-Task-Zustand READY.
  • Orthogonale Region Activation (Aktivierungs-, Entprell- & Modussperr-Logik):
    • Aktive Zustände:
      • not activated: Keine ausstehende Aktivierung vorhanden.
      • debounce activation: Aktivierung empfangen, Sperrzeit (minimumStartInterval) läuft.
      • activated: Ausführungsbedingung erfüllt; Entität ist startbereit für die Main-Region.
    • Deaktivierte Zustände (gesperrt durch Modus):
      • disabled not activated: Deaktivierter Grundzustand ohne anstehende Aktivierung.
      • disabled debounce activation: Deaktivierter Zustand während laufendem Debounce-Timer.
      • disabled activated: Deaktivierter Zustand mit bereits abgelaufenem Mindestabstand.
    • Queueing-Semantik: Parameter queue length definiert das Aktivierungslimit für die Entität (activations <= queue length).
  • Orthogonale Region ModeDisabling (Modus-Aktivierungssteuerung):
    • enabled: Entität ist für Aktivierung und Ausführung freigegeben (Standardzustand).
    • disabled: Entität ist durch mindestens einen aktiven Deaktivierungsmodus gesperrt.

3. Dynamisches Verhalten & Sequenzablauf

Partition Life-Cycle (Umfeld-Transitionen)
  1. Initialisierung: Eintritt in ExecutableEntity execution-instance is schedulable sobald Guard [RTE / SchM of the partition is running] wahr ist.
  2. Terminierung: Austritt in den Endzustand bei [RTE / SchM of the partition is stopped].
Region ModeDisabling (Modusverwaltung)
  1. Initialisierung: Startet im Zustand enabled.
  2. Moduswechsel:
    • Eintritt in deaktivierende Betriebsmodi: Trigger entersDisablingMode → Wechsel nach disabled.
    • Verlassen der deaktivierenden Betriebsmodi: Trigger exitsDisablingMode → Wechsel zurück nach enabled.
Region Activation (Ereignissteuerung, Queuing & Modussynchronisation)
  1. Erste Aktivierung:
    • Aus not activated via Event activate: Aktion /activations = 1 führt in Zustand debounce activation.
  2. Entprellung / Sperrzeit:
    • In debounce activation: Eintreffende activate-Events inkrementieren bedingt den Zähler (activations += (activations <= queue length) 1:0).
    • Sobald Guard [debounceTimer >= minimumStartInterval] erfüllt ist, erfolgt der Übergang in Zustand activated.
    • In activated: Eintreffende activate-Events inkrementieren ebenfalls bedingt den Zähler (activations += (activations <= queue length) 1:0).
  3. Modus-Deaktivierung und Re-Aktivierung:
    • Wechsel von aktiven zu inaktiven Zuständen bei Guard [ModeDisabling in state disabled]:
      • not activated → disabled not activated
      • debounce activation → disabled debounce activation
      • activated → disabled activated
    • Rückkehr bei Guard [ModeDisabling in state enabled]:
      • disabled not activated → not activated
      • disabled debounce activation → debounce activation
      • disabled activated → activated
  4. Queue-Abarbeitung & Rücksprung:
    • Auf Trigger start (synchronisiert mit Region Main): Aktion /activations -= 1; debounceTimer = 0.
    • Verzweigung (Choice-Pseudostate):
      • [activations == 0] → Rückkehr zu not activated.
      • [activations > 0] → Übergang zu debounce activation, um verbleibende Aktivierungen unter Einhaltung des minimumStartInterval abzuarbeiten.
Region Main (Ausführungs-Scheduling)
  1. Start:
    • Von suspended nach to be started, sobald Guard [Activation in state activated] greift.
    • Auf Event start → Wechsel in preempted (Task wird vom OS auf READY gesetzt).
  2. Ausführung:
    • Scheduler weist CPU zu: resume → running.
    • Bei Verdrängung: preempt → preempted.
  3. Synchronisation / Blockierung:
    • Blocking-Aufruf (nur in Extended Tasks zulässig): wait → waiting.
    • Event eintritt / Ressource frei: release → preempted.
  4. Beendigung:
    • Ende der Runnable-Funktion: terminate → Rückkehr nach suspended.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfiguration (minimumStartInterval): Das im BSW-/SWC-Dossier parametrierte minimumStartInterval schützt den Task vor Überlastung (z. B. bei hochfrequenten CAN-Interrupts oder Event-Triggerung). Ein zu groß gewählter Wert führt zu Latenzen bei Folgeaktivierungen; ein zu kleiner Wert kann CPU-Starvation niederpriorer Tasks begünstigen.
  • Queue-Überlauf (queue length): Übersteigt die Anzahl gleichzeitiger activate-Trigger die konfigurierte Queue-Tiefe, werden weitere Requests verworfen (activations += 0). Dies erfordert für sicherheitskritische Runnables eine exakte Worst-Case-Dimensionierung des Queue-Limits im System Description / EcuExtract.
  • Mode-Disabling-Mechanismus: Über die orthogonale Region ModeDisabling werden ExecutableEntities an RTE-Modi (ModeDeclarationGroup) gekoppelt. Wird ein deaktivierender Modus aktiv (entersDisablingMode), friert die Aktivierungslogik in den entsprechenden disabled ...-Zuständen ein. Da der Dispatching-Trigger in Region Main an [Activation in state activated] gebunden ist, werden in deaktivierten Modi keine neuen Task-Aktivierungen angestoßen.
  • Task-Typ-Restriktionen (Basic vs. Extended Task):
    • Die Transitionen wait und release setzen zwingend einen Extended Task (OSEK-Events) voraus.
    • Wird eine ExecutableEntity auf einen Basic Task gemappt, existiert der Unterzustand waiting zur Laufzeit nicht; der Code darf keine blockierenden RTE-APIs aufrufen (z. B. synchrone Server-Calls mit Warteoperationen).
  • RTE-Partitions-Status: Aktivierungen und Dispatching greifen nur, wenn die Partition der SWC/BSW gestartet ist (Rte_Start() / SchM-Init ausgeführt). Aufrufe oder Trigger im gestoppten Zustand bleiben inaktiv.
