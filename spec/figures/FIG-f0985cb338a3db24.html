1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML 2.x Sequenzdiagramm (Interaktionsdiagramm mit kombinierten Fragmenten alt für Verzweigungen und loop für iterative Datenübertragung).
  • Architektur-Kontext: AUTOSAR Classic Platform, Communication Stack (ComStack). Das Diagramm spezifiziert die Übertragung von TCP-Nachrichten über das DoIP-Modul (Diagnostic over IP) gemäß ISO 13400-2 / AUTOSAR SWS DoIP. Es ordnet sich vertikal zwischen dem PDU-Router (PduR) als Transport-Protocol-(TP-)Nutzer (z. B. Weiterleitung von Diagnosedaten aus dem Dcm) und dem Socket-Adaptor (SoAd) als Abstraktionsschicht zum TCP/IP-Stack ein.
  • Funktionaler Zweck: Standardisierte, asynchrone Übertragung von Diagnosenutzlasten (UDS-Frames via TCP) sowie DoIP-internen Steuernachrichten (z. B. Routing Activation Responses, Diagnostic Message ACK/NACK, Alive Check Requests/Responses) unter Wahrung des AUTOSAR TP-Pufferabrufmodells (Pull-Prinzip).

2. Komponenten, Entitäten & Schnittstellen

  • Dargestellte BSW-Module (Stereotyp «module»):
    • PduR: Routet TP-Nachrichten zwischen oberen Layern (Dcm) und DoIP; hält die Diagnose-Payload bereit.
    • DoIP: Kapselt das DoIP-Protokoll (Header-Generierung, Verbindungszustände, Routing-Aktivierung, Adresszuordnung).
    • SoAd: Verwaltet Socket-Verbindungen, TCP-Verbindungszustände und vermittelt zwischen ComStack-APIs und BSD-/AUTOSAR-TCP/IP-Sockets.
  • Verwendete Schnittstellen & APIs:
    • DoIP_TpTransmit(PduIdType TxPduId, const PduInfoType* PduInfoPtr): Synchroner Sendeanstoß von PduR an DoIP.
    • SoAd_TpTransmit(PduIdType TxPduId, const PduInfoType* PduInfoPtr): Synchroner Sendeanstoß von DoIP an SoAd.
    • DoIP_MainFunction(): Zyklischer Task-Aufruf des DoIP-Moduls zur periodischen Zustandsverwaltung und Abfertigung autonomer interner DoIP-Nachrichten.
    • SoAd_MainFunction(): Zyklischer Task-Aufruf zur Abwicklung der Socket-Puffer und Netzwerk-I/O.
    • DoIP_SoAdTpCopyTxData(PduIdType TxPduId, const PduInfoType* PduInfoPtr, const RetryInfoType* RetryInfoPtr, PduLengthType* AvailableDataPtr): TP-Callback von SoAd zur sequenziellen Abholung von Header und Nutzdaten aus dem DoIP.
    • PduR_DoIPCopyTxData(PduIdType TxPduId, const PduInfoType* PduInfoPtr, const RetryInfoType* RetryInfoPtr, PduLengthType* AvailableDataPtr): TP-Callback von DoIP an PduR zum Auslesen der Diagnosenutzlast (DCM-Puffer).
    • DoIP_SoAdTpTxConfirmation(PduIdType TxPduId, Std_ReturnType Result): Asynchroner Callback von SoAd an DoIP über den Abschluss der TCP-Übertragung.
    • PduR_DoIPTxConfirmation(PduIdType TxPduId, Std_ReturnType Result): Abschlussquittierung von DoIP an PduR.

3. Dynamisches Verhalten & Sequenzablauf

Der Ablauf gliedert sich in Sendeinitiierung, Datenbereitstellung und Bestätigung:

  1. Sendeinitiierung (Kombinationsfragment alt):
    • Pfad 1 [TCP Message from PduR]:
      1. PduR ruft synchron DoIP_TpTransmit() auf.
      2. DoIP führt interne Validierungen durch ("Check if the transmission of the data package is allowed"): Prüfung, ob die TCP-Verbindung besteht, die logische DoIP-Kanalzuordnung gültig ist und die Routing-Aktivierung für die Tester-Adresse vorliegt.
      3. DoIP konstruiert den generischen DoIP-Header ("Add the header information": Protokollversion, inverse Protokollversion, Payload-Typ z. B. 0x8001, Payload-Länge).
      4. DoIP leitet den Request via SoAd_TpTransmit() an SoAd weiter.
      5. Der Aufruf kehrt synchron über DoIP an PduR zurück (Ergebnis E_OK signalisiert lediglich Annahme des Sendeauftrags, nicht den Übertragungsabschluss).
    • Pfad 2 [DoIP internal TCP Message]:
      1. Unabhängig von PduR generiert DoIP im Kontext seiner zyklischen DoIP_MainFunction() eine DoIP-Steuerbotschaft ("Processed DoIP internal TCP message to be sent").
      2. DoIP ruft direkt SoAd_TpTransmit() auf.
  2. Übertragungsphase (Kombinationsfragment loop until all data is send):
    • Die Übertragung wird asynchron durch SoAd_MainFunction() getrieben.
    • SoAd fordert über DoIP_SoAdTpCopyTxData() segmentweise Daten an.
    • Interleaving / Chunking:
      • Für die ersten 8 Bytes (DoIP-Header) bedient DoIP den Puffer direkt aus lokalen Daten.
      • Für die Nutzlast ruft DoIP kaskadiert PduR_DoIPCopyTxData() auf, um die Nutzdaten direkt aus dem oberen Puffer (z. B. DCM) ohne Zwischenkopie in den SoAd-Puffer zu übertragen.
    • Die Schleife iteriert, bis die gesamte PDU-Länge an den Netzwerkstack übergeben wurde.
  3. Abschlussquittierung (TxConfirmation):
    • Nach erfolgreichem Absetzen bzw. TCP-Quittierung meldet SoAd den Status via DoIP_SoAdTpTxConfirmation().
    • DoIP bereinigt seinen Verbindungskontext und leitet die Quittierung bei PduR-initiierten Nachrichten über PduR_DoIPTxConfirmation() weiter.

4. Normative Relevanz & Entwickler-Hinweise

  • Virtual Header Insertion & Pufferversatz: DoIP agiert als Zero-Copy- bzw. Minimal-Copy-Protokoll-Translator. Entwickler müssen beachten, dass die Gesamtlänge der PDU an SoAd_TpTransmit() um 8 Bytes (DoIP-Header) größer ist als die ursprüngliche PDU-Länge in DoIP_TpTransmit(). Die Funktion DoIP_SoAdTpCopyTxData() muss den Zustandsübergang (Offset 0…7: lokaler DoIP-Header, Offset ≥ 8: Weiterleitung an PduR_DoIPCopyTxData()) fehlerfrei ohne Pufferüberläufe verwalten.
  • Zustandsabhängige Transmit-Gates: Der Schritt "Check if the transmission of the data package is allowed" erzwingt das Verwerfen (E_NOT_OK) von DoIP_TpTransmit(), wenn die zugehörige DoIP-Verbindung nicht im Zustand DOIP_ACTIVATED (Routing Activation erfolgt) ist oder ein Authentifizierungs-/Bestätigungsmechanismus (z. B. nach ISO 13400-2 / OEM-Spezifikation) noch aussteht.
  • Asynchrone Entkopplung & Task-Scheduling: Die Datenübergabe findet nicht im Transmit-Kontext statt, sondern zeitlich entkoppelt im Task-Kontext von SoAd_MainFunction() / DoIP_MainFunction(). Konfigurationsfehler in den Task-Perioden führen direkt zu Latenzen im Diagnose-Streaming oder zu Socket-Buffer-Underruns.
  • Fehlerbehandlung: Bricht PduR_DoIPCopyTxData() mit E_NOT_OK ab, muss DoIP den Vorgang an SoAd propagieren. Dies führt zu einem Abbruch der TCP-Verbindung (SoAd_CloseSoCon() bzw. TCP RST/FIN) gemäß SWS-Fehlerbehandlungsanforderungen.
