1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturelles Schichten- und Entkopplungsmodell (Vergleichs-Strukturdiagramm: monolithisch vs. geclustert).
  • Technischer Zweck: Gegenüberstellung der Interaktion von BSW-Modulen in einer monolithischen Classic-AUTOSAR-Laufzeitumgebung (none clustered) gegenüber einer partitionierten Architektur (clustered) gemäß AUTOSAR_SWS_SoftwareClusterConnection.
  • Funktionale Einordnung: Ermöglicht die Entkopplung und separate Kompilierung/Aktualisierung (OTA) eines Applicative Software Clusters unabhängig vom Host Software Cluster. Das Diagramm spezifiziert das Proxy-Modul-Muster (Proxy module approach), um bestehende C-API-Schnittstellenbeziehungen über Software-Cluster- und Speicherschutzgrenzen (MPU/Core-Grenzen) hinweg ohne Code-Änderung in den beteiligten BSW-Modulen transparent zu erhalten.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Partitionen

  • None clustered AUTOSAR Architecture:
  • BSW Module A: Aufrufendes BSW-Modul (exemplarisch als RTE oder CDD/Complex Device Driver annotiert), das Dienste eines unterlagerten Moduls konsumiert.
  • BSW Module B: Dienstanbietendes Basissoffware-Modul.
  • Clustered AUTOSAR Architecture:
  • Applicative Software Cluster (ASCL): Unabhängig lieferbares/flashbares Software-Paket.
  • BSW Module A: Identische Applikations-/BSW-Komponente wie im monolithischen System (bleibt source-kompatibel).
  • High Proxy BSW Module B: Lokaler Stellvertreter im ASCL. Exponiert exakt die Lower IF B-Schnittstelle gegenüber BSW Module A.
  • Binary Manifest: Enthält die Adress- und Funktionszeigertabellen / Symbol-Bindings für die clusterübergreifende Auflösung zur Laufzeit oder Ladezeit.
  • Host Software Cluster (HSCL): Basis-Cluster, der Kern-BSW, OS und Treiber hostet.
  • Binary Manifest: Gegenstück im Host zur Verifikation und Auflösung der Inter-Cluster-Endpunkte.
  • Lower Proxy BSW Module B: Empfangender Stellvertreter im HSCL; nimmt Inter-Cluster-Transfers entgegen und leitet sie lokal an BSW Module B weiter.
  • BSW Module B: Das eigentliche BSW-Modul im Host-Cluster.

#### Schnittstellen & Beziehungen

  • Interface dependency Upper IF A to LowerIF B:
  • Im monolithischen System: Direkter C-Funktionsaufruf (statisches Linking, Link-Time/Header-Inklusion).
  • Im ASCL: Standard-C-Funktionsaufruf von BSW Module A in den High Proxy.
  • Im HSCL: Standard-C-Funktionsaufruf vom Lower Proxy in BSW Module B.
  • Cluster-Boundary-Beziehung (High Proxy $\leftrightarrow$ Lower Proxy via Binary Manifest):
  • Indirekte Kopplung über Relokations- und Export-/Import-Tabellen des Binary Manifests.
  • Überbrückung des Adressraum- bzw. Cluster-Gaps ohne statische Linker-Referenz.

3. Dynamisches Verhalten & Sequenzablauf

  1. Aufruftrigger: BSW Module A führt einen synchronen oder asynchronen API-Aufruf an LowerIF B aus (z. B. Senden einer PDU, Lesen eines Status oder Hardware-Zugriff).
  2. Abfangen im ASCL (High Proxy): Der Aufruf landet im High Proxy BSW Module B. Dieser serialisiert ggf. Argumente, validiert Parameter lokal oder liest den Zielzeiger aus dem lokalen Binary Manifest.
  3. Inter-Cluster-Dispatching:
  • Der Übergang erfolgt über die clusterübergreifende Sprungtabelle / RPC-Mechanismus (z. B. Trap, Software-Interrupt, Kern-IPC oder abgesicherter Funktionszeigeraufruf über das Manifest).
  • Abbruchbedingung / Det/Dem: Ist der Ziel-Cluster ungültig, nicht initialisiert oder das Binary Manifest inkompatibel (Versionskonflikt der Interface-Signatur), bricht der Mechanismus mit einem Cluster-Verbindungsfehler ab (DET-Meldung, z. B. SC_E_INVALID_CLUSTER_STATE bzw. definierter Rückgabewert wie E_NOT_OK).
  1. Empfang im HSCL (Lower Proxy): Der Lower Proxy BSW Module B empfängt den Dispatcher-Aufruf, prüft Aufrufrechte (MPU-Partitionierung/ASIL-Level) und führt den nativen Funktionsaufruf auf BSW Module B aus.
  2. Rückgabepfad: Synchrone Rückgabewerte oder asynchrone Callbacks (z. B. TxConfirmation, RxIndication) durchlaufen den inversen Pfad (BSW Module B $\rightarrow$ Lower Proxy $\rightarrow$ Binary Manifest $\rightarrow$ High Proxy $\rightarrow$ BSW Module A).

4. Normative Relevanz & Entwickler-Hinweise

  • Transparenz für BSW-/CDD-Entwickler: Weder BSW Module A noch BSW Module B müssen für das Clustering refaktorisiert werden. Der API-Vertrag (Upper IF A zu Lower IF B) bleibt identisch; Quellcode und Header-Dateien der Module bleiben unangetastet.
  • Code-Generierung & Tooling:
  • Der BSW-Generator muss anhand der Software-Cluster-Konfiguration erkennen, dass Module A und B in getrennten Clustern (ApplicativeSoftwareCluster vs. HostSoftwareCluster) alloziert sind.
  • Entsprechend müssen High Proxy und Lower Proxy automatisiert generiert werden.
  • Binary Manifest & Kompatibilität:
  • Funktionszeiger dürfen nicht absolut gelinkt werden. Das Binary Manifest definiert verbindliche Tabellen-Offsets.
  • Beim Update des Applicative Software Clusters muss sichergestellt sein, dass die ABI-Kompatibilität der Schnittstelle Lower IF B im Host-Cluster gewahrt bleibt (strikte Versionsprüfung der Manifest-Deskriptoren).
  • Laufzeit- und Speicher-Overhead:
  • Zusätzliche Latenz durch Indirektionen (Funktionszeiger-Lookups, Register-Sicherung bei MPU-/Privilegienwechsel).
  • Erhöhter ROM-/RAM-Bedarf durch Proxy-Code, Wrapper-Funktionen und Manifest-Tabellen in beiden Clustern.
  • Einschränkungen bei Callbacks und Macros:
  • Funktions-Macros (#define) über Modulgrenzen hinweg sind nicht zulässig; Schnittstellen müssen als echte C-Funktionen mit fester ABI vorliegen.
  • Reentrancy- und Concurrency-Bedingungen: Werden BSW-Funktionen aus unterschiedlichen Clustern aufgerufen, müssen die Proxys die Thread-Sicherheit bzw. OS-Interrupt-Sperren konsistent zum Core- und Task-Kontext managen.
