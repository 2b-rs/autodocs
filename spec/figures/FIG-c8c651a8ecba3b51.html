1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration Metamodell (ECUC Parameter Definition) als UML-Klassendiagramm.
  • Funktionale Einordnung: Spezifikation der Konfigurationsstruktur für das BSW-Modul DoIP (Diagnostic over IP, AUTOSAR_SWS_DiagnosticOverIP, Kapitel 10 Configuration specification).
  • Technischer Zweck: Statische Parametrierung autorisierter externer Diagnose-Tester (DoIP Tester Entities). Es modelliert die Identifikation von Testern anhand ihrer logischen Quelladresse (Source Address, SA), begrenzt die Datenlänge für diagnostische Bestätigungsmeldungen (Diagnostic Message Ack/Nack) und verknüpft autorisierte Tester mit den zulässigen Routing-Aktivierungen (DoIPRoutingActivation), um Diagnosepfade zum PDU-Router (PduR) bzw. Diagnostic Communication Manager (Dcm) freizugeben.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Parameter

  • DoIPTester (EcucParamConfContainerDef)
  • Multiplizität: [1..255]. Mindestens ein Tester muss im Modul konfiguriert sein; maximal 255 Testerinstanzen werden unterstützt.
  • Rolle: Bündelt die Testerspezifische Sicherheits- und Routing-Konfiguration auf BSW-Ebene.
  • DoIPNumByteDiagAckNack (EcucIntegerParamDef)
  • Beziehung: Komposition (+parameter) in DoIPTester.
  • Wertebereich: min = 0, max = 4294967295 (32-Bit Unsigned Integer).
  • Semantik: Definiert die maximale Anzahl an Bytes der ursprünglichen Diagnoseanforderung (Diagnostic Message), die der DoIP-Stack im Falle einer positiven Bestätigung (Diagnostic Message Positive Acknowledgment, Payload-Typ 0x8002) oder negativen Bestätigung (Diagnostic Message Negative Acknowledgment, Payload-Typ 0x8003) als Nutzlast zurückspiegelt.
  • DoIPTesterSA (EcucIntegerParamDef)
  • Beziehung: Komposition (+parameter) in DoIPTester.
  • Wertebereich: min = 0, max = 65535 (16-Bit Unsigned Integer / ISO 13400-2 Source Address).
  • Semantik: Eindeutige logische Adresse des externen Testers. Dient dem DoIP-Stack als primärer Identifier beim Verbindungsaufbau und zur Adressvalidierung.
  • DoIPRoutingActivationRef (EcucReferenceDef)
  • Beziehung: Komposition (+reference) in DoIPTester.
  • Multiplizität: [1..255]. Jeder konfigurierte Tester muss mindestens eine und darf maximal 255 Routing-Aktivierungen referenzieren.
  • Ziel (+destination): Gerichtet auf DoIPRoutingActivation.
  • DoIPRoutingActivation (EcucParamConfContainerDef)
  • Multiplizität: [0..255]. Zentraler Konfigurationscontainer für Routing-Typen (z. B. Default, WWH-OBD, OEM-spezifisch) sowie Authentifizierungs-/Bestätigungs-Callbacks.

3. Dynamisches Verhalten & Sequenzablauf

Das Metamodell definiert die statische Datenbasis für folgende DoIP-Laufzeitmechanismen (ISO 13400-2 / AUTOSAR DoIP):

```

Externer Tester DoIP-Stack (BSW) PduR / Dcm

| | |

|--- 1. TCP Connect ---------->| |

|--- 2. Routing Activation --->| |

| Req (SA, ActivationType) | |

| |-- 3. Lookup: DoIPTesterSA |

| |-- 4. Check: Ref to Type --|

| | in DoIPRouting- |

|<-- 5. Routing Activation ----| ActivationRef |

| Resp (Success 0x10) | |

| | |

|--- 6. Diagnostic Message --->| |

| (Req Payload) |--- 7. Forward PDU ------->|

|<-- 8. Diag Message Ack ------| |

| (truncated by | |

| DoIPNumByteDiagAckNack) | |

```

  1. SA-Validierung: Bei Empfang einer Routing Activation Request (0x0005) extrahiert der DoIP-Stack die Quelladresse und gleicht sie gegen die generierte DoIPTesterSA-Tabelle ab. Ist die SA unkonfiguriert, wird die Verbindung mit NACK 0x03 (Unknown Source Address) abgewiesen.
  2. Autorisierung der Routing-Aktivierung: Der im Request spezifizierte ActivationType wird gegen die für diesen Tester hinterlegten DoIPRoutingActivationRef-Instanzen geprüft. Bei Übereinstimmung (und ggf. erfolgreichem OEM-Authentifizierungs-Callback via DoIP_RoutingActivationAuthenticationCallback) wird das Routing für diesen Socket aktiviert (0x10 Routing Successfully Activated).
  3. Quittierung von Diagnosenachrichten: Eintreffende Diagnosenachrichten werden validiert. Vor oder nach der Übergabe an den PduR generiert der DoIP-Stack ein positives (0x8002) oder negatives (0x8003) DoIP-Ack. Der Nutzdatenanhang der Quittung wird hart auf den Wert von DoIPNumByteDiagAckNack gekürzt.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Codegenerierung & Speicherlayout:
  • Die Multiplizitäten (DoIPTester [1..255], DoIPRoutingActivationRef [1..255]) steuern direkt die Dimensionierung statischer Look-up-Tabellen (z. B. DoIP_TesterConfigType[]) im generierten Code (DoIP_Cfg.c/.h).
  • Da die SA-Suche im Rx-Pfad zeitkritisch ist, generieren optimierte BSW-Stacks bei großen Tester-Zahlen (bis zu 255) sortierte Arrays für binäre Suche oder direkte Lookup-Indizes statt linearer Iterationen.
  • Pufferallokation (DoIPNumByteDiagAckNack):
  • Obwohl das Metamodell für DoIPNumByteDiagAckNack einen 32-Bit-Maximalwert (4294967295) erlaubt, muss der Konfigurationsingenieur diesen Parameter an die tatsächliche maximale Tx-PDU-Puffergröße des DoIP/SoAd-Treibers anpassen. Übliche Werte in der Praxis liegen im Bereich 0 bis maximal 4..8 Bytes (oft 0 für minimale Buslast). Zu große Werte führen zu unnötiger Pufferreservierung oder Truncation-Warnungen im Stack.
  • Referenzintegrität im ARXML:
  • Jeder DoIPTester erfordert mindestens eine gültige Referenz (lowerMultiplicity = 1) auf einen DoIPRoutingActivation-Container. Ein ARXML-Modell ohne verknüpfte Routing-Aktivierung ist schema-invalid und bricht die Generierungs-Toolchain ab.
  • Adressbereiche (ISO 13400-2):
  • Das Metamodell erlaubt für DoIPTesterSA den vollen 16-Bit-Bereich (0..65535). Entwickler/Integratoren müssen darauf achten, dass Adressen gemäß ISO 13400 (z. B. 0x0000 = reserviert, bestimmte Bereiche für gesetzliche OBD-Tester vs. Werkstatt-Tester) stack- und herstellerspezifisch korrekt vergeben werden; das Metamodell erzwingt hier keine Sub-Range-Prüfung.
