    • Illustriert den methodischen Übergang von einer hersteller- bzw. domänenspezifischen, abstrakten Funktionsarchitektur (Abstract System Description / Functional View, oben) zur standardisierten Software-Architektur des Virtual Function Bus (VFB View, unten).

2. Komponenten, Entitäten & Schnittstellen

Entitäten der Ebenen
  1. Abstract View (Obere Domäne):
    • Funktionale Einheiten: Functionality A, Functionality B, Functionality C, Functionality D (abstrakte Subsysteme/Funktionsknoten ohne Bindung an AUTOSAR-Metamodell-Klassen).
    • Abstrakte Interaktionspunkte: Quadratische Port-Symbole an den Begrenzungen der Funktionsblöcke mit Punkt-zu-Punkt-Wirklinien (gestrichelt):
      • Horizontal: A ↔ B, B ↔ C, C ↔ D.
      • Cross-Coupling (Feedback/Long-Range): A ↔ B (untere Kante) sowie B ↔ D (untere Kante).
  2. VFB View (Untere Domäne):
    • AUTOSAR Software-Komponenten: SW-C 1, SW-C 2, SW-C 3, SW-C 4 (formale Instanzen/Typen von AtomicSoftwareComponentType).
    • VFB-Ports & Connectors: Formal typisierte Ports (PortPrototype: PPortPrototype, RPortPrototype) und deren logische Verbindungen (AssemblySwConnector):
      • Horizontal: SW-C 1 ↔ SW-C 2, SW-C 3 ↔ SW-C 4.
      • Verteilte Verbindungen (untere Kante): SW-C 1 ↔ SW-C 3, SW-C 2 ↔ SW-C 4.
Abbildungsrelationen (Gepunktete Pfeile) & Schnittstellen-Synthese
  • 1:1-Mapping (Isomorphie): Functionality A → SW-C 1. Ports und externe Datenflüsse bleiben strukturell deckungsgleich erhalten.
  • 1:n-Dekomposition (Aufspaltung): Functionality B → SW-C 2 + SW-C 3.
    • Trennung der inneren Logik von Block B auf zwei eigenständige SW-Cs.
    • Aufteilung der Schnittstellen: Die Verbindungen zu A und D werden zwischen SW-C 2 und SW-C 3 aufgeteilt (keine direkte Kopplung zwischen SW-C 2 und SW-C 3 auf horizontaler VFB-Ebene dargestellt).
  • n:1-Aggregation (Konsolidierung / Fusion): Functionality C + Functionality D → SW-C 4.
  • Port-Kapselung & Eliminierung:
    • Die vormals sichtbare Schnittstelle zwischen Functionality C und Functionality D entfällt auf VFB-Ebene vollständig. Sie wird komponentenintern gekapselt (z. B. Inter-Runnable-Variable oder direkter Funktionsaufruf innerhalb derselben SW-C) und existiert nicht als formaler AUTOSAR-Port.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Statisches Struktur- und Transformationsdiagramm; kein Laufzeit-Sequenzablauf über RTE/OS-Tasks.

Entwurfszeitlicher Phasenablauf im Methodology-Prozess:

  1. Definition der Functional Architecture: Definition von Funktionen (Functionality A-D) und Kommunikationspfaden unabhängig von ECU-Allokation oder AUTOSAR-Restriktionen.
  2. Architectural Synthesis & Partitioning: Strukturierung nach Safety-Zielen (ASIL-Dekomposition), Wiederverwendbarkeit, Lieferantenverantwortung oder Echtzeitanforderungen:
    • Aufspaltung komplexer Blöcke (B → SW-C 2, SW-C 3).
    • Zusammenfassung kohärenter Teilfunktionen (C + D → SW-C 4).
  3. Port- und Interface-Resolution:
    • Erzeugung von PortInterfaces (Sender-Receiver / Client-Server).
    • Verwerfen überflüssiger Schnittstellen (C ↔ D) zur Entlastung des VFB-Kommunikationsmodells.
  4. VFB-Validierung: Modellierung der Connectors (AssemblySwConnector) als Eingabe für spätere System Description (System Signal, SwcToEcuMapping).

4. Normative Relevanz & Entwickler-Hinweise

  • Anforderungs-Tracing & RS-Bezug:
    • Umsetzung von RS_METH_00002 (System Design Support), RS_METH_00006 (VFB-Abstraktion) und RS_METH_00033/RS_METH_00078 (Schnittstellendefinition).
    • Tracing von Systemanforderungen darf nicht zwingend eine 1:1-Entsprechung zwischen Use-Case-Funktion und AtomicSoftwareComponentType voraussetzen. Tools müssen n:m-Beziehungen und Port-Verluste abbilden können.
  • Ressourcen- & Performance-Auswirkungen:
    • Overhead-Minimierung durch Aggregation: Das Verschmelzen von Funktionen (C + D → SW-C 4) verhindert unnötigen RTE-Overhead. Anstelle von RTE-APIs (Rte_Read, Rte_Write), Puffern und Task-Aktivierungen erfolgt die Interaktion über lokale Variablen oder InterRunnableVariable (implicitInterRunnableVariable / explicitInterRunnableVariable).
    • Kosten der Dekomposition: Die Aufspaltung (B → SW-C 2, SW-C 3) erhöht die Anzahl der Software-Komponenten-Deskriptoren, Port-Instanzen und bei ECU-interner Trennung die RAM/ROM-Belegung des RTE-Stacks.
  • Konsequenzen für die System- & BSW-Konfiguration:
    • Die VFB-Connectors definieren die Obergrenze der sichtbaren Kommunikation. Erst beim späteren SwcToEcuMapping entscheidet sich, ob die Connectors rein lokal via RTE oder über den BSW-Stack (Com, PduR, CAN/LIN/Ethernet-Treiber) geroutet werden.
    • Komponenteninterne Kommunikation (ehemals C ↔ D) kann nicht nachträglich über Bus-Signale abgegriffen oder auf unterschiedliche ECUs verteilt werden.
