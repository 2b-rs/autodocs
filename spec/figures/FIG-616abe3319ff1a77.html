1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Metamodell-Klassendiagramm (AUTOSAR M2-Ebene aus der AUTOSAR_TPS_ManifestSpecification, Release R22-11).
  • Technischer Zweck: Formale Spezifikation der Kopplung zwischen dem State Management Functional Cluster (StateManagementModuleInstantiation) und den Anwendungs- bzw. Plattformprozessen (Executable, Process). Es definiert, wie Zustands- und Fehleranforderungs-Ports (RPortPrototype) einer Software-Komponente über Kontextpfade («instanceRef») an konkrete Zustandsanforderungen (StateManagementStateRequest) gebunden werden.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Klassifikation
  • StateManagementModuleInstantiation: Repräsentiert die plattformspezifische Instanziierung des State Managements auf einer Machine. Generalisiert aus AdaptiveModuleInstantiation / NonOsModuleInstantiation.
  • StateManagementStateRequest (Identifiable): Abstrahiert eine konkrete Zustands- oder Fehleranforderung, die das State Management entgegennimmt.
  • PortInterface-Hierarchie:
    • PortInterface (abstrakt; ARElement, AtpBlueprint, AtpBlueprintable, AtpType): Basis für alle Schnittstellendefinitionen.
    • ServiceInterface: Standard-Dienstschnittstelle (hier als Kontrast/Abgrenzung abgebildet).
    • StateManagementPortInterface (abstrakt): Spezialisierte Schnittstellenbasis für das State Management.
    • StateManagementRequestInterface (abstrakt): Unterklasse von StateManagementPortInterface, teilt sich auf in:
      • StateManagementTriggerInterface: Dient Applikationen zur Anforderung von Funktionsgruppen-/Zustandswechseln.
      • StateManagementErrorInterface: Dient Applikationen zur Meldung deterministischer Fehler an das State Management.
  • Software-Komponenten- & Ausführungsmodell:
    • RPortPrototype: Konkreter Empfangs-/Client-Port, spezialisiert AbstractRequiredPortPrototype → PortPrototype (AtpBlueprintable, AtpPrototype).
    • SwComponentType (ARElement, AtpBlueprint, AtpBlueprintable, AtpType): Kapselt funktionale Ports.
    • RootSwComponentPrototype (AtpPrototype, Identifiable): Wurzel-Instanziierung der Software-Komponente innerhalb eines Executables.
    • Executable (AtpClassifier, UploadableDesignElement): Kompilierte Binär-/Laufzeiteinheit; spezialisiert nun UploadableDesignElement (Eingliederung in die UCM-/Software-Cluster-Hierarchie für aktualisierbare Entitäten) und AtpClassifier.
    • Process (AbstractExecutionContext): Instanz eines Executable zur Laufzeit im Betriebssystem.
    • ProcessToMachineMapping (Identifiable): Allokiert einen Process auf eine konkrete Zielmaschine.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein strukturelles Metamodell handelt, ist kein Sequenzdiagramm abgebildet. Die zur Laufzeit abgeleitete Interaktionskaskade gestaltet sich wie folgt:

  1. Manifest-Resolution beim Boot/Start: Das Execution Management (EM) und das State Management (SM) werten das Machine- und Execution-Manifest aus. Der vollständige Instanzpfad (ProcessToMachineMapping → Process → Executable → RootSwComponentPrototype → RPortPrototype) löst auf, welcher Port welcher Prozessinstanz an das SM gebunden ist.
  2. Trigger-Pfad (State Transition):
    • Eine Applikation initiiert über ihren typisierten R-Port (StateManagementTriggerInterface) eine Zustandsänderung (z. B. Request eines neuen FunctionGroup-Zustands).
    • Der Request wird plattformintern (IPC/ara::com) an die Instanz des SM geleitet.
  3. Error-Pfad (Deterministic Recovery):
    • Im Fehlerfall meldet die Applikation über einen durch StateManagementErrorInterface typisierten R-Port einen Fehlerzustand.
    • Das SM evaluiert definierte Regeln (Guards) und initiiert ggf. Fallback-Zustände oder Prozess-Restarts.
  4. Synchronisation: Requests an das SM erfolgen standardmäßig asynchron; das SM koordiniert nachfolgend Zustandsübergänge über das Execution Management.

4. Normative Relevanz & Entwickler-Hinweise

  • Vollständigkeit der InstanceReference: Da +stateRequestPort als «instanceRef» modelliert ist, schlägt die Validierung des Manifest-Generators fehl, wenn der Kontextpfad unvollständig ist. Es reicht nicht aus, nur den RPortPrototype zu benennen; der Pfad muss über Process und RootSwComponentPrototype im Kontext des Executables eindeutig aufgelöst sein.
  • Interface-Restriktion: Ports, die für State-Management-Interaktionen deklariert werden, dürfen nicht an allgemeine ServiceInterface gebunden werden, sondern müssen zwingend auf StateManagementTriggerInterface oder StateManagementErrorInterface typisiert sein.
  • Splitability im Build-Prozess: Durch «atpSplitable» an +request und +port können Entwickler die Modulkonfiguration des State Managements (StateManagementModuleInstantiation) unabhängig von der Definition der SWC-Ports (SwComponentType) in separaten ARXML-Dateien pflegen (Separation of Concerns zwischen Applikationsdesign und Deployment/Integration).
  • Variantenmanagement: Durch «atpVariation» am Port können State-Request-Verbindungen abhängig von System-Conditions (z. B. Fahrzeugvarianten oder spezifischen Plattformkonfigurationen) zur Compile-/Link-Zeit gebunden oder deaktiviert werden.
