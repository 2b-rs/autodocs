1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Strukturdiagramm mit dreistufiger horizontaler Abstraktionsschichtung (UML-Klassendiagramm-Notation zur Gegenüberstellung von Konzept-, Definitions- und Werteebene).
  • Technischer Zweck: Spezifikation des URI-basierten Referenzierungsmechanismus im EcuC-Metamodell (AUTOSAR_CP_TPS_ECUConfiguration).
  • Funktionale Einordnung: Standard-EcuC-Referenzen basieren auf statischen Pfaden (shortName-Pfad zum Ziel-Containertyp). Die URI-Indirektion entkoppelt Referenzquelle und Referenzziel auf Definitionsebene, wenn:
  • die genaue Metamodell-Position des Ziel-Containertyps dem Quellmodul zur Definitionszeit unbekannt ist,
  • die Anzahl möglicher Zieltypen dynamisch/erweiterbar ist,
  • das Ziel gegen andere Parametertypen austauschbar sein muss, ohne die Definition des Quellmoduls anzupassen.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in drei vertikal korrespondierende Schichten:

#### 1. Conceptual Level (Konzeptionelle Ebene)

  • Owner of the reference: Logischer Ursprung der Referenzbeziehung.
  • Target of the reference: Logisches Ziel der Referenzbeziehung.
  • URI: Abstrakter Bezeichner (Uniform Resource Identifier), der als lose gekoppeltes Matching-Kriterium zwischen Owner und Target dient.

#### 2. ECU Configuration Parameter Definition (Metamodell- / Definitions-Ebene)

  • EcucParamConfContainerDef (links): Container-Definition des Referenz-Owners.
  • Aggregiert (Composition ♦—>) die Referenzdefinition EcucUriReferenceDef.
  • EcucUriReferenceDef: Spezialisierte Referenzdefinition.
  • Besitzt eine gerichtete Assoziation (—>) zu EcucDestinationUriDef.
  • EcucDestinationUriDef (zentral): EcuC-Metamodell-Element, das die Ziel-URI kapselt. Fungiert als Bindeglied/Typanker.
  • EcucParamConfContainerDef (rechts): Container-Definition des Referenz-Ziels.
  • Besitzt eine gerichtete Assoziation (—>) zur selben EcucDestinationUriDef.

#### 3. ECU Configuration Value Description (Instanz- / Werte-Ebene)

  • EcucContainerValue (links): Konfigurationsinstanz des Referenz-Owners (typisiert über Definitionspfeil nach oben auf den linken EcucParamConfContainerDef).
  • Aggregiert (Composition ♦—>) den Wert EcucReferenceValue.
  • EcucReferenceValue: Konkreter Referenzwert (typisiert über EcucUriReferenceDef).
  • Besitzt eine direkte gerichtete Assoziation (—>) auf den Ziel-EcucContainerValue.
  • EcucContainerValue (rechts): Konfigurationsinstanz des Referenz-Ziels (typisiert über den rechten EcucParamConfContainerDef).

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Das Diagramm modelliert kein ECU-Laufzeitverhalten, sondern den statischen Auflösungsprozess in der Konfigurations-Toolchain (Design-/Generierungszeit):

  1. Definitionsphase (BSW-Modulpaketierung):
  • Modulentwickler definieren Quell- (EcucUriReferenceDef) und Zielcontainer (EcucParamConfContainerDef), die jeweils unabhängig auf dieselbe EcucDestinationUriDef verweisen.
  1. Konfigurationsphase (ECU-Integration):
  • Integrator instanziiert Owner (EcucContainerValue) und Target (EcucContainerValue).
  1. URI-Matching & Referenzauflösung (EcuC-Toolchain):
  • Das EcuC-Autorensystem matcht Owner und Target über die gemeinsame URI der zugrundeliegenden Definitionen.
  1. Instanzierung der Wert-Referenz:
  • Auf Wertebene wird die Indirektion aufgelöst: EcucReferenceValue verweist im finalen ARXML-Datensatz direkt auf die Zielinstanz EcucContainerValue (konkreter Pfadverweis).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW- & Stack-Entwickler:
  • Verwendung primär bei modulintegrierenden Abstraktionen (z. B. Crypto-Stack, SecOC, Diagnostic-Stack, PduR-Routen), bei denen ein Modul Daten/Dienste eines anderen konsumiert, ohne dessen exakte Containerstruktur fest im Metamodell zu verdrahten.
  • ECU-Integratoren & Toolchain-Anbieter:
  • Validierungsregeln müssen sicherstellen, dass die im EcucReferenceValue referenzierte Ziel-Instanz tatsächlich von einem Container abgeleitet ist, dessen Definition auf die spezifizierte EcucDestinationUriDef verweist.
  • Mehrdeutigkeiten (mehrere valide Ziele für dieselbe URI) müssen durch zusätzliche Filterkriterien oder manuelle Zuordnung im EcuC-Editor behandelt werden.
  • Embedded-Laufzeitauswirkung:
  • Zero-Runtime-Overhead: Auf Target-Ebene (C-Code) existiert keine URI-Auflösung. Der BSW-Codegenerator übersetzt die im EcucReferenceValue aufgelöste direkte Assoziation wie gewohnt in statische C-Pointer, PDU-IDs oder Array-Indizes in den generierten Konfigurationsstrukturen (_PBcfg.c / _Cfg.h).

Known use cases for an extended reference mechanism are: • The position of the target type is unknown to the owner of the reference. • The owner of the reference does not know in advance how many target types for the reference exist. • The target type of the reference needs to be replaced without the necessity to update the owner of the reference. The solution for these requirements is to not base the reference on the shortName path of the reference target. Instead, the reference target and the reference owner get together via an URI-based indirection mechanism, such that the match is created if both the owner of the reference and the reference target refer to the identical URI (and fulfill further conditions described below).
