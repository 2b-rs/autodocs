Figure 21: Implicit update/restore of RAM blocks 12.2.3.2 Explicit Update and Restore of RAM Mirror See Figure 22. This is a summary of use cases in which the client explicitly requests to save or restore the content of a mirror RAM block from/to non-volatile memory (e.g. in order to decrease the risk of data loss). But as in the first case, RAM blocks are permanently associated with their counterparts in NVRAM. Now we need direct communication (in the sense of the VFB) between the NvM module and its client. Also in this case, the NvM module does NOT communicate with its client via the RAM blocks. In this case, the client must use an AUTOSAR interface to communicate with the service. Similar to the case of implicit update/restore, we need certain contracts between the client and the NvM module: On the size, identification and maybe further properties of the RAM/NVRAM blocks which have to be known on both sides. For the access of the RAM mirror via the RTE see 12.4. On the states (of the ECU and/or the client component) in which the client may request to restore or save RAM blocks. For this contract, it is essential that the client is informed about its activation/termination or relevant ECU states. This communication path has to be handled by the RTE in cooperation with the ECU State Manager (not visible in Figure 22). During the explicit update and restore scenarios, the client has to follow certain rules, e.g. not to access a RAM block before the update or restore is finished.

1. Diagrammtyp & Architektur-Kontext

Konzeptionelles Architektur- und Datenflussdiagramm der AUTOSAR Classic Platform (SWS NVRAM Manager). Das Diagramm veranschaulicht das Zusammenspiel zwischen Applikationsebene (AUTOSAR SW-Component), Laufzeitumgebung (RTE) und Basissoftware (NVRAM Manager, System Management) beim Entwurfsmuster der impliziten Synchronisation (Implicit Update/Restore) von permanenten RAM-Blöcken. Es dient der Abgrenzung zur expliziten NVRAM-Nutzung über Client-Server-Service-Ports.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert vier Hauptkomponenten und eine Trennschicht:

  • AUTOSAR SW-Component: Anwendungskomponente oberhalb der RTE.
  • RTE: Runtime Environment, dargestellt als gestrichelte Trennschicht zwischen Anwendungs- und BSW-Ebene.
  • RAM block: Mehrfach instanziierte, permanente RAM-Puffer (Kartenstapel-Darstellung), die jeweils fest einem nichtflüchtigen Speicherblock zugeordnet sind.
  • NVRAM Manager: BSW-Speicherdienst zur Verwaltung und Abwicklung nichtflüchtiger Lese- und Schreiboperationen.
  • Other parts of basic SW: Systemsteuernde BSW-Module (insbesondere EcuM / BswM).

Schnittstellen und Interaktionspfade:

  • Direkter Datenzugriffspfad: „Access content of RAM blocks“ von AUTOSAR SW-Component auf RAM block.
  • BSW-Steuerpfad: „Initialize; Request to restore/save all blocks depending on ECU state“ von Other parts of basic SW an den NVRAM Manager.
  • BSW-Datenpfad: „Restore/save all blocks from/to non-volatile medium“ zwischen NVRAM Manager und RAM block.

3. Dynamisches Verhalten & Sequenzablauf

Der Ablauf gliedert sich in drei phasengesteuerte Schritte:

  1. Start-up-/Restore-Phase: Die Systemsteuerung (Other parts of basic SW, z. B. EcuM) initialisiert den NVRAM Manager und fordert zustandsabhängig das Wiederherstellen aller Blöcke an (z. B. via NvM_ReadAll). Der NVRAM Manager liest die persistenten Daten aus dem NV-Medium und befüllt die permanenten RAM-Blöcke.
  2. Betriebsphase (Runtime): Die AUTOSAR SW-Component greift während der regulären Ausführung direkt auf die Inhalte der RAM-Blöcke zu. Es findet dabei keine direkte Interaktion oder Signalisierung zwischen SW-Component und NVRAM Manager statt.
  3. Shutdown-/Save-Phase: Beim Herunterfahren der ECU fordert die Systemsteuerung (z. B. BswM/EcuM) das Speichern aller Blöcke an (z. B. via NvM_WriteAll). Der NVRAM Manager überträgt die aktuellen Inhalte der permanenten RAM-Blöcke auf das nichtflüchtige Speichermedium.

4. Normative Relevanz & Entwickler-Hinweise

Entwicklungs- und Integrationshinweise für den AUTOSAR-Entwickler:

  • Portlose Kopplung: Die SW-Component benötigt für dieses Muster keine AUTOSAR-Service-Ports (NvM_Service / NvM_Admin) zum NvM; die Bindung erfolgt rein über die Adressierung des konfigurierten permanenten RAM-Blocks (NvMRamBlockDataAddress).
  • Datenkonsistenz und Race Conditions: Da kein exklusiver Zugriffsmechanismus über RTE-Ports visualisiert ist, muss durch die ECU-Zustandsverwaltung (EcuM/BswM) und Task-Scheduling sichergestellt werden, dass die SW-Component nicht auf den RAM-Block zugreift, solange NvM_ReadAll oder NvM_WriteAll aktiv sind, um Dateninkonsistenzen (Tearing) zu verhindern.
  • Konfigurationsvorgaben: Datentyp und Speichergröße müssen zwischen SW-Component-Header und BSW-Konfiguration (NvMNvramBlockIdentifier, Blockgröße, CRC-Nutzung) exakt übereinstimmen.
  • Abgrenzung: Dieses implizite Modell eignet sich für zyklisch/beim Start bereitgestellte Daten, nicht jedoch für bedarfsgesteuerte, transaktionale Zwischenspeicherungen zur Laufzeit (hierfür ist der explizite RAM-Mirror-Ansatz erforderlich).
