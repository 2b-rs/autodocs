1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration Parameter Definition Metamodell (UML-Klassendiagramm gemäß AUTOSAR BSW-Konfigurationsstandard).
  • Technischer Zweck: Definition der statischen Konfigurationsstruktur für die Filterung auf Sicherungsschicht-Ebene (OSI Layer 2 / IEEE 802.3 & 802.1Q) innerhalb des AUTOSAR Classic Platform BSW-Moduls Firewall (Fw).
  • Funktionale Einordnung: Konkretisiert Regelsätze (FirewallRule, SWS-Kontext R23-11) für Ethernet-Frames. Ermöglicht die deterministische Filterung eingehender oder weitergeleiteter Frames anhand von MAC-Adressen (inklusive Bitmaskierung), VLAN-Tags und EtherTypes vor der Weiterreichung an höhere Stack-Schichten (z. B. TcpIp, SoAd) oder Switch-Forwarding-Instanzen.

2. Komponenten, Entitäten & Schnittstellen

Container & Hierarchien (Komposition via +subContainer)
  • FirewallRule (EcucParamConfContainerDef):
    • Multiplizität: [1..*]
    • Oberste Konfigurationsentität für eine einzelne Firewall-Regel.
  • FirewallDataLinkFilterConfig (EcucParamConfContainerDef):
    • Multiplizität: [0..1] relativ zu FirewallRule.
    • Aggregiert sämtliche L2-spezifischen Filterkriterien einer Regel (ECUC_Fw_00017).
  • FirewallFilterMACSrcAddress (EcucParamConfContainerDef):
    • Multiplizität: [0..1]. Kapselt Quell-MAC-Filterkriterien.
  • FirewallFilterMACDestAddress (EcucParamConfContainerDef):
    • Multiplizität: [0..1]. Kapselt Ziel-MAC-Filterkriterien.
Parameter (+parameter)
  • MAC-Filterung (in FirewallFilterMACSrcAddress und FirewallFilterMACDestAddress):
    • FirewallFilterMACAddressKey (EcucStringParamDef): Exakte Bitmuster-Referenz (Standard IEEE 802 Canonical Format: XX:XX:XX:XX:XX:XX).
      • Validierung: regularExpression = ([0-9a-fA-F]{2}:){5}[0-9a-fA-F]{2}, minLength = 17, maxLength = 17.
    • FirewallFilterMACAddressMask (EcucStringParamDef): Bitmaske zur Selektion relevanter Bits (z. B. für OUI-/Multicast-Matching oder Wildcards).
      • Validierung: identische Regex/Längenbeschränkung wie Key (minLength = 17, maxLength = 17).
  • Ethernet- & VLAN-Felder (in FirewallDataLinkFilterConfig):
    • FirewallFilterEtherType (EcucIntegerParamDef):
      • Multiplizität: [0..1], Wertebereich: 0 .. 65535 (16-Bit EtherType, z. B. 0x0800 IPv4, 0x86DD IPv6, 0x22F0 AVTP).
    • FirewallFilterVlanId (EcucIntegerParamDef):
      • Multiplizität: [0..1], Wertebereich: 0 .. 4094 (12-Bit IEEE 802.1Q VID; 4095 ist reserviert).
    • FirewallFilterVlanPriority (EcucIntegerParamDef):
      • Multiplizität: [0..1], Wertebereich: 0 .. 7 (3-Bit Priority Code Point / PCP gemäß IEEE 802.1p/Q).

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein Metamodell der Konfigurationsebene (ECUC) handelt, liegt kein Laufzeit-Sequenzdiagramm vor. Das abgeleitete Laufzeitverhalten des Firewall-Evaluierungs-Engines gestaltet sich wie folgt:

  1. Ingress Frame Trigger: Empfang eines L2-Frames über EthIf (EthIf_RxIndication).
  2. Kaskadierte Auswertung (Konjunktion innerhalb einer Regel):
    • Ist FirewallDataLinkFilterConfig konfiguriert, wird ein boolesches UND über alle vorhandenen Sub-Elemente gebildet: $$\text{Match} = \text{Match}_{\text{SrcMAC}} \land \text{Match}_{\text{DestMAC}} \land \text{Match}_{\text{VLAN\_ID}} \land \text{Match}_{\text{VLAN\_Prio}} \land \text{Match}_{\text{EtherType}}$$
    • MAC-Matching-Operation: $$(\text{Frame\_MAC} \mathbin{\&} \text{Mask}) == (\text{Key} \mathbin{\&} \text{Mask})$$
  3. Regel-Aktion & Abbruchbedingung:
    • Bei vollständigem Match greift die in FirewallRule definierte Aktion (ALLOW, DROP, ggf. Sicherheits-Logging/Dem-Event).
    • Bei Nicht-Übereinstimmung (Mismatch) wird die nächste Regel der Prioritätskette evaluiert; Default-Greifen der konfigurierten Fallback-Policy (z. B. Implicit Deny).

4. Normative Relevanz & Entwickler-Hinweise

  • Codegenerator-Einfluss:
    • Zeichenketten der MAC-Parameter (FirewallFilterMACAddressKey / Mask) müssen vom BSW-Generator in 6-Byte-Array-Initialisierer (uint8[6]) transformiert werden, um Laufzeit-Parsing auf dem Embedded-Target zu vermeiden.
    • Multiplizität [0..1] erfordert generierte Bitmasken oder Präprozessor-Switches (#if defined ...), um inaktive Filterkriterien im Fast-Path ohne CPU-Overhead zu überspringen.
  • Hardware-Offloading vs. Software-Filterung:
    • Sofern der Ethernet-Switch/-Controller über Hardware-TCAMs oder Frame-Filter-Register verfügt, dient diese Struktur direkt als Mappingspezifikation für Hardware-Filtertabellen.
  • Spezifikationsgrenzen & Restriktionen:
    • VLAN-ID 4095 ist normativ ausgeschlossen (max = 4094).
    • Untagged vs. Tagged Frames: Fehlt FirewallFilterVlanId, ist die Regel unabhängig vom VLAN-Header gültig oder ignoriert diesen. Ist FirewallFilterVlanId gesetzt, verwerfen Implementierungen untagged Frames implizit auf Regelebene.
