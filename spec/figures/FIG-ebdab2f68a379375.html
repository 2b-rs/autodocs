1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: VFB-Architekturdiagramm / UML-Komponentendiagramm (Strukturansicht der Virtual Functional Bus-Ebene).
  • Technischer Zweck: Modellierung der Kapselung und Bereitstellung globaler/öffentlicher Kalibrierparameter (Public Calibration Parameters) für eine Software-Komponente über einen dedizierten Parameter-Komponententyp im statischen Einzelfall (Pure single instantiation).
  • Funktionale Einordnung: Verortung auf VFB-Ebene innerhalb eines gemeinsamen Steuergeräte-Kontexts (Context of an ECU). Dient der sauberen Entkopplung von Applikationslogik und Parametrierungs-/Kalibrierdaten (z. B. für ASAM MCD-2 MC / A2L-Mess- und Verstellsysteme via XCP).

2. Komponenten, Entitäten & Schnittstellen

  • Entitäten:
    • <<ParameterSwComponentType>> : Prm: Spezieller AUTOSAR-Komponententyp zur Strukturierung und Speicherung kalibrierbarer Daten. Enthält keine Ausführungslogik (Internal Behavior besitzt keine ausführenden RunnableEntitys, Tasks oder OS-Events).
    • <<SoftwareComponentType>> : SWC: Konsumierende funktionale Komponente (typischerweise ApplicationSwComponentType oder ComplexDeviceDriverSwComponentType).
    • Context of a ECU: ECU-Kompositionsebene (EcuAbstractionSwComponentType / CompositionSwComponentType auf Steuergeräteebene), die die gemeinsame Allokation auf derselben physischen Hardware erzwingt.
  • Ports & Schnittstellen:
    • P-Port (Prm): Provide-Port (dargestellt als quadratischer Port mit auswärts gerichtetem Dreieck), typisiert über ein ParameterInterface.
    • R-Port (SWC): Require-Port (dargestellt als quadratischer Port mit einwärts gerichtetem Dreieck), kompatibel zum ParameterInterface des P-Ports.
    • Konnektor: AssemblySwConnector verbindet den P-Port der Parameter-SWC direkt mit dem R-Port der Ziel-SWC (1:1-Kardinalität im vorliegenden Fall).
  • Metamodell-Beziehungen:
    • Sowohl ParameterSwComponentType als auch SoftwareComponentType leiten im Meta-Modell von SwComponentType ab.
    • Das genutzte PortInterface kapselt mindestens einen ParameterDataPrototype.

3. Dynamisches Verhalten & Sequenzablauf

  • Kein dynamischer Kontrollfluss:
    • Da ParameterSwComponentType ausschließlich Speicherbereiche (ROM/Flash oder kalibrierbaren RAM) repräsentiert, existiert kein dynamischer Nachrichtenfluss, kein RPC und kein aktiver Prozessorkontext.
    • Es werden weder OS-Tasks noch Runnables getriggert; Callbacks (Det/Dem) existieren auf dieser Abstraktionsebene nicht.
  • Zugriffspfad:
    • Der Zugriff erfolgt synchron bei Ausführung einer RunnableEntity innerhalb von SWC über direkten Speicherzugriff, aufgelöst durch die RTE.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-API-Vertrag:
    • Applikationsseitiger Zugriff im C-Code erfolgt über die RTE-API: 
      /* Direkter Lesezugriff auf den Parameter */
Rte_Prm_<PortName>_<ParameterName>()
      (Wird vom RTE-Generator je nach Speicherkonfiguration als Makro-Zugriff auf eine const-Variable oder als Funktionsaufruf generiert).
  • Speicherzuweisung & Memory Mapping:
    • Parameter der ParameterSwComponentType erfordern die Zuordnung zu dedizierten Kalibriersegmenten über SwAddrMethod und das AUTOSAR-Speicherkonzept (MemMap.h, z. B. #pragma section für Flash, calRAM oder Emulations-RAM für Verstellkonzepte wie Shared Memory oder Page Switching).
  • Architektur-Einschränkungen:
    • Strikte ECU-Lokalität: Ein ParameterSwComponentType kann nicht netzwerkweit über den COM-Stack verteilt werden. Provide- und Require-Ports für Parameter-Interfaces sind zwingend auf denselben ECU-Context beschränkt (AssemblySwConnector anstelle von DelegationSwConnector zu Com-Signalen).
    • Schreibschutz: Für die konsumierende SWC ist der Parameterzugriff normativ rein lesend (read-only). Eine Modifikation durch die Applikation ist unzulässig; Änderungen erfolgen ausschließlich extern über Kalibriertools (z. B. via CANape/INCA über XCP).

Begleitender Spezifikationstext:

Virtual Functional Bus AUTOSAR CP R25-11 data is made available via the provide port of the parameter software component to a corresponding require port of any software component (compatibility rules do apply). Since in this model the parameters are visible on the virtual bus, parameter software components are the way to express public calibration parameters. Depending on whether the corresponding components are instantiated or not, several different cases can be distinguished, described in the following sections. 10.1.1.1 Pure single instantiation Figure 10.1 shows the simplest case, where a software component has access to a particular set of calibration parameters by ’receiving’ them via a connection from a providing parameter software component. Figure 10.1: A software component has access to a calibration parameter encapsulated in a parameter software component It should be noted here that the parameter software components and software components connected are residing per se on the same ECU. Actually, the parameter software components are only representing memory containing the encapsulated (calibration) parameter. 10.1.1.2 Multiple instantiation of the involved software components Figure 10.2 and Figure 10.3 depict the case, where several software components (instances) of the same or of different component-type have access to the same set of (calibration) parameters. 103 of 131 Document ID 56: AUTOSAR_CP_TR_VFB
