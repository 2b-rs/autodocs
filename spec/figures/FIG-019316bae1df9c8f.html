1. Diagrammtyp & Architektur-Kontext

Das Diagramm ist ein UML-Klassendiagramm auf Metamodell-Ebene (M2) aus dem Dokument AUTOSAR_SystemTemplate (Kapitel CAN / Fibex4Can Topology). Es beschreibt den Architektur-Kontext der CAN-Bustopologie innerhalb des AUTOSAR-System-Templates. Der Metamodell-Ausschnitt definiert die Spezialisierung generischer FIBEX- bzw. AUTOSAR-Kerntopologie-Klassen (CoreTopology::CommunicationCluster, CoreTopology::CommunicationController) für klassische CAN-Kommunikationsnetzwerke sowie die strukturelle Anbindung von CAN-Controller-Bit-Timing-Konfigurationen und CAN-Netzwerkmanagement-Parametern (AUTOSAR CanNm).

2. Komponenten, Entitäten & Schnittstellen

Das Klassendiagramm umfasst folgende Komponenten, Klassen und Assoziationen:

  • FibexElement: Basisklasse für Metamodellelemente des FIBEX-Topologiemodells.
  • CoreTopology::CommunicationCluster (erbt von FibexElement): Repräsentiert ein generisches Kommunikationsnetz/Cluster. Attribute: maxFrameLength: Int [0..1], nmNodeDetectionEnabled: Boolean, nmNodeIdEnabled: Boolean, nmRepeatMessageSupport: Boolean, protocolName: String [0..1], protocolVersion: String [0..1], speed: Int [0..1].
  • CanCluster (spezialisiert CommunicationCluster): CAN-spezifisches Cluster mit CanNm- und Bus-Parametern: nmBusLoadReductionActive: Boolean, nmBusLoadReductionEnabled: Boolean, nmImmediateRestartEnabled: Boolean [0..1], nmLowerCanId: Int [0..1], nmMsgCycleTime: Float [0..1], nmRemoteSleepIndicationTime: Float [0..1], nmRepeatMessageStateTime: Float, nmTimeoutTime: Float, nmUpperCanId: Int [0..1], nmWaitBusSleepTime: Float.
  • Identifiable: AUTOSAR-Basisklasse für identifizierbare Elemente mit Kurznamen.
  • CoreTopology::CommunicationController (erbt von Identifiable): Generische Steuereinheit für Kommunikationsverbindungen auf Steuergeräteebene. Attribut: wakeUpByControllerSupported: Boolean.
  • CanCommunicationController (spezialisiert CommunicationController): CAN-spezifischer Kommunikationscontroller mit Attributen für das Controllereigene NM-Verhalten: nmMsgCycleOffset: Float [0..1], nmMsgReducedTime: Float [0..1], nmUserDataEnabled: Boolean [0..1].
  • AbstractCanCommunicationControllerAttributes: Abstrakte Basisklasse für Bit-Timing-Eigenschaften; angebunden an CanCommunicationController über eine gerichtete Komposition mit der Rollenbezeichnung +canControllerAttributes und der Kardinalität 1.
  • CanControllerConfiguration (spezialisiert AbstractCanCommunicationControllerAttributes): Konkrete Bit-Timing-Parameter des CAN-Controllers: numberOfSamples: Int [0..1], propagationDelay: Int [0..1], syncJumpWidth: Int, timeSeg1: Int, timeSeg2: Int.
  • CanControllerConfigurationRequirements (spezialisiert AbstractCanCommunicationControllerAttributes): Vorgabebereiche und Anforderungen an das Bit-Timing: maxNumberOfTimeQuantaPerBit: Int [0..1], maxSamplePoint: Float [0..1], maxSyncJumpWidth: Float [0..1], minNumberOfTimeQuantaPerBit: Int [0..1], minSamplePoint: Float [0..1], minSyncJumpWidth: Float [0..1].

3. Dynamisches Verhalten & Sequenzablauf

Obgleich es sich um ein statisches Metamodell handelt, parametrisieren die Klassen das dynamische Verhalten der AUTOSAR-Basissoftware (BSW):

  • CAN Network Management (CanNm): Das Zusammenspiel von CanCluster und CanCommunicationController bestimmt das Zustands- und Sendezeitverhalten des CAN-Netzwerkmanagements. nmRepeatMessageStateTime definiert die Verweildauer im Zustand Repeat Message. nmMsgCycleTime steuert das periodische Aussenden der NM-Botschaften, wobei nmMsgCycleOffset controllerspezifisch ein Phasen-Offset zur Buslastvermeidung vorgibt. nmBusLoadReductionEnabled bzw. nmBusLoadReductionActive triggern bei Aktivierung das Umschalten auf die verlängerte Zykluszeit nmMsgReducedTime. Timeouts im Netzwerkbetrieb werden über nmTimeoutTime und nmRemoteSleepIndicationTime überwacht. Das Herunterfahren des Busses in den Sleep-Modus erfolgt verzögert über nmWaitBusSleepTime, während nmImmediateRestartEnabled einen unmittelbaren Wiederanlauf aus dem Vorbereitungszustand ermöglicht. Der NM-Botschaftsbereich wird über nmLowerCanId und nmUpperCanId adressiert.
  • Physikalische Bit-Synchronisation: CanControllerConfiguration steuert das deterministische Abtast- und Synchronisationsverhalten des CAN-Controllers auf Bitebene (Aufteilung des Bitintervalls in SYNC_SEG, PROP_SEG, PHASE_SEG1 und PHASE_SEG2 sowie Resynchronisation mittels syncJumpWidth).

4. Normative Relevanz & Entwickler-Hinweise

  • Verbindliche Metamodell-Struktur für die AUTOSAR-Systembeschreibung (System Extract / System Description) zur formalen Definition von CAN-Bussen und CAN-Controllern.
  • Die Parameter werden in nachgelagerten Toolketten zur automatischen Konfiguration der BSW-Module Can, CanIf und CanNm in die ECU-Konfiguration (ECUC) transformiert.
  • Die Komposition +canControllerAttributes 1 erzwingt, dass an jedem CanCommunicationController exakt eine Konfigurationsinstanz angebunden sein muss – entweder als voll auskonfigurierte Instanz (CanControllerConfiguration) oder als Anforderungsprofil (CanControllerConfigurationRequirements).
  • CanControllerConfigurationRequirements dient Systemintegratoren und Synthese-Tools dazu, Bit-Timing-Bereiche zu spezifizieren, aus denen konkrete Bit-Timing-Registereinstellungen unter Berücksichtigung der Controller-Quarzfrequenz und der geforderten Abtastpunkte (Sample Points) rechnerisch ermittelt werden.
