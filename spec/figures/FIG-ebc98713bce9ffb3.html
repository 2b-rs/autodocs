1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: API-zu-PDU-Mapping-Diagramm / Serialisierungs-Layout (Projektion einer C-Funktionssignatur auf eine Netzwerk-PDU).
  • Funktionale Einordnung: AUTOSAR Classic Platform, BSW-Modul SomeIpXf (SOME/IP Transformer) gemäß AUTOSAR_SWS_SOMEIPTransformer (R4.2.2 / R4.3.1).
  • Technischer Zweck: Visualisierung des Serialisierungsvorgangs bei einer Client/Server-Kommunikation. Das Diagramm definiert, wie die RTE-seitigen Aufrufparameter der generierten Transformer-API SomeIpXf_<XfId>() in den linearen Byte-Stream einer SOME/IP-Request-PDU (Header + Payload) transformiert werden, bevor die Übergabe an die unteren Kommunikationsschichten (Com / LdCom / PduR / SoAd) erfolgt.

2. Komponenten, Entitäten & Schnittstellen

  • C-Transformations-Schnittstelle (SomeIpXf_<XfId>):
    • *transactionHandle: Zeiger auf Transaktions-Metadaten; liefert die Kontextinformationen für die Request ID (Zusammensetzung aus Client ID und Session ID) im SOME/IP-Header.
    • *buffer: Zeiger auf den zusammenhängenden Speicherbereich der Ziel-PDU (nimmt Header und Payload auf).
    • *bufferLength: In/Out-Parameter für die maximal verfügbare bzw. tatsächlich serialisierte PDU-Länge in Bytes.
    • IN/INOUT argument1 … IN/INOUT argumentN: Übergabeparameter der aufgerufenen ClientServerOperation.
  • PDU-Layout (Zielstruktur im Speicher):
    • SOME/IP Header: Fester 16-Byte-Protokollkopf (Message ID, Length, Request ID, Protocol Version, Interface Version, Message Type = 0x00 [REQUEST], Return Code = 0x00).
    • Payload: Konkatenierter Datenbereich unmittelbar anschließend an das 16. Header-Byte.
  • Metamodell-Beziehungen & Kardinalitäten:
    • Quelle: ClientServerOperation aggregiert geordnet $0..\ast$ ArgumentDataPrototype.
    • Richtungsfilter: Gemäß [SWS_SomeIpXf_00120] werden ausschließlich Argumente mit der Direction IN oder INOUT in die Request-Payload serialisiert. Argumente mit Direction OUT werden ignoriert (sie sind exklusiver Bestandteil der Server-Response).
    • Ordnungsrelation: Die Positionierung in der Payload entspricht 1:1 der deklarierten Index-Reihenfolge der ArgumentDataPrototype-Elemente im Software-Component-Template (ARXML).

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger: Aufruf einer netzwerkgebundenen Server-Operation durch ein Client-SWC (Rte_Call_<p>_<o>). Die RTE delegiert die Serialisierung an SomeIpXf_<XfId>().
  2. Header-Generierung:
    • Ermittlung der Interface Version aus SOMEIPTransformationISignalProps (Fallback: SOMEIPTransformationDescription).
    • Zuweisung Message Type = 0x00 (REQUEST), Return Code = 0x00.
    • Mapping der transactionHandle-Werte in das Header-Feld Request ID (Client-ID / Session-ID zur Korrelation der Antwort).
  3. Payload-Serialisierung ([SWS_SomeIpXf_00120]):
    • Iteration über alle IN- und INOUT-Parameter von 1 bis N.
    • Direktes Schreiben der atomaren bzw. komplexen Datentypen in den Puffer ab Byte-Offset 16 unter Beachtung von Endianness (Netzwerk-Byteorder / Big-Endian) und typabhängigem Alignment/Padding.
  4. Abschluss & Längenberechnung:
    • Berechnung des Feldes Length im SOME/IP-Header (Payload-Länge + 8 Bytes für den verbleibenden Header ab Request-ID).
    • Aktualisierung von *bufferLength mit der Gesamtgröße (Payload + 16 Bytes).
  5. Abbruchbedingungen:
    • Ist der durch *bufferLength übergebene Puffer kleiner als die zu serialisierende Gesamtlänge, bricht der Transformer ab und liefert einen Fehlercode (z. B. E_SER_MALFORMED_MESSAGE / Transformer-spezifischer Overflow-Rückgabewert).

4. Normative Relevanz & Entwickler-Hinweise

  • Strikte Positionalität (Kein TLV im Request): SOME/IP überträgt Argumente positional ohne implizite Typ- oder Tag-Information. Client und Server müssen dieselbe ARXML-Reihenfolge der ArgumentDataPrototypes kompilieren; Vertauschungen führen zu Payload-Korruption ohne Erkennung auf Protokollebene.
  • Pufferallokation (RTE / Com-Stack): Der an SomeIpXf_<XfId> übergebene Puffer muss statisch auf Worst-Case-Größe (16-Byte-Header + Maximalgröße aller dynamischen Datentypen wie variabler Strings oder Arrays) ausgelegt sein.
  • Filterung von OUT-Argumenten: Embedded-Entwickler dürfen bei manueller Schnittstellenverifikation oder Stubbing keine Dummy-Bytes für OUT-Parameter im Request erwarten; die PDU enthält ausschließlich IN/INOUT.
  • Rückspiegelung bei Server-Response ([SWS_SomeIpXf_00107], [SWS_SomeIpXf_00200]): Der Server-Transformer erzeugt die Response spiegelbildlich: Payload enthält hier nur INOUT- und OUT-Argumente sowie ggf. den Anwendungs-Rückgabewert. Erreicht der Return-Wert ≥ 0x80 (csErrorReaction == autonomous), entfällt die reguläre Argument-Payload zugunsten einer standardisierten SOME/IP-Error-Response ([SWS_SomeIpXf_00201]).
