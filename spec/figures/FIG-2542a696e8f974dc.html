1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Logisches Systemarchitektur-Diagramm / Blockschaltbild (funktionale Komponentensicht und Protokoll-Routing-Ebene).
  • Kontext: AUTOSAR Adaptive Platform (AP) im Zusammenspiel mit AUTOSAR Classic Platform (CP), fahrzeuginternen High-Performance Computern (HPCs) sowie externen On-Board- und Off-Board-Diagnose-Clients gemäß ASAM SOVD / AUTOSAR EXP SOVD (R22-11).
  • Technischer Zweck: Spezifikation der zentralen Referenzarchitektur für serviceorientierte Fahrzeugdiagnose (Service-Oriented Vehicle Diagnostics, SOVD). Das Diagramm definiert den einheitlichen RESTful-/API-basierten Diagnosezugang (HTTP/JSON, WebSockets) für heterogene E/E-Architekturen, entkoppelt Clients von fahrzeuginternen Netzwerk- und Protokollgrenzen und etabliert das Routing zwischen nativen AP-Diensten, HPC-zu-HPC-Kommunikation und Legacy-UDS-Steuergeräten.

3. Dynamisches Verhalten & Sequenzablauf

  1. Request-Ingress & Autorisierung:
  • Ein Diagnose-Client initiiert einen synchronen REST-Call (GET, PUT, POST, DELETE).
  • Remote-Pfad: Zugriff via Backend Connectivity $\rightarrow$ Validierung des Träger-Tokens/mTLS $\rightarrow$ Weiterleitung an das SOVD Gateway.
  • Proximity-Pfad: Direkter Verbindungsaufbau zum SOVD Gateway über das Fahrzeug-Diagnose-LAN.
  1. Pfad-Auflösung & Dispatching durch das SOVD Gateway:
  • Pfad A (Lokale Adaptive Services):
  • URI adressiert den lokalen Host $\rightarrow$ Weiterleitung an den Diagnostic Manager (ara::diag).
  • Der Diagnostic Manager führt session-/state-relevante Vorprüfungen durch und ruft über asynchrone Callbacks (ara::core::Future/Promise-Pattern) die registrierten Methoden der Ziel-Application auf.
  • Nach Methodenrückkehr formatiert ara::diag das Ergebnis und sendet es an das SOVD Gateway zurück.
  • Pfad B (Multi-HPC Routing):
  • URI adressiert Subsysteme auf anderen Rechenknoten $\rightarrow$ Weiterleitung als HTTP-Reverse-Proxy-Call an den Ziel-HPC.
  • Pfad C (Classic UDS Gatewaying):
  • URI adressiert Ressourcen eines klassischen Steuergeräts (z. B. Read Data by Identifier oder Routine Control).
  • SOVD Gateway triggert die SOVD to UDS Translation.
  • Die Translation-Unit übersetzt die SOVD-Operation deterministisch in UDS-PDUs (z. B. POST /routines/0x0201 $\rightarrow$ UDS SID 0x31 0x01 0x02 0x01).
  • Versand via DoIP/CanTp an die Classic ECU.
  • UDS Positive Response (0x71) bzw. Negative Response Code (NRC, z. B. 0x22, 0x31) wird empfangen, in den entsprechenden HTTP-Statuscode (z. B. 200 OK, 400 Bad Request, 404 Not Found) transformiert und als JSON an das Gateway gereicht.
  1. Response-Konsolidierung:
  • Das SOVD Gateway assembliert den HTTP-Payload und liefert die synchrone HTTP-Response bzw. asynchrone WebSocket-Notifications an den anfragenden Client aus.

4. Normative Relevanz & Entwickler-Hinweise

  • Für Adaptive Platform Applikationsentwickler (ara::diag):
  • Applikationen implementieren ausschließlich die abstrakten C++ Service-Interfaces von ara::diag. Es besteht kein direkter Kontakt zu HTTP-Servern, REST-Parsern oder JSON-Serialisierern; die Kapselung erfolgt vollständig durch den Diagnostic Manager und das SOVD-Framework.
  • Methoden müssen strikt nicht-blockierend ausgelegt sein (asynchron via Futures/Promises), um Pipeline-Blockaden im Diagnostic Manager bei parallelen SOVD-Anfragen zu vermeiden.
  • Für Classic Platform Entwickler (DCM/DEM):
  • Auf den Classic ECUs bleibt der Standard-BSW-Stack unverändert. Es ist keine native SOVD-Unterstützung im Classic AUTOSAR Stack erforderlich.
  • Das Gateway (SOVD to UDS Translation) tritt gegenüber dem klassischen Steuergerät als regulärer UDS-Client (Tester) auf. Diagnose-P2/P2*-Timings und Session-Zustände (z. B. Extended Diagnostic Session, Security Access) müssen vom Translation-Modul verwaltet und gegen HTTP-Timeout-Mechanismen abgeglichen werden.
  • System- & Gateway-Integration (HPC-Entwickler):
  • Fehlermapping-Konsistenz: Entwickler des Translation-Layers müssen eine exakte Bijektion zwischen UDS-NRCs und HTTP-Statuscodes sicherstellen (z. B. NRC 0x31 RequestOutOfRange $\leftrightarrow$ HTTP 400 Bad Request; NRC 0x33 SecurityAccessDenied $\leftrightarrow$ HTTP 403 Forbidden).
  • Ressourcenpfad-Konfiguration: Die URI-Struktur des SOVD Gateway muss über AUTOSAR-Modellbeschreibungen (Manifeste) statisch mit den internen Diagnosediensten, DIDs und UDS-Zieladressen verknüpft werden.
  • Security-Zonierung: Das SOVD Gateway bildet eine kritische Sicherheitsgrenze. Authentifizierung und Berechtigungsprüfungen müssen zwingend vor dem Dispatching an ara::diag oder die SOVD to UDS Translation vollständig abgeschlossen sein.

Explanation of Service-Oriented Vehicle Diagnostics AUTOSAR AP R25-11 2 SOVD Reference Architecture Providing a central SOVD edge node in a distributed system does require some infrastructural components. To achieve this a reference architecture that clusters functions into several blocks has been introduced. This architecture is displayed in Figure 2.1). Main components of this reference architecture are: • SOVD Gateway • Diagnostic Manager • SOVD to UDS Translation Figure 2.1: SOVD Reference architecture 2.1 SOVD Gateway Upon request from a SOVD client the SOVD Gateway acts as SOVD edge node and routes the requests to respective internal SOVD endpoints. The routing takes place based on the entity part in the URI of the SOVD request. The SOVD Gateway must extract this part of the URI and route towards the corresponding endpoint. The setup of potential internal SOVD endpoints can be statically configured or dynamically discovered using mDNS. The forwarding itself takes place on application layer, i. e. the SOVD gateway acts as HTTP reverse proxy. For the configuration of the SOVD Gateway the SOVDGatewayInstantiation has been introduced in the TPS_Manifest. This manifest allows to configure the external SOVD connection towards SOVD clients as well as the internal forwarding targets. 6 of 14 Document ID 1064: AUTOSAR_AP_EXP_SOVD
