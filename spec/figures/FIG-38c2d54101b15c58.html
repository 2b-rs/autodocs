1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / Metamodell-Mapping (Gegenüberstellung von AUTOSAR M2 Software Component Template und RTE Configuration Parameter Definition / ECUC).
  • Architektur-Kontext: AUTOSAR Classic Platform, BSW-Schicht RTE (AUTOSAR_SWS_RTE, Release 4.3.1).
  • Funktionale Einordnung: Spezifikation der Konfigurationsbeziehung zwischen den M2-Artefakten einer Software-Komponente (SWC-Typ, Runnable, Datenzugriffspunkte) und dem RTE-Konfigurationscontainer RteImplicitCommunication. Es definiert, wie implizite Lese- und Schreibzugriffe (Rte_IRead_* / Rte_IWrite_*) instanzspezifisch parametriertes Puffer- und Kohärenzverhalten der RTE steuern.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die statische Parametrierung, aus der der RTE-Generator folgendes Laufzeitverhalten generiert:

[Task Context / Dispatcher]
        │
        ├── 1. Read-Phase (Pre-Execution / Copy-In)
        │      └── Kopieren aus globalem RTE-Puffer in Runnable-lokalen Schattenpuffer
        │          (Wenn RteCoherentAccess == true: geschützt via Sperre/Spinlock/Resource)
        │
        ├── 2. Ausführungs-Phase (Runnable Execution)
        │      ├── Aufruf: Symbol der RunnableEntity (symbol : CIdentifier)
        │      ├── Rte_IRead_*(): Zugriff ausschließlich auf lokalen Schattenpuffer
        │      └── Rte_IWrite_*(): Schreiben ausschließlich in lokalen Schattenpuffer
        │
        └── 3. Write-Phase (Post-Execution / Copy-Out)
               └── Rückkopieren der geänderten Variablen in den globalen RTE-Puffer
                   ├── RteImmediateBufferUpdate == false: Verzögerte/geplante Pufferübernahme
                   └── RteImmediateBufferUpdate == true: Unmittelbare Pufferübernahme bei Task-/Runnable-Terminierung
  • Kohärenz-Sicherung (RteCoherentAccess = true): Werden mehrere Datenzugriffe referenziert, generiert die RTE Interrupt-Sperren (SuspendOSInterrupts/ResumeOSInterrupts) oder Resource-Locks um den gesamten Copy-In/Copy-Out-Block, um Dateninkonsistenzen durch präemptive Tasks oder Multi-Core-Kerne zu unterbinden.
  • Keine Fehler-Callbacks: Implizite Zugriffe kennen im Gegensatz zu expliziten Kommunikationsschnittstellen (Rte_Read/Rte_Write) keine RTE-Rückgabewerte (Std_ReturnType). Fehlerbehandlung (z. B. Det/Dem) findet auf dieser Zugriffsebene nicht statt.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Signatur & Semantik:
    • Lesezugriffe über dataReadAccess führen zur Generierung von Makros/Inline-Funktionen der Form Rte_IRead_<re>_<p>_<d>() bzw. Rte_IStatus_<re>_<p>_<d>(). Rückgabe ist direkt der Pufferwert (bzw. Zeiger auf den Puffer).
    • Schreibzugriffe über dataWriteAccess erzeugen Rte_IWrite_<re>_<p>_<d>(data) bzw. Rte_IWriteRef_*.
  • Speicher- und Laufzeitaufwand (RAM/ROM):
    • Implizite Kommunikation opfert RAM (pro Runnable-Instanz lokaler Schattenpuffer) zugunsten deterministischer, verriegelungsfreier Zugriffszeiten während der Runnable-Berechnung.
    • Ist supportsMultipleInstantiation = true, allokiert die RTE die Puffer pro SwComponentPrototype (instanzspezifische Pufferstrukturen über RteSoftwareComponentInstanceRef).
  • Generator-Optimierungen:
    • Wenn RteCoherentAccess = false und Sender/Empfänger-Runnables in derselben Task ohne Präemption sequenziell laufen, kann der RTE-Generator Schattenpuffer wegoptimieren (Buffer Inlining / Direct Memory Access).
    • Das Setzen von RteCoherentAccess = true oder RteImmediateBufferUpdate = true deaktiviert aggressive Pufferbündelungen und erzwingt explizite Synchronisationspunkte.
  • Multi-Core-Restriktionen: Bei Cross-Core-Zugriffen zwischen Runnables stellt RteImplicitCommunication über die Puffergrenzen sicher, dass Core-lokale Zugriffe ohne Inter-Core-Spinlocks innerhalb der Runnable ablaufen; die Synchronisation wandert vollständig in die vom BSW/OS verwalteten Phasen vor und nach der Runnable.
