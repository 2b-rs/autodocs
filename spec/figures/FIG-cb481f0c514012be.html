1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Schichtenmodell / Blockschaltbild der statischen Software-Architektur des AUTOSAR Classic Platform Communication Stacks (AUTOSAR Release R24-11).
  • Technischer Zweck: Umfassende Darstellung der vertikalen und horizontalen Modulhierarchie, des PDU-Routings sowie der Datenfluss- und Kapselungsebenen (Signale, I-PDUs, N-PDUs, L-PDUs, L-SDUs). Kapselt die Kommunikationsdienste (inklusive Security, Ethernet/IP, XCP, DLT und Multiplexing), busspezifische State Manager, das PDU- und L-SDU-Routing sowie die Hardware-Abstraktion und MCAL-Treiber für Ethernet, FlexRay, CAN und LIN.

2. Komponenten, Entitäten & Schnittstellen

#### Schichten & Komponenten (Top-Down)

  • RTE (Orange): Explizit ausgewiesene Laufzeitumgebung; Schnittstellen über Signals zu AUTOSAR COM und Kontrollpfade zu XCP sowie zum State-Management.
  • Communication Services (Blau / BSW):
  • AUTOSAR COM: Signal-Packing/-Unpacking, Gateway-Funktionalität; Schnittstellen: Signals $\leftrightarrow$ RTE, I-PDU $\leftrightarrow$ PDU Router.
  • Diagnostic Communication Manager (DCM): Diagnoseprotokoll-Handling (UDS/OBD); Schnittstelle: I-PDU $\leftrightarrow$ PDU Router.
  • Diagnostic Log and Trace (DLT): Protokollierung und Ablaufverfolgung; Schnittstelle: I-PDU $\leftrightarrow$ PDU Router.
  • Secure Onboard Communication (SecOC): Kryptografische Verifikation und Schutz von PDUs; Schnittstelle: I-PDU $\leftrightarrow$ PDU Router.
  • IPDU Multiplexer (IpduM): Dynamisches und statisches Multiplexen mehrerer PDU-Layouts; Schnittstelle: I-PDU $\leftrightarrow$ PDU Router.
  • XCP: Kalibrierungs- und Messprotokoll; Schnittstelle: Steuerpfad $\leftrightarrow$ RTE, I-PDU $\leftrightarrow$ PDU Router.
  • SOME/IP TP: Segmentierungstransportprotokoll für SOME/IP-Nachrichten; Schnittstelle: I-PDU $\leftrightarrow$ PDU Router.
  • TCP/IP (gestrichelter Kasten): Ethernet-Protokollstack (Überlagerung zur Interface-Ebene).
  • PDU Router (PduR): Zentraler PDU-Verteiler für I-PDUs zwischen oberen Services, Transportprotokollen und Hardware-Interfaces.
  • Transportprotokolle:
  • FlexRay Tp: Transportprotokoll für segmentierte FlexRay-Daten; I-PDU¹ $\leftrightarrow$ PduR, N-PDU $\rightarrow$ FlexRay Interface.
  • CAN Tp: ISO 15765-2 Transportprotokoll; I-PDU¹ $\leftrightarrow$ PduR, N-PDU $\rightarrow$ CAN Interface².
  • J1939Tp: Transportprotokoll für Nutzfahrzeuge; I-PDU¹ $\leftrightarrow$ PduR, N-PDU $\rightarrow$ CAN Interface².
  • Network Management & State Management:
  • Communication Manager (ComM): Koordiniert Kommunikationsanforderungen über Steuerpfade zu den State Managern.
  • Bus State Manager: Eth State Manager, FlexRay State Manager, TTCAN State Manager, CAN State Manager, LIN State Manager.
  • Generic NM interface, NM Coordinator, NM Module: Mehrschichtige NM-Koordination und busbezogene NM-Zustandsmaschinen.
  • Communication HW Abstraction (Grün / BSW):
  • L-SDU Router: Horizontale Schicht zur Vermittlung und zum Routing von L-SDUs zwischen Kommunikationsschnittstellen.
  • Eth Interface, FlexRay Interface, CAN Interface², LIN Interface (incl. LIN TP): Einheitliche Bus-Controller-Abstraktion.
  • Communication Drivers / MCAL (Hellrot):
  • Eth Driver, FlexRay Driver, CAN Driver², LIN Low Level Driver: Hardwaretreiber für Controller-Register, Mailboxen und Schnittstellen.

#### PDU-Typen & Datenbeziehungen

  • Signal: Applikationsdaten über die RTE.
  • I-PDU / I-PDU¹: Interaktionsschicht-PDUs zwischen oberen Services, PduR, TP-Modulen (Fußnote 1) und Hardware-Interfaces.
  • N-PDU: Netzwerk-PDU segmentierter TP-Nachrichten an die Bus-Interfaces.
  • L-SDU: Dienstdateneinheiten auf Sicherungsschichtebene innerhalb des L-SDU Routers.
  • L-PDU: Physische Rahmen (Frame-Ebene) zwischen Hardware-Interfaces und MCAL-Treibern.

3. Dynamisches Verhalten & Sequenzablauf

#### Asynchrone Sende- und Empfangspfade (TX / RX)

  1. Unsegmentierter Direktpfad & Gateway:
  • TX: RTE $\rightarrow$ AUTOSAR COM / SecOC / IpduM $\rightarrow$ PduR $\rightarrow$ Bus-Interfaces (Eth Interface, FlexRay Interface, CAN Interface², LIN Interface) $\rightarrow$ MCAL-Treiber.
  • RX: MCAL-Treiber $\rightarrow$ Bus-Interface $\rightarrow$ PduR $\rightarrow$ COM / SecOC $\rightarrow$ RTE.
  1. Segmentierte Datenübertragung über Transportprotokolle:
  • Diagnose / Großdaten: DCM / XCP $\rightarrow$ PduR $\rightarrow$ Transportprotokolle (CAN Tp, FlexRay Tp, J1939Tp, SOME/IP TP).
  • Fragmentierung: TP-Module fordern Nutzdaten via Interaktionsschicht (I-PDU¹) an und übermitteln segmentierte N-PDUs an die Interfaces (CanIf, FrIf, etc.).
  1. L-SDU Routing:
  • Vermittlung von L-SDUs über den L-SDU Router direkt auf Hardware-Abstraktionsebene zwischen verschiedenen Controllern oder Bussen ohne Durchlauf des oberen PduR.
  1. Zustands- und Netzwerkmanagement-Abläufe:
  • ComM steuert Kommunikationsmodi über die dedizierten Bus State Manager (EthSM, FrSM, TTCAN SM, CanSM, LinSM), welche die Interfaces und Treiber aktivieren, deaktivieren oder in den Low-Power-Modus versetzen.
  • Der NM Coordinator synchronisiert über das Generic NM interface das Schlafen und Aufwachen mehrerer vernetzter Buscluster (NM Module).

4. Normative Relevanz & Entwickler-Hinweise

  • L-SDU Router Architektur: Die Einführung des L-SDU Router in der Hardware-Abstraktionsschicht ermöglicht schnelles Frame-/SDU-Routing mit minimaler Latenz unterhalb des PDU-Routers.
  • Fußnoten-Semantik:
  • Fußnote 1 (I-PDU¹): Weist auf TP-spezifische Pufferanforderungen und APIs hin (z. B. asynchrone Pufferhandhabung über CopyTxData / CopyRxData).
  • Fußnote 2 (CAN Interface², CAN Driver²): Kennzeichnet die funktionale Unterstützung erweiterter CAN-Standards, wie z. B. CAN FD mit variabler Datenrate und vergrößerter Payload (bis zu 64 Byte) oder TTCAN.
  • Security & Multiplexing: Durch die Eingliederung von SecOC werden I-PDUs vor der Weiterleitung im PduR mit Freshness-Werten und kryptografischen MACs versehen.
  • J1939Tp & Parallelbetrieb: J1939Tp koexistiert parallel zu CanTp am PDU Router und bindet an dasselbe CAN Interface² an; die Trennung erfolgt anhand konfigurierter CAN-IDs bzw. N-PDU-Zuordnungen.

Begleitender Spezifikationstext:

Specification of CAN Transport Layer AUTOSAR CP R24-11 1 Introduction and functional overview This specification defines the functionality, API and the configuration of the AUTOSAR Basic Software module CAN Transport Layer (CanTp). CanTp is the module between the PDU Router and the L-SDU Router module (see Figure 1.1). The main purpose of the CAN TP module is to segment and reassemble CAN I-PDUs longer than 8 bytes or longer than 64 bytes in case of CAN FD. The PDU Router deploys AUTOSAR COM and DCM I-PDUs onto different communication protocols. The routing through a network system type (e.g. CAN, LIN and Flex Ray) depends on the I-PDU identifier. The PDU Router also determines if a transport protocol has to be used or not. Lastly, this module carries out gateway functionality, when there is no rate conversion. L-SDU Router Module (LSduR) provides equal mechanisms to access a CAN bus channel regardless of its location (µC internal/external). From the location of CAN controllers (on chip / onboard), it extracts the ECU hardware layout and the number of CAN drivers. Because CanTp only handles transport protocol frames (i.e. SF, FF, CF and FC PDUs), depending on the N-PDU ID, the L-SDU Router module has to forward an I-PDU to CanTp or PduR.
