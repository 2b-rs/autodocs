1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Metamodell-Ausschnitt / UML-Klassendiagramm der AUTOSAR ECU Configuration Parameter Definition (ECUC Parameter Definition) gemäß AUTOSAR-Release R2.1.20.
  • Funktionale Einordnung: Definiert das XML-Schemamodell für das BSW-Modul Dem (Diagnostic Event Manager, Diagnostics Service Layer). Es beschreibt die statische Konfigurationsstruktur zur Deklaration von Diagnose-Events (DemEventParameter), deren Bindung an DTCs, Environment Data (Freeze Frames, Extended Data) sowie Event-Status- und Monitor-Initialisierungs-Callbacks.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Container-Hierarchie (Komposition via Metamodell-Definitionen)

  • Dem : ModuleDef [0..1]: Wurzel-Moduldefinition des Diagnostic Event Managers.
  • Komponiert über +container:
  • DemGeneral : ParamConfContainerDef [1..1]: Globaler Konfigurationscontainer des DEM.
  • Komponiert über +subContainer:
  • DemEventParameter : ParamConfContainerDef [0..65535]: Zentraler Container für ein individuelles Diagnose-Event (maximal $2^{16}-1$ Events).

#### Parameter und Sub-Container von DemEventParameter

  1. Direkte Parameter (+parameter):
  • DemEventID : IntegerParamDef: Wertebereich $1 \dots 65535$, symbolicNameValue = true. Definiert das symbolische C-Makro/Handle (DemConf_DemEventParameter_<Name>) für die API-Interaktion (Dem_SetEventStatus, Dem_GetEventStatus).
  • DemInitMonitorName : StringParamDef: Bezeichner der herstellerspezifischen Initialisierungsfunktion des Diagnosemonitors (Funktionszeiger/C-Callback).
  1. Sub-Container (+subContainer):
  • DemGetExtendedDataList : ParamConfContainerDef [1..1]:
  • Parameter +parameter DemGetExtendedDataTarget : StringParamDef: Symbolischer Name der Applikations-/SW-C-Callback-Funktion zur Bereitstellung der erweiterten Daten.
  • DemEventClass : ParamConfContainerDef [1..1]: Konfiguriert Event-spezifische Basiseigenschaften (Entprellung/Debouncing, Aging, Priorität).
  • DemFreezeFrameClass : ParamConfContainerDef [0..*]: Referenz/Zuordnung zu Freeze-Frame-Definitionen (Erfassung von DIDs/Snapshots bei Fehleraktivierung).
  • DemExtendedDataClass : ParamConfContainerDef [0..*]: Spezifiziert herstellerspezifische Zusatzdaten.
  • +parameter DemExtendedClassID : IntegerParamDef: Bereich $0 \dots 65535$.
  • +parameter DemExtendedDataRecordNumber : IntegerParamDef: Bereich $0 \dots 255$ (entspricht UDS Record-ID nach ISO 14229, Service 0x19 06/04).
  • +parameter DemDataSize : IntegerParamDef: Bereich $0 \dots 255$ (Größe des Daten-Records in Bytes).
  • DemDTCClass : ParamConfContainerDef [1..2]: Zuordnung des Events zu Diagnose-Fehlercodes. Die Kardinalität 1..2 erzwingt mindestens einen DTC (z. B. primärer UDS-DTC) und erlaubt maximal zwei (z. B. simultaner ISO 14229 UDS- und ISO 15031-6 OBD-DTC).
  • DemTriggerOnEventStatusList : ParamConfContainerDef [0..*]:
  • Parameter +parameter DemTriggerOnEventStatusTarget : StringParamDef: C-Funktionsname für Status-Change-Notifications bei Transitionen des UDS-Event-Statusbytes (0x00 bis 0xFF).

3. Dynamisches Verhalten & Sequenzablauf

Aus dem statischen Parameterschema resultieren folgende Laufzeitpfade im BSW-Stack:

```

[Monitor Start / Restart]

│

▼

DemInitMonitorName(InitMonitorReason) ──► Initialisierung interner Zähler / Filter

│

▼ [Zyklischer Monitorlauf: Dem_SetEventStatus(DemEventID, DEM_EVENT_STATUS_FAILED)]

│

├──► UDS-Statusänderung detektiert?

│ │

│ ▼

│ DemTriggerOnEventStatusTarget(EventStatusByteOld, EventStatusByteNew)

│

└──► Event qualifiziert (TestFailed: 0 -> 1)

│

├──► Aufruf FreezeFrame-Storage (DemFreezeFrameClass)

│

└──► Akquise Extended Data via DemGetExtendedDataTarget:

└─► Puffer-Allokation gemäß DemDataSize

└─► Speicherung unter DemExtendedDataRecordNumber

└─► Asynchrones Commit an NvM (Non-Volatile Memory)

```

  • Initialisierung: Beim Startup (Dem_Init) oder Fehlerlöschen (Dem_ClearDTC) wird über den symbolischen Namen DemInitMonitorName der Monitor zur Re-Initialisierung synchron aufgerufen.
  • Event-Qualifikation & Datenspeicherung: Meldet eine SW-C/BSW einen Fehlerstatuswechsel, prüft der DEM die Bindung an DemDTCClass. Ist ein Speicherungs-Trigger aktiv, ruft das DEM synchron den Callback DemGetExtendedDataTarget auf, um Nutzdaten der konfigurierten Länge DemDataSize für den definierten DemExtendedDataRecordNumber abzufragen und persistent (via NvM) abzulegen.
  • Benachrichtigungskette: Bei jeder Transition des Event-Statusbytes werden die in DemTriggerOnEventStatusList registrierten Notification-Targets aufgerufen.

4. Normative Relevanz & Entwickler-Hinweise

  • Symbolische Konstanten (symbolicNameValue = true): Entwickler dürfen Event-IDs im Quellcode niemals hardcodieren. Es sind zwingend die vom Konfigurator in Dem_Cfg.h generierten Bezeichner (DemEventID) zu verwenden.
  • Funktionszeiger & Linker-Symbole: Für alle StringParamDef-Einträge (DemInitMonitorName, DemGetExtendedDataTarget, DemTriggerOnEventStatusTarget) müssen korrespondierende C-Funktionen in der Applikation/SW-C mit der AUTOSAR-konformen Typsignatur deklariert und implementiert sein; andernfalls schlägt der Link-Vorgang fehl.
  • Kardinalitäts-Constraint DemDTCClass [1..2]: Ein Event kann in diesem Schema nicht DTC-los konfiguriert werden (Mindestmultiplizität 1). Reine BSW-Fehler ohne DTC erfordern hier eine explizite Pseudoklasse oder DTC-Zuordnung.
  • Speicherdimensionierung: DemDataSize (0–255 Bytes) bestimmt die statische Puffergröße im RAM sowie das Layout der korrespondierenden NVRAM-Blöcke (NvMBlockDescriptor). Eine Fehlkonfiguration führt zu Pufferüberläufen oder NVRAM-Speicherverschwendung.
