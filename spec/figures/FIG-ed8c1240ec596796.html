1. Diagrammtyp & Architektur-Kontext

UML-Sequenzdiagramm zur Spezifikation des Gateway-Verhaltens im AUTOSAR-Basissoftwaremodul PDU Router (PduR) innerhalb der Classic Platform (Release R3.2.3). Das Diagramm stellt das Weiterleiten einer I-PDU ohne Transportprotokoll (non-TP PDU) und ohne Ratenkonvertierung zwischen zwei Kommunikationsschnittstellen der unteren Schicht (Lower Layer Interface Modules) unter Verwendung des TriggerTransmit-Prinzips auf der Zielseite dar.

2. Komponenten, Entitäten & Schnittstellen

An der Interaktion sind vier Kommunikationspartner über vertikale Lebenslinien beteiligt:

  • Upper Layer ("If") for PduR: Übergeordnete Schnittstellenschicht (im dargestellten Gateway-Ablauf inaktiv / unbeteiligt).
  • «module» PduR: Das zentrale Gateway- und Routing-Modul der AUTOSAR-Basissoftware.
  • Lo1 :Lower Layer ("If") for PduR: Ziel-Schnittstellenmodul der unteren Schicht (<Lo>If - 1 = {FrIf, LinIf}).
  • Lo2 :Lower Layer ("If") for PduR: Quell-Schnittstellenmodul der unteren Schicht (<Lo>If - 2 = {CanIf, FrIf, LinIf}).

Verwendete Schnittstellenfunktionen und Signaturen:

  • PduR_<Lo>IfRxIndication(PduIdType, uint8*): Eingangsmeldung einer empfangenen I-PDU von Lo2 an den PduR.
  • Copy data from <Lo> Rx buffer(): Interne PduR-Aktion zur Pufferung der empfangenen Nutzdaten.
  • <Lo>If_Transmit(Std_ReturnType, PduIdType, const PduInfoType*) : Std_ReturnType: Sendeanforderung des PduR an das Zielmodul Lo1.
  • PduR_<Lo>IfTriggerTransmit(PduIdType, uint8*): Asynchrone Datenabruf-Funktion von Lo1 an den PduR.
  • Copy data to <Lo> Tx buffer(): Interne PduR-Aktion zur Bereitstellung der gepufferten Daten an den Zielpuffer.

3. Dynamisches Verhalten & Sequenzablauf

Der Sequenzablauf gliedert sich in zwei zeitlich entkoppelte Phasen:

  1. Empfang und Sendeinitiierung:
  • Lo2 signalisiert den Empfang einer I-PDU an den PduR über den synchronen Aufruf PduR_<Lo>IfRxIndication(PduIdType, uint8*).
  • Der PduR führt eine interne Ausführungssequenz aus: Copy data from <Lo> Rx buffer(), um die Nutzdaten in einem dedizierten PDU-Puffer zwischenzuspeichern.
  • Der PduR triggert die Zielübertragung bei Lo1 durch den Aufruf <Lo>If_Transmit(Std_ReturnType, PduIdType, const PduInfoType*) : Std_ReturnType. Da TriggerTransmit konfiguriert ist, werden die Daten nicht direkt übergeben.
  • Lo1 quittiert die Sendeanforderung mit dem Return <Lo>If_Transmit().
  • Der PduR schließt die Empfangsindikation mit dem Return PduR_<Lo>IfRxIndication() an Lo2 ab.
  1. Datenabruf via TriggerTransmit:
  • Zeitlich versetzt (z. B. getriggert durch den Buszyklus von FlexRay oder LIN) fordert Lo1 die Daten über PduR_<Lo>IfTriggerTransmit(PduIdType, uint8*) vom PduR an.
  • Der PduR kopiert die gespeicherten Nutzdaten über die interne Aktion Copy data to <Lo> Tx buffer() in den übergebenen Zeigerbereich von Lo1.
  • Die Funktion kehrt mit dem Return PduR_<Lo>IfTriggerTransmit() zu Lo1 zurück, woraufhin Lo1 die PDU auf dem Zielbus versenden kann.

4. Normative Relevanz & Entwickler-Hinweise

Normativ definiert dieses Sequenzdiagramm die Entkopplung von Empfang und Sendung beim Interface-Routing unter Verwendung von TriggerTransmit:

  • Der PduR muss bei dieser Konfiguration zwingend einen lokalen PDU-Puffer bereitstellen, um die Daten zwischen PduR_<Lo>IfRxIndication und PduR_<Lo>IfTriggerTransmit zwischenzuspeichern.
  • Die Zielmodule (Lo1) sind auf Busse beschränkt, die TriggerTransmit unterstützen (FrIf, LinIf). Quellmodule (Lo2) können CanIf, FrIf oder LinIf sein.
  • Die übergeordnete Schicht (Upper Layer) wird beim direkten Gateway-Routing vollständig umgangen.
  • Implementierer müssen die Gültigkeit und Konsistenz des internen Puffers bei konkurrierenden Lese- und Schreibzugriffen sicherstellen. Der Diagrammstatus ist im Spezifikationsvermerk explizit als „Proposed“ gekennzeichnet.
