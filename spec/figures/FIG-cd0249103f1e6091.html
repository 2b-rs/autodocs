1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt aus der AUTOSAR Adaptive Platform Spezifikation (AUTOSAR_TPS_ManifestSpecification, Release R19-03).
  • Funktionaler Zweck: Modellierung der entwurfszeitlichen Zugriffsrechte (Grant Designs) im Rahmen des Identity and Access Managements (IAM) und der serviceorientierten Kommunikation (ara::com). Es definiert, wie einem Prozess (ProcessDesign / Executable) granulare Zugriffsrechte (getter, setter, getterSetter) auf ein Field eines ServiceInterface zugeordnet werden, und wie Required-Ports (RPortPrototype) über ClientComSpec an die Feld-Operationen gekoppelt sind.

2. Komponenten, Entitäten & Schnittstellen

Identity & Access Management (IAM / Grant-Hierarchie)
  • GrantDesign («ARElement»): Abstrakte Basisklasse zur Spezifikation von Zugriffsrechten auf Architekturebene. Assoziiert über +processDesign [0..1] mit ProcessDesign.
  • ComFieldGrantDesign (Spezialisierung von GrantDesign): Konkrete Zuweisung von Zugriffsrechten für Kommunikationsfelder.
    • Attribut: + role: FieldAccessEnum
    • Instanzreferenz («instanceRef»): +field [1] referenziert eindeutig das Ziel-Field.
  • FieldAccessEnum («enumeration»): Definiert den Zugriffsumfang:
    • getter: Leserecht auf den aktuellen Feldwert.
    • setter: Schreibrecht zur Aktualisierung des Feldwerts.
    • getterSetter: Kombiniertes Lese- und Schreibrecht.
  • ProcessDesign («ARElement»): Repräsentiert die logische Instanziierung eines Prozesses zur Entwurfszeit. Referenziert über +executable [0..1] die zugrundeliegende Binärdatei.
  • Executable («ARElement», «AtpClassifier»): Das ausführbare Software-Artefakt.
    • Attribute: buildType: BuildTypeEnum [0..1], minimumTimerGranularity: TimeValue [0..1], version: StrongRevisionLabelString [0..1].
Service- und Schnittstellenebene
  • PortInterface («ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpType»): Abstrakte Schnittstellen-Basisklasse.
  • ServiceInterface (Spezialisierung von PortInterface): Modelliert serviceorientierte Schnittstellen der Adaptive Platform.
    • Aggregation («atpVariation»): +field [0..*] enthält Instanzen vom Typ Field.
  • Field (Spezialisierung von AutosarDataPrototype): Datenattribut eines Services mit Method- und Event-Charakteristik.
    • Attribute:
      • + hasGetter: Boolean: Gibt an, ob ein lesender Methodenaufruf bereitgestellt wird.
      • + hasSetter: Boolean: Gibt an, ob ein modifizierender Methodenaufruf bereitgestellt wird.
      • + hasNotifier: Boolean: Gibt an, ob ein Event/Notifikationsmechanismus bei Wertänderung existiert.
Port- & Kommunikationsspezifikation
  • AbstractRequiredPortPrototype («PortPrototype»): Abstrakter Client-/Konsumenten-Port. Enthält per Komposition +requiredComSpec [0..*] vom Typ RPortComSpec.
  • RPortPrototype (Spezialisierung von AbstractRequiredPortPrototype): Konkreter Required-Port einer Komponente.
    • Referenz: +requiredInterface [1] («isOfType», redefiniert atpType) bindet den Port an ein PortInterface (hier ServiceInterface).
  • RPortComSpec: Abstrakte Kommunikationsspezifikation auf Port-Ebene.
  • ClientComSpec (Spezialisierung von RPortComSpec): Spezifische Konfiguration für Service-Konsumenten.
    • Attribut: + clientCapability: ClientCapabilityEnum [0..1].
    • Assoziationen:
      • +getter [0..1] referenziert das Ziel-Field für Leseaufrufe.
      • +setter [0..1] referenziert das Ziel-Field für Schreibaufrufe.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Entwurfsmetamodell (Design Manifest) handelt, beschreibt das Schaubild keinen Laufzeit-Kontrollfluss, sondern determiniert die dynamische Autorisierungsprüfung zur Laufzeit:

  1. Deployment & Policy-Generierung: Die im Modell deklarierten ComFieldGrantDesign-Instanzen werden durch Generatoren in IAM-Sicherheitsrichtlinien (z. B. Zugriffsmatrizen / Access Control Lists für IPC bzw. SOME/IP) übersetzt.
  2. Aufrufinitiierung (Client-Prozess): Eine Applikation greift über die generierten Proxies von ara::com mittels Field::Get() oder Field::Set() auf das Feld zu.
  3. IAM-Enforcement:
    • Der Kommunikationsstack bzw. der IAM-Policy-Checker validiert anhand des aufrufenden Prozesses (ProcessDesign → Executable), ob ein valider ComFieldGrantDesign für die spezifische Rolle (getter bzw. setter) auf dem Ziel-Field existiert.
    • Positivfall: Aufruf wird über IPC/Netzwerk an den Service Provider dispatcht.
    • Negativfall (Rechteverletzung): Der Zugriff wird blockiert; es erfolgt ein lokaler Abbruch mit Fehlercode (ara::com::ComErrorDomain::kGrantEnforcementFailed bzw. Security Violation Event).

4. Normative Relevanz & Entwickler-Hinweise

  • Granularität der Feldberechtigungen (TPS_MANI_01234):
    • Ein Field vereint Methoden (Get, Set) und Events (Notifier). ComFieldGrantDesign steuert ausschließlich die Methodenpfade via role: FieldAccessEnum.
    • Notifier-Berechtigungen werden normativ nicht über ComFieldGrantDesign, sondern über Event-bezogene Grants (ComEventGrantDesign) gesteuert.
  • Konsistenzregeln Modellierung vs. Schnittstelle:
    • Eine Zuweisung von role = getter erfordert zwingend Field.hasGetter == true.
    • Eine Zuweisung von role = setter erfordert zwingend Field.hasSetter == true.
    • Eine Zuweisung von role = getterSetter erfordert zwingend, dass sowohl hasGetter als auch hasSetter auf true evaluiert sind.
  • Port-Bindung (ClientComSpec):
    • Auf Konsumentenseite muss für jede genutzte Operation (getter / setter) eine explizite Referenz in ClientComSpec vorliegen. Fehlt die Zuordnung im ClientComSpec, generiert der Stack-Generator keine typisierten API-Aufrufe am R-Port für die jeweilige Operation.
  • Auswirkung auf Integratoren:
    • Wird ein Prozess ohne passenden ComFieldGrantDesign deployt, kompiliert der Client-Code zwar gegen das Interface, scheitert jedoch deterministisch zur Laufzeit am IAM-Stack.
