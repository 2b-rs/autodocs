1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Dekompositionsdiagramm basierend auf dem SPEM-2.0-Metamodell (Software & Systems Process Engineering Metamodel) innerhalb der AUTOSAR-Methodik (AUTOSAR_TR_Methodology, R4.0.3).
  • Technischer Zweck: Strukturelle und hierarchische Zerlegung (Activity Breakdown Structure) der Top-Level-Aktivität Develop Basic Software in Sub-Aktivitäten (Design Basic Software, Develop BSW Module) und granulare Aufgaben (SPEM-Tasks) sowie deren Bindung an Ein- und Ausgangs-Artefakte (WorkProductPackages).
  • Architektur-Einordnung: Definiert den standardisierten Entwicklungsprozess für Basissoftware-Module (BSW) durch Tier-1-Zulieferer oder BSW-Stack-Vendors vor der eigentlichen ECU-Integration.

2. Komponenten, Entitäten & Schnittstellen

  • Work Product Packages (Artefakte):
  • BSW Standard Package [Multiplizität: 1, Stereotyp: «input»]: Standardisierte Vorgaben der AUTOSAR-Spezifikation (Standard-Header, BSW-UML-Modelle, Schema-Definitionen, standardisierte BSWMD-Templates).
  • Transformer Design Bundle [Multiplizität: 0..*, Stereotyp: «input»]: Vorgaben und Beschreibungen für Daten- und Serialisierungs-Transformatoren (z. B. SOME/IP, E2E), die als optionale Eingangsdaten in die BSW-Entwicklung einfließen.
  • BSW Module Delivered Bundle [Multiplizität: 1..*, Stereotyp: «output»]: Auslieferungsfähiges BSW-Lieferpaket (statische C-Quell-/Header-Dateien, Vendor-spezifische BSWMD, Modul-Code-Generatoren, Dokumentation).
  • Aktivitäten (Composite Activities):
  • Develop Basic Software: Übergeordnete Top-Level-Prozessklammer.
  • Design Basic Software [Multiplizität: 1, Stereotyp: «nesting»]: Modulübergreifendes BSW-Architekturdesign.
  • Develop BSW Module [Multiplizität: 1..*, Stereotyp: «nesting»]: Modulspezifische Implementierungs- und Generatorentwicklungsaktivität (instanziiert pro BSW-Modul).
  • Sub-Tasks in Design Basic Software (Stereotyp: «nesting»):
  • Define BSW Types: Spezifikation von BSW-spezifischen Typdefinitionen (Std_Types, modulspezifische Enums/Strukturen).
  • Define BSW Entries: Definition der C-Funktionsprototypen und Entry-Points (BswModuleEntry) für APIs, Callbacks und Main-Functions.
  • Define BSW Interfaces: Festlegung der Schnittstellenbeziehungen und Abhängigkeiten zwischen BSW-Modulen bzw. zur SWC-Welt.
  • Define Vendor Specific Module Definition: Erweiterung der standardisierten Moduldefinition um herstellerspezifische Konfigurationsparameter (EcucParamConfContainerDef).
  • Sub-Tasks in Develop BSW Module (Stereotyp: «nesting»):
  • Generate BSW Module Prebuild Data Set: Generierung von vorkompilierten/vorkonfigurierten Datensätzen für das BSW-Modul.
  • Compile BSW Core Code: Übersetzung und Vorab-Prüfung des C-Quellcodes der Basissoftware.
  • Define BSW Module Timing: Spezifikation von Ausführungszeiten, Task-Perioden und Latenz-Garantien (BswModuleTiming).
  • Develop BSW Module Generator: Implementierung des Konfigurations- und Codegenerators.
  • Implement a BSW Module: Programmierung des statischen C-Codes des Moduls.
  • Generate BSWM Contract Header Files: Erzeugung der Contract-Phase-Header zur Entkopplung und Vorab-Kompilierung von BSW-Quellen.
  • Define BSW Behavior: Modellierung des internen Verhaltens (BswInternalBehavior).

3. Dynamisches Verhalten & Sequenzablauf

  • Hierarchische Verschachtelung («nesting»):
  • Die Top-Level-Aktivität Develop Basic Software dekomponiert sich über «nesting»-Kanten in Develop BSW Module (Multiplizität 1..*) und Design Basic Software (Multiplizität 1).
  • Develop BSW Module umfasst über «nesting» 7 Sub-Tasks: Generate BSW Module Prebuild Data Set, Compile BSW Core Code, Define BSW Module Timing, Develop BSW Module Generator, Implement a BSW Module, Generate BSWM Contract Header Files und Define BSW Behavior.
  • Design Basic Software umfasst über «nesting» 4 Sub-Tasks: Define BSW Types, Define BSW Entries, Define BSW Interfaces und Define Vendor Specific Module Definition.
  • Abhängigkeiten und Reihenfolgebeziehungen:
  • Zwischen Develop BSW Module und Design Basic Software ist eine gestrichelte «predecessor»-Kante modelliert, die von Develop BSW Module auf Design Basic Software gerichtet ist.
  • Artefaktfluss:
  • Als Eingänge («input») sind BSW Standard Package (Multiplizität 1) und Transformer Design Bundle (Multiplizität 0..*) mit Develop Basic Software verbunden.
  • Als Ausgang («output») ist BSW Module Delivered Bundle (Multiplizität 1..*) mit Develop Basic Software verbunden.

4. Normative Relevanz & Entwickler-Hinweise

  • Konformität & Prozessbindung: Die SPEM-Zerlegung ist methodisch bindend für die Strukturierung von BSW-Lieferprozessen. Jeder BSW-Zulieferer muss die definierten Rollen, Tasks und Artefaktbeziehungen einhalten.
  • Transformer-Unterstützung: Werden Daten-Transformatoren eingesetzt, liefert das Transformer Design Bundle Spezifikationen und Schnittstellenvereinbarungen, die während der BSW-Entwicklung berücksichtigt werden müssen.
  • Parallelisierung & Iteration: Während Design Basic Software zentral einmalig (1) durchgeführt wird, kann Develop BSW Module parallel für mehrere Module (1..*) instanziiert und iterativ durchlaufen werden.
  • Artefaktvollständigkeit: Das erzeugte BSW Module Delivered Bundle muss alle statischen und generierten Dateien sowie Modulbeschreibungsdateien (BSWMD) enthalten, um stromabwärts im AUTOSAR-Integrationsprozess konsumierbar zu sein.
