1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-2.0-Klassendiagramm (Metamodell-Ausschnitt / M2-Ebene des AUTOSAR System Template, Spezifikationsdokument AUTOSAR_TPS_SystemTemplate).
  • Architektur-Einordnung: Generisches Metamodell für das AUTOSAR Network Management (Nm). Definiert die busunabhängige System- und Netzwerktopologie für NM-Cluster, NM-Knoten, koordinierte Netzwerke sowie die Zuordnung von NM-PDUs und Steuerungsparametern auf Systemebene (System Description / ARXML).
  • Funktionaler Zweck: Schnittstelle zwischen Bussystem-Topologie (CommunicationCluster, CommunicationController) und der Steuergeräte-spezifischen NM-Implementierung (NmIf, CanNm, FrNm, UdpNm). Dient Codegeneratoren (z. B. für den AUTOSAR NM Interface-Stack Nm / ComM) als Eingabe zur Ableitung von Kanal-IDs, Knoten-IDs, PDU-Routings und Koordinationsrollen (NM-Koordinator / Gateway).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • NmConfig (Spezialisierung von FibexElement):
    • Wurzel-/Top-Level-Container der Netzwerkmanagement-Konfiguration im System Template.
  • NmCluster (Spezialisierung von Identifiable):
    • Repräsentiert ein logisches NM-Netzwerk.
    • Attribute:
      • nmChannelSleepMaster : Boolean
      • nmNodeDetectionEnabled : Boolean [0..1]
      • nmNodeIdEnabled : Boolean [0..1]
      • nmPncParticipation : Boolean [0..1]
      • nmRepeatMsgIndEnabled : Boolean [0..1]
      • nmSynchronizingNetwork : Boolean
  • CommunicationCluster (Spezialisierung von FibexElement, Stereotyp «atpVariation»):
    • Physikalisches Kommunikationsnetzwerk (z. B. CAN, FlexRay, Ethernet).
    • Attribute: baudrate (PositiveUnlimitedInteger [0..1]), protocolName (String [0..1]), protocolVersion (String [0..1]).
  • NmClusterCoupling:
    • Modelliert Kopplungen zwischen mehreren NM-Clustern zur synchronisierten Busruhe/Aufweckkoordination.
  • NmEcu (Spezialisierung von Identifiable):
    • Repräsentiert die NM-Schnittstelle und -Konfiguration auf Steuergeräteebene (NmIf).
    • Attribute:
      • nmBusSynchronizationEnabled : Boolean [0..1]
      • nmComControlEnabled : Boolean [0..1]
      • nmCycletimeMainFunction : TimeValue [0..1]
      • nmNodeDetectionEnabled : Boolean [0..1]
      • nmNodeIdEnabled : Boolean [0..1]
      • nmPduRxIndicationEnabled : Boolean [0..1]
      • nmRemoteSleepIndEnabled : Boolean [0..1]
      • nmRepeatMsgIndEnabled : Boolean [0..1]
      • nmStateChangeIndEnabled : Boolean [0..1]
      • nmUserDataEnabled : Boolean [0..1]
  • BusspecificNmEcu:
    • Bus-spezifische NM-ECU-Erweiterungen (z. B. CanNm, FrNm, UdpNm).
  • NmCoordinator:
    • Konfiguration für koordinierte NM-Cluster (Gateway-/Koordinator-Funktionalität).
    • Attribute: index (Integer), nmCoordSyncSupport (Boolean [0..1]), nmGlobalCoordinatorTime (TimeValue [0..1]).
  • NmNode (Spezialisierung von Identifiable):
    • Logischer NM-Endpunkt eines Steuergeräts innerhalb eines spezifischen NmCluster.
    • Attribute: nmCoordCluster (PositiveInteger [0..1]), nmCoordinatorRole (NmCoordinatorRoleEnum [0..1]), nmNodeId (Integer [0..1]), nmPassiveModeEnabled (Boolean [0..1]).
  • CommunicationController (Spezialisierung von Identifiable, Stereotyp «atpVariation»):
    • Physischer Kommunikations-Controller auf dem Steuergerät.
    • Attribute: wakeUpByControllerSupported (Boolean [0..1]).
  • NmPdu (Spezialisierung von Pdu):
    • NM-spezifische Protokolldateneinheit zur Zustandssynchronisation auf dem Bus.
    • Attribute: nmDataInformation (Boolean [0..1]), nmVoteInformation (Boolean [0..1]), unusedBitPattern (Integer [0..1]).
  • ISignalToIPduMapping (Spezialisierung von Identifiable):
    • Signal-zu-PDU-Mapping innerhalb der NM-PDU (z. B. für NM-Nutzerdaten).
    • Attribute: packingByteOrder (ByteOrderEnum [0..1]), startPosition (Integer [0..1]), transferProperty (TransferPropertyEnum [0..1]), updateIndicationBitPosition (Integer [0..1]).
  • NmCoordinatorRoleEnum (Stereotyp «enumeration»):
    • Definiert die Koordinationsrolle eines NM-Knotens.
    • Literale: Active, Passive.

  • NmConfig -> NmClusterCoupling: Komposition via Rolle +nmClusterCoupling (Multiplizität 0..*, Stereotyp «atpVariation»).
  • NmConfig -> NmEcu: Komposition via Rolle +nmIfEcu (Multiplizität 1..*, Stereotyp «atpVariation»).

  • NmEcu -> BusspecificNmEcu: Komposition via Rolle +busDependentNmEcu (Multiplizität 0..*).
  • NmCluster -> CommunicationCluster: Gerichtete Assoziation via Rolle +communicationCluster (Multiplizität 1).
  • NmCluster -> NmNode: Komposition via Rolle +nmNode (Multiplizität 0..*, Stereotyp «atpVariation»).
  • NmCoordinator -> NmNode: Assoziation via Rolle +nmNode (Multiplizität 1..*).
  • NmEcu <-> NmNode: Bidirektionale Assoziation zwischen Rolle +nmIfEcu (Multiplizität 1) und Rolle +nmNode (Multiplizität 1..*).
  • NmNode -> CommunicationController: Gerichtete Assoziation via Rolle +controller (Multiplizität 1).

  • NmPdu -> ISignalToIPduMapping: Komposition via Rolle +iSignalToIPduMapping (Multiplizität 0..*, Stereotyp «atpVariation»).

3. Dynamisches Verhalten & Sequenzablauf

  • Statisches Metamodell ohne Laufzeitsequenz: Das Diagramm modelliert M2-Strukturdefinitionen. Die Attribute steuern jedoch direkt das deterministische Laufzeitverhalten der BSW-Module:
    • Zyklische Trigger: nmCycletimeMainFunction bestimmt das Scheduling-Intervall der Nm_MainFunction() im BSW-Scheduler (SchOS/RTE).
    • Koordinator-Shutdown: nmShutdownDelayTimer definiert die Nachlaufzeit vor Freigabe des Bus-Sleeps in gekoppelten Clustern. nmActiveCoordinator legt fest, ob die ECU aktiv Schlafbereitschaft anfordert oder passiv dem Cluster folgt.
    • Synchronisation & Sleep Master: nmSynchronizingNetwork synchronisiert den NM-Zyklus mit dem Kommunikationsnetzwerk; nmChannelSleepMaster bestimmt, welcher Knoten den Sleep-Befehl forciert.
    • PDU-Routing & Callback-Trigger:
      • nmPduRxIndicationEnabled schaltet Rx-Indication-Pfade frei (<Bus>Nm_RxIndication -> Nm_PduRxIndication).
      • nmStateChangeIndEnabled steuert die Benachrichtigung an den Communication Manager (Nm_StateChangeNotification -> ComM).
      • nmRemoteSleepIndEnabled und nmRepeatMsgIndEnabled aktivieren asynchrone Callbacks zur Erkennung netzwerkweiter Schlaf- bzw. Wachzustände.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative ARXML-Modellierung: Alle NM-bezogenen Artefakte sind streng an das AUTOSAR System Template gebunden. XML-Elemente wie NmConfig, NmCluster, NmEcu und NmNode müssen konform zu den definierten Kardinalitäten instantiiert werden.
  • Variantenmanagement: Die Präsenz von Stereotypen wie «atpVariation» an CommunicationCluster, CommunicationController, +nmCluster, +nmClusterCoupling, +nmIfEcu, +nmNode und +iSignalToIPduMapping erlaubt post-build- und bindetime-fähige Variationen innerhalb der Systemkonfiguration.
  • Codegenerierung & BSW-Ableitung: Die Parameter aus NmEcu fließen direkt in das BSW-Modul Nm (AUTOSAR NM Interface) ein, während NmNode und NmPdu die Konfiguration der busspezifischen NM-Module (CanNm, FrNm, UdpNm) determinieren.
  • Koordinatoren-Rollen: Über NmCoordinatorRoleEnum (Active / Passive) auf Knotenebene und nmCoordSyncSupport auf Koordinatorebene wird die synchrone Steuerung gekoppelter Cluster systemspezifisch parametriert.
