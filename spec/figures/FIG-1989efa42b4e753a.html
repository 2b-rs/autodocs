1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Sequence Diagram).
  • Technischer Zweck & Einordnung: Darstellung des standardisierten, fehlerfreien Aktualisierungsablaufs (Happy Path Update) einer Adaptive Application (AA) innerhalb der AUTOSAR Adaptive Platform (AP). Das Diagramm spezifiziert das Zusammenspiel zwischen dem fahrzeugexternen oder -internen Diagnose-/OTA-Master (Backend), dem Plattform-Funktionscluster-Knoten UCM Subordinate, dem State Management zur Systemzustands-Koordination und der betroffenen Adaptive Application (unter Ausführungskontrolle durch das Execution Management).

2. Komponenten, Entitäten & Schnittstellen

  • Beteiligte Instanzen (Lifelines):
    • :Backend: Client-Entität (z. B. OTA-Client, Flashtester oder Diagnosedienst über DoIP/UDS), die den Software-Update-Prozess initiiert und steuert.
    • :UCM Subordinate: Untergeordnete UCM-Instanz (ara::ucm), zuständig für Pakettransfer, Validierung, Abhängigkeitsprüfung, Installation und Bereinigung von Software-Paketen auf dem jeweiligen Steuergerät/der jeweiligen Machine.
    • :State Management: Funktionscluster ara::sm (State Management), der Fahrzeug- und Funktionsgruppenzustände steuert und auf Statusänderungen des UCM reagiert (z. B. zur Vorbereitung von sicheren Fahrzeugzuständen für Updates).
    • :Adaptive Application: Zu aktualisierende POSIX-Prozessinstanz der Anwendungsebene.
  • Schnittstellen & Interaktionspunkte:
    • Backend ↔ UCM Subordinate: Service-Interface des UCM (spezifiziert in ara::ucm::pkgmgr::PackageManagement):
      • TransferData() → liefert TransferId (Identifikator des transferierten Software-Pakets).
      • ProcessSwPackage(TransferId) → stößt das Entpacken, Integritätsprüfungen und das Bereitstellen der Binaries an.
      • Activate() → synchron/asynchron aufgerufene Methode; gibt ActivateReturnType zurück.
      • Finish() → finalisiert das Update; gibt FinishReturnType zurück.
    • UCM Subordinate → State Management: Zustandsübermittlung via Field/Event CurrentStatus (Typ ara::ucm::pkgmgr::PackageManagerStatusType):
      • Werte: kIdle, kProcessing, kActivating, kVerifying, kActivated, kCleaning-up.
    • UCM Subordinate → Adaptive Application:
      • restart(): Reinitialisierung/Neustart des Prozesses der Applikation (architektonisch über das Execution Management ara::exec mittels Transitionen der Funktionsgruppe bzw. Prozess-Terminierung/Neustart orchestriert).
    • UCM Subordinate-interne Methoden (Self-Calls):
      • CheckPackageDependencies(): Validierung von Software-Cluster-Abhängigkeiten und Manifest-Deklarationen.
      • cleanup(): Löschen temporärer Artefakte, freigeben von Flash-/Filesystem-Puffern.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Ruhezustand:
    • UCM Subordinate signalisiert dem State Management den Ausgangszustand CurrentStatus = :kIdle.
  2. Transfer-Phase:
    • Backend sendet Paketdaten via TransferData(). UCM Subordinate erzeugt eine TransferId und liefert diese an das Backend zurück.
  3. **Verarbeitungs-Phase (Processing):**
    • Backend initiiert Verarbeitung via ProcessSwPackage(TransferId).
    • UCM Subordinate signalisiert State Management den Status CurrentStatus = :kProcessing. UCM Subordinate extrahiert das Paket und verifiziert Signatur und Integrität.
  4. **Aktivierungs-Phase (Activation):**
    • Backend ruft Activate(): ActivateReturnType auf.
    • UCM Subordinate setzt CurrentStatus = :kActivating an State Management.
    • UCM Subordinate führt intern CheckPackageDependencies() aus.
    • UCM Subordinate quittiert den Methodenaufruf mit ActivateReturnType an das Backend.
  5. **Verifikations- & Neustart-Phase (Verification & Restart):**
    • UCM Subordinate setzt CurrentStatus = :kVerifying an State Management.
    • UCM Subordinate veranlasst den Neustart der Zielanwendung mittels restart() an :Adaptive Application.
    • Nach erfolgreichem Start signalisiert UCM Subordinate den Zustand CurrentStatus = :kActivated an State Management.
  6. **Abschluss & Bereinigung (Finish & Cleanup):**
    • Backend ruft Finish(): FinishReturnType auf.
    • UCM Subordinate setzt CurrentStatus = :kCleaning-up an State Management.
    • UCM Subordinate führt intern cleanup() zur Beseitigung temporärer Update-Dateien durch.
    • UCM Subordinate antwortet mit FinishReturnType an das Backend.
    • UCM Subordinate setzt CurrentStatus = :kIdle an State Management zurück und signalisiert damit die Einsatzbereitschaft für nachfolgende Aktionen.

4. Normative Relevanz & Entwickler-Hinweise

  • UCM & State Management API-Vertrag:
    • Das Backend darf Activate() und Finish() erst aufrufen, wenn die vorausgehenden Phasen erfolgreich terminiert wurden (TransferId gültig, ProcessSwPackage fehlerfrei beendet).
    • Der State Manager muss das Field CurrentStatus subskribieren, um Fahrzeug-Sicherheitszustände (z. B. ASIL-relevante Fahrmodi vs. Update-Sicherheitsmodus) abzusichern; während kActivating/kVerifying darf kein kritischer Betriebsmodus gewechselt werden.
  • Konsequenzen für Applikations-Entwickler (Adaptive Application):
    • Graceful Termination: Die Applikation muss POSIX-Terminierungssignale (SIGTERM) aus dem Execution Management innerhalb des im Execution Manifest definierten Timeouts (killTimeout) abfangen und persistente Zustände über ara::per konsistent speichern.
    • Data Migration: Ändert sich das Datenbankschema oder die Persistenzstruktur der Applikation, muss der Migrationspfad beim Hochlauf im Schritt restart() / kVerifying abwärtskompatibel greifen.
    • Self-Verification / Health Channel: Die Applikation muss dem Plattform-Monitoring (PHM/EM) schnellstmöglich melden, dass sie betriebsbereit ist (ReportApplicationState(kRunning)), da ein Verifikations-Timeout im Zustand kVerifying einen automatischen Rollback (Revert() / kRollingBack) durch das UCM auslöst.
