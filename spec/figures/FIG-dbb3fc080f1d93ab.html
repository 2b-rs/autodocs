Figure 3.7: Generate BSW Memory Mapping Header

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Activity Diagram (SPEM-basiertes Prozess-/Aktivitätsmodell gemäß AUTOSAR TR Methodology).
  • Technischer Zweck: Spezifikation der Entwurfs- und Generierungsaktivität Generate BSW Memory Mapping Header zur Erzeugung der modulspezifischen BSW-Speicherzuordnungs-Header (<Mod>_MemMap.h).
  • Funktionale Einordnung: Verortet im Integrationsprozess der Basic Software (BSW). Das Diagramm formalisiert die Transformation von abstrakten Software-Adressierungsmethoden (SwAddrMethod) und deklarierten Speichersektionen (MemorySection) eines BSW-Moduls in konkrete Präprozessor-Direktiven (Pragmas für Compiler/Linker) auf Basis der Ziel-ECU- und Toolchain-Konfiguration.

2. Komponenten, Entitäten & Schnittstellen

#### Akteure / Rollen (Performers)

  • ECU Integrator (Kardinalität 1, Beziehung: «performs»): Primärer, obligatorischer Durchführender. Verknüpft Modulanforderungen mit ECU-Ressourcen, Compilerspezifika und Linker-Sektionen.
  • Basic Software Module Developer (Kardinalität 0..1, Beziehung: «performs»): Optionaler Durchführender. Relevant, falls ein Modullieferant vorkonfigurierte Standard-MemMap-Dateien oder Stubs mitliefert.

#### Eingangsartefakte («input») & selektierte Metamodell-Elemente

  • Basic Software Module Description (BSWMD / ARXML):
  • +shortName (Kardinalität 0..1): Eindeutiger Modulbezeichner (z. B. Can, Det, Com) zur Bildung der modulspezifischen Makro-Präfixe.
  • VFB Types (ARXML):
  • +SwAddrMethod (Kardinalität 1..*): Deklaration semantischer Speicherklassen (z. B. CODE, VAR_CLEARED_8, CONST_UNSPECIFIED).
  • Basic Software Module Implementation Description (BSW Implementation / ARXML):
  • +MemorySections (Kardinalität 1): Deklaration aller im C-Code verwendeten Speichersektionen des BSW-Moduls.
  • +infixes (Kardinalität 1): Vendor-, Instance- oder API-Infixes zur Vermeidung von Namenskollisionen bei Multi-Instance- oder Multi-Vendor-Stacks.
  • +DependencyOnArtifact (Kardinalität 1): Formale Abhängigkeiten auf zu inkludierende Artefakte (z. B. Compiler-Abstraktion, Standard-Typen).
  • BSW Module Preconfigured Configuration (ARXML):
  • +MemMapAddressingModeSet (Kardinalität 1..*): Vordefinierte Abbildungsregeln zwischen SwAddrMethod und compilerspezifischen Adressierungsmodi (z. B. Far/Near, Bit-adressierbar).
  • ECU Configuration (Ecuc / ARXML):
  • +MemMapAllocation (Kardinalität 1): Explizite Zuweisung von MemorySections zu konkreten Speicherbereichen/Linker-Sektionen des Ziel-Derivats.
  • +moduleDescription (Kardinalität 0..1): ECU-spezifische Modulparametrierung und Instanzbezug.

#### Ausgangsartefakt («output»)

  • Standard Header Files:
  • +BSW_MemMap (Kardinalität 1): Generierter C-Header (<Mod>_MemMap.h, z. B. Can_MemMap.h), der die bedingten Präprozessor-Schalter (#define <MOD>_START_SEC_... / #undef ...) und die compilerspezifischen #pragma-Anweisungen enthält.

3. Dynamisches Verhalten & Sequenzablauf

  1. Konsolidierung der BSW-Deskriptoren (Start): Der Codegenerator aggregiert MemorySections, infixes und Modulidentifikator (shortName) aus der BSWMD/Implementation Description.
  2. Matching von SwAddrMethod & Addressing Modes: Abgleich der im Modul referenzierten SwAddrMethod-Definitionen mit den MemMapAddressingModeSet-Regeln der BSW-Preconfiguration.
  3. Auflösung der ECU-Allokation: Auswertung der MemMapAllocation aus der ECU Configuration, um systemspezifische RAM/ROM/Flash-Sektionen und Linker-Segmente für das Ziel-MCU-Derivat zuzuweisen.
  4. Präprozessor-Codegenerierung (Output): Erzeugung der Datei <Mod>_MemMap.h. Für jede deklarierte Sektion werden Start- und Stop-Makroblöcke generiert:

```c

#if defined (CAN_START_SEC_CODE)

#undef CAN_START_SEC_CODE

#pragma section code "CAN_CODE"

#elif defined (CAN_STOP_SEC_CODE)

#undef CAN_STOP_SEC_CODE

#pragma section code restore

#endif

```

  1. Fehlerbehandlung / Validierungsabbrüche: Unvollständige Mappings (z. B. MemorySection ohne zugeordnete SwAddrMethod oder fehlende MemMapAllocation in der Ecuc) führen zum Generierungsabbruch mit Validierungsfehler.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Entwickler (Modulerstellung):
  • Jeder C-Quellcode-Block (Funktionen, globale Variablen, Konstanten) muss zwingend über standardisierte MemMap-Klammern eingebunden werden:

```c

#define _START_SEC_

#include "_MemMap.h"

/ Deklaration / Definition /

#define _STOP_SEC_

#include "_MemMap.h"

```

  • Keine direkten Compiler-Pragmas im BSW-Quellcode verwenden (Sicherstellung der 100%igen Compiler- und Hardware-Portabilität gemäß AUTOSAR-Vorgabe).
  • ECU-Integrator (Stack-Integration):
  • Verantwortlich für die Konfiguration des Moduls MemMap im Ecuc-Modell (MemMapAllocation).
  • Muss sicherstellen, dass die generierten Header mit den Memory-Layout-Definitionen im Linker-Command-File (.ld / .icf) synchron sind.
  • Bei Multi-Core- oder MPU-geschützten Systemen ist hierüber die Segmentierung für OS-Applikationen und Core-lokalen Speicher (z. B. Scratchpad-RAM, Non-Cached Area) exakt zu steuern.
