1. Diagrammtyp & Architektur-Kontext

SPEM-2.0-basiertes Prozessdiagramm (Methodology Workflow) der AUTOSAR Adaptive Platform zur Definition und Konfiguration einer Maschine, umfassend Prozessabbildung, Modulkonfigurationen (Log and Trace, DoIP, NM) sowie Funktionsgruppen und zugehörige Timeout-Definitionen. Maschinenzustände werden vollständig über Funktionsgruppen modelliert.

2. Komponenten, Entitäten & Schnittstellen

  • Aktivitäten (Tasks):
  • Define ECU Description («SPEM_Task», (from Tasks)): Erzeugt ECU Resources Description («output», Kardinalität 1..*).
  • Map Process To Machine: Bildet Process («input», Kardinalität 1) auf Process to Machine Mapping ab («output», Kardinalität 1).
  • Configure OS for Adaptive Platform: Überführt Operating System for Adaptive Platform («input», Kardinalität 1) in Manifest-Inhalte für Machine Manifest («output», Kardinalität 0..1).
  • Describe Available HW Resources: Überführt ECU Resources Description («input», Kardinalität 1) in Hardware-Manifestanteile für Machine Manifest («output», Kardinalität 0..1).
  • Configure Log and Trace module: Verarbeitet optional Machine Design («input», Kardinalität 0..1) und liefert Konfigurationsanteile an Machine Manifest («output», Kardinalität 0..1).
  • Configure DoIP: Verarbeitet optional Machine Design («input», Kardinalität 0..1) und liefert DoIP-Konfigurationsanteile an Machine Manifest («output», Kardinalität 0..1).
  • Configure NM module: Verarbeitet optional Machine Design («input», Kardinalität 0..1) und liefert NM-Konfigurationsanteile an Machine Manifest («output», Kardinalität 0..1).
  • Define Function Groups: Spezifiziert Function Groups («output», Kardinalität 0..1).
  • Define State Timeouts: Liest Function Groups («input», Kardinalität 1) und erzeugt Per State Timeouts («output», Kardinalität 0..1).
  • Artefakte (Work Products):
  • Basis- und Eingangsartefakte: Process, Operating System for Adaptive Platform, ECU Resources Description, Machine Design.
  • Über Aggregation/Komposition («nesting») in Machine Manifest eingebettete Artefakte:
  • Process to Machine Mapping (Kardinalität 1..*)
  • Function Groups (Kardinalität 1)
  • Per State Timeouts (Kardinalität 1)
  • Zielartefakt: Machine Manifest.

3. Dynamisches Verhalten & Sequenzablauf

Der Workflow verläuft in getrennten, parallelen Pfaden:

  1. Prozessallokation: Map Process To Machine mappt Process-Definitionen in Process to Machine Mapping, das per «nesting» (1..*) an das Machine Manifest gebunden ist.
  2. OS- und Hardwareparameter: Configure OS for Adaptive Platform und Describe Available HW Resources befüllen das Machine Manifest direkt.
  3. Plattform-Dienste/Module: Configure Log and Trace module, Configure DoIP und Configure NM module beziehen optional architekturelle Vorgaben aus Machine Design und schreiben Konfigurationen in das Machine Manifest.
  4. Zustands- und Funktionsgruppensteuerung: Define Function Groups erzeugt Function Groups. Basierend ausschließlich auf Function Groups ermittelt Define State Timeouts die zeitlichen Limits (Per State Timeouts). Beide Modellelemente sind als Sub-Manifeste («nesting», je Kardinalität 1) fest an das Machine Manifest angebunden.

4. Normative Relevanz & Entwickler-Hinweise

Ab R19-11 entfällt das eigenständige Konzept separater Machine States zugunsten von Function Groups (in denen Maschinenzustände als dedizierte Funktionsgruppe MachineState abgebildet werden). Entwickler und Konfigurationswerkzeuge müssen Define State Timeouts ausschließlich an die definierten Funktionsgruppen koppeln. Die Schachtelungsregeln im Machine Manifest verlangen mindestens ein Process to Machine Mapping (1..*) sowie genau je eine Definition für Function Groups und Per State Timeouts (1).
