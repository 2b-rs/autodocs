1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-2.0-Klassendiagramm (Ausschnitt des M2-Metamodells der AUTOSAR-Spezifikation TPS BSW Module Description Template, Release R4.1.3).
  • Technischer Zweck: Spezifikation des Metamodells für ereignisgesteuerte Sender-Receiver-Kommunikation auf Basic-Software-Ebene (BSW). Es definiert die strukturelle Kopplung zwischen Datenprototypen (VariableDataPrototype), scheduler-relevanten BSW-Ereignissen (BswDataReceivedEvent) und ausführbaren Entitäten (BswSchedulableEntity).
  • Architektur-Einordnung: Ermöglicht dem BSW-Scheduler (SchM) bzw. der RTE die automatische Aktivierung und das Scheduling von BSW-Tasks bei Eintreffen neuer Daten über Modulgrenzen hinweg (primärer Anwendungsfall: partitions- und multicore-übergreifende BSW-zu-BSW-Kommunikation via IOC/OS).

2. Komponenten, Entitäten & Schnittstellen

#### Metaklassen

  • BswModuleDescription (Spezialisierung von ARElement, AtpBlueprint, AtpBlueprintable, AtpStructureElement): Oberstes Wurzelelement zur formalen Beschreibung eines BSW-Moduls.
  • BswInternalBehavior (Spezialisierung von InternalBehavior): Kapselt das interne Verhalten, Algorithmen, Ereignisse und Entitäten des BSW-Moduls.
  • VariableDataPrototype (Spezialisierung von AutosarDataPrototype): Konkreter Datenendpunkt für typisierte Sender-Receiver-Variablen auf BSW-Ebene.
  • BswModuleEntity (Spezialisierung von ExecutableEntity): Abstrakte Basiseinheit für ausführbaren Code innerhalb des BSW-Moduls.
  • BswSchedulableEntity (Spezialisierung von BswModuleEntity): Spezifische Entität, die direkt durch den BSW-Scheduler (SchM) in einem OS-Task-Kontext eingeplant und ausgeführt werden kann (entspricht im BSW dem Runnable eines SWCs).
  • BswEvent (Spezialisierung von AbstractEvent): Abstrakte Basisklasse aller Auslöser im BSW.
  • BswScheduleEvent (Spezialisierung von BswEvent): BSW-Event, das die Ausführung einer BswSchedulableEntity anstößt.
  • BswDataReceivedEvent (Spezialisierung von BswScheduleEvent): Konkretes Trigger-Event, das bei Empfang eines neuen Datenwerts an einem definierten VariableDataPrototype ausgelöst wird.

#### Beziehungen, Kardinalitäten & Stereotypen

  • BswModuleDescription $\rightarrow$ BswInternalBehavior: Komposition via +internalBehavior mit Kardinalität 0..* und Stereotyp «atpSplitable» (Verteilung der Verhaltensbeschreibungen über mehrere ARXML-Dateien zulässig).
  • BswModuleDescription $\rightarrow$ VariableDataPrototype:
  • +providedData [0..*], Stereotyp «atpVariation,atpSplitable» (gesendete S/R-Daten, varianzfähig).
  • +requiredData [0..*], Stereotyp «atpVariation,atpSplitable» (empfangene S/R-Daten, varianzfähig).
  • BswInternalBehavior $\rightarrow$ BswModuleEntity: Komposition via +entity [0..*], Stereotyp «atpVariation,atpSplitable».
  • BswInternalBehavior $\rightarrow$ BswEvent: Komposition via +event [0..*], Stereotyp «atpVariation,atpSplitable».
  • BswEvent $\rightarrow$ BswModuleEntity: Gerichtete Assoziation +startsOnEvent [0..1] (ein Event kann optional bis zu eine Entität starten; für BswDataReceivedEvent eine BswSchedulableEntity).
  • BswDataReceivedEvent $\rightarrow$ VariableDataPrototype: Gerichtete Assoziation +data [0..1] (referenziert optional das Datenelement, dessen Empfang das Event auslöst).

3. Dynamisches Verhalten & Sequenzablauf

  1. Datentransfer: Ein Sender-Modul (z. B. auf einem separaten Core oder in einer anderen OS-Partition) schreibt über eine generierte SchM-/RTE-API Daten in das konfigurierte VariableDataPrototype (referenziert über +requiredData der Empfängerseite).
  2. Event-Trigger: Das Eintreffen der Daten instanziiert bzw. signalisiert im SchM das zuständige BswDataReceivedEvent.
  3. Task-Aktivierung:
  • Über +startsOnEvent löst das BswDataReceivedEvent die verknüpfte BswSchedulableEntity aus.
  • Der SchM setzt das entsprechende OS-Event oder ruft ActivateTask() für den zugeordneten OS-Task auf (asynchroner Pfad).
  1. Ausführung: Die C-Implementierungsfunktion der BswSchedulableEntity wird im Kontext des zugeordneten OS-Tasks ausgeführt und liest die empfangenen Daten aus dem Puffer/IOC.
  2. Abbruch-/Fehlerpfade: Treten Pufferüberläufe oder Core-/Partitionsüberschreitungsfehler auf, greifen die zugrunde liegenden Mechanismen des OS/IOC (z. B. Det/Dem-Meldungen bei inkonsistenten SchM-Zuständen oder OS-Limits).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (ARXML):
  • Entwickler müssen für jedes datengetriebene BSW-Event ein BswDataReceivedEvent anlegen und die Referenz data auf genau ein VariableDataPrototype des Moduls setzen.
  • Das Ziel von startsOnEvent muss eine BswSchedulableEntity sein. Die Zuweisung zu einer BswCalledEntity ist unzulässig, da S/R-Events scheduler-getrieben und nicht über direkte Funktionsaufrufe (Client-Server) dispatcht werden.
  • BSW-Scheduler (SchM) & Multicore:
  • Bei Core- oder Partitionsgrenzen generiert der SchM-Generator die Inter-Partition- bzw. Inter-Core-Synchronisation (z. B. AUTOSAR IOC, Inter-Core-Interrupts).
  • Entwickler müssen im OS- und SchM-Modul sicherstellen, dass die Task-Mapping-Konfiguration (OsTask, Task-Priorität, Event-Masken) auf die Ausführungszeit und Latenzanforderungen der BswSchedulableEntity abgestimmt ist.
  • Variantenmanagement:
  • Wegen «atpVariation» an providedData, requiredData, entity und event können S/R-Schnittstellen und Event-Trigger über Pre-Compile- oder Post-Build-Kriterien bedingt ein- oder ausgeschlossen werden.
