1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (Metamodell-Ausschnitt der AUTOSAR Template-Spezifikation für die ECU-Konfiguration, TPS_ECUConfiguration).
  • Architektur-Einordnung: Definition der Konfigurations-Metaklassen auf Parameter-Definitionsebene (Parameter Definition Layer, BSWMD / BSW Module Description). Es spezifiziert das formale Schema, nach dem BSW-Modul- und SWC-Parameter in EcucParamConfContainerDef-Containern typisiert, validiert, begrenzt und mit Standardwerten vorbelegt werden, bevor zur Generierungs- und Konfigurationszeit konkrete Wertebelegungen (EcucParameterValue) in ARXML instanziiert werden.

2. Komponenten, Entitäten & Schnittstellen

#### Zentrale Container- und Basisklassen

  • EcucParamConfContainerDef (Spezialisierung von EcucContainerDef): Repräsentiert die Definitionsstruktur eines Konfigurationscontainers. Besitzt eine Aggregation/Komposition auf Parameterdefinitionen.
  • Beziehung zu EcucParameterDef: Komposition mit Multiplizität * (Rollenname +parameter), versehen mit dem Stereotyp «atpSplitable» (Verteilung der Parameterdefinitionen über mehrere physische ARXML-Dateien/Fragmente zulässig).
  • EcucParameterDef (erbt von EcucCommonAttributes / Identifiable): Abstrakte Basisklasse aller skalaren Konfigurationsparameter.
  • Attribute:
  • symbolicNameValue: Boolean: Bestimmt, ob der Parameterwert als Bezeichner/Makro für symbolische Namensadressierung (z. B. Generierung von C-Identifiern/Handles wie #define CANIF_TX_PDU_ID 1U) dient.
  • withAuto: Boolean [0..1]: Gibt an, ob das Konfigurationswerkzeug den Parameterwert automatisch berechnen darf/muss.

#### Spezifische Parameterspezialisierungen (Generalisierungen von EcucParameterDef)

  • EcucBooleanParamDef: Boolescher Parameter (true/false).
  • defaultValue: Boolean [0..1] («atpVariation»: Wert ist über AUTOSAR-Systemkonstanten/Post-Build-Varianten bindbar).
  • EcucIntegerParamDef: Diskreter ganzzahliger Parameter.
  • Attribute: defaultValue: UnlimitedInteger [0..1] («atpVariation»), min: UnlimitedInteger [0..1], max: UnlimitedInteger [0..1] (definiert gültige Wertegrenzen).
  • EcucFloatParamDef: Fließkomma-Parameter (IEEE 754).
  • Attribute: defaultValue: Float [0..1] («atpVariation»), min: Limit [0..1], max: Limit [0..1].
  • EcucEnumerationParamDef: Typisierte Aufzählung.
  • Aggregation zu EcucEnumerationLiteralDef: Multiplizität 0..* (Rollenname +literal, «atpSplitable»).
  • Assoziation zu Identifier: Multiplizität 0..1 (Rollenname +defaultValue).
  • EcucEnumerationLiteralDef (erbt von Identifiable): Definiert ein einzelnes Literal einer Aufzählung.
  • Attribut: origin: String (gibt den Ursprung an, z. B. Modul- oder Norm-Ursprung).
  • EcucAddInfoParamDef: Parameter für zusätzliche beschreibende Metadaten ohne direkten Einfluss auf den generierten C-Code.
  • EcucAbstractStringParamDef (abstrakt, versehen mit «atpVariation»): Basis für alle textuellen Parametertypen.
  • Attribute: defaultValue: VerbatimString [0..1], maxLength: PositiveInteger [0..1], minLength: PositiveInteger [0..1], regularExpression: RegularExpression [0..1].
  • Subklassen:
  • EcucStringParamDef: Standard-Zeichenkette.
  • EcucMultilineStringParamDef: Mehrzeiliger Text (z. B. Dokumentation, Beschreibungsblöcke).
  • EcucFunctionNameDef: Bezeichner für Funktionsnamen im C-Code.
  • EcucLinkerSymbolDef: Bezeichner für Linker-Symbole.

#### Primitive Datentypen

  • Identifier («primitive»): Bezeichner-Zeichenkette.
  • Attribute: blueprintValue: String [0..1], namePattern: String [0..1].
  • VerbatimString («primitive»): Formatierungsgetreue Zeichenkette mit Tags xml.xsd.customType = VERBATIM-STRING, xml.xsd.type = string, xml.xsd.whiteSpace = preserve.
  • Attribute: blueprintValue: String [0..1], xmlSpace: XmlSpaceEnum [0..1].
  • RegularExpression («primitive»): Regulärer Ausdruck zur syntaktischen Validierung von Zeichenketten.

3. Dynamisches Verhalten & Sequenzablauf

  • Nicht zutreffend (Statisches Metamodell): Das Diagramm bildet keine Laufzeit-Dynamik (keine RTOS-Tasks, PDU-Routen oder Callbacks wie Det/Dem) ab.
  • Tool- und Phasenablauf (Build- & Konfigurationszeit):
  1. BSWMD-Parsing: Konfigurationswerkzeug liest EcucParameterDef aus der Modulbeschreibungsdatei ein.
  2. Wertevalidierung: Eingegebene Werte werden gegen min/max (EcucIntegerParamDef, EcucFloatParamDef) bzw. regularExpression, minLength/maxLength (EcucAbstractStringParamDef) validiert.
  3. Variabilitäts-Auflösung: Attribute mit Stereotyp «atpVariation» (z. B. defaultValue) werden anhand des ausgewählten Bindungszeitpunkts (Pre-Compile, Link-Time, Post-Build) und des aktiven System-Variantenkriteriums aufgelöst.
  4. Code-Generierung: Generator liest symbolicNameValue aus; bei true wird ein Makro/Enum-Identifier im Header erzeugt. EcucFunctionNameDef erzeugt Funktionsdeklarationen/Prototypen (z. B. Notification-Callbacks im RTE/BSW).

4. Normative Relevanz & Entwickler-Hinweise

  • C-Code-Generierung & Typ-Mapping:
  • EcucIntegerParamDef mit gesetztem symbolicNameValue = true erzeugt semantische C-Defines (z. B. #define CanIf_CanId_Msg1 0x100u).
  • EcucBooleanParamDef mapped typischerweise auf STD_ON / STD_OFF oder TRUE / FALSE (boolean).
  • EcucFunctionNameDef zwingt Treiber- und Stack-Entwickler, standardkonforme C-Funktionssignaturen bereitzustellen; fehlerhafte Syntax wird bereits auf XML-Ebene via Schema/Regex abgefangen.
  • EcucLinkerSymbolDef steuert das Memory-Mapping (MemMap.h-Sektionen wie #pragma section oder Linkerscript-Symbole).
  • Varianten-Management («atpVariation»):
  • Entwickler müssen beachten, dass Parameter mit «atpVariation» varianzfähig sind. Bei Post-Build-Varianten werden diese Parameter nicht als Compile-Time-Makros (#define), sondern in ROM/RAM-Konfigurationsstrukturen (ConfigType) abgelegt.
  • Splitability («atpSplitable»):
  • Container-Parameter und Enumeration-Literale können über mehrere ARXML-Dateien verteilt definiert werden. Im Integrationsprozess müssen Werkzeuge Merging unterstützen; Entwickler dürfen keine Annahmen über eine monolithische Dateistruktur treffen.
  • Automatische Konfiguration (withAuto):
  • Wenn withAuto == true, dürfen Werte nicht fest eincodiert werden, sondern müssen durch Konsistenzgeneratoren / ECU-Konfiguratoren auf Basis der System Description (z. B. Netzwerk-Timing, PDU-Längen) deterministisch errechnet werden.
