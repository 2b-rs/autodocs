1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Architektur- und Transformationsdiagramm / Methodik-Flussdiagramm (AUTOSAR Methodology View).
  • Technischer Zweck: Visualisierung des Entwurfsschritts „Configure System“ (System Configuration). Das Diagramm stellt den methodischen Übergang von der hardware- und topologieunabhängigen Modellierungsebene (VFB-Sicht) zur konkreten Allokation (Mapping) auf physische Steuergeräte (ECUs) und Kommunikationsnetzwerke dar.
  • Funktionale Einordnung: Kernprinzip des AUTOSAR Virtual Functional Bus (VFB). Es demonstriert die Relocatability (Verschiebbarkeit) von AUTOSAR Software-Components (SW-Cs) durch Kapselung von Infrastruktur- und Transportmechanismen hinter standardisierten Port-Schnittstellen und deren Auflösung zur Entwurfs-/Generierungszeit über die RTE (Run-Time Environment).

2. Komponenten, Entitäten & Schnittstellen

  • Entwurfsebene (VFB View – Oben):
    • AUTOSAR SW-C 1 .. n: Kapselung funktionaler Einheiten (Application / Sensor-Actuator Software Components).
    • SW-C Description (ARXML): Formale Komponentenbeschreibung (SwComponentType, InternalBehavior, PortInterface, Runnables, Events).
    • VFB-Ports & Schnittstellensymbole:
      • P-Ports (Provided) / R-Ports (Required): Repräsentiert durch Rechteck-/Dreieck-/Ball-and-Socket-Metaphern an der SW-C-Grenze.
      • Sender-Receiver-Kommunikation: Datenorientierte Interaktion (asynchron / datenflussgesteuert).
      • Client-Server-Kommunikation: Operationsorientierte Interaktion (synchron / asynchroner Funktionsaufruf).
    • Virtual Functional Bus (VFB): Abstrakte logische Kommunikationsmatrix; entkoppelt Kommunikationsbeziehungen (AssemblyConnector, DelegationConnector) vollständig von physikalischen Busprotokollen.
  • Eingangsartefakte des System-Tools (Mitte):
    • Tool supporting deployment of SW components: Systemkonfigurations-Werkzeug (System Authoring Tool / Mapping Tool).
    • ECU Descriptions: Beschreibung der Hardware-Ressourcen (Prozessorarchitektur, Speicherbereiche, I/O, Transceiver, BSW-Fähigkeiten).
    • System Constraint Description: Randbedingungen für die Allokation (u. a. Mapping-Constraints, Sicherheitsanforderungen gem. ASIL, Busbandbreiten, Latenzen, Co-Location- oder Separation-Vorgaben).
  • Zieltopologie (Mapping View – Unten):
    • Knotenallokation:
      • ECU I: Beherbergt SW-C 1 und SW-C 3 → Intra-ECU-Kommunikation.
      • ECU II: Beherbergt SW-C 2 → Inter-ECU-Kommunikation über Bussegment 1.
      • ECU m: Beherbergt SW-C n → Netzübergreifende Kommunikation via Gateway.
    • Schichtenstruktur je ECU:
      • RTE: Konkrete softwaretechnische Realisierung des VFB für das jeweilige Steuergerät.
      • Basic Software (BSW): System Services, Memory Stack, I/O Hardware Abstraction, Communication Stack (Com, PduR, Bus-Treiber).
      • Netzwerkinfrastruktur: Physische Busse (z. B. CAN, FlexRay, LIN) gekoppelt über ein Gateway.
  • Kardinalitäten & Zuordnungen:
    • Software Component Type zu Prototype: 1 : n (Mehrfachinstanziierung möglich).
    • SW-C Prototype zu ECU: n : 1 (jede SW-C-Instanz wird exakt einer ECU zugewiesen).
    • Virtual Connection zu Physical Mapping:
      • Intra-ECU: Direktes Mapping auf RTE-interne Puffer / Pointer / Task-Aktivierungen.
      • Inter-ECU: 1 : 1 oder 1 : n Mapping via RTE → COM → PduR → Schnittstellentreiber → Physisches Netzwerk.

3. Dynamisches Verhalten & Sequenzablauf

  1. VFB-Modellierung: Definition von Typen, Interfaces, Datenstrukturen und logischen Konnektoren (AssemblySwConnector) im Systemmodell ohne Kenntnis der Ziel-Hardware.
  2. Artefakt-Zusammenführung (Configure System):
    • Das System-Tool konsolidiert SW-C-Beschreibungen, Netzwerk-Topologie, ECU Descriptions und System Constraints.
    • Synthese des System Extract: Zuweisung (SwcToEcuMapping) der Runnables und Instanzen auf konkrete ECUs.
    • Signal- und Frame-Mapping: Ableitung von System-Signalen aus VFB-Sender-Receiver-Elementen; Bündelung in I-PDUs; Zuweisung zu Kommunikationsclustern (Busse, Frames, Schedules, Gateway-Routingtabellen).
  3. RTE-Transformation zur Laufzeit:
    • Intra-ECU-Pfad (SW-C 1 ↔ SW-C 3 auf ECU I): VFB-Aufruf wird durch RTE-Generator direkt in shared-memory Zugriffe, geschützte Variablen (OS-Interrupt-Sperre, Spinlocks) oder OS-Inter-Task-Events übersetzt. Der Com-Stack wird umgangen.
    • Inter-ECU-Pfad (SW-C 1 ↔ SW-C 2 via Bus): VFB-Aufruf wird zu Rte_Write_* → Com_SendSignal → PDU-Assembly → Busübertragung.
    • Inter-Cluster-Pfad (SW-C 2 ↔ SW-C n via Gateway): Signal wird auf ECU II gesendet, am Gateway empfangen, umgepackt (PduR-Gatewaying bzw. Com-Signal-Gatewaying) und auf das Bussegment von ECU m geroutet.

4. Normative Relevanz & Entwickler-Hinweise

  • Applikationsentwickler (SW-C):
    • Reine C-API-Programmierung: Applikationscode greift ausschließlich über standardisierte RTE-APIs zu (Rte_Read_<p>_<o>(), Rte_Write_<p>_<o>(), Rte_Call_<p>_<o>()). Direkte Zugriffe auf BSW-Module, Treiber oder Register sind normativ verboten.
    • Zero Communication Overhead Awareness: Für den Algorithmus bleibt transparent, ob der Kommunikationspartner lokal auf demselben Core, auf einem anderen Core oder auf einer externen ECU läuft.
  • BSW- und Stack-Entwickler:
    • Das Mapping entscheidet über die Generierung des Communication Stacks (Com, PduR, CanIf, LinIf, FrIf).
    • Signale mit Inter-ECU-Bedarf erfordern Signal-Group-Konfigurationen, Endianness-Konvertierungen und Übertragungsmodi (Cyclic, Triggered).
  • System- und Integrations-Engineers:
    • Timing & Latenzen: Das Verschieben einer SW-C (Relocation) von Intra-ECU auf Inter-ECU transformiert Mikrosekunden-Laufzeiten (Speicherzugriff) in Millisekunden-Latenzen (Buszyklen, Serialisierung, Gateway-Jitter).
    • Artefakt-Abhängigkeit: Änderungen an SW-C-Ports oder Schnittstellen bedingen eine Re-Generierung der RTE und des System Extracts (ECU Extract of System Configuration).

Figure 2.2: Detailed view on the activity “Configure System” In AUTOSAR, an application is modeled as a composition of interconnected components. This is illustrated in the top half of Figure 2.2 (labeled “VFB view”). The “virtual functional bus” is the communication mechanism that allows these components to interact. In a design step called “Configure System”, the components are mapped on specific system resources (ECUs). Thereby, the virtual connections between the components are mapped onto local connections (within a single ECU) or on network-technology specific communication mechanisms (such as CAN or FlexRay frames). Finally, the individual ECUs in such a system can be configured. The concrete interface between the components and the rest of the system on an ECU is called the Run-Time Environment (RTE), which is defined in [Specification of RTE Software]. A component encapsulates complete or partial automotive functionality. Components consist of an implementation and of an associated formal software-component description (defined in [Software Component Template]). The concept of the virtual functional bus allows for a strict separation between applications and infrastructure. The software components implementing the application are largely independent of the communication mechanisms through which the component interacts with other components or with hardware (such as sensor or actuators).
