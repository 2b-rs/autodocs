1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML 2.0 Sequenzdiagramm (sd ECU Shutdown Sequence).
  • Architektur-Kontext: AUTOSAR Classic Platform (CP), Spezifikation des BSW-Moduls HWTestManager (hier: Submodul/Dienst HTMSS – Hardware Test Manager Shutdown and Startup) im Verbund mit System Management (EcuM, BswM), OS, RTE, Applikations-SWC, MCAL (MCU) und herstellerspezifischem Selbsttest-Paket (MSTP).
  • Funktionale Einordnung: Steuerung und Absicherung destruktiver bzw. reset-erzwingender Hardware-Selbsttests während des Steuergeräte-Herunterfahrens. Da Hardware-Tests beim Shutdown (z. B. Core-/Memory-BIST) einen Mikrocontroller-Reset auslösen, wird der Shutdown-Prozess als zweistufiger Zyklus (Two-Stage Shutdown Cycle) abgewickelt: Phase 1 führt die Tests aus und triggert den Reset; Phase 2 wertet nach dem Neustart die Testergebnisse aus und führt den tatsächlichen System-Shutdown herbei.

2. Komponenten, Entitäten & Schnittstellen

Beteiligte Lebenslinien (Akteure / BSW-Module)
  • µC reset: Hardware-Ebene des Mikrocontrollers (Reset-Generierung).
  • BswM: Basic Software Manager (Modus- und Regelauswertung, Initiierung von Shutdown-Zielen und State-Transitions).
  • RTE: Runtime Environment (VFB-Transportschicht zwischen SW-C, HTMSS und BswM).
  • SW_C: Application Software Component (Applikative Auswertung der Testergebnisse, Diagnosemeldung via DEM, Persistierung in NvM).
  • OS: AUTOSAR Operating System (ShutdownOS(), StartOS(), Aufruf von OS-Hooks).
  • EcuM: ECU State Manager (Zustandsverwaltung, Halten des Shutdown-Ziels EcuM_ShutdownTargetType).
  • Integrator Code: Anwender-/Integrationsschicht (Implementierung des ShutdownHook()).
  • HTMSS: Hardware Test Manager Shutdown/Startup (Koordination und Statusüberwachung der HW-Tests vor/nach Reset).
  • MSTP wrapper: Abstraktionsschicht zur Kapselung herstellerspezifischer Testbibliotheken.
  • MSTP: Microcontroller Software/Self-Test Package (Silicon-Vendor-spezifische Testroutinen für CPU, Cache, RAM, Busse).
  • MCU: Microcontroller Driver (MCAL; Auslesen des Hardware-Reset-Grundes).
Schnittstellen & Interaktionspunkte
  • BSW C-APIs (Synchron):
    • EcuM_SelectShutdownTarget(EcuM_ShutdownTargetType, EcuM_ShutdownModeType) / EcuM_GoDown(Std_ReturnType, uint16)
    • ShutdownOS() / ShutdownHook() / EcuM_Shutdown()
    • HTMSS_StartTest(Shutdown) / Starttest()
    • EcuM_Init() / StartOS()
    • MCU_GetResetReason(Mcu_ResetType)
    • HTMSS_GetTestStatus(Shutdown, NULLPTR)
  • VFB / RTE-Schnittstellen:
    • Client-Server: Rte_Call(GrpId, DstPtr) → Aufruf von HTMSS_GetTestStatus(Shutdown, *ResultPtr).
    • Sender-Receiver: Rte_Write(Shutdown) (SW-C → RTE) und Rte_Read(Shutdown) (BswM ← RTE).

3. Dynamisches Verhalten & Sequenzablauf

Sequenz 1: Initiierung des Shutdown-Tests & erzwungener Reset
  1. BswM ruft EcuM_SelectShutdownTarget() mit Ziel HWTEST_OFF oder HWTEST_RESET auf.
  2. BswM leitet den Shutdown über EcuM_GoDown() ein.
  3. EcuM ruft ShutdownOS(). Das OS triggert im ShutdownHook() den Integrator-Code, welcher EcuM_Shutdown() aufruft.
  4. Bedingter Pfad (alt [EcuMShutdownTarget == (HWTEST_OFF || HWTEST_RESET)]):
    • EcuM ruft HTMSS_StartTest(Shutdown).
    • HTMSS delegiert via MSTP wrapper an MSTP::Starttest().
    • Die Testausführung führt bestimmungsgemäß zum Hardware-Reset (µC reset).
Sequenz 2: Post-Reset-Initialisierung & BSW-Statusabfrage
  1. Nach dem Reset startet EcuM_Init().
  2. EcuM liest die Reset-Ursache über MCU_GetResetReason(Mcu_ResetType).
  3. Bedingter Pfad (alt [Mcu_ResetType == MCU_HWTEST_RESET]):
    • EcuM validiert die Ausführung via HTMSS_GetTestStatus(Shutdown, NULLPTR).
  4. EcuM startet das Betriebssystem via StartOS().
Sequenz 3: Applikative Testergebnis-Bewertung (SW-C)
  1. Das OS führt Initialize SW-C() aus.
  2. Bedingter Pfad (alt [EcuLastShutdownTarget == (HWTEST_OFF || HWTEST_RESET)]):
    • SW_C ruft via RTE (Rte_Call) HTMSS_GetTestStatus(Shutdown, *ResultPtr) auf.
    • SW_C evaluiert das Ergebnis (Evaluates Shutdown TestResult()): Bereitstellung für NvM-Speicherung und Fehlerspeichereintrag via DEM.
    • SW_C übergibt den Status via Rte_Write(Shutdown) an die RTE.
Sequenz 4: Finaler System-Shutdown
  1. Im zyklischen BswM_MainFunction() liest der BswM den Status via Rte_Read(Shutdown).
  2. Da die Tests abgeschlossen sind, setzt der BswM das reale Shutdown-Ziel: EcuM_SelectShutdownTarget(OFF || RESET).
  3. BswM ruft erneut EcuM_GoDown().
  4. Ablauf über ShutdownOS() → ShutdownHook() → EcuM_Shutdown().
  5. Da EcuMShutdownTarget nun regulär auf OFF bzw. RESET steht, wird der alt-Pfad für HTMSS_StartTest übersprungen; das Steuergerät schaltet final ab bzw. geht in den Sleep/Power-Down.

4. Normative Relevanz & Entwickler-Hinweise

  • Two-Stage Shutdown & Nichtflüchtiger Speicher (Note 1):
    • Vor dem ersten Shutdown muss das Target (ECUM_SHUTDOWN_TARGET_HWTEST_OFF / _RESET) applikativ oder im BswM persistent im nichtflüchtigen Speicher (NvM oder Warm-Start-resistenter RAM-Sektor) hinterlegt werden.
    • Nach dem Reboot muss die Applikation anhand dieses Flags und des MCU_HWTEST_RESET erkennen, dass die zweite Phase aktiv ist, um im Anschluss zwingend ECUM_SHUTDOWN_TARGET_OFF / _RESET zu wählen. Eine Endlosschleife aus Test-Shutdowns muss softwareseitig ausgeschlossen werden.
  • MCU-Treiber-Konfiguration (MCAL):
    • Die Reset-Reason-Erkennung des MCU-Treibers muss in der Lage sein, den durch das MSTP ausgelösten Reset eindeutig auf den Enumerator MCU_HWTEST_RESET (bzw. den entsprechenden vendor-spezifischen Reset-Typ) abzubilden.
  • Integrator-Restriktionen im Shutdown-Kontext:
    • HTMSS_StartTest(Shutdown) läuft nach ShutdownOS() im Kontext von EcuM_Shutdown(). Zu diesem Zeitpunkt sind keine OS-Dienste, keine RTE-Kommunikation und keine Interrupts mehr verfügbar. Der MSTP wrapper und das MSTP müssen vollständig autark und pollingbasiert im Polled-Mode auf Bare-Metal-Ebene operieren.
  • Diagnose & Fehlermanagement (DEM/FUSA):
    • Schlägt ein Shutdown-Test fehl, kann dies erst in Phase 2 nach dem Warmstart an das DEM gemeldet werden. Entwickler von Sicherheitsmechanismen (ISO 26262, ASIL-D Metriken) müssen sicherstellen, dass bei fehlgeschlagenem Test im zweiten Zyklus eine definierte Sicherheitsreaktion (z. B. Übergang in einen Safe-State statt normalem Power-Down) eingeleitet wird.
