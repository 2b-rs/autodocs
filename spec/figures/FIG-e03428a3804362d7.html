1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Layered Architecture Block Diagram (AUTOSAR Classic Platform Schichtenarchitektur) mit instanziiertem Mapping von Software-Komponenten (SWCs) und Basessoftware-Modulen (BSW).
  • Funktionaler Zweck & Einordnung:
    • Architekturelle Dekomposition eines funktionalen Sicherheits-Anwendungsfalls (Safety Use Case: Front Light Management / Headlight Control) nach ISO 26262 im Kontext von AUTOSAR_EXP_SafetyUseCase.
    • Gegenüberstellung zweier komplementärer I/O- und Kommunikationspfade:
      1. Bussystem-Pfad (CAN): Netzwerktransceiver, Controller-Treiber, Abstraktions- und Protokollstack bis AUTOSAR COM.
      2. Diskreter I/O-Pfad (MCAL & Abstraktion): Direkte Hardware-Anbindung von Schaltern, Sensoren und Aktoren via DIO, ADC und SPI.

2. Komponenten, Entitäten & Schnittstellen

  • Application Layer (SWC Layer):
    • Sensor SWC SwitchEvent: Typ SensorActuatorSoftwareComponentType; erfasst Fahrereingaben (z. B. Lichtdrehschalter, Fernlichthebel).
    • Application SWC LightRequest: Typ ApplicationSoftwareComponentType; interpretiert Roh-Events und berechnet die funktionale Lichtanforderung.
    • Application SWC FLM (Front Light Manager): Typ ApplicationSoftwareComponentType; zentrale Sicherheits- und Schaltungslogik (Plausibilisierung, Priorisierung, Zustandskontrolle).
    • Actuator SWC Headlight: Typ SensorActuatorSoftwareComponentType; physikalische Treiberschnittstelle für Scheinwerfer-Stellglieder (LED/Halogen-Stufen).
  • Runtime Environment (RTE):
    • Entkoppelt den SWC-Layer vollständig von der BSW. Realisiert Sender-Receiver- (SR) und Client-Server- (CS) Kommunikationsmechanismen sowie Inter-Runnable-Triggering.
  • System Services:
    • AUTOSAR OS: Präemptives Echtzeitbetriebssystem (vertikal über alle Schichten gespannt); stellt Tasks, ISRs, Ressourcen und Speicherschutz (MPU) bereit.
    • BSW Scheduler (SchM): Scheduling der BSW-Main-Functions und Kapselung kritischer Sektionen.
    • BSW Mode Manager (BswM): Schaltet System- und Kommunikationsmodi basierend auf Regeln und Zuständen.
    • Communication Manager (ComM): Steuert Kommunikationskanäle (Full-Com, Silent-Com, No-Com).
    • ECU State Manager (EcuM): Verwaltet Startup-Phasen, Sleep/Wakeup und Shutdown der ECU.
  • Communication Stack (CAN-Zweig):
    • Communication Services: AUTOSAR COM (Signal-Serialisierung, Signal-Gateway), PDU Router (PduR) (I-PDU-Routing), CAN-Transport Protocol (CanTp) (Segmentierung/Reassemblierung), CAN-State-Manager (CanSM) (Bus-Zustandsverwaltung).
    • Communication Hardware Abstraction: CAN-Interface (CanIf) (Hardwareunabhängige Schnittstelle), CAN-Transceiver-Driver (CanTrcv).
    • Communication Drivers (MCAL): CAN-Driver (Can) zur Ansteuerung des integrierten CAN-Controllers; SPI-Driver (Spi) für Bus-/Transceiver-Kopplung.
  • I/O Stack (MCAL & Abstraktion):
    • I/O Hardware Abstraction: DIO-Handler, ADC-Handler, SPI-Handler (abstrahieren ECU-spezifische Pin-Zuordnungen für die SWCs).
    • I/O Drivers (MCAL): Port-Driver (Port) (globale Pin- und Multiplex-Konfiguration), DIO-Driver (Dio) (Pin-Level I/O), ADC-Driver (Adc) (Analogwerterfassung).
  • Inaktive / Nicht-Instanziierte Blöcke:
    • Memory Services (NvM), Memory Hardware Abstraction (MemIf), Memory Drivers (Fls/Eep): Für den Echtzeit-Lichtsteuerpfad nicht funktional eingebunden.
    • Complex Drivers (CDD): Als Architektur-Option dargestellt, für den Standard-Pfad jedoch nicht spezifisch instanziiert.

3. Dynamisches Verhalten & Sequenzablauf

  1. Eingangs-Erfassung (Dual-Path):
    • Lokaler Pfad: Schalterposition wird via Port/Dio/Adc (MCAL) erfasst, über den DIO-Handler/ADC-Handler abstrahiert und via RTE als Input an Sensor SWC SwitchEvent übergeben.
    • Bus-Pfad: Lichtanforderung über das Fahrzeugnetzwerk trifft am CAN-Controller ein -> ISR -> CanIf_RxIndication -> PduR -> Com_RxIndication -> RTE puffert Signal für Sensor SWC SwitchEvent oder Application SWC LightRequest.
  2. Signalverarbeitung & Arbitrierung:
    • Sensor SWC SwitchEvent sendet Schalterzustand via Sender-Receiver-Port über die RTE an Application SWC LightRequest.
    • LightRequest formatiert den Wunschwert und leitet ihn an FLM (Front Light Manager) weiter.
    • FLM evaluiert den Systemstatus (Klemme 15, Umgebungslicht, EcuM/BswM-Zustand) und führt Sicherheitsabgleiche durch (z. B. Erkennung von Signalverlust -> Fail-Safe Default: Abblendlicht EIN).
  3. Aktor-Ansteuerung:
    • FLM kommandiert Actuator SWC Headlight.
    • Headlight schreibt die Schalt- oder Dimmstufen:
      • Direkt via RTE -> DIO-Handler / SPI-Handler -> Dio_WriteChannel / Spi_SyncTransmit / Spi_AsyncTransmit an die Leistungstreiber-Hardware (DIO, SPI).
      • Alternativ via AUTOSAR COM -> PduR -> CanIf an abgesetzte intelligente Scheinwerfermodule.

4. Normative Relevanz & Entwickler-Hinweise

  • ASIL-Einstufung & Freedom from Interference (FFI):
    • Scheinwerfersteuerungen unterliegen typischerweise Sicherheitsanforderungen (z. B. ASIL B gegen unbeabsichtigtes Ausschalten bei Nacht).
    • AUTOSAR OS muss zwingend als Safety OS (Scalability Class 3 oder 4) mit hardwarebasierter MPU konfiguriert werden, um Speicherzugriffe zwischen FLM/Headlight (ASIL) und unterlagerten QM-Software-Komponenten zu isolieren.
  • Treiber-Zuständigkeit (Port vs. Dio):
    • Pins für Schalter und Scheinwerfer-Stufen müssen einmalig statisch im Port-Modul während des EcuM-Startups initialisiert werden (Port_Init).
    • Laufzeitänderungen dürfen ausschließlich über Dio-APIs erfolgen; rekonfigurierende Aufrufe auf Port zur Laufzeit sind unzulässig.
  • Kommunikations-Bereitschaft (BswM / ComM):
    • Das Senden von Scheinwerfer-Statusbotschaften über COM schlägt fehl, solange der Kommunikationskanal nicht über ComM_RequestComMode(..., COMM_FULL_COMMUNICATION) freigegeben und durch den CanSM in den Modus CANSM_BSM_FULL_COMMUNICATION überführt wurde.
  • Timing & Latenzen (I/O-Abstraktion vs. CDD):
    • Die Durchlaufzeit über den Schichtenpfad (Port/Dio -> DIO-Handler -> RTE -> SWC) ist durch die Abtast-Task des SchM/RTE determiniert.
    • Müssen sicherheitskritische Abschaltzeiten im Sub-Millisekundenbereich (z. B. Kurzschlusserkennung an High-Side-Schaltern) garantiert werden, ist der Einsatz des rechts dargestellten Complex Drivers (CDD) unter Umgehung der I/O-Hardware-Abstraktion vorzuziehen.
