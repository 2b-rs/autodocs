1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: SPEM 2.0 (Software & Systems Process Engineering Metamodel) Task-Definition / Prozessflussdiagramm der AUTOSAR-Methodologie (Methodology Work Breakdown Structure).
  • Technischer Zweck: Spezifikation des methodischen Arbeitsschritts zur Modellierung von Sensor- und Aktor-Software-Komponenten (SensorActuatorSwComponentType).
  • Einordnung im Gesamtsystem: Frühe System- und VFB-Entwurfsphase (Virtual Function Bus). Der Task verbindet abstrakte VFB-Elemente (Datentypen, Schnittstellen) mit konkreten Steuergeräte-Hardwareressourcen (ECU Resources Description), um hardwareabhängige Softwarekomponenten formal in ARXML zu deklarieren, bevor die Systemkonfiguration und das ECU-Mapping stattfinden.

2. Komponenten, Entitäten & Schnittstellen

#### Akteure & Rollen

  • Software Component Designer («performs», SPEM Role Definition): Verantwortlicher Funktions- und Softwarearchitekt, der die formale Spezifikation der SWC durchführt.

#### Prozess-Task

  • Define VFB Sensor or Actuator Component (SPEM Task Definition): Der zentrale Ausführungsschritt im Komponenten-Entwurf.

#### Eingangs-Artefakte (Input Work Products)

  • VFB Interfaces («input», Kardinalität 1..*):
  • Port-Interfaces (Sender-Receiver-Interfaces, Client-Server-Interfaces, Mode-Switch-Interfaces), die die Interaktionspunkte der Komponente definieren.
  • VFB Types («input», Kardinalität 1..*):
  • AUTOSAR-Datentypen (ApplicationDataType, ImplementationDataType), Skalierungen (CompuMethod) sowie Wertebereichsgrenzen (DataConstr).
  • VFB AUTOSAR Standard Package («input», Kardinalität 0..1):
  • Standardisierte AUTOSAR-Bibliotheken (z. B. vordefinierte Basis-Datentypen, standardisierte Schnittstellen und Einheiten).
  • ECU Resources Description («input», Kardinalität 0..*):
  • Beschreibung der physischen Steuergeräte-Ressourcen (I/O-Pins, ADC-, PWM- oder SPI-Kanäle). Ermöglicht die Auslegung der Komponente auf die hardwareseitigen Gegebenheiten der Ziel-ECU.

#### Ausgangs-Artefakt (Output Work Product)

  • VFB Sensor Actuator Component Description («output», Kardinalität 1):
  • Vollständiges ARXML-Software-Component-Description-Modell eines SensorActuatorSwComponentType. Beinhaltet Ports (PPortPrototype, RPortPrototype), Port-Schnittstellen-Referenzen, SwcInternalBehavior (Runnables, RTE-Events, Inter-Runnable Variables) sowie Hardware-Constraint-Annotationen.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein Prozessmodell (SPEM) und kein MCU-Laufzeitdiagramm handelt, bildet die Dynamik den semantischen Autoren-Workflow ab:

  1. Vorbereitungsphase (Input-Resolution):
  • Der Software Component Designer importiert verbindliche Typ- (VFB Types) und Schnittstellendefinitionen (VFB Interfaces).
  • Optional werden standardisierte Basispakete eingebunden (VFB AUTOSAR Standard Package).
  • Zur Berücksichtigung von Hardware-Bindungen wird die ECU Resources Description geladen.
  1. Entwurfsdurchführung (Task-Execution):
  • Instanziierung des SensorActuatorSwComponentType.
  • Allokation von Ports: Festlegung von Provider- (PPort) und Requirer-Ports (RPort) zur logischen VFB-Interaktion mit Applikations-SWCs.
  • Definition hardwarenaher Schnittstellen zur Basissoftware (z. B. Zugriff auf die I/O Hardware Abstraction via Client-Server oder Sender-Receiver).
  • Definition des internen Verhaltens (SwcInternalBehavior): Konfiguration von periodischen oder ereignisgesteuerten RunnableEntities und deren Binding an RTE-Events (z. B. TimingEvent, DataReceivedEvent).
  1. Abschluss & Validierung (Output-Generation):
  • Generierung und Validierung des normativen ARXML-Deskriptors (VFB Sensor Actuator Component Description).
  • Übergabe des Artefakts an den nachgelagerten Integrationsschritt (z. B. Composition Type Definition oder ECU Extract Creation).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektonische Besonderheit des SensorActuatorSwComponentType:
  • Im Unterschied zum rein ortsunabhängigen ApplicationSwComponentType besitzt ein SensorActuatorSwComponentType eine inhärente Bindung an eine konkrete ECU.
  • Konsequenz für System-Architekten: Diese Komponente darf beim späteren System-Mapping nicht beliebig über das Fahrzeugnetzwerk verteilt werden, sondern muss auf jener ECU alloziert werden, die die entsprechenden Sensor-/Aktor-Pins physisch ansteuert.
  • BSW-Kopplung & Treiber-Ebene:
  • Sensor/Aktor-SWCs kommunizieren typischerweise nicht direkt mit MCAL-Treibern (Verstoß gegen das AUTOSAR-Schichtenmodell), sondern greifen über RTE-Ports auf die I/O Hardware Abstraction (IOHWAB) oder dedizierte Complex Device Driver (CDD) zu.
  • Die in der ECU Resources Description definierten Signalpfade müssen exakt mit den IOHWAB-/Port-Konfigurationen der BSW übereinstimmen.
  • RTE-API-Vertrag:
  • Aus der resultierenden Komponentenbeschreibung generiert der RTE-Generator komponentenspezifische API-Header (Rte_<swc>.h).
  • Gemäß deklariertem SwcInternalBehavior entstehen die C-Signaturen der Runnables (void <RunnableName>(void)) sowie Schnittstellen-APIs (Rte_Read_, Rte_Write_, Rte_Call_*).
