1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm).
  • Architektur-Kontext: AUTOSAR Classic Platform, Microcontroller Abstraction Layer (MCAL), I/O Hardware Abstraction / Drivers.
  • Funktionale Einordnung: Spezifikation des kooperativen Betriebsmodus im ICU-Treiber (AUTOSAR_SWS_ICUDriver, R4.0.3, Figure 9.21). Das Diagramm visualisiert das deterministische Zusammenspiel zwischen asynchroner, Interrupt-getriebener Benachrichtigung (Notification via ISR) und synchronem Status-Polling (Icu_GetInputState) für einen konfigurierten ICU-Kanal.

2. Komponenten, Entitäten & Schnittstellen

  • Akteure & Lifelines:
  • User :Icu User: Aufrufende Schicht oberhalb der MCAL (z. B. I/O Hardware Abstraction IoHwAb, Complex Device Driver CDD oder SW-C).
  • Icu :Icu: AUTOSAR MCAL ICU-Treibermodul (Treiber-Zustandslogik).
  • Hardware :ICU Hardware: Mikrocontroller-Peripheriebaustein (Timer/Input-Capture-Register, Flankendetektor, Interrupt Controller).
  • Schnittstellen & Service-APIs:
  • Icu_Init(ConfigPtr): Synchrone Treiberinitialisierung anhand der Konfigurationsstruktur (Icu_ConfigType).
  • Icu_SetActivationCondition(Channel, Activation): Dynamische Konfiguration der Flankensensitivität (z. B. fallende Flanke).
  • Icu_EnableNotification(Channel): Freigabe des anwenderspezifischen Callbacks für den definierten Kanal.
  • Icu_SignalNotification_<Channel>() bzw. Icu_SignalNotification_Channel1(): Konfigurierte Callback-Routine (Notification) an den Icu User.
  • Icu_GetInputState(Channel): Synchrone Statusabfrage mit Rückgabewert Icu_InputStateType (ICU_ACTIVE / ICU_IDLE).
  • Interne Zustände / Flags:
  • Hard-/Software-Flag des Kanals zur Ereignisspeicherung (11 = aktiv/gesetzt, 00 = rückgesetzt/idle).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierungs- & Konfigurationsphase (Synchron):
  • User initialisiert den Treiber via Icu_Init(ConfigPtr). Die Hardware wird gemäß Konfiguration aufgesetzt; Eingangssignalpegel liegt zunächst auf High.
  • User setzt die Triggerbedingung mittels Icu_SetActivationCondition(Channel, Activation) auf fallende Flanke (Hinweis: Der Rücksprungpfeil im Originaldiagramm ist typografisch fehlerhaft mit Icu_SignalNotification_<Channel>() beschriftet).
  • User schaltet die Callback-Benachrichtigung per Icu_EnableNotification(Channel) scharf.
  1. Ereignis- & Interrupt-Phase (Asynchron via ISR):
  • Das Signal an Channel #1 fällt von High auf Low.
  • Die Hardware löst Interrupt() aus; Eintritt in die ICU-ISR (ISR).
  • Die ISR setzt das interne Kanal-Flag (Set Flag() $\rightarrow$ Zustand 11).
  • Die ISR ruft synchron aus dem Interrupt-Kontext den Callback Icu_SignalNotification_Channel1() im User auf.
  • Nach Rückkehr aus dem Callback erfolgt der ISR-Ausstieg (return from ISR()).
  1. Polling- & Quittierungsphase (Read-and-Clear):
  • User ruft synchron Icu_GetInputState(return, Channel) auf.
  • Der Treiber evaluiert das interne Flag, setzt es atomar zurück (check and reset Flag() $\rightarrow$ Zustand 00) und gibt ICU_ACTIVE an den Aufrufer zurück.
  • Ein nachfolgender Aufruf von Icu_GetInputState(return, Channel) stellt fest, dass das Flag gelöscht ist (Check and (reset) Flag $\rightarrow$ Zustand 00) und liefert ICU_IDLE.

4. Normative Relevanz & Entwickler-Hinweise

  • Destruktives Lesen (Read-and-Clear Semantik): Icu_GetInputState() arbeitet zustandsverzehrend. Das Lesen des Status ICU_ACTIVE setzt das interne Ereignis-Flag unmittelbar auf ICU_IDLE zurück. Mehrfaches Polling ohne zwischenzeitliches neues Flankenereignis liefert zwingend ICU_IDLE.
  • Kooperative Parallelität: Notification und Polling schließen sich nicht gegenseitig aus, sondern arbeiten auf derselben Zustandsbasis. Das Auftreten einer Flanke setzt den Zustand auf ICU_ACTIVE, unabhängig davon, ob die Notification aktiviert ist oder bereits abgearbeitet wurde.
  • Konfigurationsanforderungen (ECUC):
  • Polling erfordert IcuInputStatusApi == TRUE.
  • Callbacks erfordern IcuNotificationSupported == TRUE sowie die Zuweisung einer gültigen Funktionsreferenz unter IcuSignalNotification.
  • Interrupt-/Kontext-Synchronisation: Da Set Flag() im ISR-Kontext und check and reset Flag() im Task-Kontext (via Icu_GetInputState) ausgeführt werden, muss der Treiber-Implementierer die Flag-Operationen über Interrupt-Sperren bzw. atomare Bitoperationen (Exclusive Areas) gegen Race Conditions absichern.
