1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Activity Diagram (basierend auf SPEM / Software & Systems Process Engineering Metamodel nach AUTOSAR_TR_Methodology).
  • Architektur-Kontext: Phase der Steuergeräte-Integration (ECU Integration). Dargestellt ist die Aktivität Generate RTE (Methodology Activity), die den Übergang vom abstrakten Virtual Function Bus (VFB) auf die konkrete ECU-Laufzeitumgebung markiert.
  • Technischer Zweck: Deterministische Generierung des RTE-C-Codes, des BSW-Schedulers (SchM), der Beschreibungsdateien und Kalibrierungsmetadaten basierend auf der ECU-Konfiguration, den Software-Komponenten-Beschreibungen und der Netzwerk-Signalabbildung.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Werkzeuge
  • ECU Integrator (Akteur, Kardinalität 1): Führt die Aktivität aus («performs»).
  • RTE Generator (Tool, Stereotyp «used tool»): Codegenerator der RTE-Toolchain.
Eingangsartefakte («input»)
  • ECU Extract (Kardinalität 1): ECU-spezifischer Auszug aus der Systembeschreibung (SystemExtract.arxml) mit FlatMap, Topologie, Signal- und Netzwerkdefinitionen sowie instanziierten Software-Komponenten.
  • Delivered Atomic Software Components (Kardinalität 1..*): Lieferpakete der Applikations-SWCs (SWC Description mit InternalBehavior, RunnableEntity, PortPrototype, Interfaces).
  • BSW Module Integration Bundle (Kardinalität 0..*): Integrationsbeschreibungen der Basissoftware-Module (BswModuleDescription, BswModuleEntry, Schedulable Entities für den SchM).
  • Service Component Description (Kardinalität 0..*): Schnittstellenbeschreibungen standardisierter AUTOSAR-Basisdienste (z. B. Dem, NvM, Dcm, ComM) als Service-SWCs.
  • ECU Service Connectors (Kardinalität 0..*): Zuordnungen und Port-Verbindungen zwischen Service-Ports von Applikations-SWCs und den Service-SWCs.
  • Software Component to BSW Mapping (Kardinalität 0..*): Spezifikation der direkten Zuordnung und Kopplung von Software-Komponenten bzw. deren Ports und Runnable Entities an Basissoftware-Module (z. B. für CDD-Anbindungen oder Service-Bypass).
  • Calibration Parameter Value Set (Kardinalität 0..1): Vordefinierte Werte für Kalibrierparameter (ParameterDataPrototype, Calibration Component Values).
  • ECU Configuration Values (Kardinalität 1): Vollständige BSW-/ECU-Parameterkonfiguration (ECUC.arxml), insbesondere OS-Konfiguration (Tasks, Alarms, Events), COM-Stack-Konfiguration und RTE-Modulkonfiguration (RteGeneration).
Ausgangsartefakte («output»)
  • RTE Source Code (Kardinalität 1): Generierte C-Dateien (Rte.c, Rte_<swc>.h, Rte_Type.h, Rte_DataHandleType.h, Rte_Cbk.h). Implementiert Datenaustausch (Buffer, Queues), Runnable-Aufrufe und COM-Anbindung.
  • BSW Scheduler Code (Kardinalität 1): C-Quellcode des Basic Software Schedulers (SchM_<Module>.h, SchM_<Module>.c), verantwortlich für BSW-MainFunctions und Exklusivbereich-Handling (SchM_Enter, SchM_Exit).
  • RTE Implementation Description (Kardinalität 1): Formale BSWMD-XML-Beschreibung (BswImplementation) des generierten RTE/SchM-Moduls für den Linker-/Build-Prozess.
  • RTE Measurement and Calibration Support Data (Kardinalität 0..1): A2L-Fragmente / MCD-Support-Daten (z. B. Adressen und Typdefinitionen interner Variablen, PIMs, Inter-Runnable Variables).
  • ECU Configuration Values (Kardinalität 0..1, Feedback-Pfad): Aktualisierung der ECU-Konfiguration, sofern der RTE-Generator abhängige Konfigurationen (z. B. OS-Task-Aktivierungen, OS-Events oder Com-Signaltreiber) anpasst oder vervollständigt.

3. Dynamisches Verhalten & Sequenzablauf

Die Aktivität ist ein zustandsloser Offline-Generierungsprozess mit deterministischem Ablauf:

  1. Konsistenz- & Syntaxprüfung:
    • Abgleich der SWC-Port-Interfaces gegen den ECU Extract und Validierung aller Assembly-/Delegation-Connectors.
    • Typ- und Kompatibilitätsprüfung von Client-Server- und Sender-Receiver-Verbindungen.
  2. Scheduling- & Task-Synthese:
    • Zuordnung der RteEvents (TimingEvents, DataReceivedEvents etc.) zu den konfigurierten OsTasks gemäß ECU Configuration Values.
    • Ableitung von Prioritäten, Preemption-Eigenschaften und Call-Reihenfolgen innerhalb der Task-Bodys.
  3. Kommunikations-Auflösung:
    • Intra-ECU: Generierung lokaler Shared-Memory-Puffer, Queues und Kopierroutinen.
    • Inter-ECU: Generierung der Wrapper-Aufrufe an das AUTOSAR COM-Modul (Com_SendSignal, Com_ReceiveSignal) und Signal-Group-Serialisierung.
  4. SchM-Synthese (Basic Software Scheduler):
    • Auflösung aller deklarierten BSW-Exklusivbereiche (ExclusiveArea) in OS-Ressourcen, Interrupt-Sperren oder Spinlocks.
    • Generierung der Aufrufketten für BSW-zyklische Funktionen (<Mod>_MainFunction).
  5. Code- & Metadaten-Emission:
    • Schreiben aller typisierten API-Header (Rte_<swc>.h) und Core-Dateien.
    • Generierung der A2L-Messdatenstrukturen und Aktualisierung der OS/COM-ECUC-Parameter.

4. Normative Relevanz & Entwickler-Hinweise

  • Applikations-Entwickler (SWC):
    • API-Vertrag: Der C-Code einer SWC bindet ausschließlich Rte_<swc>.h ein. Es dürfen keine direkten Aufrufe an BSW-Treiber, OS-Dienste oder Fremd-SWCs erfolgen.
    • Generation Phase Dependency: Ändert sich ein Interface, InternalBehavior oder Calibration Parameter, ist zwingend ein Re-Run des RTE-Generators vor dem SWC-Compile erforderlich.
  • BSW- / Stack-Entwickler:
    • Exklusivbereiche: BSW-Module dürfen keine nativen OS-Interrupt-Sperren (DisableAllInterrupts) aufrufen. Der Zugriff hat strikt über SchM_Enter_<Module>_<Area>() zu erfolgen, da die Implementierung erst durch die RTE-Generierung festgelegt wird.
    • MainFunction-Triggerung: BSW-Entwickler verlassen sich darauf, dass das zyklische Aufrufen von Modul-MainFunctions über den generierten BSW Scheduler (SchM) abgebildet wird.
  • ECU-Integrator & Build-Engineers:
    • Zyklische Tool-Abhängigkeit: Zwischen RTE- und OS-Generierung besteht eine Wechselbeziehung: Die RTE benötigt existierende OS-Tasks (ECU Configuration Values), fordert aber potenziell neue OS-Events/Alarme an, was eine mehrstufige Generierung (Contract Phase vs. Generation Phase) erfordert.
    • MemMap-Integration: Die generierte RTE verwendet #include "Rte_MemMap.h" bzw. #include "SchM_MemMap.h". Der Integrator muss alle resultierenden Speicherscheiben (RTE_START_SEC_CODE, RTE_START_SEC_VAR_NOINIT etc.) fehlerfrei auf die Linker-Sections der MCU mappen.
    • A2L-Generierung: Für Mess-/Kalibrierwerkzeuge (z. B. CANape, INCA) müssen die generierten A2L-Fragmente der RTE Measurement and Calibration Support Data zwingend in die Gesamtmessdatei der ECU gemergt werden, um RTE-interne Signale und PIMs sichtbar zu machen.
