1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR M2-Metamodell-Klassendiagramm (UML Profil für AUTOSAR Templates).
  • Architektur-Kontext: Top-Level-Sicht der Timing-Erweiterungen (AUTOSAR_TPS_TimingExtensions, Kapitel 3, R22-11).
  • Funktionaler Zweck: Bereitstellung eines einheitlichen semantischen Metamodellrahmens zur Definition, Spezifikation und formalen Verifikation von Timing-Eigenschaften (Anforderungen, Garantien, Uhren- und Ereignisbeschreibungen) über sämtliche Abstraktionsebenen der AUTOSAR-Entwicklungsmethodik hinweg (vom VFB über SWC/BSW bis hin zur ECU- und Systemebene).

2. Komponenten, Entitäten & Schnittstellen

2.1 Abstrakte Basisklasse
  • TimingExtension («ARElement», spezialisiert Identifiable):
    • Zentraler Einstiegspunkt für die Beschreibung timingrelevanter Eigenschaften.
    • Aggregiert folgende Teilstrukturen (jeweils mit Stereotypen versehen):
      • +timingRequirement [0..*] («atpVariation», «atpSplitable»): Verweist auf TimingConstraint («Identifiable», «Traceable») zur Spezifikation geforderter Zeitschranken (z. B. Deadline, Latenz, Periodizität).
      • +timingGuarantee [0..*] («atpVariation», «atpSplitable»): Verweist auf TimingConstraint («Identifiable», «Traceable») zur Dokumentation nachgewiesener/garantierter Zeitschranken (z. B. WCET, Reaktionszeiten).
      • +timingCondition [0..*] («atpVariation», «atpSplitable»): Kapselt Betriebsbedingungen (TimingCondition), unter denen Constraints Gültigkeit besitzen. TimingConstraint referenziert optional +timingCondition [0..1].
      • +timingDescription [0..*] («atpVariation», «atpSplitable»): Strukturierte Beschreibungselemente (TimingDescription, z. B. Event-Ketten, Events, Clock-Domänen).
      • +timingResource [0..1] («atpSplitable»): Verweist auf TimingExtensionResource.
      • +timingClock [0..*] («atpVariation», «atpSplitable»): Modellierung von Zeitbasen/Clocks (TimingClock).
      • +timingClockSyncAccuracy [0..*] («atpVariation», «atpSplitable»): Spezifiziert die relative Synchronisationsgenauigkeit zwischen zwei Uhren (TimingClockSyncAccuracy) über Assoziationen +upper [0..1] und +lower [0..1] mit Attribut +accuracy: MultidimensionalTime [0..1].
2.2 Konkrete Spezialisierungen (Subklassen von TimingExtension)

Jede Subklasse bindet die Timing-Erweiterung an eine spezifische Modellierungs- bzw. Entwurfsebene:

  1. VfbTiming («AtpBlueprint», «AtpBlueprintable»):
    • Assoziation: +component [0..1] → SwComponentType («ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpType»).
    • Adressiert Timing auf Ebene des Virtual Functional Bus (Komponentenschnittstellen, Port-zu-Port-Kommunikation vor Allokation).
  2. SwcTiming:
    • Assoziation: +behavior [0..1] → SwcInternalBehavior («InternalBehavior»).
    • Adressiert Runnable-Ausführungszeiten, Inter-Runnable-Kommunikation und Aktivierungsintervalle innerhalb einer SWC.
  3. BswModuleTiming:
    • Assoziation: +behavior [0..1] → BswInternalBehavior («InternalBehavior»).
    • Adressiert Ausführungszeiten von BSW-Schedulable-Entities, Interrupt-Service-Routinen (ISR) und zyklische Main-Functions einzelner BSW-Module.
  4. BswCompositionTiming:
    • Assoziationen: +behavior [0..1] → BswInternalBehavior, +implementation [0..*] → BswImplementation («Implementation»).
    • Spezifiziert das zeitliche Zusammenspiel über Modulgrenzen hinweg innerhalb eines BSW-Verbunds/Stacks.
  5. EcuTiming:
    • Assoziation: +ecuConfiguration [0..1] → EcucValueCollection («ARElement»).
    • Bindet Timing an eine konkrete Steuergerätekonfiguration (OS-Tasks, Alarm-Offsets, RTE-Schedule, MCAL-Treiber).
  6. SystemTiming:
    • Assoziation: +system [0..1] → System («ARElement», «AtpStructureElement»).
    • Umfasst netzwerkweites Timing über Bus-Topologien hinweg (CAN, LIN, FlexRay, Ethernet TSN, Gateway-Verzögerungen, Signal- und PDU-Latenzen).

3. Dynamisches Verhalten & Sequenzablauf

Als statisches M2-Metamodell existiert kein Laufzeit-Sequenzablauf auf dem Zielsteuergerät. Der methodische Lebenszyklus im AUTOSAR-Entwurfsprozess gestaltet sich wie folgt:

[VFB / System Design]   --> timingRequirement (Top-Down Constraints, End-to-End Deadlines)
        │
        ▼
[SWC / BSW Design]      --> timingCondition (Modus-Abhängigkeiten z.B. Run / Standby)
        │
        ▼
[ECU Implementation]    --> timingGuarantee (WCETs aus statischer Analyse / Messung)
        │
        ▼
[Verification / Check]  --> Automatisierter Abgleich: timingGuarantee <= timingRequirement
  • Trigger & Evaluation: TimingCondition evaluiert Betriebsmodi (z. B. ModeDeclarationGroup, Vehicle States). Ein Constraint wird nur scharf geschaltet, wenn die zugeordnete Bedingung aktiv ist.
  • Uhren-Synchronisation: Bei verteilten Systemen (z. B. IEEE 802.1AS / TSN oder AUTOSAR Synchronized Time-Base Manager StbM) definiert TimingClockSyncAccuracy das Jitter- und Offset-Intervall zwischen upper und lower Clocks, um netzwerkweite Event-Ketten deterministisch auflösen zu können.

4. Normative Relevanz & Entwickler-Hinweise

  • Separation of Concerns via «atpSplitable»:
    • Timing-Modelle müssen nicht in denselben ARXML-Dateien wie die funktionale Softwarearchitektur (SwComponentType, EcucValueCollection) liegen. OEMs können Anforderungen (timingRequirement) vorgeben, während Tier-1s Garantien (timingGuarantee) in separaten ARXML-Containern nachliefern.
  • Variantenmanagement via «atpVariation»:
    • Zeitschranken und Clock-Definitionen können über AUTOSAR-System-Constants und Post-Build-/Pre-Compile-Varianten formal bedingt werden.
  • Auswirkungen auf RTE-, OS- und Kommunikations-Stack:
    • RTE/OS: SwcTiming und EcuTiming liefern die formale Eingangsbasis für Scheduling-Synthese-Tools zur Belegung von OS-Task-Perioden, Prioritätenzuweisungen und OS-Alarm-/Schedule-Table-Konfigurationen (EcucValueCollection).
    • Treiber & BSW: BswModuleTiming definiert das maximale Ausführungsbudget für zyklische Aufrufe (<Msn>_MainFunction()) und Interrupt-Latenzen, deren Nichteinhaltung zu Task-Starvation oder Watchdog-Resets (WdgM) führt.
    • Traceability: Durch die Spezialisierung von TimingConstraint aus Traceable ist eine lückenlose Nachverfolgung bis in Requirements-Engineering-Systeme (z. B. ISO 26262 ASIL-Timing-Budgets) toolgestützt auditierbar.
