1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturschaubild / Multicore-Partitionierungs- und Schichtenmodell (Struktur- und Interaktionsdiagramm für BSW-Verteilung).
  • Technischer Zweck & Einordnung: Das Diagramm aus dem AUTOSAR BSW Distribution Guide (AUTOSAR_EXP_BSWDistributionGuide, R18-10 / R4.4.0) stellt das Entwurfsmuster „Separation on SW level (Alternative Solution)“ dar. Es beschreibt die asymmetrische Verteilung eines Basissoftware-Moduls (BSW Module) über zwei CPU-Kerne (Core 1, Core 2). Ziel ist die Entkopplung von Aufrufer-Schnittstellen (Service API) und ereignisgesteuerten Callbacks (ISR) auf entfernten Kernen von der tatsächlichen Hardware-Anbindung, Speicherhaltung und Ausführungslogik (Kernel, Mainfunction, Register), die exklusiv auf einem Master-Kern gebündelt bleiben.

2. Komponenten, Entitäten & Schnittstellen

  • Ausführungskerne (Execution Cores):
    • Core 1 (Master/Host-Kern): Beherbergt die Modul-Zentralinstanz (Kernel), periodische Scheduling-Pfade (Mainfunction), das Hardware-Register-Mapping (Shared Registers), den internen Datenzustandsspeicher (roter Zylinder) und hardwaregebundene Interrupts (ISR).
    • Core 2 (Satellite/Client-Kern): Ausgeführt als Proxy- bzw. Stub-Ebene; enthält ausschließlich Anwendungs-/Schicht-Schnittstellen (Service API) und Benachrichtigungs-ISRs/Callbacks (ISR).
  • BSW-Modul-Grenze (BSW Module, gestrichelte Umrandung): Logische Einheit des Treibers bzw. Stacks, die physisch über die Core-Grenzen partitioniert ist.
  • Interne Entitäten & Schnittstellen:
    • Service API (Core 1 & Core 2): Reentrante, lokale Einsprungpunkte für SWCs oder überlagerte BSW-Module. Wandeln Aufrufe auf Core 2 in kernübergreifende Requests um.
    • Request and Feedback System: Kernübergreifender Inter-Core-Kommunikationskanal (typischerweise AUTOSAR OS-IOC, Shared-Memory-Ringpuffer oder Inter-Core-Interrupts/Mailboxes) zur bidirektionalen Entkopplung von Aufruf-/Rückmeldefluss zwischen Core 2 und Core 1.
    • Kernel (Core 1): Zentrale Zustandsmaschine und Treiberlogik. Empfängt/quittiert Requests aus dem Feedback-System, synchronisiert mit Mainfunction und führt Lese-/Schreibzugriffe auf Hardware und Puffer aus.
    • Mainfunction (Core 1): Zyklisch durch das AUTOSAR OS bzw. SchM/BswM getriggerte Entität (<BSW>_MainFunction), interagiert bidirektional mit dem Kernel.
    • Shared Registers (MMIO-Adressen 0x789, 0x012, 0x123, 0x456): Physische Peripherie- und Kontrollregister, exklusiv von Core 1 aus adressiert.
    • Zentraler Datenpuffer (rotes Zylinder-Icon, Core 1): Modulinterner RAM-Puffer für Queuing, Zwischenspeicherung von Nutzdaten (z. B. PDU-Buffer) und Statusinformationen.
    • Untere Interrupt Service Routinen (ISR, Core 1): Hardware-ISRs, direkt angebunden an µC peripheral Element 1 und µC peripheral Element 2. Schreiben/lesen direkt im internen Puffer.
    • Obere Interrupt Service Routinen (ISR, Core 1 & Core 2): Auslöser für asynchrone Callbacks, Indications und Confirmations an übergeordnete Schichten auf dem jeweiligen Kern.
  • Peripherie-Hardware (µC peripheral Element 1 & 2): Hardware-Module (z. B. CAN-/LIN-Controller, ADC, SPI-Controller), verdrahtet mit den Core-1-Interrupt-Vektoren und spezifischen Registern (z. B. Verbindungslinie von Element 1 auf 0x456).

3. Dynamisches Verhalten & Sequenzablauf

  • Synchroner/Asynchroner API-Request (Core 2 → Core 1):
    1. Ein Client (z. B. SWC auf Core 2) ruft die lokale Service API auf.
    2. Die Service API verpackt Parameter und sendet eine Nachricht über das Request and Feedback System an Core 1.
    3. Der Kernel auf Core 1 konsumiert die Anforderung, steuert die Shared Registers an oder übergibt Daten an den internen Speicher.
    4. Die periodische Mainfunction verarbeitet die Anfrage im zugewiesenen OS-Task-Kontext weiter.
  • Hardware-Ereignis & Callback-Verteilung (Core 1 → Core 2):
    1. µC peripheral Element 1/2 löst einen physischen Hardware-Interrupt auf Core 1 aus.
    2. Die zuständige untere ISR sichert Registerinhalte, extrahiert die Nutzdaten in den internen Datenpuffer und benachrichtigt den Kernel.
    3. Ist der Callback für einen Kontext auf Core 2 bestimmt, generiert der Kernel über das Request and Feedback System ein Feedback-Ereignis (Cross-Core-Interrupt / OS-Task-Aktivierung).
    4. Die obere ISR auf Core 2 verarbeitet das Event und leitet die Rx-Indication / Tx-Confirmation an die Applikationsschicht weiter.

4. Normative Relevanz & Entwickler-Hinweise

  • Ecuc-Partitionierung & OS-Konfiguration:
    • Das BSW-Modul muss über EcucPartitionCollection beiden Cores zugewiesen werden.
    • Die Hardware-Interrupts (OsIsr) und die zyklische Task für <BSW>_MainFunction dürfen ausschließlich der EcucPartition von Core 1 zugeordnet werden.
    • Für Core 2 sind dedizierte IPC-Mechanismen (z. B. OS-IOC-Queues oder Inter-OS-Application-Events) zu konfigurieren.
  • Latenz & Synchronisationssemantik:
    • Lokale Aufrufe auf Core 2 dürfen zur Vermeidung von Core-Stalls und Inter-Core-Deadlocks nicht blockierend auf den Hardware-Zugriff von Core 1 warten. Service-APIs müssen asynchron ausgelegt sein (Rückmeldung via Callback).
    • Exklusivitätsbereiche (SchM_Enter_<Mod>_<Area>): Auf Core 1 reichen lokale Interrupt-Sperren oder Resource-Locks; das Request and Feedback System erfordert hardwareunterstützte Multicore-Locks (z. B. OS Spinlocks) oder lock-free SPSC-/MPSC-Ringpuffer im Shared RAM.
  • Speicherschutz (MPU) & Safety:
    • Peripherieregister (Shared Registers) müssen im MPU-Layout von Core 2 gesperrt werden. Dadurch wird Freedom from Interference (FFI) gewährleistet, da fehlerhafte Prozesse auf Core 2 die Hardware-Register von Core 1 nicht korrumpieren können.
