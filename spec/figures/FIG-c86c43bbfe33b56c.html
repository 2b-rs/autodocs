  • Klassifikation: UML-2.0-Klassendiagramm / AUTOSAR-M2-Metamodellausschnitt (Excerpt of Metamodel regarding Modes).

  • Technischer Zweck: Definition der statischen Metamodell-Strukturen zur Abbildung von Betriebsmodi (Modes), Modusgruppen (ModeDeclarationGroups), Modus-Schnittstellen (ModeSwitchInterface), deren Bindung an Ports und Komponenten sowie deren funktionale Kopplung an das Laufzeitverhalten der RTE (SwcInternalBehavior, SwcModeSwitchEvent, RunnableEntity inkl. 2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in vier logische Metamodell-Pakete:

#### Paket Component and Port

  • SwComponentType (Abstract, «ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpType»): Basisklasse aller SWC-Typen.
  • Aggregiert per Komposition 0..* PortPrototype (Rollenname +port, Stereotypen «atpVariation, atpSplitable», Vh.latestBindingTime = PreCompileTime).
  • AtomicSwComponentType (Spezialisierung von SwComponentType):
  • Aggregiert per Komposition 0..1 SwcInternalBehavior (+internalBehavior, Stereotypen «atpVariation, atpSplitable»).
  • PortPrototype (Abstract, «AtpBlueprintable», «AtpPrototype»): Basisklasse für SWC-Ports.
  • Spezialisierungen:
  • PPortPrototype: Provided Port (Rolle des Mode Managers / Mode Requestors).
  • RPortPrototype: Required Port (Rolle des Mode Users / Mode Observers).

#### Paket Interface

  • PortInterface (Abstract, «ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpType»):
  • PPortPrototype typisiert via Assoziation +providedInterface 1 {redefines atpType} mit Stereotyp «isOfType».
  • RPortPrototype typisiert via Assoziation +requiredInterface 1 {redefines atpType} mit Stereotyp «isOfType».
  • ModeSwitchInterface (Spezialisierung von PortInterface):
  • Spezifisches Interface für modale Interaktion (anstelle von Sender/Receiver oder Client/Server).
  • Komposition: Aggregiert genau 1 ModeDeclarationGroupPrototype (+modeGroup 1).
  • ModeDeclarationGroupPrototype («AtpPrototype»):
  • Prototypische Instanz einer Modusgruppe innerhalb des Interface-Kontexts. Typisiert via «isOfType» auf ModeDeclarationGroup (+type 1 {redefines atpType}).

#### Paket ModeDeclaration

  • ModeDeclarationGroup («ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpType»):
  • Deklarativer Typ einer Zustandsmenge (z. B. EcuMode, VehicleMode).
  • Komposition: Enthält 1..* ModeDeclaration (+modeDeclaration).
  • Assoziation: Referenziert genau 1 ModeDeclaration als Startzustand (+initialMode 1).
  • ModeDeclaration («AtpStructureElement», «Identifiable»):
  • Einzelner diskreter Modus-Zustand (z. B. STARTUP, RUN, SHUTDOWN).

#### Paket InternalBehavior and Runnables

  • SwcInternalBehavior («InternalBehavior»):
  • Komposition zu * RTEEvent (+event, Stereotypen «atpVariation, atpSplitable», Vh.latestBindingTime = PreCompileTime).
  • Komposition zu 1..* RunnableEntity (+runnable, Stereotypen «atpVariation, atpSplitable», Vh.latestBindingTime = PreCompileTime).
  • RTEEvent (Abstract, «AtpStructureElement», «Identifiable»):
  • Assoziation +startOnEvent 0..1 zu RunnableEntity: Definiert den auslösenden Trigger für eine Runnable.
  • SwcModeSwitchEvent (Spezialisierung von RTEEvent):
  • Spezifisches RTE-Event bei Moduswechseln.
  • Assoziation via «instanceRef» auf ModeDeclaration: Multiplizität 1..2 {ordered} (+mode).
  • RunnableEntity («AtpStructureElement», «ExecutableEntity»):
  • Assoziation via «instanceRef» auf ModeDeclaration: Multiplizität 0..* (+disabledInMode).

3. Dynamisches Verhalten & Sequenzablauf

Aus dem statischen Metamodell leitet sich die RTE-Laufzeitsemantik für Moduswechsel ab:

```

[Mode Manager SWC] [RTE] [Mode User SWC]

| | |

|-- Rte_Switch(ModeX) -->| |

| (via PPort) |-- Modusstatus aktualisieren |

| |-- Überprüfung disabledInMode |

| | |

| |-- SwcModeSwitchEvent triggern ------>|

| | (On-Entry / On-Exit / Transition) |-- Runnable ausführen

| | |

| |<-- Rte_Mode(ModeGroup) --------------|

| | (Statusabfrage via RPort) |

```

  1. Moduswechsel-Anforderung (Trigger): Ein Mode Manager stößt über seinen PPortPrototype via RTE-API (Rte_Switch_<p>_<modeGroup>()) einen Moduswechsel an.
  2. Event-Klassifikation über SwcModeSwitchEvent.mode (1..2 {ordered}):
  • 1 Mode referenziert: Repräsentiert ein On-Entry- (Eintritt in den Modus) oder On-Exit-Event (Verlassen des Modus).
  • 2 geordnete Modi referenziert: Repräsentiert ein explizites Transition-Event (gezielter Übergang von Modus $M_1$ nach Modus $M_2$).
  1. Runnable-Dispatching & Gating (startOnEvent vs. disabledInMode):
  • Die RTE aktiviert die mit SwcModeSwitchEvent über startOnEvent verknüpfte RunnableEntity.
  • Ausführungsinhibierung (disabledInMode): Die RTE unterdrückt die Aktivierung einer Runnable (z. B. zyklische Runnables via TimingEvent), solange der aktuelle Zustand der Modusgruppe mit einem in disabledInMode referenzierten Modus übereinstimmt.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Verträge & RTE-Generierung:
  • Für PPortPrototype mit ModeSwitchInterface generiert der RTE-Generator:
  • Asynchron/Nicht-blockierend: Std_ReturnType Rte_Switch_<p>_<modeGroup>(uint8 mode) (Rückgabe: RTE_E_OK, RTE_E_LIMIT).
  • Für RPortPrototype generiert der RTE-Generator:
  • Modusabfrage: uint8 Rte_Mode_<r>_<modeGroup>(void).
  • ARXML-Instanzreferenzen («instanceRef»):
  • SwcModeSwitchEvent.mode und RunnableEntity.disabledInMode sind Metamodell-Instanzreferenzen. Sie referenzieren nicht bloß die M2-Klasse ModeDeclaration, sondern navigieren über den Kontext:

AtomicSwComponentType $\rightarrow$ PortPrototype $\rightarrow$ ModeDeclarationGroupPrototype $\rightarrow$ ModeDeclaration. Unvollständige oder fehlerhafte Pfade führen zu Validierungsfehlern im Generator.

  • Variantenmanagement («atpVariation» mit PreCompileTime):
  • Ports, Runnables, Events und InternalBehaviors sind zur Bindungszeit PreCompileTime variierbar.
  • Modus-Mappings und disabledInMode-Tabellen werden während der RTE-Generierung fest als Bitmasken oder Zustandstabellen im Flash hinterlegt; zur Laufzeit existiert kein dynamisches Rekonfigurieren von Mode-Bindings.
  • Modellierungsrestriktion:
  • Ein ModeSwitchInterface darf exakt nur eine ModeDeclarationGroupPrototype aggregieren (+modeGroup 1). Multimodus-Schnittstellen müssen über separate Ports abgebildet werden.
