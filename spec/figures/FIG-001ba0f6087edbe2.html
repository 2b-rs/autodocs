1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (AUTOSAR-Metamodell-Ausschnitt, M2).
  • Architektur-Kontext: AUTOSAR Adaptive Platform (AP), Spezifikation TPS_ManifestSpecification (R20-11).
  • Technischer Zweck: Modellierung der clusterübergreifenden Interaktion (Functional Cluster Interaction) zwischen den Functional Clustern Persistency (ara::per) und Cryptography (ara::crypto). Das Diagramm spezifiziert die Zuordnung von persistenten Deployment-Elementen zu kryptographischen Schlüsselslots zur Realisierung von Vertraulichkeit (Verschlüsselung) und Datenintegrität (Authentizität/Verifikation) auf Feldebene bzw. Dateiebene.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Entitäten
  • PersistencyDeploymentElement (abstract, spezialisiert Identifiable):
    • Basisklasse für alle im Manifest deployten Persistenz-Artefakte.
    • Attribut: updateStrategy: PersistencyElementLevelUpdateStrategyEnum [0..1] (Steuert das Update-Verhalten bei Software-Updates für das konkrete Element).
  • PersistencyKeyValuePair (spezialisiert PersistencyDeploymentElement):
    • Repräsentiert einen atomaren Schlüssel-Wert-Eintrag innerhalb eines Key-Value-Storages.
  • PersistencyFile (spezialisiert PersistencyDeploymentElement):
    • Repräsentiert eine persistente Datei innerhalb eines File-Storages.
    • Attribute:
      • contentUri: UriString [0..1] (URI zur Bereitstellung initialer Datei-Inhalte).
      • fileName: String [0..1] (Optionaler Dateiname bzw. relativer Pfad der Datei).
  • PersistencyDeploymentElementToCryptoKeySlotMapping (spezialisiert FunctionalClusterInteractsWithFunctionalClusterMapping):
    • Assoziationsklasse zur Verknüpfung von Persistenz- und Krypto-Deployment.
    • Attribute:
      • cryptoAlgorithmString: String [0..1] (Spezifikation des Algorithmus bzw. der Krypto-Transformationskette für das Persistenz-Element).
      • keySlotUsage: CryptoKeySlotUsageEnum [0..1] (Legt fest, ob der Schlüsselslot zur Verifikation oder Verschlüsselung dient).
      • verificationHash: String [0..1] (Optionaler Referenz-Hash zur Integritätsprüfung des deployten Initialzustands).
  • CryptoKeySlot (spezialisiert Identifiable):
    • Modelliert einen logischen/physischen Schlüsselslot im Krypto-Stack.
    • Attribute:
      • allocateShadowCopy: Boolean [0..1] (Allokation einer Schattenkopie für transaktionssichere Key-Updates).
      • cryptoAlgId: String [0..1] (Krypto-Algorithmus-Identifikator, z. B. AES-256-GCM, ECDSA).
      • cryptoObjectType: CryptoObjectTypeEnum [0..1] (Typ des Krypto-Objekts, z. B. symmetrischer/asymmetrischer Schlüssel).
      • slotCapacity: PositiveInteger [0..1] (Maximale Bytegröße des Slots).
      • slotType: CryptoKeySlotTypeEnum [0..1] (z. B. flüchtig, persistent, hardware-geschützt).
  • CryptoKeySlotUsageEnum («enumeration»):
    • Literale: encryption, verification.
Beziehungen & Kardinalitäten
  • Generalisierung:
    • PersistencyKeyValuePair → PersistencyDeploymentElement (1:1 Vererbung).
    • PersistencyFile → PersistencyDeploymentElement (1:1 Vererbung).
    • PersistencyDeploymentElementToCryptoKeySlotMapping → FunctionalClusterInteractsWithFunctionalClusterMapping.
  • Gerichtete Assoziationen des Mappings:
    • +persistencyDeploymentElement mit Multiplizität 0..1: Referenziert das zu schützende PersistencyDeploymentElement.
    • +cryptoKeySlot mit Multiplizität 0..1: Referenziert den bereitzustellenden Krypto-Schlüsselslot CryptoKeySlot.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm definiert eine deklarative Deployment-Struktur; das daraus resultierende Laufzeitverhalten gliedert sich in folgende Pfade:

  1. Initialisierungsphase / Startup:
    • Der Persistency-Dämon bzw. die ara::per-Bibliothek liest das Deployment-Manifest ein.
    • Für jedes PersistencyDeploymentElementToCryptoKeySlotMapping instanziiert bzw. öffnet ara::per über die ara::crypto-Schnittstelle den zugewiesenen CryptoKeySlot.
  2. Schreibpfad (Persistierung via ara::per):
    • Aufruf von Schreiboperationen (SetKey, WriteFile).
    • Ist keySlotUsage == encryption: Das Element wird transparent über Krypto-Primitive des zugeordneten CryptoKeySlot verschlüsselt (z. B. AEAD), bevor es in das nicht-flüchtige Medium geschrieben wird.
    • Ist keySlotUsage == verification: Berechnung einer Signatur bzw. eines HMACs über die Nutzdaten unter Verwendung des Schlüssels im CryptoKeySlot; Speicherung des Integritätswerts neben den Nutzdaten.
  3. Lesepfad (Wiederherstellung via ara::per):
    • Leseaufruf (GetValue, OpenFile).
    • Ist keySlotUsage == encryption: Entschlüsselung über ara::crypto mit dem im Slot liegenden Schlüssel.
    • Ist keySlotUsage == verification: Validierung der Signatur/des Hashes (ggf. Abgleich gegen gespeicherten Status oder verificationHash).
  4. Fehlerbehandlung:
    • Bei Fehlschlag von Entschlüsselung oder Verifikation (z. B. MAC-Mismatch, manipulated data): Rückgabe von ara::per::PerErrc::kIntegrityCorrupted oder kStorageFailure an die Applikation; kein Zugriff auf kompromittierte Daten.

4. Normative Relevanz & Entwickler-Hinweise

  • Anforderungskonformität (TPS_MANI_03276):
    • Verpflichtende Modellierungsvorschrift, wenn persistente Elemente (Dateien oder KVP) kryptographisch gegen Manipulation oder unbefugtes Auslesen abgesichert werden müssen.
  • Granularität:
    • Die Absicherung erfolgt nicht zwingend pro Storage (PersistencyFileStorage / PersistencyKeyValueStorage), sondern kann gezielt auf Elementebene (PersistencyFile oder PersistencyKeyValuePair) granular konfiguriert werden.
  • Separation of Concerns:
    • Entwickler von adaptiven Anwendungen müssen Krypto-Schlüssel nicht manuell verwalten oder direkt über ara::crypto verarbeiten. Die Bindung erfolgt rein deklarativ im Manifest. Der Krypto-Stack kapselt Schlüsselverwaltung, Zugriffsrechte und Hardware-Sicherheitsmodule (HSM / Secure Elements).
  • Konfigurationsrestriktionen:
    • Soll ein Element sowohl verschlüsselt als auch signiert werden (z. B. Encrypt-then-MAC), sind zwei separate Mappings mit jeweiliger keySlotUsage (encryption bzw. verification) auf korrespondierende CryptoKeySlot-Instanzen zu instanziieren.
    • Kompatibilität zwischen CryptoKeySlot.cryptoAlgId, slotType und den von der Persistenz-Implementierung unterstützten Chiffren/Modi muss tooling-seitig (Manifest-Validator/Generator) sichergestellt werden.
