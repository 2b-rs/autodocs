1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR BSW-Schichtenmodell / Modul-Interaktionsdiagramm (Software Architecture Block Diagram).
  • Technischer Zweck: Darstellung der Einbettung des Ethernet Switch Drivers (EthSwt) in die Kommunikationsarchitektur der Classic Platform (CP) sowie dessen statische Schnittstellenbeziehungen zu oberen Abstraktionsschichten, Nachbartreibern und der Mikrocontroller-Abstraktionsschicht (MCAL).
  • Funktionale Einordnung:
    • Schicht 1 (grün): Communication Hardware Abstraction (ECU Abstraction Layer) mit Ethernet Interface (EthIf), Ethernet Switch Driver (EthSwt) und Ethernet Transceiver Driver (EthTrcv).
    • Schicht 2 (rot): Microcontroller Abstraction Layer (MCAL) mit Ethernet Driver (Eth) und SPI Driver (Spi).
    • Hardware-Übergang: Physikalische Kopplung über MII/MDIO bzw. SPI-Bus.

2. Komponenten, Entitäten & Schnittstellen

Schichtenkomponenten
  • Ethernet Interface (EthIf): Zentraler Abstraktions- und Dispatch-Layer. Bietet oberen Kommunikationsschichten (z. B. TcpIp, SoAd) eine einheitliche, hardwareunabhängige Netzwerkschnittstelle.
  • Ethernet Switch Driver (EthSwt): Abstraktionstreiber für Ethernet-Switches (Layer 2). Verantwortlich für Port-Konfiguration, Forwarding-Tabellen, VLAN-Handling, Port-Mirroring und Switch-Management. Unterstützt jeweils genau einen Switch-Hardwaretyp pro Treibermodul.
  • Ethernet Transceiver Driver (EthTrcv): Steuerung und Zustandsverwaltung der Ethernet-PHYs (Link-Status, Auto-Negotiation, Power Modes).
  • Ethernet Driver (Eth) (MCAL): On-Chip-MAC-Controller-Treiber für Frame-Senden/-Empfangen (Tx/Rx) sowie hardwarenahen Registerzugriff via MII/MDIO.
  • SPI Driver (Spi) (MCAL): Mikrocontroller-Treiber für serielle Peripherie-Kommunikation bei extern angebundenen Switch-Controllern.
Schnittstellen und Beziehungen
  • EthIf ↔ EthSwt (bidirektional): Management-API zur Konfiguration von Switch-Ports, VLANs und Abfrage von Switch-Zuständen.
  • EthSwt ↔ EthTrcv (bidirektional): Steuerung und Abfrage von Transceivern, die direkt mit den Switch-Ports assoziiert bzw. im Switch integriert sind.
  • **EthIf ↔ EthTrcv (gestrichelt, bidirektional – „ECUs without switch“):** Direkter Bypass-Pfad in Architekturen ohne Switch; EthIf steuert EthTrcv unmittelbar an.
  • EthIf ↔ Eth (bidirektional): Datenpfad (Data Plane) für Frame-Transmission/Reception (Eth_Transmit, Rx-Indication) sowie MAC-Initialisierung/Controller-Modes.
  • EthTrcv ↔ Eth (bidirektional): MDIO/SMI-Klausel-Zugriff über den MAC-Controller zur PHY-Register-Konfiguration (Eth_ReadMii, Eth_WriteMii).
  • EthSwt → Eth (unidirektional, Steuerpfad): Switch-Registerzugriff über das MII/MDIO-Management-Interface des on-chip MACs.
  • EthSwt → Spi Driver (unidirektional, Steuerpfad): Alternativer Switch-Registerzugriff über SPI für Switch-ICs mit dediziertem SPI-Management-Interface.
  • Hardware-Schnittstellen (externe Pins):
    • Eth → MII/MDIO: Datenschnittstelle (MII/RMII/RGMII) und serielle Management-Schnittstelle.
    • Spi Driver → SPI-Bus: Chip-Select-, Clock- und Datenleitungen zum externen Switch.

3. Dynamisches Verhalten & Sequenzablauf

Da das Diagramm die statische Schichtung abbildet, leiten sich hieraus zwei disjunkte Laufzeitpfade (Data Plane vs. Control Plane) ab:

Data Plane (Nutzdatenpfad)
  • Der reguläre Frame-Transfer (Tx/Rx) durchläuft nicht den EthSwt.
  • Tx: Upper Layers → EthIf_Transmit() → Eth_Transmit() → MII/Hardware.
  • Rx: MII/Hardware → Eth_RxStatusType / ISR → EthIf_RxIndication() → Upper Layers.
  • Sonderfall Switch-Header: Falls der Switch Port-Tagging/Management-Frames erfordert (z. B. Tail-Tagging), werden Header-Manipulationen durch das Zusammenspiel von EthIf und EthSwt im Buffer vorbereitet, die Datenübertragung verbleibt jedoch zwischen EthIf und Eth.
Control Plane (Management- & Konfigurationspfad)
  • Initialisierung: EthIf initialisiert Eth, EthTrcv und – falls vorhanden – EthSwt.
  • Switch-Registerzugriff (synchron/asynchron):
    • Pfad A (In-Band / MDIO): EthSwt ruft Eth_ReadMii() / Eth_WriteMii() auf.
    • Pfad B (Out-of-Band / SPI): EthSwt nutzt Spi_SyncTransmit() / Spi_AsyncTransmit() mit definierten Sequences/Channels.
  • Link-Überwachung: Statusänderungen der Ports werden von EthTrcv via EthSwt bzw. EthIf aggregiert (EthIf_TrcvModeIndication(), Link-State-Polling via MainFunctions).

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Control- und Data-Plane: EthSwt ist primär ein Control-Plane-Treiber. Entwickler dürfen keinen PDU-Payload-Durchsatz über EthSwt routen.
  • Namespace & Vendor-Präfixe: Zur Unterstützung mehrerer unterschiedlicher Switch-Hardwaretypen auf einem Steuergerät erfordert die Spezifikation modulindividuelle Präfixe (z. B. EthSwt_<VendorId>_<VendorApiInfix>_...). EthIf bindet die entsprechenden Treiberinstanzen über standardisierte Funktionszeigertabellen bzw. generierte Konfigurations-Dispatch-Tabellen ein.
  • Konfigurationsentscheidung Registerzugriff: Die BSW-Konfiguration (ECUC) von EthSwt muss explizit auf die zugrundeliegende Management-Schnittstelle (Eth-MII oder Spi) gemappt werden:
    • Bei SPI: Zuordnung von SpiSequenceRef / SpiChannelRef.
    • Bei MDIO: Zuordnung zu EthCtrlRef und MDIO-Transceiver-/Switch-Adresse.
  • Port-Abstraktion & Trcv-Mapping: Integrierte Switch-Ports mit integrierten PHYs erfordern eine konsistente Modellierung in den BSW-Modulkonfigurationen (EthIfPortGroup, EthSwtPort, EthTrcv). Bei ECUs ohne Switch (ECUs without switch) wird EthSwt in der Stack-Generierung komplett entkoppelt bzw. nicht instanziiert, wodurch der direkte Pfad EthIf ↔ EthTrcv aktiv ist.

Specification of Ethernet Switch Driver AUTOSAR CP R24-11 1 Introduction and functional overview In the AUTOSAR Layered Software Architecture [1], the Ethernet Switch Driver belongs to the Communication Hardware Abstraction. This indicates the main task of the Ethernet Switch Driver: Provide to the upper layers (e.g. Ethernet Interface [2]) a hardware independent interface comprising a switch with several ports. This interface shall be uniform for all Ethernet switches. Thus, the upper layers may access the underlying communication technology in a uniform manner. A single Ethernet Switch Driver module supports only one type of switch hardware. The Ethernet physical layer ports are configured by the Ethernet Transceiver Driver[3]. The Ethernet Switch Driver’s prefix generates a unique namespace. The Ethernet Interface can access different Ethernet controller types using different Ethernet Switch Drivers using this prefix. The decision which driver to use to access a particular transceiver is a configuration parameter of the Ethernet Interface. Figure 1.1 depicts the lower part of the Ethernet stack. Accesses via an SPI- and MII/MDIO-Hardware-Interface for switch specific configuration or functions are directly done via the Ethernet Driver [4] or the SPI driver [5].
