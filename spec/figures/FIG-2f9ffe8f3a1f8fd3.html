1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Sequenzdiagramm mit Interaktionsreferenzen (ref-Frames / Interaction Use).
  • Architektur-Kontext: AUTOSAR Classic Platform (Release 4.0.3), Spezifikation des ECU State Managers (AUTOSAR_SWS_ECUStateManager).
  • Funktionaler Zweck: Darstellung der Phasenübergänge und des Kontrollflusses während der Initialisierungssequenz (STARTUP Phase) des Steuergeräts vom Hardware-Reset über den C-Laufzeitaufbau (Pre-OS) bis zur Übergabe an das Betriebssystem (OS) und die anschließende Wiederaufnahme durch den EcuM (Post-OS).

2. Komponenten, Entitäten & Schnittstellen

  • Akteure & Lifelines:
    • Reset: Externer Hardware-Reset-Auslöser (Power-On-Reset, Watchdog, Software-Reset).
    • Boot Menu: Bootloader- / Hardware-Startup-Code bzw. Reset-Handler-Einsprungpunkt.
    • C Init Code: Hardwarenaher C-Laufzeit-Startup (Zeroing .bss, Initialisieren von .data, Stack-Pointer-Konfiguration).
    • «module» Os: AUTOSAR Operating System (Klasse: Systemdienst / Basissoftware-Modul).
    • BSW Task (OS task or cyclic call): Spezifische OS-Task (Autostart-Task) zur Ausführung zyklischer oder sequentieller Basissoftware-Abläufe.
    • «module» EcuM: ECU State Manager (Klasse: Systemdienst-Modul zur zentralen Verwaltung der ECU-Zustände).
  • Interaktionsreferenzen (ref):
    • StartPreOS Sequence: Kapselt EcuM-Initialisierungsschritte vor Start des Kernels (u. a. EcuM_InitDriverInitBlock(0), Det-, Dem- und Basistreiberinitialisierung).
    • StartPostOS Sequence: Kapselt Initialisierungsschritte nach OS-Start (u. a. Scheduler-Start via SchM, BswM_Init, Treiberinitialisierung Block 2/3).
  • Schnittstellen / Signaturen:
    • Reset Vector(): Hardwarespezifischer Eintrittsvektor.
    • Jump(): Direkter Verzweigungsbefehl in die C-Laufzeit-Initialisierung.
    • Set up stack(): Interner Aufruf zur Konfiguration der CPU-Register und Stack-Pointer.
    • EcuM_Init(): Synchrone Einstiegs-API des EcuM vor OS-Start.
    • StartOS(): Kernelschnittstelle zum Hochfahren des OS (übernimmt die Ausführungskontrolle).
    • StartupHook(): Konfigurierbarer OS-Callback für anwendungsspezifischen Pre-Task-Code.
    • ActivateTask(): OS-Systemdienst zur Aktivierung der initialen BSW-Task (bzw. impliziter Task-Start via OS-Autostart).
    • EcuM_StartupTwo(): Synchrone EcuM-API zur Fortsetzung der Startup-Sequenz im Task-Kontext.

3. Dynamisches Verhalten & Sequenzablauf

  1. Hardware-Trigger: Reset springt den Reset Vector() der Bootloader-/Boot-Menu-Logik an.
  2. Low-Level Startup: Boot Menu verzweigt via Jump() in den C Init Code.
  3. C-Laufzeit: C Init Code führt Set up stack() aus und initialisiert Speichersektionen.
  4. Pre-OS Phase (EcuM):
    • Synchroner Aufruf von EcuM_Init().
    • Ausführung der StartPreOS Sequence: Minimale Hardwaretreiber-Initialisierung (u. a. MCU, Base Clocks, Pre-OS I/O) und Konfiguration der Basistreiber.
  5. Kontrollabgabe an das OS:
    • EcuM ruft synchron StartOS() auf; der Kontrollfluss verlässt die EcuM_Init()-Sequenz dauerhaft (kein direkter Return von StartOS).
  6. OS-Initialisierung:
    • Der OS-Kernel übernimmt die CPU-Kontrolle und ruft optional den synchronen StartupHook() auf.
    • Das OS aktiviert die BSW-Starttask (explizit via ActivateTask() oder konfiguriert als AUTOSTART = TRUE).
  7. Post-OS Phase (EcuM):
    • Als allererste Aktion innerhalb der BSW-Task wird EcuM_StartupTwo() synchron aufgerufen.
    • EcuM führt die StartPostOS Sequence aus (Initialisierung der verbleibenden BSW-Stacks, SchM, Start der BSW-Scheduler-Loops).
    • Nach Rückkehr von EcuM_StartupTwo() setzt die Task ihre reguläre Ausführung fort (z. B. Übergang in zyklische Ausführung oder Beenden via TerminateTask()).

4. Normative Relevanz & Entwickler-Hinweise

  • API-Vertrag & Kontrollflussverlust: StartOS() kehrt gemäß OSEK/AUTOSAR OS-Spezifikation nie zum Aufrufer zurück. EcuM_Init() wird somit niemals regulär beendet.
  • Integrationspflicht (Autostart-Task): Der System-Integrator muss zwingend eine OS-Task konfigurieren (AUTOSTART = TRUE im OIL/ARXML), deren allererste Anweisung der Aufruf von EcuM_StartupTwo() ist. Jede Verzögerung oder vorherige Task-Aktivität verletzt den Startup-Vertrag.
  • Kontextbedingungen:
    • In StartPreOS Sequence (EcuM_Init): Kein Tasking, keine OS-Ressourcen/Events, Interrupts typischerweise global gesperrt (SuspendAllInterrupts oder HW-Level). Nur zustandslose Basistreiber zulässig.
    • In StartPostOS Sequence (EcuM_StartupTwo): Voller Task-Kontext verfügbar; Inter-Modul-Kommunikation und OS-Dienste (Events, SchM) sind betriebsbereit.
  • Fehlerbehandlung: Fehler in der StartPreOS Sequence vor Initialisierung von Dem/Det führen in hardwarenahe Trap-/Reset-Handler oder Endlosschleifen (EcuM_ErrorHook). Erst in EcuM_StartupTwo() steht die vollständige Diagnose- und Fehlerberichterstattung zur Verfügung.
