1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECUC-Metamodell-Diagramm (UML-Klassendiagramm zur Definition von ECU-Konfigurationsparametern und -containern).
  • Architektur-Kontext: AUTOSAR Classic Platform, Basic Software (BSW) Services Layer, Modul Diagnostic Communication Manager (Dcm), Submodul Diagnostic Service Processing (DSP).
  • Funktionaler Zweck: Formale Spezifikation der Konfigurationsstruktur für hierarchisch geschachtelte Nutzdatenstrukturen (Nested Data / Composite DIDs) innerhalb des UDS-Dienstes 0x22 (ReadDataByIdentifier), 0x2E (WriteDataByIdentifier) und 0x2F (InputOutputControlByIdentifier). Das Modell definiert, wie ein Diagnosedaten-Identifier (DcmDspDid) modular aus Einzelsignalen (DcmDspDidSignal) zusammengesetzt, im PDU-Buffer über Byte-Offsets positioniert und auf atomare Schnittstellen (DcmDspData) oder wiederverwendbare Signal-Verbünde (DcmDspDidSignalCompositePool) abgebildet wird.

2. Komponenten, Entitäten & Schnittstellen

#### ECUC-Container (EcucParamConfContainerDef)

  • DcmDsp [0..1]: Root-Konfigurationscontainer des Submoduls DSP; kapselt alle DID-, Daten- und Signaldefinitionen.
  • DcmDspDid [0..*]: Repräsentiert einen konkreten UDS Data Identifier (DID). Subcontainer von DcmDsp.
  • DcmDspDidSignal [0..*]: Definiert ein einzelnes Signalelement innerhalb eines DIDs oder innerhalb eines Composite-Signalpools.
  • DcmDspData [0..*]: Repräsentiert die atomare Nutzdateninstanz inklusive Zugriffsfunktionen (Sender/Receiver, Client/Server, C-Callbacks, NvM-Ports). Subcontainer von DcmDsp.
  • DcmDspDidSignalCompositePool [0..*]: Container-Pool für zusammengesetzte, wiederverwendbare Signalstrukturen. Subcontainer von DcmDspDid.

#### Parameter & Referenzen

  • DcmDspDidByteOffset (EcucIntegerParamDef) [1..1]:
  • Zugeordnet zu: DcmDspDidSignal.
  • Wertebereich: 0 .. 65535.
  • Semantik: Nullbasierter Start-Byte-Offset des Signals im linearen Diagnose-PDU-Datenstrom des übergeordneten DIDs.
  • DcmDspDataByteSize (EcucIntegerParamDef) [0..1]:
  • Zugeordnet via +parameter zu: DcmDspData und DcmDspDidSignal.
  • Wertebereich: 0 .. 65535. Flag A (automatisch berechnet bzw. abgeleitet).
  • Semantik: Physikalische Bytegröße des Nutzdatenblocks bzw. Signals.
  • DcmDspDidDataRef (EcucReferenceDef) [0..1]:
  • Quelle: DcmDspDidSignal.
  • Ziel (+destination): DcmDspData.
  • Semantik: Verknüpft das Signal mit einem konkreten atomaren Datenendpunkt.
  • DcmDspDidSignalCompositeRef (EcucReferenceDef) [0..*]:
  • Quelle: DcmDspDidSignal.
  • Ziel (+destination): DcmDspDidSignalCompositePool.
  • Semantik: Ermöglicht hierarchische Schachtelung, indem ein Signal auf einen Pool weiterer Teilsignale verweist.

3. Dynamisches Verhalten & Laufzeit-Serialisierung

Das Konfigurationsmodell determiniert den Ablauf der PDU-Serialisierung/Deserialisierung im DCM:

```

[Diagnose-Request (PduR)]

│

▼

[DSD: Service 0x22 / 0x2E / 0x2F Dispatch]

│

▼

[DSP: DID-Parser & Resolver]

│

├─► Iteration über 'DcmDspDidSignal' gemäß 'DcmDspDidByteOffset'

│ │

│ ├─► Fall 1: DcmDspDidDataRef aktiv (Atomar)

│ │ └─► Aufruf SW-C/BSW (Rte_Read, Rte_Call, NvM_ReadBlock)

│ │ Serialisierung in/aus Buffer bei [ByteOffset .. ByteOffset + ByteSize - 1]

│ │

│ └─► Fall 2: DcmDspDidSignalCompositeRef aktiv (Nested)

│ └─► Rekursiver Einstieg in 'DcmDspDidSignalCompositePool'

│ Auflösung der Sub-Signale mit relativen/absoluten Offsets

▼

[Response-PDU Assemblierung / Validierung]

```

  • Laufzeit-Ablauf (Service 0x22 - Read):
  1. DSP lokalisiert die dem DID zugeordneten DcmDspDidSignal-Einträge.
  2. Für atomare Signale (DcmDspDidDataRef) werden die konfigurierten Zugriffsoperationen (synchron oder asynchron via Dcm_ReadDataConditionCheck, Dcm_ReadData) ausgeführt.
  3. Bei asynchronen SW-C-Aufrufen wechselt der Signalverarbeitungsstatus auf DCM_E_PENDING; das Modul wartet auf die Fertigstellung, bevor die Response finalisiert wird.
  4. Die gelesenen Bytes werden exakt an der durch DcmDspDidByteOffset definierten Position in den Tx-PDU-Buffer kopiert.
  • Laufzeit-Ablauf (Service 0x2E - Write):
  1. Validierung der Request-PDU-Länge gegen die Summe aller DcmDspDataByteSize-Angaben.
  2. Extrahieren der Payload-Segmente pro Signal ab DcmDspDidByteOffset.
  3. Übergabe an die Applikation via Dcm_WriteData oder RTE-Ports.
  • Fehlerpfade & NRC-Mapping:
  • PDU-Länge stimmt nicht mit berechneter Gesamtgröße überein: Sofortiger Abbruch mit NRC 0x13 (IncorrectMessageLengthOrInvalidFormat).
  • Signal-Lese-/Schreibzugriff schlägt fehl (z. B. DCM_E_NOT_OK): Abbruch mit NRC 0x22 (ConditionsNotCorrect) oder applikativ definierter NRC.
  • Asynchroner Timeout: Abbruch, Rücksetzen des DCM-Zustandsautomaten und Meldung an DET/DEM.

4. Normative Relevanz & Entwickler-Hinweise

#### Spezifikationsanforderungen (SWS-IDs)

  • SWS_Dcm_01633 (Exklusivität der Signalbindung):

Für jedes DcmDspDidSignal gilt zwingend die XOR-Bedingung: Es muss entweder genau eine DcmDspDidDataRef oder mindestens eine DcmDspDidSignalCompositeRef konfiguriert sein, niemals beides gleichzeitig. Ein Signal ist entweder atomares Blatt oder Composite-Knoten.

  • SWS_Dcm_01634 (Offset-Konsistenz):

DcmDspDidByteOffset muss strikt monoton ansteigend sein. Überlappungen von Signalbereichen (ByteOffset + ByteSize) sind unzulässig, sofern sie nicht explizit als redundante Signalprojektionen deklariert sind.

  • SWS_Dcm_01635 (Puffer- und Größendeklaration):

Die Gesamtlänge des DcmDspDid ergibt sich deterministisch aus dem höchsten Offset plus der Größe des letzten enthaltenen Signals. Der BSW-Konfigurator muss dies gegen die maximalen Buffergrößen der DSL (DCM_BUFFER_SIZE) validieren.

  • SWS_Dcm_01636 (Hierarchische Strukturierung):

Unterstützung strukturierter Datentypen: Ermöglicht die direkte 1:1-Abbildung komplexer Autosar-Datentypen (ImplementationDataType mit Kategorie STRUCTURE oder ARRAY) aus der SWC-Beschreibung (ARXML) auf die Diagnoseebene, ohne dass manuelle Flachklopfung (Flattening) in C-Code nötig ist.

#### Konkrete Konsequenzen für Implementierung & Integration

  • BSW-Codegenerator: Generiert kompakte ROM-Deskriptor-Tabellen (z. B. Dcm_DspDidSignalType[] mit Funktionszeigern, ByteOffsets und Längen). Eine Verschachtelung über den Pool wird im Generat meist statisch "eingeebnet", um Rekursionen und Stack-Überläufe im Embedded-System zur Laufzeit zu vermeiden.
  • Applikations-Entwickler: Bei Composite-DIDs müssen keine monolithischen Datenstrukturen über einen einzelnen Service-Port bereitgestellt werden. Signale können aus unterschiedlichen SW-Cs stammen; der DCM fungiert als Assembler auf BSW-Ebene.
  • Bit-Felder vs. Byte-Offsets: Das Diagramm spezifiziert Byte-Offsets (DcmDspDidByteOffset). Werden Sub-Byte-Signale benötigt, müssen diese entweder über Bitmasken innerhalb des DcmDspData verarbeitet oder vor der PDU-Übergabe in der Applikationsschicht gepackt werden.
