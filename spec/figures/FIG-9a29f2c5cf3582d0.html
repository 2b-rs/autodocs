1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR Methodology Activity/Data-Flow Diagram (angelehnt an das SPEM-Metamodell – Software & Systems Process Engineering Metamodel).
  • Architektur-Kontext: AUTOSAR Classic Platform (Spezifikationskontext: AUTOSAR_EXP_VFB, R4.0.3, abgeleitet aus AUTOSAR_TR_Methodology).
  • Technischer Zweck: Darstellung des standardisierten, modellbasierten Entwicklungs- und Generierungsworkflows über die drei Abstraktions- und Verantwortungsdomänen System, ECU (Steuergerät/Tier-1) und Component (SWC/Funktionsentwicklung) hinweg – vom VFB-Design bis zum flashbaren Binär-Image (.exe/.elf/.hex).

2. Komponenten, Entitäten & Schnittstellen

#### Abstraktionsebenen (Swimlanes / Prozessdomänen)

  1. System: Gesamtfahrzeugebene (OEM-Verantwortung, Topologie, Bus-Cluster, systemweite VFB-Allokation).
  2. ECU: Steuergeräteebene (Tier-1-/Integrator-Verantwortung, BSW-, MCAL- und RTE-Generierung).
  3. Component: Software-Component-Ebene (Applikations- und Funktionsentwickler).

#### Aktivitäten (Prozessschritte / Chevron-Operatoren)

  • Configure System: System-Design, SWC-Instanziierung, Signal-to-PDU-Mapping, Bus-Scheduling und ECU-Allokation.
  • Extract ECU-Specific Information: Automatisierte Filterung/Projektion des Gesamtsystems auf ein Ziel-Steuergerät (ECU-Extract-Generierung).
  • Implement Component: Programmierung der Software-Komponenten (C-Code, Model-in-the-Loop/TargetLink/Simulink) basierend auf dem RTE-Component-Contract.
  • Configure ECU: BSW-, MCAL-, OS- und RTE-Parametrierung auf Basis des ECU-Extracts und der BSW-Modulbeschreibungen.
  • Generate Executable: Generierung von BSW-/RTE-Code, Kompilierung und Linken der Objektdateien/Libraries gegen OS und Hardware-Abstraktion.

#### Artefakte / Datenmodelle (Work Products)

  • ARXML-Beschreibungsdateien (Metamodell-Instanzen):
  • System Configuration Input : System: VFB-Beschreibungen (Software Component Descriptions, Datentypen, Interfaces), Topologiebeschreibungen, Kommunikationsmatrix-Vorgaben und Ressourcen-Constraints.
  • System Configuration Description :System: Vollständig instantiiertes Gesamtsystem-Modell (ARPackage mit System-Root, Cluster, Signals, Frames, EcuInstances, SWC-Mapping).
  • ECU Extract of System Configuration :System: Reduzierte Systembeschreibungs-Instanz (SYSTEM-EXTRACT), die ausschließlich die für die Ziel-ECU relevanten Ports, Signale, PDUs und gemappten SWCs enthält.
  • ECU related templates: Modulbeschreibungs-Templates der Basissoftware (BSW Module Description / BSWMD), BSW-Parametertreiber und MCAL-Konfigurationsschemata.
  • Component related templates: VFB-Schnittstellenbeschreibungen (Formales ARXML für Ports, Interfaces, Runnables, Events, SwcInternalBehavior).
  • ECU Configuration Description: Vollständiger Steuergeräte-Parametersatz (EcucDescriptionValues, .ecuc.arxml) für OS, Com-Stack, Mem-Stack, BswM, EcuM und RTE.
  • Code- und Binär-Artefakte:
  • Implemented Component: Quellcode (.c/.h) oder vorkompilierte Object-/Library-Dateien (.o/.a) der SWC inklusive Rte_Type.h-Referenzen.
  • ECU Executable: Vollständig gelinktes Binär-Image (.elf, .hex, .mot bzw. symbolisch .exe) zur Ausführung auf dem Ziel-Mikrocontroller.

#### Beziehungs- und Datenfluss-Semantik

  • Solid Lines (Data/Control Flow): Sequenzielle Produktion und Konsumation von Artefakten zwischen Aktivitäten (z. B. Configure System erzeugt System Configuration Description).
  • Dashed Lines (Referenz-/Template-Fluss):
  • System Configuration Input speist sowohl die Component related templates (Schnittstellenvorgaben für SWC-Entwickler) als auch die ECU related templates.
  • ECU Extract of System Configuration referenziert/aktualisiert ECU related templates.

3. Dynamisches Verhalten & Sequenzablauf

  1. System-Design (OEM/Lead-Architekt):
  • Bereitstellung von Komponenten- und Topologiebeschreibungen (System Configuration Input).
  • Ausführung von Configure System: Festlegung der EcuInstance, Mapping der SwComponentPrototype auf ECUs, Konfiguration von Frame-Layouts (CAN/LIN/FlexRay/Ethernet).
  • Ergebnis: System Configuration Description.
  1. Dekomposition & Verteilung (Split):
  • Ausführen von Extract ECU-Specific Information: Filterung nach Ziel-EcuInstance. Output ist der standardisierte ECU Extract of System Configuration.
  • Parallelzweig: Verteilung der Component related templates an Zulieferer oder Applikationsteams.
  1. Komponenten-Implementierung (Parallelpfad):
  • Applikationsentwickler erzeugen C-Dateien gegen die vom RTE-Generator im Contract Phase-Modus erzeugten Header (Rte_<swc>.h, Runnables mit Signaturen für Rte_Read/Rte_Write).
  • Ergebnis: Implemented Component.
  1. ECU-Integration & BSW-Konfiguration:
  • Import des ECU Extract in das ECU-Konfigurationstool.
  • Configure ECU: Auflösen von Signalen zu COM-Signalen, Konfiguration von PduR-Routings, BswM-Regeln, Task-Allokation im OS, Dem/Det-Events und Can/Lin/Eth-Treibern.
  • Ergebnis: ECU Configuration Description (.ecuc.arxml).
  1. Codegenerierung & Build-Phase:
  • Generate Executable:
  • BSW-Generatoren erzeugen Modul-Quellcode (Com_Cfg.c, Os_Cfg.c etc.).
  • RTE-Generator im Generation Phase-Modus erzeugt RTE-Glue-Code (Rte.c, Task-Bodies, Inter-Runnable-Variables).
  • Compiler und Linker binden Implemented Component, generierte RTE, BSW-Stacks, MCAL und Runtime-Libraries zum ECU Executable.

4. Normative Relevanz & Entwickler-Hinweise

  • Contract Phase vs. Generation Phase (RTE):
  • Applikationsentwickler (Component) dürfen niemals gegen den fertigen ECU-Stack kompilieren. Die Entwicklung erfolgt strikt entkoppelt auf Basis des Component related template (Metamodell-Element SwcInternalBehavior) mittels Contract-Phase-Headern.
  • ECU-Extract als bindender Integrations-Vertrag:
  • Der ECU Extract of System Configuration ist die normative Schnittstelle zwischen OEM und Tier-1. Nachträgliche manuelle Änderungen im Steuergeräte-Konfigurationstool (z. B. Port-Definitionen oder PDU-Längen) ohne Re-Import des System-Extracts verletzen die AUTOSAR-Konformität und führen zu Inkompatibilitäten beim Signal-Routing.
  • BSWMD-Konsistenz:
  • Die ECU related templates müssen exakt zum Schema und der Version des Ziel-BSW-Stacks (Vendor-spezifisch) passen; Parameterdefinitionen (EcucModuleDef) erzwingen Validierungsregeln im ECU-Konfigurationstool.
  • Metamodell-Restriktionen:
  • Datentypen müssen auf System-Ebene konsistent (ApplicationDataType zu ImplementationDataType via DataTypeMap) typisiert sein, um Compiler-Warnungen oder Alignment-Fehler bei 16-/32-/64-Bit-MCAL-Architekturen zu verhindern.
