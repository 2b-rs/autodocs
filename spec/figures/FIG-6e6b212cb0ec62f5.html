1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB-Komponentendiagramm (Virtual Function Bus View gemäß AUTOSAR-Metamodell, UML-Komponentendarstellung).
  • Technischer Zweck: Spezifikation des Zusammenspiels standardisierter AUTOSAR Application Interfaces (AI) für Human-Machine-Interfaces (HMI / UI Device Interfaces) am Beispiel einer Park-Distance-Control-Funktion (PDC).
  • Funktionale Einordnung: Demonstriert die lose Kopplung und modulare Trennung zwischen hardwarenahen UI-Bedienelementen (Taster, LED), übergeordneter HMI-Steuerungslogik (Controller) und dem fahrzeugspezifischen Funktionsdienst (Application Service) über den RTE/VFB-Kommunikationsmechanismus.

2. Komponenten, Entitäten & Schnittstellen

  • Software-Komponenten (SwComponentType):
    • PDC Button SWC (Kategorie: SensorActuator oder ApplicationSwComponent): Kapselt den physischen HMI-Taster.
    • PDC LED SWC (Kategorie: SensorActuator oder ApplicationSwComponent): Kapselt den optischen Rückmelde-Aktor (Status-LED).
    • PDC Application Controller SWC (ApplicationSwComponent): Beinhaltet die HMI-Zustands- und Vermittlungslogik zwischen Bedienelementen und PDC-Kernservice.
    • PDC Application Service SWC (ApplicationSwComponent / ServiceProxy): Realisiert die eigentliche PDC-Funktionalität (z. B. Ultraschallsensor-Auswertung, Distanzberechnung).
  • Ports & Schnittstellen (PortInterface):
    • Simple Button Ifc (Generic UI Device Interface):
      • Typ: Sender-Receiver-Interface (SenderReceiverInterface).
      • Datenelement: pressed (UInt1).
      • Port-Zuordnung: P-Port (ProvidedOuterPort, blau/Lollipop) an PDC Button SWC → R-Port (RequiredOuterPort, rot/Socket) an PDC Application Controller SWC.
    • PDC Service Ifc (Domain-spezifisches Service-Interface):
      • Typ: Sender-Receiver-Interface.
      • Datenelement: pdc_active (UInt1).
      • Port-Zuordnung: P-Port an PDC Application Controller SWC → R-Port an PDC Application Service SWC.
    • PDC Status Ifc (Domain-spezifisches Status-Interface):
      • Typ: Sender-Receiver-Interface.
      • Datenelement: pdc_on (UInt1).
      • Port-Zuordnung: P-Port an PDC Application Service SWC → R-Port an PDC Application Controller SWC.
    • Toggle State Ifc (Generic UI Device Interface):
      • Typ: Sender-Receiver-Interface.
      • Datenelement: active (UInt1).
      • Port-Zuordnung: P-Port an PDC Application Controller SWC → R-Port an PDC LED SWC.
  • Verbindungen: 4x AssemblySwConnector zur typkonformen 1:1-Verbindung zwischen P-Port und R-Port.

3. Dynamisches Verhalten & Sequenzablauf

  • Interaktionsmuster: Asynchrones, entkoppeltes Closed-Loop-Muster über Sender-Receiver-Kommunikation (kein Client-Server-RPC).
  • Ablaufkette:
    1. Eingabe-Trigger: Fahrer betätigt PDC-Taster. PDC Button SWC sendet pressed = 1 via Simple Button Ifc.
    2. Anforderungs-Generierung: PDC Application Controller SWC verarbeitet das Eingangsereignis (z. B. via DataReceivedEvent oder zyklisch abfragendes TimingEvent), toggelt die interne Funktionsanforderung und übermittelt pdc_active = 1 via PDC Service Ifc an den Service.
    3. Funktionsaktivierung & Quittierung: PDC Application Service SWC empfängt den Aktivierungswunsch, validiert systemspezifische Einschaltbedingungen (Fahrgeschwindigkeit, Getriebegang, Fehlerstatus) und schaltet die Sensorik scharf. Der tatsächliche Betriebszustand wird über PDC Status Ifc mit pdc_on = 1 zurückgespiegelt.
    4. HMI-Rückmeldung: PDC Application Controller SWC empfängt pdc_on = 1, synchronisiert den optischen Status und schreibt active = 1 via Toggle State Ifc an PDC LED SWC, woraufhin die physische Status-LED bestromt wird.
  • Rückfallebene/Abbruchbedingung: Kann PDC Application Service SWC nicht aktivieren (z. B. wegen Diagnoseblockade oder Übergeschwindigkeit), bleibt pdc_on = 0. Die HMI-LED wird nicht aktiviert; Fehlbedienungen bzw. Diskrepanzen zwischen Taster-Betätigung und tatsächlichem Systemzustand werden deterministisch verhindert.

4. Normative Relevanz & Entwickler-Hinweise

  • Generische HMI-Abstraktion: Die Standardisierung generischer Schnittstellen (Simple Button Ifc, Toggle State Ifc) entkoppelt HMI-Peripherie vollständig von Applikationsfunktionen. Dieselbe PDC Button SWC bzw. PDC LED SWC kann ohne Code-Änderung an beliebige Funktionscontroller angebunden werden.
  • RTE-API-Vertrag:
    • Da alle Schnittstellen als Sender-Receiver modelliert sind, generiert der RTE-Generator unblockierende Lese-/Schreib-APIs (z. B. Rte_Write_<p>_active() / Rte_Read_<r>_active()).
    • Je nach SWC-Design wählbar als implizite Datenkommunikation (Rte_IRead / Rte_IWrite für deterministische Ausführungskontexte) oder explizite Datenkommunikation (Rte_Read / Rte_Write).
  • Verteilungstransparenz (ECU-Mapping): Die Architektur erlaubt beliebiges Mapping:
    • Intra-ECU: Alle SW-Cs auf einem Controller (RTE wickelt Datentransfer über Puffer/Shared Memory ab).
    • Inter-ECU: PDC Button SWC und PDC LED SWC auf dem Body Control Module (BCM), PDC Application Service SWC auf dem Fahrerassistenz-Steuergerät (ADAS/PDC). Die RTE wandelt die Signale netzwerktransparent über COM/PDU-R in CAN/LIN-Botschaften um.
  • Datentyp-Restriktion: Datentyp UInt1 fungiert als binäres Flag (0 = Inaktiv, 1 = Aktiv). Für erweiterte HMI-Konzepte (z. B. langes Drücken, Doppelklick, LED-Blinkmuster) sind erweiterte Enums oder zusätzliche Timing-Events im Controller vorzusehen.
