1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML 2.x Komponentendiagramm (Modul-Abhängigkeitsdiagramm) mit Schnittstellenrealisierungen («realize») und gerichteten Abhängigkeiten («use», «mandatory», «optional») in Ball-and-Socket-Notation.
  • Funktionale Einordnung: AUTOSAR Classic Platform (Release R23-11), Schicht der Communication Services (System Services / BSW). Das Modul CanSM (CAN State Manager) abstrahiert die busspezifische Zustandsverwaltung. Es fungiert als Bindeglied zwischen den netzwerkunabhängigen Management-Modulen (ComM, BswM, EcuM), dem System-Scheduler (SchM), Diagnose/Fehlerbehandlung (Dem, Det) und den protokollspezifischen Schichten des CAN-Stacks (CanIf, CanNm).

2. Komponenten, Entitäten & Schnittstellen

Dargestellte BSW-Module («module»)
  • CanSM: Zentraler CAN State Manager zur Steuerung von Betriebszuständen (NO_COM, SILENT_COM, FULL_COM) und Bus-Off-Recovery-Zyklen.
  • Obere Management- & Systemschicht:
    • ComM: Communication Manager (initiiert Kommunikationsmodi netzwerkweit).
    • BswM: Basic Software Mode Manager (regelt systemweite Modenübergänge auf Basis von Zustandsrückmeldungen).
    • EcuM: ECU State Manager (steuert Start-up/Shutdown sowie Wake-up-Validierung).
    • SchM: Schedule Manager / BSW Scheduler (steuert die zyklische Ausführung von Main-Functions).
  • Diagnose- & Error-Services:
    • Dem: Diagnostic Event Manager (Erfassung qualifizierter Bus-Off- und Kommunikationsfehler).
    • Det: Default Error Tracer (Erfassung von Entwicklungs- und Laufzeitfehlern).
  • CAN-Protokollstack (untere Schicht):
    • CanIf: CAN Interface (Hardware-Abstraktion für CAN-Controller und Transceiver).
    • CanNm: CAN Network Management (Osek/AUTOSAR NM-Zustandsverwaltung, Teilnetzbetrieb).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierungsphase (Synchron):
    • Aufruf von CanSM_Init() durch den EcuM. Das Modul geht von CANSM_UNINIT in CANSM_INITED über. Jeder konfigurierte Kanal startet im Zustand CANSM_BSM_S_NOT_INITIALIZED bzw. CANSM_BSM_S_NOCOM.
  2. Modusanforderung & Transition (Asynchron):
    • Trigger: ComM fordert über CanSM_RequestComMode(NetworkHandle, COMM_FULL_COMMUNICATION) Vollkommunikation an.
    • Kanalsteuerung: CanSM setzt via CanIf_SetControllerMode() den CAN-Controller in den Modus CAN_CS_STARTED und schaltet via CanIf_SetPduMode() den PDU-Empfang/Versand scharf.
    • Bestätigungspfad: Der CAN-Treiber meldet den physischen Moduswechsel asynchron an CanIf, welches via Callback CanSM_ControllerModeIndication() die Zustandsmaschine des CanSM weiterschaltet.
    • Abschluss: CanSM meldet den neuen Zustand synchron via ComM_BusSM_ModeIndication() an ComM sowie via BswM_CanSM_CurrentState() an den BswM.
  3. Bus-Off Recovery:
    • Trigger: Hardware detektiert Bus-Off → CanIf ruft CanSM_ControllerBusOff().
    • Fehlerprotokollierung: CanSM setzt Event via Dem_SetEventStatus(CANSM_E_BUS_OFF, DEM_EVENT_STATUS_FAILED).
    • Recovery-Zustandsautomat: CanSM stoppt Controller und PDUs (CanIf_SetPduMode(..., CANIF_SET_TX_OFFLINE)), startet Bor-Timer (L1/L2 Erholungszeiten). Nach Ablauf re-initialisiert CanSM den Controller über CanIf. Bei erfolgreicher Erholung wird das Dem-Event auf DEM_EVENT_STATUS_PASSED zurückgesetzt.
  4. Fehlerbehandlung:
    • Vor CanSM_Init eintreffende Aufrufe oder ungültige IDs werden synchron mit Det_ReportError verworfen.

4. Normative Relevanz & Entwickler-Hinweise

  • Kein direkter MCAL-Zugriff: Der CanSM greift unter keinen Umständen direkt auf Treiber (Can, CanTrcv) zu, sondern nutzt zwingend die Abstraktionsschicht CanIf.
  • Pre-Compile Schalter & Codegenerierung:
    • CanSMDevErrorDetect: Deaktivierung spart Flash/ROM und Zykluszeit ein, schaltet jedoch alle Aufrufe von Det_ReportError ab.
    • CanSMPnSupport: Ist Partial Networking (PN) im Cluster nicht konfiguriert, entfallen die Pfade zu CanNm_ConfirmPnAvailability() vollständig.
  • Scheduling & Thread-Safety:
    • CanSM_MainFunction erfordert feste, deterministische Zykluszeiten (typisch 5–10 ms), da Bus-Off-Timer (CanSMBorTimeL1, CanSMBorTimeL2) und Modus-Timeouts (CanSMModeRequestRepetitionTime) softwarebasiert in dieser Routine dekrementiert werden.
    • Callbacks wie CanSM_ControllerBusOff() können im Interrupt-Kontext des CAN-Treibers aufschlagen. CanSM-Zustandsvariablen müssen durch SchM-Exklusivbereiche (SchM_Enter_CanSM_... / SchM_Exit_CanSM_...) vor Dateninkonsistenzen geschützt werden.
  • Entwickler-Falle (ComM-Quittierung): CanSM darf ComM_BusSM_ModeIndication erst nach vollständiger Bestätigung aller Teilschritte (Controller-Status, Transceiver-Status via CanIf) aufrufen. Das Blockieren der Schnittstelle oder synchrone Polling-Schleifen in Callbacks ist nach AUTOSAR-SWS unzulässig.
