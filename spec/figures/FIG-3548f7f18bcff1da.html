1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Architekturschichten- und Allokationsdiagramm (Deployment & Execution Model) zur Entkopplung von Betriebssystem-Kontexten über Clustergrenzen hinweg.
  • Technischer Zweck: Visualisierung des OS Proxy-Konzepts im Rahmen von AUTOSAR Classic Software Clusters (SwClu). Es ermöglicht die zeit- und ereignisgesteuerte Aktivierung von Tasks in einer separat updatebaren Applikations-Partition (SwClu Application) durch den zentral im Basis-Cluster (SwClu Host) verorteten OS-Kern.
  • Funktionale Einordnung: Entkopplung der Kompilier- und Link-Abhängigkeiten zwischen Host (enthält Kern-OS, Treiber, BSW) und Application Cluster (enthält anwendungsspezifische SWCs und RTE). Die Proxy-Schichten (OS Low Proxy / OS High Proxy) überbrücken die MPU- und Adressraumgrenzen via definierter Manifest-Schnittstellen (Binary Manifest).

2. Komponenten, Entitäten & Schnittstellen

  • Software Clusters:
  • SwClu Host: Privilegierter Basis-Cluster mit zentralem Betriebssystem (OS/IOC-Kern) und Hardware-nahen Treibern.
  • SwClu Application: Unprivilegierter bzw. separat kompilierter/flashbarer Software-Cluster für Anwendungssoftware.
  • OS-Applikationen & Partitionierung:
  • OsApp.A, OsApp.B: Entsprechen OS-Applications gemäß AUTOSAR OS-Spezifikation (MPU-geschützte Speichergrenzen, Core-Zuordnung). Beide Partitionen existieren konzeptionell gespiegelt bzw. korrespondierend im Host und im Application Cluster.
  • Proxy-Entitäten:
  • OS Low Proxy (Host-seitig): Beherbergt den OS / IOC Socket sowie clusterübergreifende Dispatcher Task A und Dispatcher Task B.
  • OS High Proxy (Application-seitig): Empfängt Dispatches aus dem Low Proxy und leitet diese an die anwendungsseitigen Tasks weiter.
  • Task-Entitäten & Scheduling-Akteure:
  • OS Task A / OS Task B (Host): Reguläre OS-Tasks (z. B. durch Schedule Tables oder Alarme im Host periodisch aktiviert), die das Dispatching anstoßen.
  • Dispatcher Task A / Dispatcher Task B: Vermittlungs-Tasks im Low Proxy, die den Kontextwechsel und Cluster-Übertritt vorbereiten.
  • OS Task App A / OS Task App B: Lokale Task-Instanzen im Application Cluster, die den eigentlichen Ausführungskontext für die SWC-Runnables bereitstellen.
  • SWCs & Runnables:
  • SWC A, SWC B (in OsApp.A): Enthalten Run1_10ms und Run2_10ms.
  • SWC C (in OsApp.B): Enthält Run3_10ms.
  • Ausführung erfolgt gekapselt über die clusterspezifische RTE.
  • Schnittstellen & Inter-Process Communication:
  • Binary Manifest: Schnittstellenkontrakt (Relocation-Tabellen, Entry-Point-Vektoren, Funktionszeiger-Tabellen), der ABI-Kompatibilität ohne Neulinken garantiert.
  • OS / IOC Socket: Kommunikationskanal zwischen Host-OS und Proxy-Infrastruktur.
  • Local IOC: Task- und Partitions-interne IPC innerhalb des Application Clusters (OsApp.A $\leftrightarrow$ OsApp.B), ohne den Host-OS-Stack passieren zu müssen.

3. Dynamisches Verhalten & Sequenzablauf

  1. Triggering im Host-OS:
  • Ein Host-OS-Ereignis (z. B. Timer-Alarm, Schedule Table Expiry Point) aktiviert die Host-Tasks OS Task A bzw. OS Task B.
  1. Delegation an Low Proxy:
  • OS Task A triggert Dispatcher Task A innerhalb des OS Low Proxy. Entsprechend aktiviert OS Task B die Dispatcher Task B.
  1. Cluster-Grenzenübertritt:
  • Der Dispatcher nutzt die Vektoren des Binary Manifest und die OS / IOC Socket-Infrastruktur, um synchron oder asynchron die Kontrollübergabe an den OS High Proxy der SwClu Application zu vollziehen (inkl. Adressraum- bzw. Privileg-Switch falls Hardware-MPU aktiv).
  1. Task-Aktivierung im Application Cluster:
  • OS High Proxy aktiviert die zugeordneten Tasks OS Task App A bzw. OS Task App B innerhalb ihrer jeweiligen OS-Application-Domäne.
  1. Runnable-Ausführung:
  • OS Task App A führt sequenziell die gemappten Runnables Run1_10ms (SWC A) und Run2_10ms (SWC B) aus.
  • OS Task App B führt Run3_10ms (SWC C) aus.
  1. Partitionsübergreifende Datenflüsse:
  • Datenübertragungen zwischen OsApp.A und OsApp.B innerhalb des Application Clusters werden über den leichtgewichtigen Local IOC abgewickelt, wodurch Roundtrips über den Host-Kernel vermieden werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Anforderungsbezug:
  • SRS_SwCluC_00204: Anforderung zur Entkopplung und Ausführung von OS-Funktionalitäten über Software-Cluster-Grenzen.
  • SWS_SwCluC_02200 & SWS_SwCluC_02201: Definition der Proxy-Architektur (OS High Proxy, OS Low Proxy) zur Kapselung des OS-Schedulings und Gewährleistung binärer Unabhängigkeit.
  • Konfigurations- und Integrationsanforderungen:
  • Manifest-Generierung: Das Binary Manifest muss während des Host-Builds statisch exponiert und im Application-Cluster-Build als Linker-Input (Jump-Table / ABI-Interface) eingebunden werden.
  • Task-Mapping-Restriktionen: Anwendungs-Runnables dürfen nicht direkt auf Host-OS-Ressourcen oder Host-spezifische Basic Tasks gemappt werden. Jede anwendungsseitige OS-Application benötigt korrespondierende Proxy-Task-Konfigurationen.
  • Latenz- & Jitter-Budgetierung: Der Kaskadenschritt Host Task $\rightarrow$ Dispatcher Task $\rightarrow$ High Proxy $\rightarrow$ Application Task fügt Kontextwechsel-Overhead hinzu. Dies muss im WCET-Budget (Worst-Case Execution Time) für harte Echtzeit-Runnables (z. B. 10ms) zwingend berücksichtigt werden.
  • Speicherschutz (MPU): Beim Übergang zwischen OsApp.A und OsApp.B greift im Application Cluster der Local IOC; MPU-Berechtigungen müssen so konfiguriert sein, dass der Local IOC-Puffer für beide OS-Applications zugreifbar ist, während der restliche Applikationsspeicher isoliert bleibt.
