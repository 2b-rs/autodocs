1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Metamodell-Klassendiagramm (Ausschnitt aus dem AUTOSAR BSW Module Description Template / BSW Behavior).
  • Technischer Zweck: Formale Beschreibung der partitionsspezifischen Eigenschaften und Interaktionen von BSW-Modul-Entitäten auf Entwurfsebene (vor der ECU-Konfiguration). Es ermöglicht BSW-Autoren, Events, Funktionsaufrufe und Datenzugriffe an abstrakte logische Partitionen (BswDistinguishedPartition) zu binden, um verteiltes BSW-Verhalten (Multi-Partition / Multi-Core) semantisch zu spezifizieren, bevor reale EcucPartitions und Task-Zuordnungen feststehen.

2. Komponenten, Entitäten & Schnittstellen

#### Metaklassen & Generalisierungen

  • BswInternalBehavior (spezialisiert InternalBehavior): Zentraler Wurzel-Container für die Ausführungssemantik und das interne Verhalten eines BSW-Moduls.
  • BswModuleEntity (spezialisiert ExecutableEntity): Ausführbare Code-Einheit des BSW-Moduls (z. B. periodische MainFunction, API-Service, Callback oder Interrupt-Service-Routine).
  • BswEvent (spezialisiert AbstractEvent): Auslöser zur Aktivierung einer BswModuleEntity (z. B. TimingEvent, DataReceivedEvent).
  • BswDistinguishedPartition (spezialisiert Referrable): Abstrakter Platzhalter für eine Partition innerhalb der Modulbeschreibung (BSWMD), der erst bei der ECU-Konfiguration auf eine konkrete Laufzeit-Partition abgebildet wird.
  • BswModuleCallPoint (spezialisiert Referrable): Modelliert den ausgehenden Aufruf einer BSW-C-API bzw. einer anderen Modul-Entität.
  • BswVariableAccess (spezialisiert Referrable): Spezifiziert Lese- oder Schreibzugriffe auf globale Variablen, Kalibrierparameter oder Signale.

#### Kompositionen & Multiplizitäten (ausgehend von BswInternalBehavior)

  • +entity (1..*, Stereotyp «atpVariation»): Aggregiert mindestens eine oder mehrere ausführbare Entitäten.
  • +event (0..*, Stereotyp «atpVariation»): Aggregiert die auslösenden Ereignisse des Moduls.
  • +distinguishedPartition (0..*, Stereotyp «atpVariation»): Deklariert die vom Modul intern unterschiedenen abstrakten Partitionen.

#### Detail-Kompositionen (ausgehend von BswModuleEntity)

  • +callPoint (0..*, Stereotyp «atpVariation»): Funktionsaufrufpunkte zu BswModuleCallPoint.
  • +dataReceivePoint (0..*, Stereotyp «atpVariation»): Eingehende Datenlesepunkte zu BswVariableAccess.
  • +dataSendPoint (0..*, Stereotyp «atpVariation»): Ausgehende Datenschreibpunkte zu BswVariableAccess.

#### Assoziationen zur Partitionsbindung

  • *+contextLimitation (0..)**: Gerichtete Assoziation von BswEvent, BswModuleCallPoint und BswVariableAccess auf BswDistinguishedPartition.
  • Schränkt die Gültigkeit, Triggerung oder Ausführung des jeweiligen Elements strikt auf die Menge der referenzierten abstrakten Partitionen ein.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Metamodell handelt, existiert keine feste Laufzeit-Sequenz. Aus der contextLimitation leitet sich jedoch folgendes dynamisches Laufzeitmuster ab:

  1. Partitions-spezifische Aktivierung:
  • Ein BswEvent feuert zur Laufzeit ausschließlich im Kontext derjenigen Partition(en), die via contextLimitation zugewiesen sind.
  1. Datenfluss & Synchronisationsmechanismen:
  • Besitzt ein dataSendPoint einer Entität eine contextLimitation auf Partition_1 und der korrespondierende dataReceivePoint einer anderen Entität (oder Instanz) eine Limitation auf Partition_2, identifiziert der Generator die Notwendigkeit von Inter-Partition- bzw. Inter-Core-Kommunikation.
  • Der BSW-Generator/die SchM generiert je nach Schnittstelle IPC-Pfade (z. B. OS-IOC, atomare Pufferkopien oder Spinlocks). Liegen beide im selben Partitionskontext, wird direkter Speicherzugriff ohne Locking-Overhead generiert.
  1. Aufrufpfade (Call Points):
  • Ein BswModuleCallPoint beschränkt den API-Aufruf auf die referenzierte Partition. Dies steuert, ob Aufrufe synchron lokal (direkter C-Funktionsaufruf) oder über SchM-/OS-Proxies (Cross-Partition Client-Server) geroutet werden müssen.

4. Normative Relevanz & Entwickler-Hinweise

  • BSWMD-Autoren & Stack-Entwickler:
  • Zur Modellierung von verteilt lauffähigen BSW-Modulen (z. B. verteiltes Com/PduR, Satelliten-Architekturen bei NvM oder Watchdog-Stack) ist zwingend BswDistinguishedPartition einzusetzen.
  • «atpVariation» ermöglicht die variantenabhängige Aktivierung von Entitäten, Events und Zugriffspunkten je nach Multi-Core- oder Single-Core-Derivat via Post-Build- oder Pre-Compile-Variabilitäten.
  • Integratoren & ECU-Konfigurationsphase:
  • Jede im BSWMD deklarierte BswDistinguishedPartition muss im BswM/EcuC-Schritt auf eine reale EcucPartition (und damit auf eine OS-Application / einen Core) gemappt werden.
  • Nicht gemappte oder inkonsistent referenzierte contextLimitation-Einträge führen zu Generierungsfehlern der RTE/SchM, da Speicherlayouts und Scheduling-Tabellen (OS-Tasks) nicht eindeutig aufgelöst werden können.
  • Embedded-C-Entwickler (Reentrancy & Speicherschutz):
  • Entitäten, die für mehrere Partitionen (contextLimitation > 1 oder ohne Einschränkung) deklariert sind, müssen thread-safe und reentrant implementiert sein (keine ungeschützten statischen Modulvariablen).
  • Durch die exakte Deklaration von dataSendPoint/dataReceivePoint wird verhindert, dass der Speicherschutz (MPU/MMU) bei unberechtigtem Partitionsübergriff Traps generiert.

Aus dem Dokument extrahierter Text & Kontext

Begleitender Spezifikationstext:

A more fine grained description of the partition specific behavior of an entity can be described by the use of BswDistinguishedPartitions, as shown in Figure 4. A BswDistinguishedPartition is the abstract representation of a partition, which allows to the mapping of a specific BswEvent, BswModuleCallPoint or BswVariableAccess to a set of abstract partitions. The representation of a partition at this point is an abstract one in the sense that it is part of the BSW module description (according to the module description template), whereas a concrete partition is determined at ECU configuration time. For example, if a module entity running in partition 1 provides data via a VariableDataPrototype to the same entity running in partitions 2 and 3, the BswModuleEntity aggregates a dataSendPoint with a contextLimitiation to partition 1 and a dataSendPoint with a contextLimitation to partitions 2 and 3.
