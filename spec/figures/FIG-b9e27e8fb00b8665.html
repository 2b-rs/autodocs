1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Statisches AUTOSAR-BSW-Schichtenmodell (Layered Architectural Block Diagram) mit Hardware-Mapping.
  • Architektur-Kontext & Zweck: Verortung der zeitgesteuerten CAN-Kommunikation (TTCAN – Time-Triggered CAN nach ISO 11898-4) innerhalb des AUTOSAR Classic Platform Communication Stacks. Es spezifiziert die vertikale und horizontale Einbettung von TTCAN-Erweiterungen in den Standard-CAN-Stack über alle BSW-Ebenen bis hin zur Hardware-Anbindung (on-chip vs. off-chip Controller via SPI).

2. Komponenten, Entitäten & Schnittstellen

Schichten- und Modul-Gliederung (von oben nach unten)
  • Communication Services (Dienstschicht):
    • Generische/Protokollunabhängige BSW-Module:
      • AUTOSAR COM: Signalbasierte Interaktion mit dem RTE.
      • IPDU Multiplexer (IpduM): Dynamisches Multiplexen von I-PDUs.
      • Diagnostic Com. Manager (Dcm): Diagnosekommunikation (UDS/OBD).
      • Debugging: Trace- und Debug-Hooks für Kommunikationsabläufe.
      • PDU Router (PduR): Zentrales Gateway und Routing von I-PDUs zwischen oberen Modulen (COM, Dcm) und unteren Transportprotokollen bzw. Interfaces.
      • Generic NM Interface (Nm): Busunabhängige Abstraktion des Netzwerkmanagements.
    • CAN-spezifische Services:
      • CAN Transport Protocol (CanTp): Segmentierung/Reassemblierung (ISO 15765-2) für Diagnose- und Langdatenübertragung.
      • CAN State Manager (CanSM): Zustandsverwaltung (Modi: NoCom, SilentCom, FullCom) und Bus-Off-Handling.
      • CAN NM (CanNm): Periodisches OSEK/AUTOSAR-Netzwerkmanagement auf dem CAN-Bus.
  • Communication Hardware Abstraction (Hardware-Abstraktionsschicht):
    • CAN Interface (CanIf): Zentrale Abstraktion aller CAN-Controller.
      • TTCAN-Erweiterung: Integriertes, gestrichelt markiertes Teilmodul TTCAN (TtcanIf) zur Handhabung von Synchronisationsbotschaften, Time-Marks, Matrix-Umschaltungen und zeitgesteuerten Triggern.
    • CAN Transceiver Driver (CanTrcv): Ansteuerung des physischen Bus-Transceivers.
    • Driver for ext. CAN ASIC: Abstraktionstreiber für externe (nicht-on-chip) CAN-/TTCAN-Controller.
  • Microcontroller Abstraction Layer – MCAL (Treiberschicht):
    • I/O Drivers: DIO Driver (digitale Pins, z. B. für Transceiver-Enable/Wakeup).
    • Communication Drivers:
      • SPIHandler Driver (Spi): Serielle Busschicht zur Anbindung externer Kommunikationsbausteine.
      • CAN Driver (Can): Low-Level-Treiber mit registerbasierter Hardwareansteuerung.
      • TTCAN-Erweiterung: Gestricheltes Teilmodul TTCAN (TtcanDrv) zur Konfiguration der TTCAN-Hardware (z. B. Basic Cycles, Trigger Memory, Local Time, Global Time Base).
  • Microcontroller (& Hardware):
    • On-Chip Peripherie: SPI-Controller sowie integrierter TTCAN-Hardware-Controller.
    • Externe Hardware: External TTCAN Controller, angebunden über SPI an den Mikrocontroller.
Beziehungen & Schnittstellenpfade
  • Datapfad (Standard CAN vs. TTCAN):
    • COM/Dcm → PduR → CanIf → Can Driver → on-chip TTCAN.
    • Über PduR können I-PDUs zeitbasiert an CanIf übergeben werden; TtcanIf steuert die Zuordnung zu exakten Zeitfenstern (Exclusive/Arbitrating Time Windows).
  • Externer Controller-Pfad:
    • CanIf → Driver for ext. CAN ASIC → SPIHandler Driver → on-chip SPI → External TTCAN Controller.
  • Management- & Kontrollpfad:
    • CanSM kontrolliert CanIf, welches wiederum Can Driver und CanTrcv steuert.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Synchronisation (Start-up):
    • Der Can Driver initialisiert die Trigger-Listen, das Capture-Register und den lokalen Timer des TTCAN-Controllers.
    • TtcanIf wartet auf Reference Messages (Synchronisations-Master) zur Synchronisation des Basic Cycle und der Matrix (Phase: Synchronizing → In_Gap / In_Schedule).
  2. Sendeablauf (Zeitfenster-gesteuert):
    • Transmit Trigger: Erreicht der Controller den definierten Zeitstempel im Basic Cycle, wird der Sendepuffer asynchron durch Hardware-Interrupt ausgelöst.
    • Bestätigung: Hardware-Interrupt → Can_Isr → CanIf_TxConfirmation() / TtcanIf-Event-Callback → Rückmeldung an PduR/COM.
  3. Empfangsablauf:
    • RX-Interrupt bei Match des Time Windows / Identifier → Can_Isr liest Hardware-Mailbox → CanIf_RxIndication() → PduR → COM/Dcm.
  4. Fehler- und Statusüberwachung:
    • Abweichungen in der Synchronisation (Clock Drift, verpasste Reference Messages) oder Bus-Offs werden via Dem_SetEventStatus() an das Dem gemeldet.
    • Modul-Inkonsistenzen (z. B. Trigger vor Initialisierung) triggern synchrone Det_ReportError()-Aufrufe.

4. Normative Relevanz & Entwickler-Hinweise

  • Dual-Stack-Integration & Koexistenz: TTCAN ist in AUTOSAR kein komplett isolierter Stack, sondern eine funktionale Erweiterung von CanIf und Can Driver. Entwickler müssen sicherstellen, dass Standard-CAN-Frames (Event-driven, arbitrierend) und TTCAN-Frames (Time-triggered, kollisionsfrei) in denselben Modulen koexistieren können.
  • Controller-Heterogenität (Internal vs. External):
    • Für On-Chip-TTCAN läuft der Datenaustausch direkt über Memory-Mapped I/O (MMIO).
    • Für externe TTCAN-ASICs erfordert die Anbindung über den Spi-Treiber asynchrone Queues und SPI-Sequenzen (Spi_AsyncTransmit), was Latenzen einführt, die bei der Parametrierung der TTCAN-Zeitfenster (Window Width, Transmission Latency) berücksichtigt werden müssen.
  • Konfigurationsaspekte (CanIf / Can):
    • Parameter wie CanIfTTCANEnable und controller-spezifische TTCAN-Parameter (Trigger-Tabellen, Tx/Rx-Trigger-Typen, Global Time Drift Limits) müssen exakt mit dem physikalischen Bus-Schedule (Fibex-/ARXML-Clusterkonfiguration) übereinstimmen.
    • PDU-Router- und COM-Konfigurationen müssen deterministic routing gewährleisten; PDU-Längen und Transmit-Trigger müssen jitterfrei bereitgestellt werden.
