1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Serialisierungs- und On-the-Wire-Binary-Payload-Layout (Netzwerk-Byte-Stream-Definition).
  • Architektur-Kontext:
    • Protokollebene: AUTOSAR Foundation (AUTOSAR_FO_PRS_SOMEIPProtocol), Serialisierungsschicht für Service-Oriented Middleware.
    • Systemeinordnung:
      • AUTOSAR Classic Platform (CP): Datentyp-Transformator SomeIpXf (SOME/IP Transformer) serialisiert komplexe Datentypen (Std_Type / ImplementationDataType) aus dem RTE/COM-Puffer in SOME/IP-PDUs zur Übergabe an SoAd (Socket Adaptor).
      • AUTOSAR Adaptive Platform (AP): Datentypserialisierung innerhalb des Kommunikations-Subsystems (ara::com) für IPC und Ethernet-Binding.
    • Technischer Zweck: Festlegung der Drahtformat-Semantik für mehrdimensionale Arrays dynamischer Länge mit hierarchischen Längenfeldern zur eindeutigen Deserialisierbarkeit variabler Datenstrukturen ohne festes Adressraster.

2. Komponenten, Entitäten & Schnittstellen

  • Äußeres Längenfeld (Length n):
    • Typ: Unsigned Integer, im Diagramm als 32-Bit-Feld dargestellt (Standardgröße; konfigurierbar über AUTOSAR-ARXML-Parameter lengthFieldSize auf 8, 16 oder 32 Bit).
    • Semantik: Definiert die Gesamtanzahl der verbleibenden Bytes (n) des gesamten mehrdimensionalen Arrays. Es schließt sich selbst nicht mit ein.
  • Sub-Array-Instanzen (Element_a[i]):
    • Mehrdimensionale Container (Element_a[1], Element_a[2], ...).
    • Jedes Sub-Array fungiert als autonome eindimensionale Slice/Dimension innerhalb des übergeordneten Arrays.
    • Unterstützt „Jagged/Ragged Arrays“: Jedes Sub-Array kann eine variable Elementanzahl besitzen (k_1 ≠ k_2).
  • Inneres Längenfeld (L_i / Sub-Array-Längenfeld):
    • Breite: Im Diagramm spezifiziert mit 32 Bit je Dimensionsebene.
    • Semantik: Repräsentiert die exakte Byte-Länge (L_1, L_2) ausschließlich der Nutzdaten/Elemente des jeweiligen Sub-Arrays (E_i,1 … E_i,k_i).
  • Array-Nutzdatenelemente (E_i,j):
    • Einzelne serialisierte Primitive oder komplexe Datenelemente innerhalb der Sub-Arrays.
    • Hinweis zum Spezifikationsfehler: Im Schaubild sind die Elemente von Element_a[2] irrtümlich mit E1,1, E1,2 ... E1,k_2 statt mit E2,1, E2,2 ... E2,k_2 indiziert; semantisch handelt es sich um die Elemente der zweiten Dimension.
  • Kardinalitäten & Beziehungen:
    • Outer Array : Inner Sub-Array → 1 : [0 … M]
    • Inner Sub-Array : Array-Elemente → 1 : [0 … K_i]
    • Die Längenrelation gehorcht: $n = \sum_{i=1}^{M} (\text{sizeof}(\text{LengthField}_{L_i}) + L_i)$.

3. Dynamisches Verhalten & Sequenzablauf

Da die Dimensionen dynamisch variieren, ist kein direkter Index-Zugriff O(1) möglich; die Deserialisierung erfolgt strikt linear stream-basiert:

  1. Outer-Header-Evaluation:
    • Empfang des 32-Bit-Werts n.
    • Konsistenzprüfung: Verbleibende PDU-Restlänge ≥ n; Pufferüberlauf- und Validitätscheck.
  2. Sub-Array-Parsing (Schleife über n Bytes):
    • Dekodieren des 32-Bit-Sub-Längenfelds L_i.
    • Validierung: sizeof(L_i) + L_i ≤ verbleibendes n.
    • Lineares Einlesen von L_i Bytes für die Elemente E_i,1 bis E_i,k_i.
      • Falls Elemente statische Größe besitzen: Elementanzahl k_i = L_i / sizeof(E).
      • Falls Elemente dynamische Datentypen sind (z. B. Strings oder Sub-Sub-Arrays): Rekursives Weiterschreiten im Bytestream.
    • Dekrementierung des Outer-Restbudgets: n ← n - (sizeof(L_i) + L_i).
  3. Abbruch- und Fehlerbedingungen:
    • Malformed Message (Return Code 0x07): Wenn das verbleibende n nach dem Verarbeiten eines Sub-Arrays negativ wird oder nicht exakt bei 0 terminiert.
    • Length Mismatch: Wenn L_i die Grenzen von n oder der Gesamt-PDU überschreitet.
    • Auslösen der Det-Meldung (CP: SOMEIPXF_E_MALFORMED_MESSAGE) bzw. Verwerfen der Deserialisierung mit Rückgabe eines ara::core::ErrorCode (AP).

4. Normative Relevanz & Entwickler-Hinweise

  • SWS-Anforderungen:
    • [PRS_SOMEIP_00114] (basierend auf RS_SOMEIP_00037): Jedes Sub-Array einer Dimension muss zwingend ein eigenes Längenfeld besitzen. Flache Längenfelder für mehrdimensionale dynamische Arrays sind normativ verboten.
  • Konfiguration (ARXML / Data Types):
    • Konfiguration via ArraySizeHandling bzw. Definition von ArrayValueSpecification.
    • Das Attribut lengthFieldSize der jeweiligen Array-Ebene bestimmt die Bitbreite auf dem Draht (8, 16 oder 32 Bit). Wenn nicht explizit anders modelliert, gilt die im Protokoll definierte Default-Größe (wie im Diagramm: 32 Bit / 4 Bytes).
  • Speichermanagement & Allokations-Strategie:
    • Classic AUTOSAR (SomeIpXf): Dynamische Arrays variabler Sub-Dimension erfordern statisch dimensionierte Puffer für die Maximalgröße (maximumArrayLength im BSW-Modell). Entwickler müssen den Stack auf Worst-Case-PDU-Größen auslegen, um Stack-/Heap-Überläufe zu verhindern.
    • Adaptive AUTOSAR (ara::com): Abbildung typischerweise auf std::vector<std::vector<T>>. Parsing erfordert dynamische Heap-Allokationen; bei harter Echtzeitfähigkeit müssen Puffer vorallokiert oder Custom-Pool-Allokatoren genutzt werden.
  • Overhead & Performance:
    • Jedes Sub-Array generiert einen Protokoll-Overhead von 4 Bytes (bei 32-Bit-Längenfeldern).
    • Lineare Deserialisierungskomplexität O(N) mit variabler CPU-Laufzeit (WCET-relevant) – ungeeignet für zyklische, hochfrequente Determinismus-Signale.
