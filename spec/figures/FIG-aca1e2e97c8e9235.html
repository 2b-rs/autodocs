3. Dynamisches Verhalten & Sequenzablauf

Die Methodologie beschreibt eine iterative, phasenorientierte Vorgehensweise:

  1. Phase 1: Datentyp-Modellierung:
  • Ausführung von Define Datatypes for the Adaptive Platform.
  • Festlegung von Basis- und Verbundtypen, Wertebereichen und Serialisierungseigenschaften.
  1. Phase 2: Service-Interface-Synthese:
  • Define Service Interface konsumiert die Datentypen («input»).
  • Modellierung von Methoden (In/Out-Argumente), Events (Notification-Typen) und Fields (Getter/Setter/Notifier).
  • Generierung/Update des primären Deliverables Service Interface Description.
  1. Phase 3: Optionale Buslast-Optimierung (Branching):
  • Bedingung/Trigger: Hohe Netzwerkauslastung oder feingranulare Services erfordern Aggregation.
  • Aktion: Aggregate Service Interfaces for reducing the bus load fasst Schnittstellen zusammen, erzeugt Service Interface Mapping und aktualisiert Service Interface Description.
  1. Phase 4: Konsumierende Folgeprozesse (Parallel/Nachgelagert):
  • Übergabe der freigegebenen Service Interface Description als unmodifizierbaren «input» an:
  • Instance-Deployment (Define provided and required service instances zur Bindung an SOME/IP Service IDs, Instance IDs, Eventgroups).
  • Signal-Translation (Define Signal to Service Translation für Gateway-PDU/Signal-Mappings).
  • Applikationszuweisung (Define Interaction with Applications).

4. Normative Relevanz & Entwickler-Hinweise

  • C++ API-Vertrag (ara::com):
  • Die Service Interface Description ist die normative Eingangsdatei für den Adaptive-Platform-Codegenerator. Sie bestimmt direkt die Generierung der typisierten C++ Skeleton- und Proxy-Klassen (<Service>Proxy.h, <Service>Skeleton.h).
  • Serialisierungs- & Typkonsistenz:
  • Fehler oder Unvollständigkeiten im Deliverable Datatypes for the Adaptive Platform führen zum Scheitern der Codegenerierung oder zu inkompatiblen SOME/IP-Serialisierern (Payload-Alignment, Endianness, Struct-Packing).
  • Auswirkung von Schnittstellen-Aggregationen:
  • Wird Aggregate Service Interfaces for reducing the bus load genutzt, müssen Entwickler das generierte Service Interface Mapping im Deployment berücksichtigen; Proxy-/Skeleton-Instanzen operieren auf der aggregierten Schnittstelle, was Auswirkungen auf Threading, Dispatching und Cache-Lokalität im Adaptive-Stack hat.
  • Signal-to-Service Gatewaying:
  • Für Gateway-Entwickler (Classic $\leftrightarrow$ Adaptive) ist die unveränderte Service Interface Description verbindlich: Signal-Definitionen (z. B. aus FIBEX/CAN-ARXML) müssen über CompuMethods und Skalierungsregeln deckungsgleich auf die definierten Service-Events/Fields abgebildet werden.
