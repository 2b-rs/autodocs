1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Layout / Wire-Format (Bit- und Byte-genaue Serialisierungsstruktur nach RFC-Stil mit 32-Bit-Rasterung und Network Byte Order / Big-Endian).
  • Technischer Zweck: Spezifikation des binären Übertragungsformats der IPv6 SD Endpoint Option (Type 0x26) innerhalb des SOME/IP Service Discovery Protokolls (AUTOSAR_FO_PRS_SOMEIPServiceDiscoveryProtocol).
  • Funktionale Einordnung: Die Option wird im Options Array einer SOME/IP-SD-PDU transportiert. Sie dient dazu, dedizierte IPv6-Adressierungsdaten (IP-Adresse, L4-Protokoll und Port) explizit für den SD-Kanal bzw. die Dienst-Endpunkte zu annoncieren (Unicast SD Endpoint), wenn diese von den Standard-Sockets oder Multicast-Vorgaben abweichen oder für Unicast-Antworten (z. B. bei FindService- oder OfferService-Entries) referenziert werden.

2. Komponenten, Entitäten & Schnittstellen

Das Schaubild definiert ein zusammenhängendes 24-Byte-Datenelement (192 Bits) mit folgender Feldstruktur:

| Bit-Offset | Feldname | Größe | Fester/Erwarteter Wert | Semantik / Normative Vorgabe |

| :--- | :--- | :--- | :--- | :--- |

| 0 – 15 | Length | 16 Bit | 0x0015 (21 Dezimal) | Länge der Option in Bytes, beginnend direkt nach dem Type-Feld (umfasst Disc. Flag, alle Reserved-Felder, IPv6-Address, L4-Proto und Port Number). |

  • Beziehungen & Kardinalitäten:
  • Wird von SD-Entries (Entry Array) über den Index 1st Option oder Index 2nd Option referenziert.
  • Kardinalität zum SD-Header: $0..n$ im Options-Array.
  • Covered by Length (incl. Reserved): Schließt exakt 21 Bytes ein ($1\text{ Byte [Flag+Reserved]} + 16\text{ Byte [IPv6]} + 1\text{ Byte [Reserved]} + 1\text{ Byte [L4-Proto]} + 2\text{ Byte [Port]} = 21\text{ Bytes} = \mathtt{0x0015}$). Die Felder Length (2 Bytes) und Type (1 Byte) sind nicht in der Längenberechnung enthalten.

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger & Serialisierung (Sender - BswM / Sd / SoAd):
  • Beim Übergang einer Server-Instanz in den Zustand Offer oder eines Clients in Find/Subscribe serialisiert das BSW-Modul Sd (bzw. der Adaptive SOME/IP-Daemon) den Header, die Entries und hängt die Endpoint-Option an.
  • Setzen von Length = 0x0015, Type = 0x26, Disc. Flag = 0, Einfügen der lokalen IPv6-Adresse (aus TcpIp-Stack bezogen) sowie des konfigurierten UDP-SD-Ports (Default: 30490).
  1. Parsing & Validierung (Empfänger - Sd-Stack):
  • Prüfung von Type == 0x26.
  • Prüfung von Length == 0x0015: Weicht die Länge ab, ist die Option ungültig und die PDU wird je nach Release/Konfiguration verworfen bzw. der Entry ignoriert (Fehlermeldung via Det_ReportError/Dem).
  • Prüfung von Disc. Flag == 0: Falls eine Entität diesen Typ nicht verarbeiten kann, darf die Option nicht ignoriert werden (im Gegensatz zu Disc. Flag = 1).
  • Prüfung L4-Proto: Überprüfung auf zulässiges Protokoll (0x11 für UDP).
  • Extraktion der IPv6-Adresse und Portnummer zur dynamischen Bindung des Remote-Sockets in SoAd/TcpIp.
  1. Abbruch-/Fehlerbedingungen:
  • Ungültiges L4-Proto (z. B. TCP 0x06 für SD-Endpoint, falls Stack nur UDP-SD unterstützt): Abweisung der Option.
  • Adress-Sanity: Erkennung unzulässiger Adressen (z. B. Multicast-Adresse in Unicast-Endpoint-Feldern) führt zur Verwerfung der Option.

4. Normative Relevanz & Entwickler-Hinweise

  • Classic Platform (Sd, SoAd, TcpIp):
  • Konfiguration (SdInstance): Bei Konfiguration von IPv6-Netzwerken muss SdIPv6AddressRef auf die entsprechende TcpIpLocalAddr verweisen.
  • Memory Alignment & Zero-Copy: Durch die 128-Bit-Adresse und die asymmetrische 24-Byte-Gesamtgröße der Option erfordert der Deserializer im BSW-Treiber Byte-Zugriff (uint8-Pointer-Arithmetik) oder gepackte Strukturen (#pragma pack(1)), um Bus-Faults auf 32-Bit/64-Bit-Mikrocontrollern (z. B. ARM Cortex-M/R, TriCore) durch unaligned Access zu verhindern.
  • Big-Endian / Network Byte Order: Felder mit mehr als 8 Bit (Length, Port Number, IPv6-Address) müssen zwingend in Big-Endian übertragen und bei Bedarf via Makros (HTONS, NTOHS) konvertiert werden.
  • Adaptive Platform (ara::com / Communication Management):
  • Daemon-Implementierungen müssen Endpoint-Optionen 0x26 parsen, um Service-Instances dynamisch den Socket-Bindings zuzuordnen.
  • Abgrenzung zu Type 0x06 und 0x16:
  • Type 0x06: IPv6 Endpoint Option (für reguläre Service-Datenübertragung Unicast).
  • Type 0x16: IPv6 Multicast Option (für Eventgroups).
  • Type 0x26: IPv6 SD Endpoint Option (spezifisch für den Signalisierungs- und Control-Endpoint von Service Discovery Instanzen).
