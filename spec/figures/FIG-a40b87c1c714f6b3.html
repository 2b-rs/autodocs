1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration (ECUC) Metamodell-Ausschnitt / UML-Klassendiagramm zur Definition des Konfigurationsschemas (EcucParamConfContainerDef).
  • Architektur-Kontext: Das Diagramm spezifiziert die Konfigurationshierarchie des ECU State Manager (EcuM) innerhalb der AUTOSAR Classic Platform (System Services). Es definiert die statischen und post-build-relevanten Parameterstrukturen unterhalb von EcuMConfiguration für Initialisierungssequenzen (Init Lists vor und nach OS-Start), Shutdown-Ziele, Sleep-Modi, Wakeup-Quellen sowie Verweise auf OS-Objekte (OsAppMode, OsResource).

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Container-Hierarchie

  • EcuMConfiguration (EcucParamConfContainerDef, [1..1]):
  • Wurzelcontainer der Modulkonfiguration.
  • Hält per Komposition (+subContainer) genau eine Instanz von EcuMCommonConfiguration.
  • EcuMCommonConfiguration (EcucParamConfContainerDef, [1..1]):
  • Zentraler Container für BSWM/OS-übergreifende Basiseinstellungen des EcuM.
  • Aggregiert folgende Parameter, Sub-Container und Referenzen:
  • EcuMConfigConsistencyHash (EcucIntegerParamDef, [0..1], +parameter): Integer-Wert zur Laufzeitprüfung der Konsistenz zwischen Pre-Compile- und Post-Build-Konfigurationsstrukturen.
  • EcuMIgnoreWakeupEvValOffPreOS (EcucBooleanParamDef, [1..1], defaultValue = false, +parameter): Steuert, ob die Validierung von Wakeup-Ereignissen in den Phasen OFF bzw. vor dem OS-Start übersprungen werden soll.
  • EcuMDefaultAppMode (EcucReferenceDef, [1..1], +reference): Verweis (+destination) auf den beim Booten an StartOS() zu übergebenden OS-Applikationsmodus OsAppMode ([1..*]).
  • EcuMDefaultShutdownTarget (EcucParamConfContainerDef, [1..1], +subContainer): Definiert den voreingestellten Shutdown-Zielzustand (z. B. ECUM_STATE_SLEEP, ECUM_STATE_RESET, ECUM_STATE_OFF).
  • EcuMWakeupSource (EcucParamConfContainerDef, [1..32], +subContainer): Konfiguriert die hardware- und softwareseitigen Wakeup-Quellen. Kardinalität begrenzt auf max. 32 (korrespondierend zum 32-Bit-Maskentyp EcuM_WakeupSourceType).
  • EcuMSleepMode (EcucParamConfContainerDef, [1..256], +subContainer): Konfiguration der Low-Power-Zustände der ECU (Zuordnung von Clock-Frequenzen, Wakeup-Masken, MCU-Modi).
  • EcuMOSResource (EcucReferenceDef, [1..], +reference): Verweis (+destination) auf vom EcuM genutzte OS-Ressourcen OsResource ([0..]) zur Synchronisation / exklusiven Ausführung.

#### Treiber-Initialisierungslisten

  • EcuMDriverInitListZero (EcucParamConfContainerDef, [0..1], +subContainer):
  • Initialisierungsliste für Treiber vor dem OS-Start, die keinen Post-Build-Konfigurationszeiger benötigen (deterministische Low-Level-Inits, z. B. Det, Dem-PreInit, Mcu).
  • EcuMDriverInitListOne (EcucParamConfContainerDef, [0..1], +subContainer):
  • Initialisierungsliste für Treiber vor dem OS-Start nach Verfügbarkeit der Post-Build-Daten (EcuM_Init()), jedoch vor StartOS().
  • EcuMDriverRestartList (EcucParamConfContainerDef, [0..1], +subContainer):
  • Re-Initialisierungsliste für Treiber beim Aufwachen aus Sleep-Modi ohne Power-Down/Reset.
  • EcuMDriverInitItem (EcucParamConfContainerDef, [1..*], requiresIndex = true):
  • Kindelement aller drei Initialisierungslisten (EcuMDriverInitListZero, EcuMDriverInitListOne, EcuMDriverRestartList).
  • requiresIndex = true erzwingt eine strikte sequenzielle Ausführungsreihenfolge der Treiber-Aufrufe (Funktionszeiger / Call-Stubs).

3. Dynamisches Verhalten & Sequenzablauf

Obgleich es sich um ein statisches ECUC-Metamodell handelt, kodiert das Schema deterministische Laufzeitabläufe:

```

[Power-On / Reset]

│

▼

EcuM_Init() Phase 0 ──────► Sequenzielle Abarbeitung von EcuMDriverInitListZero

│ (EcuMDriverInitItem[0..n] via requiresIndex)

▼

Post-Build Consistency Check ──► Auswertung EcuMConfigConsistencyHash

│

▼

EcuM_Init() Phase 1 ──────► Sequenzielle Abarbeitung von EcuMDriverInitListOne

│ (EcuMDriverInitItem[0..n] via requiresIndex)

▼

StartOS(EcuMDefaultAppMode)

│

├───────────────────► Shutdown / Sleep: EcuMDefaultShutdownTarget, EcuMSleepMode

│

▼

Wakeup-Ereignis (EcuMWakeupSource [Bitmaske 0..31])

│

▼

Wakeup Restart Sequenz ───► Sequenzielle Abarbeitung von EcuMDriverRestartList

(EcuMDriverInitItem[0..n])

```

  • Fehlerpfade: Divergiert EcuMConfigConsistencyHash zwischen ROM-Image und Post-Build-Struktur, bricht die Phase-1-Initialisierung ab (DET-Meldung ECUM_E_CONFIGURATION bzw. Verbleib im abgesicherten Zustand / Reset).

4. Normative Relevanz & Entwickler-Hinweise

  • Kardinalitätsgrenzen & Bitmasken-Mapping:
  • EcuMWakeupSource ist auf maximal 32 Instanzen beschränkt ([1..32]). Entwickler müssen beachten, dass jede Wakeup-Quelle direkt auf ein einzelnes Bit im Bitfeld EcuM_WakeupSourceType (uint32) abgebildet wird. Eine Überschreitung ist modellseitig unzulässig.
  • EcuMSleepMode ist auf maximal 256 Einträge begrenzt ([1..256]), passend zum Datentyp EcuM_ShutdownModeType (uint8).
  • Indizierung (requiresIndex = true):
  • Bei EcuMDriverInitItem generiert der BSWM/ECUC-Generator ein Array von Funktionszeigern. Die Reihenfolge in der XML/ARXML-Konfiguration bestimmt hart die Initialisierungsreihenfolge hardwarenaher BSW-Module. Fehlende Indizes führen zu Validierungsfehlern im Konfigurationswerkzeug.
  • Cross-Core / OS-Bindung:
  • Die Referenzen EcuMDefaultAppMode und EcuMOSResource etablieren eine strikte semantische Abhängigkeit zum OS-Modul (Os). Der konfigurierte AppMode muss im OS-Container OsAppMode existieren; StartOS() wird normativ genau mit diesem Modus aufgerufen.
  • Wakeup-Validierung Pre-OS (EcuMIgnoreWakeupEvValOffPreOS):
  • Der mit R21-11 neu eingeführte Parameter ([1..1], Default false) erlaubt es, das Validierungsprotokoll für Wakeup-Ereignisse, die im Zustand OFF bzw. vor StartOS() eintreffen, gezielt zu übergehen, um Boot- und Aufwachzeiten zu optimieren.
  • Release-Besonderheit (R21-11):
  • EcuM wird im Zusammenspiel mit dem BswM betrieben. EcuMDriverInitListOne und EcuMDriverRestartList können je nach gewähltem BswM/EcuM-Partitionsmodell (Fixed vs. Flexible) teilweise durch BswM-Aktionslisten ersetzt oder orchestriert werden; im EcuM-Metamodell verbleiben sie jedoch für die Low-Level-Initialisierung erhalten.
