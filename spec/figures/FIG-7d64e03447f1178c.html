1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (AUTOSAR M2-Metamodell-Ausschnitt).
  • Technischer Zweck & Einordnung: Spezifikation der Konfigurationsstrukturen für SOME/IP Service Discovery (SOME/IP-SD) im Machine Manifest der AUTOSAR Adaptive Platform (Release R17-03 / R1.1.0). Das Metamodell verankert die maschinenweiten SOME/IP-SD-Kommunikationsparameter (Port und Multicast-IP-Endpunkt) an der physischen Netzwerktopologie (EthernetPhysicalChannel).

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Stereotypen
  • Machine (Spezialisierung von ARElement, AtpStructureElement):
    • Repräsentiert die logische/physische Recheneinheit (Host/SOC) innerhalb der Adaptive Platform.
    • Aggregiert maschinenweite Konfigurationen.
  • ServiceDiscoveryConfiguration (Abstrakte Klasse):
    • Basisklasse für technologiespezifische Service-Discovery-Mechanismen auf Maschinenebene.
  • SomeipServiceDiscovery (Spezialisierung von ServiceDiscoveryConfiguration):
    • Konkrete Ausprägung für SOME/IP Service Discovery.
    • Attribut: someipServiceDiscoveryPort : PositiveInteger – Spezifiziert den UDP-Port für SOME/IP-SD-Nachrichten (standardmäßig IANA/AUTOSAR UDP 30490).
  • EthernetPhysicalChannel (Spezialisierung von PhysicalChannel):
    • Modelliert das physische Ethernet-Kommunikationscluster/-segment.
  • NetworkEndpoint (Spezialisierung von Identifiable):
    • Definiert eine logische Netzweradresse (IPv4/IPv6) inklusive Transportparameter auf dem physikalischen Kanal.
    • Attribute:
      • fullyQualifiedDomainName : String [0..1] – Optionaler FQDN für DNS-basierte Adressauflösung.
      • priority : PositiveInteger [0..1] – Optionale Prioritätssteuerung für Traffic-Klassen / VLAN-QoS.
Assoziationen & Kardinalitäten
  • Machine $\blacklozenge\xrightarrow{\text{+serviceDiscoverConfig}}$ ServiceDiscoveryConfiguration (0..*):
    • Strenge Komposition. Eine Machine kann mehrere SD-Konfigurationen parallel halten (z. B. für getrennte Netzwerksegmente).
  • SomeipServiceDiscovery $\longrightarrow\xrightarrow{\text{+multicastSdIpAddress}}$ NetworkEndpoint (0..1):
    • Gerichtete Referenz auf denjenigen NetworkEndpoint, der die Multicast-IP-Adresse für SOME/IP-SD-Broadcasts/Multicasts bereitstellt (z. B. IPv4 224.244.224.245 oder IPv6 FF02::...).
  • EthernetPhysicalChannel $\blacklozenge\xrightarrow{\text{+networkEndpoint}}$ NetworkEndpoint (0..*):
    • Komposition mit Stereotyp «atpSplitable»: Erlaubt die Verteilung und Definition einzelner Endpunkte über mehrere ARXML-Dateien/Autorenteams hinweg (Modularisierung der Netzwerkbeschreibung).

3. Dynamisches Verhalten & Laufzeit-Semantik

Das Klassendiagramm ist strukturell (statisches Metamodell). Die daraus generierten ARXML-Manifeste steuern zur Laufzeit die Initialisierungsphase des SOME/IP-Daemons bzw. des Communication Management (ara::com):

  1. Stack-Initialisierung: Beim Booten der Machine liest der SOME/IP-SD-Daemon die Manifest-Parameter (SomeipServiceDiscovery).
  2. Socket-Allokation: Bindung eines UDP-Sockets an someipServiceDiscoveryPort über die Netzwerkkarte, die dem übergeordneten EthernetPhysicalChannel zugeordnet ist.
  3. Multicast-Join: Beitritt zur Multicast-Gruppe der IP-Adresse aus multicastSdIpAddress via IGMP (IPv4) bzw. MLD (IPv6).
  4. SD-Protokollphasen:
    • Initial Delay Phase / Repetition Phase: Versenden initialer OfferService- bzw. FindService-Nachrichten an die referenzierte Multicast-IP und den Port.
    • Main Phase: Zyklischer Austausch von Heartbeat-Offers und dynamische Verarbeitung von SubscribeEventgroup-Nachrichten via Unicast/Multicast.

4. Normative Relevanz & Entwickler-Hinweise

  • Manifest-Modellierung (TPS_MANI_03064, RS_MANI_00019):
    • Ohne Instanziierung von SomeipServiceDiscovery und Referenzierung eines gültigen Multicast-NetworkEndpoint kann der Adaptive Stack auf diesem Ethernet-Interface keine dynamische Dienstsuche anbieten oder konsumieren (SOME/IP-SD deaktiviert).
  • Netzwerk- & POSIX-Stack-Konfiguration:
    • Der Socket-Layer des Adaptive-Betriebssystems (z. B. Linux/QNX) muss sicherstellen, dass Multicast-Routing für den referenzierten NetworkEndpoint aktiv ist (IP_ADD_MEMBERSHIP).
    • Port-Restriktionen beachten: Falls someipServiceDiscoveryPort im privilegierten Bereich (< 1024) konfiguriert wird, benötigt der SD-Daemon entsprechende Linux Capabilities (CAP_NET_BIND_SERVICE).
  • Multi-Homed Machines:
    • Unterstützt ein System mehrere Ethernet-Kanäle, erfordert jedes Segment eine eigene SomeipServiceDiscovery-Instanz unterhalb derselben Machine mit Zuordnung zum jeweiligen Kanal-NetworkEndpoint.
  • Artop/Validation-Rule: multicastSdIpAddress muss semantisch auf einen NetworkEndpoint zeigen, dessen IP-Adresse im definierten Multicast-Bereich liegt; Unicast-Adressen an dieser Assoziation führen zu Schema-/Validierungsfehlern während der Generierungszeit.
