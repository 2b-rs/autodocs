1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Layered BSW-Architekturdiagramm / Schnittstellenmodell des AUTOSAR Communication Stacks (Schichtenmodell gemäß AUTOSAR Classic BSW Architecture).
  • Technischer Zweck: Darstellung der vertikalen Datenflusspfade (Signal- und PDU-Transformation) sowie der orthogonalen Kontroll- und Managementschnittstellen (Network Management, State Management) über drei AUTOSAR-Basissoftware-Ebenen (Services Layer, Communication HW Abstraction Layer, Communication Drivers / MCAL) zwischen RTE und Bus-Hardware für die Kommunikationssysteme CAN, FlexRay und LIN (Gültigkeit: AUTOSAR R3.0.7, R3.1.5, R3.2.3).

2. Komponenten, Entitäten & Schnittstellen

Schichten & Module (Akteure)
  • RTE (Runtime Environment): Obere Systemgrenze; abstrahiert SWC-Ports auf Signalschnittstellen.
  • Communication Services (Dunkelblau):
    • AUTOSAR COM: Signal-to-PDU-Mapping, Packing/Unpacking, Signal-Filtering, End-to-End-Monitoring (E2E), Übertragungsmodi (Direct, Periodic, Mixed).
    • IPDU Multiplexer (IpduM): Dynamisches Zusammenführen mehrerer I-PDUs in eine Ziel-I-PDU mittels Selector-Bitfeld.
    • DCM (Diagnostic Communication Manager): Diagnoseprotokoll-Abwicklung (UDS, KWP2000, OBD).
    • PDU Router (PduR): Zentrales PDU-Routing; verteilt I-PDUs deterministisch und entkoppelt obere Kommunikationsmodule von Transportschichten und Bus-Interfaces.
    • FlexRay TP (FrTp) / CAN TP (CanTp): Segmentierung, Flusskontrolle (FC), Reassemblierung großer I-PDUs (I-PDU¹) zu transportfähigen N-PDUs.
    • Communication Manager (ComM): Aggregation von Kommunikationsanforderungen der SWCs/BAP; übergeordneter Kommunikationszustand (NoCom, SilentCom, FullCom).
    • FlexRay State Manager (FrSM) / CAN State Manager (CanSM) / LIN State Manager (LinSM): Busspezifische Zustandsmaschinen zur Koordinierung von Controllern und Transceivern.
    • Generic NM Interface / NM Coordinator (Nm): Busunabhängige Abstraktionsschicht und Koordinationsinstanz für teilnetzbasierte/synchrone Busruhe.
    • NM Module (FrNm, CanNm, LinNm): Busspezifische Netzwerkmanagement-Implementierungen.
  • Communication HW Abstraction (Grün):
    • FlexRay Interface (FrIf): Frame- und Cluster-Abstraktion, Triggering, Dynamic/Static Segment Handling.
    • CAN Interface (CanIf): Controller-/Transceiver-Hardwareabstraktion, Tx-/Rx-Pufferung, CAN-ID-Filterung.
    • LIN Interface (incl. LIN TP) (LinIf): Master-Task-Scheduling, Frame-Handling sowie integrierter Transport-Layer (K-Line/LIN-Diagnose).
  • Communication Drivers / MCAL (Rot):
    • FlexRay Driver (Fr): Registerzugriff, Message-RAM-Konfiguration, CC-Synchronisation.
    • CAN Driver (Can): Mailbox-Handling (BasicCAN/FullCAN), Acceptance-Filter, ISR-Management.
    • LIN Low Level Driver (Lin): UART/SCI-Hardwaretreiber, Break-/Sync-Generierung.
PDU-Entitäten & Datenstrukturen
  • Signals: Unformatiertes Anwendungsdatum (SWC/RTE ↔ COM).
  • I-PDU (Interaction Layer PDU): Payload-Container inkl. Update-Bits/Timeout-Überwachung (COM/IpduM/DCM ↔ PduR).
  • I-PDU^1 (TP-gepufferte I-PDU): Nutzdaten-Container für segmentierte Übertragungen (PduR ↔ CanTp/FrTp), erfordert asynchrones Puffer-Management.
  • N-PDU (Network Layer PDU): Segmentierter Transportrahmen inkl. TP-Header (PCI - Protocol Control Information) (CanTp/FrTp ↔ CanIf/FrIf).
  • L-PDU (Data Link Layer PDU): DLC/Payload-Frame direkt bezogen auf Mailbox/Hardware-ID (Interfaces ↔ MCAL).

3. Dynamisches Verhalten & Sequenzablauf

1. Sende- und Empfangspfade (Datenfluss)
  • Unsegmentierter Normalpfad (Signalbasiert):
    • Tx: SWC → RTE (Signal) → AUTOSAR COM (packt Signal in I-PDU) → PduR_Transmit() → CanIf_Transmit() / FrIf_Transmit() (L-PDU) → Can_Write() / Fr_TransmitTxLPdu() (Hardware-Mailbox).
    • Rx: Treiber-ISR → CanIf_RxIndication() → PduR_CanIfRxIndication() → Com_RxIndication() → Signalentpackung → RTE.
  • Segmentierter Pfad (Diagnose / TP-Frames via I-PDU^1):
    • Tx: DCM / COM → PduR_Transmit() → CanTp_Transmit() / FrTp_Transmit().
    • Der TP fordert Datenfragmente blockweise über PduR_ProvideTxBuffer() / PduR_CopyTxData() an.
    • Der TP übergibt die einzelnen Segmente als N-PDU via CanIf_Transmit() / FrIf_Transmit().
    • Rx: Interfaces melden Fragmente via CanTp_RxIndication(). TP allokiert Puffer via PduR_ProvideRxBuffer() / PduR_CopyRxData() im Zielmodul (DCM/COM).
  • Multiplex-Pfad (IpduM):
    • I-PDUs mit dynamischem Layout werden vom PduR in den IpduM geroutet, mit Selektormaske serialisiert und als neue Ziel-I-PDU an den PduR zurückgeführt.
  • LIN-Sonderweg:
    • Da LIN strikt Master-Schedule-getrieben arbeitet, enthält LinIf das Transportprotokoll (LinTp) direkt; die I-PDU/L-PDU-Entkopplung wird zyklisch über Schedule-Tabellen abgearbeitet.
2. Kontroll- und Steuerpfad (State & Network Management)
  • Kommunikationsanforderung: RTE/SWC fordert Modus im ComM an (z. B. COMM_FULL_COMMUNICATION).
  • Zustandssynchronisation: ComM steuert busabhängige Manager (FrSM, CanSM, LinSM) über Kontrollschnittstellen (orange Pfeile).
  • Treibersteuerung: State Manager steuern Betriebsmodi (Wakeup, Sleep, Normal) kaskadierend über CanIf/FrIf/LinIf bis zu den MCAL-Treibern und Transceivern.
  • Netzwerk-Keep-Alive: Nm koordiniert die Busruhe. Periodische NM-PDUs fließen von CanNm/FrNm direkt über das Bus-Interface (CanIf/FrIf) auf den Bus; bei Ausbleiben triggert der Bus-Sleep-Timer.

4. Normative Relevanz & Entwickler-Hinweise

  • Statisches PDU-ID-Mapping: Jedes Modul (Com, PduR, CanTp, CanIf, Can) deklariert eigene PDU-ID-Enums. Das Mapping zwischen oberen und unteren PduIds erfolgt zur Generierungszeit (ECUC / ARXML). Fehlerhafte PduId-Zuordnungen führen zu Fehlroutings oder Null-Pointer-Dereferenzierungen in Lookuptabellen.
  • Zero-Copy vs. Puffer-Allokation:
    • Unsegmentierte Pfade über CanIf/FrIf arbeiten im Sendezweig synchron („Zero-Copy“ per Pointer-Übergabe auf den L-PDU-Buffer).
    • Segmentierte TP-Pfade (CanTp, FrTp) erfordern asynchrones Polling/Callback-Puffermanagement (ProvideTxBuffer/ProvideRxBuffer in AUTOSAR R3.x). Entwickler müssen sicherstellen, dass Puffergrößen im Dcm oder Com für die maximale TP-Payload (bis zu 4095 Bytes bei CAN TP) statisch reserviert sind.
  • Konfigurationsabhängige PduR-Generierung: Der PDU Router besitzt keine dynamische Dispatch-Logik. Abhängig von ARXML-Routing-Tabellen generiert der BSW-Generator direkte Funktionsaufrufe (1:1-Makro/Direct Call) oder Tabellen-Routing (Table-based Routing), um Latenzen zu minimieren.
  • LIN-Sonderbehandlung: Aufgrund des Master-Slave-Prinzips dürfen Treiber-Entwickler für LIN keine autonomen Transmit-Requests absetzen; der Datenfluss ist strikt an den Scheduler des LinIf gebunden.
  • Treiber-Reentrancy & Kontext: APIs der Abstraktionsschicht (CanIf_Transmit) sind in der Regel reentrant bezogen auf unterschiedliche Tx-PDU-IDs, jedoch nicht reentrant für dieselbe PduId. ISRs der MCAL-Treiber dürfen komplexe Entpackungs-Logiken nicht direkt ausführen, sondern delegieren die Bearbeitung an den Polling-Task (Can_MainFunction_Read) oder triggern synchrone Callbacks in CanIf.
