1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Metamodell-Klassendiagramm (AUTOSAR M2-Ebene).
  • Architektur-Kontext: Spezifikation des BSW Module Description Template (BSWMD, R3.0.7).
  • Technischer Zweck: Formale, deklarative Beschreibung des statischen (ROM/RAM) und dynamischen (CPU-Zeit, Stack, Heap) Ressourcenbedarfs von Software-Implementierungen (BswImplementation bzw. SwcImplementation). Dient Authoring- und Integrationswerkzeugen als maschinenlesbare Grundlage für ECU-Dimensionierung, Linker-Skript-Generierung, OS-Task-Stack-Berechnung, WCET-Budgetierung und Schedulability-Analysen.

2. Komponenten, Entitäten & Schnittstellen

  • Implementation (Generalisierung: ARElement):
    • Wurzelentität für die konkrete Code-Ausprägung eines BSW-Moduls oder einer SWC.
    • Aggregiert per Komposition zwingend genau eine Ressourcenbeschreibung: +resourceConsumption 1.
  • ResourceConsumption (Generalisierung: Identifiable):
    • Zentraler Container aller Speicher- und Ausführungszeit-Metriken einer Implementierung.
    • Besitzt folgende Kompositionsbeziehungen:
      • +objectFileSection [1..*] → MemorySection: Mindestens ein Speicherabschnitt muss deklariert sein.
      • +executionTime [0..*] → ExecutionTime: Null bis n Rechenzeit-Profile.
      • +stackUsage [0..*] → StackUsage: Null bis n Stack-Verbrauchsprofile.
      • +heapUsage [0..*] → HeapUsage: Null bis n Heap-Verbrauchsprofile.
  • MemorySection (Generalisierung: Identifiable):
    • Beschreibt die physischen/logischen Sektionen der Objektdateien (.text, .rodata, .bss, .data etc.) zwecks Speicherausrichtung, Initialisierungsstrategie und Speicherschutz (MPU/Memory Mapping).
  • ExecutionTime (Generalisierung: Identifiable):
    • Quantifiziert Laufzeitmetriken (z. B. Best-, Typical-, Worst-Case Execution Time).
    • Unidirektionale Assoziation: +runnable [0..1] → ExecutableEntity.
  • StackUsage (Generalisierung: Identifiable, abstrakt):
    • Spezifiziert den Call-Stack-Bedarf.
    • Unidirektionale Assoziation: +runnable [0..1] → ExecutableEntity.
  • HeapUsage (Generalisierung: Identifiable):
    • Spezifiziert dynamisch reservierten Haldenspeicher.
  • ExecutableEntity (Generalisierung: Identifiable, abstrakt):
    • Abstrakte Zielklasse für ausführbare Einheiten (konkretisiert z. B. als RunnableEntity in SWCs oder BswModuleEntity / BswSchedulableEntity in BSW-Modulen).

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

  • Nicht zutreffend (Statisches Metamodell): Das Diagramm bildet keine Laufzeit-Zustandsübergänge oder Aufrufsequenzen ab.
  • Integrations- und Generierungsablauf (Build- und Konfigurationszeit):
    1. Deklaration: Modulentwickler parametriert im BswM-XML/ARXML alle Objektdateisektionen (MemorySection) sowie Stack- und WCET-Budgets für jede ExecutableEntity.
    2. Mapping & Allokation: Das ECU-Konfigurationswerkzeug ordnet die ExecutableEntities konkreten OSEK/AUTOSAR OS-Tasks zu.
    3. Synthese: Das Tool akkumuliert die Werte aus StackUsage (zur Bestimmung von OsTaskStackSize) und ExecutionTime (zur Auslegung von Task-Deadlines, OS-Execution-Budgets und Watchdog-Triggerzeiten).

4. Normative Relevanz & Entwickler-Hinweise

  • Memory Mapping (MemMap.h):
    • Durch die Kardinalität +objectFileSection 1..* ist jedes Modul normativ verpflichtet, mindestens eine MemorySection zu deklarieren.
    • Im C-Quellcode müssen zwingend die standardisierten Präprozessor-Symbole (z. B. <MODUL>_START_SEC_CODE, <MODUL>_STOP_SEC_CODE, <MODUL>_START_SEC_VAR_NOINIT_8BIT) umgesetzt sein, um die Segmente gegen Linker-Abschnitte aufzulösen.
  • Stack- & Laufzeit-Budgets:
    • Fehlende Zuordnungen (0..1) von StackUsage und ExecutionTime zu ExecutableEntity bedeuten, dass Werkzeuge keine automatische Stack- und Scheduling-Verifikation durchführen können und auf manuelle Integrationsschätzungen angewiesen sind.
    • Geteilte Runnables in präemptiven Multitasking-Umgebungen müssen den maximalen Stack-Pfad (Worst-Case Call Tree inkl. Interrupt-Verschachtelung) abbilden.
  • Restriktion Dynamischer Speicher (HeapUsage):
    • In sicherheitskritischen AUTOSAR Classic Systemen (ASIL A–D, ISO 26262) ist dynamische Heap-Allokation (malloc/free) nach MISRA C verboten. Der Wert verbleibt in der Praxis bei Kardinalität 0 bzw. ist nur für Ausnahmefälle unkritischer Subsysteme zulässig.

Speciﬁcation of BSW Module Description Template V1.1.0 R3.0 Rev 7 9 ResourceConsumption AUTOSAR software needs to be mapped on ECUs at some point during the development. Application software components can be basically mapped to any ECU available within the car. The mapping freedom is limited by the System Constraints [12] and the available resources on each ECU. BSW Modules are present in each ECU which provides the corresponding service. The ResourceConsumption element provides information about the needed resources concerning memory and execution time for each SwcImplementation or BswImplementation. 9.1 Static and Dynamic Resources Resources can be divided into static and dynamic resources. Static resources can only be allocated by one entity and stay with this entity. If the required amount of resources is bigger than the available resources the mapping does not ﬁt physically. ROM is an example of a spare resource where obviously only the amount of data can be stored that is provided by the storage capacity. Dynamic resources are shared and therefore can be allocated dynamically to different control threads over time. Processing time is a good example, where different tasks are given the processor for some time. If some runnable entity uses more processing time than originally planned, it can lead to functional failure.
