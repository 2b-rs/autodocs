1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm der AUTOSAR ECU Configuration Parameter Definition (ECUC-Metamodell gemäß AUTOSAR R2.1 / Rev 0020).
  • Architektur-Kontext: Spezifiziert die Konfigurationsstruktur des LIN Interface (LinIf, Communication Services Layer / BSW). Es definiert das Metamodell zur statischen Abbildung von LIN-Frames (LinIfFrame) innerhalb eines LIN-Kanals (LinIfChannel) sowie deren Zuordnung zu globalen Kommunikations-PDUs (Pdu aus dem EcuC-Kernmodul) für Sende-, Empfangs- und Slave-to-Slave-Kommunikation.

2. Komponenten, Entitäten & Schnittstellen

Container & Strukturhierarchie
  • LinIfChannel (ParamConfContainerDef)
    • Multiplizität: 1..*
    • Wurzel- bzw. Eltern-Container; fasst alle framespezifischen Definitionen pro physikalischem/logischem LIN-Kanal zusammen.
  • LinIfFrame (ParamConfContainerDef)
    • Multiplizität: 0..* (Komposition +subContainer von LinIfChannel).
    • Repräsentiert die Konfigurationsinstanz eines einzelnen LIN-Frames.
Parameter von LinIfFrame
  • LinIfPid (IntegerParamDef):
    • Protected Identifier (PID, inkl. Paritätsbits); Wertebereich: min = 0.
  • LinIfLength (IntegerParamDef):
    • Nutzdatenlänge des LIN-Frames in Byte; Wertebereich: min = 1, max = 8.
  • LinIfFrameType (EnumerationParamDef):
    • Definiert die Frame-Kategorie für das LIN-Scheduling und Protokollhandling.
    • Literale (EnumerationLiteralDef): Unconditional, MRF (Master Request Frame / Diagnostic), SRF (Slave Response Frame / Diagnostic), EventTriggered, Sporadic, Assign, Unassign, AssignNAD, Free, Conditional.
  • LinIfChecksumType (EnumerationParamDef):
    • Prüfsummenverfahren.
    • Literale (EnumerationLiteralDef):
      • Classic: Prüfsumme nur über Datenbytes (LIN 1.3 / Diagnostic Frames).
      • Enhanced: Prüfsumme über PID und Datenbytes (LIN 2.x).
  • LinIfFixedFrameSdu (IntegerParamDef):
    • Multiplizität: 0..1; statischer SDU-Identifikator für fest zugeordnete Frame-Strukturen.
PDU-Richtung & Zuordnung (LinIfPduDirection)
  • LinIfPduDirection (ChoiceContainerDef):
    • Sub-Container (+subContainer) unter LinIfFrame, realisiert eine exklusive Verzweigung (Choice) für die PDU-Richtung:
    1. LinIfTxPdu (ParamConfContainerDef, Multiplizität: 0..1):
      • Frame wird vom Steuergerät gesendet (Master-TX oder konfigurierter Slave-TX).
      • Parameter: LinIfTxPduId (IntegerParamDef, Attribut: symbolicNameValue = true zur Erzeugung statischer C-Präprozessor-Symbole für BSW-APIs wie PduR).
      • Referenz: LinIfTxPduRef (ReferenceDef, Rolle +reference) → Ziel: Pdu (ParamConfContainerDef, Multiplizität: 0..*, aus EcuC).
    2. LinIfRxPdu (ParamConfContainerDef, Multiplizität: 0..1):
      • Frame wird vom Steuergerät empfangen (Master-RX oder Slave-RX).
      • Referenz: LinIfRxPduRef (ReferenceDef, Rolle +reference) → Ziel: Pdu (ParamConfContainerDef, Multiplizität: 0..*, aus EcuC).
    3. LinIfSlaveToSlavePdu (ParamConfContainerDef, Multiplizität: 0..1):
      • Kommunikation zwischen Slaves; der Master initialisiert den Frame-Header via Schedule-Table, das eigene Steuergerät nimmt jedoch weder als aktiver TX- noch RX-Endpunkt der globalen PDU teil.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Konfigurations-Metamodell handelt, ist kein Sequenzfluss direkt abgebildet. Das abgeleitete BSW-Laufzeitverhalten gestaltet sich wie folgt:

  1. Frame-Triggering: Der LIN-Interface-Schedule-Handler wählt anhand der aktiven Schedule-Tabelle und des konfigurierten LinIfFrameType (z. B. zyklisch Unconditional oder bedarfsgesteuert Sporadic/EventTriggered) den nächsten Frame aus.
  2. TX-Pfad (LinIfTxPdu):
    • Trigger durch Schedule oder Upper Layer (PduR_LinIfTransmit).
    • Abruf der PDU-Payload via PduR/Com (LinIfTxPduRef).
    • Übergabe von Header und Payload an den LIN-Treiber (Lin_SendFrame) unter Berücksichtigung von LinIfChecksumType (Enhanced vs. Classic) und LinIfLength.
  3. RX-Pfad (LinIfRxPdu):
    • LIN-Treiber signalisiert erfolgreichen Frame-Empfang im Polling- bzw. Interrupt-Kontext (LinIf_RxIndication).
    • Validierung von Checksumme und PID gegen Konfiguration.
    • Weiterleitung der Nutzdaten an das Ziel (LinIfRxPduRef) via PduR_LinIfRxIndication.
  4. Slave-to-Slave-Pfad (LinIfSlaveToSlavePdu):
    • Header wird auf den Bus gesendet; keine lokale PDU-Kopieroperation in den oberen BSW-Schichten erforderlich.

4. Normative Relevanz & Entwickler-Hinweise

  • Generator- & Konfigurations-Restriktionen:
    • LinIfPduDirection ist als ChoiceContainerDef modelliert: Innerhalb eines LinIfFrame darf exakt eine Ausprägung (LinIfTxPdu, LinIfRxPdu oder LinIfSlaveToSlavePdu) aktiv sein.
    • Diagnose-Frames (MRF mit PID 0x3C, SRF mit PID 0x3D) erfordern zwingend Classic Checksum (LinIfChecksumType = Classic) und eine Payload-Länge von 8 Byte (LinIfLength = 8).
  • PduR-Kopplung:
    • Da LinIfTxPduId als symbolicNameValue = true definiert ist, generiert der ECUC-Code-Generator einen eindeutigen C-Makro-Bezeichner (Handle-ID). Dieser bildet den API-Vertrag zwischen PduR/Com und LinIf für Sendeaufrufe.
  • Speicher- und Routing-Optimierung:
    • Slaves müssen Frames mit LinIfSlaveToSlavePdu im LIN-Treiber ignorieren, während Master-Knoten lediglich den Frame-Header aussenden müssen, ohne BSW-PDU-Puffer zu allozieren.
