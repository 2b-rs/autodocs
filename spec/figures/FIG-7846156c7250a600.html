1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / AUTOSAR BSW-Konfigurationsmetamodell (EcucParamConfContainerDef).
  • Spezifikationskontext: AUTOSAR Classic Platform R20-11, AUTOSAR_SWS_ECUStateManager, Requirement ECUC_EcuM_00150.
  • Funktionale Einordnung: Metamodell-Definition des Containers EcuMWakeupSource. Definiert die statische Datenstruktur zur Parametrierung, Überwachung, Validierung und Weiterleitung von Wakeup-Ereignissen innerhalb des ECU State Managers (EcuM) sowie deren Kopplung an MCU-, Kommunikationskanal- (ComMChannel) und Teilnetzwerk-Instanzen (ComMPnc).

2. Komponenten, Entitäten & Schnittstellen

Zentraler Container
  • EcuMWakeupSource: EcucParamConfContainerDef
    • Kardinalität: [1..32]
    • Repräsentiert eine diskrete Aufwachquelle. Die Obergrenze 32 korrespondiert direkt mit der Wortbreite des AUTOSAR-Basistyps EcuM_WakeupSourceType (uint32-Bitmaske).
Parameter (+parameter-Aggregationen)
  • EcuMWakeupSourceId: EcucIntegerParamDef
    • Wertebereich: min = 5, max = 31, symbolicNameValue = true.
    • Weist der Wakeup-Quelle eine eindeutige Bitposition (1 << ID) in EcuM_WakeupSourceType zu. Die IDs 0..4 sind normativ für interne Standardquellen reserviert (ECUM_WKSOURCE_POWER, ECUM_WKSOURCE_RESET, ECUM_WKSOURCE_INTERNAL_RESET, ECUM_WKSOURCE_INTERNAL_WDG, ECUM_WKSOURCE_EXTERNAL_WDG).
  • EcuMValidationTimeout: EcucFloatParamDef
    • Wertebereich: min = 0.0, max = INF, Multiplizität: [0..1].
    • Maximal zulässige Zeitdauer in Sekunden bis zum Eintreffen der Validierung (EcuM_ValidateWakeupEvent). Wert 0 oder Entfall deaktiviert die Validierungsphase für diese Quelle.
  • EcuMCheckWakeupTimeout: EcucFloatParamDef
    • Wertebereich: min = 0.0, max = 10.0, Default: 0.0, Multiplizität: [0..1].
    • Timeout-Überwachung in Sekunden für asynchrone Treiberaufrufe während EcuM_CheckWakeup.
  • EcuMWakeupSourcePolling: EcucBooleanParamDef
    • Schaltet zwischen interruptbasierter Erfassung (FALSE, Wakeup via ISR/Treiber-Callback EcuM_SetWakeupEvent) und zyklischer Abfrage (TRUE, Wakeup via EcuM_MainFunction) um.
Referenzen (+reference / +destination)
  • EcuMResetReasonRef: EcucReferenceDef
    • Multiplizität: [0..*], requiresSymbolicNameValue = true.
    • Zielcontainer: McuResetReasonConf: EcucParamConfContainerDef [1..*] aus dem MCU-Treiber. Mappt Hardware-Resetursachen (Mcu_GetResetReason) auf logische EcuM-Wakeup-Quellen.
  • EcuMComMChannelRef: EcucReferenceDef
    • Multiplizität: [0..*], requiresSymbolicNameValue = true.
    • Zielcontainer: ComMChannel: EcucParamConfContainerDef [1..256] aus dem Communication Manager. Mappt Wakeup-Events auf physikalische Kommunikationskanäle.
  • EcuMComMPNCRef: EcucReferenceDef
    • Multiplizität: [0..*], requiresSymbolicNameValue = true.
    • Zielcontainer: ComMPnc: EcucParamConfContainerDef [0..504] aus dem Communication Manager. Verknüpft Wakeup-Events mit Partial Network Clusters (PNC) für partielles Netzwerk-Routing.

3. Dynamisches Verhalten & Sequenzablauf

  1. Erfassung & Setzen:
    • Interrupt-Pfad (EcuMWakeupSourcePolling == FALSE): Ein BSW-Treiber (z. B. Can, Lin, Icu) registriert ein Ereignis und ruft EcuM_SetWakeupEvent(sources) auf.
    • Polling-Pfad (EcuMWakeupSourcePolling == TRUE): EcuM fragt in der periodischen EcuM_MainFunction die zugehörigen Treiber per Check-Wakeup-API ab.
    • Startup/Reset-Pfad: Während der EcuM-Startup-Phase wird Mcu_GetResetReason() abgefragt und anhand von EcuMResetReasonRef der korrespondierende Wakeup-Source-Bitvektor aktiviert.
  2. Asynchrone Überprüfung:
    • Sofern eine asynchrone Prüfung erforderlich ist, startet der Timer EcuMCheckWakeupTimeout. Läuft dieser vor Statuserhalt ab, wird das Event verworfen.
  3. Validierungsphase:
    • Ist EcuMValidationTimeout > 0, wechselt die Quelle in den Zustand PENDING_VALIDATION. Der interne EcuM-Timer startet.
    • Erfolgreich: Ein BSW-Treiber/Stack bestätigt das Signal rechtzeitig via EcuM_ValidateWakeupEvent(sources). EcuM versetzt die Quelle in den Status VALIDATED.
    • Timeout/Abbruch: Läuft EcuMValidationTimeout ab, ohne dass die Validierung erfolgt, gilt das Event als unberechtigt (EXPIRED), wird gelöscht und die ECU kann in den Schlafzustand zurückkehren.
  4. Signalisierung an obere Schichten:
    • Für jede validierte Quelle informiert EcuM den Communication Manager synchron via ComM_EcuM_WakeUpIndication(Channel) (über EcuMComMChannelRef) bzw. ComM_EcuM_PNCWakeUpIndication(PNC) (über EcuMComMPNCRef).

4. Normative Relevanz & Entwickler-Hinweise

  • Wertebereichs-Restriktion (EcuMWakeupSourceId): Konfigurierbare Wakeup-Quellen dürfen ausschließlich IDs im Bereich 5..31 nutzen. IDs 0..4 führen im Generator-Pre-Compile-Check zu Fehlern. Die daraus resultierende C-Konstante ist typischerweise als (1uL << ID) definiert.
  • Architektur-Constraint auf 32 Quellen: Die maximale Multiplizität von 32 erzwingt eine feste Bitmasken-Abbildung auf einen skalaren 32-Bit-Datentyp (uint32). Atomare Bitoperationen (Bitwise AND/OR) sind dadurch ohne dynamischen Speicheraufwand oder Schleifenabarbeitung in Interrupt-Kontexten ausführbar.
  • Polling-Konfiguration: Ist EcuMWakeupSourcePolling == TRUE konfiguriert, muss die EcuM-Polling-Periode mit den Treiber-Antwortzeiten harmonisiert sein. Ein Betrieb im Sleep-Zustand ohne getaktetes OS erfordert besondere HW-Wakeup-Timer.
  • Dimensionierung von EcuMValidationTimeout: Der Timeout-Wert muss die Worst-Case-Initialisierungs- und Ansprechzeit des BSW-Stacks abdecken (Transceiver-Startup + Bus-Synchronisation + NM-PDU-Verifikation), darf aber nicht überdimensioniert werden, um ein Leerlaufen der Batterie durch Fehltrigger (z. B. Spikes) zu verhindern.
  • ComM-Kopplung: Fehlt bei einer netzwerkbezogenen Wakeup-Quelle die Referenz EcuMComMChannelRef, bleibt der Kommunikationskanal nach dem Aufwachen im Modus COMM_NO_COMMUNICATION.
