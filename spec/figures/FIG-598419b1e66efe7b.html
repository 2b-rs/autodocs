1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Statisches Schichten- und Blockarchitekturmodell (Layered Architectural Pattern) der AUTOSAR Classic Platform (Releases R3.0.7 / R3.2.3).
  • Technischer Zweck: Referenzarchitektur zur Definition von Testgrenzen und Integrationsstufen (Implementation Conformance Classes: ICC1, ICC2, ICC3) im Rahmen der AUTOSAR Conformance Testing Specification (AUTOSAR_CTSpec_Background).
  • Funktionale Einordnung: Visuelle Dekomposition des Gesamtsystems in hardwareunabhängige Anwendungssoftware, Middleware (RTE) und Basissoftware (BSW). Die rote Umrandung isoliert die vertikale Kommunikationsdomäne (Comms Services, Comms Hardware Abstraction, Comms Drivers) als eigenständiges Testobjekt bzw. Modulcluster auf ICC2-Ebene.

2. Komponenten, Entitäten & Schnittstellen

Schichten (Top-Down)
  • Application Layer (Grau): Träger der Application Software Components (SWCs); hardware- und busunabhängig.
  • Run Time Environment / RTE (Orange): Laufzeitumgebung und Implementierung des Virtual Functional Bus (VFB); vermittelt die Inter- und Intra-ECU-Kommunikation.
  • Basic Software / BSW:
    • Services Layer (Blau): Höchste BSW-Ebene; plattformspezifisch, aber mikrocontrollerunabhängig.
      • System Services: Modulgruppe für OS, Zustandsmanagement (EcuM, BswM), Watchdog-Manager (WdgM) sowie Diagnose/Fehlerbehandlung (Det, Dem). Verläuft L-förmig vertikal bis an die MCAL-Grenze.
      • Memory Services: Kapselung des nicht-flüchtigen Datenmanagements (NvM).
      • Comms Services (rot gerahmt): Signal- und PDU-Management (Com, PduR, IpduM) sowie Netzwerkmanagement (CanNm, FrNm, LinNm) und Diagnosekommunikation (Dcm).
    • ECU Hardware Abstraction Layer (Grün): Kapselt board-externe Peripherie und Transceiver zur Entkopplung von der ECU-Schaltung.
      • Onboard Device Abstraction: Ansteuerung boardspezifischer Komponenten (z. B. WdgIf, externe Watchdogs).
      • Memory Hardware Abstraction: Abstraktion von EEPROM/Flash-Speichern (MemIf, Fee, Ea).
      • Comms Hardware Abstraction (rot gerahmt): Businterfaces (CanIf, LinIf, FrIf, EthIf) und externe Bus-Transceiver-Treiber (z. B. CanTrcv).
      • I/O Hardware Abstraction: Direkte Brücke von der RTE zur I/O-Treiberschicht; abstrahiert diskrete I/O-Signale (Spannungen, Frequenzen) gegenüber der Applikation.
    • Microcontroller Abstraction Layer / MCAL (Magenta): Unterste Software-Schicht mit direktem Hardware-/Registerzugriff auf On-Chip-Peripherie.
      • Microcontroller Drivers: Core- und Takt-Treiber (Mcu, Gpt, Wdg).
      • Memory Drivers: On-Chip-Flash-Treiber (Fls).
      • Comms Drivers (rot gerahmt): On-Chip-Kommunikationscontroller-Treiber (Can, Lin, Fr, Eth, Spi).
      • I/O Drivers: Digitale und analoge On-Chip-Peripherietreiber (Port, Dio, Adc, Pwm, Icu).
    • Complex Drivers / CDD (Grün): Vertikaler Bypass-Block; reicht von der RTE unterbrechungsfrei bis zur Mikrocontroller-Hardware für hochgradig zeitkritische oder proprietäre Regelkreise (z. B. Motormanagement, Sonderprotokolle).
  • Microcontroller (Schwarz): Physische Halbleiterebene (Cores, Register, On-Chip-RAM/Flash).
Schnittstellentypen & Kopplungen
  • AUTOSAR Interface: Typisierte Ports (Sender-Receiver, Client-Server) zwischen SWCs sowie zwischen SWCs und RTE.
  • Standardized AUTOSAR Interface: Standardisierte Schnittstelle der Service-Module (z. B. Dem, Det, NvM, Com) zur RTE für Systemdienste.
  • Standardized Interface: C-APIs (Std_Types.h) zwischen den internen BSW-Schichten (z. B. PduR ↔ CanIf ↔ Can).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert eine statische Struktur. Aus dem rot hervorgehobenen Kommunikationspfad leiten sich folgende dynamische Interaktionskaskaden ab:

  • Sende-Pfad (Downlink, synchron zu asynchron):
    1. SWC ruft Rte_Write_<p>_<o>() auf.
    2. RTE leitet an Com_SendSignal() weiter; Signal wird in Interaktions-PDU (I-PDU) gepackt.
    3. PduR_ComTransmit() leitet I-PDU basierend auf Routing-Tabellen an das Zielinterface (z. B. CanIf_Transmit()).
    4. Interface adressiert Controller-Treiber (Can_Write()), der die Payload in Hardware-Tx-Mailboxen puffert.
    5. Asynchrone Bestätigung: Hardware sendet → Tx-Interrupt → Can_Isr_*() → CanIf_TxConfirmation() → PduR_CanIfTxConfirmation() → Com_TxConfirmation().
  • Empfangs-Pfad (Uplink, interrupt-/polling-gesteuert):
    1. Frame-Empfang im CAN-Controller erzeugt Rx-Interrupt oder Polling via Can_MainFunction_Read().
    2. CanIf_RxIndication() validiert Frame-ID und Data Length Code (DLC).
    3. Weiterleitung via PduR_CanIfRxIndication() an Com_RxIndication().
    4. Signalextraktion, Filterung und Routing an die RTE (Rte_Read_* oder Data Received Event).
  • Fehler- und Diagnoserückfallebenen:
    • Entwicklungsendpunkte melden Laufzeitfehler synchron über Det_ReportError().
    • Produktionsrelevante Hardware-/Busfehler melden asynchron an den Diagnostic Event Manager via Dem_ReportErrorStatus().

4. Normative Relevanz & Entwickler-Hinweise

  • Conformance Testing & Cluster-Zertifizierung:
    • ICC1: BSW wird monolithisch als Black-Box gegen RTE und Hardware getestet.
    • ICC2 (fokussiert durch roten Rahmen): Funktionscluster werden zusammengefasst getestet (z. B. vollständiger Comms-Stack Com + PduR + CanIf + Can). Modulinterne Schnittstellen innerhalb des Clusters müssen nicht zwingend standardkonform offengelegt sein.
    • ICC3: Jedes der ca. 60 Einzelmodule muss exakt die normierte SWS-API und das zugehörige BSWMD-XML-Modell erfüllen.
  • Schichten-Disziplin & Layer-Bypassing:
    • Direkter Zugriff von der Application Layer oder RTE auf Abstraction- oder MCAL-Module ist normativ verboten.
    • Einzige zulässige Ausnahme für Hardware-Direktzugriff an Standard-Stacks vorbei ist die Nutzung eines Complex Device Drivers (CDD).
  • Portabilitäts- und Konfigurationsregeln:
    • Beim Wechsel der Siliziumplattform verbleiben Services und ECU Abstraction quellcode-invariant; Anpassungen beschränken sich auf die MCAL-Treiberkonfiguration (.arxml → generierte Code-Artefakte *_Cfg.h, *_PBcfg.c).
    • Board-Varianten (z. B. Wechsel von CAN-Transceiver von NXP auf TI) erfordern ausschließlich Anpassungen in der Comms Hardware Abstraction, nicht in den Comms Services.
