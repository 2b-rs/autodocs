1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-2.0-Metamodell-Klassendiagramm (M2-Ebene nach AUTOSAR-Metamodell-Architektur).
  • Architektur-Kontext: AUTOSAR Adaptive Platform (AP), Teilspezifikation Manifest Specification (AUTOSAR_TPS_ManifestSpecification, Release R25-11).
  • Funktionaler Zweck: Modellierung der Zugriffsberechtigungen für Kommunikations-Events im Rahmen des Identity and Access Management (IAM) und des Communication Management (ara::com). Es definiert die formalen Beziehungen zur Gewährung von Zugriffsrechten (ComEventGrant als Spezialisierung von ComGrant) auf Instanz- und Deployment-Ebene sowie deren Entsprechung im Software-Design (ComEventGrantDesign als Spezialisierung von ComGrantDesign) gemäß den Anforderungen RS_MANI_00060 und TPS_MANI_01240.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • ComGrant (Spezialisierung von Grant):
    • Abstrakte Zwischenklasse für Kommunikations-Grants.
    • Assoziationen:
      • +serviceInstance: Referenziert optional ([0..1]) eine AdaptivePlatformServiceInstance.
      • +remoteSubject: Referenziert 0..* entfernte IAM-Subjekte vom Typ AbstractIamRemoteSubject.
  • ComEventGrant (Spezialisierung von ComGrant):
    • Konkretes Deployment-Artefakt zur Freigabe des Zugriffs auf ein bestimmtes Event einer Service-Instanz.
    • Assoziationen:
      • +serviceDeployment: Referenziert optional ([0..1]) ein Event-Deployment ServiceEventDeployment.
      • +design («atpUriDef»): Optionale Referenz ([0..1]) auf das korrespondierende Entwurfsartefakt ComEventGrantDesign.
  • AbstractIamRemoteSubject (UploadableDeploymentElement):
    • Repräsentiert ein entferntes Kommunikationssubjekt für die IAM-Autorisierung als auslieferbares Deployment-Element.
  • ComGrantDesign (Spezialisierung von GrantDesign):
    • Abstrakte Basisklasse für Entwurfszeit-Kommunikations-Grants.
  • ComEventGrantDesign (Spezialisierung von ComGrantDesign):
    • Entwurfszeit-Pendant zur Spezifikation von Berechtigungen auf Software-Architekturebene unabhängig vom konkreten Deployment.
  • GrantDesign (ARElement):
    • Abstrakte Basisklasse für Design-Grants.
    • Assoziation: Referenziert über +processDesign optional ([0..1]) ein ProcessDesign.
  • ProcessDesign (ARElement):
    • Repräsentiert den Prozessentwurf auf Architekturebene.
    • Wird referenziert von:
      • Process über Rolle +design [0..1].
      • ServiceInstanceToPortPrototypeMapping über Rolle +processDesign [0..1] («atpUriDef»).
  • Process (Spezialisierung von AbstractExecutionContext):
    • Repräsentiert die konkrete OS-Prozessinstanz zur Laufzeit.
  • AdaptivePlatformServiceInstance (UploadableDesignElement):
    • Repräsentiert eine Service-Instanz auf Design-Ebene.
    • Assoziation: Referenziert über +serviceInterfaceDeployment optional ([0..1]) ein ServiceInterfaceDeployment.
  • ServiceInterfaceDeployment (UploadableDesignElement):
    • Protokollspezifische Bindung eines Service-Interfaces auf Design-Ebene.
    • Komposition (schwarze Raute, «atpVariation,atpSplitable»): Aggregiert 0..* ServiceEventDeployment-Elemente über die Rolle +eventDeployment.
  • ServiceEventDeployment (ServiceInterfaceDeploymentElement):
    • Transport- und serialisierungsspezifisches Deployment eines einzelnen Events (z. B. SOME/IP Event ID, Event Groups), nun abgeleitet von ServiceInterfaceDeploymentElement.
  • ServiceInstanceToPortPrototypeMapping (UploadableDesignElement):
    • Verknüpft Ports mit Service-Instanzen und Prozessen auf Design-Ebene.
    • Assoziationen:
      • +process («atpSplitable»): Referenziert optional ([0..1]) einen Process.
      • +processDesign («atpUriDef»): Referenziert optional ([0..1]) ein ProcessDesign.
      • +serviceInstance: Referenziert optional ([0..1]) eine AdaptivePlatformServiceInstance.
      • +portPrototype («instanceRef,atpUriDef»): Instanzreferenz ([0..1]) auf einen PortPrototype.
  • PortPrototype (AtpBlueprintable, AtpPrototype):
    • Architektureller Kommunikationsendpunkt (RPort/PPort) einer Software-Komponente.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Metamodell für den Manifest-Entwurf handelt, existiert kein Sequenzdiagramm; das Diagramm determiniert jedoch zwingend folgende Laufzeitabläufe im AP IAM- und IPC-Stack:

  1. Deployment- & Startphase (Execution Management):
    • Beim Parsen des Execution Manifests und des Service Instance Manifests erzeugt die IAM-Instanz Zugriffskontrolltabellen (ACLs / Capabilities) für den jeweiligen Process.
  2. Access Control Check (ara::com Subscription/FindService):
    • Ruft eine Applikation innerhalb eines Prozesses Methoden wie FindService(), Subscribe() oder Send() für ein Event auf, fängt der Middleware-Stack (ara::com) bzw. der IAM-Policy-Enforcement-Point (PEP) die Anfrage ab.
  3. Validierungspfad:
    • Der PEP prüft, ob die Prozess-ID/UID über das Mapping (ServiceInstanceToPortPrototypeMapping → AdaptivePlatformServiceInstance) eine explizite ComEventGrant-Freigabe für das konkrete ServiceEventDeployment besitzt.
  4. Fehlerpfad & Abbruchbedingung:
    • Fehlt ein passender ComEventGrant, wird der Zugriff verweigert: ara::com schlägt mit einem entsprechenden Fehlercode (z. B. kGrantEnforcementFailed bzw. Zugriffsverweigerung) fehl, und es erfolgt ein Security-Event-Logging via DLT/IAM.

4. Normative Relevanz & Entwickler-Hinweise

  • Zweistufiges Design- vs. Deployment-Pattern:
    • Architekten definieren Berechtigungen zunächst abstrakt (ComEventGrantDesign via ComGrantDesign verknüpft mit ProcessDesign), während System-Integratoren die verbindlichen Laufzeit-Rechte über ComEventGrant (spezialisiert von ComGrant) konfigurieren.
  • Optionale Kardinalitäten (0..1):
    • Die Assoziationen +serviceInstance (an ComGrant) und +serviceDeployment (an ComEventGrant) besitzen nun die Kardinalität 0..1 statt zuvor strikt 1. Dies gestattet flexiblere Konstellationen bei der schrittweisen Modellierung oder partiellen Autorisierung von Service- und Event-Deployments.
  • Konfigurationsfalle (Silent Failure / Denial of Service):
    • Ist in einer Adaptive-Umgebung das IAM aktiv, führt das Fehlen des passenden Grants im Manifest dazu, dass Event-Subscriptions trotz korrekt konfigurierter Netzwerkanbindung auf Middleware-Ebene blockiert werden.
  • Port-Mapping-Konsistenz:
    • Integratoren müssen sicherstellen, dass die über ComGrant autorisierte AdaptivePlatformServiceInstance konsistent über ServiceInstanceToPortPrototypeMapping dem PortPrototype des Prozesses zugeordnet ist.
