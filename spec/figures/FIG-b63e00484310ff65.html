1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Datenflussdiagramm der AUTOSAR-Methodik auf Basis des Metamodells für Prozessdefinitionen (SPEM 2.0 / AUTOSAR Methodology Meta-Model M2).
  • Funktionale Einordnung: Spezifikation des methodischen Teilprozesses „Design System“ (AUTOSAR_TR_Methodology, Kap. 2, Figure 2.29, Release R4.3.1).
  • Technischer Zweck: Das Diagramm formalisiert den Integrationsprozess von der abstrakten VFB-Applikationsarchitektur (Virtual Functional Bus) und den Hardware-Beschreibungen hin zum konsolidierten System Description Root Element (System-Paket im M2-Metamodell) sowie der finalen Ableitung der globalen System Flat Map. Es bildet die verbindliche Vorstufe für den ECU Extract of System Description.

2. Komponenten, Entitäten & Schnittstellen

#### Aktivitäten (Tasks – gelbe Chevron-/Prozess-Icons):

  1. Define ECU Description: Deklaration der Hardware-Ressourcen einzelner Steuergeräte.
  2. Define System Topology: Aufbau des Netzwerk-Layouts und der Bus-Infrastruktur.
  3. Define Signal Path Constraints: Festlegung von Signalpfadbeschränkungen.
  4. Deploy Software Component: Zuordnung hierarchischer Software-Komponenteninstanzen zu physikalischen ECUs (SwcToEcuMapping).
  5. Derive Communication Needs: Extraktion von Bus-Kommunikationsbedarfen aus VFB-Konnektoren über ECU-Grenzen hinweg.
  6. Set System Root: Aggregation aller Teilmodelle unter dem M2-Wurzelelement System.
  7. Assign Top Level Composition: Verknüpfung der obersten Software-Architektur-Komposition mit dem System-Root.
  8. Generate or Adjust System Flat Map: Flachklopfen der hierarchischen SWC- und Port-Strukturen in eine globale Referenzebene.

#### Arbeitsergebnisse & Datenstrukturen (Work Products / Artifacts & Deliverables):

  • ECU Resources Description (Artifact): ARXML-Beschreibung der Rechenknoten, Speicher, Controller und I/O-Pins.
  • Topology (Artifact): Physikalische Vernetzung (EcuInstance, CommunicationCluster, PhysicalChannel).
  • Signal Path Constraints (Artifact): Zeit- und Integritätsrestriktionen für Signale über Gateways und Busse.
  • VFB Top Level System Composition (Artifact): Wurzel-Kompositionstyp (CompositionSwComponentType) mit Software-Component-Prototypes und VFB-Connectors.
  • VFB Software Component Mapping Constraints (Artifact, Stereotyp «input»): Optionale Allokationsregeln.
  • Mapping of Software Components to ECUs (Artifact): M2-Modellelement SwcToEcuMapping.
  • System Signal (Artifact): Netzwerkunabhängige logische Datenelemente (SystemSignal, ISignal).
  • Data Mapping (Artifact): Abbildung von Port-Datenelementen auf SystemSignals.
  • Communication Layers (Deliverable / Compound Work Product): Strukturierte Kommunikationsmatrix.
  • System Description Root Element (Artifact): Zentrale AUTOSAR-ARXML-Instanz der Metaklasse System.
  • System Flat Map (Artifact): FlatMap zur Auflösung tiefer Instanzpfade.

3. Dynamisches Verhalten & Sequenzablauf

  1. Hardware- & Topologie-Setup: Mehrere ECU Resources Descriptions (1..*) werden erstellt und zu einer Gesamttopologie (Topology) verknüpft. Parallel werden Signal Path Constraints auf Basis von Topologie und ECU-Ressourcen berechnet.
  2. SWC-Allokation: Die funktionale Software-Architektur (VFB Top Level System Composition) wird unter Berücksichtigung definierter Mapping-Constraints (0..1) auf die Topology gemappt (Deploy Software Component).
  3. Kommunikationsableitung: Aus dem Mapping of Software Components to ECUs leitet Derive Communication Needs alle Steuergeräte-übergreifenden Schnittstellen ab und erzeugt die erforderlichen System Signals und das Data Mapping (1..*).
  4. System-Root-Synthese: Set System Root aggregiert Topologie, Mapping, Data Mapping, Signal Path Constraints und das vorgegebene Kommunikationspaket (Communication Layers) in ein einziges System Description Root Element.
  5. Kompositionsbindung: Assign Top Level Composition integriert die VFB-Wurzelkomposition in das System Description Root Element.
  6. Flat-Map-Erzeugung: Generate or Adjust System Flat Map transformiert die hierarchische Instanzenstruktur in die flache Adressierungsbasis System Flat Map.
  • Abbruch-/Fehlerbedingungen:
  • Mapping-Konflikte: Verletzung von VFB Software Component Mapping Constraints (z. B. Speicherüberbuchung, inkompatible ASIL-Einstufungen).
  • Routing-Fehler: Signalpfade, die nicht erfüllbare Latenzen über Busgrenzen verlangen (Signal Path Constraints).
  • Fehlende Signalkopplung: Unvollständiges Data Mapping für externe Port-Konnektoren.

4. Normative Relevanz & Entwickler-Hinweise

  • Applikations- & SWC-Entwickler:
  • VFB-Schnittstellen (Ports, Interfaces) sind bis zum Schritt Deploy Software Component vollständig netzwerk- und hardwareagnostisch.
  • Das resultierende Mapping of Software Components to ECUs steuert, ob eine Port-zu-Port-Kommunikation von der RTE über optimierte Shared-Memory-/Pointer-Mechanismen realisiert wird oder über den BSW-Com-Stack serialisiert werden muss.
  • BSW- & Kommunikations-Stack-Entwickler (Com, PduR, CanIf/LinIf/EthIf):
  • Die Entitäten Communication Layers und Data Mapping bilden die zwingende Eingangsvoraussetzung für die Konfiguration von ComSignal, ComGroupSignal, Signal-Routing-Tabellen im PduR und die Frame-PDU-Generierung.
  • Signal Path Constraints erzwingen deterministische Gateway-Routen (PDU- oder Signal-Gatewaying) in Multibus-Steuergeräten.
  • RTE- & Tool-Kette (MCAL, A2L/MCD-2 MC):
  • Die System Flat Map ist normativ unverzichtbar für die RTE-Generierung, da sie geschachtelten Instanzen (SwComponentPrototype innerhalb von Sub-Kompositionen) global eindeutige Bezeichner zuweist.
  • Mess- und Kalibriersysteme (XCP, A2L-Generatoren) referenzieren Instanzen ausschließlich über die Pfade der System Flat Map.
