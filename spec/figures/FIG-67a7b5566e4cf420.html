1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hybrides Architektur- und Datenfluss-/Sequenzdiagramm (funktionaler Interaktionsfluss über AUTOSAR-Schichten).
  • Technischer Zweck: Visualisierung des vollständigen Modus-Verarbeitungszyklus (Mode Processing Cycle) im AUTOSAR Classic BSW Mode Manager (BswM, SWS BSWModeManager, Release R4.0.3).
  • Architektur-Kontext: Entkopplung zwischen Modus-Anforderung (Mode Request) und tatsächlicher Modus-Umschaltung (Mode Switch / Modus-Ausführung). Der BswM agiert als zentrale Arbitrierungs- und Steuerungsinstanz (unterteilt in Mode Arbitration und Mode Control), um Zustandsübergänge des Gesamtsystems deterministisch abzusichern.

2. Komponenten, Entitäten & Schnittstellen

  • Applikationsschicht (SWC Layer):
    • Mode requesting SWC: Sendet Modus-Wünsche an die Systemsteuerung.
    • Mode using SWC: Konsumiert Modus-Deklarationen (Mode Declaration Groups) und reagiert auf Mode-Switch-Events.
  • Laufzeitumgebung (RTE):
    • mode request distribution: RTE-Infrastrukturkanal zur Weiterleitung von Modus-Anfragen via Mode-Request-Ports (Rte_Write bzw. BswM-Mode-Request-Interfaces) an den BSW-Stack.
    • local mode handling: RTE-Modus-Management (Rte_Switch), das Modus-Zustände partitioniert verwaltet und Runnable Entities triggert (on-entry, on-exit, on-transition).
  • BSW Mode Manager (BswM):
    • Mode Arbitration: Bewertet eingehende Modus-Requests über konfigurierte Regeln (BswMRule), logische Ausdrücke (BswMLogicalExpression) und Bedingungen (BswMModeCondition).
    • Mode Control: Führt nach Regelauswertung verknüpfte Aktionslisten (BswMActionList) aus (BswMRuleTrueActionList / BswMRuleFalseActionList).
    • Action list: Sequenz konfigurierter Aktionen; enthält u. a. Rte_Switch-Aufrufe (BswM_RteSwitch für Mode A, Mode X) sowie native BSW-API-Aufrufe (ComM, EcuM, PduR etc.).

3. Dynamisches Verhalten & Sequenzablauf

  1. Schritt 1 (Request Mode A):
    • Die Mode requesting SWC stellt eine Modus-Anforderung (Mode A).
    • Die RTE leitet diesen Request über die mode request distribution an den BswM weiter (asynchron im Task-Kontext über BswM_MainFunction oder synchron via Immediate-Processing-Callout).
  2. Schritt 2 (Rule Evaluation & Launch Action List):
    • Innerhalb der Mode Arbitration werden gezielt die durch Mode A betroffenen Regeln re-evaluiert.
    • Ergibt die Regelauswertung eine Statusänderung, feuert die Mode Control die zugehörige Action list.
  3. Schritt 3 (Execute BSW Actions & RTE Switches):
    • Die Aktionen der Aktionsliste werden strikt sequenziell ausgeführt.
    • Neben BSW-internen Modulaufrufen erfolgt die Modus-Rückführung an die RTE über Rte_Switch(mode A) und Rte_Switch(mode X).
    • Die RTE übernimmt via local mode handling das Umschalten des Modus-Status und informiert registrierte Konsumenten (Mode using SWC sowie ggf. rückwirkend die anfordernde Mode requesting SWC) über RTE-Events.

4. Normative Relevanz & Entwickler-Hinweise

  • Keine direkte Selbst-Umschaltung durch SWCs: Eine SWC kann Modi niemals direkt umschalten; sie darf lediglich Anforderungen äußern (Mode Request). Die Autorität über die Modus-Transition (Mode Switch) obliegt ausschließlich dem BswM.
  • Immediate vs. Deferred Processing:
    • Immediate: Regelauswertung und Aktionsausführung erfolgen synchron im Kontext des aufrufenden Ports (Timing- und Interrupt-Kontext strikt beachten; Rekursionsgefahr bei synchronen Rückmeldungen).
    • Deferred: Request setzt Flags; Regelauswertung und Abarbeitung erfolgen zyklisch im Kontext der BswM_MainFunction (Task-Kontext, jitterbehaftet).
  • RTE-Konfiguration (Mode Declaration Groups):
    • Die via Rte_Switch angesprochenen Modi (mode A, mode X) erfordern typgleiche ModeDeclarationGroupPrototypes am BswM (Provided Mode Switch Port) und korrespondierende Required Ports an den konsumierenden SWCs.
    • Fehlerhafte Priorisierung oder zyklische Abhängigkeiten in der Action list können zu Livelocks oder Systemblockaden führen.
