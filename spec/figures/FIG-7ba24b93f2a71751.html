1. Diagrammtyp & Architektur-Kontext

UML-Komponentendiagramm (im Rahmen class HM_OverallFlow) zur Darstellung des funktionalen Scopes und der Black-Box-Kontextarchitektur des AUTOSAR Health Monitoring (HM). Das Diagramm verortet die zentrale Komponente :Health Monitoring im Zusammenspiel mit überwachten Entitäten, Fehlerbehandlungsmechanismen und der Watchdog-Ansteuerung auf Systemebene.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert vier UML-Komponenteninstanzen und vier Informationsflüsse («flow», gestrichelte Pfeile mit offener Pfeilspitze):

  • :Health Monitoring: Zentrale funktionale Überwachungskomponente (Black-Box).
  • :Supervised Entity: Quelle der Überwachungsdaten. Übergibt an :Health Monitoring:
    • Checkpoint ID («flow»)
    • Health Status («flow»)
  • :Error handling: Senke für Fehlerreaktionen. Empfängt von :Health Monitoring:
    • Error handler ID to be triggered («flow»)
  • :Watchdog: Senke für Hardware-/Software-Auffrischungsaktionen. Empfängt von :Health Monitoring:
    • Triggering of watchdog («flow»)

3. Dynamisches Verhalten & Sequenzablauf

Während der Ausführung meldet eine :Supervised Entity das Erreichen von Kontrollpunkten (Checkpoint ID) sowie zyklische oder ereignisbasierte Zustandsmeldungen (Health Status) an das :Health Monitoring. Bei Erkennung von Abweichungen der zeitlichen, logischen oder gesundheitlichen Integritätsbedingungen leitet :Health Monitoring die Ausführung an das Fehlermanagement weiter (Error handler ID to be triggered). Im regulären Betriebsfall sowie abhängig vom Überwachungsergebnis erfolgt die Ansteuerung bzw. Auffrischung der Überwachungsinstanz (Triggering of watchdog).

4. Normative Relevanz & Entwickler-Hinweise

Das Diagramm bietet eine konzeptionelle Übersicht (Functional Interfaces Overview) ohne direkte Anforderungsspezifikation. Für Implementierer definiert es die primären Eingangs- und Ausgangsdatenflüsse des Health-Monitoring-Subsystems: Trennung zwischen programmatischem Kontrollfluss-Monitoring (Checkpoint ID) und Zustandsüberwachung (Health Status) auf Eingangsseite sowie Trennung zwischen anwendungsspezifischer Fehlerbehandlung (Error handler ID) und Plattform-/Hardware-Absicherung (Watchdog Triggering) auf Ausgangsseite.

Specification of Health Monitoring AUTOSAR FO Release 1.4.0 6 Functional specification 6.1 Functional Overview This section presents black-box functional overview the Health Monitoring. It does not define any requirements nor details on the functionality. 6.1.1 Functional Interfaces The Health Monitoring supervises the execution of a configurable number of Supervised Entitys and it also supervises their Health Status. When it detects a violation of the configured temporal and/or logical constraints on program execution or a violation of the configured health constraints, it triggers the appropriate error handlers. Health Monitoring controls also the Watchdogs correspondingly, see Figure 6.1. Figure 6.1: Scope of Health Monitoring The Health Monitoring function can be split as a daisy chain. Each Health Monitoring instance has the same interface to Supervised Entitys, Error handling and Watchdog. In addition, the interface between the instances of Health Monitoring is standardized as well - it carries the results of Health Monitoring as well as "raw data" (Checkpoint IDs, Health Status together with necessary context information). Each instance adds some context-specific data to Checkpoints (e.g. process/task id).
