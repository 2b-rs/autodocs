1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Metamodell-Diagramm basierend auf SPEM 2.0 (Software & Systems Process Engineering Metamodel), formal eingebettet als UML-Profil über ein «SPEM_MethodContentPackage».
  • Technischer Zweck & Einordnung: Das Diagramm spezifiziert die Methodik-Schnittstelle der AUTOSAR Adaptive Platform (AP) für die Phase Implementation of Adaptive Software (Kapitel 2.5 / 3.4 in AUTOSAR_AP_TR_Methodology). Es definiert die formalen Arbeitsabläufe, Übergabeartefakte und Verantwortlichkeiten zwischen dem Applikationsentwickler (SWC/Service-Erstellung) und dem Systemintegrator (Target-Build/Packaging).
  • Normative Verweise: RS_METH_00032 (Entwicklung von Adaptive Software), RS_METH_00202 (Erzeugung von Software-Builds für Zielumgebungen). Gültig für Releases R21-11, R22-11 und R23-11.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Stereotypen
  • Package «SPEM_MethodContentPackage» Adaptive Software Implementation: Prozesskapsel, welche die Kernaktivitäten und Deliverables der Entwicklerdomäne isoliert.
  • «TaskDefinition» Develop Adaptive Software: Prozessaktivität des Entwicklers; umfasst Detailentwurf, Code-Generierung, C++-Implementierung (ara::*) sowie Modultests.
  • «Deliverable» Adaptive Software Implementation: Formales Übergabepaket vom Entwickler an die Integrationsebene.
  • Beitragende Artefakte («Artifact» mit «contributes»-Beziehung auf Adaptive Software Implementation):
    • Adaptive Software Source Code: Handgeschriebener C++-Quellcode (C++14/C++17) und Header (Business-Logik, Algorithmen).
    • Adaptive Software Generated Item: Generator-Outputs auf Basis der ARXML-Schnittstellen (spezifisch ara::com-Proxies, Skeletons, Datentypen, Serialisierungsroutinen).
    • Adaptive Software Object Code: Vorkompilierte Objektdateien (.o) oder statische/dynamische Bibliotheken (.a, .so), insbesondere bei IP-Schutz oder standardisierten Plattformdiensten.
    • Adaptive Software Build Configuration: Build-Definitionen (z. B. CMakeLists.txt, Makefiles, Toolchain-Dateien, Compiler-/Linker-Flags).
  • Eingangs-Deliverables («Deliverable»):
    • Service Interface Description: Formale Service-Verträge (ARXML: Events, Methods, Fields).
    • Application Design Description: Formale Struktur der SWCs, Port-Prototypen, interne Verhaltensbeschreibungen und Datentyp-Mappings.
  • Nachgelagerte Integrationsentitäten:
    • «TaskDefinition» Build SW for target runtime environment: Integrator-Aktivität zur Cross-Kompilierung und zum Linken gegen das konkrete Ziel-OS/Sysroot.
    • «Artifact» Adaptive Software Binary: Zielplattform-spezifisches Executable (POSIX-ELF-Binary oder Shared Library).
Beziehungen & Abhängigkeiten
  • «input»: Application Design Description → Develop Adaptive Software (formale Spezifikationsgrundlage für Codierung und Generierung).
  • «output»: Develop Adaptive Software → Adaptive Software Implementation.
  • «contributes»: 4-fache Aggregation/Spezialisierung der Artefakte (Source Code, Generated Item, Object Code, Build Configuration) in das Deliverable Adaptive Software Implementation.
  • «input»: Adaptive Software Implementation → Build SW for target runtime environment.
  • «output»: Build SW for target runtime environment → Adaptive Software Binary.

3. Dynamisches Verhalten & Sequenzablauf

  1. Design-Einspeisung (Prerequisite):
    • Die Service-Schnittstellen (Service Interface Description) und das Komponenten-Design (Application Design Description) liegen als ARXML-Modelle vor.
  2. Generierungs- und Entwicklungsphase (Develop Adaptive Software):
    • Code-Generierung: Generator liest ARXML ein und erzeugt typisierte C++-Bindeglieder (Adaptive Software Generated Item).
    • Implementierung: Entwickler implementiert die Klassenrümpfe gegen die ara::com- und Plattform-APIs (Adaptive Software Source Code).
    • Kompilierungsstrategie: Abhängig davon, ob die Zielumgebung/Toolchain dem Entwickler bereits vorliegt:
      • Source-Lieferung: Bereitstellung von Source + Generator-Items + Build Configuration.
      • Binary/Object-Lieferung: Lokale Vorkompilierung zu Adaptive Software Object Code (z. B. wenn Toolchain bekannt oder Closed-Source-Lieferung gefordert ist).
  3. Übergabe & Aggregation:
    • Schnüren des Deliverables Adaptive Software Implementation.
  4. Zielplattform-Build (Build SW for target runtime environment):
    • Integrator compiliert/linkt die Artefakte gegen POSIX-Sysroot, OS-Bibliotheken (QNX, Linux) und Platform-Core-Bibliotheken.
  5. Erzeugung des Executables:
    • Generierung des finalen ELF-Binaries (Adaptive Software Binary), bereit zur Paketierung mit dem Execution Manifest für das AUTOSAR Execution Management (ara::exec).

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Handcode und Generat: Manuelle Modifikationen an Adaptive Software Generated Item sind strikt unzulässig; Änderungen an Schnittstellen müssen über das ARXML-Designmodell erfolgen und deterministisch neu generiert werden.
  • C++ ABI- und Toolchain-Konsistenz: Werden Adaptive Software Object Code-Artefakte geliefert, erzwingt dies eine strikte Übereinstimmung der C++-Standardbibliothek (libc++ / libstdc++), C++-Dialekt-Flags und Compiler-Versionen zwischen Entwickler und Integrator, da C++ keine standardisierte ABI über Toolchains hinweg garantiert.
  • Vollständigkeit der Build-Konfiguration: Die Adaptive Software Build Configuration muss portable Zieldefinitionen enthalten (z. B. modernes Target-basiertes CMake mit sauber gekapselten Include-Directories und Link-Dependencies), um im Build-System des Integrators nahtlos cross-kompiliert werden zu können.
  • Lifecycle-Einbettung: Das resultierende Adaptive Software Binary ist nicht autonom lauffähig, sondern setzt zwingend die Initialisierung der AUTOSAR-Laufzeitumgebung (z. B. Execution Management State Client, Logging-Framework ara::log) und das dazugehörige Execution Manifest voraus.
