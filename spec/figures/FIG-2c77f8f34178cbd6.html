1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Informelles BSW-Architektur-, Topologie- und Routing-Diagramm (AUTOSAR Classic Platform, Basic Software).
  • Architektur-Kontext: AUTOSAR Communication Manager (ComM) im Zusammenspiel mit dem Network Management Interface (Nm) und busspezifischen NM-Modulen (z. B. CanNm).
  • Technischer Zweck: Spezifikation der verteilten PNC-Koordination (Partial Network Cluster Gateway Routing) bei Vorhandensein mehrerer Top-Level-PNC-Koordinatoren für denselben PNC (hier: PNC3) über hierarchische und vermaschte Bus-Topologien hinweg. Es visualisiert das Verhalten bei getrennten Aktivierungspfaden sowie beim synchronisierten PNC-Shutdown ([SWS_ComM_01082]).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Steuergeräte-Knoten (ECUs)
  • PNC-Coor1 (Root/Top-Level Coordinator für PNC1, PNC2):
    • Kanäle Ch1 und Ch2 jeweils als ComMPncGatewayType = ACTIVE konfiguriert.
    • Verwaltet [PNC1, PNC2].
  • PNC-Coor2 (Intermediate Coordinator für PNC1/2, Top-Level Coordinator für PNC3):
    • Ch1: ComMPncGatewayType = PASSIVE (Downlink von PNC-Coor1.Ch1).
    • Ch2: ComMPncGatewayType = ACTIVE (Uplink zu Node1).
    • Ch3: ComMPncGatewayType = ACTIVE (Shared Bus zu Node4 und PNC-Coor3).
    • Mapping: [PNC1, PNC2] auf Ch2; [PNC3] ausschließlich auf Ch3.
  • PNC-Coor3 (Intermediate Coordinator für PNC1/2, bedingter Top-Level Coordinator für PNC3):
    • Port oben: ComMPncGatewayType = PASSIVE (Downlink von PNC-Coor1.Ch2).
    • Port links: ComMPncGatewayType = PASSIVE (verbunden mit Shared Bus von PNC-Coor2.Ch3). (Hinweis: Im AUTOSAR-Originaldiagramm sind beide passiven Schnittstellen als Ch1 beschriftet – Spezifikationsinkonsistenz).
    • Ch2: ComMPncGatewayType = ACTIVE (Uplink zu Node2).
    • Ch3: ComMPncGatewayType = ACTIVE (Uplink zu Node3).
    • Mapping: [PNC1, PNC2] auf Ch1 und Ch2; [PNC3] ausschließlich auf Ch3.
  • Leaf Nodes (Node1, Node2, Node3, Node4):
    • Reines Endknoten-Verhalten (ComMPncGatewayType NOT set / COMM_GATEWAY_TYPE_NONE).
    • Node1, Node2, Node4: Zugeordnet zu [PNC1, PNC2].
    • Node3: Ausschließlich zugeordnet zu [PNC3].
Metamodell-Beziehungen & Konfigurationsparameter
  • ComMPncGatewayType (Stereotyp: Konfigurations-Enumeration):
    • ACTIVE (Gelb, A): Gateway leitet PNC-Requests aktiv auf diesen Kanal weiter (sendet NM-PDUs).
    • PASSIVE (Blau, P): Gateway empfängt externe PNC-Requests/Releases zur internen Weiterleitung.
    • NOT set (Orange, N): Keine Gateway-Funktionalität auf diesem Kanal (Standard-Teilnehmer).
  • ComMChannelPerPnc (Rote Pfeile):
    • Kardinalität: 1 … * Kanäle pro PNC (PncToChannelRouting).
    • Definiert, über welche physikalischen Kanäle ein PNC aktiv angefordert werden darf/muss.

3. Dynamisches Verhalten & Sequenzablauf

Szenario A: PNC3-Aktivierung durch PNC-Coor2 (Top-Down)
  1. Trigger: Lokale Nutzeranforderung (ComM_RequestComMode) auf PNC-Coor2 für PNC3.
  2. NM-Transmission: PNC-Coor2 setzt das Bit für PNC3 in der NM-PDU (User Data / CBV) und sendet es zyklisch auf Ch3 (ACTIVE).
  3. Filterung & Forwarding an PNC-Coor3:
    • PNC-Coor3 empfängt die NM-PDU auf seinem passiven Buskanal (Ch1).
    • Die NM-Filtermaske (NmPncFilterMask) an PNC-Coor3.Ch1 lässt PNC3 passieren.
    • ComM auf PNC-Coor3 erkennt den Request für PNC3 und spiegelt/leitet ihn gemäß Gateway-Routing weiter auf PNC-Coor3.Ch3 (ACTIVE).
  4. Wakeup Leaf: Node3 empfängt die Aktivierung auf Ch1 und hält den Kommunikationsstack für PNC3 aktiv.
Szenario B: Synchronisierter PNC-Shutdown ([SWS_ComM_01082])
  1. Trigger: PNC-Coor2 gibt PNC3 frei (ComM_RequestComMode(NO_COMMUNICATION)). Kein anderer interner Nutzer auf PNC-Coor2 fordert PNC3.
  2. Shutdown-Initiierung: PNC-Coor2 agiert als Top-Level-Koordinator für PNC3 und sendet eine PN-Shutdown-Botschaft über Ch3.
  3. Gateway-Propagation: PNC-Coor3 empfängt die Shutdown-Sequenz an Ch1 (PASSIVE).
  4. Forwarding ([SWS_ComM_01082]): PNC-Coor3 leitet den synchronisierten PNC-Shutdown deterministisch an PNC-Coor3.Ch3 (ACTIVE) weiter.
  5. Synchroner Sleep: PNC-Coor2, PNC-Coor3 und Node3 gehen koordiniert und synchronisiert in den Sub-Bus-Schlafzustand über.
Szenario C: PNC3-Aktivierung ausschließlich durch Node3 (Bottom-Up / Isoliert)
  1. Trigger: Node3 fordert PNC3 an und sendet NM-PDUs auf PNC-Coor3.Ch3.
  2. Mirror Back: PNC-Coor3 spiegelt die Anforderung auf Ch3 zurück (ACTIVE), um das Segment wachzuhalten.
  3. Keine Rückwärtsleitung: Da PNC3 in PNC-Coor3 ausschließlich auf Ch3 referenziert ist (ComMChannelPerPnc), erfolgt keine Weiterleitung an PNC-Coor3.Ch1 oder den Shared Bus zu PNC-Coor2.
  4. Konsequenz: PNC-Coor3 agiert in diesem Pfad autonom als lokaler Top-Level-Koordinator für PNC3.

4. Normative Relevanz & Entwickler-Hinweise

  • NM-Filtermasken-Konfiguration (NmPncFilterMask):
    • Zwingende Vorgabe: An PNC-Coor3.Ch1 muss die Bitmaske im Nm-Treiber/Nm-Interface zwingend so konfiguriert werden, dass das Bit für PNC3 nicht herausgefiltert wird, obwohl PNC3 in PNC-Coor3 primär nur auf Ch3 gemappt ist. Ein zu strikter Filter an Ch1 unterbricht die Top-Level-Koordination von PNC-Coor2 zu Node3.
  • Asymmetrisches Channel-Mapping (ComMChannelPerPnc):
    • PNC-Coor3 darf Ch1 nicht in ComMChannelPerPnc für PNC3 aufnehmen. Würde Ch1 referenziert, entstünde eine unerwünschte Rückkopplung/Netzwerkaktivierung in Richtung PNC-Coor2 und Node4, wenn nur Node3 aktiv ist.
  • Synchronized PNC Shutdown ([SWS_ComM_01082]):
    • ComMPncSynchronousWakeup und synchronisierte Shutdown-Parameter (ComMPncPrepareSleepTimer) müssen auf allen beteiligten Zwischenstationen (PNC-Coor2, PNC-Coor3) synchron parametriert sein. Fehlkonfiguration führt zu Race Conditions (z. B. vorzeitiges Einschlafen von Node3 oder Deadlocks durch nicht abklingende ERA/IRA-Timer).
  • Umgang mit Spezifikationsinkonsistenz:
    • Im AUTOSAR-Modell für PNC-Coor3 müssen zwei separate logische ComMChannel-Instanzen konfiguriert werden, auch wenn die Abbildung beide fälschlicherweise als Ch1 bezeichnet (z. B. ComMChannel_Backbone zu Coor1 vs. ComMChannel_InterCluster zu Coor2/Node4). Beide Kanäle besitzen den Typ COMM_GATEWAY_TYPE_PASSIVE.

Specification of Communication Manager AUTOSAR CP R25-11 Figure 7.6: Multiple top-level PNC coordinators of the same PNC In Figure 7.6 PNC-Coor2 and PNC-Coor3 act as top-level PNC coordinator for PNC3. For a proper behaviour, the NM filter mask at PNC-Coor3.Ch1 need to be configured such that PNC3 bit pass the filter. If synchronized PNC shutdown is enabled, then the expected behaviour should be as described in the following point: • if PNC-Coor2 request the PNC3, then this PNC request is forwarded by PNC- Coor3 to Node3 • if only PNC-Coor2 has requested PNC3 and PNC-Coor2 release PNC3, then PNC-Coor2 transmit a PN shutdown message. PNC-Coor3 forward the synchronized PNC shutdown to PNC-Coor3.Ch3 (see [SWS_ComM_01082]). Therefore PNC3 synchronously shutdown on all affected nodes from PNC-Coor2, across PNC-Coor3 down to Node3. Thus, PNC-Coor2 act as the top-level coordinator for PNC3 in that scenario. • If only Node3 request PNC3, then PNC-Coor3 consider only PNC-Coor3.Ch3 to mirror back the PNC request. The PNC request is not forwarded to any other channel for this PNC request, since PNC3 reference only PNC-Coor3.Ch3. 55 of 209 Document ID 79: AUTOSAR_CP_SWS_COMManager
