1. Diagrammtyp & Architektur-Kontext

Konzeptionelles Architektur- und Kommunikationsdiagramm zur Dienst- und Netzwerkkonfiguration im Kontext des AUTOSAR System Templates (insbesondere SOME/IP bzw. Service-orientierte Kommunikation über UDP). Dargestellt wird die Zuordnung von Service-Interfaces (Events, Methods, Eventgroups) zu netzwerkbezogenen Instanzen (Provided/Consumed Service Instances, Event Handlern) und Application Endpoints über mehrere Steuergeräte hinweg.

2. Komponenten, Entitäten & Schnittstellen

  • Service Interface / Definition (oben):
    • Methoden und Events: Event1, Event2, Method.
    • Eventgroups: EG1 (referenziert Event1), EG2 (referenziert Event1 und Event2).
    • Assoziation von Ecu1 (oberer Event Handler) auf das Service-Interface bzw. dessen Elemente.
  • Ecu1 (Server / Service Provider):
    • AEP (UDP 30490): Statischer Application Endpoint auf UDP-Port 30490.
    • PSI: Provided Service Instance.
    • Zwei EH: Event Handler innerhalb der Provided Service Instance.
  • Ecu2 (Client 1):
    • AEP (UDP dynamically): Dynamischer Application Endpoint für UDP.
    • CSI: Consumed Service Instance.
    • CEG: Consumed Event Group, verweist auf EG1.
  • Ecu3 (Client 2):
    • AEP (UDP dynamically): Dynamischer Application Endpoint für UDP.
    • CSI: Consumed Service Instance mit zwei CEG-Instanzen (referenzieren EG1 und EG2).
    • AEP (UDP Multicast): Weiterer Application Endpoint für Multicast-Empfang, assoziiert mit der unteren CEG.
  • Schnittstellen & Verbindungen:
    • Grüne Pfeile: Kommunikationsbeziehungen bzw. Service-Discovery-/Abonnement-Pfade von den Clients (Ecu2, Ecu3) zur Provided Service Instance (PSI bzw. AEP (UDP 30490)) auf Ecu1.
    • Blaue Pfeile: Datenpfade / Event-Übertragungen von den EH (Event Handlern) der Ecu1 zu den jeweiligen CEG (Consumed Event Groups) auf Ecu2 und Ecu3.
    • Schwarze Pfeile: Zuordnungen von CEG zu EG1/EG2 sowie von EG zu den atomaren Events (Event1, Event2) und lokale Endpunkt-Referenzen.

3. Dynamisches Verhalten & Sequenzablauf

  • Dienstbereitstellung: Ecu1 stellt über einen statisch konfigurierten UDP-Port (30490) eine Provided Service Instance (PSI) bereit, die Events über Event Handler (EH) verwaltet.
  • Dynamische Client-Registrierung: Die Clients Ecu2 und Ecu3 nutzen dynamisch vergebene UDP-Ports (UDP dynamically) für ihre Consumed Service Instances (CSI).
  • Event-Abonnement & Eventgruppen-Verbindung:
    • Ecu2 abonniert über seine CEG die Eventgruppe EG1 (enthält Event1).
    • Ecu3 abonniert über zwei getrennte CEG sowohl EG1 als auch EG2 (enthält Event1 und Event2).
    • Eine CEG auf Ecu3 ist zudem an einen Multicast-Endpoint (AEP (UDP Multicast)) angebunden.
  • Ereignisübertragung: Nach erfolgtem dynamischen Verbindungsaufbau / Subscription senden die Event Handler von Ecu1 die entsprechenden Event-Datenströme gezielt an die Consumed Event Groups der dynamisch konfigurierten Clients.

4. Normative Relevanz & Entwickler-Hinweise

  • Veranschaulicht das Zusammenspiel von ProvidedServiceInstance, ConsumedServiceInstance, EventHandler und ConsumedEventGroup bei Verwendung dynamischer Client-Ports (dynamic UDP Port Configuration).
  • Verdeutlicht die Modellierung im System Template: Statische Bereitstellung auf Provider-Seite (feste Portnummer für Service Discovery / Offering) gegenüber dynamischer Allokation von Client-Endpunkten zur Laufzeit sowie die Zuordnung von Eventgroups (EventGroup zu ConsumedEventGroup) und Multicast-Endpunkten.

System Template AUTOSAR CP Release 4.4.0 6.7.5.1 Example for usage of SocketConnectionBundles and SocketConnections Figure 6.39 shows a setup with a Service that contains two Events (Event1 and Event2) and one Method. In AUTOSAR an Event is described as a VariableDataPrototype in a SenderReceiverInterface. A ClientServerOperation in a ClientServerInterface is used for the description of the Method. The Service is provided on Ecu1 by the ApplicationEndpoint with Udp Port 30490. Two unicast ApplicationEndpoints with ConsumedServiceInstances exist for the service. TpPort.dynamicallyAssigned is set to true for both these ApplicationEndpoints. With the ConsumedEventGroup on Ecu2 a subscription to Event- Group1 that contains Event1 is described. With the ConsumedEventGroup on Ecu3 a subscription to EventGroup2 that contains Event1 and Event2 is described. In addition a multicast ApplicationEndpoint is defined. The ConsumedServiceInstance on Ecu3 contains a second ConsumedEventGroup that refers to the multicast ApplicationEndpoint to allow Ecu3 to receive Event1 also via multicast.
