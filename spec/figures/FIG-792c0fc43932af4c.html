1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU-Configuration-Metamodell (UML-Klassendiagramm / ECUC-Parameterspezifikation).
  • Technischer Zweck & Einordnung: Definition der Konfigurationsstruktur des Containers IKEIntegTransform innerhalb des TCP/IP-Stacks (AUTOSAR_CP_SWS_TcpIp, IPsec/IKEv2-Subsystem). Das Modell legt die zulässigen Integritätsalgorithmen (IKEv2 Transform Type 3 gemäß RFC 7296) zur Aushandlung von Security Associations (SA) fest und bildet die kryptografische Anbindung des IKE-Protokolls an den Crypto Service Manager (CSM) über symbolische Job-Referenzen ab.

2. Komponenten, Entitäten & Schnittstellen

  • IKEIntegTransform (EcucParamConfContainerDef):
  • Kardinalität: 1..* (mindestens eine Integritätstransformation muss im IKE-Stack konfiguriert sein; mehrere Instanzen zur Definition der Proposal-Listen möglich).
  • Repräsentiert die konkrete Parametrierung eines Integritätsprüfungs- und MAC-Verfahrens für IKEv2-SAs bzw. Child-SAs.

  • Referenzen & Schnittstellenbeziehungen:
  • IKEGenerateJobRef (EcucReferenceDef):
  • Ziel: CsmJob (1..*, Package Csm).
  • Attribut: requiresSymbolicNameValue = true.
  • Funktion: Verweist auf den CSM-Job zur Erzeugung von Integritätsprüfwerten/MACs (z. B. Authentifizierung ausgehender IKE-Nachrichten und Schlüsselableitungen).
  • IKEVerifyJobRef (EcucReferenceDef):
  • Ziel: CsmJob (1..*, Package Csm).
  • Attribut: requiresSymbolicNameValue = true.
  • Funktion: Verweist auf den CSM-Job zur Verifikation eingehender Integritätsprüfwerte (MAC-Prüfung zur Abwehr von Replay-/Manipulationsangriffen).

3. Dynamisches Verhalten & Sequenzablauf

Als statisches ECUC-Metamodell bildet das Diagramm keinen sequenziellen Ablauf direkt ab; die Laufzeitdynamik ergibt sich aus der IKEv2-Protokollabwicklung:

  1. Proposal-Aushandlung (IKE_SA_INIT / CREATE_CHILD_SA):
  • Der TCP/IP-IKE-Stack liest die konfigurierten IKEIntegTransform-Container aus und generiert entsprechende Proposal-Payloads gemäß RFC 7296 bzw. prüft eintreffende Gegenstellen-Proposals gegen die deklarierten IKETransformId-Instanzen.
  1. Kryptografische Ausführung via CSM:
  • Sendepfad: Berechnung des Integritätswerts erfolgt synchron oder asynchron über Csm_MacGenerate() bzw. Csm_JobExecute() unter Verwendung des via IKEGenerateJobRef referenzierten Jobs.
  • Empfangspfad: Eingehende Pakete werden über Csm_MacVerify() unter Verwendung des via IKEVerifyJobRef referenzierten Jobs validiert.
  1. Fehlerpfade:
  • Schlägt die CSM-Job-Ausführung fehl oder ist die Verifikation negativ, wird das Paket verworfen, der Security Association Setup abgebrochen und optional ein Fehler an das Det (Default Error Tracer) gemeldet.

4. Normative Relevanz & Entwickler-Hinweise

  • Anforderungsbezug: ECUC_IKE_00027 regelt die Konfigurationsanforderungen für Integritätstransformationen in AUTOSAR Classic IKEv2.
  • CSM-Konsistenz: Die referenzierten CsmJob-Instanzen müssen zwingend zum gewählten IKETransformId-Algorithmus und dessen Ausgabelänge passen (z. B. AES-CMAC mit 96-Bit-Truncation erfordert einen entsprechend konfigurierten CSM-Primitivesatz mit MAC-Generierung/-Verifikation im Crypto-Treiber/Crypto Interface).
  • Symbolische Namen: Durch requiresSymbolicNameValue = true müssen die Jobs zur Generierung und Verifikation im BSW-Modul-Code über generierte Symbolbezeichner (C-Makros aus der CSM-Konfiguration) aufgelöst werden.
  • Sicherheits- & Legacy-Hinweis: Algorithmen wie DES, MD5 und SHA-1 sind aus kryptografischer Sicht deprecated/unsicher; im Fahrzeugkontext (z. B. SecOC, IPsec nach UN R155 / ISO 21434) sollten primär moderne Algorithmen wie IKE_TRANSFORM_AUTH_HMAC_SHA2_256_128 oder IKE_TRANSFORM_AUTH_AES_CMAC_96 parametriziert werden.
