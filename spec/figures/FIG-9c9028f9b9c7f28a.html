1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt des AUTOSAR System Templates (AUTOSAR_TPS_SystemTemplate, PDU-Beschreibung im FIBEX-Modell, R4.2.2).
  • Technischer Zweck: Modellierung des PDU-Multiplexings/Packings von mehreren logischen PDUs (ContainedIPdu) in einen gemeinsamen Transportrahmen (ContainerIPdu).
  • Architektur-Einordnung: Dient als formale Entwurfsbasis für Kommunikationsstacks mit großen Frame-Kapazitäten (insbesondere CAN FD, FlexRay, Ethernet/SomeIP). Das Modell steuert im BSW-Stack (vor allem PduR, alternativ spezialisierte Module wie IpduM) das Packen, Puffern, Timen und Entpacken heterogener PDUs zur Bandbreitenoptimierung und Overhead-Reduktion.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Vererbungen
  • Pdu («FibexElement»):
    • Abstrakte Basisklasse aller Protocol Data Units.
    • Attribute: length [0..1] : Integer (statische PDU-Länge in Byte).
  • IPdu:
    • Spezialisierung von Pdu. Repräsentiert Interaktionsschicht-PDUs.
    • Komposition: Hält 0..1 Instanz von ContainedIPduProps über die Rolle +containedIPduProps.
  • ContainerIPdu:
    • Spezialisierung von IPdu. Repräsentiert die aggregierende Hüll-PDU.
    • Attribute:
      • containerTimeout [0..1] : TimeValue: Maximales Wartefenster bis zum Zwangsversand unvollständig gefüllter Container.
      • containerTrigger [0..1] : ContainerIPduTriggerEnum: Globales Auslöseverhalten für den Container.
      • headerType [1] : ContainerIPduHeaderTypeEnum: Pflichtangabe zum Header-Format der eingebetteten PDUs.
      • rxAcceptContainedIPdu [1] : RxAcceptContainedIPduEnum: Filterstrategie bei der PDU-Extraktion auf Empfangsseite.
      • thresholdSize [0..1] : PositiveInteger: Füllstandsschwelle in Bytes, bei deren Erreichen/Überschreiten der Container sofort ausgelöst wird.
      • unusedBitPattern [0..1] : PositiveInteger: Bitmuster zum Auffüllen ungenutzter Bereiche im Container.
  • ContainedIPduProps:
    • Eigenschafts-Container für eingebettete I-PDUs innerhalb eines Containers.
    • Attribute:
      • collectionSemantics [1] : ContainedIPduCollectionSemanticsEnum: Update- und Pufferstrategie (lastIsBest vs. queued).
      • headerIdLongHeader [0..1] : PositiveInteger: 32-Bit-ID bei Verwendung langer Header.
      • headerIdShortHeader [0..1] : PositiveInteger: 24-Bit-ID bei Verwendung kurzer Header.
      • offset [0..1] : PositiveInteger: Feste Byte-Offset-Position der Contained PDU innerhalb des Containers (relevant bei fester Platzierung ohne Header).
      • timeout [0..1] : TimeValue: Gültigkeits- bzw. Sammeltimeout der spezifischen Contained I-PDU.
      • trigger [0..1] : PduCollectionTriggerEnum: Legt fest, ob das Eintreffen dieser PDU den Container-Versand initiiert.
      • updateIndicationBitPosition [0..1] : PositiveInteger: Bitposition eines Update-Bits zur Erkennung neuer Daten.
  • PduTriggering («Identifiable»):
    • Abbildung einer PDU auf einen Kommunikationsport/Kanal.
    • Assoziationen:
      • Assoziation verweist auf genau 1 +iPdu (Pdu).
      • 1 ContainerIPdu aggregiert/referenziert 0..* +containedPduTriggering (PduTriggering).
Enumerationen
  • ContainerIPduHeaderTypeEnum:
    • shortHeader: Kompakter Header (24 Bit Header-ID + 8 Bit Längenfeld = 4 Bytes Overhead; Nutzlast max. 255 Bytes je Contained PDU).
    • longHeader: Erweiterter Header (32 Bit Header-ID + 32 Bit Längenfeld = 8 Bytes Overhead; für große PDUs/Ethernet).
    • noHeader: Kein Header je Contained PDU (statische Platzierung über Offset).
  • RxAcceptContainedIPduEnum:
    • acceptAll: Akzeptiert alle im Stream empfangenen Contained-Header (auch unbekannte IDs werden akzeptiert/überlesen).
    • acceptConfigured: Nur explizit im System konfigurierte Contained PDUs werden akzeptiert.
  • PduCollectionTriggerEnum:
    • always: Jedes Eintreffen dieser Contained I-PDU triggert sofort das Senden des Containers.
    • never: Das Eintreffen dieser Contained I-PDU löst keinen sofortigen Sendevorgang aus (Versand erfolgt zeit- oder schwellwertbasiert).
  • ContainerIPduTriggerEnum:
    • firstContainedTrigger: Das Eintreffen der ersten Contained PDU startet das Container-Sammelzeitfenster.
    • defaultTrigger: Standard-Triggerlogik für den Container.
  • ContainedIPduCollectionSemanticsEnum:
    • lastIsBest: Überschreibender Puffer; neuere Instanzen derselben PDU ersetzen ältere.
    • queued: FIFO-Warteschlange; alle eingehenden Instanzen werden sequentiell gesammelt.

3. Dynamisches Verhalten & Sequenzablauf

Sende-Pfad (TX-Aggregation / Packing)
  1. PDU-Anlieferung: Eine obere Schicht (COM, SecOC, Dcm) übergibt eine I-PDU via PduR_Transmit() an die Routing Engine.
  2. Klassifikation & Pufferung:
    • Ist der Zielpfad eine ContainerIPdu, prüft das verarbeitende Modul (PduR / IPDU-Multiplexer) ContainedIPduProps.
    • Bei collectionSemantics == lastIsBest wird ein bestehender Eintrag im TX-Container-Puffer aktualisiert. Bei queued wird die PDU an das Ende des Aggregationspuffers angehängt.
  3. Serialisierung: Voranstellung des Headers (shortHeader oder longHeader) mit der konfigurierten headerIdShortHeader bzw. headerIdLongHeader und der tatsächlichen DLC/Länge.
  4. Trigger-Prüfung:
    • Sofort-Trigger: Falls ContainedIPduProps.trigger == always oder ContainerIPduTriggerEnum == firstContainedTrigger, wird die ContainerIPdu unmittelbar an das Interface (CanIf, SoAd) weitergegeben.
    • Schwellwert-Trigger: Überschreitet die aggregierte Gesamtlänge thresholdSize, erfolgt sofortiger Push.
    • Zeitbasierter Trigger: Läuft der asynchrone Hardware-/Software-Timer containerTimeout oder das PDU-individuelle timeout ab, wird die ContainerIPdu mit dem aktuellen Füllstand asynchron gesendet.
Empfangs-Pfad (RX-Disaggregation / Unpacking)
  1. Container-Empfang: Die vollständige ContainerIPdu trifft über das untere Interface (<Bus>If_RxIndication()) im BSW-Stack ein.
  2. Header-Parsing: Der Byte-Stream wird sequentiell anhand des headerType geparst (Extraktion von ID und Längenfeld).
  3. Validierung & Filterung:
    • Stimmt die Header-ID mit einer bekannten containedPduTriggering überein, wird die Nutzlast extrahiert.
    • Ist die ID unbekannt: Bei acceptConfigured Abbruch bzw. PDU-Verwurf (ggf. Det-Meldung); bei acceptAll Weiterspringen um das Längenfeld zum nächsten Header.
  4. Dispatchen: Extrahierte Contained I-PDUs werden über PduR_<Target>RxIndication() an die jeweiligen Zielmodule verteilt.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (PduR / CAN FD / Ethernet):
    • Das Metamodell bildet 1:1 die Konfigurationscontainer PduRContainerIPdu und PduRContainedIPdu im BSW ab.
    • Konsistenz-Restriktion: Wenn headerType == shortHeader, muss zwingend headerIdShortHeader gesetzt sein (Bereich: 1 bis 2^24-1). Bei longHeader ist headerIdLongHeader Pflicht (Bereich: 1 bis 2^32-1). Mischbetrieb innerhalb eines Containers ist verboten.
  • Speicher- und Pufferallokation:
    • collectionSemantics == queued erzwingt im BSW-Generat statisch allokierte Ringpuffer (Multi-Element Queues). Entwickler müssen die maximale Queue-Tiefe gegen RAM-Verbrauch und Worst-Case-Latenz abgleichen.
    • lastIsBest minimiert RAM-Overhead (Single-Buffer), führt bei langsamen Buszyklen jedoch zum unbemerkten Verwerfen älterer Datenstände (Data Overwrite).
  • Echtzeit- und Latenz-Design:
    • Zeitkritische I-PDUs (z. B. Brems-/Lenkanforderungen) müssen zwingend auf trigger = always konfiguriert werden, um ein Verzögern durch containerTimeout zu unterbinden.
    • Unbedachte Kombinationen von großem thresholdSize und fehlendem containerTimeout können bei unvollständigen Daten zum Blockieren/Verhungern (Starvation) von Contained I-PDUs im Puffer führen.
