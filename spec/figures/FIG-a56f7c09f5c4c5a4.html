1. Diagrammtyp & Architektur-Kontext

Aktivitätsdiagramm / Flussdiagramm zur Spezifikation der SOME/IP-Nachrichtenvalidierung und des Fehlerbehandlungsverhaltens (Message Validation and Error Handling) innerhalb der AUTOSAR-Protokollspezifikation AUTOSAR_PRS_SOMEIPProtocol. Das Diagramm beschreibt den sequenziellen Prüfpfad, den ein SOME/IP-Stack beim Empfang einer SOME/IP-Nachricht über ein Transport-Socket (UDP oder TCP) durchläuft, bevor die Nachricht an die interne Verarbeitung übergeben oder verworfen wird.

2. Komponenten, Entitäten & Schnittstellen

  • Start-/Endzustände:
  • Receive SOME/IP Message and check depending on socket received on (Eingangspunkt)
  • SOME/IP Message Processing (Erfolgreiche Weiterleitung / reguläre Verarbeitung)
  • SOME/IP Error Processing (Fehlerverarbeitung)
  • Ignore SOME/IP Message / ErrorMessage bzw. Ignore SOME/IP Message (Verwerfen der Nachricht)
  • Entscheidungsknoten (Validierungsprüfungen):
  • Protocol Version Supported ?
  • Service ID OK?
  • Interface Version OK?
  • Method ID OK?
  • Message Type Supported ?
  • Message Type as Configured ?
  • Message Type = Error mit nachgelagerter Prüfung Return Code > 0x00 || < 0x20
  • Message Type = Response mit nachgelagerter Prüfung Client / Session ID Known?
  • Payload Parsable ?
  • Sub-Ablauf / Antwortverhalten (Answer_behavior):
  • Verzweigung Message Type = Request ?:
  • Zweig Yes: Send message with Message Type : ERROR
  • Zweig No: Ignore SOME/IP Message
  • Generierte Return-Codes bei Fehlern:
  • E_WRONG_PROTOCOL_VERSION (Protocol Version = 0x01 oder andere unterstützte Version)
  • E_UNKOWN_SERVICE (Protocol Version = wie empfangen)
  • E_WRONG_INTERFACE_VERSION (Protocol Version = wie empfangen)
  • E_UNKOWN_METHOD (Protocol Version = wie empfangen)
  • E_WRONG_MESSAGE_TYPE (Protocol Version = wie empfangen)
  • E_MALFORMED_MESSAGE (Protocol Version = wie empfangen)

3. Dynamisches Verhalten & Sequenzablauf

  1. Empfang: Die SOME/IP-Nachricht geht über den konfigurierten Socket ein.
  2. Kaskadierte Header-Validierung:
  • Ist die Protocol Version nicht unterstützt (No), springt der Kontrollfluss zum Answer_behavior mit Rückgabewert E_WRONG_PROTOCOL_VERSION.
  • Ist die Service ID unbekannt/ungültig (No), folgt Answer_behavior mit E_UNKOWN_SERVICE.
  • Ist die Interface Version ungültig (No), folgt Answer_behavior mit E_WRONG_INTERFACE_VERSION.
  • Ist die Method ID unbekannt (No), folgt Answer_behavior mit E_UNKOWN_METHOD.
  • Ist der Message Type generell nicht unterstützt (No), folgt Answer_behavior mit E_WRONG_MESSAGE_TYPE.
  • Entspricht der Message Type nicht der Konfiguration (No), folgt Answer_behavior mit E_WRONG_MESSAGE_TYPE.
  1. Typ-spezifische Pfade:
  • Wenn Message Type = Error: Es wird geprüft, ob Return Code > 0x00 || < 0x20 gilt. Ist dies wahr (True), geht die Nachricht in das SOME/IP Error Processing. Bei False wird geprüft, ob Client / Session ID Known? zutrifft; falls unbekannt (No), wird die Nachricht ignoriert (Ignore SOME/IP Message / ErrorMessage).
  • Wenn Message Type = Response: Es wird direkt geprüft, ob Client / Session ID Known? zutrifft. Falls nicht bekannt (No), wird die Nachricht ignoriert (Ignore SOME/IP Message / ErrorMessage).
  1. Payload-Parsing:
  • Bei bekanntem Client/Session-Kontext bzw. nach erfolgreicher Vorprüfung wird geprüft, ob die Nutzlast parsierbar ist (Payload Parsable ?).
  • Schlägt das Parsen fehl (No), wird Answer_behavior mit E_MALFORMED_MESSAGE aufgerufen.
  • Ist das Parsen erfolgreich (Yes), erfolgt der Übergang zu SOME/IP Message Processing.
  1. Ausführung von Answer_behavior:
  • Es wird geprüft, ob der ursprüngliche Nachrichtentyp ein Request war (Message Type = Request ?).
  • Falls ja, wird eine Fehlernachricht versendet (Send message with Message Type : ERROR) mit dem gesetzten Return-Code.
  • Falls nein (z. B. Notification, Fire&Forget oder Error), wird die Nachricht verworfen (Ignore SOME/IP Message), um Fehlerschleifen zu verhindern.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Handhabung von Fehlern: Antworten auf fehlerhafte Nachrichten dürfen ausschließlich dann gesendet werden, wenn die eingegangene Nachricht vom Typ REQUEST war; alle anderen Nachrichtentypen (Responses, Notifications, Errors) dürfen bei Fehlern nicht beantwortet, sondern müssen verworfen werden.
  • Header-Feld Protocol Version: Bei Versionsfehlern (E_WRONG_PROTOCOL_VERSION) setzt die Antwort die eigene unterstützte Protokollversion (0x01), während bei allen nachfolgenden Fehlern die Protokollversion der empfangenen Nachricht zurückgespiegelt wird.
  • Implementierungshinweis: Die Prüfung muss exakt in der dargestellten Reihenfolge implementiert werden, um Ressourcenverbrauch durch unnötiges Deserialisieren (Payload Parsing) bei ungültigen Headers oder unbekannten Services/Methoden zu vermeiden.
