1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (Metamodell-Ausschnitt des AUTOSAR System Template, TPS System Template, R4.1.3).
  • Technischer Zweck: Modellierung von logischen und physischen Endpunkten netzwerkbasierter IP-Kommunikation (ApplicationEndpoint). Es definiert die Entkopplung und Spezifikation von Transportprotokollen (L4), Applikations- und Übertragungsprotokollen (L5–L7 wie HTTP, RTP, IEEE 1722/AVB) sowie assoziierten Middleware-Diensten (Service Discovery, Remoting, Serialisierung).
  • Funktionale Einordnung: Basis für die Konfiguration des AUTOSAR Ethernet/TCP/IP-Stacks (TcpIp, SoAd – Socket Adaptor) und der Service-orientierten Kommunikation (SOME/IP über SomeIpXf, Sd bzw. AUTOSAR Client-Server-Calls).

2. Komponenten, Entitäten & Schnittstellen

Zentrale Entität
  • ApplicationEndpoint (erbt von Identifiable):
    • Repräsentiert die Adressierungsinstanz einer Applikations-Schnittstelle auf Netzwerkebene.
    • Attribut: priority : PositiveInteger [0..1] (VLAN/QoS-Priorisierung auf Socket-/Endpoint-Ebene).
Transportprotokoll-Hierarchie (TransportProtocolConfiguration)
  • TransportProtocolConfiguration (abstrakt):
    • Komposition von ApplicationEndpoint (+tpConfiguration : TransportProtocolConfiguration [0..1]).
    • Basisklasse für transportbezogene Parametrierungen.
  • GenericTp (Spezialisierung von TransportProtocolConfiguration):
    • Für proprietäre oder unspezifizierte Protokolle.
    • Attribute: tpTechnology : String, tpAddress : String [0..1].
  • TcpUdpConfig (abstrakt, Spezialisierung von TransportProtocolConfiguration):
    • Basis für standardisierte L4-IP-Protokolle.
  • UdpTp (Spezialisierung von TcpUdpConfig):
    • Enthält Komposition +udpTpPort 1 auf TpPort.
  • TcpTp (Spezialisierung von TcpUdpConfig):
    • Attribute: keepAlives : Boolean [0..1], naglesAlgorithm : Boolean [0..1] (Steuerung des Latenz-/Durchsatzverhaltens auf Socket-Ebene).
    • Enthält Komposition +tcpTpPort 1 auf TpPort.
  • TpPort:
    • Definiert Port-Eigenschaften: portNumber : PositiveInteger [0..1], dynamicallyAssigned : Boolean [0..1] (z. B. Ephemeral Ports für dynamische Client-Verbindungen).
  • RtpTp (Spezialisierung von TransportProtocolConfiguration):
    • Real-Time Transport Protocol (RFC 3550, z. B. Video/Audio-Streaming).
    • Attribut: ssrc : PositiveInteger (Synchronization Source Identifier).
    • Komposition: +tcpUdpConfig 1 zu TcpUdpConfig (bindet RTP an das darunterliegende UDP- oder TCP-Transportprotokoll).
  • HttpTp (Spezialisierung von TransportProtocolConfiguration):
    • HTTP-basierte Endpunkte (z. B. REST, Diagnose über IP/Web, Infotainment).
    • Attribute: protocolVersion : String, contentType : String [0..1], requestMethod : RequestMethodEnum [0..1], uri : UriString [0..1].
    • Komposition: +tcpTpConfig 1 zu TcpTp (HTTP erzwingt die Kopplung an einen TCP-Transport).
  • Ieee1722Tp (Spezialisierung von TransportProtocolConfiguration):
    • IEEE 1722 Transport Protocol (AVB / TSN Ethernet Audio Video Bridging).
    • Attribute: streamIdentifier : PositiveInteger, relativeRepresentationTime : TimeValue [0..1], subType : PositiveInteger [0..1], version : PositiveInteger [0..1].
Assoziierte Technologien (Middleware & Service-Layer)
  • DiscoveryTechnology:
    • Komposition: +discoveryTechnology 0..1 von ApplicationEndpoint.
    • Attribute: name : DiscoveryTechnologyEnum, version : String.
    • Werte (DiscoveryTechnologyEnum): bonjour, ssdp, dlna, some/ip, slp.
  • RemotingTechnology:
    • Komposition: +remotingTechnology 0..1 von ApplicationEndpoint.
    • Attribute: name : RemotingTechnologyEnum, version : String.
    • Werte (RemotingTechnologyEnum): ar_client_server, some/ip.
  • SerializationTechnology (Stereotyp/Kategorie: ARElement):
    • Assoziation (Referenz): +serializationTechnology 0..1 von ApplicationEndpoint.
    • Attribute: protocol : String, version : String (z. B. SOME/IP Transformer, Signals, ASN.1).
Enumerationen
  • RequestMethodEnum: get, post, head, put, delete, trace, options, connect.
  • DiscoveryTechnologyEnum: bonjour, ssdp, dlna, some/ip, slp.
  • RemotingTechnologyEnum: ar_client_server, some/ip.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

Als Metamodell-Strukturdiagramm bildet die Abbildung keine direkte Ausführungsreihenfolge ab. Die abgeleitete Ablaufdynamik im BSW-Stack gestaltet sich wie folgt:

  1. Stack-Initialisierung & Socket-Bindung:
    • Konfiguration aus ApplicationEndpoint wird vom Code-Generator in SoAd- und TcpIp-Parameter transformiert.
    • dynamicallyAssigned == false: TcpIp_Bind() bzw. TcpIp_TcpListen() erfolgt auf der definierten portNumber.
    • dynamicallyAssigned == true: Dynamische Zuweisung eines ephemeren Ports durch den IP-Stack bei Verbindungsaufbau.
  2. Service Discovery & Remoting-Aufbau:
    • Sofern DiscoveryTechnology (z. B. some/ip) und RemotingTechnology gesetzt sind, initiiert das BSW-Modul Sd (Service Discovery) die zyklische oder Event-getriebene Bekanntmachung (Offer/Find Service) des Endpunkts unter Verwendung des spezifizierten Transportprotokolls (UdpTp / TcpTp).
  3. Payload-Verarbeitungspfad:
    • Eingehende Pakete passieren L4 (TcpIp), werden via SoAd anhand von Port und IP gemappt, vom Service-Layer (SomeIpXf, Rte) deserialisiert (SerializationTechnology) und an die Zielapplikation/SWC dispatched.

4. Normative Relevanz & Entwickler-Hinweise

  • Generierungsartefakte (SoAd / TcpIp):
    • keepAlives und naglesAlgorithm in TcpTp steuern direkt Parameter im TcpIp-BSW-Modul (TcpIpKeepAlive, Nagle-Deaktivierung via TCP_NODELAY für harte Latenzanforderungen in der Echtzeit-Ethernet-Kommunikation).
  • Protokollrestriktionen:
    • HttpTp erzwingt eine 1:1-Relation auf TcpTp (+tcpTpConfig 1). HTTP über ungesichertes oder rein primitives UDP ist im Metamodell hier nicht vorgesehen.
    • RtpTp referenziert flexibel TcpUdpConfig 1, erlaubt somit sowohl RTP/UDP (Standardfall) als auch Interleaved RTP über TCP.
  • Service-Orientierung (SOME/IP):
    • Bei Auswahl von some/ip in RemotingTechnologyEnum und DiscoveryTechnologyEnum müssen ApplicationEndpoint-Ports konsistent mit den SWS-Vorgaben für SOME/IP (Standard-Port 30490 für Service Discovery) gehalten werden.
  • Separation of Concerns:
    • SerializationTechnology ist als eigenständiges ARElement modelliert und wird per Referenz verknüpft; dieselbe Serialisierungsvorschrift kann somit über mehrere ApplicationEndpoint-Instanzen wiederverwendet werden, während Transportkonfigurationen fest an den jeweiligen Endpunkt gebunden (komponiert) sind.
