1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt aus der AUTOSAR-System-Template-Spezifikation (AUTOSAR_TPS_SystemTemplate, Release R4.3.1).
  • Technischer Zweck: Formale Modellierung der portspezifischen Quality-of-Service- (QoS-) und Puffer-Architektur von Ethernet-Switches (CouplingPort) gemäß IEEE 802.1Q.
  • Architektonische Einordnung: Bildet die Grundlage im System-Design (ARXML) für das Ingress-Prioritäten-Remapping, die Traffic-Class-Zuordnung sowie die Dimensionierung und Zuordnung der Hardware-Egress-FIFOs. Dient als normativer Input für die Generierung der BSW-Konfiguration des Ethernet-Switch-Treibers (EthSwt) in Classic AUTOSAR sowie entsprechender Switch-/TSN-Treiber in Adaptive AUTOSAR.

2. Komponenten, Entitäten & Schnittstellen

  • CouplingPortDetails:
  • Zentraler Modellierungs-Container für hardwarenahe Detailkonfigurationen eines Ethernet-Switch-Ports.
  • EthernetPriorityRegeneration («Referrable»):
  • Realisiert die Priority Regeneration Table nach IEEE 802.1Q (Abschnitt 6.9).
  • Attribute:
  • + ingressPriority : PositiveInteger: Empfangene VLAN-PCP-Priorität (0–7).
  • + regeneratedPriority : PositiveInteger: Neu zugewiesene interne Priorität (0–7).
  • CouplingPortTrafficClassAssignment («Referrable»):
  • Bildet Prioritäten auf Scheduling-Verkehrsklassen ab (Priority to Traffic Class Mapping nach IEEE 802.1Q).
  • Attribute:
  • + priority : PositiveInteger [0..8]: Zu mappende Priorität (PCP / regenerierte Priorität).
  • + trafficClass : PositiveInteger: Ziel-Traffic-Class-Index.
  • CouplingPortStructuralElement («Identifiable», abstrakt):
  • Abstrakte Basiseinheit für physikalische und logische Hardware-Substrukturen eines Switch-Ports.
  • CouplingPortFifo:
  • Konkrete Spezialisierung (Generalization auf CouplingPortStructuralElement); repräsentiert eine Hardware-Puffer-Warteschlange (Egress-FIFO).
  • Attribute:
  • + assignedTrafficClass : PositiveInteger [0..8]: Traffic-Class-Nummern (bis zu 8), die durch diese FIFO gepuffert werden.
  • + minimumFifoLength : PositiveInteger [0..1]: Mindestgröße des Puffers (z. B. in Byte oder Frames) zur Sicherstellung von Burst-Toleranzen.
  • Multiplizitäten & Assoziationen:
  • CouplingPortDetails $\blacklozenge\xrightarrow{0..8}$ +ethernetPriorityRegeneration: Bis zu 8 Mappings (vollständige Abdeckung der 3-Bit-PCP-Werte 0..7).
  • CouplingPortDetails $\blacklozenge\xrightarrow{0..8}$ +ethernetTrafficClassAssignment: Bis zu 8 Mappings von Prioritäten auf interne Traffic Classes.
  • CouplingPortDetails $\blacklozenge\xrightarrow{1..*}$ +couplingPortStructuralElement: Jeder Port besitzt mindestens ein strukturelles Hardware-Element (typischerweise mehrere CouplingPortFifo-Instanzen).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert einen statischen Konfigurationsbaum, definiert jedoch die deterministische Ingress-zu-Egress-Verarbeitungskette für jeden Ethernet-Frame im Switch-Silizium:

```

[ Ingress Frame mit VLAN-Tag (PCP) ]

│

▼

[ 1. EthernetPriorityRegeneration ] ──> Wandelt ingressPriority in regeneratedPriority

│

▼

[ 2. CouplingPortTrafficClassAssignment ] ──> Mappt regeneratedPriority auf trafficClass

│

▼

[ 3. CouplingPortFifo Selection ] ──> Ordnet Frame der FIFO mit identischer assignedTrafficClass zu

│

▼

[ Hardware-Scheduling & Egress ] (Strict Priority / CBS / DWRR)

```

  1. Ingress Priority Regeneration: Bei Empfang eines 802.1Q-getaggten Frames wird dessen Priority Code Point (ingressPriority) anhand der Port-Regeneration-Tabelle auf eine interne regeneratedPriority umgeschrieben (Isolierung oder Harmonisierung fremder Netzwerkdomänen).
  2. Traffic Class Mapping: Die regenerierte Priorität wird linear einer Traffic Class (trafficClass) zugewiesen.
  3. Queue-Zuweisung: Anhand von CouplingPortFifo.assignedTrafficClass wird der Frame in die zuständige Hardware-FIFO des Egress-Ports eingesteuert.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (EthSwt / MCAL):
  • Diese ARXML-Strukturen werden im Stack-Generator direkt auf Parameter des Moduls EthSwt abgebildet (z. B. EthSwtPortPriorityRegeneration, EthSwtPortTrafficClassAssignment, EthSwtPortBufferConfiguration).
  • Hardware-Einschränkungen & Validierung:
  • Switch-ASICs besitzen eine hardwareseitig limitierte Anzahl physischer Queues (meist 4 oder 8). Konfiguriert das Systemmodell mehr CouplingPortFifo-Instanzen als Hardware-Queues vorhanden sind, schlägt die Validierung im Generator fehl.
  • Werden mehrere trafficClass-Werte derselben CouplingPortFifo zugewiesen ([0..8]), teilen sich unterschiedliche Prioritätsstufen denselben Hardware-Puffer. Dies erfordert nachgelagert die exakte Dimensionierung von minimumFifoLength, um Head-of-Line-Blocking oder Pufferüberläufe unter Last zu verhindern.
  • Vollständigkeitsprüfung:
  • Die Prioritätsabbildung muss für alle im System auftretenden PCP-Werte (0–7) lückenlos definiert sein. Nicht abgedeckte Werte führen je nach Switch-Hardware zu Default-Klassifizierungen (meist Traffic Class 0) oder unzulässigem Verwerfen (Drop) von Frames.
