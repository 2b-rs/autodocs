1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML 2.0 Composite Structure Diagram (Kompositionsstrukturdiagramm) auf VFB- bzw. RTE-Ebene.
  • Funktionale Einordnung: Dargestellt ist die strukturelle Anbindung von Anwendungs-Software-Komponenten (SW-Cs) der Applikationsschicht an den Watchdog Manager (:WdgM, BSW System Service Layer) im Standard AUTOSAR R3.0.7.
  • Technischer Zweck: Spezifikation der Service-Port-Kopplung ausschließlich für den Überwachungsmechanismus Alive Supervision (zyklische Aktivitätsüberwachung). Es illustriert, wie mehrere Supervised Entities (SE) innerhalb einzelner und mehrfach instanziierter Komponenten-Typen auf diskrete Service-Ports des WdgM abgebildet werden.

2. Komponenten, Entitäten & Schnittstellen

  • Komponenten-Instanzen («swComponentPrototype»):
    • swc1: SWC Type A und swc2: SWC Type A: Zwei separate Instanzen desselben Komponenten-Typs (SWC Type A).
    • swc3: SWC Type B: Instanz eines zweiten Komponenten-Typs (SWC Type B).
    • :WdgM: BSW-Service-Komponente (Watchdog Manager als Service-Instanz).
  • Ports & Schnittstellen:
    • Required Ports (R-Ports, Socket-Notation):
      • swc1: Ports se1 / se1 und se2 / se2 (zwei logisch getrennte Supervised Entities).
      • swc2: Ports se1 / se1 und se2 / se2 (zwei logisch getrennte Supervised Entities in der zweiten Instanz).
      • swc3: Port se / se (eine einzelne Supervised Entity).
    • Provided Ports (P-Ports, Lollipop-Notation):
      • :WdgM: Bietet dedizierte Instanz-Service-Ports alive000 / alive000, alive001 / alive001, alive002 / alive002, alive003 / alive003 und alive004 / alive004.
    • Interface-Typ: WdgM_LocalSupervision (standardisiertes AUTOSAR Client-Server-Interface).
  • Kardinalitäten & Beziehungen:
    • Strikte 1:1-Assembly-Verbindungen zwischen je einem R-Port einer Supervised Entity und einem eindeutigen P-Port des WdgM.
    • Fünf Supervised Entities führen zu exakt fünf getrennten WdgM-Service-Ports.

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger & Aufruf (SW-C-Ebene):
    • Ein zyklisches Runnable innerhalb einer Supervised Entity führt seine Aufgabe aus und ruft über den konfigurierten R-Port die synchrone Client-Server-Operation auf: Rte_Call_<port>_UpdateAliveCounter() (R3.0-Signatur).
  2. RTE-Routing:
    • Die RTE empfängt den Aufruf und leitet ihn an den BSW-Service weiter. Die Port-Zuordnung (alive000–alive004) substituiert die Notwendigkeit, dass die SW-C eine globale SupervisedEntityId kennen muss. Die RTE injiziert die konfigurierte ID als PortDefinedArgumentValue.
  3. Zähler-Inkrementierung (WdgM):
    • Der WdgM empfängt den Aufruf und inkrementiert atomar den Alive-Counter der adressierten SE.
  4. Zyklische Auswertung (WdgM_MainFunction):
    • Die periodische Hauptfunktion des WdgM evaluiert am Ende des Überwachungszyklus (WdgMSupervisionCycle), ob die Counter-Werte innerhalb des konfigurierten Toleranzfensters (WdgMMinMargin bis WdgMMaxMargin) liegen.
  5. Fehlerpfad & Statusübergang:
    • Bei Unter- oder Überschreitung: Transition des lokalen Status der betroffenen SE (WDGM_LOCAL_STATUS_FAILED bzw. EXPIRED).
    • Eskalation an das DEM (Event-Setzung) und Verweigerung des Triggerns des Hardware-Watchdogs über das Watchdog Interface (WdgIf).

4. Normative Relevanz & Entwickler-Hinweise

  • Multi-Instanziierung (SWC Type A): Da swc1 und swc2 denselben Typ teilen, darf im SW-C-Code keine hardkodierte Entitäts-ID vorliegen. Die Unterscheidung erfolgt rein instanzbasiert über den RTE-Port-Kontext.
  • Port-Defined Argument Values (BSW-Integration): Der Integrator muss den WdgM so konfigurieren, dass jeder P-Port (alive00x) auf die interne C-API WdgM_UpdateAliveCounter(WdgM_SupervisedEntityIdType SEID) gemappt wird, wobei die SEID über die RTE-Generierung an den Port gebunden wird.
  • Granularität: Mehrere Supervised Entities innerhalb einer SW-C (wie se1 und se2 in SWC Type A) erfordern getrennte Ports und verursachen separaten Monitoring-Overhead im WdgM-RAM (je ein Zähler pro SE).
  • Reentranz: UpdateAliveCounter wird potenziell nebenläufig aus unterschiedlichen Task-Kontexten (OS-Tasks unterschiedlicher Priorität) aufgerufen und muss im WdgM reentrant bzw. interrupt-sicher implementiert sein.
