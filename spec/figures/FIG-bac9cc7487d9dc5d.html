1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt (AUTOSAR ECUC Parameter Definition Metamodel gemäß AUTOSAR_TPS_ECUConfiguration, Release R4.1.3).
  • Technischer Zweck: Formale Definition des Konfigurationsschemas für die ECU-Hardware-Ressourcen im Basissoftware-Modul EcuC. Es dient als Bindeglied zwischen der systemweiten Hardware-Topologiebeschreibung (ECU Resource Template) und der BSW-/OS-Konfiguration zur statischen Allokation von Multicore-Prozessorressourcen.

2. Komponenten, Entitäten & Schnittstellen

  • Metaklassen & Konfigurationscontainer:
    • EcucHardware (: EcucParamConfContainerDef):
      • Herkunft: Modul EcuC.
      • Multiplizität: lowerMultiplicity = 1, upperMultiplicity = 1.
      • Wurzelcontainer für die Beschreibung hardwarespezifischer BSW-Eigenschaften auf Steuergeräteebene.
    • EcucCoreDefinition (: EcucParamConfContainerDef):
      • Multiplizität: lowerMultiplicity = 1, upperMultiplicity = *.
      • Übergeordneter Container: EcucHardware via Aggregation (+subContainer). Repräsentiert jeden einzelnen Prozessorkern im System (mindestens ein Kern, 1 bis n Kerne).
  • Konfigurationsparameter & Referenzen:
    • EcucCoreId (: EcucIntegerParamDef):
      • Assoziation: Teil von EcucCoreDefinition via Aggregation (+parameter).
      • Wertebereich: min = 0, max = 65535 (2^16-1).
    • EcucCoreHwRef (: EcucForeignReferenceDef):
      • Assoziation: Teil von EcucCoreDefinition via Aggregation (+reference).
      • Multiplizität: lowerMultiplicity = 0, upperMultiplicity = 1.
      • Zieltyp: destinationType = HW-ELEMENT.
      • Zielentität: Verweist auf HwElement aus dem Paket Ecu Resource Template (stereotypisiert als ARElement, HwDescriptionEntity).

3. Dynamisches Verhalten & Sequenzablauf

  • Metamodell-Natur: Kein Laufzeitverhalten im Steuergerät; statische Konfigurations- und Generierungszeit-Semantik (Design-Time / Generation-Time).
  • Generierungs- und Mapping-Workflow:
    1. Hardware-Extraktion: Einlesen der physischen Rechenkerne aus dem System Description / ECU Resource Template (HwElement).
    2. Instanziierung: Anlegen von EcucCoreDefinition-Instanzen unter EcucHardware für jeden aktiven Prozessorkern.
    3. ID-Zuweisung & Verknüpfung: Belegung von EcucCoreId mit dem logischen Core-Index (0-basiert) und Setzen der Fremdreferenz EcucCoreHwRef auf das korrespondierende HwElement.
    4. Artefakt-Generierung: Erzeugung der statischen BSW-Header (insb. Os_Cfg.h, Rte_Cfg.h), in denen EcucCoreId in C-Makros (z. B. OS_CORE_ID_<CoreName>) aufgelöst wird.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Referenzen:
    • ECUC_EcuC_00056: Spezifikation des Containers EcucHardware.
    • ECUC_EcuC_00057: Spezifikation des Untercontainers EcucCoreDefinition.
    • ECUC_EcuC_00059: Spezifikation von EcucCoreId und EcucCoreHwRef.
  • Auswirkungen auf Stack-, OS- und Treiber-Entwickler:
    • Multicore-Zuweisung: EcucCoreId ist der normative Identifikator für die Zuweisung von OS-Applikationen (OsApplicationCoreAssignment), Tasks, ISRs, Schutzzonen und BSW-Modulinstanzen (Core-spezifische Main-Functions, z. B. im BswM oder Com).
    • C-Code-Generierung (symbolicNameValue = true): Generatoren müssen für jeden EcucCoreDefinition-Container ein konsistentes C-Makro erzeugen, das direkt im C-Code (z. B. für GetCoreID()-Vergleiche im OS) verwendet werden kann.
    • Metamodell-Grenzüberschreitung (EcucForeignReferenceDef): Die Referenz EcucCoreHwRef verlässt das reine ECUC-Schema und zeigt in das System-Template (EcuResourceTemplate::HwElement). Konfigurationseditoren und Validierungswerkzeuge müssen die referenzielle Integrität über diese Dokumentgrenze hinweg sicherstellen.
    • Multiplizität 0..1 bei EcucCoreHwRef: Die Verknüpfung zum Hardware-Template ist syntaktisch optional. In reinen BSW-Generierungs-Setups ohne vollständiges ECU Resource Template genügt EcucCoreId zur BSW-Parametrierung; für automatisierte System-Validierungen und Mapping-Prüfungen ist EcucCoreHwRef jedoch zwingend erforderlich.
