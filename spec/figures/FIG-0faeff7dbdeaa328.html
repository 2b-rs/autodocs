1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology / SPEM 2.0 (Software & Systems Process Engineering Metamodel) Aktivitäts- und Prozesszerlegungsdiagramm (Activity Decomposition / Use Case Breakdown).
  • Technischer Zweck: Spezifikation des standardisierten Ablaufs zur Integration von Basissoftware-Diensten (BSW-Services wie NvM, Dem, ComM, WdgM, FiM, EcuM) mit Anwendungs-Software-Komponenten (Application SWCs) im Rahmen der AUTOSAR Classic Platform (R4.0.3).
  • Systemeinordnung: Definiert die methodische Schnittstelle zwischen komponentenbasierter Softwareentwicklung (VFB/SWC-Ebene) und ECU-spezifischer BSW-/RTE-Integration. Es formalisiert das Muster der Service Needs und Service Ports zur Entkopplung der Applikation von der BSW-Implementierung.

2. Komponenten, Entitäten & Schnittstellen

Übergeordneter Use Case & Verbundaktivitäten
  • Components and Services: Wurzel-Anwendungsfall (SPEM Use Case).
  • Add Service Ports and Service Needs: Zusammengesetzte Aktivität zur Modellierung und Implementierung der Dienst-Schnittstellen auf SWC-Ebene.
  • Connect and Configure Service Module on ECU: Zusammengesetzte Aktivität zur ECU-spezifischen Parametrierung, BSW-Generierung und RTE-Kopplung.
Stereotypen & Modellbeziehungen
  • «nesting»: Hierarchische SPEM-Strukturierung (Dekonstruktion des Use Cases in Aktivitäten und elementare Tasks).
  • «predecessor»: Gerichtete Kontroll- und Datenfluss-Abhängigkeit; Add Service Ports and Service Needs fungiert als zwingender Vorgänger für Connect and Configure Service Module on ECU.
Elementare Tasks (Blattknoten)
  1. Zugeordnet zu Add Service Ports and Service Needs:
    • Define VFB Application Software Component (Rolle: +Add Service Ports to Atomic Software Component): Modellierung typisierter Port-Prototypen (RPortPrototype / PPortPrototype) mit PortInterface (z. B. Client-Server-Interface mit Kennzeichnung isService = true).
    • Define Atomic Software Component Internal Behavior (Rolle: +Add Service Needs to Atomic Component): Deklaration formaler Dienstbedarfe (ServiceNeed, z. B. NvMServiceNeed, DiagnosticEventNeeds, CryptoServiceNeeds) im SwcInternalBehavior.
    • Generate Atomic Software Component Contract Header Files (Rolle: +Re-generate Contract Header Files with Service Intefaces): Generierung der typisierten RTE-Contract-Header (Rte_<swc>.h) auf Basis der Service-Port-Signaturen.
    • Implement Atomic Software Component (Rolle: +Re-Implement Atomic Software Component with Service Ports): C-Code-Implementierung der Runnable Entities unter Verwendung der neuen Service-APIs (Rte_Call_<p>_<o>, Rte_Result_<p>_<o>).
  2. Zugeordnet zu Connect and Configure Service Module on ECU:
    • Generate Base Ecu Configuration: Automatisiertes Vorbelegen bzw. Updaten von BSW-Parametern (EcucDescription) anhand der aus den SWC-ARXMLs aggregierten ServiceNeeds.
    • Generate BSW Source Code: Generierung modulspezifischer Konfigurationstabellen und Quellcodedateien (<Module>_Cfg.h, <Module>_Cfg.c, z. B. NvM_Cfg.c).
    • Create Service Component: Bereitstellung/Generierung der formalen Software-Komponenten-Deskriptoren für die BSW (ServiceComponentType / ServiceProxyComponentType).
    • Generate RTE: Finale Generierung der Laufzeitumgebung (Verbindung von SWC-Ports und Service-Component-Ports via AssemblySwConnector, Generierung des RTE-C-Codes und der Task-Mappings).

3. Dynamisches Verhalten & Sequenzablauf

Der Workflow erfolgt streng zweiphasig mit Vorwärtsabhängigkeit:

[SWC-Ebene: Add Service Ports and Service Needs]
   1. Define VFB Ports (R/P-Ports mit Service-Interface)
   2. Define Internal Behavior (Zuordnung ServiceNeeds: z. B. Blocklänge, Recovery-Strategie)
   3. Generate Contract Headers (RTE Contract Phase -> Rte_<swc>.h)
   4. Re-Implement C-Code (Integration Rte_Call / Rte_Read)
                  │
                  ▼ «predecessor» (Übergabe exportierter SWC Description ARXMLs)
[ECU-Ebene: Connect and Configure Service Module on ECU]
   5. Generate Base Ecu Configuration (Import ServiceNeeds -> BSW-Parametrierung)
   6. Generate BSW Source Code (Code-Generatoren für NvM, Dem, etc.)
   7. Create Service Component (ARXML-Repräsentation der BSW-Services)
   8. Generate RTE (Generierung Glue-Code: SWC <-> Service Component)
  • Trigger: Anforderung einer Applikations-SWC an Plattformdienste (z. B. persistente Datenspeicherung, Fehlereintrags-Meldung, Schlafanforderung).
  • Synchroner vs. asynchroner Pfad:
    • Client-Server-Calls zu BSW-Diensten (z. B. NvM_ReadBlock) werden typischerweise über synchrone Client-Server-Ports modelliert, können aber auf BSW-Ebene asynchron verarbeitet werden (Rückmeldung via JobEnd-Notification-Ports/Callbacks).
    • Sender-Receiver-Services (z. B. Fahrzeugzustände via Mode Switch Interfaces / ComM) arbeiten entkoppelt über den RTE-Statuspuffer.

4. Normative Relevanz & Entwickler-Hinweise

  • Kapselung (Strict RTE Boundary): Applikations-Entwickler dürfen keine BSW-Header (z. B. NvM.h, Dem.h) direkt einbinden oder BSW-C-APIs aufrufen. Sämtliche Dienstzugriffe müssen ausnahmslos über generierte RTE-APIs (Rte_Call_<Port>_<Operation>) laufen.
  • Inversion of Configuration Control (ServiceNeeds): Der BSW-Integrator konfiguriert Dienste nicht rein manuell. ServiceNeeds stellen einen verbindlichen Vertrag dar: Ein NvMServiceNeed erzwingt die Existenz eines korrespondierenden NvMBlockDescriptor im BSW-Modell.
  • Toolchain-Determinismus:
    • Änderungen an Service-Ports oder Service-Needs in der SWC erfordern zwingend einen Re-Run des RTE-Generators in der Contract Phase.
    • Konfigurationswerkzeuge müssen einen Drei-Wege-Merge (Upstream-Update) beherrschen, um bestehende BSW-Konfigurationen bei Re-Import aktualisierter ServiceNeeds nicht zu korrumpieren.
  • Standardized Interfaces vs. Standardized AUTOSAR Interfaces: Service-Komponenten nutzen Standardized AUTOSAR Interfaces (RTE-vermittelt, syntaktisch identisch zu Standard-VFB-Ports), im Gegensatz zu den hardwarenahen Standardized Interfaces (direkte C-Funktionsaufrufe zwischen BSW-Modulen).
