1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / ECUC-Metamodell-Ausschnitt (AUTOSAR BSW Parameter Configuration Definition).
  • Architektur-Kontext: AUTOSAR Classic Platform ab Release R20-11 (AUTOSAR_SWS_SoftwareClusterConnection, SwCluC).
  • Funktionaler Zweck: Modellierung der BSW-Proxy-Konfiguration für den nichtflüchtigen Speicher (NvM – Non-Volatile Memory Manager) zur Realisierung entkoppelter, partitionierter Software-Cluster (SoftwareCluster). Das Diagramm definiert die Socket-Infrastruktur (SwCluCNvMBaseSocket), über welche ein NvM-Proxy innerhalb einer Anwendungs-Partition (EcucPartition) NvM-Service-Anfragen bündelt, an die Host-/Satellite-Infrastruktur weiterleitet und an clusterweite Systemressourcen bindet.

2. Komponenten, Entitäten & Schnittstellen

#### ECUC-Konfigurationscontainer (EcucParamConfContainerDef)

  • SwCluCNvMProxy [0..1]:
  • Zentraler Konfigurationscontainer für den NvM-Proxy im Software Cluster Connection Modul.
  • Aggregiert als +subContainer mindestens einen Base-Socket.
  • SwCluCNvMBaseSocket [1..*]:
  • Kernentität für den partitions- bzw. clusterspezifischen Kommunikationsendpunkt des NvM-Proxies.
  • Kann mehrfach instanziiert werden (z. B. pro Client-Partition oder Core).
  • EcucPartition [0..] (from EcucPartition)*:
  • Repräsentiert die OS-/BSW-Partition, in deren Kontext der NvM-Proxy-Socket instantiiert und ausgeführt wird.

#### Parameter & Referenzen

  • SwCluCNativeBswApi (EcucBooleanParamDef) [0..1] (from ProxyModules):
  • Default-Wert: false.
  • Steuert, ob der Proxy die native Standard-C-API des NvM (NvM_ReadBlock(), NvM_WriteBlock() etc.) für die Applikation/SWC in der lokalen Partition direkt bereitstellt oder ob der Zugriff rein über Rte/SwCluC-spezifische Service-Ports erfolgt.
  • SwCluCProxyEcucPartitionRef (EcucReferenceDef) [1..1] (from ProxyModules):
  • Typisierte Referenz (+destination) auf die Ziel-EcucPartition. Bindet den Base-Socket fest an den Speicherschutz- und Task-Kontext einer Partition.
  • SwCluCNvMProxyUsedSatelliteRef (EcucReferenceDef) [1..1]:
  • Referenziert via +destination die zugeordnete Gegenstelle (SwCluCNvMBaseSocket des Satelliten bzw. Host-Sockets), um die Peer-to-Peer-Bindung für den IPC-Transport festzulegen.
  • SwCluCResourceRef (EcucForeignReferenceDef) [1..1] (from ProxyModules):
  • Verweist systemweit (destinationType = CP-SOFTWARE-CLUSTER-SERVICE-RESOURCE) auf das System-Metamodell der Service-Ressource.

#### ARXML-Systemmodell (CP Software Cluster Resource Pool)

  • SoftwareCluster::CpSoftwareClusterResource (abstrakt, «Identifiable»):
  • Basisklasse für Cluster-Ressourcen.
  • Attribute:
  • globalResourceId: PositiveInteger [0..1] – Systemweit eindeutige Ressourcen-ID.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches ECUC-Metamodell handelt, leitet sich hieraus folgender deterministischer Laufzeitpfad ab:

```

[SWC / Application in Partition A]

│

▼ (NvM API Call via RTE/Direct C-API)

[SwCluCNvMProxy / Base Socket (Partition A)]

│

▼ (Marshalling & Inter-Partition/Inter-Core Transfer via IOC / IPC)

[SwCluC Satellite / NvM Host Core]

│

▼ (Standard NvM Job Queue)

[NvM Core -> MemIf -> Fee/Ea -> Fls/Eep]

```

  1. Job-Triggering: Eine SWC in einer Applikations-Partition ruft einen NvM-Service auf (z. B. NvM_ReadBlock).
  2. Proxy-Abfangung:
  • Bei SwCluCNativeBswApi == true wird der Call direkt vom lokalen SwCluC-Stub abgefangen.
  • Der Stub nutzt die Konfiguration des SwCluCNvMBaseSocket, um Kontext, Pufferadresse und globalResourceId zu verifizieren.
  1. Inter-Partition-Transport (asynchron):
  • Der Proxy serialisiert die Parameter und leitet den Auftrag über den konfigurierten Kanal (SwCluCNvMProxyUsedSatelliteRef) an den NvM-Host/Satellite weiter.
  • Synchrone Rückgabe an die Applikation: Status E_OK bzw. E_NOT_OK (Prüfung, ob Job in Proxy-Warteschlange akzeptiert wurde).
  1. Asynchrone Abarbeitung & Callback:
  • Nach physischer Abarbeitung im NvM-Core sendet der Satellite das Job-Ergebnis per Cross-Partition-Interrupt/IOC an den Proxy-Socket zurück.
  • Der Proxy triggert das konfigurierte Callback (SingleBlockCallback / RTE-Event) innerhalb des Kontexts der referenzierten EcucPartition.

4. Normative Relevanz & Entwickler-Hinweise

  • ECUC_SwCluC_00056 & Partitionierung: Entwickler müssen sicherstellen, dass pro Applikations-Partition mit NVRAM-Bedarf genau eine Instanz von SwCluCNvMBaseSocket angelegt und via SwCluCProxyEcucPartitionRef eindeutig verknüpft wird. Fehlende Zuordnungen führen zu MPU/OS-Access-Violations beim BSW-Zugriff.
  • API-Kompatibilität (SwCluCNativeBswApi):
  • Wenn Legacy-SWCs oder BSW-Module in einem ausgelagerten Software-Cluster portiert werden, die direkte Header-Inklusionen (#include "NvM.h") erwarten, muss dieses Flag auf true gesetzt werden.
  • Bei reiner AUTOSAR-Port-basierter Kommunikation (Client/Server-Interfaces über RTE) bleibt es auf false, um Header-Kollisionen und inkonsistente Typ-Redefinitionen im Cluster-Build zu vermeiden.
  • Link- & Speicher-Isolation:
  • Die Datenpuffer für NvM-Lese-/Schreiboperationen müssen in Shared-RAM-Sektionen liegen, die von der jeweiligen EcucPartition und dem NvM-Kern via MPU/OS-Application-Berechtigungen les- bzw. beschreibbar sind.
  • Generatoren leiten aus SwCluCResourceRef und globalResourceId die Routing-Tabellen ab; fehlende IDs im System-Deskriptor führen zu Generator-Fehlern (E_SYS_RES_NOT_FOUND).
