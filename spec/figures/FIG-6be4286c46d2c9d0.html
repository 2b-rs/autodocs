3. Dynamisches Verhalten & Sequenzablauf

  1. Manifest-Definition & Deployment-Allokation (parallel/entkoppelt ausführbar):
  • Ausführungskonfiguration: Define Execution Manifest fusioniert architekturelle Vorgaben aus der Process Design Description mit HW-spezifischen Maschinenressourcen aus dem Machine Manifest. Es erzeugt die Function Group Configuration (State-Management-Zuordnung) und die Process Configuration (UID/GID, Scheduling-Policies, Core-Affinitäten, Startup-Dependencies) innerhalb des Execution Manifest.
  • Kommunikationskonfiguration: Create or Finalize Service Instance Manifest konkretisiert die logischen Schnittstellen der Service Instance Description mit transportspezifischen Parametern (z. B. SOME/IP Instance-IDs, Service-IDs, TCP/UDP-Ports, Multicast-Adressen, E2E-Protections).
  1. Synthese des Software-Clusters:
  • Execution Manifest und Service Instance Manifest fließen über «contributes» in die Software Cluster Description ein. Diese bündelt sämtliche Manifeste eines zusammenhängend versionierten und aktualisierbaren Softwarepakets für das Update and Configuration Management (UCM).
  1. Build & Code-Generierung (Build SW for test environment):
  • Verarbeitet die Quelldateien der Adaptive Software Implementation zusammen mit der Adaptive Software Build Configuration.
  • Bindet Generatoren ein, um Adaptive Software Glue Code bereitzustellen bzw. zu kompilieren («inoutput»).
  • Verlinkt die Implementierung gegen die AUTOSAR Runtime for Adaptive Applications (ARA) und generiert das lauffähige Adaptive Software Binary («output»).

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Design und Deployment: Entwickler von Applikationen (Adaptive Applications) definieren Services und Prozesse rein abstrakt. Erst der Cluster-Integrator bindet Prozesse an reale Hardware-Gegebenheiten (Machine Manifest) und Service-Instanzen an reale Netzwerk-Endpunkte.
  • Execution Management (EM) Konformität:
  • Das resultierende Execution Manifest ist strikt bindend für den POSIX-Startprozess durch das Execution Management.
  • Fehlende oder inkonsistente Verweise in der Function Group Configuration führen dazu, dass Prozesse beim State-Wechsel der Machine/FunctionGroup durch EM nicht gestartet oder hart terminiert (SIGKILL) werden.
  • Communication Management (CM / ara::com):
  • Die Finalisierung des Service Instance Manifest erfordert exakte Übereinstimmung mit den Network-Bindings des Gesamtfahrzeugs (FIBEX / System Description).
  • Der Adaptive Software Glue Code erzwingt die Typkompatibilität zwischen generiertem Proxy/Skeleton-Interface und den C++-Typen der Anwendung.
  • Build-Pipeline-Integration:
  • Die Trennung von Adaptive Software Build Configuration und Glue-Code-Generierung bedingt eine zweistufige CI/CD-Toolchain: Manifest-Validierung $\rightarrow$ Generierung des Glue-Codes $\rightarrow$ Cross-Kompilierung der Binaries gegen die Ziel-Toolchain.
