1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Timing- und Preemption-Ablaufdiagramm (Sequenz-/Zustandsdarstellung über einer diskreten Zeitachse mit Speicherwertverlauf).
  • Architektur-Kontext: AUTOSAR Classic Platform (CP), RTE-Spezifikation (AUTOSAR_SWS_RTE, Kapitel Runtime Data Consistency).
  • Technischer Zweck: Exemplarische Veranschaulichung des Fehlermusters „Lost Update“ (Dateninkonsistenz durch Read-Modify-Write-Race-Condition). Das Diagramm dient als normative Begründung für die Notwendigkeit von Concurrency-Schutzmechanismen (Exclusive Areas, implizite Pufferung, OS-Ressourcen) bei ungesichertem Datenaustausch zwischen präemptiven Ausführungskontexten (Tasks/Runnables).

2. Komponenten, Entitäten & Schnittstellen

  • Task B (Niedrigpriore OS-Task):
    • preemptible Ausführungseinheit (blau).
    • Hält lokalen Registerspeicher bzw. Stack-Variable X*.
  • Task A (Hochpriore OS-Task):
    • preempting Ausführungseinheit (rot).
    • Wird asynchron (z. B. durch Interrupt/Timer-Alarm, symbolisiert durch den Blitz) aktiviert.
    • Hält lokalen Registerspeicher bzw. Stack-Variable X'.
  • Data X / X (Gemeinsame Datenentität):
    • Global allozierter Speicherbereich (Shared Variable / Buffer) im RAM.
    • Repräsentiert im AUTOSAR-Metamodell typischerweise ein VariableDataPrototype (Sender-Receiver-Kommunikation) oder eine InterRunnableVariable (implicit oder explicit).
  • Schnittstellen & Zugriffssemantik:
    • Direkter Lese- und Schreibzugriff (ungeschütztes Read-Modify-Write) ohne atomare Instruktionen oder Concurrency-Barrieren.

3. Dynamisches Verhalten & Sequenzablauf

Chronologischer Ablauf über der Zeitachse:

  1. Initialzustand: Data X = 5.
  2. Phase 1 – Ungeschützter Read (Task B):
    • Task B liest globalen Wert: X* = 5.
  3. Phase 2 – Asynchrone Präemption:
    • Ein Trigger (Interrupt/Event) aktiviert die höher priorisierte Task A.
    • Der OS-Scheduler verdrängt Task B vor dem Rechen- und Schreibschritt.
  4. Phase 3 – Ausführung & Write-Back (Task A):
    • Schritt 1: Task A liest globalen Wert: X' = 5.
    • Schritt 2: Modifikation: X' += 2 → X' = 7.
    • Schritt 3: Rückschreiben: X = X' → Data X im Speicher wird 7.
    • Task A terminiert bzw. geht in den Zustand WAITING/SUSPENDED.
  5. Phase 4 – Wiederaufnahme & Stale Write (Task B):
    • Task B setzt Ausführung fort, besitzt jedoch den veralteten Registerwert X* = 5.
    • Schritt 2: Lokale Inkrementierung: X*++ → X* = 6.
    • Schritt 3: Rückschreiben: X = X* → Data X im Speicher wird mit 6 überschrieben.
  6. Fehlerbild (Lost Update):
    • Die Modifikation von Task A (+2) wird vollständig eliminiert. Der finale Zustand im Shared Memory ist 6 statt des erwarteten kumulierten Ergebnisses (8 bei serialisierter Ausführung).

4. Normative Relevanz & Entwickler-Hinweise

  • SWC-Design & Modellierung (Applikationsebene):
    • Runnables mit Schreib- und Lesezugriffen auf dieselben Daten dürfen nicht ohne Schutzmechanismen auf präemptive Tasks gemappt werden.
    • Definition von ExclusiveArea im Software Component Description File (SWC-D): Kritische Sektionen (Read-Modify-Write) müssen mittels Rte_Enter_<area>() / Rte_Exit_<area>() gekapselt werden.
    • Kennzeichnung von Runnables via canBeInvokedConcurrently = false, wenn keine Reentranz auf Funktionscode-Ebene garantiert ist.
  • RTE-Generierung & Konfiguration (Systemebene / Integrator):
    • Implizite Kommunikation (implicitInterRunnableVariable / Rte_IRead_* / Rte_IWrite_*): RTE legt Task-lokale Kopien beim Task-Eintritt an und schreibt sie beim Task-Exit zurück. Achtung: Auch implizite Pufferung verhindert Lost Updates bei verschachtelten Read-Modify-Write-Zyklen nicht prinzipiell, wenn zwei Tasks dieselbe globale Quelle fortschreiben; hier ist zwingend Synchronisation erforderlich.
    • Exclusive Area Mapping: Der RTE-Generator generiert abhängig von der Plattformarchitektur die Absicherung:
      • Single-Core (präemptiv): OS-Interrupt-Sperre (SuspendAllInterrupts() / ResumeAllInterrupts()) oder Zuweisung einer OSEK/AUTOSAR-OS-Ressource (GetResource() / ReleaseResource() via Priority Ceiling Protocol).
      • Multi-Core: Verwendung von AUTOSAR OS-Spinlocks (GetSpinlock() / ReleaseSpinlock()).
  • BSW- & Treiber-Ebene:
    • Auf Hardwareebene können fundamentale Datentypen, die nicht der nativen Wortbreite des Prozessors entsprechen oder atomare Read-Modify-Write-Instruktionen (z. B. Load-Linked/Store-Conditional, Compare-And-Swap) erfordern, ungeschützt zu Byte-Tearing und Lost Updates führen.
