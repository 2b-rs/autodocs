1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Use-Case-Diagramm (Anwendungsfalldiagramm) mit expliziter Systemgrenze (Subject boundary).
  • Architektur-Kontext: AUTOSAR Timing-Methodik auf der Abstraktionsebene Function-Level gemäß AUTOSAR_FO_TR_TimingAnalysis (Foundation Release R23-11). Es modelliert die methodischen Aktivitäten und Rolleninteraktionen in der frühen Entwurfsphase des AUTOSAR-V-Modells vor der Bindung an konkrete Steuergeräte (ECUs), Tasks oder BSW-Stacks.
  • Technischer Zweck: Definition der Verantwortlichkeiten und Prozessschritte zur Spezifikation, Zerlegung und Groballokation von Timing-Anforderungen (z. B. Sensor-to-Actuator Latencies, End-to-End-Deadlines) bezogen auf die funktionale Fahrzeugarchitektur.

2. Komponenten, Entitäten & Schnittstellen

Systemgrenze
  • Function level: Kapselt die Use Cases der vor-softwaretechnischen, logischen Entwurfsebene.
Use Cases (Anwendungsfälle)
  • Identify timing requirements for a new vehicle function: Erfassung und Spezifikation von zeitlichen Randbedingungen (z. B. Reaktionszeiten, maximale Latenzen, Abtastraten) auf Fahrzeugfunktionsebene.
  • Partition a vehicle function into a Functional Architecture: Logische Dekomposition einer Fahrzeugfunktion in kooperierende funktionale Blöcke bzw. VFB-Komponenten (Virtual Function Bus).
  • Map a Functional Architecture to a hardware components network: Zuordnung der logischen Funktionskomponenten auf Netzwerktopologie und Hardware-Ressourcen (Bussysteme, Gateway-Topologien, Ziel-Knoten).
Akteure (Rollen) & Assoziationen
  • :Function Architect: Primärer Akteur für Identify timing requirements for a new vehicle function (Spezifikation der funktionalen Zeitbudgets).
  • :E/E Architect: Assoziiert mit Partition a vehicle function into a Functional Architecture (Strukturierung der E/E-Gesamtarchitektur und Definition logischer Schnittstellen).
  • :Function Engineer: Assoziiert mit Map a Functional Architecture to a hardware components network (Konkrete Allokation der Funktionen auf Ziel-Hardware und Bussysteme).
  • :Timing Engineer: Beteiligter Akteur an:
    • Partition a vehicle function into a Functional Architecture (Timing-Budgetierung, Konsistenzprüfung der Schnittstellenlatenzen).
    • Map a Functional Architecture to a hardware components network (Netzwerk-Timing-Analyse, Buslast-Abschätzung, Nachweis der Einhaltung von End-to-End-Delays über Busgrenzen hinweg).

3. Dynamisches Verhalten & Sequenzablauf (Methodischer Ablauf)

Das Use-Case-Diagramm definiert die statischen Rollenbezüge; methodisch leitet sich daraus ein top-down orientierter Analyse- und Verfeinerungszyklus ab:

  1. Anforderungsdefinition: :Function Architect definiert die makroskopische Timing-Anforderung (z. B. Notbremsfunktion t_latency ≤ 100\,ms).
  2. Funktionale Zerlegung: :E/E Architect partitioniert die Funktion in Einzelschritte; :Timing Engineer weist Teilbudgets auf die virtuellen Kommunikationsverbindungen zu (Timing Budgeting).
  3. Hardware-Allokation: :Function Engineer und :Timing Engineer mappen die Partitionen auf Netzwerkknoten.
  4. Verifikationsschleife: Der :Timing Engineer bewertet die Auswirkungen von Busübertragungen (z. B. CAN/LIN/Ethernet-Frames, Gateway-Routen). Bei Budgetüberschreitung erfolgt eine iterative Rückmeldung zur Neu-Partitionierung oder Topologieanpassung.

4. Normative Relevanz & Entwickler-Hinweise

  • AUTOSAR Timing Extensions (AUTOSAR_TPS_TimingExtensions): Die auf dieser Ebene identifizierten Use Cases bilden die Grundlage für formale ARXML-Beschreibungen unter Verwendung von:
    • TimingExtension / VfbTiming: Beschreibung von LatencyTimingConstraint, AgeTimingConstraint und ExecutionOrderConstraint auf Software-Component-Ebene.
    • SystemTiming: Beschreibung von Signallaufzeiten und Frame-Latenzen über Busnetzwerke (CommunicationCycle, PduTimingDescriptions).
  • Relevanz für Software- und Applikations-Entwickler:
    • Anforderungen fließen direkt in die Allokation von SWCs zu Tasks (SwcInternalBehavior, Runnables) und RTE-Events ein.
    • Fehlende oder unzureichende Timing-Modellierung auf Function-Level führt zu Laufzeitkonflikten und Jitter-Verletzungen auf ECU-Ebene, die nachträglich nur durch teure Re-Architektur (Task-Splitting, Prioritätsanpassung) behoben werden können.
