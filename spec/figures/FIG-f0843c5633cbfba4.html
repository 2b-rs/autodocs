1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Activity-/Prozessdiagramm (SPEM-basiertes Prozessmodell).
  • Funktionaler Kontext: Übergang von der entkoppelten Komponentenentwicklung (Contract Phase) in die integrationsspezifische ECU-Realisierungsphase (Generation Phase / ECU Context) gemäß AUTOSAR_TR_Methodology (Classic Platform, R4.0.3).
  • Technischer Zweck: Kompilierung des unveränderten C-Quellcodes einer atomaren Software-Komponente (Atomic Software Component Source Code) gegen den für die Ziel-ECU generierten und optimierten Application Header (Optimized Application Header File). Ziel ist die Generierung hocheffizienten Maschinencodes (Optimized Software Component Object Code), der Intra-ECU-Kommunikation und RTE-APIs über Inlining und direkte Speicherzugriffe ohne Laufzeit-Overhead auflöst.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Rollen
  • Software Component Developer (im Schaubild als Software Comp abgeschnitten): Ausführende Rolle («performs») mit Multiplizität 0..*, zuständig für die Bereitstellung des Quellcodes und die Durchführung des Target-Builds im ECU-Kontext.
Aktivität (Task)
  • Re-compile Component in ECU context: Zentrale Kompilierungsaktivität im Integrationsprozess vor dem finalen Link-Vorgang der ECU-Software.
Werkzeuge
  • Compiler («used tool»): Cross-Compiler für die Ziel-Mikrocontroller-Architektur (z. B. TriCore, ARM Cortex-R, RH850).
Eingangs-Artefakte («input»)
  • Atomic Software Component Source Code (Kardinalität 1): Plattformunabhängige C-Implementierungsdatei(en) der SWC (Runnables, interne Funktionen).
  • Optimized Application Header File (Kardinalität 1): Der in der ECU-Phase generierte Header Rte_<swc>.h. Ersetzt generische Prototypen der Contract-Phase durch ECU-spezifische Optimierungen (Makros, Inline-Funktionen, direkte globale Variablenzugriffe bei 1:1-Intra-ECU-Kommunikation).
  • Standard Header Files (Kardinalität 1): AUTOSAR-Standard-Header, insbesondere Std_Types.h, Platform_Types.h, Compiler.h und Compiler_Cfg.h.
  • Library Header Files (Kardinalität 0..*): Schnittstellenheader optional genutzter AUTOSAR-Basis-Bibliotheken (z. B. Crc.h, BFX, EFX, IFX).
Ausgangs-Artefakt («output»)
  • Optimized Software Component Object Code (Kardinalität 1): Relokables Objektmodul (.o/.obj), vorkompiliert für die Zielarchitektur, bereit für das abschließende Linking gegen OS, BSW und RTE-Core.

3. Dynamisches Verhalten & Sequenzablauf

  1. Voraussetzung (Trigger): Erfolgreicher Abschluss der RTE Generation im ECU-Kontext (Generierung der optimierten Rte_<swc>.h).
  2. Include-Pfad-Konfiguration: Zuordnung der Header im Build-System:
    • Pfad zur optimierten Rte_<swc>.h priorisiert vor Contract-Phase-Stubs.
    • Einbindung der BSW- und Plattform-Header (Platform_Types.h, etc.).
    • Einbindung optionaler Library-Header.
  3. Präprozessor-Lauf:
    • Expansion der RTE-APIs (Rte_Read_*, Rte_Write_*, Rte_Call_*). Durch die ECU-Optimierung werden Funktionsaufrufe zu direkten Speicher-/Pufferzugriffen oder Inline-Code expandiert.
    • Auflösung von Compiler-Abstraktionsmakros (FUNC, VAR, CONST, P2VAR) und Speicherkonfigurations-Pragmas via <SWC>_MemMap.h.
  4. Target-Kompilierung: Übersetzung des Quellcodes in Maschinencode unter strikter Einhaltung der plattformspezifischen Typdefinitionen und Calling Conventions.
  5. Abbruchbedingungen:
    • Syntax- oder Linkage-Fehler bei Nichteinhaltung des RTE-API-Vertrags.
    • Typ-Inkonsistenzen zwischen Quellcode und dem aus dem ECU-Extract abgeleiteten Datentyp-Header (Rte_Type.h).
    • Fehlende oder inkompatible Compiler-Abstraktionen.

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Portabilität (Zero-Change-Prinzip): Der Atomic Software Component Source Code darf zwischen Contract Phase und ECU Context nicht verändert werden. Alle Anpassungen an die reale ECU erfolgen ausschließlich über den generierten Optimized Application Header File und Compiler-Switches.
  • RTE-API-Substitution: In der Contract-Phase deklariert die RTE Funktionen als Funktionsprototypen (extern FUNC(...) Rte_Read_...). Im ECU-Kontext implementiert der RTE-Generator diese je nach Communication-Graph als #define Rte_Read_... (Macro-Inlining). Entwickler dürfen Funktionszeiger auf RTE-APIs nur dann verwenden, wenn dies im ARXML explizit als Funktions-Pointer-API konfiguriert wurde.
  • Speichermapping (MemMap.h): Der SWC-Quellcode muss das AUTOSAR-Memory-Mapping-Schema über #include "<SWC>_MemMap.h" mit den jeweiligen Start/Stop-Pragmas strikt einhalten, damit der Compiler Daten und Funktionen in die im ECU-Kontext definierten Linker-Sektionen platziert.
  • Compiler-Abstraktion (Compiler.h): Zwingende Verwendung der Abstraktionsmakros für Zeigerdeklarationen (P2VAR, P2CONST) inklusive Speicherklassen, um Warnungen/Fehler durch Memory-Modelle (Near/Far-Pointer) und Compiler-Erweiterungen der Zielplattform zu vermeiden.
  • Build-Abhängigkeiten: Bei jeder Rekonfiguration von Signal-Routen, Tasks oder Mappings in der RTE muss die Re-Kompilierung zwingend getriggert werden, da geänderte RTE-Inlining-Makros Binärinkompatibilitäten hervorrufen, die zur Link-Zeit unerkannt bleiben können.
