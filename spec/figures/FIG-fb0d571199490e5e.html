1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Statisches Schichtenarchitektur- und Allokationsdiagramm (AUTOSAR BSW Layered Architecture) mit expliziter Trennung zwischen Software- und Hardware-Ebene.
  • Funktionale Einordnung: Detailliert die Entkopplung und Aggregation innerhalb des AUTOSAR Classic Platform Kommunikationsstacks (Communication Drivers / Communication Abstraction Layer).
  • Technischer Zweck: Veranschaulicht die Multidriver- und Multi-Controller-Fähigkeit des Ethernet Interface (EthIf). Es zeigt, wie das EthIf als zentrale Abstraktionsinstanz heterogene Hardware-Controller verschiedener Hersteller (Vendor A, B, C) über herstellerspezifische Gerätetreiber (EthDrv) bündelt und oberen Schichten (TcpIp, SoAd, DoIP, SomeIp) eine einheitliche, hardwareagnostische Schnittstelle bereitstellt.

2. Komponenten, Entitäten & Schnittstellen

#### Software-Domäne (BSW)

  • Ethernet Interface (EthIf):
  • Zentrale Abstraktionskomponente im Communication Abstraction Layer.
  • Handhabt das Routing von Sende- und Empfangsdaten (PDU), Frame-Typ-Multiplexing/Demultiplexing, State Management sowie die Umrechnung logischer Controller-Indizes auf physische Treiberinstanzen.
  • Ethernet Driver Vendor A / B / C (<EthDrv>):
  • MCAL-Treiberkomponenten (Microcontroller Abstraction Layer) oder komplexe Gerätetreiber (CDD / External Ethernet Controller Drivers).
  • Kapseln die hardwarenahen Registerzugriffe, DMA-Pufferdeskriptoren und Interrupt-Routinen der jeweiligen Hardwareplattform.

#### Hardware-Domäne

  • EC Type A, EC Type B, EC Type C (Ethernet Controller):
  • Physische MAC- und Ethernet-Controller-Hardwarebausteine (on-chip oder extern via SPI/PCIe angebunden).
  • EC Type A: Zwei getrennte Controller desselben Typs, betrieben über denselben Treiber Vendor A.
  • EC Type B: Einzelner Controller, betrieben über Vendor B.
  • EC Type C: Multi-Kanal-/Multi-Port-Controller, bei dem zwei Controller-Einheiten von einem gemeinsamen Treiber Vendor C verwaltet werden.
  • Ethernet physical medium:
  • Physische Übertragungsschicht (z. B. 100BASE-T1, 1000BASE-T1, 10BASE-T1S oder CAN XL bei Nutzung als Ethernet-Trägermedium).

#### Beziehungen & Kardinalitäten

  • EthIf : <EthDrv>: $1 : n$ – Das EthIf kann parallel mehrere unterschiedliche Treiber-Module ansteuern.
  • <EthDrv> : EC: $1 : m$ ($m \ge 1$) – Ein Treiber kann mehrere physische Controller-Instanzen gleichen Typs verwalten.
  • EC : Physical Medium: $1 : 1$ oder $n : 1$ – Anbindung an den Bus über zugeordnete PHYs/Transceiver (in diesem High-Level-Diagramm abstrahiert).

3. Dynamisches Verhalten & Steuerfluss

Da es sich um ein statisches Strukturmodell handelt, liegt kein zeitlicher Ablauf vor; der funktionale Interaktionspfad gestaltet sich wie folgt:

  • Initialisierung & Moduswechsel:
  • EthIf iteriert synchron über die konfigurierten Controller-Referenzen (EthIfEthCtrlRef / EthIfEthCanXLCtrlRef) und setzt Betriebsmodi via <EthDrv>_SetControllerMode().
  • Sendeoperation (Tx-Pfad):
  • Obere Schichten fordern Puffer an: EthIf_ProvideTxBuffer() $\rightarrow$ Zuordnung anhand des logischen CtrlIdx $\rightarrow$ Aufruf von <EthDrv>_ProvideTxBuffer().
  • Senden: EthIf_Transmit() delegiert synchron an <EthDrv>_Transmit().
  • Asynchrone Bestätigung: Controller löst Tx-Interrupt aus $\rightarrow$ <EthDrv>_TxConfirmation() $\rightarrow$ Callback an EthIf_TxConfirmation().
  • Empfangsoperation (Rx-Pfad):
  • Ereignisgetrieben (Interrupt) oder via Polling (<EthDrv>_MainFunctionRead()): Empfangene Frames werden über <EthDrv>_RxIndication() an EthIf_RxIndication() übergeben.
  • EthIf führt Frame-Header-Inspection (EtherType, VLAN-Tagging) durch und leitet die PDU an die registrierte Zielkomponente weiter.

4. Normative Relevanz & Entwickler-Hinweise

  • Index-Mapping (EthIfCtrlIdx):
  • Entwickler oberer Schichten greifen ausschließlich über den flachen, homogenen Index EthIfCtrlIdx auf Controller zu.
  • Die BSW-Konfiguration muss das Mapping-Tupel [DriverApiPrefix, DriverControllerIdx] im EthIfConfigSet korrekt auflösen.
  • Multi-Vendor-Namensraumkonflikte:
  • Werden mehrere Treiber parallel kompiliert (Vendor A, Vendor B), müssen zur Vermeidung von Linker-Symbolkollisionen herstellerspezifische Vendor- und Vendor-Api-Infixe gemäß AUTOSAR-Namenskonvention (<VendorId>_<VendorApiInfix>_Eth_...) implementiert und im EthIf konfiguriert werden.
  • CAN XL als Transportschicht (R22-11 bis R25-11):
  • Dient CAN XL als Ethernet-Ersatz, werden in der AUTOSAR-Konfiguration EthIfEthCanXLCtrlRef und EthIfCanXLTrcvRef verwendet.
  • Das EthIf verzweigt API-Aufrufe dann normativ nicht auf Eth_Xxx, sondern auf CanXL_Xxx bzw. CanXLTrcv_Yyy.
  • Interrupt- und Core-Allokation:
  • Unterschiedliche Controller-Typen besitzen oft divergente Priorisierungs-, Puffer- und ISR-Konzepte. Bei Multicore-Architekturen müssen Treiber-Instanzen und die zugehörigen EthIf-Funktionsaufrufe strikt gegen Core-Crossings und Race Conditions abgesichert werden (z. B. Zuordnung via Exclusive Areas / SchM).

Specification of Ethernet Interface AUTOSAR CP R25-11 7 Functional specification 7.1 Ethernet BSW stack As part of the AUTOSAR Layered Software Architecture [1], the Ethernet BSW modules also form a layered software stack. Figure 7.1 depicts the basic structure of this Ethernet BSW stack. The Ethernet Interface module accesses several Ethernet controllers using the Ethernet Driver layer, which can be made up of several Ethernet Drivers modules. Figure 7.1: Basic Structure of the Enthernet BSW Stack 7.1.1 Indexing scheme for Ethernet controller In case CAN XL is used as physical medium, the configuration will contain an EthIfEth- CanXLCtrlRef instead of an EthIfEthCtrlRef and an EthIfCanXLTrcvRef instead of an EthIfEthTrcvRef.
