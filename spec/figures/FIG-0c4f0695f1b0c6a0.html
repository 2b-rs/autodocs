1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Strukturelles Packaging- und Artefakt-Architekturdiagramm (Container- und Manifest-Hierarchie).
  • Technischer Zweck: Spezifikation der normativen Struktur eines Vehicle Package sowie dessen logischer und kryptografischer Beziehung zu den transportierten Software Packages innerhalb der AUTOSAR Adaptive Platform (Vehicle Update and Configuration Management, V-UCM / UCM Master).
  • Funktionale Einordnung: V-UCM orchestriert fahrzeugweite OTA-Update-Kampagnen über heterogene Ziel-Steuergeräte (Adaptive ECUs und UCM Subordinates). Das Schaubild definiert das mehrstufige Sicherheits- und Integritätsmodell (Defense-in-Depth), das die fahrzeugweite Kampagnenbeschreibung entkoppelt von den maschinenspezifischen Installations-Containern bündelt.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Container-Struktur
  1. Vehicle Package (V-Package):
    • Fahrzeugweiter Meta-Container für eine vollständige Update-Kampagne.
    • Signed ARXML file: Strukturierte AUTOSAR-Modellierungsdatei, kryptografisch geschützt über das OEM authentication tag (digitale Signatur/Zertifikatskette des Fahrzeugherstellers).
    • Vehicle Package manifest: Enthält Metadaten der Kampagne, fahrzeugweite Abhängigkeiten (Vehicle State Preconditions, Safety-Checks), ECU-Zuordnungen, Rollback-Strategien und Aktivierungsreihenfolgen.
    • Software Package manifest A / B: Im Vehicle Package eingebettete/referenzierte Instanzen der Teilpaket-Manifeste zur fahrzeugseitigen Vorab-Validierung vor dem Rollout auf Ziel-ECUs.
  2. Software Package (A & B):
    • Transfereinheit für ein konkretes Ziel-UCM (Subordinate auf einer Ziel-Machine).
    • Äußerer Signed container: Transportkapsel, geschützt durch ein dediziertes Authentication tag.
    • Software Package Manifest: Lokale Manifestdatei mit eigenem Authentication tag; definiert Cluster-Typ, Ziel-Hardware, Versionierung, Abhängigkeiten und Prüfsummen.
    • SoftwareCluster (A & B): Kleinste atomar aktualisierbare Funktionseinheit der Adaptive Platform.
      • Innerer Signed container: Payload-Kapsel mit separatem Authentication tag.
      • Inhalte:
        • Executables: Binärdateien der Adaptive Applications.
        • Data: Kalibrier-, Persistenz- und Konfigurationsdaten.
        • Manifests: Execution Manifests, Service Instance Manifests.
        • Software Cluster Manifest: Beschreibt die Laufzeit- und Modellparameter des SoftwareClusters.
Beziehungen & Kardinalitäten
  • 1 : n Aggregation: Ein Vehicle Package referenziert n Software Packages (im Diagramm exemplarisch Software Package A und B).
  • 1 : 1 Manifest-Bindung: Jedes im Vehicle Package eingebettete Software Package manifest [X] verweist über einen kryptografischen Digest/Pfad exakt auf das korrespondierende Software Package Manifest innerhalb des jeweiligen Software Package [X] (gerichtete Pfeilassoziation).
  • Hierarchische Signaturkapselung: $$\text{OEM Tag} \to \text{Signed ARXML} \to \text{Software Package Manifest} \to \text{Software Package Tag} \to \text{Software Cluster Tag}$$ Trennung der Authentizitätsdomänen (OEM-Ebene vs. Tier-1/Zulieferer-Signatur des SoftwareClusters).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die statische Paketstruktur, determiniert aber zwingend folgende Verarbeitungssequenz im V-UCM:

[Vehicle Package Ingestion]
         │
         ▼
[Verify OEM Authentication Tag] ──(Fehlgeschlagen)──► [Abort Campaign]
         │ (Erfolgreich)
         ▼
[Parse Vehicle Package Manifest] (Preconditions, Vehicle State, Dependencies)
         │
         ▼
[Correlate & Verify SW Package Manifests A/B] (Cross-Check Digests gegen V-Package)
         │
         ▼
[Distribute SW Packages to Target UCM Subordinates]
         │
         ▼
[Local Verification & Processing in UCM Subordinate] (Verify Package & Cluster Tags)
  • Kampagnenabbruch & Fehlerbehandlung (SWS_VUCM_01269, RS_VUCM_00034): Wird die Methode CancelCampaign aufgerufen (extern durch Diagnosetester/OTA-Backend oder intern wegen Nichterfüllung von Vorbedingungen), schreibt der V-UCM den Fehlercode kCampaignCancelled persistent in die Kampagnenhistorie (history), bevor Rollback-/Bereinigungsroutinen greifen.
  • Asynchrone Verteilung: Nach erfolgreicher Verifikation des OEM-Tags wird die Auslieferung der Software Packages an UCM Subordinates über UCM-Service-Schnittstellen (PackageManagement) asynchron angestoßen.

4. Normative Relevanz & Entwickler-Hinweise

  • Kryptographie & Key-Management (ara::crypto):
    • Es sind getrennte Trust-Anchors vorzusehen: Der V-UCM benötigt OEM-Root-/Kampagnen-Zertifikate zur Verifikation der Signed ARXML file. Ziel-UCMs benötigen Schlüssel zur Validierung der lieferantenspezifischen Container-Tags.
    • Streaming-fähige Signatur-/Hashprüfungen sind zwingend erforderlich, um Embedded-RAM-Limits bei großen Software Packages (Gigabyte-Bereich) nicht zu überschreiten.
  • Manifest-Konsistenzprüfung:
    • Der V-UCM muss strikt sicherstellen, dass die im Signed ARXML file deklarierten Hashes der Software Package manifest A/B exakt bit-identisch mit den Manifesten in den empfangenen Software Packages übereinstimmen. Diskrepanzen führen zur sofortigen Ablehnung.
  • Persistenz & Audit Trail (UNECE R156):
    • Implementierung von SWS_VUCM_01269: Die Speicherung von kCampaignCancelled in history via ara::per muss spannungsausfallsicher sein, um regulatorische Anforderungen an Software-Update-Managementsysteme (SUMS) zu erfüllen.
  • Speicher-Layouting:
    • Getrennte Staging-Partitionen für Vehicle Package (temporärer Metadaten-Speicher auf V-UCM-Knoten) und Software Packages (ECU-lokale A/B-Partitionen oder Staging-Bereiche der Ziel-Machines).
