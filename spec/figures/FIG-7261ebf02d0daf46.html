1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (Metamodell-Ausschnitt des AUTOSAR Diagnostic Extract Templates / DEXT, AUTOSAR CP R24-11).
  • Technischer Zweck: Spezifikation des Metamodells für die Konfiguration des Function Inhibition Managers (FiM). Es modelliert die Entkopplung und Zuordnung zwischen Funktionsidentifikatoren (FIDs), Hemmbedingungen (Inhibition Masks), logischen Alias-Ereignissen auf System-/OEM-Ebene und den konkreten BSW-Diagnoseereignissen (DemEventParameter bzw. DiagnosticEvent) des Diagnostic Event Managers (Dem).

2. Komponenten, Entitäten & Schnittstellen

Zentrale Konfigurationselemente & Vererbung
  • DiagnosticFunctionIdentifierInhibit (spezialisiert DiagnosticCommonElement):
    • Definiert eine konkrete Hemmungsregel für eine Zielfunktion.
    • Attribut: +inhibitionMask: DiagnosticInhibitionMaskEnum [0..1] – Kriterium, bei welchem Event-Zustand gehemmt wird.
    • Assoziation: +functionIdentifier: DiagnosticFunctionIdentifier [0..1] – Ziel-FID, das kontrolliert wird.
    • Komposition: +inhibitSource: DiagnosticFunctionInhibitSource [0..*] – Menge der auslösenden Fehlerquellen.
  • DiagnosticFunctionIdentifier (spezialisiert DiagnosticCommonElement):
    • Repräsentiert das logische Function Identifier (FID) zur Freigabe/Sperrung von Software-Funktionen.
  • «enumeration» DiagnosticInhibitionMaskEnum:
    • Literale:
      • lastFailed: Hemmung aktiv, wenn der letzte Test fehlschlug (UDS Status Bit 0: testFailed).
      • notTested: Hemmung aktiv, solange der Test im aktuellen Fahrzyklus noch nicht abgeschlossen wurde (Bit 6: testNotCompletedThisOperationCycle).
      • tested: Hemmung aktiv, sobald der Test im Zyklus abgeschlossen wurde (Bit 6 = 0).
      • testedAndFailed: Hemmung aktiv, wenn im aktuellen Zyklus getestet und fehlgeschlagen (Bit 0 == 1 && Bit 6 == 0).
  • DiagnosticFunctionInhibitSource (spezialisiert Identifiable):
    • Abstrakter Quellknoten einer Hemmbedingung.
    • Referenzen zu Alias-Ebene:
      • +event: DiagnosticFimAliasEvent [0..1]
      • +eventGroup: DiagnosticFimAliasEventGroup [0..1]
Abstraktions- & Alias-Ebene
  • DiagnosticAbstractAliasEvent:
    • Abstrakte Basisklasse für logische Stellvertreter-Ereignisse im DEXT.
  • DiagnosticFimAliasEvent (spezialisiert DiagnosticAbstractAliasEvent):
    • Logisches Alias-Event zur herstellerweiten Spezifikation von Hemmungen unabhängig von konkreten ECU-Event-IDs.
  • DiagnosticFimAliasEventGroup (spezialisiert DiagnosticAbstractAliasEvent):
    • Bündelung mehrerer Alias-Events via Assoziation +groupedAliasEvent: DiagnosticFimAliasEvent [0..*].
Mapping-Klassen (Spezialisierungen von DiagnosticMapping)
  • DiagnosticFimAliasEventMapping:
    • Mappt ein +aliasEvent: DiagnosticFimAliasEvent [0..1] auf das konkrete BSW-Ereignis +actualEvent: DiagnosticEvent [0..1].
  • DiagnosticFimAliasEventGroupMapping:
    • Mappt eine +aliasEvent: DiagnosticFimAliasEventGroup [0..1] auf eine BSW-Eventgruppe +actualEvent: DiagnosticFimEventGroup [0..1].
  • DiagnosticInhibitSourceEventMapping:
    • Ermöglicht das direkte Mapping einer +inhibitionSource: DiagnosticFunctionInhibitSource [0..1] auf BSW-Ziele ohne Alias-Zwischenschicht:
      • Entweder auf ein Einzelereignis via +diagnosticEvent: DiagnosticEvent [0..1]
      • Oder auf eine Gruppe via +eventGroup: DiagnosticFimEventGroup [0..1].
Konkrete BSW-/Dem-Zielelemente
  • DiagnosticEvent (spezialisiert DiagnosticCommonElement):
    • Konkretes Diagnoseereignis des Dem auf ECU-Ebene.
  • DiagnosticFimEventGroup (spezialisiert DiagnosticCommonElement):
    • Zusammenfassung mehrerer konkreter DiagnosticEvent Instanzen via +event: DiagnosticEvent [0..*] zur gemeinsamen Auswertung im FiM.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm definiert die statischen DEXT-Konfigurationspfade, aus denen zur Generierungszeit die Laufzeit-Auswertung im BSW-Stack (FiM / Dem / SWC) erzeugt wird:

[SWC / Sensor / Monitor]
       │ (1) Dem_SetEventStatus()
       ▼
[Dem (Diagnostic Event Manager)]
       │ (2) FiM_DemTriggerOnEventStatus()
       ▼
[FiM (Function Inhibition Manager)]
       │ (3) Maskenabgleich (DiagnosticInhibitionMaskEnum)
       │     - Event-Status & Maske != 0
       │     - ODER-Verknüpfung bei DiagnosticFimEventGroup
       │ (4) FID-Zustand aktualisieren: Inhibit = TRUE / FALSE
       ▼
[SWC (Application Function)]
       ◄── (5) FiM_GetFunctionPermission(FID, &Permission) [Synchrones Polling]
           ODER R-Port-Notification via RTE bei Statusänderung
  1. Triggering (Dem → FiM): Ein BSW-/SWC-Monitor meldet ein Fehlereignis an den Dem. Bei Statusänderung triggert der Dem synchron oder asynchron via FiM_DemTriggerOnEventStatus(EventId, EventStatusByte) den FiM.
  2. Konditionsprüfung: Der FiM löst anhand der konfigurierten Mappings auf:
    • Einzel-Event: Status von DiagnosticEvent wird mit der inhibitionMask bitweise maskiert.
    • Event-Gruppe (DiagnosticFimEventGroup): Wenn mindestens ein zugeordnetes DiagnosticEvent die Maskenbedingung erfüllt, schlägt die Gruppe an (disjunktive Logik).
  3. Wirkung auf FID: Trifft die Bedingung zu, wird das über +functionIdentifier referenzierte FID gesperrt.
  4. Applikationsauswertung: Die Applikations-SWC fragt vor Ausführung funktionsrelevanter Pfade zyklisch/ereignisgesteuert FiM_GetFunctionPermission(FID, &Permission) ab. Ist die Hemmung aktiv, liefert der FiM E_OK mit Permission = FALSE; die Funktion bleibt deaktiviert.

4. Normative Relevanz & Entwickler-Hinweise

  • DEXT-Integrationsworkflow (OEM vs. Tier-1):
    • Gemäß RS_DEXT_00077 und TPS_DEXT_01093 ermöglicht das Metamodell ein zweistufiges Entwicklungsparadigma: Der OEM spezifiziert FIDs und funktionale Abhängigkeiten abstrakt über DiagnosticFimAliasEvent / DiagnosticFimAliasEventGroup.
    • Der Tier-1/Integrator schließt die Konfigurationslücke, indem er die Alias-Objekte über DiagnosticFimAliasEventMapping bzw. DiagnosticFimAliasEventGroupMapping auf die tatsächlichen DiagnosticEvent-Instanzen der BSW-Konfiguration bindet.
    • Alternativ gestattet DiagnosticInhibitSourceEventMapping einen flachen Bypass ohne Alias-Objekte für ECU-zentrierte Direktspezifikationen.
  • Codegenerator-Einfluss (FiM BSW-Konfiguration):
    • Die Entitäten transformieren 1:1 in die AUTOSAR-BswM/FiM-Modulkonfiguration (FiMInhibitionConfiguration, FiMEventRef, FiMFunctionId, FiMInhInhibitionMask).
    • Kardinalitäts-Restriktion: Für jede DiagnosticFunctionInhibitSource darf im finalen Extrakt entweder nur ein Event oder eine EventGroup wirksam gebunden sein (Vermeidung von Mehrdeutigkeiten).
  • Embedded-Einschränkungen & Initialisierungsfallen:
    • Wahl von notTested: Führt bei ECU-Kaltstart sofort zur Sperrung des FIDs, bis der Dem den Monitor durchlaufen hat. Kritisch für Verfügbarkeit bei Startsequenzen.
    • Wahl von lastFailed: Setzt persistente Speicherung bzw. stabilen Zyklusstatus voraus, reagiert aber robust gegen noch nicht abgeschlossene Diagnosen.
    • Gruppierungskosten: Große DiagnosticFimEventGroup-Instanzen erhöhen die Ausführungszeit in FiM_DemTriggerOnEventStatus, da der FiM die kumulierte ODER-Bedingung über alle Gruppenmitglieder konsistent halten muss.
