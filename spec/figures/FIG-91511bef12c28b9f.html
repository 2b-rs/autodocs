1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Metamodell-Klassendiagramm (M2-Ebene) aus der Spezifikation AUTOSAR Software Component Template.
  • Technischer Zweck: Definition der Verbindungselemente (SwConnector) zur Modellierung von Kommunikationsbeziehungen zwischen Komponentenports auf dem Virtual Function Bus (VFB). Es spezifiziert die Syntax für komponenteninterne Verbindungen (AssemblySwConnector), hierarchische Weiterleitungen (DelegationSwConnector) sowie direkte Durchleitungen zwischen Außenports (PassThroughSwConnector) über abstrakte Port-Klassen.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Typisierung
  • SwConnector (abstrakt): Spezialisiert AtpStructureElement. Abstrakte Basisklasse aller Software-Konnektoren innerhalb einer Komposition.
  • AssemblySwConnector: Spezialisiert SwConnector. Verbindet Ports von Software-Komponenten-Prototypen horizontal auf derselben Hierarchieebene.
  • PassThroughSwConnector: Spezialisiert SwConnector. Modelliert die direkte Kopplung zwischen zwei äußeren Ports einer übergeordneten Komposition ohne Beteiligung von Sub-Komponenten.
  • DelegationSwConnector: Spezialisiert SwConnector. Modelliert die vertikale Weiterleitung zwischen einem äußeren Port der Komposition und einem Port einer inneren Komponente.
  • PortPrototype (abstrakt): Spezialisiert AtpBlueprintable und AtpPrototype. Abstrakte Basisklasse für alle Port-Prototypen.
  • AbstractProvidedPortPrototype (abstrakt): Spezialisiert PortPrototype. Abstrakte Basisklasse für bereitstellende Ports.
  • AbstractRequiredPortPrototype (abstrakt): Spezialisiert PortPrototype. Abstrakte Basisklasse für anfordernde Ports.
Assoziationen, Kardinalitäten & Stereotyp-Semantik
  • AssemblySwConnector:
    • +provider [0..1] mit Stereotyp «instanceRef» auf AbstractProvidedPortPrototype: Referenziert optional den bereitstellenden Port einer Sub-Komponente.
    • +requester [0..1] mit Stereotyp «instanceRef» auf AbstractRequiredPortPrototype: Referenziert optional den anfordernden Port einer Sub-Komponente.
  • PassThroughSwConnector:
    • +providedOuterPort [0..1] (direkte Assoziation) auf AbstractProvidedPortPrototype: Referenziert optional den bereitstellenden äußeren Port der Komposition.
    • +requiredOuterPort [0..1] (direkte Assoziation) auf AbstractRequiredPortPrototype: Referenziert optional den anfordernden äußeren Port der Komposition.
  • DelegationSwConnector:
    • +outerPort [0..1] (direkte Assoziation) auf PortPrototype: Referenziert optional den äußeren Port der umschließenden Komposition.
    • +innerPort [0..1] mit Stereotyp «instanceRef» auf PortPrototype: Referenziert optional den inneren Port einer Sub-Komponente.
  • Semantik von «instanceRef»: Ermöglicht die eindeutige Adressierung von Ports an Prototypen innerhalb der Kompositionshierarchie über einen vollständigen Instanzpfad.

3. Dynamisches Verhalten & Sequenzablauf

  • Metamodell-Charakter: Rein statisches Architekturmodell zur Entwurfszeit. Es existiert keine eigenständige Laufzeitinstanz eines Connectors auf dem Ziel-Mikrocontroller.
  • Transformationspfad im RTE-Generator (Flattening & Binding):
    • Hierarchieauflösung: DelegationConnectorPrototype wird bei der Systemgenerierung vollständig aufgelöst („geplättet“). Der RTE-Generator verbindet die inneren Ports über die Delegationspfade direkt mit den finalen AssemblyConnectorPrototype-Endpunkten.
    • Lokale Kommunikation (Intra-ECU): Liegen verbundene Provider- und Requester-Instanzen auf derselben ECU, synthetisiert der RTE-Generator direkte Funktionsaufrufe (Rte_Call), Shared-Memory-Puffer oder interne Kopieroperationen (Rte_Read/Rte_Write).
    • Netzwerk-Kommunikation (Inter-ECU): Liegen die Endpunkte auf unterschiedlichen ECUs, mappt der System-Synthesizer den Konnektor über Com-Signale, den COM-Stack und den PDU-Router auf das Bussystem (CAN/LIN/FlexRay).
    • Service-Aufrufe: ServiceConnectorPrototype verdrahtet die generierten RTE-Service-APIs mit den BSW-Modul-APIs (z. B. NvM_ReadBlock, Dem_SetEventStatus).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur-Rolle: Durch die Abstraktion über AbstractProvidedPortPrototype und AbstractRequiredPortPrototype können Konnektoren typunabhängig über Schnittstellen-Rollen hinweg modelliert werden.
  • Modellierungs-Regeln: PassThroughSwConnector erfordert keine Instanzreferenzen, da beide referenzierten Ports (providedOuterPort, requiredOuterPort) direkt auf der Ebene der umschließenden Komposition liegen. Für innere Ports von AssemblySwConnector und DelegationSwConnector bleibt «instanceRef» obligatorisch.
