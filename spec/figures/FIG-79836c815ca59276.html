1. Diagrammtyp & Architektur-Kontext

UML-Klassendiagramm zur Konfiguration von Funktionsgruppen im Kontext der Software-Cluster-Architektur der AUTOSAR Adaptive Platform. Das Diagramm modelliert die Kapselung von Funktionsgruppen über FunctionGroupSet und deren Inanspruchnahme (claimedFunctionGroup) durch Software-Cluster (SoftwareCluster). Prozessträger und Maschinenmappings sind nicht mehr Gegenstand dieses Diagramms.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm umfasst folgende Modellelemente:

  • FunctionGroupSet (ARElement, AtpClassifier): Aggregiert per Komposition +functionGroup [0..*] vom Typ ModeDeclarationGroupPrototype.
  • SoftwareCluster (ARElement): Besitzt die optionalen Attribute +installationBehavior: SoftwareClusterInstallationBehaviorEnum [0..1], +typeApproval: String [0..1], +vendorId: PositiveInteger [0..1] und +version: StrongRevisionLabelString [0..1]. Referenziert über die gerichtete Assoziation +claimedFunctionGroup [0..*] die beanspruchten ModeDeclarationGroupPrototype-Instanzen.
  • ModeDeclarationGroupPrototype (AtpPrototype): Referenziert optional über +type [0..1] (Stereotyp «isOfType», {redefines atpType}) eine ModeDeclarationGroup.
  • ModeDeclarationGroup (ARElement, AtpBlueprint, AtpBlueprintable, AtpType): Komponiert +modeDeclaration [0..*] (Stereotypen «atpVariation,atpSplitable») und referenziert optional +initialMode [0..1] auf ModeDeclaration.
  • ModeDeclaration (AtpStructureElement, Identifiable): Repräsentiert die deklarierten Modi und besitzt das optionale Attribut +value: PositiveInteger [0..1].

3. Dynamisches Verhalten & Sequenzablauf

Statisches Metamodell für die Paketierung und Zuweisung von Funktionsgruppen. Ein SoftwareCluster deklariert über claimedFunctionGroup, welche Funktionsgruppen aus dem systemweiten FunctionGroupSet für seine Ausführung und Zustandssteuerung relevant sind. Die Konfiguration ist rein deklarativ; Zustandsübergänge erfolgen zur Laufzeit über das Execution Management basierend auf diesen Deklarationen.

4. Normative Relevanz & Entwickler-Hinweise

Variabilitäts- und Metamodellregeln:

  • Für die Komposition +modeDeclaration: Tagged Value vh.latestBindingTime = blueprintDerivationTime unter «atpVariation,atpSplitable».
  • Die Multiplizitäten sind weitgehend optional ausgelegt: +type [0..1], +initialMode [0..1], +modeDeclaration [0..*] sowie +value [0..1].
  • Die Versionierung und Identifikation der Cluster erfolgt normativ über die optionalen Attribute vendorId [0..1], version [0..1] (als StrongRevisionLabelString), typeApproval [0..1] sowie das Installationsverhalten installationBehavior [0..1].

Specification of Manifest AUTOSAR AP R22-11 8.4 Function Groups 8.4.1 Semantics of Function Group Function Groups with Function Group States individually control groups of functionally coherent Application processes. The Process state may depend on a mode that is defined in the Function Group in case that the StateDependentStartupConfig refers to the Function Group State with the function- GroupState reference. The usage of Function Groups is described in more detail in [10]. [TPS_MANI_03145]{DRAFT} Description of a Function Group ⌈By defining a ModeDeclarationGroupPrototype aggregated in the role FunctionGroupSet. functionGroup it is possible to define a Function Group that has a shortName and a set of Modes (States). The ModeDeclarationGroupPrototype points to a reusable ModeDeclarationGroup in the role type that contains the different modes as ModeDeclarations and a designated initialMode.⌋(RS_MANI_00041) [TPS_MANI_03194]{DRAFT} Function Group State ⌈A Function Group State is described by a ModeDeclaration within a ModeDeclarationGroup that is referenced in the role type by a ModeDeclarationGroupPrototype aggregated as functionGroup by a FunctionGroupSet. The Function Group State is identified by its shortName.⌋(RS_MANI_00041) The modeling described in [TPS_MANI_03145] and [TPS_MANI_03194] is depicted in Figure 8.11.
