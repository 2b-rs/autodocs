1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm mit kombiniertem Fragment (par für parallele Pfade) und eingebetteten Zustandsinvarianten (State Invariants).
  • Technischer Zweck: Spezifikation des synchronen Bus-Shutdowns (Synchronous NM Shutdown) über ein Gateway/Domain-Controller-Steuergerät in der Rolle des AUTOSAR NM Coordinators (Nm-Modul mit aktiviertem Koordinations-Feature).
  • Einordnung im Gesamtsystem:
  • Schicht: AUTOSAR Classic Platform – Communication Services / System Services (BSW).
  • Funktion: Das generische NM-Interface (Nm) synchronisiert das Herunterfahren heterogener, koordinierter NM-Cluster (hier: zeitgesteuertes FlexRay via FrNm und ereignis-/timeout-gesteuertes CAN via CanNm), wenn das lokale Steuergerät keine Kommunikationsanforderung mehr hält, externe Cluster aber noch aktiv sind bzw. synchron schlafen gelegt werden müssen.

2. Komponenten, Entitäten & Schnittstellen

#### Beteiligte BSW-Module (Lebenslinien, Stereotyp «module»)

  • ComM: Communication Manager (Mode Management, initiiert Release und verarbeitet Bus-Sleep-Zustände).
  • Nm: Generic Network Management Interface (agiert hier als zentraler NM Coordinator; verwaltet Koordinationslogik und Shutdown-Timer).
  • FrNm: FlexRay Network Management (busspezifische NM-Zustandsmaschine für FlexRay).
  • CanNm: CAN Network Management (busspezifische NM-Zustandsmaschine für CAN).
  • FrSm (FrSM): FlexRay State Manager (steuert Bus-Kommunikationsmodi via ComM-Kopplung).
  • CanSM: CAN State Manager (steuert Controller/Transceiver-Modi für CAN via ComM-Kopplung).

#### Schnittstellen & Funktionssignaturen

  • Abwärtsgerichtete Steuer-APIs (Synchronous Control Calls):
  • Nm_NetworkRelease(NetworkHandleType nmNetworkHandle): Aufruf von ComM an Nm.
  • FrNm_RequestBusSynchronization(NetworkHandleType nmNetworkHandle) / FrNm_NetworkRelease(NetworkHandleType nmNetworkHandle): Aufruf von Nm an FrNm.
  • CanNm_RequestBusSynchronization(NetworkHandleType nmNetworkHandle) / CanNm_NetworkRelease(NetworkHandleType nmNetworkHandle): Aufruf von Nm an CanNm.
  • FrSM_RequestComMode(NetworkHandleType NetworkHandle, ComM_ModeType ComM_Mode): ComM an FrSM.
  • CanSM_RequestComMode(NetworkHandleType NetworkHandle, ComM_ModeType ComM_Mode): ComM an CanSM.
  • Aufwärtsgerichtete Callback-/Indikations-APIs:
  • Nm_RemoteSleepIndication(NetworkHandleType nmNetworkHandle): Signalisierung von FrNm/CanNm an Nm, dass alle anderen Knoten im Cluster schlafbereit sind.
  • Nm_SynchronizationPoint(NetworkHandleType nmNetworkHandle): Schedule-Synchronisationspunkt von FrNm an Nm.
  • Nm_PrepareBusSleepMode(NetworkHandleType nmNetworkHandle) / ComM_Nm_PrepareBusSleepMode(NetworkHandleType nmNetworkHandle): Indikation des Eintritts in Prepare Bus-Sleep.
  • Nm_BusSleepMode(NetworkHandleType nmNetworkHandle) / ComM_Nm_BusSleepMode(NetworkHandleType nmNetworkHandle): Indikation des Erreichens von Bus-Sleep.

#### Beziehungs- und Zustandssemantik

  • Kardinalität: 1 Nm-Koordinator koordiniert $N$ Kanäle/Cluster (im Schaubild: 1 FlexRay- und 1 CAN-Kanal).
  • Zustandsinvariante Abbildung:
  • FrNm: Network Mode (Normal Operation) $\rightarrow$ Network Mode (Ready Sleep) $\rightarrow$ Bus Sleep Mode.
  • CanNm: Network Mode (Normal Operation) $\rightarrow$ Network Mode (Ready Sleep) $\rightarrow$ Prepare Bus-Sleep Mode $\rightarrow$ Bus-Sleep Mode.
  • Bus-Zustände an State Managern: Silent Communication (nur CAN im Prepare Bus-Sleep), No Communication (Bus-Sleep erreicht).

3. Dynamisches Verhalten & Sequenzablauf

#### Phase 1: Koordination & Triggerung (Voraussetzung für Shutdown)

  1. Lokale Freigabe: ComM meldet via Nm_NetworkRelease() lokale Schlafbereitschaft an Nm. Da der zu koordinierende Cluster noch nicht schlafbereit ist, hält Nm den Bus aktiv (kein unmittelbares *Nm_NetworkRelease()).
  2. Remote Sleep Erkennung: Sowohl CanNm als auch FrNm detektieren den Sleep-Zustand aller Busteilnehmer und melden jeweils Nm_RemoteSleepIndication().
  3. Cluster-Synchronisation: An der FlexRay-Makrotick-/Repetition-Cycle-Grenze triggert FrNm Nm_SynchronizationPoint().
  4. Timer-Start: Nm startet die systemspezifisch berechneten Shutdown-Timer (Start shutdown timers()).

#### Phase 2: Paralleler synchroner Shutdown (par synchronous NM shutdown)

Sobald der zugehörige Shutdown-Timer im Nm abläuft (Shutdown timer expires()), laufen die Sub-Pfade parallel:

  • Zweig [FlexRay]:
  1. Nm ruft synchron FrNm_RequestBusSynchronization() und FrNm_NetworkRelease() auf.
  2. An der nächsten Repetition-Cycle-Grenze wechselt FrNm nach Network Mode (Ready Sleep).
  3. Nach Beendigung des letzten Wiederholungszyklus (Last repetition cycle finished()) schaltet FrNm in den Bus Sleep Mode und meldet Nm_BusSleepMode().
  4. Nm leitet ComM_Nm_BusSleepMode() an ComM weiter.
  5. ComM fordert über FrSM_RequestComMode(COMM_NO_COMMUNICATION) das Abschalten der FlexRay-Kommunikation an (No Communication).
  • Zweig [CAN]:
  1. Nm ruft synchron CanNm_RequestBusSynchronization() und CanNm_NetworkRelease() auf.
  2. CanNm wechselt unmittelbar in Network Mode (Ready Sleep).
  3. Ablauf des CAN-NM-Timeouts (Timer expires() / CanNmTimeoutTime): CanNm wechselt in Prepare Bus-Sleep Mode und benachrichtigt Nm_PrepareBusSleepMode().
  4. Nm meldet ComM_Nm_PrepareBusSleepMode() an ComM. ComM weist CanSM via CanSM_RequestComMode(COMM_SILENT_COMMUNICATION) in den passiven Empfangsmodus ein (Silent Communication).
  5. Ablauf des Wait-Bus-Sleep-Timers (Timer expires() / CanNmWaitBusSleepTime): CanNm wechselt in Bus-Sleep Mode und benachrichtigt Nm_BusSleepMode().
  6. Nm leitet ComM_Nm_BusSleepMode() an ComM weiter. ComM schaltet via CanSM_RequestComMode(COMM_NO_COMMUNICATION) die CAN-Transceiver/Controller ab (No Communication).

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsparameter (BSW/ARXML):
  • Nm: NmCoordinatorSupportEnabled = TRUE. Konfiguration der NmChannelConfig-Cluster-Hierarchien (NmSynchronizingNetwork = TRUE auf dem FlexRay-Kanal, da FlexRay den Zeittakt für den Shutdown-Synchronisationspunkt vorgibt).
  • Shutdown-Verzögerung: NmShutdownDelayTimer muss im Nm so dimensioniert sein, dass Restlaufzeiten von FlexRay-Zyklen und CAN-Token/Nachrichtenübertragungen exakt ausgeglichen werden.
  • Bus-spezifisch: CanNmRemoteSleepIndEnabled = TRUE, FrNmRemoteSleepIndEnabled = TRUE, FrNmSyncPointEnabled = TRUE.
  • API-Verträge & Blocking-Verhalten:
  • Aufrufe von Nm_RequestBusSynchronization() und Nm_NetworkRelease() sind strikt synchron und nicht-blockierend auszuführen; Fehlercodes (E_NOT_OK) müssen im Nm als Koordinationsfehler bewertet werden.
  • CanSM_RequestComMode und FrSM_RequestComMode sind asynchrone Anforderungen; die tatsächliche Bestätigung des Moduswechsels erfolgt entkoppelt über ComM_BusSM_ModeIndication().
  • Architektureinschränkung / Fallstricke:
  • Das Gateway-Steuergerät darf die Buskommunikation erst dann physisch abschalten, wenn alle koordinierten Kanäle den Zustand Bus Sleep Mode signalisiert haben.
  • Das Schaubild veranschaulicht den asymmetrischen Shutdown-Pfad: FlexRay schaltet direkt von Ready Sleep in Bus Sleep (deterministische Cycle-Grenzen, kein Prepare-Bus-Sleep), während CAN zwingend die Zwischenphase Prepare Bus-Sleep durchläuft, um Rest-Nachrichten auf dem Bus abklingen zu lassen.
