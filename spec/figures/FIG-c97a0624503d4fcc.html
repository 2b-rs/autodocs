1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Schichten- und Komponenten-Architekturdiagramm (Laufzeit- und Integrationsmodell für heterogene Multi-OS/Multi-Core-ECUs).
  • Technischer Zweck: Spezifikation der Signal/Service-Translation (Signal-to-Service Mapping nach AUTOSAR_TPS_ManifestSpecification, Kap. 12) zwischen AUTOSAR Classic Platform (CP) und AUTOSAR Adaptive Platform (AP) auf demselben Steuergerät/SoC.
  • Funktionale Einordnung: Ermöglicht die nahtlose Interoperabilität zwischen signalbasierter (CP: COM/LdCOM) und serviceorientierter Kommunikation (AP: ara::com) über Inter-Process-Communication (IPC) / Virtualisierung (z. B. Hypervisor, Shared Memory) unter Umgehung eines externen physischen Ethernet-Busses.

2. Komponenten, Entitäten & Schnittstellen

Classic Platform BSW (Links)
  • Classic Application: SW-C mit AUTOSAR-Standardports (Sender/Receiver oder Client/Server).
  • RTE (Runtime Environment): Vermittelt Datenzugriffe der SW-C an die BSW.
  • AUTOSAR COM / AUTOSAR LdCOM:
    • AUTOSAR COM: Signalbasiertes Packen/Entpacken von Signalen und Signalgruppen in Interaktionsschicht-PDUs (I-PDUs).
    • AUTOSAR LdCOM: Effiziente, latenzarme PDU-Verarbeitung für große Datenblöcke ohne Signal-Routing-Overhead.
  • PDU Router (PduR): Zentraler I-PDU-Router; leitet PDUs je nach Routing-Table entweder an den Netzwerk-Stack oder den IPC-Treiber weiter.
  • IPC ComplexDriver (CDD): Bindeglied zur Virtualisierungs-/Hardware-Ebene. Kapselt OS-/Hypervisor-spezifische IPC-Mechanismen und implementiert die PduR-Treiberschnittstelle (<User>_Transmit, <User>_RxIndication).
  • Ethernet Stack (EthIf, Eth Driver): Alternativer/konventioneller Pfad für Off-Board/Off-Chip-Kommunikation.
(Virtual) Machine / Hardware (Unten)
  • Physische Hardware / SoC-Grenze bzw. Hypervisor-Schicht.
  • Lila Verbindungspfad: Direkter, OS-übergreifender Datentransportkanal (Shared Memory Ringbuffers, Mailbox Registers oder VirtIO/vHost).
Adaptive Platform Foundation (Rechts)
  • Adaptive Application: POSIX-Prozess, der Services konsumiert oder bereitstellt.
  • ara::com API: C++ Interface (Proxy/Skeleton).
  • C++ 11 Language Binding & Communication Binding: Generierter Middleware-Gluecode zur (De-)Serialisierung typisierter C++ Datentypen in Transport-Payloads.
  • Communication Management:
    • Dispatching and Discovery: Identifikation und Zuordnung von Service-IDs, Methoden und Events.
    • Transport-Pfade:
      • IPC Transport über native IPC-Treiber (aktiver Pfad zur CP).
      • Parallele Netzwerkpfade: SOME/IP Transport, PDU with SOME/IP Header, PDU with Arbitrary Header (jeweils aufbauend auf TCP/IP und Ethernet Driver).
  • PDU (Protocol Data Unit): Segmentierte Container (grün dargestellt), welche die Datenbytes auf Payload-Ebene repräsentieren.

3. Dynamisches Verhalten & Sequenzablauf

Datenfluss CP → AP (Signal-to-Service):
  1. PDU-Generierung (CP): Classic Application sendet Signale über Rte_Write_*. AUTOSAR COM serialisiert die Signale in eine I-PDU (bzw. LdCOM bei unstrukturierten Großdaten).
  2. PDU-Routing (CP): PduR empfängt die PDU und routet sie via PduR_ComTransmit / PduR_LdComTransmit an den IPC ComplexDriver.
  3. Cross-Domain IPC Transfer: Der IPC ComplexDriver schreibt die PDU über die Virtualisierungs-Grenze (z. B. Shared Memory) und triggert einen Inter-VM-/Inter-Core-Interrupt.
  4. PDU-Empfang & Dispatching (AP): Der AP-OS-Treiber liest die PDU und übergibt sie an das Communication Management (IPC Transport).
  5. Translation & Binding: Das Communication Binding zerlegt die PDU anhand des hinterlegten ServiceInstanceToSignalMapping. Die enthaltenen Signale werden in Attribute/Events eines ara::com-Service-Skeletts bzw. -Proxys überführt.
  6. Zustellung (AP): Das C++11 Language Binding stellt das Event via Polling (ara::com::SampleContainer) oder Event-Callback an die Adaptive Application zu.

(Der Rückpfad AP → CP verläuft spiegelbildlich: Deserialisierung/Extraktion der Service-Daten in I-PDUs → Transfer über IPC → PduR → COM → RTE).

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML / Manifest-Modellierung:
    • Erfordert die Modellierung von ServiceInstanceToSignalMapping zur Verknüpfung von AdaptiveServiceInstance (Events/Fields/Methods) mit SystemSignal / ISignalIPdu der Classic-Welt.
    • Auf AP-Seite muss im Service Instance Manifest das entsprechende Transport-Binding für IPC (IpcServiceInstanceDeployment) bzw. PDU-Deployment (PduPayloadType) projektiert werden.
  • Treiber- & BSW-Implementierung (CP):
    • Der IPC ComplexDriver (CDD) muss zwingend standardisierte AUTOSAR PduR-Schnittstellen bereitstellen (<Msn>_Transmit, <Msn>_RxIndication, ggf. TriggerTransmit).
    • Puffer- und Speichermanagement müssen auf SoC-Ebene abgesichert werden (Cache-Invalidation, atomare Lese-/Schreibzeiger bei Shared Memory, Ringbuffer-Dimensionierung).
  • Serialisierung & Alignment:
    • Endianness-, Struct-Packing- und Padding-Diskrepanzen zwischen 32-Bit Microcontrollern (CP/C-Strukturen) und 64-Bit Microprozessoren (AP/C++-Objekte) müssen im Mapping-Generator deterministisch aufgelöst werden.
  • Laufzeit-Optimierung:
    • Durch den direkten IPC-Transport entfällt der Overhead des TCP/IP-Stacks sowie die Notwendigkeit von SOME/IP-Serialization und SOME/IP-SD (Service Discovery), sofern die Zuordnung statisch im Manifest definiert ist.
