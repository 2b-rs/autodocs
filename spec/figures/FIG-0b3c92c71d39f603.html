1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm) mit integrierten Zustands- und Modus-Annotationen (State Invariants auf der Lebenslinie).
  • Funktionale Einordnung: AUTOSAR Classic Platform (CP), Schicht der Kommunikationsdienste (Communication Services, BSW). Dargestellt ist das Zusammenspiel zwischen dem generischen Netzwerkmanagement (Nm) und dem busspezifischen FlexRay-Netzwerkmanagement (FrNm) gemäß AUTOSAR_CP_SWS_FlexRayNetworkManagement (R23-11), Kapitel 9 (Sequence Diagrams).
  • Technischer Zweck: Veranschaulichung des synchronen Steuerflusses (Netzwerkanforderung und -freigabe durch die oberen Schichten) und der asynchronen Rückmeldungen von Zustandswechseln des FlexRay-spezifischen NM-Zustandsautomaten an die generische NM-Schnittstelle.

2. Komponenten, Entitäten & Schnittstellen

Akteure / BSW-Module (Lebenslinien)
  • «module» Nm: Generische NM-Schnittstelle (Koordinator und Vermittler zwischen BswM/ComM und busspezifischen NM-Modulen).
  • «module» FrNm: FlexRay-spezifisches NM-Modul zur Überwachung und Steuerung des FlexRay-Clusters gemäß NM-Zustandslogik (TDMA-spezifisch).
Schnittstellen & Aufrufe
  • FrNm_NetworkRequest(NetworkHandle):
    • Richtung: Nm → FrNm (synchroner Funktionsaufruf).
    • Semantik: Fordert aktiven Busbetrieb für den spezifizierten Kanal/Knoten an.
  • FrNm_NetworkRelease(NetworkHandle):
    • Richtung: Nm → FrNm (synchroner Funktionsaufruf).
    • Semantik: Gibt die aktive Kommunikationsanforderung frei (Signalisiert Schlafbereitschaft).
  • Nm_StateChangeNotification(nmNetworkHandle, nmPreviousState, nmCurrentState):
    • Richtung: FrNm → Nm (Callback-Notification).
    • Parameter:
      • nmNetworkHandle: Index des betroffenen NM-Kanals (NetworkHandleType).
      • nmPreviousState: Vorheriger NM-Zustand (Nm_StateType, z. B. NM_STATE_BUS_SLEEP, NM_STATE_SYNCHRONIZE).
      • nmCurrentState: Neuer NM-Zustand (Nm_StateType, z. B. NM_STATE_SYNCHRONIZE, NM_STATE_NORMAL_OPERATION).
Zustandsentitäten (State Invariants) auf FrNm
  • Modi / Zustände:
    • Bus Sleep Mode (initialer Ruhezustand).
    • Synchronize Mode (FlexRay-spezifischer Zwischenmodus zur Cluster- und Zyklussynchronisation).
    • Network Mode mit Subzustand Normal Operation State.
    • Repeat Message State (Einstiegs-/Wiederholzustand innerhalb des Network Mode).
  • Interne Request-Flags:
    • Network Released (Bus freigegeben / keine lokale Anforderung).
    • Network Requested (aktiver Busbetrieb von oberer Schicht angefordert).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialer Ausgangszustand:
    • FrNm befindet sich im Bus Sleep Mode; der interne Anforderungsstatus ist Network Released.
  2. **Netzwerkanforderung (Wake-up / Active Startup):**
    • Nm ruft synchron FrNm_NetworkRequest(NetworkHandle) auf.
    • FrNm wechselt intern vom Zustand Network Released auf Network Requested und quittiert den Aufruf synchron (FrNm_NetworkRequest()).
  3. Eintritt in Synchronize Mode:
    • Vor dem eigentlichen Senden von NM-PDUs muss das FlexRay-Cluster synchronisiert sein.
    • FrNm meldet den Zustandsübergang von Bus Sleep Mode nach Synchronize Mode über Nm_StateChangeNotification(nmNetworkHandle, nmPreviousState, nmCurrentState) an Nm.
  4. Übergang in Network Mode / Normal Operation State:
    • Nach erfolgreicher Synchronisation wechselt FrNm in den Network Mode in den Normal Operation State (mit gesetztem Status Network Requested).
    • FrNm meldet den Zustandsübergang erneut via Nm_StateChangeNotification(...) an Nm.
  5. **Netzwerkfreigabe (Network Release):**
    • Die Applikation bzw. der ComM benötigt den Bus nicht mehr; Nm ruft synchron FrNm_NetworkRelease(NetworkHandle) auf.
    • Der Funktionsaufruf kehrt synchron zurück.
  6. Folgezustand nach Release:
    • FrNm meldet den resultierenden Zustandswechsel via Nm_StateChangeNotification(...) an Nm.
    • Diagramm-Besonderheit / Diskrepanz: Das Diagramm visualisiert hier den Eintritt in den Repeat Message State mit Flag Network Requested. (Normativer Kontext: Im regulären FrNm-Zustandsautomaten führt eine lokale Freigabe ohne externe Keep-Alive-Bedingung in den Ready Sleep State. Die Darstellung in Figure 9.4 zeigt entweder einen unmittelbaren Re-Trigger / Knotenerkennungszyklus oder eine bekannte redaktionelle Unschärfe in der SWS-Grafik bezüglich des resultierenden Zustandsbanners).

4. Normative Relevanz & Entwickler-Hinweise

  • Asynchronität von State Changes: Der Aufruf von FrNm_NetworkRequest() bzw. FrNm_NetworkRelease() führt nicht unmittelbar im selben Ausführungskontext zum Erreichen des Zielzustands. Entwickler dürfen keine Annahmen über den sofortigen Vollzug treffen; erst das Eintreffen der Nm_StateChangeNotification() signalisiert den tatsächlichen Zustandswechsel.
  • FlexRay-Spezifikum Synchronize Mode: Im Gegensatz zu CAN (wo der Zustandswechsel von Bus Sleep direkt in den Repeat Message State des Network Mode erfolgt), erzwingt FlexRay den Synchronize Mode. NM-Botschaften können erst nach erfolgter Zyklussynchronisation gesendet werden.
  • Konfigurationsabhängigkeit:
    • Der Callback Nm_StateChangeNotification wird nur gefeuert, wenn NmStateChangeInd.Enabled (NmStateReportEnabled / FrNmStateChangeIndicationEnabled) in der BSW-Konfiguration (ARXML) aktiviert ist.
    • Reentrancy: FrNm_NetworkRequest und FrNm_NetworkRelease sind pro NetworkHandle synchron und nicht reentrant für denselben Handle.
  • Zyklischer Task-Kontext (FrNm_MainFunction): Die tatsächliche Zustandsfortschreibung und der Aufruf von Nm_StateChangeNotification finden typischerweise im Kontext der zyklischen FrNm_MainFunction_<Channel>() oder über FlexRay-Trigger-Events (z. B. Start-of-Cycle) statt, entkoppelt vom Aufruferkontext des Nm.
