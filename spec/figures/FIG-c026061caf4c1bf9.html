1. Diagrammtyp & Architektur-Kontext

UML-Sequenzdiagramm zur Spezifikation von Update and Configuration Management (UCM) innerhalb der AUTOSAR Adaptive Platform. Das Diagramm illustriert das Verhalten bei einem fehlgeschlagenen Rollback nach einem vorangegangenen Fehler während einer Software-Update-Kampagne sowie die darauffolgende Behandlung des Fehlers mit anschließender erfolgreicher Bereinigung im Kontext von V-UCM-Sequenzen.

2. Komponenten, Entitäten & Schnittstellen

Beteiligte Entitäten und Lebenslinien (from V-UCM sequences):

  • V-UCM: Zentraler Fahrzeug-UCM (Vehicle UCM).
  • Vehicle State Manager: Überwacht und setzt fahrzeugweite Betriebszustände.
  • Driver HMI: Benutzerschnittstelle / Anzeige für den Fahrer.
  • UCM 1: Untergeordnete UCM-Instanz auf der Machine.
  • SM (State Management): Zustandsverwaltung für Funktionsgruppen und Maschinenmodi.
  • EM (Execution Management): Ausführungs- und Prozessverwaltung.
  • Application: Auszuführende Adaptive Application(s).
  • Persistency: Adaptive-Plattform-Dienst für persistente Datenspeicherung.

Schnittstellen & Interaktionsnachrichten:

  • V-UCM / UCM 1: CurrentStatus = kRollingBackFailed(), CampaignState = kRollingBackFailed(), Rollback(), CurrentStatus = kRolledBack(), Finish(), CurrentStatus = kIdle().
  • UCM 1 / SM / EM / Application / Persistency: Reparse Manifest(), VerifyUpdate(vector<FunctionGroup>), Failing(), Raise DTC(), PrepareRollBack(vector<FunctionGroup>), ResetMachine(), ReparseManifest(), success(), StopUpdateSession(), Normal(), OpenXXX(), Check version and replace failing persistent by backup().
  • V-UCM / HMI / State Manager: Set vehicle in degraded state(), Inform failure to driver(), Call for help to fix failed SWCL().

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm fokussiert auf den Ablauf ab dem Scheitern des ersten Rollbacks:

  1. RollingBack (Fehlgeschlagen): UCM 1 führt Reparse Manifest() aus. Innerhalb der Schleife loop for each SoftwareCluster stößt UCM 1 via VerifyUpdate(vector<FunctionGroup>) die Verifikation über SM, EM und Application an; SM meldet Failing() zurück an UCM 1.
  2. kRollingBackFailed / Rollback_Failed: UCM 1 führt intern Raise DTC() aus und übermittelt CurrentStatus = kRollingBackFailed() an V-UCM (im Zustand Cancelling). V-UCM wechselt nach Rollback_Failed, setzt via Vehicle State Manager das Fahrzeug in einen degradierten Zustand (Set vehicle in degraded state()), benachrichtigt über Driver HMI den Fahrer (Inform failure to driver()), ruft intern Call for help to fix failed SWCL() auf und stößt erneut Rollback() an UCM 1 an.
  3. RollingBack (Zweiter Versuch): UCM 1 führt pro Cluster PrepareRollBack(vector<FunctionGroup>) mit SM aus. Im Fragment alt Machine Reset erfolgt entweder ResetMachine() an SM oder lokal ReparseManifest(). Die anschließende Verifikation VerifyUpdate(vector<FunctionGroup>) pro Cluster wird von SM mit success() quittiert.
  4. RolledBack / CleaningUp / Idle: UCM 1 meldet CurrentStatus = kRolledBack() an V-UCM. V-UCM sendet Finish(). UCM 1 ruft StopUpdateSession() an SM auf, welches EM informiert. SM setzt Application auf Normal(); Application öffnet Persistency (OpenXXX()) und führt Check version and replace failing persistent by backup() aus. Abschließend meldet UCM 1 CurrentStatus = kIdle() an V-UCM, welches in Idle übergeht.

4. Normative Relevanz & Entwickler-Hinweise

Spezifiziert das Fehlerbehandlungs- und Rollback-Protokoll der Adaptive Platform UCM gemäß AUTOSAR. Zeigt die normative Pflicht zur Umschaltung in den Zustand kRollingBackFailed bei Nicht-Verifizierbarkeit eines Rollbacks, das Absetzen von Diagnose-Ereignissen (DTC), die Benachrichtigung des Vehicle State Managers zur Absicherung des Fahrzeugzustands und die Interaktion mit dem Fahrer. Nach Korrektur des fehlerhaften SoftwareClusters muss eine saubere Wiederherstellung über Rollback und persistente Backups bis zum Zustand kIdle erfolgen.
