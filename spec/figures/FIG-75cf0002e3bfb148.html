1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Classic Platform (CP) Schichtenarchitektur-Diagramm (Layered Architecture View) mit expliziter Klassifikationsmatrix für Schnittstellentypen (API 0, API 1, API 2).
  • Technischer Zweck: Spezifikation der Integration des Synchronized Time-base Manager (StbM, BSW System Service) in die ECU-Architektur. Das Diagramm fokussiert auf die Adressierung der Fragestellung „How does the SW-C access the Synchronized Time-base Mgr?“ über standardisierte RTE-Service-Ports (VFB-Ebene) im Kontrast zu direkten C-Schnittstellen (API 0) innerhalb des Basissoftware-Stacks.
  • Funktionale Einordnung (Safety-Kontext): Bereitstellung einer knotenübergreifend synchronisierten Zeitbasis (Global Time Base) für zeitgesteuerte, sicherheitskritische Applikationen (z. B. deterministische Fusion von Sensordaten, E2E-Laufzeitabsicherung, Safety-Deadlines nach ISO 26262).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Schichtenzuordnung
  • Application Software Component (SW-C): Applikationsschicht; enthält funktionale Softwarekomponenten mit typisierten Ports basierend auf AUTOSAR Interfaces.
  • AUTOSAR Runtime Environment (RTE): Middleware-Abstraktion; realisiert den Virtual Functional Bus (VFB) auf ECU-Ebene und entkoppelt Applikation von BSW.
  • Synchronized Time-base Manager (StbM): BSW-Systemdienst (Services Layer); verwaltet globale Zeitbasen (Master/Slave), berechnet Offsets, interpoliert die Virtual Local Time (VLT) und stellt Statusinformationen bereit.
  • Operating System (OS): System Service; stellt Hardware-Ticks, Counter, Alarme und zeitgesteuerte Schedule Tables bereit.
  • Communication (COM-Stack): Beinhaltet protokollspezifische Time-Sync-Module (z. B. CanTSyn, EthTSyn, FrTSyn).
  • ECU Abstraction / MCAL: Hardwareabstraktion für Timer-Hardware (z. B. GPT, ICU, RTC).
  • Complex Device Drivers (CDD): Direktanbindung hardwarenaher oder proprietärer Zeitquellen unter Umgehung der BSW-Standardschichten.
Schnittstellenklassifikation & Relationen
  • API 2 (VFB & RTE relevant – blauer Doppelpfeil):
    • Schnittstellentyp: Standardisiertes AUTOSAR Interface (Client-Server / Sender-Receiver Port-Interaktion).
    • Pfad: SW-C ↔ RTE ↔ StbM (Service Port). Dies ist die funktionale Antwort auf die Kernfrage des Diagramms: Die SW-C greift ausschließlich portbasiert über die RTE auf den StbM zu (ServiceSwComponentType).
  • API 1 (RTE relevant – oranger Doppelpfeil):
    • Schnittstellentyp: Standardized Interface zwischen BSW-Modulen (OS, COM) und der RTE zur Verwaltung von Callbacks, BSW-Scheduler-Events und Task-Aktivierungen.
  • API 0 (BSW-intern – petrolgrüner Pfad):
    • Schnittstellentyp: Direkte C-Funktionsaufrufe (Standardized Interface) zwischen BSW-Modulen ohne RTE-Zwischenschaltung:
      • StbM ↔ OS: Abgleich und Synchronisation von OS-Schedule-Tables (SyncScheduleTable).
      • StbM ↔ COM: Übergabe synchronisierter Netzwerkzeitstempel durch Bus-Synch-Treiber (StbM_BusSetGlobalTime).
      • StbM ↔ ECU Abstraction: Abruf von Low-Level-Hardware-Timern / Capture-Registern.

3. Dynamisches Verhalten & Sequenzablauf

A. Zeitabfrage durch Applikation (API 2, synchroner/asynchroner Port-Call)
  1. Trigger: SW-C benötigt konsistenten Zeitstempel oder Zeitbasis-Status.
  2. Aufruf: SW-C ruft portgenerierte RTE-API auf (z. B. Rte_Call_<port>_GetCurrentTime(&timeStamp, &userDataType)).
  3. Dispatching: RTE leitet den Aufruf über den VFB an die C-API der Service-Komponente des StbM weiter.
  4. Berechnung: StbM addiert die über Hardware-Timer interpolierte Drift zur zuletzt synchronisierten Global Time und liefert das Zeittupel (seconds, nanoseconds, timeBaseStatus) zurück.
B. Bus-Zeitsynchronisation (API 0, netzwerkgetrieben)
  1. Trigger: Empfang einer Sync-/Follow-Up-PDU auf dem Kommunikationsbus (Ethernet gPTP, CAN, FlexRay).
  2. Ingress Timestamping: COM/TSyn-Treiber (z. B. EthTSyn) erfasst den exakten Aufnahmezeitpunkt.
  3. Aktualisierung: COM übergibt Zeitdaten via direkter C-API (API 0) an den StbM (StbM_BusSetGlobalTime()).
  4. OS-Kopplung: Bei konfigurierter OS-Schedule-Table-Synchronisation triggert der StbM über API 0 das OS zur Korrektur des Schedule-Table-Phasenversatzes.
  5. Fehlerpfade:
    • Ausbleiben von Sync-Nachrichten führt zum Timeout der Zeitbasis → StbM setzt Statusflag TIMEOUT und meldet Fehler an das DEM (STBM_E_SYNC_LOSS).
    • Ungültige API-Parameter triggern DET-Einträge (STBM_E_PARAM).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur-Integrität & Speicherschutz (Safety-Relevanz):
    • SW-Cs dürfen StbM.h niemals direkt inkludieren. Ein Zugriff unter Umgehung der RTE verletzt die VFB-Architektur und hebelt Speicherschutzgrenzen (OS-Memory-Partitions) aus.
    • Läuft die SW-C in einer nicht-vertrauenswürdigen Partition (z. B. QM/ASIL-A) und der StbM in einer ASIL-D-Partition, erzwingt die RTE einen sicheren Partitionswechsel (Cross-Partition Call via OS Trusted Function).
  • ARXML-Modellierung:
    • Der StbM muss im EcuExtract als ServiceSwComponentType deklariert sein.
    • In der SW-C ist ein R-PortPrototype mit dem standardisierten Interface (z. B. GlobalTime_GetCounter oder GlobalTime_Master_...) zu instanziieren und im System-Composite mit dem P-PortPrototype des StbM zu verbinden (Service Mapping).
  • BSW-Integration & OS-Scheduling:
    • Zyklischer Aufruf von StbM_MainFunction() muss in einem festen BSW-Task mit minimalem Jitter konfiguriert werden, um Rechenfehler bei der lokalen Zeitinterpolation (VLT) zu vermeiden.
    • Hardwarespezifische Time-Stamping-Fähigkeiten (z. B. MII/RMII Ethernet Timestamping) müssen zwingend konsistent über MCAL/EthTRCV und EthTSyn auf die passende StbMTimeBaseId gemappt werden.
