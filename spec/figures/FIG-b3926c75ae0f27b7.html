1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB- (Virtual Functional Bus) und Software-Architektur-Diagramm (Komponentendiagramm mit Schnittstellen- und Daten-Mapping sowie BSW-Interaktion).
  • Technischer Zweck & Einordnung: Spezifikation des Use Case 3 („Sharing of NVRAM blocks / Fine-grained NVRAM Access“) gemäß AUTOSAR_EXP_NVDataHandling (Classic Platform, R4.3.1 – R19-11). Das Diagramm definiert das Architekturmuster, bei dem anwendungsseitige Software-Komponenten (ApplicationSwComponentType) nicht direkt auf den BSW-NVRAM Manager (NvM) zugreifen, sondern über eine zwischengeschaltete Komponente vom Stereotyp «NvBlockSwComponentType» (NvM-NvBlock). Es demonstriert sowohl das 1:1-Mapping ganzer Datenstrukturen als auch das strukturierte Bitfeld-/Element-Mapping mehrerer SWCs auf einen gemeinsamen NV-RAM-Block (ramblock1) inklusive NvM-Mirror-Synchronisation.

2. Komponenten, Entitäten & Schnittstellen

Akteure & Software-Komponenten
  • SWC1 (ApplicationSwComponentType): Exklusiver Nutzer von NvBlockDescriptor0. Hält lokale Struktur nvData0: struct0 { uint32 a; uint8 b; }.
  • SWC2 (ApplicationSwComponentType): Teilt sich NvBlockDescriptor1. Nutzt nvData2: uint8 b (Sender) und nvData1: boolean a (Receiver).
  • SWC3 (ApplicationSwComponentType): Teilt sich NvBlockDescriptor1 und besitzt Service-Kontrolle darüber. Nutzt nvData4: boolean d (Sender) sowie nvData3: uint16 c (Sender).
  • NvM-NvBlock («NvBlockSwComponentType»): Kapselt NV-Datenblöcke und deren RAM-Spiegel (ramblock0, ramblock1), entkoppelt SWCs von NvM-internen Block-IDs:
    • NvBlockDescriptor0: Kapselt ramblock0: struct0 { uint32 a; uint8 b; } rb0; (1:1-Mapping zu SWC1).
    • NvBlockDescriptor1: Kapselt ramblock1: struct1 { uint16 y; uint8 x; } rb1; (Shared Block für SWC2 und SWC3).
  • NvM (BSW-Modul NVRAM Manager): BSW-Dienstleister mit internem Puffer NVMBuffer[size = biggest block] (NVM Mirror) und asynchroner Auftrags-Warteschlange (Request1, Request2, ...).
Ports & Schnittstellen (Interfaces)
  • Sender/Receiver (S/R) Ports (Datenpfad):
    • SWC1.NvData0 (P-Port) → NvBlockDescriptor0.NvM_NvData0 (R-Port): 1:1-Mapping nvData0 <-> rb0.
    • SWC2.NvData2 (P-Port) → NvBlockDescriptor1.NvM_NvData2 (R-Port): Teil-Mapping b <-> rb1.x(4:1) (Bitfeld 1 bis 4 in Byte x).
    • 1:n S/R-Verbindung: SWC3.NvData4 (P-Port, sendet boolean d) ist gekoppelt an:
      • SWC2.nvData1 (R-Port, empfängt boolean a),
      • NvBlockDescriptor1.NvM_NvData1 (R-Port, persistiert in rb1.x(0)). Damit wird der Wert gleichzeitig zwischen SWCs übertragen und im NV-RAM-Block archiviert.
    • SWC3.NvData3 (P-Port) → NvBlockDescriptor1.NvM_NvData3 (R-Port): Element-Mapping c <-> rb1.y (uint16).
  • Client/Server (C/S) Ports (Service- & Admin-Pfad):
    • NvMService / NvMServices (R-Port an SWC → P-Port NvM_PS_* an Desriptor): Ermöglicht SWC das Anfordern von NV-Operationen (z. B. ReadBlock, WriteBlock, RestoreBlockDefaults, EraseNvBlock).
    • NvMAdmin (R-Port an SWC → P-Port NvM_PAdmin_* an Descriptor): Administrative Steuerbefehle (z. B. SetBlockProtection).
    • NvM_NotifyInitBlock (P-Port an SWC ← R-Port NvM_PNIB_* an Descriptor): Callback zur Initialisierung uninitialisierter/korrupter Blöcke (Init-Callback via RTE).
    • NvM_NotifyJobFinished (P-Port an SWC ← R-Port NvM_PNJF_* an Descriptor): Asynchrone Endemeldung eines NvM-Auftrags.

3. Dynamisches Verhalten & Sequenzablauf

  1. Datenaustausch & Aggregation im RAM-Block (SWC → RTE → NvBlockSwComponentType):
    • SWCs schreiben periodisch oder ereignisgesteuert via S/R-Kommunikation (Rte_Write_*).
    • Die RTE bzw. der NvBlockSwComponentType setzt die atomaren/zusammengesetzten Werte in die RAM-Blöcke (rb0, rb1) um. Bitmaskierung und Serialisierung (rb1.x(4:1), rb1.x(0), rb1.y) werden auf VFB-/RTE-Ebene aufgelöst.
  2. Auslösung des NV-Auftrags (Service-Trigger):
    • Autorisierte SWC (hier: SWC1 für Block 0, SWC3 für Block 1; SWC2 besitzt keine Service-Ports) ruft C/S-Operation auf: Rte_Call_<P>_WriteBlock() / SetRamBlockStatus().
    • Der Aufruf wird an das BSW-Modul NvM delegiert (NvM_WriteBlock(), NvM_SetRamBlockStatus()).
  3. Asynchrone Abarbeitung & Spiegel-Synchronisation (NvM Explicit Synchronization):
    • Der NvM reiht den Auftrag in seine FIFO-/Prioritäts-Queue ein (Request1, Request2).
    • Bei Verwendung des NvM-Mirrors (NVMBuffer) fordert der NvM die Daten über RTE-Callbacks an:
      • Rte_Call_<P>_WriteRamBlockToNvM(): Kopiert Daten aus dem SWC-/NvBlock-RAM-Block konsistent in den internen NVMBuffer des NvM, um Dateninkonsistenzen während des Schreibvorgangs auf das Speichermedium (EEPROM/Flash via MemIf/Fee/Ea) zu verhindern.
      • Analog beim Lesen: Rte_Call_<P>_ReadRamBlockFromNvM() transferiert gelesene Nutzdaten vom NVMBuffer in den RAM-Block.
  4. Abschluss & Notifikation:
    • Nach erfolgreichem/fehlerhaftem physikalischem Schreiben ruft der NvM die RTE-Notifikation auf (Rte_Call_<P>_NvMNotifyJobFinished), die über den P-Port NvM_PNJF_* des Descriptors an den R-Port von SWC1 bzw. SWC3 propagiert wird.
    • Falls der NvM beim Hochlauf ungültige Daten detektiert (z. B. CRC-Fehler), triggert er Rte_Call_<P>_NvMNotifyInitBlock, wodurch die SWC über NvM_NotifyInitBlock Default-Werte in den RAM-Block einspeisen kann.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Konfiguration (RteNvRamAllocation):
    • Die Verknüpfung zwischen dem BSW-NvM-Block und dem SW-C-seitigen NvBlockDescriptor erfolgt in der RTE-Konfiguration über die Referenzen RteNvmBlockRef (zeigt auf NvMBlockDescriptor im NvM-BSW) und RteSwNvBlockDescriptorRef (zeigt auf den Deskriptor im NvBlockSwComponentType).
    • Eine direkte Adressierung des NvM-Blocks über numerische Block-IDs in den Applikations-SWCs entfällt vollständig.
  • Shared NVRAM Access & Bit-Field Packing (Einschränkungen):
    • In Use Case 3 teilen sich mehrere SWCs (SWC2, SWC3) einen physischen NVRAM-Block (ramblock1).
    • Ownership-Konflikte: Nur eine koordinierende SWC (SWC3) darf typischerweise die Service-Ports (NvMService, NvMAdmin) bedienen, um konkurrierende Schreibbefehle (NvM_WriteBlock) zu vermeiden.
    • Datenkonsistenz: Werden Teilbereiche eines Bytes (rb1.x(4:1) vs. rb1.x(0)) von verschiedenen SWCs modifiziert, muss die RTE bzw. der generierte Code des NvBlockSwComponentType Lese-Modifiziere-Schreib-Zyklen (Read-Modify-Write) thread-sicher (mittels Interrupt-Sperren oder atomaren Zuweisungen) kapseln.
  • Pufferverwaltung (NvMUseSyncMechanism):
    • Die im Diagramm dargestellten Operationen ReadRamBlockFromNvM und WriteRamBlockToNvM implizieren die NvM-Konfigurationsoption NvMUseSyncMechanism == TRUE.
    • Entwickler müssen sicherstellen, dass die RAM-Spiegel-Callbacks innerhalb eines deterministischen Zeitschlitzes bedient werden und der globale NVMBuffer mindestens so groß dimensioniert ist wie der größte konfigurierte NV-Block (size = biggest block).
