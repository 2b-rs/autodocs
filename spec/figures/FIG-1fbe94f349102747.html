1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECUC Parameter Configuration Metamodel (UML-Klassendiagramm zur Definition des Konfigurationsschemas für das BSW-Modul DoIP).
  • Funktionale Einordnung: Definiert die Konfigurationsparameter und Datenstrukturen für die Routing-Aktivierung im DoIP-Modul (Diagnostic over IP, ISO 13400-2). Dient der Autorisierung und Zuordnung logischer Zieladressen (DoIPTargetAddress) zu einer aktiven TCP-Verbindung über spezifische Aktivierungstypen, einschließlich optionaler Authentifizierungs- und Bestätigungs-Callbacks sowie TLS-Anforderungen.

2. Komponenten, Entitäten & Schnittstellen

  • Hauptcontainer:
    • DoIPRoutingActivation (EcucParamConfContainerDef, Multiplizität 0..255): Repräsentiert eine spezifische Routing-Aktivierungsregel innerhalb der DoIP-Konfiguration.
  • Direkte Parameter & Referenzen von DoIPRoutingActivation:
    • DoIPRoutingActivationNumber (EcucIntegerParamDef, Multiplizität 1, Wertebereich 0..255): Numerischer Identifikator des Routing-Aktivierungstyps gemäß ISO 13400-2 (z. B. 0x00 Standard, 0x01 WWH-OBD, 0xE0..0xFF OEM-spezifisch).
    • DoIPRoutingActivationSecurityRequired (EcucBooleanParamDef, Multiplizität 0..1, Default false): Erzwingt eine gesicherte Verbindung (TLS / Secure Communication) als Vorbedingung für diese Routing-Aktivierung.
    • DoIPTargetAddressRef (EcucReferenceDef, Multiplizität 1..65535): Referenzbeziehung (+destination) auf den Zielcontainer DoIPTargetAddress (EcucParamConfContainerDef, Multiplizität 1..65535). Definiert die logischen Zieladressen, die durch diesen Aktivierungstyp freigeschaltet werden.
  • Subcontainer DoIPRoutingActivationConfirmationCallback (EcucParamConfContainerDef, Multiplizität 0..1):
    • Definiert den Bestätigungs-Callback bei eingehender Routing-Aktivierung.
    • DoIPRoutingActivationConfirmationFunc (EcucFunctionNameDef, Multiplizität 0..1): C-Funktionsname für den Bestätigungsaufruf.
    • DoIPRoutingActivationConfirmationReqLength (EcucIntegerParamDef, Wertebereich 0..4 Bytes): Länge der zusätzlichen Bestätigungsanforderungsdaten im Payload.
    • DoIPRoutingActivationConfirmationResLength (EcucIntegerParamDef, Wertebereich 0..4 Bytes): Länge der zusätzlichen Bestätigungsantwortdaten im Response-Payload.
  • Subcontainer DoIPRoutingActivationAuthenticationCallback (EcucParamConfContainerDef, Multiplizität 0..1):
    • Definiert den Authentifizierungs-Callback für den Aktivierungsprozess.
    • DoIPRoutingActivationAuthenticationFunc (EcucFunctionNameDef, Multiplizität 0..1): C-Funktionsname für den Authentifizierungsaufruf.
    • DoIPRoutingActivationAuthenticationReqLength (EcucIntegerParamDef, Wertebereich 0..4 Bytes): Länge der anforderungsspezifischen Authentifizierungsdaten (OEM-spezifischer Payload).
    • DoIPRoutingActivationAuthenticationResLength (EcucIntegerParamDef, Wertebereich 0..4 Bytes): Länge der antwortspezifischen Authentifizierungsdaten.
  • Schnittstellen / Port-Mapping:
    • Wenn DoIPRoutingActivationConfirmationCallback konfiguriert ist, jedoch der C-Funktionsparameter DoIPRoutingActivationConfirmationFunc ausgelassen wird, bindet der DoIP-Stack die Bestätigung über einen R-Port an:
      • Service-Interface: <RoutingActivation>_RoutingActivation
      • Port-Name: CB<RoutingActivation>RoutingActivation (wobei <RoutingActivation> dem SHORT-NAME des Containers DoIPRoutingActivation entspricht).

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger: Empfang einer DoIP Routing Activation Request Message (Payload Type 0x0005) über eine etablierte TCP-Buchse mit Angabe von Quelladresse und Aktivierungstyp (DoIPRoutingActivationNumber).
  2. Security-Prüfung: Ist DoIPRoutingActivationSecurityRequired == true, verifiziert DoIP, ob die zugrundeliegende TCP-Verbindung über TLS gesichert ist. Fehlt TLS, wird der Request abgewiesen (Routing Activation Response Code z. B. 0x07 TLS required).
  3. Authentifizierungsphase (sofern konfiguriert): Aufruf der Funktion DoIPRoutingActivationAuthenticationFunc. Auswertung der Request-Payload (Länge DoIPRoutingActivationAuthenticationReqLength). Schlägt die Authentifizierung fehl, bricht DoIP ab (Response Code 0x04 Authentication missing/denied).
  4. Bestätigungsphase (sofern konfiguriert): Aufruf der C-Funktion DoIPRoutingActivationConfirmationFunc oder Aufruf via RTE über den R-Port CB<RoutingActivation>RoutingActivation. Übergabe von bis zu 4 Bytes OEM-spezifischer Daten (ConfirmationReqLength). Bei negativer Bestätigung Abbruch (Response Code 0x05 Confirmation denied).
  5. Aktivierung & Adressbindung: Bei erfolgreicher Validierung verknüpft DoIP die referenzierten DoIPTargetAddress-Entitäten mit der TCP-Verbindung und sendet eine Routing Activation Response (Payload Type 0x0006) mit Response Code 0x10 (Routing successfully activated) inklusive der generierten Bestätigungs-/Authentifizierungs-Rückgabedaten (ResLength).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration & Codegenerierung:
    • DoIPTargetAddressRef verlangt eine Mindestkardinalität von 1. Jede Routing-Aktivierung muss zwingend auf mindestens eine Zieladresse verweisen.
    • Fehlt die C-Funktionsdeklaration (...Func), muss der BSW-Generator AUTOSAR-konforme Service-Ports im BSW-Description-File (BSWMD) generieren, um die Abfrage über den VFB/RTE an eine Applikations-SW-C zu routen.
  • Puffer- und Payload-Restriktionen:
    • ReqLength und ResLength sind strikt auf 0..4 Bytes limitiert (ISO 13400-2 Restriktion für OEM-spezifische Zusatzfelder im Routing Activation Frame). Der Generator muss Puffergrößen hierfür fest allozieren.
  • Fehlerbehandlung:
    • Timeouts oder Fehler beim Aufruf der synchronen/asynchronen Callbacks führen zum Abbruch der Routing-Aktivierung und deterministischen Schließen oder Zurücksetzen des Socket-Zustands gemäß DoIP-Zustandsmaschine (Initial State vs. Registered Routing Active).
