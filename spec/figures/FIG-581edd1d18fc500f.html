1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Metamodellierungs-Schichtenmodell / Technologische Raum-Matrix (Abbildung der 4-Ebenen-Metahierarchie der OMG [MOF M0 bis M3/M4] über drei orthogonale Technological Spaces).
  • Technischer Zweck & Einordnung: Definition der methodischen und formalen Grundlagen für die Interoperabilität von AUTOSAR-Authoring-Tools. Das Diagramm harmonisiert die abstrakte Metamodellierung (UML/MOF), das Austausch- und Serialisierungsformat (ARXML/XSD) und die proprietäre Werkzeug-Realisierung (In-Memory-Datenstrukturen, Richtlinien) bis hin zur physischen Implementierung im Fahrzeugsteuergerät.

2. Komponenten, Entitäten & Schnittstellen

Die Matrix gliedert sich vertikal in vier Meta-Ebenen und horizontal in drei technologische Räume:

```

AUTOSAR Metamodel Space XML Technological Space AUTOSAR Tools Space

M3/M4 (Meta-Meta) [MOF] <--- [UML Metamodel] [EBNF] (nicht formalisiert)

+ [Template Profile]

| | |

M2 (Meta) [AUTOSAR Metamodel] [XML Grammar] + [XML schema] [Tool Datastructure]

+ [Modeling Guidelines]

| | |

M1 (Modell) [AUTOSAR Model] [XML Description (.arxml)] [Model created by tool]

| | |

M0 (Laufzeit) [AUTOSAR Objects] [Object in Car] [Object in Car]

```

#### Entitäten nach technologischem Raum:

  1. AUTOSAR Metamodel Technological Space (OMG-basiert):
  • M3/M4: MOF (Meta-Object Facility, selbstreferenziell via «instanceOf»), UML Metamodel (ist «instanceOf» MOF) und «profile» AUTOSAR Template Profile (Erweiterung via «import»).
  • M2: AUTOSAR Metamodel (definiert Software-Komponenten, Topologie, BSW-Module; «instanceOf» UML Metamodel unter Anwendung von «apply» des Template Profile).
  • M1: AUTOSAR Model (konkretes System-/Software-Design; «instanceOf» AUTOSAR Metamodel).
  • M0: AUTOSAR Objects (Laufzeitinstanzen im Steuergerät; «instanceOf» AUTOSAR Model).
  1. XML Technological Space (Serialisierungs- und Austauschraum):
  • M3/M4: EBNF (Extended Backus-Naur Form, selbstreferenziell via «instanceOf»).
  • M2: XML Grammar («instanceOf» EBNF) und XML schema (AUTOSAR XSD; via «import» mit der Grammatik verknüpft, selbstreferenziell via «instanceOf»).
  • M1: XML Description (konkrete ARXML-Dateien; syntaktisch «instanceOf» XML Grammar, strukturell validiert via «apply» gegen XML schema).
  • M0: Object in Car (konkrete Ausprägung auf der Hardware; «instanceOf» XML Description).
  1. AUTOSAR Tools Technological Space (Werkzeug-Implementierungsraum):
  • M2: Tool Datastructure (proprietäre interne Datenstrukturen/AST/EMF des Editors) und Modeling Guidelines (projektspezifische Modellierungsregeln; Beziehung über «instanceOf» zu Tool-Datenstrukturen).
  • M1: Model created by tool (das im Authoring-Tool editierte Projektmodell; «instanceOf» Tool Datastructure unter «apply» der Modeling Guidelines).
  • M0: Object in Car (aus dem Tool-Modell kompilierte/geflashte Binärdaten; «instanceOf» Model created by tool).

#### Beziehungen & Stereotypen:

  • «instanceOf»: Vertikale Instanziierung über Meta-Ebenen hinweg (M0 $\rightarrow$ M1 $\rightarrow$ M2 $\rightarrow$ M3).
  • «apply»: Anwendung normativer Einschränkungen und Regelwerke (UML-Profil auf Metamodell, XSD-Validierung auf ARXML-Instanz, Guidelines auf Tool-Modell).
  • «import»: Einbindung externer Grammatiken oder Meta-Spezifikationen.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Metamodellierungs- und Klassifikationsdiagramm handelt, existiert kein dynamischer Laufzeit-Kontrollfluss. Der implizite Design-Time- und Tooling-Workflow verläuft wie folgt:

  1. Metamodell-Definition (M2): Das normative AUTOSAR Metamodel wird unter Nutzung des AUTOSAR Template Profile definiert und automatisiert in das korrespondierende XML schema (XSD) überführt.
  2. Tool-Abbildung (M2 $\rightarrow$ M1): Ein Authoring-Tool implementiert interne Speicherstrukturen (Tool Datastructure), die das M2-Metamodell abbilden. Der Anwender modelliert das System (Model created by tool) unter Einhaltung definierter Modeling Guidelines.
  3. Serialisierung / Interoperabler Austausch (M1): Das interne Modell wird in eine konforme XML Description (.arxml) serialisiert und gegen das normative XML schema validiert.
  4. Code- & Konfigurations-Generierung (M1 $\rightarrow$ M0): BSW- und RTE-Generatoren konsumieren die XML Description und erzeugen C-Header/Source-Dateien sowie Konfigurationsstrukturen, die als Object in Car im Flash/RAM des Mikrocontrollers instanziiert werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Herstellerübergreifende Interoperabilität: Proprietäre Werkzeug-Datenstrukturen (Tool Space) sind nicht interoperabel. Der Datenaustausch zwischen Werkzeugen (z. B. System-Authoring $\leftrightarrow$ BSW-Konfigurator $\leftrightarrow$ RTE-Generator) ist ausschließlich über den XML Technological Space (M1 ARXML) auf Basis des normativen Schemas (M2 XSD) spezifikationskonform.
  • Verbindlichkeit der XSD-Validierung: Werkzeuge und Codegeneratoren müssen eingehende ARXML-Dateien zwingend gegen das M2-XML-Schema validieren («apply»). Semantische oder strukturelle Abweichungen führen zum Abbruch der Toolchain-Verarbeitung.
  • Rolle der Modeling Guidelines: Das XSD-Schema deckt lediglich syntaktische und strukturelle Randbedingungen ab. Zusätzliche semantische Integritätsregeln (z. B. eindeutige Short-Names, spezifische Task-Zuordnungen oder Kommunikationsmuster) müssen über Modeling Guidelines und Modellprüfer (z. B. OCL/Schematron) abgesichert werden.
  • Keine Meta-Informationen zur Laufzeit (M0): Mikrocontroller-Software (Object in Car) hält keine Metamodell-Informationen vor. Alle M2/M1-Attribute müssen vor dem Build-Prozess vollständig in statische Typen, Deskriptortabellen (const, Flash) oder fixe Puffer aufgelöst sein.
