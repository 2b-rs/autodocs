1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Topologiediagramm / Netzwerk-Architekturschaubild mit Zuordnung von AUTOSAR-ComM-Kanalkonfigurationen (ComMChannel) zu partiellen Netzwerkclustern (ComMPnc).
  • Technischer Zweck: Veranschaulichung eines Randfalls im partiellen Netzwerk-Routing (PNC-Gateway nach AUTOSAR Classic ComM). Das Schaubild visualisiert die Konsequenzen, wenn ein Multi-Channel-Knoten (Node2) denselben PNCs ([PNC1, PNC2]) auf mehreren Kanälen zugeordnet ist, jedoch keine PNC-Gateway-Koordination (ComMPncGatewayType nicht konfiguriert) zwischen diesen Kanälen durchführt.
  • Funktionale Einordnung: AUTOSAR Communication Manager (ComM), Submodul Partial Network Management (Pnm). Es definiert die Schnittstelle zwischen PNC-Zustandsmaschinen, External Request Array (ERA), Internal Request Array (IRA) und den physikalischen ComMChannel-Instanzen.

2. Komponenten, Entitäten & Schnittstellen

  • Knoten / ECUs:
    • PNC-Coor1 (PNC-Koordinator 1): Hostet [PNC1, PNC2]; Kanäle Ch1 und Ch2 jeweils als ACTIVE Gateway (ComMPncGatewayType = COMM_GATEWAY_TYPE_ACTIVE) konfiguriert.
    • PNC-Coor2 (PNC-Koordinator 2): Hostet [PNC1, PNC2]; besitzt drei Kanäle:
      • Ch1: Als PASSIVE Gateway konfiguriert (COMM_GATEWAY_TYPE_PASSIVE), gekoppelt an PNC-Coor1.Ch1.
      • Ch2: Als ACTIVE Gateway konfiguriert (COMM_GATEWAY_TYPE_ACTIVE), bindet Node1 an.
      • Ch3: Als ACTIVE Gateway konfiguriert (COMM_GATEWAY_TYPE_ACTIVE), bindet den gemeinsamen Bus (Node2, Node3, Node4) an.
    • Node1, Node3, Node4 (Standard-PNC-Knoten): Single-Channel-Knoten mit [PNC1, PNC2]; ComMPncGatewayType ist nicht gesetzt (NONE).
    • Node2 (Fokus-Knoten, rot hervorgehoben): Dual-Channel-Knoten (Ch1, Ch2), beiden Kanälen sind PNC1 und PNC2 zugewiesen; an beiden Kanälen ist ComMPncGatewayType nicht gesetzt (N).
  • Konfigurationsparameter & Stereotypen:
    • ComMPncGatewayType (Parameter in ComMChannelPerPnc bzw. ComMChannel):
      • ACTIVE (Gelb / A): Koordinator leitet interne/externe PNC-Anforderungen aktiv über Netzwerkmanagement-PDUs (NM-PDU / ERA) weiter und hält den Kanal aktiv.
      • PASSIVE (Blau / P): Empfängt PNC-Anforderungen, spiegelt diese jedoch nicht aktiv zurück bzw. dient als abhängiger Zweig im Koordinationsbaum.
      • NOT set / NONE (Orange / N): Keine Routing- und Aggregationslogik für PNCs zwischen den Kanälen dieses Knotens aktiv.
  • Beziehungen:
    • PNC-Coor1.Ch2 ist Punkt-zu-Punkt mit Node2.Ch1 verbunden.
    • PNC-Coor2.Ch3, Node2.Ch2, Node3.Ch1 und Node4.Ch1 teilen sich ein physikalisches Multidrop-Bussystem.

3. Dynamisches Verhalten & Sequenzablauf

  • Fehlende kanalübergreifende PNC-Zustandssynchronisation in Node2:
    1. Autarke Kanalzustandsmaschinen: Da Node2 kein Gateway ist, wertet ComM in Node2 Anfragen (ERA/IRA) pro Kanal isoliert aus. Es findet kein interner Transfer von PNC-Zuständen zwischen Ch1 und Ch2 statt.
    2. Anforderungs-Pfad A (über PNC-Coor1): Wird ein PNC auf PNC-Coor1 aktiv, sendet dieser NM-Vektoren über Ch2 an Node2.Ch1. Node2.Ch1 wechselt in COMM_FULL_COMMUNICATION.
    3. Problemfall Asynchronität: Solange PNC-Coor2 (oder ein anderer Busteilnehmer) denselben PNC nicht gleichzeitig auf dem unteren Bus anfordert, verbleibt Node2.Ch2 in COMM_NO_COMMUNICATION bzw. COMM_SILENT_COMMUNICATION.
    4. Applikations-Erwartungsbruch: Eine SW-C auf Node2, die ComM_RequestComMode(..., COMM_FULL_COMMUNICATION) für PNC1 ausführt oder sich auf die Verfügbarkeit von PNC1 verlässt, erwartet deterministisch, dass alle diesem PNC zugeordneten Kommunikationskanäle betriebsbereit sind. Ohne Gateway-Kopplung in Node2 ist dies verletzt, falls die Koordinatoren die Kanäle nicht strikt zeitsynchron ansteuern.
  • Terminierungs- / Release-Phase:
    • Wird der PNC auf Ch1 freigegeben, schaltet Node2.Ch1 nach Ablauf des ComMPncPrepareSleepTimer ab, während Node2.Ch2 ggf. noch aktiv bleibt.

4. Normative Relevanz & Entwickler-Hinweise

  • System- & Kommunikationsdesign (System Description / Fibex / ARXML):
    • Werden einem PNC in einer ECU mehrere ComMChannels zugeordnet, ohne dass ComMPncGatewayType gesetzt ist, muss die Gesamtsystemarchitektur (Cluster-Topologie und Scheduling der NM-Botschaften über alle Koordinatoren) garantieren, dass diese Kanäle immer exakt zum selben Zeitpunkt angefordert und freigegeben werden.
  • Stack-Konfiguration (ComM):
    • Fehlt diese globale Koordination, darf Node2 nicht als unkoordinierter Dual-Channel-Knoten für denselben PNC konfiguriert werden. Die Lösung erfordert entweder:
      • Setzen von ComMPncGatewayType auf ACTIVE an mindestens einem der Ports von Node2 (sofern Node2 als Gateway agieren soll/darf), oder
      • Auftrennung der PNC-IDs, sodass PNC1/PNC2 nicht mehrdeutig über unkoordinierte Kanäle derselben ECU aufgespannt werden.
  • Applikations-Vertrag (SW-C zu ComM):
    • Applikationen fordern PNCs an, keine ComMChannels. ComM übernimmt bei fehlender Gateway-Konfiguration explizit keine Verantwortung für die Harmonisierung unkoordinierter Kanäle. Embedded-Entwickler dürfen in SW-Cs keine manuelle Kanalüberwachung implementieren, sondern müssen den Designfehler im ARXML-Extrakt adressieren.

Begleitender Spezifikationstext:

Note: If PNCs are assigned to different ComMChannels and those ComMChannels are not coordinated by a PNC gateway, then the network topology and communication design has to ensure, that the affected ComMChannels are requested and released to the same point in time. If PNCs are used, an application should not care about ComMChannel states, and additionally, ComM will not take care about ComMChannel states for this use case, since the PNC coordination for those ComMChannels is not performed. Or in other words, if a PNC is requested (passively) then also all referenced ComMChannels shall be requested (passively), because an application expects that all ComMChannels assigned to this PNCs reside in COMM_FULL_COMMUNICATION. Figure 4 depict an example for a PNC gateway (Node2) with not coordinated ComMChannels
