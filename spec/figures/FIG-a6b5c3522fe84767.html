1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Instanzendiagramm / Objekt- und Beziehungsstrukturdiagramm (AUTOSAR System Template, ARXML-Metamodell-Instanziierung).
  • Architektur-Kontext: AUTOSAR Classic Platform (Release 4.3.1), System Template (AUTOSAR_TPS_SystemTemplate), Kapitel 13.1 (Special Use-Cases: Support of sending / receiving same Can/Flexray Frame on same channel – Pdu Gateway Use-Case).
  • Technischer Zweck: Spezifikation des kanonischen ARXML-Modellierungsmusters für ein Gateway-Steuergerät (ECU4), das denselben Bus-Frame (Frame_X) bzw. dieselbe I-PDU (Pdu_X) auf ein und demselben physischen Kommunikationskanal (PhysicalChannel, z. B. CAN oder FlexRay) sowohl empfangen (Rx / in) als auch senden (Tx / out) kann (z. B. bei Variantenkonfigurationen, redundanten Sendern oder Plattform-Derivaten, bei denen ein Master-Knoten ECU1 optional entfällt und ECU4 das Senden übernimmt). Es verhindert die unzulässige Duplizierung von Frame-/PDU-Definitionen auf demselben Kanal.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert die vertikale und horizontale Assoziationskette zwischen Kommunikationsmatrix und ECU-Topologie:

  • Struktur- und Metamodellelemente:
    • Frame_X (Frame / CanFrame / FlexrayFrame): Abstrakte Frame-Definition im System Template. Aggregiert das Layout und die PDU-Einbettung.
    • Pdu_X (Pdu / I-Signal-I-Pdu): Repräsentiert die Interaktionsschicht-PDU unabhängig von ihrer physischen Übertragung.
    • PduToFrameMapping: Metamodell-Klasse («atpSplitable»); verknüpft Frame_X mit Pdu_X unter Angabe von Bit-Offset, Update-Bit-Position und Byte-Order.
    • FrameTriggering_X (FrameTriggering): Spezifische Ausprägung/Aktivierung von Frame_X auf einem konkreten PhysicalChannel (trägt z. B. CAN-ID oder FlexRay-Slot/Cycle). Referenziert Frame_X (1:1) und assoziiert die zugehörigen PduTriggering-Instanzen.
    • PduTriggering_X (PduTriggering): Spezifische Ausprägung von Pdu_X auf demselben PhysicalChannel. Referenziert Pdu_X (1:1) und wird von FrameTriggering_X referenziert.
    • FramePort (Kanal-Interface auf Frame-Ebene):
      • FramePort_ECU1_out: Sende-Port der regulären Quelle (ECU1).
      • FramePort_ECU2_in, FramePort_ECU3_in: Empfangs-Ports der reinen Busteilnehmer (ECU2, ECU3).
      • FramePort_ECU4_in & FramePort_ECU4_out: Duale Port-Definition für das Gateway-Steuergerät (ECU4) auf derselben FrameTriggering_X.
    • IPduPort (Kanal-Interface auf PDU-Ebene):
      • PduPort_ECU1_out: Sende-PDU-Port für ECU1.
      • PduPort_ECU2_in, PduPort_ECU3_in: Empfangs-PDU-Ports für ECU2 und ECU3.
      • PduPort_ECU4_in & PduPort_ECU4_out: Duale Port-Definition für ECU4 auf derselben PduTriggering_X.
  • Beziehungen und Kardinalitäten:
    • Pro PhysicalChannel existiert exakt eine FrameTriggering-Instanz für Frame_X und exakt eine PduTriggering-Instanz für Pdu_X.
    • Die Unterscheidung zwischen Senden und Empfangen erfolgt ausschließlich über die daran gebundenen FramePort- und IPduPort-Instanzen der jeweiligen EcuInstance (Kardinalität 0..* Ports pro Triggering).
    • Eine EcuInstance besitzt für denselben Frame/PDU genau zwei Ports, wenn sie beide Richtungen bedient: jeweils einen mit communicationDirection = in und einen mit communicationDirection = out.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Strukturmodell handelt, manifestiert sich das dynamische Verhalten zur Laufzeit im Kommunikations- und Gateway-Stack:

  1. Empfangspfad (ECU4 als Gateway / Sink):
    • Frame trifft über den Bus-Treiber (z. B. Can / CanIf) ein.
    • CanIf filtert anhand der CAN-ID (definiert in FrameTriggering_X) und leitet die PDU an das PduR über den konfigurierten Rx-PDU-Handle (abgeleitet aus PduPort_ECU4_in).
    • PduR routet die PDU entweder direkt weiter (PDU-Routing auf einen anderen Kanal/Interface) oder übergibt sie dem lokalen Com-Modul.
  2. Sendepfad (ECU4 als Fallback-Sender / Source):
    • Wird ECU1 auf dem Bus deaktiviert (Variantenweiche / Timeout / Bus-Monitoring), triggert die interne Gateway-Logik bzw. eine SW-C das Senden.
    • PduR bedient den Tx-PDU-Handle (abgeleitet aus PduPort_ECU4_out).
    • CanIf fordert die Übertragung über den CAN-Controller an.
  3. Konfliktvermeidung:
    • Zur Laufzeit verhindert das BSW (bzw. Systemdesign), dass ECU4 und ECU1 zeitgleich denselben Frame mit gleicher ID zyklisch senden (Vermeidung von CAN-Arbitrierungs-Bus-Offs oder FlexRay-Slot-Kollisionen).

4. Normative Relevanz & Entwickler-Hinweise

  • System-Extract- & ECU-Extract-Generierung:
    • Tool-Vendors müssen den Importer/Splitter so auslegen, dass beim Extrahieren der Konfiguration für ECU4 (EcuExtract) beide Richtungs-Ports (FramePort / IPduPort) aufgelöst werden.
    • Für reine Busteilnehmer (ECU2, ECU3) wird ausschließlich der in-Zweig extrahiert; Änderungen an ECU4 (z. B. Hinzufügen des Tx-Zweigs) invalidieren nicht die Konfiguration der anderen ECUs.
  • BSW-Konfiguration (CanIf / PduR / Com):
    • Handle-Trennung: Im generierten BSW von ECU4 entstehen zwingend zwei getrennte PDU-IDs: eine CanIfRxPduCfg (gebunden an PduPort_ECU4_in) und eine CanIfTxPduCfg (gebunden an PduPort_ECU4_out), obwohl beide im Metamodell auf dieselbe physische ID (FrameTriggering_X) und dieselbe PDU-Struktur (Pdu_X) verweisen.
    • Kein Metamodell-Duplikat: Es ist normativ unzulässig, zur Modellierung dieses Anwendungsfalls zwei unterschiedliche FrameTriggering- oder PduTriggering-Elemente mit identischer ID auf demselben PhysicalChannel anzulegen, da dies den Eindeutigkeits-Constraint im System Template verletzt.
  • Filterung & Loopback:
    • Im CAN-Treiber/CanIf von ECU4 muss sichergestellt sein, dass das Senden des Frames nicht fälschlich als eigener lokaler Empfang interpretiert wird (sofern Self-Reception / Loopback nicht explizit für Loopback-Routing konfiguriert ist).
