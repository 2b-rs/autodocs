1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Typdefinition einer Datenstruktur («structure»).
  • Technischer Zweck: Spezifikation des C-Strukturtyps E2E_P07mConfigType innerhalb des Namensraums E2E::E2E_P07mTypes gemäß SWS-Anforderung SWS_E2E_91010.
  • Funktionale Einordnung:
    • Bestandteil der AUTOSAR E2E Library (End-to-End Communication Protection, CP/AP-Umfeld).
    • E2E Profile 7m ist eine Profilvariante für Methoden- und RPC-basierte Kommunikation (z. B. SOME/IP Client-Server-Methoden, Request/Response/Fire-and-Forget) über variable und lange Nutzdatenlängen (bis zu 2^32-1 Bit).
    • Die Datenstruktur dient als unveränderlicher Konfigurationsdeskriptor (const E2E_P07mConfigType* ConfigPtr), der den funktionssicheren Schutz- und Prüfroutinen (E2E_P07mProtect, E2E_P07mCheck, E2E_P07mForward) statische Schranken, Offsets und Identifikatoren vorgibt, um Sicherheitsanforderungen nach ISO 26262 bis ASIL D (RS_E2E_08539) abzudecken.

2. Komponenten, Entitäten & Schnittstellen

  • Entität:
    • «structure» E2E::E2E_P07mTypes::E2E_P07mConfigType
  • Attribute & Typdefinitionen:
    • + DataID: uint32 Systemweit eindeutiger 32-Bit-Identifikator der Nachricht/Methode. Sichert die Kommunikation gegen Adressierungs- und Maskierungsfehler (Masquerading, Spurious/Incorrect Routing). Fließt in den E2E-Header und die CRC-Berechnung ein.
    • + MaxDataLength: uint32 Maximal zulässige Gesamtlänge der Nachricht (inklusive Nutzdaten und E2E-Header) in Bits. Definiert die Obergrenze bei Daten mit variabler Länge.
    • + MaxDeltaCounter: uint32 Maximal tolerierte Differenz zwischen den Alive-Countern zweier aufeinanderfolgend empfangener gültiger Nachrichten. Dient der Erkennung unzulässigen Nachrichtenverlusts (Message Loss vs. Sequence Error).
    • + MinDataLength: uint32 Minimal zulässige Gesamtlänge der Nachricht in Bits. Muss mindestens die Bitbreite des E2E-P07m-Headers umfassen.
    • + Offset: uint32 Startposition des E2E-Header-Blocks innerhalb des Datenpuffers/der PDU, angegeben in Bits ab Pufferbeginn.
  • Beziehungen & Kardinalitäten:
    • Reines Strukturdiagramm ohne externe Assoziationen oder Vererbungsbeziehungen.
    • Kardinalität zur Laufzeit: 1:1 pro geschütztem Event-/Methoden-Port bzw. E2E-Transformations-Instanz. Wird als statische Konstante im Flash/ROM hinterlegt.

3. Dynamisches Verhalten & Sequenzablauf

Als statische Datenstruktur besitzt E2E_P07mConfigType keine eigenen Zustandsübergänge, definiert jedoch die Kontrollgrenzen für die synchronen API-Aufrufe der E2E-Bibliothek:

Sender / Transformer           E2E Library API                  Receiver / Transformer
        |                              |                                  |
        |--- E2E_P07mProtect(Config, ->|                                  |
        |    State, Length, DataPtr)   |                                  |
        |    [Checks Min/MaxDataLength]|                                  |
        |    [Inserts Counter & CRC64] |                                  |
        |<-- Returns E2E_E_OK ---------|                                  |
        |                              |                                  |
        |================= PDU Transmission via Bus =====================>|
        |                              |                                  |
        |                              |<-- E2E_P07mCheck(Config, --------|
        |                              |    State, Length, DataPtr)       |
        |                              |    [Verifies Length, Offset,     |
        |                              |     DataID, CRC64, DeltaCounter] |
        |                              |--- Returns E2E_P_OK / Error ---->|
  • Senderpfad (E2E_P07mProtect):
    1. Synchroner Aufruf; Validierung: Pufferlänge muss im Bereich MinDataLength <= Length <= MaxDataLength liegen und Offset muss innerhalb der Puffergrenzen sein.
    2. Erhöhung des sequenziellen Counters in E2E_P07mProtectStateType.
    3. Schreiben des E2E-Headers (inkl. DataID, Counter, Length, Method-Metadaten) an Bitposition Offset.
    4. Berechnung des 64-Bit-Prüfwerts (CRC-64-ECMA) über DataID und Datenbytes; Einfügen in den Header.
  • Empfängerpfad (E2E_P07mCheck):
    1. Plausibilisierung: Entspricht die empfangene Länge MinDataLength <= Length <= MaxDataLength?
    2. CRC-Neuberechnung und Vergleich mit dem Header-Wert an Bitposition Offset.
    3. Auswertung des empfangenen Counters gegen den letzten bekannten Zustand: $\Delta = (\text{Counter}_{\text{rx}} - \text{Counter}_{\text{last}}) \pmod{2^{32}}$.
    4. Liegt $\Delta \le \text{MaxDeltaCounter}$ und $\Delta > 0$, ist der Status E2E_P_OK. Bei $\Delta = 0$ erfolgt E2E_P_REPEATED, bei Überschreitung E2E_P_WRONGSEQUENCE.
  • Forwarding (E2E_P07mForward):
    • Ermöglicht Gateways/Bridges die Weiterleitung von Methoden-Nachrichten unter Replikation des empfangenen E2E-Status inklusive Schutzdaten-Neugenerierung.
  • Fehler- und Callback-Verhalten:
    • Synchroner Rückgabewert (Std_ReturnType: E2E_E_INPUTERR_NULL, E2E_E_INPUTERR_WRONG, E2E_E_OK).
    • Die E2E Library ruft per Spezifikation weder DET (Det_ReportError) noch DEM (Dem_SetEventStatus) auf; die Signalisierung und Fehlerbehandlung obliegt dem Aufrufer (z. B. E2EXf Transformer oder RTE).

4. Normative Relevanz & Entwickler-Hinweise

  • Granularität (Bit vs. Byte):
    • Obwohl MinDataLength, MaxDataLength und Offset in Bits konfiguriert werden, verlangt die Spezifikation strikte Byte-Ausrichtung: $$\text{Offset} \pmod 8 == 0, \quad \text{MinDataLength} \pmod 8 == 0, \quad \text{MaxDataLength} \pmod 8 == 0$$
    • Eine Verletzung dieser Ausrichtung führt unmittelbar zu E2E_E_INPUTERR_WRONG.
  • Header-Größe & Schranken:
    • MinDataLength muss zwingend mindestens der Größe des Profil-7m-Headers entsprechen (CRC-64 [8 Byte] + Length [4 Byte] + Counter [4 Byte] + DataID [4 Byte] + Message Type/Result [4 Byte] = 24 Byte bzw. 192 Bit).
    • Es muss stets gelten: MinDataLength ≤ MaxDataLength.
  • Speicher- und Const-Deklaration:
    • Instanzen von E2E_P07mConfigType sind reentrant lesbar und müssen im ROM/Flash abgelegt werden (CONST(E2E_P07mConfigType, E2E_CONST)).
  • Transformer-Integration (E2EXf):
    • Bei service-orientierter Kommunikation (SOME/IP via RTE/Transformer) wird diese Struktur automatisch durch den E2E-Generator aus den Metamodell-Elementen EndToEndTransformationISignalProps bzw. EndToEndTransformationDescription erzeugt. Manuelle Modifikationen im generierten Quellcode sind strikt zu vermeiden.
