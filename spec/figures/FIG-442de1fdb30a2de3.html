1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Schichtenarchitektur (Layered Architecture) kombiniert mit einem Sicherheits- und Speicherpartitionierungsmodell (Hardware/OS Privilege Levels & MPU Memory Mapping).
  • Technischer Zweck: Spezifikation des Schutzes gegen gegenseitige Beeinflussung (Freedom from Interference, FFI gemäß ISO 26262) in AUTOSAR Classic. Das Modell demonstriert die Koexistenz von vertrauenswürdigem Basissoftware-Code (Trusted BSW) und isolierten Anwendungssoftware-Komponenten (Non-Trusted SW-Cs) auf einem Single-/Multi-Core-Mikrocontroller durch hardwaregestützte Speicherschutzeinheiten (MPU).

2. Komponenten, Entitäten & Schnittstellen

Ausführungsdomänen & Privilegienebenen
  • CPU Supervisor Mode (trusted, Speicherschutz deaktiviert/privilegiert):
    • OS-Application 1: Beherbergt das gesamte Basic Software Package (BSW) sowie ausgewählte, funktionale sicherheitskritische oder hardwarerelevante SW-Cs (im Diagramm: rechte rote Application Software Component).
    • Microcontroller Abstraction Layer (MCAL): Direkter Zugriff auf Controller-Register via Hardware-Privilegien.
    • Basic Software Stacks: Services (z. B. Dem, Det, NvM, ComM), Communication (PduR, CanIf, CanTp etc.), ECU Abstraction (I/O- und Device-Treiber-Abstraktion), Complex Device Drivers (CDD) (Umgehung von Abstraktionsschichten mit direktem Hardware- und RTE-Zugriff).
    • Operating System (OS): Privilegierte Instanz zur Ablaufsteuerung, Task-Scheduling und MPU-Konfiguration.
    • AUTOSAR Runtime Environment (RTE): Liegt im Supervisor-Kontext zur sicheren Vermittlung von Kontroll- und Datenflüssen zwischen disjunkten Partitionen.
  • CPU User Mode (non-trusted, Speicherschutz/MPU aktiv):
    • OS-Application 2 bis n: Kapselung ungesicherter (QM) oder separat eingestufter ASIL-Komponenten.
    • SW-C-Gruppierung: 1:n-Allokation von Software-Komponenten auf OS-Applications (dargestellt: Application Software Component isoliert in einer Partition; Actuator Software Component und Sensor Software Component gebündelt in einer gemeinsamen Partition).
Schnittstellen (Interfaces)
  • AUTOSAR Interface: Port-basierte Kommunikation (Sender-Receiver, Client-Server) zwischen SW-Cs und RTE sowie zwischen CDD/ECU-Abstraction und RTE.
  • Standardized AUTOSAR Interface: Vordefinierte AUTOSAR-Dienste-Schnittstellen (z. B. Zugriff auf BSW-Services wie BswM, ComM, Dem via RTE).
  • Standardized Interface: C-APIs für BSW-interne Aufrufe, MCAL-Treiberzugriffe und OS-Systemaufrufe (nicht über die RTE geführt).
Speicherlayout (Physische & Logische MPU-Partitionierung)
  • Private Data / Private Code: Jede OS-Application besitzt strikt segregierte RAM- (private data) und Flash-Bereiche (private code). User-Mode-Partitionen dürfen weder schreibend noch lesend auf fremde private Datenbereiche zugreifen.
  • Shared Data Buffer (IPC / IOC): Optionaler, durch die RTE verwalteter Shared-Memory-Puffer (zugeordnet zu OS-App 1/RTE) zur Datenübergabe zwischen Partitionen via Inter-OS-Application Communication.

3. Dynamisches Verhalten & Sequenzablauf

  • Task-Wechsel & MPU-Rekonfiguration:
    1. OS-Scheduler entzieht einer User-Mode-Task die CPU.
    2. Im Supervisor-Modus programmiert das OS die MPU-Register für die nächste OS-Application neu (Code-, Daten- und Stack-Grenzen).
    3. Absenkung des Privilegienlevels auf CPU User Mode und Sprung in die Ziel-Task.
  • Inter-Partition Communication (IPC / IOC):
    • Synchroner/Asynchroner Pfad: Ruft eine Non-Trusted SW-C eine RTE-API auf, erfolgt der Datenaustausch nicht via Pointer-Dereferenzierung, sondern über Kopieroperationen (Pass-by-Value) in den Shared Data Buffer oder über OS-Traps (System Calls / Software Interrupts via IocSend/IocReceive).
  • Trap- & Ausnahmebehandlung (Protection Violation):
    • Versucht eine User-Mode-Task einen unberechtigten Schreib-/Lesezugriff auf fremde Daten (z. B. BSW-RAM) oder führt privilegierte Instruktionen aus, feuert die Hardware-MPU einen Speicherzugriffsfehler (z. B. Memory Management Fault).
    • Die CPU springt in den Supervisor Mode; das OS fängt den Fehler ab und delegiert ihn an den ProtectionHook().
    • Reaktionspfade: Terminierung der fehlerhaften Task, Terminierung der gesamten fehlerhaften OS-Application inklusive Restart-Versuch oder koordinierter ECU-Reset via BswM/EcuM.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Konfiguration & Code-Generierung:
    • Wenn SW-Cs unterschiedlichen OS-Applications zugewiesen sind, generiert der RTE-Generator automatisch IOC-Kommunikationsstümpfe anstelle direkter Funktionsaufrufe oder globaler Variablen.
    • Zeigerübergaben über Partitionsgrenzen hinweg sind unzulässig; Datenstrukturen müssen kopierbar sein (erhöhter RAM- und Laufzeit-Overhead).
  • BSW- & Treiber-Restriktionen:
    • Treiber im MCAL und BSW laufen im Supervisor Mode, um uneingeschränkten Zugriff auf SFRs (Special Function Registers) zu gewährleisten.
    • Werden SW-Cs als trusted in OS-Application 1 konfiguriert (wie die rechte rote SW-C), entfällt der MPU-Schutz gegen Speicherüberschreibungen des BSW. Dies erfordert den gleichen ASIL-Entwicklungsgrad wie das BSW selbst, um die FFI-Integrität nicht zu korrumpieren.
  • OS-Konfiguration (Os.epc / ARXML):
    • Definition von OsApplication-Objekten mit OsTrusted = FALSE für User-Mode-Komponenten.
    • Zuweisung von Tasks, ISRs (Typ 2), Counter und Alarmen an genau eine OsApplication.
    • Exakte Konfiguration von Speicherschutz-Regionen (MPU-Alignment-Restriktionen der Ziel-Hardware beachten, z. B. 32-Byte- oder Potenz-von-2-Adressausrichtungen).
  • Stack-Überwachung:
    • Für jede Non-Trusted Task/ISR muss ein separater Task-Stack zugewiesen und über MPU-Guard-Pages gegen Überlauf (Stack Overflow) abgesichert werden.
