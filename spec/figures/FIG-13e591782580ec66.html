1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Tabellarische Protokoll- und Frame-Spezifikation (PDU Wire-Format / Bit- & Byte-Layout) gemäß AUTOSAR Foundation (PRS_IntrusionDetectionSystem).
  • Architektur-Kontext: Definiert das plattformübergreifende (Classic & Adaptive Platform) Übertragungsformat für Security Events zwischen dem Intrusion Detection System Manager (IdsM), dem Intrusion Detection System Reporter (IdsR) und fahrzeuginternen/-externen Sicherheitsinstanzen (z. B. Vehicle Security Operations Center / VSOC).
  • Funktionaler Zweck: Standardisierte Serialisierung von gefilterten und aggregierten Sicherheitsereignissen on-board über Bussysteme (CAN-FD, Ethernet via SOME/IP oder IdsM-PDU) inklusive optionaler kryptografischer Authentisierung, variabler Kontextdaten und flexibler Zeitstempelung.

2. Komponenten, Entitäten & Schnittstellen

Das Protokoll gliedert sich in einen statischen 8-Byte-Basiskopf gefolgt von optionalen Nutzdatenblöcken:

#### A. Statischer Header (Event Frame Header – exakt 64 Bit / 8 Byte)

  1. Protocol Version (4 Bit): Version des IdsM-Drahtformat-Protokolls.
  2. Protocol Header (4 Bit, Presence-Flags):
  • Bit[0]: Context Data Frame vorhanden (1) oder nicht (0).
  • Bit[1]: Timestamp vorhanden (1) oder nicht (0).
  • Bit[2]: Signature Frame vorhanden (1) oder nicht (0).
  • Bit[3]: Reserviert (0-gepaddet).
  1. IdsM Instance Id (10 Bit): Eindeutige Instanzkennung der meldenden IdsM-Instanz (Bereich: 0…1023).
  2. Module Instance Id (6 Bit): Instanz-Disambiguierung bei multi-instanzierten BSW-Modulen oder Software-Komponenten (Bereich: 0…63).
  3. Event Id (16 Bit): Eindeutige Kennung des Security Events:
  • 0x0000 … 0x7FFF: AUTOSAR-intern standardisierte Security Events.
  • 0x8000 … 0xFFFF: OEM-/kundenspezifische Events.
  1. Count (16 Bit): Zählerstand der kumulierten Vorkommnisse nach interner Filterung (z. B. Aggregation / Thresholding).
  2. Reserve (8 Bit): Byte-Alignment für Folgeblöcke, reserviert für zukünftige Protokollversionen.

#### B. Optionale Nutzdatenblöcke (durch Protocol Header bedingt)

  1. Timestamp (8 Byte, optional via Flag Bit[1]):
  • Byte[0].Bit[7] = 0: Standard AUTOSAR-Zeitbasis, Byte[0].Bit[6] reserviert.
  • Byte[0].Bit[7] = 1: OEM-spezifischer / proprietärer Zeitstempel.
  • Auflösung: Millisekunden (ms). Kann bei Fehlen oder nicht-authentischer Zeit durch den IdsR eingesetzt oder neu berechnet werden.
  1. Context Data Version (2 Byte, optional im Context Data Frame):
  • Zur Unterscheidung verschiedener Kontextdaten-Versionen.
  • Byte[0].Bit[7] = 0: Ursprünglich gemeldete Kontextdaten (Original reported Context Data).
  • Byte[0].Bit[7] = 1: Über User-Callout bereitgestellte Kontextdaten (Context Data provided by user callout).
  1. Context Data Length (1 oder 4 Byte, variabel codiert via MSB):
  • Nur vorhanden, wenn Context Data existieren (Bit[0] = 1).
  • Die 2 Bytes für Context Data (Versionsfeld) sind nicht in Context Data Length enthalten.
  • Byte[0].Bit[7] = 0: 7-Bit-Länge (Context Data Length Byte[0].Bit[0..6]), Wertebereich: 1 … 127 Byte.
  • Byte[0].Bit[7] = 1: 31-Bit-Länge (Context Data Length Byte[0].Bit[0..6] + Byte[1..3].Bit[0..7]), Wertebereich: 1 … (2^31)-1 Byte.
  1. Context Data (1 … (2^31)-1 Byte, optional via Flag Bit[0]):
  • Binärer Blob des Sensors bzw. modellierte Kontextdaten der zugehörigen Sensorkomponenten.
  1. Signature Length (2 Byte, optional via Flag Bit[2]):
  • Längeninformation der Signatur (Signature Byte[0..1]), Wertebereich: 1 … 65535 Byte.
  1. Signature (1 … 65535 Byte, optional via Flag Bit[2]):
  • Authentisierungsnachweis für das Security Event (Signature Byte[2..n]), konfigurierbar über das MetaModel.

3. Dynamisches Verhalten & Sequenzablauf

  1. Ereignis-Detektion & Filterung:
  • Ein Security-Sensor (SWC, CDD oder BSW-Stack wie CanIf, LinIf, SecOC, Dcm) detektiert eine Anomalie und ruft die IdsM-API (IdsM_SetSecurityEvent / IdsM_SetSecurityEventWithContextData) auf.
  • Die interne Filter-Engine des IdsM verarbeitet das Event (z. B. Threshold-Filter, Sliding-Window, Rate-Limiting). Der Count-Wert wird inkrementiert; erst bei Filterauslösung wird die Frame-Assemblierung gestartet.
  1. Frame-Serialisierung (Encoding):
  • Header-Generierung: Setzen von Protocol Version, IdsM Instance Id, Module Instance Id, Event Id und Count.
  • Flag-Zuweisung: Evaluierung, ob Kontextdaten übergeben wurden (Bit[0]=1) und ob die Konfiguration einen Timestamp vorsieht (Bit[1]=1).
  • Längen-Codierung: Bei vorhandenen Kontextdaten wird geprüft, ob die Länge $\le 127$ Byte ist (Kompaktcodierung in 1 Byte mit MSB=0), andernfalls erfolgt 4-Byte-Encoding (MSB=1).
  1. Signierung & Dispatching:
  • Wenn konfiguriert (Bit[2]=1), stößt IdsM die kryptografische Berechnung über den kompletten bisherigen Frame an (CSM_MacGenerate oder asymmetrische Signatur).
  • Das Paket wird als IdsM-PDU an die Transportschicht (PduR $\rightarrow$ Bus / SOME/IP) an den IdsR übergeben.
  1. IdsR-Post-Processing:
  • Empfängt der IdsR ein Event ohne Timestamp (Bit[1]=0) oder besitzt das sendende Steuergerät keine authentische Zeit, reassembliert der IdsR das Paket, berechnet den Zeitstempel neu und setzt Bit[1]=1.

4. Normative Relevanz & Entwickler-Hinweise

  • Bit-weises Encoding & Alignment:
  • Die ersten 4 Byte teilen sich in 4 Bit (Protocol Version), 4 Bit (Protocol Header), 10 Bit (IdsM Instance Id), 6 Bit (Module Instance Id) sowie 16 Bit (Event Id) und 16 Bit (Count) auf. Das anschließende Feld Reserve (8 Bit) stellt sicher, dass optionale Nutzdatenblöcke auf Byte-Grenzen beginnen.
  • Dynamische Längen-Decodierung & Offset:
  • Empfänger müssen das MSB des ersten Bytes von Context Data Length prüfen (Byte[0].Bit[7]), um zu entscheiden, ob die Längenangabe 1 Byte (bei 0) oder 4 Byte (bei 1) umfasst.
  • Bei der Längenberechnung ist zu beachten, dass die 2 Byte des Versionsfelds (Context Data Version) nicht in Context Data Length eingerechnet werden.
  • Interoperabilität:
  • Die Unterscheidung zwischen standardisierten (0x0000…0x7FFF) und anwenderspezifischen (0x8000…0xFFFF) Event-IDs ist strikt einzuhalten, um Namensraumkollisionen zwischen AUTOSAR-Basissoftware und OEM-Applikationen zu vermeiden.
