1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Methoden-, Transformations- und Metamodellierungs-Architekturdiagramm (MOF-Schichtenmodellierung: M2-Metamodell zu M1-Modellinstanz nach AUTOSAR-Methodologie).
  • Technischer Zweck: Formale Darstellung der AUTOSAR-Template-Definition und des automatisierten Toolchain-Workflows zur Schema-Generierung (exemplarisch anhand des SystemTemplate). Das Diagramm illustriert, wie textuelle Spezifikationen, formale UML-M2-Metamodelle, Serialisierungsregeln und Generatoren zusammenwirken, um das normative XML-Datenaustauschformat (XSD) und die darauf basierenden ARXML-Instanzbeschreibungen (M1) abzuleiten.

2. Komponenten, Entitäten & Schnittstellen

  • Metamodelle & Profile (M2-Ebene):
    • Model M2 Templates: Zentrales, formales AUTOSAR-Metamodell (UML-Repräsentation aller System-, Software- und BSW-Entitäten).
    • UML and the Autosar Template Profile: UML-Profildefinition, die spezifische AUTOSAR-Metamodell-Erweiterungen (z. B. Stereotypen wie «atpSplitable», «atpVariation», tagged values) festlegt.
  • Textuelle Spezifikationen & Regeln («Text Document»):
    • Generic Structure Template: Normatives Basisdokument (TPS_GST); spezifiziert die generischen Strukturmuster und Metaklassen des M2-Modells sowie die Semantik des UML-Template-Profils.
    • Requirements on System Template: Übergeordnetes Anforderungsdokument (RS), welches funktionale und strukturelle Anforderungen an das konkrete Template definiert.
    • SystemTemplate: Domänenspezifische Template-Spezifikation (TPS), die die System-Modellierungselemente ausdetailliert.
    • XML Schema Production Rules: Normative Transformationsvorschrift (TPS_XSPR), die festlegt, wie UML-Klassen, Assoziationen, Attribute und Stereotypen des M2-Metamodells deterministisch in W3C-XML-Schemakonstrukte überführt werden.
  • Verarbeitende Werkzeuge:
    • Schema Generator: Tool-Komponente, die das UML-Metamodell parst, die Serialisierungsregeln anwendet und das Zieldatenaustauschformat generiert.
  • Austausch- und Instanz-Artefakte (XSD & M1-Ebene):
    • «XML Schema» Data Exchange Format: Generiertes W3C-XML-Schema (XSD), das den normativen Syntax- und Strukturvertrag für AUTOSAR-XML-Dateien (ARXML) definiert.
    • «XML File» System Configuration Description: Konkrete M1-ARXML-Datei zur Beschreibung der Systemkonfiguration.
    • «XML File» System Constraint Description: Konkrete M1-ARXML-Datei zur Spezifikation von Systemeinschränkungen (z. B. Timing-, Mapping- oder Hardware-Constraints).
  • Beziehungen und Abhängigkeiten:
    • Model M2 Templates $\xrightarrow{\text{+isGovernedBy}}$ UML and the Autosar Template Profile: Das Metamodell unterliegt den formalen Regeln des AUTOSAR-UML-Profils.
    • Model M2 Templates $\xrightarrow{\text{+is partly described in}}$ Generic Structure Template: Generische Metamodellelemente sind im GST dokumentiert.
    • UML and the Autosar Template Profile $\xrightarrow{\text{+is described in}}$ Generic Structure Template: Das Profil selbst ist Gegenstand der GST-Spezifikation.
    • «Text Document» SystemTemplate $\xrightarrow{\text{trace/satisfies}}$ «Text Document» Requirements on System Template: Das domänenspezifische Template erfüllt die definierten Anforderungen.
    • «Text Document» XML Schema Production Rules $\xrightarrow{\text{specifiesSerialization}}$ UML and the Autosar Template Profile: Die Regeln definieren die XSD-Serialisierung für alle Profil- und Metamodellkonstrukte.
    • Schema Generator $\xrightarrow{\text{+implements}}$ XML Schema Production Rules: Der Generator setzt die formalen Produktionsregeln programmatisch um.
    • Model M2 Templates ⟶ Schema Generator: Das M2-Modell dient als primäre Eingabe für den Generator.
    • Schema Generator $\xrightarrow{\text{+generates}}$ «XML Schema» Data Exchange Format: Der Generator erzeugt das normative Schema.
    • System Configuration Description und System Constraint Description $\xrightarrow{\text{+instance of}}$ «XML Schema» Data Exchange Format: Beide ARXML-Dateien sind schema-valide Instanzen des generierten Schemas.

3. Dynamisches Verhalten & Sequenzablauf

  1. Spezifikations- & Metamodellierungsphase:
    • Definition von Anforderungen (Requirements on System Template).
    • Erstellung des formalen M2-UML-Modells (Model M2 Templates) unter Anwendung des UML and the Autosar Template Profile.
    • Dokumentation der Strukturen in Spezifikationsdokumenten (Generic Structure Template, SystemTemplate).
  2. Serialisierungs- & Schemagenerierungsphase:
    • Definition der formalen Abbildungsvorschriften im Dokument XML Schema Production Rules.
    • Der Schema Generator liest das konsolidierte Model M2 Templates ein.
    • Anwendung der Transformationsregeln (+implements XML Schema Production Rules) durch den Generator.
    • Vollautomatisierte Generierung (+generates) des Schemas (Data Exchange Format, z. B. AUTOSAR_00052.xsd).
  3. Instanziierungs- & Austauschphase (M1-Laufzeit/Engineering):
    • Modellierungs- und Konfigurationswerkzeuge (System/ECU Extractors) erzeugen konkrete M1-Beschreibungsdateien (System Configuration Description, System Constraint Description).
    • Validierung: Jede XML-Datei muss zwingend schema-konform (+instance of) gegen das generierte Data Exchange Format validieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Dualismus von Spezifikation und Schema: Das XML-Schema ist im AUTOSAR-Standard kein manuell gepflegtes Primärartefakt, sondern ein strikt aus dem M2-UML-Metamodell abgeleitetes Produkt. Diskrepanzen zwischen Textdokument und XSD werden primär über das M2-Modell und die XML Schema Production Rules bereinigt.
  • Trennung von Konfiguration und Constraints (M1-Splitting): Das Diagramm demonstriert die modulare Trennung verschiedener Aspekte desselben Systems (hier: Konfiguration vs. Constraints) in separate XML-Dateien. Beide referenzieren dasselbe Schema; die Zusammenführung (ARXML-Merging) und Konsistenzprüfung erfolgt anhand der im Metamodell definierten Identifikatoren (SHORT-NAME-Pfade).
  • Auswirkungen auf Tool- und Stack-Entwickler:
    • Eigene Parser und Codegeneratoren müssen direkt auf die durch die XML Schema Production Rules definierten Namenskonventionen, Kindelement-Reihenfolgen (xs:sequence), Rollen- und Aggregationsmuster ausgelegt sein.
    • Profile-Eigenschaften wie «atpSplitable» bedeuten für den Konfigurations-Workflow, dass unvollständige Teilbäume in separaten Dateien zulässig sind, solange sie zur Build-Zeit zu einem validen Gesamtsystemmodell resolviert werden können.
