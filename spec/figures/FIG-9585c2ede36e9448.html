1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Sequenzdiagramm (Interaktionsdiagramm auf Netzwerk-/Protokollebene).
  • Funktionale Einordnung:
    • Spezifiziert im Standard AUTOSAR Foundation (AUTOSAR_FO_PRS_SOMEIPServiceDiscoveryProtocol) und bindend für die Classic Platform (CP) sowie Adaptive Platform (AP).
    • Beschreibt das fundamentale SOME/IP Publish/Subscribe-Interaktionsmuster für Notifier/Events.
    • Trennt strikt zwischen Control Plane (Signalisierung via SOME/IP-SD über UDP-Port 30490) und Data Plane (asynchrone Übertragung serialisierter Anwendungs-Events via SOME/IP-Nachrichten über UDP oder TCP).

2. Komponenten, Entitäten & Schnittstellen

  • Akteure (Lifelines):
    • Client: Event-Subscriber bzw. Service-Konsument (CP: BSW-Modul Sd mit überlagerter Com/RTE/SWC-Kette; AP: ara::com::Proxy).
    • Server: Event-Publisher bzw. Service-Provider (CP: BSW-Modul Sd, SomeIpXf, SoAd mit RTE/SWC; AP: ara::com::Skeleton).
  • Protokoll-Entitäten & Nachrichtenformate:
    • SOME/IP-SD: SubscribeEventgroup():
      • SD-Entry-Typ 0x06 (SubscribeEventgroup).
      • Nutzlast: Service ID, Instance ID, Major Version, Eventgroup ID, TTL (> 0), Counter.
      • SD-Options: Mindestens eine IPv4/IPv6 Endpoint Option (gemäß PRS_SOMEIPSD_00443, PRS_SOMEIPSD_00703) zur Deklaration der Unicast-IP, des Ports und des L4-Protokolls (UDP/TCP) des Clients für den Event-Kanal.
    • SOME/IP-SD: SubscribeEventgroupAck():
      • SD-Entry-Typ 0x07 (SubscribeEventgroupAck).
      • Bestätigung des Abonnements durch den Server gemäß PRS_SOMEIPSD_00446 inklusive der zugestandenen TTL. Optional mit Multicast Configuration Option, falls die Eventgroup per Multicast verteilt wird.
    • SOME/IP: Event():
      • Standard-SOME/IP-PDU mit Message Type = 0x02 (NOTIFICATION) bzw. 0x22 (TP-Flag bei SOME/IP-TP-Fragmentierung).
      • Header-Felder: Message ID (Service ID [16 Bit] + Method/Event ID [16 Bit, Bit 15 = 1]), Length, Client ID / Session ID, Protocol Version, Interface Version, Return Code = 0x00 (E_OK).
  • Kardinalitäten & Beziehungen:
    • 1:n (1 Server bedient n abonnierte Clients) oder n:1.
    • Eine Service-Instanz enthält 1..n Eventgroups; eine Eventgroup aggregiert 1..n Events/Fields.

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger / Voraussetzung:
    • Der Service wurde zuvor erfolgreich gefunden und angeboten (OfferService/FindService-Phase abgeschlossen).
    • Die Client-Applikation fordert den Empfang einer Eventgruppe an.
  2. Subscription Request (PRS_SOMEIPSD_00443):
    • Client -> Server: Client sendet SubscribeEventgroup() per UDP-Unicast an den SOME/IP-SD-Port des Servers.
    • Parameter: TTL > 0 (gewünschte Gültigkeitsdauer) sowie der definierte Client-Rx-Endpoint.
  3. Validierung & Bestätigung (PRS_SOMEIPSD_00446):
    • Server prüft Existenz der Eventgroup, Versionierung und Zugriffsberechtigung.
    • Server -> Client: Bei erfolgreicher Validierung antwortet der Server mit SubscribeEventgroupAck(). (Bei Ablehnung erfolgt ein SubscribeEventgroupNack, hier nicht dargestellt).
  4. Asynchrone Event-Distribution (PRS_SOMEIPSD_00449):
    • Nach dem Senden des SubscribeEventgroupAck() schaltet der Server den Datenpfad frei.
    • Server -> Client: Übertragung von 1..n SOME/IP: Event()-Nachrichten an den konfigurierten Unicast-Endpoint des Clients (oder an die Multicast-Gruppe).
    • Die Auslösung erfolgt zyklisch (zyklischer Event-Trigger) oder spontan bei Wertänderung (On-Change / Event-driven) sowie ggf. als Initial-Event (bei Event-Properties / Fields).
  5. Lebenszyklus, Timer & Abbruch:
    • Subscription-Renewal (PRS_SOMEIPSD_00463, RS_SOMEIPSD_00015): Der Client muss vor Ablauf der TTL ein erneutes SubscribeEventgroup() mit neuer TTL senden.
    • Termination (RS_SOMEIPSD_00016): Explizites Abmelden via StopSubscribeEventgroup (TTL = 0) oder implizites Schließen durch Ablauf der Lease-Time (TTL = 0 Timeout) serverseitig.

4. Normative Relevanz & Entwickler-Hinweise

  • Classic Platform (BSW-Stack-Konfiguration):
    • Modul Sd: Konfiguration der Timer (SdClientTimerSubscribeEventgroupRetryDelay, SdClientTimerSubscribeEventgroupRetryMax).
    • Modul SoAd: Erst nach Empfang des SubscribeEventgroupAck darf die dynamische Socket-Route (SoAd_OpenSoCon bzw. Aktivierung der Routing-Relation) für die eingehenden Event-PDUs auf Client-Seite freigegeben werden.
    • Fehlerbehandlung: Bleibt das SubscribeEventgroupAck innerhalb des konfigurierten Timeouts aus, muss das BSW-Modul Sd gemäß Retry-Logik erneut senden oder einen Verbindungsfehler melden (DEM/DET).
  • Adaptive Platform (ara::com):
    • Entspricht dem Aufruf von proxy->MyEvent.Subscribe(cacheSize).
    • Zustandstransition: kNotSubscribed → kSubscriptionPending → kSubscribed (Zustand wird erst bei Eingang des SubscribeEventgroupAck erreicht).
    • Der über SetReceiveHandler() registrierte Callback der Applikation wird erst getriggert, wenn der Zustand kSubscribed aktiv ist und die ersten SOME/IP: Event()-PDUs eintreffen.
  • Timing & Network Race Conditions:
    • Bei UDP-Transport kann ein SOME/IP: Event() aufgrund von Reordering auf Switchen vor dem SubscribeEventgroupAck beim Client eintreffen. Der Client-Stack muss robust ausgelegt sein (z. B. Paket bis zum Ack puffern oder verwerfen, ohne einen fatalen Fehler auszulösen).
  • Endpoint-Matching:
    • Stimmt der im SubscribeEventgroup übermittelte Layer-4-Port nicht mit dem im Server konfigurierten Transportprotokoll (UDP vs. TCP) überein, quittiert der Server mit SubscribeEventgroupNack.
