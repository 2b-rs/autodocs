1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles AUTOSAR-Metamodell-Instanzendiagramm / Allokations- und Mapping-Diagramm (TPS System Template, AUTOSAR_CP_TPS_SystemTemplate).
  • Technischer Zweck & Einordnung:
    • Das Diagramm definiert die zweistufige Mapping-Hierarchie zur Allokation von RunnableEntity-Instanzen auf Betriebssystem-Tasks (OsTask) einer konkreten ECU (EcuInstance).
    • Ebene 1 (Applikation/VFB): Entkopplung von Software-Komponenten (AtomicSwComponentType) und deren RteEvent-Bindungen von der Hardware über logische Task-Proxys (OsTaskProxy) mittels RteEventInCompositionToOsTaskProxyMapping.
    • Ebene 2 (ECU-Integration): Bündelung und Zuweisung dieser applikationsseitigen Task-Proxys zu einem konkreten Steuergeräte-Task-Proxy (EcuTaskProxy) über AppOsTaskProxyToEcuTaskProxyMapping im Rahmen des SwcToEcuMapping.
    • Ermöglicht das Wiederverwenden aggregierter Subsystem-Compositions mit vordefinierten Task-Zuordnungen, bevor die finale ECU-Allokation feststeht.

2. Komponenten, Entitäten & Schnittstellen

  • Strukturelle Software- & Hardware-Entitäten:
    • Swc_A, Swc_B: Software-Komponenten-Instanzen (SwComponentPrototype).
    • Re_a10, Re_a50: RunnableEntity-Instanzen von Swc_A.
    • Re_b10, Re_b50: RunnableEntity-Instanzen von Swc_B.
    • EcuInstance: Physische Steuergeräte-Instanz im System-Description-Modell.
    • SwcToEcuMapping: Meta-Klasse («atpSplitable»), welche Swc_A und Swc_B der Ziel-EcuInstance zuordnet.
  • Task-Proxy-Entitäten:
    • TaskProxy1, TaskProxy2: Instanzen von OsTaskProxy (logische Task-Repräsentationen auf Software-Composition-Ebene).
    • EcuTaskProxy: Konkreter Task-Proxy auf ECU-Ebene, assoziiert mit der EcuInstance (korrespondiert mit der späteren OsTask-Konfiguration im BSW OS-Modul).
  • Mapping-Klassen, Attribute & Kardinalitäten:
    • RteEventInCompositionToOsTaskProxyMapping:
      • Bildet das die Runnable aktivierende RteEvent auf einen OsTaskProxy ab.
      • Spezifiziert das Attribut offset (relative Positionierung / Phasenoffset im Task):
        • Re_a10 → TaskProxy1 (offset = 1)
        • Re_a50 → TaskProxy1 (offset = 4)
        • Re_b10 → TaskProxy2 (offset = 2)
        • Re_b50 → TaskProxy2 (Offset = 3)
      • Kardinalität: n:1 bezüglich OsTaskProxy.
    • AppOsTaskProxyToEcuTaskProxyMapping:
      • Führt logische OsTaskProxy-Instanzen auf einen Ziel-EcuTaskProxy zusammen.
      • Spezifiziert das Attribut offset (hierarchischer Sortierindex / Proxy-Offset):
        • TaskProxy1 → EcuTaskProxy (offset = 1)
        • TaskProxy2 → EcuTaskProxy (offset = 2)
      • Kardinalität: n:1 bezüglich EcuTaskProxy (Konsolidierung mehrerer logischer Tasks in einen physischen Task).

3. Dynamisches Verhalten & Sequenzablauf

  • Deterministische Schedule-Synthese (Interleaving-Auflösung):
    1. Aktivierung: Der dem EcuTaskProxy zugrunde liegende OsTask wird zyklisch (z. B. durch einen OS-Alarm oder Schedule-Table-Expiry-Point) aktiviert.
    2. Sequenzierung der Runnables: Die finale Aufrufreihenfolge im generierten RTE-Task-Body ergibt sich aus der Auflösung der Offsets über beide Mapping-Ebenen: $$\text{Sequenz}: \quad \text{Re\_a10 (Offset 1)} \longrightarrow \text{Re\_b10 (Offset 2)} \longrightarrow \text{Re\_b50 (Offset 3)} \longrightarrow \text{Re\_a50 (Offset 4)}$$
    3. Ausführungspfad:
      • TaskProxy1 belegt Slots/Offsets 1, 4; TaskProxy2 belegt Slots/Offsets 2, 3.
      • Über die Verschachtelung werden die Runnables aus Swc_A und Swc_B deterministisch innerhalb eines einzigen OS-Task-Kontexts verschränkt (interleaved).
    4. Nebenläufigkeit: Innerhalb dieses Tasks gilt Run-to-Completion ohne Verdrängung zwischen den Runnables.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Anforderungen:
    • TPS_SYST_02368: Definiert die Bindung zwischen OsTaskProxy und EcuTaskProxy via AppOsTaskProxyToEcuTaskProxyMapping. Wenn Software-Komponenten derselben EcuInstance zugeordnet sind, müssen deren applikative Task-Proxys über gültige Mappings auf ECU-Task-Proxys dieser ECU abgebildet werden.
    • TPS_SYST_02369: Regelt die Konsistenz und Kollisionsfreiheit der kombinierten offset-Attribute. Werden mehrere OsTaskProxy-Instanzen auf denselben EcuTaskProxy zusammengeführt, müssen die resultierenden Offsets eine eindeutige, widerspruchsfreie Totalordnung für die RTE-Generierung bilden.
  • Auswirkungen auf BSW- & RTE-Generatoren:
    • Der RTE-Generator liest diese System-Extract-Informationen aus und generiert den sequentiellen C-Funktionsaufruf im Task-Body: 
      TASK(OsTask_EcuProxy) {
    /* Offset 1 */
    Rte_Runnable_Swc_A_Re_a10();
    /* Offset 2 */
    Rte_Runnable_Swc_B_Re_b10();
    /* Offset 3 */
    Rte_Runnable_Swc_B_Re_b50();
    /* Offset 4 */
    Rte_Runnable_Swc_A_Re_a50();
    
    (void)TerminateTask();
}
  • Praktische Relevanz für Integratoren & Applikationsentwickler:
    • Zero-Overhead-Kommunikation: Durch die synchrone Sequenzierung (Re_a10 → Re_b10) kann die Inter-Runnable-Kommunikation über direkte globale Puffer/RTE-interne Variablen ohne OS-Ressourcen, Semaphore oder Interrupt-Sperren abgewickelt werden.
    • Wiederverwendbarkeit: Subsystem-Lieferanten können TaskProxy1 und TaskProxy2 mit relativen internen Prioritäten vorkonfigurieren, ohne die finale Task-Struktur des Tier-1/OEM-Steuergeräts kennen zu müssen.
