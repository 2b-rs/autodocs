1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Zuordnungsdiagramm (Mapping Diagram) gemäß AUTOSAR BSW UML Modeling Guide (Rahmen: class Csm_Hash_BSWMapping).
  • Architektur-Kontext: Formales Mapping zwischen der VFB-Ebene (Virtual Function Bus / SWC-Service-Port) und der BSW-Implementierungsebene (C-API) des Moduls Crypto Service Manager (Csm) in AUTOSAR Classic (R4.3.1).
  • Technischer Zweck: Definition der Bindung von High-Level VFB-Client-Server-Operationen (ClientServerOperation) an standardisierte C-Funktionssignaturen («function») des Basissoftware-Stacks. Dient RTE- und BSW-Generatoren als Spezifikationsgrundlage zur Synthese von Service-Stubs und Wrapper-Funktionen.

2. Komponenten, Entitäten & Schnittstellen

Entitäten der VFB- / Port-Ebene (links)

Modelliert als «ClientServerOperation» (Bestandteile eines ClientServerInterface für Applikations- oder Service-SWCs):

  • HashStart: Parameterlos + HashStart().
  • HashUpdate: Dateneinspeisung + HashUpdate(HashDataBuffer, uint32).
  • HashFinish: Finalisierung + HashFinish(HashResultBuffer, HashLengthBuffer, boolean).
Entitäten der BSW-Implementierungsebene (rechts)

Modelliert als BSW-Interfaces mit Stereotyp «interface» und Operationen mit Stereotyp «function» im C-Namespace Csm:::

  • Csm::Csm_HashStart: + Csm_HashStart(Csm_ReturnType, Csm_ConfigIdType) : void
  • Csm::Csm_HashUpdate: + Csm_HashUpdate(Csm_ReturnType, Csm_ConfigIdType, const uint8*, uint32) : void
  • Csm::Csm_HashFinish: + Csm_HashFinish(Csm_ReturnType, Csm_ConfigIdType, uint8*, uint32*, boolean) : void
Beziehungen & Stereotypen
  • «abswMapping» (Abhängigkeit/UML-Dependency): Gerichtete Zuordnung (gestrichelte Pfeile) von jeder ClientServerOperation zur korrespondierenden BSW-C-Funktionsdefinition.
  • Signatur-Transformation / Parameter-Diskrepanzen:
    • Konfigurationsidentifikator (Csm_ConfigIdType): Auf BSW-Ebene zwingend erforderlich, auf VFB-Ebene nicht in der Operationssignatur enthalten. Wird port-spezifisch gebunden.
    • Rückgabewert / Status (Csm_ReturnType): In der BSW-Funktionssignatur als expliziter Parameter modelliert; auf VFB-Ebene über den RTE-Statuscode (Std_ReturnType) bzw. Standard-Fehlerbehandlungsmechanismen transportiert.
    • Typen-Mapping:
      • HashDataBuffer → const uint8* (Read-only Eingabedatenzeiger).
      • HashResultBuffer → uint8* (Ausgabedatenzeiger für Digest).
      • HashLengthBuffer → uint32* (In/Out-Längenparameter).
      • boolean → boolean (Truncation-/Verarbeitungs-Flag).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert die statische Zuordnung, bedingt aber den dreistufigen Streaming-Lebenszyklus (Init-Update-Finalize) kryptografischer Hash-Primitiven:

  1. Initialisierungsphase (HashStart → Csm_HashStart):
    • Allokation und Initialisierung des Hash-Kontextes im CSM/CryIf/Crypto-Treiber für die konfigurierte Primitiv-Instanz (ConfigId).
  2. Datenakkumulationsphase (HashUpdate → Csm_HashUpdate):
    • Sukzessive Zuführung von Datenblöcken. Kann zyklisch/iterativ für beliebig viele Chunks aufgerufen werden. Interner Zustand (Message Digest State) wird fortgeschrieben.
  3. Abschlussphase (HashFinish → Csm_HashFinish):
    • Berechnung des finalen Paddings, Abschluss der Hash-Berechnung, Schreiben des Digests in HashResultBuffer und Aktualisierung der tatsächlichen Hash-Länge über HashLengthBuffer.

Synchronität / Blockierverhalten: Das Mapping selbst determiniert nicht das Scheduling. Abhängig von der Konfiguration der BSW-Entität (synchron vs. asynchron über Polling/Callback) blockiert der aufrufende SWC-Task im Rte_Call oder erhält eine asynchrone Auftragsbestätigung.

4. Normative Relevanz & Entwickler-Hinweise

  • Port-Defined Argument Values (PDAV): Da Csm_ConfigIdType in den VFB-Operationen fehlt, muss der RTE-Generator dieses Argument über einen im Komponenten-Template (ServiceComponentTemplate) definierten PortDefinedArgumentValue statisch zur Compilezeit injizieren. Ein SWC ruft somit Rte_Call_<Port>_HashStart() ohne ConfigId auf; der RTE-Stub ruft Csm_HashStart(..., <ConfigId>).
  • Speicher- und Puffergültigkeit:
    • Eingabedatenpuffer müssen für die Dauer der Ausführung unverändert bleiben (const uint8*).
    • Ausgabepuffer (HashResultBuffer, HashLengthBuffer) müssen vom Aufrufer mit ausreichender Größe allokiert und übergeben werden.
  • Typensicherheit & Alignment: Der Treiberentwickler muss sicherstellen, dass die durch den RTE-Stub weitergeleiteten Pufferzeiger (uint8*) den hardware-spezifischen Alignment-Vorgaben der Krypto-Hardware (z. B. DMA- oder Wort-Ausrichtung im Crypto-Driver) entsprechen oder im Treiber entsprechend gebuffert werden.
  • Csm-API-Evolution: In neueren Releases (z. B. R4.4+ bzw. Crypto-Stack-Harmonisierung über Crypto Driver Objects / Jobs) wurde die Hash-Schnittstelle im CSM primär über vereinheitlichte Job-Interfaces (Csm_Job*, Crypto_Job*) konsolidiert; die dargestellte API bildet den klassischen primitiv-spezifischen Service-Contract der R4.3.1 ab.
