1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm des AUTOSAR-M2-Metamodells (Spezifikation: AUTOSAR_SoftwareComponentTemplate, Release R3.0.7).
  • Architektur-Kontext: Definition der abstrakten und konkreten Port-Schnittstellen (PortInterface) auf VFB-Ebene (Virtual Function Bus). Das Metamodell legt die typisierte Vertragsbasis fest, über welche Software-Components (SWCs) und Basissoftware-Module (BSW) über P-Ports und R-Ports typkonform miteinander gekoppelt werden und steuert direkt die Signaturgenerierung der RTE-APIs.

2. Komponenten, Entitäten & Schnittstellen

Basis-Klasse
  • PortInterface («atpType», spezialisiert ARElement):
    • Abstrakter Basistyp aller Schnittstellen im ARXML-Datenmodell.
    • Attribut: + isService: Boolean – Kennzeichnet, ob die Schnittstelle von/für BSW-Dienste (z. B. Dem, NvM, ComM) bereitgestellt wird (true) oder eine reine Applikationsschnittstelle darstellt (false).
Spezialisierungen (PortInterface)
  • SenderReceiverInterface («atpType»):
    • Dient dem asynchronen, signalbasierten Datenaustausch und der Modusverwaltung.
    • Kompositionen:
      • +dataElement 0..* → DataElementPrototype («atpPrototype», spezialisiert DataPrototype, Multiplizität zu Interface 1):
        • Attribut + isQueued: Boolean: Definiert Pufferungssemantik (Queue vs. Data-Drop/Last-is-Best).
      • +modeGroup 0..* → ModeDeclarationGroupPrototype («atpPrototype», spezialisiert Identifiable, Multiplizität zu Interface 1):
        • Bindet Modusdeklarationsgruppen an die Schnittstelle (R3.x-Metamodell-spezifisch).
  • ClientServerInterface («atpType»):
    • Ermöglicht Prozeduraufrufe (Remote Procedure Call / RPC) zwischen SWCs bzw. SWC und BSW.
    • Komposition:
      • +operation 1..* → OperationPrototype («atpStructureElement», spezialisiert Identifiable, Multiplizität zu Interface 1): Mindestens eine aufrufbare Operation ist obligatorisch.
  • CalprmInterface («atpType»):
    • Bereitstellung von Kalibrierparametern und Kennfeldern/Kennlinien.
    • Komposition:
      • +calprmElement 0..* → CalprmElementPrototype (spezialisiert DataPrototype): Konkrete Kalibrierwert-Instanz.
Detail- und Hilfsstrukturen
  • OperationPrototype → ArgumentPrototype:
    • Komposition +argument * {ordered} → ArgumentPrototype (spezialisiert DataPrototype, Multiplizität zu Operation 1):
      • Geordnete Liste von Funktionsparametern.
      • Attribut: + direction: DirectionKind.
  • DirectionKind («enumeration»):
    • Literale: in (Übergabe per Value/Const-Referenz), out (Rückgabewert über Zeiger), inout (Lese-/Schreibzugriff über Zeiger).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm bildet ein statisches Metamodell ab. Das daraus determinierte RTE-Laufzeitverhalten gliedert sich wie folgt:

  • Sender-Receiver-Kommunikation:
    • isQueued = false: Ungepufferte Semantik ("Last-is-best"). Schreibzugriffe (Rte_Write_<p>_<o>) überschreiben ältere Werte atomar; Lesezugriffe (Rte_Read_<p>_<o>) lesen den aktuellen Pufferzustand.
    • isQueued = true: FIFO-Queue. Sender sendet via Rte_Send_<p>_<o>; Empfänger liest via Rte_Receive_<p>_<o>. Bei voller Queue Rückgabewert RTE_E_LOST_DATA / RTE_E_LIMIT, bei leerer Queue RTE_E_NO_DATA.
  • Client-Server-Aufrufe:
    • Synchron (Rte_Call_<p>_<o>): Aufrufer blockiert, bis die Server-Runnable abgearbeitet ist.
    • Asynchron (Rte_Call_<p>_<o> / Rte_Result_<p>_<o>): Aufrufer triggert via Event und pollt das Ergebnis oder reagiert auf ein RTE-Callback (AsynchronousServerCallReturnsEvent).
    • Parameterübergabe erfolgt streng deterministisch entlang der {ordered}-Reihenfolge der ArgumentPrototype-Elemente.
  • Modus-Umschaltung (modeGroup):
    • Triggert ModeSwitchEvent in abhängigen SWCs zur Aktivierung/Deaktivierung von Runnables.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-API-Signatur:
    • Die Reihenfolge {ordered} der ArgumentPrototype in ARXML bestimmt exakt die C-Funktionssignatur in der RTE: Std_ReturnType Rte_Call_<port>_<operation>(in Args, out *Args, inout *Args).
  • Speicher- und Queue-Dimensionierung:
    • Steht isQueued = true, muss der RTE-Generator Ringpuffer im RAM allozieren. Fehlt in der SWC-Implementierung das regelmäßige Leeren via Rte_Receive, droht Pufferüberlauf.
  • Service-Ports (isService = true):
    • Dürfen nur mit Service-Ports der BSW verbunden werden (Service-Mapping). Sie verlangen BSW-konforme Fehlercodes (Std_ReturnType, Dem/Det-Integration) und unterliegen standardisierten Namenskonventionen.
  • Release-Differenz R3.0.7 vs. AR 4.x:
    • In R3.0.7 ist die ModeDeclarationGroupPrototype noch aggregierter Bestandteil des SenderReceiverInterface. In AUTOSAR 4.x wurde dies entkoppelt und in ein eigenständiges ModeSwitchInterface überführt.
    • CalprmInterface wurde in späteren Releases durch ParameterInterface abgelöst.
