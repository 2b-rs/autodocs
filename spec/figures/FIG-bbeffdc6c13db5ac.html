1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt der AUTOSAR-Systembeschreibung (AUTOSAR System Template, FIBEX4Multiplatform: Gateway, Release R4.0.3).
  • Zweck: Formale Spezifikation von Gateway-Mappings auf Frame-, I-PDU- und ISignal-Ebene mit Unterstützung von AUTOSAR-Post-Build-Variabilität («atpVariation»). Bindet die Mappings an eine Steuergeräte-Instanz (EcuInstance).

2. Komponenten, Entitäten & Schnittstellen

Vererbungshierarchie
  • FibexCore::FibexElement (aus PackageableElement): Abstrakte Basisklasse für paketierbare Artefakte; wird spezialisiert von:
    • CoreTopology::EcuInstance
    • Gateway
Entitäten & Relationen
  • Gateway: Zentrales Metamodell-Element für Gateway-Funktionen.
    • +ecu [1]: Unidirektionale Assoziation auf genau eine CoreTopology::EcuInstance.
    • +frameMapping [0..*]: Komposition von FrameMapping-Instanzen («atpVariation» Tags: vh.latestBindingTime = postBuild).
    • +iPduMapping [0..*]: Komposition von IPduMapping-Instanzen («atpVariation» Tags: vh.latestBindingTime = postBuild).
    • +signalMapping [0..*]: Komposition von ISignalMapping-Instanzen («atpVariation» Tags: vh.latestBindingTime = postBuild).
  • FrameMapping:
    • +sourceFrame [1] / +targetFrame [1]: Unidirektionale Referenzen auf CoreCommunication::FrameTriggering (Identifiable).
  • IPduMapping:
    • Attribute: + pdurTpChunkSize :PositiveInteger [0..1].
    • +sourceIPdu [1]: Unidirektionale Referenz direkt auf CoreCommunication::PduTriggering (Identifiable).
    • +targetIPdu [1]: Komposition von genau einer TargetIPduRef-Instanz.
    • TargetIPduRef:
      • +targetIPdu [1]: Unidirektionale Referenz auf CoreCommunication::PduTriggering (Identifiable).
      • +defaultValue [0..1]: Optionale Komposition auf PduMappingDefaultValue.
    • PduMappingDefaultValue:
      • +defaultValueElement [1..*]: Komposition von mindestens einem DefaultValueElement.
    • DefaultValueElement:
      • Attribute: + elementByteValue :Integer, + elementPosition :Integer.
  • ISignalMapping:
    • +sourceSignal [1] / +targetSignal [1]: Unidirektionale Referenzen auf CoreCommunication::ISignalTriggering (Identifiable).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm ist ein statisches Metamodell für den System-Austausch (ARXML). Aus den abgebildeten Mappings leitet sich das Laufzeitverhalten im AUTOSAR BSW-Stack wie folgt ab:

  1. Frame-Routing (Hardware-/Interface-Ebene):
    • Direkte Frame-Weiterleitung über Bus-Schnittstellen (z. B. FrIf oder CanIf) ohne Demultiplexing oder PDU-Extraktion; optimiert auf minimale Latenz.
  2. I-PDU-Routing (PduR-Ebene):
    • Triggerung über PduR_<Src>RxIndication() bei Eingang der Quell-PDU (PduTriggering).
    • Weiterleitung an das Ziel-Interface via PduR_<Dst>Transmit().
    • Bei TP-Routing steuert pdurTpChunkSize die Segmentierungsgröße.
    • Bei Längenunterschieden oder asynchronen Initialisierungszuständen: Belegung unbesetzter Byte-Offsets über die an TargetIPduRef definierten DefaultValueElement-Instanzen (elementPosition und elementByteValue).
  3. Signal-Routing (Com-Ebene):
    • Entpacken im Com-Modul (Com_RxIndication()), signalspezifisches Routing über Com_MainFunctionRouteSignals() anhand von ISignalMapping, Skalierung/Maskierung und anschließendes Packen in Ziel-IPDUs.
  4. Variabilitätsbindung:
    • Evaluierung der Mappings zur Post-Build-Bindungszeit (postBuild).

4. Normative Relevanz & Entwickler-Hinweise

  • Metamodell-Konformität: Alle Mappings unterliegen der AUTOSAR-Variabilität («atpVariation») mit spätester Bindungszeit PostBuild.
  • Asymmetrie im I-PDU-Mapping: Nur das Ziel-PDU-Ende wird über eine Wrapper-Klasse (TargetIPduRef) gekapselt, da Defaultwerte ausschließlich für die Ziel-PDU spezifiziert werden. Quell-PDUs referenzieren direkt PduTriggering.
  • Default-Werte: Ein PduMappingDefaultValue muss mindestens ein DefaultValueElement (Kardinalität 1..*) enthalten.
  • TP-Routing: pdurTpChunkSize verwendet den strikteren Datentyp PositiveInteger.
