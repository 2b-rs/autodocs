1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Lineares Speicherabbild / Serialisierungs-Layout (Memory Representation / SwRecordLayout).
  • Technischer Zweck: Spezifiziert die physische In-Memory-Ablage eines zweidimensionalen, interpolierten Kennfelds (IntMap) mit integrierten Achsenstützstellen im Speicher (Flash/ROM oder kalibrierbarem RAM) nach dem Standard AUTOSAR_TR_GeneralBlueprintsSupplement (Anforderung TPS_SWCT_01748).
  • Funktionale Einordnung:
    • Bindeglied zwischen AUTOSAR Software Component Template (SwRecordLayout), dem RTE-Code-Generator und Kalibriertools (ASAM MCD-2 MC / A2L via XCP).
    • Definiert eine zusammenhängende, selbstbeschreibende Datenstruktur für bilineare Interpolationsroutinen (z. B. AUTOSAR Math Library Bfx / Application SWCs).
    • Gewährleistet binäre Interoperabilität zwischen Steuergeräte-Firmware und Mess-/Kalibriersystemen (z. B. Vector CANape, ETAS INCA) ohne proprietäre Mapping-Algorithmen.

2. Komponenten, Entitäten & Schnittstellen

Dargestellt ist ein linear zusammenhängender Speicherblock für eine 3 × 4-Matrix (N_y = 3 Zeilen, N_x = 4 Spalten) in zeilenweiser Ausrichtung (ROW_DIR = Row-Major Order).

  • Header / Achsendimensionen (Meta-Information):
    • N x=4: Anzahl der Stützstellen der X-Achse (Abszisse / Eingangssignal 1 / Spalten; entspricht A2L NO_AXIS_PTS_X).
    • N y=3: Anzahl der Stützstellen der Y-Achse (Ordinate / Eingangssignal 2 / Zeilen; entspricht A2L NO_AXIS_PTS_Y).
  • Integrierte Stützstellenachsen (Breakpoints):
    • Valx(1) bis Valx(4): X-Stützstellenvektor (AXIS_PTS_X), streng monoton steigend parametrisiert.
    • Valy(1) bis Valy(3): Y-Stützstellenvektor (AXIS_PTS_Y), streng monoton steigend parametrisiert.
  • Kennfeldwerte / Funktionswerte (FNC_VALUES):
    • 12 Tabellenwerte / Z-Werte, abgelegt in strikter Zeilenreihenfolge (ROW_DIR):
      • Zeile 1: [1,1], [1,2], [1,3], [1,4]
      • Zeile 2: [2,1], [2,2], [2,3], [2,4]
      • Zeile 3: [3,1], [3,2], [3,3], [3,4]
  • Metamodell-Beziehungen & Stereotypen:
    • Zugehörig zu SwRecordLayout mit Kategorie MAP bzw. INT_MAP.
    • Verknüpft via ApplicationPrimitiveDataType / ApplicationRecordDataType («isOfType») mit ParameterDataPrototype an ParameterPortInterface oder CalibrationPortInterface.
    • Attribute im Metamodell: SwRecordLayoutGroup.indexIncrement = INDEX_INCR, SwRecordLayoutGroup.direction = ROW_DIR.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Speicherschema besitzt das Diagramm keinen Zustandsautomaten. Das Laufzeitverhalten betrifft den Lese-/Schreibzugriff im Steuergerät:

  1. Interpolations-Pipeline (Online-Auswertung im ASW/BSW-Taskkontext):
    • Stufe 1 (Grenzprüfung & Achsensuche X): Binäre oder sequentielle Intervallsuche des Eingangswerts x im Vektor Valx[1..Nx] zur Ermittlung des Stützstellen-Intervalls [Valx_i, Valx_i+1] und des Normierungsfaktors $f_x = \frac{x - Valx_i}{Valx_{i+1} - Valx_i}$.
    • Stufe 2 (Grenzprüfung & Achsensuche Y): Suche des Eingangswerts y im Vektor Valy[1..Ny] für [Valy_j, Valy_j+1] und $f_y = \frac{y - Valy_j}{Valy_{j+1} - Valy_j}$.
    • Stufe 3 (Adressberechnung via ROW_DIR):
      • Startadresse Wertebereich: $Offset_{Base} = \text{sizeof}(N_x) + \text{sizeof}(N_y) + (N_x \cdot \text{sizeof}(Val_x)) + (N_y \cdot \text{sizeof}(Val_y))$.
      • Indexberechnung des Werts an Position [j, i]: $Index(j, i) = (j - 1) · N_x + (i - 1)$
      • Direkter Zugriff auf die 4 Eckwerte: Z_11 = [j, i], Z_12 = [j, i+1], Z_21 = [j+1, i], Z_22 = [j+1, i+1].
    • Stufe 4 (Bilineare Interpolation): Berechnung des Ausgabewertes $z = (1 - f_x)(1 - f_y)Z_{11} + f_x(1 - f_y)Z_{12} + (1 - f_x)f_y Z_{21} + f_x f_y Z_{22}$.
  2. Kalibrier- und Modifikationspfad (XCP / ASAM MCD-2 MC):
    • Kalibriertool schreibt modifizierte Stützstellen oder Kennfeldwerte byteweise über XCP-Kommunikation.
    • Konsistenzgarantie: Um Glitches bei gleichzeitiger Modifikation von Stützstellen und Funktionswerten durch Kalibriertools zu vermeiden, müssen Page-Switching (Working Page / Reference Page) oder Interrupt-Locks / OS-Ressourcen genutzt werden.

4. Normative Relevanz & Entwickler-Hinweise

  • C-Struktur-Mapping & Compiler-Padding:
    • Typische C-Repräsentation im RTE-generierten Code (Rte_Type.h): 
      typedef struct {
    uint8 Nx;
    uint8 Ny;
    float32 Valx[4];
    float32 Valy[3];
    float32 Values[3][4]; /* Values[y][x]: 3 Zeilen, 4 Spalten */
} IntMap_3x4_Type;
    • Achtung Alignment: Weichen die Typen von N_x, N_y (z. B. uint8) von den Achs- und Kennfeldwerten ab (z. B. float32 oder uint16), erzwingen Compiler standardmäßig Füll-Bytes (Padding). Da A2L und Kalibriertools von kontinuierlichen Byte-Offsets gemäß Record Layout ausgehen, muss das Struct zwingend über Präprozessor-Direktiven (#pragma pack(1) bzw. Alignment-Makros des MCAL-Compilers) oder explizite Pad-Attribute im SwRecordLayout synchronisiert werden.
  • Transpositionsgefahr (ROW_DIR vs. COLUMN_DIR):
    • ROW_DIR legt Werte zeilenweise ab ([1,1], [1,2], …). Wird im A2L fälschlich COLUMN_DIR generiert (Spaltenausrichtung: [1,1], [2,1], …), greift das Kalibriertool transponiert zu. Das führt zu falschen Kalibrieranzeigen und fehlerhafter Steuergeräte-Bedatung.
  • Dynamische versus statische Dimensionierung:
    • Bei variablen Kennfeldern (VARIABLE_SIZE) werden N_x und N_y zur Laufzeit ausgewertet; das Array reserviert den maximal spezifizierten Speicherplatz.
    • Bei festen Kennfeldern (FIXED_SIZE) können Compiler und RTE auf die Speicherung von N_x, N_y verzichten, sofern dies im entsprechenden SwRecordLayout (z. B. FixMap) spezifiziert ist. Im hier dargestellten IntMap sind N_x und N_y integraler Bestandteil des Headers.
