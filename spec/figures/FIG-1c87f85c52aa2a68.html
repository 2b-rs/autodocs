1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Struktur- und Mapping-Diagramm (Signal-to-Data-Mapping) der AUTOSAR System Description (AUTOSAR_TPS_SystemTemplate).
  • Funktionaler Kontext: Transformation hierarchisch geschachtelter zusammengesetzter Datentypen (Composite Data Types / Records) aus der Software-Komponenten-Ebene (VFB / Application Layer) auf flache Netzwerkelemente (SystemSignalGroup, SystemSignal) der Kommunikationsebene (System / Cluster / Com Stack).
  • Zweck: Auflösung von Verschachtelungen (Records in Records), da Netzwerksignale im AUTOSAR-Metamodell ausschließlich atomare Datenstrukturen übertragen können.

2. Komponenten, Entitäten & Schnittstellen

  • Software-/VFB-Datenebene (Sender/Receiver-Datentypen):
  • Record a: Top-Level Composite Data Type (ApplicationRecordDataType bzw. ImplementationDataType).
  • Record b, Record c: Verschachtelte Record-Elemente (ApplicationRecordElement / ImplementationDataTypeElement).
  • Integer c, Integer d, Integer f, Integer g: Atomare primitive Endknoten (Leaves) innerhalb der Record-Hierarchie.
  • System-/Netzwerkebene (System Template):
  • SystemSignalGroup a: Logische Gruppierung zur Sicherstellung der kohärenten Übertragung zusammenhängender Signale.
  • SystemSignal c, SystemSignal d, SystemSignal f, SystemSignal g: Atomare Kommunikationssignale innerhalb der SystemSignalGroup a.
  • Mapping-Entitäten & Metamodell-Beziehungen:
  • SenderReceiverToSignalGroupMapping: Verknüpft die übergeordnete Datenschnittstelle Record a bidirektional mit SystemSignalGroup a.
  • SenderRecRecordTypeMapping: Definiert die strukturelle Zerlegung des Records.
  • SenderRecRecordElementMapping:
  • Für Zwischenknoten (Record b, Record c): Enthält keine systemSignal-Referenz, sondern referenziert rekursiv ein complexTypeMapping, da Signale nicht auf Composite Types referenzieren dürfen.
  • Für atomare Blattelemente (Integer c, Integer d, Integer f, Integer g): Hält die konkrete 1:1-Referenz auf das jeweilige SystemSignal.

3. Dynamisches Verhalten & Sequenzablauf

Hinweis: Das Schaubild stellt primär ein statisches Designtime-Mapping im System Template (ARXML) dar. Zur Laufzeit induziert dies folgenden Ablauf im AUTOSAR Classic Com-Stack:

  1. SWC-Sendepfad (Rte_Write): Die Applikation schreibt die verschachtelte C-Struktur Record a atomar oder per Pointer-Übergabe an den RTE-Port.
  2. RTE-Com-Interaktion & Shadow-Buffer:
  • Die RTE serialisiert bzw. kopiert die primitiven Elemente über Com_UpdateShadowSignal() für jedes atomare Signal (c, d, f, g) in den Shadow-Buffer der Signal-Gruppe.
  • Mit dem Aufruf von Com_SendSignalGroup(SignalGroupId) werden die Werte der SystemSignals atomar in den I-PDU-Sendepuffer übertragen.
  1. Bus-Transfer: Signale reisen gepackt in einer I-PDU über den Bus (CAN, LIN, FlexRay, Ethernet).
  2. Empfangspfad (Rte_Read):
  • Aufruf von Com_ReceiveSignalGroup() kopiert die Signale aus der I-PDU in den lokalen Empfangs-Shadow-Buffer.
  • Einzelne Signale werden über Com_ReceiveShadowSignal() in die verschachtelte Ziel-C-Struktur der SWC zusammengesetzt; Tearing zwischen den verschachtelten Record-Feldern wird ausgeschlossen.

4. Normative Relevanz & Entwickler-Hinweise

  • Restriktion für System-Autoren & Generatoren: Ein SenderRecRecordElementMapping darf nur dann direkt auf ein SystemSignal verweisen, wenn das referenzierte Element primitiv/atomar ist. Für verschachtelte Sub-Records ist zwingend ein complexTypeMapping zu instanziieren.
  • Kein natives Struct-Packing auf dem Bus: Ein AUTOSAR-Record wird nicht binär als Speicherabbild (C-Struct mit Compiler-Padding/Alignment) über das Netzwerk übertragen. Jedes atomare Element muss explizit über Bitposition, Bitlänge, Endianness und Skalierung (CompuMethod) im I-PDU-Layout definiert werden.
  • Konsistenzgarantie via SystemSignalGroup: Die Bündelung zu SystemSignalGroup a erzwingt im Com-Stack den Einsatz von Shadow-Buffern. Dadurch wird garantiert, dass zusammengehörige Teildaten (c, d, f, g) konsistent aus demselben Abtastzyklus stammen und nicht über I-PDU-Grenzen hinweg inkonsistent gelesen werden.
  • RTE-Generierung: Das System-Mapping bestimmt direkt die Codegenerierung der RTE (Rte_Type.h Typdefinitionen und Port-APIs) sowie die Signalkonfiguration im Com-Modul (Com_Cfg.h / Com_Lcfg.c).
