1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECUC-Parameterkonfigurations-Metamodell (UML-Klassendiagramm der BSW-Modulbeschreibung).
  • Funktionale Einordnung: AUTOSAR Classic Platform (R25-11), BSW-Treiber EthSwt (Ethernet Switch Driver), Schicht Microcontroller Abstraction Layer (MCAL) / Complex Device Driver (CDD).
  • Technischer Zweck: Konfiguration der TSN-Mechanismen für Ingress Stream Identification (IEEE 802.1CB), Per-Stream Filtering and Policing (PSFP gemäß IEEE 802.1Qci) sowie Asynchronous Traffic Shaping (ATS gemäß IEEE 802.1Qcr). Modelliert die Zuordnung von identifizierten Datenströmen (EthSwtStreamIdentificationEntry) zu Filterregeln (EthSwtStreamFilterEntry), Gate-Instanzen, Metering-Algorithmen und ATS-Instanzen auf Switch-Hardwareebene.

2. Komponenten, Entitäten & Schnittstellen

Übergeordnete & vorgelagerte Container
  • EthSwtStreamFilterTable (EcucParamConfContainerDef, Multiplizität: 0..1): Repräsentiert die hardwareseitige Stream-Filter-Tabelle des Switches.
  • EthSwtStreamIdentificationEntry (EcucParamConfContainerDef, Multiplizität: 0..*): Definiert Regeln zur Stream-Identifikation eingehender Ethernet-Frames (IEEE 802.1CB).
    • EthSwtStreamHandleAssignment (EcucIntegerParamDef, Parameter via +parameter, min: 0, max: 65535): Weist dem erkannten Stream einen numerischen Stream Handle zu.
Zentraler Konfigurationscontainer
  • EthSwtStreamFilterEntry (EcucParamConfContainerDef, Multiplizität: 1..* via +subContainer von EthSwtStreamFilterTable): Definiert eine einzelne Filterregel innerhalb der Tabelle.
    • EthSwtStreamFilterEntryPosition (EcucIntegerParamDef, Parameter, min: 0, max: 65535): Definiert die Priorität/Reihenfolge der Regelauswertung in der Hardware (Lookup-Order / Rule Precedence).
    • EthSwtStreamFilterPriority (EcucIntegerParamDef, Parameter, min: 0, max: 7): PCP/VLAN-Prioritätsfilter zur Klassifizierung des Streams (IEEE 802.1p/Q).
Sub-Container
  • EthSwtAssignedStreamHandle (EcucParamConfContainerDef, Multiplizität: 1..1 via +subContainer von EthSwtStreamFilterEntry): Bestimmt die Stream-Zuordnung für das Regellisting:
    • EthSwtStreamHandleId (EcucIntegerParamDef, Parameter, min: 0, max: 65535, Multiplizität: 0..*): Liste diskreter Stream-Identifikatoren (Stream Handles), die auf diese Filterregel matchen. Besitzt eine UML-Abhängigkeit (gestrichelte Pfeillinie) auf EthSwtStreamHandleAssignment.
    • EthSwtStreamHandleIdWildcard (EcucBooleanParamDef, Parameter): Wildcard-Flag (TRUE/FALSE). Bei Aktivierung matcht die Filterregel unabhängig von der konkreten Stream-ID auf jeden Frame.
Referenzen (EcucReferenceDef, alle optional mit Kardinalität 0..1)
  • EthSwtFilterMaxSduSizeRef → Ziel: EthSwtFilterMaxSduSizeEntry (1..*): Verknüpfung zur Längenvalidierung eingehender Frames (SDU Length Verification; Drop bei Frame-Größenüberschreitung).
  • EthSwtAtsInstanceEntryRef → Ziel: EthSwtAtsInstanceEntry (0..*): Verknüpfung zur IEEE 802.1Qcr ATS-Instanz (Urgency-Queue / Interleaved Periodic Queue Policing).
  • EthSwtFlowMeteringEntryRef → Ziel: EthSwtFlowMeteringEntry (1..*): Verknüpfung zu einer Token-Bucket-Metering-Instanz (z. B. Two-Rate Three-Color Marker nach RFC 2698 / IEEE 802.1Qci).
  • EthSwtStreamGateEntryRef → Ziel: EthSwtStreamGateEntry (1..*): Verknüpfung zu einem Stream Gate (IEEE 802.1Qci Gate Control List, GCL; zyklisches Öffnen/Schließen von Pfaden).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt ein statisches Konfigurationsmodell; hardwareseitig wird zur Laufzeit folgender deterministischer Switch-Pipeline-Pfad umgesetzt:

  1. Ingress Stream Identification: Eingehender Frame wird an einem Switch-Port empfangen und gemäß den Parametern in EthSwtStreamIdentificationEntry einer Stream-ID zugeordnet, die über EthSwtStreamHandleAssignment zugewiesen wird.
  2. Filter Matching:
    • Evaluierung erfolgt absteigend/aufsteigend anhand EthSwtStreamFilterEntryPosition.
    • Matching gegen EthSwtStreamFilterPriority (VLAN PCP 0..7).
    • Matching gegen den zugewiesenen Stream Handle: Übereinstimmung, wenn der in EthSwtStreamHandleAssignment ermittelte Wert mit einem Eintrag in EthSwtStreamHandleId übereinstimmt ODER EthSwtStreamHandleIdWildcard == TRUE.
  3. Pipeline-Aktionen (bei Match):
    • SDU Check (EthSwtFilterMaxSduSizeRef): Überschreitet die Frame-Länge den konfigurierten Schwellwert, wird der Frame verworfen und der entsprechende Error-Counter inkrementiert.
    • Stream Gate Status (EthSwtStreamGateEntryRef): Prüfung des Gate-Zustands (OPEN vs. CLOSED). Bei CLOSED wird der Frame gedroppt (Policing Violation).
    • Metering & Policing (EthSwtFlowMeteringEntryRef): Token-Bucket-Abrechnung (Conform/Exceed). Markierung oder Drop bei Bandbreitenüberschreitung.
    • Shaping (EthSwtAtsInstanceEntryRef): Zuweisung zu einer Asynchronous Traffic Shaping Scheduler-Queue zur Egress-Glättung.

4. Normative Relevanz & Entwickler-Hinweise

  • Konsistenz zwischen Stream Identification und Filtering:
    • Die modellierte Abhängigkeit zwischen EthSwtStreamHandleId und EthSwtStreamHandleAssignment erfordert Konsistenzprüfungen im Konfigurationsgenerator: Jede konfigurierte EthSwtStreamHandleId muss einem vorhandenen EthSwtStreamHandleAssignment in EthSwtStreamIdentificationEntry entsprechen, sofern kein Wildcard-Matching aktiv ist.
  • Hardware-Mapping & Allokation:
    • EthSwtStreamFilterEntryPosition muss zwingend konsistent auf hardwareseitige Filter-/TCAM-Slots abgebildet werden. Kollisionen bei identischer Position müssen vom Konfigurationsgenerator (EthSwt_BSW_Generator) per Pre-Compile-Check abgefangen werden.
    • Hardware-Ressourcen für Filter, Gates und Metering-Buckets sind in Switch-ICs (z. B. NXP SJA1110, Marvell Link Street, TI) strikt limitiert. Ein 1:N- oder 1:1-Mapping der Referenzen (EthSwtStreamGateEntryRef, etc.) muss gegen die tatsächlichen Hardware-Instanzen validiert werden.
  • Konfigurationsabhängigkeiten:
    • Wenn EthSwtStreamHandleIdWildcard == TRUE, kann EthSwtStreamHandleId leer bleiben (lowerMultiplicity = 0). Ist das Wildcard-Flag FALSE, muss mindestens eine EthSwtStreamHandleId angegeben werden, um eine wirksame Filterregel zu definieren (Pre-Compile Validator Rule erforderlich).
    • Alle vier Referenzen sind optional (0..1). Eine Filterregel kann reine Stream-Identifikation/Policing betreiben, ohne ATS oder Flow-Metering zu erzwingen.
