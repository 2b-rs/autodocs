1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Instanzdiagramm / Konzeptuelles System-Template-Datenflussmodell (AUTOSAR System Template, Release R3.2.3, Kapitel Transport Layer / ISO TP Modeling).
  • Architektur-Kontext: Repräsentation einer Transportprotokoll-Verbindung gemäß ISO 15765-2 (IsoTpConnection) im Rahmen der AUTOSAR System Description (System Template).
  • Technischer Zweck: Spezifikation der strukturellen Zuordnung einer logischen Punkt-zu-Punkt-Transportverbindung zwischen zwei Steuergeräten (EcuInstance) auf die konkreten Netzwerknachrichten (PDUs). Das Diagramm veranschaulicht gemäß TPS_SYST_01064, wie eine gerichtet definierte TP-Verbindung (vom Datensender zum Datenempfänger) trotz asymmetrischer SDU-Richtung über zwei PDU-Mengen (TxPduPool und RxPduPool) auf den bidirektionalen N-PDU-Fluss des ISO-15765-2-Protokolls (Datenframes vs. Flow-Control-Frames) abgebildet wird.

2. Komponenten, Entitäten & Schnittstellen

  • IsoTpConnection (Metaklasse):
    • Zentrale Konfigurationseinheit einer ISO-TP-Verbindung auf Systemebene.
    • Rollen-Assoziationen:
      • transmitter (Multiplizität 1): Referenziert die sendende EcuInstance (ECU A).
      • receiver (Multiplizität 1): Referenziert die empfangende EcuInstance (ECU B).
      • Aggregation/Referenz auf TxPduPool: Menge der Sende-PDUs in Übertragungsrichtung der Nutzdaten.
      • Aggregation/Referenz auf RxPduPool: Menge der Empfangs-/Rückkanal-PDUs für die Protokollflusssteuerung.
  • ECU A & ECU B (EcuInstance):
    • ECU A: Agiert in dieser Verbindung als logischer Transmitter (Quelle der TP-Nutzdaten/N-SDU). Verfügt über einen TX-Port (Senden von Pdu1) und einen RX-Port (Empfang von Pdu2).
    • ECU B: Agiert als logischer Receiver (Senke der TP-Nutzdaten/N-SDU). Empfängt Pdu1 und sendet Pdu2.
  • TxPduPool & RxPduPool (PDU-Container / Metamodell-Rollen):
    • TxPduPool: Bündelt PDUs (Pdu1), die physisch von ECU A an ECU B übertragen werden (Vorwärtskanal für SF, FF, CF).
    • RxPduPool: Bündelt PDUs (Pdu2), die physisch von ECU B an ECU A übertragen werden (Rückkanal für Flow Control Frames / FC).
  • Pdu1 & Pdu2 (Pdu / N-Pdu):
    • Konkrete Kommunikations-PDUs auf dem Bus (CAN-Frames).
    • Pdu1: Trägt Single Frame (SF), First Frame (FF) oder Consecutive Frame (CF).
    • Pdu2: Trägt Flow Control Frames (FC: CTS, WAIT, OVERFLOW).

3. Dynamisches Verhalten & Sequenzablauf

Obwohl statisch modelliert, bildet die Instanz den protokollarischen Ablauf nach ISO 15765-2 ab:

  1. Sendeinitiierung (ECU A):
    • PduR übergibt eine segmentierte N-SDU (> 8 Bytes, z. B. UDS-Diagnoseauftrag) an CanTp (PduR_CanTpTransmit).
  2. First Frame Übertragung (Forward Path via TxPduPool):
    • ECU A (transmitter) sendet Pdu1 mit PCI-Typ First Frame (FF) an ECU B.
  3. Flusssteuerungs-Rückkanal (Backward Path via RxPduPool):
    • ECU B (receiver) empfängt Pdu1, fordert Puffer via PduR_CanTpStartOfReception an und antwortet über Pdu2 mit einem Flow Control (FC) Frame (inkl. Block Size BS und minimaler Trennzeit STmin).
  4. Segmentierter Datentransfer:
    • ECU A empfängt Pdu2 auf seinem RX-Pfad, wertet die Parameter aus und sendet aufeinanderfolgende Consecutive Frames (CF) über Pdu1 (TxPduPool), bis der Block oder die Gesamt-SDU übertragen ist.
  5. Abschluss & Fehlerbehandlung:
    • Nach erfolgreicher Übertragung erfolgt auf beiden Seiten die Benachrichtigung der oberen Schichten (CanTp_TxConfirmation / CanTp_RxIndication).
    • Bei Timeout (N_As, N_Bs, N_Cr) bricht die Verbindung ab; Det meldet CANTP_E_PARAM_ID bzw. Dem setzt ereignisbezogene Kommunikationsfehler.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Generierung (CanTp-Konfiguration):
    • Die Aufteilung in TxPduPool und RxPduPool der IsoTpConnection steuert im AUTOSAR-Generator die Parametrierung des BSW-Moduls CanTp (z. B. CanTpChannel, CanTpRxNSdu, CanTpTxNSdu sowie die Zuordnung von CanTpRxNPdu und CanTpTxFcNPdu).
  • Bidirektionale PDU-Allokation für unidirektionale logische Kanäle:
    • Auch für rein unidirektionale Anwendungs-Streams (z. B. Diagnoserequest vom Tester zur ECU) müssen zwingend zwei CAN-IDs/PDUs konfiguriert werden (Pdu1 für Daten, Pdu2 für Flow Control), sofern die Payloads die Single-Frame-Grenze (8 Byte bei CAN 2.0 bzw. 64 Byte bei CAN-FD) überschreiten können.
  • Pool-Semantik (Extended / Mixed Addressing):
    • Die Verwendung von PDU-Pools statt einzelner PDU-Referenzen in IsoTpConnection erlaubt das dynamische oder adressierungsabhängige Routing, bei dem mehrere logische TP-Verbindungen denselben CAN-ID-Pool über adresscodierte N-PDUs (z. B. Extended Addressing mit Address Byte) teilen können.
  • Fallstrick bei der Parametrierung:
    • TxPduPool bezieht sich auf die Sendedaten des logischen Transmitters (ECU A). RxPduPool stellt aus Sicht des Transmitters Empfangs-PDUs dar, wird aber von ECU B physisch gesendet. Entwickler und Tool-Ketten müssen sicherstellen, dass CanIf-Routingtabellen für ECU B die PDUs aus RxPduPool als Sende-PDU (CanIfTxPduConfig) konfigurieren.
