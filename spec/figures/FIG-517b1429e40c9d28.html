1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (Metamodell-Ausschnitt des AUTOSAR Diagnostic Extract Template, DEXT).
  • Technischer Zweck: Formale Spezifikation des Metamodells zur Abbildung des UDS-Dienstes WriteMemoryByAddress (Service-ID 0x3D gemäß ISO 14229-1) innerhalb des AUTOSAR Diagnostic Extract (DEXT).
  • Funktionale Einordnung: DEXT dient als standardisiertes Austauschformat (ARXML) zwischen OEM und Tier-1. Die hier definierten Klassen bilden die Basis für die Codegenerierung und Konfiguration des AUTOSAR-Basissoftwaremoduls Dcm (Diagnostic Communication Manager, Submodul DSP/DSD) sowie der Anbindung an den Memory-Stack (MemIf, Fee, Fls, NvM) oder SWC-RTE-Schnittstellen.

2. Komponenten, Entitäten & Schnittstellen

Entitäten (Klassen)
  • DiagnosticCommonElement: Abstrakte Basiskonstruktion für wiederverwendbare Modellelemente im DEXT-Umfeld.
  • DiagnosticAccessPermission: Kapselt Sicherheits- und Sitzungsbedingungen (Diagnostic Sessions, Security Levels) für den Dienstzugriff.
  • DiagnosticServiceClass: Abstrakte Definition eines Diagnose-Services.
  • DiagnosticServiceInstance: Repräsentiert die konkrete Bereitstellung/Instanziierung eines Dienstes auf einem Steuergerät.
  • DiagnosticMemoryByAddress: Abstrakte Zwischenklasse für alle speicheradressbasierten Diagnosedienste.
  • DiagnosticMemoryAddressableRangeAccess: Spezialisierung zur Definition konkreter Speicheradressbereiche.
  • DiagnosticWriteMemoryByAddress: Konkrete Instanz des Dienstes 0x3D im DEXT.
  • DiagnosticWriteMemoryByAddressClass: Konkrete Dienstklasse für 0x3D.
Beziehungen, Kardinalitäten und Vererbungen
  • Generalisierungen (Spezialisierungen):
    • DiagnosticAccessPermission, DiagnosticServiceInstance und DiagnosticServiceClass erben von DiagnosticCommonElement.
    • Vererbungspfad Instanzebene: DiagnosticServiceInstance ← DiagnosticMemoryByAddress ← DiagnosticMemoryAddressableRangeAccess ← DiagnosticWriteMemoryByAddress.
    • Vererbungspfad Klassenebene: DiagnosticServiceClass ← DiagnosticWriteMemoryByAddressClass.
  • Assoziationen & Kardinalitäten:
    • DiagnosticServiceInstance → DiagnosticServiceClass: Assoziationsrolle +serviceClass, Multiplizität 0..1, Stereotyp «atpAbstract».
    • DiagnosticWriteMemoryByAddress → DiagnosticWriteMemoryByAddressClass: Assoziationsrolle +writeClass, Multiplizität 0..1, Constraint {redefines serviceClass}.
    • DiagnosticServiceInstance → DiagnosticAccessPermission: Assoziationsrolle +accessPermission, Multiplizität 0..1, Stereotyp «atpSplitable» (instanzspezifische Zugriffsbeschränkung).

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Metamodell handelt, determiniert die Struktur das Laufzeitverhalten im Dcm-Stack bei Empfang eines UDS-Requests 0x3D:

Tester                     Dcm (DSD/DSP)                       App / Memory-Stack
  |                              |                                     |
  |--- UDS Request (0x3D) ------>|                                     |
  |    [ALFID, Address, Size,    |                                     |
  |     DataRecord]              |                                     |
  |                              |-- 1. Session- & Security-Check ---->|
  |                              |   (DiagnosticAccessPermission)      |
  |                              |   NRC 0x7F 0x3D 0x33 / 0x22         |
  |                              |                                     |
  |                              |-- 2. Range- & Alignment-Validierung |
  |                              |   (DiagnosticMemoryAddressable-     |
  |                              |    RangeAccess)                     |
  |                              |   NRC 0x7F 0x3D 0x31 (Out of Range) |
  |                              |                                     |
  |                              |-- 3. Schreiboperation ausführen --->|
  |                              |      (synchron via Callout oder     |
  |                              |       asynchron via MemIf/NvM)      |
  |                              |<-- 4. Result (OK / PENDING / ERROR)-|
  |                              |                                     |
  |<-- Pos. Response (0x7D) -----|                                     |
  |    [ALFID, Address, Size]    |                                     |
  • NRC-Abbruchbedingungen (Standard-UDS-Verhalten via Metamodell-Restriktionen):
    • Verstoß gegen DiagnosticAccessPermission → NRC 0x33 (SecurityAccessDenied) oder NRC 0x22 (ConditionsNotCorrect).
    • Adresse/Länge liegt außerhalb des konfigurierten DiagnosticMemoryAddressableRangeAccess → NRC 0x31 (RequestOutOfRange).
    • Schreibzugriff schlägt im Treiber fehl (z. B. Hardware-Lock, Flash-Fehler) → NRC 0x72 (GeneralProgrammingFailure).

4. Normative Relevanz & Entwickler-Hinweise

  • Dcm-Generatorkonfiguration (DcmDspMemory / DcmDspWriteMemoryByAddress):
    • Aus DiagnosticMemoryAddressableRangeAccess werden im Classic Platform BSW die Container DcmDspMemoryRangeInfo generiert (Definition von DcmDspMemoryRangeLow, DcmDspMemoryRangeHigh, Schreibrechten und Adressierungsformaten wie addressAndLengthFormatIdentifier).
  • API-Verträge:
    • Der Zugriff auf den adressierten Speicher erfolgt über konfigurierte Dcm-Callouts:
      • Dcm_WriteMemory(Dcm_OpStatusType OpStatus, uint8 MemoryIdentifier, uint32 MemoryAddress, uint32 MemorySize, const uint8* MemoryData, Dcm_NegativeResponseCodeType* ErrorCode)
    • Liefert der Treiber DCM_E_PENDING, muss der Dcm asynchron warten und ggf. NRC 0x78 (ResponsePending) an den Tester senden, bis DCM_E_OK oder DCM_E_NOT_OK gemeldet wird.
  • Berechtigungskollision (accessPermissionValidity):
    • Bei gleichzeitiger Definition von accessPermission an DiagnosticWriteMemoryByAddressClass und DiagnosticWriteMemoryByAddress legt DiagnosticAccessPermissionValidityEnum normativ fest, ob die Instanzberechtigung die Klassenberechtigung überschreibt (OVERWRITE) oder beide kumulativ gelten (AND/OR).
  • Sicherheit:
    • Schreibbereiche für 0x3D dürfen sich im Flash/RAM niemals mit geschützten Bootloader- oder HSM/SecOC-Vektortabellen überschneiden; solche Restriktionen müssen zwingend auf Metamodellebene via Range-Segmentierung abgesichert werden.
