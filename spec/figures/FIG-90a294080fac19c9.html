1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (M2-Metamodell-Ausschnitt gemäß AUTOSAR_TPS_SoftwareComponentTemplate, Release R4.0.3).
  • Architektur-Kontext: Spezifikation der Kommunikationsattribute (Communication Specification, ComSpec) auf Ebene des Software-Komponenten-Templates. Es definiert die statische Struktur zur Parametrierung von Client-Server-Aufrufen an einem erfordernden Port (RPortPrototype) vor der RTE-Generierung.

2. Komponenten, Entitäten & Schnittstellen

  • Entitäten & Metaklassen:
  • PortPrototype (kursiv / abstrakt): Abstrakte Basisklasse aller Port-Definitionen einer Software-Komponente.
  • AbstractRequiredPortPrototype (kursiv / abstrakt): Abstrakte Basisklasse für Port-Prototypen mit Required-Rolle (Spezialisierung von PortPrototype).
  • RPortComSpec (kursiv / abstrakt): Abstrakte Basisklasse für alle empfängerseitigen Kommunikationsspezifikationen.
  • ClientComSpec: Konkrete Spezialisierung von RPortComSpec. Kapselt die client-spezifischen Attribute für Operationen eines ClientServerInterface.
  • ClientServerOperation: Repräsentiert eine konkrete Service-Methode/Funktion innerhalb eines ClientServerInterface. Realisiert die Metaklassen/Stereotypen:
  • Identifiable: Verleiht dem Element einen eindeutigen Bezeichner (shortName) und Namensraum.
  • AtpStructureElement: Markiert das Element als strukturellen Bestandteil im AUTOSAR-Typmodell.
  • TransformationComSpecProps: Metaklasse für transformationsbezogene Kommunikationsspezifikationen. Realisiert die Metaklasse:
  • Describable: Verleiht dem Element eine formale Beschreibungsmöglichkeit.
  • Beziehungen & Kardinalitäten:
  • Komposition (AbstractRequiredPortPrototype $\blacklozenge\!\longrightarrow$ RPortComSpec):
  • Rollenname: +requiredComSpec
  • Kardinalität: 0..*. Ein AbstractRequiredPortPrototype kann null bis viele Kommunikationsspezifikationen enthalten.
  • Generalisierung (ClientComSpec $\longrightarrow\mkern-14mu\vartriangle$ RPortComSpec):
  • ClientComSpec erbt alle Eigenschaften von RPortComSpec.
  • Gerichtete Assoziation (ClientComSpec $\longrightarrow$ ClientServerOperation):
  • Rollenname: +operation
  • Kardinalität: 0..1. Eine ClientComSpec kann optional maximal eine ClientServerOperation referenzieren.
  • Komposition (ClientComSpec $\blacklozenge\!\longrightarrow$ TransformationComSpecProps):
  • Rollenname: +transformationComSpecProps
  • Kardinalität: 0..*. Eine ClientComSpec kann null bis viele TransformationComSpecProps enthalten.

3. Dynamisches Verhalten & Sequenzablauf

Als Metamodell-Ausschnitt beschreibt das Diagramm statische Deskriptor-Strukturen; die dynamische Ausprägung erfolgt zur Laufzeit über die RTE:

  1. RTE-API-Bindung: Für jede per ClientComSpec an einen RPortPrototype gebundene ClientServerOperation generiert der RTE-Generator die clientseitigen Schnittstellen:
  • Synchroner Aufruf: Rte_Call_<Port>_<Operation>(...)
  • Asynchroner Aufruf: Rte_Call_<Port>_<Operation>(...) (Anstoß) gefolgt von Rte_Result_<Port>_<Operation>(...) (Ergebnisabfrage).
  1. Synchroner Pfad: Blockierender Aufruf via RTE; Rückkehr erfolgt nach Ausführung durch den Server oder Ablauf eines konfigurierten Timeouts mit Rückgabewert RTE_E_TIMEOUT bzw. applikativem Fehlercode.
  2. Asynchroner Pfad: Nicht-blockierender Aufruf; die Fertigstellung triggert optional ein AsynchronousServerCallReturnsEvent an einer zugeordneten Runnable Entity des Clients.

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Authoring & Konsistenz: Wenn ein RPortPrototype mit einem ClientServerInterface typisiert wird, muss für jede von der SWC tatsächlich aufgerufene Operation eine ClientComSpec innerhalb des Containers requiredComSpecs deklariert werden.
  • 1:1-Bindung pro Operation: Da die Relation +operation die Kardinalität 1 erzwingt, dürfen in einem RPortPrototype nicht mehrere ClientComSpec-Elemente dieselbe ClientServerOperation referenzieren.
  • RTE-Generierung: Fehlt die ClientComSpec für eine im C-Code genutzte Operation, verweigert der RTE-Generator die Erzeugung des zugehörigen Funktions-Prototyps (Rte_Call_*) bzw. bricht mit einem Validierungsfehler ab.
  • Plattform-Kontext: Gilt für AUTOSAR Classic Platform (CP). Im Unterschied zu Sender-Receiver-Ports (NonqueuedReceiverComSpec / QueuedReceiverComSpec) hält ClientComSpec in R4.0.3 primär die Operations-Referenz und steuert keine Datenpuffergrößen oder Init-Werte.
