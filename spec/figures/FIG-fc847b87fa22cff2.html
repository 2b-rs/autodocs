1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Prozess- und Aktivitätsdiagramm (basierend auf dem SPEM 2.0-Standard / Software & Systems Process Engineering Metamodel).
  • Funktionaler Kontext: Phase des VFB-Entwurfs (Virtual Function Bus Design) innerhalb der AUTOSAR Classic Platform Methodology (TR_Methodology, R4.0.3, Kapitel 3). Der Task definiert die formale, zielhardwareunabhängige Spezifikation von Software-Komponenten-Typen und deren Schnittstellen vor der Allokation auf konkrete Steuergeräte (ECUs).

2. Komponenten, Entitäten & Schnittstellen

  • Akteur / Rolle:
  • Software Component Designer (SPEM-RoleDefinition): Führt die Entwurfsaktivität aus («performs»).
  • Aktivität / Task:
  • Define VFB Types (SPEM-TaskDefinition): Zentraler Modellierungsschritt zur Erzeugung der VFB-Typbeschreibungen in ARXML.
  • Eingangs-Artefakte:
  • VFB AUTOSAR Standard Package [Kardinalität 0..1, Stereotyp «input»]: Optionales Referenz-ARXML-Paket der Plattform, das standardisierte Schnittstellen und Datentypen bereitstellt (z. B. Standardized AUTOSAR Interfaces für BSW-Dienste wie Diagnostic Event Manager oder NVRAM Manager).
  • Ausgangs-Artefakte:
  • VFB Types [Kardinalität 1..*, Stereotyp «output»]: Obligatorische ARXML-Artefakte mit den abstrakten Typdefinitionen:
  • SwComponentType (AtomicSoftwareComponentType, CompositionSwComponentType, SensorActuatorSwComponentType etc.).
  • PortInterface (SenderReceiverInterface, ClientServerInterface, ParameterInterface, NvDataInterface, TriggerInterface).
  • PortPrototype (PPortPrototype, RPortPrototype, PRPortPrototype).
  • VFB Data Types [Kardinalität 0..*, Stereotyp «output»]: Optionale/ergänzende Datentypdefinitionen für die Interaktionsattribute der Port-Interfaces.

3. Dynamisches Verhalten & Sequenzablauf

  • Methodology-Ablauf (Entwurfszeit):
  1. Referenzimport (optional, 0..1): Laden standardisierter Interfaces aus dem AUTOSAR-Standardpaket zur Sicherstellung der Plattform-Interoperabilität.
  2. Typdefinition: Der Software Component Designer deklariert Komponenten-Hüllen und deren funktionale Ports/Schnittstellen ohne interne Implementierungsdetails.
  3. Artefakt-Export: Erzeugung von mindestens einer VFB-Typ-Deskription (1..) sowie der zugehörigen Applikations-Datentypen (0..).
  • Keine Laufzeit-Dynamik: Rein statischer Entwurfszeitprozess. Dynamische Aspekte (Scheduling, OS-Tasks, RTE-Events, BSW-Stack-Kommunikation via Com/PduR sowie Det/Dem-Fehlerpfade) existieren hier noch nicht; sie werden erst im nachgelagerten Task Define SwcInternalBehavior und bei der RTE-Generierung instanziiert.

4. Normative Relevanz & Entwickler-Hinweise

  • *RTE-Vertragsphase (Contract Phase)*: Die in VFB Types definierten Schnittstellen determinieren die C-API-Signaturen (Rte_Read_<p>_<o>, Rte_Write_<p>_<o>, Rte_Call_<p>_<o>) und RTE-Header (Rte_<Type>.h).
  • Abstraktion & Entkopplung: Streng getrennt von SwcInternalBehavior und Ziel-Hardware. Eine Änderung an VFB Types bricht die Schnittstellenkompatibilität nachgelagerter CompositionSwComponentTypes und erzwingt Re-Generierungen der RTE im gesamten Systemverbund.
  • Datentyptrennung (AUTOSAR 4.x Datentyp-Modell): Bei der Modellierung von VFB Data Types ist auf das duale Typkonzept zu achten: Entwurf auf Ebene der ApplicationDataTypes (physikalische Einheiten, Wertebereiche, CompuMethod) erfordert für die spätere Codegenerierung ein valides Mapping auf ImplementationDataTypes und SwBaseTypes (Standard-C-Typen).
