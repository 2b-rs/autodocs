1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-Schichtenarchitekturmodell (Blockdiagramm / Layered Architecture View) der BSW-Kommunikationsinfrastruktur für den CAN-Stack (Classic Platform R24-11 / R25-11).
  • Technischer Zweck: Vertikale und horizontale Einordnung des BSW-Moduls CanIf (CAN Interface) im Classic-AUTOSAR-Stack. Das Diagramm verdeutlicht die funktionale Trennung zwischen busunabhängigen Kommunikationsdiensten, CAN-spezifischen Services/Transportprotokollen, der Hardware-Abstraktionsschicht und den hardwarenahen MCAL-Treibern (interner μC-CAN vs. externer CAN-Controller via SPI), inkl. der Erweiterungen für CAN XL.

2. Komponenten, Entitäten & Schnittstellen

Schichten und Farbcodierung
  • Communication Services (Dienstschicht):
    • Busunabhängig (Orange): SecOC (Secure Onboard Communication), IpduM (IPDU Multiplexer), AUTOSAR COM, LD-COM (Large Data COM), DCM (Diagnostic Communication Manager), DLT (Diagnostic Log and Trace), PduR (PDU Router), Generic NM Interface (Nm).
    • CAN-spezifisch (Blau): CanTp (CAN Transport Protocol – segmentierter I-PDU-Transfer gem. ISO 15765-2), CanSM (CAN State Manager – Netzwerkzustände & Bus-Off-Handling), CanNm (CAN Network Management – OSEK/AUTOSAR NM-Algorithmus).
  • Communication Hardware Abstraction (Hardware-Abstraktionsschicht - Grün):
    • L-SDU Router: Verteilt L-PDUs/L-SDUs oberhalb des CanIf.
    • CanIf (CAN Interface): Zentrales Bindeglied. Abstrahiert Controller-/Transceiver-Hardware, bietet einheitliche API nach oben (CanIf_Transmit, CanIf_RxIndication, CanIf_TxConfirmation) und aggregiert mehrere CAN-Treiber.
    • CAN Transceiver Driver (CanTrcv): Transceiver-Status- und Mode-Management (inkl. Standby, Normal, Sleep; explizit erweitert um CAN XL Transceiver wie SIC/SIC XL).
    • Driver for ext. CAN ASIC: Abstraktion für externe Standalone-CAN-Controller.
  • Microcontroller Abstraction Layer (MCAL - Rot/Rosa):
    • I/O Drivers: DIO Driver (direkte Pin-Ansteuerung, z. B. Transceiver-EN/STB-Pins oder Wake-Up-Interrupts).
    • Communication Drivers: SPIHandler Driver (MCAL-Treiber zur Kommunikation mit externen CAN-Controllern), CAN Driver (Can – Controller-spezifische Registerzugriffe, Mailbox-Management für Standard-, FD- und gestrichelt dargestellte CAN XL-Frames).
  • Hardware-Ebene ($\mu\text{C}$ & Extern):
    • $\mu\text{C}$-On-Chip-Peripherie: CAN (integrierter CAN-Controller) und SPI (Serial Peripheral Interface).
    • Extern: External CAN Controller (angebunden via SPI-Bus).
Beziehungen & Schnittstellenkopplung
  • Dienst-Ebene zu Abstraktion:
    • PduR ↔ CanIf (Direktübertragung von I-PDUs ≤ 8 Byte Classic CAN / ≤ 64 Byte CAN FD / L-PDUs).
    • PduR ↔ CanTp (Segmentierte Diagnosetelegramme / Large I-PDUs) → CanIf.
    • CanSM ↔ CanIf (Steuerung von Controller-Betriebszuständen: UNINIT, STOPPED, STARTED, SLEEP sowie Wake-Up- und Transceiver-Modi).
    • CanNm ↔ CanIf (Senden/Empfangen von NM-PDUs).
  • Innerhalb Hardware Abstraction:
    • L-SDU Router ↔ CanIf (Routing auf L-SDU-Ebene).
    • CanIf ↔ CanTrcv & Driver for ext. CAN ASIC.
  • Abstraktion zu MCAL:
    • CanIf ↔ CAN Driver (Can_Write, Can_MainFunction_Write, Can_MainFunction_Read bzw. Polling/Interrupt-Handling).
    • Driver for ext. CAN ASIC ↔ SPIHandler Driver (Spi_SyncTransmit / Spi_AsyncTransmit).
    • CanTrcv ↔ DIO Driver (sofern Transceiver über diskrete GPIOs angesteuert wird).

3. Dynamisches Verhalten & Sequenzablauf

1. Sende-Pfad (Transmit Path)
  1. Trigger: COM oder Dcm triggert PDU-Übertragung via PduR_CanIfTransmit() oder PduR_CanTpTransmit().
  2. Kanalabstraktion: CanIf_Transmit() identifiziert anhand der TxPduId den logischen CAN-Controller, mappt PDU auf ein Hardware-Transmit-Handle (HTH) und ruft synchron Can_Write() auf.
  3. Bestätigung (asynchron):
    • MCAL-Interrupt / Polling (Can_MainFunction_Write()) meldet erfolgreichen Frame-Versand via Callback CanIf_TxConfirmation().
    • CanIf routet die Bestätigung weiter an PduR_CanIfTxConfirmation(), CanTp_TxConfirmation() oder CanNm_TxConfirmation().
2. Empfangs-Pfad (Receive Path)
  1. Hardware-Ereignis: CAN-Controller empfängt Frame in Hardware-Receive-Handle (HRH).
  2. Indikation: ISR oder Can_MainFunction_Read() triggert CanIf_RxIndication().
  3. Filterung & Routing: CanIf übernimmt Software-Filterung (Range/Mask), DLC-Validierung / PDU-Längenprüfung und leitet das L-PDU synchron an die Zielschicht (PduR_CanIfRxIndication(), CanTp_RxIndication() oder CanNm_RxIndication()).
3. State-Management & Bus-Off-Kaskade
  1. Controller meldet Bus-Off an CanIf (CanIf_ControllerBusOff()).
  2. CanIf meldet Zustand weiter an CanSM (CanSM_ControllerBusOff()).
  3. CanSM triggert Error-Management (Dem-Eintrag) und führt State-Machine für Bus-Off-Recovery aus (CanIf_SetControllerMode()).

4. Normative Relevanz & Entwickler-Hinweise

  • Hardware-Entkopplung (CanIf als Single Point of Entry): Obere Schichten (PduR, CanSM, CanNm) dürfen niemals MCAL-APIs (Can.h, Spi.h) direkt aufrufen. Sämtliche Controller- und Transceiver-Kommandos laufen zwingend über logische IDs des CanIf.
  • CAN XL-Integration (R24-11 / R25-11 Spezifika):
    • Die gestrichelten Boxen kennzeichnen normative Erweiterungen für CAN XL (Payloads bis 2048 Byte, Priority ID, Acceptance Field, SDT/VCID-Handling).
    • CanDriver und CanTrcv müssen bei aktivierter CAN XL-Unterstützung SIC-XL-Modi und erweiterte Baudraten-Umschaltungen (Data-Phase bis 20+ Mbit/s) bereitstellen.
    • Das Modul L-SDU Router adressiert die Handhabung größerer Dateneinheiten und virtueller CAN-Instanzen oberhalb des klassischen Frame-Layers.
  • Konfigurationsaspekte (BSW-Generierung):
    • PDU-Mapping: Striktes Mapping zwischen oberen PduIds und unteren CanIds/Mailboxen (CanIfTxPduCfg, CanIfRxPduCfg).
    • Polling vs. Interrupt: Abhängig von der Konfiguration (CanIfTxProcessing, CanIfRxProcessing) müssen die entsprechenden Can_MainFunction_*-Tasks im OS-Schedule konfiguriert werden.
    • Gemischte Topologien: Bei ECUs mit internem MCAL-CAN und externem SPI-CAN-Controller erfordert das CanIf eine heterogene Treiber-Anbindung: ein Controller-Kanal nutzt Can_*-APIs, der andere Treiber-APIs des externen ASIC-Treibers. Die oberen Schichten sehen dennoch eine homogene Sicht auf die physischen Bus-Kanäle.

Specification of CAN Interface AUTOSAR CP R25-11 1 Introduction and functional overview This specification describes the functionality, API and the configuration for the AUTOSAR Basic Software module CAN Interface. As depicted in Figure 1.1 the CAN Interface module is located between the low level CAN device drivers (CAN Driver [1] and Transceiver Driver [2]) and the upper communication service layers (i.e. CAN State Manager [3], CAN Network Management [4], CAN Transport Protocol [5], PDU Router [6]). It represents the interface to the services of the CAN Driver for the upper communication layers. The CAN Interface module provides a unique interface to manage different CAN hardware device types like CAN Controllers and CAN Transceivers used by the defined ECU hardware layout. Thus multiple underlying internal and external CAN Controllers/CAN Transceivers can be controlled by the CAN State Managers module based on a physical CAN channel related view. Figure 1.1: AUTOSAR CAN Layered Architecture The CAN Interface module consists of all CAN hardware independent tasks, which belongs to the CAN communication device drivers of the corresponding ECU. Those functionality is implemented once in the CAN Interface module, so that underlying CAN device drivers only focus on access and control of the corresponding specific CAN hardware device. 12 of 245 Document ID 12: AUTOSAR_CP_SWS_CANInterface
