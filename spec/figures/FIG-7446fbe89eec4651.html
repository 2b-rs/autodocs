1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsdiagramm (State Machine Diagram) mit hierarchischem Verbundzustand (Composite State).
  • Architektur-Kontext: AUTOSAR Classic Platform / Foundation Protocol Specification Time Synchronization over CAN (AUTOSAR_FO_PRS_TimeSyncOverCANProtocol, Release R25-11), Spezifikationsbezug RS_TS_20035.
  • Funktionaler Zweck: Modellierung des deterministischen Empfangs- und Verarbeitungszyklus eines CAN Time Slaves (CanTSyn). Definiert das Protokollverhalten der Two-Step-Zeitsynchronisation (bestehend aus getrennter SYNC- und FUP-Nachricht / Follow-Up) inklusive Rx-Entprellung (Debouncing) und Timeout-Überwachung bei Synchronisationsverlust.

2. Komponenten, Entitäten & Schnittstellen

  • Hauptzustände:
    • TS Init: Initialer BSW-Zustand vor Abschluss der Modulinitialisierung.
    • TS Initialized: Übergeordneter Verbundzustand (Composite State) für den regulären Protokollbetrieb.
  • Subzustände innerhalb von TS Initialized:
    • TS Idle: Ruhezustand; horcht auf eingehende TimeSync-Frames.
    • TS Receive SYNC Msg: Verifikations- und Verarbeitungszustand nach Detektion einer SYNC-PDU.
    • TS Debounce Before FUP Msg: Wartezustand zur Einhaltung der minimalen Rx-Debounce-Zeit vor Annahme der FUP-PDU.
    • TS Wait For FUP Msg: Aktiver Wartezustand auf das Eintreffen der zugehörigen FUP-PDU.
    • TS Build FUP Msg: Dekodierungs- und Fusionszustand (Kombination von SYNC-Ingress-Zeitstempel und FUP-Inhalt).
    • TS Debounce Before SYNC Msg: Blockierender Entprellzustand nach Abschluss oder Abbruch eines Synchronisationsversuchs.
  • Timer, Parameter & Flags:
    • Δt_RxDebounceInterval (auch t_TSDebounceInterval / t_RxDebounceInterval): Konfigurierbares Mindestintervall zwischen der Auswertung konsekutiver Nachrichten zur Bus- und CPU-Entlastung.
    • Δt_FupRxTimeout: Maximal zulässiges Empfangszeitfenster für die zur SYNC gehörende FUP-Nachricht.
    • Δt_SlaveSyncLossTimeout: Überwachungszeitraum für den zyklischen Empfang valider Synchronisationspaare.
    • Synchronization Timeout Flag: Status-Flag zur Signalisierung des Synchronisationsverlusts an übergeordnete Schichten (StbM).
    • SYNC message ingress timestamp: Hochpräziser Erfassungszeitpunkt beim physischen Empfang der SYNC-PDU am CAN-Controller.

3. Dynamisches Verhalten & Sequenzablauf

Normaler Synchronisationspfad (Gutfall):
  1. Initialisierung: Start bei Reset → TS Init. Nach Trigger Initialization complete Wechsel in TS Initialized → Eintritt in Subzustand TS Idle.
  2. SYNC-Empfang: Eintreffen einer SYNC-PDU (SYNC message received) triggert Aktion / Take SYNC message ingress timestamp → Zustandswechsel nach TS Receive SYNC Msg.
  3. SYNC-Prüfung: Nach erfolgreicher Plausibilisierung (SYNC message evalution completed successfully) werden parallel gestartet:
    • / Start Rx Debouncing Interval (Δt_RxDebounceInterval)
    • Start FUP message Rx Timeout (Δt_FupRxTimeout) → Übergang nach TS Debounce Before FUP Msg.
  4. Debounce-Phase vor FUP: Während Δt_RxDebounceInterval aktiv ist, werden alle eintreffenden TimeSync-Nachrichten verworfen (Any Timesync message received / Discard Timesync message). Nach Ablauf (Rx Debouncing Interval has elapsed) → Wechsel nach TS Wait For FUP Msg.
  5. FUP-Empfang: Eintreffen der Follow-Up-Nachricht (FUP message received) innerhalb des Fensters → Übergang nach TS Build FUP Msg.
  6. FUP-Auswertung & Zeitkorrektur: Nach erfolgreicher Verifikation (FUP message evaluation completed successful):
    • / Update Local Time (Berechnung des Offsets und Weitergabe an den StbM)
    • / Start Rx Debouncing Interval (Δt_RxDebounceInterval)
    • / Reset Synchronization Timeout flag
    • / (Re-)start Slave Sync Loss Timeout (Δt_SlaveSyncLossTimeout) → Übergang nach TS Debounce Before SYNC Msg.
  7. Zyklusabschluss: Nach Ablauf von Δt_RxDebounceInterval erfolgt der Rücksprung nach TS Idle.
Fehler-, Timeout- und Verwerfungspfade:
  • Fehlerhafte SYNC-PDU: Schlägt die Validierung in TS Receive SYNC Msg fehl (SYNC message check failed), wird die PDU verworfen, Δt_RxDebounceInterval gestartet und direkt nach TS Debounce Before SYNC Msg verzweigt.
  • Duplizierte/Unerwartete SYNC in FUP-Wartephase: Trifft in TS Wait For FUP Msg eine SYNC-PDU derselben Time Domain ein, wird diese verworfen (Discard message).
  • FUP-Timeout: Verstreicht Δt_FupRxTimeout ohne FUP-Empfang (No FUP message received within Δt_FupRxTimeout), bricht die Transaktion ab → direkter Rücksprung nach TS Idle.
  • Fehlerhafte FUP-PDU: Schlägt die Validierung in TS Build FUP Msg fehl (FUP message check failed), wird die Nachricht verworfen, Δt_RxDebounceInterval gestartet und nach TS Debounce Before SYNC Msg gewechselt.
  • Globaler Synchronisationsverlust (Orthogonaler Event-Pfad): Läuft der Überwacher Δt_SlaveSyncLossTimeout im Zustand TS Initialized ab, wird unmittelbar / Set Synchronization Timeout Flag ausgeführt, um den Ausfall des Time Masters zu deklarieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Hardware- & Treiberanforderungen (MCAL Can / CanIf): Das Protokoll bedingt zwingend eine präzise Ingress-Zeitstempelung beim Eintreffen der SYNC-PDU. Dies erfordert entweder Hardware-Timestamping im CAN-Controller oder die Erfassung des Zeitstempels unmittelbar in der ISR des Treibers, um Jitter durch Task-Scheduling zu minimieren.
  • Konfigurationsparameter (ARXML-Mapping):
    • CanTSynRxDebounceTime / CanTSynRxDebounceInterval: Muss kleiner gewählt werden als das minimale Sendeintervall des Masters, jedoch groß genug, um Bus-Spikes abzufangen.
    • CanTSynRxFollowUpTimeout: Muss die worst-case Arbitrierungs- und Übertragungsverzögerung der FUP-PDU auf dem CAN-Bus abdecken.
    • CanTSynGlobalTimeLossTimeout: Bildet die Basis für Δt_SlaveSyncLossTimeout zur Auslösung von Dem-Events (CANTSYN_E_SYNC_LOSS) bzw. Status-Updates an den StbM.
  • Robuste Frame-Validierung: Entwickler müssen bei SYNC/FUP message check CRC-, Sequence-Counter-, Domain-ID- und Längenprüfungen deterministisch vornehmen. Ein fehlgeschlagener Check darf keine Exception auslösen, sondern muss kontrolliert über den Debounce-Pfad abgewickelt werden, um Denial-of-Service-Zustände durch fehlerhafte Frames zu verhindern.
