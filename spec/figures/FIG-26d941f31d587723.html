1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Layered Architectural Block Diagram (Schichtenmodell / Datenfluss-Architektur) zur Definition der AUTOSAR-PDU- und Signal-Nomenklatur des Classic Platform Communication Stacks (Release R24-11 / R25-11).
  • Funktionaler Kontext:
    • Standardisiert die Begrifflichkeiten und Abstraktionsebenen von Datencontainern (Signal, I-PDU, I-PDU*, N-PDU, L-PDU, L-SDU) über sämtliche Schichten der AUTOSAR Classic Architecture.
    • Erweitert die Kommunikationsarchitektur über CAN, FlexRay und LIN hinaus um Ethernet (inkl. TCP/IP- und IEEE-1722-Streaming), fahrzeugübergreifende Diagnose/Trace-Funktionen, Onboard-Security sowie busindividuelles Zustandsmanagement.
    • Definiert die vertikalen und horizontalen Schnittstellen zwischen RTE, Complex Drivers (CDD), Communication Services, ECU Abstraction Layer (Communication HW Abstraction mit L-SDU Router) und Microcontroller Abstraction Layer (MCAL).

2. Komponenten, Entitäten & Schnittstellen

  • Schichten und Module:
    • RTE (Runtime Environment): Übergabeebene für Signale zur Applikationsschicht (SWCs).
    • Complex Drivers: Direktanbindung für zeitkritische oder spezialisierte Datenströme (Media clock provider / consumer, Streamdata producer / consumer) an IEEE1722Tp, L-SDU Router und Eth Interface.
    • Communication Services:
      • AUTOSAR COM: Signal-Serialisierung, Signal-Gatewaying und I-PDU-Packing.
      • Diagnostic Communication Manager (DCM): UDS/OBD-Diagnosekommunikation via I-PDU.
      • Diagnostic Log and Trace (DLT): Protokollierung und Ablaufverfolgung via I-PDU über den PduR.
      • Secure Onboard Communication (SecOC): Kryptografische Absicherung und Authentifizierung von I-PDUs.
      • IPDU Multiplexer (IpduM): Multiplexing dynamischer Payload-Segmente in I-PDUs.
      • XCP: Mess- und Kalibrierprotokoll auf I-PDU-Ebene am PduR.
      • SOME/IP TP: Segmentierung und Reassemblierung großer SOME/IP-Nachrichten über I-PDUs.
      • PDU Router (PduR): Zentrales Vermittlungs- und Routing-Modul für I-PDUs zwischen oberen Service-Modulen, Transport-Layern und Bus-Interfaces.
      • Transport-Layer-Module:
        • FlexRay Tp: ISO-Transportprotokoll (ISO 10681-2), angebunden via I-PDU* an PduR und N-PDU an FrIf.
        • CAN Tp: ISO-Transportprotokoll (ISO 15765-2), angebunden via I-PDU* an PduR und N-PDU an CanIf.
        • J1939Tp: Nutzfahrzeug-Transportprotokoll (SAE J1939-21), angebunden via I-PDU* an PduR und N-PDU an CanIf.
        • Ethernet Protocol: Protokollstapel (u. a. TCP/UDP/IP) für Ethernet-Kommunikation.
        • IEEE1722Tp: AVB/TSN-Transportprotokoll für Audio/Video-Streaming und Medien-Taktung.
      • Management- und Netzwerk-Koordination:
        • Communication Manager (ComM): Zentrales Kommunikationsmanagement.
        • State Managers: Eth State Manager, FlexRay State Manager, TTCAN State Manager, CAN State Manager, LIN State Manager mit direkten Steuerpfaden zu den jeweiligen Bus-Interfaces.
        • NM-Stack: Generic NM interface (Nm) und NM Coordinator zur clusterübergreifenden Koordination unterhalb des ComM, angebunden an busspezifische NM Module-Instanzen (z. B. CanNm, FrNm, LinNm, UdpNm) und weiter zu den Bus-Interfaces.
    • Communication HW Abstraction:
      • L-SDU Router: Übergreifendes Routing von Service Data Units auf Data Link Layer-Ebene.
      • Bus-Interfaces: Eth Interface (EthIf), FlexRay Interface (FrIf), CAN Interface (CanIf), LIN Interface (LinIf, inkl. LIN TP).
    • Communication Drivers (MCAL):
      • Eth Driver, FlexRay Driver, CAN Driver, LIN Low Level Driver.
  • Datenobjekte & Nomenklatur-Klassifikation:
    • Signals: Anwendungsdaten zwischen RTE und AUTOSAR COM.
    • **I-PDU (Interaction Layer PDU):** Standardisierter Datencontainer im Service-Layer; ausgetauscht zwischen Service-Modulen (COM, DCM, DLT, SecOC, IpduM, XCP, SOME/IP TP), PduR und Transport- bzw. Interface-Modulen.
    • I-PDU*: Kennzeichnung der I-PDU an den Transport-Protokollen (FlexRay Tp, CAN Tp, J1939Tp) zur Abgrenzung gegenüber direkten Interface-I-PDUs bzw. segmentierungsfähigen Nutzlasten.
    • **N-PDU (Network Layer PDU):** Segmentierte Frame-Einheiten mit Protokoll-Kontrollinformationen (PCI) zwischen Transport-Layern (FlexRay Tp, CAN Tp, J1939Tp) und den Bus-Interfaces (FlexRay Interface, CAN Interface).
    • **L-PDU (Data Link Layer PDU):** Hardwarenaher Bus-Frame zwischen Hardware-Abstraktions-Interfaces (Eth Interface, FlexRay Interface, CAN Interface, Lin Interface) und MCAL-Treibern (Eth Driver, FlexRay Driver, CAN Driver, LIN Low Level Driver).
    • L-SDU: Service Data Unit auf Data Link Layer-Ebene, vermittelt durch den L-SDU Router.

3. Dynamisches Verhalten & Sequenzablauf

  • Direktes I-PDU-Routing (Unsegmentierter Pfad):
    1. Signal-Packing & Übergabe: RTE übergibt Signale an AUTOSAR COM. COM erzeugt eine I-PDU und übergibt diese an den PDU Router (PduR).
    2. Security- und Multiplex-Verarbeitung (optional): Bei geschützten oder gemultiplexten Daten leitet PduR die I-PDU an SecOC (Hinzufügen/Verifizieren von Authentifizierungs-Tags) bzw. IPDU Multiplexer weiter, bevor sie an das Zielmodul geroutet wird.
    3. Interface-Routing: PduR routet die unsegmentierte I-PDU direkt an das zuständige Bus-Interface (Eth Interface, FlexRay Interface, CAN Interface oder LIN Interface).
    4. Treiber-Transfer: Das Bus-Interface bildet die I-PDU auf eine L-PDU ab und übergibt sie an den jeweiligen MCAL-Treiber (Eth Driver, FlexRay Driver, CAN Driver, LIN Low Level Driver).
  • Segmentierter Großdatenpfad (TP-Routing):
    1. TP-Initialisierung: DCM, DLT oder COM sendet eine große I-PDU via PduR an den zuständigen Transport Layer (FlexRay Tp, CAN Tp, J1939Tp oder SOME/IP TP / Ethernet Protocol).
    2. Segmentierung & Flusssteuerung: Das TP-Modul fordert Pufferinhalte via PduR an, fügt Protokollinformationen (PCI) hinzu und erzeugt diskrete N-PDUs.
    3. Interface-Übergabe: Die N-PDUs werden an das Bus-Interface (FlexRay Interface bzw. CAN Interface) übergeben und als L-PDUs über den MCAL-Treiber auf den Bus gesendet.
    4. Empfangs- und Reassemblierungssequenz: Die Gegenstelle empfängt L-PDUs, reicht N-PDUs an das TP weiter; nach Reassemblierung wird die fertige I-PDU über den PduR an das Zielmodul signalisiert.
  • Ethernet- und Streaming-Ablauf:
    • Applikationen bzw. Complex Drivers nutzen IEEE1722Tp für getaktete AVB/TSN-Medienströme oder SOME/IP TP für serviceorientierte Kommunikation über den Ethernet Protocol-Stack zum Eth Interface.
    • Der L-SDU Router ermöglicht Routing- und Vermittlungsoperationen auf L-SDU-Ebene innerhalb der Abstraktionsschicht.
  • Zustands- und Netzwerkmanagement-Ablauf:
    • Communication Manager (ComM) koordiniert über die busindividuellen State Manager (Eth State Manager, FlexRay State Manager, TTCAN State Manager, CAN State Manager, LIN State Manager) den Aktivierungszustand der Interfaces.
    • Das Generic NM interface steuert in Abstimmung mit dem NM Coordinator und den busgebundenen NM Module-Instanzen das koordinierte Aufwecken und Schlafenlegen der Netzwerk-Cluster.

4. Normative Relevanz & Entwickler-Hinweise

  • Layer-Isolation und Datentypen:
    • Strikte Kapselung der Payload-Inhalte: Unterhalb von COM, DCM, SecOC und DLT erfolgt die Datenübergabe über PDU-Routing und Bus-Interfaces rein PduId-basiert als Byte-Array (PduInfoType), ohne Kenntnis von Signalspezifikationen.
  • Multi-Bus- und Multi-TP-Architektur:
    • Durch die Koexistenz von CAN Tp und J1939Tp am CAN Interface sowie von IEEE1722Tp, SOME/IP TP und Ethernet Protocol am Ethernet-Pfad müssen PduR- und Interface-Routingtabellen eindeutig nach Ziel-TP und Adressierung (z. B. Broadcast/Peer-to-Peer bei J1939, Multicast bei IEEE 1722) parametriert sein.
  • Pufferkonfiguration und Zero-Copy:
    • Direkte I-PDU-Pfade zwischen PduR und Bus-Interfaces erfordern keine dynamische TP-Pufferverwaltung (typisch zeigerbasierter Zero-Copy-Transfer).
    • TP-Pfade (FlexRay Tp, CAN Tp, J1939Tp, SOME/IP TP) verlangen konfigurierte Sende- und Empfangspuffer (PduR-Bufferpools oder TP-Puffer) mit Unterstützung für CopyTxData / CopyRxData.
  • Sicherheits- und Diagnose-Pipeline:
    • Bei Verwendung von SecOC muss die Latenz- und Pufferallokation für die kryptografische Authentifizierung (MAC-Berechnung und Freshness-Verifikation) in der I-PDU-Routingkette zwischen PduR und Ziel-Bus-Interface berücksichtigt werden.
  • Cluster-Management:
    • Die Entkopplung des Netzwerkmanagements über Generic NM interface und NM Coordinator ermöglicht synchronisierte Schlaf-/Wachzustände über gemischte Bussysteme (CAN, FlexRay, LIN, Ethernet) hinweg, erfordert jedoch eine konsistente Konfiguration der State-Manager-Timeouts und NM-Subsysteme.
