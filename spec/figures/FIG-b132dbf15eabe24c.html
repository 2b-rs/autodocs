1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML 2.0 Sequenzdiagramm (Interaction Diagram).
  • Dokumentkontext: AUTOSAR_SWS_PDURouter (Kapitel 9.3.2 Gateway from CAN to FlexRay, Figure 9.12).
  • Architektonische Einordnung: AUTOSAR Classic Platform (CP), Communication Stack (ComStack). Das Diagramm spezifiziert das Weiterleiten (Gatewaying) einer nachrichtenorientierten I-PDU von einem ereignisgesteuerten Bus (CAN) auf ein zeitgesteuertes Bussystem (FlexRay) unter Verwendung des Pull-Mechanismus (TriggerTransmit) mit und ohne PduR-Zwischenpufferung.

2. Komponenten, Entitäten & Schnittstellen

Akteure / Module («module» Lifelines)
  • CanIf (CAN Interface): Quell-Schnittstellenmodul der unteren Schicht (Lower Layer Source Interface).
  • PduR (PDU Router): Zentrales Routing- und Gateway-Modul; fungiert als Vermittler, verwaltet Gateway-Routen und ggf. Routing-Puffer.
  • FrIf (FlexRay Interface): Ziel-Schnittstellenmodul der unteren Schicht (Lower Layer Target Interface), das zeitgesteuert Sendezeitpunkte im FlexRay-Zyklus steuert.
Schnittstellen & Interaktionen (APIs & Callbacks)
  • PduR_<User:Lo>RxIndication(PduIdType, const PduInfoType*):
    • Synchroner Callback von CanIf an PduR zur Signalisierung empfangener CAN-Nutzdaten.
  • FrIf_Transmit(PduIdType, const PduInfoType*):
    • Synchroner Sendeaufruf von PduR an FrIf (im Diagramm typisiert als FrIf_Transmit(Std_ReturnType, PduIdType, const PduInfoType *)).
  • PduR_<User:Lo>TriggerTransmit(PduIdType, PduInfoType*):
    • Pull-Callback von FrIf an PduR zum Abrufen der aktuellen Sendedaten unmittelbar vor dem konfigurierten FlexRay-Zeitschlitz.
  • PduR_<User:Lo>TxConfirmation(PduIdType, Std_ReturnType):
    • Asynchroner Abschluss-Callback von FrIf an PduR nach erfolgreichem FlexRay-Rahmentransfer.
  • Interne Operationen (copy buffer()):
    • Pufferkopieroperationen im PduR (RAM-Gateway-Puffer) bzw. im FrIf (Controller-/Hardware-Schattenpuffer).
Datenstrukturen
  • PduIdType: Numerischer Bezeichner der Quell- bzw. Ziel-I-PDU.
  • PduInfoType: Struktur bestehend aus SduDataPtr (Zeiger auf Nutzdatenpayload) und SduLength (Länge der SDU).
  • Std_ReturnType: Statuscode (E_OK / E_NOT_OK).

3. Dynamisches Verhalten & Sequenzablauf

Das Sequenzdiagramm unterscheidet über zwei alt-Kombinationsfragmente die Betriebsarten anhand der Guard-Condition ImmediateBufferAccess:

[CanIf] ---> RxIndication ---> [PduR]
                                  |
            +---------------------+---------------------+
            |                                           |
  [NOT ImmediateBufferAccess]                 [ImmediateBufferAccess]
  - PduR puffert lokal (copy buffer)          - PduR ruft FrIf_Transmit() auf
                                              - FrIf puffert sofort (shadow)
            |                                           |
            +---------------------+---------------------+
                                  |
                                [...]
                                  |
[FrIf]  ---> TriggerTransmit -> [PduR]
  - alt [NOT ImmediateBufferAccess]: PduR kopiert Daten in PduInfoType
                                  |
[FrIf]  ---> TxConfirmation --> [PduR]
  1. Empfangsauslösung: CanIf übergibt die I-PDU via PduR_<User:Lo>RxIndication synchron an den PduR.
  2. Verzweigung 1 (Empfangsphase):
    • Pfad [NOT ImmediateBufferAccess] (PduR-Buffering aktiv): PduR führt eine interne Kopieroperation copy buffer() durch, um die Nutzdaten in einer konfigurierten Gateway-Pufferstruktur (Single-Buffer oder FIFO) zwischenzuspeichern, da FrIf die Daten erst zu einem späteren Zeitpunkt abruft.
    • Pfad [ImmediateBufferAccess] (Direkter Hardware-Transfer): PduR ruft unmittelbar FrIf_Transmit(...) auf. FrIf übernimmt die Daten synchron und kopiert sie direkt in Controller- bzw. Mailbox-Puffer. Eine Datenhaltung im PduR entfällt.
  3. PULL-Phase (FlexRay Sendeschlitz erreicht):
    • FrIf ruft zyklusgesteuert PduR_<User:Lo>TriggerTransmit auf.
    • Pfad [NOT ImmediateBufferAccess]: PduR bedient die Anfrage via copy buffer() aus dem zuvor angelegten PduR-Gateway-Puffer und füllt den bereitgestellten PduInfoType*.
  4. Bestätigungsphase:
    • Nach erfolgtem physikalischen Versand auf dem FlexRay-Bus quittiert FrIf via PduR_<User:Lo>TxConfirmation.
    • FrIf aktualisiert/reorganisiert ggf. seine internen Puffer (copy buffer()).

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsabhängigkeit (PduRQueueDepth / FrIfImmediateBufferAccess):
    • Ist FrIfImmediateBufferAccess aktiviert, entfällt der Allokierungsbedarf von PduR-Gateway-Puffern (PduRDefaultValue, PduRQueueDepth). Der Stack spart RAM und CPU-Zyklen (Zero-Copy-Potenzial im PduR).
    • Ist FrIfImmediateBufferAccess deaktiviert (NOT ImmediateBufferAccess), muss im PduR-Routing-Pfad ein Puffer (PduRQueueDepth >= 1) konfiguriert werden, da FlexRay asynchron via TriggerTransmit abruft und der Originalzeiger aus CanIfRxIndication nach Rückkehr des Callbacks ungültig wird.
  • Thread-Safety & Exklusive Bereiche:
    • Bei [NOT ImmediateBufferAccess] erfolgt das Schreiben des Puffers im Kontext der CanIfRxIndication (oft CAN-ISR oder Hochprior-Task), das Lesen im Kontext von FrIf_TriggerTransmit (FlexRay-Timer/Cycle-ISR). Entwickler müssen sicherstellen, dass PduR-Puffer über Schutzzonen (SchM_Enter_PduR / SchM_Exit_PduR) gegen Dateninkonsistenz abgesichert sind.
  • API-Namenskonvention:
    • Die Platzhalter <User:Lo> werden bei der Codegenerierung gemäß Konfiguration auf die konkreten Modulnamen aufgelöst (z. B. PduR_CanIfRxIndication, PduR_FrIfTriggerTransmit, PduR_FrIfTxConfirmation). Im Diagramm ist Triggertransmit mit kleinem t typografisch ungenau; normativ gilt CamelCase PduR_<User:Lo>TriggerTransmit.
