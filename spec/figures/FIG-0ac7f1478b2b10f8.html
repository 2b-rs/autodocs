1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptionelles Architektur- und Mapping-Diagramm (Strukturmodell einer BSW-/MCAL-Partitionierung).
  • Technischer Zweck: Darstellung der internen Struktur und Kopplung eines nicht-partitionierten Basissoftware-Moduls (typischerweise eines MCAL-Treibers) mit vollständiger Bindung an einen dedizierten Prozessorkern (Core x).
  • Funktionale Einordnung: Veranschaulicht im Rahmen des AUTOSAR BSW Distribution Guide die Referenzarchitektur eines Single Core Module als unteilbare Mappable Unit: Sämtliche Ausführungseinheiten (APIs, MainFunctions, ISRs) teilen sich ohne architektonische Barrieren denselben lokalen Adressraum (lokale globale Modulvariablen) und greifen direkt auf physische Registerblöcke der zugeordneten Hardware-Peripherie zu.

2. Komponenten, Entitäten & Schnittstellen

  • *Prozessorkern (Core x):* Hard-/Software-Partition und Ausführungskontext, an den das Modul exklusiv gebunden ist (EcucPartition / OsApplicationCoreRef).
  • BSW Module (Gestrichelte Hüllkurve): Das instanziierte Basissoftware-Modul (z. B. SPI, ADC, CAN oder PWM Driver).
  • Ausführbare Entitäten (Executable Entities):
  • Service API (Kardinalität $1..n$, gestapelt): Synchrone/asynchrone Schnittstellen des Moduls, aufgerufen durch übergeordnete Schichten/Module (Pfeile von oben).
  • Mainfunction (Kardinalität $1$, zyklisch): Periodische Scheduling-Funktion (<Mod>_MainFunction()), getaktet durch das OS bzw. SchM/BswScheduler.
  • ISR (Kardinalität $1..n$, gestapelt, Blitzsymbol): Interrupt Service Routinen (Category 1 oder Category 2), direkt durch Hardware-Ereignisse getriggert (Pfeile von unten).
  • Zentrale Datenstrukturen & Hardwareressourcen:
  • Global Data (Roter Zylinder): Modul-interne Zustands- und Pufferdaten im lokalen RAM von Core x (.bss / .data des Moduls).
  • Microcontroller Registers (0x123, 0x456, blaue Blöcke): Memory-Mapped I/O (MMIO) Kontroll-, Status- und Datenregister.
  • $\mu$C Peripheral Element 1 & 2: Physische Hardware-Einheiten / Peripheriekanäle (z. B. SPI-Kanäle, CAN-Controller-Instanzen), fest verdrahtet mit den MMIO-Registern.
  • Beziehungsstruktur: Sämtliche Entitäten (Service APIs, Mainfunction, ISRs) besitzen bidirektionalen Lese-/Schreibzugriff auf die gemeinsamen Moduldaten sowie direkten Zugriff auf die zugewiesenen Registerblöcke. Es existiert modul-intern keine Trennung nach unterschiedlichen Cores oder getrennten Speichersegmenten.

3. Dynamisches Verhalten & Sequenzablauf

  • Synchroner Pfad (Service API):
  • Caller (z. B. BSW-Stack auf demselben Core) ruft Service-API synchron auf.
  • API modifiziert Global Data und/oder setzt Ansteuerungsbits in den Registern (0x123/0x456), um Hardware-Aktionen auf $\mu$C Peripheral Element auszulösen.
  • Periodischer Pfad (Scheduler / Polling):
  • OS-Dispatcher triggert zyklisch <Mod>_MainFunction().
  • Verarbeitet Puffer in Global Data, führt Status-Polling über Register durch und stößt nachgelagerte Zustandsübergänge an.
  • Asynchroner Hardware-Pfad (Interrupt Handling):
  • Peripherie-Element generiert einen Hardware-Interrupt $\rightarrow$ Core-Interrupt-Controller aktiviert die registrierte ISR.
  • ISR liest/quittiert MMIO-Register, schreibt Empfangs-/Statusdaten in Global Data und verlässt den Interrupt-Kontext bzw. setzt Flags für die Mainfunction.
  • Nebenläufigkeit & Critical Sections:
  • Zeitgleicher Zugriff von Service API, Mainfunction und ISR auf dieselben globalen Daten erfordert SchM-Locks (z. B. SchM_Enter_<Mod>_<Resource>() via OS-Interruptsperren/SuspendOSInterrupts), da alle Entitäten auf demselben Core interagieren.

4. Normative Relevanz & Entwickler-Hinweise

  • Kernbindung & Cross-Core-Zugriff:
  • Ist das Modul an Core x gebunden, müssen Modul-Aufrufe von anderen Kernen (Core y) über BSW-Proxy/Satellite-Konzepte oder SchM/IOC (Inter-OS-Application Communicator) entkoppelt werden. Ein direkter C-Funktionsaufruf aus einem fremden Core-Kontext verletzt die Mapping-Integrität und kann zu Speicher-/MPU-Verletzungen führen.
  • Speicherallokation (Memory Mapping):
  • Globale Variablen (Global Data) müssen über das AUTOSAR Memory Mapping (<MOD>_START_SEC_VAR_CLEARED_ASIL_X_CORE_X) zwingend in den lokalen RAM-Bereich von Core x gelinkt werden, um Non-Cached-Zugriffe und Cache-Kohärenz-Overheads über Crossbar-Busse zu vermeiden.
  • MPU- & Privilegierungs-Ebene:
  • Da MCAL-Module direkt auf MMIO-Register (0x123/0x456) zugreifen, muss der ausführende OS-Task/ISR mit Supervisor-/Privileged-Rechten laufen, oder die MPU-Berechtigungen müssen explizit Lese-/Schreibrechte für diese Peripheriebereiche gewähren.
  • Hardware-Zuweisung:
  • Die Anbindung beider Peripherie-Elemente an dasselbe Modul bedingt, dass diese Hardwarekanäle unteilbar an Core x gebunden sind. Eine dynamische Verteilung einzelner Kanäle desselben Moduls auf unterschiedliche Kerne ist in dieser Modellvariante architektonisch nicht vorgesehen.
