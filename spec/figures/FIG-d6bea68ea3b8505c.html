1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Binäres Wire-/PDU-Layout (32-Bit-Raster, Protokoll-Serialisierungsformat gemäß RFC-/IETF-Darstellung).
  • Technischer Zweck: Spezifikation des bit- und bytegenauen On-Wire-Formats der Configuration Option (Type = 0x01) innerhalb des Options-Bereichs einer SOME/IP-Service-Discovery-Nachricht (SOME/IP-SD).
  • Funktionale Einordnung: Verortet im AUTOSAR Classic Platform BSW-Modul Sd (Service Discovery) der Communication Services oberhalb des Socket Adapters (SoAd). Die Option transportiert dynamische Metadaten, Dienstattribute und Instanzkonfigurationen im DNS-SD-TXT-Format (RFC 6763 / RFC 1035) komplementär zu SOME/IP-SD-Entries (OfferService, FindService, SubscribeEventgroup).

2. Komponenten, Entitäten & Schnittstellen

  • Felddefinitionen (32-Bit-Raster, Network Byte Order / Big-Endian):
    • Length (Bit 0–15, 16 Bit / 2 Byte, uint16): Gibt die Länge der Option abzüglich Header-Präfix an. Reicht vom Feld Reserved bis einschließlich des Terminators des Konfigurationsstrings (Covered by Length (incl. Reserved)).
    • Type (Bit 16–23, 8 Bit / 1 Byte, uint8): Options-Identifikator; normativ fix codiert auf 0x01 für Configuration Options.
    • Reserved (Bit 24–31, 8 Bit / 1 Byte, uint8): Füll-/Reservefeld; Sender müssen dieses Byte zwingend mit 0x00 belegen; Empfänger müssen es ignorieren.
    • Zero-terminated Configuration String (Bit 0ff. ab Byte 4, variable Länge, [len]id=value[len]id=value[0]): Nutzlast im DNS-SD-TXT-Record-Format:
      • Jedes Schlüssel-Wert-Paar besitzt ein vorangestelltes 1-Byte-Längenpräfix [len] (uint8, 1–255), das die exakte Byte-Länge des nachfolgenden Tokens (id=value bzw. boolesches id) definiert.
      • Die gesamte Kette wird durch ein Null-Byte [0] (0x00) abgeschlossen.
  • Beziehungen & Assoziationen:
    • Verknüpfung im SD-Header: Entries referenzieren Options über Indizes (Index 1st options, Index 2nd options) und Anzahlangaben (# of opt 1, # of opt 2).
    • Bindung an das AUTOSAR-Bsw-Modell: Konfiguriert über SdInstanceConfigOption bzw. SdConfigurationOption (ECUC_SD_00057) innerhalb von SdServerServiceInstance / SdClientServiceInstance.
    • Kardinalität: 0..* Configuration Options pro SD-PDU bzw. Service-Entry.

3. Dynamisches Verhalten & Sequenzablauf

  • Sende-Pfad (TX, SWS_Sd_00204, SWS_Sd_00292):
    1. Trigger durch Zustandsübergang im Sd-Zustandsautomaten (z. B. Eintritt in Initial Wait, Repetition Phase oder Main Phase via Sd_MainFunction()).
    2. BSW-Modul Sd serialisiert die konfigurierten Key-Value-Paare (ECUC_SD_00057) in DNS-SD-Syntax: [len1]key1=val1[len2]key2=val2[0x00].
    3. Berechnung des Längenfeldes: $\text{Length} = 1\ (\text{Reserved}) + \sum (\text{len}_i + 1) + 1\ (\text{Nullterminator})$.
    4. Montage der SD-Gesamt-PDU und Übergabe an den Socket-Adapter via SoAd_IfTransmit().
  • Empfangs-Pfad & Validierung (RX, SWS_Sd_00476):
    1. Eintreffen der SD-PDU via Sd_RxIndication().
    2. Plausibilisierung: Überprüfung, ob Length ≥ 2 Byte (mindestens 1 Byte Reserved + 1 Byte Nullterminator) und innerhalb der verbleibenden PDU-Grenzen liegt.
    3. Iterativer Parser liest Längenbyte [len], extrahiert id=value und terminiert bei Antreffen von 0x00.
    4. Fehlertoleranz/Ignorier-Semantik (SWS_Sd_00476): Nicht interpretierbare oder unbekannte Attribute/Keys (id) müssen stillschweigend verworfen werden; sie führen nicht zum Abbruch des Service-Matchings.
    5. Bei strukturell korrupten Längenfeldern (Länge überschreitet SD-PDU-Ende): Meldung an Det (SD_E_MALFORMED_MESSAGE), Verwerfen der Option bzw. der gesamten SD-PDU.

4. Normative Relevanz & Entwickler-Hinweise

  • Längenberechnungs-Falle: Das Feld Length deckt nicht sich selbst (2 Byte) und nicht das Feld Type (1 Byte) ab, schließt aber das Feld Reserved (1 Byte) explizit ein: $$\text{Field\_Value}(\text{Length}) = \text{Total\_Option\_Bytes} - 3 = 1 + \text{ByteLength}(\text{String}) + 1$$ Eine fehlerhafte Längenberechnung (z. B. Weglassen des Reserved-Bytes) führt zur Fehlinterpretation der nachfolgenden Options im SD-Array.
  • DNS-SD-Framing-Grenzen: Jedes einzelne id=value-Token ist durch das 1-Byte-Längenpräfix auf maximal 255 Bytes beschränkt. Der Gesamtstring muss zwingend mit 0x00 terminieren.
  • PDU-Größe & MTU (UDP): Da SOME/IP-SD-Nachrichten typischerweise unfragmentiert über UDP gesendet werden (kein SOME/IP-TP für SD-Pakete), müssen Entwickler bei der ARXML-Konfiguration von String-Attributen die Layer-3/Layer-4-MTU (typisch ≤ 1400–1500 Byte) beachten, um IP-Fragmentierung im Ethernet-Controller zu vermeiden.
  • Konfigurationsverankerung: Entwickler binden statische Konfigurationsparameter über ECUC_SD_00057 an die jeweilige Service-Instanz, um Kompatibilitätsversionen, Features oder dynamische Endpunkt-Parameter bereitzustellen.
