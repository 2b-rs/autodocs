1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Feature-Diagramm (FODA-basierter Feature-Baum / Variabilitäts- und Dekompositionsmodell).
  • Architektur-Kontext: AUTOSAR Foundation (AUTOSAR_FO_TR_Features, R24-11). Das Diagramm definiert auf höchster Abstraktionsebene die funktionale Gliederung und Variabilität von Sicherheitsmechanismen bezüglich Speicherverwaltung und Datenhaltung plattformübergreifend (Classic Platform & Adaptive Platform).
  • Funktionaler Zweck: Strukturierung des übergeordneten Sicherheitskonzepts für Speicherintegrität (Safe_Memory, FO_TR_FEAT_00052) in flüchtige Laufzeit-Speicherisolation (Memory_Protection) und integre nichtflüchtige Speicherung (Safe_Storage).

2. Komponenten, Entitäten & Schnittstellen

  • Wurzel-Feature (Root Feature):
    • FO_TR_FEAT_00052 (Safe_Memory): Abstraktes Eltern-Feature zur Gewährleistung von Speicherintegrität, Zugriffsschutz und Datenpersistenz im Kontext funktionaler Sicherheit (ISO 26262).
  • Kind-Features (Sub-Features):
    • FO_TR_FEAT_00053 (Memory_Protection): Mechanismen zur räumlichen Trennung und Durchsetzung von Zugriffsberechtigungen auf flüchtigen Arbeitsspeicher (RAM) während der Programmausführung.
    • FO_TR_FEAT_00054 (Safe_Storage): Mechanismen zur fehlertoleranten, authentifizierten und redundanten Speicherung von Daten in nichtflüchtigen Speichern (NVM, Flash, EEPROM).
  • Kanten- und Beziehungsemantik:
    • Dekompositionsbeziehung (Parent-Child-Hierarchie).
    • Die Kanten zu beiden Kind-Features enden an den Sub-Features mit einem unbefüllten Kreis (Hohlkreis). Dies kennzeichnet in der FODA-Notation optionale Features (Optional Sub-Features): Ein Systemkontext bzw. Plattformprofil, das FO_TR_FEAT_00052 deklariert, kann FO_TR_FEAT_00053, FO_TR_FEAT_00054 oder beide selektieren.

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Feature-Modell bildet das Diagramm keinen direkten Laufzeit-Kontrollfluss ab. Die abgebildeten Domänen bedingen jedoch folgende deterministische Verhaltensmuster zur Laufzeit:

  • Laufzeitpfad FO_TR_FEAT_00053 (Memory_Protection):
    • Trigger: Unautorisierter Lese-, Schreib- oder Ausführungszugriff einer Software-Entität außerhalb ihres zugewiesenen Adressbereichs.
    • Verhalten: Hardware-Trap via MPU/MMU → Exception-Vektor des AUTOSAR OS → Auslösen der ProtectionHook() → Konfigurierte Eskalation (z. B. Terminierung der OS-Application, Task-Abbruch, Core-Reset) → Fehlermeldung an das BSW-Fehlermanagement (Dem/Det).
  • Laufzeitpfad FO_TR_FEAT_00054 (Safe_Storage):
    • Trigger: Asynchroner/synchroner Read/Write-Request persistenter Datenblöcke.
    • Verhalten: Berechnung und Verifikation von Prüfsummen (CRC16/CRC32, kryptografische Hashes) → Bei Datenkorruption: Umschalten auf redundanten Backup-Block / Default-Werte → Rückmeldung an aufrufende SW-C via Status-Flags bzw. Diagnose-Event-Meldung an das Dem.

4. Normative Relevanz & Entwickler-Hinweise

  • Relevanz für funktionale Sicherheit (ISO 26262):
    • Zentrale Basis zur Erreichung von Freedom from Interference (FFI) zwischen Partitionen unterschiedlicher ASIL-Einstufungen (ASIL QM bis ASIL D).
  • Implementierung Classic Platform (CP):
    • Memory Protection: Erfordert Konfiguration des AUTOSAR OS im Scalability Class 3 (SC3) oder Scalability Class 4 (SC4). Aufteilung in Trusted und Non-Trusted OS-Applications, Festlegung dedizierter Memory Sections (OsMemoryMappingCode, OsMemoryMappingData) und Bindung an MPU-Regionen im MCU-Treiber.
    • Safe Storage: Realisierung über den Memory Stack (NvM, Fee/Ea, Fls/Eep). Konfiguration redundanter NVRAM-Blöcke (NVM_BLOCK_REDUNDANT), Aktivierung zyklischer/read-time CRC-Prüfungen (NvMBlockUseCrc) sowie optional kryptografischer Signaturen (Csm).
  • Implementierung Adaptive Platform (AP):
    • Memory Protection: Nutzung der virtuellen Speicherverwaltung (MMU) und Prozessisolation durch das POSIX-konforme Betriebssystem (getrennte Adressräume für Adaptive Applications).
    • Safe Storage: Realisierung über den Functional Cluster ara::per (Persistency) mit Redundanzmechanismen, Integritätsprüfungen und Safe-Storage-Policies auf Dateisystem- bzw. Key-Value-Storage-Ebene.
  • Integrations-Restriktion:
    • Werden Sub-Features in einem sicherheitskritischen Kontext (ASIL-Allokation) abgewählt, muss im Safety Case nachgewiesen werden, dass entweder keine Koexistenz gemischter Kritikalitäten vorliegt oder die Absicherung vollständig über externe Hardware-Mechanismen erfolgt.
