Figure 7.14: Task states and transitions for Deferrable Server Tasks

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsdiagramm (State Machine Diagram) zur Spezifikation des Task-Lebenszyklus und der Scheduler-Zustandsübergänge im AUTOSAR Classic OS.
  • Technischer Zweck & Einordnung: Spezifikation des erweiterten Task-Zustandsmodells für Deferrable Server Tasks gemäß AUTOSAR OS (Release R25-11). Ein Deferrable Server dient dem deterministischen Scheduling aperiodischer oder sporadischer Lasten (Server-Tasks) unter Erhalt harter Echtzeitgarantien für periodische Tasks. Anstelle einer harten Fehlerreaktion (Aufruf des ProtectionHook mit PRO_TERMINATETASKISR bei OsTaskExecutionBudget-Überschreitung) wird der Task bei Budgeterschöpfung kontrolliert deschedult und in den Zustand BUDGET_EXHAUSTED überführt, bis sein Kontingent zyklisch nachgeladen wird.

2. Komponenten, Entitäten & Schnittstellen

  • Zustands-Entitäten (Task Control Block States):
  • SUSPENDED: Ruhezustand; Task ist nicht für die Ausführung eingeplant und belegt keine Scheduler-Slots.
  • READY: Ausführungsbereit; Task befindet sich in der Ready-Queue des Schedulers entsprechend seiner statischen Priorität.
  • RUNNING: CPU zugeteilt; Task instruiert die Ausführung. Das aktive Kontingent (Current Task budget) wird kontinuierlich dekrementiert.
  • WAITING: Blockiert auf ein OS-Event (WaitEvent(), nur für Extended Tasks).
  • BUDGET_EXHAUSTED: Exklusiver Zustand für Deferrable Server. Task ist lauffähig, darf jedoch wegen aufgebrauchten Ausführungsbudgets ($\le 0$) nicht durch den Scheduler disponiert werden.
  • OS-Zeit- & Budget-Entitäten (Ecuc-Parameter):
  • OsTaskExecutionBudget: Konfigurierte maximale CPU-Nettoausführungszeit pro Budgetzyklus.
  • OsTaskTimeFrame: Konfiguriertes Zeitfenster / Mindestabstand (Replenishment-Periode) zur Begrenzung der Aktivierungs- bzw. Ausführungsrate.
  • Current Task budget: Dynamische Zählervariable im Task-Deskriptor zur Verfolgung des Restkontingents.
  • Strukturelle Beziehungen:
  • Erweiterung des klassischen 4-Zustände-OSEK/VDX-Modells um den fünften Zustand BUDGET_EXHAUSTED.
  • Vollständige Kompatibilität zu Basic Tasks (Zustände SUSPENDED, READY, RUNNING, BUDGET_EXHAUSTED) und Extended Tasks (inklusive WAITING).

3. Dynamisches Verhalten & Sequenzablauf

| Transition | Ausgangszustand | Zielzustand | Trigger / Bedingung | OS-Aktion & Timer-Handling |

| :--- | :--- | :--- | :--- | :--- |

| Activate | SUSPENDED | READY | Task-Aktivierung (ActivateTask(), Alarm, Schedule Table) | OsTaskTimeFrame wird gestartet; Current Task budget bleibt unverändert erhalten (is kept). |

| Start | READY | RUNNING | Scheduler-Dispatching (höchste Priorität in Ready-Queue) | Hardware-Überwachungstimer für OsTaskExecutionBudget wird gestartet/fortgesetzt. |

| Preempt | RUNNING | READY | Verdrängung durch höherprioren Task / ISR | OsTaskExecutionBudget-Timer wird gestoppt; verbleibendes Current Task budget wird gesichert (is kept). |

| Terminate | RUNNING | SUSPENDED | TerminateTask() oder ChainTask() | OsTaskExecutionBudget-Timer wird gestoppt; Restbudget bleibt für Folgeaktivierungen erhalten (is kept). |

| Wait | RUNNING | WAITING | Aufruf von WaitEvent() | OsTaskExecutionBudget-Timer wird gestoppt; Restbudget wird gesichert (is kept). |

| Release | WAITING | READY | Eintreffen des erwarteten Events (SetEvent()) | OsTaskTimeFrame wird gestartet; Restbudget bleibt erhalten (is kept). |

| Budget Exhaust | RUNNING | BUDGET_EXHAUSTED | Current Task budget exhausted (Wert $\le 0$) | CPU-Entzug durch OS-Timer-Interrupt; kein Eintritt in den ProtectionHook; Task wird aus der Ready-Queue entfernt. |

| Budget Replenish| BUDGET_EXHAUSTED | READY | Budget-Wiederauffüllung (BudgetReplenish) | Bedingung: Current Task budget nach Auffüllung $> 0$; Task wird sofort wieder in die Ready-Queue eingereiht. |

  • Asynchroner Replenishment-Pfad: Der Übergang von BUDGET_EXHAUSTED nach READY erfolgt asynchron über das Ablaufen der Replenishment-Periode (z. B. getrieben durch OS-Systemtimer/Counter).

4. Normative Relevanz & Entwickler-Hinweise

  • SWS-Anforderungsabdeckung:
  • SWS_Os_00871 / SWS_Os_00874: Definition und Durchsetzung des Zustands BUDGET_EXHAUSTED, in welchem der Task von der CPU-Zuteilung ausgeschlossen ist.
  • SWS_Os_00872: Zwingender Zustandsübergang von RUNNING nach BUDGET_EXHAUSTED, sobald das verbleibende Budget $\le 0$ erreicht.
  • SWS_Os_00877 / SWS_Os_00879: Spezifikation des BudgetReplenish-Mechanismus; sobald das Budget $> 0$ ist, erzwingt das OS den Übergang nach READY.
  • SWS_Os_00880: Normativer Erhalt des Restbudgets (Current Task budget is kept) über Kontextwechsel hinweg (Preemption, Wait, Terminate, Activation, Release).
  • SWS_Os_00881: Verhaltensvorschriften zum Starten/Stoppen der Hardware-Timer für OsTaskExecutionBudget und OsTaskTimeFrame.
  • Konfiguration & Stack-Implementierung:
  • Das OS muss für Deferrable Server Tasks so konfiguriert sein, dass Budgetüberschreitungen nicht als Timing Protection Fault gewertet werden, sondern den BUDGET_EXHAUSTED-Pfad aktivieren.
  • Der OS-Stack benötigt präzise Hardware-Timer-Unterstützung (z. B. Core-lokale Downcounter mit Reload-Registern), um Kontextwechsel-Overheads exakt aus dem Current Task budget herauszurechnen.
  • Applikations- & RTE-Vertrag:
  • Ressourcen-Sperren: Entwickler dürfen innerhalb von Deferrable Server Tasks Standard-OS-Ressourcen (GetResource() / ReleaseResource()) nicht über Budgetgrenzen hinweg halten. Ein Erschöpfen des Budgets bei gehaltener Ressource führt gemäß AUTOSAR-Sicherheitsarchitektur zu Deadlock-Gefahren bzw. Prioritätsinversionen für das Gesamtsystem.
  • Transparenz: Für SW-Cs bzw. Runnables im RTE-Kontext ist die Drosselung transparent; es existieren keine Fehlerrückgabewerte auf API-Ebene, der Task erfährt lediglich eine Latenzerhöhung bis zum nächsten BudgetReplenish.
