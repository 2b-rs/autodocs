1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration Parameter Definition Metamodell (UML-Klassendiagramm auf M2-Ebene gemäß AUTOSAR_CP_SWS_DiagnosticCommunicationManager, Release R23-11).
  • Funktionaler Kontext: Das Diagramm spezifiziert die statische Parametrierung des DCM DSL (Diagnostic Session Layer). Es definiert das Metamodell für Diagnoseprotokolle (DcmDslProtocol), deren Instanziierung (DcmDslProtocolRow) und die Verknüpfung mit physikalischen Kommunikationsressourcen (Puffer, Verbindungen), der Diensteverarbeitung im DSD (DcmDsdServiceTable) sowie der Fehlerbehandlung im Dem (DemClient).

2. Komponenten, Entitäten & Schnittstellen

Container- und Strukturhierarchie
  • Dcm (EcucModuleDef, [0..1]): Wurzelknoten der BSW-Modulkonfiguration des Diagnostic Communication Managers.
  • DcmConfigSet (EcucParamConfContainerDef): Multi-Konfigurationssatz-Container (+container).
  • DcmDsl (EcucParamConfContainerDef, [1..1]): DSL-Sub-Container (+subContainer), kapselt globale Kommunikations- und Pufferparameter.
  • DcmDslBuffer (EcucParamConfContainerDef, [1..256]): Zentraler Diagnosepuffer-Pool für Rx- und Tx-Payloads.
  • DcmDslProtocol (EcucParamConfContainerDef, [1..1]): Protokoll-Kopfcontainer innerhalb des DSL.
  • **DcmDslProtocolRow (EcucParamConfContainerDef, [1..*]):** Instanz eines konkreten Diagnoseprotokolls (z. B. UDS auf CAN, DoIP, OBD).
Parameter der Protokollinstanz (DcmDslProtocolRow)
  • DcmDslProtocolType (EcucEnumerationParamDef, [1..1]): Protokolltyp; symbolicNameValue = true zur Erzeugung typsicherer Header-Makros (z. B. DCM_UDS_ON_CAN).
  • DcmDslProtocolPriority (EcucIntegerParamDef, [1..1], Min: 0, Max: 255): Preemption-Priorität bei konkurrierenden Requests auf unterschiedlichen Protokollen/Verbindungen.
  • DcmDslProtocolRowUsed (EcucBooleanParamDef, [1..1], Default: true): Aktivierungsschalter für das Protokoll (Post-Build- / Variant-Handling).
  • DcmDspProtocolEcuAddr (EcucIntegerParamDef, [0..1], Min: 0, Max: 65535): Physikalische ECU-Knotenadresse (relevant für adressbasierte Routings wie DoIP/OBD).
  • DcmDslProtocolMaximumResponseSize (EcucIntegerParamDef, [0..1], Min: 1, Max: 65535, Default: 4095): Begrenzung der maximalen Antwortlänge in Bytes.
  • DcmTimStrP2ServerAdjust (EcucFloatParamDef, [1..1], Min: 0.0, Max: 1.0 s): P2-Offset zur Vorab-Kompensation interner Latenzen.
  • DcmTimStrP2StarServerAdjust (EcucFloatParamDef, [1..1], Min: 0.0, Max: 5.0 s): P2*-Offset für NRC 0x78 (Response Pending).
  • DcmSendRespPendOnRestart (EcucBooleanParamDef, [1..1], Default: true): Erzwingt das Senden von NRC 0x78 bei Protokollübernahme bzw. Session-Neustart.
  • DcmDslProtocolTransType (EcucEnumerationParamDef, [0..1]): Parallelitäts-Modus:
    • TYPE1: Rein sequentielles Request/Response-Verhalten (Standard).
    • TYPE2: Parallele Anfragen/Responses erlaubt (z. B. für Response On Event / periodische Nachrichten).
Subcontainer und Referenzen (DcmDslProtocolRow)
  • **DcmDslConnection (EcucChoiceContainerDef, [1..*], +subContainer):** Konfiguriert die logischen Verbindungen inkl. Zuordnung der Transport-PDUs (RxPduId, TxPduId).
  • DcmDslProtocolRxBufferRef (EcucReferenceDef, [1..1] → DcmDslBuffer [1..256]): Bindung an den zugewiesenen Empfangspuffer.
  • DcmDslProtocolTxBufferRef (EcucReferenceDef, [1..1] → DcmDslBuffer [1..256]): Bindung an den zugewiesenen Sendepuffer.
  • DcmDslProtocolSIDTable (EcucReferenceDef, [1..1] → DcmDsdServiceTable [1..256]): Verknüpfung zur autorisierten SID-Tabelle im DSD; adressiert via DcmDsdSidTabId (EcucIntegerParamDef, [1..1], Min: 0, Max: 255).
  • DcmDemClientRef (EcucReferenceDef, [1..1] → DemClient [1..255]): Multi-Client-Anbindung an die zuständige Dem-Instanz für Fehlerspeicherzugriffe.

3. Dynamisches Verhalten & Sequenzablauf

[PduR]               [DcmDslConnection]        [DcmDslProtocolRow]             [DSD / DSP]
  |                          |                          |                          |
  |--- StartOfReception ---->|                          |                          |
  |    (RxPduId)             |-- Allokiere Rx-Buffer -->|                          |
  |                          |   (DcmDslProtocolRxBufferRef)                       |
  |<-- BUFREQ_OK ------------|                          |                          |
  |--- CopyRxData ---------->|-- Schreibe Payload ----->|                          |
  |--- TpRxIndication ------>|                          |                          |
  |                          |-- Request Complete ----->|                          |
  |                          |                          |-- SID Table Lookup ----->|
  |                          |                          |   (DcmDsdServiceTable)   |
  |                          |                          |-- Start P2 Timer ------->|
  |                          |                          |   (P2 - P2ServerAdjust)  |
  |                          |                          |                          |
  |                          |                          |   [P2-Timeout droht]     |
  |                          |                          |-- Trigger NRC 0x78 ----->|
  |                          |                          |   (TxBufferRef)          |
  |                          |                          |-- Start P2* Timer ------>|
  |                          |                          |   (P2* - P2*ServerAdjust)|
  1. PDU-Annahme & Puffer-Allokation: Eingehende Diagnosenachricht triggert Dcm_StartOfReception() über die referenzierte DcmDslConnection. Der DSL bindet den über DcmDslProtocolRxBufferRef definierten Puffer.
  2. Priorisierung & Preemption: Trifft während eines aktiven Ablaufs ein Request auf einem anderen Protokoll ein, entscheidet DcmDslProtocolPriority. Niedrigere Prioritäten werden abgelehnt (NRC 0x21 BusyRepeatRequest) oder abgebrochen; höhere Prioritäten unterbrechen das laufende Protokoll.
  3. **Timing-Berechnung (P2 / P2^* Guarding):**
    • Interner Timeout-Trigger: $T_{\text{trigger}} = P2_{\text{ServerMax}} - \text{DcmTimStrP2ServerAdjust}$.
    • Kann die Applikation/DSP die Antwort nicht vor T_trigger bereitstellen, sendet der DSL autonom NRC 0x78 (Response Pending) über den DcmDslProtocolTxBufferRef und reloaded mit P2^*_ServerMax - DcmTimStrP2StarServerAdjust.
  4. Dienst-Dispatching: DSD prüft die empfangene SID anhand der über DcmDslProtocolSIDTable gebundenen DcmDsdServiceTable.

4. Normative Relevanz & Entwickler-Hinweise

  • Dimensionierung von DcmDslBuffer: Die Puffergröße muss zwingend ≥ DcmDslProtocolMaximumResponseSize ausgelegt werden, um Pufferüberläufe und Buffer-Truncation bei ReadDataByIdentifier oder RoutineControl-Diensten zu verhindern.
  • Timing-Offset-Parametrierung: DcmTimStrP2ServerAdjust muss die Task-Zykluszeit von Dcm_MainFunction(), die Verarbeitungszeit im PduR/Interface-Treiber sowie Bus-Arbitrierungszeiten abdecken. Ist der Wert zu klein gewählt, verstreicht P2_ServerMax auf Tester-Seite (Timeout); ist er zu groß, werden unnötige NRC 0x78-Meldungen auf den Bus gesendet.
  • TransType-Restriktionen: TYPE1 erzwingt streng sequentielles Verhalten. Sollen Services parallel betrieben werden (z. B. periodische Datentransfers gem. UDS 0x2A oder Response On Event 0x86 parallel zu Standard-Diagnose), muss TYPE2 gewählt und getrennte Tx-Puffer konfiguriert werden.
  • Multi-Client-DEM-Routing: Über DcmDemClientRef wird das Protokoll eindeutig einer DemClient-Instanz zugeordnet. Dies ist zwingend erforderlich in Multi-Core- oder partitionierten Steuergeräten, um DTC-Operationen thread- und partitionskonform an den zugehörigen Dem-Core zu dispatchen.
