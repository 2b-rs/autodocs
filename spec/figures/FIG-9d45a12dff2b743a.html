1. Diagrammtyp & Architektur-Kontext

Konzeptionelles Daten- und Mapping-Diagramm im Kontext der Signal-Service-Translation (Signal-to-Service-Mapping) nach AUTOSAR Adaptive Platform / TPS Manifest Specification. Das Diagramm illustriert das Zusammenspiel von signalbasierten Kommunikationsstrukturen (Classic Platform bzw. CAN/LIN/FlexRay-Frames) mit serviceorientierten Ereignissen (event xyz) unter Verwendung von Update-Bits (updateBit) und optionalen Event-Feldern.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm unterteilt sich in zwei logische Bereiche (Spezifikation/Mapping links und Laufzeitbeispiel/Wertebelegung rechts):

  • Signal-Seite (grün hinterlegt):
    • Signalgruppe x1 mit vier Elementen/Signalen: a : uint8, b : uint16, c : boolean, d : sint8.
    • Einzelsignale: signal y : uint8, signal z : sint16.
    • Zugeordnete Update-Bits: updateBit_x1, updateBit_y, updateBit_z.
  • Service-/Event-Seite (grau-blau hinterlegt):
    • Service-Ereignis event xyz.
    • Feld bzw. Elementstruktur x1 [optional] mit identischen Sub-Elementen (a : uint8, b : uint16, c : boolean, d : sint8).
    • Optionale Felder: y [optional] : uint8, z [optional] : sint16.
  • Mapping-Beziehungen (gerichtete Pfeile):
    • Direkte Zuordnung der Signale aus Signalgruppe x1 auf die Sub-Elemente von x1 [optional].
    • Abbildung von signal y auf y [optional].
    • Abbildung von signal z auf z [optional].
  • Laufzeit-Instanz:
    • Belegte Signalgruppe x1 (a: 3, b: 45, c: true, d: -23) mit updateBit_x1 = 0.
    • Belegtes Signal signal y: 12 mit updateBit_y = 1.
    • Belegtes Signal signal z: 65 mit updateBit_z = 0.
    • Resultierendes serialisiertes Event event xyz { y : 12 }.

3. Dynamisches Verhalten & Sequenzablauf

  1. Zustandsauswertung der Update-Bits: Bei der Konvertierung von eingehenden Signalen in ein Service-Event prüft der Übersetzungsmechanismus (Signal-to-Service-Gateway/Translator) den Status der Update-Bits.
  2. Filterung / Relevanzprüfung: Ein Signal bzw. eine Signalgruppe gilt nur dann als aktualisiert und serialisierungsrelevant, wenn das zugehörige Update-Bit gesetzt ist (1). Im dargestellten Beispielfall ist updateBit_y = 1, während updateBit_x1 = 0 und updateBit_z = 0 sind.
  3. Serialisierung des Events: Da nur y aktualisiert wurde, werden die optionalen Felder x1 und z für die Übertragung im Event verworfen bzw. nicht serialisiert. Das Event event xyz enthält zur Laufzeit ausschließlich das aktualisierte Feld { y : 12 }.

4. Normative Relevanz & Entwickler-Hinweise

  • Modellierungsanforderung: Die Abbildung von Signalen/Signalgruppen auf optionale Event-Felder ([optional]) ermöglicht eine bandbreitenschonende Serialisierung (z. B. SOME/IP mit TLV-Codierung für optionale Member).
  • Update-Bit-Semantik: Update-Bits steuern direkt die Präsenz (presence) optionaler Datenfelder im SOME/IP- bzw. Service-Payload.
  • Konsistenz: Für aggregierte Datentypen (Signalgruppen) existiert ein gemeinsames Update-Bit (updateBit_x1), welches die Konsistenz und gleichzeitige Übernahme aller Gruppen-Member steuert.
  • Implementierungshinweis: Bei Empfang einer signalbasierten PDU ohne gesetztes Update-Bit darf der Serializer das entsprechende optionale Element im Ziel-Event nicht übertragen, selbst wenn gültige Nutzdaten im Signalpuffer anliegen.
