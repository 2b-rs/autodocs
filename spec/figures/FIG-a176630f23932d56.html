1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm zur Definition des AUTOSAR BSW ECU-Konfigurationsmetamodells (EcucParamConfContainerDef / EcucParameterDef).
  • Funktionaler Kontext: Konfiguration des Diagnostic Service Processing (DSP) Submoduls innerhalb des Diagnostic Communication Manager (DCM).
  • Technischer Zweck: Parametrierung des UDS-Dienstes 0x31 (RoutineControl, ISO 14229-1). Das Metamodell bildet die Konfigurationsstruktur ab, über die Routinen (RIDs) registriert, autorisiert und an Applikations-SWCs (via RTE) bzw. BSW-Module angebunden werden.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm modelliert Container- und Parameter-Definitionen via Kompositionsbeziehungen (gefüllte Rauten):

  • DcmDsp (EcucParamConfContainerDef, [0..1]):
    • Wurzelcontainer für alle DSP-spezifischen Konfigurationen im DCM.
    • Hält via +subContainer die Routinen-Definitionen.
  • **DcmDspRoutine (EcucParamConfContainerDef, [0..*], SWS-ID: ECUC_Dcm_00640):**
    • Repräsentiert eine spezifische Routine Identifier (RID) Instanz.
    • Parameter:
      • DcmDspRoutineIdentifier (EcucIntegerParamDef, [1..1], Min: 0, Max: 65535): 16-Bit Routine-Identifier (RID gemäß UDS/ISO 14229).
      • DcmDspRoutineUsePort (EcucBooleanParamDef, [1..1]):
        • TRUE: Anbindung der Routine erfolgt über RTE-Ports (ClientServerInterface / Rte_Call).
        • FALSE: Direkte C-Funktionsaufrufe / Callouts ohne RTE-Port-Overhead.
      • DcmDspRoutineFncSignature (EcucEnumerationParamDef, [1..1], Default: ROUTINE_FNC_NORMAL):
        • Konfiguriert die zu verwendende C-Funktionssignatur für den Aufruf der Routine.
        • Literale (+literal):
          • ROUTINE_FNC_NORMAL (EcucEnumerationLiteralDef): Standard-Funktionssignatur.
          • ROUTINE_FNC_PROXY (EcucEnumerationLiteralDef): Proxy-Funktionssignatur zur Weiterleitung/Entkopplung.
      • DcmDspRoutineUsed (EcucBooleanParamDef, [1..1]): Aktiviert oder deaktiviert die RID zur Generierungszeit.
      • DcmDspRoutineInfoByte (EcucIntegerParamDef, [0..1], Min: 0, Max: 255): Optionales UDS routineInfo-Byte für Status-/Ergebnis-Payloads.
    • Sub-Container (korrespondierend zu Subfunktionen 0x01–0x03):
      • DcmDspStartRoutine (EcucParamConfContainerDef, [0..1]): Konfiguriert Subfunktion 0x01 (startRoutine), inklusive Eingangs-/Ausgangsparameter.
      • DcmDspStopRoutine (EcucParamConfContainerDef, [0..1]): Konfiguriert Subfunktion 0x02 (stopRoutine).
      • DcmDspRequestRoutineResults (EcucParamConfContainerDef, [0..1]): Konfiguriert Subfunktion 0x03 (requestRoutineResults).

3. Dynamisches Verhalten & Sequenzablauf

Obwohl das Diagramm statische Konfigurationsstrukturen zeigt, determiniert es die Laufzeitpfade des DCM:

  1. UDS Request Dispatching:
    • Diagnose-Tester sendet Request 0x31 <SubFunction> <RID> [<routineControlOptionRecord>].
    • DCM prüft RID gegen die via DcmDspRoutineIdentifier instanziierten Container. Existiert der RID nicht oder ist DcmDspRoutineUsed == FALSE, erfolgt NRC 0x31 (Request Out Of Range).
  2. Subfunktions-Validierung:
    • Ist die angeforderte Subfunktion (0x01, 0x02, 0x03) im jeweiligen DcmDspRoutine nicht als Sub-Container (DcmDspStartRoutine, DcmDspStopRoutine, DcmDspRequestRoutineResults) konfiguriert, antwortet der DCM mit NRC 0x12 (Sub-Function Not Supported).
  3. Ausführungspfad (synchron/asynchron):
    • DcmDspRoutineUsePort == TRUE: DCM ruft über den RTE-Port das generierte Interface RoutineServices_<RoutineName> (Methoden: Start, Stop, RequestResults) auf.
    • DcmDspRoutineUsePort == FALSE: DCM ruft statisch konfigurierte C-APIs auf (z. B. Dcm_StartRoutine_<RID>()).
    • Signalisiert der Callout/Port DCM_E_PENDING, schaltet der DCM in asynchronen Zustand und sendet bei Bedarf NRC 0x78 (Response Pending).
  4. Fehlerbehandlung:
    • Falsche Parameterlängen im Request lösen NRC 0x13 (Incorrect Message Length Or Invalid Format) aus.
    • Nicht erfüllte Vorbedingungen (z. B. Session/Security) werden vor Erreichen des DSP-Handlers im DSD (Diagnostic Service Dispatcher) abgewiesen.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Generierung vs. BSW-Kopplung:
    • Wird DcmDspRoutineUsePort auf TRUE gesetzt, erzeugt der Generator Service-Ports (PPortPrototype) am DCM. SWCs müssen kompatible RPortPrototypes mit ClientServerInterface bereitstellen.
    • Bei zeitkritischen oder BSW-nahen Routinen (z. B. Flash-Löschroutine, Memory-Erase) empfiehlt sich DcmDspRoutineUsePort = FALSE, um IPC/RTE-Laufzeitaufwand zu minimieren.
  • Granulare Subfunktionsunterstützung:
    • Jede Routine kann asymmetrisch konfiguriert werden: Eine Routine ohne DcmDspStopRoutine unterstützt kein vorzeitiges Anhalten; fehlt DcmDspRequestRoutineResults, wird das Resultat ausschließlich direkt im positiven Response von StartRoutine zurückgegeben.
  • Speicherbedarf (ROM/RAM):
    • Jede konfigurierte DcmDspRoutine führt zu Einträgen in der DSP-Routing-Tabelle (Function-Pointer, Session-/Security-Masken, In/Out-Signalstrukturen). Unbenutzte Routinen müssen über DcmDspRoutineUsed = FALSE deaktiviert oder entfernt werden, um Footprint im Flash zu sparen.
