1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR ECU Configuration (ECUC) Metamodell-Ausschnitt, dargestellt als UML-Klassendiagramm (Konfigurationslayout / Container-Baumstruktur).
  • Architektur-Kontext: Spezifiziert die statische Konfigurationshierarchie des BSW-Moduls Can (CAN-Treiber / MCAL) gemäß AUTOSAR Classic Platform (R23-11 bis R25-11).
  • Technischer Zweck: Definiert die Schablone für ARXML-Beschreibungsdateien, aus denen Konfigurationsgeneratoren die C-Header-Dateien (Pre-Compile-Makros) und Datenstrukturen (Can_ConfigType für Post-Build/Link-Time) zur Initialisierung der CAN-Peripherie generieren.

2. Komponenten, Entitäten & Schnittstellen

  • Can: EcucModuleDef
  • Bedeutung: Wurzelknoten der Konfigurationsdefinition für den CAN-Treiber.
  • Multiplizität: lowerMultiplicity = 0, upperMultiplicity = * (erlaubt mehrere CAN-Treiber-Definitionen im System, z. B. bei Multi-Vendor-MCALs).
  • CanGeneral: EcucParamConfContainerDef
  • Bedeutung: Modulglobale, variantenunabhängige Parameter (z. B. CanDevErrorDetect, CanVersionInfoApi, Polling-/Interrupt-Modi).
  • Beziehung: Komposition von Can (+container), Kardinalität exakt 1..1 (lowerMultiplicity = 1, upperMultiplicity = 1).
  • CanConfigSet: EcucParamConfContainerDef
  • Bedeutung: Post-Build-/Link-Time-fähiger Konfigurationsdatensatz für Controller- und Mailbox-Instanzen.
  • Beziehung: Komposition von Can (+container).
  • CanController: EcucParamConfContainerDef
  • Bedeutung: Repräsentiert einen physikalischen CAN-Controller/Kanal auf dem Mikrocontroller (z. B. Basisadresse, Clock-Source, Interrupt-Vektoren, Controller-ID).
  • Beziehung: Sub-Container von CanConfigSet (+subContainer), Kardinalität 1.. (lowerMultiplicity = 1, upperMultiplicity = ).
  • CanControllerBaudrateConfig: EcucParamConfContainerDef
  • Bedeutung: Bit-Timing-Parameter (Baudrate, Propagation Delay, Phase Segments 1 & 2, SJW sowie CAN-FD Data Phase Parameter).
  • Beziehung: Sub-Container von CanController (+subContainer), Kardinalität 1.. (lowerMultiplicity = 1, upperMultiplicity = ). Mindestens eine Baudrate muss pro Controller konfiguriert sein.
  • CanHardwareObject: EcucParamConfContainerDef
  • Bedeutung: Hardware Object Handle (HOH) Definition. Repräsentiert Hardware-Puffer/Mailboxen (HTH für Senden, HRH für Empfang; FullCAN oder BasicCAN; Standard/Extended Identifier; Filtermasken).
  • Beziehung: Sub-Container von CanConfigSet (+subContainer), Kardinalität 1.. (lowerMultiplicity = 1, upperMultiplicity = ).
  • CanControllerRef: EcucReferenceDef
  • Bedeutung: ECUC-Referenzbeziehung.
  • Beziehung: Gehört per Aggregation (+reference) zum CanHardwareObject und referenziert per gerichteter Assoziation (+destination) den zugehörigen CanController.

3. Dynamisches Verhalten & Sequenzablauf (falls zutreffend)

  • Diagrammcharakter: Rein statisches Konfigurationsmetamodell; kein direktes Laufzeit- oder Sequenzdiagramm.
  • Dynamische Implikationen zur Laufzeit:
  • Initialisierung (Can_Init): Der Treiber traversiert die aus CanConfigSet generierte Struktur. Pro CanController wird die Default-CanControllerBaudrateConfig in die Register geladen; anschließend werden die zugeordneten CanHardwareObject-Instanzen (Filter, Tx/Rx-Mailboxen) im jeweiligen CAN-Controller initialisiert.
  • Routing & Dispatch: Sendeanfragen (Can_Write) übergeben ein HTH (CanHardwareObject), das über CanControllerRef hardwareseitig genau einem CAN-Controller zugeordnet ist. Empfangsseitig signalisiert der Controller bei Match in einem HRH (CanHardwareObject) das Ergebnis via CanIf_RxIndication an das CAN Interface (CanIf).

4. Normative Relevanz & Entwickler-Hinweise

  • Flache HOH-Hierarchie (Entkopplung): CanHardwareObject ist nicht als Kindelement von CanController modelliert, sondern hängt direkt unter CanConfigSet. Die Bindung an die Hardware-Einheit erfolgt ausschließlich über CanControllerRef.
  • Auswirkung: HOHs besitzen modulweit eindeutige Indizes, was dem übergeordneten CanIf eine flache, controllerübergreifende Adressierung von Mailboxen (HRH/HTH) ermöglicht.
  • Varianten-Splitting: CanGeneral muss zur Compile-Zeit feststehen (Pre-Compile), während CanConfigSet als separate Wurzelstruktur für Post-Build-Varianten (LOADABLE oder SELECTABLE) im Flash/ROM abgelegt werden kann.
  • Validierungsregeln für BSW-Konfigurationstools:
  • Mindestens ein CanController sowie mindestens ein CanHardwareObject sind im CanConfigSet zwingend erforderlich (lowerMultiplicity = 1).
  • Jeder CanController benötigt mindestens eine valide CanControllerBaudrateConfig.
  • Verwaiste CanHardwareObject-Container ohne gesetzte CanControllerRef sind schemawidrig und führen zum Abbruch der Codegenerierung.
