1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR-VFB-Mapping- und Schichtenarchitektur-Diagramm (Konzeptuelles Komponenten- und Schnittstellendiagramm der Classic Platform, Releases R3.0.7/R3.1.5).
  • Technischer Zweck: Darstellung der Abbildung (Mapping) logischer VFB-Software-Komponenten auf eine konkrete ECU sowie die Abgrenzung der drei primären AUTOSAR-Schnittstellentypen:
    1. AUTOSAR Interface (SW-C zu SW-C via RTE)
    2. Standardized AUTOSAR Interface (SW-C zu BSW-Service/ECU-Abstraktion via RTE)
    3. Standardized Interface (C-API-Schnittstellen innerhalb der BSW ohne RTE)

2. Komponenten, Entitäten & Schnittstellen

Applikationsschicht (AUTOSAR Software / oberhalb der RTE)
  • SHCFrontLeft: SeatHeatingControl: Application Software Component (Symbol: Quadrat-Icon).
    • Calibration-Port: Parameter-Port (Dreieck im Quadrat) für Kalibrierungs- und Kennfelddaten.
    • ecuMode (Mode-Port): Mode-Switch-Port (schwarzes Quadrat mit drei Punkten) zum Anfordern und Empfangen von Mode-Informationen via RTE.
    • nv (Non-Volatile Port): Port (Dreieck-Symbolik) zur NV-Datenübertragung über die NvBlockSw Component.
    • Power Management: Mode-/Control-Port zur Koordination des Energiemanagements/Teilnetzes.
    • Inter-Component-Ports: P-Port (Kreis) und R-Port (Halbkreis) zur bidirektionalen Kopplung mit SHDialFrontLeft.
  • SHDialFrontLeft: HeatingDial: Sensor/Actuator Software Component (Symbol: Messanzeige-/Tacho-Icon).
    • Inter-Component-Ports: Korrespondierende R- und P-Ports zur Kommunikation mit SHCFrontLeft.
    • IO-Port: R-Port (Standardized AUTOSAR Interface) zum Zugriff auf die Hardware-E/A.
  • NvBlockSw Component: NV-Block-Software-Komponente innerhalb der Software-Schicht oberhalb/an der RTE-Grenze. Vermittelt zwischen der Applikationskomponente und dem BSW-NVRAM-Manager über standardisierte Schnittstellen.
Laufzeitumgebung (Runtime Environment – RTE)
  • Bildet das Bindeglied zwischen Applikation und BSW bzw. zwischen SW-Cs untereinander. Realisiert den Virtual Functional Bus (VFB) auf ECU-Ebene.
Basissoftware (Basic Software – BSW / unterhalb der RTE)
  • ECU State Manager (EcuM): BSW-Service. Stellt einen Mode-Switch-Port (schwarzes Quadrat mit drei Punkten) via RTE für Mode Management (ecuMode) bereit; nutzt intern das Standardized Interface zum OS.
  • NvRam Manager (NvM): BSW-Service. Bietet über RTE ein Standardized AUTOSAR Interface (gelber Doppelpfeil) für den Zugriff durch die NvBlockSw Component.
  • Communication (Com-Stack): BSW-Stack (Com, PduR, etc.). Besitzt nach oben (zur RTE) und nach unten (zu Treibern/MCAL) Standardized Interfaces; realisiert u. a. die netzwerkgebundene Signalisierung für das Powermanagement.
  • Operating System (OS): Kern-BSW-Modul. Stellt Standardized Interfaces (OSEK/AUTOSAR OS API) für Task-Aktivierung, Alarm-/Event-Handling und Scheduling an EcuM, NvM, Com, IO und die RTE bereit.
  • ECU Abstraction Component (IO / IoHwAb): Kapselt die Signalaufbereitung. Bietet über RTE einen P-Port (Standardized AUTOSAR Interface) für Sensor/Actuator-SW-Cs an; greift nach unten über Standardized Interfaces auf MCAL-Treiber zu.
  • Microcontroller Abstraction (MCAL): Unterste BSW-Schicht mit direktem Zugriff auf die ECU-Hardware (z. B. ADC-, PWM-, DIO-Treiber).
  • ECU-Hardware: Mikrocontroller-Peripherie und externe Beschaltung (Heizmatte, Drehregler, Versorgungsrelais).

3. Dynamisches Verhalten & Sequenzablauf

  • Signalerfassung (E/A-Pfad):
    1. ECU-Hardware liefert Rohsignal (z. B. ADC-Spannungswert des Heizstufen-Potis).
    2. MCAL-Treiber liest Register per Hardware-Zugriff aus.
    3. ECU Abstraction Component greift per Standardized Interface auf MCAL zu, wandelt physikalische Werte und stellt Daten über ein Standardized AUTOSAR Interface bereit.
    4. Die RTE routet das E/A-Signal an den R-Port von SHDialFrontLeft: HeatingDial.
  • VFB-Kommunikation zwischen SW-Cs:
    • Datenaustausch zwischen SHDialFrontLeft und SHCFrontLeft erfolgt über Ports via VFB/RTE (Sender-Receiver- / Client-Server-Muster).
  • Persistierung über NVBlock-Komponente:
    • SHCFrontLeft kommuniziert über den Port nv mit der NvBlockSw Component.
    • Die NvBlockSw Component interagiert über die RTE über ein Standardized AUTOSAR Interface mit dem NvRam Manager.
  • Zustandsverwaltung & Netzwerk:
    • ecuMode kommuniziert über RTE mit dem ECU State Manager.
    • Power Management tauscht Botschaften via RTE über den BSW-Kommunikationsstack (Communication) aus.
    • Das Operating System stellt den Taktschlag und Scheduling-Mechanismen für BSW-Module und RTE bereit.

4. Normative Relevanz & Entwickler-Hinweise

  • Schnittstellen-Differenzierung & NVRAM-Anbindung:
    • Der Zugriff auf nichtflüchtige Daten erfolgt über das Konzept der NvBlockSw Component, wodurch Applikations-SW-Cs NV-Daten über Standard-Ports anbinden, während die Interaktion mit dem NvRam Manager über das Standardized AUTOSAR Interface durch die RTE erfolgt.
    • Striktes Einhalten der Trennung zwischen AUTOSAR Interface, Standardized AUTOSAR Interface und Standardized Interface (C-API).
  • Architekturvorgaben:
    • Direkter Zugriff von Applikationskomponenten auf BSW-Dienste ohne RTE ist unzulässig.
    • Sensor/Actuator Software Components dürfen über die RTE auf ECU-Abstraktionskomponenten zugreifen, jedoch nicht direkt auf die MCAL.
