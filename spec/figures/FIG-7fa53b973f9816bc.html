1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm zur Definition des ECU-Konfigurationsmetamodells (ECUC Parameter Definition Metamodel gemäß AUTOSAR BSW-Standard).
  • Architektur-Kontext: Spezifiziert die Konfigurationsstruktur des Inter-OS-Application Communicator (IOC) innerhalb des AUTOSAR Classic Operating Systems (AUTOSAR_SWS_OS, Release R21-11, Referenz ECUC_Os_01000).
  • Funktionaler Zweck: Der IOC stellt die standardisierte, speicher- und threadsichere Low-Level-Kommunikationsinfrastruktur für Datenübertragungen über Partitionierungsgrenzen bereit:
    • Inter-OS-Application (verschiedene MPU-/Speicherschutzdomänen auf demselben Core).
    • Inter-Core (Multi-Core-Kommunikation über Core-Grenzen hinweg).
    • Das Metamodell dient als Eingangsvertrag für den BSW/OS-Code-Generator zur Erzeugung partitionierter Pufferstrukturen, Synchronisationsprimitive (Spinlocks, IPIs) und typsicherer IOC-APIs für die RTE.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Container & Kardinalitäten
  • Os (EcucModuleDef, Kardinalität [0..1]): Wurzel-Moduldefinition des AUTOSAR-Betriebssystems.
  • **OsApplication (EcucParamConfContainerDef, Kardinalität [0..*] via +container):** Repräsentiert die OS-Applikationen der ECU; dient als Zielcontainer (+destination) für Sender- und Empfänger-Referenzen.
  • OsIoc (EcucParamConfContainerDef, Kardinalität [0..1] via +container): Hauptcontainer für alle IOC-spezifischen Konfigurationen einer ECU.
  • **OsIocCommunication (EcucParamConfContainerDef, Kardinalität [0..*] via +subContainer):** Repräsentiert einen individuellen logischen IOC-Kommunikationskanal zwischen OS-Applications.
    • OsIocBufferLength (EcucIntegerParamDef, [0..1], Wertbereich 1 … 4\,294\,967\,295 via +parameter): Legt die Ringpuffergröße für gepufferte FIFO-Kommunikation fest (min = 1, max = 4294967295). Ungepufferte 1:1/N:1-Semantik (Last-is-Best) wird durch Weglassen des Parameters konfiguriert.
  • **OsIocSenderProperties (EcucParamConfContainerDef, Kardinalität [1..*] via +subContainer):** Definiert die Eigenschaften der an diesem Kanal teilnehmenden Sender (unterstützt 1:1, N:1, 1:N, N:M Topologien).
    • OsIocSendingOsApplicationRef (EcucReferenceDef, [1..1] via +reference, Ziel OsApplication via +destination): Mandatorische Referenz auf die Quell-OS-Application.
    • OsIocSenderId (EcucIntegerParamDef, [0..1], Wertebereich 0 … 255 via +parameter): Identifikationsnummer des Senders; erforderlich bei Multiplexing mehrerer Sender (N:1, N:M).
    • OsIocFunctionImplementationKind (EcucEnumerationParamDef, [0..1], Default DO_NOT_CARE via +parameter): Steuert die Ausprägung der generierten API. Literale (+literal): FUNCTION, MACRO, DO_NOT_CARE.
  • **OsIocReceiverProperties (EcucParamConfContainerDef, Kardinalität [1..*] via +subContainer):** Definiert die Eigenschaften der Empfänger des Kanals.
    • OsIocReceivingOsApplicationRef (EcucReferenceDef, [1..1] via +reference, Ziel OsApplication via +destination): Mandatorische Referenz auf die Ziel-OS-Application.
    • OsIocReceiverId (EcucIntegerParamDef, [0..1], Wertebereich 0 … 255 via +parameter): Identifikationsnummer des Empfängers bei 1:N/N:M-Topologien.
    • OsIocFunctionImplementationKind (EcucEnumerationParamDef, [0..1], Default DO_NOT_CARE via +parameter): Steuert die Ausprägung der Empfänger-API (FUNCTION vs. MACRO vs. DO_NOT_CARE).
    • OsIocReceiverPullCB (EcucFunctionNameDef, [0..1] via +parameter): Name einer optionalen Callback-Funktion, die auf Empfängerseite bei Datenabholung (Pull-Semantik) aufgerufen wird.
    • OsMemoryMappingCodeLocationRef (EcucForeignReferenceDef, [0..1] via +reference): Foreign Reference auf die Memory-Mapping-Definition (destinationType = SW-ADDR-METHOD) zur Platzierung von empfängerseitigem Code (z. B. Receiver-Callbacks) in spezifischen Speichersektionen.
  • **OsIocDataProperties (EcucParamConfContainerDef, Kardinalität [1..*] via +subContainer):** Definiert die Datenstruktur und Eigenschaften der über den Kanal übertragenen Datenelemente:
    • OsIocDataTypeRef (EcucForeignReferenceDef, [1..1] via +reference): Foreign Reference auf den C-Datentyp des zu übertragenden Datenelements (destinationType = IMPLEMENTATION-DATA-TYPE).
    • OsIocInitValue (EcucStringParamDef, [0..1] via +parameter): Optionaler Initialisierungswert für das Datenelement bei ungepufferten Kommunikationskanälen.
    • OsIocDataPropertyIndex (EcucIntegerParamDef, [0..1], Wertebereich 0 … 255 via +parameter): Position bzw. Parameter-Index des Datenelements bei Mehrparameter-Übertragungen.
    • OsMemoryMappingCodeLocationRef (EcucForeignReferenceDef, [0..1] via +reference): Foreign Reference auf die Memory-Mapping-Definition (destinationType = SW-ADDR-METHOD) zur Platzierung von generiertem IOC-Code bzw. Datenstrukturen.

3. Dynamisches Verhalten & Sequenzablauf

Das statische Metamodell definiert deterministisch die Generierung folgender dynamischer Laufzeitpfade:

[ Sender Task / ISR ] 
       │
       ▼ (OsIocFunctionImplementationKind: MACRO oder FUNCTION)
[ IocWrite / IocSend API ]
       │
       ├─► BufferLength == 0 (Unqueued / Data):
       │     └─► Atomarer Speichertransfer (MPU-Shared-RAM / Cache-Flush / Last-is-Best)
       │
       └─► BufferLength > 0 (Queued / FIFO):
             ├─► Belegung < OsIocBufferLength:
             │     └─► Daten in FIFO einreihen, Schreib-Zeiger inkrementieren, Status IOC_E_OK
             └─► Puffer voll:
                   └─► Verwerfen oder Fehlerbehandlung, Rückgabe IOC_E_LIMIT
       │
       ▼ (Cross-Core / Cross-Partition Synchronisation)
[ Hardware-Spinlock / Inter-Core-Interrupt (IPI) / Memory Barrier ]
       │
       ▼
[ IocRead / IocReceive API ]
       │
       ▼ (OsIocReceivingOsApplicationRef)
[ Empfänger Task / ISR ] (Rückgabe IOC_E_OK oder IOC_E_NO_DATA bei leerem FIFO)
  1. Initialisierungsphase (StartOS): Der OS-Kern initialisiert unbuffered IOC-Kanäle mit OsIocInitValue. Puffer-Pointer (Read/Write Indices) der Queued-Kanäle werden auf Null gesetzt.
  2. Sende-Sequenz (IocSend / IocWrite):
    • Aufruf durch SWC/BSW im Kontext der Partition OsIocSendingOsApplicationRef.
    • Unqueued (OsIocBufferLength = 0): IocWrite überschreibt den Speicherplatz atomar (Last-is-Best).
    • Queued (OsIocBufferLength > 0): IocSend prüft die Puffergrenze. Bei voller Queue bricht der Aufruf synchron ab und meldet IOC_E_LIMIT.
    • Core-übergreifend: Absicherung kritischer Sektionen über Hardware-Spinlocks bzw. Signalisierung an Ziel-Core via Inter-Processor Interrupt (IPI) / Cross-Core-Event.
  3. Empfangs-Sequenz (IocRead / IocReceive):
    • Aufruf im Kontext der Partition OsIocReceivingOsApplicationRef.
    • IocRead liest den aktuellen Wert zerstörungsfrei.
    • IocReceive dekrementiert den FIFO-Füllstand; ist der FIFO leer, erfolgt der synchrone Abbruch mit IOC_E_NO_DATA.

4. Normative Relevanz & Entwickler-Hinweise

  • API-Generierungsvertrag:
    • Der OS-Generator leitet die Namen der C-APIs direkt aus den Bezeichnern der Container ab:
      • Ungepuffert: IocWrite_<OsIocCommunication>(), IocRead_<OsIocCommunication>().
      • Gepuffert: IocSend_<OsIocCommunication>(), IocReceive_<OsIocCommunication>().
      • Bei N:1 / N:M Multi-Sender-Konfigurationen erzwingt OsIocSenderId die Namensdifferenzierung: IocSend_<OsIocCommunication>_<OsIocSenderId>().
  • Inlining vs. Funktionsaufruf (OsIocFunctionImplementationKind):
    • MACRO: Verhindert Funktionsaufruf-Overhead, erfordert jedoch, dass die aufrufende Partition direkten Lese-/Schreibzugriff auf die zugrundeliegenden Strukturen besitzt (MPU-Konfiguration!).
    • FUNCTION: Zwingend erforderlich, wenn der Zugriff über System-Traps/Privileged Mode oder komplexe Cross-Core-Treiber realisiert werden muss.
  • Speicherlayout & MPU/Linker-Schnittstelle:
    • Über OsMemoryMappingCodeLocationRef muss sichergestellt werden, dass die generierten IOC-Puffer in Speicherelementen liegen, die über MPU-Desktiptoren für Sender und Empfänger entsprechend geschützt und freigegeben sind (Shared Data Sections).
    • Bei Multi-Core-Controllern mit getrennten Caches müssen diese Sektionen als Non-Cacheable deklariert oder vom IOC-Treiber explizite Cache-Invalidate-/Flush-Instruktionen ausgeführt werden.
  • RTE-Interaktion:
    • Der Applikationsentwickler ruft den IOC i. d. R. nicht manuell auf. Der RTE-Generator wertet die SWC-Konnektoren aus: Wenn Port-Verbindungen Partitions- oder Core-Grenzen überschreiten, generiert die RTE automatisiert die Aufrufe gegen die hier spezifizierte IOC-Schnittstelle.
