1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (Metamodell-Ausschnitt der AUTOSAR BSW Module Description Template / BSW MTD, M1-Metamodell).
  • Technischer Zweck: Formale Definition des ereignis- und triggergesteuerten Ausführungsmodells für Basissoftware-Module (BSW).
  • Funktionale Einordnung: Dient dem Basic Software Scheduler (SchM / RTE-Generator) als Eingabemodell, um Abhängigkeiten, Aktivierungsmechanismen und Scheduling-Pfade (Task-Aktivierung, OS-Events, direkte Funktionsaufrufe) von BSW-Funktionen deterministisch auf die OS-Ebene abzubilden.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Stereotypen
  • BswModuleDescription («ARElement», «AtpBlueprint», «AtpBlueprintable», «AtpStructureElement»):
    • Wurzelelement der BSW-Modulbeschreibung.
  • Trigger («AtpStructureElement», «Identifiable»):
    • Deklaration eines externen Triggers.
    • Attribut: + swImplPolicy: SwImplPolicyEnum [0..1] (definiert die Implementierungsstrategie, z. B. queuing).
  • BswInternalBehavior («InternalBehavior»):
    • Kapselt die interne Verhaltensmodellierung eines BSW-Moduls.
  • BswModuleEntity («ExecutableEntity», abstrakt):
    • Basisklasse für jeglichen ausführbaren C-Code innerhalb eines BSW-Moduls (z. B. C-Funktionen).
  • BswSchedulableEntity:
    • Spezialisierung von BswModuleEntity. Konkrete Entität, die durch den BSW Scheduler schedulbar ist (z. B. zyklische oder ereignisgetriebene MainFunctions).
  • BswEvent («AbstractEvent», abstrakt):
    • Abstrakte Basisklasse aller Auslöseereignisse im BSW.
  • BswScheduleEvent (abstrakt):
    • Spezialisierung von BswEvent für Ereignisse, die schedulbare BSW-Entitäten über den Scheduler auslösen.
  • BswExternalTriggerOccurredEvent:
    • Konkretes BSW-Schedule-Event für das Eintreffen externer Trigger.
  • BswInternalTriggerOccurredEvent:
    • Konkretes BSW-Schedule-Event für modulinterne Trigger.
  • BswInternalTriggeringPoint («Identifiable»):
    • Modelliert den Codepunkt/Aufruf innerhalb einer BSW-Entität, der einen internen Trigger auslöst.
    • Attribut: + swImplPolicy: SwImplPolicyEnum [0..1].

    • BswModuleDescription → Trigger (+requiredTrigger: 0..*, «atpVariation,atpSplitable»).
    • BswInternalBehavior → BswModuleEntity (+entity: 0..*, «atpVariation,atpSplitable»).
    • BswInternalBehavior → BswEvent (+event: 0..*, «atpVariation,atpSplitable»).
    • BswInternalBehavior → BswInternalTriggeringPoint (+internalTriggeringPoint: 0..*, «atpVariation,atpSplitable»).
  • Generalisierungen (Vererbung):
    • BswSchedulableEntity ⟶ BswModuleEntity
    • BswScheduleEvent ⟶ BswEvent
    • BswInternalTriggerOccurredEvent ⟶ BswScheduleEvent
    • BswExternalTriggerOccurredEvent ⟶ BswScheduleEvent
  • Assoziationen & Referenzen:
    • BswScheduleEvent → BswSchedulableEntity (+startsOnEvent: 1): Jedes Schedule-Event startet exakt eine schedulbare Entität.
    • BswModuleEntity → BswInternalTriggeringPoint (+activationPoint: 0..*, «atpVariation»): Eine Entität kann Triggering-Punkte ansteuern.
    • BswExternalTriggerOccurredEvent → Trigger (+trigger: 1): Koppelt das externe Event an die Trigger-Deklaration.
    • BswInternalTriggerOccurredEvent → BswInternalTriggeringPoint (+eventSource: 1): Verknüpft das interne Trigger-Event mit der auslösenden Trigger-Quelle.

3. Dynamisches Verhalten & Sequenzablauf

Pfad 1: Externe Triggerung (BswExternalTriggerOccurredEvent)
  1. Trigger-Eingang: Ein externes Modul oder eine SWC feuert einen Trigger, der über requiredTrigger an der Modulgrenze deklariert ist.
  2. Event-Instanziierung: Das Eintreffen korreliert mit dem konfigurierten BswExternalTriggerOccurredEvent.
  3. Dispatching via SchM: Der BSW-Scheduler reagiert auf das Event gemäß der Assoziation +startsOnEvent.
  4. Ausführung: Die zugeordnete BswSchedulableEntity wird aktiviert (je nach SchM-Generierung: OS-Task-Aktivierung via ActivateTask(), OS-Event-Signal via SetEvent() oder synchroner Funktionsaufruf).
Pfad 2: Modulinterne Triggerung (BswInternalTriggerOccurredEvent)
  1. Auslösung: Eine BswModuleEntity erreicht während ihrer Abarbeitung einen definierten BswInternalTriggeringPoint (verknüpft über activationPoint).
  2. API-Aufruf: Die Entity ruft die generierte Scheduler-Trigger-API auf (z. B. SchM_Trigger_<Module>_<TriggeringPoint>()).
  3. Event-Signal: Das zugehörige BswInternalTriggerOccurredEvent (Referenz eventSource) wird signalisiert.
  4. Folgeaktivierung: Die Ziel-BswSchedulableEntity wird gestartet (+startsOnEvent: 1).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Treiber- & Stack-Entwickler (BSWMD / C-Code):
    • Modulinterne Auslösepunkte müssen im C-Code strikt über die vom SchM generierten APIs getriggert werden. Keine direkten C-Funktionsaufrufe zwischen entkoppelten Entitäten verwenden, wenn Task-Wechsel oder OS-Synchronisation erforderlich sind.
    • Entitäten, die auf externe/interne Trigger reagieren, müssen zwingend als BswSchedulableEntity modelliert werden; reine BswCalledEntity-Typen unterstützen +startsOnEvent nicht.
  • RTE/SchM-Konfigurator & Integrator:
    • Varianz-Handling («atpVariation»): Trigger-Quellen, Events und Aktivierungspunkte können an System-Konstanten (SwcImplementations / Post-Build / Pre-Compile Variant Handling) gebunden sein.
    • Reentrancy & Queueing (swImplPolicy): Gibt vor, ob Trigger-Aufrufe gepuffert werden (queued) oder ungepuffert (standard) sind. Bei queued muss der SchM/RTE Pufferstrukturen im generierten Code allokieren.
    • Task-Mapping: BswSchedulableEntity muss im OS-Kontext einem passenden Task (Basic/Extended Task) und Prioritätsniveau zugeordnet werden, um Deadlocks bei internen Kaskadentriggerungen zu verhindern.
