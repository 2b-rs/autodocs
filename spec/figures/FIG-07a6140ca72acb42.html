1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm zur Definition des AUTOSAR ECU-Konfigurations-Metamodells (ECUC Parameter Configuration Metamodel).
  • Architektur-Kontext: Modul Dcm (Diagnostic Communication Manager), Submodul DcmDsp (Diagnostic Service Processing).
  • Funktionaler Zweck: Statische Parametrierung des UDS-Dienstes ResponseOnEvent (Service 0x86 nach ISO 14229-1). Es definiert Konfigurationscontainer, Grenzwerte, Datentypen und Abhängigkeiten für zeit-, messwert- und fehlergesteuerte ereignisbasierte Diagnoseübertragungen auf BSW-Ebene.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Container (EcucParamConfContainerDef / EcucChoiceContainerDef)
  • DcmDsp (Multiplizität: 0..1): Übergeordneter Konfigurationscontainer für DSP-Dienste. Aggregiert DcmDspRoe sowie DcmDspDid via Komposition (+subContainer).
  • DcmDspRoe (Multiplizität: 0..1): Hauptcontainer zur Aktivierung und Parametrierung der ROE-Dienstfunktionalität.
  • DcmDspRoeEventWindowTime (Multiplizität: 1..*): Container zur Definition zulässiger Zeitfenster/Gültigkeitsbereiche für ROE-Events.
  • DcmDspRoeEvent (Multiplizität: 1..255): Repräsentiert ein einzelnes ROE-Ereignis. BSW-weites Limit: maximal 255 konfigurierbare Ereignisse.
  • DcmDspRoeEventProperties (Multiplizität: 1..1, Typ: EcucChoiceContainerDef): Disjunktiver XOR-Auswahlcontainer für den auslösenden Ereignistyp:
    • DcmDspRoeOnChangeOfDataIdentifier (Multiplizität: 0..1): Selektion bei ereignisgesteuerter Datenänderung eines DID.
    • DcmDspRoeOnDTCStatusChange (Multiplizität: 0..1): Selektion bei Statusänderung von Diagnose-Fehlercodes (DTC).
  • DcmDspDid (Multiplizität: 0..*): Außerhalb von ROE unter DcmDsp liegender DID-Konfigurationscontainer, der als Ziel-Entität fungiert.
Parameter (Ecuc*ParamDef) & Literale
  • DcmDspRoeInterMessageTime (EcucFloatParamDef, Multiplizität: 1..1): Minimalabstand zwischen zwei konsekutiven ROE-Botschaften (min = 0, max = 5 Sekunden).
  • DcmDspRoeEventWindowTime (EcucEnumerationParamDef, Multiplizität: 1..1): Bestimmt die Lebensdauer des konfigurierten Event-Fensters:
    • DCM_ROE_EVENT_WINDOW_INFINITE: Unbegrenzte Gültigkeit über Zündzyklen hinweg.
    • DCM_ROE_EVENT_WINDOW_CURRENT_CYCLE: Gültigkeit nur im aktuellen Operations-/Fahrzyklus.
    • DCM_ROE_EVENT_WINDOW_CURRENT_AND_FOLLOWING_CYCLE: Gültig im aktuellen und dem direkt folgenden Zyklus.
  • DcmDspRoeEventId (EcucIntegerParamDef, Multiplizität: 1..1): Eindeutige Kennung des Events (min = 0, max = 254, symbolicNameValue = true zur Symbolgenerierung im Header).
  • DcmDspRoeInitialEventStatus (EcucEnumerationParamDef, Multiplizität: 1..1): Startzustand des Events nach ECU-Initialisierung (defaultValue = DCM_ROE_CLEARED):
    • DCM_ROE_CLEARED: Event ist uninitialisiert/gelöscht.
    • DCM_ROE_STOPPED: Event ist registriert, aber gestoppt (wartet auf UDS-Subfunktion startResponseOnEvent).
  • DcmDspRoeDTCStatusMask (EcucIntegerParamDef, Multiplizität: 0..1): 8-Bit-Maske (min = 0, max = 255) zur Filterung relevanter DTC-Statusbit-Übergänge (ISO 14229 DTCStatusMask).
Referenzen (EcucReferenceDef)
  • DcmDspRoeDidRef (Multiplizität: 1..1): Gerichtete Referenz (+reference / +destination) von DcmDspRoeOnChangeOfDataIdentifier auf den Ziel-Container DcmDspDid.

3. Dynamisches Verhalten & Sequenzablauf

Obgleich das Diagramm eine statische Metamodellstruktur zeigt, determiniert es die Laufzeit-Pfade der DCM-Zustandsmaschine:

                  +--------------------------------+
                  |         ECU Startup            |
                  +---------------+----------------+
                                  |
               InitialStatus == DCM_ROE_STOPPED / CLEARED
                                  v
+------------------+     UDS 0x86 (Start)     +-------------------+
| DCM_ROE_STOPPED  | -----------------------> | DCM_ROE_STARTED   |
+------------------+                          +---------+---------+
                                                        |
      +-------------------------------------------------+
      | Trigger-Pfad
      v
+------------------------------------+------------------------------------+
| OnChangeOfDataIdentifier           | OnDTCStatusChange                  |
| -> Polling via Dcm_MainFunction    | -> Asynchroner Callback durch DEM  |
|    oder Callouts gegen SWC/DSP     |    via Dcm_DemTriggerOnDTCStatus() |
| -> Delta-Prüfung auf referen-      | -> Bitweise UND-Verknüpfung mit    |
|    ziertem DcmDspDid               |    DcmDspRoeDTCStatusMask          |
+------------------------------------+------------------------------------+
                                      |
                                      v [Bedingung erfüllt]
                       +------------------------------+
                       | Inter-Message Timer Check    |
                       | (>= DcmDspRoeInterMessage-   |
                       |  Time verstrichen?)          |
                       +--------------+---------------+
                                      | Ja
                                      v
                       +------------------------------+
                       | Diagnose-Response senden     |
                       | & EventWindowTime dekrement/ |
                       | prüfen                       |
                       +------------------------------+
  • Trigger OnDTCStatusChange: Asynchroner Trigger aus dem Diagnostic Event Manager (Dem). Bei Bitwechsel im Statusbyte meldet das Dem den Event an den Dcm. Stimmt das Bitmuster mit DcmDspRoeDTCStatusMask überein, wird die ROE-Übertragung eingeleitet.
  • Trigger OnChangeOfDataIdentifier: Entweder zyklische Überwachung im Dcm_MainFunction-Kontext oder ereignisbasierte Benachrichtigung über die Schnittstelle zum RTE/Applikationslayer für die referenzierte DcmDspDid.
  • Rate-Limiting (InterMessageTime): Bei Signalisierung eines Events blockiert der laufende Timer DcmDspRoeInterMessageTime das sofortige Absenden weiterer ROE-Frames, um Bus-Spitzenlasten (z. B. auf CAN/LIN/Ethernet) zu decken.
  • Terminierung: Ablauf des parametrierten DcmDspRoeEventWindowTime (z. B. Zündungswechsel bei CURRENT_CYCLE) führt zur automatischen Deaktivierung des Events ohne explizite Client-Anforderung.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration & Codegenerierung (ECUC_Dcm_00973):
    • Da DcmDspRoeEventId als symbolicNameValue = true definiert ist, erzeugt der BSW-Generator typisierte Makros/Konstanten (DcmConf_DcmDspRoeEvent_<Name>), die in Callouts und Applikations-SWCs zu verwenden sind.
    • Multiplizität 1..255 für DcmDspRoeEvent determiniert die statische Array-Größe interner RAM-Tabellen (Dcm_RoeEventContextType) des DCM. Unnötig hoch konfigurierte Event-Zahlen führen zu direktem RAM-Overhead.
  • Persistenzanforderungen (NvM):
    • Konfigurationen mit DCM_ROE_EVENT_WINDOW_INFINITE oder CURRENT_AND_FOLLOWING_CYCLE erzwingen die Anbindung eines persistenten NvM-Blocks, um Event-ID, Zustand (STARTED/STOPPED) und Session-Status über Power-Down- und Reset-Zyklen hinweg wiederherzustellen.
  • Implementierungs-Einschränkungen:
    • Durch den Choice-Container DcmDspRoeEventProperties schließt sich die gleichzeitige Auswertung von DTC-Status und DID-Änderung für dieselbe DcmDspRoeEventId strikt aus; kombinierte Events erfordern zwingend separate Event-IDs.
    • DcmDspRoeInterMessageTime erfordert ein granulares Zeithandling in der Task-Planung (Dcm_MainFunction-Zykluszeit muss deutlich kleiner sein als DcmDspRoeInterMessageTime, typischerweise Faktor 5–10).
