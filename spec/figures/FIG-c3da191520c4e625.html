1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Strukturelles Architektur- und Interaktionsdiagramm (Block- und Signalflussdiagramm auf BSW-/VFB-Ebene).
  • Funktionaler Kontext: Entkopplung zwischen Applikations-Software-Komponenten (SWC) und dem BSW-Modul Service Discovery (Sd, typischerweise SOME/IP-SD) über den Basic Software Mode Manager (BswM) gemäß AUTOSAR Classic Platform R23-11 (Abschnitt 7.8.2).
  • Technischer Zweck: Vermittlung von dynamischen Client-Service- und Eventgroup-Abonnements (SubscribeEventgroup). Die SWC bleibt frei von Kommunikations- und Stack-Details; der BswM übersetzt applikationsseitige Modus-Anforderungen über konfigurierte Regeln (Rules) und Aktionslisten (ActionLists) in direkte synchrone BSW-API-Aufrufe an das Sd-Modul.

2. Komponenten, Entitäten & Schnittstellen

  • SWC1 (Application SWC – Client-Rolle):
    • SWC1_P1_Req: PPortPrototype, typisiert über ein SenderReceiverInterface. Dient als Modus-Anforderungsquelle (Wertebereich typischerweise Zustände wie REQUEST_SERVICE / RELEASE_SERVICE).
    • Event Ev1, Event Ev2: RPortPrototypes für den eigentlichen Empfang der Nutzdaten/Events nach erfolgreichem Abonnement.
    • Portgroup Reference: Verknüpft den Steuerungsport (SWC1_P1_Req) semantisch mit der Port-Gruppe des zu abonnierenden Ports Event Ev1.
  • BswM (Basic Software Mode Manager):
    • RPortPrototype: Nimmt den Request von SWC1_P1_Req entgegen (konfiguriert als BswMModeRequestSource bzw. BswMRteModeRequestPort).
    • Event Subscription Arbitration: Enthält die Regel Event Subscription Rule mit dem logischen Ausdruck SWC1_P1_Req == REQUEST_SERVICE ?.
    • Event Subscription TRUE ActionList: Wird bei positivem Regelergebnis ausgeführt; adressiert die Eventgruppen-Ebene im Sd.
    • Service Request Arbitration: Enthält die Regel Service Request Rule mit demselben Auswerteausdruck SWC1_P1_Req == REQUEST_SERVICE ?.
    • Client Service Request TRUE ActionList: Wird bei positivem Regelergebnis ausgeführt; adressiert die Service-Instanz-Ebene im Sd.
  • Service Discovery (Sd Module):
    • Service Instance Si1: Repräsentiert die client-seitige Instanz des Dienstes (SdClientService).
    • Eventgroup EG1: Untergeordnete konsumierte Eventgruppe (SdConsumedEventGroup) innerhalb von Si1, der das konkrete Event Ev1 zugeordnet ist.
  • BSW-APIs (BswM → Sd Schnittstelle):
    • Sd_ClientServiceSetState(): Übergibt den Zielzustand für die Service-Instanz (SD_CLIENT_SERVICE_REQUESTED).
    • Sd_ConsumedEventGroupSetState(): Übergibt den Zielzustand für das Eventgroup-Abonnement (SD_CONSUMED_EVENTGROUP_REQUESTED).

3. Dynamisches Verhalten & Sequenzablauf

  1. Trigger (Applikationsebene):
    • SWC1 schreibt den Wert REQUEST_SERVICE auf den Port SWC1_P1_Req (via Rte_Write).
  2. Arbitration (BswM-Ebene):
    • Die Werteänderung triggert die Regelauswertung im BswM (entweder IMMEDIATE im RTE-Kontext oder DEFERRED in der BswM_MainFunction).
    • Pfad 1 (Service Instance): Service Request Rule evaluiert zu TRUE → Trigger der Client Service Request TRUE ActionList.
    • Pfad 2 (Event Subscription): Event Subscription Rule evaluiert zu TRUE → Trigger der Event Subscription TRUE ActionList.
  3. BSW-API-Ausführung:
    • BswM ruft synchron Sd_ClientServiceSetState(SdClientServiceHandleId, SD_CLIENT_SERVICE_REQUESTED) auf. Das Sd-Modul startet das Finden bzw. Überwachen der Service-Instanz Si1 auf dem Netzwerk.
    • BswM ruft synchron Sd_ConsumedEventGroupSetState(SdConsumedEventGroupHandleId, SD_CONSUMED_EVENTGROUP_REQUESTED) auf. Das Sd-Modul triggert die SOME/IP-SD SubscribeEventgroup-Nachricht für EG1 inklusive Endpoint-Konfiguration.
  4. Terminierung / Gegenpfad:
    • Wechselt SWC1_P1_Req auf RELEASE_SERVICE, evaluieren die Regeln zu FALSE. Entsprechende FALSE ActionLists rufen Sd_ConsumedEventGroupSetState(..., SD_CONSUMED_EVENTGROUP_RELEASED) und Sd_ClientServiceSetState(..., SD_CLIENT_SERVICE_RELEASED) auf.
    • Parametrierfehler (ungültige Handle-IDs) führen synchron zu DET-Einträgen (SD_E_INV_ID).

4. Normative Relevanz & Entwickler-Hinweise

  • Vollständige Stack-Kapselung: Applikations-Entwickler binden keine BSW-Header (Sd.h, SomeIp.h) ein. Die Kopplung erfolgt ausschließlich über VFB-Ports und RTE-Generierungsartefakte.
  • Naming-Convention-Automatisierung: Die AUTOSAR-Methodik schreibt für Ports und Instanzen deterministische Namensschemata vor, damit Generatoren (DaVinci, Tresos, EB Guide etc.) BswMRteModeRequestPort, Regeln, ActionLists und die Zuordnung zu SdClientServiceHandleId / SdConsumedEventGroupHandleId automatisiert ableiten können.
  • Ausführungssemantik (Immediate vs. Deferred):
    • BswMModeRequestSource muss für zeitkritische SD-Aushandlungen auf BSWM_IMMEDIATE konfiguriert werden, um Latenzen durch den Zyklus der BswM_MainFunction zu vermeiden.
    • Bei IMMEDIATE ist sicherzustellen, dass die aufgerufenen Sd_*SetState()-APIs im jeweiligen Caller-Task-Kontext reentrant und blockierungsfrei ausgeführt werden dürfen.
  • PortGroups & ComM-Zustände: Die Aktivierung der Eventgroup setzt voraus, dass die zugehörige ComM-Channel-Referenz aktiv (COMM_FULL_COMMUNICATION) ist und die RTE-Portgruppe für Event Ev1 freigeschaltet wird, sobald das SD-Abonnement netzwerkseitig bestätigt wurde (Sd_ModeSwitch-Notification zurück an BswM).
