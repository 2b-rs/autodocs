  • Klassifikation: Zweiteiliges AUTOSAR BSW-Architektur- und Schichtenmodell (Gesamtarchitektur-Übersicht der AUTOSAR Classic Platform kombiniert mit einem detaillierten Blockdiagramm der Communication Services).
  • Technischer Zweck & Einordnung: Das Diagramm verortet den J1939 Request Manager (J1939Rm) zweistufig im AUTOSAR Classic BSW-Kommunikationsstack:
    • Makro-Ebene (oberer Bildteil): Veranschaulicht die Gesamtschichtenstruktur (Application Layer, RTE, BSW-Schichten mit Hervorhebung der Communication Services, Hardware-Abstraktion, Treiber, Complex Drivers sowie Microcontroller (µC)).

Manager, PduR, CanSM, Generic NM Interface) und J1939-spezifischen Modulen (J1939 NM, CAN TP, J1939 TP) positioniert ist.

2. Komponenten, Entitäten & Schnittstellen

  • Dargestellte Komponenten, Entitäten & Schichten:
    • AUTOSAR-Gesamtarchitektur (oberer Bildteil):
      • Application Layer: Oberste Ebene für Anwendungs-Software-Components.
      • RTE (Runtime Environment): Entkopplungsschicht zwischen Applikation und Basissoftware.
      • Services Layer: Beinhaltet System, Memory und die blau hervorgehobenen Communication Services.
      • ECU Abstraction Layer: Enthält Onboard Dev. Abstraction, Memory HW Abstraction, COM HW Abstraction, I/O HW Abstraction.
      • Microcontroller Abstraction Layer (MCAL): Enthält Microcontroller Drivers, Memory Drivers, Communication Drivers, I/O Drivers.
      • Complex Drivers: Schichtenübergreifende Direktintegration zur Hardwareanbindung unter Umgehung der Standardschichten.
      • Microcontroller (µC): Physikalische Hardware-Ebene.
    • Communication Services (unterer Detailbereich):
      • J1939 Request Manager (J1939Rm) (gelb hervorgehoben): Zentrale Vermittlungsinstanz für SAE J1939 Request-PGNs (59904 / 56832) und Acknowledgments (PGN 59392).
      • COM Manager (ComM): Verwaltung des Kommunikations- und Netzwerkstatus.
      • AUTOSAR COM: Signalbasiertes PDU-Management und Triggerung von Dateninhalten.
      • DCM Diagnostic Com. Manager: Verarbeitung von J1939-Diagnosebotschaften.
      • CAN State Manager (CanSM): Steuerung der CAN-Netzwerk- und Controllerzustände.
      • Generic NM Interface & J1939 NM: Standardisiertes NM-Interface und SAE J1939-81 Address Claiming.
      • PDU Router (PduR): Zentrales I-PDU-Routing zwischen Transport-/Interface-Ebene und oberen Services.
      • CAN TP & J1939 TP: Segmentierte Datenübertragung via ISO 15765-2 bzw. SAE J1939-21 (BAM / CMDT).
  • Schnittstellenbeziehungen:
    • J1939Rm ↔ PduR: Empfang von Request-PDUs (PduR_J1939RmRxIndication) und Senden von Response-/Ack-PDUs (PduR_J1939RmTransmit).
    • J1939Rm ↔ COM / DCM / BSW: Interne Abfragefunktionen und Callback-Triggerung (<User>_RequestIndication).
    • J1939Rm ↔ ComM: Statusprüfung für Kommunikationsfreigabe.
    • Vertikale Anbindung der Communication Services nach oben über die RTE zur Applikation sowie nach unten über COM HW Abstraction und Communication Drivers zum CAN-Bus.

3. Dynamisches Verhalten & Sequenzablauf

  1. Request-Empfang (Inbound Request):
    • Eine Request-PDU (PGN 59904, 3 Bytes Payload mit angeforderter PGN) trifft via CanIf / PduR ein.
    • PduR leitet die I-PDU synchron an J1939Rm_RxIndication weiter.
  2. PGN-Dekodierung & Berechtigungsprüfung:
    • J1939Rm extrahiert die Ziel-PGN und prüft Adressierungsart (Global vs. Destination-Specific).
    • Prüfung gegen die konfigurierte PGN-Routing-Tabelle: Ist die PGN im System registriert und für den anfragenden Node freigegeben?
  3. Auslösung der Antwortbereitstellung (Triggering):
    • Positiver Fall: Aufruf des registrierten Handlers (Com_TriggerIPDUSend, DCM-Callback oder Applikations-SW-C via RTE). Falls gefordert, wird parallel ein positives ACK generiert.
    • Negativer Fall / Nicht unterstützt: J1939Rm generiert autonom ein Negative Acknowledgment (NACK), Access Denied oder Cannot Respond via Ack-PGN 59392.
  4. Outbound Request / Ack Transmission:
    • J1939Rm alloziert eine I-PDU für die Antwort/Quittung und übergibt sie via PduR_J1939RmTransmit an den PduR.
    • Der PduR leitet diese abhängig von der PDU-Größe direkt an das CanIf (Payload ≤ 8 Bytes) oder an das J1939 TP (Payload > 8 Bytes, BAM/CMDT) weiter.
    • Asynchrone Bestätigung erfolgt über J1939Rm_TxConfirmation.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (ARXML / BswM / PduR):
    • PduR-Routing-Tabellen: Für Request-PGNs (59904, 56832) und Ack-PGNs (59392) müssen separate Routing-Pfade zwischen PduR und J1939Rm definiert werden.
    • J1939Rm-Tabellen (J1939RmUser): Jede im Steuergerät verarbeitete PGN muss statisch einem Ziel-Modul (COM, DCM, CDD oder SW-C) zugeordnet sein, inklusive Angabe, ob Anforderungen global (Broadcast, Node 255) oder destinationsspezifisch akzeptiert werden.
  • Koexistenz TP-Schichten:
    • Diagnosedaten können im selben System parallel über CAN TP (UDS on CAN, ISO 14229) und J1939 TP laufen. Der PduR muss anhand der PDU-ID strikt zwischen UDS- und J1939-TP-Kanälen differenzieren.
  • Timing & API-Restriktionen:
    • J1939-21 schreibt strikte Antwortzeiten für Requests vor (Default: max. 1200 ms bis Response oder NACK; 200 ms für spezifische Quittungen). J1939Rm-Timeouts (J1939RmTimeoutDuration) müssen auf BSW-Taskebene (J1939Rm_MainFunction) exakt gegen die Taktrate des OS kalibriert werden.
    • Multi-Node-Szenarien: Unterstützt ein physikalisches ECU mehrere logische J1939-Controller-Applications (CAs), muss der J1939Rm kanal- und knotenbezogen instanziiert bzw. parametriert sein (J1939RmNode).
