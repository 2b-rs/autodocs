1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-2.0-Metamodell-Klassendiagramm (M2-Ebene nach AUTOSAR-Metamodell-Spezifikation).
  • Technischer Zweck: Spezifikation des SOME/IP-Deployments für Service-Schnittstellen in der AUTOSAR Adaptive Platform (TPS_MANI_03040, RS_MANI_00024). Das Metamodell entkoppelt die funktionale, transportunabhängige Definition von Services (ServiceInterface) von deren konkreter Protokoll- und Serialisierungsbindung an SOME/IP (SomeipServiceInterface).

3. Dynamisches Verhalten & Sequenzablauf

Als M2-Strukturmetamodell definiert das Diagramm statische Konfigurationsregeln, die das Laufzeitverhalten des SOME/IP-Stacks (ara::com / Daemon) wie folgt determinieren:

  1. Service-Discovery-Phase (SOME/IP-SD):
  • Das Skeleton annonciert Instanzen mit serviceInterfaceId, majorVersion und minorVersion.
  • Clients abonnieren spezifische Events/Notifier über die zugehörige SomeipEventGroup (eventGroupId), nicht über einzelne Events.
  1. Methodenaufrufe (SomeipMethod):
  • Synchroner oder asynchroner Methodenaufruf via UDP/TCP (transportProtocol).
  • Überschreitet die Serialisierungsgröße die MTU bzw. maximumSegmentLengthRequest/Response, aktiviert die SOME/IP-Laufzeitumgebung das SOME/IP-TP (Segmentierung mit Segment-Header, Einhaltung der Inter-Frame-Pause separationTimeRequest/Response).
  1. Field-Handling (SomeipField):
  • Get: Client sendet SOME/IP-Request an methodId von +get, Server antwortet mit aktuellem Feldwert.
  • Set: Client sendet Request an methodId von +set, Server aktualisiert und bestätigt.
  • Notifier: Bei Feldwertänderung emittiert der Server ein SOME/IP-Notification-Event via +notifier (eventId) an die Abonnenten der zugeordneten SomeipEventGroup.

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Generierung (ara::com / Bindings): Generatoren leiten aus diesem Manifest die C++ Proxy- und Skeleton-Implementierungen, SOME/IP Message IDs (32-Bit Header: serviceInterfaceId [16 Bit] + methodId/eventId [16 Bit]) sowie Serialisierungsroutinen ab.
  • Integritätsprüfung (Manifest-Validierung):
  • Ist bei einem Field hasGetter == true, muss im Deployment zwingend ein +get (SomeipMethod) instanziiert sein (analog für hasSetter $\rightarrow$ +set, hasNotifier $\rightarrow$ +notifier).
  • Methoden-IDs und Event-IDs müssen innerhalb desselben SomeipServiceInterface disjunkt sein (Method-IDs: 0x0001–0x7FFF; Event-IDs: 0x8001–0x8FFF).
  • Netzwerk- & Stack-Konfiguration:
  • Die Wahl von udp erzwingt bei Nutzdatenlasten $> 1400$ Byte die zwingende Definition von maximumSegmentLength (Vielfaches von 16 Byte gem. SOME/IP-TP-Spezifikation) und separationTime, um Pufferüberläufe auf Microcontroller-Empfängerseite zu vermeiden.
  • TCP erfordert keine SOME/IP-TP-Segmentierung (Stream-basiert via Magic Cookies und Message-Length-Feld).
  • Variantenmanagement: Durch «atpVariation» an +method, +field und +event kann die konkrete Schnittstellenausprägung über Post-Build- oder Pre-Compile-Binding-Times gesteuert werden. Das Deployment muss exakt auf die aufgelöste Variante abgestimmt sein.
