1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Zeitablauf- und Task-Scheduling-Diagramm (Execution Timeline / Preemptive Scheduling Diagram).
  • Architektur-Kontext: AUTOSAR Classic Platform – Interaktion zwischen Basic Software ([AUTOSAR OS](file:///private/tmp/autodocs-worktrees/task-figure-evidence/docs/pipeline/task-acceptance.md)), RTE (Runtime Environment) und Application Layer (Software Components, SW-Cs).
  • Normative Einordnung: AUTOSAR_EXP_FunctionalSafetyMeasures, Kap. 3.7.1.4 (Features related to protection against timing violation), Anforderung RS_BRF_00121 (Runtime timing protection and monitoring).
  • Technischer Zweck: Nachweis der zeitlichen Isolation und Beherrschbarkeit von Preemption-Szenarien zur Gewährleistung von Freedom from Interference (FFI) gemäß ISO 26262. Da das AUTOSAR OS Timing-Protection (z. B. Execution Budgeting) ausschließlich auf Task-/ISR-Ebene und nicht pro Runnable Entity (RE) anwenden kann, visualisiert das Diagramm die Kapselung einer kritischen Runnable (RE2) in einer separat überwachten, höher priorisierten Task (TaskB), während Datenkonsistenz und Kontrollfluss mit den unterbrochenen Runnables (RE1, RE3) in TaskA deterministisch erhalten bleiben.

2. Komponenten, Entitäten & Schnittstellen

  • Akteure & Entitäten:
  • TaskA: Präemptierbare AUTOSAR OS-Task niedrigerer Priorität (OS-Task-Objekt, Basis-/Extended Task). Dient als Träger für sequentiell ausgeführte Runnables (RE1, RE3).
  • TaskB: AUTOSAR OS-Task höherer Priorität (Task priority: TaskB > TaskA), dediziert zur isolierten Ausführung und Timing-Überwachung von RE2.
  • RE1, RE2, RE3: Runnable Entities («RunnableEntity»), Implementierung von C-Funktionen innerhalb des SwComponentInternalBehavior einer oder mehrerer SW-Cs.
  • RTE code: Generierter RTE-Glue-Code (Task-Body-Wrapper, Inter-Runnable-Kommunikation, Puffer-Synchronisation, Event-Dispatching).
  • Achsen & Relationen:
  • Y-Achse: Statische OS-Task-Priorität ($Priority(\text{TaskB}) > Priority(\text{TaskA})$).
  • X-Achse: Monoton wachsende Zeitachse ($t$).
  • Kardinalität/Mapping:
  • $\text{TaskA} \to \{\text{RE1}, \text{RE3}\}$ (n:1 Mapping von Runnables in eine gemeinsame Task).
  • $\text{TaskB} \to \{\text{RE2}\}$ (1:1 Mapping zur granularen Zeit- und Budgetüberwachung).

3. Dynamisches Verhalten & Sequenzablauf

  1. Ablauf in TaskA (RE1):
  • Der RTE code initialisiert den Kontext, übernimmt Eingangsdaten (implicit buffer read / local copy) und ruft das Funktionssymbol von RE1 auf.
  • RE1 beendet die Ausführung. Der anschließende RTE code führt Datenvalidierung und Zwischenspeicherung durch.
  1. Aktivierung & Präemption durch TaskB:
  • Der RTE-Wrapper aktiviert TaskB (Triggerung durch RTE-Event, z. B. TimingEvent oder API-Aufruf ActivateTask(TaskB)).
  • Der OS-Scheduler stellt die höhere Priorität von TaskB fest: TaskA wird unverzüglich präemptiert, CPU-Kontext gesichert.
  1. Ausführung von RE2 unter Timing-Kontrolle:
  • TaskB startet; RE2 wird ausgeführt.
  • Das AUTOSAR OS überwacht hierbei das konfigurierte OsTaskExecutionBudget für TaskB.
  • Die Datenkonsistenz zwischen RE2 sowie RE1/RE3 wird über die RTE sichergestellt (z. B. via Inter-Runnable Variables mit Kopiersemantik oder verriegelten Puffern).
  1. Terminierung TaskB & Resumption:
  • RE2 schließt ab; TaskB ruft TerminateTask() auf.
  • Der OS-Scheduler stellt den gesicherten Kontext von TaskA wieder her.
  1. Ablauf in TaskA (RE3):
  • Der RTE code bereitet die Ausführungsumgebung für RE3 vor.
  • RE3 wird ausgeführt.
  • Der abschließende RTE code spiegelt Ausgabedaten zurück (implicit buffer write) und beendet den Task-Zyklus.

4. Normative Relevanz & Entwickler-Hinweise

  • Granularitätsgrenze von Timing Protection (RS_BRF_00121):
  • Das AUTOSAR OS kennt keine Runnables, sondern nur OS-Tasks und OS-Applications (als Fault Containment Regions).
  • Soll eine einzelne Runnable Entity gegen Überschreitung der Worst-Case Execution Time (WCET) per OsTaskExecutionBudget abgesichert werden, ist ein 1:1-Mapping auf eine dedizierte OS-Task zwingend erforderlich (wie bei RE2).
  • Overhead vs. Isolation:
  • Jedes Aufspalten von Runnables in separate Tasks generiert Context-Switch-Overhead, zusätzlichen Stack-Bedarf und Speicherverbrauch für Task Control Blocks (TCB).
  • Datenkonsistenz über Preemption-Grenzen:
  • Bei Datenkopplung zwischen RE1/RE3 (in TaskA) und RE2 (in TaskB) reicht implizite Kommunikation innerhalb derselben Task nicht mehr aus. Es müssen Inter-Task-Mechanismen (z. B. Rte_IRead/Rte_IWrite mit Task-lokaler Pufferung oder explizite Kommunikation über OS-Interrupt-Sperren / OS-Ressourcen) im SwcInternalBehavior konfiguriert werden, um Dirty Reads/Writes zu verhindern.
  • Safety Hook & Fehlerreaktion:
  • Überschreitet TaskB während RE2 das Zeitbudget, greift der OS ProtectionHook() mit konfigurierten Aktionen (PRO_TERMINATETASKISR, PRO_TERMINATETASKISRFREE, PRO_TERMINATEAPPL). Entwickler müssen sicherstellen, dass unterbrochene oder abgebrochene Berechnungen das Gesamtsystem nicht in einen undefinierten Zustand versetzen.
