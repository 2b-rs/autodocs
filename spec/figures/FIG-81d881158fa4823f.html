1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Software- und Hardware-Schichtenarchitekturmodell (Deployment- und Integrationsdiagramm mit Prozess-/Thread-Granularität) gemäß AUTOSAR Adaptive Platform (AP).
  • Technischer Zweck & Einordnung: Exemplarische Darstellung des Accelerator Models zur hardwarebeschleunigten Parallelverarbeitung (Offloading rechenintensiver Algorithmen, z. B. Bildverarbeitung/KI für ADAS). Das Modell entkoppelt die verbrauchende Adaptive Application (Client) über serviceorientierte Kommunikation (ara::com) von einem dedizierten Server-Prozess, der Hardware-Beschleuniger (GPGPU) über standardisierte Frameworks (OpenCL) ansteuert.

2. Komponenten, Entitäten & Schnittstellen

Gemäß der integrierten Legende gliedert sich die Architektur in folgende Entitäten und Schnittstellenebenen (von oben nach unten):

  • Applikations- & Service-Ebene (OS Processes):
    • ADAS AA1 (OS Process): Client-Prozess einer ADAS-Adaptive-Application mit eigenem Ausführungsfaden (Thread).
    • Object Detection server (OS Process): Gekapselter Service-Prozess mit der Rolle Service (inkl. eigenem Worker-Thread), der die Beschleunigerlogik vor Applikationsclients abstrahiert.
  • Framework-Module & Engines:
    • OpenCL kernels (Framework specific module): Rechenkerne für die Parallelverarbeitung, vorgehalten im Server-Prozess und zur Laufzeit in das Beschleuniger-Runtime-Target überführt (loaded).
    • OpenCL (Framework/engine): Standardisierte Laufzeitumgebung/Userspace-Bibliothek zur Verwaltung von Compute-Contexts, Command-Queues und Memory-Buffers.
  • Betriebssystem- & Treiber-Ebene:
    • Accelerator device driver (OS specific module): Kernel-Space-Gerätetreiber zur direkten Interaktion mit dem Hardware-Beschleuniger.
  • Hardware-Ebene:
    • CPUs: Host-Prozessoren zur Ausführung der OS-Prozesse und POSIX-Threads.
    • GPGPU: General-Purpose Graphics Processing Unit als Beschleuniger-Hardware für die Ausführung der OpenCL-Kernels.
  • Schnittstellen (Horizontal Layer Boundaries):
    • C++ generated service I/F: Typsicheres, generiertes ara::com-Service-Interface (Proxy/Skeleton-Architektur via IPC).
    • OpenCL library I/F: Standardisierte OpenCL-C/C++-API (Userspace) zur Initialisierung von Contexts, Übertragung von Puffern und Queueing von Kernels.
    • OS specific device driver I/F: Betriebssystemspezifisches Kernel-Interface (z. B. ioctl, Syscalls, Direct Rendering Manager / DRM).
    • HW specific hardware-software I/F: Physikalische Kopplung (MMIO-Register, PCIe-Bus, Shared Memory/DMA, Hardware-Interrupts).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Offloading-Vorbereitung:
    • Object Detection server instanziiert seine OpenCL-Umgebung über das OpenCL library I/F.
    • Kompilierung/Binärladen der OpenCL kernels (loaded) in den GPU-Speicher via Accelerator Device Driver.
  2. Service Request (Asynchron/Synchron via ara::com):
    • ADAS AA1 ruft über das C++ generated service I/F eine Service-Methode auf (z. B. Übergabe von Bilddatenpuffern oder Referenzen via Shared Memory).
  3. Kernel-Execution & Beschleuniger-Interaktion:
    • Der Worker-Thread des Object Detection server serialisiert Berechnungsaufträge in eine OpenCL Command Queue.
    • Der Accelerator device driver koordiniert DMA-Transfers zur GPGPU und löst die parallele Kernel-Ausführung auf den Compute Units aus.
  4. Synchronisation & Rückmeldung:
    • Abschluss der Berechnung auf der GPGPU meldet per Interrupt an den Treiber; OpenCL setzt das Event auf CL_COMPLETE.
    • Object Detection server sammelt die Ergebnisse ein und signalisiert sie über das Service-Interface (Event/Field-Update oder Method-Response) an den Client ADAS AA1.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Verbindlichkeit: Exemplarische Architekturempfehlung (EXP) zur Strukturierung von Beschleuniger-Workloads auf der Adaptive Platform; keine normativen Einzelanforderungen (RS/SWS), sondern Entwurfsmuster für die Entkopplung von rechenintensiver Hardwarebeschleunigung.
  • Integrations- & Implementierungshinweise:
    • Kapselung der hardwarenahen Beschleunigerschnittstellen (OpenCL-Laufzeitumgebung und Kernel-Code) innerhalb eines dedizierten POSIX-Prozesses (Object Detection server), sodass Applikations-Clients (ADAS AA1) frei von proprietären oder hardwareabhängigen Bibliotheken bleiben.
    • Interprozesskommunikation zwischen Client und Server erfolgt strikt über generierte ara::com-Service-Schnittstellen (C++ generated service I/F).
    • Datenübertragung großer Datenmengen (z. B. Kamerabilder) zwischen Client, Service und Beschleuniger erfordert optimierte Speicherpfade (Zero-Copy / Shared Memory) über das OS und den Accelerator Device Driver, um Kopier-Overheads zu minimieren.
