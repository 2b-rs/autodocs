1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm (Ausschnitt des formalen AUTOSAR M2-Metamodells, Package DOC_Operation).
  • Architektur-Kontext: Spezifikation der Metaklassen für die Client-Server-Kommunikation auf VFB- (Virtual Function Bus) und RTE-Ebene (AUTOSAR Classic Platform). Es definiert das Schablonenmodell für synchrone und asynchrone Funktionsaufrufe (Remote Procedure Call-Semantik) zwischen Software-Komponenten (SWCs) sowie zwischen SWCs und Basissoftware-Diensten (BSW).

2. Komponenten, Entitäten & Schnittstellen

  • PortInterface (abstrakt; «ARElement», «AtpType»):
    • Abstrakte Basisklasse aller AUTOSAR-Port-Schnittstellen.
    • Attribut: + isService: Boolean (Kennzeichnet, ob das Interface standardisierte BSW-Funktionalität repräsentiert).
  • ClientServerInterface:
    • Konkrete Spezialisierung (Generalization) von PortInterface.
    • Bildet den Schnittstellentyp für Client- (RPortPrototype) und Server-Ports (PPortPrototype).
    • Besitzt eine Kompositionsbeziehung (+interface 1 zu +operation 1..*) zu ClientServerOperation.
  • ClientServerOperation («AtpStructureElement», «Identifiable»):
    • Repräsentiert eine konkrete aufrufbare Operation (Methode) innerhalb der Schnittstelle.
    • Ein Interface enthält mindestens eine Operation (1..*).
    • Besitzt eine Kompositionsbeziehung (1 zu * {ordered}) zu ArgumentDataPrototype.
  • AutosarDataPrototype (abstrakt; «DataPrototype»):
    • Abstrakter Basistyp für Datenprototypen im AUTOSAR-Typmodell.
  • ArgumentDataPrototype:
    • Spezialisierung von AutosarDataPrototype.
    • Definiert ein konkretes Übergabeargument einer Operation.
    • Attribute:
      • + direction: ArgumentDirectionEnum (Verbindliche Angabe der Datenflussrichtung).
      • + serverArgumentImplPolicy: ServerArgumentImplPolicyEnum [0..1] (Optionale Steuerungsanweisung für die Implementierungssignatur auf Serverseite).
  • «enumeration» ArgumentDirectionEnum:
    • in: Eingabeparameter (vom Client an den Server übertragen).
    • out: Ausgabeparameter (vom Server an den Client zurückgegeben).
    • inout: Bidirektionaler Parameter (Initialwert übergeben, Modifikation zurückgegeben).
  • «enumeration» ServerArgumentImplPolicyEnum:
    • useArgumentType: Server-Runnable nutzt exakt den konfigurierten AUTOSAR-Datentyp.
    • useArrayBaseType: Bei Array-Typen wird der Typ auf den elementaren Basistyp reduziert (z. B. Übergabe als Zeiger auf das erste Element).
    • useVoid: Signatur verwendet generische Zeiger (void*), typisch für dynamische oder generische Service-Schnittstellen.

3. Dynamisches Verhalten & Sequenzablauf

Obgleich das Klassendiagramm statische Strukturdaten abbildet, determiniert es die Laufzeit-Ausführung über den RTE-Vertrag:

  1. Aufrufinitiierung (Client):
    • Client ruft generierte RTE-API auf: Rte_Call_<Port>_<Operation>([in_args], [out_args], [inout_args]).
    • Bei synchroner Konfiguration blockiert der Client-Thread, bis die Server-Operation terminiert.
    • Bei asynchroner Konfiguration erfolgt die Trennung in Request (Rte_Call) und Abholung/Benachrichtigung (Rte_Result via Polling oder Callback-Event).
  2. Datentransport & Pufferung:
    • Argumente mit direction == in bzw. inout werden serialisiert / per Register/Stack oder Shared Memory an das Server-Runnable übergeben.
    • Bei Inter-ECU-Kommunikation erfolgt die PDU-Generierung über COM/XCP/DCM durch Serialisierung der geordneten Argumentenliste.
  3. Ausführung (Server):
    • Aktivierung des gemappten Server-Runnables (OperationInvokedEvent).
    • Rückgabe via direction == out bzw. inout über modifizierte Zeiger/Puffer.
  4. Fehlerbehandlung / Statusrückgabe:
    • Grundsätzliche Rückgabe des Systemstatus Std_ReturnType (E_OK, E_NOT_OK).

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Konsistenz:
    • Ein ClientServerInterface ohne mindestens eine aggregierte ClientServerOperation verletzt die Multiplizität (1..*) und ist schema-ungültig.
    • Die Modellierung von Argumenten ist streng geordnet ({ordered}). Die Reihenfolge im XML bestimmt zwingend die C-Funktionsparametersignatur des generierten RTE-Codes.
  • C-API & Signaturgenerierung:
    • Argumente mit in werden als Wert (Type) oder bei komplexen Datentypen als const Type* generiert.
    • Argumente mit out und inout werden ausnahmslos als Zeiger (Type*) in die Parameterliste eingefügt.
    • Der Rückgabewert der C-Funktion ist immer für Std_ReturnType reserviert; fachliche Rückgabewerte müssen zwingend als out-Argument modelliert werden.
  • Einsatz von serverArgumentImplPolicy:
    • Für Standard-SWC-Entwicklung bleibt serverArgumentImplPolicy meist undefiniert (useArgumentType).
    • Relevant vor allem für BSW-Services (z. B. NvM_ReadBlock, Dcm), bei denen variable Nutzdatenblöcke effizient als uint8* oder void* verarbeitet werden müssen, ohne typspezifische Wrapper-Runnables zu generieren.
  • Service-Ports:
    • Ist isService: true gesetzt, erzwingt der RTE-Generator Validierungsregeln hinsichtlich Service-Mapping und Kompatibilität mit dem AUTOSAR Service Manager und BSW-Modulen.
