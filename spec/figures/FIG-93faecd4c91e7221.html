1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / AUTOSAR M2-Metamodellausschnitt (Strukturmodell).
  • Architektur-Kontext: AUTOSAR Adaptive Platform (AP) zu Classic Platform (CP) Interoperabilität (AUTOSAR_TPS_ManifestSpecification, Release R17-10 / R1.2.0).
  • Funktionaler Zweck: Modellierung des semantischen Mappings einer asynchronen „Fire-and-Forget“-Methode (aus einem AP-ServiceInterface) auf korrespondierende Interaktionselemente der Classic Platform (SenderReceiverInterface oder TriggerInterface). Ermöglicht die automatisierte Konfiguration von Plattform-Gateways bzw. Kommunikationsbrücken zwischen serviceorientierter (SOME/IP, IPC) und signalbasierter/ereignisbasierter CP-Kommunikation.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Klassen & Hierarchien
  • InterfaceMappingSet (ARElement):
    • Oberstes Containerelement für Schnittstellenabbildungen im ARXML-Datenmodell.
    • Aggregiert per Komposition +interfaceMapping [0..\*] Instanzen von InterfaceMapping.
    • Stereotypen / Tags: «atpVariation, atpSplitable» mit vh.latestBindingTime = systemDesignTime, atp.Status = draft. Erlaubt aufteilbare ARXML-Dateien und System-Design-Time-Variabilität.
  • InterfaceMapping (Identifiable):
    • Abstrakte Basisklasse für Port- und Schnittstellen-Zuordnungen.
    • Komponiert über +fireAndForgetMapping [0..\*] Instanzen von FireAndForgetMapping.
  • FireAndForgetMapping (Identifiable):
    • Kernelement zur Kopplung einer unidirektionalen Methode ohne Rückgabewert an ein CP-Ziel.
    • Referenziert maximal ein AP-Element und genau ein CP-Zielelement:
      • +method [0..1] → ClientServerOperation
      • +dataElement [0..1] → VariableDataPrototype
      • +trigger [0..1] → Trigger
  • ServiceInterface (PortInterface):
    • AP-Serviceschnittstelle. Aggregiert über +method [0..\*] Operationen («atpVariation», gebunden an blueprintDerivationTime, eingeschränkt über mmt.RestrictToStandards = AP).
  • ClientServerOperation (AtpStructureElement, Identifiable):
    • Repräsentiert die AP-Methode.
    • Attribut: + fireAndForget : Boolean [0..1]. Bei gesetztem true erfolgt die Methodenabwicklung ohne Response/Return-Nachricht.
  • SenderReceiverInterface (DataInterface, PortInterface):
    • CP-Schnittstelle für signalbasierte Datenübertragung; aggregiert +dataElement [1..\*] vom Typ VariableDataPrototype.
  • VariableDataPrototype (AutosarDataPrototype, Identifiable):
    • CP-Datenelement für Sender-Receiver-Kommunikation (Aufnahme von Nutzdaten).
  • TriggerInterface (PortInterface):
    • CP-Schnittstelle zur asynchronen Aktivierung von Runnables; aggregiert +trigger [1..\*] vom Typ Trigger.
  • Trigger (AtpStructureElement, Identifiable):
    • Auslöser für RTE-Events; besitzt das Attribut + swImplPolicy : SwImplPolicyEnum [0..1].

3. Dynamisches Verhalten & Sequenzablauf

Das statische Metamodell definiert die Laufzeit-Übersetzung an der Gateway-Grenze:

[AP Service Consumer] 
       │  (F&F Method Call: Request without Return / SOME/IP 0x01)
       ▼
[Bridge / Gateway (FireAndForgetMapping)]
       ├────── Pfad A (Mapping auf VariableDataPrototype) ──────┐
       │                                                       ▼
       │                                            [Rte_Write_<p>_<o>(payload)]
       │                                                       │
       │                                                       ▼
       │                                            [CP SWC (S/R-Receiver)]
       │
       └────── Pfad B (Mapping auf Trigger) ──────────────────┐
                                                               ▼
                                                    [Rte_Trigger_<p>_<t>()]
                                                               │
                                                               ▼
                                                    [CP Runnable Activation]
  1. Triggering (AP → Bridge): Ein AP-Client sendet eine Fire-and-Forget-Methode (ara::com Message Type REQUEST_NO_RETURN). Es existiert kein Rückkanal, kein Blocking und keine Fehlerbehandlung für Applikationsfehler auf AP-Seite.
  2. Abbildungspfad A (Data Element):
    • Das Gateway deserialisiert die Input-Argumente der F&F-Methode.
    • Die Nutzlast wird in das gemappte VariableDataPrototype geschrieben (Rte_Write).
  3. Abbildungspfad B (Trigger):
    • Der Empfang der F&F-Nachricht dient ausschließlich als Aktivierungsereignis.
    • Das Gateway ruft die CP-RTE-Trigger-API auf (Rte_Trigger), wodurch ein an das Trigger-Element gekoppeltes ExternalTriggerOccurredEvent eine CP-Runnable aktiviert (reine Signalisierung ohne Nutzdatenübergabe).

4. Normative Relevanz & Entwickler-Hinweise

  • Signaturbedingungen für ClientServerOperation:
    • Eine Operation mit fireAndForget == true darf normativ weder OUT- noch INOUT-Parameter besitzen (ArgumentDataPrototype.direction).
    • Es dürfen keine ApplicationErrors (possibleErrorRefs) zugeordnet sein, da kein Transportprotokoll-Responseframe existiert.
  • Konfigurationskonsistenz (Typkompatibilität):
    • Bei Mapping auf ein VariableDataPrototype: Der Datentyp des Input-Parameters der AP-Methode muss strukturell und semantisch kompatibel zum AutosarDataType des CP-VariableDataPrototype sein (gegebenenfalls über CompuMethod / DataTypeMappingSet synchronisiert).
    • Bei Mapping auf ein Trigger: Eingangsdaten der Methode werden ignoriert oder die F&F-Operation muss parameterlos sein, da das CP-TriggerInterface keinen Datentransport unterstützt.
  • Variabilitäts- & Bindungsregeln:
    • InterfaceMappingSet ist «atpSplitable»: Definitionen können über mehrere ARXML-Pakete verteilt werden.
    • Letzte Bindungszeit für Mappings ist systemDesignTime; spätere Bindung zur Link- oder Laufzeit ist unzulässig.
  • Codegenerierung (RTE / Bridge-Stack):
    • Generatoren erzeugen aus dem FireAndForgetMapping unidirektionale Wrapper ohne Callback- oder WaitPoint-Overhead im CP-RTE-Kontext (weder Rte_Result noch Rte_Feedback erforderlich).
