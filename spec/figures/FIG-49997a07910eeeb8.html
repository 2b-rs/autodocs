1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Zeitablaufdiagramm / Strukturelles Timing-Modell (Diskretes Ablaufdiagramm einer statischen Scheduling-Tabelle).
  • Funktionale Einordnung: AUTOSAR Classic Platform OS (CP SWS OS, basierend auf OSEK/VDX-Erweiterungen bzw. AUTOSAR OS Scalability Classes SC2/SC4).
  • Technischer Zweck: Spezifikation der inneren Struktur und Zeitbasis einer OsScheduleTable gemäß SWS_Os_00401 und SRS_Os_00098. Das Diagramm definiert das Verhältnis von absolut konfigurierten Offsets, relativen Delays zwischen Ablaufpunkten (Expiry Points), Tabellendauer (Schedule Table Duration), Task-Aktivierungen und Event-Setzungen über einem zugrundeliegenden OsCounter.

2. Komponenten, Entitäten & Schnittstellen

  • OsScheduleTable (Zentrale Entität):
  • Konfigurierte Gesamtdauer: Schedule Table Duration = 50 ticks (OsScheduleTableDuration).
  • Eigenschaft: Periodisch (OsScheduleTableRepeating = TRUE), ersichtlich aus dem Rücksprungpfad von Tick 50 auf 0.
  • Getrieben durch einen zugeordneten OsCounter (Tick-Einheit: diskrete Inkremente des Counters).
  • OsScheduleTableExpiryPoint (Ablaufpunkte 1 bis 5):
  • Expiry Point 1 (Initial Expiry Point): Offset = 4 Ticks (InitialOffset = 4).
  • Task-Aktivierungen: TaskA, TaskB (OsScheduleTableTaskActivation).
  • Event-Setzungen: EventP:TaskC, EventP:TaskD (OsScheduleTableEventSetting).
  • Expiry Point 2: Offset = 12 Ticks.
  • Task-Aktivierungen: <none>.
  • Event-Setzungen: EventP:TaskC, EventP:TaskD.
  • Expiry Point 3: Offset = 20 Ticks.
  • Task-Aktivierungen: TaskA, TaskE.
  • Event-Setzungen: <none>.
  • Expiry Point 4: Offset = 32 Ticks.
  • Task-Aktivierungen: TaskA, TaskE.
  • Event-Setzungen: EventQ:TaskC, EventQ:TaskE.
  • Expiry Point 5 (Final Expiry Point): Offset = 40 Ticks.
  • Task-Aktivierungen: TaskB, TaskF.
  • Event-Setzungen: EventP:TaskC.
  • Delays / Delta-Werte (Laufzeit-Intervalle):
  • EP1 $\rightarrow$ EP2: $\Delta = 8\text{ ticks}$ ($12 - 4$).
  • EP2 $\rightarrow$ EP3: $\Delta = 8\text{ ticks}$ ($20 - 12$).
  • EP3 $\rightarrow$ EP4: $\Delta = 12\text{ ticks}$ ($32 - 20$).
  • EP4 $\rightarrow$ EP5: $\Delta = 8\text{ ticks}$ ($40 - 32$).
  • EP5 $\rightarrow$ Tabellenende: FinalDelay = 10 ticks ($50 - 40$).
  • Re-Start-Intervall (Periodischer Überlauf): $\text{Delay} = \text{FinalDelay} + \text{InitialOffset} = 10 + 4 = 14\text{ ticks}$.

3. Dynamisches Verhalten & Sequenzablauf

  1. Start & Initial-Verzögerung:
  • Start über API (StartScheduleTableRel, StartScheduleTableAbs oder Synchronisations-Start).
  • Die Tabelle startet bei Tick 0. Bis zum ersten Ablaufpunkt vergeht der InitialOffset (4 Ticks).
  1. Ausführung der Expiry Points:
  • Erreicht der Counter den absoluten Offset eines Expiry Points, triggert das OS synchron die dort gebündelten Aktionen.
  • Abarbeitung: Zuerst Task-Aktivierungen (ActivateTask()-Äquivalent), danach Event-Setzungen (SetEvent()-Äquivalent) für Extended Tasks.
  • Tasks gehen vom Zustand SUSPENDED in READY über bzw. wechseln bei Event-Zuweisung von WAITING nach READY.
  1. *Periodischer Überlauf (Wrap-Around):*
  • Nach EP5 (Tick 40) läuft der Timer weiter durch den FinalDelay (10 Ticks) bis zur konfigurierten Duration (Tick 50 / 0).
  • Bei periodischen Tabellen schließt der Zyklus nahtlos: Die Latenz zwischen dem letzten Expiry Point eines Zyklus und dem ersten des Folgezyklus beträgt exakt $\text{FinalDelay} + \text{InitialOffset} = 14\text{ Ticks}$.
  1. Verkettung & Abbruchbedingungen:
  • Ein Wechsel via NextScheduleTable() vollzieht sich deterministisch erst nach Durchlaufen der vollen Duration (Tick 50).
  • Ein Aufruf von StopScheduleTable() bricht die Progression sofort ab; laufende/bereits aktivierte Tasks bleiben unbeeinflusst im Scheduler.

4. Normative Relevanz & Entwickler-Hinweise

  • Deterministisches Scheduling (Ersatz für periodische Alarme):
  • Reduziert OS-Overhead drastisch: Statt mehrerer Einzeltimer/Alarme verwaltet das OS pro ScheduleTable nur einen einzigen aktiven Hardware-/Software-Timer-Abgleich bis zum nächsten Expiry Point.
  • Konfigurationsregeln (ARXML / BSW-Editor):
  • OsScheduleTableDuration muss strikt größer sein als der Offset des Final Expiry Point (Duration > Offset_final). Ein Konfigurationswert Duration < Offset_final ist schema- und semantisch ungültig.
  • Offsets müssen streng monoton steigend parametriert werden ($Offset_i < Offset_{i+1}$).
  • OsScheduleTableRepeating = TRUE erzwingt die Berücksichtigung von FinalDelay + InitialOffset im Gesamttiming des Systems (z. B. für Bus-Synchronisation wie FlexRay oder TSN/Global Time Interfaces).
  • API-Verhalten & Fehlerbehandlung:
  • Schlägt eine Task-Aktivierung fehl (z. B. Task-Aktivierungs-Limit OsTaskActivationLimit überschritten), meldet das OS den Fehler via ErrorHook (bzw. Det), die Schedule-Table-Ausführung selbst bricht jedoch nicht ab.
  • Werden Events auf Tasks gesetzt, die sich im Zustand SUSPENDED befinden, resultiert dies zur Laufzeit in E_OS_STATE (Standard/Extended Status).
  • Task-Prioritäten & Preemption:
  • Die Schedule Table garantiert ausschließlich den deterministischen Zeitpunkt der Task-Aktivierung / Event-Freigabe, nicht den Ausführungszeitpunkt. Die tatsächliche CPU-Zuteilung obliegt dem prioritätsbasierten OSEK/AUTOSAR-Scheduler.
