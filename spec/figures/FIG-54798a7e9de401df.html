1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Layout / Protokoll-Frame-Bitfelddefinition (Binäres Paketformat auf Schicht 5–7 gemäß AUTOSAR FO PRS Intrusion Detection System).
  • Technischer Zweck: Das Diagramm spezifiziert die 8-Byte-Basiseinheit (Event Frame) des AUTOSAR IDS-Nachrichtenformats zur standardisierten Übertragung von sicherheitsrelevanten Vorfällen (Security Events) zwischen Intrusion Detection System Managern (IdsM) oder zur Weiterleitung an fahrzeuginterne/-externe Auswerteeinheiten (z. B. On-Board Security Event Collector / SIEM).
  • Einordnung im AUTOSAR-Gesamtsystem:
    • Das Gesamtprotokoll ist modular strukturiert: Auf den obligatorischen Event Frame können optional Timestamp, Context Data Frame und Signature Frame folgen.
    • Gemäß [PRS_Ids_00005] ist das Format hardware- und busunabhängig (CAN, CAN FD, Ethernet/SOME/IP, FlexRay), jedoch mit exakt 8 Bytes so ausgelegt, dass ein minimaler Security-Event-Report verlustfrei und ohne Segmentierung in einen klassischen CAN-Standard-Frame (Payload-Länge DLC = 8) passt.

2. Komponenten, Entitäten & Schnittstellen

Übergeordneter Protokollverbund (Frame-Hierarchie)
  • Event Frame (obligatorisch, 8 Bytes): Minimale Metadatenstruktur zur Identifikation und Zählung des Vorfalls.
  • Timestamp (optional): Zeitstempel zur Korrelation (üblicherweise aus Synchronized Time-Base, z. B. StbM / IEEE 802.1AS).
  • Context Data Frame (optional): Erweiterte Rohdaten/Umgebungsdaten des gemeldeten Events (z. B. gefilterte CAN-Payload, CPU-Status).
  • Signature Frame (optional): Kryptografischer Integritäts- und Authentizitätsnachweis (z. B. via Crypto Stack / Csm / SecOC berechneter MAC oder digitale Signatur).

3. Dynamisches Verhalten & Sequenzablauf

  1. Ereignis-Trigger: Ein On-Board-Sensor (z. B. CanSM/CanIf-Filter, SecOC-MAC-Fehler, Firewall, Dem oder Applikations-SW-C) detektiert eine Security-Anomalie und ruft die IdsM-API auf:
    • CP: IdsM_SetSecurityEvent(EventDefinitionId, ...)
    • AP: ara::idsm::ReportSecurityEvent(...)
  2. Filterung & Aggregation (IdsM-intern):
    • Der IdsM validiert und filtert das Event (Thresholding, Rate-Limiting, Blacklisting).
    • Bei wiederholtem Auftreten desselben Events innerhalb eines Aggregationsintervalls wird der Count-Parameter inkrementiert, anstatt für jeden Vorfall eine separate Bus-PDU zu erzeugen.
  3. PDU-Serialisierung (Big-Endian-Serialisierung):
    • Der IdsM generiert den 8-Byte-Event Frame strikt in Network Byte Order (Byte 0 zuerst; MSB in Bit 7).
    • Wenn konfiguriert, werden Zeitstempel (via StbM) und Kontextdaten angehängt sowie ein Signature-Trailer via CSM/SecOC ergänzt.
  4. PDU-Übergabe an den Communication Stack:
    • Übergabe als I-PDU an PduR / Com bzw. Ethernet Socket/SOME/IP.
    • Asynchrone Sendebestätigung über TxConfirmation. Fehlerbehandlung bei Sendeverzug oder PDU-Pufferüberlauf erfolgt via Det (IDSM_E_PARAM_POINTER, IDSM_E_FIFO_OVERFLOW).

4. Normative Relevanz & Entwickler-Hinweise

  • Endianness ([PRS_Ids_00004]):
    • Verbindliche Ausrichtung auf Big-Endian (Motorola-Format). Auf Little-Endian-Zielarchitekturen (z. B. ARM Cortex-M/R/A, x86/AURIX-spezifische Little-Endian-Cores) ist eine explizite Byte-/Bit-Invertierung bzw. Shift-Maskierung für die 10-Bit (IdsM Instance ID) und 16-Bit (Event Definition ID, Count) Multi-Byte-Werte zwingend erforderlich.
  • Byte-Übergreifende Bitfelder (Byte 1 & Byte 2):
    • IdsM Instance ID überspannt die Grenze zwischen Byte 1 und Byte 2 (Bit 7..6). Es darf kein naiver C-Bitfield-Struct verwendet werden, da Compiler-Implementierungen bezüglich Bitfeld-Packing und Endianness nicht portabel sind. Bit-Maskierung muss über standardisierte Shift-Operationen realisiert werden: $$\text{Byte 1} = (\text{IdsM\_InstanceId} \gg 2) \ \& \ \text{0xFF}$$ $$\text{Byte 2} = ((\text{IdsM\_InstanceId} \ \& \ \text{0x03}) \ll 6) \mid (\text{Sensor\_InstanceId} \ \& \ \text{0x3F})$$
  • CAN-Payload-Optimierung ([PRS_Ids_00005], [PRS_Ids_00006]):
    • Werden für ein Event weder Kontextdaten noch Timestamps/Signaturen konfiguriert (Protocol Header = 0), entspricht die resultierende PDU exakt 8 Bytes. Dies ermöglicht die direkte Übertragung via Classical CAN ohne Transportprotokoll (CanTp).
  • Konfigurationsverträge (ARXML / BswM):
    • Event Definition ID muss konsistent mit dem BSW-Modul IdsM über standardisierte IDs aus dem Security-Modell gemappt sein.
    • Das Reserved-Byte (Byte 7) muss vom Transmitter auf 0x00 initialisiert und vom Receiver tolerant behandelt (ignoriert) werden, um Vorwärtskompatibilität zu wahren.
