1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Schichten- und Signalflussdiagramm (Struktur- und Schnittstellenmodell) mit Gegenüberstellung von Hardware-Topologie und AUTOSAR-Softwarearchitektur (VFB/BSW-Schichten).
  • Technischer Zweck: Veranschaulichung der horizontalen Signalwandlungskette vom physikalischen Fahrzeugumfeld bis zur Anwendungssoftware sowie der vertikalen 1:1-Abstraktionsentsprechung zwischen Hardware-Baugruppen und Software-Schichten gemäß AUTOSAR Classic Platform (Spezifikationsstand R2.1/V2.2.0, Software Component Template).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm ist durch eine horizontale Trennlinie in zwei Domänen unterteilt:

A. Hardware-Domäne (obere Ebene)
  • Car environment: Externe physikalische Umgebung (Quelle der Messgröße).
  • Schnittstelle (1): Physikalische Interaktionsstufe (Fahrzeuggeschwindigkeit v).
  • Sensor: Primärsensor zur Wandlung der physikalischen Größe in ein primäres elektrisches Messsignal.
  • Schnittstelle (2): Elektrische Sensorschnittstelle (I_sensor ∈ [0 … 200\,mA]).
  • ECU Electronics: Diskrete ECU-Schaltung zur Signalaufbereitung (z. B. Shunt, Tiefpassfilter, Operationsverstärker, Schutzbeschaltung).
  • Schnittstelle (3): Aufbereitetes analoges Spannungssignal (U_ECU ∈ [0 … 5\,V]).
  • μC Peripherals: On-Chip-Peripheriebausteine des Mikrocontrollers (z. B. ADC-Kanal, Input Capture, DIO).
B. Software-Domäne (untere Ebene)
  • MCAL: Microcontroller Abstraction Layer. BSW-Treiberschicht für die On-Chip-Peripherie.
    • Schnittstelle (4): Hardware-nahe C-APIs, dargestellt mit ADC_get() (Auslesen von ADC-Raw-Counts) und bidirektionalem Steuerpfad DIO_set() (z. B. Messbereichsumschaltung, Sensor-Versorgungsfreigabe).
  • ECU Abstraction: BSW-Schicht (IoHwAb / I/O Hardware Abstraction). Kapselt die Schaltplan-Topologie der ECU (z. B. Shunt-Widerstandswerte, Spannungsteilerfaktoren).
    • Schnittstelle (5): Standardisiertes AUTOSAR-Interface (get_I_sensor()), bereitgestellt über Lollipop-Notation (Client-Server-Operation). Liefert die entzerrte elektrische Kenngröße des Sensors (Stromwert).
  • Sensor SW-C: SensorActuatorSoftwareComponentType (Sensor-SW-C). Verantwortlich für Sensorkennlinie, Kalibrierdaten, Fehlerplausibilisierung und Umrechnung von elektrischer Einheit (Strom) in physikalische SI-Einheit.
    • Schnittstelle (6): Standardisiertes Application-Interface (get_v()), typischerweise VFB-basiertes Client-Server- bzw. Sender-Receiver-Interface zur Übergabe der physikalischen Größe an übergeordnete Schichten.
  • Application SW-C: ApplicationSoftwareComponentType. Reine hardware-unabhängige Anwendungslogik.

3. Dynamisches Verhalten & Sequenzablauf

Die Signalerfassungs- und Wandlungskette verläuft chronologisch über sechs Transformationsstufen:

  1. Stufe 1 (Physikalisch): Änderung des Fahrzeugzustands (v) wirkt auf das Messelement des Sensors.
  2. Stufe 2 (Elektrisch primär): Sensor moduliert das Ausgangssignal proportional zur physikalischen Größe (I_sensor = f(v)).
  3. Stufe 3 (Elektrisch sekundär): Die diskrete Schaltung der ECU wandelt den Strom über Bürde/Shunt in einen microcontroller-kompatiblen Spannungsbereich (U_ECU = f(I_sensor)).
  4. Stufe 4 (Treiber-Sampling / MCAL):
    • Synchroner oder interruptgesteuerter Aufruf von ADC_get() liest den digitalisierten Raw-Wert (Adc_ValueGroupType) aus dem ADC-Register.
    • Optionaler Kontrollpfad über DIO_set() zur Aktivierung von Messbrücken oder Diagnose-Pins.
  5. Stufe 5 (Platinen-Abstraktion / BSW): ECU Abstraction rechnet die Raw-ADC-Werte anhand fester Schaltungsparameter (Referenzspannung, Widerstandswerte) in die elektrische Messgröße um (I_sensor) und stellt diese über die RTE mittels get_I_sensor() bereit.
  6. Stufe 6 (VFB / Applikationsebene): Sensor SW-C führt Linearisierung, Filterung und Kennfeld-Mapping durch, validiert elektrische Diagnosegrenzen (Short-to-Ground, Open-Load, Short-to-Battery) und stellt den physikalischen Geschwindigkeitswert v via RTE über get_v() der Application SW-C zur Verfügung.

4. Normative Relevanz & Entwickler-Hinweise

  • Schichtenreinheit & Abstraktionsgrenzen:
    • MCAL (MAL): Darf keinerlei Kenntnis über externe Schaltungskomponenten (Shunt, Teiler) oder physikalische Einheiten besitzen. C-APIs liefern ausschließlich vorzeichenlose/vorzeichenbehaftete Rohdaten (uint16, Digit-Counts).
    • ECU Abstraction (IoHwAb): Darf hardware-spezifisch für das Steuergerät sein, transformiert aber ausschließlich in elektrische Größen (Volt, Ampere, Ohm, Duty-Cycle). Physikalische Einheiten (km/h, °C, bar) sind hier normativ verboten.
    • Sensor SW-C: Einzige Instanz, die die elektrische Sensor-Schnittstelle mit der physikalischen Domäne verknüpft. Sie ist hardware-abhängig bezüglich des Sensortyps, aber platinenunabhängig.
    • Application SW-C: Vollständig hardware-, sensor- und platinen-agnostisch. Arbeitet ausschließlich mit standardisierten Application Data Types (SI-Einheiten, Festkomma/Gleitkomma mit CompuMethod).
  • VFB-Kopplung (RTE):
    • Schnittstellen (5) und (6) passieren die RTE. Ab AUTOSAR R3.x/R4.x wird Schnittstelle 5 typischerweise über ein Client-Server Interface oder Sender-Receiver Interface zwischen IoHwAb und SensorActuatorSWC abgebildet.
  • Architektur-Evolution (R2.1 → R4.x+):
    • Das historische Kürzel MAL (Microcontroller Abstraction Layer) wurde zur Vermeidung von Verwechslungen mit HAL final als MCAL normiert.
    • Die synchrone Polling-Semantik ADC_get() weicht im realen Treiberstack dem standardisierten, gruppenbasierten asynchronen Auslesen (Adc_StartGroupConversion(), Adc_ReadGroup()).

In an implementation of AUTOSAR only the Microcontroller Abstraction (MCAL) has direct access to the peripheral hardware. This layer is going to be standardized and all hardware access should go through this layer. The idea of the AUTOSAR signal flow is to map the hardware to the corresponding software modules. So if an electrical current is the input to the microcontroller peripheral, the MCAL will deliver a data value that represents this current. As the ECU Electronics has enhanced and converted the electrical signal prior to the microcontroller, the corresponding software entity is reversing this conversion. This is performed in the ECU Abstraction layer. So if the input to the ECU is an electrical current and the ECU Electronics has converted this current into a voltage (from 2 to 3), the ECU Abstraction will convert the data value voltage into an AUTOSAR signal representing a current (from 4 to 5).
