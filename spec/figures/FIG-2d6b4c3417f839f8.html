1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Protokoll-Frame- / PDU-Layout (Wire-Format-Bitfeld-Darstellung gemäß Big-Endian / Network-Byte-Order mit 32-Bit-Raster).
  • Funktionale Einordnung: Definiert das normative SOME/IP-Nachrichtenformat (AUTOSAR_CP_SWS_SOMEIPTransformer, PRS SOME/IP).
  • Architektur-Kontext: Dient der Abgrenzung von Serialisierungszuständigkeiten im AUTOSAR Classic Communication-Stack zwischen dem SOME/IP Transformer (SomeIpXf), der RTE und dem Socket Adaptor (SoAd). Das Gesamtdiagramm zeigt das vollständige On-Wire-Format; der Transformer selbst serialisiert/deserialisiert normativ ausschließlich den unteren Block (ab Request ID), während der obere Block (Message ID, Length) vom SoAd (Header Mode) verwaltet wird ([SWS_SomeIpXf_00015]).

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert die Nachricht in zwei logische Schichten über einem 32-Bit-Raster (Bit 0 bis 31):

  1. Nicht durch SomeIpXf transformierter Header-Teil (SoAd-Verantwortung):
    • Message ID (32 Bit, Offset 0 Byte):
      • Service ID [Bit 0–15 / 16 Bit]
      • Sub-Identifier [Bit 16–31 / 16 Bit]: Method ID (Bit 16 = 0) bzw. Event ID (Bit 16 = 1).
    • Length (32 Bit, Offset 4 Byte):
      • Enthält die Bytegröße aller nachfolgenden Felder: $\text{Length} = 8\,\text{Byte (Header-Rest)} + \text{Payload-Länge}$ (gemessen ab Byte 8 bis Ende der Nachricht; gekennzeichnet durch die Klammer Covered by Length).
  2. Durch SomeIpXf transformierter Header-Teil & Nutzdaten:
    • Request ID (32 Bit, Offset 8 Byte, [SWS_SomeIpXf_00154]):
      • Zusammengesetzt aus Client ID [16 Bit] und Session ID [16 Bit] ([SWS_SomeIpXf_00024]). Wird von der RTE vorgegeben.
    • Protocol Version (8 Bit, Offset 12 Byte):
      • Identifiziert die Spezifikationsversion des SOME/IP-Protokolls (statisch konfiguriert).
    • Interface Version (8 Bit, Offset 13 Byte):
      • Major-Version des Service-Interfaces (zur Laufzeit-/Kompatibilitätsprüfung).
    • Message Type (8 Bit, Offset 14 Byte):
      • Nachrichtencharakteristik: REQUEST (0x00), REQUEST_NO_RETURN (0x01), NOTIFICATION (0x02), RESPONSE (0x80), ERROR (0x81), jeweils ggf. mit TP-Flag (0x20 für segmentierte Übertragung).
    • Return Code (8 Bit, Offset 15 Byte):
      • Status der Anfragebearbeitung (E_OK = 0x00, systemspezifische Fehlermeldungen 0x01–0x1F).
    • Payload (variable Größe, Offset 16 Byte):
      • Serialisierte Methodenargumente bzw. Signal- / Datenstrukturen.

3. Dynamisches Verhalten & Sequenzablauf

  • Transmissionspfad (Sender-Seite):
    1. RTE / Applikation: Initiiert Aufruf (ClientServer oder SenderReceiver), vergibt Client ID / Session ID.
    2. SomeIpXf Serialisierung: Transformiert Funktionsparameter in Byte-Array, fügt Request ID, Protocol Version, Interface Version, Message Type und Return Code hinzu.
    3. PDU-Router (PduR): Leitet die Transformer-PDU an das Zielmodul weiter.
    4. SoAd (Socket Adaptor): Ergänzt im Header Mode Message ID und berechnet Length (8 + n Bytes) vor der Übergabe an den TCP/UDP-Socket (TcpIp).
  • Empfangspfad (Receiver-Seite):
    1. SoAd: Evaluiert Message ID zur PDU-Demultiplexierung und validiert die empfangene Length gegen den Socket-Buffer.
    2. PduR: Übergibt Payload ab Byte 8 an die konfigurierte Transformer-Kette.
    3. SomeIpXf Deserialisierung: Validiert Header-Felder (Protocol Version, Interface Version, Message Type, Return Code) und deserialisiert die Payload in applikationsspezifische C-Datentypen. Bei Validierungsfehlern erfolgt Rückmeldung über DET/DEM (SOMEIPXF_E_WRONG_PROTOCOL_VERSION etc.).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur-Vorgabe (SoAd Header Mode):
    • SomeIpXf darf im Classic AUTOSAR-Stack niemals Message ID und Length in den PDU-Puffer schreiben ([SWS_SomeIpXf_00015]). Eine Fehlkonfiguration führt zu redundanten/doppelten Headern im Socket-Buffer.
  • Endianness:
    • Sämtliche Header-Felder müssen in Network Byte Order (Big-Endian / Most Significant Byte first) kodiert werden. Für die Payload ist das Endianness-Attribut pro Datenelement im ARXML-Datenmodell konfigurierbar.
  • Offset-Berechnung für TP (SOME/IP-TP):
    • Wird Transport-Protokoll-Segmentierung genutzt, folgt unmittelbar nach dem Standard-Header (ab Byte 16) ein 4-Byte TP-Header (Offset [28 Bit], Reserved [3 Bit], More Segments Flag [1 Bit]), wodurch sich die eigentliche Payload auf Offset 20 verschiebt.
  • PDU-Buffer-Dimensionierung:
    • Der statische PDU-Puffer in der RTE / im Com-Stack muss exakt um 8 Bytes kleiner dimensioniert werden als das On-Wire-Paket, da Message ID (4 Bytes) und Length (4 Bytes) erst im Socket Adaptor allokiert bzw. vorangestellt werden.
