1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR BSW-Schichtenmodell / Blockschaltbild (Communication Stack Layering Diagram).
  • Technischer Zweck: Das Diagramm spezifiziert die vertikale und horizontale Einbindung des Extended Communication Stacks der AUTOSAR Classic Platform. Es visualisiert den hybriden Betrieb klassischer Feldbusse (CAN, FlexRay, LIN) neben dem paket- und stream-basierten Ethernet-/IP-Stack und definiert die Einbettung des UDP Network Managements (UdpNm) in die generische Netzwerkmanagement- und Modemanagement-Architektur (ComM, Nm, State Manager).

2. Komponenten, Entitäten & Schnittstellen

Schichtenaufteilung (Top-Down nach AUTOSAR-Farbschema)
  1. Application / Runtime Environment (Orange):
    • RTE: Signalübertragung von/zu SWCs; Schnittstellen zu COM, BswM und Communication Manager (ComM).
  2. BSW Services Layer (Violett/Blau):
    • Modemanagement & Koordination:
      • BswM (Basic Software Mode Manager): Modesteuerung, verknüpft mit RTE und DNS-SD.
      • Communication Manager (ComM): Koordiniert Kommunikationszustände; steuert State Manager über Kontrollschnittstellen (orangefarbene Pfade).
      • Generic NM Interface (Nm) inkl. NM Coordinator: Busunabhängige Abstraktionsschicht für das Netzwerkmanagement; aggregiert und koordiniert NM-Zustände.
      • UDP NM Module (UdpNm): Mehrfachinstanziierbar (gestapelte Boxen); implementiert das dezentrale OSEK-ähnliche NM-Protokoll über UDP.
      • Eth State Manager (EthSM), LIN State Manager (LinSM), CAN State Manager (CanSM), FlexRay State Manager (FrSM).
    • Signal- und PDU-Verarbeitung:
      • COM: Signal-/Signal-Group-Serialisierung, Signal-to-PDU-Mapping.
      • IpduM (IPDU Multiplexer): Dynamisches PDU-Multiplexing.
      • DCM (Diagnostic Communication Manager): UDS/OBD-Diagnosedienste.
      • PDU Router (PduR): Zentraler statischer PDU-Router; leitet I-PDUs zwischen oberen Modulen (COM, IpduM, DCM), Transportprotokollen (CAN TP, FlexRay TP), dem SoAd und den Interfaces der Feldbusse (CanIf, FrIf, LinIf) weiter.
    • IP-Kommunikation & Transport:
      • SoAd (Socket Adaptor): Bildet PDU-basierte AUTOSAR-Kommunikation (I-PDU) auf Socket-basierte IP-Kommunikation ab.
      • DoIP (Diagnostic over IP, gestrichelt): Optionales Transportprotokoll für bordexterne Diagnose über IP/TCP.
      • DNS-SD: Service Discovery auf IP-Ebene.
      • TCP/IP-Stack:
        • Transport Layer: UDP (Nachrichten, DNS, DHCP) und TCP (Byte-Streams, TLS).
        • Network/Internet Layer: IP (Datagramme, Pakete/Segmente) mit Hilfsprotokollen ARP und ICMP.
  3. ECU Abstraction Layer / Hardware Abstraction (Grün):
    • Ethernet Interface (EthIf): Abstrahiert Ethernet-Controller und Transceiver; Schnittstelle zum IP-Stack via Datagrammen.
    • FlexRay Interface (FrIf), CAN Interface (CanIf), LIN Interface (LinIf, inkl. LIN TP).
  4. Microcontroller Abstraction Layer - MCAL (Rot):
    • Ethernet Driver (Eth), FlexRay Driver (Fr), CAN Driver (Can), LIN Low Level Driver (Lin).
Datenstrukturen, Informationseinheiten & Kardinalitäten
  • Signale: Interaktion zwischen SWCs und COM über die RTE.
  • I-PDU (Interaction Layer PDU): Zwischen COM/IpduM/DCM und PduR; zwischen PduR und SoAd/CanIf/FrIf/LinIf; sowie zwischen PduR und CAN TP/FlexRay TP.
  • N-PDU (Network PDU): Zwischen Transportprotokollen (CAN TP, FlexRay TP) und den jeweiligen Interfaces (CanIf, FrIf).
  • L-PDU (Data Link Layer PDU): Zwischen Schnittstellen (CanIf, FrIf, LinIf) und MCAL-Treibern.
  • Datagram / Eth-Frame: Datagramme zwischen IP und EthIf; Ethernet-Frames (Eth-Frame) zwischen EthIf und Eth Driver.
  • Kardinalitäten:
    • Nm → UdpNm: 1:n (Mehrkanalbetrieb via generischer Nm-Kanal-Identifikatoren).
    • ComM → State Manager: 1:n (kanalindividuelle Koordination).
    • PduR → Ziel-Module: 1:n (statisches 1:1- oder 1:n-Multicast-PDU-Routing).

3. Dynamisches Verhalten & Sequenzablauf

UdpNm-Sende- und Empfangspfad
  1. Netzwerk-Anforderung (Control Path):
    • SWC/BswM fordert Kommunikationsfreigabe an → ComM bewertet Kanalzustand → Aufruf von Nm_NetworkRequest() → Weiterleitung an UdpNm_NetworkRequest().
    • ComM steuert parallel den EthSM an → EthSM versetzt den Ethernet-Controller/Transceiver über EthIf in den Betriebsmodus (ETH_MODE_ACTIVE).
  2. NM-PDU-Transmission (Data Path):
    • UdpNm erzeugt zyklisch oder eventgetrieben NM-PDUs (inkl. Node-ID, Control Bit Vector und optionaler User Data).
    • UdpNm ruft SoAd_IfTransmit() auf (unter Umgehung des PduR, da UdpNm als IF-User direkt an SoAd angebunden ist).
    • SoAd mappt die PduId auf eine konfigurierte Socket-Verbindung (UDP Multicast/Unicast) → TcpIp_UdpTransmit().
    • Paketierung im IP-Stack → Übergabe als Datagramm an EthIf_Transmit() → Frame-Serialisierung im Eth Driver.
  3. NM-PDU-Reception (Data Path):
    • Rx-Interrupt im Eth Driver → EthIf_RxIndication() → TcpIp_RxIndication() (UDP-Demultiplexing auf Ziel-Port) → SoAd_RxIndication() → UdpNm_SoAdIfRxIndication().
    • UdpNm wertet Algorithmusdaten aus, setzt den NM-Timeout-Timer zurück und meldet Statusänderungen via Nm_NetworkMode() bzw. Nm_PduRxIndication() an Nm und ComM.
  4. Bus-Sleep / Shutdown-Sequenz:
    • Wegfall der Netzwerk-Anforderung (Nm_NetworkRelease()) → UdpNm wechselt in Ready Sleep State.
    • Ablauf des UdpNmTimeoutTime → Übergang in Prepare Bus-Sleep Mode → Bus-Sleep Mode.
    • Benachrichtigung von Nm an ComM → ComM weist EthSM an, das Ethernet-Netzwerk herunterzufahren (EthSM_SetMode(COMM_NO_COMMUNICATION)).

4. Normative Relevanz & Entwickler-Hinweise

  • Architektonische Sonderstellung von UdpNm gegenüber SoAd:
    • Im Gegensatz zu signalbasierten Applikations-PDUs (COM → PduR → SoAd) ist UdpNm direkt als PDU-Interface-Upper-Layer an SoAd angebunden.
    • In der BSW-Konfiguration muss für jede UdpNm-Kanal-Instanz eine korrespondierende SoAdPduRoute (Tx) und SoAdSocketRoute (Rx) konfiguriert werden, die an den dedizierten NM-UDP-Port gebunden ist (Standard-Port: 6834).
  • Multi-Channel & Multi-Instance Handling:
    • Die gestapelte Darstellung des UDP NM Module indiziert strikte Instanzentrennung. Jeder Kanal erfordert eine eigene Konfiguration von UdpNmChannelId, UDP-Sockets und NM-Timern (UdpNmMainFunctionPeriod, UdpNmTimeoutTime, UdpNmMsgCycleTime).
  • Asynchronität & Task-Kontext:
    • Vermeidung von Pufferblockaden: Da UdpNm_SoAdIfRxIndication() aus dem Kontext von TcpIp_MainFunction() oder EthIf_MainFunction() (bzw. Interrupt) aufgerufen werden kann, müssen Callback-Verarbeitungszeiten minimal sein.
    • Datenkonsistenz: NM-User-Data (UdpNm_SetUserData()) erfordert konsistenten Zugriffsschutz über exklusive Bereiche (SchM_Enter_UdpNm), um Datenkorruption bei zyklischer Transmission zu verhindern.
  • DoIP-Koexistenz:
    • DoIP agiert wie dargestellt autark neben PduR und SoAd direkt über TCP/UDP. Eine Aktivierung von Ethernet-Clustern via UdpNm muss zwingend mit Diagnose-Netzwerkanforderungen im ComM koordiniert werden (Vermeidung von voreiligem Bus-Sleep während aktiver DoIP-Sitzungen).
