1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konfigurations- und Metamodell-Übersichtsdiagramm (AUTOSAR EcuC-Struktur- und Mapping-Modell).
  • Technischer Zweck: Darstellung des Entkopplungs- und Normalisierungsansatzes im BSW-Modul V2X Data Manager (V2xDM). Das Modell abstrahiert heterogene, regionsspezifische V2X-Protokollstacks (z. B. ETSI ITS CAM/DENM vs. SAE J2735 BSM) über einen standardisierten internen Datenkatalog und mappt diese auf AUTOSAR-Softwarekomponenten (SWCs) via RTE.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in den EcuC-Konfigurationsbereich des V2xDM und den darüberliegenden AUTOSAR-SWC/RTE-Metamodell-Bereich:

  • Top-Level-Container (V2x DataManager):

Zentrales EcuC-Konfigurationsmodul, das vier logische Sub-Container aggregiert:

  1. V2X message representation:
  • V2x message: Repräsentiert die eingehende protokollspezifische V2X-PDU / -Nachricht.
  • Structured Type & Simple Type(s): Bildet die hierarchische Dekodierungsstruktur der ASN.1-Datentypen ab (primitive Leaf-Nodes vs. komplexe Strukturen/Sequenzen).
  1. V2x "Data Catalog":
  • Data Catalog item: Normalisiertes, stack-agnostisches Datenelement (z. B. OEM-weites Signal wie „Fahrzeuggeschwindigkeit“).
  • $f(x)$ (Conversion Function): Mathematische Transformationsvorschrift (Skalierung, Offset, Auflösungsanpassung), bidirektional mit dem Catalog Item gekoppelt.
  1. V2x Data mapping:
  • Link element: Verknüpfungsentität, die n:1- bzw. 1:1-Relationen zwischen den stack-spezifischen Elementen, den Catalog Items und den Zielprototypen verwaltet.
  1. V2x object representation:
  • VariableDataPrototype: EcuC-seitige Repräsentanz des Ziel-Datenelements.
  • Schnittstelle zur Applikationsebene (außerhalb ECUC):
  • AUTOSAR Foreign Reference (Symbol: Dreieck im Kasten): Zeigt eine typisierte Modellreferenz aus der BSW-EcuC-Konfiguration auf das MSR SW-Component Template (VariableDataPrototype).
  • Sender-Receiver Port & RTE: Klassischer AUTOSAR Sender-Receiver-Kommunikationspfad zur Übergabe der normalisierten Daten an Applikations-SWCs.

3. Dynamisches Verhalten & Sequenzablauf

Obwohl als statisches Konfigurationsmodell dargestellt, induziert die Struktur folgenden synchronen Laufzeit-Datenpfad (z. B. zyklisch in V2xDM_MainFunction oder event-getrieben nach Stack-Indikation):

  1. PDU-Bereitstellung: Empfang der V2X-Botschaft über den regionalen Stack (V2x message).
  2. Signalextraktion: Zugriff auf die konkreten elementaren Datenfelder (Simple Type(s) direkt oder innerhalb von Structured Type).
  3. Transformation: Falls Auflösung oder Einheit abweichen, Ausführung der konfigurierten Umrechnung $f(x)$ zur Überführung in die Zielmetrik des Data Catalog item.
  4. Mapping: Weiterleitung über das Link element an das konfigurierte VariableDataPrototype-Zielobjekt.
  5. RTE-Dispatch: Übergabe an den Sender-Receiver Port via RTE-API (z. B. Rte_Write_<p>_<o>).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration & Variantenmanagement:
  • Ermöglicht die Wiederverwendung identischer Applikations-SWCs über weltweite Märkte hinweg; Anpassungen an regionale Standards (z. B. ETSI vs. SAE vs. GB/T) erfolgen rein deklarativ im EcuC-Modell des V2xDM.
  • Entwickler müssen sicherstellen, dass für jede Variante entsprechende Mapping- und $f(x)$-Konvertierungsregeln (Gleitkomma- vs. Festkomma-Arithmetik) konfiguriert sind.
  • API- & Datenvertrag:
  • SWC-Entwickler arbeiten ausschließlich gegen standardisierte VariableDataPrototypes an Sender-Receiver-Ports; keine Abhängigkeiten zu ASN.1-Typdefinitionen im Applikationscode.
  • BSW-Generatoren erzeugen aus dem Link element effiziente Lookup-Tabellen oder direkte Zuweisungsmakros, um Laufzeit-Overhead im Pfad zwischen V2X-Stack und RTE zu minimieren.

Begleitender Spezifikationstext:

Specification of Vehicle-2-X Data Manager AUTOSAR CP R24-11 One major goal of the V2xDM is to provide a selective view to the V2x message elements contained in the V2x message. Ideally, these V2x message elements are independent from the underlying regional V2x stack and can be provided like a data catalog that contains unified V2x catalog items. For example, a view to the position, speed and heading of a car can be derived from a V2x message. This information can be provided as a unified set of V2x catalog items, independent from the underlying regional V2x stack. But one V2x stack may define the speed with resolution of 1 m/s, the other defines a resolution of 2 m/s. The vehicle database engineer of an OEM decides to provide a unified V2x catalog item "speed" within the vehicle network from the V2x stack with a unit of 1 m/s. This requires a conversion function to be applied in the V2xDM for one specific V2x stack, whereas the speed value of the other can be provided "as is". It depends on the variant which V2x stack and its set of V2x messages are currently used and, depending on this, which sources are used to derive the V2x catalog items. These items are then mapped to the corresponding VariableDataPrototypes of the V2x object. 7.2 Modelling approach To allow greater flexibility, the relations of V2x messages, V2x stack and V2x catalog item are modelled in the EcuC configuration of the V2xDM.
