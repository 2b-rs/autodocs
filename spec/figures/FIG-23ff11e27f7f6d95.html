1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm des AUTOSAR ECUC-Metamodells (Parameter- und Container-Definitionen).
  • Architektur-Kontext: AUTOSAR Classic Platform, BSW-Modul Dem (Diagnostic Event Manager, Services Layer), Submodul Event Memory Management.
  • Technischer Zweck: Modellierung der Konfigurationsstruktur für Speicherbedingungen (Storage Conditions). Dient der selektiven Freigabe oder Sperrung des physikalischen Fehlereintrags (Freeze Frames, Extended Data, DTC-Statusbits wie ConfirmedDTC) bei qualifizierten Events im Event Memory, ohne dabei die Debouncierung oder das Statusbit 0 (TestFailed) zwingend zu deaktivieren (Abgrenzung zu Enable Conditions).

2. Komponenten, Entitäten & Schnittstellen

#### Container & Parameter (EcucParamConfContainerDef / Ecuc*ParamDef)

  • DemGeneral [1..1]: Globaler Modul-Container für systemweite Dem-Konfigurationsparameter.
  • DemStorageCondition [0..255]: Repräsentiert eine diskrete physikalische Speicherbedingung (z. B. Bordnetzspannung innerhalb des zulässigen Fensters). Aggregiert unter DemGeneral via +subContainer.
  • DemStorageConditionId (EcucIntegerParamDef) [1..1]: Numerische ID (min = 0, max = 255, symbolicNameValue = true). Generiert das C-Makro/Symbol für die Laufzeit-API.
  • DemStorageConditionStatus (EcucBooleanParamDef) [1..1]: Initialwert (TRUE = freigegeben, FALSE = blockiert) nach Initialisierung (Dem_Init()).
  • DemStorageConditionGroup [0..255]: Logische Bündelung mehrerer Bedingungen. Aggregiert unter DemGeneral via +subContainer.
  • DemEventParameter [1..65535]: Repräsentiert ein einzelnes diagnostisches Event im BSW-Modul Dem.

#### Referenzen (EcucReferenceDef)

  • DemStorageConditionRef [1..255]: Ausgehend von DemStorageConditionGroup auf DemStorageCondition (+destination). Definiert die für eine Gruppe relevanten Bedingungen.
  • DemStorageConditionGroupRef [0..1]: Ausgehend von DemEventParameter auf DemStorageConditionGroup (+destination). Weist einem Event optional genau eine Gruppe zu.
  • DemStorageConditionReplacementEventRef [0..1]: Ausgehend von DemStorageCondition auf DemEventParameter (+destination). Referenziert ein Ersatz-Event, falls das Primär-Event aufgrund dieser nicht erfüllten Speicherbedingung verworfen wird.

3. Dynamisches Verhalten & Sequenzablauf

  1. Zustandssteuerung über BSW/Applikation:
  • Eine überwachende SW-C oder ein BSW-Treiber (z. B. Spannungsüberwachung) setzt den Status zur Laufzeit synchron über die API:

```c

Std_ReturnType Dem_SetStorageCondition(uint8 StorageConditionId, boolean ConditionFulfilled);

```

  1. Evaluierung bei Event-Qualifizierung:
  • Tritt ein Dem_SetEventStatus(EventId, DEM_EVENT_STATUS_FAILED) auf und qualifiziert sich das Event als defekt:
  • Der Dem prüft die verknüpfte DemStorageConditionGroup.
  • Logische Verknüpfung (SWS_Dem_00591): Alle in der Gruppe referenzierten DemStorageCondition-Instanzen werden strikt UND-verknüpft.
  1. Verzweigung:
  • Gruppe erfüllt (TRUE): Event-Speicherungssequenz wird fortgesetzt (Allokation Primär-/Sekundärspeicher, Freeze Frame Capture, Setzen von Bit 2/3 des Status-Bytes).
  • Gruppe nicht erfüllt (FALSE, SWS_Dem_00459): Das Event wird im Fehlerspeicher blockiert; es erfolgt kein Freeze-Frame-Eintrag.
  • Replacement-Event-Pfad (SWS_Dem_01085, SWS_Dem_01086): Ist an der fehlschlagenden DemStorageCondition ein DemStorageConditionReplacementEventRef hinterlegt, triggert der Dem für dieses Ersatz-Event intern den Status DEM_EVENT_STATUS_FAILED (z. B. Protokollierung von "Unterspannung" anstelle von Kommunikations-Timeout-Folgefehlern).

4. Normative Relevanz & Entwickler-Hinweise

  • Kardinalitäts-Beschränkung:
  • Ein DemEventParameter kann maximal einer Gruppe zugeordnet werden ([0..1]). Mehrfachabhängigkeiten müssen zwingend über eine gemeinsame DemStorageConditionGroup mit mehreren DemStorageConditionRef modelliert werden.
  • Maximal 256 Storage Conditions systemweit (DemStorageConditionId 0..255).
  • Differenzierung Enable vs. Storage Conditions:
  • Enable Condition: Unterdrückt Auswertung und Debouncierung (Event-Status bleibt eingefroren).
  • Storage Condition: Debouncierung läuft weiter, TestFailed (Bit 0) wird gesetzt, aber Speicherung im NvM/RAM und ConfirmedDTC (Bit 3) werden unterdrückt.
  • Architektur-Constraint (Zirkelbezüge / Replacement Events):
  • Das über DemStorageConditionReplacementEventRef referenzierte Event darf selbst nicht von derselben Storage Condition abhängen, um Deadlocks oder unendliche Rekursionen in der Event-Verarbeitungskette des Dem zu verhindern.
  • Reentrancy: Dem_SetStorageCondition ist typischerweise nicht reentrant für dieselbe StorageConditionId. Bei Multicore-Systemen muss der Aufruf thread-sicher über SchTask/BswM oder Master-Core-Routing erfolgen.
