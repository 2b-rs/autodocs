1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Klassendiagramm der AUTOSAR BSW-Modulkonfiguration (ECU Configuration Parameter Definition, ECUC).
  • Architektur-Kontext: Standardisierte Konfigurationsstruktur des BSW-Moduls Watchdog Manager (WdgM) (AUTOSAR Classic Platform, Schicht: System Services) gemäß Release R2.1.20 (basierend auf WdgM SWS v1.0.0, Mai 2006).
  • Funktionale Einordnung: Der WdgM überwacht die zyklische Ausführung von Software-Entitäten (SWCs/BSW) und bedient über das Watchdog Interface (WdgInterface / WdgIf) die hardwarenahen Watchdog-Treiber (Wdg), um bei Kontrollfluss- oder Timing-Anomalien einen gezielten ECU-Reset auszulösen.

3. Dynamisches Verhalten & Sequenzablauf

Aus dem Konfigurationsmodell resultierender Steuer- und Überwachungsablauf zur Laufzeit:

  1. Initialisierung & Moduswahl:
    • Aufruf von WdgM_Init() übergibt Zeiger auf die aktive WdgMConfigEntities-Struktur.
    • Der initiale Modus (WdgMMode: z. B. WDGIF_FAST_MODE während des ECU-Hochlaufs, WDGIF_SLOW_MODE im Normalbetrieb) wird über WdgIf_SetMode() an das Watchdog Interface propagiert.
  2. Zyklische Überwachung (WdgM_MainFunction):
    • Überwachte Entitäten melden ihre Aktivität synchron via WdgM_UpdateAliveCounter() an die jeweilige WdgMAliveSupervision-Instanz.
    • Im Takt der WdgM_MainFunction werden die Zählerstände gegen die konfigurierten Min/Max-Toleranzen abgeglichen.
  3. Trigger-Pfad (Normalbetrieb):
    • Sind alle aktiven WdgMAliveSupervision-Bedingungen erfüllt, setzt der WdgM über die konfigurierten WdgMTrigger-Parameter den Aufruf WdgIf_SetTriggerCondition() ab, um den Hardware-Watchdog zurückzusetzen.
  4. Fehlerpfad (Anomalie/Timeout):
    • Verletzt eine Instanz ihr Alive-Fenster, stoppt der WdgM das Servicing über WdgMTrigger.
    • Bei gesetztem WdgMDemErrorReport == TRUE erfolgt eine asynchrone Fehlermeldung via Dem_ReportErrorStatus().
    • Bei internen API- oder Konfigurationsfehlern erfolgt bei WdgMDevErrorDetect == TRUE ein synchroner Callback an Det_ReportError().
    • Nach Ablauf des Hardware-Watchdogs erzwingt die Hardware einen Reset.

4. Normative Relevanz & Entwickler-Hinweise

  • Historischer Release-Stand (R2.1 / SWS v1.0.0):
    • Das Modell beschränkt sich architektonisch auf die Alive-Supervision. Neuere Konzepte wie Deadline Supervision oder Logical/Program Flow Supervision existieren in diesem Stand noch nicht und dürfen nicht konfiguriert werden.
  • Speicherallokation & Codegenerierung:
    • WdgMGeneral generiert Pre-Compile-Makros in WdgM_Cfg.h (z. B. #define WDGM_DEV_ERROR_DETECT STD_ON/OFF).
    • WdgMConfigEntities wird als Post-Build-fähiges Array (WdgM_PBcfg.c / Flash-Deskriptor) generiert, was Moduswechsel und ECU-Varianten ohne Re-Kompilierung ermöglicht.
  • Sicherheitsvorgaben (Safety / ASIL):
    • WdgMOffModeEnabled darf in funktional sicheren Systemen (ISO 26262) nur aktiviert werden, wenn der WDGIF_OFF_MODE durch ein dediziertes Deaktivierungskonzept (z. B. Standby-Phasen im Power-Management) abgesichert ist. Ein unbeabsichtigtes Setzen von WDGIF_OFF_MODE führt zur dauerhaften Deaktivierung der Hardware-Überwachung.
  • Schnittstellenkonsistenz:
    • WdgIfRef erzwingt eine direkte Kopplung an das WdgIf. Die im WdgM konfigurierten Modi (WDGIF_SLOW_MODE, etc.) müssen 1:1 mit den im Watchdog-Treiber unterstützten Hardware-Modi und Timing-Fenstern übereinstimmen.
