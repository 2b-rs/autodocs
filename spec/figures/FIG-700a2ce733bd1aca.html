1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Bit- und Byte-Layout (Protokolldatenstruktur / N-PDU Frame-Format).
  • Architektur-Kontext: AUTOSAR Classic Platform, Communication Stack, Modul FrArTp (FlexRay AUTOSAR Transport Layer), angesiedelt zwischen dem PDU Router (PduR) und dem FlexRay Interface (FrIf).
  • Technischer Zweck: Spezifikation des Frame-Formats für den First Frame (FF) im Betriebsmodus ISO 15765-2 (CAN-Transportprotokoll-Emulation über FlexRay gemäß SWS_FrArTp_00237). Dient der Einleitung segmentierter Multi-Frame-Übertragungen, wenn die Gesamtgröße der zu übertragenden N-SDU die maximale Nutzlastkapazität eines Single Frames (SF) überschreitet.

2. Komponenten, Entitäten & Schnittstellen

  • Protokoll-Felder & Datenstrukturen:
    • N-PDU Gesamtstruktur: Besteht aus 2 Byte PCI (Protocol Control Information) gefolgt vom Nutzdatenbereich (Data).
    • PCI (2 Byte / 16 Bit Header, Network Byte Order / Big Endian):
      • FT (Frame Type, 4 Bit, Bits 15..12): Kodiert den N-PDU-Typ. Für First Frame zwingend auf binär 0001 (0x1) gesetzt (SWS_FrArTp_00034).
      • DL (Data Length, 12 Bit, Bits 11..0): Kodiert die Gesamtlänge der unsegmentierten N-SDU in Bytes (SWS_FrArTp_00035). Wertebereich: 8 ≤ DL ≤ 4095 Bytes (0x008 bis 0xFFF).
    • Data (Payload):
      • Länge: Konfigurationsabhängig (Length depending on configuration). Bestimmt durch die konfigurierte PDU-Größe des zugrundeliegenden FlexRay-Slots (FrIfPduLength) abzüglich der 2 Byte PCI: Payload-Länge = PduLength - 2.
      • Trägt die ersten N Bytes der zu übertragenden N-SDU (SWS_FrArTp_00036).
  • Schnittstellen:
    • PduR_FrArTpCopyTxData() / PduR_FrArTpStartOfReception(): Austausch der Payload zwischen FrArTp-Puffer und oberen Schichten (z. B. Dcm).
    • FrIf_Transmit() / FrArTp_RxIndication(): PDU-Übergabe an bzw. vom FlexRay Interface.

3. Dynamisches Verhalten & Sequenzablauf

  • Senderseite (TX-Pfad):
    1. Trigger: FrArTp_Transmit() wird von der oberen Schicht (z. B. PduR) mit einer Nutzlastlänge > SF_DL aufgerufen.
    2. Assembly & Pufferabfrage: FrArTp konstruiert den 2-Byte-PCI (FT=0x1, DL=SduLength), ruft PduR_FrArTpCopyTxData() auf, um die ersten (FrIfPduLength - 2) Bytes in den Übertragungspuffer zu kopieren, und setzt FrIf_Transmit().
    3. Timer-Start: Mit Senden des FF (bzw. Empfang von FrArTp_TxConfirmation()) wird der Timeout-Timer N_Bs (Warten auf Flow Control Frame) gestartet.
  • Empfängerseite (RX-Pfad):
    1. Trigger: FrArTp_RxIndication() liefert eine PDU mit FT == 0x1.
    2. Plausibilitätsprüfung: Validierung von DL. Ist DL ≤ SF_DL oder DL > 4095, wird der Frame verworfen und ein Fehler an Det gemeldet (SWS_FrArTp_00299).
    3. Pufferallokation: Aufruf von PduR_FrArTpStartOfReception(). Meldet der PduR BUFREQ_OK, werden die im FF enthaltenen Daten via PduR_FrArTpCopyRxData() übergeben.
    4. Ablaufsteuerung: Der Empfänger initiiert das Senden eines Flow Control (FC) Frames (CTS, WAIT oder OVFLW) zurück an den Sender (SWS_FrArTp_00037).
  • Abbruchbedingungen:
    • Ablauf von Timer N_Bs vor Empfang eines gültigen FC-Frames führt zum sofortigen Übertragungsabbruch und Callback PduR_FrArTpTxConfirmation(E_NOT_OK).
    • Rückmeldung von BUFREQ_E_OVFLW beim Empfang führt zum Senden eines FC(OVFLW) und Abbruch.

4. Normative Relevanz & Entwickler-Hinweise

  • Protokollmodus-Konfiguration:
    • Der Parameter FrArTpProtocolType der Verbindung muss explizit auf ISO 15765-2 (im Gegensatz zu ISO 10681-2 FlexRay TP) konfiguriert sein.
  • PDU-Größen & Padding:
    • Die konfigurierte PDU-Länge im FlexRay-Cluster muss mindestens 3 Byte betragen (2 Byte PCI + mindestens 1 Byte Daten).
    • Da FlexRay im statischen Segment feste Frame-Längen erzwingt, greifen bei unvollständiger Belegung die Konfigurationsparameter für Padding (FrArTpTxPaddingActivation).
  • Bit-Manipulation im Treiber/Stack (Big-Endian-Extraktion):
    • Bit-Extraktion für den 16-Bit-Header im C-Treiber: 
      uint8 frameType = (pduBuf[0] >> 4) & 0x0F;
uint16 dataLength = ((uint16)(pduBuf[0] & 0x0F) << 8) | (uint16)pduBuf[1];
  • Begrenzung:
    • Das 12-Bit-DL-Feld limitiert segmentierte Nachrichten in diesem Modus strikt auf maximal 4095 Bytes Nutzdaten. Für größere Diagnosenachrichten muss entweder ISO 10681-2 (32-Bit-Längenangabe) oder die erweiterte Adressierung nach ISO 15765-2:2016 verwendet werden.
