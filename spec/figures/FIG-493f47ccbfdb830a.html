1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Objekt-/Instanzendiagramm zur Veranschaulichung von M1-Modellinstanzen (AUTOSAR Metamodell M2 auf Instanzebene M1).
  • Architektur-Kontext:
    • Das Diagramm stellt das Zusammenspiel zwischen der BSW-Modulbeschreibung (BSW Module Description / BSWMD) des Kommunikations-Stacks (COM) und den ECU-Konfigurationswerten des Memory-Mapping-Moduls (MemMap ECUC) dar.
    • Technischer Zweck: Abbildung von BSW-Callout-Funktionen (Com_TxIpduCallout, Com_RxIpduCallout) auf Speicherbereiche über eine generische Software-Adressierungsmethode (SwAddrMethod). Es demonstriert die Entkopplung von modulspezifischen MemorySection-Definitionen des BSW-Zulieferers von der projektspezifischen Linker-Sektionsallokation des Integrators mittels MemMapGenericMapping.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert sich in zwei Namensräume / Pakete:

A. Bsw Module Description (BSWMD / MSR)
  • COM :BswModuleDescription (Attribut: category = BSW_MODULE):
    • Wurzelelement der Modulbeschreibung des AUTOSAR COM.
    • +outgoingCallback: Assoziiert externe Callout-Funktionsdeklarationen (BswModuleEntry).
    • +internalBehavior: Komposition auf das interne Modulverhalten.
  • Com_TxIpduCallout :BswModuleEntry & Com_RxIpduCallout :BswModuleEntry:
    • Deklaration der Funktionsprototypen für Tx- bzw. Rx-IPDU-Callouts, die vom COM aufgerufen, aber extern (z. B. in Applikation oder Integrations-Code) implementiert werden.
  • COM :BswInternalBehavior:
    • Kapselt Algorithmen, Tasks und interne Schnittstellen des COM-Moduls.
    • +behavior: Assoziation von BswImplementation.
  • COM :BswImplementation:
    • Repräsentiert die Auslieferungseinheit des Quell-/Objektcodes.
    • +resourceConsumption: Komposition auf Ressourcenbeschreibungen.
  • COM :ResourceConsumption:
    • Beschreibt den statischen Ressourcenbedarf (Speicher, Stack, Register).
    • +memorySection: Kompositionen auf die deklarierten Speichersektionen.
  • COM_TXIPDUCALLOUT_CODE :MemorySection & COM_RXIPDUCALLOUT_CODE :MemorySection:
    • Modulspezifische Sektionsdeklarationen des COM für die Callout-Funktionsdeklarationen.
    • +swAddrMethod: Referenzieren beide dieselbe SwAddrMethod.
  • CALLOUT_CODE :SwAddrMethod (Attribut: sectionType = code):
    • Standardisierte, modulübergreifende Adressierungsmethode zur Kennzeichnung von Callout-Code.
B. MemMap Ecu Configuration Values (ECUC)
  • MemMap :EcucModuleConfigurationValues (Attribut: implementationConfigVariant = VariantPreCompile):
    • Konfigurationssatz des MemMap-Moduls.
  • CNF_DEFAULT :EcucContainerValue (definition = MemMapAllocation):
    • Allokationscontainer zur Definition der Speicherplatzierungsregeln.
  • CNF_SEC_CALLOUT_CODE :EcucContainerValue (definition = MemMapGenericMapping):
    • Generische Mapping-Regel, die auf alle MemorySection-Elemente matcht, welche die referenzierte SwAddrMethod nutzen.
    • +referenceValue (definition = EcucMemoryMappingSwAddrMethodRef): Verweist paketübergreifend auf CALLOUT_CODE :SwAddrMethod.
    • +referenceValue (definition = MemMapAddressingModeSelection): Verweist auf den gewählten Adressierungsmodus.
  • CODE_INTERNAL :EcucContainerValue (definition = MemMapAddressingModeSet):
    • Bündelt logische Adressierungsmodi.
  • CODE_INTERNAL :EcucContainerValue (definition = MemMapAddressingMode):
    • Konkreter Adressierungsmodus (definiert Compiler-Pragmas, Sektionspräfixe/Linker-Sektionen wie z. B. .text.internal_code).

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Metamodell-/Konfigurationsdiagramm handelt, liegt kein Laufzeitablauf vor, sondern eine Kette von Modellierung über Codegenerierung bis zur Linker-Auflösung:

[BSWMD: COM Module]
  -> deklariert COM_TXIPDUCALLOUT_CODE / COM_RXIPDUCALLOUT_CODE
  -> taggt beide mit swAddrMethod = CALLOUT_CODE
       │
       ▼
[ECUC: MemMap Module Configuration]
  -> MemMapGenericMapping referenziert SwAddrMethod 'CALLOUT_CODE'
  -> bindet diese an AddressingMode 'CODE_INTERNAL'
       │
       ▼
[Build- & Generierungszeit]
  -> Generator erzeugt MemMap-Header (MemMap.h / Com_MemMap.h)
  -> Makros #define COM_START_SEC_TXIPDUCALLOUT_CODE / COM_STOP_SEC_...
  -> Auflösung der Sektionen auf die Compiler-Pragmas von 'CODE_INTERNAL'
       │
       ▼
[Kompilierung & Link-Zeit]
  -> Callout-Funktionsdeklarationen und -Aufrufe werden in die durch
     CODE_INTERNAL definierte Linker-Sektion platziert.

4. Normative Relevanz & Entwickler-Hinweise

  • Vermeidung redundanter Konfiguration: Durch den Einsatz von MemMapGenericMapping anstelle von modulspezifischem MemMapSectionSpecificMapping muss der Integrator nicht jede BSW-Sektion einzeln mappen. Alle Sektionen mit SwAddrMethod = CALLOUT_CODE folgen automatisch der zentralen Zuweisung auf CODE_INTERNAL.
  • BSW- vs. Applikations-Scope bei Callouts: Callouts werden innerhalb der Header des BSW deklariert (outgoingCallback), der tatsächliche Funktionskörper wird jedoch typischerweise im Integrationscode/Applikationskontext implementiert. Die hier konfigurierte MemorySection steuert primär die Deklarationskapselung im BSW-Header über MemMap-Inkludierungen.
  • MemMap-Präprozessor-Konvention:
    • Im C-Code des COM-Treibers erfolgt die Umschließung via: 
      #define COM_START_SEC_TXIPDUCALLOUT_CODE
#include "Com_MemMap.h"
boolean Appl_ComTxIpduCallout(PduIdType PduId, const PduInfoType* PduInfoPtr);
#define COM_STOP_SEC_TXIPDUCALLOUT_CODE
#include "Com_MemMap.h"
  • MPU- & Speicherschutz-Auswirkungen: Soll ein Callout in einer unprivilegierten Task oder Partition ausgeführt werden, erlaubt die separate SwAddrMethod = CALLOUT_CODE dem Integrator, den Adressierungsmodus gezielt auf eine Sektion mit passenden Speicherschutzattributen umzubiegen, ohne den Core-Code von COM zu modifizieren.
