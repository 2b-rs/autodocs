1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Aktivitätsdiagramm (Ausführungsmodell / Mapping-Modell).
  • Architektur-Kontext: AUTOSAR Classic Platform, Runtime Environment (AUTOSAR_SWS_RTE), Kapitel 4 (RTE Concepts / Task Mapping).
  • Technischer Zweck: Visualisierung des Mappings nicht-blockierender Category 1 Runnable Entities auf AUTOSAR OS Basic Tasks. Dargestellt werden die Einbettung eines einzelnen Runnables (links) sowie die sequentielle Kaskadierung mehrerer Runnables (rechts) innerhalb eines Basic-Task-Ausführungskontexts.

2. Komponenten, Entitäten & Schnittstellen

  • OS Basic Task (äußerer oranger Container): AUTOSAR OS Task ohne Extended-Task-Eigenschaften (besitzt die Zustände Suspended, Ready, Running, jedoch keinen Zustand Waiting).
  • Category 1 RunnableEntity (Cat 1, graue Rechtecke):
    • SWC-Ausführungseinheit ohne interne Blockierpunkte (Wait-Points).
    • Verwendet keine blockierenden RTE-APIs (kein Rte_Feedback, kein blockierendes synchrones Client-Server Rte_Call, kein WaitEvent).
  • RTE Glue Code / Task Wrapper (schmale orange Balken):
    • Prolog / Task Entry: Initialisierung des lokalen Ausführungskontexts, Einlesen und Zwischenspeichern von Port-Daten (z. B. implizite Read-Pufferung Rte_IRead), Setzen von Statusflags.
    • Inter-Runnable / Zwischenschritte: Lokale Datenkonsistenzsicherung, Pufferübergabe zwischen sequentiell gekoppelten Runnables, ggf. Rücksetzen von RTE-Events.
    • Epilog / Task Exit: Schreiben und Flush gepufferter Ausgangsdaten (z. B. implizites Schreiben Rte_IWrite), Bereinigung und Aufruf von TerminateTask().
  • Kardinalitäten & Mapping-Beziehungen:
    • Linker Pfad: 1:1-Mapping ($1 \text{ Basic Task} \rightarrow 1 \text{ Category 1 RunnableEntity}$).
    • Rechter Pfad: 1:n-Mapping ($1 \text{ Basic Task} \rightarrow n \text{ Category 1 RunnableEntities}$, deterministisch sequentiell geordnet).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialer Knoten (Black Dot / Task-Aktivierung): Task-Aktivierung erfolgt über das Betriebssystem via Alarm, Schedule Table oder API-Aufruf (ActivateTask()).
  2. RTE-Prolog: Vorabverarbeitung (Einlesen von Kommunikationspuffern, Konsistenzschutz bei implizitem Lese-Zugriff).
  3. Ausführung Runnable 1: Synchroner Funktionsaufruf des C-Symbols der Runnable Entity durch die RTE. Die Ausführung läuft deterministisch von Start bis Return (Run-to-Completion).
  4. Sequentielle Verkettung (rechter Pfad): Nach Rückkehr von Runnable 1 führt die RTE erforderliche Pufferaktualisierungen durch und ruft unmittelbar Runnable 2 auf demselben Task-Stack auf.
  5. RTE-Epilog: Übertragen modifizierter Werte an nachgelagerte Schichten (COM, inter-partition Queues) und Abschluss der Task-Transaktion.
  6. Aktivitäts-Endknoten (Bullseye / TerminateTask): Geordnetes Beenden des Tasks via OS-API TerminateTask(), Task wechselt in Zustand Suspended.

4. Normative Relevanz & Entwickler-Hinweise

  • Stack- und Ressourceneffizienz:
    • Basic Tasks teilen sich im AUTOSAR OS im Gegensatz zu Extended Tasks bei entsprechender Konfiguration denselben Single-Stack-Bereich für Tasks gleicher Priorität, was den RAM-Bedarf massiv senkt.
    • Das Verkettungsmuster (1:n) minimiert Context-Switching-Overhead und OS-Task-Deskriptor-Bedarf bei Runnables mit identischer Periode/Trigger-Bedingung.
  • Restriktionen für SWC-Entwickler:
    • In Category 1 Runnables dürfen ausschließlich nicht-blockierende Kommunikationsprimitive verwendet werden: Implizite/explizite S/R-Kommunikation (Rte_IRead/Rte_Read, Rte_IWrite/Rte_Write), asynchrone C/S-Aufrufe (Rte_Call mit asynchronem Rückgabemodell) oder synchrone Aufrufe ohne internes Warten auf OS-Events.
    • Verletzung führt zu Deadlocks oder Compiler-/Generierungsfehlern im RTE-Generator, da ein Basic Task keinen WaitEvent-Aufruf ausführen darf.
  • Konfigurationsaspekte (ARXML / RTE-Generator):
    • Die Konfiguration erfolgt über RteEventToTaskMapping: Mappings von TimingEvent, DataReceivedEvent etc. auf Tasks mit OsTaskSchedule = NON oder FULL und fehlenden OsTaskEventRef-Zuweisungen.
    • Bei Verkettung mehrerer Runnables in einem Task steuert die Eigenschaft positionInTask die exakte Reihenfolge zur Vermeidung von Race Conditions bei Inter-Runnable-Kommunikation.

The ECU Configuration-Template has to provide the sequence of RunnableEntitys mapped to the same task, see RtePositionInTask. Figure 4.12 shows the possible mappings of RunnableEntitys into a basic task. If and only if a sequence order is specified, more than one RunnableEntity can be mapped into a basic task. If an extended task is used, the entry points to the different RunnableEntitys might be distinguished by evaluation of different OS events. In the scenario above, the different activation periods may be provided by different OS alarms. The corresponding OS events have to be handled inside the task body. Therefore the RTE-generator needs for each task the number of assigned OS Events and their names.
