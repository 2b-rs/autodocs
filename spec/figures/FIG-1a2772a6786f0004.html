1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Tabellarische Spezifikations- und Austauschmatrix (Excel-basiertes Definitionsblatt Sheet 11_DataTypes_Record) zur standardisierten Modellierung zusammengesetzter AUTOSAR-Datentypen im Rahmen der AUTOSAR Application Interfaces (AI).
  • Technischer Zweck: Formale Definition domänenspezifischer Verbund-Datentypen (ApplicationRecordDataType bzw. ImplementationDataType der Kategorie STRUCTURE) für Karosserie-/Schließsysteme (Central Locking, CL).
  • Architektur-Einordnung: Dient als normative Eingangsbasis für den AUTOSAR-Tooling-Workflow. Die tabellarischen Parameter werden in ARXML-Metamodell-Beschreibungen (MSR SWC-Metamodell) transformiert und bilden die Basis für Port-Schnittstellen (SenderReceiverInterface, NvDataInterface) der Software-Komponenten (SWCs) sowie die C-Typdefinitionen (typedef struct) der RTE.

2. Komponenten, Entitäten & Schnittstellen

Metamodell-Mapping & Stereotypen
  • Container-Ebene: Bildet auf AUTOSAR::AUTOSAR::M2::AUTOSARTemplates::SWComponentTemplate::Datatype::Datatypes::ApplicationRecordDataType ab (bzw. auf ImplementationDataType mit category = STRUCTURE).
  • Element-Ebene: Bildet auf ApplicationRecordElement ab, referenziert über die Assoziation element (aggregation, Kardinalität 1..*).
  • Typ-Referenz: Jedes Record-Element instanziiert einen Basistyp über type («isOfType»), der auf ein ApplicationPrimitiveDataType oder einen weiteren ApplicationRecordDataType verweist.
Spezifizierte Record-Entitäten
  1. LockgCenSts1 (Long Name: Locking Central Status)
    • Beschreibung: Status der Zentralverriegelung inklusive Ausfallbehandlung („undefined“ bei fehlenden Rückmeldeschaltern im Schloss und Informationsverlust im Steuergerät).
    • Elementanzahl: 2
    • Elemente:
      • LockgSt (Typ: LockSts2, Ref: CL): Status der Verriegelung.
      • TrigSrc (Typ: LockTrigSrc1, Ref: CL): Auslösende Quelle der Verriegelungsanforderung.
  2. DiagcLock1 (Long Name: Diagnostic Lock)
    • Beschreibung: Diagnoseinformation zum Funktionszustand des Schließsystems.
    • Elementanzahl: 2
    • Elemente:
      • Lock (Typ: LockActvn1, Ref: CL): Zustand der Verriegelungsbetätigung.
      • Diagc (Typ: OnOff1, Ref: CL): Binärer Diagnosestatus.
  3. DiagcChdProtn1 (Long Name: Diagnostic Child Protection)
    • Beschreibung: Diagnosezustand der Kindersicherung (Mechanismus/Aktor intakt oder fehlerhaft).
    • Elementanzahl: 2
    • Elemente:
      • ChdProtn (Typ: ChdProtnCmd1, Ref: CL): Kommando-/Statuswert der Kindersicherung.
      • Diagc (Typ: OnOff1, Ref: CL): Binärer Diagnosestatus.
Metadaten-Attribute

  • Milestone: S5MS4 (Reifegrad-/Release-Tracking-Meilenstein).
  • Reference: CL (Central Locking, Zuordnung zur Funktionsdomäne Body/Comfort).

3. Dynamisches Verhalten & Sequenzablauf

Als statische Datentyp-Spezifikation existiert kein eigenständiger Zustands- oder Kontrollflussdiagramm-Ablauf. Das Laufzeitverhalten manifestiert sich in der Interaktion mit RTE und BSW:

  • RTE-Datenaustausch:
    • Bei Nutzung in SenderReceiverInterface: Bereitstellung via Call-by-Reference-APIs Rte_Write_<p>_<o>(const LockgCenSts1* data) und Rte_Read_<p>_<o>(LockgCenSts1* data).
    • Atomarität: Da es sich um Multi-Element-Strukturen handelt, erzwingt die RTE bei intra-ECU-Task-Grenzen oder unteilbaren Signalgruppen exklusive Bereiche (ExclusiveArea / Task-Sperren), um Inkonsistenzen zwischen Elementen (z. B. LockgSt passt nicht zu TrigSrc) zu verhindern.
  • Com-Stack-Serialisierung:
    • Auf BSW-Ebene werden die Record-Elemente im COM-Modul über ComSignalGroup aggregiert. Die Übertragung erfolgt konsistent über Signal-Group-Shadow-Buffer (Com_SendSignalGroup / Com_ReceiveSignalGroup).
  • Fehler- und Ausfallpfade:
    • Das Attribut Description von LockgCenSts1 definiert eine fachliche Abbruch-/Ersatzwertlogik: Geht die Positionsrückmeldung (Feedback Switches) verloren, muss die SWC den Statuszustand undefined aktiv propagieren (Mapped auf Invalid Value / Init Value im ARXML).

4. Normative Relevanz & Entwickler-Hinweise

  • C-Typdefinition (RTE Contract Phase): Der RTE-Generator erzeugt aus den Datentypen plattformspezifische Structs in Rte_Type.h: 
    typedef struct {
    LockSts2 LockgSt;
    LockTrigSrc1 TrigSrc;
} LockgCenSts1;

typedef struct {
    LockActvn1 Lock;
    OnOff1 Diagc;
} DiagcLock1;

typedef struct {
    ChdProtnCmd1 ChdProtn;
    OnOff1 Diagc;
} DiagcChdProtn1;
  • Memory-Alignment & Struct-Padding:
    • Compiler- und Architekturspezifische Alignment-Vorgaben (8/16/32-Bit) können Padding-Bytes innerhalb der C-Struktur erzeugen.
    • Für die Netzübertragung (CAN/LIN/Ethernet) darf kein ungeprüftes Memory-Copying (memcpy) auf PDUs erfolgen. Es ist zwingend das BSW-COM-Signal-Packing oder ein AUTOSAR-Transformer (SOME/IP-Transformer, E2E-Transformer) zu konfigurieren, um Endianness- und Alignment-Diskrepanzen zwischen Sender und Empfänger auszuschließen.
  • DataTypeMapping:
    • Da die Tabelle Application Data Types (ADT) abbildet, müssen Integratoren in der Software-Kompositionsphase ein DataTypeMappingSet bereitstellen, welches die abstrakten ADTs auf konkrete ImplementationDataTypes (z. B. uint8, boolean oder Fixed-Point) inklusive CompuMethod (Semantik/Skalierung) und DataConstraint abbildet.
