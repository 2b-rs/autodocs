1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Datenfluss- und Prozessarchitekturdiagramm (Toolchain- und Testsystem-Topologie).
  • Technischer Zweck: Spezifikation des standardisierten AUTOSAR Conformance Test Systems (CTS) für ein einzelnes Basissoftware-Modul (M) in den Classic-Platform-Releases R3.x.
  • Funktionale Einordnung: Definiert die zweistufige Konformitätsprüfung (statische XML-Metadatenprüfung vs. dynamische Target-Ausführung via TTCN-3). Das System trennt strikt zwischen Vendor-Lieferbestandteilen (grüner Rahmen), dem Testsystem/Host-Tester (oberer Block), dem automatisierten Build-Prozess (unterer linker Block) und dem physischen Zielsystem (System-Under-Test, SUT, unterer rechter Block).

2. Komponenten, Entitäten & Schnittstellen

A. Externe Vendor-Artefakte (SUT-Lieferumfang, links)
  • ICS (.xml) (Implementation Conformance Statement): Formale Erklärung des Herstellers über implementierte Pflicht- und optionale Features des Moduls M.
  • BSW Module Description (.xml) (BSWMD): Formale Metadatenbeschreibung gemäß AUTOSAR-Metamodell (Parameterdefinitionen, Multiplizitäten, Schnittstellen, Callbacks, Memory Sections).
  • Values for Vendor-specific Parameters (.xml): Konfigurationswerte für herstellerspezifische Parameter, die außerhalb des standardisierten Parametersatzes liegen.
  • Static Implementation Files (.h / .c / .o): Quellcode- und vorkompilierte Binärdateien des Moduls M.
  • Module Generator Tool: Herstellereigener Codegenerator, der aus der ECUC-Beschreibung die implementationsspezifischen Artefakte erzeugt.
  • Configuration Dependent Files: Modulkonfigurationsquelltexte (<Module>_Cfg.h, <Module>_Cfg.c, <Module>_PBcfg.c).
B. Tester-Subsystem (Tester, Host-Umgebung)
  • CTSpec for Module “M”: Formale Referenz-Prüfspezifikation (Regelwerk und Testfallbasis des AUTOSAR-Konsortiums für Modul M).
  • “Checks”: Statische Validierungs-Engine. Führt Konsistenzprüfungen zwischen ICS, BSWMD, Herstellerparametern und CTSpec durch; speist Steuerdaten in den Build-Prozess ein.
  • Configuration Generation: Leitet aus den Testanforderungen die standardisierte ECU Configuration Description (.xml) (ARXML) ab.
  • Test Cases: Parametrierte, ausführbare Testfallbeschreibungen.
  • Test Execution (TTCN-3 tooling) / SUT Adapter: TTCN-3-Laufzeitumgebung (Testing and Test Control Notation version 3) zur Ablaufsteuerung, Stimuligenerierung und Response-Validierung; hostseitiger Kommunikationsadapter zum Target.
  • Target Test Adapter (.c / .h): Tester-seitig generierte Quellcode-Stubs/Treiber für die Zielplattform (bedient Upper-/Lower-Layer-APIs von Modul M).
C. Build- und Zielsystem-Entitäten
  • Configuration & Build Process for Module “M”:
    • Configuration Tooling: Nimmt die generierte ECU Configuration Description entgegen und triggert das Vendor-spezifische Module Generator Tool.
    • Configured Compile & Link System: Cross-Compiler/Linker-Toolchain. Bindet Static Implementation Files, Configuration Dependent Files und Target Test Adapter (.c / .h) zu einem lauffähigen Target-Image.
  • System-Under-Test (SUT):
    • Executable BSW Module “M”: Das im Fokus stehende kompilierte Modul.
    • Target Adapter for Module “M”: Target-seitige Kommunikationsschicht (Hardware-Abstraktion, Stubs für OS/Schichten, z. B. CanIf/Det).
    • Target Hardware: Mikrocontroller-/Evaluierungsboard.
D. Schnittstellen & Test-Artefakte
  • Bidirektionaler Testkanal (dicker Pfeil): Physikalische Verbindung (z. B. CAN, Ethernet, UART oder Debug-Interface) zwischen Host-SUT Adapter und Target Adapter for Module “M”.
  • Verdicts (Outputs):
    1. Statisches Verdict: Unmittelbares Ergebnis der Metadaten-/ICS-Validierung (Checks).
    2. Dynamisches Verdict: Qualifiziertes Testergebnis (Pass, Fail, Inconclusive) aus der TTCN-3-Laufzeitauswertung.

3. Dynamisches Verhalten & Sequenzablauf

  1. Statische Verifikation (Prä-Build-Phase):
    • Bereitstellung von ICS, BSWMD und Vendor-Parametern an den Tester.
    • Checks-Engine verifiziert Syntax, Semantik und Konformität gegen die CTSpec.
    • Abbruchbedingung: Ungültige Parametereinstellungen oder ICS-Diskrepanzen erzeugen sofort ein negatives statisches Conformance Test Verdict.
  2. Generierung der Test-Konfiguration:
    • Aus den selektierten Testfällen der CTSpec generiert Configuration Generation eine testspezifische ECU Configuration Description (.xml) und übergibt die zugehörigen Test Cases an das TTCN-3-Tool.
    • Bereitstellung des passenden Target Test Adapter (.c / .h).
  3. Modulgenerierung & Build-Prozess:
    • Das Module Generator Tool parst die ECU Configuration Description und emittiert Configuration Dependent Files.
    • Der Cross-Compiler/Linker übersetzt statische BSW-Dateien, generierten Code sowie den Target Test Adapter und linkt das Binär-Image.
  4. Target-Deployment & Initialisierung:
    • Download/Flashen des Binär-Images auf die Target Hardware.
    • Initialisierung des Target-Adapters und Eintritt des Moduls M in den initialen Betriebsmodus.
  5. Dynamische Testausführung (TTCN-3-Schleife):
    • TTCN-3 Runner stimuliert das Modul M über den SUT-Adapter und den Target-Adapter (synchron über direkte API-Calls oder asynchron über Bus-/Event-Triggermechanismen).
    • Der Target-Adapter fängt Rückgabewerte, Callback-Aufrufe sowie Det-Fehlermeldungen ab und spiegelt sie an das TTCN-3-Tool zurück.
    • Dynamische Verdict-Ermittlung anhand der Soll-/Ist-Spezifikation der CTSpec.

4. Normative Relevanz & Entwickler-Hinweise

  • BSWMD/ARXML-Striktheit: Die BSW Module Description muss zwingend schema- und metamodellkonform zur Ziel-AUTOSAR-Releaseversion sein. Nicht deklarierte Parameter oder falsche Multiplizitäten scheitern bereits in den vorgelagerten statischen Checks, bevor ein Build ausgelöst wird.
  • Isolierte Modul-Testbarkeit (Stubbarkeit): Modul M darf keine zyklischen oder impliziten Link-Abhängigkeiten zu realen Nachbarmodulen (z. B. OS, Det, Dem, SchM oder benachbarten BSW-Modulen) aufweisen. Alle externen Service- und Modul-Schnittstellen müssen sauber gegen den Target Test Adapter linkbar sein.
  • Deterministisches Scheduling: Da die Ausführung über TTCN-3 getriggert wird, müssen zyklische Funktionen (<Module>_MainFunction()) explizit und deterministisch durch den Target Test Adapter aufgerufen werden können (entkoppelt von einem produktiven OS-Schedule).
  • Post-Build vs. Pre-Compile Parameter: Das Modul muss in der Lage sein, Konfigurationsänderungen ausschließlich über die vom Testsystem generierte ECU Configuration Description abzubilden. Manuelle Eingriffe in <Module>_Cfg.h oder hardcodierte Header-Overrides sind unzulässig und führen zu inkonsistenten Testergebnissen.
