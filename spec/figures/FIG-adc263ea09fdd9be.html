1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Schichtenmodell / Statischer API-Aufrufbaum (Call Tree) mit funktionaler Pfadtrennung (Job-based vs. Direct API).
  • Technischer Zweck: Darstellung der Schnittstellenarchitektur des AUTOSAR Crypto Stacks (Classic Platform) über drei Abstraktionsebenen:
  1. CSM (Crypto Service Manager, Service Layer, BSW)
  2. CryIf (Crypto Interface, Abstraktionsschicht zur Treiber-Entkopplung)
  3. Crypto (Crypto Driver, MCAL / hardware- oder softwarebasierte Ausführungsschicht)
  • Funktionale Einordnung: Entkopplung kryptografischer Operationen (Berechnungen, Verschlüsselung, Signaturen) von administrativen Schlüsselverwaltungsoperationen (Key Management).

2. Komponenten, Entitäten & Schnittstellen

#### Schichten (vertikal von oben nach unten)

  • CSM (Blau/Violett): BSW-Dienstkomponente; stellt die applikationsnahe Schnittstelle (C-API und RTE-Service-Ports) bereit.
  • CryIf (Grün): Vermittlungs- und Abstraktionsschicht; routet Anfragen anhand logischer Channel- und Key-IDs an den zuständigen Treiber.
  • Crypto Driver (Rot/Koralle): MCAL-/Treiberebene; greift auf Hardwarebeschleuniger (HSM, SHE, Secure Core) oder Software-Krypto-Bibliotheken zu.

#### Pfad 1: Job based API (Kryptografische Nutzoperationen)

  • CSM-Ebene: Diskrete Funktionsaufrufe für kryptografische Primitive:
  • Csm_Hash()
  • Csm_MacGenerate() / Csm_MacVerify()
  • Csm_Encrypt() / Csm_Decrypt()
  • Csm_JobKeySetValid()
  • Zentrale Datenstruktur: Csm_JobType / Crypto_JobType
  • Aggregiert Job-ID, Primitiv-Konfiguration (CsmPrimitives), Priorität, Zustand, Puffer-Referenzen (Input/Output/Secondary Input) sowie die Referenz auf den im Treiber liegenden Schlüssel.
  • Schnittstellentrichter:
  • CSM kapselt den Primitiv-Aufruf in die Struktur job und delegiert an CryIf_ProcessJob(job).
  • CryIf reicht diesen nach Channel-Mapping unverändert an Crypto_ProcessJob(job) weiter.

#### Pfad 2: Direct API (Schlüsselverwaltung / Key Management)

  • Diskrete 1:1 Schnittstellenspiegelung: Direkte Funktionsabbildung über alle drei Schichten hinweg ohne Kapselung in eine Job-Struktur:
  • Csm_KeySetValid() $\rightarrow$ CryIf_KeySetValid() $\rightarrow$ Crypto_KeySetValid()
  • Csm_KeyElementGet() $\rightarrow$ CryIf_KeyElementGet() $\rightarrow$ Crypto_KeyElementGet()
  • Csm_KeyElementSet() $\rightarrow$ CryIf_KeyElementSet() $\rightarrow$ Crypto_KeyElementSet()
  • Csm_KeyDerive() $\rightarrow$ CryIf_KeyDerive() $\rightarrow$ Crypto_KeyDerive()

3. Dynamisches Verhalten & Sequenzablauf

#### Job-based API (Asynchroner & Synchroner Pfad)

  1. Initialisierung/Trigger: Applikation ruft Primitiv-Funktion am CSM auf (z. B. Csm_MacGenerate()).
  2. Kapselung: CSM mappt API-Parameter auf den zugehörigen, statisch konfigurierten CsmJob und instanziiert/aktualisiert das Objekt Crypto_JobType job.
  3. Dispatch: Übergabe an CryIf_ProcessJob(job). CryIf ermittelt den zuständigen Treiber anhand des konfigurierten Kanals (CryIfChannelId) und ruft Crypto_ProcessJob(job).
  4. Ausführung:
  • Synchron (CRYPTO_PROCESSING_SYNC): Treiber führt Operation blockierend aus und liefert Ergebnisstatus direkt im Call-Stack zurück.
  • Asynchron (CRYPTO_PROCESSING_ASYNC): Treiber reiht Job in interne Queue ein und quittiert Aufruf mit E_OK. Rückmeldung der Fertigstellung erfolgt über Callback-Kette: Crypto-Interrupt/MainFunction $\rightarrow$ CryIf_CallbackNotification() $\rightarrow$ Csm_CallbackNotification() $\rightarrow$ RTE-/Applikations-Callback.
  1. Priorisierung & Preemption: Job-Prioritäten werden im CSM/Treiber ausgewertet; höher priorisierte Jobs verdrängen oder überholen anstehende Jobs in der Queue.

#### Direct API (Rein synchroner Pfad)

  1. Trigger: Applikation ruft Key-Management-Funktion auf (z. B. Csm_KeyElementSet()).
  2. Synchroner Durchgriff: CSM reicht Parameter direkt und ungekapselt an die entsprechende CryIf_Key*-Funktion weiter.
  3. Routing: CryIf mappt die logische CsmKeyId auf die hardware-spezifische CryptoKeyId und ruft blockierend Crypto_Key* am Treiber auf.
  4. Terminierung: Der Treiber führt die Schlüsseloperation direkt in Hard-/Firmware (z. B. NVM/HSM-Keystore) aus. Keine Job-Queue, keine Callbacks, strikt blockierendes Rückgabeverhalten (Std_ReturnType).

4. Normative Relevanz & Entwickler-Hinweise

  • Crypto-Driver-Implementierung (MCAL):
  • Für Nutzoperationen genügt ein einziger Einstiegspunkt: Crypto_ProcessJob(). Sämtliches Dispatching der Krypto-Primitive (AES, SHA, RSA, ECC) erfolgt treiberintern anhand des Job-Payloads.
  • Für das Schlüsselmanagement müssen diskrete Treiber-Funktionen (Crypto_Key*) implementiert werden.
  • Key-Separation & Speicherort:
  • Schlüssel verbleiben immer physisch im Crypto Driver bzw. im Secure Element/HSM.
  • CSM und Applikation halten ausschließlich abstrakte Referenzen (KeyId, KeyElementId). Klartextschlüssel werden im RAM des Host-Cores vermieden (außer bei explizitem Setzen ungesicherter Elemente via Crypto_KeyElementSet).
  • Konfigurations- & API-Regeln:
  • Parameter-Präzedenz: Parameter, die in der statischen Konfiguration (CsmJob / Crypto_JobType) definiert sind, haben Vorrang vor dynamischen Funktionsparametern der CSM-Job-API; redundante Funktionsparameter werden ignoriert.
  • Puffer-Lebensdauer: Bei asynchronen Jobs (CRYPTO_PROCESSING_ASYNC) müssen die an die Job-API übergebenen Ein-/Ausgabepuffer bis zum Eintreffen des Completion-Callbacks persistent und unverändert bleiben (keine Stack-Variablen).
  • Reentrancy & Blocking: Direct-API-Aufrufe blockieren den aufrufenden Task bis zum Hardware-Abschluss des Key-Vorgangs. Zur Vermeidung von Task-Blockaden müssen Verarbeitungszeiten von Key-Derivations- oder Schreibzyklen im NVM im OS-Scheduling berücksichtigt werden.

Specification of Crypto Service Manager AUTOSAR CP R25-11 The CSM uses a static configuration of primitives (CsmPrimitives) to define a cryptographic operation. Such a primitive is then assigned to a job configuration (CsmJob) that determines further attributes like priority, asynchronous or synchronous execution and what key shall be used for the operation. It should be noted that the key is always located in the crypto driver itself and the CSM uses only a reference to it. The separation of the keys and primitives allows to separate the API for the cryptographic operation and the key management. This allows to let an application concentrate on the required cryptographic operation like MAC calculation and verification whereas a key manager provides the keys during a configuration setup. The API of the CSM can roughly be divided into two categories: a direct API (mainly for key management) and a job-based API (mainly for cryptographic operations) (see Figure 7.2)1. The Direct API is configured through key elements, whereas the jobbased API is configured in the job configuration and its associated CsmPrimitive. Job-based API functions will ignore API parameters that have an equivalent in the Crypto_JobType job structure. The direct API has a direct correspondence of the functions in the CryIf and the Crypto Driver. These functions can only be called synchronously.
