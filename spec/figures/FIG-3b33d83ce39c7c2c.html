1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Top-down-Methoden- und Prozessablaufdiagramm (Engineering Workflow / Phasenmodell des AUTOSAR-Entwicklungsprozesses).
  • Technischer Zweck: Darstellung des System-Engineering-Pfads von der Anforderungsanalyse über die funktionale Dekomposition bis zur Aufspaltung in disziplinspezifische HW- und SW-Entwicklungsstränge. Es veranschaulicht die organisatorische und methodische Verantwortungsaufteilung zwischen OEM und Tier-1-Zulieferer sowie die Einspeisung standardisierter AUTOSAR-Austauschbeschreibungen in die klassische AUTOSAR-Methodologie.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm gliedert den Ablauf in drei hierarchische Domänen mit spezifischen Rollen, Entitäten und Artefakten:

  • Car domain (OEM):
    • Marketing: Identifiziert Anwendungsfälle und High-Level-Fahrzeugmerkmale (Car features).
    • System architect: Transformiert Merkmale in formale Fahrzeugfunktionen (Car functions).
  • Electronic domain (OEM):
    • Functional architects: Detaillieren das Funktionsdesign (Function design – I/O-Definition, internes Verhalten, Subfunktionen; entspricht der VFB-Ebene / Virtual Function Bus).
    • Electronic architects: Führen das Funktions-ECU-Mapping durch (Mapping of functions on ECU) und erstellen das Kommunikationsnetzwerk (Definition of comm matrix, z. B. CAN/LIN/FlexRay-Cluster und Signal-PDU-Layouts).
    • Schnittstellen-Artefakt: System Constraint Description (ARXML-Austauschmodell mit Restriktionen bezüglich Busbandbreite, Latenzen, Topologie und Speicherbudget).
  • Organic domain (OEM + supplier):
    • Kollaborative Ebene: Gemeinsame Konsolidierung der Systemspezifikation (ECU system spec).
    • HW-Pfad: Spezifikation (HW spec), getrieben durch die ECU Resource Description (Hardware-Eigenschaften: Controller-Architektur, RAM/ROM/Flash-Größen, Peripherie-Ports, Timings), überführt in die HW-Entwicklung (HW dvpt) bis zum finalen Target (Hardware).
    • SW-Pfad: Spezifikation (SW spec), formalisiert als Software-component Description (SWC-Template: Port-Interfaces, Internal Behavior, Runnables, Events), überführt in die SW-Implementierung (SW dvpt) bis zum generierten/implementierten Quellcode (SWC code).

3. Dynamisches Verhalten & Sequenzablauf

Der Prozess folgt einer strikten Kaskadierung mit paralleler Verzweigung in der Integrationsphase:

  1. Anforderungsdefinition (Car Domain):
    • T_0: Erfassung der Kundenanforderungen (Car features).
    • T_1: Formalisierung in funktionale Anforderungen (Car functions).
  2. Architektur & Allokation (Electronic Domain):
    • T_2: VFB-konforme Schnittstellen- und Verhaltensdefinition (Function design).
    • T_3: Synthese aus logischer Architektur und physischer Netzwerktopologie (Mapping of functions on ECU & Definition of comm matrix).
    • T_4: Export der System Constraint Description als verbindliche Vorgabe an die Steuergeräteebene.
  3. ECU-Dekomposition & Implementierung (Organic Domain):
    • T_5: Abstimmung der ECU system spec zwischen OEM und Tier-1.
    • T_6: Verzweigung in parallele Spezifikations- und Entwicklungsstränge:
      • Hardware-Zweig: HW spec → Parametrierung via ECU Resource Description → Layout/Schaltungsentwicklung (HW dvpt) → Fertigung/Lieferung (Hardware).
      • Software-Zweig: SW spec → Generierung/Modellierung der Software-component Description → Implementierung (SW dvpt) → Kompilat/Source (SWC code).

4. Normative Relevanz & Entwickler-Hinweise

  • Entkopplung durch VFB: Bis zum Schritt Mapping of functions on ECU sind Applikationsfunktionen hardware-agnostisch modelliert. Entwickler implementieren Software-Komponenten (SWCs) ausschließlich gegen den durch die Software-component Description definierten API-Vertrag (Port-Interfaces, RTE-Contract-Phase).
  • Basis für RTE- und BSW-Generierung:
    • Die Software-component Description liefert das Input-Modell für den RTE-Generator zur Erzeugung von Rte_<swc>.h und des RTE-Glue-Codes.
    • Die ECU Resource Description bildet die Basis für die MCAL- und BSW-Konfiguration (System Clocks, Memory Mapping, Pin-Multiplexing, ISR-Vektoren via Tresos, DaVinci Configurator o. ä.).
  • Lieferanten-Schnittstelle: Die strikte Trennung in System Constraint Description, ECU Resource Description und Software-component Description verhindert proprietäre Tool-Abhängigkeiten und sichert die Wiederverwendbarkeit von SWCs über verschiedene Hardware-Plattformen und Tier-1-Lieferanten hinweg.
