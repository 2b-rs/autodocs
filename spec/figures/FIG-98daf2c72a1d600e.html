1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-/Header-Layout (tabellarische Bit-/Byte-Felddefinition).
  • Funktionale Einordnung: Definiert die Bit- und Byte-Struktur des Protokoll-Headers für das AUTOSAR E2E Profile 76 gemäß AUTOSAR_FO_PRS_E2EProtocol (Foundation / Classic & Adaptive Platform).
  • Technischer Zweck: Ermöglicht die deterministische Erkennung von Kommunikationsfehlern (Verfälschung, Wiederholung, Verlust, Vertauschung, Einfügung) bei der Übertragung sicherheitsrelevanter Daten über nicht-vertrauenswürdige Medien (Black-Channel-Prinzip nach ISO 26262 bis ASIL D; Referenzen: RS_E2E_08528, RS_E2E_08539).

2. Komponenten, Entitäten & Schnittstellen

Der Header belegt exakt 5 Bytes (40 Bits) innerhalb der serialisierten PDU und gliedert sich in folgende Felder:

| Byte-Index | Bit-Position | Feldbezeichnung | Typ / Wertebereich | Semantik & Codierung |

| :--- | :--- | :--- | :--- | :--- |

| Byte 0 | Bits [7:5] | Reserved | uint8 (3 Bits: 0 0 0) | Feste Nullbelegung (0b000). Dient als Guard-Pattern und zukünftigen Protokollerweiterungen. |

| Byte 0 | Bits [4:0] | E2E Counter | uint8 (5 Bits: 0..31) | Zyklischer Sequenzzähler (Modulo 32) zur Erkennung von PDU-Verlust, Wiederholung und unzulässiger Reihung. |

| Byte 1 | Bits [7:0] | CRC (LSB) | uint8 | Least Significant Byte des 32-Bit-CRC. |

| Byte 2 | Bits [7:0] | CRC | uint8 | Mittleres Byte (Bit 8..15) des 32-Bit-CRC. |

| Byte 3 | Bits [7:0] | CRC | uint8 | Mittleres Byte (Bit 16..23) des 32-Bit-CRC. |

| Byte 4 | Bits [7:0] | CRC (MSB) | uint8 | Most Significant Byte (Bit 24..31) des 32-Bit-CRC. |

  • Endianness: Der 32-Bit-Prüfwert ist in Little-Endian-Bytereihenfolge angeordnet (CRC (LSB) auf Byte 1 bis CRC (MSB) auf Byte 4).
  • Prüfsummen-Polynom: Standardisierter 32-Bit-CRC (CRC-32 Ethernet / IEEE 802.3, Polynom: 0x04C11DB7, Startwert: 0xFFFFFFFF, XOR-Wert: 0xFFFFFFFF).
  • Header-Platzierung (PRS_E2E_01401): Das 5-Byte-Feld wird über den Konfigurationsparameter HeaderOffset (in Bits oder Bytes) an einer definierten Position innerhalb der Payload/I-PDU serialisiert.

3. Dynamisches Verhalten & Sequenzablauf

#### Sender-Pfad (E2E_P76Protect / PRS_E2E_01400):

  1. Counter-Update: Inkrementierung des internen Zählers: Counter = (Counter + 1) % 32.
  2. Byte 0 Assemblierung: Byte[0] = (0x00 << 5) | (Counter & 0x1F).
  3. CRC-Berechnung: Berechnung der 32-Bit-Prüfsumme über:
  • Die vorkonfigurierte DataID (impliziter Schutz gegen Masquerading/Addressing Errors).
  • Die Nutzdaten (Data Payload).
  • Byte 0 des E2E-Headers (inkl. Counter und Reserved-Bits).
  1. Header-Serialisierung: Einfügen des berechneten CRC32 in Byte 1 bis 4 in Little-Endian-Reihenfolge.

#### Empfänger-Pfad (E2E_P76Check):

  1. Extraktion: Auslesen von Byte 0 bis Byte 4 an Position HeaderOffset.
  2. Plausibilisierung: Verifikation der Bits [7:5] von Byte 0 auf 0b000. Abweichungen führen unmittelbar zum Statusfehler.
  3. Counter-Prüfung: Ermittlung von DeltaCounter = (ReceivedCounter - LastValidCounter) % 32. Bewertung hinsichtlich Wiederholung (Delta = 0), OK (Delta = 1) oder toleriertem PDU-Drop (Delta <= MaxDeltaCounter).
  4. CRC-Verifikation: Neuberechnung des CRC32 über empfangene Nutzdaten, DataID und Byte 0; bitgenauer Abgleich gegen empfangenes Byte 1..4.
  5. Zustandsübergabe: Rückgabe des Profil-Status an die übergeordnete State Machine (E2E_SMCheck) zur Ermittlung des Gesamtzustands (VALID, DEGRADED, INVALID).

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher- und Prozessor-Alignment:
  • Die ungerade Headerlänge von 5 Bytes bricht ein natürliches 16-/32-/64-Bit-Alignment.
  • Bei In-Place-Serialisierung/Deserialisierung im RAM (z. B. auf ARM Cortex-M/R/A oder TriCore) darf der 32-Bit-CRC nicht per direktem 32-Bit-Pointer-Cast ((uint32)&buffer[1]) dereferenziert werden, da dies auf Architekturen mit striktem Alignment Trap-Exceptions (Alignment Fault) auslöst. Byte-weises Kopieren oder memcpy ist zwingend erforderlich.
  • Zählerüberlauf bei schnellen Zyklen:
  • Der 5-Bit-Zähler besitzt eine kurze Wiederholperiode von $2^5 = 32$ Zyklen.
  • Bei hochfrequenten Botschaften (z. B. 1 ms Zykluszeit) läuft der Zähler alle 32 ms über. Die E2E-Timeout-Überwachung (MaxDeltaCounter, Überwachungsfenster) muss zwingend auf die maximale Transport- und Verarbeitungsjitterzeit abgestimmt werden, um Alias-Effekte (Erkennung eines vollen Umlaufs als reguläres Inkrement) auszuschließen.
  • ARXML-Konfiguration & Transformer:
  • Im BSW-Stack (Classic AUTOSAR: E2EXf, Com, PduR; Adaptive AUTOSAR: ara::com / SOME/IP E2E-Header) muss sichergestellt sein, dass der HeaderOffset bitgenau mit der PDU-Beschreibung der Gegenstelle übereinstimmt.
  • Die Little-Endian-Serialisierung des CRC-Wertes ist unabhängig von der CPU-Endianness (Host-Order) fest einzuhalten.
