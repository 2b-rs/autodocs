1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-2.0-Metamodell-Klassendiagramm (Strukturdiagramm).
  • Architektur-Kontext: AUTOSAR ECU Configuration Template (AUTOSAR_TPS_ECUConfiguration), Metamodell-Package ECUCParameterDefTemplate.
  • Funktionaler Zweck: Formale Definition der Basismetadaten und gemeinsamen Attribute (EcucCommonAttributes) für Konfigurationsparameter (EcucParameterDef) und Referenzen (EcucAbstractReferenceDef). Das Diagramm spezifiziert die getrennte Zuordnung von Bindungszeitpunkten (EcucConfigurationClassEnum) für Wert (EcucValueConfigurationClass) und Multiplizität (EcucMultiplicityConfigurationClass) in Abhängigkeit von Konfigurationsvarianten (EcucConfigurationVariantEnum), Flags zur Post-Build-Variabilität sowie die Anbindung von Anforderungs-Traceability (Traceable).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Spezialisierungen
  • Identifiable: AUTOSAR-Basis-Metaklasse für alle referenzierbaren Modellelemente.
  • AtpDefinition: Abstrakter Basistyp für formale Definitionselemente im AUTOSAR-Metamodell.
  • EcucDefinitionElement (erbt von Identifiable und AtpDefinition):
    • Abstrakte Basisklasse aller ECU-Konfigurationsdefinitionen; definiert Instanzgrenzen und Gültigkeit.
    • Stereotyp «atpVariation»: Multiplizitäten unterliegen dem AUTOSAR-Varianten-Mechanismus.
    • Attribute:
      • + scope: EcucScopeEnum [0..1]: Gültigkeitsbereich der Konfigurationsdefinition.
      • + lowerMultiplicity: PositiveInteger: Untere Multiplizitätsgrenze (Mindestanzahl Instanzen).
      • + upperMultiplicity: PositiveInteger [0..1]: Obere Multiplizitätsgrenze bei statischer Obergrenze.
      • + upperMultiplicityInfinite: Boolean [0..1]: Kennzeichen für unbegrenzte obere Multiplizität (*).
    • Assoziationen:
      • +relatedTraceItem 0..1: Referenz auf Traceable mit Stereotyp «atpUriDef» zur Anbindung an Spezifikationsanforderungen.
  • MultilanguageReferrable & Traceable:
    • Metaklassen für rückverfolgbare Spezifikationselemente; Traceable besitzt eine reflexive Assoziation +trace 0..*.
  • EcucCommonAttributes (erbt von EcucDefinitionElement):
    • Abstrakte Basisklasse für gemeinsame Eigenschaften von Parametern und Referenzen.
    • Attribute:
      • + origin: String: Herkunft bzw. Spezifikationsquelle der Definition.
      • + postBuildVariantMultiplicity: Boolean [0..1]: Gibt an, ob die Multiplizität post-build-variabel ist.
      • + postBuildVariantValue: Boolean [0..1]: Gibt an, ob der Wert post-build-variabel ist.
      • + requiresIndex: Boolean [0..1]: Fordert geordnete Indexierung bei Multiplizität > 1.
    • Kompositionen:
      • +multiplicityConfigClass 0..*: Komposition von EcucMultiplicityConfigurationClass.
      • +valueConfigClass 0..*: Komposition von EcucValueConfigurationClass.
  • EcucParameterDef (erbt von EcucCommonAttributes):
    • Basis für konkrete Konfigurationsparameterdefinitionen.
    • Attribute:
      • + symbolicNameValue: Boolean: Kennzeichnet, ob der Parameterwert als symbolischer Name/Literal exportiert werden soll.
      • + withAuto: Boolean [0..1]: Erlaubt die automatische Konfigurationswertberechnung (AUTO).
  • EcucAbstractReferenceDef (erbt von EcucCommonAttributes):
    • Abstrakte Basis für Referenzdefinitionen auf andere Konfigurationscontainer oder Instanzen.
  • EcucAbstractConfigurationClass:
    • Abstrakte Metaklasse zur Festlegung der Konfigurationsklasse je Variante.
    • Attribute:
      • + configClass: EcucConfigurationClassEnum: Bindungszeitpunkt.
      • + configVariant: EcucConfigurationVariantEnum: Build-Variante.
  • EcucMultiplicityConfigurationClass (erbt von EcucAbstractConfigurationClass):
    • Definiert die Konfigurationsklasse spezifisch für die Multiplizität des Elements.
  • EcucValueConfigurationClass (erbt von EcucAbstractConfigurationClass):
    • Definiert die Konfigurationsklasse spezifisch für den Wert des Elements.
Enumerationen
  • EcucConfigurationClassEnum: Bindungszeitpunkte: PublishedInformation, PreCompile, Link, PostBuild.
  • EcucConfigurationVariantEnum: Konfigurationsvarianten: PreconfiguredConfiguration, RecommendedConfiguration, VariantPreCompile, VariantLinkTime, VariantPostBuild.

3. Dynamisches Verhalten & Sequenzablauf

  • Entfällt für Target-Laufzeit: Metamodell ohne Ausführungscode, OS-Tasks oder Runnables.
  • Toolchain-/Build-Workflow:
    1. Variantenauflösung: Auswertung von EcucImplementationConfigurationClass anhand der aktiven configVariant bestimmt die Bindungszeit (configClass).
    2. Konsistenzprüfung: EcucConfigurationClassAffection erzwingt Abhängigkeiten: Wird ein Parameter auf PreCompile gesetzt, treibt PCAffectsPB referenzierte/abhängige Elemente (+affected) zwingend in eine kompatible Bindungszeit (Verhinderung von Zeiger- oder Struktur-Inkonsistenzen zwischen ROM und RAM).
    3. Artefakterzeugung:
      • PreCompile → Generierung statischer Makros (#define) und const-Konfigurationen in *_Cfg.h/*_Cfg.c.
      • Link → Deklaration via extern const in *_PBcfg.h, Definition in separaten Translation Units.
      • PostBuild (Loadable/Selectable) → Binärdeskriptoren / Root-Konfigurationsstrukturen zur Initialisierung via Pointer (<Mod>_Init(&ConfigRoot)).

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Generatoren (BSW/MCAL):
    • symbolicNameValue == true: Das Generator-Backend muss für jedes Instanzelement zwingend einen C-Bezeichner nach dem Muster <MODULE>_<ContainerShortName>_<ParameterShortName> als numerischen Identifier exportieren (relevant für PduR-Routing-IDs, CanIf-Channels, Dem-Events).
    • withAuto == true: Konfigurationstools müssen bei Initialwerten den Modus AUTO unterstützen und zulassen, dass der Wert durch Abhängigkeitsanalysen des Toolchains berechnet wird.
    • Multiplizitäten: upperMultiplicity > 1 oder upperMultiplicityInfinite == true erzwingt in C-Strukturen Array-Deklarationen; bei requiresIndex == true ist die Reihenfolge der Instanzen im generierten Code zwingend deterministisch an den Index im ARXML gebunden.
  • Varianten-Handling:
    • Fehlt für eine gewählte configVariant die passende EcucImplementationConfigurationClass, schlägt die Modellvalidierung fehl.
    • Vendor-spezifische Parameter müssen im Attribut origin zwingend den Hersteller/OEM deklarieren, um Namensraumkonflikte mit Standard-AUTOSAR-Parametern auszuschließen.
