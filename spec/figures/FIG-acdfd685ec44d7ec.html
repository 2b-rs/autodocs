Figure 31: Verification of freshness value 11.5.3.3 Successful verification of I-PDUs When SecOC sends a notification of the verification result (verification is successful), the receiver ECU maintains the constructed freshness value for verification as the previously received value. In case that the alternative method, which is to prevent discarding if out of sequence, is used, refers to the following specifications. There are two ways about list of previously-received freshness values. Specification 1: When SecOC sends a notification of the verification result (verification is successful), the receiver ECU stores the freshness values used for MAC verification (trip counter and message counter) and updates the list of previously-received freshness values corresponding to the SecOCFreshnessValueID. The freshness values that were stored up to this point are included in the list of previously-received freshness values up to a quantity of ReceivedFreshnessValueListSize by counting from the largest value. Among the values in the list of previously-received freshness values, the largest value is used as the reference value, and the smallest value is used as the tolerance value. The list of previously-received freshness values does not store duplicate freshness values. Specification 2: When SecOC sends a notification of the verification result (verification is successful), the receiver ECU stores the freshness values used for MAC verification (trip counter and message counter) and updates the list of previously-received freshness values corresponding to the SecOCFreshnessValueID. Freshness values stored up to this point that are the tolerance values or more and reference value or less are included in the list of previously-received freshness values. Among the freshness values that were stored up to this point, the largest value is used as the reference value, and the "reference value － FreshnessValueToleranceWindow” is used as the tolerance value. The list of previously-received freshness values does not store duplicate freshness values. 1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Aktivitätsdiagramm / Kontrollflussdiagramm (Entscheidungsbaum).
  • Architektur-Kontext: AUTOSAR Classic Platform, Basic Software (BSW), Kommunikations-Stack: SecOC (Secure Onboard Communication, SWS SecOC, Release R20-11 / R22-11).
  • Technischer Zweck: Spezifikation des zweistufigen Verifikationsalgorithmus für Freshness Values (FV) beim PDU-Empfang. Das Verfahren adressiert den Replay-Schutz bei asynchronem Jitter, Bus-Arbitrierung oder Multi-Core/Gateway-Laufzeitunterschieden (Out-of-Sequence PDUs), um berechtigte, verspätete Botschaften nicht fälschlich zu verwerfen, während Replay-Angriffe deterministisch abgewehrt werden.

2. Komponenten, Entitäten & Schnittstellen

  • Beteiligte BSW-Module & Entitäten:
  • SecOC (Rx-Pfad): Führt die Kontrollflusslogik bei Eintreffen einer Secured I-PDU aus.
  • FVM (Freshness Value Manager): Bereitstellung/Rekonstruktion des vollständigen Freshness Values (z. B. Trip Counter + Message Counter).
  • Verarbeitete Variablen & Datenstrukturen:
  • Received value: Der für die aktuelle Secured I-PDU ermittelte/rekonstruierte Freshness Value.
  • Reference value: Der aktuell höchste, erfolgreich verifizierte Freshness Value (oberer Referenzpunkt).
  • Tolerance value: Untere Grenze des gültigen Akzeptanzfensters.
  • list of previously-received freshness values: Historienliste/Deduplizierungsspeicher pro SecOCFreshnessValueID, speichert verarbeitete Freshness Values ohne Duplikate.
  • Konfigurationsparameter:
  • SecOCFreshnessValueID: Eindeutiger Identifikator für den Freshness-Kanal.
  • ReceivedFreshnessValueListSize: Ganzzahliger Wertebereich $[1 \dots 255]$ für die maximale Listengröße (Spec 1).
  • FreshnessValueToleranceWindow: Fensterbreite zur dynamischen Berechnung (Reference value - FreshnessValueToleranceWindow) des Toleranzwerts (Spec 2).

3. Dynamisches Verhalten & Sequenzablauf

Der Prüfpfad wird synchron während der Empfangsverarbeitung (im Kontext von SecOC_RxIndication bzw. SecOC_MainFunctionRx) durchlaufen:

```

[Start]

│

▼

[Procedure 1: Bereichsprüfung gegen Referenz- und Toleranzwert]

├── (Received value < Tolerance value)

│ └──► [verification of freshness value fails] (Paket veraltet)

│

├── (Reference value < Received value)

│ └──► [verification of freshness value is successful] (Monotoner Fortschritt)

│

└── (Tolerance value ≤ Received value ≤ Reference value)

│

▼

[Procedure 2: Historienprüfung in Deduplizierungsliste]

├── (Found in list / previously received)

│ └──► [verification of freshness value fails] (Replay erkannt)

│

└── (Not found in list / not received)

└──► [verification of freshness value is successful] (Legitimes Out-of-Sequence-Paket)

```

  1. Trigger: Rekonstruktion des Freshness Values für eine eingehende Secured I-PDU.
  2. Procedure 1 (Bereichs-Vorfilterung):
  • Pfad A (Received value < Tolerance value): Wert liegt unterhalb der Toleranzschwelle. Das Paket ist zu alt. Ergebnis: Abbruch mit Verifikationsfehler.
  • Pfad B (Reference value < Received value): Wert ist strikt größer als der bisherige Maximalwert. Neuer regulärer Zustand. Ergebnis: Verifikation erfolgreich; Procedure 2 wird übersprungen.
  • Pfad C (Tolerance value ≤ Received value ≤ Reference value): Wert liegt im Toleranzkorridor, ist aber kleiner oder gleich dem bisherigen Höchstwert. Mögliche Out-of-Sequence-PDU oder Replay-Angriff. Übergang: Verzweigung in Procedure 2.
  1. Procedure 2 (Deduplizierungs-Prüfung):
  • Pfad C1 (Found in list): Der Freshness Value existiert bereits im Speicher für diese SecOCFreshnessValueID. Identifiziert Replay. Ergebnis: Abbruch mit Verifikationsfehler.
  • Pfad C2 (Not found in list): Der Freshness Value wurde trotz kleinerem Index bisher nicht verarbeitet. Ergebnis: Verifikation erfolgreich.

4. Normative Relevanz & Entwickler-Hinweise

  • Kritische Update-Reihenfolge (Anti-DoS): Die Aufnahme des Received value in die Liste und die Aktualisierung des Reference value dürfen erst nach erfolgreicher kryptografischer MAC-Verifikation erfolgen. Ein vorzeitiges Aktualisieren würde es unauthentifizierten Angreifern erlauben, das Toleranzfenster zu verschieben oder die Liste mit Fake-Werten zu fluten.
  • RAM- und Laufzeitkomplexität im BSW-Treiber:
  • Bei bis zu 255 Einträgen pro PDU-Kanal skaliert der RAM-Bedarf direkt mit der Anzahl gesicherter PDUs.
  • Lineares Suchen ($O(N)$) in Procedure 2 kann bei Bus-Spitzen (Burst) zu Latenz-Jitter im Rx-Pfad führen. Für Multi-PDU-Gateways ist ein ringförmiger Ringspeicher mit Binärsuche oder bitmaskierter Indexierung zu implementieren.
  • Spezifikationsvarianten (Spec 1 vs. Spec 2):
  • Specification 1: Basiert auf der Anzahl (ReceivedFreshnessValueListSize). Tolerance value ist der kleinste in der sortierten Liste vorhandene Wert.
  • Specification 2: Basiert auf arithmetischem Offset (FreshnessValueToleranceWindow). Werte kleiner als Reference value - FreshnessValueToleranceWindow scheiden automatisch aus.
  • Fehlerbehandlung: Scheitert die Verifikation (fails), wird keine PDU an die oberen Schichten (PduR/Com) weitergeleitet. Es erfolgt je nach Konfiguration ein Security-Event-Reporting an das IdsM (Intrusion Detection System Manager) bzw. ein Dem/Det-Fehleraufruf (SECOC_E_FRESHNESS_FAILURE).
