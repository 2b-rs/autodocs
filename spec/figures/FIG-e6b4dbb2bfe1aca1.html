1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozess- und Dekompositionsdiagramm basierend auf dem SPEM-2.0-Metamodell (Software & Systems Process Engineering Metamodel) innerhalb der AUTOSAR-Methodik (AUTOSAR_TR_Methodology, R4.0.3).
  • Technischer Zweck: Strukturelle und hierarchische Zerlegung (Activity Breakdown Structure) der Top-Level-Aktivität Develop Basic Software in Sub-Aktivitäten (Design Basic Software, Develop BSW Module) und granulare Aufgaben (SPEM-Tasks) sowie deren Bindung an Ein- und Ausgangs-Artefakte (WorkProductPackages).
  • Architektur-Einordnung: Definiert den standardisierten Entwicklungsprozess für Basissoftware-Module (BSW) durch Tier-1-Zulieferer oder BSW-Stack-Vendors vor der eigentlichen ECU-Integration.

2. Komponenten, Entitäten & Schnittstellen

  • Work Product Packages (Artefakte):
    • BSW Standard Package [Multiplizität: 1, Stereotyp: «input»]: Standardisierte Vorgaben der AUTOSAR-Spezifikation (Standard-Header, BSW-UML-Modelle, Schema-Definitionen, standardisierte BSWMD-Templates).
    • BSW Module Delivered Bundle [Multiplizität: 1..*, Stereotyp: «output»]: Auslieferungsfähiges BSW-Lieferpaket (statische C-Quell-/Header-Dateien, Vendor-spezifische BSWMD, Modul-Code-Generatoren, Dokumentation).
  • Aktivitäten (Composite Activities):
    • Develop Basic Software: Übergeordnete Prozessklammer.
    • Design Basic Software [Multiplizität: 1, Stereotyp: «nesting»]: Modulübergreifendes oder grundlegendes BSW-Architekturdesign.
    • Develop BSW Module [Multiplizität: 1..*, Stereotyp: «nesting»]: Modulspezifische Implementierungs- und Tooling-Entwicklungsaktivität (instanziiert pro BSW-Modul, z. B. Can, Spi, Com).
  • Sub-Tasks in Design Basic Software (Stereotyp: «nesting»):
    • Define BSW Types: Spezifikation von BSW-spezifischen Typdefinitionen (Std_Types, modulspezifische Enums/Strukturen).
    • Define Vendor Specific Module Definition: Erweiterung der standardisierten Moduldefinition (BswModuleDef) um herstellerspezifische Konfigurationsparameter (EcucParamConfContainerDef).
    • Define BSW Entries: Definition der C-Funktionsprototypen und Entry-Points (BswModuleEntry) für APIs, Callbacks und Main-Functions.
    • Define BSW Interfaces: Festlegung der Schnittstellenbeziehungen und Abhängigkeiten zwischen BSW-Modulen bzw. zur SWC-Welt (Inter-Module-Interfaces).
  • Sub-Tasks in Develop BSW Module (Stereotyp: «nesting»):
    • Define BSW Behavior: Modellierung des internen Verhaltens (BswInternalBehavior), u. a. Scheduling-Entities, Events, Exclusive Areas und Per-Instance-Memory.
    • Generate BSWM Contract Header Files: Erzeugung der Contract-Phase-Header zur Entkopplung und Vorab-Kompilierung von BSW-Quellen gegen SchM/RTE-Stubs.
    • Implement a BSW Module: Programmierung des statischen C-Codes (.c/.h) des Moduls.
    • Develop BSW Module Generator: Implementierung des Konfigurations- und Codegenerators für Pre-Compile-, Link-Time- oder Post-Build-Parameter.
    • Define BSW Module Timing: Spezifikation von Ausführungszeiten, Task-Perioden und Latenz-Garantien (BswModuleTiming).
  • Beziehungen:
    • Komposition: «nesting» aggregiert Tasks und Sub-Aktivitäten unter die übergeordneten Aktivitäten.
    • Sequenzbedingung: Gerichtete Abhängigkeit «predecessor» von Develop BSW Module zu Design Basic Software.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Input-Bindung: Einlesen des normativen BSW Standard Package als Arbeitsbasis.
  2. Phase 1 – Design Basic Software (Zwingender Vorgänger):
    • Parallel oder iterativ werden Typen (Define BSW Types), Einstiegspunkte (Define BSW Entries) und Modulschnittstellen (Define BSW Interfaces) formal in AUTOSAR-XML (ARXML) beschrieben.
    • Parameterbeschreibungen werden im Parameter-Definitionstemplate um herstellerspezifische Features ergänzt (Define Vendor Specific Module Definition).
  3. Phase 2 – Develop BSW Module (Folgeschritt via «predecessor»):
    • Nach Freigabe des BSW-Designs erfolgt pro Modul (1..*) die Spezifikation des BswInternalBehavior (z. B. Zuordnung von Main-Functions zu SchM-Triggern).
    • Contract-Phase: Generate BSWM Contract Header Files erzeugt modulseitige Header-Stubs zur Syntax- und Typprüfung vor der eigentlichen ECU-weiten RTE-Generierung.
    • Modul-Implementierung (Implement a BSW Module) und Bereitstellung des zugehörigen Modul-Generators (Develop BSW Module Generator) laufen synchron mit der Definition von Timing-Constraints (Define BSW Module Timing).
  4. Abschluss & Deliverable: Paketierung der Artefakte in das BSW Module Delivered Bundle zur Weitergabe an System-Integratoren und OEM.

4. Normative Relevanz & Entwickler-Hinweise

  • Zweistufiges V-Modell (Design vs. Implementation): Embedded-Entwickler dürfen keinen statischen C-Code schreiben, bevor BswModuleEntry und BswModuleDef formal definiert sind; Funktionssignaturen müssen exakt mit den formalen ARXML-Beschreibungen übereinstimmen.
  • BswInternalBehavior als SchM-Bindeglied: Für die korrekte Integration in den Basic Software Scheduler (SchM) ist die lückenlose Modellierung aller ExclusiveAreas (Interrupt-Locks, Spinlocks) und BswSchedulableEntities verpflichtend. Fehlen diese, kann der SchM-Generator keine passenden SchM-APIs (SchM_Enter_*, SchM_Exit_*) generieren.
  • Contract-Phase-Build: Durch Generate BSWM Contract Header Files wird die Unit-Testbarkeit und Vorab-Kompilierbarkeit des BSW-Moduls ohne vollständige ECU-Konfiguration sichergestellt. Entwickler müssen sicherstellen, dass die Modul-Sourcen ausschließlich gegen diese Contract-Header und nicht gegen hardcodierte globale Symbole kompilieren.
  • Generator-Konformität: Der BSW-Modul-Generator muss gegen das definierte BSWMD-Metamodell validieren; inkonsistente ECUC-Werte müssen zur Compile-/Generierzeit mit aussagekräftigen Diagnosemeldungen abgefangen werden.
