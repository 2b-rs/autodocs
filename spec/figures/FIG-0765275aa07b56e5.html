1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (Metamodell-Ausschnitt des AUTOSAR System Template, M2-Ebene).
  • Technischer Zweck: Modellierung der Konfigurationsstrukturen für das BSW-Modul Diagnostic Log and Trace (DLT) gemäß AUTOSAR_TPS_SystemTemplate (TPS_SYST_02264).
  • Funktionale Einordnung: Verknüpft die Steuergeräte-Instanz (EcuInstance) und deren DLT-Kommunikationskanäle (DltLogChannel) bidirektional mit dem AUTOSAR-Kommunikationsstack (PduTriggering / GeneralPurposeIPdu) sowie mit den semantischen Beschreibungsstrukturen für Logging-Nachrichten (DltMessageCollectionSet, DltMessage, DltArgument) zur Offline-Dekodierung (insb. im Non-Verbose-Modus).

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Attribute
  • EcuInstance (Spezialisierung von FibexElement):
    • Repräsentiert das physische Steuergerät im Systemdesign.
    • Aggregiert per Komposition (+dltConfig, Kardinalität 0..1) die modulspezifische DLT-Konfiguration.
    • Enthält allgemeine Kommunikations- und Powermanagement-Attribute (z. B. comConfiguration*TimeBase, sleepModeSupported, wakeUpOverBusSupported, pncPrepareSleepTimer).
  • DltConfig:
    • Zentrale DLT-Eigenschaftsdefinition der ECU.
    • Attribute:
      • dltEcuId: String [0..1]: Physischer/logischer ECU-Identifikator im DLT-Header (typischerweise 4 ASCII-Zeichen).
      • sessionIdSupport: Boolean [0..1]: Aktivierung der Session-ID im DLT-Header.
      • timestampSupport: Boolean [0..1]: Aktivierung von Zeitstempeln in generierten DLT-Frames.
  • DltLogChannel (Spezialisierung von Identifiable):
    • Repräsentiert einen logischen Kommunikationskanal für DLT-Logging.
    • Attribute:
      • applicationId: String / applicationDescription: String [0..1]: Software-Komponenten-/Applikations-ID (4 Zeichen).
      • contextId: String / contextDescription: String [0..1]: Feingranulare Logging-Kontext-ID innerhalb der Applikation (4 Zeichen).
      • sessionId: PositiveInteger [0..1]: Eindeutige Sitzungskennung.
  • DltMessageCollectionSet (Spezialisierung von FibexElement):
    • Eigenständiges, austauschbares FIBEX-Element als Container für Offline-Trace-/Log-Datenbanken.
    • Aggregiert 0..* DltMessage-Elemente.
  • DltMessage (Spezialisierung von Identifiable):
    • Definiert eine diskrete Log-/Trace-Nachricht.
    • Attribute:
      • messageId: PositiveInteger: Eindeutige ID zur Auflösung nicht-ausführlicher Nachrichten (Non-Verbose Mode).
      • messageTypeInfo: String: Typklassifikation (z. B. Log/Trace/Network/Control).
      • messageSourceFile: String [0..1] & messageLineNumber: PositiveInteger [0..1]: Debug-/Quellcode-Referenzen.
  • DltArgument (Spezialisierung von Identifiable):
    • Definiert einzelne Argumente/Payload-Felder einer DltMessage.
    • Aggregiert per Komposition +networkRepresentation (0..1) das Element SwDataDefProps (markiert mit dem Stereotyp «atpVariation» für varianzabhängige Datentyprepräsentationen).
  • PDU-Hierarchie:
    • PduTriggering (Spezialisierung von Identifiable): Repräsentiert die Auslösung/das Routing einer PDU auf einem spezifischen Bus/Cluster.
    • Pdu (Spezialisierung von FibexElement): Basisklasse (hasDynamicLength, length).
    • IPdu → GeneralPurposeIPdu: Spezialisierung für generische Nutzinhalte (Transport von Roh-DLT-Datenströmen via PduR/Com-Stack über CAN, FlexRay oder Ethernet).
Assoziationen & Kardinalitäten
  • EcuInstance ◆–0..1→ DltConfig (Komposition).
  • DltConfig $\blacklozenge\xrightarrow{0..* \text{ +dltLogChannel}}$ DltLogChannel (Komposition).
  • DltLogChannel $\xrightarrow{1 \text{ +txPduTriggering}}$ PduTriggering: Exakter TX-PDU-Trigger zur Übertragung von Log-Nachrichten an das Diagnosetool/Logging-Netzwerk.
  • DltLogChannel $\xrightarrow{1 \text{ +rxPduTriggering}}$ PduTriggering: Exakter RX-PDU-Trigger für Steuer- und Injektionskommandos (z. B. Ändern des Log-Levels zur Laufzeit).
  • DltLogChannel $\xrightarrow{0..* \text{ +dltMessage}}$ DltMessage: Referenzierung der über diesen Kanal emittierbaren Nachrichten.
  • DltMessageCollectionSet $\blacklozenge\xrightarrow{0..* \text{ +dltMessage}}$ DltMessage (Komposition).
  • DltMessage $\blacklozenge\xrightarrow{0..* \text{ \{ordered\} +dltArgument}}$ DltArgument (Geordnete Komposition der Payload-Parameter).
  • DltArgument $\blacklozenge\xrightarrow{0..1 \text{ +networkRepresentation}}$ SwDataDefProps (Datentyp- und Kodierungsdefinition).
  • PduTriggering $\xrightarrow{1 \text{ +iPdu}}$ Pdu (Assoziation zur PDU-Definition).

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm modelliert statische System-Deskriptoren (M2). Zur Laufzeit bestimmt diese Struktur folgende Signalflüsse:

[SWC / BSW] 
    │  Dlt_SendLogMessage(AppId, ContextId, LogLevel, ...)
    ▼
[DLT BSW Module] ── Formatiert DLT-Frame (Header: dltEcuId, Timestamp, SessionId, Payload)
    │  Non-Verbose: messageId + kompakte Argument-Binärdaten
    │  Verbose:     Vollständige Typ-/Format-Deskriptoren im Stream
    ▼
[PduR / Com-Stack] ── Zuordnung über dltLogChannel.txPduTriggering -> GeneralPurposeIPdu
    │  Transmit-Request
    ▼
[Bus Interface / Hardware-Treiber] (z. B. CanIf, EthIf) ── Ausstrahlung auf dem Bus
    │
    ▼ (Gegenrichtung: Injektion / Filterung)
[Bus Interface / Hardware-Treiber] ── RxIndication über dltLogChannel.rxPduTriggering
    ▼
[DLT Control API] ── Dynamische Anpassung des Log-Status / Dlt_SetLogLevel()
  1. Log-Nachrichten-Generierung (TX):
    • Applikationen emittieren Logs unter Angabe von applicationId und contextId.
    • Das DLT-Modul serialisiert Header-Felder entsprechend der gesetzten Flags (sessionIdSupport, timestampSupport, dltEcuId).
    • Ist die Nachricht als Non-Verbose konfiguriert, wird die numerische messageId übertragen.
    • Weitergabe der serialisierten Payload an den Kommunikationsstack über die per txPduTriggering verknüpfte GeneralPurposeIPdu.
  2. Steuerung & Injektion (RX):
    • Externe DLT-Clients (z. B. DLT Viewer) senden Steuernachrichten an das Steuergerät.
    • Der Empfangspfad wird strikt über das am DltLogChannel referenzierte rxPduTriggering geroutet, welches Steuerbefehle an den DLT-Dispatcher übergibt.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Konfiguration (Dlt, PduR, Com):
    • GeneralPurposeIPdu: DLT-Traffic umgeht signalbasierte Signal-Router (Com) und wird direkt als PDU über PduR an Interface-Module (CanIf, EthIf, FrIf) geroutet.
    • Die Kardinalität 1 an txPduTriggering und rxPduTriggering erzwingt für jeden konfigurierten DltLogChannel eine eindeutige Zuordnung im PDU-Routing des System-Extracts.
  • Non-Verbose Mode & Offline-Toolchain:
    • Das DltMessageCollectionSet ist die normative Grundlage für den Export der DLT-Beschreibungsdatei (FIBEX/ARXML).
    • Externe Analyse-Tools (Vector CANoe, COVESA DLT Viewer) benötigen diesen Export zwingend, um im Non-Verbose-Betrieb aus der empfangenen messageId Quelltextdatei (messageSourceFile), Zeilennummer (messageLineNumber) und via SwDataDefProps die Datentypen der DltArgument-Elemente zu rekonstruieren.
  • Variantenmanagement:
    • Das Stereotyp «atpVariation» an SwDataDefProps erlaubt die bedingte Bindung von Argumentstrukturen an Post-Build- oder Pre-Compile-Systemvarianten (SystemTemplate-Varianz).
  • Restriktionen & Fallstricke:
    • dltEcuId, applicationId und contextId sind in der AUTOSAR-DLT-Spezifikation strikt auf 4-Byte-Identifier (Standard-ASCII) beschränkt, auch wenn das Metamodell hier generische String-Typen deklariert.
    • Fehlt das DltConfig-Element an einer EcuInstance, ist DLT für dieses Steuergerät im System-Design deaktiviert.
