1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm (cd Datatypes complete), Metamodell-Ausschnitt (M2-Ebene) aus der AUTOSAR-Softwarearchitektur (spezifisch für frühe Classic-Releases R2.1–R3.2, referenziert im ASCET-Styleguide).
  • Technischer Zweck: Definition des statischen Typensystems für Datentypen von Application Software Components (SW-C). Es modelliert die M2-Typ-Prototyp-Semantik (atpType / atpPrototype) zur Abbildung von Signalen, Interface-Parametern, Record- und Array-Strukturen auf VFB- und RTE-Ebene inklusive formaler OCL-Wertebereichseinschränkungen (constraints).

2. Komponenten, Entitäten & Schnittstellen

Basis-Klassen & Stereotypen
  • ARElement: Oberklasse aller im AUTOSAR-ARXML eigenständig adressierbaren und paketierbaren Modell-Elemente.
  • Datatype («atpType»): Abstrakte Basisklasse aller Datentypen; spezialisiert ARElement.
    • OCL-Constraint: {def : values : Set(OclAny)}.
  • Identifiable: Basiselement für benannte Modellelemente mit eindeutigem Pfad (shortName).
  • DataPrototype («atpPrototype»): Spezialisiert Identifiable. Instanziierbares Daten-Metamodellelement (z. B. Port-Element, Record-Element).
    • Assoziation zu Datatype: Typ-Instanz-Beziehung («isOfType»), Kardinalität: 0..* DataPrototypes verweisen auf genau 1 Datatype (+type).
Typ-Hierarchie & Komposition
  • PrimitiveType («atpType»): Abstrakte Spezialisierung von Datatype für atomare Werte.
    • Range: Wertebereichs-Definition. Aggregiert per Komposition genau zwei Grenzwerte (Limit, Typ ValueByFormula, Stereotyp «atpMixedString»): +lowerLimit [1], +upperLimit [1]. OCL: {lowerLimit < upperLimit}, {def : valuesInRange : Set(Float)}.
    • IntegerType: Mehrfachvererbung aus PrimitiveType und Range. OCL: {def: values = valuesInRange.intersect(Integer)}.
    • RealType: Mehrfachvererbung aus PrimitiveType und Range.
      • Attribute: + allowNaN: Boolean, + encoding: Enumeration{Single, Double}.
      • OCL: {def : allReals : Set(Real) = defined by encoding}, {def : values = valuesInRange.intersect(allReals)}.
    • BooleanType: Spezialisiert PrimitiveType. OCL: {def : values = {TRUE, FALSE}}.
    • OpaqueType: Spezialisiert PrimitiveType für typ-agnostische Bitfolgen (z. B. Raw-Payloads).
      • Attribute: + numberOfBits: Int. Constraint: {numberOfBits > 0}.
    • CharType: Spezialisiert PrimitiveType für Einzelzeichen.
      • Attribute: + encoding: String. Constraint: {TBD: naming convention for "encoding"!}.
    • StringType: Spezialisiert PrimitiveType für Zeichenketten.
      • Attribute: + encoding: String, + maxNumberOfChars: Int. Constraint: {maxLength > 0}.
  • CompositeType: Abstrakte Spezialisierung von Datatype für zusammengesetzte Datentypen.
    • ArrayType: Spezialisiert CompositeType.
      • Attribute: + maxNumberOfElements: Int. Constraint: {numberOfElements > 0}.
      • Assoziation: Verweist gerichtet auf den Basistyp: +elementType [1] (Datatype).
    • RecordType: Spezialisiert CompositeType für strukturierte Datensätze (C-struct-Äquivalent).
      • Komposition: Besitzt 1..* geordnete Record-Elemente: +element [1..* {ordered}] (RecordElement).
      • RecordElement: Spezialisiert DataPrototype. Damit referenziert jedes RecordElement über die geerbte «isOfType»-Relation wiederum genau einen Datatype (+type [1]).

3. Dynamisches Verhalten & Sequenzablauf

Nicht zutreffend (rein statisches M2-Struktur- und Metamodell-Klassendiagramm).

  • Synthese- & Generierungszeitpunkt: Das Metamodell wirkt zur Modellierungs- und Generierungszeit (Toolchain / RTE-Generator). Die statischen Typen und OCL-Constraints determinieren die statische Typisierung der erzeugten C-Header (Rte_Type.h), Typdefinitionen (typedef) sowie Interface-Signaturen von Runnables.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Typgenerierung & C-Mapping:
    • IntegerType und RealType mappen direkt auf standardisierte Platform-Types (uint8, sint16, float32, float64).
    • CompositeType determiniert C-Arrays bzw. struct-Typen in Rte_Type.h. Die Kardinalität 1..* {ordered} bei RecordElement erzwingt eine deterministische Reihenfolge der Struct-Member im generierten Code (Alignment/Padding-Relevanz).
  • Modellierungsrestriktionen & Validierung:
    • OCL-Constraints erzwingen strikte Gültigkeitsgrenzen vor der Codegenerierung (lowerLimit < upperLimit, numberOfBits > 0, maxNumberOfElements > 0). Modellierungsfehler führen zum Abbruch der Toolchain-Validierung.
    • allowNaN: Boolean steuert, ob Signalvalidierungsprüfungen oder Gleitkomma-Sonderwerte in Applikations-Runnables zulässig sind oder gefiltert werden müssen.
    • OpaqueType erfordert hardwarenahe Bitmaskierung bzw. byteweises Kopieren, da kein numerischer Wertebereich definiert ist.
  • Historischer Release-Kontext (R2.1–R3.2 vs. AR 4.x):
    • Vorliegendes Modell zeigt das frühere flache Datentypmodell (direkte Spezialisierung von Datatype).
    • Achtung bei Migration auf AUTOSAR Classic 4.x: Ab Release 4.0 wurde dieses System grundlegend durch das dreistufige Konzept ersetzt (ApplicationDataType, ImplementationDataType, BaseType via DataTypeMap und CompuMethod), wodurch PrimitiveType und die direkte Kopplung an Range entfallen sind.
