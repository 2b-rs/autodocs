1. Diagrammtyp & Architektur-Kontext

UML-Sequenzdiagramm zur Spezifikation des dynamischen Abbruchverhaltens (Fee_Cancel) innerhalb des AUTOSAR Memory Stacks (Classic Platform). Das Diagramm veranschaulicht das Zusammenspiel der Schichten Non-Volatile RAM Manager (NvM, Memory Service Layer), Memory Abstraction Interface (MemIf, Memory Abstraction Layer), Flash EEPROM Emulation (Fee, Memory Abstraction Layer) und Flash Driver (Fls, Microcontroller Abstraction Layer) im Kontext der Ausführung durch eine zyklische BSW-Task und der asynchronen Interaktion mit der Flash-Speicher-Peripherie (Flash Memory).

2. Komponenten, Entitäten & Schnittstellen

Beteiligte Entitäten (Lifelines):

  • «module» NvM: Non-Volatile RAM Manager (Auftraggeber für persistente Speicheroperationen).
  • BSW Task (OS task or cyclic call): Ausführungskontext für zyklische Hauptfunktionen (MainFunction).
  • «module» MemIf: Memory Abstraction Interface (Routing-Instanz).
  • «module» Fee: Flash EEPROM Emulation (Treiber für emuliertes EEPROM auf Flash).
  • «module» Fls: Flash Driver (Hardwarespezifischer Treiber).
  • «Peripheral» Flash Memory: Physikalische Flash-Speicher-Hardware.

Schnittstellen und Operationen:

  • Schreibinitiierung: MemIf_Write(uint8, uint16, uint8*), Fee_Write(uint16, uint8*), Fls_Write(Fls_AddressType, const uint8*, Fls_LengthType) mit synchronen Returns (MemIf_Write(), Fee_Write(), Fls_Write()).
  • Zyklische Verarbeitung: Fls_MainFunction(void) mit Return Fls_MainFunction().
  • Abbruchoperationen: MemIf_Cancel(DeviceIndex), Fee_Cancel(void) mit Returns MemIf_Cancel(), Fee_Cancel(), Fls_Cancel(void) mit Return Fls_Cancel().
  • Fehlermeldungen / Callbacks: Fee_JobErrorNotification(), NvM_JobErrorNotification().

3. Dynamisches Verhalten & Sequenzablauf

Der Ablauf gliedert sich in vier Phasen:

  1. Auftragserteilung (Write Request):
    • NvM stößt über MemIf_Write und Fee_Write ein Schreibkommando an.
    • Fee ruft Fls_Write auf; Fls prüft, ob die Hardware frei (idle) ist, und setzt das erste Schreibkommando an die Hardware ab.
    • Die Aufrufe kehren synchron zurück, während die Hardware die Operation asynchron ausführt.
  2. Zyklische Ausführung (loop Fls_MainFunction):
    • Die BSW-Task ruft Fls_MainFunction(void) auf. Fls prüft Hardware- und Jobstatus; falls die Hardware fertig ist, der Gesamtauftrag aber noch nicht, wird der nächste Schreibbefehl an den Flash-Speicher übermittelt.
  3. Abbruchsequenz (Fee_Cancel):
    • NvM ruft MemIf_Cancel(DeviceIndex) auf, was zu Fee_Cancel(void) und folgend zu Fls_Cancel(void) führt.
    • Fls setzt modulintern die Jobvariablen zurück; eine eventuell in der Flash-Hardware noch laufende Schreiboperation wird hardwareseitig nicht zwingend abgebrochen.
    • Entweder meldet Fls während des Abbruchs via Callback Fee_JobErrorNotification() den Abbruch an Fee (welches NvM_JobErrorNotification() an NvM weiterleitet) oder Fee signalisiert nach der Rückkehr von Fls_Cancel den Fehlerzustand an NvM.
    • Fee_Cancel und MemIf_Cancel kehren synchron zurück.
  4. Folgezustand (alt request pending):
    • Zweig 1 ([no further request until next main function cycle]): Ein folgender Aufruf von Fls_MainFunction(void) durch die BSW-Task stellt fest, dass kein Auftrag ansteht, und führt keine Aktion aus.
    • Zweig 2 ([request issued before next main function cycle is due]): Trifft vor dem nächsten Hauptfunktionszyklus ein neuer Schreibauftrag (MemIf_Write -> Fee_Write -> Fls_Write) ein, prüft Fls die Hardwareverfügbarkeit. Die letzte Schreiboperation kann in der Hardware noch andauern. Nach synchroner Rückkehr setzt der nachfolgende Fls_MainFunction-Zyklus die Bearbeitung fort, sobald die Hardware wieder bereit ist.

4. Normative Relevanz & Entwickler-Hinweise

Normative und implementierungsrelevante Aspekte:

  • Die Abbruchfunktion setzt die softwareseitigen Job- und Zustandsvariablen in Fee und Fls zurück, garantiert jedoch keinen sofortigen physischen Hardware-Abbruch einer bereits im Flash-Controller laufenden Schreibsequenz.
  • Bei Abbruch eines laufenden Jobs müssen Fehlerbenachrichtigungen (JobErrorNotification) aufwärts an die übergeordneten Schichten propagiert werden, um den unvollständigen Status zu signalisieren.
  • Entwickler müssen berücksichtigen, dass nachfolgende Schreibaufträge blockieren oder verzögert werden können, solange die Hardware durch die abgebrochene Operation noch belegt (busy) ist. Die zyklische Abfrage über Fls_MainFunction synchronisiert den Hardwarezustand mit dem Treiber.
