1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR Methodology Activity & Work Product Flow (modelliert nach SPEM – Software & Systems Process Engineering Metamodel).
  • Technischer Zweck: Spezifikation des Übergangs von der netzwerkweiten Systembeschreibung zur konkreten ECU-Implementierung in der AUTOSAR Classic Platform. Es definiert die Kette von Artefakten und Werkzeug-Aktivitäten zur Erzeugung von BSW- und RTE-Code aus Konfigurationsdeskriptoren.

2. Komponenten, Entitäten & Schnittstellen

Work Products (Artefakte)
  • ECU Extract (ECU Extract, Kardinalität 1): Sub-Modell der systemweiten Systembeschreibung (SystemExtract / ARXML). Enthält Signale, PDUs, Frames, Netzwerktopologie sowie die auf diese ECU gemappten Software-Komponenten (SWC-T). Dargestellt als modulares Übergabepaket (Umschlag-Symbol mit Ports).
  • BSW Module Delivered Bundle (1..*): Lieferartefakte der BSW-Stack-Vendor für jedes Modul (MCAL, ComStack, OS, Memory usw.). Beinhaltet primär die Modul-Metamodell-Definition (BSW Module Description / BSWMD), Standardkonfigurationswerte (Vendor Specific Pre-Configuration) und die Generatormodule.
  • ECU Configuration Values (1): Zentrales Datenmodell (EcucValueCollection in ARXML). Hält alle typisierten Konfigurationsparameter (Pre-Compile, Link-Time, Post-Build) für den BSW-Stack und das RTE/OS-Mapping.
  • BSW Module Configuration Data Source Code (1): Generierter C-Quellcode (z. B. <Mod>_Lcfg.c, <Mod>_PBcfg.c) für Link-Time- und Post-Build-Deskriptortabellen.
  • BSW Module Configuration Header File (1): Generierte C-Header (z. B. <Mod>_Cfg.h) für Pre-Compile-Schalter (#define <MOD>_DEV_ERROR_DETECT STD_ON), statische Konstanten und API-Typdefinitionen.
  • RTE Source (1): Generierter Quell- und Header-Code der Runtime Environment und des Basic Software Schedulers (Rte.c, Rte_<swc>.h, Rte_Type.h, SchM_<Mod>.h).
Activities (Methoden-Aktivitäten)
  • Prepare ECU Configuration: Initialisierungsschritt des ECU-Konfigurationsprojekts; fusioniert Systemvorgaben mit Modulschablonen.
  • Configure BSW and RTE: Werkzeuggestützte Detailkonfiguration und Parameteranpassung.
  • Generate BSW and RTE: Ausführung der deterministischen Codegeneratoren (BSW-Modulgeneratoren und RTE-Generator).
Beziehungen & Stereotypen
  • «input» (Kardinalität 1 / 1..*): Gerichtete Leseabhängigkeit (ECU Extract [1] und BSW Module Delivered Bundle [1..*] → Prepare ECU Configuration; ECU Configuration Values [1] → Generate BSW and RTE).
  • «inoutput» (Kardinalität 1): Bidirektionale Modifikationsbeziehung zwischen Configure BSW and RTE und ECU Configuration Values.
  • «output» (Kardinalität 1): Gerichtete Schreib- bzw. Generierungsbeziehung (Aktivität erzeugt Ziel-Artefakt).

3. Dynamisches Verhalten & Sequenzablauf

  1. **Initialisierung (Prepare ECU Configuration):**
    • Trigger: Vorliegen des ECU Extract vom Fahrzeughersteller/Systemintegrator und der BSW Module Delivered Bundles der Modullieferanten.
    • Ablauf: Das ECU-Konfigurationswerkzeug instanziiert die ECU Configuration Values auf Basis der BSWMD-Schemata und füllt sie vorab mit Parametern aus dem System Extract (z. B. CAN-Controller-Baudraten, PDU-IDs, Signal-Packing) sowie Hersteller-Default-Werten.
  2. **Iterative Konfiguration (Configure BSW and RTE):**
    • Ablauf: Zyklischer Read-Modify-Write-Workflow («inoutput»). Der Integrator vervollständigt Parameter, die nicht im System Extract enthalten sind (z. B. Treiber-Basisadressen, Puffergrößen, Task-Prioritäten, Mapping von SWC-Runnables auf OS-Tasks, Memory-Mapping-Sektionen).
    • Validierung: Konsistenzprüfungen prüfen Constraints (z. B. EcucParamConfContainerDef, Wertebereiche, Multiplizitäten).
  3. **Codegenerierung (Generate BSW and RTE):**
    • Trigger: Validierte, konsistente ECU Configuration Values.
    • Ablauf: Synchroner Batch-Durchlauf aller modulspezifischen BSW-Generatoren und des RTE-Generators über dieselbe konsolidierte Parameterbasis.
    • Ergebnis: Parallele Emission von Pre-Compile-Headern (<Mod>_Cfg.h), Datenstruktur-Sourcen (<Mod>_[L|PB]cfg.c) sowie der RTE/SchM-Klebeschicht.

4. Normative Relevanz & Entwickler-Hinweise

  • Single Source of Truth: ECU Configuration Values bildet die exklusive semantische Quelle für BSW- und RTE-Code. Eine manuelle Modifikation der generierten C/H-Dateien ist normativ unzulässig und wird bei Re-Generierung überschrieben.
  • Variantenmanagement (Bindungszeitpunkte):
    • Parameter mit Bindung PreCompile werden direkt in die BSW Module Configuration Header Files gemappt (Präprozessor-Makros zur Code-Eliminierung ungenutzter Treiber-Features).
    • Parameter mit Bindung LinkTime oder PostBuild fließen in die BSW Module Configuration Data Source Code-Dateien (Flash-Konstantenstrukturen oder RAM-Initialisierungstabellen für <Mod>_Init(&ConfigPtr)).
  • BSW/RTE-Kopplung (SchM): Der Schritt Generate BSW and RTE generiert die Basic Software Scheduler (SchM)-Header synchron zur RTE. Task-Aktivierungen und exklusive Bereiche (ExclusiveAreas) der BSW-Treiber müssen zwingend auf die OS-Konfiguration der ECU Configuration Values abgestimmt sein.
  • Lieferketten-Trennung (OEM vs. Tier-1): Der ECU Extract definiert die feste funktionale und topologische Grenze des OEM-Systems; Abweichungen in den generierten Treibern erfordern eine Rückkopplung in den Systementwurf (Change Request des System/ECU Extracts).
