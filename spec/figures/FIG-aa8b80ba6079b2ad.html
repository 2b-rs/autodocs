1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm zur formalen Beschreibung des AUTOSAR ECUC-Parametermodells (ECUC Parameter Definition Metamodel, M2/M3-Spezifikationsebene).
  • Technischer Zweck: Definition der Konfigurationsstruktur CanIfTxPduCfg innerhalb des Moduls CanIf (CAN Interface) gemäß Release R4.1.3.
  • Funktionale Einordnung: Das CAN Interface abstrahiert den Hardware-Treiber (CanDrv) gegenüber den oberen Kommunikationsschichten (PduR, CanNm, CanTp, J1939Tp, Xcp). Der Container CanIfTxPduCfg legt für jede zu sendende L-PDU (Tx-PDU) alle statischen Eigenschaften, CAN-Identifier, Übertragungsparameter, Pufferzuordnungen und Ziel-Callbacks der oberen Schichten fest.

    • Literale: STANDARD_CAN, EXTENDED_CAN, STANDARD_FD_CAN, EXTENDED_FD_CAN.

3. Dynamisches Verhalten & Sequenzablauf

Obgleich es sich um ein statisches Konfigurationsmetamodell handelt, determiniert CanIfTxPduCfg den Kontroll- und Datenfluss zur Laufzeit:

[Upper Layer: PduR/CanTp/Nm/CDD]
            │
            │  CanIf_Transmit(CanIfTxPduId, PduInfoPtr)
            ▼
        [CanIf] ─── Validierung: CanIfTxPduId & PnFilter Status
            │
            ├─► Dynamic ID? ──► Verrechnung CanIfTxPduCanId mit CanIfTxPduCanIdMask
            ├─► Pufferung: Lookup CanIfTxPduBufferRef
            │       │
            │       ├─► Frei / Kein HTH belegt: Direktes Can_Write(Hth, PduInfo)
            │       └─► HTH busy: Speichern im Puffer (CanIfBufferCfg)
            ▼
    [CanDrv / Controller] ── Transmit auf CAN-Bus
            │
            │  CanIf_TxConfirmation(CanTxPduId) [ISR / MainFunction]
            ▼
        [CanIf]
            │
            ├─► Status-Update: Setzen des Notify-Flags (falls CanIfTxPduReadNotifyStatus == true)
            └─► Callback-Dispatch via CanIfTxPduUserTxConfirmationUL:
                    ├─► PDUR:      PduR_CanIfTxConfirmation(TxPduId)
                    ├─► CAN_TP:    CanTp_TxConfirmation(TxPduId, E_OK)
                    ├─► CAN_NM:    CanNm_TxConfirmation(TxPduId)
                    └─► CDD:       <CanIfTxPduUserTxConfirmationName>(TxPduId)
  • Fehler- und Abbruchbedingungen:
    • Ist CanIfTxPduPnFilterPdu == false, während sich der CAN-Transceiver im Partial-Networking-Schlafmodus befindet, wird der Sendeauftrag verworfen oder blockiert.
    • Wenn CanIfTxPduType == STATIC konfiguriert ist, schlägt der Versuch fehl, die ID mittels CanIf_SetDynamicTxId() neu zuzuweisen.

4. Normative Relevanz & Entwickler-Hinweise

  • Code-Generierung (CanIf_Cfg.h / CanIf_Cfg.c):
    • CanIfTxPduId erzeugt zwingend ein Symbolik-Makro (z. B. #define CanIfConf_CanIfTxPduCfg_<Name> (0x00u)). Dies dient als Handle-ID für Aufrufe von CanIf_Transmit().
    • Jeder Eintrag instanziiert ein Element in einer internen Lookup-Tabelle (z. B. CanIf_TxPduConfigType CanIf_TxPduConfig[]).
  • Post-Build-Fähigkeit (postBuildChangeable = true):
    • CanIfTxPduCfg, CanIfTxPduRef und CanIfBufferCfg unterstützen Post-Build-Selectable bzw. Post-Build-Loadable. Sendepfade und CAN-IDs können ohne Neuübersetzen des BSW-Binärcodes über Konfigurationszeiger rekonfiguriert werden.
  • Vermeidung redundanter Längenangaben:
    • CanIfTxPduDlc ist explizit als obsolet markiert (<<ecuc.useInstead>>). Die Nutzdatenlänge (DLC) muss aus CanIfTxPduRef → Pdu.length bezogen werden. Eine statische Begrenzung auf 8 Byte entfällt, wodurch CAN FD (bis zu 64 Byte via STANDARD_FD_CAN / EXTENDED_FD_CAN) unterstützt wird.
  • CDD-Integration:
    • Bei Konfiguration von CanIfTxPduUserTxConfirmationUL = CDD muss zwingend CanIfTxPduUserTxConfirmationName gesetzt sein. Der BSW-Generator deklariert diesen Funktionsprototypen als externen C-Callback.
  • Pufferzuordnung:
    • Die Entkopplung von Sendeanforderungen und blockierten Hardware-Mailboxen (HTHs) erfordert die gültige Zuweisung von CanIfTxPduBufferRef. Fehlt die Referenz, muss die PDU im BasicCAN/FullCAN-Direktsendemodus ohne CanIf-Softwarewarteschlange übertragen werden.
