1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Sequenzdiagramm mit annotierter Zustandsmaschine (State/Mode Overlays an der Komponenten-Lebenslinie).
  • Architektur-Kontext: AUTOSAR Classic Platform (CP) Communication Stack (ComStack), Spezifikation AUTOSAR_CP_SWS_FlexRayNetworkManagement (Kapitel 9.3, Use Case 03).
  • Funktionaler Zweck: Darstellung des Signal- und Kontrollflusses beim passiven Hochlauf des FlexRay-Netzwerkmanagements (FrNm) aus dem Ruhezustand (Bus Sleep Mode), bei dem noch während der Synchronisationsphase (Synchronize Mode) ein aktiver Netzwerkwunsch (Network Requested) über die generische Managementschicht (Nm) eintrifft. Veranschaulicht die Zustandswechsel bis zum Erreichen des regulären Sendebetriebs (Normal Operation State).

2. Komponenten, Entitäten & Schnittstellen

  • Akteure / BSW-Module:
    • «module» Nm: Generische Netzwerkmanagement-Schnittstelle (Koordinator zwischen Applikation/BswM und busspezifischem NM).
    • «module» FrNm: Busspezifisches FlexRay-Netzwerkmanagement (Zustands- und PDU-Handling für FlexRay).
  • Schnittstellen & Service-APIs (Synchroner Aufruf):
    • FrNm_PassiveStartUp(NetworkHandle): API-Aufruf von Nm an FrNm zur Initiierung des passiven Bus-Startups (kein Senden von NM-Botschaften angefordert).
    • FrNm_NetworkRequest(NetworkHandle): API-Aufruf von Nm an FrNm zur Anforderung des aktiven Busbetriebs.
  • Callback-Schnittstellen (Benachrichtigung an die Oberschicht):
    • Nm_StateChangeNotification(nmNetworkHandle, nmPreviousState, nmCurrentState): Asynchroner/eventgetriebener Callback von FrNm an Nm zur Signalisierung vollzogener NM-Zustandswechsel.
  • NM-Modi & Sub-Zustände (Zustandsvariablen in FrNm):
    • Modi: Bus Sleep Mode, Synchronize Mode, Network Mode.
    • Zustände innerhalb des Network Mode: Repeat Message State, Normal Operation State.
    • Anforderungszustände (Network State): Network Released → Network Requested.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialzustand: FrNm befindet sich im Bus Sleep Mode mit Status Network Released (kein Sende- oder Kommunikationsbedarf).
  2. Trigger Passiver Start: Nm ruft synchron FrNm_PassiveStartUp(NetworkHandle) auf.
    • FrNm startet den internen Startup-Mechanismus und bestätigt den Aufruf synchron (return).
  3. Zustandsübergang zu Synchronize Mode:
    • Nach Initialisierung wechselt FrNm in den Synchronize Mode.
    • FrNm meldet den Wechsel via Nm_StateChangeNotification(NetworkHandle, NM_STATE_BUS_SLEEP, NM_STATE_SYNCHRONIZE) an Nm.
  4. Aktive Netzanforderung in Synchronize Mode:
    • Vor Abschluss der Cluster-Synchronisation fordert die Applikation über Nm den Bus an: synchroner Aufruf von FrNm_NetworkRequest(NetworkHandle).
    • FrNm setzt das interne Flag auf Network Requested und quittiert den Aufruf.
  5. Eintritt in Network Mode:
    • Sobald die Synchronisation auf den FlexRay-Zyklus abgeschlossen ist, wechselt FrNm in den Network Mode und betritt dort zwingend zuerst den Repeat Message State.
    • FrNm meldet diesen Übergang an Nm via Nm_StateChangeNotification(NetworkHandle, NM_STATE_SYNCHRONIZE, NM_STATE_REPEAT_MESSAGE).
  6. Folgeübergang nach Timerablauf:
    • Nach Ablauf des Repeat-Message-Timers (FrNmRepeatMessageTime) prüft FrNm den Netzwerkstatus:
    • Da zuvor FrNm_NetworkRequest abgesetzt wurde (Network Requested), wechselt FrNm deterministisch in den Normal Operation State (anstatt in den Ready Sleep State, der bei rein passivem Startup gewählt worden wäre).

4. Normative Relevanz & Entwickler-Hinweise

  • Pufferung des Netzwunsches: Trifft FrNm_NetworkRequest() im Zustand Synchronize Mode ein, darf der Aufruf weder verworfen noch mit Fehler quittiert werden. Das Modul muss die Anforderung intern zwischenspeichern (Network Requested).
  • Zustandspfad-Gabelung:
    • Reiner passiver Startup: Synchronize Mode → Repeat Message State → Ready Sleep State.
    • Passiver Startup mit zwischenzeitlichem Request (dieser Fall): Synchronize Mode → Repeat Message State → Normal Operation State.
  • Konfigurationsparameter & Callbacks:
    • Für Nm_StateChangeNotification muss FrNmStateChangeIndEnabled == TRUE konfiguriert sein, andernfalls entfallen die Benachrichtigungen an das Nm-Modul.
    • Das FlexRay-Cluster-Timing (FlexRay-Makroticks, Zykluslänge) bestimmt die Verweildauer im Synchronize Mode bis zum Erreichen der globalen Synchronität (FrIf / FlexRay-CC).
  • Asynchroner Stack-Vertrag: Der Entwickler darf im Aufrufkontext von FrNm_NetworkRequest() nicht davon ausgehen, dass der Bus sofort aktiv sendet. Das Senden von NM-PDUs beginnt erst mit Eintritt in den Network Mode / Repeat Message State.
