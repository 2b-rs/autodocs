1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Gantt-basiertes Zeitablauf- und Job-Level-Scheduling-Trace-Diagramm (Timing Analysis Trace) mit annotierter Ursache-Wirkungs-Kette (Cause-Effect Chain) über mehrere Task-Hierarchien.
  • Technischer Zweck & funktionale Einordnung:
    • Spezifikationskontext: AUTOSAR_FO_TR_TimingAnalysis (Foundation, R23-11/R24-11), Kapitel Timing Analysis and Design.
    • Nachweis des Verlusts von Datenfluss-Determinismus (Missing Data-Flow Determinism) in prioritätsbasierten präemptiven Echtzeitsystemen bei Verwendung impliziter Kommunikationssemantik (Read-Execute-Write).
    • Visualisierung von datenabhängigen Jitter-Effekten und Laufzeitschwankungen (Execution Time Variations zwischen BCET und WCET) auf die relative Datenfrische (Data Age) entlang einer ereignisgesteuerten Wirkkette (TimingDescriptionEventChain).

2. Komponenten, Entitäten & Schnittstellen

  • Periodische Tasks (Schedulable Entities / OS Tasks):
    • Task 1: Erzeuger-Task (Producer), Periodendauer T_1 = 10\,ms, fixe periodische Aktivierung.
    • Task 2: Vermittler-/Verarbeitungs-Task (Intermediate Processor), Periodendauer T_2 = 20\,ms, niedrigere Priorität als Task 1 und Task 3. Schraffierte Flächen kennzeichnen Unterbrechungszustände (Preemption durch höherpriore Tasks).
    • Task 3: Verbraucher-Task (Consumer), Periodendauer T_3 = 5\,ms, höchste Aktivierungsfrequenz (4 Jobs pro Hyperperiode).
  • Hyperperiode:
    • $\text{Hyperperiod} = \text{kgV}(10\,\text{ms}, 20\,\text{ms}, 5\,\text{ms}) = 20\,\text{ms}$.
  • Job-Ebene & Instanziierung:
    • Diskrete Aktivierungsinstanzen (Jobs) der Schedulable Entities. Vertikale Pfeile markieren Aktivierungstrigger (Task Activation Events).
  • Kommunikationsschnittstellen & Pufferung:
    • Implizite Kommunikation: Schwarze vertikale Balken an den Flanken jedes Jobs markieren atomare Phasen:
      • Linker schwarzer Balken: Lesephase bei Job-Start (Eingangskopie via lokaler Variable / Rte_IRead).
      • Rechter schwarzer Balken: Schreib-/Veröffentlichungsphase bei Job-Terminierung (Rte_IWrite).
    • Farbkodierte Datenblöcke (Grün, Blau, Rot) repräsentieren distinkte Datengenerationen/-inhalte entlang der Kette Task 1 → Task 2 → Task 3.

3. Dynamisches Verhalten & Sequenzablauf

  1. Hyperperiode 1 (Grüne Datengeneration):
    • Task 1 produziert grüne Daten und publiziert diese zum Ende von Job 1.
    • Task 2 liest diese Daten bei Aktivierung ein, erfährt geringe Preemption und terminiert vor dem Start des 3. Jobs von Task 3.
    • Der 3. Job von Task 3 (orange umrandet) liest deterministisch die neue grüne Datengeneration von Task 2.
  2. Hyperperiode 2 (Blaue Datengeneration):
    • Task 1 erzeugt blaue Daten.
    • Task 2 liest blaue Daten; trotz Preemption durch Task 1 und Task 3 schließt Task 2 vor Job 3 von Task 3 ab.
    • Der 3. Job von Task 3 liest erfolgreich die neuen blauen Daten (Dotted Arrow zu Task 2 Job 2).
  3. Hyperperiode 3 (Rote Datengeneration – Verlust des Determinismus):
    • Task 1 weist eine verlängerte Ausführungszeit auf (roter Block in Task 1).
    • Task 2 startet verspätet und wird wiederholt durch Task 1 und Task 3 präemptiert (hoher Anteil schraffierter Preemption-Phasen).
    • Kritischer Race-Zustand: Der 3. Job von Task 3 (orange markiert) wird aktiviert und liest seine Eingangsdaten ein, bevor Task 2 (rot) beendet ist.
    • Konsequenz: Der 3. Job liest nicht die roten Daten, sondern verbleibt auf dem vorherigen Datenstand (blau, illustriert durch die gestrichelte Rückwärts-Referenz). Erst der 4. Job von Task 3 erhält den roten Datenstand.
    • Innerhalb der identischen relativen Phasenlage (Job 3 von Task 3) variiert das gelesene Datenalter über verschiedene Hyperperioden rein in Abhängigkeit der Ausführungszeitfluktuationen vorgelagerter Knoten.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Kommunikationssemantik:
    • Das implizite Kommunikationsmodell (Rte_IRead_* / Rte_IWrite_* gem. AUTOSAR_SWS_RTE) sichert Datenkonsistenz (Torn-Read Protection) durch Kopieren auf Job-Ebene ab, bietet jedoch keine deterministische Latenz oder feste Datenfrische (Data Age Stability).
  • Regelungstechnische Implikationen:
    • Jitter im Datenfluss führt zu Totzeitvariationen in geschlossenen Regelkreisen (Closed-Loop Control), was zu Phasensprüngen, Signalverzerrungen und Instabilitäten in zeitkritischen ADAS/Chassis-Funktionen führt.
  • Architektonische Gegenmaßnahmen:
    • Logical Execution Time (LET): Migration auf das LET-Paradigma (AUTOSAR_TPS_TimingExtensions, LET-Mechanismen in der RTE ab R20-11). Ein- und Auslesezeitpunkte werden fest an Aktivierungs- und Deadline-Grenzen entkoppelt.
    • Deterministische Synchronisation: Konfiguration von deterministischen OS-Schedule-Tables mit ausreichenden Offsets oder Nutzung von expliziter Pufferkommunikation mit Sequenznummern/Time-Stamps zur Validierung der Datenfrische.
    • Timing-Verifikation: Modellierung von LatencyTimingConstraint und AgeTimingConstraint auf TimingDescriptionEventChain-Ebene, um WCET- und Blocking-Budget-Grenzen im AUTOSAR Timing Model formal nachzuweisen.
