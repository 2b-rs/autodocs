Figure 7.2: Example for calling Adc_ReadGroup which copies results from Result Buffer to optional Read Buffer

1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Datenfluss- und Speicherabbild-Diagramm (Memory Buffer Mapping & Data Flow) zwischen Hardware-, MCAL- und Applikationsebene.
  • Technischer Zweck: Visualisierung des zweistufigen Pufferkonzepts des AUTOSAR ADC-Treibers (MCAL, Microcontroller Abstraction Layer) bei Verwendung der synchronen API Adc_ReadGroup.
  • Funktionale Einordnung: Entkopplung der asynchronen Hardware-Wandlung (ADC HW / Interrupts / DMA) vom synchronen Zugriff der Applikation/SWC. Verdeutlicht den Unterschied zwischen dem obligatorischen Streaming-/Ergebnis-Puffer (ResultBuffer) und dem anwendungsseitigen Zielpuffer (ReadBuffer).

2. Komponenten, Entitäten & Schnittstellen

  • ADC HW (Hardware-Ebene):
  • HW result register: Peripherie-Ergebnisregister des Mikrocontrollers.
  • Constraint: Kein direkter Registerzugriff über AUTOSAR ADC APIs durch die Applikation (no direct access via ADC API functions supported).
  • ADC Driver (MCAL-Ebene):
  • Vermittelt den Datentransfer (per Interrupt-Serviceroutine oder DMA) von den Hardware-Registern in den Applikations-Result-Buffer.
  • Stellt die synchrone API Std_ReturnType Adc_ReadGroup(Adc_GroupType Group, Adc_ValueGroupType* DataBufferPtr) bereit.
  • Application (Applikationsebene – Result Buffer, obligatorisch):
  • Speicherbereich vom Typ Adc_ValueGroupType[], der vor dem Start der Konvertierung via Adc_SetupResultBuffer() an den Treiber übergeben werden muss.
  • G1_ResultBuffer[6]: Kanalgruppe 1 mit 2 Kanälen (G1-CH0, G1-CH1) und Streaming-Puffertiefe 3 (Streaming Access Mode: $2 \times 3 = 6$ Elemente). Datenorganisation: Kanalweise Gruppierung über mehrere Wandlungsrunden.
  • G2_ResultBuffer[2]: Kanalgruppe 2 mit 1 Kanal (G2-CH2) und Puffertiefe 2.
  • G3_ResultBuffer[1]: Kanalgruppe 3 mit 1 Kanal (G3-CH3) und Puffertiefe 1 (Single Value / Circular/Linear Buffer).
  • Application (Applikationsebene – Read Buffer, optional/API-spezifisch):
  • Zielpuffer, der als Argument DataBufferPtr an Adc_ReadGroup() übergeben wird.
  • G1_ReadBuffer[2]: Dimensioniert auf die exakte Anzahl der konfigurierten Kanäle der Gruppe 1 (hier 2 Elemente: je 1 Wert für CH0 und CH1).
  • G2_G3_ReadBuffer[1]: Generischer Puffer (Größe 1), der von der Applikation für Gruppen mit identischer Kanalanzahl (G2 und G3) wiederverwendet werden kann.
  • Ergebnis-Zustände (Schraffur):
  • Schraffiert: result of last conversion round – jeweils der gültige Abtastwert der zuletzt vollständig abgeschlossenen Wandlungsrunde der jeweiligen Gruppe.
  • Leer: Ältere historische Abtastwerte im Ring-/Streaming-Puffer.

3. Dynamisches Verhalten & Sequenzablauf

  1. Puffer-Initialisierung (Voraussetzung):
  • Aufruf von Adc_SetupResultBuffer(GroupId, &G1_ResultBuffer[0]).
  1. Asynchrone Konvertierung & MCAL-Transfer:
  • Triggerung der Gruppenkonvertierung (Software- oder Hardware-Trigger via Adc_StartGroupConversion).
  • Der ADC-Treiber / DMA transferiert Rohwerte aus den HW result register in den zugewiesenen G<x>_ResultBuffer. Im Streaming-Modus zirkulieren die Indizes; die jüngste Wandlungsrunde markiert den aktuellen Datensatz (schraffierte Blöcke).
  1. Synchrone Datenabholung (Adc_ReadGroup):
  • Die Applikation ruft synchron Adc_ReadGroup(GroupId, DataBufferPtr) auf.
  • Der Treiber ermittelt atomar die Werte der letzten abgeschlossenen Wandlungsrunde aus dem Streaming-Puffer.
  • Kopieroperation: Der Treiber kopiert genau einen Wert pro Kanal aus G<x>_ResultBuffer in den Zielspeicher G<x>_ReadBuffer (z. B. jeweils den jüngsten Wert von G1-CH0 und G1-CH1).
  1. Fehlerbehandlung / Statusbedingungen:
  • Ist keine Konvertierung abgeschlossen (ADC_IDLE oder laufende erste Konvertierung), liefert Adc_ReadGroup den Rückgabewert E_NOT_OK.
  • Bei aktivierter Entwicklungsfehlererkennung prüft Adc_ReadGroup auf uninitialisierten Treiber (ADC_E_UNINIT), ungültige Gruppen-ID (ADC_E_PARAM_GROUP) oder Null-Pointer (ADC_E_PARAM_POINTER).

4. Normative Relevanz & Entwickler-Hinweise

  • Puffer-Dimensionierung (API-Vertrag):
  • ResultBuffer: Mindestgröße $= \text{Anzahl Kanäle in Gruppe} \times \text{AdcStreamingNumSamples}$ (aus Konfigurationsparameter AdcStreamingNumSamples).
  • ReadBuffer: Mindestgröße $= \text{Anzahl Kanäle in Gruppe}$ (definiert über Container AdcChannelSignature / AdcGroupDefinition). Ein zu kleiner Read-Buffer führt zu Memory Corruption (Buffer Overflow), da die API keine Puffergröße als Parameter übergeben bekommt.
  • Speicher-Allokation:
  • Beide Puffer liegen im RAM-Bereich der Applikation (Caller-allocated memory). Der ADC-Treiber allokiert keinen dynamischen Speicher.
  • Kanalreihenfolge im ReadBuffer:
  • Die Daten werden im ReadBuffer strikt in der Reihenfolge abgelegt, wie die Kanäle in der Gruppenkonfiguration (AdcGroupDefinition) indiziert sind.
  • Puffer-Wiederverwendung:
  • Das Schaubild belegt normativ, dass ein einzelner ReadBuffer sequenziell für mehrere Gruppen genutzt werden darf (G2_G3_ReadBuffer[1]), sofern dessen Kapazität für die Kanalanzahl der jeweils abgefragten Gruppe ausreicht.
  • Performance- / Konsistenz-Implikation:
  • Adc_ReadGroup führt einen synchronen Speicher-Kopiervorgang (memcpy / Schleife) im Kontext des Aufrufers durch.
  • Für kritische Abtastraten oder kontinuierliche Datenerfassung ohne CPU-Kopier-Overhead kann die Applikation alternativ direkt auf den ResultBuffer zugreifen, erfordert dann jedoch externe Synchronisation (z. B. über Adc_GetGroupStatus oder Notification Callbacks).
