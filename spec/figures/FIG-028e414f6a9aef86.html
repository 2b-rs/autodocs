1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR M1-Instanzmodell / Konfigurationsmodell (UML-Objektdiagramm-Äquivalent) des System Templates (AUTOSAR_CP_TPS_SystemTemplate).
  • Funktionaler Kontext: Modellierung der Segmentierung von Client-Server-Methodenaufrufen über das SOME/IP Transport Protocol (SOME/IP-TP) bei gleichzeitiger/paralleler Verarbeitung mehrerer Methodenaufrufe bzw. Antworten (Concurrent Processing).
  • Systemeinordnung: Schlägt die Brücke zwischen der VFB/RTE-Dienstebene (ClientServerToSignalMapping), der Signal-/PDU-Definition im COM-Stack (ISignal, ISignalIPdu) und der TP-Segmentierungsschicht (SomeipTpConnection) hinab zur serialisierten Übertragung über Ethernet-Controller/Ports (Ch1 Port).

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Rollen (Instanzebene)

  • Client-Server-Mapping:
  • ClientServerToSignalMapping: Verbindet ein AUTOSAR-Client-Server-Interface mit COM-Systemsignalen über die Rollen callSignal und returnSignal.
  • SystemSignalCall / SystemSignalReturn: Repräsentieren die serialisierten Payloads für Request- (Call) und Response-Transaktionen (Return).
  • Signal- und Signal-PDU-Schicht (grün codiert):
  • ISignalC1, ISignalC2 / ISignalR1, ISignalR2: Separate ISignal-Instanzen für parallele Verarbeitungsstränge (Concurrent Instances 1 & 2).
  • ISignalToIPduMapping: Ordnet jedes Einzelsignal einer dedizierten Signal-PDU zu (ISignalPduC1, ISignalPduC2 bzw. ISignalPduR1, ISignalPduR2).
  • Triggering-Schicht (gelb codiert):
  • ISignalTriggering: Weist den Einzelsignalen einen Trigger auf einem physischen Kanal zu.
  • IPduTriggering: Verwaltet die Übertragungs-/Empfangstrigger der jeweiligen ISignalPdus sowie der transportierten Segment-PDUs auf dem Kanal (Ch1 Port).
  • SOME/IP-TP Schicht (weiß/schwarz codiert):
  • SomeipTpConnection Call / SomeipTpConnection Return: Beschreibt die Segmentierungs- und De-Segmentierungs-Konfiguration für Request und Response.
  • Referenz tpConcurrentProcessingSdu (Kardinalität 1..*): Referenziert mehrere IPduTriggering-Instanzen (ISignalPduC1/C2 bzw. ISignalPduR1/R2), um mehrere parallele Session-/Verarbeitungskontexte auf denselben TP-Kanal zu bündeln.
  • Referenz transportPdu (Kardinalität 1): Referenziert die resultierende segmentierte PDU (GeneralPurposeIPdu).
  • Transport-PDUs & Cluster-Zuordnung:
  • GeneralPurposeIPdu (Category: SOMEIP_SEGMENTED_IPDU): Repräsentiert die über den Bus übertragene, segmentierte SOME/IP-PDU (inkl. SOME/IP-TP Header: Message ID, Length, Request ID, Protocol Version, Interface Version, Message Type mit TP-Flag 0x20 bzw. 0x21, Offset und More-Segments-Flag).
  • Ch1 Port IN / OUT: Physischer Kommunikationsanschluss am Ethernet-Cluster (im Schaubild: Server-Konfiguration mit IN für Request-Empfang und OUT für Response-Versand).

3. Dynamisches Verhalten & Sequenzablauf

  1. Paralleler Request-Empfang (Call-Pfad, links / IN):
  • Über Ch1 Port (IN) treffen segmentierte SOME/IP-PDUs (GeneralPurposeIPdu Call, Category SOMEIP_SEGMENTED_IPDU) ein.
  • Das SomeipTp-Modul reassembliert Segmente anhand der Session ID im SOME/IP-Header.
  • Mittels tpConcurrentProcessingSdu werden mehrere simultane Requests unterschiedlichen Empfangskontexten zugeordnet: Puffer 1 reassembliert zu ISignalPduC1, Puffer 2 parallel zu ISignalPduC2.
  • Nach erfolgreicher Reassemblierung signalisiert das TP-Modul an die IPduTriggering der fertigen PDU weiter, welche via COM als ISignalC1 bzw. ISignalC2 entpackt und der RTE für die Server-Runnable bereitgestellt wird.
  1. Paralleler Response-Versand (Return-Pfad, rechts / OUT):
  • Die Server-Applikation schließt Berechnungen ab; COM übergibt ISignalPduR1 bzw. ISignalPduR2 als vollständige SDUs an das SomeipTp-Modul.
  • SomeipTpConnection Return teilt die SDU beider paralleler Kanäle in Segmente auf (max. Segmentgröße determiniert durch konfigurierte TP-PDU-Länge minus SOME/IP- und TP-Header, Vielfaches von 16 Bytes).
  • Segmente werden als GeneralPurposeIPdu Return über IPduTriggering an Ch1 Port (OUT) sequenziell auf den Bus gemultiplext.

4. Normative Relevanz & Entwickler-Hinweise

  • PDU-Router & COM-Konfiguration (ComStack / BSW):
  • GeneralPurposeIPdu mit Category SOMEIP_SEGMENTED_IPDU erfordert im BSW-Stack (PduR / SomeIpTp) eine statische Pufferallokation pro deklariertem Concurrent-Channel (ISignalPduC1..n).
  • Da SomeipTpConnection mehrere tpConcurrentProcessingSdu auf dieselbe transportPdu mappt, muss der SOME/IP-TP-Treiber Reassembly-Puffer für $N$ parallele Nachrichteninstanzen instanziieren ($N = \text{Anzahl referenzierter } \mathtt{IPduTriggering}$).
  • Session-ID-Handling:
  • Senderseitig muss jede concurrent Nachricht über eine eindeutige Session ID im SOME/IP-Header differenziert werden. Bei erschöpftem Session-ID-Bereich oder Pufferüberlauf drohen Paketverwerfungen oder Session-Kollisionen.
  • Header-Constraints & Ausrichtung:
  • Alle Segmente bis auf das letzte müssen eine Payload aufweisen, deren Länge ein ganzzahliges Vielfaches von 16 Byte beträgt (SOME/IP-TP-Payload-Alignment).
  • Speicher- & Task-Dimensionierung:
  • Für Embedded-Entwickler bedingt die parallele Verarbeitung (tpConcurrentProcessingSdu) einen linearen Anstieg des RAM-Bedarfs im SomeIpTp (Reassembly- und Transmission-Ringpuffer müssen für jeden Zweig $C_x$ bzw. $R_x$ simultan vorgehalten werden). Fehlt Pufferkapazität, führt dies zu TP-Pufferfehlern (BUFREQ_E_OVFL).
