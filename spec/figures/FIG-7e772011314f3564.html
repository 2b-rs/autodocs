1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Speicherauszug / Lineares Speicherlayout-Diagramm (Memory Representation / Stream Layout) für mehrdimensionale Kalibrier- und Stützstellendaten.
  • Technischer Zweck: Spezifikation der standardisierten Serialisierungs- und Speicherreihenfolge für zweidimensionale Kennfelder (MAP / 2D Lookup Tables) im Adressraum (Flash/RAM).
  • Funktionale Einordnung: Definiert im Ergänzungsband AUTOSAR_TR_GeneralBlueprintsSupplement (Abschnitt zu Application Data Types und Standardized Calibration Data Types). Es sichert die binäre und semantische Interoperabilität zwischen:
  • AUTOSAR Application Software Components (SWCs) bzw. BSW-Interpolationsroutinen (z. B. BFX / Ifl).
  • RTE-generierten Datentypen und Zugriffsmakros.
  • Kalibrier-, Mess- und Flashtools via ASAM MCD-2 MC (A2L) / XCP.

2. Komponenten, Entitäten & Schnittstellen

  • Datenstrukturelemente & Indizierung:
  • Das Diagramm definiert einen zusammenhängenden Speicherblock (Contiguous Memory Array) aus Funktionswerten $f(x, y)$ eines zweidimensionalen Kennfeldes mit Gittergröße $N_x \times N_y$.
  • Koordinatendarstellung $[x, y]$:
  • $x \in \{1, 2, 3, \dots, -1\}$: Diskreter Index der ersten Achse / Dimension (typischerweise $X$-Achse bzw. Input Variable 1). Der Wert -1 indiziert normativ das letzte Stützstellenelement $N_x$ dieser Achse.
  • $y \in \{1, 2, 3, 4, \dots, -1\}$: Diskreter Index der zweiten Achse / Dimension (typischerweise $Y$-Achse bzw. Input Variable 2). Der Wert -1 indiziert das letzte Element $N_y$ der zweiten Achse.
  • Element [-1, -1]: Letztes Werteelement des gesamten Kennfelds bei maximaler Ausprägung beider Dimensionen ($[N_x, N_y]$).
  • Serialisierungsreihenfolge:
  • Schnell variierender Index: Erste Dimension $x$. Aufeinanderfolgende Adressen enthalten sequenziell $[1, 1], [2, 1], [3, 1], \dots, [-1, 1]$.
  • Langsam variierender Index: Zweite Dimension $y$. Erst nach vollständiger Speicherung aller $x$-Werte einer Zeile folgt die nächste Zeile $y+1$ ($[1, 2], [2, 2], \dots$).
  • Die gestrichelten Pfeile symbolisieren den linearen, kontinuierlich ansteigenden Adressfortschritt über Zeilenumbrüche hinweg.
  • AUTOSAR-Metamodellbezug:
  • Abbildung über ein ApplicationPrimitiveDataType der Kategorie MAP bzw. zugehöriges ImplementationDataType.
  • Das genaue Ablagemuster wird über SwRecordLayout (z. B. Map_f32, Map_u16) und hierarchische SwRecordLayoutGroups parametriert, wobei der Indexzähler der inneren Schleife auf die $X$-Achse gemappt ist.

3. Dynamisches Verhalten & Sequenzablauf

  • Laufzeitzugriff & Adressberechnung:
  • Bei synchronem Lookup durch Interpolationsbibliotheken (Bfx / Ifl) oder Applikations-Runnables erfolgt die Adressierung über 0-basierte Indizes ($i_x \in [0, N_x - 1]$, $i_y \in [0, N_y - 1]$):

$$\text{Address}(i_x, i_y) = \text{BaseAddress} + (i_y \cdot N_x + i_x) \cdot \text{sizeof}(\text{ElementType})$$

  • Nebenläufigkeit & Kalibration (XCP):
  • Werden Kennfelder im laufenden Betrieb über XCP/Calibration-Toolchains modifiziert, greift das Mess-/Kalibrierwerkzeug anhand der A2L-Adressberechnung direkt linear auf diesen Block zu.
  • Zur Sicherstellung der Datenkonsistenz über das gesamte Kennfeld (Schutz vor Inkonsistenzen bei interpolierten Zwischenwerten während eines Schreibvorgangs) müssen ggf. Doppelbufferungsmechanismen oder RTE-Konsistenzmechanismen (z. B. OS-Interruptsperren/Spinlocks oder Page-Switching) verwendet werden.

4. Normative Relevanz & Entwickler-Hinweise

  • C-Deklaration & Speicherabbildung:
  • Entspricht in C einem 2D-Array der Dimensionierung ElementType Map[Ny][Nx] (in Standard-C Row-Major mit innerem Index $x$) oder einem flachen 1D-Array ElementType Map[Ny * Nx].
  • Achtung: Eine Deklaration als ElementType Map[Nx][Ny] invertiert die Speicheranordnung relativ zur Achsenbelegung und führt zu transponierten Interpolationsergebnissen.
  • Ausschuss von Compiler-Padding:
  • Es darf kein compiler-spezifisches Padding zwischen Zeilenenden ($[-1, k]$) und dem nächsten Zeilenbeginn ($[1, k+1]$) generiert werden. Die Speicherung muss strikt packed/lückenlos erfolgen (Absicherung über Compiler-Abstraktion in MemMap.h / Compiler-Pragmas).
  • Trennung von Achsen und Funktionswerten:
  • Das Diagramm stellt isoliert die Wertetabelle (FNC_VALUES) dar. Stützstellenachsen (AXIS_PTS) werden je nach definiertem SwRecordLayout entweder getrennt allokiert (COM_AXIS, STD_AXIS) oder müssen gemäß Blueprint-Spezifikation dem Werteblock an festen Offsets vorangestellt werden.
  • A2L-Generierung (ASAM MCD-2 MC):
  • Konfigurationswerkzeuge müssen beim Export des A2L-Files sicherstellen, dass die Matrix-Direktive zur Orientierung (ROW_DIR vs. COLUMN_DIR) exakt zur Festlegung im AUTOSAR SwRecordLayout korrespondiert. Diskrepanzen führen zu gespiegelten Kennfeldern im Kalibriertool.
