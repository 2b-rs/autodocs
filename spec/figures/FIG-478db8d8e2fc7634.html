1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Statisches Schichten- und Architekturmodell (AUTOSAR Layered Software Architecture Pattern).
  • Technischer Zweck: Referenzarchitektur der AUTOSAR Classic Platform (CP) zur Entkopplung hardwareunabhängiger Anwendungssoftware von hardwarenahen Treibern und Basisfunktionen. Sie definiert die Partitionierung in standardisierte Schichten und vertikale Funktionsdomänen (Stacks) sowie die Integrationsgrenzen für die Parametrierung nach AUTOSAR_CP_TPS_ECUConfiguration.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm strukturiert das System in drei übergeordnete Schichten, unterteilt in Funktionsdomänen und ergänzt durch eine vertikale Bypass-Entität:

  • Application Layer (Software-Schicht):
    • Beherbergt atomare und kompositionelle Software-Components (SWCs, z. B. Application SWCs, Sensor/Actuator SWCs).
    • Vollständig hardwareunabhängig; nutzt ausschließlich Ports und typisierte Interfaces.
  • AUTOSAR Runtime Environment (RTE):
    • Realisiert das Virtual Functional Bus (VFB)-Konzept auf ECU-Ebene.
    • Trennt die Applikation von der BSW; bietet standardisierte Laufzeit-APIs (Rte_Read, Rte_Write, Rte_Call).
  • Basic Software (BSW) – Horizontale Schichten:
    1. Services Layer (Dienste-Ebene):
      • System Services: Modulübergreifende Funktionen (z. B. OS, EcuM, BswM, WdgM, Det, Dem). Reicht im Layout bis an die Treiber-/Microcontroller-Grenze heran, da z. B. das OS direkte Prozessorressourcen (Core, Timer) steuert.
      • Memory Services: Vereinheitlichter Nichtflüchtigmesspeicher-Zugriff (NvM).
      • Communication Services: Protokollunabhängiges PDU-Routing und Signalverwaltung (COM, PduR, IPduM, SecOC, Netzwerkmanagement wie CanNm).
    2. ECU Abstraction Layer (Steuergeräte-Abstraktionsebene):
      • Kapselt periphere ECU-Hardware und Board-Layout.
      • Onboard Device Abstraction: Ansteuerung steuergeräteeigener On-Board-Peripherie.
      • Memory Hardware Abstraction: Einheitliche Schnittstelle (MemIf) zu Flash- (Fee) und EEPROM-Abstraktionen (Ea).
      • Communication Hardware Abstraction: Bus-Interfaces (CanIf, LinIf, FrIf, EthIf) zur Kapselung interner/externer Transceiver und Controller.
      • I/O Hardware Abstraction: Direkte Verbindung von Signal-E/A (IoHwAb) zu den I/O-Treibern ohne separate Zwischen-Services.
    3. Microcontroller Abstraction Layer (MCAL):
      • Hardwarenahe Treiberschicht mit direktem Zugriff auf Core- und Controller-Register.
      • Microcontroller Drivers: Core-nahe Treiber (MCU, GPT, WDG).
      • Memory Drivers: Interne/externe Treiber (Fls, Eep).
      • Communication Drivers: Controller-Treiber (Can, Lin, Fr, Eth).
      • I/O Drivers: Digitale/analoge Signal- und Porttreiber (Port, Dio, Adc, Pwm, Icu).
    4. Complex Drivers (CDD / Komplexe Treiber):
      • Vertikale Entität, die vom RTE-Interface bis zum Microcontroller durchgreift.
      • Dient der Implementierung nicht-standardisierter Protokolle, zeitkritischer Regelschleifen (z. B. Einspritzung, Motorsteuerung) oder proprietärer Hardwareansteuerungen unter Umgehung des Schichten-Overheads.
  • Schnittstellen-Kategorien (implizit verankert):
    • AUTOSAR Interface: Port-basierte Kommunikation zwischen SWCs sowie zwischen SWCs und der RTE.
    • Standardized AUTOSAR Interface: Vordefinierte Service-Ports für SWC-BSW-Interaktion (z. B. Dem, NvM, ComM).
    • Standardized Interface: Direkte C-Funktionsaufrufe (APIs) zwischen den BSW-Modulen (z. B. PduR ↔ CanIf, CanIf ↔ Can).

3. Dynamisches Verhalten & Kontrollfluss

Das Modell definiert vertikale Signal-, Daten- und Steuerpfade über synchrone und asynchrone Kommunikationskanäle:

  • Top-Down-Pfad (Transmission / Request):
    • SWC triggert Datentransfer via Rte_Write / Rte_Call.
    • RTE leitet an die Service-Schicht weiter (z. B. Com_SendSignal).
    • Signal-Packing zu I-PDUs → PduR → Übergabe an Hardware-Abstraktion (z. B. CanIf_Transmit) → MCAL-Treiber (z. B. Can_Write) → Microcontroller CAN-Mailbox.
  • Bottom-Up-Pfad (Reception / Event-Triggered):
    • Hardware-Interrupt (ISR) im Microcontroller → MCAL-Handler verarbeitet Empfang und signalisiert an die Hardware-Abstraktion (<Bus>If_RxIndication).
    • Weiterleitung via PduR an BSW-Services (z. B. Com_RxIndication).
    • Entpacken der Signale und Bereitstellung im RTE-Buffer; optional Aktivierung verknüpfter Runnable Entities via RTE Events (DataReceivedEvent).
  • Querverbindungen & Diagnosepfade:
    • Alle BSW-Module und CDDs melden Laufzeit- und Entwicklungsfehler synchron an den Det (Det_ReportError) bzw. produktionsrelevante Fehlerevents an den Dem (Dem_SetEventStatus).
    • Das OS orchestriert zyklische und eventbasierte Tasks (z. B. periodische Aufrufe von <Modul>_MainFunction).

4. Normative Relevanz & Entwickler-Hinweise

  • MCAL-Treiberentwickler:
    • Treiber dürfen ausschließlich auf eigene Microcontroller-Register und Systemressourcen zugreifen.
    • Striktes Verbot des direkten Zugriffs auf übergeordnete Schichten; Benachrichtigung nach oben darf nur über definierte Funktions-Callbacks (<UpperLayer>_RxIndication, <UpperLayer>_TxConfirmation) erfolgen.
  • BSW- und Stack-Integratoren (TPS_ECUConfiguration):
    • Jedes Modul erfordert eine formale Parametrierung im AUTOSAR-XML-Format (ARXML) gemäß BSW Module Description (BSWMD) und ECU Configuration Description (ECUC).
    • Schichten-Bypässe zwischen Standardmodulen (z. B. direkter Aufruf von MCAL-Treibern aus Communication Services ohne Interface-Zwischenschicht) sind normativ unzulässig und führen zu Architektur-Inkonsistenzen.
  • Applikations-Entwickler:
    • SWCs besitzen keinerlei Kenntnis über Hardware, Busse (CAN/LIN/Ethernet) oder Speichertypen. Zugriff auf E/A erfolgt abstrahiert über Service-Ports (z. B. IoHwAb-Ports) oder RTE-Signalports.
  • Einsatz von Complex Drivers (CDD):
    • CDDs sind anwendungsspezifisch zu kapseln. Da sie die Hardwareabstraktion umgehen, muss die Schnittstelle zur RTE explizit als AUTOSAR-Portmodell in der ARXML modelliert werden, um die Portabilität des Application Layers nicht zu verletzen.
