1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: SPEM 2.0-Prozess-/Aktivitätsdiagramm (Software & Systems Process Engineering Metamodel, profiliert in UML).
  • Technischer Zweck: Spezifikation des methodischen Teilprozesses „Design Basic Software“ (Figure 2.23, AUTOSAR_TR_Methodology, R4.0.3).
  • Funktionale Einordnung: Definiert die formalen Entwurfsschritte, Abhängigkeiten und Work Products zur Erstellung der maschinenlesbaren BSW-Beschreibungsdateien (ARXML). Es beschreibt den Übergang von standardisierten Spezifikationen (AUTOSAR BSW-Standards) zu hersteller- und modulspezifischen Metadaten (BswModuleDescription und EcucModuleDef), die als Eingangsartefakte für Codegeneratoren, RTE/BswScheduler und BSW-Konfiguratoren dienen.

2. Komponenten, Entitäten & Schnittstellen

SPEM-Tasks (Prozessschritte / Aktivitäten)
  • Define BSW Types: Deklaration modulspezifischer und generischer BSW-Datentypen (z. B. ImplementationDataType, SwBaseType, Type-Mappings).
  • Define BSW Entries: Signatur- und Funktionsdefinition der BSW-Einsprungspunkte (C-APIs, Callbacks, Main Functions, ISR-Handler).
  • Define BSW Interfaces: Aggregation und Strukturierung des Modulverhaltens, Zuordnung von Entries zu Modulen, Speicherbereichen, Exklusivbereichen und Schnittstellen.
  • Define Vendor Specific Module Definition: Ableitung und Erweiterung der standardisierten Konfigurationsparameter um vendorspezifische Parameter.
SPEM-Work-Products (Metamodell-Artefakte)
  • BSW Standard Package: Standardisiertes AUTOSAR-Paket, aggregiert über «SPEM_Aggregation» (Kardinalität 1) die AUTOSAR Standardized ECU Configuration Parameter Definition.
  • AUTOSAR Standardized ECU Configuration Parameter Definition: Normative Basiskonfigurationsstruktur (EcucModuleDef des AUTOSAR-Standards).
  • BSW Types: Datentyp-Beschreibungen für C-Basis- und Verbundtypen.
  • Basic Software Entries: Instanzen des Metaklassen-Typs BswModuleEntry (Funktionsprototypen, Reentrancy-Attribute, Call-Contexts).
  • ECU Resources Description: HW-Ressourcen-Metadaten (Interruptvektoren, Core-Zuweisungen, Speicherblöcke, I/O-Peripherie).
  • Basic Software Module Description (BSWMD): Vollständige Modulbeschreibung (BswModuleDescription inkl. BswInternalBehavior, Schichtenbindung, BSW-Schedulable Entities).
  • BSW Module Vendor-Specific Configuration Parameter Definition: Modulspezifisches EcucModuleDef mit vendor-spezifischen Parametern, Wertebereichen und Binding-Times.
Stereotypen, Beziehungen & Kardinalitäten
  • «inoutput» (1): BSW Types ↔ Define BSW Types (iterative Erstellung und Verfeinerung).
  • «input» (0..1): BSW Standard Package → Define BSW Types, Define BSW Entries, Define BSW Interfaces (optionale Standardvorgaben).
  • «input» (0..1): ECU Resources Description → Define BSW Interfaces (Hardware-Restriktionen für MCAL-Treiber).
  • «input» (1):
    • BSW Types → Define BSW Entries
    • BSW Types → Define BSW Interfaces
    • Basic Software Entries → Define BSW Interfaces
    • AUTOSAR Standardized ECU Configuration Parameter Definition → Define Vendor Specific Module Definition
  • «output» (1):
    • Define BSW Entries → Basic Software Entries
    • Define BSW Interfaces → Basic Software Module Description
    • Define Vendor Specific Module Definition → BSW Module Vendor-Specific Configuration Parameter Definition

3. Dynamisches Verhalten & Sequenzablauf

Der Entwurfsprozess gliedert sich in abhängige und parallelisierbare Schritte:

[ BSW Standard Package ] (optional)
        │
        ├──────────────────────┬──────────────────────┐
        ▼ (0..1)               ▼ (0..1)               ▼ (0..1)
[ Define BSW Types ]    [ Define BSW Entries ]        │
        │ (inoutput)           │                      │
        ▼ (1)                  │                      │

        │                      ▼ (1)                  │
        │             [ Basic Software Entries ]      │
        │                      │                      │
        │                      ▼ (1)                  │

                [ ECU Resources Description ]

                               ▼ (output: 1)
                    [ BswModuleDescription ]

─── Paralleler Zweig (Konfigurationsmetamodell) ───────────────────
[ Standardized ECU Config Param Def ] (1)
        │
        ▼ (input: 1)
[ Define Vendor Specific Module Definition ]
        │
        ▼ (output: 1)
[ BSW Module Vendor-Specific Config Param Def ]
  1. Typendefinition: Generierung der BSW Types. Bei iterativen Änderungen fließen diese über «inoutput» wieder in Define BSW Types ein.
  2. Deklaration der Funktionssignaturen: Define BSW Entries verwendet die definierten Typen und erzeugt die Basic Software Entries (BswModuleEntry).
  3. Synthese zur BSWMD: Define BSW Interfaces verknüpft Datentypen, Funktionssignaturen und Hardware-Restriktionen (ECU Resources Description, z. B. MCAL-spezifische ISRs/Register) zur finalen Basic Software Module Description.
  4. Parametrisierungsdefinition (orthogonal/parallel): Aus den standardisierten Parametern generiert der Modul-Vendor via Define Vendor Specific Module Definition die modulspezifische Konfigurationsparameter-Definition (EcucModuleDef), welche die herstellerspezifischen Schalter (Pre-Compile, Link-Time, Post-Build) deklariert.

4. Normative Relevanz & Entwickler-Hinweise

  • Artefakt-Aufteilung im Stack: Für jedes BSW-Modul (Treiber, MemStack, ComStack) müssen zwei strikt getrennte Beschreibungsdateien erzeugt und konsistent gehalten werden:
    1. BSWMD (.arxml): Definiert das Modulverhalten (BswInternalBehavior), Scheduling-Intervalle, Reentrancy-Eigenschaften, Trigger (BswEvent), Exclusive Areas (SchM) und die BswModuleEntry-Deklarationen aller _MainFunction_<x>- und API-Aufrufe.
    2. Vendor ParamDef (.arxml): Definiert die Konfigurationsstruktur (EcucModuleDef) für den BSW-Konfigurator (z. B. EB Tresos, DaVinci Configurator Pro).
  • Entkopplung über BswModuleEntry: Ein API-Endpunkt wird im AUTOSAR-Metamodell nicht als einfacher String referenziert, sondern als eigenständiges Metamodell-Element (BswModuleEntry). Signaturfehler (Datentypkonflikte zu BSW Types) werden bereits auf ARXML-Schema-Ebene vor der Codegenerierung abgefangen.
  • MCAL-/Hardware-Abhängigkeit: Die optionale Kante ECU Resources Description zu Define BSW Interfaces markiert die Grenze zwischen hardwareunabhängigen Modulen (z. B. Com, Dcm, PduR ohne Ressourcen-Input) und hardwaregebundenen Modulen (z. B. Mcu, Port, Spi, Can), die zwingend µC-Register, Clocks und Interrupt-Layouts referenzieren müssen.
  • SchM- und RTE-Relevanz: Die in Define BSW Interfaces erzeugte BSWMD ist die primäre Eingangsgröße für den BswScheduler (Bestandteil der RTE). Fehlerhafte oder unvollständige Modulbeschreibungen führen zu fehlerhafter Task-Allokation, ungeschützten Exclusive Areas oder fehlenden MainFunction-Aufrufen im zyklischen OS-Raster.
