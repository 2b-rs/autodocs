1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt der AUTOSAR ECU Configuration Parameter Definition (EcucParamConfContainerDef, EcucReferenceDef).
  • Funktionale Einordnung: AUTOSAR Classic Platform, Transport Layer (CanTp, ISO 15765-2 / ISO 11898-1). Das Diagramm modelliert die statische Konfigurationsarchitektur des BSW-Moduls CanTp zur logischen Entkopplung und Abbildung von Transport-Protokoll-Verbindungen (CanTpChannel) auf Service Data Units der oberen Schicht (N-SDU via PduR) und Protocol Data Units der unteren Schicht (N-PDU via CanIf).

2. Komponenten, Entitäten & Schnittstellen

  • CanTpChannel (EcucParamConfContainerDef, Multiplizität: 1..*):
    • Logischer ISO-TP-Kanal. Definiert die Ausführungsressourcen, Kanalmodi (z. B. Half-/Full-Duplex) sowie TP-Zustandsmaschinen und Pufferüberwachung.
  • CanTpRxNSdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 0..*):
    • Konfigurationscontainer für den Empfangspfad einer logischen N-SDU.
    • CanTpRxNSduRef (EcucReferenceDef, Multiplizität: 1..1): Referenziert das globale Ziel-PDU-Objekt (Pdu) im EcuC-System für die Aufwärtskommunikation (PduR_CanTpRxIndication, PduR_CanTpStartOfReception, PduR_CanTpCopyRxData).
    • CanTpRxNPdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 1..1): Kapselt die primäre Daten-Empfangs-PDU (SF, FF, CF) von CanIf.
      • CanTpRxNPduRef (EcucReferenceDef, Multiplizität: 1..1): Referenz auf die physische/logische RX-PDU im Pdu-Katalog (CanIf_RxIndication).
    • CanTpTxFcNPdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 0..1): Kapselt die Flusssteuerungs-PDU (Flow Control, FC) im Empfangspfad.
      • CanTpTxFcNPduRef (EcucReferenceDef, Multiplizität: 1..1): Referenz auf die globale TX-PDU für FC-Frames via CanIf_Transmit.
  • CanTpTxNSdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 0..*, Anforderung: ECUC_CanTp_00137):
    • Konfigurationscontainer für den Sendepfad einer logischen N-SDU.
    • CanTpTxNSduRef (EcucReferenceDef, Multiplizität: 1..1): Referenz auf das globale PDU-Objekt, über das PduR die Übertragung anfordert (CanTp_Transmit, PduR_CanTpCopyTxData, PduR_CanTpTxConfirmation).
    • CanTpTxNPdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 1..1): Kapselt die gesendeten Daten-Frames (SF, FF, CF) an CanIf.
      • CanTpTxNPduRef (EcucReferenceDef, Multiplizität: 1..1): Referenz auf die Ziel-PDU via CanIf_Transmit.
    • CanTpRxFcNPdu (EcucParamConfContainerDef, Sub-Container, Multiplizität: 0..1): Kapselt empfangene Flow-Control-Frames im Sendepfad.
      • CanTpRxFcNPduRef (EcucReferenceDef, Multiplizität: 1..1): Referenz auf die FC-PDU via CanIf_RxIndication.
  • Pdu (EcucParamConfContainerDef, Multiplizität: 0..*):
    • Modulübergreifende EcuC-Entität zur eindeutigen Verwaltung von PDU-IDs im Gesamtsystem.
  • Beziehungssemantik & Kardinalitäten:
    • Ein CanTpChannel aggregiert hierarchisch (+subContainer, Composition) 0..* CanTpRxNSdu und 0..* CanTpTxNSdu.
    • Jeder SDU-Container hält zwingend genau eine N-SDU-Referenz (1..1) und genau eine Daten-N-PDU (1..1).
    • Die Flow-Control-Container (CanTpTxFcNPdu, CanTpRxFcNPdu) sind optional (0..1).

3. Dynamisches Verhalten & Sequenzablauf

Aus der Konfigurationsstruktur resultieren zwei orthogonale dynamische Ablaufpfade:

  • Segmentierter RX-Pfad (CanTpRxNSdu):
    1. Trigger: Eintreffen eines First Frame (FF) oder Single Frame (SF) über CanTpRxNPduRef via CanTp_RxIndication().
    2. Buffer Allocation: Synchrone Signalisierung an obere Schichten via PduR_CanTpStartOfReception(CanTpRxNSduRef, ...).
    3. Flow Control: Sofern konfiguriert (CanTpTxFcNPdu, Multiplizität 1), berechnet CanTp Block Size (BS) / Separation Time (STmin) und sendet asynchron eine FC-PDU über CanIf_Transmit(CanTpTxFcNPduRef).
    4. Consecutive Frames: Eintreffen von CFs über CanTpRxNPduRef, Pufferung via PduR_CanTpCopyRxData().
    5. Abschluss/Abbruch: Benachrichtigung über PduR_CanTpRxIndication() nach Reassembly; Abbruch bei Timeout (N_Cr, N_Ar) oder Pufferüberlauf (BUFREQ_E_NOT_OK).
  • Segmentierter TX-Pfad (CanTpTxNSdu):
    1. Trigger: Aufruf von CanTp_Transmit(CanTpTxNSduRef, &PduInfo).
    2. Frame Transmission: Senden des SF oder FF über CanIf_Transmit(CanTpTxNPduRef).
    3. Flow Control Reception: Warten auf FC-Frame über CanTpRxFcNPduRef via CanTp_RxIndication().
    4. Bursts / Pacing: Iteratives Senden von CFs (CanTpTxNPduRef) gesteuert durch empfangene BS- und STmin-Parameter unter periodischer Abfrage von Nutzdaten via PduR_CanTpCopyTxData().
    5. Abschluss: Quittierung über PduR_CanTpTxConfirmation(); Abbruch bei Flow-Control-Timeout (N_Bs) oder FC_OVFLW.

4. Normative Relevanz & Entwickler-Hinweise

  • Relevanz der 0..1-Kardinalität bei FC-PDUs:
    • Bei unsegmentierter Kommunikation (reine Single-Frame-Verbindungen) oder funktionaler Adressierung (Broadcast-Diagnose nach ISO 14229 / ISO 15765-4, bei der FC-Frames normativ verboten sind) entfällt die Konfiguration von CanTpTxFcNPdu bzw. CanTpRxFcNPdu (lowerMultiplicity = 0). Fehlt dieser Container, verwirft die CanTp-State-Machine Segmentierungsanfragen bzw. quittiert keine Multiframe-Übertragungen.
  • Kanalressourcen & Concurrency:
    • Mehrere N-SDUs (0..*) können einem CanTpChannel zugewiesen sein. Ein physikalischer TP-Kanal kann jedoch pro Richtung zeitgleich nur eine einzige segmentierte Transaktion bedienen (Kanal-Zustandsmaschine ist belegt bis Abschluss oder Timeout). Parallele Diagnosesitzungen oder Multicast-Transfer erfordern separate CanTpChannel-Instanzen.
  • AUTOSAR R21-11 MetaData-Verarbeitung (ECUC_CanTp_00137):
    • CanTpTxNSdu verarbeitet dynamische Metadaten (SOURCE_ADDRESS_16, TARGET_ADDRESS_16, ADDRESS_EXTENSION_8).
    • Konsequenz: Ermöglicht generisches Routing (z. B. J1939 oder Extended/Mixed Addressing nach ISO 15765-2), ohne für jedes Ziel-Adresspaar eine statische N-PDU im EcuC-Modell vorhalten zu müssen. Die Adressinformationen werden zur Laufzeit dynamisch über das PduInfoType.MetaDataPtr-Array transportiert und direkt in den CAN-Identifier oder das Datenfeld (Extended/Mixed Byte) serialisiert.
  • Code-Generierung & BSW-Tabellen:
    • Der BSW-Generator überführt diese Metamodell-Knoten in statische ROM-Lookup-Tabellen (z. B. CanTp_RxConfig[], CanTp_TxConfig[]). Die *Ref-Elemente definieren dabei direkt die Indizes zur Auflösung von PduIdType zwischen CanIf-Bestätigungen und PduR-Forwarding. Fehlkonfigurationen in den Referenzen führen zu CANTP_E_INVALID_TX_ID / CANTP_E_INVALID_RX_ID im Default Error Tracer (Det).
