1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: E/E-Netzwerk- und Schichtarchitektur-Diagramm (Topologischer Datenflussplan für AUTOSAR Classic & Adaptive Platform).
  • Technischer Zweck: Veranschaulichung des normativen Anwendungsfalls UC_0001 („Forward QSEv to ECU with SOC connection“) gemäß AUTOSAR_FO_PRS_IntrusionDetectionSystem. Dargestellt wird die bus- und plattformunabhängige Weiterleitung von Qualified Security Events (QSEv) über heterogene Kommunikationsnetze (CAN, Ethernet) und Gateway-Knoten von verteilten IdsM-Instanzen (Intrusion Detection System Manager) zu einer zentralen IdsR-Instanz (Intrusion Detection System Reporter) mit Backend-/VSOC-Anbindung (Vehicle Security Operations Center).

2. Komponenten, Entitäten & Schnittstellen

Steuergeräte-Entitäten (ECUs)
  • ECU A (ASR Classic Platform): Reiner Security-Sensor-/Endknoten. Beinhaltet BSW IdsM, PduR und CAN Stack (CanIf, CanTp/CanDrv).
  • ECU B (ASR Classic Platform): Homogener Gateway-Knoten (CAN-zu-CAN). Beinhaltet IdsM, PduR mit Gateway-Routing-Pfad sowie den CAN Stack.
  • ECU C (ASR Classic Platform): Heterogener Backbone-Gateway-Knoten (CAN-zu-Ethernet). Beinhaltet IdsM, PduR mit medienübergreifendem Gateway-Routing, CAN Stack sowie Eth Stack (EthIf, TcpIp, SoAd).
  • ECU D (ASR Adaptive Platform): Zentraler Konnektivitäts- und Auswerteknoten (HPC/Telematics). Beinhaltet lokale IdsM-Instanz (Adaptive Service), zentrale IdsR-Instanz sowie Anbindung an den externen Übertragungsweg (Mobile Data Link).
Schnittstellen & Kommunikationsbeziehungen
  • IdsM → PduR (ECU A, B, C): Lokale BSW-Schnittstelle zur Übergabe serialisierter Security-I-PDUs (I-PDU).
  • PduR Gateway Routing (ECU B, ECU C): PDU-basiertes Durchrouten (PduRRoutingPath) von Ingress- zu Egress-PDU-IDs ohne Entpacken des Payloads auf Applikationsebene:
    • ECU B: CAN-Rx-PDU → CAN-Tx-PDU.
    • ECU C: CAN-Rx-PDU → Eth-Tx-PDU (z. B. via SoAd).
  • IdsM → IdsR (ECU D): Plattforminterne Service-/IPC-Kommunikation (ara::idsm an ara::idsr via ara::com).
  • IdsR → Mobile Data Link (ECU D): Telemetrie-Schnittstelle zum VSOC via Mobilfunk/Cloud-Protokolle (z. B. MQTT, HTTPS).

3. Dynamisches Verhalten & Sequenzablauf

  1. Event-Erfassung & Qualifizierung: Lokale Sensoren, SWCs oder BSW-Module melden Security Events (SEv) an die lokale IdsM-Instanz. IdsM filtert, aggregiert und drosselt diese zu Qualified Security Events (QSEv).
  2. Serialisierung & PDU-Erzeugung: IdsM packt die QSEvs in normierte IDS-Protokoll-Frames (I-PDUs mit standardisiertem Header, Event-ID, Context Data und Timestamp).
  3. Mehrstufiges Multi-Hop-Routing:
    • Hop 1 (ECU A → ECU B): ECU A sendet I-PDU via PduR und CAN Stack über den CAN-Bus an ECU B.
    • Hop 2 (ECU B → ECU C): CAN Stack von ECU B empfängt die PDU; der lokale PduR routet diese per Gateway-Routing direkt wieder in den Tx-Pfad des CAN Stack. Gleichzeitig kann IdsM auf ECU B eigene QSEv-PDUs multiplexen.
    • Hop 3 (ECU C → ECU D): PduR auf ECU C übernimmt die Umsetzung vom CAN Stack in den Eth Stack (Protokollumsetzung auf Layer 2/3, z. B. Zuordnung zur Socket-Verbindung via SoAd).
  4. Ingestion & Aggregation im IdsR:
    • ECU D empfängt die Ethernet-Frames und leitet die IDS-PDUs an IdsR weiter.
    • Die lokale IdsM-Instanz von ECU D übergibt ihre QSEvs parallel direkt an IdsR.
  5. Off-Board-Propagation: IdsR puffert, filtert und bündelt die fahrzeugweiten QSEvs zu Security-Reports und überträgt diese asynchron über den Mobile Data Link an das VSOC.

4. Normative Relevanz & Entwickler-Hinweise

  • PDU-Transparenz im PduR: Das IDS-Protokoll ist so konzipiert, dass Zwischenknoten (ECU B, ECU C) reine PDU-Router bleiben. Der PduR benötigt keine Semantik-Kenntnis des IDS-Payloads; es genügt die statische Konfiguration der Routing-Tabellen (PduRRoutingPath mit PduRSrcPdu und PduRDestPdu).
  • Pufferung, Throttling & DoS-Schutz: Bei Security-Vorfällen besteht die Gefahr von Event Flooding. IdsM muss zwingend mit Ratenbegrenzung (Traffic Throttling / Filter Chains) konfiguriert werden, um Bus-Überlastungen auf CAN-Strecken sowie Pufferüberläufe in Gateways (PduR-Queue) zu verhindern.
  • PDU-Längen & Fragmentierung: Beim Medienübergang CAN (Classic CAN: 8 Byte, CAN FD: bis 64 Byte) zu Ethernet auf ECU C müssen PDU-Größen und ggf. Transportprotokoll-Mechanismen (CanTp, DoIP, SoAd-PDU-Aggregation) sauber konfiguriert sein, um PDU-Verlust oder unnötigen Overhead zu vermeiden.
  • Zeitsynchronisation (StbM / TimeSync): Da QSEvs auf unterschiedlichen Steuergeräten entstehen, ist ein global synchronisierter Zeitstempel (Synchronized Time-Base Manager) über alle Bussegmente hinweg zwingend erforderlich, damit der IdsR bzw. das VSOC Angriffssequenzen zeitlich korrekt korrelieren kann.

ID Name Description 0001 Transmission of QSEv Transmission of qualified security events from IdsM instances to IdsR instance Table 2.1: Usecases for IDS protocols 2.1 UC_0001 "Forward QSEv to ECU with SOC connection" The main use case for the IDS protocol is the propagation of Qualified Security Events QSEv to the IdsR in a way that is independent from the kind of ECU or the used communication mechanism. IdsM instances can be allocated to all nodes of the vehicle architecture that are security relevant. This decision is typically based on a security analysis of the vehicle E/E architecture.
