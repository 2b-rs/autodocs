1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Speicher-Layout / Binärstruktur-Diagramm (Memory Image / Binary Layout).
  • Technischer Zweck & Einordnung: Spezifikation des standardisierten Binärformats für hardware-/CPU-spezifische Memory-Treiber (Mem) gemäß AUTOSAR Classic Platform (R21-11, AUTOSAR_SWS_MemoryDriver).
  • Systemkontext: Ermöglicht die Entkopplung des Memory-Treibers von der Host-Applikation bzw. dem Memory Accessor (MemAcc). Das Treiber-Binary kann als separates Link-Artefakt vorliegen, zur Laufzeit in den RAM geladen und über eine standardisierte Funktionszeigertabelle dynamisch gebunden werden (z. B. für Flash-Algorithmen, Flashen aus dem RAM oder modular aktualisierbare Treiberkomponenten).

2. Komponenten, Entitäten & Schnittstellen

Das Binary Image gliedert sich in vier contiguous angeordnete Segmente:

  1. Header (Metadatenblock am Offset 0):
    • Unique ID (Offset 0, 8 Bytes): Eindeutige Kennung zur Validierung von Treibertyp, Versionsstand und Kompatibilität.
    • Header Address (Offset 16, 4 oder 8 Bytes gemäß MemAcc_AddressType): Erwartete Startadresse des Images; dient dem Konsistenzabgleich mit der tatsächlichen Allokationsadresse im RAM-Buffer/ROM.
    • Flags (Offset 8, 8 Bytes): Konfigurations- und Statusbits für erweiterte Entwicklungsschnittstellen und Development Error Detection (Det).
    • Delimiter Address (4 oder 8 Bytes): Zeiger auf das Image-Ende (Delimiter).
  2. Service Function Pointer Table (VTable / Sprungtabelle):
    • Liegt unmittelbar hinter dem Header.
    • Enthält Funktionszeiger auf die standardisierten Treiberschnittstellen der Service Implementation:
      • Mem_Init (Initialisierung des Peripherie-Controllers)
      • Mem_MainFunction (Zyklische Task-Verarbeitung / Asynchron-Scheduler)
      • Mem_GetJobResult (Status- und Ergebnisabfrage asynchroner Operationen)
      • Mem_Read (Leseservice)
      • ... (weitere Standarddienste wie Write, Erase)
      • Mem_HwSpecificService (Herstellerspezifische Peripherie-Dienste)
  3. Service Implementation (Code-Segment / Payload):
    • Ausführbarer Maschinencode (Funktionsrümpfe) der Services, referenziert durch die Funktionszeiger der VTable.
  4. Delimiter (Abschlussmarkierung):
    • Delimiter Pattern: Fest definierte Magic-Byte-Sequenz am Ende des Binärimages zur Integritäts- und Längenvalidierung des gesamten Images.

3. Dynamisches Verhalten & Sequenzablauf

Der Aufruf- und Bindungszyklus durch den Konsumenten (MemAcc / Bootloader / Flashtreiber-Lader):

  1. Laden & Adressverifikation:
    • Das Binary wird in den Zielspeicher (RAM/ROM) geladen.
    • Der Konsument liest den Header und prüft, ob die reale Ladeadresse mit Header Address übereinstimmt (Verifikation gegen Linker-Diskrepanzen).
  2. Integritätsprüfung (Boundary Check):
    • Der Konsument liest Delimiter Address aus dem Header und verifiziert das dort hinterlegte Delimiter Pattern. Schlägt der Vergleich fehl, ist das Image unvollständig oder korrupt; der Ladevorgang bricht ab.
  3. Versionsvalidierung:
    • Abgleich von Unique ID gegen die Kompatibilitätsanforderungen des aufrufenden Moduls.
  4. Service-Dispatching:
    • Der Aufrufer initialisiert den Treiber synchron via Zeiger auf Mem_Init.
    • Asynchrone Jobs (z. B. Mem_Read) werden per Funktionszeiger getriggert, periodisch via Mem_MainFunction verarbeitet und über Mem_GetJobResult synchron/asynchron abgefragt.

4. Normative Relevanz & Entwickler-Hinweise

  • Endianness ([SWS_Mem_00040]): Alle Datenfelder und Adresszeiger innerhalb des Binärimages müssen strikt der Standard-Byte-Reihenfolge der Ziel-CPU entsprechen. Aufwendige Byte-Swap-Konvertierungen zur Laufzeit sind unzulässig.
  • Adressraum-Skalierung ([SWS_Mem_00041]): Die Feldbreite der Adressen (Header Address, Delimiter Address, Funktionszeiger) beträgt abhängig von der Plattform-Konfiguration MemAcc_AddressType 32-Bit (4 Bytes) oder 64-Bit (8 Bytes). Linker-Skripte und Toolchains müssen exakt hierauf abgestimmt sein.
  • ABI-Stabilität & Alignment: Die Reihenfolge der Funktionszeiger in der Service Function Pointer Table definiert das binäre ABI-Interface zwischen Treiber und Core-Stack. Änderungen an Typdefinitionen oder VTable-Offsets brechen die Rückwärtskompatibilität.
  • Relozierbarkeit: Ist das Image für den RAM-Betrieb vorgesehen, muss die Service-Implementierung entweder als Position-Independent Code (PIC) kompiliert oder strikt auf die in Header Address spezifizierte Ladeadresse gelinkt werden.
