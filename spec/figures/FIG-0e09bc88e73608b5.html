3. Dynamisches Verhalten & Sequenzablauf

  1. Triggerung des Clients: Innerhalb von SeatHeatingControl ermittelt eine periodische oder ereignisgesteuerte Runnable Entity (z. B. getriggert über SeatSwitch-Dateneingang) die erforderliche Heizstufe.
  2. Operationsaufruf (Client-seitig):
  • Aufruf der generierten RTE-API: Rte_Call_HeatingElement_SetPower(powerValue).
  • Ausführung: Entweder synchron blockierend (Client-Task wartet auf Server-Beendigung) oder asynchron (Client setzt Ausführung fort und fragt das Ergebnis später via Rte_Result ab).
  1. Dispatching via RTE / VFB:
  • Die RTE fängt den Aufruf ab.
  • Intra-ECU: RTE aktiviert die Server-Task bzw. führt das zugeordnete Server-Runnable in SeatHeating direkt aus (gemappt auf ein OperationInvokedEvent).
  • Inter-ECU: RTE serialisiert den Parameter in ein CAN/LIN/FlexRay-I-PDU-Signal über den AUTOSAR COM-Stack.
  1. Terminierung & Fehlerpfade:
  • Erfolgsfall: Das Server-Runnable terminiert fehlerfrei und liefert RTE_E_OK zurück.
  • Anwendungsfehler: Erkennt SeatHeating einen Kurzschluss/Lastabwurf am Aktuator, gibt das Runnable den Fehlerwert für HardwareProblem zurück. Die RTE mappt dies auf den anwendungsspezifischen Rückgabewert RTE_E_HeatingElementControl_HardwareProblem.
  • Infrastrukturfehler: Bei Kommunikationsabriss oder Timeout liefert die RTE standardisierte Fehler (z. B. RTE_E_TIMEOUT, RTE_E_COM_STOPPED).

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-API-Vertrag (C-Code):
  • Client (SeatHeatingControl):

```c

Std_ReturnType Rte_Call_HeatingElement_SetPower(sint32 Power);

```

Rückgabewerte: RTE_E_OK, RTE_E_HeatingElementControl_HardwareProblem, RTE_E_TIMEOUT, RTE_E_UNCONNECTED.

  • Server (SeatHeating): Der Entwickler muss die Server-Funktion zwingend mit folgender Signatur implementieren:

```c

Std_ReturnType (sint32 Power);

```

  • Konfigurations- und Integrationsregeln:
  • 1:1- bzw. 1:n-Kopplung: Ein Client-Server-Interface erlaubt mehrere Clients für einen Server (1:n AssemblySwConnector). Der Server muss reentrant ausgelegt sein, falls Zugriffe aus Tasks unterschiedlicher Priorität erfolgen (Gefahr von Race Conditions und Priority Inversion).
  • Fehlercode-Konfiguration (ApplicationError): Im ARXML muss HardwareProblem ein numerischer errorCode im normativen Bereich von 1 bis 63 zugewiesen werden (0 ist reserviert für RTE_E_OK).
  • Blockierungsrisiko: Bei synchronen Calls über ECU-Grenzen hinweg blockiert der Client-Task, bis das Antwort-Frame über den Bus empfangen wurde. Für zeitkritische Regelkreise ist ein asynchroner Aufruf (Rte_Result) zwingend vorzuziehen.
