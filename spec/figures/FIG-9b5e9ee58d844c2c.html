1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Informelles AUTOSAR-Adaptive-Komponenten- und Port-Interaktionsdiagramm mit Manifest-Zuordnungsannotationen (Metamodell-Abstraktion der Service-Schnittstellen und Port-Mappings).
  • Architektonischer Kontext: AUTOSAR Adaptive Platform (AP), Release R21-11, spezifiziert in AUTOSAR_TPS_ManifestSpecification (Abschnitt 4.1.15, [TPS_MANI_01360], [TPS_MANI_01361]).
  • Technischer Zweck: Darstellung der beiden orthogonalen Interaktionsmuster und Port-Rollen zwischen dem funktionalen Cluster Diagnostic Manager (DM, ara::diag) und einer Application Software Component (Adaptive Application) zur Abwicklung der Diagnose-Authentifizierung gemäß ISO 14229-1 (UDS Service 0x29 Authentication).

2. Komponenten, Entitäten & Schnittstellen

Akteure & Software-Entitäten
  • Diagnostic Manager (DM): Plattform-Cluster der Adaptive Platform, der das Diagnoseprotokoll terminiert, Sessions verwaltet und Zugriffsberechtigungen steuert. Dargestellt mit gestrichelten/schraffierten Ports, da diese intern durch die Plattform-Konfiguration instantiiert werden.
  • Application Software Component: Adaptive Application (modelliert über AdaptiveApplicationSwComponentType im ProcessDesign-Kontext), welche domänenspezifische oder kryptografische Authentifizierungslogik kapselt.
Schnittstellen & Ports
  1. Delegierte Authentifizierung (Unterer Pfad – Request-Rolle):
    • DiagnosticAuthenticationInterface: Service-Interface zur Weiterleitung von Diagnose-Authentifizierungsanfragen.
    • P-Port (PPortPrototype) an der Application Software Component: Stellt die Service-Methoden bereit (Skeleton-Implementierung).
    • R-Port (RPortPrototype) am Diagnostic Manager: Fungiert als Service-Consumer (Proxy-Instanz im DM).
    • DiagnosticAuthenticationMapping (DiagnosticAuthenticationPortMapping): Manifest-Element, das eine DiagnosticAuthentication-Instanz mit dem ProcessDesign und dem konkreten PPortPrototype (pPortPrototypeInExecutable) verknüpft.
  2. Externe Authentifizierung (Oberer Pfad – Notifikations-Rolle):
    • DiagnosticExternalAuthenticationInterface: Service-Interface zur Übermittlung extern validierter Sicherheitszustände an den DM.
    • R-Port (RPortPrototype) an der Application Software Component: Tritt als Client auf.
    • P-Port (PPortPrototype) am Diagnostic Manager: Stellt den Service zur Statusaktualisierung bereit.
    • DiagnosticExternalAuthenticationMapping (DiagnosticExternalAuthenticationPortMapping): Manifest-Element, welches den R-Port der Applikation auf die entsprechende Entität des Diagnostic Managers mappt.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm bildet zwei voneinander unabhängige Laufzeit-Interaktionspfade ab:

[ Pfad 1: In-Band UDS 0x29 ]
Diagnostic Client (Tester)
       │  UDS 0x29 (Request)
       ▼
Diagnostic Manager [R-Port] ─── Authentication Request ────► [P-Port] Application SWC
                                                                      │ (Krypto-Prüfung)
Diagnostic Manager [R-Port] ◄── Response (Verify/Result) ──── [P-Port] Application SWC

[ Pfad 2: Out-of-Band / Externe Authentifizierung ]
Security Entity / Backend
       │ (z. B. TLS, SecOC, Cloud)
       ▼
Application SWC    [R-Port] ─── Authentication Confirm/Deny ─► [P-Port] Diagnostic Manager
                                                                      │ (Session-Freigabe /
                                                                      │  White-List Update)
  1. Pfad 1: Delegation der Client-Authentifizierung (Authentication Request)
    • Trigger: Ein externer Diagnosetester sendet einen UDS-Service-0x29-Request (z. B. Sub-Funktionen zur Zertifikatsprüfung oder Challenge-Response) an den Diagnostic Manager.
    • Ablauf: Der DM leitet den Payload über seinen R-Port via DiagnosticAuthenticationInterface an den P-Port der Applikation weiter.
    • Rückmeldung: Die Applikation prüft die Authentifizierungsdaten (unter Einbindung von ara::crypto) und liefert das Ergebnis an den DM zurück, welcher den UDS-Response-Frame an den Tester erzeugt.
  2. Pfad 2: Externe Authentifizierung (Authentication Confirm/Deny)
    • Trigger: Die Authentifizierung des Testers erfolgt außerhalb des regulären UDS-0x29-Kanals (z. B. durch ein zentrales Fahrzeug-Security-Gateway, übergeordnete Backend-Verifikation oder ein proprietäres Authentifizierungsprotokoll).
    • Ablauf: Die Applikation agiert als Initiator und meldet dem Diagnostic Manager über das DiagnosticExternalAuthenticationInterface asynchron, ob die Authentifizierung für den Client bestätigt (Confirm) oder verweigert (Deny) wurde.
    • Wirkung: Der DM schaltet diagnostische Services, geschützte DIDs oder Routinen für die Client-Session frei bzw. sperrt diese ohne vorherigen direkten 0x29-UDS-Handshake.

4. Normative Relevanz & Entwickler-Hinweise

  • Manifest-Generierung & Binding ([TPS_MANI_01361]): Der referenzierte PPortPrototype der Applikation muss zum Konfigurationszeitpunkt des DM noch nicht zwingend vorliegen. Das DiagnosticAuthenticationPortMapping ist jedoch im Manifest zwingend erforderlich, um den korrekten InstanceSpecifier für das Service-Binding (ara::com / Deployment-Manifest) zu konstruieren.
  • Entwickler-Vertrag (ara::diag / AUTOSAR AP):
    • Stellt eine Applikation den Authentifizierungs-Handler bereit (Pfad 1), muss sie den C++-Typen von DiagnosticAuthenticationInterface als Skeleton erben und Methoden zur Verifikation implementieren.
    • Meldet eine Sicherheits-Applikation externe Zustände (Pfad 2), bindet sie den Proxy von DiagnosticExternalAuthenticationInterface ein und triggert die Confirm/Deny-Methoden.
  • Restriktionen & Konsistenz ([constr_10092]): Die Zuordnungen im Manifest müssen eindeutig sein. Konfigurations- und Laufzeitumgebung müssen sicherstellen, dass bei paralleler Nutzung beider Pfade keine inkonsistenten Session-Zustände im State-Handling des DM auftreten (Vorrangregeln gemäß ISO 14229-1 beachten).
