  • + Offset: uint16: Start-Bitposition des 5-Byte (40-Bit) langen E2E-Profile-6-Headers innerhalb der PDU (Offset % 8 == 0).

  • Keine Vererbung; aggregatfreie POD-Struktur (Plain Old Data).
  • Wird per Zeiger (const E2E_P06ConfigType* ConfigPtr) an die Library-APIs E2E_P06Protect(), E2E_P06Check(), E2E_P06ProtectInit() und E2E_P06CheckInit() übergeben.
  • Bildet das statische Gegenstück zu den dynamischen Zustandsstrukturen E2E_P06ProtectStateType (Sender) und E2E_P06CheckStateType (Empfänger).

3. Dynamisches Verhalten & Sequenzablauf

Obwohl das Diagramm eine statische Struktur abbildet, determiniert sie das sequentielle Laufzeitverhalten der E2E-Routinen:

  • Transmitter-Pfad (E2E_P06Protect):
  1. Eingangsvalidierung: Prüft Pointer auf NULL sowie MinDataLength <= Length <= MaxDataLength und Byte-Alignment von Offset. Rückgabe von E2E_E_INPUTERR_NULL oder E2E_E_INPUTERR_WRONG bei Verletzung.
  2. Header-Generierung: Schreibt an Bit-Offset Offset den aktuellen Sequenzzähler (Counter: uint8, 0–255) sowie die tatsächliche Datenlänge (Length: uint16).
  3. CRC-Berechnung: Berechnet die CRC-16 (Polynom 0x1021, Startwert 0xFFFF) über die Nutzdaten, die Länge, den Counter und bindet die konfigurierte DataID ein.
  4. Inkrementierung: Erhöht State->Counter mod 256 für den nächsten Zyklus.
  • Receiver-Pfad (E2E_P06Check):
  1. Längenprüfung: Validiert übergebene PDU-Länge gegen [MinDataLength, MaxDataLength] und gleicht sie mit dem Längenfeld im PDU-Header ab.
  2. CRC-Verifikation: Berechnet die Prüfsumme unter Verwendung von Config->DataID neu und vergleicht mit dem übertragenen CRC16.
  3. Counter-Validierung: Berechnet die Differenz zum letzten gültigen Counter und evaluiert gegen Config->MaxDeltaCounter.
  4. Status-Zuweisung: Setzt State->Status (z. B. E2E_P06STATUS_OK, E2E_P06STATUS_WRONGSEQUENCE, E2E_P06STATUS_REPEATED, etc.).
  • Fehlerkanäle & Reentrancy:
  • Keine direkten Aufrufe von DET (Det_ReportError) oder DEM aus der Library; Fehler werden ausschließlich über den Rückgabewert (Std_ReturnType) und die State-Struktur an den Aufrufer (z. B. RTE, E2E-Transformer / ComXf) gemeldet.

4. Normative Relevanz & Entwickler-Hinweise

  • Konfigurationsverbindlichkeit (SWS_E2E_00441):
  • Instanzen von E2E_P06ConfigType müssen als const im ROM/Flash abgelegt werden. Sie sind vollständig thread-safe und reentrant lesbar.
  • Bit- vs. Byte-Semantik:
  • Obwohl alle Längenangaben (Offset, MinDataLength, MaxDataLength) in Bits definiert sind, erzwingt die E2E-Spezifikation striktes Byte-Alignment (wert % 8 == 0). Nichteinhaltung führt zu Laufzeitfehlern (E2E_E_INPUTERR_WRONG).
  • PDU-Layout-Restriktionen:
  • Der Profile-6-Header beansprucht exakt 5 Bytes (40 Bits: 2 Bytes CRC-16, 2 Bytes Length, 1 Byte Sequence Counter).
  • Es muss sichergestellt sein, dass Offset + 40 <= MinDataLength (sofern der Header innerhalb der Mindestlänge liegt) und keine Überlappung mit anderen Protokollheadern (z. B. SecOC) auftritt.
  • Stack-Integration (Classic vs. Adaptive):
  • In Classic AUTOSAR wird die Konfiguration primär über das E2E-Transformer-Modul (ComXf) generiert und instanziiert.
  • MaxDeltaCounter muss auf die Zykluszeit und die maximale Anzahl tolerierbarer Frame-Verluste vor Auslösen eines Degradationspfades im State Manager kalibriert werden.
