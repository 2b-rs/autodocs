1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-/Payload-Bitfeld- und Serialisierungs-Layout (TLV- bzw. Tagged-Format).
  • Technischer Zweck: Spezifikation des 16-Bit-SOME/IP-Tags und des nachfolgenden optionalen Längenfelds zur Serialisierung von Datenstrukturen (struct) und Methoden-Argumenten mit optionalen Elementen.
  • Architektur-Kontext:
    • AUTOSAR Foundation (FO) / Classic Platform (CP) / Adaptive Platform (AP): Protokollschicht des SOME/IP-Transformers (SomeIpXf in CP) bzw. des Kommunikations-Bindings (ara::com in AP).
    • Funktionale Einordnung: Ermöglicht schema-evolutionäre Vorwärts- und Rückwärtskompatibilität sowie die Übertragung optionaler Datenelemente. Unbekannte oder optionale Strukturmitglieder können zur Laufzeit anhand von Data ID und Wire Type identifiziert bzw. deterministisch übersprungen werden.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert eine hierarchische Bit- und Byte-Zerlegung des SOME/IP-Serialisierungsstroms:

  1. Tag (16 Bit / 2 Bytes: Byte n und Byte n+1):
    • reserved (Byte n, Bit 7): 1 Bit; normativ auf 0 gesetzt, vom Empfänger zu ignorieren/reserviert für künftige Protokollerweiterungen.
    • Wire Type (Byte n, Bit 6..4): 3 Bits (Wertebereich 0–7); spezifiziert die Datentypkategorie und steuert die Existenz sowie die Breite des nachfolgenden Längenfeldes:
      • 0: Statische 8-Bit-Daten (kein Längenfeld).
      • 1: Statische 16-Bit-Daten (kein Längenfeld).
      • 2: Statische 32-Bit-Daten (kein Längenfeld).
      • 3: Statische 64-Bit-Daten (kein Längenfeld).
      • 4: Dynamischer Typ / komplexe Struktur mit 8-Bit-Längenfeld (1 Byte).
      • 5: Dynamischer Typ / komplexe Struktur mit 16-Bit-Längenfeld (2 Bytes).
      • 6: Dynamischer Typ / komplexe Struktur mit 32-Bit-Längenfeld (4 Bytes).
      • 7: Reserviert (reserved).
    • Data ID (12 Bits gesamt):
      • Higher Significant Part (Byte n, Bit 3..0): 4 Bits (MSB 11..8).
      • Lower Significant Part (Byte n+1, Bit 7..0): 8 Bits (LSB 7..0).
      • Wertebereich 0x000–0xFFF (0–4095); eindeutiger Identifikator des Members innerhalb seiner Hierarchieebene.
  2. Length Field (Byte n+2 …, optional / in eckigen Klammern dargestellt):
    • Breite: 8, 16 oder 32 Bit (abhängig vom konfigurierten Wire Type 4, 5 oder 6).
    • Gibt die Netto-Bytegröße der nachfolgenden Nutzdaten (Member Data) an.
  3. Member Data ... (Payload):
    • Die eigentlichen Nutzdaten des serialisierten Struktur-Members bzw. Methoden-Arguments.

3. Dynamisches Verhalten & Sequenzablauf

  1. Serialisierungspfad (Sender / Client / Server):
    • Präsenzprüfung: Ermittlung, ob das optionale Element instanziiert ist (z. B. via std::optional / ara::core::Optional in AP oder Verfügbarkeits-Flag/Pointer in CP).
    • Tag-Generierung: Ist das Element vorhanden, wird das 16-Bit-Tag aus reserved=0, dem für den Datentyp parametrierten Wire Type und der ARXML-definierten Data ID assembliert (Big-Endian / Network Byte Order).
    • Längenfeldeinfügung: Bei dynamischen Typen (Wire Type 4/5/6) wird die Bytegröße des serialisierten Inhalts berechnet und im Längenfeld vorangestellt.
    • Skipping: Nicht belegte optionale Member werden vollständig aus dem Bytestrom weggelassen (kein Tag, kein Längenfeld, keine Daten).
  2. Deserialisierungspfad (Empfänger):
    • Parser liest Byte n und n+1 als Tag ein.
    • Extrahiert Data ID und Wire Type.
    • Mapping vs. Skipping:
      • Bekannte Data ID: Member wird deserialisiert und als vorhanden markiert.
      • Unbekannte Data ID (Forward Compatibility): Anhand des Wire Type wird die Elementlänge bestimmt (feste Bytezahl 1/2/4/8 Byte oder Auslesen des 8/16/32-Bit-Längenfelds). Der Deserialisierer springt um diese Distanz im Bytestrom weiter und parst das nächste Tag.
    • Fehlerabbruch: Ungültiger Wire Type (z. B. 7) oder Längenfeld-Inkonsistenzen mit der Rest-PDU führen zum Verwerfen der SOME/IP-Nachricht und Fehlereintrag (Det/Dem bzw. Security/Logging-Event).

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Konfiguration & Datenmodellierung:
    • [PRS_SOMEIP_00201]: Eine Data ID muss nur innerhalb der direkten Member derselben Struktur bzw. Methoden-Argumentebene eindeutig sein, nicht global über unterschiedliche Strukturen hinweg.
    • [PRS_SOMEIP_00230]: All-or-Nothing-Regel: Entweder erhalten alle Member einer Hierarchieebene einer Struktur eine Data ID (TLV-Modus) oder keines (reiner positionsbasierter Flat-Modus). Mischformen auf derselben Ebene sind unzulässig.
    • [PRS_SOMEIP_00231]: Analog gilt für Methoden-Argumente: Entweder alle Argumente besitzen eine Data ID oder keines.
  • Stack- und Plattform-Restriktionen:
    • Weder die AUTOSAR-Methodik noch AUTOSAR CP RTE oder AP ara::com unterstützen Stand R20-11 bis R23-11 optionale Methoden-Argumente; die praktische Anwendung beschränkt sich primär auf struct-Typen.
  • Endianness:
    • Tag (Byte n und Byte n+1) sowie das Längenfeld werden normativ in Network Byte Order (Big Endian) codiert – unabhängig von der Plattform-Endianness oder der für primitive Nutzdaten konfigurierten Byte-Order.
  • Performance & PDU-Budgetierung:
    • Jedes mit Tag übertragene Feld fügt mindestens 2 Byte (statischer Typ) bzw. 3–6 Byte (dynamischer Typ inkl. Längenfeld) Overhead hinzu. Für Bandbreiten-kritische Signale auf CAN-FD/FlexRay/Ethernet sollte der TLV-Modus restriktiv eingesetzt werden.
