1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: UML-Klassendiagramm / Metamodell-Strukturdiagramm (AUTOSAR BSW ECU Configuration Specification / EcucModuleDef) nebst vorangestellter tabellarischer Modulspezifikation (ECUC_Nm_00243).
  • Architektur-Kontext:
    • Metamodell-Definition der Konfigurationsstruktur des Moduls Network Management Interface (Nm, AUTOSAR Classic Platform, Schicht: Communication Services / System Services).
    • Das Nm-Modul dient als hardware- und bussystemunabhängige Abstraktionsschicht zwischen dem Communication Manager (ComM) und den busspezifischen NM-Modulen (CanNm, FrNm, LinNm, UdpNm).
    • Das Diagramm definiert die normative Behälterhierarchie (Container Tree) für Pre-Compile- und Link-Time-Konfiguration (Post-Build-Support wird nicht unterstützt) sowie die Referenzierung von ECU-Partitionen im Multicore-Kontext.

2. Komponenten, Entitäten & Schnittstellen

  • Modulspezifikationstabelle (ECUC_Nm_00243):
    • Metadaten des Moduls Nm (The Generic Network Management Interface module).
    • Post-Build Variant Support: false.
    • Supported Config Variants: VARIANT-LINK-TIME, VARIANT-PRE-COMPILE.
    • Enthaltene Container: NmChannelConfig (1..*) und NmGlobalConfig (1).
  • Nm : EcucModuleDef
    • Kardinalität: lowerMultiplicity = 0, upperMultiplicity = 1.
    • Rolle: Wurzelknoten der Konfigurationsdefinition des NM-Interface pro ECU-Konfiguration.
  • NmGlobalConfig : EcucParamConfContainerDef
    • Beziehung: Komposition (+container) von Nm, Multiplizität 1..1 (obligatorisch, genau einmal vorhanden).
    • Rolle: Bündelt alle ECU-weiten, kanalübergreifenden Konfigurationsparameter (ECUC_Nm_00196). Enthält als Unterbehälter (+subContainer, Komposition):
      • NmGlobalConstants : EcucParamConfContainerDef (Multiplizität 1..1): Statische Implementierungsparameter und Identifikatoren (z. B. Version-Info-API-Aktivierung).
      • NmGlobalProperties : EcucParamConfContainerDef (Multiplizität 1..1): Grundlegende Betriebsmodi, Fehlerbehandlung und globale Ausführungsattribute.
      • NmGlobalFeatures : EcucParamConfContainerDef (Multiplizität 1..1): Schalter für optionale NM-Zusatzfunktionen (z. B. Coordinator Support, Bus Synchronization, Car Wake Up, Remote Sleep Indication, State Change Notification).
    • Referenzen (+reference):
      • NmEcucPartitionRef : EcucReferenceDef (Multiplizität lowerMultiplicity = 0, upperMultiplicity = 1): Optionale Referenz auf eine Zielpartition.
  • EcucPartition : EcucParamConfContainerDef
    • Multiplizität: lowerMultiplicity = 0, upperMultiplicity = *.
    • Rolle: Zielcontainer (+destination) der Referenz NmEcucPartitionRef zur Zuordnung des NM-Interface zu einer Ausführungspartition.
  • NmChannelConfig : EcucParamConfContainerDef
    • Beziehung: Komposition (+container) von Nm, Multiplizität 1..* (lowerMultiplicity = 1, upperMultiplicity = *).
    • Rolle: Kanalspezifische Konfigurationsinstanzen. Jeder logische Kommunikationskanal, der vom NM verwaltet wird, benötigt genau eine Instanz dieses Containers. Er kapselt Kanalindex, Bezug zum ComMChannel, Bus-Typ-Bindung (CAN, FlexRay, etc.) sowie die Referenz auf das korrespondierende unterlagerte BusNM.

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Konfigurationsmetamodell handelt, existiert kein PDU- oder Task-Laufzeitfluss direkt im Modell. Die Auswirkungen auf den Systemablauf sind:

  • Generierungsphase:
    • BSW-Generatoren parsen die Instanzen von NmGlobalConfig und NmChannelConfig aus dem EcuC-ARXML.
    • Erzeugung statischer ROM-Tabellen (Nm_ChannelConfig[]) und Präprozessor-Makros (z. B. NM_COORDINATOR_SUPPORT_ENABLED, NM_VERSION_INFO_API).
  • Initialisierungsphase (Nm_Init):
    • Bei Aufruf von Nm_Init(&Nm_Config) initialisiert das Modul seine internen Zustandstabellen für exakt die Anzahl der durch NmChannelConfig (Kardinalität 1..*) definierten Kanäle.
    • Globale Features (NmGlobalFeatures) bestimmen, ob globale Callbacks registriert und synchrone/asynchrone Koordinierungsroutinen in der Main-Function (Nm_MainFunction) ausgeführt werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Mindestanforderung (Multiplicity 1..* bei NmChannelConfig):
    • Eine gültige Nm-Konfiguration erfordert mindestens einen aktiven Kommunikationskanal. Ein fehlerhafter EcuC-Datensatz ohne Kanäle ist schema-ungültig.
  • Variantenbeschränkung (Post-Build Variant Support: false):
    • Das Modul unterstützt ausschließlich VARIANT-PRE-COMPILE und VARIANT-LINK-TIME. Eine Konfiguration zur Post-Build-Laufzeit ist ausgeschlossen.
  • Partitionierung & Multicore-Support (NmEcucPartitionRef):
    • Über NmEcucPartitionRef (0..1) kann das NM-Interface einer spezifischen EcucPartition zugewiesen werden, um Ausführung und Speicherbereiche in Multicore-Systemen zu kapseln.
  • Global vs. Per-Channel Entkopplung:
    • Globale Einstellungen dürfen nicht auf Kanalebene überschrieben werden. Feature-Aktivierungen in NmGlobalFeatures schalten Schnittstellen für das gesamte Modul frei (z. B. Nm_NetworkRequest vs. passive Überwachung).
  • BSW-Stack-Integration & API-Vertrag:
    • Die Kanalindizes aus NmChannelConfig müssen 1:1 mit den referenzierten ComMChannel-IDs und den Instanzen der BusNM-Treiber (CanNm, FrNm) konsistent gemappt sein. Falsche Zuordnungen führen zu Kanalverwechslungen bei Nm_NetworkMode / Nm_BusSleepMode Meldungen an den ComM.
    • Ist NmGlobalFeatures so parametriert, dass optionale Features (z. B. NmStateChangeIndication) deaktiviert sind, werden entsprechende Callback-Stubs zu BSW-Nutzern oder dem RTE-Layer nicht einkompiliert, was ROM/RAM-Footprint spart.
