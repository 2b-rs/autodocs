1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Zweistufiges AUTOSAR-Komponenten- und Allokationsdiagramm (oben: VFB-Abstraktionsebene; unten: ECU-Mapping und Systemverteilung mit RTE-, BSW- und Netzwerkebene).
  • Technischer Zweck & Einordnung: Veranschaulichung des normativen Musters für netzwerkübergreifende Modusanforderungen (Mode Request over the Network) gemäß AUTOSAR Classic Platform (R4.0.3/R4.1.3, AUTOSAR_TPS_SoftwareComponentTemplate, Kap. 11 Mode Management, TPS_SWCT_01415, TPS_SWCT_01416).
  • Kernproblem: Ein ModeSwitchInterface ist in AUTOSAR ein rein ECU-lokales Schnittstellenkonzept. Die RTE unterstützt keinen direkten netzwerkweiten Transport von Modusumschaltungen via COM/PDU. Ein netzwerkweiter Moduswechsel (hier Klemmensteuerung via VehicleClampControl) muss daher als Modusanforderung über SenderReceiverInterface übertragen und auf den Ziel-Steuergeräten über Adapter-/Proxy-Komponenten (VehicleClampProxy) an den lokalen Basic Software Mode Manager (BswM) übergeben werden, der den eigentlichen lokalen Moduswechsel steuert.

  • Ports: RPortPrototype (S/R, weißes Quadrat, schwarzes Dreieck nach oben) und PPortPrototype (S/R bzw. Mode-Request-Interface, schwarzes Quadrat, weißes Dreieck nach unten).
  • App1: Application1 & App2: Application2: ApplicationSwComponentType, fungieren als Modusnutzer (Mode Users).
  • Port: RPortPrototype mit ModeSwitchInterface (schwarzes Quadrat mit 3 weißen Punkten / Mode-Symbol).
  • Allokation & Infrastruktur (ECU-Ebene unten):
  • ECU1:
  • Beherbergt VCC, eine Instanz von VCP sowie App1.
  • RTE1: Löst 1:n-Verteilung auf (lokal an VCP auf ECU1 sowie busübergreifend via BSW-Kommunikationsstack).
  • BSW1 / BswM Service: BSW-Modul Basic Software Mode Manager als ServiceSwComponentType. Verfügt über Eingangs-Port (Mode Request via S/R von VCP) und PPortPrototype mit ModeSwitchInterface (Mode Manager) Richtung App1.
  • ECU2:
  • Beherbergt eine Instanz von VCP und App2.
  • RTE2: Koppelt das über den Bus empfangene Signal an den RPort von VCP.
  • BSW2 / BswM Service: Lokaler Mode Manager auf ECU2, nimmt Request von VCP entgegen und bedient das ModeSwitchInterface von App2.
  • Netzwerkverbindung: Buskoppelung (CAN, LIN, FlexRay oder Ethernet) zwischen RTE1 und RTE2, realisiert über COM, PduR und Schnittstellentreiber.
  • Beziehungen & Metamodell-Kardinalitäten:
  • SwComponentPrototype instanziiert SwComponentType («isOfType»).
  • AssemblySwConnector verbindet Ports ECU-intern (VCC $\rightarrow$ VCP, VCP $\rightarrow$ BswM, BswM $\rightarrow$ App).
  • DelegationSwConnector / SwcToEcuMapping: Mappt VFB-Ports und Komponenten auf konkrete Steuergeräte (EcuInstance).
  • SenderReceiverToSignalMapping: Mappt das S/R-Datenelement des Mode-Requests auf ein ISignal / Com-Signal für die Busübertragung.

3. Dynamisches Verhalten & Sequenzablauf

  1. Modusanforderung (Trigger): VCC auf ECU1 bestimmt anhand von Fahrzeugbedingungen einen neuen Klemmenzustand und stößt den Request an via:

$$\text{Rte\_Write\_

\_(\dots)}$$

  1. Signalverteilung über RTE1:
  • Lokal: RTE1 stellt die Daten der lokalen VCP-Instanz auf ECU1 bereit.
  • Netzwerk: RTE1 übergibt das Signal an den COM-Stack (Com_SendSignal()). Der Frame wird als I-PDU über den Fahrzeugbus übertragen.
  1. Empfang & Entpacken auf ECU2:
  • COM-Stack auf ECU2 empfängt die PDU und übergibt das Signal an RTE2.
  • RTE2 aktiviert die Runnable von VCP auf ECU2 (via DataReceivedEvent oder zyklischem Task-Polling via Rte_Read).
  1. Proxy-Weiterleitung an BswM:
  • VCP auf ECU1 und ECU2 leitet die Modusanforderung an den jeweiligen lokalen BswM Service weiter (via RTE-Port an BswM-Service-Port).
  1. BswM-Modusarbitrierung & Ausführung:
  • Der BswM-Arbitrator evaluiert konfigurierte Regeln (BswMRule mit BswMModeCondition).
  • Sind alle lokalen Sicherheits- und Zustandsbedingungen erfüllt, triggert die BswMActionList eine Modusumschaltung via BswMRteModeSwitch.
  1. Lokaler Moduswechsel (Rte_Switch):
  • BswM ruft die generierte RTE-API auf:

$$\text{Rte\_Switch\_

\_()}$$

  • Die lokale RTE wechselt den Modus der Modus-Zustandsmaschine (Mode Declaration Group).
  1. Notifikation der Mode Users:
  • App1 (ECU1) und App2 (ECU2) werden über swcModeSwitchEvent (OnEntry, OnExit oder OnTransition) geweckt oder lesen den Modus statusabhängig per:

$$\text{Rte\_Mode\_

\_()}$$

  1. Fehler- und Abbruchpfade:
  • Bei Bus-Timeout greift der COM-Rx-Timeout-Mechanismus; BswM empfängt einen Ersatzwert (BswMDefaultMode) oder schaltet über Fallback-Regeln in einen sicheren Klemmenmodus (z. B. Fail-Safe/Clamp-Fault).

4. Normative Relevanz & Entwickler-Hinweise

  • TPS_SWCT_01415 & TPS_SWCT_01416 Konformität:
  • Es ist strikt unzulässig, ein ModeSwitchInterface netzwerkübergreifend zwischen zwei verschiedenen ECUs zu mappen. Modusanforderungen über Busgrenzen müssen zwingend als Datenkommunikation (SenderReceiverInterface) modelliert werden.
  • Modusdeklarationen (ModeDeclarationGroup) sind strikt ECU-lokal gebunden.
  • Konfigurationsvorgaben im BSW-Stack (BswM / RTE):
  • BswM: Erfordert die Konfiguration eines BswMModeRequestPort (vom Typ BswMSwcModeRequest oder BswMGenericRequest), verknüpft mit dem Port von VCP.
  • RTE-Vertrag: Der BswM muss als Mode Manager für die entsprechende ModeDeclarationGroupPrototype konfiguriert sein (isReentrant = false beachten; Umschaltung ist nicht unterbrechbar).
  • Applikation (App1/App2): Werden rein als Mode User definiert (RPortPrototype mit ModeSwitchInterface). Runnables müssen an ModeSwitchEvent gebunden werden, um Kontextwechsel automatisiert auszuführen.
  • Proxy-Architekturmuster:
  • Der Einsatz von VCP: VehicleClampProxy auf jeder ECU entkoppelt die herstellerspezifische Busbotschaft vom standardisierten BswM-Service-Interface. Dies ermöglicht den Austausch des Übertragungsprotokolls (z. B. CAN-PDU vs. Ethernet SOME/IP), ohne den applikativen Kern oder die BswM-Regellogik ändern zu müssen.
