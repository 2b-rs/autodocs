1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR ECU Configuration (ECUC) Metamodell / UML-Klassendiagramm der Parameterdefinition (ModuleDef).
  • Standard & Release: AUTOSAR Classic Platform Release R2.1.20 (referenziert Spezifikation Watchdog Driver v2.0.4 vom 13.12.2006).
  • Architektur-Kontext: Definiert die formale Konfigurationsstruktur für das BSW-Modul Watchdog Driver (Wdg) innerhalb der Microcontroller Abstraction Layer (MCAL).
  • Technischer Zweck: Bereitstellung des Metamodell-Schemas für Generatoren und Konfigurations-Editoren (z. B. EB Tresos, DaVinci Configurator) zur Parametrierung interner oder externer Watchdog-Treiber sowie deren Anbindung an das Watchdog Interface (WdgIf) und den Watchdog Manager (WdgM).

2. Komponenten, Entitäten & Schnittstellen

Wurzel-Entität
  • Wdg : ModuleDef
    • Multiplizität: lowerMultiplicity = 0, upperMultiplicity = * (erlaubt 0 bis n Instanzen, z. B. paralleler Betrieb von internem Hardware-Watchdog und externem SBC-Watchdog).
Globale Treiberkonfiguration
  • WdgGeneral : ParamConfContainerDef (Aggregation via +container):
    • WdgIndex : IntegerParamDef (symbolicNameValue = true): Eindeutiger Identifikator der Treiberinstanz; wird als symbolischer C-Präprozessor-Name exportiert (WdgConf_WdgGeneral_...) zur Adressierung im WdgIf.
    • WdgVersionInfoApi : BooleanParamDef: Aktiviert/deaktiviert die Codegenerierung der Funktion Wdg_GetVersionInfo().
    • WdgDevErrorDetect : BooleanParamDef: Schaltet die statische Parameterprüfung und Meldung von Entwicklungsfehlern an den Default Error Tracer (Det_ReportError) scharf.
    • WdgDisableAllowed : BooleanParamDef: Sicherheitsrelevantes Sperrflag; definiert, ob der Watchdog im laufenden Betrieb deaktiviert werden darf.
    • WdgTriggerLocation : FunctionNameDef: Symbolischer Name/Funktionsbezeichner der hardwarenahen Trigger- bzw. Servicing-Funktion.
Laufzeit- & Modus-Konfiguration
  • WdgModeConfig : ParamConfContainerDef (Aggregation via +container):
    • Attribut: multipleConfigurationContainer = true (kennzeichnet diesen Container als Post-Build- bzw. Link-Time-selektierbaren Parametersatz zur Laufzeit-Variantenbildung).
    • WdgDefaultMode : EnumerationParamDef (Aggregation via +parameter):
      • Definiert den Default-Modus nach Ausführung von Wdg_Init().
      • Enthaltene Literale (+literal):
        • OffMode : EnumerationLiteralDef (WDGIF_OFF_MODE)
        • SlowMode : EnumerationLiteralDef (WDGIF_SLOW_MODE)
        • FastMode : EnumerationLiteralDef (WDGIF_FAST_MODE)
    • Sub-Container (+subContainer):
      • WdgSettingsFast : ParamConfContainerDef: Hardwarespezifische Register-Parametrierung (Reload-Werte, Prescaler) für den schnellen Zyklus (z. B. regulärer Task-Überwachungsbetrieb).
      • WdgSettingsSlow : ParamConfContainerDef: Hardwarespezifische Register-Werte für den langsamen Zyklus (z. B. Start-up, Shutdown oder Low-Power/Standby).
      • WdgSettingsOff : ParamConfContainerDef: Registerkonfiguration zur vollständigen Deaktivierung der Watchdog-Hardware.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt ein deklaratives Metamodell, determiniert jedoch direkt die BSW-Zustands- und Ablauflogik:

  1. Initialisierungssequenz (Wdg_Init):
    • Der Treiber erhält einen Pointer auf die selektierte WdgModeConfig-Struktur (const Wdg_ConfigType* ConfigPtr).
    • Die Hardware wird initial auf den Modus parametriert, der über WdgDefaultMode vorgegeben ist.
  2. Modusumschaltung (Wdg_SetMode):
    • Synchroner Aufruf durch das WdgIf.
    • Bei Request WDGIF_OFF_MODE: Treiber prüft WdgDisableAllowed. Ist der Wert FALSE, wird der Übergang mit E_NOT_OK abgebrochen und bei aktiver Fehlererkennung WDG_E_DISABLE_NOT_ALLOWED an das Det gemeldet.
    • Bei gültigem Wechsel (FAST, SLOW, OFF) werden die hinterlegten Hardware-Registereinstellungen aus WdgSettingsFast, WdgSettingsSlow bzw. WdgSettingsOff in die Hardware-Timer geladen.
  3. Trigger-Zyklus:
    • Die über WdgTriggerLocation definierte Routine wird zyklisch über Wdg_SetTriggerCondition() getriggert, um den Hardware-Reset-Counter vor Ablauf des konfigurierten Timeouts zurückzusetzen.

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher- und Datenstrukturlayout (Linker/ROM/RAM):
    • Durch multipleConfigurationContainer = true müssen alle Parameter unterhalb von WdgModeConfig in post-build-fähige C-Strukturen (Wdg_ConfigType in Wdg_PBCfg.c) generiert werden. Parameter aus WdgGeneral gehören in Pre-Compile-Header (Wdg_Cfg.h).
  • Funktionale Sicherheit (ISO 26262 / ASIL):
    • WdgDisableAllowed = FALSE ist für sicherheitskritische ECUs zwingend zu setzen, um ein versehentliches oder durch Softwarefehler ausgelöstes Stilllegen der CPU-Überwachung auszuschließen.
  • Multicore- & Multi-Watchdog-Betrieb:
    • Da Wdg : ModuleDef eine obere Multiplizität von * besitzt, müssen generierte APIs und Identifikatoren reentrant bzw. per Index parametrierbar sein. Das WdgIf routet über WdgIndex an die konkrete Treiberinstanz (z. B. Wdg_Channel1_SetMode).
  • Code-Größen-Optimierung:
    • WdgVersionInfoApi = FALSE entfernt die Versions-API vollständig per #if (WDG_VERSION_INFO_API == STD_ON) aus dem Binary.
    • Wenn WdgDisableAllowed = FALSE, kann der Codegenerator die Auswertung und Codepfade für WdgSettingsOff vollständig eliminieren.
