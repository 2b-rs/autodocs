1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Binäres Wire-Format / PDU-Bitfeld-Layout (128 Bit / 16 Byte).
  • Technischer Zweck: Spezifiziert die serielle On-Wire-Struktur eines Service Entry im SOME/IP-Service-Discovery-Protokoll (PRS_SOMEIPSD_00270, RS_SOMEIPSD_00006).
  • Funktionale Einordnung: Dient in der AUTOSAR Classic Platform (Modul Sd / Service Discovery) und in der AUTOSAR Adaptive Platform (ara::com / Kommunikations-Daemon) dem standardisierten Bekanntmachen (OfferService), Suchen (FindService) und Zurücknehmen (StopOfferService) von Dienstinstanzen über Ethernet/UDP (Default-Port 30490). Der Entry wird innerhalb des Entries Array einer SOME/IP-SD-Nachricht serialisiert.

2. Komponenten, Entitäten & Schnittstellen

Die PDU besitzt eine feste Länge von 16 Bytes (128 Bits) und wird in Network Byte Order (Big Endian) codiert:

  • Type (8 Bit, Bit-Offset 0–7): Kennung der Semantik des Eintrags:
    • 0x00: FindService (Suchanfrage eines Clients).
    • 0x01: OfferService bzw. StopOfferService (Bereitstellung oder Rücknahme durch den Server, differenziert über das Feld TTL).
  • Index 1st options (8 Bit, Bit-Offset 8–15): 0-basierter Offset in das nachfolgende Options-Array der SOME/IP-SD-Message für das primäre Options-Set (z. B. Endpoint-Optionen für IPv4/IPv6).
  • Index 2nd options (8 Bit, Bit-Offset 16–23): 0-basierter Offset in das Options-Array für das sekundäre Options-Set.
  • # of opt 1 (4 Bit, Bit-Offset 24–27): Anzahl aufeinanderfolgender Optionen aus Set 1 (Wertebereich 0 bis 15).
  • # of opt 2 (4 Bit, Bit-Offset 28–31): Anzahl aufeinanderfolgender Optionen aus Set 2 (Wertebereich 0 bis 15).
  • Service ID (16 Bit, Bit-Offset 32–47): Eindeutige Funktionsidentifikation des Service-Interfaces (identisch zur SOME/IP-Message-Header Service-ID).
  • Instance ID (16 Bit, Bit-Offset 48–63): Identifikation der konkreten Service-Instanz. Der Wert 0xFFFF definiert eine Wildcard („All/Any Instances“, nur zulässig bei FindService).
  • Major Version (8 Bit, Bit-Offset 64–71): Hauptversion des Service-Interface (Breaking Changes). Der Wert 0xFF kann bei FindService als Wildcard dienen.
  • TTL (Time to Live) (24 Bit, Bit-Offset 72–95): Lebensdauer des Eintrags in Sekunden:
    • TTL > 0: Gültigkeitsintervall für OfferService oder FindService.
    • TTL == 0: Signalisiert StopOfferService (Dienst wird sofort deregistriert).
  • Minor Version (32 Bit, Bit-Offset 96–127): Nebenversion des Service-Interface (abwärtskompatible Erweiterungen). Bei FindService häufig mit 0xFFFFFFFF (Wildcard/Default) belegt.

3. Dynamisches Verhalten & Sequenzablauf

  • Service Discovery Phasen:
    1. Find-Phase (Client): Ein Service-Konsument sendet bei Initialisierung oder fehlendem Server einen Entry mit Type = 0x00 (FindService), Instance ID = 0xFFFF (optional Wildcard) und TTL > 0 als Multicast.
    2. Offer-Phase (Server): Der Service-Provider antwortet oder publiziert zyklisch/bei State-Change (BswM-Trigger) einen Entry mit Type = 0x01 (OfferService), konkreter Instance ID, TTL = Service-TTL (> 0) und verweist via Index 1st options auf seine IP-Adresse und Transport-Ports (UDP/TCP).
    3. StopOffer-Phase (Server): Beim kontrollierten Herunterfahren (z. B. ECU-Sleep, Partition-Reset) sendet der Provider einen Entry mit Type = 0x01 und TTL = 0x000000 (StopOfferService), woraufhin Empfänger die Routing-Tabellen unverzüglich invalidieren.
  • Fehlerbehandlung:
    • Erkennt der Stack ungültige Indizes (Index + Count > Options Length) oder unzulässige Wildcards in Offer-Entries, wird der Entry verworfen und ein Fehler an das DET (SD_E_INV_PACKET) bzw. Security-Event-Reporting übergeben.

4. Normative Relevanz & Entwickler-Hinweise

  • Speicher- und Struct-Packing-Fallen:
    • Das 24-Bit-Feld TTL erzeugt zusammen mit den 4-Bit-Feldern (# of opt 1 / 2) unaligned Word-Grenzen. C-Structs dürfen niemals direkt auf den PDU-Puffer gecastet werden (Gefahr von Alignment-Faults auf 32/64-Bit-Cores wie ARM Cortex-M/R/A oder Infineon AURIX TriCore).
    • Serialisierung/Deserialisierung muss strikt über byteweise Shifts und Maskierungen erfolgen: 
      ttl = ((uint32)entry[9] << 16) | ((uint32)entry[10] << 8) | (uint32)entry[11];
  • Validierung des Options-Index:
    • Der SD-Parser muss vor jedem Zugriff prüfen: (Index_1st + Num_Opt_1) <= Gesamtanzahl_Optionen, um Out-of-Bounds-Lesezugriffe auf das Options-Array auszuschließen (Robustness / MISRA-C / ISO 21434).
  • Konfigurationsabgleich (Sd.epc):
    • Service ID und Instance ID müssen exakt mit den Parametern SdClientServiceConfiguration bzw. SdServerServiceConfiguration im ARXML-Datenmodell übereinstimmen.
