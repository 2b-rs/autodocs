1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Prozessmodell nach SPEM 2.0 (Software & Systems Process Engineering Metamodel), formal modelliert als «SPEM_MethodContentPackage» innerhalb der AUTOSAR Adaptive Platform Methodology (AUTOSAR_AP_TR_Methodology, Kapitel 2.1 / 3.1).
  • Technischer Zweck: Spezifikation der methodischen Phasengrenze zur Definition der fahrzeugweiten System- und Grobarchitektur. Sie definiert die disziplinübergreifende Entwurfsphase zur Vorbereitung heterogener E/E-Systeme, bestehend aus:
    • AUTOSAR Adaptive Platform (AP) Machines,
    • AUTOSAR Classic Platform (CP) ECU-Instances,
    • Nicht-AUTOSAR Rechenknoten (Non-AUTOSAR HW/SW entities).
  • Funktionale Einordnung: Bildet den vorgelagerten System-Design-Schritt vor der Allokation von Software-Komponenten auf Rechnerknoten und Kommunikationscluster in Define System Topology.

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Stereotypen (SPEM 2.0 Metamodell)
  • Paket-Container:
    • «SPEM_MethodContentPackage» High Level Architecture: Kapselt den Methodeninhalt der High-Level-Systementwurfsphase.
  • Prozessaktivitäten («TaskDefinition»):
    • Define High Level Architecture: Übergeordnete, zusammengesetzte System-Design-Task.
    • Develop Function Architecture: Erarbeitung der funktionalen Dekomposition (Funktionsnetzwerk, logische Signal- und Datenflüsse unabhängig von Plattform oder HW).
    • Develop Abstract Platform Specification: Spezifikation technologieneutraler Plattformanforderungen, Interaktionsmuster und Service-Definitionen.
    • Develop Vehicle Software Architecture: Strukturierung der Gesamtfahrzeug-Software (Aufteilung in AP-Applikationen, CP-Software-Components, Standard-/OS-Dienste).
    • Develop Vehicle Hardware Architecture: Entwurf der physikalischen E/E-Topologie (ECUs, Mikroprozessoren, Mikrocontroller, Busse, Spannungsversorgung).
    • Define System Topology (extern/nachgelagert): Downstream-Task zur Zuordnung von Software zu Hardware und Netzwerk-Clustern.
  • Arbeitsergebnisse («Artifact» & «Deliverable»):
    • «Artifact» Function Architecture: Konkretes Zwischenergebnis der Funktionsarchitektur.
    • «Artifact» Abstract Platform Specification: Konkretes Zwischenergebnis der plattformneutralen Spezifikation.
    • «Artifact» Vehicle Software Architecture: Formale Modellierung der logischen Software-Architektur.
    • «Artifact» Vehicle Hardware Architecture: Formale Modellierung der physikalischen Steuergeräte- und Gateway-Infrastruktur.
    • «Deliverable» High Level Architecture: Zusammengesetztes, freigabefähiges Gesamtergebnis (Meilenstein-Produkt).
    • «Deliverable» Service Interface Description (kontextuell begleitend): Formalisiertes Artefakt zur Definition der serviceorientierten Schnittstellen (SOI / Service Interfaces).
Beziehungen & Abhängigkeiten
  • «contributes» (Task-Ebene): Die vier spezialisierten Tasks Develop Function Architecture, Develop Abstract Platform Specification, Develop Vehicle Software Architecture und Develop Vehicle Hardware Architecture tragen per SPEM-Variabilitätsmodell (contributes) zur Composite-Task Define High Level Architecture bei.
  • «output»: Jede der vier «TaskDefinition» erzeugt unidirektional genau ein zugeordnetes «Artifact» (1:1-Beziehung).
  • «contributes» (Artifact-Ebene): Alle vier Einzel-«Artifact» aggregieren/beitragen per «contributes» in das zentrale Container-Workproduct «Deliverable» High Level Architecture.
  • «input»: Das «Deliverable» High Level Architecture dient als verbindliche Eingangsvoraussetzung («input») für die nachgelagerte Task «TaskDefinition» Define System Topology.

3. Dynamisches Verhalten & Sequenzablauf

  1. Gleichzeitige/Iterative Architekturerstellung:
    • Die vier Task-Definitionen werden iterativ und mit wechselseitiger Rückkopplung durchlaufen:
      • Funktionale Modellierung ↔ Abstrakte Plattform-Vorgaben.
      • Software-Architektur ↔ Hardware-Architektur.
  2. Artefakt-Synthese («output»):
    • Parallelisierung der vier spezialisierten Modellausleitungen in maschinenlesbare Beschreibungen (AUTOSAR ARXML).
  3. Konsolidierung zu Deliverable:
    • Die Artefakte fließen synchron zusammen («contributes») und bilden den konsistenten Snapshot High Level Architecture.
  4. Methodischer Handover («input»):
    • Die konsolidierte High Level Architecture wird der Task Define System Topology übergeben. Dort erfolgt:
      • Mapping logischer SWCs / Adaptive Applications auf ECUs / Machines (EcuInstance, Machine).
      • Definition der Netzwerk-Topologie (Ethernet-Switches, CAN-Controller, VLANs).
      • Mapping der Inter- und Intra-Machine-Kommunikation.
  5. Rolle der Service Interface Description:
    • Steht orthogonal bereit, um bei der Definition der Funktionsarchitektur und der System-Topologie die serviceorientierten Verträge (Events, Methods, Fields) frühzeitig zu fixieren, bevor transport-spezifische Bindings (SOME/IP, IPC, DDS) definiert werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Plattformübergreifender Modellvertrag:
    • Entwickler von Adaptive Applications (ara::com) und Classic SWCs (RTE-Interfaces) operieren auf gemeinsamen Vorbedingungen: Das Deliverable fixiert die Schnittstellentechnologie (Service vs. Signal-based Communication) an den Übergangspunkten zwischen CP- und AP-Knoten.
  • Entkopplung durch abstrakte Spezifikation:
    • Die Trennung in Abstract Platform Specification und Service Interface Description verhindert ein verfrühtes Lock-in auf konkrete Netzwerkprotokolle oder Serialisierungsformate (z. B. SOME/IP-Header-Layout, E2E-Profile). Die Schnittstellensignatur wird abstrakt entworfen, das Binding folgt erst in der System-Topologie und dem Deployment.
  • ARXML-Konsistenzbedingungen:
    • Werkzeuge zur Validierung der Systembeschreibung (System Description Validator) fordern Vollständigkeit aller vier Teil-Artefakte: Ohne hardwareseitige Machine- bzw. EcuInstance-Definitionen und ohne logische SoftwareComponent- bzw. AdaptiveApplication-Modelle schlägt das spätere RootSwComposition- und SoftwareMapping-Parsing in downstream Codegeneratoren fehl.
  • Keine direkte C++/C-API-Bindung:
    • Das Diagramm definiert keine Laufzeit-Schnittstellen (keine Funktionsprototypen, BSW-Stacks oder POSIX-OS-APIs), sondern regelt die methodische Governance, welche ARXML-Modellfragmente vor Beginn der komponentenbezogenen Implementierung zwingend vorliegen müssen.

Methodology for Adaptive Platform AUTOSAR AP R24-11 2.1 System - High Level Architecture A typical vehicle will be most likely equipped with ECUs hosting – ECU-Instances with software developed for the AUTOSAR classic platform (CP) – and Machines with software developed for the AUTOSAR adaptive platform (AP) – and eventually also HW entities with non-AUTOSAR software.
