1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Metamodell-Ausschnitt / UML-Klassendiagramm der AUTOSAR ECU Configuration Description (BSW ECUC Parameter Definition).
  • Technischer Zweck: Spezifikation der Abhängigkeiten und Initialisierungsreferenzen des ECU State Managers (EcuM) auf fremde BSW-Treiber- und Service-Konfigurationssätze im AUTOSAR Classic Release R2.1.20.
  • Architektonische Einordnung: Bindeglied zwischen System-Management (EcuM) und den Subsystemen Microcontroller Drivers (MCU), Timer (GPT) sowie System Services (WdgManager). Dient der statischen Konfigurationsauflösung zur Erzeugung des Post-Build-Selectable Root-Konfigurationsstruktursatzes (EcuM_ConfigType).

2. Komponenten, Entitäten & Schnittstellen

  • Klassendefinitionen & Stereotypen (Metamodell-Elemente):
    • EcuM : ModuleDef (Multiplizität 0..1): Moduldefinition des ECU State Managers.
    • EcuMConfiguration : ParamConfContainerDef: Zentraler Root-Container für die EcuM-Konfiguration.
      • Attribute: multipleConfigurationContainer = TRUE (Post-Build-fähiges Konfigurationsset), lowerMultiplicity = 1, upperMultiplicity = 1.
    • ReferenceDef (Metaklasse für Konfigurationsreferenzen):
      • EcuMWdgMInitConfig : ReferenceDef: Konfigurationsreferenz auf den Watchdog Manager.
      • EcuMMcuInitConfig : ReferenceDef: Konfigurationsreferenz auf den MCU-Treiber.
      • EcuMGptInitConfig : ReferenceDef: Konfigurationsreferenz auf den General Purpose Timer-Treiber.
    • Ziel-Container (ParamConfContainerDef):
      • WdgMConfigEntities : ParamConfContainerDef (Paket: WdgManager): multipleConfigurationContainer = true.
      • McuModuleConfiguration : ParamConfContainerDef (Paket: MCU): multipleConfigurationContainer = TRUE, Multiplizität [1..1].
      • GptChannelConfigSet : ParamConfContainerDef (Paket: GPT): multipleConfigurationContainer = TRUE, Multiplizität [1..1].
  • Beziehungen & Assoziationen:
    • Komposition (+container): EcuM aggregiert exakt eine Instanz von EcuMConfiguration.
    • Komposition (+reference): EcuMConfiguration aggregiert je eine Instanz der drei ReferenceDef-Elemente (EcuMWdgMInitConfig, EcuMMcuInitConfig, EcuMGptInitConfig).
    • Unidirektionale Zielassoziation (+destination): Jedes ReferenceDef-Element verweist typisiert auf den jeweiligen Ziel-Container des Zielmoduls.

3. Dynamisches Verhalten & Sequenzablauf (Initialisierungs-Phase)

Das statische Metamodell bildet das Fundament für die synchrone Startup-Phase des Steuergeräts (EcuM_Init):

  1. Konfigurationsauflösung (Pre-OS Startup Phase):
    • Übergabe des Basiszeigers auf die aktive Konfiguration: EcuM_Init(const EcuM_ConfigType* ConfigPtr).
    • Der EcuM dereferenziert die in EcuMConfiguration aggregierten Referenzen zur Auflösung der typisierten Zeiger auf die Sub-Konfigurationsstrukturen.
  2. Init-Kette (Synchrone Aufrufe):
    • Mcu_Init(&McuModuleConfiguration): Grundlegende Takt-, PLL- und Power-Initialisierung.
    • Gpt_Init(&GptChannelConfigSet): Bereitstellung von hardwarebasierten Zeitgebern (u. a. für OS-Ticks und Watchdog-Triggertakte).
    • WdgM_Init(&WdgMConfigEntities): Aktivierung des Watchdog-Überwachungsmanagements zur Absicherung der weiteren Bootphasen.
  3. Fehlerbehandlung:
    • Ist ein referenzierter Zielzeiger NULL oder inkonsistent, erfolgt je nach Modul ein Default-Error-Tracer-Eintrag (DET: *_E_PARAM_POINTER bzw. *_E_PARAM_CONFIG) und der Abbruch in einen definierten EcuM-Halt-/Safe-Zustand.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Code-Generierung (EcuM_PBcfg.c / EcuM_Cfg.h):
    • Der Codegenerator des EcuM leitet aus diesen Referenzen direkte Zeiger-Member in der globalen Root-Struktur ab: 
      typedef struct {
    const Mcu_ConfigType*  McuConfigPtr;
    const Gpt_ConfigType*  GptConfigPtr;
    const WdgM_ConfigType* WdgMConfigPtr;
    /* ... weitere modulspezifische Parameter ... */
} EcuM_ConfigType;
  • Post-Build- & Variantenkonsistenz:
    • Da multipleConfigurationContainer = TRUE auf allen beteiligten Containern gesetzt ist, müssen bei post-build-fähigen ECUs (PB-Selectable) die Variantenkombinationen zwingend konsistent aufeinander abgebildet werden (Link-Time/Load-Time-Validierung der Config-Sets).
  • Integrations-Restriktionen:
    • Modul-Header-Sichtbarkeit: EcuM_PBcfg.c erfordert zwingend die Inklusion von Mcu.h, Gpt.h und WdgM.h.
    • Architektonischer Hinweis (Versions-Drift): In R2.1.20 erfolgte die Verknüpfung der Treiber-Init-Sets noch über diese dedizierten ReferenceDef-Einträge in EcuMConfiguration. In späteren AUTOSAR-Releases (ab R3.x/R4.x) wurde dieses Design durch generische Driver-Init-Listen (EcuMDriverInitListOne, EcuMDriverInitItem) abgelöst.
