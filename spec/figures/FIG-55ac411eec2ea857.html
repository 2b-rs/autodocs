1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR-Methodik-Aktivitäts- und Artefaktflussdiagramm (basierend auf SPEM – Software & Systems Process Engineering Metamodel / UML-Aktivitätsnotation).
  • Architektur-Kontext: AUTOSAR Classic Platform (CP), AUTOSAR_TR_Methodology. Das Diagramm beschreibt den Build- und Bindeprozess für die BSW-Konfigurationsklasse Link-Time-Konfiguration (VARIANT-LINK-TIME). Es visualisiert die Entkopplung von herstellerseitig vorkompiliertem BSW-Kerncode (IP-Schutz/Objektcode-Lieferung) und projektspezifisch generierten Konfigurationsdaten sowie die sukzessive Bindung von Variationspunkten bis zum fertigen ECU-Binary.

2. Komponenten, Entitäten & Schnittstellen

#### Aktivitäten (Prozessschritte / Transformationen)

  • Compile Unconfigured BSW: Kompiliert herstellerseitigen BSW-Quellcode unabhängig von projektspezifischen Konfigurationswerten.
  • Generate BSW Configuration Code: Code-Generator-Schritt zur Erzeugung der Link-Time-Konfigurationsdateien aus den ECU-Konfigurationswerten.
  • Compile BSW Configuration Data: Kompiliert die generierten Konfigurationsquellen unter Einbindung der Kern- und Konfigurations-Header.
  • Link ECU Code during Link Time Configuration: Linker-Lauf zur Symbolauflösung zwischen BSW-Kernobjekten und Konfigurationsobjekten.

#### Artefakte / Work Products (Daten & Code)

  • Basic Software Module Core Source Code [1]: Modul-Implementierung (.c).
  • Basic Software Module Core Header [1]: Öffentliche Modulschnittstelle und Typdefinitionen (.h, z. B. <Module>.h, <Module>_Types.h).
  • ECU Configuration Values [1]: Aus der System-/ECU-Konfiguration abgeleitete Parameter (ARXML / Ecuc-Extrakt).
  • BSW Module Configuration Header File [1]: Generierter Header für Link-Time-Deklarationen (<Module>_Lcfg.h / <Module>_Cfg.h).
  • BSW Module Configuration Data Source Code [1]: Generierte Konfigurationsdatenstrukturen (<Module>_Lcfg.c).
  • Basic Software Module Object Code [1..*]: Vorkompilierte BSW-Bibliothek bzw. Objektdateien (.o / .a).
  • BSW Module Configuration Data Object Code [1..*]: Kompilierte Konfigurationsdaten (.o).
  • ECU Executable [1]: Vollständig gelinktes Ziel-Binary (.elf, .hex, .s19).

#### Zustand der Variationspunkte (Annotierte Notes)

  • An Basic Software Module Object Code: „Possible existence of unbound Link time variation points.“
  • An BSW Module Configuration Data Object Code: „No existence of unbound Link time variation points. Unbound Post-build variation points may still exist.“
  • An Link ECU Code during Link Time Configuration: „All Link time variation points are bound.“
  • An ECU Executable: „No existence of unbound Link time variation points. Post-build variation points may still be unbound.“

3. Dynamisches Verhalten & Sequenzablauf

Der Generierungs- und Build-Ablauf gliedert sich in zwei parallele bzw. zeitlich getrennte Vorstufen und eine finale Integrationsstufe:

  1. BSW-Kernkompilierung (Lieferanten-/Modul-Ebene):
  • Compile Unconfigured BSW verarbeitet Core Source Code und Core Header.
  • Resultat ist der Basic Software Module Object Code. Link-Time-Variationspunkte verbleiben als unaufgelöste extern-Symbole (z. B. Referenzen auf Deskriptortabellen, Puffergrößen, Funktionszeiger-Arrays). Pre-Compile-Variationspunkte müssen bereits fest gebunden sein.
  1. Konfigurationsgenerierung & -kompilierung (Integrator-Ebene):
  • Trigger: ECU Configuration Values liegen vor.
  • Generate BSW Configuration Code erzeugt modulespezifische Dateien (<Module>_Lcfg.h und <Module>_Lcfg.c).
  • Compile BSW Configuration Data übersetzt die generierten Quelltexte unter Einbindung des statischen Core Header und des generierten Configuration Header.
  • Resultat ist der BSW Module Configuration Data Object Code, in dem die für diesen BSW-Baustein gültigen Link-Time-Symbole als definierte Symbole vorliegen.
  1. Linker-Integration (ECU-Ebene):
  • Link ECU Code during Link Time Configuration bindet alle BSW-Objektdateien (1..) mit den generierten Konfigurationsobjekten (1..).
  • Alle Link-Time-Variationspunkte werden über die Symboltabelle aufgelöst (bound).
  • Resultat ist das ECU Executable. Post-Build-Variationspunkte (VARIANT-POST-BUILD-SELECTABLE / LOADABLE) bleiben ungebunden und werden erst zur Laufzeit via Initialisierungszeiger (<Module>_Init(&Config)) bzw. Flashen separater Speicherblöcke aufgelöst.

4. Normative Relevanz & Entwickler-Hinweise

  • Liefer- und Geschäftsmodell (IP-Schutz):

Ermöglicht Tier-1/Tier-2-Zulieferern die Auslieferung von BSW-Modulen als vorkompilierte Object-Code-Bibliotheken (.a/.o), ohne C-Quellcode offenlegen zu müssen, während die Parametrierung der ECU durch den Integrator vollumfänglich erhalten bleibt.

  • Restriktionen für Pre-Compile vs. Link-Time:
  • Link-Time-Parameter dürfen keine C-Präprozessormakros (#define) beeinflussen, die den inneren Kontrollfluss oder Datenstrukturen des vorkompilierten Core Source Code verändern würden (z. B. keine bedingte Kompilierung #if (CAN_DEV_ERROR_DETECT == STD_ON) im Core-Code über Link-Time-Werte steuerbar; dies erfordert VARIANT-PRE-COMPILE).
  • Link-Time-Variationspunkte müssen über feste ABI-Schnittstellen abgebildet werden: typischerweise extern const <Module>_ConfigType <Module>_Config; oder Zeiger-Arrays in <Module>_Lcfg.c.
  • Speicher-Mapping (MemMap.h):

Konfigurationsstrukturen in <Module>_Lcfg.c müssen strikt über AUTOSAR-Speichersegmente gekapselt werden (z. B. #include "<Module>_MemMap.h" mit Konstanten-Segmenten wie START_SEC_CONST_PBCFG oder START_SEC_CONFIG_DATA_...), damit der Integrator sie im Linker-Skript (.ld / .bcf) gezielt im Flash/ROM platzieren kann.

  • Symbolkollisionen & Namenskonventionen:

Da mehrere BSW-Module parallel Link-Time-Objekte beisteuern (1..*), müssen die Bezeichner in <Module>_Lcfg.c und <Module>_Lcfg.h strikt dem AUTOSAR-Präfix-Schema (<Msn>_<ParameterName>) folgen, um Mehrfachdefinitionen während des Linkens zu verhindern.
