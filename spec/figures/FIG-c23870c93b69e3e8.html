1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptionelles Architektur- und Transformationsmodell (Metamodell-Mapping / VFB-zu-Topologie-Abbildung im AUTOSAR-Methoden-Workflow).
  • Technischer Zweck: Visualisierung des Virtual Functional Bus (VFB) als Abstraktionsebene. Das Diagramm demonstriert die Entkopplung der Anwendungssoftware (SW-Cs) von der zugrundeliegenden Ausführungsumgebung (ECU-Hardware, BSW-Stack, Bus-Topologie).
  • Funktionale Einordnung:
    • Obere Ebene (VFB-Sicht): Hardware-unabhängiger Entwurf vernetzter Applikationskomponenten über standardisierte Ports und Interfaces.
    • Mittlere Ebene (Systemgenerierungs- und Mapping-Schritt): Transformation der VFB-Sicht mittels System-Tools unter Hinzunahme von ECU Descriptions und System Constraint Descriptions in allokierte ECU Extracts (ECU Description).
    • Untere Ebene (Physische Realisierung): Konkrete Instanziierung auf verteilten Steuergeräten (ECU I, ECU II, ECU n). Die virtuelle Kommunikation wird durch die jeweilige lokale Runtime Environment (RTE) realisiert – entweder als Intra-ECU-Kommunikation (z. B. Task-Aktivierung, Shared Memory, Memory-Copy) oder als Inter-ECU-Kommunikation über BSW-Kommunikationsstacks (CAN, FlexRay, Gateway-Routing via PduR).

2. Komponenten, Entitäten & Schnittstellen

  • Software-Komponenten (VFB-Ebene):
    • AUTOSAR SW-C 1 bis AUTOSAR SW-C n: Kapseln Applikationslogik. Jeder Komponente ist eine formale Komponentenbeschreibung zugeordnet (SoftwareComponentDescription / .arxml).
    • Ports & Interfaces: Dargestellt als geometrische Symbole an den Unterkanten der SW-Cs:
      • Sender-Receiver-Ports (Datenorientiert: Dreiecke für Direction, In/Out).
      • Client-Server-Ports (Dienstorientiert: Symbole für Operation-Call / Provision, Kreis/Halbkreis-Semantik analog UML-Port-Notationen).
      • Konnektoren: AssemblySwConnector verbindet P-Port (Provided) mit R-Port (Required).
  • Toolchain & Artefakte (System-Synthese):
    • Tool Supporting development of SW components: System-Konfigurations- und Mapping-Tool (System Synthesizer / Mapping Generator).
    • System Constraint Description: Definiert nicht-funktionale Anforderungen, Bus-Topologie, Latenz- und Allokationsbeschränkungen (SystemConstraintTemplate).
    • ECU Descriptions: Hardware- und BSW-Ressourcenbeschreibungen der Ziel-Steuergeräte (EcuResourceDescription).
    • ECU Description (Pfeile nach unten): Extrahierte steuergerätespezifische Systembeschreibungen (ECU Extract of System Configuration).
  • Steuergeräte-Ebene (Physische Ausführung):
    • ECU I: Co-Lokation von AUTOSAR SW-C 1 und AUTOSAR SW-C 2 auf demselben Knoten (Realisierung der VFB-Verbindung über lokale RTE-Pfade / Intra-ECU).
    • ECU II: Host für AUTOSAR SW-C 3.
    • ECU n: Host für AUTOSAR SW-C n.
    • RTE (Run-Time Environment): Generierte Schicht pro ECU, die APIs (Rte_Read, Rte_Write, Rte_Call, Rte_Result) bereitstellt.
    • Basic Software (BSW): Standardisierter Software-Stack (OS, COM, PduR, Bus-Interfaces, Transceiver/Treiber).
    • Topologie & Bussysteme: Heterogene Vernetzung über physische Kommunikationskanäle (hier FlexRay und CAN), gekoppelt über ein BSW-Gateway (Routing auf PDU- bzw. Signal-Ebene).

3. Dynamisches Verhalten & Sequenzablauf

  • Entwurfszeit-Sequenz (Workflow):
    1. Komponenten-Definition: Spezifikation von SW-C-Ports, Interfaces, Runnables und Events unabhängig von der Ziel-Hardware.
    2. System-Komposition & Mapping: Zusammenführung im Mapping-Tool; Zuweisung (SwcToEcuMapping) von SW-C 1 + SW-C 2 auf ECU I, SW-C 3 auf ECU II, SW-C n auf ECU n.
    3. Signal-/Frame-Synthese: Mapping virtueller Signale (SystemSignal) auf PDUs, Frame-Triggering und Kommunikationscluster (FlexRayCluster, CanCluster).
    4. RTE- und BSW-Generierung: Erzeugung der ECU-spezifischen RTE-Header und C-Files basierend auf dem ECU Extract.
  • Laufzeit-Kommunikationspfade (Laufzeit-Dynamik):
    • Intra-ECU (ECU I): Aufruf von Rte_Write_* durch SW-C 1 bedient SW-C 2 direkt via OS-Inter-Task-Kommunikation, Puffer oder atomaren Pointer-Austausch; kein BSW-COM-Durchlauf erforderlich.
    • Inter-ECU homogen (ECU I → ECU II über FlexRay): Aufruf an RTE führt zu Com_SendSignal → PduR → FrIf → FrDrv. Empfang auf ECU II synchronisiert über Fr-Interrupt/Task → Rte_COMCbk → RTE-Puffer/Runnable-Aktivierung.
    • Inter-ECU heterogen/geroutet (ECU I/II → ECU n über Gateway): FlexRay-Frame erreicht Gateway-Knoten → PDU-Router (PduR_FrIfRxIndication) → Gateway-Routing auf CAN-Interface (CanIf_Transmit) → CAN-Bus → Empfang auf ECU n.

4. Normative Relevanz & Entwickler-Hinweise

  • Applikations-Entwickler (SW-C-Ebene):
    • Strikte VFB-Konformität: Implementierung erfolgt ausschließlich gegen die abstrakten RTE-APIs (Rte_Type.h, Rte_<swc>.h). Es darf kein direkter Zugriff auf Hardware, OS-Tasks oder BSW-Module (CAN/FlexRay-Treiber) erfolgen.
    • Relokationsfähigkeit: Eine SW-C muss ohne Quellcode-Änderung von ECU I auf ECU II oder ECU n verschoben werden können; lediglich das RTE-Generat ändert sich von In-Memory/Task-Call auf COM-Stack-Proxying.
  • BSW- und Stack-Entwickler:
    • PduR-Gatewaying: Bei Busübergängen (wie FlexRay/CAN im Diagramm) muss die Signal- bzw. PDU-Gateway-Matrix exakt mit den Timing- und Latenzanforderungen des VFB-Designs übereinstimmen.
    • Signal Packing & Byte Ordering: Das Mapping von VFB-Datenelementen (ApplicationDataType / ImplementationDataType) in PDUs erfordert strikte Berücksichtigung von Big-/Little-Endian-Konvertierung (Com-Signal-Payloads).
  • RTE-Konfiguration (Generierungsphase):
    • Die RTE abstrahiert Kommunikationsgrenzen vollständig. Konfigurationsparameter bestimmen, ob Ports per Direct-Function-Call, Inter-Runnable-Variable (IRV), OS-Event/Spinlock oder COM-Signal realisiert werden.
    • Entwickler müssen sicherstellen, dass Übertragungseigenschaften (Data-Semantik vs. Event-Semantik, Queued vs. Unqueued) bei Inter-ECU-Mappings durch den zugrundeliegenden Bus (z. B. deterministische FlexRay Static Slots vs. ereignisgesteuerte CAN-Arbitrierung) eingehalten werden.

Figure 2.2: Concept of the virtual functional bus In AUTOSAR, an application is modeled as a composition of interconnected components. This is illustrated in the top half of Figure 2.2 (labeled “VFB view”). The “virtual functional bus” is the communication mechanism that allows these components to interact. The components are mapped on specific system resources (ECUs). Thereby, the virtual connections between the components are mapped onto local connections (within a single ECU) or on network-technology specific communication mechanisms (such as CAN or FlexRay frames). Finally, the individual ECUs in such a system can be configured. The concrete interface between the individual components and between the components and the Basic Software (BSW) [5][4] is called the Run- Time Environment (RTE) [7] A component encapsulates complete or partial automotive functionality.
