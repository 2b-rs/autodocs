1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Architektur-, Speicher- und Partitionierungsmodell (BSW Multi-Core Distribution Pattern / Memory-Mapping-Diagramm).
  • Funktionale Einordnung: Exemplarische Darstellung eines Multi-Core Type II Drivers gemäß AUTOSAR_CP_EXP_BSWDistributionGuide (Classic Platform, R21-11 / R25-11).
  • Technischer Zweck: Ermöglicht die parallele, echtzeitfähige Ausführung eines identischen Treiber-Programmcodes (Driver Code) auf mehreren CPU-Cores ohne Cross-Core-Blockaden, Spinlocks oder Inter-Core-Kommunikation (IOC). Die Trennung der Zustände erfolgt über das Architekturmuster des Clone Space (Core-Local Memory Aliasing).

2. Komponenten, Entitäten & Schnittstellen

Speicherbereiche & Scopes
  • Global Scope:
    • Enthält den reentranten, unteilbaren Programmcode (Driver Code) im global lesbaren Speicher (Flash ROM / Shared RAM), der für alle Cores gleichermaßen ausführbar ist.
  • Clone Space:
    • Virtueller bzw. hardwaregestützter Spiegel-/Alias-Adressraum.
    • Definiert eine identische logische Basisadresse für symbolische Treiberdaten (XXX_ActiveData), die je nach ausführendem Core transparent auf den physikalischen Speicher des jeweiligen Cores umgelenkt wird.
  • Local Scope (Core 1 & Core 2):
    • Physikalisch isolierte, Core-lokale RAM-Bereiche (z. B. DSPR/Data Scratchpad RAM oder Core-spezifische Tightly-Coupled Memories).
    • Enthalten die realen Speicherinstanzen XXX_CORE1_Data (Core 1) und XXX_CORE2_Data (Core 2).
Entitäten & Datenstrukturen
  • Driver Code (Cyan): Statische Funktionslogik des BSW-Moduls. Vollständig reentrant implementiert.
  • XXX_ActiveData (Orange/Clone Space): Core-unabhängige Zugriffsrepräsentanz/Symbol für den Treiberzustand.
  • XXX_CORE1_Data / XXX_CORE2_Data (Orange/Local Scope): Core-spezifische Instanzvariablen (Kanalzustände, Pufferdeskriptoren, Hardware-Shadow-Register).
  • Kardinalität: 1 (Driver Code) : 1 (XXX_ActiveData logisch) : N (XXX_COREn_Data physikalisch, hier N=2).
Schnittstellen & Funktionskategorien
  • Lifecycle / Initialisierung (Grauer Port):
    • XXX_Init(&core_data): Core-spezifische Initialisierung; übergibt die instanzspezifische Konfiguration/Datenreferenz für den jeweiligen Core.
    • XXX_Deinit(): Core-lokale Freigabe/Deinitialisierung der Treiberressourcen.
  • Ablauforganisation / Scheduling (Cyanfarbener Port):
    • XXX_Trigger(): Zyklische Task-Funktion (XXX_MainFunction) oder ereignisgesteuerte Abarbeitung/ISR im Kontext des ausführenden Cores.
  • Datenzugriff & Funktions-APIs (Gelber Port):
    • XXX_Get(): Reentrantes, synchrones Lesen lokaler Zustandsdaten über XXX_ActiveData.
    • XXX_Set(): Reentrantes, synchrones Schreiben lokaler Zustandsdaten über XXX_ActiveData.

3. Dynamisches Verhalten & Sequenzablauf

Initialisierungsphase
  1. Per-Core Startup: BswM bzw. EcuM des jeweiligen Cores ruft im lokalen Kontext XXX_Init(&core_data) auf.
  2. Klon-Bindung: Die Adressumsetzung für XXX_ActiveData wird aktiv (über MMU/MPU-Konfiguration oder native Hardware-Kloning-Mechanismen der MCU).
Laufzeitbetrieb (Nebenläufigkeit & Synchronizität)
  1. Parallele Code-Ausführung:
    • Core 1 und Core 2 führen simultan denselben Instruktionssatz im Driver Code aus (z. B. XXX_Trigger() oder XXX_Set()).
  2. Implizites Routing im Clone Space:
    • Lese- und Schreibzugriffe des Programmcodes auf die symbolische Adresse XXX_ActiveData werden durch das Core-Memory-Mapping hardwareseitig ohne Software-Overhead aufgelöst:
      • CPU Core 1 adressiert XXX_ActiveData → physischer Zugriff auf XXX_CORE1_Data.
      • CPU Core 2 adressiert XXX_ActiveData → physischer Zugriff auf XXX_CORE2_Data.
  3. Lock-Free Concurrency:
    • Es existieren keine Cross-Core-Datenabhängigkeiten.
    • Keine Notwendigkeit globaler Multicore-Spinlocks (GetSpinlock() / ReleaseSpinlock()); lokale Reentranz (Task vs. ISR desselben Cores) wird rein core-lokal abgefangen (SuspendAllInterrupts()).

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Klassifikation & Verteilung:
    • Treiber muss im BSW-Modul-Deskriptor (BswModuleDescription) als reentrant deklariert sein.
    • Zuweisung zu mehreren EcucPartition-Instanzen parallel möglich, ohne dass Master/Satellite-Proxies (Type I) generiert werden müssen.
  • Linker- & MemMap-Konfiguration:
    • Das MemMap.h-Konzept muss Klon-Sektionen unterstützen:
      • XXX_ActiveData erfordert die Platzierung in einer dedizierten Klon-Sektion (z. B. XXX_START_SEC_VAR_CLONE).
      • Linker-Skripte müssen den virtuellen Adressbereich des Clone Space definieren und auf die physikalischen Adressen der Core-lokalen Speicher (z. B. DSPR0, DSPR1) spiegeln.
  • Hardware-Voraussetzungen:
    • Erfordert Mikrocontroller-Architekturen mit nativer Clone-Space- oder Segment-Mirror-Unterstützung (z. B. Infineon AURIX Core-Local DSPR Aliasing, Arm Cortex-R Memory Aliasing) oder entsprechende MPU/MMU-Mapping-Fähigkeiten.
    • Fehlt die Hardwareunterstützung, muss dieser Mechanismus über Core-ID-indizierte Pointer-Tabellen softwareseitig emuliert werden (Performanceverlust durch Indirektion).
  • Restriktionen & Entwurfsgrenzen:
    • Strikte Datenisolation: Über XXX_ActiveData ist kein Core-übergreifender Datenaustausch möglich. Werden Daten zwischen Cores benötigt, muss zusätzlich ein IPC-Kanal (IOC / Shared Memory mit Spinlock) implementiert werden.
    • Hardware-Peripherie-Disjunktheit: Die physischen Hardware-Ressourcen (Register, Kanäle, Interrupt-Vektoren) müssen den Cores disjunkt zuordenbar sein. Ein Type-II-Treiber eignet sich primär für Peripherien mit unabhängigen Hardware-Unterkanälen (z. B. dedizierte PWM-Kanäle, CAN-Controller-Instanzen oder ADC-Wandlergruppen je Core).
