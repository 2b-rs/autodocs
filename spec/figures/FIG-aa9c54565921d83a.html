  • Technischer Zweck & funktionale Einordnung:

2. Komponenten, Entitäten & Schnittstellen

BSW-Laufzeitkomponenten (Linke Spalte)
  • RTE: Anwendungsnahe Signalkommunikation (Bereitstellung des Sender-Ports via Rte_Write_* / Rte_Send_*).
  • COM: Signal-Packing, I-PDU-Generierung und Sendemodi (Com_SendSignal()).
  • PduR: Protokoll-agnostisches Routing der I-PDU an das Ziel-Interface-Modul (PduR_ComTransmit() → SoAd_IfTransmit()).
  • SoAd: PDU-zu-Socket-Multiplexing. Fächert eine einzelne logische Sende-PDU auf n aktive Unicast-Sockets auf.
  • Socket A1, Socket A2, Socket A3: Konkrete TCP/UDP-Socket-Verbindungsinstanzen (SoCon) des darunterliegenden TcpIp-Stacks.
System Template Metamodell-Entitäten (Rechte Spalte)
  • ISignalTriggering: Steuert das Senden eines logischen Signals auf dem Kanal; assoziiert mit:
    • ISignalPort (communicationDirection = out): Sender-Port der Signalebene.
    • EthernetPhysicalChannel (VLAN X): Zugeordnetes logisches/physisches Netzwerksegment.
  • ISignal: Definition des atomaren Nutzdatums.
  • ISignalToIPduMapping: Beschreibt Start-Bit, Bit-Länge und Endianness des ISignal innerhalb der ISignalIPdu.
  • ISignalIPdu: Payload-Container (PDU-Ebene).
  • PduTriggering PSI: Kanal-Triggering der PDU für die Provided Service Instance (PSI) auf dem EthernetPhysicalChannel; assoziiert mit IPduPort (communicationDirection = out).
  • SoConIPduIdentifier: SoAd-Routingdeskriptor für die I-PDU:
    • Konfiguriert mit headerId = 0x00198001 (SOME/IP Message-ID: Service-ID 0x0019, Event-ID 0x8001 durch gesetztes MSB im 16-Bit Method/Event-Feld).
    • Referenziert PduTriggering PSI.
  • PduActivationRoutingGroup: Steuerungsgruppe im SoAd zur dynamischen Freigabe/Sperrung der PDU-Weiterleitung.
  • EventHandler: Serverseitige Repräsentanz eines SOME/IP-Events; aggregiert die PduActivationRoutingGroup.
  • ProvidedServiceInstance: Bietet den SOME/IP-Dienst auf der Server-ECU an; aggregiert den EventHandler und referenziert den ApplicationEndpoint.
  • SocketAddress: Repräsentiert die IP-Konfiguration auf dem Kanal; aggregiert den ApplicationEndpoint.
  • ApplicationEndpoint: Spezifiziert IP-Port, Transportprotokoll und Verbindungsressourcen:
    • Attribut: maxNumberOfConnections = 3 (limitiert den dynamischen SoCon-Pool exakt auf die 3 dargestellten Sockets A1–A3).

3. Dynamisches Verhalten & Sequenzablauf

  1. Service Discovery & Subscription (Vorbereitung / Asynchron):
    • Die Server-ECU publiziert den Service via Sd_ServerService_OfferService().
    • Bis zu 3 Clients abonnieren die Eventgroup via SubscribeEventgroup.
    • Das lokale BSW-Modul SD validiert die Subscriptions, reserviert für jeden Client einen Socket (Socket A1 bis Socket A3) aus dem Pool des ApplicationEndpoint und öffnet/verbindet diese über TcpIp.
    • SD aktiviert die zugeordnete PduActivationRoutingGroup via SoAd_EnableRoutingGroup().
  2. Datenpfad-Triggering (Synchron / Run-to-Completion bis SoAd):
    • Die Applikation triggert das Event über die RTE.
    • COM serialisiert das ISignal via ISignalToIPduMapping in die ISignalIPdu.
    • COM ruft PduR_ComTransmit() auf; PduR delegiert via SoAd_IfTransmit() an SoAd.
  3. SoAd Fan-Out (Verteilungspfad):
    • SoAd prüft den Status der PduActivationRoutingGroup: Ist die Gruppe aktiv, iteriert SoAd über alle zugeordneten, aktiven Socket-Verbindungen (Socket A1, A2, A3).
    • SoAd repliziert die PDU und setzt jeweils TcpIp_UdpTransmit() bzw. TcpIp_TcpTransmit() für jeden aktiven Socket ab.
  4. Abbruchbedingungen & Sonderfälle:
    • Keine Abonnenten: Wurde kein Client abonniert, bleibt die PduActivationRoutingGroup disabled → SoAd droppt die PDU lautlos (kein Network-Traffic, Vermeidung unnötiger Buslast).
    • Kapazitätsgrenze (maxNumberOfConnections = 3): Versucht ein vierter Client das Event zu abonnieren, weist das SD-Modul die Subscription ab (SubscribeEventgroupNack oder Error-Code SD_E_NO_FREE_SOCKET_CONNECTION), da der Verbindungspool des ApplicationEndpoint erschöpft ist.

4. Normative Relevanz & Entwickler-Hinweise

  • Transparenz für Applikation und COM-Stack:
    • Weder RTE, COM noch PduR besitzen Kenntnis über die Anzahl der Event-Empfänger. Die Fan-Out-Logik ist vollständig im SoAd und SD gekapselt; der PduR-API-Vertrag bleibt strikt 1:1 (SoAd_IfTransmit).
  • Konfigurationsabgleich (System Description → BSW-Module):
    • ApplicationEndpoint.maxNumberOfConnections = 3 muss direkt in den SoAd-Parameter SoAdSocketConnectionGroup.SoAdSocketConnectionBundle (Anzahl Kind-SoAdSocketConnection = 3) übersetzt werden.
    • Die PduActivationRoutingGroup erfordert eine zwingende Verknüpfung mit SdRoutingGroupRef im SD-Modul-Konfigurator (SdEventHandler).
  • SOME/IP-HeaderId-Konvention:
    • headerId = 0x00198001 bestimmt das SOME/IP Message ID Mapping. Bei gesetztem SoAdPduHeaderOption = TRUE generiert/validiert der SoAd den 32-Bit-PDU-Header ([Service-ID: 16 Bit | 1-Bit Event-Flag + 15-Bit Event-ID]).
  • Ressourcen & Laufzeitverhalten im Embedded-System:
    • Memory & Bandbreite: Unicast-Fan-Out skaliert bezüglich RAM-Pufferung und Ethernet-Transceiver-Last linear mit O(n) (n ≤ 3). Bei zeitkritischen zyklischen Events oder großen Payloads ist zur Vermeidung von TX-Buffer-Starvation im TcpIp-Stack die Migration auf Ethernet-Multicast zu prüfen.
    • Buffer-Management: Für SoAd_IfTransmit() muss sichergestellt sein, dass PDU-Puffer im SoAd nicht vorzeitig freigegeben oder überschrieben werden, bevor alle replizierten Übertragungen via TX-Confirmation des TcpIp-Treibers bestätigt wurden.
