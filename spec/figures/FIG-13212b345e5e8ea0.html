1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: AUTOSAR VFB-Komponentendiagramm (UML 2.0 Composite Structure) mit überlagerter System- und Signal-Mapping-Information (System Template, Release R3.0.7).
  • Technischer Zweck: Visualisierung der VFB-Relokationstransparenz (Virtual Functional Bus) und der Entkopplung von Software-Architektur und Hardware-Topologie:
    • Demonstration hierarchischer Schachtelung (CompositionSwComponentType) versus physischer Allokation (SwcToEcuMapping).
    • Abbildung logischer Port-Konnektoren (AssemblySwConnector, DelegationSwConnector) auf netzwerkbasierte Signal- und Frame-Pfade (SenderReceiverToSignalMapping, Frame-Packing).

2. Komponenten, Entitäten & Schnittstellen

Software-Komponenten (Instanzen / Prototypen)
  • Root-Composition: SWCompAplusB (CompositionSwComponentType).
  • Sub-Compositionen: SWCompA und SWCompB (als ComponentPrototype in SWCompAplusB aggregiert).
  • Atomic Software Components (AtomicSwComponentType):
    • Auf ECU A gemappt (orange): SW-C A1, SW-C A2, SW-C B1.
    • Auf ECU B gemappt (beige): SW-C A3, SW-C B2.
    • Architektur-Merkmal: Die Kompositionen schneiden ECU-Grenzen. SWCompA verteilt sich auf ECU A (A1, A2) und ECU B (A3); SWCompB verteilt sich auf ECU A (B1) und ECU B (B2).
Ports & Schnittstellen
  • Schnittstellentyp: Sender-Receiver-Kommunikation (SenderReceiverInterface).
  • Ports:
    • P (ProvidedPortPrototype): Sender-Port (A1, A3, B1 sowie Außengrenze SWCompA).
    • R (RequiredPortPrototype): Receiver-Port (A2, A3, B1, B2 sowie Außengrenze SWCompB).
Konnektoren & Topologie-Beziehungen
  • Intra-Composition Connectors (AssemblySwConnector):
    • A1(P) -> A2(R): Intra-ECU (ECU A → ECU A).
    • A1(P) -> A3(R): 1:n-Verzweigung, Inter-ECU (ECU A → ECU B).
    • B1(P) -> B2(R): Inter-ECU (ECU A → ECU B).
  • Inter-Composition Connectors (Delegation & Assembly):
    • A3(P) delegiert über DelegationSwConnector an den Outer-P-Port von SWCompA.
    • SWCompA(P) -> SWCompB(R) über hierarchischen AssemblySwConnector.
    • Outer-R-Port von SWCompB delegiert über DelegationSwConnector an B1(R).
    • Effektiv: Inter-ECU-Kommunikation (ECU B → ECU A).
Signal- & Frame-Mapping (DataMapping)
  • A1(P) → gemappt auf FrameX, SignalX1 (TX auf ECU A, RX auf ECU B für A3).
  • A3(P) → gemappt auf FrameY, SignalY1 (TX auf ECU B, RX auf ECU A für B1).
  • B1(P) → gemappt auf FrameX, SignalX2 (TX auf ECU A, RX auf ECU B für B2).
  • Frame-Packing-Eigenschaft: FrameX fasst Signale aus zwei funktional getrennten SW-Cs (A1 aus SWCompA und B1 aus SWCompB) auf demselben Steuergerät (ECU A) in einer gemeinsamen PDU zusammen.

3. Dynamisches Verhalten & Sequenzablauf

[ECU A]                                                     [ECU B]
 SW-C A1 --(Rte_Write)---+-> [RTE / Memory] --------> SW-C A2 (lokal)
                         |
                         +-> [COM / PduR / CanIf]
                                  |
                           (Bus: FrameX / SignalX1)
                                  |
                                  v
                             [CanIf / PduR / COM] ---> SW-C A3 (remote)
                                                           |
                                                      (Rte_Write)
                                                           |
                             [CanIf / PduR / COM] <--------+
                                  |
                           (Bus: FrameY / SignalY1)
                                  |
                                  v
 SW-C B1 <------------------- [COM / PduR / CanIf]
    |
(Rte_Write)
    |
    +-> [COM / PduR / CanIf]
             |
      (Bus: FrameX / SignalX2)
             |
             v
        [CanIf / PduR / COM] ------------------------> SW-C B2 (remote)
  1. Multicast-Verhalten an A1(P):
    • SW-C A1 setzt atomaren Aufruf Rte_Write_<p>_<o>().
    • Pfad 1 (Synchron/Lokal): Direkte Übergabe im RTE-Speicher an SW-C A2 (gleiche ECU). Je nach Task-Allokation geschieht dies per Shared Buffer (Inter-Task-Locking / OS-Ressource) oder Direktkopie.
    • Pfad 2 (Asynchron/Netzwerk): RTE leitet das Datum an die AUTOSAR COM weiter (Com_SendSignal(SignalX1)).
  2. PDU-Assemblierung (FrameX auf ECU A):
    • COM puffert SignalX1 (aus A1) und SignalX2 (aus B1).
    • Triggerung von FrameX erfolgt nach COM-Konfiguration (PENDING vs. TRIGGERED, zyklisch/gemischt via ComTxMode).
    • Routing via PduR an Interface/Treiber (z. B. CanIf/CanDrv).
  3. Kaskadierte Rückkopplung:
    • ECU B empfängt FrameX, entpackt SignalX1 im COM-Stack und benachrichtigt via RTE die SW-C A3 (Polling via Rte_Read oder eventgetriggert via DataReceivedEvent).
    • SW-C A3 verarbeitet die Daten und emittiert Daten an ihrem P-Port → Übergabe an COM auf ECU B → Versand über FrameY (SignalY1).
    • ECU A empfängt FrameY, COM übergibt SignalY1 an SW-C B1.
    • SW-C B1 schreibt Datum → COM packt SignalX2 erneut in FrameX zur Übertragung an SW-C B2 auf ECU B.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Zuordnung: AUTOSAR System Template, Spezifikation des Software-to-ECU- und Sender-Receiver-zu-Signal-Mappings.
  • Architektur-Vorgabe: Kompositionen (CompositionSwComponentType) sind rein logische Strukturierungselemente und dürfen sich über mehrere Steuergeräte erstrecken.
  • Kommunikations-Relevanz: Verbindungen zwischen Komponenten auf unterschiedlichen Steuergeräten erfordern eine Abbildung auf System-Signale und Netzwerk-Frames (ISignal, CanFrame / FlexrayFrame), während lokale Verbindungen über die RTE ohne Buskommunikation aufgelöst werden.
