1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-2.0-Metamodell-Klassendiagramm (AUTOSAR System Template, M2-Ebene).
  • Funktionaler Kontext: Modellierung der globalen Zeitsynchronisation (Global Time Synchronization, GTS) auf Ebene der System Description (AUTOSAR_TPS_SystemTemplate, Release R4.2.2).
  • Zweck: Festlegung der Systemtopologie für zeitsynchrone Netzwerke über verschiedene Kommunikationscluster (CAN, FlexRay, Ethernet/gPTP). Das Modell definiert Zeitdomänen (GlobalTimeDomain), die Rollenverteilung (Master, Slave, Gateway) sowie deren physische Bindung an Steuergeräteinstanzen (EcuInstance) und Netzwerk-Konnektoren (CommunicationConnector) gemäß den System-Anforderungen TPS_SYST_05007 und TPS_SYST_05008.

2. Komponenten, Entitäten & Schnittstellen

#### Metaklassen und Attribute

  • GlobalTimeDomain (erbt von FibexElement):

Repräsentiert eine logisch zusammenhängende globale Zeitbasis.

  • domainId: PositiveInteger: Eindeutiger Identifikator der Zeitdomäne (entspricht z. B. der Time Domain ID in IEEE 802.1AS / CAN-TSyn / FrTSyn).
  • followUpTimeoutValue: TimeValue [0..1]: Maximal zulässige Wartezeit auf eine zugehörige Follow-Up-PDU bei zweistufiger Synchronisation (Two-Step Sync).
  • syncLossThreshold: TimeValue [0..1]: Schwellwert für Phasendivergenz/Jitter, ab dem ein Synchronisationsverlust detektiert wird.
  • syncLossTimeout: TimeValue: Timeout-Intervall, nach dessen Ablauf ohne gültige Synchronisationsnachricht der Zustand „Sync Loss“ deklariert wird.
  • GlobalTimeMaster (erbt von Identifiable):

Definiert die zeitgebende Entität innerhalb der Domäne.

  • isSystemWideGlobalTimeMaster: Boolean: Kennzeichnet den Root-Master (Grandmaster Clock) des Gesamtfahrzeugs.
  • syncPeriod: TimeValue: Zykluszeit für die periodische Aussendung von Synchronisationsnachrichten (Sync-PDUs).
  • GlobalTimeSlave (erbt von Identifiable):

Zeitnehmende Entität, synchronisiert ihre lokale Uhr auf die Master-Zeitbasis.

  • GlobalTimeGateway (erbt von Identifiable):

Brückenknoten zur Weiterleitung und Synchronisation von Zeitbasen über Bus- bzw. Clustergrenzen hinweg.

  • CommunicationCluster (erbt von FibexElement, Stereotyp «atpVariation»):

Repräsentiert den physikalischen Bus (CAN, FlexRay, Ethernet). Unterstützt AUTOSAR-Variantenschnittstellen («atpVariation»).

  • Attribute: baudrate [0..1], protocolName [0..1], protocolVersion [0..1].
  • CommunicationConnector (erbt von Identifiable):

Netzwerkinterface eines Steuergeräts an einen Cluster.

  • Attribut: pncGatewayType: PncGatewayTypeEnum [0..1].
  • EcuInstance (erbt von FibexElement):

Physikalisches Steuergerät, beinhaltet allgemeine Kommunikations-, Routing- und Powermanagement-Parameter (u. a. comConfigurationGwTimeBase, sleepModeSupported, wakeUpOverBusSupported).

  • GeneralPurposePdu (erbt von Pdu):

PDU-Container, der spezifisch für zeitbezogene Protokollnachrichten verwendet wird.

#### Beziehungen und Kardinalitäten

  • Kompositionen innerhalb GlobalTimeDomain:
  • +master [0..1]: Eine Domäne hat maximal einen aktiven Master-Endpunkt.
  • +slave [0..*]: Beliebig viele Slaves pro Domäne.
  • +gateway [0..*]: Optionale Zeitgateways innerhalb der Domäne.
  • Strukturierte Topologiebeziehungen:
  • +subDomain [0..*]: Hierarchische Schachtelung von Sub-Zeitdomänen (rekursive Komposition auf GlobalTimeDomain).
  • +offsetTimeDomain [0..1]: Verknüpfung zu einer Zeitdomäne mit festem/variablem Offset zur Hauptzeitbasis.
  • Netzwerkanbindung:
  • GlobalTimeDomain $\rightarrow$ CommunicationCluster (+communicationCluster [0..*]): Zuordnung der Domäne zu einem oder mehreren physikalischen Netzwerken.
  • GlobalTimeDomain $\rightarrow$ GeneralPurposePdu (+globalTimePdu [0..1]): Referenz auf die primäre Zeit-PDU.
  • GlobalTimeMaster / GlobalTimeSlave $\rightarrow$ CommunicationConnector (+communicationConnector [1]): Eindeutige Bindung des Master-/Slave-Endpunkts an ein physisches Businterface.
  • Gateway-Struktur:
  • GlobalTimeGateway $\rightarrow$ GlobalTimeSlave (+slave [1]): Genau ein Ingress-Endpunkt (Zeitaufnahme).
  • GlobalTimeGateway $\rightarrow$ GlobalTimeMaster (+master [1]): Genau ein Egress-Endpunkt (Zeitausgabe).
  • GlobalTimeGateway $\rightarrow$ EcuInstance (+host [1]): Feste Zuordnung des Gateways zu einem physischen Host-Steuergerät.
  • EcuInstance $\rightarrow$ CommunicationConnector (+connector [*]): Komposition der Netzwerkschnittstellen des Host-ECUs.

3. Dynamisches Verhalten & Sequenzablauf

Aus den Modellparametern leitet sich folgende BSW-Laufzeitdynamik ab:

```

[GlobalTimeMaster] [Physikalischer Bus] [GlobalTimeSlave]

| | |

|--- Sync-PDU (T0) ------------>| |

| (Periode: syncPeriod) |--- Sync-PDU (T0_rx) ---------->|

| | | (Start followUpTimeoutValue)

|--- FollowUp-PDU (T0_precise)->| |

| |--- FollowUp-PDU -------------->|

| | | (Offset- & Driftberechnung)

| | |

| | x [Sync-PDU fehlt] |

| | |-- Timer: syncLossTimeout läuft ab

| | | -> Status: SYNC_LOSS

```

  1. Trigger & Zyklus: GlobalTimeMaster sendet basierend auf syncPeriod periodisch eine Synchronisations-PDU via +globalTimePdu.
  2. Two-Step-Mechanismus: Bei Controllern mit verzögertem Hardware-Timestamping (z. B. CAN/Ethernet ohne On-the-Fly-Modifikation) triggert die Sync-PDU die Erfassung des präzisen Sendezeitpunkts $T_0$. Der Master übermittelt diesen Wert anschließend in einer Follow-Up-PDU.
  3. Slave-Überwachung & Abbruchkriterien:
  • Trifft die Follow-Up-PDU nicht innerhalb von followUpTimeoutValue am Slave ein, wird der Synchronisationszyklus verworfen.
  • Bleiben Sync-PDUs länger als syncLossTimeout aus oder überschreitet die lokale Zeitabweichung syncLossThreshold, meldet der Slave intern Synchronisationsverlust (BSW-Zustandswechsel via StbM / Dem-Event).
  1. Gateway-Propagation: Das GlobalTimeGateway empfängt über seinen GlobalTimeSlave die Masterzeit des Quell-Clusters, berechnet die Gateway-interne Latenz (Verarbeitungszeit auf der EcuInstance) und fungiert über seinen GlobalTimeMaster als Zeiterzeuger für den Ziel-Cluster.

4. Normative Relevanz & Entwickler-Hinweise

  • BSW-Mapping (Classic Platform):
  • GlobalTimeDomain korrespondiert 1:1 mit einer StbMTimeBase im Synchronized Time-Base Manager (StbM).
  • GlobalTimeMaster und GlobalTimeSlave konfigurieren die Busschnittstellenmodule: CanTSyn, FrTSyn oder EthTSyn (z. B. Mapping von domainId auf CanTSynGlobalTimeDomainId).
  • Das Flag isSystemWideGlobalTimeMaster = true darf im Gesamtsystem systemweit nur an exakt einer Instanz gesetzt sein (TPS_SYST_05007); Verstöße führen zu Synchronisationskonflikten und Multimaster-Kollisionen.
  • Gateway-Realisierung:
  • Das Vorhandensein eines GlobalTimeGateway erfordert im StbM die Aktivierung des Time-Gateway-Routings (StbMTimeBaseGateway). Entwickler müssen sicherstellen, dass die Latenzkompensation (Ingress-Timestamp bis Egress-Timestamp) im BSW-Stack unterstützt und kalibriert ist.
  • PDU- und Interface-Konfiguration:
  • Die referenzierte GeneralPurposePdu (+globalTimePdu) muss im PDU-Router (PduR) für die direkte Weiterleitung an das entsprechende *TSyn-Modul ohne Umweg über den Com-Stack konfiguriert werden.
  • Restriktionen & Validierung:
  • syncLossTimeout muss strikt größer dimensioniert sein als syncPeriod, um transienten Jitter oder Busüberlastungen ohne sofortigen Sync-Verlust abzufangen (typisch: Faktor $2{,}5$ bis $3 \times \text{syncPeriod}$).
  • followUpTimeoutValue muss kleiner als syncPeriod sein, um PDU-Überholungen und Verwechslungen von Messzyklen im Treiber auszuschließen.
