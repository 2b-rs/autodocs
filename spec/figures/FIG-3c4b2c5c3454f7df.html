2. Komponenten, Entitäten & Schnittstellen

Entitäten / Artefakte (XML-Modelle & Dateiformate)
  • ECU Configuration Description (.XML): Zentrales Datenmodell (EcucDescription), das alle Modulkonfigurationen (ModuleConfiguration) des Ziel-ECU aggregiert.
  • Eingangs-Beschreibungsdateien:
    • ECU Extract of System Configuration (:System, .XML): Vom OEM bereitgestellter systemspezifischer Extrakt mit Topologie, Kommunikationsmatrix (Frames/PDUs) und Software-Component-Mapping für das spezifische ECU.
    • BSW-Module Description (:BswModuleDescription, .XML): Formale Schnittstellen- und Verhaltensbeschreibung eines BSW-Moduls.
    • Vendor Specific Module Definition (:ModuleDef, .XML): Modul-Metamodell/Schema des Herstellers mit Definition aller konfigurierbaren Parameter, Container und Bindezeiten.
    • Vendor Specific Preconfigured Configuration Description (:ModuleConfiguration, .XML): Feste, herstellerspezifisch nicht änderbare Parameterbelegungen.
    • Vendor Specific Recommended Configuration Description (:ModuleConfiguration, .XML): Empfohlene Default-Werte für Parameter.
  • Zwischenartefakte der Konfigurationsstufen (:ModuleConfiguration, .XML):
    • PC No Affect: Pre-Compile-Parameter ohne Kopplung an spätere Bindezeiten.
    • PC Affect LT: Pre-Compile-Parameter, deren Belegung Link-Time-Parameter einschränkt oder steuert (z. B. Array-Dimensionierung).
    • PC Affect PB: Pre-Compile-Parameter mit Auswirkung auf Post-Build-Strukturen.
    • LT No Affect: Reine Link-Time-Parameter.
    • LT Affects PB: Link-Time-Parameter mit Auswirkung auf Post-Build-Konfigurationen.
  • Generierte Zielartefakte:
    • .c (Module Configuration Code) & .h (Module Configuration Header): Quellcodedateien für Pre-Compile-Konfiguration (<Module>_Cfg.h, <Module>_Cfg.c).
    • .obj (Module Configuration Object Code): Kompiliertes Relocatable-Objekt für Link-Time-Konfiguration (<Module>_Lcfg.obj).
    • .hex (Module Configuration Loadable to ECU Memory): Absolut adressierte Binärdatei/Flash-Image für Post-Build-Konfigurationsstrukturen (<Module>_PBcfg).
Aktivitäten & Akteure (Rollenverteilung)
  • Tier 2 (BSW-Lieferant):
    • Edit PC ECU Configuration: Konfiguration der Pre-Compile-Parameter.
    • Generate Module Configuration: Codegenerator erzeugt Quellcode (.c, .h).
  • Tier 2 / Tier 1 (Modul-Lieferant / System-Integrator):
    • Edit LT ECU Configuration: Konfiguration der Link-Time-Parameter.
    • Generate Module Configuration: Generator/Compiler erzeugt Objektdateien (.obj).
  • OEM (Fahrzeughersteller):
    • Liefert den ECU Extract of System Configuration.
    • Edit PB ECU Configuration: Konfiguration der Post-Build-Parameter (Varianten, Kalibrierung).
    • Generate Module Configuration: Post-Build-Generator erzeugt ladbare Flash-Daten (.hex).

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Synthese (Base ECU Configuration):
    • Aktivität Generate Base ECU Configuration Description führt den ECU Extract of System Configuration mit den BSW-Moduldefinitionen (ModuleDef, BswModuleDescription) sowie Default-Parametern (Preconfigured/Recommended) zusammen.
    • Ergebnis ist die initiale ECU Configuration Description.
  2. Kaskadierte Konfigurationsphasen (Abhängigkeitskette):
    • Stufe 1 (Pre-Compile): Tier 2 editiert Pre-Compile-Parameter (Edit PC ECU Configuration). Parameteränderungen propagieren kaskadierend über PC Affect LT und PC Affect PB in nachgelagerte Konfigurationsräume.
    • Stufe 2 (Link-Time): Tier 1/Tier 2 verfeinert Link-Time-Parameter (Edit LT ECU Configuration), beeinflusst über LT Affects PB potenzielle Post-Build-Parameter.
    • Stufe 3 (Post-Build): OEM führt finale Anpassungen für Post-Build-Werte (Edit PB ECU Configuration) auf Basis der vorangegangenen Randbedingungen durch.
  3. Generierungspfad nach Bindezeitpunkten (Entkoppelte Codegenerierung):
    • Pre-Compile: Tier 2 generiert Modul-Header (.h) und Quellcode (.c) zur Compile-Zeit des Stacks.
    • Link-Time: Tier 1/Tier 2 generiert und kompiliert modulspezifische Objektdateien (.obj), die ohne Quellcode-Offenlegung in das Gesamtsystem gelinkt werden.
    • Post-Build: OEM erzeugt unabhängig vom BSW-Quellcode ladbare Hex-Dateien (.hex), die zur Laufzeit im Flash/RAM über Zeigerstrukturen vom BSW-Treiber ausgewertet werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Architektur- und API-Vertrag:
    • Parameter mit Bindezeit Pre-Compile materialisieren sich normativ als C-Präprozessor-Makros (#define) in <Modul>_Cfg.h zur Aktivierung/Deaktivierung von Features (z. B. <MODULE>_DEV_ERROR_DETECT).
    • Parameter mit Bindezeit Link-Time materialisieren sich als const-Datenstrukturen in <Modul>_Lcfg.c und werden über externe Symbole verlinkt.
    • Parameter mit Bindezeit Post-Build (PB) müssen über normierte Root-Zeiger an die Modul-Initialisierungsfunktionen übergeben werden (Signatur: void <Module>_Init(const <Module>_ConfigType* ConfigPtr)).
  • Konfigurations-Hierarchie und Validierung:
    • Modul-Generatoren müssen strikt validieren, dass Änderungen in PC Affect LT oder LT Affects PB keine Inkonsistenzen in den Parametern nachfolgender Stufen hervorrufen.
  • IP-Schutz & Lieferkette (OEM / Tier 1 / Tier 2 Trennung):
    • Das Modell ermöglicht BSW-Lieferanten (Tier 2) die Auslieferung vorkompilierter Stacks (.obj), während der Tier 1 Schnittstellen per Link-Time bindet und der OEM End-of-Line- oder Variantenkonfigurationen per Post-Build (.hex) ohne Rekompilierung des Gesamtsystems austauschen kann.
  • Speicher-Mapping:
    • Entwickler müssen über MemMap.h-Pragmas sicherstellen, dass Post-Build-Konfigurationen in separat adressierbaren Flash-Sektoren liegen, um die Erzeugung und den isolierten Austausch von .hex-Payloads zu unterstützen.
