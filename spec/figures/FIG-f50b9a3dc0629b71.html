1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Informelles Multi-Core-Deployment- und Datenflussdiagramm (AUTOSAR BSW Multi-Core Execution Architecture).
  • Technischer Zweck: Veranschaulichung der direkten Ausführung desselben BSW-Services (BswCalledEntity) auf mehreren Cores (Core 0 und Core 1) im Kontext des aufrufenden Anwendungs-Tasks via RTE ohne Task-Entkopplung.
  • Architektonische Einordnung: Spezifische Ausprägung des Master/Satellite-Musters für ECUs ohne hardwarebasierte MPU-Speichertrennung zwischen den BSW-Partitionen. Es eliminiert den Inter-Core-Kommunikations-Overhead (IOC) von R4.0, indem BSW-APIs lokal ausgeführt werden und ausschließlich die modulinternen Puffer synchronisiert werden.

2. Komponenten, Entitäten & Schnittstellen

  • Ausführungseinheiten / Partitionen:
    • core 0: Master-Core; führt die zentrale Modullogik und Hintergrundverarbeitung aus.
    • core 1: Satellite-Core; führt den Service-Endpunkt lokal aus.
  • Akteure & Entitäten:
    • Software Component (AtomicSwComponentType): Auf beiden Cores vorhanden, gekapselt in einem jeweiligen OS-Task (task).
    • RTE (Mapping): Laufzeitumgebung je Core; leitet API-Aufrufe der SWC direkt per Funktionsaufruf an die BSW weiter, da kein OperationInvokedEvent an einen OS-Task gebunden ist.
    • service X (BswCalledEntity): Reentrante, multi-core-fähige C-Implementierung des BSW-Services. Läuft auf Core 0 innerhalb der logischen master-Domäne und auf Core 1 innerhalb der satellite-Domäne im Kontext des aufrufenden Applikations-Tasks.
    • task main function (BswSchedulableEntity): Zyklische oder ereignisgesteuerte Hauptfunktion des BSW-Moduls; exklusiv auf Core 0 in einem eigenen OS-Task gebunden.
    • data buffer: Modulinterner Shared-Memory-Puffer (Global RAM), der von beiden Cores aus adressierbar ist.
  • Beziehungen & Stereotypen:
    • Synchroner Aufruf: Software Component → RTE Mapping → service X (synchroner Funktionsaufruf / Call-Return).
    • Schreibender Zugriff: service X (Core 0) → data buffer und service X (Core 1) → data buffer (gekennzeichnet als kritischer Pfad: „must be protected against concurrent access“).
    • Lesender Zugriff: data buffer → task main function (Core 0).

3. Dynamisches Verhalten & Sequenzablauf

  1. Lokaler Service-Trigger (Core 0 & Core 1 parallel):
    • Die SWC auf Core 0 oder Core 1 setzt synchron einen Service-Aufruf über das RTE-Interface ab (z. B. Client-Server-Interface oder Direkt-API).
    • Die RTE routet den Aufruf ohne Core-Wechsel und ohne Task-Switch direkt an die lokale C-Funktion von service X.
  2. Paralleler Pufferzugriff:
    • service X schreibt auf Core 0 und/oder Core 1 Nutzdaten in den modulglobalen data buffer.
    • Der Zugriff erfolgt unter Schutz eines Synchronisationsmechanismus, um gleichzeitige Schreibvorgänge abzufangen.
  3. Zyklische Verarbeitung (Core 0):
    • Das OS aktiviert periodisch den Task der main function auf Core 0.
    • main function sperrt den Puffer gegen Schreibzugriffe von service X (von beiden Cores), liest die Daten aus und leert bzw. aktualisiert den Pufferstatus für nachfolgende Verarbeitungsstufen.

4. Normative Relevanz & Entwickler-Hinweise

  • Reentrancy- und Concurrency-Anforderungen:
    • Der C-Code von service X muss strikt reentrant implementiert sein (keine ungeschützten modulglobalen/statischen Variablen, thread-lokaler Stack).
    • Der data buffer muss gegen Race Conditions zwischen Core 0 und Core 1 abgesichert werden.
  • Synchronisationsprimitive (SchM / OS):
    • Konventionelle Single-Core-Mittel (SuspendAllInterrupts(), GetResource()) sind unzureichend, da sie Core-übergreifend nicht greifen.
    • Zwingender Einsatz von AUTOSAR-OS-Multicore-Spinlocks (GetSpinlock() / ReleaseSpinlock()) oder SchM-Exklusivbereichen (SchM_Enter_<Mod>_<Area>() gemappt auf Spinlocks / hardwareunterstützte atomare Instruktionen).
    • Spinlock-Haltezeiten sind strikt zu minimieren, um Core-Stalls und Latenz-Jitter im aufrufenden SWC-Task zu verhindern.
  • Speicherschutz (MPU / OS-Applications):
    • Dieses Architekturmuster setzt voraus, dass der BSW-Bereich von Core 0 und Core 1 im selben Speicherkontext liegt oder der data buffer in einem non-cached bzw. geteilten Shared-RAM-Bereich konfiguriert ist, auf den beide OS-Applikationen Lese-/Schreibberechtigung besitzen.
  • Konfigurations-Vertrag (BswModuleDescription / RTE):
    • OperationInvokedEvent darf im BswModuleDescription nicht auf einen Task gemappt werden (mappedToTaskRef bleibt leer), um die direkte Ausführung im Aufruferkontext zu erzwingen.

Aus dem Dokument extrahierter Text & Kontext

Begleitender Spezifikationstext:

Figure 2 shows the example of a service "X", where the same API and the same code is called directly by the RTE on different cores. This is the default, if the services (respectively the OperationInvokedEvents) are not mapped to a task. The code must be reentrant and concurrency safe, which means that all access to data must be protected against concurrent access by the same or by a different entity of the same module. In this example, the same service "X" (BswCalledEntity) writes into a module internal data buffer accessible from core 0 and from core 1. A "main function" (BswSchedulableEntity), which is mapped to a task, reads the data from the buffer for further processing. In order to prevent read/write-conflicts, this “main function” must be protected from reading the buffer while it is written. This can be considered a special case of the generic master/satellite approach for systems without memory protection between the BSW partitions. The advantage of this approach is that the original, unchanged modules can be used, as long as they are implemented concurrency safe, which is usually the case for single core already, if different entities of the same module work on the same data, as shown in the example for core 0. Compared to the AUTOSAR R4.0 solution, where all service calls have to be routed to the master core, the performance can be improved considerably without much effort (assuming there is no need to do crosscore communication later).
