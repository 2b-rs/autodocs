1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Binäres Protokoll- und PDU-Layoutdiagramm (Bit- und Byte-Feld-Spezifikation für On-the-Wire-Serialisierung).
  • Architektur-Kontext: Bestandteil des AUTOSAR Classic Platform BSW-Moduls Mirror (Bus Mirroring, System Services Layer). Das Diagramm definiert die Serialisierungsstruktur eines einzelnen Bus Mirroring Protocol Data Items innerhalb einer aggregierten Mirroring-Destination-PDU.
  • Funktionaler Zweck: Standardisierte Kapselung, Zeitstempelung und Kompaktierung von Busereignissen (Frames, Bus-Statusänderungen) überwachter Quellnetzwerke (CAN, CAN FD, LIN, FlexRay) zur Weiterleitung über einen Zielbus (primär Ethernet/IP via SoAd/TcpIp oder dedizierte Trace-Schnittstellen) an externe Analysewerkzeuge (SRS_Mirror_00008).

2. Komponenten, Entitäten & Schnittstellen

Das Gesamtpaket besteht aus einem übergeordneten Header gefolgt von einer Sequenz mehrerer Data-Elemente ([Header][Data][...][Data]). Das Diagramm spezifiziert die interne Struktur eines einzelnen Data-Elements:

  • Mandatorische Basisfelder (4 Bytes Mindestgröße):
    • Timestamp (2 Bytes / 16 Bits, SWS_Mirror_00065, SWS_Mirror_00066): Relativer Zeitstempel-Offset bezogen auf den globalen HeaderTimestamp des Paket-Headers. Auflösung: Vielfache von 10 µs; Big-Endian (Network Byte Order).
    • Flag- und Typ-Byte (1 Byte / 8 Bits):
      • Netw.State Flag (1 Bit, MSB-Bereich, SWS_Mirror_00067, SWS_Mirror_00068): Präsenz-Indikator für das optionale Feld Netw.State (1 = vorhanden, 0 = entfällt).
      • FrameID Flag (1 Bit, SWS_Mirror_00069): Präsenz-Indikator für das optionale Feld FrameID (1 = vorhanden, 0 = entfällt).
      • Payload Flag (1 Bit): Präsenz-Indikator für Pay.Length und Payload (1 = vorhanden, 0 = entfällt).
      • Netw.Type (5 Bits): Bus-Technologie des Quellnetzwerks (z. B. CAN, CAN FD, LIN, FlexRay).
    • Netw.ID (1 Byte / 8 Bits): Konfigurierte Instanz-/Kanal-ID des Quellnetzwerks (MirrorSourceNetworkId).
  • Konditionale Felder (dynamische Header-Erweiterung auf 4 bis 10 Bytes):
    • Netw.State (1 Byte, optional): Bus-Zustandsinformation (z. B. CAN_BUS_OFF, LIN-Synchronisationsstatus). Nur vorhanden, wenn Bit Netw.State == 1.
    • FrameID (1–4 Bytes, optional): Frame-Identifikator des Quellbusses (z. B. 1 Byte für LIN PID, 2 Bytes für Standard-CAN 11-Bit, 4 Bytes für Extended-CAN 29-Bit bzw. FlexRay). Nur vorhanden, wenn Bit FrameID == 1.
    • Pay.Length (1 Byte, optional): Explizite Längenangabe der nachfolgenden Nutzdaten in Bytes. Nur vorhanden, wenn Bit Payload == 1.
  • Nutzdatenfeld:
    • Payload (variabel, 0..N Bytes): Eigentliche Rohdaten/PDU des Quellnetzwerks. Entfällt bei reinen Status-Events (Payload Flag == 0).
  • Kopfdaten-Kalkulation: $$\text{Data Header Size} = 4\,\text{Bytes (Basis)} + [0..1\,\text{B State}] + [0..4\,\text{B ID}] + [0..1\,\text{B Length}] = 4 \text{ bis } 10\,\text{Bytes}$$

3. Dynamisches Verhalten & Sequenzablauf

  • Trigger & Ingestion: Eingehende Frames an den Quell-Treibern (z. B. CanIf, LinIf, FrIf) lösen über standardisierte Interception-Callbacks Benachrichtigungen an das Mirror-Modul aus.
  • Serialisierung & Pufferung:
    1. Erfassung der Eingangszeit und Berechnung des 16-Bit-Offsets zum aktiven Puffer-Header (Timestamp).
    2. Auswertung der Frame-Metadaten: Setzen der Bits Netw.State, FrameID und Payload.
    3. Sequenzielles Schreiben der Felder in den PDU-Buffer gemäß normativer Reihenfolge (SWS_Mirror_00064).
    4. Überwachung der PDU-Größenbegrenzung (MirrorDestinationPduBuffering): Reicht der verbleibende Platz nicht für Header + Payload aus, wird die aktuelle Destination-PDU geschlossen und via PduR/SoAd übermittelt; das Item initiiert einen neuen Destination-Frame.
  • Fehlerbehandlung: Pufferüberläufe oder unzulässige Zeitstempel-Differenzen (> 65535 × 10 µs) erzwingen das vorzeitige Flashen des Puffers bzw. das Melden von Überlaufflags an das Det-Modul (MIRROR_E_BUFFER_OVERFLOW).

4. Normative Relevanz & Entwickler-Hinweise

  • PDU-Packing & Endianness: Entwickler von Mirror-Stack-Treibern und Parsern externer Analyse-Tools müssen beachten, dass Multibyte-Felder (Timestamp, FrameID) in Network Byte Order (Big-Endian) serialisiert werden (SWS_Mirror_00066).
  • Variable Header-Dekodierung: Da der Header zwischen 4 und 10 Bytes variiert, kann kein fester C-Struct-Pointer auf das Data Item gecastet werden. Parser müssen das Byte an Offset 2 maskieren:
    • Bit 7: Netw.State Available
    • Bit 6: FrameID Available
    • Bit 5: Payload Available
    • Bits 4..0: Network Type Die Offsets der nachfolgenden Felder müssen dynamisch zur Laufzeit berechnet werden.
  • Zero-Copy & Puffer-Allokation: Zur Minimierung von CPU-Load im Interrupt-/Task-Kontext muss der Puffer-Manager des Mirror-Moduls contiguous Memory bereitstellen, um die Payload direkt via Memory Copy aus den Interface-Pufferstrukturen einzubetten.
  • Konfigurationsaspekte (Mirror_Cfg.h): Die Zuordnung von Netw.ID und Netw.Type erfolgt statisch über die Parameter MirrorSourceNetwork und MirrorNetworkType. Entwickler müssen sicherstellen, dass Quellkanal-IDs über verschiedene Bustypen hinweg systemweit konsistent gemappt sind.
