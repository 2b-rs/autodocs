1. Diagrammtyp & Architektur-Kontext

  • Diagrammklassifikation: SPEM 2.0 (Software & Systems Process Engineering Metamodel) Methodik- und Prozessdiagramm im Profil der AUTOSAR Adaptive Platform (Package «SPEM_MethodContentPackage» Diagnostic Design).
  • Funktionale Einordnung: AUTOSAR AP R23-11 (AUTOSAR_AP_TR_Methodology, Kapitel 2.6 / 3.5). Spezifiziert den methodischen Ablauf zur Definition, Bereitstellung und Integration von UDS-/DoIP-Diagnoseanteilen (ara::diag) für Adaptive Applications und SW-Cluster.
  • Architektonischer Zweck: Trennung und Orchestrierung von Schnittstellendefinition (Interfaces), applikationsspezifischen Diagnosebeiträgen (Contributions), Diagnose-Auszügen (DEXT) und deren Zusammenführung in die finale Software-Cluster-Integration.

2. Komponenten, Entitäten & Schnittstellen

Pakete (Scope & Boundaries)
  • Diagnostic Design («SPEM_MethodContentPackage»): Kapselt alle Aufgaben und Artefakte des diagnostischen Designs.
  • Application Design («MethodContentPackage»): Externes vorgelagertes Paket; enthält übergreifende Anwendungsbeschreibungen.
  • SW Cluster Integration («MethodContentPackage»): Externes nachgelagertes Integrationspaket für die Deployment- und Cluster-Ebene.
Aufgaben («TaskDefinition»)
  • Define Diagnostic Interface Description: Spezifiziert die typsicheren Diagnose-Serviceschnittstellen für Applikationen.
  • Provide DEXT for Application Set-up: Generiert bzw. liefert den Diagnose-Extrakt (DEXT) für die Applikationskonfiguration.
  • Define Diagnostic Contribution Description: Definiert die konkreten Diagnoseanteile (DIDs, Routinen, DTCs), die eine Applikation bedient.
  • Define Interaction with Functional Clusters (aus Application Design): Bestimmt Interaktionen von Applikationen mit funktionellen Clustern.
  • Integrate Diagnostics (aus SW Cluster Integration): Verknüpft Diagnose-Designartefakte auf Cluster-Ebene zu finalen Mappings.
Artefakte («Artifact») & Liefergegenstände («Deliverable»)
  • SW Interaction Description («Artifact»): Abstrakte Interaktionsbeschreibung von Softwarekomponenten.
  • SW to Diagnostics Interaction Description («Artifact»): Generalisiert/spezialisiert SW Interaction Description (UML-Generalisierung $\triangle$); beschreibt die konkrete Schnittstelle zwischen Anwendungslogik und dem Cluster Diagnostic Management (ara::diag).
  • DEXT («Artifact»): Diagnostic Extract (ARXML-Repräsentation der Diagnose-Datenbasis nach ISO 14229-1 / ISO 13400-2).
  • Diagnostic Interface Description («Artifact»): ARXML-Modell der diagnosebezogenen Port- und Service-Interfaces.
  • Diagnostic Contribution Description («Artifact»): Festlegung der von einer SW-Komponente gelieferten diagnostischen Funktionalitäten.
  • Diagnostic Design («Deliverable»): Aggregiertes Lieferpaket des Diagnose-Designs.
  • Diagnostic Mappings for Adaptive SW («Deliverable»): Vollständiges Mapping der Diagnose-Ports und Datenelemente auf die Adaptive Platform.

3. Dynamisches Verhalten & Sequenzablauf

  1. Interaktionsspezifikation: Aus dem übergeordneten Application Design wird via Define Interaction with Functional Clusters die SW Interaction Description abgeleitet. Diese wird zur SW to Diagnostics Interaction Description konkretisiert.
  2. DEXT-Bereitstellung: Provide DEXT for Application Set-up konsolidiert Diagnoseanforderungen (unter Berücksichtigung von SW to Diagnostics Interaction Description) und erzeugt das Artefakt DEXT.
  3. Parallele Design-Aktivitäten:
    • Pfad A (Interfaces): Define Diagnostic Interface Description definiert unabhängig die ARXML-Schnittstellen (Diagnostic Interface Description).
    • Pfad B (Contributions): Define Diagnostic Contribution Description konsumiert das DEXT als Input und definiert die applikationsspezifischen Handler/Beiträge (Diagnostic Contribution Description).
  4. Aggregation: Die Artefakte Diagnostic Interface Description, Diagnostic Contribution Description und DEXT formen zusammen das Deliverable Diagnostic Design.
  5. Cluster-Integration: Der Integrationsschritt Integrate Diagnostics verarbeitet das Deliverable Diagnostic Design und erzeugt unter Einbeziehung der SW to Diagnostics Interaction Description das finale Deliverable Diagnostic Mappings for Adaptive SW.

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von DEXT und Application Interface: Applikations-Entwickler implementieren nicht gegen die rohe DEXT-Datenbasis, sondern gegen die durch Diagnostic Interface Description generierten C++-Header von ara::diag (z. B. ara::diag::GenericDataIdentifier, ara::diag::Routine).
  • Contribution-Modell: Einzelne funktionale Applikationen liefern autarke Diagnostic Contribution Descriptions. Dies ermöglicht verteilte Teams und CI/CD-Pipelines, da Applikationen diagnostische Services deklarieren können, ohne den gesamten Fahrzeug-DEXT manipulieren zu müssen.
  • Manifest- & Mapping-Konfiguration:
    • Das Deliverable Diagnostic Mappings for Adaptive SW ist bindend für die Generierung der Execution- und Service-Instance-Manifeste.
    • Hier werden PortPrototype-Referenzen der Applikationen mit den internen DEXT-Objekten (DIDs, DTCs, Diagnostic Sessions, Security Levels) des Diagnostic Management Daemons (ara::diag) verknüpft.
  • Konsistenzprüfung: Der Integrator muss vor Integrate Diagnostics sicherstellen, dass alle im DEXT referenzierten DIDs/Routinen exakt mit den in den Diagnostic Contribution Descriptions deklarierten Ports übereinstimmen. Inkonsistenzen führen zum Scheitern des Cluster-Deployments.
