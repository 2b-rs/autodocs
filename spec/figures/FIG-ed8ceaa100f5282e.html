1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Strukturelles Artefakt- und Deliverable-Diagramm basierend auf der AUTOSAR Methodology.
  • Technischer Zweck: Definition der internen Dekomposition des generischen Arbeitsergebnisses (Deliverable) System Description in der AUTOSAR-Methodik. Es spezifiziert die aggregierten Teilmodelle und ARXML-Fragmentstrukturen, die zur vollständigen Beschreibung eines vernetzten E/E-Fahrzeugsystems auf OEM-Ebene erforderlich sind.

2. Komponenten, Entitäten & Schnittstellen

Zentraler Knoten ist das Composite-Deliverable System Description. Alle Kindelemente sind über gerichtete Kompositionsbeziehungen mit dem Stereotyp «aggregation» angebunden.

Kernstruktur & Topologie
  • System Description Root Element [1]: Zwingend erforderliches Wurzelelement (formalisiert das umschließende AUTOSAR-Wurzelpaket bzw. <SYSTEM>-Tag als Ankerpunkt für Referenzen).
  • Topology [0..1]: Physikalische E/E-Vernetzungstopologie (ECUs, Hardware-Controller, Bus-Cluster/Netzwerke wie CAN, LIN, FlexRay, Ethernet sowie physikalische Gateways).
Allokation & Software-Mapping
  • Mapping of Software Components to ECUs [0..1]: Bindung von atomaren SWC-Prototypen bzw. Komponenteninstanzen an konkrete ECUs (SwcToEcuMapping).
  • Mapping of Software Components to Implementations [0..1]: Zuordnung von SWC-Instanzen zu spezifischen Code-Artefakten (SwcToImplMapping).
Signal- & Kommunikationspfade
  • **System Signal [0..*]:** Repräsentation der logischen Kommunikationssignale auf VFB- bzw. Netzwerk-Ebene.
  • **System Signal Group [0..*]:** Strukturierte Zusammenfassung von Signalen (Basis für atomare Signalübertragung und End-to-End-Protection).
  • **Data Mapping [0..*]:** Transformation und Abbildung von Port-Elementen (VFB) auf Signale bzw. von Signalen auf Signal-Gruppen und I-PDUs.
  • **Communication Matrix [0..*]:** Netzwerk-Scheduling- und Frame-Definitionen (Signal-to-PDU-to-Frame-Zuordnung, Übertragungsmodi, Zykluszeiten, Bus-Cluster-Parameter).
  • Communication Layers [0..1]: Untergeordnetes Composite-Deliverable zur Beschreibung erweiterter, schichtspezifischer Kommunikationsstacks (z. B. Netzwerkmanagement, Transportprotokolle).
Rapid Prototyping
  • Rapid Prototyping [0..1]: Spezifische Artefaktbeschreibungen und Konfigurationen zur Einbindung von Prototyping- und Bypass-Szenarien im Gesamtsystem.
Timing & Naming
  • **System Timing [0..*]:** Systemweite Zeitbedingungen (Latenzen, Execution Order Constraints, End-to-End-Deadlines gemäß AUTOSAR Timing Extensions).
  • **Alias Name Set [0..*]:** Zuordnungstabelle alternativer Bezeichner zur systemübergreifenden Harmonisierung proprietärer Namenskonventionen.
Variantenmanagement
  • **Predefined Variant [0..*]:** Vordefinierte Konfigurationen für Pre-Compile-Variabilität (systemCriterionValues).
  • **System Constant Value Set [0..*]:** Globale Systemkonstanten zur Evaluierung von Modell-Variationspunkten (swSystemconst).
  • **Postbuild Variant Set [0..*]:** Definition von Parametersätzen für Post-Build-Selectable bzw. Post-Build-Loadable Varianten.
  • **Evaluated Variant Set [0..*]:** Resultierende, vollständig gebundene Parametersätze nach Auswertung von Variantenbedingungen.

3. Dynamisches Verhalten & Sequenzablauf

Als rein statisches SPEM-Strukturdiagramm existiert kein Laufzeit-Sequenzablauf auf Target-Ebene. Im Lebenszyklus der AUTOSAR-Methodik gilt folgender Sequenzpfad:

  1. Top-Down-Synthese: Erstellung von SWC-Beschreibungen, Topologie und VFB-Schnittstellen.
  2. Signal- & Kommunikationssynthese: Definition von System Signal / System Signal Group, Verknüpfung via Data Mapping mit der Communication Matrix.
  3. Allokation: Auflösung der Software Component Mapping Constraints zur Erzeugung des Mapping of Software Components to ECUs.
  4. Variantenbindung: Anwendung von System Constant Value Set und Predefined Variant zur Generierung des konsistenten Evaluated Variant Set.
  5. Downstream-Transition (ECU Extract): Die vollständige System Description dient als exklusives Eingangsdokument für den vorgelagerten Transformationsschritt Extract ECU System Description (Erzeugung des steuergerätespezifischen ECU Extract / System Extract).

4. Normative Relevanz & Entwickler-Hinweise

  • Tier-1 / OEM-Schnittstelle: Die System Description verbleibt typischerweise in der Hoheit des Fahrzeugherstellers (OEM). Der Steuergeräte-Entwickler (Tier-1) arbeitet normativ nicht direkt auf der vollständigen System Description, sondern empfängt den daraus per Toolkette erzeugten, gefilterten ECU Extract of System Description (Flat Map).
  • BSW-Konfiguration (Com-Stack): Die Inhalte aus Communication Matrix und Data Mapping determinieren direkt die statischen Tabellen für Com, PduR, CanIf/LinIf/FrIf/EthIf sowie die Bus-Treiber (Can, Lin, Fr, Eth). Eine Diskrepanz in den Aggregationen führt zu unvollständigen Frame- und PDU-IDs im BSW-Generatorlauf.
  • RTE-Generierung: Das Mapping of Software Components to ECUs definiert die RTE-Topologie: Port-Kommunikationen zwischen SWCs auf derselben ECU werden durch den RTE-Generator als speicherinterne Operationen (Shared Memory / Direktaufruf / Pointer-Übergabe) aufgelöst; Steuergeräte-externe Port-Verbindungen werden zwingend an das AUTOSAR-COM geroutet.
  • Variabilitäts-Einschränkungen: Vorhandene Postbuild Variant Sets erfordern, dass Treiber- und Stack-Generatoren relocatable Deskriptor-Strukturen im Flash/ROM oder Initialisierungs-RAM anlegen, statt hardcodierter Präprozessor-Konstanten (#define). Fehlt dieses Set, greift Pre-Compile-Variabilität (Predefined Variant), was eine Neukompilierung für Variantenwechsel erzwingt.
