1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt für ECU Configuration (ECUC Parameter Definition Model gemäß AUTOSAR BSW Module Description Template).
  • Technischer Zweck: Spezifikation der hierarchischen Konfigurationsstruktur für den ICU-Treiber (Input Capture Unit, MCAL-Schicht, Microcontroller Drivers) der AUTOSAR Classic Platform.
  • Architektur-Einordnung: Definiert die Datenstrukturen zur Parametrierung physikalischer Input-Capture-Timerkanäle, deren logische Zuordnung zu ECU-Kanälen sowie deren Betriebsmodi für Pre-Compile-, Link-Time- und Post-Build-Konfigurationen (IcuConfigSet).

2. Komponenten, Entitäten & Schnittstellen

Entitäten & Container-Definitionen
  • Icu (:ModuleDef): Modul-Wurzelelement (Multiplizität 0..*).
  • IcuConfigSet (:ParamConfContainerDef): Top-Level-Konfigurationsbehälter mit multipleConfigurationContainer = TRUE (unterstützt Post-Build Selectable/Loadable Parametersätze).
    • Parameter: IcuMaxChannel (:DerivedIntegerParamDef, calculationLanguage = Informal, min = 0), berechnet die maximale Anzahl konfigurierter Kanäle.
    • Aggregation (+subContainer): Referenziert 1 bis n (1..*) IcuChannel-Instanzen.
  • IcuChannel (:ParamConfContainerDef): Zentrale Repräsentation eines logischen ICU-Hardwarekanals (Multiplizität 1..*).
Kanalparameter (+parameter)
  • IcuChannelId (:IntegerParamDef): Eindeutige Kanal-ID (min = 0, symbolicNameValue = true). Dient der Generierung typsicherer C-Makros für BSW- und Applikationsaufrufe.
  • IcuWakeupCapability (:BooleanParamDef): Schaltet die Fähigkeit des Kanals frei, die MCU aus dem Sleep/Halt-Zustand aufzuwecken.
  • IcuDefaultStartEdge (:EnumerationParamDef): Bestimmt die Default-Triggerflanke nach Initialisierung mit folgenden Literalen (:EnumerationLiteralDef):
    • IcuRisingEdge (steigende Flanke)
    • IcuFallingEdge (fallende Flanke)
    • IcuBothEdges (beide Flanken)
  • IcuMeasurementMode (:EnumerationParamDef): Definiert die fundamentale funktionale Betriebsart des Kanals über vier distinkte Literale (:EnumerationLiteralDef):
    • IcuSignalEdgeDetection (reine Flankenerkennung / Interrupt-Signalisierung)
    • IcuSignalMeasurement (Pulsdauer-, Periodendauer- und Tastverhältnismessung)
    • IcuTimestamp (fortlaufende Zeitstempelerfassung in Puffer)
    • IcuEdgeCounter (Ereigniszählung)
Kanal-Subcontainer (+subContainer, Multiplizität jeweils 0..1)
  • IcuSignalEdgeDetection: Parametrierung für Benachrichtigungen bei Flankenwechseln.
  • IcuSignalMeasurement: Parametrierung für Messarten (z. B. ICU_PERIOD_TIME, ICU_DUTY_CYCLE, ICU_HIGH_TIME, ICU_LOW_TIME).
  • IcuTimestampMeasurement: Puffer- und DMA-/Interrupt-Konfiguration für Zeitstempelerfassung.
  • IcuWakeup: Mapping auf EcuM-Wakeup-Quellen (EcuM_WakeupSourceType).

3. Dynamisches Verhalten & Sequenzablauf

Als statisches Metamodell zeigt das Diagramm keinen direkten Zeitablauf. Das daraus abgeleitete Laufzeitverhalten gliedert sich wie folgt:

  1. Initialisierungsphase: Icu_Init(&Icu_ConfigSet) parst die generierten Kanaltabellen. Jeder Kanal wird hardwareseitig auf IcuDefaultStartEdge sowie die in IcuMeasurementMode hinterlegte Betriebsart initialisiert.
  2. Modusabhängige Ausführung:
    • SignalEdgeDetection: Hardware-Capture-Interrupt triggert den konfigurierten Callback (sofern über Icu_EnableNotification() scharfgeschaltet). Flankenbedingung zur Laufzeit via Icu_SetActivationCondition() anpassbar.
    • SignalMeasurement: Timer-Capture-Register erfassen Flankenabstände; Bereitstellung über synchrone API-Abfragen (Icu_GetTimeElapsed(), Icu_GetDutyCycleValues()).
    • Timestamp: ISR/DMA schreibt Hardware-Timer-Ticks in einen Ring- oder Linear-Puffer (Icu_StartTimestamp()). Erreichen des Pufferlimits triggert den Überlauf-Callback.
    • EdgeCounter: Hardwarezähler akkumuliert Flanken; Abfrage via Icu_GetEdgeNumbers().
  3. Low-Power & Wakeup-Pfad: Bei Eintritt in Sleep-Zustände (Icu_SetMode(ICU_MODE_SLEEP)) bleiben Kanäle mit IcuWakeupCapability = TRUE und aktivem IcuWakeup-Subcontainer sensiert. Eine Flanke ruft EcuM_SetWakeupEvent() auf.

4. Normative Relevanz & Entwickler-Hinweise

  • Generator-Validierung & Konsistenzregeln:
    • Der Konfigurationsgenerator muss eine 1:1-Exklusivität zwischen IcuMeasurementMode und den Subcontainern erzwingen: Ist IcuMeasurementMode == IcuSignalMeasurement, muss der Subcontainer IcuSignalMeasurement instanziiert sein; die Container der jeweils anderen drei Modi müssen fehlen oder inaktiv sein.
    • Wenn IcuWakeupCapability == TRUE, ist die Konfiguration des Subcontainers IcuWakeup (inkl. valider Referenz auf EcuMWakeupSourceId) zwingend erforderlich.
  • API-Vertrag & DET-Fehler:
    • Aufruf von modusfremden APIs (z. B. Icu_StartTimestamp() auf einem Kanal mit IcuMeasurementMode == IcuSignalEdgeDetection) muss im Treiber mit ICU_E_PARAM_MODE via Det_ReportError abgefangen werden.
    • IcuChannelId mit symbolicNameValue = true erzwingt in Icu_Cfg.h die Generierung standardisierter Makros (z. B. IcuConf_IcuChannel_<Name>), welche als Argumente Channel an die API übergeben werden müssen.
  • Post-Build-Speicherlayout: Durch multipleConfigurationContainer = TRUE an IcuConfigSet müssen alle kanalspezifischen Datenfelder in ROM-Konfigurationsstrukturen (Icu_ConfigType) zeigerkompatibel serialisiert werden, um nahtloses Umschalten von Parametersätzen zur Laufzeit ohne Neukompilierung zu gewährleisten.
