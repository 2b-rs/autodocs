1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Klassendiagramm / Metamodell-Ausschnitt des AUTOSAR System Template (Package FibexCore::SignalOverview, Release R3.0.7).
  • Technischer Zweck: Definition der Schichtenarchitektur zur Signal- und PDU-Modellierung. Es entkoppelt funktionale/logische Signale (SystemSignal) von ihrer physikalischen Repräsentation auf Kommunikationsbussen (ISignal, SignalIPdu), definiert das Bit-/Byte-Packing (ISignalToIPduMapping) und bindet Signale an Cluster-Kanäle (PhysicalChannel über ISignalTriggering).
  • Funktionale Einordnung: Dient als normative Eingangsgröße für den System-Extract und die Codegenerierung des Kommunikations-Stacks (vorrangig AUTOSAR COM, PduR sowie busbezogene Interface-Module wie CanIf/FrIf/LinIf).

2. Komponenten, Entitäten & Schnittstellen

  • CoreTopology::PhysicalChannel (Identifiable): Repräsentiert den physikalischen Buskanal (CAN, LIN, FlexRay).
  • Besitzt per Komposition («splitable») $0..\*$ Instanzen von ISignalTriggering (Rolle: +iSignalTriggering).
  • ISignalTriggering (Identifiable): Bildet den Trigger- bzw. Übertragungskontext eines Signals auf einem spezifischen Kommunikationskanal ab.
  • Referenziert exakt $1$ ISignal (Rolle: +signal, Multiplizität $1..\*$).
  • ISignal (FibexElement, Identifiable): Repräsentiert das Signal auf Interaktionsebene (Interaction Layer / AUTOSAR COM).
  • Referenziert exakt $1$ AbstractSignal (Rolle: +systemSignal, Multiplizität am ISignal $1..\*$).
  • AbstractSignal (ARElement, abstrakt): Basisklasse für Signale auf Systemebene. Generalisiert zu:
  • SystemSignal: Logisches Nutzsignal mit Attribut length: Int.
  • Referenziert optional (0..1) Datatypes::PrimitiveType (Stereotyp «atpType», Rolle +dataType).
  • Referenziert optional (0..1) Constants::ValueSpecification (Rolle +initValue).
  • SystemSignalGroup: Logische Gruppierung von Signalen zur konsistenten Übertragung. Aggregiert $*$ SystemSignal (Rolle: +systemSignal).
  • IPdu (Pdu): Abstrakte Interaktions-PDU.
  • Attribute: length: Int (PDU-Gesamtlänge in Bytes), unusedBitPattern: Int [0..1] (Auffüllmuster ungenutzter Bits).
  • SignalIPdu: Spezialisierung von IPdu.
  • Hält per Komposition $0..\*$ Instanzen von ISignalToIPduMapping (Rolle: +signalToPduMapping).
  • ISignalToIPduMapping (Identifiable): Konfiguriert das Layout eines ISignal innerhalb einer SignalIPdu.
  • Referenziert exakt $1$ ISignal (Rolle: +signal, Multiplizität am Mapping $1..\*$).
  • Attribute:
  • packingByteOrder: ByteOrderEnum: Byteselektion (mostSignificantByteFirst = Big Endian/Motorola, mostSignificantByteLast = Little Endian/Intel).
  • startPosition: Int [0..1]: Startbit-Position des Signals in der PDU.
  • transferProperty: TransferPropertyEnum: Sendecharakteristik (triggered, pending, triggeredOnChange).
  • updateIndicationBitPosition: Int [0..1]: Bitposition des Update-Bits zur Signalfrische-Kennzeichnung.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm ist ein statisches Strukturmodell, dessen Konfigurationsattribute jedoch deterministisch das dynamische Laufzeitverhalten des AUTOSAR COM-Stacks steuern:

  • PDU-Sendeauslösung via transferProperty:
  • triggered: Aufruf von Com_SendSignal() stößt sofort die PDU-Übertragung an (sofern nicht durch Mindestabstandszeiten/MinimumDelayTimer blockiert).
  • pending: Signalwert wird ausschließlich im PDU-Schattenpuffer aktualisiert; Übertragung erfolgt rein zeitgesteuert (zyklischer PDU-Sendemodus).
  • triggeredOnChange: PDU-Übertragung wird nur dann unmittelbar initiiert, wenn sich der geschriebene Wert vom aktuellen Pufferwert unterscheidet.
  • Signalfrische-Tracking via updateIndicationBitPosition:
  • Sender: Setzen des Update-Bits im Serialisierungsschritt bei Aufruf von Com_SendSignal(). Rücksetzen nach erfolgreicher Bestätigung durch den Treiber/Interface-Layer (TxConfirmation).
  • Empfänger: Bei Empfang (RxIndication) prüft COM das Update-Bit. Ist es 0, wird der Signalwert ignoriert; ist es 1, wird das Signal entpackt und an die Applikations-Layer/RTE propagiert.
  • Initialisierung: Vor der ersten Kommunikation initialisiert der COM-Stack die Signalpuffer anhand von ValueSpecification (initValue) und füllt freie Bereiche der SignalIPdu mit unusedBitPattern.

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Applikations- und Übertragungssicht: Ein SystemSignal kann über mehrere ISignal-Instanzen in unterschiedliche Netzwerke (SignalIPdu auf unterschiedlichen PhysicalChannels) gemappt werden. Dies bildet die Grundlage für 1:N-Verteilungen und Signal-Gatewaying ohne Anpassung des Software-Components.
  • BSW-Konfigurations-Mapping (AUTOSAR COM):
  • ISignal $\rightarrow$ ComSignal
  • SystemSignalGroup $\rightarrow$ ComSignalGroup (erfordert atomare Schattenpufferung via Com_SendSignalGroup() / Com_ReceiveSignalGroup())
  • ISignalToIPduMapping $\rightarrow$ ComBitPosition, ComBitSize, ComSignalEndianness, ComTransferProperty
  • Bit-Adressierungs-Konvention: Entwickler von Codegeneratoren müssen die endianness-spezifische AUTOSAR-Bitnummerierung beachten: Bei mostSignificantByteFirst (Motorola) weicht die Adressierung des Startbits im Metamodell standardmäßig von nativen Bitfeld-Definitionen in C ab (AUTOSAR-Bitordnungsregeln gemäß BSW COM SWS).
  • Update-Bit-Einschränkungen: Wird updateIndicationBitPosition konfiguriert, muss die PDU-Länge sicherstellen, dass das Update-Bit kollisionsfrei außerhalb der Nutzdatenbits anderer ISignals liegt; Überlappungen führen zu Konfigurationsfehlern zur Generierungszeit.
