1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: PDU-Layout- und Metamodell-Mapping-Diagramm (Signal-to-Service-Mapping / Signal-Based Communication).
  • Technischer Zweck: Spezifikation der normativen Transformationsvorschrift zur Überführung einer klassischen, signalgemultiplexten PDU (MultiplexedIPdu des Classic-Platform-Moduls IpduM) in das C++-Typsystem der AUTOSAR Adaptive Platform (ara::com / Manifest-Spezifikation).
  • Architektur-Einordnung:
  • Vermittelt an der Gateway- bzw. Migrationsschnittstelle zwischen Signal-basierter Bordnetzkommunikation (CAN, LIN, FlexRay) und Service-orientierter Architektur (SOME/IP, IPC).
  • Löst das Problem, dass die Adaptive Platform keine native Bit-Multiplexierung auf Middleware-Ebene kennt, indem dynamische PDU-Segmente auf optionale C++-Strukturelemente (ara::core::Optional<T> / std::optional<T>) projiziert werden.

2. Komponenten, Entitäten & Schnittstellen

  • Physisches PDU-Layout (IpduM I-PDU):
  • static segment 0 & static segment 1: Feste, layout-invariante Bitfelder, die in jedem Frame-Zyklus unverändert übertragen werden.
  • dynamic segment 0 & dynamic segment 1: Mutex-geschützte, dynamisch belegte Bit-Bereiche, deren semantischer Inhalt vom Selektorfeld abhängt.
  • S F (Selector Field): Bitfeld mit fix definiertem Offset (start of the selector field) und definierter Bitbreite (size of selector field), das als Diskriminator fungiert.
  • Classic Platform I-PDU-Repräsentationen (COM-Ebene):
  • COM I-PDU static part: Aggregiert ausschließlich die statischen Signale S0, S1, S2 (in Segment 0) und S3 (in Segment 1).
  • COM I-PDU dynamic part layout 00: Belegt bei SF == 0b00 die Signale D0, D1 (Segment 0) sowie D2, D3, D4 (Segment 1).
  • COM I-PDU dynamic part layout 01: Belegt bei SF == 0b01 die Signale D5 (Segment 0) sowie D2, D6 (Segment 1).
  • COM I-PDU dynamic part layout 10: Belegt bei SF == 0b10 die Signale D0, D7 (Segment 0) sowie D8, D9 (Segment 1).
  • (Hinweis: Signale wie D0 und D2 weisen layout-abhängige Mehrfachverwendungen an identischen oder divergierenden Bit-Offsets auf).
  • Adaptive Data Model (CppImplementationDataType category = STRUCTURE):
  • Wurzelstruktur (Enclosing Record): Repräsentiert die gesamte MultiplexedIPdu.
  • Statische Member: S0, S1, S2, S3 sind direkte, obligatorische (mandatory) Member der übergeordneten Struktur.
  • Dynamische Member (CppImplementationDataTypeElement mit Attribut isOptional = true):
  • d00 record: category = STRUCTURE, enthält die Felder D0, D1, D2, D3, D4.
  • d01 record: category = STRUCTURE, enthält die Felder D2, D5, D6.
  • d10 record: category = STRUCTURE, enthält die Felder D0, D7, D8, D9.
  • Stereotypen & Metamodell:
  • Zuordnung über SignalIPduToCppImplementationDataTypeMapping («atpSplitable»).
  • Typisierung über CppImplementationDataType («isOfType»).

3. Dynamisches Verhalten & Sequenzablauf

#### Deserialisierung / RX-Pfad (Network-to-Service):

  1. PDU-Empfang: Einlesen der Rohdaten über den Netzwerk-Treiber (z. B. CAN-Interface).
  2. Selektor-Dekodierung: Parsing des Selector Fields (SF) an Bitposition start of the selector field mit Bitmaske (1 << size) - 1.
  3. Statisches Unpacking: Signale S0, S1, S2, S3 werden bedingungslos extrahiert und in die Basisstruktur geschrieben.
  4. Dynamisches Branching:
  • Wert 0b00: Deserialisierung der Bytes in d00 record. Setzen des Containers auf has_value() == true. d01 und d10 werden als std::nullopt belassen.
  • Wert 0b01: Deserialisierung in d01 record. d00 und d10 verbleiben std::nullopt.
  • Wert 0b10: Deserialisierung in d10 record. d00 und d01 verbleiben std::nullopt.
  • Ungültiger Selektor: Verwerfen des dynamischen Anteils oder Meldung eines Kommunikationsfehlers via Diagnostic Log and Trace (DLT) bzw. Rückgabe eines ara::core::ErrorCode.
  1. Event-Dispatching: Bereitstellung des zusammengesetzten C++-Structs an den Application-Subscriber via ara::com::Event::Update().

#### Serialisierung / TX-Pfad (Service-to-Network):

  1. Konsistenzprüfung: Serialisierer validiert die Exklusivität: Es darf zur Sendezeit exakt maximal ein optionaler Sub-Record (d00, d01 oder d10) gesetzt sein (has_value() == true).
  2. Selektor-Codierung: Das Selector Field SF wird hardwarenah automatisch anhand des aktiven Optional-Records auf 0b00, 0b01 bzw. 0b10 gesetzt.
  3. Payload-Assembly: Packen der statischen Signale S0..S3 sowie der aktiven dynamischen Signale in den I-PDU-Buffer; verbleibende ungenutzte Bits werden mit konfigurierten Padding-Bytes (z. B. 0xAA oder 0xFF) belegt.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative SWS-Regeln:
  • TPS_MANI_03638: Eine MultiplexedIPdu muss zwingend auf einen CppImplementationDataType der Kategorie STRUCTURE abgebildet werden.
  • TPS_MANI_03639: Statische Signale der PDU werden direkt als nicht-optionale Member im Haupt-Struct realisiert.
  • TPS_MANI_03640: Jedes dynamische Layout der PDU wird als eigenes CppImplementationDataTypeElement mit category = STRUCTURE und Gesetztem isOptional = true modelliert.
  • TPS_MANI_03641: Das Selector Field (SF) darf nicht als explizites Datenelement in der C++-Struktur auftauchen; es dient ausschließlich als interner Protokoll-Diskriminator der Serialisierungs-Engine.
  • RS_MANI_00063: Gewährleistung der Interoperabilität zwischen CP-Signal-Stack (IpduM) und AP-Service-Schicht.
  • Praktische Implikationen für Embedded-/Applikations-Entwickler:
  • C++ Typabbildung: Generierter Code realisiert optionale Felder als ara::core::Optional<dXX_type> (entspricht semantisch std::optional<T>).
  • API-Invariante (TX): Setzt die Applikation mehr als ein optionales Feld gleichzeitig, schlägt die Serialisierung fehl (ara::com::ComErrorDomainErrc::kInvalidArguments). Ist kein optionales Feld gesetzt, wird nur der statische PDU-Teil übermittelt (sofern dies im IpduM-Schema zulässig konfiguriert ist).
  • Speicher-Footprint: Obwohl auf dem physischen Bus Mutex-Segmente vorliegen, allokiert die C++-Struktur im Speicher Platz für alle Unterstrukturen plus deren Optional-Flags (bool + Alignment-Padding). Entwickler müssen diesen Overhead auf ressourcenbeschränkten Mikrocontrollern einplanen.
  • Keine Layout-Inferenz: Shared-Signale (wie D2, das in d00 und d01 vorkommt) sind getrennte Variablen im C++-Code; eine Konsistenzübertragung zwischen den Layouts muss explizit applikativ erfolgen.
