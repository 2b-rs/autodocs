1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Sequenzdiagramm (Interaktionsdiagramm mit synchronen Funktionsaufrufen, Callbacks und asynchronen Hardware-Ereignissen).
  • Technischer Zweck: Spezifikation des Zusammenspiels zwischen ECU State Manager (EcuM), dem Icu Driver (MCAL) und dem ICU-Konsumenten (ICU User, z. B. SW-C oder IoHwAb) bei Moduswechseln (ICU_MODE_NORMAL → ICU_MODE_SLEEP).
  • Funktionale Einordnung: Demonstration der Entkopplung von regulären Flanken-Benachrichtigungen (Edge Notifications) und Aufwachereignissen (Wakeup Events). Das Diagramm illustriert das Verhalten von wake-up-fähigen und nicht wake-up-fähigen Kanälen im Schlafmodus, insbesondere die Unterdrückung von Edge-Notifications bei aktivem ICU_MODE_SLEEP.

2. Komponenten, Entitäten & Schnittstellen

  • Beteiligte Instanzen (Lifelines):
    • EcuM (ECU State Manager, BSW System Service): Zuständig für ECU-Zustandsverwaltung, Modusumschaltung (Icu_SetMode) sowie Validierung und Entgegennahme von Aufwachquellen.
    • ICU User (e.g. SW-C): Applikations- oder Treiberschicht oberhalb des MCAL; konfiguriert dynamische Kanaleigenschaften (Aktivierungsflanke, Notifications, Wakeup-Freigabe) und konsumiert Kanal-Callbacks.
    • Icu Driver (MCAL Input Capture Unit Driver): Direkte Hardwareschnittstelle zur Erfassung von Flanken, Steuerung der Erfassungskanäle und Generierung von ISR-/Callback-Ereignissen.
  • Relevante Schnittstellen & APIs:
    • Initialisierung & Modus: Icu_Init(ConfigPtr), Icu_SetMode(Mode).
    • Kanalsteuerung: Icu_SetActivationCondition(Channel, Activation), Icu_EnableNotification(Channel), Icu_DisableNotification(Channel), Icu_EnableWakeup(Channel).
    • Kanal-Callbacks an User: Icu_SignalNotification_Channel1(), Icu_SignalNotification_Channel2().
    • Wakeup-Schnittstellen (EcuM ↔ ICU): EcuM_CheckWakeup(), Icu_Cbk_CheckWakeup() (Treiber-Re-Check), EcuM_SetWakeupEvent().
  • Kanalzustände & Vorkonfiguration:
    • Initialzustand: Modul im Zustand ICU_MODE_NORMAL, alle Notifications global/kanalbezogen deaktiviert, Signalpegel low.
    • Channel #1: Nicht wakeup-fähig konfiguriert (IcuWakeupCapability = FALSE), Flankenbedingung ICU_FALLING_EDGE.
    • Channel #2: Wakeup-fähig konfiguriert (IcuWakeupCapability = TRUE), Flankenbedingung ICU_RISING_EDGE, Vorkonfiguration ICU_REPORT_WAKEUP_SOURCE = STD_ON.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Laufzeitkonfiguration (Normalmodus):
    • EcuM initialisiert den Treiber synchron via Icu_Init(ConfigPtr).
    • ICU User schaltet Wakeup für Channel #2 scharf (Icu_EnableWakeup).
    • ICU User parametriert Triggerbedingungen (Channel #1 auf fallende Flanke, Channel #2 auf steigende Flanke) und aktiviert für beide Kanäle die Flanken-Benachrichtigung (Icu_EnableNotification).
  2. Ereignisverarbeitung im ICU_MODE_NORMAL:
    • Fallende Flanke an Channel #1: Treiber löst synchron/per ISR Icu_SignalNotification_Channel1() am User aus.
    • Steigende Flanke an Channel #2: Treiber löst synchron/per ISR Icu_SignalNotification_Channel2() am User aus.
  3. Übergang in den Schlafmodus:
    • ICU User deaktiviert die Flanken-Benachrichtigung für Channel #2 via Icu_DisableNotification(Channel #2).
    • EcuM schaltet das Modul synchron via Icu_SetMode(ICU_MODE_SLEEP) in den Schlafmodus.
  4. Ereignisverarbeitung im ICU_MODE_SLEEP:
    • Fallende Flanke an Channel #1 (nicht wakeup-fähig, Notification aktiv):
      • Das Signal wird verworfen bzw. erzeugt keinen Callback: Im ICU_MODE_SLEEP sind reguläre Signal-Notifications für nicht wakeup-fähige Kanäle normativ unterdrückt/inaktiv.
    • Steigende Flanke an Channel #2 (wakeup-fähig, Notification inaktiv):
      • Hardware erkennt Flanke als Aufwachgrund.
      • Treiber meldet an EcuM: EcuM_CheckWakeup(Channel#2).
      • EcuM fragt Treiber synchron zur Verifikation ab: Icu_Cbk_CheckWakeup(Channel#2) (bzw. Icu_CheckWakeup).
      • Treiber bestätigt valides Aufwachen an EcuM: EcuM_SetWakeupEvent(Channel#2).
      • Es erfolgt kein Aufruf von Icu_SignalNotification_Channel2(), da die Notification vor dem Sleep-Übergang explizit deaktiviert wurde und im Sleep-Modus ohnehin keine Standard-Signalbenachrichtigungen zugestellt werden.

4. Normative Relevanz & Entwickler-Hinweise

  • Trennung von Wakeup und Notification: Die Flankenbenachrichtigung (Icu_EnableNotification) und die Wakeup-Funktionalität (Icu_EnableWakeup) sind zwei orthogonale Steuerpfade im ICU-Treiber. Das Aktivieren eines Wakeup-Events führt im Sleep-Modus nicht automatisch zur Ausführung von Applikations-Callbacks.
  • Verhalten von Icu_SetMode(ICU_MODE_SLEEP):
    • Im Schlafmodus werden per Spezifikation (AUTOSAR SWS ICU) alle Interrupts deaktiviert oder so umkonfiguriert, dass ausschließlich wake-up-fähige Kanäle als Wakeup-Interrupts fungieren.
    • Nicht wakeup-fähige Kanäle verharren im Ruhezustand; ankommende Flanken werden ignoriert und generieren keine Icu_SignalNotification-Aufrufe.
  • Integrations- und Konfigurationspflichten:
    • Parameter IcuWakeupCapability: Muss für Kanäle, die das Steuergerät wecken sollen, statisch im Pre-Compile/Post-Build konfiguriert sein.
    • Pre-Sleep-Sequenz der Applikation: Sollen nach dem Aufwachen keine veralteten Flankenbenachrichtigungen verzögert verarbeitet werden, muss die Applikation vor Aufruf von Icu_SetMode(ICU_MODE_SLEEP) kritische Kanäle via Icu_DisableNotification() sperren.
    • Handshake mit EcuM: Bei gesetztem IcuReportWakeupSource = STD_ON ist zwingend die Callback-Kette über EcuM_SetWakeupEvent bzw. EcuM_CheckWakeup / Icu_CheckWakeup einzuhalten, um die EcuM-Zustandsmaschine aus dem Sleep-Zustand kontrolliert aufzuwecken.
