1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: AUTOSAR M2-Metamodell (UML-Klassendiagramm mit AUTOSAR-spezifischen Stereotypen wie «atpVariation» und «atpSplitable»).
  • Technischer Zweck & Einordnung:
    • Das Metamodell definiert den Übergang vom abstrakten Architektur-Entwurf eines Software-Components (SwcInternalBehavior) zum konkreten Code-Artefakt und dessen Kompilierungsanforderungen (SwcImplementation).
    • Die abstrakte Basisklasse Implementation (spezialisiert von ARElement) wird gemeinsam von der Software Component Template (TPS_SWCT) und der Basic Software Module Description Template (TPS_BSWMDT) genutzt. Das vorliegende Teildiagramm isoliert die SWC-spezifische Spezialisierung SwcImplementation.
    • Funktionale Rolle: Bindeglied für Generatoren, Build-Toolchains und den RTE-Generator zur Auflösung von Code-Deskriptoren, Ressourcenbedarfen (RAM/ROM) und compilerspezifischen Flags.

2. Komponenten, Entitäten & Schnittstellen

Metaklassen & Attribute
  • Implementation (abstrakt, Kind von ARElement):
    • programmingLanguage : ProgramminglanguageEnum (z. B. C, C++).
    • swVersion : RevisionLabelString (Software-Versionsnummer der Implementierung).
    • usedCodeGenerator : String [0..1] (Bezeichnung des Code-Generators, z. B. Simulink/TargetLink).
    • vendorId : PositiveInteger (AUTOSAR-Hersteller-ID).
  • SwcImplementation (konkrete Spezialisierung von Implementation):
    • requiredRTEVendor : String [0..1] (Beschränkung auf einen proprietären RTE-Vendor, falls vendor-spezifische RTE-APIs vorausgesetzt werden; optional).
  • ResourceConsumption (erbt von Identifiable):
    • Modelliert den statischen/dynamischen Speicher- und Laufzeitbedarf (RAM, ROM, Stack).
  • Code (erbt von Identifiable):
    • Referenziert oder kapselt physische Source-/Objektcode-Dateien (codeDescriptor).
  • DependencyOnArtifact (erbt von Identifiable):
    • Kapselt Build- und Werkzeugabhängigkeiten.
  • Compiler (erbt von Identifiable):
    • Spezifiziert die qualifizierte Toolchain: name : String, options : String, vendor : String, version : String.
  • PerInstanceMemorySize:
    • Beschreibt den Speicherbedarf von PIM-Instanzen (Per-Instance Memory):
      • alignment : PositiveInteger (Byte-Alignment für den Allokator).
      • +size : PositiveInteger (unterliegt «atpVariation», vh.latestBindingTime = preCompileTime).
  • SwcInternalBehavior (Spezialisierung von InternalBehavior):
    • Modelliert das Komponentenverhalten (Runnables, Events, RTE-APIs).
Relationen, Kardinalitäten & Stereotypen
  • Vererbung: SwcImplementation → Implementation.
  • Assoziationen von Implementation:
    • +resourceConsumption : ResourceConsumption [1] (Komposition, Stereotyp «atpSplitable» – erlaubt die Aufteilung der Definition über mehrere ARXML-Dateien).
    • +codeDescriptor : Code [1..*] (Komposition; mindestens ein Code-Deskriptor zwingend).
    • +requiredGeneratorTool : DependencyOnArtifact [0..*] (Komposition, «atpVariation», Latest Binding Time: preCompileTime).
    • +requiredArtifact : DependencyOnArtifact [0..*] (Komposition, «atpVariation», Latest Binding Time: preCompileTime).
    • +generatedArtifact : DependencyOnArtifact [0..*] (Komposition, «atpVariation», Latest Binding Time: preCompileTime).
    • +compiler : Compiler [0..*] (Komposition; zulässige/getestete Compiler-Sets).
  • Assoziationen von SwcImplementation:
    • +behavior : SwcInternalBehavior [1] (Unidirektionale Referenz; jede SwcImplementation gehört exakt zu einem internen Verhalten).
    • +perInstanceMemorySize : PerInstanceMemorySize [0..*] (Komposition, «atpVariation», Latest Binding Time: preCompileTime).

3. Dynamisches Verhalten & Sequenzablauf

Da es sich um ein statisches Daten-/Metamodell handelt, existieren keine klassischen Laufzeit-Nachrichtenfolgen. Der Prozessablauf greift auf Toolchain- und Generatorebene:

  1. Entwurfsbindung: Ein AtomicSoftwareComponentType instanziiert ein SwcInternalBehavior.
  2. Implementierungszuordnung: Die SwcImplementation wird über die 1-zu-1-Referenz +behavior an das SwcInternalBehavior gebunden.
  3. Variabilitätsauflösung (Pre-Compile Time): Sämtliche mit «atpVariation» annotierten Pfade (perInstanceMemorySize, Artefakt-Abhängigkeiten) werden anhand von System-Switches/Post-Build-Kriterien spätestens zur Vorkompilierzeit statisch ausgewertet und fixiert.
  4. Code- und RTE-Generierung:
    • Der RTE-Generator liest SwcImplementation, prüft requiredRTEVendor und erzeugt RTE-Header/Datenstrukturen (u. a. Instanzdeskriptoren für PIMs gemäß PerInstanceMemorySize.size und alignment).
    • Die Toolchain verifiziert codeDescriptor und Compiler-Optionen (Compiler.options) für die finale Übersetzung in die Zielarchitektur-Binärdatei.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE-Interoperabilität (requiredRTEVendor): Fehlt dieses Attribut (Standard), muss der generierte SWC-C-Code portabel über standardisierte AUTOSAR-RTE-Schnittstellen übersetzbar sein. Ist ein Vendor eingetragen, bindet sich die Implementierung an herstellerspezifische Erweiterungen des RTE-Generators.
  • Per-Instance Memory (PIM) Handling:
    • Der Entwickler/Integrator muss sicherstellen, dass die im ARXML deklarierten PIM-Größen (size) und Alignment-Vorgaben exakt mit den im C-Code verwendeten Strukturen (typedef struct) übereinstimmen.
    • Falsche Alignments führen auf Architekturen mit striktem Speicher-Alignment (z. B. ARM Cortex-M/R, TriCore) zu Alignment-Traps oder Padding-Fehlern im RTE-Instanzspeicher.
  • Dateiaufteilung durch «atpSplitable»: Das ResourceConsumption-Element kann getrennt von der primären SWC-Beschreibung geliefert werden (z. B. durch Messwerkzeuge oder Linker-Mapfile-Extraktoren nach dem Build), ohne die SwcImplementation-Basisdatei zu modifizieren.
  • Bindungszeit preCompileTime: Dynamische Größenanpassungen von Artefakten oder PIMs zur Link-Time oder Post-Build-Time sind normativ ausgeschlossen. Alle Varianzen müssen vor dem Übersetzen des C-Quellcodes deterministisch aufgelöst sein.
