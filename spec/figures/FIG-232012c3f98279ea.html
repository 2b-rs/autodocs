1. Diagrammtyp & Architektur-Kontext

UML-Zustandsdiagramm (stm CanNmAlgorithm) zur Spezifikation des Zustandsautomaten des AUTOSAR CAN Network Management (CanNm). Als Bestandteil des Communication Stacks (Services Layer) steuert das Modul CanNm das koordinierte Wecken, Wachhalten und Herunterfahren des CAN-Netzwerks basierend auf dem dezentralen AUTOSAR-NM-Algorithmus. Es interagiert hierbei vertikal mit dem generischen Netzwerkmanagement-Interface (Nm) nach oben sowie dem CAN Interface (CanIf) nach unten.

2. Komponenten, Entitäten & Schnittstellen

Das Diagramm definiert drei Hauptbetriebszustände/-modi sowie Subzustände und Transitionsbedingungen:

  • Zustände / Modi:
    • Bus-Sleep Mode: Ruhezustand des Busses bei minimalem Stromverbrauch.
    • Prepare Bus-Sleep Mode: Pufferzustand vor dem Übergang in den Bus-Sleep-Modus.
    • Network Mode (Composite State): Aktiver Netzwerkbetrieb, unterteilt in:
      • Repeat Message State: Initialer Zustand im Network Mode, Entry-Aktion CanNm_StopBusLoadReduction().
      • Normal Operation State: Zustand bei aktiver Kommunikationsanforderung des Knotens, Entry-Aktion CanNm_StartBusLoadReduction().
      • Ready Sleep State: Zustand bei freigegebener Netzwerkkommunikation (Network Released), in dem der Knoten passiv auf das Einschlafen des Busses wartet.
    • Pseudo-Zustände: Startzustand (PowerOn), Endzustand (PowerOff), zwei Verzweigungsknoten (Junctions: Network Mode, Repeat Message).
  • Funktions- und Callback-Schnittstellen:
    • Eingehende API- und Treiberaufrufe: CanNm_Init(), CanNm_NetworkRequest(), CanNm_PassiveStartUp(), CanNm_NetworkRelease(), CanNm_RxIndication(), CanNm_TxConfirmation(), CanNm_RepeatMessageRequest().
    • Ausgehende Aufrufe / Callbacks an Nm: Nm_NetworkMode(), Nm_NetworkStartIndication(), Nm_PassiveStartUp(), Nm_PrepareBusSleepMode(), Nm_BusSleepMode(), Nm_NetworkTimeoutException(), Nm_TxTimeoutException().
    • Interne Treiber-/Sende-Aktionen: CanNm_StartTransmission(), CanNm_StopTransmission(), CanNm_TriggerTransmission(), CanNm_StartBusLoadReduction(), CanNm_StopBusLoadReduction(), CanNm_RepeatMessageBitIndication().
  • Timer:
    • NM-Timeout Timer: Überwachung des zyklischen Empfangs/Sendens von NM-Botschaften.
    • Repeat Message Timer: Bestimmt die Verweildauer im Repeat Message State.
    • Wait Bus-Sleep Timer: Verzögerungszeit im Prepare Bus-Sleep Mode.
    • Tx Timeout Timer: Überwachung der Übertragungsbestätigung für gesendete NM-PDUs.

3. Dynamisches Verhalten & Sequenzablauf

Der Zustandsablauf gliedert sich in folgende Pfade und Transitionen:

  1. Initialisierung & Hochlauf:
    • Von PowerOn führt CanNm_Init() mit der Aktion Initialization of CanNm in den Bus-Sleep Mode.
    • Ein Verlassen des Bus-Sleep Mode erfolgt entweder passiv über CanNm_RxIndication() (Aktion: Nm_NetworkStartIndication() und Nm_PassiveStartUp()) oder aktiv über CanNm_NetworkRequest bzw. CanNm_PassiveStartUp. Beide Pfade führen über den Junction-Point Network Mode in den Repeat Message State.
    • Bei Eintritt in den Network Mode aus dem Ruhezustand werden Start NM-Timeout Timer, Start Repeat Message Timer, Nm_NetworkMode() und CanNm_StartTransmission() ausgeführt.
    • Aus dem Prepare Bus-Sleep Mode führt CanNm_NetworkRequest() mit sofortigem CanNm_TriggerTransmission() sowie Starten der Timer direkt in den Repeat Message State; CanNm_RxIndication() bzw. CanNm_PassiveStartUp führen über den Junction-Point Network Mode dorthin.
  2. Abläufe innerhalb des Network Mode:
    • Im Repeat Message State bleibt der Knoten für die Dauer des Repeat Message Timer. Bei dessen Ablauf (Repeat Message Timer has expired;) verzweigt der Junction-Knoten Repeat Message abhängig von Guards:
      • [Network Requested]: Übergang in den Normal Operation State.
      • [Network Released]: Übergang in den Ready Sleep State unter Ausführung von CanNm_StopTransmission().
    • Zwischen Normal Operation State und Ready Sleep State schalten Aufrufe von CanNm_NetworkRelease(); / CanNm_StopTransmission(); bzw. CanNm_NetworkRequest(); / CanNm_StartTransmission(); hin und her.
    • Ein wiederholtes Anfordern der Repeat-Message-Phase aus Normal Operation State oder Ready Sleep State erfolgt über CanNm_RepeatMessageBitIndication() || CanNm_RepeatMessageRequest(), was den Repeat Message Timer neu startet, CanNm_StartTransmission() ausführt und in den Repeat Message State wechselt.
    • Botschaftsempfang (CanNm_RxIndication()) oder Sendeerfolg (CanNm_TxConfirmation()) setzen im Network Mode den NM-Timeout Timer zurück (Start NM-Timeout Timer;).
    • Ein Timeout im Normal Operation State (NM-Timeout Timer has expired / Start NM-Timeout Timer;) startet den Timer neu. Im Repeat Message State meldet ein NM-Timeout zusätzlich Nm_NetworkTimeoutException().
    • Tritt ein Tx-Timeout auf (Tx Timeout Timer has expired), wird Nm_TxTimeoutException() ausgelöst.
  3. Abschaltpfad:
    • Läuft im Ready Sleep State der NM-Timeout Timer ab, wechselt der Automat in den Prepare Bus-Sleep Mode (Aktionen: Start Wait Bus-Sleep Timer; Nm_PrepareBusSleepMode();).
    • Läuft dort der Wait Bus-Sleep Timer ab (Wait Bus-Sleep Timer has expired), wird Nm_BusSleepMode() aufgerufen und der Bus-Sleep Mode eingenommen.
    • Aus dem Bus-Sleep Mode kann über PowerOff abgeschaltet werden.

4. Normative Relevanz & Entwickler-Hinweise

Normativ definiert der Automat die verbindliche Zustandslogik des CanNm-Moduls gemäß AUTOSAR 3.2:

  • Das Senden von NM-Botschaften (CanNm_StartTransmission()) ist ausschließlich im Repeat Message State und im Normal Operation State aktiv; im Ready Sleep State ist das Senden immer über CanNm_StopTransmission() deaktiviert.
  • CanNm_TriggerTransmission() wird explizit beim Verlassen des Prepare Bus-Sleep Mode durch CanNm_NetworkRequest() gefordert, um eine sofortige Busaktivierung ohne Verzögerung sicherzustellen.
  • Buslastreduktion (CanNm_StartBusLoadReduction() / CanNm_StopBusLoadReduction()) ist zustandsspezifisch an den Eintritt in den Normal Operation State bzw. Repeat Message State gekoppelt.
  • Alle Timeout-Ausnahmen (Nm_NetworkTimeoutException, Nm_TxTimeoutException) müssen unverzüglich an das übergeordnete Interface Nm gemeldet werden.
  • Fehlerbehandlung für fehlgeschlagene Transitionen oder unzulässige API-Aufrufe ist im Zustandsdiagramm abstrahiert und erfordert im Implementierungscode entsprechende Guards und Zustandsprüfungen gemäß den begleitenden SWS-Anforderungs-IDs.
