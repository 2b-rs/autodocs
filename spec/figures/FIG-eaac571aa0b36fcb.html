1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Physisches und logisches Allokationsdiagramm (Deployment- und Komponentenarchitektur) kombiniert mit einer PDU-/Protokoll-Frame-Struktur.
  • Architektur-Kontext: AUTOSAR Foundation Protocol Specification V2X Remote Access Layer (PRS_V2XRemoteAccessLayer; gültig für R22-11 bis R25-11).
  • Technischer Zweck: Spezifikation einer verteilten V2X-Systemarchitektur (Distributed V2X Architecture). Das Diagramm definiert die Entkopplung der oberen V2X-Protokollschichten (Facilities, Transport, Network) auf einem zentralen Verarbeitungs-Steuergerät von den funktechnischen Sende-/Empfangseinheiten (Access Layer, RF-Frontend, Smart Antenna/NAD) auf einem abgesetzten Steuergerät. Der bidirektionale Transport von V2X-Nutzdaten und Steuermetadaten wird über ein fahrzeuginternes Ethernet-Netzwerk standardisiert.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten (ECUs und Netzwerkknoten)

  • AUTOSAR V2X ECU (Host / Compute Node):
  • Off-Board Communication Services: BSW-/Service-Ebene für externe Kommunikation.
  • V2X Stack: Host-seitiger Protokollstapel (Facilities Layer wie CAM, DENM; Network/Transport Layer wie GeoNetworking/BTP oder IPv6).
  • PRS V2x Remote Access Layer: Client-Instanz des V2xRAL-Protokolls zur Serialisierung/Deserialisierung von V2X-PDUs und Steuerbefehlen.
  • Communication HW abstraction: Abstraktionsschicht der Kommunikationshardware (im AUTOSAR-Classic-Stack z. B. EthIf, SoAd, TcpIp).
  • Communication Drivers: Hardwaretreiber (z. B. Eth, EthTrcv).
  • Switch/Router (optional):
  • Optionale L2-Switch- bzw. L3-Routing-Infrastruktur im Fahrzeugbordnetz zur Weiterleitung der Ethernet-Frames zwischen den Steuergeräten.
  • Remote Access Layer ECU (Target / Radio Unit / Smart Antenna):
  • Router/Gateway: Gateway-Funktion mit integriertem PRS V2x Remote Access Layer (Server-Instanz), welche die Steuerschnittstelle terminiert und Datenströme an den Funk-Stack routet.
  • Communication Driver: Ethernet-Controller- und Transceiver-Treiber zur Bordnetzanbindung.
  • Radio network Access Layer: Physische Schicht (PHY) und Medium Access Control (MAC) für den V2X-Direktfunk (z. B. ITS-G5 / IEEE 802.11p bzw. C-V2X PC5 / 3GPP Sidelink).
  • Antenne / RF-Frontend: Luftschnittstelle zur drahtlosen Fahrzeug-zu-X-Übertragung (Over-The-Air, OTA).

#### Schnittstellen & PDU-Layout (Ethernet message)

  • Physische Verbindung: Automotive Ethernet (z. B. 100BASE-T1 oder 1000BASE-T1, violette Buslinie).
  • Frame-Struktur:
  • V2xRAL Control Header (Metadaten-Container): Beinhaltet radio- und kanalspezifische Steuerungsparameter für Tx/Rx (u. a. Kanal-ID/Frequenzband, Sendeleistung, Modulations- und Codierschemata, Datenrate, Prioritäts-/Kanalzugriffsklasse, Antennen-Diversity-Index, RSSI/CBR-Feedback und Zeitstempel).
  • Payload (V2x message): Transparente Nutzdaten (z. B. unverschlüsselte oder gesicherte GeoNetworking-PDU bzw. BSM/CAM/DENM-PDU).

3. Dynamisches Verhalten & Sequenzablauf

#### Sende-Pfad (Tx-Sequenz)

  1. Trigger: Die V2X-Applikation generiert ein V2X-Event (z. B. CAM-Intervall oder DENM-Auslösung).
  2. Kapselung: Der V2X Stack übergibt die PDU an den clientseitigen PRS V2x Remote Access Layer. Dieser stellt den V2xRAL Control Header mit den geforderten Tx-Parametern bereit.
  3. Bordnetz-Transport: Asynchrone Übergabe über Communication HW abstraction und Communication Drivers an den Ethernet-Bus (L2/L3-Transport).
  4. Verarbeitung auf Radio-ECU: Der serverseitige PRS V2x Remote Access Layer parst den Header, konfiguriert die Funkparameter im Radio network Access Layer und übergibt die Payload (V2x message) an das RF-Modem zur Aussendung über die Antenne.
  5. Tx-Confirmation: Asynchrone Rückmeldung des Übertragungsstatus (inkl. Timestamping) über den RAL-Kanal zurück an den Host-Stack.

#### Empfangs-Pfad (Rx-Sequenz)

  1. Funkempfang: Der Radio network Access Layer empfängt ein OTA-Funkpaket über die Antenne.
  2. RAL-Header-Generierung: Das Gateway aggregiert Empfangsmetadaten (z. B. Empfangskanal, Signalgüte/RSSI, Timestamp, Antennenpfad) in den V2xRAL Control Header.
  3. Ethernet-Forwarding: Übertragung der Ethernet message via Switch/Router an die AUTOSAR V2X ECU.
  4. Host-Decodierung: Der Host-RAL-Treiber entpackt die Metadaten, signalisiert den Empfang an den V2X Stack und übergibt die Nutzlast zur Dekodierung und Sicherheitsprüfung.

#### Fehler- und Ausnahmebehandlung

  • Verbindungsabbruch / Link-Down: Überwachung des Ethernet-Links via AUTOSAR EthSM. Bei Paketverlust greifen Timeout-Mechanismen im V2xRAL-Client.
  • Diagnose: Bei ungültigen Header-Formaten, PDU-Längenfehlern oder Pufferüberläufen im Gateway werden DET-Fehler (DET_REPORT_ERROR) bzw. DEM-Events für fehlerhafte Remote-Kommunikation ausgelöst.

4. Normative Relevanz & Entwickler-Hinweise

  • Technologie-Agnostik des V2X-Stacks: Die Abstraktion via V2xRAL erlaubt es, den V2X-Host-Stack hardwareunabhängig von der Radio-Technologie (DSRC/IEEE 802.11p vs. C-V2X PC5) zu implementieren. Die technologiespezifische Ansteuerung erfolgt über die Felder des V2xRAL Control Header.
  • Latenz- und Echtzeitbudgets: V2X-Sicherheitsanwendungen (z. B. Notbremswarnung / EEBL) verlangen strikte Latenzgrenzen ($t_{\text{latency}} < 20\,\text{ms} - 100\,\text{ms}$). Der Ethernet-Übertragungspfad muss deterministisch ausgelegt sein (z. B. Einsatz von IEEE 802.1Q VLAN-Priorisierung, TSN / 802.1Qav), um Switch-Jitter zu minimieren.
  • Zeitsynchronisation: Zur validen Zeitstempelung (Generation Time, Certificate Expiry, Replay-Schutz) ist eine phasengenaue Zeitsynchronisation zwischen AUTOSAR V2X ECU und der meist GNSS-führenden Remote Access Layer ECU via gPTP (IEEE 802.1AS / AUTOSAR StbM) zwingend erforderlich.
  • Protokoll-Implementierung: Entwickler müssen den V2xRAL entweder direkt auf Ethernet-Layer 2 (eigener EtherType) oder gekapselt über UDP/IP konfigurieren (je nach Parametrisierung im PRS-Standard und BSW-Konfiguration im SoAd).
