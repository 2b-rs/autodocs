1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Prozess- und Artefaktfluss-Diagramm basierend auf SPEM 2.0 (Software & Systems Process Engineering Metamodel), adaptiert für die AUTOSAR-Methodik (TR Methodology, R4.0.3).
  • Architektur-Kontext: Phase „Develop an Atomic Software Component“ innerhalb der VFB-Ebene (Virtual Functional Bus).
  • Funktionaler Zweck: Formale Spezifikation der Work Products (ARXML-Beschreibungen und C-Header) und Aktivitäten zur Entwicklung einer atomaren Software-Komponente (SWC) im sogenannten RTE Contract Phase Mode. Ermöglicht die autarke C-Code-Implementierung der Runnable Entities unabhängig von ECU-Allokation, Buskommunikation und BSW-Konfiguration.

2. Komponenten, Entitäten & Schnittstellen

Aktivitäten (SPEM Activities / Process Tasks – Pentagon-Symbole)
  • Define Atomic Software Component Internal Behavior: Spezifiziert Runnable Entities, Events, PIM (Per-Instance Memory), IRV (Inter-Runnable Variables) und Server-Call-Punkte auf Basis der SWC-Port-Deklaration.
  • Define Software Component Timing: Erstellt Timing-Beschreibungen (VFB/SWC Timing Extensions wie Execution Time, Ausführungsperioden, Latenzen).
  • Generate Atomic Software Component Contract Header Files: Ausführung des RTE-Generators im Contract-Modus zur Erzeugung von API- und Typ-Headern.
  • Generate Component Prebuild Data Set: Extraktion und Generierung vorkompilierbarer Konfigurationsdaten zur Auflösung von Varianten auf Komponentenebene.
Work Products / Artefakte (SPEM Work Products – Dokumentensymbole) & Pakete
Eingangs- & Referenzmodelle (VFB- & Varianten-ARXML):
  • VFB AUTOSAR Standard Package [0..1] (Paket-/Brief-Symbol): Standardisierte AUTOSAR-Basisdefinitionen (z. B. Standardized AUTOSAR Interfaces/Data Types).
  • VFB Atomic Software Component [1]: Formale Software-Component-Type-Beschreibung (Ports, PortInterfaces, Component-Typ).
  • VFB Modes [0..*]: Modusdeklarationen (ModeDeclarationGroup, ModeSwitchInterface).
  • VFB Types [0..*]: Datentypdefinitionen (ApplicationDataType, ImplementationDataType, BaseType).
  • VFB Interfaces [0..*]: Schnittstellenbeschreibungen (SenderReceiverInterface, ClientServerInterface, ParameterInterface etc.).
  • VFB Data Type mapping Set [0..1]: Mapping-Regeln zwischen anwendungsbezogenen Datentypen (ApplicationDataType) und implementierungsspezifischen C-Typen (ImplementationDataType).
  • Postbuild Variant Set [0..1]: Konfigurationen und Kriterien für Post-Build-Varianten (PostBuildVariantCriterion).
  • System Constant Value Set [0..1 für Contract-Header / 1..* für Prebuild Data Set]: Festlegung von Werten für Systemkonstanten (SwSystemconstantValue) zur statischen Bedingungsauswertung (VariantCriterion).
  • Predefined Variant [0..* für Contract-Header / 0..1 für Prebuild Data Set]: Vordefinierte Schalterkombinationen zur Festlegung von Varianten.
Zwischen- & Ergebnisartefakte:

  • Software Component Timing [1]: AUTOSAR Timing Extension Modell (SwcTimingDescription).
  • Application Header File [1]: C-Header Rte_<SWC>.h (RTE-API-Prototypen/Makros für Port-Operationen, z. B. Rte_Read, Rte_Write, Rte_Call).
  • Software Component Data Types Header [1]: C-Header Rte_Type.h (C-Typedefs, Structs, Enums und Grenzwerte für die SWC).

3. Dynamisches Verhalten & Sequenzablauf

  1. Phase 1 – Verhaltensmodellierung:
    • Basierend auf der SWC-Port-Architektur (VFB Atomic Software Component) wird Define Atomic Software Component Internal Behavior ausgeführt.
    • Ergebnis: Erzeugung des Software Component Internal Behavior (definiert, welche C-Funktionen/Runnables bei welchen RTE-Events getriggert werden).
  2. Phase 2 – Parallele Modellerweiterung & Artefaktgenerierung (Design-Time Tools):
    • Timing-Pfad: Define Software Component Timing konsumiert das interne Verhalten und instanziiert Timing-Constraints/Events (Software Component Timing).
    • Contract-Header-Pfad: Der RTE-Generator verarbeitet im Contract-Modus das Software Component Internal Behavior zusammen mit allen relevanten VFB-Typen, Interfaces, Mapping-Sets und Varianten-Parametern.
    • Ergebnis: Generierung der C-Header Rte_<SWC>.h und Rte_Type.h.
    • Prebuild-Konfigurations-Pfad: Parallele Generierung des Component RTE Prebuild Configuration Header unter Einbindung bindungsrelevanter Daten (Postbuild Variant Set, System Constant Value Set).

4. Normative Relevanz & Entwickler-Hinweise

  • RTE Contract Phase vs. Generation Phase: Die erzeugten Header Rte_<SWC>.h und Rte_Type.h stellen ausschließlich den C-Funktionsvertrag (Contract) dar. APIs wie Rte_Read_<port>_<data>() oder Rte_Call_<port>_<operation>() sind hier nur deklariert (als Prototyp oder Inline-Stumpf). Der SWC-Entwickler kompiliert seine C-Implementierung gegen diese Header; Linken gegen die echte RTE ist erst nach der ECU-spezifischen RTE Generation Phase möglich.
  • Typ-Entkopplung via Mapping Set: Bei Einsatz von ApplicationDataType ist das Vorhandensein des VFB Data Type mapping Set zwingend erforderlich, damit der RTE-Generator im Contract-Header valide C-Typen (ImplementationDataType) erzeugen kann.
  • Varianten-Handhabung (Prebuild): Systemkonstanten (SwSystemconstantValue) steuern im Contract-Modus Präprozessorschalter (#if, #ifdef). SWC-Entwickler müssen sicherstellen, dass die C-Quelltexte der Runnables dieselben Präprozessorschalter verwenden, die über den Component RTE Prebuild Configuration Header bereitgestellt werden.
  • Invarianz des C-Codes: Jede Änderung am VFB Interfaces, VFB Types oder SwcInternalBehavior erzwingt die erneute Durchführung der Aktivität Generate Atomic Software Component Contract Header Files und zieht typischerweise Signaturanpassungen in den Runnable-Funktionen des C-Entwicklers nach sich.
