1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: System- und Testarchitekturdiagramm / Schichtenmodell (Hardware, OS/POSIX, Middleware, Functional Clusters, ARA, Applikationsebene) für verteilte Integrations- und Systemtests.
  • Technischer Zweck: Spezifikation des Validierungs- und Testaufbaus für die Diagnose-Infrastruktur (ara::diag, ISO 13400 / DoIP, ISO 14229 / UDS) der AUTOSAR Adaptive Platform (AP) über vernetzte Multi-ECU-Knoten hinweg, orchestriert durch ein CI/CD-basiertes Testsystem (Jenkins).

2. Komponenten, Entitäten & Schnittstellen

Das Setup gliedert sich in zwei identisch geschichtete Prüflinge (ECU1, ECU2) sowie einen Test-Controller (Jenkins):

  • ECU1 & ECU2 (Adaptive Platform Nodes):
  • DIAG Test Application(s): Adaptive Applications (AA) im User-Space zur Verifikation von Diagnose-Services (z. B. DataIdentifier-, RoutineControl- und Fault-Memory-Handler).
  • ARA (AUTOSAR Runtime for Adaptive Applications): Normative C++ API-Schicht (ara::diag, ara::com), über welche Applikationen angebunden werden.
  • Diagnostic Manager (DM): Zentraler Daemon / Functional Cluster der Adaptive Platform. Terminiert DoIP (TCP/UDP-Port 13400) und UDS, verwaltet Session-States, Security Access und das Error Memory; routet UDS-Payloads via lokaler IPC an die entsprechenden ara::diag-Instanzen.
  • vSomeIP: SOME/IP-Stack (Referenzimplementierung für Adaptive Middleware-Kommunikation) zur serviceorientierten Inter-ECU-Kommunikation.
  • POSIX libs (libc, ...): PSE51/PSE52-kompatible POSIX-Laufzeitbibliothek (Pthreads, Sockets, IPC).
  • Linux with Real-time Patches: Betriebssystemkern mit PREEMPT_RT-Patch als deterministischer POSIX-OS-Unterbau.
  • Hardware: Physikalische Ziel-Hardware mit Ethernet-Controllerschnittstellen.
  • Jenkins Node (Automated Test Host):
  • DIAG Tester: Automatisierte Diagnose-Testsuite / UDS-over-IP-Client zur Testvektorinjektion und Auswertung.
  • Jenkins: CI/CD-Automatisierungsframework zur Steuerung der Testsequenzen und Verdict-Generierung.
  • Linux & PC: Standard-Linux-Hostplattform auf x86_64-PC-Basis.
  • Schnittstellen & Verbindungswege (gestrichelte rote Linien):
  • DoIP / UDS (Diagnostic Tester $\leftrightarrow$ ECU1 / ECU2): Punkt-zu-Punkt-Ethernet-Verbindungen vom Test-Host über PC-Hardware direkt zu den Ethernet-Interfaces der ECUs, terminiert im jeweiligen Diagnostic Manager.
  • SOME/IP (ECU1 $\leftrightarrow$ ECU2): Physische Ethernet-Verbindung zwischen ECU1 und ECU2 zur serviceorientierten Kommunikation über vSomeIP.

3. Dynamisches Verhalten & Sequenzablauf

  1. Initialisierung & Discovery:
  • Nach dem Hochfahren der ECUs starten POSIX-Prozesse (Diagnostic Manager, vSomeIP, DIAG Test Application(s)).
  • Der Diagnostic Tester initiiert DoIP Vehicle Identification (UDP) und baut eine DoIP Routing Activation (TCP-Handshake) mit dem Diagnostic Manager von ECU1 bzw. ECU2 auf.
  1. Injektion von Diagnose-Anfragen (Test Trigger):
  • Jenkins / DIAG Tester feuert UDS-Requests (z. B. 0x22 ReadDataByIdentifier, 0x2E WriteDataByIdentifier, 0x31 RoutineControl) gekapselt in DoIP-Nachrichten an ECU1.
  1. Lokales Dispatching (ECU-intern):
  • Der Diagnostic Manager parst den DoIP-Header, validiert Session und Security-Level und leitet die UDS-Payload über IPC/ARA synchron oder asynchron an die registrierten Handler der DIAG Test Application(s) weiter.
  1. Verteilte Interaktion & Cross-ECU-Verifikation:
  • Zur Verifikation verteilter Diagnose- oder Fehlerspeichereffekte löst die Test-Applikation auf ECU1 über ara::com / vSomeIP einen Service-Call auf ECU2 aus.
  • ECU2 generiert interne Zustandsänderungen oder DTC-Events, die wiederum über den Diagnostic Manager von ECU2 abgefragt werden können.
  1. Ergebnisrückführung (Verdict):
  • Positive Response (0x6x) oder Negative Response (0x7F) läuft vom Diagnostic Manager via DoIP zurück an den DIAG Tester. Jenkins wertet die Rückgabewerte und DTC-Stände gegen die Testerwartung aus.

4. Normative Relevanz & Entwickler-Hinweise

  • Kapselung des Netzwerk-Stacks: Applikationsentwickler implementieren weder DoIP-Sockets noch ISO-14229-Parser. Der API-Vertrag erfolgt ausschließlich über ara::diag-Klassen (ara::diag::GenericDataIdentifier, ara::diag::Routine, etc.).
  • Manifest-Modellierung: Das Routing zwischen DoIP Logical Addresses, UDS-DIDs und den C++ Callback-Objekten der Applikation muss im Diagnostic Execution Manifest und Service Instance Manifest exakt modelliert sein (ARXML-Binding).
  • Parallele Protokollkoexistenz: Auf Treiberebene (Linux-Netzwerkstack) müssen DoIP (Port 13400) und SOME/IP (üblicherweise Port 30490 ff.) koexistieren. Für Integratoren ist sicherzustellen, dass QoS-, VLAN- oder Firewall-Konfigurationen (z. B. iptables) weder DoIP-Broadcasts/Unicasts noch SOME/IP-SD-Multicasts blockieren.
  • HIL/SIL-Eignung: Der Aufbau eignet sich für Software-in-the-Loop (SIL) mit virtuellen Ethernet-Bridges (veth) sowie hardwarebasierte Prüfstände (HIL) mit echter PHY-Anbindung.
