1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Konzeptionelles Schichten- und Transformationsmodell (Metamodell-Mapping-Ablauf) gemäß der AUTOSAR Methodology (AUTOSAR_AP_TR_Methodology).
  • Technischer Zweck & Einordnung:
    • Visualisiert den normativen Top-Down-Entwurfsprozess von einer plattformagnostischen Fahrzeug-Funktionsarchitektur (Function Architecture) über eine abstrakte Komponentenspezifikation (Abstract Platform Specification) hin zu einer heterogenen Gesamtfahrzeug-Softwarearchitektur (Vehicle Software Architecture).
    • Beschreibt den methodischen Übergang von logischen Funktionsanforderungen zur konkreten Technologieallokation auf die AUTOSAR Adaptive Platform (AP), die AUTOSAR Classic Platform (CP) sowie Non-AUTOSAR-Systeme.
    • Dient als Referenzmodell zur Beherrschung heterogener E/E-Architekturen (z. B. HPC/Zonensteuergeräte-Topologien) und definiert die Notwendigkeit von Schnittstellen- und Protokoll-Transformationen (Signal-to-Service Translation).

2. Komponenten, Entitäten & Schnittstellen

Das Modell gliedert sich in drei vertikale Abstraktionsebenen und eine horizontale Technologiepartitionierung:

Ebene 1: Function Architecture (Funktionale Ebene)
  • Vehicle Functions (A, B, C, D): Logische Fahrzeugfunktionen hoher Abstraktionsstufe (z. B. Antriebsstrang-, ADAS- oder Komfortfunktionen).
  • Function Blocks (A.1, A.2, B.1, B.2, C.1, C.2, D.1, D.2): Dekomponierte, atomare Funktionseinheiten innerhalb einer Vehicle Function.
  • Funktionale Ports & Connectors: Plattformneutrale logische Interaktionsbeziehungen zwischen den Fahrzeugfunktionen (A ↔ C, A ↔ B, B ↔ D, C ↔ D).
Ebene 2: Abstract Platform Specification (Abstrakte VFB-Ebene)
  • Abstract SWC (1 bis 7): Plattformunabhängige Software-Komponenten (SwComponentType), noch ohne Festlegung auf C- (Classic) oder C++-Laufzeitumgebungen (Adaptive).
  • Mappierungsbeziehungen (Funktionsblock → Abstract SWC):
    • 1:1-Allokation: A.1 → SWC 1; A.2 → SWC 5; B.1 → SWC 6; C.2 → SWC 3; D.1 → SWC 4; D.2 → SWC 7.
    • N:1-Konsolidierung: B.2 und C.1 werden in einer gemeinsamen Komponente konsolidiert (B.2, C.1 → abstract SWC 2).
  • Abstrakte Ports & Assemblierungs-Konnektoren: Logische Kopplung von P-/R-Ports über virtuelle Funktionsbus-Semantik (VFB), unabhängig vom Übertragungsmedium.
Ebene 3: Vehicle Software Architecture (Plattform-Allokation)
  • AUTOSAR Adaptive Platform (adaptive SWC 1, 5, 6):
    • Realisierung als Adaptive Applications (POSIX-Prozesse, C++14/17, C++20).
    • Ausführung auf performanten Mikroprozessoren (MPU / OS).
  • AUTOSAR Classic Platform (classic SWC 2, 3, 4):
    • Realisierung als atomare Classic SW-Cs (AtomicSwComponentType, C-Code, OSEK/AUTOSAR OS Tasks).
    • Ausführung auf harten Echtzeit-Mikrocontrollern (MCU / μC).
  • Non-AUTOSAR Domain (non-AUTOSAR SWC 7):
    • Drittanbieter-Stacks, Linux/Android-Subsysteme, Cloud/Off-Board-Dienste oder proprietäre Steuergeräte.
  • Kommunikationsmuster & Protokolle:
    • Service-oriented communication: Inter-SWC-Kommunikation innerhalb der Adaptive Platform (SWC 5 \leftrightarrow SWC 6) via ara::com (SOA, typischerweise SOME/IP, DDS oder Shared-Memory IPC).
    • Signal-based communication: Statische, PDU-basierte Kommunikation innerhalb der Classic Platform (SWC 2 \leftrightarrow SWC 4, SWC 3 \leftrightarrow SWC 4) via Classic RTE und BSW-Com-Stack (CAN, LIN, FlexRay).
    • Signal / Service translation: Heterogener Gateway-Pfad zwischen Adaptive und Classic (adaptive SWC 1 \leftrightarrow classic SWC 3).
    • External communication: Anbindung von classic SWC 4 an non-AUTOSAR SWC 7 über standardisierte oder proprietäre externe Busse/Schnittstellen.

3. Dynamisches Verhalten & Sequenzablauf

[Vehicle Software Architecture: AP / CP / Non-AUTOSAR]
  1. Transformationsschritt 1 (Funktion → Abstrakt):
    • Strukturelle Zerlegung der Systemanforderungen in funktionale Blöcke.
    • Komponenten-Clustering: Zusammenführung funktional verwandter Blöcke (z. B. B.2 + C.1) zu wiederverwendbaren Komponenten (abstract SWC 2) zur Optimierung von Kohäsion und Schnittstellenkomplexität.
  2. Transformationsschritt 2 (Abstrakt → Konkret):
    • Bewertung nicht-funktionaler Anforderungen (ASIL, Latenz, Durchsatz, Dynamik, Update-Fähigkeit).
    • Allokationsentscheidung:
      • Hohe Rechenleistung, variable Datenraten, dynamische Bindung → Adaptive Platform.
      • Deterministische Steuerungszyklen, $\mu\text{s}$-Echtzeit, Fail-Operational → Classic Platform.
      • Extern/Legacy → Non-AUTOSAR.
  3. Laufzeit-Dynamik der Kommunikationspfade:
    • SOA-Pfad (Adaptive): Dynamische Dienstsuche (FindService), Skeleton/Proxy-Instanziierung, asynchrones Publish/Subscribe (Events), synchrones/asynchrones Request/Response (Methods) oder Zustandsübertragung (Fields).
    • Signal-Pfad (Classic): Statisch konfigurierte RTE-Puffer, zyklische/eventgetriebene Übertragung via Com_SendSignal / Com_ReceiveSignal und PDU-Router (PduR).
    • Signal-to-Service-Bridge:
      • Empfangsrichtung (CP ← AP): Service-Event wird empfangen, via SOME/IP-Transformer / Gateway deserialisiert und in Classic-Signale/PDUs zerlegt, die via RTE an classic SWC 3 übergeben werden.
      • Senderichtung (AP ← CP): Signale der Classic Platform werden aggregiert, serialisiert und als SOME/IP-Payload/Service-Event an adaptive SWC 1 publiziert.

4. Normative Relevanz & Entwickler-Hinweise

  • ARXML-Modellierung & Metamodell-Artefakte:
    • Abstrakte Schnittstellen müssen im AUTOSAR-Systemmodell zunächst typisiert werden (PortInterface).
    • Für den CP/AP-Übergang sind SignalServiceTranslationProps bzw. SignalToServiceEventMapping im System-Description-Manifest zwingend erforderlich.
    • Trennung von Schnittstellendefinition (ServiceInterface / SenderReceiverInterface) und Deployment-Manifesten (SomeipServiceInterfaceDeployment, CanSignal, ComSignal).
  • Auswirkungen auf Applikationsentwickler:
    • Adaptive SWC (ara::*): Implementierung gegen die C++-Standardbibliothek und Adaptive-Plattform-APIs (ara::com, ara::exec). Keine Kenntnis über Classic-PDU-Layouts erforderlich; die Interaktion erfolgt strikt über typisierte Proxies/Skeletons.
    • Classic SWC (Rte_*): Implementierung gegen standardisierte C-RTE-APIs (Rte_Read_*, Rte_Write_*, Rte_Call_*). Keine native direkte SOA-Verbindung; Signalumsetzung erfolgt transparent in der BSW oder einem dedizierten Gateway-Modul.
  • Auswirkungen auf Stack- & Integrationsentwickler:
    • Gateway-Konfiguration: Beim Pfad SWC 1 \leftrightarrow SWC 3 muss ein Mapping-Modul (z. B. Classic BSW SomeIpXf / PduR / SoAd oder ein AP-seitiger Signal-Gateway-Service) konfiguriert werden. Serialisierungs-Overheads, Endianness, Data-Type-Mappings (z. B. IEEE 754 Floats, feste Integertypen vs. variable Arrays) und Latenzbudgets müssen exakt parametriert werden.
    • Timing- & Synchronisations-Constraints: Während Classic auf festen Task-Ablaufplänen (RTE-Events, OS-Alarme) basiert, läuft Adaptive ereignisgesteuert und prioritätsbasiert im POSIX-OS. Bei Cross-Platform-Verbindungen müssen Timeouts, Jitter und Verlustabsicherungen (z. B. E2E-Protection Profile via E2E-Transformer) normkonform ausgelegt werden.
