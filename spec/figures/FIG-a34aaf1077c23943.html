1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: UML-Zustandsdiagramm (State Machine Diagram) / Erweitertes Task-Zustandsmodell (Enhanced Task State Diagram, Modellbezeichner: AR_CP_OSARTI_TASK).
  • Funktionale Einordnung: Definiert im Standard AUTOSAR CP EXP ARTI (AUTOSAR Run-Time Interface). Es erweitert das klassische 4-Zustände-Modell der OSEK/AUTOSAR-OS-Spezifikation (SUSPENDED, READY, RUNNING, WAITING) für Timing-Analyse, Tracing und Debugging.
  • Technischer Zweck: Aufspaltung des monolithischen OS-Zustands READY in drei distinkte Sub-Zustände (Activated, Preempted, Released). Dadurch können Trace- und Profiling-Tools (z. B. ASAM ARTI/OTM) Latenzzeiten, Verdrängungsdauern und Event-Verzögerungen deterministisch erfassen.

2. Komponenten, Entitäten & Schnittstellen

  • Zustände (Entitäten einer Extended Task):
    • Suspended: Task ist passiv, beendet oder noch nicht instanziiert; keine Allokation von Scheduler-Ressourcen.
    • Activated: Task wurde neu aktiviert, befindet sich in der Ready-Queue des Schedulers, hatte aber noch keinen ersten CPU-Dispatch.
    • Running: Task besitzt den CPU-Kern und führt Anweisungen aus.
    • Preempted: Task war aktiv (Running) und wurde durch einen höherprioren Task oder eine ISR verdrängt.
    • Waiting: Task hat sich blockiert (WaitEvent) und wartet auf das Eintreffen mindestens eines definierten Events.
    • Released: Das erwartete Event wurde gesetzt; die Task ist deblockiert und wieder rechenbereit in der Ready-Queue, wurde aber noch nicht auf den Kern disponiert.
  • Transitionen & Trigger (Schnittstellen/OS-Operationen):
    • Activate: Übergang Suspended → Activated.
    • Start: Übergang Activated → Running.
    • Preempt: Übergang Running → Preempted.
    • Resume: Übergang Preempted → Running.
    • Wait: Übergang Running → Waiting.
    • Release: Übergang Waiting → Released.
    • Continue: Übergang Released → Running.
    • Terminate: Übergang Running → Suspended.

3. Dynamisches Verhalten & Sequenzablauf

Das Diagramm beschreibt den vollständigen Lebenszyklus einer Extended Task (inkl. Event-Mechanismus):

  1. Aktivierung:
    • Aufruf von ActivateTask() oder ChainTask() aus Task-/ISR-Kontext (bzw. Trigger via Alarm/Schedule Table) schaltet die Task von Suspended via Activate nach Activated.
  2. Erstmaliger Dispatch:
    • Der OS-Scheduler selektiert die Task entsprechend ihrer Priorität: Transition Start führt in Running.
  3. Preemption & Wiederaufnahme:
    • Wird eine Task höherer Priorität rechenbereit oder feuert ein Interrupt mit anschließendem Rescheduling, erfolgt Preempt nach Preempted.
    • Sobald die störende Last abgearbeitet ist, stellt der Scheduler den Kontext via Resume wieder nach Running her.
  4. Synchronisation via Events (Blockierender Pfad):
    • Die Task ruft WaitEvent(EventMask) auf: Transition Wait versetzt sie in den Zustand Waiting (CPU wird freigegeben).
    • Ein asynchroner Producer (Task oder ISR) ruft SetEvent(TaskID, Mask) auf: Sobald eine erwartete Event-Maske matched, schaltet Release die Task nach Released.
    • Der Scheduler disponiert die deblockierte Task bei Prioritätsvorrang via Continue zurück nach Running.
  5. Terminierung:
    • Aufruf von TerminateTask() schaltet die Task via Terminate zurück in Suspended.

4. Normative Relevanz & Entwickler-Hinweise

  • Gültigkeit nur für Extended Tasks: Für Basic Tasks entfällt der rechte Zweig (Wait, Waiting, Release, Released), da Basic Tasks keine OS-Events besitzen und nicht blockieren können.
  • ARTI-Hook-Instrumentierung & Metriken:
    • Standard-OS-APIs (GetTaskState()) melden für Activated, Preempted und Released normativ weiterhin nur den aggregierten OSEK-Status READY.
    • Tracing-Werkzeuge instrumentieren die feingranularen ARTI-Transitions-Hooks (z. B. ARTI_TRACE_TASK_START, ARTI_TRACE_TASK_PREEMPT), um folgende Kern-Metriken exakt zu trennen:
      • Activation Latency: Verweildauer in Activated (t_Start - t_Activate).
      • Release Latency: Verweildauer in Released (t_Continue - t_Release).
      • Pure Preemption Time: Kumulierte Zeit in Preempted.
      • Blocking Time: Zeit im Zustand Waiting.
      • Netto- vs. Brutto-Laufzeit: Net Execution Time (nur Running) vs. Response Time (Gesamtzeit von Activate bis Terminate).
  • Implementierungs-Einschränkungen:
    • WaitEvent() darf niemals innerhalb von Spinlocks, Resource-Locks (GetResource()) oder Interrupt-Sperren aufgerufen werden.
    • Das Erreichen des Funktionsendes einer Task ohne vorheriges TerminateTask() oder ChainTask() verletzt die OSEK/AUTOSAR-OS-Konformität.
