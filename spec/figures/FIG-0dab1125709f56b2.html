1. Diagrammtyp & Architektur-Kontext

  • Diagrammtyp: Konzeptionelles Architektur- und Interaktionsdiagramm (AUTOSAR Component & Port Architecture Pattern).
  • Technischer Zweck: Veranschaulichung der Entkopplung von Modusanforderung (Mode Request) und Modusumschaltung (Mode Switch) im AUTOSAR Classic Platform Mode Management.
  • Funktionale Einordnung: Zeigt die Koexistenz von applikativem Mode Management (SWC als Mode Manager) und System-/Basissoftware-Mode Management (BswM als Mode Manager) über die RTE-Abstraktion. Die RTE kapselt die autoritative Zustandsführung (Mode Machine Instance).

2. Komponenten, Entitäten & Schnittstellen

Schichten & Akteure
  • Application Layer (SWC):
    • Mode Manager A: Application-SWC mit Zustandshoheit für applikative Betriebsmodi.
    • Mode User 1 & Mode User 4: Reine Modus-Anforderer (Mode Requestors).
    • Mode User 2 & Mode User 5: Hybride SWCs, die sowohl Modi anfordern als auch auf Umschaltungen reagieren (Requestor & Listener).
    • Mode User 3 & Mode User 6: Reine Modus-Konsumenten (Mode Listeners).
  • RTE (Runtime Environment):
    • Beherbergt pro definiertem ModeDeclarationGroupPrototype eine instanziierte Mode machine instance, die den aktuellen Mode-Status, Initialmodi und Transitionen verwaltet.
  • BSW Layer:
    • Basic Software Mode Manager (BswM): Zentrale BSW-Instanz zur Arbitrierung von System-, Kommunikations- und ECU-Zuständen.
Ports & Schnittstellen
  • Mode Request Port (▼):
    • Sender-Receiver- oder Client-Server-Interface zur Übertragung von Moduswünschen (z. B. BswM_ModeRequestPort oder applikatives Interface).
    • P-Port an anfordernden SWCs (Mode User 1, 2, 4, 5); R-Port am jeweiligen Manager (Mode Manager A, BswM).
  • Mode Switch Port (⚂ / Würfel-3):
    • Basiert auf einem ModeSwitchInterface unter Referenzierung einer ModeDeclarationGroup.
    • P-Port (Provided): Am Mode Manager (Mode Manager A, BswM), führt den tatsächlichen Switch-Befehl aus (Rte_Switch_<p>_<mdgp>()).
    • R-Port (Required): An den Mode Users (Mode User 2, 3, 5, 6), registriert für Mode-Ereignisse oder Zustandspolling (Rte_Mode_<p>_<mdgp>()).

3. Dynamisches Verhalten & Sequenzablauf

  1. **Modusanforderung (Request Phase):**
    • Ein oder mehrere Mode Users (z. B. Mode User 1 & 2 bzw. 4 & 5) emittieren asynchron oder synchron einen Moduswechsel-Wunsch an ihren Mode Request Ports via RTE.
  2. **Arbitrierung & Validierung (Decision Phase):**
    • Fall SWC-Manager (Mode Manager A): Interne Applikationslogik bewertet die eingehenden Requests gegen Fahrzeugzustand, Plausibilität und Prioritäten.
    • Fall BswM (BswM): Auswertung konfigurierter BswMRule-Definitionen (logische Ausdrücke über BswMModeRequestPort-Inputs) und Zuweisung zu BswMActionLists.
  3. **Modusumschaltung (Execution Phase):**
    • Der jeweilige Mode Manager initiiert die Umschaltung über seinen Provided Mode Switch Port durch Aufruf von Rte_Switch(Rte_PortHandle, NextMode).
    • Die RTE nimmt den Befehl entgegen und überführt die interne Mode machine instance in den Zielmodus (unter Berücksichtigung konfigurierter Transition-States).
  4. **Modus-Benachrichtigung (Notification / Dispatch Phase):**
    • Die RTE feuert konfigurierte ModeSwitchEvents (Typen: ON_ENTRY, ON_EXIT, ON_TRANSITION).
    • Mapped Runnables der abonnierenden Mode Users (Mode User 2, 3 bzw. 5, 6) werden aktiviert oder deren Polling-Status (Rte_Mode()) wird aktualisiert.

4. Normative Relevanz & Entwickler-Hinweise

  • Strikte Entkopplung von Rechten (Architektur-Regel): Applikations-SWCs (Mode Users) dürfen niemals eigenmächtig Modi schalten. Ein Moduswechsel erfordert zwingend die Trennung: User stellt Request → Manager arbitriert → Manager triggert Switch → RTE aktualisiert Machine → RTE benachrichtigt User.
  • RTE-API-Vertrag:
    • Aufrufer von Rte_Switch() (Manager) müssen asynchrones Rückmeldeverhalten berücksichtigen (RTE_E_OK, RTE_E_LIMIT). Mehrfache Switches im selben Zyklus auf denselben Port können blockiert werden.
    • Mode Users dürfen zeitkritische Operationen nicht direkt an den Request koppeln, sondern müssen zwingend auf das ModeSwitchEvent der RTE warten.
  • BSW-Integration (BswM vs. SWC):
    • Systemweite Zustände (z. B. Post-Run, Sleep, Wakeup, ComM-Zustände, ECU-Degradation) gehören normativ in den BswM.
    • Reine Funktions- oder Feature-Zustände (z. B. Betriebsmodi eines Fahrerassistenzsystems) werden über Application Mode Manager realisiert, um die BSW-Konfiguration schlank und plattformunabhängig zu halten.
