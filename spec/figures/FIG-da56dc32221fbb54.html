1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Hybrides Architektur- und Scheduling-Diagramm, bestehend aus:
    • Links: Gerichteter azyklischer Abhängigkeitsgraph (DAG / Precedence Graph) von ausführbaren Entitäten (Executable Entities, EE), gruppiert in Cluster (Executable Entity Clusters, EEC).
    • Rechts: Multi-Core-Gantt-Diagramm / Scheduling-Timeline entlang der Zeitachse t für zwei Prozessorkerne (core 1, core 2).
  • Technischer Zweck & Einordnung:
    • Anschauungsbeispiel für den normativen Begriff Synchronization Point gemäß AUTOSAR_FO_TR_Glossary in Verbindung mit den AUTOSAR Timing Extensions (TIMEX) und dem Multi-Core OS / RTE Execution Order Constraint (EOC)-Metamodell.
    • Formalisierung der Abbildung funktionaler Kontroll- und Datenflussabhängigkeiten zwischen atomaren Software-Einheiten auf parallele Hardware-Kerne unter Einhaltung deterministischer Kausalitäts- und Synchronisationsschranken.

2. Komponenten, Entitäten & Schnittstellen

  • Executable Entity (EE):
    • Kleinste schedulbare, atomare Ausführungseinheit in AUTOSAR (z. B. RunnableEntity einer SWC auf VFB-/RTE-Ebene oder BSW Schedulable Entity wie eine periodische MainFunction).
    • Instanzen: EE6, EE7, EE8, EE9, EE10.
  • Executable Entity Cluster (EEC):
    • Gruppierung von EEs mit enger funktionaler Kohärenz, gemeinsamer Speicherdomäne oder gemeinsamem Allokationsziel.
    • EEC1: Enthält EE6 und EE7 (zugeordnet zu core 1).
    • EEC2: Enthält EE9 (zugeordnet zu core 1).
    • EEC3: Enthält EE8 und EE10 (zugeordnet zu core 2).
  • Rechenkerne (Execution Targets):
    • core 1: Verarbeitet EEC1 (EE6, EE7) und EEC2 (EE9).
    • core 2: Verarbeitet EEC3 (EE8, EE10).
  • Abhängigkeiten (Kanten / Precedence Constraints):
    • EE6 → EE7: Intra-Cluster- und Intra-Core-Sequenz in EEC1.
    • EE7 → EE8: Inter-Cluster- und Inter-Core-Fork-Abhängigkeit (EEC1 auf core 1 → EEC3 auf core 2).
    • EE7 → EE9: Intra-Core-Fork-Abhängigkeit (EEC1 auf core 1 → EEC2 auf core 1).
    • EE8 → EE10: Intra-Cluster- und Intra-Core-Sequenz in EEC3.
    • EE9 → EE10: Inter-Cluster- und Inter-Core-Join-Abhängigkeit (EEC2 auf core 1 → EEC3 auf core 2).
  • Synchronization Points (Rote vertikale Barrieren):
    • Temporale Synchronisationsanker (Barrieren), an denen Zustand oder Daten zwischen den Kernen konsolidiert und Ausführungsfreigaben erteilt werden.

3. Dynamisches Verhalten & Sequenzablauf

  1. Sequenzielle Vorphase (core 1):
    • core 1 führt zunächst EE6 und unmittelbar folgend EE7 synchron aus (EEC1).
    • core 2 befindet sich in Wartehaltung (Idle / Suspended), da EE8 von der Fertigstellung von EE7 abhängt.
  2. Erster Synchronisationspunkt (Fork / Release Barrier):
    • Die Beendigung von EE7 erreicht den ersten Synchronisationspunkt.
    • Signalisiert zeitgleich die Freigabe für EE9 auf core 1 und via Inter-Core-Signal/Event für EE8 auf core 2.
  3. Parallele Abarbeitung mit Drift:
    • EE9 läuft auf core 1, EE8 läuft parallel auf core 2.
    • EE8 weist eine kürzere Ausführungsdauer (Execution Time) auf als EE9 und terminiert früher.
  4. Zweiter Synchronisationspunkt (Join / Wait Barrier):
    • EE10 besitzt eine Join-Bedingung ($EE8 \land EE9 \rightarrow EE10$).
    • Nach dem Ende von EE8 muss core 2 am zweiten Synchronisationspunkt blockieren (Wartezeit / Core Idle Time), bis EE9 auf core 1 vollständig terminiert ist.
    • Erst nach Eintreffen des Quittierungs- bzw. Datensignals von EE9 wird der Synchronisationspunkt passiert und EE10 auf core 2 gestartet.

4. Normative Relevanz & Entwickler-Hinweise

  • RTE- und OS-Konfiguration (Execution Order Constraints):
    • EOC-Vorgaben aus dem System-Description- bzw. Timing-Modell erzwingen dedizierte Scheduling-Artefakte im AUTOSAR OS (z. B. Task Chains, Event-gesteuerte Tasks via SetEvent/WaitEvent oder OS-Schedule-Tables).
    • Inter-Core-Kanten (EE7 → EE8 und EE9 → EE10) bedingen die Konfiguration von Inter-OS-Application Communicator (IOC) Mechanismen oder Inter-Core Interrupts (IPI) zur Barriere-Synchronisation.
  • Latenz- und Blocking-Analyse (WCET & Scheduling):
    • Der zweite Synchronisationspunkt generiert eine Totzeit auf core 2 in Höhe von $\Delta t = t_{\text{end}}(EE9) - t_{\text{end}}(EE8)$.
    • Entwickler müssen EEs im Systementwurf so clustern und austarieren (Load Balancing), dass die Inter-Core-Synchronisationsüberhänge und Blocking-Zeiten minimiert werden, um CPU-Verschwendung zu vermeiden.
  • Datenkonsistenz & Kommunikationssemantik:
    • Bei Implicit Communication (Rte_IRead/Rte_IWrite) liest eine Runnable zu Beginn und schreibt zum Ende. Die Synchronisationspunkte markieren exakt die Gültigkeitsgrenzen, an denen Puffer atomar und kohärent über Kern- und Cache-Grenzen hinweg synchronisiert werden müssen, bevor abhängige Entitäten auf die Daten zugreifen dürfen.
