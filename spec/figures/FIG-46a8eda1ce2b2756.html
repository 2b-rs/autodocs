1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Datenfluss- und Interaktionsdiagramm für das Schlüssel-Lebenszyklusmanagement (Key Lifecycle & Storage Interaction Model) an der Schnittstelle zwischen Host-Applikation und Hardware Security Module (HSM).
  • Technischer Zweck: Spezifikation des Common Key Interface (CKI) bzw. Crypto Key Interface innerhalb des AUTOSAR Adaptive Platform Designs (AUTOSAR_EXP_PlatformDesign). Das Diagramm definiert die funktionale Entkopplung zwischen ungesichertem Host-Speicher (External Storage) und gesicherter Ausführungsumgebung (HSM „Driver“ mit flüchtigem Arbeitsspeicher und geschütztem Internal Storage). Es visualisiert, wie kryptografische Schlüssel erzeugt, importiert, exportiert, abgeleitet und instanziiert werden, ohne dass Schlüsselmaterial im Klartext die Sicherheitsgrenze zum Host überschreitet.

2. Komponenten, Entitäten & Schnittstellen

#### Entitäten & Speicherbereiche

  • OEM-Domäne (Backend / Fertigung): Bereitstellungspunkt für Root-Schlüssel, Zertifikate und Schlüsselpakete über Initial-Flash (Fertigung) oder FOTA-Kampagnen.
  • External Storage (Host-NVM / Dateisystem): Unverschlüsselter oder ungesicherter physikalischer Speicherbereich der ECU (z. B. eMMC, UFS, Flash). Hält Schlüssel ausschließlich als geschützte Key Blobs (kryptografisch gewrappt / verschlüsselt und integritätsgesichert).
  • HSM „Driver“ (Sicherheitsgrenze / Trust-Boundary): Gekapselte Secure-Hardware-/Firmware-Domäne (z. B. SHE+, HSM, TPM oder Secure Enclave):
  • Active / Loaded (Volatiler HSM-RAM): Hält Arbeitsobjekte als Key Struct (deserialisierte, kryptografisch nutzbare Schlüsselrepräsentationen inkl. Flags, Algorithmus-Bindings und Counter).
  • Internal Storage (Secure NVRAM / OTP): Nichtflüchtiger interner Schlüsselspeicher innerhalb des HSM für hochkritische Stammschlüssel (z. B. Master Keys, Device Identity Keys, Boot Keys).
  • Host SW / Applications: Aufrufer auf der Host-CPU (Adaptive Applications, Functional Cluster wie ara::crypto oder Classic Crypto Stack CryIf/Crypto Driver Object).

#### Schnittstellen (CKI API-Operationen)

  • key_create(key-spec): Instanziiert ein flüchtiges Key Struct im HSM auf Basis formaler Spezifikationsparameter (Typ, Länge, Verwendungszweck, Algorithmus).
  • key_import(): Deserialisiert und un-wrappt einen externen Key Blob in ein aktives Key Struct innerhalb der HSM-Sicherheitsgrenze.
  • key_export(): Verschlüsselt/authentifiziert ein Key Struct (Key Wrapping) und gibt einen serialisierten Key Blob zur Ablage im externen Speicher aus.
  • key_load(): Lädt ein persistiertes Schlüsselobjekt aus dem sicheren internen HSM-NVRAM in den aktiven flüchtigen Speicher (Key Struct).
  • key_unload*: Persistiert bzw. flusht den Zustand eines aktiven Schlüssels zurück in den internen Speicher (Asterisk kennzeichnet optionale/modusspezifische Persistierung, z. B. Aktualisierung von monotonen Zählern/Nutzungsstatistiken).
  • key_derive, exchange, extract: Trigger für die interne HSM-Ableitungslogik (derivation logic, z. B. KDF, Diffie-Hellman-Schlüsselaustausch, HKDF); generiert ein neues Ziel-Key Struct direkt im HSM-RAM.
  • key_getInfo(): Gibt Metadaten (Key Slot Info, Attribute, Zulässigkeit von Operationen) an die Host-Software zurück – strikt ohne Extraktion des Schlüsselgeheimnisses.

3. Dynamisches Verhalten & Sequenzablauf

  1. Provisionierung & Initialisierung:
  • Bereitstellung von Schlüsselmaterial durch den OEM via Initial-Flashing oder FOTA-Update (Init / FOTA) in den externen Speicher als persistente Key Blobs.
  1. Schlüsselaktivierung (Load / Import):
  • Pfad A (Interner Schlüsselspeicher): Host triggert key_load(). Das HSM liest den internen NVM und instantiiert das Key Struct im aktiven RAM.
  • Pfad B (Externer Schlüsselspeicher): Host übergibt den Key Blob via key_import(). Das HSM entschlüsselt den Blob unter Verwendung eines internen KEK (Key Encryption Key) und legt das Klartext-Key Struct isoliert im HSM-RAM ab.
  • Pfad C (Flüchtige Erzeugung): Host ruft key_create(key-spec) auf (z. B. für Session-Keys via TRNG).
  1. Schlüsselableitung & Transformation:
  • Host initiiert key_derive, exchange, extract unter Referenzierung eines vorhandenen Basis-Key Struct.
  • Die hardwaregekapselte derivation logic erzeugt ein neues deriviertes Key Struct im HSM-RAM, ohne Zwischenergebnisse nach außen preiszugeben.
  1. Metadatenabfrage & Auslagerung:
  • Host fragt Status/Eigenschaften via key_getInfo() synchron ab.
  • Sichern flüchtiger Schlüsselstände: Bei internen Schlüsseln via key_unload*, bei extern verwalteten Schlüsseln über key_export() als gewrappter Key Blob zurück in den externen Speicher.

4. Normative Relevanz & Entwickler-Hinweise

  • Kapselung des Schlüsselmaterials (Zero-Leakage-Prinzip): Applikationen und Host-Treiber erhalten zu keinem Zeitpunkt Rohdaten (Plaintext Keys). Alle Interaktionen erfolgen ausschließlich über opaque Handles oder Referenzen (Key Struct verbleibt innerhalb des HSM).
  • Speicherdifferenzierung & Skalierbarkeit:
  • Interner HSM-NVM ist physikalisch stark limitiert (oft nur wenige Dutzend Slots für Root of Trust, Secure Boot, KEKs).
  • Skalierbare Schlüsselmengen (Applikations-Zertifikate, Session-Keys, Flotten-Verschlüsselung) müssen nach dem Schema Export -> External Storage (Key Blob) -> Import on Demand implementiert werden.
  • *Transaktionssicherheit bei key_unload:**
  • Bei Verwendung interner Schlüssel mit Nutzungslimits oder Monotonic Counter Updates muss der Entwickler sicherstellen, dass key_unload* vor dem Herunterfahren/Reset atomic ausgeführt wird, um Counter-Desynchronisationen oder Slot-Korruption zu verhindern.
  • Mapping auf AUTOSAR-Standards:
  • In AUTOSAR Adaptive bildet dieses CKI-Konzept das Fundament für die Implementierung der ara::crypto::keys::KeyStorageProvider- und ara::crypto::cryp::CryptoProvider-Schnittstellen.
  • In AUTOSAR Classic entspricht dies der Trennung zwischen NvM (für Blobs) und den hardware-internen Key-Slots im Crypto Driver (vCrypto / HSM Firmware nach AUTOSAR SWS Crypto Driver).
