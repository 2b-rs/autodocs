1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Protokoll-Frame- / PDU-Layout-Diagramm (Bit-/Byte-Struktur eines DLT-v2-Übertragungsrahmens).
  • Architektur-Einordnung: Spezifiziert in AUTOSAR_FO_PRS_LogAndTraceProtocol (Diagnostic Log and Trace – DLT). Gültig als standardisiertes Foundation-Protokoll plattformübergreifend für die AUTOSAR Classic Platform (CP) (BSW-Modul Dlt) und die AUTOSAR Adaptive Platform (AP) (ara::log-Dämon / Logging-Subsystem).
  • Funktionaler Zweck: Definition des PDU-Formats für den Non-Verbose Mode. Ziel ist die maximale Reduktion des Bandbreiten- und CPU-Overheads auf dem Übertragungsmedium (Ethernet/IP, CAN, FlexRay, UART) durch Eliminierung statischer Metadaten (Strings, Parametertypen, Extended Header). Die semantische Dekodierung erfolgt offline auf dem DLT-Client anhand von FIBEX/ARXML-Beschreibungsdateien.

2. Komponenten, Entitäten & Schnittstellen

Das Frame gliedert sich strikt in zwei aufeinanderfolgende Segmente: den standardisierten Base Header und die binäre Payload.

+-------------------------------------------------------------+------------------------------------+
|                         Base Header                         |              Payload               |
+-----------+----------+-----------+-----------+--------------+------------------------------------+
|   HTYP2   |   MCNT   |    LEN    |   TMSP2   |  Message ID  |          Non-Static Data           |
|  (1 Byte) | (1 Byte) | (2 Bytes) | (4 Bytes) |  (4 Bytes)   |         (variable Länge)           |
+-----------+----------+-----------+-----------+--------------+------------------------------------+
Base Header (Standard Header)
  • HTYP2 (Header Type 2, 1 Byte): Bitfeld zur Steuerung der Header-Eigenschaften und optionalen Felder:
    • UEH (Use Extended Header, Bit 0): Im Non-Verbose Mode zwingend auf 0 gesetzt; der Extended Header (MSIN, NOAR, APID, CTID) entfällt vollständig (PRS_Dlt_00314).
    • MSBF (Most Significant Byte First, Bit 1): Definiert die Payload- und Header-Endianness (0 = Little Endian, 1 = Big Endian).
    • WEID / WSID: Kennzeichnet das Vorhandensein optionaler ECU-ID / Session-ID-Felder (im vorliegenden Diagramm inaktiv).
    • WTMS (With Timestamp, Bit 4): Auf 1 gesetzt; signalisiert das Vorhandensein des Feldes TMSP2.
    • VERS (Version Number, Bits 5–7): Kodiert die DLT-Protokollversion (Version 2).
  • MCNT (Message Counter, 1 Byte): Monoton inkrementierender Zähler (0x00–0xFF mit Überlauf) pro DLT-Instanz/Log-Kanal zur Erkennung von PDU-Verlusten auf der Transportschicht.
  • LEN (Length, 2 Bytes, uint16): Gesamtlänge der DLT-Nachricht in Bytes (Summe aus Base Header inklusive aller aktiven Optionsfelder + Payload).
  • TMSP2 (Timestamp 2, 4 Bytes, uint32): Systemzeitstempel des Sendezeitpunkts in 100-µs-Ticks seit ECU-Boot.
Payload
  • Message ID (4 Bytes, uint32): Erster Payload-Parameter (Offset 0 der Payload). Sie ist das zentrale Identifikationsmerkmal im Non-Verbose Mode (PRS_Dlt_00315, PRS_Dlt_00352) und ersetzt APID, CTID, Log-Level sowie Format-Strings.
  • Non-Static Data (variable Länge): Ausschließlich die dynamischen Nutzdaten (Laufzeit-Variablenwerte wie Integers, Floats, Raw Buffers) der Log-Argumente. Im Gegensatz zum Verbose Mode werden keine Typ-Deskriptoren (Type Info Header) vor die Argumente serialisiert.

3. Dynamisches Verhalten & Sequenzablauf

1. Sende-Pfad (ECU / Target)
  1. API-Aufruf: Applikations-SWC oder BSW-Modul ruft die DLT-Schnittstelle auf (z. B. Dlt_SendLogMsg() in Classic oder Logger-API in Adaptive) unter Angabe einer vorkonfigurierten MessageID und variabler Argumente.
  2. PDU-Assemblierung:
    • Base Header wird aufgebaut: HTYP2.UEH = 0, aktueller MCNT wird eingetragen und inkrementiert, Boot-relative Zeitbasis wird in TMSP2 geschrieben.
    • Message ID wird als erste 4 Bytes der Payload serialisiert.
    • Non-Static Data wird direkt als raw Byte-Stream ohne Type-Header angehängt.
    • Berechnete Gesamtlänge wird in LEN geschrieben.
  3. PDU-Weiterleitung: Übergabe an den unteren Transport-Layer (PduR / SoAd in Classic Platform bzw. Socket/IPC-Stack in Adaptive Platform).
2. Empfangs- und Rekonstruktions-Pfad (DLT-Client / Tooling)
  1. Header-Validierung: DLT-Viewer prüft HTYP2 (Version = 2, UEH = 0) und liest LEN, MCNT (Fehlerzählung) und TMSP2.
  2. ID-Auflösung: Extraktion der Message ID aus den ersten 4 Payload-Bytes. Abgleich gegen die build-spezifische DLT-Beschreibungsdatei (ARXML/FIBEX).
  3. Rekonstruktion: Zuweisung von ApplicationID, ContextID, Log-Level (Fatal, Error, Warn, Info, Debug, Verbose) und dem Format-String.
  4. Parsing der Nutzdaten: Sequentielles Einlesen der Non-Static Data gemäß den in der Beschreibungsdatei hinterlegten Datentypen (z. B. uint16, float32) und Ausgabe des vollständig formatierten Klartext-Logs.

4. Normative Relevanz & Entwickler-Hinweise

  • Normative Anforderungen:
    • PRS_Dlt_00314: Im Non-Verbose Mode darf der Extended Header nicht verwendet werden (UEH = 0).
    • PRS_Dlt_00315: Im Non-Verbose Mode muss die Message ID zwingend in den ersten 4 Bytes der Payload stehen.
    • PRS_Dlt_00352: Die Nutzdaten-Parameter folgen unmittelbar auf die Message ID ohne vorangestellte Typinformationen.
    • PRS_Dlt_01062, RS_LT_00013, RS_LT_00023, RS_LT_00027, RS_LT_00058: Gewährleistung deterministischer Ausführungszeiten, minimaler Buslast und Entkopplung statischer Texte von der ECU-Software.
  • Auswirkungen auf BSW- & Applikations-Entwickler:
    • Speicheroptimierung (Flash/ROM): Statische Text-Strings verbleiben nicht im ECU-Flash, sondern ausschließlich in der Offline-Datenbank. Ideal für ressourcenbeschränkte Microcontroller (Classic Platform).
    • Bandbreite & Latenz: Reduziert die Buslast drastisch gegenüber dem Verbose Mode (kein Extended Header mit 10 Bytes, keine Type-Info-Header à 4 Bytes pro Argument).
    • Generierungs- und Toolchain-Kopplung: Jede Änderung an Log-Aufrufen erfordert die Neugenerierung der FIBEX/ARXML-Beschreibungsdatei. Ohne die exakt zur Firmware-Build passende Beschreibungsdatei ist der DLT-Client nicht in der Lage, die Payload zu dekodieren (reine Rohdaten-Anzeige).
    • Endianness & Alignment: Entwickler müssen sicherstellen, dass die Übergabe der Rohparameter in Non-Static Data mit dem im Bit HTYP2.MSBF deklarierten Endianness-Format übereinstimmt und kein Alignment-Padding ohne Spezifikation eingefügt wird.
