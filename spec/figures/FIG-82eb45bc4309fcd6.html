1. Diagrammtyp & Architektur-Kontext

  • Klassifikation: Layered Architecture / Functional Allocation Diagram (Schichtenmodell mit funktionaler Zuordnung von Sicherheits- und Fehlertoleranzmechanismen im AUTOSAR BSW Memory Stack).
  • Technischer Zweck: Spezifiziert die hierarchische Allokation von Fehlererkennungs- (Error Detection) und Fehlerbehebungsmechanismen (Recovery Mechanisms) über die Schichten Memory Services (NvM), Memory Hardware Abstraction (MemIf, Ea, Fee) und MCAL / Drivers (Eep, Fls, SPI Handler).
  • Funktionale Einordnung: Gewährleistet funktionale Sicherheit und Datenintegrität persistenter Daten (NVRAM) gegen Hardwareausfälle (z. B. Bit-Flips, Flash-Degradation), Spannungsabfälle (Loss of Power) und Bus-/Übertragungsfehler.

2. Komponenten, Entitäten & Schnittstellen

  • Schichten & Module:
    • Application Layer / RTE: Initiiert NVRAM-Zugriffe über Standard-/Client-Server-Ports.
    • Memory Services (NvM): Zentrale Instanz für blockbasierte Verwaltung, Datenintegrität, Redundanzlogik und Recovery.
    • Memory Hardware Abstraction:
      • MemIf: Abstraktionsschicht zur Virtualisierung mehrerer unterlagerter Memory-Treiber.
      • Ea (EEPROM Abstraction) / Fee (Flash EEPROM Emulation): Virtualisierung von Flash-Pages bzw. EEPROM-Sektoren zu logischen Blöcken; Handhabung von Out-of-Place-Updates und Garbage Collection.
      • Ext. EEPROM Driver (Eep) / Ext. Flash Driver (Fls): Externe Treibereinheiten (oft via SPI angebunden).
    • Drivers (MCAL) & COM Drivers:
      • Int. EEPROM Driver / Int. Flash Driver: Direkte Registerzugriffe auf internen On-Chip-Speicher.
      • SPI Handler Driver: Serial Peripheral Interface zur Kommunikation mit externen Speicherbausteinen.
    • Hardware / µC: Microcontroller-Hardwarekomponenten (SPI, interne RAM-Tests, interner EEPROM, Flash) sowie externer EEPROM-Speicherbaustein.
  • Zuordnung der Mechanismen:
    • NvM (Services Layer):
      • Detection: Job failure detection confirmation, CRC check (CRC-8, CRC-16, CRC-32), Static block check (Validierung von Block-ID im Header gegen Block-Konfiguration), Write verification (Re-Read nach Write), Loss of redundancy detection.
      • Recovery: Read Retry, Read Redundant Block, Read ROM data (Fallback auf Default-Werte im Flash/ROM), Write Retry, Write Redundant Block.
    • Ea / Fee (Hardware Abstraction Layer):
      • Detection: Read consistency check (Block-Header-Validierung, logische Statusmarker, Längen- und Alignment-Prüfung).
    • Memory / COM Drivers (MCAL):
      • Detection: Job failure detection (Hardware-Fehlerflags, Timeouts, ungültige Programmierspannungen, Verify-Fehler des Speichers).

3. Dynamisches Verhalten & Sequenzablauf

  • Asynchrone Verarbeitungs- und Eskalationskette (Read Path):
    1. Request: Applikation ruft synchron NvM_ReadBlock() auf; der Request wird in die NvM-Queue eingereiht.
    2. Treiberabarbeitung: Asynchroner Aufruf über MemIf_Read() an Fee/Ea und die MCAL-Treiber.
    3. MCAL-Fehler: Schlägt der Lesevorgang hardwareseitig fehl, meldet der Treiber MEMIF_JOB_FAILED (Job failure detection).
    4. Abstraktions-Fehler: Werden Daten gelesen, deren logischer Header korrupt ist, erkennt Fee/Ea dies via Read consistency check (MEMIF_BLOCK_INCONSISTENT / MEMIF_BLOCK_INVALID).
    5. NvM-Integritätsprüfung: Bei fehlerfreiem Treiberlauf prüft NvM Block-ID (Static block check) und verifiziert die Nutzdaten per CRC check.
    6. Recovery-Eskalation:
      • 1. Stufe: Read Retry (Wiederholung des Lesevorgangs gemäß Konfiguration NvMMaxNumOfReadRetries).
      • 2. Stufe: Bei redundanten Blöcken (NVM_BLOCK_REDUNDANT) Umschalten auf die sekundäre Kopie (Read Redundant Block); bei Ausfall der Primärkopie wird ein Loss of redundancy-Fehler an das DEM gemeldet.
      • 3. Stufe: Schlagen beide Kopien fehl, lädt der NvM persistierte Default-Werte (Read ROM data) in das RAM-Spiegel-Array (NvMRomBlockDataAddress oder Callback).
  • Asynchrone Verarbeitungs- und Eskalationskette (Write Path):
    1. Berechnung & Start: NvM generiert Headerdaten und berechnet CRC im RAM-Block. Aufruf über MemIf_Write().
    2. Write Verification (falls konfiguriert): Nach Schreibabschluss liest der NvM die Daten byteweise/blockweise zurück und vergleicht sie direkt mit dem Quell-RAM (Write verification).
    3. Recovery-Eskalation: Bei Abweichung oder Treiberabbruch greift Write Retry (NvMMaxNumOfWriteRetries), gefolgt vom Schreiben des sekundären Datenblocks (Write Redundant Block).
  • Diagnose- und Fehler-Reporting:
    • Temporäre Fehler werden stack-intern über die Retry-Zähler maskiert.
    • Permanente Fehler werden via Dem (Dem_ReportErrorStatus) gemeldet (z. B. NVM_E_INTEGRITY_FAILED, NVM_E_REQ_FAILED, NVM_E_LOSS_OF_REDUNDANCY).
    • Ungültige API-Parameter oder Sequenzierungsfehler triggern das Det (Det_ReportError).

4. Normative Relevanz & Entwickler-Hinweise

  • Treiber-Entwicklung (MCAL / Fee / Ea):
    • MCAL-Treiber (Fls, Eep) dürfen nicht blockieren; Zustände müssen strikt via MemIf_JobResultType (MEMIF_JOB_OK, MEMIF_JOB_FAILED, MEMIF_JOB_PENDING) gemeldet werden.
    • Fee/Ea müssen Schreibunterbrechungen (Power-Loss-Recovery) intern handhaben und dürfen teilbeschriebene Sektoren nicht als konsistente Blöcke an den NvM melden.
  • NvM-Stack-Konfiguration:
    • Kritische Sicherheitsblöcke: Konfiguration als NVM_BLOCK_REDUNDANT zwingend mit NvMBlockUseCrc = TRUE (CRC16 oder CRC32) und aktivierter NvMStaticBlockIdCheck = TRUE zur Erkennung von Adressierungsfehlern.
    • Write Verification: NvMWriteVerification = TRUE erhöht die Datensicherheit bei Flash-Zellenverschleiß erheblich, verdoppelt jedoch die Buslast auf internem/externem Speicherbus.
    • Retries: NvMMaxNumOfReadRetries und NvMMaxNumOfWriteRetries müssen restriktiv parametriert werden, um Deadlines während Startup (NvM_ReadAll) und Shutdown (NvM_WriteAll) nicht zu verletzen.
  • Applikations-Entwicklung:
    • Ein Rückgabewert E_OK an der NvM-API bestätigt lediglich die Queue-Annahme. Der tatsächliche Block-Status muss über NvM_GetErrorStatus() oder asynchrone Callbacks (NvM_SingleBlockCallbackFunction) ausgewertet werden.
    • Bei Nutzung von Read ROM data muss die Applikation darauf vorbereitet sein, dass nach Neustart Default-Zustände anliegen (NVM_REQ_RESTORED_FROM_ROM).
