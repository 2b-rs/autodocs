## F-TOM-OKONKWO-001 — structural change: `validate` runs detached

**Observation.** `_src/validate.py` over 428 pages is the longest uninterrupted single step of the
sequence and has now terminated two sessions at exactly that point (Rivera, Vasquez). Run in the
foreground of an agent session it has a demonstrated ~50% completion rate here.

**Change.** Stage 14 is executed as a **detached** process (`setsid nohup`) that outlives this
session: `output/detached/run-validate.sh`, stdout and stderr redirected directly into the evidence
file, real exit status captured both into the evidence file and into
`output/detached/14-validate.rc`. This session polls for completion instead of blocking on it.

**Why this is a correctness improvement and not a workaround.** If this session dies mid-stage the
*computation* survives and the successor commits a finished result instead of restarting a long
job. The evidence file is self-describing — command line, run ref, cwd, HEAD, start and end
timestamps, real exit status, and a terminal `STAGE-14-COMPLETE` marker — so a truncated file is
mechanically distinguishable from a complete one. That distinction is exactly what was missing when
Rivera left a 217-byte header-only artifact behind.

`output/detached/` is inside the git-ignored `output/` tree (`DEC-0043-001`); only the evidence file
under `docs/campaign-evidence/` is committed.

**Launched:** PID `69828` (validate interpreter `69862`),
`RUN_ARCHIVE_REF=manual-20260824T072259Z-d6eece5d`, started `2026-08-24T08:11:53Z` by the machine
clock (all timestamps in the evidence files are machine `date -u`).

**F-TOM-OKONKWO-001a — first launch attempt failed, recorded rather than hidden.** The first
invocation used `setsid`, which **does not exist on macOS**; the wrapper never started and the shell
reported `command not found: setsid` only into the nohup file. Because the wrapper writes the
evidence header as its *first* action, the failure produced **no evidence file at all** — the
absence was unambiguous and was caught by the very next poll. Relaunched with `nohup ... & disown`,
which is sufficient for detachment here. Noting this because it is a small live demonstration of why
the self-describing-evidence rule matters: a launch that fails before writing its header cannot be
mistaken for a run that produced no findings.

## F-TOM-OKONKWO-003 — verdict on the stage-1a exit status (flagged by dispatcher)

**Question.** Stage 1a of this fresh run recorded shell `exit 1` (`4484` accepted / `107` rejected),
whereas Rivera's earlier attempt recorded `exit 0` for the same command.

**Verdict: the exit status is real, is correctly recorded, is not caused by Feature 0043, and does
not invalidate the cohort — but it does mean this run cannot be reported as an unqualified
success.** Reasoning:

1. The `1` is genuine. `_src/i18n_translate.py` returns `len(fehler)` and sets the subreport's
   `exit_code` to 1 whenever any segment is rejected (`_src/i18n_translate.py:257,263`). Rivera's
   `exit 0` is a **mismeasurement** — he captured a wrapper's status, not the interpreter's; his own
   subreport already said `exit_code=1`. Vasquez identified this correctly and, rightly, recorded it
   in his own file rather than editing predecessor evidence.
2. The cause is 107 stale `unbekannte Segment-ID` entries in the tracked English translation work
   batches (`_src/i18n/work/en/batch_*.out.jsonl`). The merge is idempotent — `fehler.json` is
   byte-identical to the committed one — so this is a stable pre-existing property of the
   translation data, predating and unrelated to Feature 0043. Repairing it means editing translation
   source data, which is outside this Task's write scope.
3. **Consequence, stated plainly:** `combine` will record `overall_success=false` for this run. That
   is the honest result and it is left standing. It is **not** manufactured green and it is not
   worked around.
4. **Does it defeat the acceptance criterion?** The criterion requires a *real* run carried end to
   end with *correlated* subreports, a successful `combine`, and an appended ledger entry — not a
   run in which every producer returns 0. `combine` succeeding is a statement about aggregation, not
   about every stage being clean; the ledger schema carries a per-run exit status precisely so a
   run with findings can be recorded truthfully. A ledger whose first real entry says
   `overall_success=false` is the system working, not failing. This is surfaced to `belanna`
   actively rather than left for her to find in the delta; if she reads the criterion more strictly,
   that is a checkpoint decision and hers to make.
