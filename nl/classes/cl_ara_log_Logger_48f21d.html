klasse ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Context

De klasse ara::log::Logger representeert een loggingcontext binnen een AUTOSAR Adaptive-applicatieproces of -procesdomein. Een dergelijke context kapselt centrale eigenschappen voor de logging in: een context-ID, een bijbehorende beschrijving van de context-ID en een configureerbaar standaard-loglevel (Default Log Level). Via deze contexten wordt de loguitvoer binnen het systeem gedifferentieerd en aangestuurd.

In de systeemarchitectuur fungeert ara::log::Logger als bemiddelaar tussen drie betrokken partijen:

  • Applicatieproces (Application Process): Gebruikt instanties van ara::log::Logger om berichten te versturen en filterdrempels dynamisch op te vragen of aan te passen.
  • Logging-framework: Behoudt een strikt eigenaarschap („strong ownership”) over alle Logger-instanties, stuurt het aanmaken ervan aan via factory-functies zoals ara::log::CreateLogger en verzorgt de housekeeping.
  • Logging-backend: Neemt de eigenlijke loggegevens in ontvangst; Logger-contexten worden tijdens de initialisatiefase automatisch bij de backend geregistreerd en tijdens de ordelijke proces-shutdown gederegistreerd.

Contextdiagram: Inbedding van de Logger-klasse in samenspel met applicatie, logging-framework en backend. Bronnen: [SWS_LOG_00259]

Levenscyclus

Het beheer van de instanties van ara::log::Logger is onderworpen aan een strenge controle door het framework om een naadloze synchronisatie met de logging-backend te waarborgen:

  • Creatie en eigendomsverhoudingen: De standaardconstructor is expliciet verwijderd (Logger() = delete, [SWS_LOG_00259]). Direct instantiëren door de applicatie is niet toegestaan. Het aanmaken gebeurt gecontroleerd via functies zoals ara::log::CreateLogger. Het eigenaarschap blijft bij het logging-framework.
  • Registratie en opruiming: Een Logger-context wordt bij zijn creatie automatisch bij de logging-backend geregistreerd. Bij het beëindigen van het proces vindt de afmelding automatisch plaats, waardoor applicatieontwikkelaars worden ontlast van het handmatige levenscyclusbeheer.
  • Vernietiging: De destructor ~Logger() is gespecificeerd ([SWS_LOG_00260]). Hij is als thread-safe gedeclareerd, maar aangemerkt als niet-uitzonderingsveilig („not exception safe”) ([SWS_LOG_00260]).
  • Gelijktijdigheid: Alle methoden voor logging en drempelwaardeopvraag zijn als thread-safe gespecificeerd ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). Meerdere threads kunnen dezelfde Logger-instantie parallel gebruiken.

Gebruikspad

Het typische verloop bij het versturen van logberichten is onderverdeeld in de volgende fasen:

  1. Filterdrempel controleren of configureren: De applicatie kan de filterdrempel van een instantie tijdens runtime instellen via SetThreshold(threshold) ([SWS_LOG_00255]). Voorafgaand aan rekenintensieve voorbereidingen van loggegevens kan via IsEnabled(logLevel) worden opgevraagd of het gewenste loglevel aan de geconfigureerde rapportagedrempel voldoet ([SWS_LOG_00070]). Geeft de controle false als resultaat, dan kan de voorbereiding worden overgeslagen.
  2. Stream-gebaseerde logging initiëren: Voor tekstlogging stelt de klasse specifieke methoden voor elk niveau van ernst beschikbaar:
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • WithLevel(logLevel) ([SWS_LOG_00131]) voor het programmatisch bepalen van de urgentie.
    Elk van deze methoden retourneert een LogStream-object dat argumenten via de stream-operator << in ontvangst neemt ([SWS_LOG_00064]).
  3. Levensduur van de stream en uitvoer: In het standaardgeval is de levensduur van het LogStream-object beperkt tot een enkele instructie en eindigt deze met de puntkomma na het laatste argument ([SWS_LOG_00064]). Indien gewenst kan de stream aan een variabele worden toegewezen om de levensduur ervan over meerdere instructies uit te breiden ([SWS_LOG_00064]).
  4. Gemodelleerde berichten uitvoeren: Als alternatief voor streaming kunnen vooraf gemodelleerde berichten via Log(id, args...) worden uitgevoerd ([SWS_LOG_00204]). Als er aanvullende attributen moeten worden meegegeven, vindt de aanroep plaats via LogWith(attrs, msgId, params...) met een attribuut-tuple ([SWS_LOG_00133]).

Sequentiediagram: Aanroepvolgorde van een gefilterde stream-loggingoperatie. Bronnen: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064]

Foutscenario's

De foutafhandeling in ara::log::Logger is hoofdzakelijk gebaseerd op statische typecontrole tijdens compileertijd en strikte uitzonderingsveiligheid:

  • Niet-overeenkomende argumenten bij gemodelleerde berichten: Wordt de templatefunctie Log(id, args...) aangeroepen met parameters die niet exact overeenkomen met de definitie van het gemodelleerde bericht, dan is het programma slecht gevormd („ill-formed”) ([SWS_LOG_00204]). Dit leidt tot een fout tijdens de compilatie.
  • Ongeldige attributen bij LogWith: Bij LogWith(attrs, msgId, params...) wordt de functie via SFINAE uitgesloten van overloadresolutie als een element van het attribuut-tuple geen geldig attribuut vormt ([SWS_LOG_00133]).
  • Uitzonderingsgaranties: Alle logging- en opvraagfuncties (waaronder IsEnabled, SetThreshold, alle Log*-methoden, WithLevel, Log en LogWith) zijn gespecificeerd als uitzonderingsveilig („exception safe”) en gedeclareerd met noexcept ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). Een uitzondering vormt de destructor ~Logger(), die als niet-uitzonderingsveilig („not exception safe”) wordt vermeld ([SWS_LOG_00260]). Interpretatie: Dit betekent vermoedelijk dat bij interne opschonings- of vrijgavefouten in het kader van de backend-housekeeping fouttoestanden niet volledig worden opgevangen, waardoor de deregistratie tijdens de reguliere proces-shutdown dient plaats te vinden.
