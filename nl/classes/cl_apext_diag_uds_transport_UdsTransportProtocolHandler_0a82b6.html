Dient als abstracte basisklasse voor UDS-transport-plugins voor de overdracht en het doorsturen van diagnoseberichten.

De abstracte klasse dient UDS-transport-plugins als basisinterface voor de gestandaardiseerde koppeling met het adaptieve diagnosebeheer (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”). Een afgeleide implementatie meldt ontvangen diagnoseberichten door aan de protocolmanager en zendt gegenereerde antwoordberichten via netwerkspecifieke kanalen naar de diagnosetester. De levenscyclus is onderworpen aan een strikte volgorde van aanmaken, afzonderlijke initialisatie, asynchrone start en geordend stoppen ([SWS_DM_00329]). Na de instantiatie zijn de operationele methode-aanroepen niet thread-safe en vereisen zij een gecoördineerde besturing door de diagnosekern.

Context

De klasse apext::diag::uds_transport::UdsTransportProtocolHandler is een abstracte basisklasse binnen de module diag van het AUTOSAR Adaptive Platform. Zij definieert de gestandaardiseerde interface waarmee bedrijfseigen of protocolspecifieke UDS-transport-plugins worden gekoppeld aan het adaptieve diagnosebeheer (DM) (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). Elk concreet transportprotocol – bijvoorbeeld voor diagnose via automotive netwerkmedia – implementeert deze interface als afgeleide subklasse. De DM zal de betreffende handler-instantie vermoedelijk gedurende haar gehele operationele levenscyclus exclusief bezitten en beheren. Vraag Q-ef308265bfdf6cec (open) De interactie tussen de diagnosekern en de plugin verloopt via de referentie transportprotocolManager van het type UdsTransportProtocolMgr&, die in de constructor wordt doorgegeven en beschermd wordt opgeslagen ([SWS_DM_09015], [SWS_DM_09025]). Elke handler wordt geïdentificeerd door een numerieke UdsTransportProtocolHandlerID, die via GetHandlerID() kan worden opgevraagd ([SWS_DM_00325]).

Levenscyclus

De levenscyclus van een UDS-transportprotocol-handler wordt strikt sequentieel bestuurd door de DM ([SWS_DM_00329]). Na de instantiatie via de constructor UdsTransportProtocolHandler ([SWS_DM_09015]) scheidt de methode Initialize() de eigenlijke protocolinitialisatie van het aanmaken van het object ([SWS_DM_00319]). Afgezien van een optionele opvraag via GetPeriodicHandler() mag de DM vóór de succesvolle return van InitializationResult::kInitializeOk geen methoden op de handler aanroepen ([SWS_DM_01746], [SWS_DM_09017]). Na succesvolle initialisatie brengt de aanroep van Start() de handler in de actieve verwerkingstoestand ([SWS_DM_00322]). Om de opstarttijd te minimaliseren, is Start() ontworpen als asynchrone operatie; de DM zal de parallelle start van meerdere handlers vermoedelijk intern coördineren. Vraag Q-66e5a53d55e6d812 (open) Gaat de DM bij het afsluiten over naar de toestand ApplicationState.kTerminating, dan draagt deze de handler via Stop() op te beëindigen ([SWS_DM_00323], [SWS_DM_00333]). De DM wacht op de voltooiing, die de handler bevestigt door het aanroepen van UdsTransportProtocolMgr::HandlerStopped() ([SWS_DM_00340]). Na terugkeer uit Stop() is elke methode-aanroep van de plugin aan de manager, met uitzondering van HandlerStopped(), verboden ([SWS_DM_01741]). De vrijgave van de resources vindt tenslotte plaats via de virtuele destructor ([SWS_DM_09016]). Terwijl de constructor thread-safe is, zijn de operationele interfacemethoden als niet thread-safe gedeclareerd.

Toestandsdiagram: levenscyclusfasen en toestandsovergangen van een UDS-transport-handler. Bronnen: [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00329], [SWS_DM_01745], [SWS_DM_01746]

Gebruikspad

Tijdens de reguliere diagnosewerking verwerkt de handler inkomende berichten en verzendt hij antwoorden. Zodra op de netwerkinterface ten minste bronadres, doeladres, adrestype (fysiek of functioneel), totale berichtlengte en bij payload van meerdere bytes de eerste twee bytes (payloadInfo) beschikbaar zijn, meldt de implementatie het verzoek via UdsTransportProtocolMgr::IndicateMessage() aan de manager ([SWS_DM_00342], AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”). Elk verzoek is toegewezen aan een uniek kanaal (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”). Voor de beantwoording draagt de DM het diagnose-antwoord over aan dezelfde handler en hetzelfde kanaal middels Transmit(message, channelId) ([SWS_DM_00327], [SWS_DM_00348]). Na de fysieke overdracht geeft de handler het overgedragen berichtobject terug aan de manager via UdsTransportProtocolMgr::TransmitConfirmation() ([SWS_DM_00327], [SWS_DM_00351]). Een gespecialiseerd gebruikstraject betreft ECU-resets (UDS-service 0x11) met een positief antwoord na de herstart: hierbij verzoekt de DM vóór de reset via NotifyReestablishment(channelId) dat de handler de verbindingsinformatie niet-vluchtig bewaart; na herstart en hernieuwde Start() meldt de handler het herstel van hetzelfde kanaal via ChannelReestablished() ([SWS_DM_00326], [SWS_DM_01744]).

Foutscenario's

Mislukt de initialisatie van de transportlaag en retourneert Initialize() de status InitializationResult::kInitializeFailed, dan breekt de DM het opstartproces van dit protocol onmiddellijk af en roept op deze instantie geen verdere methoden meer aan ([SWS_DM_01745], [SWS_DM_09017]). Worden periodieke overdrachten niet ondersteund op het transportprotocol, dan levert de aanroep van GetPeriodicHandler() een ara::core::Result op met de foutcode kConfigurationMismatch ([SWS_DM_01068]). Kan een aangevraagd kanaalherstel voor een ECU-reset niet worden gegarandeerd, dan faalt NotifyReestablishment() en signaleert dit via de retourwaarde false ([SWS_DM_00326]). Mislukt ten slotte het verzendproces van een diagnose-antwoord op de netwerklaag, dan moet de handler dit bij de bevestiging aan de manager meedelen door het argument result in TransmitConfirmation() op kTransmitFailed in te stellen ([SWS_DM_00351]).

              functie NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
