Context

De klasse apext::diag::uds_transport::UdsTransportProtocolHandler is de abstracte basisklasse voor specifieke en propriëtaire UDS-transportprotocol-plug-ins in Diagnostic Management (DM) van AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). Ze ontkoppelt de generieke diagnose-Core van de bijzonderheden van concrete overdrachtsnetwerken en transportlagen zoals DoIP of op CAN gebaseerde protocollen.

Een transporthandler communiceert in wezen met drie partners:

  • Diagnostic Management Core: De DM beheert de volledige levenscyclus van de handler en stelt via de managerreferentie apext::diag::uds_transport::UdsTransportProtocolMgr de tegenpartij voor status- en data-indicaties beschikbaar ([SWS_DM_09015], [SWS_DM_09025]).
  • Netwerklaag en diagnoseclient: De plug-in handelt de fysieke respectievelijk logische gegevensuitwisseling met de voertuigexterne of -interne diagnosetester af ([SWS_DM_00326], [SWS_DM_00351]).
  • Periodieke handler (optioneel): Ondersteunt het betreffende transportprotocol periodieke overdrachten, dan stelt de handler via GetPeriodicHandler() een referentie naar een UdsTransportProtocolPeriodicHandler beschikbaar ([SWS_DM_01068]).

Levenscyclus

De levenscyclus van een transportprotocol-implementatie wordt strikt gestuurd door de DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”, [SWS_DM_00329]). De creatie vindt plaats via de constructor UdsTransportProtocolHandler(handlerId, transportProtocolMgr), waarbij de DM aan de handler een unieke identifier van het type UdsTransportProtocolHandlerID evenals de referentie naar de bijbehorende UdsTransportProtocolMgr toewijst ([SWS_DM_09015], [SWS_DM_09025]). De toegekende ID kan op elk moment via GetHandlerID() worden opgevraagd ([SWS_DM_00325]). De constructor is aangeduid als thread-safe ([SWS_DM_09015]).

Om bewerkelijke protocolinitialisaties los te koppelen van de constructor, roept de DM vervolgens Initialize() aan ([SWS_DM_00319], [SWS_DM_00329]). Met uitzondering van GetPeriodicHandler() mag de DM vóór een succesvolle retournering van InitializationResult::kInitializeOk geen andere methoden van de handler aanroepen ([SWS_DM_01746], [SWS_DM_09017]). Na succesvolle initialisatie start de DM het protocol via Start() ([SWS_DM_00322]). Omdat Start() asynchroon wordt uitgevoerd, kan de DM meerdere handlers parallel laten opstarten om de opstarttijd te minimaliseren ([SWS_DM_00322]).

Wanneer de DM-applicatie overgaat naar de toestand ApplicationState.kTerminating, roept zij Stop() aan (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). De DM wacht totdat de handler de stop via UdsTransportProtocolMgr::HandlerStopped(handlerId) bevestigt ([SWS_DM_00340]). Na terugkeer van Stop() mag de handler-plug-in geen verdere methoden op de manager aanroepen – met als enige uitzondering de bevestiging HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). De daaropvolgende afbouw vindt plaats via de virtuele destructor ([SWS_DM_09016]).

Toestandsdiagram: levenscyclusfasen en overgangsvoorwaarden van een UDS-transportprotocolhandler. Bronnen: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Gebruikspad

Tijdens normaal bedrijf verzorgt de handler de bidirectionele uitwisseling van UDS-berichten:

  1. Ontvangst van berichten (indicatie): Zodra op een kanaal een nieuw UDS-bericht binnenkomt en bronadres, doeladres, adresseringstype (fysiek of functioneel), totale berichtlengte evenals de eerste payloadbytes (bij berichten groter dan één byte minimaal twee bytes) bekend zijn, roept de plug-in UdsTransportProtocolMgr::IndicateMessage(...) aan (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 “Indication of UDS message reception”, [SWS_DM_00342], [SWS_DM_00330]). Hierbij geeft de handler de kanaalidentificatie door in de parameter globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”).
  2. Verzending van berichten (transmissie): De DM zendt het bijbehorende UDS-diagnoseantwoord via dezelfde handler en hetzelfde kanaal terug (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”, [SWS_DM_00348]). Hiervoor roept hij Transmit(message, channelId) aan ([SWS_DM_00327]). Het bericht wordt als UdsMessageConstPtr naar de aard van een std::unique_ptr aan de handler overgedragen.
  3. Verzendbevestiging: Zodra het bericht via het netwerk is verstuurd (of er een fout is opgetreden), moet de handler het eigendom van message via UdsTransportProtocolMgr::TransmitConfirmation(result, message) aan de DM teruggeven ([SWS_DM_00327]). Het resultaat wordt daarbij als kTransmitOk of kTransmitFailed verzonden (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Een ander specifiek gebruikspad is het herstel van kanalen na een ECU-reset (UDS-dienst 0x11 met positief antwoord na reset): hierbij roept de DM vóór de herstart NotifyReestablishment(channelId) aan ([SWS_DM_00326]). De plug-in slaat de verbindingsparameters (bijvoorbeeld IP-adressen en poorten) persistent op. Na de herstart via Start() herkent de plug-in de herverbinding van dezelfde diagnoseclient en informeert de DM via UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Sequentiediagram: ontvangst van UDS-berichten, antwoordoverdracht en aansluitende bevestiging. Bronnen: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Foutscenario's

De interface behandelt verschillende uitzonderings- en foutsituaties:

  • Mislukte initialisatie: Retourneert Initialize() de waarde InitializationResult::kInitializeFailed ([SWS_DM_09017]), dan breekt de DM het startproces van dit transportprotocol volledig af en roept op deze instantie geen enkele verdere methode aan ([SWS_DM_01745]).
  • Niet-ondersteunde periodieke overdrachten: Ondersteunt het concrete protocol geen periodieke overdrachten, dan retourneert de aanroep van GetPeriodicHandler() een ara::core::Result met de foutcode kConfigurationMismatch ([SWS_DM_01068]).
  • Weigering van kanaalherstel: Kan een plug-in de persistente reservering voor een kanaal niet vervullen (bijvoorbeeld bij het ontbreken van een niet-vluchtige opslagmogelijkheid of een onstabiele toewijzing), dan retourneert NotifyReestablishment(channelId) de waarde false ([SWS_DM_00326]).
  • Transmissiefout in het netwerk: Kon de netwerklaag een via Transmit() opgedragen bericht niet verzenden, dan moet de handler het resultaat kTransmitFailed in TransmitConfirmation doorgeven ([SWS_DM_00351]). Het niet teruggeven van de buffer leidt tot resourcelekken in de DM.
  • Sequentieschending na het stoppen: Roept een plug-in na terugkeer uit Stop() een andere methode dan HandlerStopped() op de UdsTransportProtocolMgr aan, dan is er sprake van een schending van de protocolsequentie ([SWS_DM_00323], [SWS_DM_01741]).

Deze klassehandleiding is gebaseerd op de specificatie AUTOSAR Adaptive R25-11.

              functie NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
