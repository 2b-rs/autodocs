EcuM_CheckRamHash function

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation function

This callout is called by the EcuM to validate a wakeup source. If a valid wakeup has been detected, it shall be reported to EcuM via EcuM_ValidateWakeupEvent().

EcuM_CheckWakeup function

This callout is called by the EcuM to poll a wakeup source. It shall also be called by the ISR of a wakeup source to set up the PLL and check other wakeup sources that may be connected to the same interrupt.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);

EcuM_DeterminePbConfiguration function

This callout should evaluate some condition, like port pin or NVRAM value, to determine which post-build configuration shall be used in the remainder of the startup process. It shall load this configuration data into a piece of memory that is accessible by all BSW modules and shall return a pointer to the EcuM post-build configuration as a base for all BSW module post-build configrations.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources function

The ECU Manager Module calls EcuM_DisableWakeupSources to set the wakeup source(s) defined in the wakeupSource bitfield so that they are not able to wake the ECU up.

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources function

The ECU Manager Module calls EcuM_EnableWakeupSource to allow the system designer to notify wakeup sources defined in the wakeupSource bitfield that SLEEP will be entered and to adjust their source accordingly.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup function

This API is called by any SW Module whose wakeup source is checked asynchronously (e.g. asynchronous Can Trcv Driver) and the Check of the Wakeup returns a negative Result (no Wakeup by this Source). The API cancels the CheckWakeupTimer for the WakeupSource. If the correponding CheckWakeupTimer is canceled the check of this wakeup source is finished.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook function

The ECU State Manager will call the error hook if the error codes "ECUM_E_RAM_CHECK_ FAILED" or "ECUM_E_CONFIGURATION_DATA_INCONSISTENT" occur. In this situation it is not possible to continue processing and the ECU must be stopped. The integrator may choose the modality how the ECU is stopped, i.e. reset, halt, restart, safe state etc.

void EcuM_ErrorHook (uint16 reason);

Systemarchitektur und Rolle des Modulclusters

Das Cluster „System Services“ umfasst die Module, die Hochlauf, Betriebsmodi, Sleep/Shutdown und die Programmablaufüberwachung eines Classic-Platform-Steuergeräts tragen. Der ECU State Manager ist dabei der Systemdienst, der nach dem OS-Shutdown den finalen Hardware-Zustand herstellt (SWS EcuM S. 82, [SWS_EcuM_04020]). Die vier Module haben klar getrennte Rollen:

  • BswM arbitriert eingehende Modusanzeigen ([SWS_BswM_00035]). Regeln verknüpfen ModeRequestPorts logisch und lösen True- oder False-Aktionslisten aus (Mode Management Guide S. 32). Aktionen laufen ausschließlich im Kontext einer Aktionsliste ([SWS_BswM_00147]).
  • EcuM initialisiert die BSW, startet und beendet das OS und verwaltet die Zustände der Wakeup-Quellen ([SWS_EcuM_02811], [SWS_EcuM_04091]). Eine eigene Zustandsmaschine besitzt er nicht. Zustandswechsel übernimmt er vom BswM (SWS EcuM S. 99, [SWS_EcuM_04116]).
  • WdgM überwacht Supervised Entities über Checkpoints ([SWS_WdgM_00263]) und bildet daraus einen Global Supervision Status ([SWS_WdgM_00360]). Watchdog-Modi setzt er über WdgIf_SetMode ([SWS_WdgM_00186]).
  • Wdg treibt interne oder externe Watchdog-Hardware ([SWS_Wdg_00161], [SWS_Wdg_00076]). Er bedient die Hardware, solange die Triggerbedingung gültig ist ([SWS_Wdg_00144]).

Kontextdiagramm: Das Kontextdiagramm zeigt BswM als Entscheider über Modi, EcuM als Ausführer der Lebenszyklus-Sequenzen und die Überwachungskette WdgM → WdgIf → Wdg → Hardware. Quellen: SWS EcuM S. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Zusammenspiel und Interaktionspfade

EcuM ↔ BswM (ECU Mode Handling): Dieser Pfad ist aktiv, wenn EcuMModeHandling konfiguriert ist ([SWS_EcuM_04115]). SW-Cs fordern RUN und POST_RUN über EcuM_RequestRUN bzw. EcuM_RequestPOST_RUN an und geben sie wieder frei ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). Das Arbitrierungsergebnis meldet EcuM über BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). Der BswM setzt den Zustand anschließend per EcuM_SetState ([SWS_EcuM_04122]). Sobald die RTE den Wechsel bestätigt hat, meldet EcuM den Zustand über BswM_EcuM_CurrentState zurück ([SWS_EcuM_04143], [SWS_BswM_91003]).

Wakeup-Pfad: Treiber melden Wakeups per EcuM_SetWakeupEvent, das das Ereignis als pending markiert ([SWS_EcuM_01117]). Ist eine Validierung erforderlich, startet EcuM das Validierungsprotokoll ([SWS_EcuM_02975]). Die Validierung übernimmt genau ein BSW-Modul (SWS EcuM S. 69). Dessen Aufruf von EcuM_ValidateWakeupEvent benachrichtigt BswM und ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). Jeder Zustandswechsel einer Wakeup-Quelle wird dem BswM als Modusanforderung gemeldet ([SWS_EcuM_04003]).

Zustandsdiagramm: Das Zustandsdiagramm zeigt die Lebenszyklen einer Wakeup-Quelle (NONE, PENDING, VALIDATED, EXPIRED) und die BswM-Meldung beim Eintritt in jeden Zustand. Quellen: [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM S. 64

WdgM → Wdg: Wdg_SetTriggerCondition nimmt einen Timeout in Millisekunden entgegen und rechnet ihn intern unter Berücksichtigung des aktuellen Modus in einen Zählerwert um ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). Die Wartungsroutine des Treibers verhält sich so:

  • Ist der Zähler größer als null, dekrementiert sie ihn und triggert die Hardware ([SWS_Wdg_00134]).
  • Bei null triggert sie nicht mehr, der Watchdog läuft ab ([SWS_Wdg_00135]).

Interpretation: WdgIf dürfte Modus und Triggerbedingung an die jeweils adressierte Wdg-Instanz weiterleiten. Mehrere Instanzen tragen eindeutige Namen ([SWS_Wdg_00172]).

EcuM → WdgM (Reset): WdgM_PerformReset ist ein Pflicht-Reset-Ziel ([SWS_EcuM_04005], [SWS_EcuM_04044]). Es setzt die Triggerbedingung aller Treiber auf 0, und die Hardware-Watchdogs lösen dadurch einen Reset aus ([SWS_WdgM_00264], SWS WdgM S. 82). Als Shutdown-Ursache steht ECUM_CAUSE_WDGM bereit ([SWS_EcuM_04045]).

Synchronisation, Reentranz und Task-Kontexte

BswM_MainFunction: Sie wertet alle Regeln aus, die eine Anforderung mit BSWM_DEFERRED verwenden ([SWS_BswM_00075]). BswM-Timer werden immer deferred behandelt ([SWS_BswM_00220]). Anforderungen mit „immediate“ werden dagegen sofort ausgewertet (Mode Management Guide S. 32).

EcuM_MainFunction: Sie läuft in allen EcuM-Instanzen ([SWS_EcuM_04011]). Sie überwacht die Validierungs-Timeouts ([SWS_EcuM_04082]) und validiert Wakeup-Kandidaten nach dem WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction: Sie startet die Überwachung beim ersten Aufruf nach WdgM_Init ([SWS_WdgM_00406]) und berechnet danach in jeder Periode den Global Supervision Status (SWS WdgM S. 34).

Interrupt-Kontext: Die Wakeup-Dienste sind aus Interrupt-, OS- und OS-freiem Kontext aufrufbar ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). Sie sind jedoch als „Non-Reentrant, Non-Interruptible“ spezifiziert ([SWS_EcuM_02826], [SWS_EcuM_02828]). Eine Ausnahme ist EcuM_ValidateWakeupEvent: Es ist reentrant und aus Interrupt- und Task-Kontext aufrufbar ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Reentranz von WdgM und Wdg:

  • WdgM_SetMode, WdgM_DeInit und Wdg_SetTriggerCondition sind nicht reentrant ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • WdgM_GetMode liefert während eines laufenden Moduswechsels noch den alten Modus ([SWS_WdgM_00168], SWS WdgM S. 77).
  • Wdg sperrt Interrupts für Datenkonsistenz nur über die vorgesehenen BSW-Mechanismen ([SWS_Wdg_00040]).

Multicore: Auf jedem Core läuft eine eigene EcuM-Instanz. Der Master-EcuM startet die übrigen Cores (SWS EcuM S. 71). Daraus folgen diese Pflichten:

  • Jede Instanz verarbeitet die Wakeups ihres eigenen Cores ([SWS_EcuM_04012]).
  • Alle core-lokalen BswM werden initialisiert ([SWS_EcuM_04014]).
  • Pro Core wird eine Ressource RES_AUTOSAR_ECUM reserviert ([SWS_EcuM_03010]).
  • Die C-APIs stehen in jeder Partition bereit, in der ein EcuM läuft ([SWS_EcuM_04095]).

Der BswM ist für Mehrpartitionssysteme bedingt reentrant ([SWS_BswM_00002]).

Lebenszyklen und Betriebsmodi

Hochlauf (StartPreOS): EcuM_Init führt die StartPreOS-Sequenz aus ([SWS_EcuM_02684]). Sie umfasst:

  • die Init-Blöcke 0 und 1 in konfigurierter Reihenfolge ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • die Auswahl der Post-Build-Konfiguration ([SWS_EcuM_02906]),
  • die Konsistenzprüfung aller Post-Build-Konfigurationen vor der ersten BSW-Initialisierung ([SWS_EcuM_02796]).

Laut Strukturbeschreibung gehört Wdg_Init zu den vom EcuM genutzten Init-Funktionen (SWS EcuM S. 34). Wdg_Init setzt Standardmodus und Timeout ([SWS_Wdg_00001]).

Hochlauf (StartPostOS): EcuM_StartupTwo läuft in einem durch StartOS gestarteten Task ([SWS_EcuM_02806]). Es startet SchM und initialisiert BswM ([SWS_EcuM_02932]). BswM_Init setzt nur ein initialisiertes OS und SchM voraus (SWS BswM S. 69). Weitere Treiber kann der BswM in der UP-Phase initialisieren, etwa über EcuM_AL_DriverInitBswM_<x> (SWS EcuM S. 46, [SWS_EcuM_04114]).

Sequenzdiagramm: Das Sequenzdiagramm zeigt die Reihenfolge von StartPreOS und StartPostOS auf dem Master-Core. Quellen: [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM S. 82, SWS EcuM S. 42

Sleep: Vor EcuM_GoDownHaltPoll muss typischerweise der BswM ein SLEEP-Ziel gewählt haben (SWS EcuM S. 54, [SWS_EcuM_91002]). Der Ablauf:

  1. GoSleep aktiviert die Wakeup-Quellen; das OS bleibt dabei aktiv ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. Danach folgt je nach Sleep-Modus Halt mit RAM-Hash ([SWS_EcuM_02863]) oder Poll ([SWS_EcuM_02962]). Kein Wakeup darf dabei verloren gehen ([SWS_EcuM_02188]).
  3. Ein Wakeup führt in die WakeupRestart-Sequenz mit Treiber-Neuinitialisierung ([SWS_EcuM_02963], [SWS_EcuM_02923]).

In R20-11 heißt das Poll-Callout EcuM_CheckWakeup ([SWS_EcuM_02929]). Erst ab R21-11 heißt es EcuM_CheckWakeupHook (SWS EcuM S. 145).

Watchdog im Sleep: Vor dem Sleep wechselt WdgM_DeInit in einen Sleep-Modus mit verträglichen Triggerbedingungen und stoppt die Überwachung (SWS WdgM S. 59, [SWS_WdgM_00407]). Die Strukturbeschreibung des EcuM nennt jedoch nur WdgM_PerformReset als WdgM-Abhängigkeit. Der Aufruf von WdgM_DeInit erfolgt daher vermutlich über eine BswM-Aktion oder Integrationscode.

Sequenzdiagramm: Das Sequenzdiagramm zeigt die SLEEP-Phase mit Halt: GoSleep, RAM-Hash, Wakeup und WakeupRestart. Quellen: SWS EcuM S. 54, SWS EcuM S. 55, SWS EcuM S. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown: Der Ablauf:

  1. OffPreOS deinitialisiert BswM und SchM (SWS EcuM S. 90). Danach verarbeitet der BswM keine Modi mehr ([SWS_BswM_00120]).
  2. Als letzte Aktivität ruft EcuM ShutdownOS auf ([SWS_EcuM_02952]). Der Shutdown-Hook ruft EcuM_Shutdown ([SWS_EcuM_02953]).
  3. Abschließend folgen EcuM_AL_Reset oder EcuM_AL_SwitchOff ([SWS_EcuM_04074], [SWS_EcuM_04075]).

Wakeup-Quellen sind vor Dem_Shutdown und NvM_WriteAll über BswM-User-Callouts zu löschen (SWS EcuM S. 124, [SWS_BswM_00054]). Ein Wakeup während des Shutdowns führt zum Neustart nach dessen Abschluss ([SWS_EcuM_02756]). Wdg besitzt keine eigene De-Init-Schnittstelle ([SWS_Wdg_00031]).

Fehlerbehandlung, DET-Tracing und Degradation

Entwicklungsfehler (DET):

  • BswM ignoriert Anzeigen vor der Initialisierung und meldet BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). Fehlschlagende Aktionen meldet er als Laufzeitfehler BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • EcuM meldet doppelte RUN-Anforderungen und unpassende Freigaben ([SWS_EcuM_03024], [SWS_EcuM_03023]) sowie unbekannte Wakeup-Quellen ([SWS_EcuM_02867]).
  • WdgM und Wdg definieren eigene Fehlercodes ([SWS_WdgM_00004], [SWS_Wdg_00010]). Ein fehlgeschlagenes WdgIf_SetMode meldet WdgM als WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Nicht behebbare Fehler: Diese leitet EcuM an EcuM_ErrorHook weiter ([SWS_EcuM_04033]). Beispiele sind inkonsistente Konfigurationsdaten oder eine fehlgeschlagene RAM-Prüfung ([SWS_EcuM_91003]). Fehler, die während der Initialisierung von Init-Funktionen zurückgegeben werden, ignoriert EcuM ([SWS_EcuM_02980]).

Degradation der Überwachung: Der globale Status startet als WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Moduswechsel sind nur in den Zuständen OK und FAILED erlaubt ([SWS_WdgM_00145]). Das Abschalten des Watchdogs kann per Konfiguration verboten werden ([SWS_WdgM_00031]). Die Eskalation verläuft so:

  1. Im Zustand EXPIRED wird die Fehlerreaktion um eine konfigurierbare Toleranz aufgeschoben (SWS WdgM S. 34).
  2. Im Zustand STOPPED meldet WdgM WDGM_E_SUPERVISION, und ein Watchdog-Reset folgt ([SWS_WdgM_00375]).
  3. Auch ein fehlgeschlagener Moduswechsel führt nach STOPPED (SWS WdgM S. 57).

Diagnose nach dem Reset: Die zuerst abgelaufene SEID wird doppelt-invers in nicht initialisiertem RAM abgelegt. Sie ist schon vor WdgM_Init lesbar ([SWS_WdgM_00348], [SWS_WdgM_00349]). Statuswechsel meldet WdgM über Mode-Ports ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset existiert in R20-11 noch ([SWS_BswM_00157]), wird aber ab R21-11 obsolet (SWS BswM S. 2).

Treiberfehler und letzte Absicherung: Wdg meldet die Produktionsfehler WDG_E_MODE_FAILED und WDG_E_DISABLE_REJECTED an den DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). Hängt EcuM_AL_SwitchOff in einem Deadlock, setzt der Hardware-Watchdog das Steuergerät zurück (SWS EcuM S. 141).
