AUTOSAR Classic CAN

Can_ConfigType type

This is the type of the external data structure containing the overall initialization data for the CAN driver and SFR settings affecting all controllers. Furthermore it contains pointers to controller configuration structures. The contents of the initializ ation data structure are CAN hardware specific.

Can_ControllerStateType type

States that are used by the several Controller Mode functions.

Can_ErrorStateType type

Error states of a CAN controller.

Can_ErrorType type

The enumeration represents a superset of CAN Error Types which typical CAN HW is able to report. That means not all CAN HW will be able to support the complete set.

Can_HwHandleType type

Represents the hardware object handles of a CAN hardware unit. For CAN hardware units with more than 255 HW objects use extended range.

Can_HwType type

This type defines a data structure which clearly provides an Hardware Object Handle including its corresponding CAN Controller and therefore Can Drv as well as the specific Can Id.

Can_IdType type

Represents the Identifier of an L - PDU. The two most significant bits specify the frame type: 00 CAN message with Standard CAN ID 01 CAN FD frame with Standard CAN ID 10 CAN message with Extended CAN ID 11 CAN FD frame with Extended CAN ID

Can_PduType type

This type unites Pdu Id (sw Pdu Handle), Sdu Length (length), Sdu Data (sdu), and Can Id (id) for any CAN L - SDU.

Stellt Hardwaretreiber, Schnittstellenabstraktion, Segmentierung und Transceiversteuerung für CAN bereit.

Der Cluster verbindet CAN-Treiber, CAN Interface, das Transportprotokoll nach ISO 15765-2 und den Transceiver-Treiber zum unteren Teil des CAN-Kommunikationsstacks. Obere Schichten senden über CanIf_Transmit(). CanIf bildet die L-PDUs auf Hardwareobjekte ab, puffert sie bei belegter Hardware und verteilt Empfangs- und Bestätigungsmeldungen [SWS_CANIF_00005]. CanTp segmentiert große Nachrichten und holt die Daten schrittweise über PduR [SWS_CanTp_00086]. Gesendet wird nur, wenn der Controller im Zustand CAN_CS_STARTED und der PDU-Kanal sendebereit ist; die Modi steuert CanSM über CanIf.

Der Cluster bildet den unteren Teil des CAN-Kommunikationsstacks. Can steuert Controller und Mailboxen, CanIf abstrahiert Treiber, Controller und Transceiver, CanTp segmentiert nach ISO 15765-2, und CanTrcv verwaltet die Betriebsmodi des Transceivers. CanIf greift auf Hardwarepuffer nur über Treiberdienste zu [SWS_CANIF_00023]. Für obere Schichten stellt es einheitliche Bereiche für ControllerId und TransceiverId bereit [SWS_CANIF_00653] [SWS_CANIF_00655].

Kontextdiagramm: CanIf vermittelt zwischen PduR, CanTp, CanSM und EcuM einerseits und den Treibern Can und CanTrcv andererseits. Quellen: [SWS_CANIF_00005] [SWS_CANIF_00006] [SWS_CANIF_00358]

Beim Senden ruft CanIf_Transmit() mit der passenden HTH Can_Write() auf [SWS_CANIF_00318]. Meldet der Treiber CAN_BUSY, puffert CanIf die L-PDU [SWS_CANIF_00381]. Während der Sendebestätigung sendet es den höchstpriorisierten gepufferten Eintrag nach [SWS_CANIF_00668]. Empfangene L-PDUs durchlaufen in CanIf Softwarefilter und Datenlängenprüfung, bevor CanIf sie an CanTp oder PduR weiterleitet [SWS_CANIF_00389] [SWS_CANIF_00390]. CanTp puffert keine Nutzdaten selbst, sondern holt sie über PduR_CanTpCopyTxData() bzw. übergibt sie über PduR_CanTpCopyRxData() [SWS_CanTp_00086] [SWS_CanTp_00269].

Sequenzdiagramm: direkter Versand oder Pufferung bei CAN_BUSY, gefolgt vom Nachsenden aus dem Puffer in CanIf_TxConfirmation. Quellen: [SWS_CANIF_00381] [SWS_CANIF_00183]

Can arbeitet interrupt- oder pollinggesteuert über seine MainFunctions [SWS_Can_00225] [SWS_Can_00226]. CanTp_RxIndication() muss im Interrupt-Kontext aufrufbar sein [SWS_CanTp_00235], während CanTp_MainFunction() die Protokoll-Timeouts überwacht [SWS_CanTp_00164]. CanIf schützt gemeinsame Puffer gegen präemptive Zugriffe [SWS_CANIF_00064].

Nach der Initialisierung stehen alle CanIf-Kanäle auf CANIF_OFFLINE [SWS_CANIF_00864]. CanSM schaltet die Controller über CanIf_SetControllerMode() [SWS_CANIF_00308]. SLEEP erzwingt CANIF_OFFLINE, STOPPED oder BusOff erzwingen CANIF_TX_OFFLINE [SWS_CANIF_00865] [SWS_CANIF_00866]. Einen BusOff meldet CanIf an CanSM [SWS_CANIF_00724]. Fehler gehen an DET; CanTrcv meldet zusätzlich CANTRCV_E_BUS_ERROR an DEM [SWS_CanTrcv_00206]. CanTp bricht Sitzungen bei Timeouts mit negativer Bestätigung ab [SWS_CanTp_00310].

Systemarchitektur und Rolle des Clusters

Der Cluster „CAN Communication“ bildet den unteren Teil des AUTOSAR-Kommunikationsstacks für CAN. Er reicht vom hardwarenahen CAN-Treiber bis zum Transportprotokoll, auf das PduR und DCM aufsetzen. Kern ist das CAN Interface, das obere Schichten von Treiber- und Hardwaredetails entkoppelt. Es greift auf hardwarespezifische Kommunikationspuffer ausschließlich über die Dienste des Treibers zu [SWS_CANIF_00023]. Controller und Transceiver mehrerer Treiberinstanzen abstrahiert es über eigene Bereiche für ControllerId und TransceiverId [SWS_CANIF_00653] [SWS_CANIF_00655].

CanIf prüft dabei, ob für die frei gewordene HTH Einträge gepuffert sind. Synchronisation, Reentranz und Task-Kontexte

CanIf_Transmit() ist für verschiedene PduIds reentrant, für dieselbe PduId nicht [SWS_CANIF_00005]. CanIf muss präemptive Zugriffe auf gemeinsame Ressourcen gegeneinander schützen [SWS_CANIF_00064]. Das betrifft insbesondere die Sendepuffer [SWS_CANIF_00033], die CanId dynamischer L-PDUs während CanIf_SetDynamicTxId() [SWS_CANIF_00673] und den Empfangspuffer während CanIf_ReadRxPduData() [SWS_CANIF_00199].

Can unterstützt Interrupt- und Polling-Betrieb. Die MainFunctions pollen je nach Konfiguration Sendebestätigungen, Empfang, BusOff, Wakeup und den Controllermodus [SWS_Can_00225] [SWS_Can_00226] [SWS_Can_00227] [SWS_Can_00228] [SWS_Can_00368] CanIf S. 152. Callbacks wie CanIf_ControllerBusOff() laufen daher wahlweise auf Interrupt- oder auf Task-Ebene CanIf S. 119. Can_DisableControllerInterrupts() und Can_EnableControllerInterrupts() wirken verschachtelt: Jede Sperre erfordert eine eigene Freigabe [SWS_Can_00231] [SWS_Can_00232] Can S. 61.

CanTp_RxIndication() und CanTp_TxConfirmation() müssen im Interrupt-Kontext aufrufbar sein [SWS_CanTp_00235] [SWS_CanTp_00236]. CanTp_MainFunction() bedient zyklisch die Timer N_As, N_Bs, N_Cs, N_Ar, N_Br, N_Cr und STmin [SWS_CanTp_00213] [SWS_CanTp_00164]. Ihr Takt folgt dem Parameter CanTpMainFunctionPeriod [SWS_CanTp_00300]. Interpretation: Diese Periode bestimmt vermutlich die erreichbare Auflösung der Timeouts. Jede Verbindung nutzt eigene Puffer, Timer und eine eigene Zustandsmaschine [SWS_CanTp_00122] CanTp S. 42. CanTrcv_MainFunction() sucht zyklisch auf Bussen in STANDBY und SLEEP nach Weckereignissen [SWS_CanTrcv_00013] [SWS_CanTrcv_00112].

Die Controller-Zustände sind UNINIT, STOPPED, STARTED und SLEEP [SWS_Can_91013] Can S. 38. Darüber liegen die PDU-Kanalmodi von CanIf [SWS_CANIF_00137]. CanIf_SetPduMode() wird nur im Zustand CAN_CS_STARTED angenommen [SWS_CANIF_00874]. SLEEP erzwingt CANIF_OFFLINE; STOPPED oder BusOff erzwingen CANIF_TX_OFFLINE [SWS_CANIF_00865] [SWS_CANIF_00866].

Fehlerbehandlung, DET-Tracing und Degradation

Alle Module des Clusters melden Entwicklungsfehler an DET. CanIf tut dies etwa bei einer ungültigen TxPduId oder einem Null-Zeiger [SWS_CANIF_00319] [SWS_CANIF_00320]. CanTp liefert dabei zusätzlich E_NOT_OK zurück [SWS_CanTp_00294]; Can und CanTrcv verwenden eigene Fehlercodes [SWS_Can_91019] [SWS_CanTrcv_00050]. Laufzeitfehler betreffen unter anderem abgelehnte Datenlängen [SWS_CANIF_00168], Sendeversuche auf Kanälen im Modus CANIF_OFFLINE [SWS_CANIF_00382], verlorene Empfangsnachrichten [SWS_Can_91020] und fehlende Kommunikation mit dem Transceiver [SWS_CanTrcv_00113].
