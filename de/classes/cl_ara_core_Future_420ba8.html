Ermöglicht den synchronen oder asynchronen Empfang von Werten und Fehlern aus einer nebenläufigen Operation.

Die Klasse ara::core::Future dient als Empfänger-Handle für das Ergebnis einer asynchronen Operation und verwaltet den Zugriff auf einen gemeinsamen Zustand [SWS_CORE_00327]. Konsumenten können den Zustand nicht-blockierend prüfen, synchron auf die Fertigstellung warten oder das Ergebnis über GetResult() ausnahmefrei als ara::core::Result entgegennehmen [SWS_CORE_00336]. Da Kopieroperationen gelöscht sind, wird der Besitz exklusiv verwaltet, und nach der Ergebnisabholung oder Weiterleitung mittels Continuation wird das Objekt unmittelbar ungültig.

Kontext

Die Template-Klasse ara::core::Future stellt das Empfänger-Endelement für Ergebnisse asynchroner Operationen innerhalb der AUTOSAR Adaptive Platform dar. Sie ermöglicht den kontrollierten Zugriff auf einen gemeinsamen Zustand (Shared State), der von einer erzeugenden Instanz asynchron befüllt wird [SWS_CORE_00327]. Konzeptionell implementiert die Klasse std::future aus dem C++17-Standard ISO/IEC 14882:2017 [11], integriert sich jedoch nahtlos in das fehlerausnahmebasierte Konzept der Plattform: Für den Template-Parameter E ist zwingend der Fehlertyp ara::core::ErrorCode vorgegeben; jede abweichende Spezifikation führt zu einem Übersetzungsfehler. Zu den primären Interaktionspartnern zählen der asynchrone Erzeuger (wie ein assoziiertes Promise), welcher den Wert oder Fehler bereitstellt, die Future-Instanz als exklusiver Empfänger sowie ein Konsument oder Ausführungskontext (ExecutorT), an den Folgeaufgaben übergeben werden [SWS_CORE_00331] [SWS_CORE_00337].

Lebenszyklus

Die Erzeugung, Zustandsverwaltung und Vernichtung von ara::core::Future unterliegt strengen Regeln zur Gewährleistung deterministischer Besitzverhältnisse:

  • Erzeugung: Der Standardkonstruktor erzeugt eine leere Instanz ohne Shared State, für die valid() == false gilt [SWS_CORE_00322] [SWS_CORE_00327]. Interpretation: Gültige Instanzen entstehen regulär durch asynchrone Plattform-Schnittstellen oder gekoppelte Promise-Objekte.
  • Besitz und Übertragung: Kopierkonstruktor und Kopierzuweisungsoperator sind explizit gelöscht (delete), sodass ein Duplizieren des Zugriffsgriffs ausgeschlossen ist [SWS_CORE_00334] [SWS_CORE_00335]. Das Verschieben (Move) von Instanzen ist über den Move-Konstruktor und Move-Zuweisungsoperator möglich und überträgt die Eigentümerschaft am Shared State vollständig [SWS_CORE_00323] [SWS_CORE_00325].
  • Zustände und Übergänge: Der Zustand gliedert sich in ungültig (valid() == false), gültig-ausstehend (valid() == true, is_ready() == false) und bereit (valid() == true, is_ready() == true) [SWS_CORE_00327] [SWS_CORE_00332]. Nach erfolgreicher Ergebnisabholung via GetResult() oder get() sowie nach Weiterleitung mittels then() verliert das Objekt seinen Zustand und wird unmittelbar ungültig (valid() == false) [SWS_CORE_00326] [SWS_CORE_00331] [SWS_CORE_00336] [SWS_CORE_00337].
  • Zerstörung: Der Destruktor ~Future() gibt einen noch gehaltenen Shared State auf [SWS_CORE_00333]. Falls Fortsetzungen registriert wurden, blockiert der Destruktor der zurückgegebenen Instanz so lange, bis eine bereits laufende Fortsetzungsfunktion vollständig ausgeführt wurde [SWS_CORE_00331] [SWS_CORE_00337].
  • Nebenläufigkeit: Die Statusmethoden valid() und is_ready() sind threadsicher [SWS_CORE_00327] [SWS_CORE_00332]. Alle übrigen Schnittstellen – inklusive wait(), wait_for(), wait_until(), GetResult(), get(), then() und der Destruktor – sind für dieselbe Instanz nicht threadsicher [SWS_CORE_00323] [SWS_CORE_00325] [SWS_CORE_00326] [SWS_CORE_00328] [SWS_CORE_00329] [SWS_CORE_00330] [SWS_CORE_00331] [SWS_CORE_00333] [SWS_CORE_00336] [SWS_CORE_00337].

Nutzungspfad

Ein typischer Nutzungspfad zur Ergebnisverarbeitung gliedert sich in folgende Phasen:

  1. Statusprüfung und Synchronisation: Mit is_ready() kann vorab ermittelt werden, ob das asynchrone Ergebnis bereits vorliegt [SWS_CORE_00332]. Ist dies der Fall, blockieren nachfolgende Abrufe garantiert nicht mehr [SWS_CORE_00332]. Andernfalls kann mit wait() unbegrenzt [SWS_CORE_00328] oder zeitbeschränkt via wait_for() bzw. wait_until() synchronisiert werden [SWS_CORE_00329] [SWS_CORE_00330].
  2. Ergebnisextraktion: In AUTOSAR Adaptive Applikationen ist der Aufruf von GetResult() maßgeblich: Die Methode blockiert bei Bedarf, löst jedoch niemals Ausnahmen aus und übergibt den Wert oder Fehler als ara::core::Result<T, E> per Move [SWS_CORE_00336]. Die Methode get() bietet STL-Konformität, wirft im Fehlerfall C++-Ausnahmen und nimmt bei deaktivierter Ausnahmebehandlung der Toolchain nicht an der Überladungsauflösung teil [SWS_CORE_00326].
  3. Asynchrone Verkettung (Continuations): Anstelle synchronen Blockierens kann über then() ein Callback registriert werden, optional unter Zuweisung an einen Ausführungskontext (Executor) [SWS_CORE_00331] [SWS_CORE_00337]. Der Callback nimmt das Ergebnis als Result<T, E>-Rvalue entgegen. Liefert die Fortsetzungsfunktion selbst ein Future oder Result zurück, führt then() ein automatisches Unwrapping durch und liefert direkt ein entsprechendes Future<T2, E2> [SWS_CORE_00331] [SWS_CORE_00337].

Fehlerszenarien

Im Umgang mit ara::core::Future sind folgende Fehlersituationen spezifiziert:

  • Aufruf auf ungültiger Instanz: Der Aufruf von is_ready(), wait(), wait_for(), wait_until(), GetResult() oder then() bei einer ungültigen Instanz (valid() == false) stellt eine FutureInvalidViolation dar [SWS_CORE_00328] [SWS_CORE_00329] [SWS_CORE_00330] [SWS_CORE_00331] [SWS_CORE_00332] [SWS_CORE_00336] [SWS_CORE_00337]. Beim Aufruf von get() wird in diesem Fall eine FutureException mit dem Fehlercode kNoState geworfen [SWS_CORE_00326].
  • Verlassener Shared State (Broken Promise): Wird der Shared State vom assoziierten Promise vorzeitig aufgegeben, liefert GetResult() ein Result mit dem standardisierten Fehlercode FutureErrc::kBrokenPromise [SWS_CORE_00336]. Beim Aufruf von get() wird die entsprechende Ausnahme ausgelöst [SWS_CORE_00326].
  • Ausnahmen in Fortsetzungsfunktionen: Eine registrierte Continuation darf keine Ausnahmen werfen, außer zur Umsetzung einer Violation. Löst sie dennoch eine Ausnahme aus, führt dies zu einer FutureContinuationHasThrownViolation [SWS_CORE_00331] [SWS_CORE_00337]. Ausnahmen in Closures müssen abgefangen und als Fehlerzustand in Form eines Result oder Future zurückgegeben werden [SWS_CORE_00331] [SWS_CORE_00337].

Dieser Leitfaden basiert ausschließlich auf den Spezifikationsanforderungen von AUTOSAR Adaptive Core (R25-11).

Ein blockierungsfreier Aufruf kann vorab über is_ready() abgesichert werden [SWS_CORE_00332].
