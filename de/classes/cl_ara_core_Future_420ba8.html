class ara::core::Future

[SWS_CORE_00321] Upstream: RS_AP_00130

template <typename T, typename E = ErrorCode> class Future final {...};

Implementation of std::future from [future.syn] in [11]. The implementation shall flag the condition E != ara::core::ErrorCode as a compile error.

Kontext

Die Klasse ara::core::Future repräsentiert das lesende Ende einer asynchronen Operation innerhalb der AUTOSAR Adaptive Platform. Sie implementiert das aus dem C++-Standard bekannte Konzept von std::future gemäß ISO/IEC 14882:2017. Die Klassenvorlage ist als template <typename T, typename E = ErrorCode> class Future final definiert. Die Spezifikation verlangt hierbei explizit, dass eine Parametrisierung mit E != ara::core::ErrorCode zu einem Übersetzungsfehler führt.

Im asynchronen Verarbeitungsmodell steht ara::core::Future in Beziehung zu folgenden Partnern:

  • Asynchroner Erzeuger (Promise): Eine korrespondierende Instanz von ara::core::Promise verwaltet denselben Shared State und befüllt ihn über SetResult oder SetError mit dem Ergebniswert bzw. einem Fehler ([SWS_CORE_00336], [SWS_CORE_00326]).
  • Konsument (Anwendung): Der konsumierende Thread fragt den Verfügbarkeitsstatus ab, blockiert synchron auf das Resultat oder registriert asynchrone Fortsetzungsfunktionen.
  • Ausführungskontext (Executor): Bei der Verkettung über then() kann optional ein Ausführungskontext ExecutorT angegeben werden, in welchem die übergebene Fortsetzung aufgerufen wird ([SWS_CORE_00337]).

Lebenszyklus

Instanzen von ara::core::Future unterliegen einem strikten Move-Besitzmodell. Sowohl der Kopierkonstruktor ([SWS_CORE_00334]) als auch der Kopierzuweisungsoperator ([SWS_CORE_00335]) sind gelöscht (=delete). Ein Transfer des Shared State ist ausschließlich per Move-Konstruktion ([SWS_CORE_00323]) oder Move-Zuweisung ([SWS_CORE_00325]) möglich. Der Standardkonstruktor erzeugt eine leere Instanz analog zu std::future ([SWS_CORE_00322]); Interpretation: Ein solches default-konstruiertes Objekt besitzt zunächst keinen Shared State und dürfte typischerweise erst durch Move-Zuweisung eine aktive Operation abbilden.

Eine Instanz durchläuft folgende Zustandsphasen:

  • Ungültig (valid() == false): Das Objekt besitzt keinen Shared State ([SWS_CORE_00327]). Dies betrifft standard-konstruierte Instanzen, verlassene Instanzen nach einem Move sowie Objekte unmittelbar nach dem Konsumieren via GetResult() ([SWS_CORE_00336]), get() ([SWS_CORE_00326]) oder then() ([SWS_CORE_00331]).
  • Gültig, ausstehend (valid() == true && is_ready() == false): Ein Shared State ist verknüpft, die asynchrone Ausführung ist jedoch noch nicht abgeschlossen ([SWS_CORE_00332]).
  • Gültig, bereit (valid() == true && is_ready() == true): Der Wert oder der Fehler wurde im Shared State abgelegt. In diesem Zustand garantieren GetResult(), get() sowie die Wartefunktionen, nicht mehr zu blockieren ([SWS_CORE_00332]).

Der Destruktor ~Future() gibt den Shared State auf ([SWS_CORE_00333]). Bei registrierten Fortsetzungen via then() blockiert der Destruktor des zurückgegebenen Future-Objekts, bis eine aktuell ausgeführte Continuation vollständig beendet ist ([SWS_CORE_00331], [SWS_CORE_00337]).

Bezüglich der Thread-Sicherheit sind die Methoden valid() ([SWS_CORE_00327]) und is_ready() ([SWS_CORE_00332]) als thread-safe spezifiziert. Alle anderen Aufrufe, insbesondere Wertabfragen und Wartefunktionen, sind nicht thread-safe.

Nutzungspfad

Der typische Ablauf gliedert sich in Synchronisation und Wertextraktion:

  1. Statusprüfung und Synchronisation: Mit is_ready() lässt sich nicht-blockierend prüfen, ob das Resultat bereitsteht ([SWS_CORE_00332]). Für synchrones Warten steht wait() zur Verfügung ([SWS_CORE_00328]). Zeitbeschränktes Warten erfolgt über wait_for() ([SWS_CORE_00329]) mit einer Zeitdauer oder über wait_until() ([SWS_CORE_00330]) mit einem absoluten Zeitpunkt, welche jeweils einen FutureStatus zurückgeben.
  2. Ergebnisabfrage: Die AUTOSAR-spezifische Methode GetResult() ([SWS_CORE_00336]) blockiert bis zur Fertigstellung, wirft keine Ausnahmen und gibt ein ara::core::Result<T, E> zurück. Alternativ liefert die Standardfunktion get() ([SWS_CORE_00326]) direkt den Wert T oder wirft im Fehlerfall eine Ausnahme; sie nimmt bei deaktivierten C++-Exceptions nicht an der Überladungsauflösung teil. Beide Methoden invalidieren das Future-Objekt ([SWS_CORE_00336], [SWS_CORE_00326]).
  3. Reaktive Verkettung: Über then() ([SWS_CORE_00331]) oder then() mit Executor ([SWS_CORE_00337]) kann eine Continuation registriert werden, die ein Result<T, E> als Rvalue übernimmt. Der Rückgabetyp führt bei verschachtelten Rückgaben ein automatisches Future- oder Result-Unwrapping durch. Das ursprüngliche Future-Objekt wird dabei sofort ungültig.

Sequenzdiagramm: Ablauf der asynchronen Bereitstellung, Statusprüfung und Wertabholung. Quellen: [SWS_CORE_00332], [SWS_CORE_00336]

Fehlerszenarien

Die Spezifikation definiert konkrete Fehlerzustände und Laufzeitverletzungen (Violations):

  • Aufruf an ungültigem Future (valid() == false): Wird GetResult() ([SWS_CORE_00336]), is_ready() ([SWS_CORE_00332]), wait() ([SWS_CORE_00328]), wait_for() ([SWS_CORE_00329]), wait_until() ([SWS_CORE_00330]) oder then() ([SWS_CORE_00331], [SWS_CORE_00337]) auf einem ungültigen Future aufgerufen, führt dies zur Laufzeitverletzung FutureInvalidViolation. Bei get() ([SWS_CORE_00326]) wird stattdessen eine FutureException mit dem Fehlercode kNoState geworfen.
  • Verlassener Shared State (Broken Promise): Wird der geteilte Zustand von der zugehörigen Promise zerstört oder verlassen, bevor ein Ergebnis gesetzt wurde, liefert GetResult() ein Resultat mit dem Fehlercode FutureErrc::kBrokenPromise ([SWS_CORE_00336]). Bei get() ([SWS_CORE_00326]) wird die assoziierte Ausnahme ausgelöst.
  • Ausnahme in Continuation: Wirft eine in then() registrierte Fortsetzung eine Exception, die keine Violation implementiert, wird die Verletzung FutureContinuationHasThrownViolation ausgelöst ([SWS_CORE_00331], [SWS_CORE_00337]). Benutzer müssen Ausnahmeinformationen abfangen und als Fehler über ein Result oder Future zurückmelden.

                                  template <typename F> auto then (F &&func) noexcept -> Future< <see below> >;
                                  

                                  Create a new Future with the content returned by func when passed the Result of this Future. The callable func may be called in the context of this call or in the context of • Promise::set_result(const T&) • Promise::set_result(T&&) • Promise::SetError(E&&) • Promise::SetError(const E&) or somewhere else.
                                  valid() ==FALSE on the original Future object immediately after it returns.
                                  The Callable input argument func takes a Result<T,E> object as parameter. This will be the Result obtained via GetResult() from the Future instance itself, on which then(...) is being called. The Result is passed to func as an rvalue expression.
                                  The return type of then(...) depends on the return type of func (aka continuation).
                                  Let U be the return type of the continuation (i.e. a type equivalent to std::invoke_result_ t<std::decay_t<F>,Result<T,E>>). Return type deduction: • If U is Future<T2,E2> for some types T2, E2, then the return type of then(...) is Future<T2,E2>. This is known as implicit Future unwrapping. • If U is Result<T2,E2> for some types T2, E2, then the return type of then(...) is Future<T2,E2>. This is known as implicit Result unwrapping. • Otherwise it is Future<U,E> Continuations that are registered with then(...) are registered in the Future F that then (...) returns. No such continuation shall be executed after the destructor of the Future F returns. A continuation that is already being executed shall run to completion.
                                  Note: that means that the destructor of Future might block until the currently running continuation has been completed.
                                  The continuation shall not throw, except for the purpose of implementing a Violation.
