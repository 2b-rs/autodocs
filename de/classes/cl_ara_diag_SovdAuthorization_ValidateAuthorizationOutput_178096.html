Kontext

Die Struktur ara::diag::SovdAuthorization::ValidateAuthorizationOutput ist der standardisierte Rückgabetyp für die Methode ValidateAuthorization() im Kontext der SOVD-Autorisierung (Service-Oriented Vehicle Diagnostics) der AUTOSAR Adaptive Platform [SWS_DM_01927]. Sie ist in der Header-Datei ara/diag/sovd_authorization.h definiert und fasst das Ergebnis einer Autorisierungsprüfung für eingehende Diagnoseanfragen zusammen AUTOSAR_AP_SWS_Diagnostics §8.52.2 „Struct: ValidateAuthorizationOutput“.

An der Verarbeitung sind typischerweise drei Kernkomponenten beteiligt:

  • SOVD-Client: Sendet diagnostische Befehle zusammen mit einem Autorisierungs-Token an das Fahrzeug.
  • Diagnostic Management (DM): Verarbeitet die SOVD-Anfragen, verwaltet temporäre Ressourcen wie laufende Routinen oder Zugriffssperren und prüft gecachte Autorisierungszustände.
  • Autorisierungsinstanz (SovdAuthorization): Anwendungsseitige Implementierung, die das übergebene Token validiert und die Autorisierungsmetadaten in Form von ValidateAuthorizationOutput bereitstellt.

Lebenszyklus

Als Datenstruktur (C++-struct) unterliegt ValidateAuthorizationOutput einer einfachen Wertsemantik:

  • Erzeugung und Besitz: Eine Instanz wird bei der Abarbeitung von ValidateAuthorization() durch die anwendungsseitige Sicherheitslogik instanziiert, mit den Validierungsergebnissen befüllt und per Wert oder Move-Operation an das aufrufende Diagnostic Management übergeben.
  • Zustände: Die Struktur selbst besitzt keine internen Zustandsmaschinen oder dynamischen Lebensphasen. Sie kapselt zwei öffentliche Mitgliedsvariablen:
    • identity ([SWS_DM_01819]): Ein optionaler Identifikator vom Typ ara::core::Optional<ara::core::String>, der den Client über Token-Grenzen hinweg eindeutig kennzeichnet.
    • validUntil ([SWS_DM_01820]): Ein Zeitstempel vom Typ std::chrono::system_clock::time_point, welcher den Cache-Horizont der Validierung angibt.
  • Zerstörung und Nebenläufigkeit: Nach der Auswertung und Übernahme der Werte in die Caching- und Sitzungsverwaltung des Diagnostic Managements endet die Lebensdauer der Struktur auf dem lokalen Aufrufstack. Interpretation: Da es sich um eine passive Datenstruktur ohne geteilten Zustand handelt, ist der nebenläufige Zugriff unkritisch, solange Aufrufer und Erzeuger auf getrennten Instanzen arbeiten.

Nutzungspfad

Der reguläre Ablauf zur Nutzung von ValidateAuthorizationOutput erfolgt ereignisgesteuert anhand eingehender Diagnose-Requests:

  1. Anfrageprüfung: Das Diagnostic Management empfängt eine SOVD-Anfrage mit einem Zugriffs-Token. Ist das Token nicht bekannt oder dessen Gültigkeitsgrenze abgelaufen, initiiert das System die Validierung über ValidateAuthorization().
  2. Ergebniserstellung: Die Autorisierungslogik überprüft das Token gegen das hinterlegte Sicherheitskonzept (z. B. Auswertung von client_id, sub oder Token-Signaturen). Sie instanziiert ValidateAuthorizationOutput und setzt validUntil auf den maximalen Zeitpunkt, bis zu dem diese Autorisierung wiederverwendet werden darf [SWS_DM_01820].
  3. Client-Identifikation: Ist ein Re-Identifikationsmechanismus gefordert, wird identity gesetzt [SWS_DM_01819].
  4. Übernahme und Caching: Das Diagnostic Management liest die Werte aus. Der Authentifizierungsstatus wird bis zum Erreichen von validUntil gecacht. Entspricht der identity-String einem bereits früher registrierten Client, ordnet das System dem Client bestehende temporäre Ressourcen (wie aktive Routinen oder Locks) erneut zu [SWS_DM_01819].

Fehlerszenarien

Bei der Verwendung und Interpretation der Ausgabestruktur sind folgende Randbedingungen und Fehlerkonstellationen relevant:

  • Fehlende Client-Identität: Wird identity nicht bereitgestellt (also als ara::core::nullopt belassen), bleibt der Zugriff auf temporäre Ressourcen strikt an das konkrete Zugriffs-Token gebunden [SWS_DM_01819]. Erneuert der Client sein Token nach Ablauf, kann das Diagnostic Management die Verbindung zu laufenden Routinen oder Sperren nicht aufrechterhalten; diese Ressourcen gehen für den Client verloren.
  • Abweichende Identitätsangaben: Ändert sich der übergebene identity-String für einen Client bei der Erneuerung des Tokens, wird dieser als neuer, nicht identischer Client eingestuft [SWS_DM_01819]. Dies verhindert die Reaktivierung zuvor reservierter Ressourcen.
  • Ablauf des Cache-Zeitpunkts: Sobald der in validUntil hinterlegte Zeitpunkt erreicht oder überschritten ist, darf die Validierung nicht mehr wiederverwendet werden [SWS_DM_01820]. Das Diagnostic Management muss nachfolgende Anfragen mit demselben Token verwerfen oder eine erneute Validierung anstoßen.

Konstanten

identity variable

Identity of the client. This identity string if present will be used to re-identify a client even if it uses a new token (e.g. because the old one expired) so that it has access to the temporary resources (e.g. running routines, locks, etc.). If the identity string is the same as one returned earlier, the client will be considered identical. Depending on the security concept it could be for example the ’client_id’, the ’sub’, or a combination of both. If the identity string is not provided, the client will only have access to the temporary resources as long as it provides the same access token and validUntil is not yet expired.

ara::core::Optional<ara::core::String> identity;
validUntil variable

Time until this validation may be reused. The point in time until which the authentication state may be reused if the same token is provided by the client (caching).

std::chrono::system_clock::time_point validUntil;
