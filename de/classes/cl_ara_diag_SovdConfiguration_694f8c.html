Dient zur anwendungsseitigen Bereitstellung und Bearbeitung explizit modellierter SOVD-Konfigurationsressourcen.

Die Schnittstelle ara::diag::SovdConfiguration dient als generischer Handler für explizit modellierte SOVD-Konfigurationen, an den der Diagnostic Server eingehende Lese- und Schreibzugriffe weiterleitet [SWS_DM_01860], [SWS_DM_01787]. Nach der portbasierten Instanziierung aktiviert die Anwendung den Nachrichtenempfang über Offer und beendet ihn bei Bedarf mit StopOffer [SWS_DM_01872], [SWS_DM_01930]. Die Datenbereitstellung erfolgt asynchron über Lese- bzw. Schreibsitzungen, wobei fachliche Fehler nach ISO 17978-3 bzw. ASAM SOVD 1.1 signalisiert werden [SWS_DM_01870].

Kontext

Die Schnittstelle ara::diag::SovdConfiguration definiert das generische Interface für explizit modellierte SOVD-Konfigurations-Handler innerhalb der Adaptive AUTOSAR-Diagnosearchitektur [SWS_DM_01860]. Sofern mindestens eine SOVD-Konfiguration im System projektiert ist, stellt die Diagnostic-Server-Instanz des Diagnostic Management (DM) nach außen die standardisierte SOVD-Methode Retrieve List of All Configurations Provided by the Entity gemäß ASAM SOVD bereit [SWS_DM_01429]. Eingehende Lese- und Schreibzugriffe auf eine solche explizite Konfiguration leitet der Diagnostic Server an die konkrete Implementierung von ara::diag::SovdConfiguration weiter: Beim Aufruf der SOVD-Methode Read Configuration ruft der Diagnostic Server die Methode RequestGetConfiguration auf [SWS_DM_01787], während beim Aufruf von Write Configuration die Methode RequestPutConfiguration ausgeführt wird [SWS_DM_01788].

Kontextdiagramm: Einbettung von ara::diag::SovdConfiguration zwischen externem SOVD-Client, Diagnostic Server (DM) und anwendungsspezifischem Handler. Quellen: [SWS_DM_01429], [SWS_DM_01787], [SWS_DM_01788], [SWS_DM_01860].

Lebenszyklus

Die Instanziierung von ara::diag::SovdConfiguration erfolgt anwendungsseitig durch Übergabe eines ara::core::InstanceSpecifier sowie der Angabe eines ConcurrencyType (kConcurrent oder kNotConcurrent) [SWS_DM_01864]. Der InstanceSpecifier referenziert einen Port-Prototyp eines DiagnosticSovdConfigurationInterface im Prozesskontext [SWS_DM_01864]. Die Klasse darf nicht kopiert werden (Kopierkonstruktor und Kopierzuweisungsoperator sind als delete deklariert) [SWS_DM_01866], [SWS_DM_01868], unterstützt jedoch geschützte Move-Operationen [SWS_DM_01867], [SWS_DM_01869]. Um Anfragen vom Diagnostic Server entgegenzunehmen, muss die Anwendung explizit Offer aufrufen [SWS_DM_01872]. Mit dem Aufruf von StopOffer wird die Weiterleitung von Anfragen wieder deaktiviert [SWS_DM_01930]. Bei Zerstörung der Instanz über den virtuellen Destruktor [SWS_DM_01865] wird das Objekt freigegeben; die Freigabe setzt voraus, dass der Handler zuvor ordnungsgemäß deregistriert wurde.

Zustandsdiagramm: Lebenszyklusphasen einer SovdConfiguration-Instanz von Initialisierung über Offer-Zustand bis zum StopOffer. Quellen: [SWS_DM_01864], [SWS_DM_01872], [SWS_DM_01930], [SWS_DM_01865].

Nutzungspfad

Ein typischer Nutzungspfad beginnt nach der Konstruktion der abgeleiteten Handler-Klasse mit dem Registrieren beim Diagnostic Management mittels Offer() [SWS_DM_01872]. Sobald ein externer Client eine SOVD-Konfigurationsanfrage an die Entität richtet, leitet der Diagnostic Server diese weiter: Bei einer Leseanforderung wird RequestGetConfiguration aufgerufen, wobei die configurationId, die metaInfo und ein CancellationHandler übergeben werden [SWS_DM_01870]. Die Methode liefert ein ara::core::Future zurück, das asynchron ein Tupel aus einer DataTransferReadSession und SovdConfigurationMetaInfo bereitstellt [SWS_DM_01870]. Analog leitet der Server Schreibanfragen über RequestPutConfiguration weiter, welches ein Future mit einer DataTransferWriteSession und SovdConfigurationMetaInfo liefert [SWS_DM_01871]. Vor dem Herunterfahren des Handlers ruft die Anwendung StopOffer() auf, um keine weiteren Anforderungen mehr anzunehmen [SWS_DM_01930].

Sequenzdiagramm: Typische Interaktionsabfolge bei Initialisierung, Abfertigung eines Read-Configuration-Requests und anschließender Deregistrierung. Quellen: [SWS_DM_01872], [SWS_DM_01787], [SWS_DM_01870], [SWS_DM_01930].

Fehlerszenarien

Bereits bei der Instanziierung im Konstruktor können Modell- und Mapping-Verletzungen auftreten, falls der InstanceSpecifier im Modell nicht aufgelöst werden kann (InstanceSpecifierMappingIntegrityViolation), der referenzierte Port-Prototyp nicht durch ein DiagnosticSovdConfigurationInterface typisiert ist (PortInterfaceMappingViolation), kein passender Prozess existiert (ProcessMappingViolation) oder der Bezeichner im aktuellen Prozess bereits belegt ist (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01864]. Beim Aufruf von Offer() gibt die Methode ein ara::core::Result<void> zurück, welches im Fehlerfall DiagOfferErrc::kConfigurationMismatch meldet, wenn die Konfiguration nicht zum DEXT-Modell passt, oder DiagOfferErrc::kAlreadyOffered, falls der Service bereits angeboten wird [SWS_DM_01872]. In den asynchronen Handler-Methoden RequestGetConfiguration und RequestPutConfiguration meldet die Anwendung Fehlerzustände über das ara::core::Future unter Verwendung standardisierter SOVD-Fehlercodes gemäß ISO 17978-3 bzw. ASAM SOVD 1.1 [SWS_DM_01870], [SWS_DM_01871]. Zudem signalisiert der CancellationHandler, ob eine laufende Kommunikation abgebrochen wurde [SWS_DM_01870], [SWS_DM_01871].

Verwendung

Die Methode Offer der Klasse ara::diag::SovdConfiguration dient dazu, die Weiterleitung von Diagnoseanfragen durch den Diagnostic Management (DM) an den konfigurierten Handler zu aktivieren [SWS_DM_01872]. Der Aufruf erfolgt synchron, nimmt keine Parameter entgegen und meldet das Ergebnis über ara::core::Result<void> zurück [SWS_DM_01872]. Solange ein Handler nicht über Offer bereitgestellt wurde, leitet der DM keine eingehenden Anfragen weiter, was dem grundlegenden Bereitstellungsmuster diagnostischer Schnittstellen entspricht (vgl. [SWS_DM_01525], [SWS_DM_00809]).

Fehlerbehandlung

Im Fehlerfall wird ein ara::core::Result mit einem Fehlercode der Enumeration DiagOfferErrc zurückgegeben, wobei eine Rollback-Semantik gilt [SWS_DM_01872]:

  • DiagOfferErrc::kAlreadyOffered: Wird gemeldet, wenn der Dienst bereits zuvor angeboten wurde [SWS_DM_01872].
  • DiagOfferErrc::kConfigurationMismatch: Tritt auf, wenn die Konfiguration nicht mit den DEXT-Beschreibungsdaten übereinstimmt [SWS_DM_01872].

Nebenläufigkeit und Einschränkungen

Die Operation ist als noexcept deklariert sowie ausnahmesicher (exception safe), ist jedoch als nicht threadsicher (not thread-safe) spezifiziert [SWS_DM_01872]. Gleichzeitige Aufrufe derselben Instanz aus mehreren Threads müssen durch die aufrufende Anwendung verhindert werden. Ein erneuter Aufruf nach bereits erfolgtem Angebot dürfte vermutlich ohne Zustandsänderung mit einem Fehler quittiert werden.

  Herkunft
  

      

      

      Verwendung
      

      Die pure virtuelle Methode RequestGetConfiguration der Klasse ara::diag::SovdConfiguration wird von der Diagnostic Server Instance aufgerufen, wenn die SOVD-Methode „Read Configuration“ für eine explizit modellierte SOVD-Konfiguration ausgeführt wird ([SWS_DM_01787], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 „Configuration – Explicit Configurations“). Als Parameter werden die Konfigurations-ID der zu lesenden Instanz (configurationId), die Metainformationen der Anfrage (metaInfo) sowie ein cancellationHandler übergeben, der über einen eventuellen Abbruch der laufenden Konversation informiert ([SWS_DM_01870]).
      

      Die Funktion arbeitet asynchron und liefert ein ara::core::Future zurück, das ein Tupel aus einer Dateilesesitzung (DataTransferReadSession) und zugehörigen Konfigurations-Metainformationen (SovdConfigurationMetaInfo) bereitstellt ([SWS_DM_01870]). Die Schnittstelle ist als noexcept deklariert und als ausnahmesicher spezifiziert ([SWS_DM_01870]).
      

      Fehlerbehandlung und Nebenläufigkeit
      

      Tritt bei der Verarbeitung ein Fehler auf, wird kein C++-Fehler geworfen, sondern über das Future ein zutreffender SOVD-Fehlercode gemäß ISO 17978-3 bzw. ASAM SOVD 1.1 zurückgegeben ([SWS_DM_01870]).
      

      Hinsichtlich der Thread-Sicherheit gilt die Vorgabe „conditional“: Ob die konkrete Implementierung der Funktion threadsicher oder nicht-threadsicher ausgelegt sein muss, entscheidet der dem Konstruktor übergebene ConcurrencyType ([SWS_DM_01870]).

          Die API-Methode ara::diag::SovdConfiguration::RequestPutConfiguration wird vom Diagnostic Server aufgerufen, wenn über die SOVD-Schnittstelle die Methode „Write Configuration“ für eine explizit modellierte Konfiguration ausgeführt werden soll [SWS_DM_01788], [SWS_DM_01871].
          

          Aufruf und Parameter
          

          Die Deklaration befindet sich im Header ara/diag/sovd_configuration.h. Der Aufruf übergibt die folgenden Eingabeparameter [SWS_DM_01871]:
          

            

          • configurationId: ID der zu schreibenden Konfigurationsinstanz als ara::core::String.
            • 

          • metaInfo: Metainformationen zur eingehenden Anfrage (MetaInfo const &).
            • 

          • cancellationHandler: Überwacht den aktuellen Vorgang und signalisiert, falls die Kommunikation abgebrochen wurde.
            • 

          

          Die Methode besitzt eine asynchrone Semantik und gibt ein ara::core::Future zurück, das im Erfolgsfall ein Tupel aus einer Schreibsitzung (DataTransferWriteSession) sowie zugehörigen Metadaten (SovdConfigurationMetaInfo) zur Verfügung stellt [SWS_DM_01871].
          

          Fehlerbehandlung und Nebenläufigkeit
          

          Im Fehlerfall wird das Future mit einem passenden SOVD-Fehlercode nach ISO 17978-3 bzw. ASAM SOVD 1.1 aufgelöst [SWS_DM_01871]. Die Funktion ist als noexcept deklariert und ausnahmesicher (exception safe). Die Thread-Sicherheit ist konditional (conditional): Ob die konkrete Implementierung threadsicher ausgelegt sein muss, bestimmt der im Konstruktor spezifizierte ConcurrencyType [SWS_DM_01871].
          

          Zusammenspiel
          

          Die Funktion bildet das schreibende Gegenstück zu RequestGetConfiguration, welche für die SOVD-Methode „Read Configuration“ verwendet wird [SWS_DM_01787] (AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 „Configuration – Explicit Configurations“).
