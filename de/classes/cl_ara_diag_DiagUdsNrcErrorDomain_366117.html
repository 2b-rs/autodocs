Kontext

Die Klasse [SWS_DM_00529] ara::diag::DiagUdsNrcErrorDomain repräsentiert die standardisierte Fehlerdomäne für Diagnosefehler, die aus unterschiedlichen Diagnoseklassen und Schnittstellen der AUTOSAR Adaptive Platform stammen. Sie leitet sich gemäß [SWS_DM_00529] von der Basisklasse ara::core::ErrorDomain ab und fungiert als primäres Bindeglied zwischen anwendungsseitigen Diagnoseroutinen und dem Diagnose-Management (Diagnostic Management, DM).

Im Gesamtsystem agiert die Fehlerdomäne an den Schnittstellen dreier zentraler Komponenten:

  • Diagnostic Server (DM): Instanz, die Diagnoseanforderungen des Fahrzeugdiagnosetesters verarbeitet, Umgebungsbedingungen prüft und normgerechte UDS-Antworten generiert.
  • Externe Diagnose-Anwendung: Anwendungslogik beziehungsweise externer Diagnoseprozessor, der fahrzeugspezifische Diagnose-Dienste implementiert und über ara::diag-Schnittstellen Ergebnisse oder Fehler zurückmeldet.
  • Diagnose-Client (Tester): Externes Prüfgerät, das Diagnosebefehle an das Steuergerät sendet und bei aufgetretenen Fehlern standardisierte negative Antworten (Negative Response Codes, NRC) erwartet.

Gibt eine Diagnose-Anwendung über eine ara::diag-Schnittstelle ein Ergebnis mit einem Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain zurück, verarbeitet der Diagnostic Server diesen Fehler zielgerichtet: Er leitet aus dem gemeldeten Fehlercode den UDS Negative Response Code ab [SWS_DM_02059] und übermittelt eine negative Antwort mit diesem Code an den Diagnose-Client [SWS_DM_02060]. Zudem interagiert die Domäne mit der Prüfung konfigurierbarer Umgebungsbedingungen: Schlägt der Abruf eines Datenelements durch einen Fehler dieser Domäne fehl, stuft der Server die Bedingung als nicht erfüllt ein und setzt eine Log- und Trace-Meldung ab [SWS_DM_00970].

Kontextdiagramm: Einbettung der Fehlerdomäne in die Interaktion zwischen Tester, Diagnostic Server und Anwendung. Quellen: [SWS_DM_02059], [SWS_DM_02060], AUTOSAR_AP_SWS_Diagnostics S. 144

Lebenszyklus

Der Lebenszyklus von ara::diag::DiagUdsNrcErrorDomain folgt den Vorgaben für zustandslose Fehlerdomänen der Plattform:

  • Erzeugung und Initialisierung: Die Klasse stellt einen parameterlosen Standardkonstruktor bereit, der als constexpr und noexcept definiert ist [SWS_DM_00532]. Interpretation: Instanzen von DiagUdsNrcErrorDomain werden als langlebige Konstanten oder Singleton-Objekte zur Compile- bzw. Ladezeit angelegt, um über die gesamte Prozesslaufzeit zur Verfügung zu stehen.
  • Besitzverhältnisse: Anwendungen erzeugen in der Regel keine dynamischen Instanzen auf dem Heap, sondern referenzieren die Domäne über konstante Referenzen bei der Typisierung von ara::core::ErrorCode-Werten.
  • Zustände und Übergänge: Die Domäne besitzt keine variablen internen Zustände und erfordert keine Zustandsübergänge. Beobachtende Abfragen wie Name() [SWS_DM_00533] oder Message() [SWS_DM_00534] verhalten sich zustandslos und deterministisch.
  • Nebenläufigkeit: Sämtliche Elementfunktionen – der Konstruktor [SWS_DM_00532], Name() [SWS_DM_00533], Message() [SWS_DM_00534] sowie ThrowAsException() [SWS_DM_00535] – sind explizit als threadsicher spezifiziert. Sie können parallel aus verschiedenen Ausführungskontexten ohne zusätzliche Sperren aufgerufen werden.

Nutzungspfad

Der reguläre Ablauf bei der Signalisierung von Diagnosefehlern gliedert sich in folgende Schritte:

  1. Dienstanforderung: Der Diagnose-Client sendet eine UDS-Serviceanforderung an den Diagnostic Server.
  2. Aufruf der Diagnose-Anwendung: Der Diagnostic Server delegiert die Verarbeitung über eine typisierte ara::diag-Schnittstelle an den zuständigen externen Diagnoseprozessor.
  3. Fehlerrückgabe: Stellt die Diagnose-Anwendung eine ungültige Bedingung fest, erzeugt sie einen Fehlercode des Typs ara::diag::DiagUdsNrcErrorDomain::Errc [SWS_DM_00530] und gibt diesen innerhalb eines ara::core::Result zurück.
  4. NRC-Ableitung: Erkennt der Diagnostic Server einen Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain, leitet er aus dem DiagUdsNrcErrc-Wert den UDS Negative Response Code ab [SWS_DM_02059]. Dies geschieht typischerweise über eine Typkonvertierung (static_cast) in einen 1-Byte-Wert im zulässigen Bereich 0x01 bis 0xFE [SWS_DM_02059].
  5. Protokollantwort: Der Diagnostic Server erzeugt eine negative UDS-Antwort mit dem ermittelten Fehlercode und sendet diese an den Client [SWS_DM_02060].
  6. Fehlertextauflösung: Für Diagnoseprotokolle oder Systemmeldungen kann die Fehlerbeschreibung über Message() abgefragt werden, welche stets einen gültigen Textzeiger liefert [SWS_DM_00534].

Sequenzdiagramm: Fehlerfortpflanzung und UDS-NRC-Ableitung bei einer fehlgeschlagenen Diagnoseoperation. Quellen: [SWS_DM_02059], [SWS_DM_02060]

Fehlerszenarien

Für die kontrollierte Behandlung von Fehlerzuständen stellt die Klasse spezialisierte Typen und Konvertierungsmechanismen bereit:

  • Fehlercode-Enumeration: Der Typ-Alias Errc verweist auf das Enum DiagUdsNrcErrc [SWS_DM_00530]. Interpretation: Die Enumerationswerte spiegeln die normierten UDS Negative Response Codes wider. Gültige Werte für die Ableitung liegen im Bereich von 0x01 bis 0xFE [SWS_DM_02059].
  • Ausnahmeabbildung: Der Alias Exception verweist auf DiagUdsNrcException [SWS_DM_00531]. Mittels ThrowAsException() [SWS_DM_00535] kann ein Fehlercode in die entsprechende Ausnahme gewandelt und geworfen werden. Sind C++-Ausnahmen in der Toolchain deaktiviert, nimmt diese Funktion nicht an der Überladungsauflösung teil [SWS_DM_00535].
  • Fehler beim Datenelement-Abruf: Führt der Abruf eines Datenelements durch einen externen Prozessor zu einem Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain, behandelt das Diagnose-Management den betreffenden Formelteil der Umweltbedingung als nicht erfüllt und stößt eine Log- und Trace-Meldung an [SWS_DM_00970].
  • Verhalten bei Multi-DID-Anfragen: Das Vorhandensein von ara::diag::DiagUdsNrcErrorDomain im Ergebnis signalisiert ein negatives Teilergebnis des externen Prozessors. Bei Anfragen über mehrere DIDs führt ein Einzelfehler jedoch nicht zwangsläufig zu einer globalen negativen Antwort, sofern mindestens ein DID in der aktiven Sitzung unterstützt wird (AUTOSAR_AP_SWS_Diagnostics §7.3.x S. 160).
