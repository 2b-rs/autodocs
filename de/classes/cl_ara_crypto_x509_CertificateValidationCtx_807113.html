Kontext

Die Klasse ara::crypto::x509::CertificateValidationCtx stellt den Validierungskontext für X.509-Zertifikate und Zertifikatspfade gemäß RFC 5280 bereit ([SWS_CRYPT_50122], [SWS_CRYPT_50123]). Innerhalb des Moduls crypto der Adaptive Platform bündelt sie die Konfiguration, vertrauenswürdige Wurzelzertifikate, Zwischenzertifikate sowie Prüfregeln und führt die kryptografische Pfadvalidierung durch.

An den Validierungsabläufen sind im Wesentlichen folgende Komponenten und Datentypen beteiligt:

  • Anwendung: Konfiguriert den Kontext über Validierungsoptionen ([SWS_CRYPT_50120]), setzt bei Bedarf die Referenzzeit ([SWS_CRYPT_50121]), registriert Vertrauensanker und stößt die Prüfung an.
  • Zertifikate (Certificate): Bilden die Vertrauensbasis und die Prüfobjekte. Unterschieden wird zwischen vertrauenswürdigen Zertifikaten ([SWS_CRYPT_50117]), unvertrauenswürdigen Zwischenzertifikaten zur Pfadkonstruktion ([SWS_CRYPT_50118]) sowie Zielzertifikaten ([SWS_CRYPT_50122]) oder Zertifikatsketten ([SWS_CRYPT_50123]).
  • OCSP-Antworten (OcspResponse): Dienen dem Nachweis des Sperrstatus von Zertifikaten und werden dem Validierungskontext zur Berücksichtigung übergeben ([SWS_CRYPT_50124]).
  • Validierungsergebnis (CertificateValidationResult): Kapselt nach erfolgter Prüfung das detaillierte Ergebnis des RFC 5280 Pfadvalidierungsvorgangs ([SWS_CRYPT_50122], [SWS_CRYPT_50123]).

Kontextdiagramm: Interaktionspartner des CertificateValidationCtx bei der Zertifikats- und Pfadprüfung. Quellen: [SWS_CRYPT_50117], [SWS_CRYPT_50118], [SWS_CRYPT_50122], [SWS_CRYPT_50123], [SWS_CRYPT_50124]

Lebenszyklus

Für den Besitz und die Weitergabe von Kontextinstanzen stellt die Schnittstelle den Typalias Sptr als std::shared_ptr<CertificateValidationCtx> bereit ([SWS_CRYPT_50116]). Da die Klasse rein virtuelle Methoden definiert, dürfte die Instanziierung der konkreten Implementierung über eine übergeordnete Factory- oder Provider-Klasse des Krypto-Stacks erfolgen.

Nach der Erzeugung befindet sich der Kontext in einem konfigurierbaren Zustand. Die Anwendung registriert schrittweise Optionen ([SWS_CRYPT_50120]), Zertifikate ([SWS_CRYPT_50117], [SWS_CRYPT_50118]), OCSP-Antworten ([SWS_CRYPT_50124]) oder OIDs zu ignorierender kritischer Erweiterungen ([SWS_CRYPT_50119]). Ein Zurücksetzen einzelner Registrierungen ist nicht vorgesehen; für unterschiedliche Validierungsdomänen werden getrennte Kontexte instanziiert.

Bezüglich der Nebenläufigkeit und Fehlertoleranz sind sämtliche virtuellen Elementfunktionen der Schnittstelle explizit als threadsicher (thread-safe) und ausnahmesicher (exception safe) spezifiziert ([SWS_CRYPT_50117] bis [SWS_CRYPT_50124]). Instanzen können somit nebenläufig von mehreren Threads genutzt werden.

Nutzungspfad

Die typische Verwendung von CertificateValidationCtx folgt einer festen Abfolge von Konfiguration, Bestückung und Ausführung:

  1. Konfiguration festlegen: Mittels SetValidationOptions wird eine Bitmaske übergeben, die die auszuführenden Prüfungen definiert ([SWS_CRYPT_50120]). Optional kann über SetCurrentTime ein expliziter Referenzzeitpunkt für die Gültigkeitsprüfung gewählt werden ([SWS_CRYPT_50121]); wird diese Funktion nicht aufgerufen, zieht der Kontext die Systemzeit heran. Falls anwendungsspezifisch validierte kritische Erweiterungen toleriert werden sollen, werden deren OIDs über IgnoreCriticalExtension hinterlegt ([SWS_CRYPT_50119]).
  2. Zertifikate und Statusdaten registrieren: Über AddTrustedCertificate werden die maßgeblichen Vertrauensanker (Root-CAs) hinzugefügt ([SWS_CRYPT_50117]). Zur Erleichterung der Pfadfindung können über AddUntrustedCertificate Zwischenzertifikate eingesteuert werden ([SWS_CRYPT_50118]). Sollen Sperrinformationen einfließen, werden OCSP-Antworten über AddOcspResponse hinzugefügt ([SWS_CRYPT_50124]).
  3. Validierung ausführen: Die Prüfung erfolgt über eine von zwei Methoden:
    • ValidateCertificate prüft ein einzelnes End-Entity-Zertifikat und baut den Pfad unter Zuhilfenahme der im Kontext hinterlegten vertrauenswürdigen und unvertrauenswürdigen Zertifikate auf ([SWS_CRYPT_50122]).
    • ValidateCertificateChain validiert eine vorliegende Kette als ara::core::Span ([SWS_CRYPT_50123]). Element 0 stellt dabei das Blattzertifikat dar und jedes Folgeelement den jeweiligen Aussteller. In diesem Modus werden zuvor per AddUntrustedCertificate hinterlegte Zertifikate ignoriert; die Validierung prüft die übergebene Kette ausschließlich gegen die per AddTrustedCertificate gesetzten Vertrauensanker.
  4. Ergebnis auswerten: Beide Validierungsfunktionen geben bei Erfolg ein CertificateValidationResult::Sptrc zur Auswertung der Detailergebnisse zurück ([SWS_CRYPT_50122], [SWS_CRYPT_50123]).

Sequenzdiagramm: Typische Aufrufabfolge zur Konfiguration, Registrierung von Zertifikaten und Ausführung der Validierung. Quellen: [SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50121], [SWS_CRYPT_50122], [SWS_CRYPT_50123], [SWS_CRYPT_50124]

Fehlerszenarien

Alle Operationen geben Fehler über ara::core::Result zurück. Standardisierte Fehlercodes und spezifische Vorbedingungen umfassen:

  • Inkompatible Argumente (ara::crypto::CryptoErrc::kIncompatibleArguments): Tritt bei ValidateCertificate ([SWS_CRYPT_50122]) und ValidateCertificateChain ([SWS_CRYPT_50123]) auf, wenn zwar über AddOcspResponse ([SWS_CRYPT_50124]) eine OCSP-Antwort hinterlegt wurde, die über SetValidationOptions ([SWS_CRYPT_50120]) gesetzten Optionen jedoch kein entsprechendes OCSP-Verhalten definieren. Beide Funktionen besitzen Rollback-Semantik.
  • Ungültige Konfigurationsoptionen (ara::crypto::CryptoErrc::kInvalidArgument): Wird SetValidationOptions ([SWS_CRYPT_50120]) mit einer unzulässigen Bitmaske aufgerufen, schlägt der Aufruf unter Rollback-Semantik fehl.
  • Validierungsfehler bei OCSP-Antworten: Für AddOcspResponse ([SWS_CRYPT_50124]) muss der Aussteller der OCSP-Antwort entweder vorab im Kontext als vertrauenswürdig oder unvertrauenswürdig hinterlegt worden sein, von einem Zertifikat mit der Extended-Key-Usage id-kp-OCSPSigning derselben CA signiert worden sein oder über das optionale Argument trustedOcspIssuerCertificate mitgegeben werden. Das zurückgegebene Result<CertificateValidationStatus> signalisiert kValid bei erfolgreicher Übernahme oder liefert den konkreten Validierungsstatus der OCSP-Antwort.
  • Implementierungsspezifische Fehler: Sämtliche Methoden können bei internen Fehlern oder Systemgrenzen implementierungsspezifische Fehlercodes im Result zurückgeben ([SWS_CRYPT_50117] bis [SWS_CRYPT_50124]).

Dieser Leitfaden basiert auf der Spezifikation AUTOSAR Adaptive R25-11 für das Modul crypto.

Methoden

AddOcspResponse function

Validate and add an OCSP response to be used during certificate validation to the set of previously added OCSP responses. Multiple OCSP responses may be added to one context. In order to validate the OCSP response, the issuer of the OCSP response must have been a) set as a trusted or untrusted certificate in this context previously, or b) the CRL must have been signed by another certificate that has the id-kp-OCSPSigning extended key usage set issued by the same CA, or c) the CRL must be signed by a trusted CA passed to this function using the optional trustedOcspIssuerCertificate parameter.

virtual ara::core::Result< CertificateValidationStatus > AddOcsp Response (OcspResponse::Sptrc ocspResponse, ara::core::Optional< Certificate::Sptrc > trustedOcspIssuerCertificate) noexcept=0;

Add a trusted certificates to be used during certificate path validation to the set of previously added trusted certificates.

virtual ara::core::Result< void > AddTrustedCertificate ( Certificate::Sptrc trustedCertificate) noexcept=0;

Add an untrusted certificate to be used during certificate path validation to the set of previously added untrusted certificates.

virtual ara::core::Result< void > AddUntrustedCertificate ( Certificate::Sptrc untrustedCertificate) noexcept=0;
IgnoreCriticalExtension function

Configure the context to ignore an extension during validation of certificates and OCSP responses, even if the extension is marked as critical and the validation context does not support the extension. It is the responsibility of the application to validate such extensions. Multiple invocations of this function lead to ignoring all passed extensions. This function has no effect if the kIgnoreUnknownCriticalExtensions validation option is set.

virtual ara::core::Result< void > IgnoreCriticalExtension (ara::core::StringView ignoredExtensionOid) noexcept=0;
SetCurrentTime function

Set the reference time point to be used as the current time during certificate validation. If this function is not called, the system time will be used during certificate validation.

virtual ara::core::Result< void > SetCurrentTime (Timestamp current Time) noexcept=0;
SetValidationOptions function

Set validation options to be used during certificate validation.

virtual ara::core::Result< void > SetValidationOptions (Certificate ValidationOptions CertificateValidationOptions) noexcept=0;
ValidateCertificate function

Performs certificate path validation according to RFC 5280 and according to the previous configuration of the context.

virtual ara::core::Result< CertificateValidationResult::Sptrc > ValidateCertificate (Certificate::Sptrc certificate) noexcept=0;
ValidateCertificateChain function

Performs certificate path validation according to RFC 5280 and according to the previous configuration of the context. The function ignores any certificates added to the context via Add UntrustedCertificate. Instead, the function validates the provided chain against any trusted certificate that has been set using the function AddTrustedCertificate.

virtual ara::core::Result< CertificateValidationResult::Sptrc > ValidateCertificateChain (const ara::core::Span< Certificate::Sptrc > certificateChain) noexcept=0;
