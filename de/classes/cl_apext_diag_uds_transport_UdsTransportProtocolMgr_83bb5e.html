class apext::diag::uds_transport::UdsTransportProtocolMgr

[SWS_DM_00306] Upstream: RS_Diag_04147, RS_Diag_04168

class UdsTransportProtocolMgr {...};

The UdsTransportProtocolMgr class manages the interaction between the Diagnostic Server instance(s) and various UDS Transport Protocols (e.g., DoIP[2], CAN[21]). It provides a standard, extensible API for handling transport-specific message reception and optional early payload access.

Literaturverzeichnis SWS Diagnostics: [2] ISO 13400-2:2019 – Road vehicles – Diagnostic communication over Internet Protocol (DoIP) – Part 2: Network and transport layer requirements and services (Edition 2, Release 2019-12) – www.iso.org
[21] ISO 15765-2 – Road vehicles – Diagnostics on Controller Area Networks (CAN) – Part2: Network layer services

Kontext

Die Klasse apext::diag::uds_transport::UdsTransportProtocolMgr bildet die standardisierte Schnittstelle zur Koordination zwischen Instanzen des Diagnostic Servers (DM Core bzw. Session Layer) und verschiedenen UDS-Transportprotokollen wie DoIP oder CAN (AUTOSAR_AP_SWS_Diagnostics §7.1.1 „Support of UDS Transport Layer“). Konkrete Transportprotokolle werden als Unterklassen der abstrakten Basisklasse apext::diag::uds_transport::UdsTransportProtocolHandler realisiert ([SWS_DM_00315], AUTOSAR_AP_SWS_Diagnostics §7.1.1 „Support of UDS Transport Layer“).

In dieser Vermittlerfunktion interagiert die Manager-Klasse im Wesentlichen mit drei Komponenten:

  • UDS Transport Protocol Handler (Transport Layer): Melden den Beginn eingehender Nachrichten an ([SWS_DM_00309]), übergeben vollständig empfangene Anfragen ([SWS_DM_00311]), quittieren Sendeaufträge ([SWS_DM_00312]) und signalisieren Kanal- sowie Statusänderungen ([SWS_DM_00313], [SWS_DM_00314]).
  • Diagnostic Server Core (Session Layer): Übernimmt gültige UDS-Anfragen zur weiteren Diagnoseverarbeitung und verwaltet die Zuweisung von Nachrichtenpuffern ([SWS_DM_00309], [SWS_DM_00311]).
  • Periodische Transport-Handler: Übermitteln Bestätigungen über die erfolgreiche Übertragung periodischer Nachrichtenketten ([SWS_DM_01069]).

Kontextdiagramm: Zusammenspiel des UdsTransportProtocolMgr mit den Transport-Handlern und dem Session Layer. Quellen: AUTOSAR_AP_SWS_Diagnostics §7.1.1 „Support of UDS Transport Layer“, [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00314].

Lebenszyklus

Der Lebenszyklus einer Transportprotokoll-Implementierung wird durch den Diagnostic Manager (DM) in einer fest definierten Reihenfolge von Konstruktion, Initialisierung bis zum Stoppen gesteuert ([SWS_DM_00329], AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 „Initialization, Starting and Stopping of a UDS TransportLayer“). Die Klasse UdsTransportProtocolMgr deklariert einen virtuellen Standard-Destruktor ([SWS_DM_01524]).

Im laufenden Betrieb werden Deaktivierungsphasen synchronisiert: Hat ein Handler in Reaktion auf ein Stoppen seine Netzwerkverbindungen geschlossen und Ressourcen freigegeben, benachrichtigt er den Manager über den Rückruf HandlerStopped unter Angabe seiner handlerId ([SWS_DM_00314]).

Hinsichtlich der Speicher- und Besitzverhältnisse gilt für Nachrichtenpuffer ein klares Transfermodell: Bei Beginn einer Übertragung erstellt der DM-Core das Nachrichtenobjekt und übergibt dessen Zeiger an den Handler ([SWS_DM_00309]). Nach vollständigem Empfang transferiert der Handler den Besitz der Nachricht mittels unique_ptr-Semantik über HandleMessage an den generischen DM-Core zurück ([SWS_DM_00311]).

Sämtliche Schnittstellenmethoden sind als ausnahmesicher (noexcept), jedoch als nicht threadsicher (not thread-safe) spezifiziert ([SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00312]). Interpretation: Aufrufe an den Manager müssen daher vermutlich durch die aufrufenden Transport- und Sitzungskomponenten synchronisiert werden.

Nutzungspfad

Der reguläre Ablauf zur Verarbeitung eingehender UDS-Diagnoseanfragen gliedert sich in folgende Schritte:

  1. Nachrichtenindikation: Sofern der Handler die Indikation unterstützt, ruft er bei Eintreffen erster Daten IndicateMessage auf ([SWS_DM_00309]). Dabei werden Quell- und Zieladresse, der Adressierungstyp (physikalisch oder funktional), die erwartete Gesamtgröße sowie der GlobalChannelIdentifier ([SWS_DM_09021]) übermittelt. Über payloadInfo können bereits die ersten Bytes übergeben werden, damit der DM beispielsweise funktionale Tester-Present-Anfragen frühzeitig erkennen kann ([SWS_DM_00309]).
  2. Pufferbereitstellung: Der Manager liefert ein Paar aus IndicationResult und einem zugewiesenen UdsMessagePtr zurück ([SWS_DM_00309]). Ist das Ergebnis IndicationResult::kIndicationOk ([SWS_DM_00384]), füllt der Handler den Puffer mit den eintreffenden Daten.
  3. Übergabe an Session Layer: Nach vollständigem Empfang übergibt der Handler die Nachricht via HandleMessage an den Manager ([SWS_DM_00311]), was dem Dienst T_Data.ind nach ISO 14229-2 entspricht. Der Aufruf kehrt unverzüglich zurück; die weitere Auswertung erfolgt asynchron im Session Layer ([SWS_DM_00311]).
  4. Sende-Quittierung: Für versendete UDS-Antworten bestätigt der Handler den Erfolg später über TransmitConfirmation mit dem Resultat kTransmitOk ([SWS_DM_00312], [SWS_DM_00307]), entsprechend T_Data.con nach ISO 14229-2.

Sequenzdiagramm: Ablauf des UDS-Nachrichtenempfangs von der Indikation bis zur asynchronen Übergabe an den Session Layer. Quellen: [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00384].

Fehlerszenarien

Fehlerbedingungen während des Transports oder der Pufferallokation werden über definierte Statuswerte und Fehlerschnittstellen abgefangen:

  • Fehlschlag bei der Indikation: Kann der DM-Core eine indizierte Nachricht nicht annehmen, meldet er dies über das Enum IndicationResult ([SWS_DM_00309], [SWS_DM_00384]):
    • kIndicationOccupied: Der Server bzw. die Diagnosesitzung ist derzeit belegt ([SWS_DM_00384]).
    • kIndicationOverflow: Die übermittelte Nachrichtengröße überschreitet die Pufferkapazität ([SWS_DM_00384]).
    • kIndicationUnknownTargetAddress: Die adressierte Zieladresse ist nicht konfiguriert ([SWS_DM_00384]).
  • Abbruch des Empfangs: Tritt nach erfolgreichem IndicateMessage ein Verbindungsabbruch oder Übertragungsfehler auf, ruft der Handler NotifyMessageFailure auf ([SWS_DM_00310]). Das zuvor erhaltene UdsMessage-Objekt wird an den DM zurückgegeben, ohne dass ein Aufruf von HandleMessage erfolgt ([SWS_DM_00310]).
  • Sendeübertragungsfehler: Kann eine ausgehende Nachricht auf Netzwerkebene nicht gesendet werden, meldet der Handler über TransmitConfirmation das Ergebnis TransmissionResult::kTransmitFailed ([SWS_DM_00312], [SWS_DM_00307]).
  • Kanalreaktivierung: Nach einem temporären Verbindungsverlust signalisiert der Handler die erneute Verfügbarkeit eines Kanals über ChannelReestablished mit dem GlobalChannelIdentifier ([SWS_DM_00313], [SWS_DM_09021]), sofern diese Benachrichtigung zuvor angefordert wurde ([SWS_DM_00313]).

Nachrichtenempfang

HandleMessage function

Hands over a valid received UDS message (currently this is only a request type) from the Transport Layer to the Session Layer. This corresponds to T_Data.ind of Figure 2 from ISO 14229-2[25]. The behavior is asynchronously, i.e. the UDS Message is handed over to the Session Layer and it is expected, that it "instantly" returns, which means, that real processing of the message shall be done asynchronously by the Transport Layer!

virtual void HandleMessage (UdsMessagePtr message) noexcept=0;
IndicateMessage function

Indicates a message start. This is an interface, which is just served/called by UdsTransportProtocolHandlers, which return TRUE from UdsTransportProtocolHandlers::isStartOfMessageIndicationSupported().

virtual std::pair< IndicationResult, UdsMessagePtr > IndicateMessage ( UdsMessage::Address sourceAddr, UdsMessage::Address targetAddr, Uds Message::TargetAddressType type, GlobalChannelIdentifier globalChannel Id, std::size_t size, ara::core::Span< const std::uint8_t > payload Info) noexcept=0;

ChannelReestablished function

Notification call from the given transport protocol channel, that it has been reestablished since the last (Re)Start from the UdsTransportProtocolHandler to which this channel belongs. To activate this notification a previous call to UdsTransportProtocolHandler::Notify Reestablishment() has to be done. virtual void ChannelReestablished (GlobalChannelIdentifier global ChannelId) noexcept=0;
HandlerStopped function

Notification call from handler, that it has stopped now (e.g. closed down network connections, freed resources, etc...) This callback is expected as a reaction from handler to a call to UdsTransportProtocol Handler::Stop().

virtual void HandlerStopped (UdsTransportProtocolHandlerID handlerId) noexcept=0;

Type of tuple to pack UdsTransportProtocolHandlerID and ChannelID together, to form a global unique (among all used UdsTransportProtocolHandlers within DM) identifier of a Uds TransportProtocol channel.
