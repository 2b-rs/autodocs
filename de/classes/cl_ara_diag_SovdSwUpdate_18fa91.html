Kontext

Die Klasse ara::diag::SovdSwUpdate bildet die Schnittstelle zur Abwicklung von Software-Aktualisierungen über das Service-Oriented Vehicle Diagnostics (SOVD) Protokoll gemäß ASAM SOVD und ISO 17978-3 ([SWS_DM_01874], [SWS_DM_01796]). Innerhalb der AUTOSAR Adaptive Platform besteht eine klare funktionale Aufgabenteilung: Die eigentliche Fachlogik zur Durchführung und Verwaltung von Software-Updates verbleibt in der adaptiven Anwendung, während der funktionale Cluster Diagnostics (Diagnostic Server Instance bzw. Diagnostic Management) die Handhabung des zugrundeliegenden SOVD-Protokolls übernimmt (AUTOSAR_AP_SWS_Diagnostics §7.3 „Figure 7.4: SOVD Software Update API“).

Als abstrakte Basisklasse definiert SovdSwUpdate die Callback-Schnittstellen, die von der Anwendungssoftware implementiert werden müssen. Eingehende Anfragen externer SOVD-Clients werden von der Diagnostic Server Instance analysiert und über die entsprechenden Methoden von SovdSwUpdate an die Anwendung delegiert (AUTOSAR_AP_SWS_Diagnostics §7.3 „SOVD Software Update API“).

Kontextdiagramm: Interaktionspartner und Rollenverteilung bei der SOVD-Software-Aktualisierung. Quellen: [SWS_DM_01796], [SWS_DM_01874], AUTOSAR_AP_SWS_Diagnostics §7.3 „Figure 7.4: SOVD Software Update API“

Lebenszyklus

Die Erzeugung einer anwendungsspezifischen Instanz erfolgt über den parametrisierten Konstruktor unter Angabe eines Instanzbezeichners (ara::core::InstanceSpecifier) und des gewünschten Nebenläufigkeitsmodells (ConcurrencyType) ([SWS_DM_01910]). Der InstanceSpecifier referenziert dabei einen im Software-Manifest deklarierten PortPrototype, der auf ein DiagnosticSovdUpdateInterface typisiert sein muss ([SWS_DM_01910]). Über den concurrencyType wird festgelegt, ob die Callback-Methoden der Instanz bei gleichzeitigen Anfragen thread-sicher (kConcurrent) oder sequentiell bzw. nicht thread-sicher (kNotConcurrent) angesteuert werden sollen ([SWS_DM_01910]).

Instanzen von SovdSwUpdate sind eineindeutig an einen Service-Port gebunden. Der Copy-Konstruktor sowie der Zuweisungsoperator sind daher explizit gelöscht (=delete) ([SWS_DM_01912], [SWS_DM_01914]). Move-Operationen sind geschützt definiert (protected) ([SWS_DM_01913], [SWS_DM_01915]).

Nach erfolgreicher Initialisierung muss die Anwendung den Dienst explizit mittels Offer() aktivieren ([SWS_DM_01924]). Erst dieser Aufruf veranlasst den Diagnostic Manager (DM), eingehende SOVD-Anfragen an die registrierten Handler-Methoden weiterzuleiten. Vor dem Zerstören des Handler-Objekts ist der Dienst über StopOffer() zu deregistrieren, um eine weitere Weiterleitung von Anfragen zu unterbinden ([SWS_DM_01925]). Der Abbau wird über den virtuellen Destruktor ~SovdSwUpdate() abgeschlossen ([SWS_DM_01911]).

Nutzungspfad

Der typische Betriebsablauf umfasst mehrere aufeinanderfolgende Phasen eines Software-Updates:

  1. Dienstangebot: Die Anwendung instanziiert ihre Ableitung von SovdSwUpdate und ruft Offer() auf ([SWS_DM_01924]).
  2. Paketregistrierung und Transfer: Eingehende Registrierungsanfragen eines SOVD-Clients leitet der Diagnostic Server an RequestUpdatePackageRegistration() weiter ([SWS_DM_01923]). Die Methode liefert ein ara::core::Future mit einem Tupel aus einer Schreibsitzung (DataTransferWriteSession) und einer eindeutigen Paketkennung (updatePackageId) zurück ([SWS_DM_01923]). Interpretation: Der eigentliche Datentransfer der Update-Nutzdaten dürfte über diese bereitgestellte Schreibsitzung abgewickelt werden (AUTOSAR_AP_SWS_Diagnostics §7.3 „Figure 7.4: SOVD Software Update API“).
  3. Paketvorbereitung: Zur Vorbereitung der Installation ruft der Diagnostic Server PrepareUpdatePackage() auf ([SWS_DM_01800], [SWS_DM_01919]). Alternativ kann eine automatisierte Installation über PutUpdatePackageAutomated() angestoßen werden ([SWS_DM_01799], [SWS_DM_01918]).
  4. Paketausführung: Die Installation des vorbereiteten Update-Pakets wird durch den Aufruf von ExecuteUpdatePackage() initiiert ([SWS_DM_01801], [SWS_DM_01920]).
  5. Statusabfrage und Inspektion: Während oder nach dem Vorgang können Detailinformationen und der Status über GetUpdatePackageStatus() ([SWS_DM_01802], [SWS_DM_01921]), GetUpdatePackageDetails() ([SWS_DM_01917]) oder die Gesamtliste über GetAllUpdates() ([SWS_DM_01797], [SWS_DM_01916]) abgefragt werden. Nicht mehr benötigte Pakete werden über DeleteUpdatePackage() entfernt ([SWS_DM_01922]).

Fehlerszenarien

Fehlerbedingungen gliedern sich in Konfigurations- und Modellierungsfehler, Dienstzustandsfehler sowie protokollspezifische Ausführungsfehler:

  • Modell- und Instanziierungsfehler: Schlägt die Auflösung des InstanceSpecifier fehl oder verweist dieser auf ein unpassendes Element, werden spezifische Laufzeitverletzungen (Violations) gemeldet: InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation sowie InstanceSpecifierAlreadyInUseViolation, falls der Bezeichner innerhalb des Prozesses bereits verwendet wird ([SWS_DM_01910]).
  • Angebotsfehler: Der Aufruf von Offer() gibt ein ara::core::Result<void> zurück. Im Fehlerfall enthält dieses DiagOfferErrc::kAlreadyOffered, falls der Service bereits angeboten wird, oder DiagOfferErrc::kConfigurationMismatch, wenn die Konfiguration nicht mit dem Diagnose-Extrakt (DEXT) übereinstimmt ([SWS_DM_01924]).
  • Ausführungs- und Protokollfehler: Die asynchronen Callback-Methoden liefern Ergebnisse als ara::core::Future zurück. Im Fehlerfall ist ein anwendbarer Fehlercode gemäß ASAM SOVD 1.1 bzw. ISO 17978-3 im Future zu hinterlegen ([SWS_DM_01917], [SWS_DM_01918], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01922], [SWS_DM_01923]).
  • Abbruchbehandlung: Allen asynchronen Methoden wird ein CancellationHandler übergeben. Die Anwendung ist dafür verantwortlich, diesen abzufragen, um eine vorzeitig abgebrochene Client-Konversation sauber zu beenden ([SWS_DM_01919], [SWS_DM_01920]).
