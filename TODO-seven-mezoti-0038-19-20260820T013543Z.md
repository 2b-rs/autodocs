## Findings / design decisions (recorded for the repair-authority trail)

1. `docs/pipeline/agent-execution.md` (the `0037-45` deliverable) plus
   `issues/_schema/{agent-capability,runner-request,runner-result}-v1.schema.json`
   are the frozen `0037-45` contract. `runner-request-v1` has
   `additionalProperties: false` and a fixed 7-value `action` enum with **no**
   `base-branch`/`merge-prereqs`/`integrate-*` member. Because the schema is
   frozen and out of my write scope, the contract in `branch-merge-actions.md`
   maps each typed action onto the closest existing generic `action` enum
   value (`generation` for `base-branch`, `path_limited_commit` for
   `merge-prereqs`, `path_limited_commit` + `bookkeeping_commit` for the
   Task→Feature/Feature→`main` integration action) and carries
   action-specific parameters (parent/source branch refs, expected tips,
   claim-union preflight) as documented string conventions inside the
   existing generic `read_scopes`/`write_scopes`/`preflight`/`dependencies`
   arrays, since no new schema property can be added.
2. `agent-capability-v1.schema.json`'s `class` enum is still
   `["sandboxed-grunt","privileged"]` — it predates the `unprivileged`
   capability class (`993ceffbc`). This is a pre-existing gap in a frozen,
   already-`[x]` schema, not created by this Task; `branch-merge-actions.md`
   notes it and treats `unprivileged` as executing the same actions directly
   without a `runner-request@v1` instance at all (per `SANDBOX.md`: direct
   execution, no runner routing), consistent with how this very claim is
   being carried out. Not fixed here — flagged for the integrator/`0037-46.01`
   owner rather than silently edited into the frozen schema.
3. Authority split, per this Task's own acceptance-criteria wording ("the
   Subtask→Task versus Task→Feature/Feature→`main` authority split") and
   `0038-20`'s dependent acceptance criteria ("Enforce Subtask→Task authority
   for sandboxed manifests and reject Task→Feature, Feature→`main`,
   acceptance-record, and Feature `[u]` verdict actions"): `base-branch` and
   `merge-prereqs` always target the *current item's own* (not-yet-integrated)
   branch, so they never advance a checkpointed ref and are grunt/unprivileged
   eligible; the integration action always targets a Feature branch or `main`
   and is privileged-only regardless of whether the specific node carries the
   `Integration review: mandatory` flag (Feature→`main` is privileged-only
   unconditionally per `branch-workflow.md`).
4. `branch-workflow.md`'s own "Capability-class execution of branch
   operations" section says "Grunt-permitted merges are limited to
   Subtask→Task", which is stricter than its "Merge authority and direction"
   section's checkpoint-based framing (illustrated by the Task-level
   "Two prerequisites on two branches" worked example). `0038-19`'s contract
   follows the destination-branch framing above, consistent with `0038-20`'s
   committed acceptance text; the residual prose tension between those two
   `branch-workflow.md` sections is noted in `branch-merge-actions.md` as an
   observation but is **not** rewritten here (out of write scope; a single
   additive cross-reference, not a restructure, would be the correct fix and
   is deferred).
