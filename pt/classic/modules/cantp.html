CanTp como camada de segmentação entre o PduR e o CanIf

O CanTp é a CAN Transport Layer da pilha de comunicação Classic. O módulo segmenta N-SDUs que não cabem em um quadro CAN, transmite-as com controle de fluxo e as remonta na recepção (SWS CanTp p. 23). A base técnica é a ISO 15765-2: qualquer recomendação não explicitamente excluída ali deve ser cumprida [SWS_CanTp_00033]. A segmentação e a remontagem ocorrem apenas no estado CANTP_ON [SWS_CanTp_00238].

Para cima, o CanTp colabora exclusivamente com o PDU Router. Usuários como o DCM ou o Com acessam CanTp_Transmit, CanTp_CancelTransmit e CanTp_CancelReceive por meio do PduR (SWS PduR p. 24). No sentido oposto, o CanTp chama os serviços PduR_CanTp…; para baixo, ele utiliza CanIf_Transmit [SWS_CanTp_00216]. Para a camada inferior, o CanTp disponibiliza os callbacks CanTp_RxIndication e CanTp_TxConfirmation [SWS_CanTp_00078] [SWS_CanTp_00076]. Ambos devem poder ser chamados no contexto de interrupção [SWS_CanTp_00235] [SWS_CanTp_00236]. Trechos de documentos mais recentes mencionam o “LSduR” como parceiro inferior (SWS CanTp p. 26). No R20-11, esse parceiro é o CanIf [SWS_CanTp_00335].

Diagrama de contexto: o CanTp situa-se entre o PduR e o CanIf, é inicializado por meio do BswM e operado ciclicamente pelo escalonador. Fontes: [SWS_CanTp_00216] [SWS_CanTp_00164] SWS CanTp p. 17 Modemanagement-Guide p. 54

Da energização, passando por CanTp_Init, até os estados dos canais

O CanTp reconhece os estados globais CANTP_OFF e CANTP_ON [SWS_CanTp_00027]. Após a energização, o módulo encontra-se em CANTP_OFF [SWS_CanTp_00168]. Nesse estado, a configuração Post-Build pode ser atualizada [SWS_CanTp_00169]. O ambiente deve chamar CanTp_Init antes de qualquer outro uso [SWS_CanTp_00199]. A função recebe, com isso, um ponteiro para CanTp_ConfigType [SWS_CanTp_00208] [SWS_CanTp_00340]. No exemplo do guia de gerenciamento de modo, a chamada está em uma regra do BswM após NvM_ReadAll (Modemanagement-Guide p. 54).

Após a inicialização bem-sucedida, o CanTp transita para CANTP_ON [SWS_CanTp_00170]. CanTp_Init inicializa todas as variáveis globais e define cada conexão como CANTP_RX_WAIT ou CANTP_TX_WAIT [SWS_CanTp_00030]. Uma nova chamada em CANTP_ON retorna ao estado ocioso; com isso, todas as conexões em andamento são perdidas [SWS_CanTp_00111] [SWS_CanTp_00273]. CanTp_Shutdown fecha todas as conexões abertas, libera os recursos e transita para CANTP_OFF [SWS_CanTp_00202]. Não há notificação sobre transmissões canceladas [SWS_CanTp_00200].

Diagrama de estados: dentro de CANTP_ON, os canais Rx e Tx passam, de forma independente entre si, pelos subestados WAIT e PROCESSING. Fontes: [SWS_CanTp_00027] [SWS_CanTp_00030] [SWS_CanTp_00202] SWS CanTp p. 27

Envio de uma N-SDU: Single Frame ou sessão segmentada

CanTp_Transmit transfere o comprimento total e, se aplicável, MetaData, mas nenhum dado útil. Sem MetaData, o CanTp utiliza apenas SduLength para preparar o PCI do Single Frame (SF) ou First Frame (FF) [SWS_CanTp_00225] [SWS_CanTp_00299].

Interpretação: [SWS_CanTp_00212] descreve a API como síncrona, enquanto [SWS_CanTp_00176] exige um comportamento assíncrono. Provavelmente, a chamada apenas confirma a aceitação, e a transmissão ocorre em seguida.

Se os dados não couberem na N-PDU atribuída, uma sessão de múltiplos quadros é iniciada [SWS_CanTp_00232] (SWS CanTp p. 60). O comprimento máximo de transmissão (TX_DL) decorre do parâmetro EcuC PduLength [SWS_CanTp_00354].

O CanTp obtém os dados úteis para cada segmento (SF, FF, CF) com PduR_CanTpCopyTxData [SWS_CanTp_00086] [SWS_CanTp_00298]. Em caso de BUFREQ_E_BUSY, o CanTp repete a tentativa de cópia mais tarde [SWS_CanTp_00184]. O parâmetro Retry é sempre um ponteiro NULL [SWS_CanTp_00272].

Após o FF, o temporizador N_Bs monitora a chegada do Flow Control (FC) [SWS_CanTp_00315]. Um FC segue sempre após um bloco de BS Consecutive Frames [SWS_CanTp_00278]. No final, o CanTp reporta a conclusão com PduR_CanTpTxConfirmation e E_OK [SWS_CanTp_00090] [SWS_CanTp_00204]. Cada requisição aceita é concluída com exatamente uma notificação desse tipo, mesmo em caso de falha [SWS_CanTp_00177].

O CanTp rejeita novas requisições com E_NOT_OK se o canal estiver ocupado (CANTP_TX_PROCESSING) ou se a N-SDU já estiver em execução em uma sessão [SWS_CanTp_00123] [SWS_CanTp_00206].

Diagrama de sequência: o CanTp obtém os dados em segmentos junto ao PduR e sincroniza os Consecutive Frames com base no Flow Control. Fontes: [SWS_CanTp_00086] [SWS_CanTp_00232] [SWS_CanTp_00315] [SWS_CanTp_00090] SWS CanTp p. 37 SWS CanTp p. 73

Recepção: concessão de buffer, Flow Control e fases de espera

Um SF ou FF recebido dispara PduR_CanTpStartOfReception [SWS_CanTp_00079]. O tamanho de buffer disponível retorna por meio do ponteiro de saída e pode ser menor que a N-SDU [SWS_CanTp_00080]. O FC para um FF só é enviado após esse resultado, e o seu conteúdo depende disso [SWS_CanTp_00064] [SWS_CanTp_00277].

Após cada Consecutive Frame (CF), o CanTp transfere os dados com PduR_CanTpCopyRxData: 6 ou 7 bytes no CAN 2.0, DLC-1 ou DLC-2 bytes no CAN FD. Como retorno, o CanTp recebe o buffer restante [SWS_CanTp_00269]. O CanTp reporta a conclusão em qualquer caso, seja bem-sucedido ou não, com PduR_CanTpRxIndication [SWS_CanTp_00084].

Se o buffer não for suficiente para o próximo bloco, o CanTp inicia o temporizador N_Br [SWS_CanTp_00082] [SWS_CanTp_00325]. Enquanto o N_Br estiver em execução, o CanTp consulta em cada MainFunction com comprimento 0 e NULL_PTR por buffer livre [SWS_CanTp_00222]. Ele envia, no máximo, WFTmax quadros FC(WAIT) consecutivos; depois disso, ele aborta com E_NOT_OK [SWS_CanTp_00223]. BS e STmin permanecem constantes dentro de uma sessão de recepção [SWS_CanTp_00067]. O exemplo da especificação mostra a recepção de 49 bytes com 25 bytes de buffer (SWS CanTp p. 38).

Diagrama de sequência: recepção segmentada com consulta de buffer, FC(CTS) ou FC(WAIT) e cópia em blocos para o buffer da camada superior. Fontes: [SWS_CanTp_00079] [SWS_CanTp_00222] [SWS_CanTp_00269] [SWS_CanTp_00084] SWS CanTp p. 38 SWS CanTp p. 76

Diagrama de atividades: o resultado de PduR_CanTpStartOfReception decide sobre cancelamento, FC(OVFLW), FC(WAIT) ou FC(CTS). Fontes: [SWS_CanTp_00081] [SWS_CanTp_00318] [SWS_CanTp_00353] [SWS_CanTp_00082] [SWS_CanTp_00312] SWS CanTp p. 67 SWS CanTp p. 69

Canais de conexão, endereçamento e estratégia de buffer

O CanTp atende a várias conexões simultaneamente [SWS_CanTp_00096]. Cada N-SDU é atribuída estaticamente a um canal de conexão; um canal pode atender a várias N-SDUs [SWS_CanTp_00121]. Cada canal possui buffers, temporizadores e máquinas de estados próprios [SWS_CanTp_00122]. Os canais são visíveis apenas internamente [SWS_CanTp_00285]. O número deles é determinado pela ferramenta de configuração a partir da atribuição de N-SDUs aos canais [SWS_CanTp_00289]. Se várias N-SDUs compartilharem um canal e nenhum canal estiver livre, o CanTp rejeita o envio ou aborta a recepção [SWS_CanTp_00288] (SWS CanTp p. 41).

O endereçamento funcional (1:n) é previsto apenas para Single Frames [SWS_CanTp_00092]. O CanTp rejeita uma sessão segmentada por meio de um handle funcional e reporta CANTP_E_INVALID_TATYPE [SWS_CanTp_00093]. No endereçamento Extended ou Mixed, o primeiro byte de dados (N_TA ou N_AE) determina a N-SDU correspondente [SWS_CanTp_00095] [SWS_CanTp_00284].

Conexões genéricas operam com MetaData. O CanTp armazena as informações de endereço de um SF/FF recebido ou de CanTp_Transmit [SWS_CanTp_00330] [SWS_CanTp_00334]. Ele as encaminha para o PduR ou para o CanIf [SWS_CanTp_00331] [SWS_CanTp_00335]. Ele verifica os CF e FC recebidos contra os valores armazenados [SWS_CanTp_00333] [SWS_CanTp_00336]. Uma N-PDU só pode ser referenciada por várias N-SDUs no endereçamento Extended/Mixed ou com MetaData [SWS_CanTp_00328].

O CanTp não copia dados úteis internamente, mas opera diretamente nos buffers da camada superior por meio dos serviços de cópia [SWS_CanTp_00298]. A camada superior mantém, portanto, o seu buffer bloqueado. O bloqueio começa com E_OK de CanTp_Transmit ou BUFREQ_OK de PduR_CanTpStartOfReception e termina com a respectiva Confirmation ou Indication (SWS CanTp p. 35).

Para o padding, aplicam-se as seguintes regras (SWS CanTp p. 43):

  • Apenas bytes de dados utilizados são enviados para a camada superior [SWS_CanTp_00116].
  • O valor de preenchimento é CANTP_PADDING_BYTE [SWS_CanTp_00059].
  • Com o padding ativo, o SF, o último CF e o FC são enviados como quadros de 8 bytes [SWS_CanTp_00348] [SWS_CanTp_00347].
  • No CAN FD, o preenchimento é feito até o próximo DLC válido [SWS_CanTp_00351].

Temporização da MainFunction e parâmetros de tempo de execução BS/STmin

CanTp_MainFunction é chamada ciclicamente pelo escalonador. Ela monitora os limites de tempo N_As, N_Bs, N_Cs, N_Ar, N_Br e N_Cr, bem como STmin [SWS_CanTp_00213] [SWS_CanTp_00164]. O seu comportamento depende de CanTpMainFunctionPeriod [SWS_CanTp_00300]. Um trecho de documento de releases posteriores recomenda utilizar para isso o tempo de ciclo da tarefa chamadora (SWS CanTp p. 77). Como exemplo, a análise de temporização cita uma tarefa de 5 ms (TR Timing p. 117).

Com CanTp_ChangeParameter e CanTp_ReadParameter, é possível definir e ler BS e STmin de uma N-SDU de recepção em tempo de execução [SWS_CanTp_00302] [SWS_CanTp_00323]. O BS é, nesse caso, um valor máximo que o CanTp pode reduzir por considerações de buffer [SWS_CanTp_00091]. Nenhuma alteração é possível durante uma recepção em andamento; o serviço retorna então E_NOT_OK [SWS_CanTp_00303] [SWS_CanTp_00304]. Em conexões genéricas, uma alteração se aplica a todas [SWS_CanTp_00338]. A existência dos serviços é controlada por CanTpChangeParameterApi (SWS CanTp p. 61). O cancelamento de transmissão é ativado estaticamente por meio de CanTpTc [SWS_CanTp_00242].

Comportamento em caso de erro

Em caso de erro de desenvolvimento, o serviço retorna E_NOT_OK e reporta o erro ao DET [SWS_CanTp_00294]. Casos típicos:

  • Chamadas antes de CanTp_Init geram CANTP_E_UNINIT; exceto CanTp_GetVersionInfo [SWS_CanTp_00031].
  • Ponteiros NULL geram CANTP_E_PARAM_POINTER [SWS_CanTp_00321] [SWS_CanTp_00322] [SWS_CanTp_00319].

Para IDs inválidos em CanTp_CancelTransmit e CanTp_CancelReceive, o R20-11 exige CANTP_E_PARAM_ID [SWS_CanTp_00254] [SWS_CanTp_00260]. Trechos de documentos mais recentes citam, em vez disso, CANTP_E_INVALID_TX_ID ou CANTP_E_INVALID_RX_ID (SWS CanTp p. 59). Para o R20-11, aplica-se o requisito. Erros de tempo de execução como CANTP_E_PADDING, CANTP_E_INVALID_TATYPE e CANTP_E_OPER_NOT_SUPPORTED são definidos por [SWS_CanTp_00352].

Erros de protocolo encerram a sessão e são reportados à camada superior com E_NOT_OK. A recuperação cabe ao usuário, por exemplo, ao DCM (EXP Error p. 30; [SWS_CanTp_00205]).

Utilização e contexto de chamada

Com a função CanTp_Transmit, a camada superior solicita a transmissão de uma PDU [SWS_CanTp_00212]. Através do parâmetro TxPduId a PDU é identificada, enquanto PduInfoPtr aponta para o comprimento dos dados, os dados úteis bem como metadados opcionais [SWS_CanTp_00212]. A função confirma a solicitação de transmissão de forma síncrona com E_OK em caso de aceitação bem-sucedida ou com E_NOT_OK em caso de rejeição [SWS_CanTp_00212]; o processo de envio propriamente dito é assíncrono [SWS_CanTp_00176].

Tratamento de erros e condições de rejeição

  • Ponteiro inválido: se o DET estiver ativado e for passado um ponteiro NULL para PduInfoPtr, a função reporta o erro CANTP_E_PARAM_POINTER ao DET e aborta sem nenhuma ação adicional [SWS_CanTp_00321].
  • Canal ocupado: se o canal de transmissão configurado se encontrar no estado CANTP_TX_PROCESSING, o módulo rejeita novas solicitações de envio para este canal e retorna E_NOT_OK [SWS_CanTp_00123].
  • Sessão em curso: uma solicitação de envio também é rejeitada se o identificador de N-SDU passado já estiver sendo utilizado em uma sessão de transporte CanTp atualmente ativa [SWS_CanTp_00206].

Concorrência e tratamento de dados

CanTp_Transmit é reentrante para diferentes IDs de PDU, contudo não é reentrante para o mesmo ID de PDU [SWS_CanTp_00212].

Em conexões sem metadados, CanTp_Transmit avalia exclusivamente a informação SduLength para a criação do PCI para Single Frames (SF) ou First Frames (FF) e não acessa o buffer de dados da N-SDU [SWS_CanTp_00225]. Se forem utilizados metadados, o módulo armazena as informações de endereço contidas (como N_SA, N_TA ou N_AE, dependendo do formato de endereçamento) para o envio posterior de N-PDUs SF, FF e CF, bem como para a identificação de N-PDUs FC [SWS_CanTp_00334].

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 6c4fb3968367 Procedência

usar

A função síncrona CanTp_CancelTransmit ([SWS_CanTp_00246]) solicita o cancelamento de uma transmissão de PDU em andamento em um módulo de comunicação subjacente. A chamada inicia o cancelamento do envio ([SWS_CanTp_00274]), após o qual a transferência na respectiva conexão é abortada ([SWS_CanTp_00243]).

  • Parâmetros: TxPduId determina o identificador da PDU a ser cancelada ([SWS_CanTp_00246]).
  • Valor de retorno: E_OK indica que o cancelamento foi executado com sucesso pelo módulo de destino; E_NOT_OK significa que o cancelamento foi rejeitado ([SWS_CanTp_00246]).

Tratamento de erros

Se a detecção de erros de desenvolvimento estiver ativada, CanTp_CancelTransmit verifica a validade do parâmetro passado TxPduId ([SWS_CanTp_00254]):

  • Em caso de valor de parâmetro inválido, a função reporta o erro de desenvolvimento CANTP_E_PARAM_ID e retorna E_NOT_OK ([SWS_CanTp_00254]).
  • Se for solicitado um cancelamento para uma N-SDU que não esteja atualmente em processo de transmissão, o módulo CanTp reporta o erro de tempo de execução CANTP_E_OPER_NOT_SUPPORTED ao Default Error Tracer (DET) e fornece E_NOT_OK ([SWS_CanTp_00254]).

Simultaneidade e restrições

CanTp_CancelTransmit é reentrante para diferentes PDU-IDs, porém não é reentrante para a mesma PDU-ID ([SWS_CanTp_00246]).

Interação

Se o serviço CanTp_CancelTransmit foi executado com sucesso, o CanTp chama PduR_CanTpTxConfirmation com o resultado E_NOT_OK ([SWS_CanTp_00255]).

Nota: Esta nota de uso foi gerada automaticamente e baseia-se exclusivamente nos dados de especificação do AUTOSAR Classic Release R20-11.

Após um cancelamento executado com sucesso, CanTp chama a interface PduR_CanTpRxIndication com o resultado de notificação E_NOT_OK ([SWS_CanTp_00263]), para informar à camada superior sobre o cancelamento prematuro da recepção.

Utilização e contexto de chamada

A função de callback síncrona CanTp_RxIndication ([SWS_CanTp_00214]) sinaliza ao módulo de transporte CAN a recepção de uma N-PDU por meio de um módulo de interface de comunicação subjacente. São passados o identificador RxPduId, bem como PduInfoPtr com ponteiros para dados de buffer (SduDataPtr), comprimento de SDU (SduLength) e metadados. A função é reentrante para diferentes PDU-IDs, porém não reentrante para a mesma PDU-ID ([SWS_CanTp_00214]). Ela pode ser chamada diretamente no contexto de interrupção, por exemplo, a partir da ISR de recepção CAN ([SWS_CanTp_00235]).

Tratamento de erros e validação

Se a detecção de erros de desenvolvimento estiver ativada e um ponteiro NULL for passado como PduInfoPtr, CanTp_RxIndication reporta o erro CANTP_E_PARAM_POINTER ao DET e aborta a execução sem realizar nenhuma ação ([SWS_CanTp_00322]).

Com a verificação de padding ativada para quadros com até 8 bytes de carga útil, aplicam-se regras de consistência específicas:

  • Se em CanTpRxPaddingActivation == CANTP_ON for recebida uma SF N-PDU com SduLength < 8, a recepção é descartada e o erro de tempo de execução CANTP_E_PADDING é reportado ao DET ([SWS_CanTp_00345]).
  • Se a última CF N-PDU de uma transmissão em andamento com padding ativo não apresentar exatamente 8 bytes (SduLength != 8), o CanTp aborta a recepção via PduR_CanTpRxIndication() com o valor de retorno E_NOT_OK e reporta CANTP_E_PADDING ([SWS_CanTp_00346]).
  • Se durante uma sessão de transmissão com CanTpTxPaddingActivation == CANTP_ON chegar uma FC N-PDU com SduLength < 8, o CanTp aborta a sessão de transmissão via PduR_CanTpTxConfirmation() com E_NOT_OK e reporta CANTP_E_PADDING ao DET ([SWS_CanTp_00349]).

Conexões genéricas

Tratando-se de uma conexão genérica (N-PDU com metadados), o módulo CanTp salva, na chamada para quadros SF ou FF, os dados de endereçamento a partir dos metadados (no caso de Normal Fixed e Mixed de 29 bits: N_SA e N_TA) para a inicialização da conexão para as camadas superiores, bem como para a posterior identificação de FC e CF ([SWS_CanTp_00330]). Para quadros subsequentes de CF ([SWS_CanTp_00333]) e FC ([SWS_CanTp_00336]), o CanTp compara os metadados recebidos com esses valores de referência armazenados.
