Papel na pilha de comunicação: intermediário neutro para I-PDUs

O PDU Router (PduR) conecta usuários independentes de barramento, como Com ou Dcm, a interfaces de comunicação (CanIf, FrIf, LinIf) e protocolos de transporte (CanTp, FrTp). Ele transmite uma I-PDU de forma inalterada e consistente da origem para os destinos [SWS_PduR_00160]. Ao fazer isso, ele realiza o roteamento exclusivamente ao longo de caminhos de roteamento configurados [SWS_PduR_00162]. Um caminho é determinado univocamente por duas informações: o ID da I-PDU de origem da configuração do PduR e os IDs das I-PDUs de destino dos módulos chamados [SWS_PduR_00161]. O PduR converte esses IDs no caminho de envio, assim como no caminho de confirmação e no de indicação [SWS_PduR_00766], SWS PduR p. 33.

Do ponto de vista da unidade de controle, existem três classes de operação. Primeiro, a recepção para módulos locais; segundo, o envio a partir de módulos locais; e terceiro, o gateway entre módulos de interface ou TP. Recepção e gateway podem ser combinados SWS PduR p. 29. Os módulos vizinhos são descritos genericamente por meio dos placeholders <Up>, <Lo> e <LoTp> SWS PduR p. 96. Complex Drivers também podem ser integrados; o seu apiServicePrefix substitui então os placeholders [SWS_PduR_00504]. Cada módulo vizinho recebe um arquivo de cabeçalho próprio, como PduR_CanIf.h [SWS_PduR_00216].

Diagrama de contexto: o PduR fica entre os usuários superiores, módulos de interface e TP, e é controlado pelo BswM por meio de grupos de caminhos de roteamento. Fontes: [SWS_PduR_00424], [SWS_PduR_00504], SWS PduR p. 96, SWS BswM p. 166

Sob duas condições os módulos vizinhos podem chamar-se diretamente: PduRZeroCostOperation está definido e todos os caminhos de roteamento são Pre-Compile [SWS_PduR_00287]. O PduR torna-se então uma camada puramente de macros SWS PduR p. 65. Se apenas um caminho não for Pre-Compile, o gerador deve reportar um erro [SWS_PduR_00619]. Independentemente disso, o gerador deve otimizar e remover recursos não utilizados, como TP, gateway ou tratamento de FIFO [SWS_PduR_00764].

Ciclo de vida e estado de configuração: de PDUR_UNINIT para PDUR_ONLINE

Existe exatamente uma máquina de estados [SWS_PduR_00644]. Ela reconhece os estados PDUR_UNINIT e PDUR_ONLINE de PduR_StateType [SWS_PduR_00324], [SWS_PduR_00742]. Após a energização, o PduR está em PDUR_UNINIT [SWS_PduR_00325]. Apenas um PduR_Init bem-sucedido o conduz para PDUR_ONLINE [SWS_PduR_00326], [SWS_PduR_00334]. O roteamento ocorre apenas em PDUR_ONLINE [SWS_PduR_00328]; em PDUR_UNINIT, não ocorre de forma alguma [SWS_PduR_00330]. Um diagrama mais antigo mostra adicionalmente um estado PDUR_REDUCED SWS PduR p. 30. Para o R20-11, no entanto, aplica-se o modelo de dois estados conforme [SWS_PduR_00324].

Diagrama de estados: apenas PduR_Init conduz de PDUR_UNINIT para a operação de roteamento; uma nova chamada de Init constitui um erro. Fontes: [SWS_PduR_00324], [SWS_PduR_00100], [SWS_PduR_00296], SWS PduR p. 53

PduR_Init recebe um ponteiro para PduR_PBConfigType [SWS_PduR_00743]. Essa estrutura é específica da implementação e localiza-se em PduR_PBcfg.c [SWS_PduR_00241]. Na inicialização, o PduR executa três tarefas:

  • Ele libera todos os buffers [SWS_PduR_00645].
  • Ele preenche os buffers de transmissão com os valores padrão configurados [SWS_PduR_00308].
  • Ele ativa os grupos de caminhos de roteamento de acordo com a configuração inicial [SWS_PduR_00709], isto é, conforme PduRIsEnabledAtInit SWS PduR p. 131.

Na variante Post-Build, as tabelas de roteamento são intercambiáveis [SWS_PduR_00295], mas apenas no estado não inicializado [SWS_PduR_00296]. PduR_GetConfigurationId fornece o PduRConfigurationId exclusivo da configuração ativa [SWS_PduR_00341], [SWS_PduR_00280], [SWS_PduR_00281]. O seu tipo é PduR_PBConfigIdType com base em uint16 [SWS_PduR_00771]. PduR_GetVersionInfo [SWS_PduR_00338] está disponível apenas se PduRVersionInfoApi estiver definido System Template p. 656.

Envio e recepção locais por meio de interfaces de comunicação

Se um módulo superior chamar PduR_<User:Up>Transmit [SWS_PduR_00406], o PduR chamará <Lo>_Transmit para cada interface de destino [SWS_PduR_00625]. Com isso, ele não armazena a I-PDU em buffer [SWS_PduR_00629] e também não verifica o seu comprimento [SWS_PduR_00745]. Em caso de singlecast, ele repassa o valor de retorno [SWS_PduR_00432]. Em caso de multicast, um único destino bem-sucedido é suficiente para E_OK [SWS_PduR_00218]. A confirmação para o módulo superior só ocorre, então, após a última confirmação de interface [SWS_PduR_00589]. Em singlecast, o PduR encaminha PduR_<User:Lo>TxConfirmation [SWS_PduR_00365] juntamente com o resultado para <Up>_TxConfirmation [SWS_PduR_00627].

Em barramentos acionados por tempo, a própria interface busca os dados, especificamente via PduR_<User:Lo>TriggerTransmit [SWS_PduR_00369]. O PduR encaminha essa solicitação para <Up>_TriggerTransmit [SWS_PduR_00430] e retorna o valor de retorno deste [SWS_PduR_00661]. A interface reporta as I-PDUs recebidas com PduR_<User:Lo>RxIndication [SWS_PduR_00362]. Em seguida, o PduR chama <Up>_RxIndication para cada módulo de destino [SWS_PduR_00621], [SWS_PduR_00164], também sem verificação de comprimento [SWS_PduR_00744].

Diagrama de sequência: o envio por meio de FrIf divide-se em três fases separadas no tempo: requisição, busca de dados via TriggerTransmit e confirmação. Fontes: [SWS_PduR_00430], [SWS_PduR_00627], SWS PduR p. 106

Caminhos de protocolo de transporte para I-PDUs segmentadas

Nos caminhos TP, o PduR opera com um handshake de cópia que viabiliza I-PDUs maiores que um quadro Layered Architecture p. 97. A recepção ocorre em três etapas:

  1. O PduR encaminha PduR_<User:LoTp>StartOfReception [SWS_PduR_00507] para <Up>_StartOfReception [SWS_PduR_00549] e repassa o seu valor de retorno [SWS_PduR_00623].
  2. Seguem-se as chamadas CopyRxData para os segmentos individuais [SWS_PduR_00512], [SWS_PduR_00428].
  3. A conclusão é formada pela indicação de recepção [SWS_PduR_00375], [SWS_PduR_00429].

Uma chamada de cópia com SduLength = 0 consulta apenas o buffer disponível ou os dados disponíveis [SWS_PduR_00740].

Diagrama de sequência: na recepção TP, o PduR solicita buffer ao módulo superior para cada segmento e repassa as suas respostas inalteradas. Fontes: [SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429], SWS PduR p. 75

No envio, o PduR chama <LoTp>_Transmit para cada TP de destino [SWS_PduR_00634]. Os módulos TP buscam os dados em seguida com PduR_<User:LoTp>CopyTxData [SWS_PduR_00518]. O PduR encaminha essas chamadas para <Up>_CopyTxData [SWS_PduR_00299], [SWS_PduR_00676]. Em caso de multicast, ele copia primeiro com TP_CONFPENDING para cada posição; para todos os demais destinos, ele copia os mesmos dados com TP_DATARETRY [SWS_PduR_00631], [SWS_PduR_00632]. Em singlecast, <Up>_TpTxConfirmation segue diretamente [SWS_PduR_00301]. Em multicast, ela segue apenas após a última confirmação, e com E_OK se pelo menos um destino tiver sido bem-sucedido [SWS_PduR_00765], [SWS_PduR_00381]. Os destinos de uma requisição de envio são ou apenas interfaces ou apenas módulos TP, nunca mistos [SWS_PduR_00633].

Diagrama de sequência: no multicast TP, o PduR obtém os mesmos dados várias vezes junto ao módulo superior e consolida as confirmações em uma só. Fontes: [SWS_PduR_00631], [SWS_PduR_00632], [SWS_PduR_00765], SWS PduR p. 86

Operação de gateway entre redes: armazenamento em buffer, FIFO e On-the-fly

Entre interfaces, o PduR suporta gatewaying 1:n [SWS_PduR_00436]. Ele repassa as I-PDUs imediatamente e não cria ciclos de envio próprios [SWS_PduR_00437]. Uma I-PDU é roteada apenas entre interfaces ou apenas entre TPs, nunca de forma mista [SWS_PduR_00638]. Se o PduR armazena em buffer depende do fornecimento de dados do destino:

  • Em PDUR_DIRECT, a interface de destino copia os dados já na chamada de Transmit [SWS_PduR_00303].
  • Em PDUR_TRIGGERTRANSMIT, o PduR armazena a I-PDU em buffer até a chamada de TriggerTransmit [SWS_PduR_00306].

Sem armazenamento em buffer, o PduR repassa o menor dos dois comprimentos: comprimento de recepção ou comprimento de destino [SWS_PduR_00783]. Com armazenamento em buffer, ele copia no máximo PduRPduMaxLength [SWS_PduR_00746].

Para cada I-PDU de destino, uma FIFO pode ser configurada [SWS_PduR_00307]. A partir de PduRQueueDepth > 1, o buffer comporta-se como FIFO [SWS_PduR_00785], e novas I-PDUs são anexadas ao final [SWS_PduR_00787]. Em caso de fornecimento direto, aplica-se o seguinte: se a FIFO estiver vazia e nenhuma confirmação estiver pendente, o PduR envia imediatamente [SWS_PduR_00665]. Caso contrário, ele enfileira a I-PDU [SWS_PduR_00793] e a envia após a próxima confirmação [SWS_PduR_00667]. No Trigger-Transmit, o PduR copia a entrada mais antiga e a remove; se restar conteúdo depois disso, ele chama novamente <DstLo>_Transmit [SWS_PduR_00666]. Se a FIFO estiver vazia, a busca retorna E_NOT_OK [SWS_PduR_00662].

Diagrama de atividades: em um gateway de interface, o fornecimento de dados e o estado da FIFO decidem se o PduR envia imediatamente, enfileira ou aguarda o TriggerTransmit. Fontes: [SWS_PduR_00665], [SWS_PduR_00786], [SWS_PduR_00255], SWS PduR p. 112

Os gateways TP operam em um de dois modos:

  • Direto: o PduR chama <DstLoTp>_Transmit apenas após a indicação de recepção bem-sucedida [SWS_PduR_00551].
  • On-the-fly: o reenvio começa assim que PduRTpThreshold for atingido [SWS_PduR_00317]. Esse modo é permitido apenas com exatamente um TP de destino [SWS_PduR_00708], SWS PduR p. 58.

Se TpSduLength couber no buffer dedicado, o PduR utiliza-o; caso contrário, ele obtém dinamicamente um buffer a partir de PduRTxBuffer [SWS_PduR_00797], [SWS_PduR_00798]. Ele repassa MetaData para o destino [SWS_PduR_00794]. Se um receptor local também estiver configurado, o PduR iniciará uma sessão de recepção própria nesse módulo após a recepção bem-sucedida [SWS_PduR_00789].

Diagrama de sequência: no gateway on-the-fly, a recepção na CAN1 e o envio na CAN2 sobrepõem-se assim que o limiar é atingido. Fontes: [SWS_PduR_00317], [SWS_PduR_00708], [SWS_PduR_00518], SWS PduR p. 100

Comutar grupos de caminhos de roteamento em tempo de execução

Contêineres PduRRoutingPathGroup agrupam os caminhos de uma rede ou de um tipo de PDU SWS PduR p. 131. Eles são endereçados por meio de PduR_RoutingPathGroupIdType, um uint16 [SWS_PduR_00654]. Eles são comutados com PduR_EnableRouting e PduR_DisableRouting [SWS_PduR_00615], [SWS_PduR_00617]. O parâmetro initialize determina se os buffers individuais são redefinidos para o valor padrão ou mantidos [SWS_PduR_00617]. A ativação tem efeito imediato [SWS_PduR_00715]. Se uma API utilizar o ID da I-PDU de um caminho desativado, o PduR retornará E_NOT_OK sem nenhuma ação adicional, desde que o tipo de retorno o permita [SWS_PduR_00717]. Isso se aplica expressamente também às funções de cancelamento [SWS_PduR_00710], [SWS_PduR_00726].

O chamador típico é o BswM por meio da ação BswMPduRouterControl SWS BswM p. 166. O guia de gerenciamento de modo cita dois casos de uso: I-PDUs sem grupo de I-PDU do Com, por exemplo via LdCom, e a comutação dependente do estado do PNC, que o ComM reporta ao BswM Mode-Management-Guide p. 50. Releases posteriores detalham como caminhos com múltiplos grupos são reavaliados SWS PduR p. 69. Essas regras não fazem parte dos requisitos do R20-11 aqui apresentados.

Diagrama de sequência: o BswM desativa um grupo de caminhos de roteamento; chamadas de envio em caminhos afetados falham até que o grupo seja ativado novamente. Fontes: [SWS_PduR_00617], [SWS_PduR_00717], [SWS_PduR_00715], Mode-Management-Guide p. 50

Comportamento em caso de erro

Se PduRDevErrorDetect estiver ativo, o PduR reporta erros de desenvolvimento ao DET [SWS_PduR_00100], SWS PduR p. 72:

  • PDUR_E_INIT_FAILED em caso de ponteiro de configuração inválido [SWS_PduR_00100].
  • PDUR_E_UNINIT em chamadas antes da inicialização, exceto PduR_Init e PduR_GetVersionInfo [SWS_PduR_00119], e em PduR_Init fora de PDUR_UNINIT [SWS_PduR_00100].
  • PDUR_E_PDU_ID_INVALID em caso de ID de PDU inválido [SWS_PduR_00221].
  • PDUR_E_PARAM_POINTER em caso de ponteiros nulos [SWS_PduR_00100].
  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID em caso de ID de grupo desconhecido [SWS_PduR_00648], [SWS_PduR_00649]. A própria função de comutação retorna sem efeito nesse caso [SWS_PduR_00647], [SWS_PduR_00716].

O PduR não reporta erros de produção SWS PduR p. 60.

Se instâncias de I-PDU forem perdidas, o PduR reportará o erro de tempo de execução PDUR_E_PDU_INSTANCES_LOST. Esse erro foi introduzido com o AUTOSAR 4.3.1 SWS PduR p. 3; ele é reportado via Det_ReportRuntimeError [SWS_PduR_91001]. Duas situações o disparam:

  • A FIFO está cheia: o PduR a esvazia e trata a nova I-PDU como em uma FIFO vazia [SWS_PduR_00255], [SWS_PduR_00669], [SWS_PduR_00670].
  • <DstLo>_Transmit retorna E_NOT_OK: o PduR descarta a instância e envia a seguinte [SWS_PduR_00788], [SWS_PduR_00807].

Interpretação: a desativação de um grupo deve ser considerada como “parada” no sentido de [SWS_PduR_00663]; as FIFOs associadas seriam então esvaziadas também.

O PduR não repete transmissões de gateway que falharam [SWS_PduR_00256]. Em transmissões locais com um destino, o módulo superior recebe o valor de retorno do destino [SWS_PduR_00626], [SWS_PduR_00700]. No caso de múltiplos destinos, [SWS_PduR_00701] exige que todos os destinos retornem E_OK; presumivelmente, isso diz respeito ao caminho de envio de TP, enquanto para o multicast de interface, de acordo com o [SWS_PduR_00218], um único sucesso é suficiente.

Para a recepção TP e os gateways TP, aplica-se o seguinte:

  • O PduR apenas repassa localmente indicações de recepção TP com falha [SWS_PduR_00207]; no gateway, elas encerram o processamento [SWS_PduR_00689].
  • Se um gateway on-the-fly não puder armazenar os dados, o PduR retornará BUFREQ_E_NOT_OK [SWS_PduR_00687]. Se faltar totalmente um buffer, ele retornará BUFREQ_E_OVFL [SWS_PduR_00799].
  • Se um destino falhar, os demais continuam em execução [SWS_PduR_00803], [SWS_PduR_00806]. Apenas quando todos os destinos TP falham é que o PduR encerra o lado de recepção [SWS_PduR_00804].
  • Em caso de erros, o PduR aborta receptores locais de TP no gateway ou os indica com E_NOT_OK [SWS_PduR_00790], [SWS_PduR_00791], [SWS_PduR_00792].

usar

A função síncrona PduR_EnableRouting serve para a ativação de um grupo de caminhos de encaminhamento ([SWS_PduR_00615]). Através do parâmetro de entrada id do tipo PduR_RoutingPathGroupIdType é endereçado o respetivo grupo de caminhos de encaminhamento previamente definido na configuração do router de PDU ([SWS_PduR_00615]). O serviço não devolve qualquer valor de retorno (void) e é declarado com o ID de serviço 0xf3 através do ficheiro de cabeçalho PduR.h ([SWS_PduR_00615]).

Tratamento de erros

No que diz respeito a possíveis estados de erro, estão especificados para PduR_EnableRouting os seguintes códigos de erro ([SWS_PduR_00100]):

  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (0x08): é detetado se for transmitida à função uma tabela de encaminhamento ou ID de grupo de caminhos de encaminhamento inválido ([SWS_PduR_00100]).
  • PDUR_E_UNINIT (0x01): ocorre se este serviço da API for chamado antes da inicialização bem-sucedida do módulo do router de PDU ([SWS_PduR_00100]).

Simultaneidade e restrições

A função está especificada como reentrante ([SWS_PduR_00615]).

função PduR_DisableRouting [SWS_PduR_00617] 📄 PDF

void PduR_DisableRouting (PduR_RoutingPathGroupIdType id, boolean initialize);

desativa um encaminhamento caminho grupo.

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: e2ac2ae9ce95 Procedência

usar

A função síncrona PduR_DisableRouting ([SWS_PduR_00617]) serve para a desativação de um grupo de caminhos de encaminhamento (Routing Path Group) no router de PDU. Não possui qualquer valor de retorno (void) e é disponibilizada através do ficheiro de cabeçalho PduR.h.

Ao ser chamada, a função espera dois parâmetros de entrada:

  • id: identifica o grupo de caminhos de encaminhamento a desativar, conforme definido na configuração do router de PDU.
  • initialize: controla o tratamento de buffers individuais (Single Buffers). Na transmissão de true, estes buffers são inicializados com o seu valor predefinido; com false, o conteúdo atual do buffer é mantido.

Simultaneidade e restrições

Segundo [SWS_PduR_00617], a função está especificada como reentrante. Para uma chamada válida, o módulo PduR tem de ter sido inicializado previamente.

Tratamento de erros e interação

No que concerne ao tratamento de erros, existem referências diretas a [SWS_PduR_00100]:

  • Se a função for chamada sem que o módulo esteja inicializado, isto diz respeito ao erro PDUR_E_UNINIT (valor do erro 0x01).
  • Se for transmitida a PduR_DisableRouting uma tabela de encaminhamento ou um ID de grupo inválido, está previsto o código de erro PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (valor do erro 0x08).

O tipo de enumeração PduR_StateType descreve os estados do PDU Router ([SWS_PduR_00742]). Está disponível através do cabeçalho PduR.h e define o ciclo de vida fundamental do módulo.

De acordo com [SWS_PduR_00324], o módulo PDU Router é composto exatamente por dois estados, que são mapeados pelos valores do tipo:

  • PDUR_UNINIT: O PDU Router não está inicializado ([SWS_PduR_00742], [SWS_PduR_00324]).
  • PDUR_ONLINE: O PDU Router foi inicializado com sucesso ([SWS_PduR_00742], [SWS_PduR_00324]).

Na interação, este tipo serve como base de estados para o PDU Router, sendo que a transição para PDUR_ONLINE indica a conclusão com sucesso da inicialização do módulo, enquanto PDUR_UNINIT representa o estado antes ou depois de sair do funcionamento operacional.
