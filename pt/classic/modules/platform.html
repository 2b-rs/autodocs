Papel do Platform_Types.h: base comum de tipos do software básico Classic

O módulo “platform” consiste no arquivo de cabeçalho Platform_Types.h. Por meio dele, todos os tipos básicos padronizados e símbolos de plataforma estão disponíveis, tais como uint8 [SWS_Platform_00013], boolean [SWS_Platform_00026] e CPU_TYPE [SWS_Platform_00064]. O módulo não contém funções. Ele especifica quais intervalos de valores, larguras de bits e codificações o código pode pressupor em uma plataforma. O motivo disso é o requisito de que todos os módulos de software básico usem apenas tipos de dados AUTOSAR. Tipos C nativos como char, int ou long são proibidos porque seu tamanho, sinal e precisão dependem da plataforma (RS_BSWGeneral p. 65).

Geralmente, os módulos não incluem os tipos diretamente. No exemplo da especificação de requisitos, Eep.h inclui o arquivo Std_Types.h, e este inclui Platform_Types.h automaticamente (RS_BSWGeneral p. 65). Bibliotecas como a Bfx associam expressamente suas siglas u8, u16, s32 e boolean aos tipos de plataforma (SWS_BFXLibrary p. 8). O arquivo em si não pode ser modificado: qualquer extensão anula a conformidade com o AUTOSAR [SWS_Platform_00002].

Diagrama de contexto: Platform_Types.h é a base comum de tipos. Os módulos BSW a acessam por meio de Std_Types.h; bibliotecas, interfaces de serviço e blueprints de modelo referem-se diretamente a ela. Fontes: RS_BSWGeneral p. 65, SWS_BFXLibrary p. 8, StandardizationTemplate p. 77, [SWS_Platform_00002]

Tipos inteiros: largura exata ou intervalo mínimo otimizado para a plataforma

Os tipos inteiros padrão têm larguras de bits e intervalos de valores fixos. uint8, uint16, uint32 e uint64 são sem sinal com 8, 16, 32 e 64 bits ([SWS_Platform_00013], [SWS_Platform_00014], [SWS_Platform_00015], [SWS_Platform_00066]). sint8 a sint64 são as contrapartes com sinal ([SWS_Platform_00016], [SWS_Platform_00017], [SWS_Platform_00018], [SWS_Platform_00067]). Os seus intervalos, como -128..+127 para sint8, decorrem do facto de o AUTOSAR suportar apenas aritmética de complemento para dois para compilador e sistema de destino [SWS_Platform_00061].

Por outro lado, os tipos otimizados garantem apenas um intervalo mínimo. uint8_least, uint16_least e uint32_least têm pelo menos 8, 16 e 32 bits, respetivamente, e são derivados de uint ([SWS_Platform_00020], [SWS_Platform_00021], [SWS_Platform_00022]). sint8_least a sint32_least são as variantes com sinal e derivadas de sint ([SWS_Platform_00023], [SWS_Platform_00024], [SWS_Platform_00025]). A especificação menciona dois usos típicos: contadores de ciclo com no máximo 124 iterações e argumentos switch com 17 estados. Em ambos os casos, deve ser selecionado uint8_least (SWS_PlatformTypes p. 17).

No payload constam declarações como typedef unsigned int uint8_least; ou typedef unsigned long uint32;. Interpretação: são mapeamentos para um compilador específico. Normativa é apenas a largura exigida ou a largura mínima ([SWS_Platform_00015], [SWS_Platform_00020]).

Tipos de ponto flutuante e de ponteiro para valores e buffers de dados

Para valores de ponto flutuante, aplicam-se os formatos segundo a IEEE 754-2008:

  • float32 segue o formato binary32, intervalo ±3.4028235e+38 [SWS_Platform_00041].
  • float64 segue o formato binary64, intervalo ±1.7976931348623157e+308 [SWS_Platform_00042].

Para buffers de dados sem tipo fixo, existem dois tipos de ponteiro com direção definida:

  • VoidPtr (void*) destina-se a buffers que retornam dados ao chamador [SWS_Platform_91001] (SWS_PlatformTypes p. 27).
  • ConstVoidPtr (const void*) destina-se a buffers que são passados ao chamado [SWS_Platform_91002] (SWS_PlatformTypes p. 28).

Diagrama de atividades: como é selecionado o tipo de plataforma adequado, desde boolean passando por ponteiros de buffer e ponto flutuante até inteiros otimizados ou de largura exata. Fontes: [SWS_Platform_00026], [SWS_Platform_91001], [SWS_Platform_91002], [SWS_Platform_00041], [SWS_Platform_00042], SWS_PlatformTypes p. 17

boolean, TRUE e FALSE: representação e expressões permitidas

No R20-11, boolean é implementado como um tipo inteiro sem sinal, e com o menor comprimento de bits suportado nativamente pela plataforma, geralmente 8 bits [SWS_Platform_00027]. A declaração armazenada é typedef unsigned char boolean; [SWS_Platform_00026].

Divergência em versões posteriores: a versão para R24-11/R25-11 exige o tipo C99 _Bool e já não define o tamanho do objeto (SWS_PlatformTypes p. 18). Para o R20-11, aplica-se o requisito acima.

Além disso, boolean deve ser mapeado para um tipo para o qual ponteiros possam apontar. Os tipos de bit eficientes de determinados hardwares são, portanto, excluídos [SWS_Platform_00060]. Esse é um pré-requisito para interfaces como CanNm_CheckRemoteSleepIndication, que retornam um resultado através de boolean* (SWS_CANNetworkManagement p. 68).

TRUE (1) e FALSE (0) são definidos apenas se ainda não existirem (#ifndef TRUE) [SWS_Platform_00056]. Só podem ser utilizados juntamente com boolean [SWS_Platform_00055]. Para a manipulação de variáveis boolean, aplicam-se estas regras [SWS_Platform_00034]:

  • Atribuições são permitidas apenas com TRUE, FALSE, comparações ou expressões lógicas (&&, ||, !).
  • Operadores aritméticos e bit a bit como +, ++, <<, ~ ou & são proibidos.
  • As comparações estão limitadas a == TRUE, == FALSE, != TRUE, != FALSE, if (var) e if (!var) (SWS_PlatformTypes p. 18).

Diagrama de atividades: verificação se uma atribuição ou comparação com uma variável boolean é admissível. Fontes: [SWS_Platform_00034], [SWS_Platform_00055], SWS_PlatformTypes p. 18

Símbolos de plataforma CPU_TYPE, CPU_BIT_ORDER e CPU_BYTE_ORDER

Platform_Types.h especifica três propriedades da CPU para cada plataforma, cada uma como #define:

  • A largura dos registradores através de CPU_TYPE [SWS_Platform_00044]. São permitidos CPU_TYPE_8, CPU_TYPE_16, CPU_TYPE_32 e CPU_TYPE_64 ([SWS_Platform_00045], [SWS_Platform_00064]).
  • A ordem dos bits ao nível do registrador através de CPU_BIT_ORDER ([SWS_Platform_00043], [SWS_Platform_00038]).
  • A ordem dos bytes na memória através de CPU_BYTE_ORDER ([SWS_Platform_00046], [SWS_Platform_00039]).

O mapeamento para a endianness é inequívoco. A ordem de bits big-endian resulta em MSB_FIRST, a ordem de bits little-endian resulta em LSB_FIRST ([SWS_Platform_00048], [SWS_Platform_00049]). A ordem de bytes big-endian resulta em HIGH_BYTE_FIRST, a ordem de bytes little-endian resulta em LOW_BYTE_FIRST ([SWS_Platform_00050], [SWS_Platform_00051]).

A especificação alerta contra a confusão entre numeração de bits e significância. Em arquiteturas Motorola com ordem de bits big-endian, o Bit0 designa o bit mais significativo; em todas as outras, o menos significativo. No acumulador, por outro lado, o MSB fica sempre na extrema esquerda (SWS_PlatformTypes p. 15).

Diagrama de atividades: procedimento de como os três símbolos de plataforma são definidos para uma plataforma de destino sem expandir o ficheiro. Fontes: [SWS_Platform_00045], [SWS_Platform_00048], [SWS_Platform_00049], [SWS_Platform_00050], [SWS_Platform_00051], [SWS_Platform_00002]

Relativamente à ordem dos bytes, a especificação apresenta um valor de 16 bits. O seu byte mais significativo chama-se Byte1 e o menos significativo Byte0. Com HIGH_BYTE_FIRST, o Byte1 localiza-se no endereço n e o Byte0 em n+1; com LOW_BYTE_FIRST, é o inverso (SWS_PlatformTypes p. 16). Esta nomenclatura não é unívoca e pode divergir na documentação dos fabricantes (SWS_PlatformTypes p. 16). Na prática, a ordem dos bytes é importante onde os dados são convertidos entre a representação do barramento e do processador. O AUTOSAR COM deve, por exemplo, suportar a conversão de endianness para uint16 a float64 (comprovativo do R25-11: RS_COM p. 14).

Diagrama de atividades: armazenamento em memória de um valor uint16 dependendo de CPU_BYTE_ORDER, baseado na Figure 7.2/7.3 da especificação. Fontes: SWS_PlatformTypes p. 16, [SWS_Platform_00039]

Tipos de plataforma em interfaces de serviço e modelos

Outras especificações baseiam as suas assinaturas nestes tipos. Dois exemplos do R24-11/R25-11 ilustram a regra de direção dos ponteiros de buffer ([SWS_Platform_91001], [SWS_Platform_91002]):

  • O Key Manager passa em KeyM_ServiceCertificateByCertId os dados de solicitação como ConstVoidPtr com um comprimento do tipo uint32. Ele recebe os resultados através de um buffer VoidPtr, cujo tamanho disponível é indicado por ResponseDataLength (INOUT) (SWS_KeyManager p. 111).
  • A operação CSM RandomSeed passa o seed como ConstVoidPtr (SWS_CryptoServiceManager p. 124).

Diagrama de sequência: o chamador disponibiliza os dados de solicitação como apenas de leitura via ConstVoidPtr e recebe os dados de volta através de um buffer VoidPtr. O valor de retorno informa se o serviço aceitou a solicitação. Fontes: SWS_KeyManager p. 111, SWS_KeyManager p. 97, [SWS_Platform_91001], [SWS_Platform_91002]

Os tipos também estão firmemente consolidados no modelo. A partir do blueprint /AUTOSAR/Platform/ImplementationDatatypes_Blueprint/uint8, é derivado o elemento /AUTOSAR_Platform/ImplementationDatatypes/uint8. Desta forma, os fornecedores de software encontram-no através de um caminho previsível (StandardizationTemplate p. 77). Os Record Layouts referenciam tipos base como /AUTOSAR/Platform/BaseTypes_Blueprint/sint16 (GeneralBlueprintsSupplement p. 47). Bibliotecas como Crc utilizam uint8, uint32 e boolean diretamente nas suas APIs (SWS_CRCLibrary p. 41).

Comportamento em caso de erro

Platform_Types.h disponibiliza apenas tipos e símbolos que estão disponíveis através deste ficheiro ([SWS_Platform_00013], [SWS_Platform_00038]). Portanto, não deve existir um comportamento de erro em tempo de execução com valores de retorno ou mensagens de erro. Em vez disso, os erros surgem durante a integração e utilização:

  • Ficheiro estendido ou complementado: qualquer extensão revoga a conformidade com o AUTOSAR [SWS_Platform_00002].
  • Definições duplicadas: se o compilador já fornecer os símbolos, redefinições devem ser evitadas através de uma verificação condicional ([SWS_Platform_00054], [SWS_Platform_00056]).
  • Símbolos de plataforma incorretos: um CPU_BYTE_ORDER ou CPU_BIT_ORDER que não corresponda ao hardware viola de [SWS_Platform_00048] a [SWS_Platform_00051]. Interpretação: o código que ramifica com base nestes símbolos iria então montar incorretamente valores de múltiplos bytes (cf. SWS_PlatformTypes p. 16).
  • Tipo de bit para boolean: sem capacidade de ponteiro, não é possível passar parâmetros através de ponteiros [SWS_Platform_00060].
  • Expressões inadmissíveis como var++ ou var = a & b violam [SWS_Platform_00034].
  • O AUTOSAR não suporta outras representações de números negativos além do complemento para dois [SWS_Platform_00061].
