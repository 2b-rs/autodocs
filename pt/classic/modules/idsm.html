Papel e limite do sistema: do evento de sensor ao Security Event qualificado

O Intrusion Detection System Manager (IdsM) é o módulo BSW da Classic Platform que recebe On-Board-Security-Events (SEv) por meio de uma interface padronizada. Ele os filtra de acordo com regras configuráveis em eventos qualificados (QSEv) e, em seguida, os armazena ou transmite SWS IdsM p. 7. Os sensores que reportam são módulos BSW, CDDs proprietários e SW-Cs. Os destinos são o IDS Reporter (IdsR), alcançado através do PduR, bem como DEM/Sem para o armazenamento local SWS IdsM p. 16 [SWS_IdsM_01202] [SWS_IdsM_01601].

O IdsM expressamente não avalia se um sistema está de fato comprometido. Ele não conhece o significado dos dados de contexto; a detecção e a reação ficam fora do módulo, por exemplo em um SOC [SWS_IdsM_CONSTR_00001]. Além disso, a especificação aceita que SEvs sejam descartados dependendo da frequência de notificações ou da carga do sistema SWS IdsM p. 11.

Outros módulos vizinhos e suas tarefas:

  • DET: erros de desenvolvimento
  • DCM: acesso de diagnóstico ao Reporting Mode
  • NvM: persistência do Reporting Mode
  • BswM: fornecedor do Block State
  • StbM ou uma SW-C: fonte de carimbo de data/hora
  • CSM: assinaturas
  • BSW-Scheduler: chamada cíclica

Evidências: SWS IdsM p. 13. Quais cabeçalhos são incluídos depende das chaves de configuração correspondentes, por exemplo, Det.h em IdsMDevErrorDetect e PduR.h em IdsMSinkIdsR [SWS_IdsM_00101] [SWS_IdsM_00105].

Diagrama de contexto: o IdsM situa-se entre os sensores (BSW/CDD diretamente, SW-C via RTE) e os destinos IdsR (via PduR) ou DEM/Sem. Os módulos de controle e suporte são BswM, DCM, NvM, StbM, CSM e DET. Fontes: SWS IdsM p. 20, SWS IdsM p. 13, [SWS_IdsM_91027], [SWS_IdsM_91028].

Ciclo de vida: inicialização e processamento cíclico

IdsM_Init inicializa todas as variáveis internas e define o módulo para o estado "inicializado" [SWS_IdsM_00202] [SWS_IdsM_91001]. Uma nova chamada no estado inicializado não reinicializa. Com IdsMDevErrorDetect ativo, ela reporta, em vez disso, IDSM_E_ALREADY_INITIALIZED [SWS_IdsM_00204]. No estado não inicializado, qualquer API, exceto IdsM_Init e IdsM_GetVersionInfo, resulta em um erro de DET [SWS_IdsM_00203].

O trabalho propriamente dito é executado de forma assíncrona. IdsM_MainFunction é chamada periodicamente e processa os eventos que foram enfileirados durante as chamadas de API [SWS_IdsM_91000] SWS IdsM p. 19. O período IdsMMainFunctionPeriod é simultaneamente a base de tempo de todos os filtros de intervalo. Seus intervalos devem ser múltiplos desse período e começam com a primeira chamada da MainFunction [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01064] [SWS_IdsM_01065].

Diagrama de estados: somente IdsM_Init torna o módulo utilizável. Chamadas incorretas em ambos os estados são reportadas ao DET, sem alterar o estado. Fontes: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], [SWS_IdsM_91000].

Notificação de Security Events: identidade, variantes de API e armazenamento em buffer

Cada instância de SEv é descrita por quatro informações: IdsMExternalEventId, IdsMSensorInstanceId, uma IdsMInternalEventId calculada internamente e o nome do evento [SWS_IdsM_00600] [SWS_IdsM_00601]. Para a utilização, aplicam-se as seguintes regras (SWS IdsM p. 21):

  • Os sensores utilizam exclusivamente a constante simbólica do contêiner IdsMEvent, nunca o valor numérico interno [SWS_IdsM_00602] [SWS_IdsM_00607].
  • O ID externo 0xFFFF é inválido [SWS_IdsM_00604].
  • Se houver apenas uma instância de módulo, a instância do sensor é 0 por padrão [SWS_IdsM_00608].

Para a notificação, estão disponíveis seis serviços síncronos e não reentrantes. Eles diferem quanto aos dados adicionais fornecidos. As variantes com contador e carimbo de data/hora destinam-se a Smart Sensors (SW-C ou CDD) que determinam esses valores por conta própria SWS IdsM p. 19. Se houver apenas um carimbo de data/hora sem contador próprio, passa-se count = 1 [SWS_IdsM_00405].

Os dados de contexto são passados como ponteiro para uma matriz de bytes e podem ter até 1500 bytes de comprimento [SWS_IdsM_00501] [SWS_IdsM_00502]. Para sensores SW-C, aplicam-se dois parâmetros adicionais SWS IdsM p. 37:

  • IdsMEventMaxContextDataSize limita a quantidade de dados de contexto [SWS_IdsM_01300].
  • IdsMAdditionalParameterOption (None, Count, CountTimestamp) determina quais parâmetros a Service-Port-Interface oferece [SWS_IdsM_01301] [SWS_IdsM_01303].

Ao receber, o IdsM armazena o SEv em um Event Buffer [SWS_IdsM_00702]. Os dados de contexto vão para um Context Data Buffer de tamanho igual ou imediatamente maior, que é vinculado ao Event Buffer [SWS_IdsM_00705] [SWS_IdsM_00706]. Sem dados de contexto, nenhum buffer de contexto é alocado [SWS_IdsM_00709]. O número e os tamanhos dos buffers são configuráveis [SWS_IdsM_00701] [SWS_IdsM_00704]. Para o número de Event Buffers, a especificação recomenda: número de instâncias de filtro de agregação mais o limite superior de eventos processados em paralelo SWS IdsM p. 22.

Diagrama de sequência: a notificação no contexto do sensor apenas armazena o SEv em buffer. O carimbo de data/hora, a filtragem e a qualificação ocorrem somente na chamada cíclica de IdsM_MainFunction (variante com StbM como fonte de tempo). Fontes: SWS IdsM p. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01104].

Diagrama de atividades: a ausência de um Event Buffer dispara um SEv interno. A ausência de um Context Data Buffer faz com que o evento seja processado adiante sem dados de contexto. Fontes: SWS IdsM p. 27, [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708].

Qualificação: Reporting Mode e cadeia de filtros

Cada SEv possui um filtro de Reporting Mode obrigatório. Ele não faz parte da cadeia de filtros, mas está associado diretamente ao evento; seu valor padrão provém de IdsMReportingModeFilter [SWS_IdsM_01010] [SWS_IdsM_01011] [SWS_IdsM_01012]. Os valores de IdsM_Filters_ReportingModeType significam [SWS_IdsM_91013] SWS IdsM p. 91:

  • IDSM_REPORTING_MODE_OFF: o evento é descartado.
  • IDSM_REPORTING_MODE_BRIEF / IDSM_REPORTING_MODE_DETAILED: notificação sem ou com dados de contexto.
  • …_BYPASSING_FILTERS: notificação contornando a cadeia de filtros.

Somente após o Reporting Mode é avaliada a cadeia de filtros atribuída ao SEv [SWS_IdsM_01001] [SWS_IdsM_01002]. Os filtros ativados são executados em uma ordem fixa: Block State, Forward Every Nth, Event Aggregation, Event Threshold [SWS_IdsM_01004]. Se um filtro descartar o SEv, qualquer avaliação posterior é cancelada [SWS_IdsM_01005] SWS IdsM p. 25. Uma cadeia de filtros precisa de pelo menos um filtro [SWS_IdsM_CONSTR_00002]. Os filtros individuais operam da seguinte forma:

  • Block State: o BswM reporta o estado atual via IdsM_BswM_StateChanged. Se esse estado pertencer aos IdsMBlockState referenciados, o SEv é descartado [SWS_IdsM_01022] [SWS_IdsM_01023] SWS IdsM p. 28.
  • Forward Every Nth: o primeiro e, em seguida, cada n-ésimo SEv são encaminhados inalterados [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  • Aggregation: os SEvs são retidos durante IdsMEventAggregationTimeInterval. No final do intervalo, um SEv prossegue com a soma de todos os contadores; os dados de contexto e o carimbo de data/hora provêm opcionalmente do primeiro ou do último SEv [SWS_IdsM_01043] [SWS_IdsM_01046] [SWS_IdsM_01047] [SWS_IdsM_01048] [SWS_IdsM_01049] SWS IdsM p. 40.
  • Threshold: enquanto a soma dos contadores no intervalo estiver abaixo de IdsMEventThresholdNumber, ocorre o descarte; a partir do momento em que o valor limite é atingido, o encaminhamento é feito. Com o fim do intervalo, o contador é reiniciado [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063] SWS IdsM p. 41.

Diagrama de atividades: primeiro, o Reporting Mode decide sobre descartar, contornar ou filtrar. Em seguida, o SEv passa pelos filtros ativados em ordem fixa, até ser descartado ou se tornar um QSEv. Fontes: SWS IdsM p. 35, SWS IdsM p. 24, [SWS_IdsM_01004], [SWS_IdsM_01005], [SWS_IdsM_91013].

Enriquecimento e encaminhamento de eventos qualificados

Os QSEvs possuem uma estrutura fixa de acordo com o protocolo IDS, independentemente do destino [SWS_IdsM_01200]. Quais destinos são utilizados é definido pela configuração para cada IdsMEvent [SWS_IdsM_01201] SWS IdsM p. 35. Com IdsMSinkIdsR, o QSEv é enviado via PduR_IdsMTransmit como IDS Message [SWS_IdsM_01203] [SWS_IdsM_01498]. Antes do envio para o IdsR, entram em ação limitações em nível de instância: a limitação de taxa restringe o número de QSEvs por intervalo, e a limitação de tráfego restringe os bytes por intervalo [SWS_IdsM_01070] [SWS_IdsM_01081] [SWS_IdsM_01091] SWS IdsM p. 32.

O caminho de transmissão depende do tamanho SWS IdsM p. 38:

  • Se a IDS Message, juntamente com a assinatura, couber em uma PDU de barramento, utiliza-se uma IF-PDU [SWS_IdsM_01400]; a confirmação chega via IdsM_TxConfirmation [SWS_IdsM_01500].
  • Caso contrário, utilizam-se TP-PDUs [SWS_IdsM_01401]. O PduR busca os dados em segmentos via IdsM_CopyTxData [SWS_IdsM_01501] e confirma via IdsM_TpTxConfirmation [SWS_IdsM_01502].
  • Antes da confirmação, o IdsM não chama PduR_IdsMTransmit novamente [SWS_IdsM_01499].

Diagrama de sequência: após a limitação, um QSEv é transmitido como IF- ou TP-PDU, dependendo do tamanho. A próxima transmissão só pode começar após a confirmação. Fontes: [SWS_IdsM_01070], [SWS_IdsM_01400], [SWS_IdsM_01401], [SWS_IdsM_01499], [SWS_IdsM_01501], [SWS_IdsM_01502].

Opcionalmente, o IdsM assina cada QSEv. Isso é ativado globalmente por meio de um trabalho CSM referenciado via IdsMCsmJobReference. A assinatura é gerada via Csm_SignatureGenerate; em trabalhos assíncronos, o CSM reporta o resultado via IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01208] SWS IdsM p. 36. O destino DEM/Sem está identificado como DRAFT no R20-11; ele armazena a IDS Message completa [SWS_IdsM_01600] [SWS_IdsM_01602].

Os carimbos de data/hora são habilitados globalmente via IdsMTimestampOption [SWS_IdsM_01100] [SWS_IdsM_01103] SWS IdsM p. 33. Aplicam-se as seguintes regras SWS IdsM p. 34:

  • Se o sensor não fornecer um carimbo de data/hora, o próprio IdsM o obtém: em "AUTOSAR" via StbM_GetCurrentTime, em "Custom" via a interface IdsM_CustomTimestamp de uma SW-C [SWS_IdsM_01104] [SWS_IdsM_01107] [SWS_IdsM_01109] [SWS_IdsM_01111].
  • Os carimbos de data/hora informados pelo sensor têm prioridade e são truncados para os 62 bits menos significativos [SWS_IdsM_01108] [SWS_IdsM_01110].
  • Em "None", os carimbos de data/hora passados também são ignorados [SWS_IdsM_01106].

Um ponto em aberto da especificação: [SWS_IdsM_01112] exige o bit de opção de carimbo de data/hora 0 quando as APIs de carimbo de data/hora são usadas sem parâmetro de carimbo de data/hora. O texto deixa em aberto como isso se relaciona com [SWS_IdsM_01101].

Diagrama de atividades: a fonte do carimbo de data/hora é determinada a partir de IdsMTimestampOption e do parâmetro informado. Fontes: SWS IdsM p. 87, [SWS_IdsM_01104], [SWS_IdsM_01106], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110].

Reporting Mode em tempo de execução: diagnóstico e persistência de NvM

Se IdsMDiagnosticSupport estiver ativo, o Reporting Mode pode ser lido e alterado por meio do DCM [SWS_IdsM_01800] [SWS_IdsM_01900] [SWS_IdsM_02000] SWS IdsM p. 40:

  • A leitura ocorre em duas etapas: IdsM_Dcm_GetReportingMode_Start inicia a rotina, IdsM_Dcm_GetReportingMode_RequestResults fornece o resultado por meio de um ponteiro [SWS_IdsM_02001] [SWS_IdsM_02002].
  • A alteração ocorre via IdsM_Dcm_SetReportingMode_Start. Um modo inválido ou um Event-ID inválido levam a E_NOT_OK com DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01901] [SWS_IdsM_01902] [SWS_IdsM_01903].

Após uma alteração bem-sucedida, o IdsM aciona NvM_WriteBlock [SWS_IdsM_01701]. Se a persistência falhar, ele redefine o modo para o valor anterior e responde com DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905]. Na inicialização, ele lê o modo persistido. Para isso, o bloco NvM deve estar contido em NvM_ReadAll; caso faltem valores de NvM, aplica-se a configuração [SWS_IdsM_01703] [SWS_IdsM_01704] [SWS_IdsM_01705] SWS IdsM p. 39.

Diagrama de sequência: a leitura ocorre em duas etapas via Start e RequestResults. Na alteração, primeiro é feita a verificação, depois a persistência e, em caso de erro, o rollback. Fontes: [SWS_IdsM_02001], [SWS_IdsM_02002], [SWS_IdsM_01902], [SWS_IdsM_01903], [SWS_IdsM_01701], [SWS_IdsM_01904], [SWS_IdsM_01905].

Comportamento em caso de erro

Com IdsMDevErrorDetect ativo, o IdsM reporta erros de desenvolvimento ao DET. Os códigos de erro são IDSM_E_PARAM_INVALID (0x0A), IDSM_E_PARAM_POINTER (0x0B), IDSM_E_PARAM_LENGTH (0x0C), IDSM_E_UNINIT (0x0D) e IDSM_E_ALREADY_INITIALIZED (0x0E) [SWS_IdsM_02003]. Atenção: [SWS_IdsM_00203] menciona IDSM_E_PARAM_UNINIT para chamadas no estado não inicializado. A tabela de erros não contém esse código; em seu lugar consta IDSM_E_UNINIT. As verificações de parâmetros em detalhes:

  • securityEventId desconhecido nas APIs de notificação, bem como count = 0 nas variantes de contador, resultam em IDSM_E_PARAM_INVALID [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106] SWS IdsM p. 42.
  • Um contextDataSize maior do que o maior IdsMContextDataBufferSize resulta em IDSM_E_PARAM_LENGTH [SWS_IdsM_02107] [SWS_IdsM_02108] [SWS_IdsM_02109] SWS IdsM p. 43.
  • Um NULL_PTR inadmissível resulta em IDSM_E_PARAM_POINTER SWS IdsM p. 42.

Gargalos em tempo de execução são reportados pelo IdsM por meio de SEvs internos próprios, caso estejam configurados. Eles possuem buffers próprios e não são filtrados por filtros em nível de instância [SWS_IdsM_91015] [SWS_IdsM_00802] [SWS_IdsM_00803] SWS IdsM p. 24. Existem três SEvs internos:

  • nenhum Event Buffer disponível [SWS_IdsM_00703]
  • nenhum Context Data Buffer disponível; o SEv é então processado adiante sem dados de contexto [SWS_IdsM_00707] [SWS_IdsM_00708]
  • limitação de tráfego excedida [SWS_IdsM_01094]

Se a persistência falhar durante uma alteração de diagnóstico, aplica-se o rollback descrito acima [SWS_IdsM_01905].

O tipo IdsM_Filters_ReportingModeType ([SWS_IdsM_91013]) define os modos de relatório utilizados pelo filtro de modo de relatório (reporting mode filter) do módulo IdsM. O tipo base é derivado de uint8 e é disponibilizado por meio do cabeçalho IdsM_Types.h.

Faixa de valores e semântica

O tipo define como ou se um evento de segurança detectado é reportado adiante:

  • IDSM_REPORTING_MODE_OFF (0x00): O evento não é reportado.
  • IDSM_REPORTING_MODE_BRIEF (0x01): O evento é reportado de forma compacta, sem dados de contexto.
  • IDSM_REPORTING_MODE_DETAILED (0x02): O evento é reportado detalhadamente, incluindo dados de contexto.
  • IDSM_REPORTING_MODE_BRIEF_BYPASSING_FILTERS (0x03): O evento é reportado sem filtragem e sem dados de contexto, contornando os filtros.
  • IDSM_REPORTING_MODE_DETAILED_BYPASSING_FILTERS (0x04): O evento é reportado sem filtragem juntamente com dados de contexto, contornando os filtros.
  • IDSM_REPORTING_MODE_INVALID (0xFF): Caracteriza um modo de relatório inválido.

Uso e restrições

Como enumeração ou tipo de configuração, IdsM_Filters_ReportingModeType controla a lógica de filtragem e encaminhamento de eventos de segurança dentro da cadeia de filtros do IdsM. Por se tratar de uma definição puramente de tipo, não existem parâmetros diretos, valores de retorno ou códigos de erro específicos de DET/DEM.
