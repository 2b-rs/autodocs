Gerencia blocos de dados não voláteis e sincroniza-os assincronamente entre a RAM e a memória NV.

O NVRAM Manager (NvM) é o único acesso à memória não volátil. Ele copia blocos de NVRAM implicitamente entre a RAM e a memória NV [SWS_NvM_00038]. Na inicialização, o NvM_ReadAll disparado pelo BswM preenche os blocos de RAM; no shutdown, o NvM_WriteAll salva os blocos modificados. Requisições individuais como NvM_WriteBlock são enfileiradas de forma assíncrona, processadas por prioridade e confirmadas via status ou callback [SWS_NvM_00185]. O NvM intercepta erros de leitura por meio de repetições, cópias redundantes e dados padrão; ainda assim, os usuários devem verificar o status do bloco por conta própria.

O NVRAM Manager (NvM) é o único acesso à memória não volátil [SWS_NvM_00384]. Ele copia blocos implicitamente entre a NVRAM e a RAM; a aplicação trabalha diretamente com os dados da RAM [SWS_NvM_00038]. Para os níveis inferiores, ele utiliza a Memory Abstraction Interface com Fee ou Ea [SWS_NvM_00051]. Ele reporta estados ao BswM, e erros ao DEM e ao DET [SWS_NvM_00745] [SWS_NvM_00592].

Diagrama de contexto: integração do NvM entre usuários, BswM, MemIf/Fee/Ea, bem como DEM e DET. Fontes: [SWS_NvM_00384] [SWS_NvM_00465] [SWS_NvM_00746]

Cada bloco de NVRAM consiste em NV block, RAM block e Administrative Block, opcionalmente complementado por um ROM block com dados padrão [SWS_NvM_00138]. Existem os tipos Native, Redundant e Dataset; eles diferem no número de blocos NV e ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559]. O NvM sincroniza o bloco de RAM diretamente de forma implícita ou explicitamente por meio de um RAM mirror com callbacks [SWS_NvM_00511].

O ciclo de vida ocorre em três etapas:

  • O BswM chama NvM_Init exclusivamente [SWS_NvM_00693].
  • O NvM_ReadAll verifica primeiro o ID de configuração e depois preenche os blocos de RAM [SWS_NvM_00073] [SWS_NvM_00718].
  • No shutdown, o NvM_WriteAll salva os blocos modificados [SWS_NvM_00092]. O NvM_CancelWriteAll cancela de forma não destrutiva [SWS_NvM_00238].

Requisições individuais como NvM_WriteBlock são enfileiradas e depois ficam em NVM_REQ_PENDING [SWS_NvM_00185]. Opcionalmente, o NvM utiliza uma fila própria para requisições imediatas [SWS_NvM_00378]. O resultado é fornecido por NvM_GetErrorStatus ou por um callback configurado [SWS_NvM_00015] [SWS_NvM_00740].

Diagrama de sequência: uma requisição assíncrona de escrita é enfileirada, processada em NvM_MainFunction e confirmada via callback, mensagem do BswM e consulta de status. Fontes: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00891], SWS NvM p. 160

O NvM intercepta erros de leitura em três níveis:

  • repetições de leitura configuradas [SWS_NvM_00526],
  • a segunda cópia de blocos redundantes [SWS_NvM_00199],
  • dados padrão com o resultado NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202].

Interpretação: a ordem dos níveis provavelmente segue a enumeração na Error Description. O NvM repete erros de escrita até NVM_MAX_NUM_OF_WRITE_RETRIES e depois reporta NVM_E_REQ_FAILED ao DEM [SWS_NvM_00684]. Os usuários verificam o status de seus blocos por conta própria [SWS_NvM_00694].

Papel na pilha de memória: único acesso à memória não volátil

O NVRAM Manager (NvM) centraliza o acesso a dados não voláteis. O ambiente acessa a memória não volátil exclusivamente por meio do NvM, que fornece uma interface de callback para essa finalidade [SWS_NvM_00384]. O acesso é implícito: o NvM copia blocos entre a NVRAM e a RAM compartilhada. A aplicação trabalha diretamente com os dados da RAM, respeitando as regras de sincronização [SWS_NvM_00038] [SWS_NvM_00692]. Um bloco é selecionado por meio de seu ID de bloco configurado [SWS_NvM_00069] [SWS_NvM_00471]. As camadas superiores incluem apenas NvM.h para isso [SWS_NvM_00691]. O diagrama de atualização implícita mostra a divisão de tarefas: outras partes do software básico disparam o salvamento e a restauração de todos os blocos em função do estado da ECU. A SW-C acessa apenas o conteúdo de seus blocos de RAM (SWS NvM p. 121).

Para os níveis inferiores, o NvM opera contra a Memory Abstraction Interface. Juntamente com Fee ou Ea, ela fornece um espaço de endereçamento linear virtual de 32 bits [SWS_NvM_00051] [SWS_NvM_00465]. O NvM calcula somas de verificação por meio do módulo Crc [SWS_NvM_00466]. Ele é informado sobre o término de um job da camada inferior por duas vias:

  • via polling por meio de MemIf_GetJobResult,
  • com o polling desativado, via NvM_JobEndNotification e NvM_JobErrorNotification [SWS_NvM_00440] [SWS_NvM_00441] (Error Description p. 43).

Erros de produção vão para o DEM [SWS_NvM_00592], erros de desenvolvimento para o DET [SWS_NvM_00614]. O NvM reporta estados de requisições ao BswM [SWS_NvM_00745] [SWS_NvM_00746].

Diagrama de contexto: o NvM faz a mediação entre usuários e BswM, de um lado, e MemIf/Fee/Ea, de outro. Ele reporta erros ao DEM e ao DET. Fontes: [SWS_NvM_00384] [SWS_NvM_00745] [SWS_NvM_00746] [SWS_NvM_00465] [SWS_NvM_00466], Error Description p. 43

Estrutura de um bloco de NVRAM e os três tipos de gerenciamento

Um bloco de NVRAM consiste nos componentes obrigatórios NV block, RAM block e Administrative Block. Um ROM block com dados padrão é opcional [SWS_NvM_00138] [SWS_NvM_00139] [SWS_NvM_00020]. A composição é definida pelo descritor de bloco no momento da configuração [SWS_NvM_00140]. Os componentes individuais:

  • O NV block contém os dados úteis, bem como, opcionalmente, CRC e cabeçalho [SWS_NvM_00125] (SWS NvM p. 39).
  • O bloco de RAM pode residir na RAM global sem restrições de endereço [SWS_NvM_00088].
  • O Administrative Block é invisível para a aplicação. Ele armazena o índice do conjunto de dados, os atributos e o campo de erro/status [SWS_NvM_00134] [SWS_NvM_00135] [SWS_NvM_00136].

O NvM suporta os tipos NVM_BLOCK_NATIVE, NVM_BLOCK_REDUNDANT e NVM_BLOCK_DATASET [SWS_NvM_00137]. Eles diferem no número de blocos NV e ROM [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559] (SWS NvM p. 10). Para blocos Dataset, aplica-se o seguinte:

  • NvM_SetDataIndex seleciona o elemento. Índices a partir de NvMNvBlockNum endereçam blocos de ROM [SWS_NvM_00014] [SWS_NvM_00445] (NV Data Handling p. 10).
  • O índice não é armazenado de forma persistente; NvM_Init o define como zero [SWS_NvM_00160] [SWS_NvM_00192].
  • A SW-C é responsável pela definição correta [SWS_NvM_00695].

Ciclo de vida: NvM_Init, NvM_ReadAll e NvM_WriteAll

O BswM chama NvM_Init exclusivamente [SWS_NvM_00693]. O NvM_Init reinicializa filas e máquinas de estados e sinaliza internamente “INIT DONE” [SWS_NvM_00399]. Ele não inicializa blocos de RAM nem módulos subordinados [SWS_NvM_00091] [SWS_NvM_00193]. O ponteiro de configuração é sempre NULL_PTR [SWS_NvM_00881]. Somente depois disso NvM_MainFunction processa requisições [SWS_NvM_00257].

Em seguida, o NvM_ReadAll preenche os blocos de RAM [SWS_NvM_00718]. A chamada apenas sinaliza a requisição. O processamento é adiado até que as requisições de bloco individuais sejam concluídas [SWS_NvM_00243]. Depois disso, o job é executado em três etapas:

  1. Primeiro, ele compara o ID de configuração armazenado com o compilado [SWS_NvM_00073]. Em caso de divergência, o comportamento depende de NvMDynamicConfiguration: com NvMDynamicConfiguration == FALSE, a divergência é ignorada [SWS_NvM_00248]. Caso contrário, blocos não resistentes a alterações recebem dados padrão [SWS_NvM_00249] [SWS_NvM_00674] (NV Data Handling p. 15).
  2. Em seguida, ele itera sobre os blocos de usuário, exceto os IDs de bloco 0 e 1 [SWS_NvM_00244]. Ao fazer isso, processa apenas blocos com bloco de RAM permanente ou sincronização explícita [SWS_NvM_00118].
  3. Por fim, define o resultado global como NVM_REQ_OK ou NVM_REQ_NOT_OK [SWS_NvM_00895] [SWS_NvM_00301].

No exemplo de gerenciamento de modos, a regra do BswM NvMReadAllFinished inicia o restante da inicialização somente após a conclusão de NvM_ReadAll (Mode Management Guide p. 31).

Diagrama de sequência: inicialização assíncrona com NvM_Init, NvM_ReadAll e feedback do estado multibloco para o BswM. Fontes: [SWS_NvM_00693] [SWS_NvM_00243] [SWS_NvM_00073] [SWS_NvM_00888] [SWS_NvM_00889], NV Data Handling p. 20

Para o shutdown, o BswM chama NvM_WriteAll [SWS_NvM_00092]. O job comporta-se da seguinte forma:

  • Ele escreve blocos de RAM permanentes ou busca dados sincronizados explicitamente via NvM_WriteRamBlockToNvm [SWS_NvM_00252].
  • Previamente, verifica o estado “valid/modified” [SWS_NvM_00682].
  • Ele pula blocos protegidos e bloqueados sem emitir mensagem de erro [SWS_NvM_00434] [SWS_NvM_00750].
  • Outras requisições não o interrompem [SWS_NvM_00567].

Os usuários marcam blocos alterados com NvM_SetRamBlockStatus(…, TRUE), desde que a API esteja ativada [SWS_NvM_00406] [SWS_NvM_00408]. Para blocos com dirty flag, a RTE assume essa chamada (NV Data Handling p. 41).

NvM_CancelWriteAll é reservado ao BswM [SWS_NvM_00703] e não tem efeito sem um NvM_WriteAll em execução [SWS_NvM_00233]. O bloco atual é finalizado de forma não destrutiva [SWS_NvM_00238]. Os blocos restantes e o resultado multibloco recebem NVM_REQ_CANCELED [SWS_NvM_00236] [SWS_NvM_00237] (SWS NvM p. 161).

Duas outras requisições multibloco complementam o ciclo de vida:

  • NvM_ValidateAll define blocos com validação automática como “VALID / CHANGED” [SWS_NvM_00856].
  • NvM_FirstInitAll grava dados padrão em blocos ou os invalida caso não haja dados disponíveis [SWS_NvM_00913] [SWS_NvM_00919].

Para todas as requisições multibloco, aplica-se um tamanho de fila de um [SWS_NvM_00380].

Diagrama de sequência: shutdown com NvM_WriteAll e cancelamento opcional por NvM_CancelWriteAll. Fontes: [SWS_NvM_00092] [SWS_NvM_00682] [SWS_NvM_00238] [SWS_NvM_00237] [SWS_NvM_00889], Mode Management Guide p. 37

Requisições individuais: filas, prioridades e feedback

Requisições de bloco individuais como NvM_ReadBlock, NvM_WriteBlock ou NvM_RestoreBlockDefaults são assíncronas. A função recebe os parâmetros, enfileira a requisição e retorna [SWS_NvM_00195] [SWS_NvM_00208] [SWS_NvM_00224]. Depois disso, o resultado do bloco fica em NVM_REQ_PENDING [SWS_NvM_00185]. Em caso de estouro de fila, a função retorna E_NOT_OK [SWS_NvM_00184]. Um bloco só é enfileirado se ainda não estiver pendente ou em processamento [SWS_NvM_00385].

Outros serviços operam de forma síncrona no contexto do chamador, como NvM_SetDataIndex [SWS_NvM_00448] e NvM_GetErrorStatus (SWS NvM p. 158). O NvM_CancelJobs remove requisições pendentes de um bloco; um job em andamento, no entanto, é continuado [SWS_NvM_00536] [SWS_NvM_00537].

O processamento ocorre de forma serializada por prioridade [SWS_NvM_00162]. Se NvMJobPrioritization estiver ativo, o NvM utiliza duas filas, sendo uma delas para requisições de escrita imediatas (dados de colisão) [SWS_NvM_00564] [SWS_NvM_00378]. Uma requisição NvM_WriteBlock desse tipo cancela um job pendente de forma destrutiva [SWS_NvM_00300]. O NvM_MainFunction reinicia o job cancelado em seguida [SWS_NvM_00258]. Sem priorização, o NvM processa na ordem de chegada, sem jobs imediatos [SWS_NvM_00379]. Requisições que chegam durante uma requisição multibloco são enfileiradas e executadas em seguida [SWS_NvM_00568] [SWS_NvM_00569].

Cada requisição assíncrona armazena seu resultado no campo de erro/status [SWS_NvM_00175]. NvM_GetErrorStatus lê esse campo [SWS_NvM_00015]. Além disso, existem duas vias opcionais de feedback:

  • Se um callback estiver configurado, NvM_MainFunction chama NvM_SingleBlockCallbackFunction [SWS_NvM_00740] [SWS_NvM_00347]. Sem callback, não há notificação assíncrona [SWS_NvM_00742] (SWS NvM p. 160).
  • Com NvMBswMBlockStatusInformation, o NvM reporta aceitação e resultado ao BswM [SWS_NvM_00890] [SWS_NvM_00891] (SWS NvM p. 162).

Diagrama de sequência: requisição assíncrona de escrita com mensagens de status do BswM, callback e consulta de status. Fontes: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00740] [SWS_NvM_00890] [SWS_NvM_00891], SWS NvM p. 160

Sincronização de blocos de RAM e estado do bloco

O NvM dispõe de duas formas de sincronizar dados com o bloco de RAM da aplicação. Na sincronização implícita, ele opera diretamente nesse bloco de RAM. A aplicação disponibiliza o bloco e não o acessa até o término da requisição [SWS_NvM_00698] [SWS_NvM_00699]. Se ela passar NULL_PTR, o NvM utiliza o bloco de RAM permanente [SWS_NvM_00898] [SWS_NvM_00900]. Um bloco temporário via ponteiro continua sendo possível [SWS_NvM_00278]. Os serviços PRAM operam sempre no bloco de RAM permanente [SWS_NvM_00765] [SWS_NvM_00794]. No cenário da RTE, esse bloco é uma Per-Instance-Memory (NV Data Handling p. 32).

Na sincronização explícita (NvMBlockUseSyncMechanism), a troca ocorre por meio de um RAM mirror interno [SWS_NvM_00511]. Existe exatamente um desse tipo, dimensionado de acordo com o maior bloco envolvido [SWS_NvM_00513]. O NvM chama NvMWriteRamBlockToNvCallback ou NvMReadRamBlockFromNvCallback [SWS_NvM_00515] [SWS_NvM_00516]. Se um callback retornar E_NOT_OK, ele repete a chamada no ciclo seguinte, até NvMRepeatMirrorOperations vezes [SWS_NvM_00579] [SWS_NvM_00840]. Até o callback, a aplicação ainda pode alterar o bloco de RAM [SWS_NvM_00705]. Um bloco utiliza ou sincronização explícita ou um bloco de RAM permanente, não ambos [SWS_NvM_00904]. O mecanismo permite blocos compartilhados por meio de uma NvBlockSwComponentType (NV Data Handling p. 12).

Diagrama de sequência: requisição de escrita com sincronização explícita por meio do RAM mirror, incluindo repetição em E_NOT_OK. Fontes: [SWS_NvM_00515] [SWS_NvM_00705] [SWS_NvM_00579] [SWS_NvM_00840], NV Data Handling p. 27

Para blocos de RAM permanentes ou o mirror, o NvM mantém um estado “valid”/“invalid” [SWS_NvM_00128] [SWS_NvM_00132]. As transições em detalhe:

  • NvM_ReadBlock invalida o bloco de RAM permanente logo no enfileiramento [SWS_NvM_00198].
  • Após leitura bem-sucedida, ele fica “valid/unchanged” [SWS_NvM_00200].
  • Após o carregamento de dados padrão, ele fica “valid/changed” [SWS_NvM_00366].
  • NvM_SetRamBlockStatus(…, TRUE) o marca como modificado e dispara um recálculo de CRC em segundo plano [SWS_NvM_00406] [SWS_NvM_00121].
  • Após escrita bem-sucedida, ele é considerado “valid/unmodified” [SWS_NvM_00472].

Configuração, mecanismos de proteção e relação com partições

Para recursos limitados, existem três classes de configuração de API [SWS_NvM_00149]. A classe 1 não suporta blocos Dataset [SWS_NvM_00365]. As tabelas de descritores são geradas [SWS_NvM_00143]. Os usuários declaram a necessidade de memória no momento da configuração [SWS_NvM_00030]. Os módulos BSW fazem isso por meio de NvBlockNeeds (BSWMD Template p. 241). O integrador de ECU deriva a configuração do NvM a partir disso (Methodology p. 444).

Para blocos individuais, estão disponíveis vários mecanismos de proteção:

  • Um campo de atributos gerencia a proteção contra escrita [SWS_NvM_00054]; NvMBlockWriteProt a ativa como configuração padrão [SWS_NvM_00326].
  • Blocos com NvMWriteBlockOnce são escritos apenas uma vez [SWS_NvM_00397]. O NvM rejeita requisições de escrita antes da primeira leitura [SWS_NvM_00952].
  • Para blocos travados (NvM_SetBlockLockStatus), NvM_WriteBlock retorna E_NOT_OK [SWS_NvM_00749]. O travamento não é alterado por NvM_SetRamBlockStatus nem por NvM_SetBlockProtection [SWS_NvM_00754].
  • Também são opcionais um cabeçalho Static-Block-ID [SWS_NvM_00522], uma comparação de CRC contra escritas desnecessárias [SWS_NvM_00849] e criptografia por meio do CSM [SWS_NvM_00976].

Em caso de particionamento, o NvM chama interfaces no contexto da partição respectivamente associada. Funções gerais são executadas na partição mestre [SWS_NvM_00969]. Apenas o mestre oferece NvM_ReadAll e NvM_WriteAll [SWS_NvM_00970] [SWS_NvM_00971] [SWS_NvM_CONSTR00974]. As SW-Cs acessam o NvM por meio de portas associadas a blocos:

  • PS_{Block} (serviço) [SWS_NvM_00847]
  • PAdmin_{Block} (administração) [SWS_NvM_00843]
  • PM_{Block} (mirror) [SWS_NvM_00844]
  • PNJF_{Block} (notificação de término de job) [SWS_NvM_00846]

Comportamento em caso de erro

Durante a leitura, o NvM avalia as mensagens da MemIf de formas distintas:

  • Ele reporta uma divergência de CRC como NVM_E_INTEGRITY_FAILED [SWS_NvM_00203].
  • Ele reporta MEMIF_JOB_FAILED como NVM_E_REQ_FAILED [SWS_NvM_00654].
  • MEMIF_BLOCK_INVALID resulta apenas em NVM_REQ_NV_INVALIDATED, sem notificação ao DEM [SWS_NvM_00341] [SWS_NvM_00652].

Depois disso, atuam vários níveis de recuperação:

  1. Em caso de erros de CRC, seguem-se repetições de leitura configuradas [SWS_NvM_00526].
  2. Para blocos redundantes, o NvM lê a segunda cópia e tenta restabelecer a redundância [SWS_NvM_00199] [SWS_NvM_00531]. Se isso falhar, ele reporta NVM_E_LOSS_OF_REDUNDANCY [SWS_NvM_00546].
  3. Por fim, o NvM carrega dados padrão com o resultado NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202]. O conteúdo da memória NV permanece inalterado [SWS_NvM_00172].

Na ausência de dados padrão, o bloco de RAM permanece inválido [SWS_NvM_00658] [SWS_NvM_00204]. Interpretação: a ordem dos níveis provavelmente segue a enumeração na Error Description (Error Description p. 62). Essa fonte diverge dos Requirements em dois pontos. Ela cita NVM_REQ_RESTORED_FROM_ROM em vez de NVM_REQ_RESTORED_DEFAULTS. Além disso, sintetiza a falha definitiva genericamente como NVM_E_REQ_FAILED. Normativos são os Requirements supracitados.

Diagrama de atividades: tratamento de erros de leitura, desde a repetição e a cópia redundante até os dados padrão. Interpretação: a ordem segue a enumeração da Error Description. Fontes: [SWS_NvM_00526] [SWS_NvM_00199] [SWS_NvM_00202] [SWS_NvM_00341] [SWS_NvM_00658], Error Description p. 62

Durante a escrita, o NvM conta retornos negativos até NVM_MAX_NUM_OF_WRITE_RETRIES [SWS_NvM_00213] [SWS_NvM_00216]. Se o limite for excedido, ele define NVM_REQ_NOT_OK e reporta NVM_E_REQ_FAILED [SWS_NvM_00683] [SWS_NvM_00684] (Error Description p. 43). Dois outros padrões de erro:

  • Se a verificação de escrita falhar, o NvM reporta NVM_E_VERIFY_FAILED e repete a escrita [SWS_NvM_00528] [SWS_NvM_00529].
  • Um bloco redundante é considerado gravado assim que uma cópia tiver sido bem-sucedida [SWS_NvM_00284].

Em caso de operação incorreta, o NvM reporta ao DET se a detecção de erros de desenvolvimento estiver ativada. Exemplos são NVM_E_UNINIT e NVM_E_BLOCK_PENDING [SWS_NvM_00614] [SWS_NvM_00615], bem como NVM_E_WRITE_PROTECTED [SWS_NvM_00962]. Se faltarem dados de ROM e callbacks de inicialização, o resultado é NVM_REQ_INTEGRITY_FAILED [SWS_NvM_00204].

  • Redundante: se a leitura da primeira cópia falhar, a segunda cópia de NV é utilizada automaticamente [SWS_NvM_00199]. Se ambas as cópias forem inválidas, o bloco completo é invalidado [SWS_NvM_00317].
