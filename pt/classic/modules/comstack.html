Papel de ComStack_Types: o vocabulário de tipos comum da pilha de comunicação

O módulo "comstack" não é um componente executável. Ele fornece por meio de ComStack_Types.h os tipos de dados com os quais os módulos da pilha de comunicação Classic descrevem PDUs, buffers e canais. Todos os nove tipos do release estão, segundo a especificação, "Available via ComStack_Types.h", de PduInfoType a NetworkHandleType ([SWS_COMTYPE_00011], [SWS_COMTYPE_00038]). PduLengthType deve ser usado em toda a pilha de comunicação AUTOSAR de uma ECU, exceto nos drivers de barramento ([SWS_COMTYPE_00008], SWS ComStackTypes p. 16). Com isso, o limite do sistema é definido: acima dos drivers de barramento, interfaces, roteadores, protocolos de transporte e camadas superiores utilizam os mesmos tipos. A RTE também importa, para os callbacks de Large Data, entre outros, BufReq_ReturnType, PduIdType, PduInfoType, PduLengthType e RetryInfoType de ComStack_Types.h (SWS RTE p. 833).

Quanto às fontes: as seções de documento citadas provêm predominantemente dos releases R23-11 a R25-11. Apenas o diagrama de retry da especificação J1939Tp é comprovado também para R20-11. Normativos para R20-11 são os requirements. Divergências são mencionadas no texto, como no caso de PNCHandleType ([SWS_COMTYPE_00036], SWS ComStackTypes p. 17).

Diagrama de contexto: ComStack_Types.h fornece tipos comuns a todos os módulos da pilha acima dos drivers de barramento; os limites de faixa derivam da configuração da EcuC. Fontes: [SWS_COMTYPE_00005], [SWS_COMTYPE_00008], [SWS_COMTYPE_00038], TPS EcuC p. 205, SWS RTE p. 833

Identidade de PDU: PduIdType e IDs de handle locais ao módulo

PduIdType é variável em R20-11 como uint16 ou uint8. O tamanho depende do maior número de PDUs utilizado por um único módulo de software. O gerador cria o limite de faixa a partir da configuração da EcuC em ComStack_Cfg.h ([SWS_COMTYPE_00005]). Na EcuC, isso corresponde ao parâmetro PduIdTypeEnum com os valores UINT8 e UINT16. Se pelo menos um módulo gerenciar mais de 256 PDUs, uint16 é necessário (ECUConfiguration p. 153).

Um valor PduIdType não é uma chave de todo o sistema. Ele é um handle dentro do respectivo módulo chamado: cada módulo BSW com API de PDU mantém uma lista própria de IDs de PDU como tabela de lookup (SWS PduR p. 33). O PDU Router identifica um caminho de roteamento por meio do ID de origem e dos IDs de destino. Ele converte o ID no caminho de transmissão e no caminho de confirmação, repassando o valor PduInfoType inalterado (SWS PduR p. 33). Para que módulos adjacentes se refiram à mesma PDU, a EcuC define uma EcucPduCollection intermodular com objetos Pdu globais (TPS EcuC p. 190).

Diagrama de sequência: O PduR converte os valores de PduIdType por módulo de destino, repassa PduInfoType inalterado e encaminha a confirmação com o ID restaurado para o Com. Fontes: SWS PduR p. 33, SWS PduR p. 33, [SWS_COMTYPE_00005]

Conteúdo de PDU: PduInfoType, PduLengthType e metadados

PduInfoType reúne as informações básicas de uma PDU de qualquer tipo. SduDataPtr aponta para os dados úteis, MetaDataPtr para os metadados e SduLength indica o comprimento em bytes ([SWS_COMTYPE_00011], SWS ComStackTypes p. 17). O comprimento possui o tipo PduLengthType. Ele é gerado como uint8, uint16 ou uint32, dependendo do comprimento máximo de PDU da ECU. Sem segmentação, o tamanho do frame do barramento determina a largura; no FlexRay, no máximo 255 bytes e, portanto, uint8. Com segmentação, o comprimento máximo de uma N-PDU segmentada determina a largura ([SWS_COMTYPE_00008], SWS ComStackTypes p. 16).

Metadados são, por exemplo, CAN-ID, Socket-ID ou endereços de diagnóstico. Eles consistem em uma sequência de elementos configurada estaticamente por PDU. Elementos com mais de 8 bits estão na byte order da plataforma ([SWS_COMTYPE_00011]). A ordem e a posição dos elementos derivam da configuração da EcuC da PDU global. A ordenação por comprimento torna o padding desnecessário (SWS BSWGeneral p. 67). Um exemplo de aplicação: em um grupo de conexões de socket, o SoAd transmite apenas na conexão indicada por PduInfoType.MetaDataPtr (SWS SoAd p. 30).

Para o tempo de vida dos ponteiros, aplica-se uma regra operacional: em uma indicação de recepção, o ponteiro de dados passado é válido apenas até o retorno da indicação (SWS CanNm p. 73). O comprimento 0 possui vários significados especiais. Uma chamada de CopyRxData com SduLength 0 consulta o buffer de recepção livre da camada superior; SduDataPtr pode então ser NULL_PTR (SWS DoIP p. 77). Na transmissão, SduLength 0 indica uma I-PDU de comprimento desconhecido. O PduR repassa esse comprimento a todos os módulos TP de destino (SWS PduR p. 43).

Handshake de buffer na recepção TP: BufReq_ReturnType

BufReq_ReturnType armazena o resultado de uma solicitação de buffer. Os valores são predefinidos: BUFREQ_OK (0), BUFREQ_E_NOT_OK (1), BUFREQ_E_BUSY (2) e BUFREQ_E_OVFL (3). Em caso de BUFREQ_E_BUSY, o solicitante deve repetir a requisição durante um determinado tempo ([SWS_COMTYPE_00012], SWS ComStackTypes p. 19).

Uma recepção TP ocorre em três etapas:

  1. O protocolo de transporte relata, com PduR_<User:LoTp>StartOfReception, o comprimento total TpSduLength e os dados do primeiro frame. Por meio de bufferSizePtr, ele obtém de volta o buffer disponível e calcula a partir dele o tamanho do bloco.
  2. Ele repassa os segmentos via CopyRxData.
  3. Ele conclui a recepção com RxIndication (SWS PduR p. 92).

BUFREQ_OK significa aqui "conexão aceita", mesmo que 0 seja relatado como tamanho de buffer (SWS PduR p. 92). O FlexRay AR-TP não mantém buffers de mensagens próprios. Ele troca os dados em partes com a camada superior (SWS FrArTp p. 50).

Diagrama de sequência: A recepção TP começa com StartOfReception, entrega os dados via CopyRxData e termina com RxIndication; em caso de início recusado de um frame único, nenhuma RxIndication se segue. Fontes: SWS FrArTp p. 50, SWS FrArTp p. 50, SWS PduR p. 92, [SWS_COMTYPE_00012]

Transmissão com repetição: RetryInfoType e TpDataStateType

Na transmissão em partes, o protocolo de transporte passa com CopyTxData um RetryInfoType. Ele é composto por TpDataState e TxTpDataCnt; este último é o offset dos bytes a serem retransmitidos ([SWS_COMTYPE_00037], SWS ComStackTypes p. 20). Os três estados significam ([SWS_COMTYPE_00027], SWS ComStackTypes p. 19):

  • TP_DATACONF: todos os dados copiados até o momento foram confirmados e podem ser removidos do buffer TP.
  • TP_DATARETRY: dados já copiados devem ser fornecidos novamente a partir do offset TxTpDataCnt.
  • TP_CONFPENDING: os dados copiados anteriormente devem ser mantidos.

O diagrama de retry da especificação SAE-J1939-TP ilustra a interação. Por bloco, o primeiro pacote é solicitado com TP_DATACONF, e os seguintes com TP_CONFPENDING. Se um TP.DT for perdido, o TP retorna ao primeiro pacote do bloco. Em seguida, solicita novamente com TP_DATARETRY; TxTpDataCnt é o offset para o início do bloco (SWS J1939Tp p. 55). O FrArTp também define TP_CONFPENDING na transmissão não segmentada com retry ativado (SWS FrArTp p. 50).

Diagrama de sequência: Por bloco, o TpDataState controla se os dados são confirmados, retidos ou copiados novamente a partir do início do bloco. Fontes: SWS J1939Tp p. 55, [SWS_COMTYPE_00027], [SWS_COMTYPE_00037]

O gateway TP direto do PduR para frames únicos mostra como uma camada superior reage ao estado. Em caso de TP_DATACONF, TP_CONFPENDING ou ausência do ponteiro RetryInfoType, ela copia SduLength bytes. Em caso de TP_DATARETRY, ela recua previamente a posição em TxTpDataCnt bytes (SWS PduR p. 57). Nem toda camada superior avalia as informações de repetição: nos callbacks do LdCom, retry não é tratado pelo LdCom nem pela sua camada superior, de acordo com a especificação (SWS LdCom p. 34). Desde o AUTOSAR 4.3.1, o parâmetro em PduR_<User:LoTp>CopyTxData é um ponteiro para const RetryInfoType (SWS PduR p. 3).

Diagrama de atividades: O PduR decide com base no TpDataState se copia diretamente, se redefine a posição ou se rejeita a solicitação. Fontes: SWS PduR p. 57, [SWS_COMTYPE_00027], [SWS_COMTYPE_00012]

Canais, redes parciais e parâmetros TP alteráveis

NetworkHandleType armazena o identificador de um canal de comunicação. Ele é um uint8 de base zero com a faixa de valores 0..255 ([SWS_COMTYPE_00038], SWS ComStackTypes p. 20). Em Mirror_GetNetworkId, ele representa o canal ComM; em CanSM_TxTimeoutException, a rede CAN afetada (SWS Mirror p. 78, SWS CanSM p. 87). Callbacks de gerenciamento de rede como Nm_RemoteSleepIndication também identificam o canal NM por meio desse tipo (SWS Nm p. 89).

PNCHandleType armazena o identificador de um cluster de rede parcial. Na R20-11, ele é derivado de uint8 ([SWS_COMTYPE_00036]). A presente seção de documento da R23-11 indica, por outro lado, uint16 como tipo base (SWS ComStackTypes p. 17). Para R20-11, aplica-se o estado de requirements uint8.

TPParameterType indica o parâmetro a ser alterado em tempo de execução. Os valores são TP_STMIN (Separation Time), TP_BS (Block Size) e TP_BC (controle de largura de banda do protocolo de transporte FlexRay) ([SWS_COMTYPE_00031], SWS ComStackTypes p. 18). Os módulos restringem o uso. J1939Tp_ChangeParameter aceita apenas TP_BS com valores até 255 (SWS J1939Tp p. 42). O FrArTp rejeita alterações durante uma recepção em andamento com E_NOT_OK (SWS FrArTp p. 49).

Comportamento em caso de erro

Os tipos em si não apresentam comportamento de erro. No entanto, eles transportam os resultados de acordo com os quais os módulos reagem ([SWS_COMTYPE_00012]). Na transmissão FrArTp não segmentada, aplica-se:

  • Se PduR_FrArTpCopyTxData retornar BUFREQ_E_BUSY, o TP repete a chamada até a expiração de FrArTpTimeCs.
  • Em caso de BUFREQ_E_NOT_OK ou após a expiração do tempo, ele aborta e chama PduR_FrArTpTxConfirmation com E_NOT_OK.
  • Se PduR_FrArTpStartOfReception retornar BUFREQ_E_NOT_OK ou BUFREQ_E_OVFL para um frame único, a recepção é encerrada imediatamente, sem PduR_FrArTpRxIndication (SWS FrArTp p. 50).

Diagrama de atividades: BUFREQ_E_BUSY leva à repetição até o timeout; BUFREQ_E_NOT_OK e BUFREQ_E_OVFL levam ao cancelamento. Fontes: SWS FrArTp p. 50, SWS FrArTp p. 44, [SWS_COMTYPE_00012]

No gateway TP direto, aplicam-se duas regras para TP_DATARETRY. Se o PduR não puder redefinir a posição, responde com BUFREQ_E_NOT_OK e mantém a posição e os dados inalterados. Se faltarem dados após a redefinição, responde com BUFREQ_E_BUSY (SWS PduR p. 57). No gateway on-the-fly, o PduR não suporta repetição de dados já transmitidos (SWS PduR p. 58). No roteamento TP multicast, ele retorna E_NOT_OK em TP_DATARETRY segundo a seção de documento (SWS PduR p. 41).

Além disso, o PduR não adota medidas de erro próprias. Ele repassa erros provenientes de valores de retorno para o módulo de origem superior, que é responsável pelo tratamento (SWS PduR p. 46, SWS PduR p. 49).
