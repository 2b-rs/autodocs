Interliga componentes de software entre si e com o software de base, e coordena a sua execução.

O Runtime Environment (RTE) interliga componentes de software AUTOSAR entre si e com os módulos do software de base, regulando o escalonamento determinístico na Classic Platform através do Basic Software Scheduler (SchM) (SWS_RTE p. 100). O ciclo de vida é coordenado através de interfaces normalizadas desde SchM_Init e Rte_Start até Rte_Stop e SchM_Deinit [SWS_Rte_08060], [SWS_Rte_03015]. A par dos padrões Sender-Receiver e Client-Server, métodos de ponteiros de software para parâmetros de calibração bem como verificações de proteção de memória em fronteiras de partição asseguram uma operação em tempo real robusta [SWS_Rte_03914], [SWS_Rte_02752].

O Runtime Environment (RTE) desacopla os componentes de software AUTOSAR do hardware da ECU e, em conjunto com o Basic Software Scheduler (SchM), coordena a execução de todos os fluxos de aplicação e de software de base (SWS_RTE p. 100). O arranque controlado ocorre gradualmente através do EcuStateManager: em primeiro lugar, SchM_Init inicializa as estruturas do escalonador, seguido por SchM_Start antes da chamada de BswM_Init, bem como SchM_StartTiming para a ativação de eventos periódicos da BSW [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548]. Os SW-Cs de aplicação são de seguida iniciados através de Rte_Start e, durante o encerramento, parados por Rte_Stop antes da desinicialização via SchM_Deinit [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551].

Diagrama de sequência: Coordenação temporal de arranque e encerramento entre EcuM, SchM e RTE. Fontes: [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

A comunicação abrange padrões Sender-Receiver e Client-Server tanto intra- como inter-ECU (SWS_RTE p. 286). Elementos de dados não armazenados em buffer asseguram valores iniciais consistentes através de initValue, ao passo que eventos armazenados em buffer são processados através de filas FIFO [SWS_Rte_06009], [SWS_Rte_02521]. Em interações Client-Server, Transaction Handles de dois elementos associam pedidos assíncronos às respetivas respostas [SWS_Rte_02649]. Mudanças de modo através de Rte_Switch executam uma sequência determinística de dez etapas, na qual Distributed Shared Mode Queues garantem a ordem estrita de processamento de várias máquinas de modo [SWS_Rte_02631], [SWS_Rte_02665], [SWS_Rte_91102].

Diagrama de contexto: Estruturas de endereçamento e indireção dos métodos de calibração Single Pointered e Double Pointered. Fontes: [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

Para a calibração online, o RTE gera estruturas de ponteiros de acordo com o princípio Single Pointered ou Double Pointered, permitindo modificar grupos de parâmetros na RAM sem emulação de hardware [SWS_Rte_03913], [SWS_Rte_03914]. Excedimentos de intervalo incorretos ou timeouts são reportados ao componente chamador através de Std_ReturnType, enquanto verificações de proteção de memória em fronteiras de partição impedem manipulações não autorizadas [SWS_Rte_01034], [SWS_Rte_03845], [SWS_Rte_02752].

Papel e limites de sistema do RTE na Classic Platform

O Runtime Environment (RTE) constitui a espinha dorsal funcional da arquitetura AUTOSAR Classic, ao desacoplar totalmente os componentes de software (SW-Cs) do hardware computacional subjacente, bem como dos módulos de software de base (BSW) próximos do hardware (SWS_RTE p. 100). O gerador de RTE cria para cada ECU uma interface personalizada, que resolve todas as relações de comunicação — tanto localmente num microcontrolador (Intra-ECU) como em toda a rede através de barramentos de comunicação (Inter-ECU) — através de chamadas de API uniformes como Rte_Read, Rte_Write ou Rte_Call [SWS_Rte_01091], [SWS_Rte_01102]. Através da disponibilização de um elemento BswModuleDescription gerado bem como das respetivas descrições BswInternalBehavior, o RTE integra-se como parte integrante no esquema de configuração e empacotamento do AUTOSAR [SWS_Rte_05165], [SWS_Rte_05166].

Múltiplas instanciações do mesmo componente de software são resolvidas pelo RTE exclusivamente por meio de Runnable Entities reentrantes com compartilhamento de código; a duplicação de código não é expressamente suportada [SWS_Rte_03015], [SWS_Rte_02002]. Para cada instância, um identificador de instância exclusivo é passado no código C ou endereçado através da Component Data Structure (CDS), garantindo execuções paralelas de instâncias em contextos de tarefas compartilhados sem corrupção mútua de dados (SWS_RTE p. 126, SWS_RTE p. 804). Complementando os SW-Cs de aplicação, o RTE abrange o escalonamento cíclico e o gerenciamento de modos de todos os módulos BSW por meio do Basic Software Scheduler (SchM) [SWS_Rte_08060], [SWS_Rte_07273].

Ciclo de vida e coordenação de inicialização do SchM e do RTE

A inicialização do sistema exige uma ordem estritamente regulada entre o BSW-Scheduler (SchM) e o RTE orientado à aplicação (SWS_RTE p. 459). Antes de o SchM ser inicializado, apenas as funções de bloqueio SchM_Enter e SchM_Exit estão disponíveis por motivos de segurança do sistema. O EcuStateManager chama inicialmente a função SchM_Init, inicializando estruturas de dados internas e máquinas de modo, além de iniciar BswSchedulableEntities com Background-Events [SWS_Rte_08060], [SWS_Rte_07584]. Antes mesmo da chamada de BswM_Init, deve-se chamar SchM_Start [SWS_Rte_07273], [SWS_Rte_04548]. A ativação de execuções periódicas de BSW (BswTimingEvents) é então liberada através de SchM_StartTiming [SWS_Rte_04548], [SWS_Rte_04551], [SWS_Rte_07574].

Diagrama de sequência: Coordenação temporal de arranque e encerramento entre EcuM, SchM e RTE. Fontes: [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

Somente quando os serviços básicos necessários estiverem em execução, o EcuStateManager ativa a execução dos SW-Cs de aplicação com Rte_Start e inicia as transições de modo para On-Entry-Runnables não agrupadas [SWS_Rte_03015], [SWS_Rte_06766]. Se a alocação de recursos falhar em Rte_Start, a função retorna o código de erro RTE_E_LIMIT [SWS_Rte_01262]. Durante o desligamento da ECU, Rte_Stop encerra inicialmente a execução da aplicação e, a partir desse momento, ignora requisições e dados recebidos [SWS_Rte_02538], [SWS_Rte_02535], [SWS_Rte_02536]. Somente após a terminação completa de Rte_Stop é permitido chamar SchM_Deinit, o que libera todos os recursos de sistema do scheduler e inicia as limpezas específicas de plug-ins por meio de Rte_Rips_SchM_Deinit [SWS_Rte_04551], [SWS_Rte_07277], [SWS_Rte_89019].

Padrões de comunicação: Sender-Receiver e Client-Server

No paradigma Sender-Receiver, o RTE distingue fundamentalmente entre a semântica de dados e a semântica de eventos (SWS_RTE p. 286). Na semântica de dados (swImplPolicy != queued), o último valor gravado é mantido no buffer e consumido explicitamente por meio de Rte_Read ou implicitamente via Rte_IRead [SWS_Rte_01091], [SWS_Rte_06000]. Na leitura implícita, o RTE garante uma cópia consistente do valor dos dados ao longo de todo o tempo de execução da Runnable Entity [SWS_Rte_06001]. Antes da primeira recepção, o RTE disponibiliza o initValue configurado, de modo que nenhum estado de memória não inicializado seja processado [SWS_Rte_06009], [SWS_Rte_06010].

Diagrama de sequência: comunicação Sender-Receiver inter-ECU para sinais não armazenados em buffer com proteção por valor inicial. Fontes: [SWS_Rte_01091], [SWS_Rte_06009], [SWS_Rte_01289], AUTOSAR_SWS_RTE p. 148.

Em contrapartida, a semântica de eventos (swImplPolicy = queued) processa sequências de dados sem perdas por meio de estruturas de buffer FIFO, preenchidas por meio de Rte_Send e decrementadas por Rte_Receive [SWS_Rte_01072], [SWS_Rte_01092], [SWS_Rte_02521]. Se o limite de buffer definido via RteQueuedReceiverQueueLength for atingido, o RTE descarta os novos dados recebidos e define uma flag de erro correspondente [SWS_Rte_08940], [SWS_Rte_02523]. Para grandes volumes de dados, o RTE utiliza vias de transporte especializadas, como LdCom ou Large-Data-COM com Signalbuffer-Locking [SWS_Rte_01376], [SWS_Rte_01379].

A comunicação Client-Server suporta chamadas síncronas (Rte_Call) bem como interações assíncronas com consulta de resultado separada via Rte_Result [SWS_Rte_01102], [SWS_Rte_01111]. Do lado do servidor, o RTE armazena as requisições recebidas em uma fila FIFO, a menos que uma chamada direta esteja configurada, enquanto a resposta é armazenada temporariamente do lado do cliente em um buffer de comprimento 1 [SWS_Rte_02527], [SWS_Rte_02528]. Em chamadas que cruzam partições ou ECUs, um Transaction Handle de duas partes, composto por Client Identifier e Sequence Counter, assegura a atribuição exata dos pacotes de resposta à requisição original [SWS_Rte_02649], [SWS_Rte_08711].

Gerenciamento de modo, transições de estado e Distributed Shared Mode Queues

O gerenciamento de modo permite a comutação coordenada de estados operacionais por meio de máquinas de modo dedicadas (ModeMachineInstances), controladas via Rte_Switch [SWS_Rte_02631]. Cada transição de estado passa por uma sequência determinística de dez etapas individuais, compreendendo, entre outras, a ativação de bloqueios de modo, a espera controlada pela conclusão das runnables afetadas, bem como a execução sequencial de entidades OnExit, OnTransition e OnEntry [SWS_Rte_02665]. Somente após a conclusão total de todas as fases é disparado o evento de confirmação ModeSwitchedAckEvent, cujo status pode ser consultado via Rte_SwitchAck [SWS_Rte_02679], [SWS_Rte_02725], [SWS_Rte_02758].

Diagrama de atividades: fluxo determinístico de dez etapas de uma transição de modo dentro de uma ModeMachineInstance. Fontes: [SWS_Rte_02665], [SWS_Rte_02679], EXP_ModeManagementGuide p. 16.

Para forçar uma ordem estrita de trocas de modo no caso de múltiplas máquinas de modo – por exemplo, entre o status da ignição e o estado do motor –, o RTE disponibiliza Distributed Shared Mode Queues (DSMQ) (SWS_RTE p. 442). O status das operações de enfileiramento e desenfileiramento em tais filas é sinalizado por meio do tipo Rte_DsmqStatusType [SWS_Rte_91102]. Para transições de clusters de software, Rte_Rips_SwitchNotificationStatusType mapeia os estados correspondentes de enqueue e dequeue [SWS_Rte_91113]. Interpretação: no BSW-Scheduler, a configuração de pontos de sincronização antes de Rte_Start provavelmente seria selecionada para estabelecer estados determinísticos do sistema antes da liberação de tarefas cíclicas [SWS_Rte_06767].

Calibração, emulação de dados e topologia de memória

Os parâmetros de calibração são alocados centralmente na memória pelo RTE, já que apenas o gerador do RTE conhece a ocupação global de todos os componentes e partições na ECU [SWS_Rte_03961]. Para permitir calibrações online sem hardware de emulação especializado, o RTE suporta métodos de emulação por software, como o Single Pointered Method e o Double Pointered Method (SWS_RTE p. 236, SWS_RTE p. 237). No Single Pointered Method, existe uma tabela de ponteiros (<RteParameterRefTab>) na RAM composta por entradas void*, que apontam para ParameterElementGroups [SWS_Rte_03913], [SWS_Rte_03947].

Diagrama de contexto: Estruturas de endereçamento e indireção dos métodos de calibração Single Pointered e Double Pointered. Fontes: [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

Em contrapartida, o Double Pointered Method utiliza uma indireção de dois níveis: uma tabela de referência armazenada na ROM/Flash aponta para grupos de parâmetros, enquanto um ponteiro base modificável (Base reference) na RAM aponta inicialmente para essa tabela em Flash e, durante uma calibração, pode ser redirecionado para uma cópia modificada na RAM [SWS_Rte_03914]. Os ParameterDataPrototypes são separados em grupos distintos com base em seu swAddrMethod [SWS_Rte_03908]. O gerador do RTE exporta todas as informações de estrutura e de ponteiros no contêiner McSupportData via McSwEmulationMethodSupport para fornecer às ferramentas de calibração (como INCA ou CANape) acesso preciso ao endereçamento A2L [SWS_Rte_05118], [SWS_Rte_05137], [SWS_Rte_05138]. Interpretação: para ECUs de segurança altamente integradas, o Double Pointered Method provavelmente seria preferido, pois a própria tabela de ponteiros permanece primariamente na Flash protegida e vincula buffers de RAM apenas durante a calibração ativa.

Particionamento, proteção de memória e comunicação Inter-OS-Application

Em arquiteturas multi-core e com proteção de memória, o RTE conecta componentes de software através de limites de partição (OS-Applications) por meio da Inter-OS-Application Communication (IOC) (SWS_RTE p. 372). O RTE substitui, neste caso, buffers internos de sinais por buffers de IOC próximos ao hardware e funções de proteção geradas. Para o acesso a áreas exclusivas (ExclusiveAreas), o integrador seleciona parâmetros de configuração específicos do mecanismo (RteExclusiveAreaImplMechanism), que variam desde bloqueios de interrupção até OS-Spinlocks para acessos cross-core (SWS_RTE p. 203).

Se uma partição não testada ou não confiável (Non-Trusted) passar parâmetros de ponteiro para uma partição BSW ou SWC confiável, o RTE realiza obrigatoriamente verificações de endereço e de área de memória [SWS_Rte_02752], [SWS_Rte_02753]. O encaminhamento do ponteiro ocorre apenas se todo o objeto de memória referenciado pertencer à partição chamadora, impedindo eficazmente violações de áreas de proteção e sobrescritas não autorizadas de áreas de memória externas (SWS_RTE p. 378).

Comportamento em caso de erro

O tratamento de erros do RTE separa estritamente erros de infraestrutura de erros de aplicação (SWS_RTE p. 579). Todos os estados de erro são sinalizados diretamente ao chamador por meio do tipo de retorno Std_ReturnType [SWS_Rte_01034]. Entre os erros diretos de infraestrutura incluem-se RTE_E_TIMEOUT (129), RTE_E_LIMIT (130), RTE_E_NO_DATA (131), RTE_E_UNCONNECTED (134), RTE_E_IN_EXCLUSIVE_AREA (135) e RTE_E_SEG_FAULT (136) (SWS_RTE p. 586).

Diagrama de sequência: detecção e propagação de erros de faixa de valores via Rte_Read. Fontes: [SWS_Rte_01091], [SWS_Rte_01371], [SWS_Rte_03845], AUTOSAR_CP_SWS_RTE p. 409.

Com a validação de dados ativada (DataSemantics range check), o RTE verifica os valores de sinal recebidos em relação a faixas de valores definidas [SWS_Rte_01371]. Se um valor recebido estiver fora dos limites, a API de leitura retorna RTE_E_OUT_OF_RANGE [SWS_Rte_03845], [SWS_Rte_03846]. Para sinais com Invalidation-Policy, o RTE substitui o valor por initValue em replace ou mantém o valor anterior em keep e define um evento de erro [SWS_Rte_05030], [SWS_Rte_05049]. Em caso de monitoramento de timeout via aliveTimeout, o RTE registra a ausência via Rte_COMCbkRxTOut e propaga RTE_E_TIMEOUT para SW-Cs em espera [SWS_Rte_08061], [SWS_Rte_03763].

Evidências mais detalhadas

A concepção técnica exata do RTE e do scheduler baseia-se nos seguintes requisitos centrais do payload:

  • Ciclo de vida e integração com SchM: [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_04551] e [SWS_Rte_03015] padronizam inicialização e parada no nível de core (SWS_RTE p. 459).
  • Geração de interfaces e funções: [SWS_Rte_01091] (Rte_Read), [SWS_Rte_01072] (Rte_Send), [SWS_Rte_01102] (Rte_Call) e [SWS_Rte_01111] (Rte_Result) regulam assinaturas e semânticas de chamada (SWS_RTE p. 720, SWS_RTE p. 731).
  • Gerenciamento de modo e DSMQ: [SWS_Rte_02665] define os 10 estágios de transição; [SWS_Rte_91102] e [SWS_Rte_91113] registram o status da fila (EXP_ModeManagementGuide p. 16, SWS_RTE p. 982).
  • Métodos de calibração: [SWS_Rte_03913] e [SWS_Rte_03914] especificam estruturas de tabelas Single e Double Pointered (SWS_RTE p. 236, SWS_RTE p. 237).
  • Sinalização de erros: [SWS_Rte_01034], [SWS_Rte_01262] bem como [SWS_Rte_03845] asseguram códigos de erro consistentes via Std_ReturnType (SWS_RTE p. 586).

função Rte_Start [SWS_Rte_03015] 📄 PDF

Std_ReturnType Rte_Start (void);

Rte_Start é intended para allocate e inicializar sistema recursos e comunicação recursos utilizado pelo RTE.

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 7e79d12edbc4 Procedência

A função Rte_Start aloca e inicializa os recursos de sistema e de comunicação utilizados pela RTE [SWS_Rte_03015]. A API é sempre gerada [SWS_Rte_01309], possui a assinatura Std_ReturnType Rte_Start (void) [SWS_Rte_02569] e deve obrigatoriamente retornar dentro de um tempo de execução finito sem loop infinito [SWS_Rte_02585].

A função pode ser chamada em cada Core exatamente uma vez pelo EcuStateManager a partir de um contexto de OS confiável, após todos os módulos de Basic Software necessários pela RTE terem sido inicializados [SWS_Rte_CONSTR_09035]. A chamada é executada de forma independente em cada Core [SWS_Rte_07615] e realiza as atividades de inicialização específicas de partição para todas as partições atribuídas a este Core [SWS_Rte_07616].

Durante o fluxo, a RTE inicializa as variáveis alocadas para blocos de RAM dependendo da estratégia configurada [SWS_Rte_07632]. Após as inicializações de variáveis, mas ainda antes da execução de Runnables, a RTE chama as funções de inicialização Rte_Rips_Rte_Start de todos os RTE Implementation Plug-Ins participantes [SWS_Rte_80052]. Em seguida, a RTE ativa uma única vez todos os Runnables disparados por InitEvent [SWS_Rte_06761] e inicia a transição para os modos iniciais [SWS_Rte_06766]. Caso a API Rte_StartTiming não exista, Rte_Start também inicia a ativação de Runnables disparados por TimingEvent [SWS_Rte_07575] ou BackgroundEvent [SWS_Rte_07178].

Para o tratamento de erros, a RTE ou o SchM, com RteDevErrorDetectUninit ativado, reporta o erro RTE_E_UNINIT (0x07) se Rte_Start for chamado antes de SchM_Init [SWS_Rte_07683]. Antes da execução de Rte_Start, APIs de tempo de execução da RTE não devem ser chamadas, pois caso contrário isso também leva a RTE_E_UNINIT [SWS_Rte_07682]; Rte_SetMirror, por outro lado, já pode ser chamado antes de Rte_Start [SWS_Rte_07319].

Esta nota de uso foi gerada automaticamente com base na especificação AUTOSAR.

função Rte_Stop [SWS_Rte_01262] 📄 PDF

Std_ReturnType Rte_Stop (void);

Rte_Stop é utilizado para finalize o RTE no core ele é chamada. Este serviço liberta todos sistema e comunicação recursos alocado pelo RTE em que core.

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 7279f2fa5c32 Procedência

A função Rte_Stop ([SWS_Rte_02570]) é gerada em qualquer configuração ([SWS_Rte_01310]) e serve para finalizar a RTE no Core executor ([SWS_Rte_01262]). Com isso, são liberados todos os recursos de sistema e de comunicação alocados pela RTE neste Core ([SWS_Rte_01262]). A chamada síncrona tem retorno garantido dentro de um tempo de execução finito ([SWS_Rte_02584]).

No sistema global, Rte_Stop deve ser chamada pelo EcuStateManager antes que os módulos de Basic Software necessários pela RTE sejam desativados ([SWS_Rte_CONSTR_09038]). Durante o fluxo, a RTE chama as funções de parada Rte_Rips_Rte_Stop de todos os RTE-Implementation-Plug-Ins participantes ([SWS_Rte_80053]), que devem disponibilizar essas interfaces de ciclo de vida ([SWS_Rte_70047]). Apenas após a conclusão total de Rte_Stop é que SchM_Deinit pode ser executado ([SWS_Rte_CONSTR_09056]).

Após a chamada de Rte_Stop em um Core, a RTE não ativará, iniciará ou liberará mais nenhuma instância de RunnableEntity ali ([SWS_Rte_02538]). Sem ser afetado por isso, Rte_GetMirror continua chamável, desde que o sistema operacional subjacente esteja ativo ([SWS_Rte_07350]).

Em caso de erro, a função retorna RTE_E_LIMIT caso um limite interno tenha sido excedido ou a alocação de um recurso necessário falhe ([SWS_Rte_01262]). Se RteDevErrorDetectUninit estiver ativado, a RTE reporta o erro RTE_E_UNINIT (0x07) se APIs inválidas forem chamadas após Rte_Stop ([SWS_Rte_07682]).

Utilização e semântica

A função SchM_Init aloca e inicializa os recursos de sistema utilizados pelo Basic Software Scheduler (SchM) da RTE no Core chamador ([SWS_Rte_08060]). Durante o fluxo de inicialização, SchM_Init executa as seguintes etapas:

  • Inicia para cada instância de máquina de modos pertencente ao Basic Software Scheduler a transição para o modo inicial ([SWS_Rte_07532]).

O tipo de dados Rte_Rips_SwitchNotificationStatusType ([SWS_Rte_91113]) é baseado em uint8 e é disponibilizado por meio de Rte_Type.h. Ele serve para sinalizar o status de operações de enqueue e dequeue em uma fila de modos (Mode Queue) no contexto de RTE Implementation Plug-Ins.
