EcuM_CheckRamHash função

Este callout é intended para fornecer um RAM integridade test. o goal de este test é para garantir que depois de um longo SLEEP duração, RAM conteúdos é ainda consistente. o verificar não necessitar para ser exhaustive desde este would consume quite algum processamento tempo durante wakeups. A bem designed verificar irá execute quickly e detect RAM integridade defects com um suficiente probability. este specification não make qualquer suposição sobre o algoritmo escolhido para um particular ECU. o areas de RAM que será verificado têm para ser escolhido carefully. ele depende no verificar algoritmo itself e o tarefa estrutura. pilha conteúdos do tarefa que executa o RAM verificar e.g. muito likely não pode ser verificado. ele é good practice para têm o hash generation e checking no mesmo tarefa e que este tarefa não é preemptible e que lá é apenas little activity entre hash generation e hash verificar. o RAM verificar itself é fornecido pelo sistema designer. em caso de applied multi core e existence de Satellite-Ecu M(s): Esta API será chamado pelo mestre-EcuM apenas.

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation função

Este callout é chamada por o EcuM para validar um despertar fonte. se um válido despertar foi detected, ele deve ser reportado para EcuM via EcuM_ValidateWakeupEvent().

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup função

Este callout é chamada por o EcuM para poll um despertar fonte. ele deve também ser chamado pelo ISR de um despertar fonte para definir acima o PLL e verificar outro despertar sources que pode ser ligado ao mesmo interrupção.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);

EcuM_DeterminePbConfiguration função

Este callout deve evaluate algum condição, like porta pino ou NVRAM valor, para determine que post-build configuração deve ser utilizado no remainder do arranque processo. ele deve carregar este dados de configuração em um piece de memória que é accessible por todos BSW módulos e deve devolver um ponteiro para o EcuM post-build configuração como um base para todos BSW módulo post-build configrations.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);

EcuM_EnableWakeupSources função

o ECU gestor módulo chamadas EcuM_EnableWakeupSource para permitir o sistema designer para notificar despertar sources definido no wakeupSource campo de bits que SLEEP será entered e para adjust seu fonte em conformidade.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup função

Esta API é chamada por qualquer SW módulo whose despertar fonte é verificado asynchronously (e.g. assíncrono Can Trcv controlador) e o verificar do despertar devolve um negativo resultado (nenhum despertar por este fonte). o API cancela o CheckWakeupTimer para o WakeupSource. se o correponding CheckWakeupTimer é cancelado o verificar de este despertar fonte é finalizado.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook função

o ECU State Manager irá chamada o erro hook se o erro codes "ECUM_E_RAM_CHECK_ FAILED" ou "ECUM_E_CONFIGURATION_DATA_INCONSISTENT" occur. em este situation ele não é possível para continuar processamento e o ECU deve ser parado. o integrator pode choose o modality how o ECU é parado, i.e. reinicializado, halt, restart, safe estado etc.

void EcuM_ErrorHook (uint16 reason);

Arquitetura de sistema e papel do cluster de módulos

O cluster "System Services" engloba os módulos que suportam a inicialização, os modos de operação, o sleep/shutdown e a monitoração do fluxo de execução do programa de uma ECU da Classic Platform. O ECU State Manager é o serviço de sistema que estabelece o estado final de hardware após o shutdown do OS (SWS EcuM p. 82, [SWS_EcuM_04020]). Os quatro módulos possuem papéis claramente separados:

  • BswM arbitra indicações de modo recebidas ([SWS_BswM_00035]). Regras conectam logicamente ModeRequestPorts e disparam listas de ações True ou False (Mode Management Guide p. 32). As ações são executadas exclusivamente no contexto de uma lista de ações ([SWS_BswM_00147]).
  • EcuM inicializa o BSW, inicia e encerra o OS e gerencia os estados das fontes de despertar ([SWS_EcuM_02811], [SWS_EcuM_04091]). Ele não possui uma máquina de estados própria. Ele recebe as transições de estado do BswM (SWS EcuM p. 99, [SWS_EcuM_04116]).
  • WdgM monitora Supervised Entities por meio de checkpoints ([SWS_WdgM_00263]) e gera a partir disso um Global Supervision Status ([SWS_WdgM_00360]). Ele define os modos do watchdog via WdgIf_SetMode ([SWS_WdgM_00186]).
  • Wdg controla o hardware de watchdog interno ou externo ([SWS_Wdg_00161], [SWS_Wdg_00076]). Ele aciona o hardware enquanto a condição de disparo for válida ([SWS_Wdg_00144]).

Diagrama de contexto: O diagrama de contexto mostra o BswM como tomador de decisão sobre modos, o EcuM como executor das sequências de ciclo de vida e a cadeia de monitoramento WdgM → WdgIf → Wdg → hardware. Fontes: SWS EcuM p. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Interação e caminhos de interação

EcuM ↔ BswM (ECU Mode Handling): Este caminho está ativo se EcuMModeHandling estiver configurado ([SWS_EcuM_04115]). SW-Cs solicitam RUN e POST_RUN via EcuM_RequestRUN ou EcuM_RequestPOST_RUN e os liberam novamente ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). O EcuM reporta o resultado da arbitragem via BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). O BswM define em seguida o estado por meio de EcuM_SetState ([SWS_EcuM_04122]). Assim que o RTE confirmar a transição, o EcuM reporta o estado de volta via BswM_EcuM_CurrentState ([SWS_EcuM_04143], [SWS_BswM_91003]).

Caminho de despertar: Os drivers reportam despertares via EcuM_SetWakeupEvent, que marca o evento como pendente ([SWS_EcuM_01117]). Se uma validação for necessária, o EcuM inicia o protocolo de validação ([SWS_EcuM_02975]). A validação é realizada por exatamente um módulo BSW (SWS EcuM p. 69). Sua chamada a EcuM_ValidateWakeupEvent notifica o BswM e o ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). Cada mudança de estado de uma fonte de despertar é reportada ao BswM como uma solicitação de modo ([SWS_EcuM_04003]).

Diagrama de estados: O diagrama de estados mostra os ciclos de vida de uma fonte de despertar (NONE, PENDING, VALIDATED, EXPIRED) e a mensagem para o BswM ao entrar em cada estado. Fontes: [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM p. 64

WdgM → Wdg: Wdg_SetTriggerCondition recebe um timeout em milissegundos e o converte internamente em um valor de contador, levando em consideração o modo atual ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). A rotina de serviço do driver comporta-se da seguinte forma:

  • Se o contador for maior que zero, ela o decrementa e dispara o hardware ([SWS_Wdg_00134]).
  • Se for zero, ela não dispara mais e o watchdog expira ([SWS_Wdg_00135]).

Interpretação: É provável que o WdgIf encaminhe o modo e a condição de disparo para a respectiva instância do Wdg endereçada. Múltiplas instâncias possuem nomes unívocos ([SWS_Wdg_00172]).

EcuM → WdgM (Reset): WdgM_PerformReset é um destino obrigatório de reset ([SWS_EcuM_04005], [SWS_EcuM_04044]). Ele define a condição de disparo de todos os drivers como 0, e os watchdogs de hardware acionam, assim, um reset ([SWS_WdgM_00264], SWS WdgM p. 82). Como causa de shutdown, ECUM_CAUSE_WDGM está disponível ([SWS_EcuM_04045]).

Sincronização, reentrância e contextos de tarefas

BswM_MainFunction: Ela avalia todas as regras que usam uma solicitação com BSWM_DEFERRED ([SWS_BswM_00075]). Temporizadores do BswM são sempre tratados de forma diferida (deferred) ([SWS_BswM_00220]). Por outro lado, solicitações com "immediate" são avaliadas imediatamente (Mode Management Guide p. 32).

EcuM_MainFunction: Ela é executada em todas as instâncias do EcuM ([SWS_EcuM_04011]). Ela monitora os timeouts de validação ([SWS_EcuM_04082]) e valida candidatos a despertar após o WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction: Ela inicia o monitoramento na primeira chamada após WdgM_Init ([SWS_WdgM_00406]) e calcula em seguida o Global Supervision Status em cada período (SWS WdgM p. 34).

Contexto de interrupção: Os serviços de despertar podem ser chamados a partir de contextos de interrupção, com OS e sem OS ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). No entanto, eles são especificados como "Non-Reentrant, Non-Interruptible" ([SWS_EcuM_02826], [SWS_EcuM_02828]). Uma exceção é EcuM_ValidateWakeupEvent: ela é reentrante e pode ser chamada a partir de contextos de interrupção e de tarefa ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Reentrância de WdgM e Wdg:

  • WdgM_SetMode, WdgM_DeInit e Wdg_SetTriggerCondition não são reentrantes ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • WdgM_GetMode ainda fornece o modo antigo durante uma mudança de modo em andamento ([SWS_WdgM_00168], SWS WdgM p. 77).
  • O Wdg desabilita interrupções para consistência de dados apenas por meio dos mecanismos de BSW previstos ([SWS_Wdg_00040]).

Multicore: Uma instância separada do EcuM é executada em cada Core. O EcuM mestre inicia os demais Cores (SWS EcuM p. 71). Disso decorrem estas obrigações:

  • Cada instância processa os despertares de seu próprio Core ([SWS_EcuM_04012]).
  • Todos os BswM locais do core são inicializados ([SWS_EcuM_04014]).
  • Um recurso RES_AUTOSAR_ECUM é reservado por Core ([SWS_EcuM_03010]).
  • As APIs C estão disponíveis em cada partição na qual um EcuM é executado ([SWS_EcuM_04095]).

O BswM é condicionalmente reentrante para sistemas multipartição ([SWS_BswM_00002]).

Ciclos de vida e modos operacionais

Inicialização (StartPreOS): EcuM_Init executa a sequência StartPreOS ([SWS_EcuM_02684]). Ela engloba:

  • os blocos de inicialização 0 e 1 na ordem configurada ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • a seleção da configuração pós-build ([SWS_EcuM_02906]),
  • a verificação de consistência de todas as configurações pós-build antes da primeira inicialização do BSW ([SWS_EcuM_02796]).

De acordo com a descrição da estrutura, Wdg_Init pertence às funções de inicialização usadas pelo EcuM (SWS EcuM p. 34). Wdg_Init define o modo padrão e o timeout ([SWS_Wdg_00001]).

Inicialização (StartPostOS): EcuM_StartupTwo é executado em uma tarefa iniciada por StartOS ([SWS_EcuM_02806]). Ele inicia o SchM e inicializa o BswM ([SWS_EcuM_02932]). BswM_Init requer apenas um OS e um SchM inicializados (SWS BswM p. 69). O BswM pode inicializar drivers adicionais na fase UP, por exemplo, via EcuM_AL_DriverInitBswM_<x> (SWS EcuM p. 46, [SWS_EcuM_04114]).

Diagrama de sequência: O diagrama de sequência mostra a ordem de StartPreOS e StartPostOS no Core mestre. Fontes: [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM p. 82, SWS EcuM p. 42

Sleep: Antes de EcuM_GoDownHaltPoll, tipicamente o BswM deve ter selecionado um destino SLEEP (SWS EcuM p. 54, [SWS_EcuM_91002]). O fluxo:

  1. GoSleep ativa as fontes de despertar; o OS permanece ativo durante o processo ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. Depois segue, dependendo do modo de suspensão, Halt com hash de RAM ([SWS_EcuM_02863]) ou Poll ([SWS_EcuM_02962]). Nenhum despertar pode ser perdido durante isso ([SWS_EcuM_02188]).
  3. Um despertar conduz à sequência WakeupRestart com reinicialização de drivers ([SWS_EcuM_02963], [SWS_EcuM_02923]).

Na R20-11, o callout de polling chama-se EcuM_CheckWakeup ([SWS_EcuM_02929]). Somente a partir da R21-11 ele passa a se chamar EcuM_CheckWakeupHook (SWS EcuM p. 145).

Watchdog no Sleep: Antes do sleep, WdgM_DeInit comuta para um modo de sleep com condições de disparo toleráveis e interrompe a monitoração (SWS WdgM p. 59, [SWS_WdgM_00407]). A descrição da estrutura do EcuM, contudo, cita apenas WdgM_PerformReset como dependência do WdgM. Portanto, a chamada de WdgM_DeInit ocorre presumivelmente por meio de uma ação do BswM ou código de integração.

Diagrama de sequência: O diagrama de sequência mostra a fase SLEEP com Halt: GoSleep, hash de RAM, despertar e WakeupRestart. Fontes: SWS EcuM p. 54, SWS EcuM p. 55, SWS EcuM p. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown: O fluxo:

  1. OffPreOS desinicializa o BswM e o SchM (SWS EcuM p. 90). Depois disso, o BswM não processa mais nenhum modo ([SWS_BswM_00120]).
  2. Como última atividade, o EcuM chama ShutdownOS ([SWS_EcuM_02952]). O hook de shutdown chama EcuM_Shutdown ([SWS_EcuM_02953]).
  3. Por fim, seguem EcuM_AL_Reset ou EcuM_AL_SwitchOff ([SWS_EcuM_04074], [SWS_EcuM_04075]).

As fontes de despertar devem ser limpas antes de Dem_Shutdown e NvM_WriteAll por meio de user callouts do BswM (SWS EcuM p. 124, [SWS_BswM_00054]). Um despertar durante o shutdown leva à reinicialização após a sua conclusão ([SWS_EcuM_02756]). O Wdg não possui interface própria de desinicialização ([SWS_Wdg_00031]).

Tratamento de erros, rastreamento pelo DET e degradação

Erros de desenvolvimento (DET):

  • O BswM ignora indicações antes da inicialização e reporta BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). Ele reporta ações com falha como erro de tempo de execução BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • O EcuM reporta solicitações duplicadas de RUN e liberações inadequadas ([SWS_EcuM_03024], [SWS_EcuM_03023]), bem como fontes de despertar desconhecidas ([SWS_EcuM_02867]).
  • O WdgM e o Wdg definem códigos de erro próprios ([SWS_WdgM_00004], [SWS_Wdg_00010]). Uma falha em WdgIf_SetMode é reportada pelo WdgM como WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Erros irrecuperáveis: O EcuM encaminha estes erros para EcuM_ErrorHook ([SWS_EcuM_04033]). Exemplos são dados de configuração inconsistentes ou uma verificação de RAM com falha ([SWS_EcuM_91003]). O EcuM ignora erros retornados pelas funções de inicialização durante a inicialização ([SWS_EcuM_02980]).

Degradação da monitoração: O status global inicia como WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Trocas de modo são permitidas apenas nos estados OK e FAILED ([SWS_WdgM_00145]). A desativação do watchdog pode ser proibida por configuração ([SWS_WdgM_00031]). A escalada ocorre da seguinte forma:

  1. No estado EXPIRED, a reação de erro é adiada por uma tolerância configurável (SWS WdgM p. 34).
  2. No estado STOPPED, o WdgM reporta WDGM_E_SUPERVISION e segue-se um reset de watchdog ([SWS_WdgM_00375]).
  3. Uma troca de modo com falha também leva a STOPPED (SWS WdgM p. 57).

Diagnóstico após o reset: O primeiro SEID a expirar é armazenado duplamente invertido na RAM não inicializada. Ele já pode ser lido antes de WdgM_Init ([SWS_WdgM_00348], [SWS_WdgM_00349]). O WdgM reporta mudanças de status via Mode-Ports ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset ainda existe na R20-11 ([SWS_BswM_00157]), mas torna-se obsoleto a partir da R21-11 (SWS BswM p. 2).

Erros de driver e proteção final: O Wdg reporta os erros de produção WDG_E_MODE_FAILED e WDG_E_DISABLE_REJECTED ao DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). Se EcuM_AL_SwitchOff travar em um deadlock, o watchdog de hardware reinicializa a ECU (SWS EcuM p. 141).
