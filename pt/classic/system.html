EcuM_CheckRamHash função

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

uint8 EcuM_CheckRamHash (void);

Coordena os ciclos de vida de ECUs, arbitra modos de operação e garante o monitoramento funcional por watchdog.

O cluster de módulos System Services controla o ciclo de vida da ECU desde as fases iniciais de boot até o shutdown, arbitra modos de operação e garante o monitoramento da execução de programas para atender aos requisitos de segurança funcional SafetyConceptStatusReport p. 15. O ECU State Manager reúne requisições de modo e delega decisões de estado ao BSW Mode Manager, enquanto o Watchdog Manager monitora a execução e aciona o Watchdog Driver SWS_ECUStateManager p. 103. Em caso de violações graves de fluxo de controle, o cluster interrompe o acionamento do watchdog e força um reset de hardware seguro [SWS_WdgM_00232].

O cluster de módulos System Services controla o ciclo de vida da ECU, comuta modos de operação e assegura o monitoramento da execução de programas em conformidade com os requisitos de segurança funcional SafetyConceptStatusReport p. 15. O BSW Mode Manager (BswM) atua como instância central de decisão, enquanto o ECU State Manager (EcuM) coordena fases específicas de hardware como StartPreOS, Sleep e Shutdown e propaga requisições ao BswM SWS_ECUStateManager p. 103. O monitoramento da execução de programas é implementado pelo Watchdog Manager (WdgM), que executa monitoramentos de alive, deadline e fluxo de controle e dispara o hardware através do Watchdog Driver (Wdg) [SWS_Wdg_00155].

Diagrama de contexto: Arquitetura e colaboração dos System Services com BSW, RTE e hardware. Fontes: SWS_ECUStateManager p. 34, AUTOSAR_EXP_ModeManagementGuide p. 61.

Durante a operação contínua, acumulam-se requisições como RUN ou POST_RUN no EcuM, que as reporta de forma agregada ao BswM [SWS_BswM_91004]. Após a avaliação das regras configuradas, o BswM define o estado via EcuM_SetState, o que é informado aos componentes através da RTE [SWS_EcuM_04116]. Em fases de suspensão, os eventos de wakeup são processados através de uma máquina de estados padronizada (NONE, PENDING, VALIDATED, EXPIRED) e sinalizados de forma síncrona ao BswM [SWS_BswM_00131].

Diagrama de sequência: Caminho de interação do manuseio de modos de ECU entre SW-C, EcuM, BswM e RTE. Fontes: SWS_ECUStateManager p. 103, ModeManagementGuide p. 34.

Se ocorrer um erro crítico de monitoramento no WdgM, o status de monitoramento muda para WDGM_GLOBAL_STATUS_STOPPED, após o que o disparo do watchdog é interrompido e o hardware dispara um reset de sistema [SWS_WdgM_00232]. Erros de configuração ou de chamada são reportados pelo cluster de forma padronizada ao Default Error Tracer (Det) [SWS_EcuM_03026].

1. Arquitetura de sistema & papel do cluster de módulos

O cluster de módulos System Services constitui a espinha dorsal funcional da AUTOSAR Classic Platform. Ele compreende o BSW Mode Manager (BswM), o ECU State Manager (EcuM), o Watchdog Manager (WdgM) e o Watchdog Driver (Wdg) de baixo nível SWS_ECUStateManager p. 35. Juntos, esses módulos controlam o ciclo de vida integral da ECU, coordenam modos operacionais de baixo nível e aplicacionais, e asseguram o monitoramento temporal e lógico da execução de programas para garantir a segurança funcional SafetyConceptStatusReport p. 15.

Na arquitetura em camadas do AUTOSAR, BswM, EcuM e WdgM estão localizados na camada de System Services acima das camadas de abstração e de drivers, enquanto o Watchdog Driver (Wdg), como parte do Microcontroller Abstraction Layer (MCAL), atende aos registradores de hardware do temporizador de watchdog [SWS_Wdg_00106]. O EcuM atua, em sua variante flexível (EcuM Flex), como elemento de ligação com o hardware para sequências iniciais de inicialização (boot) e sequências finais de desligamento antes e depois do início do sistema operacional, respectivamente. Ele não possui mais uma máquina de estados complexa própria para modos de aplicação, delegando a arbitragem de modo ao BswM SWS_ECUStateManager p. 103. Padrões externos de diagnóstico como UDS (ISO 14229) e protocolos de gerenciamento de rede acoplam-se diretamente à avaliação de regras do BswM por meio de interfaces BSW definidas (como o serviço 0x28 CommunicationControl via Dcm) [SWS_BswM_00048].

Diagrama de contexto: Arquitetura e colaboração dos System Services com BSW, RTE e hardware. Fontes: SWS_ECUStateManager p. 34, AUTOSAR_EXP_ModeManagementGuide p. 61.

2. Interação & caminhos de interação entre os módulos

A interação dentro do cluster caracteriza-se por relações de controle e notificação claramente delimitadas. No âmbito do ECU Mode Handling, o EcuM recebe requisições de estados como RUN ou POST_RUN a partir de componentes de software (SW-Cs) e encaminha o resultado de arbitragem agregado via [SWS_BswM_91004] ao BswM ModeManagementGuide p. 34. Como o EcuM não toma decisões de transição próprias, o BswM avalia regras lógicas configuradas e instrui o estado de destino de forma síncrona via EcuM_SetState para [SWS_EcuM_04116]. Em seguida, o EcuM reflete esse estado para a aplicação por meio da RTE e confirma o status de execução atual para o BswM via BswM_EcuM_CurrentState [SWS_BswM_91003].

Um caminho de interação paralelo conecta BswM, WdgM e Wdg. Componentes de software e módulos BSW reportam o alcance de checkpoints definidos ao WdgM, que a partir disso determina o status de monitoramento local e global SWS_WatchdogManager p. 51. O WdgM disponibiliza alterações de estado do monitoramento local por meio de portas de modo fornecidas [SWS_WdgM_00148]. Dependendo do estado do sistema de nível superior, o BswM comuta o modo de operação do Watchdog Manager via WdgM_SetMode [SWS_WdgM_00154]. O WdgM configura em seguida o Watchdog Driver (Wdg) por meio da Watchdog Interface (WdgIf) e controla o disparo (triggering) de hardware via Wdg_SetTriggerCondition [SWS_Wdg_00155].

3. Sincronização, reentrância e contextos de tarefas

A execução dos System Services distribui-se de forma determinística por níveis de tarefas periódicas, callbacks assíncronos e contextos de interrupção. A carga principal periódica do gerenciamento de modo é suportada por BswM_MainFunction, que é chamada no contexto de uma tarefa de OS pelo BSW Scheduler (SchM) e processa todas as regras a serem avaliadas de forma postergada [SWS_BswM_00053]. Se ocorrerem eventos com avaliação imediata de regras, estes são processados diretamente de forma síncrona no contexto da indicação BSW ou API de SW-C chamadora ModemanagementGuide p. 31.

Em sistemas multicore, a padronização exige uma alocação estrita de recursos. BswM_Init foi projetado para ser condicionalmente reentrante, a fim de permitir instanciações separadas por partição ou núcleo de processador [SWS_BswM_00002]. Durante as fases de repouso e retenção, o EcuM reserva recursos de OS próprios do núcleo (RES_AUTOSAR_ECUM_<core#>) para assegurar a sincronização entre os núcleos mestre e escravo [SWS_EcuM_03010]. A inicialização de drivers via EcuM_AL_DriverInitZero e EcuM_AL_DriverInitOne é chamada separadamente em cada núcleo e inicializa exclusivamente módulos MCAL locais do núcleo [SWS_EcuM_04145]. A limpeza de eventos de despertar via EcuM_ClearWakeupEvent é explicitamente não interrompível e pode ocorrer tanto a partir de contextos de tarefa quanto de interrupção [SWS_EcuM_02807].

4. Ciclos de vida típicos e modos de operação

O ciclo de vida de uma ECU divide-se normativamente nas fases STARTUP, UP, SHUTDOWN e SLEEP [SWS_EcuM_91005]. A fase STARTUP inicia antes da inicialização do sistema operacional na sequência StartPreOS com a chamada de EcuM_Init, a avaliação da causa de reset e o carregamento da configuração post-build via EcuM_DeterminePbConfiguration AUTOSAR_SWS_ECUStateManager p. 38. Após a transferência do controle para o sistema operacional via StartOS, o EcuM inicializa em StartPostOS o SchM bem como o BswM [SWS_EcuM_02934]. Em seguida, o BswM assume o controle e inicializa os módulos BSW restantes, bem como a aplicação.

Na operação contínua (fase UP), EcuM e BswM gerenciam os modos RUN e POST_RUN, bem como o serviço opcional de Alarm Clock SWS_ECUStateManager p. 75. Em uma transição para o estado de repouso (SLEEP), o cluster diferencia estruturalmente entre HALT (para a CPU) e POLL (clock de CPU reduzido) SWS_ECUStateManager p. 54. Previamente, a chamada WdgM_DeInit desinicializa o Watchdog Manager e ajusta os timeouts de disparo para evitar resets indesejados durante o desligamento [SWS_WdgM_00261]. Na sequência de polling, o EcuM bloqueia em um loop de verificação com chamadas periódicas de EcuM_SleepActivity e EcuM_CheckWakeupHook até que um evento de despertar seja detectado [SWS_EcuM_03020].

Os eventos de despertar detectados passam por um gerenciamento de estados estrito de ECUM_WKSTATUS_NONE passando por PENDING até VALIDATED ou EXPIRED [SWS_EcuM_04091]. O EcuM sinaliza cada mudança de status de forma síncrona por meio de BswM_EcuM_CurrentWakeup para o BswM [SWS_BswM_00131]. A validação de despertar protege contra perturbações transitórias de barramento e monitora a janela de tempo por meio de temporizadores de validação configuráveis [SWS_EcuM_04004]. Se o ciclo de vida terminar em SHUTDOWN, OffPreOS desativa o BswM e SchM antes de OffPostOS reiniciar ou desenergizar a ECU por meio de callouts de integração como EcuM_AL_Reset ou EcuM_AL_SwitchOff AUTOSAR_SWS_ECUStateManager p. 49.

5. Tratamento de erros, rastreamento de DET e degradação

Para a detecção de erros de tempo de execução e de configuração, o cluster integra mecanismos padronizados de notificação para o Default Error Tracer (Det). Se uma entidade tentar emitir uma liberação via EcuM_ReleasePOST_RUN sem requisição prévia, o EcuM reporta o erro de desenvolvimento ECUM_E_MISMATCHED_RUN_RELEASE para o Det [SWS_EcuM_03026]. Requisições múltiplas do mesmo usuário são registradas com ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03025]. Da mesma forma, o WdgM monitora chamadas de API em estado não inicializado e reporta WDGM_E_UNINIT caso serviços sejam chamados antes da conclusão da inicialização [SWS_WdgM_00288].

O monitoramento de segurança baseia-se no controle funcional em três etapas do WdgM (Alive Supervision, Deadline Supervision e monitoramento lógico de fluxo de controle) SafetyConceptStatusReport p. 47. Se uma falha de monitoramento levar à violação de tolerâncias a falhas, o status de monitoramento global transita de WDGM_GLOBAL_STATUS_OK passando por FAILED para WDGM_GLOBAL_STATUS_EXPIRED e finalmente STOPPED [SWS_WdgM_00387]. Nesse estado, o WdgM define a condição de disparo para todos os drivers de watchdog para 0, fazendo com que o watchdog de hardware reinicie imediatamente o microcontrolador [SWS_WdgM_00232]. Para resets de emergência controlados, o WdgM disponibiliza o serviço WdgM_PerformReset, que interrompe o pós-disparo contínuo e força o reset de hardware [SWS_WdgM_00264]. Para assegurar após fases de repouso mais longas, o EcuM verifica adicionalmente a consistência da memória volátil por meio de EcuM_CheckRamHash, a fim de interceptar reinicializações com falha no caso de corrupção de RAM [SWS_EcuM_02921].
