Can_ConfigType tipo

Este é o tipo do externo estrutura de dados containing o overall inicialização dados para o CAN controlador e SFR definições affecting todos controladores. Furthermore ele contém ponteiros para controlador configuração structures. os conteúdos do initializ ation estrutura de dados são CAN hardware específico.

Can_ControllerStateType tipo

estados que são utilizados pelo vários controlador modo funções.

Can_ErrorStateType tipo

erro estados de um CAN controlador.

Can_ErrorType tipo

o enumeração representa um superset de CAN erro tipos que typical CAN HW é able para reportar. que means não todos CAN HW será able para suporte o completo definir.

Can_HwHandleType tipo

representa o hardware objeto trata de um CAN hardware unidade. para CAN hardware unidades com mais de 255 HW objetos use extended intervalo.

Can_HwType tipo

Este tipo define uma estrutura de dados que clearly fornece um hardware objeto identificador incluindo seu correspondente CAN controlador e portanto Can Drv bem como o específico Can Id.

Can_IdType tipo

representa o identificador de um L - PDU. o dois a maioria significant bits specify a trama tipo: 00 CAN mensagem com padrão CAN ID 01 CAN FD trama com padrão CAN ID 10 CAN mensagem com Extended CAN ID 11 CAN FD trama com Extended CAN ID

Can_PduType tipo

Este tipo unites Pdu Id (sw Pdu identificador), Sdu comprimento (comprimento), Sdu dados (sdu), e Can Id (id) para qualquer CAN L - SDU.

Arquitetura de sistema e papel do cluster de módulos

O cluster "CAN Communication" abrange a pilha CAN da Classic Platform, desde o hardware do controlador até a camada de transporte.

  • Can (CAN Driver): encapsula o hardware do controlador. Ele grava L-PDUs em objetos de hardware com Can_Write [SWS_Can_00233]. Nessa operação, é passada uma estrutura Can_PduType composta por swPduHandle, comprimento, dados e ID CAN [SWS_Can_00415].
  • CanIf (CAN Interface): abstrai múltiplas instâncias de driver por meio de seus próprios ControllerIds e TransceiverIds [SWS_CANIF_00653] [SWS_CANIF_00655].

As camadas superiores não acessam nem os buffers de recepção do driver nem os buffers de transmissão do CanIf CanIf p. 48. O próprio CanIf acessa buffers de hardware exclusivamente por meio de serviços do driver [SWS_CANIF_00023].

O CAN Transceiver Driver (CanTrcv) controla componentes de transceptor externos. Para cada tipo de hardware, há exatamente uma instância de driver para todos os transceptores do mesmo tipo [SWS_CanTrcv_00016]. Seu modelo de estados genérico desacopla o ComM e o EcuM de estados específicos do componente CanTrcv p. 19.

A CAN Transport Layer (CanTp) segue a ISO 15765-2, desde que a SWS não exclua nada [SWS_CanTp_00033]. Ela segmenta e remonta N-SDUs e gerencia múltiplas conexões simultaneamente [SWS_CanTp_00096], como uma requisição UDS e uma requisição OBD em paralelo CanTp p. 41.

Para cima, o CanIf conecta-se por meio de callbacks, cujo destino é definido por configuração CanIf p. 133. Destinos típicos são:

  • PduR_CanIfRxIndication [SWS_CANIF_00442]
  • CanTp_RxIndication [SWS_CANIF_00448]
  • CanSM_ControllerBusOff [SWS_CANIF_00559]
  • EcuM_ValidateWakeupEvent [SWS_CANIF_00563]

Diagrama de contexto: o CanIf intermedeia centralmente entre o Can ou CanTrcv e os usuários PduR, CanTp, CanSM e EcuM. Fontes: [SWS_CANIF_00318] [SWS_CANIF_00415] [SWS_CANIF_00358] [SWS_CANIF_00711] [SWS_CANIF_00448] CanIf p. 133

Interação e caminhos de interação

Caminho de transmissão: CanIf_Transmit [SWS_CANIF_00005] chama Can_Write com o HTH pertencente a TxPduId [SWS_CANIF_00318]. Se o driver retornar E_OK, o CanIf também retorna E_OK [SWS_CANIF_00162].

Se nenhum objeto de hardware estiver livre, Can_Write reporta CAN_BUSY [SWS_Can_00039]. Com o armazenamento em buffer ativado, o CanIf então armazena a L-PDU no CanIfTxBuffer [SWS_CANIF_00381] CanIf p. 138.

A cada confirmação de transmissão, ocorre a seguinte cadeia:

  1. O CanIf verifica os buffers do objeto de hardware liberado [SWS_CANIF_00386].
  2. Ele transmite a L-PDU em espera com a maior prioridade de acordo com [SWS_CANIF_00668] [SWS_CANIF_00070].
  3. Em E_OK, ele a remove do buffer antes mesmo que a confirmação retorne [SWS_CANIF_00183].
  4. Depois disso, o CanIf notifica o usuário via <User_TxConfirmation> [SWS_CANIF_00383]. Para o PduR, trata-se de PduR_CanIfTxConfirmation [SWS_CANIF_00439].

Os diagramas de releases mais recentes chamam isso aqui de LSduR_CanIfTxConfirmation CanIf p. 157. Para o R20-11, aplica-se a nomenclatura do PduR.

Diagrama de sequência: em CAN_BUSY, o CanIf armazena a L-PDU em buffer e a envia subsequentemente por prioridade na próxima confirmação de transmissão. Fontes: CanIf p. 138 CanIf p. 157 [SWS_CANIF_00381] [SWS_CANIF_00668] [SWS_CANIF_00183]

Caminho de recepção: o driver reporta cada L-PDU de recepção via CanIf_RxIndication [SWS_CANIF_00006]. O CanIf a processa nesta ordem CanIf p. 73:

  1. filtragem por software, caso configurada [SWS_CANIF_00389]
  2. verificação de Data Length [SWS_CANIF_00390]
  3. determinação da camada de destino [SWS_CANIF_00056] e chamada de seu serviço de recepção [SWS_CANIF_00135]

Opcionalmente, o CanIf também armazena a L-SDU para CanIf_ReadRxPduData [SWS_CANIF_00198] [SWS_CANIF_00199].

Caminho de transporte, envio: CanTp_Transmit [SWS_CanTp_00212] opera de forma assíncrona [SWS_CanTp_00176]. Se a N-SDU não couber em uma N-PDU, o CanTp inicia uma transmissão de múltiplos quadros [SWS_CanTp_00232]. Os dados úteis são obtidos por segmento com PduR_CanTpCopyTxData [SWS_CanTp_00086], uma vez que não os copia internamente [SWS_CanTp_00298].

Caminho de transporte, recepção: O CanTp reporta SF ou FF com PduR_CanTpStartOfReception [SWS_CanTp_00079]. O controle de fluxo orienta-se pelo buffer ali informado [SWS_CanTp_00080] [SWS_CanTp_00082].

No R20-11, o CanIf chama CanTp_TxConfirmation [SWS_CANIF_00550]. O trecho mais recente do documento indica o LSduR para isso CanTp p. 64.

Diagrama de sequência: Na recepção segmentada, o CanTp controla o transmissor via Flow Control, dependendo do buffer do PduR. Fontes: CanTp p. 37 [SWS_CanTp_00079] [SWS_CanTp_00222] [SWS_CanTp_00223] [SWS_CanTp_00084]

Controle do transceptor: O CanIf repassa serviços de transceptor diretamente:

  • CanIf_SetTrcvMode chama CanTrcv_SetOpMode [SWS_CANIF_00358].
  • CanIf_GetTrcvWakeupReason chama CanTrcv_GetBusWuReason [SWS_CANIF_00368].
  • CanIf_SetTrcvWakeupMode chama CanTrcv_SetWakeupMode [SWS_CANIF_00372].

Após a conclusão da mudança de modo, o CanTrcv reporta CanIf_TrcvModeIndication [SWS_CanTrcv_00158]. O CanIf repassa isso para CanSM_TransceiverModeIndication [SWS_CANIF_00712].

Sincronização, reentrância e contextos de tarefas

O Can opera controlado por interrupção ou por polling. Para o polling, existem funções cíclicas:

  • Can_MainFunction_Write para confirmações de envio [SWS_Can_00225]
  • Can_MainFunction_Read para a recepção [SWS_Can_00226]
  • Can_MainFunction_BusOff [SWS_Can_00227] e Can_MainFunction_Wakeup [SWS_Can_00228]
  • Can_MainFunction_Mode para mudanças de estado do controlador [SWS_Can_00368]

Os callbacks do CanIf são executados, portanto, dependendo da configuração, no contexto de interrupção ou no contexto de tarefa CanIf p. 155 CanIf p. 156. Também CanIf_CheckWakeup pode ser chamado em ambos os contextos CanIf p. 101.

O CanIf protege acessos preemptivos a recursos compartilhados entre si [SWS_CANIF_00064]. Isso se aplica especialmente a:

  • os buffers de envio [SWS_CANIF_00033]
  • o CAN-ID em CanIf_SetDynamicTxId, que pode ser interrompido por CanIf_Transmit [SWS_CANIF_00673]

A reentrância é definida por serviço: CanIf_RxIndication é reentrante [SWS_CANIF_00006], CanIf_SetPduMode não [SWS_CANIF_00008]. Para áreas de bloqueio curtas, o Can oferece Can_DisableControllerInterrupts [SWS_Can_00231] e Can_EnableControllerInterrupts [SWS_Can_00232]. Bloqueios múltiplos exigem igual quantidade de liberações Can p. 61.

No CanTp, os níveis de interrupção e de tarefa são separados:

  • CanTp_RxIndication e CanTp_TxConfirmation devem ser passíveis de chamada no contexto de interrupção [SWS_CanTp_00235] [SWS_CanTp_00236].
  • O monitoramento de tempo (N_As, N_Bs, N_Cs, N_Ar, N_Br, N_Cr, STmin) é assumido por CanTp_MainFunction [SWS_CanTp_00164]. O seu período é configurado [SWS_CanTp_00300].
  • Cada canal de conexão possui buffers, temporizadores e uma máquina de estados próprios [SWS_CanTp_00122].

O CanTrcv verifica ciclicamente, via CanTrcv_MainFunction, todos os barramentos em STANDBY e SLEEP quanto a eventos de wakeup [SWS_CanTrcv_00112].

Ciclos de vida e modos operacionais

Inicialização: O EcuM inicializa o CanIf, bem como o driver e o driver de transceptor separadamente. Em seguida, os controladores permanecem em STOPPED CanIf p. 40. É provável que Can_Init [SWS_Can_00223] e CanTrcv_Init [SWS_CanTrcv_00001] sejam executados antes de CanIf_Init [SWS_CANIF_00001] (interpretação). Está comprovado apenas que os drivers utilizados pelo CanTrcv devem estar prontos previamente [SWS_CanTrcv_00099].

Após a inicialização, aplicam-se estes estados:

  • O CanIf comuta todos os canais para CANIF_OFFLINE [SWS_CANIF_00864].
  • CanTrcv_Init coloca cada transceptor em SLEEP ou STANDBY, conforme a configuração [SWS_CanTrcv_00148].
  • O CanTp transita, após CanTp_Init, de CANTP_OFF para CANTP_ON [SWS_CanTp_00170] e segmenta apenas ali [SWS_CanTp_00238].

Modos do controlador: Os modos (Can_ControllerStateType [SWS_Can_91013]) são solicitados pelo CanSM via CanIf_SetControllerMode [SWS_CANIF_00003]. Em seguida, o CanIf chama Can_SetControllerMode [SWS_CANIF_00308]. A mudança ocorre de forma assíncrona e é reportada ao CanSM via CanIf_ControllerModeIndication [SWS_CANIF_00699] [SWS_CANIF_00711] CanIf p. 152.

Modos de PDU: Acima disso está o modo de canal CanIf_PduModeType [SWS_CANIF_00137]. Ele só pode ser alterado no estado STARTED [SWS_CANIF_00874]. Se um controlador mudar para STOPPED, aplica-se:

  • O CanIf limpa os buffers de envio correspondentes [SWS_CANIF_00485].
  • Envios pendentes são confirmados negativamente [SWS_CANIF_00739].
  • O canal é colocado em offline [SWS_CANIF_00866].

Sleep: CAN_CS_SLEEP define o canal como CANIF_OFFLINE [SWS_CANIF_00865]. Em Partial Networking, o CanIf ativa adicionalmente o PnTxFilter [SWS_CANIF_00749]. Ele permite a passagem apenas de PN-PDUs configuradas [SWS_CANIF_00750] e é desativado com a primeira confirmação de envio [SWS_CANIF_00751]. Antes do modo de baixo consumo de energia, o CanSM limpa a flag WUF para que nenhum quadro de wakeup seja perdido [SWS_CanTrcv_00194] CanTrcv p. 57.

Wakeup: CanIf_CheckWakeup consulta o driver ou transceptor [SWS_CANIF_00395]. Ele retorna E_OK assim que uma fonte responder positivamente [SWS_CANIF_00720]. A validação ocorre por meio de CanIf_CheckValidation [SWS_CANIF_00178] e <User_ValidateWakeupEvent> [SWS_CANIF_00179].

Shutdown: CanTp_Shutdown encerra todas as conexões e define o CanTp como CANTP_OFF [SWS_CanTp_00202]. As camadas superiores não são notificadas nesse processo [SWS_CanTp_00200]. Para a desinicialização, existem Can_DeInit [SWS_Can_91002], CanIf_DeInit [SWS_CANIF_91002] e CanTrcv_DeInit [SWS_CanTrcv_91001]. Pré-requisito: nenhum controlador está mais em STARTED e não há transmissões pendentes Can p. 59 CanIf p. 81. O transceptor retorna em seguida para NOT_ACTIVE [SWS_CanTrcv_91003].

Diagrama de estados: CanTrcv_Init conduz de NOT_ACTIVE para SLEEP ou STANDBY; CanTrcv_SetOpMode alterna entre os modos ativos, CanTrcv_DeInit conduz de volta para NOT_ACTIVE. Interpretação: A transição direta SLEEP→NORMAL segue a legenda do diagrama (1a–1c). O diagrama utiliza CANIF_TRCV_MODE_*; aqui constam os identificadores da R20-11. Fontes: CanTrcv p. 19 [SWS_CanTrcv_00148] [SWS_CanTrcv_00102] [SWS_CanTrcv_00120] [SWS_CanTrcv_00121] [SWS_CanTrcv_91003]

Tratamento de erros, rastreamento pelo DET e degradação

Erros de desenvolvimento: Todos os módulos os reportam ao DET. Os códigos de erro estão tabelados por módulo: Can [SWS_Can_91019], CanIf [SWS_CANIF_91006], CanTp [SWS_CanTp_00293], CanTrcv [SWS_CanTrcv_00050]. São típicas as verificações de IDs e ponteiros inválidos, por exemplo em CanIf_SetControllerMode [SWS_CANIF_00311] ou CanIf_RxIndication [SWS_CANIF_00416]. Antes da inicialização, os serviços do CanIf recusam a operação normal com E_NOT_OK [SWS_CANIF_00661]; o CanTp reporta CANTP_E_UNINIT [SWS_CanTp_00031] nesse caso.

Erros de tempo de execução vão para Det_ReportRuntimeError [SWS_CANIF_91007] [SWS_CanTrcv_91006]. Exemplos:

  • uma verificação de comprimento com falha [SWS_CANIF_00168]
  • envio em um canal offline [SWS_CANIF_00382]
  • falta de comunicação com o transceptor [SWS_CanTrcv_00114]

Erros de produção vão para o DEM. CanTrcv_MainFunctionDiagnostics reporta CANTRCV_E_BUS_ERROR como FAILED quando a flag BUSERR estiver ativa. Quando a flag for redefinida, ela reporta o evento correspondentemente [SWS_CanTrcv_00206] [SWS_CanTrcv_00227]. A função existe apenas em CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. O CanIf reporta erros de produção somente no evento acionador [SWS_CANIF_00223].

Security Events: O CanIf repassa falhas de barramento relevantes para a segurança ao IdsM [SWS_CANIF_00913]. As fontes são CanIf_ErrorNotification [SWS_CANIF_00915] [SWS_CANIF_00916] e eventos de Bus-Off [SWS_CANIF_00918].

Bus-Off e reinicialização: O Can reporta Bus-Off via CanIf_ControllerBusOff [SWS_CANIF_00218]. Em seguida, o CanIf define o canal como offline [SWS_CANIF_00866] e informa o CanSM [SWS_CANIF_00724] CanIf p. 154. O CanSM inicia a reinicialização com CanIf_SetControllerMode para STARTED CanIf p. 160. Com CanIf_GetTxConfirmationState, ele verifica se confirmações de envio foram recebidas desde o início [SWS_CANIF_00734] [SWS_CANIF_00740].

O estado de erro e os contadores de erros estão disponíveis por meio de serviços próprios:

  • CanIf_GetControllerErrorState [SWS_CANIF_91001] com Can_ErrorStateType [SWS_Can_91003]
  • as APIs de contadores [SWS_CANIF_91003] [SWS_CANIF_91004]

Degradação no CanTp: O CanTp aborta sessões com falha individualmente:

  • Em caso de timeout (N_As, N_Bs, N_Cr), ele encerra a sessão afetada e reporta E_NOT_OK ao PduR [SWS_CanTp_00310] [SWS_CanTp_00316] [SWS_CanTp_00313].
  • Após WFTmax quadros FC(WAIT), ele aborta a recepção [SWS_CanTp_00223].
  • Se CanIf_Transmit recusar, ele encerra a conexão em andamento [SWS_CanTp_00342] [SWS_CanTp_00343].

Outros canais permanecem inalterados nesse processo, visto que cada canal possui recursos próprios [SWS_CanTp_00122].
