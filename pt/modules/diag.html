Papel do Diagnostic Management entre o testador, a camada de transporte e as aplicações

O módulo diag descreve o Diagnostic Management (DM) da Adaptive Platform. O DM recebe requisições UDS por meio de uma Transport Protocol API C++ padronizada. A essa API podem ser conectadas diferentes camadas de transporte UDS. Atualmente, apenas a conexão Ethernet com DoIP obrigatório está descrita detalhadamente; protocolos proprietários são possíveis por meio da mesma API (SWS Diagnostics p. 94). O DM instancia para cada DiagnosticContributionSet uma Diagnostic Server instance independente com recursos próprios. Todas as instâncias compartilham a mesma camada de transporte UDS (SWS Diagnostics p. 112).

A lógica de negócios propriamente dita reside em Adaptive Applications. Elas disponibilizam interfaces de porta como SecurityAccess, ServiceValidation, Authentication ou FileTransferService. Essas interfaces consistem em Offer/StopOffer e métodos de callback (EXP SWArchitecture p. 158, [SWS_DM_00766], [SWS_DM_01336]). Para resets de ECU, o Diagnostic Server chama EcuResetRequest::RequestReset e ExecuteReset ([SWS_DM_01013], [SWS_DM_01014]). Em diagramas de arquitetura mais antigos (R21-11 a R23-11), o State Management está indicado como provedor dessa interface (EXP SWArchitecture p. 143).

Diagrama de contexto: O Diagnostic Server faz a mediação entre o plugin de transporte, aplicações, extensão DoIP e o provedor de EcuResetRequest. Fontes: SWS Diagnostics p. 112, EXP SWArchitecture p. 166, [SWS_DM_00309], [SWS_DM_00834], [SWS_DM_01366]

Ciclo de vida dos plugins de transporte UDS

Um plugin de transporte implementa UdsTransportProtocolHandler. Ele recebe na construção um UdsTransportProtocolHandlerID e uma referência ao UdsTransportProtocolMgr ([SWS_DM_09015], [SWS_DM_00325]). O DM controla o plugin em etapas fixas:

  1. Initialize fornece um InitializationResult ([SWS_DM_00319], [SWS_DM_09017]).
  2. Start inicia o processamento do protocolo ([SWS_DM_00322]).
  3. Stop solicita a finalização ([SWS_DM_00323]).
  4. O plugin confirma com HandlerStopped ([SWS_DM_00314]).

Essa ordem também é mostrada no diagrama de ciclo de vida de releases anteriores (SWS Diagnostics R19-11 p. 128).

Diagrama de estados: Um plugin de transporte passa por construção, inicialização, operação e parada confirmada. Fontes: [SWS_DM_09015], [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00314], SWS Diagnostics R19-11 p. 128

Para mensagens periódicas, GetPeriodicHandler fornece um UdsTransportProtocolPeriodicHandler. Este informa o número permitido de mensagens periódicas e a carga útil máxima por canal. Ele envia com PeriodicTransmit e confirma com PeriodicTransmitConfirmation ([SWS_DM_01068], [SWS_DM_01065], [SWS_DM_01066], [SWS_DM_01067], [SWS_DM_01069]).

Canais podem ser restaurados ao longo de uma reinicialização do DM. Para isso, o DM chama NotifyReestablishment(channelId) no novo handler. O plugin relata a restauração por meio de ChannelReestablished com um GlobalChannelIdentifier ([SWS_DM_00326], [SWS_DM_00313], [SWS_DM_09021], SWS Diagnostics R19-11 p. 134). Um caso de uso típico é ECUReset com respondAfterReset: a resposta positiva só é enviada após NotifyReestablishment ter sido chamado (SWS Diagnostics p. 150).

Diagrama de sequência: Um canal é restaurado ao longo de uma reinicialização do DM por uma nova instância de handler. Fontes: SWS Diagnostics R19-11 p. 134, [SWS_DM_00326], [SWS_DM_00313], SWS Diagnostics p. 150

Aceitação e processamento de uma requisição UDS

A recepção de uma requisição começa com IndicateMessage. A chamada passa o endereço de origem e de destino, o tipo de endereço e o canal. Retorna um std::pair composto por IndicationResult e UdsMessagePtr ([SWS_DM_00309], [SWS_DM_00384], [SWS_DM_00303]). Em caso de kIndicationOk, o DM disponibiliza uma UdsMessage com capacidade de pelo menos um byte, cujo payload é inicialmente vazio (SWS Diagnostics p. 98). O plugin preenche a mensagem a partir do SID e a encaminha com HandleMessage. Em qualquer outro resultado, o encaminhamento não ocorre ([SWS_DM_00311], SWS Diagnostics p. 100).

Motivos de rejeição:

  • Ocupado: Se o DM estiver ocupado com a mesma conversa de Tester Present, ele responderá com kIndicationOccupied. A exceção é um Tester Present funcional 0x3E 0x80 (SWS Diagnostics p. 99). O DM só reconhece essa exceção se o plugin fornecer os primeiros bytes em payloadInfo (SWS Diagnostics p. 94).
  • Endereço de destino desconhecido: O resultado é kIndicationUnknownTargetAddress (SWS Diagnostics p. 100).

Com cada indicação aceita, o temporizador S3 para (SWS Diagnostics p. 145).

Diagrama de atividades: O IndicationResult decide se o plugin preenche o payload e o encaminha. Fontes: SWS Diagnostics p. 98, SWS Diagnostics p. 99, SWS Diagnostics p. 100, [SWS_DM_00384]

A UdsMessage fornece os seguintes acessos: endereço de origem e de destino, tipo de endereço e payload a partir do SID. Por meio de AddMetaInfo, o plugin adiciona metadados específicos do canal ([SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299], [SWS_DM_00301], [SWS_DM_00302], EXP SWArchitecture p. 165). Dois clientes com o mesmo endereço de origem podem estar ativos em paralelo se forem provenientes de endpoints distinguíveis (SWS Diagnostics p. 98). O servidor mapeia cada requisição para uma Diagnostic Conversation (SWS Diagnostics p. 125). Em seguida, ele a valida de acordo com a ISO 14229-1 (SWS Diagnostics p. 136). Ele envia a resposta com Transmit; o plugin confirma com TransmitConfirmation e um TransmissionResult ([SWS_DM_00327], [SWS_DM_00312], [SWS_DM_00307]).

Diagrama de sequência: O caminho de uma requisição UDS do testador até a confirmação de envio, com processamento opcional na aplicação. Fontes: SWS Diagnostics R19-11 p. 130, [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00618], [SWS_DM_00327], [SWS_DM_00312]

Interfaces de aplicação: Disponibilização, callbacks e contexto de chamada

Interfaces de callback recebem na construção um InstanceSpecifier e um ConcurrencyType. Exemplos são GenericUDSService, GenericDataIdentifier e GenericRoutine ([SWS_DM_00616], [SWS_DM_00634], [SWS_DM_00552]). Com Offer, a aplicação ativa o encaminhamento de requisições; com StopOffer, desativa-o novamente ([SWS_DM_00619], [SWS_DM_00620]). Os callbacks fornecem seus resultados de forma assíncrona como ara::core::Future ([SWS_DM_00618], [SWS_DM_00636], [SWS_DM_00554]).

O ConcurrencyType define como o DM chama os callbacks ([SWS_DM_00935], SWS Diagnostics p. 116):

  • kConcurrent: O DM pode chamar um callback novamente antes que o resultado anterior esteja disponível.
  • kNotConcurrent: O DM bloqueia até que o future esteja pronto.

Para identificadores de dados, o valor pode ser definido separadamente para leitura, escrita e acessos combinados ([SWS_DM_00937], [SWS_DM_00938], [SWS_DM_00939]).

Cada callback recebe um MetaInfo. Ele fornece valores por chave e um contexto, como kDiagnosticCommunication, kFaultMemory, kDoIP ou kSovd ([SWS_DM_00978], [SWS_DM_00979], [SWS_DM_01342], [SWS_DM_01343], [SWS_DM_01344], [SWS_DM_01818]). Importante: O objeto é válido apenas durante a chamada. Armazená-lo ou reutilizá-lo posteriormente causa comportamento indefinido (SWS Diagnostics p. 116). Por meio do CancellationHandler, a aplicação detecta um cancelamento: IsCanceled consulta o estado, SetNotifier registra uma notificação ([SWS_DM_00614], [SWS_DM_00615], EXP SWArchitecture p. 152).

Conversations, sessões e proteção de acesso

Aplicações veem o estado de uma conversation por meio da classe Conversation. GetConversation determina a conversation a partir de um MetaInfo. Métodos adicionais fornecem todas ou todas as conversations ativas, bem como a sessão e o nível de segurança ([SWS_DM_00692], [SWS_DM_00782], [SWS_DM_00783], [SWS_DM_00696], [SWS_DM_00698]). Para mudanças de sessão, é possível registrar um notifier ([SWS_DM_00697]). ResetToDefaultSession redefine ativamente para kDefaultSession (0x01) ([SWS_DM_00701], [SWS_DM_01278]). Sem um s3ServerTimeout configurado, aplica-se um timeout S3 de 5000 ms (SWS Diagnostics p. 144). Na transição para a sessão padrão, o DM reativa uma configuração de DTC desativada (SWS Diagnostics p. 145).

Para a proteção de acesso, o DM delega verificações à aplicação:

  • SecurityAccess: GetSeed e CompareKey ([SWS_DM_00764], [SWS_DM_00765]).
  • ServiceValidation: Validate e Confirmation ([SWS_DM_00774], [SWS_DM_00775]).
  • Authentication (serviço 0x29): As subfunções resultam em VerifyCertificateUnidirectional, VerifyCertificateBidirectional ou VerifyOwnership ([SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128], SWS Diagnostics p. 166).

Uma autenticação bem-sucedida atribui papéis por meio de ClientAuthentication::Authenticate. Os serviços liberados são definidos por uma DiagnosticServiceDynamicAccessList, construída com Append e Build ([SWS_DM_01142], [SWS_DM_01152], [SWS_DM_01181]). O servidor compara as requisições recebidas por correspondência de padrões com as entradas dessa lista (SWS Diagnostics p. 136).

Memória de erros: Monitores, eventos e indicadores

Um Monitor relata resultados de teste por meio de ReportMonitorAction ([SWS_DM_00543], [SWS_DM_00541]). Dependendo da variante do construtor, ele seleciona um debouncing:

  • baseado em contador ([SWS_DM_00549]),
  • baseado em tempo ([SWS_DM_00550]),
  • interno ao monitor com callback getFaultDetectionCounter ([SWS_DM_00548]).

As mensagens kPassed e kFailed atuam diretamente como resultado de teste. kPrepassed e kPrefailed acionam o debouncing (SWS Diagnostics p. 249). Se o equivalente a FDC atingir +127 ou −128, o DebouncingState torna-se kFinallyDefective ou kFinallyHealed, respectivamente, e o bit de status kTestFailed é alterado ([SWS_DM_00645], SWS Diagnostics p. 238).

Um evento só pode ser relatado a partir de exatamente uma fonte. A interface de notificação é expressamente não reentrante (SWS Diagnostics p. 225). A classe Event fornece status, notifier de alteração de status e Fault Detection Counter. O DM processa os bits de status como bits de status de UDS-DTC ([SWS_DM_00649], [SWS_DM_00650], [SWS_DM_00656], [SWS_DM_00643]). Para múltiplos monitores, eventos ou condições atrás de uma porta, existem as variantes MultipleMonitor, MultipleEvent e MultipleCondition ([SWS_DM_01695], [SWS_DM_01705], [SWS_DM_01727], EXP SWArchitecture p. 153).

GetIndicatorState relata kOnDemand assim que um evento do DTC estiver em OnDemand, e kOff apenas se todos estiverem desligados ([SWS_DM_00744], [SWS_DM_00740], SWS Diagnostics p. 259). Uma nova chamada de SetNotifier sobrescreve o notifier anterior. De acordo com a versão R24-11, o método não é thread-safe ([SWS_DM_00745], SWS Diagnostics R24-11 p. 633).

Diagrama de sequência: Notificações do monitor passam pelo debouncing para o status do evento e alcançam notifiers registrados. Fontes: SWS Diagnostics p. 249, SWS Diagnostics p. 238, [SWS_DM_00543], [SWS_DM_00650]

Comportamento em caso de erro

Erros são relatados por meio de domínios de erro próprios: DiagErrc, DiagOfferErrc, DiagReportingErrc, DiagUdsNrcErrc e DiagSovdErrc. Os códigos de erro são gerados por meio da respectiva função MakeErrorCode ([SWS_DM_00514], [SWS_DM_00559], [SWS_DM_00560], [SWS_DM_00526], [SWS_DM_01806], [SWS_DM_00537]). Se um callback retornar um erro da DiagUdsNrcErrorDomain, o servidor enviará uma resposta negativa com esse valor como NRC. São válidos apenas valores de 0x01 a 0xFE (SWS Diagnostics p. 144).

Outras reações definidas:

  • Interface não oferecida: Se uma interface necessária não estiver (mais) disponibilizada via Offer, o DM responderá com NRC 0x94 (SWS Diagnostics p. 143).
  • Muitas respostas de Response-Pending: Se a quantidade atingir maxNumberOfRequestCorrectlyReceivedResponsePending, o servidor abortará e responderá com NRC 0x10 (SWS Diagnostics p. 143). Interpretação: Esse cancelamento provavelmente se tornará visível para a aplicação por meio de CancellationHandler::IsCanceled ([SWS_DM_00614]).
  • Permissões de acesso ausentes: NRC 0x34 no UDS ou HTTP 401 no SOVD (SWS Diagnostics p. 136).
  • Erro de transporte: Erros na recepção de requisições de múltiplas partes são relatados pelo plugin via NotifyMessageFailure; erros de envio via TransmissionResult ([SWS_DM_00310], [SWS_DM_00312], SWS Diagnostics p. 145).

Diagrama de atividades: Verificação de acesso, status de oferta, limite de Response-Pending e resultado da aplicação determinam a resposta. A ordem das duas primeiras verificações é uma interpretação. Fontes: SWS Diagnostics p. 136, SWS Diagnostics p. 143, SWS Diagnostics p. 144, [SWS_DM_00526]
