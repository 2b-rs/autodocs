Papel do Safe Hardware Acceleration e fronteira com o processo da aplicação

O Safe Hardware Acceleration (SHWA, namespace ara::shwa) disponibiliza a aceleração de hardware de forma padronizada e portátil para computações seguras e eficientes SWS SHWA p. 4. De acordo com a visão geral funcional, o SHWA fornece APIs para Adaptive Applications e outros Functional Clusters. O cluster abrange três tarefas:

  • executar trabalho computacionalmente intensivo em paralelo no acelerador de hardware (HWA),
  • detetar e corrigir erros das tarefas aí em execução,
  • monitorizar os estados de funcionamento dos aceleradores SWS SHWA p. 7.

Os requirements do cluster devem ter em consideração os requisitos de segurança da AUTOSAR SWS SHWA p. 5.

A visão geral da arquitetura atribui o SHWA à categoria Safety. Ao contrário do Platform Health Management, o SHWA não é aí identificado como daemon-based EXP SW-Architektur p. 127. As interfaces são interfaces C++ nativas que uma Adaptive Application utiliza diretamente EXP SW-Architektur p. 132. Outros Functional Clusters também podem utilizar o SHWA sem a intervenção de uma Adaptive Application. A sua parte de biblioteca utiliza para isso informações de deployment próprias; os seus daemons são modelados como Adaptive Applications SWS SHWA p. 23.

Do lado do hardware, Device distingue o tipo de unidade de processamento através de IsCpu, IsGpu e IsAccelerator [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00311] [AP_SWS_SHWA_00312]. A enumeração Target define dois locais de execução: kDevice para o dispositivo ou acelerador e kHostTask para a CPU do host [AP_SWS_SHWA_00102].

Diagrama de contexto: Adaptive Applications e outros Functional Clusters utilizam o SHWA como interface nativa; o SHWA faz a ligação a CPU, GPU e aceleradores. Fontes: SWS SHWA p. 23, EXP SW-Architektur p. 127, [AP_SWS_SHWA_00310]

Quatro áreas de interface de ara::shwa

O diagrama da especificação divide a API em quatro áreas: gestão de dados, execução de tarefas, gestão e monitorização de dispositivos, bem como tratamento de erros SWS SHWA p. 17. A explicação da API descreve as três primeiras áreas como camadas EXP SHWA-API p. 15.

  • Gestão de dados: Range e Id descrevem dimensões e índices de uma a três dimensões [AP_SWS_SHWA_01009] [AP_SWS_SHWA_00709]. A estes juntam-se Buffer [AP_SWS_SHWA_00209], Accessor [AP_SWS_SHWA_00007] e PropertyList [AP_SWS_SHWA_00802].
  • Execução de tarefas: Queue [AP_SWS_SHWA_00908], TaskHandler [AP_SWS_SHWA_01202] e Event [AP_SWS_SHWA_00602].
  • Gestão e monitorização de dispositivos: Platform [AP_SWS_SHWA_01107] e Device [AP_SWS_SHWA_00308]. Acresce DeviceSelector com GpuSelector, CpuSelector e AcceleratorSelector [AP_SWS_SHWA_00403] [AP_SWS_SHWA_00407] [AP_SWS_SHWA_00410] [AP_SWS_SHWA_00413], bem como DeviceMonitor [AP_SWS_SHWA_01407].
  • Tratamento de erros: ErrorHandler [AP_SWS_SHWA_00507], ShwaErrorCode [AP_SWS_SHWA_01301], ShwaErrorDomain [AP_SWS_SHWA_01307] e ShwaException [AP_SWS_SHWA_01303].

Uma aplicação pode combinar várias Queues, Devices e Buffers. O mesmo se aplica a outros Functional Clusters SWS SHWA p. 22. O diagrama correspondente mostra dois grupos independentes. Cada grupo é composto por uma Queue com várias tarefas, por Buffers e por um Device SWS SHWA p. 23.

Diagrama de colaboração: É assim que as classes centrais se relacionam entre as áreas: a Queue está vinculada a um Device, Submit fornece um Event e o Accessor acede a um Buffer. Fontes: SWS SHWA p. 17, [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01407]

Do dispositivo para a Queue: seleção e configuração

Um Device pode ser determinado de três formas:

  1. Enumeração: Platform::GetPlatforms fornece as plataformas disponíveis, GetDevices os respetivos Devices [AP_SWS_SHWA_01107] [AP_SWS_SHWA_01108].
  2. Sem argumento: Device::Create() [AP_SWS_SHWA_00308].
  3. Através de um seletor: Device::Create(deviceSelector) [AP_SWS_SHWA_00309].

Um DeviceSelector avalia um Device com operator() e fornece para isso um Result<int>. SelectDevice fornece o Device selecionado [AP_SWS_SHWA_00404] [AP_SWS_SHWA_00403]. GetInfo<InfoType> lê informações adicionais sobre o dispositivo a partir de [AP_SWS_SHWA_00313].

A Queue é criada diretamente a partir de um seletor ou a partir de um Device concreto. Em ambas as variantes, um ErrorHandler é parâmetro obrigatório e uma PropertyList é opcional [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00909]. GetDevice fornece o Device vinculado. IsInOrder indica se as tarefas da Queue são executadas de forma ordenada [AP_SWS_SHWA_00910] [AP_SWS_SHWA_00911] EXP SW-Architektur p. 133.

Diagrama de atividades: Três caminhos conduzem ao Device, duas fábricas à Queue; cada resultado é verificado como Result. Fontes: [AP_SWS_SHWA_01107], [AP_SWS_SHWA_00308], [AP_SWS_SHWA_00309], [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]

Disponibilizar dados e submeter tarefas

Range descreve grandezas com uma a três dimensões [AP_SWS_SHWA_01007] [AP_SWS_SHWA_01009]. Buffer::Create existe em várias variantes [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00210] [AP_SWS_SHWA_00212] [AP_SWS_SHWA_00211] [AP_SWS_SHWA_00213] [AP_SWS_SHWA_00214]:

  • apenas com Range,
  • com Range e alocador adicional,
  • apenas com alocador,
  • com dados de host mutáveis ou constantes.

Um Accessor acede a um Buffer. É criado sem ou com TaskHandler [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00008]. Oferece operator[] com Id ou índice linear [AP_SWS_SHWA_00009] [AP_SWS_SHWA_00010]. Além disso, oferece Set e Get com retorno de Result [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012]. O acesso orienta-se pelo AccessMode com os valores kRead, kWrite e kReadWrite. Em kRead, ReferenceT é uma referência constante [AP_SWS_SHWA_00101] [AP_SWS_SHWA_00014].

Queue::Submit(cfg, ErrorHandler&&) submete uma tarefa e fornece um Event [AP_SWS_SHWA_00912]. O TaskHandler disponibiliza duas formas de execução: SingleTask para uma tarefa individual e ParallelFor(bufferSize, cfg) para execução com paralelismo de dados [AP_SWS_SHWA_01203] [AP_SWS_SHWA_01204]. O diagrama de casos de uso refere como cenários de utilização "Single Instructions on Multiple Data" e "Multiple Instructions on Multiple Data" EXP SW-Architektur p. 203.

Interpretação: cfg deverá ser uma configuração invocável. Provavelmente recebe o TaskHandler, cria Accessors no mesmo e chama SingleTask ou ParallelFor. A fábrica de Accessor com parâmetro TaskHandler aponta para isso [AP_SWS_SHWA_00008].

Diagrama de sequência: Os dados são disponibilizados, uma tarefa com paralelismo de dados é submetida e aguarda-se a sua conclusão. A chamada de cfg está identificada como interpretação. Fontes: [AP_SWS_SHWA_01007], [AP_SWS_SHWA_00211], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01204], [AP_SWS_SHWA_00604]

Sincronização através de eventos e funções de espera da Queue

Cada Submit fornece um Event [AP_SWS_SHWA_00912]. Ao nível do Event existem três funções de espera [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00605] [AP_SWS_SHWA_00606]:

  • Event::Wait() aguarda a conclusão das tarefas associadas.
  • A variante estática com lista de eventos aguarda por vários Events.
  • WaitFor(ms) limita o tempo de espera.

GetWaitList fornece uma lista de Events [AP_SWS_SHWA_00603]. Ao nível da Queue, Wait() aguarda de modo bloqueante por todas as tarefas em fila de espera; WaitFor(ms) faz o mesmo com limite de tempo [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] EXP SW-Architektur p. 133.

Os requirements especificam a segurança para threads para cada função individualmente:

  • Seguro para threads: Queue::Create, Accessor::Create, Range::Create, bem como Accessor::Set e Get [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00007] [AP_SWS_SHWA_01007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012].
  • Não seguro para threads: Queue::Submit, Queue::Wait, Event::Wait, Device::Create e Accessor::operator[] [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00308] [AP_SWS_SHWA_00009].
  • Diferenças dentro de uma classe: Buffer::Create é seguro para threads, enquanto a variante apenas com alocador não o é [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00212].

Uma segunda variante de Submit aceita um secondaryQueue em vez do ErrorHandler [AP_SWS_SHWA_00913]. Interpretação: esta Queue deverá servir como Queue de contingência se a execução na Queue primária falhar. A variante baseia-se no mesmo requisito upstream que o ErrorHandler [AP_SWS_SHWA_00507].

Diagrama de sequência: Duas Queues trabalham de forma independente; a aplicação sincroniza através de listas de eventos ou das funções de espera da Queue. Fontes: [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00605], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917], SWS SHWA p. 22.

Posse de objetos, propriedades e estado do dispositivo

Para todas as classes aplicam-se três regras de conceção EXP SHWA-API p. 15:

  • Os construtores são privados; os objetos são criados através de métodos Create() nomeados.
  • Classes que possuem dados fornecem std::unique_ptr.
  • A maioria dos retornos está encapsulada em ara::core::Result.

Uma versão R23-11 da explicação ainda mencionava ara::com::SamplePtr neste ponto EXP Safe-API HWA p. 15. Determinantes para a R25-11 são os requirements, e estes estabelecem std::unique_ptr [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00908].

Para a monitorização, é criado um DeviceMonitor a partir de um Device ou de um seletor [AP_SWS_SHWA_01407] [AP_SWS_SHWA_01408]. Status() fornece um DeviceStatus com um destes valores [AP_SWS_SHWA_01409] [AP_SWS_SHWA_00103]:

  • kReady: pronto para a execução da tarefa,
  • kNotAccesible: inacessível,
  • kFailure: estado de erro,
  • kUnknown: estado não determinável.

As presentes fontes não definem se este estado é transmitido a outros Functional Clusters.

Diagrama de atividades: O estado é consultado através do DeviceMonitor e ramifica de acordo com DeviceStatus; a reação a valores diferentes de kReady é uma interpretação. Fontes: [AP_SWS_SHWA_01407], [AP_SWS_SHWA_01409], [AP_SWS_SHWA_00103]

Comportamento em caso de erro

O SHWA reporta erros por meio de ara::core::Result com códigos de ShwaErrorCode. Entre eles estão kRuntime, kTaskExecutionFailure, kMemoryNotAllocated, kIntegrityCorrupted (não é possível restabelecer a integridade de uma memória de buffer), kResourceBusy e kInvalidAccessMode [AP_SWS_SHWA_01301]. Funções individuais mencionam outros códigos: kAccessorFailure, kInvalidIndex, kFeatureNotSupported e kEventInvalidOperation [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00313] [AP_SWS_SHWA_00603].

O domínio ShwaErrorDomain disponibiliza Name, Message e ThrowAsException. GetShwaDomain e MakeErrorCode associam os códigos ao domínio. ShwaException transporta um código como exceção [AP_SWS_SHWA_01308] [AP_SWS_SHWA_01309] [AP_SWS_SHWA_01310] [AP_SWS_SHWA_01311] [AP_SWS_SHWA_01312] [AP_SWS_SHWA_01303].

Erros durante a execução e a espera são particularmente graves. Se Submit, Queue::Wait, Queue::WaitFor ou Event::Wait reportarem o código kRuntime, os dados da tarefa com falha devem ser considerados como inadvertidamente modificados. No caso de Event::Wait, isso também se aplica a kTaskExecutionFailure [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] [AP_SWS_SHWA_00604]. As informações de erro de Submit trazem a identificação no_rollback_semantics [AP_SWS_SHWA_00912].

Recursos ocupados são reportados, entre outros, pelas consultas de dispositivos e por Accessor::Get com kResourceBusy [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00012]. Uma alocação com falha é reportada por Buffer::Create com kMemoryNotAllocated [AP_SWS_SHWA_00212].

Um ErrorHandler encapsula uma função std::function<void(ara::core::ErrorCode)> [AP_SWS_SHWA_00507]. HandleError(ShwaErrorCode) executa o tratamento e não é thread-safe [AP_SWS_SHWA_00508]. Cada fila recebe um ErrorHandler na criação [AP_SWS_SHWA_00908]. Interpretação: é provável que a implementação reporte via HandleError erros de tarefas submetidas que não estejam diretamente disponíveis como valor de retorno de Submit; as fontes não definem quem chama HandleError. No nível de dispositivo, DeviceStatus::kFailure indica um estado de erro [AP_SWS_SHWA_00103].

Diagrama de atividades: Um Result é avaliado e os códigos de erro do SHWA são classificados, incluindo as consequências para os dados em caso de erros de tarefas. Fontes: [AP_SWS_SHWA_01301], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00604], [AP_SWS_SHWA_01310], [AP_SWS_SHWA_00508]

ara::shwa

AcceleratorSelector classe

AcceleratorSelector manages accelerator selection for operations on HWA if available.

Accessor classe

Accessor manages read and write access to allocated memory by Buffer. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

Buffer classe

Buffer manages memory allocation for operations on the host or/and HWA. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ptr, which may be moved. ≙ std::unique_ptr

CpuSelector classe

CpuSelector manages CPU selection for operations on HWA if available Allows to get a device from any supported backends for which the device type is CPU.

Device classe

Device class represents HWA device. Provides access to the device but not controlling it. Designed as copyable since not owning resources.

DeviceMonitor classe

DeviceMonitor API class. Designed as copyable since not owning resources.

DeviceSelector classe

Class allowing to choose the most appropriate device of the available ones. This is a callable object taking a device reference and returning an integer rank. One of the device with the highest non-negative value is selected.

ErrorHandler classe

ErrorHandler manages asynchronous error handling for operations on HWA.

Event classe

Event class helps to manage task execution synchronization between HWA and Host application. Can be created only inside of the Queue otherwise it’s meaningless.

GpuSelector classe

GpuSelector manages GPU selection for operations on HWA if available Select a device from any supported backends for which the device type is GPU.

Id classe

Id API class. Designed as copyable since not owning resources.

Platform classe

Platform class is responsible for extracting different HWA platforms available for current application and listing Devices bind to each platform. Designed as copyable since not owning resources.

PropertyList classe

Property List class is designed to enable vendor specific SHWA functionality extension and adjustment. Properties are not standardized and can be defined by Vendor. Class using Property list is obliged to have HasProperty() and GetProperty() methods defined.

Queue classe

Queue API provides the functionality for parallel processing on selected Device. Designed as not copyable, since it’s owning resources. Intended to be managed exclusively by std::unique_ ptr, which may be moved. ≙ std::unique_

Range classe

Defines size of Buffer for one, two or three dimensions. Designed as copyable since not owning resources.

ShwaErrorDomain classe

Defines the error domain for Safe Hardware Acceleration.

ShwaException classe

Exception type could be thrown by application or other FC using Safe Hardware Acceleration. Safe Hardware Acceleration API is exception free and can only return an ErrorCode, but user code can transform this error to exception and throw if it’s alligned with system error handling architecture.

TaskHandler classe

Handles tasks execution on the selected Device Can be created only inside of the Queue otherwise it’s meaningless.
