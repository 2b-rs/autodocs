Papel de ara::core como base comum de todos os Functional Clusters

O Functional Cluster Core tem duas tarefas. Ele define requisitos básicos que se aplicam a todos os Functional Clusters da Adaptive Platform. Além disso, disponibiliza funcionalidade para todo o framework, principalmente tipos de dados comuns que múltiplos Functional Clusters utilizam em suas interfaces públicas (SWS Core p. 8). O próprio Core depende apenas da especificação da interface do sistema operacional, ou seja, essencialmente da biblioteca padrão C++ (SWS Core p. 10). Todos os símbolos estão no namespace ara::core e são publicamente visíveis, a menos que especificado de outra forma (SWS Core p. 47).

As regras transversais também se aplicam à implementação de outros clusters:

  • Os includes seguem o padrão #include "ara/fc/header.h".
  • Headers públicos precisam de include guards que sejam o mais exclusivos possível em todo o sistema (SWS Core p. 23).
  • Símbolos com o prefixo ARA são reservados para a AUTOSAR.
  • Os especificadores de declaração só podem ser complementados com inline e friend (SWS Core p. 24).

A descrição da arquitetura cita dois grupos como interfaces nativas: Initialize()/Deinitialize() bem como Abort()/SetAbortHandler() (EXP SWArchitecture p. 60, [SWS_CORE_00051]).

Diagrama de contexto: Core é a camada base entre aplicações, outros Functional Clusters e a biblioteca padrão C++. Uma interrupção via std::abort é reconhecida pelo Execution Management como Abnormal Termination. Fontes: SWS Core p. 8, SWS Core p. 10, SWS Core p. 187, SWS Core p. 39, EXP SWArchitecture p. 60

Início e término do tempo de execução ARA

ara::core::Initialize é a (pré-)inicialização do framework ARA. Antes disso, qualquer interação com ARA é inadmissível. Excetuam-se os tipos que devem poder ser utilizados independentemente da inicialização:

  • ErrorCode e StringView,
  • Result, mas sem ValueOrThrow ([SWS_CORE_00766]),
  • ErrorDomain com suas subclasses, mas sem ThrowAsException ([SWS_CORE_00154]) (SWS Core p. 182).

Essa exceção é justificada pelo fato de que precisamente esses tipos são necessários para a própria inicialização (SWS Core p. 46). Initialize pode configurar estruturas de dados e recursos do sistema e iniciar threads em segundo plano (SWS Core p. 45). Se necessário, ele também inicializa outros Functional Clusters (SWS Core p. 187).

ara::core::Deinitialize desliga o framework de forma ordenada. Isso inclui o encerramento de threads em segundo plano e a liberação de memória e de outros recursos do sistema. Se chamadas ARA ainda estiverem em execução em paralelo, o comportamento é indefinido (SWS Core p. 45). Antes da chamada, o uso das interfaces ARA deve ser concluído. Recomenda-se um local de chamada após a inicialização estática e antes da destruição de dados estáticos (SWS Core p. 182).

Diagrama de estados: o tempo de execução ARA transita entre três fases por meio de Initialize e Deinitialize. Fora da fase inicializada, apenas um conjunto fixo de tipos pode ser utilizado. Fontes: SWS Core p. 182, SWS Core p. 182, SWS Core p. 45

Classes de erro e valores de erro: ErrorCode, ErrorDomain, Result

Core distingue três tipos de operações malsucedidas (SWS Core p. 25):

  • Um Error significa que uma função de API presumida livre de erros não pode cumprir sua finalidade. Um Error é recuperável.
  • Uma Violation corresponde a uma asserção com falha e não é recuperável.
  • Uma Corruption é causada por recursos de sistema corrompidos e também não é recuperável.

Para cada tipo, o tratamento está definido (SWS Core p. 27):

  • Errors são retornados como Result ou Future.
  • Violations encerram a operação por meio de uma exceção não derivada de ara::core::Exception ou por ara::core::Abort ([SWS_CORE_00052]). Uma alocação padrão com falha também é considerada uma Violation.
  • Corruptions levam ao término malsucedido do processo.

Diagrama de atividades: o tipo da condição detectada determina se um valor de erro é retornado ou se a operação ou o processo é encerrado. Fontes: SWS Core p. 25, SWS Core p. 27, [SWS_CORE_00052]

Um ErrorCode contém três componentes: o valor do erro, uma referência ao domínio do erro e dados adicionais opcionais específicos do fornecedor. Eles podem ser obtidos via Value() ([SWS_CORE_00514]) e SupportData() ([SWS_CORE_00516]). Na comparação ([SWS_CORE_00571]), apenas o valor e o domínio contam, os dados adicionais são ignorados. Um ErrorCode é criado geralmente pela forma de encaminhamento de Result::FromError ([SWS_CORE_00736]) (SWS Core p. 28).

Result segue o conceito ValueOrError: ele contém um valor ou um erro. ErrorType é, por padrão, ErrorCode (SWS Core p. 30). Os acessos típicos são:

  • HasValue() ([SWS_CORE_00751]),
  • Value() ([SWS_CORE_00755]),
  • Error() ([SWS_CORE_00757]),
  • ValueOrThrow() ([SWS_CORE_00766]). Essa função conecta a abordagem livre de exceções com as exceções C++. O tipo base destas, ara::core::Exception ([SWS_CORE_00611]), fornece o ErrorCode via Error() ([SWS_CORE_00613]).

A especialização Result<void, E> dispensa operator-> e Bind (SWS Core p. 70, [SWS_CORE_00851]).

Resultados assíncronos com Future e Promise

Future e Promise são estreitamente baseados em std::future e std::promise. Ambos compartilham um Shared State. As divergências decorrem apenas da integração com Result (SWS Core p. 89). Concretamente, há duas diferenças:

  • SetError ([SWS_CORE_00353]) substitui set_exception.
  • GetResult() ([SWS_CORE_00336]) retorna um Result e nunca lança exceções.

A divisão de trabalho é clara: Result serve para chamadas síncronas, Future para chamadas assíncronas com recuperação posterior thread-safe (SWS Core p. 31).

O fluxo no lado do provedor:

  1. O provedor cria um Promise ([SWS_CORE_00341]).
  2. Ele obtém o Future associado com get_future() ([SWS_CORE_00344]) e o retorna.
  3. Mais tarde, ele cumpre o Promise com set_value ([SWS_CORE_00345], [SWS_CORE_00346]), SetError ou SetResult ([SWS_CORE_00355]).

Em ara::com, o binding chama set_value ou SetError. Com isso, as chamadas bloqueantes de get(), wait(), wait_for() e wait_until() retornam (SWS CM p. 106). Um exemplo explicativo mostra o cumprimento em uma thread de trabalho após o Future já ter sido retornado (EXP ARAComAPI p. 59).

Diagrama de sequência: o provedor retorna o Future imediatamente e cumpre o estado compartilhado mais tarde de forma assíncrona com um valor ou um erro. Fontes: [SWS_CORE_00341], [SWS_CORE_00344], [SWS_CORE_00345], [SWS_CORE_00353], [SWS_CORE_00326], SWS CM p. 106, EXP ARAComAPI p. 59

O consumidor tem múltiplos padrões de acesso:

  • get() ([SWS_CORE_00326]) e wait() ([SWS_CORE_00328]) bloqueiam.
  • wait_for() ([SWS_CORE_00329]) e wait_until() ([SWS_CORE_00330]) retornam um FutureStatus ([SWS_CORE_00361]). Isso permite distinguir um resultado disponível de um timeout (ARAComAPI (Fig. 6.15) p. 1).
  • then() ([SWS_CORE_00331]) registra uma continuação, opcionalmente com Executor ([SWS_CORE_00337]).
  • is_ready() ([SWS_CORE_00332]) não bloqueia e é adequado para aplicações de tempo real que operam por polling (EXP ARAComAPI p. 58).

Futures não são copiáveis ([SWS_CORE_00334]). Um resultado não mais necessário é descartado sobrescrevendo o Future com um Future construído por padrão ([SWS_CORE_00322]) (EXP ARAComAPI p. 59). De forma complementar, existe um Executor. De acordo com a assinatura, execute retorna um Future do resultado da chamada ([SWS_CORE_00024]), enquanto oneway_execute não retorna nada ([SWS_CORE_00025]).

Diagrama de atividades: o consumidor escolhe entre recuperação bloqueante, espera com limite de tempo, continuação e polling não bloqueante. Fontes: [SWS_CORE_00326], [SWS_CORE_00329], [SWS_CORE_00331], [SWS_CORE_00332], [SWS_CORE_00336], EXP ARAComAPI p. 58

Tipos de dados, contêineres e recursos de memória

O Core redefine tipos que já existem de forma quase equivalente no padrão C++. O motivo: o comportamento de alocação dos tipos std:: muitas vezes não é adequado para o setor automotivo. Funções que, de acordo com o padrão C++, lançam exceções causam, em vez disso, uma Violation nesses tipos (SWS Core p. 41). Especificamente:

  • Vector comporta-se como std::vector, apenas o alocador padrão é dependente da implementação (SWS Core p. 129, [SWS_CORE_01390]).
  • Map comporta-se correspondentemente como std::map (SWS Core p. 130, [SWS_CORE_01496]).
  • String é definido como BasicString<> com tipo de caractere fixo char (SWS Core p. 133, [SWS_CORE_03001]) e implicitamente conversível para StringView ([SWS_CORE_03301]).

A própria especificação admite que o comportamento de alocação de Map, Vector e String é descrito apenas como dependente da implementação (SWS Core p. 10).

Outros tipos são provenientes de padrões C++ mais recentes (SWS Core p. 43):

  • Optional mapeia elementos de registro opcionais. Verifica-se se um valor está presente com operator bool ou has_value() ([SWS_CORE_01129], SWS Core p. 131, ARAComAPI (Fig. 6.3) p. 1).
  • StringView é uma visualização somente de leitura de caracteres (SWS Core p. 132, [SWS_CORE_02112]).
  • Span é uma visualização de uma sequência contígua de objetos externos (SWS Core p. 137, [SWS_CORE_01901]). Se as_bytes pode ser usado sem problemas de aliasing depende da implementação (SWS Core p. 155, [SWS_CORE_01980]).
  • Byte não é um tipo integral e não permite conversões implícitas (SWS Core p. 44).
  • Em Array, get<I> com I >= N leva a um erro de compilação (SWS Core p. 127, [SWS_CORE_01282]).

Diferenças entre versões: os extratos da R21-11 não correspondem aos requisitos da R25-11 em dois pontos; os requisitos são determinantes.

  • De acordo com a R21-11, Array::at é omitido (SWS Core p. 41). A R25-11, por outro lado, introduz at() como noexcept ([SWS_CORE_01273]).
  • De acordo com a R21-11, Optional não possui funções-membro value (SWS Core p. 131). A R25-11 as especifica ([SWS_CORE_01130]).

Para o gerenciamento de memória, existem recursos de memória polimórficos. A base MemoryResource oferece publicamente allocate/deallocate/is_equal e ganchos privados do_*. Abaixo dela estão MonotonicBufferResource, bem como recursos de pool sincronizados e não sincronizados (EXP SWArchitecture p. 61). Os recursos de pool são construídos com PoolOptions e um recurso upstream ([SWS_CORE_00030], [SWS_CORE_00067]). Eles oferecem release() ([SWS_CORE_00037]) e upstream_resource() ([SWS_CORE_00038]) e não são copiáveis ([SWS_CORE_00034], [SWS_CORE_00046]).

Domínios de erro próprios e referência de instância via InstanceSpecifier

Um módulo de software com lógica independente deve definir domínios de erro próprios. Um domínio de erro consiste em cinco partes, todas localizadas no namespace do módulo (SWS Core p. 32):

  • uma enumeração de erros,
  • uma classe base de exceção,
  • uma subclasse de ErrorDomain,
  • uma função de acesso global,
  • uma sobrecarga de MakeErrorCode.

Regras fixas se aplicam a essas partes:

  • A enumeração chama-se <SN>Errc, não contém valores de sucesso e deixa o 0 desocupado (SWS Core p. 33).
  • A subclasse é final e possui os aliases Errc e Exception (SWS Core p. 34).
  • A função de acesso Get<SN>ErrorDomain é constexpr e retorna um singleton (SWS Core p. 35).
  • Os domínios devem ser tipos literais (SWS Core p. 30).

A identidade de um domínio baseia-se em um ID exclusivo de 64 bits ([SWS_CORE_00121], [SWS_CORE_00151], [SWS_CORE_00137]). A faixa de valores é dividida (SWS Core p. 37):

  • Bit 63 = 1 e bit 62 = 0: domínios AUTOSAR,
  • 32 bits superiores = 0xc000'0000: domínios do fabricante,
  • Bit 63 = 0: domínios do usuário.

A FutureErrorDomain possui o ID 0x8000'0000'0000'0013 ([SWS_CORE_00480]). Todos os demais erros do Core pertencem à CoreErrorDomain (SWS Core p. 84).

InstanceSpecifier estabelece a referência à instância do modelo. Ele identifica instâncias de protótipos de porta no metamodelo AUTOSAR por meio de uma lista de nomes separada por "/" do Executable até o PortPrototype. Caminhos sintaticamente inválidos são rejeitados. Existem duas maneiras para a construção: o método de fábrica livre de exceções Create ou o construtor, que pode lançar exceção em caso de entrada inválida (SWS Core p. 40).

Comportamento em caso de erro

ara::core::Abort ([SWS_CORE_00052]) encerra o processo imediata e anormalmente, sem desenrolamento de pilha (stack unwinding) e sem destruidores de objetos estáticos (SWS Core p. 38). A função possui as seguintes propriedades:

  • Ela nunca retorna.
  • Ela escreve o texto transmitido como mensagem de log no fluxo de erro padrão.
  • Outras chamadas simultâneas bloqueiam as threads chamadoras.

A chamada é considerada uma Explicit Operation Abortion (SWS Core p. 8).

Com SetAbortHandler ([SWS_CORE_00051]), é possível instalar um AbortHandler ([SWS_CORE_00050]). Seu tipo deriva de um protótipo que não está implementado ([SWS_CORE_00053], SWS Core p. 183). Um handler que encerra o processo deve utilizar std::abort para isso, para que o Execution Management reconheça uma Abnormal Termination. Se o handler retornar ou se nenhum estiver instalado, o próprio Abort chama std::abort() (SWS Core p. 39). O R25-11 introduz adicionalmente AddAbortHandler ([SWS_CORE_00054]). Sua semântica não é descrita com mais detalhes no payload e, portanto, não é detalhada aqui.

Diagrama de atividades: Abort sempre termina no encerramento do processo, seja pelo handler ou por std::abort. Interpretação: a mensagem de log é emitida antes da chamada do handler. Fontes: SWS Core p. 38, SWS Core p. 39, [SWS_CORE_00051], [SWS_CORE_00052]

No lado assíncrono, um Promise destruído ([SWS_CORE_00349]) resulta em uma future concluída. Esta contém um ErrorCode da FutureErrorDomain com o valor FutureErrc::kBrokenPromise ([SWS_CORE_00400]). Isso ocorre, por exemplo, quando um ServiceProxy é destruído (SWS CM p. 290). Por outro lado, o ara::com reporta erros de comunicação via SetError com erros da ComErrorDomain (SWS CM p. 300).

Diagrama de sequência: a destruição do proxy destrói a promise e conclui a future pendente com kBrokenPromise. Fontes: SWS CM p. 290, [SWS_CORE_00349], [SWS_CORE_00400], [SWS_CORE_00336]

Estão definidos mais dois casos de erro:

  • Se Message() for chamado com um código de erro de um domínio externo, isso constitui uma Violation ([SWS_CORE_00153], SWS Core p. 51).
  • Um erro de Deinitialize é a única via de notificação com disponibilidade garantida, por exemplo, quando ara::log já foi desinicializado. Ele é considerado irrecuperável (SWS Core p. 45).
