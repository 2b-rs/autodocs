Classificação e Finalidade

O módulo ara::core é a biblioteca base básica da plataforma adaptativa AUTOSAR e é definido na especificação oficial AUTOSAR_AP_SWS_Core.pdf (R25-11). Ele fornece o tipo de retorno livre de erros ara::core::Result, bem como a classe base de domínio de erro ara::core::ErrorDomain, que define o contexto para um conjunto de condições de erro; As subclasses ErrorDomain são a raiz de todos os dados de erro [SWS_CORE_10303]. O tratamento de erros na Plataforma Adaptativa geralmente é realizado sem exceções C++ via ara::core::ErrorCode e ara::core::Result de acordo com o conceito «ValueOrError» (EXP InterfacesGuidelines). O namespace ara e todos os namespaces subjacentes também são reservados pelo AUTOSAR; Se um Aplicativo Adaptativo adicionar suas próprias declarações, o comportamento será indefinido (EXP InterfacesGuidelines). ara::core forma assim a base comum para inicialização, tratamento de erros e regras de simultaneidade para todos os clusters de funções AP.

Objetos principais e uso típico

ara::core::Result<T, E> contém um valor ou um erro; o tipo de erro deve ser ErrorCode, caso contrário ocorre erro de compilação [SWS_CORE_00701], com especializações para tipos de referência [SWS_CORE_00901] e para valores void [SWS_CORE_00801]. Um Result é criado usando as funções estáticas de fábrica FromValue [SWS_CORE_00733] ou FromError [SWS_CORE_00736]. Bind aplica um chamável a um valor contido e devolve um novo Result; Se a instância não contiver um valor, o erro original será adotado inalterado [SWS_CORE_00768]. Resolve devolve o valor ou chama um callable compatível em caso de erro [SWS_CORE_00767], enquanto ErrorOr [SWS_CORE_00764][SWS_CORE_00763] fornece valores de fallback simples. As instâncias ErrorDomain serão iguais se e apenas se seus identificadores exclusivos de 64 bits corresponderem; O acesso geralmente é feito por meio de acessadores não membros, como GetFutureErrorDomain [SWS_CORE_10401].

Para contêineres e processamento de texto, o módulo fornece implementações compatíveis com PMR da biblioteca padrão C++: ara::core::Vector [SWS_CORE_01301], ara::core::Map [SWS_CORE_01400], ara::core::StringView [SWS_CORE_02001], ara::core::BasicString [SWS_CORE_03000] e ara::core::Span [SWS_CORE_01900]. Para referências de modelo em nível de aplicação, a classe final ara::core::InstanceSpecifier existe em ara/core/instance_specifier.h, que encapsula um caminho shortName AUTOSAR [SWS_CORE_08001].

Geração, ciclo de vida e Propriedade

O ciclo de vida de todo o ARA é controlado centralmente através das duas funções gratuitas ara::core::Initialize e ara::core::Deinitialize. Initialize lança a estrutura ARA; isso pode incluir a inicialização de estruturas de dados internas e recursos do sistema, bem como o início de threads em segundo plano [SWS_CORE_15003]. Se Initialize usar a injeção de argumentos de linha de comando, os argumentos relevantes deverão ser removidos de forma transparente para que a análise de argumentos do aplicação não seja afetada [SWS_CORE_15006]. Uma chamada bem-sucedida coloca a estrutura em um estado no qual todos os componentes configurados podem atender imediatamente chamadas de API [SWS_CORE_90026]; uma segunda chamada sem Deinitialize anterior devolve kAlreadyInitialized sem perturbar a instância em execução [SWS_CORE_90029]. Por outro lado, Deinitialize inicia o encerramento da estrutura, incluindo o encerramento de threads de segundo plano iniciados e a liberação de memória dinâmica e outros recursos do sistema [SWS_CORE_15004]; Se a estrutura não for inicializada com êxito ou já tiver sido desinicializada, cada chamada retornará kNotInitialized [SWS_CORE_90030].

Apenas um pequeno subconjunto explicitamente nomeado de ara::core - entre outros. ErrorCode, StringView, Result (sem ValueOrThrow), ErrorDomain (sem ThrowAsException), Initialize, Abort, SetAbortHandler e AddAbortHandler - podem ser usados independentemente de Initialize/Deinitialize pode ser usado como [SWS_CORE_15002]. O comportamento de todas as outras funções ARA antes de Initialize é [SWS_CORE_15005] definido pela implementação, e uma chamada após Deinitialize fora deste subconjunto também tem comportamento definido pela implementação, uma vez que uma verificação de tempo de execução correspondente não foi deliberadamente necessária por motivos de desempenho [SWS_CORE_90022]. O Guidelines for using Adaptive Platform interfaces resume isso como um contrato vinculativo de inicialização/desligamento: Initialize deve ser chamado no ponto de entrada, Deinitialize apenas após todos os recursos ARA terem sido liberados em outros threads; ambos entregam Result<void>, que deve ser verificado, e um erro não pode ser corrigido, portanto a aplicação deve terminar com EXIT_FAILURE (EXP InterfacesGuidelines). Além disso, o AUTOSAR AP RS General proíbe funções de inicialização específicas de cluster: Se um cluster de função exigir inicialização ou desinicialização explícita, ele deverá usar exclusivamente ara::core::Initialize/ara::core::Deinitialize.

Tratamento de erros, simultaneidade e restrições

A especificação define Thread-Safety com precisão: uma função membro não estática de uma API AUTOSAR é thread-safe se puder ser chamada concorrentemente no mesmo objeto a partir de várias threads, sem sincronização pelo chamador; os destruidores e operadores de atribuição não são, em regra, thread-safe [SWS_CORE_13200]. Se, ainda assim, uma função membro not thread-safe for chamada concorrentemente no mesmo objeto, o comportamento é indefinido — mesmo que a outra função envolvida seja thread-safe [SWS_CORE_13203]; em contrapartida, é permitida sem sincronização a chamada concorrente em instâncias diferentes [SWS_CORE_13205]. A implementação ARA chama exclusivamente de forma sequencial callbacks ou funções puramente virtuais especificadas como non-thread-safe, por exemplo ara::tsync::SynchronizedTimeBaseNotifier, enquanto ara::phm::RecoveryAction::RecoveryHandler é, por exemplo, thread-safe [SWS_CORE_13214]. A utilização de APIs ARA num signal handler conduz a comportamento indefinido, salvo especificação em contrário [SWS_CORE_13210] (EXP InterfacesGuidelines: Async-Signal-Safety). Além disso, AUTOSAR AP RS General exige que cada função API indique o seu nível de Thread-Safety como «thread-safe», «not thread-safe» ou «conditional» e que o contrato de Thread-Safety se aplique bilateralmente: se uma API for especificada como thread-safe, a implementação fornecida pelo Vendor ou utilizador, como callbacks ou funções Skeleton puramente virtuais, também tem de cumprir essa garantia (EXP InterfacesGuidelines).

Para erros irrecuperáveis, ara::core distingue violação de tratamento de erro regular: Uma violação é o resultado de pré ou pós-condições violadas da estrutura e não é recuperável, comparável a uma asserção falhada [SWS_CORE_00021]. No caso de violação padronizada, o processo é encerrado de forma anormal através de ara::core::Abort; uma mensagem de depuração de acordo com a definição DLT é emitida em stderr e deve ser gravada nos coletores de log com o ID de contexto do cluster de função de detecção [SWS_CORE_00090]. Enquanto uma chamada para Abort está em andamento, outras chamadas bloqueiam os threads de chamada [SWS_CORE_12407]; Os manipuladores de interrupção instalados são chamados na ordem inversa de instalação; sem manipuladores, std::abort() é chamado [SWS_CORE_12404]. Esta separação de erros recuperáveis ​​através de Result/ErrorCode e violações não recuperáveis ​​[SWS_CORE_00021] é apoiada pelo AUTOSAR AP RS General como um princípio geral para todos os clusters de funções AP.

Integração e configuração

Cada Functional Cluster ARA utiliza, ao efetuar logging através de ara::log, as definições Log-and-Trace normalizadas de ara::core, em particular o intervalo de Context ID e Message ID [SWS_CORE_00055]. Para esse efeito, a especificação define IDs de contexto de log normalizados para cada Functional Cluster, incluindo #COM para com, #COR para core, #CRY para crypto, #DIA para diag, #EXE para exec, #LOG para log e #PER para per [SWS_CORE_90024]. Ao nível dos requisitos, AUTOSAR AP RS General acrescenta que as interfaces ARA têm de utilizar tipos ara::core em vez dos tipos padrão de C++, desde que ara::core disponibilize um tipo equivalente. Uma vez que o namespace ara está totalmente reservado para AUTOSAR, todos os tipos de dados de um Functional Cluster estão igualmente disponíveis através de um ficheiro de cabeçalho de encaminhamento <fc>_fwd.h (EXP InterfacesGuidelines).
