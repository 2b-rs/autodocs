Permite que aplicações realizem o processamento genérico de serviços UDS RoutineControl com transferência assíncrona de dados.

A classe disponibiliza um handler genérico para serviços UDS RoutineControl e encaminha solicitações para diferentes identificadores de rotina a aplicações adaptativas [SWS_DM_00552]. Os desenvolvedores implementam as ações de rotina requeridas por meio de métodos assíncronos como Start e ativam o encaminhamento de mensagens através de Offer [SWS_DM_00557]. Como as instâncias não podem ser copiadas nem movidas, o ciclo de vida e a simultaneidade devem ser controlados de forma exata por meio do construtor e da configuração da interface. As operações em andamento suportam cancelamentos cooperativos bem como códigos de erro UDS padronizados.

Contexto

A classe ara::diag::GenericRoutine disponibiliza a interface genérica para o processamento de rotinas de diagnóstico conforme a ISO 14229-1 (UDS RoutineControl, serviço 0x31) na AUTOSAR Adaptive Platform. Ela atua como elemento de ligação entre o Diagnostic Management (DM) central e a aplicação adaptativa. Uma instância dessa classe é vinculada a um protótipo de porta modelado do tipo DiagnosticRoutineGenericInterface, o qual deve ser referenciado no modelo por meio de um DiagnosticServiceGenericMapping [SWS_DM_00552]. Diferentemente de interfaces de rotina específicas de tipo, GenericRoutine transfere os dados brutos da solicitação de diagnóstico como ara::core::Span<const std::uint8_t> juntamente com o identificador de rotina concreto (routineId) para a aplicação [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556]. Com isso, um único handler pode atender a múltiplas rotinas de forma flexível.

Ciclo de vida

As instâncias de GenericRoutine são vinculadas à sua porta específica e não devem ser copiadas nem movidas; os construtores de cópia e de movimento, bem como os operadores de atribuição, estão explicitamente excluídos [SWS_DM_01637], [SWS_DM_01638], [SWS_DM_01635], [SWS_DM_01636]. A inicialização ocorre por meio do construtor, com a indicação de ara::core::InstanceSpecifier bem como do comportamento de simultaneidade (ConcurrencyType: kConcurrent ou kNotConcurrent) [SWS_DM_00552]. Esse parâmetro define se os métodos virtuais de execução precisam ser implementados de forma thread-safe.

Após a criação, o DM inicialmente não encaminha mensagens para o handler. O encaminhamento é ativado apenas pela chamada de Offer() [SWS_DM_00557]. Por meio de StopOffer(), o encaminhamento pode ser desativado novamente [SWS_DM_00558], antes que a instância seja liberada pelo destrutor virtual ~GenericRoutine() [SWS_DM_00553]. Enquanto o construtor é thread-safe, Offer(), StopOffer() e o destrutor não são thread-safe e requerem sincronização externa [SWS_DM_00552], [SWS_DM_00557], [SWS_DM_00558], [SWS_DM_00553].

Diagrama de estados: ciclo de vida e transições de estado de uma instância GenericRoutine. Fontes: [SWS_DM_00552], [SWS_DM_00557], [SWS_DM_00558], [SWS_DM_00553]

Caminho de utilização

Para disponibilizar uma rotina genérica, uma aplicação deriva de GenericRoutine e sobrescreve os métodos virtuais necessários. O método Start (subfunção UDS 0x01) é puramente virtual (pure virtual) e deve ser obrigatoriamente implementado [SWS_DM_00554]. Os métodos Stop (subfunção 0x02) [SWS_DM_00555] e RequestResults (subfunção 0x03) [SWS_DM_00556] são métodos virtuais; interpretação: como não são puramente virtuais, eles provavelmente só precisam ser sobrescritos se a respectiva rotina suportar funcionalmente a parada ou a consulta separada de resultados.

O fluxo regular compreende as seguintes fases:

  • Instanciação: criação do handler derivado com referência de porta e modo de simultaneidade [SWS_DM_00552].
  • Ativação: chamada de Offer() para liberação para o DM [SWS_DM_00557].
  • Execução: em solicitações UDS recebidas, o DM chama Start, Stop ou RequestResults. A aplicação recebe routineId, requestData, metaInfo bem como um CancellationHandler e retorna um ara::core::Future<OperationOutput> [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556]. A validade de requestData é garantida até que a promise correspondente seja cumprida ou a operação seja cancelada [SWS_DM_00554].
  • Tratamento de cancelamento: a aplicação pode verificar o status de cancelamento via cancellationHandler.IsCanceled() ou registrar um callback via cancellationHandler.SetNotifier() [SWS_DM_00554]. Interpretação: em caso de cancelamento, a aplicação provavelmente deve encerrar prematuramente atividades de segundo plano em andamento e resolver a promise em tempo hábil.
  • Desativação: encerramento do encaminhamento via StopOffer() [SWS_DM_00558] antes da destruição do objeto.

Diagrama de sequência: fluxo típico de registro, execução de rotina e desregistro. Fontes: [SWS_DM_00557], [SWS_DM_00554], [SWS_DM_00558]

Cenários de erro

Erros podem ocorrer tanto na configuração quanto durante o tempo de execução e a execução:

  • Violações de modelo e de mapeamento: se a resolução de InstanceSpecifier no modelo falhar, se ele não for identificado como PortPrototype ou se não existir um DiagnosticServiceGenericMapping correspondente, o framework reporta violações como InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation ou InstanceSpecifierAlreadyInUseViolation [SWS_DM_00552].
  • Erro de disponibilização: se Offer() for chamado enquanto o serviço já estiver sendo oferecido, a chamada falha e retorna o código de erro DiagOfferErrc::kAlreadyOffered [SWS_DM_00557].
  • Códigos de erro de diagnóstico (NRC): caso uma operação de rotina não possa ser concluída com sucesso ou a solicitação contenha parâmetros inválidos, a aplicação não cumpre a future retornada com OperationOutput, mas com um UDS Negative Response Code (NRC) adequado de DiagUdsNrcErrc conforme a ISO 14229-1 [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556].

              usar
              

              
A função Offer da classe ara::diag::GenericRoutine permite que o Diagnostic Management (DM) encaminhe mensagens de pedido de diagnóstico recebidas para uma rotina ao manipulador registado [SWS_DM_00557]. A chamada ocorre de forma síncrona, não recebe parâmetros e retorna um ara::core::Result<void> [SWS_DM_00557]. Uma vez que o método está declarado com a especificação noexcept, é considerado seguro contra exceções (exception safe) [SWS_DM_00557].

              


              Tratamento de erros
              

              
Se a disponibilização falhar, o método retorna um resultado negativo. Se a rotina já tiver sido oferecida anteriormente para a instância em questão, o método retorna o código de erro específico DiagOfferErrc::kAlreadyOffered [SWS_DM_00557]. Para este caso de erro está definida uma semântica de rollback, de modo que o estado permanece inalterado [SWS_DM_00557]. O identificador de erro kAlreadyOffered está, além disso, ancorado nos domínios de erro internos para chamadas de diagnóstico [SWS_DM_00514].

              


              Simultaneidade e restrições
              

              
A interface está expressamente especificada como não segura para threads (not thread-safe) [SWS_DM_00557]. Se múltiplas threads de uma aplicação acederem ao mesmo manipulador, a chamada deve ser sincronizada. Interpretação: a chamada deverá ocorrer tipicamente durante a inicialização, dado que nenhum pedido pode ser recebido antes da execução de Offer.

              


              Interação
              

              
A disponibilização de funcionalidades através de Offer é um padrão central no cluster de diagnóstico do AUTOSAR Adaptive; é utilizado de forma análoga também para interfaces de rotina específicas de tipo [SWS_DM_00594], serviços genéricos de UDS [SWS_DM_00619], bem como Data Identifiers [SWS_DM_00638]. Apesar da identidade de nome com ara::com, trata-se de uma implementação específica do Diagnostic Management SWS Diagnostics §7.3.4.1.2 «Monitors».
