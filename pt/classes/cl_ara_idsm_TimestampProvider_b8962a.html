Contexto

A classe ara::idsm::TimestampProvider é uma interface abstrata dentro do módulo AUTOSAR Adaptive idsm, que serve para o fornecimento de carimbos de data/hora para o Intrusion Detection System Manager (IdsM) [SWS_AIDSM_10400]. No sistema geral, a classe assume o papel de intermediária entre uma fonte concreta de temporização e o componente de plataforma do IdsM. Eventos típicos de segurança e Security-Events precisam ser registrados temporalmente com precisão, motivo pelo qual o IdsM recorre a uma instância configurada de um provedor de carimbos de data/hora.

Os principais parceiros de interação são a implementação de provedor específica da aplicação, o subsistema IdsM e o modelo de manifesto subjacente. A vinculação à modelagem ocorre por meio de um identificador de instância que representa a PPort associada [SWS_AIDSM_10401]. Por meio dessa instanciação de porta, define-se para qual endpoint de comunicação o provedor é responsável.

Ciclo de vida

O ciclo de vida de uma instância de ara::idsm::TimestampProvider divide-se nas fases de criação, disponibilização ativa de serviço, desativação e destruição:

  • Criação: o objeto é inicializado com um ara::core::InstanceSpecifier que referencia a PPort modelada [SWS_AIDSM_10401]. Esse construtor é declarado como explicit e seguro para threads (thread-safe).
  • Posse e semântica de cópia: como a instância está vinculada a uma modelagem concreta de porta e gerencia recursos do serviço, tanto o construtor de cópia [SWS_AIDSM_10404] quanto o operador de atribuição por cópia [SWS_AIDSM_10406] foram excluídos (= delete). Uma duplicação da instância do provedor é, portanto, excluída.
  • Semântica de movimento: a classe oferece suporte a operações de movimentação. O construtor de movimento é seguro para threads [SWS_AIDSM_10403]. Já a atribuição por movimento é especificada como não segura para threads [SWS_AIDSM_10405] e, portanto, exige sincronização externa caso objetos sejam movidos concorrentemente.
  • Mudança de estado: após a criação, o provedor encontra-se em estado de repouso. Por meio da chamada de Offer() [SWS_AIDSM_10408], o serviço é ativado, sinalizando ao IdsM que carimbos de data/hora podem ser consultados através do método de callback. A chamada de StopOffer() [SWS_AIDSM_10409] impede novamente chamadas subsequentes.
  • Destruição: a liberação ocorre por meio do destrutor virtual [SWS_AIDSM_10402]. Este não é seguro para threads. Antes da destruição, provavelmente deve-se sempre chamar StopOffer() para evitar que o IdsM ainda acesse o objeto durante a execução do destrutor.

Caminho de utilização

O uso regular de ara::idsm::TimestampProvider ocorre em uma sequência bem definida de etapas de integração e chamada:

  1. Derivação: uma aplicação deriva sua própria classe de provedor a partir de ara::idsm::TimestampProvider e implementa o método puramente virtual GetTimestamp() [SWS_AIDSM_10407]. Nesse método, o carimbo de data/hora atual do tipo TimestampType é determinado e retornado.
  2. Instanciação: a classe derivada é instanciada e passa a instância correspondente de ara::core::InstanceSpecifier para o construtor da classe base [SWS_AIDSM_10401].
  3. Oferta de serviço: antes da primeira coleta de Security-Events, a aplicação chama Offer() [SWS_AIDSM_10408]. Somente com isso a interface é liberada para o IdsM.
  4. Consulta pelo IdsM: assim que o IdsM necessita de carimbos de data/hora para eventos, ele chama autonomamente o callback GetTimestamp() [SWS_AIDSM_10407].
  5. Encerramento: para o encerramento ordenado do serviço, a aplicação chama StopOffer() [SWS_AIDSM_10409], garantindo que nenhuma consulta adicional de carimbo de data/hora seja feita pelo IdsM. Em seguida, o objeto pode ser destruído [SWS_AIDSM_10402].

Diagrama de sequência: ordem típica de chamadas para o fornecimento e a consulta de carimbos de data/hora pelo IdsM. Fontes: [SWS_AIDSM_10401], [SWS_AIDSM_10407], [SWS_AIDSM_10408], [SWS_AIDSM_10409]

Cenários de erro

Ao utilizar a classe, devem ser considerados especialmente concorrência, valores de retorno e garantias de exceção:

  • Falha na ativação do serviço: o método Offer() retorna um ara::core::Result<void> [SWS_AIDSM_10408]. Interpretação: o resultado retornado provavelmente conterá um código de erro em caso de falha se a PPort modelada for inválida ou se o registro interno no IdsM falhar. As aplicações devem avaliar o resultado antes de outras operações.
  • Concorrência: métodos essenciais como Offer() [SWS_AIDSM_10408], StopOffer() [SWS_AIDSM_10409], GetTimestamp() [SWS_AIDSM_10407], bem como o operador de atribuição por movimento [SWS_AIDSM_10405] e o destrutor [SWS_AIDSM_10402], são especificados como não seguros para threads. Chamadas paralelas a essas operações sem sincronização externa levam a comportamento indefinido.
  • Sem exceções (noexcept): todos os métodos da classe, incluindo GetTimestamp() [SWS_AIDSM_10407] e StopOffer() [SWS_AIDSM_10409], são declarados com noexcept. A implementação concreta de GetTimestamp() em classes derivadas não pode propagar exceções C++ para o exterior.

Este guia baseia-se exclusivamente nos requisitos de especificação da AUTOSAR Adaptive Platform para R25-11.

<h4>Contexto</h4>
<p>A classe <code>ara::idsm::TimestampProvider</code> é uma interface abstrata dentro do módulo AUTOSAR Adaptive <code>idsm</code>, que serve para o fornecimento de carimbos de data/hora para o Intrusion Detection System Manager (IdsM) <a class="spec-record-ref" data-req="SWS_AIDSM_10400" href="../spec/record.html?id=SWS_AIDSM_10400">[SWS_AIDSM_10400]</a>. No sistema geral, a classe assume o papel de intermediária entre uma fonte concreta de temporização e o componente de plataforma do IdsM. Eventos típicos de segurança e Security-Events precisam ser registrados temporalmente com precisão, motivo pelo qual o IdsM recorre a uma instância configurada de um provedor de carimbos de data/hora.</p>
<p>Os principais parceiros de interação são a implementação de provedor específica da aplicação, o subsistema IdsM e o modelo de manifesto subjacente. A vinculação à modelagem ocorre por meio de um identificador de instância que representa a PPort associada <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>. Por meio dessa instanciação de porta, define-se para qual endpoint de comunicação o provedor é responsável.</p>

<h4>Ciclo de vida</h4>
<p>O ciclo de vida de uma instância de <code>ara::idsm::TimestampProvider</code> divide-se nas fases de criação, disponibilização ativa de serviço, desativação e destruição:</p>
<ul>
  <li><strong>Criação:</strong> o objeto é inicializado com um <code>ara::core::InstanceSpecifier</code> que referencia a PPort modelada <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>. Esse construtor é declarado como <code>explicit</code> e seguro para threads (<em>thread-safe</em>).</li>
  <li><strong>Posse e semântica de cópia:</strong> como a instância está vinculada a uma modelagem concreta de porta e gerencia recursos do serviço, tanto o construtor de cópia <a class="spec-record-ref" data-req="SWS_AIDSM_10404" href="../spec/record.html?id=SWS_AIDSM_10404">[SWS_AIDSM_10404]</a> quanto o operador de atribuição por cópia <a class="spec-record-ref" data-req="SWS_AIDSM_10406" href="../spec/record.html?id=SWS_AIDSM_10406">[SWS_AIDSM_10406]</a> foram excluídos (<code>= delete</code>). Uma duplicação da instância do provedor é, portanto, excluída.</li>
  <li><strong>Semântica de movimento:</strong> a classe oferece suporte a operações de movimentação. O construtor de movimento é seguro para threads <a class="spec-record-ref" data-req="SWS_AIDSM_10403" href="../spec/record.html?id=SWS_AIDSM_10403">[SWS_AIDSM_10403]</a>. Já a atribuição por movimento é especificada como não segura para threads <a class="spec-record-ref" data-req="SWS_AIDSM_10405" href="../spec/record.html?id=SWS_AIDSM_10405">[SWS_AIDSM_10405]</a> e, portanto, exige sincronização externa caso objetos sejam movidos concorrentemente.</li>
  <li><strong>Mudança de estado:</strong> após a criação, o provedor encontra-se em estado de repouso. Por meio da chamada de <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>, o serviço é ativado, sinalizando ao IdsM que carimbos de data/hora podem ser consultados através do método de callback. A chamada de <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a> impede novamente chamadas subsequentes.</li>
  <li><strong>Destruição:</strong> a liberação ocorre por meio do destrutor virtual <a class="spec-record-ref" data-req="SWS_AIDSM_10402" href="../spec/record.html?id=SWS_AIDSM_10402">[SWS_AIDSM_10402]</a>. Este não é seguro para threads. Antes da destruição, provavelmente deve-se sempre chamar <code>StopOffer()</code> para evitar que o IdsM ainda acesse o objeto durante a execução do destrutor.</li>
</ul>

<h4>Caminho de utilização</h4>
<p>O uso regular de <code>ara::idsm::TimestampProvider</code> ocorre em uma sequência bem definida de etapas de integração e chamada:</p>
<ol>
  <li><strong>Derivação:</strong> uma aplicação deriva sua própria classe de provedor a partir de <code>ara::idsm::TimestampProvider</code> e implementa o método puramente virtual <code>GetTimestamp()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a>. Nesse método, o carimbo de data/hora atual do tipo <code>TimestampType</code> é determinado e retornado.</li>
  <li><strong>Instanciação:</strong> a classe derivada é instanciada e passa a instância correspondente de <code>ara::core::InstanceSpecifier</code> para o construtor da classe base <a class="spec-record-ref" data-req="SWS_AIDSM_10401" href="../spec/record.html?id=SWS_AIDSM_10401">[SWS_AIDSM_10401]</a>.</li>
  <li><strong>Oferta de serviço:</strong> antes da primeira coleta de Security-Events, a aplicação chama <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>. Somente com isso a interface é liberada para o IdsM.</li>
  <li><strong>Consulta pelo IdsM:</strong> assim que o IdsM necessita de carimbos de data/hora para eventos, ele chama autonomamente o callback <code>GetTimestamp()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a>.</li>
  <li><strong>Encerramento:</strong> para o encerramento ordenado do serviço, a aplicação chama <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>, garantindo que nenhuma consulta adicional de carimbo de data/hora seja feita pelo IdsM. Em seguida, o objeto pode ser destruído <a class="spec-record-ref" data-req="SWS_AIDSM_10402" href="../spec/record.html?id=SWS_AIDSM_10402">[SWS_AIDSM_10402]</a>.</li>
</ol>

<h4>Cenários de erro</h4>
<p>Ao utilizar a classe, devem ser considerados especialmente concorrência, valores de retorno e garantias de exceção:</p>
<ul>
  <li><strong>Falha na ativação do serviço:</strong> o método <code>Offer()</code> retorna um <code>ara::core::Result&lt;void&gt;</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>. Interpretação: o resultado retornado provavelmente conterá um código de erro em caso de falha se a PPort modelada for inválida ou se o registro interno no IdsM falhar. As aplicações devem avaliar o resultado antes de outras operações.</li>
  <li><strong>Concorrência:</strong> métodos essenciais como <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10408" href="../spec/record.html?id=SWS_AIDSM_10408">[SWS_AIDSM_10408]</a>, <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>, <code>GetTimestamp()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a>, bem como o operador de atribuição por movimento <a class="spec-record-ref" data-req="SWS_AIDSM_10405" href="../spec/record.html?id=SWS_AIDSM_10405">[SWS_AIDSM_10405]</a> e o destrutor <a class="spec-record-ref" data-req="SWS_AIDSM_10402" href="../spec/record.html?id=SWS_AIDSM_10402">[SWS_AIDSM_10402]</a>, são especificados como não seguros para threads. Chamadas paralelas a essas operações sem sincronização externa levam a comportamento indefinido.</li>
  <li><strong>Sem exceções (noexcept):</strong> todos os métodos da classe, incluindo <code>GetTimestamp()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10407" href="../spec/record.html?id=SWS_AIDSM_10407">[SWS_AIDSM_10407]</a> e <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10409" href="../spec/record.html?id=SWS_AIDSM_10409">[SWS_AIDSM_10409]</a>, são declarados com <code>noexcept</code>. A implementação concreta de <code>GetTimestamp()</code> em classes derivadas não pode propagar exceções C++ para o exterior.</li>
</ul>
