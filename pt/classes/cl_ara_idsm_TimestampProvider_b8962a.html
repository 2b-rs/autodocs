Permite que as aplicações forneçam carimbos de data/hora específicos do sistema para eventos de segurança do IdsM.

A classe ara::idsm::TimestampProvider fornece uma interface por meio da qual as aplicações podem alimentar carimbos de data/hora para o módulo IdsM por meio de uma PPort modelada [SWS_AIDSM_10400]. A ativação e desativação dos callbacks de consulta ocorrem por meio dos métodos Offer() e StopOffer() [SWS_AIDSM_10408] [SWS_AIDSM_10409]. As instâncias não são copiáveis, suportam semântica de movimentação e requerem sincronização externa para métodos sem segurança de thread garantida.

Contexto

A classe ara::idsm::TimestampProvider atua como uma interface para o fornecimento de carimbos de data/hora para o módulo Intrusion Detection System Manager (IdsM) dentro da AUTOSAR Adaptive Platform [SWS_AIDSM_10400]. Eventos e logs relevantes para a segurança no IdsM requerem informações de tempo confiáveis, obtidas por meio dessa classe provedora a partir da plataforma ou de uma fonte de tempo específica da aplicação. Uma instância de TimestampProvider é vinculada a uma PPort modelada por meio de um ara::core::InstanceSpecifier [SWS_AIDSM_10401]. Como o método GetTimestamp() é definido como uma função de callback puramente virtual [SWS_AIDSM_10407], TimestampProvider atua como uma classe base abstrata a partir da qual implementações concretas devem ser derivadas.

Ciclo de vida

A criação de um provedor de carimbo de data/hora ocorre explicitamente por meio do construtor, especificando o ara::core::InstanceSpecifier correspondente [SWS_AIDSM_10401]. Esse construtor é declarado como thread-safe. As operações de cópia são completamente impedidas: tanto o construtor de cópia [SWS_AIDSM_10404] quanto o operador de atribuição por cópia [SWS_AIDSM_10406] foram excluídos (= delete). As instâncias possuem, portanto, uma identidade exclusiva e não podem ser duplicadas.

Em contrapartida, a classe suporta a semântica de movimentação: o construtor de movimentação transfere recursos existentes de forma thread-safe para um novo objeto [SWS_AIDSM_10403]. A atribuição por movimentação via operator= também está presente, porém, ao contrário do construtor, não é thread-safe [SWS_AIDSM_10405]. O ciclo de vida da disponibilização ativa do serviço é controlado explicitamente após a instanciação: por meio do método Offer(), o registro para o IdsM é ativado [SWS_AIDSM_10408]. Com StopOffer(), o fornecimento é novamente impedido [SWS_AIDSM_10409]. A liberação da instância ocorre por meio do destrutor virtual [SWS_AIDSM_10402], o qual é especificado como não thread-safe. Interpretação: antes da destruição de uma instância, StopOffer() provavelmente deve ser tipicamente chamado para garantir que nenhuma chamada pendente pelo IdsM ocorra mais.

Caminho de utilização

O uso típico requer a derivação de uma classe específica da aplicação que substitui o método GetTimestamp() e retorna o carimbo de data/hora atual como TimestampType [SWS_AIDSM_10407]. Assim que a instância tiver sido criada para a respectiva porta [SWS_AIDSM_10401], a aplicação sinaliza a prontidão operacional por meio da chamada de Offer() [SWS_AIDSM_10408]. A partir desse momento, o IdsM pode invocar autonomamente o método de callback GetTimestamp() para situar temporalmente os eventos. Se o serviço tiver que ser encerrado ou o componente desativado, StopOffer() revoga a disponibilidade da interface [SWS_AIDSM_10409].

Diagrama de sequência: sequência de interação durante a inicialização, consulta de carimbo de data/hora pelo IdsM e encerramento do provedor. Fontes: [SWS_AIDSM_10401], [SWS_AIDSM_10407], [SWS_AIDSM_10408], [SWS_AIDSM_10409]

Cenários de erro

Todos os métodos da interface são declarados como noexcept e não lançam exceções de C++. Em vez disso, erros na ativação do fornecimento do serviço são transportados por meio do tipo de retorno ara::core::Result<void> de Offer() [SWS_AIDSM_10408]. Interpretação: se o registro no framework de comunicação ou de plataforma falhar (por exemplo, devido a uma configuração inadequada de porta), o Result retornado conterá um código de erro correspondente, que deverá ser verificado antes do uso posterior.

Atenção especial é exigida pelo comportamento de concorrência: nem o destrutor [SWS_AIDSM_10402] nem os métodos Offer() [SWS_AIDSM_10408], StopOffer() [SWS_AIDSM_10409], operator=(&&) [SWS_AIDSM_10405] ou GetTimestamp() [SWS_AIDSM_10407] são classificados como thread-safe. Os chamadores devem, portanto, assegurar que as operações de ciclo de vida e os processamentos de callback sejam executados de forma sincronizada entre threads e que não ocorram condições de corrida de dados.

Este guia baseia-se nos requisitos da especificação AUTOSAR para o módulo idsm (R25-11).
