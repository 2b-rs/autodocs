Contexto

A classe ara::tsync::ProviderTimeBaseValidationNotification é uma interface abstrata (interface de callback) no módulo AUTOSAR Adaptive tsync. Ela serve para notificar uma aplicação de validação hierarquicamente superior (Validator Application) sobre a disponibilidade de novos blocos de dados de medição gravados para uma base de tempo.

Num sistema global sincronizado no tempo, interagem tipicamente três componentes centrais:

  • tsync-Provider (Time Base): O subsistema de sincronização recolhe dados de protocolo e de temporização em tempo de execução. Assim que estiver disponível um novo bloco de medição, o provider chama os respetivos métodos de notificação.
  • ProviderTimeBaseValidationNotification: A interface abstrata de callback define os contratos de chamada para a transmissão de dados de medição de Master e Responder ([SWS_TS_00421], [SWS_TS_00423]).
  • Aplicação Validator: A lógica específica da aplicação implementa esta interface para avaliar os blocos de medição recebidos, realizar verificações de plausibilidade e monitorizar a validade da base de tempo.

Diagrama de contexto: Interação entre o tsync-Provider, a interface de callback e a aplicação Validator. Fontes: [SWS_TS_00421], [SWS_TS_00423].

Ciclo de vida

Dado que ProviderTimeBaseValidationNotification constitui uma classe base puramente abstrata com funções-membro puramente virtuais, não pode ser instanciada diretamente. O seu ciclo de vida divide-se nas seguintes fases:

  • Criação e relações de posse: A aplicação Validator deriva uma classe observadora concreta a partir de ProviderTimeBaseValidationNotification e instancia-a. A posse (Ownership) permanece na aplicação Validator.
  • Disponibilização: Interpretação: A instância de callback criada é registada na base de tempo a monitorizar do tsync-Provider, para que o provider possa reter referências a ela e realizar chamadas de método.
  • Estados: A própria interface não possui armazenamentos de estado internos. Após o registo, o objeto permanece no estado de prontidão de receção para os dados de medição que chegam.
  • Destruição: A classe possui um destruidor virtual padrão ~ProviderTimeBaseValidationNotification() noexcept = default; ([SWS_TS_01301]). Isto assegura que instâncias polimórficas sejam limpas devidamente aquando da libertação através de um ponteiro para a interface. Antes da destruição do objeto, tem de ser assegurado que o tsync-Provider não envia mais notificações para esta instância.
  • Concorrência: De acordo com a especificação, os métodos da interface estão classificados como non_threadsafe ([SWS_TS_00421], [SWS_TS_00423]). A aplicação Validator não pode, portanto, assumir que chamadas paralelas possam ser processadas com segurança de threads sem mecanismos de sincronização externos.

Caminho de utilização

O caminho de utilização típico descreve a receção e o reencaminhamento de dados de medição de temporização durante a operação ativa da base de tempo:

  1. Implementação do callback: A aplicação substitui ambos os métodos de interface SetMasterTimingData ([SWS_TS_00421]) e SetPdelayResponderData ([SWS_TS_00423]).
  2. Disponibilização na base de tempo: Presumivelmente, a aplicação passa uma referência para a instância derivada ao subsistema tsync para ativar a monitorização.
  3. Receção de dados do Time Master: Assim que existir um novo bloco de dados de medição para o Time Master da base de tempo, o subsistema tsync chama o método SetMasterTimingData ([SWS_TS_00421]). O chamador passa, neste caso, o parâmetro measurementData do tipo const TimeMasterMeasurementType&, o qual contém dados de validação detalhados do Time Master.
  4. Receção de dados do Pdelay Responder: Caso existam dados de medição gravados para o pDelay Responder da base de tempo, SetPdelayResponderData é chamado ([SWS_TS_00423]). Neste âmbito, é passado um bloco de dados do tipo const PdelayResponderMeasurementType& para avaliação.
  5. Avaliação e conclusão: A aplicação Validator verifica a conformidade e os desvios de valores-limite dos dados de medição obtidos. Em caso de paragem do sistema ou de conclusão da validação, a instância é libertada através do destruidor virtual ([SWS_TS_01301]).

Diagrama de sequência: Disponibilização de blocos de dados de medição através da interface de notificação. Fontes: [SWS_TS_00421], [SWS_TS_00423], [SWS_TS_01301].

Cenários de erro

No que concerne ao tratamento de erros e às condições de contorno, aplicam-se a ProviderTimeBaseValidationNotification as seguintes diretrizes:

  • Segurança contra exceções: Todas as funções-membro – SetMasterTimingData ([SWS_TS_00421]), SetPdelayResponderData ([SWS_TS_00423]) bem como o destruidor ([SWS_TS_01301]) – estão declaradas como noexcept e especificadas como exception safe. As implementações da aplicação Validator não podem deixar escapar exceções C++ a partir dos callbacks, uma vez que um estado de exceção numa função noexcept conduz imediatamente à interrupção do programa via std::terminate.
  • Valores de retorno e sinalização de erros: Os métodos possuem o tipo de retorno void. Não está prevista através desta interface uma resposta direta sobre o sucesso ou falha para o tsync-Provider.
  • Validade das referências: As estruturas de dados de medição passadas são transmitidas como referências constantes. A aplicação chamada tem de partir do princípio de que a validade dos dados pode estar limitada à duração da chamada do método, razão pela qual valores que necessitem de persistência devem ser copiados para estruturas próprias da aplicação.
  • Acesso concorrente: Como ambas as funções de notificação estão assinaladas como non_threadsafe ([SWS_TS_00421], [SWS_TS_00423]), uma chamada simultânea a partir de várias threads constitui uma violação de pré-condição. As chamadas deverão ocorrer de forma síncrona através do framework; caso uma implementação modifique estruturas de dados internas, terá de tomar precauções de sincronização próprias.

Este guia baseia-se na especificação AUTOSAR Adaptive R25-11 para o módulo tsync.

<h4>Ciclo de vida</h4>
<p>Dado que <code>ProviderTimeBaseValidationNotification</code> constitui uma classe base puramente abstrata com funções-membro puramente virtuais, não pode ser instanciada diretamente. O seu ciclo de vida divide-se nas seguintes fases:</p>
<ul>
<li><strong>Criação e relações de posse:</strong> A aplicação Validator deriva uma classe observadora concreta a partir de <code>ProviderTimeBaseValidationNotification</code> e instancia-a. A posse (Ownership) permanece na aplicação Validator.</li>
<li><strong>Disponibilização:</strong> Interpretação: A instância de callback criada é registada na base de tempo a monitorizar do tsync-Provider, para que o provider possa reter referências a ela e realizar chamadas de método.</li>
<li><strong>Estados:</strong> A própria interface não possui armazenamentos de estado internos. Após o registo, o objeto permanece no estado de prontidão de receção para os dados de medição que chegam.</li>
<li><strong>Destruição:</strong> A classe possui um destruidor virtual padrão <code>~ProviderTimeBaseValidationNotification() noexcept = default;</code> (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>). Isto assegura que instâncias polimórficas sejam limpas devidamente aquando da libertação através de um ponteiro para a interface. Antes da destruição do objeto, tem de ser assegurado que o tsync-Provider não envia mais notificações para esta instância.</li>
<li><strong>Concorrência:</strong> De acordo com a especificação, os métodos da interface estão classificados como <code>non_threadsafe</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>, <a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>). A aplicação Validator não pode, portanto, assumir que chamadas paralelas possam ser processadas com segurança de threads sem mecanismos de sincronização externos.</li>
</ul>

<h4>Caminho de utilização</h4>
<p>O caminho de utilização típico descreve a receção e o reencaminhamento de dados de medição de temporização durante a operação ativa da base de tempo:</p>
<ol>
<li><strong>Implementação do callback:</strong> A aplicação substitui ambos os métodos de interface <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>) e <code>SetPdelayResponderData</code> (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>).</li>
<li><strong>Disponibilização na base de tempo:</strong> Presumivelmente, a aplicação passa uma referência para a instância derivada ao subsistema tsync para ativar a monitorização.</li>
<li><strong>Receção de dados do Time Master:</strong> Assim que existir um novo bloco de dados de medição para o Time Master da base de tempo, o subsistema tsync chama o método <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>). O chamador passa, neste caso, o parâmetro <code>measurementData</code> do tipo <code>const TimeMasterMeasurementType&amp;</code>, o qual contém dados de validação detalhados do Time Master.</li>
<li><strong>Receção de dados do Pdelay Responder:</strong> Caso existam dados de medição gravados para o pDelay Responder da base de tempo, <code>SetPdelayResponderData</code> é chamado (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>). Neste âmbito, é passado um bloco de dados do tipo <code>const PdelayResponderMeasurementType&amp;</code> para avaliação.</li>
<li><strong>Avaliação e conclusão:</strong> A aplicação Validator verifica a conformidade e os desvios de valores-limite dos dados de medição obtidos. Em caso de paragem do sistema ou de conclusão da validação, a instância é libertada através do destruidor virtual (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>).</li>
</ol>

<h4>Cenários de erro</h4>
<p>No que concerne ao tratamento de erros e às condições de contorno, aplicam-se a <code>ProviderTimeBaseValidationNotification</code> as seguintes diretrizes:</p>
<ul>
<li><strong>Segurança contra exceções:</strong> Todas as funções-membro – <code>SetMasterTimingData</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>), <code>SetPdelayResponderData</code> (<a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>) bem como o destruidor (<a class="spec-record-ref" data-req="SWS_TS_01301" href="../spec/record.html?id=SWS_TS_01301">[SWS_TS_01301]</a>) – estão declaradas como <code>noexcept</code> e especificadas como <code>exception safe</code>. As implementações da aplicação Validator não podem deixar escapar exceções C++ a partir dos callbacks, uma vez que um estado de exceção numa função <code>noexcept</code> conduz imediatamente à interrupção do programa via <code>std::terminate</code>.</li>
<li><strong>Valores de retorno e sinalização de erros:</strong> Os métodos possuem o tipo de retorno <code>void</code>. Não está prevista através desta interface uma resposta direta sobre o sucesso ou falha para o tsync-Provider.</li>
<li><strong>Validade das referências:</strong> As estruturas de dados de medição passadas são transmitidas como referências constantes. A aplicação chamada tem de partir do princípio de que a validade dos dados pode estar limitada à duração da chamada do método, razão pela qual valores que necessitem de persistência devem ser copiados para estruturas próprias da aplicação.</li>
<li><strong>Acesso concorrente:</strong> Como ambas as funções de notificação estão assinaladas como <code>non_threadsafe</code> (<a class="spec-record-ref" data-req="SWS_TS_00421" href="../spec/record.html?id=SWS_TS_00421">[SWS_TS_00421]</a>, <a class="spec-record-ref" data-req="SWS_TS_00423" href="../spec/record.html?id=SWS_TS_00423">[SWS_TS_00423]</a>), uma chamada simultânea a partir de várias threads constitui uma violação de pré-condição. As chamadas deverão ocorrer de forma síncrona através do framework; caso uma implementação modifique estruturas de dados internas, terá de tomar precauções de sincronização próprias.</li>
</ul>
