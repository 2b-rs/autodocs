Contexto

A classe ara::idsm::EventReporter é o elo central de uma aplicação Adaptive para a detecção e o repasse de incidentes relevantes para a segurança ao Intrusion Detection System Manager (IdsM) de acordo com [SWS_AIDSM_10101]. Em uma arquitetura veicular moderna, componentes de software funcionais monitoram seus respectivos domínios quanto a anomalias relevantes para a segurança, violações de comunicação ou tentativas de acesso não autorizadas. Se uma aplicação detectar tal Security Event, EventReporter assume a notificação padronizada ao subsistema de segurança.

A interação ocorre por meio de uma porta formalmente definida no modelo de arquitetura de software do tipo de interface SecurityEventReportInterface. Ao criar a instância, essa porta é endereçada por meio de um ara::core::InstanceSpecifier [SWS_AIDSM_10301]. Dessa forma, a classe atua como uma interface tipificada entre a lógica específica da aplicação e a pilha IdsM de todo o veículo.

Ciclo de vida

Um objeto da classe ara::idsm::EventReporter é instanciado no lado da aplicação. O construtor parametrizado espera a referência a um ara::core::InstanceSpecifier e é declarado como noexcept, bem como thread-safe [SWS_AIDSM_10301]. Durante a inicialização, o objeto se vincula à porta configurada no modelo AUTOSAR. Após a construção bem-sucedida, essa vinculação de porta permanece inalterada; uma reconfiguração posterior não está prevista no nível da API (Interpretação: um EventReporter permanece firmemente vinculado à porta configurada durante todo o seu ciclo de vida).

Em termos de concorrência, a classe foi projetada para uso industrial com multithreading: tanto a criação [SWS_AIDSM_10301] quanto todas as variantes da função de notificação ReportEvent são especificadas como totalmente thread-safe ([SWS_AIDSM_10302] a [SWS_AIDSM_10307]). Portanto, várias threads de um processo podem chamar a mesma instância em paralelo e sem mecanismos externos de sincronização. O objeto segue o padrão RAII regular e libera seus recursos de plataforma de forma determinística ao sair do escopo.

Caminho de utilização

O fluxo de trabalho regular compreende a instanciação do reporter na inicialização do sistema ou na inicialização do componente, seguida por repetidas notificações de eventos durante a operação:

  1. Instanciar o reporter: com base no InstanceSpecifier específico do modelo, a instância é configurada por meio do construtor EventReporter(const ara::core::InstanceSpecifier&) [SWS_AIDSM_10301].
  2. Coletar dados de eventos: se ocorrer um desvio relevante para a segurança, a aplicação seleciona a sobrecarga apropriada de ReportEvent, dependendo de quais metadados estão disponíveis para o evento.
  3. Notificar evento: chamando ReportEvent, os contadores, as informações de contexto e os carimbos de data/hora são transmitidos ao IdsM.

Diagrama de sequência: fluxo típico desde a construção até a notificação do evento ao IdsM. Fontes: [SWS_AIDSM_10101], [SWS_AIDSM_10301], [SWS_AIDSM_10304]

A interface disponibiliza um total de seis sobrecargas graduadas, que cobrem todas as variantes dos parâmetros de eventos modelados:

  • Sem contexto: eventos puramente de contagem sem payload são passados por meio de ReportEvent(const CountType count = 1) [SWS_AIDSM_10302]. Se também for necessário registrar um momento específico de captura, a assinatura com TimestampType está disponível [SWS_AIDSM_10303].
  • Com dados de contexto: dados adicionais de diagnóstico ou de frame são transmitidos por meio de ContextDataType, opcionalmente sem carimbo de data/hora [SWS_AIDSM_10304] ou com carimbo de data/hora [SWS_AIDSM_10305].
  • Com dados de contexto versionados: caso o esquema dos dados de contexto esteja sujeito a alterações evolutivas, as assinaturas aceitam VersionedContextDataType, igualmente sem carimbo de data/hora [SWS_AIDSM_10306] bem como com carimbo de data/hora [SWS_AIDSM_10307].

Em todas as assinaturas, o parâmetro count possui o valor padrão 1, de modo que uma única ocorrência possa ser notificada sem indicação explícita de contador.

Cenários de erro

A API de ara::idsm::EventReporter foi projetada de forma defensiva e estritamente non-blocking para caminhos críticos de tempo real. Todos os métodos – tanto o construtor [SWS_AIDSM_10301] quanto todas as seis variantes de ReportEvent ([SWS_AIDSM_10302] a [SWS_AIDSM_10307]) – são declarados como noexcept e não possuem valor de retorno (void).

Disto decorrem condições arquiteturais essenciais:

  • Não são lançadas exceções de C++ na interface de chamada nem são retornados códigos de erro ara::core::Result.
  • O pré-requisito para o funcionamento correto é o fornecimento de um InstanceSpecifier válido e configurado no modelo AUTOSAR durante a criação do objeto.
  • Possíveis erros no armazenamento em buffer, sobrecarga do canal de transmissão ou inacessibilidade do serviço IdsM não podem ser comunicados de forma síncrona ao chamador (Interpretação: estouros internos de buffer ou falhas na comunicação do IdsM são registrados internamente na pilha da plataforma ou descartados para não bloquear a aplicação de tempo real chamadora).
