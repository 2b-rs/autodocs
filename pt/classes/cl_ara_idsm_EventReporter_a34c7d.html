Permite que as aplicações relatem Security Events com dados de contexto opcionais ao IdsM de forma thread-safe.

A classe ara::idsm::EventReporter serve no AUTOSAR Adaptive como interface de programação central para relatar eventos de segurança ao Intrusion Detection System Manager [SWS_AIDSM_10101]. Após a instanciação por meio de um ara::core::InstanceSpecifier para a porta modelada, as aplicações transmitem incidentes de forma flexível com contador, carimbo de data/hora ou dados de contexto (versionados) [SWS_AIDSM_10301]. Todos os métodos são explicitamente especificados como thread-safe e permitem o uso paralelo a partir de múltiplas threads da aplicação. Como todas as interfaces são providas de noexcept, erros de transmissão não são reportados ao chamador por meio de exceções C++.

Contexto

A classe ara::idsm::EventReporter atua na AUTOSAR Adaptive Platform como interface de programação primária para aplicações funcionais a fim de relatar eventos relevantes para a segurança (Security Events) ao Intrusion Detection System Management (IdsM) [SWS_AIDSM_10101]. Dentro da arquitetura da plataforma, a classe assume um papel mediador entre a lógica de detecção específica da aplicação e os serviços de segurança em toda a plataforma. Entre os parceiros diretos de interação estão componentes de software funcionais que identificam anomalias ou incidentes críticos de segurança, a instância mediadora EventReporter, bem como o serviço IdsM da Adaptive Platform, responsável pela coleta, filtragem e processamento posterior de eventos de segurança.

Diagrama de contexto: Integração do EventReporter entre a aplicação notificadora e o IdsM. Fontes: [SWS_AIDSM_10101], [SWS_AIDSM_10301]

Ciclo de vida

A criação de um objeto EventReporter ocorre por meio de seu construtor, passando um identificador do tipo ara::core::InstanceSpecifier [SWS_AIDSM_10301]. Este vincula a instância a uma porta do tipo SecurityEventReportInterface modelada no manifesto [SWS_AIDSM_10301]. A posse pertence à aplicação usuária; normalmente, deve ser conveniente mantê-la ativa durante todo o tempo de execução do componente para evitar vinculações repetidas à porta. Quanto à concorrência, a especificação garante total segurança de threads: tanto a construção quanto todos os métodos para relatar eventos são projetados como thread-safe [SWS_AIDSM_10301], [SWS_AIDSM_10302]. Com isso, múltiplas threads da aplicação podem utilizar a mesma instância do reporter em paralelo, sem a necessidade de medidas de sincronização externas.

Caminho de utilização

O fluxo regular abrange a instanciação do reporter, bem como o relato subsequente de incidentes por meio do método ReportEvent. Após a inicialização com o ara::core::InstanceSpecifier adequado [SWS_AIDSM_10301], a aplicação seleciona uma das sobrecargas disponibilizadas, dependendo do tipo de evento e do nível de detalhe das informações de contexto disponíveis:

  • Notificação sem contexto: Para eventos simples sem dados complementares, utiliza-se a sobrecarga básica, que transmite opcionalmente uma contagem de eventos (count, valor padrão 1) [SWS_AIDSM_10302].
  • Notificação com carimbo de data/hora: Se o evento deve ser provido de um momento de registro explícito, está disponível uma variante com TimestampType [SWS_AIDSM_10303].
  • Notificação com dados de contexto: Para a passagem de dados de diagnóstico ou detalhes do incidente, ReportEvent pode ser chamado com parâmetros do tipo ContextDataType, opcionalmente sem ou com carimbo de data/hora explícito [SWS_AIDSM_10304], [SWS_AIDSM_10305].
  • Notificação com dados de contexto versionados: Desde que o formato de comunicação esteja definido de forma estruturada ou dependente de versão, sobrecargas com VersionedContextDataType – igualmente com ou sem carimbo de data/hora – oferecem a interface correspondente [SWS_AIDSM_10306], [SWS_AIDSM_10307].

Assim que ReportEvent é chamado, o reporter encaminha os dados para o subsistema IdsM e retorna imediatamente para a aplicação.

Diagrama de sequência: Sequência de interação típica desde a criação do reporter até o relato do evento. Fontes: [SWS_AIDSM_10301], [SWS_AIDSM_10304]

Cenários de erro

Como pré-requisito essencial para o envio de notificações, aplica-se a construção bem-sucedida do EventReporter com um identificador de porta válido e registrado no modelo da plataforma [SWS_AIDSM_10301]. Em relação ao tratamento de erros e segurança contra exceções, todas as interfaces da classe apresentam uma particularidade: o construtor, bem como todas as sobrecargas de ReportEvent sem exceção, são declarados como noexcept [SWS_AIDSM_10301], [SWS_AIDSM_10302], [SWS_AIDSM_10303], [SWS_AIDSM_10304], [SWS_AIDSM_10305], [SWS_AIDSM_10306], [SWS_AIDSM_10307]. Não são disparadas exceções C++ nem são retornados objetos de erro como ara::core::Result. Se ocorrerem problemas de infraestrutura durante a transmissão para o IdsM, como gargalos de buffer ou falhas de serviço, estes devem ser tratados internamente no serviço da plataforma, descartados ou registrados em log, para não bloquear a aplicação notificadora.

Clase para reportar Security Events a IdsM.

A classe EventReporter está definida no cabeçalho ara/idsm/event_reporter.h e serve, na Adaptive Platform, para reportar eventos relevantes para a segurança (Security Events) ao Intrusion Detection System Management (IdsM) [SWS_AIDSM_10101].

Uso e instanciação

Para a utilização da classe, é necessário criar uma instância através do construtor parametrizado, que recebe um identificador do tipo const ara::core::InstanceSpecifier& [SWS_AIDSM_10301]. Este construtor inicializa o reporter para a porta do tipo SecurityEventReportInterface configurada no modelo do sistema [SWS_AIDSM_10301]. Interpretação: presume-se que a vinculação à porta modelada pressuponha que o InstanceSpecifier passado esteja definido de forma consistente no manifesto ARXML e possa ser resolvido em tempo de execução.

Tratamento de erros e simultaneidade

Em relação ao comportamento de exceções, a construção está especificada com noexcept [SWS_AIDSM_10301]; o construtor, portanto, não lança exceptions C++. No que diz respeito à concorrência, a função de construção está declarada explicitamente como thread-safe [SWS_AIDSM_10301]. Interpretação: presume-se, assim, que múltiplas threads possam instanciar paralelamente instâncias de reporter para as suas respectivas portas sem que sejam necessários mecanismos de sincronização externos.

Interação

A interação com o IdsM baseia-se na atribuição da instância à respectiva porta de modelagem: por meio da especificação como EventReporter para a SecurityEventReportInterface [SWS_AIDSM_10301], a classe representa a interface através da qual aplicações adaptativas transmitem eventos de segurança para a arquitetura do IdsM [SWS_AIDSM_10101].
