Contexto

A estrutura ara::diag::DTCInformation::SnapshotRecordUpdatedType é um tipo de dados especializado dentro do cluster funcional Diagnostics (AUTOSAR_AP_SWS_Diagnostics §8.48.5 «Struct: SnapshotRecordUpdatedType», [SWS_DM_00662]). A sua responsabilidade central reside no encapsulamento de dados de estado e de histórico, assim que os registos de snapshot (instantâneos ou freeze frames) de um determinado código de erro de diagnóstico (Diagnostic Trouble Code, DTC) tiverem sido atualizados no sistema de diagnóstico.

Numa arquitetura AUTOSAR Adaptive, este tipo interage essencialmente com três parceiros:

  • Gestão de diagnóstico (daemon / sistema básico): Monitoriza o ciclo de vida de eventos de diagnóstico e DTCs. Quando novos parâmetros ambientais relativos a um evento de erro são registados ou freeze frames existentes são sobrescritos, a plataforma instancia e preenche a estrutura.
  • Interface ara::diag::DTCInformation: Forma o espaço de nomes e disponibiliza o canal de comunicação para alterações de estado através do tipo de callback SnapshotRecordUpdatedTypeNotifier (AUTOSAR_AP_SWS_Diagnostics §8.48.2.1.5 «Type Alias: SnapshotRecordUpdatedTypeNotifier», [SWS_DM_02123]).
  • Aplicação adaptativa: Regista observadores para alterações de DTC, de modo a poder reagir atempadamente a dados de diagnóstico atualizados (por exemplo, para monitorização de frotas, registo de dados ou avisos ao condutor).

A estrutura agrupa duas propriedades essenciais: o campo de 32 bits DTC para a identificação do código de falha afetado (AUTOSAR_AP_SWS_Diagnostics §8.48.5.1.1 «DTC», [SWS_DM_02116]), bem como o vetor snapshotDataRecords (AUTOSAR_AP_SWS_Diagnostics §8.48.5.1.2 «snapshotDataRecords», [SWS_DM_02117]) do tipo ara::core::Vector<SnapshotDataRecordType>, que transporta os registos de dados atualizados concretos.

Ciclo de vida

Como SnapshotRecordUpdatedType está declarada como struct C++, o seu ciclo de vida segue o de uma estrutura pura de valores ou de transferência (Plain Old Data com contentores):

  • Criação: Uma instância é normalmente criada internamente pela plataforma através do ambiente de execução de diagnóstico, assim que for registada uma atualização dos dados de snapshot para um DTC. Os campos DTC e snapshotDataRecords são preenchidos antes do encaminhamento.
  • Relações de posse: A estrutura é transmitida através do callback do notificador SnapshotRecordUpdatedTypeNotifier ([SWS_DM_02123]) para o callback registado da aplicação. Parte-se do princípio (interpretação) de que a transmissão ocorre como referência const ou objeto de valor temporário, de modo a que a aplicação recetora avalie os dados sincronamente ou crie uma cópia própria, se necessário.
  • Estados: A estrutura não possui uma máquina de estados interna própria. Após a sua inicialização, ela existe como um instantâneo imutável de um evento de atualização.
  • Destruição: Se a instância sair do âmbito da chamada do notificador, a sua memória e a memória dinamicamente alocada do vetor snapshotDataRecords são desalocadas de forma determinística.
  • Concorrência: O SnapshotRecordUpdatedType não implementa mecanismos internos de sincronização. Como as chamadas do notificador podem normalmente ser executadas em worker threads separados do pipeline de diagnóstico, a aplicação deve assegurar a sincronização no processamento posterior thread-safe das suas próprias estruturas de dados.

Caminho de utilização

O fluxo típico para a utilização de SnapshotRecordUpdatedType divide-se nos seguintes passos:

  1. Registar notificador: A aplicação regista uma função de callback de acordo com a assinatura de SnapshotRecordUpdatedTypeNotifier ([SWS_DM_02123]) na instância de diagnóstico de ara::diag::DTCInformation.
  2. Deteção de eventos: O sistema de base reconhece uma alteração de estado ou um novo cálculo de dados de snapshot para um DTC ativo.
  3. Instanciação e notificação: O sistema de diagnóstico empacota o DTC afetado ([SWS_DM_02116]) e os registos de dados atualizados ([SWS_DM_02117]) numa instância de SnapshotRecordUpdatedType ([SWS_DM_00662]) e aciona o callback.
  4. Avaliação: A aplicação recebe o objeto, verifica o valor do DTC e itera sobre snapshotDataRecords para, por exemplo, avaliar parâmetros ambientais alterados.

Cenários de erro

Como struct de dados passiva, SnapshotRecordUpdatedType não disponibiliza métodos próprios que possam retornar ara::core::Result ou códigos de erro. Na interação, devem contudo ser consideradas as seguintes condições limite:

  • Lista de registos de dados vazia: É possível que snapshotDataRecords seja transmitido vazio (por exemplo, se registos de dados tiverem sido invalidados ou repostos). As aplicações devem sempre verificar se o vetor contém entradas antes do acesso por índice.
  • Atribuição de DTC: O valor em DTC corresponde ao identificador de 32 bits configurado ([SWS_DM_02116]). Se uma aplicação receber atualizações para um DTC que funcionalmente não processe, deve descartar o evento.
  • Pressão de memória com grandes registos de dados: Como snapshotDataRecords se baseia em ara::core::Vector, em caso de atualizações frequentes ou grandes payloads de snapshot, o esforço de cópia local pode influenciar a velocidade de processamento; uma duplicação desnecessária dos dados no callback deve ser evitada.

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 (módulo diag) e resume a arquitetura e a utilização de SnapshotRecordUpdatedType.
