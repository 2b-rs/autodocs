Permite que o skeleton de serviço disponibilize, atualize e processe de forma tipificada solicitações de campos.

A classe <SI-Namespace>::skeleton::fields::<Field> disponibiliza no lado do servidor um campo de um ServiceInterface e conecta funções de getter, setter e notificação para o serviço disponibilizado. A aplicação provedora registra handlers assíncronos ([SWS_CM_00114], [SWS_CM_00116]) para acessos de leitura e gravação recebidos e distribui alterações de valores ativamente aos clientes assinantes por meio do método Update ([SWS_CM_00119]). Nesse contexto, os handlers passados devem ser obrigatoriamente válidos, enquanto as chamadas de envio devem respeitar o tempo mínimo de envio configurado, a fim de evitar erros como kMinimumSendIntervalViolationError.

Contexto

A classe template <SI-Namespace>::skeleton::fields::<Field> encapsula a representação do lado do servidor de um campo modelado no ServiceInterface dentro do Adaptive Communication Management. Para cada campo definido na interface de serviço, o middleware gera uma instância de classe correspondente no namespace skeleton::fields utilizando o caminho de cabeçalho #include "<SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h". Um campo combina características funcionais de transferências de dados e de chamadas de método, dispondo opcionalmente de um getter, um setter e uma função de notificação. O tipo de dados associado do valor do campo é disponibilizado por meio do alias de tipo FieldType ([SWS_CM_11402]). Entre os parceiros de interação centrais estão a aplicação provedora que disponibiliza o serviço, a instância de campo do skeleton como intermediária, os consumidores do serviço assinantes (proxies) e contextos de execução opcionais na forma de um executor ([SWS_CM_11360], [SWS_CM_11362]).

Diagrama de contexto: parceiros de interação da classe Skeleton-Field em solicitações e notificações. Fontes: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360].

Ciclo de vida

O tempo de vida da instância de campo está estritamente acoplado à instância superior do skeleton de serviço. Interpretação: a instância de Field deve ser instanciada como objeto membro da classe skeleton associada e compartilhar integralmente seu ciclo de vida. A disponibilidade de métodos individuais da interface depende diretamente da definição no projeto de software: o método RegisterGetHandler só existe se o campo tiver sido configurado com Field.hasGetter == TRUE ([SWS_CM_00114]), enquanto RegisterSetHandler pressupõe a existência de um setter via Field.hasSetter == TRUE ([SWS_CM_00116]). Para proteger a comunicação contra falhas de transporte ponta a ponta, a aplicação pode registrar um handler específico via SetTransportFaultConditionHandler ([SWS_CM_00096]) e removê-lo novamente conforme necessário por meio de UnsetTransportFaultConditionHandler ([SWS_CM_00098]). Em relação à concorrência, as sobrecargas com o parâmetro de template ExecutorT (como ara::core::Executor) oferecem a possibilidade de transferir a execução das funções de callback para um contexto de execução assíncrono definido ([SWS_CM_11360], [SWS_CM_11362], [SWS_CM_00097], AUTOSAR_AP_EXP_ARAComAPI p. 11).

Caminho de utilização

O fluxo operacional regular divide-se na configuração das funções de callback, no processamento de consultas e no envio ativo de atualizações de dados:

Interpretação: o registro dos handlers deve ocorrer convenientemente antes da disponibilização do serviço, para permitir o atendimento contínuo das solicitações recebidas. Havendo um getter presente, a aplicação vincula via RegisterGetHandler uma função de callback que retorna um ara::core::Future<FieldType> ([SWS_CM_00114]). Para acessos de modificação, ela registra via RegisterSetHandler um handler que recebe o novo valor, o processa e disponibiliza o estado resultante também de forma assíncrona por meio de um future ([SWS_CM_00116]). Se o provedor de serviço desejar atualizar o valor do campo de forma autônoma, ele chama o método Update com o novo valor ([SWS_CM_00119], AUTOSAR_AP_EXP_ARAComAPI p. 11). Com isso, o estado interno do campo é redefinido. Caso o campo tenha sido modelado com função de notificação (Field.hasNotifier == TRUE), Update aciona a transmissão imediata do valor de dados alterado a todos os assinantes registrados ([SWS_CM_00119], [SWS_CM_00120], [SWS_CM_00162]).

Diagrama de sequência: fluxo típico de registro de handlers, processamento de solicitações e atualização de dados. Fontes: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119].

Cenários de erro

Condições de erro manifestam-se como violações de contratos de programação durante o registro ou como erros de transmissão em tempo de execução. Todos os métodos de registro para handlers – RegisterGetHandler, RegisterSetHandler e SetTransportFaultConditionHandler – são especificados como noexcept e possuem a garantia de exceção exception safe ([SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00096]). Aplica-se como pré-condição que o objeto chamável (callable) passado deve existir e não pode ser nulo; a não observância dessa regra gera uma InvalidHandlerViolation ([SWS_CM_00114], [SWS_CM_11360], [SWS_CM_00116], [SWS_CM_11362], [SWS_CM_00096], [SWS_CM_00097]).

Na atualização ativa via Update, o retorno de erro ocorre por meio do tipo de retorno ara::core::Result<void> ([SWS_CM_00119]). Se ocorrer um erro, o objeto Result fornece um código de erro de ara::com::ComErrc. Em particular, o envio em intervalos menores do que o definido pelo atributo de deployment ServiceInterfaceDeploymentElement.minimumSendInterval leva ao retorno do erro ComErrc::kMinimumSendIntervalViolationError ([SWS_CM_00119]).

função RegisterGetHandler [SWS_CM_00114] Upstream: RS_CM_00218, RS_AP_00114, RS_AP_00120, RS_AP_00127, RS_AP_00128, RS_AP_00138

void RegisterGetHandler (std::function< ara::core::Future< FieldType >()> handler) noexcept;

Register a callback function to be invoked when a Get() request is received. The method exists only if the offered service contains a Field and Field.hasGetter ==TRUE

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 01ae49e1e2d8 Procedência

usar

O método RegisterGetHandler é chamado no lado do servidor no objeto de campo de um skeleton ([SWS_CM_00114]). Ele existe no código gerado exclusivamente se um getter tiver sido configurado na descrição da interface para o campo em questão (Field.hasGetter == TRUE) (EXP ARAComAPI §5.4.8.1 «Registering Getters»). É passado um callback handler do tipo std::function<ara::core::Future<FieldType>()>, o qual é chamado pela implementação de binding mediante uma solicitação Get() recebida de um proxy.

O registro de tal handler é totalmente opcional (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Usualmente, a implementação do serviço não necessita de um handler de getter, uma vez que o Communication Management armazena em cache o valor definido mais recentemente via Update() e responde autonomamente a solicitações do proxy. Um handler é útil principalmente se a determinação do valor do campo for demorada ou computacionalmente intensiva e, portanto, deva ocorrer apenas sob demanda real de forma assíncrona através do padrão promise/future.

Tratamento de erros e condições de contorno

A função não possui valor de retorno, está declarada como noexcept e é segura contra exceções (exception safe) ([SWS_CM_00114]). Se o chamável passado não existir ou for null, ocorre o erro InvalidHandlerViolation ([SWS_CM_00114]).

Interação

Ao contrário de RegisterSetHandler, cuja chamada é obrigatória havendo um setter configurado (EXP ARAComAPI §5.4.8.2 «Registering Setters»), RegisterGetHandler permanece puramente opcional. Caso o handler deva ser processado de forma assíncrona em um contexto de execução específico, está disponível adicionalmente a função de template sobrecarregada com ExecutorT ([SWS_CM_11360]).

      usar
      

      O método RegisterGetHandler no namespace <SI-Namespace>::skeleton::fields::<Field> registra um callback do lado da aplicação (handler), que é chamado pelo binding de comunicação mediante uma chamada Get() de entrada de um proxy ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). Diferente da sobrecarga básica sem parâmetros [SWS_CM_00114], o método recebe um contexto de execução executor do tipo ExecutorT, no qual a execução do callback ocorre de forma assíncrona ([SWS_CM_11360]). Como executor, pode ser utilizado o ara::core::Executor padronizado ou um tipo específico do usuário com a mesma interface ([SWS_CM_11360]).
      

      O manipulador registrado retorna um ara::core::Future<FieldType>, desacoplando o cálculo do valor do campo através do padrão Promise/Future ([SWS_CM_11360], EXP ARAComAPI §5.4.8.1 «Registering Getters»). O registro é totalmente opcional: caso nenhum manipulador esteja registrado, o Communication Management responde às requisições de forma autônoma com o último valor definido via Update() (EXP ARAComAPI §5.4.8.1 «Registering Getters»). Um manipulador getter é adequado primariamente para a determinação sob demanda de valores de campos complexos ou demorados (EXP ARAComAPI §5.4.8.1 «Registering Getters»).
      

      Restrições e tratamento de erros
      

      O método existe no skeleton exclusivamente quando um getter foi configurado na IDL para o campo (Field.hasGetter == TRUE, [SWS_CM_00114], EXP ARAComAPI §5.4.8.1 «Registering Getters»). RegisterGetHandler é declarado como noexcept; no entanto, se um callable inválido ou vazio for passado, ocorre um InvalidHandlerViolation ([SWS_CM_11360]). Interpretação: o executor fornecido provavelmente deve permanecer válido durante todo o período de uso do manipulador, já que requisições recebidas são encaminhadas de forma assíncrona em seu contexto.

          usar
          

          O método RegisterSetHandler serve, no lado do servidor (skeleton), para registrar uma função de callback que é chamada na chegada de uma requisição Set() de um cliente para um campo [SWS_CM_00116]. O método existe exclusivamente quando o campo oferecido está configurado com suporte a setter (Field.hasSetter == TRUE) [SWS_CM_00116]. Em contraste com o registro de getter, a chamada de RegisterSetHandler é obrigatória, uma vez que a implementação do servidor deve validar previamente valores de campos novos ou atualizados de clientes anônimos EXP ARAComAPI §5.4.8.2 «Registering Setters».
          

          O tratador registrado recebe o novo valor como argumento e retorna um ara::core::Future<FieldType> com o valor efetivo, eventualmente corrigido [SWS_CM_00116], EXP ARAComAPI §5.4.8.2 «Registering Setters». Este valor efetivo é adotado implicitamente pelo gerenciamento de comunicação e publicado para os clientes; uma chamada explícita de Update() dentro do tratador é, portanto, desnecessária EXP ARAComAPI §5.4.8.2 «Registering Setters».
          

          Tratamento de erros e condições de contorno
          

          A função é definida como noexcept e é segura contra exceções [SWS_CM_00116]. Se for passado um callable inexistente ou inválido (nulo), ocorre uma violação de especificação na forma de uma InvalidHandlerViolation [SWS_CM_00116]. Interpretação: O registro deve ter que ocorrer antes da disponibilização do serviço via OfferService(), para que seja possível receber requisições de clientes desde o início.
          

          Interação
          

          Além do método básico, existe uma sobrecarga de template [SWS_CM_11362], com a qual a execução do tratador pode ser vinculada a um contexto de execução específico (ExecutorT conforme [SWS_CM_11360]) EXP ARAComAPI.

Concretamente, ComErrc::kMinimumSendIntervalViolationError é retornado com semântica de rollback caso as solicitações de envio ocorram mais rapidamente do que o estipulado pelo intervalo mínimo de envio configurado ServiceInterfaceDeploymentElement.minimumSendInterval ([SWS_CM_00119]).
                              

  
                              No ciclo de vida do serviço, é necessária uma chamada inicial de Update() antes de oferecer o serviço: se OfferService() for chamado antes de o valor do campo ter sido inicializado, a disponibilização falha com ComErrc::kFieldValueNotInitialized ([SWS_CM_00101], [SWS_CM_00128]). Na ausência de uma garantia explícita de reentrância no padrão, chamadas simultâneas na mesma instância de campo deverão ser sincronizadas no lado da aplicação.
