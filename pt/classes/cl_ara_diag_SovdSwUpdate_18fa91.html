Atua como interface para o processamento de atualizações de software por meio do protocolo ASAM SOVD no servidor de diagnóstico AUTOSAR.

A classe fornece a interface do lado da aplicação para o processamento de atualizações padronizadas de software por meio do protocolo SOVD em conformidade com o ASAM SOVD [SWS_DM_01796]. Após a instanciação, a aplicação ativa o encaminhamento de requisições de diagnóstico para os manipuladores de atualização específicos por meio do método Offer() [SWS_DM_01924]. Pacotes são registrados, preparados, instalados de forma automatizada ou manual, bem como excluídos por meio de métodos assíncronos. Todos os processos relevantes para a transmissão de dados e o ciclo de vida são processados de forma não bloqueante por meio de futures.

Contexto

A classe ara::diag::SovdSwUpdate define a interface para a implementação de atualizações padronizadas de software em conformidade com o ASAM SOVD dentro da AUTOSAR Adaptive Platform [SWS_DM_01874]. Como a lógica de negócio propriamente dita das atualizações de software não reside no cluster funcional Diagnostic Management (DM), a execução permanece com a respectiva aplicação, enquanto ara::diag::SovdSwUpdate se concentra no processamento em conformidade com o padrão do protocolo SOVD subjacente AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept». Para o upload de arquivos de atualização, utilizam-se estratégias de transmissão tais como especificadas para o serviço UDS 0x38 (RequestFileTransfer) AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept», [SWS_DM_01923].

Três componentes essenciais participam dos processos: o cliente SOVD externo, a instância do Diagnostic Server (DM) para gerenciamento de protocolos e rotas, bem como a implementação de manipulador específica da aplicação de ara::diag::SovdSwUpdate [SWS_DM_01796], [SWS_DM_01924].

Diagrama de contexto: interação entre o cliente SOVD, o Diagnostic Server (DM) e ara::diag::SovdSwUpdate. Fontes: [SWS_DM_01796], [SWS_DM_01924], AUTOSAR_AP_SWS_Diagnostics §7.4 «SOVD Software Update API - concept»

Ciclo de vida

A instanciação de ara::diag::SovdSwUpdate ocorre por meio do construtor mediante a especificação de um ara::core::InstanceSpecifier, que faz referência a um protótipo de porta de um DiagnosticSovdUpdateInterface modelado, bem como de um modo de simultaneidade (ConcurrencyType: kConcurrent ou kNotConcurrent) [SWS_DM_01910]. O construtor é especificado como seguro para threads e seguro quanto a exceções [SWS_DM_01910]. Por representar uma instância única de interface, o construtor de cópia e o operador de atribuição por cópia estão excluídos (=delete) e são protegidos [SWS_DM_01912], [SWS_DM_01914]. A construção por movimento e a atribuição por movimento estão disponíveis de forma protegida, mas não são seguras para threads [SWS_DM_01913], [SWS_DM_01915].

A destruição do objeto é realizada por meio do destrutor virtual ~SovdSwUpdate(), que é considerado não seguro para threads [SWS_DM_01911]. Se os métodos de retorno de chamada virtuais da classe precisam ser executados concorrentemente depende diretamente do ConcurrencyType passado ao construtor [SWS_DM_01910], [SWS_DM_01916].

Caminho de utilização

Interpretação: Como os métodos de interface fornecidos são declarados como virtuais puros (=0), supõe-se que uma classe de aplicação derivada os implemente para realizar a execução real da atualização, enquanto a classe base regula a conexão com a plataforma. Pergunta Q-10500d9fc58503ea (aberta)

O fluxo regular é dividido nas seguintes fases:

  • Disponibilização: Após a criação do objeto, a aplicação chama Offer() para permitir que o Diagnostic Management encaminhe mensagens SOVD recebidas para esta instância [SWS_DM_01924].
  • Consulta e registro: Pacotes de atualização existentes podem ser consultados via GetAllUpdates() [SWS_DM_01797], [SWS_DM_01916]. Caso um novo pacote deva ser transmitido, o Diagnostic Server solicita um registro via RequestUpdatePackageRegistration(), o qual disponibiliza de forma assíncrona uma sessão de escrita (DataTransferWriteSession) juntamente com um ID de pacote de atualização [SWS_DM_01923]. Detalhes e status são determinados por meio de GetUpdatePackageDetails() e GetUpdatePackageStatus() [SWS_DM_01802], [SWS_DM_01917], [SWS_DM_01921].
  • Instalação ou exclusão: A instalação pode ser iniciada de forma automatizada por meio de PutUpdatePackageAutomated() [SWS_DM_01799], [SWS_DM_01918] ou realizada em duas etapas via PrepareUpdatePackage() [SWS_DM_01800], [SWS_DM_01919] seguido de ExecuteUpdatePackage() [SWS_DM_01801], [SWS_DM_01920]. Pacotes que não são mais necessários são removidos via DeleteUpdatePackage() [SWS_DM_01922].
  • Finalização: Antes do encerramento, a aplicação desativa o encaminhamento de mensagens chamando StopOffer() [SWS_DM_01925].

Diagrama de sequência: fluxo típico de um registro e instalação de pacote via SOVD. Fontes: [SWS_DM_01799], [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923], [SWS_DM_01924]

Cenários de erro

Ao oferecer os serviços via Offer(), erros específicos podem ocorrer no tipo de retorno ara::core::Result<void>: DiagOfferErrc::kAlreadyOffered, caso a instância já esteja sendo oferecida, bem como DiagOfferErrc::kConfigurationMismatch, se a configuração não coincidir com o extrato de diagnóstico (DEXT) [SWS_DM_01924].

Se o construtor for chamado com um estado de modelo incorreto, violações de arquitetura serão reportadas, entre elas InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation ou InstanceSpecifierAlreadyInUseViolation [SWS_DM_01910].

Todas as operações funcionais de atualização retornam um ara::core::Future que, em caso de falha, transporta códigos de erro de acordo com ASAM SOVD 1.1 ou ISO 17978-3 [SWS_DM_01917], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923]. Além disso, todos os métodos assíncronos recebem um CancellationHandler por meio do qual é sinalizado um cancelamento prematuro da conexão de diagnóstico em andamento [SWS_DM_01916], [SWS_DM_01919], [SWS_DM_01923].

A função puramente virtual DeleteUpdatePackage da classe ara::diag::SovdSwUpdate é chamada pela instância do Diagnostic Server de acordo com [SWS_DM_01803] quando o método SOVD “Delete Update Package from an SOVD Server” deve ser executado ([SWS_DM_01922]). Ela inicia a remoção de um pacote de atualização no lado do servidor.

A chamada ocorre de forma assíncrona e retorna um ara::core::Future<void>, que indica a conclusão bem-sucedida ou disponibiliza um objeto de erro [SWS_DM_01922]. A assinatura requer os seguintes parâmetros de entrada:

  • updatePackageId: Designa como ara::core::String o ID unívoco do pacote de atualização a ser excluído.
  • metaInfo: Passa como MetaInfo const& informações de contexto adicionais da requisição.
  • cancellationHandler: Transmite um objeto do tipo CancellationHandler, que informa se a conversa atual foi cancelada.

Se ocorrer um erro durante o processamento, o Future é preenchido com um erro SOVD correspondente. Para isso, a especificação prescreve o uso de códigos de erro adequados da ASAM SOVD 1.1 ou ISO 17978-3 [SWS_DM_01922].

Em relação à concorrência, o método é definido como condicionalmente thread-safe: se a implementação deve ser executada como thread-safe ou non-thread-safe é determinado por meio do ConcurrencyType passado no construtor [SWS_DM_01922]. Além disso, a função é declarada como noexcept e segura contra exceções, razão pela qual nenhuma exceção pode escapar.

                                  A função puramente virtual RequestUpdatePackageRegistration da classe ara::diag::SovdSwUpdate atende ao método SOVD “Register an Update at the SOVD Server” [SWS_DM_01923]. Ela inicia o registro de um pacote de atualização no servidor e dá início à respectiva sessão de transferência AUTOSAR_AP_SWS_Diagnostics §8.58.2.1.3.9 «RequestUpdatePackageRegistration».
                                  

                                  A chamada ocorre de forma assíncrona e retorna um ara::core::Future que, em caso de sucesso, contém uma tupla composta por uma DataTransferWriteSession e uma ara::core::String com o ID do pacote de atualização [SWS_DM_01923]. Na chamada, são passados os seguintes parâmetros:
                                  

                                    

                                  • metaInfo: Metainformações da requisição de entrada.
                                    • 

                                  • expectedSize: Tamanho total esperado opcional do pacote (ara::core::Optional<uint64_t>), caso declarado na requisição.
                                    • 

                                  • cancellationHandler: Sinaliza caso a conversa atual seja cancelada.
                                    • 

                                  

                                  O método é definido como noexcept e seguro contra exceções [SWS_DM_01923]. Consequentemente, os erros não são reportados por meio de exceções C++, mas sim disponibilizados assincronamente via Future; para isso, devem ser empregados os códigos de erro correspondentes da ASAM SOVD 1.1 ou ISO 17978-3 [SWS_DM_01923].
                                  

                                  A segurança de threads é condicional (“conditional”): se o método deve ser implementado como thread-safe é determinado por meio do ConcurrencyType especificado no construtor [SWS_DM_01923]. A implementação concreta, portanto, presumivelmente deverá exigir mecanismos de sincronização próprios, dependendo da instanciação.                                                   O método ara::diag::SovdSwUpdate::StopOffer encerra a oferta do serviço e desativa o encaminhamento de mensagens de requisição de entrada do Diagnostic Management (DM) para o componente de atualização de software [SWS_DM_01925]. A chamada ocorre por meio da interface de ara/diag/sovd_sw_update.h, não possui parâmetros e não fornece valor de retorno [SWS_DM_01925]. O encerramento da disponibilização do serviço ocorre de forma síncrona e corresponde à desativação conceitual de funcionalidades de diagnóstico no AUTOSAR Adaptive AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 «Monitors».
                                                  


                                                  Tratamento de erros e simultaneidade
                                                  

                                                  A função possui a especificação noexcept e é, portanto, segura contra exceções; estados de erro por meio de exceções ou códigos de erro não estão previstos [SWS_DM_01925]. Para o contexto de chamada, aplica-se que a função é definida como não segura para threads (“not thread-safe”) [SWS_DM_01925]. Chamadas paralelas na mesma instância devem ser sincronizadas no lado da aplicação. Interpretação: uma chamada repetida de StopOffer no estado já inativo presumivelmente deverá permanecer sem efeito de erro, visto que não existe tratamento de erros.
