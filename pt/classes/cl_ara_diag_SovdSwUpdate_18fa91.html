Contexto

A classe ara::diag::SovdSwUpdate constitui a interface para o processamento de atualizações de software através do protocolo Service-Oriented Vehicle Diagnostics (SOVD) em conformidade com ASAM SOVD e ISO 17978-3 ([SWS_DM_01874], [SWS_DM_01796]). No âmbito da AUTOSAR Adaptive Platform, existe uma clara divisão funcional de tarefas: a lógica de negócio propriamente dita para a execução e gestão de atualizações de software permanece na aplicação adaptativa, enquanto o cluster funcional Diagnostics (Diagnostic Server Instance ou Diagnostic Management) assume o tratamento do protocolo SOVD subjacente (AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»).

Como classe base abstrata, SovdSwUpdate define as interfaces de callback que têm de ser implementadas pelo software de aplicação. Pedidos recebidos de clientes SOVD externos são analisados pela Diagnostic Server Instance e delegados na aplicação através dos métodos correspondentes de SovdSwUpdate (AUTOSAR_AP_SWS_Diagnostics §7.3 «SOVD Software Update API»).

Diagrama de contexto: parceiros de interação e distribuição de funções na atualização de software via SOVD. Fontes: [SWS_DM_01796], [SWS_DM_01874], AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»

Ciclo de vida

A criação de uma instância específica da aplicação ocorre através do construtor parametrizado mediante a indicação de um identificador de instância (ara::core::InstanceSpecifier) e do modelo de concorrência pretendido (ConcurrencyType) ([SWS_DM_01910]). O InstanceSpecifier referencia, neste caso, um PortPrototype declarado no manifesto de software, que tem de ser tipificado para um DiagnosticSovdUpdateInterface ([SWS_DM_01910]). Através do concurrencyType define-se se os métodos de callback da instância devem ser acionados de forma segura para threads (kConcurrent) ou sequencial/não segura para threads (kNotConcurrent) no caso de pedidos simultâneos ([SWS_DM_01910]).

As instâncias de SovdSwUpdate estão vinculadas de forma biunívoca a uma porta de serviço. O construtor de cópia e o operador de atribuição foram, por isso, explicitamente eliminados (=delete) ([SWS_DM_01912], [SWS_DM_01914]). As operações move estão definidas como protegidas (protected) ([SWS_DM_01913], [SWS_DM_01915]).

Após uma inicialização bem-sucedida, a aplicação tem de ativar explicitamente o serviço através de Offer() ([SWS_DM_01924]). Apenas esta chamada faz com que o Diagnostic Manager (DM) encaminhe pedidos SOVD recebidos para os métodos de tratamento (handler) registados. Antes da destruição do objeto handler, o serviço deve ser desregistado via StopOffer() para impedir um posterior encaminhamento de pedidos ([SWS_DM_01925]). A desativação é concluída através do destrutor virtual ~SovdSwUpdate() ([SWS_DM_01911]).

Caminho de utilização

O fluxo operacional típico compreende várias fases consecutivas de uma atualização de software:

  1. Disponibilização do serviço: A aplicação instancia a sua derivação de SovdSwUpdate e chama Offer() ([SWS_DM_01924]).
  2. Registo de pacotes e transferência: O Diagnostic Server encaminha pedidos de registo recebidos de um cliente SOVD para RequestUpdatePackageRegistration() ([SWS_DM_01923]). O método retorna um ara::core::Future com um tuplo composto por uma sessão de escrita (DataTransferWriteSession) e um identificador inequívoco de pacote (updatePackageId) ([SWS_DM_01923]). Interpretação: A transferência de dados propriamente dita dos dados úteis de atualização deverá ser processada através desta sessão de escrita disponibilizada (AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»).
  3. Preparação do pacote: Para preparar a instalação, o Diagnostic Server chama PrepareUpdatePackage() ([SWS_DM_01800], [SWS_DM_01919]). Em alternativa, pode ser acionada uma instalação automatizada através de PutUpdatePackageAutomated() ([SWS_DM_01799], [SWS_DM_01918]).
  4. Execução do pacote: A instalação do pacote de atualização preparado é iniciada através da chamada de ExecuteUpdatePackage() ([SWS_DM_01801], [SWS_DM_01920]).
  5. Consulta de estado e inspeção: Durante ou após o processo, informações detalhadas e o estado podem ser consultados através de GetUpdatePackageStatus() ([SWS_DM_01802], [SWS_DM_01921]), GetUpdatePackageDetails() ([SWS_DM_01917]) ou a lista completa através de GetAllUpdates() ([SWS_DM_01797], [SWS_DM_01916]). Os pacotes já não necessários são removidos através de DeleteUpdatePackage() ([SWS_DM_01922]).

Diagrama de sequência: padrões de interação para registo, instalação e consulta de estado de um pacote de atualização. Fontes: [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01802], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01923], [SWS_DM_01924]

Cenários de erro

As condições de erro dividem-se em erros de configuração e de modelação, erros de estado do serviço, bem como erros de execução específicos do protocolo:

  • Erros de modelo e de instanciação: Se a resolução do InstanceSpecifier falhar ou se este referenciar um elemento inadequado, são reportadas violações específicas em tempo de execução (Violations): InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation bem como InstanceSpecifierAlreadyInUseViolation, caso o identificador já esteja a ser utilizado dentro do processo ([SWS_DM_01910]).
  • Erros de disponibilização: A chamada de Offer() retorna um ara::core::Result<void>. Em caso de erro, este contém DiagOfferErrc::kAlreadyOffered, se o serviço já estiver a ser disponibilizado, ou DiagOfferErrc::kConfigurationMismatch, se a configuração não coincidir com o extrato de diagnóstico (DEXT) ([SWS_DM_01924]).
  • Erros de execução e de protocolo: Os métodos de callback assíncronos retornam resultados como ara::core::Future. Em caso de erro, deve ser guardado no Future um código de erro aplicável em conformidade com a ASAM SOVD 1.1 ou a ISO 17978-3 ([SWS_DM_01917], [SWS_DM_01918], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01922], [SWS_DM_01923]).
  • Tratamento de cancelamento: A todos os métodos assíncronos é transmitido um CancellationHandler. A aplicação é responsável por consultar este último, a fim de terminar de forma limpa uma conversação de cliente abortada prematuramente ([SWS_DM_01919], [SWS_DM_01920]).

Este guia baseia-se na especificação AUTOSAR Adaptive Platform Release R25-11.

<h4>Ciclo de vida</h4>
<p>A criação de uma instância específica da aplicação ocorre através do construtor parametrizado mediante a indicação de um identificador de instância (<code>ara::core::InstanceSpecifier</code>) e do modelo de concorrência pretendido (<code>ConcurrencyType</code>) (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>). O <code>InstanceSpecifier</code> referencia, neste caso, um <code>PortPrototype</code> declarado no manifesto de software, que tem de ser tipificado para um <code>DiagnosticSovdUpdateInterface</code> (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>). Através do <code>concurrencyType</code> define-se se os métodos de callback da instância devem ser acionados de forma segura para threads (<code>kConcurrent</code>) ou sequencial/não segura para threads (<code>kNotConcurrent</code>) no caso de pedidos simultâneos (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>).</p>
<p>As instâncias de <code>SovdSwUpdate</code> estão vinculadas de forma biunívoca a uma porta de serviço. O construtor de cópia e o operador de atribuição foram, por isso, explicitamente eliminados (<code>=delete</code>) (<a class="spec-record-ref" data-req="SWS_DM_01912" href="../spec/record.html?id=SWS_DM_01912">[SWS_DM_01912]</a>, <a class="spec-record-ref" data-req="SWS_DM_01914" href="../spec/record.html?id=SWS_DM_01914">[SWS_DM_01914]</a>). As operações move estão definidas como protegidas (<code>protected</code>) (<a class="spec-record-ref" data-req="SWS_DM_01913" href="../spec/record.html?id=SWS_DM_01913">[SWS_DM_01913]</a>, <a class="spec-record-ref" data-req="SWS_DM_01915" href="../spec/record.html?id=SWS_DM_01915">[SWS_DM_01915]</a>).</p>
<p>Após uma inicialização bem-sucedida, a aplicação tem de ativar explicitamente o serviço através de <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>). Apenas esta chamada faz com que o Diagnostic Manager (DM) encaminhe pedidos SOVD recebidos para os métodos de tratamento (handler) registados. Antes da destruição do objeto handler, o serviço deve ser desregistado via <code>StopOffer()</code> para impedir um posterior encaminhamento de pedidos (<a class="spec-record-ref" data-req="SWS_DM_01925" href="../spec/record.html?id=SWS_DM_01925">[SWS_DM_01925]</a>). A desativação é concluída através do destrutor virtual <code>~SovdSwUpdate()</code> (<a class="spec-record-ref" data-req="SWS_DM_01911" href="../spec/record.html?id=SWS_DM_01911">[SWS_DM_01911]</a>).</p>

<h4>Caminho de utilização</h4>
<p>O fluxo operacional típico compreende várias fases consecutivas de uma atualização de software:</p>
<ol>
<li><strong>Disponibilização do serviço:</strong> A aplicação instancia a sua derivação de <code>SovdSwUpdate</code> e chama <code>Offer()</code> (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>).</li>
<li><strong>Registo de pacotes e transferência:</strong> O Diagnostic Server encaminha pedidos de registo recebidos de um cliente SOVD para <code>RequestUpdatePackageRegistration()</code> (<a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>). O método retorna um <code>ara::core::Future</code> com um tuplo composto por uma sessão de escrita (<code>DataTransferWriteSession</code>) e um identificador inequívoco de pacote (<code>updatePackageId</code>) (<a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>). Interpretação: A transferência de dados propriamente dita dos dados úteis de atualização deverá ser processada através desta sessão de escrita disponibilizada (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=223">AUTOSAR_AP_SWS_Diagnostics §7.3 «Figure 7.4: SOVD Software Update API»</a>).</li>
<li><strong>Preparação do pacote:</strong> Para preparar a instalação, o Diagnostic Server chama <code>PrepareUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01800" href="../spec/record.html?id=SWS_DM_01800">[SWS_DM_01800]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>). Em alternativa, pode ser acionada uma instalação automatizada através de <code>PutUpdatePackageAutomated()</code> (<a class="spec-record-ref" data-req="SWS_DM_01799" href="../spec/record.html?id=SWS_DM_01799">[SWS_DM_01799]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>).</li>
<li><strong>Execução do pacote:</strong> A instalação do pacote de atualização preparado é iniciada através da chamada de <code>ExecuteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01801" href="../spec/record.html?id=SWS_DM_01801">[SWS_DM_01801]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
<li><strong>Consulta de estado e inspeção:</strong> Durante ou após o processo, informações detalhadas e o estado podem ser consultados através de <code>GetUpdatePackageStatus()</code> (<a class="spec-record-ref" data-req="SWS_DM_01802" href="../spec/record.html?id=SWS_DM_01802">[SWS_DM_01802]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>), <code>GetUpdatePackageDetails()</code> (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>) ou a lista completa através de <code>GetAllUpdates()</code> (<a class="spec-record-ref" data-req="SWS_DM_01797" href="../spec/record.html?id=SWS_DM_01797">[SWS_DM_01797]</a>, <a class="spec-record-ref" data-req="SWS_DM_01916" href="../spec/record.html?id=SWS_DM_01916">[SWS_DM_01916]</a>). Os pacotes já não necessários são removidos através de <code>DeleteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>).</li>
</ol>

<h4>Cenários de erro</h4>
<p>As condições de erro dividem-se em erros de configuração e de modelação, erros de estado do serviço, bem como erros de execução específicos do protocolo:</p>
<ul>
<li><strong>Erros de modelo e de instanciação:</strong> Se a resolução do <code>InstanceSpecifier</code> falhar ou se este referenciar um elemento inadequado, são reportadas violações específicas em tempo de execução (Violations): <code>InstanceSpecifierMappingIntegrityViolation</code>, <code>PortInterfaceMappingViolation</code>, <code>ProcessMappingViolation</code> bem como <code>InstanceSpecifierAlreadyInUseViolation</code>, caso o identificador já esteja a ser utilizado dentro do processo (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>).</li>
<li><strong>Erros de disponibilização:</strong> A chamada de <code>Offer()</code> retorna um <code>ara::core::Result&lt;void&gt;</code>. Em caso de erro, este contém <code>DiagOfferErrc::kAlreadyOffered</code>, se o serviço já estiver a ser disponibilizado, ou <code>DiagOfferErrc::kConfigurationMismatch</code>, se a configuração não coincidir com o extrato de diagnóstico (DEXT) (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>).</li>
<li><strong>Erros de execução e de protocolo:</strong> Os métodos de callback assíncronos retornam resultados como <code>ara::core::Future</code>. Em caso de erro, deve ser guardado no Future um código de erro aplicável em conformidade com a ASAM SOVD 1.1 ou a ISO 17978-3 (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>, <a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>, <a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>).</li>
<li><strong>Tratamento de cancelamento:</strong> A todos os métodos assíncronos é transmitido um <code>CancellationHandler</code>. A aplicação é responsável por consultar este último, a fim de terminar de forma limpa uma conversação de cliente abortada prematuramente (<a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
</ul>
