classe ara::diag::TransmitCertificate

[SWS_DM_01961] Upstream: RS_Diag_04251

class TransmitCertificate {...};

Class to implement the subfunction TransmitCertificate (29 04) of UDS service Authentication as interface to application. This class implements a so called generic interface, where the application has means to handle one ore more certificateEvaluationId transferred certificates.

Contexto

A classe ara::diag::TransmitCertificate disponibiliza a interface de programação para a subfunção UDS TransmitCertificate (0x29 04) do serviço Authentication (0x29) AUTOSAR_AP_SWS_Diagnostics §8.26.1 «Class: TransmitCertificate». Ela implementa uma interface genérica por meio da qual uma aplicação Adaptive pode receber e avaliar um ou mais certificados identificados por uma identificação de 16 bits (certificateEvaluationId).

Na arquitetura do sistema, ara::diag::TransmitCertificate atua como elo de ligação entre o AUTOSAR Adaptive Diagnostic Manager (DM) ou a Diagnostic Server Instance e a lógica de aplicação concreta. Um testador de diagnóstico externo envia a solicitação de autenticação UDS para o servidor, que encaminha a solicitação para a aplicação após a ativação [SWS_DM_01968], [SWS_DM_01251].

Diagrama de contexto: incorporação de TransmitCertificate entre testador de diagnóstico, Diagnostic Manager e lógica de aplicação. Fontes: [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01249].

Ciclo de vida

A instanciação ocorre por meio do construtor, mediante a especificação de um [SWS_DM_01962]:

  • specifier: Um ara::core::InstanceSpecifier que faz referência a um PortPrototype, o qual é tipificado por meio de um DiagnosticAuthenticationPortMapping [SWS_DM_01962].
  • concurrencyType: Define se a execução posterior de Process é tratada como segura para threads (kConcurrent) ou não segura para threads (kNotConcurrent) [SWS_DM_01962], [SWS_DM_01968].

Operações de cópia e de movimentação estão completamente impedidas: o construtor de cópia [SWS_DM_01964], o construtor de movimento [SWS_DM_01963], o operador de atribuição por cópia [SWS_DM_01966] e o operador de atribuição por movimento [SWS_DM_01965] estão declarados como excluídos (=delete). Uma instância de interface de autenticação existe, portanto, como um objeto vinculado exclusivamente.

Após a construção, o ciclo de vida divide-se em duas fases de operação:

  1. Disponibilização (Offered): Por meio da chamada de Offer(), o Diagnostic Manager é autorizado a encaminhar mensagens UDS recebidas para a subfunção ao método Process() [SWS_DM_01969].
  2. Revogação (Stopped): A chamada de StopOffer() cancela novamente o registro do encaminhamento [SWS_DM_01970].

O destrutor é virtual e declarado como padrão (noexcept = default) [SWS_DM_01967]. Enquanto o construtor é seguro para threads, Offer() e StopOffer() são especificados como não seguros para threads e não podem ser chamados de forma concorrente descoordenada [SWS_DM_01962], [SWS_DM_01969], [SWS_DM_01970].

Caminho de utilização

O fluxo operacional regular compreende o registro no Diagnostic Manager, o recebimento assíncrono dos dados do certificado e a conclusão do processamento:

  1. Instanciação e liberação: A aplicação instancia a classe derivada e ativa a aceitação por meio de Offer() [SWS_DM_01962], [SWS_DM_01969].
  2. Receção e processamento: Ao receber um pedido UDS, o Diagnostic Server encaminha os dados através de Process(certificateEvaluationId, certificateData, metaInfo, cancellationHandler) [SWS_DM_01968]. O método retorna um ara::core::Future<void>, suportando assim o processamento assíncrono. A semântica concreta e a avaliação do certificado são da inteira responsabilidade da aplicação [SWS_DM_01968].
  3. Tratamento de cancelamento: A aplicação pode verificar através de cancellationHandler.IsCanceled() se a conversação de diagnóstico foi cancelada, ou registar via cancellationHandler.SetNotifier() um callback de notificação para eventos de cancelamento [SWS_DM_01968].
  4. Resposta positiva: Se a execução terminar com sucesso sem código de erro, a Diagnostic Server Instance transmite uma resposta UDS positiva com o parâmetro de retorno authenticationReturnParameter = 0x13 (CertificateVerified) ao tester [SWS_DM_01251].
  5. Limpeza: Ao terminar, a receção é encerrada através de StopOffer() [SWS_DM_01970].

Diagrama de sequência: fluxo típico da transferência e processamento de certificados. Fontes: [SWS_DM_01969], [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01970].

Cenários de erro

Tanto na inicialização como durante a operação em curso, estão definidas condições de erro específicas:

  • Erros de manifesto e modelagem na criação: O construtor reporta violações se o InstanceSpecifier não puder ser resolvido (InstanceSpecifierMappingIntegrityViolation), se o PortPrototype referenciado não for tipificado por um DiagnosticTransmitCertificateInterface (PortInterfaceMappingViolation), se não existir mapeamento de processo (ProcessMappingViolation) ou se o InstanceSpecifier no processo já estiver atribuído (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01962].
  • Registo múltiplo: Uma nova chamada de Offer() quando a disponibilização já está ativa resulta no erro DiagOfferErrc::kAlreadyOffered com semântica de rollback [SWS_DM_01969].
  • Rejeição em Process: Se a verificação do certificado falhar na aplicação ou ocorrer um erro de processamento, o Process() retorna um erro correspondente através do ara::core::Future. Neste caso, deve ser utilizado um UDS-Negative-Response-Code (NRC) adequado em conformidade com a ISO 14229-1 via DiagUdsNrcErrc [SWS_DM_01968]. A Diagnostic Server Instance gera em seguida uma resposta UDS negativa (NRC) para o tester externo [SWS_DM_01249].

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 para o módulo Diagnostics.
