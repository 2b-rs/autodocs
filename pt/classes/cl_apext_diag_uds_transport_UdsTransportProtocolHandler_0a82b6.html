Serve como classe base abstrata para plug-ins de transporte UDS visando à transmissão e ao encaminhamento de mensagens de diagnóstico.

A classe abstrata serve a plug-ins de transporte UDS como interface base para a conexão padronizada ao gerenciamento de diagnóstico adaptativo (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»). Uma implementação derivada encaminha mensagens de diagnóstico recebidas para o gerenciador de protocolos e transmite mensagens de resposta geradas através de canais específicos da rede para o testador de diagnóstico. O ciclo de vida está sujeito a uma sequência estrita de criação, inicialização separada, inicialização assíncrona e parada ordenada ([SWS_DM_00329]). Após a instanciação, as chamadas de métodos operacionais não são seguras para threads e exigem um controle coordenado pelo núcleo de diagnóstico.

Contexto

A classe apext::diag::uds_transport::UdsTransportProtocolHandler é uma classe base abstrata dentro do módulo diag da AUTOSAR Adaptive Platform. Ela define a interface padronizada por meio da qual plug-ins de transporte UDS proprietários ou específicos de protocolo são conectados ao gerenciamento de diagnóstico (DM) adaptativo (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00315]). Cada protocolo de transporte concreto – por exemplo, para diagnóstico sobre mídias de rede automotivas – implementa essa interface como uma subclasse derivada. Supõe-se que o DM possua e gerencie com exclusividade a respectiva instância de manipulador durante todo o seu ciclo de vida operacional. A interação entre o núcleo de diagnóstico e o plug-in ocorre por meio da referência transportprotocolManager do tipo UdsTransportProtocolMgr&, que é passada no construtor e armazenada de forma protegida ([SWS_DM_09015], [SWS_DM_09025]). Cada manipulador é identificado por um UdsTransportProtocolHandlerID numérico, que pode ser consultado via GetHandlerID() ([SWS_DM_00325]).

Ciclo de vida

O ciclo de vida de um manipulador de protocolo de transporte UDS é controlado de forma estritamente sequencial pelo DM ([SWS_DM_00329]). Após a instanciação pelo construtor UdsTransportProtocolHandler ([SWS_DM_09015]), o método Initialize() separa a inicialização real do protocolo da criação do objeto ([SWS_DM_00319]). Com exceção de uma consulta opcional via GetPeriodicHandler(), o DM não deve chamar nenhum método no manipulador antes do retorno bem-sucedido de InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). Após a inicialização bem-sucedida, a chamada de Start() coloca o manipulador no estado de processamento ativo ([SWS_DM_00322]). Para minimizar o tempo de inicialização, Start() é concebido como uma operação assíncrona; supõe-se que o DM coordene internamente a inicialização paralela de múltiplos manipuladores. Se o DM transitar para o estado ApplicationState.kTerminating durante o encerramento, ele instrui o manipulador a finalizar via Stop() ([SWS_DM_00323], [SWS_DM_00333]). O DM aguarda a conclusão, a qual o manipulador confirma chamando UdsTransportProtocolMgr::HandlerStopped() ([SWS_DM_00340]). Após o retorno de Stop(), qualquer chamada de método do plug-in para o gerenciador, exceto HandlerStopped(), é proibida ([SWS_DM_01741]). A liberação dos recursos ocorre, por fim, por meio do destrutor virtual ([SWS_DM_09016]). Enquanto o construtor é seguro para threads, os métodos de interface operacionais são declarados como não seguros para threads.

Diagrama de estados: fases do ciclo de vida e transições de estado de um manipulador de transporte UDS. Fontes: [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00329], [SWS_DM_01745], [SWS_DM_01746]

Caminho de utilização

Na operação de diagnóstico regular, o manipulador processa mensagens de entrada e transmite respostas. Assim que na interface de rede estiverem disponíveis, no mínimo, endereço de origem, endereço de destino, tipo de endereço (físico ou funcional), comprimento total da mensagem e, no caso de dados úteis de múltiplos bytes, os dois primeiros bytes (payloadInfo), a implementação notifica a solicitação ao gerenciador por meio de UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00342], AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer»). Cada solicitação é atribuída a um canal exclusivo (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»). Para responder, o DM passa a resposta de diagnóstico para o mesmo manipulador e canal por meio de Transmit(message, channelId) ([SWS_DM_00327], [SWS_DM_00348]). Após a transmissão física, o manipulador retorna o objeto de mensagem recebido ao gerenciador via UdsTransportProtocolMgr::TransmitConfirmation() ([SWS_DM_00327], [SWS_DM_00351]). Um caminho de uso especializado diz respeito a resets de ECU (serviço UDS 0x11) com resposta positiva após a reinicialização: aqui, o DM solicita antes do reset, via NotifyReestablishment(channelId), que o manipulador salve as informações de conexão de forma não volátil; após a reinicialização e novo Start(), o manipulador notifica a restauração do mesmo canal via ChannelReestablished() ([SWS_DM_00326], [SWS_DM_01744]).

Diagrama de sequência: fluxo de indicação de mensagem UDS e transmissão de resposta. Fontes: [SWS_DM_00327], [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00351]

Cenários de erro

Se a inicialização da camada de transporte falhar e Initialize() retornar o status InitializationResult::kInitializeFailed, o DM interrompe imediatamente o processo de inicialização desse protocolo e não chama nenhum outro método nessa instância ([SWS_DM_01745], [SWS_DM_09017]). Se transmissões periódicas não forem suportadas no protocolo de transporte, a chamada de GetPeriodicHandler() retorna um ara::core::Result com o código de erro kConfigurationMismatch ([SWS_DM_01068]). Se uma restauração de canal solicitada para um reset de ECU não puder ser assegurada, NotifyReestablishment() falha e sinaliza isso por meio do valor de retorno false ([SWS_DM_00326]). Caso, por fim, o processo de envio de uma resposta de diagnóstico na camada de rede falhe, o manipulador deve informar isso na confirmação ao gerenciador, definindo o argumento result em TransmitConfirmation() como kTransmitFailed ([SWS_DM_00351]).

          O método puramente virtual Initialize serve para a inicialização explícita de uma instância de apext::diag::uds_transport::UdsTransportProtocolHandler e separa formalmente esse processo da construção do objeto [SWS_DM_00319]. Ele é chamado de forma síncrona e sem parâmetros pelo Diagnostic Manager (DM), não lança exceções (noexcept) e retorna um InitializationResult [SWS_DM_00319] [SWS_DM_09017].
          

          Ciclo de vida e concorrência
          

          A chamada está integrada ao gerenciamento do ciclo de vida da camada de transporte UDS AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer». O DM deve gerenciar as fases em uma sequência fixa: construção, chamada de Initialize, início via Start e encerramento via Stop [SWS_DM_00329]. O método é especificado como não seguro para threads (not thread-safe) [SWS_DM_00319]; por esse motivo, o DM provavelmente deve executá-lo no âmbito de uma fase de inicialização síncrona sem acessos paralelos.
          

          Tratamento de erros e interação
          

          O método sinaliza o resultado por meio do enumerador InitializationResult::kInitializeOk ou InitializationResult::kInitializeFailed [SWS_DM_09017]. O comportamento posterior do DM depende diretamente do valor de retorno:
          

            

          • Em caso de retorno bem-sucedido com kInitializeOk, o DM tem permissão para chamar métodos subsequentes do handler; antes desse valor de retorno bem-sucedido, com exceção de GetPeriodicHandler, nenhuma outra chamada de método é permitida [SWS_DM_01746].
            • 

          • Se o handler retornar kInitializeFailed, o DM aborta completamente o processo de inicialização desse protocolo de transporte e não chama mais nenhum outro método na instância afetada [SWS_DM_01745].

              função NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.

                  O método Start da interface apext::diag::uds_transport::UdsTransportProtocolHandler inicia o processamento de protocolo de um plugin de transporte UDS no Diagnostic Management (DM) de acordo com [SWS_DM_00322]. Ele não recebe parâmetros e não retorna nenhum valor. A execução é concebida de forma assíncrona para que o DM possa iniciar várias instâncias em paralelo e, assim, reduzir o tempo de inicialização de todo o sistema ([SWS_DM_00322]). Como a assinatura declara void, o processamento assíncrono deverá ser tratado de forma específica da pilha através de mecanismos internos de segundo plano.
