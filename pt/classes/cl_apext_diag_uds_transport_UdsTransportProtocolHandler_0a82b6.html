Contexto

A classe apext::diag::uds_transport::UdsTransportProtocolHandler é a classe base abstrata para plugins específicos e proprietários de protocolo de transporte UDS no Diagnostic Management (DM) do AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00315]). Ela desacopla o núcleo genérico de diagnóstico das peculiaridades de redes de transmissão e camadas de transporte concretas, tais como DoIP ou protocolos baseados em CAN.

Um manipulador de transporte interage essencialmente com três parceiros:

  • Diagnostic Management Core: O DM gerencia todo o ciclo de vida do manipulador e disponibiliza, por meio da referência de gerenciador apext::diag::uds_transport::UdsTransportProtocolMgr, a contraparte para indicações de status e de dados ([SWS_DM_09015], [SWS_DM_09025]).
  • Camada de rede e cliente de diagnóstico: O plugin processa a troca física ou lógica de dados com o testador de diagnóstico externo ao veículo ou interno ([SWS_DM_00326], [SWS_DM_00351]).
  • Manipulador periódico (opcional): Se o respectivo protocolo de transporte suportar transmissões periódicas, o manipulador disponibiliza via GetPeriodicHandler() uma referência para um UdsTransportProtocolPeriodicHandler ([SWS_DM_01068]).

Ciclo de vida

O ciclo de vida de uma implementação de protocolo de transporte é estritamente controlado pelo DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer», [SWS_DM_00329]). A criação ocorre por meio do construtor UdsTransportProtocolHandler(handlerId, transportProtocolMgr), no qual o DM atribui ao manipulador um identificador exclusivo do tipo UdsTransportProtocolHandlerID bem como a referência ao UdsTransportProtocolMgr associado ([SWS_DM_09015], [SWS_DM_09025]). O ID atribuído pode ser consultado a qualquer momento por meio de GetHandlerID() ([SWS_DM_00325]). O construtor é especificado como seguro para threads ([SWS_DM_09015]).

Para desacoplar inicializações complexas de protocolo do construtor, o DM chama em seguida Initialize() ([SWS_DM_00319], [SWS_DM_00329]). Com exceção de GetPeriodicHandler(), o DM não deve chamar outros métodos do manipulador antes de um retorno bem-sucedido de InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). Após a inicialização bem-sucedida, o DM inicia o protocolo por meio de Start() ([SWS_DM_00322]). Como Start() é executado de forma assíncrona, o DM pode iniciar múltiplos manipuladores em paralelo para minimizar o tempo de inicialização ([SWS_DM_00322]).

Se a aplicação DM mudar para o estado ApplicationState.kTerminating, ela chamará Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). O DM aguarda até que o manipulador confirme a parada via UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). Após o retorno de Stop(), o plugin manipulador não pode chamar outros métodos no gerenciador – com a única exceção da confirmação HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). A desmontagem subsequente ocorre por meio do destrutor virtual ([SWS_DM_09016]).

Diagrama de estados: fases do ciclo de vida e condições de transição de um manipulador de protocolo de transporte UDS. Fontes: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Caminho de utilização

Em operação contínua, o manipulador assume a troca bidirecional de mensagens UDS:

  1. Recepção de mensagens (indicação): Assim que uma nova mensagem UDS chega a um canal e o endereço de origem, endereço de destino, tipo de endereçamento (físico ou funcional), comprimento total da mensagem bem como os primeiros bytes de dados úteis (para mensagens maiores que um byte, pelo menos dois bytes) são conhecidos, o plugin chama UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 «Indication of UDS message reception», [SWS_DM_00342], [SWS_DM_00330]). Neste processo, o manipulador passa a identificação do canal no parâmetro globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 «Channel Notifications»).
  2. Envio de mensagens (transmissão): O DM envia de volta a respectiva resposta de diagnóstico UDS por meio do mesmo manipulador e do mesmo canal (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 «UDS message transmission on a UDS TransportLayer», [SWS_DM_00348]). Para isso, ele chama Transmit(message, channelId) ([SWS_DM_00327]). A mensagem é passada ao manipulador como UdsMessageConstPtr na forma de um std::unique_ptr.
  3. Confirmação de envio: Assim que a mensagem tiver sido despachada pela rede (ou se tiver ocorrido um erro), o manipulador deve devolver a propriedade de message ao DM via UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). O resultado é transmitido como kTransmitOk ou kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Outro caminho de utilização específico é a recuperação de canais após um reset da unidade de controle (serviço UDS 0x11 com resposta positiva após reset): neste caso, o DM chama NotifyReestablishment(channelId) antes da reinicialização ([SWS_DM_00326]). O plugin armazena os parâmetros de conexão (por exemplo, endereços IP e portas) de forma persistente. Após a reinicialização via Start(), o plugin detecta a reconexão do mesmo cliente de diagnóstico e informa o DM via UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Diagrama de sequência: recepção de mensagens UDS, transmissão de respostas e confirmação subsequente. Fontes: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Cenários de erro

A interface trata diversas situações de exceção e de erro:

  • Falha na inicialização: Se Initialize() retornar o valor InitializationResult::kInitializeFailed ([SWS_DM_09017]), o DM cancela completamente o processo de inicialização deste protocolo de transporte e não chama nenhum outro método nesta instância ([SWS_DM_01745]).
  • Transmissões periódicas não suportadas: Se o protocolo concreto não suportar transmissões periódicas, a chamada de GetPeriodicHandler() retorna um ara::core::Result com o código de erro kConfigurationMismatch ([SWS_DM_01068]).
  • Rejeição da recuperação de canal: Se um plugin não puder atender à pré-reserva persistente para um canal (por exemplo, em caso de ausência de armazenamento não volátil ou mapeamento instável), NotifyReestablishment(channelId) retorna o valor false ([SWS_DM_00326]).
  • Erro de transmissão na rede: Se a camada de rede não puder enviar uma mensagem solicitada via Transmit(), o manipulador deve passar o resultado kTransmitFailed em TransmitConfirmation ([SWS_DM_00351]). A não devolução do buffer causa vazamentos de recursos no DM.
  • Violação de sequência após a parada: Se um plugin chamar um método diferente de HandlerStopped() no UdsTransportProtocolMgr após o retorno de Stop(), há uma violação da sequência de protocolo ([SWS_DM_00323], [SWS_DM_01741]).

Este guia de classe baseia-se na especificação AUTOSAR Adaptive R25-11.

              função NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
