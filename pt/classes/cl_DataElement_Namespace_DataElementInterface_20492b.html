Permite que aplicações disponibilizem e respondam a consultas de leitura de diagnóstico para o Diagnostic Manager.
GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 70357181b1bf Procedência

Permite que aplicações disponibilizem e respondam a consultas de leitura de diagnóstico para o Diagnostic Manager.

A interface serve para aplicações Adaptive disponibilizarem dados de diagnóstico para acessos de leitura do Diagnostic Management. Após a instanciação por meio de um especificador de instância, a aplicação deve oferecer ativamente o serviço para que requisições de leitura recebidas possam ser aceitas [SWS_DM_00597]. Requisições recebidas são processadas por meio do método de leitura assíncrono, que disponibiliza os dados de saída solicitados ou códigos de retorno negativos em um valor futuro [SWS_DM_00596]. Como as operações de cópia e movimento estão excluídas, cada instância permanece firmemente vinculada ao seu contexto.

Contexto

A classe C++ gerada <DataElementInterface> atua dentro do cluster funcional diag (AUTOSAR Adaptive Platform) como interface de servidor padronizada para a disponibilização de dados legíveis de diagnóstico AUTOSAR_AP_SWS_Diagnostics p. 68. Concretamente, ela mapeia um DiagnosticDataElementInterface no papel read, através do qual uma aplicação Adaptive transmite valores de dados para requisições de diagnóstico (como, por exemplo, UDS ReadDataByIdentifier) ao Diagnostic Manager (DM) [SWS_DM_00596].

Parceiros de interação essenciais são o Diagnostic Management do daemon da plataforma, que coordena requisições de diagnóstico recebidas, bem como a aplicação Adaptive implementadora, que herda desta interface e formula a lógica de disponibilização. A instanciação e a atribuição à arquitetura de software ocorrem através de um protótipo de porta modelado, que é conectado por meio de um ara::core::InstanceSpecifier [SWS_DM_00587]. Os dados de saída são encapsulados em uma estrutura específica de tipo, cujos argumentos são representados por elementos de saída correspondentes [SWS_DM_80023], [SWS_DM_00581].

Ciclo de vida

A criação de uma instância ocorre através do construtor mediante especificação do ara::core::InstanceSpecifier, bem como do modo de concorrência ara::diag::ConcurrencyType [SWS_DM_00587]. Para preservar uma atribuição unívoca dentro do processo, tanto o construtor de cópia quanto o construtor de movimento estão excluídos [SWS_DM_01661], [SWS_DM_01662]. Do mesmo modo, os operadores de atribuição por cópia e por movimento estão explicitamente excluídos [SWS_DM_01659], [SWS_DM_01660]. Uma instância permanece, assim, fixa em seu endereço criado.

No que diz respeito à operação, o objeto passa por fases definidas:

  • Não oferecido (Not Offered): após a construção, o objeto encontra-se inicialmente em um estado inativo, no qual o DM não encaminha requisições de leitura.
  • Oferecido (Offered): através da chamada de Offer(), o serviço é ativado no DM, de modo que requisições de leitura recebidas são encaminhadas [SWS_DM_00597].
  • Cancelado: a chamada de StopOffer() desativa o encaminhamento de requisições de diagnóstico futuras pelo DM [SWS_DM_00617].
  • Destruição: o destrutor virtual ~<DataElementInterface>() encerra o ciclo de vida da instância de interface [SWS_DM_00588].

Enquanto o construtor é especificado como seguro para threads [SWS_DM_00587], Offer(), StopOffer(), Read() e o destrutor não são seguros para threads [SWS_DM_00597], [SWS_DM_00617], [SWS_DM_00596], [SWS_DM_00588]. O parâmetro concurrencyType no construtor define se a implementação do manipulador é executada de forma thread-safe (kConcurrent) ou não thread-safe (kNotConcurrent) [SWS_DM_00587].

Diagrama de estados: fases de estado de uma instância de interface entre inicialização, status de publicação e destruição. Fontes: [SWS_DM_00587], [SWS_DM_00597], [SWS_DM_00617], [SWS_DM_00588].

Caminho de utilização

O fluxo regular para consulta de dados segue uma sequência fixa de etapas:

  1. Instanciação: a aplicação instancia a classe de handler derivada com o instanceSpec e concurrencyType desejados [SWS_DM_00587].
  2. Habilitação do serviço: a aplicação chama Offer(), capacitando o DM a encaminhar solicitações de leitura [SWS_DM_00597].
  3. Processamento de solicitações de leitura: se uma solicitação de leitura chegar ao DM, este chama o método puramente virtual Read(metaInfo, cancellationHandler) no handler [SWS_DM_00596]. A aplicação avalia metaInfo e pode verificar via cancellationHandler.IsCanceled() se a conversação foi cancelada, ou registrar um callback via cancellationHandler.SetNotifier [SWS_DM_00596].
  4. Retorno: Interpretação: a determinação propriamente dita dos dados de saída deve ocorrer tipicamente de forma assíncrona; o resultado é disponibilizado em um ara::core::Future com o respectivo objeto ReadOutput [SWS_DM_00596], [SWS_DM_00581].
  5. Encerramento do serviço: antes do desligamento, a aplicação chama StopOffer() para impedir o encaminhamento [SWS_DM_00617], seguido pela destruição do objeto [SWS_DM_00588].

Diagrama de sequência: sequência de chamadas desde o registro do serviço, passando pela leitura assíncrona, até o cancelamento do registro. Fontes: [SWS_DM_00597], [SWS_DM_00596], [SWS_DM_00617].

Cenários de erro

Em caso de falha, as diferentes fases de vida devem ser consideradas de forma diferenciada:

Já durante a construção podem ocorrer violações de integridade, que são sinalizadas por meio de violações específicas [SWS_DM_00587]:

  • InstanceSpecifierMappingIntegrityViolation: o especificador de instância não pode ser resolvido no modelo do executável ou não faz referência a um PortPrototype.
  • PortInterfaceMappingViolation: um PortPrototype tipificado pelo DiagnosticDataElementInterface não é referenciado por um DiagnosticDataPortMapping.
  • ProcessMappingViolation: embora exista uma InstanceRef correspondente, nenhum processo modelado correspondente ao processo em tempo de execução foi encontrado.
  • InstanceSpecifierAlreadyInUseViolation: o construtor foi chamado com um InstanceSpecifier que já está em uso no processo atual.

Se Offer() for chamado para um serviço já oferecido, o método retorna um ara::core::Result com o código de erro DiagOfferErrc::kAlreadyOffered (semântica de rollback) [SWS_DM_00597].

Se uma solicitação de leitura em Read() não puder ser respondida com sucesso, o ara::core::Future retornado deve conter um Negative Response Code (NRC) da ISO 14229-1 correspondente via DiagUdsNrcErrc ou um ApApplicationError [SWS_DM_00596].

              O método síncrono Offer de um DataElementInterface ativa o encaminhamento de solicitações de diagnóstico de entrada pelo daemon do Diagnostic Management (DM) para o respectivo manipulador ([SWS_DM_00597]). Ele não recebe parâmetros, garante segurança quanto a exceções (exception safe / noexcept) e retorna um ara::core::Result<void> ([SWS_DM_00597]).
              

              Para o tratamento de erros, simultaneidade e ordem, aplicam-se as seguintes especificações:
              

                

              • Tratamento de erros: Se o serviço já tiver sido oferecido anteriormente, a chamada falha e retorna o código de erro DiagOfferErrc::kAlreadyOffered com semântica de rollback ([SWS_DM_00597]).
                • 

              • Simultaneidade: A função é especificada como não thread-safe (not thread-safe) ([SWS_DM_00597]). Chamadas simultâneas na mesma instância devem ser sincronizadas no lado da aplicação.
                • 

              • Condições de ordem: Enquanto Offer não for chamado pela Adaptive Application, o DM não encaminha solicitações para o manipulador ou utiliza valores de fallback internos ([SWS_DM_01525], [SWS_DM_01527]). A chamada provavelmente deve ocorrer tipicamente na fase de inicialização da aplicação (interpretação).
                • 

              

              O conceito de disponibilização via Offer é utilizado de forma consistente também em outros manipuladores do DM, como rotinas ([SWS_DM_00594]) e identificadores de dados ([SWS_DM_00599]). A nomenclatura é de fato inspirada em ara::com, mas representa uma implementação autônoma do DM (SWS Diagnostics §7.3.4.1.2 «Monitors»).

  Procedência
  

                  

                  

                  O método Read serve para disponibilizar um elemento de dados dentro de uma instância DiagnosticDataElementInterface no papel read [SWS_DM_00596]. A chamada ocorre de forma assíncrona pelo Diagnostic Manager para o processamento de solicitações de leitura de diagnóstico.
                  

                  Uso e assinatura
                  

                  A interface retorna um ara::core::Future com um objeto ReadOutput tipado de acordo com [SWS_DM_00581] [SWS_DM_00596]. Por meio dos parâmetros passados, a implementação processa a solicitação:
                  

                    

                  • metaInfo: Passa metainformações sobre a solicitação de diagnóstico de entrada [SWS_DM_00596].
                    • 

                  • cancellationHandler: Permite o monitoramento de um cancelamento prematuro da conversação de diagnóstico via cancellationHandler.IsCanceled(), bem como o registro de uma função de notificação via cancellationHandler.SetNotifier() [SWS_DM_00596].
                    • 

                  

                  Tratamento de erros e simultaneidade
                  

                  Se o elemento de dados não puder ser lido com sucesso, o ara::core::Future não retorna um valor, mas sim um erro. Como código de erro, deve-se definir um Negative Response Code (NRC) de UDS apropriado conforme a ISO 14229-1 via DiagUdsNrcErrc ou um ApApplicationError [SWS_DM_00596].
