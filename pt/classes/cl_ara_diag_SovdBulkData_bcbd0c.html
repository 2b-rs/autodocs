Permite que aplicações disponibilizem e transmitam dados em massa de SOVD por meio do Diagnostic Management.

A interface [SWS_DM_01841] conecta aplicações adaptativas ao Diagnostic Management para disponibilizar operações de dados em massa baseadas em SOVD. Por meio de métodos puramente virtuais, metadados são consultados, uploads e downloads de dados em massa são processados e conjuntos de dados são excluídos de forma direcionada ou por categoria. Uma instância é vinculada a uma porta modelada, habilitada para o encaminhamento de requisições de diagnóstico pela chamada de Offer() e desregistrada ao término via StopOffer() [SWS_DM_01857]. Dependendo da concorrência selecionada, as rotinas de callback disponibilizadas devem ser projetadas como thread-safe.

Contexto

A classe de interface ara::diag::SovdBulkData [SWS_DM_01841] fornece uma interface de serviço genérica para acesso a dados em massa (Bulk Data) em conformidade com o Service-Oriented Vehicle Diagnostics (SOVD) SWS Diagnostics §8.53 «Class: SovdBulkData». Ela serve como elemento de ligação entre fontes de dados específicas da aplicação e o servidor de diagnóstico central da Adaptive Platform.

No processamento global participam pelo menos três componentes:

  • Cliente SOVD: Uma ferramenta de diagnóstico externa que consulta, faz upload ou exclui dados em massa. A comunicação deve ser processada tipicamente por meio de mecanismos HTTP/REST. Pergunta Q-3e713885753faa82 (aberta)
  • Diagnostic Management (DM): A Diagnostic Server Instance recebe chamadas de serviço SOVD externas e as converte em chamadas de método locais SWS Diagnostics §7.x «SOVD Bulk Data Realization».
  • Aplicação adaptativa: Uma aplicação definida pelo usuário deriva de ara::diag::SovdBulkData, instancia a classe e disponibiliza os fluxos de dados e metadados reais.

Diagrama de contexto: interação entre cliente SOVD, Diagnostic Management e a interface de aplicação ara::diag::SovdBulkData. Fontes: [SWS_DM_01790], [SWS_DM_01841], [SWS_DM_01857].

Ciclo de vida

A instanciação de ara::diag::SovdBulkData ocorre por meio do construtor mediante o fornecimento de um ara::core::InstanceSpecifier e a indicação do comportamento de concorrência via ConcurrencyType [SWS_DM_01847]. O InstanceSpecifier vincula o objeto a um PortPrototype definido no modelo de design de um DiagnosticSovdBulkDataInterface.

Em termos de propriedade, a classe é concebida como instância única: o construtor de cópia [SWS_DM_01848] e o operador de atribuição por cópia [SWS_DM_01850] são explicitamente deletados (=delete). A transferência de instâncias é prevista exclusivamente por meio de operações de movimento; o construtor de movimento [SWS_DM_01849] e a atribuição por movimento [SWS_DM_01851] são implementados como protegidos.

O ciclo de vida funcional divide-se nas seguintes fases:

  • Inativo: Após a construção, o objeto está presente localmente, mas ainda não recebe requisições de diagnóstico do Diagnostic Management.
  • Ativo (Offered): Por meio da chamada do método Offer() [SWS_DM_01857], o objeto é registrado no DM. Somente a partir deste momento o DM encaminha requisições SOVD recebidas para os métodos tratadores virtuais.
  • Parado: A chamada de StopOffer() [SWS_DM_01858] desativa novamente o encaminhamento de requisições.
  • Destruição: O destrutor virtual ~SovdBulkData() [SWS_DM_01852] encerra a vida útil do objeto. Antes da destruição, StopOffer() deve presumivelmente ser chamado para encerrar acessos pendentes de forma limpa. Pergunta Q-b89ddbd0df8a5544 (aberta)

Em relação à concorrência, o ConcurrencyType passado no construtor define se os métodos virtuais de callback devem ser executados como thread-safe (kConcurrent) ou não thread-safe (kNotConcurrent) [SWS_DM_01847]. Os métodos de controle Offer() [SWS_DM_01857], StopOffer() [SWS_DM_01858] e o destrutor [SWS_DM_01852] não são, eles próprios, thread-safe.

Caminho de utilização

Um fluxo típico para disponibilização e execução de operações de dados em massa de SOVD inclui as seguintes etapas:

  1. Derivação de classe: A aplicação implementa uma classe concreta que herda de ara::diag::SovdBulkData e sobrescreve os métodos virtuais puros.
  2. Disponibilização: Após a instanciação, a aplicação chama Offer() [SWS_DM_01857] para oferecer o serviço.
  3. Processamento de requisições:
    • Se um cliente solicitar metadados, o servidor de diagnóstico chama GetBulkDataMetaData [SWS_DM_01791], o que retorna um vetor de BulkDataMetaDataDescriptor via ara::core::Future [SWS_DM_01853].
    • Em uma chamada de download, o DM chama RequestBulkDataDownload [SWS_DM_01792]. A aplicação responde com uma sessão de leitura (DataTransferReadSession) com metadados ou um redirecionamento HTTP (HttpRedirect) [SWS_DM_01873].
    • Para operações de upload, o DM chama RequestBulkDataUpload [SWS_DM_01793], momento em que uma sessão de escrita (DataTransferWriteSession) é disponibilizada [SWS_DM_01854].
    • Requisições de exclusão são encaminhadas pelo DM para DeleteSpecificBulkData (para recursos individuais) [SWS_DM_01856] ou para DeleteAllBulkData (por categoria) [SWS_DM_01855].
  4. Desregistro do serviço: Assim que o processamento deve ser interrompido, a aplicação chama StopOffer() [SWS_DM_01858].

Diagrama de sequência: sequência de interação entre cliente SOVD, Diagnostic Management e tratador no download de Bulk Data. Fontes: [SWS_DM_01792], [SWS_DM_01857], [SWS_DM_01858], [SWS_DM_01873].

Cenários de erro

Ao usar ara::diag::SovdBulkData, diferentes tipos de erros devem ser distinguidos:

  • Violações de configuração na instanciação: Se a resolução do modelo falhar ou os mapeamentos não forem compatíveis, o construtor reporta violações específicas [SWS_DM_01847]. Isso inclui InstanceSpecifierMappingIntegrityViolation (modelo inválido ou ausência de PortPrototype), PortInterfaceMappingViolation (tipagem incorreta do mapeamento de porta), ProcessMappingViolation (nenhum processo correspondente modelado) e InstanceSpecifierAlreadyInUseViolation (especificador já ocupado dentro do processo).
  • Erros de registro no Offer: A chamada de Offer() retorna um ara::core::Result<void> [SWS_DM_01857]. Possíveis erros são DiagOfferErrc::kAlreadyOffered, se o serviço já estiver sendo oferecido, bem como DiagOfferErrc::kConfigurationMismatch, se a configuração não corresponder às descrições DEXT.
  • Códigos de erro em operações assíncronas: Se uma operação de dados em massa solicitada não puder ser executada com sucesso, o erro é transportado no ara::core::Future retornado. Para isso, a aplicação deve usar códigos de erro SOVD padronizados de acordo com a ISO 17978-3 ou ASAM SOVD 1.1 (usando DiagSovdErrc) [SWS_DM_01854], [SWS_DM_01855], [SWS_DM_01856], [SWS_DM_01873]. Para GetBulkDataMetaData, por outro lado, nenhum erro padronizado é especificado [SWS_DM_01853].
  • Tratamento de cancelamento: Os métodos de callback recebem um objeto CancellationHandler que sinaliza se a conversação de diagnóstico subjacente foi cancelada prematuramente [SWS_DM_01853], [SWS_DM_01873].

Este guia baseia-se exclusivamente na especificação AUTOSAR Adaptive R25-11 para o módulo diag.

usar

A função virtual DeleteAllBulkData da classe ara::diag::SovdBulkData é chamada para executar o método SOVD “Delete All Bulk Data Defined by Category” [SWS_DM_01855]. A definição da interface encontra-se no cabeçalho ara/diag/sovd_bulk_data.h AUTOSAR_AP_SWS_Diagnostics §8.53.1.1.3.1 «DeleteAllBulkData».

O método recebe os seguintes parâmetros de passagem:

  • bulkDataCategory (ara::core::String): identifica a categoria de dados em massa da qual todas as instâncias devem ser excluídas [SWS_DM_01855].
  • metaInfo (MetaInfo const &): transfere metainformações contextuais da requisição atual [SWS_DM_01855].
  • cancellationHandler (CancellationHandler): informa sobre o cancelamento prematuro da conversação em andamento [SWS_DM_01855].

O resultado é disponibilizado de forma assíncrona por meio de um ara::core::Future<DeleteByCategoryResult> [SWS_DM_01855]. Interpretação: como a purga de categorias inteiras de dados em massa pode ser demorada, a aplicação presumivelmente deve verificar ciclicamente o cancellationHandler passado, a fim de reagir prontamente a eventuais cancelamentos. Pergunta Q-59d2847dbe42f240 (aberta)

Tratamento de erros e segurança contra exceções

O método é declarado como noexcept e seguro quanto a exceções (exception safe) [SWS_DM_01855]. Se a exclusão falhar, um código de erro SOVD apropriado conforme ISO 17978-3 ou ASAM SOVD 1.1 deve ser transmitido no ara::core::Future [SWS_DM_01855].

simultaneidade

A segurança de threads é condicional (conditional): se a implementação deve ser projetada como segura para threads ou não segura para threads, é determinado por meio do ConcurrencyType passado ao construtor [SWS_DM_01855].
