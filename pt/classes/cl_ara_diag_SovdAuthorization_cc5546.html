Contexto

A classe ara::diag::SovdAuthorization fornece a interface padronizada através da qual uma aplicação adaptativa implementa serviços de autorização e autenticação para o protocolo Service-Oriented Vehicle Diagnostics (SOVD) ([SWS_DM_01490], AUTOSAR AP SWS Diagnostics §8.52.1 «Class: SovdAuthorization»). Dentro da arquitetura AUTOSAR, atua como elemento de ligação entre o servidor de diagnóstico interno do veículo (Diagnostic Management, DM) e uma lógica de autorização posterior, por exemplo um servidor de autorização ou de recursos baseado em OAuth 2.0 ([SWS_DM_01483], [SWS_DM_01484], [SWS_DM_01485]).

Nos processos participam essencialmente quatro partes: o cliente SOVD externo, o Diagnostic Server (DM) como intermediário, a classe de aplicação ara::diag::SovdAuthorization, bem como um servidor de autorização externo ou interno ao veículo. O DM recebe pedidos SOVD baseados em HTTP e delega a disponibilização de URLs de autorização e de token, bem como a validação de tokens de acesso transmitidos, na instância de aplicação mapeada ([SWS_DM_01470], [SWS_DM_01471], [SWS_DM_01472]).

Diagrama de contexto: Integração de ara::diag::SovdAuthorization entre o DM, o cliente SOVD e o servidor de autorização. Fontes: [SWS_DM_01470], [SWS_DM_01471], [SWS_DM_01472], [SWS_DM_01490].

Ciclo de vida

A criação é efetuada pelo construtor SovdAuthorization(ara::core::InstanceSpecifier, ConcurrencyType) ([SWS_DM_01489]). O instanceSpecifier transmitido faz referência a um PortPrototype modelado da interface DiagnosticSovdAuthorizationInterface, que deve ser atribuído a um SoftwareCluster da categoria PLATFORM através de mapeamento ([SWS_DM_01471], [SWS_DM_01489]). Através do parâmetro concurrencyType, é configurado se os métodos virtuais de callback da instância são chamados de forma concorrente (kConcurrent) ou sequencial (kNotConcurrent) ([SWS_DM_01489]).

Após a instanciação, o DM só encaminha pedidos quando a aplicação liberta explicitamente o porto através de Offer() ([SWS_DM_01487]). O encaminhamento de pedidos recebidos pode ser suspenso a qualquer momento através de StopOffer() ([SWS_DM_01486]). A libertação dos recursos ocorre no destrutor virtual ~SovdAuthorization() ([SWS_DM_01488]). O construtor, o destrutor, bem como Offer() e StopOffer() estão especificados como não seguros para threads ([SWS_DM_01486], [SWS_DM_01487], [SWS_DM_01488], [SWS_DM_01489]). Interpretação: A instância de SovdAuthorization deverá tipicamente ser criada durante a fase de inicialização do respetivo processo e mantida durante todo o tempo de execução do processo.

Caminho de utilização

Em operação normal, a classe de aplicação derivada de SovdAuthorization atende a dois casos de utilização principais:

  1. Redirecionamento de cliente (Redirection): Se o DM receber uma solicitação de cliente para a verificação de credenciais no veículo ou para a requisição de um token, ele chama GetAuthorizationUrl() ([SWS_DM_01472], [SWS_DM_01485]) ou GetTokenUrl() ([SWS_DM_01471], [SWS_DM_01484]), respectivamente. A aplicação avalia os queryParameters e metaInfo transmitidos e retorna a URL de destino de forma assíncrona como ara::core::Future<ara::core::String> (AUTOSAR AP SWS Diagnostics §7.3.3.2.1 «SOVD – Authorization»). O DM responde então ao cliente SOVD com HTTP Status 307 (Temporary Redirect) e define o cabeçalho Location para a URL retornada ([SWS_DM_01471], [SWS_DM_01472]).
  2. Validação de token: se o cliente SOVD enviar um cabeçalho HTTP Authorization cujo token ainda não esteja ou não esteja mais registrado como válido, o DM chama o método ValidateAuthorization() ([SWS_DM_01470], [SWS_DM_01483]). A aplicação verifica o token e define os papéis autorizados correspondentes no objeto ara::diag::ClientAuthentication transmitido ([SWS_DM_01483]). Assim que o Future<ValidateAuthorizationOutput> retornado for disponibilizado, a aplicação não deve mais acessar o objeto ClientAuthentication ([SWS_DM_01483]). O DM assume os papéis definidos ([SWS_DM_01469]) e utiliza o carimbo de data/hora de validade validUntil ou a identidade (identity) para o reconhecimento do cliente e para mecanismos de bloqueio subsequentes ([SWS_DM_01781], [SWS_DM_01782], AUTOSAR AP SWS Diagnostics §7.3.3.2.1 «SOVD – Authorization»).

Diagrama de sequência: fluxo da validação de token SOVD via ara::diag::SovdAuthorization. Fontes: [SWS_DM_01470], [SWS_DM_01483], [SWS_DM_01469], [SWS_DM_01781].

Cenários de erro

Condições de erro ocorrem principalmente durante a inicialização, na disponibilização do serviço e no âmbito da validação:

  • Erros de construção: a instanciação reporta violações de manifesto e de configuração ([SWS_DM_01489]), entre as quais InstanceSpecifierMappingIntegrityViolation (InstanceSpecifier não resolvível ou não é um PortPrototype), PortInterfaceMappingViolation (PortPrototype incompatível com a interface DiagnosticSovdAuthorizationInterface), ProcessMappingViolation (nenhum processo compatível modelado) e InstanceSpecifierAlreadyInUseViolation (InstanceSpecifier já atribuído no processo).
  • Erros em Offer(): a chamada retorna um ara::core::Result<void> ([SWS_DM_01487]). Os códigos de erro possíveis são DiagOfferErrc::kAlreadyOffered (a interface já foi oferecida) e DiagOfferErrc::kConfigurationMismatch (a configuração de monitoramento diverge dos dados do modelo DEXT).
  • Erros em ValidateAuthorization(): se a verificação do token falhar, o Future fornece códigos de erro de DiagSovdErrc ([SWS_DM_01483]): DiagSovdErrc::kInvalidAccessToken sinaliza um token de acesso inválido; DiagSovdErrc::kTemporarilyNotAvailable indica que a requisição não pode ser atendida no momento (por exemplo, porque o servidor de autenticação externo está inacessível para uma validação online).

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 (módulo diag) e resume os requisitos para ara::diag::SovdAuthorization.
