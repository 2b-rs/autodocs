Permite que aplicações validem tokens SOVD e forneçam URLs de autorização e de token.

A classe ara::diag::SovdAuthorization serve a aplicações para a implementação das interfaces de autorização SOVD perante o Diagnostic Server ([SWS_DM_01490]). Ela disponibiliza métodos para determinação de URLs de redirecionamento para endpoints de autorização e de token, bem como para a verificação de tokens de acesso ([SWS_DM_01483]). A recepção de mensagens deve ser ativada explicitamente após a instanciação com Offer(), e o objeto de autenticação passado não deve mais ser utilizado após o fornecimento do resultado de validação.

Contexto

A classe ara::diag::SovdAuthorization fornece a interface de aplicação adaptativa para disponibilizar mecanismos de autorização e de autenticação para o Service-Oriented Vehicle Diagnostics (SOVD) ([SWS_DM_01490]). Dentro da arquitetura de diagnóstico, ela faz a mediação entre o Diagnostic Server do Diagnostic Management (DM) e a lógica de autorização individual da aplicação veicular (SWS Diagnostics §7.3.3.2 «SOVD Request Validation and Verification»). Quando um cliente SOVD externo consulta endpoints para verificação de cliente ou para recuperação de tokens, o Diagnostic Server encaminha essas requisições à aplicação para determinar as URLs de destino ([SWS_DM_01471], [SWS_DM_01472]). Em requisições de diagnóstico de entrada com cabeçalho de autorização HTTP, a classe verifica a validade do token e define papéis de acesso transferidos ([SWS_DM_01470]). A validação real perante um servidor de autorização (como OAuth 2.0) provavelmente ocorre como uma interpretação específica da aplicação por meio de protocolos de rede externos, uma vez que a AUTOSAR padroniza aqui o ponto local de entrega da aplicação.

Diagrama de contexto: interação entre cliente SOVD, Diagnostic Server (DM), SovdAuthorization e serviço de autorização externo. Fontes: [SWS_DM_01470], [SWS_DM_01471], [SWS_DM_01472], SWS Diagnostics §7.3.3.2.1 «SOVD – Authorization»

Ciclo de vida

A instanciação de ara::diag::SovdAuthorization ocorre explicitamente através do construtor sob indicação de um ara::core::InstanceSpecifier, bem como do modo de concorrência ConcurrencyType ([SWS_DM_01489]). O InstanceSpecifier deve apontar no manifesto para um PortPrototype válido de um DiagnosticSovdAuthorizationInterface. Através do ConcurrencyType (kConcurrent ou kNotConcurrent), define-se se os métodos de callback implementados da aplicação precisam ser projetados como seguros para threads ([SWS_DM_01483], [SWS_DM_01484], [SWS_DM_01485]).

Após a construção, o Diagnostic Server só encaminha requisições quando a aplicação tiver chamado o método Offer() com sucesso ([SWS_DM_01487]). Interpretação: requisições que chegam antes do Offer() são provavelmente descartadas pelo servidor ou rejeitadas com erro. Para encerrar o encaminhamento de requisições, a aplicação chama StopOffer() ([SWS_DM_01486]). Por fim, o objeto é liberado através do destrutor virtual ([SWS_DM_01488]). As chamadas administrativas SovdAuthorization, Offer, StopOffer e o destrutor não são seguros para threads.

Caminho de utilização

Em operação corrente ocorrem dois caminhos essenciais de interação: a disponibilização de URLs de redirecionamento e a validação de tokens de sessão ativos. Se um cliente SOVD enviar uma consulta para verificação de cliente ou para requisição de um token, o DM chama GetAuthorizationUrl() ([SWS_DM_01485]) ou GetTokenUrl() ([SWS_DM_01484]). A aplicação avalia os queryParameters fornecidos, bem como a metaInfo, e retorna a URL de destino de forma assíncrona como ara::core::Future<ara::core::String>, após o que o DM responde com um HTTP 307 (Temporary Redirect) ([SWS_DM_01471], [SWS_DM_01472]).

Se uma requisição SOVD subsequente contiver um cabeçalho HTTP Authorization novo ou modificado, o Diagnostic Server chama ValidateAuthorization() ([SWS_DM_01470], [SWS_DM_01483]). A aplicação valida o token transmitido, atribui ao objeto referenciado ara::diag::ClientAuthentication os respectivos papéis de autorização ([SWS_DM_01469]) e retorna um ValidateAuthorizationOutput através do Future. Pré-requisito importante: assim que o Future estiver disponível, a aplicação não deve mais usar o objeto ClientAuthentication referenciado ([SWS_DM_01483]). O DM utiliza os valores de retorno (tempo de validade validUntil e identity) para associar requisições subsequentes do mesmo cliente sem nova verificação ([SWS_DM_01781], [SWS_DM_01782]), o que é necessário em particular para bloqueios de recursos SOVD ([SWS_DM_01783]).

Diagrama de sequência: fluxo da validação de token via ValidateAuthorization e atribuição de papéis. Fontes: [SWS_DM_01469], [SWS_DM_01470], [SWS_DM_01483], SWS Diagnostics §7.3.3.2.1 «SOVD – Authorization»

Cenários de erro

Os erros são mapeados via ara::core::Result ou dentro do ara::core::Future retornado:

  • Erros de inicialização e modelagem: se a instanciação falhar, violações são reportadas, tais como InstanceSpecifierMappingIntegrityViolation (elemento de modelo inválido), PortInterfaceMappingViolation (tipo de interface incorreto), ProcessMappingViolation (referência de processo ausente) ou InstanceSpecifierAlreadyInUseViolation ([SWS_DM_01489]).
  • Erros de liberação no Offer: em caso de falha, Offer() retorna DiagOfferErrc::kAlreadyOffered caso o serviço já esteja ativo, ou DiagOfferErrc::kConfigurationMismatch caso a configuração não coincida com os dados DEXT ([SWS_DM_01487]).
  • Erros na validação de token: caso um token não possa ser verificado, ValidateAuthorization() retorna via future DiagSovdErrc::kInvalidAccessToken (token inválido) ou DiagSovdErrc::kTemporarilyNotAvailable (por exemplo, quando o servidor de autenticação para verificação online não estiver acessível) ([SWS_DM_01483]).
  • Determinação de URL: para GetAuthorizationUrl() e GetTokenUrl(), não estão definidos códigos de erro padronizados ([SWS_DM_01484], [SWS_DM_01485]).

Este guia baseia-se exclusivamente nas especificações da Release R25-11 da AUTOSAR.

          A função membro síncrona Offer da classe ara::diag::SovdAuthorization ativa o encaminhamento de mensagens de pedido pelo Diagnostic Management (DM) para a instância de manipulador associada [SWS_DM_01487]. Não aceita parâmetros e devolve um ara::core::Result<void>, que confirma a chamada bem-sucedida ou reporta um erro ocorrido [SWS_DM_01487].
          

          No que diz respeito ao tratamento de erros, [SWS_DM_01487] especifica dois códigos de erro concretos de DiagOfferErrc com semântica de rollback:
          

            

          • DiagOfferErrc::kAlreadyOffered: ocorre quando o serviço já está a ser oferecido para esta instância [SWS_DM_01487].
            • 

          • DiagOfferErrc::kConfigurationMismatch: reporta que a configuração não coincide com os dados de descrição DEXT [SWS_DM_01487].
            • 

          

          Relativamente às propriedades de execução, a chamada está declarada como segura em termos de exceções (exception safe), mas é considerada não segura entre threads (not thread-safe) [SWS_DM_01487]. A função não pode, por isso, ser chamada concorrentemente para a mesma instância.
          

          Na interação com o DM, a função corresponde ao padrão geral de disponibilização das interfaces de diagnóstico do AUTOSAR Adaptive, tal como é utilizado também para rotinas genéricas ou serviços DoIP (por exemplo [SWS_DM_00557], [SWS_DM_00725] ou [SWS_DM_00809]). Enquanto um manipulador não tiver sido registado através de Offer, o DM não encaminha pedidos para a aplicação ou serve-os com valores de substituição predefinidos [SWS_DM_01487], [SWS_DM_01525], [SWS_DM_01527].

                  usar
                  

                  O método StopOffer da classe ara::diag::SovdAuthorization (cabeçalho ara/diag/sovd_authorization.h) serve para impedir o encaminhamento de pedidos de diagnóstico recebidos do Diagnostic Management (DM) para o serviço de autorização [SWS_DM_01486]. A função possui a assinatura void StopOffer() noexcept. Não aceita parâmetros e não devolve qualquer valor de retorno ao chamador [SWS_DM_01486].
                  


                  Tratamento de erros e simultaneidade
                  

                  A função está especificada como segura em termos de exceções (exception safe) e não lança exceções [SWS_DM_01486]. Não estão previstos códigos de erro específicos nem mensagens de erro para o DET ou DEM para esta chamada. No que diz respeito à concorrência, o método está classificado como não seguro entre threads (not thread-safe) [SWS_DM_01486].
