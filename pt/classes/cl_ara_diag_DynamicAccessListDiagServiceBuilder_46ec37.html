Contexto

A classe ara::diag::DynamicAccessListDiagServiceBuilder ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15 «Class: DynamicAccessListDiagServiceBuilder») serve para que aplicações definam e serializem gradualmente uma lista de acesso dinâmico (DynamicAccessList) para serviços de diagnóstico. Ela constitui a ferramenta central para estruturar padrões de acesso para requisições de diagnóstico de forma granular de acordo com bytes individuais, sequências de bytes, intervalos de valores ou wildcards.

No sistema geral, o builder interage com três parceiros essenciais:

  • Aplicação (Application): Configura os padrões de filtro desejados para requisições de diagnóstico recebidas por meio da Fluent API do builder.
  • DiagnosticServiceDynamicAccessList: Fornece o ponto de entrada por meio de métodos de fábrica como MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) e recebe a lista de acesso definida.
  • Diagnostic Server Instance: A instância do servidor de diagnóstico avalia em tempo de execução os padrões de bytes, wildcards e padrões finais fornecidos durante o pattern matching para direitos de acesso a serviços de diagnóstico ([SWS_DM_01220], [SWS_DM_01221]).

Diagrama de contexto: interação entre aplicação, lista de acesso, builder e servidor de diagnóstico. Fontes: [SWS_DM_01164], [SWS_DM_01166], [SWS_DM_01220].

Ciclo de vida

A criação de uma instância do builder ocorre diretamente por meio do construtor de template, fornecendo-se um valor inicial e uma referência a um buffer de serialização (ara::core::Vector<std::uint8_t>& content) ([SWS_DM_01169]), ou por meio de funções auxiliares como MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]).

Em relação à posse e à semântica de cópia, a classe impõe um uso estritamente linear:

  • Tanto o construtor de cópia ([SWS_DM_01171]) quanto o operador de atribuição por cópia ([SWS_DM_01172]) estão declarados como excluídos (=delete).
  • O operador de atribuição por movimentação também está excluído ([SWS_DM_01173]). Uma transferência só pode ocorrer por meio do construtor de movimentação ([SWS_DM_01170]).

Para a destruição por meio do destrutor ([SWS_DM_01174]), aplica-se uma invariante fixa: antes de destruir o objeto, o método Build() deve obrigatoriamente ser chamado ([SWS_DM_01181]) para concluir a criação da lista.

Em relação à concorrência, o construtor de template e o construtor de movimentação são especificados como thread-safe (thread-safe) ([SWS_DM_01169], [SWS_DM_01170]). Por outro lado, todas as operações que formam padrões (Add, Any, EndsWith, Build) e o destrutor são explicitamente não thread-safe (not thread-safe) ([SWS_DM_01174], [SWS_DM_01175], [SWS_DM_01181]) e não devem ser chamados simultaneamente na mesma instância.

Caminho de utilização

O fluxo típico para configurar um padrão de acesso de diagnóstico divide-se em três etapas:

  1. Inicialização: Solicitação de um builder por meio de DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) com o identificador de serviço ou diretamente por meio do construtor ([SWS_DM_01169]).
  2. Construção de padrão via Fluent API:
    • Adição de bytes individuais (Byte / std::uint8_t, [SWS_DM_01167]) via Add(Byte) ([SWS_DM_01175]), sequências de bytes via Add(ByteString) ([SWS_DM_01168], [SWS_DM_01176]) ou faixas de valores via Add(ByteRange) ([SWS_DM_01177]).
    • Inserção de placeholders via Any(numberOfBytesToIgnore) ([SWS_DM_01178], [SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §7.1.3 «Adding wildcards to a DynamicAccessList»). Com isso, são armazenados bytes no padrão que serão ignorados na correspondência posterior (por ex., 22F1XX para prefixos de DID).
    • Definição opcional de um padrão de encerramento por meio de EndsWith(Byte) ([SWS_DM_01179]) ou EndsWith(ByteRange) ([SWS_DM_01180], [SWS_DM_01221]).
  3. Finalização: Chamada de Build() ([SWS_DM_01181]), concluindo a lista.

Diagrama de sequência: configuração e finalização típicas de um padrão por meio da Fluent API. Fontes: [SWS_DM_01164], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Cenários de erro

Toda a interface de ara::diag::DynamicAccessListDiagServiceBuilder opera sem exceção com noexcept e é especificada como segura contra exceções (exception safe) ([SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181]). Não são lançadas C++-exceptions nem são retornados estados de erro via ara::core::Result.

Portanto, situações de erro resultam primariamente de violações de pré-condições:

  • Omissão da chamada de finalização: Se o builder for destruído sem que Build() tenha sido chamado previamente, isso violará a pré-condição de [SWS_DM_01181]. Interpretação: nesse caso, o padrão de acesso provavelmente permanecerá incompleto e não será considerado pelo servidor de diagnóstico como um critério válido.
  • Concorrência desprotegida: Como todos os métodos para adicionar elementos, bem como Build(), estão classificados como not thread-safe, uma chamada simultânea a partir de várias threads causará corrupção de dados no buffer referenciado.

Este guia baseia-se nos requisitos da especificação AUTOSAR Adaptive R25-11 para o módulo Diagnostics.
