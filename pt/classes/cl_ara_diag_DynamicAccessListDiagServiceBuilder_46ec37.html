Permite a construção passo a passo e a finalização de listas dinâmicas de autorização de acesso para serviços de diagnóstico.

A classe serve para a criação passo a passo de listas dinâmicas de autorização de acesso para serviços de diagnóstico por meio de uma Fluent API encadeável ([SWS_DM_01166]). As aplicações adicionam bytes exatos, faixas de valores e wildcards para definir de forma flexível padrões de acesso para o Diagnostic Server ([SWS_DM_01175], [SWS_DM_01220]). Antes da destruição do objeto move-only não seguro para threads, o método Build() deve ser obrigatoriamente chamado para concluir a configuração ([SWS_DM_01181]).

Contexto

A classe ara::diag::DynamicAccessListDiagServiceBuilder serve para aplicações da AUTOSAR Adaptive Platform construírem passo a passo listas dinâmicas de autorização de acesso (DynamicAccessList) para serviços de diagnóstico ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15.1 «Class: DynamicAccessListDiagServiceBuilder»). Por meio dessas listas, uma aplicação controla quais requisições de diagnóstico (por exemplo, serviços UDS específicos com DIDs ou subfunções concretas) são autorizadas dinamicamente em tempo de execução (AUTOSAR_AP_SWS_Diagnostics §8.2 «Adding wildcards to a DynamicAccessList»).

Os parceiros centrais de interação são a própria aplicação, os métodos de fábrica da classe ara::diag::DiagnosticServiceDynamicAccessList ([SWS_DM_01164], [SWS_DM_01165]) e a instância do Diagnostic Server, que avalia os padrões de bits e bytes montados ao verificar os direitos de serviço contra requisições recebidas ([SWS_DM_01220], [SWS_DM_01221]). Para a representação das estruturas de padrões, a classe disponibiliza os aliases de tipo Byte para octetos individuais (std::uint8_t) e ByteString para sequências de bytes (ara::core::Span<Byte>) ([SWS_DM_01167], [SWS_DM_01168], AUTOSAR_AP_SWS_Diagnostics §8.15.1.1 «Public Member Types»).

Ciclo de vida

Um objeto builder é tipicamente instanciado via DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) ou diretamente pelo construtor, que recebe um valor inicial e uma referência ao buffer de serialização content (ara::core::Vector<std::uint8_t>&) ([SWS_DM_01169]). Interpretação: o parâmetro content deve atuar como memória preenchida continuamente para a representação serializada, que é passada ao Diagnostic Server após a conclusão. Pergunta Q-09b6d9022b23df78 (aberta)

Em relação à posse e copiabilidade, a classe impõe semântica estrita de move-only com atribuição restrita: o construtor de cópia ([SWS_DM_01171]) e o operador de atribuição por cópia ([SWS_DM_01172]) foram excluídos (=delete). Da mesma forma, o operador de atribuição por movimentação foi excluído ([SWS_DM_01173]). Apenas o construtor de movimento está implementado ([SWS_DM_01170]), permitindo que as instâncias sejam movidas conforme a necessidade, mas sem duplicação descontrolada ou reatribuição.

O ciclo de vida está sujeito a uma pós-condição obrigatória: antes da chamada do destrutor ([SWS_DM_01174]), o método Build() deve ser chamado para concluir a criação da lista ([SWS_DM_01181]). Enquanto os construtores são especificados como thread-safe ([SWS_DM_01169], [SWS_DM_01170]), todos os métodos para extensão de padrões e o destrutor não são thread-safe (not thread-safe, [SWS_DM_01174]).

Diagrama de estados: fases de vida do builder, desde a criação e construção passo a passo do padrão até a finalização obrigatória antes da destruição. Fontes: [SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181], [SWS_DM_01174].

Caminho de utilização

A configuração de um padrão ocorre por meio de uma Fluent API, na qual as chamadas de método retornam uma referência à mesma instância do builder ([SWS_DM_01175]):

  1. Inicialização: a aplicação cria o builder, por exemplo, via DiagnosticServiceDynamicAccessList::MakeServiceBuilder com um byte inicial ou uma string de bytes ([SWS_DM_01164], [SWS_DM_01165]).
  2. Extensão do padrão: por meio de métodos Add() sobrecarregados, são anexados bytes individuais ([SWS_DM_01175]), sequências de bytes ([SWS_DM_01176]) ou intervalos fechados de valores ByteRange ([SWS_DM_01177]). Esses valores são verificados quanto à correspondência exata na avaliação posterior.
  3. Inserção de wildcards: com Any(numberOfBytesToIgnore), a aplicação define marcadores de posição ([SWS_DM_01178]). O Diagnostic Server ignora a quantidade especificada de bytes na correspondência de padrões, viabilizando filtros flexíveis como 22F1XX para intervalos de DID ([SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §8.2 «Adding wildcards to a DynamicAccessList»).
  4. Conclusão do padrão e finalização: por meio de EndsWith(), é possível definir um byte ou intervalo de terminação ([SWS_DM_01179], [SWS_DM_01180], [SWS_DM_01221]). Por fim, a chamada de Build() encerra definitivamente o processo de criação ([SWS_DM_01181]).

Diagrama de sequência: sequência típica de interação entre aplicação, método de fábrica e builder na definição de padrões. Fontes: [SWS_DM_01165], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Cenários de erro

Todos os métodos da classe são declarados com noexcept e especificados como seguros contra exceções (exception safe) ([SWS_DM_01169], [SWS_DM_01174], [SWS_DM_01181]). Tratamento de erros via exceções C++ ou valores de retorno de erro não ocorre no nível da API.

A principal pré-condição contratual reside na chamada de Build() antes da destruição do builder ([SWS_DM_01181]). Interpretação: se o objeto builder for destruído sem que Build() tenha sido executado, a configuração de padrão iniciada provavelmente será descartada ou deixará um estado inválido na lista de acesso subjacente. Pergunta Q-18b74c5f91369e94 (aberta)

Além disso, as funções de manipulação não são seguras para threads ([SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181]). O acesso concorrente desprotegido à mesma instância do builder a partir de múltiplas threads leva a estados de memória indefinidos (data races).

Este guia baseia-se exclusivamente na especificação AUTOSAR Adaptive R25-11.

                                      usar
                                      

                                      O método EndsWith da classe ara::diag::DynamicAccessListDiagServiceBuilder serve para definir um intervalo de bytes fechado (ByteRange range) no final do padrão de busca de uma lista de acesso dinâmica (DynamicAccessList) [SWS_DM_01180]. Na chamada do método, a instância do Diagnostic Server anexa o padrão especificado ao final da DynamicAccessList [SWS_DM_01221]. Esse intervalo de valores é utilizado subsequentemente na avaliação dos direitos de acesso para serviços de diagnóstico AUTOSAR_AP_SWS_Diagnostics §8.15.1.2.3.6 «EndsWith(ByteRange)». A chamada ocorre de forma síncrona e não retorna valor (void) [SWS_DM_01180].
                                      


                                      Tratamento de erros e simultaneidade
                                      

                                      A operação é declarada como noexcept e especificada como segura contra exceções (exception safe); códigos de erro ou tratamentos de exceção específicos não existem [SWS_DM_01180]. Em relação à concorrência, o método é classificado como não seguro para threads (not thread-safe) [SWS_DM_01180]. O acesso paralelo à mesma instância de builder a partir de múltiplas threads não é permitido sem sincronização externa.
                                      


                                      Zusammenspiel e ciclo de vida
                                      

                                      No escopo da criação de padrões, existe, além desta variante para intervalos de valores, uma sobrecarga alternativa de EndsWith que define um único byte (Byte value) para a correspondência exata de padrão no final [SWS_DM_01179]. Após a configuração do padrão, a lista deve ser finalizada pela chamada de Build [SWS_DM_01222], antes que a aplicação possa utilizar a DynamicAccessList gerada para verificações de permissão AUTOSAR_AP_SWS_Diagnostics §7.3.2 «End patterns of a DynamicAccessList».
