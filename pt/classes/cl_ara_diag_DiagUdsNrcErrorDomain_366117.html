Contexto

A classe [SWS_DM_00529] ara::diag::DiagUdsNrcErrorDomain representa o domínio de erro padronizado para erros de diagnóstico originários de diferentes classes e interfaces de diagnóstico da AUTOSAR Adaptive Platform. Ela deriva, de acordo com [SWS_DM_00529], da classe base ara::core::ErrorDomain e funciona como o principal elo de ligação entre rotinas de diagnóstico do lado da aplicação e o Diagnostic Management (Diagnostic Management, DM).

No sistema global, o domínio de erro atua nas interfaces de três componentes centrais:

  • Diagnostic Server (DM): Instância que processa pedidos de diagnóstico do testador de diagnóstico do veículo, verifica condições ambientais e gera respostas UDS em conformidade com as normas.
  • Aplicação de diagnóstico externa: Lógica de aplicação ou processador de diagnóstico externo que implementa serviços de diagnóstico específicos do veículo e reporta resultados ou erros através de interfaces ara::diag.
  • Cliente de diagnóstico (Tester): Dispositivo de teste externo que envia comandos de diagnóstico para a unidade de controlo e espera respostas negativas padronizadas (Negative Response Codes, NRC) em caso de ocorrência de erros.

Se uma aplicação de diagnóstico retornar, através de uma interface ara::diag, um resultado com um erro do domínio ara::diag::DiagUdsNrcErrorDomain, o Diagnostic Server processa esse erro de forma direcionada: ele deriva o UDS Negative Response Code a partir do código de erro reportado [SWS_DM_02059] e transmite uma resposta negativa com esse código para o cliente de diagnóstico [SWS_DM_02060]. Além disso, o domínio interage com a verificação de condições ambientais configuráveis: se a recuperação de um elemento de dados falhar devido a um erro deste domínio, o servidor classifica a condição como não cumprida e emite uma mensagem de log e trace [SWS_DM_00970].

Diagrama de contexto: integração do domínio de erros na interação entre o tester, o Diagnostic Server e a aplicação. Fontes: [SWS_DM_02059], [SWS_DM_02060], AUTOSAR_AP_SWS_Diagnostics p. 144

Ciclo de vida

O ciclo de vida de ara::diag::DiagUdsNrcErrorDomain segue as diretrizes para domínios de erro sem estado da plataforma:

  • Criação e inicialização: a classe fornece um construtor padrão sem parâmetros, definido como constexpr e noexcept [SWS_DM_00532]. Interpretação: instâncias de DiagUdsNrcErrorDomain são criadas como constantes de longa duração ou objetos singleton em tempo de compilação ou de carregamento, para ficarem disponíveis durante todo o tempo de execução do processo.
  • Relações de posse: em regra, as aplicações não criam instâncias dinâmicas na heap, mas referenciam o domínio por meio de referências constantes na tipagem de valores ara::core::ErrorCode.
  • Estados e transições: o domínio não possui estados internos variáveis e não requer transições de estado. Consultas de observação como Name() [SWS_DM_00533] ou Message() [SWS_DM_00534] comportam-se de forma sem estado e determinística.
  • Simultaneidade: todas as funções-membro – o construtor [SWS_DM_00532], Name() [SWS_DM_00533], Message() [SWS_DM_00534] bem como ThrowAsException() [SWS_DM_00535] – são explicitamente especificadas como thread-safe. Elas podem ser chamadas em paralelo a partir de diferentes contextos de execução sem bloqueios adicionais.

Caminho de utilização

O fluxo regular na sinalização de erros de diagnóstico divide-se nos seguintes passos:

  1. Requisição de serviço: o cliente de diagnóstico envia uma requisição de serviço UDS para o Diagnostic Server.
  2. Chamada da aplicação de diagnóstico: o Diagnostic Server delega o processamento através de uma interface ara::diag tipada ao processador de diagnóstico externo responsável.
  3. Retorno de erro: se a aplicação de diagnóstico detetar uma condição inválida, gera um código de erro do tipo ara::diag::DiagUdsNrcErrorDomain::Errc [SWS_DM_00530] e retorna-o dentro de um ara::core::Result.
  4. Derivação do NRC: se o Diagnostic Server detetar um erro do domínio ara::diag::DiagUdsNrcErrorDomain, ele deriva o UDS Negative Response Code a partir do valor de DiagUdsNrcErrc [SWS_DM_02059]. Isso ocorre tipicamente através de uma conversão de tipo (static_cast) para um valor de 1 byte no intervalo permitido de 0x01 a 0xFE [SWS_DM_02059].
  5. Resposta de protocolo: o Diagnostic Server gera uma resposta negativa de UDS com o código de erro determinado e envia-a ao cliente [SWS_DM_02060].
  6. Resolução do texto do erro: para registos de diagnóstico ou mensagens de sistema, a descrição do erro pode ser consultada através de Message(), a qual fornece sempre um ponteiro de texto válido [SWS_DM_00534].

Diagrama de sequência: propagação de erro e derivação do UDS-NRC numa operação de diagnóstico com falha. Fontes: [SWS_DM_02059], [SWS_DM_02060]

Cenários de erro

Para o tratamento controlado de estados de erro, a classe disponibiliza tipos especializados e mecanismos de conversão:

  • Enumeração de códigos de erro: o alias de tipo Errc referencia a enum DiagUdsNrcErrc [SWS_DM_00530]. Interpretação: os valores de enumeração refletem os UDS Negative Response Codes padronizados. Valores válidos para a derivação estão no intervalo de 0x01 a 0xFE [SWS_DM_02059].
  • Mapeamento de exceções: o alias Exception referencia DiagUdsNrcException [SWS_DM_00531]. Por meio de ThrowAsException() [SWS_DM_00535], um código de erro pode ser convertido na exceção correspondente e lançado. Se as exceções C++ estiverem desativadas na toolchain, essa função não participa da resolução de sobrecarga [SWS_DM_00535].
  • Erro na recuperação do elemento de dados: se a recuperação de um elemento de dados por um processador externo resultar num erro do domínio ara::diag::DiagUdsNrcErrorDomain, a gestão de diagnóstico trata a parte correspondente da fórmula da condição ambiental como não cumprida e aciona uma mensagem de log e trace [SWS_DM_00970].
  • Comportamento em requisições multi-DID: a presença de ara::diag::DiagUdsNrcErrorDomain no resultado sinaliza um resultado parcial negativo do processador externo. No entanto, em requisições de múltiplos DIDs, um erro individual não conduz necessariamente a uma resposta negativa global, desde que pelo menos um DID seja suportado na sessão ativa (AUTOSAR_AP_SWS_Diagnostics §7.3.x p. 160).

Este guia baseia-se na especificação AUTOSAR Adaptive Platform Release R25-11.
