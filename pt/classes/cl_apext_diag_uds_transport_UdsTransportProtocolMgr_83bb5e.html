The UdsTransportProtocolMgr class manages the interaction between the Diagnostic Server instance(s) and various UDS Transport Protocols (e.g., DoIP[2], CAN[21]). It provides a standard, extensible API for handling transport-specific message reception and optional early payload access.

Contexto

A classe apext::diag::uds_transport::UdsTransportProtocolMgr constitui a interface padronizada para a coordenação entre instâncias do Diagnostic Server (DM Core ou Session Layer) e diferentes protocolos de transporte UDS, como DoIP ou CAN (AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»). Os protocolos de transporte concretos são implementados como subclasses da classe base abstrata apext::diag::uds_transport::UdsTransportProtocolHandler ([SWS_DM_00315], AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»).

Nesta função de mediação, a classe gestora interage essencialmente com três componentes:

  • UDS Transport Protocol Handler (Transport Layer): Notificam o início de mensagens recebidas ([SWS_DM_00309]), entregam pedidos totalmente recebidos ([SWS_DM_00311]), confirmam ordens de envio ([SWS_DM_00312]) e sinalizam alterações de canal bem como de estado ([SWS_DM_00313], [SWS_DM_00314]).
  • Diagnostic Server Core (Session Layer): Assume pedidos UDS válidos para processamento de diagnóstico adicional e gere a atribuição de buffers de mensagens ([SWS_DM_00309], [SWS_DM_00311]).
  • Handlers de transporte periódicos: Transmitem confirmações sobre a transmissão bem-sucedida de sequências periódicas de mensagens ([SWS_DM_01069]).

Diagrama de contexto: Interação do UdsTransportProtocolMgr com os handlers de transporte e a Session Layer. Fontes: AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer», [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00314].

Ciclo de vida

O ciclo de vida de uma implementação de protocolo de transporte é controlado pelo Diagnostic Manager (DM) numa sequência estritamente definida, desde a construção e inicialização até à paragem ([SWS_DM_00329], AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer»). A classe UdsTransportProtocolMgr declara um destrutor virtual padrão ([SWS_DM_01524]).

Durante a operação, as fases de desativação são sincronizadas: se um handler fechar as suas ligações de rede e libertar recursos em reação a uma paragem, notifica o gestor através do callback HandlerStopped, indicando o seu handlerId ([SWS_DM_00314]).

No que diz respeito às relações de memória e de posse, aplica-se aos buffers de mensagens um modelo de transferência claro: no início de uma transmissão, o DM-Core cria o objeto de mensagem e passa o seu ponteiro para o handler ([SWS_DM_00309]). Após a receção completa, o handler transfere a posse da mensagem de volta para o DM-Core genérico através de HandleMessage, utilizando a semântica de unique_ptr ([SWS_DM_00311]).

Todos os métodos de interface estão especificados como seguros contra exceções (noexcept), mas não seguros para threads (not thread-safe) ([SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00312]). Interpretação: As chamadas para o gestor devem, portanto, presumivelmente ser sincronizadas pelos componentes de transporte e de sessão que realizam a chamada.

Caminho de utilização

O fluxo regular para o processamento de pedidos de diagnóstico UDS recebidos divide-se nos seguintes passos:

  1. Indicação de mensagem: Caso o handler suporte a indicação, este chama IndicateMessage aquando da chegada dos primeiros dados ([SWS_DM_00309]). Neste processo, são transmitidos o endereço de origem e de destino, o tipo de endereçamento (físico ou funcional), o tamanho total esperado, bem como o GlobalChannelIdentifier ([SWS_DM_09021]). Através de payloadInfo já podem ser passados os primeiros bytes, para que o DM possa, por exemplo, detetar antecipadamente pedidos funcionais de Tester-Present ([SWS_DM_00309]).
  2. Disponibilização de buffer: O gestor devolve um par composto por IndicationResult e um UdsMessagePtr atribuído ([SWS_DM_00309]). Se o resultado for IndicationResult::kIndicationOk ([SWS_DM_00384]), o handler preenche o buffer com os dados recebidos.
  3. Entrega à Session Layer: Após a receção completa, o handler entrega a mensagem ao gestor via HandleMessage ([SWS_DM_00311]), o que corresponde ao serviço T_Data.ind segundo a norma ISO 14229-2. A chamada retorna imediatamente; a avaliação posterior decorre de forma assíncrona na Session Layer ([SWS_DM_00311]).
  4. Confirmação de envio: Para respostas UDS enviadas, o handler confirma o sucesso posteriormente através de TransmitConfirmation com o resultado kTransmitOk ([SWS_DM_00312], [SWS_DM_00307]), correspondendo a T_Data.con segundo a norma ISO 14229-2.

Diagrama de sequência: Procedimento de receção de mensagens UDS, desde a indicação até à entrega assíncrona à Session Layer. Fontes: [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00384].

Cenários de erro

As condições de erro durante o transporte ou a alocação de buffers são intercetadas através de valores de estado e interfaces de erro definidos:

  • Falha na indicação: Se o DM-Core não conseguir aceitar uma mensagem indicada, comunica-o através do enum IndicationResult ([SWS_DM_00309], [SWS_DM_00384]):
    • kIndicationOccupied: O servidor ou a sessão de diagnóstico está atualmente ocupado(a) ([SWS_DM_00384]).
    • kIndicationOverflow: O tamanho da mensagem transmitida excede a capacidade do buffer ([SWS_DM_00384]).
    • kIndicationUnknownTargetAddress: O endereço de destino endereçado não está configurado ([SWS_DM_00384]).
  • Interrupção da receção: Se ocorrer uma quebra de ligação ou um erro de transmissão após um IndicateMessage bem-sucedido, o handler chama NotifyMessageFailure ([SWS_DM_00310]). O objeto UdsMessage anteriormente obtido é devolvido ao DM sem que ocorra uma chamada de HandleMessage ([SWS_DM_00310]).
  • Erro de transmissão de envio: Se uma mensagem de saída não puder ser enviada ao nível da rede, o handler reporta através de TransmitConfirmation o resultado TransmissionResult::kTransmitFailed ([SWS_DM_00312], [SWS_DM_00307]).
  • Reativação de canal: Após uma perda temporária de ligação, o handler sinaliza a nova disponibilidade de um canal através de ChannelReestablished com o GlobalChannelIdentifier ([SWS_DM_00313], [SWS_DM_09021]), caso essa notificação tenha sido solicitada anteriormente ([SWS_DM_00313]).

Recepção de mensagens

HandleMessage função

Hands over a valid received UDS message (currently this is only a request type) from the Transport Layer to the Session Layer. This corresponds to T_Data.ind of Figure 2 from ISO 14229-2[25]. The behavior is asynchronously, i.e. the UDS Message is handed over to the Session Layer and it is expected, that it "instantly" returns, which means, that real processing of the message shall be done asynchronously by the Transport Layer!

virtual void HandleMessage (UdsMessagePtr message) noexcept=0;

<h4>Contexto</h4>
<p>A classe <code>apext::diag::uds_transport::UdsTransportProtocolMgr</code> constitui a interface padronizada para a coordenação entre instâncias do Diagnostic Server (DM Core ou Session Layer) e diferentes protocolos de transporte UDS, como DoIP ou CAN (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»</a>). Os protocolos de transporte concretos são implementados como subclasses da classe base abstrata <code>apext::diag::uds_transport::UdsTransportProtocolHandler</code> (<a class="spec-record-ref" data-req="SWS_DM_00315" href="../spec/record.html?id=SWS_DM_00315">[SWS_DM_00315]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1 «Support of UDS Transport Layer»</a>).</p>
<p>Nesta função de mediação, a classe gestora interage essencialmente com três componentes:</p>
<ul>
<li><strong>UDS Transport Protocol Handler (Transport Layer):</strong> Notificam o início de mensagens recebidas (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>), entregam pedidos totalmente recebidos (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>), confirmam ordens de envio (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>) e sinalizam alterações de canal bem como de estado (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>, <a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>).</li>
<li><strong>Diagnostic Server Core (Session Layer):</strong> Assume pedidos UDS válidos para processamento de diagnóstico adicional e gere a atribuição de buffers de mensagens (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</li>
<li><strong>Handlers de transporte periódicos:</strong> Transmitem confirmações sobre a transmissão bem-sucedida de sequências periódicas de mensagens (<a class="spec-record-ref" data-req="SWS_DM_01069" href="../spec/record.html?id=SWS_DM_01069">[SWS_DM_01069]</a>).</li>
</ul>

<h4>Ciclo de vida</h4>
<p>O ciclo de vida de uma implementação de protocolo de transporte é controlado pelo Diagnostic Manager (DM) numa sequência estritamente definida, desde a construção e inicialização até à paragem (<a class="spec-record-ref" data-req="SWS_DM_00329" href="../spec/record.html?id=SWS_DM_00329">[SWS_DM_00329]</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=95">AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 «Initialization, Starting and Stopping of a UDS TransportLayer»</a>). A classe <code>UdsTransportProtocolMgr</code> declara um destrutor virtual padrão (<a class="spec-record-ref" data-req="SWS_DM_01524" href="../spec/record.html?id=SWS_DM_01524">[SWS_DM_01524]</a>).</p>
<p>Durante a operação, as fases de desativação são sincronizadas: se um handler fechar as suas ligações de rede e libertar recursos em reação a uma paragem, notifica o gestor através do callback <code>HandlerStopped</code>, indicando o seu <code>handlerId</code> (<a class="spec-record-ref" data-req="SWS_DM_00314" href="../spec/record.html?id=SWS_DM_00314">[SWS_DM_00314]</a>).</p>
<p>No que diz respeito às relações de memória e de posse, aplica-se aos buffers de mensagens um modelo de transferência claro: no início de uma transmissão, o DM-Core cria o objeto de mensagem e passa o seu ponteiro para o handler (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). Após a receção completa, o handler transfere a posse da mensagem de volta para o DM-Core genérico através de <code>HandleMessage</code>, utilizando a semântica de <code>unique_ptr</code> (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</p>
<p>Todos os métodos de interface estão especificados como seguros contra exceções (<code>noexcept</code>), mas não seguros para threads (<em>not thread-safe</em>) (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>, <a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>). Interpretação: As chamadas para o gestor devem, portanto, presumivelmente ser sincronizadas pelos componentes de transporte e de sessão que realizam a chamada.</p>

<h4>Caminho de utilização</h4>
<p>O fluxo regular para o processamento de pedidos de diagnóstico UDS recebidos divide-se nos seguintes passos:</p>
<ol>
<li><strong>Indicação de mensagem:</strong> Caso o handler suporte a indicação, este chama <code>IndicateMessage</code> aquando da chegada dos primeiros dados (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). Neste processo, são transmitidos o endereço de origem e de destino, o tipo de endereçamento (físico ou funcional), o tamanho total esperado, bem como o <code>GlobalChannelIdentifier</code> (<a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>). Através de <code>payloadInfo</code> já podem ser passados os primeiros bytes, para que o DM possa, por exemplo, detetar antecipadamente pedidos funcionais de Tester-Present (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>).</li>
<li><strong>Disponibilização de buffer:</strong> O gestor devolve um par composto por <code>IndicationResult</code> e um <code>UdsMessagePtr</code> atribuído (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>). Se o resultado for <code>IndicationResult::kIndicationOk</code> (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>), o handler preenche o buffer com os dados recebidos.</li>
<li><strong>Entrega à Session Layer:</strong> Após a receção completa, o handler entrega a mensagem ao gestor via <code>HandleMessage</code> (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>), o que corresponde ao serviço <code>T_Data.ind</code> segundo a norma ISO 14229-2. A chamada retorna imediatamente; a avaliação posterior decorre de forma assíncrona na Session Layer (<a class="spec-record-ref" data-req="SWS_DM_00311" href="../spec/record.html?id=SWS_DM_00311">[SWS_DM_00311]</a>).</li>
<li><strong>Confirmação de envio:</strong> Para respostas UDS enviadas, o handler confirma o sucesso posteriormente através de <code>TransmitConfirmation</code> com o resultado <code>kTransmitOk</code> (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>, <a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>), correspondendo a <code>T_Data.con</code> segundo a norma ISO 14229-2.</li>
</ol>

<h4>Cenários de erro</h4>
<p>As condições de erro durante o transporte ou a alocação de buffers são intercetadas através de valores de estado e interfaces de erro definidos:</p>
<ul>
<li><strong>Falha na indicação:</strong> Se o DM-Core não conseguir aceitar uma mensagem indicada, comunica-o através do enum <code>IndicationResult</code> (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>, <a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>):
  <ul>
  <li><code>kIndicationOccupied</code>: O servidor ou a sessão de diagnóstico está atualmente ocupado(a) (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  <li><code>kIndicationOverflow</code>: O tamanho da mensagem transmitida excede a capacidade do buffer (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  <li><code>kIndicationUnknownTargetAddress</code>: O endereço de destino endereçado não está configurado (<a class="spec-record-ref" data-req="SWS_DM_00384" href="../spec/record.html?id=SWS_DM_00384">[SWS_DM_00384]</a>).</li>
  </ul>
</li>
<li><strong>Interrupção da receção:</strong> Se ocorrer uma quebra de ligação ou um erro de transmissão após um <code>IndicateMessage</code> bem-sucedido, o handler chama <code>NotifyMessageFailure</code> (<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>). O objeto <code>UdsMessage</code> anteriormente obtido é devolvido ao DM sem que ocorra uma chamada de <code>HandleMessage</code> (<a class="spec-record-ref" data-req="SWS_DM_00310" href="../spec/record.html?id=SWS_DM_00310">[SWS_DM_00310]</a>).</li>
<li><strong>Erro de transmissão de envio:</strong> Se uma mensagem de saída não puder ser enviada ao nível da rede, o handler reporta através de <code>TransmitConfirmation</code> o resultado <code>TransmissionResult::kTransmitFailed</code> (<a class="spec-record-ref" data-req="SWS_DM_00312" href="../spec/record.html?id=SWS_DM_00312">[SWS_DM_00312]</a>, <a class="spec-record-ref" data-req="SWS_DM_00307" href="../spec/record.html?id=SWS_DM_00307">[SWS_DM_00307]</a>).</li>
<li><strong>Reativação de canal:</strong> Após uma perda temporária de ligação, o handler sinaliza a nova disponibilidade de um canal através de <code>ChannelReestablished</code> com o <code>GlobalChannelIdentifier</code> (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>, <a class="spec-record-ref" data-req="SWS_DM_09021" href="../spec/record.html?id=SWS_DM_09021">[SWS_DM_09021]</a>), caso essa notificação tenha sido solicitada anteriormente (<a class="spec-record-ref" data-req="SWS_DM_00313" href="../spec/record.html?id=SWS_DM_00313">[SWS_DM_00313]</a>).</li>
</ul>
