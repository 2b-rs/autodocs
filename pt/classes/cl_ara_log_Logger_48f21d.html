classe ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Contexto

A classe ara::log::Logger representa um contexto de logging dentro de um processo de aplicação AUTOSAR Adaptive ou domínio de processo. Tal contexto encapsula propriedades centrais para o registo de logs: um ID de contexto, uma descrição associada do ID de contexto, bem como um nível de log predefinido (Default Log Level) configurável. Através destes contextos, a saída de log é diferenciada e controlada dentro do sistema.

Na arquitetura do sistema, ara::log::Logger atua como mediador entre três intervenientes:

  • Processo de aplicação (Application Process): Utiliza instâncias de ara::log::Logger para emitir mensagens, consultar dinamicamente ou ajustar limiares de filtragem.
  • Framework de logging: Mantém uma propriedade estrita («strong ownership») sobre todas as instâncias de logger, controla a sua criação através de funções fábrica como ara::log::CreateLogger e assume o housekeeping.
  • Backend de logging: Recebe os dados de log propriamente ditos; os contextos de logger são registados automaticamente no backend durante a fase de inicialização e desregistados durante o encerramento ordenado do processo.

Diagrama de contexto: integração da classe Logger na interação com a aplicação, a framework de logging e o backend. Fontes: [SWS_LOG_00259]

Ciclo de vida

A gestão das instâncias de ara::log::Logger está sujeita a um controlo rigoroso por parte da framework, a fim de assegurar uma sincronização perfeita com o backend de logging:

  • Criação e relações de propriedade: O construtor padrão está explicitamente eliminado (Logger() = delete, [SWS_LOG_00259]). A instanciação direta pela aplicação é proibida. A criação ocorre de forma controlada através de funções como ara::log::CreateLogger. A propriedade permanece na framework de logging.
  • Registo e limpeza: Um contexto de logger é registado automaticamente no backend de logging aquando da sua criação. No encerramento do processo, o cancelamento do registo ocorre automaticamente, libertando os programadores da aplicação da gestão manual do ciclo de vida.
  • Destruição: O destrutor ~Logger() está especificado ([SWS_LOG_00260]). Está declarado como seguro para threads, mas identificado como não seguro contra exceções («not exception safe») ([SWS_LOG_00260]).
  • Simultaneidade: Todos os métodos para registo de logs e consulta de valores de limiar estão especificados como seguros para threads ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064]). Várias threads podem utilizar a mesma instância de logger em paralelo.

Caminho de utilização

O fluxo típico ao emitir mensagens de log divide-se nas seguintes fases:

  1. Verificar ou configurar o limiar de filtragem: A aplicação pode definir o limiar de filtragem de uma instância através de SetThreshold(threshold) em tempo de execução ([SWS_LOG_00255]). Antes de preparações computacionalmente intensivas de dados de log, pode consultar-se através de IsEnabled(logLevel) se o nível de log pretendido cumpre o limiar de relatório configurado ([SWS_LOG_00070]). Se a verificação retornar false, a preparação pode ser ignorada.
  2. Iniciar logging baseado em stream: Para o registo de texto, a classe disponibiliza métodos específicos para cada nível de gravidade:
    • LogFatal() ([SWS_LOG_00064])
    • LogError() ([SWS_LOG_00065])
    • LogWarn() ([SWS_LOG_00066])
    • LogInfo() ([SWS_LOG_00067])
    • LogDebug() ([SWS_LOG_00068])
    • LogVerbose() ([SWS_LOG_00069])
    • WithLevel(logLevel) ([SWS_LOG_00131]) para a determinação programática da urgência.
    Cada um destes métodos retorna um objeto LogStream, que recebe argumentos através do operador de stream << ([SWS_LOG_00064]).
  3. Tempo de vida do stream e emissão: No caso padrão, o tempo de vida do objeto LogStream está limitado a uma única instrução e termina com o ponto e vírgula após o último argumento ([SWS_LOG_00064]). Se necessário, o stream pode ser atribuído a uma variável para estender o seu tempo de vida ao longo de várias instruções ([SWS_LOG_00064]).
  4. Emitir mensagens modeladas: Em alternativa ao streaming, mensagens previamente modeladas podem ser emitidas através de Log(id, args...) ([SWS_LOG_00204]). Se for necessário passar atributos adicionais, a chamada é efetuada através de LogWith(attrs, msgId, params...) com um tuplo de atributos ([SWS_LOG_00133]).

Diagrama de sequência: sequência de chamadas de uma operação de logging de stream filtrada. Fontes: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064]

Cenários de erro

O tratamento de erros em ara::log::Logger baseia-se predominantemente na verificação estática de tipos em tempo de compilação e numa estrita segurança contra exceções:

  • Argumentos incompatíveis em mensagens modeladas: Se a função de modelo Log(id, args...) for chamada com parâmetros que não correspondam exatamente à definição da mensagem modelada, o programa é mal formado («ill-formed») ([SWS_LOG_00204]). Isto resulta num erro de compilação.
  • Atributos inválidos em LogWith: Em LogWith(attrs, msgId, params...), a função é excluída da resolução de sobrecarga via SFINAE se um elemento do tuplo de atributos não representar um atributo válido ([SWS_LOG_00133]).
  • Garantias de exceção: Todas as funções de logging e de consulta (entre as quais IsEnabled, SetThreshold, todos os métodos Log*, WithLevel, Log e LogWith) estão especificadas como seguras contra exceções («exception safe») e declaradas com noexcept ([SWS_LOG_00070], [SWS_LOG_00255], [SWS_LOG_00064], [SWS_LOG_00131], [SWS_LOG_00204], [SWS_LOG_00133]). Uma exceção é o destrutor ~Logger(), que é indicado como não seguro contra exceções («not exception safe») ([SWS_LOG_00260]). Interpretação: isto deve significar que, no caso de erros internos de limpeza ou de libertação no âmbito do housekeeping do backend, os estados de erro não são totalmente intercetados, razão pela qual o cancelamento de registo deve ocorrer no encerramento regular do processo.
