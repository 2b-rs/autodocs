classe apext::diag::uds_transport::UdsMessage

class UdsMessage {...};

class represents an UDS message exchanged between DM generic core (UdsTransport ProtocolMgr) and a specific implementation of UdsTransportProtocolHandler on diagnostic request reception path or diagnostic response transmission path. UdsMessage provides the storage for UDS requests/responses.

Instances of UdsMessage (with optimized resource allocation) are only created by DM generic core, the UdsTransportProtocolHandler can read/write on it.

Serve como suporte de armazenamento e de informações para mensagens UDS na troca de dados no Adaptive Diagnostic Manager.

A classe apext::diag::uds_transport::UdsMessage representa o objeto de armazenamento e transferência padronizado para mensagens de diagnóstico trocadas entre o núcleo de diagnóstico genérico e handlers específicos de transporte. As instâncias são criadas exclusivamente pelo núcleo genérico com alocação de memória otimizada e disponibilizadas via UdsMessagePtr [SWS_DM_09012]. No caminho de recepção, o handler preenche o buffer de dados disponibilizado a partir do Service ID e encaminha a mensagem após anexar eventuais metadados de canal [SWS_DM_00388]. Se o núcleo não puder processar uma mensagem devido à ocupação atual, a atribuição é recusada e um ponteiro nulo é fornecido [SWS_DM_00386].

Contexto

A classe apext::diag::uds_transport::UdsMessage representa o objeto central de dados e armazenamento para mensagens UDS trocadas entre o núcleo genérico do Diagnostic Management (DM Generic Core ou UdsTransportProtocolMgr) e uma implementação específica de UdsTransportProtocolHandler. Ela serve como encapsulamento e armazenamento (storage) para UDS requests de entrada e UDS responses de saída.

Além dos dados úteis, UdsMessage transporta os parâmetros de endereçamento da comunicação de diagnóstico: o endereço de origem Address [SWS_DM_00293] via GetSa() [SWS_DM_00297], o endereço de destino via GetTa() [SWS_DM_00298], bem como o tipo de endereço TargetAddressType (físico com kPhysical ou funcional com kFunctional) [SWS_DM_00296] via GetTaType() [SWS_DM_00299]. Além disso, metainformações específicas do canal, como parâmetros de conexão para DoIP, podem ser anexadas via AddMetaInfo() [SWS_DM_00294], [SWS_DM_00302].

Diagrama de contexto: interação entre o núcleo do DM, o transport handler e a UdsMessage. Fontes: [SWS_DM_09012], [SWS_DM_00385], [SWS_DM_00345]

Ciclo de vida

Instâncias de UdsMessage são criadas exclusivamente pelo núcleo genérico do Diagnostic Management com alocação otimizada de recursos. Para impedir uma instanciação descontrolada por handlers de protocolo, o construtor padrão é declarado protegido (protected) [SWS_DM_09012]. Os handlers obtêm acesso a objetos de mensagem exclusivamente por meio de ponteiros de propriedade do tipo apext::diag::uds_transport::UdsMessagePtr [SWS_DM_00303] ou, para acessos exclusivos de leitura, via apext::diag::uds_transport::UdsMessageConstPtr [SWS_DM_00304], AUTOSAR_AP_SWS_Diagnostics p. 98.

A destruição do objeto ocorre por meio do destrutor virtual ~UdsMessage() [SWS_DM_09010]. Em relação à simultaneidade, os métodos de consulta para informações de endereço (GetSa, GetTa, GetTaType) são reentrantes (reentrant) e seguros contra exceções (noexcept) [SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299]. O acesso ao buffer de dados via GetPayload(), bem como a adição de metadados via AddMetaInfo(), são classificados, por outro lado, como não thread-safe, visto que a implementação pode realizar alocações de buffer e de recursos no âmbito dessas chamadas [SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302].

Caminho de utilização

No fluxo regular do caminho de recepção, o UdsTransportProtocolHandler anuncia uma requisição UDS de entrada via UdsTransportProtocolMgr::IndicateMessage() ao DM [SWS_DM_00385]. Caso o DM esteja pronto para recepção, ele confirma isso com o status kIndicationOk e passa um UdsMessagePtr com tamanho mínimo de um byte e a capacidade de buffer desejada pelo DM [SWS_DM_00385].

Em seguida, o handler de protocolo chama o método não constante GetPayload() para obter uma referência gravável para a área de memória subjacente (uds_transport::ByteSpan&) [SWS_DM_00301]. Ele preenche esse buffer começando no identificador de serviço (SID) até a capacidade máxima do objeto UdsMessage ou o comprimento total da mensagem [SWS_DM_00388]. Após a adição opcional de metadados específicos de canal via AddMetaInfo() [SWS_DM_00302], o handler encaminha o objeto preenchido ao núcleo de diagnóstico via UdsTransportProtocolMgr::HandleMessage() [SWS_DM_00345]. (Interpretação: no caminho de transmissão para respostas de diagnóstico, a disponibilização de UdsMessage deve ocorrer de forma análoga pelo núcleo genérico.) Pergunta Q-4f568a0e527bdfbc (aberta)

Diagrama de sequência: sequência de interação na recepção de uma mensagem UDS. Fontes: [SWS_DM_00385], [SWS_DM_00386], [SWS_DM_00388], [SWS_DM_00301], [SWS_DM_00302], [SWS_DM_00345]

Cenários de erro

Se o DM não puder processar a mensagem anunciada via IndicateMessage() porque está ocupado com o processamento ativo de um serviço da mesma sessão de Tester Present, ele retornará o status kIndicationOccupied e um UdsMessagePtr igual a nullptr [SWS_DM_00386]. Nesse caso, nenhuma UdsMessage é disponibilizada e a recepção é interrompida. Da mesma forma, um endereço de destino desconhecido leva ao resultado kIndicationUnknownTargetAddress com um ponteiro nulo como referência de mensagem AUTOSAR_AP_SWS_Diagnostics p. 100.

Ao preencher o buffer, o handler de protocolo deve respeitar a capacidade de buffer predefinida: requisições recebidas que excedem a capacidade disponibilizada da UdsMessage são limitadas ao tamanho total do buffer [SWS_DM_00388]. Além disso, acessos simultâneos e desprotegidos a GetPayload() ou AddMetaInfo() a partir de múltiplas threads levam a comportamento indefinido, pois essas interfaces estão explicitamente especificadas como não seguras em relação a threads (unsafe) [SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302].

A função-membro virtual AddMetaInfo da classe apext::diag::uds_transport::UdsMessage serve para associar novos metadados a uma mensagem de diagnóstico [SWS_DM_00302]. Ela é tipicamente chamada por um plugin de protocolo de transporte para anexar informações adicionais específicas do canal – como, por exemplo, chaves de metadados predefinidas para DoIP – à respetiva solicitação de diagnóstico AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».

Para o uso da interface, aplicam-se as seguintes condições de enquadramento [SWS_DM_00302]:

  • Contexto de chamada e cabeçalho: A declaração é fornecida através do ficheiro de cabeçalho apext/diag/uds_transport/uds_message.h e executada diretamente em instâncias de UdsMessage AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».
  • Parâmetros de passagem: O parâmetro de entrada metaInfo do tipo MetaInfoMap passa as metainformações a serem adicionadas da solicitação [SWS_DM_00302].
  • Valor de retorno: A função síncrona não fornece valor de retorno (void) [SWS_DM_00302].
  • Tratamento de erros: A operação é fornecida com o identificador noexcept e especificada como segura contra exceções (exception safe); códigos de erro específicos não existem [SWS_DM_00302].

Em relação à concorrência, o método é declarado como não seguro para threads (thread safety: unsafe) [SWS_DM_00302]. Interpretação: Os chamadores deverão, portanto, ser responsáveis por proteger acessos concorrentes à mesma instância de UdsMessage através de mecanismos externos, uma vez que a especificação não prevê sincronização interna AUTOSAR_AP_SWS_Diagnostics §C.5.2.2.2.1 «AddMetaInfo».
