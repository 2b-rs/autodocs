classe apext::diag::uds_transport::UdsMessage

[SWS_DM_00291] Upstream: RS_Diag_04147

class UdsMessage {...};

class represents an UDS message exchanged between DM generic core (UdsTransport ProtocolMgr) and a specific implementation of UdsTransportProtocolHandler on diagnostic request reception path or diagnostic response transmission path. UdsMessage provides the storage for UDS requests/responses.

Instances of UdsMessage (with optimized resource allocation) are only created by DM generic core, the UdsTransportProtocolHandler can read/write on it.

Contexto

A classe apext::diag::uds_transport::UdsMessage encapsula uma mensagem UDS (Request ou Response) e atua como armazenamento central para dados de diagnóstico trocados entre o núcleo genérico do Diagnostic Management (UdsTransportProtocolMgr) e uma implementação concreta de protocolo de transporte (UdsTransportProtocolHandler). A instância fornece o buffer de mensagem subjacente tanto no caminho de recepção de requisições de diagnóstico (RX) quanto no caminho de transmissão de respostas de diagnóstico (TX).

Além dos dados úteis puros, UdsMessage gerencia metadados e informações de endereçamento. Por meio de GetSa(), consulta-se o endereço de origem ([SWS_DM_00297]) e, por meio de GetTa(), o endereço de destino ([SWS_DM_00298]) do tipo Address ([SWS_DM_00293]). O tipo de endereço de destino é determinado por meio de GetTaType() ([SWS_DM_00299]), no qual o enum TargetAddressType diferencia entre endereçamento físico (kPhysical) e funcional (kFunctional) ([SWS_DM_00296]). Além disso, informações adicionais específicas do canal (por exemplo, metadados predefinidos para plug-ins DoIP) podem ser anexadas à mensagem por meio do método AddMetaInfo() na forma de uma MetaInfoMap ([SWS_DM_00302], [SWS_DM_00294]).

Diagrama de contexto: interação entre o núcleo DM, o manipulador de protocolo de transporte e UdsMessage. Fontes: [SWS_DM_00385], [SWS_DM_09012].

Ciclo de vida

Instâncias de UdsMessage são criadas exclusivamente pelo núcleo genérico do Diagnostic Management com alocação otimizada de recursos. O construtor padrão UdsMessage() é declarado como protegido (protected) ([SWS_DM_09012]), a fim de impedir explicitamente que manipuladores de protocolo de transporte instanciem instâncias por conta própria.

A posse e o repasse de objetos UdsMessage são controlados por meio de smart pointers. Para isso, a plataforma define os aliases de tipo UdsMessagePtr para acesso de escrita ([SWS_DM_00303]) e UdsMessageConstPtr para acesso de leitura constante ([SWS_DM_00304]). Ao aceitar uma mensagem, o núcleo DM transfere a posse da instância para o manipulador por meio de um UdsMessagePtr ([SWS_DM_00385]). Após a conclusão do preenchimento, a mensagem é transferida novamente para o núcleo DM para processamento ([SWS_DM_00345]). A liberação e destruição ocorrem de forma determinística por meio do destrutor padrão virtual ~UdsMessage() ([SWS_DM_09010]).

Em relação à simultaneidade, os métodos para consulta de endereço (GetSa(), GetTa(), GetTaType()) são especificados como reentrantes ([SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299]). Por outro lado, os métodos para acesso a dados úteis e metadados (GetPayload() e AddMetaInfo()) não são thread-safe (unsafe) ([SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302]), uma vez que as implementações têm permissão para realizar alocações de buffer e de recursos durante chamadas de GetPayload().

Caminho de utilização

O fluxo típico no caminho de recepção de diagnóstico (RX) divide-se nas seguintes etapas:

  1. Anúncio: O UdsTransportProtocolHandler recebe um pedido UDS da rede e sinaliza a sua receção através da chamada de UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00385]).
  2. Instanciação e disponibilização de buffer: Se o DM puder processar o pedido, IndicateMessage() retorna um std::pair ([SWS_DM_00309]) com o estado kIndicationOk e um UdsMessagePtr que detém a UdsMessage criada. O buffer atribuído apresenta um tamanho mínimo de um byte ([SWS_DM_00385]).
  3. Preenchimento dos dados úteis: O handler chama a sobrecarga não constante GetPayload() ([SWS_DM_00301]) e obtém uma referência para uds_transport::ByteSpan&. O handler preenche o objeto UdsMessage com os dados UDS recebidos, a começar pelo ID de serviço (SID), seja até à capacidade total da mensagem ou até ao comprimento total do pedido UDS recebido ([SWS_DM_00388]).
  4. Anexação de metadados: Se necessário, o handler adiciona metadados específicos do canal através de AddMetaInfo() ([SWS_DM_00302]).
  5. Encaminhamento para o núcleo do DM: Assim que os dados úteis tiverem sido completamente escritos na UdsMessage, o handler entrega a mensagem via UdsTransportProtocolMgr::HandleMessage() ao núcleo genérico do DM para processamento adicional de diagnóstico ([SWS_DM_00345]).
  6. Acesso de leitura no núcleo do DM: O núcleo de diagnóstico lê os dados da mensagem (A_Data de acordo com a ISO) em modo de apenas leitura através da sobrecarga constante GetPayload() const ([SWS_DM_00300]).

Interpretação: No caminho de resposta de diagnóstico (TX), o núcleo genérico do DM deverá, de modo análogo, preencher ele próprio o objeto UdsMessage com dados de resposta e entregá-lo ao UdsTransportProtocolHandler para transmissão.

Diagrama de sequência: sequência de aceitação da mensagem e de preenchimento do buffer no caminho de receção. Fontes: [SWS_DM_00301], [SWS_DM_00302], [SWS_DM_00345], [SWS_DM_00385], [SWS_DM_00388].

Cenários de erro

Na interação e na alocação de buffer, podem ocorrer as seguintes situações de erro:

  • DM ocupado (Busy): Se o DM já estiver ocupado com o processamento ativo de um serviço da mesma conversação, IndicateMessage() retorna o estado kIndicationOccupied e um ponteiro nulo para UdsMessagePtr ([SWS_DM_00386]). Neste caso, nenhuma UdsMessage é disponibilizada. Uma exceção a isto são os pedidos TesterPresent funcionais com suppressPosRspMsgIndicationBit definido (payload 0x3E 0x80), que são válidos em qualquer momento e podem ser processados ([SWS_DM_00386], [SWS_DM_00126]).
  • Endereço de destino desconhecido: Se o endereço de destino da mensagem não puder ser resolvido, o DM sinaliza isso através do resultado kIndicationUnknownTargetAddress e define UdsMessagePtr como nullptr (AUTOSAR_AP_SWS_Diagnostics p. 100). Não ocorre nenhuma alocação de um objeto de mensagem.
  • Limitação do buffer: A capacidade do objeto UdsMessage transmitido está limitada pela alocação definida pelo DM. O handler só pode escrever no buffer, no máximo, até ao limite da sua capacidade ([SWS_DM_00388]).

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 (módulo diag) e resume os requisitos para apext::diag::uds_transport::UdsMessage.
