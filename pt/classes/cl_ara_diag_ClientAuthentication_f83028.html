Serve à aplicação para reportar estados de autenticação e papéis de usuário ativos ao Diagnostic Server.

A interface permite que a aplicação informe o Diagnostic Server sobre o status de autenticação, bem como sobre os papéis de usuário ativos de um cliente de diagnóstico [SWS_DM_01132]. Por meio de chamadas como Authenticate ou OverrideDefaultRoles, são controladas as transições de estado e fornecidos manipuladores para o gerenciamento de listas de acesso dinâmicas [SWS_DM_01206]. Alterações de estado decorrentes de timeouts podem ser monitoradas assincronamente por meio de um notificador. Como a classe não é segura para threads e não permite cópias, o acesso dentro da aplicação deve ocorrer de forma sincronizada.

Contexto

A classe ara::diag::ClientAuthentication serve como interface central para a aplicação informar a instância do Diagnostic Server sobre os estados de autenticação e os papéis de usuário autenticados atualmente [SWS_DM_01132], SWS Diagnostics, p. 129. Três partes essenciais participam dessa interação:

  • Aplicação (Application): Realiza verificações de autenticação – seja utilizando interfaces do Diagnostic Server ou por meio de mecanismos próprios da aplicação – e transmite os papéis de usuário para o Diagnostic Server [SWS_DM_01142].
  • Diagnostic Server / Diagnostic Manager: Gerencia as sessões de diagnóstico e aplica os direitos de acesso a recursos de diagnóstico com base nos papéis e no status de autenticação [SWS_DM_01206].
  • Cliente de diagnóstico: Um testador externo ou cliente SOVD que envia solicitações de diagnóstico para a ECU [SWS_DM_01210], [SWS_DM_01470].

A quantidade de instâncias de ClientAuthentication é definida pelo elemento de modelo DiagnosticExternalAuthenticationIdentification SWS Diagnostics, p. 129. Esse elemento permite configurar uma autenticação para um cliente com um endereço de origem fixo ou sobre uma faixa de endereços, caso o endereço de origem final ainda não seja conhecido em tempo de compilação SWS Diagnostics, p. 129. Interpretação: A associação de clientes de diagnóstico a instâncias concretas de ClientAuthentication ocorre em tempo de execução com base nessas faixas de endereços de origem. No caso de clientes SOVD, o Diagnostic Server passa diretamente um objeto ClientAuthentication para a aplicação durante a validação do token de autorização via ara::diag::SovdAuthorization::ValidateAuthorization [SWS_DM_01470].

Diagrama de contexto: parceiros de interação da interface de autenticação. Fontes: [SWS_DM_01132], [SWS_DM_01202], [SWS_DM_01470], SWS Diagnostics, p. 129

Ciclo de vida

A aplicação obtém uma instância de ClientAuthentication por meio de métodos sobrecarregados de ara::diag::ExternalAuthentication::Get [SWS_DM_01202] ou no contexto da verificação de token SOVD [SWS_DM_01470]. A classe possui semânticas estritas de posse: o construtor de cópia [SWS_DM_01139] e o operador de atribuição por cópia [SWS_DM_01140] estão excluídos (=delete). Operações de movimento (construtor de movimento [SWS_DM_01137] e operador de atribuição por movimento [SWS_DM_01138]) são predefinidas como padrão e declaradas como noexcept. O destrutor também é noexcept [SWS_DM_01136]. Todas as funções-membro, bem como o destrutor, não são seguras para threads (not thread-safe) [SWS_DM_01136], [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143], [SWS_DM_01144].

O status de autenticação é mapeado por meio do tipo enumerado DiagnosticAuthState [SWS_DM_01133]:

  • kDeAuthenticated (0x00): Nenhum cliente de diagnóstico está autenticado. Na inicialização do sistema, o cliente encontra-se por padrão nesse estado [SWS_DM_01205]. Nesse caso, são considerados papéis padrão aqueles papéis (DiagnosticAuthRole) cujo atributo isDefault esteja configurado como TRUE [SWS_DM_01204], [SWS_DM_01134]. Por meio de OverrideDefaultRoles, esses papéis padrão podem ser sobrescritos temporariamente por um timeout definido [SWS_DM_01141], [SWS_DM_01209].
  • kAuthenticated (0x01): Um cliente de diagnóstico está autenticado. Esse estado é alcançado por meio da chamada de Authenticate, ativando os papéis de usuário transmitidos no Diagnostic Server [SWS_DM_01142], [SWS_DM_01206].

Uma transição automática de estado de kAuthenticated de volta para kDeAuthenticated é disparada quando um cliente na sessão padrão não envia mais solicitações após a última confirmação de transmissão (TransmitConfirmation) e o tempo de inatividade expira [SWS_DM_01210], ou quando ocorre um timeout S3 [SWS_DM_01144], [SWS_DM_02077].

Diagrama de estados: ciclo de vida e transições de estado da autenticação do cliente. Fontes: [SWS_DM_01133], [SWS_DM_01204], [SWS_DM_01205], [SWS_DM_01206], [SWS_DM_01209], [SWS_DM_01210]

Caminho de utilização

O fluxo regular para gerenciar a autenticação do cliente compreende as seguintes etapas:

  1. Registrar notificador: A aplicação registra, com SetNotifier, uma função de retorno de chamada do tipo ClientAuthenticationSetNotifier (std::function<void(DiagnosticAuthState)>) [SWS_DM_01144], [SWS_DM_02077]. Com isso, ela é informada quando ocorrerem mudanças de status – por exemplo, a transição para kDeAuthenticated por inatividade ou um timeout S3 [SWS_DM_01144]. Uma nova chamada sobrescreve o notificador definido anteriormente [SWS_DM_01144].
  2. Consultar estado: Por meio do método GetState(), a aplicação pode consultar de forma síncrona o estado de autenticação atual do cliente [SWS_DM_01143].
  3. Reportar autenticação: Assim que a autenticação tiver sido concluída com sucesso, a aplicação chama Authenticate com os papéis de usuário a serem ativados (ara::core::Vector<DiagnosticAuthRole>) [SWS_DM_01142], [SWS_DM_01134]. O Diagnostic Server define o estado como kAuthenticated e retorna um ClientAuthenticationHandle [SWS_DM_01206].
  4. Gerenciar direitos de acesso: por meio do ClientAuthenticationHandle obtido, a aplicação pode configurar a lista de acesso dinâmico (DynamicAccessList) para o cliente [SWS_DM_01213], SWS Diagnostics, p. 132. Ao mesmo tempo, o uso desse handle atualiza a janela de tempo de inatividade do cliente SWS Diagnostics, p. 133.

Se o cliente estiver no estado kDeAuthenticated, a aplicação poderá, em vez disso, chamar OverrideDefaultRoles(defaultRoles, timeout) para ativar temporariamente funções padrão alternativas; em caso de sucesso, essa chamada também retorna um ClientAuthenticationHandle [SWS_DM_01141], [SWS_DM_01209].

Diagrama de sequência: fluxo de chamadas e notificações durante a autenticação. Fontes: [SWS_DM_01142], [SWS_DM_01144], [SWS_DM_01206], [SWS_DM_01210]

Cenários de erro

Os métodos Authenticate, OverrideDefaultRoles e GetState fornecem seus valores de retorno encapsulados em ara::core::Result e são especificados como seguros contra exceções (exception safe), bem como noexcept [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143]. Em caso de erro, é reportado o seguinte código de erro padronizado:

  • DiagErrc::kServiceNotAvailable: ocorre quando a chamada não pode ser executada porque funcionalidades essenciais do Diagnostic Manager não estão disponíveis no momento [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143]. Esse erro possui semântica de rollback (rollback_semantics), de modo que nenhuma alteração incompleta de estado permaneça [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143].

Para SetNotifier, não há códigos de erro padronizados definidos [SWS_DM_01144]. Como pré-condição essencial, OverrideDefaultRoles exige que o cliente esteja no estado kDeAuthenticated no momento da chamada [SWS_DM_01209].

Uso e chamada

A função ara::diag::ClientAuthentication::Authenticate é chamada por uma aplicação para comunicar à instância do Diagnostic Server a autenticação bem-sucedida de um cliente de diagnóstico [SWS_DM_01142]. Isso pode ocorrer após uma autenticação por meio das interfaces do Diagnostic Server ou por meio de mecanismos próprios da aplicação [SWS_DM_01142].

Como parâmetro de entrada, a função recebe userRoles (do tipo ara::core::Vector<DiagnosticAuthRole>). Em caso de chamada bem-sucedida, o status de autenticação da instância muda para kAuthenticated e as funções de usuário passadas são adotadas em definitivo [SWS_DM_01206]. Como valor de retorno, ela fornece um ara::core::Result<ClientAuthenticationHandle> [SWS_DM_01142]. Como um objeto Result é disponibilizado imediatamente, presume-se que o processamento ocorra de forma síncrona no contexto chamador.

Tratamento de erros e simultaneidade

O método está declarado como noexcept e é considerado seguro contra exceções (exception safe) [SWS_DM_01142]. Se ocorrer um erro devido à indisponibilidade de funcionalidades fundamentais do Diagnostic Manager no momento da chamada, a operação falha com semântica de rollback e retorna DiagErrc::kServiceNotAvailable no objeto Result [SWS_DM_01142].

Em relação à concorrência, o método está expressamente especificado como not thread-safe [SWS_DM_01142]. Chamadas paralelas no mesmo objeto ClientAuthentication são, portanto, inadmissíveis e devem ser sincronizadas pela aplicação.

Zusammenspiel e ciclo de vida

O ClientAuthenticationHandle obtido permite à aplicação definir ou estender uma DynamicAccessList para o cliente autenticado [SWS_DM_01142]. Além disso, a chamada inicia ou referencia o monitoramento de inatividade do cliente: se, após uma autenticação bem-sucedida no estado de sessão padrão, nenhuma outra solicitação UDS ocorrer pela duração de authenticationTimeout, a instância do Diagnostic Server redefine automaticamente o cliente de volta para kDeAuthenticated [SWS_DM_01210]. Para prevenir este timeout, a aplicação pode atualizar o temporizador por meio do método Refresh do handle [SWS_DM_01155].

  Procedência
  

                  

                  

                  
    Com o método síncrono OverrideDefaultRoles da classe ara::diag::ClientAuthentication, uma aplicação pode sobrepor temporariamente as funções de autenticação padrão (defaultRoles) de um cliente de diagnóstico [SWS_DM_01141]. Os serviços de diagnóstico liberados para as funções passadas ficam disponíveis para o testador pelo período de tempo definido no parâmetro timeout [SWS_DM_01141]. O pré-requisito para isso é que o cliente esteja no estado kDeAuthenticated [SWS_DM_01209]. Interpretação: se a chamada não ocorrer no estado kDeAuthenticated, presume-se que a sobreposição de funções seja rejeitada ou permaneça sem efeito, uma vez que a especificação prescreve o comportamento exclusivamente para este estado inicial.
