Contexto

A interface <ExtendedDataRecord-Namespace>::<ExtendedDataRecordElementInterface> destina-se, na AUTOSAR Adaptive Platform dentro do cluster funcional diag, à disponibilização de dados para os chamados Extended Data Records (AUTOSAR_AP_SWS_Diagnostics p. 68). Estes registos de dados são recolhidos em eventos de diagnóstico e persistidos permanentemente pelo Diagnostic Management (DM) numa memória não volátil ([SWS_DM_02156]).

A interface define o papel de provedor do lado da aplicação: uma aplicação adaptativa implementa o método puramente virtual Read para passar os valores solicitados ao Diagnostic Manager aquando de pedidos de diagnóstico correspondentes ([SWS_DM_02156]). Na interação participam pelo menos três componentes do sistema: a implementação de interface específica da aplicação, o Diagnostic Manager enquanto intermediário de pedidos de diagnóstico recebidos ([SWS_DM_02152]) e a memória não volátil na qual o DM persiste os dados consultados para o contexto de diagnóstico ([SWS_DM_02156]).

Diagrama de contexto: Parceiros de interação da interface de disponibilização de registos de dados. Fontes: [SWS_DM_02152], [SWS_DM_02156], AUTOSAR_AP_SWS_Diagnostics p. 68

Ciclo de vida

A instanciação ocorre através do construtor sob indicação de um ara::core::InstanceSpecifier e do modo de concorrência ara::diag::ConcurrencyType ([SWS_DM_02158]). O parâmetro concurrencyType determina se a implementação é operada como segura para threads (kConcurrent) ou não segura para threads (kNotConcurrent) ([SWS_DM_02158]). A classe possui uma vinculação estrita à sua identidade: o construtor de cópia e o operador de atribuição por cópia estão eliminados ([SWS_DM_02147], [SWS_DM_02148]). Do mesmo modo, o construtor de movimentação e o operador de atribuição por movimentação estão eliminados ([SWS_DM_02149], [SWS_DM_02150]). Uma instância fica assim vinculada à localização e não pode ser transferida.

Após a construção bem-sucedida, a instância permanece inicialmente no estado inativo (NotOffered). Através da chamada de Offer(), o reencaminhamento de pedidos é ativado pelo Diagnostic Management, fazendo com que a instância transite para o estado Offered ([SWS_DM_02152]). Uma nova chamada de Offer() no estado Offered resulta num erro ([SWS_DM_02152]). Através do método StopOffer(), o reencaminhamento é novamente desativado e o objeto regressa ao estado NotOffered ([SWS_DM_02153]).

A destruição ocorre através do destrutor virtual ([SWS_DM_02151]). Enquanto o construtor é declarado como seguro para threads ([SWS_DM_02158]), o destrutor é expressamente não seguro para threads ([SWS_DM_02151]). Interpretação: O encerramento da oferta do serviço via StopOffer() deverá impreterivelmente estar concluído antes da chamada do destrutor, a fim de evitar acessos de leitura paralelos durante a destruição do objeto.

Diagrama de estados: Ciclo de vida e estados de disponibilização da instância de interface. Fontes: [SWS_DM_02151], [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02158]

Caminho de utilização

O fluxo típico para a disponibilização e resposta a pedidos de diagnóstico processa-se da seguinte forma:

  1. Instanciação: A classe provedora derivada é criada mediante a passagem do ara::core::InstanceSpecifier, bem como do concurrencyType pretendido ([SWS_DM_02158]).
  2. Anunciar disponibilização: A aplicação chama Offer(). Apenas após o retorno bem-sucedido é que os pedidos de diagnóstico recebidos são reencaminhados pelo DM para a instância ([SWS_DM_02152]).
  3. Consultar registro de dados (Read): se o Diagnostic Management solicitar o elemento de dados, chama o método Read(metaInfo, cancellationHandler) ([SWS_DM_02156]):
    • A solicitação disponibiliza informações de contexto por meio de metaInfo ([SWS_DM_02156]).
    • Por meio de cancellationHandler.IsCanceled() ou do registro de uma função de notificação mediante cancellationHandler.SetNotifier(), a aplicação pode tratar um encerramento prematuro da conversação ([SWS_DM_02156]).
    • O método retorna um ara::core::Future com a estrutura ReadOutput ([SWS_DM_02154], [SWS_DM_02156]). Se os dados não estiverem disponíveis no momento da consulta, a implementação deve sempre retornar um valor e preencher os dados com um padrão de preenchimento (por exemplo, 0xFF) ([SWS_DM_02156]).
  4. Revogar oferta de serviço: antes do encerramento ou em estados de manutenção, a aplicação chama StopOffer() para interromper o encaminhamento de solicitações ([SWS_DM_02153]).

Diagrama de sequência: disponibilização, consulta e encerramento do serviço de diagnóstico. Fontes: [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02156]

Cenários de erro

As condições de erro e violações estão atribuídas às respectivas fases:

  • Violações durante a construção: vinculações de modelo inválidas levam a mensagens de erro definidas ([SWS_DM_02158]):
    • InstanceSpecifierMappingIntegrityViolation: o identificador não pode ser resolvido no contexto do executável ou não faz referência a um PortPrototype ([SWS_DM_02158]).
    • PortInterfaceMappingViolation: uma porta tipificada por DiagnosticExtendedDataRecordInterface não é referenciada por um DiagnosticDataPortMapping ([SWS_DM_02158]).
    • ProcessMappingViolation: não existe nenhum processo modelado correspondente para o processo de tempo de execução ([SWS_DM_02158]).
    • InstanceSpecifierAlreadyInUseViolation: o identificador já é utilizado por outra instância no processo ([SWS_DM_02158]).
  • Erro no registro de serviço: uma nova chamada de Offer() em uma instância já oferecida falha com o código de erro DiagOfferErrc::kAlreadyOffered ([SWS_DM_02152]).
  • Erro durante a consulta de dados: se a operação de leitura não puder ser realizada corretamente, o ara::core::Future retorna um código negativo de diagnóstico (DiagUdsNrcErrc) ou um código de erro específico da aplicação (ApApplicationError) ([SWS_DM_02156]). Se apenas os dados brutos estiverem ausentes, nenhum erro deve ser relatado; em vez disso, o registro de dados deve ser preenchido com o valor substituto (por exemplo, 0xFF) ([SWS_DM_02156]).

  <h4>Ciclo de vida</h4>
  <p>A instanciação ocorre através do construtor sob indicação de um <code>ara::core::InstanceSpecifier</code> e do modo de concorrência <code>ara::diag::ConcurrencyType</code> (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>). O parâmetro <code>concurrencyType</code> determina se a implementação é operada como segura para threads (<code>kConcurrent</code>) ou não segura para threads (<code>kNotConcurrent</code>) (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>). A classe possui uma vinculação estrita à sua identidade: o construtor de cópia e o operador de atribuição por cópia estão eliminados (<a class="spec-record-ref" data-req="SWS_DM_02147" href="../spec/record.html?id=SWS_DM_02147">[SWS_DM_02147]</a>, <a class="spec-record-ref" data-req="SWS_DM_02148" href="../spec/record.html?id=SWS_DM_02148">[SWS_DM_02148]</a>). Do mesmo modo, o construtor de movimentação e o operador de atribuição por movimentação estão eliminados (<a class="spec-record-ref" data-req="SWS_DM_02149" href="../spec/record.html?id=SWS_DM_02149">[SWS_DM_02149]</a>, <a class="spec-record-ref" data-req="SWS_DM_02150" href="../spec/record.html?id=SWS_DM_02150">[SWS_DM_02150]</a>). Uma instância fica assim vinculada à localização e não pode ser transferida.</p>
  <p>Após a construção bem-sucedida, a instância permanece inicialmente no estado inativo (<em>NotOffered</em>). Através da chamada de <code>Offer()</code>, o reencaminhamento de pedidos é ativado pelo Diagnostic Management, fazendo com que a instância transite para o estado <em>Offered</em> (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>). Uma nova chamada de <code>Offer()</code> no estado <em>Offered</em> resulta num erro (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>). Através do método <code>StopOffer()</code>, o reencaminhamento é novamente desativado e o objeto regressa ao estado <em>NotOffered</em> (<a class="spec-record-ref" data-req="SWS_DM_02153" href="../spec/record.html?id=SWS_DM_02153">[SWS_DM_02153]</a>).</p>
  <p>A destruição ocorre através do destrutor virtual (<a class="spec-record-ref" data-req="SWS_DM_02151" href="../spec/record.html?id=SWS_DM_02151">[SWS_DM_02151]</a>). Enquanto o construtor é declarado como seguro para threads (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>), o destrutor é expressamente não seguro para threads (<a class="spec-record-ref" data-req="SWS_DM_02151" href="../spec/record.html?id=SWS_DM_02151">[SWS_DM_02151]</a>). Interpretação: O encerramento da oferta do serviço via <code>StopOffer()</code> deverá impreterivelmente estar concluído antes da chamada do destrutor, a fim de evitar acessos de leitura paralelos durante a destruição do objeto.</p>

  <h4>Caminho de utilização</h4>
  <p>O fluxo típico para a disponibilização e resposta a pedidos de diagnóstico processa-se da seguinte forma:</p>
  <ol>
    <li><strong>Instanciação:</strong> A classe provedora derivada é criada mediante a passagem do <code>ara::core::InstanceSpecifier</code>, bem como do <code>concurrencyType</code> pretendido (<a class="spec-record-ref" data-req="SWS_DM_02158" href="../spec/record.html?id=SWS_DM_02158">[SWS_DM_02158]</a>).</li>
    <li><strong>Anunciar disponibilização:</strong> A aplicação chama <code>Offer()</code>. Apenas após o retorno bem-sucedido é que os pedidos de diagnóstico recebidos são reencaminhados pelo DM para a instância (<a class="spec-record-ref" data-req="SWS_DM_02152" href="../spec/record.html?id=SWS_DM_02152">[SWS_DM_02152]</a>).</li>
    <li><strong>Consultar registro de dados (Read):</strong> se o Diagnostic Management solicitar o elemento de dados, chama o método <code>Read(metaInfo, cancellationHandler)</code> (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>):
      <ul>
        <li>A solicitação disponibiliza informações de contexto por meio de <code>metaInfo</code> (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
        <li>Por meio de <code>cancellationHandler.IsCanceled()</code> ou do registro de uma função de notificação mediante <code>cancellationHandler.SetNotifier()</code>, a aplicação pode tratar um encerramento prematuro da conversação (<a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).</li>
        <li>O método retorna um <code>ara::core::Future</code> com a estrutura <code>ReadOutput</code> (<a class="spec-record-ref" data-req="SWS_DM_02154" href="../spec/record.html?id=SWS_DM_02154">[SWS_DM_02154]</a>, <a class="spec-record-ref" data-req="SWS_DM_02156" href="../spec/record.html?id=SWS_DM_02156">[SWS_DM_02156]</a>).       </ul>
    </li>
    <li><strong>Revogar oferta de serviço:</strong> antes do encerramento ou em estados de manutenção, a aplicação chama <code>StopOffer()</code> para interromper o encaminhamento de solicitações (<a class="spec-record-ref" data-req="SWS_DM_02153" href="../spec/record.html?id=SWS_DM_02153">[SWS_DM_02153]</a>).</li>
  </ol>
