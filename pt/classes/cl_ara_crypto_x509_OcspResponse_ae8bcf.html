Contexto

A classe ara::crypto::x509::OcspResponse representa, no módulo crypto da AUTOSAR Adaptive Platform, a interface central para a representação de uma resposta OCSP (Online Certificate Status Protocol). Dentro do subsistema X.509, essa abstração serve para a disponibilização padronizada de informações de status sobre certificados recebidos via protocolo de status de certificados online ou processados no sistema.

Na arquitetura do sistema, OcspResponse atua como um objeto de dados e de informações imutável entre instâncias de verificação criptográfica e componentes de aplicação. Entre os parceiros de interação primários estão componentes de segurança ou pilhas de comunicação que precisam validar cadeias de certificados e verificar o status de revogação atual (Revocation Status) dos certificados envolvidos. A interface assegura que os consumidores não precisem despender esforço próprio de análise sintática para estruturas OCSP codificadas em ASN.1 ou DER, podendo acessar, por meio de métodos de interface tipados, os dados úteis essenciais, como o status geral da resposta e certificados opcionalmente anexados.

Ciclo de vida

O ciclo de vida de ara::crypto::x509::OcspResponse é determinado de forma decisiva pelo alias de smart pointer tipado Sptrc. De acordo com [SWS_CRYPT_40802], Sptrc é definido como std::shared_ptr<const OcspResponse>. Essa definição estabelece vinculativamente que instâncias da interface, após sua disponibilização, sejam gerenciadas como objetos imutáveis (constantes) e referenciadas por meio de propriedade compartilhada (shared ownership).

Como OcspResponse é uma interface puramente virtual, a criação não ocorre diretamente pela aplicação, mas provavelmente por meio de métodos de fábrica internos ou funções de validação do provedor de Crypto ou de X.509. Assim que uma estrutura de resposta é analisada sintaticamente ou recebida de um serviço OCSP, ela é disponibilizada para a aplicação como Sptrc.

Em relação à concorrência, a interface destaca-se pela total segurança de threads: ambos os métodos de acesso GetResponseStatus() ([SWS_CRYPT_50130]) e GetCertificates() ([SWS_CRYPT_50131]) são declarados como const noexcept e explicitamente especificados como thread-safe. Como através do tipo de ponteiro Sptrc é possível apenas o acesso de leitura à instância constante, múltiplas threads podem consultar a mesma instância em paralelo sem mecanismos de sincronização externos. O objeto permanece em memória enquanto pelo menos uma referência std::shared_ptr estiver ativa; com a liberação da última referência, a instância é destruída automaticamente.

Caminho de utilização

O caminho típico de utilização de uma OcspResponse segue uma lógica de consulta estruturada. Um chamador que retém uma instância via OcspResponse::Sptrc ([SWS_CRYPT_40802]) verifica primeiramente o status fundamental da resposta OCSP antes que dados complementares sejam avaliados:

  1. Consulta de status: o chamador chama GetResponseStatus() ([SWS_CRYPT_50130]) para obter o status de processamento da resposta OCSP sob a forma de ara::core::Result<OcspResponseStatus>.
  2. Verificação de status: a aplicação verifica o resultado fornecido. Interpretação: uma avaliação dos certificados incorporados só deverá fazer sentido técnico e ser oportuna quando o status sinalizar uma resposta bem-sucedida.
  3. Consulta de certificados: caso a resposta inclua certificados adicionais (por exemplo, certificados do respondedor OCSP para verificação de sua assinatura), a aplicação chama GetCertificates() ([SWS_CRYPT_50131]). Como valor de retorno, é fornecido um ara::core::Result<ara::core::Vector<Certificate::Sptrc>>, que concede acesso aos objetos de certificado contidos.

Diagrama de sequência: consulta típica de status e certificados de uma resposta OCSP. Fontes: [SWS_CRYPT_50130], [SWS_CRYPT_50131].

Cenários de erro

Na interação com ara::crypto::x509::OcspResponse, o comportamento de falha é caracterizado por garantias rigorosas:

Tanto GetResponseStatus() ([SWS_CRYPT_50130]) quanto GetCertificates() ([SWS_CRYPT_50131]) possuem a classificação de especificação exception safe e são declarados com a palavra-chave noexcept. Portanto, os chamadores não precisam se proteger contra exceções síncronas de C++.

Ambos os métodos utilizam o tipo de transporte de erro ara::core::Result para o retorno. Na especificação do AUTOSAR R25-11, não estão definidos códigos de erro padronizados para nenhum dos dois métodos ([SWS_CRYPT_50130], [SWS_CRYPT_50131]). Mesmo assim, o modelo de programação da Adaptive Platform exige que os chamadores verifiquem o valor de retorno antes de acessar os dados (por exemplo, mediante .HasValue()). Caso uma implementação específica de fornecedor precise sinalizar estados de erro internos, estes serão transportados de forma controlada através de Result, sem que o fluxo de controle seja interrompido por exceções.

Este guia foi elaborado por uma IA com base na especificação AUTOSAR R25-11.

<p>Tanto <code>GetResponseStatus()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50130" href="../spec/record.html?id=SWS_CRYPT_50130">[SWS_CRYPT_50130]</a>) quanto <code>GetCertificates()</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50131" href="../spec/record.html?id=SWS_CRYPT_50131">[SWS_CRYPT_50131]</a>) possuem a classificação de especificação <code>exception safe</code> e são declarados com a palavra-chave <code>noexcept</code>. Portanto, os chamadores não precisam se proteger contra exceções síncronas de C++.</p>
<p>Ambos os métodos utilizam o tipo de transporte de erro <code>ara::core::Result</code> para o retorno. Na especificação do AUTOSAR R25-11, não estão definidos códigos de erro padronizados para nenhum dos dois métodos (<a class="spec-record-ref" data-req="SWS_CRYPT_50130" href="../spec/record.html?id=SWS_CRYPT_50130">[SWS_CRYPT_50130]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50131" href="../spec/record.html?id=SWS_CRYPT_50131">[SWS_CRYPT_50131]</a>). Mesmo assim, o modelo de programação da Adaptive Platform exige que os chamadores verifiquem o valor de retorno antes de acessar os dados (por exemplo, mediante <code>.HasValue()</code>). Caso uma implementação específica de fornecedor precise sinalizar estados de erro internos, estes serão transportados de forma controlada através de <code>Result</code>, sem que o fluxo de controle seja interrompido por exceções.</p>
