Contexto

A classe ara::tsync::ConsumerTimeBaseValidationNotification é uma interface de callback no cluster funcional tsync da AUTOSAR Adaptive Platform. A sua responsabilidade central consiste em notificar uma aplicação consumidora (Consumer Application) assim que um novo bloco de dados para a validação de uma determinada base de tempo (Time Base) tenha sido gravado e esteja disponível. Através desta interface, são disponibilizados valores de tempo e de medição detalhados para monitorizar a precisão e a consistência da base de tempo sincronizada ao nível da aplicação.

Na interação participam essencialmente duas funções: por um lado, a instância fornecedora da base de tempo dentro do subsistema tsync, que recolhe os respetivos dados de medição durante a operação em curso; por outro lado, a aplicação consumidora, que implementa a interface de notificação. A interface desacopla a disponibilização de estruturas de dados específicas: ela separa os dados de validação de um escravo de tempo ([SWS_TS_00420]) dos dados de medição relativos ao atraso de propagação de um iniciador de pDelay ([SWS_TS_00422]).

Ciclo de vida

Como a ConsumerTimeBaseValidationNotification define métodos puramente virtuais (= 0), a classe não pode ser instanciada diretamente. Uma aplicação consumidora tem de criar uma classe derivada própria que concretize as funções virtuais da interface. A criação e atribuição de uma instância concreta compete inteiramente à aplicação consumidora, a qual provavelmente também controla o tempo de vida do objeto e o entrega ao componente de base de tempo responsável.

Para uma destruição correta, a interface declara um destruidor virtual padrão ~ConsumerTimeBaseValidationNotification() noexcept = default ([SWS_TS_01300]). Isto permite a eliminação segura e polimórfica de objetos derivados através de ponteiros para o tipo base sem fugas de recursos. O destruidor está especificado como exception safe e garante, através da marcação com noexcept, que nenhuma exceção escape durante o desmantelamento no ciclo de vida do objeto.

Relativamente à concorrência, os métodos de callback da interface estão classificados como non_threadsafe ([SWS_TS_00420], [SWS_TS_00422]). Para o ciclo de vida, isto significa uma pré-condição estrita: o objeto implementador tem de permanecer ativo e válido durante todo o período em que possam ser acionadas notificações a partir do cluster tsync. Se um objeto for destruído ou modificado enquanto chegam chamadas através da interface, tal levará a comportamento indefinido devido à ausência de sincronização interna.

Caminho de utilização

O caminho de utilização típico abrange a receção dos blocos de dados gravados assim que o subsistema regista novas medições. Quando existe um novo bloco para a validação do escravo de tempo, o componente de base de tempo chama o método SetSlaveTimingData ([SWS_TS_00420]). O parâmetro measurementData do tipo const TimeSlaveMeasurementType& disponibiliza dados detalhados para a validação do escravo de tempo, os quais podem ser avaliados pela aplicação.

Por outro lado, se estiverem disponíveis dados de medição relativos ao atraso de propagação para o iniciador de pDelay da base de tempo, realiza-se a chamada de SetPdelayInitiatorData ([SWS_TS_00422]). Neste processo, são passados à aplicação, através do parâmetro measurementData do tipo const PdelayInitiatorMeasurementType&, dados detalhados de medição de tempo do iniciador. A execução de ambos os callbacks deverá ocorrer de forma síncrona no contexto de execução do componente fornecedor. Os dados são passados, em cada caso, como referência constante, o que permite uma disponibilização eficiente sem operações de cópia.

Cenários de erro

A interface implementa um design tolerante a falhas sem propagação de exceções: tanto SetSlaveTimingData ([SWS_TS_00420]) e SetPdelayInitiatorData ([SWS_TS_00422]) como o destruidor ([SWS_TS_01300]) estão especificados como exception safe e contêm a palavra-chave noexcept. Isto estabelece uma pós-condição estrita para a aplicação consumidora: uma implementação de substituição não pode, em circunstância alguma, propagar exceções para o exterior, uma vez que tal levaria à terminação imediata do processo via std::terminate.

Além disso, como os métodos apresentam o tipo de retorno void e não devolvem códigos de erro (como, por exemplo, através de ara::core::Result), erros de processamento específicos da aplicação não podem ser comunicados ao subsistema tsync através do retorno da função. Caso ocorra um erro na interpretação ou no processamento posterior das estruturas de dados recebidas, a aplicação consumidora terá de o tratar de forma autónoma e, se necessário, registá-lo internamente.

Um risco de erro essencial decorre da ausência de segurança de threads (non_threadsafe). Se múltiplos métodos de notificação forem chamados concorrentemente a partir de diferentes threads sem mecanismos de sincronização do lado da aplicação (tais como mutexes), ocorre uma condição de corrida de dados (Data Race) não permitida. O lado utilizador tem de assegurar autonomamente que o acesso a estados partilhados seja concebido de forma segura contra concorrência de threads.

Este guia baseia-se exclusivamente nos requisitos de especificação do release R25-11 da AUTOSAR.
