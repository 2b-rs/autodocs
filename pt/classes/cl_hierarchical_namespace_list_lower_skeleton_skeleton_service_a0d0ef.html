Serve como classe base para a implementação do lado do servidor e disponibilização de métodos de uma Service-Interface.

A classe serve como classe base do lado do servidor para a implementação de uma Service-Interface em ara::com, da qual a aplicação fornecedora do serviço deriva. Na criação, define-se através do construtor se as chamadas de métodos recebidas são processadas de forma orientada a eventos ou por polling [SWS_CM_00130]. Em métodos declarados como seguros contra exceções, fluxos com erro são sinalizados através do ara::core::Future retornado como código de erro [SWS_CM_00191].

Contexto

A classe {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{ <service-interface-name>}Skeleton serve na Adaptive Platform, no módulo com, como classe base abstrata gerada para a disponibilização do lado do servidor de uma Service-Interface. Um componente fornecedor de serviço específico da aplicação deriva desta classe skeleton para implementar a lógica de negócio funcional do serviço. A classe intermedeia entre a aplicação fornecedora de serviço concreta e o middleware de comunicação ou o binding de protocolo subjacente, tal como SOME/IP (SWS CommunicationManagement §8.1 «Method invocation»). Entre os parceiros de interação encontram-se a aplicação fornecedora de serviço, que cria e possui a instância, a própria classe skeleton, bem como a infraestrutura de comunicação, que recebe pedidos de serviço recebidos, os desserializa e os encaminha para o skeleton ([SWS_CM_10306], [SWS_CM_10307]).

Diagrama de contexto: interação entre a aplicação fornecedora de serviço, ServiceSkeleton e o middleware de comunicação. Fontes: [SWS_CM_10306], [SWS_CM_10307], SWS CommunicationManagement §8.1 «Method invocation».

Ciclo de vida

A criação da instância de skeleton é realizada através do construtor, ao qual é passado o modo de processamento pretendido ara::com::MethodCallProcessingMode [SWS_CM_00130]. Este modo define a estratégia de concorrência para chamadas de métodos recebidas: se kEvent ou kEventSingleThread for configurado, as chamadas de métodos recebidas são invocadas diretamente de forma orientada a eventos pelo middleware de comunicação [SWS_CM_10306]. Se, em vez disso, for passado kPoll, o processamento ocorre com base em polling pela aplicação [SWS_CM_10307]. Interpretação: é provável que a instância de skeleton permaneça na posse da aplicação fornecedora de serviço durante toda a disponibilização ativa do serviço e só seja destruída aquando da desativação do serviço.

Caminho de utilização

O fluxo típico compreende a implementação dos métodos puramente virtuais pela classe fornecedora derivada e a execução posterior aquando da chegada de pedidos. Para chamadas de métodos regulares (request-response), o skeleton define uma interface que retorna um ara::core::Future com o respetivo objeto de saída [SWS_CM_00191], [SWS_CM_99556]. Para métodos fire-and-forget sem resposta de retorno, o skeleton disponibiliza operações puramente virtuais com o tipo de retorno void [SWS_CM_90434]. Em caso de pedidos recebidos, o middleware de comunicação desserializa os dados úteis e encaminha a chamada para a implementação concreta da classe skeleton de acordo com o modo de processamento configurado ([SWS_CM_10306], [SWS_CM_00191]).

Diagrama de sequência: fluxo de uma chamada de método através do skeleton. Fontes: [SWS_CM_00191], [SWS_CM_10306], SWS CommunicationManagement §8.1 «Method invocation».

Cenários de erro

Tanto os métodos request-response como os métodos fire-and-forget estão anotados com noexcept ao nível da interface e declarados como seguros contra exceções ([SWS_CM_00191], [SWS_CM_90434]). Erros no processamento de chamadas de métodos regulares não são transmitidos através de exceções C++; em vez disso, o ara::core::Future retornado transporta, em caso de erro, um código de erro correspondente do tipo ara::com::ComErrc ou um ApApplicationError [SWS_CM_00191]. Para métodos fire-and-forget, não estão previstos, segundo a especificação, valores de retorno nem códigos de erro padronizados [SWS_CM_90434].

Provision of a fire-and-forget method (ClientServerOperation. fireAndForget ==TRUE)

GERADO POR IA não revisado Modelo: gemini-3.8-flash-medium · Effort: medium · Temperatura: nicht steuerbar · Prompt: 93c9c81c8712 Procedência

A função de API [SWS_CM_90434] define a interface puramente virtual de um método fire-and-forget no lado do servidor. Ela é parte integrante da classe de skeleton gerada {<hierarchical-namespace-list-lower-skeleton>}::skeleton::{<service-interface-name>}Skeleton e é disponibilizada por meio do arquivo de cabeçalho {<si-namespace-derived-directory-path-lower>}/{<si-shortname-lower>}_skeleton.h (AUTOSAR_AP_SWS_CommunicationManagement §8.4.5.2.4.1 «{<fnfmethod-name>}»). A função é gerada assim que o atributo ClientServerOperation.fireAndForget == TRUE estiver configurado no modelo de projeto para uma ClientServerOperation.

Para a implementação e o comportamento em tempo de execução, aplicam-se os seguintes aspectos essenciais:

  • Semântica de chamada e parâmetros: O método recebe parâmetros de entrada de modo análogo a métodos regulares conforme [SWS_CM_00191]. Por se tratar de uma comunicação puramente unidirecional, a assinatura possui o tipo de retorno void. Não são transmitidos parâmetros de saída nem valores de retorno ao cliente chamador.
  • Tratamento de erros e segurança contra exceções: A operação é declarada como noexcept=0 e, portanto, especificada como estritamente segura contra exceções (exception safe) ([SWS_CM_90434]). Não existem códigos de erro específicos da aplicação nem outros canais de feedback; a implementação do serviço não deve permitir que exceções C++ escapem do método.
  • Contexto de execução e concorrência: Caso o skeleton seja operado no modo ara::com::MethodCallProcessingMode == kPoll, o processamento de chamadas pendentes de [SWS_CM_90434] ocorre de forma determinística no contexto de thread da chamada de ProcessNextMethodCall() (AUTOSAR_AP_SWS_CommunicationManagement p. 410). Fora do modo de polling, presume-se que a execução ocorra concorrentemente em uma thread de trabalho interna do middleware de comunicação.

  Procedência
  

      

      

      
A função puramente virtual <Method> destina-se à disponibilização do lado do fornecedor de um método dentro de uma classe Skeleton para operações cliente-servidor sem semântica fire-and-forget [SWS_CM_00191]. Os programadores de aplicações implementam esta interface na classe skeleton derivada da interface de serviço para receber chamadas recebidas. Como parâmetros de entrada, são transmitidos todos os argumentos modelados cuja direção está definida como in ou inout [SWS_CM_00191].

      

      
A execução ocorre de forma assíncrona através do tipo de retorno ara::core::Future, o qual, em caso de sucesso, contém o objeto Output tipificado com os valores de resultado [SWS_CM_00191], [SWS_CM_99556]. O método está especificado como noexcept e seguro quanto a exceções; códigos de erro síncronos normalizados não estão estipulados [SWS_CM_00191]. Se ocorrer um erro durante o processamento, a implementação disponibiliza-o de forma assíncrona através do ara::core::Future, quer como código de erro do tipo ara::com::ComErrc quer como ApApplicationError específico do modelo [SWS_CM_00191].

      

      
O contexto de chamada e o comportamento de simultaneidade dependem do modo de processamento ara::com::MethodCallProcessingMode transmitido ao construtor de ServiceSkeleton aquando da instanciação [SWS_CM_00130]:

      

        

      • Se tiver sido configurado kEvent ou kEventSingleThread, o método é chamado de forma orientada a eventos pelo middleware assim que uma mensagem de pedido SOME/IP correspondente tiver sido recebida e desserializada [SWS_CM_10306].
        • 

      • No modo kPoll, por outro lado, a chamada ocorre de forma sincronizada na thread da aplicação de serviço quando esta executa explicitamente ProcessNextMethodCall() na instância do skeleton [SWS_CM_10307], [SWS_CM_00199].
