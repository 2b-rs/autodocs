Contexto

No módulo de diagnóstico da AUTOSAR Adaptive Platform (Release R25-11), a estrutura de dados <ExtendedDataRecord-Namespace>::<ExtendedDataRecordElementInterface>::<ExtendedDataRecordElement>ReadOutput assume o papel de um contêiner de dados padronizado. O objetivo dessa estrutura é agrupar todos os argumentos de saída gerados durante uma operação de leitura de um elemento Extended Data Record. Os Extended Data Records (EDR) servem, no ambiente de diagnóstico veicular, para fornecer informações estendidas de falha e de estado associadas a um evento de diagnóstico específico ou Diagnostic Trouble Code (DTC).

Participam primariamente da interação no fluxo de diagnóstico o software de aplicação diagnosticável, a interface <ExtendedDataRecordElementInterface> e o gerenciamento de diagnóstico de nível superior. Como as assinaturas de funções C++ para consultas assíncronas ou síncronas suportam apenas um único tipo de retorno, essa estrutura encapsula todos os valores de saída em uma unidade semântica. Presumivelmente, essa estrutura atua como um puro contêiner de transferência de dados (Value Object ou Plain Old Data), simplificando o retorno com segurança de tipos de elementos de dados para o subsistema de diagnóstico.

Ciclo de vida

O ciclo de vida da estrutura <ExtendedDataRecordElement>ReadOutput está vinculado ao fluxo da chamada de leitura associada e segue a semântica típica de valor do C++. A instanciação e o preenchimento devem ocorrer tipicamente no lado do servidor na aplicação de diagnóstico implementadora, assim que os dados de registro solicitados forem reunidos a partir da memória ou de registradores internos.

Após a atribuição das variáveis de membro contidas, a estrutura passa a ser de posse da camada chamadora, por exemplo, como o valor de resultado de um padrão de chamada assíncrono ou como um valor de retorno direto de método. Interpretação: devido à sua natureza de puro objeto de transferência, a estrutura presumivelmente não possui estado interno nem transições ativas de estado, sendo descartada pelo chamador após a avaliação dos dados de diagnóstico contidos.

Em relação à concorrência, deve-se notar que instâncias da estrutura normalmente não são modificadas de forma compartilhada entre limites de threads. Uma instância é criada no contexto de execução da operação de leitura e pode, em seguida, ser repassada de forma thread-safe, desde que nenhum outro acesso concorrente de escrita ocorra após a criação. O gerenciamento de memória e a destruição ocorrem automaticamente de acordo com as regras padrão para ciclos de vida de objetos automáticos ou dinâmicos em C++.

Caminho de utilização

O caminho de uso típico divide-se no fornecimento, na transmissão e na avaliação dos dados de saída de diagnóstico:

  1. Receber requisição: o sistema de diagnóstico inicia uma requisição de leitura para o elemento específico por meio da interface <ExtendedDataRecordElementInterface>.
  2. Obter dados e instanciar a estrutura: a lógica de aplicação lê os dados de estado atuais do sistema veicular e instancia um objeto do tipo <ExtendedDataRecordElement>ReadOutput.
  3. Preencher campos de saída: os valores medidos, leituras de contadores ou sinalizadores de estado obtidos são atribuídos aos respectivos campos de dados da estrutura.
  4. Retornar resultado: a estrutura preenchida é passada como valor de retorno para o gerenciamento de diagnóstico, que serializa os valores e os transmite ao testador de diagnóstico como resposta ao serviço de diagnóstico.
  5. Liberação: após a entrega e a serialização bem-sucedidas dos dados úteis, a instância é liberada ao final do escopo.
