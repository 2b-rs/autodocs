Disponibiliza interfaces e tipos para reportar eventos relevantes para a segurança de forma padronizada ao IdsM.

O namespace ara::idsm fornece interfaces e tipos padronizados através dos quais as aplicações adaptativas reportam eventos de segurança de forma estruturada ao Intrusion Detection System Management ([SWS_AIDSM_10205]). Através do EventReporter e dos respetivos providers de carimbos de data/hora, dados de contexto e modos de transmissão, os incidentes podem ser registados de forma detalhada ou filtrada ([SWS_AIDSM_10207]). No caso de identificadores de evento desconhecidos, a IdsmErrorDomain fornece códigos de erro específicos para tratamento posterior.

Contexto

O namespace ara::idsm disponibiliza a interface de programação da AUTOSAR Adaptive Platform para o Intrusion Detection System Management (IdsM). A sua tarefa central consiste em registar de forma padronizada eventos relevantes para a segurança (Security Events) a partir de processos de aplicação e instâncias da plataforma e encaminhá-los para o IdsM de nível superior.

A interface primária de interação para aplicações notificadoras é formada pela classe EventReporter. Este registo é acompanhado por interfaces funcionais especializadas: o ReportingModeProvider gere o modo de transmissão atual ([SWS_AIDSM_10207]), o ContextDataProvider fornece dados complementares dinâmicos ([SWS_AIDSM_10201], [SWS_AIDSM_10206]) e o TimestampProvider contribui com informações temporais ([SWS_AIDSM_10202]). Do lado do recetor, o QualifiedEventsReceiver processa eventos já qualificados. A interação destas funções vincula as aplicações adaptativas à monitorização orientada para a segurança.

Diagrama de contexto: interação entre componentes de aplicação, interfaces ara::idsm e IdsM. Fontes: [SWS_AIDSM_10205], [SWS_AIDSM_10207]

Caminho de utilização

Uma sequência típica para a sinalização de um evento de segurança subdivide-se na consulta do estado de notificação, na compilação de informações de contexto relevantes e no envio para o EventReporter.

Antes de disparar um evento, a aplicação consulta o modo de notificação ativo através do ReportingModeProvider ([SWS_AIDSM_10207]). A enumeração ReportingModeType distingue, entre outros, entre transmissão desativada (kOff), notificações compactas (kBrief), relatórios detalhados (kDetailed), bem como modos que contornam as regras de filtragem locais (kBriefBypassingFilters, kDetailedBypassingFilters). Se a notificação não estiver desativada, a aplicação prepara os dados úteis. Como identificador do evento serve um identificador do tipo EventIdType ([SWS_AIDSM_10205]). Para análises mais aprofundadas, o ContextDataProvider fornece dados de contexto mutáveis como um span de bytes ContextDataType ([SWS_AIDSM_10201]) ou como um par versionado VersionedContextDataType incluindo contador de versão ([SWS_AIDSM_10206]). Adicionalmente, podem ser integrados um contador do tipo CountType ([SWS_AIDSM_10203]) para eventos pré-qualificados e um carimbo de data/hora do tipo TimestampType ([SWS_AIDSM_10202]) através do TimestampProvider. Por fim, a aplicação passa os dados ao EventReporter.

Diagrama de sequência: ordem de chamada para verificação do estado de notificação e transmissão de um Security Event. Fontes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10207]

Cenários de erro

Operações com erro no interior do namespace ara::idsm são sinalizadas através do domínio de erro IdsmErrorDomain e do tipo de código de erro IdsmErrc ([SWS_AIDSM_10204]). Para o tratamento de erros em conformidade com as normas, existem as funções GetIdsmErrorDomain ([SWS_AIDSM_10702]) e MakeErrorCode ([SWS_AIDSM_10703]), com as quais é possível construir instâncias de ara::core::ErrorCode de forma thread-safe.

Um cenário de erro central ocorre quando é utilizado um ID de evento desconhecido. Neste caso, o sistema reporta o erro IdsmErrc::kUnknownEventId ([SWS_AIDSM_10204]). Isto acontece quando um chamador passa um identificador do tipo EventIdType que não é conhecido pelo IdsM ou que não está configurado no manifesto. Em interfaces síncronas com tratamento de exceções, este estado é mapeado pela classe IdsmException. A pré-condição para cada notificação bem-sucedida é, portanto, a correspondência dos valores de EventIdType transmitidos com a configuração do IdsM.

Este guia baseia-se exclusivamente nas especificações da Release R25-11 da AUTOSAR.

      Uso e finalidade
      

      A enumeração IdsmErrc representa os códigos de erro do domínio de erro do IdsM (cabeçalho ara/idsm/idsm_error_domain.h) e baseia-se no tipo básico ara::core::ErrorDomain::CodeType [SWS_AIDSM_10204]. Para um manuseio compacto em aplicações cliente, o AUTOSAR disponibiliza o alias de tipo idêntico Errc [SWS_AIDSM_10707]. Para a integração no modelo de tratamento de erros padronizado do AUTOSAR Adaptive, serve a função MakeErrorCode: ela converte um código de erro noexcept, juntamente com dados adicionais específicos do fabricante (SupportDataType), em um objeto ara::core::ErrorCode [SWS_AIDSM_10703].
      


      Códigos de erro e interação
      

      A especificação define o valor de erro concreto:
      

        

      • kUnknownEventId = 3: sinaliza que uma eventId passada não é conhecida pelo Intrusion Detection System Manager como um evento de segurança configurado [SWS_AIDSM_10204].
        • 

      

      Este código é transportado em interfaces síncronas como estado de erro dentro do tipo de retorno ara::core::Result. Tanto a consulta do modo de relatório via GetReportingMode [SWS_AIDSM_10602] quanto a sua atualização via SetReportingMode [SWS_AIDSM_10603] falham com IdsmErrc::kUnknownEventId caso um evento não configurado seja endereçado. Interpretação: devido à atribuição explícita do valor 3, presume-se que os valores 1 e 2 estejam reservados para estados de erro do domínio utilizados interna ou futuramente. Pergunta Q-374e315b0ea6d0c7 (aberta)
      


      Simultaneidade e restrições
      

      A função auxiliar MakeErrorCode para a criação de objetos de erro é segura para threads (thread-safe) e indicada como constexpr [SWS_AIDSM_10703]. Em contrapartida, as funções operacionais do reporting_mode_provider.h que retornam esses estados de erro (GetReportingMode [SWS_AIDSM_10602] e SetReportingMode [SWS_AIDSM_10603]) estão declaradas explicitamente como não seguras para threads (not thread-safe). Chamadas paralelas devem, portanto, ser sincronizadas pelo chamador.
