Contexto

O namespace ara::idsm disponibiliza a interface para o Intrusion Detection System Management (IdsM) dentro da AUTOSAR Adaptive Platform. O IdsM destina-se à detecção, registro e encaminhamento de incidentes relevantes para a segurança (Security Events) em toda a rede veicular. Aplicações Adaptive, pilhas de comunicação e serviços de plataforma atuam como sensores de segurança descentralizados, reportando atividades suspeitas ou violações de regras registradas ao subsistema central do IdsM.

Dentro do namespace, a classe EventReporter assume o papel central na transmissão de eventos de segurança ao IdsM. Para enriquecer as notificações de eventos com metadados relevantes, o repórter colabora com outros componentes especializados:

  • ContextDataProvider fornece dados de contexto mutáveis e específicos do sensor, que são transmitidos ao IdsM como uma sequência de dados brutos via [SWS_AIDSM_10201] ContextDataType (alias de tipo para ara::core::Span<const std::uint8_t>) ou de forma versionada como [SWS_AIDSM_10206] VersionedContextDataType.
  • TimestampProvider fornece carimbos de data/hora de alta precisão ou específicos do sensor por meio do tipo [SWS_AIDSM_10202] TimestampType (inteiro de 64 bits), a fim de permitir a correlação temporal de incidentes.
  • ReportingModeProvider controla o comportamento de notificação dos sensores com base na enumeração [SWS_AIDSM_10207] ReportingModeType.
  • QualifiedEventsReceiver permite que módulos de análise ou reação de nível superior recebam eventos de segurança qualificados pelo IdsM para processamento posterior.
  • IdsmErrorDomain e IdsmException definem a semântica de erros do namespace.

Diagrama de contexto: interação entre aplicações de sensores, as classes de interface do namespace ara::idsm e o subsistema IdsM. Fontes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10207].

Caminho de utilização

Um fluxo típico de monitoramento compreende a consulta do modo de operação ativo, a preparação dos dados do evento e a subsequente notificação ao IdsM:

  1. Consultar modo de notificação: Antes de uma aplicação realizar análises de contexto computacionalmente intensivas ou transmitir eventos, ela lê o modo de notificação atual por meio de ReportingModeProvider. De acordo com [SWS_AIDSM_10207], estão disponíveis cinco modos da enumeração ReportingModeType:
    • ReportingModeType::kOff: A notificação de eventos está totalmente desativada.
    • ReportingModeType::kBrief: Notificação de eventos reduzida sem dados detalhados de contexto.
    • ReportingModeType::kDetailed: Notificação detalhada, incluindo todos os dados de contexto disponíveis.
    • ReportingModeType::kBriefBypassingFilters: Notificação reduzida contornando os mecanismos de filtragem locais.
    • ReportingModeType::kDetailedBypassingFilters: Notificação completa contornando os mecanismos de filtragem locais.
    Interpretação: A distinção detalhada dos modos de notificação deverá permitir ao sistema global ajustar dinamicamente o volume de transmissão à carga atual do barramento e à situação de ameaça.
  2. Preparar dados do evento: O evento concreto é identificado por meio de um número inteiro de 16 bits do tipo [SWS_AIDSM_10205] EventIdType. Caso múltiplos eventos semelhantes tenham sido pré-qualificados, a quantidade pode ser informada por meio de [SWS_AIDSM_10203] CountType. Adicionalmente, carimbos de data/hora podem ser determinados via TimestampProvider ([SWS_AIDSM_10202]) e dados úteis via ContextDataProvider ([SWS_AIDSM_10201] ou [SWS_AIDSM_10206]).
  3. Notificar evento: A aplicação transfere os dados para EventReporter. Interpretação: A transferência para o subsistema IdsM deverá ocorrer de forma assíncrona, a fim de não bloquear os caminhos de execução de aplicações de sensores críticas em termos de tempo.
  4. Receber eventos qualificados: Módulos registrados recebem eventos qualificados por meio de QualifiedEventsReceiver para iniciar reações de segurança em todo o veículo.

Diagrama de sequência: sequência de chamadas para verificação do modo de notificação, preparação dos dados de contexto e transmissão de um evento de segurança. Fontes: [SWS_AIDSM_10201], [SWS_AIDSM_10205], [SWS_AIDSM_10206], [SWS_AIDSM_10207].

Cenários de erro

O tratamento de erros no namespace ara::idsm segue o padrão AUTOSAR Adaptive por meio de domínios de erro e tipos de resultado:

  • Domínio de erro e funções de fábrica: A função [SWS_AIDSM_10702] GetIdsmErrorDomain() retorna uma referência à ara::core::ErrorDomain estática do domínio IdsmErrorDomain. Ela é especificada como constexpr, noexcept e thread-safe. Os códigos de erro são gerados por meio de [SWS_AIDSM_10703] MakeErrorCode(), informando um valor de IdsmErrc e dados de suporte opcionais (ara::core::ErrorDomain::SupportDataType).
  • Códigos de erro específicos: De acordo com [SWS_AIDSM_10204], a enumeração IdsmErrc define o código kUnknownEventId = 3. Esse erro ocorre quando um evento é notificado com uma EventIdType que não é conhecida pelo IdsM ou não está configurada no manifesto.
  • Tratamento de exceções: Caso APIs do módulo lancem exceções, é utilizado o erro tipado IdsmException, que encapsula o ara::core::ErrorCode correspondente.
