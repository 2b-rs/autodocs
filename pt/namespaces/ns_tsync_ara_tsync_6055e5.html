Disponibiliza interfaces padronizadas para bases de tempo sincronizadas, carimbos de data/hora de alta precisão e monitorização de estado.

O namespace ara::tsync disponibiliza interfaces para o acesso sincronizado ao tempo na Adaptive Platform, ligando aplicações a bases de tempo configuradas através de SynchronizedTimeBaseConsumer. O registo do tempo é efetuado através de carimbos de data/hora de alta precisão do tipo Timestamp com base numa resolução de nanossegundos [SWS_TS_01251]. As aplicações monitorizam a sincronia através de indicadores de estado como SynchronizationStatus [SWS_TS_01050]. Como condição limite essencial, os callbacks de notificação assíncronos não são concebidos para serem thread-safe e as perdas de ligação ao daemon de tempo têm de ser tratadas.

Contexto

O namespace ara::tsync disponibiliza as interfaces para sincronização de tempo de alta precisão no âmbito da AUTOSAR Adaptive Platform. Permite às aplicações ler pontos no tempo sincronizados, monitorizar o estado de sincronização e registar valores de medição para fins de validação. O papel central para aplicações consumidoras é assumido pela classe SynchronizedTimeBaseConsumer, que encapsula o acesso a uma base de tempo configurada através de um InstanceSpecifier. No lado do fornecedor, SynchronizedTimeBaseProvider serve como ponto de acesso para a disponibilização e o controlo de bases de tempo.

A base da representação temporal é o pseudo-relógio TimeBase, através do qual o alias de tipo Timestamp é definido como std::chrono::time_point<TimeBase, std::chrono::nanoseconds> [SWS_TS_01251]. O trabalho de sincronização propriamente dito e a ligação a protocolos de barramento como IEEE 802.1AS ou PTP ocorrem tipicamente através de um serviço de segundo plano. Interpretação: este daemon de tempo comunica entre processos com as instâncias de ara::tsync, o que pode ser comprovado pelo erro específico TsyncErrc::kDaemonConnectionLost [SWS_TS_00901]. Pergunta Q-dd9d1a36f7573a03 (aberta) A arquitetura é complementada por interfaces como ConsumerTimeBaseValidationNotification e ProviderTimeBaseValidationNotification, bem como estruturas de dados para medições de tempo de execução e precisão (por exemplo, TimeMasterMeasurementType, TimeSlaveMeasurementType, PdelayInitiatorMeasurementType e PdelayResponderMeasurementType).

Diagrama de contexto: interação entre aplicações, classes de interface e daemon de tempo no namespace ara::tsync. Fontes: [SWS_TS_00901], [SWS_TS_01251].

Ciclo de vida

O ciclo de vida de uma base de tempo sincronizada é determinado por estruturas de estado e transições de estado discretas. Um instantâneo do estado temporal, incluindo todos os metadados, é representado por SynchronizedTimeBaseStatus. O estado de comunicação e sincronização é controlado através da enumeração SynchronizationStatus [SWS_TS_01050]:

  • kNotSynchronizedUntilStartup: estado inicial antes da primeira sincronização bem-sucedida após o arranque do sistema.
  • kSynchronized: a base de tempo está síncrona com o Time-Master.
  • kSynchToGateway: a sincronização ocorre através de um gateway.
  • kTimeOut: dentro de uma janela temporal definida, não foi possível estabelecer nem manter a sincronização.

Além do estado de comunicação, a enumeração LeapJump [SWS_TS_01051] regista correções bruscas da base de tempo: kTimeLeapNone sinaliza uma execução contínua sem ultrapassagem de limiar, enquanto kTimeLeapFuture e kTimeLeapPast indicam correções significativas para o futuro ou passado, respetivamente.

No que diz respeito à concorrência, deve notar-se que tipos de callback como SynchronizationNotifier [SWS_TS_14222], SynchronizedTimeBaseNotifier [SWS_TS_14221] e TimePrecisionNotifier [SWS_TS_14223] estão classificados na especificação como não sendo thread-safe. As transições de estado, especialmente a ocorrência de timeouts ou ressincronizações, exigem, portanto, uma sincronização do lado da aplicação.

Diagrama de estados: ciclo de vida e estados de comunicação de uma base de tempo sincronizada. Fontes: [SWS_TS_01050].

Caminho de utilização

O fluxo típico para a utilização de uma base de tempo sincronizada por uma aplicação consumidora subdivide-se nos seguintes passos:

  1. Inicialização e vinculação: a aplicação instancia SynchronizedTimeBaseConsumer para a base de tempo pretendida, indicando o InstanceSpecifier correspondente.
  2. Registo de notificações: para monitorizar o estado de sincronização, a aplicação passa funções de callback. Estas incluem SynchronizationNotifier [SWS_TS_14222] para alterações do SynchronizationStatus, SynchronizedTimeBaseNotifier [SWS_TS_14221] para instantâneos de estado detalhados (SynchronizedTimeBaseStatus) e TimePrecisionNotifier [SWS_TS_14223] para dados de medição de precisão (TimePrecisionMeasurement).
  3. Consulta do carimbo de data/hora: na presença do estado kSynchronized ou kSynchToGateway [SWS_TS_01050], a aplicação lê valores temporais de alta precisão do tipo Timestamp [SWS_TS_01251].
  4. Reação a saltos de estado e de tempo: se as notificações sinalizarem um LeapJump diferente de kTimeLeapNone [SWS_TS_01051] ou uma transição para kTimeOut [SWS_TS_01050], a aplicação ajusta temporizadores internos ou passa para um modo de degradação.
  5. Transmissão de dados do utilizador: se forem transmitidos dados úteis específicos do utilizador no âmbito da sincronização de tempo, é utilizada a estrutura UserData.

Cenários de erro

O tratamento de erros do namespace segue o modelo padrão da AUTOSAR através do domínio de erro TsyncErrorDomain. O acesso a este domínio global é realizado através de GetTsyncErrorDomain() [SWS_TS_00909]. As causas dos erros são descritas pelo tipo de enumeração TsyncErrc [SWS_TS_00901]:

  • kDaemonConnectionLost: a operação solicitada falha porque a ligação ao daemon de sincronização de tempo está interrompida.
  • kLimitsExceeded: um valor transmitido ou calculado encontra-se fora do intervalo de valores permitido.
  • kFunctionNotSupported: a função solicitada não é suportada na configuração atual ou no ambiente da plataforma.
  • kInvalidUserDataSize: o comprimento dos dados do utilizador transmitidos excede o máximo de atualmente 3 bytes definido por UserData::kMaxUserDataSize.

Instâncias de ara::core::ErrorCode são criadas através da função auxiliar MakeErrorCode [SWS_TS_00910]. A função está declarada como noexcept e é thread-safe. Para arquiteturas baseadas em exceções, o namespace disponibiliza a classe de exceção TsyncException.

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 para o módulo tsync.

      A enumeração SynchronizationStatus expressa o status de comunicação e sincronização de uma base de tempo no namespace ara::tsync [SWS_TS_01050]. O tipo baseia-se em std::uint32_t e é fornecido por meio do arquivo de cabeçalho ara/tsync/synchronized_time_base_status.h bem como pelo cabeçalho de encaminhamento ara/tsync/tsync_fwd.h [SWS_TS_01050]. A enumeração define quatro estados:
      

        

      • kNotSynchronizedUntilStartup (= 0): A base de tempo não está sincronizada antes da inicialização do sistema (estado inicial) [SWS_TS_01050].
        • 

      • kTimeOut (= 0x1): A base de tempo não foi sincronizada dentro de uma janela de tempo predefinida [SWS_TS_01050].
        • 

      • kSynchronized (= 0x2): A base de tempo está síncrona com o Time-Master [SWS_TS_01050].
        • 

      • kSynchToGateway (= 0x3): A base de tempo está síncrona com o gateway [SWS_TS_01050].
        • 

      

      A consulta síncrona do status ocorre por meio do método GetSynchronizationStatus() da classe ara::tsync::SynchronizedTimeBaseStatus, o qual fornece o estado no momento da criação do objeto de status de forma thread-safe e segura contra exceções (noexcept) [SWS_TS_01053]. Para notificações em mudanças de status, existe em ara/tsync/synchronized_time_base_consumer.h o alias de tipo SynchronizationNotifier (std::function<void(const SynchronizationStatus &)>), que é especificado explicitamente como não thread-safe [SWS_TS_14222].
      

      Em caso de erro ou de ausência de sincronização, deve-se observar o comportamento dos métodos associados: se a base de tempo nunca tiver sido sincronizada e apresentar o status kNotSynchronizedUntilStartup, o método GetCreationTime() retornará um ara::core::Optional vazio, pois não há um momento de criação válido em tempo sincronizado [SWS_TS_01055].

          A enumeração TsyncErrc define os códigos de erro padronizados do cluster funcional Time Synchronization [SWS_TS_00901]. Ela é baseada em ara::core::ErrorDomain::CodeType e é declarada dentro do namespace ara::tsync; além disso, um alias está disponível por meio de ara::tsync::TsyncErrorDomain::Errc [SWS_TS_01266]. A função thread-safe MakeErrorCode serve para criar objetos de erro completos, vinculando um valor de TsyncErrc a dados adicionais específicos do fabricante para formar um ara::core::ErrorCode [SWS_TS_00910].
          

  
          A especificação define quatro valores concretos de erro [SWS_TS_00901]:
          
  
            
    
          • kDaemonConnectionLost (=1): A ação não pode ser executada porque a conexão com o daemon de Time-Sync foi interrompida.
            • 
    
          • kLimitsExceeded (=2): Um parâmetro passado excede a faixa de valores permitida. Isso ocorre, por exemplo, em SetRateCorrection quando a correção de taxa solicitada for inválida [SWS_TS_01110].
            • 
    
          • kFunctionNotSupported (=3): A função solicitada não é suportada. Interpretação: isto deve afetar implementações nas quais funções opcionais de hardware ou de interface não estejam disponíveis. Pergunta Q-e22067d84fd6adb4 (aberta)
            •
