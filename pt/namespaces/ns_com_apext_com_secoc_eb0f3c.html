Define interfaces para gestão de valores de frescura e tratamento de erros para canais de comunicação protegidos.

O namespace define a interface específica do fabricante para a gestão de valores de frescura no âmbito do Secure Onboard Communication (SecOC) para o AUTOSAR Adaptive Platform Communication Management (SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h»). O tempo de vida e a inicialização do Freshness Value Manager são totalmente controlados pela gestão de comunicação, que consulta valores de frescura na interface durante operações de envio configuradas ([SWS_CM_11272]). Em caso de indisponibilidade temporária de valores de frescura, ocorrem novas tentativas controladas até um valor limite definido, antes de as mensagens com erro serem descartadas. Complementarmente, o namespace disponibiliza um domínio de erros próprio e códigos de erro padronizados para tratamentos de diagnóstico e exceção.

Contexto

O namespace apext::com::secoc define interfaces normativas para extensões de plataforma (Platform Extension Interfaces) dentro do cluster funcional Communication Management (ara::com) da AUTOSAR Adaptive Platform (SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h»). O objetivo destas interfaces de extensão é permitir que OEMs e fabricantes de stacks forneçam um Freshness Value Manager (FVM) personalizado, o qual gera, gere e verifica os valores de frescura necessários para a defesa contra ataques de repetição para o Secure Onboard Communication (SecOC).

O namespace interage essencialmente com três papéis: a gestão de comunicação (ara::com), a definição padronizada de interface (FVM) juntamente com portadores de dados como FVContainer ([SWS_CM_11286], [SWS_CM_11344]), bem como a implementação concreta do FVM do fabricante do veículo ou fornecedor do stack. Interpretation: Parte-se do princípio de que a biblioteca FVM específica do fabricante é associada como biblioteca estática ou dinâmica no âmbito da integração do sistema, uma vez que a especificação define a interface funcional, mas deixa o formato de integração em aberto em função do stack. Diagrama de contexto: Integração do namespace apext::com::secoc entre o Communication Management e a implementação do FVM específica do fabricante. Fontes: [SWS_CM_11272], SWS Communication Management §C.1 «Header: apext/com/secoc/fvm.h».

Ciclo de vida

A gestão do ciclo de vida de uma realização de FVM é totalmente controlada pela gestão de comunicação ara::com ([SWS_CM_11272]). Aplicações e instâncias de serviço não criam nem gerem diretamente o componente FVM.

A colocação em funcionamento ocorre deterministicamente durante a inicialização do stack de comunicação através da chamada da API de biblioteca apext::com::secoc::FVM::Initialize ([SWS_CM_11273]). Se a inicialização não puder ser devidamente concluída pelo lado do fabricante, a camada FVM sinaliza este estado de erro através do código de erro definido kFVInitializeFailed ([SWS_CM_11342]). Após a chamada de inicialização bem-sucedida, o Freshness Value Manager permanece no estado de operação ativo e responde a pedidos síncronos de valores de frescura de envio e receção.

Caminho de utilização

O caminho de utilização regular divide-se na proteção de envio e na verificação de receção de mensagens:

  • Mensagens de envio: Se uma mensagem estiver configurada para o envio SecOC, é tratada como mensagem autêntica ([SWS_CM_11274]). A proteção ocorre numa ordem fixa após a conclusão de todos os cálculos de proteção E2E ([SWS_CM_11274]). Se a configuração da interface de serviço possuir um atributo freshnessValueId, a gestão de comunicação chama apext::com::secoc::FVM::GetTxFreshness ([SWS_CM_11274], [SWS_CM_11275]). O valor de frescura é disponibilizado numa estrutura FVContainer, que mantém o comprimento de bits no atributo length e o próprio valor ([SWS_CM_11286], [SWS_CM_11344]).
  • Mecanismo de repetição de envio: Para cada mensagem protegida, o sistema mantém um Authentication Build Counter ([SWS_CM_11275]). Após uma geração bem-sucedida, o contador é reposto a 0. Se GetTxFreshness fornecer o erro recuperável kFVNotAvailable ou se o cálculo do autenticador falhar, o contador é incrementado e a montagem é repetida ([SWS_CM_11275]). Se o contador atingir o valor limite SecOCAuthenticationBuildAttempts, a mensagem é descartada ([SWS_CM_11275]).
  • Mensagens de receção: No caso de mensagens SecOC recebidas com verificação ativa (atributo securedRxVerification verdadeiro ou não definido), o autenticador é extraído e a mensagem é verificada antes das verificações E2E através do recálculo do MAC ([SWS_CM_11276], SWS Communication Management §8.1 «SecOC secure channel reception»). Se, pelo contrário, securedRxVerification estiver definido como falso, a verificação é ignorada (Bypass) e a mensagem é processada sem verificação ([SWS_CM_11372]).

Diagrama de sequência: Fluxo de chamadas e repetições na proteção de uma mensagem de envio por meio do FVM. Fontes: [SWS_CM_11274], [SWS_CM_11275].

Cenários de erro

Situações de erro dentro da interface FVM são tratadas através do domínio de erros com segurança de tipos ComSecOcFvmErrorDomain, cuja instância pode ser obtida através de GetComSecOcFvmErrorDomain ([SWS_CM_12521]). Os códigos de erro estão definidos no tipo de enumeração ComSecOcFvmErrc ([SWS_CM_11342]):

  • kFVNotAvailable (Código 1): O valor de frescura necessário está temporariamente indisponível. Isto sinaliza ao Communication Management um erro recuperável que desencadeia tentativas de repetição de acordo com o protocolo de envio ([SWS_CM_11275], [SWS_CM_11342]).
  • kFVInitializeFailed (Código 2): A inicialização do Freshness Value Manager falhou ([SWS_CM_11342]).

Através da função auxiliar MakeErrorCode ([SWS_CM_12522]), é possível encapsular códigos de erro juntamente com dados adicionais específicos do fabricante (SupportDataType) em objetos ara::core::ErrorCode regulares. Para chamadas síncronas que falharam em ambientes baseados em exceções, está disponível a classe de exceção ComSecOcFvmException.

Este guia baseia-se na especificação AUTOSAR Adaptive Platform R25-11 (Communication Management). Todas as afirmações apoiam-se exclusivamente nas referências de especificação e de documentação indicadas.

A função está definida no espaço de nomes apext::com::secoc e deve ser incluída através do ficheiro de cabeçalho apext/com/secoc/fvm_error_domain.h (AUTOSAR_AP_SWS_CommunicationManagement §C.2.2.1.1 «GetComSecOcFvmErrorDomain»).       A função é declarada como noexcept e especificada como totalmente segura contra exceções (exception safe) [SWS_CM_12521]. Durante a chamada não ocorrem erros de tempo de execução e não são lançadas exceções nem gerados códigos de erro. O domínio de erros retornado serve antes como referência para os programadores confrontarem univocamente códigos de erro específicos do FVM no âmbito do tratamento de erros do SecOC.
