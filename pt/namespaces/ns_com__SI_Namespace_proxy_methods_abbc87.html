Contexto

O namespace <SI-Namespace>::proxy::methods disponibiliza, dentro do módulo com da AUTOSAR Adaptive Platform, os representantes de interface do lado do cliente para chamadas de método. Na arquitetura orientada a serviços da AUTOSAR Adaptive, as relações de comunicação são definidas por meio de interfaces de serviço (ServiceInterface). Se tal interface contiver operações do tipo ClientServerOperation, o gerador de interfaces cria uma classe de método especializada no namespace do proxy para cada uma dessas operações.

A arquitetura faz uma distinção fundamental entre duas variantes de métodos, controladas pelo atributo de metamodelo fireAndForget:

  • Classe <Method>: Esta classe é gerada para cada ClientServerOperation na qual ClientServerOperation.fireAndForget == FALSE esteja configurado. Ela representa chamadas síncronas ou assíncronas do tipo solicitação-resposta (request-response), nas quais o cliente espera uma resposta ou um resultado do servidor.
  • Classe <FnFMethod>: Esta classe é gerada para operações nas quais ClientServerOperation.fireAndForget == TRUE se aplica. Ela implementa um padrão puro de mensagem unidirecional (fire-and-forget), no qual a chamada é enviada sem que uma resposta ou um valor de retorno do lado do servidor seja transmitido ao cliente.

Na hierarquia global de <SI-Namespace>::proxy, essas classes encapsulam a serialização dos parâmetros de entrada, o encaminhamento para a infraestrutura de comunicação subjacente e, no caso de métodos regulares, o recebimento dos dados de resposta.

Ciclo de vida

O tempo de vida das classes no namespace <SI-Namespace>::proxy::methods está estreitamente acoplado à instância superior do proxy da respectiva interface de serviço. Interpretação: É provável que instâncias de <Method> e <FnFMethod> sejam instanciadas como membros da classe de proxy de serviço gerada, partilhando, portanto, integralmente o seu ciclo de vida.

Ao instanciar o proxy de serviço (após descoberta de serviço bem-sucedida e vinculação a uma instância de serviço concreta), os objetos de método incorporados são inicializados. Eles recebem o contexto de acesso ao binding de comunicação subjacente. Enquanto o proxy de serviço permanecer válido, as instâncias de método estarão disponíveis para a aplicação cliente. Se o proxy de serviço for destruído, os objetos de método associados também expiram. Chamadas assíncronas em andamento ou respostas ainda pendentes devem ser processadas ou invalidadas antes ou durante a chamada do destrutor do proxy.

Em relação à concorrência, as chamadas de método são projetadas de modo que múltiplas threads do software de aplicação possam chamar o mesmo método do proxy, desde que a implementação do middleware garanta a segurança de threads (thread-safety) para o envio. Uma vez que os objetos de método tipicamente não armazenam um contexto de chamada com estado entre chamadas consecutivas, eles atuam essencialmente como interfaces funcionais sem estado para o transporte de mensagens.

Caminho de utilização

O fluxo típico ao utilizar as classes de <SI-Namespace>::proxy::methods divide-se nas seguintes fases:

  1. Disponibilização do proxy: A aplicação cliente encontra a instância de serviço pretendida por meio da descoberta de serviço do módulo com e instancia o proxy tipado.
  2. Acesso ao método: A aplicação acessa o membro de método específico do proxy. Interpretação: A chamada de um objeto de método provavelmente ocorre por meio de um operador de chamada de função sobrecarregado (operator()) do respectivo objeto.
  3. Execução de métodos regulares (<Method>): Numa operação regular, a aplicação passa os parâmetros de entrada declarados. O objeto de método encaminha a solicitação através do middleware para o servidor e retorna à aplicação chamadora um objeto que encapsula o resultado assíncrono. Em seguida, a aplicação pode bloquear sincronicamente até que o resultado esteja disponível ou registrar uma notificação assíncrona.
  4. Execução de métodos fire-and-forget (<FnFMethod>): Numa operação unidirecional, a aplicação também passa os parâmetros de entrada para o objeto de método. Este inicia a transmissão e retorna imediatamente para a aplicação, sem fornecer um objeto de retorno ou de estado para um resultado.

Cenários de erro

Ao chamar classes de <SI-Namespace>::proxy::methods, devem ser considerados diferentes níveis de erro, os quais diferem dependendo da semântica da chamada:

  • Erros de comunicação e de binding: O pré-requisito para cada chamada de método é um canal de transporte funcional para a instância de serviço. Se a conexão de rede for interrompida ou se a instância de serviço não estiver mais acessível, as chamadas falham. Em classes <Method> regulares, um erro correspondente é transportado por meio do objeto de resultado.
  • Erros de aplicação: Se o servidor não puder processar com sucesso um <Method> regular, um erro de aplicação definido na interface de serviço é transmitido de volta ao cliente.
  • Comportamento de erro em fire-and-forget: Interpretação: Em <FnFMethod>, é provável que erros de processamento do lado do servidor não sejam reportados ao chamador, visto que o padrão fire-and-forget semanticamente não prevê uma mensagem de resposta. Para a aplicação, isso significa que exceções ou erros de cálculo do lado do servidor passam despercebidos, a menos que um canal de retorno separado (como um evento) seja utilizado para isso. Erros locais ao aceitar parâmetros ou no envio, por outro lado, podem ser sinalizados diretamente no contexto chamador.
