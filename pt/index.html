A Plataforma Adaptativa em uma frase

O AUTOSAR Adaptive Platform é um ambiente de tempo de execução orientado a serviços para computadores de veículos potentes: aplicações adaptativos são executados como processos POSIX independentes, são iniciados e monitorados dinamicamente e se comunicam por meio de serviços definidos contratualmente em vez de sinais conectados estaticamente (EXP PlatformDesign §3.3 «Adaptive Platform – Characteristics», §8.2 «Service Oriented Communication»).

ARA — a interface de programação desta referência

Todos os namespaces ara::* documentados aqui juntos formam a interface ARA (AUTOSAR Runtime for Adaptive Applications). Cada Functional Cluster da plataforma exporta sua API C++ em seu próprio namespace - desde os tipos básicos em ara::core até a comunicação de serviço em ara::com até serviços de plataforma como ara::exec, ara::per ou ara::crypto (EXP PlatformDesign §4.1 «Logical view», EXP SWArchitecture §9.1 «Building Block View – Overview»).

Cluster funcional da Plataforma Adaptativa e interações típicas de uma aplicação Adaptativa (nós clicáveis). Fontes: EXP PlatformDesign §4.1, EXP SWArchitecture §9.1. Interpretação parcial: seleção e rotulagem das interações resumem os capítulos das fontes mencionadas.

Conceitos abrangentes

  • Machine & Software Cluster: Uma Machine é o ambiente de execução (possivelmente virtualizado); o software é empacotado como Software Cluster instaláveis e atualizado através de ara::ucm (EXP SWArchitecture §13.4 «Software Cluster», §13.5 «Machine»).
  • Function Groups & Estados: Os processos são atribuídos a grupos de funções; ara::sm instrui o Execution Management a iniciar/parar processos (EXP SWArchitecture §13.2 «Function Group», EXP PlatformDesign cap. 7 «State Management») por meio de estados de grupo de funções.
  • Manifestos: Execução, instância de serviço e manifesto de máquina configuram implantação, iniciam comportamento e vinculação de serviço declarativamente (EXP PlatformDesign §4.4 «Manifest», EXP SWArchitecture §13.6 «Manifest»).
  • Tratamento de erros sem exceções: Em toda a plataforma, os erros são retornados como ara::core::Result/ErrorCode (EXP PlatformDesign §18.1 «Error Handling», EXP SWArchitecture §13.12 «Error Handling»).
  • Safety & Security como dimensão transversal: a proteção E2E, Health Monitoring (ara::phm), a pilha criptográfica, Identity & Access Management, Intrusion Detection (ara::idsm) e a firewall (ara::fw) protegem a plataforma e a comunicação (EXP PlatformDesign cap. 17 «Safety», EXP SWArchitecture §13.13 «Trusted Platform»).

Interligações entre os módulos

Molduras arredondadas = módulos; Nós = subáreas de um módulo (namespaces ou grupos de funções). Seta A → B: localizações API da subárea A (assinaturas, campos, parâmetros) tipos de referência da subárea B — determinados a partir das declarações vinculadas desta referência; a largura da linha corresponde ao número de pontos de referência (número exato conforme dica de ferramenta na seta). Rótulo da aresta = tipo de interação com o alvo: valores de retorno, resultados assíncronos, tratamento de erros, tipos de dados, endereçamento de instâncias, funções auxiliares; “usa” indica outras referências de tipos. Setas cinza claro: modelagem de serviço através de ara::com. Todos os nós estão vinculados às suas respectivas páginas de namespace/classe.

Visibilidade da API para aplicaçãos

Nem todos os elementos de especificação aqui documentados fazem parte da API ARA pública: os documentos SWS indicam no respetivo capítulo 5 («Dependencies to other Functional Clusters», em cada caso tabela 5.1) quais as interfaces disponibilizadas exclusivamente a outros Functional Clusters. Esta referência torna-o visível de forma consistente pela cor de fundo do nome do módulo, namespace e classe correspondente — na página de cada elemento (cabeçalho da página e indicação à direita na barra de navegação), em todas as referências ao elemento nas páginas de nível superior, bem como nos nós ligados dos diagramas. Por predefinição, os fundos são muito claros para garantir boa legibilidade e tornam-se algo mais intensos ao passar o rato:

  • APPLICATION Blau: pode ser usado diretamente por Aplicaçãos Adaptativos - por exemplo, Por exemplo ara::core, ara::com, ara::log, ara::per, ara::crypto, ara::diag, ara::rds, ara::shwa (executa como uma biblioteca no processo de aplicação, SWS SHWA cap. 1), ara::tsync (uso de base de tempo ativa e passiva, SWS TSync §2.2) e ara::idsm (aplicações como sensores de segurança, SWS IdsM §7.2). ara::exec::ExecutionClient também pertence aqui, mas só pode relatar o status do seu próprio processo [SWS_EM_01401].
  • PRIVILEGED Vermelho: apenas para aplicações dedicadas autorizadas via IAM ou mapeamento de manifesto; o utilizador autorizado está entre colchetes na linha de navegação. Exemplos: o PackageManagement-Service de ara::ucm («Cliente UCM» = por exemplo, cliente OTA ou aplicação de diagnóstico, SWS UCM §7.1), o StateMachine-Services de ara::sm para um aplicação de controle SM [SWS_SM_00600], a API Suspend-to-RAM ara::sm::s2r (satélites autenticados por IAM apenas com SuspendToRamSatelliteMapping, [SWS_SM_00715]) e ara::fw (mudança de estado apenas com AdaptiveFirewallToPortPrototypeMapping, [AP_SWS_Fw_40013]).
  • INTERNAL Cinzento-escuro: interfaces puramente internas ao cluster, certamente não destinadas a aplicações; o Functional Cluster utilizador consta entre parênteses na barra de navegação. Exemplos: ara::exec::StateClient juntamente com FunctionGroup/FunctionGroupState (apenas para State Management, SWS EM Tab. 5.1), todo o módulo ara::nm (a Service Interface para aplicações foi removida, os requisitos de rede passam por State Management, SWS NM §4.1 e Tab. 5.1), ara::phm::RecoveryAction (SWS PHM Tab. 5.1), bem como todas as interfaces apext::* dos anexos normativos «Platform Extension Interfaces» (integração da plataforma em direção ao software de base: Watchdog, Power, transporte UDS, Freshness-Value-Manager, Trace/ARTI).
