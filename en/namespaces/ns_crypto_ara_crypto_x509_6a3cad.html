Context

Within module crypto of the AUTOSAR Adaptive Platform, the namespace ara::crypto::x509 provides interfaces and data types for managing public key infrastructures (PKI) according to the X.509 standard. Core responsibilities include representing X.509 certificates (Certificate), certificate signing requests (CertSignRequest), distinguished names (X509DN), and configuring and performing certificate path validation via CertificateValidationCtx and CertificateValidationResult. Status responses of the Online Certificate Status Protocol are represented via OcspResponse. The X509Provider serves as the entry point and overarching interface.

Context diagram: Core interfaces and their interaction in the namespace ara::crypto::x509. Sources: [SWS_CRYPT_50107], [SWS_CRYPT_40203], [SWS_CRYPT_40001].

Usage Path

A typical use case consists of verifying incoming certificates in the context of secure communication relationships or during signature and integrity verification of code artifacts. A Certificate defines usage constraints via standard key usages (X509KeyUsage [SWS_CRYPT_40101]) and extended usages (X509ExtendedKeyUsage [SWS_CRYPT_50097]).

Bitmasks are available for standard purposes:

  • kConstrDigitalSignature [SWS_CRYPT_40151] for digital signatures,
  • kConstrNonRepudiation [SWS_CRYPT_40152] for non-repudiation services,
  • kConstrKeyEncipherment [SWS_CRYPT_40153] and kConstrDataEncipherment [SWS_CRYPT_40154] for key or data encryption, respectively,
  • kConstrKeyAgreement [SWS_CRYPT_40155] for key agreements,
  • kConstrKeyCertSign [SWS_CRYPT_40156] and kConstrCrlSign [SWS_CRYPT_40157] for signing certificates or certificate revocation lists (CRLs),
  • kConstrEncipherOnly [SWS_CRYPT_40158] and kConstrDecipherOnly [SWS_CRYPT_40159] for pure encryption or decryption operations.

Extended usages are specified by corresponding flags, including kServerAuth [SWS_CRYPT_50098] and kClientAuth [SWS_CRYPT_50099] for TLS authentications, kCodeSigning [SWS_CRYPT_50100] for executable code, kEmailProtection [SWS_CRYPT_50101] for email protection, kTimeStamping [SWS_CRYPT_50102] for timestamps, and kOCSPSigning [SWS_CRYPT_50103] for OCSP responses.

Interpretation: A validation context (CertificateValidationCtx) is likely typically obtained via the X509Provider. The validation is parameterized in advance by bit flags of type CertificateValidationOptions [SWS_CRYPT_50107]:

  • Validity periods can be excluded from verification via kIgnoreNotBefore [SWS_CRYPT_50108] or kIgnoreNotAfter [SWS_CRYPT_50109].
  • Unknown critical extensions can be generally tolerated via kIgnoreUnknownCriticalExtensions [SWS_CRYPT_50110].
  • Revocation checks are controlled via kIgnoreCrl [SWS_CRYPT_50111] for CRLs or via OCSP flags: by default, OCSP is inactive (kOcspOff [SWS_CRYPT_50114]), but can be applied to the entire certificate chain (kOcspResponseCompleteChain [SWS_CRYPT_50112]) or exclusively to the target certificate (kOcspResponseTargetOnly [SWS_CRYPT_50113]).

After execution of the path validation, the context returns a CertificateValidationResult from which the overall result is read.

Sequence diagram: Typical sequence of certificate validation via the validation context. Sources: [SWS_CRYPT_50107], [SWS_CRYPT_40203].

Error Scenarios

The evaluation of the validation result takes place via the enumeration CertificateValidationStatus [SWS_CRYPT_40203]. Possible error states and status values include:

  • kValid: The certificate path validation was successful.
  • kInvalidSignature: A signature within the certificate chain could not be verified.
  • kNoPathToTrustedCertificate: A continuous path to a trusted root certificate could not be established.
  • kExpired or kFuture: The certificate is expired (notAfter) or not yet valid at the current time (notBefore).
  • kRevoked: The certificate was revoked via an imported CRL or an OCSP response.
  • kUnknownOcspStatus: The certificate status is unknown according to the OCSP response.
  • kUnknownCriticalExtension: A certificate contains an unknown critical extension that was approved neither via the flag kIgnoreUnknownCriticalExtensions nor via the function IgnoreCriticalExtension().

If OCSP is used, the interface OcspResponse returns the status via OcspResponseStatus [SWS_CRYPT_40001]. Here, kSuccessful signals a valid confirmation, whereas error scenarios such as impermissible requests (kMalformedRequest), internal issuer errors (kInternalError), temporary overload (kTryLater), mandatory request signatures (kSigRequired), or missing authorization (kUnauthorized) must be handled in a differentiated manner.

<h4>Context</h4>
<p>Within module <code>crypto</code> of the AUTOSAR Adaptive Platform, the namespace <code>ara::crypto::x509</code> provides interfaces and data types for managing public key infrastructures (PKI) according to the X.509 standard. Core responsibilities include representing X.509 certificates (<code>Certificate</code>), certificate signing requests (<code>CertSignRequest</code>), distinguished names (<code>X509DN</code>), and configuring and performing certificate path validation via <code>CertificateValidationCtx</code> and <code>CertificateValidationResult</code>. Status responses of the Online Certificate Status Protocol are represented via <code>OcspResponse</code>. The <code>X509Provider</code> serves as the entry point and overarching interface.</p>

<h4>Usage Path</h4>
<p>A typical use case consists of verifying incoming certificates in the context of secure communication relationships or during signature and integrity verification of code artifacts. A <code>Certificate</code> defines usage constraints via standard key usages (<code>X509KeyUsage</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40101" href="../spec/record.html?id=SWS_CRYPT_40101">[SWS_CRYPT_40101]</a>) and extended usages (<code>X509ExtendedKeyUsage</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50097" href="../spec/record.html?id=SWS_CRYPT_50097">[SWS_CRYPT_50097]</a>).</p>
<p>Bitmasks are available for standard purposes:</p>
<ul>
<li><code>kConstrDigitalSignature</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40151" href="../spec/record.html?id=SWS_CRYPT_40151">[SWS_CRYPT_40151]</a> for digital signatures,</li>
<li><code>kConstrNonRepudiation</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40152" href="../spec/record.html?id=SWS_CRYPT_40152">[SWS_CRYPT_40152]</a> for non-repudiation services,</li>
<li><code>kConstrKeyEncipherment</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40153" href="../spec/record.html?id=SWS_CRYPT_40153">[SWS_CRYPT_40153]</a> and <code>kConstrDataEncipherment</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40154" href="../spec/record.html?id=SWS_CRYPT_40154">[SWS_CRYPT_40154]</a> for key or data encryption, respectively,</li>
<li><code>kConstrKeyAgreement</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40155" href="../spec/record.html?id=SWS_CRYPT_40155">[SWS_CRYPT_40155]</a> for key agreements,</li>
<li><code>kConstrKeyCertSign</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40156" href="../spec/record.html?id=SWS_CRYPT_40156">[SWS_CRYPT_40156]</a> and <code>kConstrCrlSign</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40157" href="../spec/record.html?id=SWS_CRYPT_40157">[SWS_CRYPT_40157]</a> for signing certificates or certificate revocation lists (CRLs),</li>
<li><code>kConstrEncipherOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40158" href="../spec/record.html?id=SWS_CRYPT_40158">[SWS_CRYPT_40158]</a> and <code>kConstrDecipherOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40159" href="../spec/record.html?id=SWS_CRYPT_40159">[SWS_CRYPT_40159]</a> for pure encryption or decryption operations.</li>
</ul>
<p>Extended usages are specified by corresponding flags, including <code>kServerAuth</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50098" href="../spec/record.html?id=SWS_CRYPT_50098">[SWS_CRYPT_50098]</a> and <code>kClientAuth</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50099" href="../spec/record.html?id=SWS_CRYPT_50099">[SWS_CRYPT_50099]</a> for TLS authentications, <code>kCodeSigning</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50100" href="../spec/record.html?id=SWS_CRYPT_50100">[SWS_CRYPT_50100]</a> for executable code, <code>kEmailProtection</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50101" href="../spec/record.html?id=SWS_CRYPT_50101">[SWS_CRYPT_50101]</a> for email protection, <code>kTimeStamping</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50102" href="../spec/record.html?id=SWS_CRYPT_50102">[SWS_CRYPT_50102]</a> for timestamps, and <code>kOCSPSigning</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50103" href="../spec/record.html?id=SWS_CRYPT_50103">[SWS_CRYPT_50103]</a> for OCSP responses.</p>
<p>Interpretation: A validation context (<code>CertificateValidationCtx</code>) is likely typically obtained via the <code>X509Provider</code>. The validation is parameterized in advance by bit flags of type <code>CertificateValidationOptions</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50107" href="../spec/record.html?id=SWS_CRYPT_50107">[SWS_CRYPT_50107]</a>:</p>
<ul>
<li>Validity periods can be excluded from verification via <code>kIgnoreNotBefore</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50108" href="../spec/record.html?id=SWS_CRYPT_50108">[SWS_CRYPT_50108]</a> or <code>kIgnoreNotAfter</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50109" href="../spec/record.html?id=SWS_CRYPT_50109">[SWS_CRYPT_50109]</a>.</li>
<li>Unknown critical extensions can be generally tolerated via <code>kIgnoreUnknownCriticalExtensions</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50110" href="../spec/record.html?id=SWS_CRYPT_50110">[SWS_CRYPT_50110]</a>.</li>
<li>Revocation checks are controlled via <code>kIgnoreCrl</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50111" href="../spec/record.html?id=SWS_CRYPT_50111">[SWS_CRYPT_50111]</a> for CRLs or via OCSP flags: by default, OCSP is inactive (<code>kOcspOff</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50114" href="../spec/record.html?id=SWS_CRYPT_50114">[SWS_CRYPT_50114]</a>), but can be applied to the entire certificate chain (<code>kOcspResponseCompleteChain</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50112" href="../spec/record.html?id=SWS_CRYPT_50112">[SWS_CRYPT_50112]</a>) or exclusively to the target certificate (<code>kOcspResponseTargetOnly</code> <a class="spec-record-ref" data-req="SWS_CRYPT_50113" href="../spec/record.html?id=SWS_CRYPT_50113">[SWS_CRYPT_50113]</a>).</li>
</ul>
<p>After execution of the path validation, the context returns a <code>CertificateValidationResult</code> from which the overall result is read.</p>

<h4>Error Scenarios</h4>
<p>The evaluation of the validation result takes place via the enumeration <code>CertificateValidationStatus</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40203" href="../spec/record.html?id=SWS_CRYPT_40203">[SWS_CRYPT_40203]</a>. Possible error states and status values include:</p>
<ul>
<li><code>kValid</code>: The certificate path validation was successful.</li>
<li><code>kInvalidSignature</code>: A signature within the certificate chain could not be verified.</li>
<li><code>kNoPathToTrustedCertificate</code>: A continuous path to a trusted root certificate could not be established.</li>
<li><code>kExpired</code> or <code>kFuture</code>: The certificate is expired (<code>notAfter</code>) or not yet valid at the current time (<code>notBefore</code>).</li>
<li><code>kRevoked</code>: The certificate was revoked via an imported CRL or an OCSP response.</li>
<li><code>kUnknownOcspStatus</code>: The certificate status is unknown according to the OCSP response.</li>
<li><code>kUnknownCriticalExtension</code>: A certificate contains an unknown critical extension that was approved neither via the flag <code>kIgnoreUnknownCriticalExtensions</code> nor via the function <code>IgnoreCriticalExtension()</code>.</li>
</ul>
<p>If OCSP is used, the interface <code>OcspResponse</code> returns the status via <code>OcspResponseStatus</code> <a class="spec-record-ref" data-req="SWS_CRYPT_40001" href="../spec/record.html?id=SWS_CRYPT_40001">[SWS_CRYPT_40001]</a>. Here, <code>kSuccessful</code> signals a valid confirmation, whereas error scenarios such as impermissible requests (<code>kMalformedRequest</code>), internal issuer errors (<code>kInternalError</code>), temporary overload (<code>kTryLater</code>), mandatory request signatures (<code>kSigRequired</code>), or missing authorization (<code>kUnauthorized</code>) must be handled in a differentiated manner.</p>
