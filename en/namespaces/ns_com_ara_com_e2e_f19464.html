Provides types, verification statuses, and error domains for end-to-end protection of adaptive communication.

The namespace ara::com::e2e defines types, states, and error codes for the end-to-end protection of adaptive communication. Consuming applications evaluate received data samples based on ProfileCheckStatus as well as SMState and may only use data if the state is kValid ([SWS_CM_90422]). On the provider side, errors such as deadline violations or packet loss can be monitored via TransportFaultConditionHandler ([SWS_CM_00091]). Erroneous states are mapped in a standardized way via the error domain ComE2EErrorDomain.

Context

The namespace ara::com::e2e provides data types, status enumerations, and error handling structures for End-to-End protection (E2E) in the communication module of AUTOSAR Adaptive. Its primary task is to capture transmission and data integrity errors at the application and transport layers in a transparent and standardized manner.

Within the communication architecture, the namespace interacts with several key components:

  • Service Provider (Skeleton): On the provider side, error conditions of the transmission can be monitored via function pointers. The type TransportFaultConditionHandler ([SWS_CM_00092]) allows registering and unregistering corresponding monitoring callbacks for all methods of a skeleton (AUTOSAR_AP_EXP_SWArchitecture p. 68) as well as for getter and setter calls of individual skeleton fields (AUTOSAR_AP_EXP_SWArchitecture p. 69).
  • Consumers and Event Data (SamplePtr): On the consumer side, received data samples undergo an E2E check. The check result of an individual sample is mapped via ProfileCheckStatus ([SWS_CM_90421]), while the overall state of the monitoring is captured via SMState ([SWS_CM_90422]).
  • Error Handling: The error domain ComE2EErrorDomain (AUTOSAR_AP_EXP_ARAComAPI p. 9) and the associated error codes ComE2EErrc ([SWS_CM_10474]) seamlessly integrate E2E errors into the error architecture model of ara::core. The class ComE2EException exists for exception handling.

Context diagram: Interaction between service provider (Skeleton), sample management (SamplePtr), and the error domain ara::com::e2e. Sources: AUTOSAR_AP_EXP_SWArchitecture p. 68, [SWS_CM_90421], [SWS_CM_10474].

Lifecycle and State Monitoring

E2E monitoring has a state-based lifecycle phase that is coupled with the reception of data samples via an event. The state is represented by the enumeration SMState ([SWS_CM_90422]):

  • kInit: After initialization, not enough data samples with a successful E2E check are available yet; samples must not be used.
  • kValid: Communication of data samples is functioning properly according to the E2E check; samples may be consumed.
  • kInvalid: Too few error-free or too many erroneous samples were received within the E2E time window; samples must not be used.
  • kNoData: No data has been received from the publisher yet.
  • kStateMDisabled: The E2E state machine is administratively disabled.
  • kIncompatibleQoS: Configured Quality of Service (QoS) policies of both communication endpoints do not match.

In parallel, ProfileCheckStatus provides the cycle status of the individual data sample ([SWS_CM_90421]): In addition to the success state kOk, the check distinguishes counter repetitions (kRepeated), illegal counter jumps (kWrongSequence), and data check errors (kError such as CRC, length, or Data ID errors). If the check is disabled, kCheckDisabled is returned.

As a fundamental precondition for data processing: A received data sample may only be used by the application if SMState == kValid applies and the check of the data sample (GetProfileCheckStatus) did not result in an error (kError) ([SWS_CM_90422]).

Usage Path

A typical usage path spans checking received event data on the consumer side and configuring transport error notifications on the provider side:

  1. Status query of the data sample: After receiving a data sample via ara::com::SamplePtr, the consuming application calls GetProfileCheckStatus() to determine the specific check result of the sample ([SWS_CM_90421]).
  2. State check of the monitoring: The application calls GetSMState() to query the aggregated state of the E2E state machine ([SWS_CM_90422]).
  3. Processing or error handling: If SMState == kValid is present and no error was reported, payload processing takes place ([SWS_CM_90422]). Otherwise, the E2E error is handled via standardized error structures or forwarded by means of MakeErrorCode ([SWS_CM_12511]).
  4. Transport error handling on the skeleton: Service providers register a TransportFaultConditionHandler to monitor their methods and field operations ([SWS_CM_00092], AUTOSAR_AP_EXP_SWArchitecture p. 68, AUTOSAR_AP_EXP_SWArchitecture p. 69). If a transport-related error occurs, the callback is invoked with the respective TransportFaultCondition ([SWS_CM_00091]).

Sequence diagram: Call sequence for validating received data samples and handling errors. Sources: [SWS_CM_90421], [SWS_CM_90422], [SWS_CM_12511].

Error Scenarios

In case of an error, the namespace provides two separate mechanisms that map different error sources:

Transport errors are signaled via the enumeration TransportFaultCondition ([SWS_CM_00091]):

  • kSampleRejected: A data sample was dropped at layer 4 or above due to resource exhaustion at the endpoint.
  • kDeadlineMissed: A data sample exceeded its configured deadline interval.
  • kSampleLost: Loss of data samples was detected (for example, a gap in sequence numbers).

Protocol and check errors of the E2E transformation are classified via ComE2EErrc ([SWS_CM_10474]). These error codes include counter repetitions (kRepeated), counter jumps beyond the allowed delta (kWrongSequence), CRC/length errors (kError), missing new data (kNoNewData), and remote service errors (kUnspecifiedE2EError). The function MakeErrorCode serves to construct instances of type ara::core::ErrorCode ([SWS_CM_12511]), while GetComE2EErrorDomain returns a reference to the singleton instance of ComE2EErrorDomain ([SWS_CM_12510]). Interpretation: The class ComE2EException is likely used primarily when errors are mapped in execution paths with C++ exceptions enabled.

The enumeration ComE2EErrc defines the specific error codes for end-to-end protection (E2E) in namespace ara::com::e2e based on ara::core::ErrorDomain::CodeType [SWS_CM_10474]. Within the error domain ara::com::e2e::ComE2EErrorDomain, the type is provided via the type alias Errc [SWS_CM_12504].

The enumerator values describe determined check results and error states [SWS_CM_10474]:

  • kRepeated: Data exhibits a repeated counter value [SWS_CM_10474].
  • kWrongSequence: Checks were successful, but a counter jump exceeded the permissible delta [SWS_CM_10474].
  • kError: A counter-independent error has occurred (e.g., incorrect CRC, incorrect length, or invalid Data-ID) or the return of the check function was not OK [SWS_CM_10474].
  • kNoNewData: No new data is available [SWS_CM_10474].
  • kUnspecifiedE2EError: A remote service returned an unspecified E2E error [SWS_CM_10474].

During server-side request processing, ComE2EErrc is passed as argument errorCode to the skeleton's method E2EErrorHandler if the E2E check of the message fails [SWS_CM_10470], AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.3.3 “E2E error notification”. If no new request message is available, the handler is mandatorily called with ComE2EErrc::kNoNewData as well as dataID = 0 and messageCounter = 0 [SWS_CM_00047]. Following the execution of the error handler, E2E protection of the response message is performed [SWS_CM_90481].

Regarding concurrency and constraints: The method E2EErrorHandler is not specified as reentrant and not exception safe [SWS_CM_10470]. Its registration takes place purely statically prior to runtime; dynamic registration or deregistration is not provided AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.3.3 “E2E error notification”. Furthermore, in the event of CRC errors, the server application must not rely on the passed Data-ID, as it may be corrupted [SWS_CM_10470].

      Usage and Call Context
      

      The enumeration ProfileCheckStatus in namespace ara::com::e2e represents the result of the end-to-end check (E2E) for a single received sample [SWS_CM_90421]. Upon reception of an E2E-protected sample, the communication management executes the routine E2E_check within GetNewSamples(), which returns the ProfileCheckStatus [SWS_CM_90411]. This status is stored directly in the associated ara::com::SamplePtr [SWS_CM_90413]. Receivers access the check status synchronously and exception-safely via the method GetProfileCheckStatus() of class ara::com::SamplePtr [SWS_CM_00042], [SWS_CM_90420].
      

      Status Values and Error Handling
      

      std::uint8_t serves as the underlying type [SWS_CM_90421]. The enumeration defines the following states for individual error analysis:
      

        

      • kOk: All checks of the sample in the current cycle, including the counter check, were successful [SWS_CM_90421].
        • 

      • kRepeated: The received sample exhibits a repeated counter value [SWS_CM_90421].
        • 

      • kWrongSequence: The check was successful, but an impermissible counter jump above the allowed delta is present [SWS_CM_90421].
        • 

      • kError: A non-counter-related error has occurred, for example an incorrect CRC, an incorrect length, or an erroneous Data ID [SWS_CM_90421].
        • 

      • kCheckDisabled: Indicates that no E2E check is active when EndToEndTransformationComSpecProps.disableEndToEndCheck was configured to TRUE [SWS_CM_90421].
        • 

      

      Interaction and Boundary Conditions
      

      While ProfileCheckStatus reflects the isolated check result of an individual sample [SWS_CM_90421], the event class manages the higher-level state machine ara::com::e2e::SMState [SWS_CM_90413] in parallel, which can be retrieved via GetE2EStateMachineState() [SWS_CM_10475]. The definition is located in the header file ara/com/e2e/profile_check_status.h [SWS_CM_90421].
