Provides standardized interfaces for synchronized time bases, high-precision timestamps, and status monitoring.

The namespace ara::tsync provides interfaces for synchronized time access on the Adaptive Platform by connecting applications to configured time bases via SynchronizedTimeBaseConsumer. Time acquisition is performed using high-precision timestamps of type Timestamp based on a nanosecond resolution [SWS_TS_01251]. Applications monitor synchronicity via status indicators such as SynchronizationStatus [SWS_TS_01050]. As an essential constraint, the asynchronous notification callbacks are not designed to be thread-safe, and connection losses to the time daemon must be handled.

Context

Within the AUTOSAR Adaptive Platform, the namespace ara::tsync provides the interfaces for high-precision time synchronization. It enables applications to read synchronized time points, monitor the synchronization state, and log measured values for validation purposes. The central role for consuming applications is assumed by class SynchronizedTimeBaseConsumer, which encapsulates access to a time base configured via a InstanceSpecifier. On the provider side, SynchronizedTimeBaseProvider serves as the access point for providing and controlling time bases.

The basis of the temporal representation is the pseudo-clock TimeBase, via which the type alias Timestamp is defined as std::chrono::time_point<TimeBase, std::chrono::nanoseconds> [SWS_TS_01251]. The actual synchronization work and connection to bus protocols such as IEEE 802.1AS or PTP typically occurs via a background service. Interpretation: This time daemon communicates cross-process with the instances of ara::tsync, which is evidenced by the specific error TsyncErrc::kDaemonConnectionLost [SWS_TS_00901]. Question Q-dd9d1a36f7573a03 (open) The architecture is complemented by interfaces such as ConsumerTimeBaseValidationNotification and ProviderTimeBaseValidationNotification as well as data structures for runtime and precision measurements (e.g., TimeMasterMeasurementType, TimeSlaveMeasurementType, PdelayInitiatorMeasurementType, and PdelayResponderMeasurementType).

Context diagram: Interaction between applications, interface classes, and time daemon in namespace ara::tsync. Sources: [SWS_TS_00901], [SWS_TS_01251].

Lifecycle

The lifecycle of a synchronized time base is determined by state structures and discrete status transitions. A snapshot of the temporal state including all metadata is represented by SynchronizedTimeBaseStatus. The communication and synchronization state is controlled via the enumeration SynchronizationStatus [SWS_TS_01050]:

  • kNotSynchronizedUntilStartup: Initial state before the first successful synchronization after system start.
  • kSynchronized: The time base is synchronous with the time master.
  • kSynchToGateway: Synchronization is performed via a gateway.
  • kTimeOut: No synchronization could be established or maintained within a defined time window.

In addition to the communication status, the enumeration LeapJump [SWS_TS_01051] records abrupt corrections of the time base: kTimeLeapNone signals continuous running without threshold violation, while kTimeLeapFuture and kTimeLeapPast indicate significant corrections into the future and past, respectively.

Regarding concurrency, it should be noted that callback types such as SynchronizationNotifier [SWS_TS_14222], SynchronizedTimeBaseNotifier [SWS_TS_14221], and TimePrecisionNotifier [SWS_TS_14223] are classified as not thread-safe according to the specification. State transitions, in particular the occurrence of timeouts or re-synchronizations, therefore require application-side synchronization.

State diagram: Lifecycle and communication states of a synchronized time base. Sources: [SWS_TS_01050].

Usage Path

The typical sequence for using a synchronized time base by a consumer application is divided into the following steps:

  1. Initialization and binding: The application instantiates SynchronizedTimeBaseConsumer for the desired time base, specifying the appropriate InstanceSpecifier.
  2. Registration of notifications: To monitor the synchronization state, the application passes callback functions. These include SynchronizationNotifier [SWS_TS_14222] for changes to SynchronizationStatus, SynchronizedTimeBaseNotifier [SWS_TS_14221] for detailed status snapshots (SynchronizedTimeBaseStatus), and TimePrecisionNotifier [SWS_TS_14223] for precision measurement data (TimePrecisionMeasurement).
  3. Timestamp querying: If the state is kSynchronized or kSynchToGateway [SWS_TS_01050], the application reads high-precision time values of type Timestamp [SWS_TS_01251].
  4. Reaction to status and time steps: If notifications signal a LeapJump not equal to kTimeLeapNone [SWS_TS_01051] or a transition to kTimeOut [SWS_TS_01050], the application adjusts internal timers or transitions into a degraded mode.
  5. Transmission of user data: If user-specific payload data is transmitted as part of the time synchronization, the structure UserData is used.

Error Scenarios

Error handling of the namespace follows the AUTOSAR standard model via the error domain TsyncErrorDomain. Access to this global domain is provided via GetTsyncErrorDomain() [SWS_TS_00909]. Error causes are described by the enumeration type TsyncErrc [SWS_TS_00901]:

  • kDaemonConnectionLost: The requested operation fails because the connection to the time sync daemon is interrupted.
  • kLimitsExceeded: A passed or calculated value is outside the permitted value range.
  • kFunctionNotSupported: The requested function is not supported in the current configuration or platform environment.
  • kInvalidUserDataSize: The length of the passed user data exceeds the maximum currently defined by UserData::kMaxUserDataSize of 3 bytes.

Instances of ara::core::ErrorCode are created via the helper function MakeErrorCode [SWS_TS_00910]. The function is declared as noexcept and is thread-safe. For exception-based architectures, the namespace provides the exception class TsyncException.

      The enumeration SynchronizationStatus expresses the communication and synchronization status of a time base in namespace ara::tsync [SWS_TS_01050]. The type is based on std::uint32_t and is provided via the header file ara/tsync/synchronized_time_base_status.h as well as the forwarding header ara/tsync/tsync_fwd.h [SWS_TS_01050]. The enumeration defines four states:
      

        

      • kNotSynchronizedUntilStartup (= 0): The time base is not synchronized prior to system startup (initial state) [SWS_TS_01050].
        • 

      • kTimeOut (= 0x1): The time base was not synchronized within a specified time window [SWS_TS_01050].
        • 

      • kSynchronized (= 0x2): The time base is synchronous with the Time Master [SWS_TS_01050].
        • 

      • kSynchToGateway (= 0x3): The time base is synchronous with the gateway [SWS_TS_01050].
        • 

      

      The synchronous retrieval of the status is performed via the method GetSynchronizationStatus() of class ara::tsync::SynchronizedTimeBaseStatus, which provides the state at the time of creation of the status object in a thread-safe and exception-safe manner (noexcept) [SWS_TS_01053]. For notifications upon status changes, the type alias SynchronizationNotifier (std::function<void(const SynchronizationStatus &)>) exists in ara/tsync/synchronized_time_base_consumer.h, which is explicitly specified as not thread-safe [SWS_TS_14222].
      

      In case of an error or in the absence of synchronization, the behavior of associated methods must be considered: If the time base has never been synchronized and exhibits the status kNotSynchronizedUntilStartup, the method GetCreationTime() returns an empty ara::core::Optional, since no valid creation timestamp exists in synchronized time [SWS_TS_01055].

          The enumeration TsyncErrc defines the standardized error codes of the Time Synchronization functional cluster [SWS_TS_00901]. It is based on ara::core::ErrorDomain::CodeType and is declared within the namespace ara::tsync; an alias is also available via ara::tsync::TsyncErrorDomain::Errc [SWS_TS_01266]. The thread-safe function MakeErrorCode, which combines a TsyncErrc value with vendor-specific additional data into a ara::core::ErrorCode, is used to create complete error objects [SWS_TS_00910].
          

  
          The specification defines four concrete error values [SWS_TS_00901]:
          
  
            
    
          • kDaemonConnectionLost (=1): The action cannot be performed because the connection to the Time-Sync Daemon is interrupted.
            • 
    
          • kLimitsExceeded (=2): A passed parameter exceeds the permitted value range. This occurs, for example, in SetRateCorrection if the requested rate correction is invalid [SWS_TS_01110].
            • 
    
          • kFunctionNotSupported (=3): The requested function is not supported. Interpretation: This is likely to affect implementations where optional hardware or interface functions are not available. Question Q-e22067d84fd6adb4 (open)
            • 
    
          • kInvalidUserDataSize (=4): The length of the payload exceeds the maximum size of 3 bytes specified by UserData::kMaxUserDataSize. This error occurs with SetTime [SWS_TS_01107] as well as SetUserData [SWS_TS_01112].
            • 
  
          

  
          Methods for updating time and data such as SetTime, UpdateTime, SetRateCorrection, and SetUserData of class ara::tsync::SynchronizedTimeBaseProvider return results synchronously via ara::core::Result<void> and are specified as non-threadsafe [SWS_TS_01107] [SWS_TS_01108] [SWS_TS_01110] [SWS_TS_01112]. In case of an error, according to the specification, no rollback semantics apply (no_rollback_semantics) [SWS_TS_01107] [SWS_TS_01110] [SWS_TS_01112].
