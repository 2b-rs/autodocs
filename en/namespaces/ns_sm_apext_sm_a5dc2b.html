Context

The namespace apext::sm defines platform-specific extension interfaces (Platform Extension Interfaces) for the Functional Cluster State Management within the AUTOSAR Adaptive Platform (AUTOSAR_AP_SWS_StateManagement Anhang C “Platform Extension Interfaces”). According to the specification, Platform Extension Interfaces serve to be provided or used by the OEM or system integrator to specifically extend the functional scope of the platform (AUTOSAR_AP_SWS_StateManagement Anhang C “Platform Extension Interfaces”). At the center of apext::sm is the coordination of system power states with the underlying Operating System (OS). For this purpose, the class PowerStateInterface serves as an intermediary between platform-wide state management and operating-system-specific power controls.

Primarily three components are involved in this coordination: the OEM or platform integrator who implements or integrates the extension interfaces, the Operating System (such as a Linux kernel with its native power modes), and the Functional Cluster State Management with its central Controller state machine (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”). In addition to aligning power states, the interface also enables the direct forwarding of low-level wake-up signals to State Management via the function alias WakeUpHandler ([SWS_SM_71004]).

Lifecycle

The platform extensions are integrated via the header file apext/sm/power_state_interface.h and the forwarding header apext/sm/sm_fwd.h ([SWS_SM_71002], [SWS_SM_71004]). The instantiation and lifetime of the PowerStateInterface implementation are subject to the platform basic services; the class is likely instantiated by the OEM or integrator during the initialization phase of the system in order to be available before the transition to power-saving states.

To represent the kernel power states, the namespace defines the enumeration PowerState with the underlying type std::uint32_t ([SWS_SM_71002]). The enum values reflect standardized Linux power states from the kernel perspective:

  • kPmSuspendToIdle (value 1, derived from PM_SUSPEND_TO_IDLE),
  • kPmSuspendToRam (value 2, derived from PM_SUSPEND_TO_RAM),
  • kPmHibernation (value 3, derived from PM_HIBERNATION),
  • kPmOff (value 4, derived from PM_OFF) ([SWS_SM_71002]).

With regard to concurrency, it is explicitly specified for the callback function WakeUpHandler (using WakeUpHandler = std::function<void(void)>;) that it is not thread-safe (not thread-safe) ([SWS_SM_71004]). Callers from the operating system environment must synchronize the call accordingly.

Usage Path

A central use case of apext::sm is the autonomous wake-up of the machine from a sleep state such as suspend-to-RAM (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”). While control applications (SMControlApplication) normally explicitly request transitions, State Management can also react autonomously to external events (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”).

The sequence takes place in the following steps:

  1. The system is in a power-saving mode that corresponds to a state such as kPmSuspendToRam ([SWS_SM_71002]).
  2. An external hardware or system event wakes up the Operating System.
  3. The Operating System signals the event, if implemented, via the interface apext::sm::WakeUpHandler to State Management (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”).
  4. State Management then initiates an autonomous wake-up sequence and transitions the Controller state machine to the defined wake-up state LeaveSuspend (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”, [SWS_SM_CONSTR_00036]).
  5. In this state, the configured entry LeaveSuspendToRam within the ActionList is executed ([SWS_SM_CONSTR_00037]), restoring regular system operation without the intervention of an external control application (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”).

Sequence diagram: Sequence of autonomous wake-up via WakeUpHandler. Sources: AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”, AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”, [SWS_SM_71004], [SWS_SM_CONSTR_00036], [SWS_SM_CONSTR_00037].

Error Scenarios

When using and connecting the interfaces, specific modeling and runtime conditions must be observed:

  • Missing wake-up state in manifest: For the StateMachine of type Controller, a state named LeaveSuspend must mandatorily be configured to complete the manifest creation ([SWS_SM_CONSTR_00036]). If this state is missing, State Management cannot execute the autonomous wake-up.
  • Missing action in LeaveSuspend: The state LeaveSuspend must mandatorily contain the element LeaveSuspendToRam in its ActionList ([SWS_SM_CONSTR_00037]). An incomplete configuration prevents the proper resumption of operation.
  • Concurrency issues at WakeUpHandler: Since the type WakeUpHandler is normatively specified as not thread-safe ([SWS_SM_71004]), simultaneous, uncoordinated signalings from multiple operating system or driver threads presumably lead to data races. The calling integrator code must protect the call.
  • Unimplemented interface: The WakeUpHandler is declared as an optional integration interface ("if implemented") (AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”). If no implementation is provided by the OEM, signals from the Operating System cannot be processed autonomously.

<h4>Usage Path</h4>
<p>A central use case of <code>apext::sm</code> is the autonomous wake-up of the machine from a sleep state such as suspend-to-RAM (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=102">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>). While control applications (<code>SMControlApplication</code>) normally explicitly request transitions, State Management can also react autonomously to external events (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=102">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>).</p>

<p>The sequence takes place in the following steps:</p>
<ol>
<li>The system is in a power-saving mode that corresponds to a state such as <code>kPmSuspendToRam</code> (<a class="spec-record-ref" data-req="SWS_SM_71002" href="../spec/record.html?id=SWS_SM_71002">[SWS_SM_71002]</a>).</li>
<li>An external hardware or system event wakes up the Operating System.</li>
<li>The Operating System signals the event, if implemented, via the interface <code>apext::sm::WakeUpHandler</code> to State Management (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=102">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>).</li>
<li>State Management then initiates an autonomous wake-up sequence and transitions the <code>Controller</code> state machine to the defined wake-up state <code>LeaveSuspend</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=103">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>, <a class="spec-record-ref" data-req="SWS_SM_CONSTR_00036" href="../spec/record.html?id=SWS_SM_CONSTR_00036">[SWS_SM_CONSTR_00036]</a>).</li>
<li>In this state, the configured entry <code>LeaveSuspendToRam</code> within the <code>ActionList</code> is executed (<a class="spec-record-ref" data-req="SWS_SM_CONSTR_00037" href="../spec/record.html?id=SWS_SM_CONSTR_00037">[SWS_SM_CONSTR_00037]</a>), restoring regular system operation without the intervention of an external control application (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=103">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>When using and connecting the interfaces, specific modeling and runtime conditions must be observed:</p>
<ul>
<li><strong>Missing wake-up state in manifest:</strong> For the <code>StateMachine</code> of type <code>Controller</code>, a state named <code>LeaveSuspend</code> must mandatorily be configured to complete the manifest creation (<a class="spec-record-ref" data-req="SWS_SM_CONSTR_00036" href="../spec/record.html?id=SWS_SM_CONSTR_00036">[SWS_SM_CONSTR_00036]</a>). If this state is missing, State Management cannot execute the autonomous wake-up.</li>
<li><strong>Missing action in LeaveSuspend:</strong> The state <code>LeaveSuspend</code> must mandatorily contain the element <code>LeaveSuspendToRam</code> in its <code>ActionList</code> (<a class="spec-record-ref" data-req="SWS_SM_CONSTR_00037" href="../spec/record.html?id=SWS_SM_CONSTR_00037">[SWS_SM_CONSTR_00037]</a>). An incomplete configuration prevents the proper resumption of operation.</li>
<li><strong>Concurrency issues at WakeUpHandler:</strong> Since the type <code>WakeUpHandler</code> is normatively specified as not thread-safe (<a class="spec-record-ref" data-req="SWS_SM_71004" href="../spec/record.html?id=SWS_SM_71004">[SWS_SM_71004]</a>), simultaneous, uncoordinated signalings from multiple operating system or driver threads presumably lead to data races. The calling integrator code must protect the call.</li>
<li><strong>Unimplemented interface:</strong> The <code>WakeUpHandler</code> is declared as an optional integration interface ("if implemented") (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=102">AUTOSAR_AP_SWS_StateManagement §7.7.15.1 “Autonomous wake-up from suspend state”</a>). If no implementation is provided by the OEM, signals from the Operating System cannot be processed autonomously.</li>
</ul>
