Context

The namespace ara::sm::s2r provides interfaces and mechanisms for the Suspend-to-RAM functionality (S2R) within the module State Management (SM) (AUTOSAR_AP_SWS_StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). The goal of Suspend-to-RAM operation is to significantly optimize startup and shutdown times by placing the Machine into a state that enables a fast restart instead of performing a complete shutdown followed by a cold start (AUTOSAR_AP_SWS_StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”).

The central role in the namespace is assumed by the class S2RHub (AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”). The hub coordinates communication with distributed S2RSatellite instances. Applications whose executable entities are configured as suspendToRamAware integrate such a satellite instance to be notified of pending suspend and resume cycles (AUTOSAR_AP_SWS_StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”, [SWS_SM_00710]). Processes declared as suspendToRamNotSupported must already be stopped by State Management sequences (e.g. terminating affected function groups) before the operating system transitions to the suspend state (AUTOSAR_AP_SWS_StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”).

Two mutually exclusive approaches exist for controlling S2RHub ([SWS_SM_00684]):

  • StateMachine approach: The Controller integrates the S2RHub functionality internally via assigned ActionListItem objects. In this operating mode, external control applications are prohibited from accessing the C++ API of the hub in order to prevent race conditions and state inconsistencies (AUTOSAR_AP_SWS_StateManagement §7.7 “StateMachine approach”, [SWS_SM_00684]).
  • Direct C++ API: An external control application (such as SMControlApplication) uses the class methods of the S2RHub directly (AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”).

Lifecycle

The creation and release of instances in the namespace ara::sm::s2r is strictly bound to authorization checks (Identity and Access Management, IAM) and configured mappings:

  • Hub instantiation: In the StateMachine approach, State Management creates an instance of S2RHub as soon as a ActionListItem of the types EnterSuspendToRam, EnterSuspendToRamOS, or LeaveSuspendToRam is terminated ([SWS_SM_00690]). During execution of the constructor ara::sm::s2r::S2RHub::S2RHub, it is checked whether the process context corresponds to the mapping in SuspendToRamHubMapping.process ([SWS_SM_00706]). Only processes authorized via SuspendToRamHubMapping may trigger suspend operations by means of a hub instance identified by SuspendToRamModuleInstantiation ([SWS_SM_00714]).
  • Satellite creation: A satellite instance is instantiated via the factory method ara::sm::s2r::S2RSatellite::Create ([SWS_SM_00716]).
  • Registration phase: After creation, the satellite registers with the hub using ara::sm::s2r::S2RSatellite::Offer ([SWS_SM_00710]). The hub validates the process context against the configuration in SuspendToRamSatelliteMapping.process and rejects unauthorized registration attempts ([SWS_SM_00715]). From the point of successful registration, the satellite is considered actively registered ([SWS_SM_00710]).
  • Deregistration: Active registration ends as soon as the satellite calls ara::sm::s2r::S2RSatellite::StopOffer ([SWS_SM_00710], [SWS_SM_00713]).

Usage Path

The typical usage sequence comprises preparing for the sleep state, switching to suspend mode, and coordinated wakeup after reactivation of the Machine:

  1. Deployment: Each S2R-capable application initializes its S2RSatellite and reports readiness to receive to the hub via Offer() ([SWS_SM_00710]).
  2. Suspend request: To initiate the sleep state, ara::sm::s2r::S2RHub::RequestToEnterSuspendMode is called ([SWS_SM_00701]). In the StateMachine approach, this is done via the ActionListItem EnterSuspendToRam using maxActionItemDuration as the timeout parameter ([SWS_SM_00689]).
  3. Satellite notification: The hub addresses all actively registered satellites and triggers their callback ara::sm::s2r::S2RSatellite::EnterSuspendMode ([SWS_SM_00701], [SWS_SM_00711]). RequestToEnterSuspendMode blocks until all addressed satellites have responded, have deregistered, or a communication timeout occurs ([SWS_SM_00702]).
  4. Operating system suspend: Once all satellites are prepared, the actual operating system suspend command can be triggered via EnterSuspendToRamOs ([SWS_SM_00692]).
  5. Wakeup request: After wakeup, the control calls ara::sm::s2r::S2RHub::RequestToLeaveSuspendMode ([SWS_SM_00703]). In the StateMachine approach, this occurs through the ActionListItem LeaveSuspendToRam ([SWS_SM_00691]). According to constraint [SWS_SM_CONSTR_00035], LeaveSuspendToRam may only be assigned to states that are responsible for exiting suspend mode, but not to the sleep states themselves.
  6. Satellite reactivation: The hub calls ara::sm::s2r::S2RSatellite::LeaveSuspendMode on the registered satellites ([SWS_SM_00703], [SWS_SM_00711]). The call returns as soon as all satellites have responded, have been deregistered, or the timeout has expired ([SWS_SM_00707]).
  7. Deregistration: If a process or satellite is terminated, deregistration at the hub occurs via StopOffer() ([SWS_SM_00710], [SWS_SM_00713]).

Sequence diagram: Call sequence from registration via suspend and resume to deregistration. Sources: [SWS_SM_00701], [SWS_SM_00702], [SWS_SM_00703], [SWS_SM_00707], [SWS_SM_00710], [SWS_SM_00711], [SWS_SM_00713].

Error Scenarios

The following error conditions and preconditions are specified in the interaction between hub and satellites:

  • IAM violation during hub creation: If the process context of the caller of S2RHub::S2RHub does not match configuration SuspendToRamHubMapping.process, the violation InsufficientPermissionsViolation is reported and the security event SEV_ACCESS_CONTROL_SM_IAM_ACCESS_DENIED is triggered ([SWS_SM_00706]).
  • Missing authentication at the satellite: If the IAM switch “Force IAM switch” is activated, S2RSatellite::Create returns the error code kAuthenticationRequired ([SWS_SM_00716]).
  • Rejection of unauthorized satellites: If the process context of the satellite does not match SuspendToRamSatelliteMapping.process, the hub rejects the registration ([SWS_SM_00715]).
  • Communication timeout: If an addressed satellite does not respond within the time period specified by timeout during RequestToLeaveSuspendMode, the hub returns the error code kCommunicationTimeout ([SWS_SM_00707]).
  • Rejection by satellites: If at least one satellite instance responds negatively with kRejected when exiting the quiescent state, the hub returns kAtLeastOneHadIssuesToLeave as the overall result ([SWS_SM_00707]). A positive overall result is only achieved if all satellites confirm positively or deregister regularly via StopOffer ([SWS_SM_00707]).
  • Configuration and usage restrictions: Assigning LeaveSuspendToRam to suspend states of the StateMachine is not permitted ([SWS_SM_CONSTR_00035]). Likewise, concurrent access to the C++ API of S2RHub is prohibited when the StateMachine approach is active ([SWS_SM_00684]).
