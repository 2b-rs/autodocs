Provides basic types, error domains, and interfaces for service-oriented communication in AUTOSAR Adaptive.

The namespace provides the core building blocks for service-oriented communication by binding service consumers via proxies and service providers via skeletons (ARAComAPI §7.6 “meta-model to Implementation”). The interaction comprises asynchronous service discovery, method calls with returns via futures, and event subscriptions via defined states ([SWS_CM_00310]). Key obligations include the correct resolution of instance identifiers as well as adherence to configured sample quotas and transmission intervals ([SWS_CM_10432]).

Context

The namespace ara::com provides the central types and mechanisms for service-oriented communication (Communication Management) within the AUTOSAR Adaptive Platform. The architectural model separates strictly between service consumers and service providers: On the consumer side (R-Port), client applications operate via generated proxy instances (ARAComAPI §7.6 “meta-model to Implementation”), whereas service providers on the server side expose their functionality via skeleton implementations (ARAComAPI §6.2 “Definition of BatteryState”).

The technical middleware (binding) mediates between proxy and skeleton. InstanceIdentifier serves to identify and distinguish individual service instances, with collections of concrete instances being managed via InstanceIdentifierContainer ([SWS_CM_00319]). The platform supports multi-binding scenarios in which abstract model identifiers are resolved to a list of technical bindings and instances (ARAComAPI §6.6 “InstanceIdentifier Resolution”).

Context diagram: Interplay between proxy, middleware binding, and skeleton in service communication. Sources: ARAComAPI §7.6 “meta-model to Implementation”, ARAComAPI §6.6 “InstanceIdentifier Resolution”, [SWS_CM_10432].

Lifecycle

Services and communication connections are subject to clearly defined state models in ara::com. General service availability is represented via the enumeration ServiceState with the values kAvailable and kNotAvailable ([SWS_CM_01071]). State changes can be monitored by means of registered ServiceStateHandler ([SWS_CM_01072]).

For events and fields, SubscriptionState governs the lifecycle of a subscription with the states kNotSubscribed, kSubscriptionPending, and kSubscribed ([SWS_CM_00310]). State transitions are reported asynchronously to a SubscriptionStateChangeHandler ([SWS_CM_00311]). The transition from kNotSubscribed to kSubscriptionPending presumably takes place immediately upon sending the subscription request to the underlying transport binding.

On the service implementation side, MethodCallProcessingMode controls the concurrency of incoming method calls: kPoll for manual polling, kEvent for concurrent, event-driven processing, and kEventSingleThread for sequential processing in a single thread ([SWS_CM_00301]). Sample management uses SampleAllocateePtr on the sender side to optimize allocations (e.g. zero-copy approaches via shared memory) ([SWS_CM_00308], ARAComAPI §6.18 “Event Allocate/Send sample Binding implementer hint”) and SamplePtr on the receiver side ([SWS_CM_10432]).

Usage Path

A typical sequence for service usage proceeds via the following steps:

  1. Service discovery: The consumer initiates the search for compatible service instances. Upon availability, the middleware passes a ServiceHandleContainer with found handles as well as a FindServiceHandle, with which ongoing searches can be terminated, via FindServiceHandler ([SWS_CM_00383], [SWS_CM_00304]).
  2. Proxy instantiation: The proxy instance is created locally in the client using a matching handle (ARAComAPI §6.3 “Handling of optional data elements on Skeleton side”).
  3. Method call: The method call overloads the call operator of the method wrapper class. Input parameters are passed, and the call returns a ara::com::Future that encapsulates the output parameters (ARAComAPI §6.10 “Adjust Method Class”, ARAComAPI §6.12 “Adjust Method Class”).
  4. Result processing: The client retrieves the result synchronously or asynchronously (e.g. via get()) and checks optional field elements for presence prior to access (ARAComAPI §6.3 “Handling of optional data elements on Skeleton side”).
  5. Event reception: Incoming data for subscribed events, fields, or triggers are processed via registered callbacks such as EventReceiveHandler ([SWS_CM_00309]), FieldReceiveHandler ([SWS_CM_11615]), or TriggerReceiveHandler ([SWS_CM_00351]).

Sequence diagram: Call sequence from service discovery via method call with future to result retrieval. Sources: [SWS_CM_00383], [SWS_CM_00304], ARAComAPI §6.3 “Handling of optional data elements on Skeleton side”, ARAComAPI §6.10 “Adjust Method Class”.

Error Scenarios

Error conditions in the communication subsystem are mapped via ComErrorDomain and the error codes in ComErrc ([SWS_CM_10432]). Access to the domain is performed via GetComErrorDomain() ([SWS_CM_11334]), whereas concrete errors are instantiated via MakeErrorCode() ([SWS_CM_11335]). In exceptional cases, ComException is thrown.

Typical error scenarios include:

  • Service availability: Calls to unprovided services lead to ComErrc::kServiceNotOffered or ComErrc::kServiceNotAvailable ([SWS_CM_10432]).
  • Configuration and instance resolution errors: If an identifier cannot be mapped to a InstanceIdentifier, the system reports ComErrc::kInstanceIDNotResolvable ([SWS_CM_10432], ARAComAPI §6.6 “InstanceIdentifier Resolution”).
  • Resource and subscription limits: If an application holds more SamplePtr instances than agreed upon in Subscribe(), ComErrc::kMaxSamplesExceeded occurs ([SWS_CM_10432]). If the maximum number of samples deviates upon re-subscribing, this results in ComErrc::kMaxSampleCountNotRealizable ([SWS_CM_10432]).
  • Protocol and timing conditions: In case of network errors or secure communication errors, ComErrc::kCommunicationFailure is reported. If transmission intervals are fallen below, transmission fails with ComErrc::kMinimumSendIntervalViolationError ([SWS_CM_10432]).
  • Field handling: Uninitialized field values lead to ComErrc::kFieldValueNotInitialized, missing set handlers to ComErrc::kFieldSetHandlerNotSet ([SWS_CM_10432]).

The enumeration ComErrc defines, according to [SWS_CM_10432], the standardized error codes of ara::com::ComErrorDomain for recoverable errors according to EXP ARAComAPI §2 “Recoverable Errors”. It is transported in return types such as ara::core::Result or ara::core::Future of synchronous and asynchronous APIs of Communication Management to signal functional error causes precisely in the client or server context.

The enumerators cover specific error cases along the service life cycle and data transmission:

  • Service life cycle and binding: kServiceNotOffered indicates that a service has not yet been offered via OfferService() ([SWS_CM_00101]), while kServiceNotAvailable signals the intermittent loss. kInstanceIDNotResolvable occurs when a InstanceSpecifier cannot be resolved ([SWS_CM_00118]).
  • Event and sample subscriptions: kMaxSamplesExceeded warns of exceeding promised SamplePtr quotas, and kMaxSampleCountNotRealizable reports unsuitable values during resubscription via [SWS_CM_00141].
  • Fields and transmission: kFieldValueNotInitialized indicates missing initialization prior to Update() ([SWS_CM_00119]), kFieldSetHandlerNotSet a missing setter handler. Local network issues, such as during trigger transmission via [SWS_CM_00721], result in kCommunicationFailure ([SWS_CM_10517]). In addition, kMinimumSendIntervalViolationError penalizes cycle rate violations and kUnknownApplicationError unexpected server errors ([SWS_CM_10432]).

As a pure enumeration type, ComErrc has no state of its own; read and comparison operations on error values are therefore likely to be concurrently safe in the calling thread. The actual error checking is the responsibility of the application after evaluating the respective result object.

      The enumeration ara::com::MethodCallProcessingMode defines the processing modes for incoming method calls on a service instance [SWS_CM_00301]. It is passed as a parameter to the constructors of the skeleton classes, with the default value ara::com::MethodCallProcessingMode::kEvent predefined [SWS_CM_00130], [SWS_CM_00152], [SWS_CM_00153].
      

      The enumerators control the concurrency and execution context of the service methods [SWS_CM_00301]:
      

        

      • kPoll: Polling mode. Incoming calls from service consumers are not executed automatically. The service implementation actively controls their execution by calling ProcessNextMethodCall() [SWS_CM_00199]. The pending method is processed synchronously in the context of this call. This ensures full control over thread and context switches on the service side ARAComAPI §6.3.3 “Event Buffering Approaches”.
        • 

      • kEvent: Event-driven and concurrent mode for parallel processing of incoming calls.
        • 

      • kEventSingleThread: Event-driven, sequential mode for single execution of method calls.
        • 

      

      Error Handling and Restrictions:
      

        

      • If an invalid mode is passed to a skeleton constructor, violation WrongMethodCallProcessingModeViolation occurs [SWS_CM_00130], [SWS_CM_00153].
        • 

      • Calling ProcessNextMethodCall() on a skeleton constructed with kEvent likewise leads to a WrongMethodCallProcessingModeViolation [SWS_CM_00199] (interpretation: this is likely to apply to kEventSingleThread as well, since the method is intended only for kPoll).
        •

    The enumeration SubscriptionState [SWS_CM_00310] represents the current state of a subscription in namespace ara::com based on type std::uint8_t. It defines three distinct states:
  
              
  
                
    
              • kNotSubscribed: The subscription is inactive.
                • 
    
              • kSubscriptionPending: The subscription is still pending or the connection is being re-established after a failure.
                • 
    
              • kSubscribed: The subscription is active.
                • 
  
              
  
              
    The GetSubscriptionState() method serves for synchronous querying, which is provided on proxy events [SWS_CM_00316], proxy fields [SWS_CM_11604], and triggers [SWS_CM_01105] as well as skeleton triggers [SWS_CM_01109]. All of these query functions are declared as noexcept and guarantee complete exception safety.
  
              
  
              
    For asynchronous reactions to status changes, applications can register a callback of type SubscriptionStateChangeHandler via SetSubscriptionStateChangeHandler() [SWS_CM_00311] [SWS_CM_00333]. If an invalid or empty handler is passed, the violation InvalidHandlerViolation occurs [SWS_CM_00333]. Deregistration is performed via UnsetSubscriptionStateChangeHandler() [SWS_CM_00334]. Furthermore, a template overload with ExecutorT allows specifying the execution context for the callback [SWS_CM_11354].
  
              
  
              
    In the lifecycle of a proxy instance, SubscriptionState is closely interlinked with automatic updating: If a service instance fails, method calls fail and GetSubscriptionState() returns kSubscriptionPending for previously subscribed events ARAComAPI §6.1 “Auto Updating of Proxy Instance”. As soon as the service instance is reachable again via Service Discovery, communication management updates the connection transparently; GetSubscriptionState() then automatically returns kSubscribed again AUTOSAR_AP_EXP_ARAComAPI §5.3.5.2. Manual re-creation of the proxy or re-subscribing is not required in this process.
