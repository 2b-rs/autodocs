Publishing process

This page describes the complete pipeline for the AUTOSAR Adaptive Platform API reference: from authoritative specification records through translation and diagrams to HTML output, validation, reports, and traceability. It is intended for curators, maintainers, and AI agents alike. Operational agent instructions (such as AGENTS.md) are maintained as independent pipeline artifacts with their own curation and review lifecycle and are referenced here.

1. Overview

The pipeline follows a deterministic layered model: Specification DB → Curation & Review → i18n Segmentation → Diagram Translation → HTML Generation → Validation → Reports & Traceability. Every publication is created reproducibly from the defined sources under _src/.

2. Source of Truth & Artifact Categories

The storage structure strictly distinguishes between authoritative sources, managed pipeline artifacts, and ephemeral build products:

  • Source of Truth (authoritative): _src/spec/records/**/*.json (specification records) and catalogs such as _src/spec/namespaces.json and _src/spec/projects.json. All content changes must be made here.
  • Pipeline artifacts (versioned/curated): Page models under _src/sources/pages/, review and curation queues, i18n registers (_src/i18n/), diagram sources (.dot, .seq.json) and agent instructions (e.g. AGENTS.md).
  • Generated build artifacts (disposable): The entire HTML tree (index.html, classes/, namespaces/, modules/, services/) and all localized language trees (en/, es/, pt/, fr/, ru/, ar/, hi/, ko/, zh/, nl/).
  • Working and cache products: PDF cache (_src/spec/pdf-cache/), output/, and execution and log archives at output/run-archive/.

3.1 Review and feedback processes

The platform offers two separate, clearly defined interaction paths for quality assurance and corrections:

Curator decision protocol (review.js)

For authorized curators and reviewers to approve (accept) or reject (reject) unclear extraction candidates directly on the requirements panel.

Process: Decisions are collected locally in the package in the browser and then submitted as a structured GitHub issue. After ingestion, the decision is applied directly to the data set.

Flag-for-Review request process (review_request.js)

For all website visitors to report discrepancies, outdated sources or missing context in published data sets.

Flow: A request creates an immutable queue task. AI agents analyze the report and prepare a proposal; the final decision always remains with human curators.

Storage, identity and data protection

Both processes run in a privacy-preserving, isolated way in the browser (localStorage):

  • ara-review-package-v1: Local cache for approvals collected in the curator panel.
  • ara-review-github-token-v1: Optional GitHub token for authenticated submissions (reused between both dialogs).
  • ara-review-identity: Self-selected name for unauthenticated submissions.
  • No cookies, no tracking and no server-side storage of incomplete form data.

4. Localization (i18n): Extraction, Translation & Merge

Internationalization occurs via a deterministic JSONL pipeline:

  1. Extraction: python3 _src/i18n_extract.py extracts all new and changed text segments from the canonical German sources and assigns them stable IDs.
  2. Translation: The segments are translated into the 10 target languages (en, es, pt, fr, ru, ar, hi, ko, zh, nl). Code fragments, identifiers, and placeholder tokens remain protected and unchanged.
  3. Merge: _src/i18n_translate.py merge merges the translated segments with the source inventory and reports missing or incomplete translations.

Segments that are not translated automatically fall back to the original German version in the generated language tree.

5. Diagram translation

Diagrams are generated from .dot and .seq.json sources. Their labels are extracted like normal text, translated, and inserted into the generated diagrams for each language during the build. Consequently, every diagram is available consistently in all 10 languages.

6. HTML generation

The _src/generate.py generator transforms the page models (_src/sources/pages/*.json) and specification records into static HTML pages. A complete, self-contained HTML tree is generated for each language. The call is made via:

python3 _src/generate.py --lang=all

7. Validation & Quality Check

Before publishing, _src/validate.py checks the overall result for consistency:

  • Checking all internal and external links and anchors.
  • Check for orphaned pages or missing references.
  • Verification of namespace memberships and signature consistency.
  • Verification of i18n completeness and detection of unintended language mixing.

An exit code other than 0 blocks the release step and forces the underlying sources to be corrected.

9. Error Handling & Guidelines

Deviations, validation errors or translation gaps may never be patched directly in the generated HTML. Bug fixes are always done at the authoritative source level (_src/spec/ or _src/sources/pages/), followed by a full rebuild and validation. Rejections in translation batches must be checked and resubmitted by the curation team.
