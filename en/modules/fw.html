The Firewall as a Functional Cluster: Role and System Boundary

The Functional Cluster Firewall (namespace ara::fw) provides applications with exactly one functional programming interface. That is the class ara::fw::FirewallStateSwitchInterface with the method SwitchFirewallState [AP_SWS_Fw_82008]. According to the architecture description, the cluster is daemon-based. It implements the interface FirewallStateSwitchInterface with the stereotype «aapAPI,aapPortInterface», and an Adaptive Application uses it via a «use» relationship EXP SWArchitecture p. 126. The use case diagram lists two use cases. \"Switch Firewall State\" is triggered by an Adaptive Application. The Intrusion Detection System Manager is involved in \"Report Security Event\". The Operating System acts as another actor EXP SWArchitecture p. 197.

The architecture sketch of the SWS clearly separates the responsibilities:

  • The Machine Manifest provides the firewall configuration with its filter rules.
  • The FC Firewall uses this to configure the Firewall Engine.
  • An OEM application specifies the firewall state.
  • Security Events (SEvs) go to the IdsM SWS Firewall p. 16.

The platform design shows the same division EXP PlatformDesign p. 97. The actual packet inspection thus lies outside the API. The scenario for the state change assigns the rule application to the Operating System and marks it as «aapInformative» EXP SWArchitecture p. 232.

Context diagram: The FC Firewall mediates between manifest configuration, state-specifying application, executing engine or Operating System, and IdsM. Sources: SWS Firewall p. 16, EXP SWArchitecture p. 126, EXP SWArchitecture p. 232

State-Dependent Filtering: Firewall States and Filter Rules

The core of the concept is state-dependent filtering. OEM-specific firewall states represent situations in which different network traffic is to be expected, such as driving, parking, or a diagnostic session. Filter rules are assigned to a state. For inspection and filtering, the firewall uses only the rules of the currently active state. An application sets the current state via the API of the FC Firewall EXP PlatformDesign p. 92. In C++, this is the method SwitchFirewallState(EnumT firewallState) [AP_SWS_Fw_82008].

The rules themselves are contents of the manifest. The diagram of foundation requirements shows filter chains across multiple layers:

  • Ethernet with MAC addresses and EtherType,
  • IPv4,
  • TCP with state detection via flags or ICMP,
  • SOME/IP with service, method, and client ID RS Firewall p. 12.

At the transport layer, the manifest models a FirewallRule with the attributes bucketSize and refillAmount. In addition, there is a TransportLayerRule with port ranges and checksumVerification, which is specialized into UDP and TCP rules TPS Manifest p. 687.

If a packet matches none of the defined rules, the default action applies. The R23-11 version of the SWS additionally describes how the protocol layer of the mismatch is determined for a packet blocked in this way. The rule with the most consecutive matches, counted starting from the lowest network layer, is decisive. On the first non-matching layer, a layer-specific SEv is triggered SWS Firewall p. 31. This passage originates from R23-11 and is not covered in the payload by an R25-11 requirement. It is therefore to be read as an explanation, not as a normative requirement.

From InstanceSpecifier to State Change

First, an application creates an instance of FirewallStateSwitchInterface. The explicit constructor, which expects an ara::core::InstanceSpecifier, serves this purpose. It is noexcept and specified as thread-safe [AP_SWS_Fw_82002]. Interpretation: The InstanceSpecifier likely designates the RPortPrototype of the application, which is typed in the manifest by FirewallStateSwitchInterface. The manifest diagram establishes precisely this port relationship, but does not name the specifier TPS Manifest p. 677.

SwitchFirewallState(EnumT firewallState) triggers the state change. The method is noexcept and returns a ara::core::Future<void> [AP_SWS_Fw_82008]. The \"Switch Firewall State\" scenario shows the sequence in three steps:

  1. The Adaptive Application calls SwitchFirewallState() on the FC Firewall.
  2. The FC Firewall calls applyRule() at the Operating System in a loop for each FirewallRule.
  3. After that, the response goes back to the application EXP SWArchitecture p. 232.

The R22-11 representation of the same scenario shows the same sequence EXP SWArchitecture p. 158. Because applyRule() is marked as «aapInformative», the loop describes the principle. It does not define a binding Operating System interface EXP SWArchitecture p. 232.

Security Events to the Intrusion Detection System Manager

In addition to state switching, the Firewall supports the Intrusion Detection System. For blocked messages, a set of security events is specified that are reported to the IdsM. The IdsM handles their qualification and further processing. It forwards them to a SOC or persistently stores them on the ECU EXP PlatformDesign p. 92. The scenario "Report Security Event" connects Operating System, FC Firewall, and IdsM via the interactions packetBlocked(), handlePacketBlocked(), raiseSecurityEvent(), and ReportEvent(). Parts of it are marked as «aapInformative» EXP SWArchitecture p. 232.

For packets blocked by the Default Action, the R23-11 SWS specifies layer-specific events SWS Firewall p. 31:

  • SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH for Ethernet,
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

These event names are not covered by R25-11 requirements in the payload. Their validity for R25-11 must be verified against the current SWS SWS Firewall p. 31.

Behavior in the event of an error

For SwitchFirewallState, two errors are specified: FwErrc::kServiceNotAvailable and FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]. Their values are defined by the enumeration FwErrc, namely kServiceNotAvailable=1 and kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]. The method is noexcept and returns a ara::core::Future<void>. The caller therefore evaluates these errors via the future and not via an exception from the call [AP_SWS_Fw_82008].

Both errors belong to FwErrorDomain. The domain provides the following building blocks:

  • GetFwErrorDomain() returns a reference to the domain object; the function is constexpr and thread-safe [AP_SWS_Fw_83002].
  • MakeErrorCode creates a ara::core::ErrorCode from a FwErrc and additional data [AP_SWS_Fw_83003].
  • Name() and Message() return the name of the domain and the message text for a code; both are thread-safe [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • The aliases Errc and Exception refer to FwErrc and FwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

The default constructor of the domain is deleted, although its description reads "Constructs a new FwErrorDomain object" [AP_SWS_Fw_83009]. Access to the domain is therefore performed via GetFwErrorDomain().

To propagate an error as an exception, ThrowAsException is used. The function creates and throws a FwException. It is noexcept(false) and classified as "not exception safe" [AP_SWS_Fw_83012]. The exception itself is created via the explicit, thread-safe constructor FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005].

At packet level, the error case is the blocking of a packet. Packets without a matching rule fall under the Default Action, and blocked messages are reported to the IdsM as security events EXP PlatformDesign p. 92. The interface in [AP_SWS_Fw_82008] does not provide a return channel to the application for such events. Their handling lies with the IdsM.

<h4>State-Dependent Filtering: Firewall States and Filter Rules</h4>
<p>The core of the concept is state-dependent filtering. OEM-specific firewall states represent situations in which different network traffic is to be expected, such as driving, parking, or a diagnostic session. Filter rules are assigned to a state. For inspection and filtering, the firewall uses only the rules of the currently active state. An application sets the current state via the API of the FC Firewall <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign p. 92</a>. In C++, this is the method <code>SwitchFirewallState(EnumT firewallState)</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>The rules themselves are contents of the manifest. The diagram of foundation requirements shows filter chains across multiple layers:</p>
<ul>
<li>Ethernet with MAC addresses and EtherType,</li>
<li>IPv4,</li>
<li>TCP with state detection via flags or ICMP,</li>
<li>SOME/IP with service, method, and client ID <a class="docref internal-spec-ref" href="../../spec/figures/FIG-8d7d096012113639.html" data-snip="FIG-8d7d096012113639">RS Firewall p. 12</a>.</li>
</ul>
<p>At the transport layer, the manifest models a <code>FirewallRule</code> with the attributes <code>bucketSize</code> and <code>refillAmount</code>. In addition, there is a <code>TransportLayerRule</code> with port ranges and <code>checksumVerification</code>, which is specialized into UDP and TCP rules <a class="docref internal-spec-ref" href="../../spec/figures/FIG-465799fa260b6f07.html" data-snip="FIG-465799fa260b6f07">TPS Manifest p. 687</a>.</p>
<p>If a packet matches none of the defined rules, the default action applies. The R23-11 version of the SWS additionally describes how the protocol layer of the mismatch is determined for a packet blocked in this way. The rule with the most consecutive matches, counted starting from the lowest network layer, is decisive. On the first non-matching layer, a layer-specific SEv is triggered <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3.html" data-snip="SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3">SWS Firewall p. 31</a>. This passage originates from R23-11 and is not covered in the payload by an R25-11 requirement. It is therefore to be read as an explanation, not as a normative requirement.</p>

<h4>From InstanceSpecifier to State Change</h4>
<p>First, an application creates an instance of <code>FirewallStateSwitchInterface</code>. The explicit constructor, which expects an <code>ara::core::InstanceSpecifier</code>, serves this purpose. It is <code>noexcept</code> and specified as thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_82002" href="../spec/record.html?id=AP_SWS_Fw_82002">[AP_SWS_Fw_82002]</a>. Interpretation: The <code>InstanceSpecifier</code> likely designates the <code>RPortPrototype</code> of the application, which is typed in the manifest by <code>FirewallStateSwitchInterface</code>. The manifest diagram establishes precisely this port relationship, but does not name the specifier <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest p. 677</a>.</p>
<p><code>SwitchFirewallState(EnumT firewallState)</code> triggers the state change. The method is <code>noexcept</code> and returns a <code>ara::core::Future&lt;void&gt;</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. The \"Switch Firewall State\" scenario shows the sequence in three steps:</p>
<ol>
<li>The Adaptive Application calls <code>SwitchFirewallState()</code> on the FC Firewall.</li>
<li>The FC Firewall calls <code>applyRule()</code> at the Operating System in a loop for each <code>FirewallRule</code>.</li>
<li>After that, the response goes back to the application <a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP SWArchitecture p. 232</a>.</li>
</ol>
<p>The R22-11 representation of the same scenario shows the same sequence <a class="docref internal-spec-ref" href="../../spec/figures/FIG-826e9bb7c1d7761d.html" data-snip="FIG-826e9bb7c1d7761d">EXP SWArchitecture p. 158</a>. Because <code>applyRule()</code> is marked as «aapInformative», the loop describes the principle. It does not define a binding Operating System interface <a class="docref internal-spec-ref" href="../../spec/figures/FIG-bd1d9121c3dc5224.html" data-snip="FIG-bd1d9121c3dc5224">EXP SWArchitecture p. 232</a>.</p>

<h4>Generated State Types and Manifest Connection</h4>
<p>The permitted Firewall states do not form a fixed platform type. For each modeled interface, a dedicated <code>enum class {&lt;fwssi-sn&gt;} : std::uint32_t</code> is generated in the <code>ara::fw::states</code> namespace. It is included via <code>ara/fw/states/{&lt;fwssi-sn&gt;}.h</code>, and the enumerator list originates from the model <a class="spec-record-ref" data-req="AP_SWS_Fw_81001" href="../spec/record.html?id=AP_SWS_Fw_81001">[AP_SWS_Fw_81001]</a>. For each modeled Firewall state, an enumerator of the form <code>{&lt;symbol-fw-state&gt;} = {&lt;fw-state-value&gt;}</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a> is generated. Interpretation: The parameter type <code>EnumT</code> of <code>SwitchFirewallState</code> likely represents this generated state type, since [AP_SWS_Fw_81001] explicitly defines it as the state type for <code>FirewallStateSwitchInterface</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>In the metamodel, <code>FirewallStateSwitchInterface</code> is a <code>PortInterface</code>. Via the role <code>firewallStateMachine</code>, it aggregates (0..*) elements of type <code>ModeDeclarationGroupPrototype</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-b3757549d69ff2c3.html" data-snip="FIG-b3757549d69ff2c3">TPS Manifest p. 263</a>. Presumably, the modes of this group provide the enumerators from <a class="spec-record-ref" data-req="AP_SWS_Fw_81002" href="../spec/record.html?id=AP_SWS_Fw_81002">[AP_SWS_Fw_81002]</a>. However, the sources do not explicitly describe this mapping.</p>
<p>At machine level, <code>AdaptiveFirewallModuleInstantiation</code> collects the machine-specific settings of the Firewall (<code>TPS_MANI_03296</code>, status DRAFT). The metaclass <code>AdaptiveFirewallToPortPrototypeMapping</code> connects this instantiation via the reference <code>firewall</code> (0..1) to the <code>RPortPrototype</code> of the application <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58.html" data-snip="SNIP_ADAPTIVE_PLATFORM_FIGURE_Figure_12_58">TPS Manifest p. 677</a>. In doing so, the note of this metaclass refers to a "FirewallModeSwitchInterface". In contrast, the diagram and API consistently use <code>FirewallStateSwitchInterface</code> <a class="docref internal-spec-ref" href="../../spec/figures/FIG-e3d3c06875990d8f.html" data-snip="FIG-e3d3c06875990d8f">TPS Manifest p. 677</a>.</p>

<h4>Lifecycle and Concurrency of the Interface Instance</h4>
<p>An instance of <code>FirewallStateSwitchInterface</code> is non-copyable. Copy constructor and copy assignment are deleted <a class="spec-record-ref" data-req="AP_SWS_Fw_82004" href="../spec/record.html?id=AP_SWS_Fw_82004">[AP_SWS_Fw_82004]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82005" href="../spec/record.html?id=AP_SWS_Fw_82005">[AP_SWS_Fw_82005]</a>. Moving, in contrast, is permitted, because move constructor and move assignment are <code>noexcept</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82006" href="../spec/record.html?id=AP_SWS_Fw_82006">[AP_SWS_Fw_82006]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_82007" href="../spec/record.html?id=AP_SWS_Fw_82007">[AP_SWS_Fw_82007]</a>. <h4>Security Events to the Intrusion Detection System Manager</h4>
<p>In addition to state switching, the Firewall supports the Intrusion Detection System. For blocked messages, a set of security events is specified that are reported to the IdsM. The IdsM handles their qualification and further processing. It forwards them to a SOC or persistently stores them on the ECU <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2.html" data-snip="SNIP_ADAPTIVE_CAN_FIGURE_Figure_20_2">EXP PlatformDesign p. 92</a>. The scenario "Report Security Event" connects Operating System, FC Firewall, and IdsM via the interactions <code>packetBlocked()</code>, <code>handlePacketBlocked()</code>, <code>raiseSecurityEvent()</code>, and <code>ReportEvent()</code>. Parts of it are marked as «aapInformative» <a class="docref internal-spec-ref" href="../../spec/figures/FIG-b1273965639f62af.html" data-snip="FIG-b1273965639f62af">EXP SWArchitecture p. 232</a>.</p>
<p>For packets blocked by the Default Action, the R23-11 SWS specifies layer-specific events <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3.html" data-snip="SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3">SWS Firewall p. 31</a>:</p>
<ul>
<li><code>SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH</code> for Ethernet,</li>
<li><code>SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH</code>,</li>
<li><code>SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH</code>,</li>
<li><code>SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH</code>.</li>
</ul>
<p>These event names are not covered by R25-11 requirements in the payload. Their validity for R25-11 must be verified against the current SWS <a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3.html" data-snip="SNIP_ADAPTIVE_IDSM_FIGURE_Figure_7_3">SWS Firewall p. 31</a>.</p>

<h4>Behavior in the event of an error</h4>
<p>For <code>SwitchFirewallState</code>, two errors are specified: <code>FwErrc::kServiceNotAvailable</code> and <code>FwErrc::kInvalidStateDependentFirewall</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>. Their values are defined by the enumeration <code>FwErrc</code>, namely <code>kServiceNotAvailable=1</code> and <code>kInvalidStateDependentFirewall=2</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83001" href="../spec/record.html?id=AP_SWS_Fw_83001">[AP_SWS_Fw_83001]</a>. The method is <code>noexcept</code> and returns a <code>ara::core::Future&lt;void&gt;</code>. The caller therefore evaluates these errors via the future and not via an exception from the call <a class="spec-record-ref" data-req="AP_SWS_Fw_82008" href="../spec/record.html?id=AP_SWS_Fw_82008">[AP_SWS_Fw_82008]</a>.</p>
<p>Both errors belong to <code>FwErrorDomain</code>. The domain provides the following building blocks:</p>
<ul>
<li><code>GetFwErrorDomain()</code> returns a reference to the domain object; the function is <code>constexpr</code> and thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_83002" href="../spec/record.html?id=AP_SWS_Fw_83002">[AP_SWS_Fw_83002]</a>.</li>
<li><code>MakeErrorCode</code> creates a <code>ara::core::ErrorCode</code> from a <code>FwErrc</code> and additional data <a class="spec-record-ref" data-req="AP_SWS_Fw_83003" href="../spec/record.html?id=AP_SWS_Fw_83003">[AP_SWS_Fw_83003]</a>.</li>
<li><code>Name()</code> and <code>Message()</code> return the name of the domain and the message text for a code; both are thread-safe <a class="spec-record-ref" data-req="AP_SWS_Fw_83010" href="../spec/record.html?id=AP_SWS_Fw_83010">[AP_SWS_Fw_83010]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83011" href="../spec/record.html?id=AP_SWS_Fw_83011">[AP_SWS_Fw_83011]</a>.</li>
<li>The aliases <code>Errc</code> and <code>Exception</code> refer to <code>FwErrc</code> and <code>FwException</code> <a class="spec-record-ref" data-req="AP_SWS_Fw_83007" href="../spec/record.html?id=AP_SWS_Fw_83007">[AP_SWS_Fw_83007]</a> <a class="spec-record-ref" data-req="AP_SWS_Fw_83008" href="../spec/record.html?id=AP_SWS_Fw_83008">[AP_SWS_Fw_83008]</a>.</li>
</ul>
<p>The default constructor of the domain is deleted, although its description reads "Constructs a new FwErrorDomain object" <a class="spec-record-ref" data-req="AP_SWS_Fw_83009" href="../spec/record.html?id=AP_SWS_Fw_83009">[AP_SWS_Fw_83009]</a>. Access to the domain is therefore performed via <code>GetFwErrorDomain()</code>.</p>
<p>To propagate an error as an exception, <code>ThrowAsException</code> is used. The function creates and throws a <code>FwException</code>.
