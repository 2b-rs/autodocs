The Firewall as a Functional Cluster: Role and System Boundary

The Functional Cluster Firewall (namespace ara::fw) provides applications with exactly one functional programming interface. That is the class ara::fw::FirewallStateSwitchInterface with the method SwitchFirewallState [AP_SWS_Fw_82008]. According to the architecture description, the cluster is daemon-based. It implements the interface FirewallStateSwitchInterface with the stereotype «aapAPI,aapPortInterface», and an Adaptive Application uses it via a «use» relationship EXP SWArchitecture p. 126. The use case diagram lists two use cases. \"Switch Firewall State\" is triggered by an Adaptive Application. The Intrusion Detection System Manager is involved in \"Report Security Event\". The Operating System acts as another actor EXP SWArchitecture p. 197.

The architecture sketch of the SWS clearly separates the responsibilities:

  • The Machine Manifest provides the firewall configuration with its filter rules.
  • The FC Firewall uses this to configure the Firewall Engine.
  • An OEM application specifies the firewall state.
  • Security Events (SEvs) go to the IdsM SWS Firewall p. 16.

The platform design shows the same division EXP PlatformDesign p. 97. The actual packet inspection thus lies outside the API. The scenario for the state change assigns the rule application to the Operating System and marks it as «aapInformative» EXP SWArchitecture p. 232.

Context diagram: The FC Firewall mediates between manifest configuration, state-specifying application, executing engine or Operating System, and IdsM. Sources: SWS Firewall p. 16, EXP SWArchitecture p. 126, EXP SWArchitecture p. 232

State-Dependent Filtering: Firewall States and Filter Rules

The core of the concept is state-dependent filtering. OEM-specific firewall states represent situations in which different network traffic is to be expected, such as driving, parking, or a diagnostic session. Filter rules are assigned to a state. For inspection and filtering, the firewall uses only the rules of the currently active state. An application sets the current state via the API of the FC Firewall EXP PlatformDesign p. 92. In C++, this is the method SwitchFirewallState(EnumT firewallState) [AP_SWS_Fw_82008].

The rules themselves are contents of the manifest. The diagram of foundation requirements shows filter chains across multiple layers:

  • Ethernet with MAC addresses and EtherType,
  • IPv4,
  • TCP with state detection via flags or ICMP,
  • SOME/IP with service, method, and client ID RS Firewall p. 12.

At the transport layer, the manifest models a FirewallRule with the attributes bucketSize and refillAmount. In addition, there is a TransportLayerRule with port ranges and checksumVerification, which is specialized into UDP and TCP rules TPS Manifest p. 687.

If a packet matches none of the defined rules, the default action applies. The R23-11 version of the SWS additionally describes how the protocol layer of the mismatch is determined for a packet blocked in this way. The rule with the most consecutive matches, counted starting from the lowest network layer, is decisive. On the first non-matching layer, a layer-specific SEv is triggered SWS Firewall p. 31. This passage originates from R23-11 and is not covered in the payload by an R25-11 requirement. It is therefore to be read as an explanation, not as a normative requirement.

Activity diagram: Only the rules of the active firewall state are checked. If there is no match, the default action applies, and a blocked packet leads to a layer-specific SEv (representation according to R23-11). Sources: EXP PlatformDesign p. 92, SWS Firewall p. 31

From InstanceSpecifier to State Change

First, an application creates an instance of FirewallStateSwitchInterface. The explicit constructor, which expects an ara::core::InstanceSpecifier, serves this purpose. It is noexcept and specified as thread-safe [AP_SWS_Fw_82002]. Interpretation: The InstanceSpecifier likely designates the RPortPrototype of the application, which is typed in the manifest by FirewallStateSwitchInterface. The manifest diagram establishes precisely this port relationship, but does not name the specifier TPS Manifest p. 677.

SwitchFirewallState(EnumT firewallState) triggers the state change. The method is noexcept and returns a ara::core::Future<void> [AP_SWS_Fw_82008]. The \"Switch Firewall State\" scenario shows the sequence in three steps:

  1. The Adaptive Application calls SwitchFirewallState() on the FC Firewall.
  2. The FC Firewall calls applyRule() at the Operating System in a loop for each FirewallRule.
  3. After that, the response goes back to the application EXP SWArchitecture p. 232.

The R22-11 representation of the same scenario shows the same sequence EXP SWArchitecture p. 158. Because applyRule() is marked as «aapInformative», the loop describes the principle. It does not define a binding Operating System interface EXP SWArchitecture p. 232.

Sequence diagram: The application constructs the interface instance and requests the state change. The FC Firewall applies each rule, and the result is returned as ara::core::Future<void>. Sources: [AP_SWS_Fw_82002], [AP_SWS_Fw_82008], EXP SWArchitecture p. 232

Generated State Types and Manifest Connection

The permitted Firewall states do not form a fixed platform type. For each modeled interface, a dedicated enum class {<fwssi-sn>} : std::uint32_t is generated in the ara::fw::states namespace. It is included via ara/fw/states/{<fwssi-sn>}.h, and the enumerator list originates from the model [AP_SWS_Fw_81001]. For each modeled Firewall state, an enumerator of the form {<symbol-fw-state>} = {<fw-state-value>} [AP_SWS_Fw_81002] is generated. Interpretation: The parameter type EnumT of SwitchFirewallState likely represents this generated state type, since [AP_SWS_Fw_81001] explicitly defines it as the state type for FirewallStateSwitchInterface [AP_SWS_Fw_82008].

In the metamodel, FirewallStateSwitchInterface is a PortInterface. Via the role firewallStateMachine, it aggregates (0..*) elements of type ModeDeclarationGroupPrototype TPS Manifest p. 263. Presumably, the modes of this group provide the enumerators from [AP_SWS_Fw_81002]. However, the sources do not explicitly describe this mapping.

At machine level, AdaptiveFirewallModuleInstantiation collects the machine-specific settings of the Firewall (TPS_MANI_03296, status DRAFT). The metaclass AdaptiveFirewallToPortPrototypeMapping connects this instantiation via the reference firewall (0..1) to the RPortPrototype of the application TPS Manifest p. 677. In doing so, the note of this metaclass refers to a "FirewallModeSwitchInterface". In contrast, the diagram and API consistently use FirewallStateSwitchInterface TPS Manifest p. 677.

Lifecycle and Concurrency of the Interface Instance

An instance of FirewallStateSwitchInterface is non-copyable. Copy constructor and copy assignment are deleted [AP_SWS_Fw_82004] [AP_SWS_Fw_82005]. Moving, in contrast, is permitted, because move constructor and move assignment are noexcept [AP_SWS_Fw_82006] [AP_SWS_Fw_82007]. Thus, an instance can be transferred to another owner, but not duplicated.

Security Events to the Intrusion Detection System Manager

In addition to state switching, the Firewall supports the Intrusion Detection System. For blocked messages, a set of security events is specified that are reported to the IdsM. The IdsM handles their qualification and further processing. It forwards them to a SOC or persistently stores them on the ECU EXP PlatformDesign p. 92. The scenario "Report Security Event" connects Operating System, FC Firewall, and IdsM via the interactions packetBlocked(), handlePacketBlocked(), raiseSecurityEvent(), and ReportEvent(). Parts of it are marked as «aapInformative» EXP SWArchitecture p. 232.

For packets blocked by the Default Action, the R23-11 SWS specifies layer-specific events SWS Firewall p. 31:

  • SEV_FW_PACKET_BLOCKED_DATALINKLAYER_MISMATCH for Ethernet,
  • SEV_FW_PACKET_BLOCKED_IPV4_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_IPV6_MISMATCH,
  • SEV_FW_PACKET_BLOCKED_ICMP_MISMATCH.

These event names are not covered by R25-11 requirements in the payload. Their validity for R25-11 must be verified against the current SWS SWS Firewall p. 31.

Behavior in the event of an error

For SwitchFirewallState, two errors are specified: FwErrc::kServiceNotAvailable and FwErrc::kInvalidStateDependentFirewall [AP_SWS_Fw_82008]. Their values are defined by the enumeration FwErrc, namely kServiceNotAvailable=1 and kInvalidStateDependentFirewall=2 [AP_SWS_Fw_83001]. The method is noexcept and returns a ara::core::Future<void>. The caller therefore evaluates these errors via the future and not via an exception from the call [AP_SWS_Fw_82008].

Both errors belong to FwErrorDomain. The domain provides the following building blocks:

  • GetFwErrorDomain() returns a reference to the domain object; the function is constexpr and thread-safe [AP_SWS_Fw_83002].
  • MakeErrorCode creates a ara::core::ErrorCode from a FwErrc and additional data [AP_SWS_Fw_83003].
  • Name() and Message() return the name of the domain and the message text for a code; both are thread-safe [AP_SWS_Fw_83010] [AP_SWS_Fw_83011].
  • The aliases Errc and Exception refer to FwErrc and FwException [AP_SWS_Fw_83007] [AP_SWS_Fw_83008].

The default constructor of the domain is deleted, although its description reads "Constructs a new FwErrorDomain object" [AP_SWS_Fw_83009]. Access to the domain is therefore performed via GetFwErrorDomain().

To propagate an error as an exception, ThrowAsException is used. The function creates and throws a FwException. It is noexcept(false) and classified as "not exception safe" [AP_SWS_Fw_83012]. The exception itself is created via the explicit, thread-safe constructor FwException(ara::core::ErrorCode) [AP_SWS_Fw_83005].

At packet level, the error case is the blocking of a packet. Packets without a matching rule fall under the Default Action, and blocked messages are reported to the IdsM as security events EXP PlatformDesign p. 92. The interface in [AP_SWS_Fw_82008] does not provide a return channel to the application for such events. Their handling lies with the IdsM.
