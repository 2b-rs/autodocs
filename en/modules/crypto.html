Crypto Stack: standardized access to trust services

The Functional Cluster Cryptography provides applications and other functional clusters with a uniform API for cryptographic primitives, key management and certificate handling. The architecture allows different software or hardware implementations, such as libraries or HSMs, behind the same interface. SWS Cryptography §7.1.1 “Architecture”

A modeled access leads to a slot, a provider instance or the X.509 provider. Source: SWS Cryptography §7.1 “Architecture & Concepts”, SWS Cryptography §7.3 “Crypto Provider” and SWS Cryptography §7.5 “Certificate handling (X.509 Provider)”.

Provider, KeyStorage and X.509 as separate responsibilities

An CryptoProvider encapsulates transformations and associated key resources of a single implementation. Each key belongs to exactly one provider; key interoperability between different providers is deliberately unavailable. KeySlot resources are assigned to a provider at deployment time. By contrast, the machine-wide X509Provider manages persistent certificates as well as parsing and validation operations. SWS Cryptography §7.1.1 “Architecture” SWS Cryptography §7.3 “Crypto Provider” SWS Cryptography §7.5 “Certificate handling (X.509 Provider)”

Certificate storage and validation context are separate responsibilities of the X.509 area. Source: SWS Cryptography §7.5.2 “X.509 Certificate Validation” and SWS Cryptography §7.5.3 “X.509 Certificate Storage”.

Key and access concept

Persistent keys are loaded via modeled port interfaces and InstanceSpecifier. Client access allows use, a KeySlot interface additional modification; the manifest policy limits both to permitted processes. The usability of a runtime key is further limited via AllowedUsageFlags. Contexts: a calling pattern for primitives

The provider creates specialized contexts. Depending on the class, complete data can be processed via single call; The streaming path basically follows a configuration as well as Start(), one or more data calls and Finish(). The final authenticity decision for AEAD and signature checks is not anticipated ahead of time. SWS Cryptography §7.4 “Crypto Contexts”

Signing and verification follow the streaming pattern; the specific signature representation is determined by the API. Source: SWS Cryptography §7.4.5 “Digital signatures”.

Integration Guide

  1. Complete ara::core::Initialize before use and model the required provider, slot and certificate resources.
  2. For persistent material, use the appropriate slot and its rights; For temporary or keyless operations, load the provider directly.
  3. Check algorithm, key type, allowed usage and buffer sizes before calling the operation.
  4. handle return status; choose a suitable application strategy when resources are busy.
  5. Do not start new operations before ara::core::Deinitialize.
