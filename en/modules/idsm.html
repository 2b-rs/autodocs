The IdsM as the central sink for Security Events of the Adaptive Platform

The Intrusion Detection System Manager (IdsM) processes Security Events (SEv) reported by security sensors (SWS IdsM p. 9). On the Adaptive Platform, it is a daemon-based Functional Cluster. It provides the interface EventReporter, which is implemented as a class in ara::idsm ([SWS_AIDSM_10101], SWS IdsM p. 13).

There are two groups of users:

  • Platform clusters: Communication Management, Firewall, and Diagnostic Management report their events via EventReporter (EXP SWArchitecture p. 124, SWS Firewall p. 11, SWS Diagnostics p. 67, SWS CM p. 34).
  • Adaptive Applications: They additionally use ReportingModeProvider (EXP SWArchitecture p. 121). Via TimestampProvider and ContextDataProvider, they provide data (EXP SWArchitecture p. 122). Via QualifiedEventsReceiver, they receive qualified events (EXP SWArchitecture p. 123).

All associated port interfaces derive from IdsmAbstractPortInterface in the manifest metamodel (TPS Manifest p. 257).

The system boundary is tightly drawn. The IdsM does not know the meaning of the context data and therefore cannot judge for itself whether a system is compromised. Detection and response lie outside, for instance in a SOC (SWS IdsM p. 11, status R20-11).

This status warrants a note. Several document sections from R20-11 indeed bear the AP document identifier. However, according to their own introduction, they cover only aspects of the Classic Platform (SWS IdsM p. 10). This guide therefore only consults them for clarification of terms.

Context diagram: The IdsM is used by platform clusters and Adaptive Applications and in turn invokes callbacks of the applications. Sources: EXP SWArchitecture p. 121, p. 122, p. 123, p. 124

Reporting Security Events: EventReporter, overloads, and data types

A reporter is constructed with an InstanceSpecifier for the modeled SecurityEventReportInterface port ([SWS_AIDSM_10301]). ReportEvent has no event ID parameter. Which SEv is reported is defined by the model: SecurityEventReportToSecurityEventDefinitionMapping assigns the port to an SecurityEventDefinition of the Security Extract. This assignment can also be added in a project-specific or OEM-specific manner (TPS Manifest p. 146). For Functional Clusters, FunctionalClusterToSecurityEventDefinitionMapping assumes this role (TPS Manifest p. 873).

All overloads are noexcept and thread-safe ([SWS_AIDSM_10302]–[SWS_AIDSM_10307]). Overview of the data types:

  • ContextDataType is a ara::core::Span<const std::uint8_t> ([SWS_AIDSM_10201]).
  • VersionedContextDataType pairs this data with an std::uint16_t ([SWS_AIDSM_10206]).
  • TimestampType is std::uint64_t ([SWS_AIDSM_10202]).
  • CountType counts already pre-qualified occurrences and has the default value 1 ([SWS_AIDSM_10203]).

The protocol provides a 4-byte length field for long context data. This allows up to 231−1 bytes to be transmitted (PRS IDS p. 23). Interpretation: The version portion is likely to correspond to the version of a SecurityEventContextDataDefinition, as suggested by the example with version = 1 (TPS SecXT p. 66).

A typical sequence is the Firewall scenario: The operating system blocks a packet, the Firewall converts it into a Security Event and reports it via ReportEvent() (EXP SWArchitecture p. 232). Platform Health Management also calls ReportEvent(), specifically as part of an access check during checkpoint reporting (EXP SWArchitecture p. 236).

Sequence diagram: From the blocked packet to the report to the IdsM; the report itself receives no return value. Sources: EXP SWArchitecture p. 232, [SWS_AIDSM_10302]

Enriching reports: TimestampProvider and ContextDataProvider

During enrichment, the call direction is reversed: The application is the provider, and the IdsM calls its callbacks (EXP SWArchitecture p. 122).

  • TimestampProvider ([SWS_AIDSM_10400]) is created with a InstanceSpecifier ([SWS_AIDSM_10401]). The application implements the abstract callback GetTimestamp() ([SWS_AIDSM_10407]). Offer() allows the IdsM to call it; StopOffer() disables this again ([SWS_AIDSM_10408], [SWS_AIDSM_10409]).
  • ContextDataProvider ([SWS_AIDSM_10500]) additionally receives additionalBytes and originalContextDataOffset in the constructor ([SWS_AIDSM_10501]). The IdsM calls ModifyContextData(contextData, event), which provides a Result<std::size_t> ([SWS_AIDSM_10509]). Here, too, Offer() and StopOffer() control the calls ([SWS_AIDSM_10507], [SWS_AIDSM_10508]).

Both providers cannot be copied, but can be moved ([SWS_AIDSM_10404], [SWS_AIDSM_10403], [SWS_AIDSM_10504], [SWS_AIDSM_10503]). The constructors are thread-safe. In contrast, Offer(), StopOffer(), and the callbacks are not ([SWS_AIDSM_10408], [SWS_AIDSM_10407], [SWS_AIDSM_10509]).

State diagram: Callbacks of the providers and receivers are enabled only between Offer() and StopOffer(). Sources: [SWS_AIDSM_10408], [SWS_AIDSM_10409], [SWS_AIDSM_10507], [SWS_AIDSM_10508], [SWS_AIDSM_10808], [SWS_AIDSM_10809], [SWS_AIDSM_10402]

When the IdsM calls GetTimestamp() is not specified by the R25-11 requirements in the payload. Interpretation: This presumably happens when an SEv is reported without a timestamp. This is how the R20-11 text of the Classic Platform describes it for the "Custom" option (SWS IdsM p. 34).

Sequence diagram: Providing, using, and withdrawing the enrichment callbacks. The trigger of GetTimestamp() is an interpretation, and the order of the two optional callbacks is not specified. Sources: EXP SWArchitecture p. 122, [SWS_AIDSM_10407], [SWS_AIDSM_10509], SWS IdsM p. 34

Reporting modes and filter chain: how an SEv becomes a QSEv

ReportingModeType has five values ([SWS_AIDSM_10207]). Their meaning is documented (SWS IdsM p. 91):

  • kOff: The SEv is discarded.
  • kBrief: The SEv is forwarded without context data.
  • kDetailed: The SEv is forwarded with context data.
  • kBriefBypassingFilters and kDetailedBypassingFilters: like kBrief and kDetailed, respectively, but bypassing the rest of the filter chain.

The final class ReportingModeProvider ([SWS_AIDSM_10600], [SWS_AIDSM_10601]) reads and sets the mode per event ID. GetReportingMode() and SetReportingMode() serve this purpose; neither is thread-safe ([SWS_AIDSM_10602], [SWS_AIDSM_10603]).

Sequence diagram: Querying and changing the reporting mode, including the error case for an unknown event ID. Sources: [SWS_AIDSM_10601], [SWS_AIDSM_10602], [SWS_AIDSM_10603], [SWS_AIDSM_10204]

The Security Extract models the filter chain SecurityEventFilterChain with respective optional filters (TPS SecXT p. 21):

  • state
  • oneEveryN with the parameter n
  • aggregation with contextDataSource and minimumIntervalLength
  • threshold with intervalLength and thresholdNumber

SecurityEventContextMapping connects events with filter chain and reporting mode. On the Adaptive Platform, this is done via IdsmModuleInstantiation (TPS SecXT p. 33). Interpretation: The evaluation order likely corresponds to the R20-11 description of the Classic Platform. According to this, the reporting mode comes first, then the filters in model order, and the chain aborts upon the first discard (SWS IdsM p. 25).

Activity diagram: The reporting mode decides on discard, filter chain, or bypass. The filter order is an interpretation, and unconfigured filters are omitted. Sources: [SWS_AIDSM_10207], SWS IdsM p. 91, TPS SecXT p. 21, SWS IdsM p. 25

Receiving qualified events: QualifiedEventsReceiver

Applications derive from QualifiedEventsReceiver ([SWS_AIDSM_10800], [SWS_AIDSM_10801]). They must implement both pure virtual overloads of OnEventQualification(): one with unversioned and one with versioned context data. Context data and timestamps each arrive as ara::core::Optional ([SWS_AIDSM_10807], [SWS_AIDSM_10810]). The IdsM calls these callbacks (EXP SWArchitecture p. 123). Offer() enables the calls, StopOffer() terminates them ([SWS_AIDSM_10808], [SWS_AIDSM_10809]). The callback is not thread-safe.

Sequence diagram: Lifecycle of a receiver of qualified events. Sources: [SWS_AIDSM_10801], [SWS_AIDSM_10807], [SWS_AIDSM_10808], [SWS_AIDSM_10809], EXP SWArchitecture p. 123

Instance reference: InstanceSpecifier and manifest mappings

Each API class is bound to its modeled port via an InstanceSpecifier ([SWS_AIDSM_10301], [SWS_AIDSM_10401], [SWS_AIDSM_10501], [SWS_AIDSM_10601], [SWS_AIDSM_10801]). In deployment, four mappings describe this binding. All are UploadableDeploymentElements (TPS Manifest p. 881):

  • IdsmTimestampProviderMapping references idsPlatformInstantiation, pPortPrototypeInExecutable, and process (TPS Manifest p. 664).
  • IdsmContextProviderMapping (TPS Manifest S. 665)
  • IdsmReportingModeProviderMapping (TPS Manifest S. 667)
  • IdsmQualifiedEventReceiverMapping (TPS Manifest S. 669)

The IdsM instance itself has idsmInstanceId and timestampFormat (TPS SecXT p. 59).

Discrepancy between requirements and manifest diagrams: [SWS_AIDSM_10601] and [SWS_AIDSM_10801] speak of the "modeled PPort". By contrast, the manifest diagrams reference an RPortPrototype for reporting mode provider and qualified event receiver (TPS Manifest p. 667, p. 669). The requirements are normative; this difference should be clarified during integration.

Context diagram: The manifest mappings connect the IdsM platform instance, process, and port; the reporting ports are additionally mapped to an SecurityEventDefinition. Sources: TPS Manifest p. 664, p. 665, p. 667, p. 669, p. 146

Behavior in the event of an error

The only specified error code is IdsmErrc::kUnknownEventId with the value 3 ([SWS_AIDSM_10204]). GetReportingMode() and SetReportingMode() return it for event IDs that are not configured ([SWS_AIDSM_10602], [SWS_AIDSM_10603]). The surrounding error infrastructure consists of:

  • IdsmErrorDomain ([SWS_AIDSM_10706]), accessible via GetIdsmErrorDomain() ([SWS_AIDSM_10702])
  • MakeErrorCode() ([SWS_AIDSM_10703])
  • IdsmException ([SWS_AIDSM_10704], [SWS_AIDSM_10705])
  • ThrowAsException() ([SWS_AIDSM_10712])

ReportEvent() is void and noexcept; the sensor therefore receives no feedback regarding acceptance or discard ([SWS_AIDSM_10302], [SWS_AIDSM_10307]). According to R20-11, it is explicitly acceptable that SEvs are discarded depending on reporting frequency, criticality, or system overload (SWS IdsM p. 11).

The results of Offer() are to be evaluated as Result<void>; StopOffer() returns nothing ([SWS_AIDSM_10408], [SWS_AIDSM_10507], [SWS_AIDSM_10808], [SWS_AIDSM_10809]). ModifyContextData() can report an error via Result<std::size_t> ([SWS_AIDSM_10509]). How the IdsM reacts to this is not described in the payload. Operations that are not thread-safe must be serialized by the application itself.
