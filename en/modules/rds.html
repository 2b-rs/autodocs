Role of ara::rds: Raw data streams alongside service communication

The Functional Cluster Raw Data Stream gives Adaptive Applications direct access to unstructured binary data streams. The architectural view presents it as an alternative to typed, service-oriented communication, intended for bandwidth-intensive payloads (EXP SWArchitecture p. 73). In release R25-11, the module comprises two families of endpoints:

  • the IP-based classes RawDataStreamClient and RawDataStreamServer in header ara/rds/raw_data_stream.h ([SWS_RDS_10482], [SWS_RDS_11312]),
  • the IEEE 1722 classes IEEE1722RawDataStreamConsumer and IEEE1722RawDataStreamProducer in ara/rds/raw_data_stream_IEEE1722.h ([SWS_RDS_90312], [SWS_RDS_90323]).

Both families map errors uniformly via ara/rds/rds_error_domain.h ([SWS_RDS_12367]).

The logical view draws the system boundary below the endpoints. Client and server build on a TLS library and a socket/IPsec library located on the Adaptive AUTOSAR Foundation (SWS RDS p. 26). For IEEE 1722, a data link layer socket takes this place (SWS RDS p. 36). The application uses each of these interfaces via an «aapRequiredPort» (EXP SWArchitecture p. 73, EXP SWArchitecture p. 74). The diagram on SWS RDS p. 36 incorrectly labels the producer as IEEE7122RawDataStreamProducer. The normative class name is IEEE1722RawDataStreamProducer ([SWS_RDS_90323]).

Compared to older releases, the namespace has shifted. In SWS CM (R19-11 to R22-11), the classes were located in ara::com::raw (SWS CM p. 58). In R25-11, they belong to ara::rds ([SWS_RDS_10482], [SWS_RDS_11312]).

Context diagram: Via the four ara::rds endpoints, the Adaptive Application reaches the libraries or the data link layer socket, and below them the Foundation. Sources: SWS RDS p. 26, SWS RDS p. 36, EXP SWArchitecture p. 73, EXP SWArchitecture p. 74

Instance reference: from the modeled port to the endpoint

Each of the four endpoint types is created via the static factory function Create(const ara::core::InstanceSpecifier &instance). It returns a ara::core::Result with the object ([SWS_RDS_10482], [SWS_RDS_11312], [SWS_RDS_90312], [SWS_RDS_90323]). For client and server, a “modeled port” is explicitly mentioned, and both factory functions are marked as thread-safe. For consumer and producer, the payload contains no information on thread safety.

On the manifest side, RawDataStreamClientInterface and RawDataStreamServerInterface specialize the abstract AbstractRawDataStreamInterface (AP TPS Manifest p. 254). The IEEE 1722 interfaces are attached to this hierarchy via MacLayerRawDataStreamInterface (AP TPS Manifest p. 180; diagram from R24-11). In deployment, a RawDataStreamMapping links the RPortPrototype to an Process. EthernetMacRawDataStreamMapping supplements socket options for this (AP TPS Manifest p. 854).

Older documents from R21-11 and R22-11 describe further details:

  • IP configurations with remoteServerConfig and remoteClientConfig (TPS Manifest p. 656),
  • the use cases 1:1 TCP, 1:1 UDP, and 1:N UDP multicast (SWS CM p. 60).

The payload does not substantiate whether these elements apply unchanged in R25-11. In addition, the old diagrams name the operations Read() and Write(), whereas R25-11 defines ReadData and WriteData ([SWS_RDS_10486], [SWS_RDS_10487]).

Context diagram: The InstanceSpecifier designates a modeled port. Its PortInterface and deployment mapping determine the characteristics of the endpoint. Interpretation: The specialization of RawDataStreamMapping by EthernetMacRawDataStreamMapping is derived from the abridged diagram. Sources: [SWS_RDS_10482], AP TPS Manifest p. 254, AP TPS Manifest p. 180, AP TPS Manifest p. 854

Connection establishment and data exchange via IP

The IP roles are asymmetric. The server waits for a client using WaitForConnection() ([SWS_RDS_11318]), while the client establishes the connection using Connect() ([SWS_RDS_10484]). After that, both sides can read and write ([SWS_RDS_10486], [SWS_RDS_10487], [SWS_RDS_11322], [SWS_RDS_11324]). The R25-11 diagram shows precisely this connection establishment with bidirectional exchange (SWS RDS p. 10).

The scenarios of the architecture description additionally show TCP handshake (SYN, SYN-ACK, ACK) and connection termination (FIN, ACK). These messages are marked as «aapInformative», i.e., an illustration of an exemplary transport and not an API requirement (EXP SWArchitecture p. 204, EXP SWArchitecture p. 222). The connection is terminated on both sides with Shutdown() ([SWS_RDS_10485], [SWS_RDS_11320]).

The interface itself has also changed. The interface diagram for R21-11 to R23-11 does not yet list Create() (EXP SWArchitecture p. 61). As of R24-11, it is included (EXP SWArchitecture p. 73), which matches [SWS_RDS_10482].

Sequence diagram: Creation, connection establishment, bidirectional data exchange, and termination between client and server; the TCP messages are informative only. Sources: SWS RDS p. 10, EXP SWArchitecture p. 204, EXP SWArchitecture p. 222, [SWS_RDS_10484], [SWS_RDS_11318], [SWS_RDS_11320]

IEEE 1722 streams: Producer, consumer, and datagram types

IEEE 1722 endpoints do not have client/server roles, but rather the receive and transmit directions:

  • The consumer provides Connect(), ReadData(), and Shutdown() ([SWS_RDS_90319], [SWS_RDS_90321], [SWS_RDS_90320]).
  • The producer provides Connect(), WriteData(), and Shutdown() ([SWS_RDS_90330], [SWS_RDS_90332], [SWS_RDS_90331]).

The scenarios each show the sequence Create, Connect, loop, Shutdown (EXP SWArchitecture p. 203, EXP SWArchitecture p. 221).

Entire datagrams are transmitted instead of bytes. ReadData(std::size_t maxNumberOfDatagrams) returns ara::core::Result<std::vector<T>> ([SWS_RDS_90321]), and WriteData(std::vector<T> data) sends such elements ([SWS_RDS_90332]). Interpretation: T is likely one of the datagram classes of the header.

The datagram classes build upon each other (SWS RDS p. 39):

  • IEEE1722Datagram contains data and stream_data_length ([SWS_RDS_90226], [SWS_RDS_90227]).
  • IEEE1722DatagramAVTPDUCommonHeaderFields adds avtpStreamDataSubtype, headerSpecific, and version ([SWS_RDS_90230], [SWS_RDS_90231], [SWS_RDS_90232]).
  • IEEE1722DatagramAVTPDUCommonStreamHeaderFields introduces optional fields, such as avtp_timestamp as ara::tsync::Timestamp ([SWS_RDS_90237]).
  • Below these are the subtype classes 61883_IIDC, AAF, TSCF, RVF, CRF, and NTSCF ([SWS_RDS_90260], [SWS_RDS_90273], [SWS_RDS_90275], [SWS_RDS_90292], [SWS_RDS_90304], [SWS_RDS_90310]).

The fields are consistently protected. IEEE1722DatagramRVF is final and inherits protected from the stream header fields ([SWS_RDS_90276]).

Curation note: In several field entries, the heading and declaration deviate from each other. Examples are unique_id versus declared mac_address in [SWS_RDS_90235], line_number versus num_lines in [SWS_RDS_90289], and syt versus tcode in [SWS_RDS_90246]. Before use, the declaration in the header should therefore be checked.

Sequence diagram: Producer and consumer independently go through Create, Connect, a data loop, and Shutdown. A coupling of both sides is not modeled in the payload. Sources: EXP SWArchitecture p. 221, EXP SWArchitecture p. 203, [SWS_RDS_90321], [SWS_RDS_90332]

Buffers, lengths, and time limits

During IP reading, ReadData returns a ReadDataResult. It contains the buffer data as std::unique_ptr<ara::core::Byte[]> and the number of valid bytes in numberOfBytes ([SWS_RDS_11301], [SWS_RDS_11302]). The buffer thus belongs to the caller. When writing, the buffer is passed by value as std::unique_ptr, so ownership is transferred to the call ([SWS_RDS_10487], [SWS_RDS_11324]). Interpretation: maxLength likely specifies the upper limit when reading and the length of the buffer in bytes when writing.

Every IP operation that can wait has an overload with std::chrono::milliseconds timeout:

  • Connect ([SWS_RDS_11307]),
  • WaitForConnection ([SWS_RDS_11319]),
  • ReadData ([SWS_RDS_11309], [SWS_RDS_11323]),
  • WriteData ([SWS_RDS_11310], [SWS_RDS_11325]).

The variants without timeout presumably wait indefinitely. The payload does not state which RdsErrc value is reported upon expiration of the time limit ([SWS_RDS_12367]). For the IEEE 1722 endpoints, it contains no timeout overloads ([SWS_RDS_90319], [SWS_RDS_90321], [SWS_RDS_90332]).

Lifecycle, ownership, and concurrency

All destructors terminate an open connection ([SWS_RDS_10483], [SWS_RDS_11313], [SWS_RDS_90318], [SWS_RDS_90329]). Since a destructor has no return value, it cannot report errors. Only explicit Shutdown() returns a verifiable Result<void> ([SWS_RDS_10485], [SWS_RDS_11320], [SWS_RDS_90320], [SWS_RDS_90331]).

Endpoints can only be moved, not copied. The copy constructor and copy assignment operator are deleted ([SWS_RDS_11303], [SWS_RDS_11304], [SWS_RDS_11316], [SWS_RDS_11317], [SWS_RDS_90316], [SWS_RDS_90317], [SWS_RDS_90327], [SWS_RDS_90328]). The move constructor and move assignment operator are noexcept. The assignment is &-qualified and therefore only applicable to lvalues ([SWS_RDS_11305], [SWS_RDS_11306], [SWS_RDS_11314], [SWS_RDS_11315], [SWS_RDS_90314], [SWS_RDS_90315], [SWS_RDS_90324], [SWS_RDS_90326]).

Regarding concurrency, the following applies:

  • Create of client and server is thread-safe ([SWS_RDS_10482], [SWS_RDS_11312]).
  • Destructors and move operations are explicitly not thread-safe ([SWS_RDS_10483], [SWS_RDS_11305], [SWS_RDS_90318]).
  • The payload contains no information for Connect, ReadData, WriteData, and Shutdown. Concurrent accesses to the same object must therefore be clarified prior to use.

State diagram: An endpoint is created, connected, used for data transfer, and terminated via Shutdown or destructor. Interpretation: The states and the rule “transfer only after connection establishment” are derived from the order of the scenarios. Sources: SWS RDS p. 10, EXP SWArchitecture p. 203, [SWS_RDS_10483], [SWS_RDS_10485]

Behavior in the event of an error

All operations are noexcept and report errors via ara::core::Result. For Connect(), the error enumeration RdsErrc is explicitly mentioned ([SWS_RDS_10484]). If Create already fails, no endpoint is created. The Result must therefore be checked before any further use ([SWS_RDS_10482]).

The error domain consists of the following building blocks:

  • RdsErrorDomain is not default-constructible ([SWS_RDS_11294]). Access is performed via GetRdsErrorDomain() ([SWS_RDS_11298]).
  • The domain provides readable texts via Name() and Message() ([SWS_RDS_11295], [SWS_RDS_11296]).
  • It defines the aliases Errc and Exception ([SWS_RDS_11326], [SWS_RDS_11327]).
  • MakeErrorCode creates error codes for this domain ([SWS_RDS_11299]).

For exception-based handling, ThrowAsException throws a RdsException that encapsulates a ErrorCode ([SWS_RDS_11297], [SWS_RDS_11292]). The individual values of RdsErrc are not listed in the payload ([SWS_RDS_12367]); therefore, this guide does not name any specific codes.

Activity diagram: A Result returns either a value or an ErrorCode of the RDS domain. The application evaluates this in a code-based manner or converts it into an RdsException. Sources: [SWS_RDS_10484], [SWS_RDS_11296], [SWS_RDS_11297], [SWS_RDS_11298], [SWS_RDS_11299]
