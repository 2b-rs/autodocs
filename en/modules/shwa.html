Role of Safe Hardware Acceleration and Boundary to the Application Process

Safe Hardware Acceleration (SHWA, namespace ara::shwa) makes hardware acceleration usable in a standardized and portable manner for safe and efficient computations SWS SHWA p. 4. According to the functional overview, SHWA provides APIs for Adaptive Applications and other Functional Clusters. The cluster covers three tasks:

  • executing compute-intensive work in parallel on the hardware accelerator (HWA),
  • detecting and correcting errors of the tasks running there,
  • monitoring the operating states of the accelerators SWS SHWA p. 7.

The requirements of the cluster are intended to take the AUTOSAR safety requirements into account SWS SHWA p. 5.

The architecture overview assigns SHWA to the Safety category. Unlike Platform Health Management, SHWA is not marked there as daemon-based EXP SW-Architektur p. 127. The interfaces are native C++ interfaces directly used by an Adaptive Application EXP SW-Architektur p. 132. Other Functional Clusters can also use SHWA without the involvement of an Adaptive Application. Their library part uses its own deployment information for this purpose; their daemons are modeled like Adaptive Applications SWS SHWA p. 23.

On the hardware side, Device distinguishes the type of execution unit via IsCpu, IsGpu, and IsAccelerator [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00311] [AP_SWS_SHWA_00312]. The enumeration Target names two execution locations: kDevice for the device or accelerator, respectively, and kHostTask for the host CPU [AP_SWS_SHWA_00102].

Context diagram: Adaptive Applications and other Functional Clusters use SHWA as a native interface; SHWA connects CPU, GPU, and accelerators. Sources: SWS SHWA p. 23, EXP SW-Architektur p. 127, [AP_SWS_SHWA_00310]

Four Interface Areas of ara::shwa

The diagram of the specification divides the API into four areas: data management, task execution, device management and monitoring, as well as error handling SWS SHWA p. 17. The API explanation describes the first three areas as layers EXP SHWA-API p. 15.

  • Data management: Range and Id describe one- to three-dimensional sizes and indices [AP_SWS_SHWA_01009] [AP_SWS_SHWA_00709]. In addition, there are Buffer [AP_SWS_SHWA_00209], Accessor [AP_SWS_SHWA_00007], and PropertyList [AP_SWS_SHWA_00802].
  • Task execution: Queue [AP_SWS_SHWA_00908], TaskHandler [AP_SWS_SHWA_01202], and Event [AP_SWS_SHWA_00602].
  • Device management and monitoring: Platform [AP_SWS_SHWA_01107] and Device [AP_SWS_SHWA_00308]. In addition, there is DeviceSelector with GpuSelector, CpuSelector, and AcceleratorSelector [AP_SWS_SHWA_00403] [AP_SWS_SHWA_00407] [AP_SWS_SHWA_00410] [AP_SWS_SHWA_00413] as well as DeviceMonitor [AP_SWS_SHWA_01407].
  • Error handling: ErrorHandler [AP_SWS_SHWA_00507], ShwaErrorCode [AP_SWS_SHWA_01301], ShwaErrorDomain [AP_SWS_SHWA_01307], and ShwaException [AP_SWS_SHWA_01303].

An application may combine multiple queues, devices, and buffers. The same applies to other Functional Clusters SWS SHWA p. 22. The associated diagram shows two independent groups. Each group consists of a queue with multiple tasks, buffers, and a device SWS SHWA p. 23.

Collaboration diagram: How the central classes are interrelated across the areas: The queue is bound to a device, Submit provides an event, and the accessor accesses a buffer. Sources: SWS SHWA p. 17, [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01407]

From Device to Queue: Selection and Setup

A device can be determined in three ways:

  1. Enumeration: Platform::GetPlatforms provides the available platforms, GetDevices their devices [AP_SWS_SHWA_01107] [AP_SWS_SHWA_01108].
  2. Without argument: Device::Create() [AP_SWS_SHWA_00308].
  3. Via a selector: Device::Create(deviceSelector) [AP_SWS_SHWA_00309].

A DeviceSelector evaluates a device with operator() and returns a Result<int> for it. SelectDevice returns the selected device [AP_SWS_SHWA_00404] [AP_SWS_SHWA_00403]. GetInfo<InfoType> reads further information about the device from [AP_SWS_SHWA_00313].

The queue is created either directly from a selector or from a concrete device. In both variants, a ErrorHandler is a mandatory parameter; an PropertyList is optional [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00909]. GetDevice returns the bound device. IsInOrder indicates whether the tasks of the queue are executed in order [AP_SWS_SHWA_00910] [AP_SWS_SHWA_00911] EXP SW-Architektur p. 133.

Activity diagram: Three paths lead to the device, two factories to the queue; each result is checked as Result. Sources: [AP_SWS_SHWA_01107], [AP_SWS_SHWA_00308], [AP_SWS_SHWA_00309], [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]

Providing Data and Submitting Tasks

Range describes sizes with one to three dimensions [AP_SWS_SHWA_01007] [AP_SWS_SHWA_01009]. Buffer::Create exists in several variants [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00210] [AP_SWS_SHWA_00212] [AP_SWS_SHWA_00211] [AP_SWS_SHWA_00213] [AP_SWS_SHWA_00214]:

  • with range only,
  • with range and additional allocator,
  • with allocator only,
  • with mutable or constant host data.

An Accessor accesses a buffer. It is created with or without TaskHandler [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00008]. It provides operator[] with Id or a linear index [AP_SWS_SHWA_00009] [AP_SWS_SHWA_00010]. Furthermore, it provides Set and Get with Result return [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012]. Access depends on the AccessMode with the values kRead, kWrite, and kReadWrite. For kRead, ReferenceT is a constant reference [AP_SWS_SHWA_00101] [AP_SWS_SHWA_00014].

Queue::Submit(cfg, ErrorHandler&&) submits a task and returns an Event [AP_SWS_SHWA_00912]. The TaskHandler provides two execution forms: SingleTask for a single task and ParallelFor(bufferSize, cfg) for data-parallel execution [AP_SWS_SHWA_01203] [AP_SWS_SHWA_01204]. The use case diagram specifies "Single Instructions on Multiple Data" and "Multiple Instructions on Multiple Data" as usage scenarios EXP SW-Architektur p. 203.

Interpretation: cfg is likely a callable configuration. It presumably receives the TaskHandler, creates accessors in it, and calls SingleTask or ParallelFor. This is suggested by the accessor factory with TaskHandler parameter [AP_SWS_SHWA_00008].

Sequence diagram: Data is provided, a data-parallel task is submitted, and its completion is awaited. The call to cfg is marked as an interpretation. Sources: [AP_SWS_SHWA_01007], [AP_SWS_SHWA_00211], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00008], [AP_SWS_SHWA_01204], [AP_SWS_SHWA_00604]

Synchronization via Events and Wait Functions of the Queue

Each Submit returns an Event [AP_SWS_SHWA_00912]. At event level, there are three wait functions [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00605] [AP_SWS_SHWA_00606]:

  • Event::Wait() waits for the completion of the associated tasks.
  • The static variant with an event list waits for multiple events.
  • WaitFor(ms) limits the waiting time.

GetWaitList returns a list of events [AP_SWS_SHWA_00603]. At queue level, Wait() waits blocking for all queued tasks, WaitFor(ms) does the same with a time limit [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] EXP SW-Architektur p. 133.

The requirements specify thread safety for each function individually:

  • Thread-safe: Queue::Create, Accessor::Create, Range::Create as well as Accessor::Set and Get [AP_SWS_SHWA_00908] [AP_SWS_SHWA_00007] [AP_SWS_SHWA_01007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00012].
  • Not thread-safe: Queue::Submit, Queue::Wait, Event::Wait, Device::Create, and Accessor::operator[] [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00604] [AP_SWS_SHWA_00308] [AP_SWS_SHWA_00009].
  • Differences within a class: Buffer::Create is thread-safe, whereas the variant with allocator only is not [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00212].

A second Submit variant accepts an secondaryQueue instead of the ErrorHandler [AP_SWS_SHWA_00913]. Interpretation: This queue is likely to serve as a fallback queue if execution on the primary queue fails. The variant is traced back to the same upstream requirement as the ErrorHandler [AP_SWS_SHWA_00507].

Sequence diagram: Two queues operate independently; the application synchronizes via event lists or the wait functions of the queue. Sources: [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00605], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917], SWS SHWA p. 22

Object Ownership, Properties, and Device State

Three design rules apply to all classes EXP SHWA-API p. 15:

  • Constructors are private; objects are created via named Create() methods.
  • Classes that own data provide std::unique_ptr.
  • Most return values are encapsulated in ara::core::Result.

An R23-11 version of the explanation still specified ara::com::SamplePtr at this point EXP Safe-API HWA p. 15. The requirements are authoritative for R25-11, and they specify std::unique_ptr [AP_SWS_SHWA_00209] [AP_SWS_SHWA_00908].

Properties are passed as PropertyList during creation [AP_SWS_SHWA_00802]. On Buffer, Accessor, and Queue, HasProperty checks whether a property is present; GetProperty reads it. GetProperty reports unsupported properties with kFeatureNotSupported [AP_SWS_SHWA_00215] [AP_SWS_SHWA_00216] [AP_SWS_SHWA_00015] [AP_SWS_SHWA_00016] [AP_SWS_SHWA_00915] [AP_SWS_SHWA_00916]. The available sources do not specify in detail which deployment information Functional Clusters use for SHWA SWS SHWA p. 23.

For monitoring, a DeviceMonitor is created from a device or a selector [AP_SWS_SHWA_01407] [AP_SWS_SHWA_01408]. Status() returns a DeviceStatus with one of these values [AP_SWS_SHWA_01409] [AP_SWS_SHWA_00103]:

  • kReady: ready for task execution,
  • kNotAccesible: not accessible,
  • kFailure: error state,
  • kUnknown: status cannot be determined.

Whether this status is forwarded to other Functional Clusters is not specified by the available sources.

Activity diagram: The status is queried via the DeviceMonitor and branched according to DeviceStatus; the reaction to values other than kReady is an interpretation. Sources: [AP_SWS_SHWA_01407], [AP_SWS_SHWA_01409], [AP_SWS_SHWA_00103]

Behavior in the event of an error

SHWA reports errors via ara::core::Result with codes from ShwaErrorCode. These include kRuntime, kTaskExecutionFailure, kMemoryNotAllocated, kIntegrityCorrupted (integrity of a buffer memory cannot be established), kResourceBusy, and kInvalidAccessMode [AP_SWS_SHWA_01301]. Individual functions specify further codes: kAccessorFailure, kInvalidIndex, kFeatureNotSupported, and kEventInvalidOperation [AP_SWS_SHWA_00007] [AP_SWS_SHWA_00011] [AP_SWS_SHWA_00313] [AP_SWS_SHWA_00603].

The domain ShwaErrorDomain provides Name, Message, and ThrowAsException. GetShwaDomain and MakeErrorCode associate the codes with the domain. ShwaException transports a code as an exception [AP_SWS_SHWA_01308] [AP_SWS_SHWA_01309] [AP_SWS_SHWA_01310] [AP_SWS_SHWA_01311] [AP_SWS_SHWA_01312] [AP_SWS_SHWA_01303].

Errors during execution and waiting have particularly serious consequences. If Submit, Queue::Wait, Queue::WaitFor, or Event::Wait report the code kRuntime, the data of the failed task must be considered inadvertently modified. For Event::Wait, this also applies to kTaskExecutionFailure [AP_SWS_SHWA_00912] [AP_SWS_SHWA_00914] [AP_SWS_SHWA_00917] [AP_SWS_SHWA_00604]. The error specifications of Submit bear the label no_rollback_semantics [AP_SWS_SHWA_00912].

Occupied resources are reported, among others, by the device queries and Accessor::Get with kResourceBusy [AP_SWS_SHWA_00310] [AP_SWS_SHWA_00012]. A failed allocation is reported by Buffer::Create with kMemoryNotAllocated [AP_SWS_SHWA_00212].

A ErrorHandler encapsulates a function std::function<void(ara::core::ErrorCode)> [AP_SWS_SHWA_00507]. HandleError(ShwaErrorCode) executes the handling and is not thread-safe [AP_SWS_SHWA_00508]. Each queue receives an ErrorHandler upon creation [AP_SWS_SHWA_00908]. Interpretation: The implementation is likely to report errors of submitted tasks via HandleError that are not immediately available as a return value of Submit; the sources do not specify who calls HandleError. At the device level, DeviceStatus::kFailure indicates an error state [AP_SWS_SHWA_00103].

Activity diagram: A Result is evaluated and the SHWA error codes are classified, including the consequences for the data in case of task errors. Sources: [AP_SWS_SHWA_01301], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00604], [AP_SWS_SHWA_01310], [AP_SWS_SHWA_00508]
