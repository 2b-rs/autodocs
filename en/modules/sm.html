Role of State Management and Distinction from Execution Management

State Management determines the operational state of the platform. Execution Management executes the transitions between the states (SWS EM p. 51). From application-specific inputs, State Management derives the target set of active Function Group States. It requests their switching from Execution Management via the StateClient API (EXP SWArch p. 50; SWS SM p. 40). The StateMachine approach is optional. It relocates project-specific arbitration into a SMControlApplication, which requests only configured transitions (SWS SM p. 28; SWS SM p. 42).

State Management provides the following ara::com services:

  • UpdateRequest for Update and Configuration Management ([SWS_SM_91102]).
  • StateMachineService and UpdateAllowedService for the SMControlApplication ([SWS_SM_91107], [SWS_SM_91108]).
  • StateMachineNotification::CurrentState for arbitrary Adaptive Applications ([SWS_SM_91109]).

For Suspend-to-RAM, S2RHub and S2RSatellite are added, and for the operating system, the platform extension PowerStateInterface (EXP SWArch p. 51; SWS SM p. 163). For its part, State Management requires interfaces from Execution Management, Platform Health Management, and Network Management (SWS SM p. 17; EXP SWArch p. 77).

Context diagram: State Management is positioned between controlling applications, platform clusters, and the operating system. Sources: SWS SM p. 16, EXP SWArch p. 51, EXP SWArch p. 52, [SWS_SM_71001]

From Machine Startup to the Controller StateMachine

The operating system starts Execution Management as the first process. Execution Management activates the machine Function Group State Startup, and State Management must be part of this state (EXP SWArch p. 216). The result of this self-initiated transition is returned by GetInitialMachineStateTransitionResult. Afterwards, the responsibility for state changes lies with State Management (SWS EM p. 48; SWS EM p. 56). If Startup is never reached, State Management can abort the transition via SetState. The initial result is then kOperationCanceled (SWS EM p. 57).

In the StateMachine approach, the StateMachine of type Controller starts first. It manages MachineFG and starts the Agents (SWS SM p. 46). If an update session is active, the controller enters state ContinueUpdate instead of the initial state (SWS SM p. 91). After a successful "StartStateMachine", StateMachineService and StateMachineNotification are offered. The controller does not wait for the end of the initial ActionList (SWS SM p. 45; SWS SM p. 59).

Sequence diagram: Execution Management hands over control after Startup, and the controller starts the agents. Sources: SWS SM p. 93, SWS EM p. 56, SWS SM p. 45

A stop transitions an agent StateMachine via its "Off" state; thereafter, it no longer exists. An already running agent transitions to the passed state upon "StartStateMachine" with a parameter (SWS SM p. 63; SWS SM p. 60).

State diagram: Lifecycle of an agent StateMachine from start to the cessation of its services. Sources: SWS SM p. 10, SWS SM p. 62, SWS SM p. 63

State transitions: RequestTransition and ActionLists

RequestTransition evaluates the passed value in TransitionRequestTable against the current state ([SWS_SM_91107]; SWS SM p. 50). The call returns an error in these cases:

  • kInvalidValue: The value is not configured.
  • kTransitionNotAllowed: The value is not configured for the current state.
  • kRecoveryTransitionOngoing: Error recovery is in progress.
  • kUpdateInProgress: The StateMachine is marked as "ImpactedByUpdate".

References: SWS SM p. 49; SWS SM p. 83. If a request is accepted, still pending requests receive kOperationCanceled. The running ActionList is stopped, and the ActionList of the target state starts immediately (SWS SM p. 50).

ActionListItems are started in the configured order and run in parallel until a SYNC occurs. At the end of each ActionList, an implicit SYNC applies (SWS SM p. 55). There are items for Function Group States, Sleep, SetNetworkHandle, Start/Stop StateMachine, and Suspend-to-RAM (SWS SM p. 54). Sleep does not block incoming triggers (SWS SM p. 64). Errors during execution result in kTransitionFailed (SWS SM p. 51). During the transition, CurrentState is set to "InTransition" ([SWS_SM_91109]). Changes of a NetworkHandle to FullCom or NoCom also trigger table-driven transitions (SWS SM p. 52).

Activity diagram: Checks and results of a RequestTransition call; the sequence of checks is an interpretation. Sources: [SWS_SM_91107], SWS SM p. 49, SWS SM p. 50, SWS SM p. 83

Update Sessions with Update and Configuration Management

A session begins with RequestUpdateSession. State Management may reject it if the machine is not updatable. It rejects a second, parallel session with kNotAllowedMultipleUpdateSessions ([SWS_SM_91102]; SWS SM p. 30). The SMControlApplication decides whether the update is allowed via the field UpdateAllowed. There is at most one UpdateRequest port per machine, and only the controller process instantiates it ([SWS_SM_91108]; SWS SM p. 79).

PrepareUpdate, VerifyUpdate, and PrepareRollback receive the list of affected Function Groups. Every StateMachine that manages one of them is marked as "ImpactedByUpdate". If an agent is affected, the controller is also marked ([SWS_SM_91103], [SWS_SM_91104], [SWS_SM_91105]; SWS SM p. 82). Outside an active session, these methods and StopUpdateSession return kOperationRejected (SWS SM p. 31). Affected agents are treated differently depending on the method:

  • With PrepareUpdate and PrepareRollback, they are stopped.
  • With VerifyUpdate, they are brought into state VerifyUpdate.

References: SWS SM p. 84; SWS SM p. 85; SWS SM p. 89. StopUpdateSession transitions the controller to AfterUpdate and releases RequestTransition again ([SWS_SM_91101]; SWS SM p. 95).

Sequence diagram: Flow of an update session from the perspective of the controller. Sources: SWS SM p. 81, SWS SM p. 84, SWS SM p. 89, [SWS_SM_91102]

ResetMachine is Fire&Forget. Update and Configuration Management tracks progress via ResetMachineNotifier because the machine and UCM must resynchronize after the restart ([SWS_SM_91100], [SWS_SM_91106]; SWS SM p. 33).

State diagram: Values of the field ResetMachineNotifier, without unspecified intermediate values. Sources: SWS SM p. 33, SWS SM p. 90, SWS SM p. 93, SWS SM p. 95

Suspend-to-RAM via S2R Hub, Satellites, and PowerStateInterface

The applications are treated differently depending on suspendToRamAwareness (SWS SM p. 109):

  • With suspendToRamNotSupported, they are terminated via a Function Group change.
  • With suspendToRamAware, they are notified as an S2R Satellite.

A satellite is created via Create or the constructor with InstanceSpecifier and registers with Offer ([SWS_SM_81014], [SWS_SM_81003], [SWS_SM_81012]). StopOffer unregisters it, blocks until the end of running callbacks, and must be called before destruction ([SWS_SM_81013]; SWS SM p. 38). The callbacks EnterSuspendMode and LeaveSuspendMode are pure virtual and return ara::core::Future<void> ([SWS_SM_81010], [SWS_SM_81011]).

RequestToEnterSuspendMode and RequestToLeaveSuspendMode call all actively registered, IAM-authenticated satellites. They return as soon as all have responded, unregistered, or the timeout (default 1000) has expired ([SWS_SM_81110], [SWS_SM_81111]; SWS SM p. 36). Subsequently, EnterSuspendToRamOs initiates the suspend of the operating system. Interpretation: This is likely done via PowerStateInterface::SetPowerState with kPmSuspendToRam ([SWS_SM_81112], [SWS_SM_71001], [SWS_SM_71002]).

The operating system reports the wake-up via the WakeUpHandler registered with RegisterWakeUpHandler. The controller then transitions autonomously to LeaveSuspend, whose ActionList must contain LeaveSuspendToRam ([SWS_SM_71003], [SWS_SM_71004]; SWS SM p. 103). In the StateMachine approach, the controller uses the hub internally. Applications must then not use S2RHub (SWS SM p. 96). All S2R APIs have the status DRAFT.

Sequence diagram: Entry into Suspend-to-RAM and return after wake-up; the step to the operating system is interpreted. Sources: SWS SM p. 36, SWS SM p. 37, SWS SM p. 98, [SWS_SM_81112]

Configuration rules and responsibilities

In every MachineFG state except Off, a process with the affinity STATE_MANAGEMENT must run. Otherwise, the machine gets stuck in Startup, for example (SWS SM p. 146). Uniqueness rules apply to Function Groups and NmNetworkHandles:

  • Each Function Group and each NmNetworkHandle is referenced by exactly one StateMachine.
  • All ActionLists of a StateMachine contain the same set of Function Groups and NmNetworkHandles.

References: SWS SM p. 48; SWS SM p. 66; SWS SM p. 57; SWS SM p. 58. Only the controller uses Start/StopStateMachine. Agents manage only Function Groups from the same claimedFunctionGroups set and require an "Off" state (SWS SM p. 58; SWS SM p. 47; SWS SM p. 48). maxActionListDuration limits the duration of an ActionList. If the value is missing, the global value of the module instance applies (SWS SM p. 68).

Behavior in the event of an error

If Platform Health Management or Execution Management reports an error and the StateMachine is not "ImpactedByUpdate", it sets a recovery flag. It evaluates the ErrorRecoveryTable and transitions immediately to the target state. A mandatory entry ANY catches unconfigured ErrorCodes (SWS SM p. 69; SWS SM p. 70). StateMachines affected by the update ignore such requests and only log them (SWS SM p. 82). A new error during an ongoing recovery is considered a "nested recovery". All associated RecoveryHandler() calls then receive the same result (SWS SM p. 29). The flag is not reset until the recovery ActionList has been successfully processed (SWS SM p. 72).

Other error sources form separate ErrorCodes:

  • The SetState errors kNoCommunication, kInvalidTransition, and kInvalidMetaModelIdentifier are mapped to functionGroupTransitionRequestFailedError.
  • ActionList timeouts, agent start and stop, and LeaveSuspendToRam have separate ErrorCodes with default value 1.

References: SWS SM p. 73; SWS SM p. 74; SWS SM p. 76. kIntegrityOrAuthenticityCheckFailed recurs on every further attempt; recovery lies outside State Management (SWS SM p. 40). If State Management does not respond to RecoveryHandler() in time, Platform Health Management calls FireWatchdogReaction(). Supervision errors in State Management itself lead to a restart of the machine (EXP SWArch p. 234; EXP SWArch p. 235).

At the API level, State Management reports errors via SmErrorDomain with the name "Sm" and SmErrc values such as kOfferFailed or kCommunicationFailed ([SWS_SM_81240], [SWS_SM_81248]). MakeErrorCode and GetSmDomain generate the codes ([SWS_SM_81244], [SWS_SM_81251]). SmException transports them when C++ exceptions are enabled ([SWS_SM_81243], [SWS_SM_81250]). The hub aggregates the responses of the satellites into kAtLeastOneRejected, kAtLeastOneHadIssuesToLeave, kCommunicationTimeout, or kCommunicationFailed (SWS SM p. 37).

Sequence diagram: Error handling via the ErrorRecoveryTable and fallback to the watchdog reaction. Sources: EXP SWArch p. 220, EXP SWArch p. 220, SWS SM p. 69, SWS SM p. 82
