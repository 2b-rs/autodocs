Role of ara::log and Embedding into the Platform

The Functional Cluster Log and Trace provides Adaptive Applications and platform services with interfaces to forward log information to the communication bus, the console, the file system, or to ARTI trace. A dedicated method exists for each severity level (SWS LogAndTrace p. 8). At the center is the class ara::log::Logger. It represents a logger context within an application process (SWS LogAndTrace p. 68). Individual messages are created as ara::log::LogStream (SWS LogAndTrace p. 57). The API is designed independently of the underlying logging back-end (SWS LogAndTrace p. 11).

The interface Logger is used platform-wide. Execution Management, Diagnostic Management, Persistency, Network Management, and further clusters list it as a required interface (SWS LogAndTrace p. 13, EXP SWArchitecture p. 58). Log and Trace itself uses Time Synchronization to determine timestamps (SWS LogAndTrace p. 14). Trace data from non-AUTOSAR portions, such as kernel events, enter the cluster via the OS/ara::log adapter (SWS LogAndTrace p. 8, SWS LogAndTrace p. 38).

Context diagram: Applications and platform clusters use Logger; Log and Trace obtains timestamps from Time Synchronization and serves console, file, network, and ARTI. Sources: SWS LogAndTrace p. 13, SWS OperatingSystemInterface p. 21, SWS LogAndTrace p. 14

From Initialization to the Registered Logger Context

Before any use of a ara::log API, the logging framework must be initialized via ara::core::Initialize(); otherwise, the behavior is undefined. Manifest parameter Executable.loggingBehavior specifies whether logging is initialized (SWS LogAndTrace p. 17). In addition, the framework must be initialized if the executable has a PortPrototype of type LogAndTraceInterface (SWS LogAndTrace p. 22).

The application then registers one or more contexts. CreateLogger is available in three variants:

  • with context ID, description, and default log level [SWS_LOG_00021],
  • without log level [SWS_LOG_00263],
  • with ara::core::InstanceSpecifier; here, the logger is derived from the manifest [SWS_LOG_00256].

For the string variants, the following applies: without a model, the console is the default sink [SWS_LOG_00021]. For the InstanceSpecifier variant, CtxID, AppID, ECU ID, and Session ID are adopted from the model, and the connections to the sinks are established (SWS LogAndTrace p. 29).

When created, a context is automatically registered with the logging back-end and deregistered again upon process termination. Applications must therefore not construct a Logger themselves (SWS LogAndTrace p. 68); the default constructor is deleted [SWS_LOG_00259]. CreateLogger returns a reference to an instance owned by the framework (SWS LogAndTrace p. 22). Upon the call, Log and Trace also reports whether a local or a globally synchronized time base is used (SWS LogAndTrace p. 36). On ara::core::Deinitialize(), the framework forwards all still buffered messages to the sinks (SWS LogAndTrace p. 18).

Sequence diagram: Initialization, context registration via CreateLogger, and output of remaining buffers upon Deinitialize. Sources: [SWS_LOG_00021], SWS LogAndTrace p. 17, SWS LogAndTrace p. 18, SWS LogAndTrace p. 36

Constructing non-modeled messages with LogStream

Non-modeled messages are called “verbose” in the DLT protocol. They are created according to a builder pattern (SWS LogAndTrace p. 24, SWS LogAndTrace p. 23). Each entry method returns a LogStream object that accepts arguments via operator<< (SWS LogAndTrace p. 25). LogLevel is an enum based on std::uint8_t with, among others, kFatal (0x01), kError (0x02), and kWarn (0x03) [SWS_LOG_00018].

Insertion operators exist for arithmetic types, bool, strings, and several ara::core types [SWS_LOG_00040] [SWS_LOG_00062] [SWS_LOG_00124] [SWS_LOG_00128]. An overload is deliberately missing for char; a single character can be logged as ara::core::StringView (SWS LogAndTrace p. 24). Custom types are supported via additional operator<< overloads (SWS LogAndTrace p. 57). The following can also be attached to a message:

  • tags [SWS_LOG_00132]; they appear in the order in which they were added (SWS LogAndTrace p. 26),
  • the source location [SWS_LOG_00129],
  • a privacy level [SWS_LOG_00258].

The message is dispatched by the destructor upon leaving the scope [SWS_LOG_00262] or explicitly via Flush. Flush passes on the current buffer and starts a new message stream [SWS_LOG_00039]. It is only necessary if the same object continues to be used within the scope (SWS LogAndTrace p. 59). LogStream cannot be copied [SWS_LOG_00174]; the move constructor only serves for returning from factory functions [SWS_LOG_00176]. The insertion operators are not thread-safe [SWS_LOG_00040], whereas the logger methods are [SWS_LOG_00064]. Therefore, no global LogStream objects should be held in multi-threaded applications (SWS LogAndTrace p. 26).

Modeled messages, TraceSwitch, and ARTI

Modeled messages are called “non-verbose” in the DLT protocol. Their static parts reside in the ARXML model, whereby less data travels over the network (SWS LogAndTrace p. 23). They are sent with a single call to Logger::Log [SWS_LOG_00204]. If the level does not reach the threshold, the call costs only a single if check after parameter passing (PlatformDesign p. 74). With LogWith, attributes such as location or tag can be added [SWS_LOG_00133] (SWS LogAndTrace p. 34).

Types and constexpr variables of the messages are generated by the ara::log Modeled Message Generator from LogAndTraceMessageCollectionSet and DltLogSink (SWS LogAndTrace p. 29). For each collection set, a file messages.h is created in a namespace formed from SymbolProps (SWS LogAndTrace p. 31). This file must be explicitly included (SWS LogAndTrace p. 34).

Context diagram: Headers generated from the model (messages, TraceSwitch, TraceArti specializations) and their use by the application. Sources: SWS LogAndTrace p. 31, SWS LogAndTrace p. 39, SWS LogAndTrace p. 42

For tracing, TraceSwitch forwards modeled messages depending on Executable.traceSwitchConfiguration: to the logger, to ara::log::ext::TraceArti, to both, or to neither. The decision is made at compile time (SWS LogAndTrace p. 39, SWS LogAndTrace p. 40). ARTI can additionally be enabled statically: if DltLogChannel.logTraceLogMode is set to kArti, Logger::Log calls the function TraceArti, specifically before formatting and filtering (SWS LogAndTrace p. 42).

TraceArti is not an application interface; only the framework calls it internally [SWS_LOG_20000] (SWS LogAndTrace p. 90). Regarding the header file, the sources diverge: the document reference specifies ara/log/trace_arti.h (SWS LogAndTrace p. 39), whereas the requirement for R25-11 specifies apext/log/trace_arti.h. The requirement is authoritative [SWS_LOG_20000].

Activity diagram: Routing of a Log call via the TraceSwitch (compile time) as well as via ARTI sink and filter (runtime). Sources: SWS LogAndTrace p. 42, SWS LogAndTrace p. 39, [SWS_LOG_00204]

Arguments, format hints, and their representation in the sinks

Arg packages a value together with an optional name, an optional unit, and a format hint [SWS_LOG_00201]. On the console, the value and attributes appear as a single argument [SWS_LOG_00203]. Format hints are provided by helper functions such as Dflt, Hex, Bin, DecFloat, or AutoFloatMax [SWS_LOG_00208] [SWS_LOG_00209] [SWS_LOG_00215] [SWS_LOG_00217] [SWS_LOG_00224]. They set the fields fmt and precision of the structure Format [SWS_LOG_00225] [SWS_LOG_00226]. Whether the viewer application respects these hints is up to the application itself (SWS LogAndTrace p. 27).

On the console, the following applies (SWS LogAndTrace p. 43, SWS LogAndTrace p. 44):

  • Name and unit are appended with a colon, such as speed:42.1:km/h.
  • bool appears as 0 or 1.
  • Raw data appears as hex octets, separated by apostrophes.
  • Durations appear as an integer with an SI unit, such as 42ns.

In the DLT binding, the log levels are mapped 1:1 (SWS LogAndTrace p. 44). bool becomes BOOL, strings become STRG with UTF-8, and byte spans become RAWD (SWS LogAndTrace p. 45).

Manifest configuration and instance reference

Machine-specific settings are collected by LogAndTraceInstantiation. Via the execution manifest, each process provides application ID, description, default log level, log mode, and, if applicable, a file path (SWS LogAndTrace p. 18). The application ID originates from DltApplication.applicationId. The integrator is responsible for ensuring that it is unique within an ECU (SWS LogAndTrace p. 19). By contrast, the context ID is not modeled; the developer assigns it uniquely process-wide (SWS LogAndTrace p. 21).

The log mode corresponds to the category of a DltLogSink (SWS LogAndTrace p. 20):

  • DLT_LOGSINK_FILE selects file output (SWS LogAndTrace p. 44). Its path is intended only for development and integration, not for production (SWS LogAndTrace p. 21).
  • DLT_LOGSINK_NETWORK or DLT_LOGSINK_DLT select the DLT binding (SWS LogAndTrace p. 44).

The Ethernet output is configured by the PlatformModuleEthernetEndpointConfiguration referenced by DltLogSink (SWS LogAndTrace p. 21). At deployment time, a DltLogSinkToPortPrototypeMapping maps the PortPrototype in the context of a Process to a DltLogSink (SWS LogAndTrace p. 28). If timeBaseResource is referenced, each DLT message carries a timestamp (SWS LogAndTrace p. 36).

At runtime, SetThreshold sets the threshold of a logger [SWS_LOG_00255]. IsEnabled checks whether a level is active before complex data preparation [SWS_LOG_00070]. Interpretation: IsEnabled likely reflects the value set via SetThreshold. RegisterConnectionStateHandler registers a callback for changes in the connection state; only the most recently registered one is active [SWS_LOG_00205] [SWS_LOG_00265].

Behavior in the event of an error

Principle: Errors in the logging framework or in the system shall not disrupt the application. Affected calls are silently discarded; the interfaces therefore provide neither return values nor exceptions (SWS LogAndTrace p. 22). Accordingly, the functions are noexcept [SWS_LOG_00064]. Under high concurrent load, Log and Trace buffers internally to avoid data loss (SWS LogAndTrace p. 37). Individual error cases:

  • Missing initialization: The behavior is undefined (SWS LogAndTrace p. 17).
  • Logger without model connection: A Log call on such a logger is ignored (SWS LogAndTrace p. 29).
  • Message without arguments: It is discarded (SWS LogAndTrace p. 23).
  • Unresolvable InstanceSpecifier: If it cannot be resolved in the model of the executable or references an element other than a PortPrototype, a InstanceSpecifierMappingIntegrityViolation is present [SWS_LOG_00256].
  • Ill-formed at compile time: Inappropriate arguments for Log [SWS_LOG_00204], unsuitable types for Arg [SWS_LOG_00201], or a type for WithPrivacy that is neither integral nor an enum [SWS_LOG_00258] make the program ill-formed.
  • Connection state: ClientState::kUnknown reports a DLT backend that is not yet running, kNotConnected the absence of a remote client [SWS_LOG_00098]. Interpretation: Applications can presumably defer extensive diagnostic output until kConnected.
  • ~Logger: The destructor is marked as not exception-safe [SWS_LOG_00260].
