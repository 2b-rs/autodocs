Log and Trace as a routing layer

ara::log forwards messages from applications and Functional Clusters to configured sinks. Application and context are separated by IDs; the threshold filters severity levels before a backend serves the console, file, or network. Adapt the message model to the intended use

Unmodeled (verbose) messages contain all parts in the transport and are particularly suitable for development. Modeled (non-verbose) messages refer to static model information and typically reduce network load in production systems. {L72}

Behavior in the event of an error

Errors in the logging framework or the underlying system should not affect the application process: the interfaces in question neither have return values ​​nor do they throw exceptions; Calls are silently discarded in the event of such an error. SWS Log and Trace §7.1.6 “Initialization of the Logging framework” [SWS_LOG_00002]

ara::core::Initialize() is required before each use of ara::log. If the framework cannot process messages, for example because daemon communication is not yet established or initialization has not yet been completed, they are stored in a queue limited by logSink.queueSize. If this size is exceeded, the oldest entries must be discarded; the same rule applies after a daemon crash. SWS Log and Trace §7.8.1 “Startup” [SWS_LOG_00001] SWS Log and Trace §7.8.3 “Daemon crash”

The activity diagram shows the specified queue handling when logging is unavailable and during shutdown. Sources: SWS Log and Trace §7.8.1 “Startup” [SWS_LOG_00001] SWS Log and Trace §7.8.2 “Shutdown” [SWS_LOG_00123].

After ara::core::Deinitialize(), the application no longer needs to use the logging API and cannot log any further messages. At this point, the framework must pass all messages still in the queue to the configured log sinks. SWS Log and Trace §7.8.2 “Shutdown” [SWS_LOG_00123]
