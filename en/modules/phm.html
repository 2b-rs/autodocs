Role of Platform Health Management and system boundary

Platform Health Management (PHM, namespace ara::phm) monitors applications in two ways: temporally via Alive Supervision and Deadline Supervision, and logically via program flow (Logical Supervision). PHM reports detected errors to State Management. State Management coordinates the platform and decides on the reaction. For critical errors where such a report is not sufficient, PHM additionally has an interface to the hardware watchdog SWS PHM p. 22. The supervision algorithms originate from the Foundation specification Health Monitoring. The Adaptive specification primarily adds platform specifics and interfaces SWS PHM p. 8.

PHM provides two public C++ APIs:

  • ara::phm::SupervisedEntity for reporting checkpoints [SWS_PHM_01127].
  • ara::phm::RecoveryAction as a callback interface through which State Management receives recovery actions [SWS_PHM_01142].

SupervisedEntity is used not only by Adaptive Applications, but also by platform daemons such as Execution Management, State Management, Diagnostic Management, and Time Synchronization SWS PHM p. 15. PHM controls the watchdog via the native platform extension apext::phm::WatchdogInterface with AliveNotification [SWS_PHM_01255] and FireWatchdogReaction [SWS_PHM_01256]. PHM does not define Service Interfaces of the Adaptive Platform SWS PHM p. 78.

For its part, PHM requires three things:

  • Process states from Execution Management: reaching kRunning, termination, and impending SIGTERM SWS PHM p. 17.
  • the ExecutionClient for reporting its own execution state.
  • the Logger of Log and Trace SWS PHM p. 16.

The interfaces between Functional Clusters are described for information only; their details are defined by the platform vendor SWS PHM p. 89. Two features are out of scope: Health Channels are marked as obsolete, and daisy chaining is not supported SWS PHM p. 13 SWS PHM p. 72.

Context diagram: PHM receives checkpoints from applications and platform daemons, reports errors to State Management, and controls the watchdog. Sources: SWS PHM p. 46, SWS PHM p. 16, EXP SWArch p. 236, [SWS_PHM_01127], [SWS_PHM_01142]

From manifest to checkpoint: Supervised Entities in code

Each Supervised Entity is modeled in the manifest as PhmSupervisedEntityInterface with its PhmCheckpoint elements. From this, the generator creates an enum class with base type std::uint32_t for each interface [SWS_PHM_00424]. Each enumerator bears the shortName of the checkpoint and its checkpointId as value [SWS_PHM_00425]. The namespace follows the schema ara::phm::supervised_entities::… SWS PHM p. 51, and the storage of headers follows a matching folder schema SWS PHM p. 52.

At runtime, an instance identifies itself via an ara::core::InstanceSpecifier passed to the constructor [SWS_PHM_01123]. This allows multiple instances of the same Supervised Entity to be monitored separately SWS PHM p. 49. The class is non-copyable [SWS_PHM_01212] [SWS_PHM_01213], but movable [SWS_PHM_01214] [SWS_PHM_01215]. Reporting is done using ReportCheckpoint(checkpointId); the method is noexcept and thread-safe [SWS_PHM_01127]. The IDs in the code must match the deployment configuration. The manifest example shows seB.ReportCheckpoint(21) for a checkpoint with ID 21 TPS Manifest p. 566.

Before PHM evaluates a checkpoint, it checks the caller. If the call originates from a process that does not correspond to the modeled process of the SupervisionCheckpoint, a InsufficientPermissionsViolation has occurred [SWS_PHM_01127]. According to the scenario, PHM in this case reports a security event to the Intrusion Detection System Manager EXP SWArch p. 236. Checkpoints that are assigned to NoCheckpointSupervision or whose instance is set to NoSupervision in the current Supervision Mode are likewise not evaluated SWS PHM p. 25.

Sequence diagram: A reported checkpoint is evaluated only after a successful access check; an unauthorized call results in a security event. Sources: EXP SWArch p. 236, SWS PHM p. 25, [SWS_PHM_01123], [SWS_PHM_01127]

Startup, Supervision Modes, and Lifecycle of Supervisions

During its own startup, PHM takes over the watchdog as early as possible: It calls AliveNotification before reporting kRunning to Execution Management SWS PHM p. 50. Afterwards, PHM cyclically evaluates all supervisions and reports its aliveness to the WatchdogInterface [SWS_PHM_01255] EXP SWArch p. 233. The cycle time of this report is configurable and can deviate from the trigger time of the actual hardware watchdog. If the report fails to appear, the WatchdogInterface itself triggers the watchdog reaction EXP SWArch p. 130.

Sequence diagram: PHM takes over the watchdog before the kRunning report and services it cyclically afterwards; State Management releases the recovery callback via Offer(). Sources: SWS PHM p. 50, EXP SWArch p. 215, EXP SWArch p. 233, EXP SWArch p. 200

When the individual supervisions begin depends on their type:

  • An Alive Supervision starts its first reference cycle as soon as the associated process reports kRunning. It ignores checkpoints reported earlier SWS PHM p. 26.
  • Deadline Supervision and Logical Supervision begin with the first checkpoint reported for them EXP SWArch p. 219.

All times are measured in the context of the reporting process using the same time source. This prevents delays and jitter of the inter-process communication from having an impact SWS PHM p. 27.

PHM derives the Supervision Mode from the Function Group State SWS PHM p. 19. The following rules apply to processes upon a state change SWS PHM p. 31 SWS PHM p. 32:

  • If a process is terminated, PHM stops its supervisions and evaluates them as correct.
  • A restart is considered a termination followed by a start.
  • A process that continues to run retains its previous supervision parameters.

The R23-11 description explicitly excluded dynamically enabling and disabling supervision during process runtime SWS PHM p. 32. In contrast, R25-11 defines SupervisedEntity::Enable [SWS_PHM_01130] and Disable [SWS_PHM_01380]. Both return ara::core::Future<void>, can fail with PhmErrc::kServiceNotReady, and are not thread-safe. Interpretation: This API is likely to replace the earlier restriction for R25-11; in any case, the requirements are normative.

Elementary and Global Supervision Status

PHM maintains a dedicated Elementary Supervision Status for each individual Alive, Deadline, and Logical Supervision SWS PHM p. 33. In code, this corresponds to ElementarySupervisionStatus [SWS_PHM_01358]. All state machines start in kDEACTIVATED SWS PHM p. 34. Only Alive Supervision has a tolerance state SWS PHM p. 35:

  • Failed reference cycles up to the limit failedReferenceCyclesTolerance lead to kFAILED.
  • If the limit is exceeded, the status changes to kEXPIRED, and the supervision is stopped.
  • For Deadline Supervision and Logical Supervision, any incorrect result leads directly to kEXPIRED.

When the process ends, the status returns to kDEACTIVATED. Supervisions of the operating system, Execution Management, and State Management are excluded; for them, recovery via the watchdog is intended SWS PHM p. 36 SWS PHM p. 37.

State diagram: kFAILED exists only for Alive Supervision, and the return path from kEXPIRED to kDEACTIVATED is omitted for OS, EM, and SM. Sources: SWS PHM p. 32, SWS PHM p. 34, SWS PHM p. 36, SWS PHM p. 37, [SWS_PHM_01358]

Multiple elementary supervisions are grouped into a GlobalSupervision. Its status is the "worst-of" of all contained elementary statuses SWS PHM p. 38. For each configured GlobalSupervision, there is exactly one status SWS PHM p. 39; in code, this corresponds to GlobalSupervisionStatus [SWS_PHM_01137]. Two restrictions apply to the assignment: All supervisions of a Global Supervision belong to processes of the same Function Group, and each supervision belongs to at most one Global Supervision SWS PHM p. 23. Compared to the elementary status, the state kSTOPPED is added. It is reserved for critical errors that require a direct watchdog reaction SWS PHM p. 39.

Regarding spelling: The specification texts from R23-11 use kFAILED, whereas the R25-11 definition of ElementarySupervisionStatus uses kFailed [SWS_PHM_01358]. For code, the spelling from the requirements applies.

State diagram: The global status consolidates the elementary statuses; only supervisions of OS, EM, and SM reach kSTOPPED. Sources: SWS PHM p. 39, SWS PHM p. 40, SWS PHM p. 41, SWS PHM p. 42, SWS PHM p. 43, SWS PHM p. 50

Recovery via RecoveryAction and State Management

The abstract class RecoveryAction is constructed via a InstanceSpecifier [SWS_PHM_01141]. State Management derives from it and implements the pure virtual RecoveryHandler(executionError, supervision) [SWS_PHM_01142]. Following the Offer/StopOffer pattern, registering the callback and releasing it are separate steps EXP SWArch p. 42:

  • Offer() enables calls and returns ara::core::Result<void>. If communication with the PHM daemon fails, the result contains PhmErrc::kOfferFailed [SWS_PHM_01143] [SWS_PHM_01240].
  • StopOffer() blocks further calls [SWS_PHM_01144]. State Management calls it during its own shutdown EXP SWArch p. 234.

RecoveryAction is neither copyable nor movable [SWS_PHM_01149] [SWS_PHM_01150] [SWS_PHM_01151] [SWS_PHM_01152]. The rationale: If an instance were moved after Offer(), PHM could call the handler before the derived class is fully constructed [SWS_PHM_01149]. Offer(), StopOffer(), and the destructor are not thread-safe [SWS_PHM_01145].

The parameter supervision of type TypeOfSupervision indicates which type of supervision is affected, e.g., kAliveSupervision or kDeadlineSupervision [SWS_PHM_01138]. The parameter executionError is of type ara::exec::ExecutionErrorEvent [SWS_PHM_01142]. It likely conveys the numeric error value configured in the manifest per process that PHM reports to State Management in the event of a supervision violation SWS PHM p. 84.

Behavior in the event of an error

The normal case proceeds as follows:

  1. A Global Supervision assigned to a RecoveryAction port via the manifest transitions to kEXPIRED. PHM subsequently calls RecoveryHandler SWS PHM p. 46.
  2. Because ISO 26262 requires a safe reaction, PHM monitors the return of the handler using the timeout recoveryNotificationTimeout SWS PHM p. 48 SWS PHM p. 85.
  3. The scenario provides for three outcomes EXP SWArch p. 234:
    • State Management handles the error.
    • State Management cannot handle the error and responds with kSMCanNotHandleRecovery [SWS_PHM_01240] EXP SWArch p. 220.
    • The timeout expires.
  4. In the latter two cases, PHM calls FireWatchdogReaction(), thereby restarting the machine [SWS_PHM_01256].

Sequence diagram: A supervision error is reported to State Management; if no handling occurs, PHM escalates to the watchdog. Sources: EXP SWArch p. 234, EXP SWArch p. 220, EXP SWArch p. 234, [SWS_PHM_01142], [SWS_PHM_01143], [SWS_PHM_01144]

If the operating system, Execution Management, or State Management itself fails, recovery via State Management is not possible. The watchdog is then the last resort and usually leads to a machine reset SWS PHM p. 47. The sequence depends on expiredSupervisionTolerance SWS PHM p. 41 SWS PHM p. 42:

  • If the tolerance is zero, the Global Supervision transitions directly to kSTOPPED.
  • Otherwise, it first transitions to kEXPIRED and only then to kSTOPPED when the measured Expired Supervision Time reaches the tolerance.

During watchdog handling, PHM stops AliveNotification and calls FireWatchdogReaction SWS PHM p. 47 EXP SWArch p. 235. How a Global Supervision is assigned to these clusters is not standardized SWS PHM p. 44.

Activity diagram: Whether an error is reported to State Management or escalated directly to the watchdog is determined by the assignment of the Global Supervision to OS, EM, or SM. Sources: SWS PHM p. 38, SWS PHM p. 41, SWS PHM p. 46, SWS PHM p. 47, EXP SWArch p. 201

Two further error cases concern processes that terminate themselves (Self-Terminating Processes). An alive violation is reported to State Management if such a process SWS PHM p. 28:

  • does not terminate within terminatingCheckpointTimeoutUntilTermination after terminatingCheckpoint, or
  • terminates without this checkpoint and without a preceding SIGTERM.

If PHM itself receives SIGTERM, it stops all supervisions and sets all global statuses to deactivated SWS PHM p. 50.

PHM reports API errors via ara::core::Result with the PhmErrorDomain [SWS_PHM_01240] [SWS_PHM_01247] SWS PHM p. 72. Standardized exceptions do not exist. PhmException [SWS_PHM_01243] and ThrowAsException [SWS_PHM_01250] exist only so that the domain matches ara::core SWS PHM p. 73. The API does not use checked exceptions SWS PHM p. 59.
