Role: Network requests between State Management and bus

The adaptive Network Management (NM) coordinates when the underlying physical and partial networks switch between normal operation and bus-sleep. It is intended to work independently of the communication stack used SWS NM p. 5. In technical terms, it is based on the PRS NetworkManagementProtocol. It uses the communication stack to send and receive NM messages SWS NM p. 9. According to the limitations, currently only UdpNM is supported SWS NM p. 8.

Upward, the system boundary is narrowly drawn. Applications do not address NM directly. They request functions from State Management, and State Management requests or releases logical networks depending on the configuration SWS NM p. 14 SWS NM p. 29. The only interface is the class ara::nm::NetworkHandle in the header ara/nm/network_handle.h [SWS_ANM_01000]. It is explicitly intended only for State Management EXP SWArch p. 77. Accordingly, State Management lists it under its required interfaces EXP SWArch p. 56. Both clusters are daemon-based: State Management uses the interface, NM implements it SWS NM p. 13.

Older text passages of the SWS (Chapters 8/9) contradict this. There it is stated that NM contains no APIs and provides everything via services SWS NM p. 26. However, the C++ class NetworkHandle with its methods [SWS_ANM_01000] [SWS_ANM_01009] is normative for R25-11. The platform design overview describes this change from the ara::com interface to direct method calls EXP PlatformDesign p. 60.

Context diagram: Applications reach NM only indirectly via State Management, which controls NM via NetworkHandle. NM exchanges NM messages via the communication stack. Sources: SWS NM p. 13, SWS NM p. 14, SWS NM p. 9, [SWS_ANM_01000]

From logical network to channel: handles, partial networks, and NM instances

A logical network is mapped to exactly one partial or physical network. In contrast, a partial network can be assigned to multiple physical networks. Each port provided by NM controls exactly one logical network, and the ports are assigned to the logical networks via the manifest. With partial networking, the assignment of partial networks to physical networks must additionally be configured. Without partial networking, the port is mapped directly to the physical networks SWS NM p. 14.

The overview of the SWS shows the layering. Network handle instances act on the partial network state machines. These control channel-specific NM instances, each with a Network State Machine, which in turn operate on the networks SWS NM p. 18 EXP PlatformDesign p. 60. The partial network state machine is implementation-specific. However, its behavior must comply with the partial networking requirements of the PRS SWS NM p. 24.

Collaboration diagram: Handles act on channel-specific NM instances via partial network state machines. A partial network (PN2) can affect two networks in the process. Sources: SWS NM p. 18, SWS NM p. 14, SWS NM p. 15

Working with ara::nm::NetworkHandle: request, query, notify

A handle is created from the InstanceSpecifier of a port prototype of type NetworkManagementPortInterface. The constructor is noexcept and thread-safe [SWS_ANM_01001]. Copying is not possible [SWS_ANM_01005] [SWS_ANM_01006], but moving is [SWS_ANM_01003] [SWS_ANM_01004]. The destructor is not thread-safe [SWS_ANM_01002].

NetworkStateType knows only kNoCom and kFullCom. kFullCom applies if all assigned networks are FULL_COM; otherwise, kNoCom applies [SWS_ANM_01358]. The handle separates two views:

  • Requested state: SetNetworkRequestedState requests or releases a PNC, a VLAN, or a physical network [SWS_ANM_01009]. GetNetworkRequestedState reads this state [SWS_ANM_01008].
  • Effective state: GetNetworkState reads the current network state [SWS_ANM_01007].

Interpretation: The effective state kFullCom likely corresponds to the Network Mode of the assigned channels. Specifically, Network Mode means that the network is requested or active SWS NM p. 15.

For both views, there is one notifier of type NetworkStateChangeNotifier each. It is a std::function that receives the new NetworkStateType [SWS_ANM_01020]. RegisterNetworkStateChangeNotifier and RegisterNetworkRequestedStateChangeNotifier each accept at most one notifier [SWS_ANM_01010] [SWS_ANM_01012]. According to the interface table, each additional registration overwrites the existing one EXP SWArch p. 77. The variants with ExecutorT execute the notifier in the passed execution context [SWS_ANM_01014] [SWS_ANM_01015]. Deregistration is performed using UnregisterNetworkStateChangeNotifier and UnregisterNetworkRequestedStateChangeNotifier, respectively [SWS_ANM_01011] [SWS_ANM_01013].

Regarding thread safety: Only the two getters [SWS_ANM_01007] [SWS_ANM_01008] are thread-safe. SetNetworkRequestedState as well as all register and unregister functions are not [SWS_ANM_01009] [SWS_ANM_01010] [SWS_ANM_01013]. The caller must therefore serialize these calls per handle itself.

Sequence diagram: The handle is created, the notifiers are registered, the network is requested, notified asynchronously, and finally released again. Sources: [SWS_ANM_01001], [SWS_ANM_01009], [SWS_ANM_01015], [SWS_ANM_01007], SWS NM p. 13, SWS NM p. 18

Channel behavior: decentralized NM algorithm and operating modes

The algorithm operates in a decentralized and direct manner. Each node decides solely based on the received and sent NM packets. Periodic NM packets sent to all nodes via multicast keep the cluster awake. A node that can sleep no longer sends. However, it delays sleep as long as packets from other nodes continue to arrive SWS NM p. 13. Each node can integrate into an already running cluster SWS NM p. 11.

For each physical channel, the NM implements the modes Network Mode, Prepare Bus-Sleep Mode, and Bus-Sleep Mode. These modes are not visible to applications SWS NM p. 15. Network Mode is divided into Repeat Message, Normal Operation, and Ready Sleep SWS NM p. 16. The sequence in detail:

  • Upon entering Network Mode, Repeat Message is entered and the NM timeout timer is started with NmTimeoutTime. Each successfully received or sent NM packet restarts the timer SWS NM p. 17.
  • If the network is released in Normal Operation, the NM transitions to Ready Sleep, and transmission stops. A received Repeat Message Request Bit leads back to Repeat Message SWS NM p. 18.
  • Prepare Bus-Sleep lasts NmWaitBusSleepTime and ends in Bus-Sleep. If an NM packet arrives beforehand, the NM immediately returns to Network Mode SWS NM p. 19.

When sending, the first packet after entering Repeat Message is delayed by NmMsgCycleOffset. Thereafter, the NM sends cyclically with NmMsgCycleTime SWS NM p. 22. The Repeat Message Request Bit, Active Wakeup Bit, and NM Coordinator Sleep Ready Bit are always 0 in transmitted messages SWS NM p. 20. Node detection, the role as master coordinator, coordinated shutdown via the CBV, and Passive Mode are not supported SWS NM p. 8.

Partial Networking: Reception evaluation and aggregated request state

NmPnEnabled enables or disables the evaluation of PN information upon reception. The rules when Partial Networking is enabled SWS NM p. 24:

  • If the PNI bit is 1, the NM calls the NetworkHandle notifier as soon as a received BitVector changes the request state of a relevant PN or channel.
  • If the PNI bit is 0, the NM nevertheless processes the user data.
  • The getter returns the aggregated request state of the PNs and does not reflect the most recently received information. Presumably, this refers to GetNetworkRequestedState [SWS_ANM_01008].
  • NmPnResetTime must be greater than NmMsgCycleTime.

Each bit of the PN info range represents a partial network. Optionally, the NM filters out messages that do not contain a bit set to 1 for a PNC configured for the ECU SWS NM p. 25. The same section mentions the methods RequestNetwork/ReleaseNetwork of an Adaptive Application. In R25-11, they are replaced by SetNetworkRequestedState, called by State Management [SWS_ANM_01009].

If received user data changes, the NM invokes a notification SWS NM p. 23. User data and PNI do not overlap SWS NM p. 21. Application access to user data no longer exists. It remains open whether it is to take place via State Management in the future SWS NM p. 8.

Activity diagram: Decision chain upon receiving an NM message with Partial Networking, from switch NmPnEnabled to notification. Sources: SWS NM p. 24, SWS NM p. 25, SWS NM p. 23

Instance reference and configuration in the manifest

In the manifest metamodel, a NmInstantiation holds the NmNetworkHandle elements TPS Manifest p. 621. A NetworkHandlePortMapping connects a port prototype in a Process with a NmNetworkHandle TPS Manifest p. 620. The port is typed with NetworkManagementPortInterface, a specialization of PortInterface TPS Manifest p. 263. The constructor obtains its InstanceSpecifier via this port [SWS_ANM_01001].

The NM is coupled to State Management at three points:

  • NmHandleToFunctionGroupStateMapping maps handle states to Function-Group-States via mappingDirection TPS Manifest p. 624.
  • SmInteractsWithNmMapping links a StateManagementNmActionItem (nmStateRequest) with a handle TPS Manifest p. 874.
  • NmInteractsWithSmMapping connects a handle with a StateManagementStateRequest TPS Manifest p. 875.

The diagrams of the SWS State Management show two supplementary rules. A handle may affect multiple state machines SWS SM p. 53. In contrast, a restriction applies to setting a handle by state machines SWS SM p. 66.

Behavior in the event of an error

Errors are reported as ara::core::Result. They belong to domain NmErrorDomain [SWS_ANM_01101], which provides GetNmDomain [SWS_ANM_01109]. NmErrc knows kServiceNotAvailable = 1 and kInvalidHandler = 2 [SWS_ANM_01111]. The errors are distributed as follows:

  • Getters and setters report kServiceNotAvailable [SWS_ANM_01007] [SWS_ANM_01008] [SWS_ANM_01009].
  • The registration functions report kInvalidHandler [SWS_ANM_01010] [SWS_ANM_01012] [SWS_ANM_01014] [SWS_ANM_01015].
  • The unregister functions are void noexcept and have no error path [SWS_ANM_01011] [SWS_ANM_01013].

If a getter returns an error, the Result contains no NetworkStateType [SWS_ANM_01007]. Such an error is therefore not to be interpreted as kNoCom. Interpretation: kServiceNotAvailable is likely to indicate that the daemon-based NM cluster SWS NM p. 13 is currently not reachable.

Whoever prefers exceptions creates a ErrorCode with MakeErrorCode [SWS_ANM_01110]. ThrowAsException throws a NmException from it [SWS_ANM_01108] [SWS_ANM_01100] [SWS_ANM_01102]. Name and Message provide domain name and message text [SWS_ANM_01106] [SWS_ANM_01107].

At the protocol level, the NM is designed to be fault-tolerant. If it still receives an NM packet in Prepare Bus-Sleep, it returns to Network Mode so that communication is restored as quickly as possible SWS NM p. 19. If packets fail to arrive entirely, the timer leads all nodes into sleep SWS NM p. 13.
