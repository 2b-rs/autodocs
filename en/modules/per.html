Purpose and system boundary

ara::per makes configured persistent data accessible to Adaptive Applications. The model distinguishes key-value storages as sets of typed key-value pairs and file storages as sets of named files; both can be combined per application. SWS Persistency §7.1 “The Architecture of Persistency”

The storage instance cannot be freely selected, but is referenced to a manifested persistence interface through a ara::core::InstanceSpecifier. Access rights can be read-only, read/write, write-only or – for applications – write-only-once. SWS Persistency §7.1.1 “Configuration of Persistency”

Decision: key or file

Choose KeyValueStorage for addressable, typed states with an explicit synchronization boundary; choose FileStorage for file-like content and Accessor-based reading or writing. Initial values and initial files can be supplied with installation or update. SWS Persistency §7.1.2 “Configuration of Key-Value Storages” SWS Persistency §7.1.3 “Configuration of File Storages”

Interpretation: The selection is a data model decision: small, logically separated states benefit from keys; Contiguous or stream-like content is more suited to the file interface. It follows from the different access models described in the specification.

Operating model and data durability

An opened key-value storage initially works on temporary data. SyncToStorage permanently writes all changes since opening or last synchronization and updates configured redundancy; Without syncing, changes are discarded when you close or restart. SWS Persistency §7.3 “Key-Value Storage specific Features”

For files, the specific file is opened via an accessor. Write accesses can be specifically transferred to the physical memory via SyncToFile; Ownership of the accessor is exclusive. SWS Persistency §7.4 “File Storage specific Features”

Protection, recovery and resources

Redundancy can safeguard integrity through checksums or multiple copies; a Recovery Report callback can inform the application of unrecoverable findings. Recovery can yield initial or older data and must therefore be evaluated from an application perspective. SWS Persistency §7.2.4 “Redundancy Concepts”

The configured maximum limits actual memory used. The size queries include metadata as well as redundancy and backup needs and may be inaccurate for open storage or parallel operations. SWS Persistency §7.2.6 “Resource Management Concepts”

Installation, update and rollback

The target configuration can bring in predefined values ​​and files. During the verification phase, UpdatePersistency can make changes according to new configuration data; After successful finalization, CleanUpPersistency removes backup data. If an older configuration is activated, a restore or new installation will take place depending on the backup version saved. SWS Persistency §7.2.5 “Installation and Update of Persistent Data”

Opening requires a configured, initialized persistence. Sources: SWS Persistency §7.1 “The Architecture of Persistency” SWS Persistency §7.3 “Key-Value Storage specific Features”.

The persistence boundary affects all keys changed since opening or the last synchronization; updating configured redundancy is included. Source: SWS Persistency §7.3 “Key-Value Storage specific Features”.

Recovery is best effort; In the event of an error, a report can name the affected storage or elements. Source: SWS Persistency §7.2.4 “Redundancy Concepts”. Partial interpretation: The activity sequence combines several permitted redundancy procedures.

Update, finalization and rollback are anchored in the target configuration versioning. Sources: SWS Persistency §7.2.5 “Installation and Update of Persistent Data”. Partial interpretation: The arrangement shows the intended operation flow, not the signaling of a single API call.
