Role of ara::core as the Common Basis of All Functional Clusters

The Functional Cluster Core has two tasks. It specifies basic requirements that apply to all Functional Clusters of the Adaptive Platform. In addition, it provides functionality for the entire framework, especially common data types that multiple Functional Clusters use in their public interfaces (SWS Core p. 8). Core itself depends only on the specification of the operating system interface, essentially on the C++ standard library (SWS Core p. 10). All symbols are located in the namespace ara::core and are publicly visible unless specified otherwise (SWS Core p. 47).

The cross-cutting rules also apply to the implementation of other clusters:

  • Includes follow the pattern #include "ara/fc/header.h".
  • Public headers require include guards that are as system-wide unique as possible (SWS Core p. 23).
  • Symbols with the prefix ARA are reserved for AUTOSAR.
  • Declaration specifiers may only be supplemented by inline and friend (SWS Core p. 24).

The architecture description identifies two groups as native interfaces: Initialize()/Deinitialize() and Abort()/SetAbortHandler() (EXP SWArchitecture p. 60, [SWS_CORE_00051]).

Context diagram: Core is the base layer between applications, other Functional Clusters, and the C++ standard library. An abort via std::abort is recognized by Execution Management as Abnormal Termination. Sources: SWS Core p. 8, SWS Core p. 10, SWS Core p. 187, SWS Core p. 39, EXP SWArchitecture p. 60

Start and End of the ARA Runtime

ara::core::Initialize is the (pre-)initialization of the ARA framework. Prior to this, any interaction with ARA is prohibited. Excepted are types that are intended to be usable independently of the initialization:

  • ErrorCode and StringView,
  • Result, but without ValueOrThrow ([SWS_CORE_00766]),
  • ErrorDomain with its subclasses, but without ThrowAsException ([SWS_CORE_00154]) (SWS Core p. 182).

This exception is justified by the fact that precisely these types are needed for the initialization itself (SWS Core p. 46). Initialize can set up data structures and system resources and start background threads (SWS Core p. 45). If required, it also initializes other Functional Clusters (SWS Core p. 187).

ara::core::Deinitialize shuts down the framework in an orderly manner. This includes terminating background threads and releasing memory and other system resources. If ARA calls are still running in parallel, the behavior is undefined (SWS Core p. 45). Prior to the call, the use of ARA interfaces must be completed. A call location after static initialization and before destruction of static data is recommended (SWS Core p. 182).

State diagram: The ARA runtime transitions between three phases via Initialize and Deinitialize. Outside the initialized phase, only a fixed set of types is usable. Sources: SWS Core p. 182, SWS Core p. 182, SWS Core p. 45

Error Classes and Error Values: ErrorCode, ErrorDomain, Result

Core distinguishes three kinds of unsuccessful operations (SWS Core p. 25):

  • An Error means that an API function assumed to be fault-free cannot fulfill its purpose. An Error is recoverable.
  • A Violation corresponds to a failed assertion and is not recoverable.
  • A Corruption is caused by corrupted system resources and is likewise not recoverable.

The handling is specified for each kind (SWS Core p. 27):

  • Errors are returned as Result or Future.
  • Violations terminate the operation either by an exception that is not derived from ara::core::Exception, or by ara::core::Abort ([SWS_CORE_00052]). A failed default allocation is also considered a Violation.
  • Corruptions lead to an unsuccessful process termination.

Activity diagram: The kind of detected condition determines whether an error value is returned or the operation or process is terminated. Sources: SWS Core p. 25, SWS Core p. 27, [SWS_CORE_00052]

An ErrorCode contains three components: the error value, a reference to the error domain, and optional vendor-specific supplementary data. They can be retrieved via Value() ([SWS_CORE_00514]) and SupportData() ([SWS_CORE_00516]). During comparison ([SWS_CORE_00571]), only the value and domain count; the supplementary data is ignored. An ErrorCode is usually created via the forwarding form of Result::FromError ([SWS_CORE_00736]) (SWS Core p. 28).

Result follows the ValueOrError concept: It contains either a value or an error. ErrorType is ErrorCode by default (SWS Core p. 30). The typical accesses are:

  • HasValue() ([SWS_CORE_00751]),
  • Value() ([SWS_CORE_00755]),
  • Error() ([SWS_CORE_00757]),
  • ValueOrThrow() ([SWS_CORE_00766]). This function connects the exception-free approach with C++ exceptions. Their base type ara::core::Exception ([SWS_CORE_00611]) provides the ErrorCode via Error() ([SWS_CORE_00613]).

The specialization Result<void, E> omits operator-> and Bind (SWS Core p. 70, [SWS_CORE_00851]).

Asynchronous Results with Future and Promise

Future and Promise are closely based on std::future and std::promise. Both share a shared state. Deviations arise only from the integration with Result (SWS Core p. 89). Specifically, there are two differences:

  • SetError ([SWS_CORE_00353]) replaces set_exception.
  • GetResult() ([SWS_CORE_00336]) returns a Result and never throws.

The division of work is clear: Result serves synchronous calls, Future asynchronous calls with thread-safe later retrieval (SWS Core p. 31).

The sequence on the provider side:

  1. The provider creates a Promise ([SWS_CORE_00341]).
  2. It retrieves the associated Future using get_future() ([SWS_CORE_00344]) and returns it.
  3. Later, it fulfills the Promise with set_value ([SWS_CORE_00345], [SWS_CORE_00346]), SetError, or SetResult ([SWS_CORE_00355]).

In ara::com, the binding calls set_value or SetError. As a result, blocking calls of get(), wait(), wait_for(), and wait_until() return (SWS CM p. 106). An illustrative example shows the fulfillment in a worker thread after the Future has already been returned (EXP ARAComAPI p. 59).

Sequence diagram: The provider returns the Future immediately and fulfills the shared state later asynchronously with a value or an error. Sources: [SWS_CORE_00341], [SWS_CORE_00344], [SWS_CORE_00345], [SWS_CORE_00353], [SWS_CORE_00326], SWS CM p. 106, EXP ARAComAPI p. 59

The consumer has several access patterns:

  • get() ([SWS_CORE_00326]) and wait() ([SWS_CORE_00328]) block.
  • wait_for() ([SWS_CORE_00329]) and wait_until() ([SWS_CORE_00330]) return a FutureStatus ([SWS_CORE_00361]). This makes it possible to distinguish an available result from a timeout (ARAComAPI (Fig. 6.15) p. 1).
  • then() ([SWS_CORE_00331]) registers a continuation, optionally with an executor ([SWS_CORE_00337]).
  • is_ready() ([SWS_CORE_00332]) does not block and is suitable for real-time applications that operate via polling (EXP ARAComAPI p. 58).

Futures are not copyable ([SWS_CORE_00334]). A result that is no longer needed is discarded by overwriting the Future with a default-constructed Future ([SWS_CORE_00322]) (EXP ARAComAPI p. 59). In addition, there is a Executor. According to the signature, execute returns a Future of the call result ([SWS_CORE_00024]), whereas oneway_execute returns nothing ([SWS_CORE_00025]).

Activity diagram: The consumer chooses between blocking retrieval, timed waiting, continuation, and non-blocking polling. Sources: [SWS_CORE_00326], [SWS_CORE_00329], [SWS_CORE_00331], [SWS_CORE_00332], [SWS_CORE_00336], EXP ARAComAPI p. 58

Data Types, Containers, and Memory Resources

Core redefines types that already exist with almost equivalent semantics in the C++ standard. The reason: The allocation behavior of the std:: types is often unsuitable for the automotive domain. Functions that throw exceptions according to the C++ standard instead cause a Violation for these types (SWS Core p. 41). In detail:

  • Vector behaves like std::vector, except that the default allocator is implementation-defined (SWS Core p. 129, [SWS_CORE_01390]).
  • Map behaves correspondingly like std::map (SWS Core p. 130, [SWS_CORE_01496]).
  • String is defined as BasicString<> with fixed character type char (SWS Core p. 133, [SWS_CORE_03001]) and is implicitly convertible to StringView ([SWS_CORE_03301]).

The specification itself concedes that the allocation behavior of Map, Vector, and String is only described as implementation-defined (SWS Core p. 10).

Further types originate from newer C++ standards (SWS Core p. 43):

  • Optional represents optional record elements. Whether a value is present is checked using operator bool or has_value() ([SWS_CORE_01129], SWS Core p. 131, ARAComAPI (Fig. 6.3) p. 1).
  • StringView is a read-only view of characters (SWS Core p. 132, [SWS_CORE_02112]).
  • Span is a view of a contiguous sequence of external objects (SWS Core p. 137, [SWS_CORE_01901]). Whether as_bytes can be used without aliasing issues is implementation-defined (SWS Core p. 155, [SWS_CORE_01980]).
  • Byte is not an integral type and does not allow implicit conversions (SWS Core p. 44).
  • For Array, get<I> with I >= N results in a compilation error (SWS Core p. 127, [SWS_CORE_01282]).

Release differences: The R21-11 excerpts do not match the R25-11 requirements in two points; the requirements are authoritative.

  • According to R21-11, Array::at is omitted (SWS Core p. 41). R25-11, in contrast, introduces at() as noexcept ([SWS_CORE_01273]).
  • According to R21-11, Optional has no value member functions (SWS Core p. 131). R25-11 specifies them ([SWS_CORE_01130]).

Polymorphic memory resources exist for memory management. The base MemoryResource publicly provides allocate/deallocate/is_equal and private do_* hooks. Beneath it are MonotonicBufferResource as well as synchronized and unsynchronized pool resources (EXP SWArchitecture p. 61). The pool resources are constructed with PoolOptions and an upstream resource ([SWS_CORE_00030], [SWS_CORE_00067]). They offer release() ([SWS_CORE_00037]) and upstream_resource() ([SWS_CORE_00038]) and are not copyable ([SWS_CORE_00034], [SWS_CORE_00046]).

Custom Error Domains and Instance Reference via InstanceSpecifier

A software module with independent logic shall define custom error domains. An error domain consists of five parts, all of which are located in the module's namespace (SWS Core p. 32):

  • an error enumeration,
  • an exception base class,
  • a ErrorDomain subclass,
  • a global access function,
  • a MakeErrorCode overload.

Fixed rules apply to these parts:

  • The enumeration is named <SN>Errc, contains no success values, and leaves 0 unassigned (SWS Core p. 33).
  • The subclass is final and has the aliases Errc and Exception (SWS Core p. 34).
  • The access function Get<SN>ErrorDomain is constexpr and returns a singleton (SWS Core p. 35).
  • Domains must be literal types (SWS Core p. 30).

The identity of a domain is based on a unique 64-bit ID ([SWS_CORE_00121], [SWS_CORE_00151], [SWS_CORE_00137]). The value range is partitioned (SWS Core p. 37):

  • Bit 63 = 1 and bit 62 = 0: AUTOSAR domains,
  • upper 32 bits = 0xc000'0000: vendor domains,
  • Bit 63 = 0: user domains.

The FutureErrorDomain has the ID 0x8000'0000'0000'0013 ([SWS_CORE_00480]). All other Core errors belong to the CoreErrorDomain (SWS Core p. 84).

InstanceSpecifier establishes the reference to the model instance. It identifies port prototype instances in the AUTOSAR metamodel via a "/"-separated list of names from the Executable to the PortPrototype. Syntactically invalid paths are rejected. There are two ways for construction: the exception-free factory method Create or the constructor, which can throw on invalid input (SWS Core p. 40).

Behavior in the event of an error

ara::core::Abort ([SWS_CORE_00052]) terminates the process immediately and abnormally, without stack unwinding and without destructors of static objects (SWS Core p. 38). The function has the following properties:

  • It never returns.
  • It writes the passed text as a log message to the standard error stream.
  • Concurrent additional calls block the calling threads.

The call is considered an Explicit Operation Abortion (SWS Core p. 8).

With SetAbortHandler ([SWS_CORE_00051]), a AbortHandler ([SWS_CORE_00050]) can be installed. Its type is derived from a prototype that is not implemented ([SWS_CORE_00053], SWS Core p. 183). A handler that terminates the process should use std::abort for this purpose so that Execution Management detects an Abnormal Termination. If the handler returns or if none is installed, Abort itself calls std::abort() (SWS Core p. 39). R25-11 additionally introduces AddAbortHandler ([SWS_CORE_00054]). Its semantics are not described in more detail in the payload and are therefore not detailed here.

Activity diagram: Abort always ends in a process termination, either by the handler or by std::abort. Interpretation: The log message is output before the handler call. Sources: SWS Core p. 38, SWS Core p. 39, [SWS_CORE_00051], [SWS_CORE_00052]

On the asynchronous side, a destroyed Promise ([SWS_CORE_00349]) leads to a ready Future. This carries an ErrorCode of the FutureErrorDomain with the value FutureErrc::kBrokenPromise ([SWS_CORE_00400]). This happens, for example, when a ServiceProxy is destroyed (SWS CM p. 290). In contrast, ara::com reports communication errors via SetError with errors of the ComErrorDomain (SWS CM p. 300).

Sequence diagram: The destruction of the proxy destroys the promise and makes the pending future ready with kBrokenPromise. Sources: SWS CM p. 290, [SWS_CORE_00349], [SWS_CORE_00400], [SWS_CORE_00336]

Two further error cases are specified:

  • If Message() is called with an error code from a foreign domain, this is a violation ([SWS_CORE_00153], SWS Core p. 51).
  • An error from Deinitialize is the only reporting channel guaranteed to be available, for instance when ara::log is already deinitialized. It is considered unrecoverable (SWS Core p. 45).
