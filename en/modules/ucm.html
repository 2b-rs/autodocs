Role of UCM and Distinction from V-UCM

Update and Configuration Management (UCM) is the Functional Cluster of the Adaptive Platform that securely installs, updates, and removes software on a Machine. Its tasks include version reporting, receiving and buffering updates, checking available resources, log and progress messages, validating the result, and rolling back to a known functional state SWS UCM p. 8. Updates to the platform itself also fall under its responsibility, that is, of the Functional Clusters, the POSIX operating system, and the kernel SWS UCM p. 8.

Externally, UCM provides the ara::com service interface PackageManagement. It comprises methods for transfer, processing, activation, and information, as well as the field CurrentStatus [SWS_UCM_00361] SWS UCM p. 91 EXP SWArchitecture p. 138. The primary user is the vehicle-wide Vehicle Update and Configuration Management (V-UCM). In addition, Adaptive Applications such as OTA clients or diagnostic applications can use the interface SWS UCM p. 17 EXP SWArchitecture p. 138.

V-UCM supplements a UCM instance with additional functions, but has its own service instances and orchestrates campaigns across multiple Machines SWS V-UCM p. 16. V-UCM reaches Classic or legacy ECUs via a Flashing Adapter that provides the same interface PackageManagement SWS V-UCM p. 12 SWS UCM p. 64.

For activation, UCM requires the interface UpdateRequest of State Management SWS UCM p. 109. Cryptography, Persistency, as well as Log and Trace are also involved in transfer and processing EXP SWArchitecture p. 204. Many detailed passages originate from release R21-11. Normative for R25-11 are the linked service elements; deviations in names are noted in each case, e.g. for [SWS_UCM_00360].

Software Packages, Software Clusters, and Versioning Rules

The input unit for UCM is the Software Package. Each package addresses exactly one SoftwareCluster SWS UCM p. 29. Conceptually, the Software Package, with its own manifest and its own signature, encapsulates the Software Cluster along with the cluster manifest and cluster signature TR Methodology p. 77. The package manifest should be transferred at the beginning so that UCM obtains early information, such as on memory requirements or streaming SWS UCM p. 27.

Each SoftwareCluster manifest bears a name and a version in the format StrongRevisionLabelString. If an incoming package changes contents of an already installed cluster, its version must be higher; otherwise, UCM reports an error SWS UCM p. 31. A downgrade is therefore performed by repackaging the old, functioning software with a higher version number SWS UCM p. 31.

GetSwClusterChangeInfo [SWS_UCM_00356] reports pending changes to clusters with the states kAdded, kUpdating, and kRemoved. GetSwClusterInfo [SWS_UCM_00357] returns active clusters in state kPresent, their manifest information GetSwClusterManifestInfo [SWS_UCM_00358] SWS UCM p. 87. A new cluster becomes kAdded after ProcessSwPackage and kPresent after successful Finish SWS UCM p. 24. Older versions refer to the update state as kUpdated; for R25-11, kUpdating applies according to the type definition SWS UCM p. 26.

State diagram: Lifecycle of a Software Cluster between kAdded, kPresent, kUpdating, and kRemoved, controlled by ProcessSwPackage, Finish, and RevertProcessedSwPackages. Sources: SWS UCM p. 26, SWS UCM p. 27, [SWS_UCM_00356]

Transfer: block-wise transfer, registration, and streaming

A transfer begins with TransferStart [SWS_UCM_00345]. The client specifies the package size; UCM assigns a TransferId and returns the maximum permissible block size per call to TransferData [SWS_UCM_00346] via blockSize SWS UCM p. 34. The blocks carry a consecutive blockCounter, which in R21-11 starts at 0x01 and increases by one per block SWS UCM p. 35. TransferExit [SWS_UCM_00347] completes the transfer; during this, UCM checks the received package SWS UCM p. 136.

Transfers are decoupled from the package management states and are possible at any time as long as UCM is running SWS UCM p. 34. Further transfers can be started as long as the sum of the package sizes does not exceed the UCM buffer SWS UCM p. 35. Alternatively, RegisterSoftwarePackage [SWS_UCM_00344] registers a package via URI that already resides in the file system or is still being downloaded. Here, too, UCM returns a TransferId, and completion occurs with TransferExit SWS UCM p. 137. Packages that are no longer needed are removed by DeleteTransfer [SWS_UCM_00348]. A TransferId becomes invalid as soon as the package reaches its final state SWS UCM p. 36.

If UCM supports processing from the stream, ProcessSwPackage may already be called during the transfer. The package then transitions to kProcessingStream and remains there upon further calls to TransferData. With TransferExit and complete processing, it becomes kProcessed SWS UCM p. 40. The R25-11 type definition SwPackageStateType contains exactly these five package states. GetSwPackages [SWS_UCM_00359] SWS UCM p. 86 provides the status of each package. Since R24-11, the specification additionally represents the lifecycle as two separate state machines for transfer state and processing state SWS UCM p. 38.

Processing in the Preparation phase

ProcessSwPackage [SWS_UCM_00349] processes a fully or partially transferred package. Depending on the package content, this means installation, update, or removal of the addressed SoftwareCluster (kInstall, kUpdate, kRemove) SWS UCM p. 29. Unlike during transfer, only one package is processed at a time to preserve consistency. However, multiple clients can have transferred packages processed sequentially SWS UCM p. 40 EXP PlatformDesign p. 58. In R21-11, UCM rejects parallel calls during ongoing processing with ServiceBusy SWS UCM p. 42.

Cancel [SWS_UCM_00351] cancels an ongoing processing, reverts its changes, and releases reserved resources. RevertProcessedSwPackages [SWS_UCM_00350], on the other hand, discards all changes of the packages processed so far SWS UCM p. 41. This must be distinguished from Rollback [SWS_UCM_00353]: A revert is only possible before successful activation, a rollback only afterwards SWS UCM p. 41.

CurrentStatus [SWS_UCM_00361] publishes the overall state as a field with getter and notifier; clients subscribe to it and thereby track the processing SWS UCM p. 123. In R25-11, GetProgress [SWS_UCM_00360] returns the progress of the active state without a TransferId parameter. Older versions instead featured GetSwProcessProgress with a percentage value per TransferId SWS UCM p. 41. Interpretation: GetProgress is likely to replace this query and generalize it to all states.

Time-consuming or state-dependent actions can be paused with Suspend [SWS_UCM_00397] and resumed with Resume [SWS_UCM_00398]. Presumably, this primarily affects long-running processing steps; the requirements do not mention specific actions.

Activation, verification, and completion

In R24-11 and R25-11, the update cycle is divided into three phases: Preparation, Activation, and CleaningUp. The type UpdateStateType comprises the states kPreparing, kActivating, kVerifying, kActivated, kRollingBack, kRolledBack, kRollingBackFailed, and kCleaningUp SWS UCM p. 59 SWS UCM p. 85. Older passages still describe the section before activation with the states kIdle, kProcessing, and kReady SWS UCM p. 50.

Activate [SWS_UCM_00352] activates all processed packages together, regardless of which client processed them SWS UCM p. 45. UCM first checks the dependencies. It then opens an update session with State Management using RequestUpdateSession and calls PrepareUpdate for each affected Function Group SWS UCM p. 33 EXP PlatformDesign p. 58. After that, depending on the system, a machine reset or a restart of the Function Groups follows, as well as verification via VerifyUpdate. Only when this succeeds is kActivated reached SWS UCM p. 51 SWS UCM p. 138. In R21-11, Activate was only permissible from kReady SWS UCM p. 46. For R25-11, this probably corresponds to the end of the Preparation phase.

Finish [SWS_UCM_00354] completes the cycle from kActivated or kRolledBack and cleans up all processing data including the package sources. When leaving kCleaningUp, UCM terminates the session with StopUpdateSession SWS UCM p. 48. All phase transitions are observable via CurrentStatus EXP PlatformDesign p. 70.

Sequence diagram: Successful activation with dependency check, update session, PrepareUpdate, reset or restart, VerifyUpdate, and concluding Finish. Sources: SWS UCM p. 138, SWS UCM p. 33, SWS UCM p. 48, [SWS_UCM_00352], [SWS_UCM_00354]

Embedding into vehicle campaigns: identification and access protection

To enable V-UCM to distribute packages in a targeted manner, it searches for all UCM instances via Service Discovery. It then calls GetId [SWS_UCM_00343] on each proxy and obtains the identifier of the respective UcmModuleInstantiation SWS UCM p. 58 TPS Manifest p. 631. This identifier must be unique for each machine in the vehicle TPS Manifest p. 631.

V-UCM conducts the campaign via its own state machine with the phases SYNCING, TRANSFERRING, PROCESSING, ACTIVATING, and VEHICLE_CHECKING. During synchronization, it queries GetSwClusterInfo among others; in ACTIVATING, it calls Activate of the UCMs SWS V-UCM p. 37 EXP SWArchitecture p. 146. According to R21-11, information such as [SWS_UCM_00357] or [SWS_UCM_00355] may contain personally identifiable data. PackageManagement should therefore only be mapped via a confidentiality-protected channel. In addition, UCM offers its services only after initialization is complete SWS UCM p. 55.

Sequence diagram: V-UCM finds UCM instances via Service Discovery and assigns them to their UcmModuleInstantiation identifiers via GetId. Sources: TPS Manifest p. 631, SWS UCM p. 58, [SWS_UCM_00343]

Behavior in the event of an error

All application errors belong to UCMErrorDomain SWS UCM p. 109. The R25-11 service elements mention, among others:

  • kOperationNotPermitted for calls in the wrong context, such as with [SWS_UCM_00353] and [SWS_UCM_00354].
  • kTransferIdInvalid for invalid TransferIds, such as with [SWS_UCM_00347] and [SWS_UCM_00348].
  • kNotAbleToRevertPackages on [SWS_UCM_00350].
  • kDependencyMissing and kPersistencyAllocationFailed for [SWS_UCM_00352].

Older versions use different names such as InvalidTransferId SWS UCM p. 36.

During transfer, UCM checks, among others, the call sequence, the TransferId, the block counter, the block size against blockSize, the total size, the available memory, and the integrity in a defined order SWS UCM p. 36 SWS UCM p. 37. If authentication fails at TransferExit or ProcessSwPackage, UCM deletes the package along with processed data SWS UCM p. 40. If processing fails, UCM returns to kIdle in R21-11 and cleans up. If other packages have already been processed in this run, it returns to kReady instead SWS UCM p. 50.

During activation, missing dependencies, a rejected update session, or a failed PrepareUpdate lead back to the state prior to activation SWS UCM p. 46 SWS UCM p. 33 SWS UCM p. 51. If VerifyUpdate reports an error or is rejected too many times, UCM transitions to kRollingBack SWS UCM p. 52. If resetting also fails, UCM ends up in kRollingBackFailed; V-UCM handles this case vehicle-wide SWS UCM p. 142. A rollback is only permitted from kActivated or kVerifying SWS UCM p. 47.

UCM is protected against interruptions such as a power failure. At startup, it detects uncontrolled resets, checks non-volatile memory, and resumes interrupted actions; for this purpose, it persists CurrentStatus SWS UCM p. 53. Activation time, result, and last error code are recorded in the history. GetHistory [SWS_UCM_00355] queries them for a time window SWS UCM p. 54.
