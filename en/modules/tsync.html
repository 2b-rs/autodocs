Synchronized time bases as a platform service: role and system boundary

Time Synchronization provides applications with a time that is synchronized with other ECUs. This allows events in a distributed system to be temporally correlated or triggered at a precise point in time. The functionality is offered via Time Base Resources (TBR). As in the StbM, they are distinguished into Synchronized and Offset Master Time Bases as well as Synchronized and Offset Slave Time Bases SWS TimeSync p. 8. The cluster operates daemon-based. It offers the port interfaces SynchronizedTimeBaseProvider and SynchronizedTimeBaseConsumer SWS TimeSync p. 16, EXP SWArchitecture p. 80.

The consumer interface is used by applications and Functional Clusters such as Log and Trace, Intrusion Detection System Manager, or Update and Configuration Management EXP SWArchitecture p. 83. Time Synchronization itself requires four other clusters:

  • Execution Management, to report the state of the daemon SWS TimeSync p. 15.
  • Log and Trace for standardized messages SWS TimeSync p. 15.
  • Persistency for a faster startup SWS TimeSync p. 15.
  • Platform Health Management to monitor the daemon SWS TimeSync p. 16.

The Time Synchronization Providers (TSP) handle the bus protocol independently of the cluster. They only pass time information to the TBR SWS TimeSync p. 28. Time gateway functions and errors during the establishment of the Global Time that are not caused by the module are out of scope SWS TimeSync p. 12.

For freshness values, the cluster uses the platform extension apext::tsync::FVM with three functions: Initialize, GetTxFreshness, and GetRxFreshness [SWS_TS_14200] [SWS_TS_14199] [SWS_TS_14198] EXP SWArchitecture p. 83. The SWS R23-11 still describes secured time synchronization on the Adaptive Platform as not supported SWS TimeSync p. 12. The FVM interface standardized in R25-11 contradicts this.

Context diagram: Time Synchronization serves provider, consumer, and validator applications as well as other clusters. It relies on Execution Management, Persistency, Platform Health Management, Log and Trace, and the FVM plugin. Sources: SWS TimeSync p. 16, EXP SWArchitecture p. 83, EXP SWArchitecture p. 83, SWS TimeSync p. 15

From manifest to time base instance: construction and startup

An application binds a time base by constructing SynchronizedTimeBaseConsumer or SynchronizedTimeBaseProvider with a ara::core::InstanceSpecifier [SWS_TS_01001] [SWS_TS_01101]. In the manifest, TimeSyncPortPrototypeToTimeBaseMapping assigns the corresponding PortPrototype in the context of a Process to a TimeBaseResource TPS Manifest p. 599, TPS Manifest p. 600. For both constructors, a violation regarding this assignment is specified.

Both classes can be moved, but not copied [SWS_TS_01003] [SWS_TS_01005] [SWS_TS_01102] [SWS_TS_01104]. The constructors are thread-safe, whereas destructors and move assignments are not [SWS_TS_01002] [SWS_TS_01004] [SWS_TS_01106].

A Time Master can persist its time. For this purpose, TimeBaseProviderToPersistencyMapping references the provider and a PersistencyDeploymentElement TPS Manifest p. 594. The SWS R23-11 describes the startup as follows SWS TimeSync p. 24:

  • At startup, the backupTimestamp is loaded and a value increased by cyclicBackupInterval is stored immediately.
  • If loading fails, the time base starts at zero.
  • Sync messages are only sent once the link is established and a valid time has been set or the backup value has been restored.

During operation, backups are performed cyclically. During an orderly shutdown, storage takes place without an offset SWS TimeSync p. 25. The payload does not contain any R25-11 requirements for this sequence.

Activity diagram: The Time Master restores the time from persistency or starts at zero. It transmits only when the link is available and the time is valid. Sources: SWS TimeSync p. 24, SWS TimeSync p. 25, TPS Manifest p. 594

Specifying time as a provider: SetTime, UpdateTime, and rate correction

The provider has two ways to set the clock:

  • SetTime sets the value and immediately triggers a transmission on the bus [SWS_TS_01107].
  • UpdateTime updates only locally. Transmission occurs only in the next cycle [SWS_TS_01108] EXP SWArchitecture p. 80.

Both methods return ara::core::Result<void> and, in R25-11, expect the User Data as const UserData&. One location in the document still shows a signature with ara::core::Span<const ara::core::Byte> and default argument SWS TimeSync p. 42. The signature from the requirement is normative. GetCurrentTime provides the time independently of the sync status [SWS_TS_01109].

With SetRateCorrection, the application specifies a correction factor for transmitted time values [SWS_TS_01110]. According to SWS R23-11, two restrictions apply to this SWS TimeSync p. 32:

  • The factor only takes effect if allowProviderRateCorrection is set.
  • If its absolute value is greater than MasterRateDeviationMax, a deviating value is actually applied.

SetUserData and GetUserData manage the User Data distributed by the Time Master [SWS_TS_01112] [SWS_TS_01113]. In R25-11, UserData is a buffer with at most kMaxUserDataSize = 3 bytes and the field size [SWS_TS_14231] [SWS_TS_14232] [SWS_TS_14233]. This replaces the byte vector described in SWS R23-11 SWS TimeSync p. 28.

Sequence diagram: SetTime distributes the new time to the slaves immediately, UpdateTime only in the next transmission cycle. Sources: [SWS_TS_01107], [SWS_TS_01108], EXP SWArchitecture p. 225

Reading time as a consumer: status snapshot and status flags

The consumer reads the time via GetTimeWithStatus. The method generates a snapshot with status flags, configuration, as well as local and synchronized time [SWS_TS_01009]. The R22-11 interface description still mentions a dedicated GetCurrentTime on the consumer SWArchitecture p. 59. It is missing in the R25-11 requirements. Timestamp is a std::chrono::time_point on the clock TimeBase in nanoseconds. This clock is explicitly not steady [SWS_TS_01251] [SWS_TS_01265].

The snapshot SynchronizedTimeBaseStatus can be copied and moved, but not default-constructed [SWS_TS_01057] [SWS_TS_01058] [SWS_TS_01061]. Its queries are thread-safe:

  • GetSynchronizationStatus provides the synchronization status at the time of creation [SWS_TS_01053].
  • GetLeapJump reports only jumps since the previous object creation [SWS_TS_01054].
  • GetCreationTime provides the creation time as ara::core::Optional<Timestamp> [SWS_TS_01055].
  • GetCreationLocalTime provides the creation time in local time [SWS_TS_14176].
  • GetUserData provides the User Data received from the Time Master [SWS_TS_01056].

Interpretation: The Optional will likely remain empty as long as no valid synchronized point in time is available.

SynchronizationStatus starts in the initial state kNotSynchronizedUntilStartup [SWS_TS_01050]. Further values are kTimeOut (synchronization lost or delayed), kSynchronized, and kSynchToGateway SWS TimeSync p. 23. A successful update without the SYNC_TO_GATEWAY bit set leads to kSynchronized SWS TimeSync p. 28. LeapJump distinguishes between kTimeLeapNone, kTimeLeapFuture, and kTimeLeapPast [SWS_TS_01051].

Two further queries evaluate the rate correction. GetRateCorrected indicates whether a rate correction was calculated. GetRateExceeded indicates whether the deviation exceeds rateCorrectionThreshold [SWS_TS_14226] [SWS_TS_14229]. In the case of an Offset TBR, the status contains the information of the assigned Synchronized TBR, and the creation time is identical SWS TimeSync p. 62.

Sequence diagram: Synchronization runs in the background. The application receives a snapshot whose values apply to the time of creation. Sources: [SWS_TS_01009], [SWS_TS_01053], EXP SWArchitecture p. 225

State diagram: The synchronization status leads from the initial state via successful updates to kSynchronized and upon loss to kTimeOut. The transition to kSynchToGateway is interpreted. Sources: [SWS_TS_01050], SWS TimeSync p. 23, SWS TimeSync p. 28

Synchronization quality: rate correction, offset correction, and time jumps

A slave measures its rate deviation only in the kSynchronized state. It measures continuously and aligns the measurements with the reception of time values SWS TimeSync p. 29. The measurement duration is based on ara::core::SteadyClock. rateCorrectionsPerMeasurementDuration defines how many measurements run in parallel SWS TimeSync p. 29. GetRateDeviation returns r_rc − 1. As long as no value has been calculated yet, it returns 0.0 [SWS_TS_01008] SWS TimeSync p. 30, SWS TimeSync p. 22. Offset TBRs do not perform their own rate correction SWS TimeSync p. 12.

How an offset is corrected depends on its magnitude SWS TimeSync p. 31, SWS TimeSync p. 32:

  • Offsets starting at offsetCorrectionJumpThreshold are corrected via jump.
  • Smaller offsets are compensated via an additional rate r_oc, which applies for offsetCorrectionAdaptionInterval.
  • A threshold of 0 forces pure jump correction.

Time jumps are only monitored after the first synchronization and only if the respective threshold is non-zero. Detected jumps appear as LeapJump SWS TimeSync p. 27.

Activity diagram: After each received time value, the TBR decides between jump and rate correction and subsequently checks for time jumps. Sources: SWS TimeSync p. 29, SWS TimeSync p. 31, SWS TimeSync p. 27

Asynchronous feedback: notifiers, precision measurement, and Time Validation

The consumer can register three types of notifiers:

  • for each status change, i.e., synchronization status, time jump, or User Data [SWS_TS_01010],
  • only for the synchronization status [SWS_TS_01012],
  • only for time jumps [SWS_TS_01014].

At most one notifier is active per type. Any further registration overwrites the previous one SWS TimeSync p. 33. Deregistration is carried out via the appropriate unregister method in each case [SWS_TS_01011] [SWS_TS_01013] [SWS_TS_01015]. The callback types are marked as not thread-safe [SWS_TS_14221] [SWS_TS_14222]. Interpretation: Applications will probably have to protect shared data in callbacks themselves.

RegisterTimePrecisionMeasurementNotifier is used for precision measurements. After each synchronization, the notifier provides a block containing global and local time, timeBaseStatus, rateDeviation, and pathDelay [SWS_TS_01018] [SWS_TS_01401] [SWS_TS_01406] [SWS_TS_01403] [SWS_TS_01405] [SWS_TS_01408]. Time Synchronization does not buffer these blocks. Whoever needs queuing must implement it in the notifier. For Offset Time Bases, only global time and status are written SWS TimeSync p. 34.

Time Validation delivers raw data to a separate validator application SWS TimeSync p. 38. For this purpose, consumers register a ConsumerTimeBaseValidationNotification, and providers a ProviderTimeBaseValidationNotification [SWS_TS_01016] [SWS_TS_01114]. The callbacks are triggered as follows [SWS_TS_00420] [SWS_TS_00421] [SWS_TS_00422] [SWS_TS_00423] SWS TimeSync p. 35:

  • SetSlaveTimingData upon reception of a Follow_Up,
  • SetMasterTimingData upon sending a Sync message,
  • SetPdelayInitiatorData and SetPdelayResponderData after completed Pdelay measurement.

Sending and receiving messages is decoupled from the forwarding of measurement data SWS TimeSync p. 36.

Sequence diagram: A registered status notifier is called upon a status change, time jump, or new User Data. Sources: [SWS_TS_01010], EXP SWArchitecture p. 226, SWS TimeSync p. 33

Sequence diagram: Sync, Follow_Up, and Pdelay events trigger the four validation callbacks on master and slave applications. Sources: [SWS_TS_00420], [SWS_TS_00423], SWS TimeSync p. 38, SWS TimeSync p. 35

Behavior in the event of an error

The cluster reports errors via ara::core::Result SWS TimeSync p. 64. The error codes are located in TsyncErrc. An example is kDaemonConnectionLost: An action cannot be executed because the connection to the daemon was lost [SWS_TS_00901]. GetTsyncErrorDomain, MakeErrorCode, ThrowAsException, and TsyncException integrate the codes into the error concept of ara::core [SWS_TS_00909] [SWS_TS_00910] [SWS_TS_00908] [SWS_TS_00903].

A Result is returned by the write provider methods as well as GetRateCorrected and GetRateExceeded [SWS_TS_01107] [SWS_TS_01110] [SWS_TS_01112] [SWS_TS_14226]. In contrast, GetTimeWithStatus and GetRateDeviation return their value directly [SWS_TS_01009] [SWS_TS_01008]. If provider rate correction is not enabled, SetRateCorrection does nothing according to SWS R23-11 and reports kLimitsExceeded SWS TimeSync p. 32.

Faults in the time base itself become visible as status SWS TimeSync p. 23:

  • kTimeOut indicates lost synchronization. In the precision block, this corresponds to the TIMEOUT bit [SWS_TS_01403].
  • LeapJump indicates time jumps.

If loading the backup timestamp fails, the time base starts at zero SWS TimeSync p. 24. The FVM extension has its own error domain TsyncFvmErrc. Among other things, it contains the recoverable error kFVNotAvailable. In case of a failure, Initialize reports kFVInitializeFailed [SWS_TS_14202] [SWS_TS_14200] [SWS_TS_14212].
