Communication model

ara::com is the standardized application interface of the Communication Management Functional Cluster. The cluster establishes and monitors communication paths between applications on the same or different machines; the specific internal middleware architecture remains an implementation matter. SWS CM §7.1.1 “Architectural concepts” and SWS CM §7.1.2 “Design decisions” classify the API as a protocol-abstracted, service-oriented interface.

Two roles arise from a modeled service interface: The proxy is the local representation for the consumer, the skeleton connects the provider implementation with the transport infrastructure. Methods, events, fields and triggers are the four intended forms of communication. EXP ARAComAPI §4.1 “Proxy/Skeleton Architecture”, EXP ARAComAPI §4.2 “Means of Communication” and SWS CM §7.1.3 “Communication paradigms and Definitions” describe this division of labor.

From service offering to use

On the provider side, a skeleton is created and offered. On the consumer side, a one-off FindService provides the currently known instances; StartFindService monitors availability changes. A handle identifies a found instance and is used for proxy creation. In the event of temporary unavailability, the communication path should be re-established in a later offer. SWS CM §7.5.1 “Offer service”, SWS CM §7.5.10 “Find service” and SWS CM §7.5.11 “Service proxy creation” provide the function semantics.

Data and interaction forms

Events transport data to registered consumers; Triggers use the same subscription mechanism without payload. Methods model request/response and can provide a Future. A field combines reading and writing method character with notification of value changes. EXP ARAComAPI §4.3 “Event and Trigger based communication”, EXP ARAComAPI §4.4 “Method based communication” and EXP ARAComAPI §4.5 “Field based communication” explain the application view.

Operating rules and security context

Subscribe() is asynchronous: Only kSubscribed in the status or in the status handler occupies an actually established subscription. Received samples have a controlled transfer of ownership and must be returned before deregistration or proxy destruction. [SWS_CM_12006] and [SWS_CM_00085] are the relevant rules for this. E2E protection supplements data transmission with status information that can be evaluated per sample; SecOC can use freshness value management via the platform extension. SWS CM §7.4 “Safety” and SWS CM §7.3.2 “Secure Communication” provide the overarching framework.

This allows the same application code to work with a different binding on the deployment side without interpreting its representation. Behavior in the event of an error

The one-time service search FindService() returns the service handles that are appropriate at that time; the result list can be empty if no suitable service instance currently exists. A technical search error, on the other hand, is reported as a ara::core::Result error, for which the API sets, among other things, ComErrc::kCommunicationFailure. The continuous search with StartFindService() reports availability changes via its handler, which receives the container of all matching instances. EXP ARAComAPI §5.3.2 “RadarService Proxy Class Example” [SWS_CM_00122] [SWS_CM_00383]

An event subscription has the states kNotSubscribed, kSubscriptionPending and kSubscribed. Since Subscribe() initially only accepts the subscription order, the status when queried can still be kSubscriptionPending; GetSubscriptionState() and SetSubscriptionStateChangeHandler() make the effective state accessible. If the service becomes temporarily unavailable, the handler reports kSubscriptionPending; after successful re-subscription it reports kSubscribed. The communication management implementation must restore an active subscription after temporary unavailability. If the application holds more SamplePtr objects than promised for Subscribe(), GetNewSamples() returns the error ComErrc::kMaxSamplesExceeded; Samples may have been skipped. [SWS_CM_00310] [SWS_CM_00333] [SWS_CM_00315] [SWS_CM_00701] EXP ARAComAPI §5.3.5.2 “Monitoring Event Subscription”

Statechart: Event subscription transitions upon loss of service and automatic recovery. Sources: [SWS_CM_00310] [SWS_CM_00315] EXP ARAComAPI §5.3.5.2 “Monitoring Event Subscription”.

A Request/Response method call immediately returns a ara::core::Future<Output>. In addition, the result and possible errors are queried: For a configured application error response, the result contains a ara::core::ErrorCode from the domain of ApApplicationError; for a service that is no longer available, ComErrc::kServiceNotAvailable is set. If the platform detects an error locally that causes the remote call that has already been triggered to fail, it must provide the associated future with ComErrc::kCommunicationFailure. ara::com does not offer its own timeout monitoring for method calls; blocking future operations can therefore wait indefinitely if an answer is lost. For E2E-protected events, the application can inspect the E2E check result for each SamplePtr using GetProfileCheckStatus(), for example kOk, kRepeated, kWrongSequence, or kError. The SMState consolidates the check history for current E2E monitoring; the most recently checked sample may be used only with kValid and a non-erroneous profile status. If the E2E check of a method response fails, the implementation sets an error from ara::com::e2e::ComE2EErrorDomain in the associated Promise and thus in the Future result. 1. Modeling in the manifesto

The starting point is a ServiceInterface in the ARXML manifest (service interface description). The elements of the service are modeled there: Events, Methods (incl. Fire&Forget), Fields (with Get/Set/Notifier) as well as the namespace hierarchy of the interface.

2. What the generator produces

From the manifest, the tooling of the AP stack generates C++ bindings for each service interface (<SI>) two central classes:

  • The Skeleton class <SI-Namespace>::skeleton::<SI>Skeleton [SWS_CM_00002] in the header <si>_skeleton.h — the server-side base class of the service provider.
  • The Proxy class <SI-Namespace>::proxy::<SI>Proxy [SWS_CM_00004] in the header <si>_proxy.h — the client-side delegate.

For each event, field and method, additional inner classes are created in the namespaces events, fields and methods (e.g. <SI-Namespace>::proxy::events::<Event>). The placeholder class pages of this module (names with <…>) document exactly these generated types.

3. Offer Service (Skeleton Page)

  • Derive your own implementation class from <SI>Skeleton and the purely virtual ones Override service methods: regular methods return ara::core::Future<…Output> [SWS_CM_00191], Fire&Forget methods void [SWS_CM_90434].
  • Construct instance with a ara::core::InstanceSpecifier; the processing mode (MethodCallProcessingMode: kEvent, kEventSingleThread, kPoll) controls processing incoming calls [SWS_CM_00301].
  • Offer service with OfferService() [SWS_CM_00101] and with StopOfferService() take back [SWS_CM_00111].
  • Events about events::<Event>::Send() publish [SWS_CM_00162], fields about fields::<Field>::Update() update [SWS_CM_00119].

4. Use the service (proxy site)

  • Search available instances: synchronously via <SI>Proxy::FindService() [SWS_CM_00122] (with InstanceSpecifier [SWS_CM_00622]) or continuously via StartFindService() [SWS_CM_11352] [SWS_CM_11365].
  • The result is a <SI>Proxy::HandleType [SWS_CM_00312]; this becomes the proxy via the static factory <SI>Proxy::Create() generated [SWS_CM_10438] (Handle available later via GetHandle() [SWS_CM_10383]).
  • Events: events::<Event>::Subscribe() [SWS_CM_00141], received via GetNewSamples() [SWS_CM_00701].
  • Fields: fields::<Field>::Get() [SWS_CM_00112] / Set() [SWS_CM_00113]; Method calls run asynchronously and deliver ara::core::Future.
