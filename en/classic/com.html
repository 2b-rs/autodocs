Coordinates PDU routing, signal processing, and network mode management of the communication stack.

With com, comm, and pdur, the "Communication Services" module cluster bundles the central signal processing, PDU routing, and network mode management of the AUTOSAR Classic Platform SWS_PDURouter p. 24. It ensures that signals from the application are packed consistently, I-PDUs are forwarded protocol-independently to the communication interfaces via static routing tables, and bus resources are activated as needed [SWS_Com_00197], [SWS_PduR_00160]. Furthermore, selective partial network routing, deadline monitoring, and degradation mechanisms for energy-saving ECU operation are coordinated via standardized interfaces [SWS_ComM_00110].

The "Communication Services" module cluster forms the message- and signal-processing backbone of the AUTOSAR Classic Platform. It integrates the three basic software modules com, comm, and pdur in the services layer: while module com serializes, filters, and monitors RTE signals and signal groups into I-PDUs [SWS_Com_00197], the pdur, as a protocol-independent routing instance, handles 1:1 and 1:n routing of I-PDUs between upper users and the bus interfaces without modifying payload data [SWS_PduR_00160]. Module comm coordinates the communication status by evaluating requests from SW-Cs or diagnostic channels and activating the channels demand-driven via Bus State Managers [SWS_ComM_00110], [SWS_ComM_00873].

Architecture diagram: Module relationships and embedding of the Communication Services cluster into the basic software. Sources: SWS_PDURouter p. 24, SWS_COMManager p. 30

In the transmission and reception sequence, the modules work in close coordination. For transmission requests, com forwards I-PDUs via PduR_ComTransmit to pdur, which translates I-PDU IDs and drives the target drivers [SWS_PduR_00406], [SWS_PduR_00766]. In the case of clocked interfaces (e.g., LIN), the lower driver requests data demand-driven via TriggerTransmit, which the PDU Router passes through unbuffered up to com [SWS_Com_00001], [SWS_PduR_00430]. Incoming I-PDUs are handed over by pdur via RxIndication to com for signal unpacking, and can simultaneously be replicated to other buses via gateway routes [SWS_Com_00123], [SWS_PduR_00362].

The lifecycle is largely determined by the states of the comm and the pdur. After system start, PduR_Init switches the router from PDUR_UNINIT to PDUR_ONLINE [SWS_PduR_00308], [SWS_PduR_00326]. The Communication Manager manages the channels via the core states COMM_NO_COMMUNICATION, COMM_FULL_COMMUNICATION, and COMM_SILENT_COMMUNICATION [SWS_ComM_00871]. Through mechanisms such as communication inhibition (e.g., ComM_LimitChannelToNoComMode) and dynamic routing path groups (PduR_EnableRouting / PduR_DisableRouting), the cluster supports selective degradation and energy-saving states [SWS_ComM_00163], [SWS_PduR_00615].

System Architecture & Role of the Module Cluster

The "Communication Services" module cluster forms the functional center of the communication stack of the AUTOSAR Classic Platform (Release R20-11) within the services layer. It is composed of the three closely integrated basic software modules com (AUTOSAR COM), comm (Communication Manager), and pdur (PDU Router). Together, these modules encapsulate the bus-independent management, routing, and signal abstraction of the ECU network with respect to the runtime environment (RTE) and application software components (SW-Cs) according to the AUTOSAR layered architecture SWS_PDURouter p. 24. Downward, the cluster interacts directly with the interfaces of the communication hardware abstraction layer (CanIf, LinIf, FrIf, EthIf) as well as the transport protocols (CanTp, FrTp, LinTp) according to standards such as ISO 11898 (CAN), ISO 17987 (LIN), ISO 10681 (FlexRay), and ISO 15765-2 (Transport Layer) AUTOSAR_CP_SWS_PDURouter p. 110.

Module com implements signal-oriented data processing: it transforms RTE signals and signal groups into interaction layer protocol data units (I-PDUs), performs signal packing and unpacking, endianness and sign conversion, as well as filtering and transmission deadline monitoring [SWS_Com_00197], [SWS_Com_00784]. Module pdur serves as a protocol-independent routing instance that forwards I-PDUs without payload modification between upper service modules (Com, DCM) and lower communication interfaces or transport protocols, serves local 1:n multicast paths, and implements direct gateways [SWS_PduR_00160], [SWS_PduR_00406]. The comm performs resource- and state-oriented control: it aggregates communication requests from software components, the BSW mode manager (BswM), and diagnostic services (DCM according to ISO 14229 / UDS), and coordinates operating modes of physical channels and partial network clusters (PNC) [SWS_ComM_00110], [SWS_ComM_00873].

Interplay & Interaction Paths Between the Modules

Interaction within the cluster occurs via clearly defined call chains for transmit, receive, and confirmation paths. During transmission, the RTE calls module-specific transmit APIs of com, such as Com_SendSignal or Com_SendSignalGroup, to provide data atomically [SWS_Com_00197], [SWS_Com_00200]. Module com packs the signals into the corresponding I-PDU and passes it synchronously to the PDU Router using PduR_ComTransmit [SWS_PduR_00406]. The PDU Router looks up the destination I-PDU in its static routing tables, converts the I-PDU ID, and forwards the transmit request unchanged to the responsible lower layer, for example via CanIf_Transmit [SWS_PduR_00161], [SWS_PduR_00766]. After successful transmission on the bus, the interface confirms the transfer to pdur via PduR_<User:Lo>TxConfirmation [SWS_PduR_00365], which forwards the call to Com_TxConfirmation [SWS_Com_00124].

For time-triggered or polling-based bus systems such as LIN or FlexRay, the stack decouples the transmit request using the TriggerTransmit mechanism: Module com initiates readiness for transmission, but stores the payload data internally AUTOSAR_CP_SWS_PDURouter p. 101. As soon as the bus scheduler (for example in LinIf or FrIf) reaches the transmission point in time, the lower layer calls PduR_<User:Lo>TriggerTransmit [SWS_PduR_00430]. The PDU Router delegates this call immediately and unbuffered to Com_TriggerTransmit [SWS_Com_00001], whereupon com copies the current data directly into the driver buffer SWS_PDURouter p. 107.

In the receive path, the lower communication interface signals the arrival of an I-PDU via PduR_<User:Lo>RxIndication [SWS_PduR_00362]. The PDU Router forwards the PDU synchronously via Com_RxIndication to com [SWS_Com_00123], where signals are unpacked, filtered, and made available to the RTE AUTOSAR_CP_SWS_PDURouter p. 97. At the same time, pdur supports gatewaying: a received I-PDU can be delivered locally to com and forwarded in parallel to an outgoing network interface [SWS_PduR_00621], SWS_PDURouter p. 114. For transport protocol PDUs (e.g. CanTp or DCM), pdur orchestrates the segmented transmission via StartOfReception, CopyRxData, and TpRxIndication [SWS_PduR_00507], [SWS_Com_00691], [SWS_Com_00692].

Sequence diagram: Controlled I-PDU transmit path and TriggerTransmit sequence via PduR. Sources: SWS_PDURouter p. 107, AUTOSAR_SWS_COM p. 114

Synchronization, reentrancy and task contexts

The modules of the cluster operate in a hybrid execution context consisting of synchronous function calls and periodic task processing. Receive callbacks (RxIndication) and transmit confirmation callbacks (TxConfirmation) are frequently triggered in the interrupt context of the underlying drivers or in the task context of the communication interfaces. Therefore, routing functions of the PDU Router are designed to be strictly reentrant SWS_PDURouter p. 88. Canceling ongoing transmissions via PduR_<User:Up>CancelTransmit is specified as reentrant for different PDU-IDs, but non-reentrant for identical PDU-IDs [SWS_PduR_00769].

In module comm, the primary user interface ComM_RequestComMode is explicitly designed for concurrent calls by multiple runnables (canbeInvokedConcurrently = TRUE) and is implemented as reentrant [SWS_ComM_00110], SWS_COMManager p. 107. Status query functions such as ComM_GetRequestedComMode [SWS_ComM_00079] and ComM_GetMaxComMode [SWS_ComM_00085] are also available as reentrant. Administrative functions such as ComM_SetECUGroupClassification [SWS_ComM_00552], ComM_GetInhibitionStatus [SWS_ComM_00619] as well as dynamic mapping APIs (e.g. ComM_UpdatePncToChannelMapping [SWS_ComM_01037]), on the other hand, are defined as non-reentrant and require invocation from protected task levels.

To prevent data inconsistencies during multiple signal accesses, AUTOSAR prescribes atomic signal processing via signal groups for composite data types [SWS_Com_00197], [SWS_Com_00200]. The RTE unpacks signals and serializes them consistently into local shadow buffers before Com_SendSignalGroup releases the I-PDU SWS_RTE p. 329. Cyclic transmit activities and deadline monitoring are handled via periodic MainFunctions of the modules, with I-PDU groups being activated or stopped on demand by the BswM via Com_IpduGroupStart and Com_IpduGroupStop [SWS_Com_00784], SWS_BSWModeManager p. 93.

Typical lifecycles and operating modes

The lifecycle of the module cluster follows a strict initialization and operating sequence. During startup, the PDU Router is initially in the state PDUR_UNINIT, in which no routing is permitted [SWS_PduR_00325], [SWS_PduR_00330]. Calling PduR_Init allocates and initializes all internal buffers, and the module transitions to state PDUR_ONLINE [SWS_PduR_00308], [SWS_PduR_00742]. Module comm starts analogously in state COMM_UNINIT [SWS_ComM_00668]. Via ComM_Init, persistent parameters (e.g. inhibit counters and PNC mappings) are read from NVRAM and the channel state machines are transitioned to the default state COMM_NO_COM_NO_PENDING_REQUEST [SWS_ComM_00146], [SWS_ComM_00674].

The channel state machine in comm controls three top-level communication modes: COMM_NO_COMMUNICATION, COMM_SILENT_COMMUNICATION, and COMM_FULL_COMMUNICATION [SWS_ComM_00871]. Users can request only full communication or no communication [SWS_ComM_00110]. If a request from users or the DCM is received in COMM_NO_COM_NO_PENDING_REQUEST (ComM_DCM_ActiveDiagnostic), the state machine transitions to COMM_NO_COM_REQUEST_PENDING [SWS_ComM_00873]. As soon as communication permission is granted, the transition to COMM_FULL_COM_NETWORK_REQUESTED occurs, whereupon comm requests transmission and reception readiness via the respective Bus State Manager [SWS_ComM_01018], SWS_COMManager p. 64.

If full communication is released by all users, the channel switches to COMM_FULL_COM_READY_SLEEP and requests Nm_NetworkRelease in case of full network management SWS_COMManager p. 78. To prepare for bus sleep, the state machine transitions to COMM_SILENT_COM, in which transmission is inhibited but reception remains active for synchronization [SWS_ComM_00391], [SWS_ComM_00829]. Upon indication of ComM_<Bus>SM_BusSleepMode, COMM_NO_COM_NO_PENDING_REQUEST is reached again [SWS_ComM_91000]. Wakeup by the EcuM is processed via ComM_EcuM_WakeUpIndication or ComM_EcuM_PNCWakeUpIndication [SWS_ComM_91001]. An ECU shutdown via ComM_DeInit is only permitted once all channels are fully deinitialized in COMM_NO_COMMUNICATION [SWS_ComM_00147].

State diagram: State model and operating mode transitions of a ComM communication channel. Sources: SWS_COMManager p. 112, SWS_COMManager p. 63, SWS_COMManager p. 71

Error Handling, DET Tracing, and Degradation

The error and degradation management of the cluster relies on standardized notifications to the Development Error Tracer (DET) as well as configurable restriction mechanisms (Communication Inhibition). If development error detection is enabled, pdur reports uninitialized calls via error code PDUR_E_UNINIT [SWS_PduR_00100], [SWS_PduR_00119]. Incorrect routing table IDs during control calls are penalized with PDUR_E_ROUTING_PATH_GROUP_ID_INVALID [SWS_PduR_00648], whereas invalid pointer parameters are reported as PDUR_E_PARAM_POINTER SWS_PDURouter p. 72. In module comm, calling supervisory APIs prior to initialization leads to returning the status COMM_UNINIT [SWS_ComM_00242], [SWS_ComM_00668].

For controlled degradation and power consumption reduction, comm provides interfaces for communication inhibition: via ComM_LimitChannelToNoComMode or ComM_LimitECUToNoComMode, the transition to full communication can be inhibited for individual channels or the entire ECU [SWS_ComM_00124], [SWS_ComM_00163]. Furthermore, ComM_PreventWakeUp suppresses network-based wakeup of the ECU [SWS_ComM_00156]. The authorization of these inhibitions is controlled via mask bits (ComM_SetECUGroupClassification [SWS_ComM_00552]). Rejected full communication requests are logged in a non-volatile error memory counter that can be diagnosed via ComM_ReadInhibitCounter and ComM_ResetInhibitCounter [SWS_ComM_00108], [SWS_ComM_00224]. Diagnostic requests from the DCM temporarily override active communication restrictions to keep the ECU accessible at all times [SWS_ComM_00873], SWS_COMManager p. 69.

During runtime, communication paths in the PDU Router can be dynamically degraded or activated: by means of PduR_EnableRouting and PduR_DisableRouting, the BswM switches configured routing path groups immediately [SWS_PduR_00615], [SWS_PduR_00617], [SWS_PduR_00715]. If a routing path is disabled, transmit and receive calls of the affected I-PDUs reject the data transmission immediately with E_NOT_OK or BUFREQ_E_NOT_OK SWS_PDURouter p. 69. For post-build configurations, pdur monitors configuration integrity via PduR_GetConfigurationId to preclude misallocations due to changed table and buffer boundaries in RAM and NVRAM [SWS_PduR_00341], [SWS_PduR_00771], SWS_PDURouter p. 160.
