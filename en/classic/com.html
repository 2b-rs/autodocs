System architecture and role of the module cluster

The Communication Services are located between the RTE and the bus-specific interface and transport protocol modules. The cluster consists of a data path (Com, PduR) and a control path (ComM). For COM, the PDU Router is the only lower layer (RS COM p. 12).

  • Com provides the signal API to the RTE, e.g. Com_SendSignal [SWS_Com_00197] and Com_ReceiveSignal [SWS_Com_00198]. It maps the signals to I-PDUs.
  • PduR transmits I-PDUs unchanged and consistently to the destination modules [SWS_PduR_00160]. A routing path is uniquely determined by the source ID and the destination IDs [SWS_PduR_00161]. Downwards, the PduR serves interfaces and transport protocols [SWS_PduR_00424]. Upwards, it serves Com and TP users such as DCM (SWS PduR p. 24).
  • ComM handles resource management for its users. Users are runnables, SW-Cs, BswM, or DCM (SWS ComM p. 30). ComM manages the modes from ComM_ModeType [SWS_ComM_00672]. It implements the modes via <BusSm>_RequestComMode with the responsible Bus State Manager [SWS_ComM_00958], [SWS_ComM_00962].

ECU-wide control is handled by the BswM. It can start and stop I-PDU groups in Com ([SWS_Com_91001], [SWS_Com_91002]). It also switches routing path groups of the PduR ([SWS_PduR_00615], [SWS_PduR_00617], SWS BswM p. 166).

Context diagram: Com and PduR form the data path, ComM controls Bus State Managers and Nm, BswM switches groups in Com and PduR. Sources: [SWS_PduR_00424], [SWS_Com_00669], [SWS_ComM_00958], [SWS_ComM_00164], [SWS_ComM_00275], [SWS_ComM_00873]

Interaction and interaction paths

Transmission. Com passes an I-PDU with PduR_ComTransmit [SWS_Com_00669]. The PduR converts the ID to the destination module [SWS_PduR_00766] and calls <Lo>_Transmit for each destination [SWS_PduR_00625].

  • In case of singlecast, the PduR passes through the return value [SWS_PduR_00626].
  • In case of multicast, one successful destination is sufficient for E_OK [SWS_PduR_00218].
  • The PduR does not buffer PDUs from an upper layer [SWS_PduR_00629].
  • The confirmation reaches Com as Com_TxConfirmation [SWS_PduR_00627]. In case of multicast, this occurs only after the last confirmation [SWS_PduR_00589].

Trigger Transmit. Some interfaces fetch the data only at the transmission time. In that case, the PduR forwards the request to Com_TriggerTransmit [SWS_PduR_00430] and returns its return value [SWS_PduR_00661]. Com returns E_NOT_OK in two cases: when the I-PDU is stopped [SWS_Com_00884] or when the buffer is too small [SWS_Com_00869]. The sequence is shown in SWS PduR p. 106.

Sequence diagram: Transmitting an I-PDU via FrIf is a two-stage process: first the transmit request, later fetching the data via Trigger Transmit. Sources: [SWS_Com_00197], [SWS_PduR_00430], [SWS_Com_00884], [SWS_PduR_00627], SWS PduR p. 106

Reception and gateway. A call of PduR_<Lo>RxIndication [SWS_PduR_00362] leads to Com_RxIndication [SWS_PduR_00621] for each destination. The 1:n routing to upper layers [SWS_PduR_00164] can be combined with gateways between interfaces [SWS_PduR_00436]. An example is the routing CAN→CAN with simultaneous local reception (SWS PduR p. 114). Large I-PDUs use the TP path with Com_StartOfReception, Com_CopyRxData, and Com_TpRxIndication ([SWS_Com_00691], [SWS_Com_00692], [SWS_Com_00650]). The PduR forwards the TP callbacks there ([SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429]).

Signal groups. To ensure atomicity, the RTE first updates all group signals. Afterwards, it triggers Com_SendSignalGroup ([SWS_Com_00200], SWS RTE p. 329). The COM Based Transformer, in contrast, exchanges the group as a byte array ([SWS_Com_00851], [SWS_Com_00854]). The position and length of this array are specified in [SWS_Com_00844] and [SWS_Com_00845].

Control path. A user requests communication with ComM_RequestComMode [SWS_ComM_00110]. Alternatively, DCM reports active diagnostics [SWS_ComM_00873]. ComM then requests the mode from the Bus State Manager and coordinates with Nm depending on the NM variant (SWS ComM p. 167). With partial networking, ComM writes the PNC bits via Com_SendSignal ([SWS_ComM_00164], [SWS_ComM_00959]). The BswM can switch routing path groups depending on the PNC state. This source originates from release R21-11 and is informative (ModeManagementGuide p. 50).

Sequence diagram: A communication request leads to the bus and NM request via waiting for CommunicationAllowed. Sources: [SWS_ComM_00110], [SWS_ComM_00871], [SWS_ComM_00390], [SWS_ComM_00675], SWS ComM p. 167

Synchronization, reentrancy and task contexts

Com processes cyclically in three main functions: Com_MainFunctionRx, Com_MainFunctionTx, and Com_MainFunctionRouteSignals. Each is reentrant for different instances, but not for the same instance ([SWS_Com_00398], [SWS_Com_00399], [SWS_Com_00400]). The ECU extract describes their call periods as time bases (Interoperability p. 98). If a ComPreparationNotification is configured, the MainFunctionTx calls it prior to I-PDU processing [SWS_Com_00886]. The RTE provides it per instance (SWS RTE p. 832).

ComM processes per channel in ComM_MainFunction_<ComMChannel.ShortName> [SWS_ComM_00429]. ComM_RequestComMode is reentrant [SWS_ComM_00110], and the associated runnable may be called concurrently (SWS ComM p. 107). The NM callbacks operate asynchronously [SWS_ComM_00390]. ComM_Nm_PrepareBusSleepMode is reentrant, but not for the same NM channel [SWS_ComM_00391].

Throughout the data path, the same rule applies: reentrant for different PduIds, non-reentrant for the same PduId. This affects Com_RxIndication [SWS_Com_00123], Com_TxConfirmation [SWS_Com_00124], PduR_<Lo>RxIndication [SWS_PduR_00362], and PduR_<Lo>TxConfirmation [SWS_PduR_00365]. Interpretation: The integrator will likely have to prevent the same PDU from being reported simultaneously from interrupt and task context, for example by means of exclusive areas. The sources do not specify the call context.

With multiple partitions, three rules apply to ComM:

  • ComM must allow calls from foreign partitions, for example via a satellite [SWS_ComM_01019].
  • ComM calls <Bus>SM APIs only in the partition of the respective Bus State Manager [SWS_ComM_01020].
  • ComM uses the signal APIs of Com only in the partition of the respective signal [SWS_ComM_01021].

Lifecycles and operating modes

PduR possesses exactly one state machine [SWS_PduR_00644] with the states PDUR_UNINIT and PDUR_ONLINE ([SWS_PduR_00324], [SWS_PduR_00742]). After power-on, it is uninitialized [SWS_PduR_00325]. PduR_Init [SWS_PduR_00334] causes three things:

  • Transition to PDUR_ONLINE [SWS_PduR_00326],
  • Release of all buffers [SWS_PduR_00645],
  • Setting of the default values [SWS_PduR_00308].

Routing is performed only in the PDUR_ONLINE state ([SWS_PduR_00328], [SWS_PduR_00330]). The routing path groups start according to configuration [SWS_PduR_00709]. Post-build routing tables may only be exchanged in the uninitialized state [SWS_PduR_00296]. The active configuration is returned by PduR_GetConfigurationId [SWS_PduR_00280].

Com is initialized with Com_Init [SWS_Com_00432]. It starts I-PDUs without a group itself in doing so [SWS_Com_00840]. All other I-PDUs are active as soon as one of their groups is running [SWS_Com_00771]. A stop cancels pending transmit requests [SWS_Com_00777], and subsequent confirmations are ignored [SWS_Com_00800]. Com_DeInit terminates inter-ECU communication [SWS_Com_00130]. Interpretation: Starting the I-PDU groups after Full Communication will likely be handled mostly by a BswM rule. The sources only mention the actions available for this purpose (SWS BswM p. 93).

For ComM_Init [SWS_ComM_00146], ComM requires an already initialized NvM. Only then can it load inhibition status, inhibit counter, and PNC data (SWS ComM p. 97, SWS ComM p. 144). ComM_DeInit [SWS_ComM_00147] is only permissible when all channels are in No Communication. In doing so, ComM saves the non-volatile parameters (SWS ComM p. 114). The initialization status is returned by ComM_GetStatus [SWS_ComM_00242] as a value of type [SWS_ComM_00668].

For each channel, ComM_StateType distinguishes five states and sub-states [SWS_ComM_00674]:

  • A user request leads to COMM_NO_COM_REQUEST_PENDING. There, the channel waits for CommunicationAllowed ([SWS_ComM_00871], SWS ComM p. 69, p. 63).
  • Passive channels transition to COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915]. The same applies to SLAVE_ACTIVE channels without a request [SWS_ComM_01017].
  • If Nm reports Prepare Bus-Sleep, COMM_SILENT_COMMUNICATION [SWS_ComM_00826] follows. In this state, only reception is performed (SWS ComM p. 71).
  • Wake-up indications from EcuM, channel- or PNC-related ([SWS_ComM_00275], [SWS_ComM_91001], [SWS_ComM_01014]), lead to Nm_PassiveStartup via this path (SWS ComM p. 75).

State diagram: The channel state machine of ComM with request, wake-up, and shutdown paths. Sources: [SWS_ComM_00674], [SWS_ComM_00915], [SWS_ComM_00826], [SWS_ComM_01018], [SWS_ComM_00392], SWS ComM p. 63

Partial networking supplements PNC state machines. Their initial state is COMM_PNC_NO_COMMUNICATION ([SWS_ComM_00964], SWS ComM p. 37). Dynamic PNC-to-channel mapping is still marked as DRAFT in R20-11 ([SWS_ComM_91013], [SWS_ComM_01026]). Later releases change the signature of ComM_GetPncToChannelMapping to bit vectors (SWS ComM p. 122). For R20-11, the requirement applies.

Error Handling, DET Tracing, and Degradation

Com reports development errors via Det_ReportError with ModuleId 50 [SWS_Com_00442]:

  • COM_E_PARAM [SWS_Com_00803]
  • COM_E_UNINIT [SWS_Com_00804]
  • COM_E_PARAM_POINTER [SWS_Com_00805]
  • COM_E_INIT_FAILED [SWS_Com_00837]

If a transmit request for a large I-PDU is skipped, Com reports the runtime error COM_E_SKIPPED_TRANSMISSION ([SWS_Com_00863], [SWS_Com_00864]).

Functionally, Com degrades via deadline monitoring:

  • If a timely transmit confirmation is missing, Com calls the timeout notifications [SWS_Com_00304]. A confirmation terminates the timers [SWS_Com_00880].
  • Upon reception, action SUBSTITUTE replaces the values with substitute values ([SWS_Com_00875], [SWS_Com_00876]).
  • A failed TP reception is treated like an invalidation [SWS_Com_00838].
  • Signals without a set update bit are discarded [SWS_Com_00802].
  • Reception monitoring can be enabled and disabled in groups ([SWS_Com_91003], [SWS_Com_91004]).

PduR knows, among others, the errors PDUR_E_UNINIT, PDUR_E_PDU_ID_INVALID, and PDUR_E_ROUTING_PATH_GROUP_ID_INVALID ([SWS_PduR_00100], [SWS_PduR_00119], [SWS_PduR_00221], [SWS_PduR_00648]). It does not retry a failed <DstLo>_Transmit [SWS_PduR_00256]. If a FIFO overflows, it is flushed and PDUR_E_PDU_INSTANCES_LOST is reported ([SWS_PduR_00255], [SWS_PduR_00670]). If one destination fails in the TP gateway, the remaining ones continue [SWS_PduR_00803]. Reception aborts only when all destinations fail [SWS_PduR_00804]. With deactivated routing paths, the APIs return immediately with E_NOT_OK ([SWS_PduR_00717], SWS PduR p. 69).

ComM reports, among others, COMM_E_UNINIT and COMM_E_PARAM_POINTER [SWS_ComM_00234]. Without initialization, it refuses normal operation [SWS_ComM_00612]. Mode inhibition serves for targeted degradation:

  • A channel or the entire ECU can be limited to No Communication ([SWS_ComM_00163], [SWS_ComM_00124]).
  • Wake-up events can be suppressed [SWS_ComM_00156].
  • The status is located in a bit field [SWS_ComM_00669] and is retained across an ECU reset (SWS ComM p. 84).
  • Rejected requests return COMM_E_MODE_LIMITATION [SWS_ComM_00110] and are counted [SWS_ComM_00224].
  • Optionally, ComM then forces a reset via BswM [SWS_ComM_00355].

The evaluated material does not specify any DEM events for this cluster. Error handling relies on DET reports and the functional degradation described above ([SWS_PduR_00100], [SWS_ComM_00234]).
