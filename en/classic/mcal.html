AUTOSAR Classic Microcontroller Abstraction (MCAL)

Die Microcontroller Abstraction Layer (MCAL) enthält hardware-spezifische Treiber für interne Mikrocontroller-Peripherie (ADC-Wandler, PWM-Generatoren, Hardware-Watchdog) und entkoppelt obere BSW-Schichten von der Silizium-Plattform.

Provides low-level drivers for direct encapsulation and control of microcontroller peripherals and internal registers.

The Microcontroller Abstraction (MCAL) module cluster comprises the drivers Port, Dio, Adc, Pwm, Spi, and Wdg for low-level encapsulation and control of on-chip peripherals (SWS_ECUStateManager p. 34). The core tasks include pin configuration prior to peripheral access, analog and pulse-modulated signal management, as well as time-monitored execution control ([SWS_Adc_00507], [SWS_Wdg_00155]). Central mode and power state transitions must be executed strictly sequentially and non-reentrantly ([SWS_Wdg_00107]).

The Microcontroller Abstraction (MCAL) module cluster encapsulates the physical on-chip resources of the microcontroller and provides standardized interfaces for the I/O hardware abstraction (IoHwAb), the watchdog interface (WdgIf), as well as EcuM and BswM (SWS_ECUStateManager p. 34). It comprises the six driver modules Port (pin multiplexing), Dio (digital input/output), Adc (analog-to-digital conversion), Pwm (pulse-width modulation), Spi (serial peripheral communication), and Wdg (hardware execution monitoring) ([SWS_Adc_00507], [SWS_Pwm_00197], [SWS_Wdg_00155]).

The modules operate within fixed dependencies: Port_Init sets up the pin assignment before drivers such as Pwm or Adc activate the associated hardware blocks (AUTOSAR_CP_RS_PWMDriver p. 14, ModemanagementGuide p. 54). Data buffers are provided on the application side via Adc_SetupResultBuffer ([SWS_Adc_91000]), while watchdog servicing is decoupled asynchronously via timer interrupts (AUTOSAR_SWS_WatchdogDriver p. 31).

Architecture diagram: Layer architecture and classification of the MCAL cluster. Sources: SWS_ECUStateManager p. 34, AUTOSAR_CP_RS_PWMDriver p. 14.

While channel- and group-related driver calls are reentrant for disjoint instances ([SWS_Pwm_91000], [SWS_Adc_00367]), mode and state transitions require strictly synchronous, non-reentrant paths ([SWS_Wdg_00107]). To reduce power consumption, Adc and Pwm execute two-phase power state transitions with asynchronous readiness notifications to IoHwAb ([SWS_Adc_00478], [SWS_Pwm_00183], AUTOSAR_CP_SWS_IOHardwareAbstraction p. 57).

Incorrect operations such as uninitialized calls are reported to the DET ([SWS_Pwm_00177]), whereas hardware defects are reported to the DEM ([SWS_Wdg_00111]). In degradation scenarios, Wdg_SetTriggerCondition allows a targeted ECU reset to be induced by passing timeout 0 ([SWS_Wdg_00155], SWS_WatchdogDriver p. 29).

System Architecture & Role of the Module Cluster

The module cluster of the Microcontroller Abstraction Layer (MCAL) forms the lowest-level foundation of the AUTOSAR Classic Platform close to the hardware. It encapsulates the register accesses of the on-chip peripheral units and provides upper layers with a standardized, microcontroller-independent interface. Within the layered architecture, the drivers serve the I/O Hardware Abstraction (IoHwAb), the Watchdog Interface (WdgIf), as well as central system services such as the ECU State Manager (EcuM) and the Basic Software Mode Manager (BswM) (SWS_ECUStateManager p. 34).

The cluster comprises six complementary driver components: Port handles the global pin configuration and the multiplexing of the microcontroller pins (AUTOSAR_CP_RS_PWMDriver p. 14). Dio implements fast, bit- and port-wise digital I/O access, while Spi encapsulates synchronous and asynchronous serial bus communications to on-board peripheral components. For analog and pulse-modulated signals, Adc ([SWS_Adc_00507]) and Pwm ([SWS_Pwm_00197]) provide advanced conversion and modulation services. Wdg controls hardware-based time monitoring to safeguard program execution integrity ([SWS_Wdg_00155]).

Architecture diagram: Layered architecture and structural placement of the MCAL cluster between system services, abstraction layers, and peripherals. Sources: SWS_ECUStateManager p. 34, AUTOSAR_CP_RS_PWMDriver p. 14, AUTOSAR_SWS_WatchdogDriver p. 11.

Interplay & Interaction Paths Between the Modules

The modules operate in clearly defined signal and buffer flows. The driver Port pre-initializes the electrical port logic and multiplexing, after which drivers such as Pwm or Adc drive the assigned peripheral blocks without needing knowledge of the pad circuitry (AUTOSAR_CP_RS_PWMDriver p. 14). When reading internal logic states via [SWS_Pwm_00100], Pwm_GetOutputState reads the register state of the PWM unit rather than the physical port pin ([SWS_Pwm_00108], AUTOSAR_SWS_PWMDriver p. 51).

In the analog path, the higher-level IoHwAb requests conversions and provides application-side buffers (AUTOSAR_CP_SWS_IOHardwareAbstraction p. 55). Using [SWS_Adc_91000], Adc_SetupResultBuffer initializes the internal pointer to the caller's memory area (AUTOSAR_SWS_ADCDriver p. 31). After triggering a conversion via software ([SWS_Adc_00367]) or hardware trigger ([SWS_Adc_91001]), raw data is written to the buffer. Read access occurs synchronously via [SWS_Adc_00369] (copying the most recent results) or via [SWS_Adc_00375] using Adc_GetStreamLastPointer (SWS_ADCDriver p. 27).

The watchdog path separates logical program flow monitoring from hardware servicing: The WdgM controls monitoring budgets and sets the time window in Wdg_SetTriggerCondition via the WdgIf with [SWS_Wdg_00155] (SWS_WatchdogDriver p. 29). Actual hardware servicing occurs cyclically via hardware timer interrupts (AUTOSAR_SWS_WatchdogDriver p. 31). External watchdog devices are addressed as needed via driver instances of Dio or Spi ([SWS_Wdg_00111], AUTOSAR_SWS_WatchdogDriver p. 11).

Sequence diagram: Interaction of WdgM, WdgIf, and Wdg during cyclic trigger extension and mode switching. Sources: AUTOSAR_SWS_WatchdogDriver p. 31, AUTOSAR_SWS_WatchdogDriver p. 34, [SWS_Wdg_00155], [SWS_Wdg_00107].

Synchronization, reentrancy and task contexts

The MCAL drivers are subject to differentiated reentrancy rules. In module Pwm, control functions such as Pwm_SetDutyCycle ([SWS_Pwm_91000]), Pwm_SetPeriodAndDuty ([SWS_Pwm_91001]), and Pwm_SetOutputToIdle ([SWS_Pwm_91002]) are reentrant for different channels, but must not be called concurrently for the same channel (AUTOSAR_CP_SWS_PWMDriver p. 46). In module Adc, control and read APIs such as Adc_StartGroupConversion ([SWS_Adc_00367]), Adc_StopGroupConversion ([SWS_Adc_00368]), and Adc_ReadGroup ([SWS_Adc_00369]) are reentrant with respect to different channel groups.

In contrast, central configuration and mode APIs are designed to be strictly non-reentrant. This applies to Wdg_SetMode ([SWS_Wdg_00107]), Wdg_SetTriggerCondition ([SWS_Wdg_00155]), and the initialization and de-initialization routines of all drivers ([SWS_Adc_00366], [SWS_Pwm_00096]). Concurrent calls from different OS tasks must be protected via SchM exclusive areas (AUTOSAR_SWS_WatchdogDriver p. 11).

Notifications of events (e.g., edge changes or conversion end) are triggered from interrupt context (ISR) via configurable callbacks such as Pwm_Notification_<#Channel> ([SWS_Pwm_00105]) or Adc_Notification_Group_<x> ([SWS_Adc_91003]). When activating notifications, pending interrupt flags are cleared ([SWS_Pwm_91004]). If multiple ADC groups compete for converter resources, hardware prioritization or software queuing ([SWS_Adc_00522]) with a configurable abort/restart or suspend/resume mechanism applies depending on the configuration ([SWS_Adc_00523], SWS_ADCDriver p. 97).

Typical lifecycles and operating modes

The lifecycle of the MCAL drivers begins in the startup phase of the overall system under the control of the EcuM (SWS_ECUStateManager p. 34). A deterministic order is enforced via BswM rules: First, Port_Init initializes the pin functionalities (ModemanagementGuide p. 54). Only then do peripheral drivers such as Dio_Init, Spi_Init, Adc_Init ([SWS_Adc_00365]), Pwm_Init ([SWS_Pwm_00095]), and Wdg_Init follow ([SWS_Wdg_00106], AUTOSAR_CP_SWS_PWMDriver p. 47).

During operation, Wdg recognizes three static modes: WDGIF_OFF_MODE, WDGIF_SLOW_MODE, and WDGIF_FAST_MODE ([SWS_Wdg_00107]). Module Adc distinguishes between one-shot and continuous conversions ([SWS_Adc_00515]) as well as single and streaming access modes ([SWS_Adc_00528], [SWS_Adc_00519]). The group status passes through the states ADC_IDLE, ADC_BUSY, ADC_COMPLETED, and ADC_STREAM_COMPLETED ([SWS_Adc_00513], [SWS_Adc_00374], SWS_ADCDriver p. 37).

For low-power modes, Adc and Pwm implement a standardized two-phase power-state protocol: First, Adc_PreparePowerState ([SWS_Adc_00478]) and Pwm_PreparePowerState ([SWS_Pwm_00183]) prepare the transition ([SWS_Pwm_00165], [SWS_Adc_00527]). After asynchronous completion, the hardware abstraction reports readiness via callbacks such as IoHwAb_Adc_NotifyReadyForPowerState<#Mode> ([SWS_Adc_00480]). Finally, Adc_SetPowerState ([SWS_Adc_00475]) and Pwm_SetPowerState ([SWS_Pwm_00166]) switch the hardware to the target state (AUTOSAR_CP_SWS_IOHardwareAbstraction p. 57). Cyclic monitoring is ensured in tasks by Pwm_Main_PowerTransitionManager ([SWS_Pwm_00189], [SWS_Pwm_00190]).

During system shutdown or reset, de-initialization services such as Adc_DeInit ([SWS_Adc_00366], AUTOSAR_SWS_ADC_Driver p. 76) and Pwm_DeInit ([SWS_Pwm_00096], AUTOSAR_SWS_PWMDriver p. 47) transition the units to a safe quiescent state and disable all interrupts.

Error Handling, DET Tracing, and Degradation

Errors are strictly separated into development and production errors. When development error detection is active, the drivers report calls prior to completed initialization to the Default Error Tracer (DET), for example via PWM_E_UNINIT ([SWS_Pwm_00177], [SWS_Pwm_00104]) or ADC_E_UNINIT ([SWS_Adc_00476]). Pointer parameters are checked for NULL, such as in GetVersionInfo via ADC_E_PARAM_POINTER ([SWS_Adc_00376]) and WDG_E_PARAM_POINTER ([SWS_Wdg_00109]).

Runtime errors safeguard against invalid operational transitions: If Pwm_SetPowerState is called while channels are not in the IDLE state or active notifications are still pending, the driver reports runtime error PWM_E_NOT_DISENGAGED ([SWS_Pwm_00202]). In Adc, the attempt to re-trigger an occupied channel group in configurations without queuing leads to runtime report ADC_E_BUSY to the DET (SWS_ADCDriver p. 95).

Severe production errors and peripheral failures are reported to the Diagnostic Event Manager (DEM) via Dem_SetEventStatus ([SWS_Wdg_00111]). For degradation into limp-home modes, Pwm_SetOutputToIdle provides the immediate deactivation of individual PWM outputs ([SWS_Pwm_91002]). In the watchdog driver, setting the trigger timeout to the value 0 allows servicing to be stopped immediately, forcing a prompt ECU reset ([SWS_Wdg_00155], [SWS_Wdg_00136], SWS_WatchdogDriver p. 29).
