AUTOSAR Classic Memory Services

The Memory Services manage non-volatile data blocks (NvM), abstract Flash and EEPROM technologies (MemIf, Fee, Ea), and ensure data consistency and data security across ECU shutdown cycles.

Saves and manages persistent data independently of hardware via structured NVRAM blocks and abstraction drivers.

The module cluster 'Memory Services' realizes the hardware-independent storage and consistency assurance of non-volatile application data via the NVRAM Manager as well as the hardware-abstracting modules MemIf, Fee, and Ea ([SWS_NvM_00447], [SWS_MemIf_00039]). Asynchronous read and write operations are processed via cyclic MainFunctions and executed in batches during ECU startup (NvM_ReadAll) as well as during shutdown (NvM_WriteAll) ModemanagementGuide p. 54. In the event of hardware errors, multi-level retry, redundancy, and ROM restoration mechanisms take effect with automatic reporting to the DEM ([SWS_NvM_00470]).

The cluster 'Memory Services' provides the persistent storage and management of non-volatile data in the AUTOSAR Classic BSW stack. It comprises the NVRAM Manager ([SWS_NvM_00447]) at the service layer as well as the Memory Abstraction Interface ([SWS_MemIf_00039]) with the modules Flash EEPROM Emulation ([SWS_Fee_00085]) and EEPROM Abstraction ([SWS_Ea_00083]) at the hardware abstraction layer AUTOSAR SWS NVRAMManager p. 10.

Architecture diagram: Layered structure and module relationships in the Memory Services cluster. Sources: [SWS_MemIf_00039], AUTOSAR SWS NVRAMManager p. 10

Data exchange takes place via synchronous control APIs and asynchronous write and read jobs. Data is exchanged either implicitly via permanent RAM blocks or explicitly via module-managed RAM mirrors ([SWS_NvM_00455], [SWS_NvM_00514]) NVDataHandling p. 12. The cyclic processing of queued jobs is performed via periodically executed BSW main functions (NvM_MainFunction, Fee_MainFunction), while MemIf delegates calls statelessly to the underlying drivers ([SWS_MemIf_00040]) AUTOSAR CP SWS FlashEEPROMEmulation p. 42.

In the operating cycle, BswM coordinates multi-block actions: During system startup, NvM_ReadAll reads persistent data from NV memory into RAM ([SWS_NvM_00460]), while during shutdown, NvM_WriteAll saves modified data ([SWS_NvM_00461]) ModemanagementGuide p. 54. Erroneous read or write accesses are intercepted by retry attempts as well as redundant copies or ROM fallback values; permanent errors are reported by the system to DEM ([SWS_NvM_00470], [SWS_NvM_00279]) ErrorDescription p. 62.

System Architecture & Role of the Module Cluster

The memory services module cluster (Memory Services) of the AUTOSAR Classic Platform ensures the standardized, hardware-independent management and persistence of application and Basic Software data in non-volatile memory. The cluster is vertically structured into two layers of the AUTOSAR Basic Software architecture: the NVRAM Manager ([SWS_NvM_00447]) at the service layer (Services Layer) and the Memory Abstraction Interface ([SWS_MemIf_00039]) with the underlying abstraction modules Flash EEPROM Emulation ([SWS_Fee_00085]) and EEPROM Abstraction ([SWS_Ea_00083]) at the hardware abstraction layer (Memory Hardware Abstraction Layer) AUTOSAR SWS NVRAMManager p. 10.

The NVRAM Manager (NvM) forms the central entry point for software components (SW-C) and BSW modules such as the Diagnostic Event Manager module (Dem) SWS DiagnosticEventManager p. 238. It manages logical memory blocks composed of NV blocks in non-volatile memory, RAM blocks in volatile memory, and optional ROM blocks for initialization data ([SWS_NvM_00137], [SWS_NvM_00128]). Depending on requirements, the block management types native (NVM_BLOCK_NATIVE), redundant (NVM_BLOCK_REDUNDANT), or dataset (NVM_BLOCK_DATASET) are supported AUTOSAR CP RS MemoryServices p. 10.

The modules Fee and Ea encapsulate the specifics of the respective physical storage media (Flash and EEPROM, respectively) and map logical block numbers and address offsets to the linear address spaces of the respective MCAL drivers (Fls and Eep, respectively) ([SWS_Fee_00087], [SWS_Ea_00086]) AUTOSAR SWS EEPROMAbstraction p. 23. The module MemIf serves as a pure routing layer that forwards accesses to the target module based on the parameter DeviceIndex, without maintaining buffer structures of its own ([SWS_MemIf_00040]).

Interplay & Interaction Paths Between the Modules

Interaction between the modules takes place via strictly standardized synchronous and asynchronous paths. If a user initiates a write operation via NvM_WriteBlock, the request is first registered in the administrative block of NvM ([SWS_NvM_00455]). In the case of a synchronous call, it is forwarded to MemIf via MemIf_Write ([SWS_MemIf_00040]), which passes the call to Fee_Write or Ea_Write ([SWS_Fee_00088], [SWS_Ea_00087]) AUTOSAR SWS NVRAMManager p. 160.

Regarding data management and synchronization between the application and the NVRAM Manager, two core concepts exist: implicit synchronization via permanent RAM blocks (NvMRamBlockDataAddress) and explicit synchronization via mirror-based buffers (NvMBlockUseSyncMechanism) NVDataHandling p. 12. In the case of explicit synchronization, NvM copies payload data between application RAM and the internal RAM mirror via the configured callback routines NvMWriteRamBlockToNvCallback and NvMReadRamBlockFromNvCallback, respectively ([SWS_NvM_00514], [SWS_NvM_00515]) EXP NVDataHandling p. 30.

When using dataset blocks (NVM_BLOCK_DATASET), the caller selects the desired dataset index in advance via NvM_SetDataIndex ([SWS_NvM_00448]). The abstraction modules then calculate the exact address offset for the MCAL driver from the logical block number and the index ([SWS_NvM_00123]) AUTOSAR SWS Flash EEPROM Emulation p. 21. Cancellation requests are passed through directly to the submodules Fee_Cancel and Ea_Cancel, respectively, via MemIf_Cancel ([SWS_MemIf_00041], [SWS_Fee_00089]).

Synchronization, reentrancy and task contexts

Most control and status APIs of the cluster, including NvM_GetErrorStatus ([SWS_NvM_00451]), NvM_SetBlockProtection ([SWS_NvM_00450]), and MemIf_GetVersionInfo ([SWS_MemIf_00045]), are synchronous and can be processed directly in the caller's task context AUTOSAR SWS NVRAMManager p. 157. In contrast, the data-transferring functions (NvM_ReadBlock, NvM_WriteBlock, Ea_Write) are designed to be asynchronous and non-reentrant ([SWS_MemIf_00040], [SWS_Ea_00087]).

The cyclic progression of ongoing jobs is the responsibility of the main functions NvM_MainFunction and Fee_MainFunction, which are called periodically by the Schedule Manager (SchM) or a BSW task AUTOSAR CP SWS FlashEEPROMEmulation p. 42. For asynchronous notifications from the MCAL driver, the notification Fee_JobEndNotification or Fee_JobErrorNotification can occur directly at interrupt level ([SWS_Fee_00095]). This sets the status to MEMIF_JOB_OK or calls configured notification routines ([SWS_Fee_00142], [SWS_Fee_00194]) SWS FlashEEPROMEmulation p. 37.

Interpretation: To prevent race conditions between API callers at task level and the incremental further processing in the MainFunctions, internal queues and administrative attributes are likely protected by exclusive areas, while MemIf acts as a stateless forwarding layer AUTOSAR SWS NVRAMManager p. 160.

Typical lifecycles and operating modes

The lifecycle of the cluster is tightly orchestrated by the Basic Software Mode Manager (BswM) and the ECU State Manager (EcuM). During ECU startup (Startup Phase), after the drivers, first the abstraction modules are initialized synchronously via Fee_Init and Ea_Init, respectively ([SWS_Fee_00085], [SWS_Ea_00083]), and subsequently the NVRAM Manager via NvM_Init ([SWS_NvM_00447]) AUTOSAR SWS NVRAMManager p. 156.

Following initialization, BswM triggers the multi-block read operation NvM_ReadAll to restore all RAM blocks marked as persistent from non-volatile memory ([SWS_NvM_00460]) ModemanagementGuide p. 54. NvM reports the progress and the final result back to BswM via the callback function BswM_NvM_CurrentJobMode ([SWS_NvM_00745], [SWS_NvM_00888]). Individual block states are signaled via BswM_NvM_CurrentBlockMode ([SWS_NvM_00746], [SWS_NvM_00890]) ModemanagementGuide p. 28.

In the shutdown phase, the system initiates the persistent write-back of all modified RAM blocks into NV memory via NvM_WriteAll ([SWS_NvM_00461]). In order to optimize the number of flash write cycles, whether a block has been modified can be selectively marked via NvM_SetRamBlockStatus ([SWS_NvM_00453]) EXP NVDataHandling p. 18. In the event of premature wake-up events, an ongoing write operation can be canceled via NvM_CancelWriteAll ([SWS_NvM_00238]) AUTOSAR SWS NVRAMManager p. 161.

Error Handling, DET Tracing, and Degradation

The cluster features a multi-level fault detection and degradation concept. Errors occurring at driver and abstraction levels are queried via the return status MEMIF_JOB_FAILED using MemIf_GetJobResult or reported via NvM_JobErrorNotification ([SWS_Fee_00091], [SWS_Ea_00095]) ErrorDescription p. 49.

When read errors occur, NvM resorts to configured recovery mechanisms: First, retries (Read Retries) are attempted ([SWS_NvM_00390]). If these fail, the redundant copy is read in the case of redundant blocks (NVM_BLOCK_REDUNDANT) ([SWS_NvM_00171], [SWS_NvM_00531]). If a loss of redundancy is detected in this process, NvM sets the job result to NVM_REQ_REDUNDANCY_FAILED and reports the production error NVM_E_LOSS_OF_REDUNDANCY to DEM ([SWS_NvM_00470], [SWS_NvM_00546]) ErrorDescription p. 62.

If recovery via ROM default values succeeds, the NvM reports the result NVM_REQ_RESTORED_FROM_ROM ([SWS_NvM_00470]). If all recovery actions fail, NVM_E_REQ_FAILED is reported to the DEM ([SWS_NvM_00279], [SWS_NvM_00288]) and the query result is set to NVM_REQ_NOT_OK ([SWS_NvM_00451]). In the event of write errors, the NvM controls write retries (NvMMaxNumOfWriteRetries) before the request is aborted ([SWS_NvM_00168], [SWS_NvM_00213]) ErrorDescription p. 56.
