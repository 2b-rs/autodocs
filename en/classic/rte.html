System architecture and role of the module cluster

The cluster comprises a single module, the Runtime Environment (Rte). It implements the communication paths on each ECU that the ECU configuration specifies. In doing so, it also realizes the semantics of the communication attributes from the component descriptions [SWS_Rte_02200] [SWS_Rte_02201]. The RTE is configured and generated individually for each ECU [SWS_Rte_05000] [SWS_Rte_01316]. The generator produces C code which must comply with MISRA C [SWS_Rte_01167] [SWS_Rte_01168]. The location of the RTE between application software and Basic Software is shown in the ECU architecture picture (SWS RTE p. 113).

Downwards, the RTE exclusively uses standardized AUTOSAR services, including OS, COM, LdCom and Transformer [SWS_Rte_02250]. The generated code also includes the Basic Software Scheduler (SchM). It serves the scheduling, the modes, the triggers and the exclusive areas of the BSW modules. The methodology provides a separate generation step for this, which only generates the scheduler code (TR Methodology p. 463).

The generator describes the generated RTE itself as a BSW module. This includes BswModuleDescription, BswInternalBehavior and BswImplementation [SWS_Rte_05165] [SWS_Rte_05166] [SWS_Rte_05167]. The lifecycle APIs of Rte and SchM appear therein as BswModuleEntry [SWS_Rte_05177]. Central interface files are:

  • Rte.h [SWS_Rte_01157] and the lifecycle header Rte_Main.h [SWS_Rte_01158],
  • Rte_Type.h with the type declarations [SWS_Rte_01161],
  • the application header Rte_[Byps_]<name>.h per component type [SWS_Rte_01003],
  • Rte_Cbk.h with the callback prototypes [SWS_Rte_03796].

Context diagram: The RTE mediates between the SW-Cs and the BSW services OS, IOC, COM, LdCom, NvM (via NvBlockSwComponentType) and BndM. The BSW scheduler belongs to the same generated code. Sources: [SWS_Rte_02250], [SWS_Rte_03001], [SWS_Rte_01377], [SWS_Rte_03884], SWS RTE p. 259, SWS OS p. 128

Interaction and interaction paths

A SW-C consists of several RunnableEntitys. The RTE starts them according to the connected RTEEvents [SWS_Rte_02202] [SWS_Rte_02203] (SWS RTE p. 119).

For sender-receiver communication, the following applies:

  • Buffer: Buffering takes place on the receiver side [SWS_Rte_02515].
    • "data" (not queued) follows last-is-best: A new value overwrites the old one [SWS_Rte_02516] [SWS_Rte_02520].
    • "events" end up in a FIFO queue [SWS_Rte_02521] [SWS_Rte_02522]. If the buffer is full, the new event is discarded and an error flag is set [SWS_Rte_02523]. The application sees this as RTE_E_LOST_DATA [SWS_Rte_02571].
  • Access types:
    • During implicit reading, the RTE provides a copy before the start of the runnable, which remains unchanged during execution [SWS_Rte_06000] [SWS_Rte_06001] [SWS_Rte_06004].
    • Runnables access explicitly via Rte_Read, Rte_Receive and Rte_Send [SWS_Rte_01091] [SWS_Rte_01092] [SWS_Rte_01072].
    • Runnables write implicitly via Rte_IWrite [SWS_Rte_03744].

Inter-ECU communication via COM:

  • The RTE transmits composite data atomically via signal groups [SWS_Rte_04527] [SWS_Rte_03008] (SWS RTE p. 326).
  • COM reports events via callbacks such as Rte_COMCbk_<sn> [SWS_Rte_03530] [SWS_Rte_03001]. These callbacks activate runnables or wake up category 2 runnables at wait points [SWS_Rte_03531] [SWS_Rte_03532].
  • Value filters run in COM during inter-ECU communication, intra-ECU in the RTE [SWS_Rte_05500].
  • Release difference: In R20-11, [SWS_Rte_04505] requires the ComHandleId. The more recent document reference speaks of the Com Symbolic Name instead (SWS RTE p. 324).

Large byte arrays via LdCom:

  • The RTE sends and receives large byte arrays in R20-11 via LdCom and LdCom_Transmit [SWS_Rte_01376] [SWS_Rte_01377] [SWS_Rte_01378].
  • With TP transmission, the RTE locks the signal buffer until confirmation [SWS_Rte_01379] [SWS_Rte_01380] (SWS RTE p. 350).
  • Release difference: The R25-11 reference describes "Large Data Path in COM" with Com_Transmit instead (SWS RTE p. 343). LdCom applies to R20-11.

Client-server communication:

  • Clients call synchronously or asynchronously via Rte_Call [SWS_Rte_01102] [SWS_Rte_01293] [SWS_Rte_01294]. They fetch asynchronous results with Rte_Result [SWS_Rte_01111].
  • If the call is not a direct function call, the RTE buffers requests server-side in a FIFO queue and responses client-side with queue length 1 [SWS_Rte_02527] [SWS_Rte_02528]. It serializes the server access via the request queue [SWS_Rte_02530].
  • The RTE monitors timeouts independently of the reception mode [SWS_Rte_03763] (SWS RTE p. 358).

Further paths:

  • NvM requests from the SW-Cs are forwarded to the NvM by the runnables of the NvBlockSwComponentType (SWS RTE p. 259). The return values of the NvM APIs are regulated by [SWS_Rte_04535].
  • The RTE reads Bulk NvData via BndM [SWS_Rte_03883] [SWS_Rte_03884].
  • Between cores, Rte_Call writes into the IOC and activates the server task on the target core (SWS OS p. 128). The RTE does not execute ExecutableEntities in IOC callbacks, and it prevents simultaneous accesses to the same IOC API [SWS_Rte_02736] [SWS_Rte_02737].

Synchronization, reentrancy and task contexts

Execution contexts:

  • Runnables run in the context of an OS task or ISR2 (SWS RTE p. 119). Within a task, the RTE complies with the configured execution order [SWS_Rte_02207].
  • Category 1 interrupts must not reach the RTE. The generator rejects corresponding configurations [SWS_Rte_03594] (SWS RTE p. 182).
  • An ISR2 can activate ExecutableEntities via external triggers [SWS_Rte_04564]. The RTE, however, does not let runnables of SW-Cs run in the interrupt context [SWS_Rte_03600].
  • RTE callbacks must not block [SWS_Rte_01165].
  • Whether Schedule is called after a runnable is regulated by [SWS_Rte_05113] to [SWS_Rte_05115].

Data consistency: The RTE guarantees consistency for communication via AUTOSAR interfaces [SWS_Rte_03514] and for InterRunnableVariables [SWS_Rte_03516].

  • For implicit InterRunnableVariables, it avoids simultaneous accesses. For explicit ones, it blocks concurrent accesses [SWS_Rte_03517] [SWS_Rte_03519] (SWS RTE p. 207).
  • Exclusive areas are entered and left with Rte_Enter and Rte_Exit [SWS_Rte_03515] [SWS_Rte_01120] [SWS_Rte_01123]. Different areas may be nested [SWS_Rte_01122].
  • The protection mechanism is selected by RteExclusiveAreaImplMechanism: ALL_INTERRUPT_BLOCKING [SWS_Rte_03504], OS_INTERRUPT_BLOCKING [SWS_Rte_05164], OS_RESOURCE [SWS_Rte_03595] or NONE [SWS_Rte_03999].
  • If runnables call a blocking API within an exclusive area, it returns RTE_E_IN_EXCLUSIVE_AREA [SWS_Rte_02739].

Reentrancy:

  • The same runnable instance may only be concurrently activated if canBeInvokedConcurrently is set [SWS_Rte_03523] [SWS_Rte_05083].
  • The RTE only supports multiple instances via code sharing [SWS_Rte_03015] [SWS_Rte_02002]. The instance is identified via the instance handle, which the entry point receives as the first parameter [SWS_Rte_01016] [SWS_Rte_02015].
  • Because instances are scheduled independently, entry points should be reentrant (SWS RTE p. 804).

Multi-core and partitioned systems: Here [SWS_Rte_02711] restricts global variables in Rte.c. In addition, [SWS_Rte_02712] requires separate files Rte_Partition_<PartitionName>.

Lifecycles and operating modes

Startup of the BSW scheduler:

  • Before its initialization, only SchM_Enter and SchM_Exit are available (SWS RTE p. 400).
  • SchM_Start is always generated, returns in finite time and must be called before BswM_Init() [SWS_Rte_04546] [SWS_Rte_04547] [SWS_Rte_04548] (SWS RTE p. 927).
  • SchM_StartTiming starts the periodic events and requires a preceding SchM_Init [SWS_Rte_04549] [SWS_Rte_04550] [SWS_Rte_04551].
  • All three calls are made exactly once per core by the EcuM (SWS RTE p. 928).

Startup of the RTE:

  • The EcuM calls Rte_Start at the end of startup phase II, when the OS is available and all BSW modules are initialized [SWS_Rte_02569] [SWS_Rte_02585] (SWS RTE p. 460).
  • If resource allocation fails, Rte_Start returns RTE_E_LIMIT, otherwise RTE_E_OK [SWS_Rte_01261] [SWS_Rte_01262] (SWS RTE p. 806).
  • Initial values protect the receivers from uninitialized data [SWS_Rte_06009] [SWS_Rte_06010] [SWS_Rte_02517].

Shutdown and partition restart:

  • Rte_Stop follows at the beginning of shutdown phase I [SWS_Rte_02570] [SWS_Rte_02584]. If a resource cannot be released, the function reports RTE_E_LIMIT [SWS_Rte_01260].
  • Thereafter, the RTE no longer activates runnables on this core [SWS_Rte_02538].
  • Before complete initialization and after the stop, the RTE ignores incoming client-server requests as well as sender-receiver data [SWS_Rte_02535] [SWS_Rte_02536] (SWS RTE p. 461). The BSW scheduler behaves analogously [SWS_Rte_04552].
  • In case of a partition restart, the RTE restores an initial environment [SWS_Rte_02735].

Sequence diagram: Startup and shutdown of BSW scheduler and RTE per core, controlled by the EcuM. Interpretation: The order of SchM_Init and SchM_Start is not explicitly proven. Mode management:

  • The RTE maintains the active mode of each Mode Machine Instance [SWS_Rte_02546] and initiates the transition to the initial modes during initialization [SWS_Rte_02544] (SWS RTE p. 433).
  • A mode manager requests transitions via Rte_Switch [SWS_Rte_02631]. The notifications end up in a FIFO queue per instance [SWS_Rte_02718] [SWS_Rte_02719].
  • If the queue is full, the new notification is discarded [SWS_Rte_02720]. Between partitions, the RTE then reports RTE_E_LIMIT [SWS_Rte_02675]. Only after completion of the transition does it remove the notification from the queue [SWS_Rte_02721].
  • [SWS_Rte_02665] divides the transition itself into ten steps (EXP ModeManagementGuide p. 15):
    1. Activate mode disablings [SWS_Rte_02661].
    2. Execute on-exit entities [SWS_Rte_02562].
    3. Execute on-transition entities [SWS_Rte_02707] [SWS_Rte_02708].
    4. Execute on-entry entities [SWS_Rte_02564].
    5. Switch mode disablings [SWS_Rte_02563].
    6. Trigger ModeSwitchedAckEvents [SWS_Rte_02587].
  • Running runnables are not aborted during the mode transition [SWS_Rte_02504]. A transition to the same mode is also fully executed [SWS_Rte_02669].
  • The mode manager queries the confirmation via Rte_SwitchAck [SWS_Rte_02725].
  • Modes can also activate OS schedule tables [SWS_Rte_05146].

Activity diagram: A mode transition request is queued or discarded if the queue is full. Afterwards, it goes through the ordered transition steps up to the confirmation. Sources: [SWS_Rte_02665], [SWS_Rte_02718], [SWS_Rte_02720], [SWS_Rte_02721], [SWS_Rte_02587], EXP ModeManagementGuide p. 15

Error handling, tracing and degradation

The SW-C receives error states exclusively as a return value of the RTE API of type Std_ReturnType [SWS_Rte_01034] (SWS RTE p. 579). The specification distinguishes three error classes:

  • Immediate infrastructure errors overwrite application errors [SWS_Rte_02593].
  • Overlayed errors use a separate bit and can be combined with other errors [SWS_Rte_01318] (SWS RTE p. 686).
  • Application errors occupy the lower 6 bits [SWS_Rte_02573].

Degradation:

  • For unconnected ports, the RTE defines a fixed behavior [SWS_Rte_01329] [SWS_Rte_01330]. Rte_Call then reports RTE_E_UNCONNECTED [SWS_Rte_01334].
  • Senders invalidate data via Rte_Invalidate [SWS_Rte_01206], enabled via handleInvalid [SWS_Rte_05024]. Intra-ECU, the RTE implements the invalidation itself [SWS_Rte_05025]:
    • With keep, it treats the reception as an error [SWS_Rte_05030].
    • With replace, it replaces the invalid value with the initValue [SWS_Rte_05049].
  • Invalid values lead to RTE_E_INVALID [SWS_Rte_02626]. If range checking is active, values out of range lead to RTE_E_OUT_OF_RANGE [SWS_Rte_03845] [SWS_Rte_03846] [SWS_Rte_01371] (SWS RTE p. 420).
  • The monitoring for outdated data follows aliveTimeout. The value 0 turns it off [SWS_Rte_03759] [SWS_Rte_02710]. With implicit access, Rte_IStatus returns the status [SWS_Rte_02600].

Memory protection: In memory-protected systems, the RTE checks pointers from untrusted partitions before forwarding them [SWS_Rte_02752] [SWS_Rte_02753]. It reports violations as RTE_E_SEG_FAULT [SWS_Rte_02754] (SWS RTE p. 378).

Tracing: The payload contains no DET or DEM requirements of the RTE. Measurement and calibration support

The RTE allocates the memory for calibration parameters [SWS_Rte_03961] (SWS RTE p. 241). Of the emulation methods with SW support, only one is active at a time [SWS_Rte_03909] [SWS_Rte_03943]:

  • Single Pointered: Reference table in RAM [SWS_Rte_03913].
  • Double Pointered: Reference table in ROM or Flash [SWS_Rte_03914].
  • InitRam: RAM copy of the parameters from ROM/Flash [SWS_Rte_03915].

Measurement support can be turned off separately from this [SWS_Rte_03903]. The selected method and the symbol information are documented by the generator in McSupportData and McSwEmulationMethodSupport [SWS_Rte_05118] [SWS_Rte_05137] (SWS RTE p. 258).

<h4>System architecture and role of the module cluster</h4>
<p>The cluster comprises a single module, the Runtime Environment (<code>Rte</code>). It implements the communication paths on each ECU that the ECU configuration specifies. In doing so, it also realizes the semantics of the communication attributes from the component descriptions <a class="spec-record-ref" data-req="SWS_Rte_02200" href="../spec/record.html?id=SWS_Rte_02200">[SWS_Rte_02200]</a> <a class="spec-record-ref" data-req="SWS_Rte_02201" href="../spec/record.html?id=SWS_Rte_02201">[SWS_Rte_02201]</a>. The RTE is configured and generated individually for each ECU <a class="spec-record-ref" data-req="SWS_Rte_05000" href="../spec/record.html?id=SWS_Rte_05000">[SWS_Rte_05000]</a> <a class="spec-record-ref" data-req="SWS_Rte_01316" href="../spec/record.html?id=SWS_Rte_01316">[SWS_Rte_01316]</a>. The generator produces C code which must comply with MISRA C <a class="spec-record-ref" data-req="SWS_Rte_01167" href="../spec/record.html?id=SWS_Rte_01167">[SWS_Rte_01167]</a> <a class="spec-record-ref" data-req="SWS_Rte_01168" href="../spec/record.html?id=SWS_Rte_01168">[SWS_Rte_01168]</a>. The location of the RTE between application software and Basic Software is shown in the ECU architecture picture (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_FIGURE_Figure_4_2_RTE.html" data-snip="SNIP_CLASSIC_RTE_FIGURE_Figure_4_2_RTE">SWS RTE p. 113</a>).</p>
<p>Downwards, the RTE exclusively uses standardized AUTOSAR services, including OS, COM, LdCom and Transformer <a class="spec-record-ref" data-req="SWS_Rte_02250" href="../spec/record.html?id=SWS_Rte_02250">[SWS_Rte_02250]</a>. The methodology provides a separate generation step for this, which only generates the scheduler code (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_FIGURE_Figure_3_144.html" data-snip="SNIP_CLASSIC_RTE_FIGURE_Figure_3_144">TR Methodology p. 463</a>).</p>

<h4>Interaction and interaction paths</h4>
<p>A SW-C consists of several <code>RunnableEntity</code>s. The RTE starts them according to the connected <code>RTEEvent</code>s <a class="spec-record-ref" data-req="SWS_Rte_02202" href="../spec/record.html?id=SWS_Rte_02202">[SWS_Rte_02202]</a> <a class="spec-record-ref" data-req="SWS_Rte_02203" href="../spec/record.html?id=SWS_Rte_02203">[SWS_Rte_02203]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_FIGURE_Figure_4_5_RTE.html" data-snip="SNIP_CLASSIC_RTE_FIGURE_Figure_4_5_RTE">SWS RTE p. 119</a>).</p>
<p>For sender-receiver communication, the following applies:</p>
<ul>
<li><strong>Buffer:</strong> Buffering takes place on the receiver side <a class="spec-record-ref" data-req="SWS_Rte_02515" href="../spec/record.html?id=SWS_Rte_02515">[SWS_Rte_02515]</a>.
<ul>
<li>"data" (not queued) follows last-is-best: A new value overwrites the old one <a class="spec-record-ref" data-req="SWS_Rte_02516" href="../spec/record.html?id=SWS_Rte_02516">[SWS_Rte_02516]</a> <a class="spec-record-ref" data-req="SWS_Rte_02520" href="../spec/record.html?id=SWS_Rte_02520">[SWS_Rte_02520]</a>.</li>
<li>"events" end up in a FIFO queue <a class="spec-record-ref" data-req="SWS_Rte_02521" href="../spec/record.html?id=SWS_Rte_02521">[SWS_Rte_02521]</a> <a class="spec-record-ref" data-req="SWS_Rte_02522" href="../spec/record.html?id=SWS_Rte_02522">[SWS_Rte_02522]</a>. If the buffer is full, the new event is discarded and an error flag is set <a class="spec-record-ref" data-req="SWS_Rte_02523" href="../spec/record.html?id=SWS_Rte_02523">[SWS_Rte_02523]</a>. The application sees this as <code>RTE_E_LOST_DATA</code> <a class="spec-record-ref" data-req="SWS_Rte_02571" href="../spec/record.html?id=SWS_Rte_02571">[SWS_Rte_02571]</a>.</li>
</ul></li>
<li><strong>Access types:</strong>
<ul>
<li>During implicit reading, the RTE provides a copy before the start of the runnable, which remains unchanged during execution <a class="spec-record-ref" data-req="SWS_Rte_06000" href="../spec/record.html?id=SWS_Rte_06000">[SWS_Rte_06000]</a> <a class="spec-record-ref" data-req="SWS_Rte_06001" href="../spec/record.html?id=SWS_Rte_06001">[SWS_Rte_06001]</a> <a class="spec-record-ref" data-req="SWS_Rte_06004" href="../spec/record.html?id=SWS_Rte_06004">[SWS_Rte_06004]</a>.</li>
<li>Runnables access explicitly via <code>Rte_Read</code>, <code>Rte_Receive</code> and <code>Rte_Send</code> <a class="spec-record-ref" data-req="SWS_Rte_01091" href="../spec/record.html?id=SWS_Rte_01091">[SWS_Rte_01091]</a> <a class="spec-record-ref" data-req="SWS_Rte_01092" href="../spec/record.html?id=SWS_Rte_01092">[SWS_Rte_01092]</a> <a class="spec-record-ref" data-req="SWS_Rte_01072" href="../spec/record.html?id=SWS_Rte_01072">[SWS_Rte_01072]</a>.</li>
<li>Runnables write implicitly via <code>Rte_IWrite</code> <a class="spec-record-ref" data-req="SWS_Rte_03744" href="../spec/record.html?id=SWS_Rte_03744">[SWS_Rte_03744]</a>.</li>
</ul></li>
</ul>
<p><strong>Inter-ECU communication via COM:</strong></p>
<ul>
<li>The RTE transmits composite data atomically via signal groups <a class="spec-record-ref" data-req="SWS_Rte_04527" href="../spec/record.html?id=SWS_Rte_04527">[SWS_Rte_04527]</a> <a class="spec-record-ref" data-req="SWS_Rte_03008" href="../spec/record.html?id=SWS_Rte_03008">[SWS_Rte_03008]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_COM_SECTION_4_3_1_11_2_Atomicity.html" data-snip="SNIP_CLASSIC_COM_SECTION_4_3_1_11_2_Atomicity">SWS RTE p. 326</a>).</li>
<li>COM reports events via callbacks such as <code>Rte_COMCbk_&lt;sn&gt;</code> <a class="spec-record-ref" data-req="SWS_Rte_03530" href="../spec/record.html?id=SWS_Rte_03530">[SWS_Rte_03530]</a> <a class="spec-record-ref" data-req="SWS_Rte_03001" href="../spec/record.html?id=SWS_Rte_03001">[SWS_Rte_03001]</a>. These callbacks activate runnables or wake up category 2 runnables at wait points <a class="spec-record-ref" data-req="SWS_Rte_03531" href="../spec/record.html?id=SWS_Rte_03531">[SWS_Rte_03531]</a> <a class="spec-record-ref" data-req="SWS_Rte_03532" href="../spec/record.html?id=SWS_Rte_03532">[SWS_Rte_03532]</a>.</li>
<li>Value filters run in COM during inter-ECU communication, intra-ECU in the RTE <a class="spec-record-ref" data-req="SWS_Rte_05500" href="../spec/record.html?id=SWS_Rte_05500">[SWS_Rte_05500]</a>.</li>
<li>Release difference: In R20-11, <a class="spec-record-ref" data-req="SWS_Rte_04505" href="../spec/record.html?id=SWS_Rte_04505">[SWS_Rte_04505]</a> requires the <code>ComHandleId</code>. The more recent document reference speaks of the Com Symbolic Name instead (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_COM_SECTION_4_3_1_11_1_1_Primitive_Data_Types.html" data-snip="SNIP_CLASSIC_COM_SECTION_4_3_1_11_1_1_Primitive_Data_Types">SWS RTE p. 324</a>).</li>
</ul>
<p><strong>Large byte arrays via LdCom:</strong></p>
<ul>
<li>The RTE sends and receives large byte arrays in R20-11 via LdCom and <code>LdCom_Transmit</code> <a class="spec-record-ref" data-req="SWS_Rte_01376" href="../spec/record.html?id=SWS_Rte_01376">[SWS_Rte_01376]</a> <a class="spec-record-ref" data-req="SWS_Rte_01377" href="../spec/record.html?id=SWS_Rte_01377">[SWS_Rte_01377]</a> <a class="spec-record-ref" data-req="SWS_Rte_01378" href="../spec/record.html?id=SWS_Rte_01378">[SWS_Rte_01378]</a>.</li>
<li>With TP transmission, the RTE locks the signal buffer until confirmation <a class="spec-record-ref" data-req="SWS_Rte_01379" href="../spec/record.html?id=SWS_Rte_01379">[SWS_Rte_01379]</a> <a class="spec-record-ref" data-req="SWS_Rte_01380" href="../spec/record.html?id=SWS_Rte_01380">[SWS_Rte_01380]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_COM_SECTION_4_3_1_16_2_Efficient_COM_for_large_data.html" data-snip="SNIP_CLASSIC_COM_SECTION_4_3_1_16_2_Efficient_COM_for_large_data">SWS RTE p. 350</a>).</li>
<li>Release difference: The R25-11 reference describes "Large Data Path in COM" with <code>Com_Transmit</code> instead (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_3_1_16_2_Large_Data_Path_in_COM.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_3_1_16_2_Large_Data_Path_in_COM">SWS RTE p. 343</a>). LdCom applies to R20-11.</li>
</ul>
<p><strong>Client-server communication:</strong></p>
<ul>
<li>Clients call synchronously or asynchronously via <code>Rte_Call</code> <a class="spec-record-ref" data-req="SWS_Rte_01102" href="../spec/record.html?id=SWS_Rte_01102">[SWS_Rte_01102]</a> <a class="spec-record-ref" data-req="SWS_Rte_01293" href="../spec/record.html?id=SWS_Rte_01293">[SWS_Rte_01293]</a> <a class="spec-record-ref" data-req="SWS_Rte_01294" href="../spec/record.html?id=SWS_Rte_01294">[SWS_Rte_01294]</a>. They fetch asynchronous results with <code>Rte_Result</code> <a class="spec-record-ref" data-req="SWS_Rte_01111" href="../spec/record.html?id=SWS_Rte_01111">[SWS_Rte_01111]</a>.</li>
<li>If the call is not a direct function call, the RTE buffers requests server-side in a FIFO queue and responses client-side with queue length 1 <a class="spec-record-ref" data-req="SWS_Rte_02527" href="../spec/record.html?id=SWS_Rte_02527">[SWS_Rte_02527]</a> <a class="spec-record-ref" data-req="SWS_Rte_02528" href="../spec/record.html?id=SWS_Rte_02528">[SWS_Rte_02528]</a>. It serializes the server access via the request queue <a class="spec-record-ref" data-req="SWS_Rte_02530" href="../spec/record.html?id=SWS_Rte_02530">[SWS_Rte_02530]</a>.</li>
<li>The RTE monitors timeouts independently of the reception mode <a class="spec-record-ref" data-req="SWS_Rte_03763" href="../spec/record.html?id=SWS_Rte_03763">[SWS_Rte_03763]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_3_2_5_Buffering.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_3_2_5_Buffering">SWS RTE p. 358</a>).</li>
</ul>
<p><strong>Further paths:</strong></p>
<ul>
<li>NvM requests from the SW-Cs are forwarded to the NvM by the runnables of the <code>NvBlockSwComponentType</code> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_NVM_FIGURE_Figure_4_39.html" data-snip="SNIP_CLASSIC_NVM_FIGURE_Figure_4_39">SWS RTE p. 259</a>). The return values of the NvM APIs are regulated by <a class="spec-record-ref" data-req="SWS_Rte_04535" href="../spec/record.html?id=SWS_Rte_04535">[SWS_Rte_04535]</a>.</li>
<li>The RTE reads Bulk NvData via BndM <a class="spec-record-ref" data-req="SWS_Rte_03883" href="../spec/record.html?id=SWS_Rte_03883">[SWS_Rte_03883]</a> <a class="spec-record-ref" data-req="SWS_Rte_03884" href="../spec/record.html?id=SWS_Rte_03884">[SWS_Rte_03884]</a>.</li>
<li>Between cores, <code>Rte_Call</code> writes into the IOC and activates the server task on the target core (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_FIGURE_Figure_7_25_OS.html" data-snip="SNIP_CLASSIC_RTE_FIGURE_Figure_7_25_OS">SWS OS p. 128</a>). The RTE does not execute ExecutableEntities in IOC callbacks, and it prevents simultaneous accesses to the same IOC API <a class="spec-record-ref" data-req="SWS_Rte_02736" href="../spec/record.html?id=SWS_Rte_02736">[SWS_Rte_02736]</a> <a class="spec-record-ref" data-req="SWS_Rte_02737" href="../spec/record.html?id=SWS_Rte_02737">[SWS_Rte_02737]</a>.</li>
</ul>

<h4>Synchronization, reentrancy and task contexts</h4>
<p><strong>Execution contexts:</strong></p>
<ul>
<li>Runnables run in the context of an OS task or ISR2 (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_FIGURE_Figure_4_5_RTE.html" data-snip="SNIP_CLASSIC_RTE_FIGURE_Figure_4_5_RTE">SWS RTE p. 119</a>). Within a task, the RTE complies with the configured execution order <a class="spec-record-ref" data-req="SWS_Rte_02207" href="../spec/record.html?id=SWS_Rte_02207">[SWS_Rte_02207]</a>.</li>
<li>Category 1 interrupts must not reach the RTE. The generator rejects corresponding configurations <a class="spec-record-ref" data-req="SWS_Rte_03594" href="../spec/record.html?id=SWS_Rte_03594">[SWS_Rte_03594]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_2_5_4_RTE_and_interrupt_categories.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_2_5_4_RTE_and_interrupt_categories">SWS RTE p. 182</a>).</li>
<li>An ISR2 can activate ExecutableEntities via external triggers <a class="spec-record-ref" data-req="SWS_Rte_04564" href="../spec/record.html?id=SWS_Rte_04564">[SWS_Rte_04564]</a>. The RTE, however, does not let runnables of SW-Cs run in the interrupt context <a class="spec-record-ref" data-req="SWS_Rte_03600" href="../spec/record.html?id=SWS_Rte_03600">[SWS_Rte_03600]</a>.</li>
<li>RTE callbacks must not block <a class="spec-record-ref" data-req="SWS_Rte_01165" href="../spec/record.html?id=SWS_Rte_01165">[SWS_Rte_01165]</a>.</li>
<li>Whether <code>Schedule</code> is called after a runnable is regulated by <a class="spec-record-ref" data-req="SWS_Rte_05113" href="../spec/record.html?id=SWS_Rte_05113">[SWS_Rte_05113]</a> to <a class="spec-record-ref" data-req="SWS_Rte_05115" href="../spec/record.html?id=SWS_Rte_05115">[SWS_Rte_05115]</a>.</li>
</ul>
<p><strong>Data consistency:</strong> The RTE guarantees consistency for communication via AUTOSAR interfaces <a class="spec-record-ref" data-req="SWS_Rte_03514" href="../spec/record.html?id=SWS_Rte_03514">[SWS_Rte_03514]</a> and for InterRunnableVariables <a class="spec-record-ref" data-req="SWS_Rte_03516" href="../spec/record.html?id=SWS_Rte_03516">[SWS_Rte_03516]</a>.</p>
<ul>
<li>For implicit InterRunnableVariables, it avoids simultaneous accesses. For explicit ones, it blocks concurrent accesses <a class="spec-record-ref" data-req="SWS_Rte_03517" href="../spec/record.html?id=SWS_Rte_03517">[SWS_Rte_03517]</a> <a class="spec-record-ref" data-req="SWS_Rte_03519" href="../spec/record.html?id=SWS_Rte_03519">[SWS_Rte_03519]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_2_6_6_2_InterRunnableVariables_with_explicit_behavior.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_2_6_6_2_InterRunnableVariables_with_explicit_behavior">SWS RTE p. 207</a>).</li>
<li>Exclusive areas are entered and left with <code>Rte_Enter</code> and <code>Rte_Exit</code> <a class="spec-record-ref" data-req="SWS_Rte_03515" href="../spec/record.html?id=SWS_Rte_03515">[SWS_Rte_03515]</a> <a class="spec-record-ref" data-req="SWS_Rte_01120" href="../spec/record.html?id=SWS_Rte_01120">[SWS_Rte_01120]</a> <a class="spec-record-ref" data-req="SWS_Rte_01123" href="../spec/record.html?id=SWS_Rte_01123">[SWS_Rte_01123]</a>. Different areas may be nested <a class="spec-record-ref" data-req="SWS_Rte_01122" href="../spec/record.html?id=SWS_Rte_01122">[SWS_Rte_01122]</a>.</li>
<li>The protection mechanism is selected by <code>RteExclusiveAreaImplMechanism</code>: <code>ALL_INTERRUPT_BLOCKING</code> <a class="spec-record-ref" data-req="SWS_Rte_03504" href="../spec/record.html?id=SWS_Rte_03504">[SWS_Rte_03504]</a>, <code>OS_INTERRUPT_BLOCKING</code> <a class="spec-record-ref" data-req="SWS_Rte_05164" href="../spec/record.html?id=SWS_Rte_05164">[SWS_Rte_05164]</a>, <code>OS_RESOURCE</code> <a class="spec-record-ref" data-req="SWS_Rte_03595" href="../spec/record.html?id=SWS_Rte_03595">[SWS_Rte_03595]</a> or <code>NONE</code> <a class="spec-record-ref" data-req="SWS_Rte_03999" href="../spec/record.html?id=SWS_Rte_03999">[SWS_Rte_03999]</a>.</li>
<li>If runnables call a blocking API within an exclusive area, it returns <code>RTE_E_IN_EXCLUSIVE_AREA</code> <a class="spec-record-ref" data-req="SWS_Rte_02739" href="../spec/record.html?id=SWS_Rte_02739">[SWS_Rte_02739]</a>.</li>
</ul>
<p><strong>Reentrancy:</strong></p>
<ul>
<li>The same runnable instance may only be concurrently activated if <code>canBeInvokedConcurrently</code> is set <a class="spec-record-ref" data-req="SWS_Rte_03523" href="../spec/record.html?id=SWS_Rte_03523">[SWS_Rte_03523]</a> <a class="spec-record-ref" data-req="SWS_Rte_05083" href="../spec/record.html?id=SWS_Rte_05083">[SWS_Rte_05083]</a>.</li>
<li>The RTE only supports multiple instances via code sharing <a class="spec-record-ref" data-req="SWS_Rte_03015" href="../spec/record.html?id=SWS_Rte_03015">[SWS_Rte_03015]</a> <a class="spec-record-ref" data-req="SWS_Rte_02002" href="../spec/record.html?id=SWS_Rte_02002">[SWS_Rte_02002]</a>. The instance is identified via the instance handle, which the entry point receives as the first parameter <a class="spec-record-ref" data-req="SWS_Rte_01016" href="../spec/record.html?id=SWS_Rte_01016">[SWS_Rte_01016]</a> <a class="spec-record-ref" data-req="SWS_Rte_02015" href="../spec/record.html?id=SWS_Rte_02015">[SWS_Rte_02015]</a>.</li>
<li>Because instances are scheduled independently, entry points should be reentrant (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_5_7_6_Reentrancy.html" data-snip="SNIP_CLASSIC_RTE_SECTION_5_7_6_Reentrancy">SWS RTE p. 804</a>).</li>
</ul>
<p><strong>Multi-core and partitioned systems:</strong> Here <a class="spec-record-ref" data-req="SWS_Rte_02711" href="../spec/record.html?id=SWS_Rte_02711">[SWS_Rte_02711]</a> restricts global variables in <code>Rte.c</code>. In addition, <a class="spec-record-ref" data-req="SWS_Rte_02712" href="../spec/record.html?id=SWS_Rte_02712">[SWS_Rte_02712]</a> requires separate files <code>Rte_Partition_&lt;PartitionName&gt;</code>.</p>

<h4>Lifecycles and operating modes</h4>
<p><strong>Startup of the BSW scheduler:</strong></p>
<ul>
<li>Before its initialization, only <code>SchM_Enter</code> and <code>SchM_Exit</code> are available (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_6_1_1_Initialization_of_the_Basic_Software_Scheduler.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_6_1_1_Initialization_of_the_Basic_Software_Scheduler">SWS RTE p. 400</a>).</li>
<li><code>SchM_Start</code> is always generated, returns in finite time and must be called before <code>BswM_Init()</code> <a class="spec-record-ref" data-req="SWS_Rte_04546" href="../spec/record.html?id=SWS_Rte_04546">[SWS_Rte_04546]</a> <a class="spec-record-ref" data-req="SWS_Rte_04547" href="../spec/record.html?id=SWS_Rte_04547">[SWS_Rte_04547]</a> <a class="spec-record-ref" data-req="SWS_Rte_04548" href="../spec/record.html?id=SWS_Rte_04548">[SWS_Rte_04548]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_6_7_2_SchM_Start.html" data-snip="SNIP_CLASSIC_RTE_SECTION_6_7_2_SchM_Start">SWS RTE p. 927</a>).</li>
<li><code>SchM_StartTiming</code> starts the periodic events and requires a preceding <code>SchM_Init</code> <a class="spec-record-ref" data-req="SWS_Rte_04549" href="../spec/record.html?id=SWS_Rte_04549">[SWS_Rte_04549]</a> <a class="spec-record-ref" data-req="SWS_Rte_04550" href="../spec/record.html?id=SWS_Rte_04550">[SWS_Rte_04550]</a> <a class="spec-record-ref" data-req="SWS_Rte_04551" href="../spec/record.html?id=SWS_Rte_04551">[SWS_Rte_04551]</a>.</li>
<li>All three calls are made exactly once per core by the EcuM (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_6_7_3_SchM_StartTiming.html" data-snip="SNIP_CLASSIC_RTE_SECTION_6_7_3_SchM_StartTiming">SWS RTE p. 928</a>).</li>
</ul>
<p><strong>Startup of the RTE:</strong></p>
<ul>
<li>The EcuM calls <code>Rte_Start</code> at the end of startup phase II, when the OS is available and all BSW modules are initialized <a class="spec-record-ref" data-req="SWS_Rte_02569" href="../spec/record.html?id=SWS_Rte_02569">[SWS_Rte_02569]</a> <a class="spec-record-ref" data-req="SWS_Rte_02585" href="../spec/record.html?id=SWS_Rte_02585">[SWS_Rte_02585]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_6_1_2_Initialization_of_the_RTE.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_6_1_2_Initialization_of_the_RTE">SWS RTE p. 460</a>).</li>
<li>If resource allocation fails, <code>Rte_Start</code> returns <code>RTE_E_LIMIT</code>, otherwise <code>RTE_E_OK</code> <a class="spec-record-ref" data-req="SWS_Rte_01261" href="../spec/record.html?id=SWS_Rte_01261">[SWS_Rte_01261]</a> <a class="spec-record-ref" data-req="SWS_Rte_01262" href="../spec/record.html?id=SWS_Rte_01262">[SWS_Rte_01262]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_5_8_1_4_Return_Value.html" data-snip="SNIP_CLASSIC_RTE_SECTION_5_8_1_4_Return_Value">SWS RTE p. 806</a>).</li>
<li>Initial values protect the receivers from uninitialized data <a class="spec-record-ref" data-req="SWS_Rte_06009" href="../spec/record.html?id=SWS_Rte_06009">[SWS_Rte_06009]</a> <a class="spec-record-ref" data-req="SWS_Rte_06010" href="../spec/record.html?id=SWS_Rte_06010">[SWS_Rte_06010]</a> <a class="spec-record-ref" data-req="SWS_Rte_02517" href="../spec/record.html?id=SWS_Rte_02517">[SWS_Rte_02517]</a>.</li>
</ul>
<p><strong>Shutdown and partition restart:</strong></p>
<ul>
<li><code>Rte_Stop</code> follows at the beginning of shutdown phase I <a class="spec-record-ref" data-req="SWS_Rte_02570" href="../spec/record.html?id=SWS_Rte_02570">[SWS_Rte_02570]</a> <a class="spec-record-ref" data-req="SWS_Rte_02584" href="../spec/record.html?id=SWS_Rte_02584">[SWS_Rte_02584]</a>. If a resource cannot be released, the function reports <code>RTE_E_LIMIT</code> <a class="spec-record-ref" data-req="SWS_Rte_01260" href="../spec/record.html?id=SWS_Rte_01260">[SWS_Rte_01260]</a>.</li>
<li>Thereafter, the RTE no longer activates runnables on this core <a class="spec-record-ref" data-req="SWS_Rte_02538" href="../spec/record.html?id=SWS_Rte_02538">[SWS_Rte_02538]</a>.</li>
<li>Before complete initialization and after the stop, the RTE ignores incoming client-server requests as well as sender-receiver data <a class="spec-record-ref" data-req="SWS_Rte_02535" href="../spec/record.html?id=SWS_Rte_02535">[SWS_Rte_02535]</a> <a class="spec-record-ref" data-req="SWS_Rte_02536" href="../spec/record.html?id=SWS_Rte_02536">[SWS_Rte_02536]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_4_6_1_3_Finalization_of_the_RTE.html" data-snip="SNIP_CLASSIC_STD_SECTION_4_6_1_3_Finalization_of_the_RTE">SWS RTE p. 461</a>). The BSW scheduler behaves analogously <a class="spec-record-ref" data-req="SWS_Rte_04552" href="../spec/record.html?id=SWS_Rte_04552">[SWS_Rte_04552]</a>.</li>
<li>In case of a partition restart, the RTE restores an initial environment <a class="spec-record-ref" data-req="SWS_Rte_02735" href="../spec/record.html?id=SWS_Rte_02735">[SWS_Rte_02735]</a>.</li>
</ul>

<p><strong>Mode management:</strong></p>
<ul>
<li>The RTE maintains the active mode of each Mode Machine Instance <a class="spec-record-ref" data-req="SWS_Rte_02546" href="../spec/record.html?id=SWS_Rte_02546">[SWS_Rte_02546]</a> and initiates the transition to the initial modes during initialization <a class="spec-record-ref" data-req="SWS_Rte_02544" href="../spec/record.html?id=SWS_Rte_02544">[SWS_Rte_02544]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_RTE_SECTION_4_4_6_Initialization_of_mode_machine_instances.html" data-snip="SNIP_CLASSIC_RTE_SECTION_4_4_6_Initialization_of_mode_machine_instances">SWS RTE p. 433</a>).</li>
<li>A mode manager requests transitions via <code>Rte_Switch</code> <a class="spec-record-ref" data-req="SWS_Rte_02631" href="../spec/record.html?id=SWS_Rte_02631">[SWS_Rte_02631]</a>. The notifications end up in a FIFO queue per instance <a class="spec-record-ref" data-req="SWS_Rte_02718" href="../spec/record.html?id=SWS_Rte_02718">[SWS_Rte_02718]</a> <a class="spec-record-ref" data-req="SWS_Rte_02719" href="../spec/record.html?id=SWS_Rte_02719">[SWS_Rte_02719]</a>.</li>
<li>If the queue is full, the new notification is discarded <a class="spec-record-ref" data-req="SWS_Rte_02720" href="../spec/record.html?id=SWS_Rte_02720">[SWS_Rte_02720]</a>. Between partitions, the RTE then reports <code>RTE_E_LIMIT</code> <a class="spec-record-ref" data-req="SWS_Rte_02675" href="../spec/record.html?id=SWS_Rte_02675">[SWS_Rte_02675]</a>. Only after completion of the transition does it remove the notification from the queue <a class="spec-record-ref" data-req="SWS_Rte_02721" href="../spec/record.html?id=SWS_Rte_02721">[SWS_Rte_02721]</a>.</li>
<li><a class="spec-record-ref" data-req="SWS_Rte_02665" href="../spec/record.html?id=SWS_Rte_02665">[SWS_Rte_02665]</a> divides the transition itself into ten steps (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_CAN_FIGURE_Figure_2_5_MODEMANAGEMENTGUIDE.html" data-snip="SNIP_CLASSIC_CAN_FIGURE_Figure_2_5_MODEMANAGEMENTGUIDE">EXP ModeManagementGuide p. 15</a>):
<ol>
<li>Activate mode disablings <a class="spec-record-ref" data-req="SWS_Rte_02661" href="../spec/record.html?id=SWS_Rte_02661">[SWS_Rte_02661]</a>.</li>
<li>Execute on-exit entities <a class="spec-record-ref" data-req="SWS_Rte_02562" href="../spec/record.html?id=SWS_Rte_02562">[SWS_Rte_02562]</a>.</li>
<li>Execute on-transition entities <a class="spec-record-ref" data-req="SWS_Rte_02707" href="../spec/record.html?id=SWS_Rte_02707">[SWS_Rte_02707]</a> <a class="spec-record-ref" data-req="SWS_Rte_02708" href="../spec/record.html?id=SWS_Rte_02708">[SWS_Rte_02708]</a>.</li>
<li>Execute on-entry entities <a class="spec-record-ref" data-req="SWS_Rte_02564" href="../spec/record.html?id=SWS_Rte_02564">[SWS_Rte_02564]</a>.</li>
<li>Switch mode disablings <a class="spec-record-ref" data-req="SWS_Rte_02563" href="../spec/record.html?id=SWS_Rte_02563">[SWS_Rte_02563]</a>.</li>
<li>Trigger <code>ModeSwitchedAckEvent</code>s <a class="spec-record-ref" data-req="SWS_Rte_02587" href="../spec/record.html?id=SWS_Rte_02587">[SWS_Rte_02587]</a>.</li>
</ol></li>
<li>Running runnables are not aborted during the mode transition <a class="spec-record-ref" data-req="SWS_Rte_02504" href="../spec/record.html?id=SWS_Rte_02504">[SWS_Rte_02504]</a>. A transition to the same mode is also fully executed <a class="spec-record-ref" data-req="SWS_Rte_02669" href="../spec/record.html?id=SWS_Rte_02669">[SWS_Rte_02669]</a>.</li>
<li>The mode manager queries the confirmation via <code>Rte_SwitchAck</code> <a class="spec-record-ref" data-req="SWS_Rte_02725" href="../spec/record.html?id=SWS_Rte_02725">[SWS_Rte_02725]</a>.</li>
<li>Modes can also activate OS schedule tables <a class="spec-record-ref" data-req="SWS_Rte_05146" href="../spec/record.html?id=SWS_Rte_05146">[SWS_Rte_05146]</a>.</li>
</ul>

<h4>Error handling, tracing and degradation</h4>
<p>The SW-C receives error states exclusively as a return value of the RTE API of type <code>Std_ReturnType</code> <a class="spec-record-ref" data-req="SWS_Rte_01034" href="../spec/record.html?id=SWS_Rte_01034">[SWS_Rte_01034]</a> (<a class="docref internal-spec-ref" href="../../spec/snippets/SNIP_CLASSIC_STD_SECTION_5_2_6_8_Error_Handling.html" data-snip="SNIP_CLASSIC_STD_SECTION_5_2_6_8_Error_Handling">SWS RTE p. 579</a>). <li>Application errors occupy the lower 6 bits <a class="spec-record-ref" data-req="SWS_Rte_02573" href="../spec/record.html?id=SWS_Rte_02573">[SWS_Rte_02573]</a>.</li>

<p><strong>Degradation:</strong></p>
<ul>
<li>For unconnected ports, the RTE defines a fixed behavior <a class="spec-record-ref" data-req="SWS_Rte_01329" href="../spec/record.html?id=SWS_Rte_01329">[SWS_Rte_01329]</a> <a class="spec-record-ref" data-req="SWS_Rte_01330" href="../spec/record.html?id=SWS_Rte_01330">[SWS_Rte_01330]</a>. <code>Rte_Call</code> then reports <code>RTE_E_UNCONNECTED</code> <a class="spec-record-ref" data-req="SWS_Rte_01334" href="../spec/record.html?id=SWS_Rte_01334">[SWS_Rte_01334]</a>.</li>
<li>Senders invalidate data via <code>Rte_Invalidate</code> <a class="spec-record-ref" data-req="SWS_Rte_01206" href="../spec/record.html?id=SWS_Rte_01206">[SWS_Rte_01206]</a>, enabled via <code>handleInvalid</code> <a class="spec-record-ref" data-req="SWS_Rte_05024" href="../spec/record.html?id=SWS_Rte_05024">[SWS_Rte_05024]</a>. Intra-ECU, the RTE implements the invalidation itself <a class="spec-record-ref" data-req="SWS_Rte_05025" href="../spec/record.html?id=SWS_Rte_05025">[SWS_Rte_05025]</a>:
<ul>
<li>With <code>keep</code>, it treats the reception as an error <a class="spec-record-ref" data-req="SWS_Rte_05030" href="../spec/record.html?id=SWS_Rte_05030">[SWS_Rte_05030]</a>.</li>
<li>With <code>replace</code>, it replaces the invalid value with the <code>initValue</code> <a class="spec-record-ref" data-req="SWS_Rte_05049" href="../spec/record.html?id=SWS_Rte_05049">[SWS_Rte_05049]</a>.</li>
