System architecture and role of the "Operating System" cluster

The cluster comprises only the module Os. It extends OSEK OS, for instance with software counters as alarm actions and automatically starting absolute alarms SWS OS p. 38. In addition, it bundles tasks, ISRs, alarms, ScheduleTables, counters, and hooks into OS-Applications. These are either trusted or non-trusted SWS OS p. 61. GetApplicationID [SWS_Os_00016] and GetCurrentApplicationID [SWS_Os_00797] provide the configured and currently executing OS-Application, respectively. Both identifier spaces are numbered consecutively starting from zero, as are the Core IDs [SWS_Os_00826] [SWS_Os_00825].

In the BSW architecture, the OS is a service provider with defined access rights. A table in the general BSW specification specifies which module groups are permitted to use which OS services: RTE/BSW-Scheduler, BswM, CDD, EcuM, MCAL, StbM, and remaining BSW SWS BSWGeneral p. 48. For example, a CDD should only use GetCounterValue and GetElapsedValue CDD-Guideline p. 21. The Inter-OS-Application Communicator (IOC) is part of the OS. It supplements RTE-internal and COM-based communication as a third communication type SWS OS p. 119. In R20-11, the separate generation of IOC and OS code is designated as DRAFT [SWS_Os_00831].

Context diagram: The OS serves as the execution, protection, and communication basis for EcuM, StbM, RTE, BswM, and CDD. Sources: SWS BSWGeneral p. 48, SWS EcuM p. 82, SWS StbM p. 220, ALEH p. 76

Interaction and interaction paths

Time synchronization with StbM: The safety overview for R20-11 assigns SyncScheduleTable, StartScheduleTableSynchron, GetScheduleTableStatus, and SetScheduleTableAsync to the coupling between synchronized time base and OS counter FSM-Übersicht p. 66. The sequence is as follows: In StbM_MainFunction, the StbM first queries GetScheduleTableStatus [SWS_Os_00227]. Only in the states WAITING, RUNNING, or RUNNING_AND_SYNCHRONOUS does it subsequently pass the synchronization count via SyncScheduleTable [SWS_Os_00199] SWS StbM p. 220. Interpretation: This sequence originates from later releases and is likely to apply analogously to R20-11 as well. From the synchronization count, the OS determines the drift between table time and synchronization counter SWS OS p. 52.

Sequence diagram: The StbM synchronizes an explicitly synchronized ScheduleTable only in a matching state. Sources: SWS StbM p. 220, [SWS_Os_00199], [SWS_Os_00227]

IOC between partitions and Cores: For "data" semantics (LastIsBest), the OS generates IocWrite/IocRead [SWS_Os_91003] [SWS_Os_91005]; for "event" semantics (Queue), IocSend/IocReceive [SWS_Os_00718] [SWS_Os_00738]. With LastIsBest, the RTE copies its buffer into an IOC-internal buffer from which the receiver reads SWS OS p. 190. If the queue is full, the sender reports IOC_E_LIMIT, and the receiver obtains IOC_E_LOST_DATA on the next read SWS OS p. 218. Optionally, the IOC invokes a <ReceiverPullCB> on the receiver Core for each reception [SWS_Os_00757].

Calls across partition boundaries: With CallTrustedFunction [SWS_Os_00097], the caller switches to the protection context of the providing OS-Application. To this end, a stub packs the arguments into a structure. The OS checks the authorization and returns E_OS_SERVICEID SWS OS p. 185 upon denial. As asynchronous alternatives, the BSW Distribution Guide mentions ActivateTask or SetEvent on a task of the target partition BSW-Distribution-Guide p. 66. For cross-Core calls, ActivateTaskAsyn and SetEventAsyn [SWS_Os_91022] [SWS_Os_91023] are available.

Synchronization, reentrancy, and execution contexts

Most OS services are synchronous and reentrant. A few exceptions are important for integration:

StartCoreNon-reentrant, only before StartOS[SWS_Os_00676]
ControlIdlenon-reentrant[SWS_Os_00769]

IocRead_<IocId>Synchronous, non-reentrant[SWS_Os_91005]

Spinlocks: The OS provides spinlocks for cross-Core mutual exclusion. GetSpinlock [SWS_Os_00686] waits actively without descheduling the caller. In Extended Status, it reports E_OS_INTERFERENCE_DEADLOCK or E_OS_NESTING_DEADLOCK SWS OS p. 199. TryToGetSpinlock [SWS_Os_00703] returns immediately instead. Before terminating a task and before WaitEvent, all spinlocks must be released via ReleaseSpinlock [SWS_Os_00695]. Enclosing in SuspendAllInterrupts helps prevent interference on the same Core, which the OS can also handle itself via OsSpinlockLockMethod SWS OS p. 101. Spinlocks can be called at task and category 2 ISR level. From category 1 ISRs, the behavior is undefined SWS OS p. 115.

ISR categories and context rules: The OS context is available only in category 2 ISRs. Outside of a category 2 ISR, GetISRID INVALID_ISR returns [SWS_Os_00511] SWS OS p. 171. From a category 1 ISR, the result of GetCurrentApplicationID is undefined SWS OS p. 162. The interrupt source APIs exist only for category 2 sources [SWS_Os_00808]; nested calls return E_OS_NOFUNC [SWS_Os_00809]. According to [SWS_Os_00811], EnableInterruptSource additionally clears the pending flag. However, the API definition [SWS_Os_91020] contains the parameter ClearPending for this purpose. Interpretation: The clearing is presumably tied to ClearPending == TRUE. A synchronous ActivateTask across Core boundaries returns only after activation or error detection on the target Core SWS OS p. 103.

Lifecycles and operating modes

Start: In Master-Core-StartPreOS, EcuM first starts all configured Cores in a loop via StartCore. It then calls StartOS(ECUM_DEFAULT_APP_MODE) SWS EcuM p. 82. After StartOS, StartCore is no longer permitted [SWS_Os_00676]. By contrast, GetCoreID [SWS_Os_00674] may already be called before StartOS SWS OS p. 111. After StartOS and before the StartupHooks, the OS sets all OS-Applications to APPLICATION_ACCESSIBLE SWS OS p. 62. Subsequently, the StartupHook_<App> run [SWS_Os_00539]. If an IOC is configured, StartOS in default mode initializes its data structures via IocInit (DRAFT) [SWS_Os_00830] [SWS_Os_91026].

ScheduleTables: The OS starts a ScheduleTable absolutely [SWS_Os_00358] or relative to the current counter value [SWS_Os_00347]. StopScheduleTable [SWS_Os_00006] stops it. A subsequent restart begins at the start of the table again SWS OS p. 46. NextScheduleTable [SWS_Os_00191] chains two tables. In case of a synchronous start [SWS_Os_00201], the table waits for the first synchronization count, indefinitely if in doubt SWS OS p. 49. SetScheduleTableAsync [SWS_Os_00422] terminates synchronization, but the expiry points continue to be processed SWS OS p. 188. [SWS_Os_00784] defines the five states.

State diagram: Lifecycle of an explicitly synchronized ScheduleTable. Sources: [SWS_Os_00784], SWS OS p. 49, SWS OS p. 188

OS-Applications: Three states are normative for R20-11 [SWS_Os_00773]. Later releases list only two values for the type SWS OS p. 161.

  • APPLICATION_ACCESSIBLE: Startup state, the objects of the OS-Application are accessible from the outside SWS OS p. 62.
  • APPLICATION_RESTARTING: Applies until the OS-Application itself calls AllowAccess [SWS_Os_00501].
  • APPLICATION_TERMINATED: Permanently terminated; the state can be queried via GetApplicationState [SWS_Os_00499].

Idle and shutdown: ControlIdle selects an idle action for each Core, for example for power-saving measures [SWS_Os_00769]. The default is IDLE_NO_HALT [SWS_Os_00793]. ShutdownAllCores [SWS_Os_00713] triggers the synchronized shutdown. The call does not return and is ignored from non-trusted code SWS OS p. 204. EcuM issues it in Master-Core-OffPreOS after BswM_Deinit and SchM_Deinit SWS EcuM p. 91. The application-specific shutdown hooks then run on each Core, followed by a synchronization barrier and the global ShutdownHook SWS OS p. 88 SWS OS p. 189 [SWS_Os_00541].

Error handling, protection violations, and degradation

Error reporting via return values and hooks: The OS reports errors via StatusType returns, many of them only in Extended Status. The AUTOSAR-specific error codes are defined in [SWS_Os_91025]. In Extended Mode, the OS rejects pointers that are NULL_PTR with E_OS_ILLEGAL_ADDRESS SWS OS p. 38. Detected errors are passed to the ErrorHook or ErrorHook_<App> [SWS_Os_00540], such as with the interrupt source APIs [SWS_Os_00810]. A special case is IncrementCounter: If an alarm action fails, the OS calls the error hooks, but the service itself returns E_OK SWS OS p. 190. With ActivateTaskAsyn, error messages are lost if the caller no longer exists SWS OS p. 203. A DET connection of the OS is not documented in the present material.

Access protection: If configured access rights to an OS object are missing, the service returns E_OS_ACCESS SWS OS p. 73. For preventive checking, CheckObjectAccess [SWS_Os_00256], CheckObjectOwnership [SWS_Os_00017], and the memory checks [SWS_Os_00512] [SWS_Os_00513] are available. The macros OSMEMORY_IS_* evaluate their result SWS OS p. 160. An unconfigured trusted function index triggers the ErrorHook with E_OS_SERVICEID SWS OS p. 85. Even trusted OS-Applications can be restricted in write access [SWS_Os_00795].

Escalation via the ProtectionHook: In case of severe protection violations, the OS calls the ProtectionHook [SWS_Os_00538]. Its ProtectionReturnType [SWS_Os_00787] determines the reaction: terminate the task or ISR, terminate the OS-Application (with or without restart), or shut down the system SWS OS p. 187.

Sequence diagram: Escalation paths after a protection violation, controlled by the return value of the ProtectionHook. Sources: SWS OS p. 187, [SWS_Os_00538], [SWS_Os_00787], ALEH p. 69

Termination and restart: An OS-Application can also be terminated specifically via TerminateApplication [SWS_Os_00258]. The OS then terminates its tasks and ISRs, disables its interrupts, and stops its alarms and ScheduleTables SWS OS p. 62. In R20-11, RestartType controls the restart with RESTART/NO_RESTART [SWS_Os_00788]. Later releases use OS_OSAPPLICATION_RESTART instead and ignore the parameter SWS OS p. 194. For an externally triggered restart, the guide specifies the following steps: notify the RTE, store the decision for the OSRestartTask, call TerminateApplication(<partition>, RESTART), and report to the DEM ALEH p. 75. The OSRestartTask initiates cleanup via CallTrustedFunction directly or via the BswM. Afterwards, AllowAccess releases the OS-Application again ALEH p. 76 [SWS_Os_00501].
