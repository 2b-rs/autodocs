System architecture and role of the module cluster

The cluster forms the LIN communication stack of the Classic Platform from the hardware to mode management. The four modules divide the tasks as follows:

  • Lin is the MCAL driver. It encapsulates the LIN controller or UART and calculates the classic or enhanced checksum [SWS_Lin_00019]. It accepts frames as Lin_PduType with PID, checksum model, response type, length, and SDU pointer [SWS_Lin_00232].
  • LinTrcv controls the external transceiver via the modes LINTRCV_TRCV_MODE_NORMAL, …_STANDBY, and …_SLEEP [SWS_LinTrcv_00168] and checks wakeup events [SWS_LinTrcv_00012].
  • LinIf is the hardware abstraction. It manages schedule tables and channel states and contains the transport protocol LinTp [SWS_LinIf_00350].
  • LinSM implements mode requests from ComM [SWS_LinSM_00126] and reports state and schedule to BswM [SWS_LinSM_00229].

The node role determines via configuration which functions a module provides:

  • Only in the master do Lin_SendFrame, Lin_GoToSleep, and Lin_GetStatus [SWS_Lin_00287] [SWS_Lin_00288] [SWS_Lin_00289] as well as LinSM_ScheduleRequest [SWS_LinSM_00241] exist.
  • Only in the slave do the driver callbacks of LinIf [SWS_LinIf_00863] [SWS_LinIf_00866] and LinSM_GotoSleepIndication [SWS_LinSM_00243] exist.
  • For slaves, LinIf also manages NAD and PIDs according to the node model of ISO 17987-3 [SWS_LinIf_00767] [SWS_LinIf_00778] LinIf-SWS p. 59.

Context diagram: The modules of the cluster are located between ComM/BswM/PduR and the hardware; wakeup events additionally pass through EcuM. Sources: [SWS_LinSM_00126] [SWS_LinIf_00360] [SWS_LinIf_00544] [SWS_Lin_00234] [SWS_LinIf_00378]

Interaction and interaction paths

Master path. LinIf processes the schedule table in LinIf_MainFunction_<LinIfChannel.ShortName> [SWS_LinIf_00384]. A transmit slot proceeds as follows:

  1. LinIf fetches the data via <User_TriggerTransmit> [SWS_LinIf_00528] and passes them with Lin_SendFrame [SWS_Lin_00191].
  2. If the upper layer returns E_NOT_OK, the frame is not sent [SWS_LinIf_00706].
  3. At the earliest after the maximum frame length, LinIf queries the status with Lin_GetStatus [SWS_Lin_00168] LinIf-SWS p. 35.
  4. In case of LIN_TX_ERROR or LIN_TX_BUSY, <User_TxConfirmation> follows with E_NOT_OK [SWS_LinIf_00728].

If the upper layer is PduR, <User_TriggerTransmit> is fixed PduR_LinIfTriggerTransmit [SWS_LinIf_00722]. LinIf_Transmit only schedules sporadic (master) or event-triggered (slave) frames [SWS_LinIf_00201] LinIf-SWS p. 79. Under NULL_SCHEDULE, it rejects [SWS_LinIf_00719].

Slave path. The sequence is triggered by the header of the master:

  1. The driver reports each header via LinIf_HeaderIndication with PID and a pointer to its buffer [SWS_Lin_00280] [SWS_LinIf_91004].
  2. LinIf evaluates the PID:
    • For a transmit frame, <User_TriggerTransmit> writes directly into the driver buffer [SWS_LinIf_00738], and LinIf sets Drc = LIN_FRAMERESPONSE_TX [SWS_LinIf_00739].
    • Receive frames receive LIN_FRAMERESPONSE_RX [SWS_LinIf_00733].
    • Irrelevant frames receive LIN_FRAMERESPONSE_IGNORE [SWS_LinIf_00748].
  3. Lin evaluates Drc, Cs, and Dl [SWS_Lin_00282] [SWS_Lin_00283] [SWS_Lin_00286].
  4. Lin concludes each relevant response before the next header with Rx-Indication, Tx-Confirmation, or Error-Indication [SWS_Lin_00285].
  5. LinIf forwards the result to <User_RxIndication> or <User_TxConfirmation>, respectively [SWS_LinIf_00734] [SWS_LinIf_00741].

Newer releases replace these callouts with the LSduR path (status DRAFT) LinIf-SWS p. 43. For R20-11, the <User_…> interfaces apply.

Sequence diagram: A slave transmits its response only after header indication, buffer filling by the upper layer, and release via Drc. Sources: [SWS_Lin_00280] [SWS_LinIf_00738] [SWS_LinIf_00739] [SWS_Lin_00283] [SWS_LinIf_00742] LinIf-SWS p. 121

Transport protocol and schedule change. LinTp_Transmit prepares a TP message [SWS_LinIf_00351]. In the master, LinTp requests a schedule change via BswM_LinTp_RequestMode with LinTp_Mode [SWS_LinIf_00360] [SWS_LinIf_00629]. The chain then proceeds as follows LinIf-SWS p. 132:

  1. BswM calls LinSM_ScheduleRequest [SWS_LinSM_00113].
  2. LinSM calls LinIf_ScheduleRequest [SWS_LinIf_00202].
  3. LinIf confirms via <User>_ScheduleRequestConfirmation to LinSM_ScheduleRequestConfirmation [SWS_LinIf_00520] [SWS_LinSM_00129].

The parameter names of these APIs were renamed in R22-11 Release Overview p. 50. In R20-11, they are still named Schedule/schedule.

Synchronization, reentrancy and task contexts

Cyclic processing. One LinIf_MainFunction_<LinIfChannel.ShortName> exists per channel. Other LinIf APIs such as LinIf_GotoSleep, LinIf_Transmit, LinIf_ScheduleRequest, and LinIf_Wakeup can interrupt it. Shared areas must therefore be protected LinIf-SWS p. 119. LinSM_MainFunction manages the timeout timers [SWS_LinSM_00156].

Direct calls. Sleep transitions deliberately do not wait for the next MainFunction. They thus run in the context of the caller:

  • LinSM calls LinIf_GotoSleep immediately [SWS_LinSM_00036] [SWS_LinSM_00231].
  • LinIf calls Lin_GoToSleepInternal immediately [SWS_LinIf_00757].

Slave callbacks. The callbacks are reentrant for different channels, but not for the same channel [SWS_LinIf_91005] [SWS_LinIf_91006] [SWS_LinIf_91007]. In the diagram, LinIf_HeaderIndication directly follows the hardware interrupt LinIf-SWS p. 121. Interpretation: The callbacks are thus likely to run mostly in ISR context. <User_TriggerTransmit> should therefore remain short. The driver itself transmits and receives non-blockingly Lin-SWS p. 28.

Reentrancy in R20-11. R20-11 declares Lin_GoToSleep, Lin_Wakeup, and Lin_GetStatus as “Non Reentrant” [SWS_Lin_00166] [SWS_Lin_00169] [SWS_Lin_00168]. Newer documents allow reentrancy for different channels Lin-SWS p. 43. For R20-11, the stricter version is normative.

A similar discrepancy exists for the transceiver: LinIf_SetTrcvMode is reentrant [SWS_LinIf_00544], whereas the called LinTrcv_SetOpMode is not [SWS_LinTrcv_00002]. Interpretation: Competing calls should be serialized by the integration.

Multicore. Channel and transceiver channel must belong to the same ECUC partition [SWS_Lin_CONSTR_00279] [SWS_LinTrcv_00177].

Lifecycles and operating modes

Initialization. The mode management guide initializes in the sequence Lin_Init, LinIf_Init, LinSM_Init, LinTp_Init [SWS_Lin_00006] [SWS_LinIf_00198] [SWS_LinSM_00155] ModeManagementGuide p. 54. The position of LinTrcv_Init [SWS_LinTrcv_00001] is not evident from the source. The modules set the following initial states:

  • LinIf_Init sets NULL_SCHEDULE [SWS_LinIf_00197] LinIf-SWS p. 90 in the master.
  • LinTp_Init sets each channel to LINTP_CHANNEL_IDLE [SWS_LinIf_00710].
  • LinSM starts in LINSM_NO_COM without notifying ComM or BswM LinSM-SWS p. 23.

State diagram: LinSM communication modes and LIN channel states of the driver; LIN_CH_SLEEP_PENDING exists only in the master. Sources: [SWS_LinSM_00220] [SWS_LinSM_00301] LinSM-SWS p. 24 Lin-SWS p. 23 Lin-SWS p. 37

Sleep in the master. If ComM requests COMM_NO_COMMUNICATION, LinSM calls LinIf_GotoSleep [SWS_LinSM_10208]. LinIf then sends the go-to-sleep command via Lin_GoToSleep. The channel transitions to LIN_CH_SLEEP_PENDING Lin-SWS p. 43 even in case of an error. The confirmation reaches LinSM as LinSM_GotoSleepConfirmation [SWS_LinSM_00135].

Sequence diagram: The sleep request is accepted synchronously, but the command is sent only in the next LinIf MainFunction and confirmed asynchronously. Sources: [SWS_LinSM_00036] [SWS_LinSM_00135] [SWS_LinIf_00521] LinSM-SWS p. 47 LinIf-SWS p. 93

Sleep in the slave. Two events initiate the transition: an MRF with NAD 0 [SWS_LinIf_00750] or a bus idle timeout [SWS_LinIf_00755]. LinIf reports both via LinSM_GotoSleepIndication [SWS_LinIf_00756] [SWS_LinSM_91000]. The further sequence LinIf-SWS p. 55:

  1. LinSM calls LinIf_GotoSleep.
  2. LinIf puts the driver to sleep via Lin_GoToSleepInternal and confirms with TRUE [SWS_LinIf_00759].
  3. If ComM had previously requested COMM_NO_COMMUNICATION [SWS_LinSM_00230], ComM receives ComM_BusSM_BusSleepMode [SWS_LinSM_00233].
  4. Otherwise, LinSM restarts the wakeup procedure [SWS_LinSM_00234].

Optionally, the transceiver is switched as well via LinIf_SetTrcvMode(LINTRCV_TRCV_MODE_SLEEP) [SWS_LinSM_00138] LinIf-SWS p. 137.

Wakeup procedure by ComM. Upon COMM_FULL_COMMUNICATION, LinSM starts a confirmation timer and calls LinIf_Wakeup directly LinSM-SWS p. 27 LinSM-SWS p. 27. A running silence-after-wakeup timer delays this call [SWS_LinSM_00237]. LinIf decides based on the wakeup flag:

  • If the flag is not set, LinIf calls Lin_Wakeup with a wakeup pulse [SWS_LinIf_00205] LinIf-SWS p. 89.
  • If the flag is set, Lin_WakeupInternal without a pulse should be sufficient [SWS_Lin_00262].

A slave confirms wakeup only upon the first received header [SWS_LinIf_00761].

External wakeup events. EcuM calls LinIf_CheckWakeup. Depending on the source, LinIf branches to Lin_CheckWakeup or LinTrcv_CheckWakeup [SWS_LinIf_00378] [SWS_Lin_00160]. The drivers report a detected event to EcuM and via LinIf_WakeupConfirmation to LinIf [SWS_LinIf_00715] [SWS_LinTrcv_91002] Lin-SWS p. 42. LinIf_SetTrcvWakeupMode controls the wake notification of the transceiver [SWS_LinIf_00550] [SWS_LinTrcv_00169].

Error Handling, DET Tracing, and Degradation

Development errors (DET). All modules check parameters and initialization status against DET:

  • LinIf: [SWS_LinIf_00376] [SWS_LinIf_00849]
  • Lin, among others LIN_E_STATE_TRANSITION [SWS_Lin_00258] [SWS_Lin_00260]
  • LinSM: [SWS_LinSM_00053] [SWS_LinSM_00240]
  • LinTrcv: [SWS_LinTrcv_00005] LinTrcv-SWS p. 26

Runtime errors. Lin mandatorily requires Dem_SetEventStatus [SWS_Lin_00234]. The driver reports hardware timeouts as LIN_E_TIMEOUT [SWS_Lin_00290]. In the slave, Lin reports errors as Lin_SlaveErrorType [SWS_Lin_91140] [SWS_Lin_00277]. LinIf then evaluates the response as lost and reports LINIF_E_RESPONSE, except in the case of LIN_ERR_HEADER [SWS_LinIf_00735] [SWS_LinIf_00729]. LinSM reports missing callbacks as LINSM_E_CONFIRMATION_TIMEOUT [SWS_LinSM_00224].

Degradation. Several mechanisms maintain operation in an orderly manner after errors:

  • response_error signal: Response errors set the signal via Com_SendSignal [SWS_LinIf_00744] [SWS_LinIf_00764]. After successful transmission, it is reset [SWS_LinIf_00747] LinIf-SWS p. 58.
  • LinSM consistency: Upon E_NOT_OK, LinSM sets the previous state again so that ComM and BswM receive an indication [SWS_LinSM_00177].
  • LinTp aborts: Upon N_As or N_Cr timeout, LinTp aborts and reports E_NOT_OK to PduR [SWS_LinIf_00801] [SWS_LinIf_00806].
  • Buffer shortage: If receive buffer is missing, LinTp suspends the SRF headers [SWS_LinIf_00679]. Alternatively, it abortively returns to the application schedule [SWS_LinIf_00792] [SWS_LinIf_00879].
  • Node Configuration: LinIf discards a pending response upon N_As timeout [SWS_LinIf_00786].
