Role in the LIN Stack: Master and Slave Channels Behind One Interface

The LIN Interface (LinIf) is the abstraction layer above the LIN driver Lin. It accepts requests from upper layers, implements them on the bus, and additionally contains the LIN Transport Protocol (LinTp). The LIN State Manager forwards schedule requests (master only) as well as wakeup and sleep requests to LinIf (SWS LinIf p. 23). The LIN driver reports its events exclusively to LinIf (SWS LIN-Treiber p. 53). LinIf reaches upper users via configurable callouts (SWS LinIf p. 113). In R20-11, these calls are named <User_TriggerTransmit>, <User_TxConfirmation>, and <User_RxIndication> ([SWS_LinIf_00528], [SWS_LinIf_00529], [SWS_LinIf_00530]). More recent document passages and diagrams name LSduR in their place. According to the change history, this change was introduced only with R24-11 (SWS LinIf p. 1).

The parameter LinIfNodeType specifies whether a channel operates as master or slave. Slave-specific services such as LinIf_HeaderIndication, LinIf_RxIndication, or LinIf_SetPIDTable exist only if at least one slave channel is configured. Conversely, LinIf_ScheduleRequest exists only with at least one master channel ([SWS_LinIf_00858], [SWS_LinIf_00860], [SWS_LinIf_00863], [SWS_LinIf_00864]). Further components can be enabled or disabled prior to compilation:

  • LinTp via LinIfTpSupported (SWS LinIf p. 99),
  • Bus Mirroring via LinIfBusMirroringSupported ([SWS_LinIf_00875]),
  • the callout for the response_error signal ([SWS_LinIf_00766]).

The structures LinIf_ConfigType and LinTp_ConfigType are implementation-specific ([SWS_LinIf_00668], [SWS_LinIf_00426]). SWS LinIf p. 96 provides an overview of the parameters.

Context diagram: LinIf mediates between PduR, LinSM, BswM, EcuM, and Com above and Lin, LinTrcv, DET, and Mirror below. Sources: [SWS_LinIf_00359], [SWS_LinIf_00360], [SWS_LinIf_00378], [SWS_LinIf_00764], [SWS_LinIf_00838], SWS LinIf p. 23

For the transceivers, LinIf provides a uniform interface across all LinTrcv drivers. LinIf_SetTrcvMode, LinIf_GetTrcvMode, LinIf_GetTrcvWakeupReason, and LinIf_SetTrcvWakeupMode forward the call to the appropriate LinTrcv service (SWS LinIf p. 24, [SWS_LinIf_00544], [SWS_LinIf_00545], [SWS_LinIf_00547], [SWS_LinIf_00550]). If bus mirroring is enabled for a channel with LinIf_EnableBusMirroring, LinIf reports every received, transmitted, or corrupted frame via Mirror_ReportLinFrame() ([SWS_LinIf_00876], [SWS_LinIf_00838], [SWS_LinIf_00839], [SWS_LinIf_00869], SWS BusMirroring p. 30).

Lifecycle: LinIf_Init, Channel States, and Main Function per Channel

After reset, LinIf is in the LINIF_UNINIT state. LinIf_Init leads to LINIF_INIT. There, each channel has its own sub-state machine with the states LINIF_CHANNEL_OPERATIONAL and LINIF_CHANNEL_SLEEP ([SWS_LinIf_00198], SWS LinIf p. 47, SWS LinIf p. 34). On master channels, LinIf_Init sets the NULL_SCHEDULE (SWS LinIf p. 90). On slave channels, it loads initial NAD, configured NAD, and PIDs from the configuration ([SWS_LinIf_00767], [SWS_LinIf_00768]).

State diagram: LinIf_Init leads from LINIF_UNINIT to LINIF_INIT; there, each channel alternates between OPERATIONAL and SLEEP. Sources: [SWS_LinIf_00198], [SWS_LinIf_00204], [SWS_LinIf_00205], SWS LinIf p. 34

The actual processing is performed by LinIf_MainFunction_<LinIfChannel.ShortName>. It exists once per channel and is called by the SchM at the rate of LinIfMainFunctionPeriod ([SWS_LinIf_00384], SWS LinIf p. 45). In the master, it queries the Schedule Table Manager and triggers transmission and reception. In the slave, it primarily monitors times; the frames themselves can also be handled directly in the callbacks. Other calls such as LinIf_Transmit, LinIf_ScheduleRequest, LinIf_GotoSleep, or LinIf_Wakeup can interrupt the main function. Shared data must therefore be protected (SWS LinIf p. 119).

Master Channel: Schedule Tables Determine Bus Traffic

On a master channel, the schedule table is the basis of all communication. The intervals between two frames are multiples of LinIfMainFunctionPeriod. The predefined NULL_SCHEDULE contains no entries (SWS LinIf p. 44). Up to 255 tables per channel can be addressed using LinIf_SchHandleType; the value 0 stands for NULL_SCHEDULE ([SWS_LinIf_00197]). LinIf_ScheduleRequest operates asynchronously. It rejects with E_NOT_OK, for example if the channel is sleeping or the table is unknown ([SWS_LinIf_00202], SWS LinIf p. 86). Once the switch is completed, <User>_ScheduleRequestConfirmation reports this ([SWS_LinIf_00520]). In R20-11, the parameter is still named Schedule; it was renamed only later (SWS LinIf p. 1).

LinIf_Transmit does not send anything directly onto the bus. It only marks a sporadic frame (master) or an event-triggered frame (slave) as pending. For other frame types, it nevertheless returns E_OK as long as the active schedule is not NULL_SCHEDULE; there it returns E_NOT_OK ([SWS_LinIf_00201], [SWS_LinIf_00700], [SWS_LinIf_00719], SWS LinIf p. 125).

When a transmit entry is due, the following happens:

  1. LinIf fetches the payload with <User_TriggerTransmit>.
  2. It passes it to the driver using Lin_SendFrame. If the user returns E_NOT_OK, the frame is not sent ([SWS_LinIf_00706], SWS LinIf p. 37).
  3. LinIf queries the status with Lin_GetStatus at the earliest after the maximum frame length (SWS LinIf p. 35).
  4. In case of LIN_TX_ERROR or LIN_TX_BUSY, <User_TxConfirmation> follows with E_NOT_OK ([SWS_LinIf_00728]).

Sequence diagram: The data is fetched and transmitted in the due cycle; confirmation follows only after the status query in a later cycle. Sources: [SWS_LinIf_00384], [SWS_LinIf_00706], [SWS_LinIf_00728], [SWS_LinIf_00874], SWS LinIf p. 82

Slave Channel: Processing in Step with Received Headers

A slave does not know the master's schedule. It only reacts to headers reported by the LIN driver via LinIf_HeaderIndication (SWS LinIf p. 38, [SWS_LinIf_91004]). LinIf evaluates the PID and informs the driver via PduPtr whether it shall receive, transmit, or ignore the frame ([SWS_LinIf_00733], [SWS_LinIf_00739], [SWS_LinIf_00748]). For transmit frames, LinIf calls <User_TriggerTransmit> with the driver's buffer while still inside the callback. Copying the response is handled by the driver ([SWS_LinIf_00738], SWS LinIf p. 121).

The driver callbacks follow after the header:

  • A received response is reported by LinIf_RxIndication; LinIf forwards it via <User_RxIndication> ([SWS_LinIf_91005], [SWS_LinIf_00734]).
  • A transmitted response is confirmed by LinIf_TxConfirmation; this is followed by <User_TxConfirmation> with E_OK ([SWS_LinIf_91006], [SWS_LinIf_00741]).
  • If these callbacks arrive without a preceding matching header, LinIf ignores them ([SWS_LinIf_00848], [SWS_LinIf_00852]).

Activity diagram: The PID evaluation in LinIf_HeaderIndication determines whether the driver receives, transmits, or ignores. Sources: [SWS_LinIf_00733], [SWS_LinIf_00738], [SWS_LinIf_00739], [SWS_LinIf_00740], [SWS_LinIf_00748], [SWS_LinIf_00775], [SWS_LinIf_00776], [SWS_LinIf_00846], SWS LinIf p. 134

The slave transmits an event-triggered frame only if a response is pending for it. The first data byte then contains the PID of the associated unconditional frame. After successful transmission, the pending flag is cleared ([SWS_LinIf_00731], [SWS_LinIf_00732], SWS LinIf p. 130). LinIf distributes MRF and SRF between the node configuration and the transport layer. If a configuration response is pending, the Node Configuration Handler answers the SRF; otherwise, the SRF header goes to LinTp ([SWS_LinIf_00772], [SWS_LinIf_00773], [SWS_LinIf_00775], [SWS_LinIf_00776], SWS LinIf p. 54).

Sleep and Wakeup: Separate Paths for Master and Slave

LinIf_GotoSleep operates asynchronously. It returns E_OK even if the transition is already in progress or the channel is already sleeping ([SWS_LinIf_00204], SWS LinIf p. 88). For the master, the diagram shows the sequence: The main function sends the go-to-sleep command and then evaluates Lin_GetStatus. <User>_GotoSleepConfirmation reports the result (SWS LinIf p. 136, [SWS_LinIf_00521]). If a slave requests a wakeup prior to this confirmation, the channel remains operational (SWS LinIf p. 37).

A slave enters sleep mode in two cases: It receives an MRF with NAD 0, or the bus idle timer (LinIfBusIdleTimeoutPeriod) expires. The timer runs only in LINIF_CHANNEL_OPERATIONAL and restarts with every driver callback ([SWS_LinIf_00750], [SWS_LinIf_00751], [SWS_LinIf_00752], [SWS_LinIf_00753], [SWS_LinIf_00754], [SWS_LinIf_00755]). LinIf reports the sleep request with <User>_GotoSleepIndication. If the user then calls LinIf_GotoSleep, the following happens immediately and without waiting for the main function: LinIf calls Lin_GoToSleepInternal, clears the wakeup flag, and reports <User>_GotoSleepConfirmation with TRUE ([SWS_LinIf_00756], [SWS_LinIf_00757], [SWS_LinIf_00758], [SWS_LinIf_00759], SWS LinIf p. 55).

Sequence diagram: In the slave, LinIf_GotoSleep calls the driver immediately; the transceiver is optionally switched by the user. Sources: [SWS_LinIf_00756], [SWS_LinIf_00757], [SWS_LinIf_00758], [SWS_LinIf_00759], [SWS_LinIf_00544], SWS LinIf p. 137

There are two paths for wakeup (SWS LinIf p. 51):

  • Bus wakeup: EcuM checks it via LinIf_CheckWakeup. LinIf calls Lin_CheckWakeup or LinTrcv_CheckWakeup depending on the source. The driver confirms via LinIf_WakeupConfirmation, and LinIf then sets the wakeup flag of the channel ([SWS_LinIf_00378], [SWS_LinIf_00715], SWS LinIf p. 112, SWS LinIf p. 98).
  • Internal wakeup: The user calls LinIf_Wakeup. If the channel is sleeping and the wakeup flag is not set, LinIf calls Lin_Wakeup. If the channel is awake, LinIf returns E_OK without calling the driver ([SWS_LinIf_00205], SWS LinIf p. 89). If the flag is set, Lin_WakeupInternal is likely used instead; this is indicated by the description of the return values (SWS LinIf p. 89).

In the slave, LinIf confirms the wakeup only with the first received header and the value TRUE. If LinIf_Wakeup returns E_NOT_OK, LinIf reports FALSE beforehand. If the first header does not occur, there is no confirmation, and the timeout expires in the LinSM ([SWS_LinIf_00761], [SWS_LinIf_00762], SWS LinIf p. 52, SWS LinSM p. 27).

Sequence diagram: A bus wakeup sets the wakeup flag; an internal wakeup in the slave is confirmed only with the first header. Sources: [SWS_LinIf_00378], [SWS_LinIf_00715], [SWS_LinIf_00205], [SWS_LinIf_00761], [SWS_LinIf_00762], SWS LinIf p. 94

Diagnostics via LIN TP and Node Configuration According to ISO 17987-3

LinTp implements the Diagnostic Transport Layer of ISO 17987, independently for each channel (SWS LinIf p. 61). Each channel has its own LinTp state machine:

  • LinTp_Init sets the state LINTP_INIT with the sub-state LINTP_CHANNEL_IDLE.
  • A detected TP message leads to LINTP_CHANNEL_BUSY.
  • LinTp_Shutdown closes all connections and leads back to LINTP_UNINIT.

Evidence: [SWS_LinIf_00350], [SWS_LinIf_00710], [SWS_LinIf_00322], [SWS_LinIf_00323], [SWS_LinIf_00355], SWS LinIf p. 102. LinTp_ChangeParameter is only an empty stub and always rejects ([SWS_LinIf_00501], SWS LinIf p. 103).

State diagram: For each channel, LinTp alternates between IDLE and BUSY; LinTp_Shutdown leads from each sub-state to LINTP_UNINIT. Sources: [SWS_LinIf_00322], [SWS_LinIf_00323], [SWS_LinIf_00710], [SWS_LinIf_00355], SWS LinIf p. 43

On master channels, LinTp can switch the schedule tables itself if LinTpScheduleChangeDiag is set. For this purpose, it calls BswM_LinTp_RequestMode with a value from LinTp_Mode ([SWS_LinIf_00629], [SWS_LinIf_00360], [SWS_LinIf_00707], SWS LinIf p. 62):

  • when transmitting a request to the diagnostic request schedule,
  • after a physical request to the diagnostic response schedule,
  • after the response to the application schedule,
  • after a functional request back to the previous schedule.

PduR_LinTpTxConfirmation follows only when the requested schedule switch is completed or has failed. If the associated schedule request is rejected, LinTp_Transmit returns E_NOT_OK ([SWS_LinIf_00351], [SWS_LinIf_00702], [SWS_LinIf_00878]).

Sequence diagram: For a diagnostic request in the master, LinTp triggers three schedule switches via BswM and LinSM. Sources: [SWS_LinIf_00360], [SWS_LinIf_00520], [SWS_LinIf_00702], [SWS_LinIf_00878], SWS LinIf p. 62, SWS LinIf p. 92

On slave channels, LinIf manages the node model: initial NAD, configured NAD, PIDs, and product identification ([SWS_LinIf_00767], [SWS_LinIf_00769], SWS LinIf p. 170). The Node Configuration Handler answers, among others, “Assign NAD” and “Assign Frame ID range”, in each case upon the next SRF header. “Assign NAD” and “Save Configuration” are optional ([SWS_LinIf_00779], [SWS_LinIf_00780], [SWS_LinIf_00781], [SWS_LinIf_00810], [SWS_LinIf_00811], [SWS_LinIf_00812], [SWS_LinIf_00813], SWS LinIf p. 59). The upper layer can read and set NAD and PIDs, for example with data from non-volatile memory. LinIf_GetConfiguredNAD/LinIf_SetConfiguredNAD and LinIf_GetPIDTable/LinIf_SetPIDTable serve this purpose. The PIDs of MRF and SRF cannot be changed in this process ([SWS_LinIf_00830], [SWS_LinIf_00834], [SWS_LinIf_00816], [SWS_LinIf_00823], [SWS_LinIf_00809], SWS LinIf p. 57).

Behavior in the event of an error

If development error detection is active, LinIf reports errors to the DET. These include, among others, LINIF_E_UNINIT, LINIF_E_NONEXISTENT_CHANNEL, LINIF_E_PARAM_POINTER, and LINIF_E_SCHEDULE_REQUEST_ERROR ([SWS_LinIf_00376]). Such errors occur, for example, with an invalid channel or an invalid pointer in the slave callbacks ([SWS_LinIf_00843], [SWS_LinIf_00844], [SWS_LinIf_00849], [SWS_LinIf_00853], [SWS_LinIf_00855]). LinIf recognizes LINIF_E_RESPONSE and LINIF_E_NC_NO_RESPONSE as runtime errors ([SWS_LinIf_00729], SWS LinIf p. 71).

In the slave, a fault reported by LinIf_LinErrorIndication is considered a lost response. LinIf then reports LINIF_E_RESPONSE, except in case of LIN_ERR_HEADER. It confirms an affected transmit frame with E_NOT_OK ([SWS_LinIf_91007], [SWS_LinIf_00735], [SWS_LinIf_00742], [SWS_LinIf_00743]). The same applies if a new header arrives while a receive indication is still expected ([SWS_LinIf_00846]).

Certain response errors set the response_error signal. LinIf maintains it autonomously via Com_SendSignal and clears it again after successful transmission. Any change in the signal can be reported by a callout ([SWS_LinIf_00736], [SWS_LinIf_00744], [SWS_LinIf_00763], [SWS_LinIf_00764], [SWS_LinIf_00747], [SWS_LinIf_00765], SWS LinIf p. 58).

In the node configuration, the following applies ([SWS_LinIf_00785], [SWS_LinIf_00786], [SWS_LinIf_00787], [SWS_LinIf_00788], [SWS_LinIf_00789], [SWS_LinIf_00790], [SWS_LinIf_00791], SWS LinIf p. 66):

  • An N_As timeout aborts a pending response.
  • A request with an unknown NAD is discarded.
  • Requests with a functional NAD (0x7E) or invalid PCI are ignored.
  • A new valid request replaces the pending response.
  • A corrupted MRF leaves a pending response intact.

In LinTp, N_As, N_Cs, and N_Cr timeouts terminate the transmission or reception; the PduR receives E_NOT_OK ([SWS_LinIf_00799], [SWS_LinIf_00801], [SWS_LinIf_00802], [SWS_LinIf_00804], [SWS_LinIf_00806], SWS LinIf p. 73, SWS LinIf p. 66). Reception also terminates with E_NOT_OK in the event of an incorrect sequence number, an FF or SF following a CF, and—depending on LinTpDropNotRequestedNad—a foreign NAD in the response ([SWS_LinIf_00081], [SWS_LinIf_00653], [SWS_LinIf_00655]).

In the event of buffer bottlenecks, LinIf reacts in a graded manner ([SWS_LinIf_00676], [SWS_LinIf_00677], [SWS_LinIf_00792], [SWS_LinIf_00879], [SWS_LinIf_00679], [SWS_LinIf_00680], [SWS_LinIf_00793], [SWS_LinIf_00795], SWS LinIf p. 65):

  • If the reception start fails, LinIf aborts without calling the PduR again.
  • If copying fails, LinIf in the master first switches back to the application schedule and then calls PduR_LinTpRxIndication with E_NOT_OK.
  • If the buffer is too small, LinIf suspends transmitting the SRF headers until sufficient space is available.

Newer document passages additionally describe extended production errors for LinTp timeouts. These were only added with R23-11 and are not normative for R20-11 (SWS LinIf p. 1).

Usage and Semantics

The synchronous function LinIf_Transmit ([SWS_LinIf_00201]) is used to request the transmission of a PDU. It is available via the header LinIf.h with the service ID 0x49. The call expects two input parameters:

  • TxPduId (type PduIdType): Identifier of the PDU to be transmitted.
  • PduInfoPtr (type const PduInfoType*): Pointer to the PDU information, consisting of the length, a pointer to the payload data, and a pointer to metadata.

The return value of type Std_ReturnType indicates whether the transmit request could be accepted ([SWS_LinIf_00201]):

  • E_OK: The transmit request was accepted.
  • E_NOT_OK: The transmit request was not accepted.

Concurrency and Limitations

With regard to concurrent invocation, LinIf_Transmit is reentrant for different PDU IDs. However, for identical TxPduId values, the function is non-reentrant ([SWS_LinIf_00201]).

Interaction and Boundary Conditions

Going beyond the standard assumption, [SWS_LinIf_00700] requires that LinIf_Transmit must also return E_OK if the respective PDU belongs to a non-sporadic frame (on a LIN master node) or a non-event-triggered frame (on a LIN slave node) and the LIN Interface is initialized.

With the function LinIf_ScheduleRequest, a caller requests the execution of a specific schedule table for a LIN channel [SWS_LinIf_00202]. The interface is available via the header LinIf.h and is intended exclusively for LIN master nodes [SWS_LinIf_00202].
