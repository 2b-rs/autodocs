Role: Collection point between log sources and PDU Router

The Dlt module accepts log and trace messages from software components and BSW modules and forwards them as Dlt messages to an external client. The central interfaces for this are Dlt_SendLogMessage and Dlt_SendTraceMessage [SWS_Dlt_00241] [SWS_Dlt_00243]. At the beginning of the data path is an SW-C or a BSW module, at the end the PDU Router SWS Dlt p. 26. Transmission takes place exclusively via PduR_DltTransmit [SWS_Dlt_00762]. The message format, commands, and protocol to the tool are specified by the Log and Trace protocol specification SWS Dlt p. 9.

SW-Cs reach the module via two RTE ports:

  • SwcMessageService_{SW-C} for registering and sending [SWS_Dlt_91001],
  • ControlService_{SW-C} for controlling log settings [SWS_Dlt_00499].

In the opposite direction, Dlt notifies the SW-C via SessionControlCallback_{SW-C} [SWS_Dlt_00779] and invokes injections via InjectCallback_{SW-C} [SWS_Dlt_00778]. Further sources are the DET via Dlt_DetForwardErrorTrace [SWS_Dlt_00430] and the RTE via generated VFB trace hooks [SWS_Dlt_00027]. Of the underlying modules, Dlt uses Det_ReportError as well as services of Gpt, NvM, and StbM [SWS_Dlt_00763].

Startup: Buffering before Dlt_Init, configuration from NvM, start-up delay

Dlt_Init is synchronous and non-reentrant. Because Dlt uses the NVRAM Manager, initialization shall take place very late in the startup and only after the NvM [SWS_Dlt_00239]. According to the sequence diagram, the EcuM invokes the function SWS Dlt p. 159. Sources can log even before initialization. Dlt must therefore also be able to buffer data from Dlt_SendLogMessage and Dlt_SendTraceMessage before Dlt_Init [SWS_Dlt_00003].

If DltGeneralNvRAMSupport is TRUE, the following applies:

  • Dlt_Init reads the persistently stored values using NvM_ReadBlock [SWS_Dlt_00453].
  • Dlt checks the validity of the blocks [SWS_Dlt_00449].
  • The stored configuration serves as the initial value [SWS_Dlt_00350].

If NvRAM support is disabled, the static configuration applies SWS Dlt p. 26. The buffered data is only processed regularly once the module is initialized and the optional DltGeneralStartUpDelayTimer has expired [SWS_Dlt_00005].

Sequence diagram: Data buffered before Dlt_Init is only processed after initialization and expiry of the start-up delay. Sources: [SWS_Dlt_00003] [SWS_Dlt_00453] [SWS_Dlt_00005] SWS Dlt p. 90

Sessions, Application/Context IDs, and Context Registration

Each message source is identified via a Dlt_SessionIDType (uint32) [SWS_Dlt_00225]:

  • For SW-Cs, this is a Port Defined Argument Value [SWS_Dlt_00022]. The values start at 0x1000 [SWS_Dlt_00023].
  • BSW modules use their module ID [SWS_Dlt_00023].
  • Each port connected to Dlt receives a unique SessionId; the value range is contiguous [SWS_Dlt_00332].

Multi-instantiated SW-Cs and SW-Cs with multiple ports to Dlt have correspondingly multiple sessions EXP LSA p. 159. In terms of content, a message is assigned via ApplicationId and ContextId. Both are four bytes in size; 0x00000000 is the wildcard value [SWS_Dlt_00226] [SWS_Dlt_00227].

Using Dlt_RegisterContext, a source registers a tuple of ApplicationId and ContextId along with descriptions [SWS_Dlt_00245]. Dlt remembers through which port the tuple was registered [SWS_Dlt_00021] and maintains a log level and a trace status for each tuple SWS Dlt p. 20. When a software module is stopped, it invokes Dlt_UnregisterContext [SWS_Dlt_00769]. Dlt then deletes the tuple and no longer notifies it of changes. If DltGeneralRegisterContextNotification is active, Dlt additionally reports the unregistration via Dlt_GetLogInfo with status 5 SWS Dlt p. 21.

State diagram: Lifecycle of an ApplicationId/ContextId tuple with the return values of the registration APIs. Sources: [SWS_Dlt_00245] [SWS_Dlt_00769] SWS Dlt p. 49 SWS Dlt p. 50

From Send Call to PDU: Filters, LogChannels, and Decoupled Transmission

The send APIs are synchronous and reentrant [SWS_Dlt_00241] [SWS_Dlt_00243]. In addition to the payload data, they receive an info structure:

  • Dlt_MessageLogInfoType with argCount, logLevel, options, contextId, and appId [SWS_Dlt_00236],
  • Dlt_MessageTraceInfoType, which contains a trace type instead of the log level [SWS_Dlt_00237].

Still in the caller's context, the message sequentially passes through timestamp, log level/trace status filter, channel selection, length check, channel threshold, and buffering SWS Dlt p. 23 SWS Dlt p. 92.

For channel selection, Dlt collects in this order SWS Dlt p. 32:

  1. all LogChannels with an exactly matching tuple,
  2. all LogChannels with a matching ApplicationId and wildcard ContextId,
  3. the default LogChannel if the list is still empty afterwards.

The assignments can be changed at runtime using Dlt_SetLogChannelAssignment [SWS_Dlt_00751]. In R20-11, Dlt_AssignmentOperation encodes DLT_ASSIGN_ADD as 0x01 and DLT_ASSIGN_REMOVE as 0x02 [SWS_Dlt_00730]. Later versions assign the value 0x00 to DLT_ASSIGN_REMOVE instead SWS Dlt p. 87. A message is only discarded with DLT_E_MSG_TOO_LARGE if it is too long for all assigned channels SWS Dlt p. 31.

Activity diagram: Processing steps in the caller context and the points at which a message is discarded. Sources: SWS Dlt p. 23 SWS Dlt p. 32 SWS Dlt p. 31 SWS Dlt p. 32

The actual transmission is decoupled from the API call and occurs in the context of Dlt_TxFunction [SWS_Dlt_91005]. The decoupling keeps the callers' blocking time short and enables traffic shaping and retransmissions. The header is assembled before PduR_DltTransmit, and each transmission attempt increments a transmission counter of the message SWS Dlt p. 35. Dlt retrieves a timestamp only when DltHeaderUseTimestamp = TRUE, specifically via Gpt_GetTimeElapsed [SWS_Dlt_00654] or StbM_GetCurrentTime [SWS_Dlt_00655].

A message is removed from the channel buffer when one of the following cases occurs SWS Dlt p. 38:

  • PduR_DltTransmit returns E_NOT_OK.
  • A positive Dlt_TxConfirmation arrives [SWS_Dlt_00273].
  • After a negative acknowledgment, the configured number of retries is exceeded.

For TP-based channels, Dlt_CopyTxData [SWS_Dlt_00516] and Dlt_TpTxConfirmation [SWS_Dlt_00756] likely supplement this process. Dlt_TriggerTransmit [SWS_Dlt_00754] presumably serves trigger-controlled PDUs.

Sequence diagram: Acceptance of the message in the caller context, followed by cyclic, decoupled transmission with retry. Sources: SWS Dlt p. 92 SWS Dlt p. 35 SWS Dlt p. 38 [SWS_Dlt_00273]

Message Types, Header Fields, and Fixed Sources (DET, DEM, VFB Trace)

Dlt_MessageType distinguishes log, application trace, network trace, and control messages [SWS_Dlt_00224]. In the Extended Header, Dlt sets the MSTP field to 0x0 for Dlt_SendLogMessage and to 0x1 for Dlt_SendTraceMessage. The MTIN field results from the passed info structure SWS Dlt p. 35, that is, from one of these types PRS LT p. 24:

  • Dlt_MessageLogLevelType [SWS_Dlt_00230],
  • Dlt_MessageTraceType [SWS_Dlt_00231],
  • Dlt_MessageNetworkTraceInfoType for network trace [SWS_Dlt_00233].

Bit 0 of Dlt_MessageOptionsType indicates verbose mode [SWS_Dlt_00229]. In non-verbose mode, a 4-byte message ID carries the static meaning of the message [SWS_Dlt_00228]. The payload then contains only the message ID and the non-static data PRS LT p. 23.

For DET errors, Dlt provides Dlt_DetForwardErrorTrace in R20-11 [SWS_Dlt_00432]. These messages carry the ApplicationId "DET" and the ContextId "STD" [SWS_Dlt_00376]. With R25-11, the function was removed SWS Dlt p. 1. DEM events use "DEM"/"STD0" and the message ID 0x00000001 [SWS_Dlt_00377]. The message IDs 0x00000001 to 0x00000003 are reserved for DEM, DET, and trace messages [SWS_Dlt_00031].

For the VFB trace, Dlt provides a hook function for each configured RTE event. Its prototype originates from the BswModuleEntry of the RTE [SWS_Dlt_00027] [SWS_Dlt_00335]. Sequence in each hook:

  1. The hook checks the trace status of its ContextId [SWS_Dlt_00281].
  2. It invokes an internal equivalent of Dlt_SendTraceMessage [SWS_Dlt_00285], specifically in non-verbose mode [SWS_Dlt_00277].
  3. The payload contains all hook arguments [SWS_Dlt_00278].

Each hook has its own ContextId [SWS_Dlt_00279]. DLT_TYPE_APP_TRACE and DLT_TRACE_VFB are set [SWS_Dlt_00484]; the ApplicationId is "VFBT" SWS Dlt p. 23.

Sequence diagram: A VFB trace hook only sends if the trace status of its ContextId is active. Sources: [SWS_Dlt_00281] [SWS_Dlt_00285] [SWS_Dlt_00277] [SWS_Dlt_00484] SWS Dlt p. 23

Runtime Control by the External Client and Persistence

Dlt receives control messages via the configured DltRxPdu entries SWS Dlt p. 128. There are two paths for this:

  • Dlt_RxIndication [SWS_Dlt_00272],
  • the TP callbacks Dlt_StartOfReception [SWS_Dlt_91006], Dlt_CopyRxData [SWS_Dlt_91008], and Dlt_TpRxIndication [SWS_Dlt_91007].

A SetLogLevel command updates the filter, notifies the registered SW-C with LogLevelChangedNotification if required, and is answered via PduR_DltTransmit SWS Dlt p. 93. The notification runs via LogTraceSessionControl [SWS_Dlt_00496].

Behavior in the event of an error

The send APIs report problems via their return values [SWS_Dlt_00495] [SWS_Dlt_00241]:

  • DLT_E_UNKNOWN_SESSION_ID: The session is unknown.
  • DLT_E_MSG_TOO_LARGE: The message is too long for all assigned channels.
  • DLT_E_NO_BUFFER: Buffer space is lacking.

If the buffer is full, the message is discarded, an overflow flag is set for the channel buffer, and depending on the configuration, the control message "BufferOverflowNotification" is sent SWS Dlt p. 32 SWS Dlt p. 95. Besides Dlt_GetLogInfo, this is the only command that Dlt sends autonomously SWS Dlt p. 44. Dlt responds to errors during registration with DLT_E_CONTEXT_ALREADY_REG or DLT_E_CONTEXT_NOT_YET_REG [SWS_Dlt_00495].

R20-11 defines the following error codes:

  • Development errors: DLT_E_PARAM, DLT_E_PARAM_POINTER, DLT_E_INIT_FAILED, DLT_E_REGISTRATION [SWS_Dlt_00727].
  • Runtime errors: DLT_E_SKIPPED_TRANSMISSION, DLT_E_DEPRECATED_PARAMETER, DLT_E_MULTIPLE_REQUESTS [SWS_Dlt_00728].

Control commands for an unknown tuple are answered with DLT_E_ERROR SWS Dlt p. 39. The control service also knows DLT_E_NOT_SUPPORTED [SWS_Dlt_00772]. If the time source does not provide a value, the timestamp is set to 0x00000000 SWS Dlt p. 30. Failed transmissions are retried up to the configured maximum number SWS Dlt p. 38.

The synchronous and reentrant function Dlt_SendTraceMessage ([SWS_Dlt_00243]) serves basic software modules (BSW) as well as software components (SW-C) for transmitting trace parameters. It is available via the header file Dlt.h.

Parameters and Passing

  • sessionId: Module identifier (module ID within the BSW or port-defined argument value within an SW-C).
  • traceInfo: Pointer to a structure (Dlt_MessageTraceInfoType) with the information required for message filtering.
  • traceData: Pointer to the buffer with the parameters to be traced, which form the payload of the trace message.
  • traceDataLength: Length of the passed data buffer in bytes.

Return Values and Error Handling

The function returns a status of type Std_ReturnType:

  • E_OK: The operation was executed successfully.
  • DLT_E_MSG_TOO_LARGE: The message exceeds the allowed size of all assigned log channels.
  • DLT_E_NO_BUFFER: Insufficient buffer memory available; the message cannot be buffered for at least one log channel.
  • DLT_E_UNKNOWN_SESSION_ID: The passed sessionId is unknown to the DLT module.

Interaction and Buffering

The DLT module buffers data from calls to Dlt_SendTraceMessage even if the module has not yet been initialized ([SWS_Dlt_00003]). Because Dlt_SendTraceMessage is designed as an SW-C interface, an equivalent internal implementation ([SWS_Dlt_00285]) exists for generated hook functions, which is mandatorily called in non-verbose mode within the hook function ([SWS_Dlt_00277]).

The synchronous and reentrant function Dlt_SendLogMessage ([SWS_Dlt_00241]) serves basic software modules (BSW) as well as software components (SW-C) as a central interface for sending log messages. The declaration is provided via the header file Dlt.h ([SWS_Dlt_00241]).

Parameters

  • sessionId: Identifier of the session. For SW-Cs, this parameter is not visible in the interface call (Port-defined Argument Value), whereas for BSW modules it corresponds to the respective module number ([SWS_Dlt_00241]).
  • logInfo: Pointer to a structure of type Dlt_MessageLogInfoType, which contains the relevant information for filtering the log message ([SWS_Dlt_00241]).
  • logData: Pointer to the buffer with the parameters or payload of the log message to be sent ([SWS_Dlt_00241]).
  • logDataLength: Length of the passed data buffer logData ([SWS_Dlt_00241]).

Return Values and Error Handling

The service returns a status value of type Std_ReturnType ([SWS_Dlt_00241]):

  • DLT_OK: The requested operation was executed successfully.
  • DLT_E_MSG_TOO_LARGE: The message is too large for all assigned log channels.
  • DLT_E_NO_BUFFER: The log message could not be buffered on any of the assigned log channels.
  • DLT_E_UNKNOWN_SESSION_ID: The passed session ID is unknown to the DLT module.

Concurrency

Since the function is specified as reentrant ([SWS_Dlt_00241]), it can be called in parallel from different contexts, such as concurrent BSW modules or SW-C instances.

use

The function Dlt_UnregisterContext ([SWS_Dlt_00769]) is used to unregister a previously registered context and is to be called when a software module is terminated or stopped. The service is available via the header file Dlt.h.

The execution is synchronous. The function expects the following input parameters ([SWS_Dlt_00769]):

  • sessionId: Module number or session identifier (as BSW module ID within basic software or as a port-defined argument value within an SW-C).
  • appId: The application ID (Dlt_ApplicationIDType).
  • contextId: The context ID (Dlt_ContextIDType).

Return Values and Error Handling

The return value is of type Std_ReturnType and signals the result of the context unregistration ([SWS_Dlt_00769]):

  • E_OK: The requested operation was successful.
  • DLT_E_CONTEXT_NOT_YET_REG: The context of the software module was not previously registered.
