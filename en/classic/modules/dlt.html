Collects, filters, and buffers log and trace messages from SW-Cs and BSW and transmits them to external tools.

The Dlt module collects log and trace messages from SW-Cs, BSW modules, DET, and RTE VFB hooks. It filters them according to log level and trace status, assigns them to LogChannels, and buffers them. Transmission is decoupled via the cyclic Dlt_TxFunction and the PduR [SWS_Dlt_00241]. External clients can change filters and channel assignments at runtime; registered SW-Cs are notified of this. Most important constraint: Prior to Dlt_Init and until expiry of the optional startup delay, messages are only buffered [SWS_Dlt_00005].

The Dlt module is the central collection point for log and trace messages on the ECU. SW-Cs (via RTE ports) and BSW modules deliver messages via Dlt_SendLogMessage and Dlt_SendTraceMessage [SWS_Dlt_00241] [SWS_Dlt_00243]. DET errors are added via Dlt_DetForwardErrorTrace [SWS_Dlt_00430], SW-C communication via generated VFB trace hooks of the RTE [SWS_Dlt_00027]. The sole sink is the PduR with PduR_DltTransmit [SWS_Dlt_00762]. Each message is identified via a tuple of ApplicationId and ContextId with 4 bytes each; 0x00000000 serves as a wildcard [SWS_Dlt_00226] [SWS_Dlt_00227].

Context diagram: Sources, auxiliary services (NvM, Gpt/StbM, SchM), and the PduR as sink around Dlt. Sources: [SWS_Dlt_00762], [SWS_Dlt_00763], [SWS_Dlt_91005].

Even before initialization, Dlt buffers incoming messages [SWS_Dlt_00003]. They are not processed until Dlt_Init has run and the optional startup delay timer has expired [SWS_Dlt_00005]. With NvRAM support, Dlt_Init restores the runtime configuration via NvM_ReadBlock [SWS_Dlt_00453]. Saving occurs only upon explicit request via Dlt_StoreConfiguration [SWS_Dlt_00078].

In the call context, Dlt performs filtering, channel selection, length check, and buffer storage. Transmission is decoupled from the cyclic Dlt_TxFunction, including retries after negative acknowledgment SWS DLT p. 92 [SWS_Dlt_91005].

Sequence diagram: The synchronous send call ends with buffer storage. Dlt_TxFunction handles transmission, acknowledgment, and retry. Sources: SWS DLT p. 92, [SWS_Dlt_91005], [SWS_Dlt_00273].

External clients control log levels, trace status, and LogChannel thresholds via control messages that arrive via Dlt_RxIndication [SWS_Dlt_00272]. The same control parameters are also available as APIs, such as Dlt_SetLogLevel [SWS_Dlt_00252]. In order for Dlt to be able to inform registered SW-Cs via LogLevelChangedNotification, they previously register their contexts with Dlt_RegisterContext [SWS_Dlt_00245] [SWS_Dlt_00496].

In case of an error, the send calls report DLT_E_MSG_TOO_LARGE, DLT_E_NO_BUFFER, or DLT_E_UNKNOWN_SESSION_ID [SWS_Dlt_00495]. In the event of a buffer overflow, the message is discarded, an overflow flag is set, and a BufferOverflowNotification is sent according to configuration SWS DLT p. 32.

Role and System Boundary: Central Collection Point for Log and Trace Data

The Diagnostic Log and Trace (Dlt) module receives log and trace messages from software components (SW-Cs) and basic software (BSW). It filters and buffers them and forwards them as Dlt messages to an external tool. The two send interfaces Dlt_SendLogMessage and Dlt_SendTraceMessage are explicitly intended for both BSW modules and SW-Cs [SWS_Dlt_00241] [SWS_Dlt_00243]. The source of the data path is an SW-C or a BSW module, the sink is the PDU Router SWS DLT p. 26. For this, Dlt strictly requires PduR_DltTransmit [SWS_Dlt_00762]. Message format, commands, and protocol to the external client are not defined by the SWS, but by the protocol specification SWS DLT p. 9.

In addition to explicit calls, there are fixed suppliers:

  • DET: Error messages enter Dlt via the fan-out function Dlt_DetForwardErrorTrace [SWS_Dlt_00430] [SWS_Dlt_00432]. They carry the ApplicationID “DET” and the ContextId “STD” [SWS_Dlt_00376].
  • DEM: Log messages for DEM events use “DEM”, “STD0”, and the MessageID 0x00000001 [SWS_Dlt_00377].
  • RTE: It forwards SW-C communication implicitly as a VFB trace [SWS_Dlt_00276] [SWS_Dlt_00284].

Dlt obtains timestamps from Gpt or StbM, while persistence is handled by NvM [SWS_Dlt_00763]. Dlt_DetForwardErrorTrace belongs to the API in R20-11, but was removed in R25-11 SWS DLT p. 1.

Context diagram: Dlt is situated between the message sources (SW-C via RTE, BSW, DET) and the PduR as the sole sink. NvM, Gpt/StbM, and SchM are auxiliary services. Sources: [SWS_Dlt_00762], [SWS_Dlt_00763], [SWS_Dlt_00430], [SWS_Dlt_91005], SWS DLT p. 26.

From Startup to Operation: Pre-Initialization Buffering, Dlt_Init, and Persistence

SW-Cs and BSW modules can already log before Dlt is initialized. Therefore, Dlt must buffer data from Dlt_SendLogMessage and Dlt_SendTraceMessage even before initialization [SWS_Dlt_00003]. Regular processing of the buffered data only begins once two conditions are met: Dlt_Init has executed, and the optional timer DltGeneralStartUpDelayTimer has expired [SWS_Dlt_00005]. This timer is started when Dlt_Init is called, provided it is configured SWS DLT p. 25.

State diagram: Up to initialization and, if applicable, until the end of the startup delay, messages are only buffered, and only processed thereafter. Sources: [SWS_Dlt_00003], [SWS_Dlt_00005], SWS DLT p. 25.

Dlt_Init is synchronous and non-reentrant. The function expects a pointer to Dlt_ConfigType, whose content is implementation-specific [SWS_Dlt_00239] [SWS_Dlt_00437]. Because Dlt uses the NvM, initialization should take place late in startup and after the NvM [SWS_Dlt_00239]. If DltGeneralNvRAMSupport = TRUE, Dlt behaves as follows:

  • It reads the runtime values into Dlt_Init via NvM_ReadBlock [SWS_Dlt_00453].
  • It checks the validity of the blocks [SWS_Dlt_00449].
  • It uses the stored configuration as initial values [SWS_Dlt_00350].

Without NvRAM support, the static configuration applies SWS DLT p. 25. According to the diagram, the caller is the EcuM SWS DLT p. 159.

Sequence diagram: EcuM calls Dlt_Init synchronously. Dlt loads the configuration depending on DltGeneralNvRAMSupport from NvM or statically and optionally starts the startup delay timer. Sources: [SWS_Dlt_00239], [SWS_Dlt_00453], [SWS_Dlt_00005], SWS DLT p. 159, CP SWS DLT p. 90.

Message Model: Identifiers, Log Levels, and Trace Types

Each log message carries a structure Dlt_MessageLogInfoType with five fields: argCount, logLevel, options, contextId, and appId [SWS_Dlt_00236]. Trace messages use Dlt_MessageTraceInfoType, which contains a field traceInfo instead of the log level [SWS_Dlt_00237]. ApplicationId and ContextId are arrays of 4 bytes; 0x00000000 serves as a wildcard [SWS_Dlt_00226] [SWS_Dlt_00227]. The Application ID is the short name of the SW-C. The Context ID groups its messages by functionality EXP LSA p. 159. The bit field Dlt_MessageOptionsType encodes verbose mode in bit 0 and the message type in bits 1–3 [SWS_Dlt_00229].

In non-verbose mode, a unique Message ID identifies the static part of a message [SWS_Dlt_00228]. The IDs 0x00000001 (DEM), 0x00000002 (DET), and 0x00000003 (Trace) are reserved and cannot be used for SW-Cs [SWS_Dlt_00031]. On the wire, the Message ID directly follows the header, followed by the non-static data PRS DLT p. 23. The header field MTIN is formed from the log level or trace type depending on the message type MSTP PRS DLT p. 24.

Transmit Path: Filter, LogChannel Selection, Buffering, and Dlt_TxFunction

The send calls are synchronous and reentrant. They receive the sessionId, the info structure, and the payload including length [SWS_Dlt_00241] [SWS_Dlt_00243]. The R20-11 diagram shows the sequence in the call context:

  1. Message filtering
  2. Apply LogChannel threshold
  3. Select target LogChannels
  4. Check length
  5. Store message in LogChannel buffer

Transmission is handled only later by Dlt_TxFunction SWS DLT p. 92. The following individual steps are detailed in document passages of the R23-11 version and match this diagram. Dlt fetches a timestamp only if configured: via Gpt_GetTimeElapsed or via StbM_GetCurrentTime [SWS_Dlt_00654] [SWS_Dlt_00655].

The LogChannels are determined in three stages SWS DLT p. 32:

  1. Channels whose assignment exactly matches the ApplicationId/ContextId tuple.
  2. Channels with a matching ApplicationId and wildcard ContextId.
  3. If the list remains empty, the default LogChannel.

Assignments can be changed at runtime using Dlt_SetLogChannelAssignment [SWS_Dlt_00751]. A message is discarded only when it exceeds DltLogChannelMaxMessageLength for all assigned channels SWS DLT p. 31. Otherwise, it is copied into the buffers of all channels for which it is short enough SWS DLT p. 32.

Activity diagram: A message passes through filters, three-stage channel selection, length check, and buffer storage. Each branch can lead to discarding with its own return value. Sources: SWS DLT p. 31, SWS DLT p. 32, [SWS_Dlt_00495], [SWS_Dlt_00751].

Transmission via the PduR is decoupled from the send call and runs in the context of Dlt_TxFunction [SWS_Dlt_91005]. The header is assembled prior to PduR_DltTransmit, and a transmission counter counts with each message SWS DLT p. 35. A message is removed from the buffer in three cases SWS DLT p. 38:

  • PduR_DltTransmit returns E_NOT_OK.
  • A positive transmit confirmation arrives.
  • A negative confirmation arrives and DltLogChannelMaxNumOfRetries is exceeded.

The lower layer reports via the following callbacks:

  • Dlt_TxConfirmation [SWS_Dlt_00273]
  • Dlt_TriggerTransmit [SWS_Dlt_00754]
  • on the TP path Dlt_CopyTxData and Dlt_TpTxConfirmation [SWS_Dlt_00516] [SWS_Dlt_00756]

Sequence diagram: The synchronous send call ends with buffer storage. The actual transmission, confirmations, and retries are handled by the cyclic Dlt_TxFunction. Sources: SWS DLT p. 92, [SWS_Dlt_91005], [SWS_Dlt_00273], SWS DLT p. 35, SWS DLT p. 38.

VFB Trace via Generated RTE Hook Functions

VFB trace means: The RTE implicitly forwards SW-C communication to Dlt without the SW-C itself making a call SWS DLT p. 23. For this purpose, Dlt implements hook functions for each configured event described by a BswModuleEntry with the short name “Rte_Dlt…” [SWS_Dlt_00027]. The prototype is provided by the RTE description [SWS_Dlt_00335]. Dlt_SendTraceMessage is an SW-C interface. Therefore, the hooks call an equivalent internal function [SWS_Dlt_00285], specifically in non-verbose mode [SWS_Dlt_00277] and with all arguments as payload [SWS_Dlt_00278].

Additional rules apply to the hooks:

  • Each hook function receives its own ContextId. With very large numbers of signals, events may be bundled [SWS_Dlt_00279].
  • Prior to transmission, each hook checks the trace status of its ContextId [SWS_Dlt_00281].
  • The message carries DLT_TYPE_APP_TRACE with DLT_TRACE_VFB [SWS_Dlt_00484] and the ApplicationID “VFBT” SWS DLT p. 23.
  • The trace status of the hooks is changed via a dedicated function harmonized with LogTraceSessionControl [SWS_Dlt_00283].

Interpretation: Because the internal function corresponds to Dlt_SendTraceMessage, VFB messages are likely to traverse the same buffered transmit path as explicit trace messages [SWS_Dlt_00285].

Sequence diagram: An RTE hook sends a non-verbose trace message with DLT_TRACE_VFB only when the trace status is active. That it uses the shared transmit path is an interpretation. Sources: [SWS_Dlt_00027], [SWS_Dlt_00281], [SWS_Dlt_00285], [SWS_Dlt_00484], SWS DLT p. 33.

Sessions, Registration, and Runtime Control by External Clients

SW-Cs connect per configuration entry via the following ports:

  • SwcMessageService_{SW-C} for registration and sending [SWS_Dlt_91001]
  • ControlService_{SW-C} for control [SWS_Dlt_00499]
  • the callback ports SessionControlCallback_{SW-C} and InjectCallback_{SW-C} [SWS_Dlt_00779] [SWS_Dlt_00778]

Port-defined argument values serve as SessionIds [SWS_Dlt_00022]. They start at 0x1000; BSW modules use their module ID [SWS_Dlt_00023]. They are unique and consecutive per port [SWS_Dlt_00332]. Their type is Dlt_SessionIDType (uint32) [SWS_Dlt_00225]. If an SW-C is instantiated multiple times, each instance receives its own session EXP LSA p. 159.

Using Dlt_RegisterContext, a module registers its ApplicationId/ContextId tuple along with descriptions [SWS_Dlt_00245]. Dlt remembers through which port the tuple was registered [SWS_Dlt_00021]. Upon stopping, the module calls Dlt_UnregisterContext [SWS_Dlt_00769]. The registration fulfills one purpose: Dlt thereby knows which SW-C it must notify in the event of changed log levels or trace status SWS DLT p. 20. LogLevelChangedNotification and TraceStatusChangedNotification serve this purpose [SWS_Dlt_00496].

Control messages from an external client reach Dlt via the PduR. For single PDUs, they arrive via Dlt_RxIndication [SWS_Dlt_00272]. Via TP, they arrive via Dlt_StartOfReception, Dlt_CopyRxData, and Dlt_TpRxIndication [SWS_Dlt_91006] [SWS_Dlt_91008] [SWS_Dlt_91007]. Dlt then updates the filter, optionally notifies the registered SW-C, and sends the response via PduR_DltTransmit SWS DLT p. 93.

Sequence diagram: SW-Cs register their contexts. An external SetLogLevel command updates the filter, optionally triggers a notification, and is answered via PduR. Sources: SWS DLT p. 93, [SWS_Dlt_00245], [SWS_Dlt_00272], [SWS_Dlt_00496].

  • In R20-11, Dlt_AssignmentOperation encodes DLT_ASSIGN_ADD = 0x01 and DLT_ASSIGN_REMOVE = 0x02 [SWS_Dlt_00730]. R25-11 uses the value 0x00 for REMOVE SWS DLT p. 87. For R20-11, the requirement applies.

Behavior in the event of an error

The error codes of the SW-C interface are specified in interface DltSwcMessageService [SWS_Dlt_00495]. In addition, the document locations describe the behavior on the transmit path.

  • Message too long: Return DLT_E_MSG_TOO_LARGE if the message is too long for all assigned LogChannels [SWS_Dlt_00495] SWS DLT p. 31.
  • Buffer overflow: Return DLT_E_NO_BUFFER. The message is discarded, an overflow flag is set, and a BufferOverflowNotification is sent according to the configuration. Dlt_TxFunction checks the flag and debounce time SWS DLT p. 32 SWS DLT p. 95.
  • Unknown session or registration error: DLT_E_UNKNOWN_SESSION_ID, DLT_E_CONTEXT_ALREADY_REG, and DLT_E_CONTEXT_NOT_YET_REG [SWS_Dlt_00495] [SWS_Dlt_00769].
  • Timestamp not available: The timestamp is set to 0x00000000 SWS DLT p. 30.
  • Transmission error: A negative Dlt_TxConfirmation triggers retries until DltLogChannelMaxNumOfRetries is reached. If PduR_DltTransmit returns E_NOT_OK, the message is removed [SWS_Dlt_00273] SWS DLT p. 38.
  • Control commands: An unknown tuple for SetLogLevel is responded to with DLT_E_ERROR SWS DLT p. 39. The configuration APIs report E_NOT_OK [SWS_Dlt_00252].
  • Persistency: In R20-11, Dlt_StoreConfiguration provides the return values E_OK, E_NOT_OK, and DLT_E_NOT_SUPPORTED [SWS_Dlt_00736]. DLT_E_ERROR was not added until R24-11 SWS DLT p. 1.
  • Development and runtime errors:
    • Development errors: DLT_E_PARAM, DLT_E_PARAM_POINTER, DLT_E_INIT_FAILED, DLT_E_REGISTRATION [SWS_Dlt_00727]
    • Runtime errors: DLT_E_SKIPPED_TRANSMISSION, DLT_E_DEPRECATED_PARAMETER, DLT_E_MULTIPLE_REQUESTS [SWS_Dlt_00728]

  • Initialization order: The DLT module uses the NVRam Manager and must be initialized very late in the startup phase of the ECU [SWS_Dlt_00239]. Calling the function Dlt_Init must strictly take place only after full initialization of the NVRam Manager [SWS_Dlt_00239].

Since the function is specified as non-reentrant, the calling context must ensure that Dlt_Init is not re-entered concurrently or in an interrupting manner during execution [SWS_Dlt_00239].
