Connects software components with each other as well as with Basic Software and coordinates their execution.

The Runtime Environment (RTE) connects AUTOSAR software components with each other as well as with the Basic Software modules and governs deterministic scheduling on the Classic Platform via the Basic Software Scheduler (SchM) (SWS_RTE p. 100). The lifecycle is coordinated via standardized interfaces from SchM_Init and Rte_Start through to Rte_Stop and SchM_Deinit [SWS_Rte_08060], [SWS_Rte_03015]. In addition to sender-receiver and client-server patterns, software pointer mechanisms for calibration parameters as well as memory protection checks at partition boundaries ensure robust real-time operation [SWS_Rte_03914], [SWS_Rte_02752].

The Runtime Environment (RTE) decouples AUTOSAR software components from the ECU hardware and, together with the Basic Software Scheduler (SchM), coordinates the execution of all application and basic software processes (SWS_RTE p. 100). Controlled startup takes place in stages via the EcuStateManager: First, SchM_Init initializes the scheduler structures, followed by SchM_Start prior to calling BswM_Init, as well as SchM_StartTiming to enable periodic BSW events [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548]. The application SWCs are subsequently started via Rte_Start and, during shutdown, stopped by Rte_Stop prior to deinitialization via SchM_Deinit [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551].

Sequence diagram: Timing coordination of startup and shutdown between EcuM, SchM, and RTE. Sources: [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

Communication covers sender-receiver and client-server patterns both intra- and inter-ECU (SWS_RTE p. 286). Unbuffered data elements ensure consistent initial values via initValue, while buffered events are processed via FIFO queues [SWS_Rte_06009], [SWS_Rte_02521]. In client-server interactions, two-part transaction handles link asynchronous requests to the associated responses [SWS_Rte_02649]. Mode switches via Rte_Switch execute a deterministic ten-step sequence, with Distributed Shared Mode Queues guaranteeing the strict processing order of multiple mode machines [SWS_Rte_02631], [SWS_Rte_02665], [SWS_Rte_91102].

Context diagram: Addressing and indirection structures of the Single Pointered and Double Pointered calibration methods. Sources: [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

For online calibration, the RTE generates pointer structures according to the Single Pointered or Double Pointered principle, allowing parameter groups to be modified in RAM without hardware emulation [SWS_Rte_03913], [SWS_Rte_03914]. Erroneous out-of-bounds violations or timeouts are reported to the calling component via Std_ReturnType, while memory protection checks at partition boundaries prevent unauthorized manipulations [SWS_Rte_01034], [SWS_Rte_03845], [SWS_Rte_02752].

Role and System Boundaries of the RTE in the Classic Platform

The Runtime Environment (RTE) forms the functional backbone of the AUTOSAR Classic architecture by completely decoupling software components (SWCs) from the underlying computing hardware as well as from the hardware-related Basic Software modules (BSW) (SWS_RTE p. 100). For each ECU, the RTE generator produces a tailored interface that resolves all communication relationships—both locally on a microcontroller (intra-ECU) and network-wide across communication buses (inter-ECU)—via standardized API calls such as Rte_Read, Rte_Write, or Rte_Call [SWS_Rte_01091], [SWS_Rte_01102]. By providing a generated BswModuleDescription element and associated BswInternalBehavior descriptions, the RTE integrates as an integral component into the configuration and packaging scheme of AUTOSAR [SWS_Rte_05165], [SWS_Rte_05166].

Multiple instantiations of the same software component are handled by the RTE exclusively via code-sharing reentrant runnable entities; code duplication is explicitly not supported [SWS_Rte_03015], [SWS_Rte_02002]. In C code, a unique instance identifier is passed for each instance or addressed via the Component Data Structure (CDS), thereby ensuring parallel instance executions in shared task contexts without mutual data corruption (SWS_RTE p. 126, SWS_RTE p. 804). In addition to application SWCs, the RTE covers the cyclic scheduling and mode management of all BSW modules via the Basic Software Scheduler (SchM) [SWS_Rte_08060], [SWS_Rte_07273].

Lifecycle and Startup Coordination of SchM and RTE

System startup requires a strictly regulated sequence between the BSW Scheduler (SchM) and the application-oriented RTE (SWS_RTE p. 459). Before the SchM is initialized, only the locking functions SchM_Enter and SchM_Exit are available due to system safety reasons. The EcuStateManager first calls the function SchM_Init, which initializes internal data structures and mode machines and starts BswSchedulableEntities with background events [SWS_Rte_08060], [SWS_Rte_07584]. Prior to calling BswM_Init, SchM_Start must be called [SWS_Rte_07273], [SWS_Rte_04548]. The activation of periodic BSW processes (BswTimingEvents) is then enabled via SchM_StartTiming [SWS_Rte_04548], [SWS_Rte_04551], [SWS_Rte_07574].

Sequence diagram: Timing coordination of startup and shutdown between EcuM, SchM, and RTE. Sources: [SWS_Rte_08060], [SWS_Rte_07273], [SWS_Rte_04548], [SWS_Rte_03015], [SWS_Rte_01262], [SWS_Rte_04551], [SWS_Rte_89019].

Only when the required basic services are running does the EcuStateManager activate the execution of application SWCs with Rte_Start and initiate mode transitions for unbundled on-entry runnables [SWS_Rte_03015], [SWS_Rte_06766]. If resource allocation fails during Rte_Start, the function returns the error code RTE_E_LIMIT [SWS_Rte_01262]. During ECU shutdown, Rte_Stop first terminates application execution and ignores incoming requests and data from that point forward [SWS_Rte_02538], [SWS_Rte_02535], [SWS_Rte_02536]. Only after the complete termination of Rte_Stop may SchM_Deinit be called, which releases all system resources of the scheduler and initiates plug-in-specific cleanups via Rte_Rips_SchM_Deinit [SWS_Rte_04551], [SWS_Rte_07277], [SWS_Rte_89019].

Communication Patterns: Sender-Receiver and Client-Server

In the sender-receiver paradigm, the RTE fundamentally distinguishes between data semantics and event semantics (SWS_RTE p. 286). With data semantics (swImplPolicy != queued), the most recently written value is kept in the buffer and is consumed explicitly via Rte_Read or implicitly via Rte_IRead [SWS_Rte_01091], [SWS_Rte_06000]. With implicit reading, the RTE guarantees a consistent copy of the data value throughout the entire execution time of the runnable entity [SWS_Rte_06001]. Prior to the first reception, the RTE provides the configured initValue so that no uninitialized memory states are processed [SWS_Rte_06009], [SWS_Rte_06010].

Sequence diagram: Inter-ECU sender-receiver communication for unbuffered signals with initial value protection. Sources: [SWS_Rte_01091], [SWS_Rte_06009], [SWS_Rte_01289], AUTOSAR_SWS_RTE p. 148.

In contrast, event semantics (swImplPolicy = queued) processes data sequences losslessly via FIFO buffer structures that are filled using Rte_Send and decremented by Rte_Receive [SWS_Rte_01072], [SWS_Rte_01092], [SWS_Rte_02521]. If the buffer limit defined via RteQueuedReceiverQueueLength is reached, the RTE discards incoming new data and sets a corresponding error flag [SWS_Rte_08940], [SWS_Rte_02523]. For large data volumes, the RTE uses specialized transport paths such as LdCom or Large Data COM with signal buffer locking [SWS_Rte_01376], [SWS_Rte_01379].

Client-server communication supports synchronous calls (Rte_Call) as well as asynchronous interactions with separate result retrieval via Rte_Result [SWS_Rte_01102], [SWS_Rte_01111]. On the server side, the RTE buffers incoming requests in a FIFO queue unless a direct call is configured, whereas the response is temporarily stored in a buffer of length 1 on the client side [SWS_Rte_02527], [SWS_Rte_02528]. For cross-partition or cross-ECU calls, a two-part transaction handle consisting of a client identifier and sequence counter ensures the exact correlation of response packets to the original request [SWS_Rte_02649], [SWS_Rte_08711].

Mode Management, State Transitions, and Distributed Shared Mode Queues

Mode management enables the coordinated switching of operating states via dedicated mode machines (ModeMachineInstances) that are controlled via Rte_Switch [SWS_Rte_02631]. Each state transition undergoes a deterministic sequence of ten individual steps, which includes, among others, activating mode locks, controlled waiting for affected runnables to terminate, and the sequential execution of OnExit, OnTransition, and OnEntry entities [SWS_Rte_02665]. Only after all phases have fully completed is the acknowledgment event ModeSwitchedAckEvent triggered, the status of which can be queried via Rte_SwitchAck [SWS_Rte_02679], [SWS_Rte_02725], [SWS_Rte_02758].

Activity diagram: Deterministic ten-step sequence of a mode transition within a ModeMachineInstance. Sources: [SWS_Rte_02665], [SWS_Rte_02679], EXP_ModeManagementGuide p. 16.

To enforce a strict order of mode switches across multiple mode machines—for example, between ignition state and engine state—the RTE provides Distributed Shared Mode Queues (DSMQ) (SWS_RTE p. 442). The status of enqueue and dequeue operations in such queues is signaled via the type Rte_DsmqStatusType [SWS_Rte_91102]. For software cluster transitions, Rte_Rips_SwitchNotificationStatusType maps the corresponding enqueue and dequeue states [SWS_Rte_91113]. Interpretation: In the BSW Scheduler, the configuration of synchronization points prior to Rte_Start is likely chosen to establish deterministic system states before enabling cyclic tasks [SWS_Rte_06767].

Calibration, Data Emulation, and Memory Topology

Calibration parameters are centrally placed in memory by the RTE, as only the RTE generator knows the overall allocation of all components and partitions on the ECU [SWS_Rte_03961]. To enable online calibration without specialized emulation hardware, the RTE supports software emulation methods such as the Single Pointered Method and the Double Pointered Method (SWS_RTE p. 236, SWS_RTE p. 237). In the Single Pointered Method, a pointer table (<RteParameterRefTab>) composed of void* entries exists in RAM, pointing to ParameterElementGroups [SWS_Rte_03913], [SWS_Rte_03947].

Context diagram: Addressing and indirection structures of the Single Pointered and Double Pointered calibration methods. Sources: [SWS_Rte_03913], [SWS_Rte_03914], [SWS_Rte_03947], AUTOSAR_SWS_RTE p. 180, AUTOSAR_SWS_RTE p. 181.

The Double Pointered Method, by contrast, uses two-stage indirection: A reference table stored in ROM/flash points to parameter groups, while a modifiable base pointer (Base reference) in RAM initially points to this flash table and can be redirected to a modified RAM copy during calibration [SWS_Rte_03914]. In this process, ParameterDataPrototypes are separated into distinct groups based on their swAddrMethod [SWS_Rte_03908]. The RTE generator exports all structure and pointer information in container McSupportData via McSwEmulationMethodSupport to provide calibration tools (such as INCA or CANape) with precise access to A2L addressing [SWS_Rte_05118], [SWS_Rte_05137], [SWS_Rte_05138]. Interpretation: For highly integrated safety ECUs, the Double Pointered Method is likely to be preferred, since the pointer table itself primarily remains in protected flash and binds RAM buffers only during active calibration.

Partitioning, Memory Protection, and Inter-OS-Application Communication

In multi-core and memory-protected architectures, the RTE connects software components across partition boundaries (OS-Applications) using Inter-OS-Application Communication (IOC) (SWS_RTE p. 372). Here, the RTE replaces internal signal buffers with hardware-related IOC buffers and generated protection functions. To access exclusive areas (ExclusiveAreas), the integrator selects mechanism-specific configuration parameters (RteExclusiveAreaImplMechanism) ranging from interrupt locks to OS spinlocks for cross-core accesses (SWS_RTE p. 203).

If an untested or non-trusted partition passes pointer parameters to a trusted BSW or SWC partition, the RTE mandatorily performs address and memory area checks [SWS_Rte_02752], [SWS_Rte_02753]. The pointer is forwarded only if the entire referenced memory object belongs to the calling partition, effectively preventing protection area violations and unauthorized overwriting of external memory areas (SWS_RTE p. 378).

Behavior in the event of an error

RTE error handling strictly separates infrastructure errors from application errors (SWS_RTE p. 579). All error states are directly signaled to the caller via the return type Std_ReturnType [SWS_Rte_01034]. Immediate infrastructure errors include, among others, RTE_E_TIMEOUT (129), RTE_E_LIMIT (130), RTE_E_NO_DATA (131), RTE_E_UNCONNECTED (134), RTE_E_IN_EXCLUSIVE_AREA (135), and RTE_E_SEG_FAULT (136) (SWS_RTE p. 586).

Sequence diagram: Detection and propagation of range errors via Rte_Read. Sources: [SWS_Rte_01091], [SWS_Rte_01371], [SWS_Rte_03845], AUTOSAR_CP_SWS_RTE p. 409.

When data validation is enabled (DataSemantics range check), the RTE checks incoming signal values against defined ranges [SWS_Rte_01371]. If a received value is outside the boundaries, the read API returns RTE_E_OUT_OF_RANGE [SWS_Rte_03845], [SWS_Rte_03846]. For signals with an invalidation policy, the RTE replaces the value with the initValue upon replace or, upon keep, retains the previous value and sets an error event [SWS_Rte_05030], [SWS_Rte_05049]. During timeout monitoring via aliveTimeout, the RTE registers the absence via Rte_COMCbkRxTOut and propagates RTE_E_TIMEOUT to waiting SWCs [SWS_Rte_08061], [SWS_Rte_03763].

The API is always generated [SWS_Rte_01309], has the signature Std_ReturnType Rte_Start (void) [SWS_Rte_02569], and must unconditionally return within finite execution time without an infinite loop [SWS_Rte_02585].

Prior to the execution of Rte_Start, runtime APIs of the RTE must not be called, as this otherwise likewise leads to RTE_E_UNINIT [SWS_Rte_07682]; Rte_SetMirror, however, may already be called before Rte_Start [SWS_Rte_07319].

The function Rte_Stop ([SWS_Rte_02570]) is generated in every configuration ([SWS_Rte_01310]) and serves to finalize the RTE on the executing Core ([SWS_Rte_01262]). In doing so, all system and communication resources allocated by the RTE on this Core are released ([SWS_Rte_01262]). The synchronous call is guaranteed to return within a finite runtime ([SWS_Rte_02584]).

In the overall system, Rte_Stop must be called by the EcuStateManager before the Basic Software modules required by the RTE are shut down ([SWS_Rte_CONSTR_09038]). During the process, the RTE calls the stop functions Rte_Rips_Rte_Stop of all participating RTE implementation plug-ins ([SWS_Rte_80053]), which must provide these lifecycle interfaces ([SWS_Rte_70047]). Only after complete termination of Rte_Stop may SchM_Deinit be executed ([SWS_Rte_CONSTR_09056]).

After calling Rte_Stop on a Core, no further RunnableEntity instances are activated, started, or released there by the RTE ([SWS_Rte_02538]). Unaffected by this, Rte_GetMirror remains callable as long as the underlying operating system is active ([SWS_Rte_07350]).

In case of an error, the function returns RTE_E_LIMIT if an internal limit was exceeded or the allocation of a required resource fails ([SWS_Rte_01262]). If RteDevErrorDetectUninit is enabled, the RTE reports the error RTE_E_UNINIT (0x07) when illegal APIs are called after Rte_Stop ([SWS_Rte_07682]).

Usage and Semantics

The function SchM_Init allocates and initializes the system resources used by the Basic Software Scheduler (SchM) of the RTE on the calling Core ([SWS_Rte_08060]). The interface is always generated ([SWS_Rte_07271]) and has the signature void SchM_Init(const SchM_ConfigType* ConfigPtr) ([SWS_Rte_07270]). It is executed synchronously and must mandatory return within a finite execution time without entering an infinite loop ([SWS_Rte_07273]).

During the initialization sequence, SchM_Init performs the following steps:

  • It initiates the transition to the initial mode for every mode machine instance belonging to the Basic Software Scheduler ([SWS_Rte_07532]).
  • It starts the activation of BswSchedulableEntity instances triggered by BswBackgroundEvent events ([SWS_Rte_07584]).
  • It calls the initialization functions Rte_Rips_SchM_Init of all participating RTE Implementation Plug-Ins ([SWS_Rte_80051]).

Call Context and Ordering Requirements

SchM_Init may only be called exactly once on each Core by the EcuStateManager as soon as the BSW modules required by the Basic Software Scheduler have been initialized ([SWS_Rte_CONSTR_09055]). Subsequent APIs such as Rte_Start may only be called after complete termination of SchM_Init ([SWS_Rte_CONSTR_09036]).

Error handling

If SchM_Init is called with a NULL pointer as parameter, the Basic Software Scheduler reports the error RTE_E_DET_ILLEGAL_VARIANT_CRITERION_VALUE (0x02) ([SWS_Rte_07684]). If scheduler APIs (such as SchM_Switch, SchM_Mode, or SchM_Start) or Rte_Start are called before SchM_Init, the error RTE_E_UNINIT (0x07) is reported when RteDevErrorDetectUninit is activated ([SWS_Rte_07683]).

use

The function SchM_Start serves to start up the Basic Software Scheduler in the RTE module and is always provided as part of the interface generation [SWS_Rte_04547]. It has the parameterless C signature void SchM_Start(void) [SWS_Rte_04546] and returns no value. For execution, the binding requirement applies that the call must return within a finite runtime and must under no circumstances enter an infinite loop [SWS_Rte_04548]. In the absence of asynchronous callback mechanisms, it is likely to be a synchronously blocking initialization call.

Call Context and Concurrency

Strict restrictions apply to the call context and the interaction with other system components:

  • Caller and frequency: The function may be called on each processor core exclusively by the EcuStateManager and only exactly once there [SWS_Rte_CONSTR_09055].
  • Sequence conditions: The call may only take place after all Basic Software modules required by the Basic Software Scheduler part of the RTE have been completely initialized [SWS_Rte_CONSTR_09055].
  • Interaction during system startup: After execution, the Basic Software Scheduler is operational; the call must unconditionally take place before the initialization of the BSW Manager via BswM_Init() [SWS_Rte_07273].

Error handling

Specific error codes, return values, or notifications to the DET or DEM are not defined in the payload for this function.
