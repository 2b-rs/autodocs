Controls the LIN hardware and provides the LIN Interface with services for frames, sleep state, and wake-up per channel.

The LIN driver encapsulates the LIN hardware of the microcontroller and provides the LIN Interface with channel-specific services for frames, sleep state, and wake-up. Master channels trigger frames asynchronously with Lin_SendFrame and evaluate them via Lin_GetStatus. Slave channels respond to each received header with an indication to the LIN Interface and then transmit, receive, or ignore the response ([SWS_Lin_00280]). Which services are available depends on the configured node type; master services exist only if at least one master channel is present ([SWS_Lin_00287]).

The LIN driver Lin is the hardware driver of the LIN stack. It encapsulates LIN controllers or SCI/UARTs (SWS LIN Driver p. 9) and provides the LIN Interface with channel-specific services for frames, sleep state, and wake-up. It mandatorily requires Dem_SetEventStatus, EcuM_SetWakeupEvent, and LinIf_WakeupConfirmation ([SWS_Lin_00234]). Optionally, it uses DET, Icu, and the slave callbacks of LinIf ([SWS_Lin_00235]).

Context diagram: Lin is located between LinIf and the LIN hardware and reports wake-ups and errors to EcuM, LinIf, DEM, and DET. Sources: [SWS_Lin_00234], [SWS_Lin_00235]

Lin_Init transitions the module from LIN_UNINIT to LIN_INIT ([SWS_Lin_00006], SWS LIN Driver p. 24). After that, each channel alternates between LIN_CH_OPERATIONAL, LIN_CH_SLEEP_PENDING (master only), and LIN_CH_SLEEP. For this purpose, Lin_GoToSleep, Lin_GoToSleepInternal, Lin_Wakeup, and Lin_WakeupInternal are available ([SWS_Lin_00166], [SWS_Lin_00167], [SWS_Lin_00169], [SWS_Lin_00256]).

State diagram: Module states and channel states with their transitions. That Lin_GetStatus completes the step to LIN_CH_SLEEP is an interpretation of the diagram. Sources: SWS LIN Driver p. 24, [SWS_Lin_00166]

Master and slave channels operate fundamentally differently. A master triggers frames asynchronously with Lin_SendFrame and queries the result later with Lin_GetStatus ([SWS_Lin_00191], [SWS_Lin_00168]). These services exist only if at least one channel is configured as a master ([SWS_Lin_00287]). A slave reports each header via LinIf_HeaderIndication ([SWS_Lin_00280]). Depending on Drc, it then transmits, receives, or ignores the response and completes it with LinIf_TxConfirmation or LinIf_RxIndication ([SWS_Lin_00282], [SWS_Lin_00274], [SWS_Lin_00275]).

Lin_CheckWakeup checks wake-ups from the bus and reports them to EcuM and LinIf ([SWS_Lin_00160]). In the event of an error, misuses are sent to the DET, such as LIN_E_UNINIT ([SWS_Lin_00258]). A hardware timeout is reported to the DEM as LIN_E_TIMEOUT ([SWS_Lin_00290]). A master channel returns bus errors as status; a slave channel reports them via LinIf_LinErrorIndication ([SWS_Lin_00233], [SWS_Lin_00277]).

Role, System Boundary, and Instance Context of the LIN Driver

The LIN driver Lin encapsulates the LIN hardware of the microcontroller. It provides channel-specific services to the LIN Interface (LinIf): transmitting and receiving frames, putting channels to sleep and waking them up, as well as checking wake-ups. All services are available via Lin.h ([SWS_Lin_00191], [SWS_Lin_00160]). As hardware, the specification mentions three types of LIN hardware units: full-featured LIN controllers, simple SCI/UARTs, and enhanced SCI/UARTs. Each is connected to a LIN cluster via transceiver ICs (SWS LIN Driver p. 9). The driver itself does not provide any callback functions (SWS LIN Driver p. 49). Instead, it calls functions of its environment.

Mandatory external interfaces are Dem_SetEventStatus, EcuM_SetWakeupEvent, and LinIf_WakeupConfirmation ([SWS_Lin_00234]). Optionally, the driver uses, among others:

  • Det_ReportError and EcuM_CheckWakeup,
  • Icu_EnableNotification and Icu_DisableNotification,
  • for slave channels, the callbacks LinIf_HeaderIndication, LinIf_RxIndication, and LinIf_LinErrorIndication ([SWS_Lin_00235]).

The imported types such as NetworkHandleType, EcuM_WakeupSourceType, or Std_ReturnType are listed in [SWS_Lin_00226].

Context diagram: Lin is located between LinIf and the LIN hardware unit. The driver reports wake-ups to EcuM and LinIf, and errors to DEM and DET. Sources: [SWS_Lin_00234], [SWS_Lin_00235], SWS LIN Driver p. 9

The driver is partitionable. It operates as an independent instance in each partition, and an API call only affects the partition in which it is made ([SWS_Lin_CONSTR_00270]). If LinEcucPartitionRef references partitions, LinChannelEcucPartitionRef must reference exactly one of them ([SWS_Lin_CONSTR_00291]). LinChannel and LinTrcvChannel of a communication channel must reference the same partition ([SWS_Lin_CONSTR_00279]). The module rejects partition assignments that the implementation does not support ([SWS_Lin_00269]). Per channel, parameters such as baud rate, channel ID, LinChannelWakeupSupport, and the node type LinNodeType are configured. This container description originates from a later release (SWS LIN Driver p. 60).

Module and Channel States from Lin_Init to Sleep State

After reset, the module is in the LIN_UNINIT state and cannot be used. Lin_Init transitions it to LIN_INIT; there, every available channel is operational (SWS LIN Driver p. 24). Lin_Init receives a pointer to a Lin_ConfigType structure. Its content is hardware-specific; it contains the initialization data for the driver, hardware unit, and channels ([SWS_Lin_00006], [SWS_Lin_00227]). The environment should call Lin_Init only once at runtime (SWS LIN Driver p. 24).

Within LIN_INIT, each channel has its own state:

  • LIN_CH_OPERATIONAL: The channel participates in the cluster.
  • LIN_CH_SLEEP: Wake-up detection is active; the hardware is in low-power mode if applicable.
  • LIN_CH_SLEEP_PENDING: Only for master channels, after Lin_GoToSleep.

References: SWS LIN Driver p. 24, [SWS_Lin_00166]. Lin_GoToSleepInternal sets the channel directly to LIN_CH_SLEEP ([SWS_Lin_00167]). Lin_Wakeup leads back to LIN_CH_OPERATIONAL with a wake-up pulse, Lin_WakeupInternal without a pulse ([SWS_Lin_00169], [SWS_Lin_00256]).

Interpretation: Lin_GetStatus likely completes the transition from LIN_CH_SLEEP_PENDING to LIN_CH_SLEEP. The diagram shows Lin_GetStatus as a transition in the master section, and the LIN Interface expects the return value LIN_CH_SLEEP when checking the go-to-sleep command (SWS LIN Interface p. 56).

State diagram: Lin_Init transitions the module from LIN_UNINIT to LIN_INIT. Within it, each channel alternates between operation and sleep via sleep and wake-up services; the transition via Lin_GetStatus is an interpretation. Sources: SWS LIN Driver p. 24, [SWS_Lin_00166], [SWS_Lin_00167], [SWS_Lin_00169], [SWS_Lin_00256]

Frame Description via Lin_PduType and Data Mapping

Between LinIf and the driver, Lin_PduType describes a frame. The structure contains Pid, the checksum model Cs, the response direction Drc, the data length Dl, and the data pointer SduPtr ([SWS_Lin_00232]). The element types:

  • Lin_FramePidType: Identifier 0…0x3F with two parity bits, value range 0…0xFE ([SWS_Lin_00228]).
  • Lin_FrameDlType: 1…8 data bytes ([SWS_Lin_00231]).
  • Lin_FrameCsModelType: LIN_ENHANCED_CS or LIN_CLASSIC_CS ([SWS_Lin_00229]). The driver must be able to calculate both checksums ([SWS_Lin_00019]).

Lin_FrameResponseType specifies how the node handles the response ([SWS_Lin_00230]): It transmits it itself (LIN_FRAMERESPONSE_TX), receives a relevant external response (LIN_FRAMERESPONSE_RX), or ignores it (LIN_FRAMERESPONSE_IGNORE). In memory, the byte transmitted first resides in element 0, the byte transmitted last in element n-1 (SWS LIN Driver p. 30). If the hardware cannot buffer bytes, such as in a simple UART, the driver provides a temporary buffer. Transmitting with read-back check and receiving run non-blocking (SWS LIN Driver p. 28).

Master Channels: Lin_SendFrame and Status Polling

On master channels, LinIf triggers each frame with the asynchronous Lin_SendFrame. The service transmits the LIN header and, if applicable, the response ([SWS_Lin_00191]). This applies to receive, transmit, and slave-to-slave entries of the schedule (SWS LIN Interface p. 34, SWS LIN Interface p. 37, SWS LIN Interface p. 40).

LinIf queries the result with the synchronous Lin_GetStatus: at the earliest after the maximum frame length, at the latest at the next due schedule entry (SWS LIN Interface p. 35, [SWS_Lin_00168]). The service returns a Lin_StatusType, such as LIN_TX_OK, LIN_TX_BUSY, LIN_RX_OK, LIN_RX_BUSY, or LIN_RX_NO_RESPONSE. Via Lin_SduPtr, it additionally returns a pointer to the shadow or hardware receive buffer ([SWS_Lin_00233]).

Received data remains consistent until the next frame has been received successfully or the channel state changes. Complete receive processing may reside in Lin_GetStatus (SWS LIN Driver p. 30). For event-triggered frames, the following applies (SWS LIN Interface p. 127, SWS LIN Interface p. 129):

  • LIN_RX_NO_RESPONSE does not treat LinIf as an error.
  • LIN_RX_ERROR is considered a collision and causes a switch to the collision resolving schedule.

Lin_SendFrame, Lin_GoToSleep, and Lin_GetStatus exist only if at least one channel is configured as master via LinNodeType ([SWS_Lin_00287], [SWS_Lin_00288], [SWS_Lin_00289]). In R20-11, these services are specified as non-reentrant ([SWS_Lin_00168]). Later versions permit reentrancy for different channels (SWS LIN Driver p. 48); for R20-11, the requirement applies.

Sequence diagram: The master triggers a frame asynchronously with Lin_SendFrame and evaluates the result in later MainFunction calls via Lin_GetStatus. Sources: [SWS_Lin_00191], [SWS_Lin_00168], SWS LIN Interface p. 128, SWS LIN Interface p. 129, SWS LIN Interface p. 40

Slave Channels: Header-Driven Response Processing

A slave channel must be able to receive a header at any time in LIN_CH_OPERATIONAL ([SWS_Lin_00272]). For each header, the driver calls LinIf_HeaderIndication. In doing so, PduPtr->Pid contains the received PID, and PduPtr->SduPtr points to its hardware or shadow buffer ([SWS_Lin_00280]). If the hardware does not detect invalid PIDs, the driver passes the PID on unchecked ([SWS_Lin_00271]). After return of E_OK, it evaluates PduPtr->Drc ([SWS_Lin_00282]):

  • For LIN_FRAMERESPONSE_TX, it uses Cs, Dl, and SduPtr to transmit the response ([SWS_Lin_00283]).
  • For LIN_FRAMERESPONSE_RX, it configures reception using Cs and Dl ([SWS_Lin_00284]).

If LinIf_HeaderIndication returns E_NOT_OK or if Drc equals LIN_FRAMERESPONSE_IGNORE, the driver ignores the response ([SWS_Lin_00286]). It then reports nothing until the next header ([SWS_Lin_00276]). It forwards a successfully received response directly via LinIf_RxIndication and confirms a transmitted one via LinIf_TxConfirmation ([SWS_Lin_00274], [SWS_Lin_00275]). Every relevant response must be completed with one of these callbacks or with LinIf_LinErrorIndication before the next header is reported ([SWS_Lin_00285]). The reception diagram distinguishes two hardware variants: hardware LIN controller and simple UART, where the driver copies each byte into a buffer via interrupt (SWS LIN Driver p. 57).

Sequence diagram: On a slave channel, each header triggers an indication to LinIf. Depending on Drc, the driver transmits, receives, or ignores the response. Sleep, Wake-up, and Wake-up Detection

Only a master can transmit the go-to-sleep command. Lin_GoToSleep sends it asynchronously according to LIN 2.1 and sets the channel to LIN_CH_SLEEP_PENDING even in case of an erroneous transmission. If LinChannelWakeupSupport is configured, the service additionally activates bus monitoring ([SWS_Lin_00166], SWS LIN Driver p. 43). For slaves, Lin_GoToSleep is not applicable; they use Lin_GoToSleepInternal (SWS LIN Driver p. 31). This service synchronously sets LIN_CH_SLEEP, activates wake-up detection, and optionally puts the hardware into a power-saving mode ([SWS_Lin_00167], SWS LIN Driver p. 44). Each channel accepts sleep requests independently of the others (SWS LIN Driver p. 31).

Two services are available for wake-up. Lin_Wakeup transmits a wake-up pulse onto the bus, while Lin_WakeupInternal sets the channel to operational without a pulse ([SWS_Lin_00169], [SWS_Lin_00262]). Lin_CheckWakeup checks a wake-up from the bus. If the service detects an event, such as a permanently low RxD level, it immediately reports it via EcuM_SetWakeupEvent to the EcuM and via LinIf_WakeupConfirmation to LinIf ([SWS_Lin_00160], SWS LIN Driver p. 42). Based on the wake-up source, LinIf_CheckWakeup decides whether Lin_CheckWakeup or LinTrcv_CheckWakeup is called (SWS LIN Interface p. 112). LIN does not require wake-up validation (SWS EcuM p. 173).

Sequence diagram: A wake-up from the bus is passed to Lin_CheckWakeup via EcuM and LinIf_CheckWakeup. The driver reports a detected event to EcuM and LinIf. Sources: [SWS_Lin_00160], [SWS_Lin_00234], SWS LIN Driver p. 42, SWS LIN Interface p. 112, SWS EcuM p. 147

Behavior in the event of an error

When development error detection is enabled, the services report misuse to the DET ([SWS_Lin_00258], [SWS_Lin_00259], [SWS_Lin_00260]; for Lin_Wakeup analogously SWS LIN Driver p. 45):

  • LIN_E_UNINIT when called prior to initialization,
  • LIN_E_INVALID_CHANNEL for an invalid or inactive channel,
  • LIN_E_STATE_TRANSITION upon a wake-up outside of LIN_CH_SLEEP.

Lin_GetVersionInfo reports a NULL pointer with LIN_E_PARAM_POINTER ([SWS_Lin_00161], SWS LIN Driver p. 41). When the DET is disabled, Lin_CheckWakeup returns E_NOT_OK for an invalid channel (SWS LIN Driver p. 42). In general, E_NOT_OK and LIN_NOT_OK indicate that a development or production error has occurred ([SWS_Lin_00191], [SWS_Lin_00233]).

LIN_E_TIMEOUT is specified as a production error. If a state change must be waited for following a modification to hardware control registers, a configurable timeout safeguards this waiting. If it expires, the error is reported ([SWS_Lin_00290]). The notification is sent via Dem_SetEventStatus ([SWS_Lin_00234]) to the event referenced in LinDemEventParameterRefs (SWS LIN Driver p. 65).

The driver reports communication errors differently depending on the node type. Master channels return them as the status of Lin_GetStatus ([SWS_Lin_00233]):

  • LIN_TX_HEADER_ERROR upon readback, parity, or bus errors in the header,
  • LIN_TX_ERROR upon erroneous response transmission,
  • LIN_RX_ERROR upon framing, overrun, or checksum errors, as well as a response that is too short.

Slave channels abort frame processing and call LinIf_LinErrorIndication with a Lin_SlaveErrorType ([SWS_Lin_00277], [SWS_Lin_91140]). They report invalid bus events while waiting for a header as LIN_ERR_HEADER ([SWS_Lin_00281]).

Activity diagram: Development errors are sent to the DET, the hardware timeout to the DEM. A master channel reports bus communication errors as a status, a slave channel as an error indication. Sources: [SWS_Lin_00258], [SWS_Lin_00290], [SWS_Lin_00233], [SWS_Lin_00277], [SWS_Lin_00281], [SWS_Lin_00235]

The enumeration type Lin_StatusType is provided via Lin_GeneralTypes.h and defines the operational and transmission states for LIN channels and LIN frames that are reported as the return value of the API service Lin_GetStatus() [SWS_Lin_00233].

The state values are divided into channel states and frame operation values [SWS_Lin_00233]:

  • Channel status: LIN_OPERATIONAL represents normal operation, in which the LIN channel is ready to transmit the next header and no data of a previous frame is present (e.g. after initialization). In contrast, LIN_CH_SLEEP represents the sleep state of the channel, in which wake-up detection for slave nodes is enabled [SWS_Lin_00233].
  • Ongoing transmissions: LIN_TX_BUSY indicates an ongoing transmission of header or response. LIN_RX_BUSY signals an ongoing reception process in which at least one response byte, but not yet the final checksum byte, has arrived [SWS_Lin_00233].
  • Successful completion: LIN_TX_OK confirms the successful transmission, while LIN_RX_OK indicates the error-free reception of a complete response [SWS_Lin_00233].
  • Error states and timeouts: LIN_NOT_OK indicates development or production errors. For transmission operations, the type distinguishes between LIN_TX_HEADER_ERROR (error during header transmission due to data mismatch, identifier parity errors, or physical bus errors) and LIN_TX_ERROR (error during response transmission due to data mismatch or bus errors). On the reception side, LIN_RX_ERROR designates reception errors such as framing, overrun, checksum errors, or incomplete responses; LIN_RX_NO_RESPONSE reports the complete absence of response bytes [SWS_Lin_00233].
