Role of the LIN Driver Between LIN Interface and Controller Hardware

The LIN driver (Lin) encapsulates the ECU's LIN hardware unit, i.e., a dedicated LIN controller or a simple UART. It provides it to the LIN Interface (LinIf) as channel-specific services. The driver receives frame orders as Lin_PduType with the following specifications: PID, checksum model, response type, data length, and SDU pointer [SWS_Lin_00232]. In the feature model, LIN is an optional network technology with the sub-features LIN_Master and LIN_Slave FO Features p. 58. The driver serves both roles per channel. However, several services are available only to master channels [SWS_Lin_00287] [SWS_Lin_00288] [SWS_Lin_00289].

The driver uses three mandatory interfaces of other modules:

  • Dem_SetEventStatus for production errors.
  • EcuM_SetWakeupEvent and LinIf_WakeupConfirmation for detected wakeup events [SWS_Lin_00234].

Optionally, Det_ReportError, EcuM_CheckWakeup, and the Icu notification control are added [SWS_Lin_00235]. On slave channels, the driver reports headers, reception, transmit confirmation, and errors via LinIf callbacks [SWS_Lin_00280] [SWS_Lin_00274] [SWS_Lin_00275] [SWS_Lin_00277]. It does not provide callback functions of its own SWS LINDriver p. 49. Complete sequence diagrams are not located in the driver specification, but in the LinIf specification SWS LINDriver p. 52.

Context diagram: The driver is located between LinIf and hardware and reports wake-up events to EcuM as well as errors to DEM and DET. Sources: [SWS_Lin_00234] [SWS_Lin_00235] SWS LINDriver p. 50 SWS LINInterface p. 112

Module and Channel States from Reset to Operation

The driver operates with a two-stage state machine. After reset, the module is in LIN_UNINIT and cannot be used. Calling Lin_Init transitions it to LIN_INIT; there, every available channel is operational SWS LINDriver p. 24 SWS LINDriver Fig. 7.1 p. 24. Lin_Init is synchronous and non-reentrant. The service receives a pointer to a Lin_ConfigType. Its content is hardware-dependent and configures the driver, hardware unit, and channels [SWS_Lin_00006] [SWS_Lin_00227]. The environment shall call Lin_Init only once at runtime SWS LINDriver p. 24.

Within LIN_INIT, each channel has its own state SWS LINDriver p. 23:

  • LIN_CH_OPERATIONAL: The channel is initialized and participates in the LIN cluster SWS LINDriver p. 24.
  • LIN_CH_SLEEP: Wakeup pulse detection is active, and the hardware is possibly in low-power mode SWS LINDriver p. 24.
  • LIN_CH_SLEEP_PENDING: Master channels only. Intermediate state after Lin_GoToSleep that is completed only by Lin_GetStatus SWS LINDriver Fig. 7.1 p. 24.

Which channel state Lin_Init establishes is only touched upon in the payload. Presumably, each channel starts in LIN_CH_SLEEP; this is suggested by the description of the state diagram SWS LINDriver Fig. 7.1 p. 23. A channel returns to LIN_CH_OPERATIONAL via Lin_Wakeup or Lin_WakeupInternal [SWS_Lin_00169] [SWS_Lin_00256].

State diagram: Module states and channel states with the triggering services. LIN_CH_SLEEP_PENDING exists only for master channels. Sources: SWS LINDriver Fig. 7.1 p. 24 [SWS_Lin_00006] [SWS_Lin_00166] [SWS_Lin_00167] [SWS_Lin_00169] [SWS_Lin_00256]

Master Channels: Frame Request and Status Polling

On a master channel, LinIf triggers each schedule entry with Lin_SendFrame. The service is asynchronous and transmits a LIN header as well as, depending on the response type, the response [SWS_Lin_00191]. The fields of the Lin_PduType define the frame [SWS_Lin_00232]:

  • Pid (Lin_FramePidType, 0…0xFE): Identifier 0…0x3F including the two parity bits [SWS_Lin_00228].
  • Cs (Lin_FrameCsModelType): LIN_CLASSIC_CS or LIN_ENHANCED_CS. The driver calculates the appropriate checksum [SWS_Lin_00229] [SWS_Lin_00019].
  • Drc (Lin_FrameResponseType): The response comes from this node (LIN_FRAMERESPONSE_TX), from another relevant node (LIN_FRAMERESPONSE_RX), or is irrelevant (LIN_FRAMERESPONSE_IGNORE) [SWS_Lin_00230].
  • Dl (Lin_FrameDlType, 1…8): Number of data bytes to be copied [SWS_Lin_00231].

In memory, element 0 of the SDU array contains the byte transmitted first SWS LINDriver p. 30. If the hardware cannot buffer bytes, the driver provides a temporary buffer. Transmission and reception are non-blocking SWS LINDriver p. 28. The master transmits slave-to-slave frames using LIN_FRAMERESPONSE_IGNORE SWS LINDriver p. 37. LinIf supports this communication type, but does not recommend it SWS LINInterface p. 45.

Sequence diagram: A transmitted frame is triggered, transmitted, and confirmed via status polling over three cycles of the LinIf main function. In more recent releases, the upper layer is called LSduR. Sources: SWS LINInterface Fig. 9.1 p. 120 [SWS_Lin_00191] [SWS_Lin_00168] SWS LINInterface p. 37

The result of a frame is provided by the synchronous service Lin_GetStatus. It returns a Lin_StatusType. Upon reception, it sets Lin_SduPtr to a shadow buffer or to the mapped hardware receive buffer [SWS_Lin_00168] [SWS_Lin_00233]. LinIf calls it at the earliest after the maximum frame length and at the latest by the next schedule entry SWS LINInterface p. 35. The complete receive processing may reside in Lin_GetStatus. Received data remains consistent until the next frame is successfully received or the channel state changes SWS LINDriver p. 30. The end of the frame is detected either by a hardware controller or by the driver itself, byte by byte via UART interrupt SWS LINDriver Fig. 9.1 p. 56.

Sequence diagram: Frame reception on a master, depending on the hardware with controller or UART, completed by Lin_GetStatus. Sources: SWS LINDriver Fig. 9.1 p. 56 SWS LINInterface Fig. 9.4 p. 122 [SWS_Lin_00168]

Slave channels: Header-driven response processing

A slave does not know the master's schedule. It only responds to received headers SWS LINInterface p. 38. In state LIN_CH_OPERATIONAL, the driver must be able to receive a header consisting of break, sync, and PID at any time [SWS_Lin_00272]. It then calls LinIf_HeaderIndication. In doing so, it passes the received PID and a pointer to its hardware or shadow buffer [SWS_Lin_00280]. If the hardware cannot detect invalid PIDs, the driver forwards the PID unchecked [SWS_Lin_00271].

LinIf defines the response type in the callback. If it returns E_OK, the driver evaluates PduPtr->Drc [SWS_Lin_00282]:

  • LIN_FRAMERESPONSE_TX: The driver sets up the response from Cs, Dl, and SduPtr and transmits it. It reports success via LinIf_TxConfirmation [SWS_Lin_00283] [SWS_Lin_00275].
  • LIN_FRAMERESPONSE_RX: The driver configures reception with Cs and Dl. It reports success via LinIf_RxIndication with the received data [SWS_Lin_00284] [SWS_Lin_00274].
  • E_NOT_OK or LIN_FRAMERESPONSE_IGNORE: The driver ignores the response and reports nothing until the next header [SWS_Lin_00286] [SWS_Lin_00276].

Each relevant response must be completed before the next header indication, specifically with an Rx indication, Tx confirmation, or error indication [SWS_Lin_00285]. During transmission, LinIf has the data written directly into the driver buffer; the driver handles the copying SWS LINInterface p. 121.

Sequence diagram: After each header, the slave driver branches into transmit, receive, or ignore based on Drc. Sources: SWS LINInterface Fig. 9.3 p. 121 SWS LINInterface p. 123 SWS LINInterface p. 134 [SWS_Lin_00282] [SWS_Lin_00286]

Sleep command, wake-up, and wake-up detection

Only a master can transmit a go-to-sleep command. Lin_GoToSleep is asynchronous and instructs the driver to do so [SWS_Lin_00166]. In pure slave configurations, the service does not exist [SWS_Lin_00288] SWS LINDriver p. 31. The channel transitions to LIN_CH_SLEEP_PENDING in the process, even if the transmission fails SWS LINDriver p. 43.

In contrast, Lin_GoToSleepInternal works synchronously and without a bus command: The service sets the channel to LIN_CH_SLEEP, activates wake-up detection, and optionally switches the hardware into a power-saving mode [SWS_Lin_00167] SWS LINDriver p. 44. Each channel accepts sleep requests independently of the others SWS LINDriver p. 31.

Sequence diagram: Putting a master channel to sleep via LIN_CH_SLEEP_PENDING or, if it is already asleep, directly via Lin_GoToSleepInternal. Sources: SWS LINInterface Fig. 9.15 p. 136 [SWS_Lin_00166] [SWS_Lin_00167] SWS LINInterface p. 56

There are two services for waking up:

  • Lin_Wakeup generates a wake-up pulse and sets the channel to LIN_CH_OPERATIONAL [SWS_Lin_00169].
  • Lin_WakeupInternal also sets the channel to LIN_CH_OPERATIONAL, but does not send a pulse on the bus [SWS_Lin_00256] [SWS_Lin_00262].

A special case concerns wake-up during go-to-sleep: If the user requests wake-up while the sleep command is still pending, and Lin_GetStatus subsequently already reports the sleep state, LinIf calls Lin_Wakeup again SWS LINInterface p. 56.

If LinChannelWakeupSupport is configured, the hardware monitors the bus for wake-up requests in the sleep state SWS LINDriver p. 31. Lin_CheckWakeup synchronously checks whether a wake-up event is present on the channel [SWS_Lin_00160]. The service immediately reports a detected event to EcuM_SetWakeupEvent and LinIf_WakeupConfirmation SWS LINDriver p. 42 [SWS_Lin_00234]. Lin_CheckWakeup is called by LinIf_CheckWakeup. Depending on the wake-up source, this queries the driver or the transceiver driver SWS LINInterface p. 112. LIN does not require wake-up validation SWS EcuM p. 173.

Sequence diagram: A wake-up event on a sleeping channel is checked via EcuM and LinIf up to Lin_CheckWakeup and reported back to both modules. Sources: [SWS_Lin_00160] [SWS_Lin_00234] [SWS_Lin_00235] SWS EcuM Fig. 9.9 p. 175 SWS LINInterface p. 112

Configuration: Node type, channels, and partitions

The parameter LinNodeType determines which services exist. Lin_SendFrame, Lin_GoToSleep, and Lin_GetStatus exist only if at least one channel is configured as master [SWS_Lin_00287] [SWS_Lin_00288] [SWS_Lin_00289]. The container LinChannel contains, per channel, among other things baud rate, channel ID, wake-up support, node type, an optional EcuM wake-up source, and a clock reference SWS LINDriver p. 60. LinGeneral summarizes the driver-wide parameters SWS LINDriver p. 57. According to the configuration diagram, these include development error detection, version API, and timeout duration SWS LINDriver Fig. 10.1 p. 48.

In multi-partition systems, the following rules apply:

  • The driver operates as an independent instance in each partition; an API call affects only its own partition [SWS_Lin_CONSTR_00270].
  • If LinEcucPartitionRef references partitions, each channel must reference exactly one of them [SWS_Lin_CONSTR_00291].
  • LinChannel and LinTrcvChannel of a channel must use the same partition [SWS_Lin_CONSTR_00279].
  • The driver rejects unsupported partition assignments [SWS_Lin_00269].

The version information of the module is provided by Lin_GetVersionInfo [SWS_Lin_00161].

Behavior in the event of an error

If development error detection is active, the channel services check initialization, channel number, and state. For Lin_WakeupInternal, this is normatively documented [SWS_Lin_00258] [SWS_Lin_00259] [SWS_Lin_00260]:

  • LIN_E_UNINIT: Call before Lin_Init.
  • LIN_E_INVALID_CHANNEL: Invalid or inactive channel.
  • LIN_E_STATE_TRANSITION: The channel is not in LIN_CH_SLEEP.

Lin_Wakeup checks SWS LINDriver p. 45 in the same manner. Lin_GetVersionInfo reports LIN_E_PARAM_POINTER if a NULL pointer is passed SWS LINDriver p. 41. The error classes follow the scheme of the general BSW specification SWS LINDriver p. 32.

The driver reports LIN_E_TIMEOUT as a production error. If it must wait for a status change after accessing control registers, a configurable timeout protects this waiting time. If it expires, this indicates a hardware error [SWS_Lin_00290]. The notification goes via Dem_SetEventStatus to the event referenced in LinDemEventParameterRefs [SWS_Lin_00234] SWS LINDriver p. 65.

On master channels, bus errors are indicated in status value [SWS_Lin_00233]:

  • LIN_TX_HEADER_ERROR: Readback error, parity error, or physical bus error in the header.
  • LIN_TX_ERROR: Faulty response transmission.
  • LIN_RX_ERROR: Framing, overrun, or checksum error, or a response that is too short.
  • LIN_RX_NO_RESPONSE: No response byte received so far.

The evaluation is performed by LinIf. For event-triggered frames, LIN_RX_ERROR is considered a collision; LinIf then switches to a collision-resolving schedule SWS LINInterface p. 129. LIN_RX_NO_RESPONSE is not a communication error there SWS LINInterface p. 127.

Activity diagram: How LinIf evaluates the return value of Lin_GetStatus on a master channel. Sources: [SWS_Lin_00233] SWS LINInterface p. 40 SWS LINInterface Fig. 9.4 p. 122 SWS LINInterface p. 129 SWS LINInterface p. 127

On slave channels, the driver aborts frame processing in the event of an error in response transmission or reception and calls LinIf_LinErrorIndication [SWS_Lin_00277]. It reports invalid headers with LIN_ERR_HEADER [SWS_Lin_00281]. Lin_SlaveErrorType covers the following error types: header, stop bit, and checksum errors, monitoring errors in transmitted data bits, as well as missing and incomplete response [SWS_Lin_91140] SWS LINInterface p. 109.

The asynchronous function Lin_WakeupInternal ([SWS_Lin_00256]) transitions the addressed LIN channel into the state LIN_CH_OPERATIONAL without generating a wake-up pulse on the LIN bus ([SWS_Lin_00262]).   • LIN_E_STATE_TRANSITION: The channel state machine is not in state LIN_CH_SLEEP at the time of the call ([SWS_Lin_00260]).

In interaction, the LIN Driver receives internal wake-up requests from the LIN Interface via this function and ensures channel operation without transmitting physical wake-up pulses on the LIN bus ([SWS_Lin_00262]).

According to [SWS_Lin_00229], the enumeration type Lin_FrameCsModelType specifies the checksum model (Checksum model) used for a LIN frame. It is provided via the header file Lin_GeneralTypes.h and serves for the standardized definition of the checksum method in module Lin.

According to [SWS_Lin_00229], the value range comprises the following variants:

  • LIN_ENHANCED_CS: Identifies the enhanced checksum model (Enhanced checksum model).
  • LIN_CLASSIC_CS: Identifies the classic checksum model (Classic checksum model).

Context and Interaction

The type is used during configuration or passing of LIN frames to inform the LIN Driver of the calculation and validation rule to be applied for the checksum field. Interpretation: The selected checksum model likely controls in the driver whether the checksum is calculated exclusively over the payload data (classic model) or with additional inclusion of the protected identifier (enhanced model).

As a pure type definition, Lin_FrameCsModelType has no runtime errors of its own, no DET or DEM messages, and is subject to no reentrancy or execution restrictions. The validity of the assigned enumeration values is usually ensured during configuration or by the processing driver interfaces.

use

According to [SWS_Lin_00233], the enumeration type Lin_StatusType defines the operating states of a LIN channel as well as the states of ongoing or completed LIN frame operations. The type is provided via the header file Lin_GeneralTypes.h and serves as the return value of the API service Lin_GetStatus().

The state values distinguish between channel-wide states and frame-related operational states:

  • Channel states: LIN_OPERATIONAL represents normal operation, in which the channel is ready to transmit the next header and no data from the previous frame is present any longer (e.g. after initialization). LIN_CH_SLEEP indicates the sleep state (sleep mode), in which wake-up detection by slave nodes is activated.
  • Transmission states: LIN_TX_OK confirms a successful transmission, while LIN_TX_BUSY denotes an ongoing transmission (header or response).
  • Reception states: LIN_RX_OK reports the error-free reception of a response. LIN_RX_BUSY signals an ongoing reception in which at least one data byte, but not yet the checksum byte, has been received. LIN_RX_NO_RESPONSE indicates that no response byte has been received so far.

Error handling

If an error occurs during the execution of a frame operation, this is indicated via specific error values according to [SWS_Lin_00233]:

  • LIN_NOT_OK: Indicates that a development or production error occurred during a frame operation.
  • LIN_TX_HEADER_ERROR: Erroneous transmission of the header, e.g. due to discrepancies between transmitted and read-back data, identifier parity errors, or physical bus errors.
  • LIN_TX_ERROR: Erroneous transmission of the response, caused by data inconsistencies (mismatch) or physical bus errors.
  • LIN_RX_ERROR: Erroneous reception of the response, caused by framing errors, overrun errors, checksum errors, or an incomplete response (Short Response).

It records errors that are detected during reception of the header as well as during transmission or reception of the response ([SWS_Lin_91140]). Error Types and Range of Values

According to [SWS_Lin_91140], the type defines the following error constants:

  • LIN_ERR_HEADER: Indicates an error during header reception (Error in header) ([SWS_Lin_91140]).
  • LIN_ERR_RESP_STOPBIT: Signals a framing error within the response (Framing error in response) ([SWS_Lin_91140]).
  • LIN_ERR_RESP_CHKSUM: Indicates a checksum error of the response (Checksum error) ([SWS_Lin_91140]).
  • LIN_ERR_RESP_DATABIT: Reports a monitoring error regarding a transmitted data bit in the response (Monitoring error of transmitted data bit in response) ([SWS_Lin_91140]).
  • LIN_ERR_NO_RESP: Indicates the absence of an expected response (No response) ([SWS_Lin_91140]).
  • LIN_ERR_INC_RESP: Occurs when a response was incompletely transmitted or received (Incomplete response) ([SWS_Lin_91140]).
