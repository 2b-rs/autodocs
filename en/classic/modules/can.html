Role of the CAN driver between CanIf and controller hardware

The CAN driver (Can) is the lowest, hardware-oriented layer of the Classic CAN stack. Any access to the CAN hardware is encapsulated in functions of this module. The driver itself does not track the state transitions of the controllers (SWS CANDriver p. 30). Upwards, it communicates exclusively with the CAN Interface. The callbacks that the driver calls are all implemented in CanIf and are not configurable: CanIf_ControllerBusOff, CanIf_ControllerModeIndication, CanIf_RxIndication, and CanIf_TxConfirmation. In addition, the driver requires Det_ReportRuntimeError and the OS service GetCounterValue ([SWS_Can_00234], SWS CANDriver p. 73).

CanIf accesses the hardware only via abstract handles. Hardware Object Handles for transmission (HTH) and reception (HRH) reference mailbox structures whose layout is known only to the driver (SWS CANInterface p. 29). The data type of these handles is Can_HwHandleType. It is based on uint8; with more than 255 hardware objects, the extended value range with uint16 is used ([SWS_Can_00429], SWS CANDriver p. 54). Mode requests from the CanSM also reach the driver only via CanIf (SWS CANInterface p. 20).

Context diagram: The driver is located between CanIf, EcuM, BSW Scheduler, DET, Os, and the controller hardware; the CanSM reaches it only indirectly via CanIf. Sources: [SWS_Can_00234], SWS CANInterface p. 20, SWS CANInterface p. 156, SWS CANDriver p. 63

Startup and lifecycle: Driver state and controller states

The driver itself has only two states. After power-up or reset, it is in CAN_UNINIT. Can_Init initializes all controllers of the hardware unit according to their configuration and then transitions to CAN_READY ([SWS_Can_00223], SWS CANDriver p. 29). The ECU State Manager calls Can_Init during the startup phase before any other driver function is used ([SWS_Can_91012], SWS CANDriver p. 41). According to an implementation note, this happens at most once at runtime. Register settings affecting all controllers of a hardware unit are possible only in Can_Init (SWS CANDriver p. 29). The passed structure Can_ConfigType is hardware-specific. It contains the global settings and pointers to the controller configurations ([SWS_Can_00413]).

Per controller, the specification distinguishes four states in simplified form: UNINIT, STOPPED, STARTED, and SLEEP. They are represented as Can_ControllerStateType with the values CAN_CS_UNINIT through CAN_CS_SLEEP ([SWS_Can_91013], SWS CANDriver p. 30). After initialization, CanIf expects the controller to remain in STOPPED. In this state, it can neither transmit nor receive (SWS CANInterface p. 39). Each controller is started individually with Can_SetControllerMode(CAN_CS_STARTED) (SWS CANDriver p. 29). In doing so, it is reinitialized with the same configuration that was used previously (SWS CANDriver p. 59).

Can_SetControllerMode operates asynchronously and is non-reentrant. E_OK only means that the request was accepted; E_NOT_OK signals a development error ([SWS_Can_00230]). The driver reports the completed transition via CanIf_ControllerModeIndication ([SWS_Can_00234]). Without an interrupt, Can_MainFunction_Mode polls the status registers. The requirement text of the document reference mistakenly mentions Can_MainFunction_Wakeup here ([SWS_Can_00368], SWS CANDriver p. 84). Can_GetControllerMode provides the current mode ([SWS_Can_91014], SWS CANDriver p. 65). Can_DeInit handles the return path. It sets the driver to CAN_UNINIT and all controllers from STOPPED or SLEEP to UNINIT, thus preparing for a reconfiguration ([SWS_Can_91002], [SWS_Can_91010], SWS CANDriver p. 37).

State diagram: The driver state (CAN_UNINIT/CAN_READY) and the four controller states are controlled by Can_Init, Can_SetControllerMode, and Can_DeInit. The SLEEP and Bus-off transitions are marked as interpretation. Sources: SWS CANDriver p. 29, SWS CANDriver p. 30, [SWS_Can_91013], [SWS_Can_91010], SWS CANInterface p. 39

Transmit path: from Can_Write to transmit confirmation

CanIf passes each L-PDU using Can_Write(Hth, PduInfo). The function is synchronous and thread-safe reentrant. Via the HTH, the controller is also determined, because HTH numbers are unique within a hardware unit ([SWS_Can_00233]). The structure Can_PduType combines swPduHandle, length, id, and the data pointer sdu ([SWS_Can_00415], SWS CANDriver p. 53). CanIf sets swPduHandle to the CanTxPduId that it expects later in CanIf_TxConfirmation. In addition, CanIf assigns the two most significant bits of the CanId with the Extended flag and the FD flag (SWS CANInterface p. 80).

If no hardware transmit object is free, the driver returns the overlaid return value CAN_BUSY ([SWS_Can_00039], SWS CANDriver p. 54). If transmit buffering is enabled, CanIf then stores the L-PDU in a dedicated buffer, provided its size is greater than zero (SWS CANInterface p. 43). After each confirmation, CanIf resubmits the highest-priority pending L-PDU via Can_Write (SWS CANInterface p. 45, SWS CANInterface p. 157). Importantly: The driver does not check the controller state prior to Can_Write (SWS CANDriver p. 30). CanIf therefore blocks transmit requests for controllers in CAN_CS_STOPPED (SWS CANInterface p. 53).

The confirmation comes either from the transmit interrupt or, in the case of polling, cyclically from Can_MainFunction_Write, which is called by the BSW Scheduler ([SWS_Can_00225], SWS CANInterface p. 156). In both cases, the driver calls CanIf_TxConfirmation with the swPduHandle that was passed during Can_Write (SWS CANInterface p. 102).

Sequence diagram: A transmit request either leads directly into the hardware or is buffered in CanIf after CAN_BUSY; the confirmation arrives via interrupt or polling and triggers the retransmission of buffered L-PDUs. Sources: [SWS_Can_00233], [SWS_Can_00039], [SWS_Can_00225], SWS CANInterface p. 157, SWS CANInterface p. 156

Receive path, L-PDU callout, and frame formats

The driver reports received frames via interrupt or, in the case of polling, from Can_MainFunction_Read ([SWS_Can_00226], SWS CANDriver p. 79). With CanIf_RxIndication, CanIf receives HRH, CanId, data length, and a reference to the normalized data. The hardware receive object remains locked until the end of the copy process. After returning from CanIf_RxIndication, it is released immediately (SWS CANInterface p. 47). Subsequently, CanIf executes the software filter and the Data Length Check and forwards the data to the upper layer (SWS CANInterface p. 50).

Optionally, prior to forwarding, the driver calls a configurable L-PDU callout: <LPDU_CalloutName>(Hrh, CanId, CanDataLegth, CanSduPtr) with return type boolean ([SWS_Can_00443]). If the callout returns false, according to the document citation the L-PDU is not processed further (SWS CANDriver p. 77). This section originates from R25-11. That the rule also applies to R20-11 is an interpretation that is presumably accurate.

The frame format is encoded in Can_IdType. The two most significant bits distinguish classical frames and CAN FD frames, in each case with standard or extended ID (values 00 to 11) ([SWS_Can_00416]). CAN FD is active for a controller if a baud rate with CanControllerFdBaudrateConfig applies. In this way, classical CAN 2.0 frames, for example for selective wake-up, can be mixed with FD frames (SWS CANDriver p. 49). CanIf also evaluates the same bits for dynamic transmit L-PDUs (SWS CANInterface p. 34).

Sequence diagram: Reception is detected via interrupt or polling, optionally filtered by the L-PDU callout, and then passed via CanIf_RxIndication to CanIf and the upper layer. Afterwards, the hardware object is released. The callout discard is an interpretation. Sources: [SWS_Can_00226], [SWS_Can_00443], SWS CANInterface p. 47, SWS CANInterface p. 103

Polling main functions, configuration, and partitions

For each event-driven path, there is a scheduled main function provided via SchM_Can.h: Can_MainFunction_Write, Can_MainFunction_Read, Can_MainFunction_BusOff, Can_MainFunction_Wakeup, and Can_MainFunction_Mode ([SWS_Can_00225], [SWS_Can_00226], [SWS_Can_00227], [SWS_Can_00228], [SWS_Can_00368]). In the R20-11 requirements, polling is tied to mode POLLING. Document passages from later releases extend this to MIXED: there, only hardware objects with CanHardwareObjectUsesPolling = TRUE are polled. Furthermore, they allow an empty definition of the main function if polling is not performed at all (SWS CANDriver p. 81, SWS CANDriver p. 83, SWS CANDriver p. 80).

If multiple periods are configured via CanMainFunctionRWPeriods, the write main functions are named Can_MainFunction_Write_<ShortName>(). There is one function per period that is referenced by at least one TRANSMIT hardware object; for the read path, the same applies with RECEIVE objects ([SWS_Can_00441], SWS CANDriver p. 81, SWS CANDriver p. 79). The supporting passages originate from later releases, and the R20-11 text of [SWS_Can_00441] in the payload merely reflects the revision history. Therefore, the naming rule is likely to apply to R20-11 as well; this is an interpretation.

In multicore systems, the module operates as an independent instance in each partition. An API call only affects the partition in which it occurs ([SWS_Can_CONSTR_00508]). Three rules apply to the configuration:

  • The partitions referenced via CanControllerEcucPartitionRef must be a subset of the partitions in CanEcucPartitionRef ([SWS_Can_CONSTR_00509], SWS CANDriver p. 99).
  • The controller and transceiver channel of a communication channel must reference the same partition ([SWS_Can_CONSTR_00510]).
  • The driver rejects partition assignments that the implementation does not support ([SWS_Can_00507]).

Operating rules: interrupt locks, wakeup, and error counters

Can_DisableControllerInterrupts and Can_EnableControllerInterrupts are reentrant and take effect in a nested manner ([SWS_Can_00231], [SWS_Can_00232], SWS CANDriver p. 61, SWS CANDriver p. 62). If disabled multiple times, enabling must be performed just as many times. Enabling without prior disabling has no effect. Enabling only activates those interrupts that are permitted according to the current software state.

Can_CheckWakeup checks whether wake-up via the bus is present. If the requested controller has detected a wakeup, the driver reports this via EcuM_SetWakeupEvent to EcuM ([SWS_Can_00360], SWS CANDriver p. 63). The caller is CanIf: during EcuM_CheckWakeup, it queries the affected drivers and transceivers via CanIf_CheckWakeup (SWS CANInterface p. 55). Wakeup events that are statically configured as 'to be polled' are captured by Can_MainFunction_Wakeup ([SWS_Can_00228]).

Sequence diagram: The wakeup check runs from EcuM via CanIf to the driver; the driver reports a detected wakeup directly to EcuM. Sources: [SWS_Can_00360], SWS CANDriver p. 63, SWS CANInterface p. 55

For diagnostic purposes, Can_GetControllerErrorState provides the error state CAN_ERRORSTATE_ACTIVE, CAN_ERRORSTATE_PASSIVE, or CAN_ERRORSTATE_BUSOFF ([SWS_Can_91004], [SWS_Can_91003], SWS CANDriver p. 49). The Rx and Tx error counters from Can_GetControllerRxErrorCounter and Can_GetControllerTxErrorCounter are not available on all hardware; in that case, the functions return E_NOT_OK. Because the hardware counts asynchronously, the values are not a reliable basis for conclusions about the bus state ([SWS_Can_00511], [SWS_Can_00516], SWS CANDriver p. 67). Can_ErrorType describes a superset of typical hardware errors, such as bit, ACK, CRC, or stuffing errors ([SWS_Can_91021], SWS CANDriver p. 55). CanIf derives security events from these values (SWS CANInterface p. 69).

Behavior in the event of an error

The driver detects bus-off via interrupt or by polling in Can_MainFunction_BusOff. It only makes the necessary register settings and does not perform any hardware recovery. It then reports the event via CanIf_ControllerBusOff; the software state only changes within this callback ([SWS_Can_00227], [SWS_Can_00234], SWS CANDriver p. 30). CanIf then sets the PDU channel to CANIF_TX_OFFLINE and notifies CanSM via CanSM_ControllerBusOff. Reinitialization and restart as part of the bus-off recovery only follow afterwards (SWS CANInterface p. 59, SWS CANInterface p. 53, SWS CANInterface p. 121).

Sequence diagram: A bus-off is reported by the driver without hardware recovery to CanIf; CanIf sets the transmit path offline and informs CanSM. Sources: [SWS_Can_00227], SWS CANDriver p. 30, SWS CANInterface p. 59, SWS CANInterface p. 53

If development error detection is enabled, the driver reports development errors to the DET. These include, among others, CAN_E_PARAM_POINTER, CAN_E_PARAM_HANDLE, CAN_E_PARAM_DATA_LENGTH, CAN_E_PARAM_CONTROLLER, CAN_E_UNINIT, CAN_E_TRANSITION, CAN_E_PARAM_BAUDRATE, and CAN_E_INIT_FAILED ([SWS_Can_91019]). After returning from the DET, the affected function returns immediately. Functions with a return value then return E_NOT_OK (SWS CANDriver p. 48). The driver responds to impermissible state transitions with CAN_E_TRANSITION (SWS CANDriver p. 30).

Can_DeInit is particularly strict. The caller must ensure that no controller is in STARTED anymore. With error detection enabled, the function reports CAN_E_TRANSITION if the driver is not in CAN_READY or a controller is still running ([SWS_Can_91002], [SWS_Can_91012], SWS CANDriver p. 59, SWS CANDriver p. 37).

Activity diagram: With error detection active, Can_DeInit checks the driver state and running controllers. Only then does it set the module state and subsequently all controllers to UNINIT. Sources: SWS CANDriver p. 59, SWS CANDriver p. 29, SWS CANDriver p. 48, [SWS_Can_91010]

As the only runtime error, CAN_E_DATALOST is defined for a lost received message ([SWS_Can_91020]). It is reported via the DET service Det_ReportRuntimeError (SWS CANDriver p. 73). In contrast, CAN_BUSY is not an error. It is a temporary result of Can_Write when no transmit object is free, and CanIf reacts to it with buffering ([SWS_Can_00039], SWS CANInterface p. 43).

function Can_SetControllerMode [SWS_Can_00230] 📄 PDF

Std_ReturnType Can_SetControllerMode (uint8 Controller, Can_ControllerStateType Transition);

This function performs software triggered state transitions of the CAN controller State machine.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 069d5fac0a42 Provenance

The function Can_SetControllerMode ([SWS_Can_00230]) serves for the software-side initiation of state transitions in the CAN controller state machine (AUTOSAR_SWS_CANDriver §7.3 “CAN Controller State Machine”). It encapsulates hardware-related register accesses in order to trigger the required switching of hardware states (e.g., between UNINIT, STOPPED, STARTED, and SLEEP) ([SWS_Can_91010]).

Call and Semantics

  • Signature & Parameters: The invocation takes place via Can_SetControllerMode(Controller, Transition). The parameter Controller addresses the desired CAN controller, whereas Transition specifies the state transition to be requested ([SWS_Can_00230]).
  • Synchronization & Asynchrony: The function operates asynchronously (Service ID 0x03) ([SWS_Can_00230]). After leaving Can_SetControllerMode, the cyclic function Can_Mainfunction_Mode presumably takes over further processing and tracking of the state change (AUTOSAR_SWS_CANDriver p. 38).
  • Return Value: Upon successful acceptance of the transition request, the service returns E_OK. If a development error occurs or the request cannot be accepted, E_NOT_OK is returned ([SWS_Can_00230], [SWS_Can_00441]).

Restrictions and Error Handling

Can_SetControllerMode is specified as non-reentrant ([SWS_Can_00230]) and must therefore not be called multiple times in an interrupting manner for the same or parallel instances. In the event of invalid requests or internal errors, rejection occurs via E_NOT_OK as a development error ([SWS_Can_00230]).

The function Can_DisableControllerInterrupts disables all interrupts of the specified CAN controller ([SWS_Can_00231]). The call is performed synchronously and is executed reentrantly ([SWS_Can_00231]). Passed as a parameter is Controller (type uint8), which addresses the respective CAN controller; the function has no return value ([SWS_Can_00231]).

According to the specification, the function accesses the controller and supports nested calls via a counter or behavioral mechanism (AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”). Multiple calls to Can_DisableControllerInterrupts must be handled consistently in conjunction with the counterpart Can_EnableControllerInterrupts (AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”, AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”, AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”).

Error handling

If Can_DisableControllerInterrupts is called when the driver is in the uninitialized state, the function reports the error CAN_E_UNINIT (AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”). In addition, the function raises further errors in case of incorrect parameter passing or an impermissible state (AUTOSAR_SWS_CANDriver §SWS_Can_00231 “Specification of CAN Driver”).

function Can_EnableControllerInterrupts [SWS_Can_00232] 📄 PDF

void Can_EnableControllerInterrupts (uint8 Controller);

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 02988edf6266 Provenance

use

The synchronous and reentrant function Can_EnableControllerInterrupts serves to reactivate all permissible interrupts of a specified CAN controller ([SWS_Can_00232], AUTOSAR_SWS_CANDriver p. 66). It expects Controller (type uint8) as its only input parameter, through which the CAN controller concerned is addressed, and provides no return value ([SWS_Can_00232]).

Concurrency and Nesting

The function evaluates internal software flags (AUTOSAR_SWS_CANDriver p. 65). If controller interrupts were disabled multiple times previously, Can_EnableControllerInterrupts probably has to be called just as many times before the interrupts are actually re-enabled at the controller level (AUTOSAR_SWS_CANDriver p. 65). The interaction between Can_DisableControllerInterrupts and Can_EnableControllerInterrupts thus requires consistent pairing of the calls (AUTOSAR_SWS_CANDriver p. 65).

Error handling

If Can_EnableControllerInterrupts is called before the CAN driver module has been initialized, the function reports the error CAN_E_UNINIT (AUTOSAR_SWS_CANDriver p. 66). If this error is present, the function probably does not enable the hardware interrupts (AUTOSAR_SWS_CANDriver p. 66).

Interaction

The function forms the counterpart to disabling the interrupts and is subject to the standard error handling and driver requirements of the Classic Platform ([SWS_Can_00441]).

function Can_CheckWakeup [SWS_Can_00360] 📄 PDF

Std_ReturnType Can_CheckWakeup (uint8 Controller);

This function checks if a wakeup has occurred for the given controller.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 1e7164bea4c5 Provenance

Usage and Semantics

The synchronous function Can_CheckWakeup checks for a specified CAN controller (parameter Controller) whether a wakeup event was detected by the hardware ([SWS_Can_00360], AUTOSAR_SWS_CANDriver p. 48, AUTOSAR_SWS_CANDriver p. 67). The call returns as Std_ReturnType either E_OK upon successful acceptance of the call or E_NOT_OK ([SWS_Can_00360]). The availability of the function is pre-compile-time configurable: The service is added to or removed from the source code via a configuration parameter (AUTOSAR_SWS_CANDriver p. 67, AUTOSAR_SWS_CANDriver p. 97).

Concurrency and Error Handling

According to the functional specification, Can_CheckWakeup is defined as non-reentrant (Non Reentrant) ([SWS_Can_00360]). Before the call, the CAN driver must be properly initialized; if the function is called in the uninitialized state, the driver reports the error CAN_E_UNINIT (AUTOSAR_SWS_CANDriver p. 67).

Interaction in the Overall System

The invocation of Can_CheckWakeup is performed by the CAN Interface (AUTOSAR_SWS_CANDriver p. 48). If wakeup support is activated in the overall system ([SWS_CANIF_00180]), the service CanIf_CheckWakeup is called upon a wakeup event (for example, during the execution of EcuM_CheckWakeup) (AUTOSAR_SWS_CANInterface §7.18.4.1 p. 55). The CAN Interface then queries the configured CAN drivers via Can_CheckWakeup to determine which exact CAN hardware triggered the bus wakeup ([SWS_CANIF_00395], AUTOSAR_SWS_CANInterface §7.18.4.1 p. 55).

The synchronous function Can_Write ([SWS_Can_00233]) is called by CanIf to pass a CAN message to the CAN driver (CanDrv) for transmission. The hardware transmit handle is passed via the parameter Hth; since the HTH numbers are unique within a hardware unit, this identifier also implicitly determines the controller to be addressed (AUTOSAR_SWS_CANDriver, p. 73). The parameter PduInfo (of type const Can_PduType*) references the SDU user memory, the data length, and the CAN identifier ([SWS_Can_00416], AUTOSAR_SWS_CANDriver, p. 51). During processing, the function also stores the passed swPduHandle (AUTOSAR_SWS_CANDriver, p. 43).

Return Values and Error Handling

The return value of type Std_ReturnType reports the result of the transmission request to the calling layer:

  • E_OK: The transmit request was successfully accepted ([SWS_Can_00233]).
  • E_NOT_OK: A development error has occurred ([SWS_Can_00233]).
  • CAN_BUSY: No free TX hardware buffer is available, or a preemptive call to Can_Write cannot be served reentrantly (AUTOSAR_SWS_CANDriver, p. 51, AUTOSAR_SWS_CANDriver, p. 73).

Concurrency and Limitations

According to the specification, Can_Write is reentrant or thread-safe ([SWS_Can_00233]). Prior to assignment, the function first checks whether the hardware transmit object identified by the Hth is free and whether no other call to Can_Write is currently active for the same Hth (AUTOSAR_SWS_CANDriver, p. 73). If the buffer is occupied or a concurrent transmission on the same handle is in progress, CAN_BUSY is returned to CanIf.

The enumeration type Can_ControllerStateType ([SWS_Can_91013]) defines the basic operating states of a CAN controller. It is available via the header file Can_GeneralTypes.h and comprises the following states:

  • CAN_CS_UNINIT (0x00): The CAN controller is uninitialized.
  • CAN_CS_STARTED (0x01): The CAN controller is in active operation (started).
  • CAN_CS_STOPPED (0x02): The CAN controller is stopped.
  • CAN_CS_SLEEP (0x03): The CAN controller is in sleep mode.

Usage and Interfaces: The type acts as a central parameter for mode control and query functions in the CAN Interface (CanIf):

  • Mode Request: The target state is passed to the controller via CanIf_SetControllerMode(ControllerId, ControllerMode) (AUTOSAR_SWS_CANInterface p. 76).
  • State Query: The function CanIf_GetControllerMode(ControllerId, ControllerModePtr) queries the current state via an output pointer of type Can_ControllerStateType* (AUTOSAR_SWS_CANInterface p. 77).

Timing Behavior: When Can_SetControllerMode is called, the driver passes the mode request directly to the hardware of the CAN controller (AUTOSAR_SWS_CANInterface p. 144). The element Can_ErrorType ([SWS_Can_91021]) is an enumeration provided via the header Can_GeneralTypes.h. The type defines a standardized superset of CAN error types that typical CAN hardware can detect and signal. The type is used, among other things, as a passed parameter in the callback function CanIf_ErrorNotification (AUTOSAR_SWS_CANInterface p. 110) to forward error messages of a controller (identified by the ControllerId) to the CAN Interface.

According to [SWS_Can_91021], the value range comprises the following error states:

  • Bit errors: CAN_ERROR_BIT_MONITORING1 (0 sent, 1 read), CAN_ERROR_BIT_MONITORING0 (1 sent, 0 read), and CAN_ERROR_BIT (generic bit error if the hardware does not support distinguishing between bit monitoring 0 and 1).
  • Acknowledgment errors: CAN_ERROR_CHECK_ACK_FAILED (failed acknowledgment) and CAN_ERROR_ACK_DELIMITER (error at acknowledgment delimiter).
  • Frame and checking errors: CAN_ERROR_CHECK_FORM_FAILED (form error), CAN_ERROR_CHECK_STUFFING_FAILED (stuff bit error), and CAN_ERROR_CHECK_CRC_FAILED (CRC check error).
  • Arbitration and bus states: CAN_ERROR_ARBITRATION_LOST (loss of arbitration), CAN_ERROR_OVERLOAD (overload frame when receive buffers are full), and CAN_ERROR_BUS_LOCK (bus permanently blocked at dominant level).

Not every CAN hardware supports the complete spectrum of specified error types ([SWS_Can_91021]); the reported value corresponds to the error code provided by the hardware (AUTOSAR_SWS_CANDriver p. 52). As a pure data type, Can_ErrorType has no reentrancy of its own. Interpretation: The passing via CanIf_ErrorNotification is presumably expected to occur asynchronously in the interrupt context of the CAN controller. General changes and histories of the driver are documented in [SWS_Can_00441].
