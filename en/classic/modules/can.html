Controls the CAN controller hardware and mediates transmission, reception, and state changes to the CAN Interface.

The CAN driver controls the CAN controllers of a hardware unit and is the hardware layer beneath the CAN Interface. It reports reception, transmission confirmation, bus-off, and mode changes to it via callback [SWS_Can_00234]. After Can_Init, all controllers are in STOPPED. Each controller is started individually and asynchronously with Can_SetControllerMode; success is only reported subsequently [SWS_Can_00230]. Transmission is performed with Can_Write via hardware transmit handles. If no transmit object is free, the driver returns CAN_BUSY, and CanIf buffers the request.

The CAN driver encapsulates all access to the CAN controllers of a hardware unit. It serves the CAN Interface as its sole user and reports reception, transmission confirmation, bus-off, and mode changes via predefined CanIf callbacks [SWS_Can_00234]. The ECU State Manager initializes it with Can_Init and a hardware-specific Can_ConfigType [SWS_Can_00223]. After that, the driver is in CAN_READY and all controllers are in STOPPED SWS CANDriver p. 29.

Context diagram: Embedding of Can between EcuM, BSW Scheduler, CanIf, DET, Os, and the controller hardware. Sources: [SWS_Can_00234], SWS CANDriver p. 78

Each controller passes through the states UNINIT, STOPPED, STARTED, and SLEEP [SWS_Can_91013]. It is started individually and asynchronously with Can_SetControllerMode: E_OK only means "accepted" [SWS_Can_00230]. The driver reports the reached state later via CanIf_ControllerModeIndication SWS CANDriver p. 33. Bus-off leads the controller to STOPPED without hardware recovery; a bus wakeup leads it from SLEEP to STOPPED SWS CANDriver p. 35.

State diagram: Transitions of a controller through software calls as well as bus-off and wakeup events. Sources: [SWS_Can_91010], SWS CANDriver p. 38

Transmission is performed using Can_Write(Hth, PduInfo). The two most significant bits of Can_IdType distinguish CAN 2.0 and CAN FD as well as standard and extended ID [SWS_Can_00233] [SWS_Can_00416]. If no transmit object is free, the driver returns CAN_BUSY, and CanIf buffers the request [SWS_Can_00039] SWS CANDriver p. 47. Events are detected via interrupt or by polling. Cyclic main functions are provided for polling SWS CANDriver p. 41:

  • Write and Read: transmit confirmations and reception
  • BusOff and Wakeup: bus-off and wakeup events
  • Mode: mode transitions

The main functions are defined in [SWS_Can_00225] through [SWS_Can_00228] and [SWS_Can_00368].

In case of an error, the driver reports development errors such as CAN_E_UNINIT or CAN_E_TRANSITION to the DET [SWS_Can_91019]. Functions with a return value then return E_NOT_OK SWS CANDriver p. 48. Bus-off recovery is handled by CanSM via CanIf. The restart is presumed to occur via Can_SetControllerMode(CAN_CS_STARTED) again SWS CANInterface p. 138. Error state and error counters can be queried; however, the counter values are not considered a reliable bus state [SWS_Can_91004] [SWS_Can_00516].

Role: hardware-oriented driver between CanIf and CAN controllers

The CAN driver encapsulates all access to the CAN hardware of a hardware unit. State changes of the controllers occur only via Can_Init, Can_SetBaudrate, and Can_SetControllerMode. The driver does not store the state transitions itself SWS CANDriver p. 30. Its upper communication partner is the CAN Interface. All callbacks invoked by the driver are implemented in CanIf and are not configurable: CanIf_RxIndication, CanIf_TxConfirmation, CanIf_ControllerBusOff, and CanIf_ControllerModeIndication. In addition, it requires Det_ReportRuntimeError and the Os service GetCounterValue [SWS_Can_00234] SWS CANDriver p. 73. Imported types originate, among others, from ComStack_Types, EcuM, and Os [SWS_Can_00222].

The ECU State Manager initializes the driver via Can_Init. According to the implementation note, it calls the function at most once at runtime [SWS_Can_00223] SWS CANDriver p. 29. The cyclic main functions are called directly by the BSW Scheduler. They have neither parameters nor return values and are non-reentrant; no execution order is prescribed SWS CANDriver p. 78. The driver offers no callbacks toward lower layers. External CAN controllers may only be accessed via synchronous MCAL APIs such as SPI SWS CANDriver p. 76.

Context diagram: Can is initialized by EcuM, called cyclically by the BSW Scheduler, and used by CanIf. It reports to CanIf, EcuM, and DET, and uses Os for timeouts. Sources: [SWS_Can_00234], SWS CANDriver p. 45, SWS CANDriver p. 78

From power-on to STARTED: driver and controller states

The driver as a whole recognizes only the states CAN_UNINIT and CAN_READY. After reset, it is in CAN_UNINIT. Can_Init initializes all controllers according to the configuration and transitions to CAN_READY thereafter. Can_DeInit sets the module state to CAN_UNINIT before deinitializing the controllers [SWS_Can_00223] [SWS_Can_91002] SWS CANDriver p. 29.

Separate from this, each controller has four states from Can_ControllerStateType: CAN_CS_UNINIT, CAN_CS_STOPPED, CAN_CS_STARTED, and CAN_CS_SLEEP [SWS_Can_91013].

  • In STOPPED, the controller is initialized, but does not participate in bus communication and sends neither error frames nor acknowledges.
  • STARTED is normal operation.
  • SLEEP differs from STOPPED only on hardware with sleep mode SWS CANDriver p. 31.

Can_Init sets all controllers to STOPPED SWS CANDriver p. 32. Can_DeInit transitions them from STOPPED or SLEEP to UNINIT [SWS_Can_91010] SWS CANDriver p. 38. There is no direct path from STARTED to UNINIT SWS CANDriver p. 38.

State diagram: lifecycle of a CAN controller. Software and bus events trigger transitions; return to UNINIT is only possible via Can_DeInit from STOPPED or SLEEP. Sources: [SWS_Can_91013], [SWS_Can_91010], SWS CANDriver p. 38, SWS CANDriver p. 34, SWS CANDriver p. 35

Each controller is started individually with Can_SetControllerMode(CAN_CS_STARTED) SWS CANDriver p. 29. The service operates asynchronously: E_OK only indicates that the request was accepted [SWS_Can_00230]. Upon each transition to STARTED, the controller is reinitialized using the configuration last used by Can_Init or Can_SetBaudrate SWS CANDriver p. 59. The hardware may apply the transition with a delay. Therefore, the driver reports the reached state only subsequently via CanIf_ControllerModeIndication; whether the target is reached is monitored by an upper layer SWS CANDriver p. 33. Polled mode transitions are detected by Can_MainFunction_Mode [SWS_Can_00368]. Can_GetControllerMode synchronously queries the current mode [SWS_Can_91014].

Sequence diagram: initialization by EcuM and asynchronous start of a controller. The success notification only follows after polling in Can_MainFunction_Mode. Sources: [SWS_Can_00230], [SWS_Can_00368], SWS CANInterface p. 156, SWS CANDriver p. 29

Transmission via hardware transmit handles

CanIf passes transmit requests with Can_Write(Hth, PduInfo). The Hth specifies the hardware transmit object and thus also the controller, because HTH numbers are unique within a hardware unit [SWS_Can_00233]. Can_HwHandleType covers 0..0x0FF by default and, if there are more than 255 hardware objects, the extended range up to 0xFFFF [SWS_Can_00429]. Can_PduType bundles the fields swPduHandle, length, id, and sdu [SWS_Can_00415].

In Can_IdType, the two most significant bits encode the frame type [SWS_Can_00416]:

  • 00: CAN with standard ID
  • 01: CAN FD with standard ID
  • 10: CAN with extended ID
  • 11: CAN FD with extended ID

This allows CAN 2.0 and CAN FD frames to be mixed at frame level, provided an FD baud rate configuration is active for the controller SWS CANDriver p. 49 SWS CANInterface p. 71.

Can_Write must be thread-safe because CanIf_Transmit is reentrant. The driver returns CAN_BUSY if no transmit object is free or if a preemptive call cannot be executed reentrantly [SWS_Can_00039] SWS CANDriver p. 47. CanIf then buffers the request. If an object becomes free, CanIf calls Can_Write again in priority order SWS CANInterface p. 48. The driver keeps the swPduHandle available until the corresponding CanIf_TxConfirmation SWS CANDriver p. 35. Multiplexed Transmission can be configured statically to prevent priority inversion; multiple hardware objects then form an HTH SWS CANDriver p. 40.

Sequence diagram: transmit request with paths E_OK and CAN_BUSY, followed by confirmation via interrupt or polling. Afterward, CanIf can provide a buffered L-PDU. Sources: [SWS_Can_00233], [SWS_Can_00039], SWS CANInterface p. 142, SWS CANInterface p. 48

Reception and the cyclic main functions

Upon reception, the driver calls CanIf_RxIndication. It passes ID, hardware object, and abstract CanIf ControllerId as well as length and pointer to the L-SDU. For extended frames, it sets the MSB of the ID so that CanIf detects the frame type SWS CANDriver p. 43. Optionally, a configurable L-PDU callout <LPDU_CalloutName> is interposed beforehand [SWS_Can_00443]. If it returns false, the L-PDU is not processed further according to the document passage (R25-11) SWS CANDriver p. 77.

Events are detected via interrupt or by polling status flags. Pure polling operation without any interrupts must be configurable. In polling operation, the main functions invoke the same callbacks, only from task context instead of ISR context SWS CANDriver p. 41. Each main function polls one type of event:

  • Can_MainFunction_Write: TX confirmations [SWS_Can_00225]
  • Can_MainFunction_Read: RX indications [SWS_Can_00226]
  • Can_MainFunction_BusOff: bus-off events [SWS_Can_00227]
  • Can_MainFunction_Wakeup: wakeup events [SWS_Can_00228]
  • Can_MainFunction_Mode: mode transitions [SWS_Can_00368]

The R20-11 descriptions of Read and Write mention only the case POLLING [SWS_Can_00225] [SWS_Can_00226]. The document passages of later releases add MIXED; then only objects with CanHardwareObjectUsesPolling = TRUE are polled SWS CANDriver p. 81 SWS CANDriver p. 79. The R20-11 requirements do not support this extension. If multiple periods are configured via CanMainFunctionRWPeriods, the function names receive the suffix _<ShortName> [SWS_Can_00441] SWS CANDriver p. 122. In the absence of any polling, a main function may be implemented as an empty define SWS CANDriver p. 81.

Sequence diagram: reception in polling mode with ID normalization, optional L-PDU callout, and forwarding to CanIf. Sources: [SWS_Can_00226], [SWS_Can_00443], SWS CANInterface p. 153, SWS CANDriver p. 43

Sleep, wakeup, and interrupt control

The driver handles only wakeups detected by the controller itself, not those via the transceiver SWS CANDriver p. 45. Upon a hardware wakeup, the controller transitions from SLEEP to STOPPED. The triggering L-PDU is not processed further. EcuM_CheckWakeup is called in the interrupt or in Can_MainFunction_Wakeup, with the source configured via CanWakeupSourceRef SWS CANDriver p. 35. EcuM then calls Can_CheckWakeup via CanIf. This function reports a detected wakeup via EcuM_SetWakeupEvent [SWS_Can_00360] SWS CANDriver p. 63. EcuM and CanIf validate against spurious wakeups without driver involvement SWS CANDriver p. 45.

Can_DisableControllerInterrupts and Can_EnableControllerInterrupts are reentrant and act in a nested manner. After n disable calls, n enable calls are necessary. An enable without a preceding disable has no effect [SWS_Can_00231] [SWS_Can_00232] SWS CANDriver p. 61 SWS CANDriver p. 62.

Sequence diagram: bus wakeup from SLEEP, notification to EcuM, and query via CanIf with Can_CheckWakeup. Sources: [SWS_Can_00360], [SWS_Can_00228], SWS CANDriver p. 45, SWS CANDriver p. 35

Configuration sets, partitions, and instance reference

Can_Init receives a pointer to Can_ConfigType. This hardware-specific structure contains settings for all controllers and references to the individual controller configurations [SWS_Can_00223] [SWS_Can_00413]. The module supports VARIANT-PRE-COMPILE and VARIANT-POST-BUILD SWS CANDriver p. 96. In the post-build example, one of several configuration sets is selected when calling Can_Init EXP LayeredSoftwareArchitecture p. 120. For each controller, CanController defines, among other things, CanRxProcessing, CanTxProcessing, CanBusoffProcessing, CanWakeupProcessing, and at least one CanControllerBaudrateConfig SWS CANDriver p. 101.

In multi-partition systems, the module operates in each partition as an independent instance. An API call takes effect only in its own partition [SWS_Can_CONSTR_00508]. Three rules apply to partition assignment:

  • The partitions in CanControllerEcucPartitionRef must be a subset of the partitions in CanEcucPartitionRef [SWS_Can_CONSTR_00509].
  • Controller and transceiver channel of a communication channel reference the same partition [SWS_Can_CONSTR_00510].
  • The driver rejects unsupported assignments [SWS_Can_00507].

Multiple Can modules in an ECU are distinguished by a modified function prefix SWS CANDriver p. 51.

Behavior in the event of an error

When development error detection is active, the driver reports development errors to the DET. The codes range from CAN_E_PARAM_POINTER (0x01) via CAN_E_UNINIT (0x05) and CAN_E_TRANSITION (0x06) to CAN_E_INIT_FAILED (0x09) [SWS_Can_91019]. After returning from the DET, the function returns immediately; functions with a return value then return E_NOT_OK SWS CANDriver p. 48. Some examples:

  • Can_DeInit reports CAN_E_TRANSITION as long as a controller is in STARTED [SWS_Can_91012] SWS CANDriver p. 59.
  • CAN_E_TRANSITION is intended for invalid transitions in Can_SetControllerMode. In production code, its behavior is undefined SWS CANDriver p. 30 SWS CANDriver p. 32.

CAN_E_DATALOST is defined as a runtime error for lost received messages [SWS_Can_91020]. It is presumed to be reported via the required Det_ReportRuntimeError [SWS_Can_00234].

If a controller enters bus-off, it transitions from STARTED to STOPPED. The driver performs no hardware recovery. It reports the event via interrupt or in Can_MainFunction_BusOff via CanIf_ControllerBusOff [SWS_Can_00227] SWS CANDriver p. 35. Recovery is handled by CanSM, which CanIf informs with CanSM_ControllerBusOff SWS CANInterface p. 138. Interpretation: The restart is presumed to occur via Can_SetControllerMode(CAN_CS_STARTED) again, which reloads the configuration in the process SWS CANDriver p. 59.

Sequence diagram: detection and reporting of a bus-off up to the CanSM. The restart marked as an interpretation is not explicitly supported by evidence. Sources: [SWS_Can_00227], [SWS_Can_00234], SWS CANDriver p. 35, SWS CANInterface p. 138

For diagnostics, Can_GetControllerErrorState returns the error state: ACTIVE, PASSIVE, or BUSOFF [SWS_Can_91004] [SWS_Can_91003]. The Rx and Tx error counters can also be queried. If the controller does not provide them, the functions return E_NOT_OK. Because the hardware maintains the counters asynchronously, the values are unsuitable for assumptions about the bus state [SWS_Can_00511] [SWS_Can_00516] SWS CANDriver p. 67. Can_ErrorType describes a superset of typical hardware error types, from bit errors to bus-lock [SWS_Can_91021].

To handle non-responsive hardware, the driver uses an OsCounter for timeouts SWS CANDriver p. 23. If a mode change does not take effect within CanTimeoutDuration, Can_SetControllerMode exits the function instead of blocking SWS CANDriver p. 33. If a bus wakeup occurs during the transition to sleep mode, Can_SetControllerMode(CAN_CS_STOPPED) returns E_NOT_OK SWS CANDriver p. 35.

The synchronous, non-reentrant function Can_Init initializes the entire CAN driver module as well as the associated hardware units according to the passed configuration [SWS_Can_00223].

Usage and Call Context

The call to Can_Init is mandatory during the startup phase of the ECU by the ECU State Manager, before any other function of the CAN driver may be called [SWS_Can_91012]. As a parameter, the function takes a pointer to the driver configuration (const Can_ConfigType*) via Config and returns no value [SWS_Can_00223].

Initialization Scope and State Transitions

As part of the initialization, the function sets all required hardware registers and initializes all CAN controllers AUTOSAR_SWS_CANDriver p. 33:

  • Initialization of static variables and internal flags [SWS_Can_91012],
  • Configuration of common settings for the complete CAN hardware unit [SWS_Can_91012],
  • Controller-specific settings for each individual CAN controller [SWS_Can_91012].

The function call triggers state transitions of the CAN hardware AUTOSAR_SWS_CANDriver p. 10, where Can_Init performs the register configuration to transition the controllers into the intended base state [SWS_Can_91010] AUTOSAR_SWS_CANDriver p. 36.

Concurrency and Limitations

Since Can_Init is specified as non-reentrant, no parallel or repeated call may take place during an ongoing initialization [SWS_Can_00223]. Furthermore, certain global settings of the hardware unit can only be set within Can_Init AUTOSAR_SWS_CANDriver p. 33.

The function Can_DeInit serves to deinitialize the CAN driver module ([SWS_Can_91002]). The call initiates a software-controlled state transition (AUTOSAR_SWS_CANDriver p. 10; AUTOSAR_SWS_CANDriver p. 41). In doing so, Can_DeInit changes the module state (AUTOSAR_SWS_CANDriver p. 33) and resets all CAN controllers (AUTOSAR_SWS_CANDriver p. 41).

Strict preconditions and sequencing requirements regarding hardware and module states apply to the execution:

  • Likewise, the error CAN_E_TRANSITION is raised if a CAN controller remains in a state that prevents deinitialization (AUTOSAR_SWS_CANDriver p. 61). Interpretation: The driver presumably requires a stopped state of all controllers prior to the transition.

Interaction

The error and transition behavior reflects the cleaned-up driver workflows, according to which invalid state transitions are intercepted uniformly ([SWS_Can_00441]).

The function Can_SetControllerMode (provided via Can.h with service ID 0x03) performs software-triggered state transitions of the CAN controller state machine ([SWS_Can_00230], AUTOSAR_SWS_CANDriver p. 35). It performs the hardware-related register settings to bring about the transitions between the basic controller states UNINIT, STOPPED, STARTED, and SLEEP ([SWS_Can_91010], AUTOSAR_SWS_CANDriver §7.3 “CAN Controller State Machine”).

Usage and Semantics

The call is made with the parameter Controller to identify the CAN controller and Transition of type Can_ControllerStateType to specify the desired state transition ([SWS_Can_00230]). The service is defined as asynchronous and non-reentrant (Non Reentrant) ([SWS_Can_00230]). A return value of E_OK confirms that the request was accepted; E_NOT_OK indicates that the request was rejected and a development error is present ([SWS_Can_00230], [SWS_Can_00441]).

Sequence and Interaction

After setting the register configuration, Can_SetControllerMode is exited again (AUTOSAR_SWS_CANDriver p. 38). Since the Can module does not store the hardware state changes itself ([SWS_Can_91010]), the cyclic function Can_Mainfunction_Mode presumably handles the asynchronous completion or verification of the transition initiated by Can_SetControllerMode (AUTOSAR_SWS_CANDriver p. 38).

Types

Can_ConfigType type

This is the type of the external data structure containing the overall initialization data for the CAN driver and SFR settings affecting all controllers. Furthermore it contains pointers to controller configuration structures. The contents of the initializ ation data structure are CAN hardware specific.

Can_ControllerStateType type

States that are used by the several Controller Mode functions.

Can_ErrorStateType type

Error states of a CAN controller.

Can_ErrorType type

The enumeration represents a superset of CAN Error Types which typical CAN HW is able to report. That means not all CAN HW will be able to support the complete set.

Can_HwHandleType type

Represents the hardware object handles of a CAN hardware unit. For CAN hardware units with more than 255 HW objects use extended range.

Can_HwType type

This type defines a data structure which clearly provides an Hardware Object Handle including its corresponding CAN Controller and therefore Can Drv as well as the specific Can Id.

Can_IdType type

Represents the Identifier of an L - PDU. The two most significant bits specify the frame type: 00 CAN message with Standard CAN ID 01 CAN FD frame with Standard CAN ID 10 CAN message with Extended CAN ID 11 CAN FD frame with Extended CAN ID

Can_PduType type
