Provides cryptographic primitives and key management for the hardware-oriented AUTOSAR Classic crypto stack.

As an MCAL module, the Crypto Driver provides hardware-oriented cryptographic computations as well as key management for the AUTOSAR Classic crypto stack (EXP_UtilizationOfCryptoServices p. 8). It encapsulates hardware security modules (HSM) or software libraries in Driver Objects and processes synchronous as well as asynchronous jobs via the central interface Crypto_ProcessJob ([SWS_Crypto_91003]). Key accesses are subject to configurable rights, and persistent storage in the NVM is triggered only upon successful key validation (SWS_CryptoDriver p. 37).

As an MCAL driver, the Crypto Driver (module Crypto) forms the lowest foundation of the AUTOSAR Classic crypto stack and interfaces hardware security modules (HSM), crypto accelerators, and software routines directly to the crypto interface (CryIf) (EXP_UtilizationOfCryptoServices p. 8, SWS_CryptoDriver p. 15). In multi-implementations, instances are named vendor-specifically according to the schema Crypto_<vi>_<ai> ([SWS_Crypto_00012]). Initialization is performed synchronously via [SWS_Crypto_91000] with a mandatory null pointer for [SWS_Crypto_91016] ([SWS_Crypto_00215]). Internally, the module encapsulates independent computing units in Crypto Driver Objects, each of which can execute exactly one job at a time ([SWS_Crypto_00014]), while n objects enable parallel computations ([SWS_Crypto_00117]). Driver Object 0 acts as the central random number generator for internal demands of all other driver objects of the same instance ([SWS_Crypto_00224], [SWS_Crypto_00225]).

Cryptographic jobs are processed via [SWS_Crypto_91003] (Crypto_ProcessJob), where a mode bitfield (START, UPDATE, FINISH) unifies streaming and overall calls (SWS_CryptoDriver p. 25, [SWS_Crypto_00017]). Asynchronous jobs are calculated via the cyclic function [SWS_Crypto_91012] (Crypto_MainFunction) and reported to CryIf via CRYIF_CallbackNotification upon completion ([SWS_Crypto_00027], [SWS_Crypto_00028]). Running jobs can be canceled synchronously using [SWS_Crypto_00122] ([SWS_Crypto_00183], [SWS_Crypto_00214]), while direct buffer redirections to key elements reduce copy operations ([SWS_Crypto_00203], [SWS_Crypto_00221]).

Sequence diagram: Asynchronous processing sequence via Crypto_ProcessJob, cycle in Crypto_MainFunction, and feedback via CRYIF_CallbackNotification. Sources: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

Key management encompasses setting ([SWS_Crypto_91004]), reading ([SWS_Crypto_91006]), copying ([SWS_Crypto_00155], [SWS_Crypto_91015]), generating ([SWS_Crypto_91007]), and deriving ([SWS_Crypto_91008]) key elements under strict access rights control ([SWS_Crypto_00219], [SWS_Crypto_00220]). For consistency reasons, persistence in the Non-Volatile RAM Manager (NvM) is never triggered during single writes, but exclusively during key validation via [SWS_Crypto_91014] (Crypto_KeySetValid) (SWS_CryptoDriver p. 37, [SWS_Crypto_91025]). In multi-core environments, the module operates in isolation in each partition ([SWS_Crypto_CONSTR_00001]), whereby HSM objects may be assigned to at most one partition ([SWS_Crypto_CONSTR_00003]).

Role and System Boundaries of the Crypto Driver in the Classic Crypto Stack

The Crypto Driver (module abbreviation Crypto) is located at the lowest layer of the AUTOSAR Classic basic software in the Microcontroller Abstraction Layer (MCAL) (EXP_UtilizationOfCryptoServices p. 8). It is located directly below the crypto interface (Crypto Interface, CryIf) and serves the Crypto Service Manager (CSM) via this interface (SWS_CryptoDriver p. 15). Its main task consists in encapsulating the concrete cryptographic processing units—be they hardware security modules (Hardware Security Modules, HSM), dedicated crypto accelerators such as AES engines, or pure software libraries (SWS_CryptoDriver p. 15). In addition to the actual computation of cryptographic primitives, the scope of functions includes the storage, configuration, and management of cryptographic keys (SWS_CryptoDriver p. 24).

Multiple driver instances from different vendors can coexist in an ECU; in this case, file, API, and configuration identifiers are uniquely differentiated by a vendor-specific infix according to the schema Crypto_<vi>_<ai> ([SWS_Crypto_00012]). Initialization of the module is performed via the function [SWS_Crypto_91000] (Crypto_Init). As a special rule for the configuration pointer of type [SWS_Crypto_91016] (Crypto_ConfigType), it must always be passed as a null pointer ([SWS_Crypto_00215]). Version information can be queried synchronously via [SWS_Crypto_91001] (Crypto_GetVersionInfo), where passing a null pointer with active development detection is reported to DET with the error CRYPTO_E_PARAM_POINTER (SWS_CryptoDriver p. 56).

Management of Crypto Driver Objects and Hardware Abstraction

Each instance of the Crypto Driver is divided internally into one or more logical driver objects (Crypto Driver Objects) (SWS_CryptoDriver p. 15). A Crypto Driver Object forms the functional endpoint of a crypto channel and represents an independent hardware processing unit or a software implementation (SWS_CryptoDriver p. 15). Inherently, a single Driver Object can actively execute only exactly one job at any given time ([SWS_Crypto_00014]). Consequently, a Crypto Driver with n Driver Objects has the capacity to compute n crypto jobs in parallel ([SWS_Crypto_00117]). Which mathematical and security-relevant primitives are supported is determined by the capabilities of the assigned object ([SWS_Crypto_00013]).

If a driver object requires internal random numbers (for instance, to calculate public values in the context of key exchange via [SWS_Crypto_91009]) and does not have its own random number generator, it mandatorily relies on Crypto Driver Object 0 of the same driver ([SWS_Crypto_00224], [SWS_Crypto_00225]). Under no circumstances may driver objects address random number generators of external crypto driver instances ([SWS_Crypto_00226]). Interpretation: Driver Object 0 thus acts as a central internal reference random number generator for all further driver objects of the same partition.

Job Processing Between Synchronous Direct Call and Asynchronous Streaming

Cryptographic processing is passed to the module as job structures of type Crypto_JobType via the central interface [SWS_Crypto_91003] (Crypto_ProcessJob) ([SWS_Crypto_00042], AUTOSAR_CP_SWS_CryptoServiceManager p. 21). The interface combines block-based overall calls and continuous data streaming via a mode-specific bitfield: the operations START, UPDATE, and FINISH can be passed individually or combined (SWS_CryptoDriver p. 25). Setting the START flag marks a new job and cancels all previous instances of the same job ([SWS_Crypto_00017]). When passed in combination, the steps are always executed in the fixed order START, UPDATE, and finally FINISH (SWS_CryptoDriver p. 25).

Whether a job is processed synchronously or asynchronously is part of the metadata configuration in Crypto_JobType (SWS_CryptoDriver p. 26). In asynchronous mode, [SWS_Crypto_91003] only accepts the job data; the actual execution is triggered or processed by the cyclic main function [SWS_Crypto_91012] (Crypto_MainFunction) ([SWS_Crypto_00027], [SWS_Crypto_91012]). After completion of the asynchronous calculation, the Crypto Driver mandatorily notifies the upper layer CryIf by calling the callback function CRYIF_CallbackNotification, returning the status and result pointers ([SWS_Crypto_00028]). Interpretation: Synchronous calls, on the other hand, execute the crypto operation blockingly in the context of the caller without being decoupled via the main function.

Sequence diagram: Asynchronous processing sequence via Crypto_ProcessJob, cycle in Crypto_MainFunction, and feedback via CRYIF_CallbackNotification. Sources: SWS_Crypto_91003, SWS_Crypto_00027, SWS_Crypto_00028, SWS_Crypto_91012

Running or pending crypto jobs can be canceled via the function [SWS_Crypto_00122] (Crypto_CancelJob). If the requested job is not in active processing by the driver object, it is removed immediately and the call returns E_OK ([SWS_Crypto_00214]). However, if the hardware cannot interrupt the active computation process immediately, the API acknowledges the attempt with CRYPTO_E_JOB_CANCELED, and the cancellation is completed at the next reachable step ([SWS_Crypto_00183]).

Sequence diagram: Synchronous cancellation of cryptographic jobs via Crypto_CancelJob with case distinction during active hardware execution. Sources: SWS_Crypto_00122, SWS_Crypto_00183, SWS_Crypto_00214

To avoid unnecessary copy operations between application and hardware memories, the Crypto Driver supports direct buffer redirection (Job Redirection): input and output data can be referenced directly to internal key elements via jobRedirectionInfoRef ([SWS_Crypto_00203], [SWS_Crypto_00204]). To prevent data leaks, strict rights checks apply: for input redirections for encryption and decryption services, the key element must have at least the right CRYPTO_RA_ENCRYPTED; for pure read redirections, at least CRYPTO_RA_INTERNAL_COPY is required ([SWS_Crypto_00221]).

Key Management, Access Rights, and Cryptographic Key Operations

In the Crypto Driver, a logical key (Key) consists of one or more key elements (Key Elements) that hold the actual key material, initialization vectors (IV), random seeds, or SHE proofs (Proof) (SWS_CryptoDriver p. 28). Access to each individual element is strictly regulated: read and write accesses are monitored based on configured rights hierarchies (e.g., CRYPTO_RA_ALLOWED, CRYPTO_RA_ENCRYPTED, CRYPTO_RA_INTERNAL_COPY), where a smaller enumeration value represents a higher-level access right (SWS_CryptoDriver p. 28, [SWS_Crypto_00219]). Direct read operations are only permitted for CRYPTO_RA_ALLOWED or CRYPTO_RA_ENCRYPTED ([SWS_Crypto_00222]); write accesses require at least CRYPTO_WA_ALLOWED or CRYPTO_WA_ENCRYPTED ([SWS_Crypto_00223]). When copying, the source element must have at least CRYPTO_RA_INTERNAL_COPY and must not have lower rights than the target element ([SWS_Crypto_00220]).

For direct manipulation of keys and their elements, the Crypto Driver provides a series of synchronous APIs: setting and reading data is performed via [SWS_Crypto_91004] (Crypto_KeyElementSet) and [SWS_Crypto_91006] (Crypto_KeyElementGet), respectively. Existing element identifiers of a key can be determined via [SWS_Crypto_00160] (Crypto_KeyElementIdsGet). Complete keys or individual elements are duplicated using [SWS_Crypto_00155] (Crypto_KeyCopy) or [SWS_Crypto_00148] (Crypto_KeyElementCopy). For partial copies, [SWS_Crypto_91015] (Crypto_KeyElementCopyPartial) exists, which enforces precise length and offset checks on source and target buffers ([SWS_Crypto_00207], [SWS_Crypto_00208], [SWS_Crypto_00209]) and dynamically adapts the target length ([SWS_Crypto_00210], [SWS_Crypto_00211]).

In addition, the module supports complex key operations: key generation is performed via [SWS_Crypto_91007] (Crypto_KeyGenerate) based on entropy data previously initialized using [SWS_Crypto_91013] (Crypto_RandomSeed). Derivation of new key materials is handled by [SWS_Crypto_91008] (Crypto_KeyDerive). For Diffie-Hellman key exchange protocols, the functions [SWS_Crypto_91009] (Crypto_KeyExchangeCalcPubVal) for generating the public value and [SWS_Crypto_91010] (Crypto_KeyExchangeCalcSecret) for determining the shared secret are available (SWS_CryptoServiceManager p. 70).

Each logical key maintains a status that can be queried via [SWS_Crypto_91019] (Crypto_KeyGetStatus). Newly written keys are initially in the state invalid and are released as valid only after successful validation using [SWS_Crypto_91014] (Crypto_KeySetValid), whereas [SWS_Crypto_91020] (Crypto_KeySetInvalid) explicitly locks the key. Regarding data formats, the driver processes asymmetric keys according to RFC 5958 in ASN.1-PKCS#8 encoding ([SWS_Crypto_00184]), RSA key structures according to RFC 8017 with fixed algorithm OID 1.2.840.113549.1.1.1 ([SWS_Crypto_00185], [SWS_Crypto_00186], [SWS_Crypto_00187], [SWS_Crypto_00188]), as well as ECC curve data (NIST, Brainpool, ED25519) in little-endian point coordinates ([SWS_Crypto_00189], [SWS_Crypto_00190], [SWS_Crypto_00191], [SWS_Crypto_00192], [SWS_Crypto_00193]). Hardware-oriented SHE keys are passed in the format M1M2M3; their verification proof M4M5 can be read temporarily in key element 2 immediately after validation ([SWS_Crypto_00255]).

Persistence of Key Elements via the Non-Volatile RAM Manager

If keys are to be retained non-volatilely across power cycles, the Crypto Driver is connected to the Non-Volatile RAM Manager (NvM) (SWS_CryptoDriver p. 35, AUTOSAR_CP_SWS_CryptoDriver p. 37). A central architectural principle states that write operations to the NvM are never initiated directly when filling an individual element via Crypto_KeyElementSet (SWS_CryptoDriver p. 37). Instead, persistence is initiated exclusively by the status validation KEYSETVALID via [SWS_Crypto_91014] (Crypto_KeySetValid) or an equivalent crypto job (SWS_CryptoDriver p. 37). This guarantees that mutually dependent key elements are checked consistently and stored in a single NvM write access, which saves flash cycles (SWS_CryptoDriver p. 37).

Interaction with the NvM takes place via dedicated callback interfaces: during ECU startup, the NvM provides the initialization block via [SWS_Crypto_91023] (Crypto_<vi>_<ai>_NvBlock_Init_<NvBlock>). Loading persisted data from the RAM mirror of the NvM is performed via [SWS_Crypto_91024] (Crypto_<vi>_<ai>_NvBlock_ReadFrom_<NvBlock>). Prior to writing, the NvM calls [SWS_Crypto_91025] (Crypto_<vi>_<ai>_NvBlock_WriteTo_<NvBlock>) so that the crypto driver copies its internal key data into the NvM buffer; completion of the asynchronous block transfer is reported via [SWS_Crypto_91026] (Crypto_<vi>_<ai>_NvBlock_Callback_<NvBlock>). For control purposes, the driver uses the NvM services NvM_SetRamBlockStatus and NvM_WriteBlock ([SWS_Crypto_91017]). If loading a persistent key fails during startup, the driver mandatorily marks this key as invalid ([SWS_Crypto_00198]).

Sequence diagram: Persistence of key elements into NVM upon validation via NvM_WriteBlock and driver-specific callbacks. Sources: SWS_Crypto_00242, SWS_Crypto_91017, SWS_Crypto_91025, SWS_Crypto_91026

Partitioning and Multi-Core Operating Rules

To efficiently distribute crypto operations across multi-core systems, the crypto stack can be distributed over multiple software partitions (BSWDistributionGuide p. 59). The Crypto module operates in each partition as a completely independent instance: each API call processes data exclusively within the partition in which it was issued ([SWS_Crypto_CONSTR_00001]). Partitioning of the driver objects is subject to strict configuration rules: the partitions referenced by CryptoDriverObjectEcucPartitionRef must mandatorily form a proper subset of the partitions assigned to the module (CryptoEcucPartitionRef) ([SWS_Crypto_CONSTR_00002]). If a Crypto Driver Object is coupled to a hardware security module (HSM), it may be assigned to exactly 0 or 1 partition for reasons of hardware isolation ([SWS_Crypto_CONSTR_00003]).

Behavior in the event of an error

The Crypto Driver implements a two-stage error monitoring consisting of development detection (Development Errors) and runtime errors (Runtime Errors). With development error detection (DET) enabled, formal interface violations are transmitted to Det_ReportError ([SWS_Crypto_91017]). These include calls prior to driver initialization (CRYPTO_E_UNINIT, 0x00) ([SWS_Crypto_00040], [SWS_Crypto_00196], [SWS_Crypto_00205]), invalid initialization data (CRYPTO_E_INIT_FAILED, 0x01), and inadmissible null pointers (CRYPTO_E_PARAM_POINTER, 0x02) ([SWS_Crypto_00040]). If key identifiers or target key handles are outside the permissible value range, the driver aborts the call with E_NOT_OK and reports CRYPTO_E_PARAM_HANDLE (0x04) ([SWS_Crypto_00040], [SWS_Crypto_00180], [SWS_Crypto_00197], [SWS_Crypto_00202], [SWS_Crypto_00217]).

If the passed input or output buffers are insufficient for an operation, execution is refused and, with DET active, the error CRYPTO_E_SMALL_BUFFER is reported ([SWS_Crypto_00195], SWS_CryptoDriver p. 49). A normative exception applies to the services CRYPTO_HASH and CRYPTO_MACGENERATE: If the output buffer is smaller than the native hash or MAC length here, the result is not discarded, but written to the buffer truncated in the form of the most significant bits (MSB) ([SWS_Crypto_00065]). In operational mode, the driver reports specific runtime errors via the return value: Depletion of random entropy is acknowledged by [SWS_Crypto_91003] with the return code CRYPTO_E_ENTROPY_EXHAUSTED and reports the runtime error CRYPTO_E_RE_ENTROPY_EXHAUSTED (0x03) ([SWS_Crypto_00141], [SWS_Crypto_00194], [SWS_Crypto_91018]). If read or write accesses to the NVM fail, CRYPTO_E_RE_NVM_ACCESS_FAILED (0x04) is signaled ([SWS_Crypto_00194]). Further standardized API return values are CRYPTO_E_BUSY, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, CRYPTO_E_KEY_NOT_VALID, CRYPTO_E_KEY_SIZE_MISMATCH, and CRYPTO_E_KEY_EMPTY ([SWS_Crypto_00155], [SWS_Crypto_00207], [SWS_Crypto_91018]).

The synchronous function Crypto_CancelJob removes a passed job from the queue and cancels its processing if possible [SWS_Crypto_00122]. Upon the call, the identifier of the Crypto Driver Object (objectId) and a pointer to the job configuration (job) are passed [SWS_Crypto_00122].

The return values signal the result of the cancellation attempt:
