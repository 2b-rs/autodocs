Role of the Crypto Driver in the Crypto Stack

The Crypto Driver is located in the Microcontroller Abstraction Layer below the Crypto Interface (CryIf) and Crypto Service Manager (CSM). It provides a generic interface for synchronous and asynchronous cryptographic primitives and handles key storage, key configuration, and key management. An ECU integrates exactly one CSM and one CryIf. However, the CryIf can address multiple Crypto Drivers SWS_CryptoDriver p. 15. The specification summarizes the service offering into two services: crypto services and key management SWS_CryptoDriver p. 24.

The central execution unit is the Crypto Driver Object. It represents an independent crypto entity, such as an AES accelerator on an HSM or a software implementation for RSA. Each Crypto Driver Object is the endpoint of a crypto channel SWS_CryptoDriver p. 15. An object always processes only one job at a time. A driver with n objects can process n jobs in parallel, with jobs in the queue not counting as "in processing" (citation from version R25-11) SWS_CryptoDriver p. 23. Therefore, Crypto_ProcessJob and Crypto_CancelJob address the object via objectId [SWS_Crypto_91003] [SWS_Crypto_00122].

Context diagram: The Crypto Driver serves the CryIf via Crypto Driver Objects and uses NvM, DET, and SchM as neighboring modules. Sources: SWS_CryptoDriver p. 15, AUTOSAR_CP_SWS_CryptoServiceManager p. 28, [SWS_Crypto_91017], [SWS_Crypto_91012]

Startup, Instantiation, and Partitioning

Crypto_Init is synchronous and non-reentrant and initializes the driver [SWS_Crypto_91000]. The parameter configPtr must always be a null pointer [SWS_Crypto_00215]. Interpretation: The configuration is therefore not selected at runtime, but is likely bound statically in the driver. This is consistent with the content of Crypto_ConfigType being implementation-specific [SWS_Crypto_91016]. During startup, the driver reads back persistent key values SWS_CryptoDriver p. 35. If a value cannot be loaded, it sets the affected key to invalid [SWS_Crypto_00198]. In case of a null pointer, Crypto_GetVersionInfo reports CRYPTO_E_PARAM_POINTER to the DET [SWS_Crypto_91001] SWS_CryptoDriver p. 56.

If multiple driver instances exist in an ECU, file names, API names, and published parameters must differ according to the scheme Crypto_<vi>_<ai> SWS_CryptoDriver p. 23. The NvM callbacks also carry this prefix, such as Crypto_<vi>_<ai>_NvBlock_Init_<NvBlock> [SWS_Crypto_91023]. If the driver requires random numbers internally, for instance for Crypto_KeyExchangeCalcPubVal, Crypto Driver Object 0 must be configured for this purpose [SWS_Crypto_00224]. Objects without their own default random number generator obtain their random numbers from Object 0 [SWS_Crypto_00225]. In doing so, they only call generators of their own driver [SWS_Crypto_00226].

In case of partitioning, the driver operates as an independent instance in each partition. An API call only affects the partition in which it occurs [SWS_Crypto_CONSTR_00001]. The partitions of a Crypto Driver Object must be a subset of the driver partitions [SWS_Crypto_CONSTR_00002]. An object for an HSM shall be assigned to at most one partition [SWS_Crypto_CONSTR_00003]. The BSW Distribution Guide justifies this distribution with load balancing per crypto instance BSWDistributionGuide p. 59.

Job Processing via Crypto_ProcessJob

All crypto services run via the reentrant function Crypto_ProcessJob(objectId, job). Whether a job runs synchronously or asynchronously depends on its configuration [SWS_Crypto_91003]. This information is contained in the Crypto_JobType SWS_CryptoDriver p. 26. The driver imports the job types from Crypto_GeneralTypes.h of the CSM [SWS_Crypto_00042].

In the asynchronous case, the interface function passes only the necessary information to the primitive. The calculation can be triggered by the Main Function. After completion, the driver notifies the CryIf via CRYIF_CallbackNotification and passes the job and result SWS_CryptoDriver p. 27. Crypto_MainFunction is called cyclically when asynchronous processing is configured and job queues exist [SWS_Crypto_91012].

Sequence diagram: An asynchronous job returns immediately, is computed in the Main Function, and is completed via callback. The forwarding from the CryIf to the CSM is marked as an interpretation. Sources: [SWS_Crypto_91003], [SWS_Crypto_91012], SWS_CryptoDriver p. 27

The job contains a flag field with the operation modes START, UPDATE, and FINISH. The flags can be combined and are then always executed in this order. START cancels all previous requests of the same job SWS_CryptoDriver p. 25. A single call corresponds to the combination START|UPDATE|FINISH SWS_CryptoInterface p. 22. For key management jobs, the specification recommends CRYPTO_OPERATIONMODE_SINGLECALL SWS_CryptoDriver p. 66.

Activity diagram: The flags START, UPDATE, and FINISH are evaluated in a fixed order. Sources: SWS_CryptoDriver p. 25, SWS_CryptoInterface p. 22

If job->jobRedirectionInfoRef is set and the associated configuration bit is active, the driver uses key elements instead of buffers as input or output [SWS_Crypto_00203] [SWS_Crypto_00204]. Minimum permissions apply for this: For example, an input element requires CRYPTO_RA_INTERNAL_COPY "or lower" [SWS_Crypto_00221]. On the CSM side, this corresponds to the configuration container CsmInOutRedirections AUTOSAR_CP_SWS_CryptoServiceManager p. 167.

Keys, Key Elements, and Access Rights

A key consists of one or more key elements. Examples are the key material, an initialization vector, or a seed state. Each element carries read and write rights as enumeration values whose numerical values form a hierarchy SWS_CryptoDriver p. 28. These rights must be observed during direct read and write access [SWS_Crypto_00219]. Interpretation: The requirements to execute "this operation" only in case of CRYPTO_RA_ALLOWED/CRYPTO_RA_ENCRYPTED [SWS_Crypto_00222] or CRYPTO_WA_ALLOWED/CRYPTO_WA_ENCRYPTED [SWS_Crypto_00223] presumably refer to Crypto_KeyElementGet [SWS_Crypto_91006] and Crypto_KeyElementSet [SWS_Crypto_91004]. Jobs, on the other hand, use their assigned elements without permission checks. Redirection is excluded [SWS_Crypto_00221].

Crypto_KeyElementIdsGet lists the existing element IDs of a key. Upon call, keyElementIdsLengthPtr contains the buffer size, and after completion, the actual count [SWS_Crypto_00160] SWS_CryptoDriver p. 78. Two functions are available for copying:

  • Crypto_KeyCopy copies a key with all elements within the same driver [SWS_Crypto_00155].
  • Crypto_KeyElementCopy copies a single element [SWS_Crypto_00148].

The source element must have at least the same rights as the destination. A source key requires at least CRYPTO_RA_INTERNAL_COPY [SWS_Crypto_00220]. If elements are mapped directly to flash, the synchronous call can take significantly longer SWS_CryptoDriver p. 77.

Crypto_KeyElementCopyPartial copies an excerpt with source and target offset [SWS_Crypto_91015]. The function returns CRYPTO_E_KEY_SIZE_MISMATCH if the source element is shorter than offset plus length [SWS_Crypto_00207] or if the maximum buffer of the target is insufficient [SWS_Crypto_00208]. Otherwise, it copies [SWS_Crypto_00209] and adjusts the target length if necessary [SWS_Crypto_00210] [SWS_Crypto_00211].

Activity diagram: Length checks and length adjustment during partial copying. Both size checks lead to the same return value, so their order is irrelevant. Sources: [SWS_Crypto_00207], [SWS_Crypto_00208], [SWS_Crypto_00209], [SWS_Crypto_00210], [SWS_Crypto_00211]

The following functions are available for the generation and derivation of key material:

  • Crypto_KeyGenerate generates new key material [SWS_Crypto_91007].
  • Crypto_KeyDerive derives a key into targetCryptoKeyId [SWS_Crypto_91008].
  • Crypto_RandomSeed feeds the seed [SWS_Crypto_91013].
  • Crypto_KeyExchangeCalcPubVal calculates its own public value for key exchange [SWS_Crypto_91009].
  • Crypto_KeyExchangeCalcSecret stores the shared secret as an element of the same key [SWS_Crypto_91010] SWS_CryptoDriver p. 84.

Key State and Persistence in NvM

Each key is either valid or invalid:

  • Crypto_KeySetValid sets it to valid [SWS_Crypto_91014].
  • Crypto_KeySetInvalid sets it to invalid [SWS_Crypto_91020].
  • Crypto_KeyGetStatus returns the current state [SWS_Crypto_91019].

According to the change history, the functions for querying and invalidating the key state were added with R20-11 SWS_CryptoDriver p. 2. If a key is invalid, services such as Crypto_KeyGenerate or Crypto_KeyExchangeCalcSecret return the value CRYPTO_E_KEY_NOT_VALID SWS_CryptoDriver p. 80 SWS_CryptoDriver p. 84.

State diagram: Transitions between valid and invalid as well as invalidation during startup. The initial state after successful loading is not specified in the references and is therefore not shown. Sources: [SWS_Crypto_91014], [SWS_Crypto_91020], [SWS_Crypto_91019], [SWS_Crypto_00198]

The handling of key elements in the NvM is also new in R20-11 SWS_CryptoDriver p. 2. A key references at most one NvM block, and its KeyType comprises one or more KeyElements AUTOSAR_SWS_CryptoDriver p. 32. The driver writes the elements during validation and reads them during initialization SWS_CryptoDriver p. 35. Version R25-11 clarifies that only KEYSETVALID triggers storage, but not Crypto_KeyElementSet. This allows the driver to verify interdependent elements together and save them in a single write operation SWS_CryptoDriver p. 37.

The driver provides four callbacks for data exchange with the NvM:

  • Init initializes the block [SWS_Crypto_91023].
  • ReadFrom copies from the NvM mirror into the internal buffer [SWS_Crypto_91024].
  • WriteTo fills the mirror shortly before writing [SWS_Crypto_91025].
  • Callback reports the end of an asynchronous single block request [SWS_Crypto_91026].

Optionally, the driver uses NvM_SetRamBlockStatus and NvM_WriteBlock [SWS_Crypto_91017].

Sequence diagram: Key persistence during startup and during validation. Which NvM function triggers the write job is marked as an interpretation. Sources: [SWS_Crypto_91024], [SWS_Crypto_91025], [SWS_Crypto_91026], [SWS_Crypto_91017], SWS_CryptoDriver p. 37

Cancellation of Running Jobs

Crypto_CancelJob(objectId, job) is synchronous and reentrant, though not for the same Crypto Driver Object [SWS_Crypto_00122]. The return value depends on the processing state:

  • If the driver is currently not processing the job, it returns E_OK without further processing [SWS_Crypto_00214].
  • If it can cancel a running job, it removes it and returns E_OK [SWS_Crypto_00122].
  • If it cannot cancel it, for example due to hardware limitations, it returns CRYPTO_E_JOB_CANCELED [SWS_Crypto_00183].

"In processing" means here that the object is actively busy with the job. A job for which only FINISH is pending is not considered as in processing SWS_CryptoDriver p. 25. To CRYPTO_E_JOB_CANCELED, the CSM reacts with a cancellation at the next suitable step and reports it via a negative closing callback SWS_CryptoServiceManager p. 80.

Activity diagram: The three outcomes of a cancellation request. Sources: [SWS_Crypto_00122], [SWS_Crypto_00183], [SWS_Crypto_00214], SWS_CryptoServiceManager p. 80

Behavior in the event of an error

If development error detection is active, the driver reports the following codes to the DET: CRYPTO_E_UNINIT (0x00), CRYPTO_E_INIT_FAILED (0x01), CRYPTO_E_PARAM_POINTER (0x02), CRYPTO_E_PARAM_HANDLE (0x04), CRYPTO_E_PARAM_VALUE (0x05), as well as a code for buffers that are too small [SWS_Crypto_00040]. These codes are not returned via the API SWS_CryptoDriver p. 15. An example is Crypto_KeySetValid: Without initialization, it reports CRYPTO_E_UNINIT and returns E_NOT_OK [SWS_Crypto_00196]. In case of an invalid cryptoKeyId, it reports CRYPTO_E_PARAM_HANDLE [SWS_Crypto_00197]. The same pattern applies, for instance, to Crypto_KeyElementCopyPartial [SWS_Crypto_00205] and to targetCryptoKeyId in case of Crypto_KeyDerive [SWS_Crypto_00180].

Before each job, the driver checks job->cryptoKeyId and, if applicable, targetCryptoKeyId [SWS_Crypto_00217]. For CRYPTO_KEYDERIVE, the destination must always lie within the valid range [SWS_Crypto_00202]. If a buffer is too small, the driver does not execute the operation. With DET active, it reports CRYPTO_E_SMALL_BUFFER; without DET, it returns E_NOT_OK [SWS_Crypto_00195]. For CRYPTO_HASH and CRYPTO_MACGENERATE, a result truncated to the most significant bits is output instead [SWS_Crypto_00065]. The newer document reference additionally mentions CRYPTO_RANDOMGENERATE. This is not substantiated by the present R20-11 requirements SWS_CryptoDriver p. 49.

The driver reports runtime results via return values such as CRYPTO_E_BUSY, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, and CRYPTO_E_KEY_NOT_VALID [SWS_Crypto_91018]. When entropy is exhausted, the random service returns CRYPTO_E_ENTROPY_EXHAUSTED. Crypto_ProcessJob then additionally reports the runtime error CRYPTO_E_RE_ENTROPY_EXHAUSTED [SWS_Crypto_00141]. For NvM errors, there is CRYPTO_E_RE_NVM_ACCESS_FAILED [SWS_Crypto_00194]. However, the application must handle defective NvM blocks SWS_CryptoDriver p. 35.

Activity diagram: Typical check chain of a driver call from the DET checks to execution. The sequence of checks is an interpretation. Sources: [SWS_Crypto_00196], [SWS_Crypto_00197], [SWS_Crypto_00217], [SWS_Crypto_00195], [SWS_Crypto_00065], [SWS_Crypto_91018]

Service Crypto_ProcessJob.

The function Crypto_ProcessJob ([SWS_Crypto_91003]) serves to perform the cryptographic primitive configured in parameter job on the Crypto Driver Object referenced via objectId. The interface is reentrant. The execution behavior is synchronous or asynchronous depending on the job configuration. Via the in-out parameter job (type Crypto_JobType*), both controlling parameter structures and pointers to the result data buffers are passed.

Error Handling and Validation

Prior to job execution, the crypto driver checks the validity of the key references:

  • If job->cryptoKeyId or optionally job->targetCryptoKeyId are out of range, Crypto_ProcessJob reports the error CRYPTO_E_PARAM_HANDLE to the DET and returns E_NOT_OK ([SWS_Crypto_00217]). This also applies in particular if an invalid targetCryptoKeyId is passed for the service CRYPTO_KEYDERIVE ([SWS_Crypto_00202]).
  • If the random number generator service is requested and entropy is exhausted, the function reports the runtime error CRYPTO_E_RE_ENTROPY_EXHAUSTED and returns CRYPTO_E_ENTROPY_EXHAUSTED ([SWS_Crypto_00141]).
  • According to [SWS_Crypto_91003], the function acknowledges successful requests with E_OK. In the event of overload or a full queue, CRYPTO_E_BUSY is reported. Additional type-specific error codes include key access and consistency errors (CRYPTO_E_KEY_NOT_VALID, CRYPTO_E_KEY_SIZE_MISMATCH, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, CRYPTO_E_KEY_EMPTY) as well as CRYPTO_E_JOB_CANCELED for canceled synchronous jobs.

Usage and Semantics

The synchronous function Crypto_CancelJob ([SWS_Crypto_00122]) removes a passed job from the queue and cancels its processing if possible. The interface is declared via the header Crypto.h.

The input parameters include:

  • objectId (in): Identifier of the Crypto Driver Object.
  • job (inout): Pointer to the configuration of the job, which contains structures with job- and primitive-relevant information.

Return values and behavior

The function signals the result via the following return values of type Std_ReturnType:

  • E_OK: The request was successful and the job was removed from the queue ([SWS_Crypto_00122]). If the Crypto Driver detects no errors and is not processing the job at the time of the call at all, E_OK is likewise returned without further processing ([SWS_Crypto_00214]).
  • CRYPTO_E_JOB_CANCELED: If the driver detects no errors but cannot cancel the job (e.g. due to hardware restrictions), this status is reported ([SWS_Crypto_00183]). The job is considered canceled, but continues to be executed; no results are transmitted to the application ([SWS_Crypto_00122]).
  • E_NOT_OK: The request failed and the job could not be removed ([SWS_Crypto_00122]).

Concurrency and Limitations

Crypto_CancelJob is reentrant, but explicitly not for the same Crypto Driver Object (objectId) ([SWS_Crypto_00122]).
