Arbitrates mode requests and mode indications via rules and uses them to trigger actions in the Basic Software.

The BSW Mode Manager accepts mode indications from BSW modules and mode requests from SWCs. It arbitrates them via configured rules whose outcome triggers true or false action lists [SWS_BswM_00035]. After BswM_Init, it thus controls the further initialization of the Basic Software, ECU mode handling with the EcuM, and communication release, such as for I-PDU groups or Ethernet port groups. Rules with BSWM_DEFERRED inputs are evaluated cyclically by BswM_MainFunction, and all others immediately [SWS_BswM_00075]. Invalid requests or requests arriving before initialization are ignored and reported if DET is active.

The BSW Mode Manager (BswM) is the central arbitration instance of the Basic Software. It accepts mode indications from BSW modules such as EcuM, ComM, the bus state managers, NvM, DCM, or Sd, as well as mode requests from SWCs. Based on these, it uses configured rules to decide what should occur [SWS_BswM_00035], SWS BswM p. 26. Inputs arrive as C APIs, SWC ports, or events. Each C API is assigned to a specific request port via reference parameters SWS BswM p. 87.

Context diagram: Numerous reporters feed the BswM; it acts via actions on Com, EthIf, EcuM, RTE, and callouts. Sources: [SWS_BswM_00035], [SWS_BswM_00008], Mode-Mgmt-Guide p. 18

A rule is a logical expression over the current port values. Depending on the result, it executes the true action list or the false action list. Action lists contain actions, nested lists, or further rules Mode-Mgmt-Guide p. 32. In the case of BSWM_IMMEDIATE, a rule is evaluated immediately. In the case of BSWM_DEFERRED, this takes place in BswM_MainFunction [SWS_BswM_00075]. Rules with conditions that are still undefined are not arbitrated SWS BswM p. 30.

Activity diagram: A request is verified, stored, and evaluated against the rules either immediately or cyclically depending on the processing type. Sources: [SWS_BswM_00075], SWS BswM p. 30

The EcuM calls BswM_Init [SWS_BswM_00002] in the StartPostOS sequence SWS EcuM p. 42. Thereafter, the BswM uses rules to control further initialization up to the start of the RTE, in the example with NvM_ReadAll and BswM_NvM_CurrentJobMode [SWS_BswM_00152], Mode-Mgmt-Guide p. 36. In ECU mode handling, the BswM alone decides on the transitions of the EcuM SWS EcuM p. 99. Since R20-11, it additionally switches Ethernet port groups based on PNC states Mode-Mgmt-Guide p. 49. After BswM_Deinit, no further mode processing takes place [SWS_BswM_00120].

If DET is active, the input APIs ignore calls prior to initialization and report BSWM_E_UNINIT [SWS_BswM_00080]. They treat values outside the permitted range in the same way and report BSWM_E_REQ_MODE_OUT_OF_RANGE [SWS_BswM_00095]. If an action fails, the BswM reports the configurable runtime error BSWM_E_ACTION_FAILED [SWS_BswM_00238].

Role of the BswM: Central Mode Arbitration of the Basic Software

The BSW Mode Manager (BswM) accepts mode requests and mode indications. Based on these, it arbitrates via configured rules which actions are to be executed [SWS_BswM_00035], SWS BswM p. 26. Mode requests typically originate from application SWCs, but can also come from BSW modules such as the DCM. Mode indications are always delivered by other BSW modules, such as the bus-specific state managers and the EcuM. The BswM treats both types equally and groups them under the term “mode arbitration request” SWS BswM p. 26.

The BswM is modeled as a service component that serves ECU-local mode requests SWS BswM p. 48. It has no mandatory interfaces to other modules [SWS_BswM_00007]. Its actions call functions of other BSW modules. For this purpose, the specification lists optional interfaces, such as Com_IpduGroupStart, Com_IpduGroupStop, or the control of reception deadline monitoring for I-PDU groups [SWS_BswM_00008], SWS BswM p. 93. The system boundary is thus clearly drawn: The reporting modules only report their state. The reaction to it is determined solely by the configured logic in the BswM Mode-Mgmt-Guide p. 32.

Context diagram: Numerous BSW modules and SWCs report to the BswM; it acts back via actions on Com, EthIf, EcuM, RTE, and user callouts. Sources: [SWS_BswM_00035], [SWS_BswM_00008], [SWS_BswM_00202], [SWS_BswM_00270], Mode-Mgmt-Guide p. 18, SWS EcuM p. 99

Inputs: Mode Indications via C APIs, Ports, and Events

The container BswMModeRequestSource defines how an input arrives. There are three types Mode-Mgmt-Guide p. 18:

  • a C API called directly by a BSW module, which the BswM internally translates into a mode request,
  • an RPort with SenderReceiverInterface (BswMSwcModeRequest),
  • an RPort with ModeSwitchInterface (BswMSwcModeNotification).

For the port types, the BswM generates ports according to fixed naming patterns [SWS_BswM_00201], [SWS_BswM_00200]. The C APIs in R20-11 can be grouped according to origin:

  • ECU State and Wakeup: BswM_EcuM_CurrentState [SWS_BswM_91003], BswM_EcuM_RequestedState [SWS_BswM_91004], BswM_EcuM_CurrentWakeup [SWS_BswM_00131].
  • Communication: BswM_ComM_CurrentMode [SWS_BswM_00047], BswM_ComM_CurrentPNCMode [SWS_BswM_00148], BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Bus State Managers and LinTp: CanSM [SWS_BswM_00049], EthSM [SWS_BswM_00050], FrSM [SWS_BswM_00051], LinSM [SWS_BswM_00052] including schedule indication [SWS_BswM_00058], and BswM_LinTp_RequestMode [SWS_BswM_00156].
  • Network Management and Ethernet: BswM_Nm_StateChangeNotification [SWS_BswM_91002], BswM_Nm_CarWakeUpIndication [SWS_BswM_00235], BswM_J1939Nm_StateChangeNotification [SWS_BswM_00194], BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001].
  • Diagnostics: BswM_Dcm_CommunicationMode_CurrentState [SWS_BswM_00048], BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], BswM_J1939DcmBroadcastStatus [SWS_BswM_00165].
  • Memory: BswM_NvM_CurrentBlockMode [SWS_BswM_00104], BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  • Service Discovery: BswM_Sd_* [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210].
  • Partitions: BswM_WdgM_RequestPartitionReset [SWS_BswM_00157], BswM_BswMPartitionRestarted [SWS_BswM_00193].
  • Generic: BswM_RequestMode [SWS_BswM_00046] is intended only for BSW modules without an own interface. It works with BswM_UserType [SWS_BswM_00216] and BswM_ModeType [SWS_BswM_00214], both derived from uint16.

Each API is assigned to exactly one request port type. Parameters such as Network are assigned to a concrete port via reference parameters like BswMCanSMChannelRef or BswMComMChannelRef SWS BswM p. 87. Therefore, for example, one BswMCanSMIndication is created per CAN channel Mode-Mgmt-Guide p. 24. All notification APIs are synchronous. With the exception of BswM_ComM_InitiateReset, which is non-reentrant, they are reentrant [SWS_BswM_00217], [SWS_BswM_00049].

In addition to the stateful mode request ports, there are event request ports. BSW modules send events via them, for example via BswM_ComM_InitiateReset() SWS BswM p. 102. The BswM arbitrates both on such events and on their clearing SWS BswM p. 26. According to the change history, R20-11 introduced the following innovations SWS BswM p. 2:

  • Resumption of BswM_EcuM_CurrentState and BswM_EcuM_RequestedState,
  • new notification BswMNmStateChangeNotification,
  • support for Ethernet port group switching.

BswM_WdgM_RequestPartitionReset becomes obsolete only in R21-11 SWS BswM p. 2.

Rules and Action Lists: From Input to Action

The behavior of the BswM is configured via rules and action lists. A rule is a logical expression over the current values of the mode request ports. Depending on the result, its evaluation executes the True or the False action list Mode-Mgmt-Guide p. 32. An action list can contain SWS BswM p. 31:

  • atomic actions,
  • nested action lists,
  • references to rules, which are then evaluated in the context of this list.

Actions may only be invoked in the context of an action list [SWS_BswM_00147]. A diagram in the specification shows an example rule. It combines via AND a mode condition (MyModeRequestPort equal to MODE_A) with the event port ComMInitiateReset SWS BswM p. 25.

When a rule is evaluated is determined by BswMRequestProcessing for each port:

  • BSWM_IMMEDIATE: Every rule that references the port is processed immediately Mode-Mgmt-Guide p. 32. For SW-C ports, the BswM registers a runnable for this, which the RTE starts upon data reception SWS BswM p. 48.
  • BSWM_DEFERRED: The BswM reads the value cyclically. BswM_MainFunction [SWS_BswM_00053] evaluates all rules that use at least one such input [SWS_BswM_00075].

Activity diagram: An incoming request is checked, stored, and, depending on the processing type, evaluated against the rules immediately or in the MainFunction; rules with undefined conditions remain unconsidered. Sources: [SWS_BswM_00075], [SWS_BswM_00080], [SWS_BswM_00095], SWS BswM p. 30, Mode-Mgmt-Guide p. 32

Via BswMModeInitValue, a port receives an initial value during initialization. If it is missing, the condition is considered undefined until the first update. Rules with undefined conditions are not arbitrated SWS BswM p. 30. The examples in the guide therefore set initial values, such as CANSM_BSWM_NO_COMMUNICATION for CanSM indications Mode-Mgmt-Guide p. 24.

For wait times, the BswM provides timers. A BswMTimer is an internal Mode Request Source and can only be controlled via the action BswMTimerControl; an external interface does not exist SWS BswM p. 37. Its sequence SWS BswM p. 37:

  • During initialization, all timers are stopped.
  • BSWM_TIMER_START loads the timer with BswMTimerValue and sets BSWM_TIMER_STARTED.
  • In each run of BswM_MainFunction, it is decremented by its cycle time.

Regardless of their configuration, timers are always processed DEFERRED [SWS_BswM_00220]. The value BSWM_TIMER_EXPIRED is likely to indicate the expired countdown. This is an interpretation, because the section is truncated in the payload SWS BswM p. 37.

State diagram: Life cycle of a BswMTimer from STOPPED through STARTED to EXPIRED, controlled exclusively by actions and the MainFunction. Sources: [SWS_BswM_00220], SWS BswM p. 37

In addition to the functions from the list of optional interfaces [SWS_BswM_00008], specific actions exist. Thus, when executed, BswMEthIfStartAllPorts calls EthIf_StartAllPorts [SWS_BswM_00286]. Freely defined functions are configured as BswMUserCallout. In doing so, name and parameters are defined at ECU configuration time [SWS_BswM_00054], [SWS_BswM_00270].

Startup, Initialization Chains, and Shutdown

BswM_Init [SWS_BswM_00002] receives a pointer to the post-build configuration BswM_ConfigType [SWS_BswM_00213]. The function initializes all global variables. Afterwards, the BswM is ready to arbitrate requests. Only OS and SchM are required SWS BswM p. 69. The EcuM calls BswM_Init in the StartPostOS sequence after SchM_Start(); this is followed by SchM_Init and SchM_StartTiming SWS EcuM p. 42. On multi-core systems, the call occurs in a loop over each BswM instance of the core SWS EcuM p. 81. For such multiple instances in multiple partitions or cores, BswM_Init is conditionally reentrant SWS BswM p. 69.

Sequence diagram: StartPostOS sequence with initialization of each BswM instance between SchM_Start and SchM_Init; after that, the MainFunction runs cyclically. Sources: [SWS_BswM_00002], SWS EcuM p. 42, SWS EcuM p. 78, SWS BswM p. 37

From here on, the BswM takes over control of the sequence. It ensures that the remaining init routines of the basic software are called and the RTE is started Mode-Mgmt-Guide p. 36. The modules to be initialized by it are described by the EcuM container EcuMDriverInitListBswM SWS EcuM p. 224. In the example of the guide, the initialization proceeds as follows Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20:

  1. A DEFERRED rule initializes the NVRAM drivers and triggers NvM_ReadAll.
  2. The NvM reports the end of the job via BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. This notification triggers the remaining initialization and the transition to ECU_RUN.

The guide still shows a uint8 parameter for this API ServiceId Mode-Mgmt-Guide p. 26. However, the signature with NvM_MultiBlockRequestType [SWS_BswM_00152] is authoritative for R20-11.

Sequence diagram: Rule-controlled second initialization phase with NvM_ReadAll, feedback from the NvM, and subsequent RTE start. Sources: [SWS_BswM_00152], [SWS_BswM_00075], Mode-Mgmt-Guide p. 36, NV-Data-Guide p. 20

During shutdown, according to the NV guide, the BswM is responsible for writing modified blocks, in the example via NvM_WriteAll NV-Data-Guide p. 41. The NvM also reports the cancellation of a WriteAll to it via the job mode indication SWS NvM p. 155. In the OffPreOS sequence, the EcuM deinitializes the BswM as the first step SWS EcuM p. 50. After BswM_Deinit [SWS_BswM_00119], no further mode processing takes place, even if requests arrive or the MainFunction is called [SWS_BswM_00120].

Interaction with EcuM: ECU Mode Handling and Wakeup Sources

During ECU Mode Handling, the EcuM arbitrates the RUN and POST_RUN requests of the SW-Cs. It does not possess its own state machine; only the BswM decides when a transition occurs SWS EcuM p. 99. The sequence Mode-Mgmt-Guide p. 34:

  1. The EcuM reports the result of the RUN Request Protocol via BswM_EcuM_RequestedState [SWS_BswM_91004].
  2. The BswM sets the state via EcuM_SetState.
  3. The EcuM reports the corresponding mode to the RTE.
  4. After feedback from the RTE, the EcuM calls BswM_EcuM_CurrentState [SWS_BswM_91003].

The states are ECUM_STATE_STARTUP, ECUM_STATE_APP_RUN, ECUM_STATE_APP_POST_RUN, ECUM_STATE_SHUTDOWN, and ECUM_STATE_SLEEP Mode-Mgmt-Guide p. 34. This coupling allows SW-Cs designed for the EcuM with a fixed state machine to be reused. A compatibility SW-C is not required for this Mode-Mgmt-Guide p. 61.

Sequence diagram: The EcuM arbitrates RUN requests, the BswM decides on the transition, the RTE is informed, and the confirmation returns to the BswM as CurrentState. Sources: [SWS_BswM_91004], [SWS_BswM_91003], SWS EcuM p. 99, Mode-Mgmt-Guide p. 34, Mode-Mgmt-Guide p. 61

The EcuM reports state changes of wakeup sources via BswM_EcuM_CurrentWakeup [SWS_BswM_00131]. In the state machine of the wakeup sources, each of the states NONE, PENDING, VALIDATED, and EXPIRED calls this API upon entry SWS EcuM p. 60. In detail:

  • If the EcuM validates an event, it reports VALIDATED SWS EcuM p. 134.
  • If the validation remains unsuccessful until the timeout, it reports EXPIRED SWS EcuM p. 63.
  • In the GoSleep sequence, it resets the sources with ECUM_WKSTATUS_NONE SWS EcuM p. 54.
  • In the Poll sequence, it reports PENDING or VALIDATED, depending on the validation need SWS EcuM p. 57.

One BswMEcuMWakeupSource is created per wakeup source Mode-Mgmt-Guide p. 29.

State diagram: States of a wakeup source in the EcuM; each entry generates a notification to the BswM. Sources: [SWS_BswM_00131], SWS EcuM p. 60, SWS EcuM p. 57, SWS EcuM p. 63

Communication Control: Buses, Partial Networks, Diagnostics, and Services

A typical use case is the release of I-PDU groups. In the guide, a rule based on a CanSM indication activates the I-PDU groups of a CAN channel Mode-Mgmt-Guide p. 32. The CanSM reports the states CANSM_BSWM_NO_COMMUNICATION, CANSM_BSWM_SILENT_COMMUNICATION, CANSM_BSWM_FULL_COMMUNICATION, and CANSM_BSWM_BUS_OFF for this [SWS_BswM_00049], Mode-Mgmt-Guide p. 22. It reports the state FULL_COMMUNICATION, for example, upon the effect E_TX_ON SWS CanSM p. 65.

For partial networks, ComM reports every state change of a PNC via BswM_ComM_CurrentPNCMode [SWS_BswM_00148], SWS ComM p. 35. With this, the BswM switches Ethernet switch port groups Mode-Mgmt-Guide p. 49:

  • It knows the mapping of PNC to EthIfSwitchPortGroup.
  • It calls EthIf_SwitchPortGroupRequestMode with ETH_MODE_ACTIVE or ETH_MODE_DOWN.
  • EthIf reports the resulting link state of the group back via BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001], SWS EthIf p. 92.

Sequence diagram: PNC request and release switch an Ethernet port group via BswM rules; EthIf reports the determined link state back to BswM. Sources: [SWS_BswM_00148], [SWS_BswM_91001], Mode-Mgmt-Guide p. 49, SWS EthIf p. 92

Diagnostics also reports to the BswM:

  • UDS Service 0x28 (CommunicationControl): The DCM calls BswM_Dcm_CommunicationMode_CurrentState for each affected network [SWS_BswM_00048], SWS DCM p. 147. The behavior is configured via BswMDcmComModeRequest; its BswMDcmComMChannelRef corresponds to the argument Network SWS BswM p. 64.
  • Bootloader jump: If the application was updated in the process, the DCM reports BswM_Dcm_ApplicationUpdated [SWS_BswM_00158], SWS DCM p. 231.
  • J1939: BswM_J1939DcmBroadcastStatus passes a bitmask per ComMChannelId that covers only the first 16 channels [SWS_BswM_00165], SWS BswM p. 70. Depending on the J1939Nm states, the BswM switches Com I-PDU groups, PduR routing path groups, and the request handling of the J1939Rm Mode-Mgmt-Guide p. 45.

Service Discovery reports the states of Client Services, Consumed Eventgroups, and Event Handlers [SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]. For the Sd, these calls are optional interfaces SWS Sd p. 122.

Behavior in the event of an error

If BswMDevErrorDetect is active, the input APIs first check whether the BswM is initialized. Otherwise, they ignore the request and report BSWM_E_UNINIT to the DET, such as [SWS_BswM_00080], [SWS_BswM_00081], [SWS_BswM_00149], [SWS_BswM_00112], [SWS_BswM_00086], [SWS_BswM_00132]. In addition, they check the passed values for the permitted range. In case of a violation, the request is likewise ignored and BSWM_E_REQ_MODE_OUT_OF_RANGE is reported, such as [SWS_BswM_00095], [SWS_BswM_00097], [SWS_BswM_00150], [SWS_BswM_00113], [SWS_BswM_00110], [SWS_BswM_00154]. If BswM_MainFunction is called before initialization, it returns immediately without reporting an error [SWS_BswM_00076].

If an action returns E_NOT_OK, the BswM reports the runtime error BSWM_E_ACTION_FAILED. The value is between 0x80 and 0xFF and is configured in BswMReportFailRuntimeErrorId [SWS_BswM_00238]. The BswM rejects configurations that contain both BswMBswModeInitValue and BswMCompuScaleModeValue for a BswMModeInitValue SWS BswM p. 30. The code BSWM_E_REQ_USER_OUT_OF_RANGE is likely intended to check requesting_user in BswM_RequestMode. This is an interpretation, because the corresponding passage is truncated in the payload [SWS_BswM_00230], SWS BswM p. 86.

Errors of other modules reach the BswM as normal inputs:

  • Bus-off: The CanSM first reports CANSM_BSWM_BUS_OFF to the BswM and then COMM_SILENT_COMMUNICATION to ComM. In addition, it sets a DEM event to PRE_FAILED SWS CanSM p. 70, Error-Description p. 19.
  • Partition reset: The WdgM requests it via BswM_WdgM_RequestPartitionReset [SWS_BswM_00157], Mode-Mgmt-Guide p. 30.
  • Restart of the BswM partition: Afterwards, BswM_BswMPartitionRestarted is called [SWS_BswM_00193]. Rules can then specifically re-initialize the modules of this partition Mode-Mgmt-Guide p. 38.
