Role of the BswM: Arbiter for the Basic Software Modes

In the ECU, mode requests converge at the BSW Mode Manager (BswM), and it translates them into actions. It arbitrates based on incoming mode indications [SWS_BswM_00035]. The specification distinguishes between two types of inputs (SWS BswM p. 26):

  • Mode requests usually come from application SW-Cs, occasionally also from BSW modules such as the DCM.
  • Mode indications always come from BSW modules, such as the bus-specific state managers or the EcuM.

In the component model, the BswM is a Service Component that only serves mode requests of its own ECU (SWS BswM p. 48).

The BswM takes effect via actions. In principle, it is allowed to call any function of the AUTOSAR BSW (SWS BswM p. 92). The specification mentions, among others, Com_IpduGroupStart, Com_IpduGroupStop, and Com_EnableReceptionDM [SWS_BswM_00008] as optional interfaces. In addition, the BswM can execute user callouts [SWS_BswM_00270]. Their parameters are defined at configuration time in the container BswMUserCallout [SWS_BswM_00054]. The BswM has no mandatory interfaces to other modules [SWS_BswM_00007].

Context diagram: Reporting APIs of the BSW modules and SW-C ports converge at the BswM; based on rules, it acts on Com, PduR, EthIf, EcuM, J1939Rm, and callouts via actions. Sources: SWS BswM p. 87, [SWS_BswM_00008], [SWS_BswM_00201], [SWS_BswM_00202], Guide Modemanagement p. 45, Guide Modemanagement p. 61

Inputs: Indications, Requests, and Events

For BSW modules, the BswM provides a C API for each source. Internally, it maps each call to a Mode Request Port (Guide Modemanagement p. 18). For this purpose, the mapping table links an API parameter with a configuration reference in each case (SWS BswM p. 87). An example: BswM_CanSM_CurrentState is mapped to the source BswMCanSMIndication via the pair Network / BswMCanSMChannelRef [SWS_BswM_00049]. This source is created once per CAN channel (Guide Modemanagement p. 24).

The reporting APIs by origin:

  • Bus State Manager: CanSM, LinSM, FrSM, and EthSM report their state ([SWS_BswM_00049], [SWS_BswM_00052], [SWS_BswM_00051], [SWS_BswM_00050]). LinSM also reports the active schedule table [SWS_BswM_00058], and LinTp requests a LIN TP mode [SWS_BswM_00156].
  • ComM: reports channel modes [SWS_BswM_00047] and PNC modes [SWS_BswM_00148] and signals a shutdown via BswM_ComM_InitiateReset [SWS_BswM_00217].
  • Network Management: Nm and J1939Nm report state changes ([SWS_BswM_91002], [SWS_BswM_00194]). Nm additionally indicates a CarWakeUp [SWS_BswM_00235].
  • Memory and Diagnostics: Notifications come from NvM ([SWS_BswM_00104], [SWS_BswM_00152]), DCM ([SWS_BswM_00048], [SWS_BswM_00158]), and J1939Dcm [SWS_BswM_00165].
  • Service Discovery: reports via three callbacks ([SWS_BswM_00204], [SWS_BswM_00207], [SWS_BswM_00210]).
  • EthIf and WdgM: EthIf reports link states of switch port groups [SWS_BswM_91001]. WdgM requests a partition reset [SWS_BswM_00157].

If a BSW module does not have its own request interface, it uses the generic call BswM_RequestMode with the types BswM_UserType and BswM_ModeType ([SWS_BswM_00046], [SWS_BswM_00216], [SWS_BswM_00214]). SW-Cs reach the BswM via three port types:

  • modeRequestPort: Required Port for mode requests [SWS_BswM_00201].
  • modeNotificationPort: Required Port via which the BswM receives observed mode switches [SWS_BswM_00200].
  • modeSwitchPort: Provided Port via which the BswM itself switches modes [SWS_BswM_00202].

Events such as BswM_ComM_InitiateReset are configured as BswMEventRequestPort (SWS BswM p. 102). The arbitration considers both the occurrence of an event and its clearing (SWS BswM p. 26).

Release Reference R20-11: According to the change history (SWS BswM p. 2), R20-11 introduced the following changes:

  • Reintroduction of BswM_EcuM_CurrentState [SWS_BswM_91003] and BswM_EcuM_RequestedState [SWS_BswM_91004].
  • Support for Ethernet switch port groups.
  • New action BswMEthIfStartAllPorts [SWS_BswM_00286].
  • Removal of Pretended Networking.

Two later changes do not yet affect R20-11: BswM_WdgM_RequestPartitionReset [SWS_BswM_00157] was only marked as obsolete with R21-11, and the SoAd mode request was only added with R21-11 (SWS BswM p. 2).

Rules, Action Lists, and Evaluation Timing

The behavior of the BswM is configured via rules and action lists (Guide Modemanagement p. 32):

  • A rule is a logical expression over the current values of the Mode Request Ports.
  • Depending on the result, the BswM executes the True or the False action list.
  • An action list contains atomic actions, nested action lists, or references to further rules.

Actions may only be called within the context of an action list [SWS_BswM_00147].

When a rule is evaluated is determined by the parameter BswMRequestProcessing for each port:

  • IMMEDIATE: All rules that reference the port are evaluated immediately (Guide Modemanagement p. 32). For SW-C requests, the RTE must trigger an arbitration runnable via a DataReceiveEvent for this purpose (SWS BswM p. 48).
  • BSWM_DEFERRED: The rules are evaluated in BswM_MainFunction [SWS_BswM_00053] [SWS_BswM_00075].

Special rules apply to timers. Independent of its configuration, a BswMTimer is always treated as DEFERRED and arbitrated in the main function [SWS_BswM_00220]. In version R23-11, it can only be controlled via the action BswMTimerControl, and its resolution is a multiple of the cycle time of the main function (SWS BswM p. 37).

Initial values influence which rules are arbitrated at all. If an initial value is missing (BswMModeInitValue), a mode condition is considered undefined until the first update. Rules with undefined conditions are not arbitrated (SWS BswM p. 30). This clarification comes from version R23-11. It presumably applies analogously already to R20-11; however, a corresponding R20-11 requirement is not available here.

Lifecycle and Startup under the Control of the EcuM

BswM_Init [SWS_BswM_00002] initializes all module-global variables. Afterwards, the BswM can arbitrate mode requests. Before the call, only OS and SchM must be initialized (SWS BswM p. 69). The passed pointer points to the post-build data in BswM_ConfigType [SWS_BswM_00213]. BswM_Init is "Conditionally Reentrant" because the BswM can be instantiated in multiple partitions (SWS BswM p. 69). Therefore, the EcuM calls BswM_Init in a loop for each BswM instance of a core (SWS EcuM p. 83).

In the StartPostOS sequence, the EcuM first starts the BSW scheduler. Afterwards, it initializes the BswM and then concludes the SchM initialization (SWS EcuM p. 42). From this point on, the BswM controls the further startup: it ensures that the init routines of the other BSW modules run and the RTE is started (Guide Modemanagement p. 36). In the example of the guide, this proceeds as follows:

  1. A DEFERRED rule triggers NvM_ReadAll.
  2. The NvM reports the completion via BswM_NvM_CurrentJobMode [SWS_BswM_00152].
  3. A subsequent rule then starts the RTE (NV-Daten-Leitfaden p. 20).

Sequence diagram: The EcuM initializes the BswM in StartPostOS; afterwards, BswM rules drive the startup forward via NvM_ReadAll and Rte_Start. Sources: SWS EcuM p. 42, Guide Modemanagement p. 36, NV-Daten-Leitfaden p. 20, [SWS_BswM_00002]

During shutdown, the EcuM calls BswM_Deinit [SWS_BswM_00119] for each BswM instance of the core in the OffPreOS sequence (SWS EcuM p. 90). After that, the BswM no longer processes any modes, even if further requests arrive or the main function is called [SWS_BswM_00120]. If the partition of the BswM is restarted, the RestartTask reports this via BswM_BswMPartitionRestarted [SWS_BswM_00193].

State diagram: The BswM arbitrates only between BswM_Init and BswM_Deinit; before and after, no mode processing takes place. Sources: [SWS_BswM_00002], [SWS_BswM_00119], [SWS_BswM_00120], [SWS_BswM_00076], [SWS_BswM_00078], SWS BswM p. 69

Interaction with EcuM, Wakeup Sources, and Ethernet Port Groups

In ECU Mode Handling, the EcuM has no state machine of its own (SWS EcuM p. 99). It arbitrates the RUN and POST_RUN requests of the SW-Cs and reports the result via BswM_EcuM_RequestedState [SWS_BswM_91004], because only the BswM decides on transitions. The sequence is a cycle:

  1. The BswM sets the state with EcuM_SetState.
  2. The EcuM passes the mode on to the RTE (SWS EcuM p. 99).
  3. After feedback from the RTE, the EcuM reports the new state to the BswM via BswM_EcuM_CurrentState [SWS_BswM_91003] (Guide Modemanagement p. 34).

With this structure, legacy SW-Cs written for the EcuM with a fixed state machine can also continue to be used (Guide Modemanagement p. 61).

Sequence diagram: The EcuM reports the result of the RUN Request Protocol, the BswM decides and sets the state, and BswM_EcuM_CurrentState only follows after feedback from the RTE. Sources: SWS EcuM p. 99, Guide Modemanagement p. 34, Guide Modemanagement p. 61, [SWS_BswM_91003], [SWS_BswM_91004]

In the EcuM, wakeup sources pass through the states NONE, PENDING, VALIDATED, and EXPIRED. The EcuM reports each entry into one of these states via BswM_EcuM_CurrentWakeup [SWS_BswM_00131] (SWS EcuM p. 64). In the BswM, this corresponds to the source BswMEcuMWakeupSource with the initial value ECUM_WKSTATUS_NONE, which is created once for each wakeup source (Guide Modemanagement p. 29).

State diagram: Each state change of a wakeup source reaches the BswM as a mode indication. Sources: SWS EcuM p. 60, SWS EcuM p. 63, SWS EcuM p. 64, [SWS_BswM_00131]

Ethernet switch port groups are new in R20-11. ComM reports the PNC mode via BswM_ComM_CurrentPNCMode [SWS_BswM_00148]. The BswM knows the mapping of PNC to port group and calls EthIf_SwitchPortGroupRequestMode with ETH_MODE_ACTIVE or ETH_MODE_DOWN (Guide Modemanagement p. 49). In the opposite direction, EthIf reports the accumulated link state of those port groups that are not assigned to an EthIfController via BswM_EthIf_PortGroupLinkStateChg [SWS_BswM_91001] (SWS EthIf p. 29). With action BswMEthIfStartAllPorts, the BswM starts all ports via EthIf_StartAllPorts [SWS_BswM_00286].

Sequence diagram: The PNC mode controls the port group, and the accumulated link state flows back to the BswM. Sources: Guide Modemanagement p. 49, SWS EthIf p. 92, SWS EthIf p. 29, [SWS_BswM_00148], [SWS_BswM_91001]

Configuration and instance reference of the request ports

The configuration tool maps the API parameters to the referenced ECUC containers (Guide Modemanagement p. 32). Two examples:

  • BswMDcmComModeRequest connects argument Network of BswM_Dcm_CommunicationMode_CurrentState to a ComM channel [SWS_BswM_00048] via BswMDcmComMChannelRef.
  • With BswM_J1939DcmBroadcastStatus, the BswM evaluates the bit at the position of the referenced ComMChannelId (SWS BswM p. 70). Only the first 16 channels can be mapped [SWS_BswM_00165].

For J1939, the BswM switches three things depending on the J1939Nm state [SWS_BswM_00194]: COM I-PDU groups, PduR routing path groups, and the J1939Rm request handling (Guide Modemanagement p. 45).

  • BswM_ModeType and BswM_UserType are derived from uint16 ([SWS_BswM_00214], [SWS_BswM_00216]).
  • The imported types of the neighboring modules are listed collectively [SWS_BswM_00001].
  • BswM_GetVersionInfo provides the version information [SWS_BswM_00003].

Behavior in the event of an error

If BswMDevErrorDetect is active, the reporting APIs check two things:

  • Initialization: If the BswM is not initialized, the report is ignored and BSWM_E_UNINIT is reported to the DET. Examples are CanSM [SWS_BswM_00080], EthSM [SWS_BswM_00081], LinSM schedule [SWS_BswM_00086], PNC [SWS_BswM_00149], and NvM jobs [SWS_BswM_00153].
  • Value range: Values outside the permissible range are also discarded and reported with BSWM_E_REQ_MODE_OUT_OF_RANGE, such as in [SWS_BswM_00095], [SWS_BswM_00150], [SWS_BswM_00133], and [SWS_BswM_00154].

The main function behaves differently: if called before initialization, it returns immediately and reports no error [SWS_BswM_00076].

The development error codes include, among others, BSWM_E_UNINIT (0x01), BSWM_E_NULL_POINTER, BSWM_E_REQ_USER_OUT_OF_RANGE, BSWM_E_REQ_MODE_OUT_OF_RANGE, and BSWM_E_PARAM_CONFIG [SWS_BswM_00230]. If an action returns E_NOT_OK, the BswM reports the runtime error BSWM_E_ACTION_FAILED. Its value is between 0x80 and 0xFF and is configured in BswMReportFailRuntimeErrorId [SWS_BswM_00238].

System errors reach the BswM as ordinary mode indications. In the event of a bus-off, CanSM reports in this order (SWS CanSM p. 70):

  1. CANSM_BSWM_BUS_OFF to the BswM,
  2. COMM_SILENT_COMMUNICATION to ComM,
  3. a PRE_FAILED event to the DEM.

If the recovery succeeds, CANSM_BSWM_FULL_COMMUNICATION follows (SWS CanSM p. 65). How the system reacts to this is entirely up to the rules via BswMCanSMIndication [SWS_BswM_00049]. Further error paths are the partition reset requested by the WdgM [SWS_BswM_00157] and the report of a partition restart [SWS_BswM_00193].

Sequence diagram: In the event of a bus-off, CanSM informs the BswM before ComM and DEM; after recovery, CanSM reports full communication again. Sources: SWS CanSM p. 70, SWS CanSM p. 65, Fehlerbeschreibung p. 19, [SWS_BswM_00049]
