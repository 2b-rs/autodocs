Role of FrTrcv between FlexRay Interface and transceiver hardware

The FlexRay Transceiver Driver (FrTrcv) controls and monitors external FlexRay transceiver devices. It sets and reads their operating mode ([SWS_FrTrcv_00323], [SWS_FrTrcv_00324]). It also determines the wake-up reason ([SWS_FrTrcv_00325]) and clears pending wake-up events ([SWS_FrTrcv_00329]). For active-star transceivers, it additionally provides the error status per branch and can enable and disable individual branches ([SWS_FrTrcv_00419], [SWS_FrTrcv_00442], [SWS_FrTrcv_00443]). FrTrcv_GetVersionInfo explicitly provides the version of the module and not that of the transceiver hardware ([SWS_FrTrcv_00326], SWS FrTrcv p. 43).

Towards the hardware, the driver accesses via the MCAL drivers Dio, Spi, and Icu. It reports events to DEM, DET, and EcuM. The required services and imported types are defined in [SWS_FrTrcv_00334] and [SWS_FrTrcv_00321]. It implements wait times during state changes using Tm_BusyWait1us16bit ([SWS_FrTrcv_00485]).

Upwards, the FlexRay Interface calls FrTrcv_SetTransceiverMode (SWS FrTrcv p. 57). The FlexRay State Manager controls the transceivers of both channels via FrIf_SetTransceiverMode and FrIf_GetTransceiverWUReason (SWS FrSM p. 54). Interpretation: FrIf is likely to map these calls to the FrTrcv services of the same name.

Context diagram: FrTrcv is located between FrIf/FrSM on the one hand and the MCAL drivers as well as the transceiver hardware on the other; diagnostic and wake-up notifications go to DEM, DET, and EcuM. Sources: [SWS_FrTrcv_00334], [SWS_FrTrcv_00485], [SWS_FrTrcv_00330], SWS FrTrcv p. 57, SWS FrSM p. 54

From power-on to operating mode: initialization and mode changes

After power-on, the driver is in the NOT_ACTIVE state and is not initialized. The call FrTrcv_Init(ConfigPtr) ([SWS_FrTrcv_00322]) transitions it to ACTIVE, specifically into the mode defined by the configuration (SWS FrTrcv p. 21, SWS FrTrcv p. 23). The structure of FrTrcv_ConfigType is implementation-specific ([SWS_FrTrcv_00487]). Drivers that serve wake-up sources must be reinitialized in the restart block of the EcuM; in doing so, the trigger mechanism for the wake-up notification is re-armed (SWS FrTrcv p. 37).

Within ACTIVE, FrTrcv_TrcvModeType recognizes four modes ([SWS_FrTrcv_00481]):

  • NORMAL: full communication.
  • RECEIVEONLY: like NORMAL, but receive only.
  • STANDBY: no communication; the ECU remains powered if the transceiver controls the power supply.
  • SLEEP: no communication; depending on the responsibility for the power supply, the ECU may be unpowered.

In STANDBY and SLEEP, wake-up via the bus or locally is possible if the hardware supports this (SWS FrTrcv p. 21). For passive operation (Receive-Only), FrSM maintains the concurrent states FRSM_ECU_ACTIVE and FRSM_ECU_PASSIVE (SWS FrSM p. 18).

FrTrcv_SetTransceiverMode operates synchronously and is non-reentrant. Upon success, the service returns E_OK. In the case of E_NOT_OK, the previous state is retained; transitions into optional states may fail ([SWS_FrTrcv_00323]). When transitioning to STANDBY, the error history in the transceiver is cleared as far as the hardware supports this (SWS FrTrcv p. 39). If FrTrcvIcuChannelRef is configured, the following applies to the wake-up notification via ICU channels:

  • The channels are enabled upon the transition to STANDBY ([SWS_FrTrcv_00491]).
  • Upon the transition to NORMAL, they are disabled ([SWS_FrTrcv_00492]).
  • The driver uses Icu_EnableNotification and Icu_DisableNotification for this ([SWS_FrTrcv_00490]).

The reentrant FrTrcv_GetTransceiverMode provides the current mode ([SWS_FrTrcv_00324]).

State diagram: FrTrcv_Init leads from NOT_ACTIVE to the configured start mode; thereafter, FrTrcv_SetTransceiverMode switches between the four modes, and a failed switch leaves the mode unchanged. Sources: SWS FrTrcv p. 23, SWS FrTrcv p. 21, [SWS_FrTrcv_00323], [SWS_FrTrcv_00491], [SWS_FrTrcv_00492]

Sequence diagram: A Dio-controlled transceiver is brought to STANDBY and optionally further to SLEEP via port accesses; wait time and ICU enable complement the sequence. Sources: SWS FrTrcv p. 57, [SWS_FrTrcv_00485], [SWS_FrTrcv_00491]

Wakeup detection: polling, notification to EcuM, and wakeup reason

For R20-11, only the signature is documented for FrTrcv_MainFunction: service ID 0x0d, available via SchM_FrTrcv.h ([SWS_FrTrcv_00330]). The passage from R23-11 describes the task in more detail: the function polls all buses in STANDBY and SLEEP for wakeup events and stores them internally. Its period is defined by the configuration, and it is independent of the FlexRay bus schedule (SWS FrTrcv p. 49). The period is set via FrTrcvMainFunctionCycleTime (ECUC-Parameter p. 250).

If FrTrcv_CheckWakeupByTransceiver is called ([SWS_FrTrcv_00331]), the driver reports wakeup events to the ECU State Manager (SWS FrTrcv p. 46). For this, it uses EcuM_SetWakeupEvent ([SWS_FrTrcv_00334]). Presumably, this report concerns the events previously stored internally. For wakeup via the bus, there is additionally a notification that the driver triggers as soon as the SPI or DIO driver informs it. It runs in the caller's context, thus possibly in an interrupt context (SWS FrTrcv p. 46).

FrTrcv_GetTransceiverWUReason ([SWS_FrTrcv_00325]) returns the wakeup reason as FrTrcv_TrcvWUReasonType ([SWS_FrTrcv_00074]) with these values:

  • FRTRCV_WU_NOT_SUPPORTED
  • FRTRCV_WU_BY_BUS
  • FRTRCV_WU_BY_PIN
  • FRTRCV_WU_INTERNALLY
  • FRTRCV_WU_RESET
  • FRTRCV_WU_POWER_ON

The type definition is in Fr_GeneralTypes.h and can thus be shared by multiple transceiver drivers (SWS FrTrcv p. 34). How exactly wakeup reasons can be distinguished depends heavily on the hardware (SWS FrTrcv p. 42). FrTrcv_ClearTransceiverWakeup clears pending wakeup events of all types under control of the upper layer. The service can also be used when wakeup notification is disabled ([SWS_FrTrcv_00329], SWS FrTrcv p. 44).

In dual-channel wakeup, FrSM queries the wakeup reasons of both channels, such as FRTRCV_WU_POWER_ON or FRTRCV_WU_BY_BUS. Subsequently, it switches both transceivers to FRTRCV_TRCVMODE_NORMAL (SWS FrSM p. 54, SWS FrSM p. 56).

Sequence diagram: The cyclic polling stores wakeup events; a call to FrTrcv_CheckWakeupByTransceiver reports them to EcuM, after which the wakeup reason and event are queried and cleared, respectively. Sources: [SWS_FrTrcv_00330], [SWS_FrTrcv_00331], [SWS_FrTrcv_00325], [SWS_FrTrcv_00329], SWS FrTrcv p. 49

Sequence diagram (simplified): FrSM uses the wakeup reasons of both channels to select the wakeup channel and subsequently switches both transceivers to NORMAL. Sources: SWS FrSM p. 54, SWS FrSM p. 56, [SWS_FrTrcv_00325]

Active star branches: error status and branch control

The branch APIs are only available if branches of active stars are configured. Optional functionality is enabled or disabled at pre-compile time (SWS FrTrcv p. 52). FrTrcv_GetTransceiverError returns a uint32 error status for a pair of FrTrcv_TrcvIdx and FrTrcv_BranchIdx. The service is not reentrant ([SWS_FrTrcv_00419]). All mandatory errors of the FlexRay EPL supported by the hardware are accessible via it. In case of an invalid index or missing status, it returns E_NOT_OK (SWS FrTrcv p. 48).

Faulty branches are disabled with FrTrcv_DisableTransceiverBranch ([SWS_FrTrcv_00442]). Switching back on with FrTrcv_EnableTransceiverBranch occurs synchronously with the FlexRay bus schedule ([SWS_FrTrcv_00443], SWS FrTrcv p. 51). If an index is out of range, the branch state remains unchanged. Without prior initialization, both services report FRTRCV_E_UNINIT when error detection is active (SWS FrTrcv p. 50).

Configuration, hardware access, and partitions

The module supports only VARIANT-PRE-COMPILE and no post-build variants. The configuration consists of exactly one container FrTrcvGeneral and at least one container FrTrcvChannel (SWS FrTrcv p. 59). Per channel, the choice container FrTrcvAccess selects between pin access via Dio (FrTrcvDioAccess) and access via Spi (FrTrcvSpiSequence) (SWS FrTrcv p. 59, SWS FrTrcv p. 77). These citations originate from R23-11 and later releases. Interpretation: The structure is likely essentially the same for R20-11.

The global parameters include:

  • FrTrcvMainFunctionCycleTime
  • FrTrcvDevErrorDetect
  • FrTrcvGetVersionInfo
  • FrTrcvSleepSupported
  • FrTrcvReceiveonlySupport

This list originates from ECUC-Parameter p. 250. If FrTrcvDemReportErrorStatusConfiguration is set, the driver calls the function configured there with the same signature instead of Dem_SetEventStatus ([SWS_FrTrcv_00475]).

In partitioned systems, the module operates as an independent instance in each partition; an API call affects only the calling partition ([SWS_FrTrcv_00494]). The module must reject partition assignments that the implementation does not support ([SWS_FrTrcv_00497]).

Behavior in the event of an error

Development errors are specified in [SWS_FrTrcv_00085]:

  • FRTRCV_E_FR_INVALID_TRCVIDX (0x01): Transceiver index out of range.
  • FRTRCV_E_FR_INVALID_BRANCHIDX (0x02): Branch index out of range.
  • FRTRCV_E_UNINIT (0x10): Service called without initialization.
  • FRTRCV_E_PARAM_POINTER (0x15): NULL pointer as parameter.

For example, a NULL pointer at FrTrcv_GetVersionInfo leads to FRTRCV_E_PARAM_POINTER when error detection is active (SWS FrTrcv p. 43).

Runtime errors describe two error patterns ([SWS_FrTrcv_91001]):

  • Call in the wrong operating mode: FRTRCV_E_FR_TRCV_NOT_STANDBY (0x11) to FRTRCV_E_FR_TRCV_NOT_RECEIVEONLY (0x14).
  • Missing or incorrect communication with the transceiver: FRTRCV_E_FR_NO_CONTROL_TRCV (0x16).

FrTrcv_GetTransceiverMode reports FRTRCV_E_FR_NO_CONTROL_TRCV in the event of an error during transceiver access (SWS FrTrcv p. 41). Runtime errors are reported via Det_ReportRuntimeError; if a callout is configured, it is called ([SWS_FrTrcv_00493]).

For production diagnosis, there are two DEM events per transceiver:

  • FRTRCV_E_FR_BUSERROR_TRCV_<TrcvIdx> for SPI-controlled class B transceivers. The event is considered failed as soon as one of the bits 1…9 is set ([SWS_FrTrcv_00488]).
  • FRTRCV_E_FR_ERRN_TRCV_<TrcvIdx> for GPIO-controlled class A transceivers. The event is considered failed when the ERRN pin is active low ([SWS_FrTrcv_00489]).

An unexpected HALT of the communication controller serves as the criterion for "error", NORMAL_ACTIVE as the criterion for "passed". In case of a short circuit on the bus, the driver's passed information alone is not sufficient (SWS FrTrcv p. 25). Later releases write the event name without angle brackets; normative for R20-11 is the name from the requirement (SWS FrTrcv p. 27).

The following applies consistently to the return values: E_NOT_OK leaves output parameters unchanged ([SWS_FrTrcv_00324], [SWS_FrTrcv_00325], [SWS_FrTrcv_00419]). The transceiver mode also remains unchanged with E_NOT_OK ([SWS_FrTrcv_00323]).

Activity diagram: A service call undergoes initialization, pointer, and index checks as well as hardware access; each error path terminates with a notification and E_NOT_OK without a state change. Sources: [SWS_FrTrcv_00085], [SWS_FrTrcv_91001], [SWS_FrTrcv_00442], SWS FrTrcv p. 41
