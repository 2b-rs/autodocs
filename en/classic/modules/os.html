Role of the Classic OS and Its Neighbors in the BSW Stack

The os module is the real-time core of the Classic Platform. It manages counters, schedule tables, OS-Applications, cores, and spinlocks, and provides its services via Os.h, for example StopScheduleTable [SWS_Os_00006] or GetSpinlock [SWS_Os_00686]. Timers that the OS uses directly and that are not managed by the GPT driver are initialized and configured by the OS itself (SWS OS p. 39). The IOC is also part of the operating system. Alongside RTE-internal and cross-ECU communication, it forms the third type of communication (SWS OS p. 119).

Other BSW modules may only use the OS to a limited extent. The general BSW specification specifies in a table which module groups are permitted to call which OS services: RTE/BSW-Scheduler, BswM, EcuM, MCAL, StbM, and the remaining modules (SWS BSW General p. 48).

  • The EcuM starts cores with StartCore [SWS_Os_00676] and shuts them down with ShutdownAllCores [SWS_Os_00713] (SWS EcuM p. 82).
  • The StbM uses the synchronization services for schedule tables (SWS StbM p. 152).
  • Complex Drivers shall restrict themselves to GetCounterValue and GetElapsedValue (CDD-Leitfaden p. 21).

Context diagram: EcuM, StbM, RTE, Complex Drivers, and the OS-Applications each use the OS via their own, clearly delimited group of services. Sources: SWS BSW General p. 48, SWS EcuM p. 82, SWS StbM p. 152, SWS OS p. 122, [SWS_Os_00097]

Counters and Schedule Tables: From Tick to Expiry Point

There are three services for counters:

  • GetCounterValue [SWS_Os_00383] returns the current tick of a counter.
  • GetElapsedValue [SWS_Os_00392] returns the difference to a previously read value. Hardware timers are adjusted so that the smallest value is zero and consecutive readings increase until an overflow occurs (SWS OS p. 39).
  • IncrementCounter [SWS_Os_00399] only increments software counters. For hardware counters, it returns E_OS_ID. If an alarm action triggered in the process fails, it calls the error hooks, but returns E_OK itself (SWS OS p. 190).

If OsSecondsPerTick is configured, the OS additionally provides the service interface OsService_{Counter}. It operates with values of type TimeInMicrosecondsType [SWS_Os_00560] [SWS_Os_00794].

The application is responsible for starting and stopping a schedule table (SWS OS p. 46). There are two start variants:

  • StartScheduleTableAbs [SWS_Os_00358] processes the initial expiry point as soon as the counter reaches the value Start + InitialOffset.
  • StartScheduleTableRel [SWS_Os_00347] calculates relatively: Now + Offset + InitialOffset. In EXTENDED status, it rejects an offset of 0 or greater than OsCounterMaxAllowedValue − InitialOffset with E_OS_VALUE. For implicitly synchronized tables, it returns E_OS_ID (SWS OS p. 179).

Both variants report E_OS_STATE if the table is already started [SWS_Os_00358].

Additional control services:

  • StopScheduleTable [SWS_Os_00006] aborts processing immediately. A later restart begins at the start of the table again (SWS OS p. 46).
  • NextScheduleTable [SWS_Os_00191] switches to a next table after the end of the running table. Until then, the next table reports SCHEDULETABLE_NEXT. If another counter drives the target table, the service returns E_OS_ID (SWS OS p. 184).
  • GetScheduleTableStatus [SWS_Os_00227] returns the state as ScheduleTableStatusType [SWS_Os_00784] via the reference [SWS_Os_00785] (SWS OS p. 189).

State diagram: Lifecycle of a schedule table with all five values of ScheduleTableStatusType, including the states for explicit synchronization. Sources: SWS OS p. 43, SWS OS p. 49, [SWS_Os_00784]

Explicit Synchronization with a Global Time Base

There are two synchronization types:

  • Implicit: The synchronization counter drives the table directly. Only the states STOPPED, NEXT, and RUNNING_AND_SYNCHRONOUS occur (SWS OS p. 48).
  • Explicit (OsScheduleTblSyncStrategy = EXPLICIT): Another OS counter drives the table. StartScheduleTableSynchron [SWS_Os_00201] starts it only when a synchronization value is available. The initial expiry point then follows after (Duration − Value) + InitialOffset ticks of the driving counter (SWS OS p. 49). The service rejects tables without the strategy EXPLICIT with E_OS_ID (SWS OS p. 185).

SyncScheduleTable [SWS_Os_00199] passes the current value of the synchronization counter. Because the table duration corresponds to the modulus of this counter, the OS can determine the drift (SWS OS p. 52). Corrections are made at adjustable expiry points, within the configured limits for shortening and lengthening (SWS OS p. 57).

SetScheduletableAsync [SWS_Os_00422] terminates synchronization while the expiry points continue to be processed. Later releases write the service SetScheduleTableAsync (SWS OS p. 188).

A typical user is the StbM. In its main function, it queries the table status. It only calls SyncScheduleTable in the states WAITING, RUNNING, or RUNNING_AND_SYNCHRONOUS (SWS StbM p. 220). The safety documents assign these services to the safety requirement \"Synchronization with global time\" (Safety Concept Status Report p. 49, Functional Safety Measures p. 66).

Sequence diagram: The StbM synchronizes a schedule table cyclically and only when its status permits it. Sources: SWS StbM p. 220, [SWS_Os_00227], [SWS_Os_00199]

OS-Applications: Assignment, Access Rights, and Trusted Functions

An OS-Application combines trusted functions, tasks, ISRs, alarms, schedule tables, counters, and hooks into a configurable unit. It is either trusted or non-trusted (SWS OS p. 61). Two services exist for identification:

  • GetApplicationID [SWS_Os_00016] returns the configured OS-Application of the caller.
  • GetCurrentApplicationID [SWS_Os_00797] returns the OS-Application in which the caller is currently executed. Outside of CallTrustedFunction, both values match. From a Category 1 ISR, the value is undefined [SWS_Os_00798]. If no OS-Application is running, it is INVALID_OSAPPLICATION [SWS_Os_00799].

The IDs of type ApplicationType [SWS_Os_00772] are zero-based and consecutive [SWS_Os_00826].

CheckObjectOwnership [SWS_Os_00017] determines which OS-Application an object belongs to. CheckObjectAccess [SWS_Os_00256] checks whether an OS-Application may use the ID of a task, resource, counter, alarm, or schedule table. For invalid arguments, it returns NO_ACCESS (SWS OS p. 177). If a caller passes an object ID without configured access permission to a system service, the service terminates with E_OS_ACCESS. The check services themselves are exempt from this rule (SWS OS p. 73).

Memory access rights are queried by CheckTaskMemoryAccess [SWS_Os_00513] and CheckISRMemoryAccess [SWS_Os_00512]. An access right applies only if it exists for the entire requested area (SWS OS p. 174). The result of type AccessType [SWS_Os_00777] is evaluated with macros such as OSMEMORY_IS_WRITEABLE (SWS OS p. 160). Even trusted OS-Applications can be operated with restricted write access [SWS_Os_00795].

CallTrustedFunction [SWS_Os_00097] calls a function addressed via TrustedFunctionIndexType [SWS_Os_00775]. The function runs with the protection settings of the providing OS-Application. The arguments are passed as a structure via TrustedFunctionParameterRefType [SWS_Os_00776] (SWS OS p. 172). If the index is not configured, the OS calls the ErrorHook with E_OS_SERVICEID (SWS OS p. 85). In R20-11, the service is synchronous or asynchronous, depending on how the called function behaves [SWS_Os_00097]. The BSW Distribution Guide uses it to route calls between BSW modules in different partitions (BSW Distribution Guide p. 66).

Sequence diagram: A call to a trusted function runs via stub and OS check up to execution in the providing OS-Application. Sources: SWS OS p. 185, SWS OS p. 396, [SWS_Os_00097]

Peripheral Access and Interrupt Sources under Service Protection

There are three service families for access to peripheral addresses. All address an area of type AreaIdType [SWS_Os_91000]:

  • ReadPeripheral8/16/32 [SWS_Os_91013] [SWS_Os_91015] [SWS_Os_91014]
  • WritePeripheral8/16/32 [SWS_Os_91010] [SWS_Os_91012] [SWS_Os_91011]
  • ModifyPeripheral8/16/32 [SWS_Os_91016] [SWS_Os_91018] [SWS_Os_91017]. The modify services calculate *Address = ((*Address & Clearmask) | Setmask) (SWS OS p. 175).

In EXTENDED status, these services report E_OS_ID, E_OS_VALUE (address outside the area), or E_OS_CALLEVEL. E_OS_ACCESS occurs when the calling task or ISR has no access (SWS OS p. 195).

For each Category 2 ISR, the OS provides three services [SWS_Os_00808]: DisableInterruptSource [SWS_Os_91019], EnableInterruptSource [SWS_Os_91020], and ClearPendingInterrupt [SWS_Os_91021]. The following rules apply:

  • Anyone disabling an already disabled source again or enabling an already enabled source again receives E_OS_NOFUNC [SWS_Os_00809] in EXTENDED status.
  • Detected errors are returned and reported to the ErrorHook [SWS_Os_00810].
  • ClearPendingInterrupt only clears the pending flag in the interrupt controller [SWS_Os_00813] [SWS_Os_00814].
  • If an OS-Application calls the services for an ISR that does not belong to it, it receives E_OS_ACCESS (SWS OS p. 177).

Caution, contradiction: [SWS_Os_00811] requires clearing the pending flag when enabling. The API definition [SWS_Os_91020] makes precisely that selectable via the parameter ClearPending.

Multicore Operation: Core Start, Spinlocks, IOC, and Coordinated Shutdown

StartCore [SWS_Os_00676] starts an additional core under the control of the AUTOSAR OS. After StartOS, calls return E_OS_ACCESS. Subsequently, StartOS must be called on each core started in this way (SWS OS p. 166). These detailed rules originate from later specification versions. Interpretation: They are likely to apply to R20-11 as well, because the R20-11 definitions specify the same return values [SWS_Os_00676].

Additional core services:

  • StartNonAutosarCore [SWS_Os_00682] starts cores outside the AUTOSAR OS.
  • GetCoreID [SWS_Os_00674] returns the logical ID of type CoreIdType [SWS_Os_00790]. The value range is zero-based and consecutive [SWS_Os_00825].
  • In R20-11, GetNumberOfActivatedCores [SWS_Os_00672] counts the cores activated via StartCore. Later releases refer instead to the cores on which the AUTOSAR OS is running (SWS OS p. 196).

Spinlocks protect shared data across core boundaries:

  • GetSpinlock [SWS_Os_00686] waits actively without the caller being preempted (SWS OS p. 199).
  • TryToGetSpinlock [SWS_Os_00703] returns immediately if a task on another core holds the lock and reports the result via TryToGetSpinlockType [SWS_Os_00792] (SWS OS p. 203).
  • ReleaseSpinlock [SWS_Os_00695] releases the lock.
  • The value 0 of SpinlockIdType represents INVALID_SPINLOCK [SWS_Os_00791].

In EXTENDED status, the OS detects two types of deadlocks: preemption on the same core (E_OS_INTERFERENCE_DEADLOCK) and incorrect nesting (E_OS_NESTING_DEADLOCK). Via OsSpinlockLockMethod, the OS can automatically protect the lock against preemption (SWS OS p. 101).

A ActivateTask across core boundaries behaves synchronously. The asynchronous variants ActivateTaskAsyn [SWS_Os_91022] [SWS_Os_00816] and SetEventAsyn [SWS_Os_91023] [SWS_Os_00817] report errors only via the global ErrorHook (SWS OS p. 103). They are only available in systems with OS-Applications [SWS_Os_00818] [SWS_Os_00819].

The IOC transfers data using generated functions (SWS OS p. 218):

  • IocWrite [SWS_Os_91003] and IocRead [SWS_Os_91005] for unbuffered \"data\" semantics.
  • IocSend [SWS_Os_00718] and IocReceive [SWS_Os_00738] for buffered \"event\" semantics.
  • Group variants [SWS_Os_00728] [SWS_Os_91004] [SWS_Os_00746] [SWS_Os_91006], IocEmptyQueue [SWS_Os_00754], and an optional receiver callback [SWS_Os_00757].

As a DRAFT, R20-11 also contains IocInit [SWS_Os_91026] [SWS_Os_00835], which calls StartOS in default mode [SWS_Os_00830]. Separate generator modes for OS and IOC code are also DRAFT [SWS_Os_00831] [SWS_Os_00833] [SWS_Os_00834].

ControlIdle [SWS_Os_00769] specifies per core what happens during idle time. The default is IDLE_NO_HALT [SWS_Os_00793]. Invalid core or mode specifications return E_OS_ID [SWS_Os_00771], valid ones E_OK [SWS_Os_00770].

ShutdownAllCores shuts down the OS synchronously on all cores and never returns. Calls from non-trusted code are ignored (SWS OS p. 204). First, the application-specific shutdown hooks [SWS_Os_00541] run, and then, after synchronization of all cores, the global ShutdownHook (SWS OS p. 98).

Sequence diagram: The EcuM starts all cores before StartOS; ShutdownAllCores distributes the shutdown to the remaining cores and synchronizes them before the ShutdownHook. Sources: SWS EcuM p. 82, SWS EcuM p. 91, SWS OS p. 98, [SWS_Os_00713]

Behavior in the event of an error

Many checks exist only in EXTENDED status, such as E_OS_ID for invalid IDs (SWS OS p. 182). In this mode, the OS also checks pointer arguments for NULL_PTR and then returns E_OS_ILLEGAL_ADDRESS (SWS OS p. 38). The OS-specific error codes such as E_OS_PROTECTION_MEMORY, E_OS_STACKFAULT, or E_OS_CORE are defined in [SWS_Os_91025]. If a task or category 2 ISR causes an error, the ErrorHook of its OS-Application is called, ErrorHook_<App> [SWS_Os_00540].

Severe errors such as memory or timing violations trigger the ProtectionHook [SWS_Os_00538]. Its return value of type ProtectionReturnType [SWS_Os_00787] determines the reaction. The OS then terminates the task or ISR, terminates the OS-Application (with or without restart), or shuts down the system (SWS OS p. 187).

Activity diagram: The return value of the ProtectionHook determines the reaction of the OS to a protection violation. Sources: SWS OS p. 187, EXP ALEH p. 69, [SWS_Os_00787]

If the OS terminates an OS-Application, it terminates its running, ready, and waiting tasks and ISRs. In addition, it disables its interrupts and stops its alarms and schedule tables (SWS OS p. 62).

TerminateApplication [SWS_Os_00258] terminates its own OS-Application. Only a trusted caller is allowed to terminate another OS-Application. In R20-11, the option RestartType [SWS_Os_00788] has the values RESTART and NO_RESTART. Later releases only support OS_OSAPPLICATION_RESTART and ignore the parameter (SWS OS p. 158, SWS OS p. 194).

GetApplicationState [SWS_Os_00499] returns the state of an OS-Application according to ApplicationStateType [SWS_Os_00773]. From APPLICATION_RESTARTING, it returns to APPLICATION_ACCESSIBLE with AllowAccess [SWS_Os_00501].

The guide on application-level error handling describes the restart. The OS activates the OSRestartTask. This initiates cleanup operations in other partitions via CallTrustedFunction (EXP ALEH p. 69, EXP ALEH p. 76).

For asynchronous services, errors do not reach the caller. If the caller has already terminated, the ErrorHook calls are also omitted (SWS OS p. 203).

State diagram: Lifecycle of an OS-Application in R20-11 with restart phase and return via AllowAccess. Sources: SWS OS p. 59, EXP ALEH p. 53, SWS OS p. 62, [SWS_Os_00773], [SWS_Os_00501]

use

With the system service CallTrustedFunction ([SWS_Os_00097]), an OS-Application—regardless of whether it is configured as trusted or non-trusted—can call a defined Trusted Function. The declaration is provided via the header file Os.h.

Two input parameters are passed to DEM service:

  • FunctionIndex (type TrustedFunctionIndexType): Designates the index of the Trusted Function to be called ([SWS_Os_00097]).
  • FunctionParams (type TrustedFunctionParameterRefType): Pointer to the function parameters. If no parameters are required, a NULL pointer must be passed ([SWS_Os_00097]).

The synchronous or asynchronous behavior of CallTrustedFunction depends directly on the called function: If the called Trusted Function is synchronous, the service call also behaves synchronously. In addition, the call can trigger rescheduling in the operating system ([SWS_Os_00097]).

Error handling

The service returns a status value of type StatusType ([SWS_Os_00097]):

  • E_OK: The call was executed without error.
  • E_OS_SERVICEID: No function is defined for the specified FunctionIndex.

Concurrency and Limitations
