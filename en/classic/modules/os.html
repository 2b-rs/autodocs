Controls time-triggered operations, protects OS-Applications from each other, and coordinates the cores of an ECU.

The operating system executes tasks and ISRs, drives counters and schedule tables, and partitions software into protected OS-Applications. The EcuM starts the cores with StartCore; thereafter, StartOS is called on each core [SWS_Os_00676]. Schedule tables can be explicitly synchronized with a global time via the StbM. Accesses to foreign objects are possible only with configured permissions SWS OS p. 62. Upon protection violations, the ProtectionHook decides whether a task, an OS-Application, or the entire system is terminated.

Role of the Operating System and Its Neighbors in the ECU

The operating system is the execution core of the Classic stack. It manages tasks, ISRs, alarms, counters, and schedule tables. It bundles these objects together with hooks and trusted functions into configurable OS-Applications, which are either trusted or non-trusted SWS OS p. 61. In addition, it initializes and configures all timers that it uses itself and that are not managed by the GPT driver SWS OS p. 39.

The neighboring modules access it via delimited interfaces:

  • The EcuM controls startup and shutdown via StartOS, StartCore, GetCoreID, and ShutdownAllCores SWS EcuM p. 34.
  • The StbM uses GetCounterValue, GetElapsedValue, GetScheduleTableStatus, and SyncScheduleTable SWS StbM p. 152.
  • Software components reach OS services via an RTE port with the service interface OsService TR VFB p. 89. For counters with configured OsSecondsPerTick, this interface provides GetCounterValue and GetElapsedValue, among others [SWS_Os_00560].

For BSW modules, a table specifies which OS services they are allowed to use at all SWS BSWGeneral p. 48. Communication between OS-Applications is handled by the IOC. It is part of the operating system and is invoked by the RTE SWS OS p. 119, [SWS_Os_00718].

Context diagram: The Os is used by EcuM, StbM, RTE, and BSW modules via their respective service groups and encapsulates the IOC as well as hardware accesses. Sources: SWS EcuM p. 34, SWS StbM p. 152, TR VFB p. 89, SWS OS p. 119

Startup, Core Management, and Shutdown

In multi-core operation, the EcuM starts all configured cores in a loop on the master core using StartCore. Afterwards, it calls StartOS(ECUM_DEFAULT_APP_MODE) SWS EcuM p. 82. On each started core, StartOS must also be called [SWS_Os_00676]. This is handled by the EcuM of the respective slave core after GetCoreID SWS EcuM p. 83.

The following rules apply to StartCore SWS OS p. 166:

  • The service is not reentrant.
  • A call after StartOS returns E_OS_ACCESS, and the core is not started.
  • An already started core results in E_OS_STATE.

For cores outside the control of the AUTOSAR OS, StartNonAutosarCore exists [SWS_Os_00682].

Cores are identified via CoreIdType. The logical IDs are zero-based and consecutive, and OS_CORE_ID_MASTER designates the master core [SWS_Os_00790], [SWS_Os_00825]. GetCoreID returns the logical ID of the calling core [SWS_Os_00674]. The service can already be called before StartOS SWS OS p. 111.

After StartOS and before the first StartupHook, the OS sets all OS-Applications to APPLICATION_ACCESSIBLE SWS OS p. 62. This is followed by the system-wide StartupHook. Only then do the application-specific StartupHook_<App> run, each with the permissions of their OS-Application SWS OS p. 134, [SWS_Os_00539].

Sequence diagram: The master core starts the remaining cores before its own StartOS; each core calls StartOS itself, a later StartCore is rejected. Sources: SWS EcuM p. 82, SWS EcuM p. 83, SWS OS p. 166, SWS OS p. 188

In R20-11, GetNumberOfActivatedCores returns the number of cores activated with StartCore [SWS_Os_00672]. Later versions speak instead of "cores on which the AUTOSAR OS is running" SWS OS p. 196.

With ControlIdle, the action for the idle time is selected per core, for example to save power. The default is IDLE_NO_HALT. An unknown core or mode results in E_OS_ID [SWS_Os_00769], [SWS_Os_00771], [SWS_Os_00793].

ShutdownAllCores shuts down the OS on all AUTOSAR cores, forces the other cores into shutdown, and never returns [SWS_Os_00713]. In doing so, the ShutdownHook_<App> run first. Then the cores synchronize, and only after that does the global ShutdownHook follow SWS OS p. 98, [SWS_Os_00541].

Counters and ScheduleTables as Time Base

GetCounterValue returns the timer value for hardware counters and the software ticks for software counters. The OS corrects hardware values so that they start at zero and increase up to the modulus SWS OS p. 39, [SWS_Os_00383].

GetElapsedValue returns the ticks since a previously read value. If Value is greater than the maximum allowed counter value, E_OS_VALUE follows SWS OS p. 192, [SWS_Os_00392].

IncrementCounter only increments software counters; for hardware counters, it returns E_OS_ID. If an alarm action fails during this, the OS calls the error hooks, but the service itself returns E_OK SWS OS p. 190, [SWS_Os_00399].

Starting and stopping a ScheduleTable is the task of the application SWS OS p. 46. The Initial Expiry Point is processed at the following counter value:

  • StartScheduleTableAbs: at Start + InitialOffset [SWS_Os_00358].
  • StartScheduleTableRel: at Now + Offset + InitialOffset [SWS_Os_00347].

For relative start, an offset of 0 or greater than OsCounterMaxAllowedValue − InitialOffset results in the error E_OS_VALUE. An already started table results in E_OS_STATE SWS OS p. 179.

StopScheduleTable aborts immediately; an already stopped table results in E_OS_NOFUNC [SWS_Os_00006]. A later restart begins at the start of the table SWS OS p. 46.

NextScheduleTable chains a subsequent table. Both tables must be driven by the same counter; otherwise, E_OS_ID follows [SWS_Os_00191], SWS OS p. 184.

For a table that has not been started, GetScheduleTableStatus reports SCHEDULETABLE_STOPPED together with E_OK SWS OS p. 189, [SWS_Os_00784].

State diagram: Lifecycle of a ScheduleTable with all states of ScheduleTableStatusType; WAITING and RUNNING occur only with explicit synchronization, implicitly synchronized tables only know STOPPED, NEXT, and RUNNING_AND_SYNCHRONOUS. Sources: [SWS_Os_00784], SWS OS p. 43, SWS OS p. 49, SWS OS p. 48

Synchronization of ScheduleTables with Global Time

With implicit synchronization, the driving counter itself is the synchronization counter. The table then knows only three states SWS OS p. 48. StartScheduleTableRel returns the error E_OS_ID for OsScheduleTblSyncStrategy = IMPLICIT SWS OS p. 179. Explicit synchronization, on the other hand, aligns a locally driven table to an external synchronization counter. It is listed as a safety measure for coupling to the time base of the StbM Safety Measures p. 66.

There are two ways to start SWS OS p. 49, [SWS_Os_00201]:

  • Asynchronously via StartScheduleTableAbs or StartScheduleTableRel, relative to the driving counter.
  • Synchronously via StartScheduleTableSynchron. Here, the Initial Expiry Point is processed (Duration − Value) + InitialOffset ticks after provision of the synchronization value.

SyncScheduleTable passes the current value of the synchronization counter. Its modulus corresponds to the table duration SWS OS p. 52, [SWS_Os_00199].

The OS calculates the deviation from this and adjusts the delay at each expiry point. If the deviation is within OsScheduleTblExplicitPrecision, the table is considered "running and synchronous" SWS OS p. 57. SetScheduleTableAsync stops tracking until the next SyncScheduleTable; the expiry points continue to run during this SWS OS p. 188, [SWS_Os_00422].

Sequence diagram: The StbM cyclically queries the table status and provides a synchronization value only if the table is started. Sources: SWS StbM p. 220, SWS StbM p. 117, [SWS_Os_00227], [SWS_Os_00199]

Protection Concept: OS-Applications, Access Rights, and Trusted Functions

The OS prevents an OS-Application from accessing foreign objects unless the configuration explicitly permits it SWS OS p. 62. If the permissions are missing, a service returns E_OS_ACCESS. Excluded are the checking services for memory and object access, which are always permitted SWS OS p. 73.

The following queries are available at runtime:

  • GetApplicationID names the OS-Application to which the caller is configured [SWS_Os_00016].
  • GetCurrentApplicationID names the OS-Application in which the caller is currently being executed. Both values differ only within CallTrustedFunction [SWS_Os_00797], [SWS_Os_00798].
  • CheckObjectOwnership returns the owner of an object or INVALID_OSAPPLICATION SWS OS p. 178.
  • CheckObjectAccess returns ACCESS or NO_ACCESS; for invalid arguments, always NO_ACCESS SWS OS p. 177.

CheckTaskMemoryAccess and CheckISRMemoryAccess return, as AccessType, the access rights to a memory area and whether it belongs to the stack. A right that does not apply to the entire area is denied. An invalid ID results in no rights at all SWS OS p. 175, SWS OS p. 174. The result is evaluated using macros such as OSMEMORY_IS_WRITEABLE SWS OS p. 160.

CallTrustedFunction executes a function with the protection settings of the providing OS-Application. If the index is not configured, E_OS_SERVICEID and a call to ErrorHook follow SWS OS p. 85, SWS OS p. 172. In R20-11, the synchronous behavior depends on the called function, and the call can trigger a rescheduling [SWS_Os_00097]. Write access must also be restrictable for trusted OS-Applications [SWS_Os_00795].

Sequence diagram: A stub wraps the arguments; the OS checks authorization and only then switches to the providing OS-Application, whose function in turn checks memory rights. Sources: SWS OS p. 185, SWS OS p. 396, [SWS_Os_00097]

For protected hardware accesses, ReadPeripheral, WritePeripheral, and ModifyPeripheral are available in 8, 16, and 32 bits. They operate on peripheral areas of type AreaIdType [SWS_Os_91000]. The modify variant computes *Address = (*Address & Clearmask) | Setmask SWS OS p. 209.

For each Category 2 ISR, DisableInterruptSource, EnableInterruptSource, and ClearPendingInterrupt exist [SWS_Os_00808]. ClearPendingInterrupt clears only the pending flag in the interrupt controller [SWS_Os_00814].

Difference between the versions: In R20-11, EnableInterruptSource always clears the pending flag [SWS_Os_00811], even though the signature contains a parameter ClearPending. Later versions describe clearing as optional SWS OS p. 177.

Coordination Across Cores and Partitions

Spinlocks operate across core boundaries. GetSpinlock busy-waits without unscheduling the caller and can be called at task and Category 2 ISR level SWS OS p. 115. In Extended Status, it detects two deadlock cases [SWS_Os_00686]:

  • E_OS_INTERFERENCE_DEADLOCK: A task on the same core already holds the lock.
  • E_OS_NESTING_DEADLOCK: Nesting with another held spinlock is not allowed.

TryToGetSpinlock returns when a task on another core occupies the lock. It then returns E_OK with TRYTOGETSPINLOCK_NOSUCCESS [SWS_Os_00703], [SWS_Os_00792]. Before terminating a task and before WaitEvent, all spinlocks must be released in the correct order [SWS_Os_00695]. Enclosing with SuspendAllInterrupts or the setting OsSpinlockLockMethod helps against interference SWS OS p. 101.

ActivateTask across core boundaries operates synchronously. The error handler runs on the calling core SWS OS p. 103. In contrast, ActivateTaskAsyn and SetEventAsyn do not return any errors to the caller, but only report them to the global error hook [SWS_Os_00816], [SWS_Os_00817]. Both exist only in systems with OS-Applications [SWS_Os_00818], [SWS_Os_00819]. If the caller no longer exists, the notification is omitted SWS OS p. 179.

The IOC generates its functions per sender and receiver:

  • Sending: IocSend (queued) and IocWrite (unqueued) operate asynchronously [SWS_Os_00718], [SWS_Os_91003].
  • Receiving: IocReceive and IocRead operate synchronously [SWS_Os_00738], [SWS_Os_91005].
  • Groups: Group variants [SWS_Os_00728], [SWS_Os_00746] exist.
  • Additional services: IocEmptyQueue and a configurable <ReceiverPullCB> complement the offering [SWS_Os_00754], [SWS_Os_00757].

If the buffer is full, the sender reports IOC_E_LIMIT, and the receiver receives IOC_E_LOST_DATA on the next read SWS OS p. 219. IocInit and the separate generation of OS and IOC code still have the status DRAFT in R20-11 [SWS_Os_00835], [SWS_Os_00831], [SWS_Os_00834].

Behavior in the event of an error

Many checks, such as for E_OS_ID, are performed only in Extended Status. Pointer arguments are checked there for NULL_PTR and rejected with E_OS_ILLEGAL_ADDRESS SWS OS p. 38. Additional error identifiers such as E_OS_PROTECTION_MEMORY and E_OS_STACKFAULT are defined centrally [SWS_Os_91025]. If a service does not return E_OK, the OS calls the ErrorHook and the ErrorHook_<App> SWS OS p. 186, [SWS_Os_00540].

In the event of severe errors, the OS calls the ProtectionHook. Its ProtectionReturnType determines the further reaction [SWS_Os_00538], [SWS_Os_00787]. If no ProtectionHook is configured, the OS calls ShutdownOS EXP ALEH p. 60. When terminating an OS-Application, the OS stops all associated objects SWS OS p. 62:

  • all tasks and ISRs,
  • their interrupts,
  • their alarms,
  • their schedule tables.

Sequence diagram: The return value of the ProtectionHook selects between ignoring, terminating the task/ISR, terminating the OS-Application (with or without restart), and shutdown. Sources: SWS OS p. 187, [SWS_Os_00538], [SWS_Os_00787]

An OS-Application is APPLICATION_ACCESSIBLE, APPLICATION_RESTARTING, or APPLICATION_TERMINATED. The state is returned by GetApplicationState [SWS_Os_00773], [SWS_Os_00499]. In R20-11, TerminateApplication accepts RESTART or NO_RESTART [SWS_Os_00258], [SWS_Os_00788]. Later versions ignore this parameter SWS OS p. 194.

In the RESTARTING state, only the OSRestartTask runs; other OS-Applications have no access. An OS-Application leaves the state APPLICATION_TERMINATED only via a reset of the ECU EXP ALEH p. 53. If necessary, the OSRestartTask cleans up via CallTrustedFunction and then releases the OS-Application again with AllowAccess EXP ALEH p. 76, [SWS_Os_00501]. The integrator provides the code for the ECU-wide ProtectionHook and the restart task EXP ALEH p. 79.

State diagram: StartOS makes each OS-Application accessible; protection reactions or TerminateApplication lead into RESTARTING or TERMINATED, only AllowAccess leads back. Sources: EXP ALEH p. 61, [SWS_Os_00773], [SWS_Os_00501]
