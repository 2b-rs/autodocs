Maps logical memory blocks to EEPROM addresses and processes read and write jobs asynchronously.

The EEPROM Abstraction maps logical blocks of NvM to addresses of an EEPROM and uses the Eep driver in R20-11. Read, write, invalidation, and erase jobs are accepted synchronously and executed asynchronously in the cyclically called Main Function ([SWS_Ea_00096]). The module reports completion or failure via callback to NvM or via the job result. A write operation always affects the entire block. Only in R20-11 do Ea_SetMode and a synchronous Ea_Cancel still exist ([SWS_Ea_00088]).

The EEPROM Abstraction (Ea) maps logical blocks to EEPROM addresses. It is located between MemIf and the EEPROM driver Eep; the block number designates at the same time the start address of the block ([SWS_Ea_00087]). Downward, Ea in R20-11 uses the Eep services for reading, writing, erasing, cancelling, and mode switching ([SWS_Ea_00097]). Only starting with R21-11 does MemAcc replace the Eep driver and Ea_SetMode is omitted (SWS EA p. 1).

Context diagram: Ea between NvM/MemIf and Eep, initialized by EcuM and driven by the BSW Scheduler. Sources: [SWS_Ea_00084], [SWS_Ea_00096], [SWS_Ea_00097]

After Ea_Init with a pointer to the configuration set ([SWS_Ea_00084]), Ea_GetStatus reports one of the states MEMIF_IDLE, MEMIF_BUSY, or MEMIF_BUSY_INTERNAL ([SWS_Ea_00089]). The last one represents internal management such as garbage collection (SWS EA p. 28).

Read, write, invalidation, and immediate erase are asynchronous. E_OK only confirms that the job was accepted. Execution takes place in the cyclically called Ea_MainFunction ([SWS_Ea_00086], [SWS_Ea_00096]). Reading is possible with an arbitrary offset and arbitrary length. Writing always affects the entire block with offset zero (SWS EA p. 25). That the write job also starts in the Main Function is an interpretation.

Sequence diagram: synchronous acceptance, asynchronous execution via Eep, and feedback via callback to NvM. Sources: SWS Eep p. 50, [SWS_Ea_00094], [SWS_Ea_00099]

Ea_Cancel is synchronous in R20-11 ([SWS_Ea_00088]). The module reports errors via the codes EA_E_UNINIT to EA_E_INVALID_CANCEL ([SWS_Ea_91001], [SWS_Ea_91002]). Depending on the configuration, hardware errors reach NvM via one of two paths:

  • via querying the job result MEMIF_JOB_FAILED,
  • via the callback NvM_JobErrorNotification.

Recovery is handled in each case by NvM (ErrorDescription p. 48).

Role in the Memory Stack: from Logical Block to EEPROM Address

The EEPROM Abstraction (Ea) is located in the memory stack between the Memory Abstraction Interface (MemIf) and the EEPROM driver (Eep). Toward the upper layer, it provides block-oriented services. The block number designates a logical block and at the same time its start address in the EEPROM ([SWS_Ea_00086], [SWS_Ea_00087]). MemIf forwards read and write jobs to the abstraction module selected by the parameter DeviceIndex and passes through its return value (SWS MemIf p. 18, SWS MemIf p. 19).

Downward, Ea in R20-11 uses the services of the EEPROM driver: Eep_Read, Eep_Write, Eep_Erase, Eep_Cancel, Eep_GetStatus, Eep_GetJobResult, and Eep_SetMode. In addition, there is Det_ReportRuntimeError ([SWS_Ea_00097]). Det_ReportError is an optional interface ([SWS_Ea_00098]). The imported types Eep_AddressType, Eep_LengthType, MemIf_StatusType, MemIf_JobResultType, and MemIf_ModeType reflect this embedding ([SWS_Ea_00083]).

Regarding release classification: According to the change history, Ea_SetMode is omitted starting with R21-11. In addition, Ea_Cancel becomes asynchronous, buffer alignment is added, and MemAcc replaces Eep as the lower layer (SWS EA p. 1). For R20-11, therefore, Eep as lower layer and Ea_SetMode as service still apply. The rules for buffer alignment (SWS EA p. 19) do not apply to R20-11.

Context diagram: Ea mediates between NvM/MemIf above and the driver Eep below. EcuM initializes the module, the BSW Scheduler drives it cyclically, and DET receives error reports. Sources: [SWS_Ea_00084], [SWS_Ea_00096], [SWS_Ea_00097], [SWS_Ea_00098], [SWS_Ea_00099], [SWS_Ea_00100], SWS EA p. 34

Startup and Module States

Ea_Init initializes the module synchronously and is non-reentrant. ConfigPtr points to the selected configuration set ([SWS_Ea_00084]). Ea_ConfigType is a structure with implementation-specific elements ([SWS_Ea_00190]). According to the sequence diagram in the specification, the ECU State Manager calls Ea_Init during startup (SWS EA p. 47). Since it is only a single call, it appears as a transition in the state diagram below.

Ea_GetStatus returns the operating state synchronously as MemIf_StatusType ([SWS_Ea_00089]):

  • MEMIF_UNINIT: Before initialization.
  • MEMIF_IDLE: neither a job nor internal management is running.
  • MEMIF_BUSY: An upper-layer job is being processed.
  • MEMIF_BUSY_INTERNAL: an internal management operation is running, such as a reorganization of the EEPROM memory (garbage collection). In doing so, the driver can also be temporarily busy.

The states are described in SWS EA p. 28. The module accepts a write job in the MEMIF_IDLE state and also in the MEMIF_BUSY_INTERNAL state (SWS EA p. 25).

State diagram: Life cycle of the module status from MEMIF_UNINIT via MEMIF_IDLE to MEMIF_BUSY and MEMIF_BUSY_INTERNAL, respectively. A write job is accepted from within internal management. Sources: [SWS_Ea_00084], [SWS_Ea_00089], SWS EA p. 28, SWS EA p. 25, SWS EA p. 27

Accepting Jobs and Processing Them in Ea_MainFunction

Ea_Read, Ea_Write, Ea_InvalidateBlock, and Ea_EraseImmediateBlock are asynchronous. E_OK only means that the module has accepted the job. E_NOT_OK means that it has rejected it ([SWS_Ea_00086], [SWS_Ea_00087], [SWS_Ea_00091], [SWS_Ea_00093]). Until the result is available, Ea_GetJobResult reports the value MEMIF_JOB_PENDING ([SWS_Ea_00090]).

The actual work is performed by Ea_MainFunction, available via SchM_Ea.h ([SWS_Ea_00096]). The Basic Software Scheduler calls the function directly. It has neither parameters nor a return value and is not reentrant (SWS EA p. 36).

Activity diagram: Checks upon accepting a job and their error codes. The checking order is an assumption. Sources: [SWS_Ea_91001], [SWS_Ea_91002], [SWS_Ea_00089], [SWS_Ea_00090], SWS EA p. 25

Ea_Read calculates the read address from the block number and offset. Offset and length may take any value within their type range, allowing any number of bytes to be read from any position in the block. The read operation explicitly executes asynchronously in the Main Function (SWS EA p. 24).

Ea_Write calculates the write address from the block number with a fixed offset of zero. The function sets the length to the length configured for the block (SWS EA p. 25). A write operation therefore always affects the entire block ([SWS_Ea_00087]). The diagram for the write job shows the further path via Eep_Write, the cyclic Eep_MainFunction, Ea_JobEndNotification, and NvM_JobEndNotification (SWS Eep p. 50).

Interpretation: For reading, starting the driver job in Ea_MainFunction is explicitly required. In the case of a vendor-specific library, the sequence diagrams are binding only for the relationship to the calling modules, not for the calls to the driver (SWS EA p. 45).

Sequence diagram: A write job is accepted synchronously, executed asynchronously via the driver, and reported to the NvM via callback. Sources: SWS Eep p. 50, SWS MemIf p. 19, [SWS_Ea_00087], [SWS_Ea_00094], [SWS_Ea_00099]

Block Management: Address Mapping, Consistency, and Invalidation

Fig. 7.1 compares virtual and physical memory. The block number (16 bits) and offset (16 bits) form a virtual address, so that a block can span up to 64 KiB. Physically, the blocks are aligned to the configured virtual page size EA_VIRTUAL_PAGE_SIZE; unused virtual space occupies no memory (SWS EA p. 23).

Ea maintains dedicated consistency information for each block. At the start of a write process, the block is considered inconsistent; after successful completion, it is considered consistent again. Ea must be able to distinguish an inconsistent block from an intentionally invalidated block (SWS EA p. 19, version R24-11). For the caller, both cases become visible via the job results MEMIF_BLOCK_INCONSISTENT and MEMIF_BLOCK_INVALID ([SWS_Ea_00090]).

Ea_InvalidateBlock invalidates the block BlockNumber ([SWS_Ea_00091]). Depending on the implementation, this occurs via the driver's erase function or via internal management information, which must then be stored non-volatilely (SWS EA p. 31).

Ea_EraseImmediateBlock erases a block ([SWS_Ea_00093]). The function is intended for diagnostic or comparable system services that pre-erase the area for immediate data. It calculates the address with an offset of zero. It ensures that Ea can write immediate data (SWS EA p. 34).

Operating Mode, Cancellation, and Notifications

In R20-11, Ea_SetMode switches the mode of the EEPROM driver using the parameter Mode of type MemIf_ModeType. The service is asynchronous and not reentrant ([SWS_Ea_00085]). The shortened signature without parameters in the API elements deviates from this; the service description is authoritative. The diagrams show the chain NvM → MemIf_SetMode → Ea_SetMode → Eep_SetMode (SWS EA p. 42). From R21-11 onwards, the service is omitted (SWS EA p. 1).

Sequence diagram: A mode change is passed through from the NvM via MemIf and Ea to the driver (only up to R20-11). Sources: [SWS_Ea_00085], SWS EA p. 52, SWS EA p. 42

Ea_Cancel cancels the running asynchronous job and is synchronous in R20-11 ([SWS_Ea_00088]). The subsequent document section describes the service as asynchronous; for R20-11, the requirement applies. In terms of content, according to this passage: in state MEMIF_BUSY, Ea calls the driver's cancel function and resets its internal variables. The job result is then MEMIF_JOB_CANCELED (SWS EA p. 27). MemIf forwards the cancellation (SWS MemIf p. 20). A cancellation without a pending job yields EA_E_INVALID_CANCEL ([SWS_Ea_91002]).

Sequence diagram: Ea_Cancel branches depending on the module status into driver cancellation, error notification, or return without modification. Sources: [SWS_Ea_00088], [SWS_Ea_91002], [SWS_Ea_00097], SWS EA p. 27, SWS MemIf p. 20

The lower layer reports the success or failure of an asynchronous job via Ea_JobEndNotification or Ea_JobErrorNotification ([SWS_Ea_00094], [SWS_Ea_00095]). Ea then signals NvM_JobEndNotification or NvM_JobErrorNotification from NvM_MemIf.h to the NvM ([SWS_Ea_00099], [SWS_Ea_00100]). MemIf does not provide any callbacks itself (SWS MemIf p. 24).

Callbacks can run at interrupt level. Their execution time must therefore remain short, and the system design must align the configuration accordingly (SWS EA p. 35). Ea_GetVersionInfo is the only service that is reentrant ([SWS_Ea_00092]).

Behavior in the event of an error

The error codes are listed in two tables.

  • First table ([SWS_Ea_91001]): EA_E_UNINIT (0x01), EA_E_INVALID_BLOCK_NO (0x02), EA_E_INVALID_BLOCK_OFS (0x03), EA_E_PARAM_POINTER (0x04), and EA_E_INVALID_BLOCK_LEN (0x05).
  • Second table ([SWS_Ea_91002]): EA_E_BUSY (0x06) and EA_E_INVALID_CANCEL (0x08).

EA_E_INIT_FAILED was removed with R20-11 (SWS EA p. 1). Interpretation: The first table likely covers development errors via the optional Det_ReportError, the second runtime errors via Det_ReportRuntimeError ([SWS_Ea_00097], [SWS_Ea_00098]). Question Q-8443a03d306e4143 (open)

With development error detection active, the following applies in the uninitialized state: Ea_GetJobResult reports EA_E_UNINIT and returns MEMIF_JOB_FAILED (SWS EA p. 30). Ea_Cancel reports EA_E_UNINIT and returns without modifying internal variables (SWS EA p. 27). Ea_GetVersionInfo reports EA_E_PARAM_POINTER in case of a NULL pointer (SWS EA p. 32). Ea_InvalidateBlock and Ea_EraseImmediateBlock return E_NOT_OK only when DET is active ([SWS_Ea_00091], [SWS_Ea_00093]).

Hardware errors are detected by the EEPROM driver. The response of Ea is implementation-specific. Depending on the configuration, it is reported in one of two ways: via polling with the job result MEMIF_JOB_FAILED or via the callback NvM_JobErrorNotification. Recovery is handled by the NvM (ErrorDescription p. 48, [SWS_Ea_00095], [SWS_Ea_00100]). For the polling path, the error description specifies Eep_GetJobResult. That Ea polls this function in its Main Function is presumably intended, but not explicitly specified. Question (open)

The job result distinguishes the error types finely ([SWS_Ea_00090]):

  • MEMIF_JOB_CANCELED: Cancellation, considered failed.
  • MEMIF_JOB_FAILED: The job has failed.
  • MEMIF_BLOCK_INCONSISTENT: The block may contain corrupted data.
  • MEMIF_BLOCK_INVALID: The block was invalidated; the operation cannot be executed.

Sequence diagram: Depending on the configuration, a driver error reaches the NvM via callback or by polling the job result. Sources: ErrorDescription p. 48, [SWS_Ea_00095], [SWS_Ea_00100], [SWS_Ea_00090], [SWS_Ea_00097]
