Role of ComM between users, bus state managers, and lifecycle

The Communication Manager (ComM) accepts the communication requests of its users and translates them into communication modes of the physical channels. Users can be runnables, SW-Cs, the BswM, or the DCM (SWS ComM p. 30). Downwards, ComM exclusively addresses the bus state managers. It requests modes with <BusSm>_RequestComMode() [SWS_ComM_00958] and queries them with <BusSm>_GetCurrentComMode() [SWS_ComM_00963]. The prefix (CanSM, LinSM, FrSM, EthSM) results from ComMBusType [SWS_ComM_00962]. ComM receives the reported bus mode via ComM_BusSM_ModeIndication and passes it on to the users via RTE and BswM [SWS_ComM_00675].

Other partners are:

  • Nm, via the ComM_Nm_* callbacks,
  • EcuM, which reports wake-ups,
  • NvM, for persistent data,
  • BswM, with BswM_ComM_CurrentPNCMode and BswM_ComM_InitiateReset [SWS_ComM_00829].

Context diagram: ComM mediates between users (RTE, DCM, BswM) on the one hand and Nm as well as the bus state managers on the other hand. NvM, Com, and SchM are service providers. Sources: SWS ComM (Abb.) p. 17, [SWS_ComM_00829], [SWS_ComM_00871].

Initialization: ComM_Init accepts the post-build structure ComM_ConfigType and sets up the internal state machines anew [SWS_ComM_00146] [SWS_ComM_00162]. In doing so, ComM reads the non-volatile parameters from NVRAM. If this fails, it uses the default values (SWS ComM p. 97).

Status and operation: ComM_GetStatus returns COMM_UNINIT or COMM_INIT [SWS_ComM_00242] [SWS_ComM_00668]. During operation, a dedicated ComM_MainFunction_<ComMChannel.ShortName> operates for each channel [SWS_ComM_00429].

Partitioning: Calls from foreign partitions must be enabled via a satellite [SWS_ComM_01019]. ComM invokes bus state manager APIs only in their partition [SWS_ComM_01020].

Deinitialization: ComM_DeInit [SWS_ComM_00147] only takes effect when all channels are in COMM_NO_COMMUNICATION. In doing so, ComM saves the NV parameters (SWS ComM p. 114).

Channel state machine: No, Silent, and Full Communication

ComM_ModeType defines four values [SWS_ComM_00672]:

  • COMM_NO_COMMUNICATION,
  • COMM_SILENT_COMMUNICATION,
  • COMM_FULL_COMMUNICATION,
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST, internal only.

Users may only request No and Full. Silent serves solely for synchronization with the NM (SWS ComM p. 30, [SWS_ComM_00110]). A dedicated state machine runs for each channel (SWS ComM p. 65). ComM_StateType encodes main and sub-states [SWS_ComM_00674].

Path to Full Communication:

  • A request without active limitation or active diagnostics leads to COMM_NO_COM_REQUEST_PENDING (SWS ComM p. 69).
  • Transitioning further to Full only occurs when ComM_CommunicationAllowed releases the channel [SWS_ComM_00871]. If the request ceases beforehand, the channel returns to the default state (SWS ComM p. 63).

Teardown according to variant of ComMNmVariant:

  • PASSIVE and SLAVE_PASSIVE unconditionally transition to COMM_FULL_COM_READY_SLEEP [SWS_ComM_00915].
  • SLAVE_ACTIVE transitions there as soon as no user request exists anymore [SWS_ComM_01017].
  • ComM_Nm_PrepareBusSleepMode leads to Silent upon FULL or PASSIVE [SWS_ComM_00826]. There, transmission is disabled, while reception remains active (SWS ComM p. 71).
  • Slave channels terminate communication via ComM_BusSM_BusSleepMode [SWS_ComM_01018] [SWS_ComM_91000].
  • LIGHT channels leave Full after expiration of ComMNmLightTimeout (SWS ComM p. 78).

State diagram: Main and sub-states of a ComM channel with the triggering events per NM variant. Sources: SWS ComM (Abb.) p. 46, SWS ComM (Abb.) p. 41, [SWS_ComM_00826], [SWS_ComM_00915], [SWS_ComM_01017], [SWS_ComM_01018].

Communication request by users and diagnostics

Users and assignment: A user is identified via ComM_UserHandleType. Valid values are 0..254; 255 represents COMM_NOT_USED_USER_ID [SWS_ComM_00670]. Users are statically assigned to channels [SWS_ComM_00995] or PNCs [SWS_ComM_00912]. A simultaneous assignment to a PNC and to its channel is not permitted [SWS_ComM_00996].

Ports to the RTE:

  • UR_{user_name} provides the interface ComM_UserRequest [SWS_ComM_01011] [SWS_ComM_01000].
  • UM_{user_name} provides the mode-switch interface ComM_CurrentMode [SWS_ComM_01010] [SWS_ComM_01001]. The mode group ComMMode starts in COMM_NO_COMMUNICATION [SWS_ComM_01012].

Collaboration diagram: The ports through which user SW-Cs, mode managers, and tools for PNC mapping interact with ComM. Sources: SWS ComM (Abb.) p. 81, [SWS_ComM_01006], [SWS_ComM_01007], [SWS_ComM_01008], [SWS_ComM_01009], [SWS_ComM_91107].

Requesting and releasing: A request is made either via ComM_RequestComMode [SWS_ComM_00110] or via ComM_DCM_ActiveDiagnostic [SWS_ComM_00873]. Diagnostics releases the channel again with ComM_DCM_InactiveDiagnostic [SWS_ComM_00874]. During active diagnostics, a limitation is temporarily inactive (SWS ComM p. 69).

Sequence diagram: Active start from No to Full Communication using the example of CAN, depending on the NM variant. Sources: SWS ComM p. 167, SWS ComM (Abb.) p. 107, SWS ComM p. 75.

Queries:

  • ComM_GetRequestedComMode returns the request of the user stored volatilely in ComM [SWS_ComM_00079] (SWS ComM p. 118).
  • ComM_GetCurrentComMode queries the bus state managers [SWS_ComM_00083].
  • ComM_GetMaxComMode takes active limitations into account [SWS_ComM_00085].
  • In the case of multiple channels per user, both functions each return the lowest mode (SWS ComM p. 119, SWS ComM p. 117).
  • Optionally, port CR_{channel_name} specifies the users that are currently keeping a channel in Full [SWS_ComM_00904] [SWS_ComM_00906] [SWS_ComM_01005].

Wake-up, network management, and orderly shutdown

Passive start: It begins with ComM_EcuM_WakeUpIndication [SWS_ComM_00275] or ComM_EcuM_PNCWakeUpIndication [SWS_ComM_91001]. In the event of a PNC wake-up, the scope depends on ComMSynchronousWakeUp:

  • With FALSE, only the referenced channels transition to COMM_NO_COM_REQUEST_PENDING [SWS_ComM_01014].
  • With TRUE, all channels transition [SWS_ComM_01015].

In the Network Requested state, ComM then requests Nm_PassiveStartup. For managed channels, this takes place on the managing channel [SWS_ComM_01016]. The same applies after ComM_Nm_RestartIndication [SWS_ComM_00792] (SWS ComM p. 75).

Sequence diagram: Reaction to a wake-up or an NM restart up to Full Communication. Sources: SWS ComM (Abb.) p. 104, [SWS_ComM_00383], [SWS_ComM_01016], [SWS_ComM_00915].

Shutdown: It begins when the last user releases Full or ComM_LimitChannelToNoComMode takes effect (SWS ComM p. 166). The sequence:

  1. In Ready Sleep, ComM invokes Nm_NetworkRelease for FULL (SWS ComM p. 78).
  2. The NM reports ComM_Nm_PrepareBusSleepMode [SWS_ComM_00391]; the channel transitions to Silent.
  3. The NM reports ComM_Nm_BusSleepMode [SWS_ComM_00392]; the channel transitions to No Communication.

Conversely, ComM_Nm_NetworkMode indicates entry into the Network Mode [SWS_ComM_00390].

Sequence diagram: Release or forced limitation via Ready Sleep and Silent up to bus sleep, optionally with ECU reset. Sources: SWS ComM (Abb.) p. 106, SWS CanNm p. 87, SWS CanSM p. 29, [SWS_ComM_00826], [SWS_ComM_00355].

Partial Network Clusters and dynamic PNC mapping (Draft)

Basic principle: PNCs wake logical ECU groups instead of entire buses (SWS ComM p. 31). A dedicated state machine exists for each PNC; PNC actions run before channel actions (SWS ComM p. 35). The modes are described in ComM_PncModeType [SWS_ComM_00673].

Assignment to channels:

  • PNCs are mapped to channels via ComMChannelPerPnc [SWS_ComM_00913].
  • The bit position of a PNC is calculated according to [SWS_ComM_00825].
  • For hosts with an Ethernet switch, a configuration restriction applies [SWS_ComM_CONSTR_00001].

R20-11 special feature: The status exchange still runs via Com signals (Com_SendSignal, EIRA/ERA callback ComM_COMCbk_<sn>) [SWS_ComM_00164] [SWS_ComM_00959] [SWS_ComM_00819]. Only R21-11 replaces it with dedicated APIs (SWS ComM p. 2).

State diagram: PNC state machine with local request, gateway ERA, and wake-up triggers. Sources: SWS ComM p. 37, SWS ComM p. 34, SWS ComM p. 43, [SWS_ComM_00964], [SWS_ComM_00165], [SWS_ComM_01053].

Dynamic PNC-to-channel mapping: The feature is new in R20-11 and marked as draft (SWS ComM p. 2).

  • Learning phase: ComM_PnLearningRequest starts it [SWS_ComM_91019] [SWS_ComM_01026]. Gateways forward learning requests [SWS_ComM_01028]. ComM_Nm_RepeatMessageLeftIndication terminates the phase [SWS_ComM_01029].
  • During the learning phase, ComM incorporates received ERA bits into the mapping [SWS_ComM_01031] and transmits its own membership [SWS_ComM_01032] [SWS_ComM_01033].
  • Management APIs: ComM_GetPncToChannelMapping, ComM_UpdatePncToChannelMapping, ComM_ResetPncToChannelMapping, and ComM_UpdatePncMembership [SWS_ComM_91013] [SWS_ComM_91015] [SWS_ComM_91017] [SWS_ComM_91021].

Communication restriction and persistent inhibition status

Inhibition status: It is a bit field [SWS_ComM_00669]:

  • Bit 0: Wake-up inhibition,
  • Bit 1: Limit to No Com.

ComMEcuGroupClassification acts as a mask defining which inhibitions may be executed at all. It is set via ComM_SetECUGroupClassification [SWS_ComM_00552] (SWS ComM p. 73). The status is stored non-volatilely and restored at startup (SWS ComM p. 84).

Controlling APIs:

  • ComM_LimitChannelToNoComMode [SWS_ComM_00163],
  • ComM_LimitECUToNoComMode [SWS_ComM_00124],
  • ComM_PreventWakeUp [SWS_ComM_00156],
  • ComM_GetInhibitionStatus for reading [SWS_ComM_00619].

Mode manager SW-Cs access these functions via the interfaces ComM_ChannelLimitation, ComM_ChannelWakeup, and ComM_ECUModeLimitation [SWS_ComM_00743] [SWS_ComM_00742] [SWS_ComM_00741] (SWS ComM (Abb.) p. 68).

Effect of the limitation:

  • An actively requested channel transitions to Ready Sleep despite existing user requests. A channel kept awake passively remains unaffected (SWS ComM p. 88).
  • Requests during limitation are discarded. After its cancellation, users must request anew (SWS ComM p. 91).
  • If ComMResetAfterForcingNoComm is set, ComM triggers an ECU reset via the BswM [SWS_ComM_00355].
  • An inhibit counter counts rejected Full requests. ComM_ReadInhibitCounter reads it, ComM_ResetInhibitCounter resets it [SWS_ComM_00224] [SWS_ComM_00108]. Both exist only with ComMModeLimitationEnabled and a configured NvM block (SWS ComM p. 130).

Activity diagram: Decision path when activating "Limit to No Com" up to the optional reset. Sources: SWS ComM p. 88, SWS ComM p. 84, [SWS_ComM_00163], [SWS_ComM_00110], [SWS_ComM_00355].

use

The synchronous interface ComM_RequestComMode ([SWS_ComM_00110]) serves users to request or release a communication mode. It expects the handle of the requesting user (User) as well as the desired mode (ComMode). Only COMM_FULL_COMMUNICATION and COMM_NO_COMMUNICATION are valid for user calls. The modes COMM_SILENT_COMMUNICATION (used internally for synchronization during shutdown) and COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST (channel-local wake-up request via lower layers with corresponding hardware support, e.g., OA-TC10 Ethernet) are internal modes and must not be requested by users.

Return Values and Error Handling

The function indicates the result of the call via its return value:

  • E_OK: The transition to the requested communication mode was successful.
  • E_NOT_OK: The mode transition failed.
  • COMM_E_MODE_LIMITATION: The mode cannot be granted due to active inhibition (mode inhibition). An existing request can also be released by this inhibition.

Concurrency and Limitations

The function is specified as reentrant ([SWS_ComM_00110]) and is provided via the header file ComM.h.

Interaction

The presence of user requests directly influences the behavior of the channel state machine: If the channel is in the sub-state COMM_FULL_COM_NETWORK_REQUESTED and the configuration parameter ComMNmVariant = SLAVE_ACTIVE is set, the state machine transitions to the sub-state COMM_FULL_COM_READY_SLEEP as soon as a user request for COMM_FULL_COMMUNICATION via ComM_RequestComMode is no longer active ([SWS_ComM_01017]).
