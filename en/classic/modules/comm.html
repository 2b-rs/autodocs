Translates communication requests from applications and diagnostics per channel into bus and partial network states.

The Communication Manager converts communication requests from SW-Cs, BswM, and DCM per channel into requests to the bus state managers and reports the actual mode back to the users ([SWS_ComM_00958]). For this purpose, it maintains a state machine with No, Silent, and Full Communication for each channel. Its transitions depend on user requests, wake-up notifications, the CommunicationAllowed release, and network management. Optionally, it manages partial networks, in R20-11 also with a dynamic PNC-to-channel mapping that is still treated as a draft. Key boundary condition: Users request only No or Full, and an active limitation rejects Full requests with COMM_E_MODE_LIMITATION ([SWS_ComM_00110]).

ComM bundles communication requests from SW-Cs, BswM, and DCM (SWS ComM p. 30). For each channel, it converts them into calls to <BusSm>_RequestComMode() ([SWS_ComM_00958]). It returns the actual bus mode to the users via RTE and BswM ([SWS_ComM_00675]). EcuM or BswM control via ComM_CommunicationAllowed whether communication is allowed at all ([SWS_ComM_00871]).

Context diagram: ComM between users, EcuM/BswM, DCM, Nm, and the bus state managers. Sources: SWS ComM p. 17, [SWS_ComM_00958]

Each channel has its own state machine with the modes No, Silent, and Full Communication and their sub-states ([SWS_ComM_00674]). Users may only request No and Full; Silent serves for NM synchronization (SWS ComM p. 30). The transitions depend on ComMNmVariant. For FULL or PASSIVE, Prepare-Bus-Sleep leads to Silent ([SWS_ComM_00826]). For SLAVE channels, the Bus-Sleep notification from the bus state manager terminates communication ([SWS_ComM_01018]).

State diagram: Life cycle of a channel from sleep state to full communication and back. Sources: SWS ComM p. 46, [SWS_ComM_00826]

An active start begins with ComM_RequestComMode ([SWS_ComM_00110]) or with active diagnostics. A passive start follows a wake-up notification from EcuM ([SWS_ComM_00275]). In this case, ComM requests Nm_PassiveStartup, for managed channels for the managing channel ([SWS_ComM_01016]).

Optionally, ComM manages partial networks (PNC) with one state machine each ([SWS_ComM_00673]). Fixed rules apply to the mapping of users to partial networks and channels ([SWS_ComM_00996]). The dynamic PNC-to-channel mapping is new in R20-11 and is still marked as DRAFT ([SWS_ComM_01026]).

A Mode Manager can limit channels to No Communication ([SWS_ComM_00163]). User requests for Full Communication then fail with COMM_E_MODE_LIMITATION ([SWS_ComM_00110]). Before ComM_Init, almost all functions return E_NOT_OK ([SWS_ComM_00612]).

Role: Mediator between Communication Users and Bus State Managers

ComM simplifies resource management for its users. These are runnables, SW-Cs, BswM, or DCM when it requires communication for diagnostics (SWS ComM p. 30). Users only notify their demand. ComM converts this per channel into calls to <BusSm>_RequestComMode() ([SWS_ComM_00958]). The prefix CanSM, LinSM, FrSM, or EthSM results from ComMBusType ([SWS_ComM_00962]).

In the opposite direction, the bus state manager reports the actual mode via ComM_BusSM_ModeIndication. ComM forwards it to the users via RTE and BswM ([SWS_ComM_00675]). Further inputs arrive from three sides:

  • EcuM or BswM allow communication using ComM_CommunicationAllowed ([SWS_ComM_00871]).
  • DCM reports active and terminated diagnostics ([SWS_ComM_00873], [SWS_ComM_00874]).
  • Nm reports its states ([SWS_ComM_00390], [SWS_ComM_00392]).

ComM reads and writes persistent data via NvM (SWS ComM p. 144).

Context diagram: ComM is located between users and bus state managers and is influenced by EcuM/BswM, DCM, and Nm. Sources: SWS ComM p. 17, [SWS_ComM_00958], [SWS_ComM_00675], [SWS_ComM_00871]

Communication Modes and Channel State Machine

ComM_ModeType knows four modes ([SWS_ComM_00672]):

  • COMM_NO_COMMUNICATION: neither sending nor receiving.
  • COMM_SILENT_COMMUNICATION: receiving only.
  • COMM_FULL_COMMUNICATION: sending and receiving.
  • COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST.

Users may only request No and Full. Silent serves solely for NM synchronization (SWS ComM p. 30). The Mode Declaration Group ComMMode starts in COMM_NO_COMMUNICATION ([SWS_ComM_01012]).

Each channel has its own, independent state machine (SWS ComM p. 65). Its states are provided by ComM_StateType ([SWS_ComM_00674]). Upon entering Full Communication, the channel transitions to COMM_FULL_COM_NETWORK_REQUESTED and activates sending and receiving via the bus state manager (SWS ComM p. 64).

The transitions depend on ComMNmVariant:

  • FULL or PASSIVE: ComM_Nm_PrepareBusSleepMode leads to Silent ([SWS_ComM_00826]).
  • PASSIVE or SLAVE_PASSIVE: The channel transitions directly to COMM_FULL_COM_READY_SLEEP ([SWS_ComM_00915]).
  • SLAVE_ACTIVE: It transitions there as soon as no user request exists anymore ([SWS_ComM_01017]).
  • SLAVE variants: ComM_BusSM_BusSleepMode terminates communication ([SWS_ComM_01018]).
  • LIGHT: Timer ComMNmLightTimeout determines the exit (SWS ComM p. 78).

State diagram: Life cycle of a channel with transitions that depend on the NM variant. Sources: SWS ComM p. 46, [SWS_ComM_00826], [SWS_ComM_00915], [SWS_ComM_01018]

From Communication Request to the Bus and Back to Sleep

An active start begins with ComM_RequestComMode ([SWS_ComM_00110]) or with ComM_DCM_ActiveDiagnostic. Without limitation, the channel changes immediately to COMM_NO_COM_REQUEST_PENDING (SWS ComM p. 69). There it waits until the CommunicationAllowed flag is TRUE (SWS ComM p. 63). Typically, a BswM rule sets this flag during startup (Mode-Management-Guide p. 25).

Sequence diagram: active start up to mode notification, using the example of CAN. Sources: SWS ComM p. 107, SWS ComM p. 75, [SWS_ComM_00675]

A passive start follows a wake-up notification. Triggers are ComM_EcuM_WakeUpIndication ([SWS_ComM_00275]), ComM_EcuM_PNCWakeUpIndication, or ComM_Nm_RestartIndication ([SWS_ComM_00792]). A PNC wake-up notification puts the channels referenced by the PNC into COMM_NO_COM_REQUEST_PENDING. For synchronous wake-up, this applies to all channels ([SWS_ComM_01014], [SWS_ComM_01015]). Subsequently, ComM requests Nm_PassiveStartup. For a managed channel, this is done for the managing channel ([SWS_ComM_01016]).

Sequence diagram: passive start after wake-up or restart notification. Sources: SWS ComM p. 104, [SWS_ComM_91001], [SWS_ComM_01016]

Shutdown begins when the last user releases its request or a limitation takes effect (SWS ComM p. 166). In COMM_FULL_COM_READY_SLEEP, ComM calls Nm_NetworkRelease() for the FULL variant (SWS ComM p. 78). The Prepare-Bus-Sleep and Bus-Sleep notifications then lead via Silent to No Communication ([SWS_ComM_00826], [SWS_ComM_00392]).

Sequence diagram: release or forcing up to No Communication, using the example of CAN. Sources: SWS ComM p. 106, [SWS_ComM_00355]

Three functions are available for queries. ComM_GetRequestedComMode returns the stored user request ([SWS_ComM_00079]). ComM_GetCurrentComMode queries the bus state manager ([SWS_ComM_00963]) and, in case of multiple channels, returns the lowest mode (SWS ComM p. 119). ComM_GetMaxComMode returns the highest permissible mode ([SWS_ComM_00085]).

Partial Networks (PNC) and User Mapping

A PNC is a logical group of ECUs that must be active simultaneously (SWS ComM p. 31). ComM maintains exactly one state machine per PNC and executes PNC actions prior to channel actions (SWS ComM p. 35). The modes are defined in ComM_PncModeType ([SWS_ComM_00673]).

The most important transitions:

  • A PNC wake-up notification leads from COMM_PNC_NO_COMMUNICATION to COMM_PNC_PREPARE_SLEEP ([SWS_ComM_00964]).
  • A user request or a set ERA bit at the gateway leads from COMM_PNC_READY_SLEEP to COMM_PNC_REQUESTED ([SWS_ComM_00165]).
  • Gateways set or clear the PNC bits of passive channels in the process ([SWS_ComM_00164], [SWS_ComM_00959]).

State diagram: PNC state machine. The return path to the idle state is an interpretation. Sources: SWS ComM p. 37, [SWS_ComM_01053], [SWS_ComM_00165]

Users can be assigned to PNCs ([SWS_ComM_00912]) or directly to channels ([SWS_ComM_00995]). Additional assignment to a channel that the PNC already references is impermissible ([SWS_ComM_00996]). A further restriction applies to ECUs with an Ethernet switch ([SWS_ComM_CONSTR_00001]). ComM_GetCurrentPNCComMode reports errors if no PNC or multiple PNCs are assigned to a user ([SWS_ComM_01022], [SWS_ComM_01023]).

Context diagram: permissible and impermissible mappings between users, PNCs, and channels. Sources: SWS ComM p. 59, [SWS_ComM_00913]

New in R20-11 is the optional dynamic PNC-to-channel mapping. Its requirements are still marked as DRAFT (SWS ComM p. 2). A learning phase begins with the learning bit ([SWS_ComM_01026]) and ends with ComM_Nm_RepeatMessageLeftIndication ([SWS_ComM_01029]). In the meantime, the management functions reject calls with COMM_E_LEARNING_ACTIVE ([SWS_ComM_01042]). Later releases change the signature of ComM_GetPncToChannelMapping. For R20-11, [SWS_ComM_91013] applies (SWS ComM p. 122).

Communication Restriction and Wake-up Inhibition

ComM offers three interventions:

  • ComM_LimitChannelToNoComMode limits a channel to No Communication ([SWS_ComM_00163]).
  • ComM_LimitECUToNoComMode limits all channels ([SWS_ComM_00124]).
  • ComM_PreventWakeUp switches wake-up inhibition ([SWS_ComM_00156]).

The status is held by the bit field ComM_InhibitionStatusType ([SWS_ComM_00669]). The ECU group classification acts on it as a mask and is stored non-volatilely (SWS ComM p. 84). A Mode Manager reaches these functions via the ports modeLimitation, CL_…, and CW_… ([SWS_ComM_01009], [SWS_ComM_01006], [SWS_ComM_01008]).

With active limitation, an actively requested channel transitions to COMM_FULL_COM_READY_SLEEP despite user requests. New requests are ignored. A channel that is kept awake only passively remains unaffected (SWS ComM p. 87). ComM_RequestComMode then returns COMM_E_MODE_LIMITATION ([SWS_ComM_00110]). Interpretation: Exactly these rejections are counted by ComM_ReadInhibitCounter ([SWS_ComM_00224]). Active diagnostics temporarily suspends limitation (SWS ComM p. 69). Optionally, ComM forces an ECU reset after forcing to No Communication ([SWS_ComM_00355]).

Activity diagram: Effect of mask, limitation, and diagnostics. The counter step is an interpretation. Sources: [SWS_ComM_00163], [SWS_ComM_00110], SWS ComM p. 87

Initialization, Integration, and Ports

ComM_Init restarts the state machines ([SWS_ComM_00146]). In doing so, ComM reads non-volatile parameters, which requires an initialized NvM (SWS ComM p. 97). ComM_DeInit ([SWS_ComM_00147]) only takes effect when all channels are in No Communication, and then saves to NVRAM (SWS ComM p. 114).

A dedicated Main Function exists for each channel ([SWS_ComM_00429]). Its order relative to Nm and the bus-specific NM modules must be considered during integration (Mode-Management-Guide p. 39). In case of multiple partitions, ComM must permit calls from other partitions ([SWS_ComM_01019]). It calls bus state managers only in their own partition ([SWS_ComM_01020]). SW-Cs use the ports UR_… and UM_… ([SWS_ComM_01011], [SWS_ComM_01010]).

Behavior in the event of an error

Prior to initialization, only ComM_Init, ComM_GetVersionInfo, and ComM_GetStatus operate normally. All other functions return E_NOT_OK ([SWS_ComM_00612]). Development errors such as COMM_E_UNINIT or COMM_E_WRONG_PARAMETERS are defined by [SWS_ComM_00234]. If reading from NvM fails, ComM uses default values (SWS ComM p. 97).

Upon bus-off, CanSM reports Silent Communication (Error Description p. 19). ComM forwards this notification to the users ([SWS_ComM_00675]). If Nm restarts during a coordinated shutdown, ComM_Nm_RestartIndication follows ([SWS_ComM_00792]).

Usage and Call Context

The synchronous and reentrant function ComM_RequestComMode ([SWS_ComM_00110]) serves to request a communication mode for a defined user (User). It is available via ComM.h. As input parameters for ComMode, exclusively the following values are permitted as user requests:

  • COMM_FULL_COMMUNICATION: Request for full communication capability ([SWS_ComM_00110]).
  • COMM_NO_COMMUNICATION: Release or termination of the communication request ([SWS_ComM_00110]).

The modes COMM_SILENT_COMMUNICATION (serves for shutdown synchronization) and COMM_FULL_COMMUNICATION_WITH_WAKEUP_REQUEST (internal wakeup trigger for underlying layers, e.g. for OA TC10-capable Ethernet hardware) are internal states and must not be requested by users ([SWS_ComM_00110]). Interpretation: Passing these internal modes is presumably acknowledged with E_NOT_OK.

Return Values and Error Handling

The function signals the result via defined return values ([SWS_ComM_00110]):

  • E_OK: The switch to the desired communication mode was successfully performed.
  • E_NOT_OK: The mode transition failed.
  • COMM_E_MODE_LIMITATION: The requested mode cannot be granted due to an active communication limitation (mode inhibition). Communication requests can also be released again by such limitations.

Interaction and State Machine

The presence or absence of active requests affects the channel state machine of the ComM. If the channel is in the sub-state COMM_FULL_COM_NETWORK_REQUESTED with configuration ComMNmVariant = SLAVE_ACTIVE and there is no active call to ComM_RequestComMode(<user>, COMM_FULL_COMMUNICATION), the ComM state machine transitions to the sub-state COMM_FULL_COM_READY_SLEEP ([SWS_ComM_01017]).
