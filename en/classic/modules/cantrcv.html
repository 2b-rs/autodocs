Role of the driver between CanIf and transceiver hardware

The CAN transceiver driver encapsulates the physical bus driver device of a CAN channel. It switches the operating modes of the device, detects wakeup events, and reads status and diagnostic data. Its generic state model is intended to cover as many available transceivers as possible and decouple ComM as well as EcuM from the concrete hardware (SWS CanTrcv p. 19). To this end, the hardware must provide an interface that can be mapped to this model [SWS_CanTrcv_00098]. In the block diagram of the CAN stack, the control path to the transceiver runs separately from the data path via CAN controller and CAN driver (SWS CanTrcv p. 9).

The upper partner is CanIf. CanIf_SetTrcvMode calls CanTrcv_SetOpMode (SWS CanIf p. 95), CanIf_GetTrcvMode calls CanTrcv_GetOpMode (SWS CanIf p. 97), and CanIf_SetTrcvWakeupMode calls CanTrcv_SetWakeupMode (SWS CanIf p. 92). Feedback is sent to CanIf via callbacks. For this purpose, CanTrcv mandatorily requires CanIf_TrcvModeIndication and Det_ReportRuntimeError [SWS_CanTrcv_00085]. Optional are, among others, CanIf_CheckTrcvWakeFlagIndication and CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00086]. Downwards, the driver controls the hardware via Dio and Spi (SWS CanTrcv p. 26). It imports types from DEM, Dio, EcuM, Icu, and Spi [SWS_CanTrcv_00084].

Context diagram: CanTrcv is accessed by CanIf, controls the hardware via Dio/Spi, and reports to CanIf, EcuM, DEM, and DET. Sources: [SWS_CanTrcv_00085], [SWS_CanTrcv_00084], SWS CanTrcv p. 52

Lifecycle: from NOT_ACTIVE via CanTrcv_Init to CanTrcv_DeInit

Before CanTrcv_Init [SWS_CanTrcv_00001] is called, the environment must have initialized all BSW drivers used by the driver [SWS_CanTrcv_00099]. The specification justifies this with timing requirements, such as reading out the hardware early after power-on (SWS CanTrcv p. 26). Init initializes all connected transceivers based on their initialization sequences and the configuration from ConfigPtr [SWS_CanTrcv_00180]. This configuration has the type CanTrcv_ConfigType [SWS_CanTrcv_00209]. Depending on the configuration, Init transitions each transceiver to CANTRCV_TRCVMODE_SLEEP or CANTRCV_TRCVMODE_STANDBY [SWS_CanTrcv_00148]. If Init detects a wakeup caused by transceiver activity, it reports it with the source from CanTrcvWakeupSourceRef to EcuM_SetWakeupEvent [SWS_CanTrcv_00167].

Difference between the sources: The configuration diagram for the container CanTrcvChannel also lists CANTRCV_OP_MODE_NORMAL for CanTrcvInitState, specifically as the default value (SWS CanTrcv p. 54). Authoritative for R20-11 remains [SWS_CanTrcv_00148], which specifies only SLEEP or STANDBY as the target state.

CanTrcv_DeInit [SWS_CanTrcv_91001] sets the hardware to the NOT_ACTIVE state [SWS_CanTrcv_91003]. In this state, it can be reconfigured with a new configuration sequence (SWS CanTrcv p. 49). If development error detection is active and the transceiver is not in CANTRCV_TRCVMODE_NORMAL, DeInit reports CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005]. DeInit is therefore expected from NORMAL.

State diagram: Init transitions from NOT_ACTIVE to SLEEP or STANDBY depending on the configuration. Lowering is stepwise (NORMAL → STANDBY → SLEEP), NORMAL can be reached from any mode, DeInit leads back to NOT_ACTIVE. Sources: [SWS_CanTrcv_00148], [SWS_CanTrcv_00103], [SWS_CanTrcv_00104], [SWS_CanTrcv_91003], SWS CanTrcv p. 19

Switching operating modes NORMAL, STANDBY, and SLEEP

CanTrcv_SetOpMode [SWS_CanTrcv_00002] operates asynchronously. E_OK only means that the request was accepted (SWS CanTrcv p. 33). The driver switches the internal state to NORMAL, STANDBY, or SLEEP [SWS_CanTrcv_00102]. Once the mode is reached, it calls CanIf_TrcvModeIndication with the abstract CanIf TransceiverId [SWS_CanTrcv_00158]. It implements the waiting times during state changes using Tm_BusyWait1us16bit [SWS_CanTrcv_00230].

The following rules apply to the order of modes:

  • From NORMAL, the user may only request STANDBY or NORMAL [SWS_CanTrcv_00103].
  • From STANDBY, the user may only request SLEEP or STANDBY [SWS_CanTrcv_00104].
  • According to the legend of the state diagram, NORMAL can be requested from all three modes (SWS CanTrcv p. 19).
  • A request for the current mode is permissible and not an error [SWS_CanTrcv_00161].
  • If the hardware does not support the requested mode, the call returns E_NOT_OK [SWS_CanTrcv_00105].

CanIf itself does not check this order (SWS CanIf p. 88). According to the CanSM specification, only the integration code requests SLEEP, not CanSM (SWS CanSM p. 94). The current state is returned synchronously by CanTrcv_GetOpMode [SWS_CanTrcv_00005] in OpMode [SWS_CanTrcv_00106], typed as CanTrcv_TrcvModeType [SWS_CanTrcv_00163].

Sequence diagram: The mode change is accepted synchronously and confirmed asynchronously via indication. Sources: [SWS_CanTrcv_00002], [SWS_CanTrcv_00158], [SWS_CanTrcv_00230], SWS CanTrcv p. 56

Detecting, buffering, and reporting wakeup events

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] controls whether wakeup events are forwarded. The parameter has the type CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164]:

  • CANTRCV_WUMODE_ENABLE reports a stored event as "present" [SWS_CanTrcv_00111].
  • CANTRCV_WUMODE_DISABLE disables reporting. The transceiver and driver continue to detect and store events internally [SWS_CanTrcv_00093].
  • CANTRCV_WUMODE_CLEAR clears stored events [SWS_CanTrcv_00094]. This mode is intended for the phase of disabled reporting [SWS_CanTrcv_00150].

During the disabling, no event may be lost [SWS_CanTrcv_00095].

Activity diagram: SetWakeupMode branches to ENABLE, DISABLE, and CLEAR after the parameters have been checked. Sources: [SWS_CanTrcv_00111], [SWS_CanTrcv_00093], [SWS_CanTrcv_00094], [SWS_CanTrcv_00117], SWS CanTrcv p. 37

Wakeups are detected in two ways:

  • CanTrcv_MainFunction [SWS_CanTrcv_00013] cyclically polls all buses in STANDBY and SLEEP and sets a wakeup event flag [SWS_CanTrcv_00112].
  • CanIf calls CanTrcv_CheckWakeup [SWS_CanTrcv_00143] upon a wakeup interrupt. As far as supported by the hardware, the function checks whether the transceiver was the cause, and reports this with CanTrcvWakeupSourceRef to EcuM_SetWakeupEvent [SWS_CanTrcv_00146].

The entry point to the second path is CanIf_CheckWakeup, which the integration code calls within the scope of EcuM_CheckWakeup (SWS CanIf p. 56, SWS EcuM p. 163). Interpretation: The cyclic polling is likely to complement the interrupt-driven path for cases where no wakeup interrupt is available.

If CanTrcvIcuChannelRef is configured, CanTrcv switches the wakeup notification via Icu_EnableNotification and Icu_DisableNotification [SWS_CanTrcv_00171]. Upon transition to STANDBY, it activates the ICU channels [SWS_CanTrcv_00172]. A later version additionally deactivates them upon transition to NORMAL (SWS CanTrcv p. 22).

The cause of a wakeup is returned by CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] [SWS_CanTrcv_00107], such as CANTRCV_WU_BY_BUS, CANTRCV_WU_INTERNALLY, CANTRCV_WU_RESET, or CANTRCV_WU_NOT_SUPPORTED [SWS_CanTrcv_00165]. Exactly how the reasons can be distinguished strongly depends on the hardware (SWS CanTrcv p. 35).

Sequence diagram: A hardware interrupt leads via EcuM, integration code, and CanIf to CanTrcv_CheckWakeup and, if applicable, to EcuM_SetWakeupEvent. Sources: [SWS_CanTrcv_00143], [SWS_CanTrcv_00146], SWS EcuM p. 176, SWS EcuM p. 163

Selective wakeup (Partial Networking) and transceiver flags

Transceivers with selective wakeup do not only wake up on the wake-up pattern, but additionally on wake-up frames, WUF for short (SWS CanTrcv p. 27). Whether the hardware is capable of this is indicated by CanTrcvHwPnSupport [SWS_CanTrcv_00174]. Only if this parameter is set do the container CanTrcvPartialNetwork and the flag and system data APIs exist [SWS_CanTrcv_00175]. Which wake-up frame is accepted is determined by CanTrcvPnFrameCanId, CanTrcvPnFrameCanIdMask, and CanTrcvPnFrameDataMask [SWS_CanTrcv_00177]. CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] enables or disables the PN function with PN_ENABLED or PN_DISABLED [SWS_CanTrcv_00210] [SWS_CanTrcv_00221] [SWS_CanTrcv_00222].

During shutdown, CanSM uses CanTrcv_ClearTrcvWufFlag [SWS_CanTrcv_00214] so that no frame wakeup is lost upon entering a low-power mode. Afterwards, the transceiver is supposed to change to STANDBY [SWS_CanTrcv_00194]. CanTrcv reports that the flag has been cleared via CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195]. The asynchronous CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223] confirms its check via CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224]. CanSM repeats the request to clear the WUF in the state S_PN_CLEAR_WUF (SWS CanSM p. 37).

Further functions are available for diagnostics and PN monitoring:

  • CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215], CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216], and CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217] use CanTrcv_TrcvFlagStateType [SWS_CanTrcv_00211].
  • CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] provides configuration and status raw as uint32 [SWS_CanTrcv_00189].

The flags POR and SYSERR are checked at two locations:

  • For PN-capable hardware, CanTrcv_SetOpMode checks both flags [SWS_CanTrcv_00186]. If POR is set, the configuration sequence is run through again [SWS_CanTrcv_00187].
  • During initialization, the selective wakeup function is reconfigured as soon as POR or SYSERR is set [SWS_CanTrcv_00182].

A set POR is also reported via EcuM_SetWakeupEvent with the source from CanTrcvPorWakeupSourceRef [SWS_CanTrcv_00183].

Sequence diagram: During PN shutdown, WUF clearing, STANDBY, and wake flag check follow one another, each with feedback via indication. Sources: [SWS_CanTrcv_00194], [SWS_CanTrcv_00195], [SWS_CanTrcv_00224], SWS CanTrcv p. 57, SWS CanTrcv p. 53

Configuration per transceiver channel and instantiation

For each transceiver hardware type, an ECU has one driver instance. This serves all devices of this type [SWS_CanTrcv_00016], addressed via the parameter uint8 Transceiver. Each channel is described in a container CanTrcvChannel (multiplicity 1..*). It contains, among others, CanTrcvChannelId, CanTrcvInitState, CanTrcvWakeupByBusUsed, CanTrcvHwPnSupport, CanTrcvIcuChannelRef as well as the references to the wakeup sources for wakeup, POR, and SYSERR (SWS CanTrcv p. 67). Hardware access is configured via references to Dio channels or Spi sequences (SWS CanTrcv p. 78).

Partition assignments that an implementation does not support must be rejected by the driver [SWS_CanTrcv_00231]. If the hardware can distinguish bus errors from other hardware errors, this is indicated with CanTrcvBusErrFlag [SWS_CanTrcv_00178]. Version information is provided by CanTrcv_GetVersionInfo [SWS_CanTrcv_00008].

Behavior in the event of an error

The errors are classified according to the general BSW scheme (SWS CanTrcv p. 23). Defined as development errors are, among others, CANTRCV_E_INVALID_TRANSCEIVER (1), CANTRCV_E_PARAM_POINTER (2), CANTRCV_E_UNINIT (11), CANTRCV_E_TRCV_NOT_STANDBY (21), CANTRCV_E_TRCV_NOT_NORMAL (22), and CANTRCV_E_PARAM_TRCV_WAKEUP_MODE (23) [SWS_CanTrcv_00050]. All checks follow the same pattern: If DET is active, the error is reported; if DET is deactivated, the function returns E_NOT_OK. Examples are [SWS_CanTrcv_00122], [SWS_CanTrcv_00123], and [SWS_CanTrcv_00132]. Specifically for CanTrcv_SetOpMode, the following apply:

  • An invalid OpMode results in CANTRCV_E_PARAM_TRCV_OPMODE [SWS_CanTrcv_00087].
  • Impermissible mode sequences lead to CANTRCV_E_TRCV_NOT_NORMAL or CANTRCV_E_TRCV_NOT_STANDBY, respectively [SWS_CanTrcv_00120] [SWS_CanTrcv_00121].

For CanTrcv_Init, an unsupported baud rate reports CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168].

Activity diagram: The diagram shows the check and error paths from CanTrcv_SetOpMode up to the acceptance of the request. The order of the checks is not specified in the sources and is arranged here only for clarity. Sources: [SWS_CanTrcv_00122], [SWS_CanTrcv_00123], [SWS_CanTrcv_00087], [SWS_CanTrcv_00120], [SWS_CanTrcv_00121], [SWS_CanTrcv_00105], [SWS_CanTrcv_00186], [SWS_CanTrcv_00114]

If communication to the transceiver is missing or faulty, the driver reports the runtime error CANTRCV_E_NO_TRCV_CONTROL (26) [SWS_CanTrcv_91006]. This applies to Init [SWS_CanTrcv_00113], SetOpMode [SWS_CanTrcv_00114], GetOpMode [SWS_CanTrcv_00115], SetWakeupMode [SWS_CanTrcv_00117], GetTrcvSystemData [SWS_CanTrcv_00190], and ClearTrcvWufFlag [SWS_CanTrcv_00196]. These functions then return E_NOT_OK. In this case, by contrast, CanTrcv_GetBusWuReason returns E_OK [SWS_CanTrcv_00116]. Interpretation: The return value here therefore presumably indicates no valid cause. For the error case, the type provides the value CANTRCV_WU_ERROR [SWS_CanTrcv_00165].

CANTRCV_E_BUS_ERROR is defined as an Extended Production Error [SWS_CanTrcv_00228]. It is detected if the BUSERR flag is set and the function is configured and supported by the hardware [SWS_CanTrcv_00229]. The cyclic function CanTrcv_MainFunctionDiagnostics [SWS_CanTrcv_00218] exists only for CanTrcvBusErrFlag = TRUE [SWS_CanTrcv_00205]. It reports FAILED [SWS_CanTrcv_00206] or PASSED [SWS_CanTrcv_00227] via Dem_SetEventStatus. The associated event is referenced via CanTrcvDemEventParameterRefs (SWS CanTrcv p. 78).

Activity diagram: Depending on the state of the BUSERR flag, the diagnostic function reports FAILED or PASSED to DEM. Sources: [SWS_CanTrcv_00205], [SWS_CanTrcv_00206], [SWS_CanTrcv_00227], SWS CanTrcv p. 48

use

The function CanTrcv_SetOpMode sets the internal state of the specified transceiver to the operating mode OpMode ([SWS_CanTrcv_00002], [SWS_CanTrcv_00102]). Possible target modes are CANTRCV_TRCVMODE_NORMAL, CANTRCV_TRCVMODE_STANDBY, and CANTRCV_TRCVMODE_SLEEP ([SWS_CanTrcv_00102]). The call behaves asynchronously ([SWS_CanTrcv_00002]). As return value, E_OK indicates that the request for mode change was accepted, while E_NOT_OK is returned if the request was rejected, a parameter is invalid, or the requested mode is not supported by hardware ([SWS_CanTrcv_00002], [SWS_CanTrcv_00105]).

State Transitions and Constraints

The following transition rules apply to switching between operating modes:

  • If the transceiver is in mode CANTRCV_TRCVMODE_NORMAL, the caller may only request CANTRCV_TRCVMODE_STANDBY or CANTRCV_TRCVMODE_NORMAL ([SWS_CanTrcv_00103]).
  • If the transceiver is in mode CANTRCV_TRCVMODE_STANDBY, the caller may only request CANTRCV_TRCVMODE_SLEEP or CANTRCV_TRCVMODE_STANDBY ([SWS_CanTrcv_00104]).

The function is reentrant for different transceivers ([SWS_CanTrcv_00002]). If selective wakeup is supported by hardware, CanTrcv_SetOpMode checks the flags POR and SYSERR of the transceiver status ([SWS_CanTrcv_00186]).

Error handling

If development error detection (DET) is active, CanTrcv_SetOpMode reports corresponding development errors (otherwise E_NOT_OK is returned):

  • CANTRCV_E_UNINIT: Call before initialization of the CanTrcv module ([SWS_CanTrcv_00122]).
  • CANTRCV_E_INVALID_TRANSCEIVER: Call with an invalid transceiver number ([SWS_CanTrcv_00123]).
  • CANTRCV_E_PARAM_TRCV_OPMODE: Invalid parameter value for OpMode ([SWS_CanTrcv_00087]).
  • CANTRCV_E_TRCV_NOT_NORMAL: Requesting STANDBY when the current mode is neither NORMAL nor STANDBY ([SWS_CanTrcv_00120]).
  • CANTRCV_E_TRCV_NOT_STANDBY: Requesting SLEEP when the current mode is neither STANDBY nor SLEEP ([SWS_CanTrcv_00121]).

If missing or faulty communication with the transceiver occurs, the function reports the runtime error CANTRCV_E_NO_TRCV_CONTROL to the DET and returns E_NOT_OK ([SWS_CanTrcv_00114]).

Interaction

After reaching the requested operating mode, the module calls the callback function CanIf_TrcvModeIndication with the abstract CanIf TransceiverId for each transition triggered by CanTrcv_SetOpMode ([SWS_CanTrcv_00158]).

Std_ReturnType CanTrcv_SetWakeupMode (uint8 Transceiver, CanTrcv_TrcvWakeupModeType Trcv WakeupMode);

En ables, disables or clears wake - up events of the Transceiver according to Trcv Wakeup Mode.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: e6669ec10c00 Provenance

use

The synchronous function CanTrcv_SetWakeupMode enables, disables, or clears wake-up events of the addressed CAN transceiver ([SWS_CanTrcv_00009]). The affected transceiver is selected via the parameter Transceiver, while TrcvWakeupMode passes the desired wake-up mode ([SWS_CanTrcv_00009]):

  • If CANTRCV_WUMODE_CLEAR is passed, a stored wake-up event on the addressed transceiver is cleared ([SWS_CanTrcv_00094]).
  • If CANTRCV_WUMODE_ENABLE is passed and a stored wake-up event for the bus exists, the CanTrcv module updates this event as present ("present") ([SWS_CanTrcv_00111]).

The function returns E_OK if the wake-up state was successfully changed to the requested mode. If the state change fails or a parameter is outside the valid range, the function returns E_NOT_OK and the previous state remains unchanged ([SWS_CanTrcv_00009]).

Error handling

If development error detection (DET) is active, CanTrcv_SetWakeupMode performs the following parameter and state checks:

  • If the call occurs prior to module initialization, development error CANTRCV_E_UNINIT is reported ([SWS_CanTrcv_00127]).
  • In case of an invalid transceiver number, CANTRCV_E_INVALID_TRANSCEIVER is reported ([SWS_CanTrcv_00131]).
  • If an invalid mode is passed for TrcvWakeupMode, CANTRCV_E_PARAM_TRCV_WAKEUP_MODE is triggered ([SWS_CanTrcv_00089]).

If DET is disabled, E_NOT_OK is returned in these cases ([SWS_CanTrcv_00089], [SWS_CanTrcv_00127], [SWS_CanTrcv_00131]). In case of missing or faulty communication with the transceiver, the function reports runtime error CANTRCV_E_NO_TRCV_CONTROL to the Default Error Tracer and returns E_NOT_OK ([SWS_CanTrcv_00117]).

Concurrency and Limitations

The function is reentrant for different transceivers ([SWS_CanTrcv_00009]).
