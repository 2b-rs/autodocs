Controls external CAN transceivers: operating modes, wake-up detection, and selective wake-up via wake-up frames.

CanTrcv controls external CAN transceivers and maps them to a generic mode model with NORMAL, STANDBY, and SLEEP. Mode changes are requested asynchronously by CanIf; the driver reports reached modes back via an indication [SWS_CanTrcv_00158]. In addition, it detects wake-ups, reports them to EcuM, and, with suitable hardware, supports selective wake-up via wake-up frames. Key constraint: SLEEP can only be reached from STANDBY [SWS_CanTrcv_00104], and no wake-ups must be lost while notifications are disabled.

The CAN Transceiver Driver (CanTrcv) encapsulates external CAN transceivers behind a generic mode model. ComM and EcuM thereby remain decoupled from the concrete hardware (SWS CanTrcv p. 19). There is a driver instance for each transceiver hardware type [SWS_CanTrcv_00016]. The driver is accessed via CanIf and controls the hardware via Dio and Spi, which must be initialized before CanTrcv_Init [SWS_CanTrcv_00099]. After init, each transceiver is in STANDBY or SLEEP, configured per channel [SWS_CanTrcv_00148]. CanTrcv_DeInit leads to NOT_ACTIVE [SWS_CanTrcv_91003].

CanTrcv_SetOpMode switches between NORMAL, STANDBY, and SLEEP [SWS_CanTrcv_00102]. SLEEP is only permissible from STANDBY [SWS_CanTrcv_00104]. A switch to the current mode is not an error [SWS_CanTrcv_00161]. The function operates asynchronously: As soon as the target mode is reached, CanTrcv reports this via CanIf_TrcvModeIndication [SWS_CanTrcv_00158].

State diagram: Init leads to STANDBY or SLEEP, SLEEP is only reachable via STANDBY, DeInit leads to NOT_ACTIVE. Sources: SWS CanTrcv p. 19, [SWS_CanTrcv_00148]

CanIf checks wake-ups via CanTrcv_CheckWakeup. This function reports detected wake-ups via EcuM_SetWakeupEvent [SWS_CanTrcv_00146]. CanTrcv_MainFunction scans the buses in STANDBY and SLEEP [SWS_CanTrcv_00112]. CanTrcv_SetWakeupMode can disable or enable notification, or clear stored wake-ups. In doing so, no wake-up must be lost [SWS_CanTrcv_00095].

PN-capable transceivers (CanTrcvHwPnSupport) additionally wake up via configured wake-up frames [SWS_CanTrcv_00175]. During shutdown, CanSM first clears the WUF flag and then switches to STANDBY [SWS_CanTrcv_00194]. Subsequently, CanSM has the wake flag checked asynchronously [SWS_CanTrcv_00224].

In case of an error, the following applies:

  • When DET is enabled, development errors are reported; when DET is disabled, the APIs return E_NOT_OK [SWS_CanTrcv_00050].
  • The driver reports faulty hardware communication as runtime error CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006].
  • Bus errors are reported by CanTrcv_MainFunctionDiagnostics as CANTRCV_E_BUS_ERROR to DEM [SWS_CanTrcv_00206].

Role: Driver for external CAN transceivers below CanIf

The CAN Transceiver Driver (CanTrcv) controls external CAN transceiver devices. It maps their hardware states to a generic operating mode model. This model is intended to uniformly cover many available transceivers. According to the specification, it accepts having one or two states too many for a specific device, but thereby decouples ComM and EcuM from the hardware (SWS CanTrcv p. 19). To this end, the transceiver hardware must provide an interface that can be mapped to this model [SWS_CanTrcv_00098].

Upwards, CanIf is the immediate partner:

  • CanIf_SetTrcvMode calls CanTrcv_SetOpMode (SWS CanIf p. 95).
  • CanIf_GetTrcvMode calls CanTrcv_GetOpMode (SWS CanIf p. 97).
  • CanIf_GetTrcvWakeupReason calls CanTrcv_GetBusWuReason (SWS CanIf p. 98).

Feedbacks run via CanIf_TrcvModeIndication, which belongs to the mandatory interfaces [SWS_CanTrcv_00085]. For PN indications, further CanIf callbacks are listed [SWS_CanTrcv_00086]. Downwards, CanTrcv uses Dio and Spi for hardware control as well as Icu, DEM, and EcuM types, as shown in the import list [SWS_CanTrcv_00084]. Wait times during state transitions are implemented by the driver with Tm_BusyWait1us16bit [SWS_CanTrcv_00230]. CanTrcv_MainFunction and CanTrcv_MainFunctionDiagnostics are called by the BSW Scheduler (SWS CanTrcv p. 47).

Context diagram: CanTrcv is serviced by CanIf, EcuM, and the scheduler and accesses the hardware via Dio, Spi, and Icu. It reports errors to DET and DEM. Sources: [SWS_CanTrcv_00084], [SWS_CanTrcv_00085], [SWS_CanTrcv_00146], SWS EcuM p. 35

Initialization, Lifecycle, and Deinitialization

Before calling CanTrcv_Init [SWS_CanTrcv_00001], the environment must have initialized all used drivers, in particular Spi and Dio [SWS_CanTrcv_00099]. The document passage adds two timing requirements: Initialization should occur early after power-up, and the lower-layer services should be short and synchronous (SWS CanTrcv p. 26).

CanTrcv_Init initializes all connected transceivers according to their initialization sequences and the configuration from ConfigPtr [SWS_CanTrcv_00180]. The content of CanTrcv_ConfigType is hardware-specific [SWS_CanTrcv_00209]. Afterward, each transceiver is in CANTRCV_TRCVMODE_SLEEP or CANTRCV_TRCVMODE_STANDBY; this is configurable per transceiver [SWS_CanTrcv_00148].

Initialization simultaneously checks for wake-ups:

  • If supported by the hardware, CanTrcv_Init checks whether transceiver activity triggered the wake-up. It reports the result via EcuM_SetWakeupEvent with the source from CanTrcvWakeupSourceRef [SWS_CanTrcv_00167].
  • For PN-capable transceivers, the configuration sequence is additionally executed again if the POR or SYSERR flag is set. Otherwise, the configuration stored in the transceiver remains valid [SWS_CanTrcv_00182].
  • A set POR flag is also reported as a wake-up via CanTrcvPorWakeupSourceRef [SWS_CanTrcv_00183].

The POR report fits transceivers with integrated power supply. For them, passive wake-up looks like a power-on reset to the ECU (SWS EcuM p. 70).

Activity diagram: Initialization checks hardware reachability, handles POR/SYSERR, reports wake-ups to EcuM, and ends per channel in STANDBY or SLEEP. The sequence of checks is an interpretation. Sources: [SWS_CanTrcv_00180], [SWS_CanTrcv_00182], [SWS_CanTrcv_00183], [SWS_CanTrcv_00167], [SWS_CanTrcv_00148]

CanTrcv_DeInit [SWS_CanTrcv_91001] sets the transceiver hardware to the NOT_ACTIVE state [SWS_CanTrcv_91003]. In this state, it can be set up with a new configuration sequence (SWS CanTrcv p. 49). The expected initial state is CANTRCV_TRCVMODE_NORMAL; otherwise, development error detection reports CANTRCV_E_TRCV_NOT_NORMAL [SWS_CanTrcv_91005].

Operating Modes NORMAL, STANDBY, and SLEEP

CanTrcv_TrcvModeType defines the three modes [SWS_CanTrcv_00163]. CanTrcv_SetOpMode [SWS_CanTrcv_00002] switches the internal state of the addressed transceiver to one of these modes [SWS_CanTrcv_00102]. For the transitions, the following applies:

  • From NORMAL, the user requests only STANDBY or NORMAL [SWS_CanTrcv_00103].
  • From STANDBY, the user requests only SLEEP or STANDBY [SWS_CanTrcv_00104].
  • According to the diagram, NORMAL is reachable from all three modes (SWS CanTrcv p. 19).
  • A transition to the current mode is permitted and not an error [SWS_CanTrcv_00161].
  • If the hardware does not support the requested mode, the function returns E_NOT_OK [SWS_CanTrcv_00105].

State diagram: After init, the transceiver is in STANDBY or SLEEP. SLEEP is only reachable via STANDBY, NORMAL from all modes. DeInit leads to NOT_ACTIVE. Sources: SWS CanTrcv p. 19, [SWS_CanTrcv_00148], [SWS_CanTrcv_00103], [SWS_CanTrcv_00104], [SWS_CanTrcv_91003]

CanTrcv_SetOpMode operates asynchronously: E_OK only means that the request was accepted (SWS CanTrcv p. 33). Only when the target mode has been reached does CanTrcv call CanIf_TrcvModeIndication with the abstract CanIf TransceiverId [SWS_CanTrcv_00158]. CanSM ignores such a report for SLEEP because SLEEP is only requested by the integration code (SWS CanSM p. 94).

For PN-capable hardware, CanTrcv_SetOpMode additionally checks the POR and SYSERR flags [SWS_CanTrcv_00186]. After a POR, it re-initializes the transceiver [SWS_CanTrcv_00187]. CanTrcv_GetOpMode [SWS_CanTrcv_00005] synchronously returns the current state [SWS_CanTrcv_00106].

Sequence diagram: A mode change is accepted synchronously and later confirmed via CanIf to CanSM by indication. Sources: SWS CanTrcv p. 52, [SWS_CanTrcv_00158], [SWS_CanTrcv_00186]

Wake-up: Detection, Cause, and Notification Control

A wake-up is detected via interrupt or via polling (SWS EcuM p. 179). CanIf queries the function CanTrcv_CheckWakeup [SWS_CanTrcv_00143] via CanIf_CheckWakeup (SWS CanIf p. 56). If the hardware supports it, this function validates a wake-up caused by transceiver activity and reports it via EcuM_SetWakeupEvent [SWS_CanTrcv_00146].

CanTrcv_MainFunction [SWS_CanTrcv_00013] scans all buses in STANDBY and SLEEP for wake-ups and sets a wake-up flag [SWS_CanTrcv_00112]. Presumably, it is relevant primarily in polling configurations; the configuration diagram provides the value CanTrcvWakeUpByPolling for this (ECUC-Parameter p. 185).

CanTrcv_GetBusWuReason [SWS_CanTrcv_00007] returns the wake-up cause detected by the transceiver [SWS_CanTrcv_00107]. Possible values are, for instance, CANTRCV_WU_BY_BUS, CANTRCV_WU_INTERNALLY, or CANTRCV_WU_RESET [SWS_CanTrcv_00165]. How finely the causes can be distinguished depends heavily on the hardware (SWS CanTrcv p. 35).

For wake-up interrupts, the driver uses ICU channels. It calls Icu_EnableNotification and Icu_DisableNotification only if CanTrcvIcuChannelRef is configured [SWS_CanTrcv_00171]. When switching to STANDBY, it enables the channels [SWS_CanTrcv_00172]. The document passage from R24-11 additionally mentions disabling when switching to NORMAL (SWS CanTrcv p. 23).

Sequence diagram: A wake-up is checked at the transceiver via CanIf using interrupt or polling, reported to EcuM, and later queried for its cause. Sources: SWS EcuM p. 179, SWS EcuM p. 138, SWS EcuM p. 140, [SWS_CanTrcv_00146], [SWS_CanTrcv_00112]

CanTrcv_SetWakeupMode [SWS_CanTrcv_00009] controls wake-up notification via CanTrcv_TrcvWakeupModeType [SWS_CanTrcv_00164]:

  • CANTRCV_WUMODE_DISABLE: Wake-ups are not reported, but stored internally [SWS_CanTrcv_00093].
  • CANTRCV_WUMODE_ENABLE: A stored wake-up is reported as "present" [SWS_CanTrcv_00111].
  • CANTRCV_WUMODE_CLEAR: A stored wake-up is cleared [SWS_CanTrcv_00094].

In the disabled phase, no wake-ups must be lost [SWS_CanTrcv_00095]. Clearing serves to discard stored wake-ups under control of the higher layer while notifications are disabled [SWS_CanTrcv_00150]. CanIf passes the request on to CanTrcv via CanIf_SetTrcvWakeupMode (SWS CanIf p. 100).

Selective wake-up (partial networking)

With partial networking, nodes remain in low-power mode until predefined wake-up frames (WUF) wake them up. PN-capable transceivers therefore react not only to the wake-up pattern (WUP), but also to these frames (SWS CanTrcv p. 27). Whether the hardware supports this is indicated by CanTrcvHwPnSupport [SWS_CanTrcv_00174]. Only if this parameter is TRUE do the container CanTrcvPartialNetwork and five APIs exist: CanTrcv_GetTrcvSystemData, CanTrcv_ClearTrcvWufFlag, CanTrcv_ReadTrcvTimeoutFlag, CanTrcv_ClearTrcvTimeoutFlag, and CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00175].

Which frames the transceiver responds to is specified by CanTrcvPnFrameCanId, CanTrcvPnFrameCanIdMask, and CanTrcvPnFrameDataMask [SWS_CanTrcv_00177]. CanTrcv_SetPNActivationState [SWS_CanTrcv_00219] enables the PN wake-up function with PN_ENABLED [SWS_CanTrcv_00221] and disables it with PN_DISABLED [SWS_CanTrcv_00222].

Central is the shutdown sequence:

  1. CanSM clears the WUF flag via CanTrcv_ClearTrcvWufFlag so that no frame wake-up is lost upon entering low-power mode. Subsequently, the transceiver transitions to STANDBY [SWS_CanTrcv_00194].
  2. CanTrcv confirms the clearing with CanIf_ClearTrcvWufFlagIndication [SWS_CanTrcv_00195].
  3. Finally, CanSM requests the asynchronous check CanTrcv_CheckWakeFlag [SWS_CanTrcv_00223]. CanTrcv reports the result via CanIf_CheckTrcvWakeFlagIndication [SWS_CanTrcv_00224].

For SPI connection, the specification describes an asynchronous (SWS CanTrcv p. 55) and a synchronous variant (SWS CanTrcv p. 57).

Sequence diagram: During PN shutdown, the WUF flag is cleared, the transceiver is switched to STANDBY, and the wake flag is checked asynchronously after controller sleep. Sources: SWS CanTrcv p. 55, SWS CanTrcv p. 56, SWS CanSM p. 36, [SWS_CanTrcv_00194], [SWS_CanTrcv_00224]

For diagnostics, CanTrcv_GetTrcvSystemData [SWS_CanTrcv_00213] reads out the configuration and status of the transceiver as uint32 [SWS_CanTrcv_00189]. The timeout and silence flags are read and cleared via CanTrcv_ReadTrcvTimeoutFlag [SWS_CanTrcv_00215], CanTrcv_ClearTrcvTimeoutFlag [SWS_CanTrcv_00216], and CanTrcv_ReadTrcvSilenceFlag [SWS_CanTrcv_00217]. Their state is indicated by CanTrcv_TrcvFlagStateType [SWS_CanTrcv_00211].

Configuration and instance reference

For each transceiver hardware type, there is a driver instance that serves all devices of this type [SWS_CanTrcv_00016]. The CanIf diagram shows the case of identical controllers with different transceiver types, which then requires two transceiver drivers (SWS CanIf p. 34). Each channel is described by a container CanTrcvChannel (multiplicity 1..*). Among other things, it contains CanTrcvHwPnSupport, CanTrcvInitState, CanTrcvWakeupByBusUsed, and the wake-up source references (SWS CanTrcv p. 70).

One difference between the sources concerns the state after init. The configuration diagram lists CanTrcvOpModeNormal as the default for CanTrcvInitState (ECUC-Parameter p. 187). However, normative for R20-11 is [SWS_CanTrcv_00148], which provides only SLEEP or STANDBY after init. The driver must reject configurations with unsupported partition assignments [SWS_CanTrcv_00231].

Behavior in the event of an error

The development errors from [SWS_CanTrcv_00050] follow a uniform pattern. With DET enabled, the APIs report:

  • CANTRCV_E_UNINIT when called prior to init, such as [SWS_CanTrcv_00122] and [SWS_CanTrcv_00124];
  • CANTRCV_E_INVALID_TRANSCEIVER for an invalid ID, such as [SWS_CanTrcv_00123] and [SWS_CanTrcv_00129];
  • CANTRCV_E_PARAM_POINTER for NULL pointers, such as [SWS_CanTrcv_00132] and [SWS_CanTrcv_00133];
  • CANTRCV_E_TRCV_NOT_NORMAL or CANTRCV_E_TRCV_NOT_STANDBY for impermissible transitions [SWS_CanTrcv_00120] [SWS_CanTrcv_00121];
  • Parameter errors for an invalid mode [SWS_CanTrcv_00087] or an invalid wake-up mode [SWS_CanTrcv_00089].

If DET is disabled, the APIs return E_NOT_OK in these cases.

If communication with the transceiver is disrupted, the driver reports the runtime error CANTRCV_E_NO_TRCV_CONTROL [SWS_CanTrcv_91006] via Det_ReportRuntimeError [SWS_CanTrcv_00085]. This applies, for example, in Init [SWS_CanTrcv_00113], SetOpMode [SWS_CanTrcv_00114], GetOpMode [SWS_CanTrcv_00115], SetWakeupMode [SWS_CanTrcv_00117], GetTrcvSystemData [SWS_CanTrcv_00190], and ClearTrcvWufFlag [SWS_CanTrcv_00196]. An exception is CanTrcv_GetBusWuReason: in this case, according to [SWS_CanTrcv_00116], it returns E_OK. Init reports an unsupported baud rate as CANTRCV_E_BAUDRATE_NOT_SUPPORTED [SWS_CanTrcv_00168].

Usage and Semantics

The function CanTrcv_Init serves for the basic initialization of the CanTrcv module as well as all connected CAN transceivers [SWS_CanTrcv_00001] [SWS_CanTrcv_00180]. Execution is synchronous and specified as non-reentrant [SWS_CanTrcv_00001]. As a parameter, it expects a pointer to the driver configuration via ConfigPtr and has no return value [SWS_CanTrcv_00001].

Interaction and Hardware Check

During execution, the function performs the hardware-related initialization sequences of all connected transceivers according to the configuration, thereby supporting the initialization sequence of the AUTOSAR stack [SWS_CanTrcv_00180]. Upon the call, each transceiver transitions separately into either mode CANTRCV_TRCVMODE_SLEEP or CANTRCV_TRCVMODE_STANDBY, depending on its respective configuration [SWS_CanTrcv_00148]. If supported by the hardware, CanTrcv_Init also checks whether a wake-up event due to transceiver activity was previously present and reports this via EcuM_SetWakeupEvent with the source defined via CanTrcvWakeupSourceRef to the EcuM [SWS_CanTrcv_00167].

Error handling

In the event of faulty or missing communication with the hardware (for example via port pins or SPI), the function reports the runtime error CANTRCV_E_NO_TRCV_CONTROL to the Default Error Tracer [SWS_CanTrcv_00113]. If development error detection is active, CANTRCV_E_BAUDRATE_NOT_SUPPORTED is furthermore reported if a configured baud rate is not supported by the respective transceiver [SWS_CanTrcv_00168].

The function CanTrcv_SetOpMode is used to asynchronously switch the operating mode of a CAN transceiver [SWS_CanTrcv_00002]. It takes the device number of the transceiver (Transceiver) as well as the desired target mode (OpMode), which can assume the values CANTRCV_TRCVMODE_NORMAL, CANTRCV_TRCVMODE_STANDBY, or CANTRCV_TRCVMODE_SLEEP [SWS_CanTrcv_00102]. The function is reentrant for different transceivers [SWS_CanTrcv_00002]. The return value E_OK confirms acceptance of the mode switch request; E_NOT_OK signals rejection of the request, parameter errors, or lack of support for the mode by the hardware [SWS_CanTrcv_00002], [SWS_CanTrcv_00105].

When calling, specified state transitions must be observed:

  • If the transceiver is in mode CANTRCV_TRCVMODE_NORMAL, only CANTRCV_TRCVMODE_STANDBY or CANTRCV_TRCVMODE_NORMAL may be passed as the target mode [SWS_CanTrcv_00103].
  • If the transceiver is in CANTRCV_TRCVMODE_STANDBY, the function may only be called with CANTRCV_TRCVMODE_SLEEP or CANTRCV_TRCVMODE_STANDBY [SWS_CanTrcv_00104].

With Development Error Detection (DET) enabled, the function reports calls prior to initialization as CANTRCV_E_UNINIT [SWS_CanTrcv_00122], invalid transceiver numbers as CANTRCV_E_INVALID_TRANSCEIVER [SWS_CanTrcv_00123], and impermissible operating modes as CANTRCV_E_PARAM_TRCV_OPMODE [SWS_CanTrcv_00087]. If Standby is requested without the transceiver being in Normal or Standby, CANTRCV_E_TRCV_NOT_NORMAL is triggered [SWS_CanTrcv_00120]; upon requesting Sleep outside of Standby or Sleep, the notification CANTRCV_E_TRCV_NOT_STANDBY occurs [SWS_CanTrcv_00121]. If the DET is disabled, E_NOT_OK is returned in these cases.
