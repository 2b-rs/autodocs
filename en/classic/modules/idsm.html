Collects security events from sensors, filters them, and forwards qualified events to sinks.

IdsM collects security events reported by BSW modules, CDDs, and SW-Cs, buffers them, and processes them asynchronously in IdsM_MainFunction [SWS_IdsM_00702]. Reporting mode and a filter chain of block state, sampling, aggregation, and threshold filters turn them into qualified events [SWS_IdsM_01004]. These are sent via PduR to an IdsR or stored in DEM/Sem. Timestamps, signature, and diagnostic access are optional. IdsM does not evaluate the meaning of context data; the response to attacks is outside the module.

IdsM receives Security Events (SEv) from security sensors, that is, from BSW modules, CDDs, and SW-Cs. Via a filter chain, it turns them into Qualified Security Events (QSEv) [SWS_IdsM_00902]. It sends QSEvs via PduR to an IdsR, stores them in DEM/Sem, or both [SWS_IdsM_01202] [SWS_IdsM_01600]. It does not evaluate the meaning of context data. The response to attacks is outside the module, for example in an SOC [SWS_IdsM_CONSTR_00001].

Context diagram: IdsM connects the reporting sensors with the sinks PduR/IdsR and DEM/Sem. BswM, StbM, CSM, DCM, and NvM are optionally connected. Sources: SWS IdsM p. 20, [SWS_IdsM_91023]

Sensors report via IdsM_SetSecurityEvent or one of five variants with context data (up to 1500 bytes), counter, and timestamp [SWS_IdsM_00300] [SWS_IdsM_00404] [SWS_IdsM_00501]. In doing so, they always use the symbolic name of the IdsMEvent [SWS_IdsM_00607]. The reporting service only buffers the SEv. The actual processing runs asynchronously in IdsM_MainFunction [SWS_IdsM_00702]. If a free event buffer is missing, IdsM triggers an internal SEv provided this is configured [SWS_IdsM_00703].

Qualification begins with the reporting mode. Possible values are OFF, BRIEF, DETAILED, and the variants that bypass the filters [SWS_IdsM_01002] [SWS_IdsM_91013]. Thereafter, the active filters run in a fixed order: Block State, Forward Every n-th, Aggregation, Threshold [SWS_IdsM_01004]. If a filter discards the SEv, evaluation ends [SWS_IdsM_01005]. Prior to transmission to the IdsR, rate and traffic limitation additionally take effect [SWS_IdsM_01070]. These are likely to apply to the bypass modes as well (interpretation).

Activity diagram: First reporting mode, then the filter chain, finally the instance limits before the IdsR. Sources: SWS IdsM p. 35, [SWS_IdsM_01004], [SWS_IdsM_01070]

Optionally, further functions can be enabled [SWS_IdsM_01100] [SWS_IdsM_01204] [SWS_IdsM_01901] [SWS_IdsM_01702]:

  • Timestamp from StbM or from the application
  • Signature via the CSM
  • Reading and changing the reporting mode via the DCM, with NvM persistence and rollback in case of errors

The IdsM reports development errors to the DET only when IdsMDevErrorDetect is active [SWS_IdsM_02003]. The DEM/Sem sink has the status DRAFT in R20-11 [SWS_IdsM_01601].

Role: from reported security event to qualified event

The Intrusion Detection System Manager (IdsM) collects security events (SEvs). These are detected and reported by security sensors, i.e., BSW modules, complex device drivers, or SW-Cs SWS IdsM p. 10. The IdsM checks each SEv against a configurable sequence of filters, the filter chain. If the SEv passes this check, it becomes a qualified security event (QSEv) [SWS_IdsM_00902]. Only QSEvs are processed further. They are passed via the PduR to an IdsR on another ECU, stored in DEM/Sem, or both [SWS_IdsM_01202] [SWS_IdsM_01600] SWS IdsM p. 35.

The system boundary is drawn narrowly. The IdsM does not know the meaning of the context data and therefore does not decide itself whether a system is compromised. Detection and response lie outside the module, for example in an SOC [SWS_IdsM_CONSTR_00001]. There are no mandatory interfaces to other modules [SWS_IdsM_91023]. Each coupling is enabled via the configuration. This is shown by the conditional header inclusions:

  • Det.h in case of IdsMDevErrorDetect
  • Dem.h in case of IdsMSinkDem
  • Dcm.h in case of IdsMDiagnosticSupport
  • NvM.h in case of IdsMNvmBlockDescriptor
  • PduR.h in case of IdsMSinkIdsR

Evidence for these inclusions: [SWS_IdsM_00101] to [SWS_IdsM_00105].

Context diagram: The IdsM is positioned between the reporting sensors and the sinks PduR/IdsR as well as DEM/Sem. BswM, StbM, CSM, DCM, and NvM provide operating state, time, signature, and diagnostic access. Sources: SWS IdsM p. 20, SWS IdsM p. 14, [SWS_IdsM_01022], [SWS_IdsM_01104], [SWS_IdsM_01206], [SWS_IdsM_01701]

Start, event identity, and reporting interfaces

IdsM_Init initializes all internal variables and sets the module to the state \"initialized\" [SWS_IdsM_00202] [SWS_IdsM_91001]. Only IdsM_Init and IdsM_GetVersionInfo may be called before this point in time SWS IdsM p. 21. Calling IdsM_Init again does not initialize the module a second time [SWS_IdsM_00204].

State diagram: The module has two states. Erroneous calls in both states report an error to the DET only when development error detection is active. Sources: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], SWS IdsM p. 21

Each SEv is identified by three identifiers and the event name [SWS_IdsM_00600]:

  • IdsMExternalEventId is globally unique and originates from the Security Extract. The value 0xFFFF is invalid [SWS_IdsM_00603] [SWS_IdsM_00604].
  • IdsMSensorInstanceId is 0 by default if there is only one module instance [SWS_IdsM_00608].
  • IdsMInternalEventId is calculated internally by the IdsM [SWS_IdsM_00601].

Sensors report exclusively via the symbolic name of the IdsMEvent container. They must not rely on the internal value [SWS_IdsM_00602] [SWS_IdsM_00607]. Six services are available for reporting:

The sensor passes context data as a pointer to a byte array. Up to 1500 bytes are supported [SWS_IdsM_00501] [SWS_IdsM_00502]. Those having a timestamp but no own counter report with count = 1 [SWS_IdsM_00405].

Buffering and asynchronous processing in IdsM_MainFunction

The reporting services do not process an SEv immediately. The IdsM initially stores it in an event buffer. Filtering and forwarding take place later and asynchronously in the cyclically called IdsM_MainFunction [SWS_IdsM_00702] [SWS_IdsM_00901] [SWS_IdsM_91000]. The number of event buffers (IdsMNumberOfEventBuffers) is configurable [SWS_IdsM_00701]. As a guideline, the specification recommends the number of aggregation filter instances plus the upper limit of concurrently processed events SWS IdsM p. 24.

Sequence diagram: The notification returns immediately after buffering. Timestamping, filtering, and forwarding only follow in IdsM_MainFunction. Sources: SWS IdsM p. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01107]

Context data resides in dedicated context data buffers with a configurable size of up to 1500 bytes [SWS_IdsM_00704] SWS IdsM p. 122. The IdsM selects a buffer of equal or next larger size and links it to the event buffer [SWS_IdsM_00705] [SWS_IdsM_00706]. An SEv without context data does not occupy such a buffer [SWS_IdsM_00709]. Dedicated, separate buffers exist for the internal SEvs of the IdsM itself [SWS_IdsM_00802].

Activity diagram: How buffers are allocated upon receipt of an SEv. If a context buffer is missing, the SEv is processed without context data. If an event buffer is missing, the SEv cannot be handled. Sources: [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708], [SWS_IdsM_91015], SWS IdsM p. 27

Qualification: reporting mode, filter chain, and instance limits

First, the IdsM evaluates the reporting mode. Each SEv has exactly one reporting mode filter. This filter is mandatory, is attached directly to the SEv, and does not belong to the filter chain [SWS_IdsM_01010] [SWS_IdsM_01011]. The initial value originates from IdsMReportingModeFilter [SWS_IdsM_01012]. The filter chain follows only afterwards [SWS_IdsM_01002]. IdsM_Filters_ReportingModeType supports these modes [SWS_IdsM_91013]:

  • IDSM_REPORTING_MODE_OFF: The event is not reported.
  • IDSM_REPORTING_MODE_BRIEF: Reporting without context data.
  • IDSM_REPORTING_MODE_DETAILED: Reporting with context data.
  • The two variants …_BYPASSING_FILTERS: Reporting as in BRIEF or DETAILED, but unfiltered.

The filter chain is assigned to the SEv [SWS_IdsM_01001] [SWS_IdsM_00903]. Each IdsMFilterChain requires at least one filter [SWS_IdsM_CONSTR_00002]. The active filters execute in a fixed order [SWS_IdsM_01004]. If a filter discards the SEv, the evaluation terminates immediately. Otherwise, the SEv is passed to the next filter [SWS_IdsM_00904] [SWS_IdsM_00905] [SWS_IdsM_01005]. The four filters in this order:

  1. Block State: The BswM reports the current state via IdsM_BswM_StateChanged as a bitmask of type IdsM_Filters_BlockStateType. If this state is referenced in IdsMBlockState, the filter discards the SEv [SWS_IdsM_01022] [SWS_IdsM_01023] [SWS_IdsM_91017]. A filter can reference up to 16 states SWS IdsM p. 85.
  2. Forward Every n-th: The first SEv is forwarded, and thereafter every n-th according to IdsMNthParameter. The data remains unchanged in the process [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  3. Event Aggregation: During the interval, the filter forwards nothing. At the end of the interval, a single SEv is produced with the cumulative counter [SWS_IdsM_01043] [SWS_IdsM_01046]. Context data and timestamp originate from the first or last SEv of the interval, depending on IdsMContextDataSourceSelector [SWS_IdsM_01047] [SWS_IdsM_01049]. An example is shown in SWS IdsM p. 40.
  4. Event Threshold: The filter discards SEvs as long as the counter sum in the current interval is below IdsMEventThresholdNumber. When the interval expires, the sum is reset [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063]. An example is shown in SWS IdsM p. 41.

All intervals are multiples of IdsMMainFunctionPeriod. The aggregation and threshold intervals run from the first call of the main function [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01065].

Prior to transmission to the IdsR, two limits take effect for the entire IdsM instance [SWS_IdsM_01070]:

  • Rate limiting allows at most IdsMRateLimitationMaximumEvents QSEvs per interval [SWS_IdsM_01081].
  • Traffic limiting allows at most IdsMTrafficLimitationMaximumBytes bytes per interval [SWS_IdsM_01091] [SWS_IdsM_01093].

Internal SEvs of the IdsM do not pass through these instance filters. However, they may have event-specific filters [SWS_IdsM_00803] [SWS_IdsM_00804]. Interpretation: The bypass modes only bypass the filter chain. Rate and traffic limiting are likely to apply to them as well, because [SWS_IdsM_01070] requires these limits prior to each transmission to the IdsR.

Activity diagram: First reporting mode, then the filters in fixed order, finally the instance limits before the IdsR. Filters that are not configured are omitted. Sources: SWS IdsM p. 35, [SWS_IdsM_01002], [SWS_IdsM_01004], [SWS_IdsM_01070], [SWS_IdsM_91013]

Timestamp, IDS message, and sinks

The timestamp is optional and controlled globally via IdsMTimestampOption [SWS_IdsM_01100]:

  • None: The function is deactivated. Timestamps reported along with events are ignored [SWS_IdsM_01103] [SWS_IdsM_01106].
  • AUTOSAR: Source is StbM_GetCurrentTime [SWS_IdsM_01104] [SWS_IdsM_01107].
  • Custom: The IdsM queries the application via interface IdsM_CustomTimestamp (operation Get) at port CustomTimestamp [SWS_IdsM_01109] [SWS_IdsM_01111].

If the sensor itself provides a timestamp, this takes precedence [SWS_IdsM_01108]. The IdsM truncates it to the 62 least significant bits [SWS_IdsM_01110]. According to the sequence diagrams, the IdsM determines the timestamp in the main function for all buffered events SWS IdsM p. 87.

Activity diagram: How the timestamp source is selected depending on IdsMTimestampOption. Sources: [SWS_IdsM_01106], [SWS_IdsM_01107], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110], SWS IdsM p. 86

A QSEv has the same structure regardless of which sink it is sent to [SWS_IdsM_01200]. The IDS message consists of the event frame and optionally timestamp, context data, and signature PRS IDS p. 11. Which sinks an event uses is defined by the configuration of the IdsMEvent [SWS_IdsM_01201].

The signature is optional. It becomes globally active as soon as IdsMCsmJobReference is configured. It is triggered via Csm_SignatureGenerate. For synchronous jobs, the signature is available immediately; for asynchronous jobs, IdsM_CsmNotification reports the result [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01207] [SWS_IdsM_01208].

For the IdsR sink, the IdsM transmits via PduR_IdsMTransmit [SWS_IdsM_01498]. If the message fits into a bus PDU, it uses an IF PDU, otherwise a TP PDU [SWS_IdsM_01400] [SWS_IdsM_01401]. A new transmission request only follows after confirmation of the previous one [SWS_IdsM_01499]. The DEM/Sem sink stores the complete IDS message. It has the status DRAFT in R20-11 [SWS_IdsM_01601] [SWS_IdsM_01602].

Sequence diagram: First the optional signature via CSM, then the transmission as an IF PDU or segmented TP PDU with confirmation. Sources: [SWS_IdsM_01207], [SWS_IdsM_01208], [SWS_IdsM_01500], [SWS_IdsM_01501], [SWS_IdsM_01502], SWS IdsM p. 49

Diagnostic reconfiguration and persistence of the reporting mode

Diagnostic access is optional and activated via IdsMDiagnosticSupport [SWS_IdsM_01800].

  • Change: The DCM calls IdsM_Dcm_SetReportingMode_Start with the new value [SWS_IdsM_01901] [SWS_IdsM_91008]. If the mode or event ID is invalid, the IdsM responds with E_NOT_OK and DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01902] [SWS_IdsM_01903].
  • Read: The DCM first calls IdsM_Dcm_GetReportingMode_Start and then retrieves the result with IdsM_Dcm_GetReportingMode_RequestResults [SWS_IdsM_02001] [SWS_IdsM_02002].

After a successful change, the IdsM triggers NvM_WriteBlock [SWS_IdsM_01701]. If persistence fails, it restores the previous value and reports DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905].

At startup, the IdsM uses the persisted values. If they are missing, the configuration applies [SWS_IdsM_01703] [SWS_IdsM_01704]. The NvM block must be included in NvM_ReadAll and is named IdsM_NvMRamBlockData or IdsM_NvMRomBlockData [SWS_IdsM_01705] [SWS_IdsM_01706] [SWS_IdsM_01707]. Presumably, the DCM learns the persistence result via repeated calls with OpStatus DCM_PENDING. A later version specifies DCM_E_BUSYREPEATREQUEST for this SWS IdsM p. 75.

Sequence diagram: Changing the reporting mode with NvM persistence and rollback as well as two-stage reading. Sources: [SWS_IdsM_01901], [SWS_IdsM_01904], [SWS_IdsM_01905], [SWS_IdsM_91007], SWS IdsM p. 74. The feedback path of the persistence is marked as an interpretation.

Behavior in the event of an error

The IdsM reports development errors to the DET only when IdsMDevErrorDetect is active. The error codes are listed in [SWS_IdsM_02003]:

  • IDSM_E_PARAM_INVALID: All six reporting services report this error for an unknown event ID. The counter variants additionally report it if count = 0 [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106].
  • IDSM_E_PARAM_LENGTH: The error occurs when contextDataSize exceeds the largest IdsMContextDataBufferSize [SWS_IdsM_02107] [SWS_IdsM_02109].
  • Calls before initialization and duplicate initialization are also reported [SWS_IdsM_00203] [SWS_IdsM_00204].

Attention regarding naming: [SWS_IdsM_00203] names the code IDSM_E_PARAM_UNINIT, while the error table lists it as IDSM_E_UNINIT (0x0D) [SWS_IdsM_02003].

The IdsM reports resource bottlenecks as its own internal SEvs, provided these are configured [SWS_IdsM_91015]:

  • no free event buffer (ID 46) [SWS_IdsM_00703]
  • no matching context data buffer (ID 47). The SEv is then processed without context data [SWS_IdsM_00707] [SWS_IdsM_00708]
  • traffic limit exceeded (ID 48) [SWS_IdsM_01094]

If a filter discards an SEv, this is regular behavior and not an error [SWS_IdsM_00904]. A transmission error arrives as E_NOT_OK in the confirmation [SWS_IdsM_91009]. A retry rule with IdsMTransmissionRetryDelay exists only starting in R25-11 SWS IdsM p. 51.

The synchronous and non-reentrant interface IdsM_Init serves the fundamental initialization of the module IdsM according to [SWS_IdsM_91001]. When called, the service initializes all internal variables and transitions the IdsM to the initialized state ([SWS_IdsM_00202]). Via the input parameter configPtr, the function accepts a pointer to the module-specific configuration structure ([SWS_IdsM_91001]).

The execution of IdsM_Init represents an indispensable functional precondition for the operation of the module. If an API of the IdsM other than IdsM_Init or IdsM_GetVersionInfo is called in the still uninitialized state, the module reports the error IDSM_E_PARAM_UNINIT via Det_ReportError when development detection (IdsMDevErrorDetect) is enabled ([SWS_IdsM_00203], see also error code 0x0D under [SWS_IdsM_02003]).

Specific behavioral rules apply to error handling and the call context:

  • If IdsM_Init is called while the module is already in the initialized state, reinitialization of the internal variables does not take place ([SWS_IdsM_00204]).
  • Instead, with IdsMDevErrorDetect enabled, the module reports the development error IDSM_E_ALREADY_INITIALIZED with the numeric value 0x0E via Det_ReportError ([SWS_IdsM_00204], [SWS_IdsM_02003]).
  • The function has no return value and is defined as non-reentrant ([SWS_IdsM_91001]). It must therefore not be called concurrently or multiple times simultaneously by preempting contexts in the system.

Usage and Call Context

The function IdsM_MainFunction is called periodically and is available via the header file IdsM.h [SWS_IdsM_91000]. It has the signature void IdsM_MainFunction(void), takes no parameters, and has no return value [SWS_IdsM_91000]. The call of the function itself is synchronous, but serves for the asynchronous processing of security events (SEv) that were previously queued during synchronous API calls [SWS_IdsM_91000]. The periodic triggering is typically expected to be performed by the BSW scheduler or a cyclic operating system task.

Concurrency and Limitations

According to the specification, IdsM_MainFunction is classified as non-reentrant (Non Reentrant) [SWS_IdsM_91000]. The calling system environment must therefore ensure that the function is executed in only a single instance at any time and that no overlapping calls take place.

  • IDSM_REPORTING_MODE_DETAILED (0x02): The event is reported in detail, including all relevant context data [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_BRIEF_BYPASSING_FILTERS (0x03): The event bypasses subsequent filter stages and is reported unfiltered without context data [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_DETAILED_BYPASSING_FILTERS (0x04): The event bypasses subsequent filter stages and is reported unfiltered including all context data [SWS_IdsM_91013].
  • IDSM_REPORTING_MODE_INVALID (0xFF): Designates an invalid reporting mode within the range of values [SWS_IdsM_91013].

The values thus combine two functional control dimensions: the level of detail via the context data, as well as the deliberate circumvention of regular filtering mechanisms through bypassing [SWS_IdsM_91013].
