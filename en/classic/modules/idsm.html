Role and system boundary: from sensor event to qualified security event

The Intrusion Detection System Manager (IdsM) is the BSW module of the Classic Platform that receives on-board security events (SEv) via a standardized interface. It filters them according to configurable rules into qualified events (QSEv) and subsequently stores or transmits them SWS IdsM p. 7. BSW modules, proprietary CDDs, and SW-Cs report as sensors. Sinks are the IDS Reporter (IdsR), reached via the PduR, as well as DEM/Sem for local storage SWS IdsM p. 16 [SWS_IdsM_01202] [SWS_IdsM_01601].

The IdsM explicitly does not evaluate whether a system is actually compromised. It does not know the meaning of the context data; detection and reaction lie outside the module, for example in a SOC [SWS_IdsM_CONSTR_00001]. The specification also accepts that SEvs are discarded depending on reporting frequency or system load SWS IdsM p. 11.

Other neighboring modules and their tasks:

  • DET: Development errors
  • DCM: Diagnostic access to the Reporting Mode
  • NvM: Persistence of the Reporting Mode
  • BswM: Provider of the Block State
  • StbM or a SW-C: Timestamp source
  • CSM: Signatures
  • BSW Scheduler: cyclic call

Evidence: SWS IdsM p. 13. Which headers are included depends on the associated configuration switches, e.g. Det.h for IdsMDevErrorDetect and PduR.h for IdsMSinkIdsR [SWS_IdsM_00101] [SWS_IdsM_00105].

Context diagram: The IdsM is positioned between sensors (BSW/CDD directly, SW-C via the RTE) and the sinks IdsR (via PduR) and DEM/Sem, respectively. Controlling and supporting modules are BswM, DCM, NvM, StbM, CSM, and DET. Sources: SWS IdsM p. 20, SWS IdsM p. 13, [SWS_IdsM_91027], [SWS_IdsM_91028].

Lifecycle: Initialization and cyclic processing

IdsM_Init initializes all internal variables and sets the module to the "initialized" state [SWS_IdsM_00202] [SWS_IdsM_91001]. A repeated call in the initialized state does not re-initialize. If IdsMDevErrorDetect is active, it reports IDSM_E_ALREADY_INITIALIZED instead [SWS_IdsM_00204]. In the uninitialized state, every API except IdsM_Init and IdsM_GetVersionInfo leads to a DET error [SWS_IdsM_00203].

The actual work runs asynchronously. IdsM_MainFunction is called periodically and processes the events that were queued during the API calls [SWS_IdsM_91000] SWS IdsM p. 19. The period IdsMMainFunctionPeriod is also the time base of all interval filters. Their intervals must be multiples of this period and begin with the first MainFunction call [SWS_IdsM_01050] [SWS_IdsM_01051] [SWS_IdsM_01064] [SWS_IdsM_01065].

State diagram: Only IdsM_Init makes the module usable. Erroneous calls in both states are reported to the DET without changing the state. Sources: [SWS_IdsM_00202], [SWS_IdsM_00203], [SWS_IdsM_00204], [SWS_IdsM_91000].

Reporting of Security Events: Identity, API variants, and buffering

Each SEv instance is described by four specifications: IdsMExternalEventId, IdsMSensorInstanceId, an internally calculated IdsMInternalEventId, and the event name [SWS_IdsM_00600] [SWS_IdsM_00601]. The following rules apply to its usage (SWS IdsM p. 21):

  • Sensors exclusively use the symbolic constant of the IdsMEvent container, never the internal numerical value [SWS_IdsM_00602] [SWS_IdsM_00607].
  • The external ID 0xFFFF is invalid [SWS_IdsM_00604].
  • If there is only one module instance, the sensor instance is 0 by default [SWS_IdsM_00608].

Six synchronous, non-reentrant services are available for reporting. They differ in the additional data provided. The variants with counter and timestamp are aimed at Smart Sensors (SW-C or CDD) that determine these values themselves SWS IdsM p. 19. If only a timestamp is available without an own counter, count = 1 is passed [SWS_IdsM_00405].

Context data is passed as a pointer to a byte array and may be up to 1500 bytes long [SWS_IdsM_00501] [SWS_IdsM_00502]. For SW-C sensors, two additional parameters apply SWS IdsM p. 37:

  • IdsMEventMaxContextDataSize limits the amount of context data [SWS_IdsM_01300].
  • IdsMAdditionalParameterOption (None, Count, CountTimestamp) determines which parameters the service port interface offers [SWS_IdsM_01301] [SWS_IdsM_01303].

Upon reception, the IdsM stores the SEv in an Event Buffer [SWS_IdsM_00702]. Context data is placed into a Context Data Buffer of the same or next larger size, which is linked to the Event Buffer [SWS_IdsM_00705] [SWS_IdsM_00706]. Without context data, no context buffer is allocated [SWS_IdsM_00709]. The number and sizes of the buffers are configurable [SWS_IdsM_00701] [SWS_IdsM_00704]. For the number of Event Buffers, the specification recommends: number of aggregation filter instances plus upper limit of events processed in parallel SWS IdsM p. 22.

Sequence diagram: Reporting in the sensor context only buffers the SEv. Timestamp, filtering, and qualification follow only in the cyclic IdsM_MainFunction call (variant with StbM as time source). Sources: SWS IdsM p. 86, [SWS_IdsM_00702], [SWS_IdsM_00901], [SWS_IdsM_01104].

Activity diagram: A missing Event Buffer triggers an internal SEv. A missing Context Data Buffer causes the event to be processed further without context data. Sources: SWS IdsM p. 27, [SWS_IdsM_00703], [SWS_IdsM_00705], [SWS_IdsM_00707], [SWS_IdsM_00708].

Qualification: Reporting mode and filter chain

Each SEv has a mandatory reporting mode filter. It is not part of the filter chain, but is attached directly to the event; its default value originates from IdsMReportingModeFilter [SWS_IdsM_01010] [SWS_IdsM_01011] [SWS_IdsM_01012]. The values of IdsM_Filters_ReportingModeType mean [SWS_IdsM_91013] SWS IdsM p. 91:

  • IDSM_REPORTING_MODE_OFF: Event is discarded.
  • IDSM_REPORTING_MODE_BRIEF / IDSM_REPORTING_MODE_DETAILED: Reporting without or with context data, respectively.
  • …_BYPASSING_FILTERS: Reporting while bypassing the filter chain.

Only after the reporting mode is the filter chain assigned to the SEv evaluated [SWS_IdsM_01001] [SWS_IdsM_01002]. Activated filters run in a fixed order: Block State, Forward Every Nth, Event Aggregation, Event Threshold [SWS_IdsM_01004]. If a filter discards the SEv, any further evaluation is omitted [SWS_IdsM_01005] SWS IdsM p. 25. A filter chain requires at least one filter [SWS_IdsM_CONSTR_00002]. The individual filters work as follows:

  • Block State: The BswM reports the current state via IdsM_BswM_StateChanged. If this state belongs to the referenced IdsMBlockState, the SEv is discarded [SWS_IdsM_01022] [SWS_IdsM_01023] SWS IdsM p. 28.
  • Forward Every Nth: The first and thereafter every n-th SEv are forwarded unchanged [SWS_IdsM_01031] [SWS_IdsM_01032] [SWS_IdsM_01033].
  • Aggregation: SEvs are held back during IdsMEventAggregationTimeInterval. At the end of the interval, an SEv with the sum of all counters proceeds; context data and timestamp originate optionally from the first or last SEv [SWS_IdsM_01043] [SWS_IdsM_01046] [SWS_IdsM_01047] [SWS_IdsM_01048] [SWS_IdsM_01049] SWS IdsM p. 40.
  • Threshold: As long as the counter sum in the interval is below IdsMEventThresholdNumber, it is discarded; once the threshold is reached, forwarding occurs. At the end of the interval, the counter is reset [SWS_IdsM_01061] [SWS_IdsM_01062] [SWS_IdsM_01063] SWS IdsM p. 41.

Activity diagram: First, the reporting mode decides on discarding, bypassing, or filtering. Thereafter, the SEv traverses the activated filters in a fixed order until it is discarded or becomes a QSEv. Sources: SWS IdsM p. 35, SWS IdsM p. 24, [SWS_IdsM_01004], [SWS_IdsM_01005], [SWS_IdsM_91013].

Enrichment and forwarding of qualified events

QSEvs have a fixed structure according to the IDS protocol, regardless of the sink [SWS_IdsM_01200]. Which sinks are used is defined by the configuration per IdsMEvent [SWS_IdsM_01201] SWS IdsM p. 35. With IdsMSinkIdsR, the QSEv is sent via PduR_IdsMTransmit as an IDS Message [SWS_IdsM_01203] [SWS_IdsM_01498]. Prior to sending to the IdsR, instance-wide limitations apply: rate limiting restricts the number of QSEvs per interval, traffic limiting the bytes per interval [SWS_IdsM_01070] [SWS_IdsM_01081] [SWS_IdsM_01091] SWS IdsM p. 32.

The transmission path depends on the size SWS IdsM p. 38:

  • If the IDS Message including signature fits into a bus PDU, an IF-PDU is used [SWS_IdsM_01400]; the confirmation comes via IdsM_TxConfirmation [SWS_IdsM_01500].
  • Otherwise, TP-PDUs are used [SWS_IdsM_01401]. The PduR fetches the data segment by segment via IdsM_CopyTxData [SWS_IdsM_01501] and confirms via IdsM_TpTxConfirmation [SWS_IdsM_01502].
  • Prior to the confirmation, the IdsM does not call PduR_IdsMTransmit again [SWS_IdsM_01499].

Sequence diagram: After limitation, a QSEv is transmitted as an IF- or TP-PDU depending on its size. Only after confirmation may the next transmission begin. Sources: [SWS_IdsM_01070], [SWS_IdsM_01400], [SWS_IdsM_01401], [SWS_IdsM_01499], [SWS_IdsM_01501], [SWS_IdsM_01502].

Optionally, the IdsM signs each QSEv. This is activated globally by a CSM job referenced via IdsMCsmJobReference. The signature is generated via Csm_SignatureGenerate; for asynchronous jobs, the CSM reports the result via IdsM_CsmNotification [SWS_IdsM_01204] [SWS_IdsM_01206] [SWS_IdsM_01208] SWS IdsM p. 36. The DEM/Sem sink is marked as DRAFT in R20-11; it stores the complete IDS Message [SWS_IdsM_01600] [SWS_IdsM_01602].

Timestamps are enabled globally via IdsMTimestampOption [SWS_IdsM_01100] [SWS_IdsM_01103] SWS IdsM p. 33. The following rules apply SWS IdsM p. 34:

  • If the sensor does not provide a timestamp, the IdsM retrieves it itself: for "AUTOSAR" via StbM_GetCurrentTime, for "Custom" via the interface IdsM_CustomTimestamp from an SW-C [SWS_IdsM_01104] [SWS_IdsM_01107] [SWS_IdsM_01109] [SWS_IdsM_01111].
  • Timestamps reported by the sensor take precedence and are truncated to the 62 least significant bits [SWS_IdsM_01108] [SWS_IdsM_01110].
  • For "None", passed timestamps are also ignored [SWS_IdsM_01106].

An open point of the specification: [SWS_IdsM_01112] requires timestamp option bit 0 if the timestamp APIs are used without a timestamp parameter. How this relates to [SWS_IdsM_01101] is left open by the text.

Activity diagram: The timestamp source is determined from IdsMTimestampOption and the reported parameter. Sources: SWS IdsM p. 87, [SWS_IdsM_01104], [SWS_IdsM_01106], [SWS_IdsM_01108], [SWS_IdsM_01109], [SWS_IdsM_01110].

Reporting mode at runtime: Diagnostics and NvM persistence

If IdsMDiagnosticSupport is active, the reporting mode can be read and changed via the DCM [SWS_IdsM_01800] [SWS_IdsM_01900] [SWS_IdsM_02000] SWS IdsM p. 40:

  • Reading takes place in two stages: IdsM_Dcm_GetReportingMode_Start triggers the routine, IdsM_Dcm_GetReportingMode_RequestResults delivers the result via a pointer [SWS_IdsM_02001] [SWS_IdsM_02002].
  • Changing takes place via IdsM_Dcm_SetReportingMode_Start. An invalid mode or an invalid event ID results in E_NOT_OK with DCM_E_REQUESTOUTOFRANGE [SWS_IdsM_01901] [SWS_IdsM_01902] [SWS_IdsM_01903].

After a successful change, the IdsM triggers NvM_WriteBlock [SWS_IdsM_01701]. If persistence fails, it resets the mode to the previous value and responds with DCM_E_GENERALPROGRAMMINGFAILURE [SWS_IdsM_01702] [SWS_IdsM_01904] [SWS_IdsM_01905]. At startup, it reads the persisted mode. For this, the NvM block must be contained in NvM_ReadAll; if NvM values are missing, the configuration applies [SWS_IdsM_01703] [SWS_IdsM_01704] [SWS_IdsM_01705] SWS IdsM p. 39.

Sequence diagram: Reading proceeds in two stages via Start and RequestResults. When changing, verification occurs first, followed by persistence, and rolling back in case of an error. Sources: [SWS_IdsM_02001], [SWS_IdsM_02002], [SWS_IdsM_01902], [SWS_IdsM_01903], [SWS_IdsM_01701], [SWS_IdsM_01904], [SWS_IdsM_01905].

Behavior in the event of an error

If IdsMDevErrorDetect is active, the IdsM reports development errors to the DET. The error codes are IDSM_E_PARAM_INVALID (0x0A), IDSM_E_PARAM_POINTER (0x0B), IDSM_E_PARAM_LENGTH (0x0C), IDSM_E_UNINIT (0x0D), and IDSM_E_ALREADY_INITIALIZED (0x0E) [SWS_IdsM_02003]. Caution: [SWS_IdsM_00203] specifies IDSM_E_PARAM_UNINIT for calls in the uninitialized state. The error table does not list this code; instead, it contains IDSM_E_UNINIT. The parameter checks in detail:

  • Unknown securityEventId for the reporting APIs as well as count = 0 for the counter variants result in IDSM_E_PARAM_INVALID [SWS_IdsM_02101] [SWS_IdsM_02103] [SWS_IdsM_02106] SWS IdsM p. 42.
  • An contextDataSize greater than the largest IdsMContextDataBufferSize results in IDSM_E_PARAM_LENGTH [SWS_IdsM_02107] [SWS_IdsM_02108] [SWS_IdsM_02109] SWS IdsM p. 43.
  • An invalid NULL_PTR results in IDSM_E_PARAM_POINTER SWS IdsM p. 42.

The IdsM reports bottlenecks at runtime via dedicated internal SEvs, provided these are configured. They have their own buffers and are not filtered by instance-wide filters [SWS_IdsM_91015] [SWS_IdsM_00802] [SWS_IdsM_00803] SWS IdsM p. 24. There are three internal SEvs:

  • no Event Buffer available [SWS_IdsM_00703]
  • no Context Data Buffer available; the SEv is then processed further without context data [SWS_IdsM_00707] [SWS_IdsM_00708]
  • traffic limitation exceeded [SWS_IdsM_01094]

If persistence fails during a diagnostic change, the rollback described above takes effect [SWS_IdsM_01905].

Usage and Semantics

Function [SWS_IdsM_91010] (provided via IdsM_Cbk.h) is called synchronously by lower-layer modules (such as transport protocols) to retrieve transmit data of an I-PDU segment (N-PDU).

  • id: Identifies the I-PDU to be transmitted.
  • info: Passes the destination buffer (SduDataPtr) and the number of bytes to be copied (SduLength). With a value of 0 for SduLength, SduDataPtr is allowed to be a NULL_PTR; this serves to update status via the retry parameter or to query remaining data.
  • retry: Controls confirmation and error recovery. If the parameter is NULL_PTR, transmitted data can be removed from the buffer immediately after copying. Otherwise, the state controls: TP_CONFPENDING retains previously copied data for retries, TP_DATACONF confirms preceding transmissions, and TP_DATARETRY initiates recopying starting from the byte offset specified in TxTpDataCnt.
  • availableDataPtr: Returns the remaining number of bytes available in the Tx buffer, which can be used by transport protocols with variable payload length to determine subsequent segments.

Return Values and Error Handling

The return is performed via status code BufReq_ReturnType:

  • BUFREQ_OK: Data were completely copied into the destination buffer as requested.
  • BUFREQ_E_BUSY: Not enough transmit data available; no data were copied. The lower layer can repeat the query at a later point in time.
  • BUFREQ_E_NOT_OK: The request failed; no data were copied.

Concurrency

According to [SWS_IdsM_91010], the function is specified as synchronous and reentrant.

Usage and Semantics

The function IdsM_SetSecurityEvent serves as an application interface for reporting security events to the IdsM module ([SWS_IdsM_91002]). The interface is provided via the header IdsM.h and has the service ID 0x03.

  • Parameters: securityEventId (in, type IdsM_SecurityEventIdType) designates the ID of the occurred security event ([SWS_IdsM_91002]).
  • Return value: None (void).
  • Synchronous semantics: The function call is executed synchronously ([SWS_IdsM_91002]).

Concurrency and Limitations

The function is specified as non-reentrant (Non Reentrant) ([SWS_IdsM_91002]). Callers must therefore ensure that calls to IdsM_SetSecurityEvent do not occur concurrently or preemptively without appropriate synchronization.

Error Handling and Interaction

If development error detection is enabled via the configuration parameter IdsMDevErrorDetect, the IdsM module checks the passed parameter securityEventId against the configured security events. If an unknown event ID is passed that is not stored in IdsMEvent, the function reports the development error IDSM_E_PARAM_INVALID ([SWS_IdsM_02101]).

The function returns no value (void) [SWS_IdsM_91003].

Error Handling and Validation
