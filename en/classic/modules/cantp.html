CanTp as a segmentation layer between PduR and CanIf

CanTp is the CAN transport layer of the Classic communication stack. The module segments N-SDUs that do not fit into a CAN frame, transmits them with flow control, and reassembles them upon reception (SWS CanTp p. 23). The technical basis is ISO 15765-2: Every recommendation not expressly excluded therein must be adhered to [SWS_CanTp_00033]. Segmentation and reassembly take place only in the CANTP_ON state [SWS_CanTp_00238].

Upwards, CanTp interacts exclusively with the PDU Router. Users such as DCM or Com access CanTp_Transmit, CanTp_CancelTransmit, and CanTp_CancelReceive via the PduR (SWS PduR p. 24). In the reverse direction, CanTp invokes the services PduR_CanTp…; downwards, it uses CanIf_Transmit [SWS_CanTp_00216]. For the lower layer, CanTp provides the callbacks CanTp_RxIndication and CanTp_TxConfirmation [SWS_CanTp_00078] [SWS_CanTp_00076]. Both must be callable in interrupt context [SWS_CanTp_00235] [SWS_CanTp_00236]. Newer document sections designate the "LSduR" as the lower partner (SWS CanTp p. 26). In R20-11, this partner is CanIf [SWS_CanTp_00335].

Context diagram: CanTp is located between PduR and CanIf, is initialized via BswM, and is operated cyclically by the scheduler. Sources: [SWS_CanTp_00216] [SWS_CanTp_00164] SWS CanTp p. 17 Modemanagement-Guide p. 54

From power-on via CanTp_Init to the channel states

CanTp knows the global states CANTP_OFF and CANTP_ON [SWS_CanTp_00027]. After power-on, the module is in CANTP_OFF [SWS_CanTp_00168]. In this state, the post-build configuration may be updated [SWS_CanTp_00169]. The environment must call CanTp_Init before any further use [SWS_CanTp_00199]. In doing so, the function receives a pointer to CanTp_ConfigType [SWS_CanTp_00208] [SWS_CanTp_00340]. In the example of the mode management guide, the call is located in a BswM rule after NvM_ReadAll (Modemanagement-Guide p. 54).

After successful initialization, CanTp transitions to CANTP_ON [SWS_CanTp_00170]. CanTp_Init initializes all global variables and sets each connection to CANTP_RX_WAIT or CANTP_TX_WAIT [SWS_CanTp_00030]. A renewed call in CANTP_ON leads back to idle; in doing so, all running connections are lost [SWS_CanTp_00111] [SWS_CanTp_00273]. CanTp_Shutdown closes all open connections, frees the resources, and transitions to CANTP_OFF [SWS_CanTp_00202]. No notification is given regarding aborted transmissions in this case [SWS_CanTp_00200].

State diagram: Within CANTP_ON, Rx and Tx channels pass through the substates WAIT and PROCESSING independently of each other. Sources: [SWS_CanTp_00027] [SWS_CanTp_00030] [SWS_CanTp_00202] SWS CanTp p. 27

Transmitting an N-SDU: Single Frame or segmented session

CanTp_Transmit passes the total length and, if applicable, MetaData, but no payload. Without MetaData, CanTp uses only SduLength to prepare the PCI of the Single Frame (SF) or First Frame (FF) [SWS_CanTp_00225] [SWS_CanTp_00299].

Interpretation: [SWS_CanTp_00212] describes the API as synchronous, whereas [SWS_CanTp_00176] requires asynchronous behavior. Presumably, the call merely acknowledges acceptance, and the transmission takes place thereafter.

If the data does not fit into the assigned N-PDU, a multi-frame session starts [SWS_CanTp_00232] (SWS CanTp p. 60). The maximum transmission length (TX_DL) results from the EcuC parameter PduLength [SWS_CanTp_00354].

CanTp fetches the payload for each segment (SF, FF, CF) using PduR_CanTpCopyTxData [SWS_CanTp_00086] [SWS_CanTp_00298]. In case of BUFREQ_E_BUSY, CanTp retries the copy attempt later [SWS_CanTp_00184]. The retry parameter is always a NULL pointer [SWS_CanTp_00272].

After the FF, the timer N_Bs monitors the arrival of the Flow Control (FC) [SWS_CanTp_00315]. An FC follows after each block of BS Consecutive Frames [SWS_CanTp_00278]. At the end, CanTp reports completion with PduR_CanTpTxConfirmation and E_OK [SWS_CanTp_00090] [SWS_CanTp_00204]. Every accepted request ends with exactly one such feedback, even in case of failure [SWS_CanTp_00177].

CanTp rejects new requests with E_NOT_OK if the channel is occupied (CANTP_TX_PROCESSING) or the N-SDU is already running in a session [SWS_CanTp_00123] [SWS_CanTp_00206].

Sequence diagram: CanTp pulls the data segment by segment from the PduR and clocks the Consecutive Frames based on the Flow Control. Sources: [SWS_CanTp_00086] [SWS_CanTp_00232] [SWS_CanTp_00315] [SWS_CanTp_00090] SWS CanTp p. 37 SWS CanTp p. 73

Reception: buffer commitment, Flow Control, and wait phases

A received SF or FF triggers PduR_CanTpStartOfReception [SWS_CanTp_00079]. The available buffer size is returned via the output pointer and may be smaller than the N-SDU [SWS_CanTp_00080]. The FC for an FF is sent only after this result, and its content depends on it [SWS_CanTp_00064] [SWS_CanTp_00277].

After each Consecutive Frame (CF), CanTp passes the data with PduR_CanTpCopyRxData: 6 or 7 bytes for CAN 2.0, DLC-1 or DLC-2 bytes for CAN FD. As return value, CanTp receives the remaining buffer [SWS_CanTp_00269]. In any case, whether successful or not, CanTp reports completion with PduR_CanTpRxIndication [SWS_CanTp_00084].

If the buffer is insufficient for the next block, CanTp starts the timer N_Br [SWS_CanTp_00082] [SWS_CanTp_00325]. As long as N_Br is running, CanTp polls for free buffer in each MainFunction with length 0 and NULL_PTR [SWS_CanTp_00222]. In doing so, it transmits at most WFTmax consecutive FC(WAIT); thereafter, it aborts with E_NOT_OK [SWS_CanTp_00223]. BS and STmin remain constant within a reception session [SWS_CanTp_00067]. The specification example shows the reception of 49 bytes with a 25-byte buffer (SWS CanTp p. 38).

Connection channels, addressing, and buffering strategy

CanTp serves multiple connections simultaneously [SWS_CanTp_00096]. Each N-SDU is statically assigned to a connection channel; a channel can serve multiple N-SDUs [SWS_CanTp_00121]. Each channel has its own buffers, timers, and state machines [SWS_CanTp_00122]. The channels are visible only internally [SWS_CanTp_00285]. The configuration tool determines their number from the assignment of N-SDUs to channels [SWS_CanTp_00289]. If multiple N-SDUs share a channel and no channel is free, CanTp rejects the transmission or aborts the reception [SWS_CanTp_00288] (SWS CanTp p. 41).

Functional addressing (1:n) is intended only for Single Frames [SWS_CanTp_00092]. CanTp rejects a segmented session via a functional handle and reports CANTP_E_INVALID_TATYPE [SWS_CanTp_00093]. With extended or mixed addressing, the first data byte (N_TA or N_AE) determines the associated N-SDU [SWS_CanTp_00095] [SWS_CanTp_00284].

Generic connections work with MetaData. CanTp stores the address information from a received SF/FF or from CanTp_Transmit [SWS_CanTp_00330] [SWS_CanTp_00334]. It forwards it to the PduR or to CanIf [SWS_CanTp_00331] [SWS_CanTp_00335]. It checks incoming CFs and FCs against the stored values [SWS_CanTp_00333] [SWS_CanTp_00336]. An N-PDU may only be referenced by multiple N-SDUs in the case of extended/mixed addressing or with MetaData [SWS_CanTp_00328].

CanTp does not copy payload data internally, but operates directly on the buffers of the upper layer via the copy services [SWS_CanTp_00298]. The upper layer therefore keeps its buffer locked. The lock begins with E_OK of CanTp_Transmit or BUFREQ_OK of PduR_CanTpStartOfReception and ends with the associated confirmation or indication (SWS CanTp p. 35).

The following rules apply to padding (SWS CanTp p. 43):

  • Only used data bytes go to the upper layer [SWS_CanTp_00116].
  • The padding value is CANTP_PADDING_BYTE [SWS_CanTp_00059].
  • With active padding, SF, last CF, and FC are transmitted as 8-byte frames [SWS_CanTp_00348] [SWS_CanTp_00347].
  • With CAN FD, padding is applied up to the next valid DLC [SWS_CanTp_00351].

MainFunction cycle and BS/STmin runtime parameters

CanTp_MainFunction is called cyclically by the scheduler. It monitors the time limits N_As, N_Bs, N_Cs, N_Ar, N_Br, and N_Cr as well as STmin [SWS_CanTp_00213] [SWS_CanTp_00164]. Its behavior depends on CanTpMainFunctionPeriod [SWS_CanTp_00300]. A document section of later releases recommends using the cycle time of the calling task for this (SWS CanTp p. 77). As an example, the timing analysis cites a 5 ms task (TR Timing p. 117).

Using CanTp_ChangeParameter and CanTp_ReadParameter, BS and STmin of a receive N-SDU can be set and read at runtime [SWS_CanTp_00302] [SWS_CanTp_00323]. Here, BS is a maximum value that CanTp may fall below due to buffer considerations [SWS_CanTp_00091]. No change is possible during an ongoing reception; the service then returns E_NOT_OK [SWS_CanTp_00303] [SWS_CanTp_00304]. For generic connections, a change applies to all [SWS_CanTp_00338]. Whether the services exist is controlled by CanTpChangeParameterApi (SWS CanTp p. 61). Transmission cancellation is enabled statically via CanTpTc [SWS_CanTp_00242].

Behavior in the event of an error

In case of a development error, the service returns E_NOT_OK and reports the error to the DET [SWS_CanTp_00294]. Typical cases:

  • Calls prior to CanTp_Init generate CANTP_E_UNINIT; excepted is CanTp_GetVersionInfo [SWS_CanTp_00031].
  • NULL pointers generate CANTP_E_PARAM_POINTER [SWS_CanTp_00321] [SWS_CanTp_00322] [SWS_CanTp_00319].

For invalid IDs in CanTp_CancelTransmit and CanTp_CancelReceive, R20-11 requires CANTP_E_PARAM_ID [SWS_CanTp_00254] [SWS_CanTp_00260]. Newer document sections specify CANTP_E_INVALID_TX_ID or CANTP_E_INVALID_RX_ID instead (SWS CanTp p. 59). For R20-11, the requirement applies. Runtime errors such as CANTP_E_PADDING, CANTP_E_INVALID_TATYPE, and CANTP_E_OPER_NOT_SUPPORTED are defined by [SWS_CanTp_00352].

Protocol errors terminate the session and are reported to the upper layer with E_NOT_OK. Recovery is the responsibility of the user, for example DCM (EXP Error p. 30; [SWS_CanTp_00205]).

Usage and Call Context

With the function CanTp_Transmit, the upper layer requests the transmission of a PDU [SWS_CanTp_00212]. The PDU is identified via the parameter TxPduId, while PduInfoPtr references the data length, the payload data, and optional metadata [SWS_CanTp_00212]. The function acknowledges the transmission request synchronously with E_OK in case of successful acceptance or with E_NOT_OK in case of rejection [SWS_CanTp_00212]; the actual transmission process is asynchronous [SWS_CanTp_00176].

Error Handling and Rejection Conditions

  • Invalid pointer: If DET is enabled and a NULL pointer is passed for PduInfoPtr, the function reports the error CANTP_E_PARAM_POINTER to the DET and aborts without further action [SWS_CanTp_00321].
  • Channel busy: If the configured transmit channel is in the state CANTP_TX_PROCESSING, the module rejects new transmit requests for this channel and returns E_NOT_OK [SWS_CanTp_00123].
  • Ongoing session: A transmit request is also rejected if the passed N-SDU identifier is already in use in a currently active CanTp transport session [SWS_CanTp_00206].

Concurrency and Data Handling

CanTp_Transmit is reentrant for different PDU-IDs, but not reentrant for the same PDU-ID [SWS_CanTp_00212].

For connections without metadata, CanTp_Transmit evaluates exclusively the specification SduLength to create the PCI for Single Frames (SF) or First Frames (FF) and does not access the data buffer of the N-SDU [SWS_CanTp_00225]. If metadata is used, the module stores the contained address information (such as N_SA, N_TA, or N_AE depending on the addressing format) for subsequent transmission of SF, FF, and CF N-PDUs and for identifying FC N-PDUs [SWS_CanTp_00334].

The synchronous function CanTp_CancelTransmit ([SWS_CanTp_00246]) requests the cancellation of an ongoing transmission of a PDU in a lower-layer communication module. CanTp_CancelTransmit is reentrant for different PDU IDs, but non-reentrant for the same PDU ID ([SWS_CanTp_00246]).

Usage and Semantics

The function CanTp_ChangeParameter ([SWS_CanTp_00302]) serves the synchronous request to change a specific transport protocol parameter, such as the block size (block size). The call takes place via the header CanTp.h with the service ID 0x4b.

The interface expects the following input parameters:

  • parameter: Identifier of the parameter to be modified.
  • value: The new parameter value to be set.

As a return value of type Std_ReturnType, the function returns either E_OK upon successful change or E_NOT_OK in case of a rejection ([SWS_CanTp_00302]). The function is specified as non-reentrant (Non Reentrant) ([SWS_CanTp_00302]). If the service is called for an N-SDU with MetaData (indicating a generic connection), the change is applied to all generic connections, so that it takes effect for all subsequent reception processes ([SWS_CanTp_00338]).

Usage and Call Context

The synchronous callback function CanTp_RxIndication ([SWS_CanTp_00214]) signals the reception of an N-PDU by an underlying communication interface module to the CAN transport module. The identifier RxPduId as well as PduInfoPtr with pointers to buffer data (SduDataPtr), SDU length (SduLength), and metadata are passed. The function is reentrant for different PDU IDs, but non-reentrant for the same PDU ID ([SWS_CanTp_00214]). It may be called directly in the interrupt context, for example from the CAN receive ISR ([SWS_CanTp_00235]).

Error Handling and Validation

If development error detection is enabled and a NULL pointer is passed as PduInfoPtr, CanTp_RxIndication reports the error CANTP_E_PARAM_POINTER to the DET and terminates execution without doing anything ([SWS_CanTp_00322]).

When padding check is enabled for frames with up to 8 bytes of payload, specific consistency rules apply:

  • If an SF N-PDU with SduLength < 8 is received at CanTpRxPaddingActivation == CANTP_ON, the reception is discarded and the runtime error CANTP_E_PADDING is reported to the DET ([SWS_CanTp_00345]).
  • If the last CF N-PDU of an ongoing transmission does not have exactly 8 bytes when padding is active (SduLength != 8), CanTp aborts the reception via PduR_CanTpRxIndication() with the return value E_NOT_OK and reports CANTP_E_PADDING ([SWS_CanTp_00346]).
  • If an FC N-PDU with SduLength < 8 arrives during a transmission session with CanTpTxPaddingActivation == CANTP_ON, CanTp aborts the transmission session via PduR_CanTpTxConfirmation() with E_NOT_OK and reports CANTP_E_PADDING to the DET ([SWS_CanTp_00349]).

Generic Connections

If it is a generic connection (N-PDU with metadata), the CanTp module saves the addressing data from the metadata upon invocation for SF or FF frames (for Normal Fixed and Mixed 29-bit: N_SA and N_TA) for upward connection initiation as well as for subsequent FC and CF identification ([SWS_CanTp_00330]). For subsequent CF ([SWS_CanTp_00333]) and FC frames ([SWS_CanTp_00336]), CanTp matches the received metadata against these stored reference values.

Usage and Semantics

The function CanTp_TxConfirmation ([SWS_CanTp_00215]) is provided by the CanTp module for confirmation calls of the underlying communication interface ([SWS_CanTp_00076]). It synchronously confirms either the successful transmission of a PDU or the failure of the transmission process. The interface is declared via the header CanTp.h, has no return value (void), and expects two input parameters:

  • TxPduId: Identifier of the transmitted PDU.
  • result: Transmission status with the values E_OK (PDU transmitted successfully) or E_NOT_OK (transmission failed).

Error Handling and Interaction

If CanTp_TxConfirmation is called by the lower layer with the result value E_NOT_OK, the CanTp module aborts the associated transmission session ([SWS_CanTp_00355]).

Concurrency and Call Context

The following specifications apply to invocation and concurrency:

  • Call context: The function may be called explicitly in interrupt context, for example directly from the transmit interrupt service routine of the CAN driver ([SWS_CanTp_00236]).
  • Reentrancy: The function is reentrant for calls with different PDU IDs, but non-reentrant when using the same TxPduId ([SWS_CanTp_00215]).
