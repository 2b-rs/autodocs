Role of CanIf: hardware-independent hub between CAN drivers and communication stack

The CAN Interface (CanIf) takes over all hardware-independent tasks of CAN communication of an ECU. The underlying CAN drivers thus only deal with access to and control of the respective CAN hardware. CanIf processes transmit requests, transmit confirmations, receive and error indications as well as start and stop of the CAN controllers. Its data APIs operate on CAN L-SDUs, its control APIs are related to the CAN controller (SWS CanIf p. 13). CanIf never accesses hardware-specific communication buffers directly, but exclusively via services of the CanDrv [SWS_CANIF_00023].

Downwards, CanIf serves one or more CanDrv. In link-time configuration, this is done via a set of function pointers per driver [SWS_CANIF_00378]. In addition, CanIf combines the APIs of multiple CanTrcv into a uniform interface without containing transceiver logic itself (SWS CanIf p. 21, [SWS_CANIF_00358]). Upwards, there are configurable users:

  • PduR, CanNm, CanTp, Xcp, and CDDs as data users ([SWS_CANIF_00439], [SWS_CANIF_00445], [SWS_CANIF_00448], [SWS_CANIF_00555]),
  • CanSM as control instance for controller and transceiver modes [SWS_CANIF_00711],
  • EcuM for initialization and wake-up (SWS CanIf p. 40, [SWS_CANIF_00563]).

Context diagram: CanIf decouples upper layers, CanSM, and EcuM from CanDrv and CanTrcv and reports to Mirror, IdsM, and DET. Sources: SWS CanIf p. 13, [SWS_CANIF_00724], [SWS_CANIF_00905], [SWS_CANIF_00913]

Configuration, abstraction IDs, and initialization

CanIf_Init() [SWS_CANIF_00001] reads the CAN configuration from containers and parameters. This allows the configuration to be changed without rebuilding the module (SWS CanIf p. 22). CanIf_ConfigType [SWS_CANIF_00144] contains the public parameters and the definition of each L-PDU/L-SDU [SWS_CANIF_00523]. The initialization has the following effects:

  • Variables, flags, and all transmit buffers are reset ([SWS_CANIF_00085], [SWS_CANIF_00387]).
  • Each channel is set to CANIF_OFFLINE [SWS_CANIF_00864].
  • Dynamic Tx CanIds receive the value from CanIfTxPduCanId [SWS_CANIF_00857].

The controllers remain in the STOPPED state afterwards (SWS CanIf p. 40). Before CanIf_Init(), all services except CanIf_Init() and CanIf_GetVersionInfo() return the value E_NOT_OK [SWS_CANIF_00661].

CanIf assigns its own abstraction IDs starting at 0:

  • ControllerId for controllers [SWS_CANIF_00653],
  • TransceiverId for transceivers [SWS_CANIF_00655].

For access to hardware objects, CanIf uses HTH (transmission) and HRH (reception) ([SWS_CANIF_00662], [SWS_CANIF_00291], [SWS_CANIF_00292]). Per CanDrv, HTH and HRH form a common number range [SWS_CANIF_00115]. HRHs of type BasicCAN require a software filter ([SWS_CANIF_00663], SWS CanIf p. 38).

The target callbacks of the upper layers are configured. If no name is specified, the call is omitted; the assignment to the receiver is performed via the L-SDU ID (SWS CanIf p. 133). However, a BusOff user is mandatory [SWS_CANIF_00524]. Optional services can be switched off at compile time, such as:

  • CanIf_ReadRxPduData() [SWS_CANIF_00330],
  • CanIf_SetDynamicTxId() [SWS_CANIF_00357],
  • CanIf_TriggerTransmit() [SWS_CANIF_00884],
  • CanIf_EnableBusMirroring() [SWS_CANIF_00911].

Before CanIf_DeInit() [SWS_CANIF_91002], the caller must ensure that no transmissions and no transmit confirmations are pending anymore (SWS CanIf p. 81).

Transmit path: from CanIf_Transmit via buffering to confirmation

CanIf_Transmit() [SWS_CANIF_00005] determines the matching HTH for TxPduId and calls Can_Write(). As swPduHandle, CanIf passes the ID that is returned later in the confirmation [SWS_CANIF_00318]. If Can_Write() returns E_OK, CanIf_Transmit() also returns E_OK [SWS_CANIF_00162]. The request is rejected if the controller is not in CAN_CS_STARTED and the transmit path is neither online nor offline-active ([SWS_CANIF_00317], [SWS_CANIF_00677]).

When buffering is activated [SWS_CANIF_00063], CanIf stores an L-PDU rejected with CAN_BUSY in the assigned CanIfTxBuffer ([SWS_CANIF_00381], [SWS_CANIF_00836]). A buffer size greater than zero is a prerequisite [SWS_CANIF_00835]. If the same L-PDU is already buffered, it is overwritten [SWS_CANIF_00068]. If the buffer is full, the call returns E_NOT_OK [SWS_CANIF_00837]. In principle, an L-PDU is located in exactly one place only: either in the hardware object or in the CanIf buffer (SWS CanIf p. 43).

Sequence diagram: If the hardware object is free, CanIf writes directly; in case of CAN_BUSY, it buffers; the upper layer receives E_OK in both cases. Sources: SWS CanIf p. 138, [SWS_CANIF_00162], [SWS_CANIF_00381], [SWS_CANIF_00837]

After successful transmission, CanDrv calls CanIf_TxConfirmation() [SWS_CANIF_00007]. Then the following takes place:

  1. CanIf checks whether requests are waiting in the buffer of the freed HTH [SWS_CANIF_00386].
  2. It transmits the request with the highest priority ([SWS_CANIF_00668], [SWS_CANIF_00070]).
  3. After E_OK, it removes this request immediately from the buffer [SWS_CANIF_00183].
  4. Finally, it notifies the upper layer with <User_TxConfirmation>(E_OK) ([SWS_CANIF_00383], [SWS_CANIF_00011]).

Later releases call this invocation LSduR_CanIfTxConfirmation() (SWS CanIf p. 157). For R20-11, the configurable <User_TxConfirmation> applies.

Sequence diagram: Within the transmit confirmation, the buffer is pushed first and then the upper layer is confirmed. Sources: SWS CanIf p. 143, [SWS_CANIF_00386], [SWS_CANIF_00183], [SWS_CANIF_00383]

For transmission, there are two special forms and a length rule:

  • Triggered transmission: SduDataPtr may be NULL [SWS_CANIF_00882]. CanIf_TriggerTransmit() fetches the data via <User_TriggerTransmit> only when hardware is free ([SWS_CANIF_00885], SWS CanIf p. 145).
  • Dynamic Tx L-PDUs: They receive their CanId via CanIf_SetDynamicTxId() under consistency protection ([SWS_CANIF_00189], [SWS_CANIF_00673]) or from the MetaData ([SWS_CANIF_00854], [SWS_CANIF_00855]).
  • Excess length data: With CanIfTxPduTruncation, they are truncated [SWS_CANIF_00894]. Without truncation, the result is a runtime error with E_NOT_OK [SWS_CANIF_00900].

Receive path: software filter, data length check, and forwarding

Upon each reception, CanDrv calls CanIf_RxIndication(Mailbox, PduInfoPtr) ([SWS_CANIF_00006], SWS CanIf p. 48). CanIf checks the L-PDU in two stages:

  1. Software filter, if configured. If it rejects the L-PDU, processing ends [SWS_CANIF_00389]. The assignment to the L-SDU also takes into account the two most significant ID bits [SWS_CANIF_00877]. A single CanId has precedence over a range [SWS_CANIF_00852].
  2. Data length check [SWS_CANIF_00390]. Any length that is at least equal to the configured one is accepted [SWS_CANIF_00026]. Shorter L-PDUs lead to a runtime error CANIF_E_INVALID_DATA_LENGTH [SWS_CANIF_00168].

Accepted L-PDUs go to the configured <User_RxIndication>, together with the received length ([SWS_CANIF_00056], [SWS_CANIF_00135], [SWS_CANIF_00829]). For dynamic L-SDUs, CanIf stores the received CanId in MetaDataItem CAN_ID_32 [SWS_CANIF_00848]. Two query paths are optional:

  • A receive buffer from which CanIf_ReadRxPduData() reads ([SWS_CANIF_00199], [SWS_CANIF_00194]).
  • Notification status according to the “read and consume” principle: The status is set upon reception and reset upon reading ([SWS_CANIF_00392], [SWS_CANIF_00394], SWS CanIf p. 55).

In channel mode CANIF_OFFLINE, receive notifications are omitted [SWS_CANIF_00073].

Activity diagram: An L-PDU reaches the upper layer only if it passes the software filter and data length check. Sources: SWS CanIf p. 51, [SWS_CANIF_00389], [SWS_CANIF_00390], [SWS_CANIF_00168], [SWS_CANIF_00421]

Controller, PDU channel, and transceiver modes

CanIf_SetControllerMode() [SWS_CANIF_00003] operates asynchronously. It calls Can_SetControllerMode() [SWS_CANIF_00308]. CanDrv reports the actual transition later via CanIf_ControllerModeIndication(), and CanIf forwards it to CanSM ([SWS_CANIF_00699], [SWS_CANIF_00711]). If a transition fails, the upper layers must track this. They can query the mode via CanIf_GetControllerMode() (SWS CanIf p. 55, [SWS_CANIF_00229]).

Each channel has a PDU channel mode of type CanIf_PduModeType [SWS_CANIF_00137]. CanIf_SetPduMode() accepts requests only in CAN_CS_STARTED ([SWS_CANIF_00008], [SWS_CANIF_00874]). CanIf triggers some transitions itself: CAN_CS_SLEEP leads to CANIF_OFFLINE [SWS_CANIF_00865], STOPPED or BusOff to CANIF_TX_OFFLINE [SWS_CANIF_00866]. An R20-11 text excerpt describes CANIF_TX_OFFLINE_ACTIVE as “without listening” (SWS CanIf p. 58). However, [SWS_CANIF_00137] is authoritative, and according to it, the receive path remains active.

In Partial Networking, a PnTxFilter is superimposed on the channel modes for each controller ([SWS_CANIF_00747], [SWS_CANIF_00748]):

  • It is activated during initialization, upon CAN_CS_SLEEP, and upon CANIF_TX_OFFLINE ([SWS_CANIF_00863], [SWS_CANIF_00749], [SWS_CANIF_00878]).
  • Effect: It allows only the configured CanIfTxPduPnFilterPdus to pass [SWS_CANIF_00750].
  • It is deactivated by a transmit confirmation or a reception ([SWS_CANIF_00751], [SWS_CANIF_00896]).

For transceivers, CanIf passes calls through to CanTrcv and forwards its indications:

  • Set and read mode ([SWS_CANIF_00358], [SWS_CANIF_00363]),
  • Wake-up reason and wake-up mode ([SWS_CANIF_00368], [SWS_CANIF_00372]),
  • Mode change indication to CanSM [SWS_CANIF_00712],
  • PN flag services with feedback ([SWS_CANIF_00766], [SWS_CANIF_00757], [SWS_CANIF_00765], [SWS_CANIF_00753]).

SWS CanTrcv p. 57 shows how these services interact during shutdown.

Wake-up detection and validation

The integration code calls CanIf_CheckWakeup() [SWS_CANIF_00219]. CanIf then queries Can_CheckWakeup() and CanTrcv_CheckWakeup(), respectively [SWS_CANIF_00395]. If at least one driver reports E_OK, CanIf returns E_OK, otherwise E_NOT_OK ([SWS_CANIF_00720], [SWS_CANIF_00678]). The service is only available if wake-up support is configured ([SWS_CANIF_00180], SWS CanIf p. 56).

The following applies to validation:

  1. With CanIfPublicWakeupCheckValidSupport, CanIf stores the first valid CanIf_RxIndication() call of a started controller. Depending on the configuration, only NM messages count [SWS_CANIF_00286].
  2. CanIf_CheckValidation() reports this event via <User_ValidateWakeupEvent>(sources), typically EcuM_ValidateWakeupEvent ([SWS_CANIF_00179], [SWS_CANIF_00563]).
  3. Upon CAN_CS_SLEEP, the stored event is cleared [SWS_CANIF_00756].

As long as validation is ongoing, the channel must not be set to CANIF_ONLINE or CANIF_TX_OFFLINE. Otherwise, upper layers will already receive receive indications (SWS CanIf p. 60).

Sequence diagram: Detection and validation are separate calls; a received message on the switched-on controller is used for validation. Sources: SWS EcuM p. 181, [SWS_CANIF_00395], [SWS_CANIF_00720], [SWS_CANIF_00286], [SWS_CANIF_00179]

Behavior in the event of an error

BusOff. CanDrv reports a BusOff via CanIf_ControllerBusOff() [SWS_CANIF_00218]. CanIf responds as follows:

  • It calls CanSM_ControllerBusOff() [SWS_CANIF_00724].
  • It sets the channel to CANIF_TX_OFFLINE [SWS_CANIF_00866].
  • Upon entering STOPPED, it clears the transmit buffers [SWS_CANIF_00485].
  • For each pending confirmation, it calls <User_TxConfirmation>(id, E_NOT_OK) [SWS_CANIF_00739].
  • It additionally reports the security event CANIF_SEV_ERRORSTATE_BUSOFF [SWS_CANIF_00918].

CanSM controls the restart with CanIf_SetControllerMode(…STARTED) (SWS CanIf p. 160). The older error description still uses CANIF_CS_* for this (ErrorDescription p. 16); in R20-11, CAN_CS_* applies [SWS_CANIF_00003]. For recovery, CanIf also provides CanIf_GetTxConfirmationState() ([SWS_CANIF_00734], [SWS_CANIF_00738]).

Sequence diagram: The BusOff indication is followed by transmit disabling and buffer clearing; CanSM initiates the restart, and it is confirmed asynchronously. Sources: SWS CanIf p. 148, [SWS_CANIF_00218], [SWS_CANIF_00724], [SWS_CANIF_00866], [SWS_CANIF_00711]

DET errors. CanIf reports invalid parameters as development error CANIF_E_PARAM_* or CANIF_E_INVALID_* ([SWS_CANIF_00311], [SWS_CANIF_00319], [SWS_CANIF_00416], [SWS_CANIF_91006]). Runtime errors [SWS_CANIF_91007] are:

  • failed data length check [SWS_CANIF_00168],
  • transmission on an offline channel (CANIF_E_STOPPED) [SWS_CANIF_00382],
  • data length conflict during buffering [SWS_CANIF_00895].

Callbacks that arrive before initialization are ignored ([SWS_CANIF_00412], [SWS_CANIF_00421], [SWS_CANIF_00431]).

Security events. If reporting is activated [SWS_CANIF_00913], CanIf forwards two indications of the CanDrv as events to the IdsM [SWS_CANIF_91010]:

  • CanIf_ErrorNotification() as Tx or Rx error ([SWS_CANIF_00915], [SWS_CANIF_00916]),
  • CanIf_ControllerErrorStatePassive() as Error-Passive event [SWS_CANIF_00917].

See SWS CanDrv p. 50. Fault state and error counters can be queried ([SWS_CANIF_91001], [SWS_CANIF_91003], [SWS_CANIF_91004]).

CanIf_ConfigType type

This type defines a data structure for the post build parameters of the CAN interface for all underlying CAN drivers. At initialization the CanIf gets a pointer to a structure of this type to get access to its configuration data, which is necessary for initialization.
