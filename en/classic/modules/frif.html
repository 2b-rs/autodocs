Encapsulates FlexRay drivers and transceivers and controls state, PDU traffic, and job list execution per cluster.

The FlexRay Interface encapsulates FlexRay and transceiver drivers behind a uniform controller index and mediates PDUs between the upper layers and the bus. Per cluster, it maintains a state machine with the states FRIF_STATE_OFFLINE and FRIF_STATE_ONLINE, which the FlexRay State Manager switches via FrIf_SetState [SWS_FrIf_05174]. Transmission and reception take place time-controlled in the cluster's Job List Execution, and only in the online state (SWS FrIf p. 37). Start, halt, and wakeup services operate asynchronously. Therefore, the caller determines the reached POC state via FrIf_GetPOCStatus.

The FlexRay Interface (FrIf) is located between the upper communication modules and the drivers Fr and FrTrcv. For its core functionality, it requires driver services such as Fr_ControllerInit, Fr_GetPOCStatus, and Fr_ReceiveRxLPdu [SWS_FrIf_05043]. Most control services encapsulate a driver service: Based on the static configuration, they translate FrIf_CtrlIdx into the tuple (FlexRay Driver | Fr_CtrlIdx) and return the driver's result (SWS FrIf p. 55). Start, halt, coldstart enable, and wakeup operate asynchronously [SWS_FrIf_05005]. Therefore, the caller determines the state actually reached using FrIf_GetPOCStatus.

Per cluster, the FrIf maintains a state machine with the states FRIF_STATE_OFFLINE and FRIF_STATE_ONLINE [SWS_FrIf_05755]. FrIf_Init() sets each cluster to offline. The environment requests transitions with FrIf_SetState and FRIF_GOTO_ONLINE or FRIF_GOTO_OFFLINE [SWS_FrIf_05174]. Reception, transmission, and transmit confirmation run only online. When transitioning to offline, the upper layers receive E_NOT_OK for pending confirmations [SWS_FrIf_05501].

State diagram: Each cluster starts offline and switches only upon request via FrIf_SetState. Sources: [SWS_FrIf_05303], SWS FrIf p. 25

The FrSM controls the sequence. During startup, it switches the transceivers to normal, starts communication, and enables coldstart if applicable. Then it queries the POC status until FR_POCSTATE_NORMAL_ACTIVE is reached, and only then sets the cluster online (SWS FrSM p. 50). Shutdown proceeds in two stages: first offline and halt, then reinitialization of the controllers and transceiver standby (SWS FrSM p. 58).

FrIf_Transmit initially only counts transmit requests [SWS_FrIf_05033]. The actual transmission takes place in the Job List Execution per cluster [SWS_FrIf_05040]. There, the FrIf fetches the data via TriggerTransmit, confirms transmissions, and reports receptions. It reports errors in three categories: development errors to DET [SWS_FrIf_05145], the runtime error FRIF_E_JLE_SYNC [SWS_FrIf_05432], and channel-wise production errors to DEM [SWS_FrIf_05146].

Role in the FlexRay stack and system boundary

The FlexRay Interface (FrIf) is located between the upper communication modules and the hardware-oriented drivers. For its core functionality, it requires services of the FlexRay driver. These include Fr_ControllerInit, Fr_GetPOCStatus, Fr_ReceiveRxLPdu, and Fr_CheckTxLPduStatus, as well as Det_ReportRuntimeError [SWS_FrIf_05043]. Optional services include Fr_AllSlots, Fr_CancelTxLPdu, and Dem_SetEventStatus [SWS_FrIf_05044]. The header structure shows the integration of Fr.h, FrTrcv.h, PduR_FrIf.h, FrNm_Cbk.h, and FrTp_Cbk.h (SWS FrIf p. 18).

The FlexRay State Manager controls the lifecycle. It maps its functional elements to FrIf calls (SWS FrSM p. 22). PDU users are connected via configurable callbacks: <User_RxIndication>, <User_TxConfirmation>, and <User_TriggerTransmit> [SWS_FrIf_05045] [SWS_FrIf_05046] [SWS_FrIf_05047]. Permissible targets include FrTSyn [SWS_FrIf_05434], FrNm, and FrArTp. Complex Drivers with similar interfaces can also be connected (SWS FrIf p. 97). Other users have their own tasks:

  • FrTSyn reads time and status information (SWS FrTSyn p. 13).
  • The EcuM checks transceiver wakeups (SWS EcuM p. 186).
  • Bus Mirroring switches frame mirroring (SWS Mirror p. 31).

One Controller Index for All Drivers: The Wrapper Principle

Most control services address a Communication Controller (CC) via FrIf_CtrlIdx. The pattern can be shown using the example of FrIf_ControllerInit. Based on the static configuration, the service translates the index into the tuple (FlexRay Driver | Fr_CtrlIdx). It then calls Fr_ControllerInit() of the determined driver (SWS FrIf p. 55). The return value reflects the driver result [SWS_FrIf_05004]. Following the same pattern, other services encapsulate their driver counterparts: start, halt, abort, coldstart enable, wakeup, POC status, and global time [SWS_FrIf_05005] [SWS_FrIf_05006] [SWS_FrIf_05007] [SWS_FrIf_05017] [SWS_FrIf_05011] [SWS_FrIf_05014] [SWS_FrIf_05015]. The same applies to the absolute timer services [SWS_FrIf_05021] [SWS_FrIf_05025] [SWS_FrIf_05029].

For callers, synchronicity is crucial. FrIf_StartCommunication, FrIf_HaltCommunication, FrIf_AllowColdstart, and FrIf_SendWUP operate asynchronously [SWS_FrIf_05005] [SWS_FrIf_05011]. In contrast, FrIf_ControllerInit and FrIf_AbortCommunication operate synchronously [SWS_FrIf_05007]. For the asynchronous services, E_OK merely means that the driver call returned E_OK. The FrSM determines the POC state actually reached through repeated polling with FrIf_GetPOCStatus (SWS FrSM p. 50).

Transceiver services additionally address a channel FrIf_ChnlIdx and encapsulate the FlexRay Transceiver Driver [SWS_FrIf_05034] [SWS_FrIf_05036] [SWS_FrIf_05039]. The value FR_CHANNEL_AB is invalid in this context (SWS FrIf p. 73). Queries such as FrIf_GetMacroticksPerCycle or FrIf_GetCycleLength do not call a driver, but read the static configuration [SWS_FrIf_05018] [SWS_FrIf_05239].

State Machine per Cluster: FRIF_STATE_OFFLINE and FRIF_STATE_ONLINE

The FrIf maintains a dedicated state machine for each FlexRay cluster. FrIf_Init() initially sets each cluster to FRIF_STATE_OFFLINE (SWS FrIf p. 25). The two states have the following meaning [SWS_FrIf_05755]:

  • FRIF_STATE_OFFLINE: The CC is not ready to communicate, the cluster is not synchronized.
  • FRIF_STATE_ONLINE: The CC is ready to communicate, the cluster is synchronized.

The environment requests transitions using FrIf_SetState, specifically with the literals FRIF_GOTO_ONLINE or FRIF_GOTO_OFFLINE [SWS_FrIf_05174] [SWS_FrIf_05303]. A transition takes place only if the cluster is in the respective other state (SWS FrIf p. 25). FrIf_GetState is reentrant [SWS_FrIf_05170], whereas FrIf_SetState is not.

The state determines whether data traffic occurs. When offline, the FrIf executes no communication services. When online, it executes reception, transmission, and transmit confirmation (SWS FrIf p. 25). Upon transitioning to offline, the FrIf checks every PDU: If its TxConfCounter > 0, the upper layer receives <UL>_TxConfirmation(id, E_NOT_OK) [SWS_FrIf_05501]. Starting with R23-11, the specification additionally requires that FrIf_Transmit() returns E_NOT_OK in the offline state (SWS FrIf p. 68). An older diagram shows four states, including FRIF_STATE_HALT (SWS FrIf p. 28). It does not apply to R20-11, because FrIf_StateType recognizes only two values here [SWS_FrIf_05755].

State diagram: Each cluster starts offline and switches only upon request via FrIf_SetState. Upon transitioning to offline, pending transmit confirmations are concluded negatively. Sources: [SWS_FrIf_05174], [SWS_FrIf_05303], [SWS_FrIf_05501], SWS FrIf p. 25

Startup, Wakeup, and Shutdown Controlled by the FrSM

The EcuM initializes the FrIf with FrIf_Init, specifically before FrSM_Init (SWS FrSM p. 46). In doing so, it passes a pointer to FrIf_ConfigType [SWS_FrIf_05003]. The FrSM controls all further steps via its functional elements. Each element calls the associated FrIf service for each controller of the cluster (SWS FrSM p. 22):

  • FE_CONFIG calls FrIf_ControllerInit.
  • FE_START calls FrIf_StartCommunication.
  • FE_ALLOW_COLDSTART calls FrIf_AllowColdstart, but only if FrSMIsColdstartEcu is set.
  • FE_WAKEUP calls FrIf_SendWUP.
  • FE_HALT calls FrIf_HaltCommunication.

Passive startup following a bus wakeup proceeds in this order (SWS FrSM p. 50):

  1. The transceivers are switched to FRTRCV_TRCVMODE_NORMAL.
  2. Communication is started.
  3. A coldstart node additionally enables coldstart.
  4. The FrSM polls the POC status until FR_POCSTATE_NORMAL_ACTIVE is reached.
  5. Only then does FrIf_SetState(…, FRIF_GOTO_ONLINE) follow.

During active wakeup, dual-channel nodes select the wakeup channel using FrIf_SetWakeupChannel [SWS_FrIf_05010]. FrIf_GetWakeupRxStatus reports in bit-coded format on which channel a wakeup was received [SWS_FrIf_05102].

Sequence diagram: Passive startup up to the online state. The FrIf executes only the individual services; control flow logic resides with the FrSM. Interpretation: The sequence prior to start is simplified. Sources: SWS FrSM p. 50, SWS FrSM p. 21

Shutdown proceeds in two stages. First, the FrSM sets the cluster offline with FRIF_GOTO_OFFLINE and calls FrIf_HaltCommunication. Later, it reinitializes the controllers and sets the transceivers to mode STANDBY (SWS FrSM p. 58). The delay between both stages is determined by the timer t_TrcvStdbyDelay (SWS FrSM p. 21).

Sequence diagram: Transition from FullCom to NoCom, first halt, then reinitialization and standby. Interpretation: The sequence within the first phase is simplified. Sources: SWS FrSM p. 58, SWS FrSM p. 56

PDU Traffic: Transmit Request and Job List Execution

FrIf_Transmit is synchronous and reentrant for different TxPduId [SWS_FrIf_05033]. With decoupled buffer access, the FrIf stores only the number of transmit requests in TrigTxCounter, not the data itself (SWS FrIf p. 38). For immediate PDUs with fixed length, the FrIf checks the passed length against the configuration [SWS_FrIf_05757]. An ongoing transmission can be aborted with FrIf_CancelTransmit [SWS_FrIf_05070].

The actual bus communication takes place in the Job List Execution Function FrIf_JobListExec_<FrIfCluster.ShortName>, which exists per cluster [SWS_FrIf_05040]. In the diagrams, an Interrupt Service Routine invokes it (SWS FrIf p. 102). This routine is presumably triggered via the Absolute Timers of the CC [SWS_FrIf_05021]. The cyclic FrIf_MainFunction_<FrIfCluster.ShortName> [SWS_FrIf_05042] monitors the continuous execution of the job list as long as the cluster is online. This also includes the (re-)synchronization (SWS FrIf p. 26).

Each communication operation is executed only in the FRIF_STATE_ONLINE state, otherwise ignored (SWS FrIf p. 37). The most important operations work as follows:

  • Decoupled transmission: For each PDU with TrigTxCounter > 0, FrIf fetches the data via <User_TriggerTransmit> [SWS_FrIf_05047]. It then passes the frame to Fr_TransmitTxLPdu(). If the driver rejects it, FrIf resets the counters to their previous state (SWS FrIf p. 102).
  • TX_CONFIRMATION: If the driver reports FR_TRANSMITTED, FrIf confirms the transmission via <User_TxConfirmation> [SWS_FrIf_05046].
  • RECEIVE_AND_INDICATE: FrIf reads up to FrIfRxComOpMaxLoop times and reports each reception via <User_RxIndication> [SWS_FrIf_05045] (SWS FrIf p. 41).

Hardware-specific operations such as <Free_Op_A> also run in the job list [SWS_FrIf_05316]. FrIf reports transmission conflicts via <UL_TxConflictNotification> [SWS_FrIf_91001].

Time Base, Additional Services, and Configuration

FrTSyn invokes FrIf_GetGlobalTime only when FrIf_GetState returns the value FRIF_STATE_ONLINE. Only then is the CC synchronous with the global FlexRay time (SWS FrTSyn p. 19). FrIf_GetGlobalTime may also be called within an exclusive area (SWS FrIf p. 64). FrNm also determines the current cycle via this service (SWS FrNm p. 38). FrIf_GetNmVector [SWS_FrIf_05016] can be disabled via FrIfGetNmVectorSupport.

FrIf_EnableBusMirroring specifies per cluster whether Mirror_ReportFlexRayFrame is called for each transmitted or received frame. If FrIfBusMirroringSupport is disabled globally, the service returns E_NOT_OK [SWS_FrIf_05726]. The post-build configuration is implementation-specific and accessible only via pointers to FrIf_ConfigType [SWS_FrIf_05301]. A diagram from R22-11 onward shows the structure: There are one or more FrIfController with FrIfCtrlIdx 0…31, each with up to two transceivers (SWS FrIf p. 139). Optional services such as FrIf_DisableLPdu [SWS_FrIf_05710] are enabled via pre-compile switches, here via FrIfDisableLPduSupport (SWS FrIf p. 84).

Behavior in the event of an error

If FrIfDevErrorDetect is set to ON, the services report development errors to Det_ReportError. The codes range from FRIF_E_PARAM_POINTER (0x01) to FRIF_E_INV_FRIF_STATE (0x0A) and include, among others, FRIF_E_INV_CTRL_IDX and FRIF_E_UNINIT [SWS_FrIf_05145]. The most important cases:

  • Invalid FrIf_CtrlIdx: The wrappers report FRIF_E_INV_CTRL_IDX and return E_NOT_OK (SWS FrIf p. 55).
  • Invalid transition in FrIf_SetState: The service reports FRIF_E_INV_FRIF_STATE [SWS_FrIf_05037].
  • Incorrect length of an immediate PDU: FrIf_Transmit() returns E_NOT_OK and reports FRIF_E_INV_PDULENGTH [SWS_FrIf_05757].

Activity diagram: Sequence of a wrapper service from parameter check through index translation to returning the driver result. Sources: [SWS_FrIf_05004], [SWS_FrIf_05145], SWS FrIf p. 55

The specification defines FRIF_E_JLE_SYNC as a runtime error. It occurs when job list execution loses synchronization with the FlexRay time [SWS_FrIf_05432]. Interpretation: Resumption is likely the responsibility of the (re-)synchronization by the Main Function (SWS FrIf p. 26).

FrIf reports production errors channel by channel to the DEM: FRIF_E_NIT_CH_A/B, FRIF_E_SW_CH_A/B, and FRIF_E_ACS_CH_A/B [SWS_FrIf_05146]. The report is DEM_EVENT_STATUS_PREFAILED as soon as error bits such as vSS!SyntaxError are set [SWS_FrIf_05426] [SWS_FrIf_05428]. In contrast, FrSM reports the result of the cluster startup (SWS FrSM p. 50).

The function FrIf_Init serves to initialize the FlexRay Interface module ([SWS_FrIf_05003]). The call is synchronous and specified as non-reentrant (Non Reentrant) ([SWS_FrIf_05003]).

Parameters and Return Values

  • FrIf_ConfigPtr (input parameter): Base pointer to the configuration structure of the FlexRay Interface ([SWS_FrIf_05003]).
  • Return value: void – the function does not return a return value ([SWS_FrIf_05003]).

Constraints and Call Conditions

Since FrIf_Init is non-reentrant, the function must not be called again concurrently or preemptively by the same or another thread or task at any time ([SWS_FrIf_05003]). The call must take place in the system initialization context before regular services of the FlexRay Interface are used.
