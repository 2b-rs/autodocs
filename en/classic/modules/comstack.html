Role of ComStack_Types: the common type vocabulary of the communication stack

The "comstack" module is not an executing component. Via ComStack_Types.h, it provides the data types with which the modules of the Classic communication stack describe PDUs, buffers, and channels. According to the specification, all nine types of the release are "Available via ComStack_Types.h", from PduInfoType to NetworkHandleType ([SWS_COMTYPE_00011], [SWS_COMTYPE_00038]). PduLengthType shall be used throughout the entire AUTOSAR Com stack of an ECU, except for the bus drivers ([SWS_COMTYPE_00008], SWS ComStackTypes p. 16). This defines the system boundary: Above the bus drivers, interfaces, routers, transport protocols, and upper layers use the same types. For large data callbacks, the RTE also imports BufReq_ReturnType, PduIdType, PduInfoType, PduLengthType, and RetryInfoType from ComStack_Types.h, among others (SWS RTE p. 833).

Regarding the source material: The cited document sections originate predominantly from releases R23-11 to R25-11. Only the retry diagram of the J1939Tp specification is also verified for R20-11. The requirements are normative for R20-11. Deviations are stated in the text, for example for PNCHandleType ([SWS_COMTYPE_00036], SWS ComStackTypes p. 17).

Context diagram: ComStack_Types.h provides all stack modules above the bus drivers with common types; the range limits originate from the EcuC configuration. Sources: [SWS_COMTYPE_00005], [SWS_COMTYPE_00008], [SWS_COMTYPE_00038], TPS EcuC p. 205, SWS RTE p. 833

PDU identity: PduIdType and module-local handle IDs

PduIdType is variable in R20-11 as uint16 or uint8. The size depends on the highest number of PDUs used by an individual software module. The generator produces the range limit from the EcuC configuration in ComStack_Cfg.h ([SWS_COMTYPE_00005]). In the EcuC, this corresponds to parameter PduIdTypeEnum with the values UINT8 and UINT16. If at least one module manages more than 256 PDUs, uint16 is required (ECUConfiguration p. 153).

A PduIdType value is not a system-wide key. It is a handle within the respective called module: Each BSW module with a PDU API maintains its own list of PDU IDs as a lookup table (SWS PduR p. 33). The PDU Router identifies a routing path via the source ID and the destination IDs. It translates the ID in the transmit path and in the confirmation path, passing the PduInfoType value through unchanged (SWS PduR p. 33). So that neighboring modules refer to the same PDU, the EcuC defines a cross-module EcucPduCollection with global Pdu objects (TPS EcuC p. 190).

Sequence diagram: The PduR translates the PduIdType values for each target module, passes PduInfoType through unchanged, and forwards the confirmation with the reset ID to Com. Sources: SWS PduR p. 33, SWS PduR p. 33, [SWS_COMTYPE_00005]

PDU content: PduInfoType, PduLengthType, and metadata

PduInfoType aggregates the basic information of a PDU of any type. SduDataPtr points to the payload, MetaDataPtr to the metadata, and SduLength indicates the length in bytes ([SWS_COMTYPE_00011], SWS ComStackTypes p. 17). The length has the type PduLengthType. Depending on the maximum PDU length of the ECU, it is generated as uint8, uint16, or uint32. Without segmentation, the bus frame size determines the width, with a maximum of 255 bytes for FlexRay and thus uint8. With segmentation, the maximum length of a segmented N-PDU determines the width ([SWS_COMTYPE_00008], SWS ComStackTypes p. 16).

Metadata are, for example, CAN ID, socket ID, or diagnostic addresses. They consist of a sequence of elements statically configured per PDU. Elements with more than 8 bits are in platform byte order ([SWS_COMTYPE_00011]). The order and position of the elements result from the EcuC configuration of the global PDU. Sorting by length makes padding unnecessary (SWS BSWGeneral p. 67). An application example: In a socket connection group, the SoAd transmits only on the connection specified by PduInfoType.MetaDataPtr (SWS SoAd p. 30).

An operational rule applies to the lifetime of the pointers: For a receive indication, the passed data pointer is valid only until the indication returns (SWS CanNm p. 73). A length of 0 has several special meanings. A CopyRxData call with SduLength 0 queries the upper layer's available receive buffer; SduDataPtr may then be NULL_PTR (SWS DoIP p. 77). During transmission, SduLength 0 indicates an I-PDU of unknown length. The PduR forwards this length to all target TP modules (SWS PduR p. 43).

Buffer handshake during TP reception: BufReq_ReturnType

BufReq_ReturnType stores the result of a buffer request. The values are fixed: BUFREQ_OK (0), BUFREQ_E_NOT_OK (1), BUFREQ_E_BUSY (2), and BUFREQ_E_OVFL (3). In the case of BUFREQ_E_BUSY, the requester must retry the request for a certain period of time ([SWS_COMTYPE_00012], SWS ComStackTypes p. 19).

TP reception proceeds in three steps:

  1. The transport protocol reports the total length TpSduLength and the data of the first frame using PduR_<User:LoTp>StartOfReception. Via bufferSizePtr, it receives back the available buffer and calculates the block size from it.
  2. It forwards the segments via CopyRxData.
  3. It completes the reception with RxIndication (SWS PduR p. 92).

BUFREQ_OK here means "connection accepted", even if 0 is reported as the buffer size (SWS PduR p. 92). The FlexRay AR TP does not hold message buffers itself. It exchanges the data piecewise with the upper layer (SWS FrArTp p. 50).

Sequence diagram: TP reception begins with StartOfReception, delivers the data via CopyRxData, and ends with RxIndication; if the start of a single frame is rejected, no RxIndication follows. Sources: SWS FrArTp p. 50, SWS FrArTp p. 50, SWS PduR p. 92, [SWS_COMTYPE_00012]

Transmission with retry: RetryInfoType and TpDataStateType

During piecewise transmission, the transport protocol passes a RetryInfoType with CopyTxData. It consists of TpDataState and TxTpDataCnt; the latter is the offset of the bytes to be retransmitted ([SWS_COMTYPE_00037], SWS ComStackTypes p. 20). The three states mean ([SWS_COMTYPE_00027], SWS ComStackTypes p. 19):

  • TP_DATACONF: All data copied so far are confirmed and may be removed from the TP buffer.
  • TP_DATARETRY: Data already copied must be provided again starting from offset TxTpDataCnt.
  • TP_CONFPENDING: The previously copied data must be preserved.

The retry diagram of the SAE J1939 TP specification illustrates this interaction. For each block, the first packet is requested with TP_DATACONF, the subsequent ones with TP_CONFPENDING. If a TP.DT is lost, the TP jumps back to the first packet of the block. It then requests again with TP_DATARETRY; TxTpDataCnt is the offset to the beginning of the block (SWS J1939Tp p. 55). The FrArTp also sets TP_CONFPENDING during unsegmented transmission with retry enabled (SWS FrArTp p. 50).

Sequence diagram: For each block, TpDataState controls whether the data is confirmed, retained, or copied again from the beginning of the block. Sources: SWS J1939Tp p. 55, [SWS_COMTYPE_00027], [SWS_COMTYPE_00037]

The direct TP gateway of the PduR for single frames illustrates how an upper layer responds to the state. For TP_DATACONF, TP_CONFPENDING, or a missing RetryInfoType pointer, it copies SduLength bytes. For TP_DATARETRY, it previously resets the position by TxTpDataCnt bytes (SWS PduR p. 57). Not every upper layer evaluates the retry information: In the case of LdCom callbacks, retry is not handled by LdCom and its upper layer according to the specification (SWS LdCom p. 34). Since AUTOSAR 4.3.1, the parameter in PduR_<User:LoTp>CopyTxData is a pointer to const RetryInfoType (SWS PduR p. 3).

Activity diagram: The PduR decides based on TpDataState whether to copy directly, reset the position, or reject the request. Sources: SWS PduR p. 57, [SWS_COMTYPE_00027], [SWS_COMTYPE_00012]

Channels, partial networks, and changeable TP parameters

NetworkHandleType stores the identifier of a communication channel. It is a zero-based uint8 with a value range of 0..255 ([SWS_COMTYPE_00038], SWS ComStackTypes p. 20). In Mirror_GetNetworkId, it represents the ComM channel, in CanSM_TxTimeoutException, the affected CAN network (SWS Mirror p. 78, SWS CanSM p. 87). Network management callbacks such as Nm_RemoteSleepIndication also identify the NM channel via this type (SWS Nm p. 89).

PNCHandleType stores the identifier of a partial network cluster. In R20-11, it is derived from uint8 ([SWS_COMTYPE_00036]). The present document section from R23-11, on the other hand, names uint16 as the base type (SWS ComStackTypes p. 17). For R20-11, requirement status uint8 applies.

TPParameterType identifies the parameter to be changed at runtime. The values are TP_STMIN (Separation Time), TP_BS (Block Size), and TP_BC (bandwidth control of the FlexRay Transport Protocol) ([SWS_COMTYPE_00031], SWS ComStackTypes p. 18). The modules restrict its use. J1939Tp_ChangeParameter only accepts TP_BS with values up to 255 (SWS J1939Tp p. 42). The FrArTp rejects changes during ongoing reception with E_NOT_OK (SWS FrArTp p. 49).

Behavior in the event of an error

The types themselves have no error behavior. However, they transport the results according to which the modules react ([SWS_COMTYPE_00012]). For unsegmented FrArTp transmission, the following applies:

  • If PduR_FrArTpCopyTxData returns BUFREQ_E_BUSY, the TP repeats the call until FrArTpTimeCs expires.
  • In case of BUFREQ_E_NOT_OK or after the time has expired, it aborts and calls PduR_FrArTpTxConfirmation with E_NOT_OK.
  • If PduR_FrArTpStartOfReception returns BUFREQ_E_NOT_OK or BUFREQ_E_OVFL for a single frame, reception terminates immediately, without PduR_FrArTpRxIndication (SWS FrArTp p. 50).

Activity diagram: BUFREQ_E_BUSY leads to a retry until timeout; BUFREQ_E_NOT_OK and BUFREQ_E_OVFL lead to termination. Sources: SWS FrArTp p. 50, SWS FrArTp p. 44, [SWS_COMTYPE_00012]

In the direct TP gateway, two rules apply to TP_DATARETRY. If the PduR cannot reset the position, it responds with BUFREQ_E_NOT_OK and leaves the position and data unchanged. If data is missing after resetting, it responds with BUFREQ_E_BUSY (SWS PduR p. 57). In the on-the-fly gateway, the PduR does not support retransmission of data already sent (SWS PduR p. 58). For multicast TP routing, it returns E_NOT_OK on TP_DATARETRY according to the document section (SWS PduR p. 41).

In addition, the PduR does not take any error measures of its own. It forwards errors from return values to the upper source module responsible for handling (SWS PduR p. 46, SWS PduR p. 49).
