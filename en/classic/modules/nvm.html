Manages non-volatile data blocks and synchronizes them asynchronously between RAM and NV memory.

The NVRAM Manager (NvM) is the single point of access to non-volatile memory. It copies NVRAM blocks implicitly between RAM and NV memory [SWS_NvM_00038]. At startup, NvM_ReadAll triggered by the BswM fills the RAM blocks; during shutdown, NvM_WriteAll saves modified blocks. Single requests such as NvM_WriteBlock are queued asynchronously, processed according to priority, and acknowledged via status or callback [SWS_NvM_00185]. The NvM handles read errors using retries, redundant copies, and default data; users must still check the block status themselves.

The NVRAM Manager (NvM) is the single point of access to non-volatile memory [SWS_NvM_00384]. It copies blocks implicitly between NVRAM and RAM; the application works directly with the RAM data [SWS_NvM_00038]. Toward lower layers, it uses the Memory Abstraction Interface with Fee or Ea [SWS_NvM_00051]. It reports states to the BswM, and errors to DEM and DET [SWS_NvM_00745] [SWS_NvM_00592].

Context diagram: Integration of the NvM between users, BswM, MemIf/Fee/Ea, as well as DEM and DET. Sources: [SWS_NvM_00384] [SWS_NvM_00465] [SWS_NvM_00746]

Each NVRAM block consists of an NV block, a RAM block, and an Administrative Block, optionally supplemented by a ROM block containing default data [SWS_NvM_00138]. The types Native, Redundant, and Dataset exist; they differ in the number of NV and ROM blocks [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559]. The NvM synchronizes the RAM block implicitly directly or explicitly via a RAM mirror with callbacks [SWS_NvM_00511].

The lifecycle proceeds in three steps:

  • The BswM calls NvM_Init exclusively [SWS_NvM_00693].
  • NvM_ReadAll first checks the configuration ID and then fills the RAM blocks [SWS_NvM_00073] [SWS_NvM_00718].
  • At shutdown, NvM_WriteAll saves modified blocks [SWS_NvM_00092]. NvM_CancelWriteAll aborts non-destructively [SWS_NvM_00238].

Single requests such as NvM_WriteBlock are queued and then set to NVM_REQ_PENDING [SWS_NvM_00185]. Optionally, the NvM uses a dedicated queue for immediate requests [SWS_NvM_00378]. The result is provided by NvM_GetErrorStatus or a configured callback [SWS_NvM_00015] [SWS_NvM_00740].

Sequence diagram: An asynchronous write request is queued, processed in NvM_MainFunction, and acknowledged via callback, BswM notification, and status query. Sources: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00891], SWS NvM p. 160

The NvM handles read errors via three stages:

  • configured read retries [SWS_NvM_00526],
  • the second copy of redundant blocks [SWS_NvM_00199],
  • default data with the result NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202].

Interpretation: The order of stages likely follows the enumeration in the Error Description. The NvM retries write errors up to NVM_MAX_NUM_OF_WRITE_RETRIES and then reports NVM_E_REQ_FAILED to the DEM [SWS_NvM_00684]. Users check the status of their blocks themselves [SWS_NvM_00694].

Role in the memory stack: single point of access to non-volatile memory

The NVRAM Manager (NvM) consolidates access to non-volatile data. The environment accesses the non-volatile memory exclusively via the NvM, which provides a callback interface for this purpose [SWS_NvM_00384]. Access is implicit: the NvM copies blocks between NVRAM and shared RAM. Observing synchronization rules, the application works directly with the RAM data [SWS_NvM_00038] [SWS_NvM_00692]. A block is selected via its configured block ID [SWS_NvM_00069] [SWS_NvM_00471]. Upper layers include only NvM.h for this purpose [SWS_NvM_00691]. The diagram for implicit updating shows the division of work: other parts of the basic software trigger the saving and restoring of all blocks depending on the ECU state. The SW-C only accesses the contents of its RAM blocks (SWS NvM p. 121).

Toward lower layers, the NvM works against the Memory Abstraction Interface. Together with Fee or Ea, it provides a virtual linear 32-bit address space [SWS_NvM_00051] [SWS_NvM_00465]. The NvM calculates checksums via the Crc module [SWS_NvM_00466]. It learns of the completion of a lower-layer job in two ways:

  • via polling using MemIf_GetJobResult,
  • with polling disabled, via NvM_JobEndNotification and NvM_JobErrorNotification [SWS_NvM_00440] [SWS_NvM_00441] (Error Description p. 43).

Production errors are sent to the DEM [SWS_NvM_00592], development errors to the DET [SWS_NvM_00614]. The NvM reports job states to the BswM [SWS_NvM_00745] [SWS_NvM_00746].

Structure of an NVRAM block and the three management types

An NVRAM block consists of the mandatory components NV block, RAM block, and Administrative Block. A ROM block with default data is optional [SWS_NvM_00138] [SWS_NvM_00139] [SWS_NvM_00020]. The composition is defined at configuration time by the block descriptor [SWS_NvM_00140]. The individual components:

  • The NV block carries the payload data as well as optionally CRC and header [SWS_NvM_00125] (SWS NvM p. 39).
  • The RAM block may reside in global RAM without address restrictions [SWS_NvM_00088].
  • The Administrative Block is invisible to the application. It holds the dataset index, the attributes, and the error/status field [SWS_NvM_00134] [SWS_NvM_00135] [SWS_NvM_00136].

The NvM supports the types NVM_BLOCK_NATIVE, NVM_BLOCK_REDUNDANT, and NVM_BLOCK_DATASET [SWS_NvM_00137]. They differ in the number of NV and ROM blocks [SWS_NvM_00557] [SWS_NvM_00558] [SWS_NvM_00559] (SWS NvM p. 10). For dataset blocks:

  • NvM_SetDataIndex selects the element. Indices starting at NvMNvBlockNum address ROM blocks [SWS_NvM_00014] [SWS_NvM_00445] (NV Data Handling p. 10).
  • The index is not stored persistently; NvM_Init sets it to zero [SWS_NvM_00160] [SWS_NvM_00192].
  • The SW-C is responsible for setting it correctly [SWS_NvM_00695].

Lifecycle: NvM_Init, NvM_ReadAll, and NvM_WriteAll

The BswM calls NvM_Init exclusively [SWS_NvM_00693]. NvM_Init resets queues and state machines and internally signals \"INIT DONE\" [SWS_NvM_00399]. It initializes neither RAM blocks nor underlying modules [SWS_NvM_00091] [SWS_NvM_00193]. The configuration pointer is always NULL_PTR [SWS_NvM_00881]. Only after that does NvM_MainFunction process requests [SWS_NvM_00257].

The RAM blocks are subsequently filled by NvM_ReadAll [SWS_NvM_00718]. The call only signals the request. Processing is deferred until the single-block requests are completed [SWS_NvM_00243]. After that, the job runs in three steps:

  1. First, it compares the stored configuration ID with the compiled configuration ID [SWS_NvM_00073]. In case of a mismatch, the behavior depends on NvMDynamicConfiguration: with NvMDynamicConfiguration == FALSE, the mismatch is ignored [SWS_NvM_00248]. Otherwise, blocks that are not resistant to change receive default data [SWS_NvM_00249] [SWS_NvM_00674] (NV Data Handling p. 15).
  2. Then it iterates over the user blocks, excluding block IDs 0 and 1 [SWS_NvM_00244]. In doing so, it only processes blocks with a permanent RAM block or explicit synchronization [SWS_NvM_00118].
  3. Finally, it sets the overall result to NVM_REQ_OK or NVM_REQ_NOT_OK [SWS_NvM_00895] [SWS_NvM_00301].

In the mode management example, the BswM rule NvMReadAllFinished starts the remaining initialization only after completion of NvM_ReadAll (Mode Management Guide p. 31).

Sequence diagram: Asynchronous startup with NvM_Init, NvM_ReadAll, and notification of the multi-block state to the BswM. Sources: [SWS_NvM_00693] [SWS_NvM_00243] [SWS_NvM_00073] [SWS_NvM_00888] [SWS_NvM_00889], NV Data Handling p. 20

At shutdown, the BswM calls NvM_WriteAll [SWS_NvM_00092]. The job behaves as follows:

  • It writes permanent RAM blocks or retrieves explicitly synchronized data via NvM_WriteRamBlockToNvm [SWS_NvM_00252].
  • Prior to this, it checks the \"valid/modified\" state [SWS_NvM_00682].
  • It skips protected and locked blocks without an error notification [SWS_NvM_00434] [SWS_NvM_00750].
  • Other requests do not interrupt it [SWS_NvM_00567].

Users mark modified blocks with NvM_SetRamBlockStatus(…, TRUE), provided the API is enabled [SWS_NvM_00406] [SWS_NvM_00408]. For dirty-flag blocks, the RTE takes over this call (NV Data Handling p. 41).

NvM_CancelWriteAll is reserved for the BswM [SWS_NvM_00703] and remains without effect if NvM_WriteAll is not running [SWS_NvM_00233]. The current block is terminated non-destructively [SWS_NvM_00238]. The remaining blocks and the multi-block result receive NVM_REQ_CANCELED [SWS_NvM_00236] [SWS_NvM_00237] (SWS NvM p. 161).

Two additional multi-block requests supplement the lifecycle:

  • NvM_ValidateAll sets blocks with automatic validation to \"VALID / CHANGED\" [SWS_NvM_00856].
  • NvM_FirstInitAll writes default data to blocks or invalidates them if none are available [SWS_NvM_00913] [SWS_NvM_00919].

A queue length of one applies to all multi-block requests [SWS_NvM_00380].

Sequence diagram: Shutdown with NvM_WriteAll and optional cancellation by NvM_CancelWriteAll. Sources: [SWS_NvM_00092] [SWS_NvM_00682] [SWS_NvM_00238] [SWS_NvM_00237] [SWS_NvM_00889], Mode Management Guide p. 37

Single requests: queues, priorities, and feedback

Single-block requests such as NvM_ReadBlock, NvM_WriteBlock, or NvM_RestoreBlockDefaults are asynchronous. The function accepts the parameters, queues the request, and returns [SWS_NvM_00195] [SWS_NvM_00208] [SWS_NvM_00224]. Afterward, the block result is set to NVM_REQ_PENDING [SWS_NvM_00185]. In case of a queue overflow, the function returns E_NOT_OK [SWS_NvM_00184]. A block is only queued if it is not already pending or being processed [SWS_NvM_00385].

Other services act synchronously in the caller's context, such as NvM_SetDataIndex [SWS_NvM_00448] and NvM_GetErrorStatus (SWS NvM p. 158). NvM_CancelJobs removes pending requests of a block; however, a running job is continued [SWS_NvM_00536] [SWS_NvM_00537].

Processing takes place serialized according to priority [SWS_NvM_00162]. If NvMJobPrioritization is active, the NvM uses two queues, one of them for immediate write requests (crash data) [SWS_NvM_00564] [SWS_NvM_00378]. Such an NvM_WriteBlock destructively aborts a pending job [SWS_NvM_00300]. NvM_MainFunction then restarts the aborted job [SWS_NvM_00258]. Without prioritization, the NvM works in order of arrival, without immediate jobs [SWS_NvM_00379]. Requests received during a multi-block request are queued and executed subsequently [SWS_NvM_00568] [SWS_NvM_00569].

Each asynchronous request stores its result in the error/status field [SWS_NvM_00175]. NvM_GetErrorStatus reads this field [SWS_NvM_00015]. In addition, there are two optional feedback paths:

  • If a callback is configured, NvM_MainFunction calls NvM_SingleBlockCallbackFunction [SWS_NvM_00740] [SWS_NvM_00347]. Without a callback, there is no asynchronous notification [SWS_NvM_00742] (SWS NvM p. 160).
  • With NvMBswMBlockStatusInformation, the NvM reports acceptance and result to the BswM [SWS_NvM_00890] [SWS_NvM_00891] (SWS NvM p. 162).

Sequence diagram: Asynchronous write request with BswM status notifications, callback, and status query. Sources: [SWS_NvM_00185] [SWS_NvM_00347] [SWS_NvM_00740] [SWS_NvM_00890] [SWS_NvM_00891], SWS NvM p. 160

RAM block synchronization and block state

The NvM features two ways to synchronize data with the application's RAM block. With implicit synchronization, it works directly on this RAM block. The application provides the block and does not access it until the request completes [SWS_NvM_00698] [SWS_NvM_00699]. If it passes NULL_PTR, the NvM uses the permanent RAM block [SWS_NvM_00898] [SWS_NvM_00900]. A temporary block via pointer is still possible [SWS_NvM_00278]. The PRAM services always operate on the permanent RAM block [SWS_NvM_00765] [SWS_NvM_00794]. In the RTE scenario, this block is a Per-Instance-Memory (NV Data Handling p. 32).

With explicit synchronization (NvMBlockUseSyncMechanism), the exchange takes place via an internal RAM mirror [SWS_NvM_00511]. There is exactly one such mirror, sized according to the largest affected block [SWS_NvM_00513]. The NvM calls NvMWriteRamBlockToNvCallback or NvMReadRamBlockFromNvCallback [SWS_NvM_00515] [SWS_NvM_00516]. If a callback returns E_NOT_OK, it retries the call in the next cycle, up to NvMRepeatMirrorOperations times [SWS_NvM_00579] [SWS_NvM_00840]. The application may still modify the RAM block until the callback [SWS_NvM_00705]. A block uses either explicit synchronization or a permanent RAM block, not both [SWS_NvM_00904]. The mechanism allows shared blocks via an NvBlockSwComponentType (NV Data Handling p. 12).

Sequence diagram: Write request with explicit synchronization via the RAM mirror, including retry upon E_NOT_OK. Sources: [SWS_NvM_00515] [SWS_NvM_00705] [SWS_NvM_00579] [SWS_NvM_00840], NV Data Handling p. 27

The NvM maintains a \"valid\"/\"invalid\" state for permanent RAM blocks and the mirror [SWS_NvM_00128] [SWS_NvM_00132]. The transitions in detail:

  • NvM_ReadBlock invalidates the permanent RAM block already upon queuing [SWS_NvM_00198].
  • After successful reading, it is \"valid/unchanged\" [SWS_NvM_00200].
  • After default data have been loaded, it is \"valid/changed\" [SWS_NvM_00366].
  • NvM_SetRamBlockStatus(…, TRUE) marks it as changed and triggers a background CRC recalculation [SWS_NvM_00406] [SWS_NvM_00121].
  • After successful writing, it is considered \"valid/unmodified\" [SWS_NvM_00472].

State diagram: RAM block states and the triggering events. Sources: [SWS_NvM_00198] [SWS_NvM_00200] [SWS_NvM_00366] [SWS_NvM_00406] [SWS_NvM_00472] [SWS_NvM_00856]

Configuration, protection mechanisms, and partition reference

Three API configuration classes exist for constrained resources [SWS_NvM_00149]. Class 1 does not support dataset blocks [SWS_NvM_00365]. The descriptor tables are generated [SWS_NvM_00143]. Users declare the memory requirements at configuration time [SWS_NvM_00030]. BSW modules do this via NvBlockNeeds (BSWMD Template p. 241). The ECU integrator derives the NvM configuration from this (Methodology p. 444).

Several protection mechanisms are available for individual blocks:

  • An attribute field manages write protection [SWS_NvM_00054]; NvMBlockWriteProt enables it by default [SWS_NvM_00326].
  • Blocks with NvMWriteBlockOnce are written only once [SWS_NvM_00397]. The NvM rejects write requests prior to the first read [SWS_NvM_00952].
  • For locked blocks (NvM_SetBlockLockStatus), NvM_WriteBlock returns E_NOT_OK [SWS_NvM_00749]. Neither NvM_SetRamBlockStatus nor NvM_SetBlockProtection change the lock [SWS_NvM_00754].
  • Also optional are a static block ID header [SWS_NvM_00522], a CRC comparison to avoid unnecessary writing [SWS_NvM_00849], and encryption via the CSM [SWS_NvM_00976].

In case of partitioning, the NvM calls interfaces in the context of the respective assigned partition. General functions run in the master partition [SWS_NvM_00969]. NvM_ReadAll and NvM_WriteAll are offered only by the master [SWS_NvM_00970] [SWS_NvM_00971] [SWS_NvM_CONSTR00974]. SW-Cs reach the NvM via block-related ports:

  • PS_{Block} (Service) [SWS_NvM_00847]
  • PAdmin_{Block} (Administration) [SWS_NvM_00843]
  • PM_{Block} (Mirror) [SWS_NvM_00844]
  • PNJF_{Block} (Job End Notification) [SWS_NvM_00846]

Behavior in the event of an error

When reading, the NvM evaluates the notifications from the MemIf differently:

  • It reports a CRC mismatch as NVM_E_INTEGRITY_FAILED [SWS_NvM_00203].
  • It reports MEMIF_JOB_FAILED as NVM_E_REQ_FAILED [SWS_NvM_00654].
  • MEMIF_BLOCK_INVALID results only in NVM_REQ_NV_INVALIDATED, without a DEM notification [SWS_NvM_00341] [SWS_NvM_00652].

Several recovery stages take effect afterward:

  1. In case of CRC errors, configured read retries follow [SWS_NvM_00526].
  2. For redundant blocks, the NvM reads the second copy and attempts to restore redundancy [SWS_NvM_00199] [SWS_NvM_00531]. If this fails, it reports NVM_E_LOSS_OF_REDUNDANCY [SWS_NvM_00546].
  3. Finally, the NvM loads default data with the result NVM_REQ_RESTORED_DEFAULTS [SWS_NvM_00202]. The NV content remains unchanged in this process [SWS_NvM_00172].

If default data are missing, the RAM block remains invalid [SWS_NvM_00658] [SWS_NvM_00204]. Interpretation: The order of stages likely follows the enumeration in the Error Description (Error Description p. 62). This source deviates from the requirements in two points. It mentions NVM_REQ_RESTORED_FROM_ROM instead of NVM_REQ_RESTORED_DEFAULTS. In addition, it summarizes the final failure generically as NVM_E_REQ_FAILED. The requirements mentioned above are normative.

Activity diagram: Read error handling from retry through the redundant copy to default data. Interpretation: The order follows the enumeration of the Error Description. Sources: [SWS_NvM_00526] [SWS_NvM_00199] [SWS_NvM_00202] [SWS_NvM_00341] [SWS_NvM_00658], Error Description p. 62

When writing, the NvM counts negative responses up to NVM_MAX_NUM_OF_WRITE_RETRIES [SWS_NvM_00213] [SWS_NvM_00216]. If the limit is exceeded, it sets NVM_REQ_NOT_OK and reports NVM_E_REQ_FAILED [SWS_NvM_00683] [SWS_NvM_00684] (Error Description p. 43). Two additional error scenarios:

  • If write verification fails, the NvM reports NVM_E_VERIFY_FAILED and retries writing [SWS_NvM_00528] [SWS_NvM_00529].
  • A redundant block is considered written as soon as one copy was successful [SWS_NvM_00284].

The NvM reports incorrect usage to the DET if development error detection is enabled. Examples are NVM_E_UNINIT and NVM_E_BLOCK_PENDING [SWS_NvM_00614] [SWS_NvM_00615] as well as NVM_E_WRITE_PROTECTED [SWS_NvM_00962]. A multi-block request ends with NVM_REQ_NOT_OK as soon as a single block fails [SWS_NvM_00318]. Users check the status of their blocks themselves [SWS_NvM_00694]. After a failed read, they provide valid data before the next write [SWS_NvM_00696].
