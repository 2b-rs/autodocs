Role: unified access of the NvM to Fee and Ea

The Memory Abstraction Interface (MemIf) is the topmost layer of the Memory Hardware Abstraction. It conceals from the upper layers how many Fee and Ea modules lie beneath it, and provides them with virtual segmentation on a uniform linear address space (SWS MemIf p. 7). According to the SRS, MemIf replaces the earlier driver interface layers for EEPROM and Flash. Via this interface, the NVRAM manager can address multiple abstraction modules without requiring modification when changing a memory driver or memory device (SRS MemHwAb p. 5).

MemIf has no memory behavior of its own. Its API is mapped to the API of the underlying abstraction modules. For the functional behavior, the specification refers to these modules or to the memory drivers (SWS MemIf p. 17). Accordingly, each service definition describes only the invocation of the function of the same name of the selected module, for example with MemIf_Read [SWS_MemIf_00039] and MemIf_Write [SWS_MemIf_00040]. The required Ea functions are listed as Required Interfaces [SWS_MemIf_00047].

Diagrams of later releases additionally show MemAcc and Mem beneath Fee and Ea, respectively. The call MemIf_Write → Fee_Write remains unchanged there (SWS Fee p. 48). The following diagram shows the integration with directly connected drivers, as illustrated in the Ea_Write sequence (SWS Ea p. 41).

Context diagram: MemIf dispatches the jobs of the NvM to Fee or Ea; the drivers and the job feedback to the NvM lie outside MemIf. Sources: SWS MemIf p. 7, SWS Fls p. 58, SWS Ea p. 41, [SWS_MemIf_00048]

Device selection via DeviceIndex: macro or dispatch table

The parameter DeviceIndex selects the abstraction module and thus the memory device. If only one abstraction module is configured, the parameter is ignored. In this case, MemIf shall be implemented as a set of macros that map directly to the module's API, e.g., #define MemIf_Write(DeviceIndex, BlockNumber, DataPtr) Fee_Write(BlockNumber, DataPtr) (SWS MemIf p. 17, as of R24-11). The SRS follows the same direction: If a vendor library replaces all Fee and Ea modules, MemIf consists only of macros (SRS MemHwAb p. 5).

If multiple modules are configured, MemIf shall map the calls to the appropriate module using efficient mechanisms. The specification mentions tables of function pointers for this purpose. Interpretation of the note truncated there: DeviceIndex is likely to serve as an index into these tables (SWS MemIf p. 17).

There is a release difference regarding the type of the parameter. In R20-11, DeviceIndex is of type uint8 ([SWS_MemIf_00039], [SWS_MemIf_00041]). The document passages from R23-11 et seq. show uint16 (SWS MemIf p. 18). For R20-11, uint8 applies.

Activity diagram: The configuration determines whether a call reaches Fee/Ea directly via macro or after checking via DeviceIndex. Sources: SWS MemIf p. 17, [SWS_MemIf_00006], [SWS_MemIf_00039]

“Synchronous” refers only to the acceptance of the job. The actual work runs asynchronously in the cyclic main functions of the underlying modules. In the Ea_Write sequence, this takes place in a loop over Eep_MainFunction in a BSW task (SWS Ea p. 41). According to the specification, the Fee_Write sequence also applies to the remaining asynchronous services (SWS Fee p. 48). The return value of MemIf_Write is the return value of the called module function [SWS_MemIf_00040].

The NvM learns of the completion of a job in one of two ways:

  • The abstraction module calls NvM_JobEndNotification directly; MemIf is not involved (SWS Fee p. 48).
  • The NvM queries MemIf_GetJobResult in polling mode [SWS_MemIf_00043].

The MemIf API itself contains no callback function [SWS_MemIf_00038].

Sequence diagram: MemIf_Write returns immediately after forwarding; execution and result reporting follow asynchronously. Sources: SWS Ea p. 41, SWS Fee p. 48, [SWS_MemIf_00040], [SWS_MemIf_00043]

Device status, job result, and operating mode

MemIf_GetStatus [SWS_MemIf_00042] returns a value of MemIf_StatusType [SWS_MemIf_00064]. Possible values are MEMIF_UNINIT, MEMIF_IDLE, MEMIF_BUSY, and MEMIF_BUSY_INTERNAL. In the case of MEMIF_BUSY_INTERNAL, the abstraction module is busy with internal management; the driver beneath it may be busy or idle. Fee reports this value, for example, during a reorganization of the flash memory (SWS Fee p. 30). The drivers also use the same types, such as Fls_GetStatus (SWS Fls p. 35). The types from MemIf.h thus form the common vocabulary of the memory stack.

State diagram: Status transition of an abstraction module as passed through by MemIf_GetStatus. Sources: [SWS_MemIf_00064], SWS Fee p. 30

MemIf_GetJobResult returns MemIf_JobResultType [SWS_MemIf_00065]. Overview of the values:

  • MEMIF_JOB_OK and MEMIF_JOB_FAILED: Job completed successfully or unsuccessfully, respectively.
  • MEMIF_JOB_PENDING: Job not yet completed.
  • MEMIF_JOB_CANCELED: Job canceled.
  • MEMIF_BLOCK_INCONSISTENT: Block inconsistent or not found.
  • MEMIF_BLOCK_INVALID: Block marked as invalid.

Only the result of the most recently accepted job can be queried (SWS Fee p. 31). In the Flash driver, all job types share one result, which is overwritten with MEMIF_JOB_PENDING for each new job (SWS Fls p. 36).

State diagram: Lifecycle of the job result from acceptance to the final value. Sources: [SWS_MemIf_00065], SWS Fls p. 36, SWS Fee p. 31

MemIf_SetMode is the only job service that does not have a DeviceIndex. It calls the SetMode functions of all underlying modules [SWS_MemIf_00038]. The parameter MemIf_ModeType supports MEMIF_MODE_SLOW and MEMIF_MODE_FAST [SWS_MemIf_00066]. The drivers interpret this as normal SPI access or SPI burst, respectively (SWS Eep p. 34). Eep_SetMode must not be called during an ongoing operation. Fls_SetMode rejects a mode change in the "busy" state (SWS Fls p. 42). Interpretation: MemIf_SetMode is therefore likely only reasonably callable if no device is processing a job.

Canceling ongoing jobs

MemIf_Cancel returns no value and forwards the cancellation to the selected module [SWS_MemIf_00041]. Fee_Cancel and Ea_Cancel themselves run synchronously, but are asynchronous with respect to the hardware (SWS Fee p. 45, SWS Ea p. 44). In the flash path, the cancellation is passed on to Fls_Cancel. The error notification is returned to the NvM via Fee_JobErrorNotification and NvM_JobErrorNotification (SWS Fls p. 58). After that, the job result reports MEMIF_JOB_CANCELED, which Fee classifies as "failed" (SWS Fee p. 31).

A constraint applies to scheduling: Fls_Cancel must not be called during an ongoing Fls_MainFunction. This can be ensured in two ways (SWS Fls p. 58):

  • The job functions of NvM and driver run sequentially in the same task.
  • The task of the main function is non-interruptible.

Sequence diagram: The cancellation runs synchronously downward; the error notification bypasses MemIf to the NvM. Sources: SWS Fls p. 58, [SWS_MemIf_00041], SWS Fee p. 31

Integration: Headers, dependencies, and memory mapping

The file structure looks as follows (SWS MemIf p. 10):

  • MemIf.h includes the headers of the abstraction modules (Fee.h, Ea.h), MemIf_Cfg.h (with MemIf_Types.h), and Std_Types.h.
  • MemIf.c includes MemIf_MemMap.h and optionally Det.h.

Std_ReturnType and Std_VersionInfoType are imported from Std_Types.h [SWS_MemIf_00037]. Det_ReportError is an optional interface [SWS_MemIf_00048].

Context diagram: Include relationships from MemIf to configuration, standard types, Fee/Ea, and DET. Sources: SWS MemIf p. 10, [SWS_MemIf_00047]

For memory mapping, the distribution guide lists MemIf alongside FLS and FEE as an example of "Type I". To restrict the scope to one core, a SwAddrMethod with local scope can be used (EXP BSWDistribution p. 31). The MemoryMapping specification shows MemIf as part of an ICC2 cluster MEM. In it, MemIf_SetMode is a BswCalledEntity, and the module has the section prefix MEMIF (SWS MemMap p. 53).

Behavior in the event of an error

MemIf defines two development errors [SWS_MemIf_00006]:

  • MEMIF_E_PARAM_DEVICE (0x01): incorrect device index.
  • MEMIF_E_PARAM_POINTER (0x02): NULL pointer as argument.

Presumably, the pointer error affects the parameters DataBufferPtr and VersionInfoPtr. Reporting takes place via Det_ReportError [SWS_MemIf_00048]. When error detection is active and an error is detected, the following applies:

  • Read, Write, InvalidateBlock, and EraseImmediateBlock return E_NOT_OK ([SWS_MemIf_00044], [SWS_MemIf_00046]).
  • MemIf_GetJobResult returns MEMIF_JOB_FAILED (SWS MemIf p. 21).

The API does not return specific development error codes (SWS MemIf p. 12).

MemIf does not handle runtime errors from Fee or Ea itself; the intended reaction is "N/A". Only in polling mode does the NvM learn of the error via MemIf_GetJobResult with the result MEMIF_JOB_FAILED (ErrorDescription p. 58, ErrorDescription p. 60, each R20-11). An uninitialized Fee can be detected via its status query (ErrorDescription p. 53).

Recovery is handled by the NvM. If a write operation is affected, it increments a retry counter and aborts after exceeding the limit. It reports the error to the DEM; NVM_REQ_NOT_OK can then be queried via NvM_GetErrorStatus (EXP ErrorDescription p. 45, EXP ErrorDescription p. 58, as of R25-11). In contrast, MEMIF_BLOCK_INCONSISTENT and MEMIF_BLOCK_INVALID describe the state of the block content and are passed through unchanged [SWS_MemIf_00065].

Activity diagram: Depending on the stack configuration, a runtime error reaches the NvM via polling via MemIf or via callback; the reaction lies with the NvM. Sources: ErrorDescription p. 58, EXP ErrorDescription p. 45, [SWS_MemIf_00043]

The enumeration type MemIf_StatusType according to [SWS_MemIf_00064] represents the current operating state of the underlying abstraction module and the associated device driver. The type is made available via the header file MemIf.h.

State Values and Semantics

The value range comprises four discrete states according to [SWS_MemIf_00064]:

  • MEMIF_UNINIT: The underlying abstraction module or the device driver is not (yet) initialized.
  • MEMIF_IDLE: The underlying abstraction module or the device driver is currently idle.
  • MEMIF_BUSY: The underlying abstraction module or the device driver is currently busy processing a job.
  • MEMIF_BUSY_INTERNAL: The underlying abstraction module is busy with internal management operations; the underlying device driver can be either busy or idle.

The explicit distinction between MEMIF_BUSY and MEMIF_BUSY_INTERNAL makes it possible to separate internal management operations of the abstraction layer from regular driver activities. Since this is a pure type definition, [SWS_MemIf_00064] specifies no dedicated error codes, reentrancy restrictions, or DET/DEM notifications; error handling and call conditions are tied to the respective querying API functions.

Usage of MemIf_JobResultType

The enumeration type MemIf_JobResultType ([SWS_MemIf_00065]) is provided via the header file MemIf.h and designates the result of the most recently executed job within the module MemIf.

The type comprises the following status values:

  • MEMIF_JOB_OK: The job finished successfully.
  • MEMIF_JOB_FAILED: The job did not finish successfully.
  • MEMIF_JOB_PENDING: The job is not yet finished and is in progress.
  • MEMIF_JOB_CANCELED: The job was canceled.
  • MEMIF_BLOCK_INCONSISTENT: The requested block is inconsistent (may contain corrupted data) or was not found.
  • MEMIF_BLOCK_INVALID: The requested block was marked as invalid; the requested operation cannot be performed.

The enumeration values differentiate between the general execution status and block-related error causes. While MEMIF_JOB_FAILED indicates a general failure, MEMIF_BLOCK_INCONSISTENT and MEMIF_BLOCK_INVALID allow a targeted error response to integrity or validity issues of the affected block.

Interpretation: The presence of MEMIF_JOB_PENDING indicates asynchronous job processing; higher-level modules are likely to use this return value for status synchronization or for polling the completion time.
