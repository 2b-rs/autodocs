Classification: transport layer between PduR and FlexRay Interface

FrTp is the ISO 10681-2 transport layer of FlexRay communication. The module is located between the PDU Router and the FlexRay Interface. It fragments I-PDUs that do not fit into an assigned FlexRay L-PDU into segments and reassembles them upon reception (SWS FrTp p. 11). Where AUTOSAR does not specify its own requirements, ISO 10681-2 applies ([SWS_FrTp_01005]). The module supports its N-PDU formats ([SWS_FrTp_01006]).

The PduR calls the services FrTp_Transmit, FrTp_CancelTransmit, FrTp_ChangeParameter, and FrTp_CancelReceive ([SWS_FrTp_00149], [SWS_FrTp_00150], [SWS_FrTp_00151], [SWS_FrTp_01172]). In the opposite direction, FrTp uses PduR_FrTpStartOfReception, PduR_FrTpCopyRxData, PduR_FrTpRxIndication, PduR_FrTpCopyTxData, and PduR_FrTpTxConfirmation (SWS FrTp p. 19).

Downwards, FrTp passes N-PDUs with FrIf_Transmit. From below, it receives the calls FrTp_RxIndication, FrTp_TxConfirmation, and FrTp_TriggerTransmit ([SWS_FrTp_00152], [SWS_FrTp_00153], [SWS_FrTp_00154], SWS FrTp p. 20). From R24-11 onwards, an L-SDU Router is additionally located in between (SWS FrTp p. 19). For R20-11, by contrast, the direct call of FrIf_Transmit applies ([SWS_FrTp_01050], [SWS_FrTp_00577]).

Other partners are:

  • The ECU State Manager calls FrTp_Init and FrTp_Shutdown (SWS FrTp p. 19).
  • The BSW Scheduler calls FrTp_MainFunction ([SWS_FrTp_00162], SWS FrTp p. 81).
  • FrTp reports runtime errors via Det_ReportRuntimeError ([SWS_FrTp_00577]).

Context diagram: FrTp mediates between PduR and FrIf and is controlled by EcuM and BSW Scheduler. Sources: SWS FrTp p. 19, SWS FrTp p. 20, [SWS_FrTp_00577]

Module lifecycle and cyclic processing

FrTp has exactly two internal states: FRTP_OFF and FRTP_ON ([SWS_FrTp_01028]). The current state is stored in the static variable FrTpState ([SWS_FrTp_01029], [SWS_FrTp_01106]).

  • After power-on, the module is in FRTP_OFF ([SWS_FrTp_01030]).
  • A successful FrTp_Init with a pointer to FrTp_ConfigType switches to FRTP_ON ([SWS_FrTp_00147], [SWS_FrTp_01194], [SWS_FrTp_01032]). In doing so, all global variables are initialized and the instance is set to idle.
  • Segmentation, reassembly, and all other tasks run only in FRTP_ON ([SWS_FrTp_01033]).
  • If a service is called without initialization, it reports FRTP_E_UNINIT. Exceptions are FrTp_Init and FrTp_GetVersionInfo ([SWS_FrTp_01201]).

FrTp_Shutdown simply halts all open connections and frees the resources ([SWS_FrTp_00148]). Afterwards, the module is in FRTP_OFF again ([SWS_FrTp_01036], SWS FrTp p. 36).

FrTp_MainFunction drives protocol progress. It is the entry point for all processing tasks ([SWS_FrTp_00203], [SWS_FrTp_00580]) and must run at least once per FlexRay cycle ([SWS_FrTp_01152]). To this end, the services set internal flags such as TX_SDU_AVAILABLE and RX_PDU_AVAILABLE ([SWS_FrTp_00416], [SWS_FrTp_00418], SWS FrTp p. 37).

State diagram: Only FrTp_Init leads from FRTP_OFF to FRTP_ON, and processing takes place only there. Sources: [SWS_FrTp_01030], [SWS_FrTp_01032], [SWS_FrTp_01036], SWS FrTp p. 36

Transmission types according to ISO 10681-2

FrTp supports six transfer types:

  • unsegmented, without and with acknowledgment, with known length ([SWS_FrTp_01007], [SWS_FrTp_01008]);
  • segmented, without and with acknowledgment, with known length ([SWS_FrTp_01009], [SWS_FrTp_01010]);
  • segmented, without and with acknowledgment, with unknown length ([SWS_FrTp_01011], [SWS_FrTp_01012]).

A segmented transfer consists of StartFrame, FlowControl, ConsecutiveFrames, and LastFrame. A ConsecutiveFrame_EOB terminates a block; thereafter, the receiver enables the next block via FlowControl (SWS FrTp p. 28).

Transfers with unknown length work as follows:

  • The function is enabled via compiler switch ([SWS_FrTp_01062]).
  • The upper layer requests it with SduLength = 0 ([SWS_FrTp_01043], [SWS_FrTp_01064]).
  • The transfer ends as soon as the upper layer reports length 0 ([SWS_FrTp_01066]).
  • FrTp sums the partial lengths and transmits the total length in the LastFrame ([SWS_FrTp_01067]).

On 1:n connections, there is neither acknowledgment nor retry ([SWS_FrTp_00598]). Segmentation leads to error FRTP_E_SEG_ERROR there ([SWS_FrTp_01187], [SWS_FrTp_01208]).

Sequence diagram: Segmented unacknowledged transfer of known length with two blocks, each enabled via FlowControl_CTS. Sources: [SWS_FrTp_01009], SWS FrTp p. 28

Transmit sequence: from FrTp_Transmit to PduR_FrTpTxConfirmation

Each transmit operation begins with FrTp_Transmit ([SWS_FrTp_00136]). The service sets TX_SDU_AVAILABLE only if the TxPduId is valid and a channel is available ([SWS_FrTp_01039]). Otherwise, it returns E_NOT_OK ([SWS_FrTp_01040], [SWS_FrTp_01041]). The same applies if a transfer is already running for the same address information ([SWS_FrTp_01200]). The addresses originate from FrTpLa/FrTpRa or from the metadata SOURCE_ADDRESS_16/TARGET_ADDRESS_16 ([SWS_FrTp_01204], [SWS_FrTp_01205]).

In the MainFunction, the transmit operation proceeds in these steps:

  1. FrTp determines the available length via PduR_FrTpCopyTxData ([SWS_FrTp_01042]).
  2. FrTp allocates the first free FrTpTxPdu of the pool ([SWS_FrTp_01045]). If none is available, the connection is postponed to the next call ([SWS_FrTp_01047]).
  3. Based on the length of this PDU, FrTp decides whether segmentation is required ([SWS_FrTp_01048]).
  4. FrTp copies payload in PDU length ([SWS_FrTp_01123]) and sends it with FrIf_Transmit and exact length ([SWS_FrTp_01050], [SWS_FrTp_01051]).
  5. FrTp_TxConfirmation confirms each N-PDU and resets the FrTpTxPdu to “idle” ([SWS_FrTp_01052], [SWS_FrTp_01054]).

If PduR_FrTpCopyTxData returns BUFREQ_E_BUSY, FrTp retries up to FrTpTimeCs times ([SWS_FrTp_01196]).

Channel and flag are released as soon as three conditions are met: all data has been transmitted, the confirmation is positive, and in case of acknowledgment, the final acknowledgment has arrived ([SWS_FrTp_01056], [SWS_FrTp_01057]). For each accepted request, FrTp calls PduR_FrTpTxConfirmation exactly once, with E_OK or E_NOT_OK ([SWS_FrTp_01058]).

For the transmit direction, there are two buffer modes, “Immediate” and “Decoupled Buffer Access” ([SWS_FrTp_01084]). In decoupled mode, the lower layer fetches the N-PDU via FrTp_TriggerTransmit. In doing so, FrTp copies address information, PCI, and data with exact length ([SWS_FrTp_01060], [SWS_FrTp_01061]). Since this call runs in interrupt context, AI and PCI should be locally buffered in advance (SWS FrTp p. 50).

Sequence diagram: The transmit request is accepted synchronously and processed asynchronously in the MainFunction (Immediate Buffer Access; in Decoupled mode, FrTp_TriggerTransmit is added). Sources: SWS FrTp p. 44, [SWS_FrTp_01039], [SWS_FrTp_01042], [SWS_FrTp_01058]

Activity diagram: The length of the first free pool PDU determines whether segmentation is performed; on 1:n connections, necessary segmentation aborts the transfer. Sources: [SWS_FrTp_01047], [SWS_FrTp_01048], SWS FrTp p. 46, SWS FrTp p. 52

Receive sequence and reassembly

Reception always begins with FrTp_RxIndication ([SWS_FrTp_00137]). FrTp processes an N-PDU only if two conditions are met ([SWS_FrTp_01069], [SWS_FrTp_01071]):

  • The RxPduId is valid.
  • Target and source addresses match FrTpLa/FrTpRa of a FrTpConnection.

Otherwise, the N-PDU is ignored ([SWS_FrTp_01070], [SWS_FrTp_01072]). RX_PDU_AVAILABLE is additionally only set if a channel is free ([SWS_FrTp_01074]). If a free channel is missing, FrTp reports FRTP_E_NO_CHANNEL ([SWS_FrTp_01186]). The StartFrame remains buffered locally. In this way, a gateway, for example, can provide the FlowControl later as soon as a channel becomes free (SWS FrTp p. 56).

A new connection proceeds as follows:

  • FrTp calls PduR_FrTpStartOfReception with the expected length ([SWS_FrTp_01078]). For unknown length, this value is 0 ([SWS_FrTp_01184]). Data and size of the StartFrame are passed along ([SWS_FrTp_01193]).
  • The fragments go upwards via PduR_FrTpCopyRxData ([SWS_FrTp_01138]).
  • FrTp itself transmits FlowControl N-PDUs required by the protocol ([SWS_FrTp_01080]).
  • After complete reception, the channel is released ([SWS_FrTp_01081]). PduR_FrTpRxIndication reports the completion ([SWS_FrTp_01083]).
  • FrTp passes on the received addresses as metadata ([SWS_FrTp_01206]).

The sources represent the context in which PduR_FrTpStartOfReception is called differently:

  • The R20-11 illustration shows the MainFunction (SWS FrTp p. 86).
  • Newer versions show FrTp_RxIndication (SWS FrTp p. 49).
  • A note permits both (SWS FrTp p. 53).

Sequence diagram: The indication checks and buffers, the MainFunction reassembles, transmits FlowControl, and reports to the PduR. Sources: SWS FrTp p. 86, [SWS_FrTp_01074], [SWS_FrTp_01078], [SWS_FrTp_01083]

Channels, connections, PDU pools, and bandwidth control

Each communication relationship is an individual FrTpConnection container ([SWS_FrTp_01014]). It has a module-wide unique N-SDU ID and a unique address pair ([SWS_FrTp_01018], [SWS_FrTp_01017]). The number of connections is configurable post-build ([SWS_FrTp_01015]). The number of channels is defined by FrTpChanNum, and the channels operate in parallel ([SWS_FrTp_00088], [SWS_FrTp_00228]).

FrTp represents bandwidth as N-PDUs that are mapped directly to L-PDUs (SWS FrTp p. 60). The following applies to the transmit PDU pools:

  • Multiple connections may reference the same FrTpTxPduPool ([SWS_FrTp_01020]).
  • Pools may overlap ([SWS_FrTp_01176]).
  • The PDUs of a pool are ordered ascending by their position in the network schedule ([SWS_FrTp_01088]) and may vary in length ([SWS_FrTp_01089]).

ConsecutiveFrames must not overtake each other. For this purpose, a TxPduPendingCounter per channel counts the N-PDUs that are still unconfirmed ([SWS_FrTp_01090], [SWS_FrTp_01091], [SWS_FrTp_01092]). A connection is processed only if its counter is 0 ([SWS_FrTp_01094], [SWS_FrTp_01095]). All active connections take turns as long as the pool has free PDUs ([SWS_FrTp_01096], SWS FrTp p. 61).

At runtime, FrTp_ChangeParameter modifies the BandwidthControl parameter with TP_BC. It consists of FrTpSCexp and FrTpMaxNbrOfNPduPerCycle ([SWS_FrTp_00242], [SWS_FrTp_01178], ComStack Types p. 18). Bits 3..7 carry the PDU count, bits 0..2 the exponent ([SWS_FrTp_01195]). During an ongoing reception, FrTp rejects the change with E_NOT_OK ([SWS_FrTp_01115]); otherwise, the new value applies from then on ([SWS_FrTp_01156]).

As a sender, FrTp adheres to the limit reported by the receiver:

  • With BC.MPPC ≠ 0, it uses only the corresponding number of pool PDUs ([SWS_FrTp_01175]).
  • If FrTpBandwidthLimitation is set, StartFrame and FlowControl always go into the first PDU of the pool ([SWS_FrTp_01174], [SWS_FrTp_01177], SWS FrTp p. 134).

Collaboration diagram (schematic example): Connections share overlapping Tx PDU pools whose N-PDUs are mapped one-to-one to L-PDUs of the FrIf. Sources: [SWS_FrTp_01020], [SWS_FrTp_01176], SWS FrTp p. 60

Behavior in the event of an error

Development and runtime errors. When development error detection is enabled, the services check their parameters. They then report FRTP_E_INVALID_PDU_SDU_ID, FRTP_E_PARAM_POINTER, or FRTP_E_INVALID_PARAMETER ([SWS_FrTp_01201]).

  • Services with a return value return E_NOT_OK in this case, for example FrTp_Transmit ([SWS_FrTp_01139], [SWS_FrTp_01140]), FrTp_CancelTransmit ([SWS_FrTp_01141]), FrTp_ChangeParameter ([SWS_FrTp_01143], [SWS_FrTp_01144]), FrTp_TriggerTransmit ([SWS_FrTp_01145], [SWS_FrTp_01146]), and FrTp_CancelReceive ([SWS_FrTp_01180]).
  • The callbacks FrTp_RxIndication and FrTp_TxConfirmation only report the error ([SWS_FrTp_01147], [SWS_FrTp_01148], [SWS_FrTp_01149], [SWS_FrTp_01203]).
  • A transmission of unknown length that is not configured results in FRTP_E_UMSG_LENGTH_ERROR ([SWS_FrTp_01134]).
  • The runtime errors are FRTP_E_SEG_ERROR and FRTP_E_NO_CHANNEL ([SWS_FrTp_01208]).

Protocol errors. In case of these errors, FrTp actively aborts the transfer and reports PduR_FrTpTxConfirmation(E_NOT_OK) ([SWS_FrTp_01198], [SWS_FrTp_01199]):

  • a FlowControl with invalid FS or with OVFLW or ABT;
  • a ACK_RET whose buffer position is outside the sender buffer.

A negative FrTp_TxConfirmation releases the occupied channel ([SWS_FrTp_01056], [SWS_FrTp_01081]).

Timers and counters. Time monitoring follows the defined timers and timeout reactions ([SWS_FrTp_01055], [SWS_FrTp_01099], [SWS_FrTp_01100]). Their configuration must adhere to fixed inequalities ([SWS_FrTp_00599], [SWS_FrTp_01153], [SWS_FrTp_01154], [SWS_FrTp_01155]). The counters COUNTER_FCWT and Counter_RX_RN are limited; upon reaching the limit, a defined reaction applies ([SWS_FrTp_01105], [SWS_FrTp_01114], [SWS_FrTp_01113], SWS FrTp p. 69). If an error occurs during segmented reception, the flag RX_ERROR retains it until the reaction ([SWS_FrTp_00429], [SWS_FrTp_00430]).

Transmit cancellation. Transmit cancellation is activated via FrTpTransmitCancellation ([SWS_FrTp_01097]) and requested with FrTp_CancelTransmit ([SWS_FrTp_00384]). The result depends on the progress:

  • A request that has not yet started releases the connection immediately ([SWS_FrTp_00385]).
  • An ongoing transfer is stopped; the service returns E_OK ([SWS_FrTp_01116]).
  • In case of an inactive connection, or if the last N-PDU of an unacknowledged transfer has already been passed, the service returns E_NOT_OK ([SWS_FrTp_01116]).

The receiver detects an abort only via a timeout and reports it via PduR_FrTpRxIndication (SWS FrTp p. 65).

Receive cancellation. FrTp_CancelReceive cancels a segmented reception and then returns E_OK ([SWS_FrTp_01181], [SWS_FrTp_01183]). In case of unsegmented reception or during the LastFrame, the service rejects ([SWS_FrTp_01182]).

Sequence diagram: A transmit cancellation in the middle of the segmented transfer ends in a timeout with a negative completion indication at the receiver. Sources: SWS FrTp p. 65, [SWS_FrTp_01116], SWS FrTp p. 58

Usage and Semantics

The function FrTp_Transmit serves to request transmission of a PDU ([SWS_FrTp_00149]). The call behaves synchronously and returns E_OK if the transmit request was accepted, or E_NOT_OK if the request was rejected ([SWS_FrTp_00149]). Parameter TxPduId specifies the PDU to be transmitted; PduInfoPtr passes the length, the pointer to the payload, and a pointer to metadata ([SWS_FrTp_00149]). If an upper-layer data transmission with unknown message length is to be started, FrTp_Transmit must be called with the parameter value PduLength = 0 ([SWS_FrTp_01064]).

Error Handling and Checks

If Development Error Detection is enabled, the function performs checks on the input parameters:

  • If the pointer PduInfoPtr is invalid, FrTp_Transmit reports the error FRTP_E_PARAM_POINTER and returns E_NOT_OK ([SWS_FrTp_01140]).
  • If parameter TxPduId is invalid or not supported, error FRTP_E_INVALID_PDU_SDU_ID is reported, the service is aborted, and E_NOT_OK is returned ([SWS_FrTp_01040], [SWS_FrTp_01139]).

In addition, execution is aborted and E_NOT_OK is returned if no free transmit channel is currently available (state FrTpTxChannelState ≠ Idle) ([SWS_FrTp_01041]).

Concurrency and Reentrancy

FrTp_Transmit is reentrant for calls with different PDU identifiers (TxPduId). However, the function is not reentrant for the same PDU identifier ([SWS_FrTp_00149]).

The synchronous function FrTp_CancelTransmit ([SWS_FrTp_00150]) serves to request the cancellation of an ongoing PDU transmission in a lower-layer communication module. The PDU to be cancelled is specified via parameter TxPduId.

Semantics and Return Values

  • If the transmit request is still pending but the actual transmission process has not yet started, the function releases the connection immediately ([SWS_FrTp_00385]).
  • If transmission is already in progress, FrTp_CancelTransmit stops the process and returns E_OK ([SWS_FrTp_01116]).
  • If the connection is not active or the last N-PDU of an unconfirmed transmission has already been forwarded to the FrIf, the cancellation request fails and the function returns E_NOT_OK ([SWS_FrTp_01116]).

Error Handling and Concurrency

If the Development Error Tracer (DET) is enabled for FrTp_CancelTransmit, the function checks parameter TxPduId for validity. If this check fails, the development error FRTP_E_INVALID_PDU_SDU_ID is reported and E_NOT_OK is returned ([SWS_FrTp_01141]).

Regarding reentrancy, the call is reentrant for different PDU IDs, but non-reentrant for identical PDU IDs ([SWS_FrTp_00150]).

use

The synchronous function FrTp_ChangeParameter ([SWS_FrTp_00151], declared in FrTp.h) serves for runtime modification of transport protocol parameters. Via the service, the FlowControl PDU parameters of the bandwidth control (BandwidthControl) according to ISO 10681-2 – namely FrTpSCexp and FrTpMaxNbrOfNPduPerCycle – can be adjusted at runtime ([SWS_FrTp_00242]).

The function expects the following input parameters ([SWS_FrTp_00151]):

  • id (PduIdType): Identifier of the PDU that the parameter change is to affect.
  • parameter (TPParameterType): Identifier of the parameter to be modified.
  • value (uint16): The new value for the selected parameter.

The return value signals successful execution of the change with E_OK or rejection of the change request with E_NOT_OK ([SWS_FrTp_00151]).

Error handling

Provided that development error detection (Development Error Detection) is activated for FrTp_ChangeParameter, input checks are performed with specific error messages:

  • In case of an invalid PDU identifier (id), the module reports the development error FRTP_E_INVALID_PDU_SDU_ID and aborts with E_NOT_OK ([SWS_FrTp_01143]).
  • In case of an invalid parameter identifier (parameter), the development error FRTP_E_INVALID_PARAMETER is raised and E_NOT_OK is returned ([SWS_FrTp_01144]).

Concurrency and Limitations

The service is defined as non-reentrant (Non Reentrant) ([SWS_FrTp_00151]). It should also be noted that on the transmitter side, an additional FlowControl resulting from the parameter change is received as an unexpected N-PDU and ignored ([SWS_FrTp_00242]).

Usage and Semantics

The synchronous function FrTp_CancelReceive serves to request the cancellation of an ongoing PDU reception in a lower-layer transport protocol module ([SWS_FrTp_01172]). It is declared via the header file FrTp.h and has the service ID 0x4c ([SWS_FrTp_01172]).

  • Parameters: RxPduId of type PduIdType passes the identifier of the PDU whose reception is to be cancelled ([SWS_FrTp_01172]).
  • Return value: The function returns E_OK if the cancellation was successfully executed by the target module ([SWS_FrTp_01172], [SWS_FrTp_01183]). If the cancellation is rejected by the target module, it returns E_NOT_OK ([SWS_FrTp_01172]).

Concurrency and Limitations

The function is specified as non-reentrant (Non Reentrant) and synchronous ([SWS_FrTp_01172]). Consequently, calls must not be executed concurrently.

Error Handling and Interaction

If the cancellation fails or is rejected by the target module, this is signaled to the caller via the result E_NOT_OK ([SWS_FrTp_01172]). If the service FrTp_CancelReceive was successfully executed, the return value according to [SWS_FrTp_01183] must mandatorily be E_OK.

The function FrTp_TriggerTransmit ([SWS_FrTp_00154]) serves for the synchronous provision of SDU transmit data. Upon calling, the calling layer passes the identifier TxPduId and, via parameter PduInfoPtr, a pointer to structure PduInfoType. This contains the buffer address SduDataPtr and the available buffer size in SduLength.

Usage and Data Transmission

  • The module checks synchronously whether the data to be transmitted fit into the buffer reported by PduInfoPtr->SduLength ([SWS_FrTp_00154]).
  • If the buffer size is sufficient, address information, PCI, and N-SDU data are copied into the buffer ([SWS_FrTp_01060]). The field SduLength is updated to the exact number of copied data bytes, and the function returns E_OK ([SWS_FrTp_00154], [SWS_FrTp_01061]).
  • If the buffer is not sufficient, the function aborts with E_NOT_OK without modifying PduInfoPtr. In this case, the buffer must not be used ([SWS_FrTp_00154]).

Error handling

Provided that development error detection (DET) is enabled, the function validates its input parameters:

  • If an invalid TxPduId is passed, the function reports the error FRTP_E_INVALID_PDU_SDU_ID and returns E_NOT_OK ([SWS_FrTp_01145]).
  • If the pointer PduInfoPtr is invalid, the function reports FRTP_E_PARAM_POINTER and likewise returns E_NOT_OK ([SWS_FrTp_01146]).

Concurrency

The function is reentrant for different TxPduId values, but not reentrant for the same TxPduId ([SWS_FrTp_00154]).

Usage and Semantics

The function FrTp_RxIndication ([SWS_FrTp_00152]) serves to signal a received PDU by the lower-layer communication interface module. Via this service primitive call, the actual reception process in the FrTp module is initiated ([SWS_FrTp_00137]). The function operates synchronously and has no return value. Expected parameters are the identifier of the received PDU (RxPduId) and a pointer to the PDU information (PduInfoPtr), which provides buffer pointer, data length, and associated metadata ([SWS_FrTp_00152]).

Error Handling and Validation

When development error detection (DET) is activated, the function checks the passed parameters:

  • If the parameter RxPduId is invalid, the function reports the error FRTP_E_INVALID_PDU_SDU_ID ([SWS_FrTp_01147]).
  • If the pointer PduInfoPtr is invalid, the error FRTP_E_PARAM_POINTER is raised ([SWS_FrTp_01148]).

If an unsupported RxPduId is passed, FrTp_RxIndication aborts without further action ([SWS_FrTp_01075]). If no free reception channel is available (FrTpRxChannelState ≠ Idle), the call is likewise terminated without further actions ([SWS_FrTp_01076]) and the runtime error FRTP_E_NO_CHANNEL is reported ([SWS_FrTp_01186]).

Concurrency and Limitations

FrTp_RxIndication is reentrant for different PDU IDs, but not reentrant for identical PDU IDs ([SWS_FrTp_00152]). Concurrent calls with the same RxPduId are therefore not permitted.

function FrTp_TxConfirmation [SWS_FrTp_00153] 📄 PDF

void FrTp_TxConfirmation (PduIdType TxPduId, Std_ReturnType result);

The lower layer communication interface module confirms the transmission of a PDU, or the failure to transmit a PDU.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 851fa1a8fc96 Provenance

Usage and Semantics

The function FrTp_TxConfirmation is called by the lower communication layer to confirm the successful transmission or failure of a PDU to the FrTp module [SWS_FrTp_00153], [SWS_FrTp_01053]. The call is synchronous and has no return value. The PDU identifier (corresponding FrTpTxConfirmationPduId) is passed via parameter TxPduId. Parameter result indicates whether the PDU was successfully transmitted (E_OK) or transmission failed (E_NOT_OK) [SWS_FrTp_00153].

Concurrency and Limitations

The function is reentrant for calls with different PDU IDs, but not reentrant for the same PDU ID [SWS_FrTp_00153].

Error handling

When development error detection (Development Error Detection) is activated, the passed arguments are checked:

  • If TxPduId is invalid, the function reports the error FRTP_E_INVALID_PDU_SDU_ID [SWS_FrTp_01149].
  • If the parameter result is invalid, the development error FRTP_E_INVALID_PARAMETER is raised [SWS_FrTp_01203].

Interaction and State Management

With each call with the corresponding confirmation ID, the counter TxPduPendingCounter is decremented [SWS_FrTp_01092]. In addition, the call affects internal channel states and control flags:

  • Transmit channel (Tx): The module releases the allocated channel (FrTpTxChannelState = Idle) and resets the flag TX_SDU_AVAILABLE if result has the value E_NOT_OK or if all Tx N-SDU data have been transmitted, confirmation was given with E_OK, and an optionally configured final acknowledge was received [SWS_FrTp_01056], [SWS_FrTp_01057]. Under the same conditions (as well as upon a transmission abort), the flag TX_SDU_UNKNOWN_MSG_LENGTH is also reset [SWS_FrTp_01124].
  • Receive channel (Rx): The occupied receive channel is released (FrTpRxChannelState = Idle) if FrTp_TxConfirmation is reported with E_NOT_OK or if all N-SDU data have been received and all required response PDUs (FlowControl) have been successfully confirmed with E_OK [SWS_FrTp_01081].
