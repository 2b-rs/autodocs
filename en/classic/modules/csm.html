Bundles crypto services and key management for applications and BSW and passes jobs to crypto drivers.

The CSM provides cryptographic services and key management to applications and BSW modules via a unified interface. Each service operates on a job, i.e., an instance of a configured primitive [SWS_Csm_00941]. Depending on the configuration, the job runs synchronously or asynchronously. The CSM queues asynchronous jobs by priority, passes them to the crypto drivers via CryIf in the cyclic Csm_MainFunction, and reports the result via callback [SWS_Csm_00479]. Most important constraint: Keys must be set to valid, and a full queue leads to rejection with CRYPTO_E_BUSY.

The Crypto Service Manager (CSM) is the service layer of the Classic crypto stack. It offers cryptographic services and key management SWS CSM p. 25. Applications and BSW modules such as SecOC, DCM, or KeyM use it. It passes the requests on via CryIf to Crypto Driver Objects in hardware or software SWS CSM p. 29.

The parameter mode combines START, UPDATE, and FINISH. This enables streaming and single call, and the job transitions between IDLE and ACTIVE [SWS_Csm_01029] [SWS_Csm_01028]. Running jobs can be saved, restored, or canceled with Csm_CancelJob [SWS_Csm_91063] [SWS_Csm_00968].

Keys consist of standardized elements [SWS_Csm_00954] [SWS_Csm_01022]. They can be set, set valid or invalid, copied, generated, derived, and exchanged via Diffie-Hellman. Only valid keys can be used for jobs [SWS_Csm_91075] [SWS_Csm_00966].

In case of error, the services return codes such as CRYPTO_E_BUSY or CRYPTO_E_KEY_NOT_VALID [SWS_Csm_91044]. Optionally, the CSM reports development errors such as CSM_E_UNINIT to DET [SWS_Csm_91004]. A queue overflow is indicated by the runtime error CSM_E_QUEUE_FULL [SWS_Csm_01089]; presumably it is reported in addition to the return value CRYPTO_E_BUSY.

Role of the CSM Between Crypto Users and Driver Layer

The Crypto Service Manager (CSM) is the service layer of the Classic crypto stack. It provides two types of services: the cryptographic services themselves and key management SWS CSM p. 25. Cryptographic operations are requested via job-related functions. Examples are Csm_Hash [SWS_Csm_00980], Csm_MacGenerate [SWS_Csm_00982], Csm_Encrypt [SWS_Csm_00984], Csm_AEADEncrypt [SWS_Csm_01023], Csm_SignatureVerify [SWS_Csm_00996], and Csm_RandomGenerate [SWS_Csm_01543].

Downwards, the CSM forwards requests via the Crypto Interface (CryIf) to Crypto Driver Objects. The specification calls the path from a CSM queue via CryIf to a Crypto Driver Object a channel. A Crypto Driver Object can be hardware (such as an AES accelerator in the HSM) or software SWS CSM p. 29. Upwards, applications use the CSM as an AUTOSAR service via RTE ports SWS CSM p. 85. BSW modules also access it:

  • SecOC uses it to compute and verify authenticators SWS SecOC p. 78.
  • DCM uses it to verify signatures during authentication SWS DCM p. 152.
  • KeyM uses it to set and validate keys SWS KeyM p. 80.

Certificate handling has no longer been part of the CSM since R19-11, but belongs to the Key Manager Release Overview p. 32.

Jobs, Primitives, Keys, and Queues as Configuration Objects

The central unit is the job, i.e., an instance of a configured cryptographic primitive [SWS_Csm_00941]. At runtime, Crypto_JobType describes it. The structure contains, among other things, jobId, jobState, the input and output structure Crypto_JobPrimitiveInputOutputType, and a pointer to the constant Crypto_JobPrimitiveInfoType [SWS_Csm_01013] [SWS_Csm_01009] SWS CSM p. 20. Crypto_JobPrimitiveInfoType carries the callback identifier, the CryIf key, and the processing type Crypto_ProcessingType [SWS_Csm_01012] [SWS_Csm_01049]. The primitive itself defines Crypto_PrimitiveInfoType, consisting of service and algorithm. The algorithm comprises family, secondary family, key length, and mode [SWS_Csm_01011] [SWS_Csm_01031] [SWS_Csm_01008]. Optionally, Crypto_JobRedirectionInfoType redirects inputs and outputs to key elements [SWS_Csm_91026] [SWS_Csm_91024].

In the ECU configuration, each job receives the following information SWS CSM p. 173:

  • a CsmJobId and a CsmJobPriority,
  • a reference to a primitive,
  • via CsmJobInterfaceUsePort, the specification of whether it is used as a function or via ports.

A CsmKey with CsmKeyId references a CryIfKey SWS CSM p. 171. A CsmQueue with CsmQueueSize references a CryIfChannel and a MainFunction instance SWS CSM p. 173. A separate Csm_MainFunction_<shortName> is created for each configured CsmMainFunction [SWS_Csm_00479].

Csm_Init initializes the module. If the CSM is allocated to multiple partitions, there may be one init function per partition [SWS_Csm_00646]. The content of Csm_ConfigType is implementation-specific [SWS_Csm_01085]. According to version R24-11, configPtr is always a null pointer SWS CSM p. 48.

From Service Call to Driver Processing

The job configuration determines whether a service runs synchronously or asynchronously. The service functions are therefore specified as “Synchronous or Async, depending on the job configuration” [SWS_Csm_00980] [SWS_Csm_00982]. Chapter 7.2 (quoted according to R24-11) defines the following rules SWS CSM p. 21:

  • Only one instance per job is processed at a time; different jobs may run in parallel.
  • If a job is already ACTIVE, the CSM directly calls CryIf_ProcessJob and passes through its return value.
  • If a job needs to be queued and the queue is full, the CSM rejects it with CRYPTO_E_BUSY.

The queues sort jobs according to their configured priority [SWS_Csm_00940] [SWS_Csm_00944].

Activity diagram: The service entry decides between direct forwarding to CryIf, queuing into the queue, and rejection with BUSY. Interpretation: The logic originates from the diagram of later releases and is likely to apply analogously to R20-11. Sources: SWS CSM p. 30, SWS CSM p. 21, [SWS_Csm_00944]

In case of asynchronous usage, the interface functions only pass the necessary information to the lower layers SWS CSM p. 25. The sequence thereafter:

  1. The Basic Software Scheduler calls Csm_MainFunction cyclically. It checks the queues and passes jobs to CryIf [SWS_Csm_00479] SWS CSM p. 84.
  2. The lower layer reports completion via Csm_CallbackNotification [SWS_Csm_00970].
  3. The CSM calls the configured function <Csm_ApplicationCallbackNotification>(jobId, result) [SWS_Csm_00971], but only if the FINISH bit is set in the mode [SWS_Csm_01044].

RTE users are provided with the port CallbackNotification_{Job} for this purpose, provided the job is configured as asynchronous and not as a pure function [SWS_Csm_00934] [SWS_Csm_00928].

Sequence diagram: An asynchronous job is accepted and later passed to CryIf in the MainFunction. The result is returned via a callback chain. Sources: SWS CSM p. 164, [SWS_Csm_00479], [SWS_Csm_00970], [SWS_Csm_01044], [SWS_Csm_00971]

Streaming, Single Call, and Job State

The parameter mode of type Crypto_OperationModeType is a bit field consisting of START (0x01), UPDATE (0x02), and FINISH (0x04). Combined values are CRYPTO_OPERATIONMODE_STREAMSTART (0x03) and CRYPTO_OPERATIONMODE_SINGLECALL (0x07) [SWS_Csm_01029] [SWS_Csm_01039]. The modes operate as follows:

  • START resets the job and discards previous inputs and intermediate results [SWS_Csm_01029].
  • Repeated UPDATE processes large amounts of data using the streaming approach. The single call, by contrast, saves call overhead for small data EXP Krypto-Dienste p. 12.
  • START and FINISH without UPDATE are rejected with E_NOT_OK [SWS_Csm_01045].
  • FINISH completes the calculation [SWS_Csm_01046].

Crypto_JobStateType has two states [SWS_Csm_01028]:

  • CRYPTO_JOBSTATE_IDLE: after Csm_Init or after completed FINISH,
  • CRYPTO_JOBSTATE_ACTIVE: after START or UPDATE.

According to a specification note, the actual state transitions are performed by the Crypto Driver SWS CSM p. 22.

State diagram: A job transitions to ACTIVE with START, remains there upon UPDATE, and returns to IDLE after FINISH. SINGLECALL executes all steps in a single call. Sources: [SWS_Csm_01028], [SWS_Csm_01029], [SWS_Csm_01039]

Running jobs can be interrupted and resumed. Csm_SaveContextJob stores the working context in an application buffer, and Csm_RestoreContextJob restores it [SWS_Csm_91063] [SWS_Csm_91064]. Key elements do not belong to this context SWS CSM p. 35. Csm_CancelJob cancels asynchronous or streaming jobs [SWS_Csm_00968]. For this purpose, the CSM removes the job from its queue or calls CryIf_CancelJob SWS CSM p. 80.

Key Management: Elements, Validity, Generation, and Exchange

A key consists of one or more key elements [SWS_Csm_00954]. Their IDs are standardized, such as CRYPTO_KE_MAC_KEY (1), CRYPTO_KE_CIPHER_IV (5), and CRYPTO_KE_KEYGENERATE_SEED (16) [SWS_Csm_01022]. Key services are only available as a Csm_<Service> function [SWS_Csm_00950]. The basic services are synchronous, including Csm_KeyElementSet, Csm_KeySetValid, and Csm_KeyElementGet [SWS_Csm_00957] [SWS_Csm_00958] [SWS_Csm_00959]. If elements are located directly in flash, these calls can take longer. While a key function is running, the CSM does not take any new jobs from the queue until the next MainFunction call SWS CSM p. 60.

The key status (CRYPTO_KEYSTATUS_INVALID or CRYPTO_KEYSTATUS_VALID) is returned by Csm_KeyGetStatus [SWS_Csm_91102] [SWS_Csm_91047]. Csm_KeySetValid sets the key to valid. Csm_KeySetInvalid blocks it for cryptographic operations until it is set to valid again [SWS_Csm_00958] [SWS_Csm_91075]. In addition, there are job-based variants such as Csm_JobKeySetValid, Csm_JobKeyGenerate, and Csm_JobKeyDerive. Depending on the job configuration, they run synchronously or asynchronously [SWS_Csm_91027] [SWS_Csm_91029] [SWS_Csm_91030].

State diagram: Only a valid key can be used for jobs; setting and invalidating control the transition. Interpretation: The transition to INVALID via Csm_KeyElementSet is derived from an example. Sources: [SWS_Csm_91102], [SWS_Csm_00958], [SWS_Csm_91075], [SWS_Csm_91043]

Additional key services:

  • Copying: element-by-element with Csm_KeyElementCopy, partially with Csm_KeyElementCopyPartial, or as an entire key with Csm_KeyCopy [SWS_Csm_00969] [SWS_Csm_91025] [SWS_Csm_01034].
  • Generation: Prior to Csm_KeyGenerate, a random value must be present in CRYPTO_KE_KEYGENERATE_SEED, for instance from Csm_RandomGenerate. The algorithm is determined by CRYPTO_KE_KEYGENERATE_ALGORITHM [SWS_Csm_00955] SWS CSM p. 67.
  • Derivation: Csm_KeyDerive writes to a destination key and calls CryIf_KeyDerive [SWS_Csm_00956] [SWS_Csm_01018].
  • Exchange: For Diffie-Hellman, two partners determine a shared secret using Csm_KeyExchangeCalcPubVal and Csm_KeyExchangeCalcSecret without disclosing their private shares [SWS_Csm_00966] [SWS_Csm_00967] SWS CSM p. 70.

Sequence diagram: The partners only exchange public values. The shared secret is generated locally via two CSM calls. Sources: SWS CSM p. 70, [SWS_Csm_00966], [SWS_Csm_00967]

Interface Types: C-API, RTE Ports, and Buffer Types

BSW users call the C functions from Csm.h. For applications, Chapter 8.7 describes the service interfaces from which the RTE is generated SWS CSM p. 85. Depending on the configuration, the following ports are created:

  • CsmJob_{Job} for synchronous or asynchronous processing, each with a fixed argument CRYPTO_OPERATIONMODE_SINGLECALL [SWS_Csm_91023] [SWS_Csm_91062],
  • CsmKey_{Key} when CsmKeyUsePort is set [SWS_Csm_01042] [SWS_Csm_01905],
  • optionally CsmContext_{Job} [SWS_Csm_91105].

The buffer types are uint8 arrays whose size results from the primitive configuration, for example Csm_HashResultType_{Crypto} and Csm_MacVerifyCompareType_{Crypto} [SWS_Csm_00912] [SWS_Csm_00803]. Lengths and verification results are returned asynchronously via the pointer types Csm_LengthPtr and Csm_VerifyResultPtr [SWS_Csm_91045] [SWS_Csm_91046]. Verifications yield CRYPTO_E_VER_OK or CRYPTO_E_VER_NOT_OK [SWS_Csm_01024].

Behavior in the event of an error

The services return Std_ReturnType, asynchronous results Crypto_ResultType. In addition to E_OK and E_NOT_OK, there are specific codes such as CRYPTO_E_BUSY, CRYPTO_E_ENTROPY_EXHAUSTED, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_NOT_AVAILABLE, and CRYPTO_E_KEY_NOT_VALID [SWS_Csm_91044] [SWS_Csm_91043]. Key functions additionally report CRYPTO_E_KEY_SIZE_MISMATCH and CRYPTO_E_KEY_EMPTY [SWS_Csm_00969] [SWS_Csm_00956]. If Csm_KeyElementSet fails, the state of the element is considered unknown. The application can then check it using Csm_KeyGetStatus SWS CSM p. 62.

The CSM optionally reports development errors via Det_ReportError [SWS_Csm_91101]. Defined errors include [SWS_Csm_91004]:

  • CSM_E_PARAM_POINTER: null pointer,
  • CSM_E_PARAM_HANDLE: ID out of range,
  • CSM_E_UNINIT: call prior to initialization,
  • CSM_E_INIT_FAILED: initialization failed,
  • CSM_E_PROCESSING_MODE: invalid processing mode.

According to version R24-11, CSM_E_PROCESSING_MODE occurs, for example, if Csm_CancelJob is called for a synchronous job SWS CSM p. 80. As a runtime error, the queue overflow CSM_E_QUEUE_FULL is defined [SWS_Csm_01089] SWS CSM p. 35. Interpretation: It is likely reported concurrently with the return value CRYPTO_E_BUSY when the queue is full.

Csm_CancelJob can return two results [SWS_Csm_00968]:

  • E_OK: The job was removed from the queues and, if applicable, from the driver hardware.
  • CRYPTO_E_JOB_CANCELED: Immediate cancellation is not possible. Cancellation follows in the next appropriate step and is reported via a negative completion callback.

According to version R24-11, context operations on an IDLE job or on a job currently executing in the driver terminate immediately with E_NOT_OK SWS CSM p. 35.
