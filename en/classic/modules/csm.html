The CSM as a service layer between users and crypto drivers

The Crypto Service Manager provides cryptographic services to applications and BSW modules via a standardized API. These include hash, MAC, encryption and decryption, AEAD, signatures, random numbers, and key management, for example via Csm_Hash [SWS_Csm_00980], Csm_MacGenerate [SWS_Csm_00982], Csm_AEADEncrypt [SWS_Csm_01023], or Csm_SignatureVerify [SWS_Csm_00996]. The CSM does not perform calculations itself. It forwards jobs via the Crypto Interface (CryIf) to Crypto Driver Objects, which can be hardware (e.g., HSM) or software. The path from a CSM queue via the CryIf to a Crypto Driver Object is called a channel (SWS CSM p. 29). [SWS_Csm_91100] lists the required CryIf functions. Det_ReportError is an optional interface [SWS_Csm_91101].

Software components access via RTE service ports, which are formally defined in the chapter "Service Interfaces" (SWS CSM p. 85). BSW modules use the C API directly. Two examples:

  • The DCM checks Proof-of-Ownership with Csm_SignatureVerify in mode CRYPTO_OPERATIONMODE_SINGLECALL (SWS DCM p. 152).
  • The IdsM receives the result of asynchronous signature jobs via a callback configured in the CSM (SWS IdsM p. 77).

Jobs, queues, and channels: how a service call is forwarded

A job is an instance of a configured cryptographic primitive [SWS_Csm_00941]. For each job, only one instance is processed at a time. Different jobs may run in parallel (SWS CSM p. 21). At runtime, the structure Crypto_JobType carries the job. It contains jobId, jobState, the input/output structure jobPrimitiveInputOutput, the primitive information, and the key IDs [SWS_Csm_01013], [SWS_Csm_01009], [SWS_Csm_01012] (SWS CSM p. 20).

Jobs can be queued in configured CsmQueues [SWS_Csm_00940]. The queues sort by job priority [SWS_Csm_00944]. Each queue is assigned to exactly one channel, and its size is configurable (SWS CSM p. 29). The specification explicitly regulates two cases (SWS CSM p. 21):

  • If the job is already ACTIVE, the service call directly calls CryIf_ProcessJob and passes through its return value.
  • If a job must be queued and the queue is full, it is rejected with CRYPTO_E_BUSY.

For synchronous jobs, the specification recommends a queue size of 0. However, synchronous and asynchronous jobs may use the same channel. For an active job, the CSM assumes that the caller intends to continue, for example with "update". The plausibility check is then located in the driver (SWS CSM p. 29).

Synchronous and asynchronous processing in the cycle of Csm_MainFunction

The job configuration specifies whether a data service operates synchronously or asynchronously. This is described, for example, for Csm_Hash and Csm_Encrypt [SWS_Csm_00980], [SWS_Csm_00984]. The choice is encoded in Crypto_ProcessingType [SWS_Csm_01049].

If an asynchronous interface is configured, Csm_MainFunction is called cyclically. It checks the queues and passes jobs to CryIf [SWS_Csm_00479] (SWS CSM p. 21). For multicore, the following applies:

  • For each configured CsmMainFunction instance, one Csm_MainFunction_<shortName> exists [SWS_Csm_00479].
  • Csm_Init may be provided per partition [SWS_Csm_00646].
  • Queues are processed in the MainFunction referenced via CsmQueueMainFunctionRef (SWS CSM p. 36).

The result is returned via a callback chain. CryIf reports completion with Csm_CallbackNotification(job, result) [SWS_Csm_00970]. If the FINISH bit is set, the CSM calls the configured callback [SWS_Csm_01044]. Its signature is <Csm_ApplicationCallbackNotification>(jobId, result), and its name is configurable [SWS_Csm_00971]. SW-Cs receive the notification via port CallbackNotification_{Job} [SWS_Csm_00934], [SWS_Csm_00928]. Lengths and verification results are returned asynchronously via Csm_LengthPtr and Csm_VerifyResultPtr [SWS_Csm_91045], [SWS_Csm_91046].

Sequence diagram: Asynchronous call with acceptance, forwarding in the MainFunction cycle, and callback cascade to the application. Sources: SWS CSM p. 164, [SWS_Csm_00479], [SWS_Csm_00970], [SWS_Csm_01044], [SWS_Csm_00971]

Streaming, single call, and the lifecycle of a job

The parameter mode is a flag field composed of "START", "UPDATE", and "FINISH". The flags can be combined so that a single call executes multiple operations [SWS_Csm_01039]. Crypto_OperationModeType defines the following values [SWS_Csm_01029]:

  • CRYPTO_OPERATIONMODE_START: resets the job.
  • …_UPDATE: calculates intermediate results.
  • …_STREAMSTART: start and update in a single call.
  • …_FINISH: completes the calculation.

With FINISH, the application can complete a calculation [SWS_Csm_01046]. START and FINISH without UPDATE results in E_NOT_OK [SWS_Csm_01045]. Streaming is suitable for very large data because UPDATE can be called any number of times. The single-call approach saves calling overhead for small data (EXP Crypto Services p. 12).

The job has two states [SWS_Csm_01028]:

  • CRYPTO_JOBSTATE_IDLE applies after Csm_Init and after a completed FINISH.
  • CRYPTO_JOBSTATE_ACTIVE applies after START or UPDATE.

The actual state transitions are performed by the Crypto Driver (SWS CSM p. 22).

A running work context can be saved with Csm_SaveContextJob and restored with Csm_RestoreContextJob [SWS_Csm_91063], [SWS_Csm_91064]. Key elements do not belong to the context. In two cases, the call returns immediately with E_NOT_OK: if the job is IDLE or if it is currently being processed by the driver (SWS CSM p. 35).

Keys: elements, validity, generation, and exchange

A key consists of one or more key elements [SWS_Csm_00954]. Their IDs are predefined, such as CRYPTO_KE_MAC_KEY (1), CRYPTO_KE_CIPHER_IV (5), and CRYPTO_KE_KEYGENERATE_SEED (16) [SWS_Csm_01022]. Key services only offer the function Csm_<Service>() [SWS_Csm_00950]. The following functions operate synchronously:

  • Csm_KeyElementSet [SWS_Csm_00957]
  • Csm_KeyElementGet [SWS_Csm_00959]
  • Csm_KeyCopy [SWS_Csm_01034]
  • Csm_KeyElementCopy [SWS_Csm_00969]
  • Csm_KeyElementCopyPartial [SWS_Csm_91025]

Later document versions additionally require: After a key management function, the CSM does not process any new jobs from the queue until the next MainFunction (SWS CSM p. 60, R24-11/R25-11). For R20-11, the payload contains no requirement on this.

The key status is CRYPTO_KEYSTATUS_INVALID or CRYPTO_KEYSTATUS_VALID [SWS_Csm_91102]. It is controlled using these functions:

  • Csm_KeySetValid [SWS_Csm_00958]
  • Csm_KeySetInvalid [SWS_Csm_91075]
  • Csm_KeyGetStatus [SWS_Csm_91047], which calls CryIf_KeyGetStatus (SWS CSM p. 63)

The job-based variants Csm_JobKeySetValid and Csm_JobKeySetInvalid run synchronously or asynchronously depending on the job configuration. In R20-11, they accept jobId and keyId [SWS_Csm_91027], [SWS_Csm_91002]. The later document citation only shows jobId (SWS CSM p. 76). The R20-11 signature is decisive.

State diagram: Key status and the functions that change it. Interpretation: The transition by Csm_KeyElementSet follows from the example in the type description. Sources: [SWS_Csm_91102], [SWS_Csm_00958], [SWS_Csm_91075], [SWS_Csm_91027], [SWS_Csm_91002]

Csm_KeyGenerate generates key material [SWS_Csm_00955]. The result ends up in CRYPTO_KE_KEYGENERATE_KEY, and the algorithm comes from CRYPTO_KE_KEYGENERATE_ALGORITHM. The application must store the seed in CRYPTO_KE_KEYGENERATE_SEED beforehand, for instance from Csm_RandomGenerate [SWS_Csm_01543]. The entropy of the seed determines the key quality (SWS CSM p. 67). How random number generators are seeded is project-specific. However, it must occur before the first request (SWS CSM p. 59). Csm_RandomSeed calls CryIf_RandomSeed [SWS_Csm_01051], [SWS_Csm_01052]. Csm_KeyDerive calls CryIf_KeyDerive [SWS_Csm_00956], [SWS_Csm_01018].

Sequence diagram: From the random value via the seed to the generated and verified key. Interpretation: Setting to valid before Csm_KeyGenerate is derived. Csm_KeyGenerate reports CRYPTO_E_KEY_NOT_VALID if the key is invalid. Sources: [SWS_Csm_01543], [SWS_Csm_00957], [SWS_Csm_00955], [SWS_Csm_91047], SWS CSM p. 67

There are two steps for the Diffie-Hellman key exchange, including on elliptic curves. Csm_KeyExchangeCalcPubVal calculates its own public value. Csm_KeyExchangeCalcSecret calculates the shared secret from the partner's public value [SWS_Csm_00966], [SWS_Csm_00967]. Both are also available as job variants [SWS_Csm_91031], [SWS_Csm_91032]. The elements CRYPTO_KE_KEYEXCHANGE_BASE, …_PRIVKEY, and …_OWNPUBKEY hold the key material (SWS CSM p. 70).

Interface types, data types, and configuration

In addition to the C functions in Csm.h, the RTE generates job-related ports:

  • CsmJob_{Job} for synchronous use with CRYPTO_USE_PORT, fixed to CRYPTO_OPERATIONMODE_SINGLECALL [SWS_Csm_91023].
  • The asynchronous variant for CRYPTO_USE_PORT_OPTIMIZED [SWS_Csm_91062].
  • Key ports CsmKey_{Key} [SWS_Csm_01042], [SWS_Csm_01905].
  • Context ports [SWS_Csm_91105], [SWS_Csm_91106].

For each service, there is a synchronous interface such as CsmHash_{PrimitiveCfg} and an asynchronous one such as CsmHash [SWS_Csm_00946], [SWS_Csm_91051]. The buffer types are uint8 arrays from Rte_Csm_Type.h. Their size results from configured maximum lengths, such as for Csm_HashDataType_{Crypto}, Csm_HashResultType_{Crypto}, and Csm_MacGenerateDataType_{Crypto} [SWS_Csm_01920], [SWS_Csm_00912], [SWS_Csm_00935].

The content of Csm_ConfigType is implementation-specific [SWS_Csm_01085]. The configPtr of Csm_Init must be a null pointer (SWS CSM p. 48). The most important configuration contents:

  • A CsmJob carries CsmJobId, CsmJobPriority, CsmJobPrimitiveRef, and CsmJobInterfaceUsePort (SWS CSM p. 166).
  • Primitives are implemented as constant Crypto_PrimitiveInfoType structures (SWS CSM p. 23) [SWS_Csm_01011].
  • A CsmKey references a CryIf key via CsmKeyRef (SWS CSM p. 161).
  • A CsmQueue buffers jobs when hardware is busy and determines the channel (SWS CSM p. 164).

With Crypto_JobRedirectionInfoType, inputs and outputs can be redirected to key elements [SWS_Csm_91026], [SWS_Csm_91024].

Behavior in the event of an error

Services report their result as Std_ReturnType or Crypto_ResultType. In addition to E_OK and E_NOT_OK, there are specific codes such as CRYPTO_E_BUSY, CRYPTO_E_ENTROPY_EXHAUSTED, and CRYPTO_E_KEY_NOT_VALID [SWS_Csm_91044], [SWS_Csm_91043]. For verification services, E_OK only means that the request was successful. The actual verdict is in verifyPtr as CRYPTO_E_VER_OK or CRYPTO_E_VER_NOT_OK [SWS_Csm_01050], [SWS_Csm_01024].

If development error detection is active, the CSM reports the following errors to DET [SWS_Csm_91004]:

  • CSM_E_PARAM_POINTER
  • CSM_E_PARAM_HANDLE
  • CSM_E_UNINIT
  • CSM_E_INIT_FAILED, in case of failed initialization (SWS CSM p. 48)
  • CSM_E_PROCESSING_MODE

A queue overflow is the runtime error CSM_E_QUEUE_FULL [SWS_Csm_01089].

If Csm_KeyElementSet fails, the state of the element is unknown. The application can check it with Csm_KeyGetStatus (SWS CSM p. 62) [SWS_Csm_00957]. Derivation and copy can fail with CRYPTO_E_KEY_READ_FAIL, …_WRITE_FAIL, …_SIZE_MISMATCH, or CRYPTO_E_KEY_EMPTY [SWS_Csm_00956], [SWS_Csm_00969].

Csm_CancelJob cancels asynchronous or streaming jobs [SWS_Csm_00968]. The return values mean:

  • E_OK: The job is removed.
  • CRYPTO_E_JOB_CANCELED: Cancellation only occurs at the next suitable step and is reported via a negative completion callback.

The later document citation adds: For synchronous jobs, Csm_CancelJob reports CSM_E_PROCESSING_MODE. The CSM removes the job from the queue or calls CryIf_CancelJob (SWS CSM p. 80).
