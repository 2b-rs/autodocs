Controls startup, shutdown, sleep phases, and wakeup sources of the ECU in interaction with BswM.

The ECU State Manager controls the lifecycle of a Classic ECU. It initializes the basic software up to the OS start, transitions the ECU into the shutdown targets SLEEP, RESET, or OFF, and manages the wakeup sources including validation [SWS_EcuM_04136]. Hardware-related steps are handled by the integration code via callouts. EcuM arbitrates the RUN and POST_RUN requests of the users, but BswM decides on the state transitions and reports them back via EcuM_SetState [SWS_EcuM_04116]. The most important constraint is that no wakeup event must be lost during the SLEEP phase.

In the Classic Platform, the ECU State Manager (EcuM) is responsible for startup, shutdown, and sleep phases of the ECU. EcuM_Init executes the StartPreOS sequence with Init Blocks 0 and 1. In doing so, EcuM selects and checks the post-build configuration and finally calls StartOS. After that, EcuM_StartupTwo starts SchM and BswM [SWS_EcuM_02684] [SWS_EcuM_02906] [SWS_EcuM_02932]. The integration code provides hardware-related steps as callouts, for example EcuM_AL_DriverInitZero [SWS_EcuM_02905].

State diagram: The ECU transitions through STARTUP, UP, SHUTDOWN, and SLEEP. From SLEEP, it returns to UP via WakeupRestart. Sources: RS ModeManagement p. 15, [SWS_EcuM_91005], [SWS_EcuM_02963]

EcuM does not decide on state transitions itself. It collects the RUN and POST_RUN requests of the configured users and reports the result to BswM. It applies its state changes via EcuM_SetState and forwards them to the RTE [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04116] SWS EcuM p. 103. EcuM_SelectShutdownTarget only stores the target SLEEP, RESET, or OFF for later [SWS_EcuM_02585]. During shutdown, OffPreOS de-initializes BswM and SchM, checks wakeup events, and terminates the OS. The shutdown hook then calls EcuM_Shutdown, which ends with EcuM_AL_Reset or EcuM_AL_SwitchOff [SWS_EcuM_03021] [SWS_EcuM_04074] [SWS_EcuM_04075].

The SLEEP phase begins with EcuM_GoDownHaltPoll. First, GoSleep activates the wakeup sources of the sleep mode. This is followed either by Halt with RAM hash check or Poll with a loop over EcuM_SleepActivity and EcuM_CheckWakeup. WakeupRestart concludes the sequence with EcuM_AL_DriverRestart [SWS_EcuM_91002] [SWS_EcuM_02389] [SWS_EcuM_02863] [SWS_EcuM_03020] [SWS_EcuM_02963]. In this phase, no wakeup event must be lost [SWS_EcuM_02188].

Wakeup sources are individual bits in EcuM_WakeupSourceType and each have one of the states NONE, PENDING, VALIDATED, or EXPIRED [SWS_EcuM_04040] [SWS_EcuM_04091]. Drivers report events with EcuM_SetWakeupEvent. If validation is configured, EcuM starts a timeout. Only a EcuM_ValidateWakeupEvent before its expiration leads to VALIDATED; if a channel reference is configured, ComM is then also informed. Otherwise, the source becomes EXPIRED [SWS_EcuM_02709] [SWS_EcuM_02645] [SWS_EcuM_04082].

Activity diagram: A wakeup event is validated immediately or remains PENDING until a confirmation arrives or the timeout expires. Sources: SWS EcuM p. 63, [SWS_EcuM_02566], [SWS_EcuM_04082]

In case of error, EcuM calls the callout EcuM_ErrorHook if the configuration is inconsistent or the RAM check fails [SWS_EcuM_04033] [SWS_EcuM_91003]. It reports development errors, such as multiple requests or unknown wakeup sources, to DET [SWS_EcuM_03024] [SWS_EcuM_02867].

Role and System Boundary of the ECU State Manager

In the Classic Platform, the ECU State Manager (EcuM) defines the framework for the ECU lifecycle. It initializes the basic software up to the start of the operating system. Thereafter, it guides the ECU in a controlled manner into one of the shutdown targets SLEEP, RESET, or OFF [SWS_EcuM_04136]. EcuM_StateType defines its states: STARTUP, RUN, POST_RUN, SHUTDOWN, and SLEEP [SWS_EcuM_91005]. It reports them to the SW-Cs via the mode declaration group EcuM_Mode, whose initial mode is STARTUP [SWS_EcuM_04107] [SWS_EcuM_04132].

State diagram: The ECU transitions through STARTUP, UP, SHUTDOWN, and SLEEP. From SLEEP, it returns to UP via WakeupRestart; after a hardware reset or power cycle, it restarts in STARTUP. Sources: RS ModeManagement p. 15, [SWS_EcuM_91005], [SWS_EcuM_02963], [SWS_EcuM_04001]

EcuM does not decide on the state transitions itself. It has no state machine of its own, only arbitrates the requests, and leaves the transitions to the BSW Mode Manager (BswM) SWS EcuM p. 103. It delegates hardware-related and project-specific steps to callouts of the integration code, which are provided via EcuM_Externals.h. Examples are EcuM_AL_DriverInitZero and EcuM_AL_SwitchOff [SWS_EcuM_02905] [SWS_EcuM_02920]. The interfaces of neighboring modules are listed in the tables of imported functions, such as BswM_EcuM_CurrentWakeup, Can_Init, and Det_ReportError [SWS_EcuM_02858] [SWS_EcuM_02859].

Context diagram: EcuM is positioned between SW-Cs, BswM, integration code, OS, MCAL drivers, and ComM. BswM decides on transitions; the integration code executes the hardware steps. Sources: SWS EcuM p. 34, [SWS_EcuM_02858], [SWS_EcuM_04135]

Startup: StartPreOS, StartPostOS, and Configuration Data

Prior to EcuM_Init, EcuM requires only minimal MCU initialization: a stack is set up and C variables are initialized SWS EcuM p. 39. EcuM_Init executes the StartPreOS sequence and does not return because it calls StartOS [SWS_EcuM_02811] [SWS_EcuM_02684]. In doing so, all modules required for starting the OS are initialized [SWS_EcuM_02603].

Init Block 0 (EcuM_AL_DriverInitZero) prepares the loading of post-build data. Therefore, it may only use modules configured at pre-compile or link time [SWS_EcuM_02905]. Subsequently, EcuM_DeterminePbConfiguration provides a pointer to EcuM_ConfigType. This structure references the configurations of all further BSW modules [SWS_EcuM_02906] [SWS_EcuM_02801]. It contains a variant identifier and a hash. EcuM checks the hash against ECUM_CONFIGCONSISTENCY_HASH for all post-build configurable modules before the first of them is initialized [SWS_EcuM_02794] [SWS_EcuM_02798] [SWS_EcuM_02796].

Init Block 1 (EcuM_AL_DriverInitOne) initializes the drivers after a power-on reset, including the MCU [SWS_EcuM_02907] SWS EcuM p. 146. EcuMDriverInitListZero and EcuMDriverInitListOne define the sequence in both blocks. Each init function receives its parameters from the associated EcuMModuleService container [SWS_EcuM_02559] [SWS_EcuM_02730]. EcuM translates the reset reason of the Mcu driver into a wakeup source and memorizes it. If the reason cannot be determined, it sets ECUM_WKSOURCE_RESET [SWS_EcuM_02623] [SWS_EcuM_02601]. If EcuMResetLoopDetection is set, EcuM calls the callout EcuM_LoopDetection at every start [SWS_EcuM_04137].

Sequence diagram: EcuM_Init passes through Init Block 0, the selection and checking of the configuration, Init Block 1, and the reset evaluation up to StartOS. After that, EcuM_StartupTwo starts SchM and BswM. Sources: SWS EcuM p. 38, SWS EcuM p. 78, [SWS_EcuM_02684], [SWS_EcuM_02932]

After the OS start, a task that was started directly as a result of StartOS calls EcuM_StartupTwo [SWS_EcuM_02806]. This function executes StartPostOS: it initializes and starts SchM and calls BswM_Init [SWS_EcuM_02932] SWS EcuM p. 42. BswM handles further initializations via the generated functions EcuM_AL_DriverInitBswM_<x> [SWS_EcuM_04114].

On multicore ECUs, one EcuM instance runs per core, and the master EcuM starts the remaining cores. Init Blocks 0 and 1 run on each core, but only initialize its MCAL modules there. SchM, OS, and all core-local BswM are started on each core [SWS_EcuM_04145] [SWS_EcuM_04093] [SWS_EcuM_04014] SWS EcuM p. 71.

RUN and POST_RUN: User Requests and Arbitration with BswM

If EcuMModeHandling is active, users can request and release RUN and POST_RUN [SWS_EcuM_04115] [SWS_EcuM_04130]. EcuM_RequestRUN, EcuM_ReleaseRUN, EcuM_RequestPOST_RUN, and EcuM_ReleasePOST_RUN serve this purpose. All four expect a configured user ID of type EcuM_UserType [SWS_EcuM_04124] [SWS_EcuM_04127] [SWS_EcuM_04128] [SWS_EcuM_04129]. EcuM tracks requests per user, and a user cannot nest them. It maintains RUN and POST_RUN requests in separate variables [SWS_EcuM_04126] [SWS_EcuM_04125] SWS EcuM p. 116. SW-Cs access these services via port StateRequest_{UserName} [SWS_EcuM_04135].

EcuM reports the first RUN or POST_RUN request to BswM with BswM_EcuM_RequestedState(ECUM_STATE_APP_RUN, ECUM_RUNSTATUS_REQUESTED). It reports the last release of RUN or POST_RUN with the respective state and ECUM_RUNSTATUS_RELEASED [SWS_EcuM_04144] [SWS_EcuM_04117] [SWS_EcuM_04119]. BswM evaluates its rules and sets the new state using EcuM_SetState. EcuM then indicates the matching mode to the RTE and, after its feedback, reports BswM_EcuM_CurrentState [SWS_EcuM_04122] [SWS_EcuM_04116] [SWS_EcuM_04143]. The Mode Management Guide shows suitable BswM rules, for example the transition to POST_RUN as soon as RUN is released Mode-Management-Guide p. 34.

Sequence diagram: EcuM arbitrates the user requests and reports the result to BswM. BswM returns the state via EcuM_SetState, and EcuM forwards it to the RTE. Sources: [SWS_EcuM_04144], [SWS_EcuM_04117], [SWS_EcuM_04116], [SWS_EcuM_04143]

Shutdown Targets and Shutdown via OffPreOS and OffPostOS

EcuM_SelectShutdownTarget only stores the target and mode for the subsequent SHUTDOWN or SLEEP phase and does not initiate anything itself [SWS_EcuM_02822] [SWS_EcuM_00624] [SWS_EcuM_02585]. For target SLEEP, the mode parameter selects a configured sleep mode, and for target RESET, a reset mode. For OFF, it is ignored [SWS_EcuM_02979] [SWS_EcuM_02185]. The reset modes include at least Mcu_PerformReset, WdgM_PerformReset, and toggling an I/O pin [SWS_EcuM_04005] [SWS_EcuM_04044]. The cause of a shutdown is recorded with EcuM_SelectShutdownCause [SWS_EcuM_04007] [SWS_EcuM_04050]. EcuM_GetLastShutdownTarget returns the target from which wakeup or startup last occurred. This value remains unchanged until the next shutdown [SWS_EcuM_02156].

The SHUTDOWN phase ends either in OFF or in RESET [SWS_EcuM_03022]. When the target is set is typically determined by BswM SWS EcuM p. 66. In OffPreOS, BswM and SchM are de-initialized and wakeup events are checked. If events are pending, RESET is set as the target. The final action is ShutdownOS [SWS_EcuM_03021] [SWS_EcuM_02952] SWS EcuM p. 49.

Subsequently, the shutdown hook calls EcuM_Shutdown, which does not return. After EcuM_OnGoOffTwo, EcuM_AL_Reset follows for target RESET and EcuM_AL_SwitchOff follows for target OFF [SWS_EcuM_02953] [SWS_EcuM_02917] [SWS_EcuM_04074] [SWS_EcuM_04075]. Interpretation: For RESET and OFF as well, BswM is likely to trigger the phase via EcuM_GoDownHaltPoll, as its return description distinguishes according to the shutdown target [SWS_EcuM_91002].

Sequence diagram: OffPreOS de-initializes BswM and SchM, checks the wakeup events, and terminates the OS. OffPostOS then branches into reset or shutdown depending on the shutdown target. Sources: SWS EcuM p. 49, SWS EcuM p. 49, [SWS_EcuM_02953], [SWS_EcuM_91002]

SLEEP Phase: GoSleep, Halt or Poll, and WakeupRestart

If SLEEP is selected as the target, EcuM_GoDownHaltPoll initiates the SLEEP phase. The caller must have previously set the appropriate target [SWS_EcuM_91002] SWS EcuM p. 54. In GoSleep, EcuM activates all wakeup sources from EcuMWakeupSourceMask of the target sleep mode via EcuM_EnableWakeupSources. On multicore ECUs, it additionally acquires the core-specific resource RES_AUTOSAR_ECUM. Unlike during shutdown, the OS remains active [SWS_EcuM_02389] [SWS_EcuM_03010] [SWS_EcuM_02951]. No wakeup event must be lost. If one has already occurred during GoSleep, Halt and Poll are skipped [SWS_EcuM_02188].

Sleep modes that halt the microcontroller execute the Halt sequence. Before that, EcuM calls EcuM_GenerateRamHash, and afterwards EcuM_CheckRamHash [SWS_EcuM_02960] [SWS_EcuM_02863]. In contrast, sleep modes with reduced clock speed use the Poll sequence. It calls EcuM_SleepActivity and EcuM_CheckWakeup in a blocking loop until an event is reported as pending or validated [SWS_EcuM_02962] [SWS_EcuM_03020]. In R20-11, EcuM_CheckWakeup is still a callout. Only starting with R21-11 is this callout named EcuM_CheckWakeupHook [SWS_EcuM_02929] SWS EcuM p. 145.

A wakeup event leads to the WakeupRestart sequence [SWS_EcuM_02963] SWS EcuM p. 56:

  1. The MCU returns to normal mode.
  2. EcuM_DisableWakeupSources disables the currently pending wakeup sources; all others remain armed [SWS_EcuM_02922].
  3. EcuM_AL_DriverRestart re-initializes the affected drivers [SWS_EcuM_02923].
  4. The scheduler is released again.

If a hardware reset or power cycle occurs during sleep, the ECU restarts in STARTUP instead [SWS_EcuM_04001].

Sequence diagram: GoSleep prepares the wakeup sources, Halt or Poll implement sleep, and WakeupRestart leads back to the UP state. Sources: SWS EcuM p. 52, SWS EcuM p. 85, SWS EcuM p. 87, SWS EcuM p. 58

Optionally, EcuM maintains a clock that counts the seconds since the battery was connected [SWS_EcuM_04069]. Each user can set at most one wakeup alarm. The master alarm always corresponds to the earliest user alarm [SWS_EcuM_04070] [SWS_EcuM_04072]. EcuM_SetAbsWakeupAlarm rejects a later point in time with ECUM_E_EARLIER_ACTIVE and one that has already passed with ECUM_E_PAST [SWS_EcuM_04059] [SWS_EcuM_04060]. When leaving SLEEP, EcuM discards all alarms [SWS_EcuM_04009].

Wakeup Sources: States, Validation, and Querying

EcuM manages up to 32 wakeup sources as a bitmask of type EcuM_WakeupSourceType. Five bits are predefined, including ECUM_WKSOURCE_POWER and ECUM_WKSOURCE_RESET. Further sources are assigned bits 5 through 31 via EcuMWakeupSourceId [SWS_EcuM_04040] [SWS_EcuM_02165] [SWS_EcuM_02166] SWS EcuM p. 63. Each source is in one of the states NONE, PENDING, VALIDATED, or EXPIRED [SWS_EcuM_04091] [SWS_EcuM_04041]. EcuM reports every state transition to BswM as a mode request [SWS_EcuM_04003].

State diagram: A wakeup source transitions from NONE via PENDING to VALIDATED or EXPIRED. Every state transition is reported to BswM, and EcuM_ClearWakeupEvent resets the source to NONE. Sources: SWS EcuM p. 60, [SWS_EcuM_04091], [SWS_EcuM_02683]

A driver reports a detected event exactly once with EcuM_SetWakeupEvent SWS EcuM p. 71. The function may also be called from interrupt context and from OS-free context. It ORs the passed bits into the pending variable. It ignores sources that do not belong to the selected sleep mode [SWS_EcuM_02826] [SWS_EcuM_02171] [SWS_EcuM_01117] [SWS_EcuM_04138].

If the event must be validated, EcuM starts a source-specific timeout according to EcuMValidationTimeout. If the same source is reported again, the timeout does not restart [SWS_EcuM_02975] [SWS_EcuM_02565] [SWS_EcuM_02709] [SWS_EcuM_02712]. If no validation is configured for a source, EcuM_SetWakeupEvent simultaneously acts like EcuM_ValidateWakeupEvent. The five predefined sources are never validated [SWS_EcuM_02566] [SWS_EcuM_02625].

Validation itself runs in EcuM_MainFunction, which calls the callout EcuM_CheckValidation for this purpose [SWS_EcuM_02539] [SWS_EcuM_02925] SWS EcuM p. 64. EcuM_ValidateWakeupEvent has the following effect [SWS_EcuM_02710] [SWS_EcuM_04078] [SWS_EcuM_04079] [SWS_EcuM_02645] [SWS_EcuM_04140]:

  • It stops the timeout and sets the bits in the validated variable.
  • It reports ECUM_WKSTATUS_VALIDATED to BswM.
  • If a channel or PNC is configured, it calls ComM_EcuM_WakeUpIndication or ComM_EcuM_PNCWakeUpIndication, respectively.

If the timeout expires, the main function sets the expired bit and reports ECUM_WKSTATUS_EXPIRED [SWS_EcuM_04081] [SWS_EcuM_04082]. In the RUN state, validation only takes effect for communication channels [SWS_EcuM_02790] [SWS_EcuM_02791].

Activity diagram: For sources without validation requirement, an event is validated immediately. For the remaining sources, it remains PENDING until EcuM_ValidateWakeupEvent arrives or the timeout expires and the source becomes EXPIRED. Sources: SWS EcuM p. 63, SWS EcuM p. 78, [SWS_EcuM_02566], [SWS_EcuM_04082]

EcuM_GetPendingWakeupEvents, EcuM_GetValidatedWakeupEvents, and EcuM_GetExpiredWakeupEvents query the current state. EcuM_ClearWakeupEvent clears the passed bits from all three variables [SWS_EcuM_01156] [SWS_EcuM_02533] [SWS_EcuM_04076] [SWS_EcuM_02683].

Some wakeup sources have an integrated power supply, so their wakeup acts like a power-on reset. For them, EcuM_StartCheckWakeup starts a CheckWakeupTimer that prevents premature shutdown. EcuM_SetWakeupEvent or EcuM_EndCheckWakeup stops the timer again [SWS_EcuM_04096] [SWS_EcuM_04098] [SWS_EcuM_02927] SWS EcuM p. 70.

Behavior in the event of an error

EcuM reports unrecoverable errors via the callout EcuM_ErrorHook with the associated error code [SWS_EcuM_04033] [SWS_EcuM_02904]. In R20-11, there are two codes for this [SWS_EcuM_91003] [SWS_EcuM_02987]:

  • ECUM_E_CONFIGURATION_DATA_INCONSISTENT in case of inconsistent post-build data.
  • ECUM_E_RAM_CHECK_FAILED if the RAM check after wakeup fails.

If an OS call fails, EcuM maintains the requested state and likewise calls the ErrorHook [SWS_EcuM_04139]. A dedicated code ECUM_E_OS_CALL_FAILED and the note that the hook does not return are only included in a later version of the specification SWS EcuM p. 102. EcuM ignores errors during initialization, for example the return values of init functions [SWS_EcuM_02980].

When development error detection is enabled, all functions check their parameters and execution conditions. ECUM_E_UNINIT, ECUM_E_SERVICE_DISABLED, ECUM_E_PARAM_POINTER, and ECUM_E_INVALID_PAR are available for this purpose [SWS_EcuM_03009]. EcuM reports further cases to DET:

  • Multiple requests by the same user as ECUM_E_MULTIPLE_RUN_REQUESTS [SWS_EcuM_03024] [SWS_EcuM_03025].
  • Releases without a matching request as ECUM_E_MISMATCHED_RUN_RELEASE [SWS_EcuM_03023] [SWS_EcuM_03026].
  • Unknown wakeup sources as ECUM_E_UNKNOWN_WAKEUP_SOURCE; the internal variable remains unchanged in this case [SWS_EcuM_02867] [SWS_EcuM_02868].
  • Invalid states passed to EcuM_SetState as ECUM_E_STATE_PAR_OUT_OF_RANGE [SWS_EcuM_04123].

If a wakeup event occurs during shutdown, EcuM completes the shutdown and restarts immediately [SWS_EcuM_02756]. If the ECU cannot de-energize itself in EcuM_AL_SwitchOff, a reset is an appropriate response [SWS_EcuM_02920] SWS EcuM p. 141.

EcuM_CheckRamHash function

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

uint8 EcuM_CheckRamHash (void);
