Role in the memory stack: Fee between MemIf and flash driver

The module Fee (Flash EEPROM Emulation) maps a block-wise addressed, EEPROM-like data storage onto flash memory. The NVRAM Manager accesses Fee via the Memory Abstraction Interface. Downwards, Fee in R20-11 relies on the flash driver Fls: Its services such as Fls_Read, Fls_Write, Fls_Erase, Fls_Cancel, and Fls_SetMode are in the list of required interfaces [SWS_Fee_00105]. Fee also imports Fls_AddressType and Fls_LengthType as well as the types MemIf_StatusType, MemIf_JobResultType, and MemIf_ModeType [SWS_Fee_00084]. The write sequence of the specification shows the chain NvM → MemIf → Fee → Fls with a cyclic BSW task (SWS Fee Fig. 7 p. 40, SWS Fee Fig. 6 p. 48).

Release note: Newer specification versions replace Fls with MemAcc and Mem drivers. The module overview with MemAcc and the list of optional interfaces with MemAcc_BlankCheck therefore do not apply to R20-11 (SWS Fee Fig. 1.1 p. 9, SWS Fee p. 40). In R20-11, Det_ReportError and Fls_BlankCheck are the optional interfaces [SWS_Fee_00104].

Callbacks do not run via MemIf. Fee provides the callbacks Fee_JobEndNotification and Fee_JobErrorNotification to the lower layers [SWS_Fee_00095] [SWS_Fee_00096]. Fee itself calls NvM_JobEndNotification and NvM_JobErrorNotification, respectively [SWS_Fee_00098] [SWS_Fee_00099]. The MemIf does not define its own callbacks because the NVRAM Manager provides them for the abstraction modules (SWS MemIf p. 24).

Context diagram: Fee is located between MemIf and Fls; EcuM initializes the module, the BSW Scheduler drives it cyclically, and callbacks go directly to the NvM. Sources: [SWS_Fee_00104], [SWS_Fee_00105], [SWS_Fee_00098], SWS Fee Fig. 9.1 p. 42, SWS Fee Fig. 7 p. 40

Startup: from Fee_Init via MEMIF_BUSY_INTERNAL to MEMIF_IDLE

Fee_Init receives a pointer to the selected configuration set and is specified as asynchronous in R20-11 [SWS_Fee_00085]. The corresponding diagram shows the sequence: The EcuM calls Fee_Init, and the module transitions to MEMIF_BUSY_INTERNAL. In this state, it can already accept jobs. The BSW Scheduler then cyclically calls Fee_MainFunction until internal management is completed (SWS Fee Fig. 9.1 p. 42). An older diagram (R18-10) additionally features a synchronous variant: There, initialization already ends in Fee_Init, and the status is directly MEMIF_IDLE (SWS Fee Fig. 4 p. 47).

Fee_MainFunction marks the completion. If no internal management operations are necessary or if they have completed, it sets the status from MEMIF_BUSY_INTERNAL to MEMIF_IDLE. The management can take several calls in the process (SWS Fee p. 38). The main function is called directly by the Basic Software Scheduler. It has neither parameters nor a return value and is not reentrant (SWS Fee p. 40, [SWS_Fee_00097]).

Sequence diagram: After the asynchronous Fee_Init, only Fee_MainFunction completes the initialization; the synchronous variant originates from an older diagram. Sources: [SWS_Fee_00085], SWS Fee Fig. 9.1 p. 42, SWS Fee Fig. 4 p. 47, SWS Fee p. 38

Fee_GetStatus returns one of four values [SWS_Fee_00090]:

  • MEMIF_UNINIT: Before initialization.
  • MEMIF_IDLE: Neither an upper-layer job nor internal management is running.
  • MEMIF_BUSY: An upper-layer job is being processed.
  • MEMIF_BUSY_INTERNAL: An internal management operation is running, such as a reorganization (garbage collection).

The state definitions are in SWS Fee p. 30.

State diagram: Jobs are accepted from MEMIF_IDLE and MEMIF_BUSY_INTERNAL; MEMIF_BUSY ends with the end of the job or with Fee_Cancel. Sources: [SWS_Fee_00090], SWS Fee p. 30, SWS Fee p. 28, SWS Fee p. 29, SWS Fee p. 38

Logical blocks, virtual addresses, and block correctness

All job services address a logical block via BlockNumber. At the same time, this value designates the start address of the block [SWS_Fee_00087] [SWS_Fee_00088]. The memory mapping diagram divides the virtual address into a 16-bit block number and a 16-bit block offset; in virtual space, the pages are 64 KBytes in size. Physically, the blocks occupy whole flash pages, so that an unused remainder can occur (SWS Fee Fig. 3 p. 20). The following table reproduces the example from the diagram:

BlockUser dataOccupied pages (8 bytes each)Internal remainder
#132 bytes40 bytes
#5100 bytes134 bytes
#1738 bytes52 bytes

Reading and writing differ in granularity:

  • Fee_Read calculates the read address from the block start and offset. Offset and length may take any values within their value range (SWS Fee p. 26).
  • Fee_Write has no offset parameter; every write process begins at offset zero (SWS Fee p. 28).

The underlying requirement justifies the write rule with alignment to virtual 64K boundaries: A block is only erased or written completely or not at all (RS MemHwAb p. 24).

Regardless of the content, Fee maintains internal correctness information for each block. At the start of a write process, the block is considered "corrupted", and after successful completion, "not corrupted" again. This information must be strictly separated from the validity set by Fee_InvalidateBlock (SWS Fee p. 21, [SWS_Fee_00092]). Interpretation: A block marked in this way is likely reported as MEMIF_BLOCK_INCONSISTENT during reading. According to the return value description, this value represents inconsistent, possibly corrupt blocks [SWS_Fee_00091].

Asynchronous jobs: Acceptance, processing in Fee_MainFunction, feedback

Fee_Read, Fee_Write, Fee_InvalidateBlock, and Fee_EraseImmediateBlock are asynchronous and non-reentrant. Their return value only indicates whether the job was accepted (E_OK) or not (E_NOT_OK) [SWS_Fee_00087] [SWS_Fee_00088] [SWS_Fee_00092] [SWS_Fee_00094]. In status MEMIF_IDLE or MEMIF_BUSY_INTERNAL, Fee accepts the job: It accepts the parameters, initiates the job, sets the status to MEMIF_BUSY and the job result to MEMIF_JOB_PENDING, and returns with E_OK (SWS Fee p. 28, SWS Fee p. 26). In MEMIF_UNINIT or MEMIF_BUSY, the job is likely rejected with E_NOT_OK; the rule in question is only touched upon in the payload (SWS Fee p. 28).

The actual work is performed by Fee_MainFunction. It asynchronously processes read, write, erase, and invalidation jobs as well as internal management operations (SWS Fee p. 38). For read jobs, it checks whether the upper layer has invalidated the block. If this is the case, it sets the job result to MEMIF_BLOCK_INVALID and calls the error notification, if configured. If Fls_BlankCheck is configured in the flash driver, Fee_Read calls this function beforehand. In this way, ECC errors, for example, can be avoided when reading erased but unprogrammed cells [SWS_Fee_00187].

Activity diagram: A read job is accepted only in MEMIF_IDLE or MEMIF_BUSY_INTERNAL; invalidated blocks end with MEMIF_BLOCK_INVALID, and a configured blank check precedes reading. Sources: [SWS_Fee_00087], [SWS_Fee_00187], SWS Fee p. 26, SWS Fee p. 38

At the end of a job, the driver calls Fee_JobEndNotification. Fee executes the necessary block management and sets a pending MEMIF_JOB_PENDING to MEMIF_JOB_OK; otherwise, the job result remains unchanged. After that, Fee calls the upper layer's end notification, if configured (SWS Fee p. 37). Alternatively, the upper layer queries the result of the most recently accepted job with Fee_GetJobResult [SWS_Fee_00091]. The callbacks can run at interrupt level and must therefore remain short (SWS Fee p. 36).

Sequence diagram: A write job returns immediately with E_OK, is processed asynchronously, and is completed via the Fls → Fee → NvM callback cascade. Whether Fee initiates the driver already in Fee_Write or not until Fee_MainFunction is not specified bindingly. Sources: [SWS_Fee_00088], [SWS_Fee_00095], SWS Fee Fig. 7 p. 40, SWS Fee p. 42, SWS Fee p. 21

Special services: Cancellation, invalidation, immediate data, and mode change

Fee_Cancel is synchronous in R20-11 [SWS_Fee_00089]. Later versions list the service as asynchronous, but at the same time describe it as synchronous in itself and only asynchronous with respect to the hardware (SWS Fee p. 29, SWS Fee p. 45). In status MEMIF_BUSY, Fee_Cancel calls the driver's cancel function and resets the internal variables. The module is thus ready for a new job in MEMIF_IDLE (SWS Fee p. 29). The job result is then MEMIF_JOB_CANCELED [SWS_Fee_00091]. For a call without a pending job, the error code FEE_E_INVALID_CANCEL is defined [SWS_Fee_91002].

Sequence diagram: Fee_Cancel cancels an ongoing write job via Fls_Cancel and immediately makes Fee available for a new job. The original diagram shows the newer stack with MemAcc; here it is transferred to Fls (R20-11). Sources: [SWS_Fee_00089], [SWS_Fee_00105], [SWS_Fee_91002], SWS Fee Fig. 9.3 p. 44, SWS Fee p. 29

Fee_InvalidateBlock calculates the block address from the block number. It invalidates the block via the driver's erase function and/or via internal management information stored non-volatily (SWS Fee p. 32). Fee_EraseImmediateBlock is intended for diagnostic or similar system services that erase the area for immediate data in advance. Whether physical erasing takes place depends on the implementation (SWS Fee p. 35). In R20-11, both services return E_NOT_OK only with DET activated [SWS_Fee_00092] [SWS_Fee_00094]; newer versions formulate E_NOT_OK without this restriction (SWS Fee p. 32).

Fee_SetMode switches the operating mode of the underlying flash driver and is asynchronous in R20-11 [SWS_Fee_00086]. In contrast, the older diagram shows an end-to-end call chain MemIf_SetMode → Fee_SetMode → Fls_SetMode (SWS Fee Fig. 6 p. 44). Fee_GetVersionInfo is the only reentrant Fee service [SWS_Fee_00093]. With DET activated, it checks the passed pointer and reports error FEE_E_PARAM_POINTER in case of NULL (SWS Fee p. 34).

Configuration set and configurable feedback paths

Fee_ConfigType is a structure with implementation-specific elements [SWS_Fee_00188]; Fee_Init takes a pointer to it [SWS_Fee_00085]. The diagram of ECU configuration parameters shows a module container with multiplicity 0..1. It contains parameters such as FeeDevErrorDetect, FeeVersionInfoApi, and FeeVirtualPageSize as well as the function names FeeJobEndNotification and FeeJobErrorNotification (ECUC-Parameter Fig. 7.7 p. 578). However, this diagram is based on a specification status from 2006; therefore, the payload does not substantiate the exact parameter list for R20-11. A change history in the payload also mentions the parameter FeeMainFunctionPeriod (SWS MemIf p. 2).

The configurable notifications explain the addition "if configured" in the sequences. Fee calls the upper layer's end or error notification only if such a routine is configured (SWS Fee p. 37, SWS Fee p. 38). Accordingly, the error description specifies two reporting mechanisms depending on the configuration: polling or callback (ErrorDescription p. 40).

Behavior in the event of an error

Fee defines the following error codes [SWS_Fee_00010] [SWS_Fee_91002]. An example of the check: With DET activated, Fee_Cancel reports error FEE_E_UNINIT in status MEMIF_UNINIT (SWS Fee p. 29).

Error codeValueReason
FEE_E_UNINIT0x01Service called without prior initialization
FEE_E_INVALID_BLOCK_NO0x02Invalid block number
FEE_E_INVALID_BLOCK_OFS0x03Invalid block offset
FEE_E_PARAM_POINTER0x04Invalid data pointer
FEE_E_INVALID_BLOCK_LEN0x05Invalid length specification
FEE_E_BUSY0x06Call while an upper-layer job is running
FEE_E_INVALID_CANCEL0x08Fee_Cancel without a pending job

The flash driver detects hardware errors. It reports the failure of an asynchronous operation via Fee_JobErrorNotification [SWS_Fee_00096]. The reaction in Fee is implementation-specific. Depending on the configuration, MemIf queries the job result MEMIF_JOB_FAILED via Fee_GetJobResult, or Fee reports the error via NvM_JobErrorNotification. Recovery is the responsibility of NvM (ErrorDescription p. 40, [SWS_Fee_00099]). MemIf can detect an uninitialized state via Fee_GetStatus (ErrorDescription p. 53, [SWS_Fee_00090]).

In the event of consistency errors, Fee checks the read data and forwards a detected error to NvM. NvM reports NVM_E_INTEGRITY_FAILED to the DEM and, if configured, starts a recovery: re-reading, reading the redundant block, or reading the ROM block. If it fails, the job result is NVM_REQ_INTEGRITY_FAILED. The corresponding diagram originates from R22-11 (ErrorDescription Fig. 6.11 p. 64). In its job result, Fee itself additionally distinguishes invalidated (MEMIF_BLOCK_INVALID), inconsistent (MEMIF_BLOCK_INCONSISTENT), and canceled jobs (MEMIF_JOB_CANCELED) [SWS_Fee_00091].

Sequence diagram: Driver errors reach NvM via callback or polling, depending on the configuration; consistency errors trigger recovery in NvM. Sources: [SWS_Fee_00096], [SWS_Fee_00099], [SWS_Fee_00091], ErrorDescription p. 40, ErrorDescription Fig. 6.11 p. 64

Usage and Semantics

The function Fee_Read ([SWS_Fee_00087]) serves to initiate an asynchronous read job and is provided via the header Fee.h with service ID 0x02. Control and buffer passing occur via the following parameters:

  • Block Number: Logical block number, which also specifies the start address of the block in flash memory.
  • Block Offset: Read offset within the specified block.
  • Length: Number of bytes to be read from memory.
  • DataBufferPtr: Pointer to the data buffer (output parameter) into which the read data is written.

As return value, the function provides Std_ReturnType: E_OK signals that the module has accepted the read request, while E_NOT_OK indicates rejection of the job.

Concurrency and Limitations

According to [SWS_Fee_00087], Fee_Read is specified as non-reentrant (Non Reentrant). Since it is an asynchronous service, returning E_OK exclusively confirms acceptance of the job for further processing, not its completed execution.

Interaction with the Flash Driver

If the function Fls_BlankCheck is configured in the flash driver, Fee_Read must call this function in advance according to [SWS_Fee_00187]. This checks beforehand whether the affected memory area can be read without, for example, triggering ECC errors when attempting to read erased but not yet programmed flash cells.

Usage of Fee_Write

The function Fee_Write serves to initiate a write job in module Fee ([SWS_Fee_00088]). The service has the service ID 0x03, is provided via the header file Fee.h, and operates asynchronously ([SWS_Fee_00088]).

Two input parameters are specified for the call ([SWS_Fee_00088]):

  • BlockNumber: Logical block number, which also designates the start address of this block in the emulated EEPROM ([SWS_Fee_00088]).
  • DataBufferPtr: Pointer to the data buffer containing the payload to be transmitted ([SWS_Fee_00088]).

Output as well as input/output parameters are not present for this interface ([SWS_Fee_00088]).

Return Values

The return value of type Std_ReturnType indicates whether the write job was accepted ([SWS_Fee_00088]):

  • E_OK: The requested job was successfully accepted by the module ([SWS_Fee_00088]).
  • E_NOT_OK: The requested job was rejected by the module and not accepted ([SWS_Fee_00088]).

Concurrency and Limitations

The function is classified as non-reentrant (Non Reentrant) ([SWS_Fee_00088]). Since the service operates asynchronously, the return result E_OK merely confirms the acceptance of the job for further processing, but not the physical completion of the write operation ([SWS_Fee_00088]).

function Fee_InvalidateBlock [SWS_Fee_00092] 📄 PDF

Std_ReturnType Fee_InvalidateBlock (uint16 Block Number);

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 73cb79579a2b Provenance

The function Fee_InvalidateBlock ([SWS_Fee_00092]) represents a service of the module Fee to invalidate a logical block (service ID 0x07, declared in Fee.h).

use

Processing of the job is performed asynchronously (Asynchronous):

  • Parameters: The logical block number is passed via the input parameter Block Number of type uint16. This value also determines the start address of the respective block in flash memory. Additional input or output parameters are not present.
  • Return value: The service returns a Std_ReturnType. The value E_OK signals that the requested job was accepted by the module.

Error handling

If the requested job was not accepted by the module, the function returns E_NOT_OK. According to [SWS_Fee_00092], however, this feedback only occurs if DET is enabled.

Concurrency and Limitations

The interface is specified as non-reentrant (Non Reentrant). Callers must therefore ensure that no simultaneous or interrupting calls to Fee_InvalidateBlock occur.

use

The function Fee_EraseImmediateBlock ([SWS_Fee_00094]) provides a service for erasing a logical block. The interface is made available via the header Fee.h and has the service ID 0x09 ([SWS_Fee_00094]).

The execution semantics are asynchronous (Asynchronous) ([SWS_Fee_00094]). As an input parameter, Block Number of type uint16 is passed; this specifies the number of the logical block and at the same time designates the start address of this block in the EEPROM ([SWS_Fee_00094]). Input/output parameters or pure output parameters do not exist ([SWS_Fee_00094]).

The return value of type Std_ReturnType signals whether the erase job was accepted by the module ([SWS_Fee_00094]):

  • E_OK: The requested job was accepted by the module ([SWS_Fee_00094]).
  • E_NOT_OK: The requested job was not accepted by the module ([SWS_Fee_00094]).

Error handling

According to the specification, returning E_NOT_OK in the event of a rejected job occurs exclusively when the Default Error Tracer is enabled (only if DET is enabled) ([SWS_Fee_00094]).

Concurrency and Limitations

The function is defined as non-reentrant (Non Reentrant) ([SWS_Fee_00094]). Further information regarding call contexts or ordering conditions is not included in the specification data and is therefore omitted.
