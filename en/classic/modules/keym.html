Role of KeyM between key master, applications, and CSM

The Key Manager (KeyM) consists of two submodules. The crypto key submodule initializes, updates, and maintains the cryptographic key material of an ECU, for example keys for Secured I-PDUs. These keys are provided by a key master, which can reside in the vehicle or in a backend. Communication with it usually takes place via diagnostic commands (SWS KeyM p. 24). The certificate submodule holds the status of PKI certificates and provides their contents ([SWS_KeyM_00066], [SWS_KeyM_00083]). KeyM does not store key material itself. It passes it to CSM keys via the mandatory interfaces Csm_KeyElementSet, Csm_KeyElementGet, and Csm_KeySetValid ([SWS_KeyM_00076]). Further interfaces used are Csm_KeyDerive, Csm_SignatureVerify, Det_ReportError, and IdsM_SetSecurityEvent ([SWS_KeyM_00078]).

Application SWCs access it via RTE ports. For each certificate there is a port KeyMCertificate_{KeyMCertificate}, for each certificate element a port KeyMCertificateElement_…, plus the ports KeyMCryptoKey and KeyMCryptoKeyNotification ([SWS_KeyM_00160], [SWS_KeyM_00162], [SWS_KeyM_00163], [SWS_KeyM_00164]). BSW modules also use KeyM:

  • The TLS implementation of TcpIp retrieves certificates using KeyM_GetCertificate (SWS TcpIp p. 134).
  • The DCM reads whitelists using KeyM_CertElementGetFirst/KeyM_CertElementGetNext (SWS DCM p. 162).
  • The DCM receives verification results via the Dcm_KeyMAsyncCertificateVerifyFinished configured as a callback (SWS DCM p. 245).

Context diagram: KeyM mediates between applications or DCM/TcpIp and CSM, StbM, NvM, IdsM, and DET; key handlers are configurable extensions. Sources: [SWS_KeyM_00076], [SWS_KeyM_00078], [SWS_KeyM_00160], SWS KeyM (Fig. 9.4) p. 119, SWS TcpIp p. 134

Certificate chain and its configuration

Certificates are described in the configuration via KeyMCertificate containers. At runtime, they are addressed via the handles KeyM_CertificateIdType and KeyM_CertElementIdType, both of type uint16 ([SWS_KeyM_00301], [SWS_KeyM_00300]). Each container contains three references:

  • to the parent certificate; the root certificate references itself here,
  • to a CSM job for signature verification,
  • to a CSM key for the public key of the certificate.

SWS KeyM (Fig. 7.3) p. 22 shows this structure. If all verification steps are error-free, KeyM sets the public key into the CSM key referenced via KeyMCertCsmSignatureVerifyKeyRef and validates it with Csm_KeySetValid ([SWS_KeyM_00170]).

Certificate data is passed as KeyM_CertDataType. The structure consists of certDataLength and a pointer certData to a buffer of the caller ([SWS_KeyM_00041]). The sizes of the RTE data types result from the configuration: KeyMKeyCertNameMaxLength for names and KeyMCertificateElementMaxLength for element buffers ([SWS_KeyM_91000], [SWS_KeyM_91004]).

Context diagram: Three-stage chain Root – Intermediate – Working Certificate with references to one CSM job and one CSM key each; root references itself. Sources: SWS KeyM (Fig. 7.3) p. 22, [SWS_KeyM_00170]

Certificate status: from setting to validity

Each certificate has a status of type KeyM_CertificateStatusType, which KeyM_CertGetStatus provides ([SWS_KeyM_91003], [SWS_KeyM_00066]). The life cycle according to SWS KeyM (Fig. 7.4) p. 24:

  • After KeyM_Init, the certificate is set to KEYM_CERTIFICATE_NOT_AVAILABLE.
  • KeyM_SetCertificate with length > 0, KeyM_ServiceCertificate, or loading during startup leads to the transient status KEYM_CERTIFICATE_NOT_PARSED.
  • After successful parsing, KEYM_CERTIFICATE_PARSED_NOT_VALIDATED follows.
  • KeyM_SetCertificate with length 0 resets the certificate and status.

A certificate reaches KEYM_CERTIFICATE_VALID only after complete, error-free verification ([SWS_KeyM_00170]). If the check fails, a specific error status remains, such as KEYM_E_CERTIFICATE_VALIDITY_PERIOD_FAIL, KEYM_E_CERTIFICATE_SIGNATURE_FAIL, or KEYM_E_CERTIFICATE_INVALID_CHAIN_OF_TRUST ([SWS_KeyM_91003]).

State diagram: A certificate transitions through "not available → not parsed → parsed → valid"; parse and verification errors lead to separate error states. Interpretation: The assignment of verification error states and the reset path from all states are inferred. Sources: SWS KeyM (Fig. 7.4) p. 24, SWS KeyM (Fig. 7.4) p. 33, [SWS_KeyM_91003]

KeyM_SetCertificate stores a presented certificate only temporarily in the configured storage class, typically in RAM. For persistent storage, such as for the root certificate, KeyM_ServiceCertificate is provided ([SWS_KeyM_00057], SWS KeyM p. 31). For asynchronous verification, there are three variants:

  • KeyM_VerifyCertificates checks exactly one pair consisting of a lower and upper certificate ([SWS_KeyM_00059]).
  • KeyM_VerifyCertificate determines the chain for a set certificate itself from the stored certificates ([SWS_KeyM_00060]).
  • KeyM_VerifyCertificateChain checks a chain provided by the caller and sorted in PKI order ([SWS_KeyM_00061]).

If the call returns E_OK, the configured KeyMCertificateVerifyCallbackNotificationFunc reports the result later as KeyM_CertificateStatusType ([SWS_KeyM_00153], [SWS_KeyM_00073]).

Sequence diagram: A working certificate is set, parsed, asynchronously verified; the public key is subsequently set and validated in the CSM, and the result is reported via callback. Sources: SWS KeyM (Fig. 9.4) p. 119, [SWS_KeyM_00060], [SWS_KeyM_00170], [SWS_KeyM_00153]

Certificate services and access to certificate elements

If KeyMServiceCertificateFunctionEnabled and KeyMCertificateManagerEnabled are set, the certificate submodule offers KeyM_ServiceCertificate. Via this, the key master introduces or updates persistently stored certificates ([SWS_KeyM_00021], [SWS_KeyM_00056]). The operation is selected via KeyM_ServiceCertificateType ([SWS_KeyM_00039]):

  • request CSR or restore signed CSR,
  • set or update root or intermediate certificate,
  • provide revocation list,
  • vendor-specific extensions in the reserved range 0x80–0x9F.

The operation runs asynchronously and ends with KeyM_ServiceCertificateCallbackNotification ([SWS_KeyM_00149], [SWS_KeyM_00152]). Optionally, the key handler KeyM_KH_ServiceCertificate can be integrated ([SWS_KeyM_00072]).

Differences from later releases: These add KeyM_ServiceCertificateByCertId and reduce the callback to CertId and Result (SWS KeyM p. 92). For R20-11, the signature with ResultDataLength and ResultDataPtr applies ([SWS_KeyM_00147]). Installation and update attempts for root and intermediate certificates are standardized as security events KEYM_SEV_INST_ROOT_CERT_OP through KEYM_SEV_UPD_INTERMEDIATE_CERT_OP ([SWS_KeyM_00172]).

Sequence diagram: A root or intermediate certificate is introduced via KeyM_ServiceCertificate, parsed, checked for validity period, and stored in NvM or CSM depending on configuration; completion is reported by the service callback. Sources: SWS KeyM (Fig. 9.5) p. 120, [SWS_KeyM_00056], [SWS_KeyM_00149], [SWS_KeyM_00147]

KeyM_CertElementGet reads the contents of parsed certificates based on the configured object ID ([SWS_KeyM_00063], [SWS_KeyM_00127]). Elements with multiple occurrences can be traversed in two ways:

  • using KeyM_CertElementGetFirst/KeyM_CertElementGetNext and a KeyM_CertElementIteratorType held by the caller, which must remain unchanged until the end ([SWS_KeyM_00064], [SWS_KeyM_00065], [SWS_KeyM_00042]),
  • index-based using KeyM_CertificateElementGetCount and KeyM_CertificateElementGetByIndex ([SWS_KeyM_91015], [SWS_KeyM_91014]).

Iteration is permitted only for elements with KeyMCertificateElementHasIteration = TRUE ([SWS_KeyM_00148]).

Key update as a Start–Prepare–Update–Finalize session

The crypto key submodule can be operated in a session-like manner. KeyM_Start opens the session, KeyM_Finalize closes it; in between, operations such as KeyM_Prepare and KeyM_Update are accepted ([SWS_KeyM_00050], [SWS_KeyM_00053], SWS KeyM p. 25). KeyM_StartType distinguishes the OEM production mode with higher privileges from the workshop mode ([SWS_KeyM_00038]).

If a key handler is activated, KeyM_Start passes the parameters to KeyM_KH_Start and adopts its return value. In this way, vendor-specific signature verifications can be implemented, for example ([SWS_KeyM_00067], SWS KeyM p. 25). Accordingly, KeyM_Prepare and KeyM_Finalize delegate to KeyM_KH_Prepare and KeyM_KH_Finalize, respectively ([SWS_KeyM_00068], [SWS_KeyM_00070]). Completion of the finalization is reported by KeyM_CryptoKeyFinalizeCallbackNotification if KeyMCryptoKeyStartFinalizeFunctionEnabled is set ([SWS_KeyM_00080], [SWS_KeyM_00079]).

Sequence diagram: The key session opens with KeyM_Start, prepares with KeyM_Prepare, updates asynchronously with KeyM_Update, and closes with KeyM_Finalize; key handlers are engaged depending on configuration. Sources: [SWS_KeyM_00050], [SWS_KeyM_00067], [SWS_KeyM_00068], [SWS_KeyM_00077], [SWS_KeyM_00080], SWS KeyM (Fig. 9.2) p. 117

KeyM_Update operates asynchronously ([SWS_KeyM_00052]). KeyM finds the target key in one of two ways:

  • via the name in KeyMCryptoKeyName ([SWS_KeyM_00091]),
  • without a valid name, via bits 121..124 of the request data interpreted as SHE-M1M2M3, matched against KeyMCryptoKeyCryptoProps ([SWS_KeyM_00154]).

Without a match and without a key handler, the call ends with KEYM_E_PARAMETER_MISMATCH ([SWS_KeyM_00155]). With a key handler, the update proceeds as follows:

  1. KeyM calls KeyM_KH_Update with the found key or 0xFFFFFFFFul ([SWS_KeyM_00092]), providing an internal buffer in the process ([SWS_KeyM_00097]).
  2. If the handler reports KEYM_KH_UPDATE_KEY_UPDATE_REPEAT with data, KeyM stores or derives the key in the CSM and calls the handler again ([SWS_KeyM_00096], [SWS_KeyM_00055]).
  3. If the handler reports KEYM_KH_UPDATE_FINISH, KeyM copies the result into the buffer of the caller and calls KeyM_CryptoKeyUpdateCallbackNotification ([SWS_KeyM_00093]).

Until this callback, the caller must not modify the result buffer ([SWS_KeyM_00156]).

Activity diagram: KeyM_Update determines the target key via name or SHE data and processes it directly or in a key handler loop up to KEYM_KH_UPDATE_FINISH. Sources: [SWS_KeyM_00091], [SWS_KeyM_00092], [SWS_KeyM_00093], [SWS_KeyM_00096], [SWS_KeyM_00154], [SWS_KeyM_00155]

Depending on the configuration, KeyM_Verify verifies keys synchronously. If KeyMCryptoKeyVerifyAsyncMode = TRUE, the verification runs asynchronously, and the result is provided via KeyM_CryptoKeyVerifyCallbackNotification ([SWS_KeyM_00054], [SWS_KeyM_00151], [SWS_KeyM_00081]).

Module operation: initialization, timing, and invocation rules

KeyM_Init initializes the module ([SWS_KeyM_00043]). The configuration pointer must always be NULL_PTR ([SWS_KeyM_00158]), although the parameter description specifies a post-build configuration set. Interpretation: In R20-11, the configuration is therefore presumably not passed via this pointer in practice. KeyM_Deinit sets the module to the uninitialized state ([SWS_KeyM_00047]). The version starting from R23-11 additionally requires active erasing of key material in RAM (SWS KeyM p. 49).

KeyM_MainFunction is called periodically at the configured interval ([SWS_KeyM_00074]). KeyM_MainBackgroundFunction runs during idle times of a preemptive operating system and is suitable for time-consuming synchronous functions such as KeyM_KH_Update ([SWS_KeyM_00075]). Presumably, these functions advance the asynchronous services: the APIs report their acceptance with E_OK, and their completion via a callback ([SWS_KeyM_00060], [SWS_KeyM_00052]). The services are entirely non-reentrant; the iterator functions are reentrant only per iterator ([SWS_KeyM_00057], [SWS_KeyM_00064]). Callback names are configurable and are included via KeyM_Externals.h ([SWS_KeyM_00073], SWS KeyM p. 91).

Behavior in the event of an error

With development error detection enabled, KeyM checks upon each call ([SWS_KeyM_00144], [SWS_KeyM_00145], [SWS_KeyM_00146], [SWS_KeyM_00036]):

  • the initialization (KEYM_E_UNINIT),
  • the buffer sizes (KEYM_E_SMALL_BUFFER),
  • unexpected NULL pointers (KEYM_E_PARAM_POINTER).

If the referenced certificate has the storage class KEYM_STORAGE_IN_CSM or KEYM_STORAGE_IN_NVM, the specification requires KEYM_E_CONFIG_FAILURE, without development mode E_NOT_OK ([SWS_KeyM_00166]).

Synchronous return values use KeyM-specific values ([SWS_KeyM_00040]):

  • KEYM_E_BUSY: other jobs are still running,
  • KEYM_E_PENDING: job accepted, processing asynchronous,
  • KEYM_E_KEY_CERT_SIZE_MISMATCH, KEYM_E_PARAMETER_MISMATCH, and KEYM_E_KEY_CERT_INVALID.

Certificate functions add further codes. KEYM_E_KEY_CERT_EMPTY stands for empty slots, KEYM_E_KEY_CERT_READ_FAIL for denied access, and KEYM_E_CERT_INVALID_CHAIN_OF_TRUST for an invalid parent certificate ([SWS_KeyM_00058], [SWS_KeyM_00060], SWS KeyM p. 66). Non-iterable elements return KEYM_E_CERT_INVALID ([SWS_KeyM_00148]). In case of failure, KeyM_CertElementGet sets the output length to zero ([SWS_KeyM_00063], SWS KeyM p. 71).

Asynchronous errors arrive in the callback. KeyM_ResultType distinguishes, among others, KEYM_RT_NOT_OK, KEYM_RT_KEY_CERT_INVALID, KEYM_RT_KEY_CERT_WRITE_FAIL, KEYM_RT_KEY_CERT_UPDATE_FAIL, and KEYM_RT_CERT_INVALID_CHAIN_OF_TRUST ([SWS_KeyM_91008]). Certificate checks deliver the detailed status from KeyM_CertificateStatusType ([SWS_KeyM_00073], [SWS_KeyM_91003]).

A failed chain check is additionally the security event KEYM_SEV_CERT_VERIF_FAILED (ID 5) ([SWS_KeyM_00172]). It is reported to the IdsM only if KeyMEnableSecurityEventReporting = TRUE. Later releases name the event SEV_CERT_CHAIN_VERIFICATION_FAILED (SWS KeyM p. 38); for R20-11, the name from [SWS_KeyM_00172] applies.

Usage and Semantics

  • Call context and parameters: The function has the signature void KeyM_Deinit (void);. It expects no input parameters (neither in, inout nor out) and returns no return value.

  • Concurrency: The function is specified as non-reentrant (Non Reentrant) and therefore must not be executed concurrently or preemptively.

Interaction and Error Handling

Calling KeyM_Deinit transitions the module into the state prior to initialization. This entails the following interactions in the overall system:

  • If development error detection is active, the Key Manager checks according to [SWS_KeyM_00144] on each function call whether the module has been initialized with KeyM_Init() and not yet deinitialized via KeyM_Deinit().
  • If a function of the Key Manager is called after execution of KeyM_Deinit without prior re-initialization, the development error KEYM_E_UNINIT is reported ([SWS_KeyM_00144]).

Usage and Configuration

The function KeyM_Start ([SWS_KeyM_00050], AUTOSAR_SWS_KeyManager p. 35) is optional and only available if the configuration parameter KeyMCryptoKeyStartFinalizeFunctionEnabled is set to true. Its purpose is to permit subsequent key update operations. The function is provided via the header KeyM.h and operates synchronously.

  • StartType (in): Defines the mode in which the key operation is to be executed.
  • RequestData (in) and RequestDataLength (in): Pointer to the data passed with the request (e.g. a signature) as well as its length in bytes.
  • ResponseDataLength (inout): Passes on input the maximum byte amount available in the output buffer and returns on output the actual number of written bytes.
  • ResponseData (out): Buffer to receive the payload data returned by the function.

Return Values and Error Handling

The return value of type Std_ReturnType signals the result of the initialization:

  • E_OK: The start operation was successfully executed; key updates are now permitted.
  • E_NOT_OK: The start operation was rejected.
  • KEYM_E_PARAMETER_MISMATCH: A passed parameter does not match the expected value.
  • KEYM_E_KEY_CERT_SIZE_MISMATCH: The size of a passed parameter is incorrect.

Concurrency and Limitations

According to [SWS_KeyM_00050], the service function (Service ID 0x04) is specified as non-reentrant (Non Reentrant). Callers must therefore ensure that no concurrent calls to KeyM_Start occur.
