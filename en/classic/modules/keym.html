Manages an ECU's keys and certificates: update, parsing, and verification of certificate chains.

In the AUTOSAR crypto stack, Key Manager manages the key material and certificates of an ECU and is built on top of CSM. The crypto key submodule accepts keys in an optional session from KeyM_Start, KeyM_Prepare, KeyM_Update, and KeyM_Finalize; vendor-specific key handlers can be integrated. The certificate submodule stores certificates, parses them, and verifies them asynchronously against a configured chain; callback [SWS_KeyM_00153] reports the result. A certificate only becomes valid after error-free verification, and only then is its public key released in CSM [SWS_KeyM_00170].

In the crypto stack, Key Manager manages the key material and certificates of an ECU. For this purpose, it has two submodules: The crypto key submodule accepts keys from a key master in the vehicle or in the backend, mostly via diagnostic commands. The certificate submodule stores certificates, parses them, and verifies them against their chain (SWS KeyM p. 24). Downward, KeyM uses CSM; Csm_KeyElementGet, Csm_KeyElementSet, and Csm_KeySetValid are mandatory [SWS_KeyM_00076].

Key operations can run in a session-like manner (SWS KeyM p. 25). KeyM_Start() opens the session, KeyM_Prepare() synchronously provides data for the key server, and KeyM_Finalize() closes the session. KeyM_Update() runs asynchronously and reports back via KeyM_CryptoKeyUpdateCallbackNotification() ([SWS_KeyM_00052], [SWS_KeyM_00077]). Optionally, a key handler performs vendor-specific steps. In this process, KeyM_KH_Update() is called repeatedly until it reports KEYM_KH_UPDATE_FINISH ([SWS_KeyM_00092], [SWS_KeyM_00096]).

Sequence diagram: The session runs from start via prepare and the asynchronous update to finalize, with optional key handlers and result callbacks. Sources: SWS KeyM p. 25, [SWS_KeyM_00052], [SWS_KeyM_00079]

Certificates are introduced in two ways. Permanently, this is done via KeyM_ServiceCertificate(), which the key master triggers [SWS_KeyM_00021]. Temporarily, a caller passes a certificate for verification using KeyM_SetCertificate() [SWS_KeyM_00057]. Each certificate maintains a status according to KeyM_CertificateStatusType [SWS_KeyM_91003]. Only after error-free verification does it become KEYM_CERTIFICATE_VALID, and only then is its public key released in CSM [SWS_KeyM_00170].

State diagram: A certificate transitions from NOT_AVAILABLE via parsing to PARSED_NOT_VALIDATED and after verification to VALID or into an error state; a reset with length 0 leads back. The assignment of INVALID_CONTENT and REVOKED is an interpretation. Sources: SWS KeyM p. 24, [SWS_KeyM_91003]

Verification runs asynchronously via KeyM_VerifyCertificate(), KeyM_VerifyCertificates(), or KeyM_VerifyCertificateChain(). A configurable callback [SWS_KeyM_00153] reports the result. Individual contents are read with KeyM_CertElementGet(); an iterator traverses elements with multiple occurrences [SWS_KeyM_00064]. KeyM reports errors in three ways: as development errors such as KEYM_E_UNINIT [SWS_KeyM_00036], as KeyM_ResultType in callbacks [SWS_KeyM_91008], and in the case of a failed chain verification additionally as a security event [SWS_KeyM_00172].

Role in the Crypto Stack: Key and Certificate Management Above CSM

Key Manager (KeyM) is a service module in the AUTOSAR crypto stack and consists of two submodules. The crypto key submodule initializes, updates, and maintains the key material of an ECU. The certificate submodule stores certificates, parses them, and verifies them against their chain (SWS KeyM p. 23, SWS KeyM p. 28). A typical use case of the crypto key submodule is the distribution of keys for secure onboard communication to CSM keys. The data is provided by a key master located in the vehicle or in a backend; communication usually proceeds via diagnostic commands (SWS KeyM p. 24).

Downward, KeyM is built on top of CSM. [SWS_KeyM_00076] specifies Csm_KeyElementGet, Csm_KeyElementSet, and Csm_KeySetValid as mandatory interfaces. In addition, [SWS_KeyM_00078] lists Csm_KeyDerive, Csm_SignatureVerify, Det_ReportError, and IdsM_SetSecurityEvent. For temporal validity verification, KeyM imports types of StbM [SWS_KeyM_00037]. Upward, KeyM provides C APIs and RTE service interfaces for certificates, certificate elements, and crypto keys ([SWS_KeyM_00082], [SWS_KeyM_00083], [SWS_KeyM_00084]). Vendor-specific logic is integrated via configurable key handler functions, for example via KeyM_KH_Start() [SWS_KeyM_00067].

Context diagram: KeyM mediates between key master or users, optional key handlers, and the services CSM, StbM, NvM, IdsM, and DET. Sources: SWS KeyM p. 23, [SWS_KeyM_00076], [SWS_KeyM_00078], [SWS_KeyM_00037], SWS KeyM p. 119

Initialization, Scheduling, and Secure Deconstruction

KeyM_Init() initializes the [SWS_KeyM_00043] module. The content of KeyM_ConfigType is implementation-specific [SWS_KeyM_00157], and the configuration pointer shall always be NULL_PTR [SWS_KeyM_00158]. After initialization, all certificates have the status KEYM_CERTIFICATE_NOT_AVAILABLE (SWS KeyM p. 34). KeyM_Deinit() resets the module to the uninitialized state [SWS_KeyM_00047]. The corresponding document reference additionally requires that the crypto key submodule actively overwrites key material and intermediate results in RAM (SWS KeyM p. 49).

During operation, KeyM_MainFunction() is invoked periodically at the configured interval [SWS_KeyM_00074]. KeyM_MainBackgroundFunction() runs when the preemptive operating system has no other task. It can call time-consuming synchronous functions such as KeyM_KH_Update() [SWS_KeyM_00075]. The period is a parameter of the KeyMGeneral container (SWS KeyM p. 131). KeyM_GetVersionInfo() provides the version information [SWS_KeyM_00049].

Key session: from KeyM_Start to KeyM_Finalize

Key operations can be configured in a session-like manner. KeyM_Start() opens the session. Afterwards, KeyM accepts KeyM_Prepare() and KeyM_Update() until KeyM_Finalize() closes the session (SWS KeyM p. 25). KeyM_StartType distinguishes between OEM production mode and workshop mode; production mode has higher privileges [SWS_KeyM_00038]. By default, KeyM_Start() does not evaluate any input data. If KeyMCryptoKeyHandlerStartFinalizeEnabled is set, it calls KeyM_KH_Start() with the same parameters and adopts its return value, for instance for OEM-specific signature verifications ([SWS_KeyM_00050], [SWS_KeyM_00067]).

The individual steps of the session:

  • KeyM_Prepare() operates synchronously and primarily provides information for the key server [SWS_KeyM_00051]. If KeyMCryptoKeyPrepareFunctionEnabled and KeyMCryptoKeyHandlerPrepareEnabled are set, KeyM immediately calls KeyM_KH_Prepare() ([SWS_KeyM_00068], SWS KeyM p. 82).
  • KeyM_Update() is asynchronous. KeyM_CryptoKeyUpdateCallbackNotification() reports completion ([SWS_KeyM_00052], [SWS_KeyM_00077], [SWS_KeyM_00150]). The caller must not touch the passed result buffer until this callback; the callback returns the same pointer [SWS_KeyM_00156].
  • KeyM_Finalize() is also asynchronous and transitions the key operation into the idle state (SWS KeyM p. 56). With the key handler enabled, it delegates to KeyM_KH_Finalize() ([SWS_KeyM_00053], [SWS_KeyM_00070]). KeyM_CryptoKeyFinalizeCallbackNotification() reports whether all keys were successfully validated ([SWS_KeyM_00079], [SWS_KeyM_00080]).

Outside the session, KeyM_Verify() verifies keys synchronously or asynchronously [SWS_KeyM_00054]. If KeyMCryptoKeyVerifyAsyncMode = TRUE, the result arrives via KeyM_CryptoKeyVerifyCallbackNotification() ([SWS_KeyM_00081], [SWS_KeyM_00151]). A key handler can be integrated via KeyM_KH_Verify() [SWS_KeyM_00071].

Sequence diagram: The session runs from start via prepare and the asynchronous update to finalize; key handlers are optional, results arrive via callback. Sources: SWS KeyM p. 25, SWS KeyM p. 116, [SWS_KeyM_00052], [SWS_KeyM_00075], [SWS_KeyM_00079]

KeyM_Update in detail: key selection and key handler loop

First, KeyM determines the target key:

  • Using key names, KeyM searches for the KeyMCryptoKey container with a matching KeyMCryptoKeyName [SWS_KeyM_00091].
  • Without a valid name and with defined KeyMCryptoKeyCryptoProps, KeyM interprets RequestData as SHE values M1M2M3 and matches bits 121..124 [SWS_KeyM_00154].
  • If no KeyID can be determined and no update key handler is active, the call terminates with KEYM_E_PARAMETER_MISMATCH [SWS_KeyM_00155].

With KeyMCryptoKeyHandlerUpdateEnabled, KeyM_Update() calls the function KeyM_KH_Update(). It passes the request data, the name, and the identified KeymId, otherwise 0xFFFFFFFFul [SWS_KeyM_00092]. For this purpose, KeyM provides an internal buffer that it does not touch until the handler returns [SWS_KeyM_00097]. The handler's feedback controls the further procedure [SWS_KeyM_00055]:

  • KEYM_KH_UPDATE_KEY_UPDATE_REPEAT with data: KeyM stores the key in CSM or derives it there and invokes the handler again [SWS_KeyM_00096].
  • KEYM_KH_UPDATE_FINISH: KeyM copies the result data and triggers the update callback [SWS_KeyM_00093].

Whether KeyM stores or derives is defined by KeyMCryptoKeyGenerationType, with the values KEYM_STORED_KEY and KEYM_DERIVED_KEY, respectively (SWS KeyM p. 164). When deriving, Csm_KeyDerive replaces the call to Csm_KeyElementSet (SWS KeyM p. 118). In both cases, Csm_KeySetValid subsequently releases the key (SWS KeyM p. 116).

Activity diagram: KeyM_Update selects the key via name or SHE identifier, aborts without a KeyID and without a key handler, and repeats the key handler invocations until KEYM_KH_UPDATE_FINISH. Sources: [SWS_KeyM_00091], [SWS_KeyM_00154], [SWS_KeyM_00155], [SWS_KeyM_00092], [SWS_KeyM_00096], [SWS_KeyM_00093]

Certificates: persistent and temporary storage, hierarchy, and status

KeyM_ServiceCertificate() is available for persistently stored certificates. The certificate submodule provides the function when KeyMServiceCertificateFunctionEnabled and KeyMCertificateManagerEnabled are set; it is called by the Key Master [SWS_KeyM_00021]. KeyM_ServiceCertificateType distinguishes between the following services [SWS_KeyM_00039]:

  • Request CSR and return signed CSR,
  • Set or update root and intermediate certificates,
  • Provide or update CRL.

The service runs asynchronously and reports via KeyM_ServiceCertificateCallbackNotification() ([SWS_KeyM_00056], [SWS_KeyM_00149], [SWS_KeyM_00152]). Attempts to install or update root or intermediate certificates are defined as security events ([SWS_KeyM_00172], SWS KeyM p. 38).

Sequence diagram: When introducing a root or intermediate certificate, parsing and verification are performed first; storage in NvM or CSM only follows upon successful verification, followed by the service callback. Sources: SWS KeyM p. 120, [SWS_KeyM_00039], [SWS_KeyM_00056], [SWS_KeyM_00149], [SWS_KeyM_00172]

In contrast, the caller provides a presented certificate temporarily using KeyM_SetCertificate() [SWS_KeyM_00057]. It ends up in the configured KeyMCertificateStorage, typically in RAM, and is not intended for persistent storage (SWS KeyM p. 31). The data is passed in KeyM_CertDataType with length and pointer [SWS_KeyM_00041]. The chain itself is statically configured. Each KeyMCertificate references its upper certificate, with the root certificate referencing itself. In addition, each certificate references a CSM job and a CSM key for signature verification (SWS KeyM p. 22).

Structure diagram: In a three-tier chain, each KeyMCertificate references its upper certificate (root to itself) as well as the CSM job and CSM key for signature verification. Sources: SWS KeyM p. 22, SWS KeyM p. 31, [SWS_KeyM_00170]

Each certificate has a status of type KeyM_CertificateStatusType [SWS_KeyM_91003], which KeyM_CertGetStatus() queries [SWS_KeyM_00066]. The lifecycle:

  • After KeyM_Init(), KEYM_CERTIFICATE_NOT_AVAILABLE applies.
  • KeyM_SetCertificate() with certDataLength = 0 resets the certificate and status (SWS KeyM p. 34).
  • Set data undergoes parsing (NOT_PARSED → PARSED_NOT_VALIDATED) and subsequent verification (SWS KeyM p. 24).
  • Only after error-free verification does KeyM release the public key via Csm_KeySetValid() and set KEYM_CERTIFICATE_VALID [SWS_KeyM_00170].

Interpretation: KEYM_E_CERTIFICATE_INVALID_CONTENT is likely to count among the parsing errors and KEYM_E_CERTIFICATE_REVOKED among the verification errors. This is explicitly substantiated only for INVALID_FORMAT and INVALID_TYPE (SWS KeyM p. 33).

State diagram: A certificate transitions from NOT_AVAILABLE via parsing to PARSED_NOT_VALIDATED and, after successful verification, to VALID; errors lead to error states, and a reset with length 0 leads back. The assignment of INVALID_CONTENT and REVOKED is an interpretation. Sources: SWS KeyM p. 24, [SWS_KeyM_91003], [SWS_KeyM_00170], SWS KeyM p. 34

Certificate verification and access to certificate contents

Three asynchronous, non-reentrant jobs are available for verification:

  • KeyM_VerifyCertificate() determines the associated chain autonomously ([SWS_KeyM_00060], SWS KeyM p. 68).
  • KeyM_VerifyCertificates() verifies a lower certificate against an upper certificate [SWS_KeyM_00059].
  • KeyM_VerifyCertificateChain() receives a certificate list sorted in PKI order [SWS_KeyM_00061].

If KeyM accepted the job with E_OK and KeyMCertificateVerifyCallbackNotificationFunc is configured, the callback reports the result as KeyM_CertificateStatusType ([SWS_KeyM_00153], [SWS_KeyM_00073]). If this function is NULL, the required port KeyMCertificateNotification is provided instead [SWS_KeyM_00161]. According to the available DCM document references from later releases, DCM uses this mechanism for authentication (SWS DCM p. 147, SWS DCM p. 245).

Sequence diagram: A working certificate is set and parsed; the subsequent verification uses StbM time, subject verification, and CSM signature verification, ending with key release and callback. Sources: SWS KeyM p. 119, [SWS_KeyM_00057], [SWS_KeyM_00060], [SWS_KeyM_00170], [SWS_KeyM_00153]

Several functions are available for accessing certificate contents:

  • KeyM_GetCertificate() delivers the certificate data into a buffer of the caller [SWS_KeyM_00058]. The TLS sequence of TcpIp uses this (SWS TcpIp p. 134).
  • KeyM_CertElementGet() reads configured elements by object ID from the parsed and verified certificate ([SWS_KeyM_00063], [SWS_KeyM_00127]).
  • The caller traverses multi-instance elements using KeyM_CertElementGetFirst() and KeyM_CertElementGetNext() along with an iterator maintained by itself ([SWS_KeyM_00064], [SWS_KeyM_00065], [SWS_KeyM_00042]). This is only possible for elements with KeyMCertificateElementHasIteration [SWS_KeyM_00148].
  • Alternatively, KeyM_CertificateElementGetCount() and KeyM_CertificateElementGetByIndex() provide the count and specific individual entries ([SWS_KeyM_91015], [SWS_KeyM_91014]).

Using iteration, DCM reads whitelists from certificates (SWS DCM p. 155).

Behavior in the event of an error

When development error detection is enabled, KeyM checks on every invocation:

  • the initialization state (KEYM_E_UNINIT) [SWS_KeyM_00144],
  • the size of the result buffers (KEYM_E_SMALL_BUFFER) [SWS_KeyM_00145],
  • null pointers (KEYM_E_PARAM_POINTER) [SWS_KeyM_00146].

Further development errors are KEYM_E_INIT_FAILED and KEYM_E_CONFIG_FAILURE [SWS_KeyM_00036]. If the storage class of a certificate is KEYM_STORAGE_IN_CSM or KEYM_STORAGE_IN_NVM, KeyM reports KEYM_E_CONFIG_FAILURE; without development mode, it returns E_NOT_OK [SWS_KeyM_00166]. Interpretation: This presumably affects the temporary storage path via KeyM_SetCertificate(), which according to the document reference is intended for RAM (SWS KeyM p. 31).

Runtime errors occur on three levels:

  • Synchronous return values use KeyM codes such as KEYM_E_BUSY, KEYM_E_PENDING, KEYM_E_KEY_CERT_SIZE_MISMATCH, or KEYM_E_PARAMETER_MISMATCH [SWS_KeyM_00040]. Verification jobs reject empty certificate slots (KEYM_E_KEY_CERT_EMPTY) and invalid upper certificates (KEYM_E_CERT_INVALID_CHAIN_OF_TRUST) as early as during acceptance ([SWS_KeyM_00060], SWS KeyM p. 68).
  • Asynchronous key and certificate services report their result as KeyM_ResultType, such as KEYM_RT_KEY_CERT_WRITE_FAIL or KEYM_RT_CERT_INVALID_CHAIN_OF_TRUST [SWS_KeyM_91008].
  • Verification results carry error statuses such as validity period, signature, or trust chain errors [SWS_KeyM_91003]. A failed chain verification is additionally reported as security event KEYM_SEV_CERT_VERIF_FAILED [SWS_KeyM_00172].

Since KeyM_Init is specified as non-reentrant ([SWS_KeyM_00043]), the function may be executed only once and to the exclusion of concurrent calls in the system initialization phase. After successful execution, the module is available via the header file KeyM.h ([SWS_KeyM_00043]).

The function KeyM_Deinit serves to reset the Key Manager module back to the uninitialized state ([SWS_KeyM_00047]).

Usage and Call Context

The call to KeyM_Deinit is synchronous and specified as non-reentrant (Non Reentrant). The function has service ID 0x02, accepts no parameters, and returns no return value ([SWS_KeyM_00047]).

Concurrency and Interaction

Due to non-reentrancy, KeyM_Deinit must not be called concurrently with itself or in contradiction to running operations.
