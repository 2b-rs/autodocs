Role of the LinSM between ComM, BswM, and LinIf

The LIN State Manager (LinSM) is the bus state manager for LIN. ComM requests the communication capabilities requested by its users from the bus state managers SWS ComM p. 19. For LIN, this is done via LinSM_RequestComMode [SWS_LinSM_00126]. LinSM translates these requests per LIN network into calls to the LIN Interface. It reports the result back via the mandatory interfaces ComM_BusSM_ModeIndication, ComM_BusSM_BusSleepMode, BswM_LinSM_CurrentState, and BswM_LinSM_CurrentSchedule. Among other things, it controls the bus via LinIf_GotoSleep and LinIf_ScheduleRequest [SWS_LinSM_00229]. Optionally, it uses Det_ReportError and LinIf_SetTrcvMode [SWS_LinSM_00138].

The system boundary is drawn narrowly. LinSM only manages networks; which LIN driver serves a network is encapsulated by LinIf SWS LinSM p. 28. Wakeup by the cluster is not handled by LinSM, but by EcuM. This results in ComM requesting the network, so that in both cases LinSM only sees COMM_FULL_COMMUNICATION SWS LinSM p. 27. The module imports types ComM_ModeType, NetworkHandleType, and LinIf_SchHandleType [SWS_LinSM_00219].

Context diagram: LinSM mediates between the mode managers ComM/BswM and LinIf; driver and transceiver remain hidden behind LinIf. Sources: [SWS_LinSM_00229], [SWS_LinSM_00138], SWS LinSM Fig. 5.1 p. 14, SWS ComM Fig. 5.1 p. 19

State model per LIN network

At startup, LINSM_UNINIT is active even before an API is called SWS LinSM p. 22. LinSM_Init initializes the module with a pointer to LinSM_ConfigType [SWS_LinSM_00155] [SWS_LinSM_00221]. After this, LINSM_NO_COM applies per network. LinSM_Init reports this first transition neither to ComM nor to BswM, because ComM may not yet be initialized at that time SWS LinSM p. 23. In LINSM_NO_COM, the bus remains silent.

LINSM_FULL_COM is the only state in which communication is permitted on the LIN bus. Each network reaches it independently of the others. Upon entry, ComM receives COMM_FULL_COMMUNICATION and BswM receives LINSM_FULL_COM SWS LinSM p. 23. Substate LINSM_RUN_COMMUNICATION becomes active [SWS_LinSM_00301]. LinSM reports to BswM via LinSM_ModeType with the values LINSM_FULL_COM (0x01) and LINSM_NO_COM (0x02) [SWS_LinSM_00220] SWS BswM p. 72.

The second substate LINSM_GOTO_SLEEP bridges the waiting time for the sleep confirmation. If LinSM_GotoSleepConfirmation arrives in this substate, LinSM transitions to LINSM_NO_COM regardless of parameter success; in all other states, the callback is ignored SWS LinSM p. 24. LINSM_GOTO_SLEEP is presumably entered as soon as LinIf_GotoSleep returns with E_OK; the source breaks off at this point. An older diagram calls the running state LINSM_RUN_SCHEDULE SWS LinSM Fig. 5 p. 22. The name from [SWS_LinSM_00301] is authoritative.

State diagram: The module state encloses a separate state machine with NO_COM and FULL_COM for each LIN network; the path to sleep leads via LINSM_GOTO_SLEEP (entry condition as interpretation). Sources: [SWS_LinSM_00301], SWS LinSM p. 24, SWS LinSM Fig. 7.1 p. 20, SWS LinSM Fig. 7.2 p. 21

Wakeup: from ComM request to LINSM_FULL_COM

LinSM_RequestComMode operates asynchronously. The mode change does not take place immediately, and LinSM notifies the caller after completion [SWS_LinSM_00126]. For COMM_FULL_COMMUNICATION, LinSM calls LinIf_Wakeup directly, that is, without waiting for the next main function, and resets the retry counter SWS LinSM p. 27. Before that, it starts a confirmation timer for the network with LinSMConfirmationTimeout SWS LinSM p. 27.

LinIf reports the transmission of the wakeup signal via LinSM_WakeupConfirmation [SWS_LinSM_00132]. If success = TRUE, the network transitions to LINSM_FULL_COM. Otherwise, LinSM sets the previous state again so that ComM and BswM still receive a mode indication SWS LinSM p. 27. If LinSMTransceiverPassiveMode is configured, LinSM activates the transceiver via LinIf_SetTrcvMode upon entering LINSM_FULL_COM SWS LinSM p. 23.

A silence-after-wakeup timer with LinSMSilenceAfterWakeupTimeout prevents wakeup attempts that are too close together [SWS_LinSM_00235]. If ComM requests COMM_FULL_COMMUNICATION while this timer is running, LinSM delays LinIf_Wakeup until expiration [SWS_LinSM_00237]. If full communication is still requested after expiration, LinSM restarts the wakeup process [SWS_LinSM_00236].

A slave confirms the wakeup only when it receives the first LIN header from the master SWS LinIf p. 52. If the master does not start scheduling, the confirmation does not occur. The timer in LinSM then expires so that it does not wait indefinitely SWS LinSM p. 27.

Sequence diagram: Internal wakeup with direct LinIf_Wakeup, timer monitoring, and mode indication in both outcome cases. Sources: [SWS_LinSM_00126], [SWS_LinSM_00132], SWS LinSM p. 27, SWS LinSM Fig. 8 p. 42

Going to sleep: Master sends, slave reacts

Master: If ComM requests COMM_NO_COMMUNICATION in LINSM_FULL_COM, LinSM calls LinIf_GotoSleep to send the goto-sleep command [SWS_LinSM_10208]. The call is made directly, that is, without waiting for the next main function [SWS_LinSM_00036]. In all other cases, it is omitted [SWS_LinSM_10209]. If LinIf_GotoSleep returns E_NOT_OK, LinSM_RequestComMode also returns E_NOT_OK. At the same time, LinSM sets the previous state again so that ComM and BswM are informed [SWS_LinSM_00177].

LinIf reports whether the command was sent via LinSM_GotoSleepConfirmation [SWS_LinSM_00135]. The notification of entering LINSM_NO_COM to BswM and ComM takes place in any case, even after a problem SWS LinSM p. 24.

Sequence diagram: Goto-Sleep on the master with branching according to the return value of LinIf_GotoSleep. Sources: [SWS_LinSM_00036], [SWS_LinSM_00177], [SWS_LinSM_00135], SWS LinSM Fig. 6 p. 47

Slave: If ComM requests COMM_NO_COMMUNICATION in LINSM_FULL_COM, LinSM only stores the request and returns E_OK [SWS_LinSM_00230]. The trigger comes from the bus. LinIf calls LinSM_GotoSleepIndication when a goto-sleep command is received or a bus idle timeout occurs [SWS_LinSM_91000]. LinSM then directly calls LinIf_GotoSleep in LINSM_FULL_COM [SWS_LinSM_00231].

If LinIf_GotoSleep returns E_OK and COMM_NO_COMMUNICATION was requested, LinSM reports the bus-sleep event to ComM via ComM_BusSM_BusSleepMode [SWS_LinSM_00233]. Later versions formulate this obligation without the E_OK condition SWS LinSM p. 26; for R20-11, the requirement applies. If, on the other hand, full communication is requested, LinSM restarts the wakeup process after the goto-sleep sequence [SWS_LinSM_00234].

Sequence diagram: On the slave, the bus triggers going to sleep; the ComM request decides between bus-sleep indication and renewed wakeup. Sources: [SWS_LinSM_00230], [SWS_LinSM_00231], [SWS_LinSM_00233], [SWS_LinSM_00234], SWS LinSM Fig. 7 p. 48

Activity diagram: Decision logic of LinSM_RequestComMode according to requested mode, state, and node type. Sources: [SWS_LinSM_10208], [SWS_LinSM_10209], [SWS_LinSM_00177], [SWS_LinSM_00230], [SWS_LinSM_00237], SWS LinSM p. 36

Switching schedule tables (LIN master only)

LinSM_ScheduleRequest and LinSM_ScheduleRequestConfirmation exist only if at least one channel is configured as master [SWS_LinSM_00241] [SWS_LinSM_00242]. With LinSM_ScheduleRequest, the upper layer asynchronously requests a different schedule table [SWS_LinSM_00113]. LinSM immediately forwards the request to LinIf_ScheduleRequest and returns its return value SWS LinSM p. 26. A typical caller is BswM, which uses the symbolic LinSMScheduleIndex SWS LinSM p. 52. The LIN transport protocol sequence (LinTp) also switches to diagnostic tables via BswM in this way SWS LinIf p. 142.

After LinSM_ScheduleRequestConfirmation [SWS_LinSM_00129], LinSM reports the active table via BswM_LinSM_CurrentSchedule SWS BswM p. 80, provided its timer has not yet expired. For the remaining cases, these rules apply SWS LinSM p. 26:

  • If the timer has expired, LinSM reports the unchanged table.
  • In case of E_NOT_OK from LinIf_ScheduleRequest, it reports the old table in the next main function.
  • It also reports unrequested switches, such as the NULL schedule when going to sleep.

In R20-11, the parameter is called schedule [SWS_LinSM_00113]. R22-11 renamed the arguments Release Overview p. 50; later versions call it ScheduleTableIdx SWS LinSM p. 34.

Sequence diagram: Table switch with direct forwarding, confirmation, and fallback notifications to BswM; timeout detection in the main function is an interpretation. Sources: [SWS_LinSM_00113], [SWS_LinSM_00129], SWS LinSM p. 26, SWS LinSM Fig. 7 p. 41, SWS LinSM Fig. 9.4 p. 48

Configuration: Node type, time base, and initialization

LinSMNodeType determines the API scope. Master functions exist as soon as a channel is a master; LinSM_GotoSleepIndication exists as soon as a channel is a slave [SWS_LinSM_00241] [SWS_LinSM_00243]. Mixed configurations are therefore possible. The post-build parameters reside in the implementation-specific structure LinSM_ConfigType [SWS_LinSM_00221].

LinSM_MainFunction periodically drives the timers for request timeouts [SWS_LinSM_00156]. Each network has its own confirmation timer. LinSMConfirmationTimeout must be 0 or an integer multiple of the main function period SWS LinSM p. 27.

The container LinSMSchedule (0..*, master only) references LinIf tables; LinSMScheduleIndex must correspond to the LinIf value SWS LinSM p. 52. An example in the mode management guide shows a BswM rule that calls LinSM_Init after LinIf_Init Modemanagement-Leitfaden p. 54 [SWS_LinSM_00155].

Behavior in the event of an error

With LinSMDevErrorDetect, LinSM reports development errors to the DET. The codes are LINSM_E_UNINIT, LINSM_E_NONEXISTENT_NETWORK, LINSM_E_PARAMETER, LINSM_E_PARAM_POINTER, and LINSM_E_INIT_FAILED [SWS_LinSM_00053]. Callbacks such as LinSM_GotoSleepIndication report an invalid network or the UNINIT state [SWS_LinSM_00239] [SWS_LinSM_00240]. For such errors, services additionally return E_NOT_OK SWS LinSM p. 36. Invalid pointers at LinSM_GetCurrentComMode and LinSM_GetVersionInfo lead to LINSM_E_PARAM_POINTER SWS LinSM p. 35 SWS LinSM p. 34.

If a callback from LinIf fails to arrive, the runtime error LINSM_E_CONFIRMATION_TIMEOUT applies [SWS_LinSM_00224]. Interpretation: It is presumably reported via Det_ReportRuntimeError. However, this interface is specified as mandatory only in a later version SWS LinSM p. 41.

Functionally, LinSM keeps the mode managers consistent even in the event of an error:

  • A failed wakeup leads to a renewed indication of the old state SWS LinSM p. 27.
  • An unsuccessful sleep confirmation nevertheless leads to LINSM_NO_COM SWS LinSM p. 24.
  • A rejected LinIf_GotoSleep produces E_NOT_OK and a state indication [SWS_LinSM_00177].
  • A rejected table switch leads to the reporting of the old table SWS LinSM p. 26.

Usage and Semantics

The function LinSM_ScheduleRequest ([SWS_LinSM_00113]) is used by an upper layer to request the switch of a schedule table on a LIN network. The service is provided via header LinSM.h, operates asynchronously, and is specified as reentrant.

Parameters:

  • network (NetworkHandleType): Identification of the LIN channel.
  • schedule (LinIf_SchHandleType): Pointer or handle to the schedule table to be newly requested.

Return Values and Error Behavior

The function returns a status of type Std_ReturnType ([SWS_LinSM_00113]):

  • E_OK: The request for the schedule table was successfully accepted.
  • E_NOT_OK: The request could not be executed (for example, if the module is not initialized).

Configuration Dependencies and Interaction

The availability of LinSM_ScheduleRequest is tied to the role configuration of the module: according to [SWS_LinSM_00241], the function is only available if module LinSM is configured as LIN master on at least one channel via configuration parameter LinSMNodeType. In a pure LIN slave configuration, the function is not available.

In an analogous manner, the associated confirmation function LinSM_ScheduleRequestConfirmation also requires that at least one channel is operated as LIN master ([SWS_LinSM_00242]).

The function LinSM_RequestComMode ([SWS_LinSM_00126]) is used to request a communication mode for a LIN channel. The call behaves asynchronously: the mode switch is not performed immediately; instead, LinSM notifies the caller as soon as the state transition is completed. As input parameters, network for identifying the LIN channel and mode for the requested communication mode are passed.

Regarding concurrency, the interface is specified as reentrant ([SWS_LinSM_00126]). As return value, the function returns E_OK if the request was successfully accepted. If execution of the request is not possible—for example, if the module is not initialized—E_NOT_OK is returned ([SWS_LinSM_00126]).

During interaction with other modules, the following error behavior is defined: If a call of LinIf_GotoSleep returns E_NOT_OK, LinSM_RequestComMode must also respond with E_NOT_OK ([SWS_LinSM_00177]). If the LinSM module returns E_NOT_OK for LinSM_RequestComMode, the same state must be retained or set, so that ComM_BusSM_ModeIndication and BswM_LinSM_CurrentState are called ([SWS_LinSM_00177]).

The callback function LinSM_ScheduleRequestConfirmation ([SWS_LinSM_00129]) serves as confirmation to module LinSM as soon as a previously requested new schedule table has actually been switched to active. It is called by the LIN interface (LinIf).

Usage and Parameters

The call is performed synchronously and provides no return value (void). The function is declared via header LinSM.h and has the service ID 0x20 according to [SWS_LinSM_00129]. It accepts two input parameters:

  • network (NetworkHandleType): Identification of the affected LIN channel.
  • schedule (LinIf_SchHandleType): Pointer or handle to the now active schedule table.

Concurrency and Limitations

According to the specification, the function is classified as reentrant ([SWS_LinSM_00129]), allowing simultaneous confirmations for different channels to be processed.

Interaction

The function acts as an interface in the interaction between LinIf and LinSM: After a switch of the schedule table has been initiated, LinIf informs LinSM via this callback routine that the switch has taken effect ([SWS_LinSM_00129]).

The function LinSM_GotoSleepConfirmation is a synchronous callback interface (service ID 0x22) provided via header LinSM.h [SWS_LinSM_00135]. It is called by the LIN interface (LinIf) to confirm whether the command to transition into sleep state ("go to sleep command") was transmitted successfully or unsuccessfully on the network [SWS_LinSM_00135].

The result of the transmission is conveyed via the argument success [SWS_LinSM_00135]. Specific DET or DEM errors are not identified for this callback in the specification data. Module LinSM is likely to use the value of success internally to adapt the channel state accordingly or to coordinate follow-up actions for failed transmission attempts.

The function LinSM_WakeupConfirmation ([SWS_LinSM_00132]) is a callback interface of the LIN State Manager (LinSM). It is called by the LIN Interface (LinIf) as soon as the transmission of a wake-up signal command on the network has been completed – regardless of whether the transmission was successful or failed.

The signature is void LinSM_WakeupConfirmation (NetworkHandleType network, boolean success) with service ID 0x21 (available via the header file LinSM.h). The function has the following parameters:

  • network (input): Identification of the respective LIN network or channel (type NetworkHandleType).
  • success (input): Boolean indicator (type boolean) indicating whether the wake-up signal could be successfully sent on the bus (true) or not (false).

The function returns no value (void) and is specified with synchronous execution semantics (Synchronous).

Concurrency and Limitations

According to [SWS_LinSM_00132], LinSM_WakeupConfirmation is classified as reentrant (Reentrant). It can therefore be safely executed for different LIN channels within the ECU.

The type LinSM_ModeType is used in module LinSM to report the current communication mode to the BswM (Basic Software Mode Manager) ([SWS_LinSM_00220]). It is derived as an elementary type based on uint8 and is available via the header file LinSM.h ([SWS_LinSM_00220]).

Value Range

According to requirement [SWS_LinSM_00220], the type defines two discrete states for the operating mode:

  • LINSM_FULL_COM (value 0x01): Full communication ([SWS_LinSM_00220]).
  • LINSM_NO_COM (value 0x02): No communication ([SWS_LinSM_00220]).

Error Handling and Concurrency

Interpretation: Since LinSM_ModeType represents a pure type definition based on uint8, specification [SWS_LinSM_00220] defines neither separate development or production errors (DET/DEM) nor runtime or reentrancy rules for this type. The validity check for the defined values (0x01 and 0x02, respectively) is likely performed in the interface functions of the LIN State Manager that pass values of this type to the BswM.
