Role of the LinSM between ComM, BswM, and LinIf

The LIN State Manager (LinSM) is the bus state manager for LIN. ComM requests the communication capabilities requested by its users from the bus state managers SWS ComM p. 19. For LIN, this is done via LinSM_RequestComMode [SWS_LinSM_00126]. LinSM translates these requests per LIN network into calls to the LIN Interface. It reports the result back via the mandatory interfaces ComM_BusSM_ModeIndication, ComM_BusSM_BusSleepMode, BswM_LinSM_CurrentState, and BswM_LinSM_CurrentSchedule. Among other things, it controls the bus via LinIf_GotoSleep and LinIf_ScheduleRequest [SWS_LinSM_00229]. Optionally, it uses Det_ReportError and LinIf_SetTrcvMode [SWS_LinSM_00138].

The system boundary is drawn narrowly. LinSM only manages networks; which LIN driver serves a network is encapsulated by LinIf SWS LinSM p. 28. Wakeup by the cluster is not handled by LinSM, but by EcuM. This results in ComM requesting the network, so that in both cases LinSM only sees COMM_FULL_COMMUNICATION SWS LinSM p. 27. The module imports types ComM_ModeType, NetworkHandleType, and LinIf_SchHandleType [SWS_LinSM_00219].

State model per LIN network

At startup, LINSM_UNINIT is active even before an API is called SWS LinSM p. 22. LinSM_Init initializes the module with a pointer to LinSM_ConfigType [SWS_LinSM_00155] [SWS_LinSM_00221]. After this, LINSM_NO_COM applies per network. LinSM_Init reports this first transition neither to ComM nor to BswM, because ComM may not yet be initialized at that time SWS LinSM p. 23. In LINSM_NO_COM, the bus remains silent.

LINSM_FULL_COM is the only state in which communication is permitted on the LIN bus. Each network reaches it independently of the others. Upon entry, ComM receives COMM_FULL_COMMUNICATION and BswM receives LINSM_FULL_COM SWS LinSM p. 23. Substate LINSM_RUN_COMMUNICATION becomes active [SWS_LinSM_00301]. LinSM reports to BswM via LinSM_ModeType with the values LINSM_FULL_COM (0x01) and LINSM_NO_COM (0x02) [SWS_LinSM_00220] SWS BswM p. 72.

The second substate LINSM_GOTO_SLEEP bridges the waiting time for the sleep confirmation. If LinSM_GotoSleepConfirmation arrives in this substate, LinSM transitions to LINSM_NO_COM regardless of parameter success; in all other states, the callback is ignored SWS LinSM p. 24. LINSM_GOTO_SLEEP is presumably entered as soon as LinIf_GotoSleep returns with E_OK; the source breaks off at this point. An older diagram calls the running state LINSM_RUN_SCHEDULE SWS LinSM Fig. 5 p. 22. The name from [SWS_LinSM_00301] is authoritative.

State diagram: The module state encloses a separate state machine with NO_COM and FULL_COM for each LIN network; the path to sleep leads via LINSM_GOTO_SLEEP (entry condition as interpretation). Sources: [SWS_LinSM_00301], SWS LinSM p. 24, SWS LinSM Fig. 7.1 p. 20, SWS LinSM Fig. 7.2 p. 21

Wakeup: from ComM request to LINSM_FULL_COM

LinSM_RequestComMode operates asynchronously. The mode change does not take place immediately, and LinSM notifies the caller after completion [SWS_LinSM_00126]. For COMM_FULL_COMMUNICATION, LinSM calls LinIf_Wakeup directly, that is, without waiting for the next main function, and resets the retry counter SWS LinSM p. 27. Before that, it starts a confirmation timer for the network with LinSMConfirmationTimeout SWS LinSM p. 27.

LinIf reports the transmission of the wakeup signal via LinSM_WakeupConfirmation [SWS_LinSM_00132]. If success = TRUE, the network transitions to LINSM_FULL_COM. Otherwise, LinSM sets the previous state again so that ComM and BswM still receive a mode indication SWS LinSM p. 27. If LinSMTransceiverPassiveMode is configured, LinSM activates the transceiver via LinIf_SetTrcvMode upon entering LINSM_FULL_COM SWS LinSM p. 23.

A silence-after-wakeup timer with LinSMSilenceAfterWakeupTimeout prevents wakeup attempts that are too close together [SWS_LinSM_00235]. If ComM requests COMM_FULL_COMMUNICATION while this timer is running, LinSM delays LinIf_Wakeup until expiration [SWS_LinSM_00237]. If full communication is still requested after expiration, LinSM restarts the wakeup process [SWS_LinSM_00236].

A slave confirms the wakeup only when it receives the first LIN header from the master SWS LinIf p. 52. If the master does not start scheduling, the confirmation does not occur. The timer in LinSM then expires so that it does not wait indefinitely SWS LinSM p. 27.

Sequence diagram: Internal wakeup with direct LinIf_Wakeup, timer monitoring, and mode indication in both outcome cases. Sources: [SWS_LinSM_00126], [SWS_LinSM_00132], SWS LinSM p. 27, SWS LinSM Fig. 8 p. 42

Going to sleep: Master sends, slave reacts

Master: If ComM requests COMM_NO_COMMUNICATION in LINSM_FULL_COM, LinSM calls LinIf_GotoSleep to send the goto-sleep command [SWS_LinSM_10208]. The call is made directly, that is, without waiting for the next main function [SWS_LinSM_00036]. In all other cases, it is omitted [SWS_LinSM_10209]. If LinIf_GotoSleep returns E_NOT_OK, LinSM_RequestComMode also returns E_NOT_OK. At the same time, LinSM sets the previous state again so that ComM and BswM are informed [SWS_LinSM_00177].

LinIf reports whether the command was sent via LinSM_GotoSleepConfirmation [SWS_LinSM_00135]. The notification of entering LINSM_NO_COM to BswM and ComM takes place in any case, even after a problem SWS LinSM p. 24.

Sequence diagram: Goto-Sleep on the master with branching according to the return value of LinIf_GotoSleep. Sources: [SWS_LinSM_00036], [SWS_LinSM_00177], [SWS_LinSM_00135], SWS LinSM Fig. 6 p. 47

Slave: If ComM requests COMM_NO_COMMUNICATION in LINSM_FULL_COM, LinSM only stores the request and returns E_OK [SWS_LinSM_00230]. The trigger comes from the bus. LinIf calls LinSM_GotoSleepIndication when a goto-sleep command is received or a bus idle timeout occurs [SWS_LinSM_91000]. LinSM then directly calls LinIf_GotoSleep in LINSM_FULL_COM [SWS_LinSM_00231].

If LinIf_GotoSleep returns E_OK and COMM_NO_COMMUNICATION was requested, LinSM reports the bus-sleep event to ComM via ComM_BusSM_BusSleepMode [SWS_LinSM_00233]. Later versions formulate this obligation without the E_OK condition SWS LinSM p. 26; for R20-11, the requirement applies. If, on the other hand, full communication is requested, LinSM restarts the wakeup process after the goto-sleep sequence [SWS_LinSM_00234].

Sequence diagram: On the slave, the bus triggers going to sleep; the ComM request decides between bus-sleep indication and renewed wakeup. Sources: [SWS_LinSM_00230], [SWS_LinSM_00231], [SWS_LinSM_00233], [SWS_LinSM_00234], SWS LinSM Fig. 7 p. 48

Switching schedule tables (LIN master only)

LinSM_ScheduleRequest and LinSM_ScheduleRequestConfirmation exist only if at least one channel is configured as master [SWS_LinSM_00241] [SWS_LinSM_00242]. With LinSM_ScheduleRequest, the upper layer asynchronously requests a different schedule table [SWS_LinSM_00113]. LinSM immediately forwards the request to LinIf_ScheduleRequest and returns its return value SWS LinSM p. 26. A typical caller is BswM, which uses the symbolic LinSMScheduleIndex SWS LinSM p. 52. The LIN transport protocol sequence (LinTp) also switches to diagnostic tables via BswM in this way SWS LinIf p. 142.

After LinSM_ScheduleRequestConfirmation [SWS_LinSM_00129], LinSM reports the active table via BswM_LinSM_CurrentSchedule SWS BswM p. 80, provided its timer has not yet expired. For the remaining cases, these rules apply SWS LinSM p. 26:

  • If the timer has expired, LinSM reports the unchanged table.
  • In case of E_NOT_OK from LinIf_ScheduleRequest, it reports the old table in the next main function.
  • It also reports unrequested switches, such as the NULL schedule when going to sleep.

In R20-11, the parameter is called schedule [SWS_LinSM_00113]. R22-11 renamed the arguments Release Overview p. 50; later versions call it ScheduleTableIdx SWS LinSM p. 34.

Configuration: Node type, time base, and initialization

LinSMNodeType determines the API scope. Master functions exist as soon as a channel is a master; LinSM_GotoSleepIndication exists as soon as a channel is a slave [SWS_LinSM_00241] [SWS_LinSM_00243]. Mixed configurations are therefore possible. The post-build parameters reside in the implementation-specific structure LinSM_ConfigType [SWS_LinSM_00221].

LinSM_MainFunction periodically drives the timers for request timeouts [SWS_LinSM_00156]. Each network has its own confirmation timer. LinSMConfirmationTimeout must be 0 or an integer multiple of the main function period SWS LinSM p. 27.

The container LinSMSchedule (0..*, master only) references LinIf tables; LinSMScheduleIndex must correspond to the LinIf value SWS LinSM p. 52. An example in the mode management guide shows a BswM rule that calls LinSM_Init after LinIf_Init Modemanagement-Leitfaden p. 54 [SWS_LinSM_00155].

Behavior in the event of an error

With LinSMDevErrorDetect, LinSM reports development errors to the DET. The codes are LINSM_E_UNINIT, LINSM_E_NONEXISTENT_NETWORK, LINSM_E_PARAMETER, LINSM_E_PARAM_POINTER, and LINSM_E_INIT_FAILED [SWS_LinSM_00053]. Callbacks such as LinSM_GotoSleepIndication report an invalid network or the UNINIT state [SWS_LinSM_00239] [SWS_LinSM_00240]. For such errors, services additionally return E_NOT_OK SWS LinSM p. 36. Invalid pointers at LinSM_GetCurrentComMode and LinSM_GetVersionInfo lead to LINSM_E_PARAM_POINTER SWS LinSM p. 35 SWS LinSM p. 34.

If a callback from LinIf fails to arrive, the runtime error LINSM_E_CONFIRMATION_TIMEOUT applies [SWS_LinSM_00224]. Interpretation: It is presumably reported via Det_ReportRuntimeError. However, this interface is specified as mandatory only in a later version SWS LinSM p. 41.

Functionally, LinSM keeps the mode managers consistent even in the event of an error:

  • A failed wakeup leads to a renewed indication of the old state SWS LinSM p. 27.
  • An unsuccessful sleep confirmation nevertheless leads to LINSM_NO_COM SWS LinSM p. 24.
  • A rejected LinIf_GotoSleep produces E_NOT_OK and a state indication [SWS_LinSM_00177].
  • A rejected table switch leads to the reporting of the old table SWS LinSM p. 26.

Usage and Semantics

The function LinSM_ScheduleRequest ([SWS_LinSM_00113]) is used by an upper layer to request the switch of a schedule table on a LIN network. The service is provided via header LinSM.h, operates asynchronously, and is specified as reentrant.

Parameters:

  • network (NetworkHandleType): Identification of the LIN channel.
  • schedule (LinIf_SchHandleType): Pointer or handle to the schedule table to be newly requested.

Return Values and Error Behavior

The function returns a status of type Std_ReturnType ([SWS_LinSM_00113]):

  • E_OK: The request for the schedule table was successfully accepted.
  • E_NOT_OK: The request could not be executed (for example, if the module is not initialized).

Configuration Dependencies and Interaction

The availability of LinSM_ScheduleRequest is tied to the role configuration of the module: according to [SWS_LinSM_00241], the function is only available if module LinSM is configured as LIN master on at least one channel via configuration parameter LinSMNodeType. In a pure LIN slave configuration, the function is not available.

In an analogous manner, the associated confirmation function LinSM_ScheduleRequestConfirmation also requires that at least one channel is operated as LIN master ([SWS_LinSM_00242]).

The function LinSM_RequestComMode ([SWS_LinSM_00126]) is used to request a communication mode for a LIN channel. The call behaves asynchronously: the mode switch is not performed immediately; instead, LinSM notifies the caller as soon as the state transition is completed. As input parameters, network for identifying the LIN channel and mode for the requested communication mode are passed.

Regarding concurrency, the interface is specified as reentrant ([SWS_LinSM_00126]). As return value, the function returns E_OK if the request was successfully accepted. If execution of the request is not possible—for example, if the module is not initialized—E_NOT_OK is returned ([SWS_LinSM_00126]).

During interaction with other modules, the following error behavior is defined: If a call of LinIf_GotoSleep returns E_NOT_OK, LinSM_RequestComMode must also respond with E_NOT_OK ([SWS_LinSM_00177]). If the LinSM module returns E_NOT_OK for LinSM_RequestComMode, the same state must be retained or set, so that ComM_BusSM_ModeIndication and BswM_LinSM_CurrentState are called ([SWS_LinSM_00177]).

The callback function LinSM_ScheduleRequestConfirmation ([SWS_LinSM_00129]) serves as confirmation to module LinSM as soon as a previously requested new schedule table has actually been switched to active. It is called by the LIN interface (LinIf).

Usage and Parameters

The call is performed synchronously and provides no return value (void). The function is declared via header LinSM.h and has the service ID 0x20 according to [SWS_LinSM_00129]. It accepts two input parameters:

  • network (NetworkHandleType): Identification of the affected LIN channel.
  • schedule (LinIf_SchHandleType): Pointer or handle to the now active schedule table.

Concurrency and Limitations

According to the specification, the function is classified as reentrant ([SWS_LinSM_00129]), allowing simultaneous confirmations for different channels to be processed.

Interaction

The function acts as an interface in the interaction between LinIf and LinSM: After a switch of the schedule table has been initiated, LinIf informs LinSM via this callback routine that the switch has taken effect ([SWS_LinSM_00129]).

<h4>State model per LIN network</h4>
<p>At startup, <code>LINSM_UNINIT</code> is active even before an API is called <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_7_1_1_LINSM_UNINIT.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_7_1_1_LINSM_UNINIT">SWS LinSM p. 22</a>. <code>LinSM_Init</code> initializes the module with a pointer to <code>LinSM_ConfigType</code> <a class="spec-record-ref" data-req="SWS_LinSM_00155" href="../../spec/record.html?id=SWS_LinSM_00155">[SWS_LinSM_00155]</a> <a class="spec-record-ref" data-req="SWS_LinSM_00221" href="../../spec/record.html?id=SWS_LinSM_00221">[SWS_LinSM_00221]</a>. After this, <code>LINSM_NO_COM</code> applies per network. <code>LinSM_Init</code> reports this first transition neither to ComM nor to BswM, because ComM may not yet be initialized at that time <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_1_3_LINSM_NO_COM.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_1_3_LINSM_NO_COM">SWS LinSM p. 23</a>. In <code>LINSM_NO_COM</code>, the bus remains silent.</p>
<p><code>LINSM_FULL_COM</code> is the only state in which communication is permitted on the LIN bus. Each network reaches it independently of the others. Upon entry, ComM receives <code>COMM_FULL_COMMUNICATION</code> and BswM receives <code>LINSM_FULL_COM</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_1_4_LINSM_FULL_COM.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_1_4_LINSM_FULL_COM">SWS LinSM p. 23</a>. Substate <code>LINSM_RUN_COMMUNICATION</code> becomes active <a class="spec-record-ref" data-req="SWS_LinSM_00301" href="../../spec/record.html?id=SWS_LinSM_00301">[SWS_LinSM_00301]</a>. LinSM reports to BswM via <code>LinSM_ModeType</code> with the values <code>LINSM_FULL_COM</code> (0x01) and <code>LINSM_NO_COM</code> (0x02) <a class="spec-record-ref" data-req="SWS_LinSM_00220" href="../../spec/record.html?id=SWS_LinSM_00220">[SWS_LinSM_00220]</a> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_3_20_BswM_LinSM_CurrentState.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_3_20_BswM_LinSM_CurrentState">SWS BswM p. 72</a>.</p>
<p>The second substate <code>LINSM_GOTO_SLEEP</code> bridges the waiting time for the sleep confirmation. If <code>LinSM_GotoSleepConfirmation</code> arrives in this substate, LinSM transitions to <code>LINSM_NO_COM</code> regardless of parameter <code>success</code>; in all other states, the callback is ignored <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep">SWS LinSM p. 24</a>. <code>LINSM_GOTO_SLEEP</code> is presumably entered as soon as <code>LinIf_GotoSleep</code> returns with <code>E_OK</code>; the source breaks off at this point. An older diagram calls the running state <code>LINSM_RUN_SCHEDULE</code> <a class="docref internal-spec-ref" href="../../../spec/figures/FIG-9b8b9448a2891488.html" data-snip="FIG-9b8b9448a2891488">SWS LinSM Fig. 5 p. 22</a>. The name from <a class="spec-record-ref" data-req="SWS_LinSM_00301" href="../../spec/record.html?id=SWS_LinSM_00301">[SWS_LinSM_00301]</a> is authoritative.</p>

<h4>Wakeup: from ComM request to LINSM_FULL_COM</h4>
<p><code>LinSM_RequestComMode</code> operates asynchronously. The mode change does not take place immediately, and LinSM notifies the caller after completion <a class="spec-record-ref" data-req="SWS_LinSM_00126" href="../../spec/record.html?id=SWS_LinSM_00126">[SWS_LinSM_00126]</a>. For <code>COMM_FULL_COMMUNICATION</code>, LinSM calls <code>LinIf_Wakeup</code> directly, that is, without waiting for the next main function, and resets the retry counter <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process">SWS LinSM p. 27</a>. Before that, it starts a confirmation timer for the network with <code>LinSMConfirmationTimeout</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests">SWS LinSM p. 27</a>.</p>
<p>LinIf reports the transmission of the wakeup signal via <code>LinSM_WakeupConfirmation</code> <a class="spec-record-ref" data-req="SWS_LinSM_00132" href="../../spec/record.html?id=SWS_LinSM_00132">[SWS_LinSM_00132]</a>. If <code>success</code> = TRUE, the network transitions to <code>LINSM_FULL_COM</code>. Otherwise, LinSM sets the previous state again so that ComM and BswM still receive a mode indication <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process">SWS LinSM p. 27</a>. If <code>LinSMTransceiverPassiveMode</code> is configured, LinSM activates the transceiver via <code>LinIf_SetTrcvMode</code> upon entering <code>LINSM_FULL_COM</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_1_4_LINSM_FULL_COM.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_1_4_LINSM_FULL_COM">SWS LinSM p. 23</a>.</p>
<p>A silence-after-wakeup timer with <code>LinSMSilenceAfterWakeupTimeout</code> prevents wakeup attempts that are too close together <a class="spec-record-ref" data-req="SWS_LinSM_00235" href="../../spec/record.html?id=SWS_LinSM_00235">[SWS_LinSM_00235]</a>. If ComM requests <code>COMM_FULL_COMMUNICATION</code> while this timer is running, LinSM delays <code>LinIf_Wakeup</code> until expiration <a class="spec-record-ref" data-req="SWS_LinSM_00237" href="../../spec/record.html?id=SWS_LinSM_00237">[SWS_LinSM_00237]</a>. If full communication is still requested after expiration, LinSM restarts the wakeup process <a class="spec-record-ref" data-req="SWS_LinSM_00236" href="../../spec/record.html?id=SWS_LinSM_00236">[SWS_LinSM_00236]</a>.</p>
<p>A slave confirms the wakeup only when it receives the first LIN header from the master <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LIN_SECTION_7_4_3_2_Wake_up_process_in_slave_nodes.html" data-snip="SNIP_CLASSIC_LIN_SECTION_7_4_3_2_Wake_up_process_in_slave_nodes">SWS LinIf p. 52</a>. If the master does not start scheduling, the confirmation does not occur. The timer in LinSM then expires so that it does not wait indefinitely <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests">SWS LinSM p. 27</a>.</p>

<h4>Going to sleep: Master sends, slave reacts</h4>
<p><strong>Master:</strong> If ComM requests <code>COMM_NO_COMMUNICATION</code> in <code>LINSM_FULL_COM</code>, LinSM calls <code>LinIf_GotoSleep</code> to send the goto-sleep command <a class="spec-record-ref" data-req="SWS_LinSM_10208" href="../../spec/record.html?id=SWS_LinSM_10208">[SWS_LinSM_10208]</a>. The call is made directly, that is, without waiting for the next main function <a class="spec-record-ref" data-req="SWS_LinSM_00036" href="../../spec/record.html?id=SWS_LinSM_00036">[SWS_LinSM_00036]</a>. In all other cases, it is omitted <a class="spec-record-ref" data-req="SWS_LinSM_10209" href="../../spec/record.html?id=SWS_LinSM_10209">[SWS_LinSM_10209]</a>. If <code>LinIf_GotoSleep</code> returns <code>E_NOT_OK</code>, <code>LinSM_RequestComMode</code> also returns <code>E_NOT_OK</code>. At the same time, LinSM sets the previous state again so that ComM and BswM are informed <a class="spec-record-ref" data-req="SWS_LinSM_00177" href="../../spec/record.html?id=SWS_LinSM_00177">[SWS_LinSM_00177]</a>.</p>
<p>LinIf reports whether the command was sent via <code>LinSM_GotoSleepConfirmation</code> <a class="spec-record-ref" data-req="SWS_LinSM_00135" href="../../spec/record.html?id=SWS_LinSM_00135">[SWS_LinSM_00135]</a>. The notification of entering <code>LINSM_NO_COM</code> to BswM and ComM takes place in any case, even after a problem <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep">SWS LinSM p. 24</a>.</p>

<p><strong>Slave:</strong> If ComM requests <code>COMM_NO_COMMUNICATION</code> in <code>LINSM_FULL_COM</code>, LinSM only stores the request and returns <code>E_OK</code> <a class="spec-record-ref" data-req="SWS_LinSM_00230" href="../../spec/record.html?id=SWS_LinSM_00230">[SWS_LinSM_00230]</a>. The trigger comes from the bus. LinIf calls <code>LinSM_GotoSleepIndication</code> when a goto-sleep command is received or a bus idle timeout occurs <a class="spec-record-ref" data-req="SWS_LinSM_91000" href="../../spec/record.html?id=SWS_LinSM_91000">[SWS_LinSM_91000]</a>. LinSM then directly calls <code>LinIf_GotoSleep</code> in <code>LINSM_FULL_COM</code> <a class="spec-record-ref" data-req="SWS_LinSM_00231" href="../../spec/record.html?id=SWS_LinSM_00231">[SWS_LinSM_00231]</a>.</p>
<p>If <code>LinIf_GotoSleep</code> returns <code>E_OK</code> and <code>COMM_NO_COMMUNICATION</code> was requested, LinSM reports the bus-sleep event to ComM via <code>ComM_BusSM_BusSleepMode</code> <a class="spec-record-ref" data-req="SWS_LinSM_00233" href="../../spec/record.html?id=SWS_LinSM_00233">[SWS_LinSM_00233]</a>. Later versions formulate this obligation without the E_OK condition <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_COMM_SECTION_7_1_5_2_Goto_sleep_specific_for_slave_node.html" data-snip="SNIP_CLASSIC_COMM_SECTION_7_1_5_2_Goto_sleep_specific_for_slave_node">SWS LinSM p. 26</a>; for R20-11, the requirement applies. If, on the other hand, full communication is requested, LinSM restarts the wakeup process after the goto-sleep sequence <a class="spec-record-ref" data-req="SWS_LinSM_00234" href="../../spec/record.html?id=SWS_LinSM_00234">[SWS_LinSM_00234]</a>.</p>

<p><code>LinSM_ScheduleRequest</code> and <code>LinSM_ScheduleRequestConfirmation</code> exist only if at least one channel is configured as master <a class="spec-record-ref" data-req="SWS_LinSM_00241" href="../../spec/record.html?id=SWS_LinSM_00241">[SWS_LinSM_00241]</a> <a class="spec-record-ref" data-req="SWS_LinSM_00242" href="../../spec/record.html?id=SWS_LinSM_00242">[SWS_LinSM_00242]</a>. With <code>LinSM_ScheduleRequest</code>, the upper layer asynchronously requests a different schedule table <a class="spec-record-ref" data-req="SWS_LinSM_00113" href="../../spec/record.html?id=SWS_LinSM_00113">[SWS_LinSM_00113]</a>. LinSM immediately forwards the request to <code>LinIf_ScheduleRequest</code> and returns its return value <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only">SWS LinSM p. 26</a>. A typical caller is BswM, which uses the symbolic <code>LinSMScheduleIndex</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_10_3_5_LinSMSchedule.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_10_3_5_LinSMSchedule">SWS LinSM p. 52</a>. The LIN transport protocol sequence (LinTp) also switches to diagnostic tables via BswM in this way <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_9_7_Transport_Protocol_message_reception.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_9_7_Transport_Protocol_message_reception">SWS LinIf p. 142</a>.</p>
<p>After <code>LinSM_ScheduleRequestConfirmation</code> <a class="spec-record-ref" data-req="SWS_LinSM_00129" href="../../spec/record.html?id=SWS_LinSM_00129">[SWS_LinSM_00129]</a>, LinSM reports the active table via <code>BswM_LinSM_CurrentSchedule</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_3_19_BswM_LinSM_CurrentSchedule.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_3_19_BswM_LinSM_CurrentSchedule">SWS BswM p. 80</a>, provided its timer has not yet expired. For the remaining cases, these rules apply <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only">SWS LinSM p. 26</a>:</p>
<ul>
<li>If the timer has expired, LinSM reports the unchanged table.</li>
<li>In case of <code>E_NOT_OK</code> from <code>LinIf_ScheduleRequest</code>, it reports the old table in the next main function.</li>
<li>It also reports unrequested switches, such as the NULL schedule when going to sleep.</li>
</ul>
<p>In R20-11, the parameter is called <code>schedule</code> <a class="spec-record-ref" data-req="SWS_LinSM_00113" href="../../spec/record.html?id=SWS_LinSM_00113">[SWS_LinSM_00113]</a>. R22-11 renamed the arguments <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_CLASSICPLATFORMRELEASEOVERVIEW_SECTION_00202_LinIf_ScheduleRequest_and_schedule.html" data-snip="SNIP_CLASSIC_CLASSICPLATFORMRELEASEOVERVIEW_SECTION_00202_LinIf_ScheduleRequest_and_schedule">Release Overview p. 50</a>; later versions call it <code>ScheduleTableIdx</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_8_3_2_LinSM_ScheduleRequest.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_8_3_2_LinSM_ScheduleRequest">SWS LinSM p. 34</a>.</p>

<h4>Configuration: Node type, time base, and initialization</h4>
<p><code>LinSMNodeType</code> determines the API scope. Master functions exist as soon as a channel is a master; <code>LinSM_GotoSleepIndication</code> exists as soon as a channel is a slave <a class="spec-record-ref" data-req="SWS_LinSM_00241" href="../../spec/record.html?id=SWS_LinSM_00241">[SWS_LinSM_00241]</a> <a class="spec-record-ref" data-req="SWS_LinSM_00243" href="../../spec/record.html?id=SWS_LinSM_00243">[SWS_LinSM_00243]</a>. Mixed configurations are therefore possible. The post-build parameters reside in the implementation-specific structure <code>LinSM_ConfigType</code> <a class="spec-record-ref" data-req="SWS_LinSM_00221" href="../../spec/record.html?id=SWS_LinSM_00221">[SWS_LinSM_00221]</a>.</p>
<p><code>LinSM_MainFunction</code> periodically drives the timers for request timeouts <a class="spec-record-ref" data-req="SWS_LinSM_00156" href="../../spec/record.html?id=SWS_LinSM_00156">[SWS_LinSM_00156]</a>. Each network has its own confirmation timer. <code>LinSMConfirmationTimeout</code> must be 0 or an integer multiple of the main function period <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_8_Timeout_of_requests">SWS LinSM p. 27</a>.</p>
<p>The container <code>LinSMSchedule</code> (0..*, master only) references LinIf tables; <code>LinSMScheduleIndex</code> must correspond to the LinIf value <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_10_3_5_LinSMSchedule.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_10_3_5_LinSMSchedule">SWS LinSM p. 52</a>. An example in the mode management guide shows a BswM rule that calls <code>LinSM_Init</code> after <code>LinIf_Init</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_4_1_Startup.html" data-snip="SNIP_CLASSIC_MODEMANAGEMENTGUIDE_SECTION_4_1_Startup">Modemanagement-Leitfaden p. 54</a> <a class="spec-record-ref" data-req="SWS_LinSM_00155" href="../../spec/record.html?id=SWS_LinSM_00155">[SWS_LinSM_00155]</a>.</p>

<h4>Behavior in the event of an error</h4>
<p>With <code>LinSMDevErrorDetect</code>, LinSM reports development errors to the DET. The codes are <code>LINSM_E_UNINIT</code>, <code>LINSM_E_NONEXISTENT_NETWORK</code>, <code>LINSM_E_PARAMETER</code>, <code>LINSM_E_PARAM_POINTER</code>, and <code>LINSM_E_INIT_FAILED</code> <a class="spec-record-ref" data-req="SWS_LinSM_00053" href="../../spec/record.html?id=SWS_LinSM_00053">[SWS_LinSM_00053]</a>. Callbacks such as <code>LinSM_GotoSleepIndication</code> report an invalid network or the UNINIT state <a class="spec-record-ref" data-req="SWS_LinSM_00239" href="../../spec/record.html?id=SWS_LinSM_00239">[SWS_LinSM_00239]</a> <a class="spec-record-ref" data-req="SWS_LinSM_00240" href="../../spec/record.html?id=SWS_LinSM_00240">[SWS_LinSM_00240]</a>. For such errors, services additionally return <code>E_NOT_OK</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_8_3_5_LinSM_RequestComMode.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_8_3_5_LinSM_RequestComMode">SWS LinSM p. 36</a>. Invalid pointers at <code>LinSM_GetCurrentComMode</code> and <code>LinSM_GetVersionInfo</code> lead to <code>LINSM_E_PARAM_POINTER</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_8_3_4_LinSM_GetCurrentComMode.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_8_3_4_LinSM_GetCurrentComMode">SWS LinSM p. 35</a> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINSM_SECTION_8_3_3_LinSM_GetVersionInfo.html" data-snip="SNIP_CLASSIC_LINSM_SECTION_8_3_3_LinSM_GetVersionInfo">SWS LinSM p. 34</a>.</p>
<p>If a callback from LinIf fails to arrive, the runtime error <code>LINSM_E_CONFIRMATION_TIMEOUT</code> applies <a class="spec-record-ref" data-req="SWS_LinSM_00224" href="../../spec/record.html?id=SWS_LinSM_00224">[SWS_LinSM_00224]</a>. Interpretation: It is presumably reported via <code>Det_ReportRuntimeError</code>. However, this interface is specified as mandatory only in a later version <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_8_6_Mandatory_Interfaces.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_8_6_Mandatory_Interfaces">SWS LinSM p. 41</a>.</p>
<p>Functionally, LinSM keeps the mode managers consistent even in the event of an error:</p>
<ul>
<li>A failed wakeup leads to a renewed indication of the old state <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_7_Wake_up_process">SWS LinSM p. 27</a>.</li>
<li>An unsuccessful sleep confirmation nevertheless leads to <code>LINSM_NO_COM</code> <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep.html" data-snip="SNIP_CLASSIC_LINIF_SECTION_7_1_5_Goto_sleep">SWS LinSM p. 24</a>.</li>
<li>A rejected <code>LinIf_GotoSleep</code> produces <code>E_NOT_OK</code> and a state indication <a class="spec-record-ref" data-req="SWS_LinSM_00177" href="../../spec/record.html?id=SWS_LinSM_00177">[SWS_LinSM_00177]</a>.</li>
<li>A rejected table switch leads to the reporting of the old table <a class="docref internal-spec-ref" href="../../../spec/snippets/SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only.html" data-snip="SNIP_CLASSIC_BSWM_SECTION_7_1_6_Changing_schedule_table_Master_only">SWS LinSM p. 26</a>.</li>
</ul>
