Role of the Default Error Tracer and its system boundary

In the Classic stack, the Default Error Tracer (DET) receives error messages centrally. It provides three reporting services. Det_ReportError serves for development errors [SWS_Det_00009], Det_ReportRuntimeError for runtime errors [SWS_Det_01001]. For transient faults, R20-11 also provides Det_ReportTransientFault [SWS_Det_01003]. In addition, there are the management services Det_Init, Det_Start, and Det_GetVersionInfo [SWS_Det_00008] [SWS_Det_00010] [SWS_Det_00011]. All services are available via Det.h.

The DET does not evaluate messages functionally itself. It distributes them to configured error hooks and callouts (SWS DET p. 16). According to the error description valid for R20-11, it thus reaches the DEM and the RTE via integrator-specific code (ErrorDescription p. 10). In addition, optional forwarding to the Dlt via Dlt_DetForwardErrorTrace is provided [SWS_Det_00211].

Context diagram: The DET is located between the reporting modules and the integrator code. Only configuration and callouts open the path to DEM and Dlt. Sources: SWS DET Abb. Interfaces p. 28, ErrorDescription p. 10, [SWS_Det_00211]

Startup: Det_Init and Det_Start in the startup sequence of the EcuM

The EcuM lists Det_Init and Det_ReportError among its optional interfaces (SWS EcuM p. 142). Det_Init has the service ID 0x00 and is synchronous and non-reentrant. The parameter ConfigPtr points to the selected configuration set [SWS_Det_00008]. Its type Det_ConfigType has an implementation-specific structure [SWS_Det_00210]. Det_Start (0x02) starts the tracer and is likewise synchronous and non-reentrant [SWS_Det_00010].

According to the initialization diagram, the EcuM first calls Det_Init and then Det_Start (SWS DET Abb. Initialisierung p. 32). The sources do not specify which services already take effect between the two calls. This point remains open here. Det_GetVersionInfo (0x03) is reentrant and writes the version information to the passed pointer [SWS_Det_00011].

Sequence diagram: The EcuM initializes the DET with a configuration set and starts it afterwards. Only then do messages in operation follow. Sources: SWS DET Abb. Initialisierung p. 32, [SWS_Det_00008], [SWS_Det_00010]

Three reporting paths with a common numbering scheme

All three reporting services have the same parameters: ModuleId (uint16), InstanceId, ApiId, and ErrorId or FaultId, respectively (each uint8) [SWS_Det_00009] [SWS_Det_01001] [SWS_Det_01003].

  • The ModuleId originates from the list of basic software modules. The BSW only uses the range 0..255.
  • The InstanceId counts from 0. A module with only one instance passes 0.
  • ApiId and ErrorId are defined by the SWS of the reporting module (EXP LSA p. 157).

Which service applies depends on the error type:

  • A BSW module reports development errors via Det_ReportError with its module ID. This applies only if development error detection is configured (SWS BSWGeneral p. 57). A query such as #if (SPI_DEV_ERROR_DETECT == ON) is typical for this (EXP LSA p. 113). An example is an invalid parameter in CanIf (SWS CanIf p. 101).
  • Runtime errors such as ADC_E_BUSY run via Det_ReportRuntimeError (SWS Adc p. 95).
  • Transient faults run via the transient fault service (SWS BSWGeneral p. 53).

In its module description, a module declares this need as ErrorTracerNeeds. Each of the three services is an optional role there (TPS BSWMDT p. 266).

Release note: Det_ReportTransientFault is normative in R20-11 [SWS_Det_01003]. Later versions list the service as obsolete (SWS DET p. 24). With R24-11, transient faults were completely removed (SWS DET p. 1).

Activity diagram: The error type determines the reporting service, the list of called hooks or callouts, and the consequence for the reporting module. Sources: SWS BSWGeneral p. 57, [SWS_Det_00501], [SWS_Det_00009]

Distribution to Error Hooks and Callouts

Every call of Det_ReportError calls all functions configured in DetErrorHook [SWS_Det_00501]. The hooks receive the same parameters as the original call (SWS DET p. 16). The hook interface <User_Error_Hooks> has the service ID 0x10 and is synchronous and reentrant [SWS_Det_00181]. It always returns E_OK (SWS DET p. 25).

Sequence diagram: Det_ReportError calls all configured hooks in succession, optionally also the Dlt. In R20-11, the service does not return to the reporting module. Sources: SWS DET Abb. ReportError p. 36, [SWS_Det_00501], [SWS_Det_00009], SWS Dlt p. 25

For Det_ReportRuntimeError, the same principle applies with the list DetReportRuntimeErrorCallout [SWS_Det_00501]. The callout <DetReportRuntimeErrorCallout> has the service ID 0x11 [SWS_Det_00184]. The DET returns E_OK to the reporting module (SWS DET Abb. Runtime mit Hook p. 35). If no callouts are configured, it responds immediately with E_OK (SWS DET Abb. Runtime ohne Hook p. 35).

Sequence diagram: For runtime errors, E_OK is the return value, with and without configured callouts. Sources: SWS DET Abb. Runtime mit Hook p. 35, SWS DET Abb. Runtime ohne Hook p. 35, [SWS_Det_00184]

The DET distributes transient faults to the list DetReportTransientFaultCallout [SWS_Det_00501]. The callout has the service ID 0x12 [SWS_Det_00187]. Unlike with runtime errors, the DET passes the return value of the callout on to the reporting module here. Without a callout, it returns E_OK (SWS DET Abb. Transient mit Hook p. 36, SWS DET Abb. Transient ohne Hook p. 36). For multiple callouts, the later version specifies the logical OR of the return values (SWS DET p. 24). Presumably, this rule already applies in R20-11.

Sequence diagram: For transient faults, the result of the callouts determines the return value to the reporting module. Sources: SWS DET Abb. Transient mit Hook p. 36, SWS DET Abb. Transient ohne Hook p. 36, [SWS_Det_00187]

Connection of SW-Cs via the Service Port DETService

SW-Cs reach the DET via the RTE. For each configured module instance, the DET provides a port Det_{Name} with the interface DETService [SWS_Det_00205]. The operations ReportError and ReportRuntimeError call the C API with the module ID of the port [SWS_Det_00202]. The required types uint8 and uint16 are AUTOSAR data types [SWS_Det_00200].

ModuleId and InstanceId are not passed by the SW-C itself. The RTE adds them as \"port defined argument values\" [SWS_Det_00203] [SWS_Det_00204]. Their specification is thus part of the RTE configuration [SWS_Det_00206]. ApiId and ErrorId are not standardized for SW-Cs and lie in the range 0x00..0xFF [SWS_Det_00203].

Collaboration diagram: Each SW-C instance has its own DET port. The RTE adds the identifiers in the process. Sources: SWS DET Abb. Service-Ports p. 33, [SWS_Det_00205], [SWS_Det_00206]

Configuration of Hook Lists and Callout Signatures

Notification is configured in the container DetNotification (0..1). It contains the lists DetErrorHook and DetReportRuntimeErrorCallout (0..* each). In the present later version, they have the configuration class Pre-compile (SWS DET p. 37). R20-11 additionally contains the list DetReportTransientFaultCallout [SWS_Det_00501]. A hook must have the same type as Det_ReportError, i.e. Std_ReturnType (*f)(uint16, uint8, uint8, uint8).

In general, callouts have the same signature as the associated function. Multiple callouts for the same service carry the same ID (SWS DET p. 25). The error description of R20-11 limits what such handlers may do: store the event, call the DEM, or execute short, appropriate actions (ErrorDescription p. 10). All three callout interfaces are specified as reentrant [SWS_Det_00181] [SWS_Det_00184] [SWS_Det_00187].

Behavior in the event of an error

In R20-11, \"Not Applicable: The function never returns\" is stated for Det_ReportError under Sync/Async [SWS_Det_00009]. Development errors are therefore treated like assertions. After the hooks, the normal control flow does not continue, for example via an infinite loop or a halt. If only one hook is configured, it may take over exception handling (RS BSWGeneral p. 33).

The flow diagram deviates from this: it shows a return arrow and designates the behavior as implementation-specific (SWS DET Abb. ReportError p. 36). Only R21-11 clarified the call behavior (SWS DET p. 1). For R20-11, the requirement is decisive.

For runtime errors, the reporting module continues, because Det_ReportRuntimeError always returns E_OK [SWS_Det_01001] (SWS DET p. 23). For transient faults, the reporting module receives the result of the callouts as return value [SWS_Det_01003] (SWS DET Abb. Transient mit Hook p. 36).

The DET itself knows only one development error of its own: DET_E_PARAM_POINTER (0x01). It occurs when Det_GetVersionInfo is called with a null pointer [SWS_Det_00301]. The DET reports this error to all functions configured in the callouts. Runtime and production errors are not applicable to the DET (SWS DET p. 18).

function Det_ReportError [SWS_Det_00009] 📄 PDF

Std_ReturnType Det_ReportError (uint16 ModuleId, uint8 InstanceId, uint8 ApiId, uint8 ErrorId);

Service to report development errors.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: d9b89e67d641 Provenance

The function Det_ReportError serves as a central service of the Default Error Tracer (DET) for reporting development errors ([SWS_Det_00009]). The interface is available via the header file Det.h.

Usage and Parameters

The call is made by BSW modules upon detection of a development error, passing the exact error context ([SWS_Det_00009]):

  • ModuleId: Module identifier of the calling software module.
  • InstanceId: Index-based instance ID of the module (starting at 0; modules with only one instance pass 0).
  • ApiId: Identifier of the API service in which the error occurred.
  • ErrorId: Identifier of the specific development error according to the specification of the calling module.

Formally, the function has the return type Std_ReturnType, but does not return any value; it possesses this type solely for compatibility with services and hooks ([SWS_Det_00009]). A classification into synchronous or asynchronous semantics is not applicable because Det_ReportError never returns to the caller according to the specification ([SWS_Det_00009]).

Concurrency and execution

The function is specified as reentrant ([SWS_Det_00009]). Upon a call to Det_ReportError, the DET executes all callback functions configured in parameter DetErrorHook ([SWS_Det_00501]).

Interaction

Other BSW modules report parameter errors directly to this service. For example, if parameter TransceiverId in CanIf_SetTrcvMode() or CanIf_SetTrcvWakeupMode() is invalid, the CAN Interface reports error code CANIF_E_PARAM_TRCV ([SWS_CANIF_00538], CAN Interface §8.3 “CanIf_SetTrcvMode”; [SWS_CANIF_00535], CAN Interface §8.3 “CanIf_SetTrcvWakeupMode”). In the event of an inadmissible mode parameter, CanIf_SetTrcvWakeupMode() correspondingly reports CANIF_E_PARAM_TRCVWAKEUPMODE to Det_ReportError ([SWS_CANIF_00536], CAN Interface §8.3 “CanIf_SetTrcvWakeupMode”).

function Det_ReportRuntimeError [SWS_Det_01001] 📄 PDF

Std_ReturnType Det_ReportRuntimeError (uint16 ModuleId, uint8 InstanceId, uint8 ApiId, faul tErrorTracer uint8 ErrorId);

Service to report runtime errors. If a callout has been configured then this callout shall be called.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: a0a10b5ba4ea Provenance

Usage and signature

The synchronous service Det_ReportRuntimeError ([SWS_Det_01001]) serves to report runtime errors to the Default Error Tracer (DET) and is available via the header Det.h. The function has the following parameters:

  • ModuleId: Module identifier of the calling module.
  • InstanceId: Index-based instance ID of the module (0 for single-instance modules).
  • ApiId: Identifier of the API service in which the error was detected.
  • ErrorId: Specific identifier of the detected runtime error (defined in the specification of the calling module).

The return value is always E_OK ([SWS_Det_01001]).

Concurrency and behavior

The interface is defined as reentrant ([SWS_Det_01001]). When Det_ReportRuntimeError is called, all callback functions configured in DetReportRuntimeErrorCallout are called ([SWS_Det_00503]).

Interaction and error context

Calling modules use the service to report specific error states during runtime. For example, module CanIf reports error code CANIF_E_STOPPED to Det_ReportRuntimeError upon a transmit request via a channel in mode CANIF_OFFLINE ([SWS_CANIF_00382], AUTOSAR_SWS_CANInterface p. 40 §7.10 “Transmit data flow”). Another use case is exceeding the global PDU length with truncation disabled in CanIf_Transmit(), which triggers the reporting of runtime error CANIF_E_TXPDU_LENGTH_EXCEEDED ([SWS_CANIF_00900], AUTOSAR_SWS_CANInterface p. 81 §8.3.7 “CanIf_ReadRxPduData”).

function Det_ReportTransientFault [SWS_Det_01003] 📄 PDF

Std_ReturnType Det_ReportTransientFault (uint16 ModuleId, uint8 InstanceId, uint8 ApiId, uint8 FaultId);

Service to report transient faults. If a callout has been configured than this callout shall be called and the returned value of the callout shall be returned. Otherwise it returns immediately with E_ OK.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 7ff799437520 Provenance

Usage and Semantics

The function Det_ReportTransientFault serves to report transient faults to the Default Error Tracer according to [SWS_Det_01003]. The service is executed synchronously and is specified as reentrant. The declaration is provided via Det.h.

The input parameters include:

  • ModuleId: Module identifier of the calling software module.
  • InstanceId: Index-based instance ID of the module (starting from 0; single-instance modules always pass 0).
  • ApiId: Identifier of the API service in which the transient fault occurred.
  • FaultId: Identifier of the respectively detected transient fault.

Interaction and Callout Behavior

When calling Det_ReportTransientFault, all callback functions configured under DetReportTransientFaultCallout are called according to [SWS_Det_00502].

According to [SWS_Det_01003], the following semantics apply to the return value of type Std_ReturnType:

  • If no callout is configured, an immediate return with E_OK occurs.
  • If a callout is present, the return value of this configured callout is returned.
  • If multiple callouts are configured, the logical OR combination (sum) of all callout return values is returned. Since E_OK = 0 is defined, the service only returns E_OK if all called callouts without exception report E_OK.

Concurrency and Limitations

Due to the specified reentrancy ([SWS_Det_01003]), the interface can be called concurrently by multiple module instances or tasks, provided the configured callouts support this behavior.

use

The callback function <User_Error_Hooks> according to [SWS_Det_00181] serves as a user-specific hook interface for notification of development errors that have occurred in the Default Error Tracer (DET). It has the service ID 0x10 and is provided via the header file Det_Externals.h.

The call takes place synchronously to the reporting time of the error. The interface accepts the following parameters:

  • ModuleId (uint16): Module identifier of the reporting software module.
  • InstanceId (uint8): Index-based instance ID of the module (starting at 0; for single-instance modules, 0 shall be passed).
  • ApiId (uint8): Identifier of the API service in which the error was detected (according to the specification of the source module).
  • ErrorId (uint8): Identifier of the detected development error (according to the specification of the source module).

Return value and error handling

The function always returns E_OK as a return value of type Std_ReturnType [SWS_Det_00181]. Dedicated error states or differing return values are not supported; according to the specification, internal forwarding to the Diagnostic Event Manager (DEM) or separate error logs is not intended at this interface.

Concurrency and Limitations

According to [SWS_Det_00181], the function is defined as reentrant. Since processing takes place synchronously, the user-specific hook implementation is likely designed to be non-blocking in order not to unduly delay the execution time of the calling component.

Usage and Call Context

The callout function <Det Report Runtime Error Callout> is declared via the header Det_Externals.h [SWS_Det_00184]. The call is synchronous and specified as reentrant [SWS_Det_00184]. The function always returns E_OK of type Std_ReturnType as return value, as this is specified for services [SWS_Det_00184].

The interface has the service ID 0x11 and expects four input parameters [SWS_Det_00184]:

  • ModuleId: Identifier (Module ID) of the reporting software module [SWS_Det_00184].
  • InstanceId: Index-based instance ID of the module starting at 0. If the module has only a single instance, the value 0 must be passed for this [SWS_Det_00184].
  • ApiId: Identifier of the API function in which the runtime error was detected, defined in the specification of the respective caller [SWS_Det_00184].
  • ErrorId: Identifier of the reported runtime error according to the specification of the calling module [SWS_Det_00184].

Error Handling and Concurrency

Since the call is defined as reentrant, the provided callout implementation must be designed for parallel access from multiple contexts or by different module instances [SWS_Det_00184]. Input or output parameters of type inout or out are not present [SWS_Det_00184]. Specific error codes for the return value do not exist; presumably, the fixed return of E_OK purely serves to satisfy standardized service conventions in the AUTOSAR environment and does not allow rejecting the error report.

use

The callout function according to [SWS_Det_00187] (service ID 0x12) is provided via the header file Det_Externals.h. It serves as a user-specific interface for handling transient faults. The call is synchronous and specified as reentrant.

The function accepts the following input parameters:

  • ModuleId: Module identifier of the calling module.
  • InstanceId: Zero-based index of the module instance; for modules with only one instance, 0 is passed.
  • ApiId: Identifier of the API service in which the transient fault was detected.
  • FaultId: Identifier of the detected transient fault according to the specification of the calling module.

The function returns Std_ReturnType as return value. This return value is propagated directly to the caller of Det_ReportTransientFault.

Error Handling and Concurrency

No separate DET or DEM error notifications are defined within [SWS_Det_00187]. The behavior in case of error is primarily controlled by the return value of type Std_ReturnType, which the implementation of the callout reports back to the caller.

With respect to concurrency, the interface is specified as reentrant. Since the call is synchronous, the implementation of the callout function should not execute any blocking operations in order to prevent delaying the calling module.
