Role and system boundary: Check program flow, enable hardware watchdog

The Watchdog Manager (WdgM) supervises the execution of Supervised Entities (SE). Based on the result, it decides whether the hardware watchdogs continue to be serviced. The timing-accurate triggering is encapsulated in the Watchdog Driver. Via the Watchdog Interface, the WdgM merely sets a trigger condition that instructs the driver to continue triggering SWS WdgM p. 56. For this, it mandatorily requires WdgIf_SetMode, WdgIf_SetTriggerCondition, the OS function GetElapsedValue, and Det_ReportRuntimeError [SWS_WdgM_00161].

In R20-11, the module also optionally uses BswM_WdgM_RequestPartitionReset, Dem_SetEventStatus, Det_ReportError, and Mcu_PerformReset [SWS_WdgM_00162]. For the partition reset request, the BswM creates a dedicated ModeRequestSource per partition Mode Management Guide p. 30. In the safety concept, logical program flow monitoring with checkpoints and allowed transitions is the mechanism through which the WdgM fulfills the associated safety requirements Safety Concept p. 47.

Context diagram: The WdgM is located between the supervised applications, the controlling BSW modules, and the watchdog stack, and uses OS, DET, DEM, and Mcu as services. Sources: [SWS_WdgM_00161], [SWS_WdgM_00162], SWS WdgM p. 85, SWS EcuM p. 34

Lifecycle: Initialization, operation, sleep, and reset

WdgM_Init receives a pointer to WdgM_ConfigType. This structure contains all post-build configurable parameters [SWS_WdgM_00151] [SWS_WdgM_00355]. After the call, supervision is activated for the Supervised Entities of the initial mode. Re-initialization takes place via WdgM_DeInit followed by WdgM_Init SWS WdgM p. 74. Before initialization, the global status is statically set to WDGM_GLOBAL_STATUS_DEACTIVATED [SWS_WdgM_00387]. WdgM_Init also clears the SEID of the entity that expired first, which is stored in uninitialized RAM [SWS_WdgM_00370].

Supervision functions, reference cycles, and watchdog handling start only with the first call of WdgM_MainFunction after initialization [SWS_WdgM_00406]. If WdgMDemStoppedSupervisionReport is set, the WdgM reports WDGM_E_SUPERVISION as PASSED to the DEM in this first cycle [SWS_WdgM_00408]. The specification shows the startup as a sequence between EcuM, WdgM, and WdgIf SWS WdgM p. 102.

Sequence diagram: Initialization establishes the initial mode and applies the watchdog modes; supervision only becomes active with the first main function. Sources: [SWS_WdgM_00151], [SWS_WdgM_00030], [SWS_WdgM_00186], [SWS_WdgM_00406], [SWS_WdgM_00408], SWS WdgM p. 102

WdgM_DeInit stops supervision and watchdog handling [SWS_WdgM_00407]. Beforehand, the WdgM sets the trigger conditions of all running watchdogs via mode switch to a timeout that permits the remaining shutdown without a reset. This is a consequence of the "Windowed Watchdogs" concept SWS WdgM p. 75. Before SLEEP, the EcuM calls WdgM_DeInit. As long as the WdgM is deactivated, still active modules such as BswM or EcuM must service the hardware watchdogs SWS WdgM p. 59.

WdgM_PerformReset sets the trigger condition of all watchdog drivers to 0 and does not update it thereafter. The hardware watchdog then triggers an external reset [SWS_WdgM_00264] SWS WdgM p. 82. The EcuM lists this path as a dedicated reset target alongside Mcu_PerformReset SWS EcuM p. 72.

Sequence diagram: During sleep, the WdgM hands over the watchdogs with an extended timeout; during a targeted reset, it deliberately lets them expire. Sources: [SWS_WdgM_00261], [SWS_WdgM_00407], [SWS_WdgM_00264], SWS WdgM p. 59, SWS WdgM p. 82

Checkpoints and the three supervision functions

Supervised Entities report their progress synchronously and reentrantly via WdgM_CheckpointReached(SEID, CheckpointID) [SWS_WdgM_00263]. Both IDs are uint16. A checkpoint is uniquely identified only by the pair of SEID and checkpoint ID [SWS_WdgM_00356] [SWS_WdgM_00357]. The work is distributed across two contexts. In the context of the SE, the incrementing of the alive counter as well as the deadline and logical checks are executed. The cyclic WdgM_MainFunction then evaluates per SE SWS WdgM p. 32 [SWS_WdgM_00159].

  • Alive Supervision checks the cyclic execution. The parameters apply per checkpoint: WdgMExpectedAliveIndications, WdgMMinMargin, WdgMMaxMargin, and WdgMSupervisionReferenceCycle. The main function checks the counter in the respective reference cycle SWS WdgM p. 42 SWS WdgM p. 42.
  • Deadline Supervision measures the time between start and end checkpoint. GetElapsedValue with the OS counter of the SE, scaled via OsSecondsPerTick, serves this purpose [SWS_WdgM_00373] [SWS_WdgM_00374]. If the start timestamp is missing at the end checkpoint (value 0), the call terminates successfully without measurement [SWS_WdgM_00354]. The main function detects timeouts provided that WdgMEnableTimeoutDetection is set [SWS_WdgM_00403] [SWS_WdgM_00404].
  • Logical Supervision checks the sequence along configured graphs. Internal transitions lie within an SE; external transitions connect checkpoints of different SEs SWS WdgM p. 65 SWS WdgM p. 61. The WdgM derives the necessary data resources from the number of SEs, modes, and configured transitions [SWS_WdgM_00366].

Sequence diagram: Checkpoint reports are checked immediately; the main function consolidates the results into status, mode notifications, and trigger condition. Sources: [SWS_WdgM_00263], [SWS_WdgM_00373], [SWS_WdgM_00404], [SWS_WdgM_00197], [SWS_WdgM_00198], SWS WdgM p. 32, SWS WdgM p. 78

From local to global supervision status

Each SE has a local status of type WdgM_LocalStatusType with the values OK, FAILED, EXPIRED, and DEACTIVATED. FAILED remains "recoverable" as long as the configurable failure threshold is not exceeded [SWS_WdgM_00359]. A tolerance via WdgMFailedAliveSupervisionRefCycleTol exists only for Alive Supervision. Deadline and logical errors lead directly to EXPIRED SWS WdgM p. 30 SWS WdgM p. 126.

State diagram: The local status of an SE can return from FAILED; EXPIRED is final. Sources: [SWS_WdgM_00359], [SWS_WdgM_00315], [SWS_WdgM_00182], SWS WdgM p. 34

The WdgM calculates the global status WdgM_GlobalStatusType from all local statuses. In addition to the local values, STOPPED exists here. In EXPIRED, the driver continues to trigger; in STOPPED, it is instructed to stop triggering, and a watchdog reset follows [SWS_WdgM_00360]. How long EXPIRED postpones the reset is determined by WdgMExpiredSupervisionCycleTol in multiples of the Supervision Cycle. The main function calculates the status in each cycle SWS WdgM p. 34. Both statuses can be queried via WdgM_GetGlobalStatus and WdgM_GetLocalStatus [SWS_WdgM_00175] [SWS_WdgM_00169].

State diagram: The global status escalates from OK via FAILED and EXPIRED to STOPPED and ends in a watchdog reset. Sources: [SWS_WdgM_00360], [SWS_WdgM_00387], [SWS_WdgM_00139], SWS WdgM p. 38, SWS WdgM p. 32, SWS WdgM p. 57

Modes and configuration: WdgMMode as bracket

WdgMConfigSet contains the WdgMInitialMode and 1 to 255 containers WdgMMode SWS WdgM p. 114. A mode bundles:

  • the tolerance WdgMExpiredSupervisionCycleTol,
  • the alive, deadline, and external logical supervisions,
  • the local status parameters,
  • the trigger configuration WdgMTrigger SWS WdgM p. 117.

WdgMTrigger specifies the WdgMWatchdogMode (FAST, SLOW, OFF) and the WdgMTriggerConditionValue per watchdog SWS WdgM p. 125. VARIANT-PRE-COMPILE and VARIANT-POST-BUILD are supported SWS WdgM p. 97. The ECU integrator configures top-down from the ServiceNeeds of the applications TR Methodology p. 389. Per SE, the SupervisedEntityNeeds describe, for instance, the activation at startup and the alive cycle times SWC Template p. 716.

WdgM_SetMode(Mode) is synchronous and non-reentrant [SWS_WdgM_00154]. The service is executed only when the global status is OK or FAILED [SWS_WdgM_00145]. SEs that are active in the new mode retain their state [SWS_WdgM_00182]. Deactivated SEs transition to DEACTIVATED; their results and error counters are reset [SWS_WdgM_00315]. Subsequently, all watchdogs receive their mode parameters via WdgIf_SetMode [SWS_WdgM_00186]. As long as the new mode is not yet fully active, WdgM_GetMode returns the previous mode [SWS_WdgM_00168] SWS WdgM p. 77.

Activity diagram: A mode change has three preconditions and treats SEs and watchdogs separately; if WdgIf_SetMode fails, the change escalates. Sources: [SWS_WdgM_00145], [SWS_WdgM_00392], [SWS_WdgM_00031], [SWS_WdgM_00182], [SWS_WdgM_00315], [SWS_WdgM_00186], [SWS_WdgM_00139], SWS WdgM p. 57

Ports, data types, and status notifications to applications

  • Checkpoint reporting: There is a service port [SWS_WdgM_00146] per SE. It is named localSupervision_{SupervisedEntityCheckpointName}, provides WdgM_LocalSupervision with the operation CheckpointReached, and carries SEID and checkpoint ID as Port-Defined Arguments [SWS_WdgM_00147] [SWS_WdgM_00333].
  • Mode notifications: For each SE, there is the port mode_{SupervisedEntityName} with WdgM_LocalMode [SWS_WdgM_00148] [SWS_WdgM_00149] [SWS_WdgM_00335]. In addition, there is a single port globalmode with WdgM_GlobalMode [SWS_WdgM_00150] [SWS_WdgM_00336]. Both use the Mode Declaration Group WdgM_Mode with the values SUPERVISION_OK (0) to SUPERVISION_DEACTIVATED (4) [SWS_WdgM_00334].
  • Queries: The port globalSupervision provides WdgM_GlobalSupervision [SWS_WdgM_91002] [SWS_WdgM_91001]. Per SE, localSupervisonStatus_{SupervisedEntityName} provides the interface WdgM_LocalSupervisionStatus [SWS_WdgM_91003] [SWS_WdgM_91004].

If a local status changes, the WdgM reports this immediately via the mode port of the SE [SWS_WdgM_00197]. Changes to the global status go via the global mode port [SWS_WdgM_00198] and are reported only once [SWS_WdgM_00199]. Local and global status have separate interfaces. Thus, the global port does not appear in the Indirect Port API list through which the WdgM addresses all local mode ports SWS WdgM p. 101 SWS WdgM p. 100. BSW modules request the global services via GlobalSupervisionNeeds BSWMD Template p. 257.

Context diagram: Supervised SW-Cs report checkpoints and receive their local status; a state-managing component uses the global status and the global services. Sources: [SWS_WdgM_00147], [SWS_WdgM_00149], [SWS_WdgM_00150], [SWS_WdgM_91002], [SWS_WdgM_91003], SWS WdgM p. 99

Behavior in the event of an error

Error handling ranges from local recovery in the SE to a reset of the ECU SWS WdgM p. 53. If the global status reaches STOPPED, the WdgM reports the DEM event WDGM_E_SUPERVISION [SWS_WdgM_00375]. Which DemEventParameter is used for this is specified by WdgMDemEventParameterRefs SWS WdgM p. 116.

After a restart, the causing SE can be determined. WdgM_GetFirstExpiredSEID is available even before WdgM_Init [SWS_WdgM_00346] [SWS_WdgM_00348]. The service reads a doubly inverted stored value from uninitialized RAM. If value and inverse do not match, it returns E_NOT_OK and writes 0 to *SEID [SWS_WdgM_00349]. According to the change history, it was introduced precisely for evaluation after a restart SWS WdgM p. 3.

The WdgM reports runtime errors independently of WdgMDevErrorDetect [SWS_WdgM_00402]:

  • WDGM_E_DISABLE_NOT_ALLOWED: A transition to WDGIF_OFF_MODE is not permitted. The error can occur in WdgM_SetMode and WdgM_Init [SWS_WdgM_00031] [SWS_WdgM_00030].
  • WDGM_E_SET_MODE: WdgIf_SetMode has failed [SWS_WdgM_00139]. The WdgM then assumes a global error and sets STOPPED. The reset follows when the first watchdog expires, or immediately if an immediate reset is configured SWS WdgM p. 57.
  • WDGM_E_SEDEACTIVATED: A checkpoint belongs to an SE that is deactivated in the current mode. The call returns E_NOT_OK [SWS_WdgM_00319].

WdgM_Init has no return value [SWS_WdgM_00151], although [SWS_WdgM_00030] refers to a return with E_NOT_OK. Interpretation: For callers, the refused start is presumably only detectable via the reported runtime error.

Development errors such as WDGM_E_UNINIT, WDGM_E_PARAM_MODE, WDGM_E_PARAM_SEID, WDGM_E_INV_POINTER, and WDGM_E_CPID are defined in [SWS_WdgM_00004]. If WdgMDevErrorDetect is active, the services in the DEACTIVATED state report WDGM_E_UNINIT [SWS_WdgM_00253] [SWS_WdgM_00173] [SWS_WdgM_00279]. Without the option, they return without effect there [SWS_WdgM_00394] [SWS_WdgM_00397] [SWS_WdgM_00401]. For WdgM_Init, [SWS_WdgM_00389] specifies the DEACTIVATED state as the error case, whereas its counterpart [SWS_WdgM_00390] specifies "not DEACTIVATED". Interpretation: In both cases, this is probably intended to protect against double initialization.

Usage and Semantics

The synchronous and reentrant function WdgM_CheckpointReached ([SWS_WdgM_00263]) signals to the Watchdog Manager that a specific checkpoint within a supervised entity has been reached. It is provided via the header file WdgM.h and accepts as input parameters the identifier of the reporting entity (SEID) and the identifier of the reached checkpoint (Checkpoint ID). If the alive counter could be updated successfully, the function returns E_OK; if the update fails, it returns E_NOT_OK ([SWS_WdgM_00263]).

Error Handling and Initialization State

If the Watchdog Manager is in the global deactivation state WDGM_GLOBAL_STATUS_DEACTIVATED, the behavior depends on the configuration of development error detection:

  • If WdgMDevErrorDetect is enabled, WdgM_CheckpointReached reports the error code WDGM_E_UNINIT to the Default Error Tracer (DET) and returns without further effect ([SWS_WdgM_00279]).
  • If WdgMDevErrorDetect is disabled, the function aborts directly without effect ([SWS_WdgM_00394], [SWS_WdgM_00396]).

Deadline Monitoring and OS Interaction

During runtime and deadline monitoring, the function interacts with the operating system:

  • If a deadline end checkpoint referenced in active mode is reached while the timestamp of the corresponding start checkpoint has the value 0, the function terminates successfully without determining a time difference ([SWS_WdgM_00354]).
  • To determine timestamps and calculate differences (both for detecting premature arrivals and delays), the function uses the operating system function GetElapsedValue, passing the CounterID configured for the Supervised Entity ([SWS_WdgM_00373]).
  • The conversion of the time difference to the configured limit values WdgMDeadlineMin and WdgMDeadlineMax is performed using the configuration parameter OsSecondsPerTick ([SWS_WdgM_00374]).

Usage of the Mode Declaration Group WdgM_Mode

Element WdgM_Mode is specified according to [SWS_WdgM_00334] as a mode declaration group of module WdgM and belongs to category EXPLICIT_ORDER. In the Watchdog Manager, it serves for the formal declaration of supervision modes for supervised entities.

The mode declaration group comprises the following modes with their respective firmly assigned numerical attribute values:

  • SUPERVISION_OK (value 0): Defines the initial supervision mode (Initial mode).
  • SUPERVISION_FAILED (value 1): Represents the status of a failed supervision.
  • SUPERVISION_EXPIRED (value 2): Marks an expired supervision.
  • SUPERVISION_STOPPED (value 3): Signals that supervision has been stopped.
  • SUPERVISION_DEACTIVATED (value 4): Designates the deactivated state of supervision.

In addition, the transition value (On transition value) is defined as 255. Regarding dynamics, the interpretation is: Due to category EXPLICIT_ORDER, switching between the individual modes is likely subject to an ordered sequence. Transition value 255 presumably serves to indicate the active transition state during a change between two modes.

Since the specification in [SWS_WdgM_00334] exclusively declares the type, mode values, and transition parameters, no dedicated API parameters, DET or DEM error messages, or reentrancy requirements exist for this data type itself.

The type WdgM_LocalStatusType is derived from uint8 and serves to record the current supervision status of individual supervised entities (Supervised Entities) according to [SWS_WdgM_00359]. It is provided via the header file Rte_WdgM_Type.h [SWS_WdgM_00359].

The defined value range comprises four discrete states for local entity supervision [SWS_WdgM_00359]:

  • WDGM_LOCAL_STATUS_OK (0): Supervision of the Supervised Entity shows no errors [SWS_WdgM_00359].
  • WDGM_LOCAL_STATUS_FAILED (1): Supervision has failed, but is still in a recoverable state. As soon as the supervised entity returns to normal behavior, the status changes back to WDGM_LOCAL_STATUS_OK. If the number of occurred errors exceeds a configurable limit, the state changes to WDGM_LOCAL_STATUS_EXPIRED [SWS_WdgM_00359].
  • WDGM_LOCAL_STATUS_EXPIRED (2): Supervision has failed definitively; according to the specification, this status can no longer be exited [SWS_WdgM_00359].
  • WDGM_LOCAL_STATUS_DEACTIVATED (4): Supervision of the respective Supervised Entity is temporarily deactivated [SWS_WdgM_00359].

Since this is a pure type definition, neither function calls, reentrancy specifications, nor specific DEM or DET feedback are directly linked to the type itself. When evaluating variables of this type, particular attention must be paid to the irreversibility of state WDGM_LOCAL_STATUS_EXPIRED [SWS_WdgM_00359].

The type WdgM_GlobalStatusType is used for variables that represent the global monitoring status of the module Watchdog Manager (WdgM) ([SWS_WdgM_00360]). It is derived from uint8 and provided via the header Rte_WdgM_Type.h ([SWS_WdgM_00360]).

States and Value Range

The value range comprises five defined monitoring states ([SWS_WdgM_00360]):

  • WDGM_GLOBAL_STATUS_OK (0): The monitoring has yielded no errors ([SWS_WdgM_00360]).
  • WDGM_GLOBAL_STATUS_FAILED (1): The monitoring has failed, but is still within the margin of allowed errors ([SWS_WdgM_00360]).
  • WDGM_GLOBAL_STATUS_EXPIRED (2): The monitoring has failed and the allowed error tolerance has been exceeded; however, the watchdog driver has not yet been instructed to stop triggering ([SWS_WdgM_00360]).
  • WDGM_GLOBAL_STATUS_STOPPED (3): The monitoring has failed, the limit of allowed errors has been exceeded, and the watchdog driver has been instructed to stop triggering. A watchdog reset is imminent ([SWS_WdgM_00360]).
  • WDGM_GLOBAL_STATUS_DEACTIVATED (4): The module WdgM is not initialized and consequently does not trigger the watchdogs ([SWS_WdgM_00360]).

Usage and Interaction

Software components or upper-level system services that access the watchdog status via RTE interfaces evaluate variables of this type to react to state changes of watchdog monitoring—from regular operation through error tolerance cycles to an imminent reset ([SWS_WdgM_00360]).
