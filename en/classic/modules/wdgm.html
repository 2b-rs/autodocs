Monitors software execution flow and timing via checkpoints and controls watchdog triggering accordingly.

The Watchdog Manager monitors software execution. Supervised Entities report checkpoints via WdgM_CheckpointReached [SWS_WdgM_00263]. The cyclic WdgM_MainFunction evaluates alive, deadline, and logical supervision and condenses the results into local statuses and a global status. As long as everything is correct, the WdgM sets a valid trigger condition via the Watchdog Interface. If the global status reaches STOPPED, the driver stops triggering, and a watchdog reset follows [SWS_WdgM_00360]. Mode switches are only permissible with global status OK or FAILED.

The Watchdog Manager monitors the execution of Supervised Entities and only allows the hardware watchdogs to continue being triggered as long as supervision is correct. The trigger timing itself resides in the watchdog driver. The WdgM only sets a trigger condition (SWS WdgM p. 56) via the Watchdog Interface. For this, it mandatory requires WdgIf_SetMode, WdgIf_SetTriggerCondition, GetElapsedValue, and Det_ReportRuntimeError [SWS_WdgM_00161].

After WdgM_Init, supervision begins with the first call of WdgM_MainFunction [SWS_WdgM_00406]. Entities report checkpoints via WdgM_CheckpointReached [SWS_WdgM_00263]. Each call increments the alive counter and immediately checks deadline and logical supervision (SWS WdgM p. 79). The main function cyclically evaluates the alive counters and deadline timeouts [SWS_WdgM_00404].

Sequence diagram: Checkpoints are recorded event-driven, evaluation and triggering occur cyclically. Sources: SWS WdgM p. 32, [SWS_WdgM_00263]

From the results, a local status is produced for each entity. FAILED is recoverable, EXPIRED is not [SWS_WdgM_00359]. From this, the WdgM forms a global status that escalates via EXPIRED to STOPPED. In STOPPED, the driver stops triggering, and a watchdog reset follows [SWS_WdgM_00360]. The WdgM reports status changes via local mode ports and a global mode port [SWS_WdgM_00197] [SWS_WdgM_00198].

State diagram: Global supervision status from DEACTIVATED to STOPPED; two transitions are marked as interpretation. Sources: [SWS_WdgM_00387], [SWS_WdgM_00360]

Mode switches via WdgM_SetMode are only possible with global status OK or FAILED [SWS_WdgM_00145]. If WdgMOffModeEnabled is FALSE, the WdgM rejects an off mode [SWS_WdgM_00031]. If WdgIf_SetMode fails, the global status transitions to STOPPED (SWS WdgM p. 57). After a reset, WdgM_GetFirstExpiredSEID returns the entity that expired first even before WdgM_Init [SWS_WdgM_00346] [SWS_WdgM_00348].

Role: Software Supervision Between Supervised Entities and Hardware Watchdog

The Watchdog Manager (WdgM) monitors the execution of Supervised Entities, i.e., of SW-Cs, CDDs, or BSW executions. Depending on the result, it decides whether the hardware watchdogs continue to be triggered. The actual trigger timing resides in the watchdog driver. The WdgM only sets a trigger condition via the Watchdog Interface instructing the driver to continue triggering (SWS WdgM p. 56). For this, it mandatory requires WdgIf_SetMode, WdgIf_SetTriggerCondition, GetElapsedValue, and Det_ReportRuntimeError [SWS_WdgM_00161]. Optionally, it uses Dem_SetEventStatus, Det_ReportError, Mcu_PerformReset, and BswM_WdgM_RequestPartitionReset [SWS_WdgM_00162].

Supervised Entities report checkpoints via WdgM_CheckpointReached [SWS_WdgM_00263]. Mode management modules control the lifecycle with WdgM_Init, WdgM_SetMode, and WdgM_DeInit [SWS_WdgM_00151] [SWS_WdgM_00154] [SWS_WdgM_00261]. Cyclic evaluation is performed by WdgM_MainFunction from SchM_WdgM.h [SWS_WdgM_00159]. The safety concept assigns logical program flow supervision via checkpoints and permitted transitions to the WdgM (SafetyConceptStatusReport p. 15).

Context diagram: The WdgM connects the checkpoint reports of the application with the watchdog stack as well as with Os, DET, DEM, Mcu, and BswM. Sources: [SWS_WdgM_00161], [SWS_WdgM_00162], SWS WdgM p. 85

Lifecycle: Initialization, Mode Switch, and Deinitialization

The global supervision status is statically initialized to WDGM_GLOBAL_STATUS_DEACTIVATED [SWS_WdgM_00387]. In this state, services reject with WDGM_E_UNINIT or return without effect [SWS_WdgM_00253] [SWS_WdgM_00395]. WdgM_Init receives a pointer to WdgM_ConfigType [SWS_WdgM_00355]. The function initializes all module variables and establishes the initial mode (SWS WdgM p. 74). Interpretation: Afterward, the global status is likely WDGM_GLOBAL_STATUS_OK, because the entities active in the initial mode start locally with OK (SWS WdgM p. 30).

Another call to WdgM_Init outside of DEACTIVATED remains without effect [SWS_WdgM_00390]. A re-initialization therefore takes place via WdgM_DeInit followed by WdgM_Init (SWS WdgM p. 74). Supervision and watchdog handling only begin with the first call of WdgM_MainFunction after initialization [SWS_WdgM_00406].

WdgM_SetMode switches to another configured mode [SWS_WdgM_00154], though only with global status OK or FAILED [SWS_WdgM_00145]. For entities that are deactivated in the new mode:

  • They transition to WDGM_LOCAL_STATUS_DEACTIVATED [SWS_WdgM_00315].
  • Their results are considered correct again [SWS_WdgM_00315].
  • Their failure counter is set to 0 [SWS_WdgM_00315].

Entities remaining active retain their state [SWS_WdgM_00182]. For each watchdog, the WdgM sets the mode parameters via WdgIf_SetMode [SWS_WdgM_00186]. As long as a switch is in progress, WdgM_GetMode still returns the old mode (SWS WdgM p. 77).

Activity diagram: A mode switch undergoes status check, off-mode protection, and setting the watchdog modes; if the latter fails, it ends in STOPPED. Sources: [SWS_WdgM_00145], [SWS_WdgM_00031], [SWS_WdgM_00186], [SWS_WdgM_00139]; the check sequence is an interpretation

Upon transition to SLEEP, the EcuM calls WdgM_DeInit. The function first switches to a sleep mode defined by the integrator. This allows the trigger condition to permit the remaining shutdown without reset despite windowed watchdogs. The module then deinitializes itself (SWS WdgM p. 59). Supervision and watchdog handling stop in the process [SWS_WdgM_00407]. During SLEEP, BswM or EcuM must take over triggering.

Sequence diagram: from startup through mode switch to de-initialization before SLEEP. Sources: SWS WdgM p. 102, [SWS_WdgM_00406], [SWS_WdgM_00408], [SWS_WdgM_00407]

Checkpoints and the three supervision functions

A Supervised Entity reports a checkpoint with WdgM_CheckpointReached(SEID, CheckpointID) [SWS_WdgM_00263]. Both identifiers are of type uint16. A checkpoint is unique only through the pair of SE-ID and checkpoint ID [SWS_WdgM_00356] [SWS_WdgM_00357]. The call performs three things (SWS WdgM p. 79):

  • It increments the alive counter of the checkpoint.
  • It checks the deadline supervision for premature or late arrival.
  • It executes the logical supervision.

If the entity is deactivated in the current mode, the service returns E_NOT_OK and reports WDGM_E_SEDEACTIVATED [SWS_WdgM_00319].

Alive Supervision checks cyclic execution. The main function evaluates the alive counters at the rate of WdgMSupervisionReferenceCycle, a multiple of the supervision cycle (SWS WdgM p. 42). Deadline Supervision checks whether the limits WdgMDeadlineMin/WdgMDeadlineMax are observed between the start and end checkpoints. The timestamps are provided by GetElapsedValue using the OS counter of the entity; scaling is performed via OsSecondsPerTick [SWS_WdgM_00373] [SWS_WdgM_00374]. If the start timestamp is 0, the check terminates successfully without measurement [SWS_WdgM_00354]. If the end checkpoint is missing, WdgM_MainFunction detects a timeout, provided that WdgMEnableTimeoutDetection is set [SWS_WdgM_00403] [SWS_WdgM_00404].

Logical Supervision checks the sequence of checkpoints. There is one activity flag per graph, which sets WdgM_Init to false. A graph starts at an initial checkpoint (SWS WdgM p. 51). Internal graphs belong to an entity and apply in all modes. External graphs connect multiple entities and are configured per mode (SWS WdgM p. 46, [SWS_WdgM_00366]).

Sequence diagram: Checkpoints are recorded event-driven; evaluation and triggering take place cyclically in the main function. Sources: SWS WdgM p. 32, [SWS_WdgM_00263], [SWS_WdgM_00404], [SWS_WdgM_00197]

Local and Global Supervision Status

From the three results, the WdgM forms the local supervision status (SWS WdgM p. 30) for each entity. WDGM_LOCAL_STATUS_FAILED is recoverable: if the entity behaves normally again, it returns to OK. If the failures exceed a limit, it transitions to WDGM_LOCAL_STATUS_EXPIRED [SWS_WdgM_00359]. This tolerance applies only to alive supervision. For deadline and logical errors, even the first incorrect result leads to EXPIRED (SWS WdgM p. 30).

State diagram: Lifecycle of the local supervision status of a Supervised Entity. Sources: SWS WdgM p. 30, [SWS_WdgM_00359], [SWS_WdgM_00315]

For the entire software, there is a global supervision status with the values DEACTIVATED, OK, FAILED, EXPIRED, and STOPPED (SWS WdgM p. 36). EXPIRED means: the error limit has been exceeded, but the driver is still triggering. In STOPPED, the driver is instructed to no longer trigger, and a watchdog reset follows [SWS_WdgM_00360]. How long the WdgM remains in EXPIRED is defined by WdgMExpiredSupervisionCycleTol in multiples of the supervision cycle (SWS WdgM p. 36).

State diagram: Escalation of the global supervision status up to the reset; the two transitions marked as interpretation are not explicitly verified. Sources: [SWS_WdgM_00387], [SWS_WdgM_00360], SWS WdgM p. 36, SWS WdgM p. 57

Ports, Status Notifications, and Query Services

The WdgM provides a supervision port for each Supervised Entity [SWS_WdgM_00146]. It is named localSupervision_{SupervisedEntityCheckpointName} and carries the SE-ID and checkpoint ID as port-defined arguments [SWS_WdgM_00147] [SWS_WdgM_00333]. The local status is queried via localSupervisonStatus_{SupervisedEntityName} [SWS_WdgM_91003] [SWS_WdgM_91004]. Global queries such as GetGlobalStatus or GetFirstExpiredSEID run via globalSupervision [SWS_WdgM_91002] [SWS_WdgM_91001].

The WdgM reports status changes autonomously via mode ports: per entity mode_{SupervisedEntityName} and once globalmode [SWS_WdgM_00149] [SWS_WdgM_00150]. Both use the mode declaration group WdgM_Mode with the values SUPERVISION_OK to SUPERVISION_DEACTIVATED [SWS_WdgM_00334]. Local changes are reported immediately, global ones only once each [SWS_WdgM_00197] [SWS_WdgM_00199]. The local and global mode ports have different interfaces. This allows the local ports to be addressed via the indirect port API without the global port appearing in this list (SWS WdgM p. 101).

Collaboration diagram: SW-Cs and global users are connected to the WdgM via service and mode ports. Sources: SWS WdgM p. 99, [SWS_WdgM_00147], [SWS_WdgM_00149], [SWS_WdgM_00150], [SWS_WdgM_91002]

The query services and WdgM_CheckpointReached are reentrant. WdgM_SetMode and WdgM_PerformReset are not [SWS_WdgM_00175] [SWS_WdgM_00263] [SWS_WdgM_00154] [SWS_WdgM_00264]. BSW modules that control or query the WdgM globally describe this via GlobalSupervisionNeeds (TPS BSWMDT p. 257).

Configuration: Modes, Supervised Entities, and Watchdog Triggers

The WdgM supports VARIANT-PRE-COMPILE and VARIANT-POST-BUILD (SWS WdgM p. 97). Post-build-capable parameters are located in WdgM_ConfigType [SWS_WdgM_00355]. The ECU Integrator configures top-down, evaluating the ServiceNeeds from the ECU Extract for this purpose (TR Methodology p. 389). For each entity, SupervisedEntityNeeds describes, among other things, the activation at startup, the allowed deactivation, the alive cycle times, and the tolerated failure cycles (SWC-Template p. 716).

A WdgMMode comprises the following parts (SWS WdgM p. 119):

  • WdgMModeId
  • WdgMExpiredSupervisionCycleTol
  • Containers for alive, deadline, and external logical supervision
  • Containers for local status parameters
  • WdgMTrigger

A trigger defines WdgMWatchdogMode (FAST/SLOW/OFF) and WdgMTriggerConditionValue (SWS WdgM p. 125). WdgMGeneral contains switches such as WdgMDevErrorDetect and WdgMImmediateReset (SWS WdgM p. 107). For deadline supervision, each entity requires an OS counter (SWS WdgM p. 46).

Behavior in the event of an error

When WdgMDevErrorDetect is active, the WdgM reports development errors to the DET, such as WDGM_E_UNINIT, WDGM_E_PARAM_SEID, WDGM_E_INV_POINTER, or WDGM_E_CPID [SWS_WdgM_00004]. If the module is uninitialized, a fixed pattern applies: with checks enabled, WDGM_E_UNINIT is reported; without checks, the service returns without effect [SWS_WdgM_00279] [SWS_WdgM_00394]. Runtime errors include WDGM_E_DISABLE_NOT_ALLOWED, WDGM_E_SEDEACTIVATED, and WDGM_E_SET_MODE [SWS_WdgM_00402].

If WdgMOffModeEnabled is FALSE, WdgM_SetMode rejects a mode with WDGIF_OFF_MODE. The service then reports WDGM_E_DISABLE_NOT_ALLOWED and returns E_NOT_OK [SWS_WdgM_00031]. WdgM_Init behaves identically for such an initial mode [SWS_WdgM_00030]. If WdgIf_SetMode fails, the WdgM reports WDGM_E_SET_MODE and sets the global status to STOPPED [SWS_WdgM_00139]. The reset follows immediately if an immediate reset is configured, otherwise upon expiration of the first watchdog (SWS WdgM p. 57).

When the global status reaches STOPPED, the WdgM reports the DEM event WDGM_E_SUPERVISION as failed [SWS_WdgM_00375]. After startup, it optionally reports the same event as PASSED [SWS_WdgM_00408]. After a restart, WdgM_GetFirstExpiredSEID returns the entity that reached EXPIRED first [SWS_WdgM_00346]. The service is already available before WdgM_Init [SWS_WdgM_00348]. It reads the value in an inverted double-storage manner from uninitialized RAM and returns E_NOT_OK [SWS_WdgM_00349] in case of inconsistency. WdgM_Init clears the value [SWS_WdgM_00370]. Presumably, the WdgM writes it upon the first transition of an entity to EXPIRED.

WdgM_PerformReset sets the trigger condition of all drivers to 0 and does not update them thereafter (SWS WdgM p. 82). The EcuM executes this service as one of its reset targets (SWS EcuM p. 72).

use

The function WdgM_Init initializes the Watchdog Manager synchronously and is non-reentrant [SWS_WdgM_00151]. The sole input parameter is ConfigPtr, which references the post-build configuration data (WdgM_ConfigType) [SWS_WdgM_00151]. The function formally has no return value (void) [SWS_WdgM_00151].

Error Handling and Boundary Conditions

Prior to initialization, the Watchdog Manager must be in state WDGM_GLOBAL_STATUS_DEACTIVATED: If the development configuration parameter WdgMDevErrorDetect is deactivated and the module is not in this state, WdgM_Init returns without effect [SWS_WdgM_00390].

If the configuration switch WdgMOffModeEnabled is not activated and the initial mode predefined via ConfigPtr would deactivate the watchdog (WDGIF_OFF_MODE), the function aborts without further action and reports the runtime error WDGM_E_DISABLE_NOT_ALLOWED to the Default Error Tracer (DET) [SWS_WdgM_00030]. The return with E_NOT_OK required in the specification is likely to be understood as an interpretation of an internal error abort, since the signature prescribes void [SWS_WdgM_00151].

Interaction and Sequence

  • Error diagnosis prior to initialization: The function WdgM_GetFirstExpiredSEID() must already be available before calling WdgM_Init in order to read out the previously expired Supervised Entity ID (SEID) [SWS_WdgM_00348].
  • RAM cleanup: During initialization, WdgM_Init clears the double-inverted SEID value of the first expired entity stored in uninitialized RAM [SWS_WdgM_00370].
  • Status report to the DEM: Within the first call of WdgM_MainFunction after WdgM_Init, the module reports the status PASSED for WDGM_E_SUPERVISION to the DEM if parameter WdgMDemStoppedSupervisionReport is set [SWS_WdgM_00408].

use

The synchronous function WdgM_DeInit serves to de-initialize the Watchdog Manager [SWS_WdgM_00261]. The interface has the service ID 0x01, is provided via the header file WdgM.h, and neither accepts input parameters nor returns a return value to the caller [SWS_WdgM_00261]. The intended call context is presumably the orderly shutdown sequence of the ECU, in which active supervisions are terminated in a controlled manner prior to power-off.

Functional Scope and Interaction

As part of the de-initialization, the WdgM module completely stops the supervision functions across all configured supervision algorithms and at the same time terminates watchdog handling [SWS_WdgM_00407].

Error Handling and Boundary Conditions

If the Watchdog Manager is already in the global state WDGM_GLOBAL_STATUS_DEACTIVATED at the time of the call, the behavior depends on the configuration parameter WdgMDevErrorDetect: If this development detection is disabled, WdgM_DeInit returns immediately and without any effect [SWS_WdgM_00388].

Regarding concurrency, it is specified that the function is non-reentrant [SWS_WdgM_00261]. Therefore, the call must under no circumstances occur preemptively or in parallel from multiple contexts.

function WdgM_SetMode [SWS_WdgM_00154] 📄 PDF

Std_ReturnType WdgM_SetMode ();

Sets the current mode of Watchdog Manager.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 3fd969cfebd9 Provenance

Usage and Semantics

The function WdgM_SetMode serves to synchronously switch the Watchdog Manager to one of the configured operation modes ([SWS_WdgM_00154]). It expects Mode of type WdgM_ModeType as a pass-by-value parameter. The return value Std_ReturnType signals successful execution of the mode change with E_OK and failure with E_NOT_OK ([SWS_WdgM_00154]).

Restrictions and Error Handling

The function is non-reentrant (Non Reentrant) ([SWS_WdgM_00154]). Execution is bound to the current global status of the Watchdog Manager:

  • If the module is in neither the status WDGM_GLOBAL_STATUS_OK nor WDGM_GLOBAL_STATUS_FAILED, the function returns without executing any actions ([SWS_WdgM_00145]).
  • If the configuration parameter WdgMDevErrorDetect is disabled, a call in status WDGM_GLOBAL_STATUS_DEACTIVATED has no effect at all ([SWS_WdgM_00392]).

Interaction and Effects

If a valid global status (WDGM_GLOBAL_STATUS_OK or WDGM_GLOBAL_STATUS_FAILED) is present, WdgM_SetMode updates the supervised entities and the watchdogs:

  • For each Supervised Entity enabled in the target mode, the current state is preserved ([SWS_WdgM_00182]).
  • For each Supervised Entity disabled in the target mode, the local state changes to WDGM_LOCAL_STATUS_DEACTIVATED; the results of Active, Deadline, and Logical Supervision are set to correct, and the failed cycle counter is reset to 0 ([SWS_WdgM_00315]). Switching to a mode with deactivation of the entity also clears errors that previously led to WDGM_GLOBAL_STATUS_FAILED ([SWS_WdgM_00182]).
  • Finally, the configured watchdog mode parameters for each hardware watchdog are put into effect via the interface WdgIf_SetMode ([SWS_WdgM_00186]).

Std_ReturnType WdgM_CheckpointReached (WdgM_SupervisedEntityIdType SEID, WdgM_CheckpointIdType Checkpoint ID);

Indicates to the Watchdog Manager that a Checkpoint within a Supervised Entity has been reached.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 3c32ca59b4bb Provenance

Usage and Semantics

The synchronous function reports to the Watchdog Manager that a checkpoint within a Supervised Entity has been reached [SWS_WdgM_00263]. It accepts the identifier of the supervised entity (SEID) and the identifier of the reached checkpoint (CheckpointID) as input parameters and returns E_OK upon successful update of the alive counter or E_NOT_OK in case of errors [SWS_WdgM_00263].

Error Handling and Status

If the Watchdog Manager is in status WDGM_GLOBAL_STATUS_DEACTIVATED, the behavior depends on the configuration of the development identifier: If WdgMDevErrorDetect is activated, the function reports the error WDGM_E_UNINIT to the Default Error Tracer (DET) and returns without further effect [SWS_WdgM_00279]. If WdgMDevErrorDetect is deactivated, it returns without any message and without any effect [SWS_WdgM_00394].

Concurrency and Deadlines

The invocation is specified as reentrant [SWS_WdgM_00263]. To determine timestamps and time differences during deadline supervision, the function uses the OS function GetElapsedValue with the CounterID configured for the entity [SWS_WdgM_00373]. Scaling of the time differences to the limit values is performed via parameter OsSecondsPerTick [SWS_WdgM_00374]. If a deadline end checkpoint reaches the call in active mode and the timestamp of the associated start checkpoint is 0, the function terminates successfully without difference measurement [SWS_WdgM_00354].
