Role in the communication stack: signals at the top, I-PDUs at the bottom

AUTOSAR COM connects the signal-oriented view of the RTE with the PDU-oriented lower layers. Upwards, COM provides transmit and receive services for individual signals, signals of dynamic length, and signal groups, such as Com_SendSignal, Com_ReceiveSignal, Com_SendSignalGroup, and Com_ReceiveSignalGroup ([SWS_Com_00197], [SWS_Com_00198], [SWS_Com_00200], [SWS_Com_00201], [SWS_Com_00627]). Downwards, the PDU Router is the only partner. COM transmits via PduR_ComTransmit ([SWS_Com_00669]). Conversely, the PduR calls Com_RxIndication, Com_TxConfirmation, Com_TriggerTransmit, and the TP functions of COM (SWS PduR p. 24).

The BswM controls COM from the side. It starts and stops I-PDU groups, switches receive deadline monitoring, and selects the transmission mode (SWS BswM p. 93). COM reports development and runtime errors to the DET ([SWS_Com_00670]). The supported data types are boolean, unsigned and signed integers up to 64 bits, float32/float64, and uint8[n]. The latter is mapped to UINT8_N or UINT8_DYN ([SWS_Com_00675]), and such signals must be byte-aligned ([SWS_Com_00105]).

Context diagram: COM is located between RTE and PduR, is controlled by the BswM, and reports errors to the DET. Sources: SWS PduR p. 24, SWS BswM p. 93, [SWS_Com_00669], [SWS_Com_00670]

Lifecycle: Com_Init, I-PDU groups, and Com_DeInit

Com_Init initializes the internal and external interfaces. However, communication between ECUs remains blocked afterwards ([SWS_Com_00432]). An exception is made for I-PDUs that are not assigned to any group. Com_Init starts them itself, as if Com_IpduGroupStart had been called with initialize = true ([SWS_Com_00840]). Their initial transmission mode results from the ComSignalInitValues ([SWS_Com_00877]). Com_GetStatus provides the module state COM_UNINIT/COM_INIT ([SWS_Com_00194], [SWS_Com_00819]).

An I-PDU is active as soon as at least one of its groups is started ([SWS_Com_00771]). All I-PDUs of a group have the same ComIPduDirection ([SWS_Com_00871]).

  • Com_IpduGroupStart starts a group. With initialize = true, its I-PDU data is reinitialized ([SWS_Com_91001]). In the BswM, this corresponds to the parameter BswMPduGroupSwitchReinit (SWS BswM p. 165).
  • The first cyclic transmission after starting the group follows after the timeOffset of the CyclicTiming (SystemTemplate p. 268).
  • Com_IpduGroupStop cancels pending transmit requests of the affected I-PDUs, including retries ([SWS_Com_91002], [SWS_Com_00777]). COM ignores transmit confirmations arriving afterwards ([SWS_Com_00800]).
  • Com_DeInit stops all started groups and sets COM to the uninitialized state ([SWS_Com_00130]).

State diagram: Lifecycle of an I-PDU between module initialization, group start/stop, and deinitialization. Sources: [SWS_Com_00432], [SWS_Com_00840], [SWS_Com_00771], [SWS_Com_91001], [SWS_Com_91002], [SWS_Com_00130]

Transmission: from signal value to confirmed I-PDU

For atomic data, the RTE writes each group signal individually with Com_SendSignal. It then triggers the transmission with Com_SendSignalGroup (SWS RTE p. 329). In doing so, COM sets the update bit of the group ([SWS_Com_00801]). The transmit services operate asynchronously. They return E_OK or COM_SERVICE_NOT_AVAILABLE if the associated I-PDU group is stopped ([SWS_Com_00197], [SWS_Com_00865]).

What the functions called by the RTE do not handle directly is taken over by Com_MainFunctionTx ([SWS_Com_00399]). Before I-PDU processing, it calls Com_CbkTxPrep if required ([SWS_Com_00886], [SWS_Com_91013]). If a configured Com_TxIpduCallout returns false, the I-PDU is not processed further ([SWS_Com_00346]). If retries are configured, the minimum delay only starts if PduR_ComTransmit returns E_OK ([SWS_Com_00828]). Com_TxConfirmation reports success or failure ([SWS_Com_00124]), and each successful transmission triggers the configured notification ([SWS_Com_00883], [SWS_Com_00468]).

Sequence diagram: A signal group is filled, transmitted via PduR and CanIf, and confirmed. Sources: SWS RTE p. 329, SWS PduR p. 33, [SWS_Com_00399], [SWS_Com_00124]

For trigger-transmit bus interfaces such as FlexRay, the interface initially only remembers the transmission request. It requests the data later via the PduR with Com_TriggerTransmit (SWS PduR p. 106, [SWS_Com_00001]). In two cases, COM does not copy anything and returns E_NOT_OK: if the buffer is too small or the I-PDU is stopped ([SWS_Com_00869], [SWS_Com_00884]).

Sequence diagram: With Trigger Transmit, the transmission request and data retrieval are decoupled in time. Sources: SWS PduR p. 106, [SWS_Com_00001], [SWS_Com_00869], [SWS_Com_00884]

The transmission time can be influenced externally in three ways:

  • Com_SwitchIpduTxMode sets the transmission mode. Cyclic transmissions are shifted by ComTxModeTimeOffset in the process ([SWS_Com_00784], [SWS_Com_00881], SWS BswM p. 178).
  • Com_TriggerIPDUSend triggers a single transmission, regardless of the transmission mode. This is effective only if the I-PDU is started ([SWS_Com_00348], [SWS_Com_00861], SystemTemplate p. 371).
  • Com_TriggerIPDUSendWithMetaData works similarly, but passes metadata that applies only to this single transmission ([SWS_Com_00858], [SWS_Com_00862], [SWS_Com_00887]). The J1939Rm uses this variant (SWS J1939Rm p. 62).

Reception: check chain and consistent signal groups

The PduR passes received I-PDUs with Com_RxIndication ([SWS_Com_00123], SWS PduR p. 103). COM then runs through a check chain:

  1. A configured Rx callout receives the complete I-PDU. It is always called, specifically before counter handling ([SWS_Com_00816], [SWS_Com_00889]). If it returns false, the I-PDU is not processed ([SWS_Com_00700]).
  2. If the I-PDU counter differs, COM calls Com_CbkCounterErr ([SWS_Com_00726]).
  3. If the update bit is not set, the signal is discarded ([SWS_Com_00802]). If the update bit is missing because the I-PDU is too short, the signal is considered updated ([SWS_Com_00794]).
  4. If COM filters out a group signal, it discards the entire signal group ([SWS_Com_00836]).

Activity diagram: Branches during reception of an I-PDU up to the notification. Interpretation: The sequence of update bit before filter is shown, but not verified. Sources: [SWS_Com_00889], [SWS_Com_00700], [SWS_Com_00802], [SWS_Com_00794], [SWS_Com_00836], [SWS_Com_00555]

On the receive side, the RTE calls Com_ReceiveSignalGroup exactly once and then reads the group signals with Com_ReceiveSignal. COM only notifies once all signals of the group are unpacked into a buffer (SWS RTE p. 329, [SWS_Com_00201]). COM stores received metadata for access via Com_ReceiveSignalWithMetaData ([SWS_Com_00888], [SWS_Com_91005]).

Array access, large I-PDUs, and transformers

Com_SendSignalGroupArray and Com_ReceiveSignalGroupArray transport a signal group as a uint8 array. The array extends from the start byte of the group signal with the smallest to the last byte of the group signal with the highest ComBitPosition ([SWS_Com_00851], [SWS_Com_00854], [SWS_Com_00844], [SWS_Com_00845]). Conditions apply to this access:

  • The group contains only fixed-size data, is byte-aligned, and does not enclose any foreign signals ([SWS_Com_00841]).
  • For such a group, the individual signal and normal group APIs are not available ([SWS_Com_00843]).
  • The APIs must be enabled via ComEnableSignalGroupArrayApi ([SWS_Com_00853], [SWS_Com_00856]).

For transmission mode selection, COM treats array transmission like Com_SendSignalGroup ([SWS_Com_00847]). The COM Based Transformer uses precisely this path (SWS ComXf p. 14).

Large I-PDUs run via the TP interface. For reception, these are Com_StartOfReception, Com_CopyRxData, and Com_TpRxIndication ([SWS_Com_00691], [SWS_Com_00692], [SWS_Com_00650]). With TpSduLength = 0, COM reports back the configured maximum length ([SWS_Com_00874]). For transmission, these are Com_CopyTxData and Com_TpTxConfirmation ([SWS_Com_00693], [SWS_Com_00725], SWS SecOC p. 108). If another transmit request arrives during an ongoing transmission, COM skips it ([SWS_Com_00863]). In contrast, a Com_TriggerIPDUSend with a locked buffer is stored and performed later ([SWS_Com_00867]).

Sequence diagram: Segmented reception of a large I-PDU via CanTp and PduR up to the result evaluation. Sources: SWS SecOC p. 111, [SWS_Com_00691], [SWS_Com_00692], [SWS_Com_00650], [SWS_Com_00838]

Main functions, time monitoring, and signal gateway

COM has three cyclic main functions: Com_MainFunctionRx, Com_MainFunctionTx, and Com_MainFunctionRouteSignals ([SWS_Com_00398], [SWS_Com_00399], [SWS_Com_00400]). Their periods are described by the time bases comConfigurationRxTimeBase, comConfigurationTxTimeBase, and comConfigurationGwTimeBase (SWC-Template p. 841). If there are multiple instances of a main function, ComIPduMainFunctionRef assigns each I-PDU to one of them (SWS RTE p. 1470).

Transmit deadline monitoring works as follows:

  • The timer starts upon transmission, provided it is not already running. For the first start after a (re)start of monitoring, ComFirstTimeout applies, otherwise ComTimeout ([SWS_Com_00878], [SWS_Com_00879]).
  • A transmit confirmation stops the timers ([SWS_Com_00880]).
  • If a timer expires, COM calls the ComTimeoutNotifications ([SWS_Com_00304]).
  • In transmission mode NONE, monitoring is disabled ([SWS_Com_00835]).

Upon reception, a timeout can replace the values with ComTimeoutSubstitutionValue ([SWS_Com_00875], [SWS_Com_00876]). This monitoring can be enabled and disabled per group ([SWS_Com_91003], [SWS_Com_91004]).

Activity diagram: Start, cancellation, and expiration of transmit deadline monitoring. Sources: [SWS_Com_00835], [SWS_Com_00878], [SWS_Com_00879], [SWS_Com_00880], [SWS_Com_00304]

The signal gateway is an integral part of COM (SRS Gateway p. 11). It can route group signals to individual signals ([SWS_Com_00833]) and undergoes defined processing stages on the receive and transmit sides ([SWS_Com_00872], [SWS_Com_00873]).

Behavior in the event of an error

  • COM reports development errors to Det_ReportError with ModuleId 50 ([SWS_Com_00442]). The error codes are:
    • COM_E_PARAM ([SWS_Com_00803])
    • COM_E_UNINIT for API calls before Com_Init or after Com_DeInit, except for status, version, and main functions ([SWS_Com_00804])
    • COM_E_PARAM_POINTER ([SWS_Com_00805])
    • COM_E_INIT_FAILED ([SWS_Com_00837])
  • A skipped transmit request of a large I-PDU is reported as runtime error COM_E_SKIPPED_TRANSMISSION ([SWS_Com_00863], [SWS_Com_00864]).
  • When a group is stopped, the services return COM_SERVICE_NOT_AVAILABLE. If the buffer of a large I-PDU is locked, COM_BUSY may be returned ([SWS_Com_00865]). Com_CbkTxErr indicates a transmission attempt with a stopped group ([SWS_Com_00491]).
  • A TP reception with E_NOT_OK or a callout result false causes COM to treat all signals of the I-PDU as invalidated and execute the ComDataInvalidActions ([SWS_Com_00838], [SWS_Com_00839]).
  • On the sender side, Com_InvalidateSignal and Com_InvalidateSignalGroup invalidate values ([SWS_Com_00203], [SWS_Com_00557]). On the receiver side, a configured invalid value also requires a ComDataInvalidAction ([SWS_Com_00859], [SWS_Com_00860]). The reception of invalid values is reported via Com_CbkInv ([SWS_Com_00536]).
  • Com_ReceiveSignalGroupArray returns the last known data or initial values even when the I-PDU is stopped ([SWS_Com_00857]).

use

The synchronous function [SWS_Com_91001] starts a pre-configured I-PDU group. After the call, cyclic I-PDUs of this group, for example, are sent cyclically. The interface has no return value (void) and is provided via the header Com.h (service ID 0x03).

The function expects two input parameters:

  • initialize (type boolean): Controls whether the data of the I-PDUs of this group shall be initialized or re-initialized before the start.

If initialize is passed with true, all I-PDUs of the group behave as after a start-up of the COM module. This means that, among other things, the values of old_value for filter objects as well as the shadow buffers of signal groups are (re-)initialized before the start of the I-PDU group.

Regarding concurrency behavior, Com_IpduGroupStart is reentrant for different I-PDU groups. For the same I-PDU group, the function is non-reentrant; competing or nested calls with an identical IpduGroupId are therefore not permitted.
