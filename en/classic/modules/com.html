Maps signals of the RTE to I-PDUs and controls their transmission, reception, and monitoring via the PDU Router.

COM packs signals and signal groups of the RTE into I-PDUs and passes them to the bus exclusively via the PDU Router. Conversely, it unpacks received I-PDUs from Com_RxIndication and notifies the RTE [SWS_Com_00123]. Transmission takes place according to configured transmission modes; cyclical portions are handled by Com_MainFunctionTx. Communication only takes place for I-PDUs whose I-PDU group is started, typically by the BswM [SWS_Com_91001]. Stopped groups lead to COM_SERVICE_NOT_AVAILABLE; deadline monitoring detects missing confirmations.

COM mediates between the signal-oriented RTE and the I-PDU-oriented communication stack. The RTE writes signals with Com_SendSignal and signal groups with Com_SendSignalGroup [SWS_Com_00197] [SWS_Com_00200]. Reading is performed via the corresponding receive APIs [SWS_Com_00198]. Downwards, the PDU Router is the only interface (RS COM p. 12). PduR calls Com_RxIndication, Com_TxConfirmation, and Com_TriggerTransmit [SWS_Com_00123] [SWS_Com_00124] [SWS_Com_00001].

Context diagram: Embedding of COM between RTE, BswM, J1939Rm, and PduR. Sources: SWS PduR p. 24, SWS BswM p. 93

After Com_Init, inter-ECU communication is not yet enabled [SWS_Com_00432]. It is enabled via I-PDU groups, which are mostly controlled by the BswM with Com_IpduGroupStart and Com_IpduGroupStop [SWS_Com_91001] [SWS_Com_91002]. An I-PDU is active as long as at least one of its groups is started [SWS_Com_00771]. When stopping, COM discards outstanding transmit requests [SWS_Com_00777].

During transmission, the Transmission Mode Selection chooses between two configured modes (TPS SystemTemplate p. 274). Cyclical portions are handled by Com_MainFunctionTx [SWS_Com_00399]. On CAN, data is handed over directly; on FlexRay, FrIf retrieves the data via TriggerTransmit (SWS PduR p. 101). Upon reception, COM drops signals with an unset update bit as well as entire signal groups if a group signal is filtered out [SWS_Com_00802] [SWS_Com_00836]. For transformer chains, array access via Com_SendSignalGroupArray [SWS_Com_00851] is available.

Sequence diagram: Transmitting a signal group via CAN (direct) or FlexRay (TriggerTransmit), followed by confirmation to the RTE. Sources: SWS COM p. 87, SWS RTE p. 329

In case of an error, the following applies:

  • Development errors such as COM_E_UNINIT or COM_E_PARAM_POINTER go to DET [SWS_Com_00442] [SWS_Com_00804].
  • If the group is stopped, the APIs return COM_SERVICE_NOT_AVAILABLE [SWS_Com_00865].
  • If a transmit confirmation fails to appear, the transmit deadline monitoring reports this via ComTimeoutNotification [SWS_Com_00304].

Role of COM Between RTE and PDU Router

The AUTOSAR COM module mediates between the signal-oriented view of the RTE and the I-PDU-oriented view of the communication stack. Signals and signal groups are entered into I-PDUs via Com_SendSignal and Com_SendSignalGroup [SWS_Com_00197] [SWS_Com_00200]. They are read out again with Com_ReceiveSignal and Com_ReceiveSignalGroup [SWS_Com_00198] [SWS_Com_00201]. Downwards, the PDU Router is the only interface of COM (RS COM p. 12). COM calls PduR_ComTransmit there [SWS_Com_00669]. Conversely, COM provides the callbacks Com_RxIndication, Com_TxConfirmation, and Com_TriggerTransmit to PduR [SWS_Com_00123] [SWS_Com_00124] [SWS_Com_00001]. In doing so, PduR translates the I-PDU IDs between source and destination modules (SWS PduR p. 33).

In addition to the RTE, other basic software modules use the COM interfaces:

  • The BswM controls I-PDU groups, reception deadline monitoring, and transmission modes via optional interfaces (SWS BswM p. 93).
  • J1939Rm triggers specific I-PDUs via Com_TriggerIPDUSendWithMetaData [SWS_Com_00858] (SWS J1939Rm p. 62).
  • COM reports errors to DET [SWS_Com_00670].

Context diagram: COM is located between RTE, BswM, and J1939Rm above and PduR below. COM reaches interface and TP modules exclusively via PduR. Sources: RS COM p. 12, SWS PduR p. 24, SWS BswM p. 93

Lifecycle: Initialization, I-PDU Groups, and Status

Com_Init initializes the internal and external interfaces and variables with a configuration of type Com_ConfigType. Inter-ECU communication is not yet enabled afterwards [SWS_Com_00432] [SWS_Com_00825]. Com_GetStatus returns COM_UNINIT or COM_INIT; after a reset, COM_UNINIT applies [SWS_Com_00194] [SWS_Com_00819]. Com_DeInit stops all started I-PDU groups and returns the module to the uninitialized state [SWS_Com_00130].

Communication is enabled per I-PDU group:

  • Com_IpduGroupStart starts a group, optionally with re-initialization of the I-PDU data. Com_IpduGroupStop stops it again [SWS_Com_91001] [SWS_Com_91002].
  • An I-PDU is active as long as at least one of its groups is started [SWS_Com_00771].
  • I-PDUs without group assignment are already started by Com_Init, specifically as with initialize = true [SWS_Com_00840].
  • When stopping, COM discards outstanding transmit requests, including retries [SWS_Com_00777]. COM ignores subsequent transmit confirmations for the stopped I-PDU [SWS_Com_00800].

Typically, the BswM switches the groups via action BswMPduGroupSwitch. Its parameter BswMPduGroupSwitchReinit corresponds to argument initialize (SWS BswM p. 165). The cyclical transmission portion begins after the configured timeOffset starting from Com_IpduGroupStart (TPS SystemTemplate p. 268).

State diagram: Module state and activation of an I-PDU via its I-PDU groups. Sources: [SWS_Com_00432] [SWS_Com_00130] [SWS_Com_00771] [SWS_Com_00840] [SWS_Com_00777]

Transmission: From Signal to I-PDU on the Bus

Com_SendSignal operates asynchronously [SWS_Com_00197]. For data to be transmitted atomically, the RTE proceeds in two steps: First, it writes all group signals with Com_SendSignal. Afterwards, it triggers the transmission of the group with Com_SendSignalGroup (SWS RTE p. 329). In doing so, COM sets the update bit of the group [SWS_Com_00801].

When and how often an I-PDU is transmitted is determined by the transmission modes:

  • Two modes (True/False) are statically configured per I-PDU. The Transmission Mode Selection chooses between them, even at runtime (TPS SystemTemplate p. 274).
  • Alternatively, Com_SwitchIpduTxMode sets the mode explicitly [SWS_Com_00784]. Cyclical transmissions are then shifted by ComTxModeTimeOffset [SWS_Com_00881].
  • Com_TriggerIPDUSend triggers a single transmission regardless of the transmission mode, but only for started I-PDUs [SWS_Com_00348] [SWS_Com_00861] (TPS SystemTemplate p. 371).
  • ComMinimumDelayTime enforces a minimum distance between two transmissions [SWS_Com_00828].

Com_MainFunctionTx handles all transmission activities that are not carried out directly in the functions called by the RTE [SWS_Com_00399]. If a ComPreparationNotification is configured, it calls Com_CbkTxPrep before I-PDU processing [SWS_Com_00886] [SWS_Com_91013]. A Com_TxIpduCallout can prevent further processing of an I-PDU with false [SWS_Com_00346].

The sequence differs depending on the bus system:

  • CAN: The I-PDU is passed directly via PduR_ComTransmit.
  • FlexRay: After PduR_ComTransmit, FrIf retrieves the data only at the transmission slot via Com_TriggerTransmit (SWS PduR p. 101).
  • LIN: Frames that are not sporadic frames are retrieved exclusively via TriggerTransmit according to the schedule (SWS PduR p. 88).

Com_TriggerTransmit copies nothing and returns E_NOT_OK if the provided buffer is too small or the I-PDU is stopped [SWS_Com_00869] [SWS_Com_00884]. With Com_TxConfirmation, COM aborts running transmit deadline timers [SWS_Com_00880]. Furthermore, it reports every successful transmission via the configured notification [SWS_Com_00883]. In the case of IMMEDIATE processing, this happens immediately; in the case of DEFERRED, it happens with a time delay via a flag (SWS COM p. 91).

Sequence diagram: Transmitting a signal group, handover to CAN (direct) or FlexRay (TriggerTransmit), and subsequent confirmation. Sources: SWS COM p. 87, SWS PduR p. 101, SWS RTE p. 329, [SWS_Com_00880]

Reception: Indication, Unpacking, and Notification

PduR calls Com_RxIndication with the I-PDU ID, length, data pointer, and MetaData [SWS_Com_00123]. The path is identical for CanIf, FrIf, and LinIf; PduR does not buffer in this process (SWS PduR p. 97). The I-PDU then undergoes the following checks:

  • A configured Com_RxIpduCallout is always called, specifically before counter handling and with the complete I-PDU [SWS_Com_00889] [SWS_Com_00816]. If it returns false, the I-PDU is not processed further [SWS_Com_00700].
  • COM drops signals with an unset update bit [SWS_Com_00802].
  • If the update bit is missing because the received I-PDU is shorter than expected, it is considered set [SWS_Com_00794].
  • If COM filters out a group signal, it drops the entire signal group [SWS_Com_00836].

Activity diagram: Decisions during the processing of a received I-PDU up to notification. Sources: [SWS_Com_00889] [SWS_Com_00700] [SWS_Com_00802] [SWS_Com_00794] [SWS_Com_00836] [SWS_Com_00726]; the sequence of update bit before filter is an interpretation.

How COM notifies the RTE depends on the processing type. With IMMEDIATE, COM calls the RTE callbacks directly in the context of the indication. With DEFERRED, COM initially only sets a flag and copies the data (SWS COM p. 92). The check of this flag likely occurs in Com_MainFunctionRx, which handles the reception processing not done directly in Com_RxIndication [SWS_Com_00398]. In the case of signal groups, COM only informs once all group signals have been unpacked. The RTE then calls Com_ReceiveSignalGroup exactly once and subsequently Com_ReceiveSignal per group signal (SWS RTE p. 329). COM stores received MetaData for the RTE [SWS_Com_00888].

Sequence diagram: Indication by PduR, IMMEDIATE versus DEFERRED notification, and retrieval of the signal group by the RTE. Sources: SWS COM p. 92, SWS RTE p. 329, [SWS_Com_00123]

Large I-PDUs, Signal Group Arrays, and Metadata

Large I-PDUs are transmitted via transport protocols. For this purpose, COM provides its own TP interface matching the upper TP interface of PduR (SWS PduR p. 24):

  • Reception: Com_StartOfReception, Com_CopyRxData, and Com_TpRxIndication [SWS_Com_00691] [SWS_Com_00692] [SWS_Com_00650].
  • Transmission: Com_CopyTxData and Com_TpTxConfirmation [SWS_Com_00693] [SWS_Com_00725].

Several special rules apply to TP operation:

  • At TpSduLength = 0, COM reports the configured maximum length [SWS_Com_00874].
  • If a large I-PDU is triggered again while it is still being transmitted, COM discards the additional request [SWS_Com_00863].
  • If Com_TriggerIPDUSend triggers a transmission while the buffer is locked, COM queues the request and transmits later [SWS_Com_00867].

Sequence diagram: Segmented reception of a large I-PDU via CanTp and PduR, simplified without SecOC. Sources: SWS SecOC p. 111, [SWS_Com_00691] [SWS_Com_00692] [SWS_Com_00650] [SWS_Com_00838]

For transformer chains, the RTE accesses signal groups as a byte array. Com_SendSignalGroupArray and Com_ReceiveSignalGroupArray [SWS_Com_00851] [SWS_Com_00854] are provided for this purpose. The corresponding rules:

  • Array scope: It begins at the byte offset of the group signal with the smallest ComBitPosition. It ends at the last byte of the group signal with the largest ComBitPosition [SWS_Com_00844] [SWS_Com_00845].
  • Processing: During transmission, COM treats the call with regard to transfer properties and Transmission Mode Selection like Com_SendSignalGroup [SWS_Com_00847]. Only a restricted set of filters is supported [SWS_Com_00848].
  • Prerequisites: The data must have a fixed size, be mapped byte-aligned, and must not contain any foreign signals [SWS_Com_00841]. For such groups, the single signal and group APIs are not permitted [SWS_Com_00843].

The COM Based Transformer serializes data in exactly the same way as COM itself would. Additional transformers then append CRC and sequence counter (SWS ComXf p. 14, EXP LSA p. 103).

Sequence diagram: The RTE executes the transformer chain and passes the result with a single call to Com_SendSignalGroupArray. Sources: SWS ComXf p. 14, [SWS_Com_00846] [SWS_Com_00847]

MetaData of a transmit I-PDU originate from the last transfer by the RTE or, if none is available, from ComMetaDataDefault. MetaData passed with Com_TriggerIPDUSendWithMetaData apply only to the transmission triggered thereby [SWS_Com_00887] [SWS_Com_00862].

Configuration, Scheduling, and Signal Gateway

COM has three types of main functions: Com_MainFunctionRx, Com_MainFunctionTx, and Com_MainFunctionRouteSignals. Each can be instantiated multiple times and is reentrant for different instances [SWS_Com_00398] [SWS_Com_00399] [SWS_Com_00400]. They are called without parameters by the BSW Scheduler (SWS BSWGeneral p. 79). Their periods are described in EcuInstance via comConfigurationRxTimeBase, comConfigurationTxTimeBase, and comConfigurationGwTimeBase (TR Interoperability p. 98). The associated notification Rte_COMCbkTxPrep_<mn> is bound to a specific Com_MainFunctionTx instance (SWS RTE p. 832).

The signal gateway is a component of COM (SRS Gateway p. 11). It forwards received signals in Com_MainFunctionRouteSignals [SWS_Com_00400]. In doing so, it traverses defined processing stages on the receive and transmit sides [SWS_Com_00872] [SWS_Com_00873]. It can also map individual group signals to standalone signals [SWS_Com_00833].

The configuration is subject to several constraints:

  • The data types from [SWS_Com_00675] are supported. Signals of type UINT8_N and UINT8_DYN must be byte-aligned [SWS_Com_00105].
  • All I-PDUs of a group have the same direction [SWS_Com_00871].
  • If an invalid value is configured for a receive signal, an ComDataInvalidAction must also be configured [SWS_Com_00859].

Signal, group, and I-PDU group IDs are zero-based uint16 values [SWS_Com_00820] [SWS_Com_00821] [SWS_Com_00822]. Their symbolic names are derived from ComHandleId (TPS ECUConfiguration p. 138).

Behavior in the event of an error

COM reports development errors via Det_ReportError with ModuleId 50 [SWS_Com_00442]. The following are defined:

  • COM_E_PARAM for incorrect parameters [SWS_Com_00803].
  • COM_E_UNINIT for calls before Com_Init or after Com_DeInit. Status, version, and main functions are excluded [SWS_Com_00804].
  • COM_E_PARAM_POINTER for null pointers [SWS_Com_00805].
  • COM_E_INIT_FAILED for an invalid configuration selection [SWS_Com_00837].
  • As runtime error COM_E_SKIPPED_TRANSMISSION for rejected transmit requests [SWS_Com_00864].

The signal APIs return COM_SERVICE_NOT_AVAILABLE if the I-PDU group is stopped or a development error is present [SWS_Com_00865]. Com_ReceiveSignalGroupArray nevertheless copies the last known data [SWS_Com_00857].

The following applies to transmit deadline monitoring:

  • The timer starts when a signal goes to the lower layer. The first time, it is loaded with ComFirstTimeout, thereafter with ComTimeout [SWS_Com_00878] [SWS_Com_00879].
  • If it expires, COM calls ComTimeoutNotification [SWS_Com_00304].
  • In transmission mode NONE, monitoring is deactivated [SWS_Com_00835].

The following mechanisms exist on the receive side:

  • The BswM disables and re-enables deadline monitoring via Com_DisableReceptionDM and Com_EnableReceptionDM [SWS_Com_91003] [SWS_Com_91004] (SWS BswM p. 148).
  • If a receive timer expires, SUBSTITUTE replaces the values with ComTimeoutSubstitutionValue [SWS_Com_00875] [SWS_Com_00876].
  • If a TP reception fails or the callout returns false, COM treats all signals of the I-PDU as invalid [SWS_Com_00838] [SWS_Com_00839].
  • If the I-PDU counter differs, COM calls Com_CbkCounterErr [SWS_Com_00726].

Usage and Semantics
