Role of SecOC: Securing I-PDUs Alongside the PDU Router

SecOC (Secure Onboard Communication) protects I-PDUs against tampering and replay. When transmitting, SecOC appends authentication information to an Authentic I-PDU, consisting of an optionally truncated Freshness Value and an Authenticator. This results in a Secured I-PDU. Upon reception, this information is verified before the Authentic I-PDU is forwarded ([SWS_SecOC_00040], SWS SecOC Fig. 7.2 p. 30). The Authenticator is calculated over a concatenation of three parts: Data Identifier (SecOCDataId), secured part of the Authentic I-PDU, and complete Freshness Value (SWS SecOC p. 29).

In the architecture, SecOC is located alongside the PduR. Upper layers such as Com transmit via PduR_<Up>Transmit. The PduR then calls SecOC_[If|Tp]Transmit, and SecOC passes the Secured I-PDU back via the PduR to a bus interface or a transport protocol (SWS SecOC p. 40, SWS SecOC Fig. 1.1 p. 10). MetaData of an Authentic PDU appear unchanged in the Secured PDU, and the same applies vice versa ([SWS_SecOC_00212]). No other module may depend on SecOC, so that a system can also be built without SecOC (SWS SecOC p. 39).

SecOC works together with several other modules:

  • Cryptography is provided by the CSM, among others via Csm_MacGenerate and Csm_MacVerify ([SWS_SecOC_00138]). For asynchronous CSM jobs, SecOC provides vendor-specific callbacks (SWS SecOC p. 78).
  • Freshness Values originate from a Freshness Manager. For SecOCQueryFreshnessValue = RTE, it is connected via port FreshnessManagement ([SWS_SecOC_91001]), for CFUNC via C functions ([SWS_SecOC_00231], [SWS_SecOC_00247]).
  • SecOC reports errors to the DET ([SWS_SecOC_00101]).
  • Security Events go to the IdsM ([SWS_SecOC_00273]).

Module State and Cyclic Main Functions

SecOC has two states, SECOC_UNINIT and SECOC_INIT ([SWS_SecOC_00162]):

  • A successful initialization with SecOC_Init leads to SECOC_INIT ([SWS_SecOC_00106]).
  • SecOC_DeInit stops the secured communication, discards all buffered I-PDUs, and sets the module to the uninitialized state ([SWS_SecOC_00161]). In doing so, internal global variables are also cleared (SWS SecOC p. 65).
  • The error SECOC_E_UNINIT is intended for API calls without initialization, and SECOC_E_INIT_FAILED for a failed initialization ([SWS_SecOC_00101]).
  • If the module is not initialized, SecOC_MainFunctionTx returns immediately (SWS SecOC p. 84).

The actual cryptographic processing does not run in the call context of the transmit or receive functions, but cyclically. For each configured instance of SecOCMainFunctionTx or SecOCMainFunctionRx, there is a dedicated SecOC_MainFunctionTx_<shortName> or SecOC_MainFunctionRx_<shortName>, respectively ([SWS_SecOC_00176], [SWS_SecOC_00171]). The respective period is set via SecOCMainFunctionPeriodTx or SecOCMainFunctionPeriodRx (SWS SecOC p. 130, SWS SecOC p. 129). A Tx PDU is processed in the main function referenced via SecOCTxPduMainFunctionRef ([SWS_SecOC_00276]).

State diagram: Processing takes place only in SECOC_INIT; SecOC_DeInit discards all buffers. Sources: [SWS_SecOC_00162], [SWS_SecOC_00106], [SWS_SecOC_00161], [SWS_SecOC_00101], SWS SecOC p. 84

Transmit Path: From Authentic to Secured I-PDU

A transmission process begins with SecOC_IfTransmit or SecOC_TpTransmit, respectively ([SWS_SecOC_00112], [SWS_SecOC_91008]). SecOC copies the complete Authentic I-PDU into its own memory before the transmission of the Secured I-PDU begins ([SWS_SecOC_00252]). The call then returns.

In the next call of SecOC_MainFunctionTx, all new Authentic I-PDUs are authenticated. Each completed Secured I-PDU is transmitted immediately via the PduR (SWS SecOC p. 84). The generation comprises six steps, from preparing the Secured I-PDU to incrementing the Freshness Counter and transmitting (SWS SecOC p. 33).

In mode CFUNC, the Freshness Value is provided by one of two functions, depending on SecOCProvideTxTruncatedFreshnessValue:

  • SecOC_GetTxFreshnessTruncData, which additionally provides the truncated value ([SWS_SecOC_00230], [SWS_SecOC_91003]), or
  • SecOC_GetTxFreshness ([SWS_SecOC_00231], [SWS_SecOC_91004]).

SecOC reports to the Freshness Manager via SecOC_SPduTxConfirmation or FreshnessManagement_SPduTxConfirmation that the transmission of a Secured I-PDU has been initiated ([SWS_SecOC_00232], [SWS_SecOC_00233]).

After transmission, SecOC assumes the role of an upper module toward the lower layer (SWS SecOC p. 40):

  • Triggered transmission (e.g. FrIf): The lower layer fetches the data with SecOC_TriggerTransmit ([SWS_SecOC_00127]). This requires a prior call of SecOC_IfTransmit; the AlwaysTransmit operating mode is not to be used (SWS SecOC p. 44).
  • Transport protocols: The data is retrieved with SecOC_CopyTxData ([SWS_SecOC_00129]).
  • Confirmation: SecOC forwards the result from SecOC_[If|Tp]TxConfirmation upward via PduR_SecOC[If|Tp]TxConfirmation ([SWS_SecOC_00063]).

If SecOCPduType = SECOC_TPPDU is configured, SecOC_TpTransmit triggers the transmission process. SecOC then fetches the Authentic I-PDU segment by segment from the upper layer via PduR_SecOCTpCopyTxData ([SWS_SecOC_00253], [SWS_SecOC_00254], SWS SecOC Fig. 9.4 p. 109).

The position of SecOC_SPduTxConfirmation after the successful transmission call is an interpretation. Receive Path: Buffer, Verify, Forward

Upon reception, the same sequence always applies to SecOC: first transfer the complete Secured I-PDU into its own memory, then verify in the next SecOC_MainFunctionRx (SWS SecOC p. 50). The Authentic I-PDU is only copied once the Secured I-PDU is completely available ([SWS_SecOC_00255]).

  • Bus interfaces: Reception is reported via SecOC_RxIndication ([SWS_SecOC_00124]).
  • Transport protocols: Reception takes place via SecOC_StartOfReception, SecOC_CopyRxData, and SecOC_TpRxIndication ([SWS_SecOC_00130], [SWS_SecOC_00128], [SWS_SecOC_00125]). For SECOC_TPPDU, SecOC forwards the start of reception to the upper layer via PduR_SecOCTpStartOfReception (SWS SecOC p. 54).

The verification follows six fixed steps ([SWS_SecOC_00040]):

  1. Decompose Authentic I-PDU, Freshness Value, and Authenticator.
  2. Obtain the Freshness Value from the Freshness Manager.
  3. Construct the data to be authenticated.
  4. Verify the Authenticator.
  5. Confirm the result to the DEM Freshness Manager.
  6. Forward the Authentic I-PDU to the upper layer.

Which function provides the Freshness Value depends on SecOCUseAuthDataFreshness:

  • For FALSE, SecOC calls SecOC_GetRxFreshness ([SWS_SecOC_00247], [SWS_SecOC_91007]).
  • For TRUE, SecOC calls SecOC_GetRxFreshnessAuthData, passing a portion of the Authentic I-PDU ([SWS_SecOC_00246], [SWS_SecOC_91006]).
  • In RTE mode, the same rules apply to the operations of FreshnessManagement ([SWS_SecOC_00244], [SWS_SecOC_00245]).

If the verification is successful, the result is SECOC_VERIFICATIONSUCCESS ([SWS_SecOC_00242]), and the Authentic I-PDU goes to the upper layer (PRS SecOC p. 18).

For gateways, SecOC supports re-authenticating paths, i.e. verification on the source bus and re-authentication for the target bus. \"Gatewaying-on-the-fly\" is not supported in this process (SWS SecOC p. 57, SWS SecOC Fig. 9.9 p. 102).

Application Interfaces: Verification Status, Override, Default Pattern

Verification status. SecOC_VerificationStatusType summarizes the result of each verification: the Freshness Value ID and a result of type SecOC_VerificationResultType ([SWS_SecOC_00160], [SWS_SecOC_00149]). Where the status is reported is governed by the propagation mode:

  • With BOTH or FAILURE_ONLY, it goes to the application via VerificationStatusIndication; with NONE, reporting is omitted ([SWS_SecOC_00271], [SWS_SecOC_91016]).
  • With SecOCPropagateOnlyFinalVerificationStatus = TRUE, only the final status is reported; otherwise, each failed intermediate attempt is also reported ([SWS_SecOC_00272]).
  • The Freshness Manager receives the result via SecOC_VerificationStatusCallout, for example to synchronize counters ([SWS_SecOC_00119], [SWS_SecOC_00243]).
  • SecOC_VerifyStatus informs the application about the verification result ([SWS_SecOC_91014]).

Override. With SecOC_VerifyStatusOverride, the application can force the behavior for a Freshness Value ID or Data ID ([SWS_SecOC_00122], [SWS_SecOC_00142]). The R20-11 values of SecOC_OverrideStatusType ([SWS_SecOC_00991]) are:

  • SECOC_OVERRIDE_DROP_UNTIL_NOTICE and SECOC_OVERRIDE_DROP_UNTIL_LIMIT: no CSM verification, the I-PDU is discarded, the result is SECOC_NO_VERIFICATION.
  • SECOC_OVERRIDE_PASS_UNTIL_NOTICE: The verification takes place, but the I-PDU is forwarded regardless of the result.
  • SECOC_OVERRIDE_CANCEL: terminates an active override.

The passage from R23-11 additionally mentions SECOC_OVERRIDE_SKIP_UNTIL_LIMIT and SECOC_OVERRIDE_PASS_UNTIL_LIMIT (SWS SecOC p. 102). The R20-11 requirement text is truncated at this point in the payload.

Default pattern. SecOC_SendDefaultAuthenticationInformation enables or disables transmission with SecOCDefaultAuthenticationInformationPattern per Freshness Value ID ([SWS_SecOC_91013]). The interface exists only if this pattern is configured ([SWS_SecOC_00002], [SWS_SecOC_91020]).

Configuration, PDU Structure, and Separate Cryptographic I-PDUs

Configuration containers. Each Tx PDU to be secured is configured in SecOCTxPduProcessing, and each Rx PDU to be verified in SecOCRxPduProcessing. This includes the Data ID, Freshness Value ID, lengths, and retry counters in each case (SWS SecOC p. 155, SWS SecOC p. 140).

PDU structure. A Secured I-PDU consists of an optional header, the Authentic I-PDU, an optional Freshness Value, and the Authenticator. The Freshness Value and Authenticator can be transmitted in truncated form (SWS SecOC Fig. 5 p. 29). SecOC fills unused areas with SecOCTxPduUnusedAreasDefault ([SWS_SecOC_00269]). How much the receiver extracts as the Authentic I-PDU depends on the header and the length type:

  • Without header and with static length, the configured length of the global PDU applies ([SWS_SecOC_00257]).
  • Without header and with dynamic length, the length reported by the lower layer applies ([SWS_SecOC_00258]).
  • With header, the length from the header applies ([SWS_SecOC_00259]).

Separate Cryptographic I-PDU. With SecOCTxSecuredPduCollection, a Secured I-PDU is transmitted as two messages: as an Authentic I-PDU and as a separate Cryptographic I-PDU ([SWS_SecOC_00201], TPS SystemTemplate Fig. 6.18 p. 244). The following rules apply:

  • Both messages are transmitted in the same main function cycle ([SWS_SecOC_00202]).
  • A Message Linker, i.e. a portion of the Authentic I-PDU repeated in the Cryptographic I-PDU, links the two messages ([SWS_SecOC_00209], [SWS_SecOC_00210]).
  • The receiver only verifies when both messages with a matching linker are available ([SWS_SecOC_00203], [SWS_SecOC_00211]).
  • Upon success, SecOC clears both buffers. After a failure, both remain buffered, and the verification is repeated when new data arrives ([SWS_SecOC_00207], [SWS_SecOC_00208]).
  • The upper layer receives E_OK only if both transmit confirmations were E_OK ([SWS_SecOC_00270]).
  • With the overflow strategy QUEUE, no Rx collection is permitted ([SWS_SecOC_CONSTR_00265]).

Behavior in the event of an error

Transmit side.

  • If the CSM reports a recoverable error (e.g. E_BUSY), SecOC does not transmit a Secured I-PDU. The Authentic I-PDU is retained and is authenticated again in the next main function ([SWS_SecOC_00151]).
  • If SecOCAuthenticationBuildAttempts is reached, SecOC reports SECOC_E_CRYPTO_FAILURE to the DET ([SWS_SecOC_00155]).
  • When the limit is reached, on E_NOT_OK of the freshness query, or on an unrecoverable CSM error, SecOC transmits with the default pattern if it is activated ([SWS_SecOC_00229]).
  • If the pattern is not configured, SecOC removes the Authentic I-PDU and aborts the transmit request (SWS SecOC p. 124). A configured but not activated pattern is likely treated in the same way, because the rest of [SWS_SecOC_00229] is truncated in the payload.

Cancellation and errors during data transfer.

  • If the upper layer cancels via SecOC_IfCancelTransmit or SecOC_TpCancelTransmit ([SWS_SecOC_00113], [SWS_SecOC_91009]), SecOC immediately informs the lower layer, stops all associated actions, and releases the buffers (SWS SecOC p. 48).
  • If the lower layer reports a transmission error, SecOC handles it only by omitting the confirmation to the upper layer (ibid.).
  • If PduR_SecOCTpCopyTxData returns BUFREQ_E_BUSY, SecOC repeats the call in the next main function. In case of BUFREQ_E_NOT_OK, SecOC aborts immediately with E_NOT_OK ([SWS_SecOC_00260], [SWS_SecOC_00266]).
  • For reception, the same applies to PduR_SecOCTpCopyRxData ([SWS_SecOC_00267]).

Receive side. SecOC maintains two counters per Secured I-PDU, which are set to 0 upon initial processing ([SWS_SecOC_00234], [SWS_SecOC_00235]):

  • Build counter: increases on E_BUSY of the freshness query and on recoverable CSM errors ([SWS_SecOC_00236], [SWS_SecOC_00237]). Below SecOCAuthenticationBuildAttempts, a retry is performed in the next Rx main function ([SWS_SecOC_00238]). At the limit, SecOC discards the PDU with SECOC_AUTHENTICATIONBUILDFAILURE ([SWS_SecOC_00240]).
  • Verify counter: increases on an actual verification failure, and the build counter is reset in the process ([SWS_SecOC_00239]). At the limit SecOCAuthenticationVerifyAttempts or in case of E_NOT_OK/KEY_FAILURE, SecOC discards the PDU with SECOC_VERIFICATIONFAILURE ([SWS_SecOC_00241]).

If the freshness query returns E_NOT_OK, the PDU is discarded with SECOC_FRESHNESSFAILURE ([SWS_SecOC_00256]). In contrast, [SWS_SecOC_00248] describes the same case as a counted verification failure with DET report SECOC_E_FRESHNESS_FAILURE ([SWS_SecOC_00114]). Interpretation: Both requirements apply to R20-11. How they are delimited from each other is left open by the specification; the integration project should clarify this with the supplier.

An override can overrule the discard ([SWS_SecOC_00240]). If a statically long PDU turns out too short, SecOC discards it silently ([SWS_SecOC_00268]). R20-11 links this to the EcuC parameter DynamicLength; the R23-11 document passage uses SecOCDynamicRuntimeLengthHandling instead (SWS SecOC p. 52).

Security Events. SecOC reports failed MAC checks and missing freshness values as SECOC_SEV_MAC_VERIFICATION_FAILED and SECOC_SEV_FRESHNESS_NOT_AVAILABLE, respectively, to the IdsM ([SWS_SecOC_00274], [SWS_SecOC_00275]).

Usage and Semantics

The function SecOC_IfTransmit ([SWS_SecOC_00112]) serves to request the transmission of a PDU via the module SecOC. The interface is executed synchronously and is available via the header file SecOC.h with the service ID 0x49.

The following parameters are passed upon the call:

  • TxPduId: Unique identifier (PduIdType) of the PDU to be transmitted.
  • PduInfoPtr: Pointer to a structure of type const PduInfoType*, which provides the length of the data, the pointer to the payload, and a pointer to metadata.

Return Values

The return value of type Std_ReturnType signals the acceptance of the transmission request ([SWS_SecOC_00112]):

  • E_OK: The transmission request was accepted by the module.
  • E_NOT_OK: The transmit request was rejected.

Concurrency and Limitations
