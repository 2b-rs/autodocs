Protects I-PDUs with an authenticator and freshness value against manipulation and replay alongside the PDU Router.

SecOC protects I-PDUs against manipulation and replay. To this end, it appends an authenticator and a freshness value during transmission and verifies both upon reception. The acceptance of a PDU and the cryptographic processing are decoupled: the cyclic main functions authenticate or verify only in six steps ([SWS_SecOC_00040]). Cryptography is provided by the CSM, while the freshness value is provided by an external Freshness Manager. Limited retry attempts determine when a received PDU is discarded and a verification status is reported ([SWS_SecOC_00241]).

SecOC protects I-PDUs in the communication stack. It resides alongside the PduR and appends the authenticator and an optionally truncated freshness value to each Authentic I-PDU. This creates a Secured I-PDU (SWS SecOC p. 39). The authenticator is calculated over the Data Identifier, payload, and complete freshness value (SWS SecOC p. 29). Cryptography is provided by the CSM ([SWS_SecOC_00138]), while the freshness value is provided by a Freshness Manager via RTE or C function ([SWS_SecOC_91001], [SWS_SecOC_00230]).

Context diagram: SecOC between PduR, CSM, Freshness Manager, application, DET, and IdsM. Sources: [SWS_SecOC_00138], [SWS_SecOC_91001], [SWS_SecOC_00273]

Transmission and reception are decoupled. For SecOC_[If|Tp]Transmit, SecOC copies only the payload. Only the cyclic SecOC_MainFunctionTx calculates the authentication information and triggers transmission via the PduR (SWS SecOC p. 40, [SWS_SecOC_00176]). SecOC buffers received Secured I-PDUs completely and verifies them in SecOC_MainFunctionRx in six steps, from parsing to forwarding upward ([SWS_SecOC_00040], [SWS_SecOC_00255]). The module operates only in the SECOC_INIT state, which is established by SecOC_Init and cleared again by SecOC_DeInit ([SWS_SecOC_00162], [SWS_SecOC_00161]).

Two counters control retries upon reception ([SWS_SecOC_00237], [SWS_SecOC_00239], [SWS_SecOC_00240], [SWS_SecOC_00241]):

  • The build counter counts temporary bottlenecks such as E_BUSY.
  • The verify counter counts failed MAC comparisons.
  • If either reaches its limit, the PDU is discarded.

During transmission, reaching a limit leads to SECOC_E_CRYPTO_FAILURE and, if enabled, to transmission with a default pattern ([SWS_SecOC_00155], [SWS_SecOC_00229]).

Activity diagram: Build and verify counters decide on retry or discard. Sources: [SWS_SecOC_00239], [SWS_SecOC_00241]

SecOC reports the result of each attempt as SecOC_VerificationStatusType, depending on configuration to software components and to the Freshness Manager ([SWS_SecOC_00271], [SWS_SecOC_00243]). The verification can be overridden in a targeted manner using SecOC_VerifyStatusOverride ([SWS_SecOC_00122]). When split into an Authentic and Cryptographic I-PDU, verification is only performed once both parts are available with a matching message linker ([SWS_SecOC_00211]).

Role alongside the PduR and system boundary

SecOC is positioned alongside the PDU Router in the layered architecture. It transforms an Authentic I-PDU into a Secured I-PDU by appending authentication information directly behind the payload: the authenticator and the optionally truncated freshness value (SWS SecOC p. 39, SWS SecOC p. 43). No other module may depend on SecOC, so that a system can also be built without SecOC. MetaData of an Authentic PDU appears unchanged in the Secured PDU and vice versa ([SWS_SecOC_00212]).

The authenticator is calculated over the concatenation of three parts: SecOCDataId, secured part of the Authentic I-PDU, and complete freshness value (SWS SecOC p. 29). Cryptography is provided by the CSM, for example with Csm_MacGenerate and Csm_MacVerify ([SWS_SecOC_00138]). The freshness value is provided by a Freshness Manager, either via the RTE port FreshnessManagement or via C functions ([SWS_SecOC_91001], [SWS_SecOC_00230]). Further recipients of notifications are:

  • DET for development and runtime errors ([SWS_SecOC_00101]),
  • the IdsM for security events ([SWS_SecOC_00273]),
  • software components for verification results ([SWS_SecOC_00271]).

Context diagram: SecOC mediates between PduR, CSM, Freshness Manager, and application, and reports to DET and IdsM. Sources: SWS SecOC p. 24, [SWS_SecOC_00138], [SWS_SecOC_91001], [SWS_SecOC_00273]

The same mechanisms also support gateways. SecOC supports re-authentication gateways between security zones, with each operation configured separately. \"Gatewaying-on-the-fly\" is not supported (SWS SecOC p. 57).

Initialization, module state, and cyclic main functions

The module state SecOC_StateType recognizes SECOC_UNINIT and SECOC_INIT ([SWS_SecOC_00162]).

  • SecOC_Init receives an implementation-specific SecOC_ConfigType and transitions to SECOC_INIT upon success. If assigned to multiple partitions, one init function is possible per partition ([SWS_SecOC_00106], [SWS_SecOC_00104]).
  • SecOC_DeInit discards all buffered I-PDUs and resets the module to the uninitialized state ([SWS_SecOC_00161]). Internal variables and buffers are cleared in the process as well (SWS SecOC p. 65).
  • An invocation without prior initialization reports SECOC_E_UNINIT ([SWS_SecOC_00101]).

The actual processing is performed by SecOC_MainFunctionTx and SecOC_MainFunctionRx. A dedicated function …_<shortName> is created for each configured instance ([SWS_SecOC_00176], [SWS_SecOC_00171]). Its period is configurable (SWS SecOC p. 130, SWS SecOC p. 129). Each SecOCTxPduProcessing runs in the referenced instance ([SWS_SecOC_00276]).

Without initialization, the Tx main function returns immediately. Otherwise, it authenticates all new Authentic I-PDUs in the same call and immediately triggers their transmission via the PduR (SWS SecOC p. 84).

State diagram: Init and DeInit switch between SECOC_UNINIT and SECOC_INIT; the main function operates only in the initialized state. Sources: [SWS_SecOC_00162], [SWS_SecOC_00106], [SWS_SecOC_00161], SWS SecOC p. 84

Transmission: from Authentic to Secured I-PDU

The transmit path is decoupled and executes in two stages (SWS SecOC p. 40):

  1. The upper layer calls PduR_<Up>Transmit, the PduR calls SecOC_[If|Tp]Transmit. SecOC copies the Authentic I-PDU completely into its own memory and returns ([SWS_SecOC_00252]).
  2. In the next run of the main function, the Secured I-PDU is generated, and SecOC triggers its transmission via the PduR.

SecOC forwards confirmations from the lower layer upward via PduR_SecOC[If|Tp]TxConfirmation ([SWS_SecOC_00063]).

Authentication comprises six steps: prepare, construct DataToAuthenticator, generate authenticator, assemble Secured I-PDU, increment freshness counter, transmit. Data ID (16-bit) and freshness value are included in big-endian order (SWS SecOC p. 33).

If the freshness source is a C function (CFUNC), SecOC retrieves the value via SecOC_GetTxFreshness. If the Freshness Manager is to provide the truncated value itself, SecOC_GetTxFreshnessTruncData is used for this purpose ([SWS_SecOC_00231], [SWS_SecOC_00230]). SecOC reports the transmit trigger with SecOC_SPduTxConfirmation or via RTE ([SWS_SecOC_00232], [SWS_SecOC_00233]). Unused areas are padded with SecOCTxPduUnusedAreasDefault ([SWS_SecOC_00269]).

Sequence diagram: The acceptance of the Authentic I-PDU and the authentication in the next run of the main function are decoupled. Sources: SWS SecOC p. 40, [SWS_SecOC_00231], [SWS_SecOC_00232], [SWS_SecOC_00063]

For triggered transmission, at least one SecOC_IfTransmit must have occurred beforehand. Without available data, SecOC_TriggerTransmit responds with E_NOT_OK, and AlwaysTransmit must not be used (SWS SecOC p. 44, [SWS_SecOC_00127]).

For SECOC_TPPDU, SecOC_TpTransmit starts the process. SecOC retrieves the data piecewise with PduR_SecOCTpCopyTxData ([SWS_SecOC_00253], [SWS_SecOC_00254]). The TP module subsequently reads it out via SecOC_CopyTxData ([SWS_SecOC_00129]).

Sequence diagram: During TP transmission, SecOC is a TP sink to the upper layer and a TP source to the lower layer. Sources: SWS SecOC p. 109, [SWS_SecOC_00253], [SWS_SecOC_00254]

With SecOCTxSecuredPduCollection, the Secured I-PDU is split into two messages:

  • the Authentic I-PDU,
  • a Cryptographic I-PDU consisting of authentication data and message linker.

Both are sent in the same cycle ([SWS_SecOC_00201], [SWS_SecOC_00209], [SWS_SecOC_00202]). The confirmation to the upper layer is only E_OK if both parts were confirmed with E_OK ([SWS_SecOC_00270]).

Reception and verification

Verification comprises six steps ([SWS_SecOC_00040]):

  1. parse Authentic I-PDU, freshness value, and authenticator,
  2. request freshness value from the Freshness Manager,
  3. construct the data to be verified,
  4. verify the authentication information,
  5. confirm the Freshness Manager,
  6. forward the Authentic I-PDU to the upper layer.

SecOC initially copies the Secured I-PDU into its own memory and verifies it in the next run of the main function (SWS SecOC p. 50). Via bus interfaces, it arrives via SecOC_RxIndication ([SWS_SecOC_00124]). If an I-PDU of static length is shorter than configured, it is silently discarded ([SWS_SecOC_00268]). The length of the Authentic I-PDU originates from configuration, from the lower layer, or from the header ([SWS_SecOC_00257], [SWS_SecOC_00258], [SWS_SecOC_00259]).

Sequence diagram: Freshness query and MAC verification run in the context of the Rx main function in two nested retry loops. Sources: SWS SecOC p. 103, [SWS_SecOC_00237], [SWS_SecOC_00238]

For the transport protocol, reception proceeds as follows ([SWS_SecOC_00130], [SWS_SecOC_00128], [SWS_SecOC_00125]):

  • SecOC_StartOfReception reserves buffer for the entire Secured I-PDU,
  • SecOC_CopyRxData accepts the individual segments,
  • SecOC_TpRxIndication reports the end of reception.

SecOC may only forward the Authentic I-PDU after reception is complete ([SWS_SecOC_00255]). Interpretation according to the diagram: Forwarding to the upper layer should only start after successful verification (SWS SecOC p. 112). Deviating from this, version R23-11 already forwards the start of reception in SecOC_StartOfReception (SWS SecOC p. 54).

Sequence diagram: SecOC buffers the entire Secured I-PDU; forwarding to Com follows (interpretation) only after successful verification. Sources: SWS SecOC p. 112, [SWS_SecOC_00255]

With SecOCRxSecuredPduCollection, SecOC only verifies once the Authentic and Cryptographic I-PDUs are available with a matching message linker ([SWS_SecOC_00203], [SWS_SecOC_00211]). For this purpose, it maintains separate buffers ([SWS_SecOC_00204]):

  • After successful verification, both buffers are cleared ([SWS_SecOC_00207]).
  • After a failure, both are retained, and verification is performed again with each new incoming arrival ([SWS_SecOC_00208]).

The overflow strategy QUEUE excludes this splitting ([SWS_SecOC_CONSTR_00265]).

Freshness Manager, verification status, and override

SecOC does not manage freshness itself. Depending on SecOCQueryFreshnessValue (RTE or CFUNC) and SecOCUseAuthDataFreshness, it queries GetRxFreshness or GetRxFreshnessAuthData. In the second case, it additionally passes a configured excerpt of the received PDU ([SWS_SecOC_00244], [SWS_SecOC_00245], [SWS_SecOC_00246], [SWS_SecOC_00247]). The truncated freshness value and the number of previous verification attempts are also provided ([SWS_SecOC_91007], [SWS_SecOC_91006]).

The values are provided as SecOC_FreshnessArrayType ([SWS_SecOC_91012]), with the most significant bit in the first byte, i.e. big endian (SWS SecOC p. 80). The return value E_BUSY means that the value is temporarily unavailable ([SWS_SecOC_91002]).

SecOC_VerificationStatusType summarizes the result of each attempt: freshnessValueID plus a value from SecOC_VerificationResultType, such as SECOC_FRESHNESSFAILURE ([SWS_SecOC_00160], [SWS_SecOC_00149]). It is reported depending on mode BOTH, FAILURE_ONLY, or NONE ([SWS_SecOC_00271], [SWS_SecOC_91016]). Optionally, only the final status is forwarded ([SWS_SecOC_00272]). The Freshness Manager receives the result via SecOC_VerificationStatusCallout ([SWS_SecOC_00119], [SWS_SecOC_00243]).

SecOC_VerifyStatusOverride overrides verification in a targeted manner ([SWS_SecOC_00122]). In R20-11, SecOC_OverrideStatusType includes, among others, …DROP_UNTIL_NOTICE, …DROP_UNTIL_LIMIT, …CANCEL, and …PASS_UNTIL_NOTICE ([SWS_SecOC_00991]). R23-11 adds …SKIP_UNTIL_LIMIT and …PASS_UNTIL_LIMIT (SWS SecOC p. 102). On the transmit side, SecOC_SendDefaultAuthenticationInformation switches the default pattern on or off per freshness value ID ([SWS_SecOC_91013]).

Configuration and instance reference

The configuration is structured into three containers:

  • SecOCGeneral for general parameters, such as SecOCDefaultAuthenticationInformationPattern (SWS SecOC p. 124),
  • one SecOCTxPduProcessing per transmit PDU (SWS SecOC p. 155),
  • one SecOCRxPduProcessing per receive PDU (SWS SecOC p. 140).

Central parameters are SecOCDataId, SecOCFreshnessValueId, the freshness and authenticator lengths, as well as the CsmJob reference (SWS SecOC p. 106). If a CSM job operates asynchronously, SecOC requires vendor-specific callbacks for this purpose (SWS SecOC p. 78).

Some ports exist only with an appropriate configuration:

  • SendDefaultAuthenticationInformation only if a default pattern is set ([SWS_SecOC_91020]),
  • FreshnessManagement only when queried via RTE ([SWS_SecOC_91001]).

Security events are reported only if SecOCEnableSecurityEventReporting is set ([SWS_SecOC_00273]).

Behavior in the event of an error

On the transmission side, the following applies:

  • In case of recoverable CSM errors such as E_BUSY or QUEUE_FULL, SecOC retains the authentic I-PDU and retries in the next cycle ([SWS_SecOC_00151]).
  • If the retry limit is reached, it reports SECOC_E_CRYPTO_FAILURE to DET ([SWS_SecOC_00155]).
  • When the limit is reached, upon freshness E_NOT_OK, or upon an unrecoverable error, SecOC uses the default pattern, provided it is enabled ([SWS_SecOC_00229]).
  • If no pattern is configured, SecOC aborts the job (SWS SecOC p. 124).
  • If a pattern is configured but not enabled, SecOC is likely to abort as well.

Activity diagram: Recoverable errors lead to retries; limit or hard error leads to the default pattern or cancellation. Sources: [SWS_SecOC_00151], [SWS_SecOC_00155], [SWS_SecOC_00229], SWS SecOC p. 124

SecOC handles cancellations and errors of neighboring layers as follows:

  • SecOC immediately passes SecOC_[If|Tp]CancelTransmit downwards and frees all buffers (SWS SecOC p. 48, [SWS_SecOC_91009]).
  • If the lower layer reports E_NOT_OK, SecOC merely omits confirmation to the upper layer.
  • If the data retrieval during TP transmission returns BUFREQ_E_BUSY, SecOC retries it in the next cycle ([SWS_SecOC_00260]).
  • BUFREQ_E_NOT_OK leads to immediate termination during transmission as well as during reception ([SWS_SecOC_00266], [SWS_SecOC_00267]).

On the receive side, SecOC maintains a build counter and a verify counter per PDU, both starting at 0 ([SWS_SecOC_00234], [SWS_SecOC_00235]):

  • E_BUSY or a recoverable CSM error increments the build counter; SecOC retries in the next cycle ([SWS_SecOC_00236], [SWS_SecOC_00237], [SWS_SecOC_00238]).
  • If the build counter reaches its limit, SECOC_AUTHENTICATIONBUILDFAILURE follows ([SWS_SecOC_00240]).
  • An incorrect MAC increments the verify counter and resets the build counter ([SWS_SecOC_00239]).
  • When the verify limit is reached or upon a hard error, SECOC_VERIFICATIONFAILURE applies; on success, SECOC_VERIFICATIONSUCCESS applies ([SWS_SecOC_00241], [SWS_SecOC_00242]).

Activity diagram: Build and verify counters control retries and discarding during reception. Sources: SWS SecOC p. 42, PRS SecOC p. 19, [SWS_SecOC_00239], [SWS_SecOC_00241]

For freshness E_NOT_OK, R20-11 contains two requirements side by side. One discards the PDU immediately with SECOC_FRESHNESSFAILURE ([SWS_SecOC_00256]). The other counts a failed attempt and reports SECOC_E_FRESHNESS_FAILURE to DET when the limit is reached ([SWS_SecOC_00248]). In addition, security events are sent to the IdsM, such as SECOC_SEV_MAC_VERIFICATION_FAILED with the DataId as context ([SWS_SecOC_00274], [SWS_SecOC_00275]).

Usage and Semantics

The synchronous function SecOC_DeInit terminates the operation of secure on-board communication in the SecOC module and transitions it into the state SecOC_UNINIT [SWS_SecOC_00161]. The function is declared in header file SecOC.h and has service ID 0x05 as well as signature void SecOC_DeInit(void) [SWS_SecOC_00161]. It processes neither input nor output parameters and returns no value [SWS_SecOC_00161].

Buffer cleanup and state transition

Calling SecOC_DeInit discards all I-PDUs buffered in the module and removes them from the buffers [SWS_SecOC_00161]. If this data is still required after a restart of secured communication, it must be acquired again after calling SecOC_Init again [SWS_SecOC_00161].

Concurrency and Limitations

Fixed requirements and boundary conditions apply to the execution of deinitialization [SWS_SecOC_00161]:

  • Non-reentrant: The interface is specified as non-reentrant (Non Reentrant) and therefore must not be executed concurrently [SWS_SecOC_00161].
  • Sequence conditions: The module remains in the uninitialized state after the call, so that subsequent communication services unconditionally require calling SecOC_Init again [SWS_SecOC_00161].

SecOC_Init function

Initializes the the Sec OC module. Successful initialization leads to state Sec OC_ INIT. In configurations, in which Sec OC is assigned to more than one partition (i.e. Sec OC_ Main Functions are mapped to partition s), Sec OC may provide one init AUTOSAR CP R20 - of Document ID : AUTOSAR_SWS_SecureOnboardCommunication function per partition. The decision on whether a single Sec OC_ Init() function or one per partition is provided is implementation - specific. In case a given implementation provides one Sec OC_ Init() function per partition, it is up to the implementation to devise a naming pattern that prevents name clashes among the different Sec OC_ Init() functions (e.g., by adding a suffix containing short name the Ecuc Partition.
