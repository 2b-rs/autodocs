Std_Types.h as a common type base of BSW, RTE, and application

The module std does not provide any functions. It exclusively provides types and symbols, all of which are available via Std_Types.h. These include the return type Std_ReturnType [SWS_Std_00005], the version structure Std_VersionInfoType [SWS_Std_00015], and the function pointer type Std_ExtractProtocolHeaderFieldsType [SWS_Std_91003]. The system boundary defines the BSW requirement for the standard type header: all AUTOSAR standard types and constants belong in Std_Types.h. This header includes Platform_Types.h and Compiler.h. It defines Std_ReturnType, E_OK/E_NOT_OK, as well as STD_ON, STD_OFF, STD_HIGH, STD_LOW, STD_ACTIVE, and STD_IDLE SRS BSWGeneral p. 62.

Every module that uses AUTOSAR integer types or the standard return type includes Std_Types.h. The goal is uniform, platform-wide access to the standard types SRS BSWGeneral p. 62. RTE and BSW modules explicitly share the same return type [SWS_Std_00005]. The BSW scheduler also returns it for SchM_Call across partition boundaries BSWDistributionGuide p. 13. In complex device drivers, the configuration headers with their STD_ON/STD_OFF switches also build on Std_Types.h CDD-Guideline p. 14.

Context diagram: Std_Types.h builds on Platform_Types.h and Compiler.h and is used by BSW modules, configuration headers, RTE, and transformers. Sources: SRS BSWGeneral p. 62, CDD-Guideline p. 14, [SWS_Std_00005], [SWS_Std_91003]

Std_ReturnType: Value range, bit layout, and module-specific extensions

Std_ReturnType is defined as typedef uint8 Std_ReturnType;. E_OK (0) and E_NOT_OK (1) are pre-assigned. The range 0x02–0x3F is available for user-specific errors [SWS_Std_00005]. Normally, only E_OK and E_NOT_OK are to be used. If these values are not sufficient, a module may define additional values in the six low-order bits and names them with its module prefix. Bit 7 and Bit 8 are reserved and are defined by the RTE specification [SWS_Std_00011].

The RTE justifies the base type uint8 with compatibility. An enum could turn out to have different sizes in RTEs from different vendors. Therefore, the error values are declared via #define. In the reserved bits lie, for example, the overlayable error RTE_E_LOST_DATA (64) and the immediate infrastructure errors from 128 onward, for example RTE_E_COM_STOPPED SWS RTE p. 586. This table originates from R23-11. For R20-11, the bit reservation itself is normatively defined by [SWS_Std_00011].

In the BSW UML model, a module-specific extension is modeled as a class <Ma>_ReturnType with the stereotype «extra_literals». Its values bear the module prefix and lie in the range 0x02–0x3f. According to the same guide, Std_ReturnType is also the only permissible return type for operations in client/server service interfaces BSWUMLModelModelingGuide p. 28. Examples are Csm_ReturnType with CSM_E_BUSY = 2 TR BSWUMLModelModelingGuide p. 29 and the extension CAN_BUSY = 0x02 of the CAN driver for Can_Write() SWS CANDriver p. 54.

Activity diagram: A Std_ReturnType value can be classified into three ranges: RTE-reserved bits, standard values E_OK/E_NOT_OK, and module-specific range 0x02–0x3F. Sources: [SWS_Std_00005], [SWS_Std_00011], SWS StandardTypes p. 15, SWS RTE p. 586

Collaboration diagram: Module extensions such as Csm_ReturnType or CAN_BUSY occupy the range 0x02–0x3F, while the RTE occupies the reserved upper bits. Sources: TR BSWUMLModelModelingGuide p. 29, SWS CANDriver p. 54, [SWS_Std_00011]

Symbol pairs for switches, levels, and states

In addition to the return type, the module defines symbol pairs with fixed values. Each pair is available via Std_Types.h [SWS_Std_00010] [SWS_Std_00007] [SWS_Std_00013]. STD_HIGH/STD_LOW describe physical levels, whereas STD_ACTIVE/STD_IDLE describe logical states.

Version query via Std_VersionInfoType

Std_VersionInfoType is a structure with the fields vendorID and moduleID (each uint16) as well as sw_major_version, sw_minor_version, and sw_patch_version (each uint8). It is used to query the version of a BSW module via <Module name>_GetVersionInfo() [SWS_Std_00015]. The corresponding naming rule specifies GetVersionInfo as the service name. void Eep_21_LDExt_GetVersionInfo(Std_VersionInfoType *versioninfo) serves as an example SRS BSWGeneral p. 60.

The function works synchronously and is reentrant. It has exactly one parameter of type Std_VersionInfoType, which is imported from Std_Types.h. Whether it is present is configured per module at pre-compile time via <Ma>VersionInfoApi. Published information of the module is delivered: Vendor Id, Module Id, and the vendor-specific version number SWS BSWGeneral p. 76. Interpretation: The fields are likely to correspond to the parameters VendorId, ModuleId, and SwMajorVersion/SwMinorVersion/SwPatchVersion from CommonPublishedInformation ECU ConfigurationParameters p. 14. If development error detection is active, the modules check the pointer. In case of NULL, they report, for example, CAN_E_PARAM_POINTER SWS CANDriver p. 57 or ADC_E_PARAM_POINTER SWS ADCDriver p. 80.

Sequence diagram: The version query is a synchronous call with optional pointer check in which the module populates the structure. Sources: [SWS_Std_00015], SWS BSWGeneral p. 76, SWS CANDriver p. 57, SWS NVRAMManager p. 158

Transformer types: Errors, classes, and forward codes as of R20-11

In R20-11, Std_TransformerError is a structure consisting of errorCode (type uint8) and transformerClass (type Std_TransformerClass) [SWS_Std_00021]. Although the API overview states typedef uint8 as the signature, the structure definition of the requirement is decisive. Later releases type errorCode as Std_TransformerErrorCode. The meaning of the values applies there in each case to the specific transformer chain SWS StandardTypes p. 16. Std_TransformerClass is derived from uint8 and has the following values: STD_TRANSFORMER_UNSPECIFIED (0x00), STD_TRANSFORMER_SERIALIZER (0x01), STD_TRANSFORMER_SAFETY (0x02), STD_TRANSFORMER_SECURITY (0x03), and STD_TRANSFORMER_CUSTOM (0xFF) [SWS_Std_00024].

Both of the following types have Draft status in R20-11. Std_TransformerForward is a structure consisting of errorCode (type Std_TransformerForwardCode) and transformerClass [SWS_Std_00027]. Std_TransformerForwardCode has the values E_OK (0x00), E_SAFETY_INVALID_REP (0x01), E_SAFETY_INVALID_SEQ (0x02), and E_SAFETY_INVALID_CRC (0x03) [SWS_Std_00029]. With R22-11, [SWS_Std_00027] was removed SWS StandardTypes p. 1. Later releases also use the literals STD_E_FORWARDCODE_*, whose descriptions cannot be mapped congruently to the R20-11 names SWS StandardTypes p. 17. For R20-11, the names from the requirement apply. Interpretation: The codes are likely intended to deliberately re-inject detected safety errors during forwarding. This is also indicated by the E2E forward functions, which reconstruct detected errors on the output data SWS E2ELibrary p. 107.

In the RTE specification of later releases, Rte_Send can have an optional input parameter forwardedCode and an optional output parameter Std_TransformerError transformerError SWS RTE p. 704. Rte_Call also has an optional transformerError as output SWS RTE p. 731. For Rte_Trigger, this parameter is only generated if a PortAPIOption with errorHandling = transformerErrorHandling references the port SWS RTE p. 774.

Sequence diagram: An error in the transformer chain reaches the caller in two ways, as Std_TransformerError with class and as a return value for communication errors. Sources: [SWS_Std_00021], [SWS_Std_00024], SWS RTE p. 731, SwCluster-Guideline p. 245, SWS RTE p. 586

Message type, message result, and header extraction in C/S transformer chains

Std_MessageTypeType is derived from uint8. It distinguishes between STD_MESSAGETYPE_REQUEST (0x00) and STD_MESSAGETYPE_RESPONSE (0x01); the range 0x02–0x3F is reserved for future types [SWS_Std_91001]. The type encodes the message types in AUTOSAR, currently restricted to requests and responses in C/S communication [SWS_Std_00017]. The API overview refers to the type in abbreviated form as Std_MessageType, but the name Std_MessageTypeType is authoritative. Std_MessageResultType distinguishes between STD_MESSAGERESULT_OK (0x00) and STD_MESSAGERESULT_ERROR (0x01); 0x02–0x3F are reserved [SWS_Std_91002] [SWS_Std_00019]. For both types, later releases announce possible further literals SWS StandardTypes p. 18 SWS StandardTypes p. 19.

Std_ExtractProtocolHeaderFieldsType is a function pointer with the parameters const uint8* buffer, uint32 bufferLength as well as the outputs messageType and messageResult. The target function returns Std_ReturnType and is synchronous and reentrant [SWS_Std_91003]. Its purpose is currently limited to REQUEST/RESPONSE and OK/ERROR SWS StandardTypes p. 20. In <Mip>_Inv_<transformerId>, the optional argument extractProtocolHeaderFields points to the extraction function of a previous transformer in the chain. The argument exists only if the XfrmImplementationMapping has an XfrmTransformerClassExtractProtocolHeaderFields TransformerGeneral p. 40. A suitable implementation is SomeIpXf_ExtractProtocolHeaderFields SWS SOMEIPTransformer p. 61. Interpretation: The E2E transformer presumably calls this function for PXXm profiles via the pointer and passes messageType/messageResult on to the E2E Library SWS E2ETransformer p. 54.

Sequence diagram: The E2E transformer first extracts the header fields for PXXm profiles and only checks via the E2E Library in case of E_OK. Sources: [SWS_Std_91003], TransformerGeneral p. 40, SWS SOMEIPTransformer p. 61, SWS E2ETransformer p. 54, SWS E2ELibrary p. 109

Activity diagram: Message type and message result determine whether checking is performed at the data sink (server) or at the data source (client). Sources: [SWS_Std_91001], [SWS_Std_91002], SWS E2ELibrary p. 108, SWS E2ELibrary p. 109

Behavior in the event of an error

Only type and symbol definitions are available for std, starting at [SWS_Std_00005]. The error behavior therefore results from how the using modules employ these values:

  • Generic error: E_NOT_OK indicates the failure of a request. For example, Can_GetControllerErrorState reports CAN_E_UNINIT in case of missing initialization and returns E_NOT_OK SWS CANDriver p. 64.
  • Custom error values: Additional values are permitted only with a module prefix and only in the six least significant bits. Bits 7 and 8 remain reserved for the RTE [SWS_Std_00011].
  • Erroneous header: SomeIpXf_ExtractProtocolHeaderFields returns E_NOT_OK if the protocol version is incorrect or bufferLength is smaller than a minimum SOME/IP header SWS SOMEIPTransformer p. 61. The E2E transformer then branches to the FALSE path SWS E2ETransformer p. 38.
  • Transformer error: transformerError contains the error from the transformer chain, while the return value indicates communication errors SwCluster-Guideline p. 245. The RTE error table lists RTE_E_HARD_TRANSFORMER_ERROR (138) and RTE_E_SOFT_TRANSFORMER_ERROR (140) SWS RTE p. 586.
  • Callbacks: Callbacks that are AUTOSAR services return Std_ReturnType. The caller may assume E_OK, although errors can still occur in partitioned systems SWS BSWGeneral p. 69.
  • Type compatibility: BSW service APIs called via the RTE must return Std_ReturnType. A different type or void leads to incompatibility RS BSWGeneral p. 63. In addition, the return values must match on both sides ModelConstraints p. 197.
  • Name conflict with OSEK: E_OK is protected via STATUSTYPEDEFINED so that it is not defined twice [SWS_Std_00006] SRS BSWGeneral p. 62.
