Role in the communication stack: neutral mediator for I-PDUs

The PDU Router (PduR) connects bus-independent users such as Com or Dcm with communication interfaces (CanIf, FrIf, LinIf) and transport protocols (CanTp, FrTp). It transmits an I-PDU unchanged and consistently from the source to the destinations [SWS_PduR_00160]. In doing so, it routes exclusively along configured routing paths [SWS_PduR_00162]. A path is uniquely determined by two specifications: the source I-PDU ID of the PduR configuration and the destination I-PDU IDs of the called modules [SWS_PduR_00161]. The PduR translates these IDs in the transmit path just as in the confirmation and indication paths [SWS_PduR_00766], SWS PduR p. 33.

From the perspective of the ECU, there are three classes of operations: first, reception to local modules; second, transmission from local modules; and third, gatewaying between interface or TP modules. Reception and gatewaying may be combined SWS PduR p. 29. The adjacent modules are described generically via the placeholders <Up>, <Lo>, and <LoTp> SWS PduR p. 96. Complex Drivers can also be connected; their apiServicePrefix then replaces the placeholders [SWS_PduR_00504]. Each adjacent module receives its own header file, such as PduR_CanIf.h [SWS_PduR_00216].

Context diagram: The PduR is located between upper users, interface modules, and TP modules, and is controlled by BswM via routing path groups. Sources: [SWS_PduR_00424], [SWS_PduR_00504], SWS PduR p. 96, SWS BswM p. 166

Under two conditions, the adjacent modules may call each other directly: PduRZeroCostOperation is set, and all routing paths are pre-compile [SWS_PduR_00287]. The PduR then becomes a pure macro layer SWS PduR p. 65. If even a single path is not pre-compile, the generator must report an error [SWS_PduR_00619]. Independently of this, the generator is supposed to optimize away unused features, such as TP, gatewaying, or FIFO handling [SWS_PduR_00764].

Lifecycle and configuration state: from PDUR_UNINIT to PDUR_ONLINE

There is exactly one state machine [SWS_PduR_00644]. It knows the states PDUR_UNINIT and PDUR_ONLINE from PduR_StateType [SWS_PduR_00324], [SWS_PduR_00742]. After power-on, the PduR is in PDUR_UNINIT [SWS_PduR_00325]. Only a successful PduR_Init brings it to PDUR_ONLINE [SWS_PduR_00326], [SWS_PduR_00334]. Routing takes place only in PDUR_ONLINE [SWS_PduR_00328], and not at all in PDUR_UNINIT [SWS_PduR_00330]. An older diagram additionally shows a state PDUR_REDUCED SWS PduR p. 30. For R20-11, however, the two-state model according to [SWS_PduR_00324] applies.

State diagram: Only PduR_Init leads from PDUR_UNINIT into routing operation; a renewed Init call is an error. Sources: [SWS_PduR_00324], [SWS_PduR_00100], [SWS_PduR_00296], SWS PduR p. 53

PduR_Init receives a pointer to PduR_PBConfigType [SWS_PduR_00743]. This structure is implementation-specific and is located in PduR_PBcfg.c [SWS_PduR_00241]. During initialization, the PduR performs three tasks:

  • It frees all buffers [SWS_PduR_00645].
  • It initializes the transmit buffers with the configured default values [SWS_PduR_00308].
  • It activates the routing path groups according to the start configuration [SWS_PduR_00709], i.e., according to PduRIsEnabledAtInit SWS PduR p. 131.

In the post-build variant, the routing tables are exchangeable [SWS_PduR_00295], though only in the uninitialized state [SWS_PduR_00296]. PduR_GetConfigurationId returns the unique PduRConfigurationId of the active configuration [SWS_PduR_00341], [SWS_PduR_00280], [SWS_PduR_00281]. Its type is PduR_PBConfigIdType based on uint16 [SWS_PduR_00771]. PduR_GetVersionInfo [SWS_PduR_00338] is only available if PduRVersionInfoApi is set System Template p. 656.

Local transmission and reception via communication interfaces

If an upper module calls PduR_<User:Up>Transmit [SWS_PduR_00406], the PduR calls <Lo>_Transmit for each destination interface [SWS_PduR_00625]. In doing so, it does not buffer the I-PDU [SWS_PduR_00629] and also does not check its length [SWS_PduR_00745]. In singlecast, it passes the return value through [SWS_PduR_00432]. In multicast, a single successful destination is sufficient for E_OK [SWS_PduR_00218]. The confirmation to the upper module then follows only after the last interface confirmation [SWS_PduR_00589]. In singlecast, the PduR forwards PduR_<User:Lo>TxConfirmation [SWS_PduR_00365] along with the result to <Up>_TxConfirmation [SWS_PduR_00627].

In the case of time-triggered buses, the interface fetches the data itself, namely via PduR_<User:Lo>TriggerTransmit [SWS_PduR_00369]. The PduR forwards this request to <Up>_TriggerTransmit [SWS_PduR_00430] and returns its return value [SWS_PduR_00661]. The interface reports received I-PDUs with PduR_<User:Lo>RxIndication [SWS_PduR_00362]. The PduR thereupon calls <Up>_RxIndication for each destination module [SWS_PduR_00621], [SWS_PduR_00164], likewise without length checking [SWS_PduR_00744].

Sequence diagram: Transmission via FrIf breaks down into three temporally separate phases: request, data fetch via TriggerTransmit, and confirmation. Sources: [SWS_PduR_00430], [SWS_PduR_00627], SWS PduR p. 106

Transport protocol paths for segmented I-PDUs

On TP paths, the PduR operates with a copy handshake that enables I-PDUs larger than a frame Layered Architecture p. 97. Reception proceeds in three steps:

  1. The PduR forwards PduR_<User:LoTp>StartOfReception [SWS_PduR_00507] to <Up>_StartOfReception [SWS_PduR_00549] and passes back its return value [SWS_PduR_00623].
  2. The CopyRxData calls for the individual segments follow [SWS_PduR_00512], [SWS_PduR_00428].
  3. The reception indication forms the conclusion [SWS_PduR_00375], [SWS_PduR_00429].

A copy call with SduLength = 0 merely queries the available buffer or available data [SWS_PduR_00740].

Sequence diagram: During TP reception, the PduR requests buffer from the upper module for each segment and passes its responses back unchanged. Sources: [SWS_PduR_00549], [SWS_PduR_00428], [SWS_PduR_00429], SWS PduR p. 75

During transmission, the PduR calls <LoTp>_Transmit for each destination TP [SWS_PduR_00634]. The TP modules subsequently fetch the data with PduR_<User:LoTp>CopyTxData [SWS_PduR_00518]. The PduR forwards these calls to <Up>_CopyTxData [SWS_PduR_00299], [SWS_PduR_00676]. In multicast, it copies for each position first with TP_CONFPENDING; for all further destinations, it copies the same data with TP_DATARETRY [SWS_PduR_00631], [SWS_PduR_00632]. In singlecast, <Up>_TpTxConfirmation follows directly [SWS_PduR_00301]. In multicast, it follows only after the last confirmation, specifically with E_OK if at least one destination was successful [SWS_PduR_00765], [SWS_PduR_00381]. The destinations of a transmit request are either only interfaces or only TP modules, never mixed [SWS_PduR_00633].

Sequence diagram: During TP multicast, the PduR fetches the same data multiple times from the upper module and aggregates the confirmations into one. Sources: [SWS_PduR_00631], [SWS_PduR_00632], [SWS_PduR_00765], SWS PduR p. 86

Gateway operation between networks: buffering, FIFO, and on-the-fly

Between interfaces, the PduR supports 1:n gatewaying [SWS_PduR_00436]. It forwards the I-PDUs immediately and does not generate its own transmission timing [SWS_PduR_00437]. An I-PDU is routed only between interfaces or only between TPs, never mixed [SWS_PduR_00638]. Whether the PduR buffers depends on the data provision of the destination:

  • With PDUR_DIRECT, the destination interface copies the data already in the Transmit call [SWS_PduR_00303].
  • With PDUR_TRIGGERTRANSMIT, the PduR buffers the I-PDU until the TriggerTransmit call [SWS_PduR_00306].

Without buffering, the PduR forwards the smaller of the two lengths, reception length or destination length [SWS_PduR_00783]. With buffering, it copies at most PduRPduMaxLength [SWS_PduR_00746].

A FIFO can be configured for each destination I-PDU [SWS_PduR_00307]. From PduRQueueDepth > 1, the buffer behaves as a FIFO [SWS_PduR_00785], and new I-PDUs are appended at the end [SWS_PduR_00787]. In direct provision, the following applies: If the FIFO is empty and no confirmation is pending, the PduR transmits immediately [SWS_PduR_00665]. Otherwise, it queues the I-PDU [SWS_PduR_00793] and transmits it after the next confirmation [SWS_PduR_00667]. In trigger transmit, the PduR copies the oldest entry and removes it; if content remains thereafter, it calls <DstLo>_Transmit again [SWS_PduR_00666]. If the FIFO is empty, the fetch returns E_NOT_OK [SWS_PduR_00662].

Activity diagram: In an interface gateway, data provision and FIFO state determine whether the PduR transmits immediately, queues, or waits for TriggerTransmit. Sources: [SWS_PduR_00665], [SWS_PduR_00786], [SWS_PduR_00255], SWS PduR p. 112

TP gateways operate in one of two modes:

  • Direct: The PduR calls <DstLoTp>_Transmit only after a successful reception indication [SWS_PduR_00551].
  • On-the-fly: Retransmission begins as soon as PduRTpThreshold is reached [SWS_PduR_00317]. This mode is permitted only with exactly one destination TP [SWS_PduR_00708], SWS PduR p. 58.

If TpSduLength fits into the dedicated buffer, the PduR uses it; otherwise, it dynamically acquires a buffer from PduRTxBuffer [SWS_PduR_00797], [SWS_PduR_00798]. It passes MetaData through to the destination [SWS_PduR_00794]. If a local receiver is additionally configured, the PduR starts a separate reception session with this module after successful reception [SWS_PduR_00789].

Sequence diagram: In an on-the-fly gateway, reception on CAN1 and transmission on CAN2 overlap as soon as the threshold is reached. Sources: [SWS_PduR_00317], [SWS_PduR_00708], [SWS_PduR_00518], SWS PduR p. 100

Switching routing path groups at runtime

PduRRoutingPathGroup containers group the paths of a network or of a PDU type SWS PduR p. 131. They are addressed via PduR_RoutingPathGroupIdType, a uint16 [SWS_PduR_00654]. They are switched with PduR_EnableRouting and PduR_DisableRouting [SWS_PduR_00615], [SWS_PduR_00617]. The parameter initialize determines whether single buffers are reset to the default value or retained [SWS_PduR_00617]. Activation takes effect immediately [SWS_PduR_00715]. If an API uses the I-PDU ID of a disabled path, the PduR returns E_NOT_OK without further action, insofar as the return type permits [SWS_PduR_00717]. This explicitly applies to the cancellation functions as well [SWS_PduR_00710], [SWS_PduR_00726].

The typical caller is BswM via the action BswMPduRouterControl SWS BswM p. 166. The mode management guide cites two use cases: I-PDUs without a Com I-PDU group, such as via LdCom, and switching dependent on the PNC state that ComM reports to BswM Mode-Management-Guide p. 50. Later releases clarify how paths with multiple groups are re-evaluated SWS PduR p. 69. These rules do not belong to the R20-11 requirements present here.

Sequence diagram: BswM disables a routing path group; transmit calls on affected paths fail until the group is enabled again. Sources: [SWS_PduR_00617], [SWS_PduR_00717], [SWS_PduR_00715], Mode-Management-Guide p. 50

Behavior in the event of an error

If PduRDevErrorDetect is active, the PduR reports development errors to the DET [SWS_PduR_00100], SWS PduR p. 72:

  • PDUR_E_INIT_FAILED for an invalid configuration pointer [SWS_PduR_00100].
  • PDUR_E_UNINIT for calls prior to initialization, except PduR_Init and PduR_GetVersionInfo [SWS_PduR_00119], and for PduR_Init outside of PDUR_UNINIT [SWS_PduR_00100].
  • PDUR_E_PDU_ID_INVALID for an invalid PDU ID [SWS_PduR_00221].
  • PDUR_E_PARAM_POINTER for null pointers [SWS_PduR_00100].
  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID for an unknown group ID [SWS_PduR_00648], [SWS_PduR_00649]. The switching function itself returns without effect in this case [SWS_PduR_00647], [SWS_PduR_00716].

The PduR does not report production errors SWS PduR p. 60.

If I-PDU instances are lost, the PduR reports the runtime error PDUR_E_PDU_INSTANCES_LOST. This error was introduced with AUTOSAR 4.3.1 SWS PduR p. 3; it is reported via Det_ReportRuntimeError [SWS_PduR_91001]. Two situations trigger it:

  • The FIFO is full: The PduR empties it and treats the new I-PDU as with an empty FIFO [SWS_PduR_00255], [SWS_PduR_00669], [SWS_PduR_00670].
  • <DstLo>_Transmit returns E_NOT_OK: The PduR discards the instance and transmits the next one [SWS_PduR_00788], [SWS_PduR_00807].

Interpretation: Disabling a group is likely to be considered "stopping" within the meaning of [SWS_PduR_00663]; associated FIFOs would then also be emptied.

The PduR does not retry failed gateway transmissions [SWS_PduR_00256]. In local transmissions with one destination, the upper module receives the return value of the destination [SWS_PduR_00626], [SWS_PduR_00700]. With multiple destinations, [SWS_PduR_00701] requires that all destinations return E_OK; presumably this pertains to the TP transmit path, whereas for interface multicast according to [SWS_PduR_00218], a single success is sufficient.

The following applies to TP reception and TP gateways:

  • The PduR only forwards erroneous TP reception indications locally [SWS_PduR_00207]; in a gateway, they terminate processing [SWS_PduR_00689].
  • If an on-the-fly gateway cannot store the data, the PduR returns BUFREQ_E_NOT_OK [SWS_PduR_00687]. If a buffer is missing entirely, it returns BUFREQ_E_OVFL [SWS_PduR_00799].
  • If one destination fails, the remaining ones continue [SWS_PduR_00803], [SWS_PduR_00806]. Only when all TP destinations fail does the PduR terminate the reception side [SWS_PduR_00804].
  • In a gateway, the PduR aborts local TP receivers in case of errors or indicates them with E_NOT_OK [SWS_PduR_00790], [SWS_PduR_00791], [SWS_PduR_00792].

The synchronous function PduR_EnableRouting serves to activate a routing path group ([SWS_PduR_00615]). The respective routing path group previously specified in the PDU Router configuration is addressed via the input parameter id of type PduR_RoutingPathGroupIdType ([SWS_PduR_00615]). The service returns no value (void) and is declared with the service ID 0xf3 via the header file PduR.h ([SWS_PduR_00615]).

Error handling

With regard to possible error states, the following error codes are specified for PduR_EnableRouting ([SWS_PduR_00100]):

  • PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (0x08): Detected if an invalid routing table or routing path group ID is passed to the function ([SWS_PduR_00100]).
  • PDUR_E_UNINIT (0x01): Occurs if this API service is called before successful module initialization of the PDU Router ([SWS_PduR_00100]).

Concurrency and Limitations

The function is specified as reentrant ([SWS_PduR_00615]).

void PduR_DisableRouting (PduR_RoutingPathGroupIdType id, boolean initialize);

Disables a routing path group.

use

The synchronous function PduR_DisableRouting ([SWS_PduR_00617]) serves to disable a routing path group (Routing Path Group) in the PDU Router. It has no return value (void) and is provided via the header PduR.h.

Upon invocation, the function expects two input parameters:

  • id: Identifies the routing path group to be disabled, as defined in the PDU Router configuration.
  • initialize: Controls the handling of single buffers (Single Buffers). When true is passed, these buffers are initialized to their default value; with false, the current buffer contents are retained.

Concurrency and Limitations

According to [SWS_PduR_00617], the function is specified as reentrant. For a valid call, the PduR module must have been initialized previously.

Error Handling and Interaction

With regard to error handling, direct references to [SWS_PduR_00100] exist:

  • If the function is called without the module being initialized, this pertains to error PDUR_E_UNINIT (error value 0x01).
  • If an invalid routing table or group ID is passed to PduR_DisableRouting, the error code PDUR_E_ROUTING_PATH_GROUP_ID_INVALID (error value 0x08) is provided.

States of the PDU Router

The enumeration type PduR_StateType describes the states of the PDU Router ([SWS_PduR_00742]). It is available via the header PduR.h and defines the fundamental lifecycle of the module.

According to [SWS_PduR_00324], the PDU Router module consists of exactly two states, which are represented by the values of the type:

  • PDUR_UNINIT: The PDU Router is not initialized ([SWS_PduR_00742], [SWS_PduR_00324]).
  • PDUR_ONLINE: The PDU Router was successfully initialized ([SWS_PduR_00742], [SWS_PduR_00324]).

In interaction, this type serves as the state basis for the PDU Router, where the transition to PDUR_ONLINE indicates the successful completion of module initialization, while PDUR_UNINIT represents the state before or after leaving operational mode.
