Prior to forwarding, CryIf maps its own key IDs to the IDs of the driver. If they are out of range, it reports CRYPTO_E_PARAM_HANDLE to DET and returns E_NOT_OK [SWS_CryIf_00133] [SWS_CryIf_00134]. In addition, CryIf provides synchronous functions for setting, validating, invalidating, reading, generating, deriving, exchanging, and copying keys. If source and target reside in different drivers during partial copying, CryIf reads the element and writes it to the target itself [SWS_CryIf_00140].

Development errors such as CRYIF_E_UNINIT or CRYIF_E_PARAM_POINTER are reported to DET [SWS_CryIf_00009]. Runtime errors such as CRYPTO_E_BUSY or CRYPTO_E_KEY_NOT_VALID are returned as return values [SWS_CryIf_91020]. Later releases deviate from R20-11: They unify CRYIF_E_PARAM_HANDLE and specify CryIf_RandomSeed as well as CryIf_KeyGenerate as synchronous SWS CryIf p. 1.

Role of CryIf Between Crypto Service Manager and Crypto Driver

The Crypto Interface (CryIf) is located in the Classic crypto stack in the ECU Abstraction Layer. Applications request cryptographic services via RTE and CSM. These requests travel through logical channels through CryIf to the Crypto Driver in the MCAL and further to its hardware engines, such as HW-AES and HW-RSA in an HSM SWS CSM Fig. 7.4 p. 27. A Crypto Driver Object represents an independent crypto \"device\" in hardware or software, for example an AES accelerator or an RSA implementation in software SWS CSM p. 26. CryIf performs no computation itself. Its functions forward the respective call to the configured Crypto Driver Object, such as [SWS_CryIf_91005], [SWS_CryIf_91007], [SWS_CryIf_91009], and [SWS_CryIf_91014].

Toward higher layers, CryIf provides three groups of interfaces:

  • the job interface CryIf_ProcessJob [SWS_CryIf_91003],
  • the job cancellation CryIf_CancelJob [SWS_CryIf_91014],
  • direct key management from CryIf_KeyElementSet [SWS_CryIf_91004] to CryIf_KeySetInvalid [SWS_CryIf_91021].

For a job in the state \"ACTIVE\", CSM calls CryIf_ProcessJob and forwards its return value unchanged SWS CSM p. 22. Toward lower layers, CryIf receives the completion notifications of the driver via CryIf_CallbackNotification [SWS_CryIf_91013] SWS Crypto p. 27. From other modules, it requires Csm_CallbackNotification and Det_ReportRuntimeError [SWS_CryIf_91100], optionally in addition Det_ReportError [SWS_CryIf_91101].

Context diagram: CryIf connects the CSM queues channel by channel to the Crypto Driver Objects and reports results back to CSM. Sources: SWS CSM Fig. 7.4 p. 27, [SWS_CryIf_91100], [SWS_CryIf_91013]

Channels, Configuration, and Initialization

A channel is the path from a CSM queue via CryIf to a Crypto Driver Object. Each queue of CSM is assigned to exactly one channel; optionally, the Crypto Driver also has its own queue SWS CSM p. 26. Channels are configured in container CryIfChannel, with multiplicity 0..* and pre-compile configuration in all variants. The container contains parameters CryIfChannelId and CryIfDriverObjectRef SWS CryIf p. 51. CryIfChannelId determines which channel a CSM queue is connected to. At runtime, parameter channelId of [SWS_CryIf_91003] and [SWS_CryIf_91014] likewise designates the crypto channel. Interpretation: CryIfDriverObjectRef likely binds the channel to the Crypto Driver Object that executes the jobs of this channel.

Prior to any use, CryIf_Init must be called [SWS_CryIf_91000]. The function is synchronous and non-reentrant. It receives a pointer to the selected configuration of type CryIf_ConfigType, whose content is implementation-specific [SWS_CryIf_91118] SWS CryIf p. 20. For a failed initialization, the error list provides CRYIF_E_INIT_FAILED (0x01) [SWS_CryIf_00009]. CryIf_GetVersionInfo is reentrant and provides the version information of the module [SWS_CryIf_91001].

In addition to channels, CryIf maintains its own key identifiers (cryIfKeyId). It maps them to the key IDs of the responsible driver [SWS_CryIf_00133]. If a job uses job processing redirection, CryIf additionally adapts incoming key and key element references to those of the driver [SWS_CryIf_00136]. A key consists of one or more key elements, such as key material, initialization vector, or seed SWS CSM p. 30.

Job Processing from CryIf_ProcessJob to Feedback

Single call and streaming run via the same function CryIf_ProcessJob. The field job->jobPrimitiveInputOutput.mode contains the operation modes "START", "UPDATE", and "FINISH", which can be combined. A complete service in a single call corresponds to the combination of all three modes SWS CryIf p. 22. The function is reentrant and operates synchronously or asynchronously depending on the configuration [SWS_CryIf_91003]. The state transitions of a job are performed by the Crypto Driver, not the CSM SWS CSM p. 22.

In the asynchronous case, the driver only passes the necessary information to the primitive. The computation can then be triggered from the main function. After completion, the driver reports the job and result to the CryIf via CryIf_CallbackNotification SWS Crypto p. 27. This function is synchronous and non-reentrant; the passed job contains a callback ID that identifies it [SWS_CryIf_91013]. The CryIf then reports the completion via Csm_CallbackNotification to the CSM; this function is explicitly intended for the underlying CRYIF layer [SWS_CryIf_91100]. If the FINISH bit is set, the CSM invokes the configured callback SWS CSM p. 82.

Sequence diagram: The CryIf first checks the key IDs and then forwards the job. The result is returned either synchronously as a return value or asynchronously via two callback stages. Sources: [SWS_CryIf_91003], [SWS_CryIf_00134], [SWS_CryIf_91013], [SWS_CryIf_91100], SWS Crypto p. 27

Running asynchronous jobs and streaming jobs can be canceled. For this purpose, the CSM removes the job from its own queue or calls CryIf_CancelJob SWS CSM p. 80. CryIf_CancelJob is synchronous and reentrant and forwards the cancellation to the configured Crypto Driver Object. E_OK means that the job was removed; E_NOT_OK means that this was not possible [SWS_CryIf_91014] SWS CryIf p. 24. The documentation passages of later releases (R24-11/R25-11) additionally mention CRYPTO_E_JOB_CANCELED. In this case, the cancellation only takes place at the next suitable processing step and is reported via a negative completion callback SWS CSM p. 80.

Sequence diagram: A cancellation either ends already in the CSM queue or is forwarded via the CryIf to the Crypto Driver Object. Sources: [SWS_CryIf_91014], SWS CSM p. 80, SWS CryIf p. 45

Mapping and checking key IDs in the job

Some jobs carry a key management service: CRYPTO_KEYSETVALID, CRYPTO_KEYSETINVALID, CRYPTO_RANDOMSEED, CRYPTO_KEYGENERATE, CRYPTO_KEYDERIVE, CRYPTO_KEYEXCHANGECALCPUBVAL, or CRYPTO_KEYEXCHANGECALCSECRET. For them, the CryIf checks whether job->jobPrimitiveInputOutput->cryIfKeyId and, if applicable, targetCryIfKeyId lie within the valid range. If this is the case, it sets job->cryptoKeyId and job->targetCryptoKeyId, respectively, to the key IDs of the driver [SWS_CryIf_00133] [SWS_CryIf_00141]. If the source ID lies outside the range, CryIf_ProcessJob reports CRYPTO_E_PARAM_HANDLE to the DET and returns E_NOT_OK [SWS_CryIf_00134]. For CRYPTO_KEYDERIVE, the same also applies to the target ID [SWS_CryIf_00135].

Primitives with key reference are checked as well. For CRYPTO_MACGENERATE, CRYPTO_MACVERIFY, CRYPTO_ENCRYPT, CRYPTO_DECRYPT, CRYPTO_AEADENCRYPT, CRYPTO_AEADDECRYPT, CRYPTO_RANDOMGENERATE, CRYPTO_SIGNATUREGENERATE, and CRYPTO_SIGNATUREVERIFY, job->jobPrimitiveInfo->cryIfKeyId is checked for the valid range [SWS_CryIf_00143].

Activity diagram: The CryIf checks the key IDs depending on the service type and maps them to driver IDs before forwarding the job. Sources: [SWS_CryIf_00133], [SWS_CryIf_00134], [SWS_CryIf_00135], [SWS_CryIf_00143]

This area has changed between releases. R20-11 mentions CRYPTO_E_PARAM_HANDLE in the checks, whereas the module's error list defines CRYIF_E_PARAM_HANDLE (0x03) [SWS_CryIf_00009]. According to the change history, this was only unified to CRYIF_E_PARAM_HANDLE in R22-11 SWS CryIf p. 1. With the same change, the return values after DET reports were omitted. In addition, the service CRYPTO_CUSTOM was added, which is already included in the list in the later documentation passage SWS CryIf p. 23. For R20-11, the requirements apply in the form cited here.

Key management: material, status, generation, and exchange

The direct key APIs are synchronous. Non-reentrant are CryIf_KeyElementSet [SWS_CryIf_91004], CryIf_KeySetValid [SWS_CryIf_91005], CryIf_KeySetInvalid [SWS_CryIf_91021], and CryIf_KeyGetStatus [SWS_CryIf_91012]. According to the change history, the functionality for the key status was added with R20-11 SWS CryIf p. 1. If setting an element fails, its status is considered unknown according to the CSM specification SWS CSM p. 62. It can be checked with Csm_KeyGetStatus, which in turn calls CryIf_KeyGetStatus SWS CSM p. 63.

CryIf_KeyElementGet is reentrant [SWS_CryIf_91006]. The parameter resultLengthPtr serves as input and output. Upon invocation, it contains the buffer size; for elements with partial access, it contains instead the amount to be read. After completion, it contains the data amount actually stored SWS CryIf p. 30.

State diagram: A key is declared valid after its elements are set and can be set to invalid again. With an invalid key, operations fail with CRYPTO_E_KEY_NOT_VALID. The initial state before CryIf_KeySetValid is an interpretation. Sources: [SWS_CryIf_91004], [SWS_CryIf_91005], [SWS_CryIf_91021], [SWS_CryIf_91012], SWS CSM p. 70

For key generation, CryIf_RandomSeed [SWS_CryIf_91007] provides the seed values, and CryIf_KeyGenerate [SWS_CryIf_91008] generates the key. According to the CSM specification, the key is generated in element CRYPTO_KE_KEYGENERATE_KEY. The basis is the seed in CRYPTO_KE_KEYGENERATE_SEED and the algorithm in CRYPTO_KE_KEYGENERATE_ALGORITHM SWS CSM p. 67. In R20-11, both functions operate synchronously or asynchronously depending on the configuration [SWS_CryIf_91007] [SWS_CryIf_91008]. Only R21-11 specifies them as synchronous SWS CryIf p. 1. CryIf_KeyDerive is synchronous and reentrant and derives from a source key a key that is stored in the target key [SWS_CryIf_91009] SWS CryIf p. 42.

There are two functions for the Diffie-Hellman key exchange. CryIf_KeyExchangeCalcPubVal [SWS_CryIf_91010] calculates its own public value. CryIf_KeyExchangeCalcSecret [SWS_CryIf_91011] calculates the shared secret from the partner's value. The key material resides in elements CRYPTO_KE_KEYEXCHANGE_BASE, CRYPTO_KE_KEYEXCHANGE_PRIVKEY, and CRYPTO_KE_KEYEXCHANGE_OWNPUBKEY SWS CSM p. 70. The driver stores the secret as an element in the same key SWS Crypto p. 84. Interpretation: In the direct key APIs as well, the CryIf likely maps cryIfKeyId to the key ID of the driver, as in the job path [SWS_CryIf_00133].

Sequence diagram: Key exchange runs in two CryIf calls. In between, the application exchanges the public values with the partner outside the CryIf. Sources: [SWS_CryIf_91010], [SWS_CryIf_91011], SWS CSM p. 70, SWS Crypto p. 84

Copying keys within and between Crypto Drivers

For copies, there are CryIf_KeyElementCopy [SWS_CryIf_91015], CryIf_KeyCopy [SWS_CryIf_91016], and CryIf_KeyElementCopyPartial [SWS_CryIf_91018]. All three are synchronous and reentrant, but not for the same cryIfKeyId. In addition to E_OK and E_NOT_OK, they can return, among others, CRYPTO_E_KEY_READ_FAIL, CRYPTO_E_KEY_WRITE_FAIL, CRYPTO_E_KEY_SIZE_MISMATCH, and CRYPTO_E_KEY_EMPTY SWS CryIf p. 35.

For partial copying, the specification distinguishes between two cases:

  • Source and target keys reside in the same Crypto Driver: The CryIf calls Crypto_<vi>_<ai>_KeyElementCopyPartial() of the assigned driver and forwards its return value [SWS_CryIf_00139].
  • The keys reside in different drivers: The CryIf reads the element with Crypto_<vi>_<ai>_KeyElementGet(), copies the partial data to its destination, and writes the target element with Crypto_<vi>_<ai>_KeyElementSet() [SWS_CryIf_00140].

The copy functions of the drivers are optional interfaces. If an element resides directly in flash, a call may take significantly longer SWS CryIf p. 45.

Activity diagram: Whether the CryIf delegates directly to the driver or copies itself via read and write depends on whether the keys reside in the same driver. Sources: [SWS_CryIf_00139], [SWS_CryIf_00140]

The CryIf reports development errors to the DET. The module's error list comprises [SWS_CryIf_00009]:

Reporting CRYIF_E_UNINIT prior to initialization is documented for several functions: CryIf_KeyDerive SWS CryIf p. 42, CryIf_RandomSeed SWS CryIf p. 37, CryIf_CancelJob SWS CryIf p. 24, CryIf_KeyGetStatus SWS CryIf p. 29, and CryIf_CallbackNotification SWS CryIf p. 44. The same presumably applies to the remaining services. Further checks are also documented. CryIf_CancelJob reports CRYIF_E_PARAM_HANDLE in case of an inadmissible channelId, CryIf_KeyGetStatus in case of an inadmissible cryIfKeyId. CryIf_CallbackNotification checks its pointer and reports CRYIF_E_PARAM_POINTER if applicable SWS CryIf p. 44.

Runtime errors arrive as return values from the driver. The CryIf forwards them, as specified, for instance, by [SWS_CryIf_00139] for partial copying. The CSM in turn forwards the return value of CryIf_ProcessJob SWS CSM p. 22. The value range comprises, among others, [SWS_CryIf_91020]:

  • CRYPTO_E_BUSY (0x02): service still busy
  • CRYPTO_E_ENTROPY_EXHAUSTED (0x04)
  • CRYPTO_E_KEY_READ_FAIL (0x06)
  • CRYPTO_E_KEY_WRITE_FAIL (0x07)
  • CRYPTO_E_KEY_NOT_AVAILABLE (0x08)
  • CRYPTO_E_KEY_NOT_VALID (0x09)

If a CSM queue is full, the CSM already rejects the request with CRYPTO_E_BUSY SWS CSM p. 22.

Regarding the return values, a look at the release history is worthwhile. CRYPTO_E_QUEUE_FULL was only removed from [SWS_CryIf_91003] with R23-11. CRYPTO_E_KEY_EMPTY was only added for CryIf_RandomSeed in R24-11 SWS CryIf p. 1. For R20-11, the API requirements of that release are therefore decisive, not the later-dated documentation passages.

Function CryIf_ProcessJob (service ID 0x03), provided via header CryIf.h, forwards cryptographic processing jobs to the respectively configured crypto driver object [SWS_CryIf_91003]. As parameters, it takes the identifier of the crypto channel (channelId) and a pointer to the job configuration (job) [SWS_CryIf_91003]. Structure job contains all information relevant to the user as well as to the specific crypto primitive [SWS_CryIf_91003]. Depending on the configuration, job processing is performed synchronously or asynchronously; in addition, the interface is implemented as reentrant [SWS_CryIf_91003].

Upon error-free acceptance, the function returns E_OK [SWS_CryIf_91003]. If the request fails, the return value signals either E_NOT_OK or a specific error state of the driver: CRYPTO_E_BUSY (driver object busy), CRYPTO_E_QUEUE_FULL (queue full), errors regarding key states such as CRYPTO_E_KEY_NOT_VALID, CRYPTO_E_KEY_SIZE_MISMATCH, CRYPTO_E_KEY_NOT_AVAILABLE, CRYPTO_E_KEY_EMPTY, CRYPTO_E_KEY_READ_FAIL, or CRYPTO_E_KEY_WRITE_FAIL, as well as CRYPTO_E_JOB_CANCELED upon cancellation of a synchronous job and CRYPTO_E_ENTROPY_EXHAUSTED [SWS_CryIf_91003].

In addition, the interface performs pre-checks of the key identifiers:

  • If job->jobPrimitiveInfo->primitiveInfo->service is set to CRYPTO_KEYSETVALID, CRYPTO_KEYSETINVALID, CRYPTO_RANDOMSEED, CRYPTO_KEYGENERATE, CRYPTO_KEYDERIVE, CRYPTO_KEYEXCHANGECALCPUBVAL, or CRYPTO_KEYEXCHANGECALCSECRET, job->cryIfKeyId must be within the valid range of values [SWS_CryIf_00134]. Otherwise, the function reports the error CRYPTO_E_PARAM_HANDLE to the DET and aborts with E_NOT_OK [SWS_CryIf_00134].
  • If service CRYPTO_KEYDERIVE is requested, the target key identifier job->cryIfTargetKeyId must additionally be within the valid range; otherwise, CRYPTO_E_PARAM_HANDLE is likewise reported to the DET and E_NOT_OK is returned [SWS_CryIf_00135].
