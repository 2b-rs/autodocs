Collects diagnostic results from monitors, qualifies them, and manages fault memory including environment data for testers.

There is exactly one Diagnostic Event Manager per ECU [SWS_Dem_00126]. It receives test results from diagnostic monitors, debounces them, and uses them to maintain UDS status bits as well as event memory entries with freeze frames and extended data. DCM and J1939Dcm filter, read, and clear this data via client-specific APIs. They mostly follow the "select, then request" pattern [SWS_Dem_01253]. The most important constraint is the lifecycle: before Dem_Init, messages are only buffered; the module is fully functional only afterwards.

It provides the fault memory contents to DCM and J1939Dcm. It is embedded between EcuM, the scheduling of Dem_MainFunction, NvM, FiM, and DET SWS DEM p. 247.

Context diagram: Monitors deliver results, diagnostic clients and FiM use the DEM. Sources: SWS DEM p. 247

The lifecycle separates a pre-initialization mode from full functionality [SWS_Dem_00169]. Results reported after Dem_PreInit are buffered and do not yet trigger monitor status callbacks ([SWS_Dem_00167], [SWS_Dem_01289]). With Dem_Init, the DEM becomes fully functional [SWS_Dem_00340]. Dem_Shutdown completes pending operations and transfers modified data to NvM ([SWS_Dem_00102], [SWS_Dem_00341]).

Monitors report qualified or unconfirmed results using Dem_SetEventStatus [SWS_Dem_00926]. For each event, the DEM debounces on a counter-based, time-based, or monitor-internal basis [SWS_Dem_00413]. From this, it derives the Fault Detection Counter from -128 to +127 [SWS_Dem_00415]. Debouncing and monitor status run synchronously, while the UDS status byte runs asynchronously ([SWS_Dem_01279], [SWS_Dem_01285]). Enable Conditions and disabled DTC setting block processing SWS DEM p. 83.

Sequence diagram: A report is debounced synchronously; UDS processing follows in the MainFunction. Sources: SWS DEM Fig. 9.12 p. 372, [SWS_Dem_01285]

The DEM creates entries with counters, freeze frames, and extended data depending on the configured trigger ([SWS_Dem_00783], [SWS_Dem_00039], [SWS_Dem_00809]). If memory is full, the displacement strategy decides ([SWS_Dem_00400], [SWS_Dem_00402]). The DCM accesses according to the "select, then request" pattern. Dem_SelectDTC defines the target for reading, status queries, and clearing [SWS_Dem_01253]. Dem_SetDTCFilter specifies the criteria for DTC lists [SWS_Dem_00057].

The DEM reports errors as DET development errors, e.g. DEM_E_UNINIT or DEM_E_WRONG_CONDITION [SWS_Dem_00173]. At runtime, it provides return values such as DEM_WRONG_DTC or DEM_BUSY ([SWS_Dem_01261], [SWS_Dem_01306]). It initializes data that NvM cannot read [SWS_Dem_00578].

Role and system boundary: central fault memory service of the ECU

The Diagnostic Event Manager receives results from diagnostic monitors and qualifies them into events. It stores these in the event memory together with environmental data. There is exactly one DEM module per ECU [SWS_Dem_00126]. Each diagnostic event is represented by a unique EventId and an EventName ([SWS_Dem_00153], [SWS_Dem_00154]). Dem_EventIdType is based on uint16; the value 0 is invalid [SWS_Dem_00925] SWS DEM p. 339.

The interfaces to the environment are shown in Figure 8.1 SWS DEM p. 247:

  • EcuM calls Init and Shutdown.
  • Scheduling calls Dem_MainFunction.
  • NvM persists data [SWS_Dem_00164].
  • FiM is notified of status changes [SWS_Dem_00029].
  • DET receives development errors.
SW-C monitors report via RTE ports such as DiagnosticMonitor [SWS_Dem_00598]. DCM and J1939Dcm access a configured DemEventMemorySet as clients via an ClientId ([SWS_Dem_01247], [SWS_Dem_01251]).

Context diagram: The DEM is the data sink for monitors and the data source for diagnostic clients and FiM. Sources: SWS DEM p. 247, [SWS_Dem_00256]

Lifecycle: pre-initialization, operation, and shutdown

The DEM distinguishes between a pre-initialization mode and a fully initialized mode [SWS_Dem_00169]. Dem_PreInit initializes the states required for event processing [SWS_Dem_00180], including internal debouncing [SWS_Dem_01213]. Events reported afterward end up in a buffer [SWS_Dem_00167] and do not yet trigger monitor status callbacks [SWS_Dem_01289] SWS DEM Fig. 7.42 p. 169.

Dem_Init receives the post-build pointer to Dem_ConfigType ([SWS_Dem_00181], [SWS_Dem_00924]). The function initializes or reinitializes the module SWS DEM p. 260. After that, the DEM is fully functional [SWS_Dem_00340]. The monitor status is formed from previously reported results or the NvM state [SWS_Dem_01326]. Only then does FiM_DemInit follow [SWS_Dem_01325]. A cycle restart initiated prior to Dem_Init is processed retroactively [SWS_Dem_01318].

During operation, Dem_MainFunction processes all non-event-driven functions [SWS_Dem_00125]. Dem_Shutdown completes pending operations [SWS_Dem_00102]. Modified non-volatile data is sent to NvM at the latest then [SWS_Dem_00341]. From monitor report to qualified result

Monitors report test results using Dem_SetEventStatus as soon as a new result is available ([SWS_Dem_00330], SWS DEM p. 81). Dem_EventStatusType distinguishes three types of reports [SWS_Dem_00926]:

  • qualified results (DEM_EVENT_STATUS_PASSED/_FAILED),
  • preliminary results for internal debouncing (_PREPASSED/_PREFAILED),
  • DEM_EVENT_STATUS_FDC_THRESHOLD_REACHED.

Debouncing is configurable per event [SWS_Dem_00413]:

  • counter-based [SWS_Dem_00414],
  • time-based [SWS_Dem_00426],
  • monitor-internal [SWS_Dem_00437].
The DEM maps counter or timer values linearly to the Fault Detection Counter from -128 to +127 ([SWS_Dem_00415], [SWS_Dem_00427]). Counter-based debouncing and monitor status run synchronously in the call context ([SWS_Dem_01279], [SWS_Dem_01280]). In contrast, the DEM computes the UDS status byte asynchronously [SWS_Dem_01285] SWS DEM p. 83.

Sequence diagram: A report is debounced synchronously; subsequent UDS processing runs asynchronously. Sources: SWS DEM Fig. 9.12 p. 372, [SWS_Dem_01285]

The DEM sets UDS status bits 0 to 7 according to its own transition rules ([SWS_Dem_00386], [SWS_Dem_00395]). Dem_ResetEventStatus asynchronously resets bit 0 and initializes debouncing without reporting a Passed result [SWS_Dem_00187] SWS DEM p. 79. If the event has already been tested in the current cycle, the call returns E_NOT_OK [SWS_Dem_00638]. Dem_ResetEventDebounceStatus freezes or resets debouncing ([SWS_Dem_00684], [SWS_Dem_00685]).

State diagram: Transitions of UDS status bit 0 (TestFailed). Sources: SWS DEM Fig. 7.15 p. 70, [SWS_Dem_00386]

Enable conditions, operation cycles, and availability

Enable Conditions and disabled DTC setting block the processing of status reports SWS DEM p. 83. The rules for this are specified in [SWS_Dem_00449] and [SWS_Dem_00079]. DemDebounceBehavior defines whether debouncing is reset [SWS_Dem_00654] or frozen [SWS_Dem_00655] in this case. In contrast, Storage Conditions only prevent storage in memory ([SWS_Dem_00455], [SWS_Dem_00556]).

Dem_RestartOperationCycle operates asynchronously. The affected monitors are reinitialized via InitMonitorForEvent [SWS_Dem_00679] SWS DEM p. 274. Restarts are not buffered [SWS_Dem_01316]. Further triggers for InitMonitorForEvent are:

  • clearing [SWS_Dem_00680],
  • re-fulfilled Enable Conditions [SWS_Dem_00681],
  • Storage Conditions [SWS_Dem_01113].
In the case of simultaneous triggers, the callback is invoked only once, with the highest-priority reason [SWS_Dem_01046] SWS DEM p. 47.

The DEM treats unavailable events marked with Dem_SetEventAvailable as if they were not configured [SWS_Dem_01108] SWS DEM p. 66. This API is missing in VARIANT-POST-BUILD [SWS_Dem_01106]. A suppressed DTC, on the other hand, is only invisible to the tester; event processing continues [SWS_Dem_01102].

Event memory: storage, environmental data, and displacement

The DEM maintains the primary event memory [SWS_Dem_00010] and optionally user-defined memories with identical behavior [SWS_Dem_01063]. An entry bundles counters, freeze frames, and extended data SWS DEM Fig. 7.13 p. 77. DemEventMemoryEntryStorageTrigger defines when an entry is created:

  • on TestFailed or FDC threshold [SWS_Dem_00783],
  • on Pending [SWS_Dem_00784],
  • on Confirmed [SWS_Dem_00785].
Aging removes the event-related data [SWS_Dem_01075].

Freeze frames are event-specific and consist of configured DIDs ([SWS_Dem_00039], [SWS_Dem_00040]). For volatile data, the monitor captures it in advance using Dem_PrestoreFreezeFrame. The DEM uses this data during storage [SWS_Dem_00464] SWS DEM Fig. 7.37 p. 128. Extended Data Records are captured upon configured triggers [SWS_Dem_00809]. They can contain internal values such as occurrence counters [SWS_Dem_00471].

If a free entry is missing, the DEM checks for displacement [SWS_Dem_00400]. DEM_DISPLACEMENT_NONE rules it out [SWS_Dem_00402]. Without candidates, storage is rejected [SWS_Dem_00407]. Otherwise, the entry is removed and the status bits are adjusted ([SWS_Dem_00408], [SWS_Dem_00409]). The DEM indicates an overflow per memory [SWS_Dem_00397].

Activity diagram: Simplified sequence of displacement criteria, without the OBD filter stage. Sources: SWS DEM Fig. 7.28 p. 98, [SWS_Dem_00406]

Access by DCM, J1939Dcm, and OBD services

Many APIs follow the "select, then request" pattern. Dem_SelectDTC defines DTC, format, and origin as the target. For example, Dem_ClearDTC, Dem_GetStatusOfDTC, and Dem_SelectFreezeFrameData act upon this [SWS_Dem_01253] SWS DEM p. 215. For DTC lists, Dem_SetDTCFilter sets the criteria [SWS_Dem_00057]. Dem_GetNextFilteredDTC subsequently iterates over the matches [SWS_Dem_00216]. Returned status bytes are masked with the availability mask [SWS_Dem_00657].

The DCM reads freeze frames using Dem_GetNextFreezeFrameData after selecting the DTC and record [SWS_Dem_01268] SWS DEM Fig. 9.7 p. 369. In doing so, the DEM provides the finished record layout SWS DEM Fig. 7.48 p. 195. Extended data is read analogously [SWS_Dem_01272].

To clear, the DCM first verifies the selection and then calls Dem_ClearDTC ([SWS_Dem_91020], [SWS_Dem_00665]). Prior to clearing, the DEM queries DemClearEventAllowed [SWS_Dem_00515] SWS DEM Fig. 9.3 p. 367. J1939 APIs are available when DemGeneralJ1939 is configured [SWS_Dem_00845]. With OBD support, the DEM additionally provides:

  • PIDs, e.g. [SWS_Dem_00318],
  • IUMPR data [SWS_Dem_00298],
  • Service $06 test results [SWS_Dem_00751].
Only the master ECU calculates PID $31/$4D/$4E [SWS_Dem_00703] SWS DEM p. 170.

Sequence diagram: Clearing via selection, permission query, and reinitialization of monitors. Sources: SWS DEM Fig. 9.2 p. 366, [SWS_Dem_00680]

Behavior in the event of an error

The DEM reports development errors to DET, e.g. DEM_E_UNINIT, DEM_E_PARAM_POINTER, or DEM_E_WRONG_CONDITION [SWS_Dem_00173] SWS DEM p. 238. Calls prior to initialization generate DEM_E_UNINIT; excluded from this are, among others, Dem_SetEventStatus and Dem_ResetEventStatus [SWS_Dem_00124]. The same applies after shutdown [SWS_Dem_00368].

At runtime, the APIs return the following return values:

  • E_NOT_OK without prior selection or without a set filter ([SWS_Dem_01299], [SWS_Dem_01300]),
  • DEM_WRONG_DTC or DEM_WRONG_DTCORIGIN for an unknown DTC or origin ([SWS_Dem_01261], [SWS_Dem_01262]),
  • DEM_BUSY for concurrent operations by the same client ([SWS_Dem_01306], SWS DEM p. 259).
[SWS_Dem_01202] defines under which conditions a clearing process is considered failed.

The DEM initializes data that NvM cannot read [SWS_Dem_00578]. It ignores write errors [SWS_Dem_00579]. Prestore data whose layout no longer fits after reprogramming is skipped [SWS_Dem_01323].

Sets the DTC Filter. The server shall perform a bit-wise logical AND-ing operation between the parameter DTCStatusMask and the current UDS status in the server.
