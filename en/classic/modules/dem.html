Role of the DEM in the Diagnostic Stack

The Diagnostic Event Manager collects all diagnostic events of an ECU. There is exactly one DEM module per ECU [SWS_Dem_00126]. Each event is represented by a unique EventId and an associated name [SWS_Dem_00153]. In type Dem_EventIdType, the value 0 is not permitted [SWS_Dem_00925]. On the input side, SW-Cs and BSW modules report their test results via Dem_SetEventStatus [SWS_Dem_00183]. On the output side, the DCM uses the DEM to read and clear fault codes, status, and associated data SWS DCM p. 103.

Further partners of the DEM:

  • The NvM handles persistent storage [SWS_Dem_00164] [SWS_Dem_00329].
  • The FiM is informed of status changes [SWS_Dem_00029] [SWS_Dem_01132].
  • Monitors are reinitialized via InitMonitorForEvent, each with a reason from Dem_InitMonitorReasonType [SWS_Dem_00003] [SWS_Dem_00942].
  • J1939 support is available when DemGeneralJ1939 is configured [SWS_Dem_00845].

Context diagram: The DEM connects reporting monitors with DCM, J1939Dcm, FiM, and NvM. Sources: [SWS_Dem_00183], [SWS_Dem_00003], [SWS_Dem_01253], [SWS_Dem_00845], [SWS_Dem_01131], [SWS_Dem_00164], SWS FiM p. 29, [SWS_Dem_00029]

Startup, Operation, and Shutdown

The DEM distinguishes between a pre-initialized mode and fully initialized operation [SWS_Dem_00169].

  • Dem_PreInit initializes the internal states required for event processing [SWS_Dem_00180]. This includes the DEM-internal debouncing [SWS_Dem_01213].
  • From this point on, debounced reports are possible [SWS_Dem_01212].
  • Reports that arrive before Dem_Init are buffered by the DEM in a queue [SWS_Dem_00167]. Its size is configurable [SWS_Dem_00207] [SWS_Dem_01079].
  • These early reports do not trigger monitor status callbacks [SWS_Dem_01289] SWS DEM p. 169.

Dem_Init receives a pointer to Dem_ConfigType and initializes or reinitializes the module [SWS_Dem_00181] [SWS_Dem_00924].

  • Only then is the monitor status initialized. Prior to that, Dem_GetMonitorStatus returns the value E_NOT_OK [SWS_Dem_01326].
  • After Dem_Init, the DEM is fully operational [SWS_Dem_00340].
  • A previously requested restart of an operation cycle is only processed afterward [SWS_Dem_01318].
  • All non-event-driven tasks are performed by Dem_MainFunction [SWS_Dem_00125] [SWS_Dem_00266].
  • Dem_Shutdown completes open operations [SWS_Dem_00102]. Modified non-volatile data is triggered to NVRAM at the latest during shutdown [SWS_Dem_00341].

State diagram: The lifecycle proceeds from "uninitialized" via "pre-initialized" to operation and ends with shutdown. Sources: [SWS_Dem_00169], [SWS_Dem_00180], [SWS_Dem_00340], [SWS_Dem_00102], [SWS_Dem_00124], [SWS_Dem_00368], [SWS_Dem_00167], [SWS_Dem_01212], [SWS_Dem_00181], [SWS_Dem_00125]

Sequence diagram: Reports between Dem_PreInit and Dem_Init are buffered. Dem_Init initializes the monitor status, Dem_Shutdown saves modified data. From Monitor Result to Qualified Event

Dem_SetEventStatus transmits values from Dem_EventStatusType [SWS_Dem_00926]:

  • DEM_EVENT_STATUS_PASSED and DEM_EVENT_STATUS_FAILED are already qualified results.
  • …_PREPASSED and …_PREFAILED are preliminary results that the DEM debounces internally SWS DEM p. 351.

The debouncing algorithm is configured per event [SWS_Dem_00413]. The choices are counter-based [SWS_Dem_00414], time-based [SWS_Dem_00426], or monitor-internal [SWS_Dem_00437].

Counter-based debouncing:

  • Preliminary results increase or decrease the internal counter by the configured step size [SWS_Dem_00418] [SWS_Dem_00419].
  • Qualified results set the counter directly [SWS_Dem_00420] [SWS_Dem_00421].
  • Threshold values define the failed or passed state [SWS_Dem_00416] [SWS_Dem_00417].
  • A jump behavior is optionally configurable [SWS_Dem_00422] [SWS_Dem_00424].
  • The counter is mapped linearly to the Fault Detection Counter (−128…+127) [SWS_Dem_00415] SWS DEM p. 108.

With time-based debouncing, a preliminary result starts a timer [SWS_Dem_00428] [SWS_Dem_00432].

Activity diagram: In counter-based debouncing, the reported status determines the counter change; reaching a threshold qualifies the event. Sources: [SWS_Dem_00415]–[SWS_Dem_00421], SWS DEM p. 108, [SWS_Dem_00414], [SWS_Dem_00424], [SWS_Dem_00422]

Processing is divided into two parts:

  • Counter-based debouncing [SWS_Dem_01279] and bits 0 and 1 of the monitor status [SWS_Dem_01280] run synchronously in the context of the caller.
  • In contrast, the DEM calculates the UDS status asynchronously [SWS_Dem_01285].

Enable and storage conditions:

  • Enable conditions are checked per event [SWS_Dem_00447] and set via Dem_SetEnableCondition [SWS_Dem_00201].
  • As long as an enable condition is not fulfilled, reports are not accepted [SWS_Dem_00449] DEXT p. 198. Depending on DemDebounceBehavior, debouncing is then reset or frozen [SWS_Dem_00654] [SWS_Dem_00655].
  • Storage conditions, on the other hand, only control whether the event is stored in memory [SWS_Dem_00459] [SWS_Dem_00556].

Further interventions in event processing:

  • Dem_ResetEventDebounceStatus resets the debouncing or freezes it [SWS_Dem_00684] [SWS_Dem_00685]. The qualification of the event remains unaffected by this SWS DEM p. 267.
  • Dem_ResetEventStatus resets TestFailed asynchronously [SWS_Dem_00187].

Sequence diagram: Enable check, debouncing, and monitor status run synchronously; UDS status and callbacks run asynchronously. Sources: [SWS_Dem_00449], [SWS_Dem_01279], [SWS_Dem_01280], [SWS_Dem_01285], [SWS_Dem_00016], SWS DEM p. 85

Event Memory, Status Byte, and Operation Cycles

By default, the DEM maintains all UDS status bits [SWS_Dem_00006]. Each bit transition is individually defined, such as for TestFailed [SWS_Dem_00386], ConfirmedDTC [SWS_Dem_00391], and WarningIndicatorRequested [SWS_Dem_00395] SWS DEM p. 88.

Structure of the event memory:

  • There is a primary memory [SWS_Dem_00010] and optionally user-defined memories [SWS_Dem_00548].
  • These are organized into event memory sets [SWS_Dem_01247].
  • The trigger for creating an entry is configurable [SWS_Dem_00783]–[SWS_Dem_00786] SWS DEM p. 94.

When the memory is full:

  • The DEM sets an overflow indication [SWS_Dem_00397] that is readable via Dem_GetEventMemoryOverflow [SWS_Dem_00559].
  • It searches for a candidate according to the displacement strategy [SWS_Dem_00400] [SWS_Dem_00401].
  • If there is no candidate, it discards the memory request [SWS_Dem_00407].

Freeze Frames and Extended Data Records are captured depending on the configured trigger [SWS_Dem_00799]–[SWS_Dem_00802] [SWS_Dem_00809]. A pre-stored Freeze Frame takes precedence in this process [SWS_Dem_00464].

Activity diagram: Event storage proceeds via storage condition, free entry, overflow, and displacement. Sources: [SWS_Dem_00459], [SWS_Dem_00397], [SWS_Dem_00406]–[SWS_Dem_00409], SWS DEM p. 94, [SWS_Dem_00783], [SWS_Dem_00786], [SWS_Dem_00401], [SWS_Dem_00809]

Aging:

  • Each entry has an aging counter [SWS_Dem_00019].
  • Aging begins after healing is completed [SWS_Dem_00698] SWS DEM p. 133.
  • Once the threshold is reached, ConfirmedDTC is reset [SWS_Dem_00498] and the event data is removed [SWS_Dem_01075].

Operation cycles:

  • Dem_RestartOperationCycle operates asynchronously and reinitializes the affected monitors [SWS_Dem_00194] [SWS_Dem_00679].
  • There is no queue for restarts [SWS_Dem_01316].
  • Dependent cycles are qualified with Dem_SetCycleQualified [SWS_Dem_01221] [SWS_Dem_91001].

Diagnostic Memory Access According to the Principle of "Select and Query"

Many DCM services operate according to the same pattern: a client first selects a DTC or a DTC group and then calls functions that operate on this selection SWS DEM p. 215.

  • Dem_SelectDTC defines the target for Dem_ClearDTC, Dem_GetStatusOfDTC, and Dem_SelectFreezeFrameData, among others [SWS_Dem_91016] [SWS_Dem_01253].
  • The selection refers to the event memory that is assigned to the ClientId [SWS_Dem_01254].
  • Clients with different ClientId may work in parallel [SWS_Dem_01251].
  • If the same client calls Dem_SelectDTC again while the previous operation is still running, it receives DEM_BUSY [SWS_Dem_01306].

Reading Freeze Frames and Extended Data:

  • Dem_SelectFreezeFrameData and Dem_SelectExtendedDataRecord build upon the DTC selection [SWS_Dem_01268] [SWS_Dem_01272].
  • Subsequently, size and next functions provide the data [SWS_Dem_00074] [SWS_Dem_00071] [SWS_Dem_00075]. A Freeze Frame has the format {RecordNumber, NumOfDIDs, DID, data…} SWS DEM p. 225.
  • If a valid but unstored record is requested, the DEM returns E_OK with an empty buffer [SWS_Dem_00630].
  • To keep the data consistent, the DCM locks the update during reading with Dem_DisableDTCRecordUpdate and clears the lock with Dem_EnableDTCRecordUpdate again [SWS_Dem_00270] [SWS_Dem_00271].

Sequence diagram: Freeze frames are selected and read while updates are locked; DEM_PENDING leads to repeated calls. Sources: [SWS_Dem_01253], [SWS_Dem_01268], [SWS_Dem_00238], [SWS_Dem_00236], [SWS_Dem_00270], SWS DEM p. 290, [SWS_Dem_00071], [SWS_Dem_00271]

Filter functions:

  • Dem_SetDTCFilter sets the filter criteria for subsequent queries [SWS_Dem_00057]. Each call restarts the iteration [SWS_Dem_00649].
  • After that, Dem_GetNumberOfFilteredDTC and Dem_GetNextFilteredDTC provide the matches [SWS_Dem_00061] [SWS_Dem_00216].
  • In OBD format, Dem_GetNextFilteredDTC does not return DEM_PENDING [SWS_Dem_00653].

Clearing and DTC setting:

  • Dem_ClearDTC optionally queries DemClearEventAllowed [SWS_Dem_00665] [SWS_Dem_00515] and reinitializes the affected monitors [SWS_Dem_00680].
  • Dem_DisableDTCSetting prevents the storage of the affected events [SWS_Dem_00079] [SWS_Dem_00626].

Configuration-dependent functional blocks: OBD, J1939, components

OBD:

  • OBD APIs are only available if DemOBDSupport is not equal to DEM_OBD_NO_OBD_SUPPORT SWS DEM p. 315.
  • The master ECU calculates PID $31/$4D/$4E vehicle-wide [SWS_Dem_00703] and is the only one to report them to the scan tool [SWS_Dem_00704].
  • Primary ECUs receive the values via a SW-C that calls Dem_SetDataOfPID… [SWS_Dem_00735] [SWS_Dem_00736] SWS DEM p. 170.
  • The status of the IUMPR denominator conditions is transmitted between ECUs [SWS_Dem_00714] [SWS_Dem_00716].
  • The application reports test results (DTR) via Dem_SetDTR [SWS_Dem_00756].

Collaboration diagram: The PID values are calculated centrally in the master ECU and distributed to the primary ECUs. Sources: [SWS_Dem_00703], [SWS_Dem_00704], [SWS_Dem_00735], SWS DEM p. 170, [SWS_Dem_00736]

J1939: For the J1939Dcm, there are separate functions for filtering with combined lamp status [SWS_Dem_00855] [SWS_Dem_00857] and for clearing [SWS_Dem_00878].

Components (DemComponent):

  • Each component has a FAILED status and can have directed dependencies on other components [SWS_Dem_01118] [SWS_Dem_01119] [SWS_Dem_01120].
  • If a component fails, the dependent components are also considered failed [SWS_Dem_01124].
  • The FiM queries this status via Dem_GetComponentFailed [SWS_Dem_01131].
  • Unavailable components are treated as if they did not exist in the system [SWS_Dem_01134]. After startup, all components are available [SWS_Dem_01239].

Availability and suppression:

  • With Dem_SetEventAvailable, events can be suppressed at runtime [SWS_Dem_01080] [SWS_Dem_01108]. In VARIANT-POST-BUILD, this function is not available [SWS_Dem_01106].
  • A suppressed DTC is invisible to the tester [SWS_Dem_01100], but continues to be processed internally [SWS_Dem_01102].

Behavior in the event of an error

Development errors (DET) are defined in [SWS_Dem_00173], including DEM_E_PARAM_POINTER, DEM_E_UNINIT, and DEM_E_WRONG_CONDITION SWS DEM p. 238.

  • Calls before full initialization report DEM_E_UNINIT [SWS_Dem_00124]. A separate rule applies to Dem_SetEventStatus and Dem_ResetEventDebounceStatus [SWS_Dem_00364].
  • Calls after shutdown are also detected [SWS_Dem_00368].
  • Missing preconditions report DEM_E_WRONG_CONDITION [SWS_Dem_00518].

Return values in runtime operation:

  • Invalid selections result in DEM_WRONG_DTC or DEM_WRONG_DTCORIGIN [SWS_Dem_01261] [SWS_Dem_01262].
  • If selection or filter is missing, the DEM returns E_NOT_OK [SWS_Dem_01299] [SWS_Dem_01300].
  • In case of DEM_PENDING, the caller must request again later SWS DEM p. 289.

Rejections on the event side:

  • Dem_ResetEventStatus rejects if the event has already been tested in the current cycle [SWS_Dem_00638].
  • Dem_PrestoreFreezeFrame rejects if no memory is free [SWS_Dem_00808].
  • When DTC setting is disabled, the WIR bit remains unchanged [SWS_Dem_00836].
  • BSW modules may ignore the return value of Dem_SetEventStatus SWS DEM p. 273.

Persistence errors:

  • The DEM checks the validity and integrity of the NvM data [SWS_Dem_00339].
  • In case of read errors, it reinitializes the affected data [SWS_Dem_00578]. The handling of write errors is governed by [SWS_Dem_00579].
  • Inconsistent prestored data is skipped [SWS_Dem_01323].

Std_ReturnType Dem_ClearDTC (uint8 ClientId);

Clears single DTCs, as well as groups of DTCs.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: a9cf3c094bb1 Provenance

Usage and Flow

The function Dem_ClearDTC asynchronously clears individual DTCs as well as configured DTC groups [SWS_Dem_00665]. The caller is identified via the parameter ClientId [SWS_Dem_00665]. Prior to the call, the DTC to be cleared or the group, including DTCOrigin and DTCFormat, must have been selected via Dem_SelectDTC [SWS_Dem_01253]. As long as the clearing process is in progress, the API returns DEM_PENDING, which requires a new call at a later time; E_OK is returned only after successful completion [SWS_Dem_00665].

Error Handling and Return Values

If an error occurs, specific return values are available [SWS_Dem_00665]:

  • E_NOT_OK: No DTC was selected beforehand [SWS_Dem_00665].
  • DEM_WRONG_DTC: The DTC does not exist in the selected format [SWS_Dem_00665], the selected DTC is suppressed [SWS_Dem_01100], or clearing is restricted to DEM_ONLY_CLEAR_ALL_DTCS by DemClearDTCLimitation while another group was selected [SWS_Dem_00670].
  • DEM_WRONG_DTCORIGIN: The specified memory location does not exist [SWS_Dem_00665].
  • DEM_CLEAR_FAILED or DEM_CLEAR_MEMORY_ERROR: Clearing failed or an error occurred while clearing NVRAM blocks [SWS_Dem_00665].
  • DEM_CLEAR_BUSY: Another client is already performing a clear operation [SWS_Dem_00665].
  • DEM_BUSY: Another operation dependent on Dem_SelectDTC is already running for the same client [SWS_Dem_00665].

Concurrency and Interaction

Dem_ClearDTC is reentrant for different ClientId values, but not reentrant for the same ClientId [SWS_Dem_00665]. The DEM processes parallel calls from multiple clients internally [SWS_Dem_00661]; if a clear operation is already in progress, a requesting client receives DEM_PENDING [SWS_Dem_00664].

When a combined DTC is cleared, the DEM purges all associated events [SWS_Dem_00440]. In doing so, the module triggers the callback InitMonitorForEvent with the reason DEM_INIT_MONITOR_CLEAR for affected events [SWS_Dem_00680]. If DemTriggerMonitorInitBeforeClearOk is configured to TRUE, E_OK is not returned until this initialization has been initiated [SWS_Dem_00573]. In addition, the memory overflow indicator is reset as soon as all DTCs contained therein are cleared [SWS_Dem_00399].
