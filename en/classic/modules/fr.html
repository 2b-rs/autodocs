Serves the FlexRay Interface as unified access to FlexRay controllers: start, halt, wakeup, transmission, reception.

The FlexRay driver encapsulates FlexRay communication controllers. Except for initialization by the EcuM, it is used exclusively by the FlexRay Interface Fr-SWS p. 15. It controls the POC state machine of the controller: initialization, start, wakeup, deferred halt, and immediate cancellation. It transmits data via configured LPDUs, checks the transmission status, and receives; this is supplemented by global time and absolute timers. Many services require a specific POC state or synchronicity with global time; otherwise, Fr reports the runtime error FR_E_INV_POCSTATE [SWS_Fr_91004].

The FlexRay driver encapsulates one or more FlexRay communication controllers (CC). Its only user is the FlexRay Interface; only initialization via Fr_Init is handled by the EcuM Fr-SWS p. 15. Each service addresses the controller via Fr_CtrlIdx, such as Fr_ControllerInit [SWS_Fr_00017]. The configuration is split into two parts: cluster parameters and LPDU assignments reside with the FrIf, while controller-related parameters reside with the Fr Fr-SWS p. 25.

At its core, Fr controls the POC state machine of the CC. Only five services are permitted to change the state Fr-SWS p. 23:

  • Fr_ControllerInit transitions the CC via POC:config to POC:ready.
  • Fr_StartCommunication starts the startup asynchronously [SWS_Fr_00010].
  • Fr_SendWUP transmits a wakeup pattern.
  • Fr_HaltCommunication halts at cycle end.
  • Fr_AbortCommunication aborts immediately [SWS_Fr_00011].

After Fr_StartCommunication, POC:normal active or normal passive is not guaranteed. Interpretation: The caller is therefore likely to track progress via Fr_GetPOCStatus.

Role in the FlexRay Stack: Controller Access for FrIf and EcuM

The FlexRay driver (Fr) encapsulates one or more FlexRay communication controllers (CC). Its only user is the FlexRay Interface (FrIf). An exception is the initialization via Fr_Init, which is called by the EcuM Fr-SWS p. 15. All other services address the controller via Fr_CtrlIdx, such as Fr_ControllerInit [SWS_Fr_00017]. Resources shared by the CC with other components (e.g., PLL configuration or memory mapping) are not configured by Fr itself. Their initialization must precede that of Fr Fr-SWS p. 15.

For data consistency, Fr uses the BSW Scheduler with SchM_Enter_Fr and SchM_Exit_Fr; optionally, it reports development errors via Det_ReportError [SWS_Fr_00391]. In addition, the specification lists Dem_SetEventStatus and Det_ReportRuntimeError as interfaces [SWS_Fr_00390]. From the perspective of the FrIf, POC control, data path, and absolute timers are mandatory interfaces FrIf-SWS p. 95. In contrast, services such as Fr_AllSlots, Fr_CancelTxLPdu, or Fr_GetNmVector are used only optionally by the FrIf FrIf-SWS p. 97.

POC Control: From Fr_Init to Synchronous Communication

Each CC executes the state machine of the Protocol Operation Control (POC). Its transitions are triggered partly by hardware events and partly by host CHI commands Fr-SWS p. 23. Only Fr_StartCommunication, Fr_HaltCommunication, Fr_AbortCommunication, Fr_SendWUP, and Fr_ControllerInit are allowed to change the POC state. The states are mapped by Fr_POCStateType [SWS_Fr_00505].

Fr_Init only stores the configuration address for subsequent calls and imposes no precondition on the CC Fr-SWS p. 39. Fr_ControllerInit transitions the CC from any state to POC:config and loads the cluster and node parameters as well as the buffers. Afterwards, the function leaves the CC in POC:ready without pending transmission requests Fr-SWS p. 41. Fr_StartCommunication starts startup asynchronously using the CHI command RUN [SWS_Fr_00010]. That the CC subsequently reaches POC:normal active or normal passive is not guaranteed Fr-SWS p. 42. Interpretation: The caller is therefore likely to track progress via Fr_GetPOCStatus, which provides the status as Fr_POCStatusType [SWS_Fr_00510]. Fr_AllowColdstart is permissible in POC:ready or POC:startup [SWS_Fr_00114]. Fr_AllSlots requires synchronicity with global time and switches from key-slot operation to all-slots operation starting with the next cycle Fr-SWS p. 44.

There are two ways to terminate. Fr_HaltCommunication issues DEFERRED_HALT; POC:halt is reached only at the end of the running cycle Fr-SWS p. 45. In contrast, Fr_AbortCommunication aborts synchronously with FREEZE and transitions to POC:halt from any state [SWS_Fr_00011], Fr-SWS p. 47.

Wakeup via a Selected Channel

Fr_SetWakeupChannel selects FR_CHANNEL_A or FR_CHANNEL_B as the wakeup channel [SWS_Fr_00091]. For this purpose, the CC transitions briefly to POC:config using the CHI command CONFIG and returns to POC:ready with CONFIG_COMPLETE Fr-SWS p. 49. Fr_SendWUP is permitted only in POC:ready and initiates the transmission of the wakeup pattern with WAKEUP. The CC traverses POC:wakeup and then returns to POC:ready. A transmitted pattern does not guarantee that all nodes in the cluster will wake up Fr-SWS p. 48.

The result is indicated by Fr_WakeupStatusType in the POC status, for example as FR_WAKEUP_TRANSMITTED, FR_WAKEUP_RECEIVED_WUP, or as a collision case [SWS_Fr_00508]. These values are evaluated by the FlexRay State Manager FrSM-SWS p. 19. In addition, Fr_GetWakeupRxStatus reports bit-coded whether a wakeup pattern was received on channel A (bit 0) or channel B (bit 1) [SWS_Fr_00587].

L-PDU Data Path: Transmission, Confirmation, Reception

Data flows as LSDU via LPDUs configured in the FrIf and uniquely designated via Fr_LPduIdx. Fr_TransmitTxLPdu passes buffer and length asynchronously to the transmission resource [SWS_Fr_00092]. Via Fr_SlotAssignmentPtr, the caller receives cycle, slot ID, and channel (Fr_SlotAssignmentType, [SWS_Fr_91002]); if it passes NULL_PTR, this information is omitted Fr-SWS p. 53. The FrIf calls Fr_TransmitTxLPdu directly from FrIf_Transmit and increments the TxConfCounter of the PDU upon E_OK FrIf-SWS p. 106.

In its job list, the FrIf queries Fr_CheckTxLPduStatus [SWS_Fr_00094]. Possible outcomes are FR_TRANSMITTED, FR_TRANSMITTED_CONFLICT, and FR_NOT_TRANSMITTED [SWS_Fr_00511]. Only upon FR_TRANSMITTED do TxConfirmations to upper layers follow FrIf-SWS p. 38. Fr_CancelTxLPdu terminates a pending transmission request and returns E_OK; if none is pending, it returns E_NOT_OK Fr-SWS p. 54.

Fr_ReceiveRxLPdu synchronously copies payload data, length, and the status Fr_RxLPduStatusType into the buffers of the caller [SWS_Fr_00093]. The value FR_RECEIVED_MORE_DATA_AVAILABLE indicates further instances in a receive FIFO [SWS_Fr_00512]. Fr uses the hardware FIFO if the configured filter criteria apply to it. Each call then retrieves the first valid frame; a dedicated FIFO API does not exist Fr-SWS p. 22. LPDU resources can be reconfigured at runtime. Fr_PrepareLPdu configures the assigned resource (slot ID, cycle filter, length, header CRC), provided the configuration generator uses reconfiguration. The function can be disabled via FrPrepareLPduSupport Fr-SWS p. 61. Fr_ReconfigLPdu resets frame ID, channel, cycle filter, payload length, and header CRC [SWS_Fr_00524]. It does not recalculate the CRC, but merely checks whether it lies within the range 0–2047. Fr_DisableLPdu removes a resource from transmission and reception operation, but only for dynamically reconfigurable LPDUs Fr-SWS p. 65.

Global Time, Status Values, and Absolute Timers

Several queries require synchronicity with the global FlexRay time. Fr_GetGlobalTime returns cycle and macrotick consistently and may be called within an Exclusive Area Fr-SWS p. 67. Behavior in the event of an error

Functions with Std_ReturnType return E_OK or E_NOT_OK. Upon E_NOT_OK, the output parameters remain unchanged Fr-SWS p. 36. If a function detects a hardware error of the controller, it invokes Dem_SetEventStatus(FR_E_CTRL_TESTRESULT, DEM_EVENT_STATUS_FAILED) and returns E_NOT_OK Fr-SWS p. 43.
