Role in the FlexRay stack and system boundary

The FlexRay driver (Fr) provides unified access to one or more FlexRay Communication Controllers (CC). Its only user is the FlexRay Interface (FrIf). The only exception is initialization: EcuM calls Fr_Init SWS FrDriver p. 15. All services except Fr_Init and Fr_GetVersionInfo address the controller via Fr_CtrlIdx, the "Index of FlexRay CC within the context of the FlexRay Driver" ([SWS_Fr_00017], [SWS_Fr_00032], [SWS_Fr_00070]).

Downwards, Fr accesses the CC hardware. Outwards, the module mandatorily requires Dem_SetEventStatus and Det_ReportRuntimeError [SWS_Fr_00390]. Optionally, it uses Det_ReportError as well as SchM_Enter_Fr/SchM_Exit_Fr [SWS_Fr_00391]. The CC shares some resources with other components, such as PLL or memory mapping. Fr does not configure these itself; their initialization must occur before that of Fr SWS FrDriver p. 15.

FrIf distinguishes between mandatory and optional services among the Fr services:

  • Mandatory services include, among others, Fr_ControllerInit, Fr_GetPOCStatus, Fr_ReceiveRxLPdu, Fr_CheckTxLPduStatus, and the absolute timer services SWS FrIf p. 95.
  • Optional services include, among others, Fr_AllSlots, Fr_CancelTxLPdu, and the diagnostic services SWS FrIf p. 97.

Many FrIf functions directly encapsulate an Fr service. Thus, FrIf_GetPOCStatus wraps the function Fr_GetPOCStatus SWS FrIf p. 67.

POC state machine: which service triggers which transition

A FlexRay CC internally executes the Protocol Operation Control (POC) state machine. Its transitions are caused by hardware events and by CHI commands from the host. Only five services trigger such commands: Fr_StartCommunication, Fr_HaltCommunication, Fr_AbortCommunication, Fr_SendWUP, and Fr_ControllerInit. All other services must not change the POC state SWS FrDriver p. 23. The states are mapped by Fr_POCStateType [SWS_Fr_00505]. The individual transitions:

  • Fr_ControllerInit transitions from any state to POC:config, configures cluster, node, and buffer parameters, and ends in POC:ready SWS FrDriver p. 41.
  • Fr_StartCommunication sends the command RUN and transitions to the POC:startup transitional state. Whether the CC reaches normal active or normal passive afterwards is not guaranteed SWS FrDriver p. 42.
  • Fr_SendWUP leads via POC:wakeup and subsequently back to POC:ready SWS FrDriver p. 48.
  • Fr_HaltCommunication sends DEFERRED_HALT; POC:halt is reached only at the end of the current cycle SWS FrDriver p. 45.
  • Fr_AbortCommunication sends FREEZE and transitions immediately and from any state to POC:halt; in doing so, vPOC!Freeze is set SWS FrDriver p. 47.

A special case is Fr_SetWakeupChannel. The function transitions briefly to POC:config with CONFIG and back to POC:ready with CONFIG_COMPLETE [SWS_Fr_00091], SWS FrDriver p. 49. It is missing from the list of state-changing services. In net terms, the CC remains in POC:ready, but the intermediate step must be observed.

Fr_GetPOCStatus reads the CHI variable vPOC and has no CC precondition SWS FrDriver p. 51. The result is a Fr_POCStatusType with the following fields [SWS_Fr_00510]:

  • State;
  • ErrorMode with the values FR_ERRORMODE_ACTIVE, FR_ERRORMODE_PASSIVE, and FR_ERRORMODE_COMM_HALT [SWS_Fr_00507];
  • SlotMode [SWS_Fr_00506];
  • StartupState [SWS_Fr_00509];
  • WakeupStatus [SWS_Fr_00508];
  • the flags Freeze, CHIHaltRequest, CHIReadyRequest, and ColdstartNoise.

State diagram: POC transitions triggered by Fr services, as well as implicit transitions of the CC. Sources: SWS FrDriver p. 23, [SWS_Fr_00505], [SWS_Fr_00010], [SWS_Fr_00011], [SWS_Fr_00009]

From Fr_Init to Communication in All Slots

Fr_Init is synchronous and non-reentrant [SWS_Fr_00032]. The function stores the configuration address for all subsequent calls SWS FrDriver p. 39. In R20-11, Fr_ConfigType is an implementation-specific post-build type, “derived from void” [SWS_Fr_91001]. Later document versions describe it as a structure SWS FrDriver p. 34. The change history locates this change in R22-11 SWS FrDriver p. 1. For R20-11, the requirement text applies.

Afterwards, Fr_ControllerInit brings each CC to POC:ready and ensures that no more transmission requests are pending SWS FrDriver p. 41. For a wakeup, Fr_SetWakeupChannel selects the channel; only FR_CHANNEL_A and FR_CHANNEL_B are valid [SWS_Fr_00091]. Subsequently, Fr_SendWUP sends the wakeup pattern in POC:ready. This does not necessarily wake all nodes SWS FrDriver p. 48. Retries are handled by FrSM: it waits for FR_READY and evaluates vPOC!WakeupStatus, such as FR_WAKEUP_RECEIVED_HEADER or FR_WAKEUP_TRANSMITTED SWS FrSM p. 27. Fr_GetWakeupRxStatus reports a received wakeup bit-coded per channel [SWS_Fr_00587].

To start, Fr_AllowColdstart is called (permitted in POC:ready or POC:startup) and then Fr_StartCommunication SWS FrDriver p. 43, [SWS_Fr_00010]. Both services are asynchronous. The caller is therefore expected to observe success via repeated Fr_GetPOCStatus (interpretation). The sequence is presumably controlled by FrSM via FrIf; its states are mapped to POC states SWS FrSM p. 18. As soon as the CC is synchronous to the global time, Fr_AllSlots requests the change from keyslot-only mode to all-slots mode for the next cycle SWS FrDriver p. 44. Until then, SlotMode indicates the value FR_SLOTMODE_ALL_PENDING [SWS_Fr_00506].

LPdu Data Path: Transmit, Confirm, Cancel, Receive

All parameters for transmission and reception are located in the FrIf configuration (FrIfLPdu, FrIfFrameTriggering). FrIf merely passes the Fr_LPduIdx to Fr SWS FrDriver p. 25. Fr_TransmitTxLPdu is asynchronous and receives the buffer pointer and length of the LSdu [SWS_Fr_00092]. Via Fr_SlotAssignmentPtr, the caller can query cycle, slot ID, and channel (Fr_SlotAssignmentType); an NULL_PTR dispenses with this [SWS_Fr_91002], SWS FrDriver p. 53.

The confirmation originates in the FrIf job list. There, the TX_CONFIRMATION operation calls Fr_CheckTxLPduStatus SWS FrIf p. 38. The return status is FR_TRANSMITTED, FR_TRANSMITTED_CONFLICT, or FR_NOT_TRANSMITTED [SWS_Fr_00511]. Only upon FR_TRANSMITTED does FrIf confirm the contained PDUs SWS FrIf p. 112. Fr_CancelTxLPdu cancels a pending transmission in the hardware buffer and returns E_OK. If nothing is pending, the function returns E_NOT_OK SWS FrDriver p. 54.

Sequence diagram: Transmission request with direct buffer access and subsequent confirmation in the job list. Sources: SWS FrIf p. 106, SWS FrIf p. 112, [SWS_Fr_00094]

Fr_ReceiveRxLPdu is synchronous. The function writes the LSdu, the status (Fr_RxLPduStatusType), and the length [SWS_Fr_00093], [SWS_Fr_00512]. FrIf uses it in two ways:

  • RECEIVE_AND_STORE calls it once and stores the PDUs in FrIf buffers SWS FrIf p. 39.
  • RECEIVE_AND_INDICATE calls it repeatedly until FR_NOT_RECEIVED is returned or FrIfRxComOpMaxLoop is reached SWS FrIf p. 41.

If the filter criteria match a hardware receive FIFO, Fr assigns the LPdus to it. A call then retrieves the first valid frame; a dedicated FIFO API does not exist SWS FrDriver p. 22. FR_RECEIVED_MORE_DATA_AVAILABLE signals further entries [SWS_Fr_00512].

Global Time, Absolute Timers, and Cluster Diagnosis

Fr_GetGlobalTime returns cycle and macrotick. The function may only be called when the CC is synchronous, and is also permitted within an exclusive area [SWS_Fr_00042]. Time values must be consistent and valid SWS FrDriver p. 67. For data consistency, Fr uses the mechanisms of the BSW scheduler SWS FrDriver p. 15.

Absolute timers are addressed per CC via Fr_AbsTimerIdx SWS FrDriver p. 104. Overview of the services:

  • Fr_SetAbsoluteTimer programs cycle and offset in macroticks; the CC must be synchronous at this time SWS FrDriver p. 79.
  • Fr_EnableAbsoluteTimerIRQ and Fr_DisableAbsoluteTimerIRQ switch the interrupt line ([SWS_Fr_00034], [SWS_Fr_00035]).
  • Fr_GetAbsoluteTimerIRQStatus reports TRUE when an interrupt is pending [SWS_Fr_00108].
  • Fr_AckAbsoluteTimerIRQ resets the interrupt condition [SWS_Fr_00036].
  • Fr_CancelAbsoluteTimer stops the timer [SWS_Fr_00095].

Sequence diagram: Lifecycle of an absolute timer from programming to stopping. Sources: [SWS_Fr_00033], [SWS_Fr_00034], [SWS_Fr_00108], [SWS_Fr_00036], [SWS_Fr_00095]

The following services are available for cluster diagnosis; most require a synchronous CC:

  • Fr_GetChannelStatus provides a bit-coded status per channel with aggregated channel, NIT, and symbol window status SWS FrDriver p. 71.
  • Fr_GetClockCorrection provides rate and offset correction [SWS_Fr_00564].
  • Fr_GetSyncFrameList provides sync frame lists per channel and even/odd cycles [SWS_Fr_00573].
  • Fr_GetNumOfStartupFrames provides the startup frame pairs of the previous double cycle SWS FrDriver p. 65.
  • Fr_GetNmVector must not be called at the update time of the NM vector SWS FrDriver p. 68.

Configuration, Indexing, and Reconfiguration at Runtime

The configuration tool of the driver reads the configurations of Fr and FrIf. Cluster parameters are located in FrIf, CC parameters in Fr SWS FrDriver p. 25. The container FrController contains, among others, FrCtrlIdx, FrPKeySlotId, and FrPKeySlotUsedForStartup. This representation originates from R25-11 SWS FrDriver p. 98. Fr_ReadCCConfig reads individual protocol parameters via the macros FR_CIDX_<…> [SWS_Fr_00651]. If there are multiple FlexRay drivers in the system, Fr_GeneralTypes.h may occur only once SWS FrDriver p. 32.

Context diagram: Indexing via drivers, controllers, timers, LPdus, and channels. Sources: SWS FrDriver p. 20, SWS FrDriver p. 25, [SWS_Fr_00514]

There are three tools for runtime:

  • Fr_PrepareLPdu reconfigures a buffer for an LPdu, provided the configuration tool uses reconfiguration. The function can be disabled via FrPrepareLPduSupport SWS FrDriver p. 61. FrIf calls it via the job list (PREPARE_LPDU) SWS FrIf p. 42.
  • Fr_ReconfigLPdu resets frame ID, channel, cycle filter, payload length, and header CRC [SWS_Fr_00524]. The CRC is checked only for the range 0–2047 [SWS_Fr_00539]. FrIf excludes FR_CHANNEL_AB for this purpose SWS FrIf p. 89.
  • Fr_DisableLPdu removes an LPdu from communication. This applies only to dynamically reconfigurable LPdus SWS FrDriver p. 65.

Behavior in the event of an error

A uniform convention applies to all services: E_OK signifies success with validly written output parameters. In the case of E_NOT_OK, the output parameters remain unchanged SWS FrDriver p. 36.

Hardware error: If a service detects an error in the CC hardware, it calls Dem_SetEventStatus(FR_E_CTRL_TESTRESULT, DEM_EVENT_STATUS_FAILED) and returns E_NOT_OK SWS FrDriver p. 43. A PASS is reported when Fr_ControllerInit has successfully verified the registers SWS FrDriver p. 26. Protocol errors on the network are explicitly not covered by this event SWS FrDriver p. 28.

Protocol errors: For this purpose, FR_E_LPDU_SLOTSTATUS exists per LPdu. It reports syntax, content, and boundary violations in the slot status [SWS_Fr_00600].

Development errors: When error detection is activated, the codes FR_E_INV_CTRL_IDX, FR_E_INV_TIMER_IDX, FR_E_INV_CYCLE, FR_E_INV_LPDU_IDX, FR_E_PARAM_POINTER, and FR_E_INIT_FAILED apply, among others [SWS_Fr_91003]. For calls prior to initialization, FR_E_INIT_FAILED is likely reported (“Fr module was not initialized”). This is an interpretation because the relevant requirement text is truncated in the payload SWS FrDriver p. 51. Two specific cases are documented:

  • Fr_GetSyncFrameList reports error FR_E_INV_FRAMELIST_SIZE when Fr_ListSize > 15 [SWS_Fr_00667].
  • Fr_GetVersionInfo reports error FR_E_PARAM_POINTER upon NULL_PTR SWS FrDriver p. 86.

Runtime error: As the only runtime error, FR_E_INV_POCSTATE is defined (0x09; the CC is not in the expected POC state) [SWS_Fr_91004]. For such notifications, Det_ReportRuntimeError is designated as a mandatory interface [SWS_Fr_00390]. The chapter on error classification was revised in R20-11 SWS FrDriver p. 1.

Recovery: Fr_AbortCommunication stops the CC immediately. Fr_ControllerInit leads from any state, including POC:halt, via POC:config back to POC:ready SWS FrDriver p. 41. If a CC enters HALT due to an error during wakeup, FrSM aborts the wakeup transmission SWS FrSM p. 27.
