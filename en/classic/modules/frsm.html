Role of the FrSM: Mode Converter Between ComM, BswM, and FlexRay Interface

The FlexRay State Manager (FrSM) is the bus state manager for FlexRay. It accepts a communication mode for each FlexRay cluster via FrSM_RequestComMode ([SWS_FrSM_00020]). It converts this mode into control sequences for communication controllers and transceivers, invoking functions of the FlexRay Interface to do so (FrIf_*, [SWS_FrSM_00096]). The state machine diagram describes this purpose as the translation of COMM_NO_COMMUNICATION and COMM_FULL_COMMUNICATION into hardware-oriented sequences (SWS FrSM Fig. 7.1 p. 24).

The FrSM provides feedback in two directions. It reports the achieved bus mode to ComM using ComM_BusSM_ModeIndication, and its internal state to BswM using BswM_FrSM_CurrentState ([SWS_FrSM_00096]). The value reported to BswM has the type FrSM_BswM_StateType ([SWS_FrSM_00199]). At the same time, BswM acts as a requester: for instance, it can switch the FrSM to passive for diagnostic use cases via FrSm_SetEcuPassive() (EXP ModeMgmt p. 36). In key-slot-only mode, it enables full operation (SWS FrSM Fig. 9.10 p. 55).

The EcuM initializes the module with FrSm_Init, passing a pointer to the post-build structure FrSM_ConfigType ([SWS_FrSM_00013], [SWS_FrSM_00198]). Figure 9.1 shows EcuM, FrIf, and FrSM as participants in this phase (SWS FrSM Fig. 9.1 p. 46). Subsequently, the BSW Scheduler calls a dedicated FrSM_MainFunction_<FrSMCluster.ShortName> for each cluster (Service ID 0x80, provided via SchM_FrSm.h, [SWS_FrSM_00118]). Optionally, the FrSM integrates DEM, DET, FrNm_StartupError, and further FrIf services ([SWS_FrSM_00097]). In addition, there is a configurable CDD callback upon loss of synchronization ([SWS_FrSM_00190]).

Context diagram: The FrSM receives requests from EcuM, SchM, ComM, and BswM, controls the hardware exclusively via the FrIf, and reports to ComM, BswM, DEM, DET, FrNm, and an optional CDD. Sources: [SWS_FrSM_00096], [SWS_FrSM_00097], [SWS_FrSM_00118], [SWS_FrSM_00190], SWS FrSM Fig. 9.1 p. 46, EXP ModeMgmt p. 36

Two Concurrent Regions: Controller States per Cluster and ECU Passive Mode

The state machine consists of two concurrent regions (SWS FrSM p. 18, SWS FrSM Fig. 7.1 p. 24):

  • The region [CcCtrl] comprises eight states per cluster.
  • The region [TrcvCtrl] controls reception mode via FRSM_ECU_ACTIVE and FRSM_ECU_PASSIVE.

Table 7.1 assigns a POC state of the FlexRay controller to each cluster state (SWS FrSM p. 18):

FrSM statePOC stateMeaning
FRSM_READYreadyquiescent state after init
FRSM_WAKEUPwake-upFrSM performs wakeup
FRSM_STARTUPstart-upFrSM performs startup
FRSM_HALT_REQnormal active/passiveFrSM shuts down
FRSM_ONLINEnormal activefull communication
FRSM_ONLINE_PASSIVEnormal passiveno data due to clock synchronization errors
FRSM_KEYSLOT_ONLYnormal active, slot mode ≠ AllSlotstransmission only in key slots
FRSM_LOW_NUMBER_OF_COLDSTARTERSnormal activefull communication, synchronization only via sync frames

The states FRSM_ONLINE, FRSM_KEYSLOT_ONLY, FRSM_LOW_NUMBER_OF_COLDSTARTERS, and FRSM_ONLINE_PASSIVE form the FullCom group (SWS FrSM p. 36). A transition takes place when its condition is met in the source state and the event occurs. The FrSM executes the associated actions in the order of the transition table (SWS FrSM p. 24). Variables such as reqComMode or wakeupCounter are merely auxiliary means that make the specification more readable (SWS FrSM p. 18).

FrSm_SetEcuPassive switches the region [TrcvCtrl] for all clusters simultaneously ([SWS_FrSM_00174]). With TRUE it transitions to FRSM_ECU_PASSIVE, with FALSE to FRSM_ECU_ACTIVE. If a cluster is not in FRSM_READY at this time—meaning its transceivers are not in standby—FE_TRCV_NORMAL is executed for this cluster (SWS FrSM p. 40).

State diagram: The region [CcCtrl] guides each cluster from FRSM_READY via wakeup and startup to FullCom, and back via FRSM_HALT_REQ. Independently of this, the region [TrcvCtrl] switches the passive mode. Transitions within FullCom are governed by the transition table; they are not shown here. Sources: SWS FrSM p. 27, SWS FrSM p. 35, [SWS_FrSM_00174], [SWS_FrSM_00209]

From the FullCom Request to Online Operation: Startup and Wakeup

FrSM_RequestComMode operates asynchronously ([SWS_FrSM_00020]). The function stores the requested mode as reqComMode; it is processed in the next run of the MainFunction of the affected cluster (SWS FrSM p. 36). According to [SWS_FrSM_00020], the following applies to R20-11:

  • Parameters NetworkHandle and ComM_Mode,
  • Service ID 0x02,
  • reentrant for different clusters.

In contrast, the passage from later releases specifies Service ID 0x40 and parameters network/mode. For R20-11, the requirement applies (SWS FrSM p. 36).

Without sending a wakeup pattern, the cluster transitions directly from FRSM_READY into startup (SWS FrSM p. 52, SWS FrSM Fig. 9.3 p. 48):

  1. The transceivers are set to FRTRCV_TRCVMODE_NORMAL.
  2. The controllers are started with FrIf_StartCommunication.
  3. For coldstart ECUs (FrSMIsColdstartEcu), FrIf_AllowColdstart enables coldstart.

Timer t1 delays this enable by FrSMDurationT1. If 0, it follows FrIf_StartCommunication immediately (SWS FrSM p. 21).

After that, the MainFunction cyclically queries FrIf_GetPOCStatus (SWS FrSM Fig. 9.5 p. 50, [SWS_FrSM_00096]). If it returns FR_POCSTATE_NORMAL_ACTIVE, then:

  • the FrSM reports the DEM event FRSM_E_CLUSTER_STARTUP as PASSED,
  • it switches the FrIf online with FRIF_GOTO_ONLINE,
  • it informs BswM and ComM.

Sequence diagram: The request is stored and converted into startup actions by the MainFunction. The online transition only follows once the POC status reports normal active. Instead of the figure labels, the R20-11 values of FrSM_BswM_StateType are used. Sources: SWS FrSM Fig. 9.3 p. 48, SWS FrSM p. 52, SWS FrSM Fig. 9.7 p. 52, [SWS_FrSM_00020], [SWS_FrSM_00199]

If the ECU must wake up the cluster first, it goes through FRSM_WAKEUP ([SWS_FrSM_00097]). It selects the wake-up channel using FrIf_SetWakeupChannel, where FR_CHANNEL_AB must not be used. Subsequently, it sends a wakeup pattern using FrIf_SendWUP. A dual-channel ECU that was woken from the bus on channel A forwards the wake-up selectively to channel B (SWS FrSM p. 56, SWS FrSM Fig. 9.8 p. 53).

How often the pattern is repeated is determined by FrSMNumWakeupPatterns (SWS FrSM p. 27). The repetition ends as soon as bus traffic is detected. If a controller enters HALT due to an error, transmission is aborted. This document section originates from R23-11/R24-11; the payload does not contain a dedicated R20-11 requirement for this.

Activity diagram: Wakeup pattern transmission repeats under counter control. It ends when bus traffic is detected, the count is reached, or a controller enters HALT due to an error. Sources: SWS FrSM p. 27, SWS FrSM p. 18

Key-Slot-Only Startup and Reception Mode upon Request of BswM

If pKeySlotOnlyEnabled is set on the controller, the node initially transmits only in the key slots after startup (SWS FrSM Fig. 9.10 p. 55, [SWS_FrSM_00199]). The cluster is then in FRSM_KEYSLOT_ONLY, which the FrSM reports to BswM as FRSM_BSWM_KEYSLOT_ONLY. According to Figure 9.10, BswM subsequently enables full operation using FrSm_AllSlots ([SWS_FrSM_00172]). For this asynchronous function, the following applies (SWS FrSM p. 41):

  • It calls FrIf_AllSlots for each controller of the cluster.
  • It returns E_OK only if all of these calls yield E_OK.
  • It can be disabled at compile time via FrSMAllSlotsSupport.

If the POC status subsequently reports FR_SLOTMODE_ALL, the cluster transitions to FRSM_ONLINE (SWS FrSM p. 57).

Sequence diagram: Only the BswM call FrSm_AllSlots leads from key slot operation to full operation. FrSM reports the transition as soon as the POC status indicates slot mode ALL. Figure 9.10 labels the BswM state with FRSM_ONLINE_KEYSLOT_ONLY, whereas the R20-11 type lists it as FRSM_BSWM_KEYSLOT_ONLY. Sources: [SWS_FrSM_00172], [SWS_FrSM_00199], SWS FrSM p. 57, SWS FrSM Fig. 9.10 p. 55

FrSm_SetEcuPassive is synchronous and non-reentrant; a single call affects all FlexRay clusters of the ECU ([SWS_FrSM_00174]). The type FrSM_BswM_StateType contains a variant with the suffix _ECU_PASSIVE for each state value, such as FRSM_BSWM_ONLINE_ECU_PASSIVE (0x0B) ([SWS_FrSM_00199]). Interpretation: The FrSM likely uses this to report the state of [CcCtrl] and the passive status of [TrcvCtrl] to BswM in a single value, allowing BswM rules to evaluate both together (SWS FrSM p. 35).

Return to NoCom and Query of the Current Communication Mode

If NoCom is requested while the cluster is in a FullCom state, FrSM_RequestComMode processes the transition immediately within the call according to the later specification version (SWS FrSM p. 36). Figure 9.11 shows a two-stage sequence for this (SWS FrSM p. 58, SWS FrSM Fig. 9.11 p. 56):

  1. In the call itself: FrIf_SetState with FRIF_GOTO_OFFLINE, FrIf_HaltCommunication, reporting HALT_REQ to BswM, and COMM_NO_COMMUNICATION to ComM.
  2. In the following MainFunction runs: Reinitialization of the controller with FrIf_ControllerInit, transceivers to STANDBY, reporting READY.

If FrSMTrcvStdbyDelay is not configured or set to 0, timer t_TrcvStdbyDelay is not started; the transition from FRSM_HALT_REQ to FRSM_READY then occurs immediately ([SWS_FrSM_00209]). During the coordinated shutdown of multiple buses, the FrSM acts as a participant in Nm coordination (SWS Nm Fig. 9.1 p. 83).

Sequence diagram: The NoCom request stops communication and reports NoCom immediately. Controller reinitialization and transceiver standby follow cyclically, if applicable after t_TrcvStdbyDelay. Sources: SWS FrSM p. 58, SWS FrSM Fig. 9.11 p. 56, [SWS_FrSM_00209], [SWS_FrSM_00096]

In R20-11, FrSM_GetCurrentComMode is synchronous, has the Service ID 0x03, and is reentrant for different clusters ([SWS_FrSM_00024]). The function writes the current mode to the passed address. It returns COMM_FULL_COMMUNICATION only in FRSM_ONLINE and FRSM_LOW_NUMBER_OF_COLDSTARTERS, and COMM_NO_COMMUNICATION in all other states (SWS FrSM p. 38). This therefore also applies to FRSM_KEYSLOT_ONLY and FRSM_ONLINE_PASSIVE, even though both belong to the FullCom group. SilentCom is not supported on FlexRay (SWS FrSM p. 18).

Configuration per FlexRay Cluster: Roles, Timers, and Switches

Each cluster is described by a container FrSMCluster (multiplicity 1..*), which can comprise multiple controllers per ECU (SWS FrSM p. 62). It contains, among other things:

  • the references FrSMComMNetworkHandleRef and FrSMFrIfClusterRef,
  • the roles FrSMIsColdstartEcu and FrSMIsWakeupEcu,
  • the repetition parameters FrSMStartupRepetitions, FrSMStartupRepetitionsWithWakeup, and FrSMNumWakeupPatterns,
  • the cycle time FrSMMainFunctionCycleTime.

The container description originates from R23-11 et seq. From the R20-11 requirements, FrSMTrcvStdbyDelay of this is evidenced ([SWS_FrSM_00209]). The timers per cluster are (SWS FrSM p. 21):

  • t1 (FrSMDurationT1): delays the call of FrIf_AllowColdstart.
  • t2 (FrSMDurationT2): interval after which the startup is repeated.
  • t3 (FrSMDurationT3): monitors the transition to FullCom.
  • t4: ensures that a dual-channel node clears its coldstart inhibit and becomes leading coldstarter.
  • t_TrcvStdbyDelay: delays controller reinitialization and transceiver standby ([SWS_FrSM_00209]).

The following switches take effect module-wide:

  • FrSMDevErrorDetect enables development error detection (SWS FrSM p. 35).
  • FRSM_VERSION_INFO_API enables or disables the version info API at compile time ([SWS_FrSM_00029]); in the System Template, the parameter is called FrSMVersionInfoApi.
  • FrSMSyncLossErrorIndicationName specifies the CDD callback; if the parameter is absent, the indication is omitted (SystemTemplate p. 1528, [SWS_FrSM_00190]).

The imported types, including ComM_ModeType, NetworkHandleType, and the types from Fr_GeneralTypes.h, are listed in [SWS_FrSM_00095].

Behavior in the event of an error

The FrSM reports development errors via Det_ReportError ([SWS_FrSM_00097]) using the codes from [SWS_FrSM_91001]:

  • FRSM_E_PARAM_POINTER (0x01): The service returns without further action.
  • FRSM_E_INV_HANDLE (0x02): invalid network handle.
  • FRSM_E_UNINIT (0x03): module not initialized.
  • FRSM_E_INV_MODE (0x04): invalid communication mode requested.
  • FRSM_INIT_FAILED (0x05): initialization failed.

To allow other functions to verify initialization, FrSm_Init remembers successful initialization when error detection is active (SWS FrSM p. 35). In R20-11, FrSM_GetCurrentComMode rejects requests prior to initialization with E_NOT_OK ([SWS_FrSM_00024]). An invalid NetworkHandle passed to FrSm_AllSlots leads to FRSM_E_INV_HANDLE and E_NOT_OK (SWS FrSM p. 41). A SilentCom request is likely to fall under FRSM_E_INV_MODE, as this mode is not supported on FlexRay (SWS FrSM p. 18).

If the startup fails, the timers take effect: t2 repeats the startup, t3 monitors reaching FullCom (SWS FrSM p. 21). If the cluster cannot be synchronized, the FrSM calls FrNm_StartupError ([SWS_FrSM_00097]). It reports the startup of the cluster as DEM event FRSM_E_CLUSTER_STARTUP (SWS FrSM Fig. 9.7 p. 52). The associated events are referenced in container FrSMClusterDemEventParameterRefs (SWS FrSM p. 62).

During ongoing operation, the state machine distinguishes two fault cases (SWS FrSM p. 18):

  • Clock synchronization errors lead to FRSM_ONLINE_PASSIVE; no data is transmitted.
  • If there are too few coldstarters, FRSM_LOW_NUMBER_OF_COLDSTARTERS applies: Synchronization runs via sync frames only, communication remains complete.

If the ECU loses synchronization, <Cdd>_SyncLossErrorIndication is called with true ([SWS_FrSM_00190]). With false, the call follows as soon as the ECU can synchronize again or the FullCom request has been released. During wakeup, a fault-induced HALT of a controller aborts the pattern transmission (SWS FrSM p. 27).

Usage and Call Context

The function FrSM_RequestComMode ([SWS_FrSM_00020]) serves the Communication Manager (ComM) to start or shut down communication on a specific FlexRay cluster (startup or shutdown). It is provided via the header file FrSm.h and has the service ID 0x02.

Execution of the function is asynchronous. It accepts the following parameters:

  • NetworkHandle (input parameter): Identifies the specific FlexRay cluster for which a communication mode is requested.
  • ComM_Mode (input parameter): Passes the requested communication mode.

Return Values and Error Handling

The function returns a status value of type Std_ReturnType:

  • E_OK: The mode request was accepted (Request accepted). Since the call executes asynchronously, this return value confirms acceptance of the request by the FlexRay State Manager.
  • E_NOT_OK: The mode request was rejected (Request not accepted).

Concurrency

Regarding concurrency, [SWS_FrSM_00020] specifies that FrSM_RequestComMode is reentrant for different FlexRay clusters (Reentrant for different Flex Ray clusters).

The enumeration type FrSM_BswM_StateType defines the states of the FlexRay State Manager (FrSM) that are reported to the Basic Software Mode Manager (BswM) and is declared via the header file FrSm.h [SWS_FrSM_00199].

Usage and Interaction

The type serves as the data basis for status reporting to the BswM by means of interface BswM_FrSM_CurrentState [SWS_FrSM_00199]. Based on the transmitted states, the BswM evaluates mode changes and coordinating actions of the overall vehicle communication.

Value Range

According to [SWS_FrSM_00199], the range of values comprises the following states from 0x00 to 0x0F:

  • FRSM_BSWM_READY (0x00) and FRSM_BSWM_READY_ECU_PASSIVE (0x01)
  • FRSM_BSWM_STARTUP (0x02) and FRSM_BSWM_STARTUP_ECU_PASSIVE (0x03)
  • FRSM_BSWM_WAKEUP (0x04) and FRSM_BSWM_WAKEUP_ECU_PASSIVE (0x05)
  • FRSM_BSWM_HALT_REQ (0x06) and FRSM_BSWM_HALT_REQ_ECU_PASSIVE (0x07)
  • FRSM_BSWM_KEYSLOT_ONLY (0x08) and FRSM_BSWM_KEYSLOT_ONLY_ECU_PASSIVE (0x09)
  • FRSM_BSWM_ONLINE (0x0A) and FRSM_BSWM_ONLINE_ECU_PASSIVE (0x0B)
  • FRSM_BSWM_ONLINE_PASSIVE (0x0C) and FRSM_BSWM_ONLINE_PASSIVE_ECU_PASSIVE (0x0D)
  • FRSM_LOW_NUMBER_OF_COLDSTARTERS (0x0E) and FRSM_LOW_NUMBER_OF_COLDSTARTERS_ECU_PASSIVE (0x0F)

Interpretation: The paired provision of regular states and variants with the suffix _ECU_PASSIVE likely signals whether the ECU is in passive mode during the respective communication status.
