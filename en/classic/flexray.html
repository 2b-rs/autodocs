System architecture and role of the module cluster

The cluster forms the FlexRay communication stack of the Classic Platform. It extends from the transceiver via the Communication Controller (CC) to the segmenting transport protocol. Where the specification does not define anything of its own, FrTp follows ISO 10681-2 [SWS_FrTp_01005]. The State Manager handles network control on behalf of ComM. It reports its state back to BswM and ComM [SWS_FrSM_00096]. Upwards, FrTp serves the PduR; downwards, it uses FrIf_Transmit [SWS_FrTp_00577].

Interaction and Data Paths

The transmit path always begins with FrTp_Transmit [SWS_FrTp_00136]. The call only sets the TX_SDU_AVAILABLE flag, and only if the ID is valid and a channel is free [SWS_FrTp_01039]. The actual work takes place in the MainFunction:

  1. FrTp queries the available length using PduR_FrTpCopyTxData [SWS_FrTp_01042].
  2. FrTp occupies the first free FrTpTxPdu of the pool [SWS_FrTp_01045] and decides on segmentation [SWS_FrTp_01048].
  3. FrTp copies the data [SWS_FrTp_01123] and passes them via FrIf_Transmit [SWS_FrTp_01050] [SWS_FrIf_05033].
  4. FrTp_TxConfirmation resets the N-PDU to “idle” [SWS_FrTp_01054].
  5. After the last segment and, if applicable, the final acknowledgment, FrTp releases the channel [SWS_FrTp_01056] and reports PduR_FrTpTxConfirmation [SWS_FrTp_01058].

For the transmit side, there are the modes “Immediate Buffer Access” and “Decoupled Buffer Access” [SWS_FrTp_01084]. In decoupled mode, FrIf fetches the data later via FrTp_TriggerTransmit. FrTp thereby copies address information, PCI, and payload data [SWS_FrTp_00154] [SWS_FrTp_01060]. Difference between releases: Newer diagrams additionally show an LSduR between FrTp and FrIf (FrTp-SWS p. 39). The R20-11 diagram, on the other hand, connects PduR, FrTp, and FrIf directly (FrTp-SWS p. 44).

Sequence diagram: A transmit request is accepted synchronously, but segmented and transmitted asynchronously in the FrTp_MainFunction. Sources: [SWS_FrTp_01039], [SWS_FrTp_01042], [SWS_FrTp_01056], FrTp-SWS p. 44

Reception begins with FrTp_RxIndication [SWS_FrTp_00137]. FrTp processes an N-PDU only if the ID is valid and the addresses match a connection [SWS_FrTp_01069] [SWS_FrTp_01071]. The further sequence:

  • FrTp announces a new connection with PduR_FrTpStartOfReception [SWS_FrTp_01078].
  • It passes the data with PduR_FrTpCopyRxData [SWS_FrTp_01138].
  • If required, it sends FlowControl back [SWS_FrTp_01080].
  • It reports completion with PduR_FrTpRxIndication [SWS_FrTp_01083].

PDU pools control the bandwidth:

  • Multiple connections can share the same pool [SWS_FrTp_01020]. Its N-PDUs are arranged in ascending order according to the network schedule [SWS_FrTp_01088].
  • Active connections are served alternately [SWS_FrTp_01096].
  • Weak receivers limit the sender via BC.MPPC [SWS_FrTp_01175] or via overlapping pools [SWS_FrTp_01176] (FrTp-SWS p. 134).
  • The BC parameter can be changed at runtime using FrTp_ChangeParameter [SWS_FrTp_00151] [SWS_FrTp_01195].

Task Contexts, Synchronization, and Reentrancy

Each module has its own cyclic function:

  • FrTp_MainFunction is the entry point of all FrTp sequences [SWS_FrTp_00203]. It must run at least once per FlexRay cycle [SWS_FrTp_01152].
  • FrSM and FrIf have their own function per cluster: FrSM_MainFunction_<FrSMCluster.ShortName> [SWS_FrSM_00118] and FrIf_MainFunction_<FrIfCluster.ShortName> [SWS_FrIf_05042].
  • FrTrcv_MainFunction [SWS_FrTrcv_00330] is independent of the bus schedule. It checks buses in STANDBY and SLEEP for wakeups (FrTrcv-SWS p. 49).

FrIf_JobListExec_<FrIfCluster.ShortName> is time-critical. It processes the Job List [SWS_FrIf_05040]. If it loses synchronization to the Global Time, FrIf reports the runtime error FRIF_E_JLE_SYNC [SWS_FrIf_05432]. Interpretation: The function is likely triggered by the absolute timer interrupt. FrIf provides FrIf_EnableAbsoluteTimerIRQ and FrIf_AckAbsoluteTimerIRQ for this purpose [SWS_FrIf_05025] [SWS_FrIf_05029]. The wakeup notification from FrTrcv can also arrive in interrupt context (FrTrcv-SWS p. 46, [SWS_FrTrcv_00331]).

Reentrancy is tiered:

  • Fr services are non-reentrant per device [SWS_Fr_00010].
  • FrIf wrappers are reentrant for different FrIf_CtrlIdx [SWS_FrIf_05004]. FrIf_SetState, by contrast, is non-reentrant [SWS_FrIf_05174].
  • FrTp callbacks are reentrant for different PduIds [SWS_FrTp_00152] [SWS_FrTp_00153]. FrTp_CancelReceive is non-reentrant [SWS_FrTp_01172].

Fr uses exclusive areas via SchM_Enter_Fr/SchM_Exit_Fr [SWS_Fr_00391]. FrIf_GetGlobalTime may also be called within an exclusive area (FrIf-SWS p. 64, [SWS_FrIf_05015]).

FrTp protects the order of Consecutive Frames with a TxPduPendingCounter per channel [SWS_FrTp_01090]. A connection is only processed if this counter is zero [SWS_FrTp_01094]. Otherwise, a frame delayed in the dynamic segment could be overtaken (FrTp-SWS p. 56).

Lifecycles and operating modes

Initialization is handled by EcuM. It calls FrIf_Init and FrSm_Init in succession (FrSM-SWS p. 46, [SWS_FrIf_05003], [SWS_FrSM_00013]). In R20-11, the function is named FrSm_Init, in newer releases FrSM_Init. The other modules behave as follows:

  • Fr_Init stores the configuration [SWS_Fr_00032].
  • FrTp knows the states FRTP_OFF and FRTP_ON [SWS_FrTp_01028]. After power-up, it is in FRTP_OFF [SWS_FrTp_01030]; FrTp_Init switches to FRTP_ON [SWS_FrTp_01032]. It operates only in this state [SWS_FrTp_01033].
  • FrTp_Shutdown terminates all connections and returns to FRTP_OFF [SWS_FrTp_00148] [SWS_FrTp_01036].
  • FrIf maintains the states FRIF_STATE_OFFLINE and FRIF_STATE_ONLINE per cluster [SWS_FrIf_05755]. Switching is performed using FrIf_SetState and FRIF_GOTO_ONLINE/FRIF_GOTO_OFFLINE [SWS_FrIf_05303] (FrIf-SWS p. 25).

FrSM manages the CC lifecycle via FrIf:

  • Fr_ControllerInit transitions the CC from POC:config to POC:ready [SWS_Fr_00017].
  • Fr_StartCommunication transitions to the transitional state POC:startup [SWS_Fr_00010]. Whether POC:normal active is reached thereafter is not guaranteed. Therefore, FrSM queries the state via FrIf_GetPOCStatus in its MainFunction. Only then does FrSM switch FrIf online and report FRSM_ONLINE (FrSM-SWS p. 50).
  • FrIf_SendWUP (POC:wakeup) and FrIf_SetWakeupChannel serve for wakeup [SWS_Fr_00009] [SWS_Fr_00091] [SWS_FrIf_05011].

The startup diagram calls ComM_FrSM_ModeIndication. However, ComM_BusSM_ModeIndication is normative [SWS_FrSM_00096].

During shutdown, the following sequence is followed (FrSM-SWS p. 58):

  1. FrSM reports HALT_REQ to BswM.
  2. FrSM switches FrIf offline and calls FrIf_HaltCommunication.
  3. FrSM calls FrIf_ControllerInit and sets the transceiver to STANDBY.

If FrSMTrcvStdbyDelay is 0, the transition to FRSM_READY follows immediately [SWS_FrSM_00209]. FrSm_SetEcuPassive switches all clusters to receive-only [SWS_FrSM_00174]. The transceiver supports the modes NORMAL, STANDBY, SLEEP, and RECEIVEONLY [SWS_FrTrcv_00481]. When switching to STANDBY, it activates the ICU wakeup channels; when switching to NORMAL, it deactivates them [SWS_FrTrcv_00491] [SWS_FrTrcv_00492] (FrTrcv-SWS p. 23).

Error Handling, DET Tracing, and Degradation

Each module defines development errors itself:

  • FrTp: FRTP_E_UNINIT and FRTP_E_INVALID_PDU_SDU_ID [SWS_FrTp_01201].
  • FrIf: FRIF_E_INV_CTRL_IDX [SWS_FrIf_05145].
  • Fr: Parameter and index errors [SWS_Fr_91003] as well as FR_E_INV_POCSTATE [SWS_Fr_91004].
  • FrSM: FRSM_E_INV_HANDLE [SWS_FrSM_91001].
  • FrTrcv: Invalid transceiver index [SWS_FrTrcv_00085].

As runtime errors, FrTp reports FRTP_E_NO_CHANNEL and FRTP_E_SEG_ERROR [SWS_FrTp_01208] [SWS_FrTp_01185].

The following events enter the DEM error memory:

  • Fr reports hardware errors of the CC via Dem_SetEventStatus(FR_E_CTRL_TESTRESULT, …) (Fr-SWS p. 43, [SWS_Fr_00114]). Fr reports slot status errors as FR_E_LPDU_SLOTSTATUS [SWS_Fr_00600].
  • FrIf reports NIT and SW channel errors [SWS_FrIf_05426] [SWS_FrIf_05428].
  • FrTrcv reports bus errors [SWS_FrTrcv_00488] [SWS_FrTrcv_00489], optionally via a configured substitute function [SWS_FrTrcv_00475].
  • FrSM uses Dem_SetEventStatus optionally [SWS_FrSM_00097], for example for FRSM_E_CLUSTER_STARTUP (FrSM-SWS p. 50).

There are several means for degradation at network level:

  • Faulty active star branches can be switched off via FrIf_DisableTransceiverBranch [SWS_FrIf_05028] [SWS_FrTrcv_00442].
  • FrSM reports the loss of synchronization to a CDD [SWS_FrSM_00190].
  • If FrIf goes offline, it confirms pending transmissions with E_NOT_OK [SWS_FrIf_05501].

FrTp safeguards the transport itself:

  • Timeouts are handled according to defined rules [SWS_FrTp_01100].
  • Bounded counters control the reaction upon reaching a limit [SWS_FrTp_01105] [SWS_FrTp_01113] (FrTp-SWS p. 70).
  • Upon BUFREQ_E_BUSY, FrTp tries again to obtain a buffer [SWS_FrTp_01196].
  • In the case of FlowControl with OVFLW or ABT, FrTp aborts [SWS_FrTp_01198].

Ongoing transmissions can be aborted in a targeted manner. FrTp_CancelTransmit stops an ongoing transmission [SWS_FrTp_01116]. If the transmission has not yet started, it releases the connection immediately [SWS_FrTp_00385]. The function can be switched via configuration [SWS_FrTp_01097] (FrTp-SWS p. 58). FrTp_CancelReceive rejects unsegmented receptions and the LastFrame [SWS_FrTp_01182].
