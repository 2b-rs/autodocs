EcuM_CheckRamHash function

This callout is intended to provide a RAM integrity test. The goal of this test is to ensure that after a long SLEEP duration, RAM contents is still consistent. The check does not need to be exhaustive since this would consume quite some processing time during wakeups. A well designed check will execute quickly and detect RAM integrity defects with a sufficient probability. This specification does not make any assumption about the algorithm chosen for a particular ECU. The areas of RAM which will be checked have to be chosen carefully. It depends on the check algorithm itself and the task structure. Stack contents of the task executing the RAM check e.g. very likely cannot be checked. It is good practice to have the hash generation and checking in the same task and that this task is not preemptible and that there is only little activity between hash generation and hash check. The RAM check itself is provided by the system designer. In case of applied multi core and existence of Satellite-Ecu M(s): this API will be called by the Master-EcuM only.

uint8 EcuM_CheckRamHash (void);
EcuM_CheckValidation function

This callout is called by the EcuM to validate a wakeup source. If a valid wakeup has been detected, it shall be reported to EcuM via EcuM_ValidateWakeupEvent().

void EcuM_CheckValidation (EcuM_WakeupSourceType wakeupSource);
EcuM_CheckWakeup function

This callout is called by the EcuM to poll a wakeup source. It shall also be called by the ISR of a wakeup source to set up the PLL and check other wakeup sources that may be connected to the same interrupt.

void EcuM_CheckWakeup (EcuM_WakeupSourceType wakeupSource);

EcuM_DeterminePbConfiguration function

This callout should evaluate some condition, like port pin or NVRAM value, to determine which post-build configuration shall be used in the remainder of the startup process. It shall load this configuration data into a piece of memory that is accessible by all BSW modules and shall return a pointer to the EcuM post-build configuration as a base for all BSW module post-build configrations.

const EcuM_ConfigType* EcuM_DeterminePbConfiguration (void);
EcuM_DisableWakeupSources function

The ECU Manager Module calls EcuM_DisableWakeupSources to set the wakeup source(s) defined in the wakeupSource bitfield so that they are not able to wake the ECU up.

void EcuM_DisableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EnableWakeupSources function

The ECU Manager Module calls EcuM_EnableWakeupSource to allow the system designer to notify wakeup sources defined in the wakeupSource bitfield that SLEEP will be entered and to adjust their source accordingly.

void EcuM_EnableWakeupSources (EcuM_WakeupSourceType wakeupSource);
EcuM_EndCheckWakeup function

This API is called by any SW Module whose wakeup source is checked asynchronously (e.g. asynchronous Can Trcv Driver) and the Check of the Wakeup returns a negative Result (no Wakeup by this Source). The API cancels the CheckWakeupTimer for the WakeupSource. If the correponding CheckWakeupTimer is canceled the check of this wakeup source is finished.

void EcuM_EndCheckWakeup (EcuM_WakeupSourceType WakeupSource);
EcuM_ErrorHook function

The ECU State Manager will call the error hook if the error codes "ECUM_E_RAM_CHECK_ FAILED" or "ECUM_E_CONFIGURATION_DATA_INCONSISTENT" occur. In this situation it is not possible to continue processing and the ECU must be stopped. The integrator may choose the modality how the ECU is stopped, i.e. reset, halt, restart, safe state etc.

void EcuM_ErrorHook (uint16 reason);

System architecture and role of the module cluster

The "System Services" cluster encompasses the modules that support startup, operating modes, sleep/shutdown, and program flow monitoring of a Classic Platform ECU. The ECU State Manager is the system service that establishes the final hardware state after the OS shutdown (SWS EcuM p. 82, [SWS_EcuM_04020]). The four modules have clearly separated roles:

  • BswM arbitrates incoming mode indications ([SWS_BswM_00035]). Rules logically combine ModeRequestPorts and trigger true or false action lists (Mode Management Guide p. 32). Actions execute exclusively in the context of an action list ([SWS_BswM_00147]).
  • EcuM initializes the BSW, starts and terminates the OS, and manages the states of the wakeup sources ([SWS_EcuM_02811], [SWS_EcuM_04091]). It does not have its own state machine. It takes over state changes from the BswM (SWS EcuM p. 99, [SWS_EcuM_04116]).
  • WdgM monitors Supervised Entities via checkpoints ([SWS_WdgM_00263]) and derives a Global Supervision Status from them ([SWS_WdgM_00360]). It sets watchdog modes via WdgIf_SetMode ([SWS_WdgM_00186]).
  • Wdg drives internal or external watchdog hardware ([SWS_Wdg_00161], [SWS_Wdg_00076]). It services the hardware as long as the trigger condition is valid ([SWS_Wdg_00144]).

Context diagram: The context diagram shows BswM as the decision-maker for modes, EcuM as the executor of lifecycle sequences, and the supervision chain WdgM → WdgIf → Wdg → hardware. Sources: SWS EcuM p. 34, [SWS_WdgM_00186], [SWS_WdgM_00162], [SWS_EcuM_04143]

Interaction and interaction paths

EcuM ↔ BswM (ECU Mode Handling): This path is active when EcuMModeHandling is configured ([SWS_EcuM_04115]). SW-Cs request RUN and POST_RUN via EcuM_RequestRUN and EcuM_RequestPOST_RUN, respectively, and release them again ([SWS_EcuM_04124], [SWS_EcuM_04127], [SWS_EcuM_04128]). EcuM reports the arbitration result via BswM_EcuM_RequestedState ([SWS_BswM_91004], [SWS_EcuM_04144], [SWS_EcuM_04117]). The BswM then sets the state via EcuM_SetState ([SWS_EcuM_04122]). As soon as the RTE has confirmed the transition, EcuM reports the state back via BswM_EcuM_CurrentState ([SWS_EcuM_04143], [SWS_BswM_91003]).

Wakeup path: Drivers report wakeups via EcuM_SetWakeupEvent, which marks the event as pending ([SWS_EcuM_01117]). If validation is required, EcuM starts the validation protocol ([SWS_EcuM_02975]). Exactly one BSW module performs the validation (SWS EcuM p. 69). Its call of EcuM_ValidateWakeupEvent notifies BswM and ComM ([SWS_EcuM_04079], [SWS_EcuM_02645]). Every state change of a wakeup source is reported to the BswM as a mode request ([SWS_EcuM_04003]).

State diagram: The state diagram shows the lifecycles of a wakeup source (NONE, PENDING, VALIDATED, EXPIRED) and the BswM notification upon entry into each state. Sources: [SWS_EcuM_04091], [SWS_EcuM_02976], [SWS_EcuM_04081], [SWS_EcuM_02683], SWS EcuM p. 64

WdgM → Wdg: Wdg_SetTriggerCondition accepts a timeout in milliseconds and converts it internally into a counter value, taking into account the current mode ([SWS_Wdg_00155], [SWS_Wdg_00138], [SWS_Wdg_00139]). The driver's servicing routine behaves as follows:

  • If the counter is greater than zero, it decrements it and triggers the hardware ([SWS_Wdg_00134]).
  • At zero, it no longer triggers; the watchdog expires ([SWS_Wdg_00135]).

Interpretation: WdgIf is likely to forward the mode and trigger condition to the respectively addressed Wdg instance. Multiple instances carry unique names ([SWS_Wdg_00172]).

EcuM → WdgM (Reset): WdgM_PerformReset is a mandatory reset target ([SWS_EcuM_04005], [SWS_EcuM_04044]). It sets the trigger condition of all drivers to 0, and the hardware watchdogs thereby trigger a reset ([SWS_WdgM_00264], SWS WdgM p. 82). ECUM_CAUSE_WDGM is available as a shutdown cause ([SWS_EcuM_04045]).

Synchronization, reentrancy and task contexts

BswM_MainFunction: It evaluates all rules that use a request with BSWM_DEFERRED ([SWS_BswM_00075]). BswM timers are always handled as deferred ([SWS_BswM_00220]). Requests with "immediate", on the other hand, are evaluated immediately (Mode Management Guide p. 32).

EcuM_MainFunction: It runs in all EcuM instances ([SWS_EcuM_04011]). It monitors the validation timeouts ([SWS_EcuM_04082]) and validates wakeup candidates after the WakeupRestart ([SWS_EcuM_02539]).

WdgM_MainFunction: It starts supervision upon the first call after WdgM_Init ([SWS_WdgM_00406]) and thereafter calculates the Global Supervision Status in each period (SWS WdgM p. 34).

Interrupt context: The wakeup services can be called from interrupt, OS, and non-OS context ([SWS_EcuM_02171], [SWS_EcuM_02807], [SWS_EcuM_02532]). However, they are specified as "Non-Reentrant, Non-Interruptible" ([SWS_EcuM_02826], [SWS_EcuM_02828]). An exception is EcuM_ValidateWakeupEvent: It is reentrant and can be called from interrupt and task context ([SWS_EcuM_02829], [SWS_EcuM_02345]).

Reentrancy of WdgM and Wdg:

  • WdgM_SetMode, WdgM_DeInit, and Wdg_SetTriggerCondition are non-reentrant ([SWS_WdgM_00154], [SWS_WdgM_00261], [SWS_Wdg_00155]).
  • WdgM_GetMode still returns the old mode during an ongoing mode switch ([SWS_WdgM_00168], SWS WdgM p. 77).
  • Wdg disables interrupts for data consistency only via the intended BSW mechanisms ([SWS_Wdg_00040]).

Multicore: A separate EcuM instance runs on each Core. The master EcuM starts the remaining Cores (SWS EcuM p. 71). This results in the following obligations:

  • Each instance processes the wakeups of its own Core ([SWS_EcuM_04012]).
  • All core-local BswM are initialized ([SWS_EcuM_04014]).
  • One resource RES_AUTOSAR_ECUM is reserved per Core ([SWS_EcuM_03010]).
  • The C APIs are available in each partition in which an EcuM runs ([SWS_EcuM_04095]).

The BswM is conditionally reentrant for multi-partition systems ([SWS_BswM_00002]).

Lifecycles and operating modes

Startup (StartPreOS): EcuM_Init executes the StartPreOS sequence ([SWS_EcuM_02684]). It comprises:

  • init blocks 0 and 1 in the configured order ([SWS_EcuM_02559], [SWS_EcuM_02905], [SWS_EcuM_02907]),
  • the selection of the post-build configuration ([SWS_EcuM_02906]),
  • the consistency check of all post-build configurations before the first BSW initialization ([SWS_EcuM_02796]).

According to the structure description, Wdg_Init belongs to the init functions used by the EcuM (SWS EcuM p. 34). Wdg_Init sets the default mode and timeout ([SWS_Wdg_00001]).

Startup (StartPostOS): EcuM_StartupTwo runs in a task started by StartOS ([SWS_EcuM_02806]). It starts SchM and initializes BswM ([SWS_EcuM_02932]). BswM_Init only requires an initialized OS and SchM (SWS BswM p. 69). The BswM can initialize additional drivers in the UP phase, for example via EcuM_AL_DriverInitBswM_<x> (SWS EcuM p. 46, [SWS_EcuM_04114]).

Sequence diagram: The sequence diagram shows the order of StartPreOS and StartPostOS on the master Core. Sources: [SWS_EcuM_04015], [SWS_EcuM_04016], SWS EcuM p. 82, SWS EcuM p. 42

Sleep: Before EcuM_GoDownHaltPoll, the BswM typically must have selected a SLEEP target (SWS EcuM p. 54, [SWS_EcuM_91002]). The sequence:

  1. GoSleep activates the wakeup sources; the OS remains active in the process ([SWS_EcuM_02389], [SWS_EcuM_02951]).
  2. After that, depending on the sleep mode, Halt with RAM hash ([SWS_EcuM_02863]) or Poll ([SWS_EcuM_02962]) follows. No wakeup must be lost in the process ([SWS_EcuM_02188]).
  3. A wakeup leads to the WakeupRestart sequence with driver re-initialization ([SWS_EcuM_02963], [SWS_EcuM_02923]).

In R20-11, the poll callout is named EcuM_CheckWakeup ([SWS_EcuM_02929]). Only starting with R21-11 is it named EcuM_CheckWakeupHook (SWS EcuM p. 145).

Watchdog in Sleep: Before sleep, WdgM_DeInit transitions to a sleep mode with compatible trigger conditions and stops supervision (SWS WdgM p. 59, [SWS_WdgM_00407]). However, the structure description of the EcuM only mentions WdgM_PerformReset as a WdgM dependency. Therefore, the call of WdgM_DeInit presumably occurs via a BswM action or integration code.

Sequence diagram: The sequence diagram shows the SLEEP phase with Halt: GoSleep, RAM hash, wakeup, and WakeupRestart. Sources: SWS EcuM p. 54, SWS EcuM p. 55, SWS EcuM p. 56, [SWS_EcuM_04024], [SWS_EcuM_02987]

Shutdown: The sequence:

  1. OffPreOS de-initializes BswM and SchM (SWS EcuM p. 90). After that, the BswM no longer processes any modes ([SWS_BswM_00120]).
  2. As its last activity, EcuM calls ShutdownOS ([SWS_EcuM_02952]). The shutdown hook calls EcuM_Shutdown ([SWS_EcuM_02953]).
  3. Finally, EcuM_AL_Reset or EcuM_AL_SwitchOff follow ([SWS_EcuM_04074], [SWS_EcuM_04075]).

Wakeup sources must be cleared via BswM user callouts before Dem_Shutdown and NvM_WriteAll (SWS EcuM p. 124, [SWS_BswM_00054]). A wakeup during shutdown leads to a restart after its completion ([SWS_EcuM_02756]). Wdg does not have its own de-init interface ([SWS_Wdg_00031]).

Error Handling, DET Tracing, and Degradation

Development errors (DET):

  • BswM ignores indications prior to initialization and reports BSWM_E_UNINIT ([SWS_BswM_00078], [SWS_BswM_00230]). It reports failing actions as runtime error BSWM_E_ACTION_FAILED ([SWS_BswM_00238]).
  • EcuM reports duplicate RUN requests and inappropriate releases ([SWS_EcuM_03024], [SWS_EcuM_03023]) as well as unknown wakeup sources ([SWS_EcuM_02867]).
  • WdgM and Wdg define their own error codes ([SWS_WdgM_00004], [SWS_Wdg_00010]). WdgM reports a failed WdgIf_SetMode as WDGM_E_SET_MODE ([SWS_WdgM_00139]).

Unrecoverable errors: EcuM forwards these to EcuM_ErrorHook ([SWS_EcuM_04033]). Examples are inconsistent configuration data or a failed RAM check ([SWS_EcuM_91003]). EcuM ignores errors that are returned by init functions during initialization ([SWS_EcuM_02980]).

Degradation of supervision: The global status starts as WDGM_GLOBAL_STATUS_DEACTIVATED ([SWS_WdgM_00387]). Mode switches are only permitted in the states OK and FAILED ([SWS_WdgM_00145]). Disabling the watchdog can be prohibited by configuration ([SWS_WdgM_00031]). The escalation proceeds as follows:

  1. In the EXPIRED state, the fault reaction is postponed by a configurable tolerance (SWS WdgM p. 34).
  2. In the STOPPED state, WdgM reports WDGM_E_SUPERVISION, and a watchdog reset follows ([SWS_WdgM_00375]).
  3. A failed mode switch also leads to STOPPED (SWS WdgM p. 57).

Diagnostics after the reset: The SEID that expired first is stored double-inversely in uninitialized RAM. It is readable even before WdgM_Init ([SWS_WdgM_00348], [SWS_WdgM_00349]). WdgM reports status changes via mode ports ([SWS_WdgM_00197], [SWS_WdgM_00198]). BswM_WdgM_RequestPartitionReset still exists in R20-11 ([SWS_BswM_00157]), but becomes obsolete starting with R21-11 (SWS BswM p. 2).

Driver errors and final safeguard: Wdg reports the production errors WDG_E_MODE_FAILED and WDG_E_DISABLE_REJECTED to the DEM ([SWS_Wdg_00180], [SWS_Wdg_00182]). If EcuM_AL_SwitchOff hangs in a deadlock, the hardware watchdog resets the ECU (SWS EcuM p. 141).
