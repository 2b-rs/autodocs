Returns the Rx error counter for a CAN controller. This value might not be available for all CAN controllers, in which cas e E_ NOT_ OK would be returned. Please note that the value of the counter might not be correct at the moment the API returns it, because the Rx counter is handled asynchronously in hardware. Can_ConfigType type

This is the type of the external data structure containing the overall initialization data for the CAN driver and SFR settings affecting all controllers. Furthermore it contains pointers to controller configuration structures. The contents of the initializ ation data structure are CAN hardware specific.

Can_ControllerStateType type

States that are used by the several Controller Mode functions.

Can_ErrorStateType type

Error states of a CAN controller.

Can_ErrorType type

The enumeration represents a superset of CAN Error Types which typical CAN HW is able to report. That means not all CAN HW will be able to support the complete set.

Can_HwHandleType type

Represents the hardware object handles of a CAN hardware unit. For CAN hardware units with more than 255 HW objects use extended range.

Can_HwType type

This type defines a data structure which clearly provides an Hardware Object Handle including its corresponding CAN Controller and therefore Can Drv as well as the specific Can Id.

Can_IdType type

Represents the Identifier of an L - PDU. The two most significant bits specify the frame type: 00 CAN message with Standard CAN ID 01 CAN FD frame with Standard CAN ID 10 CAN message with Extended CAN ID 11 CAN FD frame with Extended CAN ID

Can_PduType type

This type unites Pdu Id (sw Pdu Handle), Sdu Length (length), Sdu Data (sdu), and Can Id (id) for any CAN L - SDU.

System architecture and role of the module cluster

The cluster "CAN Communication" encompasses the CAN stack of the Classic Platform from the controller hardware to the transport layer.

  • Can (CAN Driver): encapsulates the controller hardware. It writes L-PDUs with Can_Write into hardware objects [SWS_Can_00233]. In doing so, a Can_PduType structure consisting of swPduHandle, length, data, and CAN ID is passed [SWS_Can_00415].
  • CanIf (CAN Interface): abstracts multiple driver instances via dedicated ControllerIds and TransceiverIds [SWS_CANIF_00653] [SWS_CANIF_00655].

Upper layers access neither the receive buffers of the driver nor the transmit buffers of CanIf CanIf p. 48. CanIf itself accesses hardware buffers exclusively via services of the driver [SWS_CANIF_00023].

The CAN Transceiver Driver (CanTrcv) controls external transceiver devices. For each hardware type, there is exactly one driver instance for all transceivers of the same type [SWS_CanTrcv_00016]. Its generic state model decouples ComM and EcuM from device-specific states CanTrcv p. 19.

The CAN Transport Layer (CanTp) follows ISO 15765-2, unless the SWS excludes anything [SWS_CanTp_00033]. It segments and reassembles N-SDUs and manages multiple connections simultaneously [SWS_CanTp_00096], such as a UDS and an OBD request in parallel CanTp p. 41.

Upwards, CanIf interfaces via callbacks whose target is defined by configuration CanIf p. 133. Typical targets are:

  • PduR_CanIfRxIndication [SWS_CANIF_00442]
  • CanTp_RxIndication [SWS_CANIF_00448]
  • CanSM_ControllerBusOff [SWS_CANIF_00559]
  • EcuM_ValidateWakeupEvent [SWS_CANIF_00563]

Context diagram: CanIf mediates centrally between Can or CanTrcv and the users PduR, CanTp, CanSM, and EcuM. Sources: [SWS_CANIF_00318] [SWS_CANIF_00415] [SWS_CANIF_00358] [SWS_CANIF_00711] [SWS_CANIF_00448] CanIf p. 133

Interaction and interaction paths

Transmit path: CanIf_Transmit [SWS_CANIF_00005] calls Can_Write with the HTH that belongs to TxPduId [SWS_CANIF_00318]. If the driver returns E_OK, CanIf also returns E_OK [SWS_CANIF_00162].

If no hardware object is free, Can_Write reports CAN_BUSY [SWS_Can_00039]. When buffering is activated, CanIf then stores the L-PDU in CanIfTxBuffer [SWS_CANIF_00381] CanIf p. 138.

With each transmit confirmation, the following sequence takes place:

  1. CanIf checks the buffers of the hardware object that has become free [SWS_CANIF_00386].
  2. It subsequently transmits the waiting L-PDU with the highest priority [SWS_CANIF_00668] [SWS_CANIF_00070].
  3. In case of E_OK, it removes it from the buffer even before the confirmation returns [SWS_CANIF_00183].
  4. Afterwards, CanIf notifies the user via <User_TxConfirmation> [SWS_CANIF_00383]. For the PduR, this is PduR_CanIfTxConfirmation [SWS_CANIF_00439].

The diagrams of newer releases name LSduR_CanIfTxConfirmation CanIf p. 157 here. For R20-11, the PduR naming applies.

Sequence diagram: In case of CAN_BUSY, CanIf buffers the L-PDU and transmits it subsequently by priority upon the next transmit confirmation. Sources: CanIf p. 138 CanIf p. 157 [SWS_CANIF_00381] [SWS_CANIF_00668] [SWS_CANIF_00183]

Receive path: The driver reports each receive L-PDU via CanIf_RxIndication [SWS_CANIF_00006]. CanIf processes it in this order CanIf p. 73:

  1. Software filtering, if configured [SWS_CANIF_00389]
  2. Data length check [SWS_CANIF_00390]
  3. Determination of the target layer [SWS_CANIF_00056] and invocation of its receive service [SWS_CANIF_00135]

Optionally, CanIf additionally stores the L-SDU for CanIf_ReadRxPduData [SWS_CANIF_00198] [SWS_CANIF_00199].

Transport path, transmission: CanTp_Transmit [SWS_CanTp_00212] operates asynchronously [SWS_CanTp_00176]. If the N-SDU does not fit into an N-PDU, CanTp starts a multi-frame transmission [SWS_CanTp_00232]. It fetches the payload for each segment with PduR_CanTpCopyTxData [SWS_CanTp_00086], as it does not copy it internally [SWS_CanTp_00298].

Transport path, reception: CanTp reports SF or FF with PduR_CanTpStartOfReception [SWS_CanTp_00079]. The flow control depends on the buffer reported there [SWS_CanTp_00080] [SWS_CanTp_00082].

In R20-11, CanIf calls CanTp_TxConfirmation [SWS_CANIF_00550]. The newer document passage names the LSduR for this CanTp p. 64.

Sequence diagram: During segmented reception, CanTp controls the sender via flow control, depending on the buffer of the PduR. Sources: CanTp p. 37 [SWS_CanTp_00079] [SWS_CanTp_00222] [SWS_CanTp_00223] [SWS_CanTp_00084]

Transceiver control: CanIf directly passes through transceiver services:

  • CanIf_SetTrcvMode calls CanTrcv_SetOpMode [SWS_CANIF_00358].
  • CanIf_GetTrcvWakeupReason calls CanTrcv_GetBusWuReason [SWS_CANIF_00368].
  • CanIf_SetTrcvWakeupMode calls CanTrcv_SetWakeupMode [SWS_CANIF_00372].

After the completed mode change, CanTrcv reports CanIf_TrcvModeIndication [SWS_CanTrcv_00158]. CanIf forwards this to CanSM_TransceiverModeIndication [SWS_CANIF_00712].

Synchronization, reentrancy and task contexts

Can operates interrupt-driven or in polling mode. For polling, cyclic functions are available:

  • Can_MainFunction_Write for transmit confirmations [SWS_Can_00225]
  • Can_MainFunction_Read for reception [SWS_Can_00226]
  • Can_MainFunction_BusOff [SWS_Can_00227] and Can_MainFunction_Wakeup [SWS_Can_00228]
  • Can_MainFunction_Mode for controller state changes [SWS_Can_00368]

Depending on the configuration, the CanIf callbacks therefore run in interrupt or task context CanIf p. 155 CanIf p. 156. CanIf_CheckWakeup can also be called in both contexts CanIf p. 101.

CanIf protects preemptive accesses to shared resources against each other [SWS_CANIF_00064]. This applies in particular to:

  • the transmit buffers [SWS_CANIF_00033]
  • the CAN ID for CanIf_SetDynamicTxId, which can be interrupted by CanIf_Transmit [SWS_CANIF_00673]

Reentrancy is defined per service: CanIf_RxIndication is reentrant [SWS_CANIF_00006], CanIf_SetPduMode is not [SWS_CANIF_00008]. For short critical sections, Can provides Can_DisableControllerInterrupts [SWS_Can_00231] and Can_EnableControllerInterrupts [SWS_Can_00232]. Multiple locks require just as many releases Can p. 61.

In CanTp, interrupt and task levels are separated:

  • CanTp_RxIndication and CanTp_TxConfirmation must be callable in interrupt context [SWS_CanTp_00235] [SWS_CanTp_00236].
  • Time monitoring (N_As, N_Bs, N_Cs, N_Ar, N_Br, N_Cr, STmin) is handled by CanTp_MainFunction [SWS_CanTp_00164]. Its period is configured [SWS_CanTp_00300].
  • Each connection channel has its own buffers, timers, and its own state machine [SWS_CanTp_00122].

CanTrcv cyclically checks all buses in STANDBY and SLEEP for wake-up events via CanTrcv_MainFunction [SWS_CanTrcv_00112].

Lifecycles and operating modes

Initialization: EcuM initializes CanIf as well as driver and transceiver driver separately. Afterwards, the controllers remain in STOPPED CanIf p. 40. Can_Init [SWS_Can_00223] and CanTrcv_Init [SWS_CanTrcv_00001] are likely to run before CanIf_Init [SWS_CANIF_00001] (interpretation). It is only proven that the drivers used by CanTrcv must be ready beforehand [SWS_CanTrcv_00099].

After initialization, the following states apply:

  • CanIf switches all channels to CANIF_OFFLINE [SWS_CANIF_00864].
  • CanTrcv_Init sets each transceiver to SLEEP or STANDBY depending on the configuration [SWS_CanTrcv_00148].
  • CanTp transitions from CANTP_OFF to CANTP_ON after CanTp_Init [SWS_CanTp_00170] and segments only there [SWS_CanTp_00238].

Controller modes: The modes (Can_ControllerStateType [SWS_Can_91013]) are requested by CanSM via CanIf_SetControllerMode [SWS_CANIF_00003]. CanIf then calls Can_SetControllerMode [SWS_CANIF_00308]. The transition runs asynchronously and is reported to CanSM via CanIf_ControllerModeIndication [SWS_CANIF_00699] [SWS_CANIF_00711] CanIf p. 152.

PDU modes: Above this lies the channel mode CanIf_PduModeType [SWS_CANIF_00137]. It can only be changed in the STARTED state [SWS_CANIF_00874]. If a controller transitions to STOPPED, the following applies:

  • CanIf clears the associated transmit buffers [SWS_CANIF_00485].
  • Pending transmissions are negatively confirmed [SWS_CANIF_00739].
  • The channel is set offline [SWS_CANIF_00866].

Sleep: CAN_CS_SLEEP sets the channel to CANIF_OFFLINE [SWS_CANIF_00865]. With partial networking, CanIf additionally activates the PnTxFilter [SWS_CANIF_00749]. It only lets configured PN-PDUs pass through [SWS_CANIF_00750] and is deactivated with the first transmit confirmation [SWS_CANIF_00751]. Prior to low-power mode, CanSM clears the WUF flag so that no wake-up frame is lost [SWS_CanTrcv_00194] CanTrcv p. 57.

Wakeup: CanIf_CheckWakeup queries the driver or transceiver [SWS_CANIF_00395]. It returns E_OK as soon as one source responds positively [SWS_CANIF_00720]. Validation is performed via CanIf_CheckValidation [SWS_CANIF_00178] and <User_ValidateWakeupEvent> [SWS_CANIF_00179].

Shutdown: CanTp_Shutdown closes all connections and sets CanTp to CANTP_OFF [SWS_CanTp_00202]. The upper layers are not notified in this process [SWS_CanTp_00200]. For deinitialization, Can_DeInit [SWS_Can_91002], CanIf_DeInit [SWS_CANIF_91002], and CanTrcv_DeInit [SWS_CanTrcv_91001] are available. Prerequisite: No controller is STARTED anymore, and no transmissions are pending Can p. 59 CanIf p. 81. The transceiver then returns to NOT_ACTIVE [SWS_CanTrcv_91003].

Development errors: All modules report them to the DET. The error codes are tabulated per module: Can [SWS_Can_91019], CanIf [SWS_CANIF_91006], CanTp [SWS_CanTp_00293], CanTrcv [SWS_CanTrcv_00050].   • a failed length check [SWS_CANIF_00168]
