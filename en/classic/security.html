Ensures on-board security through crypto services, PDU authentication, key management, and event detection.

The Security & Intrusion Detection cluster provides cryptographic primitives via CSM, CryIf, and Crypto Driver, protects I-PDUs with authentication data via SecOC, and manages keys as well as certificates with KeyM AUTOSAR_CP_SWS_CryptoServiceManager p. 21. Security incidents are reported as events to the IdsM, buffered there, and asynchronously filtered [SWS_IdsM_00702]. During shutdown, the active deletion of RAM key data protects against unauthorized compromise.

The module cluster Security & Intrusion Detection combines the modules secoc, idsm, keym, csm, cryif, and crypto to secure vehicle communication and to detect security incidents in the AUTOSAR Classic Platform AUTOSAR_CP_SWS_IntrusionDetectionSystemManager p. 21. The basic cryptographic services are provided hierarchically via the Crypto Service Manager (CSM), which encapsulates jobs in Crypto_JobType structures [SWS_Csm_01013] and forwards them via the Crypto Interface (CryIf_ProcessJob [SWS_CryIf_91003]) to the specific hardware or software driver objects of the Crypto Driver.

PDU communication is protected by SecOC via message authentication codes (MAC) and freshness values ([SWS_SecOC_91006], [SWS_SecOC_00012]), while the Key Manager (KeyM) prepares, updates, and validates certificates and keys for the CSM ([SWS_KeyM_00052], [SWS_KeyM_00059]). Security-relevant events—such as failed PDU checks—are reported as Security Events (SEv) to the IdsM [SWS_IdsM_91002], which buffers them synchronously [SWS_IdsM_00701] and qualifies them asynchronously via configurable filter chains [SWS_IdsM_01020].

Execution separates synchronous API entries from computationally intensive background tasks in IdsM_MainFunction, SecOC_MainFunctionTx [SWS_SecOC_00176], and KeyM_MainBackgroundFunction [SWS_KeyM_00075]. System Architecture & Role of the Module Cluster

The module cluster Security & Intrusion Detection of the AUTOSAR Classic Platform (Release R20-11) provides standardized services for cryptography, secure on-board communication, key and certificate management, and intrusion detection. Functionally, the cluster is structured across several layers of the AUTOSAR Basic Software (BSW): At the service layer, the Crypto Service Manager (CSM) encapsulates hardware-independent cryptographic services AUTOSAR_CP_SWS_CryptoServiceManager p. 21. Secure communication of I-PDUs is handled by the Secure Onboard Communication (SecOC) module in the communication layer [SWS_SecOC_00162], while the Key Manager (KeyM) orchestrates the lifecycle of cryptographic keys and certificates as a security service SWS_KeyManager p. 31. In addition, the Intrusion Detection System Manager (IdsM) acts as a central aggregator and filter for security-relevant events in the overall system AUTOSAR_CP_SWS_IntrusionDetectionSystemManager p. 21.

Below the CSM, the Crypto Interface (CryIf) abstracts the hardware- or software-specific access to multiple cryptographic driver objects as layer CryIf and unifies the job and key dispatching mechanism SWS_CryptoInterface p. 1. At the MCAL and driver layer, the Crypto Driver (Crypto) performs the actual computations in software or on Hardware Security Modules (HSM) [SWS_Crypto_91016]. The interaction of these layers ensures complete decoupling of the application software (SW-C) and communication modules from the hardware-specific crypto accelerators.

Interplay & Interaction Paths Between the Modules

The modules of the cluster are linked to one another via clearly defined control and data flow paths. Cryptographic jobs are primarily processed via the CSM. Application modules or BSW modules such as SecOC and KeyM initiate jobs via CSM services such as Csm_MacGenerate [SWS_Csm_00982], Csm_Encrypt [SWS_Csm_00984], Csm_AEADEncrypt [SWS_Csm_01023], Csm_SignatureGenerate [SWS_Csm_00992], Csm_Hash [SWS_Csm_00980], or Csm_RandomGenerate [SWS_Csm_01543]. The jobs are encapsulated in the standardized runtime structure Crypto_JobType [SWS_Csm_01013], which is controlled via operational modes (Crypto_OperationModeType such as CRYPTO_OPERATIONMODE_START, UPDATE, FINISH, or SINGLECALL) [SWS_Csm_00802]. The CSM passes the job to CryIf_ProcessJob [SWS_CryIf_91003], which forwards the call to the responsible crypto driver object.

The SecOC module secures PDU transfer between PduR and the communication bus. Upon reception of a secured PDU via SecOC_TpRxIndication [SWS_SecOC_00125], SecOC first retrieves freshness values via SecOC_GetRxFreshnessAuthData [SWS_SecOC_91006] and constructs the data to be authenticated according to the specification SecOcProtocol p. 19. For MAC verification, SecOC uses the CSM [SWS_SecOC_00012]. After successful verification, the authentic PDU is passed to the upper layers. If the verification fails, the result is captured in status SecOC_VerificationStatusType [SWS_SecOC_00160], [SWS_SecOC_91014]; interpretation: this failure is reported to the IdsM as a Security Event AUTOSAR_CP_SWS_IntrusionDetectionSystemManager p. 21.

In the Key Manager (KeyM), key and certificate updates are prepared and executed. During certificate verifications (e.g., via KeyM_VerifyCertificates [SWS_KeyM_00059] or KeyM_VerifyCertificateChain [SWS_KeyM_00061]), KeyM uses the cryptographic primitives of the CSM for signature verification and external time bases of the StbM for validity verification SWS_KeyManager p. 119. Key updates (KeyM_Update [SWS_KeyM_00052]) integrate user-specific handlers (KeyM_KH_Update [SWS_KeyM_00069], [SWS_KeyM_00055]), with resulting key bytes being activated in the crypto driver via Csm_KeyElementSet [SWS_Csm_00957] and Csm_JobKeySetValid [SWS_Csm_91027]. CryIf forwards key derivations and copy operations via CryIf_KeyDerive [SWS_CryIf_91009] and CryIf_KeyElementCopy [SWS_CryIf_91015], respectively, to driver functions such as Crypto_KeyElementCopyPartial [SWS_Crypto_91015].

The IdsM collects security events (Security Events, SEv) from BSW sensors (including SecOC) as well as application SW-Cs via interfaces such as IdsM_SetSecurityEvent [SWS_IdsM_91002] or IdsM_SetSecurityEventWithCount [SWS_IdsM_91018]. The events are buffered, qualified via filter chains (e.g., Block State Filter [SWS_IdsM_01020] or aggregation filter AUTOSAR_CP_SWS_IntrusionDetectionSystemManager p. 40), and finally forwarded via PduR [SWS_IdsM_91009], [SWS_IdsM_91010].

Synchronization, reentrancy and task contexts

The execution of cryptographic computations and security operations requires a strict separation of synchronous call paths and asynchronous task contexts. In the CSM and CryIf, execution behavior depends on the configuration of the crypto primitives: operations can execute in a synchronously blocking or asynchronous manner [SWS_Csm_00982], [SWS_CryIf_91003]. For asynchronous jobs, the crypto driver reports completion via CryIf_CallbackNotification [SWS_CryIf_91013], whereupon CSM serves the caller's registered callback function [SWS_SecOC_00012]. For interruptible or longer-running computations, the CSM provides the cancel function Csm_CancelJob [SWS_Csm_00968], which is delegated to the driver via CryIf_CancelJob [SWS_CryIf_91014].

Transmission in the SecOC module is decoupled in a time-controlled manner: in periodic cycles, SecOC_MainFunctionTx checks whether new authentic PDUs are pending for signing, calculates the authenticators, and initiates the PduR transmission [SWS_SecOC_00176]. In the IdsM, reported events are ingested with high performance in the sensor context (task or ISR) via IdsM_SetSecurityEvent [SWS_IdsM_91002], with the events initially being stored synchronously in configurable event buffers [SWS_IdsM_00701], [SWS_IdsM_00702]. The time-intensive filtering, context data processing, and timestamp enrichment via StbM or RTE are processed completely asynchronously in the context of the periodic IdsM_MainFunction SWS_IntrusionDetectionSystemManager p. 87, AUTOSAR_CP_SWS_IntrusionDetectionSystemManager p. 86.

The Key Manager distinguishes between time-critical and computationally intensive tasks: while standard status queries and callback orchestrations run in KeyM_MainFunction [SWS_KeyM_00074], execution in a preemptive background function KeyM_MainBackgroundFunction is intended for computationally intensive synchronous handler routines (such as KeyM_KH_Update) [SWS_KeyM_00075]. In multicore architectures, the CSM additionally supports partition-specific main functions and initializations [SWS_Csm_00646], SWS_CryptoInterface p. 1; interpretation: this partitioning corresponds to the assignment of dedicated hardware driver objects per processor core.

Typical lifecycles and operating modes

Cluster initialization follows a strict bottom-up dependency hierarchy. First, the hardware-related drivers are configured via Crypto_Init [SWS_Crypto_91016], followed by the interface CryIf [SWS_CryIf_91118] and the CSM via Csm_Init [SWS_Csm_00646]. Only afterwards may the dependent modules SecOC, KeyM, and IdsM be initialized. Through initialization, SecOC transitions from state SECOC_UNINIT to SECOC_INIT [SWS_SecOC_00162]. In KeyM, all configured certificates initially receive the status KEYM_CERTIFICATE_NOT_AVAILABLE [SWS_KeyM_00021], [SWS_KeyM_91003] before being read from the NvM or loaded and verified via KeyM_SetCertificate or diagnostics SWS_KeyManager p. 119.

At runtime, vehicle state transitions influence the operational mode of the IdsM: the Basic Software Manager (BswM) notifies the IdsM of state changes via IdsM_BswM_StateChanged [SWS_IdsM_91005]. These states control the Block State Filter [SWS_IdsM_01020], [SWS_IdsM_91017], which suppresses the forwarding of security events during certain operating phases (e.g., programming mode or sleep phases). In addition, reporting modes of events can be modified diagnostically via DCM (IdsM_Dcm_SetReportingMode_Start [SWS_IdsM_91008], [SWS_IdsM_91013]) and stored persistently in the NvM [SWS_IdsM_01700], [SWS_IdsM_01701].

When shutting down the ECU (shutdown), the modules are de-initialized in an orderly manner. SecOC_DeInit stops secure communication, flushes all internal buffers as well as variables, and transitions SecOC back to state SECOC_UNINIT [SWS_SecOC_00161]. When calling KeyM_Deinit [SWS_KeyM_00047], all cryptographic key material located in RAM is actively destroyed and overwritten with initial values for security reasons to prevent unauthorized readout in the quiescent state.

Error Handling, DET Tracing, and Degradation

The module cluster implements end-to-end mechanisms for detecting development errors (Development Error Tracer, DET) and runtime problems. All modules check their initialization and report DET errors upon uninitialized invocation, for example CRYIF_E_UNINIT in CryIf interfaces such as CryIf_RandomSeed [SWS_CryIf_91007], CryIf_CancelJob [SWS_CryIf_91014], CryIf_KeyDerive [SWS_CryIf_91009], or CryIf_CallbackNotification [SWS_CryIf_91013]. Likewise, invalid pointer parameters lead to DET reports, such as CRYPTO_E_PARAM_POINTER in Crypto_GetVersionInfo [SWS_Crypto_91001], while initialization errors in the CSM are reported with CSM_E_INIT_FAILED [SWS_Csm_00646].

In the event of overload or failure of crypto hardware objects, the driver signals the status CRYPTO_E_BUSY [SWS_CryIf_91003], [SWS_Csm_00957]. In such degradation scenarios, SecOC allows the configurable sending of unauthenticated replacement PDUs to the lower layers via SecOC_SendDefaultAuthenticationInformation to maintain vehicle availability [SWS_SecOC_91013]. In the IdsM, exhaustion of the configured event buffers triggers the internal security event SEV_IDSM_NO_EVENT_BUFFER_AVAILABLE [SWS_IdsM_00703]. If NvM persistency of modified IdsM parameters fails, the IdsM performs an automatic rollback to the previous state [SWS_IdsM_01702]. If an error occurs when setting keys in Csm_KeyElementSet, the status of the key element is considered undefined and must be validated via Csm_KeyGetStatus [SWS_Csm_91047] and CryIf_KeyGetStatus [SWS_CryIf_91012].
