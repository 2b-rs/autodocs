Context

The class ara::diag::DataTransferReadSession encapsulates all read variants of the data transfer within the diagnostic module of the AUTOSAR Adaptive Platform ([SWS_DM_01548]). In diagnostic sequences where data is transferred from the vehicle to the diagnostic tester—for example, in file-based transfers such as reading files ([SWS_DM_01314]) or reading file directories ([SWS_DM_01315])—the session object acts as a link between the diagnostic server instance and the application-specific transfer handlers.

The functional interaction involves at least three components:

  • Diagnostic Server instance: Receives incoming diagnostic requests (UDS services) and coordinates the transfer steps ([SWS_DM_01317], [SWS_DM_01318]).
  • DataTransferReadSession: Represents the active read session and links the registered handlers via specialized template constructors (AUTOSAR_AP_SWS_Diagnostics §7.7 “Realization of TransferData and RequestTransferExit”).
  • Handler classes: Provide the domain-specific read and completion logic (Read and Exit methods) that are called by the diagnostic server in the context of the session ([SWS_DM_01317], [SWS_DM_01318]).

Context diagram: Interaction between Diagnostic Server, DataTransferReadSession, and registered handlers. Sources: [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01548]

Lifecycle

The lifecycle and ownership concept of ara::diag::DataTransferReadSession enforces the unique binding to a single, well-defined transfer session ([SWS_DM_01548], AUTOSAR_AP_SWS_Diagnostics §8.10.4 “Class: DataTransferReadSession”):

  • Creation: The parameterless default constructor is deleted (delete according to [SWS_DM_01549]) to exclude uninitialized instances without handler binding. Creation takes place instead via template constructors that register vendor-specific handlers (AUTOSAR_AP_SWS_Diagnostics §7.7 “Realization of TransferData and RequestTransferExit”).
  • Exclusivity and non-copyability: To prevent multiple ownership and concurrency conflicts on the same transfer, both the copy constructor ([SWS_DM_01553]) and the copy assignment operator ([SWS_DM_01554]) are deleted. An instance of ara::diag::DataTransferReadSession is by definition a non-copyable single instance.
  • Move semantics: The class provides a move constructor ([SWS_DM_01551]) and a move assignment operator ([SWS_DM_01552]). Both are implemented as default and explicitly declared as noexcept, which enables an efficient and exception-safe transfer of ownership.
  • Destruction: The destructor is specified as noexcept=default ([SWS_DM_01550]) and ensures the clean release of session resources upon termination.

Usage Path

The regular operational flow of a read data transfer follows a fixed sequence of UDS services and interface calls:

  1. Initialization of the read session: Upon receipt of an initiating service request (such as RequestFileTransfer with read intent according to [SWS_DM_01314] or [SWS_DM_01315]), the Diagnostic Server instance instantiates the DataTransferReadSession via the appropriate template constructor, passing the specific read handler. Interpretation: The server instance is likely to maintain the lifetime of the session object for the duration of the read transfer.
  2. Data transfer (TransferData 0x36): As soon as the diagnostic tester successively requests data blocks by means of TransferData (0x36), the Diagnostic Server instance calls the Read method of the handler that was registered via the template constructor of the DataTransferReadSession ([SWS_DM_01317]). The read data is transmitted to the tester in the diagnostic response.
  3. Termination of the transfer (RequestTransferExit 0x37): After completion of the data blocks, the tester sends the service RequestTransferExit (0x37). The diagnostic server then calls the Exit method of the registered handler of the DataTransferReadSession ([SWS_DM_01318]).
  4. Session cleanup: After successful feedback of the exit call, the session object is destroyed ([SWS_DM_01550]), which completes the read cycle.

Sequence diagram: Call sequence of a read transfer from initialization via TransferData to RequestTransferExit. Sources: [SWS_DM_01317], [SWS_DM_01318], AUTOSAR_AP_SWS_Diagnostics §7.7 “Realization of TransferData and RequestTransferExit”

Error Scenarios

At the level of interface definition and control flow, the following error sources and integrity rules are relevant:

  • Invalid instantiation or copy attempts: Since the default constructor ([SWS_DM_01549]) as well as copy operations ([SWS_DM_01553], [SWS_DM_01554]) are deleted, any erroneous usage in the application code is already prevented at compile time by the compiler.
  • Exception safety during transfer phases: The noexcept guarantees for move operations ([SWS_DM_01551], [SWS_DM_01552]) and for destruction ([SWS_DM_01550]) ensure that stack unwinding and resource cleanups proceed without additional exceptions even in the event of an error.
  • Misconfiguration of handlers: If a registered handler does not provide the required signatures for Read or Exit, the processing of TransferData (0x36) ([SWS_DM_01317]) or RequestTransferExit (0x37) ([SWS_DM_01318]) fails, whereupon the diagnostic server aborts the transfer with a negative response code.
