Provides a sequential fixed-size container with type-safe bounds checking for AUTOSAR Adaptive.

The template class ara::core::Array serves as a sequential fixed-size container for elements of type T and adapts the behavior of std::array for AUTOSAR Adaptive Platform applications. Callers initialize the container with a fixed number of elements, manipulate contents via methods such as fill(), and access elements either unchecked via operator[] or bounds-checked via at() [SWS_CORE_01273]. As a safety-relevant constraint, an out-of-bounds access on at() triggers the specific violation IsoStdOutOfRangeViolation instead of std::out_of_range, whereas calls to front() or back() on empty instances fail as early as compile time [SWS_CORE_01267].

Context

The template class ara::core::Array encapsulates a sequential container with a size N statically fixed at compile time for elements of type T. It implements the standardized type std::array in the core module of the AUTOSAR Adaptive Platform and represents a type-safe abstraction for contiguous memory blocks. By providing standardized type aliases such as value_type ([SWS_CORE_01216]), size_type ([SWS_CORE_01214]), difference_type ([SWS_CORE_01215]), as well as pointer types ([SWS_CORE_01217], [SWS_CORE_01218]) and reference types ([SWS_CORE_01210], [SWS_CORE_01211]), the class acts as an interoperable peer for generic C++ algorithms and platform-internal data flows.

Lifecycle

The creation and destruction of an array instance follows the standard rules for aggregate and value types: the implicitly declared special member functions of the ISO C++ standard are used and not separately redeclared. The array owns its elements directly inline in the same memory area. The lifetime of the contained elements is therefore inextricably linked to the lifetime of the enclosing array object; dynamic allocation on the free store (heap) presumably does not take place, ensuring deterministic timing and memory behavior.

The container is always in a valid state and manages exactly N elements. Whether the array can hold elements or exists as a special case with N = 0 can be evaluated via empty() ([SWS_CORE_01264]), size() ([SWS_CORE_01262]), and max_size() ([SWS_CORE_01263]). Regarding concurrency, concurrent read accesses are likely safe without synchronization, whereas parallel mutating modifications require external coordination by the caller.

Usage Path

In typical use cases, ara::core::Array undergoes a sequence of initialization, element population, random or sequential access, and, if applicable, content swapping:

  • Initialization and population: The entire data buffer can be uniformly filled with a specified value via fill() ([SWS_CORE_01241]).
  • Random access: The unchecked subscript operator operator[] ([SWS_CORE_01265], [SWS_CORE_01266]) is available for performant access. When bounds checking is required, at() ([SWS_CORE_01273], [SWS_CORE_01274]) is used.
  • Boundary elements: Direct access to the first and last element is performed via front() ([SWS_CORE_01267], [SWS_CORE_01268]) and back() ([SWS_CORE_01269], [SWS_CORE_01270]).
  • Iteration: Traversing the container is performed forwards via begin() and end() ([SWS_CORE_01250], [SWS_CORE_01251], [SWS_CORE_01252], [SWS_CORE_01253]) or via const iterators such as cbegin() and cend() ([SWS_CORE_01258], [SWS_CORE_01259]). The iterator types are defined as basic pointers T* and const T*, respectively ([SWS_CORE_01212], [SWS_CORE_01213]). For reverse traversals, rbegin(), rend(), crbegin(), and crend() are available ([SWS_CORE_01254], [SWS_CORE_01255], [SWS_CORE_01256], [SWS_CORE_01257], [SWS_CORE_01260], [SWS_CORE_01261], [SWS_CORE_01219], [SWS_CORE_01220]).
  • Pointer access and swap: The underlying memory area can be passed as a pointer via data() ([SWS_CORE_01271], [SWS_CORE_01272]). Two equally sized arrays can be swapped using swap() ([SWS_CORE_01242]).

Sequence diagram: Typical call sequence for populating, bounds checking, and swapping array instances. Sources: [SWS_CORE_01241], [SWS_CORE_01273], [SWS_CORE_01242].

Error Scenarios

The specification defines strict preconditions and postconditions for boundary and error situations:

  • Bounds violation during indexed access: In at(), if the index n lies outside the array bounds (n >= size()), IsoStdOutOfRangeViolation is triggered instead of the C++ standard exception std::out_of_range ([SWS_CORE_01273], [SWS_CORE_01274]). Both overloads are declared with noexcept.
  • Access to empty instances: Calling front() or back() on an empty array (empty() == true, i.e. N = 0) mandatorily leads to a compile-time error ([SWS_CORE_01267], [SWS_CORE_01268], [SWS_CORE_01269], [SWS_CORE_01270]).
  • Undefined behavior with iterators: Dereferencing the iterator returned by begin() on an empty array constitutes undefined behavior ([SWS_CORE_01250], [SWS_CORE_01251]).
  • Special case pointer retrieval: If the size of the array is 0, the member function data() mandatorily returns nullptr ([SWS_CORE_01271], [SWS_CORE_01272]).
  • Conditional exception safety: The operation swap() is noexcept only if the type-related condition ara::core::is_nothrow_swappable<T>::value is satisfied ([SWS_CORE_01242]). Correspondingly, the noexcept property of fill() is determined via std::is_nothrow_copy_assignable<T>::value ([SWS_CORE_01241]).

The member function at of class ara::core::Array enables synchronous read and write access to an array element at the specified position n with implicit bounds checking [SWS_CORE_01273]. The function returns a mutable reference (reference) to the addressed element and can be evaluated at compile time (constexpr) [SWS_CORE_01273].

In case of error, when the requested index reaches or exceeds the container bound (n >= size()), the behavior deviates from the standard C++ container std::array: instead of an exception of type std::out_of_range, a IsoStdOutOfRangeViolation is triggered [SWS_CORE_01273]. Since the signature is declared as noexcept and classified as exception-safe, no regular C++ exceptions are thrown [SWS_CORE_01273]. Interpretation: Triggering this violation in a noexcept context is likely to lead directly to controlled termination of execution.

For read-only instances, there is the complementary const overload [SWS_CORE_01274], which provides a const reference. The same error semantics via IsoStdOutOfRangeViolation are also consistently applied in related containers such as ara::core::Vector ([SWS_CORE_01354], [SWS_CORE_01355]) and ara::core::StringView [SWS_CORE_02133].
