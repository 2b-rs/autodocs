Context

The template class ara::core::Array provides a standard-compliant adaptation of std::array in the Adaptive Platform. It encapsulates a fixed-size array N with elements of type T and avoids dynamic memory allocations at runtime. As a fundamental sequential container, ara::core::Array serves functional clusters and AUTOSAR applications as a type-safe data structure for passing payload data with a statically known number of elements.

The interface is closely aligned with the requirements of the C++ standard, but defines specific adaptations for the AUTOSAR runtime environment. These include typed interfaces for indexing, iterators, and memory queries. The type aliases for references and pointers ([SWS_CORE_01210], [SWS_CORE_01211], [SWS_CORE_01217], [SWS_CORE_01218]), indices ([SWS_CORE_01214], [SWS_CORE_01215]), and forward as well as reverse iterators ([SWS_CORE_01212], [SWS_CORE_01213], [SWS_CORE_01219], [SWS_CORE_01220]) ensure interoperability with standard algorithms and generic interfaces.

Lifecycle

As an aggregate type, ara::core::Array directly binds the contained elements to its own memory representation. The implicitly declared special member functions (such as default, copy, and move constructors as well as destructors) are not explicitly re-declared according to the specification, but follow the standard behavior of C++ arrays. The lifetime of all N elements is thus inextricably linked to the lifetime of the container instance.

Dimensioning is determined at compile time via the template parameter N. Size query methods such as size() ([SWS_CORE_01262]), max_size() ([SWS_CORE_01263]), and empty() ([SWS_CORE_01264]) are declared as constexpr and noexcept. Exchanging the content of two equally dimensioned instances is performed via swap() ([SWS_CORE_01242]). The exception safety of swap() conditionally depends on whether the element type T is specified as non-throwing via ara::core::is_nothrow_swappable<T>::value ([SWS_CORE_01242]). With regard to concurrency, ara::core::Array provides no internal synchronization; concurrent write accesses to the same instance must be synchronized by the application (Interpretation).

Usage Path

The typical usage of ara::core::Array is divided into initialization, sequential or random data processing, and passing to low-level interfaces:

  • Initialization and filling: The container can be initially populated or homogeneously written with a copy of a value via the method fill() ([SWS_CORE_01241]). The operation is noexcept provided that the element type is assignment-safe (std::is_nothrow_copy_assignable<T>::value).
  • Random and direct element access: For performant access without runtime checks, operator[] ([SWS_CORE_01265], [SWS_CORE_01266]) is available. The boundary elements can be referenced via front() ([SWS_CORE_01267], [SWS_CORE_01268]) and back() ([SWS_CORE_01269], [SWS_CORE_01270]).
  • Iterator-compliant processing: Algorithms can iterate over the sequence using forward iterators (begin() / end() acc. to [SWS_CORE_01250], [SWS_CORE_01251], [SWS_CORE_01252], [SWS_CORE_01253]), constant iterators (cbegin() / cend() acc. to [SWS_CORE_01258], [SWS_CORE_01259]), or reverse iterators (rbegin() / rend() / crbegin() / crend() acc. to [SWS_CORE_01254], [SWS_CORE_01255], [SWS_CORE_01256], [SWS_CORE_01257], [SWS_CORE_01260], [SWS_CORE_01261]).
  • C-API bridge: The method data() ([SWS_CORE_01271], [SWS_CORE_01272]) provides a direct pointer to the underlying contiguous memory segment, for example for passing to drivers or serialization routines.

Error Scenarios

In the areas of error handling and boundary value protection, ara::core::Array deviates from the ISO C++ standard in key points in order to maintain AUTOSAR-specific exception safety guidelines:

Call / Situation Condition Reaction / Specification
at(size_type n) n >= size() Triggering of a IsoStdOutOfRangeViolation instead of std::out_of_range ([SWS_CORE_01273], [SWS_CORE_01274]).
front() / back() empty() == true (d. h. N == 0) Calling on an empty array inevitably results in a compile-time error ([SWS_CORE_01267], [SWS_CORE_01268], [SWS_CORE_01269], [SWS_CORE_01270]).
begin() dereferencing empty() == true Dereferencing the returned iterator on an empty array leads to undefined behavior ([SWS_CORE_01250], [SWS_CORE_01251]).
data() size() == 0 Return of nullptr ([SWS_CORE_01271], [SWS_CORE_01272]).
operator[] n >= size() No bounds checking at runtime; leads to undefined behavior as in the C++ standard (interpretation).
