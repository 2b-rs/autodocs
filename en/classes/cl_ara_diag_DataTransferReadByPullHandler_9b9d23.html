Context

The class ara::diag::DataTransferReadByPullHandler serves the standardized handling of read data transfers initiated by diagnostic requests such as RequestReadFile or RequestReadDirectory AUTOSAR_AP_SWS_Diagnostics §8.10.2 “Class: DataTransferReadByPullHandler”, [SWS_DM_01506]. It acts as an interface between the diagnostic framework AraDiag and the actual application implementation.

The transfer concept is based on a pull mechanism: AraDiag sequentially requests data chunks from the application implementation in order to subsequently transfer them to the UDS client (diagnostic tester) [SWS_DM_01513]. The class encapsulates the application-specific provision of file or directory contents in the context of the UDS transfer services.

Context diagram: Integration of the handler between UDS client, AraDiag framework, and application. Sources: [SWS_DM_01506], AUTOSAR_AP_SWS_Diagnostics §8.10.2 “Class: DataTransferReadByPullHandler”

Lifecycle

Strict rules apply to instances of DataTransferReadByPullHandler regarding creation, ownership, and destruction:

  • Creation: The default constructor is declared as protected and noexcept=default [SWS_DM_01507]. Interpretation: Since the class contains pure virtual interface methods and the default constructor is protected, the application software likely implements and instantiates its own derived handler class.
  • Non-copyability: Both the copy constructor [SWS_DM_01509] and the copy assignment operator [SWS_DM_01512] are explicitly deleted (=delete). A handler is intended for exactly one single file transfer session (single file transfer session) and must not be copied AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.2 “Constructors”.
  • Moveability: Move constructor [SWS_DM_01508] and move assignment operator [SWS_DM_01511] are defined as noexcept=default AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1 “Special Member Functions”, so that a transfer of ownership is supported.
  • Destruction condition: The destructor is virtual and specified as noexcept=default [SWS_DM_01510]. A central invariant is that an instance must under no circumstances be destroyed before ExitRead() has been called [SWS_DM_01510], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.1.2 “Destructor”.
  • Concurrency: The virtual interface methods Read() and ExitRead() are classified as not thread-safe (not thread-safe) [SWS_DM_01513], [SWS_DM_01514].

Usage Path

The typical call sequence of a pull-based read data transfer comprises two main phases:

  1. Pull read loop: During the ongoing transfer, AraDiag repeatedly calls the method Read() on the handler [SWS_DM_01513]. In doing so, AraDiag passes a memory view response_data (of type ara::core::Span<const ara::core::Byte>) to a pre-allocated buffer as well as meta_info and a cancellation_handler. The application implementation compiles the content of the next data block and copies it into it up to the maximum size of the span [SWS_DM_01513].
  2. Chunk return: Read() returns a ara::core::Future<std::uint32_t>. The future is fulfilled with the number of bytes actually written to the buffer [SWS_DM_01513]. AraDiag embeds this payload in the positive UDS response directly after the blockSequenceCounter as transferResponseParameterRecord [SWS_DM_01513], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 “Read”.
  3. Session termination: As soon as all data has been transferred or the transfer is to be ended, AraDiag calls ExitRead() [SWS_DM_01514]. Passed are the termination reason (exit_type of type DataTransferExitType), vehicle manufacturer-specific parameters (transfer_request_parameter_record), as well as metadata and the cancellation handler [SWS_DM_01514].
  4. End of transaction: The application acknowledges the session end via a ara::core::Future<ara::core::Vector<ara::core::Byte>>. Upon positive acknowledgment, the data contained in the vector is placed after the service ID (SID) as transferResponseParameterRecord into the positive UDS response [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 “ExitRead”. Only after this call may the handler instance be destructed [SWS_DM_01510].

Sequence diagram: Call sequence for iterative pull reading and subsequent ExitRead. Sources: [SWS_DM_01513], [SWS_DM_01514], AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.1 “ExitRead”, AUTOSAR_AP_SWS_Diagnostics §8.10.2.1.3.2 “Read”

Error Scenarios

The specification defines clear requirements for error states and exceptional situations:

  • UDS error codes (NRC): If an error occurs while reading a data block or terminating the transfer, the respective future is not fulfilled regularly. Instead, the future must be completed with a matching Negative Response Code (NRC) from DiagUdsNrcErrc according to ISO 14229-1 as an error condition [SWS_DM_01513], [SWS_DM_01514]. AraDiag generates a negative UDS response message from this.
  • Cancellation handling: The parameters cancellation_handler allow the application to actively check via cancellation_handler.IsCanceled() whether the diagnostic conversation was canceled [SWS_DM_01513], [SWS_DM_01514]. Alternatively, a callback can be registered via cancellation_handler.SetNotifier() that is called when the conversation is canceled by the framework [SWS_DM_01513], [SWS_DM_01514].
  • Validity period of buffers: The buffer response_data passed by AraDiag in Read() as well as the transfer_request_parameter_record in ExitRead() have a limited lifetime. They are only valid until the associated promise is fulfilled or processing is canceled via the cancellation_handler [SWS_DM_01513], [SWS_DM_01514].
  • Premature destruction: If the instance of DataTransferReadByPullHandler is destroyed before ExitRead() has been executed, this represents a violation of the API contract conditions [SWS_DM_01510].
