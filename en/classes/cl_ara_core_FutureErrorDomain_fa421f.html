Defines the error domain for translation and exception handling of errors from Future and Promise.

The class ara::core::FutureErrorDomain represents the central error domain for asynchronous operations in Future and Promise and provides type aliases for error codes and exceptions [SWS_CORE_00431], [SWS_CORE_00432]. Via Message(), it handles the thread-safe translation of numeric error values into readable text messages without returning null pointers [SWS_CORE_00443]. Provided exceptions are enabled in the compiler, it also enables throwing typed FutureException objects [SWS_CORE_00444].

Context

The class ara::core::FutureErrorDomain forms the specific error domain for all error situations arising during asynchronous communication and synchronization via ara::core::Future and ara::core::Promise. It derives finally from the general base class ara::core::ErrorDomain and encapsulates the identification as well as the textual translation of domain-specific root causes. For a structured definition, the class provides the type alias Errc for enumeration FutureErrc [SWS_CORE_00431] as well as the alias Exception for the exception type FutureException [SWS_CORE_00432]. Through this bundling, the domain acts as a central link between asynchronous core components and the overarching AUTOSAR error handling model.

Context diagram: Classification of the error domain between asynchronous components, error codes, and exceptions. Sources: [SWS_CORE_00431], [SWS_CORE_00432], [SWS_CORE_00444]

Lifecycle

Initialization is performed via the default constructor, which is declared as constexpr and specified as exception-safe and thread-safe [SWS_CORE_00441]. This allows instantiation already at compile time or during the static initialization phase of the application. Since error domains in the AUTOSAR Adaptive ecosystem are typically maintained as long-lived global or static singleton instances, the instance is not subject to dynamic state transitions; the specification requires complete thread safety for all querying interfaces [SWS_CORE_00442], [SWS_CORE_00443].

Usage Path

During regular operation, an application rarely comes into direct contact with an instance of FutureErrorDomain. Instead, the domain is consulted when an instance of ara::core::ErrorCode needs to be formatted or evaluated. First, method Name() identifies the domain via a character-based name [SWS_CORE_00442]. For logging or error analysis, Message() translates a numeric error code of base type ErrorDomain::CodeType into a readable string [SWS_CORE_00443]. The interface ensures that the returned pointer is never nullptr [SWS_CORE_00443]. If the application does not process errors via return codes but employs exception handling, method ThrowAsException() converts a passed ErrorCode object directly into the associated FutureException [SWS_CORE_00444].

Sequence diagram: Resolution of error details and conditional triggering of exceptions via the error domain. Sources: [SWS_CORE_00443], [SWS_CORE_00444]

Error Scenarios

Failures within this class are limited to explicit error forwarding when exception handling is enabled. While Name(), Message(), and the constructor are declared as noexcept and are fully exception-safe [SWS_CORE_00441], [SWS_CORE_00442], [SWS_CORE_00443], ThrowAsException() is explicitly annotated with noexcept(false) and is not exception-safe, as it throws a FutureException by design [SWS_CORE_00444]. An essential precondition concerns the toolchain configuration: If C++ exceptions are disabled in the compiler, ThrowAsException() must not participate in overload resolution according to specification [SWS_CORE_00444]. Invalid or unrecognized error codes do not lead to a crash or null pointer in Message(), but are presumably mapped to generic placeholder texts, since the specification mandates a guaranteed return not equal to nullptr [SWS_CORE_00443].
