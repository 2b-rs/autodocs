Context

The class ara::diag::DynamicAccessListDiagServiceBuilder::ByteRange is defined as a nested class within ara::diag::DynamicAccessListDiagServiceBuilder ([SWS_DM_01182], AUTOSAR_AP_SWS_Diagnostics §8.15.2 “Class: ByteRange”). It represents a closed interval of single-byte values (closed range) and acts as an atomic pattern element (pattern element) when defining dynamic access lists (DynamicAccessList).

In the overall diagnostic system, the class interacts with two main partners:

  • Diagnostic application: Creates instances of ByteRange to specify the permitted byte values at specific positions of a diagnostic request, and reads configured limits if needed.
  • DynamicAccessListDiagServiceBuilder: Serves as the recipient of the range objects. Via member functions such as Add(ByteRange) ([SWS_DM_01177], AUTOSAR_AP_SWS_Diagnostics §8.15.1.2.3.1 “Add(ByteRange)”) or EndsWith(ByteRange) ([SWS_DM_01180], AUTOSAR_AP_SWS_Diagnostics §8.15.1.2.3.6 “EndsWith(ByteRange)”), the builder accepts ByteRange objects to incrementally construct the search or release pattern for incoming UDS services.

Lifecycle

ByteRange is modeled as a final C++ value type (class ByteRange final). The class encapsulates values exclusively and does not manage dynamic operating system or heap resources. Accordingly, the lifecycle is straightforward:

  • Creation: Instances are initialized via the parameterized constructor ByteRange(Byte min, Byte max) ([SWS_DM_01183], AUTOSAR_AP_SWS_Diagnostics §8.15.2.1.2.1 “ByteRange”). The parameters specify the lower and upper limits of the value range to be matched.
  • Copying and moving: The class possesses full value semantics. It provides a copy constructor ([SWS_DM_01184]) as well as a move constructor ([SWS_DM_01185], AUTOSAR_AP_SWS_Diagnostics §8.15.2.1.1.1 “Move Constructor”). Likewise, copy and move assignment operators ([SWS_DM_01186], [SWS_DM_01187]) exist, each of which is provided with a reference qualifier (&).
  • Destruction: The destructor ~ByteRange() ([SWS_DM_01188], AUTOSAR_AP_SWS_Diagnostics §8.15.2.1.1.2 “Destructor”) releases the object. Since no dynamic resources are allocated, cleanup is trivial.
  • Concurrency: Regarding thread safety, the specification distinguishes clearly between reading and modifying accesses: The constructors ([SWS_DM_01183], [SWS_DM_01184], [SWS_DM_01185]) as well as the inspectors GetMin() ([SWS_DM_01189]) and GetMax() ([SWS_DM_01190]) are declared as thread-safe. In contrast, the assignment operators ([SWS_DM_01186], [SWS_DM_01187]) and the destructor ([SWS_DM_01188]) are not thread-safe. A concurrent assignment or destruction on the same instance therefore requires external synchronization.

Usage Path

The typical usage of ByteRange comprises creation, optional verification of the limits, and integration into a diagnostic pattern:

  1. Define range: The application instantiates ByteRange specifying the desired byte limits via ByteRange(min, max) ([SWS_DM_01183]). If a single fixed byte value is to be checked, min and max are set to the same value.
  2. Query limits (optional): If needed, the configured threshold values can be read via GetMin() ([SWS_DM_01189]) and GetMax() ([SWS_DM_01190]).
  3. Configure pattern in builder: The ByteRange instance is passed to DynamicAccessListDiagServiceBuilder. Calling Add(ByteRange) ([SWS_DM_01177]) extends the pattern by another byte condition. By means of EndsWith(ByteRange) ([SWS_DM_01180]), it can be specified that the pattern terminates with this value range.

Sequence diagram: Typical call sequence for creating, querying, and integrating ByteRange into the builder. Sources: AUTOSAR_AP_SWS_Diagnostics §8.15.2.1.2.1 “ByteRange”, AUTOSAR_AP_SWS_Diagnostics §8.15.1.2.3.1 “Add(ByteRange)”.

Error Scenarios

The interface of ByteRange is characterized by maximum robustness and simplicity:

  • Freedom from exceptions: All constructors, assignment operators, inspectors, and the destructor are declared with noexcept and specified as exception-safe (exception safe) ([SWS_DM_01183] to [SWS_DM_01190]). Neither C++ exceptions are thrown nor are error codes (such as ara::core::Result) reported back.
  • Validity of interval limits: The specification does not define an error signal if min > max is passed during constructor invocation. Presumably, it is the responsibility of the applying component to ensure that min <= max is satisfied; Interpretation: An inverse interval would likely be treated as an unmatchable sub-range in the downstream matching process of the DynamicAccessListDiagServiceBuilder.
  • Concurrency conflicts: Since assignments ([SWS_DM_01186], [SWS_DM_01187]) and destruction ([SWS_DM_01188]) are not thread-safe, concurrent unprotected write and read accesses lead to data races, which must be avoided on the application side through mutexes or isolated instances.
