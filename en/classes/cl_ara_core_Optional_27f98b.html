Encapsulates an optionally present value in a type-safe manner in stack memory and enables state-dependent access.

The class ara::core::Optional provides a standard-compliant implementation of std::optional<T> to encapsulate values of type value_type in a type-safe and allocation-free manner on the stack [SWS_CORE_01102]. Applications check the engaged state via has_value() [SWS_CORE_01129] and access the content via value() or operators. Access to empty instances must be strictly avoided because, despite the noexcept declaration, it triggers the platform violation IsoStdBadOptionalAccessViolation [SWS_CORE_01131].

Context

The class ara::core::Optional provides a standard-compliant implementation of the container std::optional<T> for the Adaptive Platform. It serves as a type-safe wrapper for encapsulating an optional value of type value_type [SWS_CORE_01102]. Its use eliminates the need for error-prone sentinel values, special error flags, or dynamic memory allocations (such as null pointers) to denote absent data. The object is stored directly within the stack memory of the instance, thereby ensuring deterministic resource management and cache locality in the AUTOSAR runtime environment.

Lifecycle

An instance of ara::core::Optional is at any time in one of two discrete states: uninitialized (empty) or engaged with a value of type T. The empty initial state is entered via the default constructor [SWS_CORE_01103] or explicit initialization with nullopt_t [SWS_CORE_01104]. Initialization with a concrete value occurs either via copy and move constructors [SWS_CORE_01105], [SWS_CORE_01106], [SWS_CORE_01109], type-converting constructors [SWS_CORE_01110], [SWS_CORE_01111], or directly in-place via in_place_t [SWS_CORE_01107], [SWS_CORE_01108], completely avoiding temporary copies.

During runtime, the state can change multiple times: The methods emplace construct a new value directly in the memory of the object and discard any previously existing state [SWS_CORE_01119], [SWS_CORE_01120]. Likewise, assignment operators that are strictly bound to lvalues via ref-qualifiers & lead into the engaged state [SWS_CORE_01114], [SWS_CORE_01115], [SWS_CORE_01116], [SWS_CORE_01117], [SWS_CORE_01118]. Resetting to the empty state is performed deterministically via reset() [SWS_CORE_01136] or by assigning nullopt_t [SWS_CORE_01113]. Furthermore, two instances can efficiently swap their states and data contents via swap [SWS_CORE_01121]. Upon reaching the end of its life, the destructor destroys any contained object; its noexcept guarantee is directly linked to the destructibility of type T [SWS_CORE_01112].

Usage Path

The regular flow comprises verification of engagement and subsequent retrieval of the value. For state queries, has_value() [SWS_CORE_01129] and the explicit conversion operator operator bool [SWS_CORE_01128] are available.

If a value is present, it can be accessed via the dereference operators operator* ([SWS_CORE_01124], [SWS_CORE_01125], [SWS_CORE_01126], [SWS_CORE_01127]) or operator-> ([SWS_CORE_01122], [SWS_CORE_01123]). Additionally, the method value() enables qualified access to lvalues and rvalues ([SWS_CORE_01130], [SWS_CORE_01131], [SWS_CORE_01132], [SWS_CORE_01133]). If a predefined replacement value is to be used in the absence of an engaged value, value_or provides a direct fallback strategy ([SWS_CORE_01134], [SWS_CORE_01135]). After processing is complete, the container can be cleared via reset() if required [SWS_CORE_01136].

Error Scenarios

An erroneous access occurs when an empty instance is dereferenced or its value is requested without authorization. The access methods value(), operator*, and operator-> are declared as noexcept in AUTOSAR Adaptive, but trigger the violation IsoStdBadOptionalAccessViolation in the empty state ([SWS_CORE_01122], [SWS_CORE_01123], [SWS_CORE_01124], [SWS_CORE_01125], [SWS_CORE_01126], [SWS_CORE_01127], [SWS_CORE_01130], [SWS_CORE_01131], [SWS_CORE_01132], [SWS_CORE_01133]). Interpretation: Since the methods are declared as noexcept, triggering the IsoStdBadOptionalAccessViolation is likely not propagated as a catchable standard exception, but presumably leads to immediate program termination via the platform-specific violation mechanism. Callers must therefore mandatorily validate the engagement state before reading.

Another error scenario concerns exception handling during type construction: Constructors, assignment operators, swap, and emplace have conditional noexcept specifications that depend on whether the corresponding type operations of T are themselves declared as noexcept ([SWS_CORE_01105], [SWS_CORE_01114], [SWS_CORE_01119], [SWS_CORE_01121]). The fallback method value_or is also explicitly designated as not exception safe (\"not exception safe\") ([SWS_CORE_01134], [SWS_CORE_01135]), so that errors occurring during the creation of the return value are passed on to the caller.
