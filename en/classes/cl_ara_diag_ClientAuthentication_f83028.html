Serves the application to report authentication states and active user roles to the Diagnostic Server.

The interface allows the application to inform the Diagnostic Server about the authentication status as well as active user roles of a diagnostic client [SWS_DM_01132]. Via calls such as Authenticate or OverrideDefaultRoles, state transitions are controlled and handles for managing dynamic access lists are provided [SWS_DM_01206]. State changes as a result of timeouts can be monitored asynchronously via a notifier. Since the class is not thread-safe and does not allow copies, access within the application must be synchronized.

Context

The class ara::diag::ClientAuthentication serves as a central interface for the application to notify the Diagnostic Server instance about authentication states and the currently authenticated user roles [SWS_DM_01132], SWS Diagnostics, p. 129. Three key parties are involved in this interaction:

  • Application: Performs authentication checks—either using interfaces of the Diagnostic Server or via application-specific mechanisms—and transmits user roles to the Diagnostic Server [SWS_DM_01142].
  • Diagnostic Server / Diagnostic Manager: Manages diagnostic sessions and enforces access rights to diagnostic resources based on roles and authentication status [SWS_DM_01206].
  • Diagnostic Client: An external tester or SOVD client that directs diagnostic requests to the ECU [SWS_DM_01210], [SWS_DM_01470].

The number of instances of ClientAuthentication is determined by the model element DiagnosticExternalAuthenticationIdentification SWS Diagnostics, p. 129. This element allows configuring authentication for a client with a fixed source address or via an address range if the final source address is not yet known at compile time SWS Diagnostics, p. 129. Interpretation: Mapping of diagnostic clients to concrete instances of ClientAuthentication takes place at runtime based on these source address ranges. In the case of SOVD clients, the Diagnostic Server passes a ClientAuthentication object directly to the application during authorization token validation via ara::diag::SovdAuthorization::ValidateAuthorization [SWS_DM_01470].

Context diagram: Interaction partners of the authentication interface. Sources: [SWS_DM_01132], [SWS_DM_01202], [SWS_DM_01470], SWS Diagnostics, p. 129

Lifecycle

The application receives an instance of ClientAuthentication via overloaded methods of ara::diag::ExternalAuthentication::Get [SWS_DM_01202] or in the context of SOVD token validation [SWS_DM_01470]. The class features strict ownership semantics: copy constructor [SWS_DM_01139] and copy assignment operator [SWS_DM_01140] are deleted (=delete). Move operations (move constructor [SWS_DM_01137] and move assignment operator [SWS_DM_01138]) are predefined as default and declared as noexcept. The destructor is likewise noexcept [SWS_DM_01136]. All member functions as well as the destructor are not thread-safe (not thread-safe) [SWS_DM_01136], [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143], [SWS_DM_01144].

The authentication status is represented via the enumeration type DiagnosticAuthState [SWS_DM_01133]:

  • kDeAuthenticated (0x00): No diagnostic client is authenticated. At system startup, the client is in this state by default [SWS_DM_01205]. Here, those roles (DiagnosticAuthRole) whose attribute isDefault is configured to TRUE are considered default roles [SWS_DM_01204], [SWS_DM_01134]. Via OverrideDefaultRoles, these default roles can be temporarily overridden for a defined timeout [SWS_DM_01141], [SWS_DM_01209].
  • kAuthenticated (0x01): A diagnostic client is authenticated. This state is reached by calling Authenticate, thereby activating the passed user roles in the Diagnostic Server [SWS_DM_01142], [SWS_DM_01206].

An automatic state transition from kAuthenticated back to kDeAuthenticated is triggered if a client in the default session sends no further requests after the last transmission confirmation (TransmitConfirmation) and the inactivity time expires [SWS_DM_01210], or if an S3 timeout occurs [SWS_DM_01144], [SWS_DM_02077].

State diagram: Lifecycle and state transitions of client authentication. Sources: [SWS_DM_01133], [SWS_DM_01204], [SWS_DM_01205], [SWS_DM_01206], [SWS_DM_01209], [SWS_DM_01210]

Usage Path

The regular sequence for managing client authentication comprises the following steps:

  1. Register notifier: The application registers a callback function of type ClientAuthenticationSetNotifier (std::function<void(DiagnosticAuthState)>) with SetNotifier [SWS_DM_01144], [SWS_DM_02077]. This informs it when status changes occur—such as the transition to kDeAuthenticated due to inactivity or an S3 timeout [SWS_DM_01144]. A renewed call overwrites the previously set notifier [SWS_DM_01144].
  2. Query state: Via the method GetState(), the application can synchronously query the current authentication state of the client [SWS_DM_01143].
  3. Report authentication: As soon as authentication has been successfully completed, the application calls Authenticate with the user roles to be activated (ara::core::Vector<DiagnosticAuthRole>) [SWS_DM_01142], [SWS_DM_01134]. The Diagnostic Server sets the state to kAuthenticated and returns a ClientAuthenticationHandle [SWS_DM_01206].
  4. Manage access rights: Via the obtained ClientAuthenticationHandle, the application can configure the dynamic access list (DynamicAccessList) for the client [SWS_DM_01213], SWS Diagnostics, p. 132. At the same time, using this handle refreshes the client's inactivity time window SWS Diagnostics, p. 133.

If the client is in state kDeAuthenticated, the application can instead call OverrideDefaultRoles(defaultRoles, timeout) to temporarily activate alternative default roles; on success, this call also returns a ClientAuthenticationHandle [SWS_DM_01141], [SWS_DM_01209].

Sequence diagram: Call and notification flow during authentication. Sources: [SWS_DM_01142], [SWS_DM_01144], [SWS_DM_01206], [SWS_DM_01210]

Error Scenarios

The methods Authenticate, OverrideDefaultRoles, and GetState return their return values encapsulated in ara::core::Result and are specified as exception-safe (exception safe) and noexcept [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143]. In the event of an error, the following standardized error code is reported:

  • DiagErrc::kServiceNotAvailable: Occurs when the call cannot be executed because essential functionalities of the Diagnostic Manager are currently unavailable [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143]. This error has rollback semantics (rollback_semantics), ensuring that no incomplete state changes remain [SWS_DM_01141], [SWS_DM_01142], [SWS_DM_01143].

No standardized error codes are defined for SetNotifier [SWS_DM_01144]. As an essential precondition, OverrideDefaultRoles requires that the client is in state kDeAuthenticated at the time of the call [SWS_DM_01209].

Usage and Invocation

The function ara::diag::ClientAuthentication::Authenticate is called by an application to notify the Diagnostic Server instance of the successful authentication of a diagnostic client [SWS_DM_01142]. This can occur after authentication via the interfaces of the Diagnostic Server or via application-own mechanisms [SWS_DM_01142].

As an input parameter, the function accepts userRoles (of type ara::core::Vector<DiagnosticAuthRole>). Upon a successful call, the instance's authentication status transitions to kAuthenticated, and the passed user roles are firmly adopted [SWS_DM_01206]. As a return value, it provides a ara::core::Result<ClientAuthenticationHandle> [SWS_DM_01142]. Since a result object is provided immediately, the processing is likely to take place synchronously in the calling context.

Error Handling and Concurrency

The method is declared as noexcept and is considered exception safe (exception safe) [SWS_DM_01142]. If an error occurs because fundamental functionalities of the Diagnostic Manager are not available at invocation time, the operation fails with rollback semantics and returns DiagErrc::kServiceNotAvailable in the result object [SWS_DM_01142].

Regarding concurrency, the method is explicitly specified as not thread-safe [SWS_DM_01142]. Parallel calls on the same ClientAuthentication object are therefore not permitted and must be synchronized by the application.

Interaction and Lifecycle

The received ClientAuthenticationHandle allows the application to define or extend a DynamicAccessList for the authenticated client [SWS_DM_01142]. In addition, the call starts or references the inactivity monitoring of the client: if no further UDS request occurs after successful authentication in the default session state for the duration of authenticationTimeout, the Diagnostic Server instance automatically resets the client to kDeAuthenticated [SWS_DM_01210]. To prevent this timeout, the application can update the timer via method Refresh of the handle [SWS_DM_01155].

This function is called by the Diagnostic Server instance as soon as the authentication status of a client changes [SWS_DM_01144]. This enables the application to respond immediately to state transitions, for example when an automatic transition to state kDeAuthenticated occurs after an S3 server timeout [SWS_DM_01211] or a timeout due to client inactivity occurs [SWS_DM_01210].
                      


                      Error Handling and Return Value
                      

                      The function returns a ara::core::Result<void> and is declared as noexcept as well as exception safe [SWS_DM_01144]. No standardized error codes are specified [SWS_DM_01144]; presumably the Result object always returns success (void) in regular operation.
                      


                      Concurrency and Interaction
                      

                      Regarding thread safety, the method is specified as "not thread-safe" [SWS_DM_01144]. Calls on the same instance must therefore not be made unprotected from concurrent threads. In addition, an overwrite behavior applies to the registration: a subsequent call to SetNotifier completely replaces the previously registered notifier [SWS_DM_01144]. This behavior complies with the unified registration pattern in Diagnostic Management, as defined analogously for [SWS_DM_00615] (CancellationHandler), [SWS_DM_00745] (Indicator), and [SWS_DM_00755] (OperationCycle).
