class ara::log::Logger

[SWS_LOG_00172] Upstream: RS_LT_00003, RS_LT_00046

class Logger final {...};

Represents a logger context. The Logging framework defines contexts which can be seen as logger instances within one Application process or process scope. The contexts have the following properties: • Context ID • Description of the Context ID • Default log level A context will be automatically registered against the Logging backend during creation phase, as well as automatically deregistered during process shutdown phase. So the end user does not care for the objects life time. To ensure such housekeeping functionality, a strong ownership of the logger instances needs to be ensured towards the Logging framework. This means that the Application process are not supposed to call the Logger constructor themselves. The user is not allowed to create a Logger object by himself. Logger context needs to be created by one of the ara::log::CreateLogger functions.

Encapsulates a logging context for thread-safe recording of formatted or modeled log messages.

The class ara::log::Logger represents a context for recording log messages within an application process via temporary streams or modeled message formats [SWS_LOG_00064]. Because the default constructor is deleted, creation and lifecycle management are handled entirely by the logging framework [SWS_LOG_00259]. Before the time-consuming preparation of message data, the currently active reporting severity can be queried. All interfaces of the class are specified as thread-safe and allow synchronization-free invocation from multiple threads.

Context

The class ara::log::Logger represents a logger context within an application process or process area in module log. Such a context encapsulates a specific context ID, an associated description, and a default log level. Application developers interact with logger instances to pass log messages to the logging framework either via stream objects such as LogStream [SWS_LOG_00064] or as structured, modeled messages [SWS_LOG_00204]. The instances act as intermediaries between application-internal threads and the logging backend.

Context diagram: Integration of the logger between application, logging framework, and LogStream. Sources: [SWS_LOG_00064], [SWS_LOG_00259].

Lifecycle

The management of instances is subject to strict ownership by the logging framework. To ensure automatic registration with the logging backend upon creation and deregistration during application process shutdown, the default constructor is deleted [SWS_LOG_00259]. Applications must not and cannot instantiate Logger objects directly, but must instead use the creation functions ara::log::CreateLogger. Destruction and deallocation take place via the destructor [SWS_LOG_00260], which is controlled by the logging framework so that users do not have to manage the lifetime.

Regarding concurrency, all access methods are specified as thread-safe (thread-safe), including [SWS_LOG_00070], [SWS_LOG_00255], and [SWS_LOG_00260]. As a result, multiple concurrent threads can use the same logger context simultaneously without requiring additional synchronization mechanisms on the application side.

Usage Path

Typical usage of a logger includes checking the current configuration, adjusting thresholds, and issuing messages:

  • Checking output permission: Before costly preparations of log data, IsEnabled can be used to query whether a desired log level is actively reported [SWS_LOG_00070].
  • Configuration: The minimum reporting threshold of a logger instance can be reconfigured at runtime via SetThreshold [SWS_LOG_00255].
  • Stream-based logging: Via specific methods for individual severity levels—LogFatal [SWS_LOG_00064], LogError [SWS_LOG_00065], LogWarn [SWS_LOG_00066], LogInfo [SWS_LOG_00067], LogDebug [SWS_LOG_00068], or LogVerbose [SWS_LOG_00069]—as well as via the dynamic WithLevel [SWS_LOG_00131], a LogStream object is created. This object accepts data via the operator <<. Typically, the lifetime of the stream object ends with the semicolon of the statement [SWS_LOG_00064].
  • Modeled messages: Alternatively, typed and modeled messages can be passed directly with Log [SWS_LOG_00204] or, by specifying attributes, with LogWith [SWS_LOG_00133].

Sequence diagram: Typical sequence for threshold checking and stream-based logging. Sources: [SWS_LOG_00070], [SWS_LOG_00067], [SWS_LOG_00064].

Error Scenarios

The interfaces of the class are largely specified as noexcept and exception-safe (exception safe), which minimizes unexpected runtime interruptions [SWS_LOG_00070], [SWS_LOG_00255]. Nevertheless, formal error conditions and edge cases exist:

  • Incorrect model parameters: If Log is called with arguments that do not match the specification of the modeled message, the C++ program is ill-formed (ill-formed) and fails at compile time [SWS_LOG_00204].
  • Missing attribute properties: If the tuple for LogWith contains types that do not satisfy the required attribute criteria, the function does not participate in overload resolution [SWS_LOG_00133]. The exclusion is presumably performed via SFINAE or concepts.
  • Exception safety during destruction: The destructor ~Logger is declared as not exception safe [SWS_LOG_00260]. This is likely attributable to the fact that errors may occur during deregistration at the logging backend that must not be propagated via exceptions.
