Context

The class ara::idsm::EventReporter is the central link of an Adaptive application for detecting and forwarding security-relevant events to the Intrusion Detection System Manager (IdsM) according to [SWS_AIDSM_10101]. In a modern vehicle architecture, functional software components monitor their respective domains for security-relevant anomalies, communication violations, or unauthorized access attempts. If an application detects such a security event, EventReporter handles the standardized reporting to the security subsystem.

Interaction takes place via a port of interface type SecurityEventReportInterface formally defined in the software architecture model. When the instance is created, this port is addressed via an ara::core::InstanceSpecifier [SWS_AIDSM_10301]. As a result, the class acts as a typed interface between the application-specific logic and the vehicle-wide IdsM stack.

Lifecycle

An object of class ara::idsm::EventReporter is instantiated on the application side. The parameterized constructor expects a reference to a ara::core::InstanceSpecifier and is declared as noexcept and thread-safe [SWS_AIDSM_10301]. During initialization, the object binds to the port defined in the AUTOSAR model. After successful construction, this port binding remains unchanged; subsequent reconfiguration is not provided for at the API level (Interpretation: An EventReporter remains firmly bound to the configured port throughout its entire lifecycle).

In terms of concurrency, the class is designed for industrial multithreading use: Both the creation [SWS_AIDSM_10301] and all variants of the reporting function ReportEvent are specified as fully thread-safe ([SWS_AIDSM_10302] to [SWS_AIDSM_10307]). Multiple threads of a process can therefore call the same instance in parallel and without external synchronization mechanisms. The object follows the regular RAII pattern and deterministically releases its platform resources upon leaving scope.

Usage Path

The regular workflow comprises instantiating the reporter during system startup or component initialization followed by repeated event reports during ongoing operation:

  1. Instantiate reporter: Based on the model-specific InstanceSpecifier, the instance is set up via the constructor EventReporter(const ara::core::InstanceSpecifier&) [SWS_AIDSM_10301].
  2. Capture event data: If a security-relevant deviation occurs, the application selects the appropriate overload of ReportEvent, depending on which metadata is available for the event.
  3. Report event: By calling ReportEvent, the counters, context information, and timestamps are transmitted to the IdsM.

Sequence diagram: Typical sequence from construction to event reporting to the IdsM. Sources: [SWS_AIDSM_10101], [SWS_AIDSM_10301], [SWS_AIDSM_10304]

The interface provides a total of six graduated overloads that cover all variants of the modeled event parameters:

  • Without context: Pure counter events without payload are passed via ReportEvent(const CountType count = 1) [SWS_AIDSM_10302]. If a specific capture timestamp is to be recorded in addition, the signature with TimestampType is available [SWS_AIDSM_10303].
  • With context data: Additional diagnostic or frame data is transmitted via ContextDataType, either without a timestamp [SWS_AIDSM_10304] or with a timestamp [SWS_AIDSM_10305].
  • With versioned context data: If the schema of the context data is subject to evolutionary changes, the signatures accept VersionedContextDataType, likewise without a timestamp [SWS_AIDSM_10306] as well as with a timestamp [SWS_AIDSM_10307].

In all signatures, the parameter count has the default value 1, so that a single incident can be reported without an explicit counter specification.

Error Scenarios

The API of ara::idsm::EventReporter is designed defensively and strictly non-blocking for real-time-critical paths. All methods—both the constructor [SWS_AIDSM_10301] and all six variants of ReportEvent ([SWS_AIDSM_10302] to [SWS_AIDSM_10307])—are declared as noexcept and have no return value (void).

This results in key architectural constraints:

  • Neither C++ exceptions are thrown nor are ara::core::Result error codes returned at the call interface.
  • A precondition for correct functioning is the provision of a valid InstanceSpecifier configured in the AUTOSAR model during object creation.
  • Possible errors during buffering, overload of the transmission channel, or unavailability of the IdsM service cannot be communicated synchronously to the caller (Interpretation: Internal buffer overflows or failures of the IdsM communication are logged internally in the platform stack or discarded in order not to block the calling real-time application).

<h4>Context</h4>
<p>The class <code>ara::idsm::EventReporter</code> is the central link of an Adaptive application for detecting and forwarding security-relevant events to the Intrusion Detection System Manager (IdsM) according to <a class="spec-record-ref" data-req="SWS_AIDSM_10101" href="../spec/record.html?id=SWS_AIDSM_10101">[SWS_AIDSM_10101]</a>. In a modern vehicle architecture, functional software components monitor their respective domains for security-relevant anomalies, communication violations, or unauthorized access attempts. If an application detects such a security event, <code>EventReporter</code> handles the standardized reporting to the security subsystem.</p>
<p>Interaction takes place via a port of interface type <code>SecurityEventReportInterface</code> formally defined in the software architecture model. When the instance is created, this port is addressed via an <code>ara::core::InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>. As a result, the class acts as a typed interface between the application-specific logic and the vehicle-wide IdsM stack.</p>

<h4>Lifecycle</h4>
<p>An object of class <code>ara::idsm::EventReporter</code> is instantiated on the application side. The parameterized constructor expects a reference to a <code>ara::core::InstanceSpecifier</code> and is declared as <code>noexcept</code> and thread-safe <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>. During initialization, the object binds to the port defined in the AUTOSAR model. After successful construction, this port binding remains unchanged; subsequent reconfiguration is not provided for at the API level (Interpretation: An <code>EventReporter</code> remains firmly bound to the configured port throughout its entire lifecycle).</p>
<p>In terms of concurrency, the class is designed for industrial multithreading use: Both the creation <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a> and all variants of the reporting function <code>ReportEvent</code> are specified as fully thread-safe (<a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a> to <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>). Multiple threads of a process can therefore call the same instance in parallel and without external synchronization mechanisms. The object follows the regular RAII pattern and deterministically releases its platform resources upon leaving scope.</p>

<h4>Usage Path</h4>
<p>The regular workflow comprises instantiating the reporter during system startup or component initialization followed by repeated event reports during ongoing operation:</p>
<ol>
<li><strong>Instantiate reporter:</strong> Based on the model-specific <code>InstanceSpecifier</code>, the instance is set up via the constructor <code>EventReporter(const ara::core::InstanceSpecifier&amp;)</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a>.</li>
<li><strong>Capture event data:</strong> If a security-relevant deviation occurs, the application selects the appropriate overload of <code>ReportEvent</code>, depending on which metadata is available for the event.</li>
<li><strong>Report event:</strong> By calling <code>ReportEvent</code>, the counters, context information, and timestamps are transmitted to the IdsM.</li>
</ol>

<p>The interface provides a total of six graduated overloads that cover all variants of the modeled event parameters:</p>
<ul>
<li><em>Without context:</em> Pure counter events without payload are passed via <code>ReportEvent(const CountType count = 1)</code> <a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a>. If a specific capture timestamp is to be recorded in addition, the signature with <code>TimestampType</code> is available <a class="spec-record-ref" data-req="SWS_AIDSM_10303" href="../spec/record.html?id=SWS_AIDSM_10303">[SWS_AIDSM_10303]</a>.</li>
<li><em>With context data:</em> Additional diagnostic or frame data is transmitted via <code>ContextDataType</code>, either without a timestamp <a class="spec-record-ref" data-req="SWS_AIDSM_10304" href="../spec/record.html?id=SWS_AIDSM_10304">[SWS_AIDSM_10304]</a> or with a timestamp <a class="spec-record-ref" data-req="SWS_AIDSM_10305" href="../spec/record.html?id=SWS_AIDSM_10305">[SWS_AIDSM_10305]</a>.</li>
<li><em>With versioned context data:</em> If the schema of the context data is subject to evolutionary changes, the signatures accept <code>VersionedContextDataType</code>, likewise without a timestamp <a class="spec-record-ref" data-req="SWS_AIDSM_10306" href="../spec/record.html?id=SWS_AIDSM_10306">[SWS_AIDSM_10306]</a> as well as with a timestamp <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>.</li>
</ul>
<p>In all signatures, the parameter <code>count</code> has the default value <code>1</code>, so that a single incident can be reported without an explicit counter specification.</p>

<h4>Error Scenarios</h4>
<p>The API of <code>ara::idsm::EventReporter</code> is designed defensively and strictly non-blocking for real-time-critical paths. All methods—both the constructor <a class="spec-record-ref" data-req="SWS_AIDSM_10301" href="../spec/record.html?id=SWS_AIDSM_10301">[SWS_AIDSM_10301]</a> and all six variants of <code>ReportEvent</code> (<a class="spec-record-ref" data-req="SWS_AIDSM_10302" href="../spec/record.html?id=SWS_AIDSM_10302">[SWS_AIDSM_10302]</a> to <a class="spec-record-ref" data-req="SWS_AIDSM_10307" href="../spec/record.html?id=SWS_AIDSM_10307">[SWS_AIDSM_10307]</a>)—are declared as <code>noexcept</code> and have no return value (<code>void</code>).</p>
<p>This results in key architectural constraints:</p>
<ul>
<li>Neither C++ exceptions are thrown nor are <code>ara::core::Result</code> error codes returned at the call interface.</li>
<li>A precondition for correct functioning is the provision of a valid <code>InstanceSpecifier</code> configured in the AUTOSAR model during object creation.</li>
<li>Possible errors during buffering, overload of the transmission channel, or unavailability of the IdsM service cannot be communicated synchronously to the caller (Interpretation: Internal buffer overflows or failures of the IdsM communication are logged internally in the platform stack or discarded in order not to block the calling real-time application).</li>
</ul>
