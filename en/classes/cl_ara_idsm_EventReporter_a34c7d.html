Enables applications to report security events with optional context data to the IdsM in a thread-safe manner.

Class ara::idsm::EventReporter serves in AUTOSAR Adaptive as the central programming interface for reporting security events to the Intrusion Detection System Manager [SWS_AIDSM_10101]. After instantiation via a ara::core::InstanceSpecifier for the modeled port, applications flexibly transmit incidents with a counter, timestamp, or (versioned) context data [SWS_AIDSM_10301]. All methods are explicitly specified as thread-safe and allow parallel usage from multiple application threads. Since all interfaces are provided with noexcept, transmission errors are not reported to the caller via C++ exceptions.

Context

Class ara::idsm::EventReporter serves in the AUTOSAR Adaptive Platform as the primary programming interface for functional applications to report security-relevant events (security events) to the Intrusion Detection System Management (IdsM) [SWS_AIDSM_10101]. Within the platform architecture, the class assumes an intermediary role between application-specific detection logic and platform-wide security services. Direct interaction partners include functional software components that identify anomalies or security-critical incidents, the mediator instance EventReporter, and the IdsM service of the Adaptive Platform, which is responsible for capturing, filtering, and further processing security events.

Context diagram: Integration of EventReporter between the reporting application and the IdsM. Sources: [SWS_AIDSM_10101], [SWS_AIDSM_10301]

Lifecycle

Creation of an EventReporter object takes place via its constructor by passing an identifier of type ara::core::InstanceSpecifier [SWS_AIDSM_10301]. This binds the instance to a port of type SecurityEventReportInterface modeled in the manifest [SWS_AIDSM_10301]. Ownership lies with the utilizing application; long-lived retention across the entire runtime of the component is typically likely to be expedient to avoid repeated bindings to the port. For concurrency, the specification guarantees complete thread safety: Both construction and all methods for reporting events are designed to be thread-safe [SWS_AIDSM_10301], [SWS_AIDSM_10302]. As a result, multiple application threads can use the same reporter instance in parallel without requiring external synchronization measures.

Usage Path

The regular workflow comprises instantiating the reporter and subsequently reporting incidents via method ReportEvent. After initialization with the matching ara::core::InstanceSpecifier [SWS_AIDSM_10301], the application selects one of the provided overloads depending on the event type and level of detail of the available context information:

  • Reporting without context: For simple events without accompanying data, the base overload is used, which optionally transmits an event count (count, default value 1) [SWS_AIDSM_10302].
  • Reporting with timestamp: If the event is to be provided with an explicit acquisition timestamp, a variant with TimestampType is available [SWS_AIDSM_10303].
  • Reporting with context data: To pass diagnostic data or incident details, ReportEvent can be called with parameters of type ContextDataType, optionally without or with an explicit timestamp [SWS_AIDSM_10304], [SWS_AIDSM_10305].
  • Reporting with versioned context data: Provided that the communication format is defined in a structured or version-dependent manner, overloads with VersionedContextDataType—likewise with or without a timestamp—offer the corresponding interface [SWS_AIDSM_10306], [SWS_AIDSM_10307].

As soon as ReportEvent is called, the reporter forwards the data to the IdsM subsystem and returns immediately to the application.

Sequence diagram: Typical interaction sequence from reporter creation to event reporting. Sources: [SWS_AIDSM_10301], [SWS_AIDSM_10304]

Error Scenarios

An essential precondition for sending reports is the successful construction of EventReporter with a valid port identifier stored in the platform model [SWS_AIDSM_10301]. Regarding error handling and exception safety, all interfaces of the class exhibit a particular characteristic: The constructor and without exception all ReportEvent overloads are declared as noexcept [SWS_AIDSM_10301], [SWS_AIDSM_10302], [SWS_AIDSM_10303], [SWS_AIDSM_10304], [SWS_AIDSM_10305], [SWS_AIDSM_10306], [SWS_AIDSM_10307]. Neither are C++ exceptions thrown nor are error objects such as ara::core::Result returned. If infrastructural issues like buffer bottlenecks or service failures occur during transmission to the IdsM, these are likely handled, discarded, or logged internally within the platform service so as not to block the reporting application.
