Defines the SecOC FVM error domain and maps specific error codes to message texts and exceptions.

The class apext::com::secoc::ComSecOcFvmErrorDomain encapsulates the error domain for the Freshness Value Manager in the SecOC communication module of AUTOSAR Adaptive [SWS_CM_12514]. It maps error codes from ComSecOcFvmErrc to descriptive texts and enables their conversion into ComSecOcFvmException exceptions. Access is typically performed process-wide via the helper function GetComSecOcFvmErrorDomain() [SWS_CM_12521]. If compiler exceptions are disabled, the method for exception generation is automatically removed from overload resolution.

Context

The class apext::com::secoc::ComSecOcFvmErrorDomain defines the error domain for the Freshness Value Manager (FVM) in the context of secure onboard communication (SecOC) for Adaptive AUTOSAR Communication Management [SWS_CM_12514] (AUTOSAR_AP_SWS_CommunicationManagement §C.2.3 “Class: ComSecOcFvmErrorDomain”). As a final subclass of ara::core::ErrorDomain, it integrates domain-specific FVM error states into the platform-wide error handling model of AUTOSAR Adaptive.

To encapsulate error identifiers and exception types, the class provides two central type aliases: via Errc, the error code enum ComSecOcFvmErrc is referenced [SWS_CM_12515] (AUTOSAR_AP_SWS_CommunicationManagement §C.2.3.1 “Public Member Types”), while the type alias Exception specifies the specialized exception class ComSecOcFvmException [SWS_CM_12516] (AUTOSAR_AP_SWS_CommunicationManagement §C.2.3.1 “Public Member Types”). Standardized access to the instance of this error domain is performed process-wide via the free function apext::com::secoc::GetComSecOcFvmErrorDomain() [SWS_CM_12521] (AUTOSAR_AP_SWS_CommunicationManagement §C.2.2.1.1 “GetComSecOcFvmErrorDomain”).

Lifecycle

Creation of an instance of ComSecOcFvmErrorDomain is performed via the parameterless default constructor [SWS_CM_12517]. Due to the declaration as constexpr and noexcept, it is guaranteed that instantiation can already take place at compile time without allocation risk and is completely exception-safe.

During operation, the error domain typically acts as a long-lived, immutable singleton in the process (interpretation). Question Q-fc901552d01e33de (open) Application and middleware components usually do not instantiate the domain locally, but use the const reference provided via GetComSecOcFvmErrorDomain() [SWS_CM_12521]. Because the member functions Name() [SWS_CM_12518] and Message() [SWS_CM_12519] are stateless and defined as const noexcept, concurrent read access from multiple threads is safe without additional synchronization mechanisms.

Usage Path

If an error occurs in the Freshness Value Manager, callers interact with the error domain along a fixed sequence:

  • Retrieve reference: The component retrieves the global domain reference using GetComSecOcFvmErrorDomain() [SWS_CM_12521].
  • Domain identification: The fixed identifier assigned to the error domain can be queried via Name() for logging or diagnostic purposes [SWS_CM_12518].
  • Resolve error message: Based on a passed error code (CodeType), Message() returns a pointer to the static, human-readable description of the error [SWS_CM_12519].
  • Throw exception: If the error path is to be handled exception-based, ThrowAsException() transforms an ara::core::ErrorCode object into the corresponding exception [SWS_CM_12520].

Sequence diagram: Typical query of error texts or raising of an exception via ComSecOcFvmErrorDomain. Sources: [SWS_CM_12519], [SWS_CM_12520], [SWS_CM_12521]

Error Scenarios

The functions Name() [SWS_CM_12518] and Message() [SWS_CM_12519] have exception safety noexcept and never throw under any circumstances. For unknown numeric error codes, Message() presumably returns a generic default string (interpretation). Question Q-4f9834f33957160b (open)

In contrast, the method ThrowAsException() is by definition not exception-safe (not exception safe), since its explicit task is to construct and throw an ComSecOcFvmException object based on the passed ara::core::ErrorCode [SWS_CM_12520]. Toolchain configuration is an important precondition: If C++ exceptions are disabled in the compiler, ThrowAsException() does not participate in overload resolution [SWS_CM_12520]. Callers in exception-free runtime environments must therefore implement error handling via ara::core::Result or direct error code evaluations.

It takes a reference to an error code errorCode of type const ara::core::ErrorCode& as an input parameter and has no return value. The function creates a new instance of apext::com::secoc::ComSecOcFvmException based on the passed error code and throws it synchronously ([SWS_CM_12520]).

              The method is declared with noexcept(false) and classified as not exception safe (not exception safe) according to the specification ([SWS_CM_12520]). The regular execution pattern provides that the function does not return normally, but immediately reports the created exception apext::com::secoc::ComSecOcFvmException to the caller in case of an error.
              


              restrictions
