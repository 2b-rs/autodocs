Context

The class ara::diag::MultipleEvent provides operations for diagnostic events via multiple event interfaces. In contrast to dedicated single-event interfaces, MultipleEvent enables bundled interaction with multiple diagnostic events via a common port, where the concrete event is addressed on each method call via an identifier of type EventHandleType. The class acts as an adapter between the adaptive application software and the central Diagnostic Management (DM) of the AUTOSAR Adaptive Platform.

Essentially three components are involved in the interaction: the using software component, the instance of ara::diag::MultipleEvent, and the underlying Diagnostic Management service. The application initializes the instance by specifying a model reference and uses it for status queries, debouncing checks, and notifier registrations regarding concrete event handles [SWS_DM_01705] [SWS_DM_01707] [SWS_DM_01708].

Context diagram: Integration of ara::diag::MultipleEvent between adaptive application and Diagnostic Management. Sources: [SWS_DM_01705], [SWS_DM_01707], [SWS_DM_01709]

Lifecycle

An instance of ara::diag::MultipleEvent is created via its explicit constructor, which takes a ara::core::InstanceSpecifier [SWS_DM_01705]. This identifier must refer to a PortPrototype of a DiagnosticMultipleEventInterface declared in the AUTOSAR model. The constructor is declared exception-safe (exception safe) and thread-safe [SWS_DM_01705].

The class has strict semantics regarding identity and resource binding: Both the copy constructor and the assignment operator are explicitly deleted (=delete) [SWS_DM_02070] [SWS_DM_02067]. Likewise, the move constructor and the move assignment operator are deleted [SWS_DM_02069] [SWS_DM_02068]. An instance of MultipleEvent is therefore neither copyable nor movable; it remains fixed at its storage location, typically as a long-lived member of an application component.

The destructor ~MultipleEvent() is exception-safe, but specified as not thread-safe [SWS_DM_01706]. Consequently, the instance may only be released once no concurrent query or registration operations are taking place on the object. Regarding the thread safety of the status query methods, conditional behavior applies: Whether the query methods must be executed thread-safe is determined via the concurrency type provided in the constructor [SWS_DM_01707] [SWS_DM_01709] [SWS_DM_01710] [SWS_DM_01711].

Usage Path

The typical usage path comprises the instantiation of the interface, the optional registration of change notifications, and the querying of event-specific diagnostic data:

  1. Instantiation: The application creates the MultipleEvent object by passing the configured InstanceSpecifier [SWS_DM_01705].
  2. Register notifier: A callback of type EventStatusByteNotifier for a specific eventHandle is registered via SetEventStatusChangedNotifier [SWS_DM_01708]. A renewed call overwrites the previously registered notifier. The method returns a ara::core::Result<void> and is not thread-safe [SWS_DM_01708].
  3. Query status and fault counters: The current status (EventStatusByte) is queried by means of GetEventStatus(eventHandle) [SWS_DM_01707]. Additional diagnostic information can be determined asynchronously via GetDebouncingStatus(eventHandle) for the debouncing status [SWS_DM_01710] as well as GetFaultDetectionCounter(eventHandle) for the fault detection counter [SWS_DM_01711].
  4. Read DTC mapping: Using GetDTCNumber(eventHandle, dtcFormat), the DTC number assigned to the event can be determined in the requested format (DTCFormatType) [SWS_DM_01709].

All query methods return a ara::core::Future, which makes calls non-blocking and allows results to be received asynchronously via the Future interface [SWS_DM_01707] [SWS_DM_01709] [SWS_DM_01710] [SWS_DM_01711].

Sequence diagram: Typical interaction sequence for registering notifiers and for asynchronous status and DTC queries. Sources: [SWS_DM_01705], [SWS_DM_01707], [SWS_DM_01708], [SWS_DM_01709]

Error Scenarios

Error conditions occur both during initialization and during regular operation:

  • Modeling and instantiation errors: The constructor reports model-related violations if the InstanceSpecifier cannot be resolved in the context of the process (InstanceSpecifierMappingIntegrityViolation), the referenced PortPrototype is not typed by a DiagnosticMultipleEventInterface (PortInterfaceMappingViolation), the mapping to the process runtime is missing (ProcessMappingViolation), or the identifier is already in use within the process (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01705].
  • Invalid parameters: If an invalid handle or invalid arguments are passed, methods such as SetEventStatusChangedNotifier, GetEventStatus, GetDebouncingStatus, GetFaultDetectionCounter, and GetDTCNumber return the error code DiagErrc::kInvalidArgument [SWS_DM_01707] [SWS_DM_01708] [SWS_DM_01709] [SWS_DM_01710] [SWS_DM_01711].
  • Missing DTC mapping: If no DTC is configured in the system for the passed eventHandle, the call to GetDTCNumber fails with DiagErrc::kNoSuchDTC [SWS_DM_01709].
  • Service availability: If the essential functionality of Diagnostic Management is not available at runtime, the error DiagErrc::kServiceNotAvailable is returned [SWS_DM_01707] [SWS_DM_01709] [SWS_DM_01710] [SWS_DM_01711]. All error calls have rollback semantics.
