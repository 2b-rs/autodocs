Context

The class ara::diag::DiagOfferErrorDomain functions in AUTOSAR Adaptive as a dedicated error domain for errors that occur in connection with offering and providing diagnostic services (Diagnostic Offers) (AUTOSAR_AP_SWS_Diagnostics §8.11.5 “Class: DiagOfferErrorDomain”, [SWS_DM_00989]). The class is specified as final and derives directly from the fundamental base class ara::core::ErrorDomain of the platform. Its primary responsibility consists in the semantic encapsulation of offer-related error codes, their mapping to descriptive text messages, and the on-demand throwing of type-safe exceptions.

Within the diagnostic architecture, DiagOfferErrorDomain interacts with application modules and the general error handling infrastructure of AUTOSAR Adaptive. Error states during service offering are typically transported via instances of ara::core::ErrorCode that reference the error domain ([SWS_DM_00995]). For the typed definition of error states, the class integrates the underlying enumeration type DiagOfferErrc via the type alias Errc ([SWS_DM_00990]). For exception-based control flows, it provides the domain-specific base exception DiagException via the type alias Exception ([SWS_DM_00991]).

Lifecycle

The instantiation of DiagOfferErrorDomain takes place via the parameterless default constructor constexpr DiagOfferErrorDomain() noexcept; (AUTOSAR_AP_SWS_Diagnostics §8.11.5.2.1 “Special Member Functions”, [SWS_DM_00992]). Since the constructor is declared as constexpr and noexcept, creation can already take place at compile time without dynamic memory being allocated or runtime exceptions being able to occur ([SWS_DM_00992]).

In terms of ownership, the class possesses no mutable state. Interpretation: Instances of DiagOfferErrorDomain are likely kept as long-lived global or static singletons in typical Adaptive Platforms, so that no manual lifecycle management by callers is required. Destruction is stateless and does not require the release of operating system resources. All member functions of the class are explicitly specified as thread-safe (thread-safe) ([SWS_DM_00992], [SWS_DM_00993], [SWS_DM_00994], [SWS_DM_00995]), allowing instances to be queried without issues and without external synchronization by multiple concurrent threads.

Usage Path

The practical use of DiagOfferErrorDomain focuses on the evaluation and translation of error values for failed diagnostic operations:

  • Querying the domain name: The symbolic short name (Shortname) of the error domain can be retrieved via the member function Name() (AUTOSAR_AP_SWS_Diagnostics §8.11.5.2.2 “Member Functions”, [SWS_DM_00993]). The return value is a const char *, the call is exception-safe (exception safe) and throws no exceptions ([SWS_DM_00993]).
  • Translation of error codes: If a caller receives an error code in the context of a diagnostic offer, the numeric error value of type ara::core::ErrorDomain::CodeType is resolved into a textual description using Message(errorCode) ([SWS_DM_00994]).
  • Guaranteed validity of the error message: The return pointer of Message() points to a null-terminated string and, according to the specification, is guaranteed to never be nullptr ([SWS_DM_00994]). Diagnostic loggers and application modules can therefore process the message without an additional check for null pointers.

Error Scenarios

To forward errors in architectures with exception handling, the domain implements the virtual function ThrowAsException(errorCode) ([SWS_DM_00995]). This method accepts a reference to a ara::core::ErrorCode and throws the exception of type Exception or DiagException corresponding to the error value ([SWS_DM_00995], [SWS_DM_00991]).

Since ThrowAsException() throws an exception by design, the method is declared with noexcept(false) and classified as not exception-safe (not exception safe) ([SWS_DM_00995]). An essential configuration aspect is the support for toolchains without C++ exceptions: If C++ exceptions are disabled in the compiler toolchain, ThrowAsException() does not participate in overload resolution ([SWS_DM_00995]). In such environments, error handling remains deterministic by checking error codes via the alias Errc (DiagOfferErrc) and the corresponding error capsules ([SWS_DM_00990]).

<h4>Lifecycle</h4>
<p>The instantiation of <code>DiagOfferErrorDomain</code> takes place via the parameterless default constructor <code>constexpr DiagOfferErrorDomain() noexcept;</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=407">AUTOSAR_AP_SWS_Diagnostics §8.11.5.2.1 “Special Member Functions”</a>, <a class="spec-record-ref" data-req="SWS_DM_00992" href="../spec/record.html?id=SWS_DM_00992">[SWS_DM_00992]</a>). Since the constructor is declared as <code>constexpr</code> and <code>noexcept</code>, creation can already take place at compile time without dynamic memory being allocated or runtime exceptions being able to occur (<a class="spec-record-ref" data-req="SWS_DM_00992" href="../spec/record.html?id=SWS_DM_00992">[SWS_DM_00992]</a>).</p>

<p>In terms of ownership, the class possesses no mutable state. Interpretation: Instances of <code>DiagOfferErrorDomain</code> are likely kept as long-lived global or static singletons in typical Adaptive Platforms, so that no manual lifecycle management by callers is required. Destruction is stateless and does not require the release of operating system resources. All member functions of the class are explicitly specified as thread-safe (<code>thread-safe</code>) (<a class="spec-record-ref" data-req="SWS_DM_00992" href="../spec/record.html?id=SWS_DM_00992">[SWS_DM_00992]</a>, <a class="spec-record-ref" data-req="SWS_DM_00993" href="../spec/record.html?id=SWS_DM_00993">[SWS_DM_00993]</a>, <a class="spec-record-ref" data-req="SWS_DM_00994" href="../spec/record.html?id=SWS_DM_00994">[SWS_DM_00994]</a>, <a class="spec-record-ref" data-req="SWS_DM_00995" href="../spec/record.html?id=SWS_DM_00995">[SWS_DM_00995]</a>), allowing instances to be queried without issues and without external synchronization by multiple concurrent threads.</p>

<h4>Usage Path</h4>
<p>The practical use of <code>DiagOfferErrorDomain</code> focuses on the evaluation and translation of error values for failed diagnostic operations:</p>
<ul>
<li><strong>Querying the domain name:</strong> The symbolic short name (Shortname) of the error domain can be retrieved via the member function <code>Name()</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=408">AUTOSAR_AP_SWS_Diagnostics §8.11.5.2.2 “Member Functions”</a>, <a class="spec-record-ref" data-req="SWS_DM_00993" href="../spec/record.html?id=SWS_DM_00993">[SWS_DM_00993]</a>). The return value is a <code>const char *</code>, the call is exception-safe (<code>exception safe</code>) and throws no exceptions (<a class="spec-record-ref" data-req="SWS_DM_00993" href="../spec/record.html?id=SWS_DM_00993">[SWS_DM_00993]</a>).</li>
<li><strong>Translation of error codes:</strong> If a caller receives an error code in the context of a diagnostic offer, the numeric error value of type <code>ara::core::ErrorDomain::CodeType</code> is resolved into a textual description using <code>Message(errorCode)</code> (<a class="spec-record-ref" data-req="SWS_DM_00994" href="../spec/record.html?id=SWS_DM_00994">[SWS_DM_00994]</a>).</li>
<li><strong>Guaranteed validity of the error message:</strong> The return pointer of <code>Message()</code> points to a null-terminated string and, according to the specification, is guaranteed to never be <code>nullptr</code> (<a class="spec-record-ref" data-req="SWS_DM_00994" href="../spec/record.html?id=SWS_DM_00994">[SWS_DM_00994]</a>). Diagnostic loggers and application modules can therefore process the message without an additional check for null pointers.</li>
</ul>

<h4>Error Scenarios</h4>
<p>To forward errors in architectures with exception handling, the domain implements the virtual function <code>ThrowAsException(errorCode)</code> (<a class="spec-record-ref" data-req="SWS_DM_00995" href="../spec/record.html?id=SWS_DM_00995">[SWS_DM_00995]</a>). This method accepts a reference to a <code>ara::core::ErrorCode</code> and throws the exception of type <code>Exception</code> or <code>DiagException</code> corresponding to the error value (<a class="spec-record-ref" data-req="SWS_DM_00995" href="../spec/record.html?id=SWS_DM_00995">[SWS_DM_00995]</a>, <a class="spec-record-ref" data-req="SWS_DM_00991" href="../spec/record.html?id=SWS_DM_00991">[SWS_DM_00991]</a>).</p>

<p>Since <code>ThrowAsException()</code> throws an exception by design, the method is declared with <code>noexcept(false)</code> and classified as not exception-safe (<code>not exception safe</code>) (<a class="spec-record-ref" data-req="SWS_DM_00995" href="../spec/record.html?id=SWS_DM_00995">[SWS_DM_00995]</a>). An essential configuration aspect is the support for toolchains without C++ exceptions: If C++ exceptions are disabled in the compiler toolchain, <code>ThrowAsException()</code> does not participate in overload resolution (<a class="spec-record-ref" data-req="SWS_DM_00995" href="../spec/record.html?id=SWS_DM_00995">[SWS_DM_00995]</a>). In such environments, error handling remains deterministic by checking error codes via the alias <code>Errc</code> (<code>DiagOfferErrc</code>) and the corresponding error capsules (<a class="spec-record-ref" data-req="SWS_DM_00990" href="../spec/record.html?id=SWS_DM_00990">[SWS_DM_00990]</a>).</p>
