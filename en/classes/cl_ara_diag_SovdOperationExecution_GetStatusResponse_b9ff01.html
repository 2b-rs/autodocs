Context

The data structure ara::diag::SovdOperationExecution::GetStatusResponse is defined as a C++ struct according to [SWS_DM_02200] in AUTOSAR_AP_SWS_Diagnostics §8.62.6 “Struct: GetStatusResponse”. It acts as a standardized response container for querying the execution status of a diagnostic operation via the SOVD (Service-Oriented Vehicle Diagnostics) interface in the AUTOSAR Adaptive Platform.

Primarily three architectural components are involved in the interaction around GetStatusResponse:

  • External SOVD client: Initiates diagnostic operations and queries their current state via the standardized SOVD method Read the Status of an operation ([SWS_DM_02180]).
  • Diagnostic Management (DM): Processes the incoming SOVD request, performs required security checks, and addresses the responsible operation instance based on the transmitted execution-id ([SWS_DM_02177]). After successful execution, the DM reads the attributes from GetStatusResponse and transfers them into the ASAM SOVD response body ([SWS_DM_02181]).
  • Application service (SovdOperationExecution): Implements the business logic of the diagnostic operation and provides the current processing status as well as any result data by implementing the pure virtual method GetStatus (AUTOSAR_AP_SWS_Diagnostics §8.62).

Lifecycle

The struct GetStatusResponse has a clearly defined, short-lived value character and serves exclusively for data transport between the service application and the Diagnostic Management daemon:

  • Creation: The instance of GetStatusResponse is instantiated by the application software as soon as the DM queries the status of an ongoing or completed operation by means of SovdOperationExecution::GetStatus. According to the interface declaration in AUTOSAR_AP_SWS_Diagnostics §8.62, the return is encapsulated asynchronously via a ara::core::Future<GetStatusResponse>. For this purpose, the application populates the structure fields status and Parameters.
  • Ownership and concurrency: Ownership is transferred to the calling Diagnostic Manager via the ara::core::Promise and ara::core::Future mechanism. This transfer presumably occurs via move semantics. Since the structure is passed to the future as a pure value object, read access by the DM requires no further synchronization within the structure.
  • Destruction: As soon as the DM has extracted the values from GetStatusResponse.status and GetStatusResponse.Parameters and incorporated them into the SOVD serialization ([SWS_DM_02181]), the functional lifetime of the object ends and the structure is presumably discarded.

Usage Path

The typical sequence for querying the operation status is divided into authorization, calling the diagnostic interface, and preparing the response data:

  1. Request reception: An external client sends the SOVD method Read the Status of an operation with a specific execution-id to the vehicle gateway or the Diagnostic Manager ([SWS_DM_02180]).
  2. Validation: If configured in the system, the DM first validates the proximity_challenge according to [SWS_DM_02173].
  3. Method call: After successful validation, the DM identifies the assigned instance of SovdOperationExecution based on [SWS_DM_02177] and calls its method GetStatus ([SWS_DM_02180]). In doing so, environmental information (ara::diag::MetaInfo) and a ara::diag::CancellationHandler are passed (AUTOSAR_AP_SWS_Diagnostics §8.62).
  4. State provision: The application determines the progress, initializes an instance of GetStatusResponse, sets field status to the current operating state, and stores any output data in field Parameters. Subsequently, the returned ara::core::Future is fulfilled.
  5. SOVD response construction: If GetStatus has responded successfully, the DM constructs the response body according to ASAM SOVD with the following attributes ([SWS_DM_02181]):
    • status: Corresponds to the value stored in GetStatusResponse.status.
    • capability: Is fixed to the value execute.
    • parameters: Is generated from the parameters of GetStatusResponse.Parameters (derived from DiagnosticSovdContentData).

Error Scenarios

During status determination, various exception and error states can occur that affect the creation or evaluation of GetStatusResponse:

  • Security validation failure: If a required proximity_challenge fails according to [SWS_DM_02173], the call of SovdOperationExecution::GetStatus is omitted completely ([SWS_DM_02180]). In this case, no instance of GetStatusResponse is created.
  • Failed status determination: If the application instance cannot determine the status or GetStatus fails (for example, due to an error state in the asynchronous ara::core::Future), the specification from [SWS_DM_02181] does not apply. In this case, the DM does not send a regular response body with the fields from GetStatusResponse, but signals an error to the SOVD client.
  • Cancellation via CancellationHandler: The signature of GetStatus accepts a ara::diag::CancellationHandler (AUTOSAR_AP_SWS_Diagnostics §8.62). If the query is cancelled before completion, the future in the application use case is presumably resolved with a corresponding error code, so that no valid GetStatusResponse is produced.
