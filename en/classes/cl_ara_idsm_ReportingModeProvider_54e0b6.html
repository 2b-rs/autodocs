Context

The class ara::idsm::ReportingModeProvider is defined as a final interface in the AUTOSAR Adaptive module idsm ([SWS_AIDSM_10600]). Its main responsibility is to provide reporting modes for configured security events to the Intrusion Detection System Manager (IdsM) ([SWS_AIDSM_10600]). In doing so, it acts on the application side as a concrete provider instance for a PPort declared in the system model ([SWS_AIDSM_10601]).

The following parties typically interact in the overall system:

  • Adaptive Application: Acts as a mode provider and decides, based on states or external diagnostics, which reporting mode should be active.
  • ReportingModeProvider: Encapsulates the port-specific interface for querying and updating the event modes ([SWS_AIDSM_10602], [SWS_AIDSM_10603]).
  • IdsM platform instance: Interpretation: Receives the set reporting modes in order to control the filtering and forwarding of the corresponding security events in the vehicle network.

Lifecycle

Creation of a ReportingModeProvider object is strictly explicit via the passing of a ara::core::InstanceSpecifier ([SWS_AIDSM_10601]). This specifier establishes the binding to the modeled PPort in the application manifest. The constructor throws no exceptions (noexcept) and is explicitly specified as thread-safe (thread-safe) ([SWS_AIDSM_10601]).

Regarding ownership and runtime: The instance is typically expected to be created during the initialization phase of the application and held throughout its entire operating phase. With the destruction of the object, the provision of the interface for the associated port ends. Concurrency at runtime requires special attention: While instantiation is thread-safe ([SWS_AIDSM_10601]), the operational methods GetReportingMode ([SWS_AIDSM_10602]) and SetReportingMode ([SWS_AIDSM_10603]) are designated as not thread-safe (not thread-safe). If multiple threads of execution access the same provider instance, the caller must synchronize access externally.

Usage Path

Typical usage is divided into creating the instance, querying existing states, and dynamically switching the reporting mode:

  1. Instantiation: The application initializes the ReportingModeProvider with the corresponding ara::core::InstanceSpecifier of the PPort ([SWS_AIDSM_10601]).
  2. Querying the current mode: Via GetReportingMode(eventId), the application determines the currently configured reporting mode for the specified event ([SWS_AIDSM_10602]).
  3. Setting a new mode: Using SetReportingMode(eventId, reportingMode), the desired mode for the relevant security event is updated ([SWS_AIDSM_10603]).
  4. Evaluating the result: Since both calls return ara::core::Result, the application verifies in each case whether the operation was successful or an error occurred.

Sequence diagram: Call and return sequence during initialization, querying, and updating of a reporting mode. Sources: [SWS_AIDSM_10601], [SWS_AIDSM_10602], [SWS_AIDSM_10603]

Error Scenarios

The interfaces of the class operate entirely without C++ exceptions (noexcept) and report error conditions via the error type ara::core::Result:

  • Unknown event ID (IdsmErrc::kUnknownEventId): This error is returned in ara::core::Result by both GetReportingMode ([SWS_AIDSM_10602]) and SetReportingMode ([SWS_AIDSM_10603]) if the passed eventId (of type EventIdType) does not correspond to any security event configured for this PPort in the system model.
  • Preconditions: The provider instance must have been properly constructed ([SWS_AIDSM_10601]), and the caller must ensure that the queried or modified event identifier is valid.
  • Postconditions: After a successful call to SetReportingMode, GetReportingMode returns the newly set value for the same eventId. In the event of an error, the state in the IdsM remains unchanged.
