Context

The class ara::crypto::CryptoErrorDomain represents the central error domain for all error conditions that can be reported by public interfaces in the namespace ara::crypto. As a functional specialization of the platform-wide base class ara::core::ErrorDomain, it defines domain-specific metadata and translation routines for cryptographic error cases. Within the Adaptive Platform architecture, the class acts as a link between the cryptographic services and the calling application software by providing uniform mechanisms for error identification, error text translation, and exception handling.

For direct type-related integration, the class provides two essential type aliases: via Errc ([SWS_CRYPT_19903]), the underlying enumeration CryptoErrc for cryptographic errors is bound, while Exception ([SWS_CRYPT_19904]) serves as an alias for the base exception class CryptoException. Essential interaction partners are, on the one hand, the cryptographic operations that generate error states and encapsulate them in objects of type ara::core::ErrorCode, and, on the other hand, the calling application logic that analyzes these error states or records them via logging and diagnostic structures.

Lifecycle

The instantiation of ara::crypto::CryptoErrorDomain occurs via the default constructor CryptoErrorDomain() ([SWS_CRYPT_19902]). This is defined as constexpr as well as noexcept and guarantees both exception safety and thread safety ([SWS_CRYPT_19902]).

Interpretation: Presumably, CryptoErrorDomain is primarily provided in the system as a static singleton instance, since the class is declared as final and has no mutable runtime states. All operations provided on the instance are read-only and access static metadata in a thread-safe manner. Therefore, the object does not undergo complex state transitions or sequential phases. Destruction requires no dynamic cleanup, and the thread safety of all methods permits unrestricted, concurrent access from any number of threads.

Usage Path

The typical sequence for detecting and handling errors in the crypto module comprises the following steps:

  1. A cryptographic operation fails and returns a ara::core::Result containing a ara::core::ErrorCode with a reference to CryptoErrorDomain and a specific CryptoErrc.
  2. The application checks the return object and determines the presence of an error.
  3. For error logging or message output, the error handling calls Message(errorCode) ([SWS_CRYPT_19953]) to convert the error code into a readable description. In addition, the unique domain name can be queried via Name() ([SWS_CRYPT_19950]).
  4. If the software architecture is based on C++ exceptions, the error can be thrown directly as a typed exception via ThrowAsException(errorCode) ([SWS_CRYPT_19954]).

Sequence diagram: Typical sequence of error handling and error text retrieval during cryptographic operations. Sources: [SWS_CRYPT_19950], [SWS_CRYPT_19953], [SWS_CRYPT_19954].

Error Scenarios

The interfaces of the error domain have clear guarantees regarding preconditions and postconditions as well as thread safety and exception safety:

  • Message(errorCode): Translates the passed error value into a descriptive text ([SWS_CRYPT_19953]). The call is noexcept, fully exception-safe, and thread-safe. Interpretation: For error values that are not defined in the enumeration CryptoErrc, the implementation is likely to return a generic fallback text.
  • Name(): Returns the unique identifier of the error domain ([SWS_CRYPT_19950]). This query is also thread-safe and noexcept.
  • ThrowAsException(errorCode): Throws an exception of type CryptoException ([SWS_CRYPT_19904]) matching the passed error code ([SWS_CRYPT_19954]). The function is annotated with [[noreturn]] and classified as "not exception safe", since its explicit purpose is to throw an exception.
  • Disabled C++ exceptions: In toolchains or build configurations in which C++ exceptions are disabled, ThrowAsException does not participate in overload resolution ([SWS_CRYPT_19954]). A call in such environments leads to a compilation error, so that applications must handle errors exclusively in a value-based manner via return types and Message().
