Serves for digital signature creation using private cryptographic keys in single-step or streaming procedures.

The interface ara::crypto::cryp::SignerPrivateCtx encapsulates private keys for digital signature operations on the Adaptive Platform [SWS_CRYPT_23501]. After configuring the key via SetKey(), messages can be signed either in a single step via Sign() or in multiple stages via Start(), Update(), and Finish() [SWS_CRYPT_23515] [SWS_CRYPT_23512] [SWS_CRYPT_50040]. All calls are thread-safe and signal errors such as insufficient buffer capacities or invalid context states via ara::core::Result [SWS_CRYPT_50040].

Context

The interface ara::crypto::cryp::SignerPrivateCtx represents the cryptographic execution context for digital signature operations using a private key on the AUTOSAR Adaptive Platform. The class inherits from CryptoContext and encapsulates asymmetric signature algorithms. To bind the required key material, the context interacts either directly with a private key object via PrivateKey::Sptr [SWS_CRYPT_23515] or with a managed key slot via KeySlot::Sptr [SWS_CRYPT_50036]. Callers typically manage instances of this interface via the defined smart pointer type alias ara::crypto::cryp::SignerPrivateCtx::Sptr [SWS_CRYPT_23501].

Lifecycle

Instances of SignerPrivateCtx are operated as stateful objects and managed via shared pointer structures (std::shared_ptr) [SWS_CRYPT_23501]. Prior to performing cryptographic calculations, the instance is in an uninitialized state and requires the assignment of a suitable key. Via the method SetKey(), either a concrete private key is assigned to the context [SWS_CRYPT_23515] or a KeySlot is stored whose key value is used at the start time of the signature calculation [SWS_CRYPT_50036]. As soon as a key has been successfully bound, the context transitions to the operational state. All interface methods are specified as exception-safe (exception safe) and thread-safe (thread-safe) [SWS_CRYPT_23512] [SWS_CRYPT_50037].

Within data processing, the interface distinguishes between one-time signing and multi-stage streaming procedures. A streaming signature operation is initiated by Start() [SWS_CRYPT_50037] [SWS_CRYPT_50038], incrementally supplied with data blocks via Update() [SWS_CRYPT_50039], and finalized by Finish() [SWS_CRYPT_50040]. Alternatively, an ongoing streaming process can be aborted at any time via Cancel(), whereby the instance returns to the operational state [SWS_CRYPT_50041].

State diagram: State transitions of the signing context from configuration to completion of the operation. Sources: [SWS_CRYPT_23515], [SWS_CRYPT_50036], [SWS_CRYPT_23512], [SWS_CRYPT_50037], [SWS_CRYPT_50039], [SWS_CRYPT_50040], [SWS_CRYPT_50041]

Usage Path

Applications can generate signatures either in a single step (single-call) or as a continuous data stream (streaming). Prior to execution, the application determines the expected buffer size for the desired signature format via GetSignatureSize() FormatId [SWS_CRYPT_29004] as well as the maximum permissible block size of individual read-in operations via GetMaximumChunkSize() [SWS_CRYPT_50042].

In the single-step path, the complete message is directly signed using Sign(). The method accepts the input message, the destination buffer ReadWriteMemRegion, the signature format, and an optional algorithm-specific context value, and returns the actual number of bytes written [SWS_CRYPT_23512].

For larger amounts of data or fragmented messages, the streaming path follows a three-phase pattern:

  1. Initialization: Call to Start() without parameters [SWS_CRYPT_50037] or with an application-specific context buffer ReadOnlyMemRegion [SWS_CRYPT_50038].
  2. Processing: Repeated supply of partial messages via Update(), where each block must adhere to the upper limit specified by GetMaximumChunkSize() [SWS_CRYPT_50039] [SWS_CRYPT_50042].
  3. Completion or abortion: Finalization of the signature generation and writing to the destination memory via Finish() [SWS_CRYPT_50040], or premature abortion of the ongoing process using Cancel() [SWS_CRYPT_50041].

Sequence diagram: Typical flow of a streamed signature creation with buffer verification and finalization. Sources: [SWS_CRYPT_23515], [SWS_CRYPT_29004], [SWS_CRYPT_50037], [SWS_CRYPT_50039], [SWS_CRYPT_50040]

Error Scenarios

Method calls return ara::core::Result by default and use standardized error codes from ara::crypto::CryptoErrc with rollback semantics in the event of failures. Common causes of errors include:

  • CryptoErrc::kUninitializedContext: Call to Sign() or Start() before a key was bound via SetKey() [SWS_CRYPT_23512] [SWS_CRYPT_50037] [SWS_CRYPT_50038].
  • CryptoErrc::kUsageViolation: The provided key does not possess the required usage permission kAllowSigGeneration [SWS_CRYPT_23515] [SWS_CRYPT_23512] [SWS_CRYPT_50037].
  • CryptoErrc::kIncompatibleObject: The passed PrivateKey or KeySlot is incompatible with the algorithm of the context [SWS_CRYPT_23515] [SWS_CRYPT_50036].
  • CryptoErrc::kProcessingNotStarted: Invocation of Update(), Finish(), or Cancel() without Start() having been called successfully beforehand [SWS_CRYPT_50039] [SWS_CRYPT_50040] [SWS_CRYPT_50041].
  • CryptoErrc::kInsufficientCapacity: The output buffer passed for Sign() or Finish() is smaller than the signature to be written [SWS_CRYPT_23512] [SWS_CRYPT_50040].
  • CryptoErrc::kUnsupportedFormat: The requested FormatId is not supported by the context [SWS_CRYPT_29004] [SWS_CRYPT_23512] [SWS_CRYPT_50040].
  • CryptoErrc::kEmptyKeySlot: A configured KeySlot contains no key at the time of execution [SWS_CRYPT_23512] [SWS_CRYPT_50037].
  • CryptoErrc::kInvalidInputSize: Invalid buffer sizes during calls to Sign(), Start(), or Update() [SWS_CRYPT_23512] [SWS_CRYPT_50038] [SWS_CRYPT_50039].

function Cancel [SWS_CRYPT_50041] Upstream: RS_CRYPTO_02302

virtual ara::core::Result< void > Cancel () noexcept=0;

Cancel the ongoing streaming operation that has been initiated by Start() and has not yet been finished.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: add6f8db34cb Provenance

The method Cancel() serves to synchronously abort an ongoing, not yet completed streaming operation within class ara::crypto::cryp::SignerPrivateCtx that was previously initiated by a call to Start() [SWS_CRYPT_50041]. The purely virtual interface virtual ara::core::Result<void> Cancel() noexcept = 0; is declared in header ara/crypto/cryp/signer_private_ctx.h, takes no input parameters, and signals successful abort via an empty ara::core::Result<void> [SWS_CRYPT_50041]. For the caller, the method is specified as exception-safe (exception safe) and concurrently thread-safe (thread-safe) [SWS_CRYPT_50041].

Regarding call sequence and error handling, Cancel() strictly requires active processing: If data processing was not previously initiated by a call to method Start(), the abort fails and returns the error code ara::crypto::CryptoErrc::kProcessingNotStarted with defined rollback semantics [SWS_CRYPT_50041]. Interpretation: After a successful call to Cancel(), the context should return to an unstarted basic state so that a new signature or streaming process can be started.

The design follows a uniform principle for all streaming operations in the crypto module. Completely identical signatures and error semantics exist for related contexts such as VerifierPublicCtx [SWS_CRYPT_50023], MessageAuthnCodeCtx [SWS_CRYPT_50027], SymmetricCipherCtx [SWS_CRYPT_50046], HashFunctionCtx [SWS_CRYPT_50058], DecryptorPrivateCtx [SWS_CRYPT_50069], AuthCipherCtx [SWS_CRYPT_50077], and EncryptorPublicCtx [SWS_CRYPT_50089].

      use
      

      The ara::crypto::cryp::SignerPrivateCtx::Finish method synchronously completes signature generation and writes the calculated signature directly into the provided output buffer signature [SWS_CRYPT_50040]. The function expects the writable memory area signature (type ReadWriteMemRegion) and the desired format signatureFormat (type FormatId) as input parameters [SWS_CRYPT_50040]. As the return value, ara::core::Result<size_t> provides the actual byte size of the written signature data; this amount of data may be smaller than the capacity of the destination buffer [SWS_CRYPT_50040].
      


      Error handling
      

      Rollback semantics are specified for all occurring error cases [SWS_CRYPT_50040]. The following error codes can be returned via the result:
      

        

      • ara::crypto::CryptoErrc::kProcessingNotStarted: Signature generation was not successfully started beforehand [SWS_CRYPT_50040].
        • 

      • ara::crypto::CryptoErrc::kInsufficientCapacity: The capacity of the passed output buffer signature is too small [SWS_CRYPT_50040].
        • 

      • ara::crypto::CryptoErrc::kUnsupportedFormat: The value of signatureFormat is unknown or not supported [SWS_CRYPT_50040].
        • 

      


      Concurrency and Limitations
      

      The method is specified as thread-safe and exception safe and must not throw exceptions (noexcept) [SWS_CRYPT_50040]. A valid call strictly requires that the generation process in the context was successfully initiated beforehand [SWS_CRYPT_50040].
      


      Interaction
      

      The direct functional counterpart for verifying the generated signature is the ara::crypto::cryp::VerifierPublicCtx::Finish method [SWS_CRYPT_50022]. In contrast to contexts for hash or MAC calculations, where Finish() only finalizes the calculation and the intermediate or final result is fetched separately [SWS_CRYPT_21115] [SWS_CRYPT_21116], SignerPrivateCtx::Finish writes the signature directly into the buffer [SWS_CRYPT_50040].
