Used for asymmetric verification of digital signatures in a single-step or multi-stage streaming process.

The interface ara::crypto::cryp::VerifierPublicCtx is used for the verification of digital signatures using asymmetric public keys via a one-shot call or multi-step streaming ([SWS_CRYPT_24112], [SWS_CRYPT_50022]). Prior to verification, the context must imperatively be configured with a valid key whose assigned usage rights permit signature verification ([SWS_CRYPT_24115]). All interface methods are designed to be exception-safe as well as thread-safe.

Context

The interface ara::crypto::cryp::VerifierPublicCtx is used for the verification of digital signatures based on asymmetric cryptography using a public key. It interacts directly with key objects ([SWS_CRYPT_24115]) or outsourced key storages ([SWS_CRYPT_50018]) and provides methods to verify signatures either in a single step (one-shot) or streamed over multiple partial steps.

Lifecycle

Instances of the verification context are typically managed application-internally via the smart pointer type alias ara::crypto::cryp::VerifierPublicCtx::Sptr, which is defined as std::shared_ptr<VerifierPublicCtx> ([SWS_CRYPT_24101]). All interface methods are declared as exception-safe as well as thread-safe.

The context goes through clearly defined operational phases. After its instantiation, the context is in an uninitialized state in which verification calls are rejected with ara::crypto::CryptoErrc::kUninitializedContext ([SWS_CRYPT_50019], [SWS_CRYPT_24112]). Only upon assigning a suitable key via SetKey() does the context transition to the ready-for-operation state ([SWS_CRYPT_24115], [SWS_CRYPT_50018]). From this state, either an atomic verification can be performed or a streaming session can be initiated. After finishing ([SWS_CRYPT_50022]) or aborting ([SWS_CRYPT_50023]) a streaming operation, the context is expected to be available again for new verifications.

State diagram: Lifecycle and state transitions of the verification context. Sources: [SWS_CRYPT_24115], [SWS_CRYPT_50018], [SWS_CRYPT_50019], [SWS_CRYPT_50021], [SWS_CRYPT_50022], [SWS_CRYPT_50023], [SWS_CRYPT_24112].

Usage Path

Two complementary processing paths are available for signature verification:

  • One-shot verification: If the complete message is available in memory, Verify() can be called directly ([SWS_CRYPT_24112]) after key assignment via SetKey() ([SWS_CRYPT_24115]). If the algorithm supports or requires application-specific context data, the overloaded variant with an additional context buffer is used ([SWS_CRYPT_50024]). Both variants return a ara::core::Result<bool> whose boolean value indicates the validity of the signature.
  • Streaming verification: For large amounts of data or data blocks arriving in steps, Start() is initially called after SetKey() ([SWS_CRYPT_50019], optionally with a context buffer according to [SWS_CRYPT_50020]). Subsequently, the data fragments are fed repeatedly using Update() ([SWS_CRYPT_50021]). The maximum buffer size for individual sections can be determined in advance via GetMaximumChunkSize() ([SWS_CRYPT_50025]). The process is concluded by calling Finish() while passing the signature and its format identifier ([SWS_CRYPT_50022]). An ongoing streaming session can be discarded at any time via Cancel() ([SWS_CRYPT_50023]).

Sequence diagram: Step-by-step sequence of a signature verification in the streaming process. Sources: [SWS_CRYPT_24115], [SWS_CRYPT_50019], [SWS_CRYPT_50021], [SWS_CRYPT_50022].

Error Scenarios

All state-modifying and verifying methods work with ara::core::Result and have rollback semantics in case of errors:

  • Key configuration: If a key or KeySlot incompatible with the algorithm is passed, SetKey() returns the error CryptoErrc::kIncompatibleObject ([SWS_CRYPT_24115], [SWS_CRYPT_50018]). If the key lacks the usage permission kAllowSigVerification, the call fails with CryptoErrc::kUsageViolation ([SWS_CRYPT_24115]). In addition, SetKey() reports CryptoErrc::kUnsupported if the context exclusively accepts the respective other key form (KeySlot or PublicKey).
  • Sequence and precondition errors: If Update(), Finish(), or Cancel() are called without a prior successful call to Start(), they fail with CryptoErrc::kProcessingNotStarted ([SWS_CRYPT_50021], [SWS_CRYPT_50022], [SWS_CRYPT_50023]). Calling Start() or Verify() without prior key reference results in CryptoErrc::kUninitializedContext ([SWS_CRYPT_50019], [SWS_CRYPT_24112]). For referenced but empty KeySlots, CryptoErrc::kEmptyKeySlot is reported.
  • Data and format errors: The methods acknowledge invalid buffer sizes with CryptoErrc::kInvalidInputSize ([SWS_CRYPT_50021], [SWS_CRYPT_50022], [SWS_CRYPT_24112]). Unsupported signature formats generate CryptoErrc::kUnsupportedFormat, whereas structurally faulty signatures trigger CryptoErrc::kInvalidArgument ([SWS_CRYPT_50022], [SWS_CRYPT_24112]). If hardware resources are occupied, CryptoErrc::kBusyResource is returned.

Usage and Semantics

The method Cancel() aborts an ongoing streaming operation that was previously initiated by Start() and has not yet been completed [SWS_CRYPT_50023]. It is defined in header ara/crypto/cryp/verifier_public_ctx.h as a pure virtual method of context ara::crypto::cryp::VerifierPublicCtx [SWS_CRYPT_50023]. The call is synchronous and takes no arguments. The return value is a ara::core::Result<void>, which is empty on success and confirms the successful cancellation of the operation [SWS_CRYPT_50023].

Error handling

If data processing has not yet been started by calling the method Start(), the abort operation fails. In this scenario, the function returns an error result with error code ara::crypto::CryptoErrc::kProcessingNotStarted while guaranteeing rollback semantics [SWS_CRYPT_50023].

Concurrency and Limitations

The specification identifies the method as thread-safe and exception safe with the designation noexcept [SWS_CRYPT_50023]. Interpretation: After a successful abort, the context is likely to revert to the initial state prior to the start of processing so that a new streaming process can be started.

Interaction in Module crypt

This uniform cancellation pattern with identical signature and error handling applies consistently to all streaming contexts of module crypt:

  • MessageAuthnCodeCtx for Message Authentication Codes [SWS_CRYPT_50027],
  • SignerPrivateCtx for digital signature generation [SWS_CRYPT_50041],
  • SymmetricCipherCtx for symmetric encryption and decryption [SWS_CRYPT_50046],
  • HashFunctionCtx for cryptographic hash operations [SWS_CRYPT_50058],
  • DecryptorPrivateCtx for asymmetric decryption [SWS_CRYPT_50069],
  • AuthCipherCtx for authenticated encryption [SWS_CRYPT_50077], and
  • EncryptorPublicCtx for asymmetric encryption [SWS_CRYPT_50089].
