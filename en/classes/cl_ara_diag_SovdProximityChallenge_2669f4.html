Context

The class [SWS_DM_01481] defines the application interface for providing and verifying SOVD proximity challenges (proofs of proximity) in the AUTOSAR Adaptive diagnostic module. It mediates directly between the Diagnostic Management (DM or Diagnostic Server) and the application-specific logic as soon as an SOVD operation requires proof of physical vehicle proximity via the model attribute DiagnosticSovdOperation.proximityProofRequired = TRUE [SWS_DM_01398] (AUTOSAR_AP_SWS_Diagnostics, p. 215).

Conceptually, the specification assumes that at any given time, only a single proximity challenge usually exists, which is valid across all requesting SOVD clients and all affected operations (AUTOSAR_AP_SWS_Diagnostics, p. 215). An application therefore normally does not need to manage separate challenges per client. If advanced scenarios nevertheless require differentiated handling, the application can evaluate the passed metadata of type ara::diag::MetaInfo to implement operation- or client-specific checks (AUTOSAR_AP_SWS_Diagnostics, p. 215).

Lifecycle

The creation of an object of ara::diag::SovdProximityChallenge takes place explicitly via the constructor [SWS_DM_01480]. In doing so, an ara::core::InstanceSpecifier pointing to the modeled PortPrototype of the interface and the concurrency mode ConcurrencyType (kConcurrent or kNotConcurrent) are passed. After construction, the instance is in the Unoffered state and does not yet receive any messages from the Diagnostic Management.

Calling the method Offer() [SWS_DM_01478] subsequently transitions the instance to the Offered state. Only then is the Diagnostic Management authorized and enabled to forward incoming challenge and validation requests to the virtual methods of the handler. Calling StopOffer() [SWS_DM_01495] stops this forwarding again, and the state returns to Unoffered.

The destructor ~SovdProximityChallenge() [SWS_DM_01479] terminates the lifetime of the instance. Regarding thread safety, the constructor is specified as thread-safe, whereas Offer(), StopOffer(), and the destructor must not be called in a thread-safe manner (not thread-safe) [SWS_DM_01478], [SWS_DM_01495], [SWS_DM_01479]. For the execution of the application-side callback methods, the ConcurrencyType selected in the constructor determines whether the DM invokes them concurrently or synchronized [SWS_DM_01494], [SWS_DM_01493].

Usage Path

The regular interaction is divided into the following phases:

  1. Initialization and offering: The application instantiates its class derived from SovdProximityChallenge and activates forwarding via Offer() [SWS_DM_01478].
  2. Challenge generation: If an SOVD client requests a protected operation, the Diagnostic Management calls the method GetChallenge() [SWS_DM_01494]. The application generates the challenge, specifies its validity timestamp (valid_until), and returns the result asynchronously via ara::core::Future<SovdProximityChallengeType>. The DM embeds the challenge into the response body to the client [SWS_DM_01398].
  3. Validation: If the client subsequently sends its response (proximity_response), the DM calls the callback method ValidateResponse() [SWS_DM_01493]. The application logic verifies the passed byte data (ara::core::Span<const ara::core::Byte>) and returns the verification result asynchronously via ara::core::Future<ProximityChallengeValidationResultType>. The lifetime of the buffer data remains guaranteed until fulfillment of the associated promise [SWS_DM_01493].
  4. Deactivation: Prior to shutdown or upon unavailability of the functionality, the application revokes forwarding using StopOffer() [SWS_DM_01495].

Interpretation: Managing the validity period (valid_until) and potential internal timeouts is entirely up to the application-specific implementation, since the specification only mentions guideline values such as two minutes (AUTOSAR_AP_SWS_Diagnostics, p. 215).

Error Scenarios

During operation, specific error states and model violations can occur:

  • Modeling and instantiation errors: The constructor [SWS_DM_01480] checks the validity of the InstanceSpecifier. If the resolution fails or the identifier does not refer to a PortPrototype, a InstanceSpecifierMappingIntegrityViolation is reported. If the referenced port is not typed by a DiagnosticSovdProximityChallengeInterface, this results in a PortInterfaceMappingViolation. If no modeled process matches the runtime process, a ProcessMappingViolation is present. If the identifier has already been used in the same process, a InstanceSpecifierAlreadyInUseViolation is triggered.
  • Offering errors: Offer() returns a ara::core::Result<void> [SWS_DM_01478]. The call fails with DiagOfferErrc::kAlreadyOffered if the service is already offered, or with DiagOfferErrc::kConfigurationMismatch if the configuration does not match the DEXT model data.
  • Standardized error codes: AUTOSAR defines no standardized error codes for the methods GetChallenge() [SWS_DM_01494] and ValidateResponse() [SWS_DM_01493]; error conditions are handled via the return types or Future objects.
