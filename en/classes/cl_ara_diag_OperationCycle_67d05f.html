Cycle context for event processing

OperationCycle makes changes of a configured operation cycle visible to the application. The DM uses operation cycles in event-status and fault-memory processing; the cycle is therefore the temporal context in which test results and certain status bits are interpreted SWS Diagnostics §7.3.4.3 “Operation Cycles Management” SWS Diagnostics §7.3.4.1.6 “Event Status processing”.

Operation cycles provide temporal context for event and DTC status processing; the interface reports cycle changes to the application. Sources: SWS Diagnostics §7.3.4.3 “Operation Cycles Management”, SWS Diagnostics §7.3.4.1.6 “Event Status processing”, SWS Diagnostics §7.3.4.4 “Event memory”. Partial interpretation: State names summarize the temporal role of the Operation Cycle API.

Notifier as state transfer

SetNotifier registers a callback for operation cycle changes; a subsequent registration replaces the previous callback [SWS_DM_00755]. The notifier implementation should only take over the cycle state or start or end its own audit trails, not write event status bits itself.

Classify restart semantically

RestartOperationCycle is an explicit DM request to restart an operation cycle. Whether and which event/DTC consequences arise from this depends on the configured event processing. Therefore, first clearly assign the notified or configured cycle and only then use the restart; Monitor actions continue to be reported via Monitor.

Subscribe to cycle changes

SetNotifier registers the function for changes to an Operation Cycle [SWS_DM_00755]. Another call replaces the previous registration; There should therefore be a clear callback owner for each instance.

Use in event context

The notifier provides the time frame for diagnostic event and DTC processing SWS Diagnostics §7.3.4.3 “Operation Cycles Management”. He should only coordinate his own test logic; Monitor findings continue to be passed on to the DM via Monitor::ReportMonitorAction.
