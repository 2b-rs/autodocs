Context

The class ara::diag::OperationCycle represents the C++ interface of the DiagnosticOperationCycleInterface according to AUTOSAR_AP_SWS_Diagnostics p. 81. It provides application software with functional mechanisms for controlling and monitoring operation cycles. In diagnostics, operation cycles are authoritative reference periods and state windows on the basis of which fault checks, debouncings, and qualifications of diagnostic trouble codes (DTCs) are evaluated.

Essentially three entities are involved in the interaction:

  • Application software: Instantiates the class object based on a port identifier, registers callback functions for monitoring cycle changes if required, and triggers the restart of the cycle when relevant operating conditions occur.
  • ara::diag::OperationCycle: Acts as a local proxy in the application's process, binds the configured port, and forwards calls to the platform subsystem.
  • Diagnostic Management: Manages the overall state of the operation cycle, coordinates dependent diagnostic monitors, and reports status transitions back to registered instances.

Context diagram: Interaction between application software, ara::diag::OperationCycle, and platform Diagnostic Management. Sources: [SWS_DM_00752], AUTOSAR_AP_SWS_Diagnostics p. 81.

Lifecycle

An instance is created via the explicit constructor OperationCycle(const ara::core::InstanceSpecifier &specifier) ([SWS_DM_00752]). The constructor is declared as noexcept and is considered exception safe.

With regard to ownership and semantics, the class is designed as a strictly bound single instance:

  • The copy constructor ([SWS_DM_01598]) and the assignment operator ([SWS_DM_01596]) are explicitly deleted (=delete), thereby precluding duplication of the interface binding.
  • Likewise, the move constructor ([SWS_DM_01599]) and the move assignment operator ([SWS_DM_01597]) are deleted (=delete). Thus, an existing instance cannot be moved to other scopes.

The instance is released via the virtual destructor ~OperationCycle() ([SWS_DM_00753]), which is likewise implemented as noexcept.

Different guarantees apply to concurrency: While instantiation via the constructor is specified as thread-safe (thread-safe) ([SWS_DM_00752]), the destructor ([SWS_DM_00753]) as well as all regular method calls are designated as not thread-safe (not thread-safe). If multiple application threads access the same OperationCycle object, access must be synchronized by the caller.

Usage Path

The regular workflow for monitoring and controlling an operation cycle is divided into the following steps:

  1. Instantiation: The application creates the object by passing the ara::core::InstanceSpecifier, which references the corresponding PortPrototype in the manifest ([SWS_DM_00752]).
  2. Notification registration: A callback of type OperationCycleSetNotifier (defined as std::function<void(void)>, [SWS_DM_02078]) is registered via SetNotifier() ([SWS_DM_00755]). A subsequent call to SetNotifier() completely overwrites a previously configured notifier.
  3. Request restart: As soon as the operation cycle is to be restarted (e.g., after a terminal change or end of driving cycle), the application calls RestartOperationCycle() ([SWS_DM_01102]).
  4. Event feedback: Interpretation: The execution of the registered notifier upon a status change of the operation cycle is likely performed asynchronously by the diagnostic subsystem, as no synchronous context is specified. As soon as the cycle status has been adapted in the system, the configured callback function is called.

Sequence diagram: Initialization, registration of the notifier, and triggering of the cycle restart. Sources: [SWS_DM_00752], [SWS_DM_00755], [SWS_DM_01102], [SWS_DM_02078].

Error Scenarios

During instantiation, configuration and model conflicts can occur that are reported via specific runtime violations ([SWS_DM_00752]):

  • InstanceSpecifierMappingIntegrityViolation: The specified InstanceSpecifier cannot be resolved in the model context of the executable or refers to a model element that is not an PortPrototype.
  • PortInterfaceMappingViolation: The PortPrototype referenced by an DiagnosticOperationCyclePortMapping is not typed as DiagnosticOperationCycleInterface in the design model.
  • ProcessMappingViolation: Although a matching instance reference (InstanceRef) exists, the mapping to a modeled process (Process) that corresponds to the running process is missing.
  • InstanceSpecifierAlreadyInUseViolation: The constructor was called with an InstanceSpecifier that is already used by an existing instance within the same process.

For the operational calls RestartOperationCycle() ([SWS_DM_01102]) and SetNotifier() ([SWS_DM_00755]), the API returns a ara::core::Result<void> in each case. The interface specification specifies no standardized error codes for either function. Both methods are declared as noexcept.
