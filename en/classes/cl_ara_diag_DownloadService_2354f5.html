Context

In the module diag of the AUTOSAR Adaptive Platform, the class ara::diag::DownloadService provides the central C++ interface for handling diagnostic downloads AUTOSAR_AP_SWS_Diagnostics, p. 74. It serves as an application-side service handler that encapsulates download operations for a specific diagnostic interface. The primary interaction takes place between the AUTOSAR Diagnostic Management (DM) and the concrete application implementation. Interpretation: The Diagnostic Management receives UDS requests from an external diagnostic tester in accordance with ISO 14229-1 and forwards them to the instance as soon as the service is offered.

After activation via Offer(), the class acts as an interface for the standardized phases of a diagnostic download: request (RequestDownload), segmented data transfer (TransferData via DownloadData), and completion (RequestTransferExit via RequestDownloadExit). The application implements the pure virtual methods [SWS_DM_00789], [SWS_DM_00790], and [SWS_DM_00791] to receive, verify, and store data blocks in the target memory.

Lifecycle

An instance of DownloadService is created via the constructor DownloadService(const ara::core::InstanceSpecifier&, ConcurrencyType) [SWS_DM_00787]. The InstanceSpecifier links the instance to a PortPrototype of an DiagnosticDownloadInterface defined in the design model. Via the argument concurrencyType, it is specified whether the implemented service methods are called concurrently (kConcurrent) or non-concurrently (kNotConcurrent), which forms the specification for the thread safety of the application logic [SWS_DM_00787]. The constructor itself is implemented in a thread-safe manner.

With regard to ownership and copy semantics, DownloadService is designed as unique: both copy constructor [SWS_DM_01649] and assignment operator [SWS_DM_01647] as well as move constructor [SWS_DM_01650] and move assignment operator [SWS_DM_01648] are deleted (delete).

The operational lifecycle is divided into the following states and transitions:

  • Instantiated (inactive): After construction, the instance is ready, but does not yet forward any diagnostic requests.
  • Offered (active): The call to Offer() [SWS_DM_00792] authorizes the DM to forward incoming diagnostic download requests to the virtual handler methods of the instance.
  • Stopped: By means of StopOffer() [SWS_DM_00793], the forwarding of requests is deactivated; the instance returns to the inactive state.
  • Destruction: The virtual destructor ~DownloadService() [SWS_DM_00788] releases the resources. Since the destructor is not thread-safe, the service should be stopped beforehand.

State diagram: State phases of a DownloadService instance from construction through offering to termination. Sources: [SWS_DM_00787], [SWS_DM_00792], [SWS_DM_00793], [SWS_DM_00788].

Usage Path

After successful instantiation and offering via Offer(), a download process typically goes through three sequential steps via asynchronous interface calls:

  1. Download initialization (RequestDownload): The DM calls RequestDownload(...) [SWS_DM_00789]. The data format identifier (dataFormatIdentifier), the address and length format (addressAndLengthFormatIdentifier), the target address and size as a byte span (memoryAddressAndSize), as well as metaInfo and a cancellationHandler are passed. The data in memoryAddressAndSize remains valid until the associated promise is fulfilled or processing is canceled. The method returns a ara::core::Future<void>, which is successfully provided upon positive validation.
  2. Blockwise data transfer (DownloadData): For each subsequent transfer request, the DM calls DownloadData(...) [SWS_DM_00790]. The payload is passed in transferRequestParameterRecord. The application processes the data and signals the result via a ara::core::Future<OperationOutput>. Data in OperationOutput.responseData is placed after the block sequence counter in the positive UDS response.
  3. Transfer completion (RequestDownloadExit): To terminate the download, the DM calls RequestDownloadExit(...) [SWS_DM_00791]. After a final integrity check (e.g., checksum validation), the application returns a ara::core::Future<OperationOutput> whose optional response data is placed after the service ID.

All three methods receive a cancellationHandler [SWS_DM_00789]. Via cancellationHandler.IsCanceled(), the application can check the cancellation status; with cancellationHandler.SetNotifier(...), a callback can be registered to react immediately to a cancellation of the diagnostic conversation. Interpretation: In the event of a premature cancellation, the application terminates internal buffering and cancels ongoing write operations.

Sequence diagram: Typical interaction sequence between Diagnostic Management and DownloadService during a diagnostic download. Sources: [SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791].

Error Scenarios

Errors can occur during creation and configuration as well as during service provision and data processing:

  • Modeling and initialization errors: Modeling violations can be triggered during constructor invocation [SWS_DM_00787]:
    • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the model within the execution context or does not reference a PortPrototype.
    • PortInterfaceMappingViolation: A PortPrototype typed with DiagnosticDownloadInterface is not mapped to a DiagnosticServiceGenericMapping in a type-compliant manner.
    • ProcessMappingViolation: No matching modeled Process exists for the InstanceRef.
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by another instance within this process.
  • Error when offering the service: A repeated call to Offer() when the service is already offered fails and returns the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_00792].
  • Diagnostic errors (Negative Response Codes): If processing in RequestDownload, DownloadData, or RequestDownloadExit fails (for instance, in case of incorrect formatting, invalid memory area, or write errors), the returned future is provided with a corresponding error code from DiagUdsNrcErrc according to ISO 14229-1 [SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]. The DM uses this to generate the negative response (NRC) to the tester.
