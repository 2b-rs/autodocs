Serves as an interface for processing UDS download sessions with data transfer and final verification.

The abstract class ara::diag::DownloadService serves as a functional interface for handling UDS download operations on the AUTOSAR Adaptive Platform ([SWS_DM_00787]). After activation via Offer(), Diagnostic Management forwards the diagnostic requests for initialization, block-by-block data transfer, and final verification to the application-specific implementation ([SWS_DM_00792]). The instance is neither copyable nor movable and requires a unique port mapping as well as the definition of concurrency behavior upon creation. All transfer routines return asynchronous futures, with errors being signaled via Negative Response Codes.

Context

The abstract class ara::diag::DownloadService defines the functional C++ interface for implementing diagnostic download services in the AUTOSAR Adaptive Platform ([SWS_DM_00787]). It acts as a standardized service handler to which Diagnostic Management (DM) forwards incoming UDS requests according to ISO 14229-1 ([SWS_DM_00792]). Binding to the software architecture is achieved via a modeled PortPrototype of a DiagnosticDownloadInterface, which is resolved at runtime via an ara::core::InstanceSpecifier ([SWS_DM_00787]). An application-specific diagnostic component inherits from this interface and implements the concrete sequence logic for initiation, block-by-block data transfer, and the orderly termination of download sequences in the ECU ([SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]).

Lifecycle

Instantiation is performed via the constructor by specifying a ara::core::InstanceSpecifier and an ConcurrencyType ([SWS_DM_00787]). In doing so, the platform validates model integrity; incorrect port assignments or multiple use of the same identifier in the process result in runtime errors ([SWS_DM_00787]). To ensure unique mapping to the diagnostic port, ara::diag::DownloadService is designed as a single instance: both the copy constructor ([SWS_DM_01649]) and copy assignment operator ([SWS_DM_01647]) as well as the move constructor ([SWS_DM_01650]) and move assignment operator ([SWS_DM_01648]) are deleted (delete).

After creation, the instance is in the inactive state. Only by calling Offer() is the forwarding of diagnostic requests enabled by the DM ([SWS_DM_00792]). This forwarding can be deactivated again using StopOffer() ([SWS_DM_00793]). After deactivation, a renewed call to Offer() is likely permissible (interpretation) if the service is to be reactivated in the application sequence. The virtual destructor ~DownloadService() terminates the lifecycle of the handler ([SWS_DM_00788]).

Regarding thread safety, the constructor is thread-safe, whereas Offer(), StopOffer(), and the destructor are not thread-safe ([SWS_DM_00787], [SWS_DM_00788], [SWS_DM_00792], [SWS_DM_00793]). Whether the derived service methods must be processed concurrently depends on the ConcurrencyType (kConcurrent or kNotConcurrent) selected during the constructor call ([SWS_DM_00787], [SWS_DM_00789]).

State diagram: Lifecycle of a DownloadService instance from creation through offering status to destruction. Sources: [SWS_DM_00787], [SWS_DM_00792], [SWS_DM_00793], [SWS_DM_00788].

Usage Path

A regular download process follows a three-stage sequence of initialization, data transfer, and final verification:

  • Download initialization: After offering the service via Offer() ([SWS_DM_00792]), the DM receives a UDS request for download initialization and calls RequestDownload() ([SWS_DM_00789]). The application verifies parameters such as dataFormatIdentifier, addressAndLengthFormatIdentifier, as well as target address and memory size in memoryAddressAndSize ([SWS_DM_00789]). After successful verification, the returned ara::core::Future<void> is resolved positively ([SWS_DM_00789]).
  • Data transfer: For subsequent TransferData messages, the DM cyclically calls DownloadData() ([SWS_DM_00790]). The segment transferRequestParameterRecord contains the payload and remains valid until the associated promise is fulfilled or processing is canceled ([SWS_DM_00790]). The returned ara::core::Future<OperationOutput> provides positive response data, which is placed after the block counter in the UDS response ([SWS_DM_00790]).
  • Transfer termination: After complete data transfer, the DM calls RequestDownloadExit() ([SWS_DM_00791]). The application processes manufacturer-specific parameters from transferRequestParameterRecord (e.g., concluding checksums) and acknowledges the request asynchronously via a ara::core::Future<OperationOutput> ([SWS_DM_00791]).

Processing of the payload data blocks is likely to typically take place in asynchronous background threads of the application (interpretation), because the interface works with ara::core::Future and a cancellationHandler for cancellation checking is passed on every call ([SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]). After completion of all operations, the application unregisters the service via StopOffer() ([SWS_DM_00793]).

Sequence diagram: Typical sequence of a UDS download session between Diagnostic Management (DM) and DownloadService. Sources: [SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791], [SWS_DM_00792], [SWS_DM_00793].

Error Scenarios

Errors can occur during configuration, during service registration, as well as during ongoing protocol execution:

  • Configuration violations: If the InstanceSpecifier cannot be resolved in the model or does not reference a PortPrototype, a InstanceSpecifierMappingIntegrityViolation is raised ([SWS_DM_00787]). A missing typing by a DiagnosticServiceGenericMapping leads to a PortInterfaceMappingViolation ([SWS_DM_00787]). In addition, missing process assignments (ProcessMappingViolation) or the reuse of an already assigned identifier (InstanceSpecifierAlreadyInUseViolation) result in instantiation errors ([SWS_DM_00787]).
  • Offering errors: If Offer() is called when the service is already actively offered, the call returns the error code DiagOfferErrc::kAlreadyOffered in a ara::core::Result ([SWS_DM_00792]).
  • Diagnostic negative responses: If processing in RequestDownload(), DownloadData(), or RequestDownloadExit() fails (e.g., due to invalid address ranges or block errors), the application completes the respective ara::core::Future with an error code from DiagUdsNrcErrc according to ISO 14229-1 ([SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]). The DM then generates the corresponding negative response message.
  • Cancellation and abort: Via the object cancellationHandler, the application can check using IsCanceled() whether the ongoing diagnostic conversation has been canceled, or register a callback for cancellation via SetNotifier() ([SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]). In the event of a cancellation, the validity of the passed buffer data expires prematurely ([SWS_DM_00789], [SWS_DM_00790], [SWS_DM_00791]).

use

Method [SWS_DM_00790] is called to process data for the UDS service TransferData (0x36) following a previously initiated download request (AUTOSAR_AP_SWS_Diagnostics §8.14.1.1.3.1 “DownloadData”). Execution is asynchronous via ara::core::Future<OperationOutput>.

As inputs, a ara::core::Span<const std::uint8_t> with the data to be transferred (transferRequestParameterRecord), context data via MetaInfo, and a CancellationHandler are passed. The payload remains valid until the promise is satisfied or the operation is cancelled. Upon successful completion, response data is stored in OperationOutput.responseData and placed behind the block sequence counter in the positive response message [SWS_DM_00786].

Error handling

If an error occurs during processing, the promise is completed with an appropriate ErrorCode from DiagUdsNrcErrc (NRC in accordance with ISO 14229-1) as a negative UDS response [SWS_DM_00790].

Concurrency and Limitations

The function is declared as noexcept. Whether the implementation must be executed thread-safely is conditionally determined by the ConcurrencyType passed in the constructor [SWS_DM_00790]. Via the CancellationHandler, the cancellation status can be queried (IsCanceled) or a notification callback can be registered via SetNotifier.

Interaction

The operation implements the processing of TransferData [SWS_DM_00137] after the download session was previously started via RequestDownload (0x34) [SWS_DM_00869]. The transfer of the data blocks presumably occurs sequentially according to the UDS session order.

                  The method Offer of class ara::diag::DownloadService enables the forwarding of incoming download requests by the Diagnostic Management Daemon (DM) to the specific handler [SWS_DM_00792]. The call is made synchronously and without parameters without throwing C++ exceptions (noexcept) [SWS_DM_00792]. Typically, offering is likely to be called during the initialization phase of the processing application before external diagnostic requests arrive.
