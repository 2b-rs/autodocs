intended use

Authentication is the application interface for implementing Diagnostic Service authentication. It is generated for a port of a DiagnosticAuthenticationInterface with InstanceSpecifier and ConcurrencyType and can be offered to the DM via Offer(). [SWS_DM_01123] [SWS_DM_01124] [SWS_DM_01130]

Interaction with other classes

For the UDS subfunction VerifyCertificateUnidirectional, the Diagnostic Server calls VerifyCertificateUnidirectional() with communication configuration, client certificate, client challenge, MetaInfo and CancellationHandler. The application checks the certificate and returns the challenge and ephemeral public key in a future. [SWS_DM_01126] [SWS_DM_01230]

For the bidirectional variant, VerifyCertificateBidirectional() checks the certificate and challenge and generates the challenge, ephemeral public key, proof of ownership and the server certificate for the tester. With proof of ownership, the DM calls VerifyOwnership() with client POWN and client key; the future provides session key information or an error. [SWS_DM_01127] [SWS_DM_01128] [SWS_DM_01235] [SWS_DM_01240]

Creation & lifecycle

StopOffer() stops request forwarding. If the offer is made again, DiagOfferErrc::kAlreadyOffered will be returned. Copying, moving and both assignments are prohibited; the class has a virtual noexcept destructor. [SWS_DM_01130] [SWS_DM_01131] [SWS_DM_01607] [SWS_DM_01608] [SWS_DM_01609] [SWS_DM_01610] [SWS_DM_01125]

Limitations & Error handling

The three verification callbacks are exception-safe. Your thread safety depends on the ConcurrencyType chosen in the constructor; The callbacks can be called reentrantly for requests from different clients. The passed byte views are only valid until the promise is fulfilled or processing is canceled via the CancellationHandler. In the event of a technical failure, a suitable DiagUdsNrcErrc should be used. [SWS_DM_01124] [SWS_DM_01126] [SWS_DM_01127] [SWS_DM_01128]

function VerifyCertificateBidirectional [SWS_DM_01127] Upstream: RS_Diag_04251, RS_AP_00128

virtual ara::core::Future< std::tuple< ara::core::Vector< ara::core::Byte >, ara::core::Vector< ara::core::Byte >, ara::core::Vector< ara::core::Byte >, ara::core::Vector< ara::core::Byte > > > VerifyCertificateBidirectional (ara::core::Byte communicationConfiguration, ara::core::Span< const ara::core::Byte > clientCertificate, ara::core::Span< const ara::core::Byte > client Challenge, const MetaInfo &metaInfo, CancellationHandler cancellation Handler) noexcept=0;

This function accepts the certificate and challenge received from the tester, verifies the certificate, and creates a challenge, Ephemeral Public Key and Proof Of Ownership that must be returned to the tester. The function also returns the server certificate that will be used by the tester to verify the Proof Of Ownership. This callback may be called re-entrant to requests from different clients.

The callback can be called reentrantly for requests from different clients [SWS_DM_01127]. communicationConfiguration, clientCertificate, clientChallenge, metaInfo and a cancellationHandler are handed over.
