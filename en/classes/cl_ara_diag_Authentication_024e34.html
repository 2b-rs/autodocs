Provides interfaces to the application for UDS Service 0x29 authentication towards external diagnostic testers.

The class ara::diag::Authentication serves as an application-side interface for performing UDS Service 0x29 authentication towards external testers (AUTOSAR AP SWS Diagnostics p. 63). After initialization and activation via Offer(), the application takes over certificate verification as well as proof of ownership via asynchronous callbacks ([SWS_DM_01126], [SWS_DM_01130]). Instances are neither copyable nor movable and are bound to Diagnostic Management via a port-specific InstanceSpecifier ([SWS_DM_01124], [SWS_DM_01609]).

Context

The class ara::diag::Authentication provides the application-side interface for handling the UDS service 0x29 (Authentication) within the AUTOSAR Adaptive Platform (AUTOSAR AP SWS Diagnostics p. 63). It acts as a type-safe base for application-specific handlers that control and execute the cryptographic authentication of incoming diagnostic connections.

In the system architecture, the class interacts with two major partners: the external diagnostic tester, which directs authentication requests to the vehicle, and the vehicle-internal Diagnostic Management (DM), which receives, filters, and forwards diagnostic messages to registered handlers ([SWS_DM_01130]). The application implements the interface functions specified by ara::diag::Authentication to verify certificates, calculate challenges, and generate session keys ([SWS_DM_01126], [SWS_DM_01128]).

Context diagram: Embedding of the authentication handler between Diagnostic Management and external diagnostic tester. Sources: [SWS_DM_01124], [SWS_DM_01130], AUTOSAR AP SWS Diagnostics p. 63.

Lifecycle

Instances of ara::diag::Authentication are bound to a specific port model. The constructor expects an ara::core::InstanceSpecifier that references a PortPrototype of a DiagnosticAuthenticationInterface, as well as the parameter ConcurrencyType ([SWS_DM_01124]). The latter specifies whether the implementation is designed to be thread-safe (kConcurrent) or non-thread-safe (kNotConcurrent) ([SWS_DM_01124]). Because the verification callbacks can be invoked reentrantly for different clients ([SWS_DM_01126], [SWS_DM_01127]), Diagnostic Management is expected to serialize the calls to the instance in case of kNotConcurrent. Question Q-5d890d01c54e70ca (open)

Regarding ownership, ara::diag::Authentication is strictly defined as a non-copyable and non-movable single instance: both copy and move constructors as well as the corresponding assignment operators are explicitly deleted ([SWS_DM_01609], [SWS_DM_01610], [SWS_DM_01607], [SWS_DM_01608]). After instantiation, the class does not automatically accept requests. Only by calling Offer() is Diagnostic Management authorized to forward incoming authentication requests to the instance ([SWS_DM_01130]). Forwarding can be deactivated again at any time via StopOffer() ([SWS_DM_01131]). Resources are released deterministically via the virtual destructor ~Authentication() ([SWS_DM_01125]).

Usage Path

A typical use case comprises offering the service, certificate verification, and proof of key ownership (Proof of Ownership):

  1. Offering the service: After instantiation, the application registers with Diagnostic Management via Offer() ([SWS_DM_01130]).
  2. Certificate verification: When an authentication request from the tester arrives, the DM forwards it to the responsible method:
    • In the case of unidirectional authentication, the DM calls VerifyCertificateUnidirectional(...) ([SWS_DM_01126]). The application verifies the passed client certificate and asynchronously returns a tuple consisting of a server challenge and the server's ephemeral public key via ara::core::Future.
    • In the case of bidirectional authentication, the DM calls VerifyCertificateBidirectional(...) ([SWS_DM_01127]). In this process, the application additionally generates the server certificate as well as its own proof of ownership for the tester.
  3. Proof of ownership: If the tester responds to the server challenge, the DM calls the method VerifyOwnership(...) ([SWS_DM_01128]). The application checks the passed clientPOWN together with the client's ephemeral key against the previously generated challenge. Upon success, the future returns the session key information.
  4. Stopping the service: If the interface is to be closed, the application calls StopOffer() ([SWS_DM_01131]).

Sequence diagram: Sequence of unidirectional authentication with subsequent verification of the proof of ownership. Sources: [SWS_DM_01126], [SWS_DM_01128], [SWS_DM_01130].

Error Scenarios

When using ara::diag::Authentication, static modeling errors and dynamic runtime errors must be distinguished:

  • Construction violations: If the model configuration does not match the process or if the InstanceSpecifier is erroneous, construction fails with defined violations (among others InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, or InstanceSpecifierAlreadyInUseViolation) ([SWS_DM_01124]).
  • State errors on offer: Calling Offer() again when the service is already offered fails with the error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_01130]).
  • Cryptographic and protocol errors: If the verification of the client certificate or the proof of ownership fails, the application must resolve the future with a suitable UDS Negative Response Code (NRC) according to ISO 14229-1 via DiagUdsNrcErrc ([SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128]).
  • Connection termination: If an ongoing diagnostic conversation is canceled, the DM signals this via the object CancellationHandler ([SWS_DM_01126]). The application can query the status via cancellationHandler.IsCanceled() or register a callback function via SetNotifier. The passed data spans remain valid only until the promise is fulfilled or processing is canceled ([SWS_DM_01126], [SWS_DM_01128]).

The constructor synchronously initializes an object of handler class ara::diag::Authentication to process diagnostic authentication requests on a software port [SWS_DM_01124]. The parameter specifier refers to the modeled PortPrototype, which must mandatory be typed by a DiagnosticAuthenticationInterface via a DiagnosticAuthenticationPortMapping [SWS_DM_01124]. Via the parameter concurrencyType, it is defined whether the framework delivers method calls concurrently (kConcurrent) or non-thread-safely (kNotConcurrent) [SWS_DM_01124].

Since the function is declared as noexcept, incorrect calls are not reported via exceptions, but trigger framework violations [SWS_DM_01124]:

  • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the Executable or does not reference a PortPrototype [SWS_DM_01124].
  • PortInterfaceMappingViolation: The referenced PortPrototype is not modeled as a DiagnosticAuthenticationInterface [SWS_DM_01124].
  • ProcessMappingViolation: At runtime, no matching modeled process is found [SWS_DM_01124].
  • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier has already been used for an instance in the current process [SWS_DM_01124].

The constructor itself is thread-safe and exception-safe [SWS_DM_01124], whereas the associated destructor ~Authentication() is specified as not thread-safe [SWS_DM_01125]. Immediately after instantiation, no diagnostic requests are forwarded yet: the application must first call Offer() to activate forwarding for the UDS service 0x29 (Authentication with PKI Certificate Exchange, APCE AUTOSAR_AP_SWS_Diagnostics Tab. 4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”) by the Diagnostic Manager [SWS_DM_01130]. Certificate validation is subsequently processed via VerifyCertificateUnidirectional [SWS_DM_01126], VerifyCertificateBidirectional [SWS_DM_01127], and VerifyOwnership [SWS_DM_01128]. Before object destruction, forwarding must be stopped with StopOffer() [SWS_DM_01131].

              With the synchronous method Offer() of class ara::diag::Authentication ([SWS_DM_01130]), an Adaptive Application registers its authentication handler with Diagnostic Management (DM). As a result, the DM is authorized and enabled to forward incoming requests to this handler (AUTOSAR_AP_SWS_Diagnostics §8.3.1.1.3.1 “Offer”). The function takes no input parameters and indicates the outcome of the operation via the return type ara::core::Result<void>.
              
  
              The call is declared as noexcept and is thus exception-safe ([SWS_DM_01130]). If registration fails because the service has already been provided for this instance previously, the specific error code DiagOfferErrc::kAlreadyOffered is returned in the result object ([SWS_DM_01130]). In addition, the interface is specified as not thread-safe; parallel accesses to the same instance must presumably not occur unprotected and must be synchronized on the application side. Question Q-51ab72e4e72a7351 (open)
              
  
              In the lifecycle of diagnostic processing, Offer() corresponds directly to the counter-function StopOffer() ([SWS_DM_01131], AUTOSAR_AP_SWS_Diagnostics §8.3.1.1.3.2 “StopOffer”), which terminates the forwarding of requests again. This pattern follows the uniform offering approach of diagnostic handlers, as also applied for example in ara::diag::CommunicationControl::Offer ([SWS_DM_00809]) or ara::diag::DoIPPowerMode::Offer ([SWS_DM_00735]), where requests can only be processed after explicit offering by the application ([SWS_DM_01525]).

The call is executed synchronously, requires no input parameters, and has no return value AUTOSAR_AP_SWS_Diagnostics §8.3.1.1.3.2 “StopOffer”.
                  


                  Error Handling and Execution Safety
                  

                  The function is specified as exception safe (noexcept); specific error codes or exceptions are not defined [SWS_DM_01131].
                  


                  Concurrency and Limitations
                  

                  The operation is explicitly designated as not thread-safe (“not thread-safe”) [SWS_DM_01131]. Concurrent calls on the same instance must be synchronized by the calling application.
                  


                  Interaction and Architectural Context
                  

                  The design pattern of StopOffer is used consistently across various services and handlers in the Adaptive Diagnostic Manager, including SecurityAccess [SWS_DM_00767], CommunicationControl [SWS_DM_00810], DownloadService [SWS_DM_00793], and EcuResetRequest [SWS_DM_01017]. Although the naming is based on service offering in ara::com, it is a diagnostics-specific implementation AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”.
