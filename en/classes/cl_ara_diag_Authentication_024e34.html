Context

The class ara::diag::Authentication provides the interface for adaptive applications to handle UDS service authentication (UDS service 0x29 Authentication) as a service handler AUTOSAR_AP_SWS_Diagnostics §4.1 “Limitations of sub-functions”. The application implements the pure virtual methods of this class to perform incoming cryptographic checks, while the Diagnostic Manager (DM) controls the forwarding of diagnostic requests [SWS_DM_01130].

The interaction comprises three essential parties: the external diagnostic tester, the Diagnostic Manager as mediator of the UDS messages, and the adaptive application, which takes over the actual certificate and ownership verification via a concrete subclass of ara::diag::Authentication [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].

Context diagram: Integration of ara::diag::Authentication between diagnostic tester, Diagnostic Manager, and application. Sources: [SWS_DM_01130], [SWS_DM_01126], AUTOSAR_AP_SWS_Diagnostics §4.1

Lifecycle

Instantiation is performed explicitly by specifying an ara::core::InstanceSpecifier and an ConcurrencyType [SWS_DM_01124]. The InstanceSpecifier references a modeled PortPrototype of an DiagnosticAuthenticationInterface. Via the parameter concurrencyType, the application specifies whether calls are processed in a thread-safe (kConcurrent) or non-thread-safe (kNotConcurrent) manner [SWS_DM_01124]. Instances of ara::diag::Authentication are strictly bound to their identity: copy and move constructors as well as assignment operators are deleted (=delete) [SWS_DM_01609], [SWS_DM_01610], [SWS_DM_01607], [SWS_DM_01608].

After creation, the handler is initially in the passive state. Only by calling Offer() is the Diagnostic Manager authorized to forward incoming diagnostic requests to the instance [SWS_DM_01130]. The method StopOffer() deactivates this forwarding again [SWS_DM_01131]. When destroying the instance via the virtual destructor ~Authentication(), the lifecycle ends; this destructor is specified as not thread-safe [SWS_DM_01125].

Usage Path

The typical flow of a diagnostic authentication follows a fixed sequence of preparation, certificate verification, and proof of ownership:

  1. Offering: The application instantiates its derived Authentication class and announces its readiness to receive via Offer() to the Diagnostic Manager [SWS_DM_01124], [SWS_DM_01130].
  2. Certificate verification: Upon receipt of an authentication request, the Diagnostic Manager calls either VerifyCertificateUnidirectional() [SWS_DM_01126] or VerifyCertificateBidirectional() [SWS_DM_01127], depending on the diagnostic configuration. The application checks the transmitted client certificate and the challenge of the tester. As a response, it returns asynchronously via an ara::core::Future a generated server challenge as well as the ephemeral public key (in the case of bidirectional authentication, additionally the server certificate and its own proof of ownership) [SWS_DM_01126], [SWS_DM_01127].
  3. Proof of ownership (Proof of Ownership): In the subsequent step, the DM calls the method VerifyOwnership() [SWS_DM_01128]. The application verifies the proof of ownership (clientPOWN) transmitted by the tester against the public key from the previously received certificate and the generated server challenge. In case of success, it returns the session key information in the Future [SWS_DM_01128].
  4. Deregistration: Before shutting down, the application withdraws the offer by means of StopOffer() [SWS_DM_01131].

The callbacks can be called reentrantly for requests from different clients [SWS_DM_01126], [SWS_DM_01127]. Via the passed CancellationHandler, the application can check whether processing was canceled, or register a cancellation notifier [SWS_DM_01126], [SWS_DM_01128].

Sequence diagram: Typical flow of authentication via the Diagnostic Manager. Sources: [SWS_DM_01130], [SWS_DM_01126], [SWS_DM_01128], [SWS_DM_01131]

Error Scenarios

When using ara::diag::Authentication, the following error conditions and pre-checks must be taken into account:

  • Construction errors (violations): If the mapping of the InstanceSpecifier fails (e.g. InstanceSpecifierMappingIntegrityViolation or PortInterfaceMappingViolation), the process is not configured correctly (ProcessMappingViolation), or an identifier that is already in use is specified again (InstanceSpecifierAlreadyInUseViolation), the platform reports a corresponding violation [SWS_DM_01124].
  • Multiple offering: If Offer() is called while the service is already being offered, the method returns an error with the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_01130].
  • Verification and protocol errors: If the certificate check or the verification of the proof of ownership fails (e.g. invalid signature or expired certificate), the application returns a corresponding ISO-14229-1 Negative Response Code (NRC) in the Future using DiagUdsNrcErrc [SWS_DM_01126], [SWS_DM_01127], [SWS_DM_01128].
  • Premature cancellation: If the diagnostic conversation is aborted on the part of the tester or the DM, cancellationHandler.IsCanceled() reports the value TRUE; the application should cancel the cryptographic operations in order to free computing resources [SWS_DM_01126].

This guide is based on the requirements of the AUTOSAR Adaptive specification R25-11.
