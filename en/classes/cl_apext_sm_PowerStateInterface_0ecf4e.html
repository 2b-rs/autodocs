Context

The interface class apext::sm::PowerStateInterface defines the functional connection between State Management (SM) and the underlying operating system for coordinating power states [SWS_SM_71000]. Within the Adaptive Platform, it serves as an abstraction layer through which State Management can delegate requests for global or platform-specific power state changes to the operating system [SWS_SM_71001]. At the same time, it enables the reception of system wake-up signals via a dedicated callback mechanism [SWS_SM_71003].

Primarily three roles are involved in the coordination: State Management as the controlling entity, the interface class apext::sm::PowerStateInterface as an intermediary, and the OS wrapper or the operating system itself, which executes the actual hardware and state transitions AUTOSAR_AP_SWS_StateManagement §C.1.2 “Class: PowerStateInterface”.

Context diagram: Components involved in the coordination of power states. Sources: [SWS_SM_71000], [SWS_SM_71001], [SWS_SM_71003].

Lifecycle

The instantiation of apext::sm::PowerStateInterface takes place in the context of State Management initialization, as the coordination of power states affects fundamental platform services [SWS_SM_71000]. The lifetime of an instance is likely typically bound to the process lifecycle of the State Management daemon in order to be able to accept and process requests throughout the entire active operating time.

With regard to the internal lifecycle, the interface essentially distinguishes two operating phases regarding notification:

  • Registered state: After a successful call to RegisterWakeUpHandler, a notification function is stored in the OS wrapper, via which State Management is notified of wake-up events [SWS_SM_71003].
  • Unregistered state: Calling UnregisterWakeUpHandler removes the callback from the OS wrapper, so that subsequent wake-up events no longer trigger signaling to this handler [SWS_SM_71005].

With regard to concurrency, all member functions of the class (RegisterWakeUpHandler, SetPowerState, and UnregisterWakeUpHandler) are explicitly specified as not thread-safe (not-threadsafe) AUTOSAR_AP_SWS_StateManagement §C.1.2.1.1 “Member Functions”. Calls from concurrent threads must therefore be serialized by the caller or restricted to a dedicated execution context.

Usage Path

A typical usage path comprises the registration of the callback function, the forwarding of state requests to the operating system, and the final deregistration before shutdown or during reconfigurations:

  1. Register wake-up handler: Before initiating sleep states, State Management registers a function pointer or function object of type apext::sm::WakeUpHandler using RegisterWakeUpHandler [SWS_SM_71003]. This instructs the OS wrapper to inform the SM upon wake-up.
  2. Request power state: State Management requests the transition via SetPowerState with the desired target state (apext::sm::PowerState) [SWS_SM_71001]. The function synchronously forwards this request to the operating system.
  3. Process wake-up notification: As soon as the operating system wakes up, the OS wrapper executes the previously registered handler [SWS_SM_71003], allowing State Management to initiate its wake-up logic.
  4. Deregister handler: If the wake-up mechanism is no longer required or the component is to be terminated, State Management deregisters the callback using UnregisterWakeUpHandler [SWS_SM_71005].

Sequence diagram: Typical sequence of handler registration, state request, wake-up notification, and deregistration. Sources: [SWS_SM_71001], [SWS_SM_71003], [SWS_SM_71005].

Error Scenarios

All three specified methods of the interface have the return type void and are declared with the specification noexcept AUTOSAR_AP_SWS_StateManagement §C.1.2.1.1 “Member Functions”:

  • Exception safety: Each function is classified as exception-safe (exception safe) [SWS_SM_71001], [SWS_SM_71003], [SWS_SM_71005]. Neither during handler registration nor when sending state changes are C++ exceptions thrown.
  • Error signaling: Since no return codes or ara::core::Result types are returned, no direct error handling or feedback on failed OS transitions to the immediate caller occurs at the level of this interface class.
  • Preconditions: Since the methods are not thread-safe, concurrent unprotected access leads to undefined behavior. In addition, a passed callback of type apext::sm::WakeUpHandler presumably must remain valid until its deregistration via UnregisterWakeUpHandler [SWS_SM_71005].
