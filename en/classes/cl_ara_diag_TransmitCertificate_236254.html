Enables the application to receive and verify diagnostic certificates in the UDS Authentication service.

The class ara::diag::TransmitCertificate implements the application interface for the UDS sub-function TransmitCertificate (0x29 0x04) of the service Authentication [SWS_DM_01961]. After release via Offer(), the application receives transmitted certificate data in the asynchronous method Process() and initiates application-specific verification [SWS_DM_01968]. Upon successful verification, Diagnostic Management triggers a positive UDS response with the return parameter 0x13 (CertificateVerified), whereas errors are answered as a negative response with a corresponding NRC. The instance is permanently bound to a port interface and must neither be copied nor moved.

Context

The class ara::diag::TransmitCertificate [SWS_DM_01961] in the header ara/diag/transmit_certificate.h (AUTOSAR_AP_SWS_Diagnostics §8.26 “Header: ara/diag/transmit_certificate.h”) represents the interface of the Adaptive Application for realizing the UDS sub-function TransmitCertificate (0x29 0x04) of the service Authentication. As a generic interface, it enables the application to receive and process one or more transmitted certificates based on a 16-bit identifier (certificateEvaluationId).

Three main components are involved in the interaction:

  • The external diagnostic tester, which sends the UDS request for certificate transmission to the vehicle [SWS_DM_01968].
  • The Diagnostic Server (Diagnostic Management, DM) of the Adaptive Platform, which filters incoming diagnostic requests, forwards them, and generates the final UDS responses [SWS_DM_01251], [SWS_DM_01969].
  • The Adaptive Application, which provides an instance derived from ara::diag::TransmitCertificate, performs the certificate verification, and returns the result asynchronously to the server [SWS_DM_01968].

Context diagram: Involved components during certificate transmission via UDS 0x29 04. Sources: [SWS_DM_01968], [SWS_DM_01969], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Successful verification of transmitCertificate”.

Lifecycle

Instances of ara::diag::TransmitCertificate are created via the constructor by specifying an ara::core::InstanceSpecifier as well as the concurrency mode ConcurrencyType [SWS_DM_01962]. In the manifest, the InstanceSpecifier must reference an PortPrototype that is typed by an DiagnosticTransmitCertificateInterface [SWS_DM_01962]. If this mapping fails or if the instance identifier is used multiple times in the current process, runtime violations such as InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, or InstanceSpecifierAlreadyInUseViolation occur [SWS_DM_01962].

The class is subject to strict ownership and instantiation rules: An authentication handler is designed as a unique, non-copyable, and non-movable instance. Accordingly, the copy constructor [SWS_DM_01964], copy assignment operator [SWS_DM_01966], move constructor [SWS_DM_01963], and move assignment operator [SWS_DM_01965] are explicitly deleted (=delete).

The constructor itself is specified as thread-safe and exception-safe [SWS_DM_01962]. Destruction is performed via the default virtual destructor [SWS_DM_01967]. Whether the actual execution method Process must be implemented in a thread-safe manner depends on the selected concurrencyType (kConcurrent or kNotConcurrent) [SWS_DM_01962], [SWS_DM_01968].

Usage Path

The regular flow comprises handler registration, processing of incoming certificates, and subsequent deregistration:

  1. Offer service (Offer): The application calls Offer() to signal to Diagnostic Management that requests for the configured interface may be forwarded to this handler [SWS_DM_01969].
  2. Receive request (Process): If a UDS request of the sub-function TransmitCertificate arrives at the Diagnostic Server, it forwards the data to the pure virtual method Process() of the application [SWS_DM_01968]. The method receives the 16-bit identifier certificateEvaluationId, the raw certificate data as ara::core::Span<ara::core::Byte const>, metadata (metaInfo), and an cancellationHandler [SWS_DM_01968].
  3. Evaluation and action: Since AUTOSAR does not prescribe fixed semantics for the certificates, verification and the derivation of necessary actions are entirely the responsibility of the application [SWS_DM_01968]. Interpretation: The application is typically expected to verify the transmitted certificate cryptographically or use it to update an internal key storage.
  4. Result transmission: The method returns an ara::core::Future<void> [SWS_DM_01968]. If the application completes the future successfully without errors, the Diagnostic Server transmits a positive UDS response to the tester in which the parameter authenticationReturnParameter (RV) is set to the value 0x13 (CertificateVerified) [SWS_DM_01251] (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Successful verification of transmitCertificate”).
  5. Stop service (StopOffer): If the handler is no longer to receive requests, the application terminates forwarding by calling StopOffer() [SWS_DM_01970].

Sequence diagram: Typical sequence of certificate transmission from Offer to the UDS response. Sources: [SWS_DM_01968], [SWS_DM_01969], [SWS_DM_01970], [SWS_DM_01249], [SWS_DM_01251].

Error Scenarios

Error states can occur in different phases of the lifecycle:

  • Already active offer: If Offer() is called even though the service is already actively offered for this instance, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered with rollback semantics in the ara::core::Result<void> [SWS_DM_01969]. Offer() and StopOffer() are not thread-safe and must not be called concurrently [SWS_DM_01969], [SWS_DM_01970].
  • Failed certificate verification: If the application detects an error during evaluation in Process(), it completes the future with a corresponding error code from DiagUdsNrcErrc according to ISO 14229-1 [SWS_DM_01968]. The Diagnostic Server intercepts this return value and sends a negative diagnostic response (Negative Response) to the tester, whose Negative Response Code (NRC) corresponds exactly to the transmitted error code [SWS_DM_01249] (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8 “Handling Negative return values of ara::diag::TransmitCertificate::Process method”).
  • Cancellation of ongoing conversations: During asynchronous processing, the application can query the status via cancellationHandler.IsCanceled() to determine whether the diagnostic conversation was canceled [SWS_DM_01968]. In addition, a callback function can be registered via cancellationHandler.SetNotifier(...) that is notified immediately upon cancellation [SWS_DM_01968].

function Offer [SWS_DM_01969] Upstream: RS_Diag_04251

ara::core::Result< void > Offer () noexcept;

This Offer will enable the DM to forward request messages to this handler.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: db62dd9c27e2 Provenance

Via the method Offer, an Adaptive Application activates the forwarding of diagnostic requests by the Diagnostic Management (DM) to the responsible handler of class ara::diag::TransmitCertificate [SWS_DM_01969]. The call is synchronous and parameterless; the interface is defined as exception-safe (noexcept) [SWS_DM_01969]. ara::core::Result<void> serves as the return type, communicating the success of the registration or an error state to the caller [SWS_DM_01969].

If the function has already been called previously for the relevant handler instance, a renewed call fails and returns the specific error DiagOfferErrc::kAlreadyOffered with rollback semantics [SWS_DM_01969], which corresponds to the standardized error value in DiagErrc [SWS_DM_00514]. Because the method is explicitly specified as not thread-safe [SWS_DM_01969], concurrent accesses to the same instance must be avoided (Interpretation: Protection against concurrent calls is the responsibility of the application software).

The functional pattern of Offer follows the unified provision concept of diagnostic handlers, as also applied to ara::diag::Authentication::Offer [SWS_DM_01130], ara::diag::CommunicationControl::Offer [SWS_DM_00809], or ara::diag::GenericRoutine::Offer [SWS_DM_00557]. AUTOSAR clarifies that despite naming aligned with ara::com, this is an independent diagnostic implementation (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”). Prior to provision by Offer, the DM does not forward any requests to the handler, analogously to DoIP services which are considered not ready prior to the call [SWS_DM_01525].

          The method StopOffer of class ara::diag::TransmitCertificate ([SWS_DM_01970]) terminates the provision of the certificate transmission service for Diagnostic Management (DM). Calling it deactivates the forwarding of incoming diagnostic request messages from the DM to this handler ([SWS_DM_01970]).
          


          Usage and Semantics
          

          The call is parameterless via the signature void StopOffer() noexcept; from header ara/diag/transmit_certificate.h ([SWS_DM_01970]). The function does not return a value and is specified as noexcept as well as exception safe ([SWS_DM_01970]), so that it is guaranteed not to throw any exceptions.
          


          Concurrency and Limitations
          

          The method is explicitly specified as not thread-safe ([SWS_DM_01970]). Callers must therefore ensure that concurrent calls on the same instance of ara::diag::TransmitCertificate are synchronized by external mechanisms. Interpretation: Prior to destroying a service instance or during temporary deactivation, StopOffer is likely called to prevent the arrival of new requests during the state transition.
          


          Interaction
          

          The concept corresponds to the standardized DM pattern for disabling message forwarding, as also defined in related interfaces such as [SWS_DM_00767] (SecurityAccess), [SWS_DM_00810] (CommunicationControl), or [SWS_DM_01017] (EcuResetRequest). Although this vendor-specific diagnostic implementation shares its naming with the communication framework, it is to be distinguished from ara::com (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”). The element serves to fulfill the upstream requirement RS_Diag_04251, which also underlies the authentication interface (AUTOSAR_AP_SWS_Diagnostics §8.3.1.1.3.2 “StopOffer”; [SWS_DM_01131]).
