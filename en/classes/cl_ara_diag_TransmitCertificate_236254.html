class ara::diag::TransmitCertificate

[SWS_DM_01961] Upstream: RS_Diag_04251

class TransmitCertificate {...};

Class to implement the subfunction TransmitCertificate (29 04) of UDS service Authentication as interface to application. This class implements a so called generic interface, where the application has means to handle one ore more certificateEvaluationId transferred certificates.

Context

The class ara::diag::TransmitCertificate provides the programming interface for the UDS subfunction TransmitCertificate (0x29 04) of the service Authentication (0x29) AUTOSAR_AP_SWS_Diagnostics §8.26.1 “Class: TransmitCertificate”. It implements a generic interface via which an Adaptive Application can receive and evaluate one or more certificates identified by a 16-bit identifier (certificateEvaluationId).

In the system architecture, ara::diag::TransmitCertificate acts as a link between the AUTOSAR Adaptive Diagnostic Manager (DM) or the Diagnostic Server Instance and the concrete application logic. An external diagnostic tester sends the UDS authentication request to the server, which forwards the request to the application after activation [SWS_DM_01968], [SWS_DM_01251].

Context diagram: Embedding of TransmitCertificate between diagnostic tester, Diagnostic Manager, and application logic. Sources: [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01249].

Lifecycle

Instantiation takes place via the constructor by specifying a [SWS_DM_01962]:

  • specifier: A ara::core::InstanceSpecifier that references a PortPrototype which is typed via a DiagnosticAuthenticationPortMapping [SWS_DM_01962].
  • concurrencyType: Defines whether the subsequent execution of Process is treated as thread-safe (kConcurrent) or non-thread-safe (kNotConcurrent) [SWS_DM_01962], [SWS_DM_01968].

Copy and move operations are completely prevented: copy constructor [SWS_DM_01964], move constructor [SWS_DM_01963], copy assignment operator [SWS_DM_01966], and move assignment operator [SWS_DM_01965] are declared as deleted (=delete). An authentication interface instance thus exists as a uniquely bound object.

Following construction, the life cycle is divided into two operating phases:

  1. Provision (Offered): By calling Offer(), the Diagnostic Manager is authorized to forward incoming UDS messages for the subfunction to the method Process() [SWS_DM_01969].
  2. Revocation (Stopped): Calling StopOffer() deregisters the forwarding again [SWS_DM_01970].

The destructor is virtual and declared as default (noexcept = default) [SWS_DM_01967]. While the constructor is thread-safe, Offer() and StopOffer() are specified as not thread-safe and must not be called concurrently without coordination [SWS_DM_01962], [SWS_DM_01969], [SWS_DM_01970].

Usage Path

The regular operational sequence comprises registration with the Diagnostic Manager, asynchronous receipt of the certificate data, and completion of processing:

  1. Instantiation and release: The application instantiates the derived class and activates acceptance via Offer() [SWS_DM_01962], [SWS_DM_01969].
  2. Reception and processing: Upon receipt of a UDS request, the Diagnostic Server forwards the data via Process(certificateEvaluationId, certificateData, metaInfo, cancellationHandler) [SWS_DM_01968]. The method returns a ara::core::Future<void>, thereby supporting asynchronous processing. The concrete semantics and evaluation of the certificate are entirely the responsibility of the application [SWS_DM_01968].
  3. Cancellation handling: The application can check via cancellationHandler.IsCanceled() whether the diagnostic conversation was canceled, or register a notification callback for cancellation events via cancellationHandler.SetNotifier() [SWS_DM_01968].
  4. Positive response: If the execution completes successfully without an error code, the Diagnostic Server Instance transmits a positive UDS response with the return parameter authenticationReturnParameter = 0x13 (CertificateVerified) to the tester [SWS_DM_01251].
  5. Cleanup: Upon termination, reception is stopped via StopOffer() [SWS_DM_01970].

Sequence diagram: Typical flow of certificate transmission and processing. Sources: [SWS_DM_01969], [SWS_DM_01968], [SWS_DM_01251], [SWS_DM_01970].

Error Scenarios

Specific error conditions are defined both during initialization and during ongoing operation:

  • Manifest and modeling errors during creation: The constructor reports violations if the InstanceSpecifier cannot be resolved (InstanceSpecifierMappingIntegrityViolation), the referenced PortPrototype is not typed by a DiagnosticTransmitCertificateInterface (PortInterfaceMappingViolation), no process mapping exists (ProcessMappingViolation), or the InstanceSpecifier is already assigned in the process (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01962].
  • Multiple registration: A renewed call to Offer() when offering is already active leads to error DiagOfferErrc::kAlreadyOffered with rollback semantics [SWS_DM_01969].
  • Rejection in process: If the verification of the certificate fails in the application or a processing error occurs, Process() returns a corresponding error via the ara::core::Future. In this case, an appropriate UDS Negative Response Code (NRC) according to ISO 14229-1 must be used via DiagUdsNrcErrc [SWS_DM_01968]. The Diagnostic Server Instance then generates a negative UDS response (NRC) to the external tester [SWS_DM_01249].

This guide is based on the AUTOSAR Adaptive Platform R25-11 specification for the Diagnostics module.
