Context

The class ara::com::ComErrorDomain represents the standardized error domain for general errors of communication management (ara::com). It encompasses error states that can occur during calls to service methods (ServiceInterface), but are not defined specifically for a single service interface (SWS CommunicationManagement §7.5.22.6 [SWS_CM_11265]).

As a derivation of the base class ara::core::ErrorDomain, ComErrorDomain integrates the communication errors into the uniform error model of AUTOSAR Adaptive (EXP ARAComAPI §4.7). Recoverable errors (Recoverable Errors) are not thrown as exceptions, but are returned to the application via instances of ara::core::ErrorCode [SWS_CORE_00501] within a ara::core::Result (EXP ARAComAPI §4.7).

The essential interaction partners are:

  • Adaptive Application: Initiates method calls, receives ara::core::Result objects, and evaluates the error code contained therein based on the error domain (EXP ARAComAPI §4.7).
  • Service methods (Method class): The ara::com runtime environment executes remote calls via the function call operator operator() [SWS_CM_00196] and, in the event of errors, completes the corresponding ara::core::Promise via SetError [SWS_CORE_00353] with the domain ComErrorDomain [SWS_CM_11329] (SWS CommunicationManagement §7.4.2).
  • Delimitation from other domains: General communication errors differ from specific end-to-end errors of the domain ara::com::e2e::ComE2EErrorDomain as well as from functional application errors (ApApplicationError) (SWS CommunicationManagement §7.5.22.6, EXP ARAComAPI §4.7).

Context diagram: Embedding of ComErrorDomain into the error architecture of ara::com and ara::core. Sources: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.5.22.6.

Lifecycle

The class ComErrorDomain is declared as final and inherits publicly from ara::core::ErrorDomain. Its lifecycle is subject to fixed architectural specifications:

  • Creation: The default constructor ComErrorDomain() is explicitly deleted (= delete) [SWS_CM_11330]. Direct creation of instances by the application logic is therefore prevented.
  • Instance management: Interpretation: Since error domains in the AUTOSAR Adaptive standard function as global descriptors per process, the platform is likely to provide a long-lived singleton instance accessed by internal runtime structures and error codes.
  • State and ownership: The class encapsulates purely static type and translation information and manages no mutable state of individual service instances.
  • Concurrency: The information functions Name() [SWS_CM_11331] and Message() [SWS_CM_11332] are const, declared as noexcept, and specified as exception-safe ("exception safe"). Since they return constant strings, they can be called concurrently from arbitrary threads without additional synchronization.

Usage Path

The typical call sequence in the event of an error is divided into the following steps:

  1. Method call: An application calls a service method via operator() of the Method class [SWS_CM_00196] and receives a ara::core::Future in return.
  2. Error detection: If a general error occurs during communication—for example, a transmission error or an unconfigured application error [SWS_CM_00048]—the corresponding Promise is set to the error state by means of SetError [SWS_CORE_00353] (SWS CommunicationManagement §7.4.2).
  3. Error code assignment: The passed ara::core::ErrorCode [SWS_CORE_00501] references the error domain ara::com::ComErrorDomain [SWS_CM_11329] and sets the code, for example, to ComErrc::kCommunicationFailure (EXP ARAComAPI §2.1, SWS CommunicationManagement §7.4.2 [SWS_CM_10432]).
  4. Result evaluation: The application checks the returned ara::core::Result (EXP ARAComAPI §4.7). If it contains an error code, the application can:
    • query the domain designation by means of Name() [SWS_CM_11331] ([SWS_CORE_90023]),
    • retrieve the plain-text error message for logging purposes via Message(errorCode) [SWS_CM_11332],
    • or throw an exception via ThrowAsException(errorCode) [SWS_CM_11333].

Sequence diagram: Process of error handling for a method call with ComErrorDomain. Sources: EXP ARAComAPI §4.7, SWS CommunicationManagement §7.4.2, [SWS_CM_11332], [SWS_CM_11333].

Error Scenarios

The specification of error handling via ComErrorDomain includes the following details:

  • Error code enumeration and type aliases: Via the type alias Errc [SWS_CM_11336], the class provides the enumeration ComErrc, which defines the error codes of the domain (SWS CommunicationManagement §8.2). The type alias Exception [SWS_CM_11337] refers to the base class ComException.
  • Additional error codes: In addition to standardized error values such as ComErrc::kCommunicationFailure [SWS_CM_10432], a stack vendor may define further vendor-specific error codes in this domain that must be taken into account by the application (EXP ARAComAPI §4.7).
  • Throwing exceptions: The method ThrowAsException() [SWS_CM_11333] creates a ara::com::ComException object from a passed ara::core::ErrorCode and throws it (noexcept(false)). If C++ exceptions are disabled in the compiler, this function does not participate in overload resolution according to [SWS_CORE_10304] [SWS_CM_11333].
  • Classification of error handling: The ara::com API strictly distinguishes between recoverable errors (Recoverable Errors), which are passed deterministically via ara::core::Result, and severe programming errors (Violations or Corruptions), where exceptions are used (EXP ARAComAPI §4.7).

<h4>Lifecycle</h4>
<p>The class <code>ComErrorDomain</code> is declared as <code>final</code> and inherits publicly from <code>ara::core::ErrorDomain</code>. Its lifecycle is subject to fixed architectural specifications:</p>
<ul>
<li><strong>Creation</strong>: The default constructor <code>ComErrorDomain()</code> is explicitly deleted (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_CM_11330" href="../spec/record.html?id=SWS_CM_11330">[SWS_CM_11330]</a>. Direct creation of instances by the application logic is therefore prevented.</li>
<li><strong>Instance management</strong>: Interpretation: Since error domains in the AUTOSAR Adaptive standard function as global descriptors per process, the platform is likely to provide a long-lived singleton instance accessed by internal runtime structures and error codes.</li>
<li><strong>State and ownership</strong>: The class encapsulates purely static type and translation information and manages no mutable state of individual service instances.</li>
<li><strong>Concurrency</strong>: The information functions <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> and <code>Message()</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a> are <code>const</code>, declared as <code>noexcept</code>, and specified as exception-safe ("exception safe"). Since they return constant strings, they can be called concurrently from arbitrary threads without additional synchronization.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical call sequence in the event of an error is divided into the following steps:</p>
<ol>
<li><strong>Method call</strong>: An application calls a service method via <code>operator()</code> of the <code>Method</code> class <a class="spec-record-ref" data-req="SWS_CM_00196" href="../spec/record.html?id=SWS_CM_00196">[SWS_CM_00196]</a> and receives a <code>ara::core::Future</code> in return.</li>
<li><strong>Error detection</strong>: If a general error occurs during communication—for example, a transmission error or an unconfigured application error <a class="spec-record-ref" data-req="SWS_CM_00048" href="../spec/record.html?id=SWS_CM_00048">[SWS_CM_00048]</a>—the corresponding <code>Promise</code> is set to the error state by means of <code>SetError</code> <a class="spec-record-ref" data-req="SWS_CORE_00353" href="../spec/record.html?id=SWS_CORE_00353">[SWS_CORE_00353]</a> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a>).</li>
<li><strong>Error code assignment</strong>: The passed <code>ara::core::ErrorCode</code> <a class="spec-record-ref" data-req="SWS_CORE_00501" href="../spec/record.html?id=SWS_CORE_00501">[SWS_CORE_00501]</a> references the error domain <code>ara::com::ComErrorDomain</code> <a class="spec-record-ref" data-req="SWS_CM_11329" href="../spec/record.html?id=SWS_CM_11329">[SWS_CM_11329]</a> and sets the code, for example, to <code>ComErrc::kCommunicationFailure</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=9">EXP ARAComAPI §2.1</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=300">SWS CommunicationManagement §7.4.2</a> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>).</li>
<li><strong>Result evaluation</strong>: The application checks the returned <code>ara::core::Result</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>). If it contains an error code, the application can:
<ul>
<li>query the domain designation by means of <code>Name()</code> <a class="spec-record-ref" data-req="SWS_CM_11331" href="../spec/record.html?id=SWS_CM_11331">[SWS_CM_11331]</a> (<a class="spec-record-ref" data-req="SWS_CORE_90023" href="../spec/record.html?id=SWS_CORE_90023">[SWS_CORE_90023]</a>),</li>
<li>retrieve the plain-text error message for logging purposes via <code>Message(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11332" href="../spec/record.html?id=SWS_CM_11332">[SWS_CM_11332]</a>,</li>
<li>or throw an exception via <code>ThrowAsException(errorCode)</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a>.</li>
</ul>
</li>
</ol>

<h4>Error Scenarios</h4>
<p>The specification of error handling via <code>ComErrorDomain</code> includes the following details:</p>
<ul>
<li><strong>Error code enumeration and type aliases</strong>: Via the type alias <code>Errc</code> <a class="spec-record-ref" data-req="SWS_CM_11336" href="../spec/record.html?id=SWS_CM_11336">[SWS_CM_11336]</a>, the class provides the enumeration <code>ComErrc</code>, which defines the error codes of the domain (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=439">SWS CommunicationManagement §8.2</a>). The type alias <code>Exception</code> <a class="spec-record-ref" data-req="SWS_CM_11337" href="../spec/record.html?id=SWS_CM_11337">[SWS_CM_11337]</a> refers to the base class <code>ComException</code>.</li>
<li><strong>Additional error codes</strong>: In addition to standardized error values such as <code>ComErrc::kCommunicationFailure</code> <a class="spec-record-ref" data-req="SWS_CM_10432" href="../spec/record.html?id=SWS_CM_10432">[SWS_CM_10432]</a>, a stack vendor may define further vendor-specific error codes in this domain that must be taken into account by the application (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
<li><strong>Throwing exceptions</strong>: The method <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a> creates a <code>ara::com::ComException</code> object from a passed <code>ara::core::ErrorCode</code> and throws it (<code>noexcept(false)</code>). If C++ exceptions are disabled in the compiler, this function does not participate in overload resolution according to <a class="spec-record-ref" data-req="SWS_CORE_10304" href="../spec/record.html?id=SWS_CORE_10304">[SWS_CORE_10304]</a> <a class="spec-record-ref" data-req="SWS_CM_11333" href="../spec/record.html?id=SWS_CM_11333">[SWS_CM_11333]</a>.</li>
<li><strong>Classification of error handling</strong>: The <code>ara::com</code> API strictly distinguishes between recoverable errors (Recoverable Errors), which are passed deterministically via <code>ara::core::Result</code>, and severe programming errors (Violations or Corruptions), where exceptions are used (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=21">EXP ARAComAPI §4.7</a>).</li>
</ul>
