Enables the secure wrapping and unwrapping of keys by means of symmetric key encryption.

The context SymmetricKeyWrapperCtx serves for the cryptographic wrapping and unwrapping of keys using symmetric algorithms. Prior to executing Wrap or UnwrapSymmetricKey, the context must be configured with a compatible key encryption key (KEK) via SetKey [SWS_CRYPT_24018]. All operations require corresponding usage permissions of the involved key objects and report errors via ara::core::Result with rollback semantics [SWS_CRYPT_24014]. The interface is exception-safe and specified as thread-safe for concurrent operation.

Context

The class SymmetricKeyWrapperCtx defines the standardized interface for symmetric key wrapping algorithms within the AUTOSAR Adaptive Platform. Its central responsibility consists in the cryptographic protection of keys during export as well as in restoring wrapped keys for internal use. In doing so, the class primarily interacts with key encryption keys (KEK) that are provided either as a volatile key object of type SymmetricKey or persistently via a KeySlot [SWS_CRYPT_24018], [SWS_CRYPT_50034]. During wrapping, the context accepts a generic CryptoObject [SWS_CRYPT_24014], whereas the unwrapping operation creates and returns a new, ready-to-use SymmetricKey object [SWS_CRYPT_24016].

Lifecycle

Instances of SymmetricKeyWrapperCtx are managed via the typed smart pointer Sptr (an alias for std::shared_ptr<SymmetricKeyWrapperCtx>) [SWS_CRYPT_24001]. The actual object creation is likely performed via a responsible provider factory, as the class represents an abstract interface with pure virtual methods. All member functions of the interface are specified as exception-safe as well as thread-safe, which enables safe use in concurrent software components [SWS_CRYPT_24014], [SWS_CRYPT_24016].

During its lifecycle, the context passes through two main phases: Immediately after instantiation, it is in an uninitialized state. In this phase, cryptographic operations and buffer calculations fail with the error kUninitializedContext [SWS_CRYPT_50035], [SWS_CRYPT_24014]. Only upon the successful call of SetKey with a compatible KEK or KeySlot does the context transition to the operational state in which keys can be securely wrapped or unwrapped [SWS_CRYPT_24018], [SWS_CRYPT_50034].

Usage Path

The regular procedure for wrapping a key requires a coordinated sequence of configuration, buffer verification, and execution. First, the application configures the context via SetKey with the desired KEK object [SWS_CRYPT_24018] or binds a corresponding KeySlot [SWS_CRYPT_50034]. In the second step, the application determines the maximum required output buffer size for the target object to be wrapped via GetRequiredWrappedKeyBufferSize [SWS_CRYPT_50035]. After a correspondingly sized memory area (ReadWriteMemRegion) has been provided, Wrap is called, which writes the serialized and encrypted key data into the buffer and returns the exact number of bytes [SWS_CRYPT_24014].

Sequence diagram: Typical call sequence for symmetric key wrapping. Sources: [SWS_CRYPT_24018], [SWS_CRYPT_50035], [SWS_CRYPT_24014]

For the complementary process of unwrapping, the application passes the input buffer containing the wrapped data to UnwrapSymmetricKey after configuration via SetKey [SWS_CRYPT_24016]. In doing so, the target algorithm identifier (targetAlgId) and the permitted usage flags (allowedUsage) for the symmetric key to be newly created must be explicitly specified [SWS_CRYPT_24016].

Error Scenarios

Methods of the class signal errors via the return type ara::core::Result with rollback semantics. Central error scenarios include:

  • Missing initialization: If GetRequiredWrappedKeyBufferSize, Wrap, or UnwrapSymmetricKey are called before a successful key assignment, they return ara::crypto::CryptoErrc::kUninitializedContext [SWS_CRYPT_50035], [SWS_CRYPT_24014], [SWS_CRYPT_24016].
  • Violation of usage rights: When setting the KEK, it must possess at least the permission kAllowKeyWrapping or kAllowKeyUnwrapping; otherwise, SetKey fails with ara::crypto::CryptoErrc::kUsageViolation [SWS_CRYPT_24018]. For Wrap, the absence of kAllowKeyWrapping on the KEK or the absence of kAllowSecuredExport on the object to be wrapped likewise leads to kUsageViolation [SWS_CRYPT_24014]. During unwrapping, a check is performed to determine whether the KEK permits kAllowKeyUnwrapping [SWS_CRYPT_24016].
  • Incompatibilities and buffer errors: If the target buffer for Wrap is too small, ara::crypto::CryptoErrc::kInsufficientCapacity is reported [SWS_CRYPT_24014]. Faulty key formats or incompatible types lead to ara::crypto::CryptoErrc::kInvalidArgument [SWS_CRYPT_24014], [SWS_CRYPT_24016]. If the context only supports slots or only key objects, SetKey reports the error kUnsupported [SWS_CRYPT_24018], [SWS_CRYPT_50034].
  • Resource conflicts and empty slots: If the operation accesses a busy resource, ara::crypto::CryptoErrc::kBusyResource is returned; if the referenced KeySlot is empty, this results in ara::crypto::CryptoErrc::kEmptyKeySlot [SWS_CRYPT_24014], [SWS_CRYPT_24016].

      Usage and Semantics
      

      The synchronous member function SetKey configures an instance of ara::crypto::cryp::SymmetricKeyWrapperCtx such that the passed object SymmetricKey::Sptr is used as a Key Encryption Key (KEK) for subsequent key operations [SWS_CRYPT_24018]. The function is specified as a pure virtual method with noexcept and returns an empty ara::core::Result<void> if the assignment was successful [SWS_CRYPT_24018].
      


      Error Handling and Rollback
      

      If an error occurs during configuration, mandatory rollback semantics apply, ensuring that the state of the context remains unchanged [SWS_CRYPT_24018]. Possible error causes are mapped via error codes from ara::crypto::CryptoErrc:
      

        

      • kIncompatibleObject: The passed key object is incompatible with the symmetric context [SWS_CRYPT_24018].
        • 

      • kUsageViolation: The permitted usage of the key includes neither kAllowKeyWrapping nor kAllowKeyUnwrapping [SWS_CRYPT_24018].
        • 

      • kUnsupported: The context implementation exclusively supports setting a key via a KeySlot [SWS_CRYPT_24018].
        • 

      


      Concurrency and Interaction
      

      The method is specified as thread-safe and exception safe [SWS_CRYPT_24018]. If keys are managed via slots or the context exclusively supports KeySlots, the alternative overload SetKey with KeySlot::Sptr exists for the same wrapper context [SWS_CRYPT_50034]. This configures the context to load the key stored in the slot at the execution time of the key wrapping [SWS_CRYPT_50034].
