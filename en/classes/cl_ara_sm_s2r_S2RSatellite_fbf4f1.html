Receives Suspend-to-RAM notifications for applications for coordinated preparation and resume.

The interface ara::sm::s2r::S2RSatellite serves Adaptive Applications as a receiver for Suspend-to-RAM notifications from State Management ([SWS_SM_81002], AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”). Following initialization and activation via Offer(), the implemented callback functions EnterSuspendMode() and LeaveSuspendMode() are called to asynchronously control application-specific preparations such as data backup or service restarts ([SWS_SM_00710], [SWS_SM_81010], [SWS_SM_81011]). Registration with the central hub strictly requires an appropriately modeled and IAM-authenticated process context ([SWS_SM_00715]).

Context

The abstract base class ara::sm::s2r::S2RSatellite defines the interface for Adaptive Applications to receive notifications for transitioning to and from the \"prepared for Suspend-to-RAM\" state ([SWS_SM_81002], AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”). While the central S2RHub within State Management controls the coordination of the suspend sequences (AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”), the instance of S2RSatellite acts as a local endpoint in the respective application. An Adaptive Application implements the abstract callback functions to perform application-specific preparations such as saving persistent data, stopping offered services, or halting safety-critical activities (AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).

Context diagram: Interaction between Adaptive Application, S2RSatellite, S2RHub, and Identity Access Management. Sources: [SWS_SM_00710], [SWS_SM_00715], AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”, AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”.

Registration and interaction are subject to security checks by Identity and Access Management (IAM): The S2RHub only permits registration if the process context of the satellite matches the configured SuspendToRamSatelliteMapping ([SWS_SM_00715]).

Lifecycle

An instance is created via the explicit constructor S2RSatellite(const ara::core::InstanceSpecifier&) ([SWS_SM_81003]) or via the static factory method Create() ([SWS_SM_81014]). The default constructor is deleted ([SWS_SM_81004]). The class has strict ownership semantics: copy constructor and copy assignment operator are explicitly deleted ([SWS_SM_81007], [SWS_SM_81009]), whereas move constructor and move assignment are permitted, exception-safe, and thread-safe ([SWS_SM_81006], [SWS_SM_81008]).

After instantiation, the object is in the inactive state. Only by calling Offer() does the satellite actively register with the hub and enable the handler calls ([SWS_SM_00710], [SWS_SM_81012]). The satellite remains actively registered until StopOffer() is called ([SWS_SM_00710], [SWS_SM_81013]). Upon destruction via the virtual destructor ~S2RSatellite() ([SWS_SM_81005]), the instance presumably must have been deregistered previously or is implicitly released. While constructors and assignments are thread-safe, Offer(), StopOffer(), the destructor, and the handlers are non-thread-safe ([SWS_SM_81003], [SWS_SM_81005], [SWS_SM_81010], [SWS_SM_81011], [SWS_SM_81012], [SWS_SM_81013]).

Usage Path

The regular flow includes provision, processing state changes, and final deregistration:

  1. Provision: The application instantiates its derived satellite class and calls Offer() to establish communication readiness with S2RHub ([SWS_SM_00710], [SWS_SM_81012]).
  2. Suspend request: When State Management triggers a suspend operation ([SWS_SM_00701]), the satellite calls the pure virtual method EnterSuspendMode() ([SWS_SM_00711], [SWS_SM_81010]). The application executes its backup routines and signals readiness asynchronously via the returned ara::core::Future<void> ([SWS_SM_81010]).
  3. Resume request: After waking up, the hub requests leaving the suspend mode ([SWS_SM_00703]). The satellite executes the method LeaveSuspendMode() ([SWS_SM_00711], [SWS_SM_81011]), whereupon the application reactivates services.
  4. Termination: Prior to shutdown, the application calls StopOffer(), whereby the satellite is deregistered from the hub and handlers are deactivated ([SWS_SM_00713], [SWS_SM_81013]).

Sequence diagram: Typical flow of registration, Suspend-to-RAM notification, resume, and deregistration. Sources: [SWS_SM_00701], [SWS_SM_00703], [SWS_SM_00710], [SWS_SM_00711], [SWS_SM_00713], [SWS_SM_81010], [SWS_SM_81011], [SWS_SM_81012], [SWS_SM_81013].

Error Scenarios

Errors can already occur during instantiation. The static method Create() returns the error ara::sm::SmErrc::kAuthenticationRequired if a forced IAM switch is active; in this case, the parameterized constructor with InstanceSpecifier must be used instead ([SWS_SM_00716], [SWS_SM_81014]). The constructor S2RSatellite(const ara::core::InstanceSpecifier&) checks modeling and platform states and raises runtime violations in case of errors:

  • AraNotInitializedViolation, if the platform runtime environment is not initialized ([SWS_SM_81003]).
  • InstanceSpecifierMappingIntegrityViolation, if the identifier cannot be resolved or does not refer to a PortPrototype ([SWS_SM_81003]).
  • PortInterfaceMappingViolation, if the interface type does not match the expected interface mapping ([SWS_SM_81003]).
  • ProcessMappingViolation, if no matching modeled process exists for the instance reference ([SWS_SM_81003]).
  • InstanceSpecifierAlreadyInUseViolation, if the instance identifier is already in use within the process ([SWS_SM_81003]).

If registration with Offer() fails due to connection issues with the State Management daemon, the call returns a ara::core::Result with the error SmErrc::kOfferFailed ([SWS_SM_81012]). In case of problems during the execution of EnterSuspendMode() or LeaveSuspendMode(), the satellite signals the error SmErrc::kRejected via the returned Future ([SWS_SM_81010], [SWS_SM_81011]). On the hub side, this leads to the overall result kAtLeastOneHadIssuesToLeave when exiting suspend mode ([SWS_SM_00707]).

use

The static factory method ara::sm::s2r::S2RSatellite::Create serves for the synchronous instantiation of a satellite for direct connection to the S2RHub within the same machine ([SWS_SM_81014]). The call takes no parameters and returns a ara::core::Result<S2RSatellite>, which provides the created satellite object in case of success ([SWS_SM_81014]).

Error handling

If the configuration switch “Force IAM switch” is set to true, the call fails and returns the error code ara::sm::SmErrc::kAuthenticationRequired ([SWS_SM_00716]). In this case, the constructor ara::sm::s2r::S2RSatellite::S2RSatellite must mandatorily be used instead ([SWS_SM_81014]). In addition, a AraNotInitialized-Violation is triggered if the ARA runtime environment is not initialized at the time of the call ([SWS_SM_81014]).

Concurrency and Constraints

The function is specified as thread-safe as well as exception-safe and declared with noexcept ([SWS_SM_81014]). It can thus be called safely from concurrent application contexts.

Interaction

Instances of S2RSatellite are used in S2R-capable applications to process notifications before and after suspend mode (SWS StateManagement §7.5.2 “S2R Satellite”). After successful instantiation, the application registers with the hub via Offer ([SWS_SM_00710]). Before destroying the object, deregistration must be called by means of StopOffer ([SWS_SM_00713]). Interpretation: The method Create is likely intended primarily for application scenarios in which no IAM authentication is forced for the satellite.

      The pure virtual callback method EnterSuspendMode of class ara::sm::s2r::S2RSatellite [SWS_SM_81010] requests a satellite instance to enter suspend mode [SWS_SM_00711]. The call is initiated when the S2R Hub instructs all actively registered satellites via RequestToEnterSuspendMode to transition to the suspend state [SWS_SM_00701]. A prerequisite for receiving this call is that the satellite instance was previously successfully registered with the hub via Offer [SWS_SM_81010] [SWS_SM_00710].
      

      ara::core::Future<void> serves as the return value [SWS_SM_81010]. If the application can successfully enter suspend mode, the future is fulfilled with void [SWS_SM_81010]. If an error occurs, the future must be completed with the error code SmErrc::kRejected [SWS_SM_81010]. If at least one satellite reports kRejected, the hub request returns the overall result kAtLeastOneRejected [SWS_SM_00702]. If a satellite does not respond in time within the timeout, communication is aborted with the error kCommunicationTimeout AUTOSAR_AP_SWS_StateManagement p. 36.
      

      Regarding concurrency, the interface is defined as not thread-safe (not-threadsafe) and not exception-safe (not exception safe) [SWS_SM_81010]. Before destroying the satellite object, StopOffer must be called; this call unregisters the satellite and blocks until running callback executions are finished [SWS_SM_00713]. Since the method is declared as pure virtual, the concrete implementation is likely done in a derived application class in order to persist local states before suspend-to-RAM.

As an interpretation, the application-specific resume logic is likely implemented in a class derived from ara::sm::s2r::S2RSatellite.
          


          Usage and Call Context
          

          The call is asynchronous and is initiated by receiving a resume trigger at the satellite [SWS_SM_00711]. This trigger originates from ara::sm::s2r::S2RHub::RequestToLeaveSuspendMode, which sends a message to all actively registered satellite instances [SWS_SM_00703]. The method expects no parameters and returns a ara::core::Future<void> [SWS_SM_81011].               The synchronous member function ara::sm::s2r::S2RSatellite::Offer registers a satellite instance with the central S2R hub [SWS_SM_00710]. The parameterless call activates the reception of notifications so that application-side callbacks for the transition into suspend mode as well as waking up again can be invoked [SWS_SM_81012], [SWS_SM_81010], [SWS_SM_81011]. The method returns a ara::core::Result<void> and is declared as exception safe (noexcept) [SWS_SM_81012].
              

              In the regular case of success, the returned Result is empty [SWS_SM_81012]. If the service cannot be provided due to disrupted communication with the State Management daemon, the call fails with error code SmErrc::kOfferFailed [SWS_SM_81012]. In addition, the process context of the satellite must conform to the IAM requirements for the registered application, as unauthorized instances are rejected [SWS_SM_00715]. Interpretation: If registration fails, the instance is likely to remain unregistered with the hub.
              

              With regard to concurrency, Offer is specified as not thread-safe (not thread-safe) [SWS_SM_81012]; parallel calls on the same instance therefore require external synchronization. After successful offering, the satellite remains actively registered until the application explicitly calls ara::sm::s2r::S2RSatellite::StopOffer [SWS_SM_00710]. Deregistration via StopOffer must occur before destruction of the satellite and blocks until running callbacks are completed [SWS_SM_00713].

                                  Usage and Semantics
                                  

                                  The method StopOffer() deregisters an instance of ara::sm::s2r::S2RSatellite at S2R Hub and deactivates future callback invocations ([SWS_SM_81013], [SWS_SM_00710]). The call is synchronous and blocks until all currently active callback executions are completely finished ([SWS_SM_00713]). The function takes no parameters and has no return value.
                                  


                                  Lifecycle and Error Handling
                                  

                                  The interface is declared as noexcept and throws no exceptions; specific error codes do not exist ([SWS_SM_81013]). According to the specification, StopOffer() is not thread-safe (not thread-safe). The application must ensure that StopOffer() is called either explicitly before destruction of the S2RSatellite object or—Interpretation: presumably—executed within the destructor of the encapsulating user class (SWS StateManagement §7.5.2 “Deregistration of S2R Satellites at S2R Hub”).
                                  


                                  Interaction in the Suspend-to-RAM Sequence
                                  

                                  If the S2R Hub is executing RequestToEnterSuspendMode or RequestToLeaveSuspendMode, it waits for all addressed satellites. If a satellite deregisters via StopOffer() during this phase, this is treated by the hub like a positive acknowledgment and prevents a failure of the state change ([SWS_SM_00702], [SWS_SM_00707]).
