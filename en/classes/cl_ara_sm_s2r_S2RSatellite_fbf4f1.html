Context

The abstract class ara::sm::s2r::S2RSatellite [SWS_SM_81002] forms the interface for Adaptive Applications to receive notifications about the transition to a \"prepared for Suspend-to-RAM\" state and leaving this state AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”. It serves as the counterpart to component S2RHub, which coordinates communication across instances with all registered satellites AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”.

Typical tasks of an application when entering this state include persisting data, stopping offered services, or terminating security activities before the operating system performs the suspend AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”. Communication between S2RHub and the satellites is secured via Identity and Access Management (IAM), so that only authorized satellite processes are registered [SWS_SM_00715].

Context diagram: Interaction between S2RHub, S2RSatellite within an Adaptive Application, and the operating system. Sources: AUTOSAR_AP_EXP_SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”, AUTOSAR_AP_SWS_StateManagement §7.5.1 “S2R Hub”, [SWS_SM_00715].

Lifecycle

An instance of S2RSatellite can be created either via the static entry point Create(), which establishes a direct connection to S2RHub on the same machine [SWS_SM_81014], or via the parameterized constructor with a ara::core::InstanceSpecifier [SWS_SM_81003]. The default constructor is deleted [SWS_SM_81004]. Since S2RSatellite is an abstract class, an application-specific subclass is instantiated that implements the pure virtual callback methods.

Copy operations are explicitly prohibited [SWS_SM_81007] [SWS_SM_81009]. However, an object can be moved via move semantics [SWS_SM_81006] [SWS_SM_81008]. After instantiation, the object is in the unregistered state. By calling Offer(), the satellite actively registers with S2RHub and enables the reception of handler calls [SWS_SM_81012] [SWS_SM_00710]. The state remains active until StopOffer() cancels the registration and deactivates calls [SWS_SM_81013] [SWS_SM_00713]. Resources are released via the virtual destructor ~S2RSatellite() [SWS_SM_81005].

With regard to concurrency, the creation methods and move operations are specified as thread-safe, whereas Offer(), StopOffer(), the destructor, and the handlers EnterSuspendMode() and LeaveSuspendMode() are designated as not thread-safe [SWS_SM_81003] [SWS_SM_81005] [SWS_SM_81010] [SWS_SM_81011] [SWS_SM_81012] [SWS_SM_81013] [SWS_SM_81014].

State diagram: Lifecycle and registration phases of an S2RSatellite object. Sources: [SWS_SM_81003], [SWS_SM_81005], [SWS_SM_81012], [SWS_SM_81013], [SWS_SM_00710].

Usage Path

The regular sequence is divided into initialization, registration, suspend/resume handling, and deregistration:

  1. Creation: The application creates an instance of its derived class, for example via S2RSatellite::Create() [SWS_SM_81014] or via the constructor with InstanceSpecifier [SWS_SM_81003].
  2. Registration (Offer): The application calls Offer() [SWS_SM_81012]. This registers the satellite with S2RHub [SWS_SM_00710].
  3. Suspend trigger: If the S2RHub initiates the change via RequestToEnterSuspendMode [SWS_SM_00701], the runtime environment calls EnterSuspendMode() on the satellite [SWS_SM_00711]. The application performs preparations and signals completion asynchronously via a ara::core::Future<void> [SWS_SM_81010].
  4. Resume trigger: When exiting the suspend state, the S2RHub triggers the call of LeaveSuspendMode() via RequestToLeaveSuspendMode [SWS_SM_00703] [SWS_SM_00711]. The application restores its regular operation and completes the resulting future [SWS_SM_81011].
  5. Deregistration (StopOffer): Before terminating the application, StopOffer() is called to block handler calls and unregister the instance at the hub [SWS_SM_81013] [SWS_SM_00713].

Sequence diagram: Interaction of Adaptive Application, S2RSatellite, and S2RHub during the Suspend-to-RAM cycle. Sources: [SWS_SM_00701], [SWS_SM_00703], [SWS_SM_00710], [SWS_SM_00711], [SWS_SM_81010], [SWS_SM_81011], [SWS_SM_81012], [SWS_SM_81013].

Error Scenarios

In the event of an error, the methods report error codes from the error domain SmErrc or trigger architectural violations:

  • SmErrc::kAuthenticationRequired: Is returned by Create() if the \"Force IAM switch\" is set and IAM authentication is required [SWS_SM_00716] [SWS_SM_81014]. In this case, the constructor S2RSatellite(const ara::core::InstanceSpecifier&) must be used instead [SWS_SM_81014].
  • SmErrc::kOfferFailed: Occurs when calling Offer() if communication with the State Management daemon fails [SWS_SM_81012].
  • SmErrc::kRejected: Is signaled by the application via the returned future if difficulties arise when entering suspend mode ([SWS_SM_81010]) or leaving suspend mode ([SWS_SM_81011]). Negative feedback for LeaveSuspendMode leads to the overall result kAtLeastOneHadIssuesToLeave on the S2RHub [SWS_SM_00707].
  • Model and context violations: When calling the constructor with InstanceSpecifier, integrity checks are performed. If these fail, specific violations are triggered, including AraNotInitializedViolation, InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, and InstanceSpecifierAlreadyInUseViolation [SWS_SM_81003].

This guide is based exclusively on the AUTOSAR specification for State Management in Release R25-11.
