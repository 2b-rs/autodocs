Enables applications to perform generic processing of UDS RoutineControl services with asynchronous data transfer.

The class provides a generic handler for UDS RoutineControl services and forwards requests for different routine identifiers to adaptive applications [SWS_DM_00552]. Developers implement the required routine actions via asynchronous methods such as Start and activate message forwarding by Offer [SWS_DM_00557]. Because instances are neither copyable nor movable, lifecycle and concurrency must be controlled precisely via the constructor and the interface configuration. Ongoing operations support cooperative cancellations as well as standardized UDS error codes.

Context

The class ara::diag::GenericRoutine provides the generic interface for processing diagnostic routines according to ISO 14229-1 (UDS RoutineControl, Service 0x31) in the AUTOSAR Adaptive Platform. It acts as a link between the central Diagnostic Management (DM) and the adaptive application. An instance of this class is bound to a modeled port prototype of type DiagnosticRoutineGenericInterface, which must be referenced via a DiagnosticServiceGenericMapping in the model [SWS_DM_00552]. In contrast to type-specific routine interfaces, GenericRoutine passes the raw data of the diagnostic request as ara::core::Span<const std::uint8_t> together with the concrete routine identifier (routineId) to the application [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556]. This allows a single handler to serve multiple routines flexibly.

Lifecycle

Instances of GenericRoutine are bound to their specific port and must neither be copied nor moved; copy and move constructors as well as assignment operators are explicitly deleted [SWS_DM_01637], [SWS_DM_01638], [SWS_DM_01635], [SWS_DM_01636]. Initialization is performed via the constructor by specifying the ara::core::InstanceSpecifier as well as the concurrency behavior (ConcurrencyType: kConcurrent or kNotConcurrent) [SWS_DM_00552]. This parameter defines whether the virtual execution methods must be implemented in a thread-safe manner.

After creation, the DM initially does not forward any messages to the handler. Only by calling Offer() is forwarding activated [SWS_DM_00557]. Via StopOffer(), forwarding can be deactivated again [SWS_DM_00558] before the instance is released by the virtual destructor ~GenericRoutine() [SWS_DM_00553]. While the constructor is thread-safe, Offer(), StopOffer(), and the destructor are not thread-safe and require external synchronization [SWS_DM_00552], [SWS_DM_00557], [SWS_DM_00558], [SWS_DM_00553].

State diagram: Lifecycle and state transitions of a GenericRoutine instance. Sources: [SWS_DM_00552], [SWS_DM_00557], [SWS_DM_00558], [SWS_DM_00553]

Usage Path

To provide a generic routine, an application derives from GenericRoutine and overrides the required virtual methods. The method Start (UDS subfunction 0x01) is pure virtual (pure virtual) and must be implemented mandatory [SWS_DM_00554]. The methods Stop (subfunction 0x02) [SWS_DM_00555] and RequestResults (subfunction 0x03) [SWS_DM_00556] are virtual methods; interpretation: Since they are not pure virtual, they would presumably only need to be overridden if the respective routine functionally supports stopping or separate result querying. Question (open)

The regular sequence comprises the following phases:

  • Instantiation: Creating the derived handler with port reference and concurrency mode [SWS_DM_00552].
  • Activation: Calling Offer() to enable for the DM [SWS_DM_00557].
  • Execution: Upon incoming UDS requests, the DM calls Start, Stop, or RequestResults. The application receives routineId, requestData, metaInfo as well as a CancellationHandler and returns a ara::core::Future<OperationOutput> [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556]. The validity of requestData is guaranteed until the associated promise is fulfilled or the operation is cancelled [SWS_DM_00554].
  • Cancellation handling: The application can check the cancellation status via cancellationHandler.IsCanceled() or register a callback via cancellationHandler.SetNotifier() [SWS_DM_00554]. Interpretation: In the event of a cancellation, the application would presumably terminate running background activities prematurely and resolve the promise promptly. Question (open)
  • Deactivation: Stopping forwarding via StopOffer() [SWS_DM_00558] prior to destruction of the object.

Sequence diagram: Typical sequence of registration, routine execution, and deregistration. Sources: [SWS_DM_00557], [SWS_DM_00554], [SWS_DM_00558]

Error Scenarios

Errors can occur both during configuration and during runtime and execution:

  • Model and mapping violations: If resolution of the InstanceSpecifier in the model fails, if it is not identified as PortPrototype, or if no matching DiagnosticServiceGenericMapping exists, the framework reports violations such as InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, or InstanceSpecifierAlreadyInUseViolation [SWS_DM_00552].
  • Provisioning errors: If Offer() is called even though the service is already offered, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_00557].
  • Diagnostic error codes (NRC): If a routine operation cannot be completed successfully or if the request contains invalid parameters, the application fulfills the returned future not with OperationOutput, but with an appropriate UDS Negative Response Code (NRC) from DiagUdsNrcErrc according to ISO 14229-1 [SWS_DM_00554], [SWS_DM_00555], [SWS_DM_00556].

              use
              

              
The function Offer of class ara::diag::GenericRoutine enables Diagnostic Management (DM) to forward incoming diagnostic request messages for a routine to the registered handler [SWS_DM_00557]. The call is synchronous, takes no parameters, and returns a ara::core::Result<void> [SWS_DM_00557]. Since the method is declared with the specification noexcept, it is considered exception safe (exception safe) [SWS_DM_00557].

              


              Error handling
              

              
If offering fails, the method returns a negative result. If the routine was already previously offered for the instance in question, the method returns the specific error code DiagOfferErrc::kAlreadyOffered [SWS_DM_00557]. Rollback semantics are defined for this error case so that the state remains unchanged [SWS_DM_00557]. The error identifier kAlreadyOffered is also anchored in the internal error domains for diagnostic calls [SWS_DM_00514].

              


              Concurrency and Limitations
              

              
The interface is explicitly specified as not thread-safe (not thread-safe) [SWS_DM_00557]. If multiple threads of an application access the same handler, the call must be synchronized. Interpretation: The call would typically occur during initialization, since no requests can be received prior to executing Offer. Question Q-0c42f415bcb0de20 (open)

              


              Interaction
              

              
Offering functionalities via Offer is a central pattern in the AUTOSAR Adaptive diagnostic cluster; it is analogously used for type-specific routine interfaces [SWS_DM_00594], generic UDS services [SWS_DM_00619], and data identifiers [SWS_DM_00638]. Despite sharing the name with ara::com, this represents a specific Diagnostic Management implementation SWS Diagnostics §7.3.4.1.2 “Monitors”.

                  The method RequestResults of class ara::diag::GenericRoutine is called by the diagnostic server instance to generically process UDS RoutineControl requests of service 0x31 with subfunction requestRoutineResults (0x03) for the parameterized diagnostic routine identifier ([SWS_DM_00575], [SWS_DM_00556]).
                  

                  During the call, routine identifier routineId, request-specific metadata metaInfo, and input data requestData are passed ([SWS_DM_00556]). A passed cancellationHandler allows querying the cancellation status via IsCanceled as well as registering a notification function via SetNotifier ([SWS_DM_00556]).
                  

                  The result is returned asynchronously as ara::core::Future<OperationOutput> ([SWS_DM_00556]). Interpretation: The provision of output data is likely typically done asynchronously via an application-side ara::core::Promise. The function is declared as noexcept and is considered exception-safe ([SWS_DM_00556]).
                  

                  Regarding concurrency, thread safety is conditional (conditional): Whether the method must be implemented thread-safe is bindingly controlled via the ConcurrencyType passed to the constructor ([SWS_DM_00556]).
