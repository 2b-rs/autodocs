Encapsulates addressing information of discovered service instances for flexible management and construction of service proxies.

The class HandleType represents a discovered service instance and provides the technical address information required to construct a service proxy (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”). Because the default constructor is deleted ([SWS_CM_00349]), the handle is obtained via discovery functions such as FindService and, thanks to full copyability, movability, and comparability, can be managed flexibly in containers. After checking the instance identity, it serves as a mandatory constructor parameter for creating the actual communication proxy.

Context

The class <SI-Namespace>::proxy::<SI>Proxy::HandleType represents an instance-specific handle for a discovered service instance of the Adaptive Platform (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”). It encapsulates all technical addressing information required by Communication Management and its transport-layer binding implementation to establish a communication relationship with a concrete service instance (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”). As a nested class of the generated service proxy, HandleType decouples the discovery of service instances from the creation of the actual proxy objects (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”). Since proxy instances are stateful as well as neither copyable nor assignable, this indirection allows the application to decide whether to create multiple separate proxies for the same service or to reuse existing proxies (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”).

Lifecycle

The default constructor of HandleType is explicitly deleted ([SWS_CM_00349]). Consequently, instances cannot be freely instantiated by the application, but arise exclusively in a controlled manner through mechanisms of Communication Management such as FindService or asynchronous discovery handlers (AUTOSAR_AP_EXP_ARAComAPI §5.3 “Proxy Class”, AUTOSAR_AP_EXP_ARAComAPI §6.5 “Service Discovery”).

A created handle is designed as a full value type: it implements both the copy constructor ([SWS_CM_00317]) and the move constructor ([SWS_CM_00318]) as well as corresponding assignment operators ([SWS_CM_11532], [SWS_CM_11533]). In addition, HandleType fulfills the requirements for equalitycomparable via operator== ([SWS_CM_11529]) and lessthancomparable via operator< ([SWS_CM_11530]). These properties allow the application to flexibly store, sort, and manage discovered handles in standard containers (such as lists, sorted sets, or associative containers). Destruction takes place deterministically via the destructor specified as exception safe ([SWS_CM_11371]).

Usage Path

The typical flow begins with searching for offered services via the static methods FindService of the proxy class (AUTOSAR_AP_EXP_ARAComAPI §6.5 “Service Discovery”, ARAComAPI §6.5 “Service Discovery”). As a result, Communication Management returns a ara::com::ServiceHandleContainer, which can contain zero, one, or more instances of HandleType (AUTOSAR_AP_EXP_ARAComAPI §6.5 “Service Discovery”).

The application can select a handle from the container and query the associated ara::com::InstanceIdentifier via GetInstanceId() ([SWS_CM_11531]). Subsequently, the application passes the handle to the constructor of the proxy class, which creates the operational communication proxy object from it (AUTOSAR_AP_EXP_ARAComAPI §5.3.3 “Constructor and Handle Concept”). Error Scenarios

When using HandleType, defined constraints of the methods must be observed. The operations for copying, moving, and comparing as well as the instance ID query GetInstanceId() are explicitly classified as not exception safe (not exception safe) ([SWS_CM_00317], [SWS_CM_00318], [SWS_CM_11529], [SWS_CM_11530], [SWS_CM_11531], [SWS_CM_11532], [SWS_CM_11533]). Only the destructor guarantees complete exception safety with noexcept ([SWS_CM_11371]).

If no matching instance is found in the network during a service discovery, FindService returns an empty ServiceHandleContainer (AUTOSAR_AP_EXP_ARAComAPI §6.5 “Service Discovery”). In this case, no valid handle exists, so construction of a service proxy must be omitted. Assigning and comparing invalid handles or handles originating from moved objects is likely to lead to undefined behavior at the binding level.
