class <SI-Namespace>::proxy::<SI>Proxy::HandleType

[SWS_CM_00312] Upstream: RS_CM_00102, RS_AP_00114, RS_AP_00122

class HandleType {...};

Handle for a specific AdaptivePlatformServiceInstance. It contains the information that is needed to create a service proxy. HandleType satisfies the [equalitycomparable] and [lessthancomparable] requirements as per [30]. This, together with [SWS_CM_00317] and [SWS_CM_00318], allows storing and managing HandleTypes by the application.

Context

The class <SI-Namespace>::proxy::<SI>Proxy::HandleType represents an identifier for a specific service instance (AdaptivePlatformServiceInstance) within the AUTOSAR Adaptive Platform. As an embedded type of the generated proxy class, HandleType encapsulates all addressing information required by the communication binding and the underlying transport layer to establish a connection to a potentially remote service instance (EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”). Which addressing data is contained in detail is determined entirely by the concrete binding implementation (EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”).

The handle concept acts as an essential decoupling layer between service discovery and the actual proxy usage (EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”). Since proxy instances manage internal communication state (such as event subscriptions) and can neither be copied nor assigned, the ara::com architecture leaves it to the application whether to share a single proxy instance for the same physical service instance or to create multiple independent proxy instances with separate state (EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”). The primary interaction partners are the application's own business logic, the service discovery of the Communication Management layer, and the generated proxy class.

Context diagram: Interaction partners and role of HandleType in decoupling discovery and proxy creation. Sources: EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”, EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”, EXP ARAComAPI §6.5 “Service Discovery”.

Lifecycle

The lifecycle of HandleType is designed as a lightweight value type (Value Type):

  • Creation: The default constructor is explicitly deleted ([SWS_CM_00349]). The application can therefore not instantiate any uninitialized handles. Valid handles are created exclusively in a controlled manner via the service discovery of ara::com, such as via synchronous search calls (EXP ARAComAPI §6.5 “Service Discovery”) or asynchronous handlers (EXP ARAComAPI §5.3 “FindServiceHandler”).
  • Copying and moving: HandleType supports full value semantics. The class provides both a copy constructor ([SWS_CM_00317]) and a move constructor ([SWS_CM_00318]). Accordingly, both the copy assignment operator ([SWS_CM_11532]) and the move assignment operator ([SWS_CM_11533]) are defined.
  • Comparability and management in containers: HandleType satisfies the C++ requirements for [equalitycomparable] via operator== ([SWS_CM_11529]) as well as for [lessthancomparable] via operator< ([SWS_CM_11530]). These properties allow the application to store handles in standard containers (for example, sorted sets or lookup tables), order them, and check them for equality as needed.
  • Destruction: The release of the resources occupied by the handle takes place via the destructor, which is specified as exception-safe (noexcept) ([SWS_CM_11371]).

Usage Path

The regular usage of HandleType follows a clearly structured call sequence:

  1. Initiating service search: The application starts the service search via the static method FindService of the proxy class, specifying an InstanceIdentifier or InstanceSpecifier (EXP ARAComAPI §6.5 “Service Discovery”), or registers an FindServiceHandler (EXP ARAComAPI §5.3 “FindServiceHandler”).
  2. Receiving the result container: As a return value, FindService provides an ara::com::ServiceHandleContainer<HandleType> within an ara::core::Result (EXP ARAComAPI §6.5 “Service Discovery”). This container comprises zero, one, or more found instances.
  3. Identification and handle check: For each found handle, the application can query the associated ara::com::InstanceIdentifier using GetInstanceId() ([SWS_CM_11531]) or check via operator== ([SWS_CM_11529]) whether the handle is already present in an application-specific data structure.
  4. Proxy instantiation: The selected handle is passed to the constructor of the generated proxy class (EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”). As a result, the proxy instance is bound and ready for further communication.

Sequence diagram: Typical sequence of service discovery, handle processing, and proxy creation. Sources: EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”, EXP ARAComAPI §6.5 “Service Discovery”, [SWS_CM_11531].

Error Scenarios

When using HandleType, the following preconditions and error scenarios must be observed:

  • No matches during service discovery: If no matching service instance is active or no OfferService() has been executed yet, the returned ServiceHandleContainer remains empty (EXP ARAComAPI §6.5 “Service Discovery”). Since the default constructor of HandleType is deleted ([SWS_CM_00349]), the application cannot create a replacement or dummy handle itself; proxy instantiation must not take place until a valid handle is provided via the search.
  • Exception safety of element operations: In contrast to the destructor ([SWS_CM_11371]), the copy constructor ([SWS_CM_00317]), the move constructor ([SWS_CM_00318]), the assignment operators ([SWS_CM_11532], [SWS_CM_11533]), the comparison operators ([SWS_CM_11529], [SWS_CM_11530]), and GetInstanceId() ([SWS_CM_11531]) are explicitly classified as "not exception safe" in the specification. Errors during memory allocations during copy or comparison operations can therefore lead to exceptions.

This guide is based on the AUTOSAR Adaptive Platform R25-11 specifications for the Communication Management module.

<h4>Context</h4>
<p>The class <code>&lt;SI-Namespace&gt;::proxy::&lt;SI&gt;Proxy::HandleType</code> represents an identifier for a specific service instance (<code>AdaptivePlatformServiceInstance</code>) within the AUTOSAR Adaptive Platform. As an embedded type of the generated proxy class, <code>HandleType</code> encapsulates all addressing information required by the communication binding and the underlying transport layer to establish a connection to a potentially remote service instance (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=32">EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”</a>). Which addressing data is contained in detail is determined entirely by the concrete binding implementation (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=32">EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”</a>).</p>
<p>The handle concept acts as an essential decoupling layer between service discovery and the actual proxy usage (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=33">EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”</a>). Since proxy instances manage internal communication state (such as event subscriptions) and can neither be copied nor assigned, the <code>ara::com</code> architecture leaves it to the application whether to share a single proxy instance for the same physical service instance or to create multiple independent proxy instances with separate state (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=33">EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”</a>). The primary interaction partners are the application's own business logic, the service discovery of the Communication Management layer, and the generated proxy class.</p>

<h4>Lifecycle</h4>
<p>The lifecycle of <code>HandleType</code> is designed as a lightweight value type (Value Type):</p>
<ul>
<li><strong>Creation:</strong> The default constructor is explicitly deleted (<a class="spec-record-ref" data-req="SWS_CM_00349" href="../spec/record.html?id=SWS_CM_00349">[SWS_CM_00349]</a>). The application can therefore not instantiate any uninitialized handles. Valid handles are created exclusively in a controlled manner via the service discovery of <code>ara::com</code>, such as via synchronous search calls (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=89">EXP ARAComAPI §6.5 “Service Discovery”</a>) or asynchronous handlers (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=30">EXP ARAComAPI §5.3 “FindServiceHandler”</a>).</li>
<li><strong>Copying and moving:</strong> <code>HandleType</code> supports full value semantics. The class provides both a copy constructor (<a class="spec-record-ref" data-req="SWS_CM_00317" href="../spec/record.html?id=SWS_CM_00317">[SWS_CM_00317]</a>) and a move constructor (<a class="spec-record-ref" data-req="SWS_CM_00318" href="../spec/record.html?id=SWS_CM_00318">[SWS_CM_00318]</a>). Accordingly, both the copy assignment operator (<a class="spec-record-ref" data-req="SWS_CM_11532" href="../spec/record.html?id=SWS_CM_11532">[SWS_CM_11532]</a>) and the move assignment operator (<a class="spec-record-ref" data-req="SWS_CM_11533" href="../spec/record.html?id=SWS_CM_11533">[SWS_CM_11533]</a>) are defined.</li>
<li><strong>Comparability and management in containers:</strong> <code>HandleType</code> satisfies the C++ requirements for <code>[equalitycomparable]</code> via <code>operator==</code> (<a class="spec-record-ref" data-req="SWS_CM_11529" href="../spec/record.html?id=SWS_CM_11529">[SWS_CM_11529]</a>) as well as for <code>[lessthancomparable]</code> via <code>operator&lt;</code> (<a class="spec-record-ref" data-req="SWS_CM_11530" href="../spec/record.html?id=SWS_CM_11530">[SWS_CM_11530]</a>). These properties allow the application to store handles in standard containers (for example, sorted sets or lookup tables), order them, and check them for equality as needed.</li>
<li><strong>Destruction:</strong> The release of the resources occupied by the handle takes place via the destructor, which is specified as exception-safe (<code>noexcept</code>) (<a class="spec-record-ref" data-req="SWS_CM_11371" href="../spec/record.html?id=SWS_CM_11371">[SWS_CM_11371]</a>).</li>
</ul>

<h4>Usage Path</h4>
<p>The regular usage of <code>HandleType</code> follows a clearly structured call sequence:</p>
<ol>
<li><strong>Initiating service search:</strong> The application starts the service search via the static method <code>FindService</code> of the proxy class, specifying an <code>InstanceIdentifier</code> or <code>InstanceSpecifier</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=89">EXP ARAComAPI §6.5 “Service Discovery”</a>), or registers an <code>FindServiceHandler</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=30">EXP ARAComAPI §5.3 “FindServiceHandler”</a>).</li>
<li><strong>Receiving the result container:</strong> As a return value, <code>FindService</code> provides an <code>ara::com::ServiceHandleContainer&lt;HandleType&gt;</code> within an <code>ara::core::Result</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=89">EXP ARAComAPI §6.5 “Service Discovery”</a>). This container comprises zero, one, or more found instances.</li>
<li><strong>Identification and handle check:</strong> For each found handle, the application can query the associated <code>ara::com::InstanceIdentifier</code> using <code>GetInstanceId()</code> (<a class="spec-record-ref" data-req="SWS_CM_11531" href="../spec/record.html?id=SWS_CM_11531">[SWS_CM_11531]</a>) or check via <code>operator==</code> (<a class="spec-record-ref" data-req="SWS_CM_11529" href="../spec/record.html?id=SWS_CM_11529">[SWS_CM_11529]</a>) whether the handle is already present in an application-specific data structure.</li>
<li><strong>Proxy instantiation:</strong> The selected handle is passed to the constructor of the generated proxy class (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=32">EXP ARAComAPI §5.3.3 “Constructor and Handle Concept”</a>). As a result, the proxy instance is bound and ready for further communication.</li>
</ol>

<h4>Error Scenarios</h4>
<p>When using <code>HandleType</code>, the following preconditions and error scenarios must be observed:</p>
<ul>
<li><strong>No matches during service discovery:</strong> If no matching service instance is active or no <code>OfferService()</code> has been executed yet, the returned <code>ServiceHandleContainer</code> remains empty (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=89">EXP ARAComAPI §6.5 “Service Discovery”</a>). Since the default constructor of <code>HandleType</code> is deleted (<a class="spec-record-ref" data-req="SWS_CM_00349" href="../spec/record.html?id=SWS_CM_00349">[SWS_CM_00349]</a>), the application cannot create a replacement or dummy handle itself; proxy instantiation must not take place until a valid handle is provided via the search.</li>
<li><strong>Exception safety of element operations:</strong> In contrast to the destructor (<a class="spec-record-ref" data-req="SWS_CM_11371" href="../spec/record.html?id=SWS_CM_11371">[SWS_CM_11371]</a>), the copy constructor (<a class="spec-record-ref" data-req="SWS_CM_00317" href="../spec/record.html?id=SWS_CM_00317">[SWS_CM_00317]</a>), the move constructor (<a class="spec-record-ref" data-req="SWS_CM_00318" href="../spec/record.html?id=SWS_CM_00318">[SWS_CM_00318]</a>), the assignment operators (<a class="spec-record-ref" data-req="SWS_CM_11532" href="../spec/record.html?id=SWS_CM_11532">[SWS_CM_11532]</a>, <a class="spec-record-ref" data-req="SWS_CM_11533" href="../spec/record.html?id=SWS_CM_11533">[SWS_CM_11533]</a>), the comparison operators (<a class="spec-record-ref" data-req="SWS_CM_11529" href="../spec/record.html?id=SWS_CM_11529">[SWS_CM_11529]</a>, <a class="spec-record-ref" data-req="SWS_CM_11530" href="../spec/record.html?id=SWS_CM_11530">[SWS_CM_11530]</a>), and <code>GetInstanceId()</code> (<a class="spec-record-ref" data-req="SWS_CM_11531" href="../spec/record.html?id=SWS_CM_11531">[SWS_CM_11531]</a>) are explicitly classified as "not exception safe" in the specification. Errors during memory allocations during copy or comparison operations can therefore lead to exceptions.</li>
