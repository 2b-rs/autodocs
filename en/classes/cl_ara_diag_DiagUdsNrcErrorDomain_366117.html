Kontext

Die Klasse [SWS_DM_00529] ara::diag::DiagUdsNrcErrorDomain repräsentiert die standardisierte Fehlerdomäne für Diagnosefehler, die aus unterschiedlichen Diagnoseklassen und Schnittstellen der AUTOSAR Adaptive Platform stammen. Sie leitet sich gemäß [SWS_DM_00529] von der Basisklasse ara::core::ErrorDomain ab und fungiert als primäres Bindeglied zwischen anwendungsseitigen Diagnoseroutinen und dem Diagnose-Management (Diagnostic Management, DM).

Im Gesamtsystem agiert die Fehlerdomäne an den Schnittstellen dreier zentraler Komponenten:

  • Diagnostic Server (DM): Instanz, die Diagnoseanforderungen des Fahrzeugdiagnosetesters verarbeitet, Umgebungsbedingungen prüft und normgerechte UDS-Antworten generiert.
  • Externe Diagnose-Anwendung: Anwendungslogik beziehungsweise externer Diagnoseprozessor, der fahrzeugspezifische Diagnose-Dienste implementiert und über ara::diag-Schnittstellen Ergebnisse oder Fehler zurückmeldet.
  • Diagnose-Client (Tester): Externes Prüfgerät, das Diagnosebefehle an das Steuergerät sendet und bei aufgetretenen Fehlern standardisierte negative Antworten (Negative Response Codes, NRC) erwartet.

Gibt eine Diagnose-Anwendung über eine ara::diag-Schnittstelle ein Ergebnis mit einem Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain zurück, verarbeitet der Diagnostic Server diesen Fehler zielgerichtet: Er leitet aus dem gemeldeten Fehlercode den UDS Negative Response Code ab [SWS_DM_02059] und übermittelt eine negative Antwort mit diesem Code an den Diagnose-Client [SWS_DM_02060]. Zudem interagiert die Domäne mit der Prüfung konfigurierbarer Umgebungsbedingungen: Schlägt der Abruf eines Datenelements durch einen Fehler dieser Domäne fehl, stuft der Server die Bedingung als nicht erfüllt ein und setzt eine Log- und Trace-Meldung ab [SWS_DM_00970].

Lebenszyklus

Der Lebenszyklus von ara::diag::DiagUdsNrcErrorDomain folgt den Vorgaben für zustandslose Fehlerdomänen der Plattform:

  • Erzeugung und Initialisierung: Die Klasse stellt einen parameterlosen Standardkonstruktor bereit, der als constexpr und noexcept definiert ist [SWS_DM_00532]. Interpretation: Instanzen von DiagUdsNrcErrorDomain werden als langlebige Konstanten oder Singleton-Objekte zur Compile- bzw. Ladezeit angelegt, um über die gesamte Prozesslaufzeit zur Verfügung zu stehen.
  • Besitzverhältnisse: Anwendungen erzeugen in der Regel keine dynamischen Instanzen auf dem Heap, sondern referenzieren die Domäne über konstante Referenzen bei der Typisierung von ara::core::ErrorCode-Werten.
  • Zustände und Übergänge: Die Domäne besitzt keine variablen internen Zustände und erfordert keine Zustandsübergänge. Beobachtende Abfragen wie Name() [SWS_DM_00533] oder Message() [SWS_DM_00534] verhalten sich zustandslos und deterministisch.
  • Nebenläufigkeit: Sämtliche Elementfunktionen – der Konstruktor [SWS_DM_00532], Name() [SWS_DM_00533], Message() [SWS_DM_00534] sowie ThrowAsException() [SWS_DM_00535] – sind explizit als threadsicher spezifiziert. Sie können parallel aus verschiedenen Ausführungskontexten ohne zusätzliche Sperren aufgerufen werden.

Nutzungspfad

Der reguläre Ablauf bei der Signalisierung von Diagnosefehlern gliedert sich in folgende Schritte:

  1. Dienstanforderung: Der Diagnose-Client sendet eine UDS-Serviceanforderung an den Diagnostic Server.
  2. Aufruf der Diagnose-Anwendung: Der Diagnostic Server delegiert die Verarbeitung über eine typisierte ara::diag-Schnittstelle an den zuständigen externen Diagnoseprozessor.
  3. Fehlerrückgabe: Stellt die Diagnose-Anwendung eine ungültige Bedingung fest, erzeugt sie einen Fehlercode des Typs ara::diag::DiagUdsNrcErrorDomain::Errc [SWS_DM_00530] und gibt diesen innerhalb eines ara::core::Result zurück.
  4. NRC-Ableitung: Erkennt der Diagnostic Server einen Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain, leitet er aus dem DiagUdsNrcErrc-Wert den UDS Negative Response Code ab [SWS_DM_02059]. Dies geschieht typischerweise über eine Typkonvertierung (static_cast) in einen 1-Byte-Wert im zulässigen Bereich 0x01 bis 0xFE [SWS_DM_02059].
  5. Protokollantwort: Der Diagnostic Server erzeugt eine negative UDS-Antwort mit dem ermittelten Fehlercode und sendet diese an den Client [SWS_DM_02060].
  6. Fehlertextauflösung: Für Diagnoseprotokolle oder Systemmeldungen kann die Fehlerbeschreibung über Message() abgefragt werden, welche stets einen gültigen Textzeiger liefert [SWS_DM_00534].

Fehlerszenarien

Für die kontrollierte Behandlung von Fehlerzuständen stellt die Klasse spezialisierte Typen und Konvertierungsmechanismen bereit:

  • Fehlercode-Enumeration: Der Typ-Alias Errc verweist auf das Enum DiagUdsNrcErrc [SWS_DM_00530]. Interpretation: Die Enumerationswerte spiegeln die normierten UDS Negative Response Codes wider. Gültige Werte für die Ableitung liegen im Bereich von 0x01 bis 0xFE [SWS_DM_02059].
  • Ausnahmeabbildung: Der Alias Exception verweist auf DiagUdsNrcException [SWS_DM_00531]. Mittels ThrowAsException() [SWS_DM_00535] kann ein Fehlercode in die entsprechende Ausnahme gewandelt und geworfen werden. Sind C++-Ausnahmen in der Toolchain deaktiviert, nimmt diese Funktion nicht an der Überladungsauflösung teil [SWS_DM_00535].
  • Fehler beim Datenelement-Abruf: Führt der Abruf eines Datenelements durch einen externen Prozessor zu einem Fehler der Domäne ara::diag::DiagUdsNrcErrorDomain, behandelt das Diagnose-Management den betreffenden Formelteil der Umweltbedingung als nicht erfüllt und stößt eine Log- und Trace-Meldung an [SWS_DM_00970].
  • Verhalten bei Multi-DID-Anfragen: Das Vorhandensein von ara::diag::DiagUdsNrcErrorDomain im Ergebnis signalisiert ein negatives Teilergebnis des externen Prozessors. Bei Anfragen über mehrere DIDs führt ein Einzelfehler jedoch nicht zwangsläufig zu einer globalen negativen Antwort, sofern mindestens ein DID in der aktiven Sitzung unterstützt wird (AUTOSAR_AP_SWS_Diagnostics §7.3.x S. 160).

<h4>Kontext</h4>
<p>Die Klasse <a class="spec-record-ref" data-req="SWS_DM_00529" href="../spec/record.html?id=SWS_DM_00529">[SWS_DM_00529]</a> <code>ara::diag::DiagUdsNrcErrorDomain</code> repräsentiert die standardisierte Fehlerdomäne für Diagnosefehler, die aus unterschiedlichen Diagnoseklassen und Schnittstellen der AUTOSAR Adaptive Platform stammen. Sie leitet sich gemäß <a class="spec-record-ref" data-req="SWS_DM_00529" href="../spec/record.html?id=SWS_DM_00529">[SWS_DM_00529]</a> von der Basisklasse <code>ara::core::ErrorDomain</code> ab und fungiert als primäres Bindeglied zwischen anwendungsseitigen Diagnoseroutinen und dem Diagnose-Management (Diagnostic Management, DM).</p>
<p>Im Gesamtsystem agiert die Fehlerdomäne an den Schnittstellen dreier zentraler Komponenten:</p>
<ul>
<li><strong>Diagnostic Server (DM):</strong> Instanz, die Diagnoseanforderungen des Fahrzeugdiagnosetesters verarbeitet, Umgebungsbedingungen prüft und normgerechte UDS-Antworten generiert.</li>
<li><strong>Externe Diagnose-Anwendung:</strong> Anwendungslogik beziehungsweise externer Diagnoseprozessor, der fahrzeugspezifische Diagnose-Dienste implementiert und über <code>ara::diag</code>-Schnittstellen Ergebnisse oder Fehler zurückmeldet.</li>
<li><strong>Diagnose-Client (Tester):</strong> Externes Prüfgerät, das Diagnosebefehle an das Steuergerät sendet und bei aufgetretenen Fehlern standardisierte negative Antworten (Negative Response Codes, NRC) erwartet.</li>
</ul>
<p>Gibt eine Diagnose-Anwendung über eine <code>ara::diag</code>-Schnittstelle ein Ergebnis mit einem Fehler der Domäne <code>ara::diag::DiagUdsNrcErrorDomain</code> zurück, verarbeitet der Diagnostic Server diesen Fehler zielgerichtet: Er leitet aus dem gemeldeten Fehlercode den UDS Negative Response Code ab <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a> und übermittelt eine negative Antwort mit diesem Code an den Diagnose-Client <a class="spec-record-ref" data-req="SWS_DM_02060" href="../spec/record.html?id=SWS_DM_02060">[SWS_DM_02060]</a>. <h4>Kontext</h4>
<p>Die Klasse <a class="spec-record-ref" data-req="SWS_DM_00529" href="../spec/record.html?id=SWS_DM_00529">[SWS_DM_00529]</a> <code>ara::diag::DiagUdsNrcErrorDomain</code> repräsentiert die standardisierte Fehlerdomäne für Diagnosefehler, die aus unterschiedlichen Diagnoseklassen und Schnittstellen der AUTOSAR Adaptive Platform stammen. <p>Im Gesamtsystem agiert die Fehlerdomäne an den Schnittstellen dreier zentraler Komponenten:</p>
<ul>
<li><strong>Diagnostic Server (DM):</strong> Instanz, die Diagnoseanforderungen des Fahrzeugdiagnosetesters verarbeitet, Umgebungsbedingungen prüft und normgerechte UDS-Antworten generiert.</li>

</ul>
<p>Gibt eine Diagnose-Anwendung über eine <code>ara::diag</code>-Schnittstelle ein Ergebnis mit einem Fehler der Domäne <code>ara::diag::DiagUdsNrcErrorDomain</code> zurück, verarbeitet der Diagnostic Server diesen Fehler zielgerichtet: Er leitet aus dem gemeldeten Fehlercode den UDS Negative Response Code ab <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a> und übermittelt eine negative Antwort mit diesem Code an den Diagnose-Client <a class="spec-record-ref" data-req="SWS_DM_02060" href="../spec/record.html?id=SWS_DM_02060">[SWS_DM_02060]</a>. <h4>Lebenszyklus</h4>
<p>Der Lebenszyklus von <code>ara::diag::DiagUdsNrcErrorDomain</code> folgt den Vorgaben für zustandslose Fehlerdomänen der Plattform:</p>
<ul>
<li><strong>Erzeugung und Initialisierung:</strong> Die Klasse stellt einen parameterlosen Standardkonstruktor bereit, der als <code>constexpr</code> und <code>noexcept</code> definiert ist <a class="spec-record-ref" data-req="SWS_DM_00532" href="../spec/record.html?id=SWS_DM_00532">[SWS_DM_00532]</a>. Interpretation: Instanzen von <code>DiagUdsNrcErrorDomain</code> werden als langlebige Konstanten oder Singleton-Objekte zur Compile- bzw. Ladezeit angelegt, um über die gesamte Prozesslaufzeit zur Verfügung zu stehen.</li>
<li><strong>Besitzverhältnisse:</strong> Anwendungen erzeugen in der Regel keine dynamischen Instanzen auf dem Heap, sondern referenzieren die Domäne über konstante Referenzen bei der Typisierung von <code>ara::core::ErrorCode</code>-Werten.</li>
<li><strong>Zustände und Übergänge:</strong> Die Domäne besitzt keine variablen internen Zustände und erfordert keine Zustandsübergänge. Beobachtende Abfragen wie <code>Name()</code> <a class="spec-record-ref" data-req="SWS_DM_00533" href="../spec/record.html?id=SWS_DM_00533">[SWS_DM_00533]</a> oder <code>Message()</code> <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a> verhalten sich zustandslos und deterministisch.</li>
<li><strong>Nebenläufigkeit:</strong> Sämtliche Elementfunktionen – der Konstruktor <a class="spec-record-ref" data-req="SWS_DM_00532" href="../spec/record.html?id=SWS_DM_00532">[SWS_DM_00532]</a>, <code>Name()</code> <a class="spec-record-ref" data-req="SWS_DM_00533" href="../spec/record.html?id=SWS_DM_00533">[SWS_DM_00533]</a>, <code>Message()</code> <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a> sowie <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a> – sind explizit als threadsicher spezifiziert. </ul>

<h4>Nutzungspfad</h4>
<p>Der reguläre Ablauf bei der Signalisierung von Diagnosefehlern gliedert sich in folgende Schritte:</p>
<ol>
<li><strong>Dienstanforderung:</strong> Der Diagnose-Client sendet eine UDS-Serviceanforderung an den Diagnostic Server.</li>
<li><strong>Aufruf der Diagnose-Anwendung:</strong> Der Diagnostic Server delegiert die Verarbeitung über eine typisierte <code>ara::diag</code>-Schnittstelle an den zuständigen externen Diagnoseprozessor.</li>
<li><strong>Fehlerrückgabe:</strong> Stellt die Diagnose-Anwendung eine ungültige Bedingung fest, erzeugt sie einen Fehlercode des Typs <code>ara::diag::DiagUdsNrcErrorDomain::Errc</code> <a class="spec-record-ref" data-req="SWS_DM_00530" href="../spec/record.html?id=SWS_DM_00530">[SWS_DM_00530]</a> und gibt diesen innerhalb eines <code>ara::core::Result</code> zurück.</li>
<li><strong>NRC-Ableitung:</strong> Erkennt der Diagnostic Server einen Fehler der Domäne <code>ara::diag::DiagUdsNrcErrorDomain</code>, leitet er aus dem <code>DiagUdsNrcErrc</code>-Wert den UDS Negative Response Code ab <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>. Dies geschieht typischerweise über eine Typkonvertierung (<code>static_cast</code>) in einen 1-Byte-Wert im zulässigen Bereich <code>0x01</code> bis <code>0xFE</code> <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>.</li>
<li><strong>Protokollantwort:</strong> Der Diagnostic Server erzeugt eine negative UDS-Antwort mit dem ermittelten Fehlercode und sendet diese an den Client <a class="spec-record-ref" data-req="SWS_DM_02060" href="../spec/record.html?id=SWS_DM_02060">[SWS_DM_02060]</a>.</li>
<li><strong>Fehlertextauflösung:</strong> Für Diagnoseprotokolle oder Systemmeldungen kann die Fehlerbeschreibung über <code>Message()</code> abgefragt werden, welche stets einen gültigen Textzeiger liefert <a class="spec-record-ref" data-req="SWS_DM_00534" href="../spec/record.html?id=SWS_DM_00534">[SWS_DM_00534]</a>.</li>
</ol>

<h4>Fehlerszenarien</h4>
<p>Für die kontrollierte Behandlung von Fehlerzuständen stellt die Klasse spezialisierte Typen und Konvertierungsmechanismen bereit:</p>
<ul>
<li><strong>Fehlercode-Enumeration:</strong> Der Typ-Alias <code>Errc</code> verweist auf das Enum <code>DiagUdsNrcErrc</code> <a class="spec-record-ref" data-req="SWS_DM_00530" href="../spec/record.html?id=SWS_DM_00530">[SWS_DM_00530]</a>. Interpretation: Die Enumerationswerte spiegeln die normierten UDS Negative Response Codes wider. Gültige Werte für die Ableitung liegen im Bereich von <code>0x01</code> bis <code>0xFE</code> <a class="spec-record-ref" data-req="SWS_DM_02059" href="../spec/record.html?id=SWS_DM_02059">[SWS_DM_02059]</a>.</li>
<li><strong>Ausnahmeabbildung:</strong> Der Alias <code>Exception</code> verweist auf <code>DiagUdsNrcException</code> <a class="spec-record-ref" data-req="SWS_DM_00531" href="../spec/record.html?id=SWS_DM_00531">[SWS_DM_00531]</a>. Mittels <code>ThrowAsException()</code> <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a> kann ein Fehlercode in die entsprechende Ausnahme gewandelt und geworfen werden. Sind C++-Ausnahmen in der Toolchain deaktiviert, nimmt diese Funktion nicht an der Überladungsauflösung teil <a class="spec-record-ref" data-req="SWS_DM_00535" href="../spec/record.html?id=SWS_DM_00535">[SWS_DM_00535]</a>.</li>
<li><strong>Fehler beim Datenelement-Abruf:</strong> Führt der Abruf eines Datenelements durch einen externen Prozessor zu einem Fehler der Domäne <code>ara::diag::DiagUdsNrcErrorDomain</code>, behandelt das Diagnose-Management den betreffenden Formelteil der Umweltbedingung als nicht erfüllt und stößt eine Log- und Trace-Meldung an <a class="spec-record-ref" data-req="SWS_DM_00970" href="../spec/record.html?id=SWS_DM_00970">[SWS_DM_00970]</a>.</li>
<li><strong>Verhalten bei Multi-DID-Anfragen:</strong> Das Vorhandensein von <code>ara::diag::DiagUdsNrcErrorDomain</code> im Ergebnis signalisiert ein negatives Teilergebnis des externen Prozessors. Bei Anfragen über mehrere DIDs führt ein Einzelfehler jedoch nicht zwangsläufig zu einer globalen negativen Antwort, sofern mindestens ein DID in der aktiven Sitzung unterstützt wird (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=160">AUTOSAR_AP_SWS_Diagnostics §7.3.x S. 160</a>).</li>
</ul>
