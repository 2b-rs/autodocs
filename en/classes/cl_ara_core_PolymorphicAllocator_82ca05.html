Manages polymorphic memory allocation for objects and containers via replaceable memory resources.

The template class encapsulates memory-resource-based dynamic allocation for adaptive applications and containers as a completely exception-free implementation of polymorphic allocators [SWS_CORE_06541]. For flexible control of the object lifecycle, the instance delegates all memory requests to an exchangeable memory resource, where failed allocations deterministically return null pointers instead of C++ exceptions [SWS_CORE_06547]. As an essential functional constraint, regular copy assignment is explicitly prevented, while failed deallocation operations during ongoing operation are always silently ignored.

Context

The template class ara::core::PolymorphicAllocator implements the interface for stateful, polymorphic memory allocation in AUTOSAR Adaptive according to the C++ standard pattern and defines the underlying element type value_type [SWS_CORE_06572]. As an adapter, it mediates between calling components—such as containers or application structures—and a concrete memory resource. Via the method resource(), the pointer to the utilized MemoryResource can be queried at any time [SWS_CORE_06557]. Through this encapsulation, the request for memory is semantically decoupled from the concrete implementation of memory management.

Context diagram: Integration of the allocator between caller and memory resource. Sources: [SWS_CORE_06557], [SWS_CORE_06572].

Lifecycle

Instances of the allocator are constructed either by default [SWS_CORE_06541] or with a pointer to a specific MemoryResource [SWS_CORE_06542]. Since the allocator merely references the memory resource, responsibility for its lifetime presumably lies with the caller. In addition to the regular copy constructor [SWS_CORE_06543], a converting constructor permits initialization from allocators for other element types U [SWS_CORE_06544].

With respect to ownership transfers, the regular copy assignment operator is deleted (=delete) [SWS_CORE_06545]. In contrast, AUTOSAR explicitly defines a move constructor [SWS_CORE_06546] and a default move assignment operator [SWS_CORE_00066]. During container copy operations, the method select_on_container_copy_construction() creates a corresponding allocator instance [SWS_CORE_06573].

Regarding concurrency, the default and converting constructors as well as the query of the memory resource are specified as thread-safe ([SWS_CORE_06541], [SWS_CORE_06542], [SWS_CORE_06544], [SWS_CORE_06557]). In contrast, move operations ([SWS_CORE_06546]), copy selections ([SWS_CORE_06573]), and all allocation, construction, and deallocation operations are declared as non-thread-safe.

Usage Path

The regular flow comprises memory provision, object construction, and their subsequent destruction and deallocation:

  • Memory allocation: Raw memory for n objects of type Tp is requested using allocate() [SWS_CORE_06547]. Alternatively, allocate_bytes() is available for byte-precise allocation with alignment [SWS_CORE_06549], as is the template allocate_object() for typed allocations [SWS_CORE_06551].
  • Object initialization: The method construct() creates objects in the previously allocated memory area [SWS_CORE_06555]. As a combined operation, new_object() provides allocation and in-place construction in a single call [SWS_CORE_06553].
  • Destruction and deallocation: Destruction is performed via destroy() [SWS_CORE_06556], followed by deallocation via deallocate() [SWS_CORE_06548], deallocate_bytes() [SWS_CORE_06550], or deallocate_object() [SWS_CORE_06552]. Alternatively, both can be combined with delete_object() [SWS_CORE_06554].

Sequence diagram: Typical flow of allocation, construction, destruction, and deallocation. Sources: [SWS_CORE_06547], [SWS_CORE_06548], [SWS_CORE_06555], [SWS_CORE_06556].

Error Scenarios

The class differs from the ISO C++ standard in key error handling mechanisms in order to satisfy strict requirements for exception-free systems:

  • Absence of exceptions during allocation: All allocation methods (allocate() [SWS_CORE_06547], allocate_bytes() [SWS_CORE_06549], and allocate_object() [SWS_CORE_06551]) are noexcept. If a memory reservation fails, a nullptr is returned instead of an exception. The caller is likely required to validate the pointer prior to further use.
  • Conditional exception safety: Construction and destruction routines (construct() [SWS_CORE_06555], destroy() [SWS_CORE_06556], new_object() [SWS_CORE_06553], and delete_object() [SWS_CORE_06554]) are conditionally noexcept, depending on std::is_nothrow_constructible or std::is_nothrow_destructible of the affected types. If new_object() fails, nullptr is returned as well [SWS_CORE_06553].
  • Error suppression during deallocation: If deallocation operations fail, any errors that occurred in deallocate() [SWS_CORE_06548], deallocate_bytes() [SWS_CORE_06550], deallocate_object() [SWS_CORE_06552], and delete_object() [SWS_CORE_06554] are silently ignored without exception.

                      The member function allocate of class ara::core::PolymorphicAllocator serves for synchronously requesting uninitialized memory for n objects of type Tp [SWS_CORE_06547]. It is modeled on the functionality of [mem.poly.allocator.class], but deliberately deviates from the C++ standard through the declaration as noexcept and attribute [[nodiscard]] [SWS_CORE_06547].
                      
  
                      In case of error, allocate does not throw an exception such as std::bad_alloc, but returns a nullptr instead [SWS_CORE_06547]. Because of [[nodiscard]], the caller must explicitly receive the return value and check it for nullptr before using the memory area [SWS_CORE_06547]. Regarding concurrency, the function is classified as exception-safe, but is considered not thread-safe (not thread-safe) [SWS_CORE_06547]. Interpretation: A synchronous call via the same allocator from different threads should therefore require external protection by the caller.
                      
  
                      The fault-tolerant behavior without exceptions corresponds directly to interface ara::core::MemoryResource::allocate [SWS_CORE_06503], which is likewise defined as noexcept and returns nullptr in case of error. Predefined instances such as NullMemoryResource [SWS_CORE_06563] also use this principle and consistently return nullptr upon allocation calls. At a higher level, this mechanism interacts with containers such as ara::core::Vector [SWS_CORE_01315], whose assignment operators are aligned with such allocation characteristics.
