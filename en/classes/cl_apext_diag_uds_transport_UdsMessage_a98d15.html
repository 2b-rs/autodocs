Context

The class apext::diag::uds_transport::UdsMessage encapsulates a UDS message (request or response) and acts as central storage for diagnostic data exchanged between the generic core of Diagnostic Management (UdsTransportProtocolMgr) and a concrete transport protocol implementation (UdsTransportProtocolHandler). The instance provides the underlying message buffer both on the reception path for diagnostic requests (RX) and on the transmission path for diagnostic responses (TX).

In addition to the pure payload data, UdsMessage manages metadata and addressing information. The source address ([SWS_DM_00297]) is queried via GetSa() and the target address ([SWS_DM_00298]) of type Address via GetTa() ([SWS_DM_00293]). The target address type is determined using GetTaType() ([SWS_DM_00299]), where the enum TargetAddressType distinguishes between physical (kPhysical) and functional (kFunctional) addressing ([SWS_DM_00296]). In addition, channel-specific additional information (for example predefined metadata for DoIP plug-ins) can be appended to the message via the method AddMetaInfo() in the form of a MetaInfoMap ([SWS_DM_00302], [SWS_DM_00294]).

Context diagram: Interaction of DM core, transport protocol handler, and UdsMessage. Sources: [SWS_DM_00385], [SWS_DM_09012].

Lifecycle

Instances of UdsMessage are created exclusively by the generic core of Diagnostic Management with optimized resource allocation. The default constructor UdsMessage() is declared protected (protected) ([SWS_DM_09012]) to explicitly prevent transport protocol handlers from instantiating instances independently.

The ownership and transfer of UdsMessage objects are governed via smart pointers. For this purpose, the platform defines the type aliases UdsMessagePtr for write access ([SWS_DM_00303]) and UdsMessageConstPtr for constant read access ([SWS_DM_00304]). Upon accepting a message, the DM core transfers ownership of the instance to the handler via a UdsMessagePtr ([SWS_DM_00385]). After populating is complete, the message is passed back to the DM core for processing ([SWS_DM_00345]). Deallocation and destruction occur deterministically via the virtual default destructor ~UdsMessage() ([SWS_DM_09010]).

Regarding concurrency, the methods for querying addresses (GetSa(), GetTa(), GetTaType()) are specified as reentrant ([SWS_DM_00297], [SWS_DM_00298], [SWS_DM_00299]). The methods for accessing payload data and metadata (GetPayload() and AddMetaInfo()), however, are not thread-safe (unsafe) ([SWS_DM_00300], [SWS_DM_00301], [SWS_DM_00302]), since implementations are permitted to perform buffer and resource allocations during calls to GetPayload().

Usage Path

The typical sequence on the diagnostic reception path (RX) is divided into the following steps:

  1. Announcement: The UdsTransportProtocolHandler receives a UDS request from the network and signals its receipt by calling UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00385]).
  2. Instantiation and buffer provisioning: If the DM can process the request, IndicateMessage() returns a std::pair ([SWS_DM_00309]) with status kIndicationOk and a UdsMessagePtr that owns the created UdsMessage. The allocated buffer has a minimum size of one byte ([SWS_DM_00385]).
  3. Payload population: The handler calls the non-const overload GetPayload() ([SWS_DM_00301]) and obtains a reference to uds_transport::ByteSpan&. The handler populates the UdsMessage object with the received UDS data starting with the service ID (SID) either up to the full capacity of the message or up to the complete length of the received UDS request ([SWS_DM_00388]).
  4. Appending metadata: If required, the handler adds channel-specific metadata via AddMetaInfo() ([SWS_DM_00302]).
  5. Forwarding to the DM core: Once the payload has been completely written to the UdsMessage, the handler passes the message via UdsTransportProtocolMgr::HandleMessage() to the generic DM core for further diagnostic processing ([SWS_DM_00345]).
  6. Read access in the DM core: The diagnostic core reads the message data (A_Data according to ISO) read-only via the const overload GetPayload() const ([SWS_DM_00300]).

Interpretation: On the diagnostic response path (TX), the generic DM core presumably populates the UdsMessage object with response data itself in an analogous manner and passes it to the UdsTransportProtocolHandler for transmission.

Sequence diagram: Process of message acceptance and buffer population in the receive path. Sources: [SWS_DM_00301], [SWS_DM_00302], [SWS_DM_00345], [SWS_DM_00385], [SWS_DM_00388].

Error Scenarios

The following error situations can occur during interaction and buffer allocation:

  • DM busy: If the DM is already busy with the active processing of a service of the same conversation, IndicateMessage() returns the status kIndicationOccupied and a null pointer for UdsMessagePtr ([SWS_DM_00386]). In this case, no UdsMessage is provided. An exception to this are functional TesterPresent requests with suppressPosRspMsgIndicationBit set (payload 0x3E 0x80), which are valid at any time and may be processed ([SWS_DM_00386], [SWS_DM_00126]).
  • Unknown target address: If the target address of the message cannot be resolved, the DM signals this via the result kIndicationUnknownTargetAddress and sets UdsMessagePtr to nullptr (AUTOSAR_AP_SWS_Diagnostics p. 100). No message object is allocated.
  • Buffer limitation: The capacity of the passed UdsMessage object is limited by the allocation determined by the DM. The handler may write to the buffer at most up to the capacity limit ([SWS_DM_00388]).

<h4>Context</h4>
<p>The class <code>apext::diag::uds_transport::UdsMessage</code> encapsulates a UDS message (request or response) and acts as central storage for diagnostic data exchanged between the generic core of Diagnostic Management (<code>UdsTransportProtocolMgr</code>) and a concrete transport protocol implementation (<code>UdsTransportProtocolHandler</code>). The instance provides the underlying message buffer both on the reception path for diagnostic requests (RX) and on the transmission path for diagnostic responses (TX).</p>
<p>In addition to the pure payload data, <code>UdsMessage</code> manages metadata and addressing information. The source address (<a class="spec-record-ref" data-req="SWS_DM_00297" href="../spec/record.html?id=SWS_DM_00297">[SWS_DM_00297]</a>) is queried via <code>GetSa()</code> and the target address (<a class="spec-record-ref" data-req="SWS_DM_00298" href="../spec/record.html?id=SWS_DM_00298">[SWS_DM_00298]</a>) of type <code>Address</code> via <code>GetTa()</code> (<a class="spec-record-ref" data-req="SWS_DM_00293" href="../spec/record.html?id=SWS_DM_00293">[SWS_DM_00293]</a>). The target address type is determined using <code>GetTaType()</code> (<a class="spec-record-ref" data-req="SWS_DM_00299" href="../spec/record.html?id=SWS_DM_00299">[SWS_DM_00299]</a>), where the enum <code>TargetAddressType</code> distinguishes between physical (<code>kPhysical</code>) and functional (<code>kFunctional</code>) addressing (<a class="spec-record-ref" data-req="SWS_DM_00296" href="../spec/record.html?id=SWS_DM_00296">[SWS_DM_00296]</a>). In addition, channel-specific additional information (for example predefined metadata for DoIP plug-ins) can be appended to the message via the method <code>AddMetaInfo()</code> in the form of a <code>MetaInfoMap</code> (<a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>, <a class="spec-record-ref" data-req="SWS_DM_00294" href="../spec/record.html?id=SWS_DM_00294">[SWS_DM_00294]</a>).</p>

<h4>Lifecycle</h4>
<p>Instances of <code>UdsMessage</code> are created exclusively by the generic core of Diagnostic Management with optimized resource allocation. The default constructor <code>UdsMessage()</code> is declared protected (<code>protected</code>) (<a class="spec-record-ref" data-req="SWS_DM_09012" href="../spec/record.html?id=SWS_DM_09012">[SWS_DM_09012]</a>) to explicitly prevent transport protocol handlers from instantiating instances independently.</p>
<p>The ownership and transfer of <code>UdsMessage</code> objects are governed via smart pointers. For this purpose, the platform defines the type aliases <code>UdsMessagePtr</code> for write access (<a class="spec-record-ref" data-req="SWS_DM_00303" href="../spec/record.html?id=SWS_DM_00303">[SWS_DM_00303]</a>) and <code>UdsMessageConstPtr</code> for constant read access (<a class="spec-record-ref" data-req="SWS_DM_00304" href="../spec/record.html?id=SWS_DM_00304">[SWS_DM_00304]</a>). Upon accepting a message, the DM core transfers ownership of the instance to the handler via a <code>UdsMessagePtr</code> (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>). After populating is complete, the message is passed back to the DM core for processing (<a class="spec-record-ref" data-req="SWS_DM_00345" href="../spec/record.html?id=SWS_DM_00345">[SWS_DM_00345]</a>). Deallocation and destruction occur deterministically via the virtual default destructor <code>~UdsMessage()</code> (<a class="spec-record-ref" data-req="SWS_DM_09010" href="../spec/record.html?id=SWS_DM_09010">[SWS_DM_09010]</a>).</p>
<p>Regarding concurrency, the methods for querying addresses (<code>GetSa()</code>, <code>GetTa()</code>, <code>GetTaType()</code>) are specified as reentrant (<a class="spec-record-ref" data-req="SWS_DM_00297" href="../spec/record.html?id=SWS_DM_00297">[SWS_DM_00297]</a>, <a class="spec-record-ref" data-req="SWS_DM_00298" href="../spec/record.html?id=SWS_DM_00298">[SWS_DM_00298]</a>, <a class="spec-record-ref" data-req="SWS_DM_00299" href="../spec/record.html?id=SWS_DM_00299">[SWS_DM_00299]</a>). The methods for accessing payload data and metadata (<code>GetPayload()</code> and <code>AddMetaInfo()</code>), however, are not thread-safe (unsafe) (<a class="spec-record-ref" data-req="SWS_DM_00300" href="../spec/record.html?id=SWS_DM_00300">[SWS_DM_00300]</a>, <a class="spec-record-ref" data-req="SWS_DM_00301" href="../spec/record.html?id=SWS_DM_00301">[SWS_DM_00301]</a>, <a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>), since implementations are permitted to perform buffer and resource allocations during calls to <code>GetPayload()</code>.</p>

<h4>Usage Path</h4>
<p>The typical sequence on the diagnostic reception path (RX) is divided into the following steps:</p>
<ol>
<li><strong>Announcement:</strong> The <code>UdsTransportProtocolHandler</code> receives a UDS request from the network and signals its receipt by calling <code>UdsTransportProtocolMgr::IndicateMessage()</code> (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>).</li>
<li><strong>Instantiation and buffer provisioning:</strong> If the DM can process the request, <code>IndicateMessage()</code> returns a <code>std::pair</code> (<a class="spec-record-ref" data-req="SWS_DM_00309" href="../spec/record.html?id=SWS_DM_00309">[SWS_DM_00309]</a>) with status <code>kIndicationOk</code> and a <code>UdsMessagePtr</code> that owns the created <code>UdsMessage</code>. The allocated buffer has a minimum size of one byte (<a class="spec-record-ref" data-req="SWS_DM_00385" href="../spec/record.html?id=SWS_DM_00385">[SWS_DM_00385]</a>).</li>
<li><strong>Payload population:</strong> The handler calls the non-const overload <code>GetPayload()</code> (<a class="spec-record-ref" data-req="SWS_DM_00301" href="../spec/record.html?id=SWS_DM_00301">[SWS_DM_00301]</a>) and obtains a reference to <code>uds_transport::ByteSpan&amp;</code>. The handler populates the <code>UdsMessage</code> object with the received UDS data starting with the service ID (SID) either up to the full capacity of the message or up to the complete length of the received UDS request (<a class="spec-record-ref" data-req="SWS_DM_00388" href="../spec/record.html?id=SWS_DM_00388">[SWS_DM_00388]</a>).</li>
<li><strong>Appending metadata:</strong> If required, the handler adds channel-specific metadata via <code>AddMetaInfo()</code> (<a class="spec-record-ref" data-req="SWS_DM_00302" href="../spec/record.html?id=SWS_DM_00302">[SWS_DM_00302]</a>).</li>
<li><strong>Forwarding to the DM core:</strong> Once the payload has been completely written to the <code>UdsMessage</code>, the handler passes the message via <code>UdsTransportProtocolMgr::HandleMessage()</code> to the generic DM core for further diagnostic processing (<a class="spec-record-ref" data-req="SWS_DM_00345" href="../spec/record.html?id=SWS_DM_00345">[SWS_DM_00345]</a>).</li>
<li><strong>Read access in the DM core:</strong> The diagnostic core reads the message data (A_Data according to ISO) read-only via the const overload <code>GetPayload() const</code> (<a class="spec-record-ref" data-req="SWS_DM_00300" href="../spec/record.html?id=SWS_DM_00300">[SWS_DM_00300]</a>).</li>
</ol>
<p>Interpretation: On the diagnostic response path (TX), the generic DM core presumably populates the <code>UdsMessage</code> object with response data itself in an analogous manner and passes it to the <code>UdsTransportProtocolHandler</code> for transmission.</p>

<h4>Error Scenarios</h4>
<p>The following error situations can occur during interaction and buffer allocation:</p>
<ul>
<li><strong>DM busy:</strong> If the DM is already busy with the active processing of a service of the same conversation, <code>IndicateMessage()</code> returns the status <code>kIndicationOccupied</code> and a null pointer for <code>UdsMessagePtr</code> (<a class="spec-record-ref" data-req="SWS_DM_00386" href="../spec/record.html?id=SWS_DM_00386">[SWS_DM_00386]</a>). In this case, no <code>UdsMessage</code> is provided. An exception to this are functional <code>TesterPresent</code> requests with <code>suppressPosRspMsgIndicationBit</code> set (payload <code>0x3E 0x80</code>), which are valid at any time and may be processed (<a class="spec-record-ref" data-req="SWS_DM_00386" href="../spec/record.html?id=SWS_DM_00386">[SWS_DM_00386]</a>, <a class="spec-record-ref" data-req="SWS_DM_00126" href="../spec/record.html?id=SWS_DM_00126">[SWS_DM_00126]</a>).</li>
<li><strong>Unknown target address:</strong> If the target address of the message cannot be resolved, the DM signals this via the result <code>kIndicationUnknownTargetAddress</code> and sets <code>UdsMessagePtr</code> to <code>nullptr</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=100">AUTOSAR_AP_SWS_Diagnostics p. 100</a>). No message object is allocated.</li>
<li><strong>Buffer limitation:</strong> The capacity of the passed <code>UdsMessage</code> object is limited by the allocation determined by the DM. The handler may write to the buffer at most up to the capacity limit (<a class="spec-record-ref" data-req="SWS_DM_00388" href="../spec/record.html?id=SWS_DM_00388">[SWS_DM_00388]</a>).</li>
</ul>
