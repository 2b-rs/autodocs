Used to retrieve authentication instances for managing the status of external diagnostic clients.

The class ara::diag::ExternalAuthentication provides a port interface through which an adaptive application queries instances of ara::diag::ClientAuthentication to manage the authentication state of external diagnostic clients [SWS_DM_01191]. After binding to a modeled service port, the authentication objects are requested specifically from the Diagnostic Manager based on the source address or meta-information [SWS_DM_01200]. The instance possesses move semantics, prohibits copy operations, and requires synchronized destruction due to a non-thread-safe destructor.

Context

In the AUTOSAR Adaptive Platform, the class ara::diag::ExternalAuthentication acts as a port interface for the authentication of external diagnostic clients [SWS_DM_01191], AUTOSAR_AP_SWS_Diagnostics §8.17 “Header: ara/diag/external_authentication.h”. Via this port, an adaptive application obtains access to specific instances of ara::diag::ClientAuthentication, which represent and manage the authentication state of the respective diagnostic client [SWS_DM_01202].

The mapping and number of available client instances is defined in the software model via the element DiagnosticExternalAuthenticationIdentification. This allows the application to define fixed source addresses or configured address ranges of type Address (alias for std::uint16_t [SWS_DM_01192]) for diagnostic testers if the final source address is only known at runtime AUTOSAR_AP_SWS_Diagnostics §7.3.2.2 “Get ClientAuthentication Instance”.

The participating interaction partners include:

  • The adaptive application, which creates the port instance and queries authentication states.
  • The Diagnostic Manager (DM), which controls the diagnostic connections and manages the authentication states of the clients [SWS_DM_01202].
  • The ara::diag::ClientAuthentication objects associated with the requesting client.
  • The external diagnostic client, whose connection is identified via source address or meta-information.

Context diagram: Integration of the port class between application, Diagnostic Manager, and client authentication. Sources: [SWS_DM_01191], [SWS_DM_01202], AUTOSAR_AP_SWS_Diagnostics §7.3.2.2 “Get ClientAuthentication Instance”.

Lifecycle

The creation of an ara::diag::ExternalAuthentication instance is performed explicitly by passing an ara::core::InstanceSpecifier to the constructor [SWS_DM_01193]. This identifier binds the object to the modeled PortPrototype of a DiagnosticExternalAuthenticationInterface.

Regarding ownership, the class has pure move semantics: move constructor [SWS_DM_01194] and move assignment operator [SWS_DM_01195] are present (default), while copy constructor [SWS_DM_01196] and copy assignment operator [SWS_DM_01197] are deleted (delete). A port thus represents an indivisible, non-copyable interface object.

Destruction is provided by the destructor ~ExternalAuthentication() [SWS_DM_01198]. With respect to concurrency, the constructor and the query methods are specified as thread-safe (thread-safe) and exception-safe (exception safe) [SWS_DM_01193], [SWS_DM_01199], [SWS_DM_01200], [SWS_DM_01201]. In contrast, the destructor is explicitly not thread-safe (not thread-safe) [SWS_DM_01198]. The application must therefore ensure that no concurrent calls take place prior to destructing the object.

Usage Path

The typical sequence comprises initialization of the port followed by retrieval of authentication objects:

  1. The application instantiates ExternalAuthentication, specifying the instance identifier [SWS_DM_01193].
  2. The application requests the authentication instance for a specific client. For this purpose, the overloaded methods Get(Address) using the tester address [SWS_DM_01200] or Get(const MetaInfo&) based on received request metadata [SWS_DM_01199] are available. Alternatively, it retrieves a list of all instances currently maintained by the Diagnostic Manager using GetAll() [SWS_DM_01201].
  3. The Diagnostic Manager identifies the corresponding object and returns an ara::core::Result<ClientAuthentication> or a vector [SWS_DM_01202].
  4. The application checks the result and subsequently interacts with the obtained ClientAuthentication instance, which presumably acts as an application-side handle for the state of the authentication session.

Sequence diagram: Typical call sequence for instantiating and querying a ClientAuthentication instance. Sources: [SWS_DM_01193], [SWS_DM_01200], [SWS_DM_01202].

Error Scenarios

During instantiation via the constructor, configuration and modeling errors can lead to defined violations [SWS_DM_01193]:

  • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the executable or does not reference a PortPrototype.
  • PortInterfaceMappingViolation: The referenced PortPrototype is not typed as DiagnosticExternalAuthenticationInterface.
  • ProcessMappingViolation: No matching modeled process definition exists for the runtime process.
  • InstanceSpecifierAlreadyInUseViolation: The identifier is already used by another port instance in the same process.

For calls to Get(const MetaInfo&) or Get(Address), the return value via ara::core::Result may contain the error code DiagErrc::kServiceNotAvailable [SWS_DM_01199], [SWS_DM_01200]. This indicates that essential functionality of the Diagnostic Manager is temporarily unavailable. If instances are missing, the call GetAll() does not return an error code, but an empty vector [SWS_DM_01201].
