Manages memory blocks in a monotonically growing buffer with exception-free allocation and bundled deallocation.

The class ara::core::MonotonicBufferResource provides a specialized memory resource for fast, monotonic allocations from a fixed memory buffer or via an upstream resource. Requested memory is allocated incrementally and is not freed immediately upon individual deallocations, but is instead reset collectively via release() ([SWS_CORE_06530]). All operations are declared completely exception-free, with an out-of-memory condition signaled by returning nullptr instead of an exception ([SWS_CORE_06569]). The instances are not copyable and require external synchronization for concurrent access from multiple threads.

Context

The class ara::core::MonotonicBufferResource is a concrete memory resource within the module core of the AUTOSAR Adaptive Platform and inherits from the base class ara::core::MemoryResource. It adapts the concept of std::pmr::monotonic_buffer_resource from [mem.res.monotonic.buffer], known from the C++ standard, for safety-relevant and deterministic automotive applications. The primary role of the class is to serve allocation requests with minimal management overhead from a contiguous memory area by allocating memory monotonically.

Calling components, polymorphic allocators, and containers that request memory blocks at runtime act as interaction partners on the one hand. On the other hand, the class interacts with an optional upstream memory resource (MemoryResource). This upstream resource can be passed via constructors such as [SWS_CORE_06521] and queried via the accessor method upstream_resource() ([SWS_CORE_06531]).

Lifecycle

The initialization of ara::core::MonotonicBufferResource can be controlled via multiple constructors. In addition to a parameterless default constructor ([SWS_CORE_06524]), overloads are available that accept an explicit upstream resource ([SWS_CORE_06521]), define an initial buffer size ([SWS_CORE_06525], [SWS_CORE_06522]), or utilize an externally provided raw memory area (void* buffer, std::size_t buffer_size) as the initial buffer ([SWS_CORE_06526], [SWS_CORE_06523]).

Regarding ownership semantics, the class is defined as strictly non-copyable: the copy constructor ([SWS_CORE_06527]) and the copy assignment operator ([SWS_CORE_06529]) are deleted (=delete). In contrast to the ISO 14882 standard, however, the AUTOSAR class implements explicit move semantics via the move constructor ([SWS_CORE_06576]) and the move assignment operator ([SWS_CORE_06577]), each defined as noexcept=default.

Destruction takes place via the destructor ~MonotonicBufferResource() ([SWS_CORE_06528]). A significant AUTOSAR deviation from the standard is that the destructor is not declared virtual. Via the method release() ([SWS_CORE_06530]), all allocated memory can be reset before the end of the object lifetime.

For concurrency, a strict distinction must be observed: the parameterless constructor ([SWS_CORE_06524]), the equality check do_is_equal() ([SWS_CORE_06571]), and the query upstream_resource() ([SWS_CORE_06531]) are declared thread-safe. All parameterized constructors ([SWS_CORE_06521], [SWS_CORE_06522], [SWS_CORE_06523], [SWS_CORE_06525], [SWS_CORE_06526]), allocation operations ([SWS_CORE_06569], [SWS_CORE_06570]), release() ([SWS_CORE_06530]), as well as the destructor ([SWS_CORE_06528]) are not thread-safe and require external synchronization during concurrent access.

Usage Path

A typical application flow comprises provisioning, continuous allocation, and bundled deallocation:

  1. Instantiation: The application creates an instance, for example by specifying a buffer size and an upstream resource ([SWS_CORE_06522]) or a fixed buffer ([SWS_CORE_06526]).
  2. Allocation: Memory requests are served via the protected method do_allocate(bytes, alignment) ([SWS_CORE_06569]). If the available buffer is insufficient, the instance obtains a new buffer from the upstream resource.
  3. Deallocation: Calls to do_deallocate(p, bytes, alignment) ([SWS_CORE_06570]) do not shrink the buffer individually; the internal allocation pointer advances monotonically.
  4. Buffer reset: With release() ([SWS_CORE_06530]), all memory blocks obtained via upstream are released at once, and the buffer is ready for new cycles.
  5. Resource comparison: Via do_is_equal() ([SWS_CORE_06571]), it can be checked whether two memory resources are identical.

Sequence diagram: Typical memory cycle from allocation through ignored deallocation to collective reset via release(). Sources: [SWS_CORE_06522], [SWS_CORE_06569], [SWS_CORE_06570], [SWS_CORE_06530]

Error Scenarios

The class follows strict requirements for exception-free embedded systems: all member functions, constructors, and operators are declared as noexcept and provide complete exception safety.

In the event of an error, the behavior deliberately deviates from the standard library:

  • Failed allocation: If a request in do_allocate() ([SWS_CORE_06569]) cannot be served, no exception std::bad_alloc is thrown; instead, nullptr is returned. Callers must check the return value for nullptr.
  • Error during deallocation: If an error occurs during deallocation in do_deallocate() ([SWS_CORE_06570]), it is silently ignored according to the specification.
  • Destruction via base pointer: Since the destructor ([SWS_CORE_06528]) is not virtual, destruction via a pointer to the base class MemoryResource is likely to lead to undefined behavior (Interpretation: destruction must occur via the concrete type). Question Q-add18020b48f3131 (open)
