Allows applications to provide system-specific timestamps for security events of the IdsM.

The class ara::idsm::TimestampProvider provides an interface through which applications can feed timestamps for the IdsM module via a modeled PPort [SWS_AIDSM_10400]. Activation and deactivation of the query callbacks take place via the methods Offer() and StopOffer() [SWS_AIDSM_10408] [SWS_AIDSM_10409]. Instances cannot be copied, support move semantics, and require external synchronization for methods without guaranteed thread safety.

Context

The class ara::idsm::TimestampProvider serves as an interface for providing timestamps for the Intrusion Detection System Manager (IdsM) module within the AUTOSAR Adaptive Platform [SWS_AIDSM_10400]. Security-relevant events and logs in the IdsM require reliable time information, which is obtained by this provider class from the platform or an application-specific time source. An instance of TimestampProvider is bound to a PPort modeled via a ara::core::InstanceSpecifier [SWS_AIDSM_10401]. Since the method GetTimestamp() is defined as a pure virtual callback function [SWS_AIDSM_10407], TimestampProvider acts as an abstract base class from which concrete implementations must be derived.

Lifecycle

Creation of a timestamp provider takes place explicitly via the constructor specifying the associated ara::core::InstanceSpecifier [SWS_AIDSM_10401]. This constructor is declared as thread-safe. Copy operations are completely prevented: both the copy constructor [SWS_AIDSM_10404] and the copy assignment operator [SWS_AIDSM_10406] are deleted (= delete). Instances thus possess a unique identity and cannot be duplicated.

In contrast, the class supports move semantics: the move constructor transfers existing resources to a new object in a thread-safe manner [SWS_AIDSM_10403]. Move assignment via operator= is also available, but in contrast to the constructor is not thread-safe [SWS_AIDSM_10405]. The lifecycle of active service provision is controlled explicitly after instantiation: registration for the IdsM is activated via the method Offer() [SWS_AIDSM_10408]. With StopOffer(), provision is prevented again [SWS_AIDSM_10409]. The instance is released via the virtual destructor [SWS_AIDSM_10402], which is specified as not thread-safe. Interpretation: prior to destroying an instance, StopOffer() is typically likely to be called to ensure that no more pending calls occur through the IdsM. Question Q-fcf21d9d93d053a6 (open)

Usage Path

Typical usage requires deriving an application-specific class that overrides the method GetTimestamp() and returns the current timestamp as TimestampType [SWS_AIDSM_10407]. Once the instance has been created for the corresponding port [SWS_AIDSM_10401], the application signals operational readiness by calling Offer() [SWS_AIDSM_10408]. From this point onward, the IdsM can autonomously invoke the callback method GetTimestamp() to locate events in time. If the service is to be terminated or the component shut down, StopOffer() revokes the availability of the interface [SWS_AIDSM_10409].

Sequence diagram: Interaction sequence during initialization, timestamp query by IdsM, and termination of the provider. Sources: [SWS_AIDSM_10401], [SWS_AIDSM_10407], [SWS_AIDSM_10408], [SWS_AIDSM_10409]

Error Scenarios

All methods of the interface are declared as noexcept and do not throw C++ exceptions. Errors during activation of service provision are instead conveyed via the return type ara::core::Result<void> of Offer() [SWS_AIDSM_10408]. Interpretation: if registration with the communication or platform framework fails (for example, due to an unsuitable port configuration), the returned Result contains a corresponding error code that must be checked before further use. Question Q-5a971906b458dd6f (open)

Special attention is required for the concurrency behavior: neither the destructor [SWS_AIDSM_10402] nor the methods Offer() [SWS_AIDSM_10408], StopOffer() [SWS_AIDSM_10409], operator=(&&) [SWS_AIDSM_10405], or GetTimestamp() [SWS_AIDSM_10407] are classified as thread-safe. Callers must therefore ensure that lifecycle operations and callback processing occur thread-synchronized and that no data races arise.
