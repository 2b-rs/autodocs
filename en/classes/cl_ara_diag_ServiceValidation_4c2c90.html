Context

The class ara::diag::ServiceValidation represents the functional interface element for manufacturer- and supplier-specific validation of incoming diagnostic requests in the AUTOSAR Adaptive module diag [SWS_DM_00772]. Depending on the modeling of the attribute DiagnosticServiceValidationMapping.category, validation via the method Validate is performed either as a manufacturer check or as a supplier check within the negative response code (NRC) order according to Chapter 8.7 of ISO 14229-1 [SWS_DM_00772].

Essentially three parties are involved in the interaction:

  • Adaptive application: Implements the concrete validation logic by specializing the virtual methods Validate [SWS_DM_00774] and Confirmation [SWS_DM_00775].
  • Diagnostic Management (DM): Receives UDS requests, forwards them to the instance for preliminary checking after successful activation by Offer [SWS_DM_00776], and reports the overall completion back via Confirmation [SWS_DM_00775].
  • Diagnostic tester: Initiates diagnostic messages whose raw data and meta-information are the subject of the check [SWS_DM_00774].

Lifecycle

The instantiation of ServiceValidation is performed explicitly by passing a ara::core::InstanceSpecifier, which must reference a modeled PortPrototype of a DiagnosticServiceValidationInterface [SWS_DM_00772]. The constructor is specified as thread-safe [SWS_DM_00772]. An instance of ServiceValidation must be neither copied nor moved: copy constructor [SWS_DM_01689], copy assignment operator [SWS_DM_01687], move constructor [SWS_DM_01690], and move assignment operator [SWS_DM_01688] are explicitly deleted (= delete).

After construction, the instance is in the Not offered state. Calling Offer() enables the forwarding of incoming requests by Diagnostic Management [SWS_DM_00776]. If processing is to be paused or terminated, calling StopOffer() prevents the forwarding of further diagnostic messages [SWS_DM_00777]. The enablement can be reactivated by a renewed Offer(). Final destruction occurs via the virtual destructor ~ServiceValidation() [SWS_DM_00773].

With regard to concurrency, the methods Offer, StopOffer, Validate, Confirmation and the destructor are classified as not thread-safe [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Calls to these operations must be synchronized by the application in the event of concurrent access.

Usage Path

The typical sequence for securing diagnostic services is divided into the following steps:

  1. Instantiation: The application creates the instance while binding to the modeled port [SWS_DM_00772].
  2. Enablement: Call of Offer(). Diagnostic Management is instructed to forward incoming diagnostic messages to this instance [SWS_DM_00776].
  3. Validation: For each incoming diagnostic request, the DM calls the method Validate [SWS_DM_00774]. The request data (including service identifier) is passed as ara::core::Span<const std::uint8_t>, and the context via MetaInfo. The lifetime of the request data remains valid until the associated promise is fulfilled or processing is canceled via the CancellationHandler [SWS_DM_00774].
  4. Asynchronous result: The method returns a ara::core::Future<void> [SWS_DM_00774]. Upon successful validation, the future is resolved without error. If the request is invalid, the future is completed with a suitable Negative Response Code (NRC) from DiagUdsNrcErrc according to ISO 14229-1 [SWS_DM_00774].
  5. Confirmation of completion: As soon as the processing of the diagnostic request is completely finished, the DM calls Confirmation to transmit the overall result (status) and the metaInfo [SWS_DM_00775].
  6. Deregistration: Before shutting down, the application calls StopOffer() [SWS_DM_00777]. Interpretation: After calling StopOffer(), ongoing validation requests whose future has not yet been fulfilled are likely either discarded or canceled by the DM.

Sequence diagram: Interaction sequence between application, ServiceValidation handler, and Diagnostic Management (DM). Sources: [SWS_DM_00774], [SWS_DM_00775], [SWS_DM_00776], [SWS_DM_00777].

Error Scenarios

Error situations can occur in various phases and are signaled via specific mechanisms:

  • Construction and model violations: If binding of the InstanceSpecifier fails, the framework reports defined violations [SWS_DM_00772]:
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved or does not point to a PortPrototype.
    • PortInterfaceMappingViolation: The PortPrototype is not typed by a DiagnosticServiceValidationInterface.
    • ProcessMappingViolation: No matching modeled process exists for the reference for the current runtime process.
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by another instance in the running process.
  • Faulty enablement: If Offer() is called while the service is already being offered, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered with rollback semantics in the return value ara::core::Result<void> [SWS_DM_00776].
  • Validation error: If the check detects a violated condition (e.g., insufficient preconditions or security requirements), the error is transmitted via DiagUdsNrcErrc in the ara::core::Future<void> [SWS_DM_00774]. Since Validate is declared as noexcept, no C++ exceptions may be thrown.
  • Exception safety: All methods of the class are specified as exception-safe (exception safe) and annotated with noexcept [SWS_DM_00772] [SWS_DM_00773] [SWS_DM_00774] [SWS_DM_00775] [SWS_DM_00776] [SWS_DM_00777]. Error states are without exception mapped via return types and platform notifications.
