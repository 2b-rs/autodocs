Validates incoming diagnostic requests in Diagnostic Management using manufacturer or supplier checks.

The class ara::diag::ServiceValidation serves for the application-specific validation of incoming UDS diagnostic requests in Diagnostic Management based on manufacturer or supplier criteria [SWS_DM_00772]. After creation, the service must be activated using Offer() so that request data is forwarded asynchronously to Validate() for verification and subsequently confirmed via Confirmation() [SWS_DM_00776]. As an essential constraint, the instance is bound to a port, is neither copyable nor movable, and is not thread-safe apart from the constructor.

Context

The class ara::diag::ServiceValidation provides the programming interface for the modeling element DiagnosticServiceValidationInterface within the AUTOSAR Adaptive diagnostic stack. Via this interface, an application can implement application-specific checks for incoming diagnostic requests. The instance interacts directly with Diagnostic Management (DM), which is authorized to forward incoming diagnostic requests to the validation logic [SWS_DM_00776].

The functional assignment of the validation is controlled via the modeling attribute DiagnosticServiceValidationMapping.category. Depending on this category, the validation method Validate() is called within the scope of the UDS response rules according to ISO 14229-1 (Chapter 8.7) either in the context of a manufacturer check (\"Manufacturer Check\") or a supplier check (\"Supplier Check\") [SWS_DM_00772]. The DM is likely to subject incoming request messages to this validation check prior to actual service execution in order to filter out invalid requests early on.

Lifecycle

Creation is performed explicitly via the constructor by specifying an ara::core::InstanceSpecifier, which must reference an PortPrototype defined in the system model [SWS_DM_00772]. ara::diag::ServiceValidation is designed as a non-copyable and non-movable single instance: both the copy constructor [SWS_DM_01689] and the move constructor [SWS_DM_01690] as well as the assignment operators for copy [SWS_DM_01687] and move [SWS_DM_01688] are declared as deleted (=delete).

After initialization, the object is in an inactive state. Only by calling Offer() is the forwarding of diagnostic requests from DM to the handler enabled [SWS_DM_00776]. Service offering can be terminated during runtime via StopOffer(), whereupon DM deactivates forwarding again [SWS_DM_00777]. The resources are released via the virtual destructor ~ServiceValidation() [SWS_DM_00773].

With regard to concurrency, only the constructor is specified as thread-safe [SWS_DM_00772]. The methods Offer() [SWS_DM_00776], StopOffer() [SWS_DM_00777], Validate() [SWS_DM_00774], Confirmation() [SWS_DM_00775] as well as the destructor [SWS_DM_00773] are classified as not thread-safe, but are exception-safe (noexcept).

Usage Path

The concrete validation logic is presumably provided by deriving from ara::diag::ServiceValidation and overriding the virtual interface methods by the application. The typical operational flow is divided into the following phases:

  1. Instantiation: Creating the instance by passing the InstanceSpecifier that references the configured port [SWS_DM_00772].
  2. Service offering: Calling Offer() to activate request forwarding by the DM [SWS_DM_00776].
  3. Validation: For each incoming diagnostic request, the DM calls the method Validate() [SWS_DM_00774]. The raw data (including Service Identifier, SID) is passed as ara::core::Span<const std::uint8_t> along with the MetaInfo of the request [SWS_DM_00774]. The data remains valid until the returned ara::core::Future<void> is satisfied or processing is cancelled by a cancellation handler [SWS_DM_00774].
  4. Confirmation: As soon as the processing of the diagnostic request is completed, the DM informs the handler via the method Confirmation(), passing the result status (ConfirmationStatusType) and the MetaInfo [SWS_DM_00775].
  5. Deactivation: Terminating request processing by means of StopOffer() [SWS_DM_00777].

Sequence diagram: Call sequence for validating and confirming a diagnostic request. Sources: [SWS_DM_00772], [SWS_DM_00774], [SWS_DM_00775], [SWS_DM_00776], [SWS_DM_00777].

Error Scenarios

Error conditions occur both during the static configuration check during construction and at runtime:

  • Construction violations: The constructor reports specific modeling errors as violations [SWS_DM_00772]:
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the Executable or does not reference an PortPrototype [SWS_DM_00772].
    • PortInterfaceMappingViolation: The referenced PortPrototype is not typed by an DiagnosticServiceValidationInterface [SWS_DM_00772].
    • ProcessMappingViolation: No matching modeled Process exists for the process [SWS_DM_00772].
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already being used by another instance in the running process [SWS_DM_00772].
  • Service offering: If Offer() is called when the service is already actively offered, the return value ara::core::Result<void> returns the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_00776].
  • Validation errors: If the content check of the request fails, the application signals rejection via the returned ara::core::Future<void> by setting a corresponding Negative Response Code (NRC) from ISO 14229-1 via DiagUdsNrcErrc [SWS_DM_00774].

The method Confirmation of interface ara::diag::ServiceValidation ([SWS_DM_00775], declared in ara/diag/service_validation.h) serves as notification about the completion and result of a previously processed diagnostic request.

Usage and Semantics

The virtual callback function is called synchronously by Diagnostic Management as soon as request processing is finished. It has no return value (void) and takes two input parameters ([SWS_DM_00775]):

  • status (ConfirmationStatusType): Signals the final status or the result of the service processing ([SWS_DM_00775]).
  • metaInfo (const Meta Info &): Contains associated meta-information of the diagnostic request ([SWS_DM_00775]).

Error Handling and Concurrency

The function is specified as exception-safe (exception safe) and declared with the identifier noexcept ([SWS_DM_00775]). Application-side overrides must therefore not propagate exceptions to the outside. Specific error codes such as DET or DEM reports are not defined for this method. Regarding concurrency, Confirmation is classified as not thread-safe (not thread-safe) ([SWS_DM_00775]); access to application-internal states within the callback requires appropriate synchronization during concurrent sequences.

Interaction

Triggering the notification is coupled to the lifecycle end of a diagnostic request ([SWS_DM_00775]). This cycle is completed as soon as a positive or negative response has been transmitted or suppressed (AUTOSAR_AP_SWS_Diagnostics §7.3.2.1.2 “Life-cycle of a Diagnostic Conversation”). Interpretation: At module level, Diagnostic Management is likely to trigger the callback Confirmation only after transmission via the transport layer has been acknowledged by means of TransmitConfirmation and the result kTransmitOk or kTransmitFailed ([SWS_DM_00307], [SWS_DM_00351]).

      The member function Offer of class ara::diag::ServiceValidation (header ara/diag/service_validation.h) activates the forwarding of incoming diagnostic requests by the Diagnostic Manager (DM) to this specific validation handler [SWS_DM_00776]. The call is made synchronously and without input parameters via the signature ara::core::Result<void> Offer() noexcept; [SWS_DM_00776]. A ara::core::Result<void> serves as the return value, which is empty in case of success or encapsulates the occurred error code in case of an error [SWS_DM_00776].
      


      Error handling
      

      If the registration fails, the method returns an errored Result. If the service was already offered previously for the instance in question, the error code DiagOfferErrc::kAlreadyOffered is returned [SWS_DM_00776]. Here, rollback semantics apply, so that the previous state of the instance remains unchanged [SWS_DM_00776].
      


      Concurrency and Limitations
      

      The function is specified as exception-safe (exception safe), but explicitly as not thread-safe (not thread-safe) [SWS_DM_00776]. Parallel accesses to the same instance must be coordinated by the calling application. Regarding the sequence, Offer must be called before the Diagnostic Manager can forward service requests for validation [SWS_DM_00776].
      


      Interaction
      

      Offering interfaces via Offer is a consistent design pattern of AUTOSAR Adaptive diagnostics and is applied analogously to routines ([SWS_DM_00557], [SWS_DM_00594]), generic UDS services ([SWS_DM_00619]), DoIP functions ([SWS_DM_00725], [SWS_DM_00735]), and security access ([SWS_DM_00766]), among others. As long as an interface has not been provided via Offer, the DM discards requests or falls back on defined replacement values ([SWS_DM_01525], [SWS_DM_01527]). Conceptual parallels to ara::com are functionally motivated, but represent an independent implementation of diagnostics (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”).

The call is synchronous, takes no input parameters, and returns no return value [SWS_DM_00777].
                      


                      Error Handling and Concurrency
                      

                      The function is declared as noexcept and is considered exception safe, so that no C++ exceptions occur during execution [SWS_DM_00777]. Specific error codes or feedback to error management are not defined for this call [SWS_DM_00777].
                      

                      With regard to concurrency, the method is specified as not thread-safe [SWS_DM_00777]. Interpretation: The calling application must ensure that concurrent calls to the same instance of StopOffer() are synchronized to avoid data inconsistencies.
                      


                      Interaction
                      

                      Offering and stopping interfaces via Offer() and StopOffer() is modeled on the familiar semantics of ara::com, but represents independent functionality in the diagnostics domain AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”.
