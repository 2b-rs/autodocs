Manages storage for cryptographic keys and enables metadata queries as well as modification callbacks.

The interface encapsulates persistent or volatile storage for cryptographic keys and enables querying key metadata as well as the responsible CryptoProvider [SWS_CRYPT_30403]. Applications can monitor content changes via a registrable observer callback [SWS_CRYPT_30404]. If the slot is empty, access to the key type or its algorithm fails with the error code ara::crypto::CryptoErrc::kEmptyKeySlot [SWS_CRYPT_50055]. Because copying and moving are prohibited, access is thread-safe via shared pointers.

Context

The interface ara::crypto::cryp::KeySlot represents a dedicated storage location for cryptographic keys within the AUTOSAR Adaptive Platform. As an encapsulation of a logical key slot, it manages metadata, type information, and the assignment of supported algorithms for the key stored within it. An instance typically interacts with three parties: the application software, the associated cryp::CryptoProvider (to which a shared reference can be obtained via [SWS_CRYPT_30403]), and an application-specific callback for content monitoring according to [SWS_CRYPT_30404].

Context diagram: Interaction partners of the KeySlot interface. Sources: [SWS_CRYPT_30403], [SWS_CRYPT_30404]

Lifecycle

A KeySlot is permanently bound to the key storage it represents. Accordingly, the interface prohibits duplicating and moving the instance: both the copy constructor [SWS_CRYPT_50149] and the move constructor [SWS_CRYPT_50150] are explicitly deleted. The same applies to the copy assignment operator [SWS_CRYPT_50147] and the move assignment operator [SWS_CRYPT_50148].

To manage ownership and reference relationships, the class defines the smart pointer type alias Sptr as std::shared_ptr<KeySlot> [SWS_CRYPT_50151]. Deallocation is performed via a virtual default destructor [SWS_CRYPT_50146]. Interpretation: Since the interface defines no public constructors, concrete instances are likely created by the responsible CryptoProvider and provided as Sptr. All provided methods are declared thread-safe, meaning concurrent read and monitoring accesses from multiple execution contexts are permitted.

Usage Path

Typical interaction with a KeySlot is divided into configuring content monitoring and querying stored key metadata:

  1. Registering an observer: Using RegisterUpdateObserver, the application registers a callback function as well as an application-specific identifier keySlotIdentifier [SWS_CRYPT_30404]. Upon repeated calls, only the most recently passed callback is ever invoked upon updates or deletions of the slot content.
  2. Querying supported algorithms: Via GetPossibleAlgIds, the application determines a list of all algorithm identifiers supported by the slot [SWS_CRYPT_50056].
  3. Checking current key: If a key is present in the slot, GetCryptoObjectType returns the object type of the key [SWS_CRYPT_50054] and GetAlgId returns its concrete algorithm identifier [SWS_CRYPT_50055].
  4. Determining responsible provider: If needed, the managing CryptoProvider can be queried as a shared pointer via GetCryptoProvider [SWS_CRYPT_30403].
  5. Unregistering observer: After monitoring is complete, the registration is revoked via UnregisterUpdateObserver [SWS_CRYPT_30406].

Sequence diagram: Typical flow for registration, metadata query, and unregistration at a KeySlot. Sources: [SWS_CRYPT_30404], [SWS_CRYPT_50056], [SWS_CRYPT_50054], [SWS_CRYPT_50055], [SWS_CRYPT_30406]

Error Scenarios

The querying methods safeguard error states via the result type ara::core::Result. If a KeySlot contains no key, the calls GetCryptoObjectType [SWS_CRYPT_50054] and GetAlgId [SWS_CRYPT_50055] each return the standardized error code ara::crypto::CryptoErrc::kEmptyKeySlot with rollback semantics. The methods GetPossibleAlgIds [SWS_CRYPT_50056] and GetCryptoProvider [SWS_CRYPT_30403] specify no standardized error codes. For observer management using RegisterUpdateObserver [SWS_CRYPT_30404] as well as UnregisterUpdateObserver [SWS_CRYPT_30406], implementation-specific errors in the result object are intended in case of error.

                          The method RegisterUpdateObserver of class ara::crypto::cryp::KeySlot serves to register an application-specific callback function that is notified upon every update of the content of a key slot [SWS_CRYPT_30404]. Here, both modifications of content and the complete clearing of the slot are considered updates [SWS_CRYPT_30404].
                          
  
                          Usage and Parameters
                          
  
                          The function is included via header ara/crypto/cryp/keyslot.h and accepts callback callback as well as an identifier keySlotIdentifier [SWS_CRYPT_30404]. When called, function object callback receives string keySlotIdentifier as argument to allow unambiguous assignment of the affected slot in the application logic [SWS_CRYPT_30404]. Upon repeated calls to RegisterUpdateObserver by the same application, only the most recently registered callback function is retained and executed [SWS_CRYPT_30404].
                          
  
                          Concurrency and Error Handling
                          
  
                          The interface is thread-safe (thread-safe) and specified as noexcept without throwing exceptions [SWS_CRYPT_30404]. It returns a ara::core::Result<void> [SWS_CRYPT_30404]. Standardized errors do not exist; in case of an error, an implementation-specific error code is returned [SWS_CRYPT_30404]. Interpretation: The actual invocation of the callback function is likely to occur asynchronously in the context of the crypto driver as soon as the update takes effect in the key storage.
