Serves to identify Execution Management errors and map them to message texts and exception objects.

Class ara::exec::ExecErrorDomain defines the error domain for Execution Management and maps numeric error codes to descriptive messages ([SWS_EM_02288]). It is default-constructed ([SWS_EM_02286]) and allows type-safe ExecException exceptions to be thrown ([SWS_EM_02289]). When C++ exceptions are disabled, function ThrowAsException() is disabled at compile time according to [SWS_CORE_10304] ([SWS_EM_02289]).

Context

Class ara::exec::ExecErrorDomain defines the specific error domain for the Execution Management functional cluster within the AUTOSAR Adaptive Platform. As a final specialization of base class ara::core::ErrorDomain, it encapsulates the mapping of domain-specific error causes and bridges numeric error codes and semantic error descriptions. In addition to base type ara::core::ErrorDomain, the class interacts closely with ara::core::ErrorCode and, in the event of an error, instantiates specific exception objects of type ExecException ([SWS_EM_02289]). Via method Name(), the class provides a textual identifier of the domain that corresponds to specification ara::exec::ExecErrorDomain in [SWS_CORE_90023] ([SWS_EM_02287]).

Context diagram: Classification of ExecErrorDomain and its interaction partners in the error system. Sources: [SWS_EM_02287], [SWS_EM_02289], [SWS_CORE_90023]

Lifecycle

Objects of ara::exec::ExecErrorDomain are created via the default constructor ([SWS_EM_02286]). Construction is declared as noexcept and guarantees complete exception safety as well as thread safety ([SWS_EM_02286]). Because the class exposes no mutable state and is declared as final, all read operations operate without side effects. In real applications, a global or static instance of the error domain is presumably typically used (interpretation: in accordance with the general error model of Adaptive AUTOSAR), although direct instantiation via the constructor is possible at any time.

With regard to concurrency, all member functions—namely querying the name via Name() ([SWS_EM_02287]), resolving error messages via Message() ([SWS_EM_02288]), and throwing exceptions using ThrowAsException() ([SWS_EM_02289])—are explicitly specified as thread-safe. Multiple threads of execution can thus query the same instance concurrently and without external synchronization.

Usage Path

In the regular execution path, the domain serves to translate error numbers into comprehensible diagnostic messages and to convert error codes into exception objects. If an error occurs within an Execution Management operation, it is usually represented as ara::core::ErrorCode, which internally references the instance of ara::exec::ExecErrorDomain. For text output, the caller passes the numeric error identifier to Message() ([SWS_EM_02288]) and receives a pointer to an immutable string (const char*) that describes the cause.

If a calling component chooses exception-based error handling, method ThrowAsException() is used ([SWS_EM_02289]). The function accepts the reference to an ara::core::ErrorCode, creates a new instance of ExecException from it, and throws it directly as a C++ exception into the call context ([SWS_EM_02289]).

Sequence diagram: Flow when throwing a C++ exception via ThrowAsException. Sources: [SWS_EM_02289], [SWS_CORE_10304]

Error Scenarios

The information-querying methods are characterized by strict guarantees: neither construction ([SWS_EM_02286]), nor name retrieval via Name() ([SWS_EM_02287]), nor message retrieval via Message() ([SWS_EM_02288]) throws exceptions (noexcept), and all three are classified as exception-safe. For unknown error codes, Message() is likely to return a generic placeholder text or empty string (interpretation: the payload defines no separate error behavior for invalid CodeType values).

A separate behavior applies to ThrowAsException(): this function is specified as noexcept(false) and explicitly as not exception safe, since its actual purpose consists in throwing an ExecException ([SWS_EM_02289]). In addition, an essential toolchain condition takes effect: according to [SWS_CORE_10304], ThrowAsException() does not participate in overload resolution when C++ exceptions are disabled in the compiler ([SWS_EM_02289]). In system environments without exception support, this path is therefore not available at compile time, so errors must strictly be evaluated via return values.
