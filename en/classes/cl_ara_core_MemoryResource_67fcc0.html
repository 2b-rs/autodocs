Serves as a base interface for exception-free memory allocation and deallocation.

The class provides an abstract base interface for polymorphic memory resources modeled after the C++ standard interface. Via the Non-Virtual Interface pattern, it delegates allocation and deallocation requests to derived resource classes [SWS_CORE_06503]. In contrast to the C++ standard, all interface functions are declared exception-safe, which is why memory errors are not signaled via an exception, but by returning a null pointer [SWS_CORE_06566]. Furthermore, allocation and deallocation operations are by default not designed to be thread-safe.

Context

The class ara::core::MemoryResource provides an abstract base interface for memory management in the AUTOSAR Adaptive Platform (module core), modeled after the C++ standard type std::pmr::memory_resource. It serves as a common foundation for interchangeable allocation strategies and decouples calling data structures from the concrete mechanisms of memory provisioning. As a key difference from the ISO C++ standard, the AUTOSAR specification completely dispenses with dynamic exceptions and formulates strict noexcept guarantees for all operations [SWS_CORE_06501].

The architecture follows the Non-Virtual Interface pattern (NVI): public, non-virtual member functions define the fixed interface for callers, whereas the actual behavior must be implemented in derived classes via private, pure virtual member functions. Interpretation: Concrete memory resources derive from ara::core::MemoryResource and override the private base interfaces do_allocate [SWS_CORE_06566], do_deallocate [SWS_CORE_06567], and do_is_equal [SWS_CORE_06568] to provide application-specific buffer or pool managements. Question Q-d09d47b0a8f6b822 (open)

Lifecycle

Specializations are instantiated via the parameterless default constructor, which is specified as noexcept=default [SWS_CORE_06501]. A noexcept copy constructor [SWS_CORE_06502] and a noexcept copy assignment operator [SWS_CORE_06507] are likewise available. In addition to the C++ standard, AUTOSAR explicitly defines a move constructor [SWS_CORE_06574] and a move assignment operator [SWS_CORE_06575], both of which are specified as noexcept=default.

The lifecycle of polymorphic instances is secured by a virtual destructor declared as exception-safe [SWS_CORE_06506]. Regarding concurrency, it should be noted that both the destructor and the allocation and deallocation functions allocate [SWS_CORE_06503] and deallocate [SWS_CORE_06504] are specified as not thread-safe. Interpretation: Higher-level synchronization mechanisms or specialized subclasses are likely responsible for thread-safe allocations and deallocations, since the base methods are specified as not thread-safe. Question Q-adac4b6cf6e0db7c (open) Equality comparison via is_equal, on the other hand, is explicitly designed to be thread-safe [SWS_CORE_06505].

Usage Path

The primary workflow in memory management consists of requesting, optionally checking identity, and subsequently releasing memory blocks via the public NVI interface:

  • Memory allocation: The caller invokes allocate, specifying the byte size and optional alignment [SWS_CORE_06503]. The method delegates internally to the private pure virtual function do_allocate of the concrete class [SWS_CORE_06566].
  • Equality comparison: To determine whether two memory resources are equivalent to each other and memory from one can be deallocated by the other, the user invokes is_equal [SWS_CORE_06505], which delegates to do_is_equal [SWS_CORE_06568].
  • Memory deallocation: After usage is complete, the block is returned via deallocate, specifying the pointer, byte size, and alignment [SWS_CORE_06504], which triggers internal forwarding to do_deallocate [SWS_CORE_06567].

Sequence diagram: Call delegation via the NVI pattern during allocation and deallocation. Sources: [SWS_CORE_06503], [SWS_CORE_06504], [SWS_CORE_06566], [SWS_CORE_06567]

Error Scenarios

A central characteristic of the class is the complete elimination of exceptions. While the ISO C++ standard specifies an exception of type std::bad_alloc in case of exhaustion, AUTOSAR intentionally deviates from this: If an allocation fails in allocate or do_allocate, the function mandatorily returns nullptr [SWS_CORE_06503], [SWS_CORE_06566]. The attribute [[nodiscard]] on allocate obligates the caller to always receive the return value and check it for validity prior to access.

For the deallocation operations deallocate and do_deallocate, any errors during the return of memory are silently ignored [SWS_CORE_06504], [SWS_CORE_06567]. Neither exceptions are thrown nor error codes returned, which facilitates compliance with hard real-time and safety requirements in the Adaptive Platform context.
