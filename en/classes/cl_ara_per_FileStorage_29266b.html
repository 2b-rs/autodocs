Manages persistent files and opens them via RAII-based handles for block-wise reading and writing.

The class ara::per::FileStorage enables managing and opening a set of configured persistent files via unique file names [SWS_PER_00110]. The actual read and write access is performed via UniqueHandle-guided accessors, which automatically close the file again upon leaving the scope [SWS_PER_00114]. Since already opened files are protected against concurrent deletion or recovery operations, such parallel accesses fail with PerErrc::kResourceBusy [SWS_PER_00111].

Context

The class ara::per::FileStorage encapsulates access to a configured collection of persistent files identified by unique file names. It acts as a central interface for applications to perform file operations such as listing existing files via GetAllFileNames [SWS_PER_00110], checking for existence by means of FileExists [SWS_PER_00112], and querying metadata and file sizes via GetFileInfo [SWS_PER_00438] and GetCurrentFileSize [SWS_PER_00407]. Direct read or write access at the byte level does not take place on the storage instance itself, but is mediated via special accessor objects provided by the open methods as UniqueHandle [SWS_PER_00114] [SWS_PER_00113] [SWS_PER_00115].

Lifecycle

Instantiation of FileStorage is subject to strict restrictions: the default constructor [SWS_PER_00460] as well as copy and move constructors [SWS_PER_00328] [SWS_PER_00326] and copy and move assignment operators [SWS_PER_00329] [SWS_PER_00327] are explicitly deleted. An instance of FileStorage is therefore typically opened and provided via platform-side factory functions of the persistence module. The destructor ~FileStorage is exception-safe (noexcept), but explicitly specified as not thread-safe [SWS_PER_00330], which is why it must be ensured that no concurrent calls take place on the object during destruction.

During ongoing operation, regular file operations such as FileExists, DeleteFile, or opening files are designed to be thread-safe [SWS_PER_00111] [SWS_PER_00112] [SWS_PER_00114]. However, it must be noted that results of status queries such as GetAllFileNames [SWS_PER_00110] or FileExists [SWS_PER_00112] are only precisely valid if files are not concurrently added or deleted in another thread. The same applies to GetFileInfo: modification and access times as well as the editing status are only reliably accurate as long as the target file is not opened [SWS_PER_00438].

Usage Path

A typical usage path includes checking, targeted opening, data processing via the accessor handle, and final cleanup:

  1. Check file status: Prior to access, it can optionally be determined via FileExists whether a desired file exists [SWS_PER_00112], or the inventory can be queried via GetAllFileNames [SWS_PER_00110].
  2. Open file: Depending on the intended access mode, the class provides dedicated methods. For read-only access, OpenFileReadOnly overloads are available [SWS_PER_00114] [SWS_PER_00376] [SWS_PER_00430]. For read and write access, OpenFileReadWrite [SWS_PER_00113] [SWS_PER_00375] [SWS_PER_00429] is used, whereby a non-existent file is automatically created. For write-only access, OpenFileWriteOnly [SWS_PER_00115] [SWS_PER_00377] [SWS_PER_00431] exists, which by default truncates (kTruncate) or newly creates the file. To increase performance with many small accesses, overloads allow passing a user-defined buffer for block-wise reading or writing [SWS_PER_00430] [SWS_PER_00429] [SWS_PER_00431].
  3. Close file and release resources: The ara::core::Result returned by the open methods encapsulates an UniqueHandle to the respective accessor. The file is automatically closed as soon as this UniqueHandle leaves its scope [SWS_PER_00114] [SWS_PER_00113] [SWS_PER_00115]. Presumably, the file-related busy flag in FileStorage is also cleared here.
  4. Maintenance and cleanup: Files that are no longer needed are deleted with DeleteFile [SWS_PER_00111]. In the event of integrity violations, RecoverFile offers best-effort recovery of redundant data [SWS_PER_00337], while ResetFile resets a file to its initial deployment content or recreates it if missing [SWS_PER_00338].

Error Scenarios

Methods of FileStorage signal errors via ara::core::Result using the error enum PerErrc. The most important error situations include:

  • Resource conflicts (PerErrc::kResourceBusy): A file cannot be opened, deleted, recovered, or reset if it is already open or a DeleteFile, RecoverFile, or ResetFile is concurrently being executed on the same file name [SWS_PER_00111] [SWS_PER_00114] [SWS_PER_00113] [SWS_PER_00337] [SWS_PER_00338].
  • Files not found (PerErrc::kFileNotFound): Occurs when a non-existent file is to be opened for read-only access [SWS_PER_00114], deleted [SWS_PER_00111], queried [SWS_PER_00407] [SWS_PER_00438], or recovered [SWS_PER_00337].
  • Access and permission violations: Write openings or deletions fail with PerErrc::kIllegalWriteAccess if the storage is configured as read-only [SWS_PER_00111] [SWS_PER_00113] [SWS_PER_00115]. Invalid mode combinations are rejected with PerErrc::kInvalidOpenMode [SWS_PER_00114] [SWS_PER_00113].
  • Storage limits and quotas: During new creation or expansion, PerErrc::kOutOfStorageSpace (physical storage full), PerErrc::kTooManyFiles (exceeding maxNumberOfFiles), or PerErrc::kQuotaExceeded (exceeding maximumAllowedSize) may occur [SWS_PER_00113] [SWS_PER_00337] [SWS_PER_00338].
  • Integrity and security errors: In case of failures of the physical storage tier, PerErrc::kPhysicalStorageFailure is reported. Corrupted data structures, failed validations, or cryptography issues result in PerErrc::kIntegrityCorrupted, PerErrc::kValidationFailed, PerErrc::kEncryptionFailed, or PerErrc::kAuthenticationFailed [SWS_PER_00110] [SWS_PER_00112] [SWS_PER_00114] [SWS_PER_00337].
  • Missing initial data (PerErrc::kInitValueNotAvailable): Fails during reset via ResetFile if initial values were defined neither in the Application Design nor in the target configuration [SWS_PER_00338].

The synchronous method DeleteFile of class ara::per::FileStorage deletes a file from file storage by its name (fileName) [SWS_PER_00111]. The identifier can correspond to the configured PersistencyFile.fileName [SWS_PER_00111]. The invocation is specified as noexcept, is considered exception safe and thread-safe, and reports the result via ara::core::Result<void> [SWS_PER_00111].

Before the call, all active accesses to the target file must have ended. If the file is currently open, the deletion fails with error PerErrc::kResourceBusy [SWS_PER_00111]. Applications must therefore ensure that UniqueHandle instances previously created via OpenFileReadWrite [SWS_PER_00113], OpenFileReadOnly [SWS_PER_00114], or OpenFileWriteOnly [SWS_PER_00115] have left their scope, thereby closing the file. Likewise, a concurrently running execution of RecoverFile [SWS_PER_00337] or ResetFile [SWS_PER_00338] for the same file name leads to PerErrc::kResourceBusy [SWS_PER_00111].

In case of error, the returned Result type provides specific error causes [SWS_PER_00111]:

  • PerErrc::kFileNotFound: The specified file does not exist in the file storage [SWS_PER_00111].
  • PerErrc::kIllegalWriteAccess: The file storage is configured as read-only [SWS_PER_00111].
  • PerErrc::kPhysicalStorageFailure: Access to the physical storage medium fails (without rollback semantics) [SWS_PER_00111].
  • PerErrc::kIntegrityCorrupted, PerErrc::kEncryptionFailed, or PerErrc::kAuthenticationFailed: Errors in structural integrity, encryption/decryption, or MAC verification (each with rollback semantics), as well as vendor-specific errors [SWS_PER_00111].
