Classification: Records and specializations

The specification mirrors std::variant_alternative one-to-one: primary template [SWS_CORE_01607] is accompanied by partial specializations variant_alternative< I, Variant< Types... > > [SWS_CORE_01611], variant_alternative< I, const T > [SWS_CORE_01608], variant_alternative< I, volatile T > [SWS_CORE_01609], and variant_alternative< I, const volatile T > [SWS_CORE_01610], as well as alias variant_alternative_t [SWS_CORE_01612]. All records describe the content exclusively as “As per corresponding usage in [variant]” and carry DRAFT status. A separate trait is nevertheless necessary because ara::core::Variant is an independent type: std::variant_alternative is specialized only for std::variant, and the signatures of get [SWS_CORE_01613], get_if [SWS_CORE_01621], and Variant::emplace [SWS_CORE_01663] are formulated through variant_alternative_t.

Interpretation: Practically only variant_alternative_t is relevant for application code; the trait itself is rarely directly instantiated. The cv specializations reflect the C++17 status of [variant] — in the ISO standard the volatile and const volatile forms have been marked as obsolete since C++20 (P1831R1 “Deprecating volatile: library”), their removal is proposed (P2866 “Remove Deprecated Volatile Features”); the const form remains unaffected. The fact that AUTOSAR includes all four cv forms unchanged in R25-11 should be read as completeness compared to C++17, not as a recommendation for use: New code should only apply the trait to unqualified Variant types and avoid volatile-qualified variant types. The consistent DRAFT status also means that the interface is not yet formally binding and may change in future releases.
