Subscribes to dataless service triggers and counts incoming trigger pulses for the client application.

The class <SI-Namespace>::proxy::triggers::<Trigger> allows client applications to subscribe to dataless trigger pulses via Communication Management [SWS_CM_00723]. After registering a callback via SetReceiveHandler(), the application reads newly arrived pulses using GetNewTriggers() [SWS_CM_00226], [SWS_CM_00250]. Exception safety is guaranteed by default except for UnsetReceiveHandler() [SWS_CM_11614].

Context

The generated proxy class <SI-Namespace>::proxy::triggers::<Trigger> represents on the client side exactly one trigger element modeled in the service interface in the role trigger AUTOSAR_AP_SWS_CommunicationManagement §8 “Service proxy Trigger class”. Unlike event-based data streams, a trigger transmits pure trigger pulses without payload data. The class serves as an intermediary entity between the consuming client application, Communication Management (ara::com), and the E2E protection system. Its core task consists of controlling the subscription for incoming triggers, registering notification callbacks for the arrival of pulses or state changes, and providing the number of arrived triggers via a counter [SWS_CM_00226], [SWS_CM_00250].

Lifecycle

The lifetime of an instance of <SI-Namespace>::proxy::triggers::<Trigger> is tied to the lifetime of the enclosing service proxy object in which it exists as a class member. In terms of state, the trigger subscription passes through several phases that are represented by ara::com::SubscriptionState and can be queried via GetSubscriptionState() [SWS_CM_01105]:

  • Not subscribed: Initial state prior to calling Subscribe() or after a successful Unsubscribe() [SWS_CM_00723], [SWS_CM_00810].
  • Subscription pending (kSubscriptionPending): Intermediate state after triggering Subscribe() during acknowledgment of the subscription [SWS_CM_00723].
  • Subscribed (kSubscribed): The subscription is active; incoming trigger pulses increment the internal counter and lead to notification of the registered handler [SWS_CM_00226], [SWS_CM_00250].

A renewed call to Subscribe() in the states kSubscribed or kSubscriptionPending has no effect and returns without action [SWS_CM_00723]. Unsubscribe() behaves analogously if the trigger subscription does not exist at the time of the call [SWS_CM_00810]. To observe state changes, the application can register a corresponding callback by means of SetSubscriptionStateChangeHandler() [SWS_CM_01107] or deregister it via UnsetSubscriptionStateChangeHandler() [SWS_CM_01108].

State diagram: Lifecycle of the trigger subscription with transitions through Subscribe and Unsubscribe. Sources: [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_01105].

Usage Path

A typical usage path for event-driven processing of trigger signals comprises callback configuration, subscription activation, and counter query:

  1. Handler registration: The application optionally registers a state handler via SetSubscriptionStateChangeHandler() [SWS_CM_01107] and mandatorily a reception handler via SetReceiveHandler() [SWS_CM_00250]. For concurrent architectures, overloads with a dedicated ExecutorT are provided, which define the execution context for asynchronous computations [SWS_CM_00352], [SWS_CM_01106].
  2. Request subscription: The trigger subscription is started by means of Subscribe() [SWS_CM_00723].
  3. Signal reception and counter retrieval: As soon as a trigger pulse arrives, Communication Management calls the TriggerReceiveHandler without parameters [SWS_CM_00250]. Within this handler, the application calls GetNewTriggers() to update the trigger counter and read out the number of pulses that have arrived since the last call [SWS_CM_00226]. The value 0 signals here that no new pulses are present.
  4. Termination: For an orderly teardown, the application calls Unsubscribe() [SWS_CM_00810] and removes set handlers via UnsetReceiveHandler() [SWS_CM_11614] and UnsetSubscriptionStateChangeHandler() [SWS_CM_01108].

Sequence diagram: Typical flow of trigger processing from registration and subscription through signal reception to deregistration. Sources: [SWS_CM_00226], [SWS_CM_00250], [SWS_CM_00723], [SWS_CM_00810], [SWS_CM_11614].

Error Scenarios

The specification defines specific violation conditions (violations) and exception safety guarantees for the interface methods:

  • InvalidHandlerViolation: Occurs when an invalid or null callable is passed to SetReceiveHandler() [SWS_CM_00250], [SWS_CM_00352], SetSubscriptionStateChangeHandler() [SWS_CM_01106], [SWS_CM_01107], or SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107].
  • InsufficientPermissionsViolation: Is triggered in Subscribe() if access control (grant enforcement) denies permission for the trigger subscription [SWS_CM_00723].
  • Transport errors in E2E protection: Faulty transmission states are reported via the handler registered by means of SetTransportFaultConditionHandler() [SWS_CM_00106], [SWS_CM_00107], which can be deregistered again via UnsetTransportFaultConditionHandler() [SWS_CM_00108].
  • Exception safety: Almost all operations are declared as noexcept and are exception safe [SWS_CM_00226], [SWS_CM_00723]. An exception is UnsetReceiveHandler(), which according to the specification is explicitly classified as not exception safe [SWS_CM_11614]; the call presumably propagates exceptions on errors or requires separate error handling in the client application.

This guide is based exclusively on the AUTOSAR Adaptive R25-11 specification for the Communication Management module.

    With the function [SWS_CM_01107], a callback handler is registered in the proxy area of a trigger (<SI-Namespace>::proxy::triggers::<Trigger>), which Communication Management calls upon every change of the subscription state (ara::com::SubscriptionState). The function has no return value and is specified as exception-safe (noexcept).
  
                      
  
                      
    Since subscribing must fundamentally be treated as an asynchronous process, the application may only assume a successful subscription once the handler registered via [SWS_CM_01107] or the polling function GetSubscriptionState() reports the state kSubscribed [SWS_CM_12006]. In case of time delays or if the server is temporarily unavailable due to a restart or network problem, Communication Management activates the handler with the state kSubscriptionPending [SWS_CM_00313].
  
                      
  
                      
    The following boundary conditions apply to error handling and integration:
  
                      
  
                        
    
                      • Error handling: Passing a non-existent or empty callable (null) is invalid and leads to a InvalidHandlerViolation [SWS_CM_01107].
