Context

The interface <ExtendedDataRecord-Namespace>::<ExtendedDataRecordElementInterface> serves in the AUTOSAR Adaptive Platform within the functional cluster diag to provide data for so-called Extended Data Records (AUTOSAR_AP_SWS_Diagnostics p. 68). These records are collected during diagnostic events and permanently saved in non-volatile memory by Diagnostic Management (DM) ([SWS_DM_02156]).

The interface defines the provider role on the application side: An adaptive application implements the pure virtual method Read to pass the requested values to the Diagnostic Manager upon corresponding diagnostic requests ([SWS_DM_02156]). At least three system components are involved in the interaction: the application-specific interface implementation, the Diagnostic Manager as mediator of incoming diagnostic requests ([SWS_DM_02152]), and the non-volatile memory in which the DM persists the retrieved data for the diagnostic context ([SWS_DM_02156]).

Context diagram: Interaction partners of the interface for record provision. Sources: [SWS_DM_02152], [SWS_DM_02156], AUTOSAR_AP_SWS_Diagnostics p. 68

Lifecycle

Instantiation takes place via the constructor by specifying a ara::core::InstanceSpecifier and the concurrency mode ara::diag::ConcurrencyType ([SWS_DM_02158]). The parameter concurrencyType determines whether the implementation is operated thread-safe (kConcurrent) or not thread-safe (kNotConcurrent) ([SWS_DM_02158]). The class has a strict binding to its identity: copy constructor and copy assignment operator are deleted ([SWS_DM_02147], [SWS_DM_02148]). Likewise, move constructor and move assignment operator are deleted ([SWS_DM_02149], [SWS_DM_02150]). An instance is therefore bound to its location and cannot be transferred.

After successful construction, the instance initially remains in the inactive state (NotOffered). By calling Offer(), the forwarding of requests by Diagnostic Management is activated, causing the instance to transition to the Offered state ([SWS_DM_02152]). Calling Offer() again in the Offered state leads to an error ([SWS_DM_02152]). Via the method StopOffer(), forwarding is deactivated again and the object returns to the NotOffered state ([SWS_DM_02153]).

Destruction takes place via the virtual destructor ([SWS_DM_02151]). While the constructor is declared as thread-safe ([SWS_DM_02158]), the destructor is explicitly not thread-safe ([SWS_DM_02151]). Interpretation: Terminating the service offering via StopOffer() must presumably be completed before calling the destructor in order to prevent concurrent read accesses during object decay.

State diagram: Lifecycle and provision states of the interface instance. Sources: [SWS_DM_02151], [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02158]

Usage Path

The typical sequence for providing and answering diagnostic requests is as follows:

  1. Instantiation: The deriving provider class is created by passing ara::core::InstanceSpecifier and the desired concurrencyType ([SWS_DM_02158]).
  2. Announce offering: The application calls Offer(). Only after a successful return are incoming diagnostic requests forwarded from the DM to the instance ([SWS_DM_02152]).
  3. Query data record (Read): If Diagnostic Management requests the data element, it calls the method Read(metaInfo, cancellationHandler) ([SWS_DM_02156]):
    • The request provides context information via metaInfo ([SWS_DM_02156]).
    • Via cancellationHandler.IsCanceled() or by registering a notifier function using cancellationHandler.SetNotifier(), the application can handle a premature termination of the conversation ([SWS_DM_02156]).
    • The method returns a ara::core::Future with the structure ReadOutput ([SWS_DM_02154], [SWS_DM_02156]). If the data is not available at the time of retrieval, the implementation must always return a value and pad the data with a fill pattern (e.g., 0xFF) ([SWS_DM_02156]).
  4. Stop offering service: Prior to shutdown or in maintenance states, the application calls StopOffer() to stop forwarding requests ([SWS_DM_02153]).

Sequence diagram: Provision, retrieval, and termination of the diagnostic service. Sources: [SWS_DM_02152], [SWS_DM_02153], [SWS_DM_02156]

Error Scenarios

Error conditions and violations are assigned to the respective phases:

  • Violations during construction: Invalid model links lead to defined error messages ([SWS_DM_02158]):
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the executable or does not reference a PortPrototype ([SWS_DM_02158]).
    • PortInterfaceMappingViolation: A port typed by DiagnosticExtendedDataRecordInterface is not referenced by a DiagnosticDataPortMapping ([SWS_DM_02158]).
    • ProcessMappingViolation: No matching modeled process exists for the runtime process ([SWS_DM_02158]).
    • InstanceSpecifierAlreadyInUseViolation: The identifier is already used by another instance in the process ([SWS_DM_02158]).
  • Error during service registration: A repeated call to Offer() on an already offered instance fails with error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_02152]).
  • Error during data query: If the read operation cannot be performed properly, the ara::core::Future returns a diagnostic negative code (DiagUdsNrcErrc) or an application-specific error code (ApApplicationError) ([SWS_DM_02156]). If only the raw data is missing, no error may be reported; instead, the data record must be filled with the replacement value (e.g., 0xFF) ([SWS_DM_02156]).
