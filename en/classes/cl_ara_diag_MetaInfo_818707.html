Context

The class ara::diag::MetaInfo provides a standardized interface through which Diagnostic Management (DM) transmits meta information—especially from the underlying transport protocol layer—to interested applications (AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo class”). In the AUTOSAR Adaptive Platform, MetaInfo acts as an information carrier in the interaction between three main participants:

  • Diagnostic Client / transport layer: Sends UDS or SOVD diagnostic requests to the ECU. The connection attributes such as the source address (SA) [SWS_DM_02094], the target address (TA) [SWS_DM_02095], and the UDS addressing mode (TAType, physical or functional) [SWS_DM_02096] originate from the transport messages.
  • Diagnostic Management (DM): Instantiates and manages the Diagnostic Server ([SWS_DM_00420]) and creates MetaInfo objects to pass the execution context as well as transport layer parameters to registered interfaces (AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo class”, [SWS_DM_01345]).
  • Adaptive Application (AA): Implements diagnostic services (for example, service handlers via callback interfaces as in [SWS_DM_00618]), performs validations for SOVD resources (AUTOSAR_AP_SWS_Diagnostics §7.3.3 “SovdServiceValidation”), or evaluates proximity challenges in a client-specific manner (AUTOSAR_AP_SWS_Diagnostics §7.3.3 “SovdProximityChallenge”).

Context diagram: Embedding of ara::diag::MetaInfo in the interaction between Diagnostic Client, Diagnostic Management, and Adaptive Application. Sources: AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo class”, [SWS_DM_01345], [SWS_DM_02094].

Lifecycle

The instantiation and handling of ara::diag::MetaInfo are subject to strict semantic specifications. The default constructor is explicitly deleted [SWS_DM_00972], so that an application cannot create MetaInfo independently. In addition, the copy constructor [SWS_DM_00973] and the copy assignment operator [SWS_DM_00975] are deleted; the class possesses exclusive ownership semantics and prevents unintentional duplication.

Only move operations via the move constructor [SWS_DM_00974] and the move assignment operator [SWS_DM_00976] as well as destruction via the destructor [SWS_DM_00980] are permitted.

Regarding the lifetime, the binding rule [SWS_DM_01345] applies: For every method called by the DM to the application with a MetaInfo parameter, the guaranteed lifetime of the MetaInfo object is strictly limited to the execution duration of this function call. Storing the reference or reusing it after the method call returns is impermissible and leads to undefined behavior (AUTOSAR_AP_SWS_Diagnostics §7.3.1.1.2 “Lifetime of MetaInfo”).

Regarding concurrency, the read access methods GetContext() [SWS_DM_00979] and GetValue() [SWS_DM_00978] are defined as thread-safe and exception-safe (noexcept). The move assignment operator [SWS_DM_00976] and the destructor [SWS_DM_00980] are not thread-safe.

Usage Path

The typical workflow for evaluating metadata by an application is divided into the following steps:

  1. Reception of the call: Diagnostic Management calls a callback method of the application (e.g., for service processing according to [SWS_DM_00618]) and passes a ara::diag::MetaInfo instance by reference.
  2. Context check: The application calls GetContext() [SWS_DM_00979] to determine the cause or environment of the call based on the type ara::diag::MetaInfo::Context [SWS_DM_00977]. Possible values are:
    • kDiagnosticCommunication (value 0x01 [SWS_DM_01342]): Regular service request in the DCM context.
    • kFaultMemory (value 0x02 [SWS_DM_01343]): Call within the scope of the fault memory, e.g., to record snapshot DIDs.
    • kDoIP (value 0x03 [SWS_DM_01344]): DoIP-specific context, for example to read out the vehicle identification number (VIN).
    • kSovd (value 0x04 [SWS_DM_01818]): Service request in the SOVD context.
  3. Query metadata: Via the method GetValue() [SWS_DM_00978], the application reads out relevant key values. In the ara::diag interfaces, the DM provides in particular:
    • Source address of the diagnostic client via the key kSA [SWS_DM_02094].
    • Target address of the diagnostic server via the key kTA [SWS_DM_02095].
    • UDS addressing mode via the key kTAType (physical or functional) [SWS_DM_02096].
  4. Processing and return: The application processes the request taking the metadata into account and completes execution before the method returns and the lifetime of MetaInfo ends [SWS_DM_01345].

Sequence diagram: Typical query of context and transport metadata during a method call. Sources: [SWS_DM_00618], [SWS_DM_00978], [SWS_DM_00979], [SWS_DM_01345].

Error Scenarios

When using ara::diag::MetaInfo, erroneous accesses and lifetime violations can occur that require special attention:

  • Missing keys or unsuitable context: If no entry exists for a requested key, GetValue() returns an empty ara::core::Optional<ara::core::StringView> [SWS_DM_00978]. According to the specification, none of the standard keys is explicitly applicable to the context kDoIP (AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo type definition”); calls to GetValue() with UDS keys are likely to always return an empty Optional here (Interpretation 1). The application must check the return object before the contained ara::core::StringView is accessed.
  • Lifetime exceedance (Dangling References): Since the guaranteed lifetime of MetaInfo expires with the end of the method call [SWS_DM_01345], any attempt to temporarily store pointers or references to the object leads to undefined behavior (AUTOSAR_AP_SWS_Diagnostics §7.3.1.1.2 “Lifetime of MetaInfo”). Interpretation: The ara::core::StringView returned by GetValue() references volatile internal memory of MetaInfo; for asynchronous or deferred further processing, the string content must therefore be deep-copied into a separate instance (e.g., ara::core::String) before returning (Interpretation 2).
  • Exception safety: The methods GetContext() [SWS_DM_00979] and GetValue() [SWS_DM_00978] as well as the move operations [SWS_DM_00974], [SWS_DM_00976] and the destructor [SWS_DM_00980] are noexcept and do not throw any C++ exceptions.

<h4>Context</h4>
<p>The class <code>ara::diag::MetaInfo</code> provides a standardized interface through which Diagnostic Management (DM) transmits meta information—especially from the underlying transport protocol layer—to interested applications (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=113">AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo class”</a>). In the AUTOSAR Adaptive Platform, <code>MetaInfo</code> acts as an information carrier in the interaction between three main participants:</p>
<ul>
<li><strong>Diagnostic Client / transport layer:</strong> Sends UDS or SOVD diagnostic requests to the ECU. The connection attributes such as the source address (SA) <a class="spec-record-ref" data-req="SWS_DM_02094" href="../spec/record.html?id=SWS_DM_02094">[SWS_DM_02094]</a>, the target address (TA) <a class="spec-record-ref" data-req="SWS_DM_02095" href="../spec/record.html?id=SWS_DM_02095">[SWS_DM_02095]</a>, and the UDS addressing mode (TAType, physical or functional) <a class="spec-record-ref" data-req="SWS_DM_02096" href="../spec/record.html?id=SWS_DM_02096">[SWS_DM_02096]</a> originate from the transport messages.</li>
<li><strong>Diagnostic Management (DM):</strong> Instantiates and manages the Diagnostic Server (<a class="spec-record-ref" data-req="SWS_DM_00420" href="../spec/record.html?id=SWS_DM_00420">[SWS_DM_00420]</a>) and creates <code>MetaInfo</code> objects to pass the execution context as well as transport layer parameters to registered interfaces (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=113">AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo class”</a>, <a class="spec-record-ref" data-req="SWS_DM_01345" href="../spec/record.html?id=SWS_DM_01345">[SWS_DM_01345]</a>).</li>
<li><strong>Adaptive Application (AA):</strong> Implements diagnostic services (for example, service handlers via callback interfaces as in <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>), performs validations for SOVD resources (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=197">AUTOSAR_AP_SWS_Diagnostics §7.3.3 “SovdServiceValidation”</a>), or evaluates proximity challenges in a client-specific manner (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=215">AUTOSAR_AP_SWS_Diagnostics §7.3.3 “SovdProximityChallenge”</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>The instantiation and handling of <code>ara::diag::MetaInfo</code> are subject to strict semantic specifications. The default constructor is explicitly deleted <a class="spec-record-ref" data-req="SWS_DM_00972" href="../spec/record.html?id=SWS_DM_00972">[SWS_DM_00972]</a>, so that an application cannot create <code>MetaInfo</code> independently. In addition, the copy constructor <a class="spec-record-ref" data-req="SWS_DM_00973" href="../spec/record.html?id=SWS_DM_00973">[SWS_DM_00973]</a> and the copy assignment operator <a class="spec-record-ref" data-req="SWS_DM_00975" href="../spec/record.html?id=SWS_DM_00975">[SWS_DM_00975]</a> are deleted; the class possesses exclusive ownership semantics and prevents unintentional duplication.</p>
<p>Only move operations via the move constructor <a class="spec-record-ref" data-req="SWS_DM_00974" href="../spec/record.html?id=SWS_DM_00974">[SWS_DM_00974]</a> and the move assignment operator <a class="spec-record-ref" data-req="SWS_DM_00976" href="../spec/record.html?id=SWS_DM_00976">[SWS_DM_00976]</a> as well as destruction via the destructor <a class="spec-record-ref" data-req="SWS_DM_00980" href="../spec/record.html?id=SWS_DM_00980">[SWS_DM_00980]</a> are permitted.</p>
<p>Regarding the lifetime, the binding rule <a class="spec-record-ref" data-req="SWS_DM_01345" href="../spec/record.html?id=SWS_DM_01345">[SWS_DM_01345]</a> applies: For every method called by the DM to the application with a <code>MetaInfo</code> parameter, the guaranteed lifetime of the <code>MetaInfo</code> object is strictly limited to the execution duration of this function call. Storing the reference or reusing it after the method call returns is impermissible and leads to undefined behavior (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=116">AUTOSAR_AP_SWS_Diagnostics §7.3.1.1.2 “Lifetime of MetaInfo”</a>).</p>
<p>Regarding concurrency, the read access methods <code>GetContext()</code> <a class="spec-record-ref" data-req="SWS_DM_00979" href="../spec/record.html?id=SWS_DM_00979">[SWS_DM_00979]</a> and <code>GetValue()</code> <a class="spec-record-ref" data-req="SWS_DM_00978" href="../spec/record.html?id=SWS_DM_00978">[SWS_DM_00978]</a> are defined as thread-safe and exception-safe (<code>noexcept</code>). The move assignment operator <a class="spec-record-ref" data-req="SWS_DM_00976" href="../spec/record.html?id=SWS_DM_00976">[SWS_DM_00976]</a> and the destructor <a class="spec-record-ref" data-req="SWS_DM_00980" href="../spec/record.html?id=SWS_DM_00980">[SWS_DM_00980]</a> are not thread-safe.</p>

<h4>Usage Path</h4>
<p>The typical workflow for evaluating metadata by an application is divided into the following steps:</p>
<ol>
<li><strong>Reception of the call:</strong> Diagnostic Management calls a callback method of the application (e.g., for service processing according to <a class="spec-record-ref" data-req="SWS_DM_00618" href="../spec/record.html?id=SWS_DM_00618">[SWS_DM_00618]</a>) and passes a <code>ara::diag::MetaInfo</code> instance by reference.</li>
<li><strong>Context check:</strong> The application calls <code>GetContext()</code> <a class="spec-record-ref" data-req="SWS_DM_00979" href="../spec/record.html?id=SWS_DM_00979">[SWS_DM_00979]</a> to determine the cause or environment of the call based on the type <code>ara::diag::MetaInfo::Context</code> <a class="spec-record-ref" data-req="SWS_DM_00977" href="../spec/record.html?id=SWS_DM_00977">[SWS_DM_00977]</a>. Possible values are:
<ul>
<li><code>kDiagnosticCommunication</code> (value <code>0x01</code> <a class="spec-record-ref" data-req="SWS_DM_01342" href="../spec/record.html?id=SWS_DM_01342">[SWS_DM_01342]</a>): Regular service request in the DCM context.</li>
<li><code>kFaultMemory</code> (value <code>0x02</code> <a class="spec-record-ref" data-req="SWS_DM_01343" href="../spec/record.html?id=SWS_DM_01343">[SWS_DM_01343]</a>): Call within the scope of the fault memory, e.g., to record snapshot DIDs.</li>
<li><code>kDoIP</code> (value <code>0x03</code> <a class="spec-record-ref" data-req="SWS_DM_01344" href="../spec/record.html?id=SWS_DM_01344">[SWS_DM_01344]</a>): DoIP-specific context, for example to read out the vehicle identification number (VIN).</li>
<li><code>kSovd</code> (value <code>0x04</code> <a class="spec-record-ref" data-req="SWS_DM_01818" href="../spec/record.html?id=SWS_DM_01818">[SWS_DM_01818]</a>): Service request in the SOVD context.</li>
</ul>
</li>
<li><strong>Query metadata:</strong> Via the method <code>GetValue()</code> <a class="spec-record-ref" data-req="SWS_DM_00978" href="../spec/record.html?id=SWS_DM_00978">[SWS_DM_00978]</a>, the application reads out relevant key values. In the ara::diag interfaces, the DM provides in particular:
<ul>
<li>Source address of the diagnostic client via the key <code>kSA</code> <a class="spec-record-ref" data-req="SWS_DM_02094" href="../spec/record.html?id=SWS_DM_02094">[SWS_DM_02094]</a>.</li>
<li>Target address of the diagnostic server via the key <code>kTA</code> <a class="spec-record-ref" data-req="SWS_DM_02095" href="../spec/record.html?id=SWS_DM_02095">[SWS_DM_02095]</a>.</li>
<li>UDS addressing mode via the key <code>kTAType</code> (physical or functional) <a class="spec-record-ref" data-req="SWS_DM_02096" href="../spec/record.html?id=SWS_DM_02096">[SWS_DM_02096]</a>.</li>
</ul>
</li>
<li><strong>Processing and return:</strong> The application processes the request taking the metadata into account and completes execution before the method returns and the lifetime of <code>MetaInfo</code> ends <a class="spec-record-ref" data-req="SWS_DM_01345" href="../spec/record.html?id=SWS_DM_01345">[SWS_DM_01345]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>When using <code>ara::diag::MetaInfo</code>, erroneous accesses and lifetime violations can occur that require special attention:</p>
<ul>
<li><strong>Missing keys or unsuitable context:</strong> If no entry exists for a requested key, <code>GetValue()</code> returns an empty <code>ara::core::Optional&lt;ara::core::StringView&gt;</code> <a class="spec-record-ref" data-req="SWS_DM_00978" href="../spec/record.html?id=SWS_DM_00978">[SWS_DM_00978]</a>. According to the specification, none of the standard keys is explicitly applicable to the context <code>kDoIP</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=114">AUTOSAR_AP_SWS_Diagnostics §7.3.1.1 “MetaInfo type definition”</a>); calls to <code>GetValue()</code> with UDS keys are likely to always return an empty <code>Optional</code> here (Interpretation 1). The application must check the return object before the contained <code>ara::core::StringView</code> is accessed.</li>
<li><strong>Lifetime exceedance (Dangling References):</strong> Since the guaranteed lifetime of <code>MetaInfo</code> expires with the end of the method call <a class="spec-record-ref" data-req="SWS_DM_01345" href="../spec/record.html?id=SWS_DM_01345">[SWS_DM_01345]</a>, any attempt to temporarily store pointers or references to the object leads to undefined behavior (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=116">AUTOSAR_AP_SWS_Diagnostics §7.3.1.1.2 “Lifetime of MetaInfo”</a>). Interpretation: The <code>ara::core::StringView</code> returned by <code>GetValue()</code> references volatile internal memory of <code>MetaInfo</code>; for asynchronous or deferred further processing, the string content must therefore be deep-copied into a separate instance (e.g., <code>ara::core::String</code>) before returning (Interpretation 2).</li>
<li><strong>Exception safety:</strong> The methods <code>GetContext()</code> <a class="spec-record-ref" data-req="SWS_DM_00979" href="../spec/record.html?id=SWS_DM_00979">[SWS_DM_00979]</a> and <code>GetValue()</code> <a class="spec-record-ref" data-req="SWS_DM_00978" href="../spec/record.html?id=SWS_DM_00978">[SWS_DM_00978]</a> as well as the move operations <a class="spec-record-ref" data-req="SWS_DM_00974" href="../spec/record.html?id=SWS_DM_00974">[SWS_DM_00974]</a>, <a class="spec-record-ref" data-req="SWS_DM_00976" href="../spec/record.html?id=SWS_DM_00976">[SWS_DM_00976]</a> and the destructor <a class="spec-record-ref" data-req="SWS_DM_00980" href="../spec/record.html?id=SWS_DM_00980">[SWS_DM_00980]</a> are <code>noexcept</code> and do not throw any C++ exceptions.</li>
</ul>
