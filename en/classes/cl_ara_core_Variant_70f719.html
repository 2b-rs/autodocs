Context

The template class ara::core::Variant provides a type-safe union (sum type) in the core module of the AUTOSAR Adaptive Platform. The implementation is conceptually based on the type std::variant from the C++ standard, but defines platform-specific deviations and clarifications regarding exception handling and the conditions for noexcept. At any given time, a ara::core::Variant either manages exactly one value from the declared type list Types... or is in the valueless state as a result of an error.

Typical interaction partners are functional Adaptive Applications and service interfaces that pass polymorphic data structures in a type-safe manner without dynamic memory allocation or inheritance hierarchies. Inclusion is performed via the header file ara/core/variant.h, as specified in the associated specification requirements such as [SWS_CORE_01649].

Lifecycle

The lifecycle of an instance of ara::core::Variant is divided into the phases of creation, state transformation, error state, and destruction:

  • Default construction: The parameterless default constructor [SWS_CORE_01649] initializes the instance with the first alternative (index 0), provided that it is default-constructible. Execution is constexpr and conditionally noexcept.
  • Value and move construction: An instance can be instantiated by taking a value [SWS_CORE_01652], via the copy constructor [SWS_CORE_01650], or via the move constructor [SWS_CORE_01651]. All three operations are subject to specific noexcept conditions.
  • In-place construction: To avoid temporary copies, constructors with placeholder tags are available: type-based via in_place_type_t ([SWS_CORE_01653], [SWS_CORE_01654]) or index-based via in_place_index_t ([SWS_CORE_01655], [SWS_CORE_01656]). These constructors are declared as explicit and constexpr.
  • Value modification and state transition: During the usage phase, the contained value can be replaced via assignment operators ([SWS_CORE_01658], [SWS_CORE_01659], [SWS_CORE_01660]), via type-based emplace methods ([SWS_CORE_01661], [SWS_CORE_01662]), via index-based emplace methods ([SWS_CORE_01663], [SWS_CORE_01664]), or by swap [SWS_CORE_01667].
  • Destruction: The destructor [SWS_CORE_01657] destroys the currently active alternative. It is conditionally declared noexcept.

State diagram: States and transitions of a Variant instance between validity, error state, and destruction. Sources: [SWS_CORE_01649], [SWS_CORE_01657], [SWS_CORE_01661], [SWS_CORE_01666].

Usage Path

A typical usage path includes in-place initialization, querying the active type, and changing the held alternative:

  1. Initialization: The object is specifically initialized with an alternative, for example via in_place_type_t according to [SWS_CORE_01653], in order to forward arguments directly to the constructor of the target type.
  2. Status check: Before access, the application checks the zero-based index of the currently held alternative via the method index() [SWS_CORE_01665]. In addition, valueless_by_exception() [SWS_CORE_01666] can be used to verify whether the instance is in an intact state.
  3. Reassignment: If an alternative type is to be placed in the same memory area, emplace ([SWS_CORE_01661] or [SWS_CORE_01663]) is called. This destroys the previous alternative and creates the new value directly in place.
  4. Destruction: When leaving the scope, the destructor [SWS_CORE_01657] is called, which properly cleans up the active alternative.

Sequence diagram: Typical sequence of initialization, status query, and type change in ara::core::Variant. Sources: [SWS_CORE_01653], [SWS_CORE_01661], [SWS_CORE_01665], [SWS_CORE_01666].

Error Scenarios

In the area of error scenarios and exception handling, ara::core::Variant is characterized by the following properties:

  • valueless_by_exception state: If during a value assignment ([SWS_CORE_01658], [SWS_CORE_01659], [SWS_CORE_01660]) or a re-initialization via emplace ([SWS_CORE_01661], [SWS_CORE_01663]) the constructor of the new alternative throws an exception and the old alternative has already been destroyed, the object remains in the state without a value. This state is queried via valueless_by_exception() [SWS_CORE_01666]. In this state, index() returns the value variant_npos. Recovery is only possible through another successful assignment or emplace.
  • Conditional noexcept guarantees: Almost all constructing and modifying methods (e.g., [SWS_CORE_01650], [SWS_CORE_01653], [SWS_CORE_01661]) have the status conditionally exception safe and are provided with conditional noexcept clauses (for example, based on std::is_nothrow_constructible). They guarantee freedom from exceptions exclusively when the involved operations of the user types themselves are noexcept.
  • Unrestricted guarantees: The query methods index() [SWS_CORE_01665] and valueless_by_exception() [SWS_CORE_01666] are unconditionally declared as noexcept and offer unrestricted exception safety (exception safe).
  • Swap modifications: For swap [SWS_CORE_01667], the conditions for exception safety are modified compared to the standard to ensure controlled handling in AUTOSAR environments.
