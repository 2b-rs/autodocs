class ara::per::WriteAccessor

[SWS_PER_00595] Upstream: RS_PER_00004, RS_AP_00122, RS_AP_00146

class WriteAccessor final :              public virtual FileAccessor {...};

WriteAccessor is used to write file data. It provides the WriteBinary and WriteText methods featuring a Result for controlled, unformatted writing, and the operator<< method for simple formatted writing. It also provides SyncToFile() to flush the buffer of the operating system to the physical storage.

Context

The class ara::per::WriteAccessor represents the interface for write file access within the AUTOSAR Adaptive Platform. It inherits virtually from FileAccessor and takes responsibility for targeted modification, overwriting, and truncation of persistent file contents. It provides unformatted write methods for data passing: WriteBinary accepts raw data as ara::core::Span<const ara::core::Byte> ([SWS_PER_00423]), while WriteText processes strings in the form of ara::core::StringView ([SWS_PER_00166]). In addition, the overloaded streaming operator operator<< offers a simplified possibility for formatted text output ([SWS_PER_00125]).

A key characteristic of WriteAccessor is the decoupling of virtual writing and physical persistence: when calling WriteBinary or WriteText, data is initially transferred into buffer structures. The exact point in time at which this data is permanently stored on the storage medium is implementation-dependent ([SWS_PER_00423], [SWS_PER_00166]). To force immediate writing from the operating system buffer to physical storage, the class provides the synchronization method SyncToFile ([SWS_PER_00122]). In addition, SetFileSize enables reducing the size of existing files to a specified byte size ([SWS_PER_00428]).

Lifecycle

The default constructor of WriteAccessor is explicitly deleted (WriteAccessor() = delete;, [SWS_PER_00596]). Direct, uninitialized instantiation by the application is therefore not permitted; valid instances are typically likely to be created and passed by higher-level persistence management entities when opening files in write mode. Destruction and resource release occur deterministically via the virtual destructor ~WriteAccessor() ([SWS_PER_00597]).

With regard to concurrency, all member functions of WriteAccessor are specified as not thread-safe ("not thread-safe") ([SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00125], [SWS_PER_00428], [SWS_PER_00122], [SWS_PER_00597]). If multiple threads of execution access the same instance simultaneously, cross-thread synchronization is the responsibility of the calling application. All operations are declared as noexcept and ensure exception safety ("exception safe"), since feedback and error states are signaled not via C++ exceptions, but via the return type ara::core::Result<void>.

Usage Path

The typical usage of WriteAccessor is divided into data transfer, optional resizing, and explicit synchronization with the storage medium:

  1. Write data: The application passes data blocks sequentially using WriteBinary ([SWS_PER_00423]) or WriteText ([SWS_PER_00166]). Both methods return a ara::core::Result<void> that must be checked for success. For non-critical use cases, operator<< can be used alternatively ([SWS_PER_00125]).
  2. Resize file (optional): If the file is to be truncated, SetFileSize is called ([SWS_PER_00428]). If the current file position is beyond the new target size, it is set to the new end of file; with a target size of 0, the position is also set to 0.
  3. Force persistence: To ensure that modified data does not remain in the volatile buffer in case of an error or power loss, the application calls SyncToFile ([SWS_PER_00122]), which commits the buffer content to the physical medium.

Sequence diagram: Typical sequence when writing data and subsequently forcing persistence. Sources: [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122]

Error Scenarios

In the event of errors, the specification distinguishes strictly by the interface used as well as between errors with and without rollback semantics:

  • Silent ignoring with operator<<: If an error occurs during the use of the streaming operator, it is ignored without feedback ([SWS_PER_00125]). This operator is explicitly intended as a convenience function for non-critical paths and must not be used in safety-relevant use cases.
  • Errors with WriteBinary and WriteText: If a write operation fails, the file content may be corrupted ([SWS_PER_00423], [SWS_PER_00166]). With PerErrc::kPhysicalStorageFailure ("no_rollback_semantics"), the state of the file is undefined; it may be completely destroyed. With PerErrc::kOutOfStorageSpace ("no_rollback_semantics"), the file content is updated, but the part exceeding the available storage space is discarded; the file position is at the end of the file. If PerErrc::kEncryptionFailed ("rollback_semantics") occurs, the buffer and position were updated, but the changes could not be persisted, leaving the stored file at an older state. Further possible errors with rollback semantics are PerErrc::kQuotaExceeded (exceeding the configured AllowedSize of the file storage), PerErrc::kValidationFailed (validation failed), and PerErrc::kAuthenticationFailed (error during MAC calculation or verification).
  • Errors with SetFileSize: The method is used exclusively to reduce the file size. If the parameter size is greater than the current file size, the call fails with PerErrc::kInvalidSize ([SWS_PER_00428]). In addition, PerErrc::kPhysicalStorageFailure, PerErrc::kValidationFailed, PerErrc::kEncryptionFailed, and PerErrc::kAuthenticationFailed can occur.
  • Errors during SyncToFile: When flushing the buffer to the medium, PerErrc::kPhysicalStorageFailure and PerErrc::kOutOfStorageSpace (without rollback) as well as PerErrc::kEncryptionFailed, PerErrc::kQuotaExceeded, and PerErrc::kAuthenticationFailed (with rollback) can be reported ([SWS_PER_00122]).

WriteBinary function

Writes the content of a Span of Byte to the file. The time when the content is persisted depends on the implementation of Persistency. SyncTo File can be used to force Persistency to persist the file content. In case of an error, the file content might be corrupted, and the current position might or might not have changed. The expected state of the file for each supported error can be expected to be as follows: • kPhysicalStorageFailure: The state of the file is unknown. It could have been entirely destroyed. • kEncryptionFailed: The content of the file and the current position will have been updated, but could not be persisted. The persisted file will reflect an older version of the file. • kOutOfStorageSpace: The content of the file will have been updated, but the part of the operation that exceeded the quota will have been discarded. The current position will be at the end of the file.

<h4>Context</h4>
<p>The class <code>ara::per::WriteAccessor</code> represents the interface for write file access within the AUTOSAR Adaptive Platform. It inherits virtually from <code>FileAccessor</code> and takes responsibility for targeted modification, overwriting, and truncation of persistent file contents. It provides unformatted write methods for data passing: <code>WriteBinary</code> accepts raw data as <code>ara::core::Span&lt;const ara::core::Byte&gt;</code> (<a class="spec-record-ref" data-req="SWS_PER_00423" href="../spec/record.html?id=SWS_PER_00423">[SWS_PER_00423]</a>), while <code>WriteText</code> processes strings in the form of <code>ara::core::StringView</code> (<a class="spec-record-ref" data-req="SWS_PER_00166" href="../spec/record.html?id=SWS_PER_00166">[SWS_PER_00166]</a>). In addition, the overloaded streaming operator <code>operator&lt;&lt;</code> offers a simplified possibility for formatted text output (<a class="spec-record-ref" data-req="SWS_PER_00125" href="../spec/record.html?id=SWS_PER_00125">[SWS_PER_00125]</a>).</p>
<p>A key characteristic of <code>WriteAccessor</code> is the decoupling of virtual writing and physical persistence: when calling <code>WriteBinary</code> or <code>WriteText</code>, data is initially transferred into buffer structures. The exact point in time at which this data is permanently stored on the storage medium is implementation-dependent (<a class="spec-record-ref" data-req="SWS_PER_00423" href="../spec/record.html?id=SWS_PER_00423">[SWS_PER_00423]</a>, <a class="spec-record-ref" data-req="SWS_PER_00166" href="../spec/record.html?id=SWS_PER_00166">[SWS_PER_00166]</a>). To force immediate writing from the operating system buffer to physical storage, the class provides the synchronization method <code>SyncToFile</code> (<a class="spec-record-ref" data-req="SWS_PER_00122" href="../spec/record.html?id=SWS_PER_00122">[SWS_PER_00122]</a>). In addition, <code>SetFileSize</code> enables reducing the size of existing files to a specified byte size (<a class="spec-record-ref" data-req="SWS_PER_00428" href="../spec/record.html?id=SWS_PER_00428">[SWS_PER_00428]</a>).</p>

<h4>Lifecycle</h4>
<p>The default constructor of <code>WriteAccessor</code> is explicitly deleted (<code>WriteAccessor() = delete;</code>, <a class="spec-record-ref" data-req="SWS_PER_00596" href="../spec/record.html?id=SWS_PER_00596">[SWS_PER_00596]</a>). Direct, uninitialized instantiation by the application is therefore not permitted; valid instances are typically likely to be created and passed by higher-level persistence management entities when opening files in write mode. Destruction and resource release occur deterministically via the virtual destructor <code>~WriteAccessor()</code> (<a class="spec-record-ref" data-req="SWS_PER_00597" href="../spec/record.html?id=SWS_PER_00597">[SWS_PER_00597]</a>).</p>
<p>With regard to concurrency, all member functions of <code>WriteAccessor</code> are specified as not thread-safe ("not thread-safe") (<a class="spec-record-ref" data-req="SWS_PER_00423" href="../spec/record.html?id=SWS_PER_00423">[SWS_PER_00423]</a>, <a class="spec-record-ref" data-req="SWS_PER_00166" href="../spec/record.html?id=SWS_PER_00166">[SWS_PER_00166]</a>, <a class="spec-record-ref" data-req="SWS_PER_00125" href="../spec/record.html?id=SWS_PER_00125">[SWS_PER_00125]</a>, <a class="spec-record-ref" data-req="SWS_PER_00428" href="../spec/record.html?id=SWS_PER_00428">[SWS_PER_00428]</a>, <a class="spec-record-ref" data-req="SWS_PER_00122" href="../spec/record.html?id=SWS_PER_00122">[SWS_PER_00122]</a>, <a class="spec-record-ref" data-req="SWS_PER_00597" href="../spec/record.html?id=SWS_PER_00597">[SWS_PER_00597]</a>). If multiple threads of execution access the same instance simultaneously, cross-thread synchronization is the responsibility of the calling application. All operations are declared as <code>noexcept</code> and ensure exception safety ("exception safe"), since feedback and error states are signaled not via C++ exceptions, but via the return type <code>ara::core::Result&lt;void&gt;</code>.</p>

<h4>Usage Path</h4>
<p>The typical usage of <code>WriteAccessor</code> is divided into data transfer, optional resizing, and explicit synchronization with the storage medium:</p>
<ol>
<li><strong>Write data</strong>: The application passes data blocks sequentially using <code>WriteBinary</code> (<a class="spec-record-ref" data-req="SWS_PER_00423" href="../spec/record.html?id=SWS_PER_00423">[SWS_PER_00423]</a>) or <code>WriteText</code> (<a class="spec-record-ref" data-req="SWS_PER_00166" href="../spec/record.html?id=SWS_PER_00166">[SWS_PER_00166]</a>). Both methods return a <code>ara::core::Result&lt;void&gt;</code> that must be checked for success. For non-critical use cases, <code>operator&lt;&lt;</code> can be used alternatively (<a class="spec-record-ref" data-req="SWS_PER_00125" href="../spec/record.html?id=SWS_PER_00125">[SWS_PER_00125]</a>).</li>
<li><strong>Resize file (optional)</strong>: If the file is to be truncated, <code>SetFileSize</code> is called (<a class="spec-record-ref" data-req="SWS_PER_00428" href="../spec/record.html?id=SWS_PER_00428">[SWS_PER_00428]</a>). If the current file position is beyond the new target size, it is set to the new end of file; with a target size of 0, the position is also set to 0.</li>
<li><strong>Force persistence</strong>: To ensure that modified data does not remain in the volatile buffer in case of an error or power loss, the application calls <code>SyncToFile</code> (<a class="spec-record-ref" data-req="SWS_PER_00122" href="../spec/record.html?id=SWS_PER_00122">[SWS_PER_00122]</a>), which commits the buffer content to the physical medium.</li>
</ol>

<h4>Error Scenarios</h4>
<p>In the event of errors, the specification distinguishes strictly by the interface used as well as between errors with and without rollback semantics:</p>
<ul>
<li><strong>Silent ignoring with <code>operator&lt;&lt;</code></strong>: If an error occurs during the use of the streaming operator, it is ignored without feedback (<a class="spec-record-ref" data-req="SWS_PER_00125" href="../spec/record.html?id=SWS_PER_00125">[SWS_PER_00125]</a>). This operator is explicitly intended as a convenience function for non-critical paths and must not be used in safety-relevant use cases.</li>
<li><strong>Errors with <code>WriteBinary</code> and <code>WriteText</code></strong>: If a write operation fails, the file content may be corrupted (<a class="spec-record-ref" data-req="SWS_PER_00423" href="../spec/record.html?id=SWS_PER_00423">[SWS_PER_00423]</a>, <a class="spec-record-ref" data-req="SWS_PER_00166" href="../spec/record.html?id=SWS_PER_00166">[SWS_PER_00166]</a>). With <code>PerErrc::kPhysicalStorageFailure</code> ("no_rollback_semantics"), the state of the file is undefined; it may be completely destroyed. With <code>PerErrc::kOutOfStorageSpace</code> ("no_rollback_semantics"), the file content is updated, but the part exceeding the available storage space is discarded; the file position is at the end of the file. If <code>PerErrc::kEncryptionFailed</code> ("rollback_semantics") occurs, the buffer and position were updated, but the changes could not be persisted, leaving the stored file at an older state. Further possible errors with rollback semantics are <code>PerErrc::kQuotaExceeded</code> (exceeding the configured <code>AllowedSize</code> of the file storage), <code>PerErrc::kValidationFailed</code> (validation failed), and <code>PerErrc::kAuthenticationFailed</code> (error during MAC calculation or verification).</li>
<li><strong>Errors with <code>SetFileSize</code></strong>: The method is used exclusively to reduce the file size. If the parameter <code>size</code> is greater than the current file size, the call fails with <code>PerErrc::kInvalidSize</code> (<a class="spec-record-ref" data-req="SWS_PER_00428" href="../spec/record.html?id=SWS_PER_00428">[SWS_PER_00428]</a>). In addition, <code>PerErrc::kPhysicalStorageFailure</code>, <code>PerErrc::kValidationFailed</code>, <code>PerErrc::kEncryptionFailed</code>, and <code>PerErrc::kAuthenticationFailed</code> can occur.</li>
<li><strong>Errors during <code>SyncToFile</code></strong>: When flushing the buffer to the medium, <code>PerErrc::kPhysicalStorageFailure</code> and <code>PerErrc::kOutOfStorageSpace</code> (without rollback) as well as <code>PerErrc::kEncryptionFailed</code>, <code>PerErrc::kQuotaExceeded</code>, and <code>PerErrc::kAuthenticationFailed</code> (with rollback) can be reported (<a class="spec-record-ref" data-req="SWS_PER_00122" href="../spec/record.html?id=SWS_PER_00122">[SWS_PER_00122]</a>).</li>
</ul>
