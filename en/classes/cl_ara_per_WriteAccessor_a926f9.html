class ara::per::WriteAccessor

[SWS_PER_00595] Upstream: RS_PER_00004, RS_AP_00122, RS_AP_00146

class WriteAccessor final :              public virtual FileAccessor {...};

WriteAccessor is used to write file data. It provides the WriteBinary and WriteText methods featuring a Result for controlled, unformatted writing, and the operator<< method for simple formatted writing. Serves for buffered writing of binary and text files as well as their synchronization to physical storage.

The ara::per::WriteAccessor class enables writing binary or textual file contents in the persistence module and provides methods for unformatted write access as well as a formatted stream operator [SWS_PER_00423]. Because write operations can initially be buffered in the operating system, calling SyncToFile() forces permanent flushing to physical storage [SWS_PER_00122]. All methods are exception-safe, but not thread-safe, which is why concurrent access must be protected by the application.

Context

ara::per::WriteAccessor is a final class of the persistence module (per) of the AUTOSAR Adaptive Platform and inherits virtually from FileAccessor. The class provides write operations for file contents. It offers methods for unformatted, controlled writing with error handling via ara::core::Result as well as an overloaded stream operator for formatted writing. The calling application, the operating system's internal file buffer, and the physical storage medium act as interaction partners.

Lifecycle

The default constructor of WriteAccessor is explicitly deleted and must not be used [SWS_PER_00596]. (Interpretation: Instances of WriteAccessor are likely created and provided via factory methods of higher-level persistence management entities such as file storage.) Question Q-af92be8494274611 (open)

Destruction takes place via the virtual destructor ~WriteAccessor() [SWS_PER_00597]. The class and its methods are specified as exception safe and declared as noexcept. Regarding concurrency, WriteAccessor is not thread-safe [SWS_PER_00597]; concurrent access to the same instance must be protected externally by the application.

Usage Path

The regular flow comprises writing data in unformatted or formatted mode, optionally adjusting the file size, and the concluding persistent storage:

  • Writing binary data: A byte range (ara::core::Span<const ara::core::Byte>) is written to the file via WriteBinary() [SWS_PER_00423].
  • Writing text data: Strings are passed via a ara::core::StringView using WriteText() [SWS_PER_00166]. In addition, operator<< is available as a convenience function for non-critical use cases, with occurring errors being silently ignored [SWS_PER_00125].
  • Enforcing persistence: The time of physical storage depends on the persistence implementation; SyncToFile() conclusively flushes the operating system buffer to the storage medium [SWS_PER_00122], [SWS_PER_00423], [SWS_PER_00166].
  • Adjusting file size: The file can be truncated using SetFileSize(), whereby trailing contents are removed; the file position remains unchanged or is set to the last valid position or 0 [SWS_PER_00428].

Sequence diagram: Write operations with subsequent synchronization to physical storage. Sources: [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122]

Error Scenarios

The methods WriteBinary(), WriteText(), SyncToFile(), and SetFileSize() return a ara::core::Result<void> that contains specific error codes upon failure:

  • PerErrc::kPhysicalStorageFailure: Access to the physical storage medium fails [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122], [SWS_PER_00428]. The state of the file is unknown and may be completely corrupted (no rollback semantics).
  • PerErrc::kOutOfStorageSpace: Insufficient physical storage space [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122]. During writing, the exceeding portion is discarded and the position is at the end of the file (no rollback semantics).
  • PerErrc::kQuotaExceeded: The file would exceed the configured maximum size (AllowedSize) [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122] (rollback semantics).
  • PerErrc::kEncryptionFailed: Encryption or decryption fails [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122], [SWS_PER_00428]. While buffer and position are updated, the file cannot be persisted and reflects an older version on storage (rollback semantics).
  • PerErrc::kAuthenticationFailed: Calculation or verification of the MAC fails [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00122], [SWS_PER_00428] (rollback semantics).
  • PerErrc::kValidationFailed: Validity of the stored data cannot be ensured [SWS_PER_00423], [SWS_PER_00166], [SWS_PER_00428] (rollback semantics).
  • PerErrc::kInvalidSize: The new file size in SetFileSize() is larger than the current file size [SWS_PER_00428] (rollback semantics).

WriteBinary function

Writes the content of a Span of Byte to the file. The time when the content is persisted depends on the implementation of Persistency. SyncTo File can be used to force Persistency to persist the file content. In case of an error, the file content might be corrupted, and the current position might or might not have changed. The expected state of the file for each supported error can be expected to be as follows: • kPhysicalStorageFailure: The state of the file is unknown. It could have been entirely destroyed. • kEncryptionFailed: The content of the file and the current position will have been updated, but could not be persisted. The persisted file will reflect an older version of the file. • kOutOfStorageSpace: The content of the file will have been updated, but the part of the operation that exceeded the quota will have been discarded. The current position will be at the end of the file.

                  ara::core::Result< void > WriteText (ara::core::StringView s) noexcept;
                  

                  Writes the content of a StringView to the file. The time when the content is persisted depends on the implementation of Persistency. SyncTo File can be used to force Persistency to persist the file content. In case of an error, the file content might be corrupted, and the current position might or might not have changed. The expected state of the file for each supported error can be expected to be as follows: • kPhysicalStorageFailure: The state of the file is unknown. It could have been entirely destroyed. • kEncryptionFailed: The content of the file and the current position will have been updated, but could not be persisted. The persisted file will reflect an older version of the file. • kOutOfStorageSpace: The content of the file will have been updated, but the part of the operation that exceeded the quota will have been discarded. The current position will be at the end of the file.
