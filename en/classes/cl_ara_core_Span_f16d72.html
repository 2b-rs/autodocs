Provides an efficient, non-owning view of contiguous memory areas of arbitrary containers or buffers.

The class ara::core::Span provides a non-owning, contiguous view of memory areas and allows efficient encapsulation of arrays or buffers without copy overhead [SWS_CORE_01942]. Applications typically use the class for passing data windows and for creating subviews by means of slicing operations. Callers must strictly ensure that the lifetime of the underlying memory outlasts that of the view and that valid bounds are observed during operations such as subspan(), since out-of-bounds violations trigger undefined behavior [SWS_CORE_01966].

Context

The class ara::core::Span represents a standard-compliant implementation of a contiguous sequence view based on std::span from [views.span]. As a lightweight abstraction, it encapsulates a pointer to the first element and the number of available elements without owning the data itself. It serves as a uniform interface between components that provide data and algorithms that process this data.

The primary interaction partners include:

  • Calling application logic: Uses the view for read or write accesses to sequential memory areas without memory allocations or copy overhead.
  • Memory sources and containers: Arbitrary contiguous memory areas such as native C arrays [SWS_CORE_01944], standardized platform containers such as ara::core::Array [SWS_CORE_01945] [SWS_CORE_01946], generic container structures [SWS_CORE_01947] [SWS_CORE_01948], or raw buffers with pointer and length specification [SWS_CORE_01942].
  • Subviews (subspans): Further instances of ara::core::Span that result from decomposing a parent view [SWS_CORE_01965] [SWS_CORE_01966].

Context diagram: Integration of ara::core::Span as a non-owning view between application logic and memory buffers. Sources: [SWS_CORE_01942], [SWS_CORE_01945], [SWS_CORE_01951]

Lifecycle

Instances of ara::core::Span are designed as pure value objects without their own resource management. Creation is performed either as an empty span via the default constructor [SWS_CORE_01941], by directly specifying start address and element count [SWS_CORE_01942], or via a pointer range consisting of begin and end [SWS_CORE_01943]. In addition, typed constructors for C arrays [SWS_CORE_01944], containers of type ara::core::Array [SWS_CORE_01945] [SWS_CORE_01946], and generic containers [SWS_CORE_01947] [SWS_CORE_01948] are available. Existing spans can be duplicated via the default copy constructor [SWS_CORE_01949] or via converting constructors with compatible element types and extents [SWS_CORE_01950].

Since ara::core::Span assumes no ownership whatsoever of the referenced data, the destructor has the default implementation and is specified as noexcept=default [SWS_CORE_01951]. This leads to the fundamental invariant (Interpretation: Assumption 1) that the lifetime of the underlying memory buffer must always at least span the lifetime of all span objects referencing it; if the buffer is destroyed, remaining spans become invalid. Assignment via the assignment operator occurs trivially via shallow copy [SWS_CORE_01952]. Since all access functions are declared as noexcept and have no internal synchronization mechanisms, concurrent read access to the same span instance from multiple threads is likely safe provided that the underlying memory area is not modified concurrently (Interpretation: Assumption 2).

Usage Path

A typical use case comprises encapsulating an existing data block, checking dimensions, extracting relevant sections, and accessing the elements:

  1. View creation: The application instantiates ara::core::Span on a contiguous buffer, for instance from an instance of ara::core::Array [SWS_CORE_01945] or via raw data pointers with length specification [SWS_CORE_01942].
  2. State and dimension checking: Before further processing, the sizing is verified via empty() [SWS_CORE_01969], size() [SWS_CORE_01967], or size_bytes() [SWS_CORE_01968], or the base address is queried using data() [SWS_CORE_01971].
  3. Slicing / subspan formation: To focus on relevant data windows, the application creates subviews via prefixes with first() [SWS_CORE_01961] [SWS_CORE_01962], suffixes with last() [SWS_CORE_01963] [SWS_CORE_01964], or arbitrary sub-ranges using subspan() [SWS_CORE_01965] [SWS_CORE_01966].
  4. Element processing: Actual data access is performed randomly via the subscript operator operator[] [SWS_CORE_01970], boundary element accesses via front() [SWS_CORE_01959] and back() [SWS_CORE_01960], or sequentially via iterators from begin() to end() [SWS_CORE_01972] [SWS_CORE_01973].

Sequence diagram: Typical call sequence for creating, sub-slicing, and querying elements of a view. Sources: [SWS_CORE_01942], [SWS_CORE_01966], [SWS_CORE_01970]

Error Scenarios

All methods of ara::core::Span are declared as exception-safe and noexcept; neither are C++ exceptions thrown nor error objects such as ara::core::ErrorCode returned. Error states result primarily from violations of preconditions, which lead directly to undefined behavior (Undefined Behavior):

  • Size exceeded for prefixes and suffixes: If a count is requested in first() that exceeds the current size (Count > size() or count > size(), respectively), the behavior is undefined [SWS_CORE_01961] [SWS_CORE_01962]. The identical precondition violation also leads to undefined behavior in last() [SWS_CORE_01963] [SWS_CORE_01964].
  • Invalid sub-range parameters in subspan: Calling subspan() mandatorily requires that offset <= size() holds and, with explicitly specified count (not equal to dynamic_extent), that count <= size() - offset is also observed. Non-compliance leads to undefined behavior [SWS_CORE_01966].
  • Out of bounds on element access: The subscript operator operator[] [SWS_CORE_01970] as well as the access functions front() [SWS_CORE_01959] and back() [SWS_CORE_01960] perform no bounds checking. Access outside valid bounds is likely to lead directly to undefined memory accesses (Interpretation: Assumption 3).
