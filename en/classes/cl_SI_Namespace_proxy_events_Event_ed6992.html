Context

The generated C++ class <SI-Namespace>::proxy::events::<Event> represents the receive-side interface for a specific service event within a service proxy in AUTOSAR Adaptive (AUTOSAR_AP_EXP_ARAComAPI p. 10). Its primary responsibility consists in managing the event subscription, registering notification callbacks, and providing type-safe access to incoming event data via the type alias SampleType [SWS_CM_11401].

The class primarily interacts with three parties:

  • Application software: Initiates the subscription via methods such as Subscribe [SWS_CM_00141] and Unsubscribe [SWS_CM_00151], sets callbacks, and processes received data samples using functors in GetNewSamples [SWS_CM_00701].
  • Communication Management (runtime environment): Monitors the connection and subscription status, receives the serialized event data, and triggers the registered EventReceiveHandler upon data arrival [SWS_CM_00181].
  • Execution context (ExecutorT): Optionally allows passing a user-defined execution context so that notifications, state transitions, and error handlers are processed specifically in dedicated threads or worker queues [SWS_CM_11354], [SWS_CM_11356], [SWS_CM_00100].
  • End-to-End protection (E2E): Enables monitoring of transport errors via SetTransportFaultConditionHandler [SWS_CM_00099] as well as querying the E2E state after evaluating received samples [SWS_CM_11554].

Lifecycle

An instance of <SI-Namespace>::proxy::events::<Event> is instantiated as part of the parent service proxy and shares its lifetime; ownership thus lies with the proxy object. The functional lifecycle is largely determined by the internal state of the subscription (SubscriptionState), which can be queried at any time via GetSubscriptionState [SWS_CM_00316].

Initially, the event is in the state of no subscription. Calling Subscribe(maxSampleCount) [SWS_CM_00141] initiates the transition: depending on the communication state, the instance changes to the state kSubscriptionPending or directly to kSubscribed [SWS_CM_00141]. State changes are reported to the callback registered via SetSubscriptionStateChangeHandler [SWS_CM_00333] or [SWS_CM_11354], respectively. If Subscribe is called again with the same buffer value, the call has no effect [SWS_CM_00141].

Termination takes place via Unsubscribe [SWS_CM_00151], whereby the event returns to the unsubscribed state. If the event was not subscribed, the call has no effect [SWS_CM_00151]. To release resources, registered handlers can be explicitly removed via UnsetSubscriptionStateChangeHandler [SWS_CM_00334], UnsetReceiveHandler [SWS_CM_00183], and UnsetTransportFaultConditionHandler [SWS_CM_00105]. All API methods are declared as noexcept.

State diagram: Lifecycle of the event subscription with states and transitions. Sources: [SWS_CM_00141], [SWS_CM_00151], [SWS_CM_00316], [SWS_CM_00333].

Usage Path

A typical usage path for event-driven processing of data samples is divided into the following steps:

  1. Configure handler: The application first registers a receive handler via SetReceiveHandler [SWS_CM_00181] or in conjunction with an execution context via SetReceiveHandler(handler, executor) [SWS_CM_11356]. Optionally, handlers for state changes [SWS_CM_00333] or E2E transport errors [SWS_CM_00099] can be set.
  2. Activate subscription: Via Subscribe(maxSampleCount) [SWS_CM_00141], the application informs the middleware of the maximum number of samples that may be held simultaneously in the local cache.
  3. Notification and data retrieval: As soon as new data is available, Communication Management triggers the registered handler [SWS_CM_00181]. Inside it, the application calls GetNewSamples [SWS_CM_00701]. A passed callable functor receives each new data item as a typed pointer ara::com::SamplePtr<SampleType const>. The return value provides information about the total number of processed samples.
  4. Check buffer and state: The application can query free cache slots via GetFreeSampleCount [SWS_CM_00705] and, after GetNewSamples, evaluate the result of the E2E check with GetE2EStateMachineState [SWS_CM_11554].
  5. Deactivation: After processing is complete, the application deregisters the handlers ([SWS_CM_00183], [SWS_CM_00334], [SWS_CM_00105]) and cancels the subscription with Unsubscribe [SWS_CM_00151].

Sequence diagram: Call sequence during handler registration, event subscription, and sample processing. Sources: [SWS_CM_00141], [SWS_CM_00181], [SWS_CM_00701], [SWS_CM_00151].

Error Scenarios

The interface methods signal error conditions primarily via ara::core::Result as well as via specified API violations:

  • ComErrc::kMaxSamplesExceeded: Returned by GetNewSamples if the application holds more ara::com::SamplePtr instances at the same time than previously guaranteed in Subscribe. No rollback semantics apply here, and subsequent samples may have been dropped [SWS_CM_00701].
  • ComErrc::kMaxSampleCountNotRealizable: Occurs with Subscribe if, during a resubscription, a different maxSampleCount is passed than was agreed for the currently existing subscription [SWS_CM_00141].
  • InsufficientPermissionsViolation: Triggered if grant enforcement denies access to the event subscription upon calling Subscribe [SWS_CM_00141].
  • InvalidHandlerViolation: Occurs if an invalid or empty handler is passed to the registration methods SetReceiveHandler [SWS_CM_00181], [SWS_CM_11356], SetSubscriptionStateChangeHandler [SWS_CM_00333], [SWS_CM_11354], or SetTransportFaultConditionHandler [SWS_CM_00099], [SWS_CM_00100].
  • DanglingSamplesViolation: Signals upon calling Unsubscribe that open samples (dangling samples) still exist in the application context and the preconditions for unsubscribing were violated [SWS_CM_00151].
