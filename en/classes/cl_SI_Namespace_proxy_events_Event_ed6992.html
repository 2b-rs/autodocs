Enables client applications to subscribe to service events and receive typed new data samples.

The interface class <SI-Namespace>::proxy::events::<Event> enables client applications in the AUTOSAR Adaptive Platform to receive service events on the consumer side via the com module. The typical workflow comprises requesting the subscription via Subscribe [SWS_CM_00141], reactive notification via registered handlers, and synchronous sample retrieval using GetNewSamples [SWS_CM_00701]. In doing so, no more sample pointers may be held concurrently than were reserved during subscription, and all references must be released prior to unsubscription via Unsubscribe.

Context

The C++ class <SI-Namespace>::proxy::events::<Event> represents the consumer-side interface for a service event in the com module of the AUTOSAR Adaptive Platform (Release R25-11). Within the service-oriented communication pattern, this generated class serves as the local representative of an event provided by the server skeleton. Client applications use instances of this class to subscribe to event data, receive incoming samples from the communication network, and control their lifecycle on the consumer side AUTOSAR_AP_EXP_ARAComAPI p. 10.

The essential interaction partners of the class are:

  • Application (Subscriber): Initiates the registration of the event subscription via Subscribe [SWS_CM_00141], provides callback routines for data reception as well as status changes, and queries new samples via GetNewSamples [SWS_CM_00701].
  • Communication Management: Coordinates the transmission of event data across the underlying middleware, manages the network status, and executes the registered notification handlers upon arrival of new events or state changes [SWS_CM_00181], [SWS_CM_00333].
  • Execution context (Executor): When using overloaded registration methods, asynchronous handlers are executed within an explicitly passed context ExecutorT [SWS_CM_11354], [SWS_CM_11356], [SWS_CM_00100].

Context diagram: Interaction relationships between application, proxy event, and Communication Management. Sources: [SWS_CM_00141], [SWS_CM_00181], AUTOSAR_AP_EXP_ARAComAPI p. 10

Lifecycle

The instantiation and destruction of <SI-Namespace>::proxy::events::<Event>, as a member of the enclosing proxy class, is presumably tightly bound to the lifetime of the service proxy. After creation, the event is initially in the unsubscribed state. The current subscription status can be queried at any time via GetSubscriptionState, which returns the state as ara::com::SubscriptionState [SWS_CM_00316].

The transition to the active subscription state is initiated via Subscribe, where the maximum number of concurrently available cache slots is specified via maxSampleCount [SWS_CM_00141]. If the event is already in the states kSubscribed or kSubscriptionPending at the time of the call and the passed value matches the current one, the call has no effect [SWS_CM_00141]. Communication Management reports state changes of the subscription via a handler registered by means of SetSubscriptionStateChangeHandler [SWS_CM_00333] or with an execution context via SetSubscriptionStateChangeHandler [SWS_CM_11354]. This registration can be revoked via UnsetSubscriptionStateChangeHandler [SWS_CM_00334] AUTOSAR_AP_EXP_ARAComAPI p. 10.

In addition, the class manages the state of End-to-End protection (E2E). Via GetE2EStateMachineState, the state ara::com::e2e::SMState of the E2E state machine is determined as determined during the most recent internal call to E2E_Check() during GetNewSamples() [SWS_CM_11554]. Faulty transmission conditions can be monitored by handlers set via SetTransportFaultConditionHandler [SWS_CM_00099] or [SWS_CM_00100] and removed via UnsetTransportFaultConditionHandler [SWS_CM_00105].

The subscription is terminated via Unsubscribe [SWS_CM_00151] AUTOSAR_AP_EXP_ARAComAPI p. 10. If the event is not subscribed at this time, the method returns without action [SWS_CM_00151]. All member functions are declared as noexcept and provide full exception safety.

Usage Path

The typical procedure for using the proxy event is divided into the following sequential phases:

  1. Initiate subscription: The application calls Subscribe(maxSampleCount) [SWS_CM_00141] to reserve the buffer size for incoming samples.
  2. Configure notification: Via SetReceiveHandler [SWS_CM_00181] (or with execution context via [SWS_CM_11356]), a parameterless callback is registered that is invoked by Communication Management when new events arrive.
  3. Retrieve and process samples: In the callback, the application calls GetNewSamples [SWS_CM_00701]. A passed callable f with signature void(ara::com::SamplePtr<SampleType const>) processes each sample sequentially. Here, SampleType corresponds to the type-specific payload type of the event [SWS_CM_11401]. The return value provides, as ara::core::Result<std::size_t>, the exact number of samples passed to f [SWS_CM_00701].
  4. Monitor cache: Using GetFreeSampleCount [SWS_CM_00705], the application can check the number of unused slots in the local cache to detect buffer bottlenecks early.
  5. Dereferencing and unsubscription: After data processing is complete, the receive trigger is deactivated with UnsetReceiveHandler [SWS_CM_00183] and the subscription is terminated via Unsubscribe [SWS_CM_00151].

Sequence diagram: Typical sequence of subscription, notification, sample processing, and unsubscription. Sources: [SWS_CM_00141], [SWS_CM_00181], [SWS_CM_00701], [SWS_CM_00151]

Error Scenarios

When using the class, specific error codes and runtime violations can occur that require defensive checks:

  • Configuration error during re-subscription: If Subscribe is called while the event is already subscribed, and the new maxSampleCount differs from the current value, the call fails with error code ComErrc::kMaxSampleCountNotRealizable [SWS_CM_00141]. In case of missing permissions, the system refuses execution with a InsufficientPermissionsViolation [SWS_CM_00141].
  • Exceeding buffer limits: If the application holds more instances of ara::com::SamplePtr than were guaranteed in the previous call to Subscribe, GetNewSamples returns the error code ComErrc::kMaxSamplesExceeded; in this case, data samples may have been dropped [SWS_CM_00701].
  • Invalid handler passed: If an invalid or empty (null) callable object is passed to SetReceiveHandler, SetSubscriptionStateChangeHandler, or SetTransportFaultConditionHandler, a InvalidHandlerViolation is triggered ([SWS_CM_00181], [SWS_CM_11356], [SWS_CM_00333], [SWS_CM_11354], [SWS_CM_00099], [SWS_CM_00100]).
  • Remaining samples upon unsubscription: If not all held ara::com::SamplePtr are released prior to calling Unsubscribe, this results in a DanglingSamplesViolation [SWS_CM_00151].
