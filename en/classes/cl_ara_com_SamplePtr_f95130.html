class ara::com::SamplePtr

[SWS_CM_00306] Upstream: RS_CM_00202, RS_CM_00203, RS_AP_00114, RS_AP_00122, RS_AP_00135, RS_AP_00145

template <typename T> class SamplePtr {...};

Emulates a std::unique_ptr to an event sample.

The ara::com::SamplePtr behaves as a std::unique_ptr as long as the event/ field is subscribed to, or the Proxy it belongs to is not destroyed. The precondition defined in [SWS_CM_00085] and [SWS_CM_00087] must be fulfilled. Otherwise it is considered a violation.

Note: The SamplePtr is always passed with a const SampleType to the callable in GetNewSamples() (see [SWS_CM_00701]). Therefore the sample datatype (typename T) and the SamplePtr operators using the sample datatype (typename T) are implicitly declared as const. This means that the sample data will always be read-only.

Context

The class template ara::com::SamplePtr represents the central access and entry point for read access to received event data (event samples) in the Communication Management of the Adaptive Platform (EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”). According to [SWS_CM_00306], the class semantically emulates an exclusive pointer modeled on std::unique_ptr to a concrete event sample.

In the overall system, ara::com::SamplePtr interacts with three main partners:

  • Application logic (callable): The application provides a callable entity (callable) with the signature void(ara::com::SamplePtr<SampleType const>) (EXP_ARAComAPI §5.3.5 “Event Reception”, EXP_ARAComAPI §5.3.5.3 “GetNewSamples”). The payload is always passed to the callable as const SampleType, which makes the data type and all access operators implicitly read-only ([SWS_CM_00701]).
  • Communication Management (proxy event wrapper): Upon synchronous invocation of GetNewSamples(), the runtime environment deserializes new data into buffer slots and transfers lifetime responsibility for each slot to the application via a SamplePtr instance (EXP_ARAComAPI §5.3.5.3 “GetNewSamples”, EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”).
  • Local cache and middleware buffer: The architecture favors a reference-based approach for 1:N event communication. Instead of copying and duplicating event data in local memory, SamplePtr references the managed buffer area of the middleware directly, enabling efficient zero-copy processing (EXP_ARAComAPI §5.3.5 “Buffer Management”).

In addition to data encapsulation, SamplePtr provides an interface with GetProfileCheckStatus() ([SWS_CM_90420]) to query the end-to-end (E2E) protection status of the received sample.

Lifecycle

The lifecycle of a ara::com::SamplePtr follows strict rules of exclusive ownership (move-only semantics):

  • Creation: An empty pointer can be explicitly created via the default constructor ([SWS_CM_11534]) or via the null pointer constructor ([SWS_CM_11535]). Both constructors are defined as constexpr and noexcept. A valid SamplePtr populated with data is created exclusively by the ara::com implementation and transferred to the application's own callable via ownership transfer during the execution of GetNewSamples() (EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”).
  • Exclusion of copy operations: To preserve the uniqueness of buffer access, the copy constructor ([SWS_CM_11536]) and the copy assignment operator ([SWS_CM_11538]) are explicitly deleted (= delete).
  • Ownership transfer and swapping: Ownership of a buffer slot can be transferred to other SamplePtr instances via move construction ([SWS_CM_11537]) or move assignment ([SWS_CM_11540]). The method Swap() ([SWS_CM_11544]) enables exception-safe swapping of the managed objects of two instances.
  • Release and destruction: As long as the application holds a SamplePtr, the middleware cannot reclaim the occupied memory slot (EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”). The slot is returned to the middleware by calling Reset(nullptr) ([SWS_CM_11545]), assigning nullptr ([SWS_CM_11539]), or upon leaving scope via the destructor ~SamplePtr() ([SWS_CM_11547]).
  • Validity limits: SamplePtr behaves as a valid proxy modeled after std::unique_ptr only as long as the respective event or field is actively subscribed and the associated proxy exists. If these preconditions are violated, continued use is considered a specification violation according to [SWS_CM_00085] and [SWS_CM_00087].

Usage Path

The typical call sequence for receiving and processing event data is divided into the following steps:

  1. Providing the callback: The application passes a callable function f with signature void(ara::com::SamplePtr<SampleType const>) and optionally the parameter maxNumberOfSamples to GetNewSamples() (EXP_ARAComAPI §5.3.5.3 “GetNewSamples”).
  2. Reception and ownership transfer: For each available event, the middleware deserializes the data and calls f. With the handover, exclusive ownership transfers to the user (EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”).
  3. Validity and protection check:
    • The instance is checked for validity. Interpretation: Although the specification in [SWS_CM_11543] describes the return of operator bool() as "TRUE if the stored pointer is null, FALSE otherwise", the conversion operator is presumably used in analogy to standard smart pointers to query the presence of a managed object.
    • Using GetProfileCheckStatus() ([SWS_CM_90420]), the application queries the E2E check status in order to detect corrupted or incomplete samples prior to further processing.
  4. Read access to data: After a successful status check, the application accesses the payload via the dereference operator operator*() ([SWS_CM_11541]), the arrow operator operator->() ([SWS_CM_11542]), or via the raw pointer Get() ([SWS_CM_11546]). Modifying access is precluded by the const typing ([SWS_CM_00701]).
  5. Release or lifetime extension:
    • If the sample is only required within the callback, its lifetime ends automatically upon leaving the scope by calling the destructor ([SWS_CM_11547]), which immediately releases the middleware slot (EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”). Early manual release is possible via Reset(nullptr) ([SWS_CM_11545]).
    • If the sample is to be retained beyond the callback, the application must transfer the SamplePtr into its own data structures via move semantics ([SWS_CM_11537], [SWS_CM_11540]).

Sequence diagram: Processing sequence of an event sample upon calling GetNewSamples(). Sources: [SWS_CM_00701], [SWS_CM_11541], [SWS_CM_11545], [SWS_CM_11547], [SWS_CM_90420], EXP_ARAComAPI §5.3.5.3 “GetNewSamples”, EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”.

Error Scenarios

When using ara::com::SamplePtr, the following error situations and boundary conditions must be observed:

  • Quota violation: Prior to deserialization, the ara::com implementation checks whether the number of SamplePtr instances currently held by the application exceeds the maximum number agreed upon during the previous Subscribe(). If this is the case, GetNewSamples() aborts and returns an error code in ara::core::Result (EXP_ARAComAPI §5.3.5.3 “GetNewSamples”, EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”). Relief only occurs when the application releases held instances via destruction or Reset(nullptr).
  • Violation of proxy and subscription binding: If a SamplePtr continues to be used after the destruction of the associated proxy object or after cancellation of the subscription, the preconditions according to [SWS_CM_00085] and [SWS_CM_00087] are violated, leading to undefined system behavior.
  • Failed E2E check: If the result of GetProfileCheckStatus() ([SWS_CM_90420]) deviates from a successful status, the referenced data must not be interpreted as valid control data. In this case, the application must initiate the release of the pointer.
  • Exception safety: All operations and constructors of class ara::com::SamplePtr have the specification noexcept ([SWS_CM_11534], [SWS_CM_11535], [SWS_CM_11537], [SWS_CM_11539] to [SWS_CM_11547], [SWS_CM_90420]). They do not throw exceptions and provide a complete no-throw guarantee.

<h4>Context</h4>
<p>The class template <code>ara::com::SamplePtr</code> represents the central access and entry point for read access to received event data (event samples) in the Communication Management of the Adaptive Platform (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>). According to <a class="spec-record-ref" data-req="SWS_CM_00306" href="../spec/record.html?id=SWS_CM_00306">[SWS_CM_00306]</a>, the class semantically emulates an exclusive pointer modeled on <code>std::unique_ptr</code> to a concrete event sample.</p>
<p>In the overall system, <code>ara::com::SamplePtr</code> interacts with three main partners:</p>
<ul>
<li><strong>Application logic (callable)</strong>: The application provides a callable entity (callable) with the signature <code>void(ara::com::SamplePtr&lt;SampleType const&gt;)</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=39">EXP_ARAComAPI §5.3.5 “Event Reception”</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=44">EXP_ARAComAPI §5.3.5.3 “GetNewSamples”</a>). The payload is always passed to the callable as <code>const SampleType</code>, which makes the data type and all access operators implicitly read-only (<a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a>).</li>
<li><strong>Communication Management (proxy event wrapper)</strong>: Upon synchronous invocation of <code>GetNewSamples()</code>, the runtime environment deserializes new data into buffer slots and transfers lifetime responsibility for each slot to the application via a <code>SamplePtr</code> instance (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=44">EXP_ARAComAPI §5.3.5.3 “GetNewSamples”</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>).</li>
<li><strong>Local cache and middleware buffer</strong>: The architecture favors a reference-based approach for 1:N event communication. Instead of copying and duplicating event data in local memory, <code>SamplePtr</code> references the managed buffer area of the middleware directly, enabling efficient zero-copy processing (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=50">EXP_ARAComAPI §5.3.5 “Buffer Management”</a>).</li>
</ul>
<p>In addition to data encapsulation, <code>SamplePtr</code> provides an interface with <code>GetProfileCheckStatus()</code> (<a class="spec-record-ref" data-req="SWS_CM_90420" href="../spec/record.html?id=SWS_CM_90420">[SWS_CM_90420]</a>) to query the end-to-end (E2E) protection status of the received sample.</p>

<h4>Lifecycle</h4>
<p>The lifecycle of a <code>ara::com::SamplePtr</code> follows strict rules of exclusive ownership (move-only semantics):</p>
<ul>
<li><strong>Creation</strong>: An empty pointer can be explicitly created via the default constructor (<a class="spec-record-ref" data-req="SWS_CM_11534" href="../spec/record.html?id=SWS_CM_11534">[SWS_CM_11534]</a>) or via the null pointer constructor (<a class="spec-record-ref" data-req="SWS_CM_11535" href="../spec/record.html?id=SWS_CM_11535">[SWS_CM_11535]</a>). Both constructors are defined as <code>constexpr</code> and <code>noexcept</code>. A valid <code>SamplePtr</code> populated with data is created exclusively by the <code>ara::com</code> implementation and transferred to the application's own callable via ownership transfer during the execution of <code>GetNewSamples()</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>).</li>
<li><strong>Exclusion of copy operations</strong>: To preserve the uniqueness of buffer access, the copy constructor (<a class="spec-record-ref" data-req="SWS_CM_11536" href="../spec/record.html?id=SWS_CM_11536">[SWS_CM_11536]</a>) and the copy assignment operator (<a class="spec-record-ref" data-req="SWS_CM_11538" href="../spec/record.html?id=SWS_CM_11538">[SWS_CM_11538]</a>) are explicitly deleted (<code>= delete</code>).</li>
<li><strong>Ownership transfer and swapping</strong>: Ownership of a buffer slot can be transferred to other <code>SamplePtr</code> instances via move construction (<a class="spec-record-ref" data-req="SWS_CM_11537" href="../spec/record.html?id=SWS_CM_11537">[SWS_CM_11537]</a>) or move assignment (<a class="spec-record-ref" data-req="SWS_CM_11540" href="../spec/record.html?id=SWS_CM_11540">[SWS_CM_11540]</a>). The method <code>Swap()</code> (<a class="spec-record-ref" data-req="SWS_CM_11544" href="../spec/record.html?id=SWS_CM_11544">[SWS_CM_11544]</a>) enables exception-safe swapping of the managed objects of two instances.</li>
<li><strong>Release and destruction</strong>: As long as the application holds a <code>SamplePtr</code>, the middleware cannot reclaim the occupied memory slot (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>). The slot is returned to the middleware by calling <code>Reset(nullptr)</code> (<a class="spec-record-ref" data-req="SWS_CM_11545" href="../spec/record.html?id=SWS_CM_11545">[SWS_CM_11545]</a>), assigning <code>nullptr</code> (<a class="spec-record-ref" data-req="SWS_CM_11539" href="../spec/record.html?id=SWS_CM_11539">[SWS_CM_11539]</a>), or upon leaving scope via the destructor <code>~SamplePtr()</code> (<a class="spec-record-ref" data-req="SWS_CM_11547" href="../spec/record.html?id=SWS_CM_11547">[SWS_CM_11547]</a>).</li>
<li><strong>Validity limits</strong>: <code>SamplePtr</code> behaves as a valid proxy modeled after <code>std::unique_ptr</code> only as long as the respective event or field is actively subscribed and the associated proxy exists. If these preconditions are violated, continued use is considered a specification violation according to <a class="spec-record-ref" data-req="SWS_CM_00085" href="../spec/record.html?id=SWS_CM_00085">[SWS_CM_00085]</a> and <a class="spec-record-ref" data-req="SWS_CM_00087" href="../spec/record.html?id=SWS_CM_00087">[SWS_CM_00087]</a>.</li>
</ul>

<h4>Usage Path</h4>
<p>The typical call sequence for receiving and processing event data is divided into the following steps:</p>
<ol>
<li><strong>Providing the callback</strong>: The application passes a callable function <code>f</code> with signature <code>void(ara::com::SamplePtr&lt;SampleType const&gt;)</code> and optionally the parameter <code>maxNumberOfSamples</code> to <code>GetNewSamples()</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=44">EXP_ARAComAPI §5.3.5.3 “GetNewSamples”</a>).</li>
<li><strong>Reception and ownership transfer</strong>: For each available event, the middleware deserializes the data and calls <code>f</code>. With the handover, exclusive ownership transfers to the user (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>).</li>
<li><strong>Validity and protection check</strong>:
<ul>
<li>The instance is checked for validity. Interpretation: Although the specification in <a class="spec-record-ref" data-req="SWS_CM_11543" href="../spec/record.html?id=SWS_CM_11543">[SWS_CM_11543]</a> describes the return of <code>operator bool()</code> as "TRUE if the stored pointer is null, FALSE otherwise", the conversion operator is presumably used in analogy to standard smart pointers to query the presence of a managed object.</li>
<li>Using <code>GetProfileCheckStatus()</code> (<a class="spec-record-ref" data-req="SWS_CM_90420" href="../spec/record.html?id=SWS_CM_90420">[SWS_CM_90420]</a>), the application queries the E2E check status in order to detect corrupted or incomplete samples prior to further processing.</li>
</ul>
</li>
<li><strong>Read access to data</strong>: After a successful status check, the application accesses the payload via the dereference operator <code>operator*()</code> (<a class="spec-record-ref" data-req="SWS_CM_11541" href="../spec/record.html?id=SWS_CM_11541">[SWS_CM_11541]</a>), the arrow operator <code>operator-&gt;()</code> (<a class="spec-record-ref" data-req="SWS_CM_11542" href="../spec/record.html?id=SWS_CM_11542">[SWS_CM_11542]</a>), or via the raw pointer <code>Get()</code> (<a class="spec-record-ref" data-req="SWS_CM_11546" href="../spec/record.html?id=SWS_CM_11546">[SWS_CM_11546]</a>). Modifying access is precluded by the const typing (<a class="spec-record-ref" data-req="SWS_CM_00701" href="../spec/record.html?id=SWS_CM_00701">[SWS_CM_00701]</a>).</li>
<li><strong>Release or lifetime extension</strong>:
<ul>
<li>If the sample is only required within the callback, its lifetime ends automatically upon leaving the scope by calling the destructor (<a class="spec-record-ref" data-req="SWS_CM_11547" href="../spec/record.html?id=SWS_CM_11547">[SWS_CM_11547]</a>), which immediately releases the middleware slot (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>). Early manual release is possible via <code>Reset(nullptr)</code> (<a class="spec-record-ref" data-req="SWS_CM_11545" href="../spec/record.html?id=SWS_CM_11545">[SWS_CM_11545]</a>).</li>

</ul>
</li>

<h4>Error Scenarios</h4>
<p>When using <code>ara::com::SamplePtr</code>, the following error situations and boundary conditions must be observed:</p>
<ul>
<li><strong>Quota violation</strong>: Prior to deserialization, the <code>ara::com</code> implementation checks whether the number of <code>SamplePtr</code> instances currently held by the application exceeds the maximum number agreed upon during the previous <code>Subscribe()</code>. If this is the case, <code>GetNewSamples()</code> aborts and returns an error code in <code>ara::core::Result</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=44">EXP_ARAComAPI §5.3.5.3 “GetNewSamples”</a>, <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_EXP_ARAComAPI&amp;page=45">EXP_ARAComAPI §5.3.5.4 “Event Sample Management via SamplePtrs”</a>). Relief only occurs when the application releases held instances via destruction or <code>Reset(nullptr)</code>.</li>
<li><strong>Violation of proxy and subscription binding</strong>: If a <code>SamplePtr</code> continues to be used after the destruction of the associated proxy object or after cancellation of the subscription, the preconditions according to <a class="spec-record-ref" data-req="SWS_CM_00085" href="../spec/record.html?id=SWS_CM_00085">[SWS_CM_00085]</a> and <a class="spec-record-ref" data-req="SWS_CM_00087" href="../spec/record.html?id=SWS_CM_00087">[SWS_CM_00087]</a> are violated, leading to undefined system behavior.</li>
<li><strong>Failed E2E check</strong>: If the result of <code>GetProfileCheckStatus()</code> (<a class="spec-record-ref" data-req="SWS_CM_90420" href="../spec/record.html?id=SWS_CM_90420">[SWS_CM_90420]</a>) deviates from a successful status, the referenced data must not be interpreted as valid control data. In this case, the application must initiate the release of the pointer.</li>
<li><strong>Exception safety</strong>: All operations and constructors of class <code>ara::com::SamplePtr</code> have the specification <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CM_11534" href="../spec/record.html?id=SWS_CM_11534">[SWS_CM_11534]</a>, <a class="spec-record-ref" data-req="SWS_CM_11535" href="../spec/record.html?id=SWS_CM_11535">[SWS_CM_11535]</a>, <a class="spec-record-ref" data-req="SWS_CM_11537" href="../spec/record.html?id=SWS_CM_11537">[SWS_CM_11537]</a>, <a class="spec-record-ref" data-req="SWS_CM_11539" href="../spec/record.html?id=SWS_CM_11539">[SWS_CM_11539]</a> to <a class="spec-record-ref" data-req="SWS_CM_11547" href="../spec/record.html?id=SWS_CM_11547">[SWS_CM_11547]</a>, <a class="spec-record-ref" data-req="SWS_CM_90420" href="../spec/record.html?id=SWS_CM_90420">[SWS_CM_90420]</a>). They do not throw exceptions and provide a complete no-throw guarantee.</li>
</ul>
