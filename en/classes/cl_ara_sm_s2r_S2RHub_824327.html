Context

The class ara::sm::s2r::S2RHub forms the central mediation and coordination instance for Suspend-to-RAM sequences in the State Management (SM) functional cluster (EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”, SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). To optimize shutdown and startup times of the machine, a transition to the Suspend-to-RAM state can take place instead of a complete system restart (SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). S2RHub is not intended for use by regular Adaptive Applications, but exclusively serves a State Management implementation or a dedicated control application (SMControlApplication) (EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).

The coordination of Suspend-to-RAM can take place either declaratively via the StateMachine approach of State Management or imperatively via the C++ API of S2RHub in a SMControlApplication; both usage types are strictly mutually exclusive ([SWS_SM_00684], SWS StateManagement §7.5.1 “S2R Hub”, SWS StateManagement §7.7.15). Key interaction partners are:

  • SMControlApplication / State Management: Initiates the suspend and resume sequences via the C++ interface of the hub and triggers the suspend of the operating system after confirmation of the preparations ([SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]).
  • S2R Satellites: Instances of ara::sm::s2r::S2RSatellite in processes of Adaptive Applications whose executable is configured as suspendToRamAware (SWS StateManagement §7.5 “Interaction with Suspend-to-RAM Functionality”). They register with the hub via Offer and receive instructions to save persistent data and stop services ([SWS_SM_00701], [SWS_SM_00710], EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).
  • Identity and Access Management (IAM): Authenticates registering satellites and restricts creation of the hub to the process referenced in the deployment model ([SWS_SM_00706], [SWS_SM_00714], [SWS_SM_00715]).
  • Operating system (OS): Is put into the low-power suspend state by the hub ([SWS_SM_81112]).

Context diagram: Embedding of S2RHub and interaction with SMControlApplication, S2RSatelliten, and operating system. Sources: EXP SWArchitecture §9.2.2.1.4, SWS StateManagement §7.5.1, [SWS_SM_81112].

Lifecycle

The creation of a hub instance takes place explicitly via the constructor S2RHub(const ara::core::InstanceSpecifier &instance) ([SWS_SM_81103]). During construction, the hub performs a mandatory IAM check: If the context of the current process does not match the modeling in SuspendToRamHubMapping.process, creation is rejected ([SWS_SM_00706], [SWS_SM_00714]).

The class possesses move semantics and completely prevents copy operations:

  • Copy constructor and copy assignment operator are deleted (=delete) ([SWS_SM_81107], [SWS_SM_81109]).
  • Move constructor and move assignment operator transfer the resources to a new instance and are declared thread-safe (thread-safe) ([SWS_SM_81106], [SWS_SM_81108]).
  • The destructor ~S2RHub() is virtual and specified as not thread-safe (not thread-safe) ([SWS_SM_81105]).

Regarding concurrency, the operative methods (RequestToEnterSuspendMode, RequestToLeaveSuspendMode, EnterSuspendToRamOs) are classified as not thread-safe ([SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]). Callers must therefore ensure that control calls on the same instance occur sequentially or are synchronized externally.

Usage Path

The typical usage sequence comprises the registration phase of the satellites, the coordinated shutdown into the suspend state, and subsequent reactivation:

  1. Initialization and registration: The SMControlApplication instantiates S2RHub ([SWS_SM_81103]). In parallel, the involved satellites register with the hub via ara::sm::s2r::S2RSatellite::Offer and are considered actively registered until an eventual StopOffer ([SWS_SM_00710], [SWS_SM_00713]). The hub verifies the IAM authenticity of each satellite ([SWS_SM_00715]).
  2. Suspend request: To prepare for the suspend operation, the control application calls RequestToEnterSuspendMode(timeout) ([SWS_SM_81110]). The hub sends a message to all actively registered satellites, whereupon they execute their callback EnterSuspendMode ([SWS_SM_00701], [SWS_SM_00711]) and prepare for freezing (saving persistent data, terminating service offers and security activities) (EXP SWArchitecture §9.2.2.1.4 “Interfaces for Suspend-to-Ram Notifications”).
  3. Waiting for readiness: The ara::core::Future<void> returned by RequestToEnterSuspendMode is resolved as soon as all addressed satellites have responded positively, have been deregistered, or have timed out ([SWS_SM_00702], [SWS_SM_81110]).
  4. Initiating OS suspend: After successful return of the future, the application triggers the transition of the operating system into Suspend-to-RAM via EnterSuspendToRamOs() ([SWS_SM_81112]).
  5. Wakeup and normal operation: After the operating system wakes up, the control application calls RequestToLeaveSuspendMode(timeout) ([SWS_SM_81111]). The hub requests all registered satellites to execute their callback LeaveSuspendMode and restore normal functionality ([SWS_SM_00703], [SWS_SM_00707], [SWS_SM_00711]).

Sequence diagram: Typical sequence of the Suspend-to-RAM cycle from preparation through OS suspend to reactivation. Sources: [SWS_SM_00701], [SWS_SM_00702], [SWS_SM_00703], [SWS_SM_00707], [SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112].

Error Scenarios

All constructors and interface methods are declared as noexcept and provide unrestricted exception safety (exception safe) ([SWS_SM_81103], [SWS_SM_81110], [SWS_SM_81111], [SWS_SM_81112]). Error states are signaled via security violations (Violations) or specific error codes in the returned ara::core::Future.

During creation of the object, the following violations can occur ([SWS_SM_81103]):

  • InsufficientPermissionsViolation: The calling process has insufficient permissions or deviates from the modeled SuspendToRamHubMapping.process; in addition, security event SEV_ACCESS_CONTROL_SM_IAM_ACCESS_DENIED is triggered ([SWS_SM_00706]).
  • InstanceSpecifierMappingIntegrityViolation: The passed InstanceSpecifier cannot be resolved in the model or does not reference a PortPrototype element.
  • PortInterfaceMappingViolation: The mapping type does not correspond to the expected type of the port interface.
  • ProcessMappingViolation: A matching InstanceRef exists, but no modeled process matches the current runtime process.
  • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by an existing instance within this process.
  • AraNotInitializedViolation: The Adaptive Platform runtime environment (ara) is not yet initialized at the time of invocation.

During asynchronous suspend and resume requests, the following errors can be reported in the future object:

  • SmErrc::kCommunicationFailed: Communication to the satellites failed on lower transport layers (with rollback semantics) ([SWS_SM_81110], [SWS_SM_81111]).
  • SmErrc::kCommunicationTimeout: At least one satellite did not respond within the specified timeout (with rollback semantics) ([SWS_SM_00707], [SWS_SM_81110], [SWS_SM_81111]).
  • SmErrc::kAtLeastOneRejected: In RequestToEnterSuspendMode, individual satellites entered the suspend state, but at least one satellite rejected the request (no rollback semantics) ([SWS_SM_81110]).
  • SmErrc::kAtLeastOneHadIssuesToLeave: In RequestToLeaveSuspendMode, at least one satellite responded with kRejected, so that not all satellites could properly return to the normal state (no rollback semantics) ([SWS_SM_00707], [SWS_SM_81111]).

This guide is based exclusively on the specifications of AUTOSAR Adaptive Platform Release R25-11.
