Serves to execute diagnostic monitorings and report status to Diagnostic Management.

The class ara::diag::Monitor provides the functional interface for implementing diagnostic monitoring functions and connecting them to Diagnostic Management [SWS_DM_00548]. After binding to a port prototype, the application signals its readiness to receive via Offer() and continuously transmits test results via ReportMonitorAction() [SWS_DM_01088], [SWS_DM_00543]. Monitor instances are neither copyable nor movable, and all operations are specified as not thread-safe [SWS_DM_01685].

Context

The class ara::diag::Monitor represents the standardized C++ interface for realizing diagnostic monitoring functions (monitors) within the Adaptive Platform [SWS_DM_00548]. A monitor is responsible for detecting and reporting fault symptoms in functional software components and transmits their states to the Diagnostic Management (DM) module.

Binding to the AUTOSAR system model is performed via an ara::core::InstanceSpecifier, which must mandatory reference a PortPrototype typed by a DiagnosticMonitorInterface [SWS_DM_00548]. Essentially three components are involved in the overall execution: the application-specific function monitoring (Application), the local interface instance of ara::diag::Monitor, and the platform module Diagnostic Management (DM), which accepts events and requests re-initializations.

Context diagram: Interaction relationships between application software, ara::diag::Monitor, and Diagnostic Management. Sources: [SWS_DM_00548], [SWS_DM_00543], [SWS_DM_01088], [SWS_DM_01089]

Lifecycle

Instantiation of a monitor depends on the debouncing mechanism defined in the model. The Adaptive Platform provides four constructor variants for this purpose:

  • Monitor-internal debouncing with registration of a InitMonitorNotifier callback and a function pointer for querying the Fault Detection Counter (std::function<std::int8_t()> getFaultDetectionCounter) [SWS_DM_00548].
  • Counter-based debouncing by passing parameters of type CounterBased [SWS_DM_00549].
  • Time-based debouncing by passing parameters of type TimeBased [SWS_DM_00550].
  • Direct monitoring without debouncing algorithm [SWS_DM_01972].

Instances of ara::diag::Monitor are firmly bound to their original storage location: copy constructor [SWS_DM_01685] and copy assignment operator [SWS_DM_01683] are deleted (delete). Likewise, move constructor [SWS_DM_01686] and move assignment [SWS_DM_01684] are explicitly deleted.

After creation, the instance is in the Unoffered state. Only through the explicit call of Offer() does the application declare its readiness to receive and process diagnostic callouts such as initMonitor [SWS_DM_01088]. With StopOffer(), the forwarding of diagnostic requests from the DM is deactivated again [SWS_DM_01089]. After calling StopOffer(), resuming operation later by calling Offer() again would presumably be possible. Prior to the final destruction of the monitor object, the application would presumably have to execute StopOffer() to reliably prevent pending notifications.

Regarding concurrency, all member functions of ara::diag::Monitor are specified as not thread-safe [SWS_DM_00548], [SWS_DM_01088], [SWS_DM_00543], [SWS_DM_01089]. If multiple threads of the application software access the same monitor, synchronization is the responsibility of the application. However, all methods are declared as exception-safe (noexcept) [SWS_DM_00548], [SWS_DM_01088], [SWS_DM_00543], [SWS_DM_01089].

State diagram: Lifecycle states and transitions during service offering of ara::diag::Monitor. Sources: [SWS_DM_01088], [SWS_DM_01089]

Usage Path

The regular sequence for monitoring a fault path comprises the following steps:

  1. Instantiation: The application creates the Monitor instance by specifying the InstanceSpecifier, the callback initMonitor, and any required debouncing parameters or the FDC callback [SWS_DM_00548], [SWS_DM_00549].
  2. Service offering: Via Offer(), the monitor registers with the DM as ready to receive [SWS_DM_01088].
  3. Initialization: Diagnostic Management informs the application about pending initialization events via the registered InitMonitorNotifier callback [SWS_DM_01088].
  4. Cyclic/event-based reporting: During operative operation, the application continuously reports the status of the monitoring path via ReportMonitorAction(action) [SWS_DM_00543]. The passed action contains either test results (qualified/unqualified) or commands for debounce control or prestorage. If monitor-internal debouncing was configured, the DM queries the fault detection value via the registered callback if needed [SWS_DM_00548].
  5. Service termination: Prior to shutdown or upon deactivation of the diagnostic function, the application calls StopOffer() to prevent incoming DM messages [SWS_DM_01089].

Sequence diagram: Typical call sequence from initialization via status reporting to deactivation. Sources: [SWS_DM_00548], [SWS_DM_01088], [SWS_DM_00543], [SWS_DM_01089]

Error Scenarios

Error situations manifest themselves in ara::diag::Monitor on two different levels: as an error code via ara::core::Result or as runtime violations of the framework.

The method Offer() returns a ara::core::Result<void>. If the monitor is already in the offered state, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_01088].

Severe configuration or call errors trigger defined violation messages:

  • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the model context of the process or does not reference a PortPrototype [SWS_DM_00548].
  • PortInterfaceMappingViolation: The referenced port is not typed by a DiagnosticMonitorInterface [SWS_DM_00548].
  • ProcessMappingViolation: No matching modeled process exists for the runtime instance [SWS_DM_00548].
  • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by another monitor within the current process [SWS_DM_00548].
  • InvalidDebouncingAlgorithmViolation: The debouncing mechanism selected in the constructor deviates from the debouncing method modeled in the DEXT diagnostic descriptions [SWS_DM_00548], [SWS_DM_00549], [SWS_DM_00550].
  • UnexpectedMonitorActionHandlingViolation: An action value that is not supported for the configured debouncing algorithm is passed to the method ReportMonitorAction() [SWS_DM_00543].

                                  The method ara::diag::Monitor::StopOffer disables the forwarding of requests and messages from Diagnostic Management (DM) to the respective monitor instance ([SWS_DM_01089]). The call is executed synchronously, requires no input parameters, and has no return value ([SWS_DM_01089]). The operation serves as the counterpart to Offer and allows an Adaptive Application to suspend active monitoring if the associated system part does not need to be monitored temporarily (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”). Although the identifier is oriented toward the interfaces from ara::com, the specification explicitly emphasizes that it is an independent implementation of ara::diag::Monitor (AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”).

As a key constraint, StopOffer is classified as not thread-safe ([SWS_DM_01089]). Interpretation: In the case of concurrent accesses to the same monitor object, the caller is likely responsible for suitable synchronization itself.
