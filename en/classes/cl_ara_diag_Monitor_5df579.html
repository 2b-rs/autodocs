Monitor as a reporting point for an event

Monitor connects the error logic of an application with the diagnostic event management. It is offered for a configured diagnostic monitor and reports the information relevant to the error path to [SWS_DM_00543] via ReportMonitorAction. The DM processes this message in the context of the associated event; The interface therefore neither replaces the event configuration nor its own DTC management.

Evaluation limits

EnableConditions can allow or disable monitor processing. Debounce can be done within the counter, time or monitor; Only the result is included in the event status processing SWS Diagnostics §7.3.4.1.4 “EnableConditions” SWS Diagnostics §7.3.4.1.5 “Debouncing”. A monitoring action should therefore report the technical test finding, not a self-invented copy of the DTC status bits.

State-oriented view of monitor processing: EnableConditions control evaluation, the result passes through configured debouncing, and is processed as an event status. Sources: SWS Diagnostics §7.3.4.1.2 “Monitors”, SWS Diagnostics §7.3.4.1.4 “EnableConditions”, SWS Diagnostics §7.3.4.1.5 “Debouncing”. Partial interpretation: The states consolidate the specified sequence into a developer view.

Life cycle and concurrency

The application creates the interface based on its instance-specific monitor mapping and exposes it with Offer. Calls from the application to the DM can be cached if the DM is not yet available, unless the contract provides for kServiceNotAvailable SWS Diagnostics §7.3.1 “Interaction between DM and applications”. The API is not thread-safe by reference: multiple audit trails must serialize the call to ReportMonitorAction before entering this instance.

function ReportMonitorAction [SWS_DM_00543] Upstream: RS_Diag_04179, RS_AP_00139, RS_AP_00119

void ReportMonitorAction (MonitorAction action) noexcept;

Function to report the status information being relevant for error monitoring paths.

Usage AI generated

Automatically generated usage notice derived from the referenced AUTOSAR R25-11 documents — not official AUTOSAR text.

When to report?

ReportMonitorAction reports the technical test results of a configured monitor to the DM [SWS_DM_00543]. The method is the transition from the application to configured debounce and event processing, not the place to set DTC status bytes yourself.

Proceed
  1. Only execute the audit trail if its EnableConditions are technically valid.
  2. Select the appropriate MonitorAction for the determined finding.
  3. Send the message serially to this monitor instance and only report the next finding after your own synchronization.
Don't anticipate the episode

Debounce and event status processing are handled by the DM SWS Diagnostics §7.3.4.1.5 “Debouncing” SWS Diagnostics §7.3.4.1.6 “Event Status processing”. A call therefore does not necessarily mean that a DTC is immediately saved or a status bit becomes visible.

Supplementary, already linked specification evidence for this API: [SWS_DM_00543].
