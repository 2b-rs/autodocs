Serves as a generic UDS interface for the asynchronous processing of incoming diagnostic requests in the Diagnostic Manager.

As a generic UDS service handler, the ara::diag::GenericUDSService class enables receiving and processing arbitrary UDS diagnostic requests via the AUTOSAR Diagnostic Manager [SWS_DM_00616]. After binding to a port prototype, the service is activated via Offer(), processes requests asynchronously in the HandleMessage() method, and is deregistered again with StopOffer() [SWS_DM_00618], [SWS_DM_00619], [SWS_DM_00620]. The instance is neither copyable nor movable and signals errors via NRCs from DiagUdsNrcErrc [SWS_DM_01657], [SWS_DM_00618].

Context

The ara::diag::GenericUDSService class provides a generic service interface for diagnostic communication according to UDS (Unified Diagnostic Services). It serves as a base class for applications that want to implement and process custom UDS services or UDS services not covered by dedicated interfaces. Interaction essentially takes place between the diagnosing application component, the AUTOSAR Diagnostic Manager (DM), and the underlying modeling context. Connecting to the Diagnostic Manager and the platform model takes place during instantiation via an ara::core::InstanceSpecifier that references a corresponding port prototype of an DiagnosticGenericUdsInterface [SWS_DM_00616]. As soon as registration via the interface is activated, the Diagnostic Manager forwards incoming UDS requests to the implemented instance [SWS_DM_00619].

Context diagram: Component and interaction context of ara::diag::GenericUDSService with DM and application. Sources: [SWS_DM_00616], [SWS_DM_00618], [SWS_DM_00619]

Lifecycle

An instance of ara::diag::GenericUDSService is bound to a fixed port prototype and designed as a single instance: copy constructor [SWS_DM_01657], move constructor [SWS_DM_01658], as well as assignment operators [SWS_DM_01655], [SWS_DM_01656] are deleted (delete). Creation takes place explicitly via the constructor specifying an InstanceSpecifier and the concurrency configuration ConcurrencyType (kConcurrent or kNotConcurrent) [SWS_DM_00616]. The lifecycle of service readiness is divided into two main phases:

  • Not offered (Stopped / Initial): After construction or after calling StopOffer(), the DM does not forward any requests to the instance [SWS_DM_00620].
  • Offered: After successfully calling Offer(), the handler is active and processes incoming diagnostic messages [SWS_DM_00619].

Destruction takes place via the virtual destructor ~GenericUDSService() [SWS_DM_00584]. With regard to thread safety, the constructor is specified as thread-safe, whereas Offer(), StopOffer(), and the destructor are not thread-safe and require external synchronization [SWS_DM_00616], [SWS_DM_00619], [SWS_DM_00620], [SWS_DM_00584].

State diagram: Lifecycle and service provisioning states. Sources: [SWS_DM_00616], [SWS_DM_00619], [SWS_DM_00620], [SWS_DM_00584]

Usage Path

The regular flow comprises instantiating the derived service class, enabling the handler, asynchronous request processing, and subsequent deactivation:

  1. Instantiation: The application instantiates the specialized service class with the matching ara::core::InstanceSpecifier and the desired ConcurrencyType [SWS_DM_00616].
  2. Offer service: Calling Offer() signals readiness to accept messages to the Diagnostic Manager [SWS_DM_00619].
  3. Message processing: Incoming UDS requests lead to the DM calling the pure virtual method HandleMessage(). Passed parameters are service identifier (sid), payload (requestData), metadata (metaInfo), and a cancellationHandler [SWS_DM_00618]. The method returns a ara::core::Future<OperationOutput> through which the result or an error is provided asynchronously [SWS_DM_00618]. The handler can check via cancellationHandler.IsCanceled() whether the operation was canceled, or register a notification via cancellationHandler.SetNotifier() [SWS_DM_00618].
  4. Stop service: By means of StopOffer(), the forwarding of requests is stopped before the instance is destroyed [SWS_DM_00620], [SWS_DM_00584].

Sequence diagram: Typical call sequence during registration, message processing, and deregistration. Sources: [SWS_DM_00616], [SWS_DM_00618], [SWS_DM_00619], [SWS_DM_00620]

Error Scenarios

Error situations can occur in various phases and require differentiated handling:

  • Instantiation violations: If mapping the InstanceSpecifier in the model fails, the framework reports defined violations: InstanceSpecifierMappingIntegrityViolation (specifier cannot be resolved in the model or does not reference an PortPrototype), PortInterfaceMappingViolation (port is not referenced via an DiagnosticServiceGenericMapping), ProcessMappingViolation (no matching process modeled), or InstanceSpecifierAlreadyInUseViolation (specifier is already used in the process) [SWS_DM_00616].
  • Duplicate offer call: If Offer() is called even though the service is already actively offered, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered (rollback semantics) [SWS_DM_00619].
  • Diagnostic-related execution errors: If a UDS message cannot be answered positively from a domain perspective in HandleMessage(), the result in the Future must be set with an appropriate Negative Response Code (NRC) according to ISO 14229-1 via DiagUdsNrcErrc [SWS_DM_00618]. In addition, the implementation must react to cancellation signals of the cancellationHandler if the underlying diagnostic conversation was terminated prematurely [SWS_DM_00618].

              The method HandleMessage from ara::diag::GenericUDSService serves for application-specific processing of incoming UDS diagnostic requests [SWS_DM_00618].
              

              use
              

              Diagnostic Management (DM) calls the method for each received diagnostic request message [SWS_DM_00618]. Based on the parameters, the service identifier (sid), the payload (requestData as ara::core::Span<const std::uint8_t>), connection information (metaInfo), and a cancellationHandler are passed. Processing occurs asynchronously via the return of a ara::core::Future<OperationOutput> [SWS_DM_00618]. The payload in requestData remains valid until the associated promise is fulfilled or the operation is canceled. Via cancellationHandler.IsCanceled(), the application can check the cancellation status or register a notification for session cancellations by means of cancellationHandler.SetNotifier() [SWS_DM_00618].
              

              Error handling
              

              If a request cannot be processed successfully, the application signals the error via the returned future by means of an appropriate negative response code (NRC according to ISO 14229-1) via DiagUdsNrcErrc [SWS_DM_00618].
              

              Concurrency and Constraints
              

                

              • Lifetime of metaInfo: The validity of the metaInfo object is strictly limited to the active execution duration of the method call [SWS_DM_01345]. Storing or using it after return from HandleMessage results in undefined behavior.
                • 

              • Reentrancy and Concurrency: The ara::diag::ConcurrencyType defined in the constructor determines whether calls must be thread-safe SWS Diagnostics §7.3.1.2 “Concurrency of ara::diag interfaces”. In the case of kConcurrent, the DM may call subsequent requests in parallel; in the case of kNotConcurrent, the DM waits until the result of the ongoing request has been provided.

                  use

The synchronous call has no parameters, is non-blocking, and returns a ara::core::Result<void> [SWS_DM_00619]. Execution would typically (Interpretation:) take place during the initialization and startup phase of the Adaptive Application, before diagnostic messages need to be processed over the network. Question Q-c1e385a434fe1e4e (open)
                  


                  Error Handling and Concurrency
                  

                  The function is declared with noexcept and guarantees exception safety [SWS_DM_00619]. If the service was already previously offered, the registration fails and returns the error code DiagOfferErrc::kAlreadyOffered with rollback semantics [SWS_DM_00619]. Regarding thread safety, the interface is specified as not thread-safe [SWS_DM_00619]; concurrent calls on the same instance must be synchronized by the calling application.
                  


                  Interaction
                  

                  Offering via Offer corresponds to the standardized registration pattern in the AUTOSAR Adaptive diagnostic subsystem, as specified similarly for routines ([SWS_DM_00557]) or data identifiers ([SWS_DM_00638]). Although the nomenclature is based on ara::com, it is a diagnostics-specific method of the Diagnostic Manager AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.2 “Monitors”.
