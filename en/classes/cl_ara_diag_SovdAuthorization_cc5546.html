Enables applications to validate SOVD tokens and to provide authorization and token URLs.

The class ara::diag::SovdAuthorization serves applications for implementing SOVD authorization interfaces toward the Diagnostic Server ([SWS_DM_01490]). It provides methods for determining redirect URLs for authorization and token endpoints as well as for checking access tokens ([SWS_DM_01483]). Message reception must be explicitly enabled with Offer() after instantiation, and the passed authentication object must no longer be used after the validation result has been provided.

Context

The class ara::diag::SovdAuthorization provides the adaptive application interface to provide authorization and authentication mechanisms for Service-Oriented Vehicle Diagnostics (SOVD) ([SWS_DM_01490]). Within the diagnostics architecture, it mediates between the Diagnostic Server of Diagnostic Management (DM) and the individual authorization logic of the vehicle application (SWS Diagnostics §7.3.3.2 “SOVD Request Validation and Verification”). When an external SOVD client queries endpoints for client verification or for retrieving tokens, the Diagnostic Server forwards these requests to the application to determine the destination URLs ([SWS_DM_01471], [SWS_DM_01472]). For incoming diagnostic requests with an HTTP authorization header, the class checks the validity of the token and defines assigned access roles ([SWS_DM_01470]). The actual validation against an authorization server (such as OAuth 2.0) is likely to occur as an application-specific interpretation via external network protocols, since AUTOSAR standardizes the local application handoff point here.

Context diagram: Interplay between SOVD client, Diagnostic Server (DM), SovdAuthorization, and external authorization service. Sources: [SWS_DM_01470], [SWS_DM_01471], [SWS_DM_01472], SWS Diagnostics §7.3.3.2.1 “SOVD – Authorization”

Lifecycle

The instantiation of ara::diag::SovdAuthorization occurs explicitly via the constructor specifying an ara::core::InstanceSpecifier as well as the concurrency mode ConcurrencyType ([SWS_DM_01489]). In the manifest, the InstanceSpecifier must reference a valid PortPrototype of an DiagnosticSovdAuthorizationInterface. Via the ConcurrencyType (kConcurrent or kNotConcurrent), it is determined whether the implemented callback methods of the application must be designed to be thread-safe ([SWS_DM_01483], [SWS_DM_01484], [SWS_DM_01485]).

After construction, the Diagnostic Server does not forward requests until the application has successfully called the method Offer() ([SWS_DM_01487]). Interpretation: Requests arriving before the Offer() are presumably discarded by the server or rejected with an error. To stop the forwarding of requests, the application calls StopOffer() ([SWS_DM_01486]). Finally, the object is released via the virtual destructor ([SWS_DM_01488]). The administrative calls SovdAuthorization, Offer, StopOffer and the destructor are not thread-safe.

Usage Path

During ongoing operation, two main interaction paths occur: the provisioning of redirect URLs and the validation of active session tokens. If an SOVD client sends a query for client verification or for requesting a token, the DM calls GetAuthorizationUrl() ([SWS_DM_01485]) or GetTokenUrl() ([SWS_DM_01484]), respectively. The application evaluates the passed queryParameters as well as the metaInfo and returns the destination URL asynchronously as ara::core::Future<ara::core::String>, whereupon the DM responds with an HTTP 307 (Temporary Redirect) ([SWS_DM_01471], [SWS_DM_01472]).

If a subsequent SOVD request contains a new or modified HTTP Authorization header, the Diagnostic Server calls ValidateAuthorization() ([SWS_DM_01470], [SWS_DM_01483]). The application validates the passed token, assigns the corresponding authorization roles to the referenced object ara::diag::ClientAuthentication ([SWS_DM_01469]), and returns a ValidateAuthorizationOutput via the Future. Important precondition: As soon as the Future is available, the application must no longer use the referenced ClientAuthentication object ([SWS_DM_01483]). The DM uses the return values (validity duration validUntil and identity) to map subsequent requests of the same client without re-validation ([SWS_DM_01781], [SWS_DM_01782]), which is required in particular for SOVD resource locks ([SWS_DM_01783]).

Sequence diagram: Sequence of token validation via ValidateAuthorization and role assignment. Sources: [SWS_DM_01469], [SWS_DM_01470], [SWS_DM_01483], SWS Diagnostics §7.3.3.2.1 “SOVD – Authorization”

Error Scenarios

Errors are mapped via ara::core::Result or within the returned ara::core::Future:

  • Initialization and modeling errors: If instantiation fails, violations are reported, such as InstanceSpecifierMappingIntegrityViolation (invalid model element), PortInterfaceMappingViolation (incorrect interface type), ProcessMappingViolation (missing process reference), or InstanceSpecifierAlreadyInUseViolation ([SWS_DM_01489]).
  • Offer release errors: In the event of an error, Offer() returns DiagOfferErrc::kAlreadyOffered if the service is already active, or DiagOfferErrc::kConfigurationMismatch if the configuration does not match the DEXT data ([SWS_DM_01487]).
  • Errors during token validation: If a token cannot be verified, ValidateAuthorization() returns DiagSovdErrc::kInvalidAccessToken (invalid token) or DiagSovdErrc::kTemporarilyNotAvailable (e.g., if the authentication server is not reachable for online verification) via the future ([SWS_DM_01483]).
  • URL determination: No standardized error codes are defined for GetAuthorizationUrl() and GetTokenUrl() ([SWS_DM_01484], [SWS_DM_01485]).

                      The pure virtual method ValidateAuthorization is called by the diagnostic server when a request from an SOVD client contains an Authorization HTTP header and its token is not yet validly validated [SWS_DM_01470]. The application verifies the transmitted authorization token according to the protocol configured in the system (for example OAuth 2.0 in the context of a Resource Server) and assigns the corresponding roles to the client [SWS_DM_01483].
                      

                      The interface specification comprises the following parameters and returns SWS Diagnostics §8.52.1.1.3.5 “ValidateAuthorization”:
                      

                        

                      • token (ara::core::StringView): The access token transmitted from the HTTP header [SWS_DM_01483].
                        • 

                      • metaInfo (const MetaInfo&): Meta-information of the diagnostic service port [SWS_DM_01483].
                        • 

                      • clientAuthentication (ClientAuthentication&): Object via which the application sets the authenticated roles of the SOVD client [SWS_DM_01483]. After providing the returned Future, the application must no longer use this reference [SWS_DM_01483].
                        • 

                      • Return value: A ara::core::Future<ValidateAuthorizationOutput> [SWS_DM_01483]. Upon successful validation, the structure ValidateAuthorizationOutput [SWS_DM_01927] contains the validity timestamp validUntil [SWS_DM_01820] as well as the client identifier identity [SWS_DM_01819].
                        • 

                      

                      The Diagnostic Server considers assigned roles for requests with an identical token as authenticated until reaching validUntil [SWS_DM_01469] and recognizes the SOVD client again based on the token or identity [SWS_DM_01781] [SWS_DM_01782]. This recognition is required, among other things, for temporary operations and SOVD locks, since unauthenticated clients are denied lock access with HTTP 401 [SWS_DM_01783].
                      

                      In the event of an error, the Future is resolved with DiagSovdErrc::kInvalidAccessToken (invalid token) or DiagSovdErrc::kTemporarilyNotAvailable (e.g. authentication server temporarily unreachable) [SWS_DM_01483]. The function is specified as noexcept and exception safe; whether the implementation must be thread-safe is controlled via the ConcurrencyType passed in the constructor [SWS_DM_01483].
