Runtime model of a client dialog

Conversation represents the relationship of a particular diagnostic client to a Diagnostic Server, created dynamically at runtime. The client is identified as a tuple of UDS source address and globalChannelId [SWS_DM_00421]; a server can manage multiple conversations concurrently. The number of offered Conversation instances follows maxConversations, with a default of one without configuration [SWS_DM_00840].

Visible state and parallelism

The interface displays activity, diagnostic session, security level and identifier and can report status changes via a notifier. In default session operation, parallel client requests are possible; If a client switches to a non-default session, its conversation becomes the exclusive UDS context SWS Diagnostics §7.3.2.1.1 “Multiple Client Handling”. Applications should therefore treat state queries as momentary observations and notifiers as a result of changes.

The lifecycle begins with the first UDS request; In a non-default session, the conversation remains until it times out or is aborted. Sources: SWS Diagnostics §7.3.2.1.2 “Life-cycle of a Diagnostic Conversation”, [SWS_DM_00842], [SWS_DM_00843]. Partial interpretation: The representation condenses the end conditions described.

Reset session specifically

ResetToDefaultSession does not request an immediate termination: the DM first ends the current request and then switches to the default session [SWS_DM_00842]. At the end of the conversation, its ActivityStatus is set to kInactive [SWS_DM_00843]. Setting an activity, session or security notifier again overwrites the previous registration; the callback lifetime must therefore follow the ownership of the respective conversation.

Error handling and orderly session termination

Queries on a conversation, such as GetActivityStatus() or GetDiagnosticSession(), return their state as ara::core::Result. If essential Diagnostic Manager functionality is unavailable, the error DiagErrc::kServiceNotAvailable is returned; the calling application handles this path without partial progress or with rollback semantics [SWS_DM_00694], [SWS_DM_00696]. The return value must therefore be checked as a domain error path and must not be used further as a valid state value.

If a conversation ends due to cancellation or timeout, the Diagnostic Manager sets its activity status to kInactive and reports the change through the registered activity notifier [SWS_DM_00843], [SWS_DM_00695]. For application logic, the inactivity callback marks the end of observation; no follow-up requests are derived from this conversation. Registering again replaces the previously configured notifier [SWS_DM_01355].

function SetActivityNotifier [SWS_DM_00695] Upstream: RS_AP_00139, RS_Diag_04169

ara::core::Result< void > SetActivityNotifier (ActivityStatusType Notifier notifier) noexcept;

Register a notifier function which is called if the activity is changed. A consecutive call of this method will overwrite the previous registered notifier.

Usage AI generated

Automatically generated usage notice derived from the referenced AUTOSAR R25-11 documents — not official AUTOSAR text.

Monitor conversation activity

SetActivityNotifier registers a callback for changing the activity of a Conversation [SWS_DM_00695]. The instance represents the dialog of a specific client, not a global diagnostic status.

Treat registration interchangeably

When registering again, the DM overwrites the previous activity notifier [SWS_DM_01355]. Therefore, link the callback to the lifespan of the conversation and do not let multiple components compete for the same registration.

Consider the end

At the end of the conversation, the ActivityStatus is set to kInactive [SWS_DM_00843]. Treat inactive states as completion of the observation and do not derive further requests from the abandoned conversation.

Supplementary, already linked specification evidence for this API: [SWS_DM_00695].
