Manages memory-backed pools for fast allocations in single threads without exceptions.

The class implements an unsynchronized memory pool resource modeled on std::pmr::unsynchronized_pool_resource and manages memory blocks via a configurable upstream resource. It efficiently serves repeated memory requests via internal pools, where unused total memory can be released via the interface if required [SWS_CORE_00065]. Because the allocation paths are not designed to be thread-safe, an instance may only ever be operated within a single execution context without concurrent access [SWS_CORE_00058]. In contrast to standard C++, allocation does not throw exceptions in the event of memory exhaustion, but strictly signals failures by returning a null pointer.

Context

In AUTOSAR Adaptive, the class ara::core::UnsynchronizedPoolResource provides an implementation of std::pmr::unsynchronized_pool_resource according to standard [mem.res.pool] and derives from the base class MemoryResource. Its core task is to process recurring memory requests via internal pools of fixed chunk sizes in order to reduce fragmentation and management overhead compared to direct system allocations. The instance obtains larger memory areas from a higher-level upstream memory resource that is attached as MemoryResource* and can be queried via the method upstream_resource() [SWS_CORE_00056].

The behavior of the internal chunks and pool boundaries is controlled by configuration parameters of type PoolOptions, which can be viewed via options() [SWS_CORE_00057]. In addition, the overridden method do_is_equal() allows a runtime comparison with other memory resources for equality [SWS_CORE_00060]. The class thus operates as an intermediary between the requesting execution context and the underlying upstream resource.

Context diagram: Embedding of UnsynchronizedPoolResource between calling thread and upstream memory resource. Sources: [SWS_CORE_00056], [SWS_CORE_00057], [SWS_CORE_00060]

Lifecycle

Several constructors are available for creating an instance: a parameterless default constructor [SWS_CORE_00063], constructors with explicit passing of an upstream resource [SWS_CORE_00064], configuration options [SWS_CORE_00068], or both combined [SWS_CORE_00067]. Copy operations are completely prevented; both the copy constructor [SWS_CORE_00046] and the copy assignment operator [SWS_CORE_00047] are deleted (delete). In contrast to the ISO 14882 standard, however, AUTOSAR explicitly defines move semantics: move constructor [SWS_CORE_00048] and move assignment operator [SWS_CORE_00049] are available as noexcept=default.

During operation, all memory allocated by the upstream resource can be released via the call to release() without destroying the pool object itself [SWS_CORE_00065]. End of life is sealed by the destructor ~UnsynchronizedPoolResource(), which is declared as noexcept override, but exhibits the significant AUTOSAR deviation of being non-virtual [SWS_CORE_00062].

With regard to concurrency, the class is not synchronized: the protected allocation and deallocation functions do_allocate() [SWS_CORE_00058] and do_deallocate() [SWS_CORE_00059] are explicitly specified as not thread-safe. In contrast, the constructors, inspectors such as upstream_resource() [SWS_CORE_00056] and options() [SWS_CORE_00057], as well as release() [SWS_CORE_00065] and the destructor are classified as thread-safe.

Usage Path

A typical usage path includes instantiation, repeated memory allocations and deallocations, and final cleanup:

  1. Initialization: The caller creates the instance specifying desired PoolOptions and an upstream resource [SWS_CORE_00067].
  2. Allocation: Memory is obtained via the base class interface, which delegates to do_allocate() [SWS_CORE_00058]. Interpretation: If no suitable block is free in the internal pool, new chunk memory is requested from the upstream resource via its regular allocation interface.
  3. Deallocation: Blocks to be released are passed to do_deallocate() and returned to the internal pool for subsequent requests [SWS_CORE_00059].
  4. Resource reset: Prior to reuse or shutdown, release() can be called to return upstream memory blocks collectively [SWS_CORE_00065].
  5. Destruction: The object is regularly destroyed at the end of its scope via its concrete type [SWS_CORE_00062].

Sequence diagram: Typical sequence from allocation through deallocation to memory release. Sources: [SWS_CORE_00058], [SWS_CORE_00059], [SWS_CORE_00065], [SWS_CORE_00067]

Error Scenarios

AUTOSAR defines specific deviations from standard C++ for ara::core::UnsynchronizedPoolResource in order to meet the requirements for deterministic runtime behavior without exceptions:

  • Memory exhaustion during allocation: If a memory request fails in do_allocate(), no std::bad_alloc exception is thrown. The function is declared as noexcept and strictly returns nullptr instead [SWS_CORE_00058]. Callers must therefore consistently check return values for nullptr.
  • Error during deallocation: If deallocation via do_deallocate() fails, the error is silently ignored ("silently ignored") without exceptions being propagated [SWS_CORE_00059].
  • Polymorphic destruction: Since the destructor is explicitly non-virtual in deviation from [mem.res.pool] [SWS_CORE_00062], Interpretation: Destruction via a pointer of the base class MemoryResource* is likely to lead to undefined behavior. Instances must always be destroyed via their derived type.
  • Exception safety during creation: While the constructor with options and upstream resource is considered noexcept [SWS_CORE_00067], the default constructor [SWS_CORE_00063] as well as the constructors [SWS_CORE_00064] and [SWS_CORE_00068] are marked as not exception-safe. Interpretation: The lack of exception safety in these constructors is likely attributable to the fact that advance allocations from the upstream resource can fail during initialization.
