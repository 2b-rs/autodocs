Context

The ara::diag::MultipleMonitor class serves to implement monitor operations via bundled monitor interfaces ([SWS_DM_01695]). It acts as a central mediator between the application-specific diagnostic and functional logic and the diagnostic system (Diagnostic Management, DM). While a simple monitor maps only a single fault monitoring path, MultipleMonitor enables managing and reporting the status of multiple monitors via a shared interface port ([SWS_DM_01695], [SWS_DM_01698]).

The binding to the AUTOSAR model takes place via a port instance (PortPrototype) of type DiagnosticMultipleMonitorInterface ([SWS_DM_01695]). Via this port, the monitoring instance registers and forwards commands as well as feedback, such as debouncing controls and qualification status, to the DM or receives requests from the diagnostic system ([SWS_DM_01698], [SWS_DM_01699]).

Lifecycle

An instance of MultipleMonitor has a strict object identity and is bound to a firmly defined execution context. The constructor requires an ara::core::InstanceSpecifier that addresses the corresponding port in the system model ([SWS_DM_01695]). To prevent side effects and multiple bindings, both the copy constructor and the move constructor (Move) and the associated assignment operators are explicitly deleted ([SWS_DM_02065], [SWS_DM_02066], [SWS_DM_02063], [SWS_DM_02064]). A transfer of the instance between scopes is thus precluded.

After instantiation, the object is in the initialization state: each monitor managed within it must be configured exactly once via one of the overloads of ConfigureMonitor before its first use ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). As soon as the monitors are initialized, a call to Offer() activates the forwarding of requests from Diagnostic Management ([SWS_DM_01699]). The forwarding can be suspended again via StopOffer() ([SWS_DM_01700]). Regarding thread safety, construction is thread-safe ([SWS_DM_01695]), whereas configuration and offering methods (ConfigureMonitor, Offer, StopOffer) are not thread-safe ([SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700]). Reporting via ReportMonitorAction is protected depending on the concurrency model defined in the design or constructor ([SWS_DM_01698]).

State diagram: Lifecycle states of a MultipleMonitor instance from creation through configuration and offering to stopping. Sources: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700].

Usage Path

The regular procedure for using MultipleMonitor is divided into the phases of creation, individual monitor configuration, offering, and ongoing event reporting:

  1. Creation: The application instantiates MultipleMonitor by specifying the InstanceSpecifier ([SWS_DM_01695]).
  2. Monitor configuration: For each monitored event or each monitorHandle, the appropriate debouncing strategy is defined. AUTOSAR provides four dedicated overloads of ConfigureMonitor for this purpose:
    • Monitor-internal debouncing with registration of a callback to determine the Fault Detection Counter (FDC) ([SWS_DM_01696]).
    • Time-based debouncing by passing parameters of type TimeBased ([SWS_DM_01697]).
    • Counter-based debouncing using parameters of type CounterBased ([SWS_DM_01702]).
    • Operation without debouncing, where only the optional InitMonitorNotifier is registered ([SWS_DM_01973]).
    Each overload may be called only exactly once per monitor handle ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]).
  3. Service offering: By calling Offer(), the interface is activated so that the Diagnostic Management daemon can deliver requests to this handler ([SWS_DM_01699]).
  4. Status reporting: During ongoing operation, the application logic transmits test results, debouncing control commands, or pre-storage commands via ReportMonitorAction(monitorHandle, action) ([SWS_DM_01698]).
  5. Deactivation: Prior to shutdown or upon temporary deactivation of diagnostic forwarding, StopOffer() is called ([SWS_DM_01700]).

Sequence diagram: Typical call sequence for configuration, offering, and status reporting of multiple diagnostic monitors. Sources: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01698], [SWS_DM_01699], [SWS_DM_01700].

Error Scenarios

Error situations for MultipleMonitor are signaled partly via standardized platform violations and partly via ara::core::Result with specific error codes:

  • Model and process violations during construction: If the assignment of the InstanceSpecifier fails, documented runtime violations occur ([SWS_DM_01695]):
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the model of the executable or does not refer to a PortPrototype.
    • PortInterfaceMappingViolation: The referenced port is not typed by a DiagnosticMultipleMonitorInterface.
    • ProcessMappingViolation: No matching process context exists at runtime for the modeled process.
    • InstanceSpecifierAlreadyInUseViolation: The identifier is already occupied by another instance in the running process.
  • Configuration errors: In the event of an error, a call to ConfigureMonitor returns DiagErrc::kInvalidArgument ([SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973]). This occurs, for example, if invalid parameters or contradictory debouncing states (e.g. kPreFailed for internal debouncing) are passed.
  • Offering errors: If Offer() is called while the service is already being offered, the operation fails with error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_01699]).
  • Invalid monitor handles during reporting: If an unconfigured or incorrect monitorHandle is passed to ReportMonitorAction, the call does not abort; instead, the call is silently ignored according to the specification ([SWS_DM_01698]).
