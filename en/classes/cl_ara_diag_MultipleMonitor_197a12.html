Bundles and controls diagnostic test results of multiple monitors via a shared adaptive port interface.

The class ara::diag::MultipleMonitor bundles the monitoring operations of multiple diagnostic monitors via a shared port interface in the AUTOSAR system [SWS_DM_01695]. Before reporting test results, each monitor must be configured individually and the overall service must be enabled for Diagnostic Management via Offer [SWS_DM_01696]. Because copy and move operations are completely prohibited, each instance is permanently bound to its creation context. Faulty monitor handles are fault-tolerantly ignored when issuing status reports during ongoing operation.

Context

The class ara::diag::MultipleMonitor is used to implement monitor operations via multiple monitor interfaces within the AUTOSAR Adaptive Platform [SWS_DM_01695]. In contrast to interfaces for single monitors, MultipleMonitor bundles the fault monitoring and status reporting of multiple diagnostic monitors via a shared PortPrototype, which must be typed in the model by a DiagnosticMultipleMonitorInterface [SWS_DM_01695].

The overall system integrates three central interaction partners:

  • Application software: Instantiates the class, configures the individual monitors, and delivers test results as well as debouncing instructions cyclically or event-based [SWS_DM_01695], [SWS_DM_01698].
  • MultipleMonitor: Manages the monitor configurations, accepts action reports, and ensures forwarding to Diagnostic Management [SWS_DM_01696], [SWS_DM_01699].
  • Diagnostic Management (DM): Processes the status information of relevant fault monitoring paths and forwards incoming request messages to the monitor handler after the service has been offered [SWS_DM_01698], [SWS_DM_01699], [SWS_DM_01700].

Context diagram: Embedding of MultipleMonitor between application software and Diagnostic Management. Sources: [SWS_DM_01695], [SWS_DM_01698], [SWS_DM_01699].

Lifecycle

Instantiation of MultipleMonitor occurs synchronously by passing a ara::core::InstanceSpecifier, which establishes the port mapping [SWS_DM_01695]. Regarding ownership, the class is designed as a purely location-bound resource: both the copy constructor [SWS_DM_02065] and the move constructor [SWS_DM_02066] as well as all assignment operators [SWS_DM_02063], [SWS_DM_02064] are explicitly deleted (delete). An instance can therefore neither be copied nor moved.

With regard to service state, the instance is initially inactive after creation. Calling Offer() activates the forwarding of diagnostic requests by the DM [SWS_DM_01699]. With StopOffer(), this forwarding can be selectively disabled again, for instance prior to shutdown or during reconfigurations [SWS_DM_01700].

The concurrency requirements are governed in a differentiated manner: The constructor is declared as thread-safe [SWS_DM_01695]. In contrast, monitor configuration via ConfigureMonitor as well as the service controls Offer and StopOffer are specified as not thread-safe and require externally coordinated calls [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01700]. The thread safety of ReportMonitorAction is conditional: it is defined via the ConcurrencyType stored in the construction context [SWS_DM_01698]. Interpretation: Because the C++ constructor only accepts the InstanceSpecifier, this ConcurrencyType is likely configured via the manifest stored in the model.

Usage Path

The typical usage of MultipleMonitor follows a fixed sequence of phases:

  1. Creation: Creating the object with the configured InstanceSpecifier [SWS_DM_01695].
  2. Configuration: Each assigned monitor must be configured exactly once prior to its use via an overload of ConfigureMonitor [SWS_DM_01696]. Four debouncing types are available for selection:
    • Without debouncing, registering the InitMonitorNotifier [SWS_DM_01973],
    • time-based debouncing with default values of TimeBased [SWS_DM_01697],
    • counter-based debouncing with default values of CounterBased [SWS_DM_01702], or
    • monitor-internal debouncing, passing a function pointer to query the current fault detection counter (FDC) [SWS_DM_01696].
  3. Offer: Calling Offer() to enable Diagnostic Management to forward requests [SWS_DM_01699].
  4. Operation: Ongoing reporting of monitor results or control commands to the DM via ReportMonitorAction, passing the respective monitorHandle and action [SWS_DM_01698].
  5. Termination: Calling StopOffer() to disable the forwarding of request messages [SWS_DM_01700].

Sequence diagram: Phases of the lifecycle and usage cycle of MultipleMonitor. Sources: [SWS_DM_01695], [SWS_DM_01696], [SWS_DM_01699], [SWS_DM_01698], [SWS_DM_01700].

Error Scenarios

The specification defines clear error and exception behaviors for MultipleMonitor:

  • Integration and modeling violations:\nUpon instantiation, the framework verifies model consistency [SWS_DM_01695]:
    • InstanceSpecifierMappingIntegrityViolation: The identifier does not reference a PortPrototype or cannot be resolved in the model.
    • PortInterfaceMappingViolation: The port is not typed by a DiagnosticMultipleMonitorInterface.
    • ProcessMappingViolation: No matching modeled process exists for the executing process.
    • InstanceSpecifierAlreadyInUseViolation: The identifier is already used by another instance in the same process.
  • Configuration errors:\nAll overloads of ConfigureMonitor return an ara::core::Result<void>. For invalid parameters, such as prohibited debouncing values or rollback semantics (e.g. kPreFailed for internal debouncing), the error DiagErrc::kInvalidArgument is returned [SWS_DM_01696], [SWS_DM_01697], [SWS_DM_01702], [SWS_DM_01973].
  • Error during service offering:\nIf Offer() is called when the service is already actively offered, the call fails with the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_01699].
  • Fault tolerance for action reports:\nThe method ReportMonitorAction returns no error code (return type void). If called with an invalid or unknown monitorHandle, the call is silently ignored according to the specification [SWS_DM_01698].

use

The method ara::diag::MultipleMonitor::ConfigureMonitor initializes a diagnostic monitor for monitor-internal debouncing [SWS_DM_01696]. Via parameter monitorHandle, the monitor to be configured is addressed, while initMonitor registers a notifier callback for re-initializations and getFaultDetectionCounter registers a function to retrieve the current fault detection counter (FDC) [SWS_DM_01696]. Execution is synchronous and returns a ara::core::Result<void> AUTOSAR_AP_SWS_Diagnostics §8.44.2.1.3.4 “ConfigureMonitor”.

Error Handling and Concurrency

In case of error, the error result DiagErrc::kInvalidArgument is returned [SWS_DM_01696]. This is likely to occur in particular if invalid function pointers are passed or incompatible states exist in internal debouncing (interpretation). The operation is specified as noexcept as well as exception safe, but explicitly marked as not thread-safe [SWS_DM_01696]. Invocations on the same monitor instance must therefore be synchronized on the application side.

Sequence and Interaction

Each overload of ConfigureMonitor may only be called exactly once for a monitor; the monitor is ready for use only after this initialization step [SWS_DM_01696]. In monitor-internal debouncing, the diagnostic monitor application processes the debouncing logic autonomously and only transmits final results to the Diagnostic Management AUTOSAR_AP_SWS_Diagnostics §7.3.4.1.5.3 “Monitor-internal debouncing”. For other debouncing mechanisms, alternative overloads are available for time-based [SWS_DM_01697], counter-based [SWS_DM_01702], or unbounced monitors [SWS_DM_01973].
