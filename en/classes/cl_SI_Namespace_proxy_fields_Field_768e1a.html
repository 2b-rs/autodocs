Context

The C++ class <SI-Namespace>::proxy::fields::<Field> represents the client-side representation of a field declared in a service interface. In the AUTOSAR Adaptive Platform, a field combines properties of a queryable state value, a modifiable state value, and an event stream for notification of value changes.

The class interacts primarily with the calling application logic and the underlying Communication Management. Depending on the modeling in the service interface, the class provides different interface elements:

  • Getter: If Field.hasGetter == TRUE is configured in the interface, the method Get() exists for asynchronous value querying ([SWS_CM_00112]; AUTOSAR_AP_EXP_ARAComAPI p. 10).
  • Setter: If Field.hasSetter == TRUE is defined, the class provides the method Set() for changing the value ([SWS_CM_00113]; AUTOSAR_AP_EXP_ARAComAPI p. 10).
  • Notifier: Incoming notifications about changed field values are provided in the local data cache via subscription-based reception mechanisms ([SWS_CM_11601], [SWS_CM_11610]).

In addition, the class provides monitoring functions for End-to-End protection (E2E): The state of the E2E state machine can be retrieved separately for the getter ([SWS_CM_00145]), the setter ([SWS_CM_00146]), and the notifier ([SWS_CM_11612]).

Lifecycle

The lifetime of an instance of <SI-Namespace>::proxy::fields::<Field> is presumably bound to the lifetime of the parent service proxy instance that aggregates the field.

An explicit subscription lifecycle exists for the notifier functionality. The states include kNotSubscribed, kSubscriptionPending, and kSubscribed. Calling Subscribe() requests the subscription, specifying the buffer size maxSampleCount ([SWS_CM_11601]). If the field is already in states kSubscribed or kSubscriptionPending with an unchanged quota upon this call, the call has no effect ([SWS_CM_11601]).

The current subscription state can be queried using GetSubscriptionState() ([SWS_CM_11604]). State transitions can be monitored by registering a handler via SetSubscriptionStateChangeHandler() ([SWS_CM_00106], [SWS_CM_11607]), optionally also with a custom executor ([SWS_CM_11608]). The handler can be removed again via UnsetSubscriptionStateChangeHandler() ([SWS_CM_11609]).

Notifications are terminated by Unsubscribe() ([SWS_CM_11602]). If the field is not subscribed at the time of the call, the method returns without action ([SWS_CM_11602]). For transport errors on the notifier channel, a transport fault handler can also be registered ([SWS_CM_00109], [SWS_CM_00110]) and deregistered again ([SWS_CM_00126]).

Usage Path

Typical interaction with the field comprises two separate communication paths:

  1. Subscription and sample processing:
    • The application reserves buffer slots for updates using Subscribe(maxSampleCount) ([SWS_CM_11601]).
    • Via SetReceiveHandler(), a callback is registered that is triggered upon arrival of new field data ([SWS_CM_11605], optionally with an executor according to [SWS_CM_11611]).
    • In the handler, the application calls GetNewSamples(f, maxNumberOfSamples) to process the new values in the local cache ([SWS_CM_11610]). The number of remaining free cache slots can be queried with GetFreeSampleCount() ([SWS_CM_11603]).
    • Finally, the handler is deregistered via UnsetReceiveHandler() ([SWS_CM_11606]) and the subscription is terminated via Unsubscribe() ([SWS_CM_11602]).
  2. Direct value query and modification:
    • Using Get(), the application requests the current value and receives a ara::core::Future<FieldType> ([SWS_CM_00112]; type alias FieldType according to [SWS_CM_11403]).
    • Using Set(value), a new value is transmitted to the service skeleton, which is also synchronized via a ara::core::Future<FieldType> ([SWS_CM_00113]).

Sequence diagram: Typical sequence of subscription, notifier reception, and get and set calls. Sources: [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601], [SWS_CM_11605], [SWS_CM_11610], [SWS_CM_11602].

Error Scenarios

The methods of the class ensure their functionality via error codes, exceptions, and access restrictions:

  • Communication errors (ComErrc::kCommunicationFailure): Reported by the network binding in case of transmission errors or disruptions of secure communication. For Get(), rollback semantics apply ([SWS_CM_00112]). For Set(), no rollback semantics exist because, in the case of a communication timeout, the remote state on the server side may remain uncertain ([SWS_CM_00113]).
  • Minimum send interval violation (ComErrc::kMinimumSendIntervalViolationError): Occurs for Get() ([SWS_CM_00112]) and Set() ([SWS_CM_00113]) if transmission requests are triggered faster than the configured minimum send interval (minimumSendInterval) allows.
  • Buffer limits (ComErrc::kMaxSampleCountNotRealizable and ComErrc::kMaxSamplesExceeded): Subscribe() fails if the requested sample count cannot be provided by the system ([SWS_CM_11601]). GetNewSamples() reports an error if the maximum sample count is exceeded ([SWS_CM_11610]).
  • Security violations (InsufficientPermissionsViolation): Triggered by grant enforcement if the client does not have sufficient permissions to execute Get() ([SWS_CM_00112]), Set() ([SWS_CM_00113]), or Subscribe() ([SWS_CM_11601]).
  • Invalid callback handlers (InvalidHandlerViolation): Thrown if an empty or invalid callable is passed during registration via SetReceiveHandler() ([SWS_CM_11605], [SWS_CM_11611]), SetSubscriptionStateChangeHandler() ([SWS_CM_11607], [SWS_CM_11608]), or SetTransportFaultConditionHandler() ([SWS_CM_00109], [SWS_CM_00110]).
