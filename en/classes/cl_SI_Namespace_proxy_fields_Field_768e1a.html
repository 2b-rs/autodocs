Enables client applications to asynchronously query, modify, and monitor a subscribed service field.

The class serves as a client-side interface for accessing a field defined in the ServiceInterface and bundles getter, setter, and notification functions. Via [SWS_CM_00112] and [SWS_CM_00113], values can be queried and modified asynchronously, provided the corresponding operations are modeled. For field updates, a subscription-based caching mechanism is used that buffers notifications and forwards them via callback handlers. Essential constraints include observing minimum send intervals and the absence of rollback semantics for write accesses.

Context

In the communication management of the AUTOSAR Adaptive Platform (ara::com), the class <SI-Namespace>::proxy::fields::<Field> represents an individual field modeled in the service interface on the client or proxy side. The class bundles access to attribute values and combines three functional roles: querying the current value (getter), modifying the value (setter), and receiving asynchronous value changes (notifier) (AUTOSAR_AP_EXP_ARAComAPI p. 10). It acts as an interface between the client application and the underlying communication layer (network binding).

Which operations are available on the instance is determined by the definition of the service interface: The method Get() is only generated if Field.hasGetter == TRUE is configured [SWS_CM_00112]. The method Set() is exclusively available if Field.hasSetter == TRUE holds [SWS_CM_00113]. The concrete data type of the field is mapped type-safely via the provided type alias FieldType [SWS_CM_11403].

Lifecycle

The field objects are instantiated as members of the parent proxy class. Their lifetime is therefore presumably bound directly to the lifecycle of the corresponding proxy instance. For the event-based notifier mechanism, the instance goes through a clearly regulated subscription lifecycle:

  • Not subscribed: Initially, the field is in the kNotSubscribed state.
  • Subscription requested: Through the synchronous call to Subscribe(maxSampleCount) [SWS_CM_11601], the buffer is set up and registration is started. The notifier transitions to kSubscriptionPending or, upon confirmation by the communication layer, to kSubscribed, with this state transition presumably being executed asynchronously.
  • Subscription ended: Through Unsubscribe() [SWS_CM_11602], the notification stream is stopped and the state transitions back to kNotSubscribed.

The current state can be queried synchronously at any time with GetSubscriptionState() [SWS_CM_11604]. To be notified of state changes asynchronously, a callback can be registered with SetSubscriptionStateChangeHandler() [SWS_CM_11607], optionally with a dedicated execution context [SWS_CM_11608]. Before destroying the instance or upon deactivation, registered callbacks should be explicitly removed via UnsetReceiveHandler() [SWS_CM_11606], UnsetSubscriptionStateChangeHandler() [SWS_CM_11609], and UnsetTransportFaultConditionHandler() [SWS_CM_00126].

State diagram: Lifecycle of the notifier subscription via ara::com::SubscriptionState. Sources: [SWS_CM_11601], [SWS_CM_11602], [SWS_CM_11604].

Usage Path

The typical usage path comprises registering for notifications, receiving new data, and occasional read and write access:

  1. Set up subscription: The application calls Subscribe() with the desired cache capacity [SWS_CM_11601] and registers a parameterless notification callback using SetReceiveHandler() [SWS_CM_11605]. For concurrent architectures, execution can be delegated via an executor [SWS_CM_11611]. In addition, a handler for transport errors can be registered for notifier events [SWS_CM_00109], [SWS_CM_00110].
  2. Process samples: As soon as communication management receives new field data, it triggers the receive handler. The handler determines available buffer slots via GetFreeSampleCount() [SWS_CM_11603] and processes the new values via GetNewSamples() [SWS_CM_11610]. The E2E state of the received notifications can be verified via GetE2EStateMachineStateNotifier() [SWS_CM_11612].
  3. Explicit read: Retrieving the current value is performed asynchronously via Get() [SWS_CM_00112] and returns a ara::core::Future<FieldType> [SWS_CM_11403]. After completion, the E2E check status can be verified with GetE2EStateMachineStateGetter() [SWS_CM_00145].
  4. Explicit write: Modification of the value is performed via Set(value) [SWS_CM_00113]. The returned ara::core::Future<FieldType> provides the result of the set operation, whose E2E status can be retrieved via GetE2EStateMachineStateSetter() [SWS_CM_00146].

Sequence diagram: Typical flow of interaction with notifications as well as get and set operations. Sources: [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601], [SWS_CM_11605], [SWS_CM_11610].

Error Scenarios

Various error states can occur when using the field methods:

  • Communication failure: If network transmission fails for Get() or Set(), the error ComErrc::kCommunicationFailure is transmitted in the future [SWS_CM_00112], [SWS_CM_00113]. For Get(), rollback semantics apply; for Set(), no_rollback_semantics holds, so that in the event of a timeout an indeterminate state can arise on the server [SWS_CM_00113].
  • Violation of transmission interval: If requests are sent faster than configured in the deployment, this results in ComErrc::kMinimumSendIntervalViolationError [SWS_CM_00112], [SWS_CM_00113].
  • Buffer limits: If memory cannot be allocated during Subscribe(), the method returns ComErrc::kMaxSampleCountNotRealizable [SWS_CM_11601]. If too many samples are retrieved during GetNewSamples(), the call fails with ComErrc::kMaxSamplesExceeded [SWS_CM_11610].
  • Access and handler violations: Missing execution rights result in a InsufficientPermissionsViolation for Get(), Set(), or Subscribe() [SWS_CM_00112], [SWS_CM_00113], [SWS_CM_11601]. Passing empty or invalid callable objects to handler registrations raises a InvalidHandlerViolation [SWS_CM_11605], [SWS_CM_11607], [SWS_CM_00109].
  • Idempotence: Calling Subscribe() again with an identical buffer value in states kSubscribed or kSubscriptionPending has no effect [SWS_CM_11601]; likewise, Unsubscribe() returns without effect if there is no active subscription [SWS_CM_11602].

use

In the proxy scope <SI-Namespace>::proxy::fields::<Field>, the method Get serves for asynchronously retrieving the current field value ([SWS_CM_00112]; see also AUTOSAR_AP_EXP_ARAComAPI §6 “FieldGet”). The function is provided via the proxy header <SiNamespaceDerivedDirectoryPath>/<SiShortname>_proxy.h and exists only if Field.hasGetter == TRUE is modeled for the field ([SWS_CM_00112]). It accepts no parameters and returns a ara::core::Future<FieldType>, which contains the current value after successful transmission ([SWS_CM_00112]).

Error Handling and Boundary Conditions

The interface is defined as noexcept and exception-safe ([SWS_CM_00112]). If the operation fails, the returned ara::core::Future contains an error code with rollback semantics ([SWS_CM_00112]):

  • ComErrc::kCommunicationFailure: The network binding reports a recoverable communication error or the failure of secured communication ([SWS_CM_00112]).
  • ComErrc::kMinimumSendIntervalViolationError: A send request occurred faster than permitted by the minimum send interval configured for the element (minimumSendInterval) ([SWS_CM_00112]).
  • InsufficientPermissionsViolation: Execution is rejected by grant enforcement ([SWS_CM_00112]).

Application errors do not exist for the getter ([SWS_CM_00113]).

Interaction

On the skeleton side, processing the getter request requires a callback registered via RegisterGetHandler ([SWS_CM_00114]). Each call to Get() performs an End-to-End (E2E) check; the resulting state status can be queried synchronously on the proxy side via GetE2EStateMachineStateGetter ([SWS_CM_00145]).
