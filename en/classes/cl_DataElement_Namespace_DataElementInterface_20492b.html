Context

The interface class <DataElement-Namespace>::<DataElementInterface> is part of the Diagnostics functional cluster (diag) of the AUTOSAR Adaptive Platform (AUTOSAR_AP_SWS_Diagnostics p. 68). It serves as a type-specific base class for providing diagnostic data in the role of reading (Read DataElement) according to [SWS_DM_00596].

Within the diagnostic architecture, the class interacts with two essential partners:

  • Diagnostic Management (DM): The central diagnostic server forwards incoming diagnostic requests (for example, UDS services such as ReadDataByIdentifier) to registered handlers ([SWS_DM_00597]).
  • Adaptive Application: The concrete application derives from <DataElementInterface>, implements the pure virtual method Read() ([SWS_DM_00596]), and returns the requested sensor data, status values, or parameters.
  • Manifest and instance modeling: The object is bound to a port configured in the model via a ara::core::InstanceSpecifier ([SWS_DM_00587]).

Lifecycle

The lifecycle of an instance of <DataElement-Namespace>::<DataElementInterface> is controlled by creation, explicit service offering, and destruction:

  • Creation: Instantiation is performed via the constructor, specifying the ara::core::InstanceSpecifier and the concurrency mode ara::diag::ConcurrencyType ([SWS_DM_00587]). This defines whether the implementation is to be operated thread-safely (kConcurrent) or non-thread-safely (kNotConcurrent). The constructor itself is thread-safe and exception-safe (noexcept).
  • Semantics and ownership: Instances of the class may neither be copied nor moved. The copy constructor ([SWS_DM_01661]), the move constructor ([SWS_DM_01662]), and the corresponding assignment operators ([SWS_DM_01659], [SWS_DM_01660]) are explicitly deleted (= delete). The identity and memory address remain bound throughout the entire lifetime.
  • Offering (Offer): After construction, the object is in the inactive state. Calling Offer() enables the forwarding of requests by the Diagnostic Management ([SWS_DM_00597]).
  • Revocation (StopOffer): Forwarding by the DM is deactivated via StopOffer() ([SWS_DM_00617]).
  • Destruction: The virtual destructor ~<DataElementInterface>() terminates the lifecycle ([SWS_DM_00588]). Prior to release, the application would typically call StopOffer() to orderly terminate pending accesses.

With regard to concurrency, the methods Offer(), StopOffer(), and the destructor are specified as non-thread-safe ([SWS_DM_00597], [SWS_DM_00617], [SWS_DM_00588]), which is why concurrent administrative method calls on the same instance must be synchronized.

Usage Path

A regular usage sequence is divided into the following phases:

  1. Derivation and instantiation: The application implements a derived class and overrides the pure virtual function Read() ([SWS_DM_00596]). At startup, the instance is created with the corresponding InstanceSpecifier ([SWS_DM_00587]).
  2. Activation: The application calls Offer(), whereby the handler is registered with the DM ([SWS_DM_00597]).
  3. Request processing: As soon as a diagnostic request arrives, the DM calls the method Read(metaInfo, cancellationHandler) ([SWS_DM_00596]).
    • The handler receives metadata about the request via metaInfo.
    • Via cancellationHandler, the handler can check cyclically with IsCanceled() whether the ongoing diagnostic conversation has been canceled, or register a notification function via SetNotifier() ([SWS_DM_00596]).
  4. Result return: The call returns a ara::core::Future, which in case of success is resolved with the output structure ([SWS_DM_00596], [SWS_DM_00581]). The output data is passed via the declared out arguments such as <DataElementOutArg> ([SWS_DM_80023]).
  5. Deactivation: Prior to shutdown or upon service interruption, the application calls StopOffer() ([SWS_DM_00617]).

Sequence diagram: Typical sequence of instantiation, registration, read access, and deregistration. Sources: [SWS_DM_00587], [SWS_DM_00597], [SWS_DM_00596], [SWS_DM_00617].

Error Scenarios

Errors can occur during instantiation, registration, and the execution of the read request:

  • Construction errors (model violations): The constructor reports configuration and model inconsistencies via the framework's violation concept ([SWS_DM_00587]):
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the executable or does not reference a PortPrototype.
    • PortInterfaceMappingViolation: The referenced PortPrototype is not linked to a DiagnosticDataElementInterface via a DiagnosticDataPortMapping.
    • ProcessMappingViolation: No matching modeled process exists at runtime for the instance identifier.
    • InstanceSpecifierAlreadyInUseViolation: The identifier is already used by another instance in the process.
  • Offer errors: If Offer() is called multiple times while the service is already being offered, the method returns a ara::core::Result with the error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_00597]).
  • Runtime and diagnostic errors in Read(): If the data provision fails, the returned ara::core::Future is populated with an error code ([SWS_DM_00596]):
    • DiagUdsNrcErrc: An applicable Negative Response Code according to ISO 14229-1 (e.g., for unavailable or invalid values).
    • ApApplicationError: An application-specific diagnostic error code.
  • Cancellation: If cancellationHandler.IsCanceled() reports the value true, processing shall be canceled because the client or the DM is no longer accepting the transaction ([SWS_DM_00596]).

This guide is based on the AUTOSAR Adaptive Platform specification for the Diagnostics module (R25-11).
