Provides Communication Management with an interface for vendor-specific freshness value management for SecOC.

The class serves as an interface implemented by the OEM or stack vendor to provide and manage freshness values for SecOC in Communication Management [SWS_CM_11287]. It supplies ara::com with freshness values when sending and receiving secured messages via GetTxFreshness() and GetRxFreshness(), and receives the verification result via SetVerificationStatus() [SWS_CM_11274] [SWS_CM_11276]. Its lifecycle is managed entirely as a singleton by ara::com [SWS_CM_11272].

Context

Class apext::com::secoc::FVM defines the standardized interface for Freshness Value Management (FVM) within Communication Management of AUTOSAR Adaptive [SWS_CM_11287]. It acts as an extension point (plugin interface) implemented by the OEM or the stack vendor to provide application-specific freshness values for per-message protection AUTOSAR_AP_SWS_CommunicationManagement §C.1.2 “Class: FVM”. Interaction partners include Communication Management (ara::com), the cryptographic protection module SecOC, and the vendor's specific FVM library.

Context diagram: Embedding of the FVM interface between Communication Management and vendor-specific freshness value library. Sources: [SWS_CM_11272], [SWS_CM_11287], AUTOSAR_AP_SWS_CommunicationManagement §C.1.2 “Class: FVM”

Lifecycle

Exactly one instance of this class exists within Communication Management AUTOSAR_AP_SWS_CommunicationManagement §C.1.2 “Class: FVM”. The entire lifecycle of the SecOC FreshnessValueManager implementation is managed entirely by ara::com [SWS_CM_11272]. Initialization of the FVM implementation is mandatorily performed by calling method Initialize() [SWS_CM_11273] [SWS_CM_11290]. All methods of the interface are declared as exception safe (noexcept) [SWS_CM_11288]. Interpretation: Because instantiation and lifecycle management are performed internally by ara::com, internal synchronization against concurrent calls from multiple communication channels is the responsibility of the concrete FVM plugin implementation.

Usage Path

During regular operation, Communication Management distinguishes between sending and receiving secured messages:

  • Transmission operation: If a message is configured for SecOC transmission and has a freshnessValueId, Communication Management calls GetTxFreshness() with the freshness value ID [SWS_CM_11274] [SWS_CM_11289]. Upon successful return, the freshness value is used in FVContainer to calculate the authenticator (MAC), which takes place after the calculations for E2E protection [SWS_CM_11274].
  • Reception operation: Unless verification of incoming messages is bypassed by configuration [SWS_CM_11372], SecOC calls GetRxFreshness() prior to E2E checking [SWS_CM_11276] [SWS_CM_11288]. In doing so, the SecOCFreshnessValueID, the received truncated freshness value (SecOCTruncatedFreshnessValue), and the number of previous verification attempts (SecOCAuthVerifyAttempts) are passed [SWS_CM_11288]. After comparing the calculated authenticator, Communication Management reports the result back to the FVM via SetVerificationStatus(), specifying the VerificationStatus [SWS_CM_19999] [SWS_CM_11378].

Sequence diagram: Verification flow when receiving a secured message with freshness value query and status feedback. Sources: [SWS_CM_11276], [SWS_CM_11288], [SWS_CM_19999], AUTOSAR_AP_SWS_CommunicationManagement §8.1 “SecOC secure channel reception”

Error Scenarios

Errors are signaled via return types of type ara::core::Result:

  • Initialization error: If the preparation of the FVM implementation fails, Initialize() returns the error code ComSecOcFvmErrc::kFVInitializeFailed [SWS_CM_11290].
  • Unavailable freshness value: If transmission or reception freshness values cannot temporarily be determined, GetTxFreshness() and GetRxFreshness() return the error ComSecOcFvmErrc::kFVNotAvailable [SWS_CM_11288] [SWS_CM_11289].
  • Transmission retries: If GetTxFreshness() returns the recoverable error kFVNotAvailable or calculation of the authenticator fails, the system increments an Authentication Build Counter [SWS_CM_11275]. Securing the message is retried in a vendor-specific manner; if the counter reaches the configured limit SecOCAuthenticationBuildAttempts, the message is discarded [SWS_CM_11275] AUTOSAR_AP_SWS_CommunicationManagement §8.1 “SecOC secure message build attempts”.
  • Status messages upon verification failures: Specific error modes such as kSecOcVerificationFailure, kSecOcFreshnessFailure, or kSecOcAuthenticationBuildFailure are reported to the FVM via SetVerificationStatus() [SWS_CM_19999] [SWS_CM_11378].

Used by the SecOC to obtain the current freshness value.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 2598e93ae192 Provenance

The member function apext::com::secoc::FVM::GetRxFreshness serves the SecOC layer to determine the full freshness value for received messages [SWS_CM_11288]. As input parameters, the function expects the identifier SecOCFreshnessValueID, the truncated freshness value extracted from the secured message in FVContainer according to [SWS_CM_11286], as well as the counter SecOCAuthVerifyAttempts [SWS_CM_11288]. This counter starts with value 0 on the first verification attempt and is incremented on each subsequent failed attempt for the same message [SWS_CM_11288].

The method is specified as noexcept and exception safe (AUTOSAR_AP_SWS_CommunicationManagement §C.1.2.2.1.1 “GetRxFreshness”). Due to the direct return of a ara::core::Result<FVContainer> without a future type, the call is expected to be processed synchronously blocking. In case of success, the result contains the full freshness value for the subsequent MAC verification of the authenticator [SWS_CM_11288]. If the value cannot be provided, the function returns the recoverable error code ComSecOcFvmErrc::kFVNotAvailable [SWS_CM_11288].

Freshness value determination is an integral part of the SecOC reception path: Message authentication generally takes place prior to downstream E2E checks [SWS_CM_11276] and is coupled with the counter for authentication attempts [SWS_CM_11277]. Specific requirements for reentrancy or thread safety are not defined in the standard; behavior upon concurrent calls is therefore likely to depend on the concrete implementation of the Freshness Value Manager.

      Usage and Call Context
      

      The call is made by ara::com, provided that a freshnessValueId is stored in the configuration for the respective service interface element ([SWS_CM_11274]):
      

        
  
      • Parameter: SecOCFreshnessValueID (type std::uint16_t) identifies the freshness value to be requested ([SWS_CM_11289]).
        • 
  
      • Return value: A ara::core::Result<FVContainer> ([SWS_CM_11289]). In case of success, this contains a apext::com::secoc::FVContainer ([SWS_CM_11286]) whose freshness value is used for the subsequent authenticator or MAC calculation ([SWS_CM_11274]).
        • 
  
      • Exception safety: The function is declared as noexcept ([SWS_CM_11289]).
        • 

      


      Error Handling and Boundary Conditions
      

      If no valid freshness value can be provided, the function returns a ara::core::Result with the error code ComSecOcFvmErrc::kFVNotAvailable ("Freshness Value not available") with rollback semantics ([SWS_CM_11289]). Specific notifications to DET or DEM are not defined for this interface in the Adaptive standard.
      


      Sequence and concurrency
      

      Within the sending process, the call is subject to a strict sequence ([SWS_CM_11274]):
      

        
  
      1. Previously, the lifecycle of the Freshness Value Manager must have been managed by ara::com ([SWS_CM_11272]) and the instance initialized via apext::com::secoc::FVM::Initialize ([SWS_CM_11273]).
        2. 
  
      2. When sending, GetTxFreshness takes place downstream of the E2E protection calculations ([SWS_CM_11274]).
        3. 
  
      3. Subsequently, MAC calculation, optional truncations, and the assembly of the secured message are performed ([SWS_CM_11274]).
        4. 

      

      The specification is silent regarding reentrancy; however, the FVM implementation presumably needs to be designed thread-safe or reentrant if concurrent communication flows request freshness values simultaneously.
