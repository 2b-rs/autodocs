Context

The class apext::com::secoc::FVM provides the standardized interface for Freshness Value Management (FVM) within the Communication Management (CM) module ([SWS_CM_11287]). It serves to protect service-oriented communication against replay attacks within the scope of Secure Onboard Communication (SecOC). The interface is implemented as a library specific to the manufacturer by the OEM or the stack supplier (AUTOSAR_AP_SWS_CommunicationManagement p. 537 “Class: FVM”). Within Communication Management, exactly one central instance (singleton) of this class exists for managing the freshness values (AUTOSAR_AP_SWS_CommunicationManagement p. 537 “Class: FVM”).

The main interaction partners are Communication Management (ara::com) as the controlling instance, the manufacturer-specific FVM library for calculating and synchronizing freshness values, and the secured communication channels (transmission and reception channels) for authenticated messages ([SWS_CM_11272], [SWS_CM_11274], [SWS_CM_11276]).

Context diagram: Interaction between Communication Management, FVM library, and SecOC channel. Sources: [SWS_CM_11272], [SWS_CM_11274], [SWS_CM_11276], AUTOSAR_AP_SWS_CommunicationManagement p. 224 “Lifecycle management of FVM”.

Lifecycle

The lifecycle of the FVM implementation is fully managed by ara::com ([SWS_CM_11272]). During initialization of the communication stack, Communication Management creates the singleton instance and explicitly calls the method Initialize() ([SWS_CM_11273], [SWS_CM_11290]). Only after the successful return of Initialize() is the Freshness Value Manager in the operational state.

Ownership and control rights lie exclusively with Communication Management. Since the class is operated as a singleton and potentially multiple transmit and receive connections are processed in parallel, the thread safety of the method calls is likely ensured by the manufacturer-specific implementation of the FVM library (interpretation). An orderly shutdown takes place analogously via the lifecycle management of ara::com ([SWS_CM_11272]).

Usage Path

After initialization, the typical interaction is divided into two operational paths: the transmit path (Tx) and the receive path (Rx).

  • Initialization: Communication Management calls Initialize() to prepare internal structures, synchronization counters, or cryptographic timers of the FVM library ([SWS_CM_11273], [SWS_CM_11290]).
  • Transmit path (Tx): If a message is to be sent secured via SecOC and a freshnessValueId is stored in the configuration, ara::com requests the current freshness value via GetTxFreshness(SecOCFreshnessValueID) ([SWS_CM_11274], [SWS_CM_11289]). Authentication takes place in the processing order after the E2E protection calculations ([SWS_CM_11274]). The obtained FVContainer is subsequently used to calculate the authenticator ([SWS_CM_11289]).
  • Reception path (Rx): Upon arrival of a secured message, ara::com checks the attribute securedRxVerification. If this is activated or not explicitly defined, the freshness value is queried via GetRxFreshness(SecOCFreshnessValueID, SecOCTruncatedFreshnessValue, SecOCAuthVerifyAttempts) ([SWS_CM_11276], [SWS_CM_11288]). The call passes the truncated freshness value from the received message as well as the verification attempt counter. After calculation and verification of the authenticator, ara::com reports the result back to the FVM via SetVerificationStatus(secOCFreshnessValueID, secOCVerificationStatus) ([SWS_CM_19999]). If, on the other hand, securedRxVerification is configured to false, verification is bypassed and the message is forwarded without an FVM check ([SWS_CM_11372]).

Sequence diagram: Call sequence for initialization, transmit and receive paths between Communication Management and FVM. Sources: [SWS_CM_11273], [SWS_CM_11274], [SWS_CM_11276], [SWS_CM_11288], [SWS_CM_11289], [SWS_CM_19999].

Error Scenarios

All interface methods of apext::com::secoc::FVM are declared with noexcept and report error states deterministically via the error type ara::core::Result ([SWS_CM_11288], [SWS_CM_11289], [SWS_CM_11290], [SWS_CM_19999]).

The following error and status codes are specified:

  • Initialization failure: If the preparation of the FVM library fails, Initialize() returns the error code ComSecOcFvmErrc::kFVInitializeFailed ([SWS_CM_11290]). In this case, the SecOC subsystem cannot process secured messages.
  • Unavailable freshness value (Tx): If GetTxFreshness() returns the error ComSecOcFvmErrc::kFVNotAvailable or calculation of the authenticator fails, ara::com increments the Authentication Build Counter for this message ([SWS_CM_11275], [SWS_CM_11289]). The creation process is repeated in an implementation-specific manner. If the counter reaches the configured threshold SecOCAuthenticationBuildAttempts, the message is discarded ([SWS_CM_11275]). Upon successful creation, the counter is reset to 0 ([SWS_CM_11275]).
  • Unavailable freshness value (Rx): If the freshness value cannot be determined for a received message, GetRxFreshness() also returns ComSecOcFvmErrc::kFVNotAvailable ([SWS_CM_11288]). This prevents successful verification of the authenticator.
  • Feedback of verification status: Via SetVerificationStatus(), ara::com transmits the result of the check to the FVM ([SWS_CM_19999]). The enumeration VerificationStatus ([SWS_CM_11378]) distinguishes between:
    • Success: Verification successful.
    • kSecOcVerificationFailure (0x01): General verification error.
    • kSecOcFreshnessFailure (0x02): Verification failed due to an invalid freshness value.
    • kSecOcAuthenticationBuildFailure (0x03): Error generating the authentication code.
    • kSecOcNoVerification (0x04): Verification was skipped and data directly passed.
    • kSecOcVerificationFailureOverwritten (0x05): Verification failed; message was forwarded anyway due to override status.

No standardized error codes are defined for SetVerificationStatus() itself ([SWS_CM_19999]).

This guide is based exclusively on the AUTOSAR specification for Communication Management (R25-11).
