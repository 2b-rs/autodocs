Context

The data structure ara::tsync::PdelayResponderMeasurementType serves to capture and provide high-precision timestamps for the responder within the scope of the peer delay mechanism (Pdelay). Within the AUTOSAR Adaptive module tsync (Time Synchronization), it is declared in the header file ara/tsync/time_validation_measurement_types.h and forms a central building block for time validation (Time Validation). Its main task is to forward the measurement data of a responder cycle relevant for the propagation delay measurement between two neighboring network nodes in bundled form to higher-level analysis or validation instances.

Essentially three components are involved in this measurement and evaluation context:

  • Pdelay Requester: An initiating network node that periodically transmits a delay request (Pdelay_Req) and awaits the corresponding response (Pdelay_Resp).
  • Pdelay Responder: The local protocol endpoint within the stack of tsync that receives the request, responds to it, and records the exact points in time at the local level.
  • Validation instance: A monitoring or diagnostic unit at the application level that receives the generated measurement structures to verify synchronization quality, network jitter, and protocol compliance.

The structure encapsulates both protocol mapping parameters and temporal measurement points. Upon arrival of the request, the sequence number contained in the packet is recorded as sequenceId [SWS_TS_14174] in order to uniquely assign the data record to the associated transaction. The associated ingress time is stored as requestReceiptTimestamp [SWS_TS_14170] in units of virtual local time (Virtual Local Time). When sending the response message, the egress time is also recorded as responseOriginTimestamp [SWS_TS_14171] in virtual local time. In order to be able to convert these local measured values into a standardized global time base, the structure additionally contains a reference time tuple: the local time value referenceLocalTimestamp [SWS_TS_14172] and the corresponding global time value referenceGlobalTimestamp [SWS_TS_14173] of type ara::tsync::Timestamp.

Lifecycle

The class is modeled as a pure data transfer object (Value Type) with the signature struct PdelayResponderMeasurementType final. It has no polymorphic properties, no state storage, and manages no dynamic resources. This results in distinct characteristics for its lifecycle:

  • Instantiation: An instance is created directly by the time validation logic of the tsync stack as soon as a Pdelay responder run is completed and all ingress and egress timestamps are available. This typically happens on the stack or in a reserved buffer.
  • Assignment and consistency: The instance is populated with all measurement values in a single coherent step. The fields requestReceiptTimestamp [SWS_TS_14170] and responseOriginTimestamp [SWS_TS_14171] are semantically consistent only when using the contained sequenceId [SWS_TS_14174] and in relation to the same reference time tuple ([SWS_TS_14172], [SWS_TS_14173]).
  • Ownership and forwarding: The completed structure is passed to registered consumers by copy of value or move semantics. From an interpretation perspective, this likely occurs via event-based callbacks or data streams of the time validation.
  • Destruction: The lifetime ends automatically when leaving the scope at the receiver, without requiring manual cleanup work or release calls.
  • Concurrency: Since the structure does not have any internal locking mechanisms, it is not thread-safe for concurrent read and write accesses. However, after full initialization by the stack, the structure is immutable (effectively read-only) and can be evaluated in parallel across threads.

Usage Path

The typical usage and processing workflow of PdelayResponderMeasurementType follows a fixed sequence from hardware-related measurements to evaluation in the validation domain:

  1. Reception of Pdelay_Req: The responder receives the peer's request. The ingress timestamp is registered, converted to virtual local time, and stored in field requestReceiptTimestamp [SWS_TS_14170]. At the same time, the frame's sequence number is read out and saved as sequenceId [SWS_TS_14174]. Presumably, this timestamp corresponds to the standardized PTP measurement point t2.
  2. Transmission of Pdelay_Resp: The protocol stack generates the response message and transmits it to the network interface. When sending, the egress timestamp is registered, converted into virtual local time, and stored as responseOriginTimestamp [SWS_TS_14171]. This point in time presumably corresponds to the standardized PTP measurement point t3.
  3. Coupling to the global time: The module determines the currently valid reference tuple of the time base and populates referenceLocalTimestamp [SWS_TS_14172] as well as referenceGlobalTimestamp [SWS_TS_14173]. This documents the relationship that existed between virtual local time and global time at the time of measurement.
  4. Export and time conversion: The aggregated data record is transmitted to the validation application. Based on the two reference timestamps, the consumer can accurately evaluate the difference between reception and transmission, check the residence time of the responder, or transform the timestamps into global time for further protocol verification.
