Context

The class ara::com::e2e::ComE2EErrorDomain represents the specific error domain for errors in the context of End-to-End protection (E2E) within the AUTOSAR Adaptive Communication Management middleware (ara::com). It derives from the base infrastructure class ara::core::ErrorDomain and defines the standardized error context for all communication errors that occur during the E2E validation of messages.

In the interaction of distributed adaptive applications, ComE2EErrorDomain handles the identification and mapping of errors that are detected when sending or receiving E2E-protected method and event data. If, during a method call, an error within the scope of the E2E check (E2E_check) is detected in the request message on the server side, an E2E error response message is generated (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.4.2 “Serializing the response payload”). The payload of this error response contains a ara::core::ErrorCode whose error domain is mandatorily set to ara::com::e2e::ComE2EErrorDomain ([SWS_CM_00033]). The error value itself reflects the concrete result of the check routine ([SWS_CM_00033]).

On the client side, the middleware evaluates the response message: If the client detects an E2E error during deserialization or notification, the communication layer provides a ara::core::Result to the calling application (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”). If an E2E check error occurs, this Result encapsulates a ara::core::ErrorCode of domain ComE2EErrorDomain with the corresponding error code of the enumeration ComE2EErrc (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”).

Context diagram: Embedding of ComE2EErrorDomain into the E2E check and error forwarding between client, server, and middleware. Sources: [SWS_CM_00033], AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.4.2 “Serializing the response payload”, AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”.

Lifecycle

Instantiation of ComE2EErrorDomain is performed via a parameterless constexpr constructor ([SWS_CM_12506]). Since the constructor is declared as constexpr and noexcept ([SWS_CM_12506]), the instance can already be created at compile time or during static initialization of the application.

Interpretation: According to the general architectural pattern of ara::core::ErrorDomain, the class is likely to be typically provided as a global, immutable singleton in order to retain error-related text and type information over the entire runtime.

The class is declared as final, precluding further derivation. Since all querying member functions such as Name() ([SWS_CM_12507]) and Message() ([SWS_CM_12508]) are specified as const and noexcept, the class has no mutable state. This results in complete exception safety (exception safe) and unrestricted thread safety during concurrent access by multiple threads of the application or middleware routines. Special precautions for synchronization or locking are not required during the entire lifecycle of the instance.

Usage Path

The regular usage path of ComE2EErrorDomain spans server-side error detection, transmission of the error information, and client-side evaluation:

  1. Server-side E2E check: Upon arrival of an E2E-protected method call, the communication layer of the server performs the check E2E_check ([SWS_CM_00033]).
  2. Generation of the error response: If the check fails, the server serializes an E2E error response whose payload contains a ara::core::ErrorCode with domain ComE2EErrorDomain ([SWS_CM_00033]).
  3. Client-side evaluation: After receiving and deserializing the response message (AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”), ara::com provides a ara::core::Result to the client application, which encapsulates the transmitted ara::core::ErrorCode in the event of an error.
  4. Querying error details: The application checks the Result and, via the error domain ComE2EErrorDomain, determines the textual description by means of Message() ([SWS_CM_12508]) or the domain name by means of Name() ([SWS_CM_12507]).
  5. Optional exception handling: If the application prefers exception handling, the ErrorCode is converted into a concrete exception via ThrowAsException() ([SWS_CM_12509]).

Sequence diagram: Typical sequence of error detection, error response, and evaluation involving ComE2EErrorDomain. Sources: [SWS_CM_00033], [SWS_CM_12508], AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”.

Error Scenarios

In faulty communication scenarios, ComE2EErrorDomain acts as a link between numerical check codes and comprehensible diagnostics:

  • Error code mapping: The type alias Errc maps the enumeration ComE2EErrc ([SWS_CM_12504]). Each concrete error value is resolved into a descriptive string via the function Message() ([SWS_CM_12508]) to enable a precise root-cause analysis (for example, faulty checksum or invalid counter value).
  • Domain identification: Via Name(), the instance returns the standardized name of the error domain ([SWS_CM_12507]), allowing applications to reliably check whether an occurred error object originates from the E2E domain.
  • Exception handling and compiler configuration: The type alias Exception binds the exception class ComE2EException ([SWS_CM_12505]). If ThrowAsException() is called with a ara::core::ErrorCode, the method instantiates a ComE2EException and throws it ([SWS_CM_12509]). The function is declared as non-exception-safe (not exception safe) ([SWS_CM_12509]). If C++ exceptions are disabled in the compiler toolchain, ThrowAsException() does not participate in overload resolution according to the specification ([SWS_CM_12509]), so that applications must work based on error codes via ara::core::Result instead.

<h4>Lifecycle</h4>
<p>Instantiation of <code>ComE2EErrorDomain</code> is performed via a parameterless <code>constexpr</code> constructor (<a class="spec-record-ref" data-req="SWS_CM_12506" href="../spec/record.html?id=SWS_CM_12506">[SWS_CM_12506]</a>). Since the constructor is declared as <code>constexpr</code> and <code>noexcept</code> (<a class="spec-record-ref" data-req="SWS_CM_12506" href="../spec/record.html?id=SWS_CM_12506">[SWS_CM_12506]</a>), the instance can already be created at compile time or during static initialization of the application.</p>
<p>Interpretation: According to the general architectural pattern of <code>ara::core::ErrorDomain</code>, the class is likely to be typically provided as a global, immutable singleton in order to retain error-related text and type information over the entire runtime.</p>
<p>The class is declared as <code>final</code>, precluding further derivation. Since all querying member functions such as <code>Name()</code> (<a class="spec-record-ref" data-req="SWS_CM_12507" href="../spec/record.html?id=SWS_CM_12507">[SWS_CM_12507]</a>) and <code>Message()</code> (<a class="spec-record-ref" data-req="SWS_CM_12508" href="../spec/record.html?id=SWS_CM_12508">[SWS_CM_12508]</a>) are specified as <code>const</code> and <code>noexcept</code>, the class has no mutable state. This results in complete exception safety (<code>exception safe</code>) and unrestricted thread safety during concurrent access by multiple threads of the application or middleware routines. Special precautions for synchronization or locking are not required during the entire lifecycle of the instance.</p>

<h4>Usage Path</h4>
<p>The regular usage path of <code>ComE2EErrorDomain</code> spans server-side error detection, transmission of the error information, and client-side evaluation:</p>
<ol>
<li><strong>Server-side E2E check:</strong> Upon arrival of an E2E-protected method call, the communication layer of the server performs the check <code>E2E_check</code> (<a class="spec-record-ref" data-req="SWS_CM_00033" href="../spec/record.html?id=SWS_CM_00033">[SWS_CM_00033]</a>).</li>
<li><strong>Generation of the error response:</strong> If the check fails, the server serializes an E2E error response whose payload contains a <code>ara::core::ErrorCode</code> with domain <code>ComE2EErrorDomain</code> (<a class="spec-record-ref" data-req="SWS_CM_00033" href="../spec/record.html?id=SWS_CM_00033">[SWS_CM_00033]</a>).</li>
<li><strong>Client-side evaluation:</strong> After receiving and deserializing the response message (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_CommunicationManagement&amp;page=261">AUTOSAR_AP_SWS_CommunicationManagement §7.4.1.2.5.2 “Deserializing the payload”</a>), <code>ara::com</code> provides a <code>ara::core::Result</code> to the client application, which encapsulates the transmitted <code>ara::core::ErrorCode</code> in the event of an error.</li>
<li><strong>Querying error details:</strong> The application checks the <code>Result</code> and, via the error domain <code>ComE2EErrorDomain</code>, determines the textual description by means of <code>Message()</code> (<a class="spec-record-ref" data-req="SWS_CM_12508" href="../spec/record.html?id=SWS_CM_12508">[SWS_CM_12508]</a>) or the domain name by means of <code>Name()</code> (<a class="spec-record-ref" data-req="SWS_CM_12507" href="../spec/record.html?id=SWS_CM_12507">[SWS_CM_12507]</a>).</li>
<li><strong>Optional exception handling:</strong> If the application prefers exception handling, the <code>ErrorCode</code> is converted into a concrete exception via <code>ThrowAsException()</code> (<a class="spec-record-ref" data-req="SWS_CM_12509" href="../spec/record.html?id=SWS_CM_12509">[SWS_CM_12509]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>In faulty communication scenarios, <code>ComE2EErrorDomain</code> acts as a link between numerical check codes and comprehensible diagnostics:</p>
<ul>
<li><strong>Error code mapping:</strong> The type alias <code>Errc</code> maps the enumeration <code>ComE2EErrc</code> (<a class="spec-record-ref" data-req="SWS_CM_12504" href="../spec/record.html?id=SWS_CM_12504">[SWS_CM_12504]</a>). Each concrete error value is resolved into a descriptive string via the function <code>Message()</code> (<a class="spec-record-ref" data-req="SWS_CM_12508" href="../spec/record.html?id=SWS_CM_12508">[SWS_CM_12508]</a>) to enable a precise root-cause analysis (for example, faulty checksum or invalid counter value).</li>
<li><strong>Domain identification:</strong> Via <code>Name()</code>, the instance returns the standardized name of the error domain (<a class="spec-record-ref" data-req="SWS_CM_12507" href="../spec/record.html?id=SWS_CM_12507">[SWS_CM_12507]</a>), allowing applications to reliably check whether an occurred error object originates from the E2E domain.</li>
<li><strong>Exception handling and compiler configuration:</strong> The type alias <code>Exception</code> binds the exception class <code>ComE2EException</code> (<a class="spec-record-ref" data-req="SWS_CM_12505" href="../spec/record.html?id=SWS_CM_12505">[SWS_CM_12505]</a>). If <code>ThrowAsException()</code> is called with a <code>ara::core::ErrorCode</code>, the method instantiates a <code>ComE2EException</code> and throws it (<a class="spec-record-ref" data-req="SWS_CM_12509" href="../spec/record.html?id=SWS_CM_12509">[SWS_CM_12509]</a>). The function is declared as non-exception-safe (<code>not exception safe</code>) (<a class="spec-record-ref" data-req="SWS_CM_12509" href="../spec/record.html?id=SWS_CM_12509">[SWS_CM_12509]</a>). If C++ exceptions are disabled in the compiler toolchain, <code>ThrowAsException()</code> does not participate in overload resolution according to the specification (<a class="spec-record-ref" data-req="SWS_CM_12509" href="../spec/record.html?id=SWS_CM_12509">[SWS_CM_12509]</a>), so that applications must work based on error codes via <code>ara::core::Result</code> instead.</li>
</ul>
