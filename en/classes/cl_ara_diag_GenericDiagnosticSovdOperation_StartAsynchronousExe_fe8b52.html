Context

The structure ara::diag::GenericDiagnosticSovdOperation::StartAsynchronousExecutionResponse is a component of the diagnostic module (diag) in the AUTOSAR Adaptive Platform ([SWS_DM_02209], AUTOSAR_AP_SWS_Diagnostics §8.62.3 “Struct: StartAsynchronousExecutionResponse”). It serves as a standardized return structure within the Service-Oriented Vehicle Diagnostics (SOVD) framework when a requested diagnostic operation cannot be completed immediately, but transitions into asynchronous background processing ([SWS_DM_01396]).

In the overall system, three primary participants interact with each other (AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 “Operations – Start execution of an operation”):

  • The external SOVD client, which requests diagnostic operations via the method Start Execution of an Operation in accordance with the ASAM SOVD specification ([SWS_DM_01396]).
  • The diagnostic server instance (Diagnostic Management, DM), which receives incoming SOVD calls, performs required security checks such as proximity challenges, and delegates execution to the application ([SWS_DM_02174]).
  • The diagnostic service implementation, which is derived from the abstract base class ara::diag::GenericDiagnosticSovdOperation and implements the pure virtual method StartExecution (AUTOSAR_AP_SWS_Diagnostics p. 858).

In this arrangement, StartAsynchronousExecutionResponse signals to Diagnostic Management that the requested operation has been successfully initiated and is now continuing asynchronously.

Lifecycle

The creation and lifetime of StartAsynchronousExecutionResponse are strictly bound to the invocation and return path of method StartExecution:

  • Instantiation: An instance of StartAsynchronousExecutionResponse is created by the application-specific diagnostic implementation ([SWS_DM_02209]) as soon as it has been decided that the requested SOVD operation cannot be completed synchronously. Interpretation: The structure is likely to act as a typed indicator for the asynchronous processing mode.
  • Ownership and passing: The instance is embedded as a value type into a ara::core::Variant<StartSynchronousExecutionResponse, StartAsynchronousExecutionResponse>, which is returned to Diagnostic Management via a ara::core::Future (AUTOSAR_AP_SWS_Diagnostics p. 858). Ownership transfers to Diagnostic Management upon fulfillment of the underlying promise.
  • Destruction: As soon as Diagnostic Management has resolved the future, evaluated the variant, and prepared the SOVD start response for the client, the instance's lifetime ends.
  • Concurrency: Since StartExecution returns a ara::core::Future (AUTOSAR_AP_SWS_Diagnostics p. 858), StartAsynchronousExecutionResponse can be provided concurrently via a background thread of the application. At the same time, the operation receives a ara::diag::CancellationHandler (AUTOSAR_AP_SWS_Diagnostics p. 858) through which ongoing asynchronous activities can be cancelled in a coordinated manner.

Usage Path

The typical usage path comprises the initiation of an asynchronous SOVD operation via Diagnostic Management:

  1. Request reception: An external diagnostic tester sends the SOVD method for starting an operation to the Diagnostic Server instance ([SWS_DM_01396]).
  2. Verification and forwarding: Diagnostic Management validates required preconditions (such as the Proximity Challenge) and, upon successful verification, calls method StartExecution of the responsible instance of ara::diag::GenericDiagnosticSovdOperation ([SWS_DM_02174]).
  3. Parameter passing: When StartExecution is called, the operation name (sovd_operation_name), the content data (sovd_content_data), meta-information (meta_info), and the cancellation_handler are passed (AUTOSAR_AP_SWS_Diagnostics p. 858).
  4. Asynchronous execution: The diagnostic application starts the internal background activity and creates an instance of StartAsynchronousExecutionResponse ([SWS_DM_02209]).
  5. Feedback: The application packages StartAsynchronousExecutionResponse into the ara::core::Variant and provides it via the returned ara::core::Future (AUTOSAR_AP_SWS_Diagnostics p. 858).
  6. SOVD response: Diagnostic Management receives the result and transmits the standard-compliant SOVD response for a successful asynchronous start to the client ([SWS_DM_01396]).

Error Scenarios

In connection with the use of StartAsynchronousExecutionResponse, several preconditions and postconditions as well as error cases are relevant:

  • Failed security validation: If the validation preceding the start (such as the Proximity Challenge) fails, the call of StartExecution by the DM does not take place ([SWS_DM_02174]). Consequently, no instance of StartAsynchronousExecutionResponse is created.
  • Freedom from exceptions (noexcept): The interface StartExecution is declared as noexcept (AUTOSAR_AP_SWS_Diagnostics p. 858). Errors during the initialization of asynchronous operation must not be thrown as C++ exceptions, but must be reported as an error state via the ara::core::Future.
  • Deviating execution mode: If, contrary to original expectations, an operation can be completed synchronously immediately, StartAsynchronousExecutionResponse must not be returned. Instead, StartSynchronousExecutionResponse must be set in the ara::core::Variant (AUTOSAR_AP_SWS_Diagnostics p. 858, [SWS_DM_02176]).
  • Cancellation during processing: If the DM or the client requests a cancellation during the running background activity, this is signaled via the passed ara::diag::CancellationHandler (AUTOSAR_AP_SWS_Diagnostics p. 858).

<h4>Error Scenarios</h4>
<p>In connection with the use of <code>StartAsynchronousExecutionResponse</code>, several preconditions and postconditions as well as error cases are relevant:</p>
<ul>
<li><strong>Failed security validation:</strong> If the validation preceding the start (such as the Proximity Challenge) fails, the call of <code>StartExecution</code> by the DM does not take place (<a class="spec-record-ref" data-req="SWS_DM_02174" href="../spec/record.html?id=SWS_DM_02174">[SWS_DM_02174]</a>). Consequently, no instance of <code>StartAsynchronousExecutionResponse</code> is created.</li>
<li><strong>Freedom from exceptions (<code>noexcept</code>):</strong> The interface <code>StartExecution</code> is declared as <code>noexcept</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=858">AUTOSAR_AP_SWS_Diagnostics p. 858</a>). Errors during the initialization of asynchronous operation must not be thrown as C++ exceptions, but must be reported as an error state via the <code>ara::core::Future</code>.</li>
<li><strong>Deviating execution mode:</strong> If, contrary to original expectations, an operation can be completed synchronously immediately, <code>StartAsynchronousExecutionResponse</code> must not be returned. Instead, <code>StartSynchronousExecutionResponse</code> must be set in the <code>ara::core::Variant</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=858">AUTOSAR_AP_SWS_Diagnostics p. 858</a>, <a class="spec-record-ref" data-req="SWS_DM_02176" href="../spec/record.html?id=SWS_DM_02176">[SWS_DM_02176]</a>).</li>
<li><strong>Cancellation during processing:</strong> If the DM or the client requests a cancellation during the running background activity, this is signaled via the passed <code>ara::diag::CancellationHandler</code> (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=858">AUTOSAR_AP_SWS_Diagnostics p. 858</a>).</li>
</ul>
