Serves as an interface for applications to verify and execute UDS ECU resets in Diagnostic Management.

The class ara::diag::EcuResetRequest represents the application interface for handling UDS reset services (Service 0x11) in Diagnostic Management AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.1. After activation by means of Offer(), it accepts requests to verify and execute restarts as well as for rapid shutdown control ([SWS_DM_01016], [SWS_DM_01013], [SWS_DM_01014]). Instances are neither copyable nor movable, and all methods are specified as not thread-safe ([SWS_DM_01010], [SWS_DM_01621]).

Context

The interface class ara::diag::EcuResetRequest serves to handle the UDS service ECUReset (Service 0x11) in the AUTOSAR Adaptive Platform AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.1 “Service 0x11 – ECUReset – RapidPowerShutdown sub function”. It enables an application to act as a handler for reset requests from the Diagnostic Management (DM). Its responsibilities include enabling or disabling rapid shutdown ([SWS_DM_01012]), checking incoming reset requests ([SWS_DM_01013]), and the actual execution of the restart ([SWS_DM_01014]). Involved interaction partners are the external diagnostic tester, the instance of the Diagnostic Management (DM or Diagnostic Server), and the application-side implementation of EcuResetRequest.

Context diagram: Interaction between diagnostic tester, Diagnostic Management (DM), and the handler application. Sources: AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.1, AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.2, [SWS_DM_01010], [SWS_DM_01016].

Lifecycle

An instance of EcuResetRequest is created via its explicit constructor by specifying an ara::core::InstanceSpecifier that refers to an PortPrototype of an DiagnosticEcuResetInterface ([SWS_DM_01010]). According to the design guidelines, the class is neither copyable nor movable; copy and move constructors ([SWS_DM_01621], [SWS_DM_01622]) as well as the corresponding assignment operators ([SWS_DM_01619], [SWS_DM_01620]) are explicitly deleted (=delete). All interface methods as well as the destructor ([SWS_DM_01011]) are specified as not thread-safe ([SWS_DM_01010], [SWS_DM_01016], [SWS_DM_01017]). After initialization, the handler is initially in the state where no forwarding of requests takes place, until registration is explicitly activated via Offer() ([SWS_DM_01016]). Calling StopOffer() deactivates the forwarding of requests again ([SWS_DM_01017]) before the object can be destroyed ([SWS_DM_01011]).

State diagram: Life phases and registration states of an EcuResetRequest instance. Sources: [SWS_DM_01010], [SWS_DM_01016], [SWS_DM_01017], [SWS_DM_01011].

Usage Path

A typical usage path is divided into initialization, enablement, and the subsequent processing of diagnostic requests:

  1. Instantiation and enablement: The application instantiates the derived class with the appropriate InstanceSpecifier ([SWS_DM_01010]) and calls Offer() to enable the DM to forward requests ([SWS_DM_01016]).
  2. Rapid shutdown control: When the DM receives a UDS request for EnableRapidPowerShutdown or DisableRapidPowerShutdown, it calls EnableRapidShutdown(enable, metaInfo, cancellationHandler) ([SWS_DM_01020], [SWS_DM_01021], [SWS_DM_01012]). In case of a positive acknowledgment, the DM inserts the configured value for the shutdown time into the response (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.1 [SWS_DM_01092]).
  3. Reset request: For all other UDS reset subfunctions, the DM calls the method RequestReset(resetType, id, metaInfo, cancellationHandler) ([SWS_DM_01013]). The instantiating process must carefully check whether a restart of parts or the entire machine is permissible ([SWS_DM_01013]). The cancellation status can be queried or a notifier can be registered via the cancellationHandler ([SWS_DM_01013]).
  4. Reset execution: If the request is accepted and it is configured that the positive response is sent before the reset (respondBeforeReset or not present), the Diagnostic Server sends the positive UDS response and subsequently calls ExecuteReset(metaInfo) (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.2 [SWS_DM_01023], [SWS_DM_01014]). If respondAfterReset was configured instead, the positive response is returned only after the restart, provided that RequestReset() has not reported an error (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.2 [SWS_DM_00360]).
  5. Service deregistration: To terminate service forwarding, the application calls StopOffer() ([SWS_DM_01017]).

Sequence diagram: Sequence of an EcuReset request with confirmation before reset execution (respondBeforeReset). Sources: [SWS_DM_01016], [SWS_DM_01013], [SWS_DM_01014], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.2 [SWS_DM_01023].

Error Scenarios

In case of an error, the following aspects must be observed for the various calls:

  • Constructor violations: During creation, model violations can occur, among others if the InstanceSpecifier cannot be resolved in the model (InstanceSpecifierMappingIntegrityViolation), refers to an incorrect model element, the port mapping is missing (PortInterfaceMappingViolation), no process reference is present (ProcessMappingViolation), or the identifier is already in use in the process (InstanceSpecifierAlreadyInUseViolation) ([SWS_DM_01010]).
  • Registration errors: If Offer() is called even though the service is already offered, the method returns a ara::core::Result with the error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_01016]).
  • Diagnostic negative response codes (NRCs): If EnableRapidShutdown, RequestReset, or ExecuteReset cannot be completed successfully, their return futures return an error with a matching ISO 14229-1 Negative Response Code (NRC) via DiagUdsNrcErrc ([SWS_DM_01012], [SWS_DM_01013], [SWS_DM_01014]). Note: If respondToReset is set to respondBeforeReset or not configured, an error in ExecuteReset() has no further effect on the diagnostic response, because the positive acknowledgment has already been sent to the tester beforehand ([SWS_DM_01014], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.5.2 [SWS_DM_01023]).

              Usage and Call Context
              

              The pure virtual method EnableRapidShutdown of class ara::diag::EcuResetRequest serves as an interface for handling the UDS subfunctions for rapid power shutdown ([SWS_DM_01012]). Upon incoming diagnostic requests of service 0x11 (ECUReset), the Diagnostic Manager (DM) calls this function: for EnableRapidPowerShutdown with the argument enable = true ([SWS_DM_01020]) and for DisableRapidPowerShutdown with enable = false ([SWS_DM_01021]). This distinguishes these two subfunctions from all other ECUReset services, which trigger RequestReset instead ([SWS_DM_00235]).
              

              The method takes three parameters ([SWS_DM_01012]):
              

                

              • enable: Enables rapid power shutdown in case of true and disables it in case of false.
                • 

              • metaInfo: Passes meta-information on the diagnostic request.
                • 

              • cancellationHandler: Serves to monitor the cancellation status via cancellationHandler.IsCanceled() or to register a notifier via cancellationHandler.SetNotifier() if the ongoing diagnostic conversation is canceled.
                • 

              

              Semantics, error handling, and concurrency
              

              The interface returns a ara::core::Future<void>; the actual processing thus presumably occurs asynchronously in the background ([SWS_DM_01012]). In case of success, the future returns no value. In case of an error, an appropriate Negative Response Code (NRC) according to ISO 14229-1 must be set by means of DiagUdsNrcErrc (AUTOSAR_AP_SWS_Diagnostics §8.16.3.1.3.1 “EnableRapidShutdown”). The function is specified as noexcept and exception-safe (exception safe), but is considered not thread-safe (not thread-safe), which is why concurrent calls on the same instance must be avoided on the application side ([SWS_DM_01012]).

                  The method ExecuteReset of interface ara::diag::EcuResetRequest is called by the Diagnostic Server (DM) to actually trigger in the implementing process the ECU reset previously accepted via [SWS_DM_01013] [SWS_DM_01014]. The metaInfo of the request is passed as parameter. The function is specified as not thread-safe (not thread-safe), but exception-safe (exception safe) [SWS_DM_01014].

                  • If the parameter is not present or set to respondBeforeReset, the Diagnostic Server calls ExecuteReset only after the positive UDS response has been sent [SWS_DM_01023].
                    • 
    
                  • If respondAfterReset is configured, ExecuteReset is called directly and without previously sending the positive response [SWS_DM_01090].
                    •

If incoming UDS requests were blocked after acceptance of the reset [SWS_DM_01022], the Diagnostic Server unblocks them as soon as the Future returned by ExecuteReset is completed [SWS_DM_01309]. Possible errors are signaled via ISO 14229-1 NRCs by means of DiagUdsNrcErrc in the Future; with configuration respondBeforeReset, however, a passed error remains without effect [SWS_DM_01014].

    With the method ara::diag::EcuResetRequest::Offer ([SWS_DM_01016]), an Adaptive Application signals to Diagnostic Management (DM) that it is ready to receive incoming diagnostic requests for an ECU reset. Through the synchronous call, the DM is authorized to forward corresponding request messages to this handler ([SWS_DM_01016]). The call is likely to typically take place during the initialization phase of the application before diagnostic requests are to be processed by the DM.
  
                      
  
                      Call and error handling
                      
  
                      
    The function has no input parameters, is declared as noexcept, and guarantees exception safety ([SWS_DM_01016]). A ara::core::Result<void> serves as return value. If providing fails because the service was already offered previously, the method returns the error code DiagOfferErrc::kAlreadyOffered with rollback semantics ([SWS_DM_01016]).
