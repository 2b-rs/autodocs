Provides typed read and write access to array elements of SOVD diagnostic data via indices and iterators.

The class provides a structured interface for random as well as iterator-based access to array-based diagnostic data elements of the Adaptive Platform ([SWS_DM_02227]). It enables applications to dynamically append primitive data values and complex content elements, as well as to preemptively reserve memory capacities. In case of incompatible data types, invalid index accesses, or explicitly set error states, error codes are propagated to the caller via Result types ([SWS_DM_02228]). According to the standard, all specified operations are implemented completely exception-safe and thread-safe.

Context

The class ara::diag::DiagnosticSovdArrayContentElementDataView is defined in AUTOSAR_AP_SWS_Diagnostics §8.60.5 “Class: DiagnosticSovdArrayContentElementDataView” under [SWS_DM_02227]. In the AUTOSAR Adaptive Diagnostics module, it serves as a typed view on a diagnostic content element (DiagnosticSovdContentElementData) with the underlying type ArrayContentElementData. It is declared via the header ara/diag/diagnostic_sovd_content_element_data.h.

Its primary responsibility lies in the structured encapsulation of array operations for Service-Oriented Vehicle Diagnostics (SOVD). Calling diagnostic applications that process or provide SOVD data structures, as well as the underlying generic data containers, act as interaction partners. Access to individual array elements is handled either via dedicated iterators or via typed index operators.

Lifecycle

As a view object, the instance presumably does not hold sole ownership of the actual payload data, but binds to the memory of an existing DiagnosticSovdContentElementData. The lifecycle of the data is subject to the following phases:

  • Memory reservation and capacity: Prior to inserting larger amounts of data, the internal memory capacity can be set proactively via Reserve ([SWS_DM_02240]). The current capacity can be determined using Capacity ([SWS_DM_02231]).
  • Population: New elements are appended sequentially via overloads of PushBack. Primitive data types such as std::int64_t ([SWS_DM_02241]), std::uint64_t ([SWS_DM_02242]), double ([SWS_DM_02243]), bool ([SWS_DM_02244]), and ara::core::StringView ([SWS_DM_02245]) as well as nested DiagnosticSovdContentElementData instances ([SWS_DM_02246]) are supported.
  • Inspection and cleanup: The occupancy state can be queried at any time via Size ([SWS_DM_02230]) and Empty ([SWS_DM_02232]). Individual elements can be removed per iterator via Erase ([SWS_DM_02247]), while Clear ([SWS_DM_02233]) resets the entire array.

Regarding concurrency and exception behavior, all member functions of the class are specified to be exception-safe (declared with noexcept) and thread-safe.

Usage Path

A typical usage path comprises preparatory capacity reservation, step-by-step data population, reading the elements, and final validation for error states:

  1. Reserve capacity: The application calls Reserve to minimize dynamic reallocations during subsequent write accesses ([SWS_DM_02240]).
  2. Insert elements: Data records are appended using PushBack ([SWS_DM_02241]).
  3. Read or traverse elements: Access is performed either randomly via operator[] ([SWS_DM_02234], [SWS_DM_02235]) or sequentially via iterators via Begin/End ([SWS_DM_02236], [SWS_DM_02237]) or CBegin/CEnd ([SWS_DM_02238], [SWS_DM_02239]).
  4. Check status: After completing the operations, the application checks via HasError whether the array content has remained free of errors ([SWS_DM_02228]).

Sequence diagram: Typical flow for populating, indexing, and error checking an SOVD array element. Sources: [SWS_DM_02240], [SWS_DM_02241], [SWS_DM_02234], [SWS_DM_02228].

Error Scenarios

Methods with error potential use ara::core::Result to report violated preconditions or execution aborts instead of C++ exceptions:

  • Type mismatch: Operations such as PushBack ([SWS_DM_02241]) or operator[] ([SWS_DM_02234]) require that the encapsulated element is actually of type ArrayContentElementData. Otherwise, they return a corresponding error in the Result object. For PushBack, the inserted type must additionally match the data type specified in the constructor of the array element.
  • Failed erasure: Calling Erase ([SWS_DM_02247]) returns an error in Result if the target is not of type ArrayContentElementData or if the element could not be removed via the specified iterator.
  • Explicit error states: A ara::core::ErrorCode can be assigned to the array content via SetError ([SWS_DM_02229]). If the content is marked as faulty in this way, the query HasError ([SWS_DM_02228]) returns the error code as ara::diag::DiagSovdErrc.
