Context

The class ara::phm::RecoveryAction is a fundamental abstract base class within the module phm (Platform Health Management) of the AUTOSAR Adaptive Platform. Its central responsibility is to provide a standardized interface through which the Platform Health Management can request recovery and remediation actions if a system health monitoring fails [SWS_PHM_01142].

The class acts as a link between platform monitoring and the application-specific error response. In typical system architectures, it is derived by higher-level functional components such as State Management in order to respond specifically to detected errors and, for example, transition affected processes or function groups into safe states [SWS_PHM_01142].

Essentially three components are involved in the interaction:

  • Application / State Management: Derives from ara::phm::RecoveryAction, implements the pure virtual method RecoveryHandler, and executes the concrete recovery logic [SWS_PHM_01142].
  • RecoveryAction instance: Binds the recovery action to a modeled port and encapsulates the control of the readiness to receive via Offer and StopOffer [SWS_PHM_01141], [SWS_PHM_01143], [SWS_PHM_01144].
  • Phm-Daemon / Platform Health Management: Detects errors in elementary monitorings, triggers registered recovery actions via the handler, and triggers the watchdog in the event of unrecoverable errors [SWS_PHM_01142], [SWS_PHM_01143]. In addition, the type ara::exec::ExecutionErrorEvent from Execution Management provides the detailed context data of the error [SWS_PHM_01142].

Lifecycle

An instance of ara::phm::RecoveryAction is created via its explicit constructor, which accepts a ara::core::InstanceSpecifier [SWS_PHM_01141]. This identifier must reference a modeled PPortPrototype that is linked to a PhmSupervisionRecoveryNotificationInterface via a RecoveryNotificationToPPortPrototypeMapping [SWS_PHM_01141]. The constructor is specified as exception safe (exception safe) and thread-safe (thread-safe) [SWS_PHM_01141].

Copy and move operations are completely prohibited for ara::phm::RecoveryAction:

  • Both the copy constructor and the copy assignment operator are deleted (= delete) [SWS_PHM_01150], [SWS_PHM_01152].
  • Likewise, the move constructor and the move assignment operator are explicitly deleted (= delete) [SWS_PHM_01149], [SWS_PHM_01151]. This prevents a move operation, after offering has occurred (Offer), from leading to a premature call of the RecoveryHandler before the derived class is completely constructed, which could lead to undefined behavior or unhandled exceptions and compromise system safety [SWS_PHM_01149], [SWS_PHM_01151].

After construction, the instance is initially in an inactive state. Only calling Offer() activates the readiness for potential calls of the RecoveryHandler by the Phm-Daemon [SWS_PHM_01142], [SWS_PHM_01143]. This readiness can be deactivated again at any time via StopOffer() [SWS_PHM_01144].

The lifecycle ends with the call of the virtual destructor ~RecoveryAction() [SWS_PHM_01145]. While construction and handler execution are thread-safe, Offer(), StopOffer(), and the destructor are not thread-safe (not thread-safe) [SWS_PHM_01141], [SWS_PHM_01142], [SWS_PHM_01143], [SWS_PHM_01144], [SWS_PHM_01145]. Interpretation: Prior to destroying the object, StopOffer() would typically be called to ensure that no asynchronous handler calls take place anymore during object teardown.

Usage Path

The regular procedure for using a recovery action is divided into the following steps:

  1. Derivation and instantiation: The application-specific component derives from ara::phm::RecoveryAction, implements the method RecoveryHandler [SWS_PHM_01142], and instantiates the object with the appropriate InstanceSpecifier [SWS_PHM_01141].
  2. Offering: The application calls Offer() to perform registration with the Phm-Daemon and enable incoming recovery requests [SWS_PHM_01143]. Prior to this call, no handler call may be made by the PHM [SWS_PHM_01142].
  3. Execution of error handling: If an elementary monitoring fails, the Phm-Daemon calls the method RecoveryHandler and passes the error information (executionError) as well as the affected monitoring type (supervision) [SWS_PHM_01142].
  4. Asynchronous feedback: The implementation returns a ara::core::Future<void>, which is fulfilled empty (void) upon successful recovery or transports the error code PhmErrc::kSMCanNotHandleRecovery in the event of an error [SWS_PHM_01142].
  5. Deactivation: If the action is no longer required, the application calls StopOffer(), which prevents future handler calls [SWS_PHM_01144].

Sequence diagram: Typical call sequence of offering, execution of the recovery handler, and deactivation. Sources: [SWS_PHM_01142], [SWS_PHM_01143], [SWS_PHM_01144]

Error Scenarios

When working with ara::phm::RecoveryAction, errors and violations can occur at different levels:

  • Construction violations (Violations): During object creation, the constructor checks the model and process configuration. If these checks fail, specific violations are triggered [SWS_PHM_01141]:
    • AraNotInitializedViolation: The runtime environment ara was not initialized prior to calling the constructor [SWS_PHM_01141].
    • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the model context of the executable or does not reference a PortPrototype [SWS_PHM_01141].
    • PortInterfaceMappingViolation: The referenced PortPrototype is not typed by a PhmSupervisionRecoveryNotificationInterface in the mapping [SWS_PHM_01141].
    • ProcessMappingViolation: For the matching InstanceRef, no corresponding process exists in the model that matches the current runtime process [SWS_PHM_01141].
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already in use within this process [SWS_PHM_01141].
  • Offering failure: If registration fails when calling Offer() due to disrupted communication with the Phm-Daemon, the function returns a ara::core::Result<void> with the error code PhmErrc::kOfferFailed (rollback semantics) [SWS_PHM_01143].
  • Unrecoverable monitoring errors: If the State Management or the derived class cannot handle the reported error, the error code PhmErrc::kSMCanNotHandleRecovery is reported via the returned Future [SWS_PHM_01142]. In this case, rollback semantics take effect, in which the Platform Health Management takes control and triggers the hardware watchdog [SWS_PHM_01142].

<h4>Context</h4>
<p>The class <code>ara::phm::RecoveryAction</code> is a fundamental abstract base class within the module <code>phm</code> (Platform Health Management) of the AUTOSAR Adaptive Platform. Its central responsibility is to provide a standardized interface through which the Platform Health Management can request recovery and remediation actions if a system health monitoring fails <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</p>
<p>The class acts as a link between platform monitoring and the application-specific error response. In typical system architectures, it is derived by higher-level functional components such as State Management in order to respond specifically to detected errors and, for example, transition affected processes or function groups into safe states <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</p>
<p>Essentially three components are involved in the interaction:</p>
<ul>
<li><strong>Application / State Management:</strong> Derives from <code>ara::phm::RecoveryAction</code>, implements the pure virtual method <code>RecoveryHandler</code>, and executes the concrete recovery logic <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</li>
<li><strong>RecoveryAction instance:</strong> Binds the recovery action to a modeled port and encapsulates the control of the readiness to receive via <code>Offer</code> and <code>StopOffer</code> <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01144" href="../spec/record.html?id=SWS_PHM_01144">[SWS_PHM_01144]</a>.</li>
<li><strong>Phm-Daemon / Platform Health Management:</strong> Detects errors in elementary monitorings, triggers registered recovery actions via the handler, and triggers the watchdog in the event of unrecoverable errors <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>. In addition, the type <code>ara::exec::ExecutionErrorEvent</code> from Execution Management provides the detailed context data of the error <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</li>
</ul>

<h4>Lifecycle</h4>
<p>An instance of <code>ara::phm::RecoveryAction</code> is created via its explicit constructor, which accepts a <code>ara::core::InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>. This identifier must reference a modeled <code>PPortPrototype</code> that is linked to a <code>PhmSupervisionRecoveryNotificationInterface</code> via a <code>RecoveryNotificationToPPortPrototypeMapping</code> <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>. The constructor is specified as exception safe (<em>exception safe</em>) and thread-safe (<em>thread-safe</em>) <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</p>
<p>Copy and move operations are completely prohibited for <code>ara::phm::RecoveryAction</code>:</p>
<ul>
<li>Both the copy constructor and the copy assignment operator are deleted (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_PHM_01150" href="../spec/record.html?id=SWS_PHM_01150">[SWS_PHM_01150]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01152" href="../spec/record.html?id=SWS_PHM_01152">[SWS_PHM_01152]</a>.</li>
<li>Likewise, the move constructor and the move assignment operator are explicitly deleted (<code>= delete</code>) <a class="spec-record-ref" data-req="SWS_PHM_01149" href="../spec/record.html?id=SWS_PHM_01149">[SWS_PHM_01149]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01151" href="../spec/record.html?id=SWS_PHM_01151">[SWS_PHM_01151]</a>. This prevents a move operation, after offering has occurred (<code>Offer</code>), from leading to a premature call of the <code>RecoveryHandler</code> before the derived class is completely constructed, which could lead to undefined behavior or unhandled exceptions and compromise system safety <a class="spec-record-ref" data-req="SWS_PHM_01149" href="../spec/record.html?id=SWS_PHM_01149">[SWS_PHM_01149]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01151" href="../spec/record.html?id=SWS_PHM_01151">[SWS_PHM_01151]</a>.</li>
</ul>
<p>After construction, the instance is initially in an inactive state. Only calling <code>Offer()</code> activates the readiness for potential calls of the <code>RecoveryHandler</code> by the Phm-Daemon <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>. This readiness can be deactivated again at any time via <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_PHM_01144" href="../spec/record.html?id=SWS_PHM_01144">[SWS_PHM_01144]</a>.</p>
<p>The lifecycle ends with the call of the virtual destructor <code>~RecoveryAction()</code> <a class="spec-record-ref" data-req="SWS_PHM_01145" href="../spec/record.html?id=SWS_PHM_01145">[SWS_PHM_01145]</a>. While construction and handler execution are thread-safe, <code>Offer()</code>, <code>StopOffer()</code>, and the destructor are not thread-safe (<em>not thread-safe</em>) <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01144" href="../spec/record.html?id=SWS_PHM_01144">[SWS_PHM_01144]</a>, <a class="spec-record-ref" data-req="SWS_PHM_01145" href="../spec/record.html?id=SWS_PHM_01145">[SWS_PHM_01145]</a>. Interpretation: Prior to destroying the object, <code>StopOffer()</code> would typically be called to ensure that no asynchronous handler calls take place anymore during object teardown.</p>

<h4>Usage Path</h4>
<p>The regular procedure for using a recovery action is divided into the following steps:</p>
<ol>
<li><strong>Derivation and instantiation:</strong> The application-specific component derives from <code>ara::phm::RecoveryAction</code>, implements the method <code>RecoveryHandler</code> <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>, and instantiates the object with the appropriate <code>InstanceSpecifier</code> <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
<li><strong>Offering:</strong> The application calls <code>Offer()</code> to perform registration with the Phm-Daemon and enable incoming recovery requests <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>. Prior to this call, no handler call may be made by the PHM <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</li>
<li><strong>Execution of error handling:</strong> If an elementary monitoring fails, the Phm-Daemon calls the method <code>RecoveryHandler</code> and passes the error information (<code>executionError</code>) as well as the affected monitoring type (<code>supervision</code>) <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</li>
<li><strong>Asynchronous feedback:</strong> The implementation returns a <code>ara::core::Future&lt;void&gt;</code>, which is fulfilled empty (<code>void</code>) upon successful recovery or transports the error code <code>PhmErrc::kSMCanNotHandleRecovery</code> in the event of an error <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.</li>
<li><strong>Deactivation:</strong> If the action is no longer required, the application calls <code>StopOffer()</code>, which prevents future handler calls <a class="spec-record-ref" data-req="SWS_PHM_01144" href="../spec/record.html?id=SWS_PHM_01144">[SWS_PHM_01144]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>When working with <code>ara::phm::RecoveryAction</code>, errors and violations can occur at different levels:</p>
<ul>
<li><strong>Construction violations (Violations):</strong> During object creation, the constructor checks the model and process configuration. If these checks fail, specific violations are triggered <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>:
  <ul>
  <li><code>AraNotInitializedViolation</code>: The runtime environment <code>ara</code> was not initialized prior to calling the constructor <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
  <li><code>InstanceSpecifierMappingIntegrityViolation</code>: The <code>InstanceSpecifier</code> cannot be resolved in the model context of the executable or does not reference a <code>PortPrototype</code> <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
  <li><code>PortInterfaceMappingViolation</code>: The referenced <code>PortPrototype</code> is not typed by a <code>PhmSupervisionRecoveryNotificationInterface</code> in the mapping <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
  <li><code>ProcessMappingViolation</code>: For the matching <code>InstanceRef</code>, no corresponding process exists in the model that matches the current runtime process <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
  <li><code>InstanceSpecifierAlreadyInUseViolation</code>: The <code>InstanceSpecifier</code> is already in use within this process <a class="spec-record-ref" data-req="SWS_PHM_01141" href="../spec/record.html?id=SWS_PHM_01141">[SWS_PHM_01141]</a>.</li>
  </ul>
</li>
<li><strong>Offering failure:</strong> If registration fails when calling <code>Offer()</code> due to disrupted communication with the Phm-Daemon, the function returns a <code>ara::core::Result&lt;void&gt;</code> with the error code <code>PhmErrc::kOfferFailed</code> (rollback semantics) <a class="spec-record-ref" data-req="SWS_PHM_01143" href="../spec/record.html?id=SWS_PHM_01143">[SWS_PHM_01143]</a>.</li>
<li><strong>Unrecoverable monitoring errors:</strong> If the State Management or the derived class cannot handle the reported error, the error code <code>PhmErrc::kSMCanNotHandleRecovery</code> is reported via the returned <code>Future</code> <a class="spec-record-ref" data-req="SWS_PHM_01142" href="../spec/record.html?id=SWS_PHM_01142">[SWS_PHM_01142]</a>.
