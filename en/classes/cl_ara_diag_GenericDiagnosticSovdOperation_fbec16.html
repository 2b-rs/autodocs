Enables applications to process and respond to generic SOVD operation requests from the Diagnostic Manager.

The base class serves to implement generic SOVD operation handlers for processing execution requests in Diagnostic Management [SWS_DM_02203]. After instantiation, the application activates reception via Offer(), whereupon the Diagnostic Manager forwards incoming requests via the asynchronous interface StartExecution [SWS_DM_02174] [SWS_DM_02210]. Passed payload data and the cancellation handler are strictly bound to the duration of the operation [SWS_DM_02210].

Context

The class ara::diag::GenericDiagnosticSovdOperation provides a generic interface for executing operations in the context of ASAM SOVD (Service-Oriented Vehicle Diagnostics) [SWS_DM_02203]. It acts as a link between the diagnostic platform and the application-specific implementation of diagnostic routines or actions. When an external SOVD client requests an operation execution, the Diagnostic Server instance provides the corresponding SOVD method AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 “Operations – Start execution of an operation” [SWS_DM_01396]. As soon as authorization or verification of a required proximity challenge has been successfully completed, the Diagnostic Manager (DM) forwards the call to the method StartExecution of the registered handler instance [SWS_DM_02174].

Lifecycle

Creation of an instance is performed via the constructor by specifying an ara::core::InstanceSpecifier, which references a PortPrototype, and a concurrency type (ConcurrencyType) [SWS_DM_02204]. Since the move constructor [SWS_DM_02206] and move assignment operator [SWS_DM_02207] are declared as protected, the class is designed as a base class for derived application-specific handlers. After instantiation, the object is in the inactive state and does not accept any requests. Forwarding of requests by the Diagnostic Manager is activated via Offer() [SWS_DM_02211]. This forwarding can be deactivated again with StopOffer() [SWS_DM_02212]. During destruction of the instance, the virtual destructor ensures proper cleanup [SWS_DM_02205]. The constructor, destructor, and move operations are specified as thread-safe, whereas Offer() and StopOffer() are not thread-safe and should typically be called during the initialization or shutdown phase of the process.

State diagram: Lifecycle states of handler registration. Sources: [SWS_DM_02204], [SWS_DM_02211], [SWS_DM_02212], [SWS_DM_02205]

Usage Path

The regular sequence comprises offering the handler, accepting operation requests, and providing the response asynchronously:

  1. Offer service: The application calls Offer(), whereby the Diagnostic Manager is authorized to forward incoming SOVD requests to the object [SWS_DM_02211].
  2. Start operation: After arrival of the SOVD method and passed verification of the proximity challenge, the DM calls the pure virtual method StartExecution [SWS_DM_02174] [SWS_DM_02210]. In doing so, the name of the SOVD operation (sovd_operation_name), payload data (sovd_content_data), meta information (meta_info), and a CancellationHandler are passed [SWS_DM_02210].
  3. Return result: The method returns a ara::core::Future that contains either a synchronous response (StartSynchronousExecutionResponse) or an asynchronous response (StartAsynchronousExecutionResponse) [SWS_DM_02210]. In the case of a synchronous operation, the DM adopts the data from the result to generate the SOVD response body [SWS_DM_02176].
  4. Stop service: Prior to destruction of the object, the application stops forwarding by means of StopOffer() [SWS_DM_02212].

Sequence diagram: Typical sequence of an SOVD operation execution via StartExecution. Sources: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02210], [SWS_DM_02211]

Error Scenarios

When using the interface, administrative as well as protocol-specific errors can occur:

  • Already offered: Calling Offer() again on an already offered instance fails with the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_02211].
  • SOVD error: If the execution of the operation fails, a corresponding negative response code according to ISO 17978-3 or ASAM SOVD 1.1 must be returned in ara::core::Future [SWS_DM_02210].
  • Cancellation: The application is notified via the passed object cancellation_handler if the ongoing request is cancelled. The specification explicitly prohibits storing or accessing this handler beyond the lifetime of the ongoing operation [SWS_DM_02210]. In addition, the passed input data in sovd_content_data remain valid only until the associated promise has been fulfilled or processing has been cancelled [SWS_DM_02210].

          The method Offer of class ara::diag::GenericDiagnosticSovdOperation enables the forwarding of incoming diagnostic and service requests from Diagnostic Management (DM) to the respective handler [SWS_DM_02211]. The function takes no parameters, declares noexcept, and returns an ara::core::Result<void> [SWS_DM_02211]. Interpretation: Since no ara::core::Future is returned, activation of forwarding is likely completed synchronously during the method call.
          


          Regarding error handling, the interface guarantees rollback semantics [SWS_DM_02211]. If the service was already offered for this handler instance previously, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_02211]. This error state corresponds to the failure scenario defined in diagnostic error domains for multiple registrations [SWS_DM_00514].
          


          For concurrency and the invocation context, the following constraints apply:
          

            

          • Thread safety: The operation is specified as not thread-safe, but exception safe [SWS_DM_02211]. Concurrent invocations on the same handler instance must be synchronized on the application side.
            • 

          • State ordering: Offer must be called before forwarding requests [SWS_DM_02211]. Calling it again without revoking it in the meantime leads to an error.
            • 

          


          In the overall system, Offer follows the uniform offering pattern of Adaptive Diagnostic Management, as defined analogously for generic routines [SWS_DM_00557], UDS services [SWS_DM_00619], or communication controls [SWS_DM_00809]. This principle is specifically designed for ara::diag and must not be confused with service offering in ara::com (SWS Diagnostics §7.3.4.1.2 “Monitors”).

              The interface StartExecution of class ara::diag::GenericDiagnosticSovdOperation serves to start an SOVD operation on the Diagnostic Server [SWS_DM_02210]. Diagnostic Management calls the method as soon as a corresponding SOVD request has been received and any required validation of the proximity_challenge according to [SWS_DM_02173] was successful ([SWS_DM_02174], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.5.5 “Operations – Start execution of an operation”).
              

              The parameters of the method include:
              

                

              • sovd_operation_name: Name of the SOVD operation to be executed [SWS_DM_02210].
                • 

              • sovd_content_data: Input data of the operation, which remains valid until the associated promise is fulfilled or processing is canceled via the cancellation handler [SWS_DM_02210].
                • 

              • meta_info: Additional meta-information regarding the diagnostic context [SWS_DM_02210].
                • 

              • cancellation_handler: Reports a cancellation of the ongoing request; this object must not be stored or referenced beyond the lifetime of the operation [SWS_DM_02210].
                • 

              

              As return value, the function provides an ara::core::Future with an ara::core::Variant from StartSynchronousExecutionResponse or StartAsynchronousExecutionResponse [SWS_DM_02210]. In case of synchronous execution, Diagnostic Management sets the parameters in the SOVD response body from the content data of the response [SWS_DM_02176]. In case of asynchronous processing, Diagnostic Management assigns a unique identifier (id) to identify the running operation and sets the execution status [SWS_DM_02177].
              

              In case of an error, a negative response with an applicable SOVD error code according to ISO 17978-3 or ASAM SOVD 1.1 is returned via the Future [SWS_DM_02210]. Regarding concurrency and safety, the method is defined as thread-safe and exception safe ([SWS_DM_02210], AUTOSAR_AP_SWS_Diagnostics §8.62.2.1.3.2 “StartExecution”).
