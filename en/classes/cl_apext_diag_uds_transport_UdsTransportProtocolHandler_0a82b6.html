Context

The class apext::diag::uds_transport::UdsTransportProtocolHandler is the abstract base class for specific and proprietary UDS transport protocol plugins in Diagnostic Management (DM) of AUTOSAR Adaptive (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). It decouples the generic diagnostic core from the peculiarities of concrete transmission networks and transport layers such as DoIP or CAN-based protocols.

A transport handler essentially interacts with three partners:

  • Diagnostic Management Core: The DM manages the entire lifecycle of the handler and provides the peer for status and data indications via the manager reference apext::diag::uds_transport::UdsTransportProtocolMgr ([SWS_DM_09015], [SWS_DM_09025]).
  • Network layer and diagnostic client: The plugin handles the physical or logical data exchange with the external or internal diagnostic tester ([SWS_DM_00326], [SWS_DM_00351]).
  • Periodic handler (optional): If the respective transport protocol supports periodic transmissions, the handler provides a reference to a UdsTransportProtocolPeriodicHandler via GetPeriodicHandler() ([SWS_DM_01068]).

Lifecycle

The lifecycle of a transport protocol implementation is strictly controlled by the DM (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”, [SWS_DM_00329]). Creation takes place via the constructor UdsTransportProtocolHandler(handlerId, transportProtocolMgr), in which the DM assigns the handler a unique identifier of type UdsTransportProtocolHandlerID and the reference to the associated UdsTransportProtocolMgr ([SWS_DM_09015], [SWS_DM_09025]). The assigned ID can be queried at any time via GetHandlerID() ([SWS_DM_00325]). The constructor is designated as thread-safe ([SWS_DM_09015]).

To decouple complex protocol initializations from the constructor, the DM subsequently calls Initialize() ([SWS_DM_00319], [SWS_DM_00329]). Except for GetPeriodicHandler(), the DM must not call any other methods of the handler before a successful return of InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). After successful initialization, the DM starts the protocol via Start() ([SWS_DM_00322]). Because Start() is executed asynchronously, the DM can start multiple handlers in parallel to minimize startup time ([SWS_DM_00322]).

When the DM application transitions to the ApplicationState.kTerminating state, it calls Stop() (AUTOSAR_AP_SWS_Diagnostics §7.1.1.1, [SWS_DM_00333], [SWS_DM_00323]). The DM waits until the handler confirms the stop via UdsTransportProtocolMgr::HandlerStopped(handlerId) ([SWS_DM_00340]). After the return from Stop(), the handler plugin must not call any further methods on the manager—with the sole exception of the acknowledgement HandlerStopped() ([SWS_DM_01741], [SWS_DM_00323]). The subsequent teardown takes place via the virtual destructor ([SWS_DM_09016]).

State diagram: Lifecycle phases and transition conditions of a UDS transport protocol handler. Sources: [SWS_DM_00329], [SWS_DM_00319], [SWS_DM_01746], [SWS_DM_01745], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00340].

Usage Path

In ongoing operation, the handler performs the bidirectional exchange of UDS messages:

  1. Message reception (indication): As soon as a new UDS message is received on a channel and the source address, target address, addressing type (physical or functional), total message length, and the first payload bytes (at least two bytes for messages larger than one byte) are known, the plugin calls UdsTransportProtocolMgr::IndicateMessage(...) (AUTOSAR_AP_SWS_Diagnostics §7.1.1.2 “Indication of UDS message reception”, [SWS_DM_00342], [SWS_DM_00330]). In doing so, the handler passes the channel identification in parameter globalChannelId (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”).
  2. Message transmission (transmission): The DM sends the associated UDS diagnostic response back via the same handler and the same channel (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”, [SWS_DM_00348]). To do so, it calls Transmit(message, channelId) ([SWS_DM_00327]). The message is passed to the handler as UdsMessageConstPtr in the manner of a std::unique_ptr.
  3. Transmission acknowledgement: As soon as the message has been sent over the network (or an error occurred), the handler must return ownership of message to the DM via UdsTransportProtocolMgr::TransmitConfirmation(result, message) ([SWS_DM_00327]). The result is transmitted as kTransmitOk or kTransmitFailed (AUTOSAR_AP_SWS_Diagnostics §7.1.1.3, [SWS_DM_00351]).

Another specific usage path is the restoration of channels after an ECU reset (UDS service 0x11 with positive response after reset): Here, the DM calls NotifyReestablishment(channelId) before the restart ([SWS_DM_00326]). The plugin persistently stores the connection parameters (for example, IP addresses and ports). After restarting via Start(), the plugin detects the reconnection of the same diagnostic client and informs the DM via UdsTransportProtocolMgr::ChannelReestablished(...) ([SWS_DM_00326], [SWS_DM_01744]).

Sequence diagram: UDS message reception, response transmission, and subsequent acknowledgement. Sources: [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00327], [SWS_DM_00351].

Error Scenarios

The interface handles various exception and error situations:

  • Failed initialization: If Initialize() returns the value InitializationResult::kInitializeFailed ([SWS_DM_09017]), the DM completely aborts the startup process of this transport protocol and does not call any further methods on this instance ([SWS_DM_01745]).
  • Unsupported periodic transmissions: If the concrete protocol does not support periodic transmissions, calling GetPeriodicHandler() returns a ara::core::Result with the error code kConfigurationMismatch ([SWS_DM_01068]).
  • Rejection of channel restoration: If a plugin cannot satisfy the persistent reservation for a channel (for example, in the absence of a non-volatile storage option or unstable mapping), NotifyReestablishment(channelId) returns the value false ([SWS_DM_00326]).
  • Transmission error in the network: If the network layer was unable to send a message requested via Transmit(), the handler must pass the result kTransmitFailed in TransmitConfirmation ([SWS_DM_00351]). Failing to return the buffer leads to resource leaks in the DM.
  • Sequence violation after stopping: If a plugin calls a method other than HandlerStopped() on UdsTransportProtocolMgr after returning from Stop(), this constitutes a violation of the protocol sequence ([SWS_DM_00323], [SWS_DM_01741]).

              function NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.
