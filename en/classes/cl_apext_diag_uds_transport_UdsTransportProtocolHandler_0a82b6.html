Serves as an abstract base class for UDS transport plugins to transmit and forward diagnostic messages.

The abstract class serves UDS transport plugins as a base interface for standardized integration into adaptive Diagnostic Management (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”). A derived implementation forwards received diagnostic messages to the protocol manager and transmits generated response messages via network-specific channels to the diagnostic tester. The lifecycle is subject to a strict sequence of creation, separate initialization, asynchronous start, and orderly stopping ([SWS_DM_00329]). Following instantiation, operational method calls are not thread-safe and require coordinated control by the diagnostic core.

Context

The class apext::diag::uds_transport::UdsTransportProtocolHandler is an abstract base class within the module diag of the AUTOSAR Adaptive Platform. It defines the standardized interface through which proprietary or protocol-specific UDS transport plugins are connected to adaptive Diagnostic Management (DM) (AUTOSAR_AP_SWS_Diagnostics §7.1.1 “Support of UDS Transport Layer”, [SWS_DM_00315]). Each concrete transport protocol—for example for diagnostics via automotive network media—implements this interface as a derived subclass. The DM is likely to exclusively own and manage the respective handler instance throughout its entire operational lifecycle. Interaction between the diagnostic core and the plugin takes place via the reference transportprotocolManager of type UdsTransportProtocolMgr&, which is passed in the constructor and stored protected ([SWS_DM_09015], [SWS_DM_09025]). Each handler is identified by a numerical UdsTransportProtocolHandlerID that can be queried via GetHandlerID() ([SWS_DM_00325]).

Lifecycle

The lifecycle of a UDS transport protocol handler is strictly controlled sequentially by the DM ([SWS_DM_00329]). Following instantiation via the constructor UdsTransportProtocolHandler ([SWS_DM_09015]), the method Initialize() separates the actual protocol initialization from object creation ([SWS_DM_00319]). Except for an optional query via GetPeriodicHandler(), the DM must not call any methods on the handler before the successful return of InitializationResult::kInitializeOk ([SWS_DM_01746], [SWS_DM_09017]). After successful initialization, calling Start() transitions the handler into the active processing state ([SWS_DM_00322]). To minimize startup time, Start() is designed as an asynchronous operation; the DM is likely to coordinate the parallel start of multiple handlers internally. If the DM transitions to the state ApplicationState.kTerminating during shutdown, it instructs the handler to terminate via Stop() ([SWS_DM_00323], [SWS_DM_00333]). The DM waits for completion, which the handler acknowledges by calling UdsTransportProtocolMgr::HandlerStopped() ([SWS_DM_00340]). After returning from Stop(), the plugin is prohibited from making any method calls to the manager except HandlerStopped() ([SWS_DM_01741]). Finally, release of resources takes place via the virtual destructor ([SWS_DM_09016]). While the constructor is thread-safe, the operational interface methods are declared not thread-safe.

State diagram: Lifecycle phases and state transitions of a UDS transport handler. Sources: [SWS_DM_00319], [SWS_DM_00322], [SWS_DM_00323], [SWS_DM_00329], [SWS_DM_01745], [SWS_DM_01746]

Usage Path

During regular diagnostic operation, the handler processes incoming messages and transmits responses. As soon as at least source address, target address, address type (physical or functional), total message length, and, for multi-byte payloads, the first two bytes (payloadInfo) are available at the network interface, the implementation indicates the request to the manager via UdsTransportProtocolMgr::IndicateMessage() ([SWS_DM_00342], AUTOSAR_AP_SWS_Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”). Each request is assigned to a unique channel (AUTOSAR_AP_SWS_Diagnostics §7.1.1.4 “Channel Notifications”). To provide a response, the DM passes the diagnostic response to the same handler and channel using Transmit(message, channelId) ([SWS_DM_00327], [SWS_DM_00348]). Following physical transmission, the handler returns the passed message object to the manager via UdsTransportProtocolMgr::TransmitConfirmation() ([SWS_DM_00327], [SWS_DM_00351]). A specialized usage path involves ECU resets (UDS service 0x11) with a positive response after the restart: here, prior to the reset, the DM requests via NotifyReestablishment(channelId) that the handler preserve the connection information non-volatilely; following restart and renewed Start(), the handler indicates the restoration of the same channel via ChannelReestablished() ([SWS_DM_00326], [SWS_DM_01744]).

Sequence diagram: Sequence of UDS message indication and response transmission. Sources: [SWS_DM_00327], [SWS_DM_00342], [SWS_DM_00348], [SWS_DM_00351]

Error Scenarios

If initialization of the transport layer fails and Initialize() returns the status InitializationResult::kInitializeFailed, the DM immediately aborts the startup process of this protocol and does not call any further methods on this instance ([SWS_DM_01745], [SWS_DM_09017]). If periodic transmissions are not supported on the transport protocol, calling GetPeriodicHandler() returns a ara::core::Result with the error code kConfigurationMismatch ([SWS_DM_01068]). If a requested channel restoration for an ECU reset cannot be guaranteed, NotifyReestablishment() fails and signals this via the return value false ([SWS_DM_00326]). Finally, if the transmission process of a diagnostic response fails on the network layer, the handler must notify the manager during confirmation by setting the argument result in TransmitConfirmation() to kTransmitFailed ([SWS_DM_00351]).

          The pure virtual method Initialize serves for the explicit initialization of an instance of apext::diag::uds_transport::UdsTransportProtocolHandler and formally separates this process from the construction of the object [SWS_DM_00319]. It is called synchronously and without parameters by the Diagnostic Manager (DM), throws no exceptions (noexcept), and returns a InitializationResult [SWS_DM_00319] [SWS_DM_09017].
          

          Life cycle and concurrency
          

          The call is embedded in the lifecycle management of the UDS transport layer AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”. The DM must manage the phases in a fixed order: construction, call of Initialize, start via Start, and termination via Stop [SWS_DM_00329]. The method is specified as not thread-safe (not thread-safe) [SWS_DM_00319]; the DM is therefore likely to execute it as part of a synchronous initialization phase without concurrent accesses.

              function NotifyReestablishment [SWS_DM_00326] Upstream: RS_Diag_04147, RS_Diag_04168
              

              virtual bool NotifyReestablishment (ChannelID channelId) noexcept=0;
              

              Tells the UdsTransportProtocolHandler, to notify the DM core via UdsTransportProtocol Mgr::ChannelReestablished() if the given channel has been re-established after next Uds TransportProtocolHandler::Start(). The main purpose of this method is to allow the DM to provide an ECU-Reset (0x11 service), with configuration option "positive response AFTER reset". In this scenario, the request for 0x11 will be received on a certain channel (GlobalChannel Identifier), then the ECU-Reset takes place and after ECU-Restart, all UdsProtocol Handlers/-plugins get restarted via call to UdsTransportProtocolHandler::Start().
              Now there are two expectations, when this method has been called before and returned "TRUE": If the same remote client connects to the UdsProtocolHandler, it shall get a channel identification with the same identifying as the last time. It consecutively calls UdsTransportProtocolMgr::ChannelReestablished(Global ChannelIdentifier).
              The detection/decision, whether the "same" client reconnects as before is an UdsProtocol Handler implementation specific decision.
              The general expectation is:
              If the channel is set up from exactly the same remote network-endpoint, it typically gets the same ChannelID. To support this functionality, the implementation at least has to store non-volatile, that this notification has to be done. Further it might be needed to store some additional connection specific info non-volatile to make sure, that the same ChannelID can be reassigned. This is the case if the mapping of protocol specific channel info -> channelID isn’t a
              stable bijective mapping!
              Small example:
              The underlying network protocol, which UdsProtocolHandler implements is based on TCP. At the point in time, where the 0x11 Service Identifier request is received on channel identified by the DM calls UdsTransportProtocolHandler::NotifyReestablishment() on this ChannelID.
              Now the implementation of UdsProtocolHandler stores non-volatile in the context of this call:
              • NetworkEndpoint (IP-address and port number) of the channel. • NetworkEndpoint (IP-address and port number) of the local port (because in this example, the UdsTransportProtocolHandler listens on/supports different ports). • ChannelID it has currently assigned. After restart this ChannelID is only reused for a channel with exactly the same Network Endpoint addresses as stored non-volatile.
              If this ChannelID then gets reassigned, then UdsTransportProtocolMgr::Channel Reestablished() has to be called.

The boolean return value signals with true that the notification request was accepted and can be fulfilled; otherwise, false is returned ([SWS_DM_00326]).

                •

                  Method Start of interface apext::diag::uds_transport::UdsTransportProtocolHandler starts protocol processing of a UDS transport plugin in Diagnostic Management (DM) according to [SWS_DM_00322]. It takes no parameters and returns no value. Execution is designed to be asynchronous so that DM can start multiple instances in parallel and thus reduce the startup time of the overall system ([SWS_DM_00322]). Since the signature declares void, asynchronous processing is likely handled stack-specifically via internal background mechanisms.
                  
  
                  With regard to the lifecycle (SWS Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer”, [SWS_DM_00329]), strict sequencing conditions apply:
                  
  
                    
    
                  • Preconditions: Prior to the call, initialization via Initialize ([SWS_DM_00319]) must have been completed with the result kInitializeOk ([SWS_DM_01746]). If initialization yields kInitializeFailed instead, DM aborts the procedure and must not call Start ([SWS_DM_01745]).
                    • 
    
                  • Postconditions: Only after Start has been called may DM trigger downstream functions such as Transmit or Stop on the handler ([SWS_DM_01743]). In addition, DM processes notifications via ChannelReestablished ([SWS_DM_00313]) exclusively if Start was executed beforehand ([SWS_DM_01744]), which is essential, among other things, for ECU reset scenarios with reconnection ([SWS_DM_00326]).
                    • 
  
                  
  
                  The method is declared as noexcept and thus exception-safe, but explicitly specified as not thread-safe (not thread-safe) ([SWS_DM_00322]). Callers must therefore ensure that instance calls occur synchronously.

                      The method Stop of the interface apext::diag::uds_transport::UdsTransportProtocolHandler signals to a UDS transport protocol instance that it should terminate [SWS_DM_00323]. The call is triggered by Diagnostic Management (DM) as soon as it transitions to the state ApplicationState.kTerminating [SWS_DM_00333]. The function takes no parameters, has no return value, is declared as noexcept, and is specified as exception-safe (exception safe) [SWS_DM_00323].
                      

                      The following conditions apply to the call context and concurrency:
                      

                        

                      • Calling order: According to the lifecycle of a transport protocol, the DM may call the method Stop only after the instance was previously put into operation with Start [SWS_DM_01743] AUTOSAR_AP_SWS_Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer” [SWS_DM_00329].
                        • 

                      • Concurrency: The operation is specified as not thread-safe (not thread-safe) [SWS_DM_00323].
                        • 

                      • Call restriction: After returning from Stop, the handler plugin must not call any further methods on apext::diag::uds_transport::UdsTransportProtocolMgr, with the sole exception of the acknowledgment HandlerStopped [SWS_DM_01741] [SWS_DM_00323].
                        • 

                      

                      Interaction with the DM occurs asynchronously: After the handler has terminated its network connections and released resources, it must notify the DM via apext::diag::uds_transport::UdsTransportProtocolMgr::HandlerStopped while passing its handlerId [SWS_DM_00314]. After calling Stop, the DM strictly waits for this confirmation callback before finally terminating the process [SWS_DM_00340].

                          Method Transmit is called to send a diagnostic UDS message to the network via a specific channel of the transport protocol ([SWS_DM_00327], SWS Diagnostics §7.1.1.3 “UDS message transmission on a UDS TransportLayer”). It maps service T_Data.req according to ISO 14229-2 ([SWS_DM_00327]). The caller passes the message to be transmitted as UdsMessageConstPtr in the ownership style of a unique_ptr as well as the channelId, which must correspond to the channel of the previously received request ([SWS_DM_00327], [SWS_DM_00348], SWS Diagnostics §7.1.1.4 “Channel Notifications”).
                          


                          Regarding ordering and lifecycle, the Diagnostic Manager must not call Transmit until initialization of the handler with kInitializeOk has been completed ([SWS_DM_01746]) and method Start has been called ([SWS_DM_01743]). Since the operation is specified as not thread-safe and exception safe ([SWS_DM_00327]), coordination of parallel transmit requests is, according to interpretation, likely required to take place on the caller side in the Diagnostic Manager.
                          


                          The function synchronously returns no value. The transport handler is required to return the message pointer asynchronously to the Diagnostic Manager via apext::diag::uds_transport::UdsTransportProtocolMgr::TransmitConfirmation after transmission ([SWS_DM_00327], [SWS_DM_00312]). Upon successful transmission at network level, the result kTransmitOk is reported, otherwise kTransmitFailed ([SWS_DM_00351]).
