class ara::per::SharedHandle

[SWS_PER_00362] Upstream: RS_PER_00002, RS_AP_00122, RS_AP_00140

template <typename T> class SharedHandle final {...};

Handle to a File Storage or Key-Value Storage. A SharedHandle is returned by the functions OpenFileStorage() and OpenKeyValueStorage() and can be passed between threads as needed. It provides the abstraction that is necessary to allow thread-safe implementation of OpenFile Storage() and OpenKeyValueStorage().

Context

The template class ara::per::SharedHandle serves in the persistence module (ara::per) as a smart access handle to instances of the file or key-value storage. As a generic abstraction (template <typename T> class SharedHandle final), the class encapsulates the managed storage resource of type T and is provided as the return type of the functions OpenFileStorage() and OpenKeyValueStorage().

The primary task of SharedHandle is to enable the as-needed exchange of storage handles between different execution threads (“can be passed between threads as needed”). At the same time, the class provides the necessary abstraction to ensure a thread-safe implementation of the storage opening functions OpenFileStorage() and OpenKeyValueStorage(). The central interaction partners are calling application threads, the storage-creating factory functions, and the encapsulated storage object.

Lifecycle

The lifecycle of a SharedHandle typically begins with its return by OpenFileStorage() or OpenKeyValueStorage(). Alternatively, a handle can be created from an existing instance via the copy constructor [SWS_PER_00369]. Interpretation: The class likely realizes a shared-ownership concept in which multiple handle instances jointly reference the same underlying storage.

In terms of its state, a handle is either in a valid state (when it represents a valid object of the template class) or in an empty state [SWS_PER_00398]. In particular, a handle transitions to the empty state when it is used as a source (sh) in a move construction [SWS_PER_00367] or a move assignment [SWS_PER_00368]. In both cases, the source object is invalidated and may no longer be used for storage accesses [SWS_PER_00367], [SWS_PER_00368]. An empty handle can be returned to the valid state by a copy assignment [SWS_PER_00370] or a move assignment [SWS_PER_00368] with a valid handle.

The release of the handle instance occurs deterministically via the destructor ~SharedHandle() [SWS_PER_00568] upon leaving the respective scope. For concurrency, a clear distinction applies: Querying the state via operator bool() [SWS_PER_00398] as well as dereferencing via operator*() [SWS_PER_00402], [SWS_PER_00403] and operator->() [SWS_PER_00363], [SWS_PER_00364] are thread-safe (thread-safe). In contrast, modifying operations on the same handle instance—namely the assignment operators [SWS_PER_00368], [SWS_PER_00370] and the destructor [SWS_PER_00568]—are specified as not thread-safe (not thread-safe).

Usage Path

A typical usage path for SharedHandle comprises the following steps:

  1. Obtain handle: The application calls OpenFileStorage() or OpenKeyValueStorage() and receives the resulting instance of SharedHandle<T>.
  2. Check state: Prior to using access operators, the state is checked via the explicit conversion operator operator bool() [SWS_PER_00398]. This step is mandatory, especially after preceding move operations [SWS_PER_00367], [SWS_PER_00368].
  3. Access storage object: Via operator*(), the application receives a reference to the underlying object (non-const [SWS_PER_00402] or const [SWS_PER_00403]). Via the arrow operator operator->(), member functions of the encapsulated storage class can be executed directly (non-const [SWS_PER_00363] or const [SWS_PER_00364]).
  4. Thread transfer (optional): For division of labor, the handle can be copied ([SWS_PER_00369], [SWS_PER_00370]) or moved ([SWS_PER_00367], [SWS_PER_00368]) and passed to other threads.
  5. Resource cleanup: At the end of its lifetime, the handle instance is destroyed by ~SharedHandle() [SWS_PER_00568].

Error Scenarios

When using SharedHandle, the following preconditions and error scenarios must be observed:

  • Undefined behavior with empty handle: Calling operators other than operator bool() on an empty or invalidated handle leads to undefined behavior (“undefined behavior”) [SWS_PER_00398]. Therefore, the specification requires checking the state by means of operator bool() [SWS_PER_00367], [SWS_PER_00368] before using further operators.
  • Usage after move operation: As soon as a handle has been passed as an argument to the move constructor [SWS_PER_00367] or the move assignment operator [SWS_PER_00368], the source object is invalid and may no longer be used for storage accesses.
  • Exception safety: All member functions of SharedHandle—constructors ([SWS_PER_00367], [SWS_PER_00369]), assignment operators ([SWS_PER_00368], [SWS_PER_00370]), dereferencing operators ([SWS_PER_00363], [SWS_PER_00364], [SWS_PER_00402], [SWS_PER_00403]), status check [SWS_PER_00398], and destructor [SWS_PER_00568]—are annotated with noexcept and declared as exception safe. Error states are therefore not expressed in C++ exceptions, but in the logical handle state (operator bool() == false).
  • Data races during assignment or destruction: While read accesses to the referenced storage object are thread-safe ([SWS_PER_00363], [SWS_PER_00364], [SWS_PER_00402], [SWS_PER_00403], [SWS_PER_00398]), assignments ([SWS_PER_00368], [SWS_PER_00370]) and destruction [SWS_PER_00568] on the same handle instance must not be executed concurrently without protection.
