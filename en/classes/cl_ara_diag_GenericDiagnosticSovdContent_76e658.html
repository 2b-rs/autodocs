Context

In the AUTOSAR Adaptive Platform, the class ara::diag::GenericDiagnosticSovdContent provides the generic diagnostic interface for SOVD contents (Service-Oriented Vehicle Diagnostics) [SWS_DM_02186]. According to the specification, SOVD data is structurally modeled via DiagnosticSovdContent, which is composed of one or more DiagnosticSovdContentElement components SWS Diagnostics §7.3.3.3 “Definition of SOVD data”. Diagnostic Management (DM) uses this interface to read or write the complete diagnostic data using defined conversion rules SWS Diagnostics §7.3.3.3 “Definition of SOVD data”.

In the system architecture, the class acts as an intermediary layer between three key interaction partners: An external SOVD client sends standardized read or write requests to the vehicle SWS Diagnostics §7.3.3.3 “Definition of SOVD data”. The vehicle-side Diagnostic Management daemon processes these SOVD methods, handles protocol conversion, and forwards the standardized calls to the concrete implementation of GenericDiagnosticSovdContent [SWS_DM_01432], [SWS_DM_02166]. The diagnostic application implements the application-specific provision of the data.

Context diagram: Interaction partners and intermediary role of the GenericDiagnosticSovdContent interface. Sources: [SWS_DM_01432], [SWS_DM_02166], [SWS_DM_02186], SWS Diagnostics §7.3.3.3 “Definition of SOVD data”.

Lifecycle

The instantiation of GenericDiagnosticSovdContent takes place via the parameterized constructor by specifying an ara::core::InstanceSpecifier that references a DiagnosticDataIdentifierGenericInterface port, as well as a concurrency model of type SovdContentConcurrencyType [SWS_DM_02187]. Interpretation: Since the processing functions are declared as pure virtual and the move operations have protected visibility [SWS_DM_02189], [SWS_DM_02190], the class acts as an abstract base class for application-specific handlers.

After construction, the instance is in the Not Offered (Not Offered) state. The synchronous call of the Offer() method registers the service offer with the DM [SWS_DM_02193]. As soon as registration is successful, the object is in the Offered (Offered) state, in which the DM is permitted to delegate read and write requests to the instance. Calling StopOffer() deregisters the handler again and terminates the forwarding of requests by the DM [SWS_DM_02194]. Upon destruction, the virtual destructor ensures the proper release of all derived resources [SWS_DM_02188]. Regarding concurrency, all operations are defined as thread-safe and exception-safe (noexcept) [SWS_DM_02187], [SWS_DM_02193].

State diagram: Lifecycle and registration states of a GenericDiagnosticSovdContent instance. Sources: [SWS_DM_02187], [SWS_DM_02188], [SWS_DM_02193], [SWS_DM_02194].

Usage Path

The typical sequence comprises initialization, provision via the service interface, asynchronous responding to requests, and final deregistration:

  1. Offer service: After instantiation, the application calls Offer() [SWS_DM_02193]. The return value indicates the successful activation of forwarding in the DM.
  2. Process read access: If the DM receives the “Read a data resource” method via the SOVD protocol, it calls Read() on the instance [SWS_DM_01432]. The method receives the content name (sovd_content_name), meta-information (meta_info), and a cancellation_handler [SWS_DM_02191]. The application returns a ara::core::Future<DiagnosticSovdContentData>. As soon as the underlying promise is fulfilled with the data, the DM generates the SOVD response message with the corresponding element values [SWS_DM_01432].
  3. Process write access: If the “Write a data resource” method is configured for the SOVD data [SWS_DM_01431], the DM forwards incoming write operations to the handler via Write() [SWS_DM_02166]. In doing so, the converted contents are passed in the form of DiagnosticSovdContentData [SWS_DM_02166], [SWS_DM_02192]. Confirmation takes place asynchronously via a ara::core::Future<void> [SWS_DM_02192].
  4. Stop service: Before shutdown or in case of unavailability, the application calls StopOffer() [SWS_DM_02194].

Sequence diagram: Typical usage path from registration via read request to deregistration. Sources: [SWS_DM_01432], [SWS_DM_02191], [SWS_DM_02193], [SWS_DM_02194].

Error Scenarios

When using the interface, specific error conditions and preconditions must be observed:

  • Multiple offering: If Offer() is called while the service is already being offered, the method returns a ara::core::Result containing the error code DiagOfferErrc::kAlreadyOffered [SWS_DM_02193].
  • Failure of asynchronous operations: Since Read() and Write() are declared with noexcept, functional errors during request processing are not reported via C++ exceptions. Instead, the handler sets a corresponding SOVD error into the associated promise, which is transported in the resulting ara::core::Future [SWS_DM_02191], [SWS_DM_02192].
  • Cancellation and validity limits: The passed ara::diag::CancellationHandler indicates if an ongoing operation was cancelled prematurely [SWS_DM_02191], [SWS_DM_02192]. This object must explicitly not be stored or referenced beyond the execution duration of the respective operation [SWS_DM_02191]. In addition, the data sovd_abstract_content_data passed with Write() remains valid only until the associated promise is fulfilled or the operation is cancelled [SWS_DM_02192].

This guide is based on the AUTOSAR Adaptive R25-11 specification (diag module) and summarizes the context, lifecycle, interaction patterns, and error scenarios of the interface.
