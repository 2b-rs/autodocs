Enables monitoring, status querying, and clearing of diagnostic trouble codes for a memory destination.

The class ara::diag::DTCInformation enables adaptive applications to perform status-related monitoring, querying, and clearing of diagnostic trouble codes (DTCs) for a configured diagnostic memory destination ([SWS_DM_00664]). In addition to asynchronously reading the UDS DTC status byte and controlling the DTC status, the class supports registering event-driven notifiers and clearing fault memory entries via Clear ([SWS_DM_00671]). Instances are neither copyable nor movable; read operations are thread-safe, whereas modifying methods and notifier registrations must be synchronized.

Context

The class ara::diag::DTCInformation provides interfaces to perform operations on diagnostic trouble code information (Diagnostic Trouble Codes, DTCs) related to a configured diagnostic memory destination (DiagnosticMemoryDestination) ([SWS_DM_00664]). Within the AUTOSAR Adaptive Platform, it mediates between the adaptive application and Diagnostic Management (DM). Binding to the diagnostic interface takes place during construction via an ara::core::InstanceSpecifier, which must reference a port prototype of a DiagnosticDTCInformationInterface ([SWS_DM_00664]).

The core responsibilities of the class include querying fault status values such as the UDS DTC status byte ([SWS_DM_00666]), reading out the number of currently stored fault entries ([SWS_DM_00669]), monitoring memory overflow ([SWS_DM_00919]), as well as controlling and querying the status of DTC setting enablement in the context of UDS service 0x85 (ControlDTCSetting) ([SWS_DM_00672], [SWS_DM_00674]). In addition, the class enables targeted clearing of individual DTCs or entire DTC groups ([SWS_DM_00671]). With respect to the functional scope, defined limits exist in Diagnostic Management: according to AUTOSAR_AP_SWS_Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”, the DM supports neither OBD/WWH-OBD nor the UDS functionality of a mirror event memory.

Lifecycle

An instance of ara::diag::DTCInformation is created explicitly via its constructor by passing the modeled ara::core::InstanceSpecifier ([SWS_DM_00664]). The constructor is executed in a thread-safe manner ([SWS_DM_00664]). The class possesses strict semantics of uniqueness: copy constructor ([SWS_DM_01613]) and move constructor ([SWS_DM_01614]) as well as copy assignment operator ([SWS_DM_01611]) and move assignment operator ([SWS_DM_01612]) are deleted (=delete). An instance thus remains fixed at its creation location and can be neither copied nor moved. Furthermore, the same InstanceSpecifier must not be instantiated multiple times per process ([SWS_DM_00664]).

Destruction takes place via the destructor ~DTCInformation() ([SWS_DM_00665]). The destructor is not thread-safe ([SWS_DM_00665]). Regarding concurrency, the class differentiates between read and mutating operations: pure queries such as GetCurrentStatus ([SWS_DM_00666]), GetNumberOfStoredEntries ([SWS_DM_00669]), GetControlDTCStatus ([SWS_DM_00672]), and GetEventMemoryOverflow ([SWS_DM_00919]) are thread-safe. In contrast, modifying operations such as Clear ([SWS_DM_00671]) and EnableControlDtc ([SWS_DM_00674]) as well as all notifier registration methods are not thread-safe ([SWS_DM_00667], [SWS_DM_00668], [SWS_DM_00670], [SWS_DM_00673], [SWS_DM_00918]).

Usage Path

A typical use case is divided into the following phases:

  1. Instantiation: The application initializes the object by specifying the appropriate InstanceSpecifier ([SWS_DM_00664]).
  2. Callback configuration: The application registers notifiers for event-driven monitoring. Available callbacks are for DTC status changes (SetDTCStatusChangedNotifier with DtcStatusChangedNotifier) ([SWS_DM_00667], [SWS_DM_02122]), updates of snapshot records (SetSnapshotRecordUpdatedNotifier with SnapshotRecordUpdatedTypeNotifier) ([SWS_DM_00668], [SWS_DM_02123]), changes in the fault entry count (SetNumberOfStoredEntriesNotifier with NumberOfStoredEntriesNotifier) ([SWS_DM_00670], [SWS_DM_02124]), changes in the ControlDTC status (SetControlDtcStatusNotifier with ControlDtcStatusTypeNotifier) ([SWS_DM_00673], [SWS_DM_02125]), and memory overflows (SetEventMemoryOverflowNotifier with EventMemoryOverflowSetNotifier) ([SWS_DM_00918], [SWS_DM_02076]). Subsequent calls overwrite previously registered callbacks; these registrations are preferably to take place bundled during the initialization phase.
  3. Status queries: The application can query DTC information at any time. A call to GetCurrentStatus(dtc) returns a ara::core::Future<UdsDtcStatusByteType> ([SWS_DM_00666]). Additionally, GetNumberOfStoredEntries() ([SWS_DM_00669]) and GetControlDTCStatus() ([SWS_DM_00672]) are available asynchronously via future, as well as GetEventMemoryOverflow() ([SWS_DM_00919]) synchronously via ara::core::Result<bool>.
  4. Fault memory clearing and control: The application initiates the clearing of trouble codes via Clear(dtcGroup), which provides an asynchronous ara::core::Future<void> ([SWS_DM_00671]). If setting of DTCs is to be re-enabled, EnableControlDtc() activates the ControlDTC status ([SWS_DM_00674]).

Sequence diagram: Typical sequence of instantiation, notifier registration, status query, and fault clearing. Sources: [SWS_DM_00664], [SWS_DM_00667], [SWS_DM_00666], [SWS_DM_00671]

Error Scenarios

When working with ara::diag::DTCInformation, the following error possibilities are specified:

  • Configuration violations during construction: An incomplete or incorrect model binding leads to specific violations ([SWS_DM_00664]):
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved in the context of the executable or does not reference a PortPrototype.
    • PortInterfaceMappingViolation: The PortPrototype is not typed as DiagnosticDTCInformationInterface.
    • ProcessMappingViolation: No matching modeled process exists at runtime.
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by another instance in the running process.
  • Runtime errors during queries and memory clearing:
    • DiagErrc::kServiceNotAvailable: Essential functions of Diagnostic Management are temporarily unavailable; occurs with GetCurrentStatus ([SWS_DM_00666]), GetNumberOfStoredEntries ([SWS_DM_00669]), GetControlDTCStatus ([SWS_DM_00672]), GetEventMemoryOverflow ([SWS_DM_00919]), and Clear ([SWS_DM_00671]).
    • DiagErrc::kNoSuchDTC: No associated DTC exists for the requested event ([SWS_DM_00666]).
    • DiagErrc::kWrongDtc: An invalid DTC number was passed to Clear ([SWS_DM_00671]).
    • DiagErrc::kBusy: The interface is still busy with a previous processing ([SWS_DM_00671]).
    • DiagErrc::kMemoryError or DiagErrc::kFailed: Error accessing the physical fault memory or general processing errors during Clear ([SWS_DM_00671]).
  • Invalid arguments during notifier registration: The methods SetSnapshotRecordUpdatedNotifier ([SWS_DM_00668]), SetNumberOfStoredEntriesNotifier ([SWS_DM_00670]), SetControlDtcStatusNotifier ([SWS_DM_00673]), and SetEventMemoryOverflowNotifier ([SWS_DM_00918]) fail with DiagErrc::kInvalidArgument if an invalid function pointer or parameter is passed.

function Clear [SWS_DM_00671] Upstream: RS_AP_00119, RS_AP_00139, RS_Diag_04194

ara::core::Future< void > Clear (std::uint32_t dtcGroup) noexcept;

Method for Clearing a DTC or a group of DTCs.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 99369a404985 Provenance

The method Clear of class ara::diag::DTCInformation ([SWS_DM_00671]) serves to clear an individual DTC or a DTC group in the fault memory (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.6 “Service 0x14 – ClearDiagnosticInformation”). As a parameter, it accepts the identifier of the group or DTC to be cleared via dtcGroup and returns the result asynchronously as ara::core::Future<void> ([SWS_DM_00671]). The permission to clear individual DTCs or groups is subject to configuration parameters such as clearDtcLimitation ([SWS_DM_00160]).

Error Handling and Semantics

The function is declared as noexcept and reports errors asynchronously via the Future with rollback semantics ([SWS_DM_00671]). Possible error codes from DiagErrc are:

  • DiagErrc::kBusy: The interface is already busy with processing.
  • DiagErrc::kFailed: A general processing error occurred during execution.
  • DiagErrc::kMemoryError: A memory error occurred during processing.
  • DiagErrc::kWrongDtc: An invalid DTC number was passed.
  • DiagErrc::kServiceNotAvailable: Essential functions of the Diagnostic Manager are currently not available.

Concurrency and Distinction

The method is exception safe (exception safe), but explicitly classified as not thread-safe ([SWS_DM_00671]). Parallel calls on the same instance must therefore be synchronized by the caller; otherwise, DiagErrc::kBusy threatens. Interpretation: The returned ara::core::Future is likely to be fulfilled only when the physical fault memory has been completely cleared, analogously to the acknowledgment of UDS service 0x14 ([SWS_DM_00162]).

Functionally, the operation is to be distinguished from SOVD methods of the same name: While ara::diag::DiagnosticSovdContentElementDataView::Clear ([SWS_DM_02233]) clears data containers synchronously and thread-safe, this method controls diagnostic sequences in Diagnostic Management.
