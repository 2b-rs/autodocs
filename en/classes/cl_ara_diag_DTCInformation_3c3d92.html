Context

In AUTOSAR Adaptive (module diag), the class ara::diag::DTCInformation provides functional interfaces to perform operations and status queries on DTC (Diagnostic Trouble Code) information related to a configured diagnostic memory target (DiagnosticMemoryDestination) [SWS_DM_00664]. It serves as a link between the application-specific diagnostic and monitoring logic and the underlying Diagnostic Management (DM).

The primary interaction partners include the Adaptive Application, the internal memory management of the DM, and external diagnostic testers. The latter interact with the ECU in a standardized manner via UDS services such as Service 0x19 (ReadDTCInformation) or Service 0x85 (ControlDTCSetting), with the DM defining specific restrictions regarding supported subfunctions and memory areas AUTOSAR AP SWS Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”. The application uses ara::diag::DTCInformation to query DTC states, receive notifications upon status changes, inspect control states, and, if necessary, delete fault memory entries in a targeted manner [SWS_DM_00666] [SWS_DM_00671] [SWS_DM_00672].

Context diagram: Interaction relationships of the class ara::diag::DTCInformation in the overall diagnostic system. Sources: [SWS_DM_00664], [SWS_DM_00672], AUTOSAR AP SWS Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”.

Lifecycle

The instantiation of ara::diag::DTCInformation takes place explicitly via passing a ara::core::InstanceSpecifier, which must reference a modeled PortPrototype of a DiagnosticDTCInformationInterface [SWS_DM_00664]. The constructor is specified as thread-safe and exception-safe (noexcept) [SWS_DM_00664].

With regard to ownership, the class is designed as a strict single object: both the copy constructor and the move constructor, as well as the corresponding assignment operators, are deleted (=delete) [SWS_DM_01611] [SWS_DM_01612] [SWS_DM_01613] [SWS_DM_01614]. An instance can therefore neither be copied nor moved, but remains at its original creation location throughout its entire lifetime.

Destruction is performed via the destructor ~DTCInformation() [SWS_DM_00665]. The destructor is classified as not thread-safe, which is why it must be ensured that no concurrent accesses to the same instance take place during teardown. The concurrency model distinguishes clearly between reading and modifying methods: Pure query methods such as GetCurrentStatus [SWS_DM_00666], GetControlDTCStatus [SWS_DM_00672], GetNumberOfStoredEntries [SWS_DM_00669], and GetEventMemoryOverflow [SWS_DM_00919] are thread-safe. Modifying actions such as Clear [SWS_DM_00671] and EnableControlDtc [SWS_DM_00674], as well as all registrations of notifier callbacks, are not thread-safe and require external synchronization in the case of shared access.

Usage Path

A typical usage path comprises the creation of the instance, the configuration of event-driven callback functions, periodic or event-driven querying of status values, as well as the execution of control or cleanup actions:

  1. Initialization: The application instantiates ara::diag::DTCInformation by specifying the matching InstanceSpecifier [SWS_DM_00664].
  2. Registration of notifiers: For reactive handling of diagnostic events, the application registers callback functions, such as via SetDTCStatusChangedNotifier with the type DtcStatusChangedNotifier [SWS_DM_00667] [SWS_DM_02122], SetNumberOfStoredEntriesNotifier [SWS_DM_00670] [SWS_DM_02124], SetEventMemoryOverflowNotifier [SWS_DM_00918] [SWS_DM_02076], SetControlDtcStatusNotifier [SWS_DM_00673] [SWS_DM_02125], or SetSnapshotRecordUpdatedNotifier [SWS_DM_00668] [SWS_DM_02123]. A renewed call overwrites the previously registered callback.
  3. Status query: The application asynchronously queries the current UDS DTC status of a specific DTC via GetCurrentStatus, which returns a ara::core::Future<UdsDtcStatusByteType> [SWS_DM_00666]. In addition, the number of stored entries ([SWS_DM_00669]), the overflow status ([SWS_DM_00919]), and the control status regarding UDS Service 0x85 ([SWS_DM_00672]) can be queried.
  4. Control and cleanup: If application-side conditions require it, status control can be set to enabled via EnableControlDtc [SWS_DM_00674]. To clear individual DTCs or a DTC group, the application calls Clear and receives a ara::core::Future<void> to monitor the process [SWS_DM_00671].

Error Scenarios

Error conditions are divided into static configuration and instantiation violations as well as dynamic runtime errors via ara::diag::DiagErrc:

During creation of the instance via the constructor, the following violations can occur [SWS_DM_00664]:

  • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the execution model or does not reference a PortPrototype.
  • PortInterfaceMappingViolation: The referenced PortPrototype is not typed by a DiagnosticDTCInformationInterface.
  • ProcessMappingViolation: No matching modeled process exists at runtime for the reference.
  • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by an existing instance within this process.

During ongoing operation, asynchronous methods (via ara::core::Future) and synchronous calls (via ara::core::Result) return specific error codes:

  • DiagErrc::kServiceNotAvailable: The basic functionality of Diagnostic Management is temporarily or permanently unavailable. Affects, among others, GetCurrentStatus [SWS_DM_00666], GetNumberOfStoredEntries [SWS_DM_00669], Clear [SWS_DM_00671], GetControlDTCStatus [SWS_DM_00672], and GetEventMemoryOverflow [SWS_DM_00919].
  • DiagErrc::kNoSuchDTC: Occurs with GetCurrentStatus if no associated DTC exists in the memory target for the requested diagnostic event [SWS_DM_00666].
  • DiagErrc::kBusy: The interface is currently busy with another operation, e.g., if Clear is requested concurrently [SWS_DM_00671].
  • DiagErrc::kWrongDtc: An invalid DTC identification number was passed to Clear [SWS_DM_00671].
  • DiagErrc::kMemoryError or DiagErrc::kFailed: Hardware or internal memory errors as well as general processing aborts during the clearing process with rollback semantics [SWS_DM_00671].
  • DiagErrc::kInvalidArgument: Returned by notifier registration methods such as SetSnapshotRecordUpdatedNotifier [SWS_DM_00668], SetNumberOfStoredEntriesNotifier [SWS_DM_00670], SetControlDtcStatusNotifier [SWS_DM_00673], or SetEventMemoryOverflowNotifier [SWS_DM_00918] if incorrect parameters are passed.
