class ara::com::InstanceIdentifier

[SWS_CM_00302] Upstream: RS_CM_00101, RS_CM_00102, RS_AP_00114, RS_AP_00127

class InstanceIdentifier {...};

Unique identifier of a specific AdaptivePlatformServiceInstance, to distinguish different instances of exactly the same service. ara::com::InstanceIdentifier satisfies the [equalitycomparable], [lessthancomparable] and [copyassignable] requirements as per [30] to allow for logging of ara::com::InstanceIdentifiers as well as storing and managing ara::com::InstanceIdentifiers by the application (see operators). ara:: com::InstanceIdentifier does not contain a fully qualified name, which would also have service type information.

Technical name of a service instance

InstanceIdentifier is the binding-specific identity of a service instance, encapsulated as a value. Its character representation is not intended for application-side interpretation because its structure depends on binding and platform. EXP ARAComAPI §4.8.1 “Instance Identifiers and Instance Specifiers” explains the abstraction limit.

Create and dissolve

Create() validates a serialized representation and returns it as Result. However, a InstanceSpecifier is normally used; the runtime resolution against the manifest can return one or more identifiers, for example with multi-binding. SWS CM §7.5.21 “Instance Specifier Translation” and EXP ARAComAPI §4.8.2 “When to use InstanceIdentifier versus InstanceSpecifier” give the selection rule.

Server-side uniqueness

For skeleton creation, Communication Management checks instance identifiers for uniqueness; For a container, non-empty entries, unique entries and assignment to the same specifier also apply. [SWS_CM_10410] and [SWS_CM_10451] are the corresponding function rules.

Consciously validate serialized ID

Create() converts a serialized instance identifier into a InstanceIdentifier and signals an invalid format via the result path. The method is suitable for the controlled reconstruction of an already known technical ID, not for deriving its internal structure. EXP ARAComAPI §4.8.1 “Instance Identifiers and Instance Specifiers” emphasizes the binding dependency.

Preferred alternative

For the normal application path, InstanceSpecifier is more stable; runtime resolution selects the binding from the Manifest. EXP ARAComAPI §4.8.2 “When to use InstanceIdentifier versus InstanceSpecifier” supports this recommendation.
