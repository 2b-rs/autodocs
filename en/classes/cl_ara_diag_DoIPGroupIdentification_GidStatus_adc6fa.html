Context

The C++ data structure ara::diag::DoIPGroupIdentification::GidStatus is part of the diagnostic module (diag) of the AUTOSAR Adaptive Platform in release R25-11 ([SWS_DM_00721], SWS Diagnostics §8.34.2 “Struct: GidStatus”). It acts as a standardized data container for positive response data (“Response data of positive response message”) during queries for group identification (Group Identification, GID) within the framework of the Diagnostic over IP (DoIP) protocol.

In the DoIP subsystem, group identification serves to identify logical groups or clusters of ECUs and diagnostic nodes in the vehicle network. According to [SWS_DM_00813] (SWS Diagnostics §7 “Providing the GID in DoIP protocol messages using application interface”), the Diagnostic Management Daemon (DM) is responsible for providing the GID in outgoing DoIP protocol messages. If parameter DoIpInstantiation.gid is not statically preconfigured, Diagnostic Management must request the group identification at runtime via the application interface. For this purpose, the DM calls the interface function ara::diag::DoIPGroupIdentification::GetGidStatus ([SWS_DM_00724], SWS Diagnostics §8.34.1.1.3.1 “GetGidStatus”).

In this interaction, struct GidStatus represents the link between the providing adaptive application and Diagnostic Management. It encapsulates the status and identification information relevant for the positive response message, enabling the daemon to assemble the DoIP message in compliance with the specification and transmit it to the requesting external client.

Lifecycle

As a data structure (struct GidStatus), GidStatus possesses no internal state machine of its own, but behaves like a classic data transfer object. Instances of this structure are created by the adaptive application that implements and provides service ara::diag::DoIPGroupIdentification in order to answer the call of GetGidStatus ([SWS_DM_00724]).

Interpretation: Since GidStatus is designated in the specification exclusively as a result structure for positive response messages, the lifetime of an object is likely closely coupled to the execution and return of the query method. The adaptive application typically creates the instance in a local context or transfers it via move semantics or via result wrappers to the Diagnostic Management runtime environment. As soon as Diagnostic Management has read the GID values for the protocol message, the instance is discarded again.

With regard to concurrency, GidStatus exhibits no internal synchronization mechanisms. Since queries via GetGidStatus can be processed asynchronously by Diagnostic Management, it is the responsibility of the implementing application to ensure that the diagnostic data passed within GidStatus is provided consistently and thread-safely.

Usage Path

The typical usage sequence of GidStatus occurs during the dynamic response to DoIP identification requests. The interaction between external DoIP client, Diagnostic Management, and the adaptive application is divided into the following phases:

  • 1. Request by DoIP client: An external diagnostic tester or DoIP client sends a message for vehicle or group identification to the ECU.
  • 2. Checking the GID configuration: Diagnostic Management checks whether the group identification is configured statically in the model via DoIpInstantiation.gid ([SWS_DM_00813]).
  • 3. Querying the application interface: If no static configuration is present, the DM calls method ara::diag::DoIPGroupIdentification::GetGidStatus ([SWS_DM_00724]).
  • 4. Creation and return of GidStatus: The adaptive application determines the current GID data, instantiates an object of type GidStatus ([SWS_DM_00721]), and returns it as a positive response to the DM.
  • 5. Assembly of the DoIP response: Diagnostic Management extracts the identification data from GidStatus, builds the standard-compliant DoIP response message, and sends it to the DoIP client.
