class <SI-Namespace>::skeleton:: events::<Event>

Enables service providers to send events from the server side to subscribing applications.
AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 61a657b4f5c6 Provenance

Enables service providers to send events from the server side to subscribing applications.

The class <SI-Namespace>::skeleton::events::<Event> serves service providers on the AUTOSAR Adaptive Platform to publish event data to subscribing applications. Events can be sent either copy-based or efficiently without copying via buffers pre-allocated via Allocate() ([SWS_CM_90438]). The send call via Send() strictly requires that the associated service instance was previously successfully offered and that the configured minimum send interval is adhered to ([SWS_CM_00162]).

Context

The class <SI-Namespace>::skeleton::events::<Event> represents the server-side interface for publishing events of a service within the AUTOSAR Adaptive Platform. It enables a service application (skeleton) to asynchronously transmit updated event data of type SampleType ([SWS_CM_11400]) to all subscribing client applications ([SWS_CM_00162]). The skeleton interacts directly with the communication layer (Communication Management), which handles the discovery of service instances and the physical distribution of event data. In addition to sending data, the event instance monitors the current subscription status and notifies the service provider of changes in the subscriber base ([SWS_CM_12008], [SWS_CM_12011]).

Context diagram: Interaction of the Event class with service provider, Communication Management, and subscribers. Sources: [SWS_CM_00162], [SWS_CM_90437], [SWS_CM_12011]

Lifecycle

Instantiation of the Event class takes place in conjunction with the enclosing skeleton service instance. Presumably, the lifetime of the event instance is bound tightly to the lifetime of the skeleton, so that an event object becomes usable only after construction of the service and ends with its destruction. Before active data transmission, the service must have been offered, as transmission attempts prior to service offering fail ([SWS_CM_00162]).

During the operational phase, the instance reflects the state of subscriber connections. The current status can be queried via GetSubscriptionState() ([SWS_CM_12011]). For asynchronous reactions to state changes, the application registers a corresponding callback using SetSubscriptionStateChangeHandler() ([SWS_CM_12008]), optionally coupled to a specific execution context via an executor object ([SWS_CM_12009]). Upon termination or re-orientation of the service, this handler can be deregistered again via UnsetSubscriptionStateChangeHandler() ([SWS_CM_12010]). All status queries and handler methods are declared as noexcept and ensure exception safety ([SWS_CM_12008], [SWS_CM_12011]).

Usage Path

Two principal transmission modes are available to the service application for publishing event data: copy-based transmission and the zero-copy method using managed memory (EXP ara::com API p. 10).

In the regular usage path, the service provider initially registers a callback for subscription changes if needed ([SWS_CM_12008]). As soon as subscribers are present, the application either creates local data and passes it by value to Send() ([SWS_CM_00162]), whereby Communication Management creates a copy of the data and forwards it to all subscribers (EXP ara::com API p. 10).

Alternatively, to avoid copy overhead, the application requests a memory buffer in the form of a Allocate() directly from the communication layer via ara::com::SampleAllocateePtr<SampleType> ([SWS_CM_90438], EXP ara::com API p. 10). After filling the buffer, it is transmitted via the specialized overload of Send() ([SWS_CM_90437]). Interpretation: Upon sending, ownership of the memory likely transfers completely to Communication Management, as any further access to the data after the call is explicitly prohibited for the application ([SWS_CM_90437]).

Sequence diagram: Typical sequence of event transmission including handler registration and allocation. Sources: [SWS_CM_12008], [SWS_CM_90438], [SWS_CM_90437], [SWS_CM_00162]

Error Scenarios

Calls to Send() return a ara::core::Result<void>, which in case of error contains a corresponding error code of type ara::com::ComErrc ([SWS_CM_00162], [SWS_CM_90437]). Defined error cases include:

  • ComErrc::kServiceNotOffered: The service was not yet provided via OfferService() before the send attempt ([SWS_CM_00162], [SWS_CM_90437]).
  • ComErrc::kMinimumSendIntervalViolationError: The minimum send interval configured for the event (minimumSendInterval) was violated because send calls were issued in too rapid succession ([SWS_CM_00162], [SWS_CM_90437]).

In addition, preconditions must be observed during allocation and handler configuration:

  • Allocate() is not exception-safe (not exception safe) and results in a SampleAllocationViolation in the event of insufficient memory resources, or in a AllocateUsageViolation in the event of impermissible use of user-defined allocators ([SWS_CM_90438]).
  • SetSubscriptionStateChangeHandler() requires a valid, callable function object; if a null or non-existent handler is passed, this results in a InvalidHandlerViolation ([SWS_CM_12008], [SWS_CM_12009]).

function Allocate [SWS_CM_90438] Upstream: RS_CM_00201, RS_AP_00114, RS_AP_00115, RS_AP_00120

ara::com::SampleAllocateePtr< SampleType > Allocate ();

Allocating data for event transfer when Communication Management is responsible for the data.

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: fc3608719061 Provenance

The method Allocate is called at the skeleton level for an event ([SWS_CM_90438]; AUTOSAR_AP_EXP_ARAComAPI §5.4.1 “Skeleton Class API’s”) in order to allocate memory for the transmission of event data when Communication Management (ara::com) is responsible for managing the data ([SWS_CM_90438]). It returns an instance of type ara::com::SampleAllocateePtr<SampleType> ([SWS_CM_90438]). This pointer type conceptually behaves like a std::unique_ptr<T>, so that only one party owns the pointer at any given time (ARAComAPI §6 “Event Allocate/Send sample Binding implementer hint”).

Regarding error handling and exception safety, Allocate is specified as not exception safe ([SWS_CM_90438]). The specification defines two possible violations:

  • SampleAllocationViolation: Insufficient memory resources are available to allocate the data ([SWS_CM_90438]).
  • AllocateUsageViolation: The allocation was impermissibly performed via a custom allocator ([SWS_CM_90438]).

The concept behind Allocate primarily aims at supporting zero-copy mechanisms, particularly with shared-memory-based IPC transport, where strict synchronization between readers and writers is assumed (ARAComAPI §6 “Event Allocate/Send sample Binding implementer hint”). Implementers must note that serialization requirements can negate zero-copy if data types in deployment are not configured to be binary compatible or detection logic precludes this (ARAComAPI §6 “Event Allocate/Send sample Binding implementer hint”).

In interaction with sending events, the memory pointer obtained via Allocate is passed to Send(ara::com::SampleAllocateePtr<SampleType> data) ([SWS_CM_90437]). After calling Send, the service application may no longer access the data once Communication Management transmits the data to all subscribing applications ([SWS_CM_90437]).

The function [SWS_CM_00162] serves on the service provider side within <SI-Namespace>::skeleton::events::<Event> to send event data to all subscribing applications. In this variant, responsibility for data allocation remains entirely with the applying application. The data object is passed via parameter data, whereupon the binding implementation creates an internal copy during the call (ARAComAPI, Figure 6.17 “BrakeEvent Class”). After the synchronous method call returns, the application can immediately modify or free the original memory area.

          

          
The method is declared with noexcept and specified as exception-safe. It returns a ara::core::Result<void>, which contains void in case of success and reports error codes from [SWS_CM_10432] in case of error ([SWS_CM_00162]):

            • 

          • ComErrc::kMinimumSendIntervalViolationError: Occurs if the send request was issued faster than the configured minimum send interval (ServiceInterfaceDeploymentElement.minimumSendInterval).
            • 

          

          
In contrast to the zero-copy alternative [SWS_CM_90437], which requires pointers of type ara::com::SampleAllocateePtr obtained via Allocate(), this call does not require any memory binding to the framework. The same transmission behavior and error conditions also apply according to [SWS_CM_00119] to the update method Update of fields.

              Usage and Call Context
              

              The method Send is called on an event instance in the service skeleton (<SI-Namespace>::skeleton::events::<Event>) ([SWS_CM_90437]). It transmits event data for whose memory management Communication Management is responsible. The parameter data of type ara::com::SampleAllocateePtr<SampleType> must have been obtained beforehand via Allocate() ([SWS_CM_90437]). This pointer type behaves semantically like a std::unique_ptr, whereby ownership of the data passes to the communication layer upon the call (ARAComAPI §6.17 “BrakeEvent Class”). After the transfer, the sending application is prohibited from any further access to the data ([SWS_CM_90437]).
              

              Error Handling and Boundary Conditions
              

              The function is declared as noexcept and returns a ara::core::Result<void> ([SWS_CM_90437]). If sending fails, the result contains an error code from ara::com::ComErrc ([SWS_CM_10432]):
              

                

              • ComErrc::kServiceNotOffered: The associated service has not yet been offered beforehand with OfferService() ([SWS_CM_90437]).
                • 

              • ComErrc::kMinimumSendIntervalViolationError: The minimum sending interval (minimumSendInterval) configured for the service element has not yet elapsed since the last transmission ([SWS_CM_90437]).
                • 

              

              Both error cases have rollback semantics ([SWS_CM_90437]). Before the call, the service must therefore mandatorily have been offered, and consecutive send calls must adhere to the configured minimum interval.
              

              Interaction and optimization
              

              Compared to the signature [SWS_CM_00162], in which application-managed data is passed and copied by Communication Management, this variant aims at zero-copy communication via shared memory (ARAComAPI §6.18 “Event Allocate/Send sample”). In doing so, strict synchronization between writers and readers is assumed, whereby possible serialization requirements between communication partners must be observed (ARAComAPI §6.18 “Event Allocate/Send sample”).

                  use
                  

                  The function SetSubscriptionStateChangeHandler registers a callback handler in the skeleton scope (skeleton::events) for monitoring the subscription state of an event [SWS_CM_12008]. Parameter handler must be a callable object of type SubscriptionStateChangeHandler according to [SWS_CM_00311]. The method returns no value and is specified as noexcept [SWS_CM_12008].
                  

                  Communication Management calls the registered handler as soon as the subscription state of the event changes [SWS_CM_12012]. On the skeleton side, this happens with the state kSubscribed as soon as the number of active subscriptions becomes greater than zero [SWS_CM_12013], or with kNotSubscribed when there are no longer any active subscriptions [SWS_CM_12014] SWS CommunicationManagement §7.5.4 “Query Service Event Subscription State on Skeleton side”.
                  

                  Error Handling and Concurrency
                  

                  The operation is classified as exception safe [SWS_CM_12008]. If the passed callable is invalid or null, a InvalidHandlerViolation occurs [SWS_CM_12008]. Interpretation: Since the function neither throws exceptions nor returns an error code, this specification violation is likely caught via platform-specific runtime mechanisms.
                  

                  The handler may be overwritten at runtime [SWS_CM_12012]. For execution in a dedicated thread or task context, the overload with the template parameter executor exists [SWS_CM_12009]. An analogous registration for trigger elements of the skeleton is defined by [SWS_CM_01110].
