Context

The class ara::core::Future represents the reading end of an asynchronous operation within the AUTOSAR Adaptive Platform. It implements the concept of std::future known from the C++ standard in accordance with ISO/IEC 14882:2017. The class template is defined as template <typename T, typename E = ErrorCode> class Future final. The specification explicitly requires that parameterization with E != ara::core::ErrorCode leads to a compilation error.

In the asynchronous processing model, ara::core::Future is related to the following peers:

  • Asynchronous producer (Promise): A corresponding instance of ara::core::Promise manages the same shared state and populates it via SetResult or SetError with the result value or an error ([SWS_CORE_00336], [SWS_CORE_00326]).
  • Consumer (application): The consuming thread queries the availability status, blocks synchronously for the result, or registers asynchronous continuation functions.
  • Execution context (Executor): When chaining via then(), an execution context ExecutorT can optionally be specified in which the passed continuation is called ([SWS_CORE_00337]).

Lifecycle

Instances of ara::core::Future are subject to a strict move-ownership model. Both the copy constructor ([SWS_CORE_00334]) and the copy assignment operator ([SWS_CORE_00335]) are deleted (=delete). A transfer of the shared state is possible exclusively via move construction ([SWS_CORE_00323]) or move assignment ([SWS_CORE_00325]). The default constructor creates an empty instance analogous to std::future ([SWS_CORE_00322]); Interpretation: Such a default-constructed object initially has no shared state and is typically expected to represent an active operation only through move assignment.

An instance goes through the following state phases:

  • Invalid (valid() == false): The object has no shared state ([SWS_CORE_00327]). This applies to default-constructed instances, abandoned instances after a move, as well as objects immediately after consumption via GetResult() ([SWS_CORE_00336]), get() ([SWS_CORE_00326]), or then() ([SWS_CORE_00331]).
  • Valid, pending (valid() == true && is_ready() == false): A shared state is linked, but the asynchronous execution is not yet completed ([SWS_CORE_00332]).
  • Valid, ready (valid() == true && is_ready() == true): The value or the error has been placed in the shared state. In this state, GetResult(), get(), as well as the wait functions, are guaranteed no longer to block ([SWS_CORE_00332]).

The destructor ~Future() abandons the shared state ([SWS_CORE_00333]). If continuations have been registered via then(), the destructor of the returned future object blocks until a currently executing continuation is completely finished ([SWS_CORE_00331], [SWS_CORE_00337]).

Regarding thread safety, the methods valid() ([SWS_CORE_00327]) and is_ready() ([SWS_CORE_00332]) are specified as thread-safe. All other calls, especially value queries and wait functions, are not thread-safe.

Usage Path

The typical flow is divided into synchronization and value extraction:

  1. Status check and synchronization: is_ready() can be used to check in a non-blocking manner whether the result is ready ([SWS_CORE_00332]). For synchronous waiting, wait() is available ([SWS_CORE_00328]). Timed waiting is performed via wait_for() ([SWS_CORE_00329]) with a duration or via wait_until() ([SWS_CORE_00330]) with an absolute point in time, each returning a FutureStatus.
  2. Result query: The AUTOSAR-specific method GetResult() ([SWS_CORE_00336]) blocks until completion, throws no exceptions, and returns a ara::core::Result<T, E>. Alternatively, the standard function get() ([SWS_CORE_00326]) directly provides the value T or throws an exception in case of an error; it does not participate in overload resolution if C++ exceptions are disabled. Both methods invalidate the future object ([SWS_CORE_00336], [SWS_CORE_00326]).
  3. Reactive chaining: A continuation that accepts a Result<T, E> as an rvalue can be registered via then() ([SWS_CORE_00331]) or then() with executor ([SWS_CORE_00337]). In the case of nested returns, the return type performs automatic future or result unwrapping. The original future object becomes invalid immediately.

Sequence diagram: Flow of asynchronous provision, status check, and value retrieval. Sources: [SWS_CORE_00332], [SWS_CORE_00336]

Error Scenarios

The specification defines specific error states and runtime violations:

  • Call on invalid future (valid() == false): Calling GetResult() ([SWS_CORE_00336]), is_ready() ([SWS_CORE_00332]), wait() ([SWS_CORE_00328]), wait_for() ([SWS_CORE_00329]), wait_until() ([SWS_CORE_00330]), or then() ([SWS_CORE_00331], [SWS_CORE_00337]) on an invalid future results in runtime violation FutureInvalidViolation. For get() ([SWS_CORE_00326]), a FutureException with the error code kNoState is thrown instead.
  • Abandoned shared state (Broken Promise): If the shared state is destroyed or abandoned by the associated promise before a result was set, GetResult() returns a result with the error code FutureErrc::kBrokenPromise ([SWS_CORE_00336]). For get() ([SWS_CORE_00326]), the associated exception is triggered.
  • Exception in continuation: If a continuation registered in then() throws an exception that does not implement a violation, the violation FutureContinuationHasThrownViolation is triggered ([SWS_CORE_00331], [SWS_CORE_00337]). Users must catch exception information and report it back as an error via a Result or Future.

The specification explicitly requires that parameterization with <code>E != ara::core::ErrorCode</code> leads to a compilation error.</p>
<p>In the asynchronous processing model, <code>ara::core::Future</code> is related to the following peers:</p>
<ul>
<li><strong>Asynchronous producer (Promise):</strong> A corresponding instance of <code>ara::core::Promise</code> manages the same shared state and populates it via <code>SetResult</code> or <code>SetError</code> with the result value or an error (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>).</li>
<li><strong>Consumer (application):</strong> The consuming thread queries the availability status, blocks synchronously for the result, or registers asynchronous continuation functions.</li>
<li><strong>Execution context (Executor):</strong> When chaining via <code>then()</code>, an execution context <code>ExecutorT</code> can optionally be specified in which the passed continuation is called (<a class="spec-record-ref" data-req="SWS_CORE_00337" href="../spec/record.html?id=SWS_CORE_00337">[SWS_CORE_00337]</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>Instances of <code>ara::core::Future</code> are subject to a strict move-ownership model. Both the copy constructor (<a class="spec-record-ref" data-req="SWS_CORE_00334" href="../spec/record.html?id=SWS_CORE_00334">[SWS_CORE_00334]</a>) and the copy assignment operator (<a class="spec-record-ref" data-req="SWS_CORE_00335" href="../spec/record.html?id=SWS_CORE_00335">[SWS_CORE_00335]</a>) are deleted (<code>=delete</code>). A transfer of the shared state is possible exclusively via move construction (<a class="spec-record-ref" data-req="SWS_CORE_00323" href="../spec/record.html?id=SWS_CORE_00323">[SWS_CORE_00323]</a>) or move assignment (<a class="spec-record-ref" data-req="SWS_CORE_00325" href="../spec/record.html?id=SWS_CORE_00325">[SWS_CORE_00325]</a>). The default constructor creates an empty instance analogous to <code>std::future</code> (<a class="spec-record-ref" data-req="SWS_CORE_00322" href="../spec/record.html?id=SWS_CORE_00322">[SWS_CORE_00322]</a>); Interpretation: Such a default-constructed object initially has no shared state and is typically expected to represent an active operation only through move assignment.</p>
<p>An instance goes through the following state phases:</p>
<ul>
<li><strong>Invalid (<code>valid() == false</code>):</strong> The object has no shared state (<a class="spec-record-ref" data-req="SWS_CORE_00327" href="../spec/record.html?id=SWS_CORE_00327">[SWS_CORE_00327]</a>). This applies to default-constructed instances, abandoned instances after a move, as well as objects immediately after consumption via <code>GetResult()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>), <code>get()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>), or <code>then()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00331" href="../spec/record.html?id=SWS_CORE_00331">[SWS_CORE_00331]</a>).</li>
<li><strong>Valid, pending (<code>valid() == true &amp;&amp; is_ready() == false</code>):</strong> A shared state is linked, but the asynchronous execution is not yet completed (<a class="spec-record-ref" data-req="SWS_CORE_00332" href="../spec/record.html?id=SWS_CORE_00332">[SWS_CORE_00332]</a>).</li>
<li><strong>Valid, ready (<code>valid() == true &amp;&amp; is_ready() == true</code>):</strong> The value or the error has been placed in the shared state. In this state, <code>GetResult()</code>, <code>get()</code>, as well as the wait functions, are guaranteed no longer to block (<a class="spec-record-ref" data-req="SWS_CORE_00332" href="../spec/record.html?id=SWS_CORE_00332">[SWS_CORE_00332]</a>).</li>
</ul>
<p>The destructor <code>~Future()</code> abandons the shared state (<a class="spec-record-ref" data-req="SWS_CORE_00333" href="../spec/record.html?id=SWS_CORE_00333">[SWS_CORE_00333]</a>). If continuations have been registered via <code>then()</code>, the destructor of the returned future object blocks until a currently executing continuation is completely finished (<a class="spec-record-ref" data-req="SWS_CORE_00331" href="../spec/record.html?id=SWS_CORE_00331">[SWS_CORE_00331]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00337" href="../spec/record.html?id=SWS_CORE_00337">[SWS_CORE_00337]</a>).</p>
<p>Regarding thread safety, the methods <code>valid()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00327" href="../spec/record.html?id=SWS_CORE_00327">[SWS_CORE_00327]</a>) and <code>is_ready()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00332" href="../spec/record.html?id=SWS_CORE_00332">[SWS_CORE_00332]</a>) are specified as thread-safe. All other calls, especially value queries and wait functions, are not thread-safe.</p>

<h4>Usage Path</h4>
<p>The typical flow is divided into synchronization and value extraction:</p>
<ol>
<li><strong>Status check and synchronization:</strong> <code>is_ready()</code> can be used to check in a non-blocking manner whether the result is ready (<a class="spec-record-ref" data-req="SWS_CORE_00332" href="../spec/record.html?id=SWS_CORE_00332">[SWS_CORE_00332]</a>). For synchronous waiting, <code>wait()</code> is available (<a class="spec-record-ref" data-req="SWS_CORE_00328" href="../spec/record.html?id=SWS_CORE_00328">[SWS_CORE_00328]</a>). Timed waiting is performed via <code>wait_for()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00329" href="../spec/record.html?id=SWS_CORE_00329">[SWS_CORE_00329]</a>) with a duration or via <code>wait_until()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00330" href="../spec/record.html?id=SWS_CORE_00330">[SWS_CORE_00330]</a>) with an absolute point in time, each returning a <code>FutureStatus</code>.</li>
<li><strong>Result query:</strong> The AUTOSAR-specific method <code>GetResult()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>) blocks until completion, throws no exceptions, and returns a <code>ara::core::Result&lt;T, E&gt;</code>. Alternatively, the standard function <code>get()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>) directly provides the value <code>T</code> or throws an exception in case of an error; it does not participate in overload resolution if C++ exceptions are disabled. Both methods invalidate the future object (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>).</li>
<li><strong>Reactive chaining:</strong> A continuation that accepts a <code>Result&lt;T, E&gt;</code> as an rvalue can be registered via <code>then()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00331" href="../spec/record.html?id=SWS_CORE_00331">[SWS_CORE_00331]</a>) or <code>then()</code> with executor (<a class="spec-record-ref" data-req="SWS_CORE_00337" href="../spec/record.html?id=SWS_CORE_00337">[SWS_CORE_00337]</a>). In the case of nested returns, the return type performs automatic future or result unwrapping. The original future object becomes invalid immediately.</li>
</ol>

<h4>Error Scenarios</h4>
<p>The specification defines specific error states and runtime violations:</p>
<ul>
<li><strong>Call on invalid future (<code>valid() == false</code>):</strong> Calling <code>GetResult()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>), <code>is_ready()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00332" href="../spec/record.html?id=SWS_CORE_00332">[SWS_CORE_00332]</a>), <code>wait()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00328" href="../spec/record.html?id=SWS_CORE_00328">[SWS_CORE_00328]</a>), <code>wait_for()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00329" href="../spec/record.html?id=SWS_CORE_00329">[SWS_CORE_00329]</a>), <code>wait_until()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00330" href="../spec/record.html?id=SWS_CORE_00330">[SWS_CORE_00330]</a>), or <code>then()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00331" href="../spec/record.html?id=SWS_CORE_00331">[SWS_CORE_00331]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00337" href="../spec/record.html?id=SWS_CORE_00337">[SWS_CORE_00337]</a>) on an invalid future results in runtime violation <code>FutureInvalidViolation</code>. For <code>get()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>), a <code>FutureException</code> with the error code <code>kNoState</code> is thrown instead.</li>
<li><strong>Abandoned shared state (Broken Promise):</strong> If the shared state is destroyed or abandoned by the associated promise before a result was set, <code>GetResult()</code> returns a result with the error code <code>FutureErrc::kBrokenPromise</code> (<a class="spec-record-ref" data-req="SWS_CORE_00336" href="../spec/record.html?id=SWS_CORE_00336">[SWS_CORE_00336]</a>). For <code>get()</code> (<a class="spec-record-ref" data-req="SWS_CORE_00326" href="../spec/record.html?id=SWS_CORE_00326">[SWS_CORE_00326]</a>), the associated exception is triggered.</li>
<li><strong>Exception in continuation:</strong> If a continuation registered in <code>then()</code> throws an exception that does not implement a violation, the violation <code>FutureContinuationHasThrownViolation</code> is triggered (<a class="spec-record-ref" data-req="SWS_CORE_00331" href="../spec/record.html?id=SWS_CORE_00331">[SWS_CORE_00331]</a>, <a class="spec-record-ref" data-req="SWS_CORE_00337" href="../spec/record.html?id=SWS_CORE_00337">[SWS_CORE_00337]</a>). Users must catch exception information and report it back as an error via a <code>Result</code> or <code>Future</code>.</li>
</ul>
