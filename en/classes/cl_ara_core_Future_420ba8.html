intended use

ara::core::Future<T, E> represents the later available result or error of an asynchronous call. The error type must be ara::core::ErrorCode, otherwise a compile-time error is required. Together with Promise, the type enables thread-safe, exception-free handling of asynchronous values ​​and errors. [SWS_CORE_00321] [SWS_CORE_10800]

Lifecycle & Ownership

Copying is prohibited (=delete); Move construction and move assignment are available. The destructor gives up any shared state. GetResult(), get() and then() invalidate the original Future. [SWS_CORE_00334] [SWS_CORE_00335] [SWS_CORE_00323] [SWS_CORE_00325] [SWS_CORE_00333] [SWS_CORE_00336] [SWS_CORE_00326] [SWS_CORE_00337]

Interaction with other classes

GetResult() blocks until there is a value or error and returns a non-triggering Result<T,E>. then() creates a subsequent Future from a function using this Result; the overload with Executor executes the function in its execution context. [SWS_CORE_00336] [SWS_CORE_00331] [SWS_CORE_00337]

Limitations & Error handling

If the corresponding Promise is given up, GetResult() returns the error FutureErrc::kBrokenPromise. Before blocking, is_ready() can be checked; at true, get(), GetResult() and wait calls do not block. Prohibited calls on invalid futures are specified as violations. [SWS_CORE_00336] [SWS_CORE_00332] [SWS_CORE_13011]

Asynchronous error handling

Future is the harmonized return type for asynchronous calls that can return a value or fail. In contrast to get(), after waiting, GetResult() returns a Result with a value or error and does not trigger an exception. RS General §4.1.2 “Error handling” EXP PlatformDesign §18.1.4 “Future and Promise” EXP ARAComAPI §5.3.6.2 “Event-Driven vs Polling access to method results”

Use with ara::com

For method-based communication, the Future/Promise pattern enables non-blocking behavior. Blocking waiting, a continuation with then() and polling via is_ready() are available for the arrival of a result; After successful is_ready(), subsequent access is not blocked. EXP ARAComAPI §4.4 “Method based communication” EXP ARAComAPI §5.3.6.2 “Event-Driven vs Polling access to method results”

The continuation then() is an extension of std::future; it can reduce context switching, but leads to callback nesting. EXP ARARustApplications §4.2.1 “Asynchronous Rust”

Sequence diagram: Common flow of an asynchronous service method with Promise and Future. Sources: EXP ARAComAPI §4.4 “Method based communication” EXP ARAComAPI §5.3.6.2 “Event-Driven vs Polling access to method results” EXP ARAComAPI §5.4.6 “Methods”.

Common state and error transport

The functional specification treats Future and Promise as the asynchronous counterpart of the error path: the later result can represent value or error without separating error handling from the return. SWS Core §7.2 “Error handling” SWS Core §7.2.5.5 “Future and Promise”

Behavior in the event of an error

GetResult() blocks until value or error is available and returns the contents of the shared state as Result<T,E>; An error set by SetError() therefore remains in the results path. If the shared state was abandoned by the corresponding Promise, GetResult() delivers FutureErrc::kBrokenPromise instead. In contrast, get() transports an error in the shared state as an exception; If Future is invalid, kNoState is included there. [SWS_CORE_00336] [SWS_CORE_00326] [SWS_CORE_00400]

wait_for() waits at most for the duration transferred, wait_until() at most until the deadline. Both return a FutureStatus; kTimeout only means that the shared state was not ready within the respective deadline. A timeout must therefore be distinguished from an error transported in the result. [SWS_CORE_00329] [SWS_CORE_00330] [SWS_CORE_00361]

The error is read as Result from the shared state; The alternative field shows the error caused by abandoning the Promise and the separate waiting timeout. Sources: [SWS_CORE_00336] [SWS_CORE_00329] [SWS_CORE_00330].

then() passes to its continuation exactly the Result that GetResult() would return for this Future; the continuation can therefore evaluate the error and pass it on as Result or a subsequent Future. After then(), the original Future is invalid. An exception escaping from the continuation is specified as a Violation; to propagate errors, it should be translated into an error. [SWS_CORE_00337] [SWS_CORE_00331]

States future_already_retrieved and promise_already_satisfied named in the API contracts appear in R25-11 as violation descriptions. A violation is also defined for access to an invalid Future; only get() specifies the FutureException with kNoState for this case. [SWS_CORE_13013] [SWS_CORE_13014] [SWS_CORE_13015] [SWS_CORE_00326]
