Context

The class ara::diag::DataTransferReadByPushHandler [SWS_DM_01515] provides the standardized interface for diagnostic data transfers in the Adaptive module diag that are initiated by a UDS service such as RequestReadFile or RequestReadDirectory and in which the payload is actively provided (“pushed”) by the application implementation AUTOSAR_AP_SWS_Diagnostics §8.10.3 “Class: DataTransferReadByPushHandler”.

In the overall system, three main actors interact:

  • UDS client (diagnostic tester): Initiates the file or directory transfer via the vehicle diagnostic protocol and requests data blocks sequentially.
  • Diagnostic Management (ara::diag): Processes the UDS requests, manages the diagnostic session, and forwards read and termination calls to the application-specific handler [SWS_DM_01522].
  • Application handler: Implements the class derived from ara::diag::DataTransferReadByPushHandler, reads the data from local memory, and transfers ownership of the payload blocks to ara::diag [SWS_DM_01522].

Context diagram: Interaction between UDS client, Diagnostic Management (ara::diag), and the application-specific handler. Sources: [SWS_DM_01515], [SWS_DM_01522], [SWS_DM_01523], AUTOSAR_AP_SWS_Diagnostics §8.10.3 “Class: DataTransferReadByPushHandler”

Lifecycle

The lifecycle of a handler instance is tightly bound to the duration of a single file transfer session:

  • Creation: The default constructor is declared as protected [SWS_DM_01516]. Interpretation: The class is designed as a pure base class that must be derived from by the application-specific implementation in order to provide the pure virtual methods.
  • Ownership and non-copyability: Copy constructor [SWS_DM_01518] and copy assignment operator [SWS_DM_01521] are deleted (=delete). A handler is intended exclusively for exactly one read transfer (“only one way usage i.e. per single file transfer session”).
  • Moveability: Move constructor [SWS_DM_01517] and move assignment operator [SWS_DM_01520] are defined as default (=default) and are exception-safe (noexcept).
  • Destruction: The virtual destructor [SWS_DM_01519] has a strict precondition: An instance must under no circumstances be destroyed before the call to ExitRead() AUTOSAR_AP_SWS_Diagnostics §8.10.3.1.1.2 “Destructor”. Interpretation: The destruction prohibition ensures the protocol consistency of the UDS session in Diagnostic Management.
  • Concurrency: The methods Read and ExitRead are specified as not thread-safe (not thread-safe) [SWS_DM_01522], [SWS_DM_01523]. Parallel calls on the same instance must be avoided on the application side.

Usage Path

The typical sequence of a read transfer comprises the following steps:

  1. Initialization: Upon arrival of a read request (RequestReadFile or RequestReadDirectory), the application instantiates its concrete handler via the protected constructor [SWS_DM_01516].
  2. Data transfer (Read): Diagnostic Management repeatedly calls the pure virtual method Read() [SWS_DM_01522] AUTOSAR_AP_SWS_Diagnostics §8.10.3.1.3.2 “Read”. In doing so, recommended_number_bytes_to_return for throughput optimization, meta_info, and a cancellation_handler are passed. The application compiles the next chunk and transfers its ownership to ara::diag via a ara::core::Future<ara::core::Vector<ara::core::Byte>>. The payload is placed in the positive UDS response after the blockSequenceCounter as transferResponseParameterRecord.
  3. Termination (ExitRead): To conclude the transfer, Diagnostic Management calls ExitRead() [SWS_DM_01523] AUTOSAR_AP_SWS_Diagnostics §8.10.3.1.3.1 “ExitRead”. Passed are the termination reason (exit_type of type DataTransferExitType), vehicle manufacturer-specific parameters (transfer_request_parameter_record as ara::core::Span<const ara::core::Byte>), meta_info, and cancellation_handler. The application acknowledges the termination asynchronously via the return future.
  4. Release: Only after ExitRead() has been completed may the destruction of the handler object take place [SWS_DM_01519].

Sequence diagram: Typical call sequence for a push-based read transfer from initialization to release. Sources: [SWS_DM_01516], [SWS_DM_01519], [SWS_DM_01522], [SWS_DM_01523], AUTOSAR_AP_SWS_Diagnostics §8.10.3.1.3.1 “ExitRead”, AUTOSAR_AP_SWS_Diagnostics §8.10.3.1.3.2 “Read”

Error Scenarios

For error handling and exceptional conditions, the following requirements must be observed:

  • Negative Response Codes (NRC): Both core methods (Read and ExitRead) are declared as noexcept and do not throw C++ exceptions [SWS_DM_01522], [SWS_DM_01523]. If an error occurs, the returned ara::core::Future is resolved with a ara::core::ErrorCode from the domain DiagUdsNrcErrc according to ISO 14229-1 to transmit a specific NRC to the client.
  • Cancellation handling: The methods receive a CancellationHandler [SWS_DM_01522], [SWS_DM_01523]. The application can query the cancellation status via cancellation_handler.IsCanceled() or register a notification function via cancellation_handler.SetNotifier(). If cancellation is signaled, further data preparation should be aborted.
  • Validity period of parameters: The parameter transfer_request_parameter_record passed in ExitRead() is only valid until the associated promise has been fulfilled or processing has been canceled by the CancellationHandler [SWS_DM_01523]. Access outside this time window is impermissible.
  • Violation of the destruction precondition: If the instance is destroyed before ExitRead() is called, this constitutes an explicit specification violation [SWS_DM_01519], which can lead to inconsistent behavior in Diagnostic Management.

This guide is based on the specification AUTOSAR Adaptive Platform Release R25-11.
