Context

In module rds of the AUTOSAR Adaptive Platform, the class ara::rds::RawDataStreamServer forms the server-side interface for accepting connections as well as the subsequent bidirectional exchange of unformatted binary data streams. It encapsulates the communication connection to a remote peer via a software port identified by a ara::core::InstanceSpecifier. The primary responsibility of the class lies in waiting for client connections as well as the synchronous and time-monitored reading and writing of byte sequences.

Lifecycle

The instantiation of ara::rds::RawDataStreamServer does not occur via a public constructor, but exclusively via the static factory method Create [SWS_RDS_11312]. This method expects a ara::core::InstanceSpecifier and is declared as thread-safe.

With regard to the ownership and copy model, it is a move-only type:

  • The copy constructor [SWS_RDS_11316] and the copy assignment operator [SWS_RDS_11317] are explicitly deleted (delete).
  • A transfer of the resource is possible via the move constructor [SWS_RDS_11314] and the move assignment operator [SWS_RDS_11315]. Both operations are defined as noexcept, but are explicitly designated as not thread-safe.

The lifecycle of a connection ends either through the explicit call of Shutdown [SWS_RDS_11320] or implicitly when the destructor [SWS_RDS_11313] is called. The destructor is noexcept as well as not thread-safe and ensures that a still open connection is closed and shut down when the object is destroyed.

Usage Path

The typical workflow when using a RawDataStreamServer is divided into the phases of creation, connection acceptance, data exchange, and connection teardown:

  1. Creation: The application creates the server instance via Create [SWS_RDS_11312], specifying the modeled port.
  2. Connection acceptance: The application waits for the arrival of an incoming client connection. This takes place either blocking via WaitForConnection() [SWS_RDS_11318] or with a maximum time period via WaitForConnection(timeout) [SWS_RDS_11319].
  3. Data transfer: As soon as the connection is established, data can be received and sent:
    • Binary data is read using ReadData(maxLength) [SWS_RDS_11322] or time-limited via ReadData(maxLength, timeout) [SWS_RDS_11323]. A ara::core::Result<ReadDataResult> is returned as the result.
    • Binary data is sent via WriteData, optionally without timeout [SWS_RDS_11324] or with timeout [SWS_RDS_11325]. The payload is passed to the method as std::unique_ptr<ara::core::Byte[]>.
  4. Connection teardown: After completion of the data transmission, the connection is closed in an orderly manner by Shutdown() [SWS_RDS_11320].

Sequence diagram: Typical call sequence for instantiation, connection acceptance, data transmission, and connection termination. Sources: [SWS_RDS_11312], [SWS_RDS_11318], [SWS_RDS_11319], [SWS_RDS_11320], [SWS_RDS_11322], [SWS_RDS_11323], [SWS_RDS_11324], [SWS_RDS_11325].

Error Scenarios

All state-modifying and data-transferring functions dispense with C++ exceptions and are declared as noexcept. Instead, they signal success or error via ara::core::Result:

  • Connection establishment failure: If the connection cannot be established within the specified deadline, WaitForConnection with timeout [SWS_RDS_11319] returns a corresponding error result.
  • Failure and timeouts during data operations: For read and write operations with timeout ([SWS_RDS_11323] and [SWS_RDS_11325]), an error is returned in the Result if the specified time period is exceeded.
  • Preconditions: A call to ReadData or WriteData presumably requires a previously successfully established connection via WaitForConnection; otherwise, the operation is likely to be rejected with an error in the ara::core::Result.
  • State after shutdown: After execution of Shutdown [SWS_RDS_11320], the connection is closed; subsequent calls to read and write methods are likely to fail.
