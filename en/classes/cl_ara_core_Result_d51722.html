Encapsulates either a success value or an error value for synchronous, exception-free result transmission.

The class represents a type-safe container that holds either a payload value or an error code to transmit computation results synchronously and without C++ exceptions [SWS_CORE_00751]. Callers create instances via dedicated constructors or factory functions and subsequently evaluate the result conditionally via check and access functions such as value or error access. As an essential constraint, the underlying error type must strictly correspond to the standard error code, as differing type assignments are rejected at compile time. In addition, functions for triggering exceptions require a compiler environment with C++ exceptions enabled [SWS_CORE_00766].

Context

The class ara::core::Result is the central construct of the AUTOSAR Adaptive Platform for the synchronous, typed return of operation results without the mandatory use of C++ exceptions. It represents a tagged union that contains either a payload value of type value_type (T) or an error of type error_type (E) at any point in time [SWS_CORE_00711] [SWS_CORE_00712]. By default, ara::core::ErrorCode acts as the type for E; deviating error definitions are prevented by implementations already at compile time through a compiler error.

In the application architecture, ara::core::Result mediates between called services and consumers. Services instantiate the object to return the status, while consumers trigger further processing via state tests such as [SWS_CORE_00751] or functional chaining such as [SWS_CORE_00768]. Furthermore, the state can be converted into ara::core::Optional via [SWS_CORE_00770] (Ok) and [SWS_CORE_00772] (Err).

Lifecycle

Initialization of an instance occurs either directly via constructors for values ([SWS_CORE_00721], [SWS_CORE_00722]) or explicitly for errors ([SWS_CORE_00723], [SWS_CORE_00724]). In addition, static factory functions are available: FromValue for lvalues, rvalues, and in-place arguments ([SWS_CORE_00731], [SWS_CORE_00732], [SWS_CORE_00733]) as well as FromError for creating error states ([SWS_CORE_00734], [SWS_CORE_00735], [SWS_CORE_00736]).

ara::core::Result exclusively owns the contained datum and manages its lifetime. It supports full value semantics via copy and move constructors ([SWS_CORE_00725], [SWS_CORE_00726]) as well as corresponding assignment operators ([SWS_CORE_00741], [SWS_CORE_00742]). Changing the contents of existing instances is possible by means of Swap [SWS_CORE_00745] or by in-place overwriting via EmplaceValue [SWS_CORE_00743] or EmplaceError [SWS_CORE_00744].

The destructor releases the active element and is considered trivially destructible if both T and E are trivially destructible [SWS_CORE_00727]. With regard to concurrency, purely reading accesses are thread-safe, whereas modifying operations such as EmplaceValue, EmplaceError, move assignments, or Swap are not thread-safe and require external synchronization.

Usage Path

The regular flow includes creation, validation, and retrieval of the result:

  1. Provision: A service creates the result via [SWS_CORE_00731] or [SWS_CORE_00734] and returns the instance by value.
  2. State check: The caller checks whether a value is present using HasValue() [SWS_CORE_00751] or the explicit conversion operator operator bool() [SWS_CORE_00752]. The latter is disabled if T itself is of type bool.
  3. Value and error access: If a value is present, it can be read out via Value() ([SWS_CORE_00755], [SWS_CORE_00756], [SWS_CORE_00775]) or the operators operator* ([SWS_CORE_00753], [SWS_CORE_00759]) and operator-> ([SWS_CORE_00754], [SWS_CORE_00777]). In the event of an error, access occurs via Error() ([SWS_CORE_00757], [SWS_CORE_00758], [SWS_CORE_00776]) or targeted error checking with CheckError() [SWS_CORE_00765].
  4. Functional transformation: Alternatively, Bind() [SWS_CORE_00768] permits monadic further processing: The passed callable is executed only if a payload value is contained; an existing error is propagated unchanged into the new Result instance. Fallbacks can be mapped with Resolve() [SWS_CORE_00767].

Sequence diagram: Typical call flow during query and evaluation of a Result instance. Sources: [SWS_CORE_00731], [SWS_CORE_00751], [SWS_CORE_00755], [SWS_CORE_00757], [SWS_CORE_00768]

Error Scenarios

Accessing non-active states violates the preconditions of the class:

  • Calling Value(), operator*, or operator-> without a contained value triggers the documented system violation ResultWithNoValueViolation ([SWS_CORE_00755], [SWS_CORE_00753], [SWS_CORE_00754]).
  • Calling Error() when a payload value is present leads to the violation ResultWithNoErrorViolation ([SWS_CORE_00757], [SWS_CORE_00776]).

Interpretation: Triggering such a precondition violation is likely to lead to an immediate process termination typically in runtime environments, since the standard classifies these states as severe programming errors. Question Q-15376f67084c4be6 (open) To avoid hard terminations, defensive methods can be used: ValueOr() ([SWS_CORE_00761], [SWS_CORE_00762]) and ErrorOr() ([SWS_CORE_00763], [SWS_CORE_00764]) return a specified default value if the element is absent. Optional variants such as Ok() ([SWS_CORE_00770], [SWS_CORE_00771]) and Err() ([SWS_CORE_00772], [SWS_CORE_00773]) encapsulate access without exceptions.

If exception handling is desired, ValueOrThrow() ([SWS_CORE_00766], [SWS_CORE_00769], [SWS_CORE_00778]) throws the C++ exception associated with the error in the event of an error. If C++ exceptions are disabled in the compiler, ValueOrThrow() is removed from overload resolution [SWS_CORE_00766]; likewise, the non-const lvalue overload of operator* is disabled in this case [SWS_CORE_00774].
