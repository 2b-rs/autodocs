Used for categorizing, textually describing, and converting Adaptive Platform diagnostic errors into exceptions.

Class ara::diag::DiagErrorDomain defines the error domain for diagnostic errors in AUTOSAR Adaptive and derives from ara::core::ErrorDomain ([SWS_DM_00517]). It translates numeric diagnostic error values into descriptive texts in a thread-safe manner without returning nullptr ([SWS_DM_00522]) and enables conversion into typed exceptions when C++ exceptions are enabled ([SWS_DM_00523]). If compiler exceptions are disabled, the exception interface is omitted in favor of purely value-based error handling.

Context

Class ara::diag::DiagErrorDomain represents the standardized error domain for diagnostic errors within module diag of the AUTOSAR Adaptive Platform ([SWS_DM_00517]). According to the class definition in AUTOSAR_AP_SWS_Diagnostics §8.11.3 “Class: DiagErrorDomain”, it is declared as final and derives from the base infrastructure class ara::core::ErrorDomain. Its primary responsibility is to integrate diagnostic error codes into the unified error model of AUTOSAR Adaptive.

To this end, the class binds the domain-specific enumeration type for error values via type alias Errc ([SWS_DM_00518]), provides an alias for the associated base exception class DiagException with Exception ([SWS_DM_00519]), and translates error codes into human-readable text messages ([SWS_DM_00522]). Via method Name(), it returns the short name of the domain specified in [SWS_CORE_90023] ([SWS_DM_00521]), allowing it to be uniquely identified by diagnostic components and applications.

Lifecycle

Instantiation of ara::diag::DiagErrorDomain occurs via the default constructor (AUTOSAR_AP_SWS_Diagnostics §8.11.3.2.1.1 “Default Constructor”). This constructor is defined as constexpr and noexcept ([SWS_DM_00520]). Due to these properties, instances are typically constructed already at compile time and held as long-lived or static singleton objects in the address space to enable efficient error resolution without dynamic memory allocation.

Regarding concurrency, the default constructor as well as all derived interface methods (Name(), Message(), and ThrowAsException()) are explicitly specified as thread-safe (thread-safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523]). The object holds no mutable internal state after construction, so concurrent read accesses across multiple application or diagnostic threads are permitted without additional external synchronization. Destruction of the object requires no cleanup of external resources.

Usage Path

The typical usage path occurs when a diagnostic operation fails and an error of type ara::core::ErrorCode needs to be evaluated or logged. The application or a diagnostic framework accesses the error domain to resolve the error text or throw an exception if applicable.

  1. Domain identification: The caller verifies the error domain based on the short name via Name() ([SWS_DM_00521]).
  2. Retrieve error message: Via Message(errorCode), the numeric code value is converted into a textual description ([SWS_DM_00522]).
  3. Throw exception (optional): If the calling control flow provides for exception-based error handling, ara::core::ErrorCode delegates to ThrowAsException(), whereby the associated exception DiagException is instantiated and thrown ([SWS_DM_00519], [SWS_DM_00523]).

Sequence diagram: Sequence of error identification, text resolution, and optional exception throwing via DiagErrorDomain. Sources: [SWS_DM_00519], [SWS_DM_00521], [SWS_DM_00522], [SWS_DM_00523].

Error Scenarios

When using Message(), the function accepts an error code of base type ara::core::ErrorDomain::CodeType. Contractually, it is guaranteed that the return value is never nullptr ([SWS_DM_00522]). For invalid or unspecified code values, the implementation presumably returns a generic fallback string to satisfy the guarantee.

Regarding exception safety, the constructor and methods Name() and Message() are declared as noexcept and are considered exception-safe (exception safe) ([SWS_DM_00520], [SWS_DM_00521], [SWS_DM_00522]). In contrast, ThrowAsException() is explicitly annotated with noexcept(false) and classified as not exception safe ([SWS_DM_00523]), because throwing an exception deliberately represents its defined main function.

A central constraint concerns toolchains without C++ exception support: If C++ exceptions are disabled in the compiler, ThrowAsException() does not participate in overload resolution according to [SWS_CORE_10304] ([SWS_DM_00523]). Applications must process diagnostic errors in such environments in a purely value-based manner via error code enumeration type Errc ([SWS_DM_00518]).
