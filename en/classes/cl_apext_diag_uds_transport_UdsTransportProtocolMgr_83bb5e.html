Coordinates UDS message exchange between transport layer plugins and the session layer of the Diagnostic Server.

The class apext::diag::uds_transport::UdsTransportProtocolMgr manages the interaction between the Diagnostic Server and specific UDS transport protocols according to AUTOSAR AP SWS Diagnostics §7.1.1 “Support of UDS Transport Layer”. It controls two-stage message reception via advance indication and asynchronous forwarding to the session layer, as well as the feedback of transmission and lifecycle events ([SWS_DM_00309], [SWS_DM_00311]). All interface calls are designed to be exception-safe, but not thread-safe.

Context

The class apext::diag::uds_transport::UdsTransportProtocolMgr acts as a central intermediary between the instances of the Diagnostic Server or the DM core (session layer) and various UDS transport protocols such as DoIP or CAN according to AUTOSAR AP SWS Diagnostics §7.1.1 “Support of UDS Transport Layer”. It provides an extensible interface through which implementation-specific transport plugins deriving the base class UdsTransportProtocolHandler ([SWS_DM_00315]) report incoming UDS messages and forward transport confirmations to the diagnostic core. Interpretation: The instance of the manager is likely operated by Diagnostic Management as a long-lived mediator component to bundle heterogeneous transport interfaces uniformly. Question Q-79e155960156d04a (open)

Context diagram: Embedding of UdsTransportProtocolMgr between transport layer handlers and the session layer. Sources: [SWS_DM_00309], [SWS_DM_00311], [SWS_DM_00312], [SWS_DM_01069], AUTOSAR AP SWS Diagnostics §7.1.1 “Support of UDS Transport Layer”.

Lifecycle

Destruction takes place via the virtual destructor ~UdsTransportProtocolMgr(), which is specified with noexcept = default ([SWS_DM_01524]). During operation, the manager reacts to lifecycle events of the registered transport protocol handlers according to AUTOSAR AP SWS Diagnostics §7.1.1.1 “Initialization, Starting and Stopping of a UDS TransportLayer” and [SWS_DM_00329]: If a handler is shut down, it reports completion via HandlerStopped() ([SWS_DM_00314]) back to the manager. If a previously disconnected channel becomes available again, this is communicated to the manager after prior activation via ChannelReestablished(), specifying the GlobalChannelIdentifier ([SWS_DM_00313], [SWS_DM_09021]).

Regarding ownership, strict buffer transfer using unique-pointer semantics applies during message processing: Upon announcement of a message, the diagnostic core creates the object UdsMessagePtr and temporarily passes it to the handler for filling ([SWS_DM_00309]). After successful reception or in the event of a transmission abort, ownership of the message is returned entirely to the generic DM core ([SWS_DM_00310], [SWS_DM_00311]). All callback methods of the interface are classified as exception-safe (noexcept), but explicitly as not thread-safe ([SWS_DM_00309], [SWS_DM_00311]).

Usage Path

The regular sequence of UDS message reception is divided into two consecutive phases. First, the transport handler signals the start of a message via IndicateMessage() ([SWS_DM_00309]). Here, source and target address, addressing type (physical or functional), channel ID, total size, and a byte view of the initial payload data (payloadInfo) are passed. This advance information allows the diagnostic core to evaluate requests early, for example to recognize a functional Tester Present ([SWS_DM_00309]). If the core accepts the request, the manager returns the pair consisting of IndicationResult::kIndicationOk and the message buffer to be filled.

As soon as the transport handler has received the complete message, it forwards it via HandleMessage() to the session layer ([SWS_DM_00311]). This corresponds to the primitive T_Data.ind from ISO 14229-2. Interpretation: The required immediate return of HandleMessage() is likely implemented by handing it over to an internal queue of the session layer, since the actual processing must occur asynchronously in the background ([SWS_DM_00311]). Question Q-b6e97504ca3a3a95 (open) The handler confirms outgoing transmissions after completion via TransmitConfirmation() ([SWS_DM_00312]), whereas periodic messages are acknowledged via PeriodicTransmitConfirmation() ([SWS_DM_01069]).

Sequence diagram: Typical sequence of UDS message reception via IndicateMessage and HandleMessage. Sources: [SWS_DM_00309], [SWS_DM_00311].

Error Scenarios

If the DM core cannot accept an announced message, IndicateMessage() already fails. For this, the enumeration IndicationResult defines the error causes kIndicationOccupied (channel busy), kIndicationOverflow (buffer overflow), or kIndicationUnknownTargetAddress (unknown target address), whereupon no message buffer is provided ([SWS_DM_00309], [SWS_DM_00384]).

If an error occurs on the transport layer level during ongoing transmission after a successful indication, such that no HandleMessage() takes place anymore, the handler must mandatory call NotifyMessageFailure() ([SWS_DM_00310]). As a result, the previously allocated message buffer is returned to the session layer in a controlled manner and released. For transmit operations, TransmitConfirmation() reports the result via TransmissionResult; if sending fails on the network level, kTransmitFailed is transmitted ([SWS_DM_00307], [SWS_DM_00312]).

use

The method ChannelReestablished of class apext::diag::uds_transport::UdsTransportProtocolMgr serves as feedback from a UDS transport protocol implementation to Diagnostic Management (DM) that a communication channel is available again after a (re-)start [SWS_DM_00313]. The transport protocol implementation calls this method exactly once as soon as the re-availability of the network channel represented by ChannelID is detected [SWS_DM_00358]. As a parameter, globalChannelId is passed, consisting of the tuple of own handlerIdent and the ChannelID [SWS_DM_00358].

Interaction and Lifecycle

A prerequisite for the notification is a preceding call of NotifyReestablishment [SWS_DM_00313], [SWS_DM_00356]. A typical use case is performing an ECU reset (UDS service 0x11) with the option of a positive response after the restart [SWS_DM_00326]. In order to ensure notification even after a restart of the DM, the notification request must be persistently stored by the transport protocol [SWS_DM_00359].

Error Handling and Concurrency

The function has no return value and is specified as noexcept (exception safe) [SWS_DM_00313]. Since the interface is classified as not thread-safe (not thread-safe) [SWS_DM_00313], calling handlers might have to synchronize access externally. Question Q-aaf14893457cceb6 (open) As a timing constraint, the DM may process the call to ChannelReestablished only after the call to UdsTransportProtocolHandler::Start [SWS_DM_01744].

      Method HandleMessage serves to hand over a completely received, valid UDS request message from the transport layer to the session layer of Diagnostic Management ([SWS_DM_00311]).       Call and Parameters
      

      As soon as the transport protocol implementation has filled the payload of the buffer previously requested via IndicateMessage ([SWS_DM_00388]), it calls HandleMessage on the instance of apext::diag::uds_transport::UdsTransportProtocolMgr ([SWS_DM_00345]). message of type UdsMessagePtr is passed as an argument. Through the std::unique_ptr semantics, ownership of the UDS message is returned to the generic DM core ([SWS_DM_00311]). The function returns no value.

      • Asynchrony: The call must return immediately ("instantly returns") ([SWS_DM_00311]). Interpretation: The actual processing of the diagnostic request is likely continued asynchronously in a separate execution context in the DM core. Question Q-b8dd1a5f3d2dcdf0 (open)

      • Error case: The method is declared as noexcept and exception-safe ([SWS_DM_00311]). If reception or filling of the message fails, no call to HandleMessage must occur; instead, the error must be reported via NotifyMessageFailure ([SWS_DM_00310]).
        • 

      • Thread safety: The operation is specified as not thread-safe ([SWS_DM_00311]). Callers must synchronize parallel accesses to the same instance.
        •

      The interface belongs to the transport protocol layer and is to be distinguished from the application-side service processing method ara::diag::GenericUDSService::HandleMessage ([SWS_DM_00618]).
