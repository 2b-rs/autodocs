Context

The class ara::diag::SovdSwUpdate forms the interface for handling software updates via the Service-Oriented Vehicle Diagnostics (SOVD) protocol according to ASAM SOVD and ISO 17978-3 ([SWS_DM_01874], [SWS_DM_01796]). Within the AUTOSAR Adaptive Platform, there is a clear functional division of responsibilities: The actual business logic for performing and managing software updates remains in the adaptive application, while the functional cluster Diagnostics (Diagnostic Server Instance or Diagnostic Management) handles the underlying SOVD protocol (AUTOSAR_AP_SWS_Diagnostics §7.3 “Figure 7.4: SOVD Software Update API”).

As an abstract base class, SovdSwUpdate defines the callback interfaces that must be implemented by the application software. Incoming requests from external SOVD clients are analyzed by the Diagnostic Server Instance and delegated to the application via the corresponding methods of SovdSwUpdate (AUTOSAR_AP_SWS_Diagnostics §7.3 “SOVD Software Update API”).

Context diagram: Interaction partners and role distribution in the SOVD software update. Sources: [SWS_DM_01796], [SWS_DM_01874], AUTOSAR_AP_SWS_Diagnostics §7.3 “Figure 7.4: SOVD Software Update API”

Lifecycle

An application-specific instance is created via the parameterized constructor by specifying an instance identifier (ara::core::InstanceSpecifier) and the desired concurrency model (ConcurrencyType) ([SWS_DM_01910]). In doing so, the InstanceSpecifier references a PortPrototype declared in the software manifest, which must be typed to a DiagnosticSovdUpdateInterface ([SWS_DM_01910]). The concurrencyType specifies whether the callback methods of the instance are to be invoked in a thread-safe manner (kConcurrent) or sequentially or not thread-safe (kNotConcurrent) in the case of concurrent requests ([SWS_DM_01910]).

Instances of SovdSwUpdate are uniquely bound to a service port. The copy constructor and the assignment operator are therefore explicitly deleted (=delete) ([SWS_DM_01912], [SWS_DM_01914]). Move operations are defined as protected (protected) ([SWS_DM_01913], [SWS_DM_01915]).

After successful initialization, the application must explicitly activate the service using Offer() ([SWS_DM_01924]). Only this call causes the Diagnostic Manager (DM) to forward incoming SOVD requests to the registered handler methods. Before destroying the handler object, the service must be deregistered via StopOffer() to prevent further forwarding of requests ([SWS_DM_01925]). Teardown is completed via the virtual destructor ~SovdSwUpdate() ([SWS_DM_01911]).

Usage Path

The typical operational sequence comprises several consecutive phases of a software update:

  1. Service offering: The application instantiates its derived class from SovdSwUpdate and calls Offer() ([SWS_DM_01924]).
  2. Package registration and transfer: The Diagnostic Server forwards incoming registration requests from an SOVD client to RequestUpdatePackageRegistration() ([SWS_DM_01923]). The method returns a ara::core::Future with a tuple consisting of a write session (DataTransferWriteSession) and a unique package identifier (updatePackageId) ([SWS_DM_01923]). Interpretation: The actual data transfer of the update payload is likely handled via this provided write session (AUTOSAR_AP_SWS_Diagnostics §7.3 “Figure 7.4: SOVD Software Update API”).
  3. Package preparation: To prepare the installation, the Diagnostic Server calls PrepareUpdatePackage() ([SWS_DM_01800], [SWS_DM_01919]). Alternatively, an automated installation can be triggered via PutUpdatePackageAutomated() ([SWS_DM_01799], [SWS_DM_01918]).
  4. Package execution: The installation of the prepared update package is initiated by calling ExecuteUpdatePackage() ([SWS_DM_01801], [SWS_DM_01920]).
  5. Status query and inspection: During or after the process, detailed information and the status can be queried via GetUpdatePackageStatus() ([SWS_DM_01802], [SWS_DM_01921]), GetUpdatePackageDetails() ([SWS_DM_01917]), or the complete list via GetAllUpdates() ([SWS_DM_01797], [SWS_DM_01916]). Packages that are no longer required are removed via DeleteUpdatePackage() ([SWS_DM_01922]).

Sequence diagram: Interaction patterns for registration, installation, and status query of an update package. Sources: [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01802], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01923], [SWS_DM_01924]

Error Scenarios

Error conditions are divided into configuration and modeling errors, service state errors, and protocol-specific execution errors:

  • Model and instantiation errors: If the resolution of the InstanceSpecifier fails or references an inappropriate element, specific runtime violations are reported: InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, and InstanceSpecifierAlreadyInUseViolation if the identifier is already in use within the process ([SWS_DM_01910]).
  • Offer errors: The call to Offer() returns a ara::core::Result<void>. In the event of an error, this contains DiagOfferErrc::kAlreadyOffered if the service is already offered, or DiagOfferErrc::kConfigurationMismatch if the configuration does not match the diagnostic extract (DEXT) ([SWS_DM_01924]).
  • Execution and protocol errors: The asynchronous callback methods return results as ara::core::Future. In the event of an error, an applicable error code according to ASAM SOVD 1.1 or ISO 17978-3 must be stored in the future ([SWS_DM_01917], [SWS_DM_01918], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01921], [SWS_DM_01922], [SWS_DM_01923]).
  • Cancellation handling: A CancellationHandler is passed to all asynchronous methods. The application is responsible for querying this to cleanly terminate a prematurely aborted client conversation ([SWS_DM_01919], [SWS_DM_01920]).

<li><strong>Package registration and transfer:</strong> The Diagnostic Server forwards incoming registration requests from an SOVD client to <code>RequestUpdatePackageRegistration()</code> (<a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>). Interpretation: The actual data transfer of the update payload is likely handled via this provided write session (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=223">AUTOSAR_AP_SWS_Diagnostics §7.3 “Figure 7.4: SOVD Software Update API”</a>).</li>
<li><strong>Package preparation:</strong> To prepare the installation, the Diagnostic Server calls <code>PrepareUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01800" href="../spec/record.html?id=SWS_DM_01800">[SWS_DM_01800]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>). Alternatively, an automated installation can be triggered via <code>PutUpdatePackageAutomated()</code> (<a class="spec-record-ref" data-req="SWS_DM_01799" href="../spec/record.html?id=SWS_DM_01799">[SWS_DM_01799]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>).</li>
<li><strong>Package execution:</strong> The installation of the prepared update package is initiated by calling <code>ExecuteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01801" href="../spec/record.html?id=SWS_DM_01801">[SWS_DM_01801]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
<li><strong>Status query and inspection:</strong> During or after the process, detailed information and the status can be queried via <code>GetUpdatePackageStatus()</code> (<a class="spec-record-ref" data-req="SWS_DM_01802" href="../spec/record.html?id=SWS_DM_01802">[SWS_DM_01802]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>), <code>GetUpdatePackageDetails()</code> (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>), or the complete list via <code>GetAllUpdates()</code> (<a class="spec-record-ref" data-req="SWS_DM_01797" href="../spec/record.html?id=SWS_DM_01797">[SWS_DM_01797]</a>, <a class="spec-record-ref" data-req="SWS_DM_01916" href="../spec/record.html?id=SWS_DM_01916">[SWS_DM_01916]</a>). Packages that are no longer required are removed via <code>DeleteUpdatePackage()</code> (<a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>Error conditions are divided into configuration and modeling errors, service state errors, and protocol-specific execution errors:</p>
<ul>
<li><strong>Model and instantiation errors:</strong> If the resolution of the <code>InstanceSpecifier</code> fails or references an inappropriate element, specific runtime violations are reported: <code>InstanceSpecifierMappingIntegrityViolation</code>, <code>PortInterfaceMappingViolation</code>, <code>ProcessMappingViolation</code>, and <code>InstanceSpecifierAlreadyInUseViolation</code> if the identifier is already in use within the process (<a class="spec-record-ref" data-req="SWS_DM_01910" href="../spec/record.html?id=SWS_DM_01910">[SWS_DM_01910]</a>).</li>
<li><strong>Offer errors:</strong> The call to <code>Offer()</code> returns a <code>ara::core::Result&lt;void&gt;</code>. In the event of an error, this contains <code>DiagOfferErrc::kAlreadyOffered</code> if the service is already offered, or <code>DiagOfferErrc::kConfigurationMismatch</code> if the configuration does not match the diagnostic extract (DEXT) (<a class="spec-record-ref" data-req="SWS_DM_01924" href="../spec/record.html?id=SWS_DM_01924">[SWS_DM_01924]</a>).</li>
<li><strong>Execution and protocol errors:</strong> The asynchronous callback methods return results as <code>ara::core::Future</code>. In the event of an error, an applicable error code according to ASAM SOVD 1.1 or ISO 17978-3 must be stored in the future (<a class="spec-record-ref" data-req="SWS_DM_01917" href="../spec/record.html?id=SWS_DM_01917">[SWS_DM_01917]</a>, <a class="spec-record-ref" data-req="SWS_DM_01918" href="../spec/record.html?id=SWS_DM_01918">[SWS_DM_01918]</a>, <a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>, <a class="spec-record-ref" data-req="SWS_DM_01921" href="../spec/record.html?id=SWS_DM_01921">[SWS_DM_01921]</a>, <a class="spec-record-ref" data-req="SWS_DM_01922" href="../spec/record.html?id=SWS_DM_01922">[SWS_DM_01922]</a>, <a class="spec-record-ref" data-req="SWS_DM_01923" href="../spec/record.html?id=SWS_DM_01923">[SWS_DM_01923]</a>).</li>
<li><strong>Cancellation handling:</strong> A <code>CancellationHandler</code> is passed to all asynchronous methods. The application is responsible for querying this to cleanly terminate a prematurely aborted client conversation (<a class="spec-record-ref" data-req="SWS_DM_01919" href="../spec/record.html?id=SWS_DM_01919">[SWS_DM_01919]</a>, <a class="spec-record-ref" data-req="SWS_DM_01920" href="../spec/record.html?id=SWS_DM_01920">[SWS_DM_01920]</a>).</li>
</ul>
