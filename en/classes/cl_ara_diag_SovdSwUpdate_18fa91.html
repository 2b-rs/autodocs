Serves as an interface for processing software updates via the ASAM SOVD protocol in the AUTOSAR diagnostic server.

The class provides the application-side interface for processing standardized software updates via the SOVD protocol according to ASAM SOVD [SWS_DM_01796]. After instantiation, the application activates the forwarding of diagnostic requests to the specific update handlers via the method Offer() [SWS_DM_01924]. Packages are registered, prepared, installed automatically or manually, and deleted again via asynchronous methods. All data transfer- and lifecycle-relevant operations are processed in a non-blocking manner via futures.

Context

The class ara::diag::SovdSwUpdate defines the interface for implementing standardized software updates according to ASAM SOVD within the AUTOSAR Adaptive Platform [SWS_DM_01874]. Since the actual business logic of software updates does not reside in the Diagnostic Management (DM) functional cluster, execution remains with the respective application, while ara::diag::SovdSwUpdate concentrates on the standard-compliant processing of the underlying SOVD protocol AUTOSAR_AP_SWS_Diagnostics §7.4 “SOVD Software Update API - concept”. For uploading update files, transfer strategies are used as specified for the UDS service 0x38 (RequestFileTransfer) AUTOSAR_AP_SWS_Diagnostics §7.4 “SOVD Software Update API - concept”, [SWS_DM_01923].

Three essential components are involved in the processes: the external SOVD client, the Diagnostic Server (DM) instance for protocol and route management, and the application-specific handler implementation of ara::diag::SovdSwUpdate [SWS_DM_01796], [SWS_DM_01924].

Context diagram: Interaction of SOVD client, Diagnostic Server (DM), and ara::diag::SovdSwUpdate. Sources: [SWS_DM_01796], [SWS_DM_01924], AUTOSAR_AP_SWS_Diagnostics §7.4 “SOVD Software Update API - concept”

Lifecycle

Instantiation of ara::diag::SovdSwUpdate takes place via the constructor by specifying an ara::core::InstanceSpecifier that references a port prototype of a modeled DiagnosticSovdUpdateInterface, as well as a concurrency mode (ConcurrencyType: kConcurrent or kNotConcurrent) [SWS_DM_01910]. The constructor is specified to be thread-safe and exception-safe [SWS_DM_01910]. Representing a unique interface instance, the copy constructor and copy assignment operator are deleted (=delete) and protected [SWS_DM_01912], [SWS_DM_01914]. Move construction and move assignment are available as protected, but are not thread-safe [SWS_DM_01913], [SWS_DM_01915].

Destruction of the object is handled via the virtual destructor ~SovdSwUpdate(), which is considered not thread-safe [SWS_DM_01911]. Whether the virtual callback methods of the class must be executed concurrently depends directly on the ConcurrencyType passed to the constructor [SWS_DM_01910], [SWS_DM_01916].

Usage Path

Interpretation: Since the provided interface methods are declared pure virtual (=0), a derived application class is likely to implement them to perform the actual update execution, while the base class governs the platform integration.

The regular sequence is divided into the following phases:

  • Offering: After creating the object, the application calls Offer() to enable Diagnostic Management to forward incoming SOVD messages to this instance [SWS_DM_01924].
  • Information and registration: Existing update packages can be queried via GetAllUpdates() [SWS_DM_01797], [SWS_DM_01916]. If a new package is to be transferred, the Diagnostic Server requests a registration via RequestUpdatePackageRegistration(), which asynchronously provides a write session (DataTransferWriteSession) along with an update package ID [SWS_DM_01923]. Details and status are determined via GetUpdatePackageDetails() and GetUpdatePackageStatus() [SWS_DM_01802], [SWS_DM_01917], [SWS_DM_01921].
  • Installation or deletion: The installation can either be initiated automatically via PutUpdatePackageAutomated() [SWS_DM_01799], [SWS_DM_01918] or take place in two steps via PrepareUpdatePackage() [SWS_DM_01800], [SWS_DM_01919] followed by ExecuteUpdatePackage() [SWS_DM_01801], [SWS_DM_01920]. Packages that are no longer needed are removed via DeleteUpdatePackage() [SWS_DM_01922].
  • Termination: Prior to shutdown, the application deactivates message forwarding by calling StopOffer() [SWS_DM_01925].

Sequence diagram: Typical sequence of package registration and installation via SOVD. Sources: [SWS_DM_01799], [SWS_DM_01800], [SWS_DM_01801], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923], [SWS_DM_01924]

Error Scenarios

When offering the services via Offer(), specific errors can occur in the return type ara::core::Result<void>: DiagOfferErrc::kAlreadyOffered if the instance is already offered, and DiagOfferErrc::kConfigurationMismatch if the configuration does not match the diagnostic extract (DEXT) [SWS_DM_01924].

If the constructor is called with an incorrect model state, architectural violations are reported, including InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, or InstanceSpecifierAlreadyInUseViolation [SWS_DM_01910].

All functional update operations return a ara::core::Future that transports error codes according to ASAM SOVD 1.1 or ISO 17978-3 in case of an error [SWS_DM_01917], [SWS_DM_01919], [SWS_DM_01920], [SWS_DM_01923]. In addition, all asynchronous methods receive a CancellationHandler through which a premature abort of the ongoing diagnostic connection is signaled [SWS_DM_01916], [SWS_DM_01919], [SWS_DM_01923].

It initiates the server-side removal of an update package.

The call takes place asynchronously and returns a ara::core::Future<void>, which indicates successful completion or provides an error object [SWS_DM_01922]. The signature requires the following input parameters:

  • updatePackageId: Designates as ara::core::String the unique ID of the update package to be deleted.
  • metaInfo: Passes additional context information of the request as MetaInfo const&.
  • cancellationHandler: Transmits an object of type CancellationHandler that informs whether the current conversation was cancelled.

If an error occurs during processing, the Future is populated with a corresponding SOVD error. The specification prescribes the use of appropriate error codes from ASAM SOVD 1.1 or ISO 17978-3 for this purpose [SWS_DM_01922].

Regarding concurrency, the method is defined as conditionally thread-safe: Whether the implementation must be executed thread-safe or non-thread-safe is determined via the ConcurrencyType passed in the constructor [SWS_DM_01922]. In addition, the function is declared as noexcept and exception-safe, which is why no exceptions may escape.
