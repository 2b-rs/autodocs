Defines the Firewall error domain for translating error codes into descriptive texts and module-specific exceptions.

The class represents the error domain of the Firewall module and links module-specific error codes with error texts and exceptions [AP_SWS_Fw_83007]. It provides descriptions for error codes and enables module-specific exceptions to be thrown selectively [AP_SWS_Fw_83011], [AP_SWS_Fw_83012]. Because the default constructor is deleted, usage occurs via a pre-instantiated domain whose interfaces are implemented as thread-safe [AP_SWS_Fw_83009].

Context

Class ara::fw::FwErrorDomain represents the specific error domain for the Firewall module (fw) within the AUTOSAR Adaptive Platform. As a specialization of ara::core::ErrorDomain, it defines the semantic context for all error states that can occur during Firewall operations. Encapsulation in a dedicated domain ensures that error codes of the Firewall module can be uniquely identified platform-wide and distinguished from errors of other subsystems.

Standardized type aliases belong to the central components of the interface: Errc references the underlying enumeration FwErrc [AP_SWS_Fw_83007], while Exception acts as an alias for the module-specific exception base class FwException [AP_SWS_Fw_83008]. Via method Name(), the class provides the identifier of the error domain [AP_SWS_Fw_83010]. The primary interaction partners are the functional Firewall implementation, the application software, and the higher-level error handling infrastructure of ara::core.

Lifecycle

The instantiation of ara::fw::FwErrorDomain is subject to strict requirements: the parameterless default constructor is explicitly declared as deleted (FwErrorDomain() = delete) [AP_SWS_Fw_83009]. Direct creation of instances on the stack or heap by users is thus prevented. In accordance with the platform standard for error domains, the domain instance typically exists as a global singleton that applications presumably access via a platform-wide access function.

Regarding ownership, the error domain remains under the control of the runtime environment and has a static lifetime over the entire process runtime. Because multiple execution paths can access error descriptions concurrently, the central inspection methods Name() and Message() are specified as thread-safe [AP_SWS_Fw_83010], [AP_SWS_Fw_83011]. Method ThrowAsException() also guarantees thread safety during concurrent access [AP_SWS_Fw_83012].

Usage Path

The typical usage path is divided into error generation on the part of the module, evaluation by the caller, and, if applicable, conversion into a C++ exception. If an operation of the Firewall fails, an error based on enumeration Errc [AP_SWS_Fw_83007] and encapsulated as ara::core::ErrorCode is delivered to the caller. The user can subsequently query detailed error texts via the domain or control error handling deterministically.

For diagnosis or logging, the application passes the error code to method Message(), which returns the associated textual description as a pointer to constant char [AP_SWS_Fw_83011]. If execution is instead to be continued via C++ exceptions, ThrowAsException() is called with the respective error object, whereupon the method instantiates and throws an instance of Exception (FwException) [AP_SWS_Fw_83008], [AP_SWS_Fw_83012].

Sequence diagram: Typical flow of error handling and exception throwing via FwErrorDomain. Sources: [AP_SWS_Fw_83007], [AP_SWS_Fw_83011], [AP_SWS_Fw_83012].

Error Scenarios

The information-querying methods offer strict guarantees against runtime errors. Both Name() and Message() are declared with noexcept and thus guarantee that no exceptions are thrown during the query of identifiers and error texts [AP_SWS_Fw_83010], [AP_SWS_Fw_83011]. A precondition for Message() is passing a valid error value of type CodeType [AP_SWS_Fw_83011].

In contrast, ThrowAsException() is explicitly annotated with noexcept(false), since its primary task consists in deliberately interrupting the regular control flow by throwing an FwException [AP_SWS_Fw_83012]. According to the specification, this function is classified as not exception safe, since it creates and emits an exception. Callers must therefore ensure that calls to ThrowAsException() are embedded in corresponding try-catch blocks if premature program termination is to be avoided.
