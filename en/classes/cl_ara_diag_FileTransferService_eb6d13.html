Context

The interface class ara::diag::FileTransferService ([SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §8.18 “Header: ara/diag/file_transfer.h”) provides the functional abstraction for file-based diagnostic transfers in AUTOSAR Adaptive. It serves to implement the UDS service 0x38 (RequestFileTransfer) and enables the standardized exchange of files and directory information across process boundaries (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”).

Three main components are involved in the file transfer sequences:

  • Diagnostic client: Initiates file operations via standardized UDS service calls (RequestFileTransfer 0x38, TransferData 0x36, and RequestTransferExit 0x37).
  • Diagnostic Management (Diagnostic Server Instance): Receives the diagnostic messages of the client, handles protocol processing, and forwards the requests to the registered service instance (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 “Realization of modeOfOperation”).
  • Adaptive Application: Implements the functional callback methods of ara::diag::FileTransferService, creates data sessions, and accesses the local file system.

The architecture supports different strategies for data exchange (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”):

  • Simple: Copies the data between the Adaptive Application and Diagnostic Management; suitable for smaller file sizes.
  • Zero Copy: Avoids memory copies between the application and Diagnostic Management for resource efficiency with large amounts of data.
  • OS File System Handle: Passing native operating system file handles for direct transfer without copying overhead in the diagnostic stack.

Context diagram: Interaction partners and role distribution in file-based diagnostic transfer. Sources: [SWS_DM_01320], AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”.

Lifecycle

The class ara::diag::FileTransferService acts as a base class for application-specific diagnostic handlers. Upon instantiation, the constructor expects a ara::core::InstanceSpecifier referencing a modeled PortPrototype of type DiagnosticRequestFileTransferInterface, as well as the definition of concurrency via ConcurrencyType ([SWS_DM_01325]).

The instance and ownership relationships are strictly regulated:

  • Copy protection: The class represents a unique instance; copy constructor ([SWS_DM_01327]) and copy assignment operator ([SWS_DM_01329]) are deleted (delete).
  • Movability: Move constructor ([SWS_DM_01328]) and move assignment operator ([SWS_DM_01330]) are defined in scope protected.
  • Destruction: The virtual destructor ~FileTransferService() ([SWS_DM_01326]) ensures proper cleanup of derived classes.

The functional lifecycle is actively controlled by the application:

  1. Provided: After creation, Diagnostic Management does not yet forward any requests to the instance.
  2. Active (Offered): By calling Offer(), Diagnostic Management is authorized to forward requests to the service handler ([SWS_DM_01336]).
  3. Deactivated: Calling StopOffer() revokes authorization and prevents the forwarding of new requests ([SWS_DM_01337]).

With regard to thread safety, AUTOSAR differentiates: The callbacks of the interface align their concurrency behavior with the ConcurrencyType (kConcurrent or kNotConcurrent) passed in the constructor ([SWS_DM_01325]). In contrast, administrative methods such as Offer(), StopOffer(), and the destructor are specified as not thread-safe ([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

State diagram: Lifecycle phases of a FileTransferService instance. Sources: [SWS_DM_01325], [SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337].

Usage Path

The interface covers all operating modes defined in UDS service 0x38 via dedicated pure virtual methods:

  • RequestReadFile: Called for modeOfOperation ReadFile (0x04) ([SWS_DM_01314], [SWS_DM_01331]).
  • RequestWriteFile: Called for modeOfOperation ReplaceFile (0x03) with WriteFileMode::kReplace ([SWS_DM_01313], [SWS_DM_01324], [SWS_DM_01333]) as well as for kAdd.
  • RequestResumeWriteFile: Called for modeOfOperation ResumeFile (0x06) ([SWS_DM_01316], [SWS_DM_01334]).
  • RequestReadDirectory: Called for modeOfOperation ReadDir (0x05) ([SWS_DM_01315], [SWS_DM_01332]).
  • DeleteFile: Performs the complete deletion of a file for modeOfOperation DeleteFile ([SWS_DM_01335]).

A typical usage path for reading a file (ReadFile) takes place in the following steps:

  1. Offering: The application instantiates its derived service class and activates the interface using Offer() ([SWS_DM_01336]).
  2. Initial transfer request: The diagnostic client sends the UDS command 0x38 (ReadFile). The Diagnostic Server forwards the call to the application via RequestReadFile(fileName, dataFormatIdentifier, metaInfo, cancellationHandler) ([SWS_DM_01314], [SWS_DM_01331]).
  3. Session establishment: The application checks the request and asynchronously returns a ara::core::Future that contains a tuple of an initialized DataTransferReadSession and the file sizes (FileSizes) ([SWS_DM_01331]). Diagnostic Management responds positively to the UDS request.
  4. Block transfer: For each subsequent TransferData request (0x36) from the client, the Diagnostic Server calls the read methods of the handlers registered in the session ([SWS_DM_01317]).
  5. Transfer termination: After the complete transfer, the client sends RequestTransferExit (0x37). The Diagnostic Server then calls the session's Exit method ([SWS_DM_01318]) and completes the process.

Sequence diagram: Sequence of a file read operation according to UDS services 0x38, 0x36, and 0x37. Sources: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331], [SWS_DM_01336].

Error Scenarios

Error conditions are intercepted and reported in different layers of the system:

  • Construction and modeling errors: If the configuration does not correspond to the system model, the instantiation fails ([SWS_DM_01325]):
    • InstanceSpecifierMappingIntegrityViolation: The identifier cannot be resolved or does not point to a PortPrototype.
    • PortInterfaceMappingViolation: The DEM port typed by DiagnosticRequestFileTransferInterface is missing the DiagnosticServiceGenericMapping.
    • ProcessMappingViolation: No matching runtime process exists for the modeled process.
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already being used within the process.
  • Multiple offering: A repeated call to Offer() on an already active instance returns an error with DiagOfferErrc::kAlreadyOffered ([SWS_DM_01336]).
  • Diagnostic negative responses (NRC): If file operations cannot be executed successfully in the virtual methods, the application signals this via the returned ara::core::Future with a UDS Negative Response Code (NRC) from the error domain DiagUdsNrcErrc according to ISO 14229-1 ([SWS_DM_01331], [SWS_DM_01332], [SWS_DM_01333], [SWS_DM_01334], [SWS_DM_01335]).
  • Operation cancellation: Via the parameter CancellationHandler, the application can continuously check the cancellation status with cancellationHandler.IsCanceled() during asynchronous file operations or register a notification via cancellationHandler.SetNotifier() to immediately release resources in the event of an early session termination ([SWS_DM_01331], [SWS_DM_01335]).
