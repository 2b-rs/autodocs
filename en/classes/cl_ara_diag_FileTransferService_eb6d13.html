Enables adaptive applications to provide file and directory operations for UDS diagnostic services.

The service interface serves to connect application-specific file transfers to Diagnostic Management for the UDS service RequestFileTransfer ([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”). After instantiation, the application activates the forwarding of incoming file requests with Offer() and processes file operations such as read, write, or delete asynchronously via specialized handler methods ([SWS_DM_01336]). For read and write operations, the service provides session objects through which the actual data transfer is handled. Instances of the class are non-copyable and require a fixed binding via an instance specifier.

Context

The class ara::diag::FileTransferService defines the diagnostic interface for implementing the UDS service RequestFileTransfer (0x38) in the AUTOSAR Adaptive Platform ([SWS_DM_01320], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”). It acts as a service interface between Diagnostic Management (DM or Diagnostic Server) and the concrete diagnostic application to flexibly handle the reading, writing, resuming, and deleting of files or directories across process boundaries (SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”).

Three parties are typically involved in a file transfer scenario: the external UDS client (diagnostic tester), the Diagnostic Server as mediator, and the adaptive application that inherits from FileTransferService. For incoming diagnostic requests, the Diagnostic Server delegates the request to the implemented virtual methods of the service ([SWS_DM_01313], [SWS_DM_01314]). For subsequent data transfers (UDS 0x36 TransferData) and completion (UDS 0x37 RequestTransferExit), Diagnostic Management directly accesses handler classes provided via session objects (DataTransferReadSession or DataTransferWriteSession) ([SWS_DM_01317], [SWS_DM_01318]).

Context diagram: Interaction between UDS client, Diagnostic Management, service implementation, and transfer sessions. Sources: [SWS_DM_01317], [SWS_DM_01318], SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”.

Lifecycle

An instance of FileTransferService is created by specifying a modeled ara::core::InstanceSpecifier and the concurrency model ConcurrencyType ([SWS_DM_01325]). Via ConcurrencyType, it is defined whether callback methods of the class must be implemented thread-safe (kConcurrent) or non-thread-safe (kNotConcurrent) ([SWS_DM_01325], [SWS_DM_01331]). As a protected single function, the class is non-copyable ([SWS_DM_01327], [SWS_DM_01329]), but supports move semantics ([SWS_DM_01328], [SWS_DM_01330]).

After instantiation, the service must be explicitly activated via the method Offer() so that Diagnostic Management forwards incoming requests ([SWS_DM_01336]). With StopOffer(), forwarding can be deactivated again at any time ([SWS_DM_01337]). Interpretation: It is likely required to call StopOffer() before the object is destroyed by the virtual destructor ~FileTransferService() ([SWS_DM_01326]) in order to avoid orphaned callback accesses by Diagnostic Management. Question Q-3c5c406a144ced0c (open) Neither Offer(), StopOffer() nor the destructor are thread-safe ([SWS_DM_01326], [SWS_DM_01336], [SWS_DM_01337]).

State diagram: State transitions of a FileTransferService instance between instantiation, offering, and termination. Sources: [SWS_DM_01325], [SWS_DM_01336], [SWS_DM_01337], [SWS_DM_01326].

Usage Path

The typical flow of a file operation is divided into configuration, triggering of the operation, and subsequent block transfer. First, for a UDS request 0x38 with mode ReadFile (0x04), Diagnostic Management forwards the call to RequestReadFile ([SWS_DM_01314], [SWS_DM_01331]). The application processes the file name as well as format and meta information and asynchronously returns a tuple of a DataTransferReadSession and the file sizes (FileSizes) via a ara::core::Future ([SWS_DM_01331]). Interpretation: Which transfer strategy (such as copy, zero-copy, or file system handle) is used is presumably determined by the application upon instantiating the respective session class (SWS_Diagnostics §7.3.2.8.20 “Service 0x38 – RequestFileTransfer”, [SWS_DM_01317]). Question Q-80b541ae6dd7cc34 (open)

After positive acknowledgment, the client requests the data blocks via TransferData (0x36). The Diagnostic Server then directly calls the Read method of the registered handler of DataTransferReadSession ([SWS_DM_01317]). As soon as all blocks have been transferred, the client completes the transaction with RequestTransferExit (0x37), whereupon the Diagnostic Server calls the handler's Exit method ([SWS_DM_01318]). Similar patterns apply to writing via RequestWriteFile ([SWS_DM_01313], [SWS_DM_01333]) with mode WriteFileMode ([SWS_DM_01324]), resuming via RequestResumeWriteFile ([SWS_DM_01316], [SWS_DM_01334]), directory reading via RequestReadDirectory ([SWS_DM_01315], [SWS_DM_01332]), or direct deletion via DeleteFile ([SWS_DM_01335]).

Sequence diagram: Flow of a read operation via UDS 0x38, 0x36, and 0x37. Sources: [SWS_DM_01314], [SWS_DM_01317], [SWS_DM_01318], [SWS_DM_01331].

Error Scenarios

Errors can occur in several phases:

  • Construction violations: If resolving or mapping InstanceSpecifier fails, modeling errors such as InstanceSpecifierMappingIntegrityViolation, PortInterfaceMappingViolation, ProcessMappingViolation, or InstanceSpecifierAlreadyInUseViolation occur ([SWS_DM_01325]).
  • Activation errors: A repeated call to Offer() when the service is already active returns the error DiagOfferErrc::kAlreadyOffered ([SWS_DM_01336]).
  • Diagnostic error codes (NRC): If an operation cannot be executed successfully, the callback methods in ara::core::Future return an appropriate negative UDS response code (NRC according to ISO 14229-1) via DiagUdsNrcErrc ([SWS_DM_01331], [SWS_DM_01333], [SWS_DM_01335]).
  • Cancellation handling: Via the passed CancellationHandler object, the application can check with IsCanceled whether the conversation was cancelled, or register a notification function for asynchronous cancellations via SetNotifier ([SWS_DM_01331], [SWS_DM_01335]).

Upon invocation, three parameters are passed [SWS_DM_01335]:

  • fileName (ara::core::String): Path specification and name of the destination file (interpretation: despite the editorial specification text "file to read", this is the file to be deleted). Question Q-cdbe1185bb030e87 (open)

                  use
                  

                  Method Offer of class ara::diag::FileTransferService registers the handler with Diagnostic Management (DM) so that it can forward incoming file transfer diagnostic requests to the instance [SWS_DM_01336]. The call is parameterless and synchronous. ara::core::Result<void> serves as the return type, indicating the success of the registration or an error that occurred [SWS_DM_01336].
                  


                  Error handling
                  

                  If an error occurs during offering, the function returns an erroneous ara::core::Result. If the service was already successfully offered previously for the respective instance, the specific error code DiagOfferErrc::kAlreadyOffered is returned with rollback semantics [SWS_DM_01336].
                  


                  Concurrency and Limitations
                  

                  The function is declared as exception safe (exception safe) and noexcept, but is considered not thread-safe (not thread-safe) [SWS_DM_01336]. Calls on the same service instance must therefore not be executed unprotected in parallel from multiple threads.
