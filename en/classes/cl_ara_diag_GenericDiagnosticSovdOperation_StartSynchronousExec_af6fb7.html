Context

As part of ASAM SOVD (Service-Oriented Vehicle Diagnostics), the AUTOSAR Adaptive Platform provides standardized interfaces to provide diagnostic operations via modern, service-oriented protocols. According to [SWS_DM_01396] (SWS Diagnostics §7.3.3.5.5.5 “Operations – Start execution of an operation”), the Diagnostic Server instance provides the method "Start Execution of an Operation" for each configured DiagnosticSovdOperationStart element.

If a synchronous SOVD operation is requested by an external client, the Diagnostic Manager (DM) delegates the call to the implementing application and calls ara::diag::GenericDiagnosticSovdOperation::StartExecution for this purpose ([SWS_DM_02174]). The structure ara::diag::GenericDiagnosticSovdOperation::StartSynchronousExecutionResponse ([SWS_DM_02208], SWS Diagnostics §8.62.4 “Struct: StartSynchronousExecutionResponse”) serves as a structured response of the application handler for synchronous operation sequences.

It acts as a pure information carrier between the adaptive application and Diagnostic Management: The DM takes the result data (DiagnosticSovdContentData) from the structure and maps it directly to the attribute parameters of the outgoing SOVD response body ([SWS_DM_02176]).

Lifecycle

The structure StartSynchronousExecutionResponse is defined as a pure data type (struct) ([SWS_DM_02208]). It has no independent state machine and does not manage any long-lived system resources.

  • Creation: Instantiation takes place directly within the application-specific implementation of StartExecution as soon as the synchronous diagnostic functionality has been processed successfully.
  • Ownership and transfer: Interpretation: The structure is typically created as a value object on the stack, populated with the result data, and passed to the Diagnostic Manager as a return value (for example, wrapped in a result or future type).
  • Destruction: As soon as the DM has extracted the contained DiagnosticSovdContentData according to [SWS_DM_02176] and serialized it into the SOVD protocol message, the object is discarded and its memory is released.
  • Concurrency: Since synchronous operations are executed and returned in the context of the responsible thread, the object acts thread-locally and does not require separate synchronization.

Usage Path

The typical workflow for using the structure is divided into the following phases:

  1. Request by SOVD client: A client initiates the execution of an SOVD operation via the network ([SWS_DM_01396]).
  2. Invocation of the application handler: After successful pre-verification, the Diagnostic Manager calls method StartExecution of the adaptive application ([SWS_DM_02174]).
  3. Return of the result structure: The application executes the operation synchronously and returns a populated instance of StartSynchronousExecutionResponse ([SWS_DM_02208]).
  4. Creation of the SOVD response: The DM processes the content data contained in the structure and sets the parameters attribute of the SOVD response ([SWS_DM_02176]).
  5. Response transmission: The generated SOVD response body is sent to the external client.

Sequence diagram: Sequence of a synchronous SOVD operation execution and return of the result structure. Sources: [SWS_DM_01396], [SWS_DM_02174], [SWS_DM_02176], [SWS_DM_02208].

Error Scenarios

During synchronous operation processing, the following error situations are relevant in connection with the return structure:

  • Failure of operation execution: If execution within the application fails, an error status is likely to be signaled to the DM via the general error mechanism of the Adaptive Platform instead of a valid StartSynchronousExecutionResponse.
  • Failed preconditions: If the upstream validation of the proximity check (Proximity Challenge) fails, the call to StartExecution ([SWS_DM_02174]) is omitted completely, so that no instance of StartSynchronousExecutionResponse is created.
  • Inconsistent payload: If the data passed within the structure does not comply with the specifications of the associated operation, the DM presumably cannot generate the parameters attribute according to [SWS_DM_02176] without errors, leading to an error protocol on the SOVD level.
