Context

The class ara::shwa::ErrorHandler provides a central error handling mechanism in module shwa of the AUTOSAR Adaptive Platform. Its primary responsibility lies in receiving and processing module-specific error events represented via the type ara::shwa::ShwaErrorCode [AP_SWS_SHWA_00508]. During initialization, the class interacts closely with an application component that provides a handler routine in the form of a callback function with the signature void(ara::core::ErrorCode) [AP_SWS_SHWA_00507]. Through this design, the ErrorHandler acts as a link between internal error detection and the application's error handling logic, where notification of the application presumably occurs via the passed callback.

Lifecycle

The lifecycle of an instance of ara::shwa::ErrorHandler is controlled via the factory pattern. Direct instantiation via a parameterless constructor is not possible because the default constructor is explicitly deleted [AP_SWS_SHWA_00502]. Creation takes place instead via the static factory method Create [AP_SWS_SHWA_00507].

In terms of ownership, Create transfers ownership of the created instance to the caller in the form of a std::unique_ptr<ErrorHandler>, wrapped in a ara::core::Result [AP_SWS_SHWA_00507]. The class implements strict uniqueness semantics: both the copy constructor [AP_SWS_SHWA_00503] and the copy assignment operator [AP_SWS_SHWA_00504] are deleted. Likewise, the move constructor [AP_SWS_SHWA_00505] and the move assignment operator [AP_SWS_SHWA_00506] are declared as deleted. An instance is thus stationary in memory, bound to the lifetime of the managing std::unique_ptr, and can neither be copied nor moved. Destruction of the object occurs as soon as the std::unique_ptr is reset or leaves its scope.

With regard to concurrency, the creation method Create is specified as thread-safe [AP_SWS_SHWA_00507]. In contrast, the method HandleError is explicitly designated as not thread-safe [AP_SWS_SHWA_00508], which means that concurrent accesses to an instance must be synchronized by the application software.

Usage Path

The typical workflow when using the class is divided into three consecutive phases:

  1. Creation and configuration: The application defines a handler routine of type std::function<void(ara::core::ErrorCode)> and calls ErrorHandler::Create [AP_SWS_SHWA_00507].
  2. Evaluation of the result: The returned ara::core::Result is checked, and the std::unique_ptr<ErrorHandler> contained therein is retained for later calls.
  3. Error handling: When an error occurs, the application calls HandleError with the corresponding ara::shwa::ShwaErrorCode [AP_SWS_SHWA_00508]. The instance processes the error code and presumably forwards it to the previously registered handler callback.
  4. Release: When the std::unique_ptr is destroyed or reset, the instance is properly deallocated.

Error Scenarios

When considering errors, two aspects of the interface are relevant:

  • Instantiation failure: Although the factory method Create does not specify standardized error codes [AP_SWS_SHWA_00507], it returns a ara::core::Result. Should creation fail (for example due to lack of memory), the result object is likely to contain an error status. Create is specified as noexcept and exception-safe (exception safe) [AP_SWS_SHWA_00507].
  • Exception safety during error processing: The method HandleError accepts values of type ara::shwa::ShwaErrorCode [AP_SWS_SHWA_00508]. It is explicitly declared as not exception-safe (not exception safe) and not thread-safe (not thread-safe) [AP_SWS_SHWA_00508]. This implies that uncoordinated parallel calls or exceptions occurring during error handling can lead to inconsistent states and must be avoided by the caller.

<li><strong>Release:</strong> When the <code>std::unique_ptr</code> is destroyed or reset, the instance is properly deallocated.</li>

<h4>Error Scenarios</h4>
<p>When considering errors, two aspects of the interface are relevant:</p>
<ul>
<li><strong>Instantiation failure:</strong> Although the factory method <code>Create</code> does not specify standardized error codes <a class="spec-record-ref" data-req="AP_SWS_SHWA_00507" href="../spec/record.html?id=AP_SWS_SHWA_00507">[AP_SWS_SHWA_00507]</a>, it returns a <code>ara::core::Result</code>. Should creation fail (for example due to lack of memory), the result object is likely to contain an error status. <code>Create</code> is specified as <code>noexcept</code> and exception-safe (<code>exception safe</code>) <a class="spec-record-ref" data-req="AP_SWS_SHWA_00507" href="../spec/record.html?id=AP_SWS_SHWA_00507">[AP_SWS_SHWA_00507]</a>.</li>
<li><strong>Exception safety during error processing:</strong> The method <code>HandleError</code> accepts values of type <code>ara::shwa::ShwaErrorCode</code> <a class="spec-record-ref" data-req="AP_SWS_SHWA_00508" href="../spec/record.html?id=AP_SWS_SHWA_00508">[AP_SWS_SHWA_00508]</a>. It is explicitly declared as not exception-safe (<code>not exception safe</code>) and not thread-safe (<code>not thread-safe</code>) <a class="spec-record-ref" data-req="AP_SWS_SHWA_00508" href="../spec/record.html?id=AP_SWS_SHWA_00508">[AP_SWS_SHWA_00508]</a>. This implies that uncoordinated parallel calls or exceptions occurring during error handling can lead to inconsistent states and must be avoided by the caller.</li>
</ul>
