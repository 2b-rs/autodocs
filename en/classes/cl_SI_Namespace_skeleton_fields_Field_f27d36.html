Enables the service skeleton to provide, update, and process field requests in a typed manner.

The class <SI-Namespace>::skeleton::fields::<Field> provides a field of a ServiceInterface on the server side and combines getter, setter, and notification functions for the provided service. The provider application registers asynchronous handlers ([SWS_CM_00114], [SWS_CM_00116]) for incoming read and write accesses and actively distributes value changes to subscribing clients via the method Update ([SWS_CM_00119]). In doing so, passed handlers must be valid, while send calls must adhere to the configured minimum send interval to avoid errors such as kMinimumSendIntervalViolationError.

Context

The template class <SI-Namespace>::skeleton::fields::<Field> encapsulates the server-side representation of a field modeled in the ServiceInterface within Adaptive Communication Management. For each field defined in the service interface, the middleware generates a corresponding class instance in the namespace skeleton::fields using the header path #include "<SiNamespaceDerivedDirectoryPath>/<SiShortname>_skeleton.h". A field combines functional characteristics of data transfers and method calls by optionally featuring a getter, a setter, and a notification function. The associated data type of the field value is provided via the type alias FieldType ([SWS_CM_11402]). Central interaction partners include the providing provider application, the skeleton field instance as mediator, the subscribing service consumers (proxies), and optional execution contexts in the form of an executor ([SWS_CM_11360], [SWS_CM_11362]).

Context diagram: Interaction partners of the skeleton field class during requests and notifications. Sources: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360].

Lifecycle

The lifetime of the field instance is tightly coupled to the higher-level service skeleton instance. Interpretation: The field instance is presumably instantiated as a member object of the associated skeleton class and fully shares its lifecycle. Question Q-dedeaea09a8abb20 (open) The availability of individual interface methods directly depends on the definition in the software design: The method RegisterGetHandler exists only if the field was configured with Field.hasGetter == TRUE ([SWS_CM_00114]), whereas RegisterSetHandler requires the presence of a setter via Field.hasSetter == TRUE ([SWS_CM_00116]). To protect communication against end-to-end transport errors, the application can register a specific handler via SetTransportFaultConditionHandler ([SWS_CM_00096]) and remove it again if needed using UnsetTransportFaultConditionHandler ([SWS_CM_00098]). Regarding concurrency, the overloads with the template parameter ExecutorT (such as ara::core::Executor) offer the possibility of shifting the execution of callback functions to a defined asynchronous execution context ([SWS_CM_11360], [SWS_CM_11362], [SWS_CM_00097], AUTOSAR_AP_EXP_ARAComAPI p. 11).

Usage Path

The regular operational flow is divided into configuring the callback functions, processing queries, and actively sending data updates:

Interpretation: Registering the handlers is presumably expediently performed prior to offering the service in order to be able to seamlessly serve incoming requests. Question Q-617e65d056af24f9 (open) If a getter is present, the application binds a callback function via RegisterGetHandler that returns a ara::core::Future<FieldType> ([SWS_CM_00114]). For modifying accesses, it registers a handler via RegisterSetHandler that receives and processes the new value and likewise provides the resulting state asynchronously via a future ([SWS_CM_00116]). If the service provider wants to update the field value independently, it calls the method Update with the new value ([SWS_CM_00119], AUTOSAR_AP_EXP_ARAComAPI p. 11). This resets the internal state of the field. If the field was modeled with a notification function (Field.hasNotifier == TRUE), Update triggers the immediate transmission of the changed data value to all registered subscribers ([SWS_CM_00119], [SWS_CM_00120], [SWS_CM_00162]).

Sequence diagram: Typical sequence of handler registration, request processing, and data update. Sources: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119].

Error Scenarios

Error conditions manifest either as violations of programming contracts during registration or as transmission errors at runtime. All registration methods for handlers—RegisterGetHandler, RegisterSetHandler, and SetTransportFaultConditionHandler—are specified as noexcept and possess the exception guarantee exception safe ([SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00096]). As a precondition, the passed callable object must exist and must not be null; non-observance triggers an InvalidHandlerViolation ([SWS_CM_00114], [SWS_CM_11360], [SWS_CM_00116], [SWS_CM_11362], [SWS_CM_00096], [SWS_CM_00097]).

During active updates via Update, error feedback is provided via the return type ara::core::Result<void> ([SWS_CM_00119]). If an error occurs, the result object returns an error code from ara::com::ComErrc. In particular, sending at shorter intervals than specified by the deployment attribute ServiceInterfaceDeploymentElement.minimumSendInterval leads to the return of the error ComErrc::kMinimumSendIntervalViolationError ([SWS_CM_00119]).

void RegisterGetHandler (std::function< ara::core::Future< FieldType >()> handler) noexcept;

Register a callback function to be invoked when a Get() request is received. The method exists only if the offered service contains a Field and Field.hasGetter ==TRUE

AI-GENERATED unreviewed Model: gemini-3.8-flash-medium · Effort: medium · Temperature: nicht steuerbar · Prompt: 01ae49e1e2d8 Provenance

use

The method RegisterGetHandler is called server-side on the field object of a skeleton ([SWS_CM_00114]). It exists in the generated code exclusively if a getter was configured for the respective field in the interface description (Field.hasGetter == TRUE) (EXP ARAComAPI §5.4.8.1 “Registering Getters”). A callback handler of type std::function<ara::core::Future<FieldType>()> is passed, which is called by the binding implementation upon an incoming Get() request from a proxy.

Registering such a handler is entirely optional (EXP ARAComAPI §5.4.8.1 “Registering Getters”). Typically, the service implementation does not require a getter handler because Communication Management caches the value most recently set via Update() and answers proxy requests autonomously. A handler is particularly useful when determining the field value is time-consuming or computationally intensive and should therefore only occur asynchronously via the promise/future pattern when actually required.

Error Handling and Boundary Conditions

The function has no return value, is declared as noexcept, and is exception-safe (exception safe) ([SWS_CM_00114]). If the passed callable does not exist or is null, the error InvalidHandlerViolation occurs ([SWS_CM_00114]).

Interaction

In contrast to RegisterSetHandler, whose invocation is mandatory when a setter is present (EXP ARAComAPI §5.4.8.2 “Registering Setters”), RegisterGetHandler remains purely optional. If the handler is to be processed asynchronously in a specific execution context, the overloaded template function with ExecutorT is additionally available ([SWS_CM_11360]).
