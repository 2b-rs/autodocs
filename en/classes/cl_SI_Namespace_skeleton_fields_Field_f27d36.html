Context

The C++ class <Field> in namespace <SI-Namespace>::skeleton::fields represents the server-side interface of a single field defined in a ServiceInterface in the role field (module com of the AUTOSAR Adaptive Platform). A field combines state data with optional read (Get), write (Set), and notification mechanisms (Notifier). The associated data type is provided via the type alias FieldType ([SWS_CM_11402]).

The class mediates between the following main interaction partners:

  • Provider application: The actual service implementation. It registers callback functions for incoming read and write operations and initiates value updates.
  • Skeleton field instance (<Field>): Manages the registered callbacks, monitors invocation conditions, and acts as a link between service logic and transmission infrastructure.
  • Communication layer and clients: Forwards remote read and write requests from service clients and transmits Notifier notifications to active subscribers.

In addition, an execution context such as ara::core::Executor can be integrated via the template argument ExecutorT, in which the registered handlers are executed asynchronously ([SWS_CM_11360], [SWS_CM_11362], EXP ARAComAPI p. 11).

Context diagram: Interaction relationships of the skeleton field class. Sources: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], [SWS_CM_11360], [SWS_CM_11362].

Lifecycle

The lifecycle of a Field instance comprises configuration, operational, and termination phases:

  • Creation and ownership: For each field modeled in the ServiceInterface, an instance of <Field> exists as part of the service skeleton. Its lifetime is likely firmly coupled to the lifetime of the enclosing skeleton instance.
  • Configuration and registration: Prior to activating the service offering, the service implementation registers the required callbacks. If Field.hasGetter == TRUE is configured in the model, RegisterGetHandler is available ([SWS_CM_00114]). If Field.hasSetter == TRUE is set, RegisterSetHandler is provided ([SWS_CM_00116]). Both methods also exist in an overload with a ExecutorT parameter for context-bound execution ([SWS_CM_11360], [SWS_CM_11362]). Optionally, an E2E error handler can be registered using SetTransportFaultConditionHandler to monitor transport errors ([SWS_CM_00096], [SWS_CM_00097]).
  • Operational phase: Incoming Get and Set requests are served via the registered callbacks. In the event of state changes, the service implementation calls the method Update() ([SWS_CM_00119], EXP ARAComAPI p. 11). If Field.hasNotifier == TRUE is defined in the interface model, Update() transmits the new value to all subscribers and updates the internal state of the field.
  • Cleanup: A previously set transport error handler can be explicitly removed again via UnsetTransportFaultConditionHandler ([SWS_CM_00098]). The release of the Field instance occurs upon destruction of the skeleton.

Usage Path

A typical sequence when using a fully equipped field (getter, setter, and notifier active) comprises the following steps:

  1. Register Get handler: The application registers a function of type std::function<ara::core::Future<FieldType>()> ([SWS_CM_00114]) via RegisterGetHandler that asynchronously provides the current state upon incoming read requests.
  2. Register Set handler: Via RegisterSetHandler, the application passes a callable of type std::function<ara::core::Future<FieldType>(value)> ([SWS_CM_00116]) that checks and accepts new values and returns the resulting field value.
  3. Update and publish values: If the field value changes on the server side, the service implementation calls Update(value) ([SWS_CM_00119]). The communication infrastructure sends the update to all registered subscribers.
  4. Process requests: If read or write requests from clients are received via the communication layer, the middleware forwards them to the previously registered handlers. If an executor was configured ([SWS_CM_11360], [SWS_CM_11362]), execution takes place within its context.

Sequence diagram: Typical interaction sequence of registration, value update, and request processing. Sources: [SWS_CM_00114], [SWS_CM_00116], [SWS_CM_00119], EXP ARAComAPI p. 11.

Error Scenarios

When using the Field class, the following error and exception conditions are specified:

  • Invalid handlers (InvalidHandlerViolation): If a callable that does not exist or is null is passed to RegisterGetHandler ([SWS_CM_00114], [SWS_CM_11360]), RegisterSetHandler ([SWS_CM_00116], [SWS_CM_11362]), or SetTransportFaultConditionHandler ([SWS_CM_00096], [SWS_CM_00097]), an InvalidHandlerViolation is present.
  • Violation of the minimum transmission interval: The Update() method returns a ara::core::Result<void> ([SWS_CM_00119]). If transmission requests occur faster than configured via ServiceInterfaceDeploymentElement.minimumSendInterval, the call fails and returns the error code ComErrc::kMinimumSendIntervalViolationError with rollback semantics.
  • Exception safety: All specified methods of the Field class (including RegisterGetHandler, RegisterSetHandler, Update, SetTransportFaultConditionHandler, and UnsetTransportFaultConditionHandler) are declared as noexcept and designated as exception-safe.
