Context

The class ara::diag::DynamicAccessListDiagServiceBuilder ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15 “Class: DynamicAccessListDiagServiceBuilder”) serves applications to incrementally define and serialize a dynamic access list (DynamicAccessList) for diagnostic services. It forms the central tool for structuring access patterns for diagnostic requests in a granular manner according to individual bytes, byte sequences, value ranges, or wildcards.

In the overall system, the builder interacts with three key partners:

  • Application: Configures the desired filter patterns for incoming diagnostic requests via the builder's fluent API.
  • DiagnosticServiceDynamicAccessList: Provides the entry point via factory methods such as MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) and receives the defined access list.
  • Diagnostic Server Instance: The diagnostic server instance evaluates the passed byte patterns, wildcards, and end patterns at runtime during pattern matching for diagnostic service access rights ([SWS_DM_01220], [SWS_DM_01221]).

Context diagram: Interaction between application, access list, builder, and diagnostic server. Sources: [SWS_DM_01164], [SWS_DM_01166], [SWS_DM_01220].

Lifecycle

A builder instance is created either directly via the template constructor by specifying an initial value and a reference to a serialization buffer (ara::core::Vector<std::uint8_t>& content) ([SWS_DM_01169]), or via helper functions such as MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]).

Regarding ownership and copy semantics, the class enforces strictly linear usage:

  • Both the copy constructor ([SWS_DM_01171]) and the copy assignment operator ([SWS_DM_01172]) are declared as deleted (=delete).
  • The move assignment operator is also deleted ([SWS_DM_01173]). A transfer can take place exclusively via the move constructor ([SWS_DM_01170]).

For destruction via the destructor ([SWS_DM_01174]), a fixed invariant applies: Prior to destroying the object, the method Build() must be called ([SWS_DM_01181]) to complete the creation of the list.

Regarding concurrency, the template constructor and the move constructor are specified as thread-safe (thread-safe) ([SWS_DM_01169], [SWS_DM_01170]). In contrast, all pattern-forming operations (Add, Any, EndsWith, Build) and the destructor are explicitly not thread-safe (not thread-safe) ([SWS_DM_01174], [SWS_DM_01175], [SWS_DM_01181]) and must not be called concurrently on the same instance.

Usage Path

The typical procedure for configuring a diagnostic access pattern is divided into three steps:

  1. Initialization: Requesting a builder via DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) with the service identifier or directly via the constructor ([SWS_DM_01169]).
  2. Pattern construction via fluent API:
    • Adding individual bytes (Byte / std::uint8_t, [SWS_DM_01167]) via Add(Byte) ([SWS_DM_01175]), byte sequences via Add(ByteString) ([SWS_DM_01168], [SWS_DM_01176]), or value ranges via Add(ByteRange) ([SWS_DM_01177]).
    • Inserting wildcards via Any(numberOfBytesToIgnore) ([SWS_DM_01178], [SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §7.1.3 “Adding wildcards to a DynamicAccessList”). This stores bytes in the pattern that are ignored during subsequent matching (e.g. 22F1XX for DID prefixes).
    • Optional specification of a terminating pattern using EndsWith(Byte) ([SWS_DM_01179]) or EndsWith(ByteRange) ([SWS_DM_01180], [SWS_DM_01221]).
  3. Finalization: Calling Build() ([SWS_DM_01181]), whereby the list is completed.

Sequence diagram: Typical configuration and finalization of a pattern via the fluent API. Sources: [SWS_DM_01164], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Error Scenarios

The entire interface of ara::diag::DynamicAccessListDiagServiceBuilder operates without exception with noexcept and is specified as exception-safe (exception safe) ([SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181]). Neither are C++ exceptions thrown, nor are error states returned via ara::core::Result.

Error situations therefore result primarily from violations of preconditions:

  • Omission of the finalization call: If the builder is destroyed without Build() having been called beforehand, this violates the precondition of [SWS_DM_01181]. Interpretation: In this case, the access pattern is likely to remain incomplete and not be considered a valid criterion by the diagnostic server.
  • Unprotected concurrency: Since all methods for adding elements as well as Build() are classified as not thread-safe, a concurrent call from multiple threads leads to data corruption in the referenced buffer.

This guide is based on the requirements of the AUTOSAR Adaptive specification R25-11 for the Diagnostics module.
