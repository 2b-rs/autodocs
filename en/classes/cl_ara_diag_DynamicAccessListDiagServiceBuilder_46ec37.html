Enables the stepwise construction and finalization of dynamic access lists for diagnostic services.

The class serves the stepwise creation of dynamic access lists for diagnostic services via a chainable fluent API ([SWS_DM_01166]). Applications add exact bytes, value ranges, and wildcards to flexibly define access patterns for the Diagnostic Server ([SWS_DM_01175], [SWS_DM_01220]). Before destroying the non-thread-safe move-only object, the method Build() must strictly be called to complete the configuration ([SWS_DM_01181]).

Context

The class ara::diag::DynamicAccessListDiagServiceBuilder serves applications of the AUTOSAR Adaptive Platform for the stepwise construction of dynamic access lists (DynamicAccessList) for diagnostic services ([SWS_DM_01166], AUTOSAR_AP_SWS_Diagnostics §8.15.1 “Class: DynamicAccessListDiagServiceBuilder”). Via these lists, an application controls which diagnostic requests (for example, specific UDS services with concrete DIDs or subfunctions) are dynamically authorized at runtime (AUTOSAR_AP_SWS_Diagnostics §8.2 “Adding wildcards to a DynamicAccessList”).

Central interaction partners are the application itself, the factory methods of class ara::diag::DiagnosticServiceDynamicAccessList ([SWS_DM_01164], [SWS_DM_01165]), and the Diagnostic Server instance, which evaluates the assembled bit and byte patterns against incoming requests when checking service permissions ([SWS_DM_01220], [SWS_DM_01221]). To represent pattern structures, the class provides the type aliases Byte for single octets (std::uint8_t) and ByteString for byte sequences (ara::core::Span<Byte>) ([SWS_DM_01167], [SWS_DM_01168], AUTOSAR_AP_SWS_Diagnostics §8.15.1.1 “Public Member Types”).

Lifecycle

A builder object is typically instantiated via DiagnosticServiceDynamicAccessList::MakeServiceBuilder ([SWS_DM_01164], [SWS_DM_01165]) or directly via the constructor, which takes an initial value and a reference to the serialization buffer content (ara::core::Vector<std::uint8_t>&) ([SWS_DM_01169]). Interpretation: The parameter content is likely to serve as continuously filled storage for the serialized representation that is handed over to the Diagnostic Server after completion.

Regarding ownership and copyability, the class enforces strict move-only semantics with restricted assignment: The copy constructor ([SWS_DM_01171]) and the copy assignment operator ([SWS_DM_01172]) are deleted (=delete). The move assignment operator is likewise deleted ([SWS_DM_01173]). Only the move constructor is implemented ([SWS_DM_01170]), so that instances can be moved when needed, but cannot be duplicated or reassigned in an uncontrolled manner.

The lifecycle is subject to a mandatory postcondition: Before calling the destructor ([SWS_DM_01174]), method Build() must be called to complete list creation ([SWS_DM_01181]). While the constructors are specified as thread-safe ([SWS_DM_01169], [SWS_DM_01170]), all methods for pattern extension as well as the destructor are not thread-safe (not thread-safe, [SWS_DM_01174]).

State diagram: Life phases of the builder from creation through stepwise pattern construction to mandatory finalization before destruction. Sources: [SWS_DM_01169], [SWS_DM_01175], [SWS_DM_01181], [SWS_DM_01174].

Usage Path

Configuring a pattern is done via a fluent API where method calls return a reference to the same builder instance ([SWS_DM_01175]):

  1. Initialization: The application creates the builder, for example via DiagnosticServiceDynamicAccessList::MakeServiceBuilder with an initial byte or byte string ([SWS_DM_01164], [SWS_DM_01165]).
  2. Pattern extension: Overloaded Add() methods append single bytes ([SWS_DM_01175]), byte sequences ([SWS_DM_01176]), or closed value ranges ByteRange ([SWS_DM_01177]). These values are checked for exact match during subsequent evaluation.
  3. Insert wildcards: Using Any(numberOfBytesToIgnore), the application defines placeholders ([SWS_DM_01178]). The Diagnostic Server ignores the specified number of bytes during pattern matching, allowing flexible filters such as 22F1XX for DID ranges to be realized ([SWS_DM_01220], AUTOSAR_AP_SWS_Diagnostics §8.2 “Adding wildcards to a DynamicAccessList”).
  4. Pattern termination and finalization: Via EndsWith(), a terminating byte or range can be specified ([SWS_DM_01179], [SWS_DM_01180], [SWS_DM_01221]). Finally, calling Build() concludes the creation process ([SWS_DM_01181]).

Sequence diagram: Typical interaction sequence between application, factory method, and builder during pattern definition. Sources: [SWS_DM_01165], [SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181].

Error Scenarios

All methods of the class are declared with noexcept and specified as exception-safe (exception safe) ([SWS_DM_01169], [SWS_DM_01174], [SWS_DM_01181]). Error handling via C++ exceptions or error return values does not take place at API level.

The essential contractual precondition lies in calling Build() before destroying the builder ([SWS_DM_01181]). Interpretation: If the builder object is destroyed without Build() having been executed, the started pattern configuration is likely discarded or leaves an invalid state in the underlying access list.

Furthermore, the manipulating functions are not thread-safe ([SWS_DM_01175], [SWS_DM_01178], [SWS_DM_01181]). Unprotected concurrent access to the same builder instance from multiple threads leads to undefined memory states (data races).
