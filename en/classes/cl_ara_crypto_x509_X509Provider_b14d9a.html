Provides interfaces for creating, parsing, persistently storing, and validating X.509 security certificates.

The interface enables applications to create, parse, and manage X.509 certificates, certificate revocation lists, and validation contexts within the Adaptive Platform ([SWS_CRYPT_40614]). In addition to verifying certificate chains, it controls the creation of signing requests and OCSP queries in cooperation with the crypto subsystem. It also encapsulates persistent storage in individual certificate slots as well as in certificate groups via standardized instance specifiers ([SWS_CRYPT_40621]). All operations are designed to be thread-safe and, to prevent multiple instantiations, strictly require referencing via smart pointers without copy or move permissions.

Context

In the AUTOSAR Adaptive Platform, the class ara::crypto::x509::X509Provider forms the central abstraction and management interface for artifacts of a public key infrastructure (PKI) according to the X.509 standard. It decouples applying processes from vendor-specific implementation details of cryptographic drivers and provides uniform mechanisms for parsing, creating, and persistently storing certificates and certificate revocation lists (CRLs).

The interface interacts primarily with three functional areas:

  • Application / Security services: Use the interface to decode serialized certificates ([SWS_CRYPT_40614]) or certificate chains ([SWS_CRYPT_40616]), to generate distinguished names ([SWS_CRYPT_50186], [SWS_CRYPT_50187]), and to provide dedicated validation contexts ([SWS_CRYPT_50125]).
  • Persistent certificate storage: Enables persistently storing, reading, and deleting certificates in individual certificate slots ([SWS_CRYPT_40621], [SWS_CRYPT_40641], [SWS_CRYPT_40622]) or within configured certificate groups ([SWS_CRYPT_50126], [SWS_CRYPT_50127], [SWS_CRYPT_50128]) via ara::core::InstanceSpecifier.
  • Crypto subsystem (ara::crypto::cryp): Supplies keys and signing contexts (such as cryp::SignerPrivateCtx and cryp::PublicKey) that are used for issuing certificate signing requests (CSR) according to RFC 2986 ([SWS_CRYPT_40640]) or for signed OCSP requests according to RFC 6960 ([SWS_CRYPT_40626], [SWS_CRYPT_40627]).

Lifecycle

The interface X509Provider is defined as an abstract class. Instances are referenced and managed at the application level via the standardized smart pointer Sptr (alias for std::shared_ptr<X509Provider>) ([SWS_CRYPT_40601]). The actual instantiation of a platform-specific implementation is likely to occur via higher-level entry points of the crypto module (Interpretation).

To prevent multiple instantiations and uncontrolled copy or move operations, the copy constructor ([SWS_CRYPT_41013]), the move constructor ([SWS_CRYPT_41014]), and the corresponding assignment operators ([SWS_CRYPT_30226], [SWS_CRYPT_30227]) are explicitly deleted (=delete). The lifecycle ends with destruction via the virtual destructor ~X509Provider() ([SWS_CRYPT_40604]).

With regard to concurrency, all member functions of the class are specified as thread-safe (thread-safe) and exception-safe (exception safe) (including [SWS_CRYPT_40614], [SWS_CRYPT_40621], [SWS_CRYPT_50125]). Multiple threads can thus use the same provider instance in parallel without manual synchronization mechanisms.

Usage Path

A typical sequence for registering, storing, and subsequently checking certificates comprises the following steps:

  1. Parsing: A binary or textually serialized X.509v3 certificate is read in via ParseCert, passing the memory region and format identifier, and converted into a transient certificate object ([SWS_CRYPT_40614]). For certificate chains, ParseCertChain is equivalently available ([SWS_CRYPT_40616]).
  2. Persistent storage: The certificate object is persistently stored via ImportCertificate in a slot addressed by an instance specifier ([SWS_CRYPT_40621]) or assigned to a certificate group via ImportCertificateInGroup ([SWS_CRYPT_50127]). Already stored certificates can be loaded via LoadCertificate ([SWS_CRYPT_40641]) or LoadCertificateGroup ([SWS_CRYPT_50126]) as needed.
  3. Create validation context: To check certificates, a context object is created via CreateCertificateValidationCtx ([SWS_CRYPT_50125]).
  4. Manage revocation information: To ensure revocation status, CRLs can be imported via ImportCrl ([SWS_CRYPT_50183]), or OCSP requests can be generated via CreateOcspRequest ([SWS_CRYPT_40626]) and their responses evaluated with ParseOcspResponse ([SWS_CRYPT_50185]).

Sequence diagram: Flow for parsing, storing, and preparing certificate validation. Sources: [SWS_CRYPT_40614], [SWS_CRYPT_40621], [SWS_CRYPT_50125]

Error Scenarios

The interface signals errors via ara::core::Result without the use of C++ exceptions. Error handling is divided into functional crypto error codes and process-related configuration violations.

The functional error codes (ara::crypto::CryptoErrc) include:

  • kInvalidArgument: The input format cannot be interpreted (e.g., in case of a faulty buffer in ParseCert [SWS_CRYPT_40614], ParseCertChain [SWS_CRYPT_40616], ImportCrl [SWS_CRYPT_50183], or CreateDn [SWS_CRYPT_50186]) or the public key does not match the private signing key in CreateCertSignRequest ([SWS_CRYPT_40640]).
  • kUnsupportedFormat: The specified format identifier (FormatId) is unknown or not supported ([SWS_CRYPT_40614], [SWS_CRYPT_50185]).
  • kBusyResource: A persistent resource or cryptographic context is temporarily blocked ([SWS_CRYPT_40621], [SWS_CRYPT_40622], [SWS_CRYPT_40626]).
  • kEmptyCertificateSlot: Occurs when calling LoadCertificate if the addressed slot does not contain a persisted certificate ([SWS_CRYPT_40641]).
  • kInsufficientCapacity: Occurs when the capacity of a certificate group is insufficient for a further import ([SWS_CRYPT_50127]).
  • kNoSuchValue: Is reported when a certificate to be removed from a group cannot be found there ([SWS_CRYPT_50128]).
  • kUninitializedContext: The signing context was not initialized with a key prior to calling CreateCertSignRequest ([SWS_CRYPT_40640]) or CreateOcspRequest ([SWS_CRYPT_40626]).

At the architectural level, manifest and permission conflicts are differentiated:

  • ProcessMappingViolation: The passed InstanceSpecifier does not point to a port prototype of type CryptoCertificateInterface or CryptoCertificateGroupInterface modeled for the running process ([SWS_CRYPT_40621], [SWS_CRYPT_40641], [SWS_CRYPT_50126]).
  • InsufficientPermissionsViolation: No write permission is configured in the manifest for the modeled port prototype (writeAccess != True), which is strictly required for importing or deleting methods ([SWS_CRYPT_40621], [SWS_CRYPT_40622], [SWS_CRYPT_50127], [SWS_CRYPT_50183], [SWS_CRYPT_50184]).
