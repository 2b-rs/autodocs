Context

In the AUTOSAR Adaptive diagnostics module, the class ara::diag::DoIPGroupIdentification provides the interface for querying the current group identification status (GID status) for the DoIP protocol ([SWS_DM_00724]). Application-specific diagnostic components derive from this base class and implement the pure virtual query method GetGidStatus() ([SWS_DM_00724]).

As an intermediary element, the class interacts with three central system participants:

  • Adaptive Application: Implements the concrete handler, creates the instance, and controls its availability ([SWS_DM_00722], [SWS_DM_00725]).
  • Diagnostic Management (DM): Acts as the central manager on the platform and forwards incoming DoIP messages to the registered handler ([SWS_DM_00725], [SWS_DM_00726]).
  • DoIP protocol stack: Requires the current GID state to identify vehicle assemblies and network groups in the context of vehicle-external communication ([SWS_DM_00724]).

Context diagram: Interaction partners of the DoIPGroupIdentification interface. Sources: [SWS_DM_00722], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726].

Lifecycle

Instantiation takes place via the constructor DoIPGroupIdentification, specifying a modeled ara::core::InstanceSpecifier and a ConcurrencyType ([SWS_DM_00722]). The class represents a stationary single instance for the assigned port. Copy and move operations are explicitly deleted (AUTOSAR_AP_SWS_Diagnostics, p. 71): neither copy constructor ([SWS_DM_01641]), move constructor ([SWS_DM_01642]), copy assignment ([SWS_DM_01639]), nor move assignment ([SWS_DM_01640]) is available.

With regard to operation, the instance goes through clearly defined phases:

  1. Initialized: After construction, the object exists, but has not yet been reported to the DM as an active receiver.
  2. Offered (Offered): By calling Offer(), Diagnostic Management is authorized to forward requests to the handler ([SWS_DM_00725]).
  3. Stopped: Calling StopOffer() revokes the forwarding authorization from the DM and returns the instance to the inactive state ([SWS_DM_00726]).

The destructor is virtual and defined as noexcept ([SWS_DM_00723]). Interpretation: Prior to destroying the object, the application is likely required to call StopOffer() to ensure that the DM no longer forwards incoming requests to the handler being torn down.

With regard to concurrency, the constructor is thread-safe ([SWS_DM_00722]). For the pure virtual method GetGidStatus(), the required thread safety depends on parameter concurrencyType ([SWS_DM_00722], [SWS_DM_00724]): for kConcurrent, the subclass must be implemented thread-safe; for kNotConcurrent, this is not required. The administrative methods Offer() ([SWS_DM_00725]) and StopOffer() ([SWS_DM_00726]) as well as the destructor ([SWS_DM_00723]) are not thread-safe and require synchronized calls.

Usage Path

The provision and execution of the DoIP group identification follows a fixed call sequence:

  1. Subclassing: The application defines a derived class and overrides the method GetGidStatus() ([SWS_DM_00724]).
  2. Instantiation: The derived object is created; in doing so, the InstanceSpecifier of the associated PortPrototype is passed and the concurrency model is specified ([SWS_DM_00722]).
  3. Service offer (Offer): The application activates forwarding by calling Offer() ([SWS_DM_00725]). The DM enables forwarding.
  4. Status query: For incoming DoIP messages, the DM calls the method GetGidStatus() of the handler ([SWS_DM_00724]). The application returns the result asynchronously via ara::core::Future<GidStatus> ([SWS_DM_00724]). Interpretation: The asynchronous interface via Future was likely chosen to bridge potential latencies when reading hardware- or bus-related group identification data without blocking the DM thread.
  5. Termination (StopOffer): Prior to deinitialization, the application calls StopOffer() ([SWS_DM_00726]), which deactivates forwarding. Subsequently, the object can be destroyed ([SWS_DM_00723]).

Sequence diagram: Typical flow from registration via asynchronous status querying to deregistration. Sources: [SWS_DM_00722], [SWS_DM_00723], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726].

Error Scenarios

Error conditions are primarily concentrated on configuration violations during instantiation and invalid state transitions at runtime:

  • Model and port violations (constructor) ([SWS_DM_00722]):
    • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the execution context or does not refer to a PortPrototype.
    • PortInterfaceMappingViolation: The port referenced by mapping DiagnosticDoIpGroupIdentificationPortMapping is not typed by a DiagnosticDoIPGroupIdentificationInterface.
    • ProcessMappingViolation: No matching process exists at runtime for the modeled InstanceRef.
    • InstanceSpecifierAlreadyInUseViolation: The specified InstanceSpecifier is already occupied by an existing instance within the current process.
  • Runtime errors during Offer ([SWS_DM_00725]): If Offer() is called when the service is already being offered, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered with rollback semantics in ara::core::Result.
  • Error-free methods: No standardized error codes are specified for GetGidStatus() ([SWS_DM_00724]). StopOffer() has a void return type and defines no error states ([SWS_DM_00726]).
  • Exception safety: All methods of the class are declared with noexcept and specified as exception-safe (exception safe) ([SWS_DM_00722], [SWS_DM_00723], [SWS_DM_00724], [SWS_DM_00725], [SWS_DM_00726], AUTOSAR_AP_SWS_Diagnostics, p. 73).

This guide is based on the specification AUTOSAR Adaptive Platform R25-11 (module diag) and summarizes the architecture, lifecycle, and error behavior.
