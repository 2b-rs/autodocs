Serves as a base class for controlling error codes and maps domain-specific error values to text messages.

The class ara::core::ErrorDomain serves as an abstract base class for controlling error values and maps domain-specific codes to their textual representations [SWS_CORE_00153]. Subclasses encapsulate a system-wide unique identification number and define the translation into immutable error texts as well as type-specific exception handling. To enable usage as a literal type at compile time, the base class has a non-virtual, protected destructor [SWS_CORE_00136]. Copy and move operations are completely prohibited so that instances act as immutable identities.

Context

The class ara::core::ErrorDomain forms the common foundation for structured error management in the AUTOSAR Adaptive Platform. It acts as an abstract base class for concrete error domains and assumes central control responsibility for error values encapsulated in ara::core::ErrorCode. Each domain spans its own namespace and defines the mapping of domain-specific error values of type CodeType ([SWS_CORE_00122]) to meaningful text representations via Message() ([SWS_CORE_00153]). Furthermore, the class provides the type alias IdType ([SWS_CORE_00121]) for system-wide unique domain identifiers as well as SupportDataType ([SWS_CORE_00123]) for vendor-specific supplementary data.

In the overall system, ara::core::ErrorDomain interacts with three main partners:

  • Subclasses: Specific error domains inherit from ara::core::ErrorDomain and implement the pure virtual member functions for domain names, error messages, and exception handling.
  • ara::core::ErrorCode: Represents a concrete error value and delegates the retrieval of the descriptive text to the associated error domain.
  • Client / application code: Queries status information via the error code or directly on the domain ([SWS_CORE_00152]) or receives thrown C++ exceptions ([SWS_CORE_00154]).

Context diagram: Relationships and collaboration of ara::core::ErrorDomain with subclasses, error codes, and application code. Sources: [SWS_CORE_00151], [SWS_CORE_00152], [SWS_CORE_00153], [SWS_CORE_00154].

Lifecycle

Instantiation of ara::core::ErrorDomain is protected: The constructor has protected visibility and expects a system-wide unique domain identifier of type IdType ([SWS_CORE_00135]). Because the constructor is declared as constexpr and noexcept, the base class supports creation as a literal type at compile time. Subclasses are explicitly recommended to ensure this literal type property as well.

Any duplication or transfer of domain instances is prohibited:

  • The copy constructor ([SWS_CORE_00131]) and move constructor ([SWS_CORE_00132]) are declared as deleted (delete).
  • The copy assignment operator ([SWS_CORE_00133]) and move assignment operator ([SWS_CORE_00134]) are also deleted.

The destructor is declared as protected and defined as a default implementation ([SWS_CORE_00136]). It is deliberately kept trivial and non-virtual so that the class can remain a literal type. Although ara::core::ErrorDomain provides pure virtual interfaces, polymorphic destruction via base class pointers is not required ([SWS_CORE_00136]). In practice, concrete domain instances are likely managed as long-lived or static objects (interpretation).

Regarding ownership, all pointers to names ([SWS_CORE_00152]) and error texts ([SWS_CORE_00153]) remain in the ownership of the domain class and must not be deallocated by clients. All read and comparison operations are thread-safe and exception-safe ([SWS_CORE_00135], [SWS_CORE_00151]).

Usage Path

Two instances of ara::core::ErrorDomain compare equal if and only if their domain identifiers obtained via Id() ([SWS_CORE_00151]) match ([SWS_CORE_00137], [SWS_CORE_00138]). The typical sequence during error resolution and exception handling is divided into the following steps:

  1. Domain identification: The client or the error object determines the domain name as a null-terminated string via Name() ([SWS_CORE_00152]).
  2. Message resolution: The numeric error value is passed to the domain via Message(errorCode) ([SWS_CORE_00153]). The domain returns a pointer-based, null-terminated error text that is never nullptr.
  3. Exception handling: If an error code is to be transformed into an exception, the client calls ThrowAsException(errorCode) ([SWS_CORE_00154]). The domain then throws an appropriate instance of ara::core::Exception that encapsulates the passed error code.

Sequence diagram: Typical sequence during text resolution and exception throwing via an ErrorDomain. Sources: [SWS_CORE_00152], [SWS_CORE_00153], [SWS_CORE_00154].

Error Scenarios

When working with ara::core::ErrorDomain, the following error scenarios and interface requirements must be taken into account:

  • Incorrect domain association: If an errorCode that does not originate from this specific ErrorDomain is passed to the method Message(), this constitutes the specified violation WrongDomainOfAn-ErrorCodeViolation ([SWS_CORE_00153]). Callers must ensure that the error code matches the domain instance.
  • Disabled C++ exceptions: The method ThrowAsException() is not exception-safe (not exception safe) and throws an exception ([SWS_CORE_00154]). If C++ exceptions are disabled in the compiler toolchain, this function must not participate in overload resolution ([SWS_CORE_00154]).
  • Null pointer exclusion: Neither Name() nor Message() must ever return nullptr ([SWS_CORE_00152], [SWS_CORE_00153]). A subclass implementation returning nullptr violates the interface specification.

              With respect to concurrency and call conditions, Id() is specified as thread-safe ([SWS_CORE_00151]).
