Context

The structure ara::diag::DTCInformation::SnapshotRecordUpdatedType is a specialized data type within the Diagnostics functional cluster (AUTOSAR_AP_SWS_Diagnostics §8.48.5 “Struct: SnapshotRecordUpdatedType”, [SWS_DM_00662]). Its central responsibility lies in encapsulating state and history data once the snapshot records (snapshots or freeze frames) of a specific diagnostic trouble code (Diagnostic Trouble Code, DTC) have been updated in the diagnostics system.

In an AUTOSAR Adaptive architecture, this type essentially interacts with three partners:

  • Diagnostics Management (daemon / base system): Monitors the lifecycle of diagnostic events and DTCs. When new environmental parameters for a fault event are captured or existing freeze frames are overwritten, the platform instantiates and populates the structure.
  • Interface ara::diag::DTCInformation: Forms the namespace and provides the communication channel for status changes via the callback type SnapshotRecordUpdatedTypeNotifier (AUTOSAR_AP_SWS_Diagnostics §8.48.2.1.5 “Type Alias: SnapshotRecordUpdatedTypeNotifier”, [SWS_DM_02123]).
  • Adaptive Application: Registers observers for DTC changes in order to react promptly to updated diagnostic data (for example, for fleet monitoring, data logging, or driver warnings).

The structure combines two essential properties: the 32-bit field DTC for identifying the affected fault code (AUTOSAR_AP_SWS_Diagnostics §8.48.5.1.1 “DTC”, [SWS_DM_02116]) and the vector snapshotDataRecords (AUTOSAR_AP_SWS_Diagnostics §8.48.5.1.2 “snapshotDataRecords”, [SWS_DM_02117]) of type ara::core::Vector<SnapshotDataRecordType>, which conveys the specific updated records.

Lifecycle

Since SnapshotRecordUpdatedType is declared as a C++ struct, its lifecycle follows that of a pure value or transfer structure (plain old data with containers):

  • Creation: An instance is typically created platform-internally by the diagnostic runtime environment as soon as an update to snapshot data is registered for a DTC. The fields DTC and snapshotDataRecords are populated prior to forwarding.
  • Ownership: The structure is passed to the application's registered callback via the notifier callback SnapshotRecordUpdatedTypeNotifier ([SWS_DM_02123]). It can be assumed (interpretation) that it is passed as a const reference or temporary value object, so that the receiving application evaluates the data synchronously or creates its own copy if necessary.
  • States: The structure has no internal state machine of its own. After initialization, it exists as an immutable snapshot of an update event.
  • Destruction: When the instance leaves the scope of the notifier invocation, its memory and the dynamically allocated memory of vector snapshotDataRecords are deallocated deterministically.
  • Concurrency: SnapshotRecordUpdatedType implements no internal synchronization mechanisms. Since notifier invocations can usually be executed on separate worker threads of the diagnostic pipeline, the application must ensure synchronization for thread-safe further processing of its own data structures.

Usage Path

The typical sequence for using SnapshotRecordUpdatedType is divided into the following steps:

  1. Register notifier: The application registers a callback function conforming to the signature of SnapshotRecordUpdatedTypeNotifier ([SWS_DM_02123]) on the diagnostic instance of ara::diag::DTCInformation.
  2. Event detection: The base system detects a status change or recalculation of snapshot data for an active DTC.
  3. Instantiation and notification: The diagnostic system packs the affected DTC ([SWS_DM_02116]) and the updated records ([SWS_DM_02117]) into an instance of SnapshotRecordUpdatedType ([SWS_DM_00662]) and triggers the callback.
  4. Evaluation: The application receives the object, checks the DTC value, and iterates over snapshotDataRecords, for example to evaluate changed environmental parameters.

Error Scenarios

As a passive data struct, SnapshotRecordUpdatedType provides no methods of its own that could return ara::core::Result or error codes. However, the following boundary conditions must be taken into account during interaction:

  • Empty record list: It is possible that snapshotDataRecords is passed empty (e.g., if records were invalidated or reset). Applications should always check whether the vector contains entries before accessing by index.
  • DTC mapping: The value in DTC corresponds to the configured 32-bit identifier ([SWS_DM_02116]). If an application receives updates for a DTC that it does not functionally process, it should discard the event.
  • Memory pressure with large records: Since snapshotDataRecords is based on ara::core::Vector, local copying overhead can affect processing speed during frequent updates or with large snapshot payloads; unnecessary duplication of data in the callback should be avoided.
