Context

The class <RoutineInterface-Namespace>::<RoutineInterface> forms the central C++ interface in the AUTOSAR Adaptive module diag for providing and controlling diagnostic routines (AUTOSAR AP SWS Diagnostics p. 68). In the context of the UDS service RoutineControl (service 0x31 according to ISO 14229-1), an application-specific derivative of this class acts as a server-side handler. The class accepts requests that are forwarded from the central Diagnostic Management (DM) to the application ([SWS_DM_00594]). The interface defines the three essential control operations of a routine: starting via Start ([SWS_DM_00591]), stopping via Stop ([SWS_DM_00592]), and querying results via RequestResult ([SWS_DM_00593]). The functional connection in the system is established via a PortPrototype of type DiagnosticRoutineInterface, which must be referenced in the model via an DiagnosticServiceGenericMapping ([SWS_DM_00589]).

Lifecycle

A routine handler is created via the parameterized constructor specifying an ara::core::InstanceSpecifier and the desired concurrency ara::diag::ConcurrencyType ([SWS_DM_00589]). The parameter concurrencyType determines whether the interface is implemented thread-safe (kConcurrent) or not thread-safe (kNotConcurrent) ([SWS_DM_00589]). The constructor call itself is declared as thread-safe and noexcept ([SWS_DM_00589]).

With regard to object semantics, <RoutineInterface> has a unique identity: The copy constructor ([SWS_DM_01669]), the move constructor ([SWS_DM_01670]), the copy assignment operator ([SWS_DM_01667]), and the move assignment operator ([SWS_DM_01668]) are explicitly deleted (=delete). Duplicating or moving instances is therefore precluded.

After construction, the instance is in the inactive state. Only by calling Offer() is the forwarding of incoming diagnostic requests by Diagnostic Management to this handler activated ([SWS_DM_00594]). Calling StopOffer() deactivates the forwarding of requests again ([SWS_DM_00595]). The instance is released via the virtual destructor ~<RoutineInterface>(), which is specified as noexcept and not thread-safe ([SWS_DM_00590]). Before calling the destructor, StopOffer() should probably be called to cleanly unregister pending forwardings of the DM prior to object destruction.

State diagram: Lifecycle and activation states of the routine interface. Sources: [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00595], [SWS_DM_00590].

Usage Path

The typical usage path is divided into initialization, request processing, and termination:

  1. Instantiation: The application derives an implementation class from <RoutineInterface>, overrides the pure virtual methods, and creates the instance with the associated InstanceSpecifier as well as specifying ConcurrencyType ([SWS_DM_00589]).
  2. Service offering (Offer): The application calls Offer() ([SWS_DM_00594]), authorizing the DM to forward routine requests.
  3. Processing of control operations:
    • Start routine: When a start request arrives, the DM calls the method Start(...) with the modeled input arguments, ara::diag::MetaInfo, and a ara::diag::CancellationHandler ([SWS_DM_00591]). The method returns a ara::core::Future with the associated StartOutput object ([SWS_DM_00581], [SWS_DM_80003]).
    • Request results: Intermediate or final results of the routine are queried using RequestResult(...) ([SWS_DM_00593]). The returned ara::core::Future provides the RequestResultOutput object ([SWS_DM_00583], [SWS_DM_80005]).
    • Stop routine: An active routine execution is stopped by calling Stop(...) ([SWS_DM_00592]), which returns a ara::core::Future with the StopOutput object ([SWS_DM_00582], [SWS_DM_80004]).
    • Cancellation handling: Via the passed cancellationHandler, the handler can query the cancellation status using IsCanceled() or register a callback via SetNotifier(...) in case the diagnostic conversation is cancelled prematurely ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).
  4. Stop service offering (StopOffer): If the handler is no longer to service requests, the application calls StopOffer() ([SWS_DM_00595]).

Sequence diagram: Interaction patterns between application, routine handler, and Diagnostic Management. Sources: [SWS_DM_00589], [SWS_DM_00594], [SWS_DM_00591], [SWS_DM_00593], [SWS_DM_00592], [SWS_DM_00595].

Error Scenarios

Error situations can occur both during instantiation and provision as well as during actual routine execution:

  • Integrity and model violations during construction: Although the constructor is declared as noexcept, violations are triggered in the event of configuration errors ([SWS_DM_00589]):
    • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the model context of the executable or does not refer to a PortPrototype ([SWS_DM_00589]).
    • PortInterfaceMappingViolation: The PortPrototype of type DiagnosticRoutineInterface is not referenced by an DiagnosticServiceGenericMapping ([SWS_DM_00589]).
    • ProcessMappingViolation: A modeled InstanceRef exists, but no modeled process matches the current runtime process ([SWS_DM_00589]).
    • InstanceSpecifierAlreadyInUseViolation: The specified InstanceSpecifier is already used by another instance in this process ([SWS_DM_00589]).
  • Errors during offering (Offer): If Offer() is called even though the service is already offered, the method returns a ara::core::Result<void> with the error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_00594]). The call is specified as not thread-safe ([SWS_DM_00594]).
  • Domain errors during operation execution: If the operations Start, Stop, or RequestResult fail, the methods do not throw exceptions (all methods are noexcept). Instead, the error is transported asynchronously via the returned ara::core::Future. For this purpose, the implementation must provide a suitable UDS Negative Response Code (NRC) according to ISO 14229-1 via ara::diag::DiagUdsNrcErrc or a Ap ApplicationError ([SWS_DM_00591], [SWS_DM_00592], [SWS_DM_00593]).
