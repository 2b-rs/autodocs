Context

The class ara::nm::NetworkHandle represents the central access object for managing and monitoring a network handle [SWS_ANM_01000]. It is primarily designed for use by functional components such as State Management [SWS_ANM_01000]. Binding to a concrete logical or physical communication resource takes place via an ara::core::InstanceSpecifier that references a corresponding NetworkManagementPortInterface port prototype [SWS_ANM_01001].

Within the system environment, the class interacts with at least three parties:

  • State Management: Requests network states, queries the current status, and registers notification callbacks [SWS_ANM_01000].
  • NetworkHandle: Serves as a typed C++ interface and encapsulation of port communication [SWS_ANM_01000].
  • Network Management Service (NM): Manages the actual Partial Network Clusters (PNC), VLANs, or physical networks and reports their effective states back to the handle [SWS_ANM_01008], [SWS_ANM_01009].

Context diagram: Interaction between State Management, NetworkHandle, and NM subsystem. Sources: [SWS_ANM_01000], [SWS_ANM_01001], [SWS_ANM_01008], [SWS_ANM_01009].

Lifecycle

An NetworkHandle is explicitly instantiated based on an ara::core::InstanceSpecifier [SWS_ANM_01001]. Construction is thread-safe. With regard to ownership, the class enforces strict move-only semantics: the copy constructor [SWS_ANM_01005] and the copy assignment operator [SWS_ANM_01006] are deleted (= delete). Instances can only be transferred via the move constructor [SWS_ANM_01003] (whose thread safety is implementation-defined) or the non-thread-safe move assignment [SWS_ANM_01004].

The destructor is defined as noexcept and not thread-safe [SWS_ANM_01002]. When destroying the instance, it must be ensured that no concurrent accesses take place anymore.

The network resources controlled via the handle pass through the states defined by NetworkStateType [SWS_ANM_01358]:

  • kNoCom (0): Non-communication; occurs as soon as at least one of the assigned networks is not in state FULL_COM [SWS_ANM_01358].
  • kFullCom (1): Full communication; is active when all assigned networks are fully activated [SWS_ANM_01358].

The interface methodically distinguishes between the target state requested by the caller ([SWS_ANM_01008]) and the actually established, effective network state ([SWS_ANM_01007]).

State diagram: Elementary states of NetworkStateType and state transitions. Sources: [SWS_ANM_01358], [SWS_ANM_01009].

Usage Path

A typical workflow comprises instantiation, registration of state observers, requesting communication, and subsequent release:

  1. Instantiation: State Management creates the object via the InstanceSpecifier of the port [SWS_ANM_01001].
  2. Register notifier: For asynchronous notification, the application registers an NetworkStateChangeNotifier [SWS_ANM_01020]. This is possible for the effective state via RegisterNetworkStateChangeNotifier [SWS_ANM_01010] or for the requested state via RegisterNetworkRequestedStateChangeNotifier [SWS_ANM_01012]. Optionally, a dedicated ExecutorT for the execution context can be specified via corresponding template variants [SWS_ANM_01014], [SWS_ANM_01015]. A maximum of one notifier may be active per handle at any time.
  3. Request network: Activation of the PNC, VLAN, or network is initiated via SetNetworkRequestedState(NetworkStateType::kFullCom) [SWS_ANM_01009].
  4. Monitor state: In addition to receiving callbacks, the current state can be queried synchronously using GetNetworkState() [SWS_ANM_01007] and the requested state via GetNetworkRequestedState() [SWS_ANM_01008]. Both queries are thread-safe.
  5. Release network and unregister: When the requirement ends, the caller sets the state to kNoCom [SWS_ANM_01009] and cancels registered notifiers via UnregisterNetworkStateChangeNotifier() [SWS_ANM_01011] or UnregisterNetworkRequestedStateChangeNotifier() [SWS_ANM_01013].

Sequence diagram: Typical call sequence for network request and status monitoring. Sources: [SWS_ANM_01001], [SWS_ANM_01007], [SWS_ANM_01009], [SWS_ANM_01010].

Error Scenarios

All essential operations return results in error scenarios via ara::core::Result:

  • NmErrc::kServiceNotAvailable: Occurs with GetNetworkState() [SWS_ANM_01007], GetNetworkRequestedState() [SWS_ANM_01008], and SetNetworkRequestedState() [SWS_ANM_01009] if the NM service is not reachable or operational.
  • NmErrc::kInvalidHandler: Returned by the registration methods [SWS_ANM_01010], [SWS_ANM_01012], [SWS_ANM_01014], and [SWS_ANM_01015] if an invalid notification function was passed (interpretation: presumably also when attempting multiple registration without prior deregistration).

Pre- and postconditions as well as concurrency: While read operations are thread-safe, writing methods (SetNetworkRequestedState) as well as notifier registrations and deregistrations are specified as not thread-safe [SWS_ANM_01009], [SWS_ANM_01010], [SWS_ANM_01011]. They require external synchronization when an instance is shared. Before destroying the handle, notifiers should be unregistered to avoid accesses to invalid contexts.
