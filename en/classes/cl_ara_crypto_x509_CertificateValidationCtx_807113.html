Context

The ara::crypto::x509::CertificateValidationCtx class provides the validation context for X.509 certificates and certificate paths according to RFC 5280 ([SWS_CRYPT_50122], [SWS_CRYPT_50123]). Within the crypto module of the Adaptive Platform, it bundles the configuration, trusted root certificates, intermediate certificates, and validation rules, and performs cryptographic path validation.

Essentially, the following components and data types are involved in the validation processes:

  • Application: Configures the context via validation options ([SWS_CRYPT_50120]), sets the reference time if needed ([SWS_CRYPT_50121]), registers trust anchors, and initiates the validation.
  • Certificates (Certificate): Form the trust base and the objects to be verified. A distinction is made between trusted certificates ([SWS_CRYPT_50117]), untrusted intermediate certificates for path construction ([SWS_CRYPT_50118]), and target certificates ([SWS_CRYPT_50122]) or certificate chains ([SWS_CRYPT_50123]).
  • OCSP responses (OcspResponse): Serve to verify the revocation status of certificates and are passed to the validation context for consideration ([SWS_CRYPT_50124]).
  • Validation result (CertificateValidationResult): Encapsulates the detailed result of the RFC 5280 path validation process after verification has been performed ([SWS_CRYPT_50122], [SWS_CRYPT_50123]).

Lifecycle

For ownership and transfer of context instances, the interface provides the type alias Sptr as std::shared_ptr<CertificateValidationCtx> ([SWS_CRYPT_50116]). Since the class defines pure virtual methods, the instantiation of the concrete implementation is likely performed via a higher-level factory or provider class of the crypto stack.

After creation, the context is in a configurable state. The application incrementally registers options ([SWS_CRYPT_50120]), certificates ([SWS_CRYPT_50117], [SWS_CRYPT_50118]), OCSP responses ([SWS_CRYPT_50124]), or OIDs of critical extensions to be ignored ([SWS_CRYPT_50119]). Resetting individual registrations is not supported; separate contexts are instantiated for different validation domains.

Regarding concurrency and fault tolerance, all virtual member functions of the interface are explicitly specified as thread-safe (thread-safe) and exception-safe (exception safe) ([SWS_CRYPT_50117] to [SWS_CRYPT_50124]). Instances can therefore be used concurrently by multiple threads.

Usage Path

The typical usage of CertificateValidationCtx follows a fixed sequence of configuration, population, and execution:

  1. Define configuration: By means of SetValidationOptions, a bitmask defining the checks to be performed is passed ([SWS_CRYPT_50120]). Optionally, an explicit reference time for the validity check can be selected via SetCurrentTime ([SWS_CRYPT_50121]); if this function is not called, the context uses the system time. If application-specifically validated critical extensions are to be tolerated, their OIDs are stored via IgnoreCriticalExtension ([SWS_CRYPT_50119]).
  2. Register certificates and status data: Via AddTrustedCertificate, the authoritative trust anchors (root CAs) are added ([SWS_CRYPT_50117]). To facilitate path finding, intermediate certificates can be fed in via AddUntrustedCertificate ([SWS_CRYPT_50118]). If revocation information is to be included, OCSP responses are added via AddOcspResponse ([SWS_CRYPT_50124]).
  3. Execute validation: The check is performed using one of two methods:
    • ValidateCertificate validates a single end-entity certificate and constructs the path using the trusted and untrusted certificates stored in the context ([SWS_CRYPT_50122]).
    • ValidateCertificateChain validates an existing chain as ara::core::Span ([SWS_CRYPT_50123]). Element 0 represents the leaf certificate and each subsequent element its respective issuer. In this mode, certificates previously stored via AddUntrustedCertificate are ignored; the validation verifies the passed chain exclusively against the trust anchors set via AddTrustedCertificate.
  4. Evaluate result: Upon success, both validation functions return a CertificateValidationResult::Sptrc for evaluating the detailed results ([SWS_CRYPT_50122], [SWS_CRYPT_50123]).

Sequence diagram: Typical call sequence for configuration, registration of certificates, and execution of validation. Sources: [SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50121], [SWS_CRYPT_50122], [SWS_CRYPT_50123], [SWS_CRYPT_50124]

Error Scenarios

All operations return errors via ara::core::Result. Standardized error codes and specific preconditions include:

  • Incompatible arguments (ara::crypto::CryptoErrc::kIncompatibleArguments): Occurs for ValidateCertificate ([SWS_CRYPT_50122]) and ValidateCertificateChain ([SWS_CRYPT_50123]) if an OCSP response was stored via AddOcspResponse ([SWS_CRYPT_50124]), but the options set via SetValidationOptions ([SWS_CRYPT_50120]) do not define corresponding OCSP behavior. Both functions have rollback semantics.
  • Invalid configuration options (ara::crypto::CryptoErrc::kInvalidArgument): If SetValidationOptions ([SWS_CRYPT_50120]) is called with an invalid bitmask, the call fails with rollback semantics.
  • Validation error for OCSP responses: For AddOcspResponse ([SWS_CRYPT_50124]), the issuer of the OCSP response must either have been previously stored in the context as trusted or untrusted, have been signed by a certificate with the extended key usage id-kp-OCSPSigning of the same CA, or be provided via the optional argument trustedOcspIssuerCertificate. The returned Result<CertificateValidationStatus> signals kValid upon successful acceptance or provides the specific validation status of the OCSP response.
  • Implementation-specific errors: In case of internal errors or system limits, all methods can return implementation-specific error codes in Result ([SWS_CRYPT_50117] to [SWS_CRYPT_50124]).

<h4>Context</h4>
<p>
The <code>ara::crypto::x509::CertificateValidationCtx</code> class provides the validation context for X.509 certificates and certificate paths according to RFC 5280 (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>). Within the <code>crypto</code> module of the Adaptive Platform, it bundles the configuration, trusted root certificates, intermediate certificates, and validation rules, and performs cryptographic path validation.
</p>
<p>
Essentially, the following components and data types are involved in the validation processes:
</p>
<ul>
<li><strong>Application:</strong> Configures the context via validation options (<a class="spec-record-ref" data-req="SWS_CRYPT_50120" href="../spec/record.html?id=SWS_CRYPT_50120">[SWS_CRYPT_50120]</a>), sets the reference time if needed (<a class="spec-record-ref" data-req="SWS_CRYPT_50121" href="../spec/record.html?id=SWS_CRYPT_50121">[SWS_CRYPT_50121]</a>), registers trust anchors, and initiates the validation.</li>
<li><strong>Certificates (<code>Certificate</code>):</strong> Form the trust base and the objects to be verified. A distinction is made between trusted certificates (<a class="spec-record-ref" data-req="SWS_CRYPT_50117" href="../spec/record.html?id=SWS_CRYPT_50117">[SWS_CRYPT_50117]</a>), untrusted intermediate certificates for path construction (<a class="spec-record-ref" data-req="SWS_CRYPT_50118" href="../spec/record.html?id=SWS_CRYPT_50118">[SWS_CRYPT_50118]</a>), and target certificates (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>) or certificate chains (<a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>).</li>
<li><strong>OCSP responses (<code>OcspResponse</code>):</strong> Serve to verify the revocation status of certificates and are passed to the validation context for consideration (<a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>).</li>
<li><strong>Validation result (<code>CertificateValidationResult</code>):</strong> Encapsulates the detailed result of the RFC 5280 path validation process after verification has been performed (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>).</li>
</ul>

<h4>Lifecycle</h4>
<p>
For ownership and transfer of context instances, the interface provides the type alias <code>Sptr</code> as <code>std::shared_ptr&lt;CertificateValidationCtx&gt;</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50116" href="../spec/record.html?id=SWS_CRYPT_50116">[SWS_CRYPT_50116]</a>). Since the class defines pure virtual methods, the instantiation of the concrete implementation is likely performed via a higher-level factory or provider class of the crypto stack.
</p>
<p>
After creation, the context is in a configurable state. The application incrementally registers options (<a class="spec-record-ref" data-req="SWS_CRYPT_50120" href="../spec/record.html?id=SWS_CRYPT_50120">[SWS_CRYPT_50120]</a>), certificates (<a class="spec-record-ref" data-req="SWS_CRYPT_50117" href="../spec/record.html?id=SWS_CRYPT_50117">[SWS_CRYPT_50117]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50118" href="../spec/record.html?id=SWS_CRYPT_50118">[SWS_CRYPT_50118]</a>), OCSP responses (<a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>), or OIDs of critical extensions to be ignored (<a class="spec-record-ref" data-req="SWS_CRYPT_50119" href="../spec/record.html?id=SWS_CRYPT_50119">[SWS_CRYPT_50119]</a>). Resetting individual registrations is not supported; separate contexts are instantiated for different validation domains.
</p>
<p>
Regarding concurrency and fault tolerance, all virtual member functions of the interface are explicitly specified as thread-safe (<code>thread-safe</code>) and exception-safe (<code>exception safe</code>) (<a class="spec-record-ref" data-req="SWS_CRYPT_50117" href="../spec/record.html?id=SWS_CRYPT_50117">[SWS_CRYPT_50117]</a> to <a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>). Instances can therefore be used concurrently by multiple threads.
</p>

<h4>Usage Path</h4>
<p>
The typical usage of <code>CertificateValidationCtx</code> follows a fixed sequence of configuration, population, and execution:
</p>
<ol>
<li><strong>Define configuration:</strong> By means of <code>SetValidationOptions</code>, a bitmask defining the checks to be performed is passed (<a class="spec-record-ref" data-req="SWS_CRYPT_50120" href="../spec/record.html?id=SWS_CRYPT_50120">[SWS_CRYPT_50120]</a>). Optionally, an explicit reference time for the validity check can be selected via <code>SetCurrentTime</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50121" href="../spec/record.html?id=SWS_CRYPT_50121">[SWS_CRYPT_50121]</a>); if this function is not called, the context uses the system time. If application-specifically validated critical extensions are to be tolerated, their OIDs are stored via <code>IgnoreCriticalExtension</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50119" href="../spec/record.html?id=SWS_CRYPT_50119">[SWS_CRYPT_50119]</a>).</li>
<li><strong>Register certificates and status data:</strong> Via <code>AddTrustedCertificate</code>, the authoritative trust anchors (root CAs) are added (<a class="spec-record-ref" data-req="SWS_CRYPT_50117" href="../spec/record.html?id=SWS_CRYPT_50117">[SWS_CRYPT_50117]</a>). To facilitate path finding, intermediate certificates can be fed in via <code>AddUntrustedCertificate</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50118" href="../spec/record.html?id=SWS_CRYPT_50118">[SWS_CRYPT_50118]</a>). If revocation information is to be included, OCSP responses are added via <code>AddOcspResponse</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>).</li>
<li><strong>Execute validation:</strong> The check is performed using one of two methods:
<ul>
<li><code>ValidateCertificate</code> validates a single end-entity certificate and constructs the path using the trusted and untrusted certificates stored in the context (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>).</li>
<li><code>ValidateCertificateChain</code> validates an existing chain as <code>ara::core::Span</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>). Element 0 represents the leaf certificate and each subsequent element its respective issuer. In this mode, certificates previously stored via <code>AddUntrustedCertificate</code> are ignored; the validation verifies the passed chain exclusively against the trust anchors set via <code>AddTrustedCertificate</code>.</li>
</ul>
</li>
<li><strong>Evaluate result:</strong> Upon success, both validation functions return a <code>CertificateValidationResult::Sptrc</code> for evaluating the detailed results (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>, <a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>).</li>
</ol>

<h4>Error Scenarios</h4>
<p>
All operations return errors via <code>ara::core::Result</code>. Standardized error codes and specific preconditions include:
</p>
<ul>
<li><strong>Incompatible arguments (<code>ara::crypto::CryptoErrc::kIncompatibleArguments</code>):</strong> Occurs for <code>ValidateCertificate</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50122" href="../spec/record.html?id=SWS_CRYPT_50122">[SWS_CRYPT_50122]</a>) and <code>ValidateCertificateChain</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50123" href="../spec/record.html?id=SWS_CRYPT_50123">[SWS_CRYPT_50123]</a>) if an OCSP response was stored via <code>AddOcspResponse</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>), but the options set via <code>SetValidationOptions</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50120" href="../spec/record.html?id=SWS_CRYPT_50120">[SWS_CRYPT_50120]</a>) do not define corresponding OCSP behavior. Both functions have rollback semantics.</li>
<li><strong>Invalid configuration options (<code>ara::crypto::CryptoErrc::kInvalidArgument</code>):</strong> If <code>SetValidationOptions</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50120" href="../spec/record.html?id=SWS_CRYPT_50120">[SWS_CRYPT_50120]</a>) is called with an invalid bitmask, the call fails with rollback semantics.</li>
<li><strong>Validation error for OCSP responses:</strong> For <code>AddOcspResponse</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>), the issuer of the OCSP response must either have been previously stored in the context as trusted or untrusted, have been signed by a certificate with the extended key usage <code>id-kp-OCSPSigning</code> of the same CA, or be provided via the optional argument <code>trustedOcspIssuerCertificate</code>. The returned <code>Result&lt;CertificateValidationStatus&gt;</code> signals <code>kValid</code> upon successful acceptance or provides the specific validation status of the OCSP response.</li>
<li><strong>Implementation-specific errors:</strong> In case of internal errors or system limits, all methods can return implementation-specific error codes in <code>Result</code> (<a class="spec-record-ref" data-req="SWS_CRYPT_50117" href="../spec/record.html?id=SWS_CRYPT_50117">[SWS_CRYPT_50117]</a> to <a class="spec-record-ref" data-req="SWS_CRYPT_50124" href="../spec/record.html?id=SWS_CRYPT_50124">[SWS_CRYPT_50124]</a>).</li>
</ul>
