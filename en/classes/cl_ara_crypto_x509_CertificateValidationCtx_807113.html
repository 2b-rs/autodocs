Used for path validation of X.509 certificates and certificate chains based on configured trust anchors.

The class ara::crypto::x509::CertificateValidationCtx is used for validating X.509 certificates and complete certificate chains in accordance with RFC 5280 ([SWS_CRYPT_50122]). Prior to execution, the application configures the context by adding trust anchors, optional intermediate certificates, verification timestamps, and verification options, and binds OCSP responses for revocation checking as needed ([SWS_CRYPT_50117]). If OCSP responses are registered, the validation options must mandatorily define the corresponding OCSP behavior to avoid incompatibility errors during path verification. All interface methods are exception safe and designed for concurrent access.

Context

The class ara::crypto::x509::CertificateValidationCtx defines the standardized interface for validating X.509 certificates and certificate chains in accordance with RFC 5280 ([SWS_CRYPT_50122], [SWS_CRYPT_50123]). In the overall system of the AUTOSAR Adaptive Platform, it undertakes the task of demonstrating trust relationships, verifying certificate paths, and determining the status of cryptographic certificates before their use in security relationships.

The calling application serves as the central interaction partner, supplying the context with trust anchors ([SWS_CRYPT_50117]), untrusted intermediate certificates ([SWS_CRYPT_50118]), and revocation information in the form of OCSP responses ([SWS_CRYPT_50124]). The result of the validation is provided as CertificateValidationResult ([SWS_CRYPT_50122]).

Context diagram: Integration of CertificateValidationCtx between application, input certificates, revocation checks, and result object. Sources: [SWS_CRYPT_50117], [SWS_CRYPT_50122], [SWS_CRYPT_50124].

Lifecycle

Instances of the interface are managed via the type alias Sptr ([SWS_CRYPT_50116]) as std::shared_ptr<CertificateValidationCtx>, enabling shared ownership and flexible lifetime management by the using software components. Since this is a pure virtual interface class, no public constructor exists; creation of the concrete context instance is presumably likely to occur via corresponding creation functions of a crypto stack provider implementation. Regarding concurrency, all virtual member functions are specified as thread-safe ([SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50122]). Furthermore, all methods ensure exception safety and are declared with noexcept ([SWS_CRYPT_50117], [SWS_CRYPT_50122]). In terms of state, the context behaves as a configurable accumulator: it accepts verification parameters, certificates, and status responses, and holds them ready for validation steps.

Usage Path

Typical usage of the validation context is structured into a sequence of configuration steps followed by validation execution:

  1. Providing trust anchors: By means of AddTrustedCertificate ([SWS_CRYPT_50117]), one or more trusted certificates are added as starting points for path validation. Additional, untrusted intermediate certificates can be provided via AddUntrustedCertificate ([SWS_CRYPT_50118]).
  2. Configuring validation rules and reference time: A bitmask for controlling the verification behavior is passed via SetValidationOptions ([SWS_CRYPT_50120]). With SetCurrentTime ([SWS_CRYPT_50121]), an explicit point in time can be specified for validity checks; if this call is omitted, the context automatically uses the system time ([SWS_CRYPT_50121]). If specific, unsupported critical extensions are to be excluded from verification, their OID can be registered via IgnoreCriticalExtension ([SWS_CRYPT_50119]). This has no effect if the option kIgnoreUnknownCriticalExtensions is set ([SWS_CRYPT_50119]).
  3. Adding revocation information: One or more OCSP responses can be added via AddOcspResponse ([SWS_CRYPT_50124]). The issuer of the OCSP response must either have been previously stored as a certificate in the context, possess the extended key usage attribute id-kp-OCSPSigning of the same CA, or be passed via the optional parameter trustedOcspIssuerCertificate ([SWS_CRYPT_50124]).
  4. Perform validation: ValidateCertificate ([SWS_CRYPT_50122]) is used to verify a target certificate. Alternatively, ValidateCertificateChain ([SWS_CRYPT_50123]) validates an ordered certificate chain starting with the leaf certificate at position 0. In this process, certificates previously registered via AddUntrustedCertificate are ignored, and exclusively the passed chain is verified against the trusted certificates ([SWS_CRYPT_50123]).

Sequence diagram: Typical call sequence for configuring and validating certificates. Sources: [SWS_CRYPT_50117], [SWS_CRYPT_50120], [SWS_CRYPT_50122], [SWS_CRYPT_50124].

Error Scenarios

Error handling is performed consistently via ara::core::Result without C++ exceptions:

  • Invalid configuration options: If SetValidationOptions is called with an invalid bitmask, the call fails and returns the error code ara::crypto::CryptoErrc::kInvalidArgument with rollback semantics ([SWS_CRYPT_50120]).
  • Conflicting OCSP configuration: If at least one OCSP response was stored via AddOcspResponse without the behavior for OCSP being specified in the CertificateValidationOptions, both ValidateCertificate ([SWS_CRYPT_50122]) and ValidateCertificateChain ([SWS_CRYPT_50123]) return the error ara::crypto::CryptoErrc::kIncompatibleArguments with rollback semantics.
  • Failed OCSP validation: If the signature or origin of an OCSP response in AddOcspResponse ([SWS_CRYPT_50124]) cannot be validated against the defined criteria, the function returns the corresponding status code CertificateValidationStatus or an implementation-specific error instead of kValid.
  • Implementation-specific errors: In case of internal crypto library issues, methods such as AddTrustedCertificate ([SWS_CRYPT_50117]) or IgnoreCriticalExtension ([SWS_CRYPT_50119]) can report implementation-specific error codes in the result object.

use

The method AddOcspResponse of the class ara::crypto::x509::CertificateValidationCtx validates a passed OCSP response (ocspResponse) and, if valid, adds it to the set of already stored OCSP responses in the validation context [SWS_CRYPT_50124]. Multiple responses can be added to a context [SWS_CRYPT_50124]. Via the optional parameter trustedOcspIssuerCertificate, a specific certificate can be passed that is considered trusted during the check of the OCSP response; if this parameter is omitted, the validation draws on the certificates previously configured by means of AddTrustedCertificate [SWS_CRYPT_50124].

The synchronous call returns a ara::core::Result<CertificateValidationStatus>, which contains the status kValid upon successful acceptance or otherwise represents the result of the OCSP validation or an error [SWS_CRYPT_50124].

Error handling

The specification does not define any standardized error codes for this call [SWS_CRYPT_50124]. If the operation fails, either the corresponding validation status is conveyed in the result or an implementation-specific error is signaled via the Result object [SWS_CRYPT_50124].

Concurrency and Limitations

The operation is specified as thread-safe and exception-safe [SWS_CRYPT_50124]. For the validation of the OCSP response to succeed, one of the following conditions must be met [SWS_CRYPT_50124]:

  • The issuer was previously stored in the context as a trusted or untrusted certificate [SWS_CRYPT_50124].
  • The signature originates from a certificate with set extension id-kp-OCSPSigning of the same certificate authority (CA) [SWS_CRYPT_50124].
  • The signature originates from a trusted CA that was passed directly via trustedOcspIssuerCertificate [SWS_CRYPT_50124].

Interaction

The registered OCSP responses are incorporated into downstream validation checks, such as those performed by [SWS_CRYPT_50122] (ValidateCertificate) and [SWS_CRYPT_50123] (ValidateCertificateChain). Interpretation: The OCSP responses likely have to be added before starting the path validation so that the revocation status of the certificates can be taken into account.
