Context

The class ara::diag::UploadService represents the functional service interface for upload diagnostic services within the AUTOSAR Adaptive Platform ([SWS_DM_00797]). It acts as a standardized handler in the header ara/diag/upload.h to which the central Diagnostic Management daemon (DM) forwards incoming UDS diagnostic requests ([SWS_DM_00802]).

In the diagnostic architecture, three essential roles interact in the context of the upload service:

  • External diagnostic tester / client: Initiates the upload transaction via the standardized Unified Diagnostic Services protocol (ISO 14229-1), requests data blocks step by step, and completes the transfer ([SWS_DM_00799], [SWS_DM_00800], [SWS_DM_00801]).
  • Diagnostic Management (DM): Receives and validates the transport and session parameters at platform level, determines the responsible port, and delegates the functional execution to the registered instance of ara::diag::UploadService ([SWS_DM_00802]).
  • Application-specific handler: A concrete derivation of ara::diag::UploadService that reads out, segments, and provides the requested memory areas as response data at the application level ([SWS_DM_00799], [SWS_DM_00800]).

Lifecycle

The instantiation of ara::diag::UploadService takes place explicitly via binding to a modeled interface port using ara::core::InstanceSpecifier and specifying the concurrency behavior via the parameter concurrencyType ([SWS_DM_00797]). The class has strict singleton or unique semantics per port: Both the copy and move constructors as well as all assignment operators are deleted (=delete), so that an instance can neither be copied nor moved ([SWS_DM_01671], [SWS_DM_01672], [SWS_DM_01673], [SWS_DM_01674]).

After successful construction, the object initially remains in the inactive state (stopped). The method call Offer() signals to the DM that the handler is ready and requests may be forwarded from now on ([SWS_DM_00802]). Forwarding can be suspended at any time by StopOffer() ([SWS_DM_00803]). Calling StopOffer() before destroying the object is likely recommended in practice (interpretation) in order to prevent hanging calls during shutdown. The instance is released via the virtual destructor ~UploadService() ([SWS_DM_00798]).

With regard to concurrency, the constructor is thread-safe ([SWS_DM_00797]). In contrast, Offer(), StopOffer(), and the destructor are specified as not thread-safe (not thread-safe) and must therefore not be called concurrently in an uncoordinated manner ([SWS_DM_00798], [SWS_DM_00802], [SWS_DM_00803]). The thread safety of the handler methods themselves depends conditionally on the selected ConcurrencyType (kConcurrent or kNotConcurrent) ([SWS_DM_00797], [SWS_DM_00799], [SWS_DM_00800], [SWS_DM_00801]).

State diagram: Lifecycle and offering states of UploadService. Sources: [SWS_DM_00797], [SWS_DM_00798], [SWS_DM_00802], [SWS_DM_00803]

Usage Path

A typical use case comprises the step-by-step processing of a complete UDS upload transaction:

  1. Offering: The application instance calls Offer() to activate the forwarding of requests by the DM ([SWS_DM_00802]).
  2. Start of the upload session (RequestUpload): As soon as a UDS request is received, the DM calls the method RequestUpload() ([SWS_DM_00799]). The application evaluates dataFormatIdentifier, addressAndLengthFormatIdentifier, and the content of memoryAddressAndSize. The referenced memory data remains valid until the returned ara::core::Future<void> is fulfilled or the execution is canceled via the passed CancellationHandler ([SWS_DM_00799]).
  3. Blockwise data transfer (UploadData): The DM repeatedly calls UploadData() in a loop ([SWS_DM_00800]). Via the parameter numBytesToReturn, the DM signals the maximum buffer capacity for this block. The application asynchronously returns a ara::core::Future<OperationOutput>. The format of the payload data in OperationOutput.responseData is presumably subject to application-specific agreements (interpretation), since the specification merely specifies that this data is placed directly after the UDS Block Sequence Counter ([SWS_DM_00800]).
  4. Ending the session (RequestUploadExit): Finally, the DM calls RequestUploadExit() and passes manufacturer-specific parameters in the transferRequestParameterRecord ([SWS_DM_00801]). After confirmation by the returned ara::core::Future<OperationOutput>, the transfer is complete.

During all processing steps, the application can check via the CancellationHandler using IsCanceled() whether the conversation was canceled, or configure a callback for the cancellation via SetNotifier() ([SWS_DM_00799], [SWS_DM_00800], [SWS_DM_00801]).

Sequence diagram: Flow of a three-stage diagnostic upload transaction. Sources: [SWS_DM_00799], [SWS_DM_00800], [SWS_DM_00801]

Error Scenarios

Errors can occur both during instantiation and offering as well as during functional request processing:

  • Modeling and mapping violations: When the constructor is called, the consistency of the model is validated ([SWS_DM_00797]). If the resolution of the InstanceSpecifier fails or it does not point to a PortPrototype, an InstanceSpecifierMappingIntegrityViolation is raised. An PortInterfaceMappingViolation occurs if the port typed by DiagnosticUploadInterface is not referenced by an DiagnosticServiceGenericMapping. If the mapping to the runtime process is missing, an ProcessMappingViolation follows. If the same InstanceSpecifier is used multiple times in the process, this results in an InstanceSpecifierAlreadyInUseViolation ([SWS_DM_00797]).
  • State error during registration: If Offer() is called while the service is already being offered, the call fails and returns the error code DiagOfferErrc::kAlreadyOffered ([SWS_DM_00802]).
  • Negative diagnostic responses (NRC): If the application cannot serve a request in RequestUpload(), UploadData(), or RequestUploadExit() positively (e.g. invalid address range or invalid block length), the returned future is not fulfilled with a regular result, but readied with a corresponding UDS NRC error code from DiagUdsNrcErrc according to ISO 14229-1 ([SWS_DM_00799], [SWS_DM_00800], [SWS_DM_00801]).
  • Premature cancellation: If the client or the system cancels the diagnostic conversation, this is signaled via the CancellationHandler ([SWS_DM_00799]). The application must then discard ongoing preparations and terminate processing.
