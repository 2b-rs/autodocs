Context

Within module shwa (Hardware Accelerators) of the AUTOSAR Adaptive Platform, class ara::shwa::AcceleratorSelector forms a central building block for the targeted evaluation and selection of hardware accelerators. Class syntax identifies AcceleratorSelector as a public specialization of base class DeviceSelector (class AcceleratorSelector : public DeviceSelector). Its primary responsibility is to evaluate physical or logical instances of type Device according to a predefined selector strategy and to provide the device best suited for a task ([AP_SWS_SHWA_00412], [AP_SWS_SHWA_00413]).

Interaction partners at system level are the requesting Adaptive application, base class DeviceSelector as an interface contract, and the Device objects to be evaluated or allocated. The application integrates the selector to decouple hardware-related selection logic from the higher-level application logic.

Lifecycle

An instance of AcceleratorSelector is typically created in the initialization context of the application software component or a higher-level component manager. Regarding ownership, the class is designed as a function object and strategy instance: It presumably does not own the Device instances to be evaluated exclusively, but references them during evaluation or passes the selected device via a result object (ara::core::Result<Device>).

Methods operator() and SelectDevice() are declared as const as well as noexcept ([AP_SWS_SHWA_00412], [AP_SWS_SHWA_00413]). Despite the const interface, thread safety for both operations is explicitly specified as not thread-safe. Concurrent access by multiple threads to the same selector instance without external synchronization is therefore inadmissible. The specification does not mandate specific internal state phases; destruction occurs deterministically via standard C++ lifecycle rules.

Usage Path

Interaction with AcceleratorSelector typically follows two complementary paths: individual evaluation of candidate devices and direct selection of a target device.

For comparative analysis or filtering, applications can use function call operator operator()(const Device &device) ([AP_SWS_SHWA_00412]). This evaluates the passed device and returns a ara::core::Result<int>. Here, the integer result value is expected to serve as a quantitative suitability or priority score, based on which multiple accelerators can be sorted.

If the application wants to leave the selection decision entirely to the internal selector strategy, it calls SelectDevice() ([AP_SWS_SHWA_00413]). The method determines the most suitable device and provides it directly as ara::core::Result<Device>.

Error Scenarios

The error handling concept relies on ara::core::Result. According to the specification requirements, the methods are exception-safe (exception safe) and do not use rollback mechanisms (no_rollback_semantics) ([AP_SWS_SHWA_00412], [AP_SWS_SHWA_00413]). If a call fails, an error code from ShwaErrorCode is returned:

  • ShwaErrorCode::kResourceBusy: The evaluation or selection operation could not be completed because a required hardware or platform resource is currently busy ([AP_SWS_SHWA_00412], [AP_SWS_SHWA_00413]). The caller should retry the request at a later time.
  • ShwaErrorCode::kFeatureNotSupported: Occurs when a hardware feature required for the strategy or device is not supported ([AP_SWS_SHWA_00412], [AP_SWS_SHWA_00413]).

A precondition for operator() is that the passed Device reference must point to a valid device. In addition, callers must ensure that no concurrent accesses to the same instance take place. After an error occurs, the selector and devices remain in a consistent state.
