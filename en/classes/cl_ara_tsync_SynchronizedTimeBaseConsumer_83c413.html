Enables applications to query synchronized time values in a thread-safe manner and to register status notifiers.

Class ara::tsync::SynchronizedTimeBaseConsumer enables time applications to access a synchronized time base referenced via a ara::core::InstanceSpecifier ([SWS_TS_01001]). Via thread-safe methods, applications can query current snapshots of time values and status flags as well as clock rate deviation ([SWS_TS_01009]). In addition, notifiers can be registered for status changes, time leaps, validation data, and precision measurements, with at most one registration active per event type. Copy operations are prohibited, so instances can only be moved or released via their destructor.

Context

For time applications on the Adaptive Platform, class ara::tsync::SynchronizedTimeBaseConsumer forms the interface to a synchronized time base identified via a ara::core::InstanceSpecifier ([SWS_TS_01001]). Its core task is to provide applications with the current query point in time, clock rate deviation ([SWS_TS_01008]), as well as consistent status flags and received user data ([SWS_TS_01009]). Essential interaction partners are the calling application software (Time Consumer Application), the consumer instance itself, and the Tsync subsystem, which acquires synchronization data and initiates notification events ([SWS_TS_01016], [SWS_TS_01018]).

Lifecycle

Instantiation is performed via the explicit constructor by specifying a ara::core::InstanceSpecifier ([SWS_TS_01001]). This constructor is classified as thread-safe and exception-safe. To manage resources, the class implements strict move semantics: the move constructor ([SWS_TS_01003]) and move assignment operator ([SWS_TS_01004]) permit transfer of ownership, whereas the copy constructor ([SWS_TS_01005]) and copy assignment operator ([SWS_TS_01006]) are explicitly deleted (=delete). This prevents inadvertent duplication of access to the same time base resource.

The destructor releases the instance ([SWS_TS_01002]). Concurrency follows a clear separation: while the constructor ([SWS_TS_01001]) and the query methods GetRateDeviation ([SWS_TS_01008]) and GetTimeWithStatus ([SWS_TS_01009]) are implemented as thread-safe, all registration and deregistration functions, the move operations, and the destructor are specified as not thread-safe (non_threadsafe).

Usage Path

A regular usage sequence comprises the phases initialization, registration of relevant notifiers, cyclic or event-driven queries, and final cleanup:

  • Initialization: The application creates the object with the appropriate port instance specification ([SWS_TS_01001]).
  • Notifier registration: The application registers callback functions or notifier objects for specific events:
    • General status flag changes via RegisterStatusChangeNotifier ([SWS_TS_01010]),
    • Synchronization state changes via RegisterSynchronizationStateChangeNotifier ([SWS_TS_01012]),
    • Occurrence of a time leap via RegisterTimeLeapNotifier ([SWS_TS_01014]),
    • Reception of validation data blocks via RegisterTimeValidationNotification ([SWS_TS_01016]),
    • Availability of time precision measurements via RegisterTimePrecisionMeasurementNotifier ([SWS_TS_01018]).
    At most one registration can be active per notifier type; each subsequent registration overwrites the previous one ([SWS_TS_01010], [SWS_TS_01018]).
  • Querying during operation: Via GetTimeWithStatus(), the application retrieves a coherent snapshot (SynchronizedTimeBaseStatus) with status flags, clock configuration, and both local and synchronized time values ([SWS_TS_01009]). The current clock rate deviation is determined by means of GetRateDeviation() ([SWS_TS_01008]).
  • Cleanup: Before tearing down the consumer, notifiers are deregistered as needed via the corresponding calls such as UnregisterStatusChangeNotifier ([SWS_TS_01011]), UnregisterSynchronizationStateChangeNotifier ([SWS_TS_01013]), UnregisterTimeLeapNotifier ([SWS_TS_01015]), UnregisterTimeValidationNotification ([SWS_TS_01017]), or UnregisterTimePrecisionMeasurementNotifier ([SWS_TS_01019]) before the object is destroyed ([SWS_TS_01002]).

Sequence diagram: Typical sequence of initialization, notifier registration, cyclic query, and cleanup. Sources: [SWS_TS_01001], [SWS_TS_01008], [SWS_TS_01009], [SWS_TS_01010], [SWS_TS_01011], [SWS_TS_01002].

Error Scenarios

All interface methods of the class are declared with noexcept and specified as exception-safe (exception safe). Therefore, errors are not reported via C++ exceptions. The following boundary conditions and configuration violations must be observed:

  • Port mapping configuration errors: A PortPrototype referenced via an TimeSyncPortPrototypeToTimeBaseMapping must mandatory be typed via a SynchronizedTimeBaseConsumerInterface; otherwise a PortInterfaceMappingViolation is present ([SWS_TS_01001]).
  • Overwriting existing callbacks: If a registration method is called again, the new notifier overwrites the previously stored callback without a separate error notification ([SWS_TS_01010], [SWS_TS_01012], [SWS_TS_01014], [SWS_TS_01016], [SWS_TS_01018]).
  • Lack of queuing for precision measurements: The Tsync subsystem does not perform queuing for time precision measurement data ([SWS_TS_01018]). If the notifier cannot process the data in time, subsequent measurements are presumably lost unless the application provides its own buffering in the notifier.
  • Risk of data races with notifier methods: Because notifier registrations and deregistrations are designated as not thread-safe, a concurrent call from different execution contexts without external protection mechanisms is likely to lead to inconsistent states (interpretation).
