Context

In the shwa (Shared Hardware Accelerator) module, the ara::shwa::Queue class forms the central interface for execution scheduling on hardware accelerators. A queue encapsulates the connection to a specific execution device (Device) or a hardware unit addressed via a DeviceSelector and coordinates the submission and synchronization of work orders.

In the overall system, ara::shwa::Queue interacts with the following participants:

  • Application: Creates the queue via factory methods and controls the dispatching of tasks as well as the synchronization.
  • Device / DeviceSelector: Represents the target device to which the queue is bound and whose properties it reflects [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00910].
  • ErrorHandler: Receives feedback on asynchronously occurred errors during task processing [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00912].
  • Event: Is created when scheduling a task (Submit) and serves as a control and synchronization object for subsequent operations [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913].
  • PropertyList: Passes optional configuration parameters during the creation of the queue [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].

Context diagram: Interaction partners of the ara::shwa::Queue class. Sources: [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912]

Lifecycle

The ara::shwa::Queue class has strictly controlled instantiation and ownership semantics:

  • Creation: The default constructor is explicitly deleted [AP_SWS_SHWA_00902]. New instances can only be created via the static factory methods Create, which return a ara::core::Result<std::unique_ptr<Queue>> [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]. Creation binds the queue to a Device or a DeviceSelector, links an ErrorHandler, and evaluates optional PropertyList properties.
  • Ownership and identity: ara::shwa::Queue is neither copyable nor movable. Both the copy constructor [AP_SWS_SHWA_00903] and the copy assignment operator [AP_SWS_SHWA_00904], the move constructor [AP_SWS_SHWA_00905], and the move assignment operator [AP_SWS_SHWA_00906] are deleted. Therefore, the lifecycle of the instance is managed exclusively via the returned std::unique_ptr.
  • Destruction: If the queue is released or destroyed, the object is considered invalid. Calls to methods on destroyed or invalid queues are rejected with the error ShwaErrorCode::kInvalidObject [AP_SWS_SHWA_00913], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
  • Concurrency: The creation methods Create are thread-safe (thread-safe) [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]. In contrast, all regular member functions of the created instance (GetDevice, GetProperty, HasProperty, IsInOrder, Submit, Wait, WaitFor) are not thread-safe (not thread-safe). Concurrent access to the same queue instance from multiple threads therefore requires external synchronization by the application.

Usage Path

A typical workflow when using ara::shwa::Queue includes instantiation, property checking, task submission, and synchronization:

  1. Creating the queue: The application calls Queue::Create with the desired Device (or DeviceSelector), an ErrorHandler, and optionally a PropertyList [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].
  2. Querying properties: Before task submission, it can be checked whether tasks are processed strictly sequentially (IsInOrder [AP_SWS_SHWA_00911]), which Device is assigned (GetDevice [AP_SWS_SHWA_00910]), or whether specific feature properties are present (HasProperty [AP_SWS_SHWA_00915], GetProperty [AP_SWS_SHWA_00916]).
  3. Enqueuing tasks (Submit): A work task is submitted to the queue via Submit. The configuration cfg (interpretation: task-specific kernel or command configuration) is passed either with a task-specific ErrorHandler [AP_SWS_SHWA_00912] or coupled to a secondary queue (secondaryQueue) [AP_SWS_SHWA_00913]. Both variants return an ara::core::Result<Event>.
  4. Synchronizing task completion: The application waits for the completion of the enqueued tasks either indefinitely by means of Wait() [AP_SWS_SHWA_00914] or time-limited with a millisecond timeout via WaitFor(ms) [AP_SWS_SHWA_00917].

Sequence diagram: Typical call sequence from queue creation through Submit to synchronization. Sources: [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00911], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00917]

Error Scenarios

Methods of ara::shwa::Queue use ara::core::Result with error codes from the ShwaErrorCode domain for error indication:

  • Creation errors: Create fails if passed parameters are invalid (ShwaErrorCode::kInvalidParameter), a requested property is not supported (ShwaErrorCode::kFeatureNotSupported), the hardware resource is busy (ShwaErrorCode::kResourceBusy), or a general runtime error occurs (ShwaErrorCode::kRuntime) [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909].
  • Submission errors: With Submit, the operation can fail if invalid arguments were passed (ShwaErrorCode::kInvalidParameter), the queue is already destroyed or invalid (ShwaErrorCode::kInvalidObject), the resource is busy (ShwaErrorCode::kResourceBusy), or task execution fails (ShwaErrorCode::kTaskExecutionFailure) [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913].
  • Synchronization errors and timeouts: For Wait and WaitFor, in addition to kResourceBusy, kInvalidObject, kFeatureNotSupported, and kTaskExecutionFailure, particularly with WaitFor the error ShwaErrorCode::kTimedOut can occur if the specified deadline expires before the tasks are completed [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
  • Missing rollback semantics: For Submit, Wait, and WaitFor, in case of an error of kTaskExecutionFailure or kRuntime, explicitly no rollback guarantee (no_rollback_semantics) applies. Data and memory areas that were referenced within the failed task must be considered unintentionally modified [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00913], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
