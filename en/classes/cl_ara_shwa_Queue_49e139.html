Serves as an execution channel for submitting and synchronizing tasks on accelerator hardware.

The non-copyable class ara::shwa::Queue serves for the safe submission of computation tasks to acceleration hardware in interaction with devices and buffers SWS_SafeHardwareAcceleration p. 22 “Figure 7.1: High Level Design of Safe Hardware Acceleration in an Adaptive Platform”. After creation via factory method Create(), tasks are submitted with Submit() and synchronized via Wait() or WaitFor() [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00914]. Because object methods are not thread-safe and no rollback semantics apply in the event of execution errors, attention must be paid to external thread synchronization and data integrity [AP_SWS_SHWA_00912].

Context

The class ara::shwa::Queue represents the central execution channel for safe hardware acceleration in the Adaptive Platform. As illustrated by the overall design, applications typically interact with a combination of several queues, devices, and buffers SWS_SafeHardwareAcceleration p. 22 “Figure 7.1: High Level Design of Safe Hardware Acceleration in an Adaptive Platform”. Within this interaction, the queue assumes the task of accepting computation tasks or acceleration jobs and forwarding them to the underlying hardware device. The assigned device can be queried via GetDevice() [AP_SWS_SHWA_00910]. In addition, it can be determined via IsInOrder() whether jobs within the queue are processed strictly sequentially [AP_SWS_SHWA_00911]. Specific capabilities or parameters of the queue can be checked beforehand via HasProperty() [AP_SWS_SHWA_00915] and retrieved with GetProperty() [AP_SWS_SHWA_00916].

Context diagram: Embedding of the queue between application, hardware device, and error handling. Sources: SWS_SafeHardwareAcceleration p. 22 “Figure 7.1: High Level Design of Safe Hardware Acceleration in an Adaptive Platform”, [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00910].

Lifecycle

Instances of ara::shwa::Queue are subject to a strict ownership model. Both the default constructor [AP_SWS_SHWA_00902] as well as copy and move operations are explicitly deleted: copy constructor [AP_SWS_SHWA_00903], copy assignment [AP_SWS_SHWA_00904], move constructor [AP_SWS_SHWA_00905], and move assignment [AP_SWS_SHWA_00906] are not available. A queue is therefore neither copyable nor movable (Interpretation: It represents a firmly anchored resource).

Creation occurs exclusively via static factory methods Create(), which return the object encapsulated in a std::unique_ptr<Queue> within a ara::core::Result. The instantiation can be performed either based on an existing Device reference [AP_SWS_SHWA_00909] or via a generic DeviceSelector [AP_SWS_SHWA_00908]. Both variants additionally accept a ErrorHandler and an optional PropertyList. Regarding concurrency, the factory functions Create() are specified as thread-safe [AP_SWS_SHWA_00908], [AP_SWS_SHWA_00909]. In contrast, all regular member functions of the created instance—including Submit(), Wait(), and GetDevice()—are declared as not thread-safe [AP_SWS_SHWA_00910], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00914]; concurrent accesses from multiple threads must consequently be synchronized on the application side.

Usage Path

The regular sequence is divided into the phases of creation, job scheduling, and synchronization:

  1. Create queue: The application creates the queue via Create() with a concrete device or DeviceSelector as well as error handling routines [AP_SWS_SHWA_00909].
  2. Configuration and check: Optionally, properties are validated with HasProperty() [AP_SWS_SHWA_00915] and IsInOrder() [AP_SWS_SHWA_00911].
  3. Submit job: With Submit(), a task is passed to the hardware. Here, either a dedicated ErrorHandler can be passed [AP_SWS_SHWA_00912] or a secondary queue (secondaryQueue) can be specified for fallback or subsequent paths [AP_SWS_SHWA_00913]. The method returns a ara::core::Result<Event>.
  4. Synchronize: The application synchronizes on the completion of the submitted tasks. For this purpose, the unbounded Wait() [AP_SWS_SHWA_00914] or the time-limited WaitFor() with specification of a millisecond duration is available [AP_SWS_SHWA_00917].

Sequence diagram: Typical call sequence from creation via job submission to synchronization. Sources: [AP_SWS_SHWA_00909], [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00914].

Error Scenarios

The methods report error cases via the error code type ShwaErrorCode in ara::core::Result:

  • Resource and parameter conflicts: If Create() fails, ShwaErrorCode::kResourceBusy, ShwaErrorCode::kInvalidParameter, or ShwaErrorCode::kFeatureNotSupported, among others, can occur [AP_SWS_SHWA_00909]. Rollback semantics apply to these creation errors.
  • Call on invalid objects: If methods such as Submit(), Wait(), or WaitFor() are executed on already destroyed or invalid objects, the API acknowledges this with ShwaErrorCode::kInvalidObject [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00914], [AP_SWS_SHWA_00917].
  • Execution errors and data integrity: If an error occurs during task execution (ShwaErrorCode::kTaskExecutionFailure or more generally ShwaErrorCode::kRuntime), there are explicitly no rollback semantics (no_rollback_semantics). In these cases, the specification requires that the data involved in the execution must be considered inadvertently modified [AP_SWS_SHWA_00912], [AP_SWS_SHWA_00914].
  • Timeout: During synchronizing waiting via WaitFor(), ShwaErrorCode::kTimedOut signals the expiration of the specified deadline; here as well, affected data must be classified as potentially inconsistent [AP_SWS_SHWA_00917].
