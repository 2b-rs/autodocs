Context

The class ara::core::SynchronizedPoolResource acts as a thread-safe polymorphic memory resource in the AUTOSAR Adaptive Platform. It is based on the specification pattern of std::pmr::synchronized_pool_resource from [mem.res.pool] and derives from the base interface ara::core::MemoryResource. Its primary task is to serve dynamic memory requests from predefined pools of memory blocks efficiently and in a synchronized manner in order to minimize fragmentation and allocation overhead in concurrent software components.

Typically, three parties are involved in the interaction: firstly, multiple requesting threads or containers that request memory via polymorphic allocators; secondly, the instance of SynchronizedPoolResource itself, which serializes access to the internal pools in a thread-safe manner; and finally, a higher-level memory resource (upstream resource) from which the pool instance requests larger memory chunks when needed ([SWS_CORE_00038]).

Context diagram: Coordination of memory requests from multiple application threads via SynchronizedPoolResource to the higher-level upstream memory resource. Sources: [SWS_CORE_00030], [SWS_CORE_00038], [SWS_CORE_00061].

Lifecycle

The lifecycle of a SynchronizedPoolResource begins with its instantiation via one of four constructors. Configuration can be performed via options (PoolOptions) and by specifying a higher-level memory resource (MemoryResource*):

  • The default constructor [SWS_CORE_00031] creates an instance with default parameters; it is classified as thread-safe, but formally as not exception-safe (not exception safe).
  • The constructor with explicit passing of an upstream resource [SWS_CORE_00032] allows linking to a specific base memory manager.
  • Allocation limits and pool sizes can be adjusted by passing PoolOptions [SWS_CORE_00033].
  • The fully featured constructor, which accepts both PoolOptions and an upstream pointer [SWS_CORE_00030], is declared as noexcept and is completely exception-safe.

Interpretation: If no upstream pointer is passed to the constructor ([SWS_CORE_00031], [SWS_CORE_00033]), the instance presumably falls back internally to the platform's default polymorphic memory resource.

Regarding ownership and copy semantics, the specification prohibits duplicating pool resources: Both the copy constructor [SWS_CORE_00034] and the copy assignment operator [SWS_CORE_00036] are deleted (=delete). A significant AUTOSAR-specific extension compared to the ISO/IEC 14882 standard is move semantics: Both the move constructor [SWS_CORE_00043] and the move assignment operator [SWS_CORE_00044] are provided as noexcept = default and are exception-safe.

During operation, all allocated memory can be returned to the upstream resource via the call to release() [SWS_CORE_00037] without destroying the resource instance. Upon destruction via the destructor ~SynchronizedPoolResource() [SWS_CORE_00035], which is declared as noexcept override, AUTOSAR exhibits a deviation from the C++ standard: The destructor function is not declared virtual.

Usage Path

In a typical usage scenario, the resource instance is created centrally and passed to polymorphic containers or memory requesters. Prior to allocation, properties such as the configured options can be inspected via options() [SWS_CORE_00039] or the upstream resource via upstream_resource() [SWS_CORE_00038]. In addition, do_is_equal() [SWS_CORE_00042] allows checking for equality with another MemoryResource.

Memory requests are processed in a thread-safe manner via the protected interface do_allocate() [SWS_CORE_00061]. If the internal pool for the requested size is exhausted, the instance requests additional memory block buffers from the upstream resource. Individual blocks are subsequently released via do_deallocate() [SWS_CORE_00041]. At the end of a processing phase or prior to shutdown, release() [SWS_CORE_00037] enables a complete release of all retained chunks to the upstream.

Sequence diagram: Typical sequence of allocation, upstream replenishment, and buffer cleanup via SynchronizedPoolResource. Sources: [SWS_CORE_00030], [SWS_CORE_00037], [SWS_CORE_00038], [SWS_CORE_00061].

Error Scenarios

AUTOSAR defines a strict behavior without C++ exceptions (no-throw guarantee) for ara::core::SynchronizedPoolResource, which deviates significantly from std::pmr::synchronized_pool_resource:

  • Allocation errors: The allocation method do_allocate() is declared as noexcept ([SWS_CORE_00061]). If the memory resource cannot fulfill a request due to a lack of memory, no exception of type std::bad_alloc is thrown; instead, the function mandatorily returns a null pointer (nullptr). Calling components must therefore explicitly validate the return result for nullptr.
  • Errors during deallocation: do_deallocate() is also declared with noexcept ([SWS_CORE_00041]). If errors occur when releasing a memory area, they are silently ignored according to the specification (silently ignored).
  • Construction risks: While the complete constructor [SWS_CORE_00030] is exception-safe and defined as noexcept, the alternative constructors ([SWS_CORE_00031], [SWS_CORE_00032], [SWS_CORE_00033]) are marked as not exception-safe, as errors can occur during the initial reservation of internal pool structures.
