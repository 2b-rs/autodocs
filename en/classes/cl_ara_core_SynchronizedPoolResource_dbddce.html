Provides a thread-safe pool memory resource for efficient allocation and deallocation of memory blocks.

The class ara::core::SynchronizedPoolResource provides a thread-safe memory resource that handles allocations via internal pools and requests additional memory from a higher-level upstream resource ([SWS_CORE_00030]). In contrast to the C++ standard, memory allocation does not throw exceptions upon failures, but instead returns nullptr ([SWS_CORE_00061]). Copy operations are completely prevented, while move operations are explicitly supported. In addition, the destructor is non-virtual, which is why instances must not be deallocated polymorphically via a base class pointer.

Context

The class ara::core::SynchronizedPoolResource provides a thread-safe memory resource for the AUTOSAR Adaptive Platform within the module core. It is based on the concept of std::pmr::synchronized_pool_resource according to C++ standard [mem.res.pool] and derives publicly from the base class MemoryResource. Its core task is to manage memory blocks via internal pools categorized by size classes in order to handle recurring allocations efficiently and concurrently. If the internal supply is insufficient, the instance obtains larger memory blocks from a higher-level upstream memory resource ([SWS_CORE_00038]).

Typical interaction partners include concurrent threads of an application requesting allocations, the SynchronizedPoolResource as an intermediary pool manager, and an underlying MemoryResource as an upstream source. All central access and management functions such as do_allocate, do_deallocate, options, and release are designed to be thread-safe ([SWS_CORE_00061], [SWS_CORE_00041], [SWS_CORE_00039], [SWS_CORE_00037]).

Context diagram: Interplay between concurrent application threads, the pool resource, and the upstream memory source. Sources: [SWS_CORE_00030], [SWS_CORE_00038].

Lifecycle

The instantiation of SynchronizedPoolResource can occur via several constructor overloads. If both allocation options (PoolOptions) and an upstream resource are available, initialization guarantees complete exception safety and is declared as noexcept ([SWS_CORE_00030]). In addition, there are constructors without parameters ([SWS_CORE_00031]), with an upstream pointer only ([SWS_CORE_00032]), or with pool options only ([SWS_CORE_00033]). Interpretation: If no upstream pointer is passed, the implementation presumably falls back on a platform-specific default memory resource.

Regarding ownership, the class strictly excludes copying: both the copy constructor ([SWS_CORE_00034]) and the copy assignment operator ([SWS_CORE_00036]) are deleted (=delete). In contrast to the ISO C++17 standard, however, AUTOSAR explicitly defines move semantics for this class: a move constructor ([SWS_CORE_00043]) and a move assignment operator ([SWS_CORE_00044]) are each provided as noexcept=default.

A central aspect of destruction is the deviation from standard behavior: the destructor ~SynchronizedPoolResource() is explicitly non-virtual ([SWS_CORE_00035]). Interpretation: Since the destructor is not virtual, polymorphic destruction via a pointer of base class MemoryResource* is likely to lead to undefined behavior; instances should therefore always be destroyed via their concrete type. In addition, by calling release(), all allocated memory can be returned to the upstream resource while the resource object remains intact ([SWS_CORE_00037]).

Usage Path

The typical sequence comprises initialization, repeated allocation and deallocation of memory blocks, and final cleanup:

  1. Initialization: The application creates the instance specifying configuration parameters and a higher-level memory resource ([SWS_CORE_00030]). The active settings can be queried via options() ([SWS_CORE_00039]), and the upstream pointer via upstream_resource() ([SWS_CORE_00038]).
  2. Memory allocation: Memory requests are processed in a protected manner via do_allocate ([SWS_CORE_00061]). Interpretation: The invocation in application code usually does not take place directly via the protected method do_allocate, but via the inherited public interface allocate of the base class MemoryResource.
  3. Identity check: Via do_is_equal, it can be determined whether two memory resources are equivalent to each other ([SWS_CORE_00042]).
  4. Deallocation: Individual memory areas are returned to the pool via do_deallocate ([SWS_CORE_00041]). If required, all memory of all pools can be returned collectively to the upstream resource via release() ([SWS_CORE_00037]).

Sequence diagram: Typical sequence of initialization, memory request, deallocation, and cleanup via upstream resources. Sources: [SWS_CORE_00030], [SWS_CORE_00061], [SWS_CORE_00041], [SWS_CORE_00037].

Error Scenarios

In error handling, the AUTOSAR Adaptive Platform deliberately deviates from the exception conventions of the C++ standard:

  • Allocation error: While ISO C++ provides for throwing std::bad_alloc in the event of exhaustion, do_allocate in AUTOSAR is defined as noexcept. If no suitable memory block can be provided, the method mandatorily returns a null pointer (nullptr) instead ([SWS_CORE_00061]). Callers must therefore check every allocation return value for nullptr.
  • Deallocation error: The method do_deallocate is also noexcept. If an error occurs when returning a memory block, it is silently ignored according to the specification ([SWS_CORE_00041]).
  • Construction risks: While the constructor with options and upstream resource is exception-safe ([SWS_CORE_00030]), the constructors without an upstream specification or without options are classified as not exception-safe ("not exception safe") ([SWS_CORE_00031], [SWS_CORE_00032], [SWS_CORE_00033]). Interpretation: If the internal provisioning of pool management structures fails for these constructors, object creation may fail.

                          Usage and Allocation Semantics
                          

                          The member function do_allocate of class ara::core::SynchronizedPoolResource from the header file #include "ara/core/memory_resource.h" serves to allocate memory areas with the specified byte size bytes and alignment alignment [SWS_CORE_00061]. In the event of success, the synchronous call returns a valid pointer of type void* to the allocated memory block according to [mem.res.pool] [SWS_CORE_00061].
                          

                          Error Handling and Deviations
                          

                          Regarding error behavior, the implementation explicitly deviates from the requirements in [mem.res.pool]: The method is declared as noexcept and does not throw a std::bad_alloc exception [SWS_CORE_00061]. Upon failure of the memory request, the returned pointer is instead mandatorily nullptr [SWS_CORE_00061]. Callers must therefore check the return value for a null pointer to reliably intercept allocation errors.
                          

                          Concurrency and Interaction
                          

                          The function is specified as exception safe and, in contrast to other memory resources, as thread-safe [SWS_CORE_00061]. Due to its protected visibility, it is expected in practice to function primarily as an internal override of the pure virtual base interface do_allocate from ara::core::MemoryResource [SWS_CORE_06566]. While ara::core::SynchronizedPoolResource secures concurrent access [SWS_CORE_00061], comparable implementations such as ara::core::UnsynchronizedPoolResource::do_allocate [SWS_CORE_00058] and ara::core::MonotonicBufferResource::do_allocate [SWS_CORE_06569] are defined as not thread-safe.
