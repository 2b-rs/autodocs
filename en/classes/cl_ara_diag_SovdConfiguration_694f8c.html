Serves for the application-side provision and processing of explicitly modeled SOVD configuration resources.

The interface ara::diag::SovdConfiguration serves as a generic handler for explicitly modeled SOVD configurations to which the Diagnostic Server forwards incoming read and write accesses [SWS_DM_01860], [SWS_DM_01787]. After port-based instantiation, the application activates message reception via Offer and terminates it when required with StopOffer [SWS_DM_01872], [SWS_DM_01930]. Data provision is performed asynchronously via read or write sessions, whereby functional errors are signaled according to ISO 17978-3 or ASAM SOVD 1.1 [SWS_DM_01870].

Context

The interface ara::diag::SovdConfiguration defines the generic interface for explicitly modeled SOVD configuration handlers within the Adaptive AUTOSAR diagnostic architecture [SWS_DM_01860]. If at least one SOVD configuration is configured in the system, the Diagnostic Server instance of Diagnostic Management (DM) provides the standardized SOVD method Retrieve List of All Configurations Provided by the Entity according to ASAM SOVD externally [SWS_DM_01429]. The Diagnostic Server forwards incoming read and write accesses to such an explicit configuration to the concrete implementation of ara::diag::SovdConfiguration: When the SOVD method Read Configuration is invoked, the Diagnostic Server calls the method RequestGetConfiguration [SWS_DM_01787], whereas when Write Configuration is invoked, the method RequestPutConfiguration is executed [SWS_DM_01788].

Context diagram: Embedding of ara::diag::SovdConfiguration between external SOVD client, Diagnostic Server (DM), and application-specific handler. Sources: [SWS_DM_01429], [SWS_DM_01787], [SWS_DM_01788], [SWS_DM_01860].

Lifecycle

Instantiation of ara::diag::SovdConfiguration is performed on the application side by passing a ara::core::InstanceSpecifier and specifying a ConcurrencyType (kConcurrent or kNotConcurrent) [SWS_DM_01864]. The InstanceSpecifier references a port prototype of a DiagnosticSovdConfigurationInterface in the process context [SWS_DM_01864]. The class must not be copied (copy constructor and copy assignment operator are declared as delete) [SWS_DM_01866], [SWS_DM_01868], but supports protected move operations [SWS_DM_01867], [SWS_DM_01869]. To accept requests from the Diagnostic Server, the application must explicitly call Offer [SWS_DM_01872]. Calling StopOffer deactivates request forwarding again [SWS_DM_01930]. Upon destruction of the instance via the virtual destructor [SWS_DM_01865], the object is released; release requires that the handler was previously properly deregistered.

State diagram: Lifecycle phases of a SovdConfiguration instance from initialization through Offer state to StopOffer. Sources: [SWS_DM_01864], [SWS_DM_01872], [SWS_DM_01930], [SWS_DM_01865].

Usage Path

A typical usage path begins after construction of the derived handler class with registration with Diagnostic Management via Offer() [SWS_DM_01872]. As soon as an external client sends an SOVD configuration request to the entity, the Diagnostic Server forwards it: For a read request, RequestGetConfiguration is called, passing the configurationId, the metaInfo, and a CancellationHandler [SWS_DM_01870]. The method returns a ara::core::Future that asynchronously provides a tuple of a DataTransferReadSession and SovdConfigurationMetaInfo [SWS_DM_01870]. Analogously, the server forwards write requests via RequestPutConfiguration, which returns a future with a DataTransferWriteSession and SovdConfigurationMetaInfo [SWS_DM_01871]. Prior to shutting down the handler, the application calls StopOffer() to no longer accept any further requests [SWS_DM_01930].

Sequence diagram: Typical interaction sequence during initialization, servicing of a Read Configuration request, and subsequent deregistration. Sources: [SWS_DM_01872], [SWS_DM_01787], [SWS_DM_01870], [SWS_DM_01930].

Error Scenarios

Model and mapping violations can already occur during instantiation in the constructor if the InstanceSpecifier cannot be resolved in the model (InstanceSpecifierMappingIntegrityViolation), the referenced port prototype is not typed by a DiagnosticSovdConfigurationInterface (PortInterfaceMappingViolation), no matching process exists (ProcessMappingViolation), or the identifier is already occupied in the current process (InstanceSpecifierAlreadyInUseViolation) [SWS_DM_01864]. When calling Offer(), the method returns a ara::core::Result<void>, which in the event of an error reports DiagOfferErrc::kConfigurationMismatch if the configuration does not match the DEXT model, or DiagOfferErrc::kAlreadyOffered if the service is already offered [SWS_DM_01872]. In the asynchronous handler methods RequestGetConfiguration and RequestPutConfiguration, the application reports error states via the ara::core::Future using standardized SOVD error codes according to ISO 17978-3 or ASAM SOVD 1.1 [SWS_DM_01870], [SWS_DM_01871]. In addition, the CancellationHandler signals whether an ongoing communication was cancelled [SWS_DM_01870], [SWS_DM_01871].

use

The method Offer of class ara::diag::SovdConfiguration serves to enable the forwarding of diagnostic requests by Diagnostic Management (DM) to the configured handler [SWS_DM_01872]. The call takes place synchronously, takes no parameters, and reports back the result via ara::core::Result<void> [SWS_DM_01872]. As long as a handler has not been offered via Offer, the DM does not forward incoming requests, which corresponds to the basic offering pattern of diagnostic interfaces (cf. [SWS_DM_01525], [SWS_DM_00809]).

Error handling

In the event of an error, a ara::core::Result with an error code of the enumeration DiagOfferErrc is returned, whereby rollback semantics apply [SWS_DM_01872]:

  • DiagOfferErrc::kAlreadyOffered: Is reported if the service was already offered beforehand [SWS_DM_01872].
  • DiagOfferErrc::kConfigurationMismatch: Occurs if the configuration does not match the DEXT description data [SWS_DM_01872].

Concurrency and Limitations

The operation is declared as noexcept and exception-safe (exception safe), but is specified as not thread-safe (not thread-safe) [SWS_DM_01872]. Simultaneous calls to the same instance from multiple threads must be prevented by the calling application. A repeated call after an offering has already taken place would presumably be acknowledged with an error without a state change. Question Q-f9b1a995dbb002ef (open)

      use
      

      The pure virtual method RequestGetConfiguration of class ara::diag::SovdConfiguration is called by the Diagnostic Server Instance when the SOVD method "Read Configuration" is executed for an explicitly modeled SOVD configuration ([SWS_DM_01787], AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 “Configuration – Explicit Configurations”). Passed as parameters are the configuration ID of the instance to be read (configurationId), the meta-information of the request (metaInfo), and a cancellationHandler that informs about a possible cancellation of the running conversation ([SWS_DM_01870]).
      

      The function works asynchronously and returns a ara::core::Future that provides a tuple consisting of a file read session (DataTransferReadSession) and associated configuration meta-information (SovdConfigurationMetaInfo) ([SWS_DM_01870]). The interface is declared as noexcept and specified as exception-safe ([SWS_DM_01870]).
      

      Error Handling and Concurrency
      

      If an error occurs during processing, no C++ error is thrown, but an applicable SOVD error code in accordance with ISO 17978-3 or ASAM SOVD 1.1 is returned via the Future ([SWS_DM_01870]).
      

      Regarding thread safety, the "conditional" requirement applies: Whether the concrete implementation of the function must be designed to be thread-safe or non-thread-safe is decided by the ConcurrencyType passed to the constructor ([SWS_DM_01870]).

          The API method ara::diag::SovdConfiguration::RequestPutConfiguration is called by the Diagnostic Server when the method "Write Configuration" is to be executed via the SOVD interface for an explicitly modeled configuration [SWS_DM_01788], [SWS_DM_01871].
          

          Call and Parameters
          

          The declaration is located in header ara/diag/sovd_configuration.h. The call passes the following input parameters [SWS_DM_01871]:
          

            

          • configurationId: ID of the configuration instance to be written as ara::core::String.
            • 

          • metaInfo: Meta-information on the incoming request (MetaInfo const &).
            • 

          • cancellationHandler: Monitors the current operation and signals if communication was cancelled.
            • 

          

          The method has asynchronous semantics and returns a ara::core::Future, which in the event of success provides a tuple consisting of a write session (DataTransferWriteSession) and associated metadata (SovdConfigurationMetaInfo) [SWS_DM_01871].
          

          Error Handling and Concurrency
          

          In the event of an error, the Future is resolved with an appropriate SOVD error code according to ISO 17978-3 or ASAM SOVD 1.1 [SWS_DM_01871]. The function is declared as noexcept and exception-safe (exception safe). Thread safety is conditional (conditional): Whether the concrete implementation must be designed to be thread-safe is determined by the ConcurrencyType specified in the constructor [SWS_DM_01871].
          

          Interaction
          

          The function forms the writing counterpart to RequestGetConfiguration, which is used for the SOVD method "Read Configuration" [SWS_DM_01787] (AUTOSAR_AP_SWS_Diagnostics §7.3.3.5.2.1 “Configuration – Explicit Configurations”).
