Serves for the secure unpacking and importing of protected cryptographic keys and data in an application.

The interface enables the secure unpacking and importing of protected cryptographic data and keys using a configured transport key [SWS_CRYPT_50205]. The unpacked key material can either be written directly to a persistent key slot or loaded into memory as a typed key object [SWS_CRYPT_50207]. All methods operate thread-safely and follow strict rollback error semantics, while Reset ensures the residue-free erasure of internal buffers [SWS_CRYPT_50212].

Context

The interface ara::crypto::cryp::ProtectedKeyImportCtx provides a cryptographic context to securely import and unpack protected data structures such as secret key material into the system. The context acts as an intermediary between a requesting application, a protection mechanism based on a transport key, and the target structures of AUTOSAR cryptography. Incoming serialized data packets are authenticated, decrypted, and parsed by the context [SWS_CRYPT_50207]. Either standalone symmetric key objects [SWS_CRYPT_50205] or key slots of a key storage [SWS_CRYPT_50206] serve as sources for the required transport key. As a sink, unpacked key objects can be passed directly to the calling application or serialized directly into a writable key slot [SWS_CRYPT_50207].

Lifecycle

The context is usually managed for shared access via the provided smart pointer type Sptr [SWS_CRYPT_50085]; instances are likely provided by a responsible crypto driver component. Prior to actual processing, the context is in an unconfigured initial state in which no transport key is assigned yet. The assignment of a transport key takes place via the method SetKey, whereby the context transitions into the operational state [SWS_CRYPT_50205] [SWS_CRYPT_50206].

After successful execution of the operation Import, the context maintains the unpacked data and metadata in internal buffers so that the object type can be identified and key objects can be read out [SWS_CRYPT_50207] [SWS_CRYPT_50208]. Via the method Reset, the context is reset back to its initial state: all internal buffers with previously imported data are completely cleared and the stored transport key is removed [SWS_CRYPT_50212]. All interface methods are specified as exception-safe and thread-safe, whereby concurrent accesses from multiple execution contexts remain manageable [SWS_CRYPT_50207].

State diagram: Life phases of the context from configuration through import to cleanup. Sources: [SWS_CRYPT_50205], [SWS_CRYPT_50206], [SWS_CRYPT_50207], [SWS_CRYPT_50212]

Usage Path

The regular workflow begins with the configuration of the transport key. For this purpose, the application calls SetKey either with a SymmetricKey::Sptr [SWS_CRYPT_50205] or with a KeySlot::Sptr [SWS_CRYPT_50206]. In the next step, the method Import is executed, to which the serialized data packet is passed as ReadOnlyMemRegion [SWS_CRYPT_50207]. If the key is to be stored persistently, a WriteableKeySlot::Sptr into which the unpacked material is written can optionally be passed directly [SWS_CRYPT_50207].

If no target slot was specified or if the key is to be used transiently, the application determines the category of the most recently imported object via GetCryptoObjectType [SWS_CRYPT_50208]. Based on this type, the application calls the type-appropriate retrieval method: GetPrivateKey for private keys [SWS_CRYPT_50209], GetPublicKey for public keys [SWS_CRYPT_50211], or GetSymmetricKey for symmetric key material [SWS_CRYPT_50210]. If the used import protocol requires a response to the sender—such as with the control blocks M4 and M5 of a SHE LoadKey sequence—this can be written into a provided buffer via GetResponse [SWS_CRYPT_41020]. After completion of the processing sequence, a call to Reset resets the context back to the initial state [SWS_CRYPT_50212].

Sequence diagram: Typical call sequence when importing and reading out key material. Sources: [SWS_CRYPT_50205], [SWS_CRYPT_50207], [SWS_CRYPT_50208], [SWS_CRYPT_50210], [SWS_CRYPT_50212]

Error Scenarios

If an error occurs during a method call, strict rollback semantics take effect that preserve the state prior to the call. During configuration via SetKey, the call fails with CryptoErrc::kUsageViolation if the key's usage flag does not contain the permission kAllowKeyUnwrapping [SWS_CRYPT_50205] [SWS_CRYPT_50206]. If the key object or the referenced slot cannot fundamentally be used as a transport key, CryptoErrc::kIncompatibleObject is reported [SWS_CRYPT_50205] [SWS_CRYPT_50206].

When calling Import, size discrepancies of the input data lead to CryptoErrc::kInvalidInputSize and format violations lead to CryptoErrc::kInvalidArgument [SWS_CRYPT_50207]. If the integrity or authenticity check of the protection layer fails (e.g. due to an invalid message authentication code or a faulty signature), the call returns CryptoErrc::kAuthTagNotValid [SWS_CRYPT_50207]. If the crypto component is temporarily busy, this is signaled via CryptoErrc::kBusyResource [SWS_CRYPT_50207].

A precondition for reading out imported keys is the successful execution of Import; otherwise GetPrivateKey, GetPublicKey, and GetSymmetricKey respond with CryptoErrc::kProcessingNotFinished [SWS_CRYPT_50209] [SWS_CRYPT_50210] [SWS_CRYPT_50211]. If the requested key type does not match the actually unpacked object or if no object has been imported yet, the retrieval methods acknowledge this with CryptoErrc::kNoSuchValue [SWS_CRYPT_50208] [SWS_CRYPT_50209] [SWS_CRYPT_50210] [SWS_CRYPT_50211]. If the output buffer does not provide sufficient capacity in GetResponse, this results in CryptoErrc::kInsufficientCapacity [SWS_CRYPT_41020]. If the concrete implementation does not support a sub-function (e.g. certain key types or resetting), CryptoErrc::kUnsupported is consistently returned [SWS_CRYPT_50205] [SWS_CRYPT_50208] [SWS_CRYPT_50212].
