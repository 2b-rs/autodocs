Context

The ara::diag::SecurityAccess class defines the interface for handling the UDS service 0x27 (SecurityAccess) in AUTOSAR Adaptive. It serves as an abstract handler through which applications provide the seed and key procedure for unlocking protected diagnostic functions. The primary interaction partner is the central diagnostic manager (Diagnostic Management, DM), which receives incoming diagnostic messages from external diagnostic testers and, after registration, forwards them to the instance of ara::diag::SecurityAccess [SWS_DM_00766]. The application software derives from this class and implements the pure virtual methods for providing a seed ([SWS_DM_00764]) and for key validation ([SWS_DM_00765]).

Context diagram: Interaction between diagnostic tester, Diagnostic Management (DM), and the application-specific SecurityAccess implementation. Sources: [SWS_DM_00764], [SWS_DM_00765], [SWS_DM_00766]

Lifecycle

Instances of ara::diag::SecurityAccess represent a single, unique port element. Accordingly, copy and move operations are explicitly prevented: neither the copy constructor nor the move constructor or the corresponding assignment operators are available ([SWS_DM_01615], [SWS_DM_01616], [SWS_DM_01617], [SWS_DM_01618]). Creation must be performed via the parameterized constructor specifying a modeled ara::core::InstanceSpecifier and the concurrency mode ConcurrencyType [SWS_DM_00762].

After instantiation, the object is in the \"not offered\" state. The active reception of requests must be explicitly activated by calling Offer() [SWS_DM_00766]. Forwarding of diagnostic requests by the DM can be interrupted at any time via StopOffer() [SWS_DM_00767]. Interpretation: It is likely advisable to explicitly call StopOffer() before destroying the instance via the virtual destructor ~SecurityAccess() [SWS_DM_00763], since the destructor is declared as not thread-safe. The ConcurrencyType (kConcurrent or kNotConcurrent) passed to the constructor determines whether the derived callback functions must be implemented thread-safely [SWS_DM_00762].

Usage Path

A typical sequence of security authentication comprises offering the service, the seed query, and the validation of the transmitted key:

  1. Offering the service: The application instantiates the derived class and calls Offer(), thereby authorizing the DM to forward diagnostic requests for the assigned security level [SWS_DM_00766].
  2. Requesting a seed: If the diagnostic tester sends a UDS message requesting a seed (subfunction Request Seed), the DM forwards this call to GetSeed() [SWS_DM_00764]. The method receives the payload record (securityAccessDataRecord), request metadata (metaInfo), and a cancellationHandler. The implementation returns a ara::core::Future that provides the seed as a byte vector. The passed payload remains valid until the associated promise is fulfilled or the operation is canceled [SWS_DM_00764].
  3. Verifying the key: After receiving the key from the tester (subfunction Send Key), the DM calls the CompareKey() method [SWS_DM_00765]. The key to be verified is passed as ara::core::Span. The application validates the key asynchronously and reports the result back via ara::core::Future<KeyCompareResultType>.
  4. Stopping the service: If the interface is to be deactivated, the application calls StopOffer(), whereby the DM delivers no further requests [SWS_DM_00767].

Sequence diagram: Typical sequence of security authentication from Offer via GetSeed and CompareKey to StopOffer. Sources: [SWS_DM_00764], [SWS_DM_00765], [SWS_DM_00766], [SWS_DM_00767]

Error Scenarios

Errors can occur during modeling, during service provision, and during the execution of the authentication methods:

  • Modeling and instantiation errors: Violations can be triggered during constructor call [SWS_DM_00762]:
    • InstanceSpecifierMappingIntegrityViolation: The InstanceSpecifier cannot be resolved in the process context or does not refer to a PortPrototype.
    • PortInterfaceMappingViolation: The PortPrototype does not refer to a DiagnosticSecurityLevelInterface.
    • ProcessMappingViolation: No matching modeled process exists for the instance reference.
    • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already used by another instance in the running process.
  • State conflicts when offering: If Offer() is called while the service is already being offered, the call fails and returns error code DiagOfferErrc::kAlreadyOffered in the result [SWS_DM_00766].
  • Diagnostic errors (NRC): If seed generation or key comparison cannot be completed regularly, the application signals errors via the returned ara::core::Future using corresponding Negative Response Codes (NRCs according to ISO 14229-1) using DiagUdsNrcErrc ([SWS_DM_00764], [SWS_DM_00765]).
  • Persistent failed attempt counters: After each failure when changing the security level, the failed attempt counter must be incremented and mandatorily stored persistently to survive resets (AUTOSAR_AP_SWS_Diagnostics §4.1 p. 63).
  • Cancellation of conversations: If a diagnostic conversation terminates prematurely, this can be queried via cancellationHandler.IsCanceled() or monitored via SetNotifier ([SWS_DM_00764], [SWS_DM_00765]).

use

The pure virtual method CompareKey of class ara::diag::SecurityAccess ([SWS_DM_00765], header #include "ara/diag/security_access.h") is implemented by the diagnostic application in order to validate the key transmitted by the client for unlocking a security level in the context of the UDS service 0x27 (SecurityAccess) ([SWS_DM_00236], [SWS_DM_00765]).

  • key: ara::core::Span<const std::uint8_t> with the key to be validated. The validity of the data is guaranteed until the promise is fulfilled or the operation is canceled ([SWS_DM_00765]).
  • metaInfo: Provides metainformation (MetaInfo) on the incoming request ([SWS_DM_00765]).
  • cancellationHandler: Enables querying a cancellation of the conversation via IsCanceled as well as registering a notification function via SetNotifier ([SWS_DM_00765]).

Processing takes place asynchronously via the return of a ara::core::Future<KeyCompareResultType> ([SWS_DM_00765]).

Error handling

In case of error, an applicable negative response code (NRC) according to ISO 14229-1 must be provided via DiagUdsNrcErrc ([SWS_DM_00765]). The diagnostic server instance counts failed attempts to change the security level ([SWS_DM_00270]) and compares them with configured threshold values ([SWS_DM_00271]).

Concurrency and Limitations

The function is defined as noexcept and exception safe (exception safe) ([SWS_DM_00765]). The thread safety is conditional (conditional): Whether the method must be designed thread-safe depends on the ConcurrencyType passed in the constructor ([SWS_DM_00765]).

Interaction

Together with GetSeed, CompareKey forms the application-side implementation of the seed/key mechanism for service 0x27 (AUTOSAR_AP_SWS_Diagnostics §7.3.2.8.9 “Service 0x27 – SecurityAccess”). Upon successful unlocking, the server instance updates the security status of the conversation ([SWS_DM_00846]) and reports the security event SEV_UDS_SECURITY_ACCESS_SUCCESSFUL to the IdsM ([SWS_DM_02019]).

<h4>Lifecycle</h4>
<p>Instances of <code>ara::diag::SecurityAccess</code> represent a single, unique port element. Accordingly, copy and move operations are explicitly prevented: neither the copy constructor nor the move constructor or the corresponding assignment operators are available (<a class="spec-record-ref" data-req="SWS_DM_01615" href="../spec/record.html?id=SWS_DM_01615">[SWS_DM_01615]</a>, <a class="spec-record-ref" data-req="SWS_DM_01616" href="../spec/record.html?id=SWS_DM_01616">[SWS_DM_01616]</a>, <a class="spec-record-ref" data-req="SWS_DM_01617" href="../spec/record.html?id=SWS_DM_01617">[SWS_DM_01617]</a>, <a class="spec-record-ref" data-req="SWS_DM_01618" href="../spec/record.html?id=SWS_DM_01618">[SWS_DM_01618]</a>). Creation must be performed via the parameterized constructor specifying a modeled <code>ara::core::InstanceSpecifier</code> and the concurrency mode <code>ConcurrencyType</code> <a class="spec-record-ref" data-req="SWS_DM_00762" href="../spec/record.html?id=SWS_DM_00762">[SWS_DM_00762]</a>.</p>
<p>After instantiation, the object is in the \"not offered\" state. The active reception of requests must be explicitly activated by calling <code>Offer()</code> <a class="spec-record-ref" data-req="SWS_DM_00766" href="../spec/record.html?id=SWS_DM_00766">[SWS_DM_00766]</a>. Forwarding of diagnostic requests by the DM can be interrupted at any time via <code>StopOffer()</code> <a class="spec-record-ref" data-req="SWS_DM_00767" href="../spec/record.html?id=SWS_DM_00767">[SWS_DM_00767]</a>. Interpretation: It is likely advisable to explicitly call <code>StopOffer()</code> before destroying the instance via the virtual destructor <code>~SecurityAccess()</code> <a class="spec-record-ref" data-req="SWS_DM_00763" href="../spec/record.html?id=SWS_DM_00763">[SWS_DM_00763]</a>, since the destructor is declared as not thread-safe. The <code>ConcurrencyType</code> (<code>kConcurrent</code> or <code>kNotConcurrent</code>) passed to the constructor determines whether the derived callback functions must be implemented thread-safely <a class="spec-record-ref" data-req="SWS_DM_00762" href="../spec/record.html?id=SWS_DM_00762">[SWS_DM_00762]</a>.</p>

<h4>Usage Path</h4>
<p>A typical sequence of security authentication comprises offering the service, the seed query, and the validation of the transmitted key:</p>
<ol>
  <li><strong>Offering the service:</strong> The application instantiates the derived class and calls <code>Offer()</code>, thereby authorizing the DM to forward diagnostic requests for the assigned security level <a class="spec-record-ref" data-req="SWS_DM_00766" href="../spec/record.html?id=SWS_DM_00766">[SWS_DM_00766]</a>.</li>
  <li><strong>Requesting a seed:</strong> If the diagnostic tester sends a UDS message requesting a seed (subfunction Request Seed), the DM forwards this call to <code>GetSeed()</code> <a class="spec-record-ref" data-req="SWS_DM_00764" href="../spec/record.html?id=SWS_DM_00764">[SWS_DM_00764]</a>. The method receives the payload record (<code>securityAccessDataRecord</code>), request metadata (<code>metaInfo</code>), and a <code>cancellationHandler</code>. The implementation returns a <code>ara::core::Future</code> that provides the seed as a byte vector. The passed payload remains valid until the associated promise is fulfilled or the operation is canceled <a class="spec-record-ref" data-req="SWS_DM_00764" href="../spec/record.html?id=SWS_DM_00764">[SWS_DM_00764]</a>.</li>
  <li><strong>Verifying the key:</strong> After receiving the key from the tester (subfunction Send Key), the DM calls the <code>CompareKey()</code> method <a class="spec-record-ref" data-req="SWS_DM_00765" href="../spec/record.html?id=SWS_DM_00765">[SWS_DM_00765]</a>. The key to be verified is passed as <code>ara::core::Span</code>. The application validates the key asynchronously and reports the result back via <code>ara::core::Future&lt;KeyCompareResultType&gt;</code>.</li>
  <li><strong>Stopping the service:</strong> If the interface is to be deactivated, the application calls <code>StopOffer()</code>, whereby the DM delivers no further requests <a class="spec-record-ref" data-req="SWS_DM_00767" href="../spec/record.html?id=SWS_DM_00767">[SWS_DM_00767]</a>.</li>
</ol>

<h4>Error Scenarios</h4>
<p>Errors can occur during modeling, during service provision, and during the execution of the authentication methods:</p>
<ul>
  <li><strong>Modeling and instantiation errors:</strong> Violations can be triggered during constructor call <a class="spec-record-ref" data-req="SWS_DM_00762" href="../spec/record.html?id=SWS_DM_00762">[SWS_DM_00762]</a>:
    <ul>
      <li><code>InstanceSpecifierMappingIntegrityViolation</code>: The <code>InstanceSpecifier</code> cannot be resolved in the process context or does not refer to a PortPrototype.</li>
      <li><code>PortInterfaceMappingViolation</code>: The PortPrototype does not refer to a <code>DiagnosticSecurityLevelInterface</code>.</li>
      <li><code>ProcessMappingViolation</code>: No matching modeled process exists for the instance reference.</li>
      <li><code>InstanceSpecifierAlreadyInUseViolation</code>: The <code>InstanceSpecifier</code> is already used by another instance in the running process.</li>
    </ul>
  </li>
  <li><strong>State conflicts when offering:</strong> If <code>Offer()</code> is called while the service is already being offered, the call fails and returns error code <code>DiagOfferErrc::kAlreadyOffered</code> in the result <a class="spec-record-ref" data-req="SWS_DM_00766" href="../spec/record.html?id=SWS_DM_00766">[SWS_DM_00766]</a>.</li>
  <li><strong>Diagnostic errors (NRC):</strong> If seed generation or key comparison cannot be completed regularly, the application signals errors via the returned <code>ara::core::Future</code> using corresponding Negative Response Codes (NRCs according to ISO 14229-1) using <code>DiagUdsNrcErrc</code> (<a class="spec-record-ref" data-req="SWS_DM_00764" href="../spec/record.html?id=SWS_DM_00764">[SWS_DM_00764]</a>, <a class="spec-record-ref" data-req="SWS_DM_00765" href="../spec/record.html?id=SWS_DM_00765">[SWS_DM_00765]</a>).</li>
  <li><strong>Persistent failed attempt counters:</strong> After each failure when changing the security level, the failed attempt counter must be incremented and mandatorily stored persistently to survive resets (<a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_Diagnostics&amp;page=63">AUTOSAR_AP_SWS_Diagnostics §4.1 p. 63</a>).</li>
  <li><strong>Cancellation of conversations:</strong> If a diagnostic conversation terminates prematurely, this can be queried via <code>cancellationHandler.IsCanceled()</code> or monitored via <code>SetNotifier</code> (<a class="spec-record-ref" data-req="SWS_DM_00764" href="../spec/record.html?id=SWS_DM_00764">[SWS_DM_00764]</a>, <a class="spec-record-ref" data-req="SWS_DM_00765" href="../spec/record.html?id=SWS_DM_00765">[SWS_DM_00765]</a>).</li>
</ul>
