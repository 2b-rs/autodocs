Serves to provide and validate seed and key values for diagnostic security accesses.

The class ara::diag::SecurityAccess serves the application-specific implementation of diagnostic security accesses according to UDS Service 0x27 ([SWS_DM_00762]). After activation via Offer(), the handler receives requests for seed provision and validates transmitted key values asynchronously ([SWS_DM_00766]). As an uncopyable and unmovable instance, the interface requires explicit configuration of the concurrency behavior in the constructor, while processing errors are reported to the diagnostic system via standardized UDS return codes ([SWS_DM_00765]).

Context

The class ara::diag::SecurityAccess represents the interface for implementing UDS Service 0x27 (SecurityAccess) in AUTOSAR Adaptive. It acts as a link between the internal Diagnostic Management (DM) and the application-specific authentication logic of an adaptive application. When an external diagnostic tester requests a security-relevant diagnostic operation, it transmits corresponding diagnostic messages according to ISO 14229-1 to the vehicle (AUTOSAR_AP_SWS_Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”). Diagnostic Management receives these requests and forwards the seed request and key comparison to the registered instance of ara::diag::SecurityAccess ([SWS_DM_00766]).

Context diagram: Classification of ara::diag::SecurityAccess between diagnostic tester, Diagnostic Management, and application. Sources: [SWS_DM_00762], [SWS_DM_00766], AUTOSAR_AP_SWS_Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”

Lifecycle

Instantiation is performed via the constructor by specifying an ara::core::InstanceSpecifier as well as the concurrency behavior concurrencyType ([SWS_DM_00762]). The instance identifier links the object to a port prototype, which must be typed by a DiagnosticSecurityLevelInterface ([SWS_DM_00762]). The parameter concurrencyType definitively defines whether the method calls must be processed in a thread-safe (kConcurrent) or non-thread-safe (kNotConcurrent) manner ([SWS_DM_00762]).

In terms of ownership semantics, the class is designed as a single instance: both copy constructor ([SWS_DM_01617]) and copy assignment operator ([SWS_DM_01615]) as well as move constructor ([SWS_DM_01618]) and move assignment operator ([SWS_DM_01616]) are deleted (=delete). After creation, the instance is in an inactive state until it is registered with the DM via Offer() ([SWS_DM_00766]). Prior to termination, StopOffer() disables the forwarding of requests ([SWS_DM_00767]). Interpretation: StopOffer() is likely always to be called before the object is destroyed by the virtual destructor ([SWS_DM_00763]) in order to ensure that ongoing requests are deregistered with the DM.

Usage Path

The typical usage sequence of a derived handler implementation comprises the following steps:

  1. Activation: The application instantiates the derived class and calls Offer() to enable the forwarding of diagnostic requests by the DM ([SWS_DM_00766]).
  2. Seed provision: If a diagnostic request for seed generation arrives, the DM calls the method GetSeed ([SWS_DM_00764]). The application processes the passed securityAccessDataRecord, takes into account the cancellationHandler, and returns the calculated seed asynchronously via a ara::core::Future<ara::core::Vector<std::uint8_t>> ([SWS_DM_00764]). The buffer of the passed data span remains valid until the promise is fulfilled or until cancellation ([SWS_DM_00764]).
  3. Key validation: As soon as the diagnostic tester transmits the calculated key, the DM calls CompareKey ([SWS_DM_00765]). The application checks the parameter key and transmits the result asynchronously via a ara::core::Future<KeyCompareResultType> ([SWS_DM_00765]).
  4. Deactivation: To terminate diagnostic operation, the application calls StopOffer() ([SWS_DM_00767]).

Sequence diagram: Interaction cycle from activation via GetSeed and CompareKey through to deactivation. Sources: [SWS_DM_00764], [SWS_DM_00765], [SWS_DM_00766], [SWS_DM_00767]

Error Scenarios

When using ara::diag::SecurityAccess, several error levels are specified:

  • Constructor and model violations: If the InstanceSpecifier cannot be resolved in the model or does not reference a PortPrototype, an InstanceSpecifierMappingIntegrityViolation is reported ([SWS_DM_00762]). If the referenced port is not typed by a DiagnosticSecurityLevelInterface, an PortInterfaceMappingViolation is present ([SWS_DM_00762]). If the matching modeled process is missing at runtime, an ProcessMappingViolation occurs, and in case of multiple uses of the same identifier within the process, an InstanceSpecifierAlreadyInUseViolation is triggered ([SWS_DM_00762]).
  • State error during offer: A renewed call to Offer() while the service offer is already active fails and returns the error DiagOfferErrc::kAlreadyOffered with rollback semantics ([SWS_DM_00766]).
  • Negative UDS responses: If the generation of the seed or the key verification fails, the application must report an appropriate Negative Response Code (NRC) in accordance with ISO 14229-1 via DiagUdsNrcErrc ([SWS_DM_00764], [SWS_DM_00765]).
  • Cancellation of the diagnostic connection: Via the parameter cancellationHandler, the application can use IsCanceled() to check whether the conversation was cancelled, or register a notification function for a cancellation via SetNotifier() ([SWS_DM_00764], [SWS_DM_00765]).
  • Persisting failed attempts: After each failed attempt to change the security level, Diagnostic Management requires persistent storage of the counter in order to survive tampering or resets (AUTOSAR_AP_SWS_Diagnostics §4.1 “Limitations of sub-functions of 0x19 ReadDTCInformation”, [SWS_DM_00479]).

use

The pure virtual method CompareKey from class ara::diag::SecurityAccess [SWS_DM_00765] is implemented application-side to validate the key transmitted by the client in UDS service 0x27 (SecurityAccess) SWS Diagnostics §7.3.2.8.9 “Service 0x27 – SecurityAccess”. Together with GetSeed, it forms the basis for the static seed-key mechanism according to ISO 14229-1 [SWS_DM_00863].

The parameters of the function include:

  • key: A ara::core::Span<const std::uint8_t> to the key data to be verified. The buffer remains valid until the associated promise is fulfilled or processing is canceled via cancellationHandler [SWS_DM_00765].
  • metaInfo: Meta-information of the incoming diagnostic request [SWS_DM_00765].
  • cancellationHandler: Enables querying a cancellation via cancellationHandler.IsCanceled as well as registering a notification function via cancellationHandler.SetNotifier upon cancellation of conversation [SWS_DM_00765].

The check result is provided asynchronously via ara::core::Future<KeyCompareResultType> [SWS_DM_00765].

Error Handling and Interaction

If key comparison fails or an error occurs during processing, an appropriate Negative Response Code (NRC) in accordance with ISO 14229-1 must be passed via the future using DiagUdsNrcErrc [SWS_DM_00765]. If the requested sub-function is not configured for CompareKey, the request is answered with NRC 0x12 (kSubFunctionNotSupported) [SWS_DM_00363]. The Diagnostic Server counts failed attempts [SWS_DM_00270] and compares them with threshold values [SWS_DM_00271].

If security access is successfully unlocked, the server updates the security level internally [SWS_DM_00846], resets the failed attempt counter [SWS_DM_00270], and reports the security event SEV_UDS_SECURITY_ACCESS_SUCCESSFUL to the IdsM [SWS_DM_02019].

Concurrency and Limitations

The interface is declared as noexcept and exception safe [SWS_DM_00765]. Thread safety is conditional: whether the implementation must be thread-safe is determined via the ConcurrencyType passed in the constructor of SecurityAccess [SWS_DM_00765].

              use
              

              
The explicit constructor initializes an instance of ara::diag::SecurityAccess synchronously and exception-safely ([SWS_DM_00762]). As parameters, it takes a reference to a ara::core::InstanceSpecifier as well as a ConcurrencyType. The parameter specifier must reference a modeled PortPrototype that is typed by a DiagnosticSecurityLevelInterface. Via concurrencyType, it is defined whether the callback methods of the interface are processed concurrently (kConcurrent) or non-concurrently (kNotConcurrent).

                • 

              • PortInterfaceMappingViolation: The referenced PortPrototype is not typed as DiagnosticSecurityLevelInterface.
                • 

              • ProcessMappingViolation: No matching modeled process exists at runtime for the instance identifier.
                • 

              • InstanceSpecifierAlreadyInUseViolation: The InstanceSpecifier is already being used within the process.
