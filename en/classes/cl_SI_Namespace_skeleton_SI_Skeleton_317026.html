intended use

<SI-Namespace>::skeleton::<SI>Skeleton is the skeleton base class generated by the generation toolchain from the service interface model in the ARXML manifest. The SI hierarchical namespace and class name are derived from the manifest; the generated header follows the <SiShortname>_skeleton.h path [SWS_CM_00002] derived in the model. A custom service implementation inherits from this class and overrides the pure virtual service methods or fire-and-forget methods [SWS_CM_00191] [SWS_CM_90434].

Generation & destruction

The derived implementation can create the skeleton with ara::core::InstanceSpecifier, a single InstanceIdentifier, or an identifier container; By default, the processing mode is kEvent [SWS_CM_00152] [SWS_CM_00130] [SWS_CM_00153]. The virtual destructor allows destruction via the base class [SWS_CM_11370].

Lifecycle & Ownership

Copying is prohibited [SWS_CM_00134] [SWS_CM_11548]. Move construction and move assignment are present; the construction is not exception-safe, but the assignment is exception-safe [SWS_CM_00135] [SWS_CM_11549].

Interaction with other classes

  • After instantiation, OfferService() offers the service; StopOfferService() is ending the offer [SWS_CM_00101] [SWS_CM_00111].
  • For each model event, there is a member events::<Event>; the implementation sends values through skeleton::events::<Event>::Send [SWS_CM_99557] [SWS_CM_00162].
  • For each field there is a member fields::<Field>; Field values are updated via skeleton::fields::<Field>::Update [SWS_CM_99558] [SWS_CM_00119].
  • Modes kEvent, kEventSingleThread, and kPoll control the handling of incoming method calls [SWS_CM_00301]. With kPoll, ProcessNextMethodCall() executes the next waiting call in the context of this function [SWS_CM_00199].

Limitations & Error handling

OfferService() may fail due to uninitialized field values, missing field set handler, or communication error [SWS_CM_00101]. An E2E error handler can be overridden but is not reentrant; In the case of CRC errors, the DataID passed is not reliable [SWS_CM_10470]. Transport error handlers can be registered and removed for all methods [SWS_CM_00093] [SWS_CM_00094] [SWS_CM_00095].

Architectural embedding

The skeleton is the generated adapter on the provider side: The service implementation is typically derived from it and thus provides its methods, events and fields via communication management. The interface is generated from the service interface description; The underlying modeling allows events, fields, methods and triggers in a service interface. EXP ARAComAPI §4.1 “Proxy/Skeleton Architecture” TPS Manifest §4.2 “Service Interface”

Offering and method processing

Before OfferService(), the instance is not visible to consumers. After the call, methods may already be delivered, even if the call has not yet returned; After StopOfferService() no further calls will be delivered. The processing mode selected when creating it applies throughout the lifetime of the skeleton instance. Implementation may be overridden by the actual ServiceSkeleton implementation and it is not required to be reentrant. If the E2E error is a CRC error then some parts of the received message are faulty. If this part is the DataID then the E2E error handler is called with a faulty DataID. Consequently, in case of CRC error the server application can not rely on the DataID received by its error handler.

function ProcessNextMethodCall [SWS_CM_00199] Upstream: RS_CM_00211, RS_AP_00114, RS_AP_00120, RS_AP_00127, RS_AP_00128, RS_AP_00138

bool ProcessNextMethodCall () noexcept;

Allows the service to trigger the execution of the next service consumer method call at a specific point of time if the ara::com::MethodCallProcessingMode == kPoll The pending service method (see [SWS_CM_00191] or [SWS_CM_90434]) is executed in the context of the call to ProcessNextMethodCall().

Usage AI generated

Automatically generated usage notice, derived in substance from the referenced AUTOSAR R25-11 documents — not official AUTOSAR text.

The noexcept method <SI-Namespace>::skeleton::<SI>Skeleton::ProcessNextMethodCall allows targeted triggering of execution of the next pending service-consumer method call, provided the skeleton was constructed with ara::com::MethodCallProcessingMode::kPoll; the pending method is executed in the calling context of ProcessNextMethodCall() [SWS_CM_00199]. The method is exception-safe.

Return value

The bool value returned is TRUE if there was at least one call pending, and FALSE if there was no call pending.

Concurrency & restrictions

If the contract is violated, the implementation throws a WrongMethodCallProcessingModeViolation if the skeleton was not constructed with MethodCallProcessingMode::kPoll.

ProcessNextMethodCall() is the explicit call in mode kPoll. It processes at most one waiting call and uses the return value to report whether there are any further calls pending; This allows a cyclically activated application to control its own time budget. EXP ARAComAPI §5.4.5.1 “Polling Mode”
