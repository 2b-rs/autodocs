The Adaptive Platform in one sentence

The AUTOSAR Adaptive Platform is a service-oriented runtime environment for high-performance vehicle computers: Adaptive Applications run as independent POSIX processes, are started and supervised dynamically, and communicate through contractually defined services rather than statically wired signals (EXP PlatformDesign §3.3 “Adaptive Platform – Characteristics”, §8.2 “Service Oriented Communication”).

ARA — the programming interface of this reference

All ara::* namespaces documented here together form the ARA interface (AUTOSAR Runtime for Adaptive Applications). Each functional cluster of the platform exports its C++ API in its own namespace - from the basic types in ara::core to the service communication in ara::com to platform services such as ara::exec, ara::per or ara::crypto (EXP PlatformDesign §4.1 “Logical view”, EXP SWArchitecture §9.1 “Building Block View – Overview”).

Overarching concepts

  • Machine & Software Cluster:A Machine is the (possibly virtualized) execution environment; Software is packaged as an installable Software Cluster and updated via ara::ucm (EXP SWArchitecture §13.4 “Software Cluster”, §13.5 “Machine”).
  • Function Groups & States: Processes are assigned to function groups; ara::sm uses function group states to instruct execution management to start/stop processes (EXP SWArchitecture §13.2 “Function Group”, EXP PlatformDesign ch. 7 “State Management”).
  • Manifests: Execution, service instance and machine manifest configure deployment, startup behavior and service binding declaratively (EXP PlatformDesign §4.4 “Manifest”, EXP SWArchitecture §13.6 “Manifest”).
  • Error handling without exceptions: Platform-wide errors are returned as ara::core::Result/ErrorCode (EXP PlatformDesign §18.1 “Error Handling”, EXP SWArchitecture §13.12 “Error Handling”).
  • Safety & Security as a cross-section: E2E protection, health monitoring (ara::phm), crypto stack, identity & Access management, intrusion detection (ara::idsm) and firewall (ara::fw) secure the platform and communication (EXP PlatformDesign ch. 17 “Safety”, EXP SWArchitecture §13.13 “Trusted Platform”).

API visibility for applications

Not every specification element documented here is part of the public ARA API: The SWS documents indicate in their Chapter 5 (“Dependencies to other Functional Clusters”, Table 5.1 in each case) which interfaces are exclusively provided to other Functional Clusters. This reference makes this consistently visible in the background color of the respective module, namespace and class name - on the page of each element (page header and label on the right in the navigation bar), in all references to the element in parent pages and on the linked nodes of the diagrams. By default, the backgrounds are very pale to ensure good readability and become a little more intense when mouseover:

  • APPLICATION Blue: can be used directly by Adaptive Applications - e.g. B. ara::core, ara::com, ara::log, ara::per, ara::crypto, ara::diag, ara::rds, ara::shwa (runs as a library in the application process, SWS SHWA ch. 1), ara::tsync (active and passive Time base usage, SWS TSync §2.2) and ara::idsm (applications as security sensors, SWS IdsM §7.2). ara::exec::ExecutionClient also belongs here, but can only report its own process status [SWS_EM_01401].
  • PRIVILEGED Red: only for dedicated applications authorized via IAM or manifest mapping; the authorized user is in brackets in the navigation line. Examples: the PackageManagement-Service of ara::ucm (“UCM Client” = e.g. OTA client or diagnostic application, SWS UCM §7.1), the StateMachine-Services of ara::sm for an SM control application [SWS_SM_00600], the Suspend-to-RAM API ara::sm::s2r (IAM-authenticated satellites only with SuspendToRamSatelliteMapping, [SWS_SM_00715]) and ara::fw (state change only with AdaptiveFirewallToPortPrototypeMapping, [AP_SWS_Fw_40013]).
  • INTERNAL Dark gray: purely cluster-internal interfaces, certainly not for applications; The functional cluster being used is in brackets in the navigation line. Examples: ara::exec::StateClient including FunctionGroup/FunctionGroupState (only for state management, SWS EM Tab. 5.1), the entire module ara::nm (service interface for applications removed, network requests run via state management, SWS NM §4.1 and Tab. 5.1), ara::phm::RecoveryAction (SWS PHM Tab. 5.1) and all apext::* interfaces of the normative appendices “Platform Extension Interfaces” (platform integration towards basic software: Watchdog, Power, UDS transport, Freshness Value Manager, Trace/ARTI).

Aggregate pages (modules, namespaces) with mixed content carry the keyword of the majority of their sub-elements and list the exceptions in parentheses, e.g. B. APPLICATION (Except INTERNAL StateClient, …). The color scheme can be changed centrally in the visibility block of style.css: the color values ​​via --vis-app-rgb (blue), --vis-priv-rgb (red) and --vis-internal-rgb (dark gray), the paleness of the backgrounds via --vis-bg-alpha (standard) and --vis-bg-alpha-hover (mouseover).

Interpretation: The color classification is a classification of the AI based on tables 5.1, the usage chapter (Chapter 7) and the appendices of the respective SWS; the standards themselves do not provide such element-by-element classification. Companion types (error domains, exceptions, handles) have been mapped to the visibility of their main interface.

Interpretation: The grouping of the modules in this overview (base, runtime, communication, storage, security, diagnostics) follows the building block structure of the architecture documentation and is not a normative classification of the standards.
