Role and system context of the service interface

The service interface UpdateRequest serves as a standardized interaction bridge between the functional cluster State Management (SM) and Update and Configuration Management (UCM) on the AUTOSAR Adaptive Platform AUTOSAR_AP_SWS_StateManagement §9.2 “Provided Service Interfaces”. In this architectural context, State Management acts as a server or service provider via a provided port [SWS_SM_91016], whereas UCM acts as a service consumer. The purpose of the interface is to coordinate updates of software clusters—including installation, update, and uninstallation—in a controlled manner with the system and function group states of the machine [SWS_SM_91017].

Methods and Fields of the Service Interface

The service interface UpdateRequest comprises six methods and one field for status monitoring. With the exception of the machine reset, all methods have synchronous client-server semantics (Fire & Forget: false), so that the caller waits for execution or confirmation by State Management:

  • RequestUpdateSession(): Initiates an update session without parameters; is rejected if the system is not updatable or a session is already running [SWS_SM_91102].
  • PrepareUpdate(IN FunctionGroupListType functionGroupList): Prepares the function groups of the affected software cluster for the update [SWS_SM_91103] [SWS_SM_00206].
  • VerifyUpdate(IN FunctionGroupListType functionGroupList): Verifies the updated function groups after preparation [SWS_SM_91104].
  • PrepareRollback(IN FunctionGroupListType functionGroupList): Prepares the rollback of the specified function groups if an update fails [SWS_SM_91105].
  • ResetMachine(): Triggers a restart of the machine; this is a fire-and-forget method (Fire & Forget: true) [SWS_SM_91100]. Before the reset, all relevant information must be persisted.
  • StopUpdateSession(): Closes the active update session and signals a stable machine state again to State Management [SWS_SM_91101] [SWS_SM_00205].
  • ResetMachineNotifier: A field of type UpdateStatusType with getter and notifier (no setter), via which UCM can track the status during and after the execution of ResetMachine() [SWS_SM_91106] [SWS_SM_00211].

Lifecycle, session sequences, and state dependencies

The interaction strictly requires an active update session. UCM must first call RequestUpdateSession() before subsequent operations are permitted AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”. State Management persists information about an ongoing update session so that UCM can consistently resume the process even after a planned or unplanned machine reset [SWS_SM_00204]. After a restart via ResetMachine(), State Management transitions to state ContinueUpdate, where UCM must be in a runnable state to synchronize again via ResetMachineNotifier AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”.

Within the session, the sub-steps depend on one another: VerifyUpdate() strictly requires a previously successful call to PrepareUpdate() [SWS_SM_91104]. Depending on whether software clusters are installed, deleted, or updated, UCM executes the corresponding steps AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”. Once all changes are completed, StopUpdateSession() terminates the process [SWS_SM_00205].

Error handling and Application Errors

The methods of UpdateRequest define specific application errors (Application Errors) to signal unauthorized calls or internal error states:

  • kOperationRejected: Returned by all methods if the request is not permitted due to the current internal state of State Management or the machine [SWS_SM_91102]. In particular, calls to PrepareUpdate, VerifyUpdate, PrepareRollback, or StopUpdateSession return this error if they occur outside an active update session [SWS_SM_00213].
  • kNotAllowedMultipleUpdateSessions: Occurs exclusively with RequestUpdateSession(), since only a single active update session may exist concurrently on a machine at any given time [SWS_SM_91102].
  • kOperationFailed: Indicates in PrepareUpdate, VerifyUpdate, and PrepareRollback that the requested preparation or verification operation on the function groups failed [SWS_SM_91103] [SWS_SM_91104] [SWS_SM_91105].

use

The service method PrepareRollback [SWS_SM_91105] is called via the service interface UpdateRequest by Update and Configuration Management (UCM) after State Management has agreed to the update and previous update steps have failed SWS StateManagement §7.x “ResetMachine notification”. Since PrepareRollback is not defined as fire-and-forget, the call is performed with synchronous confirmation or error transmission [SWS_SM_91105]. As an input parameter, functionGroupList of type FunctionGroupListType is passed, which specifies the list of function groups within the software cluster that are to be prepared for rollback [SWS_SM_91105].

Error handling

The specification provides specific return errors for the method [SWS_SM_91105]:

  • kOperationRejected: The request is rejected due to the internal state of State Management or its state machines [SWS_SM_91105]; this is mandatorily the case if the call occurs outside of an active update session [SWS_SM_00213].
  • kOperationFailed: Occurs if the rollback preparation fails [SWS_SM_91105]. Errors during the update session are reported to UCM [SWS_SM_00644].

Interaction and State Control

During the execution of PrepareRollback, the controlling process of the controller state machine marks each state machine as ImpactedByUpdate provided that at least one of the function groups managed by it is contained in the parameter functionGroupList [SWS_SM_00654]. If an agent state machine is marked, the controller state is transitively set to ImpactedByUpdate as well [SWS_SM_00655]. A state machine marked in this way ignores recovery requests upon execution errors and merely logs the event [SWS_SM_00664]. Furthermore, the method corresponds to the mandatory state PrepareRollback that each state machine in State Management must exhibit SWS StateManagement §7.7.1 “StateMachine introduction”.

              The service method ResetMachine() is called by Update and Configuration Management (UCM) via the service interface UpdateRequest to request a controlled restart of the machine during an ongoing update session ([SWS_SM_91100]).
              

  
              Usage and Semantics
              
  
              The method has no parameters and is specified with Fire & Forget ([SWS_SM_91100]). Prior to executing the reset, State Management (SM) persists all relevant state information about the ongoing update session so that the update can be consistently continued after the machine restarts ([SWS_SM_00204], AUTOSAR_AP_SWS_StateManagement, p. 31).
              

  
              State Transitions and Interaction
              
  
                
    
              • State transition: When calling ResetMachine, the controlling process transitions the StateMachine of type Controller into the state Restart ([SWS_SM_00658]). After the restart and completion of the startup sequence, the transition into state ContinueUpdate occurs in State Management (AUTOSAR_AP_SWS_StateManagement, p. 33).
                • 
    
              • Status notification: Since the method operates asynchronously without direct return values, UCM and State Management synchronize via the notifier field ResetMachineNotifier in interface UpdateRequest ([SWS_SM_00211], [SWS_SM_91106], AUTOSAR_AP_EXP_SWArchitecture, p. 53). The initial value of the field is kIdle ([SWS_SM_00212]).
                • 
  
              

  
              Restrictions and Error Handling
              
  
              The call requires an update session previously initiated successfully via RequestUpdateSession. If the call occurs outside of an active session, the request is rejected and returns the application error kOperationRejected ([SWS_SM_91100]). In addition, the controlling process sets the field ResetMachineNotifier to kRejected in this error case ([SWS_SM_00661]).

The service interface <code>UpdateRequest</code> serves as a standardized interaction bridge between the functional cluster <em>State Management</em> (SM) and <em>Update and Configuration Management</em> (UCM) on the AUTOSAR Adaptive Platform <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=137">AUTOSAR_AP_SWS_StateManagement §9.2 “Provided Service Interfaces”</a>. In this architectural context, State Management acts as a server or service provider via a provided port <a class="spec-record-ref" data-req="SWS_SM_91016" href="../spec/record.html?id=SWS_SM_91016">[SWS_SM_91016]</a>, whereas UCM acts as a service consumer. The purpose of the interface is to coordinate updates of software clusters—including installation, update, and uninstallation—in a controlled manner with the system and function group states of the machine <a class="spec-record-ref" data-req="SWS_SM_91017" href="../spec/record.html?id=SWS_SM_91017">[SWS_SM_91017]</a>.
</p>

<h4>Methods and Fields of the Service Interface</h4>
<p>
The service interface <code>UpdateRequest</code> comprises six methods and one field for status monitoring. With the exception of the machine reset, all methods have synchronous client-server semantics (<code>Fire &amp; Forget: false</code>), so that the caller waits for execution or confirmation by State Management:
</p>
<ul>
<li><code>RequestUpdateSession()</code>: Initiates an update session without parameters; is rejected if the system is not updatable or a session is already running <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a>.</li>
<li><code>PrepareUpdate(IN FunctionGroupListType functionGroupList)</code>: Prepares the function groups of the affected software cluster for the update <a class="spec-record-ref" data-req="SWS_SM_91103" href="../spec/record.html?id=SWS_SM_91103">[SWS_SM_91103]</a> <a class="spec-record-ref" data-req="SWS_SM_00206" href="../spec/record.html?id=SWS_SM_00206">[SWS_SM_00206]</a>.</li>
<li><code>VerifyUpdate(IN FunctionGroupListType functionGroupList)</code>: Verifies the updated function groups after preparation <a class="spec-record-ref" data-req="SWS_SM_91104" href="../spec/record.html?id=SWS_SM_91104">[SWS_SM_91104]</a>.</li>
<li><code>PrepareRollback(IN FunctionGroupListType functionGroupList)</code>: Prepares the rollback of the specified function groups if an update fails <a class="spec-record-ref" data-req="SWS_SM_91105" href="../spec/record.html?id=SWS_SM_91105">[SWS_SM_91105]</a>.</li>
<li><code>ResetMachine()</code>: Triggers a restart of the machine; this is a fire-and-forget method (<code>Fire &amp; Forget: true</code>) <a class="spec-record-ref" data-req="SWS_SM_91100" href="../spec/record.html?id=SWS_SM_91100">[SWS_SM_91100]</a>. Before the reset, all relevant information must be persisted.</li>
<li><code>StopUpdateSession()</code>: Closes the active update session and signals a stable machine state again to State Management <a class="spec-record-ref" data-req="SWS_SM_91101" href="../spec/record.html?id=SWS_SM_91101">[SWS_SM_91101]</a> <a class="spec-record-ref" data-req="SWS_SM_00205" href="../spec/record.html?id=SWS_SM_00205">[SWS_SM_00205]</a>.</li>
<li><code>ResetMachineNotifier</code>: A field of type <code>UpdateStatusType</code> with getter and notifier (no setter), via which UCM can track the status during and after the execution of <code>ResetMachine()</code> <a class="spec-record-ref" data-req="SWS_SM_91106" href="../spec/record.html?id=SWS_SM_91106">[SWS_SM_91106]</a> <a class="spec-record-ref" data-req="SWS_SM_00211" href="../spec/record.html?id=SWS_SM_00211">[SWS_SM_00211]</a>.</li>
</ul>

<h4>Lifecycle, session sequences, and state dependencies</h4>
<p>
The interaction strictly requires an active update session. UCM must first call <code>RequestUpdateSession()</code> before subsequent operations are permitted <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=31">AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”</a>. State Management persists information about an ongoing update session so that UCM can consistently resume the process even after a planned or unplanned machine reset <a class="spec-record-ref" data-req="SWS_SM_00204" href="../spec/record.html?id=SWS_SM_00204">[SWS_SM_00204]</a>. After a restart via <code>ResetMachine()</code>, State Management transitions to state <code>ContinueUpdate</code>, where UCM must be in a runnable state to synchronize again via <code>ResetMachineNotifier</code> <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=33">AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”</a>.
</p>
<p>
Within the session, the sub-steps depend on one another: <code>VerifyUpdate()</code> strictly requires a previously successful call to <code>PrepareUpdate()</code> <a class="spec-record-ref" data-req="SWS_SM_91104" href="../spec/record.html?id=SWS_SM_91104">[SWS_SM_91104]</a>. Depending on whether software clusters are installed, deleted, or updated, UCM executes the corresponding steps <a class="docref internal-spec-ref" href="../spec/record.html?doc=AUTOSAR_AP_SWS_StateManagement&amp;page=32">AUTOSAR_AP_SWS_StateManagement §7.7 “Update Handling”</a>. Once all changes are completed, <code>StopUpdateSession()</code> terminates the process <a class="spec-record-ref" data-req="SWS_SM_00205" href="../spec/record.html?id=SWS_SM_00205">[SWS_SM_00205]</a>.
</p>

<h4>Error handling and Application Errors</h4>
<p>
The methods of <code>UpdateRequest</code> define specific application errors (Application Errors) to signal unauthorized calls or internal error states:
</p>
<ul>
<li><code>kOperationRejected</code>: Returned by all methods if the request is not permitted due to the current internal state of State Management or the machine <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a>. In particular, calls to <code>PrepareUpdate</code>, <code>VerifyUpdate</code>, <code>PrepareRollback</code>, or <code>StopUpdateSession</code> return this error if they occur outside an active update session <a class="spec-record-ref" data-req="SWS_SM_00213" href="../spec/record.html?id=SWS_SM_00213">[SWS_SM_00213]</a>.</li>
<li><code>kNotAllowedMultipleUpdateSessions</code>: Occurs exclusively with <code>RequestUpdateSession()</code>, since only a single active update session may exist concurrently on a machine at any given time <a class="spec-record-ref" data-req="SWS_SM_91102" href="../spec/record.html?id=SWS_SM_91102">[SWS_SM_91102]</a>.</li>
<li><code>kOperationFailed</code>: Indicates in <code>PrepareUpdate</code>, <code>VerifyUpdate</code>, and <code>PrepareRollback</code> that the requested preparation or verification operation on the function groups failed <a class="spec-record-ref" data-req="SWS_SM_91103" href="../spec/record.html?id=SWS_SM_91103">[SWS_SM_91103]</a> <a class="spec-record-ref" data-req="SWS_SM_91104" href="../spec/record.html?id=SWS_SM_91104">[SWS_SM_91104]</a> <a class="spec-record-ref" data-req="SWS_SM_91105" href="../spec/record.html?id=SWS_SM_91105">[SWS_SM_91105]</a>.</li>
</ul>
